Введение в kernel pwn — это переход от эксплуатации userland-процессов к эксплуатации ядра Linux. Ядро — привилегированный код с доступом ко всей памяти, поэтому успешная атака даёт root (или обход всех защит). Задачи kernel pwn обычно построены вокруг уязвимого модуля (LKM), символьного устройства или системного вызова, доступного непривилегированному пользователю. Типичные баги — переполнения, UAF, произвольное чтение/запись в ядерных структурах. В этом уроке — базовые приёмы: ret2usr, modprobe_path, msg_msg, устройство `/dev`-модуля, работа с KASLR/SMEP/SMAP и практические сценарии.

## Модель угроз и окружение

В kernel pwn предполагается, что злоумышленник — непривилегированный пользователь, а цель — повышение до root (часто с чтением `/flag`). Типичное задание: загружен уязвимый LKM, создающий `/dev/vuln`, через который можно вызвать `read`/`write`/`ioctl`. Модуль имеет баг (переполнение, UAF, OOB), эксплуатируя который вы получаете контроль над ядром. Защиты: **KASLR** (рандомизация ядра), **SMEP** (запрет исполнения user-страниц в ядре), **SMAP** (запрет доступа к user-памяти из ядра), **KPTI** (изоляция таблиц страниц), **FGKASLR**, **CFI**. Проверяются через `/proc/cpuinfo`, `/sys/devices/system/cpu/vulnerabilities/`, конфиг ядра.

## Сборка окружения для отладки

Для локальной разработки используют QEMU с ядром и initramfs:

```bash
# запуск уязвимого ядра под QEMU с gdb
qemu-system-x86_64 \
  -m 256M -nographic \
  -kernel ./bzImage \
  -initrd ./rootfs.cpio.gz \
  -append "console=ttyS0 kaslr oops=panic panic=1 nokaslr" \
  -s -S
```

Флаг `-s` открывает gdb-сервер на порту 1234, `-S` останавливает CPU до подключения отладчика. Подключение: `gdb ./vmlinux -ex 'target remote :1234'`. `nokaslr` отключает рандомизацию для удобства отладки (в реальном задании KASLR включён). Часто дают `run.sh` с готовой командой — изучайте его.

## Первый взгляд на модуль

Начните с анализа модуля: `file vuln.ko`, `modinfo vuln.ko`, дизассемблирование (`objdump -d` или Ghidra). Ищите функции, зарегистрированные как `file_operations`:

```c
static struct file_operations fops = {
    .read = vuln_read,
    .write = vuln_write,
    .ioctl = vuln_ioctl,
};
```

Далее найдите баг: неверные границы в `copy_from_user`/`copy_to_user`, отсутствие проверки индекса, UAF при `kfree` без зануления, гонки. Посмотрите размеры буферов и структуры, которыми управляет модуль.

## Приём 1: ret2usr

Если SMEP выключен, можно вернуть управление на userland-код: подделав указатель на функцию (например, в структуре модуля) так, чтобы он указывал на вашу функцию в user-памяти, которая вызывает `commit_creds(prepare_kernel_cred(0))` и возвращается. Это классический приём:

```c
void escalate() {
    commit_creds(prepare_kernel_cred(NULL));
}
// в эксплойте: перезаписать указатель на escalate и триггернуть вызов
```

Требует отключённого SMEP/SMAP. При включённых — нужен ROP в ядре (см. `pwn-kernel-rop`).

## Приём 2: modprobe_path

`modprobe_path` — ядерная переменная, содержащая путь к `modprobe` (по умолчанию `/sbin/modprobe`). Если перезаписать её на путь к вашему скрипту и вызвать обработку неизвестного формата файла (через `execve` файла с «магическим» заголовком, который ядро пытается загрузить через `request_module`), ядро выполнит ваш скрипт **от root**. Это простой и мощный приём:

```bash
# эксплойт: записать /tmp/x в modprobe_path
echo -e '#!/bin/sh\nchmod 777 /flag' > /tmp/x
chmod +x /tmp/x
# затем execve файла с неизвестной сигнатурой -> request_module -> /tmp/x от root
```

Приём не требует ROP и работает даже при включённых SMEP/SMAP — нужно лишь произвольно записать в `modprobe_path`.

## Приём 3: msg_msg

`msg_msg` — структура ядерных сообщений (System V IPC). Она размещается в SLUB-кэшах (`kmalloc`) и может использоваться для создания UAF-примитивов: освободив `msg_msg` и переиспользовав память другим объектом, вы получаете перекрытие. `msg_msg` удобна тем, что её размер контролируется, а содержимое — тоже. Техника широко применяется в современных kernel-задачах (например, для перекрытия `tty_struct`, `pipe_buffer`, `seq_operations`). Подробнее — в `pwn-kernel-heap`.

## Практический сценарий: UAF в модуле

Пусть модуль выделяет объект и освобождает его, но оставляет указатель (UAF), а через `ioctl` можно писать в объект. План: (1) определить размер объекта и SLUB-кэш; (2) освободить объект; (3) переиспользовать память другим ядерным объектом (например, `msg_msg` или `tty_struct`) с контролируемым содержимым; (4) через UAF перезаписать указатель на функцию в переиспользованном объекте; (5) триггернуть вызов. Если SMEP включён, используйте ROP-гаджеты в ядре; иначе — ret2usr или `modprobe_path`.

## Защиты и их проверка

```bash
# SMEP/SMAP
grep -oE "smep|smap" /proc/cpuinfo | sort -u
# KASLR
dmesg | grep -i "Kernel Offset"
# KPTI
grep -i pti /sys/devices/system/cpu/vulnerabilities/*
# конфиг ядра
zcat /proc/config.gz | grep -E "CONFIG_SLAB_FREELIST|CONFIG_RANDOMIZE_BASE|CONFIG_SMEP"
```

Знание защит определяет выбор приёма: ret2usr (нужен выключенный SMEP), kernel ROP (при SMEP), modprobe_path (при произвольной записи), msg_msg (для heap-атак).

## Отладка ядра в gdb

```bash
gdb ./vmlinux
(gdb) target remote :1234
(gdb) b commit_creds
(gdb) c
(gdb) p $lx_current()
(gdb) p &modprobe_path
```

Полезны расширения pwndbg/`gef` с kernel-поддержкой (`kbase`, `slub`, `kmalloc`). Символы берутся из `vmlinux` (если он есть) или восстанавливаются из `/proc/kallsyms`.

## Частые ошибки

- **Забыть про KASLR.** Адреса ядра рандомизированы — нужна утечка или `nokaslr` в отладке.
- **SMEP/SMAP.** ret2usr не сработает при включённых защитах.
- **Неверный SLUB-кэш.** Объект может не попасть в нужный кэш из-за размера.
- **Гонки.** Многие kernel-баги — race condition; нужен userfaultfd/FUSE.
- **Паника ядра.** Ошибка в эксплойте «убивает» систему — тестируйте осторожно.

## Полный разбор учебной kernel-задачи

Рассмотрим типичную CTF-задачу kernel pwn целиком, чтобы связать теорию с практикой. Дано: ядро Linux с загруженным модулем `vuln.ko`, устройство `/dev/vuln`, initramfs, `run.sh` для QEMU. Первый шаг — распаковка initramfs (`cpio -idmv < rootfs.cpio.gz`) и изучение скриптов инициализации: там видно, как монтируется `/dev`, какие права, где флаг, включены ли `kptr_restrict` и `dmesg_restrict`. Затем анализируем модуль: `modinfo vuln.ko`, `objdump -d vuln.ko`, Ghidra. Ищем функции `vuln_ioctl`, `vuln_read`, `vuln_write` и их баги. Часто модуль реализует объект с полем-указателем и позволяет освободить его, не зануляя указатель, — классический UAF. Определяем размер объекта (например, `kmalloc(0x20)`), затем планируем переиспользование через `seq_operations`.

## Переиспользование памяти и привязка к CPU

Важная деталь ядерной эксплуатации — per-CPU freelist. SLUB хранит свободные объекты в `kmem_cache_cpu` текущего процессора, поэтому освобождение и последующая аллокация на разных ядрах могут дать разные slab'ы, и переиспользование не сработает. Чтобы стабилизировать эксплойт, привяжите процесс к одному CPU: `sched_setaffinity(0, sizeof(mask), &mask)` с маской, где установлен один бит. Это частая причина «эксплойт работает через раз» в kernel pwn. Кроме того, помогает «прогрев» кэша: перед ключевой операцией выполните несколько аллокаций/освобождений, чтобы нужный slab был активен. Все эти манипуляции выполняйте в одном процессе и на одном CPU.

## Отладка ядра и типичные сообщения

Отладка ведётся через QEMU с `-s -S` и gdb с символам из `vmlinux`. Полезно установить `nokaslr` на время разработки, чтобы адреса были фиксированы, и только в конце проверить с KASLR. В gdb используйте kernel-aware команды pwndbg (`kbase`, `slab`, `kmalloc`), ставьте точки останова на функции модуля (`b vuln_ioctl`) и на ключевые ядерные функции (`b commit_creds`, `b native_write_cr4`). Если ядро паникует, смотрите `dmesg` в QEMU: сообщение вида `BUG: unable to handle kernel paging request` с адресом и регистрами подскажет, где ошибка. Логируйте всё: адреса, значения регистров, содержимое структур.

## Стратегия выбора приёма

Выбор приёма зависит от бага и защит. Если SMEP/SMAP выключены — простой `ret2usr` с `commit_creds`. Если включены, но есть произвольная запись — `modprobe_path` (самый простой). Если есть только контроль RIP — kernel ROP с trampoline. Если баг — heap UAF — переиспользование объектов (`seq_operations`, `msg_msg`, `pipe_buffer`). Если баг — гонка — нужен `userfaultfd`/FUSE для расширения окна. Начинайте с самого дешёвого приёма, соответствующего примитиву, и усложняйте только при необходимости. Так вы экономите время и снижаете риск паники.

## Итоговая мысль

Kernel pwn требует системного подхода: сначала разведка (модуль, защиты, окружение), затем выбор приёма, затем отладка в QEMU. Не пытайтесь сразу писать ROP — начните с простого UAF и переиспользования объекта. Постепенно усложняйте, включая защиты. Записывайте все адреса и смещения, проверяйте каждый шаг в gdb, и вы сможете решать задачи любой сложности.
