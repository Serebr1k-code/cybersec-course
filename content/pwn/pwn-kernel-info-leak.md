## Вопрос, с которого всё начинается

Ты получил примитив чтения в ядре. Но что именно читать? Адреса ядра
рандомизированы KASLR — без базы нельзя вычислить, куда писать. Значит, первый
шаг эксплойта — **утечка**. Откуда в ядре вообще берутся адреса и как их
достать?

## Наш пример

Смотрим на типичный вывод утечки — кусок памяти ядра, прочитанный через
OOB-чтение:

```
$ cat leak.bin | xxd | head
00000000: 0000 0000 0000 0000 ffff 8880 1234 ab00  .............4..
00000010: ffff 8880 1234 ab80 0000 0000 0000 0001  .....4..........
00000020: 0000 0000 0000 0040 ffff ffff 8a2b 1000  .......@.....+..
```

Здесь `ffff 8880 ...` — типичный адрес кучи ядра (`ffff8880...` на x86-64),
а `ffff ffff 8a2b 1000` — адрес в области ядра (`.text`/данные). Уже из этого
дампа видно: утечка даёт **адреса ядра**.

## Шаг 1: откуда берётся неинициализированная память

Ядро часто выделяет объект и **не обнуляет** его. Тогда в нём остаётся
содержимое предыдущего владельца — включая указатели. Если такая память
копируется в userland, мы получаем утечку. Классика:

- `uninitialized stack variable` — локальная переменная не инициализирована,
  копируется в `copy_to_user`.
- `slab object reuse` — освобождённый объект с указателями отдан новому и
  прочитан.

Это самый «дешёвый» тип утечки, но его всё чаще закрывают (`CONFIG_INIT_STACK_ALL`).

## Шаг 2: OOB-чтение как источник

Если есть out-of-bounds чтение (например, через увеличенный `m_ts` у `msg_msg`),
можно прочитать соседние объекты кучи. В них лежат указатели ядра: `m_list`,
`next`, указатели на `file`, `cred`, `task_struct`. Первая утечка обычно даёт
**адрес в куче ядра** — этого достаточно, чтобы узнать, где находится наша
куча, и построить произвольное чтение.

## Шаг 3: от утечки кучи к базе ядра

Адрес кучи (`ffff8880...`) сам по себе не даёт базу ядра (`ffffffff8...`). Чтобы
вычислить базу, нужен указатель в область `.text`/данных ядра. Такие указатели
есть в структурах: например, в `tty_struct` — указатель на `tty_operations` в
секции данных ядра; в `seq_operations` — на функции ядра. Утечка такого
указателя минус известное смещение = база ядра.

Практический приём: спреить объект с «ядерным» указателем рядом с утечкой и
прочитать его. Часто используется `tty_struct` (открываем `/dev/ptmx`).

## Шаг 4: классификация утечек

| Тип | Источник | Что даёт |
|---|---|---|
| Uninit stack | неинициализированная переменная | остатки стека, иногда указатели |
| Uninit heap | переиспользованный объект | указатели кучи/ядра |
| OOB-read | выход за границу буфера | соседние объекты |
| Type confusion | неверная интерпретация | поля чужого объекта |
| Side-channel | prefetch/тайминги | база ядра без чтения |

Последний тип — особый: `prefetch`-атаки (EntryBleed и др.) позволяют вычислить
базу ядра **без** утечки памяти, измеряя время доступа. Это отдельная техника,
разобранная в `pwn-kaslr-bypass`.

## Шаг 5: стабильность утечки

Хорошая утечка — **воспроизводимая**. Плохая практика: полагаться на то, что
«в этот раз повезло». Приёмы стабилизации:

- Повторять утечку много раз и брать значение, которое повторяется.
- Проверять, что адрес похож на ядро (`0xffff...`), иначе повторять.
- Комбинировать несколько источников: если один не сработал, взять другой.

```c
uint64_t leak = 0;
for (int i = 0; i < 100; i++) {
    leak = do_leak();
    if ((leak >> 40) == 0xffffff) break;   // похоже на ядро
}
```

## Шаг 6: что делать с базой

Получив базу ядра, вычисляем адреса целей:
- `modprobe_path` — строка, вызываемая при неизвестном формате; перезапись даёт
  выполнение команды.
- `core_pattern` — похожий трюк.
- `commit_creds`/`prepare_kernel_cred` — для kernel ROP.
- `init_cred` — готовая структура root-прав для data-only атаки.

Без утечки все эти адреса случайны.

## Что мы теперь знаем

- Ядро часто отдаёт неинициализированную память — это источник утечек.
- OOB-чтение читает соседние объекты с указателями ядра.
- Адрес кучи — не база; базу даёт указатель в `.text`/данные.
- Утечки бывают стабильные и «одноразовые»; нужна валидация.
- Side-channel (prefetch) даёт базу без чтения памяти.

## Куда дальше

Дальше — **data-only атаки**: когда и утечка, и запись есть, но перехватывать
поток управления не нужно. А пока запомни: **первый шаг любого kernel-эксплойта
— стабильная утечка адреса, ведущего к базе ядра**.

## Где пригодится

- Обход KASLR в kernel-эксплойтах.
- Аудит утечек: неинициализированная память, OOB.
- Разбор публичных PoC.
