DirtyCred — техника эксплуатации ядра, которая меняет правила игры: вместо захвата потока управления (ROP, ret2usr) атакующий **подменяет объект `cred`** (структуру привилегий) на привилегированный. Это не требует обхода SMEP/SMAP/KPTI, потому что код ядра не меняется — меняется лишь то, «кем» является процесс. Техника формализована в 2022 году и применена к CVE-2022-2588 (cls_route) и CVE-2022-3913 (net/9p).

В этом уроке — устройство `cred`, механика подмены, конкретные CVE и контейнерный escape. Материал завершает модуль `pwn-kernel-modern`.

## Что такое DirtyCred

`struct cred` в ядре описывает привилегии процесса: UID, GID, capabilities, security-контекст. Когда процесс выполняет привилегированную операцию, ядро проверяет его `cred`. Идея DirtyCred: используя UAF или другой примитив, заменить `cred` непривилегированного процесса на `cred` привилегированного (или подделать поля). После этого процесс считается root — без изменения кода.

Преимущества: не нужны ROP/SMEP/KPTI-обходы; эксплойт проще и стабильнее. Недостатки: нужен примитив, позволяющий переиспользовать память под `cred`, и синхронизация.

## Credentials в ядре

| Поле | Смысл |
|---|---|
| usage | счётчик ссылок |
| uid/gid | реальные ID |
| suid/sgid | сохранённые ID |
| euid/egid | эффективные ID |
| fsuid/fsgid | ID для ФС |
| cap_* | capability-наборы |
| security | LSM-контекст |

`cred` аллоцируется из `cred_jar` (собственный slab-кэш) или через `kmalloc`. Это важно: чтобы переиспользовать память под `cred`, нужен cross-cache или совпадение размеров.

## Механика подмены

Схема:

1. Получить примитив, дающий доступ к освобождённой памяти (`cred_jar`).
2. Освободить `cred` (например, завершив процесс или через баг).
3. Аллоцировать привилегированный `cred` так, чтобы он занял ту же память.
4. Через UAF-указатель изменить поля (uid=0, capabilities).
5. Проверить `getuid()` / выполнить привилегированную операцию.

Ключ — «пересадить» привилегированный `cred` в память, к которой у вас есть доступ. В некоторых CVE это делается через объект, чей размер совпадает с `cred`.

## CVE-2022-2588 и CVE-2022-3913

- **CVE-2022-2588 (cls_route).** UAF в net/sched, позволяющий переиспользовать память под `cred`. Эксплойт DirtyCred подменяет cred процесса на root.
- **CVE-2022-3913 (net/9p).** Ещё одна UAF, эксплуатируемая тем же подходом.
- Оба показывают, что «логическая» LPE может не требовать control-flow hijack.

Практический вывод: ищите UAF, где размер объекта совпадает с `cred` (или где можно организовать cross-cache), — это кандидат на DirtyCred.

## Инструменты и команды

```bash
# версия ядра
uname -r

# информация о cred процесса (через /proc)
cat /proc/self/status | grep -E "Uid|Gid|Cap"

# slab-кэш cred
sudo cat /proc/slabinfo | grep cred_jar

# проверка capabilities
capsh --print

# в отладке ядра (gdb + vmlinux)
# p *(struct cred *)task->cred
```

`/proc/self/status` показывает текущие UID/GID и capabilities. `/proc/slabinfo` — размер `cred_jar`, полезно для планирования cross-cache.

## Разобранный пример

Концептуально:

```c
// 1. через UAF получаем доступ к освобождённому объекту размера cred
void *victim = get_uaf();

// 2. спамим привилегированными cred (например, через fork от root-процесса)
for (int i = 0; i < N; i++) spawn_privileged();

// 3. объект victim теперь переиспользован под cred
struct cred *c = (struct cred *)victim;

// 4. проверяем
if (getuid() == 0) win();
```

В реальном эксплойте вы либо напрямую пишете в `cred` через UAF, либо подменяете указатель `task->cred` на подготовленный объект.

## Контейнерный escape

DirtyCred особенно эффективен для выхода из контейнера: получив root внутри контейнера, можно атаковать структуры, общие с хостом (например, через namespace-утечки), и повысить привилегии до хостовых. В CTF это типичная финальная стадия: `root` в контейнере → `root` на хосте.

## Ограничения

- **Нужен UAF.** DirtyCred — не самостоятельная уязвимость, а способ эксплуатации.
- **Размеры должны совпадать.** `cred` имеет фиксированный размер; нужен подходящий кэш.
- **Синхронизация.** Подмена должна произойти до использования cred.
- **Проверки LSM.** Некоторые системы (SELinux/AppArmor) проверяют контекст.

## Сравнение DirtyCred и DirtyPipe

Обе техники называют «Dirty», но они устроены по-разному. Dirty Pipe меняет **данные** (page cache файла), не трогая структуры ядра. DirtyCred меняет **объект привилегий** (`cred`), не трогая файлы. Объединяет их то, что обе обходятся без захвата потока управления и потому не требуют обхода SMEP/SMAP/KPTI.

| Критерий | DirtyPipe | DirtyCred |
|---|---|---|
| Что меняется | page cache файла | struct cred |
| Нужен UAF | нет | да |
| Обход SMEP | не нужен | не нужен |
| Стабильность | высокая | средняя |
| Итог | запись в RO-файл | root в процессе |

Понимание разницы помогает выбрать вектор: если в задаче есть только UAF, смотрите в сторону DirtyCred; если есть доступ к файлам и уязвимое ядро — Dirty Pipe.

## Практика: поиск подходящего UAF

Не любой UAF годится для DirtyCred. Ключевые критерии:

- **Размер объекта** должен совпадать с размером `cred` или позволять cross-cache в `cred_jar`.
- **Окно переиспользования** должно быть достаточно широким, чтобы вы успели «посадить» привилегированный `cred`.
- **Доступ к памяти** должен сохраняться после `free` (UAF-чтение/запись).

На практике ищут объекты в общих `kmalloc`-кэшах, чей размер близок к `cred`. Затем организуют спам привилегированных `cred` (например, через `fork` от процесса с нужными правами) и проверяют `getuid()`. Если не сработало — меняют размер/кэш или используют cross-cache для переноса страницы в `cred_jar`.

## Почему DirtyCred изменил подход к kernel LPE

Традиционная kernel-эксплуатация требовала длинной цепочки: UAF → heap grooming → произвольная запись → обход KASLR → ROP → обход SMEP/SMAP/KPTI → повышение привилегий. Каждый этап хрупок, а защит всё больше. DirtyCred сокращает цепочку: UAF → переиспользование памяти под `cred` → root. Никакого ROP, никаких обходов control-flow защит.

Это смещение парадигмы: вместо «захватить исполнение» атакующий «становится другим пользователем». Защиты от ROP (SMEP, SMAP, CET, shadow stack) против такой атаки бесполезны, потому что они защищают поток управления, а не данные. Отсюда растущая популярность data-only атак в ядре: они проще, стабильнее и невосприимчивы к целому классу митигаций. Ожидайте, что в будущем таких техник будет больше.

## Практика: как проверить успех

Признак успеха прост: `getuid()`/`geteuid()` возвращают 0, либо привилегированная операция (открытие `/etc/shadow`, `mount`, загрузка модуля) проходит. Проверяйте сразу после подмены, не дожидаясь конца программы: `cred` может быть перезаписан ядром.

Если uid остался прежним, возможные причины: подмена не попала в нужный объект (неверный размер/кэш), `cred` был immutable, либо сработал LSM. Попробуйте другой кэш/размер, другой момент подмены или иной примитив. Логируйте, какой объект вы переиспользовали и что прочитали через UAF — это покажет, попали ли вы в `cred`.

Для повышения стабильности используйте многократные попытки: подмена `cred` — гонка, и не каждая попытка успешна. Оборачивайте в цикл с перезапуском, проверяя `getuid()` после каждой. Если после сотен попыток результата нет, скорее всего, выбранный UAF не подходит под размер `cred` — тогда переходите к cross-cache или другому объекту-цели (например, `pipe_buffer` для произвольной записи). Не зацикливайтесь на одной цели: в kernel-эксплуатации гибкость важнее упорства, а выбор объекта-цели часто определяет успех всей атаки.

## Итог и что запомнить

DirtyCred — data-only атака: вместо захвата исполнения она подменяет `struct cred`, делая процесс привилегированным. Она не требует обхода SMEP/SMAP/KPTI, потому что не меняет поток управления. Нужен UAF, объект подходящего размера (или cross-cache в `cred_jar`) и стабильные попытки. Техника формализована на CVE-2022-2588 и CVE-2022-3913 и особенно эффективна для выхода из контейнера. В сочетании с cross-cache она превращает почти любой подходящий UAF в повышение привилегий без обхода control-flow защит. Это делает DirtyCred обязательной темой для любого, кто занимается современной kernel-эксплуатацией. Начните с простого UAF в учебной среде, отработайте переиспользование памяти под `cred` и только потом переходите к реальным CVE, где добавляются проверки LSM и особенности конкретной подсистемы ядра.

## Частые ошибки

- **Неверный размер объекта.** Память не переиспользуется под `cred`.
- **Гонка.** `cred` меняется ядром; подмена должна быть своевременной.
- **Игнорировать `usage`.** Счётчик ссылок влияет на освобождение.
- **Забыть про capabilities.** Одного uid=0 иногда мало.
- **Нестабильность.** Прогоняйте эксплойт многократно.
