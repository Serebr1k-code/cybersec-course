Off-by-one и off-by-null — уязвимости, при которых записывается один лишний байт (или нулевой байт) за границей буфера. Казалось бы, всего один байт, но он позволяет изменить размер соседнего чанка, флаг `PREV_INUSE` или младший байт указателя — а это открывает целые классы heap-атак: overlap, House of Einherjar, poison null byte. Off-by-one — один из самых «недооценённых» багов, дающий полный контроль над кучей.

## Как возникает off-by-one

```c
char buf[16];
for (int i = 0; i <= 16; i++)   // УЯЗВИМО: <= вместо <
    buf[i] = 'A';
// или
read(fd, buf, 17);              // на 1 больше размера
// или
strncat(dst, src, sizeof(dst)); // нет места для '\0'
```

Классика: цикл с `<=`, `strncat` без резерва под нуль-терминатор, `snprintf` с неверным размером. Результат — перезапись одного байта сразу после буфера.

## Почему один байт опасен

Если буфер граничит с чанком кучи, лишний байт попадает в поле `size` следующего чанка (или в `prev_size`). Изменение младшего байта `size` позволяет увеличить или уменьшить размер чанка, создать overlap, или сбросить флаг `PREV_INUSE`. Это основа атак:

| Что перезаписал | Атака |
|---|---|
| младший байт `size` | overlap, расширение чанка |
| нулевой байт в `size` | poison null byte, House of Einherjar |
| `prev_size` | unsafe unlink |
| указатель | сдвиг на страницу |

## Off-by-one в размер чанка

Пусть есть чанк A (0x60), за ним B (0x60). Если off-by-one меняет младший байт `size` чанка B с 0x61 на 0x81 (или больше), аллокатор считает B больше, и при освобождении B «поглотит» часть соседней памяти — overlap. Теперь A и B перекрываются, и через A можно писать в B.

```python
# off-by-one: пишем 0x41 вместо 0x21 -> size становится 0x41*...
# затем free(B) создаёт overlap
```

## Poison null byte

Если off-by-one пишет `\x00` в младший байт `size`, флаг `PREV_INUSE` сбрасывается (младший бит). Тогда при `free` соседнего чанка аллокатор думает, что предыдущий свободен, и консолидирует их, используя `prev_size` — который мы тоже контролируем через overlap. Это классический «poison null byte»: комбинация сброса `PREV_INUSE` и подделки `prev_size` даёт overlap с произвольным смещением.

## House of Einherjar

House of Einherjar использует off-by-null для сброса `PREV_INUSE` и подделки `prev_size`. При освобождении чанка аллокатор «откатывается» назад на `prev_size` байт и консолидирует с фейковым чанком, который мы разместили в контролируемой области. Это даёт overlap с произвольным адресом.

```python
# 1) создать чанк A, за ним B
# 2) off-by-null сбросил PREV_INUSE у B
# 3) подделать prev_size B = расстояние до фейкового чанка
# 4) free(B) -> консолидация с фейком -> overlap
```

## Практический пример

```python
#!/usr/bin/env python3
from pwn import *
context.binary = elf = ELF('./chall')
libc = ELF('./libc.so.6', checksec=False)

def start():
    return process('./chall') if args.LOCAL else remote('host', 1337)

def exploit():
    p = start()
    # аллоцируем три чанка
    a = alloc(0x18)   # чанк 0x20
    b = alloc(0x18)
    c = alloc(0x18)
    # off-by-one: перезаписываем младший байт size чанка b
    edit(a, b'A'*0x18 + b'\x41')   # size b: 0x21 -> 0x41
    free(b)
    # теперь b "больше" -> при следующем alloc получим overlap
    d = alloc(0x38)                 # перекрывает c
    edit(d, b'X'*0x20 + p64(0) + p64(0x91))
    free(c)
    # ... далее tcache poisoning/unsorted leak
    p.interactive()

exploit()
```

## Тонкости и подводные камни

- **Младший байт `size` кратен 0x10.** Меняйте на значение, сохраняющее выравнивание.
- **Проверки glibc.** Современные версии проверяют `size` и `prev_size` при `free`/`malloc`.
- **tcache.** Для чанков ≤ 0x410 сначала проверьте, не мешает ли tcache.
- **Off-by-null в `prev_size`.** Если нуль попал в `prev_size`, а не в `size`, эффект иной.
- **ASLR.** Адреса фейковых чанков требуют утечки heap base.
- **Точность.** Off-by-one работает только при точном совпадении границ — проверяйте раскладку в GDB.

## Справочные таблицы

| Тип | Записывает | Эффект |
|---|---|---|
| off-by-one | 1 байт | изменить size/flag |
| off-by-null | `\x00` | сбросить PREV_INUSE |
| off-by-n | n байт | перезапись указателя |

| Атака | Основа |
|---|---|
| overlap | изменённый size |
| House of Einherjar | off-by-null + prev_size |
| poison null byte | сброс PREV_INUSE |

## Что дальше / решение

Дальше: `pwn-house-einherjar` (подробно), `pwn-unsafe-unlink`, `pwn-heap-fengshui` (раскладка). Практический алгоритм: (1) найдите место, где пишется лишний байт; (2) определите, во что он попадает (size/prev_size/указатель); (3) проверьте раскладку чанков в GDB; (4) выберите атаку по таблице; (5) постройте overlap и далее используйте tcache poisoning или unsorted leak. Один байт — это не «почти ничего», а ключ к полному контролю над кучей.

## Детальный разбор poison null byte

Poison null byte — техника, при которой off-by-null обнуляет младший байт `size` следующего чанка. Поскольку младший байт содержит флаги, его обнуление сбрасывает `PREV_INUSE` (бит 0). Теперь при `free` следующего чанка аллокатор считает, что предыдущий чанк свободен, и пытается консолидировать их, отступая на `prev_size` байт. Если мы контролируем `prev_size` (например, через предыдущий off-by-one или через данные в перекрытом чанке), мы можем направить консолидацию в контролируемую область и получить overlap.

Пошагово: (1) аллоцируем чанки A, B, C; (2) off-by-null обнуляет младший байт `size` B, сбрасывая `PREV_INUSE`; (3) через отдельный примитив (например, запись в данные A) подделываем `prev_size` B так, чтобы он указывал на фейковый чанк в контролируемой области; (4) `free(B)` консолидирует B с фейковым чанком, создавая чанк большого размера, перекрывающий другие; (5) дальнейшими аллокациями получаем overlap.

```python
# 1) A, B, C
a = alloc(0xf8)   # чанк 0x100
b = alloc(0x68)   # чанк 0x70
c = alloc(0xf8)
# 2) off-by-null: обнуляем младший байт size B
edit(a, b'A'*0xf8 + b'\x00')
# 3) подделываем prev_size B (через данные A или overlap)
edit(a, b'A'*0xf0 + p64(0x100) + b'\x00')
# 4) free(B) -> консолидация
free(b)
# 5) overlap
```

## House of Einherjar по шагам

House of Einherjar — обобщение poison null byte. Ключевые условия: off-by-null, контроль `prev_size` и возможность разместить фейковый чанк с валидными `fd`/`bk` (для проверки unlink). При консолидации glibc выполняет `unlink` фейкового чанка, что записывает указатели и даёт примитив записи. Если фейковый чанк расположен так, что `fd`/`bk` указывают на цель, мы получаем запись по произвольному адресу.

```python
# фейковый чанк в контролируемой области:
# size = distance (чтобы консолидация дошла до него)
# fd = target - 0x18, bk = target - 0x10 (для обхода проверки unlink)
```

## Off-by-one в указатель

Иногда лишний байт попадает не в `size`, а в младший байт указателя (например, `next` в связном списке). Тогда указатель сдвигается на 0x100 байт, что может направить его на другой объект той же страницы. Это реже, но в задачах с массивами указателей встречается.

## Сравнение техник

| Техника | Требует | Результат |
|---|---|---|
| overlap через size | off-by-one в size | перекрытие чанков |
| poison null byte | off-by-null | сброс PREV_INUSE |
| House of Einherjar | off-by-null + prev_size | overlap с произвольным смещением |
| unsafe unlink | перезапись fd/bk | запись по адресу |

## Итог

Off-by-one и off-by-null — минимальные по объёму записи, но максимальные по последствиям. Один байт, попавший в метаданные чанка, открывает overlap и полный контроль над кучей. Освойте poison null byte и House of Einherjar — это обязательные техники для современной heap-эксплуатации, особенно на старых glibc, где проверки слабее.

## Расширенный практический чек-лист

1. Найдите место записи лишнего байта (цикл `<=`, `strncat`, `read` на 1 больше).
2. Определите, во что попадает байт: `size`, `prev_size` или указатель.
3. Посмотрите раскладку чанков в GDB (`heap`), чтобы понять границы.
4. Если это `size` — планируйте overlap; если `prev_size` — House of Einherjar.
5. Получите утечку heap base (safe-linking) и libc (unsorted bin).
6. Постройте overlap и далее tcache poisoning или запись в hook/FSOP.
7. Проверьте, что изменённый `size` сохраняет выравнивание на 0x10.

Каждый шаг опирается на предыдущий: без утечки не построить фейковый чанк, без понимания границ не выбрать значение. Off-by-one требует аккуратности, но награда — полный контроль над кучей.

Помните: минимальная перезапись требует максимальной точности — проверяйте каждый байт в отладчике перед финальным запуском.
 Аккуратность и терпение здесь важнее скорости: один неверный байт рушит всю цепочку.

## Где пригодится

- **CTF (Pwn):** классические heap-задачи с off-by-null/off-by-one — ядро «heap»-жанра.
- **Bug bounty:** граничные ошибки в парсерах и аллокаторах редко дают один байт «в пустоту» — часто это heap corruption.
- **Vulnerability research:** off-by-one — частая причина реальных CVE (libpng, libtiff, glibc-подобные баги).
- **Работа:** понимание устройства чанков нужно для отладки heap-крашей в проде.
