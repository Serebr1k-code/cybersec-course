## Вопрос, с которого всё начинается

Ты уже умеешь собирать ret2win под ARM64. Но реальная эксплуатация требует
деталей: почему компилятор сохраняет регистры **парами** (`stp`/`ldp`), как
влияет выравнивание стека на 16 байт, какие гаджеты искать и почему на новых
устройствах всё это ломает **PAC**. Разберём глубоко.

## Наш пример

```
$ file aarch64.elf
aarch64.elf: ELF 64-bit LSB relocatable, ARM aarch64
$ readelf --file-header aarch64.elf
  Class:                             ELF64
  Data:                              2's complement, little endian
  Machine:                           AArch64
```

64 бита, little-endian. Листинг (`aarch64.s`):

```
f:
	sub	sp, sp, #16
	str	w0, [sp, #12]
	ldr	w8, [sp, #12]
	add	w0, w8, #1
	add	sp, sp, #16
	ret
```

## Шаг 1: x30 — регистр связи

`ret` — это `br x30`: переход по адресу в регистре **`x30`** (он же `lr`).
Инструкция `bl` (Branch with Link) кладёт адрес возврата в `x30`. В нашем
примере `f` — leaf-функция, поэтому `x30` не сохраняется. В не-leaf функции
пролог сохранит его на стек.

## Шаг 2: stp/ldp и сохранение пары

Компилятор AArch64 почти всегда сохраняет `x29` (fp) и `x30` (lr) **парой**
одной инструкцией:

```
	stp	x29, x30, [sp, #16]
	...
	ldp	x29, x30, [sp, #16]
	ret
```

Это важно для эксплуатации: адрес возврата (`x30`) лежит **сразу за** `x29` в
стеке. Значит, переполнив буфер, ты затираешь сначала `x29`, потом `x30`.
Смещение до `x30` = offset до пары + 8.

## Шаг 3: выравнивание стека на 16 байт

AAPCS64 требует, чтобы `sp` был выровнен на 16 байт при вызове функции. Поэтому
кадры всегда кратны 16. Если твой payload сдвинет стек «не туда», `ldp`/`stp` с
невыровненным `sp` может вызвать исключение выравнивания. При построении цепочек
следи, чтобы количество байт до перехода было согласовано.

## Шаг 4: гаджеты AArch64

Ищем последовательности, заканчивающиеся `ret` (`br x30`). Типичные полезные
гаджеты:

```
ldp x29, x30, [sp], #16 ; ret    — «эпилог», двигает sp и восстанавливает lr
ldr x0, [sp, #8] ; ret           — загрузка аргумента
mov x0, x19 ; blr x0             — косвенный вызов
```

Инструменты: `ROPgadget --rawArch=arm64`, `ropper --arch arm64`, Ghidra. Помни,
что инструкции ровно 4 байта — границы выровнены.

## Шаг 5: собираем эксплойт

```python
from pwn import *
context.arch = 'aarch64'
p = process('./challenge')
offset = 40
payload  = b'A' * offset
payload += p64(ret2win_addr)   # перезаписанный x30
p.sendline(payload)
p.interactive()
```

Little-endian, адреса 8 байт. Если нужен аргумент в `x0`, добавь гаджет загрузки.

## Шаг 6: почему дальше появляется PAC

На современных ARM (arm64e, Apple Silicon, часть Android) включается **Pointer
Authentication**: перед сохранением `x30` на стек пролог его **подписывает**
(`paciasp`), а перед `ret` — **проверяет** (`autiasp`). Если ты перезаписал
сохранённый `x30` «сырым» адресом, проверка провалится и процесс упадёт.

Отсюда — необходимость обхода PAC: подписывающие гаджеты, утечки подписанных
указателей, атаки на модификатор. Этому посвящён отдельный урок
`pwn-arm-pac`.

## Шаг 7: митигации и контекст

На ARM64-Linux действуют те же RELRO/NX/PIE/ASLR, что и на x86-64, плюс BTI
(Branch Target Identification) — грубая защита от прыжков в середину функций.
Эксплуатация начинается со стандартной разведки: `checksec`, поиск утечек,
определение версии libc.

## Что мы теперь знаем

- Возврат AArch64 — `ret` = `br x30`; адрес возврата в `x30`.
- Компилятор сохраняет `x29`/`x30` парой `stp`, поэтому `x30` идёт за `x29`.
- Стек выровнен на 16 байт.
- Гаджеты заканчиваются `ret`; инструкции 4 байта.
- На новых ARM добавляется PAC и BTI.

## Как читать пролог и эпилог не-leaf функции

В прошлом уроке мы разобрали leaf-функцию. Теперь возьмём не-leaf — она вызывает
другую и обязана сохранить `x30`. Листинг:

```
g:
    stp x29, x30, [sp, #-16]!   ; pre-index: sp -= 16, сохраняем пару
    mov x29, sp                 ; frame pointer
    bl  helper                  ; вызов: x30 = адрес возврата в g
    ldp x29, x30, [sp], #16     ; post-index: грузим пару, sp += 16
    ret
```

Здесь три важные детали. Во-первых, `[sp, #-16]!` — «pre-indexed» адресация:
сначала `sp` уменьшается на 16, потом по новому адресу пишется пара;
восклицательный знак означает, что `sp` обновляется. Во-вторых, `mov x29, sp`
создаёт frame pointer — по нему отладочная информация привязывает переменные к
стеку. В-третьих, `[sp], #16` — «post-indexed»: сначала читаем пару по старому
`sp`, затем прибавляем 16.

Для эксплуатации вывод простой: адрес возврата `x30` лежит по адресу, где `sp`
был на входе в функцию, минус 8. Если буфер объявлен `char buf[32]`, компилятор
выделит под него и под сохранённую пару общий кадр, и `x30` окажется на
`32 + 8 = 40` байт от начала буфера (плюс возможный padding). Именно поэтому в
payload мы ставили `offset = 40`.

## Практика: находим смещение через cyclic

Не угадывай смещение — измерь. pwntools умеет генерировать уникальный паттерн и
находить в нём позицию:

```
$ python3 -c "from pwn import *; print(cyclic(64))"
aaaabaaacaaadaaaeaaafaaagaaahaaaiaaajaaakaaalaaamaaanaaaoaaapaaaqaaaraaa
$ gdb ./challenge
(gdb) run
Program received signal SIGSEGV, Segmentation fault.
(gdb) x/s $x30
0x6161616b6161616a: <error: Cannot access memory at address ...>
$ python3 -c "from pwn import *; print(cyclic_find(0x6161616a))"
40
```

`cyclic(64)` создаёт строку, где каждая четвёрка байт уникальна. Когда программа
падает, `$x30` содержит кусок паттерна; `cyclic_find` по этим байтам возвращает
точное смещение. На AArch64 адреса 8-байтовые, но паттерн ищется по первым
четырём байтам — этого достаточно.

## Что именно перезаписывать: x30 или сохранённый указатель

Есть тонкость: `x30` — это регистр, а на стеке лежит его *сохранённая копия*. При
переполнении мы перезаписываем именно стек. Когда функция дойдёт до эпилога,
`ldp` загрузит испорченное значение обратно в `x30`, и `ret` прыгнет туда.
Значит, перезаписывать надо сохранённую пару, а не «текущий регистр».

Если функция — leaf (нет `stp x29, x30`), то `x30` вообще не на стеке, и
переполнение буфера не даст контроля над возвратом. В таком случае цель — другая:
сохранённые callee-saved регистры (`x19`–`x28`), локальные указатели функций или
данные, которые позже используются как адрес вызова. Это называется data-only
атакой, и для ARM64 она часто единственный путь.

## Гаджеты: ищем нужное

Для ret2win достаточно одного адреса. Для передачи аргумента (например, в
`system`) нужен гаджет загрузки в `x0`. Ищем их так:

```
$ ROPgadget --binary libc.so.6 --rawArch=arm64 2>/dev/null | head
$ ropper --file libc.so.6 --arch arm64 --search "ldr x0 ; ret"
```

Типичный гаджет `ldr x0, [sp, #8] ; ret` берёт значение из стека — значит, в
цепочке после адреса гаджета надо положить аргумент. Часто проще найти готовую
функцию-обёртку, чем строить длинную ROP-цепочку: в ARM64 много функций
принимают указатель в `x0` и сразу вызывают нужное.

## Частые ошибки при сборке ARM64-payload

| Симптом | Причина | Решение |
|---|---|---|
| `SIGILL` сразу | неверный порядок байт | ARM64 little-endian, `p64` без `endian='big'` |
| падение на `ldp` | `sp` не выровнен на 16 | добавь padding до кратности 16 |
| падение на `autiasp` | включён PAC | искать подписывающий гаджет |
| `ret` прыгает не туда | перезаписан не тот слот | перепроверь смещение через `cyclic` |

## Почему BTI меняет правила

BTI (Branch Target Identification) разрешает косвенные переходы только на адреса,
помеченные инструкцией `bti`. Если PIE-бинарь собран с
`-mbranch-protection=bti`, прыжок в середину функции (классический «ret в
гаджет») вызовет исключение. Приходится целиться в начало функций или искать
последовательности «`bti; ...; ret`». Это ещё один пример того, как аппаратные
защиты сужают набор пригодных гаджетов и заставляют планировать цепочку заранее.

## Как отличить leaf от не-leaf по листингу

Быстрый признак: если в прологе нет `stp x29, x30, [sp, ...]`, функция, скорее
всего, leaf и не сохраняет адрес возврата. Тогда переполнение буфера не даёт
контроля над `pc` напрямую, и нужен другой примитив — перезапись указателя,
который позже используется для косвенного вызова, или callee-saved регистра.
Проверять просто: `objdump -d challenge | grep -A2 '<имя_функции>:'` и смотреть
первые инструкции. Наличие `stp x29, x30` — сигнал, что `x30` лежит на стеке и
является целью.

## Мини-чек-лист перед сборкой

1. Определить тип функции (leaf/не-leaf) по прологу.
2. Измерить смещение через `cyclic` и `cyclic_find`.
3. Проверить выравнивание стека (кратно 16).
4. Убедиться, что нет PAC/BTI (или учесть их).
5. Собрать payload с `p64` (little-endian).

Эти пять шагов покрывают большинство ошибок новичков на AArch64.

## Частые вопросы

**Что такое leaf-функция и почему это важно?** Функция без вызовов других
функций; компилятор может не сохранять `x30`. Тогда стекового переполнения
недостаточно для контроля `pc`.

**Всегда ли стек выровнен на 16?** Да, этого требует AAPCS64. Нарушение
выравнивания ломает `stp`/`ldp` и может вызвать исключение.

**Как проверить, включён ли PAC?** По наличию `paciasp`/`autiasp` в прологе и
эпилоге в дизассемблере, либо по флагам сборки (`-mbranch-protection`).
