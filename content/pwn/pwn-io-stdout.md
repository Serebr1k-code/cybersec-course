## Вопрос, с которого всё начинается

В прошлых уроках мы подделывали `_IO_FILE` в куче и прицепляли её в список потоков. Но есть цель проще: **статическая** структура `stdout`, которая уже лежит в libc. Её не надо подделывать целиком — достаточно поменять пару полей, и обычный `printf` в программе сам сделает нужное.

Разберём два приёма: утечку через `stdout` и **House of Husk** — вызов произвольной функции через цепочку `printf`.

## Наш пример

Найдём структуру `stdout` и связанные с ней объекты в целевой libc:

```
$ readelf -sW /usr/lib/libc.so.6 | grep -E '_IO_2_1_stdout_|_IO_file_jumps|_IO_list_all|system'
  53b00  system
  1e6030 _IO_file_jumps
  1e8480 _IO_list_all
  1e8580 _IO_2_1_stdout_
```

`_IO_2_1_stdout_` лежит в libc (`0x1e8580`), её `vtable` — легальная `_IO_file_jumps` (`0x1e6030`). Значит, проверка `IO_validate_vtable` для неё проходит автоматически, и менять `vtable` не нужно.

## Шаг 1. Почему stdout удобен

Три причины:

1. Структура уже в libc — не нужна heap-аллокация под подделку.
2. `vtable` легальна — проверка не мешает.
3. Обращение к ней происходит при **каждом** `puts`/`printf`/`fflush` — легко вызвать срабатывание.

Поэтому атаки через `stdout` часто проще FSOP через кучу.

## Шаг 2. Утечка через поля записи

`stdout` при сбросе буфера печатает память от `_IO_write_base` до `_IO_write_ptr`. Если изменить эти поля, программа напечатает то, что нам нужно:

| Смещение | Поле | Управление |
|---|---|---|
| `0x00` | `_flags` | режим потока |
| `0x20` | `_IO_write_base` | начало вывода |
| `0x28` | `_IO_write_ptr` | конец вывода |

Обнулив `_IO_write_base` и сделав `_IO_write_ptr` большим, получаем вывод памяти из диапазона — вместе с адресами libc. Это даёт утечку **без** отдельного UAF-примитива: достаточно уметь писать в `stdout`.

## Шаг 3. House of Husk: идея

`printf` поддерживает «пользовательские» спецификаторы формата. Если внутренняя таблица `__printf_function_table` не пуста, `printf` для каждого спецификатора ищет в ней функцию и вызывает её. Таблицы — глобальные переменные в libc, и их можно перезаписать.

Механика упрощённо:

```
для каждого спецификатора spec в строке формата:
    if (__printf_function_table && __printf_function_table[spec])
        вызвать __printf_function_table[spec](FILE*, info, args)
```

Значит, если подменить `__printf_function_table` на нашу таблицу, где по индексу нужного символа лежит `system`, а затем вызвать `printf` со строкой, содержащей этот спецификатор, — glibc вызовет `system`.

## Шаг 4. Собираем House of Husk

План:

1. Готовим в куче фейковую таблицу функций, где по индексу `ord('s')` (`0x73`) лежит `system`.
2. Готовим фейковую таблицу arginfo (она сообщает `printf`, какие аргументы у спецификатора) так, чтобы аргумент передавался.
3. Перезаписываем глобальные `__printf_function_table` и `__printf_arginfo_table` на наши адреса.
4. В программе должен быть вызов вида `printf("%s", ...)` — он триггерит нашу функцию.
5. Первым аргументом `system` получит строку, которую можно контролировать (например, через сам формат).

## Шаг 5. Где лежат таблицы

`__printf_function_table` и `__printf_arginfo_table` — локальные переменные libc, они **не экспортируются** в таблице символов. Их смещения находят:

- по отладочным символам, если libc с ними;
- поиском паттернов в дизассемблированном `vfprintf`;
- из известных баз смещений для конкретной сборки.

Это ключевое отличие House of Husk: цели не в куче, а в writable-данных libc, и их надо найти для целевой версии.

## Шаг 6. Другие приёмы через stdout

| Приём | Что делает |
|---|---|
| `_IO_write_base/_IO_write_ptr` | утечка памяти при выводе |
| House of Husk | вызов функции через `__printf_function_table` |
| подмена `_chain` | включить подделку в список потоков |
| `_IO_buf_base/_IO_buf_end` | управлять буфером вывода |

Все они опираются на то, что `stdout` — обычная структура `_IO_FILE` в writable-памяти libc.

## Полный прогон от начала до конца

Соберём утечку через `stdout` в один сценарий. Пусть у нас есть запись по произвольному адресу.

1. Узнаём адрес `_IO_2_1_stdout_` из целевой libc (`0x1e8580` в нашем примере) — но пока без базы libc он неизвестен.
2. Первую утечку берём другим способом (например, `unsorted bin` из прошлого урока) и вычисляем базу libc.
3. Теперь `_IO_2_1_stdout_ = libc_base + 0x1e8580`.
4. Пишем в поле `_flags` (`+0x00`) значение, при котором поток готов к записи, и обнуляем `_IO_write_base` (`+0x20`).
5. Выставляем `_IO_write_ptr` (`+0x28`) так, чтобы он охватывал область с адресами libc.
6. Программа делает обычный `puts` — glibc сбрасывает буфер и печатает память из диапазона. В выводе — адреса libc.
7. Из вывода вычисляем базу повторно (уже с высокой точностью) и продолжаем эксплойт.

Смысл: `stdout` превращает обычный вывод программы в канал утечки, не требуя отдельного примитива чтения.

## Шаг 7. Как найти __printf_function_table

Раз таблицы House of Husk не экспортируются, их ищут так:

- в libc с отладочными символами — по имени;
- без символов — по дизассемблированному `vfprintf`: ищем обращения к глобальным адресам в `.bss`, которые проверяются перед вызовом;
- из базы смещений для конкретной сборки (в CTF часто известны).

Найдя смещение, получаем адрес как `libc_base + offset` — ровно как с `system`.

## Если не сработало

Первое: не тот режим `_flags`. Если поток считает, что писать нечего, вывод не сработает. Проверь `_flags` в отладчике.

Второе: таблицы не найдены. `__printf_function_table` не экспортируется; если ты взял смещение из другой версии libc, оно не подойдёт.

Третье: нет вызова с нужным спецификатором. House of Husk срабатывает только когда программа реально вызывает `printf`/`fprintf` с форматом, содержащим твой спецификатор.

Четвёртое: arginfo неверен. Без корректной `__printf_arginfo_table` `printf` не передаст аргумент или упадёт.

Пятое: диапазон вывода слишком большой. Для утечки подбирай `_IO_write_ptr` так, чтобы не вывести гигабайты и не упасть.

Шестое: `vtable` затёрта. Хотя менять `vtable` у `stdout` не нужно, случайная запись может её испортить — тогда `IO_validate_vtable` уронит программу. Пиши строго в нужные смещения (`0x00`, `0x20`, `0x28`) и не задень `0xd8`.

## Что мы теперь знаем

- `_IO_2_1_stdout_` — статическая структура в libc с легальной `vtable`; менять её проще, чем строить FSOP в куче.
- Управляя `_IO_write_base`/`_IO_write_ptr`, получают утечку памяти при обычном выводе.
- House of Husk перезаписывает `__printf_function_table`/`__printf_arginfo_table`, чтобы `printf` вызвал нашу функцию.
- Эти таблицы — локальные символы libc, их смещения ищут для конкретной сборки.
- Атаки через `stdout` не требуют подделки `vtable`.

## Почему именно stdout, а не stdin/stderr

`_IO_2_1_stdin_` читает, `_IO_2_1_stderr_` пишет небуферизованно, а `_IO_2_1_stdout_` — это **буферизованный вывод**, который программа вызывает постоянно (`printf`, `puts`, `fwrite`). У stdout есть готовая точка вызова через vtable, и она инициализируется в libc при старте. Атакующему это удобно: не нужно ждать конкретного вызова, достаточно спровоцировать любой вывод. Плюс `stdout` ссылается на `_IO_file_jumps`, а его поля (`_IO_write_base`, `_IO_write_ptr`, `_IO_buf_base`) лежат в предсказуемом месте относительно базы libc — их легко перезаписать после утечки.

Отличие от FSOP через `_IO_2_1_stdout_`: FSOP подменяет vtable на `_IO_wfile_jumps` и вызывает цепочку через `_IO_wdoallocbuf`, а House of Husk идёт через `__printf_function_table`. Оба используют одну и ту же структуру FILE, но разные «крючки» вызова. Если переполнение даёт контроль над `__printf_function_table`, выбирайте Husk; если только над полями FILE — FSOP.

## Разбираем поля _IO_FILE по порядку

```
0x00 _flags            — флаги (например, 0xfbad1800 = _IO_USER_BUF|...)
0x08 _IO_read_ptr
0x10 _IO_read_end
0x18 _IO_read_base
0x20 _IO_write_base    — начало «грязного» буфера, откуда пойдёт write
0x28 _IO_write_ptr     — конец «грязного» буфера
0x30 _IO_write_end
0x38 _IO_buf_base      — начало буфера
0x40 _IO_buf_end
0x68 _chain
0xd8 _fileno           — индекс fd в _IO_2_1_stderr_
0xd8.. vtable          — таблица методов
```

Для утечки достаточно выставить `_flags = 0xfbad1800`, `_IO_write_base` в начало нужного региона, `_IO_write_ptr` в его конец — и следующий `fflush`/`fwrite` выведет память. Классический приём: затереть `_IO_read_end` и `_IO_read_ptr`, чтобы `_IO_write_base` указал туда, где лежит libc-адрес.

## Утечка в три поля

Минимальный набор для утечки libc:

1. `_flags = 0xfbad1800` — включает нужные биты, отключает проверки.
2. `_IO_write_base = &(что-то_до_libc)`.
3. `_IO_write_ptr = _IO_write_base + N`.

После этого любой `printf` выльет `N` байт. На практике удобно целиться в `_IO_2_1_stdout_ + 0x30` (там лежит `_IO_write_end`, часто содержащий указатель на libc). Если получили 6 байт — этого достаточно для вычисления базы.

## Когда House of Husk не срабатывает

- **glibc >= 2.34.** Многие символы (`__printf_function_table`) скрыты/переехали, а vtable-проверки ужесточены. Проверьте версию (`ldd --version` или `/proc/self/maps`).
- **Нет контроля над argv/таблицей.** Husk требует записи в `__printf_function_table` и `__printf_arginfo_table`; если есть только произвольное чтение — не выйдет.
- **Нет вызова printf после перезаписи.** Нужно спровоцировать вывод: нажмите «print», отправьте строку, вызовите меню.
- **Pointer mangling.** В новых glibc указатели в vtable защищены (`PTR_MANGLE`); обходится утечкой `__libc_argv[0]` и пересчётом.

## Сравнение двух крючков FSOP

| Приём | Что перезаписываем | Требует | Устойчив к glibc |
|---|---|---|---|
| House of Husk | `__printf_function_table` + arginfo | произвольную запись + printf | до 2.34 |
| FSOP stdout | `_IO_2_1_stdout_` + vtable | произвольную запись + flush | шире |
| FSOP wide data | `_IO_wide_data` + `_IO_wfile_jumps` | запись в куче | 2.34+ |

Выбор диктуется тем, куда именно у вас есть запись: в статическую область (`__printf_function_table`) или в кучу (FILE-структуры).

## Чек-лист

1. Получите утечку libc через `_IO_write_base/_write_ptr`.
2. Определите glibc: `ldd --version`, `strings libc.so.6 | grep release`.
3. Выберите крючок под версию и доступную запись.
4. Подготовьте полезную нагрузку (one_gadget или `system("/bin/sh")` через контролируемую строку).
5. Спровоцируйте вывод и дождитесь срабатывания.

## Таблица смещений _IO_FILE

Полезно держать под рукой карту полей `_IO_FILE` (для 64-битной glibc):

| Смещение | Поле | Роль |
|---|---|---|
| `0x00` | `_flags` | режим/состояние потока |
| `0x08` | `_IO_read_ptr` | указатель чтения |
| `0x10` | `_IO_read_end` | конец буфера чтения |
| `0x18` | `_IO_read_base` | начало буфера чтения |
| `0x20` | `_IO_write_base` | начало вывода |
| `0x28` | `_IO_write_ptr` | текущий указатель записи |
| `0x30` | `_IO_write_end` | конец буфера записи |
| `0x38` | `_IO_buf_base` | начало буфера |
| `0x40` | `_IO_buf_end` | конец буфера |
| `0x68` | `_chain` | следующий поток в списке |
| `0xd8` | `vtable` | таблица виртуальных функций |

Для утечки управляют парой `0x20`/`0x28`: печатается диапазон от `_IO_write_base` до `_IO_write_ptr`.

## Отладка в gdb

Проверить поля прямо в отладчике:

```text
pwndbg> p &_IO_2_1_stdout_
pwndbg> p _IO_2_1_stdout_._IO_write_base
pwndbg> p _IO_2_1_stdout_._IO_write_ptr
pwndbg> x/4gx &_IO_2_1_stdout_
```

Перед `puts` полезно поставить breakpoint на `_IO_file_xsputn`/`_IO_do_write` и посмотреть, какие адреса реально попадают в буфер. Если вывод пуст — почти всегда виноват `_flags` (поток считает, что писать нечего) или `_IO_write_ptr <= _IO_write_base`.

## Взаимодействие с _IO_vtable_check

Начиная с glibc 2.24, перед вызовом функции из `vtable` выполняется `IO_validate_vtable`, которая проверяет, что указатель `vtable` лежит в диапазоне `__start___libc_IO_vtables … __stop___libc_IO_vtables`. Для `stdout` это условие выполнено автоматически — её `vtable` легальна. Именно поэтому атаки через `stdout` устойчивы: не нужно ни подделывать `vtable`, ни искать «магическую» таблицу, попадающую в проверяемый диапазон. Если же вы строите FSOP в куче и подделываете `vtable`, обязана быть хотя бы одна легальная запись-функция (например, `_IO_str_jumps`), иначе проверка уронит процесс.
