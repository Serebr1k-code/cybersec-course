RISC-V pwn — эксплуатация бинарей под открытой архитектурой RISC-V, которая всё чаще встречается во встраиваемых системах, IoT и учебных задачах. RISC-V имеет собственный набор инструкций, соглашение о вызовах и особенности, отличные от x86/ARM. Понимание регистров, порядка аргументов, вызовов и гаджетов необходимо для построения эксплойтов. В этом уроке — основы RISC-V: регистры, ABI, вызовы, ROP, особенности RV32/RV64 и практические примеры под qemu-user.

## Регистры RISC-V

RISC-V имеет 32 целочисленных регистра (`x0`–`x31`), из которых `x0` всегда ноль. По соглашению о вызовах (RV64) им даны символические имена:

| Регистр | Имя | Роль |
|---|---|---|
| `x0` | `zero` | всегда 0 |
| `x1` | `ra` | адрес возврата |
| `x2` | `sp` | stack pointer |
| `x8` | `s0`/`fp` | frame pointer |
| `x10`–`x17` | `a0`–`a7` | аргументы/возврат |
| `x5`–`x7`,`x28`–`x31` | `t0`–`t6` | временные |
| `x8`–`x9`,`x18`–`x27` | `s0`–`s11` | сохраняемые |

Аргументы передаются в `a0`–`a7` (8 штук), возврат — в `a0`. Адрес возврата — в `ra` (`x1`), сохраняется на стеке при прологе.

## Соглашение о вызовах

RISC-V использует соглашение, где первые восемь аргументов идут в `a0`–`a7`, остальные — на стек. Caller-saved: `ra`, `t0`–`t6`, `a0`–`a7`; callee-saved: `s0`–`s11`, `sp`. Пролог функции обычно: `addi sp, sp, -N; sd ra, N-8(sp); sd s0, N-16(sp)`, эпилог: `ld ra, N-8(sp); ld s0, N-16(sp); addi sp, sp, N; ret`. `ret` — псевдоним `jalr x0, 0(ra)`.

## Поиск offset и гаджетов

```bash
# дизассемблирование
riscv64-linux-gnu-objdump -d ./chall
# гаджеты (ROPgadget поддерживает RISC-V)
ROPgadget --binary ./chall --only "ld|ret" | grep "ld ra"
ROPgadget --binary ./chall | grep "c.jr"
```

Гаджеты в RISC-V обычно загружают `ra` из стека (`ld ra, off(sp)`) и делают `ret`. Для установки аргументов используют `ld a0, off(sp)` или `mv a0, t0`. Так как аргументы грузятся из стека, ROP часто проще: вы размещаете значения на стеке и используете гаджеты-загрузчики.

## Разобранный пример: ret2win

```python
from pwn import *
context.binary = elf = ELF('./chall')
context.arch = 'riscv64'
p = process('./chall')
offset = cyclic_find(0x61616161)   # из gdb/cyclic
win = elf.symbols['win']
p.sendline(flat(b'A'*offset, win))
p.interactive()
```

На RISC-V `ra` сохраняется на стеке, поэтому переполнение перезаписывает именно его. Offset вычисляется через cyclic и gdb (`info registers ra`).

## ROP на RISC-V

Полноценный ROP: нужно установить `a0` (аргумент) и вызвать функцию. Гаджеты: `ld a0, X(sp); ld ra, Y(sp); addi sp, sp, Z; ret` — загружают `a0` и `ra` из стека. Так как многие функции RISC-V имеют такой эпилог, гаджетов достаточно. Цепочка:

```python
rop  = flat(
    load_a0_ra_gadget,
    value,          # a0
    system_addr,    # ra (следующая цель)
    binsh_addr
)
```

Порядок зависит от конкретного гаджета; проверяйте в gdb.

## Особенности RV32 vs RV64

На RV32 регистры 32-битные, указатели 4 байта; на RV64 — 64-битные. Различаются размеры стека, выравнивание (16 байт) и набор гаджетов. Для embedded-задач часто встречается RV32 (IoT). Учитывайте разрядность при вычислении offset и построении цепочки.

## Отладка под qemu-user

```bash
qemu-riscv64 -g 1234 ./chall
gdb-multiarch ./chall -ex 'set architecture riscv:rv64' -ex 'target remote :1234'
```

Используйте `gdb-multiarch` с правильной архитектурой. Смотрите `ra`, `sp`, `a0` в момент падения. Команда `x/10gx $sp` покажет стек.

## Частые ошибки

- **Не та архитектура в gdb.** Установите `riscv:rv64`/`riscv:rv32`.
- **Неверный offset.** `ra` сохраняется на стеке, а не в отдельном месте.
- **Выравнивание стека.** 16 байт, как в ARM64.
- **Разрядность.** RV32 vs RV64.
- **Гаджеты.** Их меньше, но эпилоги функций дают `ld ra`-гаджеты.

## Полный разбор RISC-V ROP

Разберём сквозной пример. Дано: RV64-бинарь с переполнением стека, есть функция `system` (или PLT) и строка `"/bin/sh"`. Цель — вызвать `system("/bin/sh")`. Шаги: (1) найти offset до сохранённого `ra` (обычно через cyclic + gdb: `info registers ra`, `x/20gx $sp`); (2) найти гаджет-загрузчик, например `ld a0, 0x??(sp); ld ra, 0x??(sp); addi sp, sp, 0x??; ret`; (3) выяснить, по каким смещениям гаджет грузит `a0` и `ra`; (4) построить payload так, чтобы по этим смещениям лежали `binsh_addr` и `system_addr`; (5) отправить. Если готового гаджета нет, используйте несколько гаджетов: один грузит `a0`, другой `ra`. Помните про выравнивание стека (16 байт) — при необходимости добавьте `ret`-гаджет. Проверяйте в gdb: `b *system`, `info registers a0 ra`.

## Особенности RV32 и embedded

Большинство RISC-V IoT-устройств используют RV32 (32-бит). В RV32 указатели 4 байта, регистры `a0`–`a7` те же, но адреса упаковываются как 32-битные (`p32`). Стековые слоты по 4 байта, что меняет смещения. Также в embedded часто отсутствует libc (static binary) или используется musl — учитывайте это при поиске функций. Для ret2win достаточно найти `win`-функцию; для ROP — гаджеты в бинаре. Часто RV32-бинари имеют NX, поэтому ROP обязателен. Практикуйтесь на qemu-riscv32.

## Отладка и инструменты

`gdb-multiarch` с `set architecture riscv:rv64` (или `riscv:rv32`) — основной отладчик. `qemu-riscv64 -g 1234 ./chall` запускает бинарь с gdb-сервером. Полезно установить `pwndbg` — он поддерживает RISC-V и показывает регистры/стек. `ROPgadget`/`ropper` поддерживают RISC-V. Для дизассемблирования — `riscv64-linux-gnu-objdump`. Всегда проверяйте разрядность и endianness (RISC-V обычно little-endian). Ведите заметки по гаджетам.

RISC-V pwn — молодая, но растущая область. Основы те же (переполнение, ROP, offset), но детали специфичны: `ra` на стеке, гаджеты-загрузчики, 8 аргументов в регистрах. Освоив RISC-V, вы сможете эксплуатировать IoT и embedded-устройства, которые всё чаще используют эту архитектуру. Начните с ret2win, затем ROP, затем более сложные приёмы.
## Расширенные приёмы и тонкости

Помимо базового ROP, в RISC-V есть нюансы. Во-первых, **compressed instructions** (RVC): многие инструкции имеют 16-битную форму, что меняет дизассемблирование и поиск гаджетов — учитывайте при анализе. Во-вторых, **позиционно-независимый код** (PIC) в PIE-бинарях использует `auipc`/`addi` для адресации, что влияет на гаджеты. В-третьих, в embedded часто нет libc, и функции (`system`) реализованы иначе или отсутствуют — тогда цельтесь в syscall-гаджеты (`ecall`) для `execve`. В-четвёртых, `ecall` в RISC-V — аналог `syscall`; номер syscall в `a7`, аргументы в `a0`–`a5`. Для ORW-цепочек (open/read/write) это удобно. Изучайте конкретную сборку и не переносите гаджеты между разрядностями.

## Полный список syscall-регистров и пример ORW

Для ORW-цепочек (open/read/write) на RISC-V: номер syscall в `a7`, аргументы в `a0`–`a5`, инструкция `ecall`. Номера: `openat` = 56, `read` = 63, `write` = 64, `execve` = 221. Цепочка: установить `a7` (номер), `a0`–`a2` (аргументы) через гаджеты-загрузчики, выполнить `ecall`. После каждого `ecall` нужно обработать результат (в `a0`). Это стандартный маршрут при seccomp, запрещающем `execve`. Ищите гаджеты `ld a7, off(sp); ld a0, off(sp); ...; ecall`. Собирайте цепочку пошагово и проверяйте в gdb. ORW-техники важны для sandbox-задач на любой архитектуре.


## Практика: ROP под qemu-riscv64

Соберите цепочку: (1) offset до `ra`; (2) гаджет `ld a0, N(sp); ld ra, M(sp); ...; ret`; (3) payload: по `N` — `binsh_addr`, по `M` — `system_addr`; (4) проверка в gdb (`set architecture riscv:rv64`, `b *system`). Для ORW — `ecall`, номер в `a7`, аргументы в `a0`–`a5` (openat=56, read=63, write=64). Для RV32 — `p32`/4-байтовые слоты. Практикуйтесь под qemu-riscv64/32. RISC-V — растущая архитектура; навык востребован в IoT и embedded.
