## Вопрос, с которого всё начинается

RISC-V — молодая открытая архитектура, которая всё чаще появляется в embedded-устройствах, и на CTF уже встречаются задачи под неё. Ты берёшь бинарник `chall`, и он снова «не такой»: регистры называются `a0`, `ra`, `sp`, а возврат делается не через `ret`. Хорошая новость: **RISC-V проще, чем MIPS** — в нём нет delay slots, и адрес возврата ведёт себя почти как на x86. Разберёмся.

## Наш пример

Смотрим файл:

```
$ file chall
chall: ELF 64-bit LSB executable, UCB RISC-V, RVC, double-float ABI, version 1 (SYSV),
statically linked, not stripped
```

- **UCB RISC-V** — архитектура RISC-V.
- **64-bit, LSB** — little-endian (в отличие от многих MIPS). Адреса упаковываются как на x86.
- **RVC** — сжатые инструкции (Compressed). Это влияет на размер кода, но не на логику.
- **statically linked** — статически слинкован: libc «вшита» внутрь, отдельной библиотеки нет.

Заголовок подтверждает:

```
$ readelf -h chall | grep -E 'Machine|Data|Class'
  Class:                             ELF64
  Data:                              2's complement, little endian
  Machine:                           RISC-V
```

## Шаг 1: регистры и соглашение вызовов

RISC-V использует единый набор регистров с понятными именами. Для эксплуататора важны:

- **`a0`–`a7`** — аргументы функции (первые восемь). `a0` — первый, как `rdi` на x86.
- **`ra`** — *return address* (адрес возврата).
- **`sp`** — указатель стека.
- **`s0`–`s11`** — сохраняемые регистры; `s0` часто работает как frame pointer.
- **`t0`–`t6`** — временные.

Возврат значения — в `a0`. Первый аргумент — тоже `a0`, поэтому `system("/bin/sh")` требует положить адрес строки в `a0`.

## Шаг 2: возврат и стек

В RISC-V нет инструкции `ret` как отдельного opcode — это **псевдоинструкция**: `ret` = `jalr x0, 0(ra)`. Она прыгает на адрес в `ra`.

```
$ objdump -d chall | sed -n '/<vuln>:/,/^$/p' | head
0000000000010140 <vuln>:
   10140: 1141        addi  sp,sp,-16
   10142: e406        sd    ra,8(sp)      ; СОХРАНИТЬ $ra на стеке
   10144: e022        sd    s0,0(sp)
   ...
   10158: 60a2        ld    ra,8(sp)      ; восстановить
   1015a: 0141        addi  sp,sp,16
   1015c: 8082        ret               ; = jalr x0,0(ra)
```

Тут всё почти как на x86: `sd ra,8(sp)` сохраняет адрес возврата на стек, `ret` его использует. Переполнив буфер, ты затираешь сохранённый `ra` — и управляешь возвратом. **Delay slots отсутствуют**: инструкция после перехода не выполняется «заранее», код читается линейно, как ты привык.

## Шаг 3: ROP на RISC-V

Раз `ret` есть (пусть и псевдо), ROP строится привычно: гаджеты заканчиваются на `ret`, цепочка лежит на стеке. Особенности:

- Гаджеты ищут тем же `ROPgadget`, но список опкодов другой: `ld a0,...`, `jalr`, `ret`.
- Чтобы передать аргумент, нужен гаджет вида `ld a0, X(sp); ... ; ret` или `pop`-эквивалент (в RISC-V «pop» — это загрузка из памяти по `sp`).
- Полезны «косвенные» прыжки: `jalr` по регистру — аналог `jmp`/`call` через регистр.

Идея та же, что и везде: **собрать из чужих кусочков вызов `system("/bin/sh")`**. Разница только в именах инструкций.

## Шаг 4: эмуляция и отладка

RISC-V-бинарь на x86 не запустится — нужен qemu-user:

```
$ qemu-riscv64 -L ./rootfs ./chall
$ qemu-riscv64 -g 1234 ./chall            # отладочный сервер на :1234
$ gdb-multiarch ./chall -ex 'target remote :1234'
```

- **`-L ./rootfs`** — корень с библиотеками, если бинарник динамический. Для статического не нужен.
- **`-g 1234`** — qemu ждёт подключения gdb на порту 1234.
- **`gdb-multiarch`** — gdb, умеющий RISC-V (обычный `gdb` может не знать эту архитектуру).

Если под рукой есть инструмент **`pwninit`** или **`pwn`-скрипты**, они помогут собрать окружение автоматически.

## Шаг 5: где это встречается

RISC-V растёт быстро: микроконтроллеры, учебные платформы, всё больше embedded-устройств и даже серверов. На CTF это чаще всего:

- **«Забыли про переполнение»** — классический stack overflow с перезаписью `ra`.
- **ROP без libc** — в статическом бинарнике гаджеты ищутся по всему файлу.
- **Обход ограничений** — RVC-инструкции и выравнивание иногда мешают гаджетам, что добавляет головной боли.

Практический совет: **сначала определи, статический бинарник или динамический** — от этого зависит, искать ли утечку libc или гаджеты прямо в файле. В статическом случае ещё проверь, нет ли PIE: без него адреса гаджетов постоянны, и эксплойт становится совсем простым. С PIE — понадобится утечка кода, как и на x86-64.

## Шаг 6: статический или динамический — вот в чём вопрос

Это первое, что стоит проверить на RISC-V-задаче, потому что от ответа зависит вся стратегия.

**Если бинарник динамический** (есть `interpreter /lib/ld-linux-riscv64-lp64d.so.1`), то внутри есть только маленькие заглушки вроде `puts@plt`, а сама `system` живёт в libc. Тогда:

1. Нужна **утечка** адреса функции из libc (через тот же `puts(got['puts'])`-трюк).
2. По утечке вычисляешь **базу libc** (вычитаешь известное смещение `puts`).
3. Ищешь в libc гаджеты (`ROPgadget --binary libc.so.6`) и собираешь цепочку `system("/bin/sh")`.

**Если бинарник статический** (как в нашем примере — `statically linked`), libc «вшита» внутрь, и все гаджеты, строки и функции лежат в самом файле. Тогда:

- Гаджеты ищутся по всему бинарнику, а не только в «своём» коде.
- Строка `/bin/sh` почти всегда найдётся в статической libc — искать через `strings -a -t x`.
- Часто достаточно одного-двух гаджетов, потому что адреса фиксированы (если PIE выключен).

Пример построения простой цепочки на RISC-V (псевдокод):

```python
# положить адрес строки "/bin/sh" в a0 и вызвать system
chain  = p64(gadget_ld_a0_sp)   # ld a0, X(sp); ... ; ret
chain += p64(binsh_addr)
chain += p64(system_addr)
```

Обрати внимание: в RISC-V нет привычных `pop rdi; ret` — загрузка аргумента делается из памяти относительно `sp`, поэтому и гаджет называется «`ld a0, X(sp)`». Искать его лучше `ropper` или `ROPgadget` с фильтром по `a0`.

## Что мы теперь знаем

- RISC-V — **little-endian**, 64-бит, без delay slots (в отличие от MIPS).
- Аргументы — в `a0`–`a7`, адрес возврата — в **`ra`**, `ret` = `jalr x0,0(ra)`.
- Переполнение стека перезаписывает сохранённый `ra` — управление возвратом, как на x86.
- ROP строится из гаджетов с `ret`/`jalr`, инструменты — `ROPgadget`, `ropper`.
- Запуск и отладка — через `qemu-riscv64 -L rootfs` и `gdb-multiarch`.
