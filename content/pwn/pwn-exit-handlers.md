## Вопрос, с которого всё начинается

FSOP через `exit` опирается на обход списка потоков. Но у `exit` есть и другой список — очередь функций, зарегистрированных через `atexit`. Он тоже обходится при завершении программы и тоже может быть подменён. Как он устроен и что защищает указатели в нём?

Разберём **exit-механизм** glibc: `__run_exit_handlers`, `__exit_funcs` и защиту указателей через pointer guard.

## Наш пример

Посмотрим на функцию, которую glibc вызывает при выходе для обработки очереди:

```
$ readelf -sW /usr/lib/libc.so.6 | grep -E '__call_tls_dtors|system'
  53b00  system
  40660  __call_tls_dtors
```

`__call_tls_dtors` (смещение `0x40660`) обходит похожий список — `tls_dtor_list` — и вызывает функции из него. А очередь `atexit` обслуживает `__run_exit_handlers`. Обе — пути к вызову нашего кода.

## Шаг 1. Как exit доходит до функций

Когда программа вызывает `exit(status)`, glibc выполняет:

```
exit -> __run_exit_handlers(status, &__exit_funcs, true, true)
```

`__run_exit_handlers` берёт указатель `__exit_funcs` и идёт по **связному списку** узлов. В каждом узле — массив записей `exit_function`, и для каждой записи в зависимости от её «flavor» вызывается функция. Упрощённо:

```c
while (f != NULL) {
    while (f->idx > 0) {
        struct exit_function *ef = &f->fns[--f->idx];
        if (ef->flavor == ef_at)
            (*ef->func)(ef->arg);     // <- вызов
        ...
    }
    f = f->next;
}
```

Вот она — точка вызова: поле `func` записи.

## Шаг 2. Структура узла и записи

| Структура | Поля |
|---|---|
| `exit_function_list` | `next`, `idx`, `fns[]` |
| `exit_function` | `flavor`, `func`, `arg` |

`flavor` — целое, определяющее способ вызова:

| Значение | Имя | Смысл |
|---|---|---|
| 0 | `ef_free` | пустой слот |
| 1 | `ef_us` | `__cxa_atexit` |
| 2 | `ef_on` | `__internal_atexit` |
| 3 | `ef_at` | `atexit` — прямой вызов `func(arg)` |

Нас интересует `ef_at`: он вызывает `(*func)(arg)` напрямую.

## Шаг 3. Pointer guard: что усложняет подмену

С давних пор glibc **шифрует** указатели в этих записях приёмом, который называют **pointer guard**. При регистрации `func` проходит через `PTR_MANGLE` — операцию с секретным значением, хранящимся в потоковом хранилище (TLS):

```
PTR_MANGLE(func) = rotate_left(func XOR guard, ...)
```

При вызове `__run_exit_handlers` делает обратное `PTR_DEMANGLE`. Значит, чтобы подставить свой `system`, надо знать **guard** и закодировать указатель так же. Иначе glibc расшифрует мусор и упадёт.

## Шаг 4. Как обойти pointer guard

Способы:

| Подход | Суть |
|---|---|
| Утечка guard | читаем TLS (иногда доступен через другой примитив) |
| Использовать уже закодированный указатель | найти в памяти валидную `PTR_MANGLE(system)` |
| Перезаписать весь узел | если можно задать и `func`, и `flavor`, и обойти мангл |
| `tls_dtor_list` | обход через `__call_tls_dtors` |

Часто проще атаковать `tls_dtor_list` — список деструкторов потока, который тоже обходится при выходе. Если удаётся контролировать его элементы, вызов идёт без дополнительной структуры `exit_function_list`.

## Шаг 5. Регистрация своих функций

`atexit(func)` добавляет запись с `flavor = ef_at` и `func`, закодированным `PTR_MANGLE`. Программа может регистрировать свои обработчики — это легальная функциональность. Атака же заключается в том, чтобы **изменить** уже зарегистрированную запись: подменить `func` на нужный адрес (закодированный) или добавить свой узел в список.

## Шаг 6. Полный прогон

Типичный сценарий атаки:

1. Утекаем базу libc (см. `pwn-io-leak`).
2. Находим адрес `__exit_funcs` в целевой libc (локальный символ, смещение из сборки).
3. Добираемся до узла списка и его записей.
4. Если знаем pointer guard — кодируем `system` через `PTR_MANGLE` и записываем в `func`.
5. Программа завершается — `exit` обходит список и вызывает `system`.
6. Аргумент `arg` подставляем как `"/bin/sh"`.

## Шаг 7. Почему это актуально на 2.34+

После удаления `__free_hook`/`__malloc_hook` exit-механизмы стали одной из основных целей. Они живы во всех версиях, и атака на них не зависит от tcache-защит. Плата — pointer guard, который надо обойти.

## Полный прогон от начала до конца

Соберём атаку на exit-механизм в один сценарий. Пусть программа регистрирует один `atexit`-обработчик и у нас есть запись по произвольному адресу.

1. Утекаем базу libc (`unsorted bin`, см. `pwn-io-leak`).
2. Находим смещение `__exit_funcs` в целевой libc (локальный символ, берём из сборки).
3. Читаем содержимое `__exit_funcs` — это указатель на первый узел `exit_function_list` в куче или libc.
4. В этом узле есть записи `exit_function`. Первая запись, зарегистрированная `atexit`, имеет `flavor = ef_at`.
5. Если знаем pointer guard — кодируем `system` через `PTR_MANGLE` и записываем в поле `func` записи.
6. Меняем `arg` на адрес строки `"/bin/sh"`.
7. Программа вызывает `exit` — `__run_exit_handlers` доходит до записи и вызывает `system("/bin/sh")`.

Если pointer guard неизвестен, шаг 5 не проходит; тогда ищем другой путь — например, уже закодированный указатель в памяти или `tls_dtor_list`.

## Шаг 8. Как читать PTR_MANGLE

Формула pointer guard в glibc (упрощённо):

```
PTR_MANGLE(ptr)   = rol(ptr XOR guard, 0x11)
PTR_DEMANGLE(x)   = ror(x, 0x11) XOR guard
```

где `rol`/`ror` — циклические сдвиги. Значит, зная `guard` из TLS, ты можешь закодировать любой адрес так, что `PTR_DEMANGLE` вернёт его обратно. Без `guard` — не можешь, и это основная сложность атаки. `guard` иногда утекает через тот же примитив, что и другие адреса.

## Если не сработало

Первое: неверный flavor. Для прямого вызова нужен `ef_at`; с другими flavor glibc пойдёт другой веткой.

Второе: pointer guard. Если ты записал «сырой» `system`, `PTR_DEMANGLE` превратит его в мусор. Нужен либо guard, либо уже закодированный указатель.

Третье: узел не в списке. `__exit_funcs` должен указывать на твой узел (или твой узел — быть в цепочке `next`).

Четвёртое: `idx` равен нулю. `__run_exit_handlers` обходит записи от `idx-1` вниз; если `idx` не выставлен, твоя запись не будет обработана.

Пятое: не тот аргумент. `arg` подставляется как первый аргумент; для `system` там должна быть строка команды.

Шестое: узел перезаписан частично. `exit_function_list` содержит `next`, `idx` и массив записей; если испортить `next` или `idx`, обход пойдёт не туда или пропустит твою запись. Проверь все поля узла, а не только `func`.

## Что мы теперь знаем

- `exit` вызывает `__run_exit_handlers`, который обходит список `__exit_funcs`.
- Узел — `exit_function_list` с массивом записей `exit_function` (`flavor`, `func`, `arg`).
- `flavor = ef_at` означает прямой вызов `(*func)(arg)`.
- Указатели в записях закодированы pointer guard (`PTR_MANGLE`/`PTR_DEMANGLE`).
- Обход guard — утечка или уже закодированный указатель; альтернатива — `tls_dtor_list`.
- Exit-механизмы — актуальная цель на glibc 2.34+.
