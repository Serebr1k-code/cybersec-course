`__run_exit_handlers` и `atexit` — механизм glibc для выполнения функций при завершении процесса. `atexit(func)` регистрирует обработчик в списке `__exit_funcs`; при `exit` glibc обходит этот список и вызывает зарегистрированные функции (в обратном порядке). Для pwn это означает: если вы можете перезаписать запись в `__exit_funcs` (или `initial`-структуру), вы получите вызов контролируемой функции при завершении программы — даже при Full RELRO и без `__free_hook`. Это классический обход, активно используемый на glibc 2.34+, где хуки удалены. В этом уроке — устройство `__exit_funcs`, типы записей, техника перезаписи и практические эксплойты.

## Устройство __exit_funcs

Список `__exit_funcs` — связный список структур `exit_function_list`. Каждый узел содержит массив `fns` из `exit_function`:

```c
struct exit_function {
    long int flavor;                 // ef_free, ef_us, ef_on, ef_at, ef_cxa
    union {
        void (*at)(void);            // ef_at: atexit
        void (*on)(int, void*);      // ef_on: on_exit
        void (*cxa)(int, void*);     // ef_cxa: __cxa_atexit
    } func;
    void *arg;
    void *dso_handle;
};
```

Поле `flavor` определяет, как вызывается `func`. Для `ef_cxa` вызывается `func.cxa(arg, dso_handle)` — то есть **два** аргумента, что удобно для передачи `"/bin/sh"`. Для `ef_at` — `func.at()` без аргументов. При обходе `__run_exit_handlers` сначала проверяется `flavor`, затем происходит вызов.

## Перезапись __exit_funcs

Есть несколько путей: (1) подделать запись в существующей структуре `initial` (статическая в libc/`exit.c`), изменив `flavor` на `ef_cxa` и `func` на `system`, `arg` — на `"/bin/sh"`; (2) создать собственную структуру на heap и связать её с `__exit_funcs`; (3) использовать largebin attack для записи указателя на поддельную структуру в `__exit_funcs`. Затем вызвать `exit` (или дождаться завершения `main`).

```python
# подделка записи: flavor = ef_cxa, func = system, arg = "/bin/sh"
fake = flat(
    4,                                  # ef_cxa (значение flavor зависит от glibc)
    libc.sym['system'],                 # func.cxa
    next(libc.search(b'/bin/sh\x00')),  # arg
    0                                   # dso_handle
)
```

Значение `ef_cxa` (обычно 4) и точная раскладка `exit_function` зависят от версии; сверяйте в gdb (`ptype struct exit_function`).

## Триггер: exit vs _exit

Важно: обработчики вызываются только при **нормальном** завершении — `exit`, `return` из `main`, или `__libc_start_main` после возврата. Функции `_exit`/`_Exit` (syscall `exit_group`) **не** вызывают `atexit`-обработчики, как и `abort`. Поэтому убедитесь, что программа завершается через `exit`/`return`. В CTF это обычно так; в реальных сервисах проверяйте.

## Практический сценарий: FSOP-альтернатива

На glibc 2.34+ путь через `__exit_funcs` часто проще, чем FSOP: не нужна корректная vtable, достаточно подделать запись с `flavor` и `func`. Сценарий: (1) получите произвольную запись; (2) найдите `__exit_funcs` (`libc.sym['__exit_funcs']`); (3) запишите поддельную структуру; (4) триггерните `exit`. Если структура лежит на heap (например, в вашем чанке), сначала запишите её адрес в `__exit_funcs` (через largebin attack или direct write).

```python
exit_funcs = libc.address + libc.sym['__exit_funcs']
# записать указатель на нашу поддельную структуру
write(exit_funcs, p64(fake_addr))
```

## Частые ошибки

- **Использование `_exit`.** Обработчики не вызовутся — проверяйте путь завершения.
- **Неверный `flavor`.** Значение зависит от версии; для `ef_cxa` обычно 4, но сверяйте.
- **Забыт `arg`.** Для `system` нужен указатель на `"/bin/sh"` — иначе вызов упадёт.
- **Структура не в списке.** Поддельная структура должна быть достижима из `__exit_funcs`.
- **`dso_handle`.** Для `ef_cxa` третий аргумент может влиять на вызов — учитывайте.

## Сквозной разбор: перезапись __exit_funcs на glibc 2.35

Разберём практический сценарий на современной glibc, где хуки удалены. Пусть есть heap UAF и произвольная запись. План — подделать запись в `__exit_funcs` и вызвать `exit`. Шаги: (1) через UAF/перекрытие утекаем libc (например, `bk` unsortedbin-чанка → `main_arena`); (2) находим адрес `__exit_funcs` = `libc.address + libc.sym['__exit_funcs']`; (3) готовим структуру `exit_function` с `flavor = ef_cxa (4)`, `func.cxa = system`, `arg = "/bin/sh"`, `dso_handle = 0`; (4) размещаем структуру в контролируемой памяти (наш чанк); (5) записываем указатель на неё в `__exit_funcs` (в поле, откуда начинается обход); (6) завершаем процесс нормально. При `__run_exit_handlers` glibc дойдёт до нашей записи и вызовет `system("/bin/sh")`. Важно: указатель в `__exit_funcs` должен указывать на корректную структуру `exit_function_list`, а не просто на функцию — сверяйте раскладку в gdb.

## Разница между ef_at, ef_on и ef_cxa

Тип `flavor` определяет сигнатуру вызова. `ef_at` (3) вызывает `func.at()` без аргументов — подходит для one-gadget или функции без параметров. `ef_on` (2) вызывает `func.on(arg, status)` — два аргумента. `ef_cxa` (4) вызывает `func.cxa(arg, dso_handle)` — тоже два аргумента, причём первый (`arg`) полностью контролируется. Для `system("/bin/sh")` идеален `ef_cxa`: кладём `system` в `func.cxa`, `"/bin/sh"` в `arg`. Для `one_gadget` подойдёт `ef_at`. Учитывайте порядок и количество аргументов: неверный `flavor` приведёт к тому, что функция получит мусор и упадёт. Значения констант (`ef_free=0`, `ef_us=1`, `ef_on=2`, `ef_at=3`, `ef_cxa=4`) стабильны между версиями, но раскладку структуры проверяйте.

## Взаимодействие с _IO_cleanup и порядком вызовов

При `exit` glibc выполняет действия в определённом порядке: сначала `__exit_funcs` (через `__run_exit_handlers`), затем сбрасывает потоки (`_IO_cleanup`), затем вызывает `.fini_array`-финализаторы. Это значит, что если вы атакуете `__exit_funcs`, вызов произойдёт **раньше**, чем FSOP через `_IO_list_all` и чем `.fini_array`. Если первая попытка падает, процесс может завершиться до второй цели — поэтому выбирайте одну надёжную цель, а не комбинируйте несколько. Порядок также важен при отладке: ставьте точки останова на `__run_exit_handlers`, `_IO_cleanup` и `__libc_csu_fini`, чтобы видеть последовательность. Понимание порядка помогает предсказать, какой примитив сработает первым.

## Диагностика: почему __exit_funcs не сработала

Если вызова не происходит, проверьте: (1) завершается ли процесс через `exit`/`return`, а не через `_exit`/`abort`; (2) корректен ли указатель в `__exit_funcs` — указывает ли он на валидную `exit_function_list`; (3) правильный ли `flavor` и `func`; (4) не портит ли запись соседние поля; (5) верно ли вычислена база libc. В gdb поставьте `b __run_exit_handlers`, пройдите по списку и посмотрите, доходит ли до вашей структуры. Выведите `p *__exit_funcs` и вручную пройдите `_chain`-поля. Часто проблема в том, что структура лежит не там, куда указывает `__exit_funcs`, или в неверном `flavor`.

## Чек-лист применения

1. Подтвердите путь завершения (`exit`/`return`, не `_exit`).
2. Найдите `__exit_funcs` и раскладку `exit_function` в вашей версии.
3. Определите цель (`system` + `"/bin/sh"` для `ef_cxa`, one-gadget для `ef_at`).
4. Подготовьте структуру в контролируемой памяти.
5. Свяжите её с `__exit_funcs` (direct write или largebin attack).
6. Триггерните нормальное завершение.
7. Проверьте в gdb, что `__run_exit_handlers` доходит до записи.

## Итоговые рекомендации

`__exit_funcs` — это «тихий» путь к исполнению, который работает на всех версиях glibc и не требует подделки vtable. Его главное преимущество — простота структуры: достаточно выставить `flavor`, `func` и `arg`. Главный недостаток — зависимость от нормального завершения процесса, поэтому убедитесь, что сервис вызывает `exit`/`return`. На glibc 2.34+, где хуки удалены, этот путь часто оказывается самым коротким. Комбинируйте его с largebin attack, если нужно записать указатель на структуру в `__exit_funcs`. И всегда проверяйте раскладку `exit_function` в целевой версии — она стабильна, но детали (размер, выравнивание) стоит подтвердить в gdb.

Наконец, помните, что `atexit`-обработчики выполняются в обратном порядке регистрации, поэтому порядок в списке `__exit_funcs` может влиять на то, какая запись сработает первой; при отладке учитывайте этот порядок.
