## Вопрос, с которого всё начинается

На современных ядрах включают CFI и shadow stack — защиты, которые ломают ROP.
Но что, если вообще не перехватывать поток управления? Есть целый класс атак,
которые меняют только **данные**. В ядре это часто и проще, и надёжнее. Как это
работает?

## Наш пример

Смотрим, как ядро хранит права процесса:

```c
struct cred {
    atomic_t usage;
    kuid_t   uid, gid, suid, sgid, euid, egid, fsuid, fsgid;
    unsigned cap_*;       // capabilities
    ...
};
```

Права root — это `uid = 0`, `gid = 0` и полный набор capabilities в структуре
`cred`. Если мы можем **записать нули** в поля чужого `cred`, процесс станет
root. Поток управления при этом не трогается вообще.

## Шаг 1: почему data-only обходит CFI

CFI (Control-Flow Integrity) проверяет, что косвенные вызовы идут в допустимые
цели. Shadow stack проверяет, что `ret` возвращается туда, откуда пришёл. Обе
защиты следят за **потоком управления**. Data-only атака меняет данные, поэтому
обе защиты «не замечают» атаку — они просто не на этом уровне.

Именно поэтому на системах с CFI/CET data-only — предпочтительный путь.

## Шаг 2: цель №1 — cred

Классический data-only privesc:

1. Находим адрес `cred` текущего процесса. Его можно утечь через
   `task_struct` → `cred` (если есть read-примитив) или через спрей.
2. Записываем нули в `uid`..`fsgid` и выставляем все capabilities в `0xffffffff`.
3. Проверяем `id` — процесс стал root.

Есть тонкость: `cred` иммутабелен, ядро использует copy-on-write через
`prepare_creds`. Но если мы пишем напрямую в память, это неважно — главное
попасть в правильную структуру.

## Шаг 3: цель №2 — modprobe_path

`modprobe_path` — глобальная строка в ядре (обычно `/sbin/modprobe`). Когда
ядро встречает файл с неизвестным форматом (например, `\xff\xff\xff\xff`), оно
вызывает `call_usermodehelper` и запускает `modprobe_path` от имени root.

Атака:

1. Перезаписываем строку на `/tmp/x` (наш скрипт).
2. Создаём `/tmp/x`, который делает что-то полезное (например, копирует shell).
3. Триггерим неизвестный формат — ядро запускает наш скрипт как root.

Здесь тоже нет перехвата потока управления — только запись строки.

## Шаг 4: цель №3 — core_pattern

Похожий приём: `core_pattern` определяет, что делать с core-дампом. Если
перезаписать его на `|/tmp/x %p`, то при падении процесса ядро запустит наш
скрипт как root. Запись данных — и root без ROP.

## Шаг 5: когда data-only не подходит

Data-only требует **записи** по нужному адресу. Если у нас только read или
только control-flow-примитив, придётся строить ROP. Кроме того:

- Нужно точно знать смещения полей (`cred` менялся между версиями ядра).
- Некоторые структуры защищены (например, `cred` может быть в `SLAB_ACCOUNT`).
- KASLR всё равно нужно обойти, чтобы найти адрес цели.

То есть data-only — не замена утечке, а замена control-flow части эксплойта.

## Шаг 6: пример с перезаписью cred

```c
uint64_t cred_addr = leak_cred();        // нашли через утечку
uint64_t zeros[4] = {0};
write_kernel(cred_addr + 4, zeros, 32);  // uid..fsgid = 0
uint64_t caps = 0xffffffffffffffffULL;
write_kernel(cred_addr + 0x28, &caps, 8); // capabilities
```

После этого `getuid()` вернёт 0. Смещения (4, 0x28) — примерные, для конкретного
ядра их берут из BTF/отладочных символов.

## Шаг 7: отладка и проверка

Проверяем через `id`/`getuid` после атаки. Под `qemu` с `gdb` смотрим
`cred` процесса: `p ((struct task_struct*)$current)->cred`. Если поля обнулились —
атака сработала. Полезно логировать адрес `cred` до и после.

## Что мы теперь знаем

- Data-only меняет данные, не трогая поток управления.
- `cred` — главная цель: нулевые uid = root.
- `modprobe_path`/`core_pattern` дают выполнение команды как root.
- CFI/CET не ловят data-only.
- Нужны запись по адресу и обход KASLR.

## cred и copy-on-write

Важная тонкость: структура `cred` в ядре **иммутабельна**. Когда процесс меняет
свои права (например, `setuid`), ядро не меняет `cred` на месте, а создаёт копию
через `prepare_creds`/`commit_creds`. Это защита от гонок: другие процессы,
читающие `cred`, всегда видят согласованное состояние.

Для data-only атаки это неважно: мы пишем **напрямую в память**, минуя API.
Ядро не знает, что `cred` изменился, и продолжает использовать нашу
испорченную структуру. Главное — найти правильный адрес и не попасть в
`cred` другого процесса (иначе повысим не себя).

Как найти свой `cred`: через `task_struct` текущего процесса. Если есть
read-примитив, читаем `current->cred`. Если нет — можно утечь через
`/proc/self/stat` или спреить и найти по сигнатуре.

## Перезапись modprobe_path пошагово

```
1. leak kernel base
2. write_kernel(base + modprobe_path_off, "/tmp/x\0")
3. create /tmp/x:
       #!/bin/sh
       cp /bin/sh /tmp/sh; chmod +s /tmp/sh
   chmod +x /tmp/x
4. trigger: create a file with unknown magic (e.g. printf '\xff\xff\xff\xff' > /tmp/f)
   then execve("/tmp/f")
5. kernel runs modprobe_path ("/tmp/x") as root
6. /tmp/sh is now setuid root -> privilege escalation
```

Ключевое: `modprobe_path` — обычная строка в данных ядра, её легко перезаписать.
Ядро вызывает её через `call_usermodehelper` от root. Никакого перехвата потока
управления — чистый data-only.

## core_pattern и другие финишеры

- **`core_pattern`** — строка, определяющая обработчик core-дампов. Если начать
  её с `|`, ядро запустит указанную программу от root при падении процесса.
  Перезапись на `|/tmp/x %p` даёт выполнение команды.
- **`poweroff_cmd`**, **`uevent_helper`** (старые ядра) — похожие механизмы.
- **Перезапись указателя в структуре** (например, `timer_list.function`) —
  штатный код потом вызовет наш указатель. Это уже ближе к control-flow, но
  тоже часто проходит CFI, если указатель легального типа.

## Ограничения и защита

Data-only требует **точных смещений** для конкретного ядра. Их берут из BTF
(`/sys/kernel/btf/vmlinux`) или отладочных символов. На разных версиях смещения
меняются, поэтому эксплойт нужно адаптировать.

Защита:
- **Read-only `modprobe_path`** (некоторые патчи/хардненинги) — ломает финишер.
- **STATIC_USERMODEHELPER** — заменяет `modprobe_path` на фиксированную
  программу-диспетчер, которую нельзя подменить.
- **SLAB_ACCOUNT/случайные аллокаторы** — усложняют поиск `cred`.
- **CFI не помогает** — data-only не трогает поток; нужна защита целостности
  данных (редко встречается).

## Сравнение финишеров

| Финишер | Что нужно | Устойчивость к защитам |
|---|---|---|
| cred | точный адрес cred | высокая (data-only) |
| modprobe_path | запись строки | высокая |
| core_pattern | запись строки | высокая |
| kernel ROP | контроль потока | средняя (CET/CFI мешают) |

Data-only финишеры (`cred`, `modprobe_path`, `core_pattern`) предпочтительны на
современных ядрах: они не трогают поток управления и потому переживают CFI/CET.
Выбор зависит от примитива: если есть только read, придётся идти через ROP; если
есть запись — data-only.

## Итог по data-only

Data-only атаки меняют данные (`cred`, `modprobe_path`, `core_pattern`), а не
поток управления, поэтому они устойчивы к CFI/CET. Нужны запись по адресу и
обход KASLR. Это предпочтительный путь на современных ядрах.

## Разбор реального data-only сценария

Цель — контейнер на современном ядре с CFI. Уязвимость — UAF, дающий запись по
адресу. Стратегия:

1. Утечкой вычисляем базу ядра и адрес `cred` текущего процесса.
2. Обнуляем `uid`..`fsgid` и выставляем capabilities в максимум.
3. Проверяем `id` — root.

Никакого ROP, никакого перехвата потока. CFI молчит, потому что все переходы
штатные. Именно так эксплуатируются многие современные kernel-баги на
CFI-ядрах.

## Почему это предпочтительный путь

На современном ядре control-flow атаки встречают CET/shadow stack и CFI. Data-
only обходит их все. Единственные требования — запись по адресу и обход KASLR.
Если у бага есть data-примитив, эксплойт через `cred`/`modprobe_path` проще и
надёжнее ROP. Поэтому при выборе стратегии сначала проверяй: «могу ли я получить
запись?» — если да, иди data-only.

## Типичные ошибки data-only

- **Не тот `cred`.** Перезапись чужого `cred` повысит не тебя.
- **Смещения из другой версии.** `cred` менялся; сверяй с целевым ядром.
- **Забыть про capabilities.** Только `uid=0` иногда мало — выставляй caps.
- **STATIC_USERMODEHELPER.** Тогда `modprobe_path` не сработает.

## Заключение по data-only

Data-only — стратегия первого выбора на современных ядрах. Если у бага есть
примитив записи, перезапись `cred` или `modprobe_path` даёт root без единого
перехвата потока управления, а значит, без борьбы с CFI/CET. Требования просты:
запись по адресу и обход KASLR. Освоив data-only, ты сможешь эксплуатировать
большинство современных kernel-багов, даже когда control-flow атаки закрыты.

## Финальная мысль

Помни главное: data-only не заменяет обход KASLR и не отменяет необходимость
примитива записи. Но когда оба есть, именно data-only даёт самый короткий путь к
root на современном ядре, потому что все защиты потока управления оказываются
неприменимы. Это тот случай, когда «проще» совпадает с «надёжнее».

## Что дальше в теме

Data-only тесно связан с обходом KASLR: без базы адрес `cred` неизвестен, поэтому
две темы изучают вместе. В следующем уроке ветки разбираем обход защит ядра.

## Куда дальше

Дальше — **обход защит ядра**: KASLR и KPTI. А пока запомни: **data-only меняет
данные (cred, modprobe_path) и потому переживает CFI/CET, которые смотрят только
на поток управления**.
