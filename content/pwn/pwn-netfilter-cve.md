## Вопрос, с которого всё начинается

Мы уже видели nf_tables. Но в 2022 году были и другие громкие kernel-баги, часто
объединяемые в одну «коллекцию контейнерного побега». Два из них — **CVE-2022-0185**
(переполнение в `fs_context`) и **CVE-2022-2588** (use-after-free в netfilter
traffic-control). Разберём оба, потому что они показывают разные примитивы:
переполнение кучи и UAF.

## Наш пример

Смотрим ядро и доступные возможности:

```
$ uname -r
5.15.0-52-generic
$ id
uid=1000(user) gid=1000(user) groups=1000(user)
$ cat /proc/self/status | grep CapEff
CapEff: 0000000000000000
```

Ядро `5.15` попадает под оба CVE. Но чтобы эксплуатировать CVE-2022-0185, часто
нужен **user namespace** — способность создавать свои namespace без root.

## Шаг 1: что такое fs_context

Когда ядро монтирует файловую систему, оно создаёт объект `fs_context` — контекст
монтирования, куда складываются параметры (`-o`). Параметры разбираются в
`legacy_parse_param`. В CVE-2022-0185 там **переполнение кучи**: при передаче
слишком длинного параметра данные пишутся за границу выделенного буфера.

Термин: **переполнение кучи (heap overflow)** — запись данных за пределами
выделенного блока в куче; позволяет испортить соседние объекты.

Эксплуатация требует, чтобы пользователь мог вызвать разбор параметров — обычно
через создание нового user namespace и монтирование `ext4`/`fuse`.

## Шаг 2: CVE-2022-0185 — от переполнения к root

Схема (по публичному PoC Crusaders of Rust):

1. Создаём user namespace (получаем CAP_SYS_ADMIN внутри него).
2. Открываем контекст ФС и передаём длинный параметр — переполняем буфер.
3. Спреим кучу `msg_msg` (System V IPC) так, чтобы переполнение задело
   подконтрольный объект.
4. Получаем примитив чтения/записи и перезаписываем `modprobe_path`.

Особенность: переполнение ограничено по длине, поэтому спрей и раскладка кучи
подбираются очень точно. На разных ядрах смещения разные.

## Шаг 3: CVE-2022-2588 — UAF в cls_route

Второй баг — в подсистеме **traffic-control** (net/sched). Фильтр `cls_route`
при определённой последовательности операций освобождает объект, но оставляет
на него ссылку. Получается use-after-free.

Термин: **traffic-control (tc)** — механизм ядра для управления трафиком
(очереди, фильтры, классификаторы). `cls_route` — один из фильтров.

Эксплуатация:

1. Создаём qdisc и фильтр `cls_route` в своём network namespace.
2. Триггерим удаление/замену, получая UAF.
3. Спреим кучу и захватываем контроль над освобождённым объектом.
4. Через примитив — root.

## Шаг 4: почему это важно для контейнеров

Обе уязвимости особенно ценились в контейнерных средах:

- CVE-2022-0185 позволяет **побег из контейнера**, потому что ядро общее для
  хоста и контейнера; получив root в контейнере, через уязвимость ядра получают
  root на хосте.
- CVE-2022-2588 работает даже без user namespace, если есть CAP_NET_ADMIN.

Именно поэтому в Kubernetes-аудитах проверяют: обновлено ли ядро ноды, ограничены
ли capabilities у подов, включён ли `userns` для непривилегированных.

## Шаг 5: полный прогон

```
$ ./exploit-0185
[*] creating user namespace...
[*] mounting context...
[*] heap overflow len=...
[*] spraying msg_msg...
[*] overwriting modprobe_path -> /tmp/p
[*] done
# id
uid=0(root) gid=0(root) groups=0(root)
```

Если user namespace запрещён, PoC печатает `unshare failed` — вектор недоступен.

## Шаг 6: KASLR и цепочка примитивов

Как и в любом kernel-эксплойте, после получения UAF нужно:

1. **Спрей** — занять освобождённый слот подконтрольным объектом. Часто
   используют `msg_msg` (System V IPC) или `sk_buff`. Их содержимое мы задаём
   сами, а ядро кладёт их в ту же кучу.
2. **Leak** — через подменённый объект прочитать адрес ядра (например, указатель
   в `msg_msg`), чтобы вычислить базу.
3. **Write** — записать по нужному адресу (перезаписать `modprobe_path` или
   `cred`).
4. **Trigger** — заставить ядро выполнить наш код (запустить неизвестный формат
   файла, если использован `modprobe_path`).

Каждый шаг проверяется отдельно: сначала убеждаются, что спрей «поймал» слот,
потом — что утечка верна, и только затем пишут.

## Шаг 7: почему эксплуатация хрупкая

Kernel-эксплойты 2022 года известны своей хрупкостью:

- **Раскладка кучи** зависит от версии ядра, конфигурации (`CONFIG_*`) и
  активных модулей. Один и тот же PoC на разных сборках падает.
- **SLUB freelist randomization** перемешивает порядок свободных слотов, из-за
  чего спрей надо повторять сотни раз.
- **KASAN/KASLR** в отладочных ядрах меняют поведение; PoC для «боевого» ядра не
  работает под отладкой.
- **Timing** — некоторые окна UAF очень узкие.

Поэтому хороший эксплойт печатает прогресс и умеет повторять попытки, пока не
выиграет гонку/спрей.

## Шаг 8: защита и аудит

Основные меры:

- **Обновление ядра** — единственный надёжный фикс обоих CVE.
- **Отключение unprivileged user namespaces** (`kernel.unprivileged_userns_clone=0`)
  ломает CVE-2022-0185 для непривилегированных пользователей.
- **Ограничение capabilities** у контейнеров: без CAP_NET_ADMIN нет `tc`/`nft`.
- **seccomp-профили** — блокируют вызовы `unshare`, `mount`, `keyctl`.

В Kubernetes аудите смотрят `securityContext.capabilities`, `allowPrivilegeEscalation`
и версию ядра ноды.

## Шаг 9: полный разбор одной строкой

Если сжать всё в одну фразу: **примитив памяти в ядре → спрей + утечка →
произвольная запись → финишер (`modprobe_path`) → root**. Все kernel-CVE
различаются только способом получить первый шаг; дальше схема почти всегда одна
и та же, и именно поэтому полезно выучить её один раз.

## Что если не сработало

| Симптом | Причина | Что делать |
|---|---|---|
| `unshare failed` | userns выключен | проверить `sysctl kernel.unprivileged_userns_clone` |
| panic | неверный спрей | остановиться, подобрать раскладку |
| нет root | offset не тот | сверить ядро и PoC |
| `Operation not permitted` | нет CAP_SYS_ADMIN | искать другой вектор |

## Где искать такие баги

Как и в случае nf_tables, лучшие источники — syzbot (публикует C-репродукторы
крашей ядра), git-история подсистем (`fs/`, `net/sched/`) с коммитами вида
«fix UAF», и материалы kernelCTF. Отдельно стоит следить за почтовыми рассылками
`linux-distros` и `oss-security`: там анонсируют критические фиксы ещё до
публичного раскрытия, что даёт время на аудит и подготовку патчей. Для атакующего
это же окно — время, чтобы понять баг до того, как он станет массово известен.

## Краткая шпаргалка

| Что | CVE-2022-0185 | CVE-2022-2588 |
|---|---|---|
| Тип | heap overflow | use-after-free |
| Подсистема | fs_context (монтирование) | net/sched cls_route |
| Условие | user namespace | CAP_NET_ADMIN |
| Примитив | переполнение → R/W | UAF → R/W |
| Применение | container escape | privesc/escape |

## Сравнение примитивов: переполнение vs UAF

Две уязвимости этого урока дают разные «входные» примитивы, и от этого зависит
вся дальнейшая стратегия.

**Переполнение (CVE-2022-0185).** Мы пишем данные за границу буфера. Плюс: можно
сразу испортить соседний объект, зная раскладку. Минус: длина ограничена, нужно
точно попасть в цель и не задеть ничего лишнего (иначе паника).

**Use-after-free (CVE-2022-2588).** Мы получаем указатель на освобождённую
память. Плюс: объект можно заменить своим (спрей), получив полный контроль над
его полями. Минус: нужно выиграть момент между free и использованием (окно UAF),
а также правильно подобрать объект-заполнитель.

Общий приём — **heap grooming** (укладка кучи): серией выделений и освобождений
добиваются, чтобы нужный объект оказался рядом с уязвимым. Это отдельный навык,
который приходит с опытом; в CTF ему посвящены целые задания.

## Практические заметки по эксплуатации

- **Проверяйте `dmesg`** — ядро пишет туда следы UAF и паник; по ним видно, что
  эксплойт «попал».
- **Не гонитесь за 100% надёжностью** — kernel-эксплойты часто имеют шанс успеха
  30–70%; их запускают в цикле.
- **Сохраняйте стабильность цели** — паника ядра уронит всю машину. Если цель —
  единственный доступ, потеряете и его.
- **Собирайте под целевую версию** — заголовки ядра должны совпадать, иначе
  структуры «поедут». Всегда сохраняйте версию ядра и конфиг цели для отладки.

## Что такое user namespace и зачем он тут

**User namespace** — механизм ядра, позволяющий непривилегированному процессу
«притвориться» root внутри своего namespace: он получает полный набор
capabilities (включая CAP_SYS_ADMIN) над объектами, созданными в этом
namespace. Хост при этом защищён: реальный root у процесса не появляется.

Именно поэтому CVE-2022-0185 эксплуатируется так широко: чтобы разобрать
параметры `fs_context`, нужен CAP_SYS_ADMIN, а user namespace его выдаёт без
всяких привилегий. Проверить, разрешён ли unprivileged userns:

```
$ cat /proc/sys/kernel/unprivileged_userns_clone
1
$ unshare -Ur id
uid=0(root) gid=0(root) groups=0(root)
```

Если `unshare -Ur id` печатает `uid=0`, значит создание userns разрешено, и
CVE-2022-0185 становится доступной. Если команда падает с `Operation not
permitted` — вектор требует другого пути (или цель пропатчена по конфигу).

## Что мы теперь знаем

- `fs_context` разбирает параметры монтирования и переполняется на длинном входе.
- CVE-2022-0185 часто требует user namespace.
- CVE-2022-2588 — UAF в traffic-control (`cls_route`).
- Обе ведут к root и используются для побега из контейнеров.
- Ключевые проверки — версия ядра и доступные capabilities.
