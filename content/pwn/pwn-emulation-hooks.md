Хуки превращают эмулятор из «проигрывателя байтов» в контролируемую среду. Вместо того чтобы реализовывать каждый syscall, вы перехватываете нужный и возвращаете ровно то, что нужно для дальнейшего анализа. Это ключевой навык для pwn-задач с анти-анализом, для malware-анализа и для автоматизации реверса: один раз написав хук, вы прогоняете бинарь сотни раз с разными входами.

В этом уроке — продвинутые приёмы хуков в Unicorn и Qiling, практические сценарии (подмена результата функции, логирование, «раскрутка» цикла) и сравнение с Frida. Материал завершает модуль `pwn-emulation`.

## Зачем продвинутые хуки

Базовый хук печатает событие. Продвинутый — **меняет состояние**: переписывает регистры, подменяет память, пропускает инструкции, меняет поток исполнения. Именно это нужно, когда программа:

- проверяет наличие отладчика/эмулятора и отказывается работать;
- вызывает функции, которых нет в эмуляторе;
- требует сетевого ответа, которого вы не можете дать;
- использует длинный цикл, который нужно «прокрутить» быстро.

## Хуки в Unicorn: код, память, инструкции

Unicorn предоставляет несколько типов хуков:

| Хук | Когда вызывается | Типичное применение |
|---|---|---|
| `UC_HOOK_CODE` | перед каждой инструкцией | трассировка, подмена регистров |
| `UC_HOOK_BLOCK` | на базовый блок | оптимизированная трассировка |
| `UC_HOOK_MEM_READ` | чтение памяти | перехват доступа к данным |
| `UC_HOOK_MEM_WRITE` | запись памяти | детект порчи данных |
| `UC_HOOK_INSN` | конкретная инструкция | `syscall`, `cpuid`, `rdtsc` |

Пример перехвата `cpuid` (частая anti-VM проверка) и подмены результата:

```python
from unicorn import *
from unicorn.x86_const import *

def hook_cpuid(mu, user_data):
    # вернуть «обычный» CPU: eax=0x756e6547 (GenuineIntel часть)
    mu.reg_write(UC_X86_REG_RAX, 0x0000000b)
    mu.reg_write(UC_X86_REG_RBX, 0x756e6547)
    mu.reg_write(UC_X86_REG_RCX, 0x6c65746e)
    mu.reg_write(UC_X86_REG_RDX, 0x49656e69)

mu.hook_add(UC_HOOK_INSN, hook_cpuid, None, 1, 0, UC_X86_INS_CPUID)
```

Так программа «видит» обычный Intel и продолжает работу.

## Хуки в Qiling: API и адреса

В Qiling высокоуровневый API проще:

```python
from qiling.const import QL_INTERCEPT

# перехватить функцию по имени (Linux syscall)
ql.os.set_syscall("open", lambda ql, path, flags, mode: 3)

# перехватить API по имени (Windows)
ql.os.set_api("IsDebuggerPresent", lambda ql, *a: 0, QL_INTERCEPT.CALL)

# хук на конкретный адрес
def at_check(ql):
    ql.reg.rax = 1          # «проверка пройдена»
ql.hook_address(at_check, 0x400123)
```

`QL_INTERCEPT.CALL` означает «заменить вызов», `QL_INTERCEPT.ENTER`/`EXIT` — «до/после». Это позволяет, например, логировать аргументы перед вызовом и возвращаемое значение после.

## Frida vs эмуляция: когда что

| Критерий | Эмуляция (Unicorn/Qiling) | Frida (динамика) |
|---|---|---|
| Нужна ли реальная ОС | нет | да |
| Чужая архитектура | да | нет |
| Скорость | медленнее | быстрее |
| Скрытность | высокая | зависит от anti-Frida |
| Простота хуков | средняя | высокая (JS) |

Эмуляция выигрывает, когда нельзя запустить бинарь (чужая арка, malware, анти-отладка). Frida — когда бинарь работает нативно и нужна скорость/удобство. На практике их комбинируют: Frida для быстрого прототипа, эмуляция для «стерильного» анализа.

## Разобранный пример: подмена результата функции

Задача: программа вызывает `getrandom()` и использует результат как ключ; нужно сделать ключ предсказуемым. Под Qiling:

```python
def fake_getrandom(ql, buf, buflen, flags):
    ql.mem.write(buf, b"\x00" * buflen)   # нулевой ключ
    return buflen

ql.os.set_syscall("getrandom", fake_getrandom)
ql.run()
```

Теперь ключ всегда нулевой, и крипто-логику можно предсказать. Аналогично подменяют `time`, `getpid`, `ptrace`, результаты `read` с `/dev/urandom`.

## Разобранный пример: логирование и автоперехват

Автоматический реверс строится на хуке кода с дизассемблером (Capstone) и логированием ветвлений:

```python
from capstone import Cs, CS_ARCH_X86, CS_MODE_64
md = Cs(CS_ARCH_X86, CS_MODE_64)

def hook_code(mu, address, size, user_data):
    insn = next(md.disasm(bytes(mu.mem_read(address, size)), address))
    if insn.mnemonic in ("cmp", "test", "je", "jne"):
        print(f"{address:#x}: {insn.mnemonic} {insn.op_str}  flags={mu.reg_read(UC_X86_REG_EFLAGS):#x}")
```

Фильтруя только сравнения и переходы, вы получаете «скелет» проверки: какие байты сравниваются, куда идут ветки. Это ускоряет восстановление алгоритма в разы.

## Практика: «раскрутка» цикла

Если программа проверяет ввод побайтово в цикле, можно «раскрутить» цикл хуком: на каждой итерации записывать нужный байт и пропускать сравнение. Альтернативно — перехватить функцию сравнения (`strcmp`) и логировать оба аргумента:

```python
def on_strcmp(ql, a, b):
    s1 = ql.mem.string(a)
    s2 = ql.mem.string(b)
    print(f"strcmp({s1!r}, {s2!r})")
    return 0     # «строки равны»
ql.os.set_api("strcmp", on_strcmp, QL_INTERCEPT.CALL)
```

Так вы получаете и ожидаемую строку (второй аргумент), и то, что ввели.

## Практика: эмуляция сетевого взаимодействия

Многие бинари общаются с сервером: получают ключ, ждут ответа, проверяют подпись. Под эмулятором сеть можно полностью подменить хуками на `socket`/`recv`/`send`. В Qiling:

```python
def fake_recv(ql, fd, buf, length, flags):
    data = b"RESPONSE"          # «ответ сервера»
    ql.mem.write(buf, data)
    return len(data)

ql.os.set_syscall("recv", fake_recv)
ql.os.set_syscall("recvfrom", fake_recv)
```

Это позволяет пройти сетевую часть и добраться до локальной логики, не поднимая сервер. В Unicorn аналогично перехватывается `syscall` и подменяются регистры-результаты. Такой подход особенно полезен для malware, который ждёт C2-команду: вы «становитесь» сервером и смотрите, что образ делает дальше.

## Практика: автоматический брутфорс проверки

Хук можно использовать не только для обхода, но и для **ускорения** брутфорса. Эмулируя функцию проверки под Unicorn, вы за секунды прогоняете миллионы кандидатов. Комбинация с хуком на функцию сравнения даёт «оракул»:

```python
correct = []
def on_memcmp(ql, a, b, n):
    s1 = ql.mem.read(a, n)
    s2 = ql.mem.read(b, n)
    # фиксируем, сколько байт совпало, — это подсказка для брутфорса
    match = sum(1 for x, y in zip(s1, s2) if x == y)
    print(f"match {match}/{n}")
    return 0
ql.os.set_api("memcmp", on_memcmp, QL_INTERCEPT.CALL)
```

Если сравнение побайтовое, число совпавших байт показывает прогресс — классический timing-оракул, но детерминированный. Так восстанавливают флаги и ключи без запуска на реальной цели.

## Сравнение с реальной отладкой: плюсы и минусы

Эмуляция с хуками — не замена отладчику, а другой инструмент. Плюсы: полный контроль над временем и окружением, возможность «отмотать» состояние (запустить заново), безопасность (malware не убежит), работа с чужой архитектурой, детерминизм. Минусы: эмулятор реализует не всё (некоторые инструкции, syscall, аппаратные особенности), производительность ниже, а поведение может отличаться от реального из-за неполной модели.

Практическое правило: используйте эмуляцию, когда цель **не запускается** или **не должна запускаться** нативно (malware, чужая арка, анти-отладка). Используйте gdb/pwndbg, когда нужно точно повторить реальный сценарий эксплойта, особенно для heap-эксплуатации, где поведение аллокатора критично. И помните, что хуки могут «сгладить» реальную гонку или утечку — не делайте выводов о безопасности цели только по эмуляции.

Для pwn есть отдельная тонкость: эксплойт, отработавший под эмулятором, не обязан работать на реальной цели, потому что адреса, ASLR и поведение libc отличаются. Эмуляцию применяйте для **понимания** и **поиска**, а финальный эксплойт отлаживайте на настоящей цели через `pwn-gdb-pwndbg`.

Наконец, помните о воспроизводимости: сохраняйте сценарии хуков в отдельные файлы и запускайте их одной командой. Это превращает разовый анализ в повторяемый пайплайн, который можно применять к новым версиям того же бинаря. Хороший сценарий документирован: что перехватывается, что подменяется и зачем — чтобы через месяц вы сами поняли свою логику.

## Отладка хуков и типичные грабли

Хуки сами по себе могут быть источником ошибок. Полезно вести лог каждого перехвата и проверять, что аргументы имеют ожидаемый тип. В Qiling аргументы приходят как Python-числа (адреса), поэтому строки читаются через `ql.mem.string(addr)`, а байты — через `ql.mem.read(addr, n)`. Если забыть это, вы получите «адрес» вместо содержимого и удивитесь, почему сравнение не работает.

Ещё одна грабля — рекурсия: если ваш хук вызывает функцию, которая снова триггерит тот же хук, эмуляция зациклится. Например, хук на `strcmp`, который внутри тоже вызывает `strcmp`. Решение — флаг «внутри хука» или вызов «сырой» реализации через `ql.os.set_api(...)` до перехвата. Всегда тестируйте хук на простом входе и смотрите на трассу, прежде чем полагаться на результат.

## Частые ошибки

- **Хук меняет тайминг.** В динамике хуки влияют на гонки; в эмуляции — на «поведение, зависящее от времени».
- **Забыть `UC_HOOK_INSN` для `syscall`.** Обычные хуки кода не перехватывают семантику syscall.
- **Слишком широкий хук.** `UC_HOOK_CODE` на всю программу печатает гигабайты; ограничивайте диапазон.
- **Неверный тип перехвата.** `CALL` vs `ENTER`/`EXIT` в Qiling меняет семантику.
- **Подмена без учёта последствий.** Изменив регистр, вы можете увести программу в ветку, которую не исследовали.

## Что дальше / решение

- Соберите собственный «автологгер» проверок на Capstone — это ваш личный инструмент.
- Изучите `pwn-symbolic-angr` — символьное исполнение решает похожие задачи иначе.
- Для нативного анализа загрузите навык Frida из ветки reversing.
- Комбинируйте эмуляцию с `pwn-unicorn-emulation` и `pwn-qiling-emulation`.
