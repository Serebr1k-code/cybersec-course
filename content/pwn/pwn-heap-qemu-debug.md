## Вопрос, с которого всё начинается

Ты запустил ARM-бинарь под qemu и даже подключил gdb. Но привычные команды `heap`, `bins`, `tcache` из pwndbg не работают или показывают мусор. Дело в том, что для разбора кучи нужны **символы glibc** — а в cross-arch отладке их по умолчанию нет. В этом уроке настроим отладку так, чтобы heap-команды снова заработали.

## Наш пример

Возьмём `heapnote` (ARM-бинарь с менеджером заметок) и запустим под qemu с открытой отладкой:

```
$ qemu-arm -g 1234 -L ./rootfs ./heapnote
```

В другом терминале подключаемся:

```
$ gdb-multiarch ./heapnote
(gdb) set architecture arm
(gdb) target remote :1234
0x000104f0 in _start ()
```

Символы основного бинарника подхватились (`not stripped`), но glibc — нет. Проверим:

```
(gdb) p &main_arena
No symbol "main_arena" in current context.
```

`main_arena` — центральная структура аллокатора glibc (списки свободных chunk). Без неё pwndbg не может разобрать кучу. Значит, надо **подгрузить символы гостевой libc**.

## Шаг 1: указываем gdb, где искать библиотеки

Ключевая настройка — **sysroot**, тот же корень, что мы дали qemu:

```
(gdb) set sysroot ./rootfs
(gdb) set solib-search-path ./rootfs/lib:./rootfs/usr/lib
```

После этого попросим gdb найти уже загруженные библиотеки:

```
(gdb) info sharedlibrary
From        To          Syms Read   Shared Object Library
0x00000000  0x00000000  Yes         /lib/ld-linux-armhf.so.3
0x00000000  0x00000000  Yes         ./rootfs/lib/libc.so.6
```

Если `Syms Read = Yes` — символы загружены. Если `No`, укажем вручную:

```
(gdb) add-symbol-file ./rootfs/lib/libc.so.6 0x76f00000
```

Адрес `0x76f00000` — база, по которой libc загружена в эмулируемом процессе (её видно из `info sharedlibrary` или из вывода qemu при старте). Теперь `main_arena` доступна, и heap-команды оживают.

## Шаг 2: разбираем heap

После загрузки символов работают привычные команды:

```
(gdb) heap
Allocated chunk | PREV_INUSE
Addr: 0x76fff000
Size: 0x101
...
(gdb) bins
tcachebins
0x20 [  1]: 0x76fff010
fastbins
empty
unsortedbin
empty
```

`bins` показывает **tcache** и **fastbin** — те же структуры, что на x86-64. Значит, вся методология heap-эксплуатации применима: ты видишь, куда указывают указатели `next`, где лежат освобождённые chunk.

Посмотреть «сырую» память вокруг chunk:

```
(gdb) x/16gx 0x76fff000
0x76fff000: 0x00000000  0x00000101   0x00000000  0x00000000
```

Первые два поля — `prev_size` и `size` (размер с флагами в младших битах). Дальше — данные chunk. Всё как на x86-64, только адреса в 32-битном пространстве.

## Шаг 3: находим базу кучи

Под qemu **`info proc mappings` не работает** (gdb не видит `/proc` эмулируемого процесса). Поэтому базу кучи получают иначе:

- Из регистра **`brk`** или из указателя, который вернул `malloc` (посмотри аргумент/результат функции в момент вызова).
- Через `p main_arena.top` — вершина кучи.
- Через адрес любого chunk, который ты уже знаешь из эксплойта.

Это важное отличие от x86-отладки, где `vmmap`/`info proc mappings` показывают карту памяти одним движением. Здесь карту приходится собирать «по кусочкам».

## Шаг 4: точки останова и watchpoints

Остальные инструменты работают как обычно:

```
(gdb) b malloc
(gdb) b *0x000106a0
(gdb) watch *(int*)0x76fff010     # следить за изменением поля
(gdb) c
```

`watch` особенно полезен для гонок и UAF: он останавливает процесс в момент, когда кто-то **трогает** нужный адрес. Под qemu watchpoints работают медленнее (эмуляция), но работают.

Ещё приём — **сравнивать состояния**: поставь брейкпоинт до и после операции и посмотри, как изменились `bins`. Так быстро находится, какой `free` реально освободил нужный chunk.

## Шаг 5: типичные проблемы

- **`info proc mappings` пусто** — норма под remote-отладкой; используй `main_arena.top` или регистры.
- **`main_arena not found`** — не подгружены символы libc; проверь `sysroot` и `add-symbol-file`.
- **Адреса «плывут»** — под qemu раскладка может отличаться от железа; не прошивай адреса жёстко, пока не сверишь с реальной целью.
- **Heap-команды pwndbg падают** — чаще всего это несовпадение версии glibc: инструмент парсит структуры под свою версию, а в rootfs лежит другая. Сверь версии (`p (char*)gnu_get_libc_version()`).

## Шаг 6: практический сценарий — ловим UAF

Соберём всё вместе на типичной задаче. В `heapnote` есть use-after-free: после `free(note)` указатель не обнуляется, и через `edit` можно писать в освобождённый chunk.

Порядок отладки:

1. **Ставим брейкпоинт на `free`** и смотрим `bins` **до** и **после**:
   ```
   (gdb) b free
   (gdb) c
   (gdb) bins
   ```
   Освобождённый chunk появится в `tcachebins` с указателем в поле `next`.
2. **Ищем, что окажется в этом chunk при следующем `malloc`.** Если между `free` и `malloc` мы можем записать в поле `next` (через UAF), tcache вернёт нам **подконтрольный адрес**.
3. **Следим за полем `next` watchpoint-ом**:
   ```
   (gdb) watch *(long*)0x76fff010
   ```
   Как только наше значение запишется — мы знаем, что отравление tcache сработало.
4. **Проверяем safe-linking.** При записи в `next` значение шифруется: `next = target ^ (chunk_addr >> 12)`. Если записать «сырой» target, `malloc` вернёт мусор и упадёт. В отладчике видно, что именно оказалось в `next` после записи, — сверяй с ожидаемым.
5. **Ловим момент возврата target** брейкпоинтом на выходе `malloc` и смотрим возвращаемое значение в регистре `r0` (на ARM).

Так отладка под qemu превращается в обычную работу с chunk: ты видишь `next`, ловишь запись watchpoint-ом и проверяешь, куда вернулся `malloc`. Разница с x86 только в регистрах и в том, что карту памяти приходится получать вручную. Именно поэтому так важно сначала **настроить символы glibc** — без них ни `bins`, ни `watch` по полю chunk осмысленно не проверить.

## Как ускорить cross-arch heap-отладку

Несколько приёмов, которые экономят время:

- **Скриптуй gdb.** Вместо ручного ввода команд напиши `.gdbinit` или `-ex`-строки: `set sysroot`, `add-symbol-file`, брейкпоинты — всё автоматически при старте.
- **Симлинкуй libc.** Иногда проще положить нужную libc рядом с бинарником и указать на неё, чем бороться с `sysroot`.
- **Сравнивай с x86-версией.** Если задача существует и под x86-64 (часто бывает), сначала отладь на ней — механика heap та же, а отладка удобнее. Потом перенеси адреса на ARM.
- **Держи под рукой `pwndbg`.** Команды `heap`, `bins`, `vis_heap_chunks`, `tcache` работают и под gdb-multiarch — если символы загружены.

Главная мысль: cross-arch heap-отладка — это **та же x86-отладка**, только с ручной настройкой символов и ручным поиском карты памяти. Настроил один раз — дальше работаешь как обычно.

## Что мы теперь знаем

- Для отладки heap нужны **символы гостевой glibc** — их подгружают через `set sysroot` / `add-symbol-file`.
- После этого работают `heap`, `bins`, `x/` — как на x86-64.
- **`info proc mappings` под qemu не работает**; базу кучи берут из `main_arena.top` или регистров.
- Watchpoints и брейкпоинты работают; ими удобно ловить UAF и гонки.
- Главный источник проблем — **несовпадение версии glibc** с той, под которую настроен отладчик.

## Куда дальше

Мы научились отлаживать heap под эмуляцией. Дальше — **инструменты анализа**: санитайзеры (ASan/UBSan), фаззинг и символьное исполнение, которые помогают **находить** баги, а не только эксплуатировать уже найденные. А пока запомни главное: **подгрузи символы гостевой libc — и heap-отладка под qemu станет такой же привычной, как на x86-64.**

- **CTF Pwn:** cross-arch heap-задачи.
- **Embedded/IoT:** отладка прошивок без железа.
