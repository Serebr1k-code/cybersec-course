## Вопрос, с которого всё начинается

До сих пор мы переполняли **стек** — область с предсказуемой раскладкой, где рядом лежит адрес возврата. Но многие уязвимости живут в **куче**: динамической памяти, которую программа просит через `malloc` и отдаёт через `free`.

В куче нет адреса возврата. Как её эксплуатировать? Оказывается, аллокатор хранит служебные данные **рядом** с данными программы — и если их испортить, можно получить примитив чтения или записи. Сегодня разберём, как куча устроена.

## Наш пример: три malloc и два free

```c
#include <stdlib.h>
int main(void) {
    char *a = malloc(0x28);
    char *b = malloc(0x28);
    char *c = malloc(0x28);
    free(b);
    free(a);
    return 0;
}
```

Скомпилируем и посмотрим в pwndbg, что происходит с памятью:

```bash
$ gcc -o chall chall.c
$ gdb -q ./chall
(gdb) b main
(gdb) run
(gdb) heap
```

Прежде чем разбирать вывод, поймём, что такое **чанк**.

## Шаг 1. Чанк и его заголовок

Каждое выделение — это **чанк**. Минимальный размер на amd64 — `0x20` байт: `0x10` заголовок плюс `0x10` данных. Заголовок устроен так:

| Поле | Размер | Назначение |
|---|---|---|
| `prev_size` | 8 | размер предыдущего чанка (если свободен) |
| `size` | 8 | размер текущего + флаги |
| `fd` | 8 | указатель вперёд (только у свободных) |
| `bk` | 8 | указатель назад (только у свободных) |
| user data | ... | полезные данные |

Младшие 3 бита `size` — это **флаги**, потому что размер всегда кратен 16. Главный из них — `PREV_INUSE` (значение 1): он говорит, что предыдущий чанк занят. Отсюда и размер с флагом: занятый чанк `0x40` хранит `size = 0x41`.

## Шаг 2. Что делает malloc

`malloc(n)` округляет размер до кратного 16 (`(n + 8 + 15) & ~15`), добавляет заголовок и ищет подходящий чанк:

1. сначала в **tcache** (для размеров ≤ `0x410`),
2. затем в fastbins, smallbins, unsorted bin, largebins,
3. если ничего — режет **top chunk** (остаток невыделенной памяти).

Для очень больших размеров (≥ 128 КБ) используется `mmap`, и чанк помечается флагом `IS_MMAPPED`.

## Шаг 3. Что делает free

`free(p)` определяет размер чанка и кладёт его:

- в **tcache**, если размер подходит и бин не полон,
- иначе в **fastbin** (≤ `0x80` на amd64),
- иначе выполняет **консолидацию**: если сосед свободен — объединяет.

Объединение использует `prev_size` и флаг `PREV_INUSE`. Ошибки в этих полях (off-by-null, перезапись `prev_size`) ведут к известным атакам.

## Шаг 4. Bins: классификация

Свободные чанки раскладываются по «корзинам»:

| Bin | Размер | Особенность |
|---|---|---|
| tcache | ≤ 0x410 | на поток, LIFO, нет проверок (до 2.32) |
| fastbin | ≤ 0x80 | LIFO, одинарный список, без консолидации |
| smallbin | ≤ 0x3f0 | двусвязный, точный размер |
| largebin | > 0x3f0 | двусвязный, отсортирован по размеру |
| unsorted | — | «карантин» перед сортировкой |

Посмотрим наш пример в pwndbg:

```text
pwndbg> bins
tcachebins
0x40 [  2]: 0x5555557592a0 —▸ 0x555555759260 ◂— 0
```

После `free(b); free(a)` оба чанка попали в tcache размера `0x40`. Список `a -> b`: последний освобождённый (`a`) — в голове. Это **LIFO** (last in, first out).

## Шаг 5. tcache — самый важный bin

С glibc 2.26 появился **tcache** — кеш на поток, ускоряющий `malloc`/`free`. Каждый бин — односвязный список до 7 чанков. До glibc 2.32 в tcache **не было проверок**, что делало **tcache poisoning** тривиальным: перезаписав `fd` свободного чанка, ты заставляешь следующий `malloc` вернуть произвольный адрес.

```c
char *a = malloc(0x40);   // чанк A
char *b = malloc(0x40);   // чанк B
free(a);
// UAF: пишем в a->fd произвольный адрес target
*(long*)a = target;
malloc(0x40);             // вернёт A
char *c = malloc(0x40);   // вернёт target!
```

С glibc 2.32 добавили **safe-linking**: `fd` хранится как `ptr ^ (chunk_addr >> 12)`, поэтому для обхода нужна утечка heap-адреса. С 2.29 второе поле свободного tcache-чанка хранит `tcache_key`, ловящий double-free.

## Шаг 6. Как исследовать кучу

```text
(gdb) heap                # все чанки (pwndbg)
(gdb) bins                # содержимое бин-списков
(gdb) vis_heap_chunks     # визуализация
(gdb) tcache              # tcache-бин
(gdb) x/4gx chunk_ptr
```

pwndbg показывает чанки с размерами, флагами и связями — незаменимо при отладке. `parseheap` в gef делает то же самое.

## Шаг 7. Какие метаданные атакуют

| Поле | Атака |
|---|---|
| `fd`/`bk` | tcache poisoning, fastbin dup |
| `prev_size` | House of Einherjar |
| `size` (PREV_INUSE) | off-by-null, overlap |
| top `size` | House of Force |
| `fd_nextsize`/`bk_nextsize` | largebin attack |

## Разбор malloc/free по шагам

Проследим последовательность на конкретных размерах. `malloc(0x28)` округляется так: `0x28 + 8` (заголовок) `= 0x30`, затем до кратного 16 — `0x40`. Значит, все три наших чанка имеют размер `0x40`.

```c
char *a = malloc(0x28);   // чанк 0x40
char *b = malloc(0x28);   // чанк 0x40
char *c = malloc(0x28);   // чанк 0x40
free(b);                  // b -> tcache[0x40]
free(a);                  // a -> tcache[0x40], голова = a, a->fd = b
```

После этого `tcache[0x40]` = `a -> b -> NULL`. Следующий `malloc(0x28)` вернёт `a`, а голова списка станет `b`. Если у нас есть UAF на `a`, мы можем переписать `a->fd` и подсунуть произвольный адрес — это и есть tcache poisoning.

Проверим в pwndbg:

```text
Allocated chunk | PREV_INUSE
Addr: 0x555555757000
Size: 0x40 (with flag bits: 0x41)

Free chunk (tcache) | PREV_INUSE
Addr: 0x555555757040
Size: 0x40 (with flag bits: 0x41)
fd: 0x0
```

Так видно, какой чанк куда попал, и можно проверить, что после poisoning голова списка указывает на цель.

## Взаимодействие с top и brk

Когда tcache и bins пусты, `malloc` режет **top chunk** — остаток невыделенной памяти в конце сегмента. Top растёт: `brk` сдвигает границу heap вверх. Если `brk` не может расширить сегмент, создаётся новый через `mmap`. Это важно для атак, где чанк должен лежать рядом с top (например, House of Force).

## На что смотреть дальше

- **Размер округляется.** `malloc(0x18)` вернёт чанк `0x20`.
- **tcache LIFO.** Последний освобождённый — первый выданный.
- **Safe-linking (2.32+).** `fd` обфусцирован, нужна утечка heap.
- **`tcache_key` (2.29+).** Ловит double-free.
- **fastbins не консолидируются**, остальные — да.
- **Современные glibc добавили много проверок** — часть атак работает только на старых версиях.

## Что мы теперь знаем

- Куча управляется аллокатором; служебные данные лежат рядом с данными.
- Чанк = заголовок (`prev_size`, `size`, `fd`, `bk`) + данные.
- `malloc` берёт из tcache/fastbin/bins или режет top; `free` кладёт обратно.
- tcache — LIFO, до 7 чанков, с 2.32 защищён safe-linking.
- Испортив `fd`, получают tcache poisoning — произвольную аллокацию.
