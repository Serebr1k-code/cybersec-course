Куча glibc — самая богатая на уязвимости подсистема userland. Понимание её устройства (чанки, бин-списки, tcache, метаданные) необходимо для эксплуатации use-after-free, double-free, overflow и десятков «House of» атак. Этот урок — фундамент: как `malloc`/`free` управляют памятью, как выглядит чанк, что такое top chunk, bins, tcache и метаданные, и как из этого вырастают примитивы чтения и записи.

## Зачем нужна куча и чем она отличается от стека

Стек выделяется фиксированно и управляется компилятором; куча — динамическая область, которой управляет аллокатор. Программа вызывает `malloc(size)`, получает указатель, а `free(ptr)` возвращает блок. Аллокатор решает, откуда взять память и как переиспользовать освобождённое. Все баги кучи — следствие того, что аллокатор хранит служебные данные рядом с пользовательскими, и их можно испортить.

## Устройство чанка

Каждое выделение — чанк. Минимальный размер на amd64 — 0x20 байт (0x10 заголовок + 0x10 данные). Структура:

| Поле | Размер | Назначение |
|---|---|---|
| `prev_size` | 8 | размер предыдущего чанка (если свободен) |
| `size` | 8 | размер текущего + флаги (PREV_INUSE=1, IS_MMAPPED=2, NON_MAIN_ARENA=4) |
| `fd` | 8 | указатель вперёд (только для свободных) |
| `bk` | 8 | указатель назад (только для свободных) |
| user data | ... | полезные данные |

Младшие 3 бита `size` — флаги, потому что размер всегда кратен 16. `PREV_INUSE` в текущем чанке означает, что предыдущий занят. `prev_size` предыдущего чанка валиден только если предыдущий свободен.

## Алгоритм malloc

```c
void *p = malloc(n);
```

`malloc` округляет `n` до 16 (на amd64: `(n + 8 + 15) & ~15`), добавляет заголовок и ищет подходящий чанк: сначала в tcache (для размеров ≤ 0x410), затем в fastbins, smallbins, unsorted bin, largebins; если ничего — режет top chunk. Для больших размеров (≥ mmap_threshold, обычно 128 КБ) используется `mmap`, и такой чанк помечается `IS_MMAPPED`.

## Алгоритм free

```c
free(p);
```

`free` определяет размер, кладёт чанк в tcache (если размер подходит и tcache не полон), иначе в fastbin (≤ 0x80 на amd64), иначе выполняет консолидацию: если сосед свободен — объединяет; если освободился top — возвращает память. Объединение использует `prev_size` и флаг `PREV_INUSE`; ошибки в них (off-by-null, перезапись `prev_size`) ведут к известным атакам.

## Bins: классификация

| Bin | Размер | Особенность |
|---|---|---|
| tcache | ≤ 0x410 | per-thread, LIFO, нет проверок (до 2.32) |
| fastbin | ≤ 0x80 | LIFO, одинарный список, без консолидации |
| smallbin | ≤ 0x3f0 | двусвязный, точный размер |
| largebin | > 0x3f0 | двусвязный, отсортирован по размеру |
| unsorted | — | «карантин» перед сортировкой |

## Top chunk и Wilderness

Top chunk — остаток невыделенной памяти в конце heap-сегмента. Когда bins пусты, `malloc` режет top. Атаки на top (`House of Force`) перезаписывают его `size` огромным значением и заставляют `malloc` вернуть произвольный адрес.

## tcache: самый важный bin

С glibc 2.26 появился tcache — кеш на поток, ускоряющий `malloc`/`free`. Каждый бин — односвязный список до 7 чанков (по умолчанию). До glibc 2.32 в tcache не было проверок, что сделало tcache poisoning тривиальным: перезапись `fd` свободного чанка заставляет `malloc` вернуть произвольный адрес. С 2.32 добавлена safe-linking (XOR указателя с адресом>>12), обход которой требует утечки heap-адреса.

## Практический пример: tcache poisoning

```c
char *a = malloc(0x40);   // чанк A
char *b = malloc(0x40);   // чанк B (защита от top)
free(a);
// UAF: пишем в a->fd произвольный адрес target
*(long*)a = target;
malloc(0x40);             // вернёт A
char *c = malloc(0x40);   // вернёт target!
```

```python
from pwn import *
p = process('./chall')
# ... получаем UAF и записываем target в fd ...
p.send(p64(target))
# теперь malloc дважды вернёт target
```

## Как исследовать кучу

```bash
gdb ./chall
(gdb) heap                  # pwndbg: все чанки
(gdb) bins                  # содержимое бин-списков
(gdb) vis_heap_chunks       # визуализация
(gdb) tcache                # tcache-бин
(gdb) x/4gx chunk_ptr
```

pwndbg показывает чанки с размерами, флагами и связями — это незаменимо при отладке. `parseheap` в gef делает то же самое.

## Метаданные, которые атакуют

| Поле | Атака |
|---|---|
| `fd`/`bk` | tcache poisoning, fastbin dup |
| `prev_size` | House of Einherjar |
| `size` (PREV_INUSE) | off-by-null, overlap |
| top `size` | House of Force |
| `fd_nextsize`/`bk_nextsize` | largebin attack |

## Тонкости и подводные камни

- **Размер округляется.** `malloc(0x18)` вернёт чанк 0x20.
- **tcache LIFO.** Последний освобождённый — первый выданный.
- **Safe-linking (2.32+).** `fd` хранится как `ptr ^ (chunk_addr >> 12)`.
- **Key в tcache (2.29+).** Второе поле свободного tcache-чанка хранит `tcache_key`, ловящий double-free.
- **Консолидация.** fastbins не консолидируются, остальные — да.
- **Top chunk.** Растёт при нехватке памяти через `brk`/`mmap`.
- **Проверки glibc.** Современные версии добавили много проверок; часть атак работает только на старых.

## Что дальше / решение

Дальше: `pwn-heap-tcache` (tcache poisoning подробно), `pwn-heap-uaf` (use-after-free), `pwn-fastbin-dup` (fastbin attack), `pwn-unsortedbin-attack`. Практический алгоритм: (1) определите версию glibc; (2) найдите тип бага (UAF/double-free/overflow); (3) выберите бин, соответствующий размеру; (4) постройте примитив (утечка через unsorted bin, запись через tcache); (5) нацельтесь на `__free_hook`, `_IO_2_1_stdout_` или GOT. Куча — это марафон, но освоив её базовое устройство, вы откроете половину сложных pwn-задач.

## Разбор malloc/free по шагам на конкретном примере

Рассмотрим последовательность и посмотрим, что происходит с чанками.

```c
char *a = malloc(0x28);   // чанк 0x40 (0x28 -> +8 заголовок -> 0x30 -> округление 0x40)
char *b = malloc(0x28);   // ещё 0x40
char *c = malloc(0x28);   // ещё 0x40
free(b);                  // b -> tcache[0x40]
free(a);                  // a -> tcache[0x40], голова = a, a->fd = b
```

После этого `tcache[0x40]` = `a -> b -> NULL`. Следующий `malloc(0x28)` вернёт `a`, а `tcache[0x40]` станет `b`. Если у нас есть UAF на `a`, мы можем переписать `a->fd` и подсунуть произвольный адрес.

## Проверка в GDB

```bash
gdb ./chall
(gdb) b malloc
(gdb) run
(gdb) heap
(gdb) bins
```

pwndbg выведет примерно:

```
Allocated chunk | PREV_INUSE
Addr: 0x555555757000
Size: 0x40 (with flag bits: 0x41)

Free chunk (tcache) | PREV_INUSE
Addr: 0x555555757040
Size: 0x40 (with flag bits: 0x41)
fd: 0x0
```

Это позволяет точно увидеть, какой чанк куда попал, и проверить, что после poisoning голова списка указывает на цель.

## Взаимодействие чанков с top и brk

Когда tcache и bins пусты, `malloc` режет top chunk. Top растёт: `brk` сдвигает границу heap вверх. Если `brk` не может расширить сегмент, создаётся новый сегмент через `mmap` (arena). Понимание этого важно для атак, где требуется, чтобы чанк лежал рядом с top (например, House of Force).

## Overlap и консолидация

Если испортить `size` чанка (off-by-one/off-by-null), можно заставить аллокатор «видеть» перекрывающиеся чанки. Это даёт overlap: два указателя на одну память. Через overlap переписывают метаданные соседнего чанка, добиваясь произвольной записи. Это основа House of Einherjar и родственных атак.

## Расширенная таблица атак по типам багов

| Баг | Атака |
|---|---|
| UAF | tcache poisoning, unsortedbin leak |
| double-free | fastbin dup, tcache dup |
| overflow | House of Force, top chunk |
| off-by-one | overlap, poison null byte |
| off-by-null | House of Einherjar |
| unlink | unsafe unlink |

## Итог

Куча — это управляемая структура с предсказуемыми метаданными. Освоив чанки, bins и tcache, вы получаете язык, на котором описываются все heap-атаки. Начните с tcache poisoning — самого простого примитива, затем переходите к overlap и House of.

## Рекомендации по изучению

Начните с практики: скомпилируйте программу с `malloc`/`free`, откройте её в pwndbg и прогоните последовательности аллокаций, наблюдая за чанками и бинами. Затем реализуйте tcache poisoning на учебном бинаре без safe-linking, после чего усложните задачу включением safe-linking. Только после этого переходите к overlap и House of — они требуют свободного владения метаданными.

## Финальная мысль

Куча кажется хаосом лишь на первый взгляд. Как только вы видите в ней чанки с заголовками и связные списки, эксплуатация становится инженерной задачей: испортить конкретное поле и получить конкретный примитив. Практикуйтесь на реальных бинарях, и heap перестанет быть страшным.
