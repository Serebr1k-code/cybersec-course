## Вопрос, с которого всё начинается

Ты нашёл гонку, но окно между проверкой и использованием — **микросекунды**. Запускаешь эксплойт тысячу раз — и почти всегда промах. Как сделать гонку **надёжной**, а не «лотереей»? Ответ — **искусственно расширить окно**: заставить поток **остановиться** ровно в нужной точке и ждать, пока второй поток сделает своё дело. В этом уроке разберём инструменты для этого.

## Наш пример

Вернёмся к гонке из прошлого урока: поток делает проверку, затем обращается к памяти, и между этими шагами — крошечное окно. Проблема в том, что окно **не детерминировано**: планировщик может переключить поток в любой момент, но не обязательно там, где нужно.

Идея расширения: **сделать так, чтобы обращение к памяти в нужной точке вызвало «заминку»** — страница памяти помечается недоступной, поток ловит ошибку, а обработчик **блокирует его** до сигнала от второго потока. Пока первый поток «висит», второй спокойно меняет состояние. Это и есть контролируемое окно.

## Шаг 1: userfaultfd — ловим обращение к странице

**`userfaultfd`** — механизм Linux, позволяющий пользовательскому процессу **обрабатывать page fault** самому. Идея:

1. Регистрируем регион памяти через `userfaultfd`.
2. Помечаем страницу как «отсутствующую».
3. Когда поток обращается к ней — ядро **не убивает процесс**, а присылает нам событие.
4. Мы (в другом потоке) **получаем событие** и можем подождать, сделать что-то ещё и только потом отдать страницу.

Схема в коде (упрощённо):

```c
int uffd = userfaultfd(O_CLOEXEC);
struct uffdio_api api = { .api = UFFD_API };
ioctl(uffd, UFFDIO_API, &api);

struct uffdio_register reg = { .range = { .start = page, .len = 0x1000 } };
reg.mode = UFFDIO_REGISTER_MODE_MISSING;
ioctl(uffd, UFFDIO_REGISTER, &reg);

// ... целевой поток обращается к page -> застревает ...

struct uffd_msg msg;
read(uffd, &msg, sizeof(msg));      // получили fault: окно ОТКРЫТО
/* ... здесь второй поток делает своё дело ... */
struct uffdio_copy copy = { .dst = page, .src = zeropage, .len = 0x1000 };
ioctl(uffd, UFFDIO_COPY, &copy);    // отпустили страницу
```

Пока `read(uffd, ...)` не завершён, целевой поток **точно стоит** на обращении к `page`. Это превращает микросекундное окно в «бесконечное».

Важно: в новых ядрах `userfaultfd` для непривилегированных процессов **ограничен** (`vm.unprivileged_userfaultfd`). Тогда используют `FUSE` (следующий шаг) или запускают с нужным флагом.

## Шаг 2: FUSE — тормозим файловые операции

Если гонка связана с файлами, удобно затормозить саму файловую систему. **FUSE** (Filesystem in Userspace) позволяет написать свой «файловый сервер», который обрабатывает операции как хочет. Например, `open` нужного файла в FUSE-системе может **висеть**, пока атакующий не скажет «продолжай».

Схема:

1. Монтируем FUSE-ФС, где путь жертвы — наш обработчик.
2. Когда программа делает `access`/`open`, FUSE-сервер **задерживает ответ**.
3. В это время атакующий меняет состояние.
4. Отпускаем — программа продолжает с уже подменённым объектом.

FUSE — тяжёлый, но **очень надёжный** способ: окно контролируешь полностью, и он работает без привилегий (если `fuse` доступен).

## Шаг 3: mprotect и самопальные «заминки»

Более простой приём — **сделать страницу недоступной** через `mprotect(PROT_NONE)` и обработать `SIGSEGV` сигналом. Когда поток обращается к странице, приходит сигнал, и в обработчике можно подождать:

- `mprotect(page, 0x1000, PROT_NONE)` перед опасным обращением;
- в `SIGSEGV`-обработчике — синхронизация со вторым потоком;
- затем `mprotect(..., PROT_READ|PROT_WRITE)` и возврат из сигнала.

Это «userfaultfd для бедных»: работает везде, но обработка сигналов сложнее и требует аккуратности (async-signal-safe код).

## Шаг 4: трюки планировщика

Иногда расширять окно нужно не памятью, а **таймингом**:

- **`sched_setaffinity`** — привязать потоки к конкретным ядрам, чтобы уменьшить случайные переключения.
- **`nice`/приоритеты** — замедлить или ускорить поток.
- **`ptrace`** — остановить целевой поток в нужный момент (в отладке).
- **Нагрузка** — запустить «шумные» процессы, чтобы растянуть планирование.

Планировщик — самый ненадёжный инструмент: он **помогает**, но не даёт гарантии. Основной упор — на `userfaultfd`/`FUSE`. Если гонка не файловая и не связана с памятью, попробуй комбинировать приёмы: `mprotect` для памяти плюс привязка к ядрам для тайминга. Начни с простого и усложняй, пока эксплойт не станет стабильным на десятках запусков подряд.

## Шаг 5: как это выглядит в эксплойте

Полный сценарий для гонки на куче:

1. **Находим точку гонки** (например, `free` до обнуления указателя).
2. **Ставим userfaultfd** на страницу, обращение к которой произойдёт ровно между шагами.
3. **Целевой поток** застревает на fault.
4. **Второй поток** делает `free`/`malloc`/подмену.
5. **Отпускаем страницу** — первый поток продолжает, уже с испорченным состоянием.
6. Получаем **double-free** или **overlapping chunks** детерминированно.

Так «лотерея» превращается в стабильный эксплойт. Именно поэтому `userfaultfd` — ключевой инструмент современной эксплуатации гонок (и ядра в частности). Приём стоит освоить отдельно: он пригодится далеко за пределами конкретной задачи.

## Шаг 6: почему userfaultfd ограничили и что это значит

`userfaultfd` оказался настолько удобен для эксплуатации гонок в **ядре**, что его ограничили: в новых ядрах непривилегированные процессы не могут создавать «настоящий» userfaultfd без флага `vm.unprivileged_userfaultfd=1`. Причина — именно массовое использование в kernel-exploit'ах.

Что это меняет для тебя:

- **Если ты root/в контейнере с правами** — userfaultfd доступен как раньше.
- **Если нет** — используй **FUSE** (часто разрешён) или `mprotect`+SIGSEGV.
- **Проверь версию ядра.** Поведение отличается между версиями; не полагайся на один приём.
- **В CTF** флаг часто выставлен специально — читай условие задачи.

Это хороший пример того, как защита рождается из практики эксплуатации: инструмент, которым атакуют, постепенно «закручивают». Тот же путь прошли многие механизмы.

Итог: **расширять окно можно разными способами**, и выбор зависит от того, что разрешено в конкретной среде. Держи в арсенале все три: `userfaultfd`, `FUSE`, `mprotect`. Начни с самого доступного в твоей среде и усложняй только при необходимости. Умение стабилизировать гонку отличает «сработало один раз» от полноценного эксплойта.

## Что мы теперь знаем

- Окно гонки можно **расширить** до детерминированного.
- **`userfaultfd`** ловит page fault и позволяет «подвесить» поток в нужной точке.
- **`FUSE`** тормозит файловые операции и даёт полный контроль над окном.
- **`mprotect`+SIGSEGV** — простой аналог, но требует аккуратной обработки сигналов.
- Планировочные трюки (`sched_setaffinity`, `nice`) **помогают**, но не гарантируют.
