## Вопрос, с которого всё начинается

У тебя есть бинарь из прошивки роутера — под MIPS, для чужой архитектуры. Запустить его «как есть» нельзя: процессор другой, да и роутера под рукой нет. Unicorn из прошлого урока помог бы вызвать одну функцию, но этот бинарь нужно прогнать **целиком** — он читает пароль и сравнивает его где-то внутри.

Нужна эмуляция не только CPU, но и операционной системы. Это делает **Qiling** — надстройка над Unicorn.

## Наш пример: MIPS-бинарь из прошивки

Пусть `router_check` — это ELF под MIPS, который печатает `Enter password:` и читает строку. Мы хотим понять, как он проверяет пароль, не имея ни MIPS-устройства, ни исходников.

## Шаг 1. Что Qiling добавляет к Unicorn

Unicorn даёт «голый CPU»: `syscall` он не обрабатывает — на первом же обращении к ядру эмуляция упадёт. **Qiling = Unicorn + ОС.** Он умеет:

- загружать ELF, PE, Mach-O и shellcode;
- эмулировать Linux, Windows, macOS, FreeBSD, UEFI;
- предоставлять **rootfs** — виртуальную файловую систему, из которой программа «видит» файлы;
- реализовывать системные вызовы и перехватывать их;
- эмулировать API Windows (`kernel32.dll` и другие).

Отличие в уровне абстракции: Unicorn — «вызови одну функцию», Qiling — «запусти программу и посмотри, что она делает».

## Шаг 2. Установка и rootfs

```bash
$ pip install qiling
$ python3 -c "import qiling; print(qiling.__version__)"
1.4.6
```

**rootfs** — дерево каталогов, которое программа видит как свою файловую систему: `/lib`, `/usr/lib`, `/etc`, `/bin`. Именно оттуда Qiling берёт динамический линкер и разделяемые библиотеки. Без подходящего rootfs программа не найдёт `ld-linux` и упадёт.

```bash
$ git clone https://github.com/qilingframework/qiling.git
$ ls qiling/examples/rootfs/
x86_64_linux  x86_linux  arm_linux  mips_linux  x86_windows  ...
```

Для нашего MIPS-бинаря нужен `mips_linux`.

## Шаг 3. Запускаем бинарь целиком

```python
from qiling import Qiling
from qiling.const import QL_VERBOSE

ql = Qiling(["./router_check", "admin"],
            rootfs="./rootfs/mips_linux",
            verbose=QL_VERBOSE.DEBUG)
ql.run()
```

`verbose=QL_VERBOSE.DEBUG` печатает каждый системный вызов — это фактически встроенный `strace`. Смотрим вывод:

```text
[=] write(fd = 1, buf = 0x...("Enter password: "), count = 15) = 15
[=] read(fd = 0, buf = 0x..., count = 64) = 6
[=] write(fd = 1, buf = 0x...("wrong\n"), count = 6) = 6
```

Мы видим ровно то, что делает программа: пишет приглашение, читает ввод, отвечает `wrong`. Уже понятно, где находится логика проверки — между `read` и вторым `write`.

## Шаг 4. Подсовываем ввод и перехватываем syscall

Чтобы «раскрутить» программу, подменим реализацию `read` и подсунем ей свои данные. Высокоуровневый API — `ql.os.set_syscall`:

```python
def fake_read(ql, fd, buf, count):
    data = b"admin\x00"
    ql.mem.write(buf, data)      # кладём данные в буфер программы
    return len(data)             # говорим, что прочитали столько

ql.os.set_syscall("read", fake_read)
```

Теперь при каждом `read` программа получит нашу строку. Меняя её и наблюдая ответ (`wrong` или `ok`), мы восстанавливаем ожидаемый пароль.

## Шаг 5. Хуки на функции и адреса

Кроме syscall, Qiling позволяет подменять **функции** по имени и ставить хуки на адреса:

```python
from qiling.const import QL_INTERCEPT

ql.os.set_api("strcmp", my_strcmp, QL_INTERCEPT.CALL)  # подменить strcmp
ql.hook_address(callback, 0x400780)                     # сработает на адресе
ql.hook_code(callback)                                  # на каждой инструкции (медленно)
```

`set_api` заменяет библиотечную функцию (удобно для `ptrace`, `strcmp`), `hook_address` вызывает наш код при достижении адреса. Комбинируя `set_syscall` и `hook_address`, можно логировать ветвления и подсовывать данные в нужные моменты — постепенно восстанавливая алгоритм без статического анализа целиком.

## Шаг 6. Обходим анти-анализ

Анти-отладка часто проверяет `ptrace`, наличие файлов `/proc`, `cpuid`, тайминги. Под Qiling всё это перехватывается:

```python
from qiling.const import QL_INTERCEPT

def fake_ptrace(ql, *args):
    return 0                       # «трассировки нет»
ql.os.set_api("ptrace", fake_ptrace, QL_INTERCEPT.CALL)

def fake_isdebugger(ql, *args):
    return 0                       # для Windows PE
ql.os.set_api("IsDebuggerPresent", fake_isdebugger, QL_INTERCEPT.CALL)
```

Так проверки проходят, а мы наблюдаем за дальнейшей логикой. Это безопаснее, чем запускать malware на хосте, и работает для любой архитектуры.

## Шаг 7. Windows PE без Windows

Отдельная сильная сторона Qiling — эмуляция PE на Linux-хосте. Он загружает `kernel32.dll`, `ntdll.dll` из Windows-rootfs и реализует большую часть API:

```python
ql = Qiling([r"rootfs/x86_windows/bin/sample.exe"],
            rootfs=r"rootfs/x86_windows")
ql.run()
```

`QL_VERBOSE.DEBUG` покажет, какие API-функции вызывает образ, — это автоматический API-монитор, родственный тому, что дают Cuckoo и Speakeasy.

## Чем Qiling отличается от qemu-user

Есть и третий путь запуска чужой архитектуры — `qemu-user` (см. `pwn-qemu-user`). Он исполняет бинарь почти нативно: быстрее и точнее воспроизводит реальное поведение, но не даёт хуков уровня памяти и инструкций и требует, чтобы бинарь действительно работал. Выбор такой: **Qiling** — для анализа и обхода анти-анализа (полный контроль, но медленно), **qemu-user** — для эксплуатации и точного поведения (быстро, но без инструментации), **Unicorn** — для эмуляции отдельных функций. Не смешивай их: для «посмотреть, что делает программа» бери Qiling, для «довести эксплойт на реальной libc» — qemu-user или саму цель.

## Ограничения Qiling

Понимание ограничений экономит часы:

- **Неполная реализация syscall.** Сложные программы (`epoll`, `io_uring`, потоки) могут падать — тогда нужны хуки.
- **Производительность.** Эмуляция в десятки раз медленнее нативной. Для крипто-брутфорса бери Unicorn на конкретной функции.
- **Динамические зависимости.** Нет библиотеки в rootfs — эмуляция прервётся; её докладывают вручную.
- **Анти-эмуляция.** Продвинутый malware ищет аномалии окружения; Qiling их не скрывает без хуков.
- **Нет реального ядра.** Всё, что требует специфичных `ioctl`, эмулируется ограниченно.

Рабочая стратегия: сначала запусти бинарь целиком под Qiling и посмотри, доходит ли он до интересной логики. Если да — хукай нужное. Если нет — переходи на Unicorn и эмулируй отдельные функции, где ты контролируешь всё. Не трать время на «заставление» Qiling запустить то, что он принципиально не тянет.

## На что смотреть дальше

- **Нет rootfs** — программа не найдёт `ld-linux` и упадёт. Всегда указывай rootfs.
- **Неверная архитектура rootfs** — MIPS-бинарь с x86-rootfs не запустится.
- **Ожидание полной эмуляции** — часть syscall реализована заглушками.
- **`QL_VERBOSE.DEBUG` на большой программе** печатает мегабайты — пиши в файл.
- **Сеть** Qiling эмулирует, но для реального взаимодействия нужен свой хук.

## Что мы теперь знаем

- Qiling = Unicorn + эмуляция ОС (загрузчик, rootfs, syscall).
- rootfs обязателен: из него берутся линкер и библиотеки.
- `QL_VERBOSE.DEBUG` заменяет `strace` и показывает поведение.
- `set_syscall`/`set_api`/`hook_address` позволяют подменять и перехватывать.
- Qiling хорош для анализа и анти-анализа, но медленнее и неполон.

## Куда дальше

В `pwn-emulation-hooks` мы углубимся в хуки: перехват отдельных инструкций и syscall, модификация памяти и регистров «на лету». А пока главное: **Qiling запускает бинарь целиком — с ОС, syscall и чужой архитектурой, — и позволяет перехватить любую его часть.**

## Где пригодится

- **CTF:** задачи с анти-отладкой и чужой архитектурой.
- **Bug bounty:** безопасный запуск подозрительных бинарей.
- **Пентест:** анализ прошивок IoT без устройства.
- **Работа:** malware analysis и DFIR.
