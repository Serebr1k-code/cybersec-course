ASan/UBSan — это санитайзеры компилятора, обнаруживающие ошибки памяти (ASan) и неопределённое поведение (UBSan). Для pwn-специалиста они важны с двух сторон: как инструмент поиска багов (фаззинг с ASan) и как защита, которую нужно обойти (если цель собрана с санитайзерами). ASan добавляет проверки и «отравленные» (poisoned) области вокруг объектов; UBSan ловит переполнения, сдвиги, деление на ноль. В этом уроке — устройство санитайзеров, чтение отчётов, использование для фаззинга и обход (если требуется).

## ASan: устройство

ASan резервирует «shadow memory» — область, где на каждый байт приложения приходится байт-статус (доступен/отравлен). При каждом обращении к памяти ASan проверяет shadow: если адрес отравлен — ошибка. Вокруг каждого объекта — «redzone» (отравленные байты), ловящие переполнения. ASan также отслеживает освобождённую память (quarantine) для детекта UAF. Отчёт показывает тип бага, стек и shadow bytes. Это делает ASan незаменимым при фаззинге.

## Чтение отчётов ASan

```
==12345==ERROR: AddressSanitizer: heap-buffer-overflow on address 0x...
WRITE of size 8 at 0x... thread T0
    #0 0x... in vuln_func file.c:42
    #1 0x... in main file.c:100
0x... is located 0 bytes to the right of 16-byte region
```

Разбор: (1) тип (`heap-buffer-overflow`, `use-after-free`, `stack-buffer-overflow`, `global-buffer-overflow`); (2) READ/WRITE и размер; (3) стек — где баг; (4) регион — что за объект. `use-after-free` — UAF; `heap-buffer-overflow WRITE` — переполнение записи (эксплуатируемо). `SEGV on unknown address` — может быть NULL-deref. Эти отчёты — ключ к триажу и пониманию бага.

## UBSan

UBSan ловит: signed integer overflow, shift overflow, деление на ноль, misaligned access, неверные приведения типов. Отчёт вида `runtime error: signed integer overflow: 2147483647 + 1`. Для pwn UBSan полезен при поиске багов в парсерах/вычислениях, которые могут вести к переполнению буфера. UBSan не останавливает выполнение (по умолчанию), а логирует. Комбинируйте с ASan.

## Использование для фаззинга

Собирайте цель с `-fsanitize=address,undefined` и фаззьте (AFL++/libFuzzer). ASan/UBSan найдут баги, которые иначе остались бы незамеченными (особенно UAF и целочисленные). Это стандартный сетап современного фаззинга. Помните, что ASan замедляет и увеличивает память — настройте `-m none` для AFL.

## Обход санитайзеров (если цель с ними)

Если цель собрана с ASan (редко в CTF, но возможно), обходы: (1) ASan не защищает от логических ошибок; (2) ASan можно «обойти» через повреждение shadow memory (если есть arbitrary write); (3) ASan отключается при `ASAN_OPTIONS=...` (если переменные окружения контролируются); (4) некоторые операции (например, доступ к памяти вне инструментированного кода) не проверяются. На практике ASan в целевой системе — редкость; чаще это инструмент анализа. UBSan не является защитой вовсе.

## Разобранный пример

```bash
# сборка с санитайзерами
clang -fsanitize=address,undefined -g target.c -o target
# запуск
./target input
# отчёт ASan покажет баг
```

## Частые ошибки

- **ASan + AFL память.** Нужно `-m none`.
- **ASan замедляет.** Учитывайте при таймингах.
- **UBSan не останавливает.** Логирует, не падает.
- **Обход ASan.** Редко нужен, но возможен.
- **Сборка.** Флаги важны (`-g`, `-O1`).

## Полный разбор ASan-отчёта

Разберём сквозной пример. Дано: цель собрана с ASan, при фаззинге получен креш. Отчёт:

```
==12345==ERROR: AddressSanitizer: heap-use-after-free on address 0x...
READ of size 8 at 0x... thread T0
    #0 0x... in use_func target.c:42
    #1 0x... in main target.c:100
freed by thread T0 here:
    #0 0x... in free
    #1 0x... in free_func target.c:30
previously allocated by thread T0 here:
    #0 0x... in malloc
    #1 0x... in alloc_func target.c:20
```

Разбор: (1) тип — `heap-use-after-free` (UAF); (2) READ of size 8 — чтение указателя (может быть утечка); (3) стек использования, освобождения и аллокации — полная картина жизненного цикла. UAF с READ — потенциальная утечка; с WRITE — потенциальный контроль. `heap-buffer-overflow WRITE of size 8` — переполнение записи, часто эксплуатируемо. `stack-buffer-overflow` — переполнение стека (ROP). Используйте минимизированный вход и стройте PoC/эксплойт. ASan-отчёты — отправная точка для понимания бага.

## Использование ASan/UBSan при фаззинге

Стандартный сетап: соберите цель с `-fsanitize=address,undefined -g -O1` и фаззьте (AFL++/libFuzzer). ASan найдёт overflow/UAF/double-free, UBSan — целочисленные/UB. Это значительно повышает шанс найти баги. Помните: ASan замедляет (~2x) и увеличивает память (настройте `-m none` для AFL). Для UBSan используйте `-fsanitize=undefined` и опцию `halt_on_error=1` (чтобы падать на UB). Комбинируйте с coverage-guided фаззингом. Триажьте отчёты, дедуплицируйте, минимизируйте. ASan/UBSan — основа современного поиска багов.

## Обход санитайзеров

Если цель собрана с ASan (редко в CTF), обходы: (1) ASan не проверяет память вне инструментированного кода (например, в libc без ASan); (2) можно повредить shadow memory через arbitrary write (сложно); (3) `ASAN_OPTIONS` может отключить проверки (если контролируете окружение); (4) логические баги не детектируются. На практике ASan в цели — редкость; чаще это инструмент анализа. UBSan не защита вовсе (логирует). Поэтому «обход санитайзеров» — скорее академическая тема; сосредоточьтесь на использовании их для поиска багов.

## Расширенный разбор ASan/UBSan

Дополним. ASan использует shadow memory: на каждый 8-байтовый блок приложения — 1 байт статуса. Формула: `shadow = (addr >> 3) + offset`. При обращении ASan читает статус и, если адрес «отравлен», сообщает. Redzones вокруг объектов ловят переполнения; quarantine ловит UAF (освобождённая память не переиспользуется сразу). `-fsanitize=address` также ловит double-free, use-after-return (с `detect_stack_use_after_return=1`). UBSan (`-fsanitize=undefined`) ловит signed overflow, shift, деление на ноль, misaligned, неверные приведения. Отчёты UBSan начинаются с `runtime error:`. Комбинируйте оба для максимального покрытия. Настройки через `ASAN_OPTIONS`/`UBSAN_OPTIONS` (например, `halt_on_error=1`, `detect_leaks=1`). ASan/UBSan — основа современного фаззинга.

## Интеграция с фаззингом и триаж

Стандартный workflow: (1) соберите с `-fsanitize=address,undefined -g -O1`; (2) фаззьте (AFL++ с `AFL_USE_ASAN=1`, или libFuzzer `-fsanitize=fuzzer,address`); (3) соберите отчёты; (4) дедуплицируйте (по стеку/типу); (5) минимизируйте входы (`afl-tmin`); (6) классифицируйте эксплуатируемость. ASan-отчёт даёт полную картину (тип, стек, регион), что ускоряет анализ. Для каждого бага оцените: overflow/UAF (эксплуатируемо) или логический. Практикуйтесь на реальных проектах (парсеры, библиотеки) — фаззинг с ASan регулярно находит баги. Это ключевой навык bug hunting.

## Практика: сборка и запуск

Соберите цель: `clang -fsanitize=address,undefined -g -O1 target.c -o target`. Запустите: `./target input`. ASan выведет отчёт при баге; UBSan — `runtime error:` при UB. Настройте `ASAN_OPTIONS=halt_on_error=1:detect_leaks=1`, `UBSAN_OPTIONS=halt_on_error=1`. Для фаззинга с AFL: `AFL_USE_ASAN=1 afl-clang-fast ...`, затем `afl-fuzz -m none`. Для libFuzzer: `clang -fsanitize=fuzzer,address ...`. Триажьте отчёты: тип, стек, регион. Минимизируйте входы. Практикуйтесь на реальных проектах — ASan/UBSan регулярно находят баги. Это основа bug hunting.


## Практика: полный workflow

(1) Соберите: `clang -fsanitize=address,undefined -g -O1`. (2) Фаззьте: AFL++ (`AFL_USE_ASAN=1`, `-m none`) или libFuzzer. (3) Соберите отчёты. (4) Дедуплицируйте и минимизируйте (`afl-tmin`). (5) Классифицируйте (overflow/UAF/логический). (6) Постройте PoC/эксплойт. Практикуйтесь на реальных проектах. ASan/UBSan — основа bug hunting; их отчёты ускоряют анализ. Держите скрипты сборки/триажа под рукой.
