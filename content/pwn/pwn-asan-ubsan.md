## Вопрос, с которого всё начинается

Ты запускаешь программу с длинным вводом — и вместо загадочного `Segmentation fault` получаешь **подробный отчёт**: какая операция, по какому адресу, в какой строке, какая переменная переполнена. Это работа **санитайзеров** — ASan и UBSan. Они превращают «что-то упало» в «вот баг, вот место, вот размер». В этом уроке разберём, как они это делают и — главное для нас — **что меняется, когда цель собрана с санитайзером**.

## Наш пример

Возьмём маленькую программу с выходом за границу массива:

```c
int main() { int a[4]; a[7] = 1; return 0; }
```

Соберём её с AddressSanitizer и запустим:

```
$ gcc -fsanitize=address san.c -o san
$ ./san
=================================================================
==232426==ERROR: AddressSanitizer: stack-buffer-overflow on address 0x7b640670003c
WRITE of size 4 at 0x7b640670003c thread T0
    #0 0x557223d10265 in main san.c:2
  This frame has 1 object(s):
    [32, 48) 'a' (line 2) <== Memory access at offset 60 overflows this variable
SUMMARY: AddressSanitizer: stack-buffer-overflow san.c:2 in main
```

Без санитайзера это было бы просто падение (или тихое повреждение памяти). Здесь же мы сразу знаем: **переполнение стека**, переменная `a`, размер 16 байт (`[32, 48)`), а запись была по смещению 60.

## Шаг 1: как ASan это понимает

ASan работает через **shadow memory** — «теневую» копию памяти, где для каждых 8 байт программы хранится 1 байт состояния: доступны они или нет. Перед каждой операцией чтения/записи компилятор вставляет проверку: посмотреть в теневую память, разрешён ли доступ. Если нет — отчёт и остановка.

Вокруг каждой переменной ASan оставляет **redzone** — «запретную» область. В нашем примере `a` занимает байты `[32, 48)`, а redzone идёт сразу после. Запись по смещению 60 попадает в redzone — это и есть «overflow».

Для кучи то же самое: вокруг каждого `malloc`-блока — redzone. Проверим:

```
$ gcc -fsanitize=address asanheap.c -o asanheap && ./asanheap
==243870==ERROR: AddressSanitizer: heap-buffer-overflow on address 0x7c08bebe0024
WRITE of size 1 at 0x7c08bebe0024 thread T0
    #0 0x5575b6fe51fa in main asanheap.c:3
0x7c08bebe0024 is located 4 bytes after 16-byte region [0x7c08bebe0010,0x7c08bebe0020)
allocated by thread T0 here:
    #0 ... in malloc
```

Отчёт говорит прямо: адрес в **4 байтах после** блока на 16 байт, выделенного в `malloc`. Это **heap-buffer-overflow**.

## Шаг 2: UBSan — про поведение, а не про память

Второй санитайзер, **UBSan** (UndefinedBehaviorSanitizer), ловит не работу с памятью, а **неопределённое поведение**: знаковое переполнение, сдвиги, выход за границы массива на уровне типов. Соберём:

```
$ gcc -fsanitize=undefined ubsan.c -o ubsan && ./ubsan
ubsan.c:2:35: runtime error: signed integer overflow: 2147483647 + 1 cannot be represented in type 'int'
ubsan.c:2:73: runtime error: index 5 out of bounds for type 'int [2]'
ubsan.c:2:76: runtime error: store to address 0x7ffdd653c364 with insufficient space
```

Три ошибки в одной строке: переполнение `int`, выход за границы массива, запись в недостаточное место. UBSan **не останавливает** программу по умолчанию — он печатает и продолжает (в отличие от ASan, который делает `abort`).

Для эксплуататора ценность в том, что UBSan находит **источник** странного поведения: например, целочисленное переполнение, которое позже приводит к маленькому `malloc` и большому `memcpy` — классический путь к heap overflow.

## Шаг 3: что меняется, когда цель собрана с ASan

В CTF иногда дают бинарник **с включённым ASan** (например, чтобы ты не искал баг, а сразу эксплуатировал его). Тут важно помнить:

- **Раскладка памяти другая.** Вокруг объектов redzone, адреса сдвинуты. Жёстко прошитые адреса из «обычной» сборки не подойдут.
- **ASan ставит свой аллокатор.** `malloc`/`free` идут через ASan, а не через glibc, поэтому tcache/fastbin-техники могут не работать — структур glibc просто нет.
- **ASan прерывает процесс** при первом же нарушении. Значит, «потрогать» redzone в эксплойте нельзя — надо обходить.
- **Много «шума».** Иногда ASan-сборка содержит доп. проверки, которые тоже надо обойти.

Обратная сторона: санитайзер **сам сообщает** о баге. Если задача — найти уязвимость (а не только проэксплуатировать), ASan-сборка — лучший помощник: подай вход и читай отчёт.

## Шаг 4: как это используют на практике

Стандартный рабочий процесс при анализе бинарника:

1. **Собери/запусти с ASan**, если есть исходники или задача это позволяет. Получи точное место и тип бага.
2. **Проверь UBSan** — нет ли целочисленных ошибок, которые ведут к переполнению.
3. **Прочитай отчёт**: какой объект, какой размер, какая операция. Это подсказывает стратегию эксплойта.
4. **Убери санитайзер** (собери без него) для эксплуатации — либо адаптируй эксплойт под ASan-раскладку, если дана именно такая сборка.

Полезно помнить: ASan — это **debug-инструмент**, а не защита в проде. В реальных бинарниках его нет, поэтому «эксплуатация с ASan» — редкий сценарий, а вот **диагностика** с ним — ежедневная.

## Шаг 5: где это встречается

- **Bug bounty / research:** проекты собирают fuzzing-сборки с ASan — любой краш приходит с готовым отчётом.
- **CTF:** задачи «найди баг» часто дают ASan-сборку; задачи «проэксплуатируй» — обычную.
- **Разработка:** санитайзеры в CI ловят утечки и переполнения до релиза.
- **Аудит кода:** комбинация ASan+UBSan+фаззинг — стандартный способ найти баги в C/C++.

## Шаг 6: как читать отчёт построчно

Разберём типичный ASan-отчёт по строкам, чтобы ты не терялся:

```
==232426==ERROR: AddressSanitizer: stack-buffer-overflow on address 0x7b640670003c
WRITE of size 4 at 0x7b640670003c thread T0
    #0 0x557223d10265 in main san.c:2
  This frame has 1 object(s):
    [32, 48) 'a' (line 2) <== Memory access at offset 60 overflows this variable
SUMMARY: AddressSanitizer: stack-buffer-overflow san.c:2 in main
```

- **`stack-buffer-overflow`** — тип бага (бывает `heap-buffer-overflow`, `use-after-free`, `global-buffer-overflow`).
- **`WRITE of size 4`** — операция и размер; запись 4 байт (int).
- **`#0 ... san.c:2`** — стек вызовов в момент нарушения, с файлом и строкой.
- **`[32, 48) 'a'`** — реальные границы объекта `a`; `48-32 = 16` байт = 4 int.
- **`offset 60`** — куда мы попали; `60 - 48 = 12` байт за границей.
- **`SUMMARY`** — одна строка «что и где» для быстрого поиска.

Прочитав это, ты сразу знаешь: переполнение стека, переменная `a`, запись на 12 байт за границей. Для эксплуатации важно: **смещение до адреса возврата отсчитывается от `a`**, и его можно взять из этого же отчёта (границы объекта + структура кадра).

## Что мы теперь знаем

- **ASan** использует **shadow memory** и **redzone**, чтобы ловить выход за границы стека, кучи и глобалов.
- Отчёт ASan указывает **операцию, адрес, объект и строку** — сразу видно баг.
- **UBSan** ловит неопределённое поведение (переполнения, сдвиги) и по умолчанию не останавливает программу.
- ASan-сборка меняет **раскладку памяти** и **аллокатор** — обычные heap-техники могут не работать.
- Санитайзеры — инструмент **диагностики**, а не защита в проде.

## Куда дальше

Мы научились читать отчёты санитайзеров и поняли, что меняется в ASan-сборке. Дальше — **фаззинг**: как **находить** такие краши автоматически, миллионами входов, и превращать их в эксплойт. А пока запомни главное: **ASan и UBSan — это ускорители диагностики; они показывают баг точно, но меняют среду исполнения.**

## Где пригодится

- **CTF Pwn:** задачи «найди баг» и ASan-сборки.
- **Bug bounty:** fuzzing-сборки с ASan дают готовые отчёты.
- **Vulnerability research:** быстрый поиск переполнений.
- **Разработка:** санитайзеры в CI против утечек и порчи памяти.
