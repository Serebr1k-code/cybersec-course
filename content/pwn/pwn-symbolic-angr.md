## Вопрос, с которого всё начинается

Фаззинг перебирает входы **случайно**. Но если задача — «подбери пароль, при котором программа дойдёт до функции `win`», случайный перебор может идти вечно. Есть ли способ **решить** это аналитически? Да — **символьное исполнение**: мы говорим движку «вход неизвестен» и просим найти такой вход, при котором выполнение дойдёт до нужной точки. Инструмент — **angr**.

## Наш пример

Возьмём простой crackme: программа читает пароль и сравнивает его посимвольно с секретом. Функция `win` печатает флаг, если пароль верный. Наша цель — заставить исполнение дойти до `win`, не подбирая пароль вручную.

## Шаг 1: идея символьного исполнения

Обычное исполнение: вход **конкретный** (`argv[1] = "abc"`), программа идёт по одному пути. Символьное: вход — **символьная переменная** `x` (неизвестное). Движок исполняет программу, накапливая **ограничения** на `x`:

- прошли проверку `x[0] == 's'` → ограничение `x[0] = 's'`;
- прошли `x[1] == '3'` → добавляем `x[1] = '3'`;
- и так далее, пока не дошли до `win`.

В конце движок отдаёт ограничения **решателю (solver)**, который находит конкретное значение `x`, удовлетворяющее всем им. Это и есть «решение» пароля — без перебора.

## Шаг 2: запускаем angr

Загружаем бинарник и указываем, куда хотим дойти и чего избегать:

```python
import angr, claripy
proj = angr.Project('./crackme', auto_load_libs=False)

# 32 байта символьного ввода со стандартного входа
flag = claripy.BVS('flag', 8 * 32)

state = proj.factory.entry_state(stdin=flag)
for b in flag.chop(8):
    state.solver.add(b >= 0x20, b <= 0x7e)   # печатаемые символы

simgr = proj.factory.simulation_manager(state)
simgr.explore(find=0x401200, avoid=0x401230)  # find=win, avoid=проигрыш
```

- **`claripy.BVS`** — символьная переменная (bitvector symbol).
- **`entry_state(stdin=flag)`** — входной поток программы становится символьным.
- **`solver.add(...)`** — ограничения на символы (например, только печатаемые).
- **`explore(find=..., avoid=...)`** — «дойди до адреса `find`, не заходя в `avoid`».

## Шаг 3: читаем решение

После запуска смотрим, нашёлся ли путь:

```python
if simgr.found:
    s = simgr.found[0]
    print(s.posix.dumps(0))   # 0 = stdin
```

Типичный вывод:

```
$ python3 solve.py
b's3cr3t_p4ssw0rd\x00...'
```

Движок сам собрал пароль. Именно так решается большая часть «crackme»-задач: указал `find`/`avoid` — получил вход.

## Шаг 4: хуки — заменяем функции

Символьное исполнение плохо работает с реальными библиотеками: `strlen`, `memcmp`, `printf` реализованы в машинном коде и порождают лавину путей. Решение — **хуки**: заменить функцию простой моделью.

```python
@proj.hook(0x401080, length=5)      # адрес call strlen
def strlen_hook(state):
    s = state.memory.load(state.regs.rdi, 64)
    state.regs.rax = state.solver.eval(...)   # модель длины
```

Хуки нужны, чтобы:

- **ускорить** поиск (убрать «тяжёлые» функции);
- **смоделировать** функцию точно (например, `memcmp` как ограничение равенства);
- **обойти** антисимвольные проверки.

Часто `auto_load_libs=False` (не грузить системные библиотеки) плюс хуки на внешние вызовы — рабочий набор по умолчанию.

## Шаг 5: подводные камни

- **Path explosion.** Если ветвлений много (особенно в циклах), число путей растёт экспоненциально. Спасение — хуки, ограничения, `avoid`, декомпозиция.
- **Неподдерживаемые инструкции.** Angr не всегда эмулирует всё (некоторые syscall, самописные VM, обфускацию).
- **Внешние данные.** Если путь зависит от «настоящего» файла/сети, angr не знает значения — надо моделировать.
- **Антисимволические трюки.** Авторы задач специально добавляют код, который angr не может решить. Тогда — фаззинг или ручной анализ.
- **Время.** Иногда angr «думает» часами. Начни с маленького `find`-адреса и `avoid` рядом, постепенно расширяя.

Практическое правило: **angr — не серебряная пуля**. Он отлично берёт «линейные» проверки ввода, но против сложной логики часто проигрывает ручному разбору. Выбирай инструмент под задачу.

## Шаг 6: где это встречается

- **CTF:** crackme, задачи «найди вход», обход простых проверок.
- **Bug hunting:** поиск входа, приводящего к конкретной опасной функции.
- **Реверс:** автоматический анализ проверок лицензий/паролей.
- **Malware analysis:** обход анти-анализа и поиск путей к полезной нагрузке.

## Шаг 7: angr для ROP и «нестандартных» целей

Символьное исполнение годится не только для «введи пароль». Ещё один частый сценарий — **автоматическое построение пути до `win` при переполнении**: angr сам выяснит, какая последовательность байт приведёт к нужному адресу.

Идея: вместо символьного stdin ты можешь сделать символьным **буфер, в который попадает переполнение**, и попросить angr дойти до `win`. Движок учтёт, что часть байт затирает адрес возврата, и найдёт вход, при котором управление уходит на `win`. Это удобно, когда смещение или логика проверок неочевидны.

Ещё angr полезен для **разбора виртуальных машин и обфускации**: если задача «прогоняет» твой ввод через самописную VM, angr может исполнить её символически и найти вход, при котором VM выдаёт «правильно». Руками это часто нереально.

Но помни ограничения: чем больше кода и ветвлений, тем хуже работает angr. На больших бинарниках (браузеры, ядра) символьное исполнение «в лоб» не масштабируется — там нужны специализированные инструменты и декомпозиция. Поэтому angr — это **точечный инструмент** для небольших, хорошо очерченных задач.

Ещё одна типичная цель — **сравнение с хешем**: программа берёт твой ввод, считает хеш и сравнивает с константой. Angr «перевернёт» это только если хеш-функция целиком символьная и не слишком тяжёлая; часто проще вынести её в хук и задать ограничение «hash(x) == const» в самом solver. Понимание, что именно стоит заменить моделью, — половина успеха.

## Шаг 8: практические приёмы ускорения

- **Сужай пространство.** Ограничь символы печатаемым диапазоном, известной длиной, известным префиксом — меньше вариантов у solver.
- **Ставь `avoid` вокруг тупиков.** Чем раньше отсечёшь бесполезные ветки, тем меньше путей.
- **Хукай библиотеки.** `strlen`, `memcmp`, `printf`, `atoi` — моделируй, а не исполняй.
- **Разбивай задачу.** Реши подзадачу (например, найти длину), зафиксируй её как константу, реши следующую.
- **Ограничь время.** Запускай с таймаутом и смотри, продвинулся ли `find`; иногда помогает переставить порядок.

Если angr «завис» на сложной функции — не бейся в неё, а **замени моделью**. Часто быстрее написать десятистрочный хук, чем ждать, пока solver справится с настоящим кодом.

## Что мы теперь знаем

- **Символьное исполнение** трактует вход как неизвестное и накапливает ограничения по пути.
- **angr** запускает символьное исполнение: `Project`, `entry_state`, `simulation_manager.explore(find, avoid)`.
- Решение выдаёт **solver** (z3 внутри angr) — конкретный вход, удовлетворяющий ограничениям.
- **Хуки** заменяют тяжёлые функции моделями и ускоряют поиск.
- Главные проблемы — **path explosion**, неподдерживаемые инструкции и антисимволические приёмы.

## Полный рабочий скрипт с хуком memcmp

Соберём всё вместе: загрузим бинарник, сделаем stdin символьным, захукаем `memcmp` и попросим angr дойти до `win`. Это шаблон, который решает большинство «сравни ввод с секретом» задач.

```python
import angr, claripy

proj = angr.Project('./crackme', auto_load_libs=False)

# символьный ввод: 32 байта
flag = claripy.BVS('flag', 32 * 8)
st = proj.factory.entry_state(stdin=flag)
for b in flag.chop(8):
    st.solver.add(b >= 0x20, b <= 0x7e)

# хук memcmp: вместо исполнения libc ставим ограничение равенства
@proj.hook(proj.loader.find_symbol('memcmp').rebased_addr)
def hook_memcmp(state):
    a = state.memory.load(state.regs.rdi, 32)
    b = state.memory.load(state.regs.rsi, 32)
    state.solver.add(a == b)         # требуем равенство
    state.regs.rax = 0

simgr = proj.factory.simulation_manager(st)
simgr.explore(find=lambda s: b'Correct' in s.posix.dumps(1),
              avoid=lambda s: b'Wrong' in s.posix.dumps(1))

if simgr.found:
    print(simgr.found[0].posix.dumps(0).split(b'\x00')[0])
```

Обратите внимание: `find`/`avoid` здесь заданы **предикатами** по выводу, а не адресами — это удобнее, когда точные адреса неизвестны. Хук `memcmp` превращает «перебор 32 байт» в одно линейное ограничение, и solver решает его мгновенно.

## Автоматический поиск смещения до win

Когда переполнение затирает адрес возврата, angr умеет сам найти нужный ввод — если сделать символьным буфер переполнения и попросить дойти до `win`:

```python
st = proj.factory.entry_state()
buf = st.memory.load(0x4040a0, 64)       # символьный регион стека
st.solver.add(buf.get_byte(0) == 0x41)   # первый байт известен
simgr = proj.factory.simulation_manager(st)
simgr.explore(find=win_addr)
```

Если путь найдётся, `simgr.found[0]` покажет, какая последовательность байт привела к цели. Это спасает, когда смещение до RIP неочевидно: angr «проигрывает» все варианты и отдаёт рабочий. Ограничение — `find` должен быть достижим без реального ввода-вывода (сеть, файлы) и без анти-символьных проверок.

## angr против фаззинга: когда что выбирать

| Критерий | angr (символьное) | AFL++ (фаззинг) |
|----------|-------------------|-----------------|
| Вход | маленький, структурированный | любой размер |
| Логика | линейные проверки | глубокая, с данными |
| Покрытие | гарантирует путь (если решимо) | вероятностное |
| Скорость | медленно на больших бинарниках | быстро, тысячи exec/s |
| Сложные проверки (хеши) | «зависает» | иногда пробивает по частям |

Правило: если задача — «найди конкретный вход, удовлетворяющий проверкам», бери angr. Если задача — «найди любой краш в большом парсере», бери фаззер. Комбинируйте: фаззер находит интересные пути, angr «дожимает» конкретный.

## Диагностика: почему solver возвращает unsat

Частые причины «решение не найдено»:

- **Слишком жёсткие ограничения.** Ограничение `b >= 0x20, b <= 0x7e` конфликтует с реальным входом (например, в пароле есть `\n`). Уберите или расширьте диапазон.
- **Неверная длина.** Ввод длиннее или короче, чем символьная переменная, — лишние байты берутся из «нулевой» памяти.
- **`find` недостижим.** Проверьте адрес: возможно, ветка требует выполнения, которого angr не эмулирует.
- **Path explosion до `find`.** Добавьте `avoid` и хуки, уменьшите границы цикла.
- **Анти-символьная защита.** Программа проверяет, что вход «настоящий» (например, `readlink /proc/self/fd/0`), — angr на такое реагирует непредсказуемо.

Отладка: запустите `simgr.explore()` без `find` и посмотрите, сколько состояний и где они «застряли»; затем сузьте поиск.

## angr и z3: где чей уровень

Часто путают angr и z3. Разделение такое: **angr** — это движок символьного исполнения, он исполняет машинный код, ведёт состояние регистров и памяти, порождает пути и накапливает ограничения. **z3** (через обёртку `claripy`) — это SMT-решатель, который принимает накопленные ограничения и выдаёт конкретную модель. angr без решателя не смог бы «придумать» вход, а решатель без angr не знал бы, какие ограничения собирать. На практике вам почти всегда нужен angr как «сборщик» ограничений, а к z3 напрямую обращаются, когда задача сводится к чистой алгебре (например, найти `x`, проходящий заданный набор проверок), без исполнения бинарника.

## Сташи (stashes): как понять, что делает angr

`simulation_manager` держит пути в «сташах» с говорящими именами:

- **`active`** — пути, которые ещё исполняются.
- **`found`** — дошли до `find` (то, что вам нужно).
- **`avoid`** — попали в `avoid` (отброшены).
- **`deadended`** — завершились (программа вышла, не достигнув цели).
- **`errored`** — упали на неподдерживаемой инструкции или ошибке.
- **`unconstrained`** — инструкционный указатель стал символьным (часто признак того, что можно «увести» исполнение куда угодно).

Диагностика простая: если `found` пуст, а `deadended` полон — цель недостижима по текущим ограничениям. Если полон `errored` — смотрите, на чём падает, и хукайте это место. Если появились `unconstrained` — вероятно, переполнение уже управляет RIP, и путь можно направить на `win` через `explore`.

## Практика: полный скрипт для crackme

Покажем законченный пример: бинарник просит пароль и печатает «win» при правильном. Задача — найти вход автоматически, без перебора.

```python
import angr, claripy

proj = angr.Project("./crackme", auto_load_libs=False)

# символьный аргумент: 16 байт ввода
arg = claripy.BVS("input", 16 * 8)
state = proj.factory.entry_state(args=["./crackme", arg])
for i in range(16):
    state.solver.add(arg.get_byte(i) >= 0x20)
    state.solver.add(arg.get_byte(i) <= 0x7e)

simgr = proj.factory.simulation_manager(state)
simgr.explore(
    find=lambda s: b"win" in s.posix.dumps(1),   # нашли вывод "win"
    avoid=lambda s: b"fail" in s.posix.dumps(1), # отсекаем неверные пути
)

if simgr.found:
    sol = simgr.found[0].solver.eval(arg, cast_to=bytes)
    print("пароль:", sol)
```

`find`/`avoid` — сердце angr: вы задаёте условие на состояние, а движок сам исследует пространство путей и решает ограничения. `solver.eval` возвращает **конкретное** значение символической переменной, удовлетворяющее всем накопленным ограничениям.

## Ускорение: где angr «залипает» и как помочь

Символьное исполнение дорого: число путей растёт экспоненциально, а сложные функции (крипто, `strcmp` по частям) порождают гигантские ограничения. Практические приёмы:

| Приём | Что делает | Пример |
|---|---|---|
| `SimProcedure`-хук | заменяет функцию готовой моделью | `project.hook_symbol('strlen', angr.SIM_PROCEDURES['libc']['strlen']())` |
| Отсечение `avoid` | убирает «неверные» ветки рано | `avoid=lambda s: ...` |
| Ограничение диапазона | сужает пространство | `state.solver.add(b >= 0x20)` |
| `unicorn` engine | эмулирует «дорогие» участки | `proj.factory.entry_state(engines=...)` |
| `Veritesting` | сворачивает прямолинейный код | `angr.options.VERITESTING` |
| Символическое → конкретное | хук «непрозрачной» функции заглушкой | свой `SimProcedure` |

Особенно помогает замена **сравнения строк** на модель «побайтово равно»: вместо того чтобы angr разбирал цикл `strcmp`, хук делает один символический `==`, и решатель находит вход сразу.

## angr против альтернатив

| Инструмент | Подход | Когда выбирать |
|---|---|---|
| angr | символьное исполнение, полный путь | «найти вход к цели» без перебора |
| Unicorn | конкретная эмуляция | быстрый массовый перебор |
| z3 напрямую | решатель ограничений | ограничения уже извлечены вручную |
| Triton/PINCE | символьное поверх трассы | анти-эмуляция, узкие задачи |
| GDB+Python | ручной контроль | маленькие функции, точная отладка |

Правило: если условие «узкое» и его легко сформулировать как ограничение — хватит z3; если нужно исследовать **ветвления и пути** в бинарнике — angr; если нужен **скоростной перебор** конкретных значений — Unicorn. Часто angr комбинируют с z3 для финального решения сложных ограничений.

## Краевые случаи

- **`auto_load_libs=True`** тянет библиотеки хоста и может «съесть» цель в системном коде — для crackme отключайте.
- **Незамапленный ввод.** Если пароль читается из файла/сети, используйте `simfile`/`SimPackets`, а не `args`.
- **Анти-символика.** Проверки на `is_symbolic` (например, через тайминги) могут увести angr по ложному пути — хукайте такие функции.
- **Слишком много путей.** Добавьте `num_find`/лимит и `avoid`; без них `explore` может не завершиться.
- **Неоднозначный `eval`.** Если решений несколько, `solver.eval` вернёт одно; используйте `solver.eval_upto(x, n)`, чтобы получить все.
- **Флаги проверяются по частям.** Пошаговое сравнение требует `find` по промежуточному состоянию или декомпозиции ограничения.
