## Вопрос, с которого всё начинается

Ты получил shell внутри контейнера. Но контейнер — не песочница: он использует
**то же ядро**, что и хост. Если в ядре есть баг, ты можешь выйти наружу и стать
root на хосте. Один из самых удобных путей — **overlayfs**, файловая система,
на которой построены почти все Docker-образы. Разберём две её уязвимости:
CVE-2021-3493 и CVE-2023-0386.

## Наш пример

Смотрим окружение: мы внутри контейнера, проверяем ядро и наличие overlayfs:

```
$ id
uid=1000(user) gid=1000(user) groups=1000(user)
$ uname -r
5.4.0-42-generic
$ mount | grep overlay
overlay on / type overlay (rw,relatime,lowerdir=/var/lib/docker/overlay2/...)
```

Корень — overlayfs. Ядро `5.4` уязвимо к CVE-2021-3493 (Ubuntu-специфичный баг).
CVE-2023-0386 затрагивает более широкий диапазон ядер.

## Шаг 1: что такое overlayfs

**overlayfs** — файловая система, которая «накладывает» несколько слоёв друг на
друга, создавая единое дерево. Слои бывают:

- **lowerdir** — нижние слои (только для чтения), например базовый образ;
- **upperdir** — верхний слой (для записи), куда попадают изменения;
- **merged** — объединённый вид, который видит процесс.

Когда ты меняешь файл из нижнего слоя, overlayfs **копирует** его в верхний
(copy-up) и там меняет. Изначально нижний файл не трогается. Именно в логике
копирования и копирования прав живут уязвимости.

## Шаг 2: CVE-2021-3493 — баг в Ubuntu-патче

Этот баг специфичен для Ubuntu: дистрибутив добавил в overlayfs поддержку
**расширенных атрибутов** (`xattr`) и **capabilities файлов** раньше, чем они
появились в основном ядре. В реализации была ошибка проверки: непривилегированный
пользователь мог создать файл в overlayfs и навесить на него **file capabilities**
(например, `cap_setuid`).

Идея: если файл помечен capability, при его запуске процесс получает эту
возможность. Получив `cap_setuid` на своём бинарнике, ты можешь стать root:

```
$ cp /bin/bash /tmp/x
$ setcap cap_setuid+ep /tmp/x    # в уязвимом overlayfs проходит без root
$ /tmp/x -p
root#
```

В обычной ФС `setcap` требует root; в уязвимом overlayfs проверка была неполной,
и атрибут «протекал» в нижний слой, где его подхватывало ядро.

## Шаг 3: CVE-2023-0386 — use-after-free при копировании прав

Второй баг — **use-after-free** в `ovl_copy_up`. Когда overlayfs копирует файл из
нижнего слоя в верхний, он переносит и его атрибуты. При определённой
последовательности операций (копирование файла с правами из lowerdir, затем
манипуляции с ним) ядро освобождает объект, но продолжает его использовать.

Эксплуатация:

1. Создаём в overlayfs файл с особыми правами в нижнем слое.
2. Триггерим copy-up так, чтобы получить UAF.
3. Занимаем освобождённую память объектом, который даёт контроль над правами.
4. Получаем файл с root-владельцем или capabilities.
5. Запускаем его — root.

Это уже не «Ubuntu-специфика», а общий баг основного ядра, поэтому он опасен на
многих дистрибутивах.

## Шаг 4: полный прогон (CVE-2023-0386)

```
$ gcc -o exploit exploit.c
$ mkdir -p lower upper work merged
$ ./exploit
[*] creating overlay mount...
[*] triggering UAF in ovl_copy_up...
[*] getting file with root ownership...
$ ls -l merged/pwned
-rwsr-xr-x 1 root root ... merged/pwned
$ ./merged/pwned
root#
```

Как и везде, результат проверяем обратно: `id` должен показать `uid=0`.

## Шаг 5: почему это «побег из контейнера»

Важное различие:

- **Повышение привилегий внутри контейнера** — стать root внутри (если контейнер
  не в user-namespace, это может дать root на хосте).
- **Побег на хост** — выйти за пределы namespaces и получить доступ к хосту.

overlayfs-баги дают оба: получив root в контейнере и доступ к ядру, атакующий
может смонтировать хостовые пути или переписать файлы хоста. Поскольку ядро
общее, «граница» контейнера — это лишь namespaces и cgroups, а не отдельное ядро.

## Шаг 6: как проверить и защититься

Проверка (безопасная) — версия ядра:

```
$ uname -r
5.4.0-42-generic   # CVE-2021-3493 уязвимо
```

Защита:

- **Обновить ядро** — CVE-2021-3493 закрыт в Ubuntu-патчах, CVE-2023-0386 в 6.2+.
- **User namespaces** — включение userns для контейнеров меняет картину (сложнее).
- **Seccomp/AppArmor** — ограничивают `mount`, `setxattr`.
- **Rootless-контейнеры** — снижают последствия.

## Шаг 7: детектирование

Признаки эксплуатации overlayfs-багов:

- создание overlay-монтирований внутри контейнера;
- `setxattr`/`setcap` непривилегированным процессом;
- появление setuid-бинарников в необычных местах (`/tmp`, `/dev/shm`);
- аномальные mount-события в audit-логе.

В Kubernetes смотрят на `securityContext`, запрет `allowPrivilegeEscalation` и
read-only root filesystem.

## Побег из контейнера vs повышение привилегий

Полезно чётко различать два сценария, потому что защита от них разная.

**Повышение привилегий внутри.** Контейнер запущен от root хоста (классический
Docker без userns). Внутри ты уже «root», но ограничен namespaces. Если баг
ядра даёт произвольную запись, ты можешь выйти за namespaces и стать root на
хосте. Здесь важно: контейнер **не** изолирует от ядра.

**Повышение привилегий в rootless-контейнере.** Контейнер запущен от обычного
пользователя через user namespace. Внутри ты можешь быть «root», но на хосте —
нет. Баг ядра всё ещё опасен (можно выйти из userns), но требует дополнительного
шага.

**Побег на хост.** Явная цель — получить доступ к файлам/процессам хоста. Достигается
через перезапись хостовых файлов, монтирование хостовых путей или эксплуатацию
`/proc` хоста.

Понимание, в каком из сценариев ты находишься, определяет и вектор, и то, что
считать «успехом».

## Связанные уязвимости файловых систем

overlayfs — не единственная ФС-поверхность. Схожие баги встречались в:

- **`fs_context`** (CVE-2022-0185) — разбор параметров монтирования.
- **FUSE** — пользовательские ФС, обрабатываемые в ядре.
- **`/proc/self/mem`** — запись в чужую память при определённых условиях.
- **`shiftfs`** (Ubuntu) — ещё один способ «пересоздать» права файлов.

Общий принцип: **любая сложная логика в ядре, работающая с пользовательскими
данными, — поверхность атаки**. Файловые системы особенно привлекательны, потому
что их легко «натравить» на подконтрольные данные (создать файл, смонтировать,
прочитать).

## Как это устроено: copy-up и права

Разберём механику copy-up подробнее, потому что именно в ней живут баги.

Когда процесс открывает файл из нижнего слоя на запись, overlayfs:

1. Создаёт копию файла в верхнем слое.
2. Копирует **содержимое** файла.
3. Копирует **метаданные**: владельца, права, расширенные атрибуты.
4. Переключает путь в merged-слое на новую копию.

Проблема в шагах 2–3: если во время копирования атакующий изменит исходный файл
(например, заменит его симлинком или другим файлом с иными правами), то
скопированные метаданные могут не соответствовать содержимому. Это классическая
**гонка time-of-check-to-time-of-use (TOCTOU)**.

CVE-2023-0386 эксплуатирует именно это: между проверкой и копированием прав
объект меняется, и в результате в верхнем слое оказывается файл с правами,
которые атакующий не должен был получить. Уязвимость усугубляется тем, что
overlayfs используется в контейнерах повсеместно, а значит, вектор доступен из
любого контейнера с правом монтирования.

## Почему этот урок стоит здесь

Этот урок идёт после `pwn-kernel-core` не случайно: обе overlayfs-уязвимости —
это **баги ядра**, а не приложения. Без понимания пула, UAF и copy-up ты не
поймёшь, почему «безобидное» монтирование даёт root. Кроме того, здесь впервые
появляется контейнерная специфика: та же самая уязвимость в обычной системе даёт
просто privesc, а в контейнере — побег на хост. Дальше (`pwn-container-escape-cve`,
`pwn-k8s-escape-cve`) эта идея развивается до побега из Kubernetes.

## Итог по технике

Обе уязвимости показывают один важный урок: **граница контейнера — это не
граница безопасности**. Пока контейнер делит ядро с хостом, любой баг ядра
становится путём наружу. overlayfs особенно удобен для атакующего, потому что
доступен почти везде (Docker, Podman, containerd), а его логика copy-up сложна и
подвержена гонкам. Правильный вывод для защищающихся — держать ядро нод
обновлённым и минимизировать права контейнеров; для атакующих — помнить, что
«внутри контейнера» ещё не значит «в тупике».

## Что если не сработало

| Симптом | Причина | Что делать |
|---|---|---|
| `mount failed` | нет CAP_SYS_ADMIN | искать другой вектор |
| `setcap failed` | ядро пропатчено | проверить версию |
| нет root | не та версия | сверить CVE и ядро |
| контейнер read-only | запрещены монтирования | искать escape иначе |

## Краткая шпаргалка

| Что | CVE-2021-3493 | CVE-2023-0386 |
|---|---|---|
| Тип | неверная проверка xattr/cap | use-after-free |
| Область | Ubuntu overlayfs | основное ядро |
| Примитив | file capabilities | UAF → root-файл |
| Итог | root | root / escape |
| Фикс | патч Ubuntu | ядро 6.2+ |

## Что мы теперь знаем

- overlayfs накладывает слои и копирует файлы при записи (copy-up).
- CVE-2021-3493 — Ubuntu-баг с расширенными атрибутами и capabilities.
- CVE-2023-0386 — UAF при копировании прав в основном ядре.
- Обе дают root и позволяют выйти из контейнера.
- Защита: обновление ядра, userns, seccomp, rootless-контейнеры.
