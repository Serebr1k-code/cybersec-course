## Вопрос, с которого всё начинается

Ты привык, что баг — это переполнение буфера в C-коде. В браузере баг живёт в **JavaScript-движке**, написанном на C++, а ввод — это твой же JavaScript. И всё равно получается полноценный RCE: от строки `let a = [1.2];` до исполнения кода в процессе Chrome. Как? Через **type confusion** и **JIT-баги**. В этом уроке разберём, как «неправильная догадка оптимизатора» превращается в чтение и запись произвольной памяти.

## Наш пример

Возьмём движок **V8** (Chrome, Node.js). Для отладки есть shell `d8` с флагом `--allow-natives-syntax`, который открывает доступ к внутренним функциям движка.

Запускаем:

```
$ d8 --allow-natives-syntax
d8> let obj = {a: 1, b: 2};
d8> %DebugPrint(obj);
DebugPrint: 0x1a2b3c4d0e21: [JS_OBJECT_TYPE]
 - map: 0x1a2b3c4d1234 <Map(HOLEY_ELEMENTS)>
 - properties: 0x1a2b3c4d5678 <FixedArray[2]>
 - elements: 0x1a2b3c4d9abc <FixedArray[0]>
 0x1a2b3c4d0e21: [Object] in OldSpace
 - map: ...
 - {a: 1}
 - {b: 2}
```

`%DebugPrint` показывает, из чего реально состоит объект в памяти: **map** (описание типа), **properties** и **elements**. Запомним это — дальше мы будем ломать именно map.

## Шаг 1: map — «паспорт» объекта в V8

В V8 у каждого объекта есть **map** — структура, описывающая его тип: какие свойства, какого типа, как лежат элементы. Когда движок видит `obj.a`, он по map понимает, где лежит `a` и какого оно типа.

JIT-оптимизатор (`TurboFan`) использует map для **спекуляций**: «если у этого объекта такая-то map, то поле `x` — это double, и его можно читать как число». Если спекуляция верна, код работает быстро. Если движок где-то ошибся и объект на самом деле **другого типа** — возникает **type confusion**: код трактует байты не как то, чем они являются.

## Шаг 2: type confusion — почему это опасно

Простой пример концепции: движок считает, что массив содержит **double** (числа с плавающей точкой, 8 байт каждое), а на деле мы подсунули массив **указателей**. Тогда:

- запись числа в такой массив перезапишет **указатель** на объект;
- чтение «числа» вернёт нам **адрес объекта**, интерпретированный как double.

Вот это и есть два базовых примитива браузерного эксплойта:

- **addrof** — «дай адрес объекта» (читаем указатель как число).
- **fakeobj** — «сделай объект по адресу» (пишем адрес туда, где движок ждёт указатель).

В реальных эксплойтах type confusion получают через баг JIT (оптимизатор сделал неверное предположение) или через UAF (объект освободили, а ссылка осталась — и по ней подсунули другой тип).

## Шаг 3: из addrof/fakeobj — в arbitrary read/write

Имея `addrof` и `fakeobj`, строят поддельный объект, у которого поле «длина массива» огромно (например, `0xFFFFFFFF`). Получается **array length corruption**:

```javascript
// концептуально: массив с длиной 0xffffffff
// index out of bounds -> чтение/запись за пределами реального массива
let rw = [1.1, 2.2, 3.3, 4.4];
// после подмены длины:
let val = rw[0x1000];        // читаем произвольную память
rw[0x1000] = someAddress;    // пишем произвольную память
```

Так получают **arbitrary read/write**: чтение и запись по любому адресу в адресном пространстве процесса. Это уже практически RCE: находишь адрес JIT-кода (он исполняемый) и переписываешь его на свой shellcode.

## Шаг 4: от arbitrary write к исполнению кода

Дальше путь стандартный:

1. Найти адрес **JIT-страницы** (регион с исполняемым кодом, сгенерированным движком).
2. Перезаписать начало сгенерированной функции своим шеллкодом.
3. **Вызвать эту JS-функцию** — процессор исполнит наш код.

Именно поэтому браузерные эксплойты так ценятся: одна строка JS с багом в движке даёт исполнение кода внутри процесса браузера, а оттуда — побег из песочницы (sandbox escape) вторым багом.

## Шаг 5: современные защиты

Браузеры не стоят на месте, и эксплойт усложняется:

- **Pointer compression** в V8 — указатели внутри кучи хранятся 32-битными смещениями, что ломает наивные addrof/fakeobj.
- **Sandbox (V8 sandbox)** — объекты кучи изолированы, и произвольная запись внутри неё не даёт выйти за пределы.
- **CFI / CET** — проверка косвенных вызовов и потока управления, как на других платформах.
- **ASLR + раздельные процессы** — сайт в отдельном процессе от «привилегированных» частей браузера.

Поэтому современный browser-эксплойт — это цепочка: **баг движка → arbitrary r/w → RCE в рендерер-процессе → sandbox escape → RCE в системе**. Каждый шаг — отдельная уязвимость.

## Шаг 6: как искать такие баги

Браузерные баги не «видно глазами» — их находят системно. Несколько практических подходов:

- **Диффинг патчей.** Разработчики чинят type confusion и UAF и выпускают обновление. Диффинг коммитов движка (V8, SpiderMonkey) показывает, **где** они тронули проверку типа — это и есть место бага. Мы подробно разберём этот подход в уроке про N-day.
- **Фаззинг JS-движка.** Специализированные фаззеры (например, `domato`, `fuzzilli`) генерируют JavaScript и ищут падения. Type confusion часто проявляется как несовпадение типов при оптимизации.
- **Аудит оптимизаций JIT.** Баг почти всегда там, где оптимизатор делает предположение о типе. Читая код оптимизации, ищут места, где предположение можно нарушить из JS.
- **Отладка через `--allow-natives-syntax`.** `%DebugPrint`, `%HaveSameMap`, `%OptimizeFunctionOnNextCall` позволяют из JS видеть, что движок думает об объекте, и ловить расхождение между «думает» и «есть».

Начинать обычно проще с **известного CVE**: берёшь публичный эксплойт, воспроизводишь в нужной версии `d8`, разбираешь примитивы. А уже потом — поиск своих багов. Так ты учишься на готовых примерах, понимая каждый шаг, вместо того чтобы сразу искать баг «с нуля».

Отдельно стоит помнить про **разделение процессов**: современный Chrome запускает сайт в рендерер-процессе, изолированном от системы. Поэтому RCE в движке — это ещё не «конец»: нужен **sandbox escape**, чтобы выйти из изоляции. В CTF часто дают только первую половину (RCE в движке), и на этом задача заканчивается. В реальном bug bounty вторая половина ценится даже дороже первой.

## Что мы теперь знаем

- Баги браузера живут в **JS-движке**, но дают полноценный RCE.
- **map** описывает тип объекта; **type confusion** — когда движок трактует объект не как его настоящий тип.
- Базовые примитивы: **addrof** (адрес объекта) и **fakeobj** (объект по адресу).
- Через поддельный массив получают **arbitrary read/write**, затем переписывают **JIT-код** на shellcode.
- Современные защиты (pointer compression, sandbox, CFI) требуют многошаговых цепочек.
