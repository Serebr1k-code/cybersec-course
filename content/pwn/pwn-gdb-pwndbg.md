## Вопрос, с которого всё начинается

Эксплойт не сработал: программа упала, но непонятно почему. Смещение не то? Выравнивание? Адрес неверный? Смотреть на «Segmentation fault» бесполезно — нужно заглянуть внутрь процесса в момент падения.

Для этого есть **GDB** — отладчик, который умеет останавливать программу, показывать память и регистры. Сам по себе он аскетичен, поэтому его дополняют расширениями **pwndbg** или **gef** — они рисуют стек, кучу и регистры человеческим языком.

## Наш пример: краш, который надо понять

Возьмём знакомый бинарь:

```c
// vuln.c
#include <stdio.h>
#include <stdlib.h>
void win(void) { system("/bin/sh"); }
int main(void) { char buf[64]; gets(buf); puts(buf); return 0; }
```

```bash
$ gcc -fno-stack-protector -no-pie -o vuln vuln.c
```

Мы уже знаем, что он падает на длинном вводе. Разберём этот краш под отладчиком и заодно покажем, что делать, когда эксплойт «почти работает».

## Шаг 1. Установка и первый запуск

```bash
$ git clone https://github.com/pwndbg/pwndbg
$ cd pwndbg && ./setup.sh
```

После установки запускаем:

```bash
$ gdb -q ./vuln
pwndbg: loaded 194 commands. Type pwndbg for a list.
Reading symbols from ./vuln...
(gdb) run < pattern.txt
Program received signal SIGSEGV, Segmentation fault.
```

Отладчик остановился в момент падения — самое интересное место. Дальше смотрим, что там.

## Шаг 2. bt и info registers — где мы упали

`bt` (backtrace) показывает цепочку вызовов, приведшую к падению:

```bash
(gdb) bt
#0  0x00000000004011db in main ()
#1  0x00007ffff7a03d90 in __libc_start_main ()
```

Это говорит, что упали внутри `main` — значит, управление ушло по нашему перезаписанному адресу. Посмотрим регистры:

```bash
(gdb) info registers rip rsp rbp
rip            0x4141414141414141     # управляем!
rsp            0x7fffffffe3a0
rbp            0x4141414141414141
```

Регистр `rip` — это адрес следующей инструкции. Он равен `0x4141414141414141` («AAAA»), значит, адрес возврата действительно перезаписан. Регистр `rsp` указывает на вершину стека — туда `ret` и заглядывает за адресом.

## Шаг 3. cyclic в pwndbg — смещение без калькулятора

Помнишь `cyclic_find` из прошлых уроков? В pwndbg есть команда `cyclic`, которая делает то же самое, но прямо в отладчике:

```bash
(gdb) cyclic
[+] Found a cyclic pattern at offset 72
```

Одна команда — и смещение известно. Это самый быстрый способ: не надо вручную копировать значение `rip` в Python.

## Шаг 4. telescope и stack — смотрим стек

Команда `telescope` (сокращённо `tele`) показывает содержимое памяти, разыменовывая указатели — сразу видно, где лежат какие адреса:

```bash
(gdb) telescope $rsp 8
00:0000│ rsp 0x7fffffffe3a0 ◂— 0x4141414141414141 ('AAAAAAAA')
01:0008│     0x7fffffffe3a8 ◂— 0x4141414141414141 ('AAAAAAAA')
02:0010│     0x7fffffffe3b0 ◂— 0x0
```

Стрелкой `◂—` pwndbg помечает, что ячейка указывает на адрес. Здесь мы видим наши `A` — мусор, который залил возврат. Если бы вместо `A` стоял адрес `win`, всё бы сработало.

Есть и простая команда `x` — посмотреть память без разыменования:

```bash
(gdb) x/4gx $rsp
0x7fffffffe3a0: 0x4141414141414141  0x4141414141414141
0x7fffffffe3b0: 0x0000000000000000  0x00007ffff7a03d90
```

`x/4gx` читает 4 «giant» (8-байтовых) значения в hex.

## Шаг 5. vmmap и checksec — карта памяти и защиты

`vmmap` показывает, какие области памяти куда отображены, и главное — какие из них исполняемые (`x`):

```bash
(gdb) vmmap
LEGEND: STACK | HEAP | CODE | DATA | WX | RODATA
  0x400000     0x401000 r--p   [ELF] /vuln
  0x401000     0x402000 r-xp   [ELF] /vuln     # код — исполняемый
  0x7fffffff0000 0x7ffffffff000 rw-p   [stack]  # стек — только rw, не x
```

Отсюда видно, почему NX блокирует shellcode: у стека нет бита `x` (исполняемость). А `checksec` в pwndbg покажет все защиты разом:

```bash
(gdb) checksec
    Canary:  disabled
    NX:      enabled
    PIE:     disabled
```

## Шаг 6. gdb.attach — отладка из эксплойта

Ручной запуск удобен, но в реальном эксплойте мы хотим остановиться на нужном моменте. Функция `gdb.attach(p)` подключает отладчик к живому процессу, запущенному из Python:

```python
from pwn import *
p = process('./vuln')
gdb.attach(p, gdbscript='b *main+80\nc')
p.sendline(b'A'*72 + p64(0x4011a6))
p.interactive()
```

`gdbscript` — команды, которые отладчик выполнит сразу: здесь поставить брейкпоинт на `main+80` и продолжить (`c`). Дальше отладчик даст посмотреть состояние ровно перед возвратом.

## Шаг 7. Отладка сервиса, который форкается

Иногда программа запускается под `socat` или `inetd` и на каждое соединение делает `fork`. Тогда отлаживать надо **дочерний** процесс, а не родителя. В GDB включают режим follow-fork и ставят точку останова на входе в `main`:

```bash
(gdb) set follow-fork-mode child
(gdb) set detach-on-fork off
(gdb) b main
(gdb) run
```

После этого отладчик останавливается уже в форкнутом процессе, и можно смотреть стек и регистры так же, как обычно.

## Шпаргалка по командам

| Команда | Что делает |
|---|---|
| `run < input` | запустить с вводом из файла |
| `bt` | стек вызовов до падения |
| `info registers` | значения регистров |
| `cyclic` | найти смещение до RIP |
| `telescope $rsp` | показать стек с разыменованием |
| `x/8gx $rsp` | прочитать 8 слов памяти |
| `vmmap` | карта областей памяти и их права |
| `checksec` | включённые защиты |
| `b *main+80` | брейкпоинт по адресу |
| `ni` / `si` | шаг без захода / с заходом в функции |
| `heap` / `bins` | состояние кучи и бинов (pwndbg) |

Этой шпаргалки достаточно, чтобы разобрать почти любой упавший эксплойт: находишь, где остановились, смотришь `bt` и `info registers`, проверяешь стек через `telescope`.

## Шаг 8. Работа с утечками

Когда эксплойт печатает адрес libc, его нужно аккуратно прочитать из вывода. В GDB удобно смотреть, что именно легло в регистр в момент вызова:

```bash
(gdb) b *main+80
(gdb) c
(gdb) x/s $rdi        # что за строка в rdi
(gdb) x/gx $rsp       # что на вершине стека
```

Команда `x/s` печатает строку по адресу, `x/gx` — 8-байтовое значение в hex. С их помощью проверяют, что утечка — действительно адрес libc, а не мусор. Ещё полезно сравнить утёкший адрес с картой памяти:

```bash
(gdb) vmmap libc
0x00007ffff7dc0000 0x00007ffff7f8f000 r-xp /usr/lib/x86_64-linux-gnu/libc.so.6
```

Если утёкший адрес попадает в диапазон libc — можно смело вычислять базу вычитанием известного смещения.

## Что мы теперь знаем

- GDB останавливает программу и показывает регистры и память в момент краха.
- `bt` показывает стек вызовов, `info registers` — значения регистров.
- `cyclic` в pwndbg сам находит смещение до `rip`.
- `telescope` разыменовывает стек, `x/gx` читает память напрямую.
- `vmmap` показывает права областей памяти, `checksec` — включённые защиты.
- `gdb.attach(p)` подключает отладчик к процессу из эксплойта.

## Куда дальше

Отладчик — твой главный союзник при разборе любого эксплойта. В следующем уроке (`pwn-shellcode`) мы займёмся кодом, который хотим выполнить: научимся писать shellcode и размещать его так, чтобы NX его не убил. Запомни главное: **когда эксплойт падает, не гадай — останови процесс в GDB и посмотри, куда реально ушёл rip.**

## Где пригодится

- **CTF Pwn:** почти каждый нетривиальный эксплойт отлаживается в GDB.
- **Отладка эксплойтов:** быстрое нахождение ошибок смещения, выравнивания, утечек.
- **Реверс-инжиниринг:** понимание поведения программы в динамике.
- **Разработка эксплойтов:** `gdb.attach` встраивает отладку прямо в скрипт.
