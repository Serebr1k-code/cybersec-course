## Вопрос, с которого всё начинается

В прошлом уроке мы разобрали use-after-free: программа освободила объект, но оставила на него живой указатель. UAF — это дверь. А что за дверью? В этом уроке мы возьмём конкретный сценарий — **двойное освобождение** (double-free) маленького чанка — и превратим его в запись по произвольному адресу.

Спойлер: одного `free` лишнего раза достаточно, чтобы аллокатор начал выдавать нам один и тот же кусок памяти дважды.

## Наш пример

Возьмём классический уязвимый сервис: у него есть меню `alloc / free / edit`, и он **не зануляет указатель после `free`** и **не мешает освободить один и тот же чанк дважды**. Именно такие программы дают уязвимость `double-free`.

Чтобы увидеть механику, соберём минимальный стенд и прогоним его. Программа берёт чанки по `0x50` байт, наполняет кэш малых чанков несколькими освобождениями, затем освобождает два чанка `H` и `I`, а потом повторно освобождает `H` (через UAF занулив его служебное поле):

```
A..G=0x292db010..0x292db250  H=0x292db2b0  I=0x292db310
free-list: H -> I -> H   (цикл)

  malloc -> 0x292db2b0 (H)
  malloc -> 0x292db310 (I)
  malloc -> 0x292db2b0 (H)
  malloc -> 0x292db310 (I)
  ...
```

Смотри, что произошло: `malloc` начал выдавать `H` и `I` **по кругу**. Это и есть перекрытие: две «разные» аллокации указывают на одни и те же байты.

Важная оговорка про современную glibc: маленькие освобождения сначала перехватывает `tcache` (кэш на поток, о нём — в прошлых уроках), поэтому наш стенд демонстрирует цикл именно в нём. Классический **fastbin dup** — тот же приём, но в `fastbin`, куда чанк попадает, когда кэш для его размера уже полон. Механика цикла одинаковая; ниже разберём оба случая.

## Шаг 1. Что такое fastbin

`fastbin` — это массив коротких односвязных списков в аллокаторе glibc. В них попадают маленькие чанки (на amd64 — размером до `0x80`). «Односвязный» значит, что у каждого свободного чанка хранится только один указатель на следующий — он лежит в первых 8 байтах пользовательской области и называется `fd`. Список работает по принципу LIFO: `free` кладёт чанк в голову, `malloc` забирает из головы.

Главное отличие fastbin от больших бинов: **консолидации нет**. Освобождённые маленькие чанки не сливаются с соседями, а лежат отдельными звеньями. Именно поэтому в fastbin легко создать цикл.

## Шаг 2. Почему двойной free создаёт цикл

Освободим `A`, потом `B`, потом `A` снова. Проследим за списком (запись `X -> Y` значит «голова X, его `fd` указывает на Y»):

```
free(A)   ->  A          (A.fd = NULL)
free(B)   ->  B -> A     (B.fd = A)
free(A)   ->  A -> B -> A   <- A.fd снова указывает на B, получился цикл
```

Теперь `malloc` выдаёт `A`, потом `B`, потом снова `A`, потом снова `B` — и так бесконечно. Два `malloc` вернули один и тот же адрес: это перекрытие, из которого растёт произвольная запись.

## Шаг 3. Почему нельзя просто `free(A); free(A)`

glibc не даёт освободить один и тот же чанк дважды подряд. При `free` в fastbin она сравнивает чанк с текущей головой списка:

```c
if (__glibc_unlikely (old == p))       /* p == голова fastbin */
    malloc_printerr ("double free or corruption (fasttop)");
```

Поэтому «в лоб» — `free(A); free(A)` — программа упадёт с `double free or corruption (fasttop)`. Обход прост: между двумя `free(A)` освобождаем **другой** чанк `B`. Тогда голова — `B`, а не `A`, проверка `old == p` проходит, и цикл создаётся. Отсюда канонический порядок: `free(A); free(B); free(A)`.

## Шаг 4. Из цикла — в произвольную запись

Цикл сам по себе даёт только перекрытие. Произвольную запись получают так: перезаписывают `fd` одного из чанков на **целевой адрес** (через тот же UAF/`edit`), а потом «вычерпывают» список несколькими `malloc`, пока не дойдут до цели.

```python
from pwn import *
p = process('./chall')
alloc(0x60); alloc(0x60)          # A, B
free(A); free(B); free(A)         # A -> B -> A
edit(A, p64(target - 0x10))       # пишем цель в fd головного чанка
alloc(0x60)                       # вернёт A
alloc(0x60)                       # вернёт B
alloc(0x60)                       # вернёт A (снова)
alloc(0x60)                       # вернёт target!
```

Два смещения здесь неслучайны. Первое: `target - 0x10`, потому что `malloc` возвращает указатель **на данные**, а не на заголовок чанка (заголовок — 16 байт: `prev_size` и `size`). Второе: по адресу `target` должен лежать **правдоподобный `size`**, иначе `malloc` заметит подделку.

## Шаг 5. Какие проверки обходит malloc

Когда `malloc` берёт чанк из fastbin, он проверяет, что это вообще похоже на чанк:

1. размер чанка соответствует бин-индексу запрошенного размера;
2. `fd` указывает на **выровненный** адрес (иначе `malloc(): unaligned fastbin chunk detected`);
3. размер находится в допустимом диапазоне fastbin.

Поэтому «магический» адрес цели выбирают так, чтобы рядом лежало подходящее число-размер. В старых glibc (до 2.34) классикой был `__malloc_hook`:

```python
# glibc < 2.34: рядом с __malloc_hook есть байты, похожие на size
target = libc.symbols['__malloc_hook'] - 0x23
```

Смещение `-0x23` подобрано так, чтобы по `target + 8` лежало значение `0x7f` — валидный размер чанка. Записав туда адрес `system`, а потом сделав `malloc`, эксплойт получает вызов `system` — но это уже тема FSOP и целей modern glibc.

## Шаг 6. fastbin dup в эпоху tcache

Начиная с glibc 2.26 появился `tcache` — кэш на поток, который перехватывает все освобождения размером до `0x410`. Это значит: чтобы вообще дойти до fastbin, `tcache` для нужного размера должен быть **заполнен** (по умолчанию 7 слотов). Именно поэтому в нашем примере сначала идут семь `free`, наполняющих tcache, и только восьмой `free` уходит в fastbin.

Практический вывод: если доступен tcache, обычно проще делать **tcache poisoning** — там нет проверки «голова списка». fastbin dup применяют, когда tcache для нужного размера уже полон или когда нужен размер ≤ `0x80`.

## Шаг 7. Связка с malloc_consolidate

Если запросить большой чанк (не из fastbin), glibc вызовет `malloc_consolidate`: она сольёт все fastbin-чанки и поместит их в `unsorted bin`. Это можно использовать в свою пользу — например, чтобы превратить перекрытие в утечку libc:

```python
# после создания цикла и перезаписи fd:
alloc(0x500)   # вызовет malloc_consolidate -> чанки уйдут в unsorted bin
```

## Что мы теперь знаем

- `fastbin` — короткие односвязные LIFO-списки для чанков до `0x80`, без консолидации.
- Указатель на следующий чанк лежит в `fd` (первые 8 байт данных).
- Двойной `free` подряд ловится проверкой `old == p`; обход — вставить между ними другой чанк.
- Порядок `free(A); free(B); free(A)` создаёт цикл `A -> B -> A` и перекрытие.
- Перезапись `fd` на `target - 0x10` даёт аллокацию по произвольному адресу.
- Для этого `tcache` нужного размера должен быть полон, а по `target + 8` — лежать валидный `size`.

## Разбор в GDB: смотрим список fastbin вживую

Теория видна в отладчике за один прогон. Остановимся после `free(A); free(B); free(A)` и попросим glibc показать бин:

```gdb
pwndbg> bins
fastbins
0x20: 0x0
0x30: 0x0
0x40: 0x0
0x50: 0x0
0x60: 0x5555555592b0 ◂— 0x555555559310 ◂— 0x5555555592b0 (circular)
0x70: 0x0
```

Строка `0x60` — это и есть наш цикл: `A → B → A`. Стрелка `◂—` показывает переход по полю `fd`. Именно эту структуру мы потом перезаписываем на `target - 0x10`, и именно поэтому важно, чтобы целевой адрес был выровнен: `malloc` отвергает нечётный указатель.

## tcache poisoning против fastbin dup

На modern glibc удобнее чаще атаковать tcache — он раньше fastbin и проще. Сравним:

| | tcache | fastbin |
|---|--------|---------|
| Размер | до `0x410` | до `0x80` |
| Проверка двойного free | `key`-поле (2.29+) | `old == p` (только голова) |
| Нужен ли «разбавитель» | да (для обхода `key`) | да (`free(A); free(B); free(A)`) |
| Заголовок чанка | `fd` и `key` | только `fd` |
| Когда выбирают | по умолчанию | когда tcache полон или нужен ≤ `0x80` |

Практический вывод: если задача допускает оба, сначала пробуй tcache — там меньше проверок. fastbin dup оставляй на случаи, когда tcache нужного размера уже заполнен (7 слотов) или когда цель требует маленького размера.

## Частые ошибки и ограничения

- **`free(A); free(A)` подряд** — падение с `double free or corruption (fasttop)`. Между ними обязателен другой чанк.
- **Невыровненный `target`** — `malloc(): unaligned fastbin chunk detected`. Цель выравнивают по 16 байт.
- **Нет валидного `size`** по `target + 8` — `malloc(): invalid size`. Поэтому целятся в места вроде `__malloc_hook - 0x23`, где рядом лежит `0x7f`.
- **glibc ≥ 2.34** убрала `__malloc_hook` — классическая цель исчезла; на новых системах целятся в `_IO_list_all`, `exit_funcs` или перекрывают структуры приложения.
- **Совместимость версий.** Смещение `-0x23` и наличие tcache зависят от сборки glibc; всегда проверяй `ldd --version` на целевой машине, а не полагайся на «средний» дистрибутив.
