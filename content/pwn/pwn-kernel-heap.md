Kernel heap — это область эксплуатации, связанная с аллокатором ядра SLUB (в новых ядрах — SLAB/SLUB) и объектами, размещаемыми в `kmalloc`-кэшах. В отличие от userland-glibc, в ядре нет tcache и бинов в привычном виде: есть SLUB-кэши, per-CPU freelist, а объекты часто переиспользуются. Типичные баги — UAF, переполнения в slab-объектах, произвольная запись через метаданные. В этом уроке — устройство SLUB, `kmalloc`-кэши, переиспользование объектов, техники UAF (msg_msg, tty_struct, pipe_buffer, seq_operations) и практические эксплойты.

## Устройство SLUB

SLUB управляет кэшами фиксированного размера. `kmalloc` выбирает кэш по размеру: `kmalloc-8`, `kmalloc-16`, ..., `kmalloc-1024`, `kmalloc-2048`, `kmalloc-4096` и т.д. Каждый кэш состоит из slab'ов (страниц), разбитых на объекты. Свободные объекты связаны в freelist внутри slab'а. Ключевые структуры: `struct kmem_cache`, `struct page` (флаги slab), `freelist`. При освобождении объект возвращается в freelist; при выделении берётся первый свободный (LIFO). Это означает, что освобождение объекта, а затем аллокация объекта того же размера с большой вероятностью вернут ту же память — основа UAF-эксплуатации.

## kmalloc-кэши и выбор размера

```bash
# посмотреть кэши
cat /proc/slabinfo | grep kmalloc
# в gdb (pwndbg)
kmalloc
slub
```

Размеры кэшей: 8, 16, 32, 64, 96, 128, 192, 256, 512, 1024, 2048, 4096, 8192. Если объект занимает, например, 0x80 байт, он попадёт в `kmalloc-128`. Важно подобрать ядерный объект-«жертву» того же кэша, чтобы переиспользовать освобождённую память.

## Переиспользование объектов (object overlap)

Идея UAF-эксплуатации: (1) уязвимый модуль освобождает объект, но оставляет указатель; (2) вы аллоцируете ядерный объект того же размера с контролируемым содержимым, который занимает ту же память; (3) через UAF-указатель вы читаете/пишете поля этого объекта; (4) перезаписываете указатель на функцию и триггерите вызов. Популярные объекты-«жертвы»:

| Объект | Размер | Триггер |
|---|---|---|
| `tty_struct` | ~0x2b8 | операции с `/dev/ptmx` |
| `pipe_buffer` | 0x280 (массив) | `pipe`/`read`/`write` |
| `seq_operations` | 0x20 | чтение `/proc/self/stat` |
| `msg_msg` | переменный | `msgsnd`/`msgrcv` |
| `sk_buff` | переменный | сокеты |

## msg_msg как примитив

`msg_msg` — структура System V-сообщений, размещаемая в `kmalloc`. Её размер = `sizeof(struct msg_msg) + размер данных`. Это позволяет «занять» почти любой kmalloc-кэш и контролировать содержимое. Также `msg_msgseg` (сегменты для больших сообщений) дают дополнительные примитивы. Классика: освободить уязвимый объект, занять его `msg_msg` с контролируемыми данными, через UAF перезаписать `m_ts` (размер) для создания произвольного чтения/записи (OOB через msgrcv). Подробные техники — в специализированных writeup'ах; здесь важно понять идею.

## seq_operations как простой приём

`seq_operations` (0x20 байт) содержит четыре указателя на функции (`start`, `stop`, `next`, `show`). Он аллоцируется при открытии `/proc/self/stat`. Если у вас UAF в кэше `kmalloc-32`, вы можете занять объект `seq_operations`, перезаписать `start` на ROP-гаджет/функцию и триггернуть чтение файла. Это один из самых простых приёмов для получения RIP-контроля в ядре:

```c
int fd = open("/proc/self/stat", O_RDONLY);   // аллоцирует seq_operations
// через UAF перезаписать seq_ops->start
read(fd, buf, 1);                              // вызовет start
```

## Разобранный пример: UAF → seq_operations → RIP

```python
# эскиз эксплойта (в userland, взаимодействует через /dev/vuln)
# 1) освободить уязвимый объект размера 0x20
ioctl(fd, FREE_IDX, 0)
# 2) открыть /proc/self/stat, чтобы занять память seq_operations
fd2 = open('/proc/self/stat', O_RDONLY)
# 3) через UAF записать в seq_operations->start адрес гаджета
write(fd, p64(stack_pivot_gadget), 8)
# 4) прочитать файл -> вызов start -> контроль RIP
read(fd2, buf, 1)
```

Далее строят ROP для `commit_creds(prepare_kernel_cred(0))` или `modprobe_path`.

## Проверка в gdb

```bash
gdb ./vmlinux
(gdb) target remote :1234
(gdb) kmalloc          # состояние кэшей (pwndbg)
(gdb) slub             # slab'ы
(gdb) p &modprobe_path
(gdb) b seq_read
```

Смотрите freelist и адреса объектов, чтобы понять, куда попадёт переиспользование.

## Частые ошибки

- **Неверный размер.** Объект уходит в другой кэш — переиспользование не срабатывает.
- **Per-CPU freelist.** Освобождение и аллокация на разных CPU дадут разные slab'ы; привязывайте процесс (`sched_setaffinity`).
- **Hardened freelist.** Новые ядра шифруют freelist — нужны утечки/обходы.
- **Паника.** Ошибка в ядерном объекте убивает систему.
- **Не тот триггер.** Проверьте, что перезаписанный указатель действительно вызывается.

## Полный разбор UAF в kernel-модуле

Рассмотрим сквозной пример. Модуль создаёт структуру `struct obj { char data[0x18]; void (*callback)(void); }` размером 0x20 и предоставляет `ioctl` для аллокации, освобождения и записи. В `free` он вызывает `kfree(obj)` но не зануляет указатель — UAF. План эксплойта: (1) определить кэш (`kmalloc-32`); (2) освободить объект; (3) открыть `/proc/self/stat`, что аллоцирует `seq_operations` (0x20) в том же кэше и переиспользует память; (4) через UAF записать в поле `start` указатель на гаджет/функцию; (5) прочитать файл, вызвав `start`. Для получения root при SMEP можно записать `start = stack_pivot`, а далее построить ROP. Если SMEP выключен — записать указатель на userland-функцию `escalate`, которая вызовет `commit_creds`. Каждый шаг проверяется в gdb: `kmalloc`, `slub`, `b seq_read`.

## msg_msg: расширенный примитив

`msg_msg` даёт больше гибкости, чем `seq_operations`. Структура `msg_msg` начинается с полей `m_list`, `m_type`, `m_ts`, `next`, `security`, после которых идут данные. Размер объекта = `0x30 + размер данных` (зависит от ядра). Техники: (1) занять освобождённый объект сообщением с контролируемыми данными; (2) через UAF перезаписать `m_ts` (размер) на большое значение, чтобы `msgrcv` прочитал за пределами буфера — OOB-чтение (утечка ядерных указателей); (3) для записи использовать `msg_msgseg` (сегменты). Комбинация OOB-чтения и записи позволяет построить полноценный arbitrary read/write в ядре, что затем ведёт к `modprobe_path` или ROP. Это стандартный маршрут в современных задачах.

## pipe_buffer и page-cache

`pipe_buffer` — массив структур в кэше `kmalloc-1024`, создаваемый при `pipe()`. Каждый элемент содержит `struct page *page`, `offset`, `len`, `ops`. Перезаписав `page` или `ops`, можно получить примитивы: чтение/запись произвольных страниц (через page-cache) или RIP-контроль (через `ops->release`). Техника `Dirty Pipe` (CVE-2022-0847) — известный пример эксплуатации `pipe_buffer` для записи в read-only файлы. В CTF `pipe_buffer` часто используется как цель переиспользования: UAF-объект занимается `pipe_buffer`, затем перезаписывается `page`/`ops`.

## Чек-лист kernel heap-эксплуатации

1. Определите размер уязвимого объекта и его kmalloc-кэш.
2. Привяжите процесс к одному CPU (`sched_setaffinity`).
3. Выберите объект-жертву того же размера (`seq_operations`, `msg_msg`, `pipe_buffer`, `tty_struct`).
4. Освободите уязвимый объект и займите память жертвой.
5. Через UAF прочитайте/перезапишите нужные поля.
6. Получите утечку (KASLR) или RIP-контроль.
7. Перейдите к ROP/`modprobe_path`.
8. Проверяйте каждый шаг в gdb (`kmalloc`, `slub`, `vis_heap_chunks`-аналог).

## Итог

Kernel heap — область, где понимание SLUB и переиспользования объектов критично. Начинайте с `seq_operations` (простой RIP), затем осваивайте `msg_msg` (OOB r/w) и `pipe_buffer`. Помните про per-CPU freelist и привязку к CPU — это отличает стабильный эксплойт от нестабильного. И всегда проверяйте гипотезы в gdb: ядро не прощает ошибок, и цена неверного шага — паника всей системы.

## Итоговая мысль

Kernel heap — это прежде всего понимание того, как объекты переиспользуют память. Научитесь определять кэш объекта и подбирать жертву того же размера; привязывайте процесс к CPU; проверяйте freelist в gdb. Начните с `seq_operations` для RIP-контроля, затем освойте `msg_msg` для OOB read/write и `pipe_buffer` для работы со страницами. Эти три объекта покрывают большинство современных kernel-задач, и уверенное владение ими — признак опытного kernel-эксплуататора.

## Расширение окна гонки и стабильность

Многие kernel-баги — это гонки (race conditions), и их эксплуатация требует расширения временного окна между проверкой и использованием (TOCTOU). Инструменты: `userfaultfd` (блокировка страницы при обращении ядра к user-памяти) и FUSE (медленный файловый бэкенд, задерживающий операции). С их помощью вы заставляете ядро «зависнуть» в нужный момент, пока другой поток выполняет действие. Это ключевой навык для race-based kernel pwn. Без расширения окна эксплойт почти невозможно сделать надёжным, потому что окно составляет наносекунды. Комбинируйте `userfaultfd` с многопоточностью и привязкой к CPU, чтобы контролировать порядок событий.

## Диагностика и логирование

При отладке kernel-эксплойта логирование обязательно. Выводите адреса объектов, значения `cr4`, `kbase`, содержимое переиспользованных структур. В QEMU смотрите `dmesg` на предмет предупреждений ядра (`WARNING`, `BUG`, `general protection fault`). Каждое сообщение содержит регистры и адрес ошибки — это прямой указатель на проблему. Если ядро паникует, уменьшите шаг: возможно, вы перезаписали не то поле. Используйте `oops=panic panic=1` в отладке, чтобы система быстро перезапускалась, и не теряйте время на «зависшее» ядро.
