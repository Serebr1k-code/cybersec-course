Эксплуатация под qemu-user — это разработка эксплойтов для бинарей другой архитектуры (ARM, MIPS, RISC-V), запускаемых через `qemu-user`. QEMU-user эмулирует системные вызовы и CPU, что позволяет отлаживать кросс-архитектурные задачи на x86-хостe. Однако есть особенности: адреса загрузки, отсутствие ASLR по умолчанию, специфика syscall-эмуляции, а также различия в поведении (например, размер стека). В этом уроке — запуск, отладка, поиск offset и гаджетов под qemu-user, а также типичные ловушки.

## Запуск под qemu-user

```bash
qemu-aarch64 ./chall                    # запуск
qemu-aarch64 -g 1234 ./chall            # с gdb-сервером
qemu-aarch64 -L /usr/aarch64-linux-gnu ./chall   # с sysroot
qemu-mips -L ./lib ./chall              # big-endian MIPS
```

Флаг `-g <port>` открывает gdb-сервер; `-L <path>` задаёт sysroot (для динамических бинарей нужны библиотеки целевой архитектуры). Часто в CTF дают `run.sh` с готовой командой — изучайте его.

## Отладка

```bash
gdb-multiarch ./chall
(gdb) set architecture aarch64
(gdb) target remote :1234
(gdb) b *main
(gdb) c
(gdb) info registers
```

Используйте `gdb-multiarch` и правильную архитектуру. `pwndbg`/`gef` поддерживают кросс-архитектуры (с ограничениями). Смотрите регистры, стек и память. Для syscall'ов учитывайте ABI целевой архитектуры.

## Поиск offset и гаджетов

Offset до адреса возврата ищется через cyclic + gdb, как обычно. Гаджеты — через `ROPgadget`/`ropper` с учётом архитектуры. Помните: гаджеты должны быть в целевом бинаре/libc, а не в qemu. Проверяйте архитектуру в `ROPgadget` (`--arch arm64`, `--arch mips`, `--arch riscv64`).

```bash
ROPgadget --binary ./chall --arch arm64 --only "ldp|ret"
ROPgadget --binary ./chall --arch mips
```

## Особенности qemu-user

- **Адреса загрузки.** QEMU-user загружает бинарь по определённому адресу (часто `0x400000` для PIE — по базе); ASLR может быть отключён.
- **Стек.** Размер стека и его расположение могут отличаться от нативной системы.
- **Syscalls.** QEMU транслирует syscall'ы в хостовые; поведение близко, но есть нюансы (например, `brk`, `mmap`).
- **Библиотеки.** Для динамических бинарей нужен sysroot с целевыми libc.
- **Тайминги.** Эмуляция медленнее, гонки могут вести себя иначе.

## Разобранный пример: ret2win под qemu-aarch64

```python
from pwn import *
context.binary = elf = ELF('./chall')
context.arch = 'aarch64'
p = process(['qemu-aarch64', './chall'])
offset = cyclic_find(0x61616161)
p.sendline(flat(b'A'*offset, elf.symbols['win']))
p.interactive()
```

Используйте `process(['qemu-aarch64', './chall'])` в pwntools — это удобнее, чем ручной запуск.

## Отладка с pwntools

```python
p = gdb.debug(['qemu-aarch64', '-g', '1234', './chall'],
              gdbscript='set architecture aarch64\ntarget remote :1234\nc')
```

Или через `process` + `gdb.attach`. Полезно логировать адреса и проверять их соответствие ожиданиям.

## Частые ошибки

- **Не та архитектура в gdb.** Установите целевую.
- **Отсутствует sysroot.** Динамический бинарь не запустится без `-L`.
- **Неверный endian.** Для MIPS BE используйте `qemu-mips`, для LE — `qemu-mipsel`.
- **Гаджеты из хоста.** Ищите в целевом бинаре.
- **ASLR.** Может быть отключён, что упрощает, но не полагайтесь.

## Что дальше / решение

Дальше: `pwn-heap-qemu-debug`, `pwn-arm64-basics`, `pwn-mips`, `pwn-riscv`. Практический алгоритм: (1) определите архитектуру (`file`); (2) подготовьте sysroot; (3) запустите под qemu с `-g`; (4) подключитесь `gdb-multiarch`; (5) найдите offset и гаджеты; (6) соберите эксплойт. qemu-user — стандартный инструмент кросс-архитектурной эксплуатации; освоив его, вы сможете решать задачи для любой архитектуры.
## Полный разбор кросс-архитектурной задачи

Разберём сквозной пример. Дано: AArch64-бинарь (динамический) с переполнением стека, приложена ARM-сборка libc. Хост — x86-64. Шаги: (1) `file ./chall` — определяем архитектуру; (2) подготавливаем sysroot (копируем `/usr/aarch64-linux-gnu` или приложенные библиотеки); (3) запускаем `qemu-aarch64 -g 1234 -L ./sysroot ./chall`; (4) подключаемся `gdb-multiarch -q ./chall -ex 'set architecture aarch64' -ex 'target remote :1234'`; (5) находим offset до `x30` через cyclic; (6) находим гаджеты в бинаре и libc (`ROPgadget --arch arm64`); (7) строим цепочку с `ldr x0`/`ldp`-гаджетами; (8) проверяем локально под qemu, затем — на удалённом сервисе (если он есть). Логика идентична нативной, отличаются архитектура и syscall ABI.

## Работа с sysroot и библиотеками

Для динамических бинарей под qemu-user нужен sysroot с целевыми библиотеками (libc, ld). Если в задаче приложена libc, скопируйте её в sysroot: `cp libc.so.6 ./sysroot/lib/`. Также может потребоваться `ld-linux-aarch64.so.1`. Флаг `-L ./sysroot` указывает qemu искать библиотеки там. Если библиотек нет, бинарь не запустится — ищите их в дистрибутивных пакетах (`apt install libc6-arm64-cross`). Для статических бинарей sysroot не нужен. Проверяйте зависимости через `readelf -d ./chall | grep NEEDED`.

## Особенности отладки и таймингов

QEMU-user медленнее нативной системы, поэтому эксплойты с таймингами (гонки) могут вести себя иначе. Увеличивайте таймауты, используйте `recvuntil` вместо фиксированных задержек. ASLR под qemu-user часто отключён (или предсказуем), что упрощает отладку, но не полагайтесь на это для удалённого сервиса. Если задача использует `fork`, qemu может вести себя не так, как ядро — проверяйте. Для системных вызовов учитывайте трансляцию: qemu транслирует целевые syscall'ы в хостовые, и большинство работает, но есть исключения (`brk`, специфичные флаги `mmap`). Логируйте адреса и сверяйте с `info proc mappings`.

## Практические рекомендации

Начните с простых ret2win под qemu для разных архитектур, чтобы привыкнуть к инструментам. Затем переходите к ROP и heap. Держите под рукой `qemu-user`, `gdb-multiarch`, `pwndbg`, `ROPgadget` с нужным `--arch`. Изучайте writeup'ы кросс-архитектурных CTF. Помните, что qemu-user — лишь среда эмуляции; поведение реального устройства может отличаться (например, endianness, наличие ASLR, специфика libc). Всегда проверяйте на максимально близком к цели окружении.
## Работа с приложенной libc под qemu

Если задача даёт libc целевой архитектуры, положите её в sysroot и используйте для расчёта смещений. В pwntools: `libc = ELF('./libc.so.6', checksec=False)`, затем `libc.address = leak - libc.symbols['puts']`. Смещения ARM/MIPS/RISC-V libc отличаются от x86-64 — не переносите. Для поиска гаджетов используйте `ROPgadget --binary ./libc.so.6 --arch <arch>`. Если libc не дана, но есть утечка, идентифицируйте версию через `libc-database` (с ARM/MIPS-сборками). Проверяйте, что `ld` (динамический загрузчик) тоже в sysroot, иначе бинарь не запустится. Для статических бинарей libc вкомпилирована — используйте символы из самого бинаря (`nm`, `objdump`).

## Отладка многопоточных и форкающих бинарей под qemu

QEMU-user по-разному обрабатывает `fork`/`clone`. Для форкающих сервисов используйте `set follow-fork-mode child` в gdb. Для потоков — `info threads`. Помните, что qemu эмулирует `clone` и потоки, но тайминги отличаются. Если задача использует `fork` и общается по сокету, удобно запускать через `socat` и подключаться pwntools, а gdb цеплять к процессу. Всегда увеличивайте таймауты — эмуляция медленнее. Логируйте адреса и проверяйте их в `info proc mappings`.

## Практические рекомендации

Начните с ret2win для каждой архитектуры, чтобы освоить инструменты. Затем ROP с `ldp`/`lw`/`ld`-гаджетами. Держите под рукой шпаргалку по архитектурам (регистры, syscall ABI). Изучайте writeup'ы кросс-архитектурных CTF (DEF CON, PlaidCTF, Real World CTF). Помните, что qemu-user — приближение; реальное устройство может отличаться (ASLR, libc, endianness). Практикуйтесь на разных бинарях, чтобы привыкнуть к переключению контекста между архитектурами. Кросс-архитектурная эксплуатация — ценный навык для IoT и embedded.


## Специфика работы с сетевыми сервисами под qemu

Если задача — удалённый сервис на другой архитектуре, qemu-user не нужен (вы работаете с сетью), но для локальной отладки вы запускаете бинарь под qemu и подключаетесь pwntools. Для сервисов, форкающих на соединение, используйте `socat` с qemu: `socat TCP-LISTEN:1337,reuseaddr,fork EXEC:"qemu-aarch64 -L ./sysroot ./chall"`. Затем отлаживайте через gdb (attach к процессу). Помните, что тайминги под эмуляцией отличаются, а ASLR может быть отключён. Проверяйте карту памяти (`info proc mappings`) и логируйте адреса. Кросс-архитектурная эксплуатация удалённых сервисов — редкий, но ценный навык.


## Практика: сетап для нескольких архитектур

Для каждой архитектуры подготовьте sysroot: `apt install libc6-arm64-cross libc6-mips-cross` (или скопируйте библиотеки). Запускайте: `qemu-aarch64 -L /usr/aarch64-linux-gnu ./chall`, `qemu-mips -L /usr/mips-linux-gnu ./chall`. Отладка: `gdb-multiarch` с `set architecture <arch>`. Гаджеты: `ROPgadget --arch <arch>`. Практикуйтесь, переключаясь между архитектурами, чтобы привыкнуть. Ведите шпаргалку (регистры, syscall ABI, команды qemu). Кросс-архитектурная эксплуатация — ценный навык для IoT и embedded.
