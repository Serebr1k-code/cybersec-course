## Вопрос, с которого всё начинается

Ты получил бинарник под ARM (или MIPS, или RISC-V) и пытаешься его запустить на своём x86-ноутбуке. В ответ — ошибка. Как вообще работать с чужой архитектурой, если «железа» под неё нет? Ответ — **qemu-user**: программа, которая эмулирует чужой процессор и системные вызовы, позволяя запускать бинарник прямо на твоём хосте. В этом уроке научимся правильно его использовать и понимать, где эмуляция врёт.

## Наш пример

Возьмём ARM-бинарь `armvuln` (32-битная ARM-программа с переполнением). Пробуем запустить напрямую:

```
$ ./armvuln
bash: ./armvuln: cannot execute binary file: Exec format error
```

Ожидаемо: ядро Linux на x86 не умеет исполнять ARM-код. Смотрим формат:

```
$ file armvuln
armvuln: ELF 32-bit LSB executable, ARM, EABI5 version 1 (SYSV),
dynamically linked, interpreter /lib/ld-linux-armhf.so.3, not stripped
```

- **ARM, 32-bit, LSB** — little-endian ARM (ARMhf).
- **dynamically linked** — нужен ARM-вариант libc и динамический линкер `ld-linux-armhf.so.3`, которых на x86-хосте нет.

Значит, просто запустить мало — нужно дать эмулятору и **корень с ARM-библиотеками**.

## Шаг 1: запускаем через qemu-user

Устанавливаем эмулятор (`qemu-user`) и нужный корень (rootfs) с библиотеками. Для CTF чаще всего берут готовый rootfs под архитектуру задачи.

```
$ qemu-arm -L ./rootfs ./armvuln
Enter your name:
```

Параметр **`-L ./rootfs`** — самое важное: он говорит qemu, где искать ARM-линкер и libc. Без `-L` динамический бинарник не стартует («No such file or directory», хотя файл есть — типичная ошибка новичка).

Если бинарник статический, `-L` не нужен:

```
$ qemu-arm ./armvuln_static
```

## Шаг 2: смотрим системные вызовы

Qemu-user умеет трассировать syscall — это как `strace`, но для эмулируемого процесса:

```
$ qemu-arm -strace -L ./rootfs ./armvuln
...
write(1, "Enter your name: ", 17) = 17
read(0, "AAAA\n", 5) = 5
write(1, "Hello, AAAA\n", 12) = 12
exit(0) = ?
```

Это бесценно при разборе: видно, что программа читает ввод, как реагирует. Если программа «висит» или падает до эксплойта — `-strace` покажет, на каком syscall.

## Шаг 3: отладка под qemu

Для отладки qemu умеет открыть gdb-сервер:

```
$ qemu-arm -g 1234 -L ./rootfs ./armvuln
$ gdb-multiarch ./armvuln
(gdb) target remote :1234
(gdb) b *0x000104f0
(gdb) c
```

- **`-g 1234`** — qemu останавливает программу и ждёт подключения gdb на порту 1234.
- **`gdb-multiarch`** — gdb, знающий ARM/MIPS/RISC-V. Обычный `gdb` на x86 может не понимать чужую архитектуру.

Внутри отладчика работают привычные команды: `info registers` (покажет `r0`–`r12`, `sp`, `lr`, `pc`), `x/` (посмотреть память), `bt` (backtrace). Только регистры называются по-своему.

## Шаг 4: где эмуляция отличается от реального железа

Qemu-user очень удобен, но помни о различиях — иначе эксплойт «работает локально, не работает на устройстве»:

- **ASLR.** Под qemu адреса часто **фиксированы** (эмуляция упрощает раскладку). На реальном устройстве ASLR может быть включён — тогда понадобится утечка.
- **Раскладка памяти.** Стек, куча и mmap могут лежать по другим адресам, чем на «железе». Жёстко прошитые адреса придётся перепроверять.
- **Syscall-уровень.** Qemu транслирует гостевые syscall в хостовые. Иногда возвращаемые значения (например, `uname`, `auxv`) отличаются.
- **Устройства.** Нет реального железа (GPIO, кнопки, специфические ioctl) — связанные с ними части программы могут вести себя иначе.

Практический вывод: **отлаживай под qemu, но финальные адреса и поведение сверяй с реальной целью или её точной копией.**

## Шаг 5: как это выглядит в CTF

Типичная cross-arch задача:

1. Дают бинарник + (иногда) rootfs и libc.
2. Ты запускаешь `qemu-<arch> -L rootfs ./chall`, понимаешь поведение.
3. Отлаживаешь через `-g` + `gdb-multiarch`, находишь смещение до адреса возврата.
4. Собираешь эксплойт с учётом **endianness** и **регистров** этой архитектуры (см. уроки про MIPS/RISC-V/ARM64).
5. Если есть `libc.so.6` из задачи — вычисляешь смещения гаджетов в ней, а не в системной.

Важно: **всегда проверяй, какой именно libc даёт задача**. Эксплойт, собранный под системную libc, на задаче с другой версией не сработает.

## Шаг 6: альтернативы и полезные мелочи

Qemu-user — не единственный способ, и полезно знать окружение:

- **Готовые rootfs.** Для CTF и embedded часто используют rootfs из Buildroot/OpenWrt или собранные скриптом (`qemu-debootstrap`). Внутри — правильные `ld` и libc под задачу.
- **`binfmt_misc`.** Можно зарегистрировать qemu в ядре, и тогда бинарник чужой архитектуры запускается «прямо», без явного `qemu-arm` в командной строке. Удобно, но для отладки всё равно понадобится `-g`.
- **`-cpu`.** Если программа использует специфичные инструкции (например, ARMv7 NEON), можно указать модель CPU: `qemu-arm -cpu cortex-a15`.
- **`-E` и `-U`.** Позволяют задать переменные окружения и `ulimit` для гостевого процесса — иногда важно для воспроизведения поведения.
- **`-d`.** Дамп инструкций/регистров для глубокой отладки, если gdb не помогает.

Ещё один практический момент — **версия qemu**. Разные версии по-разному эмулируют syscall и раскладку памяти. Если эксплойт, найденный в интернете, не работает — проверь, на какой версии qemu он тестировался.

И наконец, важный навык: **уметь быстро поднять окружение**. Скрипт из нескольких строк (скачать rootfs, проверить `file`, запустить под qemu) экономит время на каждой задаче. Многие CTF-команды держат такой скрипт в репозитории. Заведи и ты: функция `run()` с нужным `qemu-<arch> -L rootfs`, которая сама выбирает эмулятор по `file`. На десятой задаче это окупается.

## Как это выглядит на реальной задаче

Представим конкретный сценарий, чтобы всё сложилось. Тебе выдали файл `chall` и папку `lib/`. Что делать по шагам:

1. **Определи архитектуру**: `file chall` → например, `ELF 32-bit LSB executable, ARM, EABI5`. Если бы это был MIPS, ты бы взял `qemu-mips`, для ARM64 — `qemu-aarch64`, для RISC-V — `qemu-riscv64`.
2. **Собери окружение**: положи libc и линкер в структуру `rootfs/lib/`, чтобы `-L rootfs` их нашёл. Часто в задаче уже приложен готовый rootfs.
3. **Запусти и пощупай**: `qemu-arm -L rootfs ./chall`, пойми, что программа делает (просит ввод, печатает, что-то сравнивает).
4. **Отладь**: `qemu-arm -g 1234 -L rootfs ./chall` + `gdb-multiarch`. Найди смещение до адреса возврата.
5. **Собери эксплойт** с учётом endianness и регистров архитектуры, используя libc **из задачи**, а не системную.
6. **Проверь на реальной цели**, если она есть: адреса под qemu могут отличаться.

Этот порядок одинаков для любой cross-arch задачи — меняются только имя эмулятора и имена регистров.

## Что мы теперь знаем

- **qemu-user** запускает бинарник чужой архитектуры на твоём хосте.
- **`-L ./rootfs`** обязателен для динамических бинарников — задаёт корень с библиотеками.
- **`-strace`** показывает syscall, **`-g PORT`** открывает отладку для `gdb-multiarch`.
- Под qemu память и ASLR часто **проще**, чем на реальном устройстве.
- Финальные адреса и версию libc надо **сверять** с настоящей целью.

Дальше — **отладка heap в qemu/gdb-multiarch**: как посмотреть chunk, tcache и glibc-структуры, когда процесс работает на ARM/MIPS под эмуляцией. ## Где пригодится

- **CTF Pwn:** почти каждая cross-arch задача запускается под qemu.
- **Embedded/IoT:** отладка прошивок без железа.
- **Vulnerability research:** быстрый анализ ARM/MIPS-бинарей.
- **Malware analysis:** запуск образцов под чужую архитектуру.
