## Зачем это нужно

Эксплуатация бинарных уязвимостей (pwn) всегда начинается с ответа на три вопроса: **как устроен файл**, **как процессор хранит данные** и **как функции вызывают друг друга**. Без этих знаний невозможно понять, куда именно «переполняется» буфер, что такое gadget и почему перезапись одного числа даёт исполнение кода.

В этом уроке мы разберём:
1. Формат исполняемого файла **ELF** и его ключевые секции.
2. Регистры общего назначения x86-64 и их роль.
3. Соглашение о вызовах **System V AMD64** (Linux).
4. Устройство **стека** и кадра функции.
5. Инструменты, которыми это всё смотрят: `file`, `readelf`, `objdump`, `checksec`, GDB/pwndbg.

Это корневой урок дерева pwn. Все остальные уроки опираются на материал здесь.

## Формат ELF

**ELF (Executable and Linkable Format)** — стандартный формат исполняемых файлов, объектных файлов и разделяемых библиотек в Linux. Структура:

```
+---------------------+
| ELF Header          |  тип, архитектура, точка входа (e_entry)
+---------------------+
| Program Headers     |  как загружать в память (сегменты)
+---------------------+
| .text               |  машинный код (r-x)
| .plt / .got.plt     |  отложенное связывание функций
| .rodata             |  строки-константы (r--)
| .data               |  инициализированные глобальные переменные (rw-)
| .bss                |  неинициализированные глобальные (rw-, нули)
+---------------------+
| Section Headers     |  метаданные секций (не нужны в рантайме)
+---------------------+
```

Ключевые понятия:

- **Точка входа (`e_entry`)** — адрес, с которого стартует процесс (обычно `_start`, который вызывает `__libc_start_main`).
- **Сегменты (Program Headers)** — единицы загрузки в память. Сегмент `LOAD` с флагом `R E` содержит код, `RW` — данные.
- **Секции (Section Headers)** — единицы для линковщика/отладчика. Могут быть вырезаны (strip), но сегменты остаются.

Типы ELF:
- `ET_EXEC` — исполняемый с фиксированными адресами (без PIE). Загружается по адресам вроде `0x400000`.
- `ET_DYN` — позиционно-независимый (PIE) или разделяемая библиотека. Загружается по случайному базовому адресу.
- `ET_REL` — перемещаемый объектный файл (`.o`), ещё не слинкованный.

## Инструменты: смотрим на файл

Начнём с базового:

```bash
file ./challenge
# ./challenge: ELF 64-bit LSB executable, x86-64, version 1 (SYSV), dynamically linked, interpreter /lib64/ld-linux-x86-64.so.2, for GNU/Linux 3.2.0, not stripped
```

Если написано `pie executable` — включён PIE; если `executable` — адреса фиксированы.

Заголовки и секции:

```bash
readelf -h ./challenge      # ELF header: тип, entry point, машинная архитектура
readelf -l ./challenge      # Program headers: сегменты, флаги, GNU_STACK (NX), GNU_RELRO
readelf -S ./challenge      # Section headers: .text, .got, .got.plt, .bss
readelf -s ./challenge      # Таблица символов: имена функций/переменных (если not stripped)
readelf -r ./challenge      # Релокации: какие адреса линкер заполнит в рантайме
readelf -d ./challenge      # Динамические зависимости: libc.so.6, NEEDED
```

Дизассемблируем код:

```bash
objdump -d -M intel ./challenge        # дизассемблер всего .text
objdump -d -M intel ./challenge | less # искать нужную функцию
objdump -t ./challenge                 # символы
```

Проверяем защиты одной командой:

```bash
checksec --file=./challenge
# Arch:     amd64-64-little
# RELRO:    Partial RELRO
# Stack:    No canary found
# NX:       NX enabled
# PIE:      No PIE (0x400000)
```

Если `checksec` не установлен — он есть в pwntools (`pwn checksec ./challenge`) или pwndbg (`checksec` внутри GDB).

## Регистры x86-64

64-битные регистры общего назначения и их младшие части:

| 64-bit | 32-bit | 16-bit | 8-bit | Назначение |
|--------|--------|--------|-------|-----------|
| RAX | EAX | AX | AL | аккумулятор, возврат функции, номер syscall |
| RBX | EBX | BX | BL | callee-saved, часто указатель |
| RCX | ECX | CX | CL | счётчик, 4-й аргумент |
| RDX | EDX | DX | DL | 3-й аргумент |
| RSI | ESI | SI | SIL | 2-й аргумент, source |
| RDI | EDI | DI | DIL | 1-й аргумент, destination |
| RBP | EBP | BP | BPL | base pointer — дно кадра стека |
| RSP | ESP | SP | SPL | stack pointer — вершина стека |
| R8–R15 | R8D–R15D | R8W–R15W | R8B–R15B | 5–6-й аргументы, callee-saved (кроме R8–R11) |

Специальные:

- **RIP** — instruction pointer, адрес следующей инструкции. Именно его перезаписывают при захвате управления.
- **RFLAGS** — флаги (ZF, SF, CF, OF…), влияют на условные переходы (`jz`, `jne`).
- **FS/GS** — сегментные регистры, `fs:0x28` хранит stack canary, `gs:0x0` — TLS.

## Соглашение о вызовах System V AMD64

Linux x86-64 передаёт целочисленные аргументы в регистрах в порядке:

```
1-й: RDI
2-й: RSI
3-й: RDX
4-й: RCX
5-й: R8
6-й: R9
7-й и далее: через стек (push справа налево)
```

Возврат — в **RAX**. Floating point — в XMM0–XMM7.

Важно про «сохранность» регистров:
- **Caller-saved** (можно свободно портить вызывающей стороне): RAX, RCX, RDX, RSI, RDI, R8–R11.
- **Callee-saved** (функция обязана восстановить): RBX, RBP, R12–R15, RSP.

**Выравнивание стека**: перед инструкцией `call` RSP должен быть выровнен на 16 байт. Если не выровнен — функции, использующие SSE-инструкции (`movaps`), падают с SIGSEGV. При построении ROP это классическая причина краха: «не добавил лишний `ret` для выравнивания».

Посмотрим, как компилятор это делает:

```bash
cat > hello.c <<'EOF'
#include <stdio.h>
int add(int a, int b) { return a + b; }
int main(void) {
    int r = add(2, 3);
    printf("%d\n", r);
    return 0;
}
EOF
gcc -O0 -fno-stack-protector -no-pie hello.c -o hello
objdump -d -M intel ./hello | sed -n '/<add>:/,/^$/p'
objdump -d -M intel ./hello | sed -n '/<main>:/,/^$/p'
```

В `<add>` вы увидите `mov eax, edi` и `add eax, esi` — аргументы пришли в EDI/ESI. В `<main>` — `mov esi, 3` / `mov edi, 2` перед `call add`.

## Стек и кадр функции

Стек растёт **вниз** (от старших адресов к младшим). Типичный пролог функции:

```asm
push rbp            ; сохраняем кадр вызывающего
mov  rbp, rsp       ; rbp = дно нашего кадра
sub  rsp, 0x20      ; место под локальные переменные
```

Эпилог:

```asm
leave               ; mov rsp, rbp ; pop rbp
ret                 ; pop rip
```

Кадр функции в момент, когда управление внутри функции:

```
высокие адреса
   +------------------+
   | аргументы 7+     |
   +------------------+
   | адрес возврата   |  <- [rbp+8], сюда прыгнет ret
   +------------------+
   | сохранённый rbp  |  <- [rbp]
   +------------------+  <- rbp
   | локальные        |  <- [rbp-4], [rbp-8], ...
   |   переменные     |
   +------------------+  <- rsp
низкие адреса
```

**Адрес возврата** — это то, что лежит прямо над `rbp`. Переполнив локальный буфер на стеке, можно дотянуться до него и подменить — это и есть основа **buffer overflow**. Именно поэтому этот урок — фундамент: следующая ступень дерева (`pwn-buffer-overflow`) перезаписывает именно `[rbp+8]`.

## Разбор примера: читаем бинарь вручную

```bash
checksec --file=./challenge
readelf -h ./challenge | grep -E 'Type|Entry'
objdump -d -M intel ./challenge | sed -n '/<main>:/,/ret/p'
```

Что искать глазами:
1. `Type: EXEC` → адреса фиксированы, gadget-адреса стабильны.
2. `Entry point: 0x401050` → область кода.
3. В `main`: `sub rsp, N` → размер локального буфера; `call gets`/`call read` без ограничения → потенциальный overflow.
4. `lea rdi, [rbp-0x30]` перед `call gets` → буфер на 0x30 (48) байт от rbp. Значит, до адреса возврата: 48 + 8 (сохранённый rbp) = 56 байт.

Эти вычисления (`offset до RIP`) — первый шаг любой pwn-задачи.

## Типичные ошибки

- **Путать секции и сегменты.** В рантайме загрузчик работает с сегментами; `.bss` и `.data` — внутри RW-сегмента.
- **Забывать про выравнивание стека.** В ROP отсутствие лишнего `ret` ломает `movaps` внутри libc → SIGSEGV. Симптом: «эксплойт падает где-то в libc».
- **Считать, что RBP всегда используется.** С `-O2` компилятор часто работает через RSP (omit frame pointer), и смещение до RIP считается от RSP.
- **Путать callee-saved и caller-saved.** После `call` RDI/RSI/RAX могут быть любыми — нельзя на них рассчитывать.
- **Забывать `-M intel`.** По умолчанию objdump выводит AT&T (операнды в обратном порядке) — легко запутаться.
- **Игнорировать `readelf -d`.** Если бинарь статический или линкует нестандартный libc, `ret2libc` требует именно того libc, который указан в `NEEDED`.


## Финальные рекомендации по ELF

Изучите структуру ELF: заголовок, секции (`.text`, `.data`, `.bss`, `.got`, `.plt`), сегменты, таблицы символов/релокаций. Умейте читать `readelf -S/-l/-s`, `objdump -d/-R`. Понимание PLT/GOT критично для ret2libc и GOT-перезаписи. Практикуйтесь на разных бинарях (PIE/non-PIE, static/dynamic). ELF — фундамент pwn; уверенное владение ускоряет все задачи.

## Где пригодится

- **CTF (Pwn/Reversing):** обязательный первый шаг любой задачи — определить тип бинаря, защиты и смещение до адреса возврата.
- **Bug bounty / pentest:** анализ нативных бинарников сервисов (демоны, сокеты, парсеры) на предмет memory corruption.
- **Реверс-инжиниринг:** понимание ELF и ABI нужно для анализа малвари и проприетарного ПО.
- **Работа:** разработка и аудит системного ПО на C/C++, разбор крэш-дампов, чтение ассемблера в отладчике.
