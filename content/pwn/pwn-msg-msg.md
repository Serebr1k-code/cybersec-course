## Вопрос, с которого всё начинается

Ты нашёл в ядре use-after-free. Освобождённый объект лежит в SLUB-кэше, и его
надо чем-то занять, чтобы получить контроль. Чем? Оказывается, в Linux есть
почти идеальный для этого объект — **`msg_msg`**. Он подконтролен пользователю,
у него предсказуемый размер и удобные указатели. Разберём его до винтика.

## Наш пример

System V IPC — старый механизм межпроцессного взаимодействия. Сообщения
отправляют через `msgsnd`, получают через `msgrcv`. Внутри ядро хранит каждое
сообщение как объект `msg_msg`:

```c
struct msg_msg {
    struct list_head m_list;   // 16 байт: prev/next в очереди
    long m_type;               // 8 байт: тип сообщения
    size_t m_ts;               // 8 байт: размер данных
    struct msg_msgseg *next;   // 8 байт: следующая часть (для больших)
    void *security;            // 8 байт: LSM-метка
    /* данные сообщения идут сразу за структурой */
};
```

Ключевое: **данные сообщения лежат сразу за структурой** в том же выделении.
Значит, размер `msg_msg` = `sizeof(struct msg_msg) + len(данных)`, и мы
контролируем этот размер через `msgsnd`.

## Шаг 1: как msg_msg попадает в нужный кэш

SLUB-аллокатор ядра выдаёт память из кэшей по размеру (`kmalloc-32`, `-64`,
`-96`, `-128`, `-192`, ...). Отправляя сообщения разной длины, мы попадаем в
разные кэши. Например, сообщение с 16 байтами данных создаёт объект ~64 байта →
кэш `kmalloc-64`. Это позволяет **прицельно спреить нужный кэш**: если UAF-
объект живёт в `kmalloc-64`, мы шлём сообщения, дающие объекты того же размера.

Формула: `size = sizeof(msg_msg) + data_len`, где `sizeof(msg_msg)` ≈ 48 байт
(зависит от ядра и включённых опций). Хочешь попасть в `kmalloc-64` — бери
`data_len` около 16.

## Шаг 2: спрей и перехват слота

Классический сценарий UAF на объекте X в `kmalloc-64`:

1. Триггерим баг: X освобождается, но ссылка на него остаётся.
2. Спреим `msg_msg` нужного размера — одно из сообщений займёт слот X.
3. Теперь «старая ссылка» указывает на наш `msg_msg`.
4. Через операцию над X ядро читает/пишет поля нашего `msg_msg`.

Так UAF превращается в контролируемый объект. Именно так работал
CVE-2021-22555 (netfilter): после спрея `msg_msg` через уязвимость переписывали
поле `m_ts` (размер данных), увеличивая его — и получали **out-of-bounds
чтение** соседних объектов кучи.

## Шаг 3: из msg_msg делают утечку

Почему `msg_msg` хорош для leak: `m_list.next` и `m_list.prev` — это **адреса
ядра** (указатели на соседние сообщения в очереди). Если прочитать их обратно
в userland (через OOB-чтение или через подменённый объект), мы получаем адрес
в куче ядра. А если удастся прочитать `security` или указатели, можно вычислить
базу.

Приём с `m_ts`: увеличив размер сообщения, `msgrcv` вернёт нам больше данных,
чем мы отправили — то есть содержимое соседних объектов, среди которых могут
быть указатели ядра. Это даёт **стабильную утечку** адресов кучи.

## Шаг 4: msg_msg как произвольное чтение

`msg_msg` для больших сообщений разбивается на сегменты: в `next` лежит
указатель на `msg_msgseg`, а данные продолжаются там. Если через баг
перезаписать `next` на произвольный адрес, `msgrcv` прочитает данные по этому
адресу и вернёт их нам — это **arbitrary read**. Комбинируя чтение и запись,
строят примитив и идут к root (например, перезаписывают `modprobe_path`).

## Шаг 5: минимальный пример на C

```c
#include <sys/msg.h>
#include <string.h>

struct msgbuf { long mtype; char mtext[16]; };

int main(void) {
    int qid = msgget(IPC_PRIVATE, 0666 | IPC_CREAT);
    struct msgbuf m;
    m.mtype = 1;
    memset(m.mtext, 'A', sizeof(m.mtext));
    msgsnd(qid, &m, sizeof(m.mtext), 0);   // создаёт msg_msg ~64 байта
    msgrcv(qid, &m, sizeof(m.mtext), 1, 0); // читает обратно
    return 0;
}
```

`msgsnd` создаёт объект в ядре, `msgrcv` его читает и освобождает. Спрей — это
цикл из сотен `msgsnd` без `msgrcv`.

## Шаг 6: почему msg_msg так популярен

- **Контроль размера** — точное попадание в нужный kmalloc-кэш.
- **Контроль содержимого** — данные идут за структурой.
- **Указатели ядра** — `m_list`, `next` дают утечки.
- **Простой API** — не нужны привилегии, только `msgget`.
- **Работает в контейнерах** — System V IPC обычно разрешён.

Из-за этого `msg_msg` встречается в десятках публичных kernel-эксплойтов:
CVE-2021-22555, CVE-2022-0185 и многих других.

## Шаг 7: ограничения и защита

- **CONFIG_CHECKPOINT_RESTORE / rlimits** могут ограничить число сообщений.
- **SLUB freelist randomization** усложняет попадание — спрей надо повторять.
- **CONFIG_SLAB_FREELIST_HARDENED** кодирует указатели freelist, но не мешает
  самому `msg_msg`.
- **KASAN** в отладочных ядрах ловит OOB раньше, чем ты его используешь.

Защита от такого класса — обновление ядра, ограничение IPC для
непривилегированных (`kernel.msgmax`, `kernel.msgmni`) и seccomp.

## Что мы теперь знаем

- `msg_msg` — объект System V IPC; данные лежат сразу за структурой.
- Размером сообщения мы выбираем kmalloc-кэш — это и есть спрей.
- После UAF `msg_msg` занимает освобождённый слот.
- `m_list`/`next` — адреса ядра, источник утечек.
- Подмена `m_ts`/`next` даёт OOB-read и arbitrary read.

## msgsnd и msgrcv: полный API

Работа с `msg_msg` строится на четырёх вызовах System V IPC:

```c
int msgget(key_t key, int flags);                 // создать/получить очередь
int msgsnd(int qid, const void *msgp, size_t sz, int flags);
ssize_t msgrcv(int qid, void *msgp, size_t sz, long type, int flags);
int msgctl(int qid, int cmd, struct msqid_ds *buf); // управление (IPC_RMID)
```

В `msgp` первое поле — `long mtype` (тип), дальше — данные. Ядро копирует
структуру `msg_msg` плюс данные одним блоком, поэтому размер объекта —
`sizeof(struct msg_msg) + sz`. Флаг `MSG_COPY` у `msgrcv` позволяет **прочитать
сообщение, не удаляя его** — это важно для повторных утечек: мы можем несколько
раз читать один и тот же объект.

Есть лимиты: `/proc/sys/kernel/msgmax` (макс. размер сообщения),
`/proc/sys/kernel/msgmnb` (макс. байт в очереди), `/proc/sys/kernel/msgmni`
(число очередей). Для спрея сотен сообщений удобно создать **несколько очередей**,
чтобы не упереться в `msgmnb`.

## msg_msgseg и большие сообщения

Если сообщение больше, чем влезает в один kmalloc-объект (обычно ~4 КБ), ядро
разбивает его на сегменты: первая часть в `msg_msg`, остальные — в цепочке
`msg_msgseg`, связанных через `next`:

```c
struct msg_msgseg {
    struct msg_msgseg *next;   // следующий сегмент
    /* данные идут следом */
};
```

Для эксплуатации это и плюс, и минус. Плюс: подменив `next` на произвольный
адрес, `msgrcv` прочитает данные оттуда — **arbitrary read**. Минус: сегменты
живут в разных kmalloc-кэшах, и надо аккуратно подобрать размер.

## Разбор CVE-2021-22555

Показательный пример: уязвимость в netfilter (`xt_compat_target_from_user`)
давала out-of-bounds запись нулей в кучу. Эксплуатация:

1. Спрей `msg_msg` так, чтобы сразу за одним сообщением оказалось другое.
2. OOB-запись обнуляет поле `m_ts` (или указатель) соседнего сообщения.
3. Увеличенный `m_ts` → `msgrcv` возвращает данные **за** сообщением —
   OOB-чтение, из которого достают указатели ядра.
4. Из утечки вычисляют базу, затем через подмену `next`/`m_ts` получают
   произвольное чтение и запись.
5. Финишер — перезапись `modprobe_path` или `cred`.

Здесь видно, зачем нужны **все** части: спрей, утечка, примитив записи и
финишер. `msg_msg` участвует почти в каждом шаге.

## Что смотреть в коде при аудите

Если ты ищешь похожие баги, обрати внимание на:

- места, где `copy_from_user`/`copy_to_user` работают с размером, зависящим от
  пользователя;
- структуры, которые не обнуляются при выделении (`kmalloc` без `__GFP_ZERO`);
- разбор параметров из `setsockopt`, `ioctl`, netlink;
- поля-размеры (`m_ts`, `len`, `count`), которые можно «растянуть».

Каждое такое место — потенциальный источник OOB, который затем превращается в
утечку через `msg_msg`.
