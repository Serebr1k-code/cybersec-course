Unsafe unlink — это техника эксплуатации старой уязвимости в glibc (`unlink` без проверок), позволяющая записать произвольное значение по произвольному адресу. Когда чанк извлекается из двусвязного списка бина, вызывается `unlink`, который выполняет:

```c
fd = p->fd;
bk = p->bk;
fd->bk = bk;      // запись
bk->fd = fd;      // запись
```

Если `p->fd` и `p->bk` контролируются, это даёт две записи: по адресу `p->fd + 0x18` пишется `p->bk`, и по адресу `p->bk + 0x10` пишется `p->fd`. Исторически это давало arbitrary write, но современные glibc (с 2.3.x) добавили проверку `fd->bk == p && bk->fd == p`, что требует корректного поддельного окружения. В этом уроке — механика unsafe unlink, обход проверки, практический эксплойт и родственные приёмы (overlapping chunks).

## Классический unlink и его проверка

Современная реализация `unlink_chunk`:

```c
static void unlink_chunk (mstate av, mchunkptr p) {
    if (chunksize (p) != chunksize (p->fd->bk) ||
        chunksize (p) != chunksize (p->bk->fd))
        malloc_printerr ("corrupted double-linked list");
    ...
    p->fd->bk = p->bk;
    p->bk->fd = p->fd;
}
```

Проверка требует, чтобы `p->fd->bk == p` и `p->bk->fd == p`. Это значит, что вы должны сконструировать **два** фиктивных чанка: `fake_fd` (по адресу `p->fd`) с полем `bk`, равным `p`, и `fake_bk` (по адресу `p->bk`) с полем `fd`, равным `p`. Тогда при `unlink(p)` произойдут записи:

- по адресу `p->fd + 0x18` (то есть `fake_fd->bk`) пишется `p->bk`;
- по адресу `p->bk + 0x10` (то есть `fake_bk->fd`) пишется `p->fd`.

Выбрав `p->fd` и `p->bk` как указатели на нужные места, вы получаете запись.

## Обход проверки: раскладка

Чтобы обход сработал, обычно делают так: переполняют чанк A, чтобы подделать метаданные **следующего** чанка B (перезаписывают `B->prev_size` и снимают `PREV_INUSE`), а также размещают фиктивный чанк `fake` в самом A. При `free(B)` glibc попытается консолидировать B с «предыдущим» (нашим fake), вызовет `unlink(fake)`. Подделав `fake->fd` и `fake->bk`, вы получаете запись. Классическая цель — `__free_hook`/`__malloc_hook` (записать `system`) или GOT (записать `system`).

```python
from pwn import *
context.binary = elf = ELF('./chall')
p = process('./chall')

# переполнение чанка A:
# fake->fd = target - 0x18, fake->bk = value
target = elf.got['free']
value  = elf.plt['system']   # или libc.sym['system']
payload  = p64(0)            # prev_size
payload += p64(0x20)         # size fake
payload += p64(target - 0x18)  # fd
payload += p64(value)          # bk
payload += b'A' * (0x100 - len(payload))
payload += p64(0x20) + p64(0x20)   # fake prev_size/size для B
p.sendline(payload)
# free(B) -> unlink(fake) -> запись value по target
```

Здесь `target - 0x18` выбран так, чтобы запись `fd->bk = bk` попала ровно в `target` (потому что `fd->bk` пишется по `fd + 0x18`).

## Overlapping chunks

Unsafe unlink часто комбинируют с перекрытием чанков. Идея: после успешного unlink вы получаете указатель, который можно использовать для изменения размера соседнего чанка. Увеличив размер, вы заставляете следующую аллокацию вернуть чанк, перекрывающий уже используемый, — это даёт UAF/arbitrary write. Перекрытие — мощный примитив, лежащий в основе многих heap-эксплойтов.

## Проверка в gdb

```bash
gdb ./chall
(gdb) b *free
(gdb) r
(gdb) vis_heap_chunks 20
(gdb) p *(struct malloc_chunk*)<addr_fake>
(gdb) x/6gx <addr_fake>
```

Убедитесь, что `fake->fd->bk == fake` и `fake->bk->fd == fake` перед `free`, иначе сработает `malloc_printerr("corrupted double-linked list")`.

## Частые ошибки

- **Не выполнен обход проверки.** Без корректных `fd->bk`/`bk->fd` — abort.
- **Неверный `target - 0x18`.** Ошибка на 8 байт — запись мимо цели.
- **PREV_INUSE не снят.** Консолидация не сработает.
- **Неверный размер fake.** Должен совпадать с ожидаемым.
- **Версия glibc.** Современные проверки строже; техника усложняется.

## Сквозной разбор unsafe unlink на glibc 2.23

Разберём классическую задачу: glibc 2.23, переполнение в чанк A, следующий чанк B, есть возможность записать произвольные данные. Цель — перезаписать `__free_hook` на `system`. Шаги: (1) заполняем чанк A поддельными метаданными фиктивного чанка `fake`; (2) подделываем `B->prev_size` и снимаем `PREV_INUSE` у `B->size`; (3) при `free(B)` glibc видит, что предыдущий чанк свободен, и вызывает `unlink(fake)`; (4) если `fake->fd` и `fake->bk` подделаны с прохождением проверки, происходит запись по цели. Для `__free_hook`: `fake->fd = __free_hook - 0x18`, `fake->bk = system`. Тогда `fd->bk = bk` запишет `system` по адресу `__free_hook - 0x18 + 0x18 = __free_hook`. Далее вызываем `free("/bin/sh")` и получаем shell. Каждый шаг проверяем в gdb: `p *(struct malloc_chunk*)fake`, `x/6gx fake`, `b *free`.

## Обход проверки fd->bk == p и bk->fd == p

Современный `unlink` требует `fd->bk == p` и `bk->fd == p`. Чтобы обойти, нужно, чтобы по адресам `fake->fd + 0x18` и `fake->bk + 0x10` лежали указатели, равные `fake`. На практике это делают так: выбирают `fake->fd` и `fake->bk` так, чтобы эти адреса попадали в записываемую область, и заранее кладут туда `fake`. Часто `fake->fd` указывают на контролируемый чанк C (где `C+0x18 = fake`), а `fake->bk` — на другой контролируемый чанк D (где `D+0x10 = fake`). Тогда проверка проходит, и записи происходят по адресам C+0x18 и D+0x10, которые вы контролируете. Комбинируя цели, добиваются нужной записи.

## Связь с перекрытием чанков

После успешного unlink вы получаете указатель, позволяющий изменять метаданные соседей. Это открывает перекрытие (overlapping chunks): увеличив `size` чанка, вы заставляете следующую `malloc` вернуть область, пересекающуюся с уже используемой. Перекрытие — универсальный примитив: имея два указателя на одну память, вы можете читать чужой чанк (утечка) и писать в него (подмена указателей). Именно перекрытие превращает unlink в основу для сложных цепочек (FSOP, tcache poisoning). Поэтому unsafe unlink часто изучают вместе с overlapping chunks.

## Чек-лист применения

1. Найдите переполнение, дотягивающееся до следующего чанка.
2. Разместите фиктивный чанк `fake` в контролируемой памяти.
3. Подделывайте `fake->fd`/`fake->bk` так, чтобы прошла проверка unlink.
4. Снимите `PREV_INUSE` у следующего чанка и запишите `prev_size`.
5. Освободите следующий чанк — сработает `unlink(fake)`.
6. Получите запись по цели (GOT/хук).
7. Триггерните вызов (следующий `free`/`printf`).
8. При необходимости используйте перекрытие для сложных цепочек.

## Итог

Unsafe unlink — историческая техника, которая объясняет появление проверок `unlink` и устройство консолидации. На современных glibc она требует аккуратного оформления фиктивных чанков, но базовый принцип (две записи из `fd`/`bk`) остаётся. Освоив её, вы сможете разбирать более новые атаки (House of Einherjar, tcache poisoning), которые используют те же метаданные.

## Замечание о выборе цели записи

Выбор цели зависит от версии glibc. На старых (до 2.34) удобны `__free_hook`/`__malloc_hook`: записав туда `system`, вы получаете shell при следующем `free`/`malloc`. На новых (2.34+) хуков нет — используйте GOT (при Partial RELRO), `.fini_array`, `__exit_funcs` или `_IO_list_all`. Формула записи одна: `target = fd + 0x18` (или `bk + 0x10`), поэтому выбирайте `fd`/`bk` так, чтобы попасть в цель с учётом смещений. Всегда проверяйте смещения в gdb и не полагайтесь на «примерные» значения: ошибка на 8 байт приводит к записи мимо и падению.

## Замечание о современных glibc

На glibc 2.29+ проверки `unlink` ужесточены, а на 2.32+ safe-linking маскирует указатели в fastbin/tcache. Поэтому «чистый» unsafe unlink в исходном виде работает лишь на старых версиях. Однако концепция остаётся полезной: та же операция `fd->bk = bk` лежит в основе House of Einherjar, tcache stashing и largebin attack. Изучив unsafe unlink, вы поймёте, почему появились эти митигации и как их обходят в современных эксплойтах.

Практический совет: держите под рукой небольшой скрипт, который выводит карту кучи (`vis_heap_chunks`, `bins`) на каждом шаге, — это ускоряет отладку и помогает быстро находить расхождения между ожидаемой и реальной раскладкой.

И наконец, помните, что техника не существует в вакууме: комбинируйте её с grooming и утечками, чтобы получить устойчивый примитив, пригодный для повторного применения в рамках одной сессии.
