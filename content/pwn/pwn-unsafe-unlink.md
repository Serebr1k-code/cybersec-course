## Вопрос, с которого всё начинается

В прошлом уроке один байт сдвинул границы чанка. Теперь посмотрим, что происходит, когда испорченный чанк **выбывает из списка свободных**. В больших бинах чанки связаны двусвязным списком, и операция удаления из него — **unlink** — исторически давала одну из самых мощных примитивов: запись по произвольному адресу.

Разберём классическую атаку и защиту, которую glibc добавила против неё.

## Наш пример

Соберём стенд: освободим большой чанк в `unsorted bin`, испортим его указатели `fd`/`bk` и заставим соседний чанк освободиться, вызвав unlink:

```
corrupted a.fd = a.bk = 0x...  (значение по этому адресу != a)
free(b) -> backward consolidation -> unlink(a) -> проверка...
corrupted double-linked list
```

Программа аварийно завершилась с сообщением **`corrupted double-linked list`**. Это и есть защита glibc, о которой пойдёт речь: она заметила, что `fd`/`bk` указывают не туда, куда должны.

## Шаг 1. Двусвязный список и unlink

Чанки в `unsorted bin` (и других больших бинах) связаны двумя указателями:

- `fd` (forward) — следующий чанк;
- `bk` (backward) — предыдущий.

Когда чанк нужно убрать из списка (при слиянии или выдаче), glibc «выцепляет» его:

```c
next = p->fd;
prev = p->bk;
next->bk = prev;   /* следующий теперь смотрит назад через p */
prev->fd = next;   /* предыдущий теперь смотрит вперёд через p */
```

Две записи — `next->bk` и `prev->fd` — идут **по адресам, которые мы можем контролировать**, если контролируем `p->fd` и `p->bk`. В этом и суть атаки.

## Шаг 2. Классический unsafe unlink

Идея: заставить `next->bk = prev` записать нужное значение по нужному адресу. Классическая цель — глобальный массив указателей, который ведёт сама программа (например, `chunks[i]`). Подбирая `fd` и `bk`, добиваются, чтобы после unlink в этом массиве оказался адрес нашего чанка — то есть мы получаем указатель на подконтрольную память там, где программа ожидает безопасный объект.

Схема (до защиты):

```
p->fd = target - 0x18;
p->bk = target - 0x10;
unlink(p):
    (target-0x18)->bk = target-0x10   =>  *(target-8) = target-0x10
    (target-0x10)->fd = target-0x18   =>  *(target)   = target-0x18
```

Запись по `target` даёт нам контроль над тем, что там лежит.

## Шаг 3. Safe-unlink: проверка

Начиная с glibc 2.3.4 (и во всех современных) перед unlink добавлена проверка:

```c
if (fd->bk != p || bk->fd != p)
    malloc_printerr ("corrupted double-linked list");
```

Смысл: указатель `fd` должен вести на чанк, у которого `bk` равен нашему `p`, и наоборот. Просто подставить произвольные `fd`/`bk` нельзя — цепочка должна быть **согласованной**. Именно эту проверку и сработало наше демо.

## Шаг 4. Как обходят safe-unlink

Проверку обходят, если в памяти уже существует указатель на `p`. Тогда `fd` и `bk` строят так, чтобы проверка прошла, а запись всё равно попала куда нужно.

Классический трюк: пусть есть глобальная переменная `ptr`, которая указывает на наш чанк `p` (программа сама её хранит). Тогда:

```
fd = &ptr - 0x18;    /* fd->bk == *(fd+0x18) == *(&ptr) == p  ✓ */
bk = &ptr - 0x10;    /* bk->fd == *(bk+0x10) == *(&ptr) == p  ✓ */
```

Проверка проходит, а unlink записывает `fd` и `bk` в область вокруг `&ptr` — то есть **перезаписывает сам указатель** `ptr`. Теперь `ptr` указывает туда, куда мы хотим, и мы получаем произвольную запись через программу, которая доверяет `ptr`.

## Шаг 5. Откуда берётся off-by-one

Unsafe unlink почти всегда идёт в связке с off-by-one из прошлого урока: чтобы испортить метаданные соседнего чанка (`prev_size`, флаг `prev_inuse`), нужен переполнение на байт или UAF. Без способа записать `fd`/`bk` атака невозможна.

## Шаг 6. Полный прогон

Соберём цепочку:

1. Выделяем `A`, `B`, `C`; держим `A` в глобальном массиве `chunks[0] = A`.
2. Через off-by-one сбрасываем `prev_inuse` у `B` и подделываем `prev_size`, чтобы `B` считал `A` свободным.
3. Освобождаем `B` — glibc пытается консолидировать `A`, то есть вызвать `unlink(A)`.
4. Устанавливаем `A.fd = &chunks[0] - 0x18`, `A.bk = &chunks[0] - 0x10`, чтобы проверка прошла.
5. Unlink перезаписывает `chunks[0]` на `A` (или на выбранное значение).
6. Дальше правим `chunks[0]` и получаем запись по произвольному адресу.

## Шаг 7. Актуальность сегодня

Unsafe unlink — «дедушка» heap-эксплуатации. На modern glibc его используют реже, потому что есть более прямые приёмы (tcache poisoning, overlap), но:

- в CTF он встречается регулярно;
- понимание unlink помогает понять консолидацию и бин-атаки;
- связка «off-by-one + unlink» — классика, которую нужно уметь собрать.

Кроме того, unlink лежит в основе более новых техник: House of Einherjar, House of Lore, tcache stashing — все они так или иначе используют выбывание чанка из списка. Поэтому разобраться в safe-unlink стоит не ради старой атаки, а чтобы понимать современные.

## Шаг 8. Почему проверка называется safe-unlink

Название говорит само за себя: это защита, добавленная именно против классического unlink-эксплойта. До неё достаточно было записать в `fd`/`bk` пару произвольных адресов — и unlink давал две записи куда угодно. После неё цепочка должна быть **самосогласованной**: `fd` обязан указывать на структуру, которая «знает» про наш чанк `p`. Атакующему пришлось искать в памяти настоящую ссылку на `p` — а это уже дополнительное требование к уязвимости.

## Если не сработало

Первое: сработала проверка safe-unlink. Ты увидишь `corrupted double-linked list`. Нужен реальный указатель на `p` в памяти, чтобы построить согласованные `fd`/`bk`.

Второе: чанк ушёл в tcache. Размеры ≤ `0x410` освобождаются в tcache, где нет `fd`/`bk` unlink-семантики. Бери размер больше `0x410`.

Третье: не сброшен `prev_inuse`. Backward consolidation не запустится, и unlink не вызовется.

Четвёртое: `prev_size` неверен. glibc сверит его с реальным размером предыдущего чанка — при несовпадении `corrupted size vs. prev_size`.

Пятое: `fd`/`bk` не выровнены или недоступны. Обращение к невалидному адресу уронит программу до проверки.

## Что мы теперь знаем

- `unsorted`/большие бины — двусвязные списки (`fd`/`bk`); удаление из них — `unlink`.
- Unlink выполняет `next->bk = prev` и `prev->fd = next` — две записи по контролируемым адресам.
- Safe-unlink проверяет `fd->bk == p && bk->fd == p`.
- Обход — найти реальный указатель на `p` и построить согласованные `fd`/`bk`.
- Unsafe unlink обычно комбинируется с off-by-one, который портит метаданные соседа.
