## Вопрос, с которого всё начинается

Помимо документированных API, ядро Windows предоставляет **недокументированные**
механизмы, которые исследователи используют как строительные блоки для
эксплойтов. Один из них — **I/O ring** (`IoRing`), аналог `io_uring` в Linux.
Разберём, что это и зачем он нужен эксплойт-разработчику.

## Наш пример

Параметры создаваемого I/O ring:

```
$ cat ioring.txt
IoRingVersion       = 0x00000001
SubmissionQueueSize = 0x10000   (65536 bytes)
SubmissionEntrySize = 0x10      (16 bytes)
CompletionQueueSize = 0x2000
CompletionEntrySize = 0x10
```

Число записей: `0x10000 / 0x10 = 4096`. Разберём, что это за структура.

## Шаг 1: что такое I/O ring

**I/O ring** — механизм асинхронного ввода-вывода в Windows, во многом похожий
на Linux `io_uring`. Пользователь и ядро разделяют **две очереди** в общей
памяти:

- **Submission queue** — куда userland кладёт запросы (SQE);
- **Completion queue** — куда ядро кладёт результаты (CQE).

Ядро читает SQE и выполняет операцию, не переключаясь на каждый запрос.

## Шаг 2: зачем это эксплойту

Ключевое свойство — **общая память** и **регистрация объектов**. Приложение
может **зарегистрировать** в ring:

- **файлы** (handle'ы);
- **буферы** (адреса памяти, в т.ч. ядерные структуры для операций);
- **пользовательские страницы**, отображённые в ядро.

Исследователи используют это для:

- **data-only примитивов**: ring даёт доступ к структурам ядра;
- **обхода проверок**: недокументированные поля обходят митигации;
- **надёжных записей**: операции ring работают с известными смещениями.

## Шаг 3: структура ring

Ring описывается структурами:

- **`IORING`** — главная структура с указателями на очереди;
- **SQE** (submission queue entry) — операция: код, дескриптор, буфер, смещение;
- **CQE** (completion) — результат: статус, информация.

Пользователь создаёт ring через `NtCreateIoRing`, отображает очереди в свою
память и управляет ими напрямую. Именно «прямое управление» и делает ring
интересным: часть данных доступна и userland, и ядру.

## Шаг 4: недокументированные примитивы

I/O ring — не единственный недокументированный механизм. Среди других:

- **`NtQuerySystemInformation`** с недокументированными классами — утечки.
- **`NtSetSystemInformation`** — настройка системных структур.
- **`SystemExtendedHandleInformation`** — обход handle-таблиц.
- **Worker factory / callback-объекты** — планирование кода.

Их объединяет одно: они дают **примитивы** (чтение/запись/планирование) без
обычных API, и потому их проверки слабее.

## Шаг 5: связь с митигациями

Недокументированные примитивы ценны тем, что:

- **data-only**: меняют данные, обходя CFG/CET/HVCI;
- **не проходят через проверяемые API**: меньше проверок прав;
- **дают доступ к структурам ядра**: где живут токены, callback'и, флаги.

Поэтому в современном Windows-эксплойте часто комбинируют **баг драйвера**
(примитив) + **недокументированный механизм** (цель/усиление).

## Шаг 6: осторожность

- **PatchGuard** может ловить правки критичных структур → BSOD.
- **Недокументированное = версионное**: смещения и поведение меняются между
  сборками.
- **Нестабильность**: ошибка в работе с ring роняет процесс (или систему).
- **Для kernelCTF/BB** важна **безопасность**: не ронять хост.

## Шаг 7: как это встроить в исследование

1. **Определи примитив** бага (что даёт запись/чтение).
2. **Выбери цель**: токен, флаг, структура ядра.
3. **Используй ring/недокументированный API** для доступа к цели.
4. **Проверь стабильность** на разных сборках.
5. **Собери** повышение привилегий или обход митигации.

## Пример работы с ring

Создание и использование ring (схематично):

```c
// создать ring
NtCreateIoRing(&hRing, IORING_VERSION_1, submitSize, completeSize, &ringInfo);
// отобразить очереди в своё адресное пространство
// положить SQE: код операции, дескриптор, буфер, смещение
// сообщить ядру о новом SQE (обновить счётчик)
// забрать CQE из completion queue
```

Ядро читает SQE из **общей** памяти и выполняет операцию. Поскольку очереди —
в общей памяти, часть структур видна и userland, и ядру. Исследователи
используют это для доступа к структурам ядра и как data-only примитив.

## Другие недокументированные механизмы

Помимо I/O ring, эксплойт-разработчики используют:

- **`NtQuerySystemInformation`** с нестандартными классами — утечки структуры
  системы, handle-таблиц.
- **`NtSetSystemInformation`** — настройка системных структур (в т.ч. тех, что
  влияют на поведение ядра).
- **Worker factories** — планирование кода через объекты ядра.
- **Callback-объекты** — регистрация обработчиков, которые ядро вызывает.
- **`SystemExtendedHandleInformation`** — обход handle-таблиц, поиск объектов.

Общее у них — **слабые проверки** и доступ к внутренностям ядра.

## Частые ошибки

- **Версионность.** Недокументированные структуры меняются между сборками —
  смещения и поля «уезжают».
- **Нестабильность.** Ошибка в работе с ring роняет процесс/систему.
- **PatchGuard.** Правка критичных структур → BSOD.
- **Ложная цель.** Не всякий примитив ведёт к повышению привилегий.
- **Игнорирование HVCI.** Код в ядре не исполнится; нужен data-only.

## Как встроить в исследование

1. **Определи примитив** бага (что даёт чтение/запись).
2. **Выбери цель** (токен, флаг, структура ядра).
3. **Задействуй** ring или недокументированный API для доступа.
4. **Проверь стабильность** на нескольких сборках.
5. **Собери** повышение привилегий или обход митигации.
6. **Задокументируй** зависимость от версии.

## Код работы с ring подробнее

Упрощённый цикл работы с I/O ring:

```c
IORING_INFO info = {0};
NtCreateIoRing(&hRing, IORING_VERSION_1, sqSize, cqSize, &info);
// отображаем SQ и CQ в адресное пространство процесса
IORING_SQE* sqe = (IORING_SQE*)info.SubmissionQueue;
sqe->opcode = IORING_OP_READ;
sqe->file   = hFile;
sqe->buffer = buf;
sqe->length = len;
// сообщаем ядру: увеличиваем счётчик отправленных SQE
NtSubmitIoRing(hRing, 1, 0, NULL);
// ждём CQE
IORING_CQE* cqe = (IORING_CQE*)info.CompletionQueue;
```

Ключевое: **очереди лежат в общей памяти**, поэтому часть структур доступна
обеим сторонам. Это и делает ring интересным для доступа к внутренностям ядра.

## Риски и стабильность

- **Версионность**: layout ring меняется между сборками Windows.
- **Ошибка в указателях**: неверный буфер роняет процесс (или систему).
- **PatchGuard**: правка защищённых структур → BSOD.
- **HVCI**: код в ядре не исполнится; ring используют как data-only.

Поэтому работа с ring требует точного знания формата и аккуратности.

## Зачем ring нужен ядру

I/O ring снижает **накладные расходы** на системные вызовы: вместо перехода
user↔kernel на каждую операцию приложение пишет запросы в общую очередь, а ядро
обрабатывает их пакетно. Для высоконагруженных серверов это ускорение.

Но «общая память» — это и **поверхность атаки**. Часть структур видна обеим
сторонам, и неверная синхронизация/проверка открывает примитивы. Именно поэтому
ring используют в эксплойтах: он даёт доступ к внутренностям ядра через
полулегальный интерфейс.

## Сравнение с io_uring

| Аспект | Windows IoRing | Linux io_uring |
|---|---|---|
| Очереди | SQ/CQ в общей памяти | SQ/CQ + mmap |
| Регистрация | файлы, буферы | файлы, буферы, флаги |
| Статус | недокументирован | частично документирован |
| Эксплуатация | data-only, доступ к структурам | частые CVE (гонки/UAF) |

Оба механизма ценны для исследователя: Linux io_uring дал серию CVE, Windows
IoRing — недокументированные примитивы. Понимание одного помогает в другом.

## Вывод

Недокументированные механизмы вроде I/O ring — «серая зона» между API и
внутренностями ядра. Они дают сильные примитивы, но требуют аккуратности:
версионность, стабильность и митигации (HVCI/PatchGuard) диктуют, как их
применять.

## Частые вопросы

**IoRing — это уязвимость?** Нет, это **механизм**. Уязвимости могут быть в его
реализации или в драйверах, использующих ring. Для эксплойта ring ценен как
источник примитивов и доступа к структурам.

**Почему недокументированные API вообще существуют?** Их используют внутренние
компоненты Windows; они не входят в публичный контракт и могут меняться.
Для эксплойт-разработчика это и хорошо (слабые проверки), и плохо
(версионность).

**Как выбрать между ring и обычным API?** Обычный API проще и стабильнее, но
проверяется строже. Ring/недокументированные API дают больше свободы ценой
нестабильности. Выбор — по задаче.

**Что важнее для отчётности — примитив или стабильность?** Стабильность. В
kernelCTF и bug bounty нестабильный эксплойт, роняющий хост, не засчитывают.

## Сводка

I/O ring — недокументированный механизм асинхронного ввода-вывода, похожий на
Linux `io_uring`. Для эксплойт-разработчика он ценен тремя свойствами: общими
очередями в памяти, возможностью регистрировать файлы и буферы, и слабыми
проверками по сравнению с публичными API.

Использовать его стоит аккуратно: структуры версионны, ошибка роняет систему, а
HVCI и PatchGuard ограничивают прямые правки. Правильная стратегия — применять
ring как **data-only** примитив доступа к внутренностям ядра, а не как способ
исполнить свой код.

Вместе с уязвимым драйвером (или BYOVD) ring замыкает цепочку: баг даёт запись,
а недокументированный механизм помогает добраться до нужной структуры ядра.

## Что мы теперь знаем

- I/O ring — аналог io_uring, с общими очередями user/kernel.
- Ring позволяет регистрировать файлы и буферы.
- Недокументированные API дают слабопроверяемые примитивы.
- Они удобны для data-only атак и обхода митигаций.
- Осторожность: PatchGuard, версионность, стабильность.
