## Вопрос, с которого всё начинается

Ты освободил объект через UAF. Но между `free` и повторным использованием есть
окно: если никто не займёт освобождённый слот, ядро отдаст его чему-то
случайному, и эксплойт упадёт. Как **гарантированно** положить в этот слот свой
объект? Это и есть heap spray.

## Наш пример

Возьмём типичную задачу: UAF-объект размером ~64 байта в `kmalloc-64`. Нам нужен
объект того же размера, содержимое которого мы контролируем. Кандидаты:

- **`msg_msg`** — данные задаём через `msgsnd`.
- **`sk_buff`** (сетевые буферы) — данные задаём, отправляя пакеты.
- **`user_key_payload`** — через `keyctl`, но в новых ядрах ограничен.
- **`setxattr`** — временный буфер при установке расширенных атрибутов.

Для нашего примера берём `msg_msg`: он прост, не требует привилегий и даёт
точный контроль размера.

## Шаг 1: как SLUB отдаёт память

SLUB держит для каждого кэша список свободных объектов (freelist). При
освобождении объект возвращается в freelist; при следующем выделении SLUB
берёт объект **с головы freelist**. Значит, если сразу после `free` сделать
`alloc` того же размера, мы с высокой вероятностью получим именно этот слот.
Это называется **LIFO-поведение** (последний освобождённый — первый выданный).

```
free(X)            → freelist: [X, ...]
alloc(64)          → возвращает X   ← наш шанс
```

Проблема: ядро может выделить что-то своё в промежутке. Поэтому окно узкое, и
спрей делают сразу, без лишних syscall между `free` и `alloc`.

## Шаг 2: пер-кэш и пер-CPU

SLUB держит отдельный freelist на каждый CPU. Если процесс мигрирует между
ядрами, `free` и `alloc` могут произойти на разных CPU и не совпасть. Решение —
**закрепить поток на одном CPU**:

```c
#define _GNU_SOURCE
#include <sched.h>
cpu_set_t set;
CPU_ZERO(&set);
CPU_SET(0, &set);
sched_setaffinity(0, sizeof(set), &set);
```

Без этого спрей на многопроцессорной машине работает нестабильно — классическая
ошибка новичков.

## Шаг 3: heap grooming (укладка кучи)

Чтобы цель оказалась рядом с нашими объектами, кучу «укладывают» заранее:

1. Выделяем много объектов-заполнителей (`msg_msg`) — куча наполняется.
2. Освобождаем часть, создавая «дырки» нужного размера.
3. Триггерим уязвимость так, чтобы цель попала в дырку.
4. Освобождаем цель (UAF) и сразу спреим.

Grooming повышает предсказуемость: мы управляем тем, что лежит рядом с целью.
В CTF часто хватает простого спрея, но в реальных ядрах grooming обязателен.

## Шаг 4: спрей с повторами

Даже с закреплением на CPU нельзя гарантировать 100% попадание. Поэтому спрей
делают **много раз**: сотни сообщений, затем проверка (например, изменился ли
наблюдаемый эффект). Если не вышло — освобождаем и повторяем. Хороший эксплойт
выглядит так:

```c
for (int attempt = 0; attempt < 100; attempt++) {
    spray_msg(64, N);            // N сообщений
    if (check_overwrite()) break; // проверили, что слот наш
    cleanup();
}
```

`check_overwrite` — это «детектор успеха»: например, чтение поля, которое мы
задали, или отсутствие краша. Без детектора эксплойт «слепой».

## Шаг 5: замена объекта

Когда слот занят нашим `msg_msg`, «старая ссылка» на освобождённый X указывает
на контролируемый объект. Дальше два пути:

- **Испортить поля `msg_msg`** — например, увеличить `m_ts` (OOB-read) или
  подменить `next` (arbitrary read). Это даёт примитивы.
- **Заставить X-операцию писать в наш объект** — тогда мы перезаписываем
  указатели внутри `msg_msg` и получаем произвольную запись.

Выбор зависит от того, что делает операция над X: читает или пишет.

## Шаг 6: альтернативные объекты

- **`sk_buff`** — данные в `skb->data`; размер подбирается под кэш. Удобно, когда
  `msg_msg` недоступен (seccomp блокирует `msgget`).
- **`setxattr`** — `setxattr("/tmp/f", "user.x", buf, len, 0)` временно выделяет
  буфер в ядре и копирует туда данные. Хорошо для одноразового спрея.
- **`user_key_payload`** — через `add_key`; в новых ядрах ограничен по размеру.

Для каждого важно точно знать размер выделения, чтобы попасть в нужный кэш.

## Шаг 7: отладка и проверка

Под `qemu` с `gdb` можно смотреть SLUB: `b *kmem_cache_alloc` или проверять
адреса объектов. Полезно печатать, сколько объектов каждого размера выделено.
В `dmesg` видны паники, если спрей «промахнулся» и задел чужой объект.

## Что мы теперь знаем

- SLUB выдаёт слот с головы freelist (LIFO) — сразу после free делаем alloc.
- Закрепление на одном CPU обязательно для стабильности.
- Grooming управляет раскладкой кучи.
- Спрей повторяют с детектором успеха.
- `msg_msg`/`sk_buff`/`setxattr` — рабочие объекты-заполнители.

## Per-CPU и per-node кэши SLUB

SLUB хранит freelist на каждый CPU в структуре `kmem_cache_cpu`. Когда на CPU
заканчиваются свободные объекты, SLUB берёт новый «slab» (страницу) из
**per-node partial list**. Это добавляет ещё один уровень сложности: даже
закрепившись на CPU, можно попасть не в тот slab, где лежит цель.

Приёмы для повышения предсказуемости:

- **Прогрев (warm-up):** заранее выделить много объектов, чтобы slab-ы
  заполнились и freelist был стабилен.
- **Синхронизация:** делать free и alloc максимально близко, без syscall между
  ними.
- **Повтор:** если не вышло, освободить всё и начать заново.

## Freelist hardening и рандомизация

Современные ядра включают:

- `CONFIG_SLAB_FREELIST_RANDOM` — порядок объектов внутри нового slab
  рандомизируется. Значит, «следующий объект рядом» — не гарантия.
- `CONFIG_SLAB_FREELIST_HARDENED` — указатель freelist XOR-кодируется случайным
  значением, что ломает классические атаки на freelist.
- `CONFIG_SLAB_MERGE_DEFAULT` — кэши одинакового размера могут сливаться, что
  меняет раскладку.

Эти опции не мешают спрею как таковому, но требуют больше попыток и точного
детектора успеха. В CTF их часто отключают, в реальных ядрах — нет.

## Детекторы успеха спрея

Без детектора спрей «слепой». Хорошие детекторы:

- **Наблюдаемый эффект:** после записи через UAF читаем поле, которое задали, и
  сравниваем с ожидаемым.
- **Отсутствие краша:** если после триггера процесс жив — вероятно, попал.
- **Утечка-маркер:** спрей уникальным значением (например, `0x41414141`), затем
  читаем и проверяем.

Детектор позволяет **повторять** до успеха и не тратить попытки впустую.

## Полный пример grooming

```c
pin_cpu(0);
int qid = msgget(IPC_PRIVATE, 0666 | IPC_CREAT);
spray_fillers(qid, 256);        // 1) наполнить кучу
free_some(qid, 128);            // 2) сделать дырки
trigger_alloc_vuln();           // 3) цель попадает в дырку
trigger_free_vuln();            // 4) UAF
spray_msg(64, 512);             // 5) занять слот
if (check_overwrite()) exploit(); // 6) проверить и продолжить
```

Каждый шаг управляем: мы знаем, что лежит вокруг цели, и можем повторить всю
последовательность. Именно такая дисциплина отличает стабильный эксплойт от
«иногда работает».
