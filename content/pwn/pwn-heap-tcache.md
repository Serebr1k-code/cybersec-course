## Вопрос, с которого всё начинается

В прошлых уроках мы гоняли `fastbin` и `unsorted bin`. Но на современной glibc почти все маленькие освобождения попадают не туда, а в **tcache** — кэш на поток, придуманный, чтобы `malloc`/`free` работали быстрее. И у него есть слабое место: если у тебя есть UAF, из tcache делается **самая короткая в мире произвольная аллокация**.

Разберём `tcache poisoning` — приём, который в 90% современных heap-задач CTF является основным путём к победе.

## Наш пример

Соберём стенд: два чанка `A` и `B`, глобальный буфер `target`, и один UAF-записью подменим указатель в tcache:

```
A=0x16929010  B=0x16929060  target=0x404060
after free(A),free(B):  tcache[0x50] = B -> A
B.fd <- target ^ (B>>12) = 0x412949
malloc -> 0x16929060 (B)
malloc -> 0x404060 (target!)
```

Второй `malloc` вернул **не чанк из кучи, а наш `target`**. Дальше любая запись в этот указатель пишет в `target`. Это и есть произвольная аллокация.

## Шаг 1. Что такое tcache

`tcache` — это массив из 64 односвязных списков (по одному на размерный класс), плюс счётчик заполненности. По умолчанию в каждом списке не больше **7** элементов. Он появился в glibc 2.26 и перехватывает освобождения размером до `0x410`.

Структура простейшая: у каждого свободного tcache-чанка первое слово — указатель `next` на следующий свободный чанк того же размера, а второе слово — служебный `key`. `free` кладёт чанк в голову, `malloc` забирает из головы (LIFO).

## Шаг 2. Почему это идеальная цель для UAF

Список односвязный, а проверки минимальны. Если через UAF перезаписать поле `next` у первого свободного чанка, то следующий `malloc` вернёт «следующий» указатель — а мы туда записали что угодно. Никакой проверки на голову списка, как в fastbin, здесь нет.

План атаки прост:

1. `alloc(0x40)` -> `A`; `alloc(0x40)` -> `B`.
2. `free(A)`; `free(B)` — теперь `tcache -> B -> A`.
3. Через UAF пишем в `B.next` адрес цели.
4. Два `malloc(0x40)` — первый вернёт `B`, второй вернёт нашу цель.

## Шаг 3. Safe-linking: зачем тут XOR

С glibc 2.32 указатели в tcache и fastbin **зашифрованы** приёмом `safe-linking`. Хранимое значение — это не сам `next`, а `next XOR (адрес_поля >> 12)`. Смысл: младшие 12 бит адреса — это смещение в странице, они одинаковы у соседних чанков, поэтому без знания heap-базы нельзя просто подставить нужный указатель.

В нашем выводе видно, что реально записано в память:

```
B.fd <- target ^ (B>>12) = 0x412949
```

Мы вычислили зашифрованное значение как `target XOR (B >> 12)`. `B` мы знаем (у нас есть UAF и адрес чанка), поэтому можем закодировать любую цель. Именно так safe-linking обходится, когда heap-база известна.

## Шаг 4. Когда heap-базы нет

Если адрес `B` неизвестен, есть два пути. Первый — **частичная перезапись** младшего байта `next` (см. `pwn-partial-overwrite`): зашифрованный указатель сохраняет старшие биты, и подправка одного байта переносит аллокацию на соседний чанк в той же странице. Второй — сначала **утечь** heap-базу (например, через `_IO_FILE` или неинициализированную память), а потом закодировать полный адрес.

## Шаг 5. Куда целиться

Исторически целились в `__free_hook` (написать туда `system`, потом `free("/bin/sh")`) или `__malloc_hook`. С glibc 2.34 функциональность хуков **удалена** — символы ещё есть, но они ничего не делают. Современные цели:

| Цель | Зачем |
|---|---|
| `_IO_list_all` / `_IO_2_1_stdout_` | FSOP: подмена vtable при flush/exit |
| `__exit_funcs` / `tls_dtor_list` | вызов при выходе из программы |
| `.fini_array` / `.got` | подмена указателя функции |
| локальные указатели на стеке | перезапись сохранённого адреса |

`tcache poisoning` даёт аллокацию по любому из этих адресов — остаётся записать туда полезное значение.

## Шаг 6. tcache poisoning за один приём

Полный скрипт в стиле pwntools выглядит так:

```python
from pwn import *
context.binary = elf = ELF('./chall')
libc = ELF('./libc.so.6', checksec=False)
p = process('./chall')

alloc(0x40); alloc(0x40)             # A, B
free(0); free(1)                     # tcache: B -> A
heap = ...                           # утечка адреса B
enc = (libc.symbols['_IO_list_all'] ^ (heap >> 12))
edit(1, p64(enc))                    # UAF: пишем в B.next
alloc(0x40)                          # -> B
alloc(0x40)                          # -> _IO_list_all
```

## Шаг 7. Tcache key и double-free

Второе слово свободного tcache-чанка — `key`. Это случайное число, которое glibc кладёт при освобождении, чтобы ловить double-free: если при `free` увидит `key == tcache_key`, начнёт искать чанк в списке и упадёт с `free(): double free detected in tcache 2`. Обход: занулить `key` через UAF перед повторным освобождением. В прошлом уроке про fastbin dup мы делали ровно это.

## Если не сработало

`tcache poisoning` чувствителен к нескольким мелочам. Если второй `malloc` вернул не то, что ожидалось, проверь по порядку.

Первое: размер должен совпадать. Класс tcache определяется размером чанка с точностью до `0x10`. Если ты освободил `0x40`, а аллоцируешь `0x30`, попадёшь в другой список, и подменённый `next` не сработает. Держи одинаковый размер.

Второе: количество. Если в списке больше одного элемента, первый `malloc` вернёт голову, и только второй дойдёт до подменённого указателя. Убедись, что ты правильно посчитал, сколько `malloc` нужно сделать до цели.

Третье: safe-linking. Если ты записал в `next` «сырой» адрес цели без XOR, `malloc` упадёт или вернёт мусор. Кодируй значение как `target XOR (chunk_addr >> 12)`, используя адрес **того самого чанка**, чьё поле ты перезаписываешь.

Четвёртое: `key`. Если ты делаешь double-free, а не UAF, glibc поймает это по полю `key`. Зануль `key` перед повторным `free`.

Пятое: `target` должен быть выровнен на 8 (а лучше на 0x10) и находиться в доступной на запись памяти. Аллокация по невалидному адресу приведёт к падению на первом же обращении.

## Что мы теперь знаем

- `tcache` — кэш на поток из списков до 7 элементов, перехватывает освобождения до `0x410`.
- Указатель `next` лежит в первом слове свободного чанка; список LIFO, без проверки головы.
- UAF-перезапись `next` даёт аллокацию по произвольному адресу — `tcache poisoning`.
- С glibc 2.32 указатели зашифрованы safe-linking: `хранимое = next XOR (addr >> 12)`.
- При известной heap-базе цель кодируется легко; без неё — частичная перезапись или утечка.
- После 2.34 хуки мертвы — целятся в FSOP, `__exit_funcs`, `.fini_array`.
