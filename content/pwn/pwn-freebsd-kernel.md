## Вопрос, с которого всё начинается

Ты получил kernel R/W на FreeBSD. В Linux ты бы правил `struct cred`, чтобы стать
root. Но здесь этой структуры нет. Как называется аналог и что вообще менять?
Разберём ядро FreeBSD — оно ближе всего к macOS/XNU, и навыки туда переносятся.

## Наш пример

Заголовок ядра FreeBSD:

```
$ cat ucred.h
struct ucred {
    u_int   cr_ref;      /* reference count */
    uid_t   cr_uid;      /* effective user id */
    gid_t   cr_gid;      /* effective group id */
    ...
};
```

Структура **`ucred`** описывает учётные данные процесса. Именно её правят, чтобы
повысить привилегии. Разберём путь к ней.

## Шаг 1: монолитное ядро и интерфейсы

FreeBSD — **монолитное** ядро (как Linux), но с другими интерфейсами:

- **ioctl** — основной способ общения с драйверами (`ioctl(fd, cmd, arg)`);
- **sysctl** — чтение/запись параметров ядра;
- **системные вызовы** — как везде;
- **jail** — изоляция (аналог контейнера), с собственными правами.

Большинство драйверов обрабатывают ioctl'ы; ошибки в проверке аргументов — самый
частый источник багов.

## Шаг 2: ucred и учётные данные

**`ucred`** (user credentials) хранит:

- **`cr_uid`/`cr_gid`** — эффективные uid/gid;
- **`cr_ref`** — счётчик ссылок;
- **`cr_groups`** — дополнительные группы;
- **`cr_prison`** — ссылку на jail (если процесс в jail);
- флаги и capabilities.

Правка `cr_uid` на 0 (root) — классический примитив повышения привилегий. Но, как
и везде, нужен доступ к структуре через kernel R/W.

## Шаг 3: путь к структуре

Как найти `ucred` процесса из примитива ядра:

1. **Через `proc`.** У каждого процесса есть `struct proc` (аналог
   `task_struct`), в нём — указатель на `ucred` (`p_ucred`).
2. **Через `thread`.** У потока есть `td_ucred`.
3. **По списку процессов.** `allproc` — глобальный список процессов; можно
   пройтись и найти свой.
4. **По известной утечке.** Если утечка дала адрес `proc`/`thread`, до `ucred`
   один переход.

## Шаг 4: Capsicum

**Capsicum** — модель capabilities FreeBSD: процесс может перейти в «capability
mode», где доступ ограничен явно выданными правами на файловые дескрипторы. Это
аналог песочницы. Для эксплуатации это значит: даже с правами процесса не всё
доступно, если он в capability mode.

## Шаг 5: защиты

- **KASLR** — рандомизация ядра; нужна утечка.
- **W^X** — страницы либо записываемы, либо исполняемы (не оба).
- **Capsicum** — ограничение прав процессов.
- **HARDENEDBSD** — опциональный набор усилений.
- **Stack guard** — защита стека ядра.

## Шаг 6: типичные баги

- **ioctl с неполной проверкой** — переполнение буфера ядра.
- **Race conditions** — гонки в структурах ядра.
- **UAF** — освобождение и повторное использование объектов.
- **Integer overflow** — неверные размеры при копировании.
- **Отсутствие проверки прав** — доступ к функциям, которые должны быть
  привилегированными.

## Шаг 7: собираем тактику

1. Найди баг в драйвере (ioctl) или подсистеме.
2. Получи info-leak (KASLR) и kernel R/W.
3. Найди `ucred` своего процесса (через `proc`/`thread`).
4. Обнули `cr_uid`/`cr_gid` (и группы).
5. Проверь, что не в jail/capability mode, где прав всё равно мало.

## Шаг 8: переносимость на XNU

Многое из FreeBSD есть и в macOS (XNU использует код FreeBSD). Аналогия структур:
`ucred` (FreeBSD) ↔ `kauth_cred` (XNU), `proc` есть в обоих. Поэтому, разобравшись
с FreeBSD, ты легче поймёшь XNU.

## Как это выглядит в реальном эксплойте

Цепочка FreeBSD-kernel-эксплойта:

1. **Триггер через ioctl.** Вызываем уязвимый драйвер с данными, ломающими
   проверку.
2. **Куча-примитив.** Через переполнение/UAF получаем контроль над объектом.
3. **Info-leak.** Утекаем адреса ядра (KASLR).
4. **R/W ядра.** Подменяем указатель, получаем чтение/запись.
5. **Правка `ucred`.** Через `allproc` находим свой `proc`, от него `p_ucred`,
   обнуляем `cr_uid`/`cr_gid` и группы.
6. **Проверка окружения.** Убеждаемся, что процесс не в jail/capability mode,
   иначе прав всё равно мало.

## Частые ошибки

- **Искать `cred`.** В FreeBSD структура называется `ucred`.
- **Забыть про jail.** Процесс в jail имеет `cr_prison`; правка uid внутри jail
  не даёт выйти наружу.
- **Игнорировать Capsicum.** В capability mode доступ ограничен даже с root.
- **Не учесть KASLR.** Без утечки адрес не подставить.

## Сравнение с Linux kernel

- **Модель.** Оба монолитные; FreeBSD драйверы чаще общаются через `ioctl`.
- **Учётные данные.** Linux — `cred`; FreeBSD — `ucred`; поля похожи
  (`cr_uid`/`uid`), но структуры разные.
- **Изоляция.** Linux — namespaces/cgroups; FreeBSD — **jails**.
- **Capabilities.** Linux — capability-биты; FreeBSD — **Capsicum**.

Зная Linux-методологию (info-leak → R/W → правка учётных данных), ты быстро
адаптируешься к FreeBSD, поменяв имена структур и интерфейсов.

## Инструменты анализа FreeBSD kernel

- **Исходники ядра** — FreeBSD открыт; структуры (`ucred`, `proc`) и обработчики
  `ioctl` читаются напрямую.
- **`sysctl`** — инспекция параметров и подсистем ядра.
- **DDB/KGDB** — отладочные интерфейсы ядра.
- **Ghidra/IDA** — если исходников целевой сборки нет.

Открытость исходников — большое преимущество: контракт `ioctl` и структуры видны
сразу, что ускоряет поиск и построение триггера.

## ZFS, jails и поверхность атаки

У FreeBSD есть собственные крупные подсистемы, дающие дополнительные цели:

- **ZFS** — продвинутая файловая система; её код сложен, и в нём находили
  уязвимости (в том числе в ioctl'ах `zfs`).
- **jails** — изоляция на уровне ядра; баги в jail-логике могут позволить выход.
- **network stack** — собственный стек (не Linux); ошибки в обработке пакетов
  дают kernel-баги.
- **capsicum** — подсистема capabilities; ошибки в ней ломают песочницу.

Кроме драйверов, эти подсистемы — перспективные цели для поиска kernel-багов на
FreeBSD.

## Почему FreeBSD — хорошая учебная цель

FreeBSD удобна для обучения kernel-эксплуатации:

- **открытые исходники** — структуры и обработчики видны сразу;
- **меньше митигаций**, чем на современных Linux/Android, по умолчанию;
- **код общий с XNU** — навыки переносятся на macOS/iOS;
- **активное сообщество** — публичные разборы и CVE.

Разобравшись с FreeBSD, ты легче поймёшь и Linux (та же модель монолита), и XNU
(общие структуры).

## ioctl как главный канал

Большинство уязвимостей в FreeBSD-ядре живут в обработчиках `ioctl` устройств и системных вызовов, которые принимают пользовательскую структуру и копируют её в ядро. Классические ошибки: несоответствие `_IOW`/`_IOR` размеров, `copyin` без проверки длины, использование непроверенного указателя. Ищи функции `sys_*` и обработчики `d_ioctl` в драйверах, смотри на `copyin`/`copyout` и `malloc` с размером из пользовательских данных.

```c
/* типичный шаблон: размер из userland без проверки */
copyin(data, uap->buf, uap->len);
```

Практический подход: статически ищи места, где размер или индекс приходит из пользовательского пространства и не валидируется. Это первая гипотеза при ревью FreeBSD-драйвера.

## Capsicum, jails и примитивы

**Capsicum** — capability-фреймворк FreeBSD: процесс может перейти в режим capability, потеряв доступ к глобальному пространству имён и ограничившись файловыми дескрипторами. Это усложняет постэксплуатацию: даже с kernel R/W нужно обойти capability-ограничения. **Jails** — изоляция (аналог контейнеров), и побег из jail — отдельная цель.

Типичные примитивы после kernel-бага: чтение/запись памяти ядра (arbitrary R/W), подмена `ucred` текущего процесса (data-only privesc), или выполнение кода в ring0. Для FreeBSD часто предпочтителен data-only: он обходит KASLR и не требует ROP. Ищи структуру `ucred` текущего процесса через `p_cred` в `struct proc` и переписывай `cr_uid`/`cr_groups` на 0.

## Сравнение с Linux и инструменты

FreeBSD-ядро монолитно, как Linux, но код отличается: `ucred` вместо `cred`, KBI стабильнее, а `sysctl`-поверхность шире. Для учебных целей FreeBSD хорош тем, что ядро меньше Linux, документация яснее, а отлаживать его проще (`kgdb`, DDB). Инструменты: `clang`/`Ghidra` для анализа, `dtrace` для трассировки, `kgdb` для отладки ядра, `syzkaller` для фаззинга системных вызовов. Помни про отличия: указатели в ядре FreeBSD могут быть «tagged» (для отладки), а `copyin`/`copyout` — основной канал пользовательских данных.

## Практические заметки по FreeBSD

FreeBSD удобен для обучения kernel-эксплуатации: ядро меньше Linux, документация (man-страницы, исходники) доступна, отладка проще (`kgdb`, DDB). Типовой сценарий: найти `ioctl`-обработчик с непроверенным `copyin`, получить переполнение, построить kernel R/W, затем data-only подменить `ucred`. Data-only предпочтителен, потому что обходит KASLR и не требует ROP в ядре.

## Итог по FreeBSD

FreeBSD — удобная учебная цель: меньше кода, доступная документация, простая отладка. Главный канал — `ioctl`/`copyin` без проверки размера. Data-only подмена `ucred` обходит KASLR. Capsicum и jails усложняют постэксплуатацию, но не мешают самому примитиву.

## Итог

FreeBSD: главный канал — `ioctl`/`copyin`; data-only подмена `ucred` обходит KASLR. Отладка через `kgdb`.

## Что мы теперь знаем

- FreeBSD — монолитное ядро с ioctl/sysctl-интерфейсами.
- `ucred` — структура учётных данных; правка даёт root.
- Путь: `allproc` → `proc` → `p_ucred`.
- Capsicum ограничивает права даже после компромисса.
- Защиты: KASLR, W^X, stack guard.
- Многое переносится на XNU.
