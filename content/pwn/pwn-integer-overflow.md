Целочисленные переполнения — это класс уязвимостей, при которых арифметическая операция даёт неожидаемый результат из-за ограниченного размера типа. Виды: **signedness** (знаковое/беззнаковое смешение), **truncation** (усечение при приведении к меньшему типу), **underflow** (отрицательный результат беззнакового), **overflow** (выход за диапазон). В pwn они критичны, потому что часто ведут к переполнению буфера: например, `size = a + b` переполняется, и проверка `if (size < MAX)` проходит, а `memcpy` копирует больше. В этом уроке — виды переполнений, типовые баги, эксплуатация и практические примеры.

## Виды целочисленных переполнений

1. **Unsigned overflow.** `UINT_MAX + 1 == 0`; проверки `if (size < MAX)` могут пройти.
2. **Signed overflow.** `INT_MAX + 1` — UB, часто становится отрицательным; сравнения `if (n < 0)` обходятся.
3. **Sign conversion.** `int` → `unsigned` даёт огромное число; `unsigned` → `int` может дать отрицательное.
4. **Truncation.** Приведение `size_t` (64) к `int` (32) отбрасывает старшие биты; проверка по 64-битному значению проходит, а используется 32-битное.
5. **Underflow.** `size - offset` при `offset > size` даёт огромное беззнаковое число.
6. **Integer promotion.** Неявные приведения в выражениях меняют тип результата.

## Типовые баги

- **`malloc(a * b)`** переполняется, выделяется мало, затем `memcpy` переполняет буфер.
- **`len = header.len; buf[len]`** при `len` отрицательном/огромном.
- **`if (size > 1024) return; buf[size]`** при `size` signed и отрицательном.
- **`read(fd, buf, size)`** с `size` из переполненного выражения.
- **`idx * stride`** переполняется, давая доступ по неверному индексу.

## Эксплуатация

Схема: (1) найти арифметику с user-контролем; (2) вычислить вход, вызывающий переполнение; (3) обойти проверку (например, `size < MAX` проходит при переполнении); (4) добиться переполнения буфера/неверного индекса; (5) эксплуатировать (heap/stack overflow). Пример: `malloc(n * sizeof(T))` при большом `n` переполняется в маленькую аллокацию, затем цикл записывает `n` элементов — heap overflow.

## Разобранный пример

```c
// уязвимый код
unsigned int n = read_int();       // user input
unsigned int size = n * 4;          // overflow!
char *buf = malloc(size);           // маленькая аллокация
for (unsigned i = 0; i < n; i++)
    buf[i * 4] = input();           // heap overflow
```

Если `n = 0x40000000`, `size = 0` (overflow), `malloc(0)` возвращает маленький чанк, а цикл пишет `n` элементов — переполнение. Эксплойт: подобрать `n`, получить heap overflow и переписать соседние структуры.

## Поиск в бинарях

Ищите арифметику с user-вводом: `imul`, `add`, `sub`, `shl`, приведение типов (`movsx`/`movzx`). В Ghidra/IDA декомпиляция покажет выражения. Проверяйте проверки: если они по другому типу, чем использование — баг. Учитывайте integer promotion и signedness.

## Проверка в gdb

```bash
(gdb) p/x n * 4
(gdb) b *malloc
(gdb) p $rdi          # размер аллокации
```

Убедитесь, что размер переполнился и аллокация маленькая.

## Частые ошибки

- **Не учли signedness.** Сравнение signed/unsigned ведёт себя неочевидно.
- **Truncation.** 64→32 теряет старшие биты.
- **Promotion.** Неявные приведения меняют результат.
- **UB.** Signed overflow — UB, компилятор может оптимизировать.
- **Проверки.** Проверка по одному типу, использование — по другому.

## Полный разбор целочисленного переполнения

Разберём сквозной пример. Дано: приложение читает число `n`, вычисляет `size = n * 4`, выделяет буфер и копирует `n` элементов. Цель — heap overflow. Шаги: (1) реверсните код (Ghidra/IDA) и найдите арифметику; (2) определите тип (`unsigned int`?); (3) подберите `n` так, чтобы `n * 4` переполнилось в маленькое значение (например, `n = 0x40000000` → `size = 0`); (4) убедитесь, что проверка (`if (n > MAX)`) не ловит переполнение; (5) отправьте `n` — `malloc(0)` вернёт маленький чанк; (6) цикл запишет `n` элементов — heap overflow; (7) используйте переполнение для контроля (перезапись соседних чанков). Проверяйте в gdb: `b *malloc`, `p $rdi` (размер), `heap`. Целочисленное переполнение — «ключ», открывающий переполнение буфера.

## Signedness и truncation на практике

**Signedness:** если `len` объявлен `int`, а проверка `if (len > 1024)` — при `len = -1` проверка проходит (отрицательное < 1024), а `memcpy(buf, src, len)` преобразует `-1` в `SIZE_MAX` — огромное копирование. **Truncation:** если `size_t size = ...; int n = size;` — при `size = 0x100000000` `n = 0`, проверка по `n` проходит, а используется `size`. Ищите несоответствия типов между проверкой и использованием. В декомпиляторе обращайте внимание на `movsx`/`movzx` (знаковое/беззнаковое расширение) и приведение размеров. Это частые источники багов (CWE-190, CWE-195).

## Расширенный разбор целочисленных багов

Дополним. **Integer promotion** в C: в выражениях типы меньше `int` повышаются до `int`, что может изменить результат. Пример: `unsigned short a = 65535; a + 1` → `65536` (int), а не `0`. **Usual arithmetic conversions:** при смешении signed/unsigned результат — unsigned, что даёт неожиданные сравнения (`-1 > 1u` истинно). **Truncation** при присваивании/приведении теряет старшие биты. **Underflow** беззнакового: `size - 1` при `size == 0` → `SIZE_MAX`. Эти правила — источник множества багов. Изучите их и проверяйте арифметику в декомпилированном коде. В gdb наблюдайте фактические значения (`p/x expr`) — компилятор мог оптимизировать UB.

## Практические сценарии эксплуатации

Типовые цепочки: (1) `malloc(n * m)` переполняется → маленькая аллокация → heap overflow; (2) `len` signed отрицательный → `memcpy` с огромным размером; (3) индекс `idx * stride` переполняется → OOB-доступ; (4) проверка `size < MAX` по 32-битному, а использование 64-битного → truncation. Для каждого: подберите вход, обойдите проверку, добейтесь переполнения, эксплуатируйте. Проверяйте в gdb: `p/x size`, `b *malloc`, `heap`. Комбинируйте с heap/stack-техниками. Целочисленные баги часто «открывают» путь к memory corruption, который иначе недостижим.
