## Вопрос, с которого всё начинается

Представь, что на цели включён **полный CFI**: и `ret`, и косвенные `jmp`, и
косвенные `call` проверяются. Ни ROP, ни JOP, ни COP не проходят. Остаётся ли
атака? Да — **DOP**: мы не трогаем поток управления вообще, а заставляем
штатный код программы сделать то, что нам нужно, управляя только данными.

## Наш пример

Смотрим фрагмент программы, который «принимает решения» по данным:

```c
struct op {
    int  kind;      // 0 = add, 1 = sub, 2 = mul
    int  a, b;
    int  result;
};

void run(struct op *o) {
    switch (o->kind) {
        case 0: o->result = o->a + o->b; break;
        case 1: o->result = o->a - o->b; break;
        case 2: o->result = o->a * o->b; break;
    }
}
```

Если мы контролируем структуру `op`, мы управляем тем, **что** программа
вычисляет — без единого изменения в потоке управления. Это микро-пример DOP.

## Шаг 1: идея DOP

DOP исходит из того, что полезный эффект можно получить, меняя данные, которые
штатный код читает. Атака состоит из **gadget'ов данных** — коротких
последовательностей операций над памятью, которые программа выполняет
естественным образом. Собирая их, можно вычислить значения, изменить поля
структур и достичь цели (например, сделать `is_admin = 1`).

Код при этом исполняется штатный — CFI счастлив, потому что поток не нарушен.

## Шаг 2: почему DOP устойчив к CFI

CFI следит за **адресами переходов**. DOP не создаёт новых переходов — он
пользуется существующими. Значит, проверять нечего: все переходы легальны.
Единственное, что нарушено, — целостность данных. Поэтому защита от DOP — это
не CFI, а проверка целостности данных (data-flow integrity), которая на практике
редка.

## Шаг 3: data-gadget

**Data gadget** — операция, которая читает входные данные и пишет результат.
Примеры: `o->result = o->a + o->b`, инкремент счётчика, копирование поля,
установка флага. Атака — это цепочка таких операций, приводящая к желаемому
состоянию памяти.

Собирать их можно полуавтоматически: инструмент ищет в коде последовательности
загрузок/сохранений и строит граф зависимостей (это уже research-уровень,
инструменты вроде `dop`-фреймворков).

## Шаг 4: DOP в userland vs в ядре

В userland DOP используется против CFI-защищённых бинарей: меняем флаги
проверок, поля структур, счётчики. В **ядре** родственный класс — data-only
атаки (перезапись `cred`, `modprobe_path`). Разница в терминологии, идея одна:
данные вместо потока.

## Шаг 5: практический пример — обход проверки

```c
if (user->role == ROLE_ADMIN) {
    grant_access();
}
```

Если мы можем записать `ROLE_ADMIN` в поле `role` (через баг), `grant_access`
выполнится штатно. Никакого ROP. Это самый простой DOP: одна запись в данные.

## Шаг 6: когда DOP — единственный путь

- **Полный CFI** (проверяются все косвенные переходы).
- **Hardware CFI/CET + shadow stack**.
- **Изолированные языки** (Rust/Go с проверками) — там контроль потока почти
  невозможен, а data-баги остаются.

В этих случаях DOP (и родственные data-only) — реалистичная стратегия.

## Шаг 7: ограничения

- Нужен **data-примитив** (запись по нужному адресу).
- Нужно знать структуру данных (смещения полей).
- Цепочка может быть длинной и хрупкой.
- Не всегда можно добиться нужного эффекта только данными (например, вызвать
  `system` без перехвата потока трудно — но можно перезаписать указатель,
  который штатный код потом вызовет).

## Что мы теперь знаем

- DOP управляет данными, а не потоком управления.
- Он устойчив к CFI, потому что переходы легальны.
- Data-gadget — операция над памятью, из них собирают цепочку.
- В ядре аналог — data-only атаки.
- Нужен data-примитив и знание структуры.

## Поиск data-gadget'ов

Data gadget — это операция, которая читает одни данные и пишет другие. В
отличие от code gadget (заканчивается переходом), data gadget — это просто
фрагмент штатного кода. Искать их можно вручную или полуавтоматически:

- **Вручную:** смотрим на функции, которые обрабатывают структуры, и ищем
  присваивания вида `a->field = b->field + 1`, копирования, установки флагов.
- **Автоматически:** инструменты строят граф зависимостей памяти и ищут
  последовательности, ведущие от входа к нужному выходу.

Пример полезного data gadget из нашего кода выше:

```c
case 0: o->result = o->a + o->b; break;   // если control kind == 0
```

Контролируя `o->kind`, мы выбираем операцию; контролируя `o->a`, `o->b` —
входные значения. Так из одной структуры строится «АЛУ атакующего».

## Пример цепочки вычислений

Пусть цель — записать ноль в поле `is_admin`. Если есть data gadget, который
прибавляет к полю контролируемое значение, можно вычесть текущее:

```
gadget1: field = field + delta   // delta = -field
```

Или, если есть операция копирования между полями, скопировать значение из
поля, которое мы контролируем (например, из `a`), в `is_admin`. Каждый шаг —
штатная операция программы.

## DOP против указателей

Мощный приём DOP — перезапись **указателя**, который штатный код потом
разыменует или вызовет. Это ещё не перехват потока (переход легален — через
существующий `call`), но эффект — выполнение нашего кода или чтение наших
данных. Пример: подменить указатель на буфер, в который `memcpy` копирует
данные — получим произвольную запись.

## DOP в ядре и userland

В userland DOP борется с CFI: меняем флаги, поля, счётчики. В ядре аналог —
data-only атаки: перезапись `cred`, `modprobe_path`. Разница в терминологии;
идея одна — данные вместо потока.

## Ограничения DOP

- Нужен **data-примитив** (запись по адресу).
- Нужно **знание структуры** (смещения полей).
- Цепочка может быть длинной и хрупкой; её сложнее строить, чем ROP.
- Не всё достижимо: вызвать `system` без перехвата потока трудно, но можно
  подменить указатель, который штатный код затем вызовет.

DOP — не «серебряная пуля», а стратегия для случаев, когда CFI закрывает
control-flow. Часто её комбинируют с data-only финишерами.

## DOP и автоматизация

Строить DOP-цепочки вручную трудоёмко, поэтому существуют исследовательские
инструменты, которые:

- строят граф зависимостей памяти программы;
- находят data-gadget'ы, ведущие от контролируемого входа к нужному выходу;
- синтезируют цепочку.

Это уровень научных работ (например, из конференций по безопасности), но идея
доступна и вручную: ищи операции над полями структур, которые ты можешь
контролировать, и выстраивай из них последовательность.

## Итог по DOP

DOP управляет данными, а не потоком управления, поэтому обходит CFI/CET. Нужен
data-примитив и знание структур. Это стратегия для целей с полным CFI, где
control-flow атаки невозможны.

## Разбор реального DOP-сценария

Цель — приложение с полным CFI: любой косвенный переход проверяется. Уязвимость
даёт запись по контролируемому адресу. Стратегия:

1. Находим структуру, влияющую на безопасность (флаг `is_admin`, поле `role`,
   указатель на буфер).
2. Утечкой определяем её адрес.
3. Через data-примитив меняем поле на нужное значение.
4. Штатный код сам делает остальное (grant_access, копирование, вызов).

Ни одного нового перехода — CFI нечего проверять.

## Комбинирование с перезаписью указателей

Мощный приём: перезаписать **указатель на функцию**, который штатный код
вызывает легально. Тогда CFI видит нормальный `call [obj+off]`, но цель уже
наша. Это гибрид DOP и control-flow: переход легален по форме, но ведёт туда,
куда мы хотим. Так data-примитив превращается в выполнение кода.

## DOP и целостность данных

Единственная надёжная защита от DOP — data-flow integrity (DFI): проверка, что
данные не меняются в обход ожидаемых путей. На практике DFI почти не
встречается из-за накладных расходов. Поэтому DOP остаётся актуальным на
системах с сильным CFI. Понимание DOP полезно и для защиты: оно показывает, что
CFI — не серебряная пуля, и целостность данных важна не меньше целостности
потока.

## Типичные ошибки DOP

- **Нет data-примитива.** Без записи по адресу DOP не собрать.
- **Неверные смещения.** Поля структур меняются между версиями; бери из BTF.
- **Слишком длинная цепочка.** Каждый шаг — риск; упрощай.
- **Забыть про обход KASLR.** Адрес цели тоже рандомизирован.

## Заключение по DOP

DOP — ответ на полный CFI: мы не создаём новых переходов, а управляем данными,
которые читает штатный код. Это делает технику устойчивой к любым защитам потока
управления, но требует data-примитива и знания структур. DOP сложнее ROP, но на
целях с сильным CFI это часто единственный путь. Начни с поиска простых data-
gadget'ов (запись в поле, инкремент) и комбинируй их с перезаписью указателей,
которые программа вызовет штатно.

## Финальная мысль

DOP учит смотреть на программу как на набор операций над данными, а не только
как на поток инструкций. Этот взгляд полезен и защитнику: он показывает, что CFI
защищает лишь одну грань, а целостность данных не менее важна. Для атакующего DOP
— запасной путь, который работает там, где control-flow закрыт.

работать с нашими данными — поэтому CFI его не видит**.
