## Вопрос, с которого всё начинается

Ты нашёл переполнение стека в Windows-приложении. DEP включён — исполнять
shellcode со стека нельзя. Нужен **ROP**: собрать цепочку из кусочков
существующего кода. Но в Windows соглашение вызова **другое**, чем в Linux, и
привычные гаджеты `pop rdi` бесполезны. Разберём, как строить ROP под Windows
x64.

## Наш пример

Выдержка поиска гаджетов:

```
$ cat ropgadget.txt
0x0000000140001000 : pop rax ; ret
0x0000000140001010 : pop rbx ; ret
0x0000000140001234 : pop rcx ; ret
0x0000000140001240 : pop rdx ; ret
0x0000000140001250 : pop r8 ; ret
0x0000000140001260 : pop r9 ; ret
0x0000000140001270 : add rsp, 0x28 ; ret
```

Первый аргумент Windows x64 передаётся в `rcx`, поэтому нам нужен `pop rcx`.
Разберём, почему и как это собирается в цепочку.

## Шаг 1: соглашение вызова Windows x64

Windows использует **Microsoft x64 calling convention**:

- целочисленные аргументы 1–4: `RCX`, `RDX`, `R8`, `R9`;
- аргументы 5+: на стеке, справа налево;
- **возвращаемое значение**: `RAX`;
- **volatile** (не сохраняются): `RAX, RCX, RDX, R8-R11`;
- **non-volatile**: `RBX, RBP, RDI, RSI, R12-R15` — вызываемый обязан сохранить.

Сравни с Linux (System V): там аргументы в `RDI, RSI, RDX, RCX, R8, R9`. В
Windows `RDI`/`RSI` вообще не используются для аргументов — они non-volatile.
Поэтому гаджеты ищем именно под `RCX`, `RDX`, `R8`, `R9`.

## Шаг 2: shadow space — обязательный зазор

Перед каждым `call` вызывающий обязан зарезервировать **32 байта** на стеке —
**shadow space** (home space) для callee. Это место, куда вызываемая функция
может «сбросить» первые четыре аргумента. Даже если аргумент в регистре,
зазор обязан быть.

Практическое следствие для ROP: при вызове функции через цепочку нужно, чтобы
`RSP` указывал на корректно выровненный стек с зазором. Часто для этого
используют гаджет вида `add rsp, 0x28 ; ret` (32 байта зазора + 8 на адрес
возврата) или `pop`-гаджеты, которые сдвигают стек на нужное число.

## Шаг 3: выравнивание стека

Windows x64 требует, чтобы `RSP` был **16-байтово выровнен** перед `call`
(точнее, на входе в функцию `RSP % 16 == 8` из-за адреса возврата). Если
выравнивание сбито, функции, использующие SSE (`movaps`), упадут на
невыровненном обращении.

Поэтому в цепочку добавляют **выравнивающие гаджеты** (`ret` без действия или
`add rsp, 8 ; ret`), чтобы подогнать `RSP`. Это одна из самых частых причин
«цепочка правильная, а падает» — забыли про выравнивание.

## Шаг 4: где искать гаджеты

Источники гаджетов:

- **модуль программы** (`challenge.exe`) — если ASLR сломан или база утекла;
- **системные DLL** (`ntdll.dll`, `kernel32.dll`, `kernelbase.dll`) — большие,
  много гаджетов;
- **`ntoskrnl.exe`** — для kernel-mode цепочек.

Инструменты: `ROPgadget`, `ropper`, `rp++`. Для Windows удобно искать гаджеты,
заканчивающиеся на `ret`, `jmp`, а также «поп-поп-рет» под нужные регистры.

## Шаг 5: цель цепочки

Классика на Windows — вызвать `VirtualProtect`, чтобы сделать область памяти
исполняемой, и прыгнуть в shellcode. Сигнатура:

```
BOOL VirtualProtect(LPVOID lpAddress, SIZE_T dwSize,
                    DWORD flNewProtect, PDWORD lpflOldProtect);
```

Аргументы идут в `RCX, RDX, R8, R9`. Значит, цепочка:

1. `pop rcx ; ret` → адрес области;
2. `pop rdx ; ret` → размер;
3. `pop r8 ; ret`  → `PAGE_EXECUTE_READWRITE` (0x40);
4. `pop r9 ; ret`  → адрес для старого флага;
5. вызов `VirtualProtect`;
6. переход в shellcode.

В нашей выдержке есть все четыре гаджета — цепочка собирается.

## Шаг 6: SEH и «безопасный» стек

В 32-битном Windows исторически эксплуатировали **SEH** (Structured Exception
Handling): перезаписывали обработчик исключения. Современный **SafeSEH** и
`/GS` это закрывают. В x64 SEH реализован иначе (таблицы), и классический
SEH-overwrite не работает — поэтому в x64 основной путь именно ROP.

Также есть **stack cookies** (`/GS`): канарейка перед сохранённым `RIP`.
Её нужно утекать или обходить (перезапись обработчика до проверки, частичное
переполнение и т.п.).

## Шаг 7: последовательность сборки

1. **Утечка** базы модуля (обход ASLR) — иначе адреса гаджетов неизвестны.
2. **Определи смещение** до `RIP` (pattern, отладчик).
3. **Собери гаджеты**: pop rcx/rdx/r8/r9 + вызов + выравнивание.
4. **Учти shadow space** и 16-байтовое выравнивание.
5. **Проверь** в отладчике: `RSP` перед `call`, содержимое регистров.
6. **Прыгни** в shellcode после `VirtualProtect`.

## Отладка ROP-цепочки в отладчике

Собрать цепочку «на бумаге» мало — её надо увидеть. В Windows удобны `WinDbg`
(kernel и user) и `x64dbg` (userland). Порядок:

1. Запусти цель под отладчиком с включённым **page heap**, если доступно.
2. Найди точку переполнения: заполни буфер циклическим паттерном
   (`pattern create 500`) и посмотри, какие 8 байт попали в `RIP`.
3. Вычисли **смещение** до адреса возврата: `pattern offset <значение>`.
4. Поставь breakpoint на `ret` и посмотри `RSP` — там начнётся цепочка.
5. Шагай (`t`) по гаджетам и проверяй регистры.

```
0:000> g
(1f30.2a4c): Access violation - code c0000005 (first chance)
rax=4141414141414141 rbx=0000000000000000 rcx=4141414141414141
rip=4141414141414141 rsp=000000000014f8f0 rbp=0000000000000000
```

`RIP = 0x4141414141414141` означает, что мы управляем адресом возврата. Теперь
важно не ошибиться с выравниванием: в момент `call` в цепочке `RSP % 16` должен
быть равен 8 (на входе функции). Если это не так — добавь выравнивающий `ret`.

## Где искать гаджеты на практике

Гаджеты ищут в **загруженных модулях**. Для пользовательского эксплойта это:

- сам `.exe` — если ASLR сломан или база утекла;
- `ntdll.dll`, `kernelbase.dll`, `kernel32.dll` — всегда загружены и огромны;
- `msvcrt.dll` — старые сборки.

```
$ ropper --file ntdll.dll --search "pop rcx; ret"
0x0000000180001234: pop rcx; ret;
```

Учитывай, что `ntdll`/`kernelbase` имеют **разные версии** на разных сборках
Windows: адрес гаджета из твоей лабораторной машины не совпадёт с целью. Поэтому
цепочку лучше строить **относительно базы** модуля, которую узнаём утечкой, а
не хардкодить абсолютные адреса.

## Сравнение Windows и Linux ROP

| Аспект | Windows x64 | Linux x64 |
|---|---|---|
| Аргументы 1–4 | `RCX, RDX, R8, R9` | `RDI, RSI, RDX, RCX` |
| Shadow space | 32 байта обязательны | нет |
| Выравнивание | 16 байт (`RSP%16==8` на входе) | 16 байт (на `call`) |
| Возврат значения | `RAX` | `RAX` |
| Volatile | `RAX,RCX,RDX,R8-R11` | `RAX,RCX,RDX,RSI,RDI,R8-R11` |
| Основной путь | `VirtualProtect` + shellcode | `execve`/`system` |

Это объясняет, почему Linux-гаджет `pop rdi ; ret` бесполезен на Windows:
`RDI` там **non-volatile**, и компилятор редко оставляет его в начале функций.
Ищи именно `pop rcx`/`pop rdx`/`pop r8`/`pop r9`.

## Частые ошибки

- **Забыли shadow space.** Функция пишет в зазор, которого нет → падение.
- **Неверное выравнивание.** `movaps` падает на нечётном `RSP`.
- **Хардкод адресов.** На другой сборке цепочка не работает — считай от базы.
- **Гаджеты с `jmp` вместо `ret`.** Ломают линейность цепочки.
- **Неправильный размер буфера.** Переполнение «не дотягивается» до `RIP`.
- **NUL-байты в payload.** Некоторые копирующие функции обрежут строку.

Проверяй каждый шаг в отладчике: один неверный адрес — и ты не поймёшь, где
именно цепочка рассыпалась.

## Практический рецепт

1. Определи **смещение** до адреса возврата паттерном.
2. Утеки **базу модуля** (см. следующий урок).
3. Найди гаджеты `pop rcx/rdx/r8/r9` и вызов `VirtualProtect`.
4. Собери цепочку: аргументы → `VirtualProtect` → адрес shellcode.
5. Добавь **выравнивание** и **shadow space**.
6. Прогони под отладчиком, поправь `RSP`.
7. Положи shellcode (например, `WinExec('calc')` для проверки).

## Полный пример цепочки

Представим, что мы сделали память исполняемой через `VirtualProtect` и хотим
вызвать её. В байтах цепочка выглядит так (адреса условные, считаем от базы):

```
[RSP+0x00] pop rcx ; ret        ; адрес области (lpAddress)
[RSP+0x08] <адрес области>
[RSP+0x10] pop rdx ; ret        ; размер (dwSize)
[RSP+0x18] 0x1000
[RSP+0x20] pop r8 ; ret         ; flNewProtect = PAGE_EXECUTE_READWRITE
[RSP+0x28] 0x40
[RSP+0x30] pop r9 ; ret         ; lpflOldProtect (любой writable адрес)
[RSP+0x38] <адрес для старого флага>
[RSP+0x40] <адрес VirtualProtect>
[RSP+0x48] <адрес shellcode>   ; куда вернёмся после вызова
```

Важные детали: между адресом `VirtualProtect` и shellcode может понадобиться
**выравнивающий** гаджет, чтобы `RSP` был кратен 16. Без него `movaps` внутри
функции уронит процесс.

## Работа с паттерном

Точное смещение до `RIP` находят циклическим паттерном. В `x64dbg`:

```
pattern create 500        ; получить строку из уникальных 8-байтовых кусков
run                       ; упасть
pattern offset <RIP>      ; узнать смещение
```

В `pwntools` для Windows-целей удобно генерировать паттерн заранее и смотреть,
какие 8 байт попали в регистр. Ошибка в смещении — самая частая причина «цепочка
не запускается».

## Простой shellcode для проверки

Прежде чем писать полноценный payload, проверь исполнение примитивом:

```asm
; WinExec('calc', SW_SHOWNORMAL) — проверка, что управление дошло
sub rsp, 0x28
xor rcx, rcx
mov rcx, 0x636c6163       ; 'calc'
push rcx
mov rcx, rsp
mov rdx, 1
mov rax, <WinExec>
call rax
```

Если открылся калькулятор — цепочка верна. Дальше заменяешь payload на нужный
(например, запуск reverse shell). Такой «калькулятор» — стандартный smoke-test
Windows-эксплойта.

## Что мы теперь знаем

- Windows x64: аргументы в `RCX, RDX, R8, R9`.
- Перед `call` нужен shadow space (32 байта).
- `RSP` должен быть выровнен на 16 байт.
- Гаджеты ищем в модуле и системных DLL.
- SEH в x64 не эксплуатируется как в x86 — основной путь ROP.
