## Вопрос, с которого всё начинается

Ты разбираешь баг в Rust-сервисе или C++-приложении, собранном с **mimalloc**.
Пытаешься применить технику с glibc — не работает: нет tcache, нет привычных
chunk'ов. Зато в отладчике видны «сегменты», «страницы» и странные «закодированные
указатели». Разберём mimalloc и его механизмы.

## Наш пример

Метаданные сегмента:

```
$ cat segment.txt
segment: base=0x7f0000000000 size=0x4000000
  page_size=0x10000  pages=1024
  page[0]: state=usable block_size=0x30 free=0
```

Сегмент — крупный регион, внутри которого страницы по `0x10000` (64 КБ). Каждая
страница обслуживает блоки одного размера. Разберём модель.

## Шаг 1: сегменты и страницы

mimalloc организует память в два уровня:

- **сегмент** — большой регион адресного пространства (десятки мегабайт),
  выровненный по своему размеру;
- **страница** (page) — блок внутри сегмента (обычно 64 КБ), нарезанный на
  объекты одного размера.

Выделение идёт так: находим страницу с нужным размером блока, берём из неё
свободный объект. Страницы одного размера связаны в список, чтобы быстро находить
подходящую.

## Шаг 2: thread-local heaps

mimalloc использует **thread-local heaps (TLH)**: у каждого потока свои структуры
для быстрой аллокации без блокировок. Когда поток освобождает объект, он может
вернуть его в **thread-free list** — локальный список, который периодически
сливается с общим списком страницы.

Следствие для эксплуатации: свежеосвобождённый объект может остаться в
thread-free list и не сразу стать доступным для переиспользования. Это влияет на
тайминг UAF-атак — как карантин, но короче.

## Шаг 3: free-list sharding

**Free-list sharding** — ключевая идея mimalloc. Вместо одного глобального списка
свободных объектов на всю кучу, свободные объекты распределены по
**множеству списков** (shards):

- у каждой страницы свой список свободных объектов (`free`);
- плюс локальный список потока (`local_free`);
- плюс thread-free list.

Это снижает конкуренцию между потоками, но усложняет атаку: нельзя «зацепиться»
за один глобальный freelist. Приходится разбираться, в каком именно списке
оказался целевой объект.

## Шаг 4: кодирование указателей

Свободные объекты в списках связаны указателями. mimalloc **кодирует** эти
указатели: значение получается операцией XOR с адресом самого объекта (и/или
случайным ключом). Это защита от наивной подмены.

Чтобы подменить указатель freelist, нужно:

- знать **адрес объекта** (для XOR);
- при некоторых конфигурациях — **случайный ключ** кодирования.

Без утечки подделка не сработает: при декодировании получится мусор.

## Шаг 5: состояния страниц

Страница mimalloc находится в одном из состояний: `free`, `usable`, `full` и
т.п. Переходы между состояниями — важная часть логики. Баги часто связаны с
рассинхронизацией состояния: страница помечена `free`, но ещё используется
(UAF), или помечена `usable`, хотя все объекты заняты.

## Шаг 6: где искать примитивы

1. **UAF** — объект освобождён, указатель жив; переиспользование даёт тот же
   адрес (с учётом thread-free list).
2. **Порча данных объекта** — указатель, длина, флаг внутри объекта.
3. **Порча freelist-указателя** — только при наличии утечки для обхода
   кодирования.
4. **Логические баги** — не зависят от аллокатора.

## Шаг 7: собираем тактику

1. Определи mimalloc (символы `mi_`, поведение).
2. Уточни размер блока и страницу целевого объекта.
3. Проверь кодирование указателей (нужна ли утечка).
4. Целься в данные объекта или в freelist при наличии утечки.
5. Учти thread-free list при планировании UAF.

## Шаг 8: сравнение с другими аллокаторами

- **glibc:** один глобальный набор bin'ов, заголовки в блоках.
- **mimalloc:** множество shard'ов + кодирование + thread-local heaps —
  распределённая модель, сложнее для атаки.
- **PartitionAlloc:** партиции по назначению + MiraclePtr.
- **hardened_malloc:** изоляция + guard-страницы.

Каждый следующий — жёстче; mimalloc занимает «серьёзный, но не крайний» уровень.

## Как это выглядит в реальном эксплойте

Цепочка против mimalloc:

1. **Разогрев страницы.** Выделяем много объектов нужного размера, чтобы страница
   заполнилась и раскладка стала предсказуемой.
2. **Триггер.** Освобождаем объект, сохраняя указатель (UAF), или переполняем в
   соседний объект той же страницы.
3. **Учёт thread-free list.** Ждём (или форсируем) слив локального списка, чтобы
   объект стал доступен для переиспользования.
4. **Порча.** Пишем в тело объекта (указатель/длину) либо, при утечке, в
   freelist-указатель.
5. **Примитив и побег.** R/W → обход ASLR → ROP/privesc.

## Частые ошибки

- **Искать единый freelist.** Его нет — списки шардированы по страницам и потокам.
- **Подменять указатель без утечки.** Кодирование не даст корректно декодировать.
- **Игнорировать thread-free list.** UAF может «не переиспользоваться» сразу.
- **Путать состояния страниц.** Баг в состоянии (`free` vs `usable`) — отдельный
  класс уязвимостей.

## mimalloc в Rust и Go

mimalloc часто встречается в **Rust**- и **C++**-сервисах (его легко подключить
как глобальный аллокатор) и в приложениях Microsoft. В Rust это задаётся атрибутом
`#[global_allocator]`; тогда весь `Box`/`Vec` идёт через mimalloc. В Go —
собственный аллокатор, но некоторые C-компоненты могут использовать mimalloc.

Практический вывод: увидев Rust-сервис, не предполагай glibc — проверь, какой
аллокатор подключён. От этого зависит, применима ли твоя техника.

## Что мы теперь знаем

- mimalloc организует память сегментами и страницами (обычно 64 КБ).
- Свободные объекты распределены по множеству списков (free-list sharding).
- Указатели freelist кодируются — подмена требует утечки.
- thread-local heaps и thread-free list влияют на тайминг UAF.
- Состояния страниц — источник логических багов.

## Куда дальше

На этом блок серверных/браузерных аллокаторов завершён. Дальше — **ядра других
ОС** (macOS/XNU, iOS, Android, FreeBSD) и **KASLR bypass**. А пока главное: **в
mimalloc свободные объекты распределены по спискам с кодированием — целься в
данные объекта или добывай утечку**.
