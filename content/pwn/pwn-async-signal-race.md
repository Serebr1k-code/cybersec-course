Сигналы асинхронны: они прерывают поток исполнения в произвольный момент. Если обработчик вызывает функцию, не безопасную в контексте сигнала (не async-signal-safe), или работает с общим состоянием, которое основной поток меняет параллельно, возникает гонка. В pwn это превращается в эксплуатируемый примитив: атакующий может «поймать» программу в нужный момент и подменить данные.

В этом уроке — типичные схемы: `SIGALRM`-таймеры, `setjmp`/`longjmp` из обработчика, небезопасные `malloc`/`printf` внутри обработчика и подмена состояния между доставкой сигналов.

## Почему сигналы создают гонки

Обработчик сигнала выполняется в том же потоке, прерывая основную логику. POSIX определяет список async-signal-safe функций — тех, которые можно вызывать из обработчика. Всё остальное (`malloc`, `free`, `printf`, `syslog`) небезопасно: оно может держать внутренний lock, который прервал сам сигнал, и привести к deadlock или порче структур.

Атака строится на том, что:

- обработчик видит частично обновлённое состояние;
- `longjmp` из обработчика возвращает управление в сохранённый `setjmp`, обходя cleanup;
- повторный вход (re-entrancy) в небезопасную функцию ломает её внутренние структуры.

## Типовые паттерны уязвимости

| Паттерн | Проблема | Примитив для атакующего |
|---|---|---|
| `SIGALRM` + `setjmp`/`longjmp` | выход из середины операции | обход проверки/очистки |
| `malloc` в обработчике | re-entrancy кучи | порча heap-метаданных |
| общий флаг без `volatile sig_atomic_t` | компилятор кэширует значение | логический обход |
| `printf` в обработчике | lock на stdout | deadlock / частичный вывод |
| запись в буфер из обработчика | TOCTOU | подмена данных |

## Инструменты и команды

```bash
# посмотрим, какие обработчики ставит бинарь
objdump -d ./chall | grep -E "sigaction|signal@plt|sigemptyset|sigaddset"

# найдём вызовы alarm/setitimer (источник SIGALRM)
objdump -d ./chall | grep -E "alarm@plt|setitimer@plt|ualarm"

# проверим setjmp/longjmp
objdump -d ./chall | grep -E "setjmp|longjmp|__sigsetjmp|__longjmp"

# в gdb: трассируем доставку сигналов
gdb -q ./chall
(gdb) handle SIGALRM stop print
(gdb) run
(gdb) bt          # кто прерван
(gdb) info registers rip
```

Флаг `handle SIGALRM stop print` заставляет gdb останавливаться на каждом сигнале — это позволяет увидеть, в какой точке прерывается основной поток. Полезно сравнить `bt` в момент сигнала и после возврата из обработчика.

## Разобранный пример: обход проверки через longjmp

Классика CTF: программа проверяет пароль, а по `SIGALRM` из обработчика делает `longjmp` в сохранённую точку, минуя сброс привилегий.

```c
jmp_buf env;
void handler(int sig) { longjmp(env, 1); }

int main(void) {
    char buf[64];
    if (setjmp(env) == 0) {
        signal(SIGALRM, handler);
        alarm(3);
        read(0, buf, 256);        // переполнение, если не сработал таймер
    } else {
        // сюда прыгает обработчик, buf уже переполнен
        system(buf);
    }
}
```

Атака: отправляем переполняющий ввод, но так, чтобы `alarm` сработал **после** записи в `buf`. Обработчик делает `longjmp`, и управление попадает в ветку `else`, где `buf` уже под нашим контролем.

```python
from pwn import *
io = process('./chall')
payload = b'/bin/sh\x00' + b'A'*56
io.send(payload)
# ждём SIGALRM (3 сек), затем longjmp -> system(buf)
io.interactive()
```

Ожидаемый результат:

```
[*] Waiting for SIGALRM...
$ id
uid=1000(user) gid=1000(user)
```

## Расширение окна гонки

Если окно узкое, его расширяют детерминированно:

- **Задержка ввода.** Отправляйте данные частями, чтобы удержать программу в нужной точке.
- **`userfaultfd`.** Для kernel- и некоторых user-space-целей — заморозить поток на page fault (см. `pwn-race-widening`).
- **Многократные попытки.** Оберните эксплойт в цикл: `for i in range(1000): try:`.
- **`sched_setaffinity`.** Привязать потоки к ядрам, чтобы стабилизировать планировщик.
- **`LD_PRELOAD`.** Перехватить `alarm`/`read` в тестовом окружении и управлять таймингом.

## Async-signal-safety на практике

Список async-signal-safe функций (`signal-safety(7)`) включает `read`, `write`, `open`, `close`, `_exit`, `kill`. Не входят `malloc`, `free`, `printf`, `fprintf`, `syslog`, `strtok`. Если обработчик вызывает небезопасную функцию, а основной поток в этот момент держит её внутренний lock — возможен deadlock. Атакующий может намеренно вызвать такую ситуацию и использовать зависание как побочный канал или как окно для второй операции.

Например, обработчик `SIGALRM`, который печатает отладочное сообщение через `printf`, может зависнуть, если сигнал прервал основной поток ровно внутри `printf` (тот держит lock на `stdout`). Для эксплуатации это иногда полезно: зависший поток перестаёт менять состояние, и атакующий получает стабильное окно. В других случаях deadlock мешает — тогда обработчик нужно спроектировать на `write(2)`.

Отдельно стоит помнить про `errno`: обработчик сигнала обязан сохранять и восстанавливать `errno`, иначе он «протечёт» в основной поток и сломает логику. Ошибки такого рода часто приводят к неочевидным багам, которые и эксплуатируются как логические уязвимости.

Ещё один тонкий момент — реентерабельность и глобальные буферы. Если обработчик и основной поток используют один и тот же статический буфер (например, возвращаемый `strerror` или `inet_ntoa`), сигнал в середине заполнения буфера оставит его в неконсистентном состоянии. Атакующий может этим воспользоваться, чтобы подсунуть строку, которая затем интерпретируется как путь к файлу или команда. Ищите глобальные буферы, к которым обращаются и обработчик, и основной код, — это верный признак уязвимости.

## Пример: перехват SIGSEGV и повторный вход

Некоторые программы устанавливают обработчик `SIGSEGV` для «мягкой» обработки ошибок (например, JIT-движки, сборщики мусора, эмуляторы). Это создаёт управляемую среду: атакующий намеренно вызывает падение, обработчик делает `longjmp` в цикл, а программа продолжает работу в полуразрушенном состоянии.

```c
static jmp_buf recover;
void segv_handler(int sig, siginfo_t *si, void *ctx) {
    // «восстановление» без сброса состояния
    longjmp(recover, 1);
}
```

Атака: спровоцировать `SIGSEGV` в момент, когда внутренние структуры частично обновлены, и воспользоваться тем, что обработчик не сбрасывает их. Это классическая уязвимость «восстановление после падения без очистки». В pwn её используют, чтобы обойти проверку: падение происходит после того, как флаг уже выставлен, а `longjmp` возвращает в точку, где флаг считается доверенным.

## Стабилизация нестабильного эксплойта

Гонки почти никогда не срабатывают с первого раза. Практические приёмы стабилизации:

- **Цикл попыток с перезапуском.** `for _ in range(500): io = process(...); try: exploit(); break; except EOFError: continue`.
- **Разделение этапов.** Сначала добиться нужного состояния (проверить, что сигнал доставлен), и только потом делать второй шаг.
- **Точная синхронизация по выводу.** `io.recvuntil(b'> ')` вместо фиксированных задержек.
- **Управление таймером.** Если есть `alarm`, подберите размер ввода так, чтобы запись завершалась прямо перед срабатыванием.
- **Логирование.** Сохраняйте, на какой попытке сработало, — это подсказывает направление оптимизации.

Если гонка не срабатывает после сотен попыток, вероятно, окно слишком узкое или вы неверно поняли порядок операций. Тогда переходите к `pwn-race-widening` (userfaultfd/FUSE) или меняйте вектор.

## Связь с TOCTOU и файловыми дескрипторами

Сигналы часто сочетаются с файловыми операциями. Классический сценарий: обработчик по таймеру закрывает или переоткрывает файл, а основной поток в это же время читает из него. Между проверкой (`fstat`) и использованием (`read`) дескриптор подменяется — это TOCTOU в чистом виде. Если программа работает от повышенных привилегий, такая гонка может позволить прочитать файл, недоступный пользователю.

Другой распространённый паттерн — `SIGCHLD` и повторное использование PID. Программа запускает дочерний процесс, ждёт его завершения, а обработчик `SIGCHLD` (или его отсутствие) приводит к тому, что `waitpid` вызывается по устаревшему PID. Злоумышленник выигрывает гонку и заставляет программу «подождать» чужой процесс или послать сигнал не тому адресату.

С точки зрения эксплуатации важно: сигналы — это **асинхронные точки**, которые ломают вашу ментальную модель последовательного кода. Всегда спрашивайте себя: «что произойдёт, если между этими двумя строками доставится сигнал?». Если ответ — «состояние будет частично обновлено», перед вами кандидат на гонку.

## Частые ошибки

- **Игнорировать `volatile sig_atomic_t`.** Без него компилятор кэширует флаг, и гонка «не воспроизводится».
- **Ставить breakpoint внутри обработчика.** Это меняет тайминг и маскирует гонку.
- **Забыть про маскирование сигналов.** `sigprocmask` может блокировать сигнал в критической секции — тогда окно закрыто.
- **Слишком быстрый эксплойт.** Иногда нужно намеренно замедлить отправку, чтобы сигнал успел доставиться.
- **Не учитывать `SA_RESTART`.** С `SA_RESTART` прерванный `read` перезапускается, без него — возвращает `EINTR`.

## Что дальше / решение

- Перейдите к модулю `pwn-race-conditions` для системного разбора гонок.
- Изучите `pwn-race-widening` — `userfaultfd` и FUSE.
- Для kernel-гонок смотрите `pwn-kernel-userfaultfd`.
- Свяжите с `pwn-signal-frame-forgery`: `longjmp` — родственник `setcontext`.
