## Вопрос, с которого всё начинается

Программа запускает два потока, и оба меняют одну переменную. Ты ожидаешь, что результат будет «суммой», но получаешь меньше. Это **data race** — гонка данных. В pwn гонки опаснее: если два потока одновременно работают с **кучей**, можно получить **double-free** и, как следствие, произвольную запись. В этом уроке разберём и то, и другое.

## Наш пример

Вот программа `race` с двумя потоками, каждый увеличивает общий счётчик 100000 раз:

```c
int counter = 0;
void *worker(void *arg) {
    for (int i = 0; i < 100000; i++) counter++;
    return 0;
}
int main() {
    pthread_create(&t1, 0, worker, 0);
    pthread_create(&t2, 0, worker, 0);
    pthread_join(t1, 0); pthread_join(t2, 0);
    printf("counter=%d (expected 200000)\n", counter);
}
```

Ожидаем 200000. Запускаем трижды:

```
$ ./race
counter=106340 (expected 200000)
counter=109697 (expected 200000)
counter=121499 (expected 200000)
```

Каждый раз — разное и **меньше** ожидаемого. Программа теряет обновления.

## Шаг 1: почему счётчик теряет значения

Инструкция `counter++` на уровне процессора — это **три шага**: прочитать `counter` в регистр, увеличить, записать обратно. Если два потока делают это одновременно:

1. Поток A читает `counter = 5`.
2. Поток B тоже читает `counter = 5` (не успел увидеть запись A).
3. A пишет `6`.
4. B пишет `6`.

Два «плюс один» дали один прирост. Это и есть **гонка данных**: результат зависит от **порядка** доступа к общей памяти, а порядок непредсказуем.

Лечение в обычном коде — **мьютекс** (взаимное исключение) или атомарные операции. Но нас интересует, как из гонки сделать эксплойт.

## Шаг 2: гонка на куче — double-free

Куда опаснее гонка, когда два потока одновременно работают с **одним и тем же объектом** в куче. Типичный сценарий:

- **Поток A** и **поток B** имеют доступ к одному указателю (например, разделяемая структура).
- Оба одновременно вызывают `free(ptr)` — **double-free**.
- Двойное освобождение ломает списки свободных chunk: один и тот же chunk попадает в tcache дважды.
- Дальше два `malloc` возвращают **один и тот же адрес** — и мы можем перезаписать его, пока «второй владелец» думает, что владеет им.

Это классический путь: **гонка → double-free → overlapping chunks → произвольная запись**.

Важно: tcache в glibc **не защищён от гонок** сам по себе (в старых версиях), и два потока могут «проскочить» проверку ключа, если успеют одновременно.

## Шаг 3: где ещё гонки бьют по pwn

- **Race на указателе.** Один поток проверяет `ptr != NULL`, другой в это время освобождает и обнуляет — и мы используем освобождённый объект (UAF).
- **Race на длине/размере.** Проверили размер буфера, а между проверкой и `memcpy` его изменили — переполнение.
- **Race на fd.** Закрыли дескриптор, а другой поток читает/пишет в переиспользованный номер.
- **Race на счётчике ссылок.** Refcount-баг: объект освобождён, пока «кто-то ещё держит ссылку».

Общий признак: **разделяемое изменяемое состояние без синхронизации**.

## Шаг 4: как находить гонки

Руками гонку почти не поймать — нужны инструменты:

- **ThreadSanitizer (TSan).** Собери с `-fsanitize=thread` — он сообщает о гонках доступа к памяти с точным местом:
  ```
  $ gcc -fsanitize=thread race.c -o race_tsan && ./race_tsan
  WARNING: ThreadSanitizer: data race
    Write of size 4 at ... by thread T2:
      #0 worker race.c:2
    Previous write of size 4 at ... by thread T1:
      #0 worker race.c:2
  ```
- **Valgrind --tool=helgrind.** Аналог для тех же целей.
- **Фаззинг с потоками.** Специализированные фаззеры гонок воспроизводят сценарии многократно.
- **Анализ кода.** Ищи общий доступ без блокировки.

Отдельно стоит упомянуть **гонки на указателях**: один поток проверяет `ptr`, другой обнуляет его — и проверка «проходит» для уже освобождённого объекта. Такие баги дают UAF без double-free и часто встречаются в коде с ленивой инициализацией. Лечится это либо блокировкой вокруг проверки и использования, либо атомарными операциями (`atomic_compare_exchange`).

TSan — первый инструмент: он показывает **обе** конфликтующие операции и стек.

## Шаг 5: стабилизация гоночного эксплойта

Гонка нестабильна. Чтобы эксплойт срабатывал надёжно:

- **Повторяй.** Оберни атаку в цикл на тысячи итераций; успех рано или поздно придёт.
- **Синхронизируй потоки.** Используй барьеры/`pthread_barrier`, чтобы оба потока дошли до опасной точки одновременно.
- **Привязка к ядрам.** `sched_setaffinity` — уменьшает шум планировщика.
- **Расширяй окно.** `userfaultfd`, `FUSE`, `mprotect` — отдельный урок про это.
- **Проверяй успех.** После каждой попытки определяй, «сработало ли» (например, изменился ли нужный байт), и повторяй при неудаче.

Опытные эксплуататоры часто пишут «стабилизирующий цикл»: запускать гонку, пока не получится нужный эффект, с фиксацией промежуточного состояния.

## Шаг 6: гонка на tcache — пошагово

Разберём, как гонка превращается в эксплойт, на конкретном примере. Есть объект, на который ссылаются два потока:

1. **Поток A** вызывает `free(ptr)` и начинает выполнять внутренности `free` (кладёт chunk в tcache).
2. **Поток B**, не дождавшись, тоже вызывает `free(ptr)` для того же указателя — пока A ещё не закончил, `ptr` ещё не «помечен» как освобождённый.
3. Оба освобождения «проходят» — chunk попадает в tcache **дважды**.
4. Теперь `malloc()` вернёт этот chunk один раз (A), а следующий `malloc()` — **тот же самый** (B). У нас два «разных» объекта по одному адресу.
5. Пишем в один — меняем другой. Через аккуратную перезапись поля `next` получаем **произвольную запись**.

Ключ — синхронизация: нужно, чтобы B вошёл в `free` **между** началом и концом `free` у A. Именно для этого окно расширяют `userfaultfd` (следующий урок).

Ещё вариант — **race на refcount**: объект освобождается, пока другой поток ещё «держит ссылку». Это тоже даёт UAF без явного double-free. Refcount-баги особенно коварны: код выглядит корректным, но при определённом чередовании счётчик достигает нуля раньше времени. Именно поэтому refcount-ошибки годами живут в ядрах и браузерах.

## Что мы теперь знаем

- **Data race** — результат зависит от порядка доступа потоков к общей памяти.
- `counter++` не атомарен: read-modify-write теряет обновления.
- Опаснее всего гонки на **куче**: double-free → overlapping chunks → произвольная запись.
- Находить гонки помогают **TSan** и Helgrind.
- Гоночный эксплойт **стабилизируют**: повтор, барьеры, привязка к ядрам, расширение окна.

## Куда дальше

Мы разобрали гонки между потоками. Дальше — **расширение окна гонки**: как детерминированно «растянуть» момент между проверкой и использованием через `userfaultfd`, `FUSE` и планировщик. А пока запомни главное: **разделяемое состояние без синхронизации — это гонка, а гонка на куче — это double-free.**
