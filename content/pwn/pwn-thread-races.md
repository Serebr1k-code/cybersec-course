Многопоточность превращает гонки из «успей подменить файл» в полноценный класс эксплуатируемых багов. Два потока, обращающихся к общим данным без синхронизации, дают атакующему контроль над промежуточными состояниями: двойное освобождение одного чанка, переиспользование указателя после free, инкремент, который теряется. В modern glibc гонки на tcache особенно ценны — они позволяют обойти проверки, рассчитанные на однопоточный сценарий.

В этом уроке — модель гонок между потоками, гонки на куче, инструменты обнаружения и полный многопоточный эксплойт с оценкой надёжности.

## Гонки между потоками: модель

Потоки одного процесса разделяют адресное пространство: глобальные переменные, кучу, файловые дескрипторы. Локальные переменные и стек — свои у каждого потока. Гонка возникает, когда два потока обращаются к одному объекту и хотя бы один пишет, а синхронизации нет.

Критические секции защищают мьютексами (`pthread_mutex_lock`), но ошибки случаются:

- забыли захватить мьютекс на одном из путей;
- захватили разные мьютексы на один объект;
- использовали `pthread_mutex_trylock` и проигнорировали отказ;
- освободили объект, пока другой поток ещё держит указатель (use-after-free между потоками).

## Data race и модель памяти

Формально data race — это несинхронизированный доступ к одной ячейке, где хотя бы один доступ — запись. В C/C++ это undefined behavior: компилятор вправе кэшировать значения в регистрах, переставлять обращения, «оптимизировать» проверки. Отсюда классический баг:

```c
volatile int ready = 0;
void *worker(void *arg) {
    while (!ready) { }     // без volatile компилятор зациклит навсегда
    do_work();
    return NULL;
}
```

Без `volatile`/атомиков цикл может не заметить изменения. В pwn это используют двояко: либо баг создаёт зацикливание (отказ в обслуживании), либо, наоборот, гонка позволяет проскочить проверку `if (ready)` до того, как данные валидны.

На практике компиляторы агрессивно оптимизируют именно такие проверки. Сборка `-O2` может вынести чтение `ready` из цикла в регистр, и тогда поток никогда не увидит запись из другого потока. С точки зрения эксплуатации это означает, что поведение программы зависит от уровня оптимизации: то, что «работает» на `-O0`, может сломаться на `-O2` и наоборот. Всегда проверяйте, как собрана цель (`file`, наличие символов, `objdump`), и воспроизводите тайминг на той же сборке. Если гонка зависит от оптимизации, попробуйте обе крайности: релизную и отладочную.

## Гонки на куче и double-free между потоками

glibc `malloc`/`free` потокобезопасны (per-thread arenas, блокировки), но это не спасает от **логических** гонок. Пример: поток A делает `free(p)`, поток B в этот момент читает `p->data`. Между чтением и освобождением — UAF. Хуже: два потока одновременно освобождают один указатель, и в tcache образуется дубликат:

```c
// оба потока вызывают это с одним p
free(p);
```

tcache — LIFO-список; два `free(p)` подряд дают в списке `p -> p`. Следующие два `malloc` вернут один и тот же адрес — это классическое **tcache double-free**, дающее overlap без каких-либо дополнительных багов. В однопоточном коде glibc ловит двойное освобождение через `key` (tcache_key), но при гонке оба потока могут прочитать `key` до того, как он будет записан, и проверка пропустит дубликат.

## Инструменты и команды

```bash
# собрать с ThreadSanitizer
gcc -fsanitize=thread -g -O1 -pthread chall.c -o chall_tsan
./chall_tsan
# WARNING: ThreadSanitizer: data race ...

# Valgrind Helgrind / DRD
valgrind --tool=helgrind ./chall
valgrind --tool=drd ./chall

# в gdb: переключение между потоками
gdb -q ./chall
(gdb) set scheduler-locking on
(gdb) info threads
(gdb) thread 2
(gdb) bt

# трассировка клонирования потоков
strace -f -e trace=clone,clone3 ./chall 2>&1 | head
```

ThreadSanitizer (`-fsanitize=thread`) — самый быстрый способ найти data race в исходниках. Helgrind и DRD работают без пересборки, но медленнее. `set scheduler-locking on` в gdb замораживает остальные потоки — это позволяет изучать один поток, не теряя состояние от гонки.

## Разобранный пример: гонка на куче

```c
char *chunk;
void *thr(void *a) {
    free(chunk);          // поток освобождает
    return NULL;
}
int main(void) {
    chunk = malloc(0x40);
    pthread_t t;
    for (int i = 0; i < 100; i++) {
        pthread_create(&t, NULL, thr, NULL);
        // основной поток тоже освобождает тот же указатель
        free(chunk);
        pthread_join(t, NULL);
        chunk = malloc(0x40);   // перевыделяем
    }
}
```

Здесь `free(chunk)` в основном потоке и в `thr` выполняются параллельно — это гонка, которая с некоторой вероятностью даёт double-free. Эксплуатация:

```python
from pwn import *
context.log_level = 'error'
for attempt in range(1, 5000):
    io = process('./chall')
    try:
        io.recvuntil(b'> ')
        io.sendline(b'go')
        data = io.recv(timeout=1)
        if b'overlap' in data or b'win' in data:
            print(f"[+] hit on attempt {attempt}")
            io.interactive()
            break
    except EOFError:
        pass
    finally:
        io.close()
```

Ожидаемый вывод:

```
[+] hit on attempt 137
$ id
uid=1000(user) gid=1000(user)
```

## Стабилизация многопоточного эксплойта

Гонки нестабильны, и это нормально. Что помогает:

- **Много попыток.** 5000 попыток — обычное дело; оборачивайте в цикл с перезапуском процесса.
- **CPU affinity.** `os.sched_setaffinity(0, {0,1})` — привяжите процесс к двум ядрам, чтобы потоки гарантированно шли параллельно.
- **Синхронизация по выводу.** `recvuntil` вместо `sleep` — реагируйте на состояние, а не на время.
- **Усиление окна.** Вставьте в целевой код `sleep` (если контролируете) или используйте `userfaultfd` (`pwn-race-widening`).
- **Наблюдение.** Логируйте, на какой попытке сработало; если никогда — вы неверно поняли порядок.

Отдельно стоит учитывать, что при удалённой эксплуатации (по сети) тайминг непредсказуем, и гонку лучше стабилизировать на стороне цели, а не клиента. Если сервер обрабатывает соединения в отдельных потоках, попробуйте открыть несколько соединений одновременно: иногда это само по себе создаёт нужное перекрытие.

## Гонки на аренах malloc

Многопоточный `malloc` в glibc использует несколько арен, чтобы потоки не блокировали друг друга. Каждый поток при первом выделении привязывается к арене (обычно к той, что свободна). Это важно для grooming: чанки, выделенные в разных потоках, могут попасть в **разные** арены, и тогда вы не сможете «сшить» их в одну цепочку. В эксплойте либо заставляйте все потоки использовать одну арену (создавайте их заранее и ограничивайте число), либо учитывайте, что tcache всегда per-thread и не шарится между потоками.

Per-thread tcache — отдельная ловушка. Если поток A освободил чанк в свой tcache, поток B его не увидит, пока A не выйдет или tcache не переполнится (тогда чанки уйдут в общий fastbin/unsortedbin). Поэтому гонки, рассчитанные на общий tcache, часто «не работают» — потоки видят разные списки. Проверяйте, в каком потоке происходит free, и планируйте grooming соответственно.

## Пример: логический обход проверки через гонку

Гонки не всегда про память. Рассмотрим проверку «одноразового» действия:

```c
int used = 0;
void *handler(void *arg) {
    if (!used) {           // check
        used = 1;          // use
        grant_access();    // привилегированное действие
    }
    return NULL;
}
```

Два потока могут одновременно увидеть `used == 0` и оба выполнить `grant_access()` — это классический **race condition на флаге**. Если действие должно было произойти один раз (например, выдать уникальный токен или разблокировать функцию), повторное выполнение даёт атакующему лишний ресурс или обход лимита. В CTF такие задачи часто маскируются под «получите флаг только один раз».

Эксплуатация — запустить несколько потоков одновременно и надеяться, что хотя бы два проскочат проверку до записи. Для детерминизма можно использовать барьеры (`pthread_barrier`) в самом эксплойте, если целевой код их использует, или подобрать тайминг через CPU affinity. Логические гонки особенно ценны тем, что не требуют контроля над памятью — только над порядком исполнения.

## Частые ошибки

- **Одиночная попытка.** Гонка почти никогда не срабатывает с первого раза.
- **Отладка в gdb без `scheduler-locking`.** Отладчик меняет тайминг, и гонка «исчезает».
- **Забыть про арены.** В многопоточном malloc разные потоки могут получить разные арены; учитывайте это при grooming.
- **TSan на релизе.** Санитайзеры меняют тайминг; используйте их для **поиска**, а эксплойт отлаживайте на релизной сборке.
- **Игнорировать `pthread_join`.** Без join поток может завершиться раньше, чем вы ожидали.

## Что дальше / решение

- Освойте TSan/Helgrind для быстрого поиска гонок в исходниках.
- Перейдите к `pwn-race-widening` — `userfaultfd`/FUSE для детерминизма.
- Свяжите с `pwn-heap-tcache` и `pwn-tcache-mechanics` — гонки часто дают double-free.
- Для kernel-целей смотрите `pwn-kernel-userfaultfd` и `pwn-kernel-modern`.
