## Вопрос, с которого всё начинается

Ты уже знаешь переполнение буфера: пишешь больше, чем вмещает буфер, затираешь адрес возврата. Но что если функция просто **выделяет очень большой кадр на стеке** — и программа падает, хотя никакого «переполнения» ты не писал? А иногда — наоборот, не падает, а тихо портит память в соседнем регионе. Это класс уязвимостей **Stack Clash**. Разберём его на одном конкретном бинарнике.

## Наш пример

Вот программа `stackclash`: функция рекурсивно вызывает себя, и в каждом кадре лежит массив на 64 КБ.

```c
__attribute__((noinline)) void recurse(unsigned long n) {
    char pad[65536];          // 64 КБ на кадр
    pad[0] = (char)n;
    if (n > 0) recurse(n - 1);
}
int main(void) { recurse(200); }
```

Компилируем и запускаем:

```
$ gcc -fno-pie -no-pie -O0 stackclash.c -o stackclash
$ ./stackclash
Segmentation fault (core dumped)
```

Никакого `strcpy`, никакого ввода — просто большой кадр и рекурсия. Почему падает? Смотрим, где именно:

```
$ gdb -q -batch -ex run -ex bt ./stackclash
Program received signal SIGSEGV, Segmentation fault.
0x0000000000401131 in recurse ()
#0  0x0000000000401131 in recurse ()
#1  0x0000000000401162 in recurse ()
#2  0x0000000000401162 in recurse ()
rsp            0x7fffff7fd150
```

Мы упали на **очень низком** адресе стека (`0x7fffff7fd150` — почти у самого края). Это и есть Stack Clash.

## Шаг 1: стек растёт вниз, а под ним — guard-страница

Стек в Linux растёт **вниз**: каждый новый кадр функции уменьшает `rsp`. Ядро отдаёт программе не бесконечный стек, а ограниченный — по умолчанию 8 МБ:

```
$ ulimit -s
8192
```

За нижней границей стека лежит **guard-страница** — специальная страница, доступ к которой запрещён. Ядро использует её как «датчик»: когда `rsp` подходит слишком близко, обращение к guard-странице вызывает `SIGSEGV`, и ядро понимает, что пора либо **дорастить** стек (если есть куда), либо убить процесс.

Именно это мы и видим: 200 кадров × 64 КБ = больше 12 МБ, что превышает лимит 8 МБ, и рекурсия упёрлась в край стека.

## Шаг 2: как это превращается в атаку

Само по себе падение — не уязвимость. Уязвимость начинается там, где функция выделяет **одну большую область за раз**, а не растит стек по чуть-чуть. Посмотри на пролог нашей функции:

```
$ objdump -d -M intel stackclash | sed -n '/<recurse>:/,/^$/p'
0000000000401126 <recurse>:
  401126: push   rbp
  401127: mov    rbp,rsp
  40112a: sub    rsp,0x10010        ; сразу 64 КБ + 16
```

Компилятор сдвинул `rsp` **сразу** на `0x10010` байт. Ядро увеличивает стек не при каждом обращении, а по факту доступа: если между старым и новым `rsp` есть «дыра», туда может попасть другой регион памяти (например, куча через `mmap` или стек другого потока).

Классический сценарий (CVE-2017-1000364, «Stack Clash»):

1. В цикле вызываются функции, которые `alloca`-ят или объявляют **переменную длину массива (VLA)** — размер контролируется пользователем.
2. Стек сдвигается вниз **на несколько страниц сразу**, проскакивая guard-страницу.
3. В «дыру» ядро уже успело положить другую `mmap`-область (кучу, `ld.so`, стек потока).
4. Следующая запись в этот большой кадр **попадает в чужой регион** — это и есть *clash* (столкновение стека с кучей).

По сути ты получаешь запись по адресам вне своего стека, не имея классического переполнения буфера.

## Шаг 3: где встречается на практике

Stack Clash интересен тем, что он **обходит границы**: тебе не нужен баг `gets`/`strcpy`. Достаточно, чтобы программа делала большую стековую аллокацию по недоверенному размеру. Типичные места:

- **setuid-программы** (так классический Stack Clash давал локальное повышение привилегий): запись в чужой регион — это уже LPE.
- **Парсеры с VLA**: `char buf[n]`, где `n` приходит из файла/сети.
- **Рекурсивные функции** без ограничения глубины — каждая с большим кадром.

## Шаг 4: как защищаются

Раз это отдельный класс, под него есть отдельная защита — **stack clash protection**. Компилятор вставляет в пролог «прощупывание» страниц: прежде чем сдвинуть `rsp` далеко, он пошагово трогает каждую страницу, заставляя ядро корректно дорастить стек и не проскочить guard.

Проверить, есть ли она, можно по прологу — вместо одного `sub rsp, big` там серия мелких `sub` + записей:

```
$ gcc -fstack-clash-protection -O0 stackclash.c -o stackclash_prot
$ objdump -d -M intel stackclash_prot | grep -A6 '<recurse>:'
0000000000401126 <recurse>:
  401126: push   rbp
  401127: mov    rbp,rsp
  40112a: sub    rsp,0x1000          ; шагами по странице
  401131: or     QWORD PTR [rsp],0x0 ; «коснуться» страницы
  401135: sub    rsp,0x1000
  ...
```

Вместо прыжка на 64 КБ — серия шагов по 4 КБ, каждый с записью-касанием. Теперь ядро видит доступ к каждой странице и растит стек по одной, а не проваливается в «дыру».

## Шаг 5: как искать Stack Clash в реальном коде

Stack Clash не выдаёт себя одной подозрительной строкой — его ищут по признакам «большая стековая аллокация по чужому размеру». Вот на что смотреть:

- **VLA (`char buf[n]`)** и **`alloca(size)`**, где `size` приходит из ввода, из файла или из заголовка сетевого пакета. Именно так CVE-2017-1000364 добрался до setuid-утилит glibc.
- **Рекурсия без ограничения глубины**: каждая итерация с крупным кадром съедает десятки килобайт, и глубина задаётся атакующим (например, длина JSON/XML-вложенности).
- **`-fstack-check` отсутствует в сборке**: если бинарник собран без stack clash protection, пролог снова будет одним большим `sub rsp`.
- **Соседний регион, до которого легко дотянуться**: куча через `mmap`, стек другого потока или загруженная библиотека — чем «ближе» чужой регион, тем вероятнее столкновение.

Проверить подозрительный бинарник можно так: посмотреть прологи функций (`objdump -d | grep -B1 'sub.*rsp,0x[0-9a-f]\{4,\}'`), найти крупные сдвиги `rsp` и понять, контролируется ли их размер извне. Если да и защиты нет — перед тобой кандидат на Stack Clash.

Важно понимать разницу: **классическое переполнение** затирает адрес возврата *в пределах* кадра, а Stack Clash **выходит за пределы стека** вообще. Поэтому защита от первого (canary) от второго не спасает.

## Что мы теперь знаем

- **Стек растёт вниз** и ограничен (`ulimit -s`, по умолчанию 8 МБ).
- За нижней границей стека лежит **guard-страница** — датчик для ядра.
- Если функция сдвигает `rsp` **сразу на много страниц**, можно **проскочить** guard и попасть записью в чужой регион — это **Stack Clash**.
- Это не классическое переполнение: баг в самом факте большой стековой аллокации по недоверенному размеру.
- Защита — **stack clash protection**: прощупывание страниц по одной.

## Куда дальше

Мы разобрали, как большой кадр может столкнуть стек с соседним регионом. Дальше посмотрим на **shellcode**: если запись в чужой регион уже есть, что именно туда класть и как заставить процессор это исполнить. А пока запомни главное: **стек — это ограниченный регион с guard-страницей, и слишком большой шаг вниз может вывести запись за его пределы.**

## Где пригодится

- **CTF Pwn:** задачи с VLA/alloca и большими кадрами.
- **Привилегированное повышение:** Stack Clash исторически давал LPE в setuid-программах.
- **Vulnerability research:** анализ парсеров, где размер буфера приходит извне.
- **Аудит кода:** поиск рекурсии без ограничения глубины и VLA по недоверенному размеру.
