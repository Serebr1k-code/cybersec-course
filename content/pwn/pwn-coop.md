## Вопрос, с которого всё начинается

Программа на C++ активно использует виртуальные вызовы: `obj->method()`
компилируется в чтение указателя на vtable и косвенный `call`. CFI проверяет,
что этот вызов идёт в допустимый метод **какого-то** класса. Что, если подсунуть
программе свой объект с vtable, указывающей на существующие методы? Все вызовы
легальны — а поведение наше. Это **COOP**.

## Наш пример

Смотрим, как C++ вызывает виртуальный метод:

```cpp
struct Animal {
    virtual void speak();
    virtual void feed();
};
void run(Animal *a) {
    a->speak();   // call [vptr + 0]
}
```

Дизассемблер `a->speak()`:

```
mov  rax, [rdi]       ; rax = vptr (указатель на vtable)
call [rax + 0]        ; вызов первого метода
```

Мы контролируем `rdi` (объект) — значит, контролируем `vptr` и всю vtable.

## Шаг 1: идея COOP

COOP — это JOP/COP для объектного кода. Мы создаём **поддельный объект**:
блок памяти, где первое поле — указатель на нашу vtable, а дальше — данные
объекта. Vtable заполняем адресами **существующих** виртуальных методов
(«легальных» для CFI). Когда программа делает виртуальный вызов, она попадает
в нужный метод с нашим объектом в качестве `this` (`rdi`). Метод работает с
нашими данными — и делает то, что нам нужно.

Ключевое: мы не создаём новых переходов, а используем легальные виртуальные
вызовы программы. Поэтому CFI на vtable не срабатывает.

## Шаг 2: main-loop gadget

В COOP есть понятие **main-loop gadget** — виртуальный метод, который сам
вызывает другие виртуальные методы своего `this` (например, `run()` вызывает
`step()` у подчинённых объектов). Подсунув такой объект, мы получаем «диспетчер
изнутри программы», который раскручивает нашу цепочку легальными вызовами.

## Шаг 3: построение цепочки

1. Находим в бинаре классы с виртуальными методами, полезными как «gadgets»
   (например, методы, пишущие в поля, вызывающие `memcpy`, делающие syscall).
2. Строим фальшивый объект: `vptr → [method_A, method_B, ...]`.
3. Передаём объект в точку, где программа делает виртуальный вызов.
4. Программа «штатно» вызывает наши методы по очереди.

Каждый метод легален, CFI доволен, а эффект — наш.

## Шаг 4: COOP vs JOP/COP/DOP

| Техника | Единица переиспользования | Против чего |
|---|---|---|
| ROP | ret-гаджет | нет CET |
| JOP | jmp-гаджет + диспетчер | shadow stack |
| COP | call-гаджет | CFI на ret |
| COOP | виртуальный метод (vtable) | CFI на vtable |
| DOP | операция над данными | всё (кроме data-flow) |

COOP — «объектно-ориентированная» разновидность JOP: вместо голых гаджетов
используются методы, а диспетчер — сам объект.

## Шаг 5: отладка

Под `gdb` смотрим `vptr` и содержимое vtable. Ставим точки на виртуальные
методы и проверяем, что вызываются именно они. Полезно распечатать `this`
(`rdi`) — он должен указывать на наш поддельный объект.

## Шаг 6: ограничения и защита

- Нужен контроль над указателем на объект (type confusion, UAF).
- Не все методы полезны — нужен анализ бинаря.
- CFI с проверкой **точного** типа vtable (не «любой легальный») мешает COOP.
- Современные компиляторы с `-fsanitize=cfi` и раздельными vtables усложняют.

Защита — CFI строгого типа, изоляция vtables, а также уменьшение числа
виртуальных вызовов в критичных местах.

## Что мы теперь знаем

- COOP использует поддельные C++-объекты с контролируемыми vtables.
- Виртуальные вызовы легальны — CFI на vtable не срабатывает.
- Main-loop gadget раскручивает цепочку изнутри программы.
- Единица переиспользования — виртуальный метод.
- Нужен контроль указателя на объект.

## Как устроены vtables

У каждого полиморфного C++-объекта первое поле — указатель на vtable (таблицу
виртуальных методов). Компилятор генерирует её один раз на класс:

```
class Animal {
    virtual void speak();
    virtual void feed();
};

// объект:
// [0] vptr -----> vtable: [ speak, feed, typeinfo, ... ]
// [8] data...
```

Вызов `a->speak()` компилируется в:

```
mov  rax, [rdi]      ; rax = vptr
call [rax + 0]       ; первый слот vtable
```

Если мы контролируем `rdi` (указатель на объект), мы контролируем `vptr`, а
значит — всю vtable.

## Поиск полезных методов

Для COOP нужны виртуальные методы, которые делают полезную работу. Ищем в
бинаре классы с методами, которые:

- пишут в поля объекта (`this->x = ...`);
- вызывают другие виртуальные методы (main-loop gadgets);
- делают `memcpy`, `read`, `write`, syscall;
- меняют глобальное состояние.

Их адреса берём из vtable-таблиц в секции данных (`.data.rel.ro`), которые
видны в дизассемблере как массивы указателей на функции.

## Полный пример

Задача: вызвать метод, который копирует данные, с нашим `this`.

1. Находим в бинаре виртуальный метод `copy(this, src, n)`.
2. Создаём поддельный объект: `vptr` → таблица, где нужный слот указывает на
   `copy`.
3. Передаём объект в точку, где программа делает `obj->virtualMethod()`.
4. Программа «легально» вызывает `copy` с нашими `this`/аргументами.

Все переходы легальны для CFI, потому что идут через настоящую vtable-механику.

## Main-loop gadget

Особенно ценны методы, которые сами вызывают виртуальные методы своих полей:

```cpp
void Container::run() {
    for (auto *c : children) c->step();   // вызовы через vtable!
}
```

Если подсунуть `Container` с поддельным списком `children`, каждая `step()` —
наш контролируемый виртуальный вызов. Это «диспетчер изнутри программы»,
который раскручивает цепочку без нашего участия.

## Ограничения и защита

- Нужен контроль указателя на объект (UAF, type confusion, переполнение).
- CFI строгого типа проверяет, что vtable соответствует **ожидаемому** классу —
  это ломает подделку.
- Изоляция vtables (`-fno-rtti`, раздельные таблицы) и рандомизация усложняют.
- Современные компиляторы всё чаще применяют devirtualization, убирая вызовы
  через vtable в горячих местах.

COOP — мощная техника для C++-целей (браузеры, СУБД), но требующая хорошего
понимания объектной модели.

## COOP и JOP: родство

COOP — это JOP на уровне объектов: вместо голых jmp-гаджетов используются
виртуальные методы, а диспетчером служит main-loop gadget (метод, вызывающий
другие методы). Поэтому инструменты и мышление те же: искать «полезные
единицы», собирать из них цепочку, отлаживать по точкам останова.

## Итог по COOP

COOP подсовывает программе поддельный C++-объект с контролируемой vtable, и
штатные виртуальные вызовы исполняют нужные методы. Все переходы легальны,
поэтому CFI на vtable не срабатывает. Техника требует контроля указателя на
объект и понимания объектной модели. Это завершающий урок модуля code-reuse:
вместе с JOP/COP/DOP он покрывает атаки на защищённый поток управления.

## Разбор реального COOP-сценария

Цель — C++-приложение (браузер, медиаплеер) с CFI на vtable. Уязвимость — UAF
объекта. Стратегия:

1. Занимаем освобождённый слот поддельным объектом: `vptr` → наша таблица.
2. В таблицу кладём адреса **существующих** виртуальных методов, полезных как
   gadgets (пишущих в поля, вызывающих `memcpy`, делающих нужные операции).
3. Ждём, когда программа вызовет виртуальный метод по нашей ссылке.
4. Программа «легально» вызывает наш метод с нашим `this`.

Поскольку методы существуют и их типы корректны, CFI пропускает вызов.

## Main-loop gadget на практике

Самый ценный элемент — метод-контейнер, который перебирает детей и вызывает у
каждого виртуальный метод. Подсунув ему поддельный список детей, мы получаем
цикл, который сам вызывает нужные методы по порядку. Это «программируемый
диспетчер» изнутри цели, не требующий наших переходов вообще.

## Ограничения и обход

CFI строгого типа проверяет, что vtable принадлежит ожидаемому классу. Обойти
это можно, подобрав класс-жертву, чьи методы нам подходят, или используя
легальные объекты как «строительный материал». Современные компиляторы также
применяют devirtualization — если вызов можно разрешить статически, vtable не
используется, и COOP не работает. Поэтому техника требует анализа конкретного
бинаря, но на реальных C++-целях она по-прежнему применима.

## Типичные ошибки COOP

- **vptr не контролируется.** Нужен контроль указателя на объект.
- **CFI строгого типа.** Проверка ожидаемого класса ломает подделку.
- **Devirtualization.** Компилятор убрал вызов через vtable — техника не работает.
- **Метод делает не то.** Анализируй метод перед использованием: он работает с
  `this`, который ты подсунул.

## Заключение по COOP

COOP завершает модуль code-reuse: он показывает, как объектная модель C++ сама
становится источником «гаджетов». Подделав vtable, мы заставляем штатные
виртуальные вызовы исполнять нужные методы — без единого нелегального перехода.
Это делает COOP устойчивым к CFI на vtable, пока проверка не станет строго
типовой. Вместе с JOP, COP и DOP он покрывает весь спектр атак на защищённый
поток управления, и выбор техники определяется конкретной защитой цели.

## Финальная мысль

COOP показывает, что объектная модель — это тоже поверхность атаки. Понимание
vtables и виртуальных вызовов пригодится и при защите: сужение типов в CFI,
devirtualization и изоляция таблиц заметно поднимают планку для атакующего.
