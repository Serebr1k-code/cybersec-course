## Вопрос, с которого всё начинается

После glibc 2.34 писать `system` в `__free_hook` бесполезно. Куда же целиться? Ответ: в структуры `_IO_FILE` — описания потоков ввода-вывода (`stdout`, `stdin`, файлы). У каждой такой структуры есть таблица функций, и если её подменить, glibc сама вызовет то, что нам нужно. Техника называется **FSOP** — File Stream Oriented Programming.

Разберём, из чего состоит `_IO_FILE` и как из её подмены получить вызов `system`.

## Наш пример

Посмотрим на структуру стандартного потока вывода в целевой libc:

```
$ readelf -sW /usr/lib/libc.so.6 | grep -E '_IO_2_1_stdout_|_IO_list_all|_IO_file_jumps|system'
  53b00  system
  1e6030 _IO_file_jumps
  1e8480 _IO_list_all
  1e8580 _IO_2_1_stdout_
```

Здесь `_IO_2_1_stdout_` — сама структура `stdout` (смещение `0x1e8580`), `_IO_file_jumps` — её таблица функций (`0x1e6030`), `_IO_list_all` — указатель на список всех потоков, а `system` — наша цель (`0x53b00`). Дальше будем комбинировать эти адреса.

## Шаг 1. Что такое _IO_FILE

`_IO_FILE` — это структура, которой glibc описывает любой поток. Вот ключевые поля (смещения для x86_64):

| Смещение | Поле | Смысл |
|---|---|---|
| `0x00` | `_flags` | флаги потока |
| `0x20` | `_IO_write_base` | начало буфера записи |
| `0x28` | `_IO_write_ptr` | текущая позиция записи |
| `0x38` | `_IO_buf_base` | начало буфера |
| `0x68` | `_chain` | следующий поток в списке |
| `0xa0` | `_wide_data` | данные для «широких» (wchar) потоков |
| `0xd8` | `vtable` | указатель на таблицу функций |

Последнее поле — самое важное. Размер структуры — `0xe0` байт, поэтому `vtable` лежит на `0xd8`.

## Шаг 2. Что такое vtable

`vtable` — это массив указателей на функции, которые обслуживают поток: прочитать, записать, сбросить буфер, закрыть. Когда glibc нужно, например, сбросить буфер вывода, она вызывает `fp->vtable->_IO_overflow(fp)`. Если подменить `vtable` на нашу таблицу, glibc вызовет **наш** указатель.

Стандартная таблица для файлов — `_IO_file_jumps`. Для «широких» потоков — `_IO_wfile_jumps`. Для строковых — `_IO_str_jumps`. Нам важен сам принцип: `vtable` — массив указателей функций, и его содержимое управляет поведением потока.

## Шаг 3. Как FSOP приводит к вызову system

Классическая цепочка (её называют House of Orange) опирается на то, что при завершении программы `exit` обходит список всех потоков `_IO_list_all` и вызывает для каждого `_IO_flush_all_lockp`, а тот — `vtable->_IO_overflow`.

План:

1. Подделываем `_IO_FILE`: `_flags` выставляем так, чтобы поток считался «на запись», а `_IO_write_base` < `_IO_write_ptr` — тогда `flush` решит, что есть данные для сброса.
2. В поле `vtable` пишем адрес фейковой таблицы, где нужная позиция (обычно `_IO_overflow`, смещение `0x18`) указывает на `system`.
3. Заставляем `_IO_list_all` (или `_chain` предыдущего потока) указывать на нашу структуру.
4. Программа завершается — `exit` идёт по списку, доходит до нас и вызывает `system`.

## Шаг 4. Аргумент вызова

Тонкость: `system` вызовется с первым аргументом `fp` — то есть указателем на нашу `_IO_FILE`. Значит, по адресу структуры должна лежать строка `"/bin/sh"`. Часто `_flags` (первые 8 байт) и подставляют как `"/bin/sh\x00"`, либо используют гаджет, который переносит указатель на другое поле. На практике в CTF часто проще записать `"/bin/sh"` в начало структуры.

## Шаг 5. Проверка vtable (glibc 2.24+)

Сразу после FSOP-атак glibc добавила проверку `IO_validate_vtable`: `vtable` обязан указывать **внутрь** секции `__libc_IO_vtables` (там лежат легальные таблицы). Произвольный адрес в куче больше не пройдёт.

Обход: указывать не на «свою» таблицу, а внутрь **легальной** — так, чтобы нужное смещение совпало с полезной функцией. Это тема следующего урока (`pwn-vtable-check-bypass`). Здесь важно запомнить: `vtable` должна быть валидной, поэтому её «сдвигают» внутри настоящей таблицы.

## Шаг 6. Список потоков и _chain

Потоки связаны полем `_chain`: `_IO_list_all` указывает на первый, его `_chain` — на следующий, и т.д. Чтобы `exit` дошёл до нашей подделки, нужно либо подменить `_IO_list_all`, либо «прицепить» нашу структуру в конец существующего списка через `_chain`. Второй путь удобнее: подменяем `_chain` у `_IO_2_1_stderr_` (последнего в списке) на адрес нашей структуры.

## Шаг 7. Почему это работает и сейчас

FSOP жив именно потому, что `exit` (и `fclose`, и `fflush`) доверяют полю `vtable`. Даже с проверкой `IO_validate_vtable` остаётся возможность использовать **легальные** таблицы и сдвиги внутри них. Поэтому FSOP — основная современная техника для glibc 2.34+, где хуки удалены.

## Полный прогон от начала до конца

Соберём историю целиком. Дана программа, которая после ввода завершается. У нас есть запись по произвольному адресу.

1. Читаем целевую libc: `_IO_2_1_stdout_` = `0x1e8580`, `_IO_file_jumps` = `0x1e6030`, `system` = `0x53b00`.
2. В куче готовим поддельный `_IO_FILE`: в начало кладём `"/bin/sh"`, выставляем `_flags` и `_IO_write_base < _IO_write_ptr`, в поле `vtable` пишем адрес нашей таблицы.
3. В нашей таблице на смещении `_IO_overflow` (`0x18`) кладём `system`.
4. Подменяем `_IO_list_all` (или `_chain` последнего потока) на адрес подделки.
5. Программа завершается, `exit` обходит список потоков, вызывает `flush`, тот дёргает `_IO_overflow` — и получает `system("/bin/sh")`.

Ключевая мысль: FSOP не пишет в одну «магическую» переменную, а заставляет **саму glibc** вызвать нашу функцию через штатный механизм.

## Если не сработало

FSOP капризен, потому что цепочка длинная. Частые причины провала:

Первое: не выполнено условие flush. Если `_flags` или `_IO_write_base`/`_IO_write_ptr` выставлены неверно, glibc решит, что сбрасывать нечего, и не вызовет `_IO_overflow`.

Второе: `vtable` не проходит проверку. Произвольный адрес в куче отклоняется; нужна валидная таблица (или сдвиг внутри неё).

Третье: структура не в списке. Если `_IO_list_all`/`_chain` не указывают на подделку, `exit` до неё не дойдёт. Проверь, куда именно ведёт список.

Четвёртое: не тот аргумент. `system` получит `fp`, а не обязательно `"/bin/sh"`. Убедись, что по адресу структуры лежит нужная строка, либо используй гаджет для переноса указателя.

Пятое: версия. На старых glibc (≤2.23) не было проверки vtable, и цепочка проще; на новых — обязателен валидный `vtable`. Всегда сверяйся с версией.

## Инструмент: nm — таблица символов

`nm` перечисляет символы бинарника: имена функций и глобальных переменных с их адресами. Если символы не срезаны, это самый быстрый способ найти нужную функцию.

Ключи, которые пригодятся:
* `nm <файл>` — все символы с адресами;
* `nm -C <файл>` — демутируй C++-имена (читаемые сигнатуры);
* `T`/`t` — код (глобальный/локальный), `R`/`r` — только чтение (`.rodata`), `D`/`B` — данные;
* нижний регистр = локальный символ, верхний = глобальный/экспортируемый.

### Рабочий пример (как в лаборатории)

```
$ nm -D libc.syms
00000000001e84a0 D _IO_2_1_stderr_@@GLIBC_2.2.5
00000000001e8580 D _IO_2_1_stdout_@@GLIBC_2.2.5
00000000001e6030 D _IO_file_jumps@@GLIBC_2.2.5
00000000001e6228 D _IO_wfile_jumps@@GLIBC_2.2.5
```

Подсказка из лаборатории: `nm -D <файл>`.

## Что мы теперь знаем

- `_IO_FILE` — структура потока; `vtable` (на `0xd8`) — её таблица функций.
- FSOP подменяет `vtable`, и glibc вызывает нужный указатель (например, `system`).
- Цепочка: подделать структуру → подменить `vtable` → попасть в список `_IO_list_all` → дождаться `exit`.
- С glibc 2.24+ `vtable` обязана указывать внутрь легальной таблицы (`IO_validate_vtable`).
- FSOP — основная замена мёртвым хукам на glibc 2.34+.
