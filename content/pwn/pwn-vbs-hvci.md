## Вопрос, с которого всё начинается

Ты нашёл баг в ядре Windows и хочешь загрузить свой код в ring 0. Но система
защищена **VBS/HVCI** — гипервизор не даёт исполнять неподписанный код ядра.
Как эта защита устроена и можно ли её обойти? Разберём.

## Наш пример

Конфигурация Device Guard:

```
$ cat deviceguard.txt
VirtualizationBasedSecurity     : enabled
VBS Running                     : 1
HypervisorEnforcedCodeIntegrity : 1
Kernel DMA Protection           : enabled
Secure Launch                   : disabled
```

`HypervisorEnforcedCodeIntegrity = 1` — HVCI **включён**. Разберём, что это
значит.

## Шаг 1: что такое VBS

**VBS (Virtualization-Based Security)** — использование гипервизора для
изоляции чувствительных компонентов от основной ОС. Даже если ядро Windows
скомпрометировано, **secure kernel** (защищённое ядро под управлением
гипервизора) остаётся недосягаемым.

VBS держит:

- **целостность кода** (HVCI);
- **учётные данные** (Credential Guard);
- **защиту ядра** от модификаций.

## Шаг 2: HVCI и KMCI

**HVCI (Hypervisor-Protected Code Integrity)**, он же **KMCI** (Kernel Mode Code
Integrity), проверяет, что **все страницы, исполняемые в режиме ядра**, —
подписанные и неизменяемые. Механика:

1. Гипервизор ведёт **second-level address translation** (SLAT/EPT).
2. Страницы, помеченные как исполняемые, могут быть **только** из подписанных
   образов.
3. Попытка исполнить неподписанный/модифицированный код → отказ/BSOD.

Практическое следствие: нельзя просто записать shellcode в ядро и прыгнуть в
него. Также нельзя менять существующий код ядра на лету.

## Шаг 3: что HVCI НЕ защищает

HVCI защищает **целостность кода**, но **не данные**. Это ключ к обходу:

- **data-only** атаки (подмена токена, флагов, указателей на **легальные**
  функции) проходят;
- **переиспользование подписанных** драйверов (BYOVD) возможно;
- **подмена данных**, которые использует подписанный код, — работает.

То есть HVCI переводит эксплуатацию из «выполнить свой код» в «изменить
данные, которые исполняет чужой подписанный код».

## Шаг 4: Credential Guard

VBS также защищает **учётные данные**: LSA-секреты изолированы в secure
kernel. Это ломает классический **LSASS dumping** — не получится просто
прочитать хэши из памяти LSASS. Для обхода нужны другие пути (делегирование,
DPAPI, токены).

## Шаг 5: классы обхода

Обходы VBS/HVCI:

- **Data-only примитивы**: подмена токена, правка полей структур (наш случай из
  kernel-эксплуатации).
- **BYOVD (Bring Your Own Vulnerable Driver)**: загрузить **подписанный**, но
  уязвимый драйвер и через него писать в ядро. Подпись валидна → HVCI не
  мешает.
- **Атака на сам secure kernel/гипервизор**: баг в VBS-компоненте (высшая
  сложность).
- **DMA-атаки**: через Kernel DMA Protection не всегда закрыто.
- **Обход через доверенные интерфейсы**: использование легальных API/структур.

## Шаг 6: практика для эксплойт-разработчика

Если цель с HVCI:

1. **Откажись от shellcode** в ядре — он не исполнится.
2. **Ищи data-only** цель: токен, флаги, указатели на подписанные функции.
3. **Рассмотри BYOVD**: есть ли подписанный уязвимый драйвер.
4. **Проверь Credential Guard**: LSASS-дамп не сработает, ищи альтернативы.
5. **Проверь VBS-конфиг** (как в нашем `deviceguard.txt`).

## Шаг 7: почему это важно в облаке

VBS/HVCI включены по умолчанию во многих облачных и корпоративных Windows.
Понимание их обхода — разница между «теоретическим» и «рабочим» эксплойтом.
Для VM-escape (предыдущий урок) обход VBS — финальный шаг к контролю хоста.

## Как проверить VBS и HVCI

На работающей системе:

```
PS> Get-CimInstance -ClassName Win32_DeviceGuard -Namespace root\Microsoft\Windows\DeviceGuard
```

Смотри поля `VirtualizationBasedSecurityStatus`, `SecurityServicesRunning` (там
бит HVCI), `CodeIntegrityPolicyEnforcementStatus`. Через реестр —
`HKLM\SYSTEM\CurrentControlSet\Control\DeviceGuard`. Значение HVCI = 1 означает,
что неподписанный код ядра не исполнится.

## BYOVD подробнее

**BYOVD (Bring Your Own Vulnerable Driver)** — обход, не ломающий целостность
кода: используется **подписанный**, но **уязвимый** драйвер. Поскольку подпись
валидна, HVCI разрешает загрузку. Через баг драйвера получают примитив записи в
ядро и делают data-only token stealing.

Этапы:

1. Найти публично известный уязвимый подписанный драйвер (есть списки).
2. Загрузить его на цель (`sc create`/`sc start`).
3. Открыть устройство, вызвать уязвимый IOCTL.
4. Получить запись в ядро → подменить токен.

BYOVD — один из самых практичных обходов VBS/HVCI.

## Credential Guard и обход

Credential Guard изолирует **LSA-секреты** в secure kernel. Классический дамп
`lsass.exe` через `MiniDumpWriteDump` больше не даёт хэшей/тикетов. Обходы:

- **делегирование** (Kerberos) для доступа к ресурсам без хэшей;
- **DPAPI**-материалы, доступные пользователю;
- **токены** уже аутентифицированных сессий;
- **атака на сам secure kernel** (высшая сложность).

То есть Credential Guard меняет тактику: не «украсть хэш», а «использовать
существующую сессию».

## Частые ошибки

- **Пытаются исполнить shellcode в ядре.** HVCI не даст — нужен data-only.
- **Дамп LSASS.** Credential Guard ломает его; ищи альтернативы.
- **Не проверили конфиг.** Эксплойт «работает» на стенде без VBS и падает на
  цели.
- **Игнорируют BYOVD.** Самый практичный обход часто забывают.

## Итоговая картина

Современный Windows-эксплойт при VBS/HVCI — это **data-only цепочка**: баг
(свой или BYOVD) даёт примитив записи, а цель — данные (токен, флаги), которые
исполняет **подписанный** код. Понимание VBS/HVCI — обязательная часть
профессиональной kernel-эксплуатации.

## Команды проверки VBS/HVCI

```powershell
# Статус VBS и запущенных сервисов безопасности
Get-CimInstance -ClassName Win32_DeviceGuard `
  -Namespace root\Microsoft\Windows\DeviceGuard |
  Select-Object VirtualizationBasedSecurityStatus, SecurityServicesRunning,
                CodeIntegrityPolicyEnforcementStatus

# Через msinfo32 / реестр
reg query "HKLM\SYSTEM\CurrentControlSet\Control\DeviceGuard" /s
```

`SecurityServicesRunning` содержит биты: 1 = Credential Guard, 2 = HVCI. Если
бит 2 выставлен — код ядра защищён гипервизором.

## Secure kernel и VTL

VBS создаёт **secure kernel**, работающий в **VTL1** (Virtual Trust Level 1),
тогда как обычная ОС — в **VTL0**. Гипервизор переключает уровни доверия.
Компоненты в VTL1 недоступны из VTL0 напрямую — даже скомпрометированное
обычное ядро не может их тронуть. Это и есть «защита гипервизором».

Побег из VTL0 в VTL1 требует бага **в самом secure kernel или гипервизоре** —
высшая сложность. Поэтому на практике чаще обходят не изоляцию, а **целостность
кода** (HVCI) через data-only/BYOVD.

- [ ] Проверено состояние VBS/HVCI на цели.

- [ ] Рассмотрен BYOVD как путь.
- [ ] Учтён Credential Guard (LSASS-дамп не работает).
- [ ] Цель — данные, а не код.

## Почему VBS включён по умолчанию

На новых Windows (и в облаке) VBS/HVCI включаются **по умолчанию**: Microsoft
считает, что изоляция критичных компонентов гипервизором стоит небольшой потери
производительности. Это значит, что современный эксплойт-разработчик почти
всегда имеет дело с VBS и должен планировать **data-only** цепочку с самого
начала, а не как «запасной вариант».

Дополнительно VBS защищает учётные данные (Credential Guard), ломая классические
приёмы кражи хэшей. Red team вынужден переходить на использование существующих
сессий и делегирования вместо дампа LSASS.

## Практический вывод

Если на цели включены VBS/HVCI:

1. **Не планируй shellcode** в ядре — его не будет.
2. **Ищи data-only** цель (токен, флаги, указатели на подписанные функции).
3. **Рассмотри BYOVD** как быстрый путь к примитиву записи.
4. **Проверь Credential Guard** и пересмотри тактику сбора учётных данных.
5. **Проверяй конфиг** на каждом стенде: без VBS эксплойт может вести себя
   иначе.

VBS/HVCI — не «непреодолимая стена», а **смена парадигмы**: эксплуатируют
данные, которые исполняет доверенный код, а не сам код.

## Частые вопросы

**VBS и HVCI — это одно и то же?** Нет. VBS — общий механизм изоляции через
гипервизор; HVCI — одна из его функций (целостность кода ядра). Вместе они
защищают и код, и (через Credential Guard) учётные данные.

**Можно ли вообще обойти HVCI?** Напрямую исполнить неподписанный код — нет.
Но обходят **не HVCI, а его предположения**: используют подписанные уязвимые
драйверы (BYOVD) и data-only примитивы.

**Почему data-only работает при HVCI?** HVCI защищает **код**, а не **данные**.
Меняя данные (токен, флаги), которые исполняет доверенный код, мы не нарушаем
целостность кода.

**Включён ли VBS на моей цели?** Проверь `Win32_DeviceGuard` и реестр
`DeviceGuard`. На новых Windows и в облаке — обычно да.

**Что делать с Credential Guard?** Пересмотреть тактику: вместо дампа LSASS
использовать существующие сессии, делегирование и DPAPI-материалы.

## Сводка

VBS использует гипервизор для изоляции критичных компонентов Windows, а HVCI
запрещает исполнять неподписанный код в режиме ядра. Это меняет парадигму
эксплуатации: вместо захвата потока управления и shellcode мы атакуем **данные**,
которые исполняет доверенный код.

Практические пути при VBS/HVCI: data-only примитивы (token stealing), загрузка
подписанного уязвимого драйвера (BYOVD) и, в редких случаях, атака на сам secure
kernel. Credential Guard дополнительно ломает классическую кражу учётных данных,
заставляя использовать существующие сессии и делегирование. Понимание VBS/HVCI —
обязательная часть современной Windows kernel-эксплуатации.

## Что мы теперь знаем

- VBS изолирует защищённые компоненты через гипервизор.
- HVCI/KMCI запрещает исполнять неподписанный код ядра.
- HVCI защищает код, но **не** данные.
- Обходы: data-only, BYOVD, атака на secure kernel.
- Credential Guard ломает классический LSASS-дамп.
