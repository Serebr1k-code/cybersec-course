## Вопрос, с которого всё начинается

Ты не знаешь, где в программе баг. Можно часами читать ассемблер — а можно заставить **машину** искать за тебя: подавать миллионы входов и ловить падения. Это **фаззинг**. В этом уроке напишем простейший фаззер руками, увидим, как он находит краш, и разберём, чем занимаются «взрослые» инструменты — AFL++, libFuzzer, honggfuzz.

## Наш пример

Возьмём крошечный парсер, который проверяет строку:

```c
int parse(const char *s) {
    if (strlen(s) >= 3 && s[0]=='F' && s[1]=='U' && s[2]=='Z') {
        if (s[3]=='Z') puts("crash-ish");
        return 1;
    }
    return 0;
}
```

Уязвимость: при `s[3]` нет проверки длины. Если строка ровно «FUZ», чтение `s[3]` выходит за буфер. Напишем **тупой мутационный фаззер**: генерируем случайные строки, запускаем программу, смотрим на код возврата и вывод.

```python
import random, subprocess
random.seed(1)
for i in range(3000):
    s = ''.join(random.choice('FUZAB') for _ in range(random.randint(1, 8)))
    r = subprocess.run(['./parser', s], capture_output=True)
    if r.returncode != 0 or b'crash' in r.stdout:
        print('crash input:', repr(s))
```

Запускаем:

```
$ python3 fuzz.py
crash input: 'FUZZ'
crash input: 'FUZZ'
crash input: 'FUZZBF'
done, crashes found: 3
```

Фаззер сам нашёл вход «FUZZ», на котором срабатывает баг. За считанные секунды — без чтения кода.

## Шаг 1: что такое фаззинг

**Фаззер** — программа, которая:

1. **генерирует вход** (случайный, мутированный из известных «хороших» входов, или по грамматике формата);
2. **запускает цель** с этим входом;
3. **следит за результатом** (код возврата, сигнал, таймаут);
4. при падении **сохраняет вход** — это «краш».

Простейший вариант (как выше) — **dumb fuzzing**: без обратной связи. Он работает, но медленно: почти все входы уходят впустую.

## Шаг 2: coverage-guided фаззинг

Идея «умного» фаззинга — **покрытие кода** (coverage). Фаззер отслеживает, какие ветки программы были исполнены. Если новый вход открыл **новую ветку** — вход сохраняется в **corpus** (набор интересных входов) и мутируется дальше. Так фаззер постепенно «прощупывает» всё больше кода.

Именно так работает **AFL++** (American Fuzzy Lop, плюс-версия):

- **Инструментирование.** Цель компилируется спец-компилятором (`afl-clang-fast`), который вставляет в код учёт покрытия. Без него фаззер слеп.
- **Corpus.** Начальный набор входов («seed»). Чем ближе они к формату, тем быстрее успех.
- **Dictionary.** Словарь «магических» строк формата (например, `GET`, `HTTP/1.1`) — мутации подставляют их, чтобы проходить проверки заголовков.
- **Детерминированные и случайные мутации.** AFL++ комбинирует смену байт, вставку, удаление, подстановку из словаря.

Запуск выглядит так:

```
$ afl-clang-fast -o parser_fuzz parser.c
$ afl-fuzz -i seeds/ -o out/ -- ./parser_fuzz @@
```

`-i seeds/` — входной corpus, `-o out/` — куда писать находки, `@@` — подстановка имени файла с входом. В `out/crashes/` окажутся входы, которые уронили программу.

## Шаг 3: libFuzzer и honggfuzz

AFL++ — не единственный. Два других популярных инструмента:

- **libFuzzer** — встроен в clang. Ты пишешь функцию `LLVMFuzzerTestOneInput(data, size)`, а фаззер сам генерирует входы и вызывает её in-process (без перезапуска процесса — это быстро). Инструментирование через `-fsanitize=fuzzer,address`.
- **honggfuzz** — похож по идее, умеет много архитектур, хорошо работает с бинарниками и ядром.

Выбор прост: **есть исходники и clang** → libFuzzer; **есть исходники, но нужен максимально богатый движок** → AFL++; **бинарник без исходников или железо** → honggfuzz/AFL в режиме QEMU.

## Шаг 4: от краша к эксплойту

Найденный вход — это **ещё не эксплойт**, а воспроизводимый краш. Дальше:

1. **Воспроизведи** краш: запусти цель с сохранённым входом под отладчиком.
2. **Определи тип бага**: переполнение стека/кучи, UAF, переполнение целых.
3. **Минимизируй вход** (`afl-tmin`) — оставь только байты, необходимые для краша.
4. **Построй эксплойт**: изучи смещения, примитивы, защиты (см. уроки про переполнение, ROP, heap).
5. **Учти санитайзеры**: если фаззинг шёл с ASan, убери его для эксплуатации.

Важно: фаззер находит **вход**, приводящий к падению, а не объясняет **почему**. Понимание бага — по-прежнему твоя работа. Именно поэтому фаззинг не отменяет навыки отладки и чтения кода: он лишь даёт зацепку.

## Шаг 5: где это встречается

- **Bug bounty:** fuzzing — основной способ находить баги в парсерах, браузерах, ядре.
- **CTF:** иногда дают фаззинг-цель; умение быстро настроить AFL++ экономит часы.
- **Аудит кода:** fuzzing+ASan в CI ловит баги до релиза.
- **Vulnerability research:** Google OSS-Fuzz — это фаззинг сотен open-source проектов, тысячи найденных CVE.

## Шаг 6: как настроить фаззинг эффективно

Результат фаззинга сильно зависит от подготовки. Несколько правил:

- **Хороший corpus.** Начальные входы должны быть **валидными** для формата: настоящий заголовок, настоящий файл. С пустого seed фаззер будет долго угадывать структуру.
- **Dictionary.** Дай фаззеру «магические» строки и числа формата. Это резко ускоряет проход проверок.
- **Инструментированная сборка.** Без coverage-инструментирования AFL++ работает вслепую. Собирай цель `afl-clang-fast`, а не обычным `gcc`.
- **Один процесс = один вход.** Классический AFL запускает цель заново на каждый вход; libFuzzer работает in-process (быстрее, но нужно следить за состоянием).
- **ASan рядом.** Сборка `-fsanitize=address` ловит баги, которые не дают явного падения (тихое повреждение памяти).
- **Параллельность.** Запускай несколько экземпляров (`-M`/`-S`) — они делят находки и ускоряют поиск. На многоядерной машине это даёт кратный прирост: каждый экземпляр исследует свои ветки, а corpus синхронизируется.

Ещё один важный момент — **что считать «крашем»**. Падение по сигналу, срабатывание ASan, зависание (таймаут) — всё это интересно. Настрой так, чтобы не пропустить ни один класс.

И наконец, **фаззинг — это процесс, а не кнопка**. Между первым запуском и стабильной находкой багов проходят часы настройки: подбор seed, словаря, проверка, что цель вообще инструментирована. Не жди результата с первого запуска — итеративно улучшай корпус и мутации. Опытные исследователи ведут фаззинг неделями на фермах машин — это норма, а не признак неудачи.

## Что мы теперь знаем

- **Фаззинг** — автоматический поиск падений через генерацию входов.
- **Coverage-guided** фаззинг (AFL++) использует покрытие кода и corpus, чтобы прощупывать программу.
- **libFuzzer** встроен в clang и работает in-process; **honggfuzz** — ещё один движок.
- Найденный краш — **не эксплойт**: его воспроизводят, минимизируют и разбирают вручную.
- Фаззинг даёт **вход**, а понимание бага остаётся за тобой.

## Куда дальше

Мы научились находить краши фаззингом. Дальше — **символьное исполнение (angr)**: вместо случайного перебора можно **решать** вход аналитически, чтобы дойти до нужной функции. А пока запомни главное: **фаззинг — это автоматический поиск падений; он даёт вход, а эксплойт ты строишь сам.**

## Где пригодится

- **CTF Pwn:** быстрый поиск бага в незнакомом бинарнике.
- **Bug bounty:** фаззинг — основной инструмент охоты за CVE.
- **Vulnerability research:** OSS-Fuzz и подобные проекты.
- **Разработка:** fuzzing в CI против регрессий.
