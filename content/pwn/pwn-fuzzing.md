Фаззинг — это автоматизированный поиск уязвимостей путём подачи множества входных данных и наблюдения за аномалиями (крешами). Для pwn-специалиста фаззинг — способ найти баги, которые затем эксплуатируются. Инструменты: AFL++ (coverage-guided), libFuzzer (in-process), honggfuzz, а также специализированные (syzkaller для ядра). В этом уроке — устройство фаззинга, инструменты, сетап, приёмы повышения эффективности и практические примеры.

## Основы фаззинга

Фаззер генерирует входы, подаёт их в цель и отслеживает падения. Ключевая идея coverage-guided фаззинга: фаззер инструментирует цель, отслеживает покрытие кода и мутирует входы, чтобы исследовать новые пути. AFL++ — самый популярный; он использует `afl-gcc`/`afl-clang-fast` для инструментации, `afl-fuzz` для мутаций, и отслеживает покрытие через shared memory. Найденные креши сохраняются в `crashes/`, уникальные пути — в `queue/`.

## AFL++

```bash
# сборка с инструментацией
CC=afl-clang-fast CXX=afl-clang-fast++ ./configure --disable-shared
make
# запуск
afl-fuzz -i seeds/ -o out/ -- ./target @@
# с ASAN
AFL_USE_ASAN=1 afl-clang-fast target.c -o target
afl-fuzz -i seeds/ -o out/ -- ./target @@
# параллельно (master/slave)
afl-fuzz -M master -i seeds/ -o out/ -- ./target @@
afl-fuzz -S slave1 -i seeds/ -o out/ -- ./target @@
```

Ключевые опции: `-i` (seeds), `-o` (output), `-M/-S` (master/slave), `-x` (dictionary), `-t` (timeout), `-m` (memory limit). Результаты: `out/default/crashes/`, `out/default/queue/`.

## libFuzzer

libFuzzer работает in-process (быстрее) и требует функцию `LLVMFuzzerTestOneInput`:

```c
int LLVMFuzzerTestOneInput(const uint8_t *data, size_t size) {
    // вызываем цель с data/size
    return 0;
}
```

```bash
clang -fsanitize=fuzzer,address target.c -o fuzz
./fuzz corpus/
```

libFuzzer сам управляет мутациями и покрытием. Идеален для библиотек и функций, принимающих буфер.

## honggfuzz

honggfuzz — альтернатива с поддержкой множества режимов (persistent, hardware coverage). Установка и запуск:

```bash
honggfuzz -i seeds/ -o out/ -- ./target ___FILE___
honggfuzz --persistent -- ./target
```

## Повышение эффективности

- **Словарь.** Добавьте `-x dict` с ключевыми строками (magic bytes, команды).
- **Seeds.** Качественные seeds (валидные входы) ускоряют исследование.
- **ASAN.** Сборка с ASan ловит больше багов (heap overflow, UAF).
- **Persistent mode.** Для libFuzzer/honggfuzz — уменьшает накладные расходы.
- **Dictionaries и cmp-log.** Помогают пройти проверки (magic, сравнения).
- **Параллелизм.** Несколько инстансов (master/slave) используют все ядра.

## Разобранный пример

```bash
# 1) цель с багом
cat > target.c <<'EOF'
#include <stdio.h>
int main() {
    char buf[16];
    read(0, buf, 64);   // overflow
    return 0;
}
EOF
# 2) сборка с ASAN + AFL
AFL_USE_ASAN=1 afl-clang-fast target.c -o target
# 3) seeds
mkdir seeds && echo "AAAA" > seeds/seed
# 4) фаззинг
afl-fuzz -i seeds/ -o out/ -- ./target
# 5) результат
ls out/default/crashes/
```

## Частые ошибки

- **Нет инструментации.** Фаззер не видит покрытие.
- **Плохие seeds.** Фаззинг буксует.
- **Таймауты.** Цель зависает — настройте `-t`.
- **ASAN + AFL.** Требует больше памяти (`-m none`).
- **Формат ввода.** Используйте `@@` для файлов, stdin — для потоков.

## Полный разбор фаззинга реальной цели

Разберём сквозной пример. Дано: CLI-парсер, принимающий файл. Цель — найти баг. Шаги: (1) соберите цель с `afl-clang-fast` и ASan (`AFL_USE_ASAN=1`); (2) подготовьте seeds — валидные файлы минимального размера; (3) добавьте словарь с ключевыми строками формата; (4) запустите AFL++ параллельно (master + slaves); (5) через несколько часов/дней соберите креши из `out/default/crashes/`; (6) триажьте: воспроизведите каждый креш (`./target < crash`), классифицируйте (ASan-отчёт покажет тип: heap-buffer-overflow, use-after-free, stack-overflow); (7) для эксплуатируемых багов постройте эксплойт. AFL++ покажет статистику (покрытие, exec/s, уникальные пути). Увеличивайте время фаззинга, добавляйте seeds по мере нахождения новых путей.

## Триаж и минимизация

После фаззинга нужно триажить креши: (1) воспроизвести; (2) определить тип (ASan/GDB); (3) дедуплицировать (одинаковые баги); (4) минимизировать вход (`afl-tmin`, `afl-cmin`) для упрощения; (5) оценить эксплуатируемость. `afl-tmin -i crash -o min -- ./target @@` уменьшит вход до минимального, вызывающего креш. Это критично: минимизированный вход проще анализировать и использовать в эксплойте. Затем постройте PoC и, при необходимости, эксплойт (например, heap overflow → RCE). Фаззинг находит баги, но эксплуатация — отдельный этап.

## libFuzzer: сетап и структуры

libFuzzer требует функцию `LLVMFuzzerTestOneInput(const uint8_t *data, size_t size)`, которая вызывает цель с данными. Сборка: `clang -fsanitize=fuzzer,address -o fuzz fuzz.c target.c`. Запуск: `./fuzz corpus/` (corpus — директория с seeds). libFuzzer сам мутирует и отслеживает покрытие, сохраняя интересные входы в corpus. Для структурных данных используйте `FuzzedDataProvider` (C++). libFuzzer быстрее AFL++ (in-process), но требует, чтобы цель была функцией. Идеален для библиотек, парсеров, API. Комбинируйте с ASan/UBSan для обнаружения багов.

## Разбор ASan-отчётов при фаззинге

ASan (AddressSanitizer) — ключевой инструмент триажа. При креше он выводит отчёт: тип бага (`heap-buffer-overflow`, `use-after-free`, `stack-buffer-overflow`, `global-buffer-overflow`), адрес, стек вызовов и карту памяти вокруг. Разбор: (1) прочитайте тип — он определяет эксплуатируемость; (2) посмотрите стек — где именно баг; (3) обратите внимание на «shadow bytes» — показывают доступную/недоступную память; (4) используйте минимизированный вход. Например, `heap-buffer-overflow WRITE of size 8` указывает на запись за границей heap-буфера — потенциально эксплуатируемо. `use-after-free` — UAF. `SEGV on unknown address` может быть NULL-deref (менее интересен). ASan замедляет цель (~2x) и увеличивает память, но находит больше багов. Всегда собирайте фаззер с ASan.

## Fuzzing harnesses: советы

Качество harness'а определяет эффективность фаззинга. Советы: (1) вызывайте цель напрямую (не через shell); (2) избегайте лишнего I/O; (3) сбрасывайте состояние между вызовами (для persistent mode); (4) обрабатывайте исключения/сигналы; (5) используйте `FuzzedDataProvider` для структурированных данных; (6) добавьте `__AFL_LOOP` для persistent-режима AFL++ (многократный вызов в одном процессе — огромный прирост скорости). Для сетевых сервисов используйте пре-форк-модель (AFL++ `-M/-S` с forkserver). Для файловых форматов — принимайте путь через `@@`. Хороший harness — половина успеха фаззинга; плохой (например, с большим оверхедом) даёт низкий exec/s и мало находок.
