N-day exploitation — это эксплуатация уже исправленных уязвимостей (с известным CVE) в непропатченных системах. В отличие от 0-day, для N-day есть патч, advisory и часто публичный PoC, что упрощает работу. Метод: patch diff (сравнение уязвимой и исправленной версий) для локализации бага, затем анализ и адаптация эксплойта под целевую версию. N-day — основной сценарий реального пентеста: большинство систем уязвимы к уже известным багам. В этом уроке — процесс N-day, patch diff, поиск PoC, адаптация и практические примеры.

## Процесс N-day

1. **Идентификация версии.** Определите точную версию цели (`--version`, баннеры, `/proc/version`, файлы).
2. **Поиск CVE.** Используйте базы (NVD, exploit-db, GitHub advisories) для известных уязвимостей этой версии.
3. **Patch diff.** Скачайте уязвимую и исправленную версии, сделайте diff (`git diff`, `diff -ru`), локализуйте исправление.
4. **Анализ.** Поймите баг по патчу (что проверялось/не проверялось).
5. **Поиск/написание PoC.** Ищите публичный PoC (exploit-db, GitHub) или пишите свой.
6. **Адаптация.** Подстройте PoC под целевую версию/окружение.
7. **Эксплуатация.** Проверьте наименее деструктивно, затем получите цель.

## Patch diff на практике

```bash
# скачать две версии
git clone https://github.com/vendor/project
cd project
git log --oneline | head
git diff v1.0 v1.1 -- path/to/affected.c
# или сравнить архивы
diff -ru vulnerable/ patched/ | grep -A20 "buffer\|memcpy\|size"
```

Ищите изменения в проверках границ, длинах, типах. Патч часто добавляет проверку — значит, баг был в её отсутствии. Если патч меняет `if (len > MAX)` на `if (len >= MAX)`, баг — off-by-one. Если добавляет `free(ptr); ptr = NULL;` — баг — UAF. Патч — прямая карта к уязвимости.

## Поиск и оценка PoC

Источники: `exploit-db` (`searchsploit`), GitHub (`CVE-XXXX-YYYY`), Metasploit modules, nuclei templates. При использовании публичного PoC: (1) прочитайте код (не запускайте вслепую); (2) проверьте, куда он обращается (не эксфильтрует ли данные); (3) оцените деструктивность (может ли уронить сервис); (4) адаптируйте под цель (IP/порт/пути); (5) проверьте версию. PoC — отправная точка, но часто требует доработки.

## Разобранный пример: CVE в парсере

```text
1) Цель: сервис v1.2.3. Известен CVE-2021-XXXX (heap overflow в парсере).
2) Patch diff: исправление добавляет проверку длины перед memcpy.
3) Баг: memcpy с user-контролируемой длиной -> heap overflow.
4) PoC: отправить пакет с длиной > буфера.
5) Эксплойт: переполнить чанк, получить контроль (по обстоятельствам).
6) Адаптация: учесть версию/архитектуру/ASLR.
```

- **pwntools** — разработка эксплойта.

## Частые ошибки

- **Неверная версия.** CVE для другой версии.
- **Запуск PoC вслепую.** Может быть вредоносным или деструктивным.
- **Игнорирование окружения.** PoC для другой архитектуры/ОС.
- **Падение сервиса.** Эксплойт может убить цель — тестируйте осторожно.
- **Патч не тот.** Иногда CVE не соответствует патчу.

## Полный разбор N-day на примере

Разберём сквозной пример. Дано: веб-сервер версии X, известно о CVE-2023-XXXX. Шаги: (1) подтвердите версию (баннер, `--version`); (2) найдите advisory (NVD) — описание, affected versions, ссылки; (3) скачайте патч (коммит в GitHub) и сделайте `git diff` — локализуйте изменение; (4) поймите баг: например, патч добавляет проверку длины в парсере заголовков → был buffer overflow; (5) найдите публичный PoC (GitHub, exploit-db) или напишите свой; (6) адаптируйте: измените путь/порт, учтите версию/архитектуру, проверьте смещения; (7) проверьте наименее деструктивно (например, отправьте безопасный запрос, вызывающий креш в контролируемых условиях); (8) эксплуатируйте. Логируйте всё и не роняйте сервис без необходимости.

## Patch diff: инструменты и приёмы

`git diff v1.0 v1.1` — базовый способ. Если патч в одном коммите: `git show <commit>`. Для бинарных патчей: `bindiff` (BinDiff, Diaphora) — сравнение двух бинарей, показывающее изменённые функции. Это мощно, когда нет исходников: скачайте уязвимую и исправленную версии бинаря, сравните — изменённая функция = место бага. Для прошивок/embedded — `binwalk` + bindiff. Патч часто «инвертирует» логику: то, что раньше проходило, теперь блокируется. Изучайте проверки: добавленные `if`, изменённые сравнения, новые `free`/`NULL`. Каждый патч — карта к уязвимости.

## Адаптация PoC и оценка риска

Публичный PoC — отправная точка, но он может: (1) быть для другой версии/ОС/архитектуры; (2) использовать фиксированные адреса (нужна адаптация под ASLR/версию); (3) быть деструктивным (ронять сервис); (4) содержать вредоносный код (читайте перед запуском!). Адаптация: измените цели (IP/порт), смещения (под вашу libc/бинарь), payload (под ваш случай). Оценка риска: может ли PoC уронить сервис? Если да — адаптируйте до безопасной проверки или согласуйте. В реальном пентесте цель должна остаться живой; используйте маркеры и минимально инвазивные проверки.

## Разбор CVE и патча: практические советы

Эффективный разбор CVE: (1) прочитайте advisory целиком — там часто есть описание бага и affected versions; (2) найдите коммит-фикс по ссылке; (3) `git show` покажет изменения; (4) сопоставьте с вашей версией — если она до фикса, уязвима; (5) проверьте, есть ли публичный PoC. Иногда advisory неполный, и patch diff — единственный способ понять баг. Ищите изменения в: проверках границ, обработке ошибок, управлении памятью (`free`/`malloc`), типах, целочисленной арифметике. Каждое изменение — подсказка. Ведите заметки по CVE: версия, тип, примитив, PoC. Это ускоряет будущие задачи.

## Bindiff для бинарных патчей

Когда исходников нет, используйте BinDiff/Diaphora: (1) откройте уязвимый и исправленный бинари в IDA/Ghidra; (2) экспортируйте в формате для bindiff; (3) запустите сравнение — оно покажет совпавшие и изменённые функции; (4) изменённые функции — кандидаты на баг. Это мощный метод для прошивок, драйверов, проприетарного ПО. Для embedded: `binwalk -e firmware.bin`, найдите бинари, сравните с исправленной версией. Bindiff экономит часы ручного анализа. Изучите инструменты (BinDiff от Google, Diaphora для IDA/Ghidra) и практикуйтесь на известных CVE (например, в роутерах).
