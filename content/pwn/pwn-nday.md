## Вопрос, с которого всё начинается

Ты хочешь эксплуатировать реальный продукт, но не знаешь, где в нём баг. Ответ часто лежит прямо на виду: **производитель выпустил обновление безопасности**. Патч показывает, что именно было сломано. Если понять патч — ты знаешь уязвимость. Это называется **N-day exploitation**: баг уже исправлен в новой версии, но старая всё ещё стоит у многих. Разберём весь путь: от коммита до эксплойта.

## Наш пример

Представим библиотеку-парсер. Есть две версии: `v1.2` (уязвимая) и `v1.3` (пропатченная). Смотрим историю и диффим:

```
$ git log --oneline v1.2..v1.3
9f3c1a2 Fix heap overflow in parse_header (CVE-2024-XXXX)

$ git show 9f3c1a2
diff --git a/src/parse.c b/src/parse.c
@@ -42,6 +42,8 @@ int parse_header(const uint8_t *buf, size_t len) {
     uint16_t name_len = read_u16(buf);
+    if (name_len > len - 2)
+        return -1;
     memcpy(dest, buf + 2, name_len);
```

Вот и баг: в `v1.2` **не было проверки** `name_len > len - 2`. `name_len` читается из данных, а `memcpy` копирует его байт в `dest` — если `name_len` больше реального буфера, получаем **heap overflow**. Патч просто добавил проверку.

## Шаг 1: получаем обе версии

Первое — добыть исходники (или бинарники) уязвимой и исправленной версий:

```
$ git clone https://github.com/vendor/lib && cd lib
$ git tag -l
v1.2
v1.3
$ git checkout v1.2     # уязвимая
```

Если исходников нет, работают с **бинарниками** релизов (об этом — Шаг 5).

## Шаг 2: диффим и находим исправление

Ищем коммиты, связанные с безопасностью:

```
$ git log --oneline v1.2..v1.3 --grep='fix\|overflow\|bounds\|CVE' -i
```

Или диффим всё:

```
$ git diff v1.2 v1.3 -- src/
```

Любое добавление **проверки границ, длины, типа** — потенциальный фикс уязвимости. В нашем примере это `if (name_len > len - 2) return -1;`.

## Шаг 3: инвертируем фикс — понимаем баг

Ключевой приём: **фикс показывает, чего не хватало**. Спроси себя:

- Что проверяет патч? → что вход может быть **больше**, чем ожидалось.
- Где эта проверка отсутствует в старой версии? → там и баг.
- Как это использовать? → подсунуть `name_len` больше реального размера.

В нашем случае: контролируем `name_len` (первые 2 байта заголовка), `dest` фиксированного размера, `memcpy` копирует слишком много → переполнение кучи. Причём `name_len` — `uint16_t`, максимум `65535` байт, чего хватит, чтобы выйти далеко за пределы буфера.

## Шаг 4: воспроизводим

Собираем уязвимую версию и пишем минимальный вход:

```python
import socket
name = b"A" * 0x2000                      # большое значение
pkt  = len(name).to_bytes(2, 'little')    # name_len из данных
pkt += name
```

Отправляем в сервис/парсер и смотрим падение:

```
$ ./lib_v1.2 < crash.bin
Segmentation fault (core dumped)
```

Проверяем в ASan-сборке — она подтвердит тип бага:

```
$ gcc -fsanitize=address ... && ./lib_v1.2_asan < crash.bin
==12345==ERROR: AddressSanitizer: heap-buffer-overflow ... in parse_header
```

Теперь у нас есть **воспроизводимый N-day**.

## Шаг 5: от краша к эксплойту

Дальше — обычная работа:

1. **Понять примитив**: сколько переполняем, что затираем (chunk метаданные, соседний объект).
2. **Учесть защиты** конкретной сборки (`checksec`): canary, PIE, RELRO, ASLR.
3. **Выбрать технику** по таблице рецептов: heap-эксплуатация (tcache/unsorted), утечка адреса, ROP.
4. **Написать эксплойт** и стабилизировать его (особенно если ASLR/тайминги).

Важно: **эксплойт зависит от версии**. Другая версия — другие адреса, другой аллокатор, другой layout. Поэтому для каждого таргета — своя подгонка.

## Шаг 6: когда исходников нет — бинарный диффинг

Часто патч доступен только в виде **нового бинарника**. Тогда используют **binary diffing**:

- **Diaphora** (плагин IDA) и **BinDiff** сравнивают две версии и показывают изменённые функции.
- **radiff2** (из radare2) — быстрый дисплей `radiff2 -C old new`.
- Изменённая функция с новой проверкой — это и есть место фикса.

Логика та же: найди, **что изменилось**, и инвертируй. Только вместо строк кода сравниваешь графы функций.

## Шаг 7: N-day vs 1-day и как защищаются

Разберём термины, чтобы не путаться:

- **0-day** — уязвимость, о которой производитель не знает; патча нет.
- **1-day** — патч **вышел**, но он ещё очень свежий, и многие системы не успели обновиться. «Золотое окно» для атакующего — дни и недели после релиза фикса.
- **N-day** — патч вышел давно, но старая версия всё ещё стоит где-то.

Практический вывод: **чем быстрее ты разберёшь патч после релиза, тем ценнее N-day**. Именно поэтому компании мониторят обновления и диффят их в первые часы.

Как защищается обороняющаяся сторона:

- **Быстрое обновление.** Чем меньше окно между патчем и установкой, тем меньше N-day-риск.
- **Автоматический диффинг.** Некоторые вендоры сами публикуют детали CVE — это ускоряет и защиту, и атаку.
- **Defense in depth.** Даже при N-day взрыв не должен давать полный контроль: сегментация, ASLR, sandbox, EDR.

Отдельно стоит упомянуть **гражданскую ответственность**: N-day-эксплуатация против чужих систем без разрешения — преступление. В рамках пентеста или CTF — законно; вне их — нет.

Ещё один практический совет: **веди архив версий**. Скачивай релизы сразу, пока они доступны: старые версии иногда удаляют из репозиториев, и тогда диффить становится не с чем. Многие исследователи держат локальные зеркала популярных проектов именно для этого.

И последнее: **не все N-day равны**. Баг с готовым публичным PoC («weaponized») эксплуатируется за минуты, а баг, для которого есть только патч, требует полного цикла — от диффа до стабилизации. Оценивай задачу по тому, что уже доступно публично, и не трать часы там, где есть готовое решение.

Ещё полезно уметь **отличать security-фикс от обычного рефакторинга**. В коммите ищи: добавленную проверку границ, смену типа на более широкий, экранирование ввода, изменение порядка проверок. Это сигналы фикса. Обычный рефакторинг (переименование, форматирование) тебя не интересует. Тренируйся на реальных репозиториях: открой любой проект, отфильтруй коммиты по слову `fix` и попробуй угадать, какой из них — security.

## Что мы теперь знаем

- **N-day** — эксплуатация уже исправленной уязвимости в старой версии.
- Патч показывает баг: **добавленная проверка** указывает, чего не хватало.
- Порядок: **получить версии → диффить → инвертировать фикс → воспроизвести → эксплуатировать**.
- Эксплойт **привязан к версии**; для другой сборки — пересобирать адреса.
- Без исходников работает **бинарный диффинг** (Diaphora, BinDiff, radiff2).

## Куда дальше

Мы научились превращать патч в эксплойт. Дальше — **Rust/Go бинари**: почему они «безопаснее», но всё равно ломаются, и что меняется в их анализе. А пока запомни главное: **патч — это карта уязвимости; найди изменение и инвертируй его.**

## Где пригодится

- **Red team:** эксплуатация реальных продуктов с известными CVE.
- **Bug bounty:** понимание фиксов помогает искать похожие баги.
- **Vulnerability research:** diffing — базовый метод.
- **Blue team:** оценка, какие системы уязвимы, по версиям.
