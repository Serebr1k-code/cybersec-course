В современном ядре Linux классические heap-атаки (fastbin dup, unsorted bin) неприменимы: SLUB не хранит сложных метаданных, а объекты разных типов живут в разных кэшах. Cross-cache attack обходит это ограничение: атакующий заставляет ядро освободить **целую страницу** slab одного кэша и переиспользовать её как страницу другого кэша. Тогда объект из кэша A оказывается в памяти, где теперь живут объекты кэша B, — и UAF из A позволяет управлять B.

В этом уроке — устройство SLUB, механику cross-cache, условия и практический пример. Материал открывает модуль `pwn-kernel-modern`.

## Что такое cross-cache attack

SLUB выделяет память страницами (обычно 4 КБ), которые делятся на объекты фиксированного размера. У каждого типа объекта (например, `kmalloc-64`, `cred_jar`, `filp`) свой кэш. Атакующий обычно получает UAF на объект кэша A. Чтобы эксплуатация стала возможной, нужно, чтобы память объекта перешла в кэш B, где лежит «цель» (например, `cred` или `pipe_buffer`).

Cross-cache делает именно это: если освободить **все** объекты на slab-странице, ядро может вернуть страницу в buddy allocator. Затем другой кэш запросит страницу и получит её же. Теперь «старый» объект из A лежит поверх объекта из B.

## SLUB и slab-кэши

| Понятие | Описание |
|---|---|
| slab | набор страниц одного кэша |
| cache | кэш объектов фиксированного размера |
| kmalloc-N | общий кэш для размера N |
| slab page | страница (или несколько), нарезанная на объекты |
| freelist | список свободных объектов |

SLUB хранит freelist внутри самих объектов (указатель на следующий свободный). Метаданные минимальны, поэтому «классических» атак на них почти нет — отсюда ценность cross-cache.

## Почему нужен cross-cache

Без cross-cache UAF на объекте кэша A даёт контроль только над объектами A. Если целевой объект (например, `cred`) в другом кэше, напрямую его не переиспользовать. Cross-cache «перекидывает» память между кэшами и делает UAF универсальным. Это ключевая техника для эксплуатации UAF в modern kernel.

## Механика: освобождение страниц

Схема:

1. **Массово выделить** объекты кэша A, чтобы занять целые slab-страницы (желательно, чтобы на странице были только ваши объекты).
2. **Создать дыру** — освободить один объект (получив UAF-указатель).
3. **Освободить остальные** объекты на этой же странице, чтобы страница стала полностью свободной.
4. **Спровоцировать возврат страницы** в buddy allocator (иногда требуется «ударить» по кэшу: `drain` через выделение/освобождение или вызвать `kmem_cache_shrink`).
5. **Заставить кэш B** выделить страницы и получить ту же физическую страницу.
6. Теперь UAF-указатель указывает на объект кэша B — эксплуатируем.

## Инструменты и команды

```bash
# посмотреть slab-кэши и их размеры
sudo cat /proc/slabinfo | head -30

# конкретный кэш
sudo cat /proc/slabinfo | grep -E "kmalloc-64|cred_jar|filp"

# версия ядра
uname -r

# проверить, включён ли SLUB (обычно да)
cat /boot/config-$(uname -r) | grep -E "CONFIG_SLUB|CONFIG_SLAB"

# трассировка slab-операций (через ftrace)
sudo trace-cmd record -e kmem:kmalloc -e kmem:kfree
```

`/proc/slabinfo` показывает, сколько объектов и slab-страниц в каждом кэше. Если у кэша A `slabs` не уменьшается при освобождении — страница не возвращается, и cross-cache не сработает; тогда нужно «выдавить» кэш.

## Разобранный пример

Пусть есть UAF на объекте `kmalloc-64`. Хотим переиспользовать память под `cred` (структура привилегий). Шаги:

```c
// 1. занять страницы kmalloc-64
for (i = 0; i < 4096; i++) spray_64(i);

// 2. освободить один (получаем UAF)
free_64(victim_idx);

// 3. освободить все остальные на странице
for (i = 0; i < 4096; i++)
    if (i != victim_idx) free_64(i);

// 4. спровоцировать возврат страницы и захват её cred_jar
for (i = 0; i < 1000; i++) fork();   // создаём процессы -> cred

// 5. теперь UAF-указатель -> объект cred
```

Ожидаемый результат: чтение/запись через UAF меняет `cred`, повышая привилегии.

## Полный эксплойт (концептуально)

```c
// после cross-cache: UAF-указатель указывает на cred
struct cred *c = (struct cred *)victim;
c->uid = 0;
c->gid = 0;
c->euid = 0;
c->egid = 0;
// -> getuid() == 0
```

В реальном эксплойте нужно ещё обойти проверки ядра (например, `cred` может быть immutable) и синхронизировать аллокации, но принцип именно такой: memory из-под одного типа объекта становится памятью другого.

## Ограничения

- **Стабильность.** Cross-cache нестабилен: страница может не вернуться или быть захвачена другим кэшем.
- **Ядерные настройки.** Некоторые конфигурации (`CONFIG_SLAB_FREELIST_RANDOM`, hardening) мешают.
- **Время.** Нужны тысячи аллокаций; в CTF это допустимо, в реальной атаке — заметно.
- **Проверки.** Ядро может проверять `cred` при использовании.

## Практика: наблюдение за slab

Ключ к успешному cross-cache — видеть, что происходит с slab-страницами. `/proc/slabinfo` даёт снимок: число активных объектов, общее число объектов и число slab-страниц. Формат строки: `name active_objs num_objs objsize objperslab pagesperslab ...`. Следите за колонкой `num_slabs` (число страниц): когда вы массово освобождаете объекты, она должна уменьшаться, если страницы возвращаются.

Если `num_slabs` не падает, кэш «держит» пустые страницы (это нормально для SLUB — он кэширует их). Тогда нужен `drain`: например, через `/proc/sys/vm/drop_caches` (если есть права) или через массовые операции, вынуждающие ядро вернуть память. В CTF часто используют спам и освобождение в цикле, чтобы «продавить» кэш.

## Связь с другими техниками

Cross-cache — не цель, а инструмент. Он открывает путь к:

- **DirtyCred** (см. `pwn-dirtycred`) — перенос страницы в `cred_jar` для подмены привилегий;
- **pipe_buffer hijack** — переиспользование под `pipe_buffer` для произвольного чтения/записи;
- **msg_msg** — классический объект для kernel heap-эксплуатации;
- **перезапись `modprobe_path`** — если удаётся получить произвольную запись.

Освоив cross-cache, вы получаете универсальный «переходник» между кэшами, который применяется почти в каждой современной kernel-задаче с UAF. Именно поэтому его изучают сразу после базового kernel heap.

## Почему cross-cache стал обязательным

Раньше kernel-эксплуатация полагалась на «классические» heap-атаки: перезапись `cred` напрямую, атаки на freelist, переполнения. С ужесточением SLUB (freelist hardening, рандомизация, разделение кэшей по типам) эти приёмы умерли. Cross-cache появился как ответ: если нельзя атаковать объект напрямую, «пересадите» его память в другой кэш, где лежит удобная цель.

Сегодня cross-cache — базовый навык для эксплуатации UAF в ядре. Он используется в публичных эксплойтах для Android, ChromeOS, десктопного Linux. Без него большинство современных UAF просто не эксплуатируются. Именно поэтому его изучают сразу после базового kernel heap и перед DirtyCred.

## Практика: как понять, что страница «переехала»

Ключевой момент — убедиться, что UAF-указатель теперь указывает на объект другого кэша. Практический способ: после cross-cache «посадите» в кэш B объект с узнаваемым содержимым (например, заполните `cred` известными значениями) и прочитайте память через UAF. Если увидите своё содержимое — переезд удался. Если видите старые данные кэша A — страница не вернулась или её захватил другой кэш.

Также полезно мониторить `/proc/slabinfo` до и после: уменьшилось ли число страниц в кэше A, выросло ли в кэше B. Это даёт объективную картину. Если страница «застряла», увеличьте объём спама или добавьте принудительный drain.

Ещё один приём — «подкрашивание»: заполните объекты кэша A уникальным маркером и после переезда поищите этот маркер в памяти кэша B. Если маркер не найден, страница не переехала. Это быстрее, чем сверять `/proc/slabinfo` вручную, и работает даже без отладочных символов ядра. Комбинируйте оба способа: маркер для быстрой проверки, slabinfo — для подтверждения.

## Итог и что запомнить

Cross-cache — мост между кэшами SLUB: освободите всю slab-страницу, заставьте ядро вернуть её и переиспользовать под другой тип объектов. Это делает UAF универсальным и лежит в основе большинства современных kernel-эксплойтов. Запомните последовательность «spray → free всей страницы → reclaim → reallocate» и умейте проверять переезд через `/proc/slabinfo` и маркеры.

## Частые ошибки

- **Не освободить всю страницу.** Если хоть один объект занят, страница не вернётся.
- **Не «выдавить» кэш.** Иногда нужен `kmem_cache_shrink` или массовые операции.
- **Слишком мало спама.** Для захвата страницы нужно много объектов.
- **Неверный размер.** Кэш B должен запрашивать тот же порядок страниц.
- **Игнорировать стабильность.** Прогоняйте эксплойт много раз.

## Что дальше / решение
