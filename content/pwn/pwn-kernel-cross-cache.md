## Вопрос, с которого всё начинается

Мы знаем, что в ядре UAF даёт перекрытие объектов **одного** кэша: освободил объект `kmalloc-64` — занял его другим `kmalloc-64`. Но что, если целевой объект (например, `cred` или `pipe_buffer`) живёт в **другом** кэше? Тогда прямой перезаписи не получится. Обойти это ограничение позволяет **cross-cache attack**: она заставляет ядро переиспользовать целую страницу одного кэша под другой. Сегодня разберём, как это работает.

## Наш пример: смотрим slab-кэши

Посмотрим, какие кэши есть в системе:

```
$ uname -r
6.19.11-arch1-1
$ ls /sys/kernel/slab/ | grep -E '^(cred|filp|kmalloc-64|kmalloc-512|msg_msg-128|seq_file|skbuff_head_cache)$' | sort
cred
filp
kmalloc-512
kmalloc-64
msg_msg-128
seq_file
skbuff_head_cache
```

Каждое имя — отдельный кэш. Всего в системе сотни кэшей (`ls /sys/kernel/slab/ | wc -l` покажет число). У каждого кэша свой размер объектов: `kmalloc-64` — объекты по 64 байта, `msg_msg-128` — по 128, `cred` — структура привилегий процесса.

## Шаг 1. SLUB и slab-страницы

SLUB выделяет память **страницами** (обычно 4 КБ). Каждая страница нарезается на объекты **одного** размера. Термины:

| Понятие | Описание |
|---|---|
| cache | кэш объектов фиксированного размера |
| slab | набор страниц одного кэша |
| slab page | страница, нарезанная на объекты |
| freelist | список свободных объектов |

SLUB хранит `freelist` **внутри самих объектов** (указатель на следующий свободный). Метаданные минимальны, поэтому «классических» атак на них почти нет — отсюда ценность cross-cache.

## Шаг 2. Почему нужен cross-cache

Без cross-cache UAF на объекте кэша A даёт контроль только над объектами A. Если цель — `cred` (в кэше `cred`) или `pipe_buffer` (в `kmalloc-1k`), напрямую его не переиспользовать. Cross-cache «перекидывает» память между кэшами и делает UAF **универсальным**: старый объект из A оказывается поверх объекта из B.

Ключевая идея: если освободить **все** объекты на slab-странице, ядро может вернуть страницу в buddy allocator (общий менеджер страниц). Затем другой кэш запросит страницу и получит **ту же самую**. Теперь «старый» UAF-указатель из A указывает на объект из B.

## Шаг 3. Механика

Схема:

1. **Массово выделить** объекты кэша A, чтобы занять целые slab-страницы (желательно, чтобы на странице были только ваши объекты).
2. **Создать дыру** — освободить один объект, получив UAF-указатель.
3. **Освободить остальные** объекты на этой же странице, чтобы страница стала полностью свободной.
4. **Спровоцировать возврат страницы** в buddy allocator.
5. **Заставить кэш B** выделить страницы и получить ту же физическую страницу.
6. Теперь UAF-указатель указывает на объект кэша B — эксплуатируем.

Шаг 4 — самый тонкий. Ядро не всегда сразу возвращает освобождённую страницу: SLUB держит «частичные» страницы для повторного использования. Чтобы страница вернулась, нужно либо опустошить кэш целиком, либо «ударить» по нему (drain через массовые выделения/освобождения, либо `kmem_cache_shrink`).

## Шаг 4. Условия и «выдавливание» кэша

Cross-cache требует, чтобы на выбранной странице лежали **только** объекты нужного кэша. Если на странице есть чужие объекты, страница не освободится. Поэтому сначала «прогревают» кэш: делают много аллокаций, чтобы новые страницы целиком принадлежали вам, затем работают с одной такой страницей.

Также важно, чтобы целевой объект кэша B действительно аллоцировался **после** возврата страницы. Для этого кэш B «выдавливают»: заставляют его запросить новые страницы (например, создавая много `cred` или `pipe`), чтобы он подхватил освободившуюся.

Понимание buddy allocator помогает настраивать cross-cache. Buddy allocator — это менеджер физических страниц ядра: он выдаёт страницы кэшам и забирает обратно. Когда SLUB освобождает последнюю slab-страницу кэша, он возвращает её в buddy. Но SLUB не спешит это делать: у него есть пороги (`min_partial`), и он держит несколько частичных страниц «про запас». Пока кэш держит свободную страницу, другой кэш её не получит. Именно поэтому «выдавливание» (drain) — обязательный шаг: нужно либо превысить порог, либо заставить кэш освободить свои частичные страницы. На практике это делают циклами аллокаций/освобождений большого числа объектов, пока страница не вернётся. Полезно также следить за счётчиком `slabs` кэша (в `/proc/slabinfo` при наличии прав): если он не уменьшается, страница не возвращается, и cross-cache не сработает.

## Шаг 5. Практический пример

Пусть есть UAF на объекте `kmalloc-64`, а цель — `cred`. Шаги (эскиз):

```c
/* 1. занять страницы kmalloc-64 */
for (i = 0; i < 4096; i++) spray_64(i);
/* 2. освободить один (получаем UAF-указатель) */
free_64(victim_idx);
/* 3. освободить остальные объекты на той же странице */
for (i = 0; i < 4096; i++)
    if (i != victim_idx) free_64(i);
/* 4. выдавить кэш, чтобы страница вернулась */
drain_64();
/* 5. заставить кэш cred выделить страницы */
spray_cred();
/* 6. UAF-указатель из kmalloc-64 теперь указывает на cred */
```

Проверять процесс удобно в QEMU с gdb: смотрите, какой странице принадлежит объект, и меняется ли она после выдавливания.

## Если не сработало

- **Страница не возвращается.** Нужно «выдавить» кэш (drain) или опустошить его целиком.
- **На странице чужие объекты.** Прогрейте кэш массовыми аллокациями.
- **Кэш B не подхватил страницу.** Заставьте его запросить новые страницы после возврата.
- **Не тот размер.** Убедитесь, что UAF-объект и цель в разных кэшах, как задумано.
- **Паника.** Ошибка в slab роняет систему; отлаживайте в QEMU.

## Что мы теперь знаем

- SLUB нарезает страницы на объекты одного размера; у каждого типа свой кэш.
- UAF напрямую переиспользует только объекты того же кэша.
- Cross-cache освобождает целую страницу и отдаёт её другому кэшу.
- Для этого нужно занять страницу своими объектами и «выдавить» кэш.
- После возврата страницы UAF указывает на объект другого кэша.
- Техника делает UAF универсальным в modern kernel.

## На что смотреть дальше

- **Кэши.** Имена и размеры в `/sys/kernel/slab/`.
- **Выдавливание.** Как заставить кэш вернуть страницу.
- **Прогрев.** Чтобы на странице были только ваши объекты.
- **Отладка.** QEMU + gdb, состояние slab-страниц.
- **Цель.** Какой объект вы хотите перекрыть (`cred`, `pipe_buffer`).

Заметим: cross-cache — не отдельный баг, а **техника**, которая применяется поверх уже найденной уязвимости (обычно UAF или double-free). Она не создаёт примитив сама, а лишь расширяет его действие на другой кэш. Поэтому в отчёте о задаче cross-cache фигурирует как шаг эксплуатации, а не как уязвимость.
