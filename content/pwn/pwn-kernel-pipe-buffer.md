## Вопрос, с которого всё начинается

Среди ядерных объектов есть один особенно удобный для эксплуатации — `pipe_buffer`. Он создаётся при вызове `pipe()`, имеет удобный размер и содержит указатели, перезаписав которые можно получить либо запись в произвольный файл, либо контроль потока выполнения. На нём построена знаменитая уязвимость **Dirty Pipe** (CVE-2022-0847). Сегодня разберём устройство `pipe_buffer` и оба примитива.

## Наш пример: смотрим параметры pipe

Прежде чем работать с pipe, посмотрим его параметры в системе:

```
$ uname -r
6.19.11-arch1-1
$ cat /proc/sys/fs/pipe-max-size
1048576
$ ulimit -p
8
$ cat /proc/sys/fs/pipe-user-pages-soft
16384
```

Читаем:

- `pipe-max-size = 1048576` — максимальный размер одного канала (1 МБ).
- `ulimit -p = 8` — размер pipe в блоках по 512 байт, то есть по умолчанию `8 × 512 = 4096` байт (одна страница).
- `pipe-user-pages-soft = 16384` — лимит страниц, которые пользователь может занять pipe-буферами.

Эти параметры показывают, что pipe — обычный объект ядра, размеры которого мы можем менять через `fcntl`.

## Шаг 1. Устройство pipe_buffer

`pipe()` создаёт канал. Внутри ядра данные канала описываются массивом структур `pipe_buffer`:

```c
struct pipe_buffer {
    struct page *page;       /* страница с данными */
    unsigned int offset;     /* смещение в странице */
    unsigned int len;        /* длина данных */
    const struct pipe_buf_operations *ops;  /* операции */
    unsigned int flags;
    unsigned long private;
};
```

Ключевые поля:

- `page` — указатель на **страницу** памяти, где лежат данные. Важно: это не копия данных, а именно страница.
- `offset`, `len` — где в странице начинаются данные и сколько их.
- `ops` — таблица операций (`release`, `try_steal`, `get`), которые ядро вызывает при работе с буфером.

## Шаг 2. Размер и кэш

Массив `pipe_buffer` по умолчанию — 16 элементов по `0x28` байт, то есть `0x280`, что округляется до кэша `kmalloc-1024`. Это делает его удобной целью для UAF-переиспользования: если уязвимый объект размером около `0x280` освобождён, `pipe_buffer` может занять ту же память.

## Шаг 3. Примитив 1: запись в page-cache (Dirty Pipe)

Идея Dirty Pipe: поле `page` в `pipe_buffer` может указывать на страницу **page-cache** любого файла. Page-cache — это кэш содержимого файлов в памяти; когда вы читаете файл, ядро держит его страницы в этом кэше.

Если мы контролируем `page`, `offset` и `len`, то запись в pipe (через `write`) изменит содержимое этой страницы в page-cache — то есть мы получаем запись в произвольный файл, **включая read-only** (например, `/etc/passwd` или SUID-бинарь). Dirty Pipe эксплуатировала именно это: флаги буфера не сбрасывались, и ядро позволяло «дописывать» в страницу за пределами допустимого.

Схема:

1. Подготовить pipe (заполнить и опустошить его, чтобы буферы были в нужном состоянии).
2. Перезаписать `page` на нужную страницу (например, страницу файла `/etc/passwd`).
3. Выставить `offset`/`len`.
4. Записать данные — они попадут в page-cache файла.

Практический эффект: можно изменить пароль root в `/etc/passwd` или подменить код SUID-программы, не имея прав на запись.

Разберём саму суть бага Dirty Pipe подробнее, потому что она поучительна. В ядре у буфера есть флаг `PIPE_BUF_FLAG_CAN_MERGE`, который разрешает «дописывать» новые данные в конец уже существующего буфера, если они помещаются в ту же страницу. При создании pipe флаги должны сбрасываться. Баг был в том, что при определённой последовательности операций (заполнить pipe, опустошить его) структура `pipe_buffer` сохраняла старый флаг. Тогда следующая запись в pipe «сливалась» в страницу, на которую указывал `page`, — а если подготовить `page` так, чтобы он указывал на page-cache нужного файла, запись попадала прямо в файл. Причём `offset` и `len` позволяли выбрать точное место.

Именно поэтому Dirty Pipe не требовала ни UAF, ни произвольной записи — только правильную последовательность `splice`/`write`. Это редкий пример «чистой» логической ошибки в ядре, дающей запись в read-only файлы. Исправление (в 5.16.11) сбрасывает флаги при инициализации буфера, поэтому на новых ядрах техника не работает напрямую. Но понимание `pipe_buffer` остаётся: тот же объект используется и для RIP-примитива через `ops`.

## Шаг 4. Примитив 2: RIP через ops

`pipe_buf_operations` содержит указатели на функции. При закрытии или освобождении pipe ядро вызывает `ops->release`. Если перезаписать `ops` на **поддельную таблицу**, где `release` указывает на гаджет или функцию, получим контроль потока выполнения:

```c
/* перезаписать pipe_buffer->ops на поддельную таблицу */
/* fake_ops->release = stack_pivot или гаджет */
close(pipe_fd);   /* вызовет ops->release */
```

Это прямой RIP-контроль в ядре, откуда дальше строят ROP (`commit_creds`) или используют `modprobe_path`.

Почему `ops` так удобен? Потому что `release` вызывается ядром **автоматически** при закрытии pipe — нам не нужно угадывать момент. Достаточно подготовить поддельную таблицу `pipe_buf_operations` (в контролируемой памяти, например в `msg_msg` или в другом pipe_buffer), перезаписать указатель `ops` на неё и закрыть дескриптор. Ядро само прыгнет по нашему указателю. Это делает связку «UAF + pipe_buffer» одним из самых надёжных способов получить RIP в ядерных задачах.

## Шаг 5. Полный сценарий: UAF → pipe_buffer → RIP

Эскиз (userland):

```python
# 1) освободить уязвимый объект размером ~0x280
ioctl(fd, FREE, 0)
# 2) создать pipe, чтобы занять память pipe_buffer
r, w = os.pipe()
# 3) записать данные, чтобы page/offset/len были валидны
os.write(w, b'A' * 0x100)
# 4) через UAF перезаписать pipe_buffer->ops на поддельную таблицу
write_uaf(p64(fake_ops_addr))
# 5) закрыть pipe -> вызвать ops->release -> RIP
os.close(r); os.close(w)
```

После получения RIP строят ROP для `commit_creds(prepare_kernel_cred(0))` или меняют `modprobe_path`.

## Если не сработало

- **Неверный размер.** `pipe_buffer` попадает в `kmalloc-1024`; уязвимый объект должен быть того же кэша.
- **Pipe не инициализирован.** Запишите данные, иначе `page`/`offset`/`len` невалидны.
- **KASLR.** Адреса `page`/`ops` нужно знать или утечь.
- **Dirty Pipe исправлена.** Проверяйте версию ядра (`uname -r`); флаги теперь сбрасываются.
- **Паника.** Неверный `page` приводит к краху ядра.

## Что мы теперь знаем

- `pipe_buffer` описывает буфер канала: `page`, `offset`, `len`, `ops`.
- Массив буферов живёт в `kmalloc-1024` (16 × `0x28`).
- Перезапись `page`/`offset`/`len` даёт запись в page-cache произвольного файла (Dirty Pipe).
- Перезапись `ops` даёт контроль RIP через `ops->release`.
- Размер и кэш делают `pipe_buffer` удобной целью UAF-переиспользования.
- Dirty Pipe исправлена сбросом флагов; проверяйте версию.

## На что смотреть дальше

- **Версия ядра.** Применима ли Dirty Pipe.
- **Кэш объекта.** `kmalloc-1024` для `pipe_buffer`.
- **Утечки.** Адреса `page`/`ops` при KASLR.
- **Отладка.** `b pipe_write`, `p *(struct pipe_buffer*)<addr>`.
- **Флаги буфера.** `PIPE_BUF_FLAG_CAN_MERGE` и его сброс.
