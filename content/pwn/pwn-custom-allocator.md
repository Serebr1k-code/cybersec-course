## Задача

Всё, что мы делали раньше, опиралось на устройство glibc: tcache, бины, safe-linking. Но в CTF часто дают бинарь, который **не использует** `malloc`/`free`, а реализует свой менеджер памяти — *кастомный аллокатор*. Зачем? Чтобы автор задачи контролировал, какие баги в нём есть, и чтобы нельзя было применить готовые приёмы. Наша цель: разобрать такой аллокатор, найти его слабое место и захватить управление.

## Данные, с которыми работаем

Возьмём маленький самописный аллокатор. Он держит один статический пул и список свободных блоков:

```c
#define POOL 0x1000
static char pool[POOL];
static unsigned long pool_off = 0;
static char *freelist = 0;

static void *my_alloc(unsigned long n){
    if (freelist){ char *r = freelist; freelist = *(char**)r; return r; }
    char *r = pool + pool_off;
    pool_off += (n + 0x10) & ~0xfUL;
    return r;
}
static void my_free(void *p){
    *(char**)p = freelist;        /* кладём блок в начало списка */
    freelist = p;
}
```

Разберём его по частям:

- `my_alloc` — если список свободных непуст, берёт блок оттуда; иначе «откусывает» от пула (bump-аллокатор).
- `my_free` — записывает в первые 8 байт блока указатель на текущую голову списка и делает блок новой головой.

Это классический **односвязный free-list**. Указатель на следующий свободный блок хранится прямо в освобождённом блоке.

## Пробуем в лоб

Первая мысль — «тут нет багов». Аллокатор детерминированный, размеры выровнены. Но присмотримся к `my_free`: он **не зануляет** указатель вызывающего кода и **не проверяет** повторное освобождение. Значит, у программы остаётся «висячий» указатель на освобождённый блок — это use-after-free. А ещё `my_free` не проверяет, что блок вообще из пула.

Проверим это на объекте с указателем на функцию:

```c
typedef void (*fp)(void);
struct obj { fp cb; char data[0x28]; };
```

## Приём

Захват управления строится в три шага:

1. Создаём объект, в котором есть указатель на функцию (`o->cb`).
2. Освобождаем объект, но программа сохраняет указатель `o` (UAF).
3. Аллоцируем объект того же размера — `my_alloc` вернёт **тот же блок** (голова free-list). Записываем туда свой указатель на функцию. Затем вызываем `o->cb()` через старый (висячий) указатель — и попадаем в нашу функцию.

Ключевое отличие от glibc: здесь нет tcache, нет проверок `safe-linking`, нет key-полей. Free-list простой, и переиспользование блока происходит мгновенно.

## Полный прогон от начала до конца

Добавим в программу штатный обработчик и «победную» функцию:

```c
static void good(void){ puts("good(): штатный обработчик"); }
static void win(void){ puts("WIN: управление захвачено"); }

int main(void){
    struct obj *o = my_alloc(sizeof(struct obj));
    o->cb = good;
    printf("o=%p  o->cb=%p\n", o, (void*)o->cb);
    o->cb();                                   /* штатный вызов */
    my_free(o);                                /* UAF: указатель не занулён */
    puts("o освобождён, но указатель жив");
    struct obj *o2 = my_alloc(sizeof(struct obj)); /* вернёт тот же слот */
    printf("o2=%p  (== o? %d)\n", o2, o2 == o);
    o2->cb = win;                              /* перезапись указателя функции */
    puts("вызываем o->cb() через UAF:");
    o->cb();                                   /* прыжок на win */
    return 0;
}
```

Компилируем и запускаем:

```
$ gcc -fno-pie -no-pie -O0 -o custom custom.c
$ ./custom

```

Успех: `o2` вернул ровно тот же адрес `0x404040`, что и `o`. Мы записали `win` в переиспользованный блок, и вызов через висячий указатель `o->cb()` прыгнул в нашу функцию. Это полный захват потока управления.

## Типовые классы багов в кастомных аллокаторах

Прежде чем строить эксплойт, полезно знать, какие баги встречаются чаще всего — по ним и ведут анализ.

1. **UAF из-за незанулённого указателя.** Как в нашем примере: `free` кладёт блок в список, но не обнуляет указатель в вызывающем коде.
2. **Double-free без проверки.** `my_free` не смотрит, лежит ли блок уже в списке. Двойное освобождение даёт два указателя на один блок — заготовка для перекрытия.
3. **Off-by-one в размере.** Аллокатор округляет размер вниз или вверх неправильно, и следующий блок «съезжает» — классическое перекрытие.
4. **Метаданные в общем пуле.** Если размер блока хранится прямо перед данными и не проверяется при освобождении, его можно подделать и получить запись мимо пула.
5. **Отсутствие проверки принадлежности пулу.** `my_free` принимает любой указатель — можно освободить область в `.bss` или на стеке (аналог House of Spirit).
6. **Использование освобождённого блока как списка.** Первые 8 байт свободного блока — указатель; если программа читает оттуда данные, вы управляете этим указателем.

Практический приём анализа: найдите функции `alloc`/`free`, выпишите, где хранятся размер и связи, и проследите, что происходит с указателем после освобождения. Чаще всего одного из шести пунктов достаточно, чтобы построить примитив.

## Если не сработало

- **Указатель зануляется после free.** Тогда чистого UAF нет — ищите другой баг: переполнение в блок, off-by-one в размер, ошибку в метаданных.- **Размеры не совпали.** `my_alloc` вернёт другой блок. Подбирайте размер так, чтобы блок лёг в ту же «дырку».
- **Аллокатор хранит метаданные отдельно.** Тогда UAF даёт доступ к метаданным — можно подделать размер и получить перекрытие.
- **Есть проверки.** Современные кастомные аллокаторы добавляют canary в метаданные или зануляют указатели — читайте исходник/дизассемблер.
- **Отладка.** Поставьте точку останова на `my_alloc`/`my_free` и смотрите, какой блок возвращается.

## Инструмент: objdump — дизассемблер

`objdump` показывает машинный код бинарника в виде ассемблера. Именно по нему считают смещения буферов, находят вызовы и адреса — основа статического разбора.

Ключи, которые пригодятся:
* `objdump -d <файл>` — дизассемблировать секцию `.text` (машинный код функций);
* `objdump -d <файл> | less` — листать вывод, искать нужную функцию по имени;
* `objdump -M intel -d <файл>` — синтаксис Intel (привычнее, чем AT&T);
* в выводе важны пролог функции (`push rbp; mov rbp,rsp`) и `sub rsp,N` — по нему видно размер кадра.

## Что мы теперь знаем

- Кастомный аллокатор может быть простым free-list или bump-аллокатором.
- Метаданные часто лежат прямо в блоке (первые 8 байт — указатель на следующий).
- Типовые баги: отсутствие зануления (UAF), отсутствие проверки double-free, ошибки в границах.
- Переиспользование блока даёт контроль над его содержимым.
- Объект с указателем функции превращает UAF в захват управления.
- Анализ начинается с чтения кода аллокатора, а не с готовых glibc-приёмов.

## На что смотреть дальше

- **Формат метаданных.** Где хранится размер и указатель на следующий блок.
- **Выравнивание.** Bump-аллокаторы часто округляют размер — учитывайте это.
- **Проверки.** Есть ли canary в метаданных, зануляется ли указатель.
- **Тип примитива.** UAF, overflow, double-free — какой доступен.
- **Цель.** Указатель функции, vtable, длина/индекс — что можно подменить.

## Куда дальше

В `pwn-house-roman` мы вернёмся к glibc и разберём запись в цель **без утечки libc** — через комбинацию fastbin и unsorted bin и частичную перезапись адреса. А пока главное: **кастомный аллокатор читай как код — его баги лежат в его собственной логике.**

## Где пригодится

- **CTF:** Pwn — heap-задачи с самописными аллокаторами.
- **Bug bounty:** проприетарные аллокаторы в продуктах.
- **Пентест:** анализ встраиваемого ПО.
- **Работа:** security research, exploit development.
