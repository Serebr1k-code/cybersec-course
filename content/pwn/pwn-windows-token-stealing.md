## Вопрос, с которого всё начинается

У тебя есть примитив произвольной записи в память ядра (из уязвимого драйвера).
Как из него получить права SYSTEM? Самый популярный путь — **подмена токена**
процесса. Разберём, что такое токен, где он лежит и как его подменить.

## Наш пример

Карта полей `_EPROCESS` для целевой сборки:

```
$ cat offsets.txt
_EPROCESS fields (build 22621):
  Pcb                 0x000
  UniqueProcessId     0x440
  ActiveProcessLinks  0x448
  Token               0x4b8
  ImageFileName       0x5a8
  InheritedFromUniqueProcessId 0x540
```

Нас интересует `Token` по смещению `0x4b8`. Разберём, что это за поле и как им
воспользоваться.

## Шаг 1: что такое токен

У каждого процесса Windows есть **access token** (`_TOKEN`) — структура,
описывающая «личность»: SID пользователя, группы, привилегии, уровень
целостности. Когда процесс открывает объект, ядро проверяет права **по его
токену**.

Если у процесса токен SYSTEM, он — SYSTEM. Значит, подмена токена = повышение
привилегий.

## Шаг 2: где лежит токен

Токен — указатель `_EPROCESS.Token` (смещение зависит от сборки, у нас
`0x4b8`). Найти нужный процесс можно через список `ActiveProcessLinks`
(`0x448`), а идентифицировать — по `UniqueProcessId` (`0x440`) и
`ImageFileName` (`0x5a8`).

Алгоритм: пройти список процессов, найти тот, у которого `UniqueProcessId == 4`
(SYSTEM), и взять его `Token`.

## Шаг 3: классический token-stealing

Классический shellcode в ядре:

1. **Найти** `_EPROCESS` текущего процесса (через `gs:[0x188]` —
   `KPCR.PrcbData.CurrentThread` → `_KTHREAD.ApcState.Process`).
2. **Пройти** список процессов, найти SYSTEM (PID 4).
3. **Скопировать** `Token` SYSTEM в наш `Token`.

Но современные митигации (**SMEP/SMAP**, **KVA shadow**, **HVCI**) мешают
исполнять user-shellcode в ядре. Поэтому чаще используют **data-only**
вариант.

## Шаг 4: data-only token stealing

Вместо shellcode — просто **запись**:

1. Из userland (или через примитив чтения) узнать адрес `_EPROCESS` нашего
   процесса и `Token` SYSTEM.
2. Примитивом записи положить SYSTEM-токен в наш `Token`.
3. Готово — процесс SYSTEM.

Нужны только **адреса**, которые добываются утечкой. Никакого исполнения кода
в ring 0.

## Шаг 5: почему токен, а не что-то другое

Альтернативы и их минусы:

- **Подмена `TokenPrivileges`** — выдать `SeDebugPrivilege`; сложнее и уже.
- **Правка callback-таблиц** — PatchGuard → BSOD.
- **Правка `modprobe`-аналогов** — не всегда есть.
- **Подмена токена** — проста, стабильна, не трогает защищённые структуры.

Именно поэтому token stealing — «золотой стандарт» kernel-эксплуатации
Windows.

## Шаг 6: проверка и подводные камни

- **Смещения зависят от сборки** — обязательно бери из символов конкретного
  `ntoskrnl.exe`.
- **KASLR** — нужна база ядра (утечка).
- **`UniqueProcessId` vs `InheritedFromUniqueProcessId`** — не перепутай.
- **Ссылки** — иногда токен «утекает» по refcount; простая подмена обычно
  работает.
- **Проверка**: после подмены `whoami` должен показать `nt authority\system`.

## Шаг 7: последовательность

1. **Утечка** базы ядра и адресов структур.
2. **Найти** `_EPROCESS` нашего процесса.
3. **Найти** `_EPROCESS` SYSTEM (PID 4) и его `Token`.
4. **Записать** SYSTEM-токен в наш `Token` (data-only).
5. **Проверить** привилегии (`whoami`).

## Как найти _EPROCESS в отладчике

WinDbg даёт готовые команды:

```
kd> !process 0 0              # список процессов (EPROCESS, PID, имя)
kd> dt _EPROCESS <addr> Token # значение поля Token
kd> !token <token_addr>       # разбор токена: SID, привилегии
kd> !process <addr> 7         # подробно, включая Token
```

`!process 0 0` выведёт список с адресами `_EPROCESS` и PID. Найди PID 4
(SYSTEM), возьми его `Token` — это цель для подмены. `!token` покажет, что это
действительно SYSTEM (`S-1-5-18`).

## Проверка результата

После подмены токена:

```
C:\> whoami
nt authority\system

C:\> whoami /priv
... SeDebugPrivilege ... Enabled
```

Если `whoami` показывает `system` — эксплойт удался. Дополнительно можно
проверить доступ к защищённым объектам (`\\.\PhysicalMemory`, реестр SAM).

## Частые ошибки

- **Неверные смещения.** Смещение `Token` зависит от сборки; бери из символов.
- **Перепутали поля.** `UniqueProcessId` vs `InheritedFromUniqueProcessId`.
- **Не учли KASLR.** Адреса структур нужно утечь.
- **Refcount.** При некоторых операциях ядро «удерживает» токен; простая запись
  обычно работает, но бывают нюансы.
- **Правка не того процесса.** Убедись, что пишешь в **свой** `_EPROCESS`.

## Альтернативные цели

Помимо подмены токена, есть и другие цели:

- **`TokenPrivileges`** — выдать `SeDebugPrivilege`/`SeLoadDriverPrivilege`,
  затем действовать легальными средствами.
- **`_EPROCESS.Protection`** — понизить уровень защиты процесса (PPL).
- **`_SEP_TOKEN_PRIVILEGES.Enabled`** — включить уже имеющиеся привилегии.
- **callback-таблицы** — перехват (рискованно из-за PatchGuard).

Token stealing остаётся самым прямым: одна запись — и процесс SYSTEM.

## Почему это «золотой стандарт»

- **Просто**: нужна одна запись указателя.
- **Стабильно**: не требует исполнения кода, не трогает защищённые структуры.
- **Обходит HVCI**: data-only, код не исполняется.
- **Проверяемо**: `whoami` подтверждает результат.

Именно поэтому token stealing — первый приём, который пробуют при наличии
произвольной записи в ядро Windows.

## Полный пример data-only цепочки

1. **Утечка** базы `ntoskrnl.exe` (KASLR сломан).
2. **Примитив чтения** находит `_EPROCESS` нашего процесса:

```
kd> !process 0 0
... 0000ffffa10b2c3d4080  MyProc.exe
```

3. **Чтение** поля `Token` нашего процесса и `Token` SYSTEM (PID 4).
4. **Запись** SYSTEM-токена в наш `Token` примитивом драйвера.
5. **Проверка**: `whoami` → `nt authority\system`.

Ни одного shellcode в ядре — только чтение и запись данных. Именно поэтому
цепочка проходит при HVCI.

## Работа с KASLR

Смещение `Token` фиксировано для **сборки**, но **база** `ntoskrnl` сдвинута
KASLR. Поэтому сначала:

- **утечка** адреса функции ядра → база;
- либо фиксированные смещения из `ntoskrnl.exe` целевой сборки.

Без базы адрес `_EPROCESS` неизвестен, и подмена токена невозможна. Связка
«утечка + смещение» — обязательна.

## Проверка привилегий

После подмены проверь не только `whoami`, но и токен:

```
kd> !token <наш_EPROCESS.Token>
_TS_EXPIRES ...
User: S-1-5-18 (Well Known Group: NT AUTHORITY\SYSTEM)
```

Если `!token` показывает `S-1-5-18` — токен действительно SYSTEM. Дополнительно
можно проверить доступ к защищённым объектам.

## Итоговый чек-лист

- [ ] База ядра утекла.
- [ ] Найден `_EPROCESS` своего процесса.
- [ ] Найден SYSTEM-токен (PID 4).
- [ ] Токен подменён примитивом записи.
- [ ] `whoami`/`!token` подтверждают SYSTEM.

## Как работает проверка прав

Когда процесс обращается к объекту (файлу, ключу реестра, процессу), ядро
вызывает подсистему безопасности (`SeAccessCheck`), которая сравнивает
**access token** процесса с **security descriptor** объекта. Токен содержит
SID пользователя, группы и привилегии. Если токен — SYSTEM (`S-1-5-18`), все
проверки проходят.

Именно поэтому подмена токена так эффективна: мы не обходим проверки — мы
**становимся** тем, кому всё разрешено. Никакие права не «взламываются», просто
у процесса теперь правильная личность.

## Разница между userland и kernel привилегиями

Важно понимать, что token stealing даёт **не** ring 0 сам по себе, а
**привилегии** в userland-контексте (SYSTEM). Для большинства задач (чтение
`SAM`, загрузка драйверов, доступ к защищённым объектам) этого достаточно.
Если же нужен именно ring 0, уже из SYSTEM можно загрузить драйвер или
использовать другой примитив.

Связка «произвольная запись в ядро → token stealing» — стандартный финал
Windows kernel-эксплойта, потому что превращает примитив памяти в конкретные
права.

## Почему это надёжнее, чем перехват кода

Перехват потока управления в ядре ловят PatchGuard и HVCI: правка SSDT,
callback-таблиц или кода ядра приводит к BSOD или отказу. Подмена токена —
**data-only** и не трогает защищённые структуры, поэтому стабильна и
безопасна для хоста. Это ключевое преимущество для отчётности и bug bounty.

## Частые вопросы

**Достаточно ли подменить токен, чтобы получить ring 0?** Нет — ты получаешь
права **SYSTEM** в userland. Для ring 0 из SYSTEM можно загрузить драйвер или
использовать другой примитив. Но для большинства задач SYSTEM достаточно.

**Почему не перехватить код ядра вместо токена?** Перехват ловят PatchGuard и
HVCI: правка SSDT/callback/кода ведёт к BSOD. Подмена токена — data-only и
стабильна.

**Как узнать смещение Token?** Из символов `ntoskrnl.exe` целевой сборки
(WinDbg, публичные карты смещений). Смещения меняются между сборками.

**Работает ли это при Credential Guard?** Да: token stealing не зависит от
защиты учётных данных, он меняет токен процесса напрямую.

**Что если нет примитива чтения?** Иногда токен находят по фиксированному
смещению от утечки или через `ActiveProcessLinks`, если известна база ядра.

## Сводка по шагам

Ещё раз, коротко и по порядку, что делает эксплойт token stealing:

1. **Утечка** даёт базу `ntoskrnl.exe` (KASLR сломан).
2. Примитив **чтения** находит адрес `_EPROCESS` нашего процесса через список
   `ActiveProcessLinks` или по известному смещению.
3. Из `_EPROCESS` читается поле `Token` (смещение зависит от сборки).
4. Отдельно находится `Token` процесса SYSTEM (PID 4).
5. Примитив **записи** кладёт SYSTEM-токен в поле `Token` нашего процесса.
6. Проверка: `whoami` возвращает `nt authority\system`.

Обрати внимание: шаги 2–5 — чисто **data-only**. Ни одной инструкции нашего
кода в ring 0 не исполняется. Именно поэтому цепочка работает даже при HVCI, где
исполнение неподписанного кода запрещено. Это делает token stealing базовым
приёмом для любого современного Windows kernel-эксплойта.

## Что мы теперь знаем

- Токен (`_TOKEN`) определяет личность процесса.
- `_EPROCESS.Token` — указатель, смещение зависит от сборки.
- Подмена токена на SYSTEM-токен = повышение привилегий.
- Data-only вариант не требует shellcode в ядре.
- Смещения берут из символов `ntoskrnl.exe`.
