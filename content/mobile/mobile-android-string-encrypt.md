## Вопрос, с которого всё начинается

Вы ищете в декомпилированном коде URL сервера — и не находите: `grep` по строкам пусто. Причина
в том, что строки зашифрованы и расшифровываются в рантайме. `strings` по APK тоже ничего не
даёт. Как добраться до спрятанных строк?

## Наш пример: app.apk без читаемых строк

```bash
$ strings app.apk | grep -i http
$ grep -rn 'http' out/sources | head
```

Оба пусто. Значит, строки где-то зашифрованы. Ищем след расшифровки.

## Шаг 1: зачем шифруют строки

Строковые константы — самый быстрый путь для аналитика: URL, ключи, тексты ошибок. Чтобы
затруднить анализ, приложение хранит их зашифрованными, а в коде оставляет вызов `decrypt()`.
Это **не** криптографическая защита (ключ всё равно в приложении), а обфускация: повышает
стоимость анализа.

## Шаг 2: поиск функции расшифровки

```bash
$ grep -rn -iE 'decrypt|deobf|xor|decode' out/sources --include='*.java' | head
Cipher.java:23:  public static String d(String s) { return xor(s, KEY); }
```

Функция `d` (короткое имя — типичный приём обфускации) расшифровывает строки XOR-ом с ключом.
Нашли точку входа.

## Шаг 3: разбор алгоритма статически

Открываем `Cipher.java`:

```java
static String d(String s) {
  byte[] b = Base64.decode(s, 0);
  for (int i = 0; i < b.length; i++) b[i] ^= (byte) KEY[i % KEY.length];
  return new String(b);
}
```

Алгоритм прост: Base64-декодировать, затем XOR с ключом. Теперь мы можем расшифровать все
строки сами — или перехватить результат в рантайме.

## Шаг 4: динамика через Frida

Надёжнее не реализовывать алгоритм повторно, а перехватить вызов расшифровки:

```javascript
Java.perform(function () {
  var C = Java.use('com.example.Cipher');
  C.d.overload('java.lang.String').implementation = function (s) {
    var out = this.d(s);
    console.log('dec: ' + out);
    return out;
  };
});
```

Каждый раз, когда приложение расшифровывает строку, мы видим результат. Запускаем приложение,
проходим по экранам — и собираем все строки.

## Шаг 5: массовая выгрузка

Чтобы не ходить по экранам вручную, можно дампить пул строк. Приём — вызвать расшифровку для
всех зашифрованных констант. Если известен список зашифрованных строк (из smali/Java), прогоняем
их через функцию:

```javascript
var enc = ['SGVsbG8=', 'V29ybGQ='];   // зашифрованные
enc.forEach(function (s) { console.log(C.d(s)); });
```

Так за один прогон получаем весь словарь строк.

## Шаг 6: автоматизация

В инструментах вроде `frida-dexdump`/скриптов на Frida есть готовые рецепты дампа строк. Для
нативных строк-шифровальщиков используют Unicorn (эмуляция функции расшифровки) или angr.

## Шаг 7: защита

Продвинутые обфускаторы (DexGuard, Stringer) не оставляют одну простую функцию: строки
расшифровываются инлайн, ключи зависят от контекста, используется несколько алгоритмов. Тогда
применяют трассировку (Stalker) и автоматический деобфускатор.

## Шаг 8: расшифровка строк в нативном коде

Если расшифровка уехала в `.so`, Java-хук её не поймает. Тогда работают с нативной функцией:
находят её адрес (по символам или по ссылке из JNI), вырезают и эмулируют в Unicorn, либо
трассируют через Frida:

```bash
$ readelf -sW libnative.so | grep -iE 'decrypt|decode|xor'
  42: 0000000000003a10    96 FUNC    GLOBAL DEFAULT   11 decode_str
```

Получив функцию, её эмулируют в цикле по всем зашифрованным константам — так за один прогон
получают весь словарь строк, не запуская приложение.

## Шаг 9: автоматические деобфускаторы

Для DEX-строк существуют готовые инструменты, которые сами находят функцию расшифровки и
применяют её ко всем константам:

| Инструмент | Что делает |
|---|---|
| dex-oracle | символически исполняет методы-расшифровщики |
| simplify | упрощает запутанные выражения |
| dexdump/frida-dexdump | дамп рантайм-DEX |
| jadx + скрипт | прогон всех строк через функцию |

Их применяют, когда расшифровка инлайн и вручную собирать вызовы долго. Результат — новый APK
с читаемыми строками, который дальше анализируют статически.

## Таблица: как распознать обфускатор строк

| Признак | Обфускатор | Подход |
|---|---|---|
| одна функция `d()` с XOR | самопис | Frida/скрипт |
| строки как `int[]` + inline | DexGuard | dex-oracle |
| несколько алгоритмов, ключ из контекста | Stringer | трассировка Stalker |
| расшифровка в `.so` | нативная | Unicorn/Frida |

## Практический пример: извлечение URL

Пусть после перехвата мы видим расшифрованные строки:

```text
dec: https://api.example.com/v1/
dec: X-Api-Key
dec: sk_live_51H...
```

Первая — базовый URL API, вторая — имя заголовка, третья — секрет. Именно такие находки и
составляют ценность реверса: они открывают путь к анализу сетевого взаимодействия и к поиску
уязвимостей в API.

## Ограничения

Шифрование строк не защищает от рантайма: ключ всё равно внутри приложения, и в момент
расшифровки строка видна. Единственный способ усложнить — не хранить ключ статически, а
собирать его из окружения (идентификатор устройства, время). Тогда статическая эмуляция
потребует воспроизвести контекст, и часть строк удастся получить только динамически.

## Практический вывод

Порядок работы со строками прост: убедиться, что они не читаются статически; найти функцию
расшифровки grep-ом по именам; перехватить её Frida, если она в Java, или эмулировать, если в
нативной библиотеке; собрать весь словарь строк; вернуть читаемость в декомпиляцию. Это
стандартный первый шаг реверса защищённого приложения, и он почти всегда даёт URL, ключи и
имена параметров.

## Шаг 10: строки в ресурсах и ассетах

Строки прячут не только в DEX. Часть конфигурации лежит в ресурсах (`strings.xml`, JSON в
`assets/`), часть — в нативных библиотеках. Проверить все три места можно так:

```bash
$ unzip -o app.apk -d apk >/dev/null
$ grep -rn -i 'http' apk/res apk/assets 2>/dev/null | head
$ strings apk/lib/arm64-v8a/*.so | grep -iE 'http|key' | head
```

Если строки находятся в ассетах открытым текстом — задача решена без расшифровки. Если в нативной
библиотеке они тоже зашифрованы, применяют эмуляцию (Unicorn) или трассировку.

## Как проверить, что собраны все строки

Полноту проверяют сравнением: до расшифровки и после. Сначала считаем, сколько вызовов
расшифровки в коде:

```bash
$ grep -rn 'Cipher.d(' out/sources --include='*.java' | wc -l
87
```

Затем — сколько уникальных строк мы получили в рантайме. Если числа близки, покрытие полное.
Оставшиеся вызовы (например, на редко посещаемых экранах) добирают, прогоняя приложение по всем
сценариям или вызывая функцию расшифровки напрямую для всех констант.

## Чек-лист по строкам

- Статический `strings` и grep по DEX пусты.
- Найдена функция расшифровки (по именам или по трассировке).
- Frida/эмуляция даёт читаемые строки.
- Число расшифрованных строк сопоставимо с числом вызовов.
- Найденные URL и ключи задокументированы.

## Практический сценарий целиком

Разберём полный цикл на примере. Сначала убеждаемся, что строки не читаются статически:
`strings app.apk` и `grep` по DEX пусты. Ищем функцию расшифровки по именам (`decrypt`, `d`,
`xor`, `decode`) и находим короткую функцию. Читаем её алгоритм: Base64 + XOR с ключом. Дальше
выбираем способ — перехват через Frida (если функция в Java) или эмуляцию (если в нативной
библиотеке). Получаем строки, среди которых находим базовый URL API, имя заголовка авторизации и
секретный ключ. Проверяем полноту: сравниваем число расшифрованных строк с числом вызовов в коде.
Наконец, документируем находки и переходим к анализу сетевого протокола.

## Что писать в отчёте

Указывают: где именно хранились строки (DEX/ресурсы/нативная библиотека), каким алгоритмом
шифровались, каким инструментом удалось их получить, и сами значимые строки (URL, ключи, имена
параметров). Отдельно отмечают, что шифрование строк — обфускация, а не криптографическая защита:
ключ находится в приложении, поэтому секреты нельзя считать защищёнными.

## Типичные ошибки при расшифровке строк

Первая ошибка — реализовывать алгоритм вручную и ошибиться в деталях (порядок байт, padding
Base64). Надёжнее перехватить результат через Frida, а не повторять логику. Вторая — прогнать
только часть экранов и решить, что собраны все строки: редко посещаемые функции останутся
нерасшифрованными. Третья — не проверять, что функция расшифровки вообще одна: в больших
приложениях их несколько, с разными алгоритмами. Четвёртая — забыть про нативную часть: строки
могут расшифровываться в `.so`, и тогда Java-хук их не увидит. Проверка полноты по числу вызовов
помогает не пропустить ни одну из этих ловушек.

## Связь с другими техниками обфускации

Шифрование строк редко встречается в одиночку. Обычно его комбинируют с переименованием классов
и методов (чтобы по именам нельзя было догадаться о назначении), с reflection (чтобы вызовы были
по строкам) и с нативной защитой (чтобы расшифровка уехала в `.so`). Поэтому, разобрав строки, вы
часто получаете ключ и к остальным слоям: расшифрованные имена классов подсказывают, где искать
логику, а найденные URL открывают путь к анализу сети. В этом смысле работа со строками — не
изолированная задача, а входная точка: она возвращает читаемость, на которой строятся все
остальные шаги реверса. Именно поэтому её делают первой, до попыток разобрать отдельные функции.

## Что мы теперь знаем

- Строки прячут за шифрованием, чтобы усложнить анализ.
- Функцию расшифровки находят grep-ом по именам.
- Frida перехватывает вызов и показывает результат.
- Массовая выгрузка собирает весь словарь строк.
- Продвинутые обфускаторы требуют трассировки.
