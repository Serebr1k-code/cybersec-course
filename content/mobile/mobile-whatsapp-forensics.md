## Вопрос, с которого всё начинается

У нас есть дамп Android-устройства. Нужно понять, о чём переписывался владелец в WhatsApp —
и приходил ли ему код подтверждения от банка. Открываем папку приложения и видим файл с
загадочным именем `msgstore.db.crypt15`. Открыть его как базу не выходит. Что это за файл и
как до него добраться?

## Наш пример: файлы WhatsApp в дампе

Смотрим, что лежит в песочнице мессенджера:

```bash
$ ls -l /data/data/com.whatsapp/files/
-rw------- 1 u0_a123 u0_a123       32 key
-rw------- 1 u0_a123 u0_a123  8210432 msgstore.db.crypt15
-rw------- 1 u0_a123 u0_a123   512000 wa.db
```

Рядом с базой сообщений лежит файл `key` размером ровно 32 байта. Это уже подсказка: база
зашифрована, а ключ — вот он. Весь урок мы будем вести эту пару файлов до читаемой переписки.

## Шаг 1: почему база не открывается

Файл `msgstore.db.crypt15` — не обычная база SQLite. Приложение **шифрует** свою базу целиком,
чтобы её нельзя было прочитать, просто скопировав файл. Расширение `crypt15` — это версия
схемы шифрования WhatsApp (были `crypt12`, `crypt14`, теперь `crypt15`). Первые байты файла —
не заголовок SQLite (`SQLite format 3`), а служебный блок шифра. Проверим:

```bash
$ xxd -l 16 msgstore.db.crypt15
00000000: 00000000 00000000 00000000 00000000  ................
```

Вместо сигнатуры базы — нули. Значит, перед нами зашифрованный контейнер.

## Шаг 2: где ключ

Приложение хранит ключ шифрования в файле `key` в своей же папке. Тот факт, что ключ лежит
рядом с базой, — типичная ситуация для мобильных приложений: шифрование тут защищает от
простого копирования файла, но не от доступа к песочнице (root/бэкап). Ключ — 32 байта,
это AES-256. На iOS ключ хранится иначе — в Keychain, и его достают иначе.

```bash
$ xxd -l 32 key
00000000: 8f2a 91c4 0d7b e510 44aa 12f9 6b30 88d1  .*...{..D...k0..
```

Теперь у нас есть и шифротекст, и ключ.

## Шаг 3: расшифровка

Для расшифровки используют готовые инструменты (`wa-crypt-tools`, `whatsapp-forensic-decryptor`)
или скрипт, который читает формат `crypt15` и расшифровывает поток AES-CBC. Запускаем:

```bash
$ python3 wa_decrypt.py msgstore.db.crypt15 key msgstore.db
[+] decrypted 8210432 bytes -> msgstore.db
$ file msgstore.db
msgstore.db: SQLite 3.x database, last written using SQLite version 3045001
```

Мы получили обычную базу SQLite. Половина задачи сделана: шифрование снято, дальше — обычные
SQL-запросы.

## Шаг 4: схема и чтение сообщений

Смотрим, из чего состоит база:

```bash
$ sqlite3 msgstore.db ".tables"
call_log         message_media    message_thumbnail
chat             message          message_add_on
jid              message_ftsv2    receipt_user
```

Нас интересуют `message` (сами сообщения) и `chat` (чаты). Смотрим структуру:

```bash
$ sqlite3 msgstore.db ".schema message" | head
CREATE TABLE message (
  _id INTEGER PRIMARY KEY AUTOINCREMENT,
  key_remote_jid TEXT,
  key_from_me INTEGER,
  key_id TEXT,
  data TEXT,
  timestamp INTEGER,
  ...
);
```

`key_remote_jid` — собеседник (JID вида `7999...@s.whatsapp.net`), `key_from_me` — 1 для
исходящих и 0 для входящих, `data` — текст сообщения, `timestamp` — время. Читаем переписку:

```bash
$ sqlite3 msgstore.db "SELECT datetime(timestamp/1000,'unixepoch'), key_from_me, data FROM message WHERE data IS NOT NULL ORDER BY timestamp LIMIT 3;"
2026-09-01 12:04:11|0|привет
2026-09-01 12:04:40|1|привет, ты дома?
2026-09-01 12:05:02|0|otp 4821
```

## Шаг 5: что искать в переписке

В форензике важны не только слова, но и факты: коды подтверждения (`otp`, «код»), ссылки
(фишинг), вложения (в `message_media`), удалённые сообщения. Удалённые записи часто остаются
в свободных страницах базы — их можно достать через `.recover` или `undark`. Также полезен
`wa.db`: это отдельная база с контактами (`wa_contacts`), она даёт имена к номерам.

```bash
$ sqlite3 msgstore.db ".recover" | grep -i 'nto{'
```

## Шаг 6: облако и шифрованные бэкапы

Тот же файл встречается в Google Drive-бэкапах WhatsApp (`msgstore.db.crypt15` в аккаунте
пользователя). Ключ от него — в самом бэкапе или извлекается из `key` на устройстве. Если
устройство недоступно, ключ берут из зашифрованного бэкапа, а пароль бэкапа подбирают
ограниченно — это уже отдельная ветвь про облачные бэкапы.

## Шаг 7: версии шифрования — crypt12, crypt14, crypt15

Расширение файла менялось вместе с версией защиты. `crypt12` — старая схема, где
использовался AES-CBC и ключ из файла `key`; её давно разобрали по байтам. `crypt14` добавила
соль и инициализационный вектор прямо в заголовок файла и зашифровала часть метаданных. В
`crypt15` появилась дополнительная защита: ключ стал «завёрнут» и меняется при некоторых
операциях, а база получила более строгий формат заголовка. Практический вывод один: **версия
определяет инструмент**. Скрипт для `crypt12` не откроет `crypt15`, и наоборот. Поэтому первым
делом смотрят имя файла и первые байты, чтобы понять схему.

```bash
$ xxd -l 64 msgstore.db.crypt15 | head -2
00000000: 00000000 00000000 00000000 00000000  ................
```

Нулевая шапка — признак того, что перед нами зашифрованный контейнер, а не готовая база.

## Шаг 8: медиа и вложения

Текст — не всё. В папке WhatsApp лежит каталог `Media/` с фотографиями, видео, голосовыми и
документами, сгруппированными по датам и чатам. База `msgstore.db` ссылается на них через
таблицы `message_media` и `message_thumbnail`. В форензике медиа ценны по двум причинам:
во-первых, в метаданных (EXIF) бывают геолокация и время съёмки; во-вторых, вложения часто
содержат то, что человек не стал бы пересылать текстом — сканы документов, чеки, пароли на
фото. Имена файлов содержат идентификаторы чата, поэтому их можно связать с перепиской.

```bash
$ sqlite3 msgstore.db "SELECT file_path, media_name FROM message_media LIMIT 3;"
Media/WhatsApp Images/IMG-20260901-WA0001.jpg|IMG-20260901-WA0001.jpg
```

## Шаг 9: группы и удалённые сообщения

Групповые чаты хранятся в той же таблице `message`, но с `key_remote_jid` вида
`<groupid>@g.us`, а участники — в отдельной таблице `group_participants`. Это позволяет
восстановить, кто и когда писал в группу. Отдельная задача — удалённые сообщения: если
пользователь удалил сообщение «для всех», в локальной базе может остаться запись с
`message_type=15` (системное «сообщение удалено») и пустым `data`, а сам текст иногда
сохраняется в свободных страницах. Инструменты вроде `undark` вытаскивают такие строки из
неиспользуемого пространства.

## Шаг 10: облачный бэкап

Google Drive-бэкап WhatsApp — это отдельный `msgstore.db.crypt15`, зашитый ключом, который
хранится в самом бэкапе или в аккаунте. Если устройство недоступно, а нужен именно бэкап, его
скачивают через API аккаунта и расшифровывают тем же инструментом, подобрав пароль бэкапа.
Пароль — слабое место: пользователи часто ставят простой, и тогда бэкап вскрывается. В отчёте
это отдельная находка: «резервная копия защищена слабым паролем».

## Шаг 11: что писать в отчёте

Итог по WhatsApp: перечень чатов с датами, ключевые сообщения (коды подтверждения, ссылки,
реквизиты), список вложений с метаданными и вывод о том, защищена ли локальная база и бэкап.
Каждый факт сопровождается источником: имя таблицы, идентификатор сообщения, время. Только
так форензический вывод нельзя оспорить.

## Шаг 12: связываем номера и контакты

JID в базе — это номер, а не имя. Чтобы понять, кому принадлежит переписка, номер связывают с
контактами. Часть имён лежит в `wa.db` (`wa_contacts`), часть — в системной базе контактов
(`contacts2.db`). Совпадение по номеру даёт имя, а `wa.db` дополнительно хранит статусы и
аватары. В отчёте пишут оба значения: номер и имя, потому что номер — это первичный
идентификатор, а имя может быть подписано произвольно самим владельцем.

## Шаг 13: время и часовые пояса

`timestamp` в базе WhatsApp — Unix-миллисекунды в UTC. Пользователь же живёт в локальном
времени. Если в отчёте указать время без зоны, вывод легко оспорить: событие «в 14:32» в
одной зоне окажется «в 11:32» в другой. Поэтому всегда фиксируют: исходное значение из базы,
пересчёт в UTC и локальную зону устройства (её видно в свойствах системы и в `settings`).
Отдельно проверяют, не менял ли пользователь зону: в некоторых артефактах остаются следы.

## Шаг 14: целостность и фиксация

Прежде чем что-то менять (расшифровывать, открывать базу), снимают хэши исходных файлов. Это
доказательство того, что вы работали с неизменными данными. Расшифровку делают в копию, а не
поверх оригинала: `msgstore.db` создаётся заново, а `msgstore.db.crypt15` остаётся нетронутым.
В отчёте приводят хэши исходников — это стандарт цифровой форензики, без которого выводы
легко дискредитировать.

## Шаг 15: чек-лист WhatsApp-форензики

Кратко, что должно быть сделано к концу работы: (1) зафиксированы хэши `msgstore.db.crypt15`,
`key`, `wa.db`; (2) определена версия шифрования; (3) база расшифрована в копию; (4) выгружены
чаты, сообщения, вложения; (5) проверены удалённые записи; (6) проверен облачный бэкап;
(7) в отчёте для каждого факта указан источник (таблица, идентификатор, время). Пропуск любого
пункта делает вывод неполным.

## Что мы теперь знаем

- База WhatsApp лежит в `msgstore.db.crypt15` и зашифрована целиком.
- Ключ — в соседнем файле `key` (Android) или в Keychain (iOS).
- Расшифрованная база — обычный SQLite с таблицами `message`, `chat`, `jid`.
- `key_from_me`, `timestamp`, `data` дают время, направление и текст.
- Удалённые записи восстанавливаются из свободных страниц (`.recover`, `undark`).
