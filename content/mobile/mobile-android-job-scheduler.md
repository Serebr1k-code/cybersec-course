## Вопрос, с которого всё начинается

Приложение закрыто, но каждые пятнадцать минут просыпается, что-то проверяет и отправляет на
сервер. Никакого уведомления при этом нет. Кто его будит и как это устроено?

## Наш пример: периодическая задача

В коде видим:

```java
JobInfo job = new JobInfo.Builder(42, new ComponentName(this, SyncJob.class))
        .setRequiredNetworkType(JobInfo.NETWORK_TYPE_ANY)
        .setPeriodic(15 * 60 * 1000L)
        .build();
JobScheduler js = getSystemService(JobScheduler.class);
js.schedule(job);
```

`JobScheduler` — системный сервис планирования задач. Мы просим: «выполни `SyncJob` примерно раз в
15 минут, когда есть сеть». Уведомления нет, приложение может быть не запущено — задача всё равно
сработает.

## Шаг 1: три механизма планирования

- **AlarmManager** — точное время. Будит устройство в заданный момент. Дорого для батареи,
  ограничен в Doze.
- **JobScheduler** — условия. «Когда есть сеть и зарядка» — система сама выберет момент.
- **WorkManager** — обёртка над JobScheduler/AlarmManager, умеет цепочки задач, повторы и
  наблюдаемость; рекомендуется для новых приложений.

Выбор механизма влияет на то, что видно в аудите: JobScheduler — это `dumpsys jobscheduler`,
WorkManager — те же job-ы плюс собственная база.

## Шаг 2: JobService и его жизненный цикл

Задачу выполняет `JobService`:

```java
public class SyncJob extends JobService {
    public boolean onStartJob(JobParameters p) {
        doWorkAsync();
        return true;   // работа продолжается в фоне
    }
    public boolean onStopJob(JobParameters p) { return true; }
}
```

`onStartJob` возвращает `true`, если работа продолжится после выхода из метода. `onStopJob`
вызывается, когда система отменяет задачу (например, условия перестали выполняться).

## Шаг 3: constraints и почему это удобно атакующему

Constraints (требования) — сеть, зарядка, простой, тип сети. Для атакующего это подарок: задача
«выполнись, когда есть Wi-Fi и зарядка» гарантирует, что данные уйдут в удобный момент, когда
пользователь спит. `setPersisted(true)` делает задачу переживающей перезагрузку — но требует
разрешения `RECEIVE_BOOT_COMPLETED`.

## Шаг 4: где начинается абуз

- **Персистентность.** Периодическая задача + `setPersisted` = код, который живёт всегда.
- **Скрытый сетевой обмен.** Нет уведомления — пользователь не видит отправку.
- **Сбор данных порциями.** Задача читает маленькие порции и складывает в буфер.
- **Wakeup-цепочки.** Задача будит сервис, сервис ставит новую задачу — бесконечный цикл.

## Шаг 5: экспортированный JobService

Если `JobService` объявлен `exported="true"` (а по умолчанию без intent-filter он не экспортирован,
но разработчики иногда включают), чужое приложение может запланировать его выполнение со своими
параметрами. Проверяем манифест:

```xml
<service android:name=".SyncJob"
         android:permission="android.permission.BIND_JOB_SERVICE"
         android:exported="false"/>
```

`BIND_JOB_SERVICE` — системное разрешение; если оно указано и `exported="false"`, снаружи задачу
не подкинуть.

## Шаг 6: как аудировать

```bash
$ adb shell dumpsys jobscheduler | grep -A8 'com.example.app'
  JOB #u0a123/com.example.app/.SyncJob: 42
    Required constraints: CONNECTIVITY
    Periodic: interval=900000ms
    Persisted: true
```

`dumpsys jobscheduler` показывает все запланированные задачи: пакет, компонент, интервал,
constraints, persisted. Это точная карта фоновой активности. Дополнительно смотрим
`dumpsys alarm` для AlarmManager.

## Шаг 7: как защищаться

- Не использовать `setPersisted` без необходимости.
- Минимальный интервал и мягкие constraints там, где это возможно.
- `exported="false"` + `BIND_JOB_SERVICE` для JobService.
- Не складывать в задачи чувствительные данные без шифрования.

## Что мы теперь знаем

- JobScheduler выполняет задачи по условиям, WorkManager — удобная обёртка.
- JobService реализует работу, constraints задают условия.
- Персистентность достигается `setPersisted` + boot-receiver.
- Аудит: `dumpsys jobscheduler`.
- Защита: `exported="false"`, `BIND_JOB_SERVICE`, минимум персистентности.

## Куда дальше

Мы разобрали фоновые задачи. Дальше — синхронизация, которая связывает фон с аккаунтом.

## Шаг 8: WorkManager подробнее

`WorkManager` — рекомендуемый механизм для отложенной работы. Он хранит задачи в собственной базе,
умеет цепочки (`beginWith(...).then(...)`), повторы с backoff и наблюдаемость через
`WorkInfo`. Под капотом он использует JobScheduler (или AlarmManager на старых версиях), поэтому
в `dumpsys jobscheduler` задачи WorkManager тоже видны — но с системными компонентами
`androidx.work.impl.background.systemjob.SystemJobService`. Если видите такие job-ы, значит
приложение использует WorkManager, а не сырой JobScheduler.

## Шаг 9: Doze и App Standby

Начиная с Android 6 система переводит устройство в **Doze** (экран выключен, нет движения) и
приложения — в **App Standby**. В Doze откладываются сетевые доступы и alarm-ы; JobScheduler
задачи выполняются только в maintenance-окна. Именно поэтому задачи «раз в 15 минут» на деле
могут срабатывать реже. Для атакующего это значит, что не стоит полагаться на точность; для
защитника — что фоновая активность всё равно происходит, просто пачками.

## Шаг 10: реальный кейс

Типичный рекламный SDK планирует периодическую задачу, которая собирает рекламный идентификатор
и события использования и отправляет их на сервер. Уведомления нет, приложение может быть
закрыто. Пользователь не видит ни запросов, ни отправки. В аудите такая задача находится в
`dumpsys jobscheduler` и связывается с SDK по имени компонента. Отсюда рекомендация: перечислять
все периодические задачи и для каждой спрашивать «зачем это приложению».

## Шаг 11: чек-лист

- Список всех job-ов и их интервалов.
- Persisted-задачи и boot-receiver.
- Сетевой обмен внутри задач.
- Экспортирован ли JobService.
- Используется ли WorkManager и какие у него цепочки.

## Частые вопросы

**Можно ли убить задачу пользователю?** Через настройки «Батарея»/«Автозапуск», но не все
производители это дают. Программно — только остановив приложение.

**JobScheduler = фоновый сервис?** Нет. Это планировщик; он будит компонент на короткое время, а
не держит процесс постоянно.

**Как отличить легитимную задачу?** По соответствию функции приложения и по наличию понятной
пользовательской пользы.

## Шаг 12: AlarmManager и точные будильники

Помимо JobScheduler, приложение может использовать `AlarmManager`. Он умеет будить устройство в
точное время (`setExactAndAllowWhileIdle`), что делает его удобным для «будильников», но дорогим
для батареи. Для атакующего точный alarm — способ гарантировать выполнение в нужный момент, не
полагаясь на Doze. Проверять будильники можно так:

```bash
$ adb shell dumpsys alarm | grep -A6 'com.example.app'
  RTC_WAKEUP #0: Alarm{... type=0 when=+1h20m com.example.app}
    operation=PendingIntent{... BroadcastReceiver: .AlarmReceiver}
    repeatInterval=3600000
```

Видно время, тип (RTC_WAKEUP будит устройство), получателя и интервал повтора. Если приложение
ставит десятки повторяющихся wakeup-alarm-ов, это признак либо плохой инженерии, либо намеренной
персистентности.

## Шаг 13: сочетание механизмов

Реальная малварь комбинирует всё: `BOOT_COMPLETED` → foreground-сервис → периодическая job →
точный alarm как страховка. Убрав один механизм, вы не остановите остальные. Поэтому в отчёте
важно перечислить всю цепочку: receiver, сервис, job, alarm. Каждое звено проверяется своей
командой `dumpsys`, и вместе они дают полную картину персистентности.

## Шаг 14: почему нельзя просто запретить фон

Разработчики возражают: «нам нужен фон для синхронизации». И это правда — легитимный фон
существует. Поэтому оценка строится не на факте фоновой задачи, а на её содержании: какие данные
читаются, куда отправляются, соответствует ли это функции приложения, может ли пользователь это
отключить. Только ответив на эти вопросы, можно отличить нормальную синхронизацию от слежки.

## Частые вопросы

**JobScheduler работает в Doze?** Да, но только в maintenance-окна, поэтому интервалы не точные.

**AlarmManager точнее?** Да, `setExactAndAllowWhileIdle` точен, но ограничен по частоте.

**Можно ли отключить фон пользователю?** Частично — через настройки батареи; не все производители
дают полный контроль.

**Что важнее в отчёте — механизм или данные?** Данные. Механизм лишь показывает, как они утекают.

## Шаг 15: App Standby Buckets и запрос исключений

Android делит приложения на «корзины» активности: active, working set, frequent, rare, restricted.
Чем реже приложение используют, тем жёстче ограничивается фон. Приложение может попросить
исключение из оптимизации батареи (`REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`), и тогда его задачи
выполняются чаще. В манифесте это выглядит так:

```xml
<uses-permission android:name="android.permission.REQUEST_IGNORE_BATTERY_OPTIMIZATIONS"/>
```

Само по себе разрешение легитимно (будильники, трекеры здоровья), но если приложение просит
исключение без понятной причины и при этом активно шлёт данные — это красный флаг. В аудите
проверяйте, запрашивает ли приложение исключение и объясняет ли зачем.

## Шаг 16: как выглядит вся картина

Соберём картину по нашему примеру. `dumpsys jobscheduler` показывает периодическую задачу с
`persisted=true` и сетевым constraint. `dumpsys alarm` показывает повторяющийся `RTC_WAKEUP`,
который будит устройство. Манифест показывает `RECEIVE_BOOT_COMPLETED` и запрос исключения из
оптимизации. Вместе это означает: приложение просыпается после перезагрузки, регулярно будит
устройство и отправляет данные на сервер. Каждый элемент по отдельности объясним, а вместе они
складываются в устойчивую фоновую слежку.

## Шаг 17: что писать в отчёте

Опишите каждый механизм отдельно (job, alarm, receiver, исключение из оптимизации), приведите
вывод соответствующей команды `dumpsys`, укажите, какие данные передаются и куда, и предложите
конкретные правки: убрать `setPersisted`, увеличить интервалы, не запрашивать исключение из
оптимизации без нужды, уважать настройки пользователя. Такой отчёт читается как история, а не как
набор разрозненных замечаний.

## Шаг 18: итог

Планировщик задач — тихий, но мощный механизм: он работает без UI и без запущенного приложения.
Оценивайте каждую задачу по её содержанию: что читает, куда шлёт, можно ли отключить. Вместе с
foreground-сервисами и будильниками он образует устойчивый фон, который нужно описывать цепочкой.

Проверяйте фоновые задачи в связке: одна задача сама по себе безобидна, но вместе с будильником,
boot-receiver и исключением из оптимизации батареи она становится звеном устойчивой
персистентности. Описывайте цепочку целиком, а не отдельные элементы.
