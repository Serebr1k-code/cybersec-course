## Вопрос, с которого всё начинается

**Account takeover (ATO)** — полный захват чужого аккаунта: мы получаем доступ к нему и можем действовать от имени жертвы. Отдельная уязвимость редко даёт ATO сразу; обычно её собирают из нескольких мелких ошибок в одну **цепочку**. Мобильные приложения дают для этого богатую почву: одноразовые коды (OTP) без лимита попыток, перехват OAuth-редиректов через custom-scheme, слабое восстановление пароля и доверие к «привязке устройства».

Разберём две реальные механики на локальном API, который мы подняли в прошлых уроках.

## Наш пример: OTP-эндпоинт без лимита

Наш бэкенд `http://127.0.0.1:18080` умеет подтверждать вход по **OTP** — одноразовому коду из 6 цифр: `POST /v1/otp/verify?user=1001` с телом `{"code":"......"}`. Код для Алисы (`1001`) — `482913`. Ключевой вопрос: **ограничивает ли сервер число попыток**?

Отправим неверный код:

```
$ curl -s -i -X POST -H "Content-Type: application/json" \
       -d '{"code":"000000"}' \
       "http://127.0.0.1:18080/v1/otp/verify?user=1001" | head -1
HTTP/1.0 403 Forbidden
```

`403` — код не подошёл, это нормально. Но сервер не заблокировал нас после ошибки. Значит, можно перебирать. Перебор 6-значного кода «в лоб» — это до миллиона попыток, но **без rate-limit** он технически возможен; проверим, что блокировки нет:

```
$ for c in 000001 000002 000003 000004; do
    curl -s -o /dev/null -w "$c -> %{http_code}\n" -X POST \
      -H "Content-Type: application/json" -d "{\"code\":\"$c\"}" \
      "http://127.0.0.1:18080/v1/otp/verify?user=1001"
  done
000001 -> 403
000002 -> 403
000003 -> 403
000004 -> 403
```

Четыре неверные попытки подряд — и всё ещё `403`, а не `429 Too Many Requests`. Блокировки нет. Теперь подставляем верный код:

```
$ curl -s -X POST -H "Content-Type: application/json" \
       -d '{"code":"482913"}' \
       "http://127.0.0.1:18080/v1/otp/verify?user=1001"
{"ok": true, "session": "sess-1001"}
```

Мы получили сессию Алисы. **OTP-байпас через отсутствие rate-limit** — классический шаг ATO. Частые варианты той же ошибки: код проверяется на клиенте, ответ сравнивается по «похожести», код не инвалидируется после успеха, срок жизни кода слишком велик, а `429` отсутствует или обходится сменой IP/заголовков.

## Шаг 1: перехват OAuth-редиректа через custom-scheme

Второй механизм — **OAuth-флоу**. Приложение открывает браузер, пользователь логинится, сервер редиректит обратно в приложение по **custom-scheme** (например, `myapp://callback?code=...`). **Custom-scheme** — это «своя схема» URL, которую приложение регистрирует в манифесте, чтобы система открывала ссылки такого вида именно в нём.

Проблема: custom-scheme может зарегистрировать **любое** приложение, в том числе вредоносное. Посмотрим, как схема объявлена в реальном приложении — декодируем манифест `fdroid.apk`:

```
$ java -jar apktool.jar d -f -o fdroid_dec fdroid.apk
$ grep -B2 -A1 'fdroidrepos' fdroid_dec/AndroidManifest.xml
<category android:name="android.intent.category.BROWSABLE"/>
<category android:name="android.intent.category.DEFAULT"/>
<data android:scheme="fdroidrepos"/>
<data android:scheme="FDROIDREPOS"/>
```

Схема `fdroidrepos` открыта всему миру: любое приложение может объявить её у себя и перехватывать такие ссылки. Если через эту схему возвращается OAuth-код, атакующий перехватит его первым (Android отдаёт ссылку приложению-«перехватчику», если оно зарегистрировалось раньше или пользователь выбрал его). С `code` злоумышленник обменяет его на токен — и получит аккаунт. Категория `BROWSABLE` означает, что ссылку можно открыть из браузера, а `DEFAULT` — что схема работает без явного выбора.

Защита — **App Links / Universal Links**: привязка `https`-ссылки к домену через файл `.well-known/assetlinks.json`, который нельзя подделать чужому приложению.

## Шаг 2: как складывать цепочку

ATO собирают из звеньев, каждое из которых по отдельности — «средняя» находка. Типовая цепочка выглядит так:

1. **Утечка email/телефона** жертвы (из ответа API, из `users.json` открытой Firebase).
2. **Инициируем восстановление** на этот email — сервер шлёт OTP/ссылку.
3. **OTP без rate-limit** — перебираем код или перехватываем его.
4. **OAuth custom-scheme** — перехватываем `code` редиректа, если приложение логинится через соцсеть.
5. **Обмен кода** — получаем токен доступа.
6. **Device binding** — обходим привязку подстановкой `X-Device-Id` жертвы.

Каждый шаг по отдельности может не дать полного доступа, но вместе они дают контроль над аккаунтом. Поэтому на пентесте фиксируют **всю цепочку** и показывают, как звенья соединяются, — иначе находку не поймут и не исправят.

## Шаг 3: привязка к устройству — не панацея

Мы уже видели в уроке про BOLA, что `X-Device-Id` приходит от клиента и не проверяется. Для ATO это означает: украденный токен сессии можно «оживить» на своём устройстве, подставив идентификатор жертвы. Настоящая привязка должна опираться на аттестацию (Play Integrity / App Attest) с **криптографической проверкой подписи на сервере**, а не на присланную строку.

## Шаг 4: восстановление пароля

Ещё один вход в цепочку — сброс пароля. Ищите: токен сброса с малым сроком жизни или предсказуемый, ссылку сброса, которая не привязана к сессии, возможность подставить чужой email/телефон в запрос, отсутствие проверки, что запрос сброса инициировал владелец. Часто сброс и OTP делят одну уязвимую проверку — «нашли один, проверьте второй».

## Полный прогон от начала до конца

1. **OTP** — отправляем неверные коды, убеждаемся в отсутствии `429` (нет rate-limit).
2. **Подбор** — перебираем код (или используем утечку) → получаем сессию.
3. **OAuth** — ищем в манифесте custom-scheme, регистрируем её перехватчиком, ловим `code`.
4. **Обмен** — меняем `code` на токен на сервере авторизации.
5. **Device binding** — подставляем чужой `X-Device-Id`, обходим привязку.
6. **Восстановление** — проверяем сброс пароля на ту же слабость.
7. **Цепочка** — комбинируем: перехваченный `code` + отсутствие rate-limit + обход привязки → полный ATO.

## Если не сработало

Есть rate-limit? Попробуйте смену заголовков (`X-Forwarded-For`), разные эндпоинты того же кода, другой формат (код в query vs в body). Custom-scheme закрыт? Проверьте `App Links` — иногда домен ассоциирован не полностью. OTP приходит SMS? Тогда на первый план выходит **SIM-swap** или перехват SMS — но это уже вне приложения. И всегда проверяйте, инвалидируется ли код после использования и не живёт ли он слишком долго.

## Что мы теперь знаем

1. ATO — это цепочка мелких ошибок, а не одна «кнопка».
2. Отсутствие rate-limit на OTP позволяет перебрать код и войти.
3. Custom-scheme OAuth-редирект можно перехватить чужим приложением; защита — App Links.
4. Привязка к устройству, основанная на клиентском `device_id`, обходится.
5. Восстановление пароля — вторая точка входа с теми же слабостями.
6. Доказательство ATO — воспроизводимая цепочка до доступа к чужому аккаунту.
