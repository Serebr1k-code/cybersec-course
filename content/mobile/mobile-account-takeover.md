## Введение

Захват аккаунта (Account Takeover, ATO) в мобильных приложениях почти всегда — цепочка из нескольких мелких ошибок, а не одна дыра. По отдельности каждое звено может выглядеть безобидно: отсутствие `state` в OAuth, предсказуемый reset-токен, отсутствие rate-limit на OTP, слабая привязка устройства. Собранные вместе они дают полный контроль над чужим аккаунтом. Задача пентестера — не просто найти звено, а собрать работающий end-to-end PoC и доказать реальный захват.

Ключевой принцип: думайте как атакующий, который хочет пройти весь путь «получить чужой аккаунт», а не как сканер, ищущий отдельные CVE. Мобильный ATO почти всегда логический, а не память-безопасностный.

## Карта аутентификационных потоков

Прежде чем атаковать, составьте карту всех способов входа и восстановления:

- Логин по паролю.
- OTP по SMS/email (и его повторная отправка).
- OAuth/OpenID Connect (социальный вход, SSO).
- Восстановление пароля (reset link, reset code).
- Magic link / passwordless.
- Смена email/телефона.
- Привязка устройств и «доверенные устройства».
- Биометрия как локальный гейт поверх токена.

Для каждого потока выпишите: какие параметры клиент может контролировать, какие проверки выполняет сервер, что происходит при ошибке, есть ли лимиты. Именно на стыках потоков рождаются цепочки.

## Векторы OTP

OTP — самый частый источник ATO, потому что коды короткие (4-6 цифр) и их можно перебирать, если нет защиты.

- **Нет rate-limit / lockout** → перебор 4-6-значного OTP реален. Не нужен mega-словарь: нужен аккуратный перебор с подсчётом попыток.
- **OTP в ответе API** (в debug/error/response) → читаете код напрямую.
- **OTP не инвалидируется** после использования → повторное применение старого кода.
- **OTP предсказуем** (по времени/счётчику, слабый PRNG) → вычисление следующего кода.
- **SMS Retriever API** с широким фильтром → чужое приложение перехватывает OTP.
- **OTP утекает** в лог/уведомление/deep-link → перехват через ADB/Frida.
- **Response manipulation:** если клиент сам решает «OTP верный» по булеву ответу — обход через Frida.

```bash
# проверка отсутствия rate-limit (ТОЛЬКО на своём аккаунте!)
for i in $(seq 1 50); do
  code=$(printf "%04d" $i)
  st=$(curl -s -o /tmp/r.json -w "%{http_code}" -X POST https://api.example/v1/verify \
        -H "Content-Type: application/json" \
        -d "{\"phone\":\"+70000000000\",\"otp\":\"$code\"}")
  echo "$i -> $st $(jq -r '.error // "ok"' /tmp/r.json 2>/dev/null)"
  sleep 0.2
done
# если все 50 вернули 200/401 без 429 -> rate-limit отсутствует
```

## OAuth-перехват

Мобильные OAuth-потоки (public clients) особенно уязвимы, потому что не могут хранить секрет и полагаются на redirect.

- Custom scheme без `state` → hijacking кода (любое приложение заявляет схему).
- `redirect_uri` со слабой валидацией (wildcard, суффикс, open redirect) → код уходит атакующему.
- Universal/App Link с широкими `paths` → редирект на произвольный хост.
- Отсутствие PKCE → перехват authorization code для публичного клиента.
- Отсутствие проверки `iss`/nonce в id_token → подмена токена.

## Восстановление пароля

- Reset-токен предсказуем или не привязан к пользователю.
- Ссылка сброса уходит на неверный email по слабому токену.
- Host-header injection в письме сброса → ссылка ведёт на атакующий хост.
- Изменение email/телефона без подтверждения старого канала → перепривязка аккаунта.
- Повторное использование одноразового токена сброса.

## Device-binding bypass

Если API привязан к устройству, попробуйте:

- подделать `device_id` / `installation_id` в запросе;
- переиспользовать чужой device-id;
- обойти клиентскую attestation (Play Integrity/SafetyNet/DeviceCheck) через Frida-хук на «success»;
- привязать своё устройство к чужому аккаунту, если операция привязки не подтверждается.

## Сборка цепочки

Пример полного ATO:

1. Приложение регистрирует custom scheme `bank://oauth` без параметра `state`.
2. `redirect_uri` не валидируется строго → authorization code жертвы уходит на `evil://callback`.
3. Обмен кода на токен проходит без PKCE → доступ к аккаунту жертвы.
4. Дополнительно: OTP на смену пароля без rate-limit → закрепление доступа.

Каждое звено документируйте отдельно (шаг, запрос, ответ, эффект), затем соберите сквозной PoC с реальным токеном/сессией. В отчёте важен именно end-to-end сценарий: заказчик должен видеть, что комбинация даёт захват.

## Разобранный пример

Bug bounty: `POST /api/reset` принимает произвольный `phone` и при определённых условиях возвращает `200` с `resetToken` в теле ответа.

```bash
curl -s -X POST https://api.example/v1/reset \
  -H "Content-Type: application/json" \
  -d '{"phone":"+70000000000"}' | jq .
# {"status":"sent","resetToken":"a1b2c3d4"}   <- токен утёк в ответе!
```

Пентестер ставит свой номер, получает токен, но токен не привязан к конкретному аккаунту → применяет его к чужому пользователю → сбрасывает пароль → ATO. Отчёт: критический ATO.

## Частые ошибки и подводные камни

- Искать одну «большую» дыру, игнорируя цепочки из мелких.
- Проверять rate-limit слабым перебором (2-3 попытки) — вывод о защите некорректен.
- Забывать про инвалидацию OTP/токенов после использования.
- Не проверять привязку reset-токена к конкретному пользователю.
- Тестировать на чужом аккаунте — грубое нарушение этики и scope; всегда свой тестовый аккаунт.
- Не учитывать server-side vs client-side: обход клиентской проверки Frida ничего не значит, если сервер проверяет сам.

## Справочная таблица векторов

| Звено | Признак | Проверка |
|-------|---------|----------|
| OTP | нет 429 после N попыток | серия запросов |
| OTP | код в ответе/логе | смотрим body, logcat |
| OAuth | нет `state`/PKCE | разбор authorize-URL |
| OAuth | слабый `redirect_uri` | подмена на свой хост |
| Reset | токен в ответе | curl, смотрим body |
| Reset | токен без привязки | применить к другому юзеру |
| Device | подмена `device_id` | изменить тело запроса |
| Attestation | клиентский гейт | Frida-хук |

## Что дальше / решение

- **OTP/токен утекает или не привязан** → стройте PoC ATO и фиксируйте полный сценарий.
- **OAuth без state/PKCE** → цепочка перехвата кода через deep-link.
- **Есть rate-limit** → ищите обход (разные IP, заголовки, регистр, вариации формата).
- **Всё закрыто** → переходите к IDOR/BOLA для доступа к данным и к анализу биометрии/device-binding.
- Приоритизация в отчёте: полный ATO — Critical; перехват кода без обмена — High; отсутствие rate-limit — Medium/High по последствиям.

## Перехват и модификация ответов через Frida

Частая ошибка мобильных приложений — доверять клиентской проверке. Если сервер возвращает `{"success": false}`, а клиент сам решает, пускать ли пользователя, то хук на разбор ответа даёт обход.

```javascript
Java.perform(function () {
  // принудительно «успешный» ответ на проверку OTP
  var Resp = Java.use('com.target.app.api.VerifyResponse');
  Resp.isValid.implementation = function () {
    console.log('[bypass] isValid -> true');
    return true;
  };
  // либо подмена поля в JSON-модели
  var Model = Java.use('com.target.app.model.LoginResult');
  Model.success.overwrite(true);
});
```

Важно понимать: обход клиентской проверки **не является** уязвимостью, если сервер проверяет сам. Настоящая находка — когда серверный ответ всё равно выдаёт токен/сессию, то есть проверка целиком на клиенте.

## Проверка инвалидации OTP и токенов

Правильный OTP/токен должен инвалидироваться после первого использования и иметь срок жизни. Проверка:

```bash
# 1) запрашиваем OTP, применяем один раз -> успех
# 2) повторяем тот же код -> должен быть отказ
curl -s -X POST https://api.example/v1/verify -d '{"otp":"123456"}'
curl -s -X POST https://api.example/v1/verify -d '{"otp":"123456"}'   # reuse
# 3) ждём дольше TTL и пробуем снова -> должен истечь
```

Если старый код продолжает работать — это звено для цепочки (replay). Аналогично проверяйте reset-токены и magic-link: многоразовость или отсутствие TTL превращает утечку ссылки в ATO.

## Тестирование rate-limit правильно

Отсутствие rate-limit легко ложно подтвердить или ложно опровергнуть. Методика:

- считайте именно неверные попытки и ищите `429`/`423`/блокировку;
- меняйте источник (X-Forwarded-For, разные аккаунты) — иногда лимит привязан к IP, а не к аккаунту;
- проверяйте, сбрасывается ли счётчик после успешного входа;
- проверяйте лимит на «отправить OTP снова» (SMS-bombing) отдельно от лимита на «проверить код».

## Справочная таблица «признак → вектор ATO»

| Наблюдение | Вектор | Severity |
|------------|--------|----------|
| нет `state` в OAuth | hijacking кода | High |
| нет PKCE | перехват code | High |
| `redirect_uri` слабый | утечка кода | High |
| reset-токен в ответе | ATO напрямую | Critical |
| reset-токен без привязки | ATO чужого аккаунта | Critical |
| нет rate-limit на OTP | перебор | Medium/High |
| OTP многоразовый | replay | Medium |
| device_id в теле | подмена устройства | High |

## Правовые и этические рамки

ATO-тестирование всегда проводится **на собственных тестовых аккаунтах** и в рамках согласованного scope. Перебор OTP против чужого аккаунта, даже «для доказательства», — это уже атака. В bug bounty используйте два своих аккаунта (A и B) и показывайте переход A→B. Все PoC — минимально достаточные, без реального вреда данным.
