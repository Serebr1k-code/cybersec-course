## Вопрос, с которого всё начинается

В приложении есть «секрет» — ключ шифрования, API-токен или проверочная строка. Он не приходит с сервера, а зашит внутрь. Значит, его можно достать из APK, не запуская приложение. Как найти такой секрет и как понять, что найденное — действительно он?

## Наш пример: UnCrackable Level 1

Возьмём учебное приложение **UnCrackable Level 1** (OWASP MSTG). В нём есть проверка «правильной строки», зашитой в код. Разберём полный путь от APK до расшифрованного секрета.

## Шаг 1: первичный триаж строками

APK — это ZIP. Первое, что делают, — прогоняют его через `strings` и ищут «говорящие» слова:

```
$ strings uncrack1.apk | grep -iE 'secret|key|token|flag|password'
Enter the Secret String
```

Приложение само просит «Secret String» — значит, проверка точно есть. Но сам секрет в открытом виде не лежит: он либо в коде, либо зашифрован. Идём в код.

## Шаг 2: декомпилируем и читаем логику

Распакуем DEX в Java через jadx:

```
$ jadx -d out --no-res uncrack1.apk
$ find out -name '*.java'
out/sources/sg/vantagepoint/uncrackable1/MainActivity.java
out/sources/sg/vantagepoint/uncrackable1/a.java
out/sources/sg/vantagepoint/a/a.java
```

В `MainActivity` видно, как проверяется ввод: вызывается метод `a.a(obj)`. Открываем класс `a`:

```java
public class a {
    public static boolean a(String str) {
        byte[] bArr = sg.vantagepoint.a.a.a(
            b("8d127684cbc37c17616d806cf50473cc"),
            Base64.decode("5UJiFctbmgbDoLXmpL12mkno8HT4Lv8dlat8FxR2GOc=", 0));
        return str.equals(new String(bArr));
    }
    public static byte[] b(String str) { /* hex -> bytes */ }
}
```

Здесь прямо в коде лежат **два секрета**:

- `8d127684cbc37c17616d806cf50473cc` — 32 hex-символа, то есть 16 байт: **ключ AES-128**;
- `5UJiFctbmgbDoLXmpL12mkno8HT4Lv8dlat8FxR2GOc=` — Base64, расшифровывается в 32 байта: **шифртекст**.

А в `sg.vantagepoint.a.a` видно, чем расшифровывают:

```java
SecretKeySpec k = new SecretKeySpec(bArr, "AES/ECB/PKCS7Padding");
Cipher c = Cipher.getInstance("AES");
c.init(2, k);          // 2 = DECRYPT_MODE
return c.doFinal(bArr2);
```

То есть секрет хранится **зашифрованным**, а ключ к нему — тут же рядом, открытым текстом. Это классическая ловушка: шифрование без сокрытия ключа бесполезно.

## Шаг 3: воспроизводим расшифровку

Раз алгоритм и ключ известны, расшифруем сами. AES-128-ECB с ключом-байтами из hex:

```
$ python3 - <<'EOF'
import base64
from Crypto.Cipher import AES
key = bytes.fromhex("8d127684cbc37c17616d806cf50473cc")
ct  = base64.b64decode("5UJiFctbmgbDoLXmpL12mkno8HT4Lv8dlat8FxR2GOc=")
print(AES.new(key, AES.MODE_ECB).decrypt(ct))
EOF
b'I want to believe\x0f\x0f\x0f\x0f\x0f\x0f\x0f\x0f\x0f\x0f\x0f\x0f\x0f\x0f\x0f'
```

Получаем `I want to believe` — это и есть секрет. Хвост из байтов `0x0f` — это **PKCS7-паддинг**: блочный шифр работает блоками по 16 байт, и недостающие байты дополняют значением, равным их количеству (здесь 15 байт `0x0f`). Убираем паддинг — секрет готов.

Обратите внимание: мы не запускали приложение и не реверсили нативный код — только декомпилировали и повторили шифрование.

## Шаг 4: где ещё прячут секреты

Тот же подход работает для других мест:

- **Ресурсы** — `res/values/strings.xml` (после apktool), `assets/` (часто конфиги, `.json`, `.properties`).
- **`BuildConfig`** — константы, зашитые при сборке: `API_KEY`, `BASE_URL`.
- **`AndroidManifest.xml`** — ключи карт, App ID, секреты в `<meta-data>`.
- **Нативный код** — строки в `.rodata` `.so`, иногда XOR-обфусцированные (см. `mobile-android-native`).
- **Сторонние SDK** — Firebase, Google Maps, аналитика: их ключи лежат в APK и легко находятся.

Быстрый рекурсивный поиск по распакованному APK:

```
$ grep -rInE 'AIza[0-9A-Za-z_-]{35}|AKIA[0-9A-Z]{16}|-----BEGIN' out/
```

Это сигнатуры типовых ключей: `AIza...` — Google API, `AKIA...` — AWS access key.

Помимо регулярных выражений, применяют **поиск по энтропии**: настоящий ключ — это случайная строка, и её «энтропия» (мера непредсказуемости символов) выше, чем у обычного текста. Инструмент `trufflehog` и подобные сканеры вычисляют энтропию и выделяют подозрительно случайные фрагменты, которые не совпали ни с одним шаблоном. Это помогает найти ключи нестандартного формата, которые `grep` пропустил.

Отдельная категория — **секреты сторонних SDK**. Firebase-конфиг (`google-services.json`, зашитый в ресурсы) содержит ключ API, а карты и аналитика кладут свои ключи в манифест или ресурсы. Их легко найти, и они часто реально активны — но проверить их работу нужно аккуратно, чтобы не нарушить границы тестирования.

## Шаг 5: проверяем находку

Не всё, что похоже на ключ, им является. Признаки настоящего секрета:

1. **Он используется в коде** — на него ссылается логика, а не просто строка в ресурсах.
2. **Формат совпадает** с ожидаемым (длина, алфавит, префикс).
3. **Он что-то открывает** — расшифровывает данные, даёт доступ к API, проходит проверку.

Последний пункт — решающий. В нашем примере ключ `8d12...` реально расшифровал секрет, поэтому он настоящий. Ключ, который нигде не используется, — мусор.

## Шаг 6: что делать, если ключа рядом нет

Иногда секрет зашифрован, а ключ приходит с сервера или выводится из чего-то известного (например, из имени пакета). Тогда прямой путь не работает, и порядок такой:

1. **Найти место расшифровки.** В jadx ищем `Cipher`, `doFinal`, `SecretKeySpec` — это точки, где данные расшифровываются.
2. **Понять, откуда берётся ключ.** Если он вычисляется (например, хэш от строки), повторяем вычисление. Если приходит из сети — перехватываем трафик (см. урок про MITM).
3. **Перехватить в рантайме.** Вместо того чтобы повторять алгоритм, хук на `Cipher.doFinal` или на метод, возвращающий ключ, покажет расшифрованные данные «как есть».

Часто самый быстрый путь — не расшифровывать самому, а попросить приложение расшифровать за тебя, перехватив результат. Это тот же принцип, что и с нативными проверками: не повторять логику, а наблюдать её в рантайме.

## Шаг 7: автоматизация триажа

Когда APK много, ручной `grep` не масштабируется. Для потока используют сканеры секретов:

- **`trufflehog filesystem out/`** — рекурсивно ищет и проверяет секреты, включая по энтропии;
- **`gitleaks detect --source out/`** — сканер с набором правил под типовые ключи;
- **MobSF** — в отчёте по APK отдельный раздел со строками, ключами и потенциальными секретами.

Эти инструменты не заменяют понимание: они подсвечивают кандидатов, а подтверждать всё равно нужно вручную — декомпилировать и проверить, что ключ используется.

## Что мы теперь знаем

По-простому:

1. Зашитые секреты ищут `strings`, `grep` по распакованному APK и декомпиляцией через jadx.
2. Шифрование в приложении бесполезно, если ключ лежит рядом с шифртекстом.
3. AES-ECB с известным ключом легко воспроизводится — секрет расшифровывается без запуска.
4. PKCS7-паддинг добавляет байты в конце — их надо отбрасывать.
5. Настоящий секрет тот, который используется в коде и реально что-то открывает.

## На что смотреть дальше

- **Не останавливайтесь на `strings`.** Секрет может быть зашифрован — идите в jadx.
- **Ищите ключ рядом с шифртекстом.** В мобильных приложениях это самое частое.
- **Проверяйте сигнатуры ключей.** `AIza`, `AKIA`, `-----BEGIN` — быстрые маркеры.
- **Не сообщайте о «ключе», не проверив его работу.** Ложные находки обесценивают отчёт.

## Куда дальше

Мы научились вытаскивать секреты, зашитые в приложение. В следующем уроке разберём, как приложение пытается этому противодействовать на уровне интерфейса — запрет скриншотов (`FLAG_SECURE`) — и как такой запрет обходится. А пока главное: зашитый секрет — это всегда компромисс, и если ключ лежит рядом с шифртекстом, секрет считается раскрытым.

## Где пригодится

- **CTF Mobile:** поиск флагов и секретов в ресурсах и коде.
- **Bug bounty:** утечки API-ключей и токенов в клиенте — валидные находки.
- **Пентест:** оценка хранения секретов по OWASP MASVS-CRYPTO.
- **Работа:** рекомендации — выносить секреты на сервер, использовать аттестацию.
