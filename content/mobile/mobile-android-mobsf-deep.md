## Вопрос, с которого всё начинается

У вас не одно приложение, а двадцать — и каждое надо проверить на типовые проблемы: экспорт
компонентов, хардкод-секреты, небезопасный TLS. Открывать каждое в JADX и вручную проверять
одни и те же чек-листы — часы рутины. Нужен автоматический сканер, который прогонит всё сам.

## Наш пример: app.apk и MobSF

MobSF (Mobile Security Framework) — сканер, который делает статический и динамический анализ
APK/IPA и выдаёт отчёт. Поднимаем его локально в контейнере:

```bash
$ docker run -it -p 8000:8000 opensecurity/mobile-security-framework-mobsf:latest
[INFO] Running on http://0.0.0.0:8000
```

Теперь у нас есть HTTP-сервис на порту 8000. Кликать по веб-интерфейсу можно, но для
автоматизации нужен API.

## Шаг 1: авторизация в API

MobSF использует API-ключ, который лежит в конфиге и виден на странице профиля:

```bash
$ curl -s http://localhost:8000/api/v1/scan -H 'Authorization: <APIKEY>'
```

Ключ передаётся заголовком `Authorization`. Без него API вернёт 401.

## Шаг 2: загрузка файла

```bash
$ curl -s -F 'file=@app.apk' http://localhost:8000/api/v1/upload -H 'Authorization: <APIKEY>'
{"hash":"a1b2c3d4e5f6","scan_type":"apk","file_name":"app.apk"}
```

Сканер посчитал хеш файла — по нему потом запрашивается отчёт. Хеш — это уникальный отпечаток
содержимого файла, он же идентификатор сканирования.

## Шаг 3: запуск сканирования

```bash
$ curl -s -F 'hash=a1b2c3d4e5f6' http://localhost:8000/api/v1/scan -H 'Authorization: <APIKEY>'
```

Сканирование занимает от секунд до минут. По завершении MobSF готов отдать отчёт.

## Шаг 4: получение JSON-отчёта

```bash
$ curl -s -F 'hash=a1b2c3d4e5f6' http://localhost:8000/api/v1/report_json        -H 'Authorization: <APIKEY>' -o report.json
$ jq '.appsec.high, .appsec.warning' report.json
```

`report.json` — структурированный отчёт. Внутри разделы `appsec` (проблемы безопасности),
`manifest_analysis`, `permissions`, `secrets`. Ключевое преимущество JSON — его можно парсить
скриптом и вытаскивать только важное.

## Шаг 5: что именно находить в отчёте

```bash
$ jq -r '.appsec.high[] | .title' report.json
Exported Activity
Hardcoded Secret in Java
```

Так мы получаем список проблем, отсортированный по критичности. Дальше скрипт может сравнивать
отчёт с порогом: например, «если есть critical — упасть с ошибкой». Это и есть встраивание в CI.

## Шаг 6: динамический анализ

MobSF умеет и динамику: загрузить APK на эмулятор, запустить и перехватить трафик. Для этого
нужен запущенный эмулятор Android и настройка динамического анализатора. Это сложнее и
требует окружения, но даёт то, чего не видит статика: реальные сетевые запросы, поведение в
рантайме, работа с хранилищем.

## Шаг 7: чего MobSF не видит

Автосканер — это не замена ручному анализу. Он не понимает бизнес-логику, не находит сложные
цепочки и не доказывает эксплуатируемость. Он отлично ловит типовое: экспорт, хардкод,
небезопасные флаги. Поэтому MobSF используют как первый проход, а дальше руками разбирают
самое интересное.

## Шаг 8: статический и динамический анализ вместе

Статический анализ MobSF разбирает APK без запуска: манифест, разрешения, экспорт компонентов,
хардкод-секреты, небезопасные флаги. Динамический — запускает приложение на эмуляторе и
наблюдает поведение: сетевые запросы, работу с файлами, логи. Сила в комбинации: статика
подсказывает, что проверять, а динамика подтверждает или опровергает.

```bash
$ curl -s -F 'hash=a1b2c3d4e5f6' http://localhost:8000/api/v1/dynamic/start_analysis \
    -H 'Authorization: <APIKEY>'
```

Динамический анализ требует подготовленного эмулятора (`adb devices` должен показывать
устройство). Если эмулятора нет, доступна только статика.

## Шаг 9: встраивание в CI

Главная ценность JSON-отчёта — автоматизация. Скрипт проверяет отчёт и «падает», если найдено
критичное:

```bash
$ n=$(jq '[.appsec.critical[]?] | length' report.json)
$ if [ "$n" -gt 0 ]; then echo "BLOCK: $n critical"; exit 1; fi
```

Так мобильный анализ становится частью конвейера: каждое изменение сборки прогоняется через
MobSF, и релиз блокируется при появлении критичных проблем. Порог задаётся политикой команды.

## Шаг 10: работа с iOS

MobSF умеет и IPA: загрузка и сканирование устроены так же, но статический анализ IPA без
jailbreak ограничен (бинарник зашифрован). Для полноценного анализа IPA сначала
«дешифруют» (dump decrypted) на jailbreak-устройстве, а затем сканируют. Часть проверок (URL,
классы, Info.plist) доступна и без дешифровки.

## Таблица: что находит MobSF

| Раздел | Что показывает |
|---|---|
| manifest_analysis | экспорт компонентов, debug-флаг, backup |
| permissions | опасные разрешения |
| secrets | хардкод-ключи, токены, URL |
| appsec | проблемы безопасности с severity |
| code_analysis | небезопасные вызовы API |

## Ограничения

MobSF не понимает бизнес-логику и не находит уязвимости, требующие цепочки шагов. Он может
давать ложные срабатывания (например, «секрет» в тестовых данных) и пропускать обфусцированный
код. Поэтому отчёт — это вход в ручной анализ, а не его замена. Сканер экономит время на
типовом, оставляя человеку самое интересное.

## Практический вывод

Рабочий процесс с MobSF прост: поднять сканер, прогнать APK через API, распарсить JSON, взять
самые серьёзные находки и проверить их руками. Встраивание в CI превращает это в постоянный
контроль качества сборок. Главное — не принимать отчёт как истину: автосканер расставляет
приоритеты, но доказательства собирает человек.

## Шаг 11: MobSF и другие сканеры

MobSF — не единственный инструмент. Полезно знать альтернативы и их ниши:

| Инструмент | Тип | Сильная сторона |
|---|---|---|
| MobSF | статика + динамика | веб-интерфейс + API, CI |
| APKLeaks | статика | быстрый поиск секретов |
| QARK | статика | анализ компонентов |
| Frida + скрипты | динамика | гибкость, ручной контроль |
| jadx | декомпиляция | чтение кода |

На практике их комбинируют: MobSF даёт общий обзор, APKLeaks — быстрый срез секретов, jadx —
глубокое чтение. Автосканеры расставляют приоритеты, а доказательства собирают вручную.

## Как читать отчёт и приоритизировать

Не все находки одинаково важны. Порядок разбора: сначала `critical` и `high` (экспорт
компонентов, хардкод-ключи, разрешённый debug), затем `warning` (небезопасные флаги, слабый
TLS), и только потом `info`. Для каждой критичной находки проверяют эксплуатируемость: экспорт
компонента — реально ли его вызвать без прав; секрет — действителен ли он. Отчёт — это список
гипотез, а не приговор.

## Пример полного прогона в CI

```bash
$ curl -s -F 'file=@app.apk' http://localhost:8000/api/v1/upload -H "Authorization: $KEY" -o up.json
$ HASH=$(jq -r .hash up.json)
$ curl -s -F "hash=$HASH" http://localhost:8000/api/v1/scan -H "Authorization: $KEY" >/dev/null
$ curl -s -F "hash=$HASH" http://localhost:8000/api/v1/report_json -H "Authorization: $KEY" -o report.json
$ jq -r '.appsec.high[]?.title' report.json
Exported Activity
```

Такой скрипт легко встроить в конвейер сборки: он загружает APK, ждёт сканирование и печатает
находки. При необходимости добавляется порог, блокирующий релиз.

## Итоговая мысль

MobSF экономит часы на типовых проверках, но остаётся инструментом приоритизации. Его отчёт —
это карта, по которой вы идёте в ручной анализ: экспортированные компоненты проверяете вызовом,
секреты — валидацией, логику — чтением кода. Встраивание в CI делает проверку постоянной и
дешёвой. Главное — не путать «сканер не нашёл» с «уязвимостей нет».

## Частые вопросы при работе с MobSF

**Нужен ли интернет?** Нет, сканер работает локально; интернет нужен только для загрузки
обновлений баз. **Можно ли сканировать несколько APK пачкой?** Да, через API в цикле; отчёты
хранятся по хешам. **Почему отчёт пустой по динамике?** Обычно не запущен эмулятор или не
настроен динамический анализатор. **Ложные срабатывания бывают?** Да, особенно на «секретах» в
тестовых данных; их проверяют вручную. **Поддерживается ли Flutter/React Native?** Да, но часть
логики лежит в нативных библиотеках и требует отдельного анализа.

## Что делать с ложными срабатываниями

Сканер не знает контекста, поэтому помечает как «секрет» любую строку, похожую на ключ. Порядок
проверки: посмотреть, где строка используется (в коде или только в тестах); проверить, активен
ли ключ (например, попробовать обратиться к API); оценить, есть ли у него срок действия. Если
это тестовый ключ — понижают severity и отмечают в отчёте. Так отчёт становится точным, а не
шумным.

## Итог по MobSF

Автоматический сканер ценен там, где нужен масштаб: двадцать приложений за вечер вместо недели
ручной работы. Он не заменяет аналитика, но расставляет приоритеты и избавляет от рутины.
Правильное использование — прогнать, распарсить, взять топ находок и проверить их руками.
Встроенный в CI, MobSF становится фильтром, не пропускающим типовые проблемы в релиз.

## Как совмещать MobSF с ручным анализом

Практический рабочий цикл выглядит так. Сначала прогоняем APK через MobSF и получаем общий
список проблем. Затем берём самые серьёзные находки и проверяем их вручную: экспортированный
компонент пробуем вызвать через `am start`; найденный «секрет» проверяем на действительность;
небезопасный TLS тестируем перехватом трафика. Параллельно открываем код в jadx и ищем то, что
сканер не увидел: логику авторизации, обработку данных, работу с хранилищем. В конце сверяем
результаты: находки сканера подтверждаем или опровергаем, а найденное вручную добавляем в отчёт.
Так автоматизация и ручная работа дополняют друг друга, а отчёт получается и полным, и точным.

## Что мы теперь знаем

- MobSF запускается в docker и даёт HTTP API.
- API авторизуется ключом, файл загружается, сканирование идёт по хешу.
- Отчёт — JSON, который парсится jq и встраивается в CI.
- Есть и динамический анализ, но он требует эмулятора.
- Автосканер дополняет, а не заменяет ручной разбор.

## Куда дальше

Автоматический сканер разобрал типовое, но код, который он не понимает, приходится смотреть
глазами. Если логика спрятана в нативной библиотеке — нужен дизассемблер. Дальше — Ghidra
для Android native.

## Где пригодится

- Массовая проверка приложений на типовые проблемы.
- Встраивание мобильного анализа в CI/CD.
- Быстрый первичный проход перед ручным пентестом.
