## Вопрос, с которого всё начинается

Приложение генерирует «одноразовый» токен для сброса пароля. Токен выглядит случайным — но
если он создан через `java.util.Random`, а не `SecureRandom`, его можно предсказать, зная seed.
Как найти слабый источник случайности и доказать, что он предсказуем?

## Наш пример: генерация токена

Разбираем код:

```java
Random r = new Random();
String token = String.format("%06d", r.nextInt(1000000));
```

`java.util.Random` — не криптостойкий генератор. Весь урок ведём этот пример.

## Шаг 1: случайность бывает разной

**PRNG** (pseudo-random) генерирует числа детерминированно из **seed** (начального числа).
Одинаковый seed → одинаковая последовательность. `java.util.Random` — именно такой PRNG: он
быстрый и воспроизводимый, но **не для безопасности**. Для секретов нужен **CSPRNG**
(криптостойкий) — в Java/Android это `SecureRandom`.

## Шаг 2: чем Random опасен

`new Random()` без seed берёт seed из системного времени (`System.nanoTime()`), а
`new Random(seed)` — из заданного значения. Оба варианта предсказуемы: время можно угадать в
узком окне, а известный seed даёт точную последовательность. Зная seed и позицию, атакующий
вычисляет «случайные» токены.

## Шаг 3: как найти в коде

Ищем вызовы генераторов:

```bash
$ grep -rn 'new Random\|Math.random\|Random(\|SecureRandom' smali/ | head
smali/com/example/Token.smali: invoke-direct {v0}, Ljava/util/Random;-><init>()V
```

`new Random()` в месте генерации токена — красный флаг. `Math.random()` — тот же класс
проблемы.

## Шаг 4: SecureRandom — правильный инструмент

```java
byte[] b = new byte[16];
new SecureRandom().nextBytes(b);
String token = Base64.encodeToString(b, Base64.NO_WRAP);
```

`SecureRandom` берёт энтропию из системного источника и не даёт предсказать следующие
значения. Это стандарт для токенов, ключей, IV, соли.

## Шаг 5: слабый seed — тоже ошибка

Даже `SecureRandom` можно испортить явным seed:

```java
SecureRandom sr = new SecureRandom();
sr.setSeed(System.currentTimeMillis()); // сводит энтропию к времени
```

Явный `setSeed` **добавляет** детерминизм к уже накопленной энтропии; если генератор только
создан и сразу засеян временем, его предсказуемость резко растёт. Это частая ошибка.

## Шаг 6: как доказать предсказуемость

Практический подход:
1. Найти генерацию и её seed-источник (время, счётчик, device ID).
2. Собрать несколько выданных значений.
3. Воспроизвести последовательность для предполагаемого seed.
4. Совпадение → доказано.

Для токена из времени окно поиска — секунды, поэтому перебор seed-ов времени быстрый.

## Шаг 7: где это встречается

- Коды сброса пароля и OTP (самое опасное).
- Идентификаторы сессий.
- IV для шифрования (при слабом IV ломается GCM/CBC).
- Соль для хеширования.
- «Случайные» имена файлов, ключи API.

## Шаг 8: IV и почему это критично

В режиме **CBC** фиксированный или предсказуемый **IV** (initialization vector) позволяет
узнавать, одинаковы ли первые блоки, и открывает атаки на шифротекст. В **GCM** повтор IV при
одном ключе полностью ломает и шифрование, и целостность. Поэтому IV должен быть
криптостойко-случайным и уникальным.

## Шаг 9: как защищают правильно

Использовать `SecureRandom` для всех секретов, не задавать seed вручную, генерировать
достаточную длину (≥128 бит), не полагаться на `Random`/`Math.random`/время. Для токенов —
криптостойкие байты и Base64url. Случайность — фундамент криптографии: слабый генератор
обесценивает любые алгоритмы поверх него.

## Что мы теперь знаем

- `java.util.Random` — предсказуемый PRNG, не для секретов.
- `SecureRandom` — криптостойкий источник для токенов, ключей, IV.
- Явный seed и seed из времени ломают даже SecureRandom.
- Предсказуемость доказывается воспроизведением последовательности.
- Случайность — фундамент, а не деталь.
