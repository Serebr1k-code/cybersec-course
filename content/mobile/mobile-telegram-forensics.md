## Вопрос, с которого всё начинается

Мы разобрали WhatsApp. Теперь другой мессенджер — Telegram. У него нет файла `msgstore`, и
выглядит он совсем иначе: вместо одной базы — каталог с несколькими `.db`. Как понять, где
лежат сообщения и как их прочитать?

## Наш пример: каталог Telegram

```bash
$ ls -l /data/data/org.telegram.messenger/files/
-rw-r--r-- 1 u0_a456 u0_a456  671744 cache4.db
-rw-r--r-- 1 u0_a456 u0_a456    4096 cache4.db-wal
-rw-r--r-- 1 u0_a456 u0_a456   32768 cache4.db-shm
```

Главный файл — `cache4.db`. Рядом `-wal` и `-shm` — служебные файлы **WAL-режима** SQLite.
Весь урок будем вести эту базу.

## Шаг 1: что такое WAL и почему это важно

SQLite может писать изменения не сразу в основную базу, а в отдельный журнал — **Write-Ahead
Log** (файл `-wal`). Свежие сообщения часто лежат именно в `-wal`, а не в `cache4.db`. Файл
`-shm` — разделяемая память для доступа к журналу. Для форензики это критично: если забрать
только `cache4.db`, можно потерять последние сообщения. Забираем все три файла.

## Шаг 2: открытие базы

```bash
$ file cache4.db
cache4.db: SQLite 3.x database
$ sqlite3 cache4.db ".tables"
messages_v2   dialogs      encrypted_*   users      ...
```

Таблица `messages_v2` — это сообщения, `dialogs` — список чатов, `users` — участники.
Смотрим схему:

```bash
$ sqlite3 cache4.db ".schema messages_v2"
CREATE TABLE messages_v2 (
  uid INTEGER,
  dialog_id INTEGER,
  mid INTEGER,
  date INTEGER,
  out INTEGER,
  data BLOB,
  ...
);
```

Поле `data` — **BLOB** (двоичные данные), а не текст. Telegram хранит сообщение сериализованным
объектом, а не строкой. Поле `out` — направление, `date` — время, `dialog_id` — чат.

## Шаг 3: чтение сообщений

Просто `SELECT data` даст бинарь. Нужен либо инструмент-парсер (например, скрипты из
`telegram-forensics`), либо разбор BLOB вручную. Часть строк всё же читаема:

```bash
$ sqlite3 cache4.db "SELECT dialog_id, out, date, hex(substr(data,1,8)) FROM messages_v2 ORDER BY date DESC LIMIT 3;"
1234|1|1756720511|2A020A01
1234|0|1756720499|2A020A01
1234|0|1756720480|2A020A01
```

`2A020A01` — префикс сериализованного сообщения. Специализированный парсер вытащит из него
текст, автора и вложения. Важно: в кэше лежит и то, что пользователь мог «удалить» — кэш
чистится лениво.

## Шаг 4: dialogs и users

Даже без разбора BLOB метаданные дают много:

```bash
$ sqlite3 cache4.db "SELECT did, date, unread_count FROM dialogs ORDER BY date DESC LIMIT 3;"
1234|1756720511|2
```

`dialogs` показывает, с кем и когда общались, сколько непрочитанных. `users` — имена и
телефоны. Связка `dialog_id` → `users` даёт, кому принадлежит чат.

## Шаг 5: секретные чаты и iOS

Секретные чаты Telegram (`encrypted_*`) устроены иначе: ключ только на устройстве, сервер
хранит шифротекст. В форензике их читают через дамп памяти процесса или хукинг рантайма, а не
из `cache4.db`. На iOS данные лежат в контейнере приложения
(`Containers/Data/Application/<uuid>/Documents/`), в тех же `cache4.db`; путь находят по
`Manifest.db` из бэкапа.

## Шаг 6: облако

Telegram-облако синхронизирует обычные (не секретные) чаты. Это значит, что часть переписки
восстанавливается через API аккаунта (Telegram Desktop), а не из устройства. Для отчёта важно
разделять «нашёл на устройстве» и «подтвердил через облако».

## Шаг 7: типы данных и вложения

В `cache4.db` лежит не только текст. Таблица `messages_v2` хранит и служебные записи
(изменение аватара, создание группы), а вложения описываются в отдельной таблице. Медиафайлы
складываются в подкаталоги кэша, а их имена — это идентификаторы, по которым можно связать
файл с сообщением. В форензике это важно: фотография, отправленная в чат, может содержать
метаданные о времени и месте, а документ — быть сканом паспорта или договора.

## Шаг 8: секретные чаты и ключи

Секретные чаты Telegram используют end-to-end шифрование по протоколу MTProto: сервер хранит
только шифротекст, а ключ есть лишь у двух устройств. Значит, из `cache4.db` их текст не
достать — там лежат либо зашифрованные блобы, либо метаданные. Чтобы прочитать переписку,
нужен доступ к расшифрованному состоянию в памяти: дамп процесса, хукинг рантайма или
эмуляция устройства с известным ключом. Это уже динамическая форензика, и она опирается на
инструменты из ветки Frida. Практический вывод: если клиент заявляет «у нас секретные чаты»,
проверяйте, есть ли вообще на устройстве ключ, или переписка недостижима.

## Шаг 9: iOS-контейнер

На iOS данные Telegram лежат не в `/data/data`, а в контейнере приложения:
`Containers/Data/Application/<uuid>/Documents/`. Точный `<uuid>` узнают из `Manifest.db` в
бэкапе — это база, которая сопоставляет логические пути и идентификаторы. Дальше схема та же:
`cache4.db`, таблица `messages_v2`. Дополнительно в iOS-песочнице встречается кэш вложений и
`preferences`, где лежат идентификаторы аккаунта.

```bash
$ sqlite3 Manifest.db "SELECT fileID FROM Files WHERE relativePath LIKE '%cache4.db';"
```

## Шаг 10: облако против устройства

Telegram синхронизирует обычные чаты в облако, поэтому часть переписки можно восстановить
через API аккаунта (например, экспортом из Telegram Desktop), а не из устройства. Для отчёта
это принципиально: факт, полученный из облака, имеет другой источник доказательства, чем факт
из локальной базы. Всегда разделяйте «найдено на устройстве» и «подтверждено через облако», а
также указывайте, что именно не синхронизируется (секретные чаты).

## Шаг 11: удалённые сообщения и кэш

Telegram кэширует сообщения лениво: даже удалённые в приложении записи какое-то время остаются
в `messages_v2` и в `-wal`. Поэтому дамп надо снимать целиком, включая журнальные файлы, и как
можно раньше после интересующего события. Если есть основания считать, что пользователь
чистил кэш, восстановление удалённых записей из свободных страниц базы даёт дополнительный
материал — тем же приёмом, что и в браузерной форензике.

## Шаг 12: MTProto и что он защищает

Telegram использует собственный протокол **MTProto**. Обычные (облачные) чаты шифруются в
транзите и на сервере, но сервер видит содержимое — поэтому их можно восстановить через
аккаунт. Секретные чаты — end-to-end: сервер хранит только шифротекст, а ключ есть лишь у
устройств. Из этого следуют два разных подхода к форензике: облачные чаты достают из
`cache4.db` и из API, секретные — только из памяти устройства. Не путайте эти два случая: в
отчёте должно быть ясно, какой тип чата рассматривается.

## Шаг 13: работа с WAL и целостностью

Как и в любой базе SQLite, у Telegram есть журнал `-wal` и разделяемая память `-shm`. Если
снять только `cache4.db`, вы потеряете свежие записи. Правильный порядок — скопировать все
три файла атомарно (в идеале на остановленном приложении), затем открыть. Перед этим — хэши
исходников. Если база открыта «на живую», результаты могут быть противоречивы: два чтения
дадут разные наборы сообщений.

## Шаг 14: идентификаторы и связывание

Каждый чат и пользователь в Telegram имеет числовой идентификатор. `dialog_id` связывает
сообщение с чатом, а таблица `users` — идентификатор с именем и телефоном. По этим связям
восстанавливают, кто с кем общался. Дополнительно полезны `dialogs` (последняя активность) и
служебные записи об изменении состава групп. Связывание по идентификаторам — ключ к читаемой
картине: без него вы видите набор числовых строк.

## Шаг 15: чек-лист Telegram-форензики

(1) Хэши `cache4.db`, `-wal`, `-shm`; (2) определён путь (Android/iOS); (3) база скопирована
целиком; (4) разобраны `messages_v2`, `dialogs`, `users`; (5) выявлены секретные чаты и
указано, что для них нужен дамп памяти; (6) проверен облачный доступ через аккаунт;
(7) в отчёте разделены «устройство» и «облако».

## Шаг 16: вложения, стикеры и медиа

Telegram щедро кэширует медиа. Вложения, стикеры, гифки и аватары складываются в подкаталоги
кэша, а база хранит ссылки на них. Для форензики это важно по двум причинам. Во-первых, по
медиа восстанавливают контекст: что пересылали, какие документы получали. Во-вторых, сами
файлы содержат метаданные (EXIF у фотографий, имена у документов), которые не зависят от
приложения. Кэш медиа живёт дольше, чем текст: даже если сообщение удалено, картинка может
остаться на диске.

## Шаг 17: экспорт через API и его пределы

Облачные чаты можно выгрузить через клиент Telegram Desktop (экспорт чата в JSON/HTML). Это
законный путь, когда есть доступ к аккаунту, и он даёт полную переписку, включая старую. Но
есть пределы: секретные чаты не экспортируются, а удалённые из облака сообщения не
восстанавливаются. Поэтому API-экспорт дополняет, а не заменяет анализ устройства. В отчёте
всегда разделяют источник: «экспорт облака» и «локальный кэш».

## Шаг 18: ограничения форензики Telegram

Главное ограничение — секретные чаты. Их ключ не хранится в базе, поэтому файл бесполезен.
Второе ограничение — ленивая очистка: часть данных уже удалена, а часть ещё в журнале, и
результат зависит от момента снятия дампа. Третье — шифрование кэша на новых версиях. Вывод:
для Telegram всегда снимают полный дамп и как можно раньше, а для секретных чатов заранее
оговаривают, что нужен доступ к памяти или к разблокированному устройству.

## Что мы теперь знаем

- Сообщения Telegram — в `cache4.db`, таблица `messages_v2`.
- Поле `data` — BLOB; нужен парсер, а не просто SELECT.
- Свежие записи могут лежать в `-wal`; забираем все три файла.
- `dialogs`/`users` дают метаданные чатов и участников.
- Секретные чаты требуют дампа памяти, а не базы.
