## Вопрос, с которого всё начинается

В прошлом уроке мы нашли JNI-функцию по имени `Java_...` и прочитали секрет прямо из дизассемблера. Но в реальных приложениях так везёт не всегда: символов нет, строки зашифрованы, а библиотека собрана под другую архитектуру. Как действовать, когда простой путь не работает?

## Наш пример: та же библиотека, но глубже

Возьмём **тот же** `libfoo.so` из UnCrackable Level 2 и посмотрим на него так, как смотрят на защищённое приложение: сравним архитектуры, разберём JNI-конвенции и научимся находить функцию, даже когда имя скрыто.

## Шаг 1: одна библиотека — четыре архитектуры

В APK лежат четыре версии одной библиотеки. Это не дубликаты: под каждый процессор свой машинный код. Сравним две:

```
$ file lib/x86/libfoo.so
libfoo.so: ELF 32-bit LSB shared object, Intel i386, ... stripped
$ file lib/arm64-v8a/libfoo.so
libfoo.so: ELF 64-bit LSB shared object, ARM aarch64, ... 
```

x86 — 32-битный Intel, arm64 — 64-битный ARM. Реальные телефоны работают на ARM, эмуляторы часто на x86. Отсюда правило: **берите ту версию, на которой будете запускать**, иначе не поймёте ни дизассемблер, ни поведение хука.

Полезно посмотреть зависимости и секции — они одинаковы по смыслу:

```
$ readelf -d lib/arm64-v8a/libfoo.so | grep NEEDED
 (NEEDED)  Shared library: [libm.so]
 (NEEDED)  Shared library: [libdl.so]
 (NEEDED)  Shared library: [libc.so]
$ readelf -S lib/arm64-v8a/libfoo.so | grep -E 'text|rodata'
 [10] .text    PROGBITS   0x8a0
 [11] .rodata  PROGBITS   0xea0
```

`.text` — код, `.rodata` — константы. Всё как у обычного ELF.

## Шаг 2: почему JNI-имена иногда не видны

`nm -D` показывает только **экспортируемые** символы. Их два вида. Первый — именованные, как у нас:

```
$ nm -D lib/arm64-v8a/libfoo.so | grep Java_
0000000000000dac T Java_sg_vantagepoint_uncrackable2_CodeCheck_bar
0000000000000d8c T Java_sg_vantagepoint_uncrackable2_MainActivity_init
```

Обратите внимание на адреса: `0xdac` и `0xd8c`. Это **смещения от начала библиотеки**, и они понадобятся для хука по адресу.

Второй способ — **`RegisterNatives`**: приложение не полагается на имена, а в `JNI_OnLoad` динамически регистрирует таблицу из пар «имя метода, сигнатура, указатель на функцию». В этом случае в `nm -D` остаётся только `JNI_OnLoad`, а функции `Java_...` вообще нет. Это популярная защита: убрать имена — значит усложнить реверс.

Чтобы достать эту таблицу, перехватывают сам вызов `RegisterNatives` — он получает массив методов, и его можно выгрузить в рантайме:

```javascript
var rn = Module.getGlobalExportByName("RegisterNatives");
Interceptor.attach(rn, { onEnter(args) {
  var methods = args[2], n = args[3].toInt32();
  for (var i = 0; i < n; i++) {
    var name = methods.add(i * 12).readPointer().readCString();
    var fn   = methods.add(i * 12 + 8).readPointer();
    console.log(name + " -> " + fn);
  }
}});
```

Так вы получаете имена и адреса всех нативных методов — основу для хуков даже без символов.

## Шаг 3: JNI-конвенции и ABI

Чтобы читать нативный код, надо помнить сигнатуру. Любая JNI-функция получает первыми двумя аргументами `JNIEnv*` (интерфейс к виртуальной машине) и `jobject`/`jclass` (объект или класс Java). Пользовательские аргументы идут следом.

Как они передаются — зависит от архитектуры:

- **ARM64:** первые 8 аргументов в регистрах `x0`–`x7`, результат в `x0`. То есть `x0` = `JNIEnv*`, `x1` = `jobject`, `x2` = наш `byte[]`.
- **x86 (32-бит):** аргументы в стеке — `[esp]`, `[esp+4]`, `[esp+8]`.

Зная это, в Ghidra вы сразу читаете, где какой аргумент, и находите пользовательский ввод.

## Шаг 4: читаем функцию, когда символов нет

Вернёмся к нашей `bar`. В x86-версии секрет собирается в коде — смотрим дизассемблер:

```
$ objdump -d --disassemble=Java_sg_vantagepoint_uncrackable2_CodeCheck_bar lib/x86/libfoo.so
00000f60 <Java_..._CodeCheck_bar@@Base>:
     f8e:  movl  $0x6e616854,(%esp)
     f95:  movl  $0x6620736b,0x4(%esp)
     f9d:  movl  $0x6120726f,0x8(%esp)
     fa5:  movl  $0x74206c6c,0xc(%esp)
     fad:  movw  $0x6568,0x10(%esp)
     fb4:  movl  $0x73696620,0x12(%esp)
     fbc:  movw  $0x68,0x16(%esp)
```

Это сборка строки в стеке. x86 хранит числа младшим байтом вперёд, поэтому `0x6e616854` = `54 68 61 6e` = `Than`. Складываем все куски и получаем **`Thanks for all the fish`** — ожидаемый секрет.

А теперь важное наблюдение: **в arm64-версии этой же библиотеки строки в коде нет** — там в `.rodata` лежит только фрагмент `Thanks for all t`. Компиляторы под разные ABI собирают строку по-разному. Мораль: нашли строку в одной архитектуре — проверьте, как она хранится в других, потому что смещения и способ сборки отличаются.

## Шаг 5: динамика — хук по имени и по смещению

Статический реверс даёт ответ, но часто быстрее — перехватить функцию в рантайме. Если имя есть, Frida найдёт его по символу:

```javascript
var f = Module.getGlobalExportByName("Java_sg_vantagepoint_uncrackable2_CodeCheck_bar");
Interceptor.attach(f, {
  onEnter(args) { console.log("bar called"); },
  onLeave(ret) { console.log("ret=" + ret); }
});
```

Если имени нет (используется `RegisterNatives`), берём **базу модуля плюс смещение** из Ghidra:

```javascript
var base = Module.findBaseAddress("libfoo.so");
var check = base.add(0xdac);      // смещение из nm/Ghidra
Interceptor.replace(check, new NativeCallback(function() { return 1; }, 'jboolean', []));
```

Здесь `Interceptor.replace` подменяет функцию целиком: она всегда возвращает «истину». Это классический обход булевой проверки — не нужно понимать логику, достаточно знать, что она возвращает true/false.

Внутреннюю механику Frida — как именно `Interceptor` ставит хук на нативную функцию — мы разберём отдельно в уроке `mobile-hooking-internals`.

## Шаг 6: строковая обфускация и анти-анализ

Если `strings` по `.so` пуст, строки шифрованы и расшифровываются при старте. Тогда находят функцию-декриптор, перехватывают её и логируют результат. Другие защиты:

- **OLLVM** (control-flow flattening) — поток управления запутан, Ghidra декомпилирует плохо; помогает динамика, а не часы статики.
- **anti-debug** — вызов `ptrace(PTRACE_TRACEME)`: если под отладчиком, вернёт ошибку. Обходится подменой `ptrace` на заглушку.
- **anti-Frida** — поиск строк `frida` в `/proc/self/maps`. Обходится тем, что хук ставится до проверки (через spawn), либо переименованием агента.

## Что мы теперь знаем

По-простому:

1. В APK лежит по одной `.so` на архитектуру — берите ту, что совпадает с устройством.
2. JNI-функции бывают именованными (`Java_...`) или зарегистрированными через `RegisterNatives`.
3. ARM64 передаёт аргументы в `x0`–`x7`; `x0` = `JNIEnv*`, `x1` = `jobject`.
4. Хукать можно по имени (`getGlobalExportByName`) или по смещению (`base.add(off)`).
5. Строковая обфускация и OLLVM обходятся динамикой, а не упорной статикой.

## На что смотреть дальше

- **Смещения меняются между сборками.** Фиксируйте хэш `.so`.
- **Проверяйте `JNI_OnLoad`.** Если есть — методы регистрируются динамически.
- **`Interceptor.replace` для булевых проверок.** Самый быстрый обход.
- **Не тратьте часы на OLLVM.** Динамика быстрее.

## Куда дальше

Мы разобрали нативную сторону Android: архитектуры, JNI, статику и динамику. Дальше логично перейти к тому, как именно Frida перехватывает код — на уровне ART и нативных инлайн-хуков. А пока главное: `.so` реверсится комбинацией «найти смещение → прочитать логику → подменить результат», а архитектура и способ регистрации JNI определяют, как именно это делать.

## Где пригодится

- **Реверс:** нативные проверки — ядро защиты современных приложений.
- **Пентест:** обход нативного root/лицензии и проверок целостности.
- **Bug bounty:** понимание криптографии и логики, вынесенной в `.so`.
- **CTF:** задачи, где флаг проверяется нативным кодом.
