## Вопрос, с которого всё начинается

Приложение банка отправляет команду «открой экран оплаты» не своему экрану, а *всей системе* —
`Intent(ACTION_VIEW)` без указания, кому именно. Система спрашивает: «кто умеет обрабатывать
`ACTION_VIEW`?». И тут в игру вступает любое приложение на телефоне. Как это происходит и как
этим воспользоваться, чтобы перехватить чужую команду?

## Наш пример: вызов без адресата

В декомпилированном коде видим:

```java
Intent i = new Intent("com.example.bank.ACTION_PAY");
i.putExtra("amount", amount);
startActivity(i);
```

`com.example.bank.ACTION_PAY` — это **action**, то есть имя действия. Компонента (конкретного
класса) тут нет. Такой `Intent` называется **неявным**: он не называет получателя, а описывает
работу. Система сама ищет, кто её умеет сделать. Уже здесь видно слабое место: раз адресат не
назван, его может подставить кто угодно. Мы будем вести этот пример через весь урок — от
объявления фильтров до реального перехвата.

## Шаг 1: явный и неявный интент

**Явный** интент называет адресата прямо:

```java
Intent i = new Intent(this, PayActivity.class);
```

Здесь `PayActivity.class` — конкретный класс, система обязана доставить интент ему и только ему.
Подменить получателя нельзя, это надёжный способ общения внутри приложения.

**Неявный** интент адресата не называет. Вместо этого он содержит action, категории и иногда
MIME-тип данных. Любое приложение, в манифесте которого есть подходящий `intent-filter`, может
объявить, что умеет обрабатывать это действие. Если таких приложений несколько, Android
показывает выбор — либо (что важнее для нас) выбирает по приоритету. Запомните простое правило:
**явный интент — это письмо с адресом, неявный — объявление в газете.** Объявление прочитает
любой, кто подписан на рубрику.

## Шаг 2: из чего состоит фильтр

`intent-filter` — это объявление «я умею делать вот это». Он состоит из трёх частей: `<action>`
(что делаю), `<category>` (в каком контексте) и `<data>` (с какими данными — MIME-тип, схема URI,
хост). Чтобы интент подошёл фильтру, должны совпасть action и **все** категории, а если задан
тип данных — ещё и data.

```xml
<activity android:name=".PayActivity" android:exported="true">
  <intent-filter>
    <action android:name="com.example.bank.ACTION_PAY"/>
    <category android:name="android.intent.category.DEFAULT"/>
  </intent-filter>
</activity>
```

Важно: если в интенте категория не указана, система неявно подставляет
`android.intent.category.DEFAULT`. Поэтому фильтр без неё просто не будет найден для обычного
`startActivity`. Разработчики это знают, но атакующий тоже — он всегда добавляет DEFAULT.

## Шаг 3: как система выбирает получателя

Правила подбора: у получателя должен совпасть action, все категории и, если задан тип данных,
MIME. Среди совпавших побеждает тот, у кого выше `android:priority` в фильтре, а при равенстве —
либо диалог выбора, либо приложение, назначенное пользователем «по умолчанию» для этого действия.
Посмотрим, кто вообще регистрируется на наше действие:

```bash
$ adb shell dumpsys package | grep -A3 'com.example.bank.ACTION_PAY'
    com.example.bank.ACTION_PAY:
      com.example.bank/.PayActivity filter priority=0
```

`dumpsys package` печатает зарегистрированные фильтры. Если на наше action, кроме самого банка,
подписан кто-то ещё — это уже подозрительно. В штатной ситуации на внутреннее действие должен
быть подписан только сам пакет.

## Шаг 4: перехват через собственный intent-filter

Атакующее приложение объявляет в манифесте свой фильтр на то же действие:

```xml
<activity android:name=".StealActivity" android:exported="true">
  <intent-filter android:priority="1000">
    <action android:name="com.example.bank.ACTION_PAY"/>
    <category android:name="android.intent.category.DEFAULT"/>
  </intent-filter>
</activity>
```

Теперь при неявном вызове `ACTION_PAY` система может выбрать именно `StealActivity` — особенно
если исходное приложение не задало `setPackage(...)`. Атакующий получает `amount` из extras и
может показать фальшивый экран оплаты. Два условия успеха: (1) действие не закреплено за пакетом,
(2) атакующий объявил фильтр с высоким приоритетом. Оба закрываются одной строкой кода защитника.

## Шаг 5: проверка вручную через adb

Не нужно даже писать приложение, чтобы убедиться в уязвимости. Явно вызвать чужой компонент:

```bash
$ adb shell am start -n com.example.bank/.PayActivity \
    -e amount 1000000 -a com.example.bank.ACTION_PAY
Starting: Intent { act=com.example.bank.ACTION_PAY cmp=com.example.bank/.PayActivity ... }
```

Если так подставляется сумма — бизнес-логика ломается. А неявный вызов без `-n` покажет, какие
приложения вообще готовы принять action:

```bash
$ adb shell am start -a com.example.bank.ACTION_PAY -e amount 1
Starting: Intent { act=com.example.bank.ACTION_PAY }
```

Если система предложит диалог выбора или молча уйдёт не туда — значит действие не закреплено за
пакетом. Тот же тест годится и для проверки, подхватывает ли ваш фильтр чужое действие.

## Шаг 6: intent redirection

Отдельный подвид — **intent redirection** («перенаправление интента»). Уязвимое приложение само
достаёт вложенный Intent из extras и запускает его:

```java
Intent inner = getIntent().getParcelableExtra("next");
startActivity(inner);   // ← доверяем тому, что пришло снаружи
```

Тогда атакующий передаёт свой интент как «next» и заставляет жертву запустить произвольный
внутренний компонент — часто не экспортированный, но доступный только через этот прокси. Это
обёртка «недоверенный вход → доверенный выход». Проверить цепочку можно через `am start` с
вложенным интентом, переданным как Parcelable или как URI.

## Шаг 7: почему это важно на практике

Перехват неявного интента — не теоретическая угроза. На bug bounty такие находки регулярно
классифицируются как medium/high: через подмену действия можно украсть данные из extras, обойти
проверку суммы, заставить приложение открыть свой внутренний экран с подставленными параметрами.
Отдельно ценятся цепочки, где неявный интент ведёт к запуску не экспортированного компонента —
это уже escalation.

## Шаг 8: как защищаться

- Для внутренних вызовов использовать **явный** интент (`new Intent(this, X.class)`).
- Задавать пакет: `intent.setPackage("com.example.bank")` — неявный станет адресным.
- Проверять `getCallingActivity()` / `getCallingPackage()` перед доверием extras.
- Не пробрасывать наружу вложенный `Intent` без проверки, что он указывает внутрь приложения.
- Не объявлять `exported="true"` там, где хватает внутреннего вызова.

## Шаг 9: чек-лист аудита

- Найти в декомпилированном коде все `startActivity`/`startService` без явного класса.
- Проверить, нет ли `setPackage` рядом с неявным вызовом.
- Посмотреть манифест: какие фильтры объявлены на собственные действия пакета.
- Прогнать `am start`/`am startservice` и посмотреть на результат.
- Искать `getParcelableExtra` + `startActivity` — кандидаты на redirection.

## Что мы теперь знаем

- Неявный интент не называет получателя — его выбирает система по фильтрам.
- Фильтр с высоким `priority` может перехватить чужое действие.
- `am start` позволяет проверить и экспортированный компонент, и сам перехват.
- Intent redirection превращает недоверенный вход в запуск внутреннего компонента.
- Защита: явные интенты, `setPackage`, проверка вызывающего.

## Шаг 10: реальные примеры и классы уязвимостей

Разберём, как такие находки выглядят в реальных отчётах, чтобы вы понимали приоритет.
Типичный кейс: приложение объявляет activity `com.bank/.PayActivity` с фильтром на собственное
действие `com.bank.ACTION_PAY`. Второе приложение регистрирует тот же action с приоритетом 1000.
При вызове «оплатить» система отдаёт интент атакующему, и тот получает сумму и идентификатор
заказа. Второй частый кейс — «внутренний» экран, помеченный `exported="false"`, но вызываемый
через `Intent` из другого компонента, который сам экспортирован: получается обход через
redirection. Третий — приложение получает `Intent` от системы (например, от шаринга) и слепо
запускает вложенный компонент из extras.

Отдельно стоит смотреть на `startService`/`bindService` с неявным интентом: там перехват даёт не
только чтение данных, но и выполнение действий от имени приложения. Если сервис принимает
неявный интент и что-то делает с его extras — это ещё опаснее, чем activity.

## Шаг 11: инструменты для поиска

Вручную искать удобно так. Сначала статика: декомпилируем APK через `jadx` и ищем неявные вызовы.

```bash
$ jadx -d out app.apk
$ grep -rn 'new Intent("' out/sources | grep -v 'new Intent(this'
```

Второй проход — манифест: `aapt dump xmltree app.apk AndroidManifest.xml` или
`apktool d app.apk` покажут все фильтры. Затем динамика: `drozer` умеет перечислять
экспортированные компоненты и их фильтры:

```bash
$ drozer console connect
dz> run app.package.attacksurface com.example.bank
dz> run app.activity.info -a com.example.bank
```

Наконец, `am start`/`am broadcast` даёт быструю проверку без написания PoC-приложения.

## Шаг 12: не путать с другими механизмами IPC

Неявный интент — не единственный канал. Не путайте:

- **Явный интент** — адресат задан, перехват невозможен.
- **Deep link** — интент приходит из URI (`https://`/`scheme://`) и тоже попадает в activity;
  это отдельная тема `mobile-deeplink-deep`.
- **Broadcast** — «всем», а не «одному экрану».
- **Content Provider** — доступ к данным по `content://`, а не запуск компонента.

Каждый механизм имеет свою поверхность и свои проверки.

## Частые вопросы

**Можно ли перехватить интент, если activity `exported="false"`?** Напрямую — нет. Но если
экспортированный компонент пробрасывает вложенный `Intent`, то да — через redirection.

**Обязательно ли писать APK для перехвата?** Нет. Часто достаточно `am start` для проверки
подстановки параметров, а для полноценного перехвата — простейшее приложение с фильтром.

**Помогает ли `android:permission` на activity?** Да, если разрешение объявлено с
`protectionLevel="signature"`. Иначе его может запросить любой.
