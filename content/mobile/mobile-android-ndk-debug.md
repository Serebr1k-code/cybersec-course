## Вопрос, с которого всё начинается

Вы нашли в Ghidra функцию проверки, но не понимаете, какие значения туда приходят в реальности:
статический анализ показывает код, но не данные. Нужно остановить программу в нужном месте,
посмотреть регистры и память, пройти по шагам. Для нативного кода это делает отладчик.

## Наш пример: приложение с libcheck.so

Приложение загружает `libcheck.so` и вызывает проверку. Хотим остановиться в функции проверки
и посмотреть аргументы.

## Шаг 1: подготовка устройства

Отладка нативного кода требует прав `ptrace` — то есть rooted-устройства или эмулятора с
отключённой защитой. Проверяем доступ:

```bash
$ adb shell su -c id
uid=0(root) gid=0(root)
```

Без root `ptrace` приложение не разрешит — это механизм, которым ядро запрещает одному процессу
читать память другого.

## Шаг 2: gdbserver на устройстве

`gdbserver` — маленький отладочный сервер, который запускается на устройстве и слушает порт:

```bash
$ adb push gdbserver /data/local/tmp/
$ adb shell su -c '/data/local/tmp/gdbserver :1234 --attach <PID>'
Attached; pid = 1234
Listening on port 1234
```

`--attach <PID>` подключается к уже запущенному процессу приложения. PID можно узнать через
`adb shell pidof com.example`.

## Шаг 3: проброс порта и подключение

```bash
$ adb forward tcp:1234 tcp:1234
$ gdb
(gdb) target remote :1234
Remote debugging using :1234
```

`adb forward` пробрасывает порт с устройства на хост, чтобы gdb на компьютере мог подключиться.

## Шаг 4: базовые операции

```bash
(gdb) info sharedlibrary
0x0000007fb6...  libcheck.so
(gdb) break Java_com_example_NativeChecker_check
Breakpoint 1 at 0x...
```

`break` ставит точку останова — место, где исполнение приостановится. `info sharedlibrary`
показывает, куда загружены библиотеки (адреса рандомизированы из-за ASLR — рандомизации адресного
пространства).

## Шаг 5: инспекция

Когда точка сработала:

```bash
(gdb) info registers x0 x1
x0  0x7fc1234000  0x7fc1234000
x1  0x7fc1234100  0x7fc1234100
(gdb) x/s 0x7fc1234000
0x7fc1234000: "nto-input"
```

`info registers` показывает значения регистров (x0, x1 — аргументы), `x/s` читает строку по
адресу. Так мы видим реальные данные, которых не было в статике.

## Шаг 6: lldb вместо gdb

На macOS/iOS-инструментарии чаще используют lldb. Команды аналогичны: `breakpoint set -n func`,
`register read x0`, `memory read`. Для Android удобен gdb, для iOS — lldb.

## Шаг 7: обход anti-debug

Приложения часто проверяют, не отлаживаются ли они (читают `TracerPid` в `/proc/self/status`).
Признаки: при подключении отладчика приложение падает. Обход: хукать проверку через Frida,
патчить проверку в smali/native, или использовать скрытый отладчик. Иногда проще Frida, чем
gdbserver.

## Что мы теперь знаем

- Отладка native требует root и ptrace.
- gdbserver запускается на устройстве и слушает порт.
- adb forward пробрасывает порт на хост.
- Точки останова, регистры и память показывают реальные данные.
- anti-debug обходят хуком или патчем.

## Куда дальше

процессе, её надо загрузить — и этот механизм тоже поверхность атаки. Дальше — нативные
библиотеки и инъекции.
