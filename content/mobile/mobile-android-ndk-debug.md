## Вопрос, с которого всё начинается

Вы нашли в Ghidra функцию проверки, но не понимаете, какие значения туда приходят в реальности:
статический анализ показывает код, но не данные. Нужно остановить программу в нужном месте,
посмотреть регистры и память, пройти по шагам. Для нативного кода это делает отладчик.

## Наш пример: приложение с libcheck.so

Приложение загружает `libcheck.so` и вызывает проверку. Хотим остановиться в функции проверки
и посмотреть аргументы.

## Шаг 1: подготовка устройства

Отладка нативного кода требует прав `ptrace` — то есть rooted-устройства или эмулятора с
отключённой защитой. Проверяем доступ:

```bash
$ adb shell su -c id
uid=0(root) gid=0(root)
```

Без root `ptrace` приложение не разрешит — это механизм, которым ядро запрещает одному процессу
читать память другого.

## Шаг 2: gdbserver на устройстве

`gdbserver` — маленький отладочный сервер, который запускается на устройстве и слушает порт:

```bash
$ adb push gdbserver /data/local/tmp/
$ adb shell su -c '/data/local/tmp/gdbserver :1234 --attach <PID>'
Attached; pid = 1234
Listening on port 1234
```

`--attach <PID>` подключается к уже запущенному процессу приложения. PID можно узнать через
`adb shell pidof com.example`.

## Шаг 3: проброс порта и подключение

```bash
$ adb forward tcp:1234 tcp:1234
$ gdb
(gdb) target remote :1234
Remote debugging using :1234
```

`adb forward` пробрасывает порт с устройства на хост, чтобы gdb на компьютере мог подключиться.

## Шаг 4: базовые операции

```bash
(gdb) info sharedlibrary
0x0000007fb6...  libcheck.so
(gdb) break Java_com_example_NativeChecker_check
Breakpoint 1 at 0x...
```

`break` ставит точку останова — место, где исполнение приостановится. `info sharedlibrary`
показывает, куда загружены библиотеки (адреса рандомизированы из-за ASLR — рандомизации адресного
пространства).

## Шаг 5: инспекция

Когда точка сработала:

```bash
(gdb) info registers x0 x1
x0  0x7fc1234000  0x7fc1234000
x1  0x7fc1234100  0x7fc1234100
(gdb) x/s 0x7fc1234000
0x7fc1234000: "nto-input"
```

`info registers` показывает значения регистров (x0, x1 — аргументы), `x/s` читает строку по
адресу. Так мы видим реальные данные, которых не было в статике.

## Шаг 6: lldb вместо gdb

На macOS/iOS-инструментарии чаще используют lldb. Команды аналогичны: `breakpoint set -n func`,
`register read x0`, `memory read`. Для Android удобен gdb, для iOS — lldb.

## Шаг 7: обход anti-debug

Приложения часто проверяют, не отлаживаются ли они (читают `TracerPid` в `/proc/self/status`).
Признаки: при подключении отладчика приложение падает. Обход: хукать проверку через Frida,
патчить проверку в smali/native, или использовать скрытый отладчик. Иногда проще Frida, чем
gdbserver.

## Шаг 8: точки останова и watchpoint

Кроме обычных точек останова (`break`) в gdb есть точки наблюдения (`watch`) — они срабатывают
при изменении памяти:

```bash
(gdb) watch *(int*)0x7fc1234010
Hardware watchpoint 2: *(int*)0x7fc1234010
(gdb) continue
Old value = 0
New value = 42
```

Так удобно ловить момент, когда проверка получает «правильное» значение: вы ставите watchpoint на
переменную результата и видите, где именно она меняется. На нативном коде это быстрее, чем
перебирать точки останова по всем функциям.

## Шаг 9: отладка JNI-функций по имени

Имена JNI-функций кодируют пакет и класс: `Java_com_example_NativeChecker_check`. Зная это,
можно ставить точку останова по имени, не ища адрес вручную:

```bash
(gdb) info functions Java_com_example
0x... Java_com_example_NativeChecker_check(JNIEnv*, jobject, jstring)
(gdb) break Java_com_example_NativeChecker_check
```

Если символы вырезаны (strip), функция остаётся в таблице динамических символов только если
экспортирована. Для strip-библиотек ищут по адресу из Ghidra и ставят точку как `break *0x7fc...`.

## Шаг 10: скрипты gdb и автоматизация

Повторяющиеся проверки оформляют скриптом:

```bash
(gdb) commands
> silent
> printf "x0=%p x1=%p\n", $x0, $x1
> x/s $x0
> continue
> end
```

Скрипт выполняется при каждом срабатывании точки останова и логирует аргументы, не останавливая
процесс. Так снимают поток значений за один прогон — это быстрее, чем останавливаться вручную.

## Типичные ошибки и решения

| Симптом | Причина | Решение |
|---|---|---|
| `ptrace: Operation not permitted` | нет root / SELinux | запустить `su`, снять SELinux |
| отладчик не видит .so | библиотека ещё не загружена | `break` после `dlopen` |
| приложение падает при attach | anti-debug | хукать проверку TracerPid |
| адреса «плывут» | ASLR | читать базу из `info sharedlibrary` |

## Ограничения метода

Отладка нативного кода требует прав `ptrace`, а значит — rooted-устройства или эмулятора с
отключённой защитой. На реальном «боевом» устройстве это часто невозможно, и тогда переходят на
Frida-инструментацию: она работает в адресном пространстве приложения и не требует ptrace между
процессами. Ещё одна граница — проверки целостности: если приложение сверяет хэш своей памяти,
отладчик и точки останова могут это заметить. В таких случаях отладку совмещают с патчем
проверок или используют аппаратные точки останова, которые не меняют код.

## Отладка многопоточных приложений

Нативные проверки часто выполняются в отдельном потоке. Чтобы выбрать поток в gdb, смотрят их
список и переключаются:

```bash
(gdb) info threads
  Id   Target Id         Frame
* 1    Thread 1234 "app"  ...
  2    Thread 1235 "check" ...
(gdb) thread 2
```

`*` отмечает текущий поток. Дальше точки останова можно привязать к конкретному потоку, чтобы не
останавливать главный UI-поток. Это важно: остановка главного потока подвешивает приложение и
может сработать anti-debug-таймер.

## Работа с сигналами и крашами

Когда приложение падает, gdb останавливается на сигнале (обычно `SIGSEGV`). В этот момент полезно
прочитать стек и виновную инструкцию:

```bash
(gdb) bt
#0  0x0000007fb6a1f40 in decrypt () from libcrypto.so
#1  0x0000007fb6a1200 in check () from libcheck.so
(gdb) x/i $pc
=> 0x7fb6a1f40 <decrypt+0>: ldr x0, [x1, #8]
```

`bt` показывает цепочку вызовов, `x/i $pc` — инструкцию, на которой произошёл сбой. Так находят
место, где приложение упало из-за неверных данных, и связывают его с логикой проверки.

## Проверка результата

Успешная отладка — это когда вы получили то, чего не было в статике: конкретные значения
аргументов, ветвь, которую выбрала программа, или расшифрованную строку. Чтобы результат был
воспроизводимым, фиксируйте базу библиотеки (из `info sharedlibrary`) и смещение точки останова:
при следующем запуске ASLR сдвинет адреса, но смещение останется тем же. Записывайте пару
«смещение + значение», а не абсолютный адрес.

## Чек-лист по нативной отладке

- Получить root/ptrace на устройстве.
- Запустить `gdbserver` и пробросить порт через `adb forward`.
- Подключиться, найти базу библиотеки в `info sharedlibrary`.
- Поставить точку останова по имени или адресу+смещению.
- Прочитать регистры, память и стек.
- Зафиксировать смещения, а не абсолютные адреса.

## Как отличить отладчик от инструментации

Отладчик останавливает процесс и управляет им пошагово — это самый глубокий, но и самый заметный
инструмент: anti-debug-проверки легко ловят ptrace. Инструментация через Frida не останавливает
процесс и живёт внутри него, поэтому её сложнее обнаружить, но она хуже подходит для пошагового
разбора незнакомого кода. На практике их комбинируют: Frida для обхода защит и подмены значений,
gdb — для глубокого разбора конкретной функции.

## Что даёт отладчик там, где бессилен статический анализ

Статический анализ показывает код, но не данные. Отладчик показывает и то, и другое: в какой
ветви пошло исполнение, какие значения пришли в функцию, что записалось в память. Для проверок,
построенных на рантайм-значениях (хеш устройства, время, ответ сервера), это единственный способ
увидеть «правильный» вход. Поэтому нативная отладка — не просто удобство, а метод: она превращает
непрозрачную проверку в наблюдаемый процесс, который можно воспроизвести и обойти.

## Практический вывод по нативной отладке

Нативная отладка отвечает на вопрос «что происходит в рантайме», на который статический анализ
ответить не может. Порядок: получить root и ptrace, поднять `gdbserver`, пробросить порт, найти
базу библиотеки, поставить точку останова по имени или по смещению, прочитать регистры и память.
Для защит, зависящих от рантайм-значений, это единственный способ увидеть корректный вход. Важно
работать с относительными смещениями, а не абсолютными адресами: ASLR меняет базу при каждом
запуске, и только смещение воспроизводимо. Если anti-debug мешает, комбинируйте отладчик с Frida:
инструментация снимает защиту и подменяет значения, а отладчик даёт пошаговый разбор. Так два
инструмента дополняют друг друга — один обходит препятствия, другой показывает глубину.

## Безопасность самой отладки

Помните, что отладка меняет процесс: точки останова правят память, watchpoint занимают аппаратные
регистры, а пауза может сорвать сетевой таймаут. На боевых системах это заметно и по логам, и по
поведению. Поэтому нативная отладка — инструмент для контролируемой лаборатории, а не для
скрытного анализа чужого устройства. Если требуется незаметность, выбирают инструментацию без
остановки процесса.

## Что мы теперь знаем

- Отладка native требует root и ptrace.
- gdbserver запускается на устройстве и слушает порт.
- adb forward пробрасывает порт на хост.
- Точки останова, регистры и память показывают реальные данные.
- anti-debug обходят хуком или патчем.
