## Вопрос, с которого всё начинается

В прошлом уроке мы подставляли чужой `id` и читали чужие объекты. Но что, если сервер доверяет не только идентификатору, а **всем полям**, которые присылает клиент? Мобильное приложение формирует запрос на сервер само — и ничто не мешает нам дописать в это тело лишние поля. Ошибка, при которой сервер вслепую копирует поля из запроса в объект пользователя, называется **mass assignment** (массовое присваивание). Она позволяет обычному пользователю выставить себе `role: admin` или увеличить `balance`.

Разберём на том же локальном API, что и в уроке про BOLA.

## Наш пример: профиль, который «принимает всё»

Наш бэкенд `http://127.0.0.1:18080` умеет менять профиль методом `PATCH /v1/users/me`. Клиент шлёт JSON с полями, которые пользователь реально может менять — например, email. Ответ содержит весь объект пользователя:

```
$ curl -s -X PATCH -H "Authorization: Bearer tok-A" \
       -H "Content-Type: application/json" \
       -d '{"email":"alice@example.com"}' \
       "http://127.0.0.1:18080/v1/users/me"
{"id": "1001", "email": "alice@example.com", "role": "user", "balance": 100}
```

Заметьте: в ответе есть поля `role` и `balance`, которые пользователь менять не должен. Вопрос урока: а что если их **дописать в запрос**?

## Шаг 1: подставляем лишние поля

**Поле (field)** — это пара «имя: значение» внутри JSON, например `email`. Если сервер перебирает все присланные поля и копирует их в объект, то `role` и `balance` тоже попадут в него:

```
$ curl -s -X PATCH -H "Authorization: Bearer tok-A" \
       -H "Content-Type: application/json" \
       -d '{"email":"alice@example.com","role":"admin","balance":999999}' \
       "http://127.0.0.1:18080/v1/users/me"
{"id": "1001", "email": "alice@example.com", "role": "admin", "balance": 999999}
```

Мы стали **администратором** и подняли себе баланс. Это и есть mass assignment: сервер не различал «разрешённые» и «запрещённые» поля. Проверим, что состояние сохранилось:

```
$ curl -s -H "Authorization: Bearer tok-A" \
       "http://127.0.0.1:18080/v1/users/1001/profile"
{"id": "1001", "email": "alice@example.com", "role": "admin", "balance": 999999}
```

## Шаг 2: почему это работает

Классическая причина — **автоматическая привязка (auto-binding)**. Фреймворк получает JSON и «накладывает» его на модель пользователя целиком, без списка разрешённых полей. В разных стеках это называется по-разному:

- Ruby on Rails — `params.permit!` или отсутствие strong parameters.
- Node/Express — `Object.assign(user, req.body)`.
- Django REST — сериализатор с `fields = '__all__'`.
- Java/Spring — `@ModelAttribute` без ограничений.

Мобильный контекст усиливает проблему: клиент — это APK, который можно декомпилировать, найти в коде имена полей (`isAdmin`, `role`, `credits`) и дописать их в запрос. Даже если приложение никогда их не отправляет, сервер их примет.

## Шаг 3: какие поля искать

Список кандидатов — всё, что влияет на права, деньги или доступ:

- `role`, `roles`, `is_admin`, `isAdmin`, `admin`, `is_staff`
- `balance`, `credits`, `limit`, `quota`, `discount`
- `email`, `phone`, `verified`, `email_verified`
- `user_id`, `owner_id`, `account_id` (смена владельца объекта)
- `status`, `blocked`, `active`, `plan`, `tier`

Хороший источник этих имён — сама декомпилированная APK: в моделях данных (data-классы) часто перечислены все поля объекта. Дополните их значениями из ответов API — сервер сам подскажет, что у него есть.

## Шаг 4: как находить системно

1. **Перехватите** запросы на создание/обновление профиля (`POST /register`, `PATCH /users/me`, `PUT /users/{id}`).
2. **Сравните** поля запроса и ответа: если в ответе есть поля, которых не было в запросе, — их стоит попробовать добавить.
3. **Добавляйте по одному** подозрительному полю и смотрите, меняется ли ответ и поведение (доступ к админским эндпоинтам, изменение баланса).
4. **Проверяйте вложенность**: иногда поле лежит глубже (`{"user":{"role":"admin"}}`) или в массиве.
5. **Проверяйте типы**: строка `"1"` против числа `1`, `true` против `"true"`.

## Шаг 5: массовое назначение и GraphQL

В REST проблема чаще всего в теле `POST`/`PATCH`. В **GraphQL** она выглядит иначе: мутация принимает объект-вход (`input`), и если сервер пробрасывает его целиком, лишние поля тоже попадут в модель. Схему GraphQL можно получить **интроспекцией** (запрос `__schema`) — она прямо перечислит все поля типа, включая те, что клиент не использует. Например, если в схеме есть `updateProfile(input: ProfileInput!)` и в `ProfileInput` есть `role`, — это готовый кандидат.

Ещё один вариант — **массовое назначение через вложенность**. Сервер может фильтровать верхний уровень, но не проверять вложенный объект: `{"profile":{"email":"...","role":"admin"}}`. Пробуйте оба уровня.

## Справочная таблица: поля-кандидаты

| Категория | Поля для проверки |
|-----------|-------------------|
| Права | `role`, `roles`, `is_admin`, `isAdmin`, `is_staff`, `permissions` |
| Деньги/лимиты | `balance`, `credits`, `limit`, `quota`, `discount`, `price` |
| Владение | `user_id`, `owner_id`, `account_id`, `tenant_id` |
| Статус | `verified`, `email_verified`, `active`, `blocked`, `plan`, `tier` |

Подставляйте их по одному и смотрите на эффект: доступ к админ-эндпоинту, изменение баланса, видимость чужих данных.

## Шаг 6: как от этого защищаются

Правильная защита — **белый список** (allow-list) разрешённых полей на сервере. Клиентский ввод никогда не накладывают на модель напрямую: его принимают в отдельный объект передачи данных (DTO), где перечислены только безопасные поля, а затем явно переносят в модель. В разных фреймворках это strong parameters (Rails), сериализаторы с явным `fields` (Django REST), `@JsonIgnoreProperties` и DTO (Spring), явное перечисление полей в схеме (GraphQL). Если ревьюер спрашивает «почему это не сработает у нас», ответ — «потому что мы не биндим `req.body` в модель, а читаем поля поимённо».

## Полный прогон от начала до конца

Маршрут по нашему API:

1. **Разведка** — `PATCH /v1/users/me` возвращает объект с `role` и `balance`.
2. **Гипотеза** — сервер доверяет телу запроса.
3. **Проверка** — дописываем `role: admin` и `balance: 999999`.
4. **Подтверждение** — `200 OK`, в ответе новые значения; повторный `GET` их подтверждает.
5. **Impact** — вертикальная эскалация (мы админ) и обход лимитов (баланс).
6. **PoC** — сохранить запрос «до» (только email) и «после» (с ролью) — разница доказывает уязвимость.

## Если не сработало

Если сервер отбросил лишнее поле, попробуйте: другие HTTP-методы (`PUT` вместо `PATCH`, `POST` на создание), вложенные объекты, альтернативные имена (`isAdmin` vs `is_admin` vs `admin`), поля из GraphQL-схемы (её можно запросить интроспекцией), а также заголовки вместо тела. Иногда фильтр есть только на одном эндпоинте — ищите тот, где его забыли. И помните: сам факт, что поле не отразилось в ответе, ещё не значит, что оно не записалось в базу — проверяйте эффект (доступ, баланс).

## Что мы теперь знаем

1. Mass assignment — сервер вслепую копирует поля клиента в объект пользователя.
2. Причина — автоматическая привязка без списка разрешённых полей.
3. Опасно для полей прав (`role`, `is_admin`), денег (`balance`) и владения (`owner_id`).
4. Имена полей берут из ответов API и из декомпилированной APK.
5. Проверяют, дописывая поля по одному и глядя на эффект, а не только на эхо ответа.
6. Доказательство — пара запросов «без лишнего поля / с ним».
