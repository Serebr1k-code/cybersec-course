## Вопрос, с которого всё начинается

Вы получили root на Android-устройстве, но команда `mount` не срабатывает: «Permission
denied». Пользователь root, а доступа нет. Так работает **SELinux** — мандатный контроль
доступа, который ограничивает даже root. Разберём, как это устроено и как обходят.

## Наш пример: попытка записи в system

На устройстве с root пытаемся смонтировать `/system` на запись:

```bash
$ adb shell
$ su
# mount -o rw,remount /system
mount: '/system' not in /proc/mounts
# echo test > /system/x
/system/x: Permission denied
```

UID у нас 0 (root), но ядро всё равно запрещает запись. Причина — не UNIX-права, а политика
SELinux: домену процесса не разрешено писать в этот тип файла.

## Шаг 1: что такое SELinux

SELinux (Security-Enhanced Linux) — механизм **мандатного** контроля доступа (MAC). В отличие
от классических UNIX-прав, которые проверяют «кто ты» (UID/GID), SELinux проверяет «в каком
контексте ты и к чему обращаешься». Каждому процессу и файлу присвоен **контекст** вида:

```
u:r:untrusted_app:s0:c512,c768
```

Разбор: `u` — пользователь, `r` — роль, `untrusted_app` — домен (тип процесса), `s0` — уровень
MLS. Файл имеет свой контекст, например `u:object_r:system_file:s0`. Политика разрешает
пересечение домена и типа — или запрещает.

## Шаг 2: режимы работы

SELinux работает в одном из режимов:

- **enforcing** — запрещает всё, что не разрешено, и логирует.
- **permissive** — разрешает, но логирует нарушения.
- **disabled** — выключен.

Проверить текущий режим:

```bash
$ adb shell getenforce
Enforcing
```

На современных устройствах Android режим по умолчанию — enforcing. Именно поэтому root сам по
себе не даёт полной власти: нужно ещё подобрать домен, которому политика разрешает нужное
действие.

## Шаг 3: контексты и как их смотреть

Посмотреть контекст процесса и файла:

```bash
$ adb shell ps -Z | grep untrusted
u:r:untrusted_app:s0:c512,c768 u0_a123 ... com.example.app
$ adb shell ls -Z /system/bin/sh
u:object_r:shell_exec:s0 /system/bin/sh
```

Искать типичные домены, полезные для эксплуатации: `su`, `init`, `shell`, `kernel`. Каждый
домен имеет свой набор разрешений. Например, домен `su` шире, чем `untrusted_app`.

## Шаг 4: почему обход SELinux обязателен

Получив уязвимость в ядре или root-доступ, исследователь почти всегда упирается в SELinux.
Например, чтобы изменить системный файл или загрузить модуль, нужен домен с соответствующими
разрешениями. Отсюда две классические техники:

1. **Переход в другой домен** (`domain transition`) через эксплуатацию процесса, который уже
   имеет широкий домен (init, system_server).
2. **Загрузка модуля/политики** при наличии доступа к ядру.

Именно поэтому цепочки эксплуатации Android почти всегда включают шаг «обход SELinux».

## Шаг 5: типичные ошибки конфигурации

Иногда производитель оставляет устройство в **permissive** или добавляет слишком широкие
правила. Проверить это можно так:

```bash
$ adb shell getenforce
Permissive
```

Permissive на пользовательском устройстве — серьёзная находка: любое нарушение политики не
блокируется. Также ищут нестандартные домены в `/sys/fs/selinux/` и правила, разрешающие
`untrusted_app` больше обычного.

## Шаг 6: как аудировать

При пентесте устройства:

1. Проверить `getenforce` — не permissive ли.
2. Посмотреть, какие домены доступны приложению.
3. Проверить, есть ли кастомные политики производителя.
4. Оценить, можно ли из уязвимого процесса перейти в привилегированный домен.

## Шаг 7: что писать в отчёте

Опишите: режим SELinux, найденные широкие правила, возможность обхода и последствия. Для
эксплуатации ядра укажите, какой домен удалось получить и что это дало. MITRE: Exploitation
for Privilege Escalation, с пометкой о платформенных ограничениях.

## Шаг 8: рекомендации

- Держать SELinux в enforcing на всех пользовательских устройствах.
- Не добавлять кастомные правила, расширяющие `untrusted_app`.
- При разработке — тестировать в enforcing, чтобы не зависеть от permissive.

## Что мы теперь знаем

- SELinux ограничивает даже root через мандатный контроль доступа.
- Домены и типы задают, что кому разрешено.
- Enforcing/permissive — режимы; permissive на устройстве пользователя — находка.
- Обход SELinux — обязательный шаг современной эксплуатации Android.

## Шаг 9: политика изнутри — allow-правила

Политика SELinux — это набор правил вида:

```
allow <домен> <тип>:<класс> <разрешения>;
```

Например:

```
allow untrusted_app app_data_file:file { read write open };
```

Читается так: домену `untrusted_app` разрешено читать/писать/открывать файлы типа
`app_data_file`. Работает принцип **default deny**: чего нет в правилах — запрещено. Кроме
`allow` есть `neverallow` — инварианты, которые компилятор политики не даст нарушить даже
производителю (именно они защищают критичные границы, и именно их чаще всего пытаются обойти
эксплойтом).

## Шаг 10: инструменты анализа политики

- `seinfo` / `sesearch` (пакет `setools`) — поиск типов, доменов и правил по политике.
- `audit2allow` — превращает запись об отказе (`avc: denied`) в готовое allow-правило.
- `magiskpolicy` / `supolicy` — правка политики прямо на устройстве с root.

Разбор реального отказа:

```bash
$ adb shell dmesg | grep avc
avc: denied { write } for pid=1234 comm="sh" name="x" dev="dm-0" ino=42   scontext=u:r:shell:s0 tcontext=u:object_r:system_file:s0 tclass=file permissive=0
```

Читаем: процесс в домене `shell` (scontext) пытался писать (write) в файл типа `system_file`
(tcontext). `permissive=0` значит отказ реальный, а не просто лог. Прогнав строку через
`audit2allow`, получаем ровно то правило, которое нужно было бы добавить:

```
allow shell system_file:file write;
```

## Шаг 11: domain transition по шагам

**Domain transition** — переход процесса в другой (обычно более привилегированный) домен. Он
требует выполнения трёх условий в политике: у исходного домена есть `transition` на новый тип,
у исполняемого файла проставлен `entrypoint`, и есть `allow <старый> <новый>:process transition`.
Классический пример — `init` запускает `su` и тот получает домен `su`, у которого больше прав,
чем у `shell`. Атакующий, получивший управление над процессом с широким доменом, получает и
его права — обходить SELinux «с нуля» не нужно.

## Шаг 12: практика на устройстве с root

С Magisk можно ослабить политику вживую (в исследовательской среде):

```bash
# magiskpolicy --live 'allow untrusted_app system_file:file write'
# getenforce
Enforcing
# echo test > /system/x && echo OK
OK
```

Здесь мы не выключили SELinux, а добавили точечное правило — так обход выглядит «чище» и
меньше заметен, чем перевод устройства в permissive.

## Крайние случаи и подводные камни

- **Per-domain permissive**: отдельный домен может быть permissive, даже когда вся система в
  enforcing. Такой домен — приоритетная цель (`seinfo` покажет).
- Категории **MCS** (`s0:c512,c768`) изолируют приложения друг от друга — два приложения с
  разными категориями не прочитают файлы друг друга, даже если тип совпадает.
- `isolated_app` — ещё более узкий домен, чем `untrusted_app` (для isolatedProcess).
- На кастомных сборках SELinux иногда **выключен** — тогда проверка `getenforce` не работает,
  и ограничения нет вовсе.
- Полагаться только на `getenforce` нельзя: enforcing + слишком широкие кастомные правила даёт
  тот же эффект, что permissive.

## Что дальше / решение

Итог: SELinux — это default-deny MAC поверх UNIX-прав; root без подходящего домена бесполезен.
В аудите проверяйте режим, домены и кастомные правила производителя. Следующий урок — про
аппаратное доверие: как ключ «доказывает», что он рождён в TEE, и как эта проверка ломается.

## Шаг 13: MLS/MCS и категории приложений

Android использует **MCS** (Multi-Category Security) поверх MLS. Каждому приложению выдаётся
уникальная пара категорий (`s0:c512,c768`), и политика запрещает домену одного приложения
читать файлы другого, даже если тип совпадает. Поэтому «одного root» недостаточно: чтобы
прочитать данные чужого приложения, нужно либо подобрать домен, либо снять категории.

```bash
$ adb shell ps -Z | grep com.bank
u:r:untrusted_app:s0:c100,c256 u0_a201 ... com.bank.app
```

Категории `c100,c256` — это «метка» приложения. Файлы в его песочнице имеют тот же набор
категорий, и другое приложение (`c512,c768`) их не увидит.

## Шаг 14: типичные ошибки аудита SELinux

- Считать, что `getenforce = Enforcing` гарантирует защиту: кастомные `allow`-правила могут
  делать enforcing бессмысленным.
- Забывать про per-domain permissive: часть доменов может быть ослаблена.
- Игнорировать MLS-категории: «root, но нет доступа» — это почти всегда MCS.
- Не проверять `neverallow`-инварианты, которые производитель мог ослабить.
- Оценивать только политику AOSP, не глядя на вендорские дополнения в `/sys/fs/selinux/`.

## Шаг 15: практическая модель угроз «root + SELinux»

На устройствах с Magisk root-процесс получает широкий домен, потому что сам Magisk правит
политику на лету. Но это лишь удобство исследователя: в «дикой» эксплуатации эксплойт даёт
выполнение кода внутри **конкретного** домена (например, домена медиа-сервиса), и дальше
атакующий ограничен именно его разрешениями. Отсюда типичная структура современной цепочки
эксплуатации Android: найти уязвимость в процессе с относительно широким доменом, выполнить
код в нём, затем либо перейти в ещё более привилегированный домен через domain transition, либо
загрузить модуль ядра, либо ослабить политику. Ключевой вывод для аудита: «получен root» само
по себе ничего не значит, пока не сказано, **в каком домене** и что этому домену разрешено.
Именно поэтому в отчётах по Android-эксплуатации всегда указывают scontext — иначе оценка
ущерба будет неверной.
