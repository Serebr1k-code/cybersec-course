## Вопрос, с которого всё начинается

Многие проверки Android и приложений читают **системные свойства**: версию, режим загрузки,
флаги отладки. Если атакующий может менять свойства, он может влиять на эти проверки. А
некоторые свойства сохраняются между перезагрузками — идеальное место для персистентности.
Разберём систему свойств изнутри.

## Наш пример: свойство, переживающее перезагрузку

Мы хотим, чтобы наш флаг выжил после перезагрузки и влиял на поведение системы. Разберём путь
через `setprop` и `persist.*`.

## Шаг 1: как читать и писать свойства

Читают свойства через `getprop`, пишут через `setprop`:

```bash
$ getprop ro.build.version.sdk
34
$ setprop my.debug.flag 1
$ getprop my.debug.flag
1
```

Свойства — это единое дерево ключ-значение, общее для всей системы. Приложения читают их через
`SystemProperties` (скрытый API) или `Build`.

## Шаг 2: префиксы и их роль

- `ro.*` — **read-only**, устанавливаются один раз при загрузке (`ro.build.*`, `ro.debuggable`);
- `persist.*` — **сохраняются** между перезагрузками в отдельном разделе;
- `sys.*`, `debug.*` — изменяемые во время работы;
- `net.*` — сетевые настройки.

Именно `persist.*` интересен для персистентности: значение остаётся после перезагрузки.

## Шаг 3: property_service и доступ

Запись свойств контролирует системная служба **property_service**. Она проверяет, кому какие
свойства разрешено менять, по SELinux-политике `property_contexts`. Обычное приложение не может
писать `ro.*` (они read-only) и большинство `persist.*` без соответствующих прав.

## Шаг 4: property-триггеры

`init` умеет реагировать на изменение свойств:

```text
on property:sys.boot_completed=1
    start mysvc
```

Значит, изменив свойство, можно **запустить службу** или изменить ход загрузки. Это связывает
свойства с персистентностью из прошлого урока.

## Шаг 5: злоупотребление

Типичные приёмы:

- выставить `persist.*` флаг, который читает проверка, и обойти её;
- подменить `ro.debuggable` (на раннем этапе) для включения отладки;
- создать `persist.*`-свойство, которое триггерит запуск вредоносной службы;
- замаскировать своё свойство под вендорское (`vendor.*`, `ro.vendor.*`).

При форензике подозрительны нестандартные `persist.*`-свойства и те, что не встречаются в
эталоне прошивки.

## Что мы теперь знаем

- Свойства — общее дерево ключ-значение (`getprop`/`setprop`).
- `ro.*` только для чтения, `persist.*` переживают перезагрузку.
- Запись контролирует property_service по SELinux-политике.
- `on property:` триггеры позволяют запускать код при смене свойства.

## Если не сработало

Если `setprop` возвращает `failed to set property`, у вас нет прав по SELinux — нужен root и
соответствующий контекст. `ro.*` изменить нельзя после установки. На новых версиях часть
`persist.*` защищена от записи даже под root.

## Частые вопросы

**Свойства — это файлы?** Логически дерево; физически — раздел `persist` и память.

**Как обнаружить подмену?** Сравнением списка свойств с эталоном.

**Опасен ли `persist.*` для приложений?** Приложения обычно не могут его писать.

## Где физически живут свойства

Логически свойства — единое дерево ключ-значение, но физически они разложены по нескольким
местам.

- `ro.*` устанавливаются один раз при загрузке и хранятся в памяти; изменить их после этого
  нельзя.
- `persist.*` сохраняются на разделе `persist` (или в `/data/property/`) и переживают
  перезагрузку.
- `sys.*`, `debug.*`, `net.*` живут в памяти и меняются во время работы.
- `vendor.*` относятся к вендорской части платформы.

Понимание «где живёт» объясняет поведение: почему `ro.*` не меняется и почему `persist.*`
восстанавливается после ребута. Это же определяет, какие свойства годятся для персистентности.

## Полный набор префиксов и правил

Префикс — не просто соглашение, а правило доступа. Разберём основные.

| Префикс | Изменяемость | Сохраняется | Назначение |
|---|---|---|---|
| ro.* | нет | нет (загрузка) | версия, флаги сборки |
| persist.* | да (с правами) | да | настройки между ребутами |
| sys.* | да | нет | рантайм-состояние |
| debug.* | да | нет | отладочные флаги |
| net.* | да | нет | сетевые настройки |
| ctl.* | спец. | — | управление службами |
| vendor.* | да (с правами) | зависит | вендорская часть |

Отдельно стоит `ctl.*`: запись в `ctl.start` или `ctl.stop` — это команда `init` запустить или
остановить службу. Так свойства связаны с управлением процессами.

## property_service и SELinux-политика

Запись свойств контролирует служба `property_service` внутри `init`. Она не даёт писать всем подряд:
для каждого префикса определён список контекстов, которым разрешена запись. Эти правила описаны в
`property_contexts` (в `/system/etc/selinux/` и `/vendor/etc/selinux/`).

```bash
$ grep -E '^persist\.' /system/etc/selinux/plat_property_contexts | head
persist.sys.timezone   u:object_r:system_prop:s0
persist.vendor.radio   u:object_r:vendor_radio_prop:s0
```

Строка слева — шаблон свойства, справа — SELinux-контекст. Приложение не может писать `persist.*`,
потому что его домен не входит в разрешённые. Именно поэтому `setprop` из обычного приложения
часто возвращает `failed to set property`.

## Чтение свойств из приложения

Из кода приложения свойства читают несколькими способами.

- Через `android.os.Build` — он даёт самые частые поля (`Build.VERSION.SDK_INT`,
  `Build.TAGS`, `Build.MANUFACTURER`).
- Через `SystemProperties.get("ro.build.version.sdk")` — скрытый API, доступен через рефлексию.
- Из нативного кода — `__system_property_get`.

Для аналитика это важно: проверки, основанные на свойствах, ломаются, если свойство подменить.
Например, приложение считает устройство «правильным» по `Build.TAGS`, а атакующий подменяет
значение — проверка проходит.

## Таблица: типовые приёмы злоупотребления

| Приём | Как работает | Что ломает |
|---|---|---|
| подмена флага проверки | `persist.*`, который читает проверка | анти-тампер, лицензия |
| запуск службы | `on property:` + `ctl.start` | персистентность |
| подмена `ro.debuggable` | ранняя установка значения | включает отладку |
| маскировка под вендор | `vendor.*` имя | обнаружение |

## Если не сработало

Если `setprop` возвращает `failed to set property`, — нет прав по SELinux. Нужен root и
соответствующий контекст, либо запись напрямую в память в обход `property_service` (это умеет,
например, `resetprop` из Magisk).

Если свойство не сохраняется после перезагрузки, — вы пишете не `persist.*`, а `sys.*` или
`debug.*`, которые живут только в памяти.

Если `ro.*` не меняется, — это ожидаемо: `ro` означает read-only после загрузки. Менять его можно
только на очень раннем этапе, до фиксации значения.

## Ограничения

Свойства — мощный, но ограниченный механизм. Обычные приложения почти не могут писать `persist.*`
и не могут писать `ro.*` вовсе. Поэтому злоупотребление свойствами — сценарий с root или
модифицированной прошивкой.

При форензике подозрительны нестандартные `persist.*`-свойства и любые значения, которых нет в
эталонной прошивке. Сравнение дампа `getprop` с эталоном — простой и эффективный способ найти
закладку.

Наконец, свойства не являются секретным хранилищем: они видны всем процессам. Хранить в них
пароли или ключи — грубая ошибка, которую, к сожалению, иногда встречают в реальных приложениях.

## Мини-практика: найти подменённое свойство

При форензике устройства часто ищут закладки в свойствах. Разберём порядок действий.

Шаг 1. Собираем дамп свойств:

```bash
$ adb shell getprop > current.txt
```

Шаг 2. Сравниваем с эталоном той же прошивки:

```bash
$ diff <(sort reference.txt) <(sort current.txt) | head
> [persist.sys.hidden_flag]: [1]
> [persist.vendor.extra]: [on]
```

Всё, чего нет в эталоне, — потенциальная закладка. `persist.*` особенно подозрительны, потому что
переживают перезагрузку.

Шаг 3. Проверяем, кто читает это свойство. Ищем по имени в `.rc`-файлах и в коде приложений:

```bash
$ grep -rn 'persist.sys.hidden_flag' /system/etc/init/ /data/adb/
```

Если на свойство ссылается `on property:`-триггер — оно может запускать службу. Это связывает
подмену свойства с персистентностью.

## Частые ошибки

Ошибка первая — искать только в `ro.*`. Они не меняются после загрузки, поэтому закладку туда не
положить без правки образа. Основной интерес — `persist.*` и `sys.*`.

Ошибка вторая — не сравнивать с эталоном. Без эталона вы не отличите вендорское свойство от
добавленного. Скачайте официальную прошивку и снимите её `getprop`.

Ошибка третья — считать, что `setprop` всегда сработает. Без прав по SELinux запись не пройдёт;
закладки часто пишут свойства в обход `property_service` (например, `resetprop`).

## Что запомнить

Свойства — общий ресурс, видимый всем процессам, и при этом сохраняемый (для `persist.*`). Это
делает их удобным местом для флагов-переключателей и для запуска служб через триггеры. При аудите
свойств правило одно: сравнивай с эталоном и проверяй, кто их читает.

## Шпаргалка: свойства и команды

| Задача | Команда |
|---|---|
| прочитать свойство | `getprop ro.build.version.sdk` |
| список всех свойств | `getprop` |
| записать свойство | `setprop my.flag 1` |
| статус службы | `getprop init.svc.<name>` |
| сохранить дамп | `getprop > current.txt` |
| сравнить с эталоном | `diff <(sort ref) <(sort cur)` |

Эта таблица покрывает и аудит, и анализ. Помните главное правило: `ro.*` только читается,
`persist.*` переживает перезагрузку, а запись контролирует `property_service` по SELinux.

## Почему это стоит запомнить

Свойства читают и приложения, и сама система. Поэтому подмена свойства — универсальный рычаг:
она влияет и на проверки приложений, и на порядок загрузки. Кто понимает модель `ro.*`/`persist.*`
и роль `property_service`, тот и находит закладки при форензике, и обходит клиентские проверки при
анализе.
