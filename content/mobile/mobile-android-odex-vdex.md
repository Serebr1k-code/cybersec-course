## Вопрос, с которого всё начинается

Ты открыл APK и видишь внутри `classes.dex`. Установил приложение на телефон, заглянул
в его каталог в `/data/app` — а там совсем другие файлы: `.odex`, `.vdex`, `.art`.
**Что это, зачем они нужны и где на самом деле лежит код?**

## Наш пример: приложение после установки

Возьмём `com.example.app`, установленный на Android 13. Посмотрим его каталог:

```bash
$ adb shell ls /data/app/~~x/com.example.app-y/
base.apk  lib  oat  split_config.arm64_v8a.apk
$ adb shell ls /data/app/~~x/com.example.app-y/oat/arm64/
base.art  base.odex  base.vdex
```

Три файла рядом с `base.apk`. Разберём каждый.

## Шаг 1: зачем вообще компилировать

Android не исполняет dex-байткод напрямую «как есть» на современных версиях. При
установке (или при работе) система компилирует байткод в **нативный код** процессора —
это быстрее, чем интерпретировать. Делает это утилита `dex2oat`.

У компиляции есть режимы: **AOT** (ahead-of-time, заранее, при установке) и **JIT**
(just-in-time, на лету, во время работы). Обычно система комбинирует: сначала JIT,
потом по «горячим» методам — AOT в фоне. Результат кладётся в каталог `oat`.

## Шаг 2: что такое OAT и ODEX

**OAT** — общий контейнер скомпилированного кода. Внутри него — нативные инструкции и
метаданные. `.odex` (optimized dex) — историческое имя для файла с оптимизированным
dex; в формате OAT это часть того же пайплайна.

Ключевое: `.odex` **не заменяет** dex. Он содержит нативный код для уже проверенных
классов, но исходный байткод остаётся нужен для всего, что не скомпилировано.

## Шаг 3: VDEX — где лежит байткод

**VDEX** (verified dex) — файл, который хранит *верифицированный* dex-байткод. Когда
приложение компилируется, dex из APK извлекается, проверяется и складывается в `.vdex`.
Именно поэтому `.vdex` — самый ценный файл для реверса: внутри лежит тот самый код,
только в отдельном файле.

```bash
$ file base.vdex
base.vdex: Android dex file, version 039
```

`file` прямо говорит: это dex. Значит, из него можно восстановить `classes.dex` и
открыть в jadx.

## Шаг 4: что такое .art и профили

`.art` — файл, связанный с **ART** (Android Runtime). Он хранит состояние рантайма и
профили: какие методы вызываются часто. Профили (`primary.prof`) подсказывают системе,
что компилировать в первую очередь. Для реверса `.art` обычно малоинтересен, но он
показывает, что приложение уже запускалось и прогревалось.

## Шаг 5: почему это важно при анализе

Три практических следствия:

1. Если в APK dex обфусцирован, а `.vdex` получен из **другой** версии приложения —
   они не совпадут. Всегда проверяй соответствие версий.
2. Некоторые сборки поставляют код **только** в скомпилированном виде (например,
   предустановленные системные приложения). Тогда `.vdex` — единственный источник.
3. Наличие `.odex`/`.vdex` само по себе — индикатор, что приложение устанавливалось и
   запускалось; полезно в форензике.

## Шаг 6: профили, PGO и ручная компиляция

Мы уже упомянули, что профили подсказывают системе, что компилировать. Разберём это
подробнее, потому что от профилей зависит, что именно окажется в `.odex`, а что
останется в байткоде.

**Профиль** — файл вида `primary.prof`, куда ART пишет статистику: какие методы
вызываются часто. По этой статистике система решает, какие методы перевести в
нативный код (**profile-guided optimization**, PGO). Чем больше приложение
использовали, тем больше методов скомпилировано.

Посмотреть, что попало в oat-каталог, можно так:

```bash
$ adb shell ls -la /data/app/~~x/com.example.app-y/oat/arm64/
-rw-r--r-- 1 u0_a123 u0_a123  51234 base.art
-rw-r--r-- 1 u0_a123 u0_a123 402123 base.odex
-rw-r--r-- 1 u0_a123 u0_a123 300451 base.vdex
```

Размер `base.vdex` при этом **не уменьшается** при компиляции: байткод остаётся в
vdex, а `.odex` лишь добавляет нативный код поверх. Это важный практический вывод:
исходный dex никуда не пропадает, пока приложение установлено.

С root можно компилировать вручную и наблюдать эффект:

```bash
$ adb shell cmd package compile -m speed -f com.example.app
Success
```

Флаг `speed` компилирует максимум методов, `verify` — только проверяет. Для реверса
полезно знать: после `speed` в `.odex` окажется больше нативного кода, но `.vdex`
останется источником байткода.

## Если не сработало

* Каталог `oat` пуст — приложение ещё ни разу не запускалось; запусти его, чтобы
  появились артефакты.
* `.vdex` отсутствует, есть только `.odex` — переходи к следующему уроку: оттуда код
  достают иначе.
* Для системных приложений каталог может быть доступен только на чтение и содержать
  заранее собранные артефакты; их нельзя перекомпилировать без размонтирования
  системного раздела.

## Что проверить на реальном устройстве

Когда в APK нет нужного кода, первым делом загляни в каталог `oat`. Полный путь
зависит от версии и способа установки, но структура одна: рядом с `base.apk` лежит
`oat/<архитектура>/`. Там ищи `.vdex` — именно он содержит байткод.

```bash
$ adb shell find /data/app -name "*.vdex" 2>/dev/null | head
```

Обрати внимание на несколько архитектур: на 64-битном устройстве может быть и
`arm64`, и `arm` — анализируй ту, что соответствует работающему процессу. Иногда
интересующий код есть только в одной из них.

Проверь также, не является ли приложение системным. Для системных приложений
артефакты лежат в `/system/.../oat/` и доступны только для чтения; извлечь их можно
через `adb pull` на rooted-устройстве или из образа прошивки.

И держи в голове версии. Сверь `versionCode` манифеста с тем, что на устройстве:
анализ `.vdex` от другой версии приведёт к путанице в именах классов и ложным выводам.

## А если приложение обновлялось

После обновления система пересобирает артефакты, но старые файлы могут какое-то время
оставаться на диске. Это значит, что в каталоге `oat` иногда лежат артефакты **двух**
версий приложения. Если взять `.vdex` от старой версии и APK от новой, классы не
совпадут, и анализ уведёт в сторону. Поэтому всегда сверяй имена каталогов установки
(`~~x`, `~~y` и подобные префиксы) и даты файлов. Самый свежий `.vdex` по времени
изменения, как правило, соответствует текущей версии. Если сомневаешься — удали
приложение, установи заново и работай с чистым набором артефактов.

## Главное на практике

Держи в голове одну мысль: **dex не исчезает при компиляции**. Он остаётся в `.vdex`,
а `.odex` лишь добавляет нативный код. Поэтому «в APK нет кода» почти никогда не
означает «кода нет вообще» — он есть рядом, в каталоге `oat`. Умение посмотреть туда
отличает анализ, который застрял, от анализа, который продолжается.

## Что мы теперь знаем

- При установке Android компилирует dex в нативный код через `dex2oat`.
- В каталоге `oat` лежат `.odex` (оптимизированный код), `.vdex` (байткод) и `.art`.
- `.vdex` содержит верифицированный dex — из него восстанавливают `classes.dex`.
- `.odex` не заменяет dex, а дополняет его.
- `.art`/профили показывают, что приложение уже запускалось.

А пока запомни: **`.vdex` — это dex; если в APK пусто, смотри в oat**.
