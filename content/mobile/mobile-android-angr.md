## Вопрос, с которого всё начинается

В нативной библиотеке спрятана проверка пароля: код читает строку, делает с ней десятки
операций и сравнивает результат с константой. Читать это в Ghidra долго и легко ошибиться.
Хочется, чтобы компьютер сам подобрал вход, который проходит проверку. Именно это делает
символьное исполнение.

## Наш пример: libcheck.so с проверкой

Гипотеза: функция по адресу `0x2000` возвращает 1, если пароль верный. Наша задача — найти
пароль, не разбирая алгоритм вручную.

<!-- lab -->

## Шаг 1: что такое символьное исполнение

Обычное исполнение подставляет конкретные числа. **Символьное исполнение** вместо числа
подставляет «символ» — неизвестное значение, а над ним строит формулу (уравнение). В конце
солвер (решатель формул, например z3) находит такие значения символов, при которых условие
истинно. Проще: мы не считаем вручную, а описываем «что должно быть» и просим решить.

## Шаг 2: загрузка бинарника

```python
import angr
proj = angr.Project('libcheck.so', auto_load_libs=False)
```

`angr` — библиотека символьного исполнения. `auto_load_libs=False` говорит не подгружать
системные библиотеки: для Android `.so` их всё равно нет, а нам нужна только наша функция.

## Шаг 3: точки find и avoid

Ключевая идея angr — двигаться к «хорошему» адресу (`find`) и избегать «плохого» (`avoid`).
Смотрим функцию: где возвращается успех, а где неудача. По декомпиляции из Ghidra находим,
что успех — ветка с `return 1`. Тогда:

```python
state = proj.factory.entry_state()
simgr = proj.factory.simulation_manager(state)
simgr.explore(find=0x2100, avoid=0x2200)
```

`find` — адрес, куда должны прийти, `avoid` — куда не должны. Это и есть вся «магия».

## Шаг 4: запуск и результат

```bash
$ python3 solve.py
[+] found solution
[+] password = nto-4ngr
```

Когда `explore` доходит до `find`, в найденном состоянии лежит конкретное значение входных
байтов — это и есть искомый пароль. Мы получили его, не разбирая алгоритм.

## Шаг 5: как передать вход

Реальные проверки читают вход не как аргумент, а из памяти/строки. Тогда вход моделируют:
создают символический буфер, кладут его по нужному адресу и помечают как переменную. Пример:

```python
import claripy
arg = claripy.BVS('arg', 8 * 16)          # 16 неизвестных байт
state = proj.factory.call_state(0x2000, arg)
```

`claripy` — библиотека символьных значений, на которой работает angr.

## Шаг 6: когда angr не работает

Символьное исполнение взрывается по сложности: циклы и криптография порождают огромное число
путей, и angr «зависает». Приёмы: ограничить область (передать вход напрямую в функцию проверки,
а не с самого старта), добавить `avoid` для тупиков, использовать хуки для известных функций
(например, заменить хеш-функцию символьным ограничением). Иногда проще вернуться к Ghidra.

## Шаг 7: практический пайплайн

Типовой порядок: Ghidra — найти функцию проверки и её адрес; angr — запустить `explore` с
`find`/`avoid`; полученную строку проверить динамически (ввести в приложение). Так статика и
символика дополняют друг друга.

## Шаг 8: хуки и символьные ограничения

Реальные проверки часто используют хеш-функцию или CRC. Символически исполнять саму хеш-функцию
бессмысленно — angr утонет. Вместо этого функцию заменяют хуком, который добавляет ограничение
на результат:

```python
def hook_md5(state):
    inp = state.memory.load(state.regs.x0, 16)
    state.regs.x0 = 0xdeadbeef          # фиктивный «хеш»
    state.solver.add(inp == b'nto-4ngr')  # сразу задаём ожидаемое
proj.hook(0x1500, hook_md5, length=4)
```

Так сложная функция сворачивается в одно ограничение, и решатель находит вход. Это ключевой
приём: не эмулировать криптографию, а описывать её результат.

## Шаг 9: angr против Unicorn

Это разные инструменты для разных задач. Unicorn **исполняет** функцию с конкретным входом и
даёт конкретный выход — быстро, но без поиска. angr **ищет** вход, при котором выполняется
условие, — медленно, но автоматически. На практике их комбинируют: angr находит кандидата, а
Unicorn (или приложение) проверяет его на реальном коде. Если проверка не выражается формулой
(например, зависит от времени), angr не поможет, и остаётся только эмуляция или динамика.

## Пример: проверка со сравнением хеша

Пусть функция берёт строку, считает MD5 и сравнивает с константой. Порядок работы: в Ghidra
находим адрес вызова MD5 и адрес сравнения; в angr хукаем MD5, добавляя ограничение; запускаем
`explore` до адреса успеха. Решатель вернёт строку, чей MD5 совпадает с константой. Это и есть
пароль. Так обходится даже проверка, которую нереально прочитать глазами.

## Таблица типичных проблем angr

| Проблема | Причина | Решение |
|---|---|---|
| зависание | взрыв путей | `avoid`, ограничить вход |
| пусто в found | неверный адрес | сверить адрес из Ghidra |
| нет конкретных байтов | символический вход | вызвать `eval` на буфере |
| ошибка загрузки .so | зависимости | `auto_load_libs=False` |
| долгий поиск | циклы | хуки вместо эмуляции |

## Практический вывод

angr — это автоматический подбор входа для проверок, которые можно выразить формулой. Порядок:
найти функцию и адреса успеха/неудачи в Ghidra, смоделировать вход символическим буфером,
запустить `explore`, при необходимости свернуть сложные функции хуками. Когда проверка упирается
в окружение или криптографию, символьное исполнение уступает место эмуляции и динамике. Умение
вовремя переключиться между этими подходами и есть суть мобильного реверса.

## Шаг 10: ограничение пространства поиска

Самый частый способ ускорить angr — сузить задачу. Не запускать исполнение с самого старта
библиотеки, а вызывать функцию проверки напрямую:

```python
state = proj.factory.call_state(0x2000, arg_buf)
simgr = proj.factory.simulation_manager(state)
simgr.explore(find=lambda s: b'OK' in s.posix.dumps(1), num_find=1)
```

`call_state` создаёт состояние «как будто функцию только что вызвали» — это убирает лишние пути
инициализации. Второй приём — задавать `find` не адресом, а условием (например, появлением
строки в выводе). Третий — использовать `avoid` для всех тупиков, которые вы уже знаете.

## Пример: проверка с циклом

Цикл — главный источник «взрыва путей». Если проверка идёт посимвольно, angr может генерировать
ветвь на каждом символе. Приёмы: заранее задать длину входа (уменьшить неизвестное); добавить
ограничения на диапазон символов (`claripy.And(c >= 0x20, c < 0x7f)`); использовать
`loop_unrolling` или хуки на функции, которые внутри цикла. Иногда проще разбить проверку на
части и решать их по отдельности.

## Когда переходить на динамику

angr не работает, если проверка зависит от окружения: времени, идентификатора устройства, ответа
сервера. Тогда символическое исполнение бессильно — значение просто неизвестно статически. В
таких случаях переходят к динамике: перехватывают значение через Frida или эмулируют функцию в
Unicorn с реальными входными данными, снятыми с устройства. Правило: символика — для «чистых»
формул, динамика — для всего, что связано с реальным миром.

## Итоговая мысль

angr — мощный, но требовательный инструмент. Он блестяще решает проверки, выраженные формулой, и
проваливается там, где нужен контекст. Успех зависит от умения сузить задачу: вызвать функцию
напрямую, ограничить вход, свернуть криптографию хуком. Комбинируя angr со статикой (Ghidra) и
динамикой (Frida, Unicorn), вы закрываете почти весь спектр нативных проверок.

## Частые ошибки новичков

Первая — запускать angr с самого начала библиотеки: путей слишком много, поиск не завершается.
Начинать надо с `call_state` на функции проверки. Вторая — забыть `auto_load_libs=False` и
утонуть в попытках загрузить Android-библиотеки, которых нет. Третья — не задать `avoid` и
получить «решение», которое на самом деле прошло через ветвь ошибки. Четвёртая — пытаться
символически исполнить криптографию вместо того, чтобы свернуть её хуком. Пятая — не проверять
найденный вход на реальном коде: символьное решение может быть неверным из-за неучтённого
ограничения. Все эти ошибки лечатся сужением задачи и проверкой результата.

## Как проверить найденный вход

Найденную строку обязательно проверяют вне angr: подставляют в реальную функцию (через
Unicorn), вводят в приложение или сверяют с логикой из Ghidra. Только совпадение результата
подтверждает, что символьная модель верна. Если проверка не сходится — значит, в модели
упущено ограничение (например, на диапазон символов или длину). Такой контроль исключает
ложные «решения» и делает результат воспроизводимым.

## Итог по angr

Символьное исполнение — это автоматический подбор входа для формульных проверок. Оно не
универсально: там, где нужен реальный контекст, оно уступает динамике. Но для «чистых» проверок
(сравнение, хеш, XOR) angr даёт результат за минуты, которые вручную ушли бы на часы чтения
ассемблера. Умение сузить задачу и вовремя переключиться на другой инструмент — вот что делает
его по-настоящему полезным.

## Как сочетать angr со статикой и динамикой

Успешный разбор нативной проверки почти всегда идёт в три шага. Статика (Ghidra) даёт карту:
где функция проверки, где ветви успеха и неудачи, какие функции она вызывает. Символика (angr)
находит вход, при котором достигается успех. Динамика (Frida или Unicorn) подтверждает результат
на реальном коде. Пропуск любого шага ослабляет вывод: без статики непонятны адреса, без
символики нет автоматического решения, без динамики результат не проверен. Именно комбинация
инструментов, а не один «лучший», даёт надёжный ответ в мобильном реверсе.

## Что мы теперь знаем

- Символьное исполнение подставляет неизвестные и решает формулы.
- angr ищет путь до `find`, избегая `avoid`.
- Вход моделируется символическим буфером.
- Сложные проверки вызывают «взрыв путей».
- Адрес функции проверки берут из Ghidra.
