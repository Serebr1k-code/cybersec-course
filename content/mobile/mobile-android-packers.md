## Что такое упаковщики и анти-тампер

Разработчики защищают приложения от анализа и модификации: обфусцируют код (ProGuard/R8), упаковывают DEX (DEX-пакеры, packers), проверяют целостность (anti-tamper), детектируют отладку и патчи. Задача пентестера — распаковать приложение и обойти эти защиты. Цель модуля — понять типовые упаковщики и методы их снятия.

## ProGuard и R8

ProGuard/R8 — это обфускаторы и оптимизаторы, встроенные в Android-сборку. Они переименовывают классы/методы в короткие имена (`a`, `b`, `c`), удаляют неиспользуемый код, инлайнят. Это не «шифрование», а переименование. Восстановить исходные имена полностью нельзя, но можно:

- `jadx --deobf` — пытается вернуть осмысленные имена;
- искать строки (они сохраняются);
- искать вызовы стандартных API (`Crypto`, `Http`, `Reflection`);
- идти от точек входа.

```bash
jadx -d out --deobf app.apk
```

## DEX-пакеры

Пакеры шифруют `classes.dex` и расшифровывают его в рантайме. Признаки: подозрительно маленький `classes.dex` с нативным загрузчиком, `Application`-класс, который что-то делает при старте, наличие `.so` с необычными именами. Методы снятия:

1. **Дамп из памяти** — запустить приложение и сдампить расшифрованный DEX из памяти (`frida-dexdump`, `dexhunter`).
2. **Хук загрузки** — перехватить `DexClassLoader`/`openDexFile`.
3. **Статический анпакинг** — иногда ключ расшифровки лежит рядом.

```bash
frida-dexdump -U -f com.example.app
```

## Проверки целостности

Anti-tamper проверяет CRC/хеш файлов, подпись, наличие изменений. Обход: хукать функцию проверки и возвращать «успех» либо патчить сравнение. Признаки: вычисления хешей (`MessageDigest`), чтение APK, сравнение с константой.

## Проверки подписи

Приложение может проверять свою подпись и завершаться при пересборке. Обход:

```javascript
Java.perform(function () {
    var PkgManager = Java.use('android.app.ApplicationPackageManager');
    PkgManager.getPackageInfo.overload('java.lang.String', 'int').implementation = function (n, f) {
        var info = this.getPackageInfo(n, f);
        info.signatures.value = [/* оригинальная подпись */];
        return info;
    };
});
```

## Root/эмулятор/отладка

Тесно связано: root detection, эмулятор detection, anti-debug. Обход — через Frida-хуки на соответствующие проверки (см. отдельные модули).

## Инструменты

- **`frida-dexdump`** — дамп DEX из памяти.
- **`dexhunter`** — поиск DEX в памяти.
- **`jadx --deobf`** — деобфускация.
- **`apkid`** — определение пакеров.
- **`objection`** — обход защит.

```bash
apkid app.apk
```

## Типичные ошибки и подводные камни

- **Путать обфускацию с шифрованием** — ProGuard не шифрует.
- **Пытаться восстановить все имена** — невозможно; идите от строк.
- **Не дампить DEX** — при пакере статика бесполезна.
- **Забыть про нативный загрузчик** — ключ может быть в `.so`.
- **Не обойти anti-tamper** — патч не запустится.
- **Игнорировать несколько DEX** — приложение может быть мультидекс.
- **Не проверить подпись** — пересборка может не работать.

## Что дальше / решение

План: определите защиту (`apkid`), для обфускации — `jadx --deobf` и поиск строк, для пакеров — дамп DEX из памяти, для anti-tamper и подписи — хуки через Frida. Комбинируйте со обходом root/отладки. Помните: любая клиентская защита обходится, потому что исполняется на устройстве, которое контролирует атакующий.

## Практический пример: снимаем DEX-пакер

Разберём сквозной сценарий. `apkid app.apk` сообщает, что приложение упаковано (`DEXGuard`/кастомный пакер). `jadx` показывает только маленький загрузчик `classes.dex`, а вся логика — в зашифрованном виде. Шаг 1: запускаем приложение на эмуляторе с root. Шаг 2: подключаем Frida и дампим расшифрованные DEX из памяти:

```bash
frida-dexdump -U -f com.example.app
```

Шаг 3: получаем набор `.dex`-файлов — это распакованный код. Шаг 4: декомпилируем их `jadx` и ищем логику. Если `frida-dexdump` не срабатывает, хукаем загрузку: перехватываем `DexClassLoader.$init` или `openDexFile` и сохраняем байты.

Это стандартный путь обхода пакеров: динамический дамп из памяти. Статический анпакинг возможен, но сложнее и зависит от пакера.

## Практический пример: обход проверки целостности

Другой сценарий: при пересборке APK приложение падает — срабатывает anti-tamper. Шаг 1: ищем проверку — `MessageDigest`, чтение APK, сравнение с константой. Шаг 2: хукаем функцию проверки и возвращаем «успех»:

```javascript
Java.perform(function () {
    var Checker = Java.use('com.example.app.IntegrityChecker');
    Checker.verify.implementation = function () {
        return true;
    };
});
```

Шаг 3: приложение запускается. Если проверка в нативном коде — используем `Interceptor` и `retval.replace(1)`.

## Частые вопросы

«`frida-dexdump` не находит DEX?» — другая версия загрузчика; хукайте ClassLoader вручную. «Пакер детектит Frida?» — сначала обойдите детектор. «Проверка в `.so`?» — Interceptor. «Как определить пакер?» — `apkid`. «Мультидекс?» — дампите все.

## Расширенный чек-лист по упаковщикам

Порядок. Первое: `apkid app.apk` — определите защиту. Второе: `unzip -l app.apk` — посмотрите размер `classes.dex`; маленький размер при большом приложении указывает на пакер. Третье: если пакер — дампите DEX из памяти (`frida-dexdump`), предварительно обойдя детекторы Frida. Четвёртое: если обфускация — `jadx --deobf` и поиск строк. Пятое: если anti-tamper — ищите проверки хешей/подписи и хукайте их. Шестое: если проверка подписи — хукайте `getPackageInfo`. Седьмое: если логика в `.so` — Ghidra.

## Как понять, что пакер

Признаки: маленький `classes.dex`, наличие нативного загрузчика (`System.loadLibrary` в `Application`), странные `.so` с обфусцированными именами, строки вида `StubApp`, `jiagu`, `libDexHelper`. Иногда `jadx` показывает только класс `Application`, который вызывает нативную функцию. Тогда статически логики нет — только динамика.

## Частые вопросы

«`frida-dexdump` не работает?» — детектор Frida; обойдите его. «Мультидекс?» — дампите все DEX. «Проверка подписи мешает?» — хук `getPackageInfo`. «Anti-tamper?» — хук проверки. «Нативный код?» — Ghidra.
