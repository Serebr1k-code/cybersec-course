## Вопрос, с которого всё начинается

Приложение-банк при старте проверяет «честность» телефона и отказывается работать на
рутованном устройстве. Но откуда приложение вообще знает, что система не подменена? Кто и
что проверяет при загрузке? Ответ — **Verified Boot**: цепочка, в которой каждый слой
подписан и проверяется следующим. Разберём её на реальных артефактах.

## Наш пример: образ с разблокированным загрузчиком

На столе — тестовый аппарат, у которого загрузчик разблокирован, и дамп разметки `vbmeta`
(это метаданные проверки загрузки Android). Первое, что смотрим — состояние verified boot:

```bash
$ adb shell getprop ro.boot.verifiedbootstate
orange
$ adb shell getprop ro.boot.flash.locked
0
```

`verifiedbootstate = orange` означает: загрузчик разблокирован, система загружается, но её
целостность не гарантируется. `flash.locked = 0` — «флеш разрешён». Уже из этих двух строк
понятно, что приложение, которое полагается только на флаг «locked», будет обмануто.

## Шаг 1: что такое Verified Boot

Verified Boot — это проверка, что код, который выполняется, — ровно тот, что был подписан
производителем. Работает по принципу **цепочки доверия**: неизменяемый кусок (ROM, root of
trust) проверяет следующий (загрузчик), тот — ядро и `vbmeta`, а `vbmeta` — остальные
разделы. Каждый слой содержит подпись или хеш ожидаемого содержимого. Если хеш не сходится —
устройство либо не грузится, либо показывает предупреждение.

## Шаг 2: AVB 2.0 и vbmeta

Android Verified Boot 2.0 (AVB) хранит проверочные данные в структуре **vbmeta**. Внутри —
набор **дескрипторов**: для каждого раздела либо хеш-дескриптор (одно значение на весь
раздел), либо hashtree-дескриптор (для больших разделов, где нужна построчная проверка).
Посмотрим на vbmeta:

```bash
$ avbtool info_image --image vbmeta.img
Footer version:           1.0
Image size:               4096 bytes
Original image size:      6144 bytes
Algorithm:                SHA256_RSA2048
Rollback index:           20240901
Flags:                    0
Descriptors:
  Hashtree descriptor:
    dm-verity version: 1
    Image size: 2147483648
    Tree offset: 2147483648
    Data block size: 4096
    Hash block size: 4096
  Hash descriptor:
    Partition Name: boot
    Hash Algorithm: sha256
    Digest: 8f3c...d21a
```

Читаем по-человечески: алгоритм подписи — RSA-2048 поверх SHA-256; для раздела `system`
используется hashtree (хеш-дерево), а для `boot` — простой хеш всего раздела. Подпись
защищает сами дескрипторы, поэтому подменить раздел без приватного ключа нельзя.

## Шаг 3: dm-verity и хеш-дерево

Проверять 2 ГБ раздела целиком при каждой загрузке — долго. Поэтому для больших разделов
применяют **dm-verity**: блоки проверяются на лету, по мере чтения. Строится **хеш-дерево**:
хеши блоков данных → хеши этих хешей → … → один корневой хеш, который лежит в подписанном
vbmeta. При чтении блока ядро сверяет его с деревом; несовпадение → ошибка ввода-вывода и
kernel panic. Проверить дерево можно вручную:

```bash
$ avbtool verify_image --image system.img
Verifying image system.img
Image system.img is verified successfully.
```

`verified successfully` означает, что корневой хеш образа совпал с подписанным ожиданием.
Именно поэтому «тихо» пропатчить `system` на устройстве с включённым dm-verity не выйдет.

## Шаг 4: состояния загрузки

Загрузчик сообщает системе и приложениям, насколько он «чист». Есть четыре состояния:

| Состояние | Цвет | Что значит | Верит ли приложение |
|---|---|---|---|
| Verified | green | всё подписано производителем | да |
| Self-signed | yellow | своя подпись, загрузчик заблокирован | частично |
| Unverified | orange | загрузчик разблокирован | нет |
| Failed | red | проверка не прошла | нет |

Приложение должно смотреть на **securityLevel** и `verifiedBootState`, а не на один флаг
`locked`. Разница критична: `locked = 1` может означать и green, и red.

## Шаг 5: практика — читаем состояние и vbmeta

Соберём минимум команд, которые нужны на любом аудите целостности:

```bash
$ adb shell getprop | grep -E 'verifiedbootstate|flash.locked|vbmeta.device_state'
[ro.boot.flash.locked]: [0]
[ro.boot.verifiedbootstate]: [orange]
[ro.boot.vbmeta.device_state]: [unlocked]
```

`ro.boot.vbmeta.device_state = unlocked` — прямое подтверждение разблокировки. Обратите
внимание: три разных свойства говорят об одном и том же — если приложение проверяет только
одно, его легко обмануть подменой (на root-устройстве свойства можно перезаписать через
`resetprop`).

## Шаг 6: почему это важно атакующему

Цепочка доверия ломается ровно в одном месте — там, где проверку можно отключить. Варианты:

- разблокировать загрузчик (проверки отключаются официально, но теряется доверие);
- найти уязвимость в самом загрузчике (до проверки vbmeta);
- загрузить пропатченное ядро, которое не применяет dm-verity.

Первые два — про целостность, третий — про уровень ниже. Поэтому на устройствах с
разблокированным загрузчиком смысл verified boot почти исчезает: система загрузится, но
никто не гарантирует, что она оригинальна.

## Шаг 7: рекомендации защищающейся стороне

- Никогда не полагаться на один флаг; проверять `verifiedBootState` **и** `securityLevel`.
- Требовать зелёное состояние для чувствительных операций.
- Помнить, что на root-устройстве `getprop` подделывается — комбинировать с аппаратной
  аттестацией (Key Attestation), где состояние загрузки подписано ключом в TEE.

## Что мы теперь знаем

- Verified Boot — цепочка подписей от ROM до системы.
- vbmeta хранит дескрипторы (hash / hashtree) и подписана производителем.
- dm-verity проверяет блоки на лету через хеш-дерево.
- Состояния green/yellow/orange/red и поле securityLevel — то, на что смотрит приложение.
- На разблокированном загрузчике проверки легко обходятся подменой свойств.

## Шаг 8: AVB в деталях — rollback index и chained partitions

У AVB есть две возможности, о которых новичок не догадывается. Первая — **rollback index**:
число, которое растёт с каждым обновлением и хранится в защищённом хранилище устройства.
Оно защищает от отката на старую уязвимую прошивку: если прошить образ со старым индексом,
загрузчик откажется. Именно поэтому «откатиться на версию, где был баг» на современных
устройствах нельзя просто так. Вторая — **chained partitions**: vbmeta может ссылаться на
другую vbmeta, и проверка идёт цепочкой. Это позволяет вендору подписывать разные части
разными ключами и делегировать доверие.

```bash
$ avbtool info_image --image vbmeta_system.img | grep -i chain
Chained Partition Descriptor:
  Partition Name: system
  Public Key: /vendor/etc/avb/keys/system.pem
  Rollback Index Location: 1
```

Читаем: раздел `system` проверяется не ключом из `vbmeta_system.img`, а отдельным ключом
`system.pem`. Это и есть цепочка — сломать её можно только подменив ключ, а ключ защищён
подписью верхнего уровня.

## Шаг 9: практика — распаковка и проверка образа

Исследователь почти всегда идёт от «что подписано» к «что внутри». Минимальный сценарий:
вытащить vbmeta и boot из прошивки, посмотреть дескрипторы и понять, какие разделы
защищены хешем, а какие деревом.

```bash
$ unzip -o firmware.zip vbmeta.img boot.img
Archive:  firmware.zip
  inflating: vbmeta.img
  inflating: boot.img
$ avbtool info_image --image boot.img | grep -E 'Algorithm|Digest'
Algorithm:  SHA256_RSA4096
Digest:     a91f...7c02
```

Теперь видно: `boot` подписан RSA-4096, а не 2048 — более сильный ключ. Сравнивая алгоритмы
разных разделов, можно заметить, где вендор сэкономил (слабый ключ или только хеш без
hashtree), и это часто подсказывает, куда смотреть при поиске слабого звена.

## Шаг 10: реальные ошибки конфигурации

Самое частое, что встречается на практике:

- `dm-verity` включён, но раздел `vendor` в режиме `logging` (только логирует несоответствия,
  не блокирует) — тихая модификация проходит.
- `vbmeta` без `flags` блокировки — устройство грузится в orange без предупреждения.
- Отключённая проверка `boot` при включённой проверке `system` — ядро подменяется свободно.

Каждая такая «мелочь» обесценивает всю цепочку. При аудите смотрите не на наличие verified
boot, а на то, **все ли** критические разделы реально проверяются и не стоит ли режим
логирования вместо enforce.

## Шаг 11: measured boot и аппаратные «якоря» доверия

Verified Boot проверяет **подписи**, но есть и второй подход — **measured boot**: система не
просто проверяет, а измеряет (хеширует) каждый компонент и складывает результат в защищённый
регистр. На ARM-платформах роль такого якоря играет фьюз (одноразово записываемый бит) с
публичным ключом вендора. Смысл один и тот же: цепочка доверия начинается с неизменяемого
аппаратного значения, которое нельзя подменить программно.

Разница для атакующего: подписи можно обойти, отключив проверку (разблокировка загрузчика),
а измерение остаётся зафиксированным. Поэтому продвинутые проверки целостности смотрят именно
на «якорь» — фьюз-ключ или результат аттестации, — а не на текущие свойства системы, которые
на root-устройстве подделываются.

## Шаг 12: частые вопросы при аудите

**«Мы включили verified boot — значит защищены?»** Не обязательно: проверьте, что включён
enforce-режим dm-verity, а не logging, и что все критические разделы покрыты.

**«Почему на нашем устройстве verifiedbootstate = green, но приложение всё равно ругается?»**
Скорее всего, приложение смотрит не только на состояние загрузки, но и на наличие root,
отладочный флаг или подпись самого APK. Green загрузки не отменяет рутованную систему поверх.

**«Можно ли прошить официальную прошивку и вернуть доверие?»** Обычно да, если загрузчик
снова заблокирован: перепрошивка восстанавливает подписи. Но rollback index может запретить
откат на старую версию, даже официальную.

## Шаг 13: как это связано с остальными проверками

Verified Boot — фундамент, на который опираются Key Attestation, Play Integrity и root-детект.
Когда приложение проверяет `securityLevel = TEE` и `verifiedBootState = Verified` в
аттестационном сертификате, оно получает заверение, подписанное ключом из кремния. Именно
поэтому аппаратная аттестация — самый устойчивый сигнал: чтобы её обмануть, нужна атака на
TrustZone или на загрузочную цепочку, а не подмена строки в `/proc`.
