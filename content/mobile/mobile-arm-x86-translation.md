## Вопрос, с которого всё начинается

Ты распаковал APK и увидел внутри несколько каталогов с нативным кодом: `lib/arm64-v8a/`, `lib/armeabi-v7a/`, `lib/x86/`. Один и тот же файл лежит в четырёх вариантах. Зачем? И какой из них анализировать?

## Наш пример: libfoo.so из uncrack2.apk

Возьмём `uncrack2.apk` — учебное приложение с нативной проверкой секрета. Внутри четыре версии одной библиотеки:

```
$ unzip -l uncrack2.apk | grep '\.so'
    14176   lib/arm64-v8a/libfoo.so
    13948   lib/armeabi-v7a/libfoo.so
    13788   lib/x86/libfoo.so
    14440   lib/x86_64/libfoo.so
```

Четыре каталога — четыре **ABI** (Application Binary Interface): способа представления машинного кода. `arm64-v8a` — 64-битный ARM (современные телефоны), `armeabi-v7a` — 32-битный ARM (старые), `x86`/`x86_64` — Intel (эмуляторы и редкие устройства).

## Шаг 1: определяем архитектуру

Извлечём arm64-версию и посмотрим, что это за файл:

```
$ file lib/arm64-v8a/libfoo.so
libfoo.so: ELF 64-bit LSB shared object, ARM aarch64, version 1 (SYSV), dynamically linked, ... stripped
```

`ARM aarch64` — это arm64. `stripped` означает, что имена функций удалены — реверс усложняется. Сравним с x86-версией:

```
$ file lib/x86/libfoo.so
libfoo.so: ELF 32-bit LSB shared object, Intel 80386, ... stripped
```

Это уже `Intel 80386` (32-битный x86). Один и тот же исходный код скомпилирован под разные процессоры.

## Шаг 2: читаем ELF-заголовок

`readelf` показывает заголовок ELF (формат нативных библиотек на Android/Linux):

```
$ readelf -h lib/arm64-v8a/libfoo.so | head -12
  Class:                             ELF64
  Data:                              2's complement, little endian
  Type:                              DYN (Shared object file)
  Machine:                           AArch64
  Entry point address:               0x8a0
  Number of section headers:         22
```

`Machine: AArch64` подтверждает архитектуру, `Type: DYN` — это разделяемая библиотека (не исполняемый файл). `Entry point` — адрес точки входа.

## Шаг 3: ищем экспортируемые символы

Даже в stripped-библиотеке экспортируемые функции остаются видимыми — их вызывает Java через JNI (Java Native Interface). Найдём их:

```
$ strings lib/arm64-v8a/libfoo.so | grep -iE 'Java_|strncmp|secret'
Java_sg_vantagepoint_uncrackable2_CodeCheck_bar
strncmp
```

Имя `Java_sg_vantagepoint_uncrackable2_CodeCheck_bar` — это **JNI-символ**. По соглашению JNI нативная функция называется `Java_<пакет>_<класс>_<метод>`: пакет `sg.vantagepoint.uncrackable2`, класс `CodeCheck`, метод `bar`. Значит, проверка секрета в этом приложении реализована в нативном коде, и Java-декомпиляция её не покажет.

## Шаг 4: зачем несколько ABI

Android выбирает библиотеку под архитектуру устройства. Современный телефон возьмёт `arm64-v8a`, старый — `armeabi-v7a`, эмулятор — `x86_64`. Разработчик кладёт все версии, чтобы приложение работало везде.

Для тестировщика это значит: **анализировать нужно ту ABI, которая соответствует твоему устройству**. Если ты запускаешь на arm64-телефоне, тебе нужна `arm64-v8a`; если на эмуляторе x86_64 — `x86_64`. Логика в них одинаковая, но адреса и регистры разные.

## Шаг 5: трансляция ARM на x86

Возникает вопрос: как x86-эмулятор запускает arm64-приложение? Ответ — **трансляция**. Google долгое время поставлял `libhoudini` (от Intel) — слой, который на лету переводит ARM-инструкции в x86. Сейчас эту роль выполняет **ARM-to-x86 translation** в новых эмуляторах. Трансляция бывает медленной и неполной: не все ARM-инструкции поддерживаются, а некоторые приложения просто не запускаются на эмуляторе.

Практический вывод: если нативное приложение не работает на x86-эмуляторе, попробуй arm64-образ (на Apple Silicon эмулятор нативно ARM) или реальное устройство.

## Шаг 6: что искать в нативном коде

Нативная библиотека — это отдельный мир анализа. Что там ищут:

- **JNI-функции** — точки входа из Java (`Java_...`).
- **Строки** — секреты, URL, ключи (`strings`).
- **Сравнения** — `strncmp`, `memcmp` часто прячут проверку пароля.
- **Анти-отладка** — `ptrace`, проверки `/proc/self/status`.
- **Шифрование** — константы AES/SHA.

Для глубокого разбора используют Ghidra/IDA/r2. Но даже `strings` и `readelf` часто дают первую зацепку — как в нашем случае с JNI-символом.

## Шаг 7: когда ABI не совпадает

Частая ошибка новичка — взять «не ту» библиотеку. Например, реверсить `armeabi-v7a`, когда приложение на телефоне грузит `arm64-v8a`: адреса и вызовы не совпадут с тем, что происходит в рантайме. Поэтому всегда сверяй ABI с устройством:

```
$ adb shell getprop ro.product.cpu.abi
arm64-v8a
```

И выбирай соответствующий каталог. Для эмулятора — `ro.product.cpu.abi` покажет `x86_64` (или `arm64-v8a`, если эмулятор ARM).

## Шаг 8: JNI и загрузка библиотеки

Связь Java и нативного кода устроена так: Java-класс объявляет метод `native`, а система ищет соответствующую функцию в загруженной библиотеке. Библиотеку грузят явно:

```java
static { System.loadLibrary("foo"); }
```

`System.loadLibrary("foo")` ищет `libfoo.so` в каталоге нужной ABI и загружает его. После этого Java-метод `bar` вызывает нативную `Java_sg_vantagepoint_uncrackable2_CodeCheck_bar`. Если хочешь перехватить эту функцию динамически, имя символа уже известно из `strings` — можно поставить хук по экспорту через Frida:

```javascript
var f = Module.findExportByName("libfoo.so", "Java_sg_vantagepoint_uncrackable2_CodeCheck_bar");
Interceptor.attach(f, { onLeave: function (r) { r.replace(1); } });
```

## Шаг 9: что делать, если символов нет

Иногда библиотека не экспортирует JNI-функции, а регистрирует их динамически через `RegisterNatives` — тогда имён в таблице нет. В таком случае ищут адреса через анализ `JNI_OnLoad` в дизассемблере: там перечислены пары «имя метода → указатель на функцию». Это уже глубокий реверс, но он открывает нативную логику, спрятанную от `strings`.

## Шаг 10: практический вывод

На практике для анализа нативного кода действуй так: определи ABI устройства (`getprop ro.product.cpu.abi`), извлеки соответствующую библиотеку, посмотри `file` и `readelf -h`, найди JNI-символы через `strings`, а дальше — либо хук по экспорту через Frida, либо дизассемблер для глубокого разбора. Этого порядка достаточно, чтобы не потеряться среди четырёх ABI. И помни: если динамика не сходится со статикой, первым делом перепроверь ABI — это самая частая причина расхождений. Начни анализ с той библиотеки, которую реально грузит устройство.

## Шаг 11: разбираем заголовок реальной библиотеки

Чтобы понять, что именно определяет запускаемость, прогоним `readelf` по собранной библиотеке (у нас x86-64, но поля те же и для `arm64`):

```
$ file libfoo.so
libfoo.so: ELF 64-bit LSB shared object, x86-64, version 1 (SYSV), dynamically linked, not stripped
$ readelf -h libfoo.so | head -8
ELF Header:
  Magic:   7f 45 4c 46 02 01 01 00 00 00 00 00 00 00 00 00
  Class:                             ELF64
  Data:                              2's complement, little endian
  Type:                              DYN (Shared object file)
  Machine:                           Advanced Micro Devices X86-64
```

Поле `Machine` — то самое место, где для Android-библиотеки будет `AArch64` (ARM64) или `ARM` (32-бит). Именно это значение определяет, на каком ABI загрузится `.so`. Если `Machine` не совпадает с ABI устройства, `System.loadLibrary` падает с `UnsatisfiedLinkError` — вот корень проблемы «библиотека есть, а JNI не находится».

## Что мы теперь знаем

- APK содержит нативные библиотеки под несколько ABI: arm64-v8a, armeabi-v7a, x86, x86_64.
- ABI — способ представления машинного кода; устройство выбирает подходящую.
- `file` и `readelf -h` показывают архитектуру ELF-библиотеки.
- JNI-символы вида `Java_<pkg>_<Class>_<method>` указывают точки входа из Java.
- Трансляция ARM→x86 позволяет запускать ARM-код на x86-эмуляторе, но не всегда.
- Анализировать нужно ту ABI, что соответствует устройству.
