## Вопрос, с которого всё начинается

Ты обошёл Java-пиннинг, обошёл нативный — а трафик всё равно иногда рвётся, причём не сразу,
а после нескольких запросов. Это признак **многослойной** защиты: проверок несколько, и они
независимы. Как их найти все и не потратить день на слепой перебор хуков?

## Наш пример: карта проверок

Разбор приложения дал такую картину:

```bash
$ grep -Rni 'pinn\|spki\|certificate' smali/ lib/ | head
smali/com/example/net/Pinning.smali:  CertificatePinner
lib/arm64-v8a/libcore.so:             SSL_CTX_set_verify
server header: X-Pin-SPKI: <hash>
```

Три независимых слоя: Java (`CertificatePinner`), native (`SSL_CTX_set_verify`) и серверный
заголовок `X-Pin-SPKI`. Весь урок ведём эту карту.

## Шаг 1: почему «несколько слоёв» — это сложно

Один слой обходится одним хуком. Несколько слоёв означают, что отключение одного не помогает:
следующий всё равно отвергает соединение. Хуже того, слои могут проверять друг друга (например,
Java проверяет, что нативный хук не стоит). Поэтому задача не «найти хук», а «составить карту
всех проверок и обойти их согласованно».

## Шаг 2: слой Java — OkHttp CertificatePinner

`CertificatePinner` в OkHttp сравнивает SHA-256 публичного ключа сертификата с ожидаемым.
Обход — подменить метод `check` так, чтобы он ничего не делал:

```javascript
Java.perform(function () {
  const Pinner = Java.use('okhttp3.CertificatePinner');
  Pinner.check.overload('java.lang.String', 'java.util.List').implementation = function () {};
});
```

Это отключает Java-слой. Но native-слой продолжит работать.

## Шаг 3: слой native — SSL_CTX_set_verify

Native-слой мы уже разбирали в отдельном уроке: подменяем режим verify на `SSL_VERIFY_NONE`
или возвращаем «успех» из `X509_verify_cert`. Важно: этот слой независим от Java, поэтому его
надо обходить отдельно.

## Шаг 4: слой серверный — SPKI-заголовок

Самый коварный слой — на сервере. Клиент шлёт в заголовке отпечаток своего ожидаемого ключа,
а сервер сверяет его со своим. Если ты подменяешь сертификат, отпечаток не сходится, и сервер
рвёт соединение — причём **на уровне приложения**, а не TLS. Здесь хук на клиенте не поможет:
надо либо подменить заголовок, либо заставить клиент не отправлять его.

```bash
$ grep -rn 'X-Pin-SPKI' smali/ | head
smali/com/example/net/Api.smali: const-string v0, "X-Pin-SPKI"
```

## Шаг 5: порядок обхода

Правильная последовательность:

1. Составить карту всех проверок (grep по строкам, разбор `.so`, заголовки).
2. Начать с самого внешнего слоя (обычно Java).
3. Затем native.
4. Затем серверный — подменой заголовка или его удалением.
5. После каждого шага проверять трафик, а не гадать.

## Шаг 6: как слои проверяют друг друга

Продвинутые приложения сверяют результаты слоёв: например, native-код проверяет, что
Java-класс `CertificatePinner` не изменён, или наоборот. Тогда одного хука мало — надо
«согласовать» хуки, чтобы каждый слой видел непротиворечивую картину. Это уже не обход
одной проверки, а аккуратная работа со всем рантаймом.

## Шаг 7: признак того, что слой остался

Симптомы недобранного слоя: соединение рвётся после N запросов (счётчик), рвётся на конкретном
эндпоинте, приходит `403` вместо разрыва TLS. Это значит, что TLS-слои обойдены, а проверка
живёт в логике приложения или на сервере. Тогда ищут сравнение отпечатка в smali и в заголовках.

## Шаг 8: инструменты

Полезное: `strings`/`grep` по `.so` и smali, Frida для Java и native, Ghidra для нативной
логики, прокси для наблюдения за заголовками. Часто ключ к разгадке — именно заголовок в
запросе, который видно только на прокси.

## Шаг 9: что считать успехом

Успех — не «хук поставился», а «трафик читается и приложение работает». Поэтому критерий:
на прокси видны расшифрованные запросы и ответы, и приложение не падает. Промежуточные
результаты («хук не выдал ошибку») ничего не значат.

## Шаг 10: как защищают правильно

Настоящая защита — не количество проверок, а их согласованность и серверная верификация:
attestation (сервер знает, что клиент неперепрошитый), проверка целостности кода, обфускация,
несколько независимых отпечатков. Но даже это — повышение порога, а не абсолют: на устройстве
под контролем атакующего любой код можно обойти. Задача защиты — сделать обход дороже, чем
выгода.

## Что мы теперь знаем

- Пиннинг бывает многослойным: Java + native + серверный.
- Обходить надо по слоям, начиная с внешнего.
- Серверный слой (SPKI-заголовок) хуком клиента не обходится.
- Критерий успеха — читаемый трафик, а не отсутствие ошибок хука.
- Правильная защита — согласованность слоёв и attestation.
