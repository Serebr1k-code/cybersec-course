Мы уже разобрали базовую сетевую конфигурацию, MITM и обход пиннинга в Java-слое. Но самые
упрямые приложения переносят проверку сертификата в **нативный код** (C/C++ через JNI), где
обычный Frida-хук по Java-методам её не видит. А ещё есть **Certificate Transparency** —
механизм, по которому приложение узнаёт, что сертификат сервера не попал в публичные логи. И
**OAuth**, где вместо сертификата ломается сам редирект. Этот модуль — про три места, где
сетевой трафик «теряется» даже при настроенном прокси.

## Что покрывает модуль

1. **Нативный пиннинг** (`mobile-android-ssl-pinning-native`) — как `SSL_CTX_set_verify` и
   OpenSSL/BoringSSL проверяют сертификат из C и почему хук по Java их не трогает.
2. **Certificate Transparency** (`mobile-android-cert-transparency`) — что такое SCT и
   `NetworkSecurityPolicy` CT-enforcement, и как отличить «нет логов» от «нет трафика».
3. **Продвинутый multi-layer пиннинг** (`mobile-android-pinning-deep`) — когда проверок
   несколько (Java + native + проверка отпечатка на сервере), и как их обходить по слоям.
4. **OAuth-редиректы** (`mobile-android-oauth`) — Custom Tabs, AppAuth, перехват
   `redirect_uri` и почему `https`-редирект на стороне приложения — точка атаки.

## Почему такой порядок

Сначала — самый частый случай: пиннинг, уехавший в нативный код. Затем CT: если пиннинг
обойдён, а трафик всё равно не идёт, причина часто в CT-enforcement. Дальше — обобщение:
несколько защит сразу. И в конце — OAuth, где вопрос уже не «как расшифровать канал», а «как
перехватить авторизацию». Каждый урок опирается на базовую сетевую конфигурацию из
`mobile-network-security`, поэтому идите по порядку.

## Чему вы научитесь

- Находить нативный пиннинг в `.so` и обходить его без пересборки приложения.
- Понимать, что такое SCT и CT-enforcement, и отличать сетевую защиту от ошибки прокси.
- Разбирать многослойный пиннинг и обходить его по одному слою за раз.
- Перехватывать OAuth-редирект и находить небезопасный `redirect_uri`.

## Связь с другими ветками

Обход Java-пиннинга и базовый MITM — в `mobile-ssl-pinning` и `mobile-tls-pinning-bypass`.
Работа с самим API (JWT, GraphQL, версии, rate-limit) — в модуле `mobile-android-api-deep`.
Инструменты нативного реверса — в `mobile-reverse-native`.

## Квиз

Проверь себя.

```quiz
- question: Почему Frida-хук по Java-методам не обходит нативный пиннинг?
  options:
    - Frida не работает с Java
    - Проверка сертификата идёт в C/C++ коде, а не в Java-слое
    - Нативный код зашифрован
    - Android не поддерживает OpenSSL
  answer: 1
  explanation: Нативный пиннинг живёт в .so, хук по Java-классам его не задевает.
- question: Что такое SCT в контексте Certificate Transparency?
  options:
    - Тип шифра
    - Подписанная метка времени, доказывающая попадание сертификата в лог
    - Протокол сжатия
    - Формат PNG
  answer: 1
  explanation: Signed Certificate Timestamp подтверждает запись сертификата в публичный CT-лог.
- question: Признак многослойного пиннинга?
  options:
    - Одна проверка в Java
    - Проверки и в Java, и в native, и на сервере по отпечатку
    - Только cleartext
    - Отсутствие TLS
  answer: 1
  explanation: Multi-layer — это несколько независимых проверок в разных слоях.
- question: Что чаще всего ломается в OAuth у мобильного приложения?
  options:
    - Алгоритм шифрования
    - redirect_uri и перехват кода авторизации
    - Версия HTTP
    - DNS
  answer: 1
  explanation: Небезопасный redirect_uri позволяет перехватить authorization code.
```
