## Вопрос, с которого всё начинается

Пользователь копирует пароль или токен в приложении, а потом вставляет его куда-то ещё. Но пока
данные лежат в буфере обмена, их может прочитать **любое** приложение — или они уедут на другое
устройство через universal clipboard. Разберём, как устроен буфер обмена iOS и какие утечки он
создаёт.

## Наш пример: скопированный токен

Приложение копирует токен авторизации в буфер, чтобы пользователь вставил его в веб-форму. Что
происходит с этим токеном дальше — и как его перехватить?

## Шаг 1: виды буфера обмена

- **UIPasteboard.general** — системный буфер, общий для всех приложений.
- **UIPasteboard.system** — используется системными механизмами (иногда отдельно).
- **Именованные (named) pasteboard** — создаются приложением и живут только пока приложение
  живо (для внутреннего обмена).

Самое опасное — `general`: его видит любое приложение.

## Шаг 2: чтение и запись

Запись и чтение просты:

```swift
UIPasteboard.general.string = "secret-token-123"
let s = UIPasteboard.general.string
```

Другое приложение, находящееся на переднем плане, может прочитать `general.string`, если
получит фокус. Исторически это позволяло приложениям «подглядывать» за буфером в фоне.

## Шаг 3: universal clipboard

Если включён **Handoff** и universal clipboard, содержимое буфера синхронизируется между
устройствами одного Apple ID. То есть токен, скопированный на iPhone, окажется на Mac и
наоборот. Это удобно — и это канал утечки между устройствами.

## Шаг 4: уведомления о вставке (iOS 16+)

С iOS 16 приложение, читающее буфер, не принадлежащий ему, вызывает системное уведомление
«Вставка из …». Это ограничивает тихое подглядывание. Приложения обходят это через
`UIPasteControl` (кнопка вставки) или через пользовательский жест.

## Шаг 5: где искать утечки

- Пароли и токены, копируемые через `general` без очистки (`UIPasteboard.general.items = []`).
- Секреты, остающиеся в буфере после использования.
- Синхронизация на общие устройства.
- Приложения, читающие буфер при старте (частая причина утечек).

При анализе проверяют, очищает ли приложение буфер после копирования и использует ли
`localOnly`/`expirationDate`.

## Что мы теперь знаем

- `UIPasteboard.general` виден всем приложениям.
- Universal clipboard переносит данные между устройствами одного Apple ID.
- С iOS 16 чтение чужого буфера вызывает уведомление.
- Защита — очистка буфера и использование `localOnly`/срока жизни.

## Если не сработало

Если чтение буфера не даёт данных на iOS 16+, вероятно, требуется пользовательское действие
(вставка через `UIPasteControl`). Если данные не синхронизируются, проверьте Handoff и
универсальный буфер в настройках. Для внутреннего обмена используйте named pasteboard, а не
`general`.

## Частые вопросы

**Буфер обмена шифруется?** Хранится в защищённом виде, но доступен приложениям.

**Можно ли очистить буфер?** Да: `UIPasteboard.general.items = []`.

**Опасен ли universal clipboard?** Да, при общих устройствах или Apple ID.

## Полная модель UIPasteboard

`UIPasteboard` — это не один буфер, а несколько, и различать их важно.

- `UIPasteboard.general` — системный буфер, общий для всех приложений. Его содержимое доступно
  любому приложению, которое получит фокус (с ограничениями новых версий iOS).
- Именованные (named) pasteboard — создаются приложением через `UIPasteboard(name:create:)` и
  существуют, пока живо приложение. Используются для внутреннего обмена между расширениями и
  приложением.
- Системные pasteboard — используются системными механизмами, приложения обычно их не трогают.

Самое опасное — `general`: всё, что в него попало, потенциально видно другим приложениям и может
уехать на другое устройство через universal clipboard.

## Типы данных и items

Буфер хранит не одну строку, а набор элементов (`items`), у каждого — свой тип. Приложение может
положить сразу несколько представлений одного объекта: строку, URL, картинку.

```swift
let pb = UIPasteboard.general
pb.items = [["public.utf8-plain-text": "secret-token-123"]]
let types = pb.types  // ["public.utf8-plain-text"]
```

`types` перечисляет доступные представления. Читая `pb.string`, вы получаете строковое
представление; `pb.url` — URL; `pb.image` — картинку. Для анализа это полезно: приложение может
класть в буфер больше, чем видно в интерфейсе, — например, полный JSON, а не только текст.

## Как приложения читают буфер

Исторически любое приложение могло читать `UIPasteboard.general.string` в фоне — это породило
целый класс утечек: фоновое приложение тихо забирало то, что пользователь скопировал в другом
месте (пароли, коды, номера карт).

```swift
let leaked = UIPasteboard.general.string
```

С iOS 14 Apple добавила баннер «Вставка из …», который показывается, когда приложение читает
буфер, принадлежащий другому приложению. С iOS 16 появился полноценный запрос разрешения: чтобы
прочитать чужой буфер программно, нужно согласие пользователя. Обходной путь для разработчиков —
`UIPasteControl` (системная кнопка вставки), которая не требует отдельного разрешения, потому что
действие инициирует сам пользователь.

Для аналитика это значит: на старых версиях iOS утечка через чтение буфера — реальный вектор; на
новых она ограничена уведомлением и запросом.

## Извлечение данных через Frida

На джейлбрейкнутом устройстве буфер можно перехватывать динамически. Хукают методы `UIPasteboard`,
чтобы видеть, что читается и что записывается.

```javascript
if (ObjC.available) {
  var UIPasteboard = ObjC.classes.UIPasteboard;
  Interceptor.attach(UIPasteboard['- setString:'].implementation, {
    onEnter: function (args) {
      var s = new ObjC.Object(args[2]).toString();
      console.log('[copy] ' + s);
    }
  });
}
```

Так ловят момент, когда приложение кладёт секрет в общий буфер, и проверяют, очищает ли оно его
после. Если секрет остаётся в `general` — это утечка: следующее приложение (или злоумышленник)
может его прочитать.

## Universal clipboard как канал между устройствами

Если включён Handoff и universal clipboard, содержимое буфера синхронизируется между
устройствами одного Apple ID: скопированное на iPhone появляется на Mac и наоборот. Это удобно —
и это канал утечки между устройствами. Секрет, скопированный на рабочем телефоне, может оказаться
на личном Mac, и наоборот.

При аудите проверяют, не копирует ли приложение чувствительные данные в общий буфер, где они
синхронизируются и остаются.

## Таблица: типы буфера и риски

| Буфер | Видимость | Риск утечки |
|---|---|---|
| general | все приложения | высокий |
| named | только приложение | низкий |
| system | системные механизмы | средний |
| universal (Handoff) | устройства Apple ID | высокий |

## Если не сработало

Если чтение буфера не даёт данных на iOS 16+, — требуется пользовательское действие
(`UIPasteControl`) или разрешение. Программное чтение чужого буфера заблокировано.

Если данные не синхронизируются между устройствами, — проверьте Handoff и universal clipboard в
настройках; они должны быть включены на обоих устройствах и в одном Apple ID.

Если Frida-хук не срабатывает, — убедитесь, что приложение использует `setString:` (а не
`setItems:` или `setData:`). Хукать стоит все три, чтобы не пропустить запись.

## Ограничения

Буфер обмена — общий ресурс, и Apple постепенно ограничивает его тихое использование. Тем не
менее остаются легальные причины: обмен между своими приложениями, вставка по жесту пользователя.
Опасность появляется, когда секрет (пароль, токен, номер карты) попадает в `general` и остаётся
там без очистки.

Правильная практика — очищать буфер после использования (`UIPasteboard.general.items = []`),
использовать `localOnly` и `expirationDate`, а для внутреннего обмена применять named pasteboard,
а не общий. При пентесте эти проверки входят в чек-лист приватности.

## Мини-практика: проверить приложение на утечку буфера

Разберём чек-лист аудита буфера обмена.

Пункт 1. Ищем в коде запись в общий буфер:

```bash
$ grep -rn 'UIPasteboard' . | grep -vE 'named|private'
```

Каждое обращение к `UIPasteboard.general` — кандидат на утечку. Смотрим, что именно копируется:
если пароль, токен или номер карты — это чувствительные данные.

Пункт 2. Проверяем, очищается ли буфер после использования:

```bash
$ grep -rn 'items = \[\]\|removePasteboard\|UIPasteboard.general.string = nil' .
```

Если очистки нет — секрет остаётся в буфере и доступен следующему приложению.

Пункт 3. Динамически подтверждаем через Frida: хукаем `setString:` и смотрим, что попадает в
буфер.

```javascript
Interceptor.attach(ObjC.classes.UIPasteboard['- setString:'].implementation, {
  onEnter: function (args) {
    console.log('[copy] ' + new ObjC.Object(args[2]).toString());
  }
});
```

Пункт 4. Проверяем, не читает ли приложение буфер при старте (частая причина утечек): ищем
`UIPasteboard.general.string` в `applicationDidBecomeActive`.

## Частые ошибки

Ошибка первая — считать, что на новых iOS чтение буфера невозможно. Ограничения есть, но
приложение всё равно может копировать секрет в общий буфер, откуда его прочитает другое
приложение (или universal clipboard увезёт на другое устройство).

Ошибка вторая — игнорировать universal clipboard. Даже если на самом устройстве утечка
невозможна, синхронизация через Handoff переносит данные на другие устройства Apple ID.

Ошибка третья — проверять только `string`. Приложение может класть данные через `items` или
`setData:`, и их нужно хукать отдельно.

## Итог

Буфер обмена — простой механизм с далеко идущими последствиями. Правильная практика: очищать
буфер после копирования секрета, использовать `localOnly` и `expirationDate`, а для внутреннего
обмена — named pasteboard. При аудите эти четыре пункта дают быстрый и наглядный результат.

## Шпаргалка: буфер обмена iOS

| Задача | Приём |
|---|---|
| найти запись в общий буфер | `grep -rn 'UIPasteboard.general'` |
| проверить очистку | `grep 'items = \[\]'` |
| перехватить копирование | Frida-хук `setString:` |
| проверить чтение при старте | `applicationDidBecomeActive` |
| ограничить срок жизни | `expirationDate`, `localOnly` |

Главное правило аудита: секрет (пароль, токен, номер карты) не должен оставаться в
`UIPasteboard.general`. Копирование допустимо, если сразу за ним следует очистка буфера.

## Куда дальше

Буфер — канал утечки данных. Но Apple требует от разработчиков **декларировать**, какие данные
они собирают. Разберём Privacy Manifest.

- Аудит утечек паролей и токенов через буфер.
- Проверка приватности приложений.
