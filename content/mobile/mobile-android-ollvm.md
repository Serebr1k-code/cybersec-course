## Вопрос, с которого всё начинается

Вы открыли нативную функцию в Ghidra, но вместо понятной логики — огромный `while` с гигантским
`switch`, куча бессмысленных проверок и вычислений. Код явно «закручен». Это результат OLLVM.
Как понять, что именно применили, и как вернуть читаемость?

## Наш пример: функция check в libprotect.so

Декомпиляция начинается с диспетчера:

```c
while (true) {
  switch (state) {
    case 0x1a3f: x = x + 7; state = 0x2b; break;
    case 0x2b:   if (x == 42) state = 0x9c; else state = 0x1a3f; break;
    ...
  }
}
```

Это классический признак обфускации. Разберём приёмы.

## Шаг 1: что такое OLLVM

OLLVM (Obfuscator-LLVM) — модификация компилятора, которая добавляет в код «запутывание». Её
используют, чтобы защитить логику приложения: аналитику приходится тратить больше времени.
Это не шифрование, а искажение структуры.

## Шаг 2: control-flow flattening

Самый известный приём: нормальные блоки кода превращаются в «плоскую» структуру с одной
переменной-состоянием и большим `switch`. Управление идёт не по естественным ветвям, а через
диспетчер. Читать такой код линейно невозможно — нужно восстановить граф переходов.

## Шаг 3: bogus control flow

Второй приём: в код вставляются ложные ветви, которые никогда не выполняются, но выглядят
правдоподобно:

```c
if (opaque_predicate()) { real_code(); } else { junk(); }
```

`opaque_predicate` — условие, которое всегда истинно, но компилятор не может это доказать.
Аналитику приходится вычислять предикат, чтобы отбросить мусор.

## Шаг 4: instruction substitution

Третий приём: простые операции заменяются эквивалентными сложными. Например, `x + 1` может
стать `x - (-1)` или цепочкой XOR/сдвигов. Смысл тот же, но читаемость падает.

## Шаг 5: как распознать

Признаки в Ghidra: один большой `switch` с числовыми состояниями; множество маленьких блоков;
странные арифметические последовательности; вызовы, ведущие в «мусорные» функции. Отдельно
проверяют секции `.text` на аномалии и наличие строк вроде `ollvm`.

## Шаг 6: деобфускация

Полностью автоматической «кнопки» нет, но есть подходы:

- **Трассировка**: прогнать функцию и записать реальный порядок выполнения блоков (Frida
  Stalker, Unicorn-хуки). Тогда `switch`-диспетчер превращается в линейный список.
- **Символьное исполнение**: angr может пройти путь и восстановить значения.
- **Скрипты для Ghidra**: плагины, которые анализируют граф и «схлопывают» диспетчер.

Часто достаточно трассировки: она даёт фактический поток управления, и логика становится видна.

## Шаг 7: практика

Типовой порядок: определить тип обфускации по структуре → восстановить поток трассировкой →
отбросить bogus-ветви (они не выполняются) → упростить подстановки. Это трудоёмко, но реально,
особенно если защищён небольшой участок.

## Шаг 8: разбор диспетчера вручную

Вернёмся к нашему `switch`. Переменная `state` — это обычная локальная переменная, а каждый
`case` присваивает ей следующее значение. Чтобы вернуть читаемость, надо построить граф переходов:
для каждого `case` выписать, какие значения `state` он может выставить. Начнём с одного блока:

```c
case 0x1a3f: x = x + 7;   state = 0x2b;   break;
case 0x2b:   if (x == 42) state = 0x9c; else state = 0x1a3f; break;
case 0x9c:   return 1;
```

Читая последовательно, получаем: `0x1a3f` → `0x2b` → либо `0x9c` (успех), либо обратно на
`0x1a3f`. То есть это цикл «прибавляй 7, пока не станет 42». Диспетчер растворился, и логика
стала линейной. На большом графе это делают скриптом, а не глазами.

## Как flattening выглядит в машинном коде

На уровне ассемблера «плоский» диспетчер узнаётся по косвенному переходу по таблице:

```asm
adrp  x8, .jumptable
ldr   w9, [x8, w0, uxtw #2]   ; взять адрес блока по индексу-состоянию
br    x9                      ; косвенный прыжок
```

`br x9` (branch register) — прыжок на адрес из регистра. Именно так реализуется большой `switch`.
Признаки: одна переменная, которая перезаписывается перед каждым переходом; таблица адресов в
`.rodata`; блоки, не связанные обычными `b`/`cbz`. В Ghidra это выглядит как граф с «звездой»
вокруг диспетчера.

## Деобфускация трассировкой: рабочий пример

Самый надёжный путь — записать фактический порядок блоков. Через Frida Stalker это делается так:

```javascript
const f = Module.getExportByName('libprotect.so', 'check');
Interceptor.attach(f, {
  onEnter() { Stalker.follow(Process.getCurrentThreadId(), {
    events: { call: false, ret: false, exec: true },
    onReceive(events) { /* события exec дают реальные адреса блоков */ }
  }); },
  onLeave() { Stalker.unfollow(); }
});
```

Получив список адресов, сопоставляем их с блоками в Ghidra и выписываем линейную цепочку. Bogus-
ветви в трассу не попадут — они не выполняются, поэтому автоматически отбрасываются. Для функции
без внешних зависимостей то же самое делает Unicorn с хуком `UC_HOOK_BLOCK`.

## Символьное исполнение против предикатов

`opaque predicate` — условие, всегда истинное, но недоказуемое статически. angr может его
«упростить»: строится выражение ветвления, и решатель проверяет, достижима ли одна из ветвей.

```python
import angr
p = angr.Project('libprotect.so')
sm = p.factory.simgr(p.factory.entry_state())
sm.explore(find=0x1f40, avoid=[0x1f80])   # ищем путь к цели, минуя мусор
print(sm.found[0].posix.dumps(0))         # аргумент, приводящий к успеху
```

Если решатель говорит, что мусорная ветвь недостижима при любых входах, её можно смело вырезать.
Это дороже трассировки по времени, но даёт готовые значения без запуска устройства.

## Таблица: как узнать приём

| Приём | Признак в декомпиляции | Признак в асме |
|---|---|---|
| Flattening | один большой `switch` + `state` | `br x9` по таблице |
| Bogus flow | ветви с `if (opaque)` | сравнение с константой, всегда истинное |
| Substitution | странная арифметика (`x ^ (x+1)`) | цепочки XOR/LSL/ADD |
| String enc | строки нечитаемы, есть decrypt-функция | вызов с XOR-константой |

## Что не поможет

Не стоит рассчитывать на «кнопку деобфускации»: полностью автоматического снятия OLLVM нет.
Простые скрипты спотыкаются на вложенном flattening и на комбинации с шифрованием строк.
Единственный устойчивый подход — комбинация: трассировка для потока управления, символика для
предикатов, ручная работа на небольших участках. И помните: если обфусцирован весь файл, дешевле
искать незащищённую точку входа (сетевой протокол, хранилище), чем вскрывать всё целиком.

## Вложенный flattening и как его распознать

Продвинутые обфускаторы применяют flattening несколько раз: внутри одного `case` диспетчера
прячется второй `switch`. Признак — блок с собственным `state`-подобным счётчиком и своей таблицей
переходов. Распутывать вложенность вручную почти нереально; помогает только трассировка, которая
даёт реальный порядок блоков обоих уровней сразу. Символьное исполнение здесь дорого: пространство
состояний растёт, и решатель может не завершиться за разумное время.

## Упрощение выражений вручную

При instruction substitution полезно помнить несколько тождеств:

```text
x + 1        ==  x - (-1)
x ^ (x + 1)  ==  2*x + 1        (для младшего бита — индикатор чётности)
x & 0        ==  0
(x << 2) | 1 ==  x*4 + 1
```

Найдя такое в декомпиляции, заменяем на простое. Это делают пошагово, от листьев к корню
выражения, пока не останется читаемая формула. Часто именно упрощение предикатов и есть ключ ко
всей функции.

## Инструменты и плагины

| Инструмент | Что делает |
|---|---|
| Ghidra + деобфускаторы | схлопывание диспетчера, упрощение графа |
| Frida Stalker | трассировка реального потока блоков |
| angr | символьное решение предикатов и поиск пути |
| Triton / Miasm | символьное упрощение выражений |
| Unicorn | изолированное исполнение с хуками |

Комбинация «Stalker для потока + angr для предикатов» покрывает большинство практических случаев
OLLVM. Полностью автоматические декомпиляторы OLLVM существуют, но на реальных бинарях дают
частичный результат и требуют ручной доводки.

## Чек-лист по деобфускации

- Определить приём по структуре (flattening/bogus/substitution).
- Записать реальный поток блоков (Stalker или Unicorn).
- Отбросить невыполняемые ветви.
- Упростить арифметические подстановки.
- Сверить восстановленную логику с поведением на устройстве.

## Почему деобфускация — это про стоимость, а не про «взлом»

Важно понимать цель обфускации: она не делает реверс невозможным, она повышает его цену. Пока
стоимость анализа выше ценности результата, защита работает. Для пентеста это означает, что не
всегда нужно вскрывать функцию целиком: часто достаточно понять один проверяемый факт —
принимает ли `check()` конкретный вход. Тогда вместо полной деобфускации используют динамику:
подставляют вход и наблюдают результат, обходя статический разбор вовсе. Такой «чёрный ящик» на
защищённой функции экономит часы и даёт тот же ответ.

## Практический вывод по OLLVM

Соберём всё в один рабочий подход. Сначала классифицируем защиту: flattening выдаёт себя большим
диспетчером, bogus flow — невыполняемыми ветвями, substitution — странной арифметикой. Затем
запускаем приложение под Stalker и записываем реальный порядок блоков; это самый быстрый способ
получить «скелет» логики, потому что трасса автоматически исключает мусорные ветви. После этого
упрощаем оставшиеся выражения и сверяем результат с поведением функции на устройстве. Если трасса
недоступна, включается символьное исполнение: angr проходит путь и решает предикаты. И только
когда ни трассировка, ни символика не помогают — например, при вложенном flattening — переходим к
кропотливому ручному разбору небольшого участка. Такой порядок экономит время и не даёт утонуть в
деталях, которые не влияют на итоговый ответ.

## Что мы теперь знаем

- OLLVM искажает структуру кода тремя приёмами.
- Flattening делает один switch-диспетчер.
- Bogus flow добавляет невыполняемые ветви.
- Substitution заменяет операции эквивалентными.
- Деобфускация — трассировка, символика, скрипты.
