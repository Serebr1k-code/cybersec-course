## Вопрос, с которого всё начинается

Программа читает на один байт больше, чем выделено. Часто это ничего не ломает: память
рядом занята «мусором», программа работает дальше. Но иногда там лежит чужая структура, и
программа падает — или того хуже, отдаёт данные наружу. Как поймать такую ошибку **в момент**
её совершения, а не через месяц в проде?

## Наш пример: функция копирования

Возьмём маленький C-код из нативной библиотеки:

```c
void copy_name(char *dst, const char *src) {
    for (int i = 0; i <= 8; i++) dst[i] = src[i];  // i == 8 читает за границей
}
```

Цикл идёт до `i <= 8`, то есть на последнем шаге читает девятый байт. Если `src` — строка
из 8 символов плюс терминатор, всё «работает». Ошибку не видно.

## Шаг 1: что такое санитайзер

Санитайзер — это **дополнительные проверки, которые компилятор вставляет в код**. В обычной
сборке их нет, поэтому ошибка проходит молча. Включаются флагом `-fsanitize`:

```bash
$ clang -fsanitize=address -fno-omit-frame-pointer -o libdemo.so demo.c
```

`address` — санитайзер адресов (ASan). `-fno-omit-frame-pointer` сохраняет указатели стека,
чтобы отчёт содержал понятную трассу.

## Шаг 2: ASan — память

ASan ведёт учёт того, какие участки памяти выделены. При каждом обращении он проверяет:
адрес входит в выделенную область? Если нет — печатает отчёт и завершает процесс:

```bash
$ ./demo
=================================================================
==7788==ERROR: AddressSanitizer: stack-buffer-overflow on address 0x7ffc...
READ of size 1 at 0x7ffc... thread T0
    #0 0x4012a6 in copy_name demo.c:2
```

`stack-buffer-overflow` — выход за границу буфера на стеке. Указан файл и строка. Именно так
ошибка из примера становится видимой.

## Шаг 3: UBSan — неопределённое поведение

Другой класс ошибок — **неопределённое поведение**: формально недопустимые операции, на
которые стандарт C не даёт гарантий. Например, переполнение знакового числа:

```c
int x = 2147483647;
int y = x + 1;  // переполнение знакового int
```

Компилятор может «оптимизировать» такой код непредсказуемо. UBSan сообщает о проблеме:

```bash
$ clang -fsanitize=undefined -o demo demo.c && ./demo
demo.c:2:11: runtime error: signed integer overflow: 2147483647 + 1 cannot be represented
```

## Шаг 4: комбинирование

Обычно включают несколько сразу: `-fsanitize=address,undefined`. Но есть несовместимости:
ASan и MSan (санитайзер неинициализированной памяти) вместе не работают — оба управляют
памятью. Для фаззинга стандартная связка: `fuzzer,address,undefined`.

## Шаг 5: сборка под Android

Для Android нужен NDK и указание архитектуры:

```bash
$ $NDK/toolchains/llvm/prebuilt/linux-x86_64/bin/clang \
    --target=aarch64-linux-android24 -fsanitize=address,undefined \
    -shared -o libdemo.so demo.c
```

Готовую `libdemo.so` подкладывают в APK на место оригинальной (для тестового стенда) и
запускают приложение. Отчёты ASan идут в `logcat`, где их и читают.

## Шаг 6: что важно помнить

Санитайзеры замедляют выполнение в 2–20 раз и требуют больше памяти — это инструмент
тестирования, не продакшена. В отчёте ASan адрес и стек могут быть «смазаны» оптимизацией:
собирайте с `-O1` и `-fno-omit-frame-pointer`. И помните: санитайзер находит **первую**
ошибку и останавливается, поэтому их гоняют вместе с фаззером многократно.

## Что мы теперь знаем

- Санитайзеры — компиляторные проверки, включаются `-fsanitize`.
- ASan ловит выход за границы памяти, UBSan — неопределённое поведение.
- Для фаззинга: `-fsanitize=fuzzer,address,undefined`.
- Под Android сборка идёт через NDK с `--target`.
- Отчёты читают из `logcat`; сборка с `-O1` даёт понятную трассу.

## Куда дальше

В следующем уроке — `mobile-valgrind`: анализатор, который не требует пересборки и ищет
утечки памяти в готовом бинарнике. А пока запомни: санитайзеры превращают тихие ошибки в
явные, и именно поэтому они — обязательная пара к фаззеру.

## Где пригодится

- **Пентест:** точная локализация memory-safety багов.
- **Разработка:** отлов неопределённого поведения до релиза.
- **Bug bounty:** доказательство наличия ошибки памяти.
- **CTF:** быстрый поиск причины краша.
