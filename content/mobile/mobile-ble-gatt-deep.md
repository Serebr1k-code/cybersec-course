## Задача

Мы уже умеем подключиться к BLE-устройству и увидеть его сервисы. Теперь нужно понять **структуру
GATT до конца**: где именно лежит команда, чем `read` отличается от `notify` и как отличить
безобидную характеристику от той, через которую устройство управляется.

## Данные, с которыми работаем

Возьмём таблицу GATT, снятую с носимого браслета командой `gatttool --characteristics`. В ней —
сервисы, характеристики, их handles, UUID и свойства. Этой таблицы достаточно, чтобы найти
точку управления.

## Пробуем в лоб

Наивный подход — «прочитать все характеристики». Но большинство из них только для чтения:
там батарея, версия прошивки, имя. Читать их бесполезно — команду туда не отправишь. Нужно
научиться **фильтровать по свойствам**: нас интересуют `write` и `write-without-response`.

## Приём

### Иерархия GATT

GATT — это дерево из трёх уровней:

* **Service** — логическая группа (например, «Battery Service» или vendor-сервис `fff0`).
* **Characteristic** — значение, которое можно читать/писать/слушать.
* **Descriptor** — метаданные характеристики (единицы, формат, а главное — `CCCD`, о нём ниже).

Каждый элемент адресуется **handle** — числом вида `0x0013`. Именно по handle идут операции ATT.

### Операции ATT

Протокол ATT (Attribute Protocol) определяет, что можно делать с характеристикой:

* **Read** — прочитать значение (например, уровень заряда).
* **Write Request / Write Command** — записать значение; `Write Command` не ждёт ответа.
* **Notify / Indicate** — устройство само присылает значение при изменении. `Indicate`
  требует подтверждения, `Notify` — нет.

Чтобы включить `notify`, нужно записать в специальный дескриптор **CCCD** (Client
Characteristic Configuration Descriptor, UUID `0x2902`) значение `0x0001`. Без этого уведомления
не придут — частая ошибка новичков.

### Свойства в битах

Свойства характеристики — это битовая маска:

```
0x02 = read
0x04 = write without response
0x08 = write
0x10 = notify
0x20 = indicate
```

Увидев `char properties: 0x1a` (= `0x02|0x08|0x10`), мы понимаем: характеристику можно читать,
в неё можно писать и она умеет присылать уведомления. Вот кандидат на точку управления.

## Полный прогон от начала до конца

```bash
$ gatttool -b 4A:2C:11:9F:03:1B --characteristics
handle = 0x0003, char properties: 0x02, uuid: 00002a19-...   # Battery, read
handle = 0x0012, char properties: 0x1a, uuid: 0000fff1-...   # vendor, r/w/notify
handle = 0x0016, char properties: 0x02, uuid: 0000fff2-...   # vendor, read only
```

Читаем «безопасную» характеристику и ту, что умеет писать:

```bash
$ gatttool -b 4A:2C:11:9F:03:1B --char-read -a 0x0012
Characteristic value/descriptor: 4f 4b
```

`4f 4b` — это ASCII `OK`: характеристика отдаёт статус. Теперь включаем уведомления, записав
`0100` в CCCD (handle CCCD обычно на единицу больше):

```bash
$ gatttool -b 4A:2C:11:9F:03:1B --char-write-req -a 0x0013 -n 0100 --listen
Notification handle = 0x0012 value: 53 54 41 54 55 53 3d 52 45 41 44 59
```

`STATUS=READY` — устройство само сообщило состояние. Так находят скрытые состояния, которые не
видны при обычном чтении.

Наконец, пробуем записать команду и смотрим реакцию:

```bash
$ gatttool -b 4A:2C:11:9F:03:1B --char-write-req -a 0x0013 -n 434d443d554e4c4f434b
Characteristic value was written successfully
```

Payload `43 4d 44 3d 55 4e 4c 4f 43 4b` — это ASCII `CMD=UNLOCK`. Устройство приняло команду.
Значит, `fff1` — управляющая характеристика без аутентификации.

## Если не сработало

Если запись отклоняется (`Write not permitted`), значит характеристика защищена: нужен
спаривание или подпись. Тогда проверяют:

* требуется ли `Authenticated Read/Write` (виден в свойствах как отдельные флаги);
* нет ли **bonding** — сохранённого ключа, без которого запись невозможна;
* не проверяет ли устройство поле подписи внутри payload (тогда реверс — на стороне приложения).

## Что мы теперь знаем

- GATT — дерево: сервис → характеристика → дескриптор, всё адресуется handle.
- Операции ATT: read, write, notify/indicate.
- `notify` включается записью `0100` в CCCD (`0x2902`).
- Свойства — битовая маска: `0x08` write, `0x10` notify, `0x1a` = read+write+notify.
- Управляющая характеристика — та, что принимает `write`; её payload и есть команда.

## Куда дальше

Мы научились находить точку управления в GATT. Дальше — как устроен обмен на уровне APDU у NFC:
там та же идея «команда → ответ», но с другими форматами. А пока главное: **смотри свойства,
а не названия** — команда живёт в той характеристике, в которую можно писать.

## Где пригодится

- **Пентест IoT:** поиск управляющих характеристик.
- **Анализ приложений:** понимание GATT-модели устройства.
- **CTF:** задачи на перечисление сервисов и notify-подписки.


## Шаг 4: дескрипторы и что в них лежит

Кроме CCCD, у характеристики бывают и другие дескрипторы: **User Description** (`0x2901`) с
человекочитаемым именем, **Presentation Format** (`0x2904`) с единицами и форматом числа,
**Valid Range** (`0x2906`) с допустимым диапазоном. Для пентеста важнее всего `0x2904`: он
говорит, как интерпретировать байты значения (uint8, utf8, float), и помогает не ошибиться при
разборе протокола.

```bash
$ gatttool -b 4A:2C:11:9F:03:1B --char-desc
handle = 0x0014, uuid: 00002902-...   # CCCD для fff1
```

## Шаг 5: notify против опроса

Опрос (`read` в цикле) — плохая идея: он тратит батарею и пропускает быстрые изменения. Поэтому
устройства используют `notify`. Для атакующего `notify` ценен тем, что устройство **само**
присылает внутренние события: смену состояния, ошибки, иногда отладочные строки. Подписавшись на
все notify-характеристики, можно собрать картину работы устройства без единой записи.

```bash
$ gatttool -b 4A:2C:11:9F:03:1B --char-write-req -a 0x0014 -n 0100 --listen
Notification handle = 0x0013 value: 53 54 41 54 55 53 3d 4f 50 45 4e
```

`STATUS=OPEN` — устройство сообщило состояние двери. Это уже утечка.

## Шаг 6: MTU и фрагментация

**MTU** (Maximum Transmission Unit) — максимальный размер пакета данных в BLE. По умолчанию он
маленький (23 байта, из которых на payload остаётся 20), поэтому длинные значения разбиваются на
фрагменты. В начале соединения стороны обмениваются `Exchange MTU` и могут поднять MTU до 517
байт.

Для реверса это важно: одна «команда» может прийти несколькими write-запросами, и склеивать их
надо самому. Если видишь, что payload не парсится, — проверь, не разрезан ли он по границе MTU.

## Шаг 7: запись с подписью и bonding

Некоторые устройства принимают write только после **bonding** — сохранения ключей при
спаривании. В свойствах это видно как `Authenticated Write` или как требование шифрования.
Тогда перед записью нужно выполнить спаривание, а если используется **Signed Write** — добавлять
к payload 12-байтовую подпись CSRK-ключом.

Без bonding запись вернёт `Insufficient Authentication`, и это подсказка: устройство
защищено, нужно искать путь через приложение или через уязвимость спаривания.

## Шаг 8: инструменты

Для перечисления GATT используют `gatttool`, `bluetoothctl` (команда `gatt`), `nRF Connect`
(графически) и `bettercap` (модуль `ble.recon`). `bettercap` удобен для массового обхода и
сохранения дампов. На iOS — приложения вроде LightBlue. Главное — уметь читать таблицу:
handle, UUID, properties, value.

## Шаг 9: стандартные и vendor-сервисы

Стандартные сервисы имеют фиксированные UUID из базовой части `0000xxxx-0000-1000-8000-00805f9b34fb`:
`1800` — Generic Access, `180a` — Device Information, `180f` — Battery, `180d` — Heart Rate.
Vendor-сервисы используют свой UUID (часто начинается с `fff0`) и не описаны в стандарте — именно
там лежит логика производителя.

Практическое правило: стандартные сервисы дают контекст (имя, батарея, версия), а
**vendor-сервис — цель**. Читай его характеристики, смотри свойства и разбирай payload.

## Шаг 10: аудит GATT по шагам

Полноценный аудит GATT выглядит так:

1. Перечислить все сервисы и характеристики с handles и properties.
2. Найти vendor-сервис и все его характеристики.
3. Отметить `write`/`write-without-response` — кандидаты на управление.
4. Подписаться на все `notify`/`indicate` — собрать события.
5. Попробовать записать в каждую write-характеристику и посмотреть реакцию.
6. Проверить, требуется ли bonding/шифрование.
7. Зафиксировать вывод: управляется ли устройство без аутентификации.

Каждый шаг даёт факт для отчёта. Если устройство принимает команду без спаривания — это находка
высокой критичности.

## Шаг 11: как связать GATT с приложением

Таблица GATT показывает *что можно*, но не *что делает* приложение. Чтобы связать одно с другим,
снимают HCI-лог во время работы приложения: видно, в какие handles оно пишет и какие значения.
Сопоставив лог с таблицей, получаешь карту «действие → handle → payload». Это и есть реверс
протокола.

## Шаг 12: частые ошибки в GATT

Разработчики BLE-устройств регулярно повторяют одни и те же ошибки: открывают запись в
характеристику без спаривания, хранят ключ прямо в значении характеристики, отдают отладочные
строки в read-характеристиках и не проверяют длину/формат payload. Последнее особенно опасно:
если устройство не проверяет длину, слишком длинная запись может привести к переполнению буфера на
стороне прошивки — это уже переход от логической уязвимости к памяти.

## Шаг 13: как связать notify и команды

Собирая события notify, можно восстановить конечный автомат устройства: последовательность
`STATUS=IDLE → STATUS=BUSY → STATUS=DONE` показывает, что команда принята. Так реверс GATT
превращается в реверс логики: ты понимаешь не только какие команды есть, но и в каком порядке их
шлёт приложение.
