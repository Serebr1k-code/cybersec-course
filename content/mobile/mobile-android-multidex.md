## Вопрос, с которого всё начинается

Вы ищете класс в декомпилированном коде, но его нет в `classes.dex` — он оказался в
`classes2.dex`. Что это за второй файл и почему класс не в первом?

## Наш пример: app.apk с несколькими DEX

```bash
$ unzip -l app.apk | grep dex
  classes.dex
  classes2.dex
  classes3.dex
```

Три DEX-файла. Это multidex.

## Шаг 1: лимит 64K методов

Формат DEX хранит ссылки на методы в таблице, где индекс — 16-битное число. Значит, максимум
~65536 методов на один DEX. Крупные приложения с библиотеками перерастают этот лимит. Решение —
разбить методы на несколько DEX-файлов.

## Шаг 2: как выглядит multidex

- `classes.dex` — основной, загружается системой.
- `classes2.dex`, `classes3.dex` — дополнительные, подгружаются multidex-механизмом.

Приложение объявляет `MultiDexApplication` или использует современный рантайм, который грузит
дополнительные DEX автоматически.

## Шаг 3: загрузка классов

Когда приложению нужен класс, система ищет его во всех DEX-файлах по очереди. Для аналитика это
значит: класс может быть в любом из них. Инструменты вроде JADX читают все DEX и показывают
объединённое дерево.

## Шаг 4: анализ

```bash
$ jadx -d out app.apk
$ find out/sources -name 'MyClass.java'
out/sources/com/example/MyClass.java
```

JADX сам разбирает все DEX. Но если вы патчите вручную (apktool), надо помнить, в каком именно
`smali_classesN` лежит класс — apktool создаёт отдельные папки под каждый DEX.

## Шаг 5: загрузка дополнительных DEX

На старых Android (до 5.0) дополнительные DEX приходилось грузить вручную, и это источник
проблем. На новых системах ART грузит их сам. Это влияет на динамический анализ: класс может
«появиться» только после старта.

## Шаг 6: проблемы multidex

- Класс-инициализатор в неверном DEX может не найти свои зависимости.
- Некоторые инструменты видят только `classes.dex` — код «пропадает».
- Патч не того DEX ничего не меняет.

## Шаг 7: практика

Типовой порядок: посмотреть, сколько DEX; найти нужный класс среди всех; при патче —
редактировать именно тот `smali_classesN`, где он лежит. JADX для чтения, apktool для патча.

## Что мы теперь знаем

- Лимит 64K методов на DEX порождает multidex.
- Классы распределены по classes.dex, classes2.dex и т.д.
- JADX читает все DEX и показывает объединённое дерево.
- apktool создаёт smali_classesN под каждый DEX.
- Патчить надо нужный DEX.

## Как точно узнать, сколько DEX в приложении

Самый быстрый способ — посмотреть список файлов внутри APK. DEX-файлы всегда лежат в корне
архива и называются строго по шаблону: первый — `classes.dex`, дальше `classes2.dex`,
`classes3.dex` и так далее до `classesN.dex`.

```bash
$ unzip -l app.apk | awk '{print $4}' | grep -E '^classes.*\.dex$'
classes.dex
classes2.dex
classes3.dex
```

Если видите больше одного `classes*.dex` — приложение собрано в режиме multidex. Количество
файлов — это уже полезная метрика: крупное приложение с десятком DEX почти наверняка тянет за
собой много сторонних библиотек, а значит и много «интересных» мест для анализа.

Полезно сразу прикинуть, какой DEX самый большой. Часто именно в первом лежит код приложения, а
в дополнительных — SDK и библиотеки. Но это не правило, поэтому дальше смотрим содержимое.

## Разбор заголовка DEX: где живёт счётчик методов

Чтобы понять, почему возникает лимит, заглянем в заголовок DEX-файла. DEX начинается с
сигнатуры (magic) `dex\n035\0`, дальше идут контрольная сумма, хеш, размер файла и таблица
смещений на разные секции: строки, типы, прототипы, поля, методы, классы.

```bash
$ xxd classes.dex | head -4
00000000: 6465 780a 3033 3500 4c1a 3a5c 0000 0000  dex.035.L.:\....
00000010: 0000 0000 0000 0000 7000 0000 0000 0000  ........p.......
```

Нас интересует поле `method_ids_size` — количество методов, на которые ссылается файл. Оно
хранится как 32-битное число, и само по себе может быть большим. Ограничение рождается не в
заголовке, а в **системе команд**: инструкции вида `invoke-*` адресуют метод 16-битным индексом.
16 бит — это максимум 65536 значений. Когда приложение ссылается на большее число методов,
индекс не помещается, и нужно разбивать код на несколько DEX.

Точное число можно увидеть инструментом `dexdump` из Android SDK build-tools:

```bash
$ dexdump -f classes.dex | grep -E 'method_ids_size|class_defs_size'
  method_ids_size     : 61874
  class_defs_size     : 3421
```

`method_ids_size` близко к 65536 — верный признак, что дальше пришлось добавить второй DEX.

## Практический рецепт: найти класс, если их много

Задача «где лежит класс X» решается перебором DEX. Есть три рабочих подхода, от простого к
точному.

Первый — довериться JADX: он читает все DEX и строит объединённое дерево исходников. Вы просто
ищете класс в дереве и не думаете о том, в каком файле он был.

```bash
$ jadx -d out app.apk
$ find out/sources -name 'CryptoHelper.java'
out/sources/com/example/secure/CryptoHelper.java
```

Второй — когда нужно понять привязку к конкретному DEX, распаковать APK и искать сигнатуру класса
в бинарнике. Имена классов в DEX хранятся как строки вида `Lcom/example/secure/CryptoHelper;`.

```bash
$ for d in classes*.dex; do echo "== $d"; strings "$d" | grep -m1 'Lcom/example/secure/CryptoHelper;'; done
== classes.dex
== classes2.dex
Lcom/example/secure/CryptoHelper;
```

Пусто у `classes.dex`, попадание у `classes2.dex` — класс живёт во втором файле.

Третий — для патча. `apktool` при разборе создаёт по папке на каждый DEX: `smali/`,
`smali_classes2/`, `smali_classes3/`. Класс нужно править именно в той папке, где он лежит.

```bash
$ apktool d app.apk
$ ls -d smali*
smali  smali_classes2  smali_classes3
```

## Почему DEX не только про методы: лимиты строк и типов

Лимит 64K чаще всего обсуждают применительно к методам, но у DEX есть и другие счётчики. Строки
(`string_ids`) и типы (`type_ids`) тоже адресуются индексами, и очень крупные приложения могут
упираться в них. На практике первым заканчивается лимит методов, потому что каждый вызов
добавляет запись, а строки переиспользуются.

Это важно для диагностики: если инструмент жалуется на «too many methods», но число методов в
заголовке меньше 65536, стоит проверить, не считает ли он ещё и методы из подключённых
библиотек. Сборщик (`d8`) видит всю картину целиком и решает, как резать.

## Таблица: где что искать

| Что нужно | Где смотреть | Команда |
|---|---|---|
| Сколько DEX | корень APK | `unzip -l app.apk \| grep classes` |
| Счётчик методов | заголовок DEX | `dexdump -f classes.dex` |
| Объединённое дерево | JADX | `jadx -d out app.apk` |
| Класс в конкретном DEX | бинарник | `strings classesN.dex \| grep 'Lcom/...'` |
| Папки для патча | apktool | `ls -d smali*` |

Таблица экономит время: не надо каждый раз вспоминать, какой инструмент для чего.

## Если не сработало

Если JADX не видит класс, которого вы ждёте, — проверьте, не защищён ли DEX упаковщиком: тогда
настоящий код появится только в рантайме, и статически его нет ни в одном `classesN.dex`. Это уже
тема распаковки, а не multidex.

Если `strings classes2.dex` не находит класс, хотя он должен быть, — возможно, имена обфусцированы
и класс переименован. Ищите по вызываемым системным API, а не по исходному имени.

Если apktool создал только `smali/` без `smali_classes2/`, значит на вход подали APK с одним DEX,
либо патчите не тот файл.

## Ограничения и подводные камни

Multidex решает проблему сборки, но не анализа: инструмент, который читает только `classes.dex`,
будет молча показывать неполную картину. Всегда проверяйте число DEX перед тем, как доверять
результату.

Порядок загрузки классов не гарантирует, что класс из `classes2.dex` доступен на самом раннем
этапе инициализации. Поэтому статически «всё есть», а в рантайме возможны ошибки загрузки — это
не артефакт анализа, а реальное свойство multidex.

Наконец, при патче важно помнить: если вы правите `classes.dex`, но класс лежит в
`classes2.dex`, изменения не применятся. Сверяйте привязку класса к DEX перед правкой.

## Мини-практика: инвентаризация DEX

Прежде чем читать код, полезно составить карту: сколько DEX, какие размеры, где лежит нужный
класс. Такой «паспорт» приложения экономит время и сразу выдаёт аномалии.

```bash
$ unzip -l app.apk | awk '$4 ~ /^classes.*\.dex$/ {print $1, $4}'
3812340 classes.dex
  98210 classes2.dex
   1024 classes3.dex
```

Первый DEX — 3.8 МБ, второй — 98 КБ, третий — всего 1 КБ. Третий почти пустой: возможно, там
лежит один-два класса-заглушки. Второй — небольшой набор библиотечных классов. Основной код — в
первом.

Дальше ищем класс в каждом файле:

```bash
$ for d in classes*.dex; do printf '%s: ' "$d"; strings "$d" | grep -c 'Lcom/example/app/'; done
classes.dex: 4210
classes2.dex: 12
classes3.dex: 0
```

Классы приложения в основном в первом DEX — типичная картина. Если же класс не находится ни в
одном, это повод заподозрить упаковку.

## Частые ошибки при анализе multidex

Ошибка первая — доверять инструменту, который читает только `classes.dex`. Некоторые старые
декомпиляторы видят один файл и молча показывают неполную картину. Проверяйте число DEX заранее.

Ошибка вторая — патчить класс не в том DEX. В `apktool` каждый DEX — своя папка
(`smali/`, `smali_classes2/`). Правка `smali/` не затронет класс из `smali_classes2/`, и
приложение продолжит работать по-старому. Всегда сверяйте, где лежит целевой класс.

Ошибка третья — считать порядок DEX гарантией загрузки. Порядок влияет на поиск классов, но не
даёт гарантий по времени инициализации. Класс может быть доступен статически и ещё не загружен в
рантайме.

## Как выглядит патч multidex-приложения

Типовой сценарий: обойти проверку, которая находится в классе из дополнительного DEX.

1. Находим класс и определяем его DEX (через `strings` или по папкам apktool).
2. Разбираем APK: `apktool d app.apk`.
3. Правим smali именно в `smali_classesN/`, где лежит класс.
4. Собираем обратно: `apktool b app -o patched.apk`.
5. Подписываем и ставим.

```bash
$ apktool d app.apk
$ grep -rl 'Lcom/example/secure/Check;' app/smali_classes2/ | head
app/smali_classes2/com/example/secure/Check.smali
```

Так подтверждается, что правки нужно вносить в `smali_classes2/`, а не в `smali/`. Это ровно тот
случай, когда незнание multidex приводит к «патч есть, а эффекта нет».
