## Вопрос, с которого всё начинается

Открываешь APK — а классы называются `a`, `b`, `c`, методы `a()`, `b()`, строки зашифрованы, а проверка вообще ушла в нативный код. Читать нечего. Это не случайность: приложение защищено от анализа. Какие слои защиты бывают и как подступиться к каждому?

## Наш пример: UnCrackable Level 3

Возьмём учебное приложение **UnCrackable Level 3** (OWASP MSTG). Оно специально собрано с несколькими слоями защиты: обфускация имён, нативный код, шифрование строк и проверка целостности. Разберём каждый слой на реальном коде.

## Шаг 1: переименование — ProGuard/R8

Первый и самый распространённый слой — **переименование**. Инструменты **ProGuard** и **R8** (встроен в Android-сборку) заменяют осмысленные имена классов и методов на короткие (`MainActivity` → `a`, `checkPassword` → `a`). Смысл кода при этом не меняется — меняется читаемость.

Как с этим работать:

- **Искать по строкам, а не по именам.** Строки (URL, тексты ошибок, ключи) не переименовываются, если не включено шифрование.
- **Идти от точек входа.** `MainActivity` всегда виден в манифесте — от него строим граф вызовов.
- **Смотреть сигнатуры.** Даже с именем `a` видно, что метод принимает `String` и возвращает `boolean` — это проверка.

Важно: переименование не прячет логику, оно только усложняет навигацию.

## Шаг 2: строковая обфускация

Второй слой — строки. В UnCrackable Level 3 в коде виден ключ, по которому расшифровываются строки:

```java
public class MainActivity extends AppCompatActivity {
    private static final String xorkey = "pizzapizzapizzapizzapizz";
    private native long baz();
    private native void init(byte[] bArr);
    ...
}
```

`xorkey` — это ключ для **XOR** (побитового сложения по модулю два): каждая строка в приложении зашифрована так, что при XOR с этим ключом возвращается исходный текст. XOR обратен сам себе: `(текст XOR ключ) XOR ключ = текст`. Поэтому одна и та же операция и шифрует, и расшифровывает.

Что это даёт защите: `strings` по DEX больше не показывает осмысленных строк — все они выглядят как мусор. Но ключ `pizzapizza...` лежит тут же, в открытом виде. Значит, строки можно расшифровать: либо повторить XOR локально, либо перехватить функцию расшифровки в рантайме.

## Шаг 3: нативный код

Третий слой — перенос логики в `.so`. В том же классе объявлены:

```java
private native long baz();
private native void init(byte[] bArr);
```

Реализации этих методов — в `libfoo.so`. Как их анализировать, мы разбирали в уроках про нативный реверс: искать JNI-функции (`nm -D | grep Java_`), читать дизассемблер, при необходимости хукать. Часто именно в нативном коде прячется настоящая проверка, а Java-часть только передаёт туда данные.

## Шаг 4: проверка целостности (анти-тампер)

Четвёртый слой — **анти-тампер**: приложение проверяет, что его не изменили. В UnCrackable Level 3 это делается через CRC-суммы нативных библиотек:

```java
private void verifyLibs() {
    this.crc = new HashMap();
    this.crc.put("arm64-v8a", Long.parseLong(getResources().getString(R.string.arm64_v8a)));
    ...
    ZipFile zipFile = new ZipFile(getPackageCodePath());
    for (Map.Entry<String, Long> entry : this.crc.entrySet()) {
        String str = "lib/" + entry.getKey() + "/libfoo.so";
        ZipEntry entry2 = zipFile.getEntry(str);
        Log.v(TAG, "CRC[" + str + "] = " + entry2.getCrc());
        if (entry2.getCrc() != entry.getValue().longValue()) { ... }
    }
}
```

**CRC** — контрольная сумма, короткое число, которое меняется при любом изменении файла. Приложение открывает собственный APK как ZIP, берёт `.so` для каждой архитектуры и сравнивает их CRC с эталонными значениями из ресурсов. Если ты пропатчил библиотеку — CRC изменится, и приложение поймёт, что его модифицировали.

Обход: подменить не саму проверку CRC, а её **результат** — хукнуть `verifyLibs` или метод, который реагирует на несовпадение, и не дать приложению завершиться.

## Шаг 5: динамическая загрузка и анти-Frida

Пятый слой — **динамическая загрузка**: код или DEX подгружается в рантайме (из ресурсов, из сети, расшифровывается на месте). Тогда статический анализ DEX ничего не показывает — кода там просто нет. Так поступают и упаковщики (packers): настоящий DEX зашифрован и распаковывается в память при старте.

Шестой слой — **анти-Frida/анти-debug**: приложение проверяет, не работает ли оно под инструментацией:

- ищет строку `frida` в `/proc/self/maps`;
- проверяет `TracerPid` в `/proc/self/status` (не отлаживают ли его);
- вызывает `ptrace(PTRACE_TRACEME)` — если уже под отладчиком, получит ошибку.

Обход: хук ставится **до** проверки (через `frida -f`, spawn), либо маскируется присутствие агента. Это отдельная дисциплина, ей посвящён урок `mobile-frida-detection`.

## Шаг 6: упаковщики (packers)

Отдельная категория защиты — **упаковщики**. Это инструменты, которые шифруют весь DEX и заменяют его маленьким загрузчиком. При запуске загрузчик расшифровывает настоящий DEX в память и отдаёт его виртуальной машине. В файле APK при этом лежит только загрузчик — статически кода приложения нет.

Признаки упакованного APK: в `classes.dex` мало кода, но есть класс-загрузчик и зашифрованный ресурс; в нативных библиотеках — функции распаковки. Так делают не только защитные продукты, но и создатели вредоносных приложений (банковские трояны), чтобы антивирусы не видели код.

Обход упаковки строится на **дампе памяти**: приложение всё равно расшифровывает DEX в оперативную память, и оттуда его можно выгрузить. Инструменты вроде `frida-dexdump` ищут в памяти сигнатуру DEX-файла и сохраняют найденное. Подробнее — в уроке `mobile-frida-dexdump`.

## Что мы теперь знаем

По-простому:

1. Обфускация — это слои: переименование, шифрование строк, нативный код, анти-тампер, динамическая загрузка, анти-Frida.
2. Переименование не прячет логику — ориентируйтесь на строки и точки входа.
3. Строки XOR-шифруют ключом, который часто лежит рядом.
4. Анти-тампер (CRC) проверяет неизменность APK — обходится хуком результата.
5. Динамическая загрузка объясняет, почему в DEX «нет кода».

## На что смотреть дальше

- **Не сдавайтесь на переименовании.** Это косметика, а не защита.
- **Ищите ключ строковой обфускации.** XOR-ключ почти всегда в коде.
- **Проверяйте CRC и целостность.** Патч `.so` может быть обнаружен.
- **Ставьте хуки раньше проверок.** Иначе анти-Frida обгонит вас.
- **Разделяйте слои.** Проблема может быть в строковой обфускации, а не в нативном коде — не тратьте время не на тот слой.
- **Помните про упаковщики.** Если в DEX «пусто», а приложение работает — это packer, нужен дамп памяти.
- **Слои складываются.** Переименование + строки + нативка вместе делают анализ трудоёмким, но не невозможным.
