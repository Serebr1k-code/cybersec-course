## Вопрос, с которого всё начинается

Настраиваешь прокси, ставишь свой CA-сертификат, запускаешь приложение — а в прокси тишина или ошибка сертификата. Приложение отказывается говорить по HTTPS через посредника. Это **certificate pinning**. Что он проверяет и как его снять?

## Наш пример: самоподписанный сертификат

Чтобы увидеть проблему своими глазами, поднимем локальный HTTPS-сервер с самоподписанным сертификатом и посмотрим, как клиент реагирует на него. Это модель того, что происходит, когда прокси подсовывает приложению свой сертификат.

```
$ openssl req -x509 -newkey rsa:2048 -keyout key.pem -out cert.pem \
    -days 365 -nodes -subj "/CN=api.example.com"
$ openssl x509 -in cert.pem -noout -subject -issuer -fingerprint -sha256
subject=CN=api.example.com
issuer=CN=api.example.com
sha256 Fingerprint=EA:3B:AF:8C:A1:39:D8:B6:0B:F2:58:45:76:22:91:EA:45:AC:07:0C:77:8E:BA:8C:03:E9:A4:7A:AB:1D:2C:CC
```

Сертификат самоподписанный: `subject` и `issuer` совпадают. Теперь подключимся к серверу как клиент:

```
$ openssl s_client -connect 127.0.0.1:8443 -servername api.example.com
subject=CN=api.example.com
issuer=CN=api.example.com
New, TLSv1.3, Cipher is TLS_AES_256_GCM_SHA384
Verify return code: 18 (self-signed certificate)
```

Ключевая строка — `Verify return code: 18 (self-signed certificate)`. Клиент увидел сертификат, проверил его по доверенным корням и **отверг**: подписи доверенного центра нет. Именно так ведёт себя обычный браузер и большинство клиентов.

## Шаг 1: как работает проверка TLS

Когда клиент соединяется по HTTPS, сервер присылает **сертификат** — документ с открытым ключом и подписью удостоверяющего центра (CA). Клиент проверяет:

1. подписан ли сертификат доверенным CA (из системного хранилища);
2. соответствует ли имя хоста;
3. не истёк ли срок.

Прокси (Burp, mitmproxy) работает так: он вклинивается в соединение и предъявляет клиенту **свой** сертификат, подписанный его собственным CA. Если пользователь добавил CA прокси в доверенные — проверка проходит, и прокси видит трафик. Если нет — ошибка, как `Verify return code: 18`.

## Шаг 2: что добавляет pinning

**Certificate pinning** — это дополнительная проверка: приложение не доверяет всему системному хранилищу, а требует конкретный сертификат или ключ. Даже если CA прокси добавлен в систему, приложение скажет: «этот сертификат не тот, который я ожидаю».

Варианты пиннинга:

- **Пиннинг сертификата** — приложение хранит сам сертификат (или его хэш) и сравнивает.
- **Пиннинг открытого ключа** — сравнивает публичный ключ (чаще, чем сертификат целиком).
- **Config-level pinning** — через Network Security Config в ресурсах (см. урок `mobile-network-security-config`).
- **Пиннинг в нативном коде** — проверка вынесена в `.so`, что усложняет обход.

## Шаг 3: где приложение задаёт доверие

Настройки TLS часто описаны в ресурсе `res/xml/network_security_config.xml`. Пример реального файла из открытого приложения:

```xml
<network-security-config>
    <base-config cleartextTrafficPermitted="true">
        <trust-anchors>
            <certificates src="system" />
            <certificates src="user" />
        </trust-anchors>
    </base-config>
</network-security-config>
```

Здесь `<certificates src="user" />` означает: приложение **доверяет пользовательским сертификатам**. То есть установи свой CA в систему (или как пользовательский) — и перехват заработает без обхода. Это «уязвимая» настройка, и она встречается в реальных приложениях.

Если же в файле только `src="system"`, пользовательский CA игнорируется — тогда нужен системный сертификат (root) или обход пиннинга.

## Шаг 4: обход через Frida и Objection

Самый быстрый путь — перехватить проверку сертификата. Objection делает это одной командой:

```
$ objection -g com.target.app explore
com.target.app on (android: 14) [usb] # android sslpinning disable
```

Под капотом Objection подменяет методы проверки в популярных библиотеках (`TrustManager`, `OkHttp`, `Conscrypt`) так, что они всегда возвращают «доверять». Если приложение использует стандартный стек TLS, этого достаточно.

Свой хук для `TrustManager` выглядит так:

```javascript
Java.perform(function () {
  var X509TrustManager = Java.use("javax.net.ssl.X509TrustManager");
  X509TrustManager.checkServerTrusted.implementation = function (chain, authType) {
    console.log("[*] checkServerTrusted bypassed");
    // не бросаем исключение -> сертификат "доверенный"
  };
});
```

Метод `checkServerTrusted` как раз и проверяет цепочку. Если не выбросить исключение — проверка пройдена.

## Шаг 5: патч APK

Если Frida не подходит (обнаруживается), пиннинг убирают из кода:

1. `apktool d app.apk` — распаковать.
2. Найти проверку (в smali или через Network Security Config).
3. Убрать вызовы или заменить результат.
4. `apktool b` — собрать, подписать, установить.

Минус — переподпись: приложение может проверять свою подпись (см. `mobile-integrity`). Тогда патч обнаружат.

## Шаг 6: системный сертификат

Иногда обход не нужен вовсе. Если приложение доверяет системным CA (`src="system"`), достаточно добавить CA прокси **в системное хранилище**. На Android 7+ пользовательские сертификаты приложениями не принимаются, поэтому CA ставят в системный раздел — для этого нужен root. С рутованным устройством CA кладут в `/system/etc/security/cacerts/` (или через Magisk-модуль), и перехват работает без патча приложения.

Порядок выбора метода: сначала проверьте NSC — если `src="user"`, хватит пользовательского CA; если нет — системный CA (root); если и это не помогает — Frida-хук или патч.

## Шаг 7: если пиннинг в нативном коде

Самое сложное — когда проверка сертификата реализована не в Java, а в `.so` (например, приложение использует собственный TLS-стек или нативную библиотеку вроде BoringSSL). Тогда Java-хук на `TrustManager` не сработает, потому что код вообще не вызывает Java-проверку.

Признаки: приложение использует `libssl.so`/`libcrypto.so` или собственный `.so` с TLS; строки пиннинга (хэши, домены) лежат в нативной библиотеке. Обход в этом случае:

- **Перехватить нативную функцию проверки** по имени или смещению (`Interceptor.attach` в `.so`).
- **Найти хэш/сертификат** в нативной библиотеке и подменить ожидаемое значение.
- **Хукнуть сравнение** — если приложение сравнивает хэш сертификата, перехватить `memcmp`/`strcmp` и вернуть «совпало».

Это заметно труднее Java-варианта, поэтому сначала исключают простые пути: проверьте, нет ли пиннинга в Java или в NSC, — и только потом идите в нативный код.

## Что мы теперь знаем

По-простому:

1. Прокси ломает TLS, потому что предъявляет свой сертификат; клиент его отвергает (`Verify return code: 18`).
2. Pinning — требование конкретного сертификата/ключа сверх системного доверия.
3. Network Security Config определяет, доверяет ли приложение пользовательским CA.
4. Обход: Objection/Frida (`sslpinning disable`), патч APK, системный CA.
5. Выбор метода зависит от того, как настроено доверие в приложении.

## На что смотреть дальше

- **Сначала смотрите NSC.** Часто обход не нужен — доверие уже разрешено.
- **Проверьте, где пиннинг.** Java, нативный код или конфиг — разные обходы.
- **Objection — быстрый старт.** Для стандартного TLS достаточно одной команды.
- **Помните про переподпись.** Патч APK меняет подпись, и приложение может это обнаружить.
- **Проверьте нативный TLS.** Если Java-хук молчит, пиннинг может быть в `.so`.
