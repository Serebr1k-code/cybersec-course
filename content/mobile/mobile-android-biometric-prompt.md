## Вопрос, с которого всё начинается

Приложение показывает запрос отпечатка пальца перед входом. Ты думаешь: без моего пальца
внутрь не попасть. Но если проверка — это просто вызов `onAuthenticationSucceeded`, который
переключает экран, то хук, вызывающий этот метод, открывает приложение без биометрии. Как
отличить настоящую защиту от декорации?

## Наш пример: поток биометрии

Разбираем код входа:

```java
biometricPrompt.authenticate(promptInfo,
    new BiometricPrompt.CryptoObject(cipher));
// ...
@Override public void onAuthenticationSucceeded(Result r) {
    startActivity(new Intent(this, VaultActivity.class));
}
```

Ключевой вопрос: что делает приложение в `onAuthenticationSucceeded` — использует `cipher` из
`CryptoObject` или просто открывает экран? Весь урок ведём этот пример.

## Шаг 1: что такое BiometricPrompt

**BiometricPrompt** — системный диалог проверки биометрии (отпечаток, лицо). Он изолирует
проверку: приложение не видит сам отпечаток, только результат. Диалог показывает систему, а не
приложение, — поэтому подделать его из приложения нельзя.

## Шаг 2: CryptoObject — настоящая привязка

`BiometricPrompt.authenticate` может принимать **CryptoObject** — объект `Cipher`/`Mac`,
инициализированный ключом из Keystore. Тогда ключ сгенерирован с
`setUserAuthenticationRequired(true)`, и **система** не даст использовать его без успешной
биометрии. Это настоящая защита: без пальца `cipher.doFinal()` выбросит исключение.

```java
KeyGenParameterSpec spec = new KeyGenParameterSpec.Builder("vault_key", ...)
    .setUserAuthenticationRequired(true)
    .build();
```

## Шаг 3: фальшивая защита

Если приложение создаёт `CryptoObject`, но **не использует** его результат, а просто реагирует
на callback — защита декоративная:

```java
@Override public void onAuthenticationSucceeded(Result r) {
    // cipher из r не используется; ключ не привязан
    unlockVault();
}
```

Тогда хук на `onAuthenticationSucceeded` открывает доступ. Это самая частая находка в
биометрических проверках.

## Шаг 4: обход через хук

```javascript
Java.perform(function () {
  const Cb = Java.use('androidx.biometric.BiometricPrompt$AuthenticationCallback');
  // вызываем успех, не дожидаясь биометрии
  // (в реальном скрипте — переопределение реализации колбэка)
});
```

Если после хука приложение открывает хранилище — ключ не привязан к аутентификации, и вся
защита была в UI.

## Шаг 5: проверка привязки ключа

Как понять, привязан ли ключ:
- Посмотреть параметры `KeyGenParameterSpec`: `setUserAuthenticationRequired(true)`.
- Посмотреть, используется ли `CryptoObject` (результат `r.getCryptoObject()`).
- Попробовать использовать ключ без аутентификации — должно быть исключение.

```bash
$ grep -rn 'setUserAuthenticationRequired\|CryptoObject' smali/ | head
```

## Шаг 6: ошибки привязки

- `setUserAuthenticationRequired(true)`, но ключ не используется в операции.
- `setUserAuthenticationValidityDurationSeconds` слишком большое (ключ доступен долго).
- Биометрия как «дополнительный» фактор при уже открытой сессии.
- Проверка `isDeviceSecure` вместо реальной аутентификации.
- Откат на пароль/PIN при недоступной биометрии без привязки ключа.

## Шаг 7: почему callback-проверка не защищает

Callback — это код в приложении. Всё, что живёт в приложении, можно изменить (хук, пересборка).
Защита работает только тогда, когда решение принимает система (Keystore) на основе
недоступного приложению секрета. Поэтому ключ обязан быть привязан к аутентификации.

## Шаг 8: как проверить на пентесте

1. Найти код биометрической проверки.
2. Посмотреть, есть ли `CryptoObject` и `setUserAuthenticationRequired`.
3. Если привязки нет — попробовать вызвать успех хуком.
4. Если привязка есть — попробовать использовать ключ без аутентификации.
5. Проверить длительность validity.

## Шаг 9: как защищают правильно

Ключ генерируется с `setUserAuthenticationRequired(true)`, используется через `CryptoObject` в
реальной криптооперации, привязан к StrongBox, validity минимальна. Тогда без биометрии
криптография просто не сработает, и обход callback ничего не даст. Это принцип: **секрет
защищён системой, а не UI**.

## Шаг 10: классы биометрии

Android делит биометрию на **классы**: сильная (Class 3 — отпечаток, надёжное лицо) и слабая
(Class 2 — только удобство). Для доступа к ключу нужен Class 3. Проверяют, какой класс
требует приложение: `setAllowedAuthenticators(...BIOMETRIC_STRONG)`. Если разрешён слабый класс
или откат на устройство без биометрии — защита ниже заявленной.

## Шаг 11: инвалидация при смене биометрии

Ключ можно привязать к конкретному набору отпечатков: `setInvalidatedByBiometricEnrollment(true)`
означает, что при добавлении нового отпечатка ключ перестаёт работать. Это защищает от
сценария «злоумышленник добавил свой палец». Проверяют, включён ли этот параметр: без него
новый отпечаток даёт доступ к старому ключу.

## Шаг 12: откат на PIN

Многие приложения при недоступной биометрии предлагают ввести PIN. Это нормально, **если** PIN
защищает тот же секрет через отдельный механизм. Проблема — когда откат превращается в
«биометрия или вообще без проверки». Проверяют логику отката: не открывает ли она хранилище
без реальной аутентификации.

## Шаг 13: проверка на реальном устройстве

Эмулятор не даёт настоящей биометрии, поэтому проверку делают на устройстве (или через
подмену результата системного диалога на рутованном устройстве). Практический тест: получить
`CryptoObject`, отменить диалог — операция должна упасть; вызвать успех хуком без реальной
биометрии — операция должна упасть, если привязка настоящая.

## Если не сработало

Если после хука хранилище не открывается — привязка настоящая, ключ защищён системой. Это
положительный результат аудита. Тогда переключайся на другие аспекты: класс биометрии,
инвалидацию, откат на PIN, хранение токена. И помни: биометрия — удобный, но не единственный
фактор; безопасность обеспечивает привязка ключа, а не сам диалог.
## Полный прогон: проверка привязки

**Шаг A.** Находим код биометрии и смотрим, есть ли `CryptoObject`:

```bash
$ grep -rn 'BiometricPrompt\|CryptoObject\|setUserAuthenticationRequired' smali/
```

**Шаг B.** Если `CryptoObject` создан, но результат `r.getCryptoObject()` не используется —
защита декоративная.

**Шаг C.** Ставим хук на успешный callback и проверяем, открывается ли хранилище:

```javascript
Java.perform(function () {
  // переопределяем успех без реальной биометрии
});
```

**Шаг D.** Если хранилище открылось — ключ не привязан. Если операция упала — привязка
настоящая.

**Шаг E.** Проверяем класс биометрии и инвалидацию при добавлении отпечатка.

## Частые ошибки

- Путать показ диалога с реальной защитой.
- Не проверять, используется ли `CryptoObject`.
- Забывать про класс биометрии и инвалидацию.
- Считать, что откат на PIN — всегда безопасен.
## Как это устроено внутри

Разделение здесь принципиальное: **диалог** и **секрет** — разные вещи. BiometricPrompt
показывает системный диалог и возвращает результат «аутентификация прошла». Но результат —
это просто значение в памяти приложения, а значение можно подменить. Поэтому безопасность
строится не на результате диалога, а на том, что ключ **физически не работает** без
аутентификации: Keystore отказывается выполнять операцию с таким ключом, пока пользователь не
подтвердил личность.

Это и есть смысл `CryptoObject`. Приложение инициализирует `Cipher` ключом, привязанным к
аутентификации, передаёт его в диалог, а после успеха использует **именно этот** `Cipher`.
Если ключ не привязан, `Cipher` сработает и без биометрии — и проверка окажется декорацией.
Поэтому аудит сводится к одному вопросу: используется ли результат `CryptoObject` в реальной
криптооперации, или приложение просто реагирует на callback.

Второй уровень — детали: класс биометрии (сильная против слабой), инвалидация при добавлении
нового отпечатка, минимальное окно валидности. Каждая настройка закрывает свой сценарий.
Безопасная реализация — это привязанный ключ + правильный класс + инвалидация, а не просто
«показали отпечаток пальца».
## Типичный сценарий на реальном устройстве

Аудит приложения с «хранилищем документов», вход в которое защищён отпечатком. Ты смотришь
код: диалог есть, `CryptoObject` создаётся, но результат не используется — приложение просто
открывает экран после callback. Ставишь хук на успешный callback, вызываешь его без биометрии,
и хранилище открывается. Находка доказана: проверка декоративная.

Затем ты проверяешь второй экран — ввод PIN. Там ключ действительно привязан к аутентификации,
и хук не помогает: операция падает с исключением. Это правильная реализация, и её надо
зафиксировать отдельно — не «всё плохо», а «здесь защита есть, здесь нет». В отчёте ты
показываешь разницу между двумя экранами, и рекомендация становится конкретной: использовать
результат `CryptoObject` везде, где сейчас проверка ограничивается callback. Такой аудит
требует root или тестовой сборки, но не требует обхода реальной биометрии — и это важно
подчеркнуть, потому что защита должна держаться без неё.
## Что важно не перепутать

Не путай **показ биометрического диалога** и **привязку ключа к аутентификации**: первое — UI,
второе — криптографическая гарантия. Не путай **callback** и **CryptoObject**: callback — это
код приложения, который можно подменить; `CryptoObject` — это операция с ключом, которую
подменить нельзя. И не путай **класс биометрии**: слабая биометрия подходит для удобства, но не
для защиты секретов. В аудите вывод делается по одному вопросу: сработает ли криптооперация без
биометрии. Если да — защита декоративная, сколько бы диалогов ни показывалось; если нет —
привязка настоящая, независимо от того, как выглядит интерфейс.
## Итоговая мысль

Биометрия защищает только тогда, когда за ней стоит ключ, привязанный к аутентификации.
Диалог, callback и «зелёная галочка» — это интерфейс, и его можно подменить. Настоящая защита
проверяется одним вопросом: сработает ли криптооперация без биометрии. Если нет — реализация
правильная, независимо от деталей UI; если да — это декорация, и в отчёте так и надо написать.
## Что мы теперь знаем

- BiometricPrompt показывает системный диалог проверки.
- Настоящая привязка — через CryptoObject и ключ с auth-required.
- Проверка только в callback обходится хуком.
- Признак привязки — использование результата CryptoObject.
- Правильно — ключ привязан к аутентификации в Keystore/StrongBox.
