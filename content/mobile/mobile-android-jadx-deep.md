## Вопрос, с которого всё начинается

В прошлом уроке вы декомпилировали APK в JADX и вручную искали секреты. Но приложение большое:
тысячи классов, обфусцированные имена `a.a.a`, и глазами такое не пролистать. Как превратить
JADX из «просмотрщика» в инструмент, который сам находит нужное? Разберём продвинутую работу
с JADX.

## Наш пример: приложение app.apk

Берём один APK и ведём его через весь урок. Сначала базовый прогон в командной строке — это
воспроизводимее, чем клики в GUI:

```bash
$ jadx -d out app.apk
INFO - loading ...
INFO - processing ...
INFO - done
```

`jadx` — декомпилятор DEX (формата байткода Android) обратно в читаемый Java. Флаг `-d out`
задаёт папку вывода. Результат — дерево `out/sources/**.java` плюс `out/resources/`.

## Шаг 1: что именно мы получили

```bash
$ find out/sources -name '*.java' | wc -l
1843
```

1843 файла — вручную не пройти. Ключевой вопрос: как быстро сузить область до интересного
кода? Ответ — текстовая индексация: ищем по декомпилированному дереву обычным `grep`.

## Шаг 2: поиск по коду вместо кликов

```bash
$ grep -rn -E 'password|apiKey|secret|Bearer ' out/sources --include='*.java' | head
out/sources/com/example/net/Api.java:41:  private String apiKey = "AKIA-EXAMPLE-PLACEHOLDER";
out/sources/com/example/auth/Login.java:88:  body.put("password", md5(pass));
```

Мы нашли хардкод-ключ и точку, где формируется логин. Такой поиск работает на порядок быстрее
любого GUI. Второй полезный запрос — по URL и доменам:

```bash
$ grep -rhoE 'https?://[a-zA-Z0-9./_-]+' out/sources | sort -u
https://api.example.com/v1
https://cdn.example.com/static
```

## Шаг 3: деобфускация имён

Обфусцированный код читается плохо: `a.b.c(1,2)`. JADX умеет переименовывать сущности обратно
в осмысленные (`--deobf` — от «de-obfuscate»):

```bash
$ jadx --deobf -d out_deobf app.apk
```

Для полей/методов, где восстановление невозможно, JADX даёт синтетические имена вроде
`f1234a`. Часто полезнее не имена, а структура: какие классы вызывают `crypto`-API.

## Шаг 4: битый байткод и --show-bad-code

Иногда декомпилятор не может построить корректный Java-код (сложные `goto`, оптимизации).
Тогда JADX по умолчанию скрывает такой код. Флаг `--show-bad-code` заставляет показать
частично декомпилированный результат — лучше кривой, чем ничего:

```bash
$ jadx --show-bad-code -d out_bad app.apk
```

## Шаг 5: скрипты JADX (автоматизация)

Ручной `grep` хорош, но JADX умеет исполнять скрипты на Java API и ходить по всем классам
программно. Пример скрипта, который печатает все методы с «decrypt» в имени:

```java
import jadx.api.*;
public class FindDecrypt implements IJadxScript {
  public void run(JadxDecompiler jadx) {
    for (JavaClass cls : jadx.getClasses())
      for (JavaMethod m : cls.getMethods())
        if (m.getName().toLowerCase().contains("decrypt"))
          System.out.println(m.getFullName());
  }
}
```

Запуск:

```bash
$ jadx --script FindDecrypt.java app.apk
com.example.crypto.CipherUtil.decrypt(String, byte[])
com.example.net.Payload.unwrap(byte[])
```

Теперь мы знаем точные имена точек расшифровки — дальше их можно хукать Frida или разбирать
вручную. Скрипт можно расширить: обход строковых констант, поиск вызовов `Runtime.exec`,
`socket`, `loadLibrary`.

## Шаг 6: плагины

Кроме скриптов есть плагины, которые встраиваются в GUI и добавляют панели. Полезный приём —
плагин, который показывает кросс-ссылки (кто вызывает метод). При анализе это отвечает на
вопрос «где эта функция реально используется», без ручного поиска.

## Шаг 7: ограничения

JADX декомпилирует Java/DEX, но **не** трогает нативный код (`lib/*.so`) — для него нужен
Ghidra/IDA. Также JADX не исполняет код: строки, расшифрованные в рантайме, он не покажет.
Поэтому статику JADX всегда дополняют динамикой.

## Что мы теперь знаем

- JADX декомпилирует DEX в Java-дерево.
- `--deobf` восстанавливает имена, `--show-bad-code` не прячет кривой код.
- `grep` по дереву быстрее ручного просмотра.
- Скрипты на Java API автоматизируют поиск.
- Нативный код JADX не покрывает.

## Как JADX показывает код: Java, smali и fallback

JADX по умолчанию отображает декомпилированный **Java**. Но декомпиляция — не восстановление исходника: это перевод байткода в приблизительный Java-эквивалент. Иногда перевод неоднозначен, и JADX показывает либо `bad code` (если разрешён флагом), либо «fallback» — фрагмент в smali-подобном виде прямо внутри Java-метода.

Полезно уметь переключаться. В GUI есть вкладки Smali и Java для одного и того же метода: Java читается легче, smali точнее отражает реальные инструкции. Когда Java-версия «странная» (например, `while(true)` с непонятным выходом), смотрите smali — там видно, что за ветвление компилятор реально сгенерировал.

Ещё одна особенность: JADX может показывать **синтетические** методы (`access$000`, `lambda$...`), которые появились из-за замыканий и внутренних классов. Они не обфускация, а побочный продукт компиляции — не путайте их с намеренно запутанным кодом.

## Regex-коллекция для аудита

Текстовый поиск по дереву — главный инструмент. Держите под рукой набор запросов:

```bash
# секреты и ключи
grep -rnE 'AKIA[0-9A-Z]{16}|AIza[0-9A-Za-z_-]{35}|sk_live_[0-9a-zA-Z]{24}' out/sources
# пароли в открытом виде
grep -rnE '(password|passwd|pwd)\s*=\s*"' out/sources
# endpoint'ы и домены
grep -rhoE 'https?://[a-zA-Z0-9./_-]+' out/sources | sort -u
# опасные вызовы
grep -rnE 'Runtime\.getRuntime|ProcessBuilder|loadLibrary|exec\(' out/sources
# криптография
grep -rnE 'Cipher\.getInstance|MessageDigest|SecretKeySpec' out/sources
```

Каждый запрос отвечает на свой вопрос: где лежат секреты, куда ходит приложение, что оно исполняет и как шифрует. Пропускать через такой «частокол» стоит всё дерево, а не отдельные файлы.

| Цель поиска | Ключевые слова |
|-------------|----------------|
| Секреты | `apiKey`, `secret`, `token`, `AKIA`, `AIza` |
| Сеть | `http://`, `https://`, `OkHttp`, `Retrofit` |
| Опасные вызовы | `exec`, `ProcessBuilder`, `loadLibrary` |
| Крипто | `Cipher`, `MessageDigest`, `KeyStore` |
| Хранилище | `SharedPreferences`, `getExternalStorage` |

## Полноценный JADX-скрипт

Скрипт на Java API может сделать то, что grep не умеет: пройти по всем классам и проверить структуру. Пример, который собирает все строковые константы, похожие на ключи, и все вызовы исполнения:

```java
import jadx.api.*;
public class Audit implements IJadxScript {
  public void run(JadxDecompiler jadx) {
    for (JavaClass cls : jadx.getClasses()) {
      for (JavaMethod m : cls.getMethods()) {
        String src = m.getCodeStr();
        if (src == null) continue;
        if (src.contains("Runtime.getRuntime") || src.contains("ProcessBuilder"))
          System.out.println("EXEC: " + m.getFullName());
        if (src.matches("(?s).*AKIA[0-9A-Z]{16}.*"))
          System.out.println("KEY : " + m.getFullName());
      }
    }
  }
}
```

Запуск — `jadx --script Audit.java app.apk`. Такой скрипт прочёсывает всё приложение за секунды и выдаёт короткий отчёт. Преимущество перед grep в том, что он привязан к структуре (метод, класс), а не к строкам файла.

## Reference: флаги jadx

| Флаг | Назначение |
|------|------------|
| `-d DIR` | папка вывода |
| `--deobf` | деобфускация имён |
| `--show-bad-code` | показывать кривой код |
| `--no-res` | не декодировать ресурсы |
| `--no-src` | не декомпилировать код |
| `--script FILE` | выполнить скрипт |
| `--single-class NAME` | только один класс |
| `--escape-unicode` | экранировать Unicode |

## Обфускация ProGuard/R8 и обход

Большинство Android-приложений проходят через ProGuard/R8, которые переименовывают классы в `a`, `b`, `c` и удаляют неиспользуемый код. JADX `--deobf` пытается восстановить имена по сигнатурам (например, по наследованию от известных классов), но часто бессилен.

Практический обход: **искать не по именам, а по поведению**. Строки, URL, вызовы системных API остаются узнаваемыми даже при обфускации имён. Если найдёте строку `"https://api.example.com"`, переходите по ссылке на константу в классе `a.b.c` — имя неважно, важно, что этот класс делает. Дополнительно помогает сопоставление с необфусцированными версиями приложения (если есть) и анализ по стеку вызовов от `onCreate`.

## GUI против командной строки

GUI удобен для навигации: перейти к определению, посмотреть xrefs, почитать smali. Но он не масштабируется на тысячи классов. CLI выигрывает в воспроизводимости и автоматизации: результат `jadx -d out` можно проиндексировать, залить в редактор, прогнать grep и скрипты. Рабочий приём — сначала CLI-прогон и grep, затем открыть в GUI только найденные точки для детального разбора.

## Если не сработало

- **JADX падает на декомпиляции.** Ограничьте область: `--single-class` для подозрительного класса; отключите ресурсы (`--no-res`), чтобы изолировать проблему.
- **Метод отсутствует.** Он может быть нативным (в `.so`) или удалён R8 как неиспользуемый. Проверьте `lib/` и вызывающие методы.
- **Строки не находятся.** Они могут собираться в рантайме или храниться в нативном коде. Нужна динамика (Frida).
- **`--deobf` не помог.** Имена восстановить невозможно — ищите по поведению и строкам.
- **Java-код не компилируется при пересборке.** Это ожидаемо: JADX не гарантирует компилируемость. Для патча используйте apktool/smali.

## Ограничения подхода

JADX даёт статическую картину, но не исполняет код. Любая логика, зависящая от рантайма (расшифровка строк, динамическая загрузка, отражение), останется скрытой. Поэтому статический разбор JADX — это карта, а не полное описание: он указывает, куда смотреть динамически.

## Быстрая сортировка находок

Когда находок много, полезно раскладывать их по категориям прямо по ходу разбора: секреты, сетевые точки, опасные вызовы, крипто-API. Ведите отдельный файл-журнал и записывайте туда полный путь до метода и строку-улику. Через час работы такой журнал сэкономит вам повторный обход дерева и станет основой отчёта: по нему видно, что именно вы проверили и что осталось непокрытым.

## Куда дальше

JADX даёт нам Java-код, но пересобрать изменённое приложение он не умеет. Дальше разберём
apktool — инструмент, который разбирает APK до smali и собирает обратно, чтобы патчить
поведение приложения.

- CTF по мобильному реверсу.
