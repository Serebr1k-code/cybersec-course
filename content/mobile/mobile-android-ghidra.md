## Вопрос, с которого всё начинается

Приложение проверяет что-то в нативном коде: в APK лежит `lib/arm64-v8a/libcheck.so`. JADX его
не разбирает, `strings` показывает только обрывки. Логика «зашита» в машинный код. Как её
прочитать? Нужен дизассемблер, понимающий ARM64.

## Наш пример: libcheck.so

Начинаем с базового осмотра файла:

```bash
$ file libcheck.so
libcheck.so: ELF 64-bit LSB shared object, ARM aarch64, dynamically linked
$ nm -D libcheck.so | grep Java
0000000000012a40 T Java_com_example_NativeChecker_check
```

`nm -D` показывает динамические символы. Символ с префиксом `Java_` — это **JNI**-функция:
мост между Java-кодом приложения и нативной библиотекой. JNI (Java Native Interface) — механизм,
через который Java вызывает нативный код. Имя `Java_com_example_NativeChecker_check`
кодирует пакет, класс и метод, который её вызывает.

## Шаг 1: импорт в Ghidra

Ghidra — бесплатный дизассемблер/декомпилятор от NSA. Создаём проект, импортируем `.so`,
соглашаемся на автоанализ. Ghidra определит архитектуру (AArch64) и найдёт функции.

## Шаг 2: находим JNI-функции

В Ghidra открываем Symbol Tree, ищем `Java_com_example_NativeChecker_check`. Именно эта функция
вызывается из Java. Декомпилированный вид (C-подобный псевдокод):

```c
undefined8 Java_com_example_NativeChecker_check(JNIEnv *env, jobject thiz, jstring input) {
  char *s = (*env)->GetStringUTFChars(env, input, 0);
  int ok = strcmp(s, "nto-example");
  return ok == 0;
}
```

Это упрощённый пример, но идея ясна: Ghidra восстановила логику — сравнивается строка. Реальные
проверки сложнее (хеши, шифрование), но подход тот же.

## Шаг 3: понимаем JNI-аргументы

Первый аргумент JNI-функции — `JNIEnv*` (таблица функций для работы с Java-объектами), второй —
`jobject`/`jclass` (сам объект), дальше идут аргументы Java-метода. В Ghidra типы этих
параметров часто «сырые», их полезно переопределить, чтобы декомпиляция читалась лучше.

## Шаг 4: строки и константы

Ghidra показывает ссылки на строки. Если строка «спрятана» (зашифрована), в декомпиляции
увидим вызов функции расшифровки — тогда переходим к ней и разбираем алгоритм. Полезно
использовать `Search > For Strings` и смотреть, кто на них ссылается (xref).

## Шаг 5: headless-режим

Ручной клик по каждой функции не масштабируется. Ghidra умеет работать без GUI:

```bash
$ analyzeHeadless /tmp/proj proj -import libcheck.so -postScript FindCheck.java
```

`analyzeHeadless` — консольный запуск анализа. `-postScript` выполняет скрипт после импорта.
Скрипт на Python (Ghidra API) может, например, напечатать все функции, вызывающие `strcmp`:

```python
# FindCheck.py (Ghidra)
for f in currentProgram.getFunctionManager().getFunctions(True):
    if 'check' in f.getName().lower():
        print(f.getName(), f.getEntryPoint())
```

## Шаг 6: подтверждение через Frida

Статика даёт гипотезу, динамика — подтверждение. Найденный адрес проверки хукаем Frida:

```javascript
var base = Module.findBaseAddress('libcheck.so');
Interceptor.attach(base.add(0x12a40), {
  onLeave: function (retval) { retval.replace(1); }
});
```

Так проверка всегда возвращает «успех» — мы подтвердили, что именно эта функция решает исход.

## Шаг 7: где Ghidra не идеальна

Декомпилятор восстанавливает логику приблизительно: типы могут быть неверны, оптимизации
запутывают поток. Для обфусцированного кода (OLLVM) читаемость падает — там помогают трассировка
и эмуляция.

## Что мы теперь знаем

- Нативный код Android лежит в `lib/*.so` и требует дизассемблера.
- JNI-функции видны по префиксу `Java_` в символах.
- Ghidra декомпилирует ARM64 в читаемый псевдокод.
- `analyzeHeadless` + скрипты автоматизируют анализ.
- Гипотезу из Ghidra подтверждают Frida-хуком.

## Регистрация JNI-функций: статическая и динамическая

Префикс `Java_` — это статическая регистрация: линкер сам сопоставляет имя символа с Java-методом. Но существует и **динамическая** регистрация через `RegisterNatives`. В этом случае имена символов не содержат `Java_`, и `nm -D` покажет, например, `native_check` или вообще ничего. Разберём, как её найти:

```c
static JNINativeMethod methods[] = {
  {"check", "(Ljava/lang/String;)Z", (void*)native_check},
};
(*env)->RegisterNatives(env, clazz, methods, 1);
```

В `JNI_OnLoad` (или при инициализации класса) приложение вызывает `RegisterNatives`, передавая массив `JNINativeMethod`. Каждая запись — тройка (имя Java-метода, сигнатура, указатель на нативную функцию). В Ghidra ищем xref на `RegisterNatives`: функция, которая её вызывает, передаёт указатель на таблицу. Кликнув по нему, видим массив — и оттуда переходим к настоящей реализации.

Это важный навык: если `nm -D | grep Java` пуст, не делаем вывод «нативного кода нет». Проверяем `JNI_OnLoad` и `RegisterNatives`.

## Чтение дескрипторов типов

Сигнатура `(Ljava/lang/String;)Z` — это JNI-дескриптор. `L...;` означает объект класса, `Z` — boolean, `I` — int, `[B` — массив байт. В Ghidra эти типы не всегда восстановлены: параметр, который на деле `jstring`, может отображаться как `long`. Улучшаем декомпиляцию, вручную задав тип параметра через `Edit Function Signature`. После этого вызовы вроде `GetStringUTFChars` читаются осмысленно: видно, что первый аргумент — `JNIEnv*`, второй — строка.

Таблица базовых дескрипторов:

| Дескриптор | Java-тип | В JNI |
|------------|----------|-------|
| `Z` | boolean | `jboolean` |
| `I` | int | `jint` |
| `J` | long | `jlong` |
| `F` | float | `jfloat` |
| `D` | double | `jdouble` |
| `Ljava/lang/String;` | String | `jstring` |
| `[B` | byte[] | `jbyteArray` |
| `[I` | int[] | `jintArray` |

## Навигация в Ghidra: ускоряем разбор

Ручной обход графа вызовов быстро утомляет. Полезные приёмы:

- `Ctrl+Shift+F` — Search For Strings, найти проверочную строку.
- Правый клик по символу → `References → Show References to` — кто вызывает функцию.
- `G` — переход к адресу; удобно для перехода по offset из Frida.
- `L` — переименовать функцию или переменную, чтобы декомпиляция читалась.
- `Ctrl+Shift+E` — Edit Function Signature (исправить типы).
- `Window → Decompiler` — синхронизированный C-вид рядом с дизассемблером.

## Worked example: обход проверки лицензии целиком

Соберём полный сценарий, как это делается на реальном задании. Дано: приложение при запуске вызывает нативную `checkLicense`; без правильного ключа показывается экран «trial expired».

1. Распаковываем APK и находим библиотеку: `unzip -l app.apk | grep '\.so'`.
2. Берём arm64-вариант: `unzip -o app.apk 'lib/arm64-v8a/*' -d out/`.
3. Смотрим символы: `nm -D out/lib/arm64-v8a/liblicense.so | grep -i check`.
4. Импортируем в Ghidra, находим функцию, смотрим декомпиляцию.
5. Видим ветвление: `if (result == 0) return 1; else return 0;`.
6. В Frida хукаем на возврат и подменяем значение.

После шага 5 статическая гипотеза есть. Шаг 6 её подтверждает: если после хука экран trial исчез — мы нашли нужную функцию.

## Работа с обфускацией и stripped-бинарниками

Иногда символов нет вовсе (`nm -D` пуст, таблица `.dynsym` урезана). Тогда:

- ищем строки-подсказки (`grep -a` по бинарнику или Search For Strings);
- идём от точек входа JNI (`JNI_OnLoad`) и от `RegisterNatives`;
- анализируем, какие функции читают ввод пользователя (передаётся `jstring`).

OLLVM дополнительно разбивает поток на «диспетчер + блоки», добавляет непрозрачные предикаты. Ghidra всё ещё покажет логику, но читать её придётся по частям: сначала понять диспетчер состояния, затем — блоки.

## Если не сработало

- **Функция вызывается не из Java.** Проверка может быть целиком в C, вызвана из нативного кода. Ищите вызовы от `JNI_OnLoad`.
- **Строка собирается в рантайме.** `strcmp` со «спрятанной» строкой бесполезен — ищите функцию расшифровки и разбирайте её алгоритм.
- **Проверка размазана.** Итог зависит от нескольких функций; хук одной не помогает. Хукайте все подозрительные и смотрите, какая меняет поведение.
- **Frida не видит модуль.** Библиотека загружается позже; ставьте `Java.perform` и ждите `dlopen` через `frida -f ... --no-pause`.

## Ограничения подхода

Статический разбор даёт понимание, но не доказательство: декомпилятор может ошибиться в границах ветвлений. Динамический хук даёт факт, но требует root или эмулятора. Наиболее надёжный путь — совмещать: гипотеза из Ghidra, подтверждение в Frida, финальная проверка повторным запуском с реальным ключом.

## Шпаргалка по JNI-функциям окружения

При чтении декомпилированной JNI-функции полезно держать под рукой, что делает каждая функция окружения:

| Функция JNIEnv | Назначение |
|----------------|------------|
| `GetStringUTFChars` | получить указатель на UTF-8 строку Java |
| `ReleaseStringUTFChars` | освободить буфер после использования |
| `GetStringUTFLength` | длина строки в байтах |
| `NewStringUTF` | создать Java-строку из C-строки |
| `GetByteArrayElements` | доступ к элементам `byte[]` |
| `FindClass` | найти класс по имени |
| `GetMethodID` | получить id метода для вызова |
| `CallBooleanMethod` | вызвать Java-метод, вернуть boolean |

Когда в декомпиляции видна пара `GetStringUTFChars` → работа → `ReleaseStringUTFChars`, перед нами почти наверняка обработка пользовательского ввода. Это самый короткий путь от «сырого» псевдокода к пониманию назначения функции.

## Полезный паттерн Frida-скрипта

Чтобы не подбирать offset вручную, привязываемся к экспортируемому символу, а не к адресу:

```javascript
Java.perform(function () {
  var Checker = Java.use('com.example.NativeChecker');
  Checker.check.implementation = function (s) {
    console.log('input=' + s);
    var r = this.check(s);
    console.log('result=' + r);
    return true;
  };
});
```

Если проверка целиком в C и не экспонирована как Java-метод, остаётся `Interceptor.attach` по адресу, вычисленному от базы модуля. Адрес базы надёжнее брать через `Module.findBaseAddress('libcheck.so')`, а не хардкодить — ASLR каждый раз меняет раскладку.

## Сверка статики и динамики

Финальная проверка гипотезы строится на воспроизводимости. Если после подмены возврата приложение ведёт себя как «лицензия валидна», а до неё — как «trial», значит найденная функция действительно управляет исходом. Если поведение не меняется, значит проверок несколько или исход решает другая ветка — возвращаемся к графу вызовов в Ghidra и ищем остальные точки `strcmp` или сравнения хешей.
