## Вопрос, с которого всё начинается

Мы запустили свой код. Но пользователь перезагрузит телефон — и код исчезнет. Значит,
нужен способ **закрепиться**: чтобы после перезагрузки, обновления и смены сети код
запускался снова. Это и называется персистентностью. У Android для неё есть много
легальных механизмов, и все они доступны малвари.

## Наш пример: приложение, которое просыпается после перезагрузки

Возьмём образец, который после установки ничего не делает, а через минуту после
перезагрузки начинает отправлять данные. Посмотрим, как он это устроен.

## Шаг 1: BOOT_COMPLETED — классика

Самый известный механизм — широковещательное сообщение `BOOT_COMPLETED`, которое
система рассылает после загрузки. Приложение объявляет receiver в манифесте:

```xml
<receiver android:name=".BootReceiver" android:exported="true">
  <intent-filter>
    <action android:name="android.intent.action.BOOT_COMPLETED"/>
  </intent-filter>
</receiver>
```

И просит разрешение `RECEIVE_BOOT_COMPLETED`. После загрузки система вызывает
`onReceive`, и код стартует сам. Это первое, что ищут при анализе.

```bash
$ aapt dump xmltree sample.apk AndroidManifest.xml | grep -i boot
A: android:name="android.intent.action.BOOT_COMPLETED"
```

## Шаг 2: foreground-сервис

Второй слой — **foreground-сервис**: сервис с постоянным уведомлением. Система не
убивает его так агрессивно, а пользователь видит иконку. Малварь либо маскирует
уведомление под системное, либо делает его максимально неприметным. Ключевой признак в
коде — вызов `startForeground` с типом сервиса.

## Шаг 3: JobScheduler и WorkManager

Третий путь — отложенные задачи. `JobScheduler` позволяет попросить систему запустить
работу при определённом условии: «когда появится сеть», «раз в час», «когда устройство
простаивает». Для системы это законная оптимизация батареи, для малвари — способ
просыпаться без явного автозапуска.

```bash
$ adb shell dumpsys jobscheduler | grep -i sample
  JobInfo #1: com.evil.sample/.SyncJob
```

Если приложение без причины держит периодические job'ы — это повод присмотреться.

## Шаг 4: accessibility и device admin

Более агрессивные механизмы требуют действия пользователя, но дают огромные права.

* **Accessibility Service** — читает экран и нажимает кнопки. Формально для
  доступности, фактически — полный контроль над UI: перехват паролей, нажатия,
  подтверждение платежей.
* **Device Admin / Device Owner** — управляет политиками: блокировка, стирание,
  запрет удаления приложения.

```xml
<service android:name=".A11yService" android:permission="android.permission.BIND_ACCESSIBILITY_SERVICE">
  <intent-filter><action android:name="android.accessibilityservice.AccessibilityService"/></intent-filter>
</service>
```

Малварь просит включить эти службы, маскируя запрос под «ускорение» или «оптимизацию».

## Шаг 5: как обнаруживать

При анализе образца смотри на четыре вещи:

1. Есть ли `BOOT_COMPLETED` и другие автостартовые действия в манифесте.
2. Не запускается ли foreground-сервис с подозрительным уведомлением.
3. Нет ли периодических job'ов без понятной причины.
4. Не просит ли приложение accessibility/device admin.

```bash
$ adb shell dumpsys activity services | grep -i sample
$ adb shell dumpsys device_policy | grep -i sample
```

Эти четыре проверки покрывают большинство реальной персистентности.

## Скрытая персистентность: account authenticator и alarm

`BOOT_COMPLETED` — самый заметный механизм, поэтому продвинутая малварь использует
менее очевидные. Один из них — **Account Authenticator**: приложение регистрирует
свой тип аккаунта, и система периодически синхронизирует его. Синхронизация запускает
код приложения без явного автозапуска.

```xml
<service android:name=".SyncAdapterService">
  <intent-filter><action android:name="android.content.SyncAdapter"/></intent-filter>
</service>
```

Второй механизм — **AlarmManager** с повторяющимся будильником. Приложение ставит
точное время, и система будит его даже после перезагрузки, если будильник сохранён.
Это выглядит как обычная функция напоминаний, но используется и для закрепления.

```bash
$ adb shell dumpsys alarm | grep -i sample
RTC_WAKEUP #0: Alarm{... com.evil.sample}
```

Третий, самый изощрённый путь — **override pending intent** и переиспользование чужих
задач. Он реже, но тоже встречается.

Вывод для аналитика: не ограничивайся `BOOT_COMPLETED`. Смотри на весь набор
автозапуска — receivers, services, sync adapters, alarms, jobs. Чем меньше механизм
заметен пользователю, тем охотнее его используют.

## Что проверить на реальном устройстве

Собери полную картину автозапуска с устройства, где образец установлен. Посмотри по
очереди receivers, services, jobs и alarms:

```bash
$ adb shell dumpsys activity broadcasts | grep -i sample
$ adb shell dumpsys jobscheduler | grep -i sample
$ adb shell dumpsys alarm | grep -i sample
$ adb shell dumpsys device_policy | grep -i sample
```

Если хотя бы в одном из списков есть образец — механизм найден. Сопоставь его с
манифестом: там видно, какие действия заявлены, а какие разрешения запрошены.

И проверь, что происходит после перезагрузки. Наблюдение «до и после reboot» —
самое убедительное доказательство персистентности: процесс снова поднялся, сеть снова
пошла, данные снова ушли.

## Типичное заблуждение: удалил приложение — и всё

Кажется, что удаление пакета убирает весь его код. На практике остаются следы, которые
продолжают влиять на устройство. Во-первых, **отложенные alarms и jobs** могут жить
некоторое время после удаления, если система ещё не почистила очередь. Во-вторых,
**device admin** и **accessibility** иногда требуют явного отключения: пока политика
активна, удаление может быть заблокировано. В-третьих, данные и кэш могут остаться в
общих каталогах, доступных другим приложениям.

Поэтому при реагировании на инцидент недостаточно удалить пакет. Надо проверить, не
осталось ли активных политик, не зарегистрирован ли sync-адаптер, не висит ли будильник.
Только после этого можно считать закрепление снятым.

Есть и обратный случай: приложение удалили, но вредоносный код уже **вынес себя** в
другой процесс — например, записал dex и запускает его динамически. Тогда удаление
основного пакета ничего не меняет: закрепление живёт в другом месте. Это редкий, но
вполне реальный сценарий, и он подчёркивает главное правило: персистентность ищут не
по одному пакету, а по всей картине автозапуска устройства.

Правило простое: персистентность ищут по устройству целиком, а не по одному пакету, и снимают её так же — проверяя каждый механизм закрепления по отдельности, а не только удаляя приложение.

## Итог по персистентности

Персистентность — это не один трюк, а целый набор легальных механизмов Android, каждый
из которых по отдельности выглядит безобидно: автозапуск после загрузки, фоновая служба,
отложенная задача, синхронизация аккаунта, будильник. Вместе они образуют прочную сеть,
и именно поэтому защита строится не на поиске «главного» механизма, а на инвентаризации
всех. При анализе образца выписывай каждый механизм закрепления, при реагировании —
снимай их по очереди, а не только удаляй пакет. Только полная картина автозапуска даёт
уверенность, что код действительно больше не поднимется.

## Что мы теперь знаем

- `BOOT_COMPLETED` — базовый автозапуск после загрузки.
- Foreground-сервисы живут дольше и маскируются под системные уведомления.
- JobScheduler просыпает код по условиям, не требуя явного автозапуска.
- Accessibility и device admin дают максимум прав, но требуют согласия пользователя.
- Обнаружение строится на манифесте и `dumpsys` по сервисам, job'ам и политикам.

## Куда дальше

Мы умеем и поднимать права, и удерживаться. Дальше логично разобрать **системные
приложения** — привилегированный слой, который атакуют в первую очередь. А пока
запомни: **персистентность на Android — это набор легальных механизмов, и защита
начинается с их инвентаризации**.
