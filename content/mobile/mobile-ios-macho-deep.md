## Вопрос, с которого всё начинается

У вас есть `Payload/MyApp.app/MyApp` — исполняемый файл из IPA. Это уже не текст и не классы,
а машинный код. Но прежде чем что-то в нём искать, нужно понять **карту файла**: где лежит код,
где строки, где подпись, какие библиотеки он подгружает. Без этой карты отладчик и хукер будут
работать вслепую. Разберём формат Mach-O — контейнер iOS-бинарников — на одном файле.

## Наш пример: исполняемый файл из IPA

Распакуем IPA и посмотрим на бинарник:

```bash
$ unzip -o MyApp.ipa -d app >/dev/null
$ file app/Payload/MyApp.app/MyApp
app/Payload/MyApp.app/MyApp: Mach-O 64-bit executable arm64
```

`Mach-O` — это формат исполняемого файла Apple (как ELF на Linux, PE на Windows). `arm64` —
архитектура процессора. Мы будем вести этот файл через весь урок: от заголовка до подписи.

## Шаг 1: заголовок и магические байты

Любой Mach-O начинается с **заголовка** (`mach_header_64`). Первое поле — магические байты,
по которым система понимает, что это Mach-O:

```bash
$ xxd -l 16 app/Payload/MyApp.app/MyApp
00000000: cffa edfe 0c00 0001 0000 0000 0200 0000  ................
```

`cffa edfe` в little-endian — это `0xfeedfacf`, magic 64-битного Mach-O. `0c 00 00 01` —
тип процессора `CPU_TYPE_ARM64`. Сразу после заголовка идут **load-команды** — инструкции
для загрузчика (`dyld`) о том, как собирать процесс из этого файла.

## Шаг 2: load-команды — оглавление файла

Заголовок сообщает, сколько load-команд в файле. Прочитать их списком проще всего через
`otool -l`:

```bash
$ otool -l app/Payload/MyApp.app/MyApp | head -20
Load command 0
      cmd LC_SEGMENT_64
  cmdsize 72
  segname __PAGEZERO
   vmaddr 0x0000000000000000
   vmsize 0x0000000100000000
Load command 1
      cmd LC_SEGMENT_64
  cmdsize 632
  segname __TEXT
```

Каждая `LC_SEGMENT_64` описывает **сегмент** — непрерывную область виртуальной памяти. Есть и
другие команды: `LC_LOAD_DYLIB` (какую библиотеку подгрузить), `LC_SYMTAB` (где таблица
символов), `LC_CODE_SIGNATURE` (где подпись). Это и есть оглавление.

## Шаг 3: сегменты __TEXT, __DATA, __LINKEDIT

Три сегмента встречаются почти всегда:

- **`__TEXT`** — исполняемый код и неизменяемые данные, доступны только на чтение и исполнение.
- **`__DATA`** — изменяемые данные: глобальные переменные, указатели Objective-C.
- **`__LINKEDIT`** — служебные таблицы для загрузчика: символы, строки, **подпись**.

Права сегмента видны в выводе как `initprot`/`maxprot`. Если у `__TEXT` стоит право записи —
это тревожный признак: нормальный код себя не переписывает.

## Шаг 4: секции — где строки и имена методов

Внутри сегментов лежат **секции**. Для реверса важны:

- `__TEXT.__cstring` — C-строки (URL, ключи, тексты ошибок);
- `__TEXT.__objc_methname` — имена Objective-C-методов;
- `__TEXT.__objc_classname` — имена классов;
- `__DATA.__objc_data` — структуры классов.

```bash
$ otool -s __TEXT __cstring app/Payload/MyApp.app/MyApp | grep -i 'https' | head
0000000000004a10  https://api.myapp.example/v1/login
0000000000004a48  https://api.myapp.example/v1/pay
```

Вот и первый реальный результат: мы видим адреса API-эндпоинтов. Адрес слева — виртуальный
адрес строки; по нему её можно найти в отладчике.

## Шаг 5: зависимые библиотеки (LC_LOAD_DYLIB)

Загрузчик собирает процесс из нескольких файлов. Список зависимостей показывает `otool -L`:

```bash
$ otool -L app/Payload/MyApp.app/MyApp
app/Payload/MyApp.app/MyApp:
	/System/Library/Frameworks/Foundation.framework/Foundation
	/usr/lib/libSystem.B.dylib
	@rpath/FridaGadget.dylib
```

Системные библиотеки — норма. А вот `@rpath/FridaGadget.dylib` в приложении, которое не
использует Frida, — это **инъекция**: кто-то встроил хукер прямо в бинарник. Так выглядит
перехват без jailbreak.

## Шаг 6: подпись и целостность

Последняя load-команда обычно `LC_CODE_SIGNATURE`; она указывает на блок подписи в
`__LINKEDIT`. Проверить подпись можно так:

```bash
$ codesign -dv --verbose=4 app/Payload/MyApp.app/MyApp
Identifier=com.example.myapp
TeamIdentifier=ABCDE12345
Authority=Apple Development: dev@example.com
```

Любая правка байтов в `__TEXT` ломает подпись. Поэтому при перепаковке IPA подпись снимают и
накладывают заново — этим занимается отдельный урок про sideloading.

## Что мы теперь знаем

- Mach-O = заголовок + load-команды + сегменты (`__TEXT`/`__DATA`/`__LINKEDIT`).
- `otool -l` показывает сегменты, `otool -s` — секции со строками и символами.
- `otool -L` вскрывает посторонние библиотеки — быстрый признак инъекции.
- Подпись лежит в `__LINKEDIT`, и её ломает любая правка кода.

## Если не сработало

Если `otool` не установлен, используйте `rabin2 -I` из radare2 или `lief` из Python. Если
файл — fat-бинарник (несколько архитектур), сначала выберите нужный срез через `lipo -thin
arm64`. Если бинарник зашифрован (App Store), `__TEXT` будет выглядеть мусором — нужен дамп из
памяти, а не разбор файла.

## Частые вопросы

**Чем Mach-O fat отличается от thin?** Fat содержит несколько архитектур, thin — одну.

**Где искать хардкод-секреты?** В `__cstring` и `__const`; затем в строках Swift-метаданных.

**Зачем `__PAGEZERO`?** Это пустой сегмент, ловящий разыменование нулевого указателя.

## Практика: парсим load-команды вручную

`otool` удобен, но иногда его нет. Разберём заголовок самим Python-ом:

```
$ python3 - <<'PY'
import struct
d = open("MyApp", "rb").read()
magic, cputype, cpusub, ftype, ncmds, sizeofcmds, flags, res = struct.unpack_from("<8I", d, 0)
print(f"magic={magic:#x} ncmds={ncmds} sizeofcmds={sizeofcmds}")
off = 32
for _ in range(ncmds):
    cmd, cmdsize = struct.unpack_from("<II", d, off)
    print(f"cmd={cmd:#x} size={cmdsize}")
    off += cmdsize
PY
magic=0xfeedfacf ncmds=18 sizeofcmds=1480
cmd=0x19 size=72
cmd=0x1 size=632
...
```

Мы прошли по всем load-командам, зная только их размеры: каждая команда начинается с
`cmd` и `cmdsize`, и следующая лежит через `cmdsize` байт. Это и есть структура файла:
заголовок задаёт число команд, команды задают карту процесса.

## Таблица: ключевые load-команды

| Команда | Значение | Зачем смотреть |
|---------|----------|----------------|
| `LC_SEGMENT_64` | сегмент памяти | границы `__TEXT`/`__DATA` |
| `LC_LOAD_DYLIB` | зависимая библиотека | поиск инъекций (Frida) |
| `LC_SYMTAB` | таблица символов | восстановление имён функций |
| `LC_DYLD_INFO` | биндинги/экспорты | связи между символами |
| `LC_CODE_SIGNATURE` | блок подписи | проверка целостности |
| `LC_RPATH` | путь поиска `@rpath` | перехват через `@rpath`-инъекцию |

## FAT-бинарники и fat-заголовок

Если файл собран под несколько архитектур, это **FAT** (universal) бинарник. Тогда
первый заголовок — не `mach_header`, а `fat_header` с magic `0xcafebabe`:

```
$ file MyApp
MyApp: Mach-O universal binary with 2 architectures
$ lipo -info MyApp
Architectures in the fat file: MyApp are: x86_64 arm64
```

`lipo -thin arm64 -output MyApp.arm64 MyApp` вырезает одну архитектуру — удобно, когда
`otool` путается или когда нужно анализировать конкретную. Для iOS актуальна `arm64`.

## Если сработало / не сработало

- **Сработало:** заголовок `0xfeedfacf`, команды читаются по `cmdsize`, `otool -L`
  показал постороннюю библиотеку — есть инъекция.
- **Magic `0xcafebabe`:** это FAT-бинарник. Сначала раздели архитектуры `lipo -thin`,
  потом читай Mach-O.
- **`otool` ругается на файл:** возможно, это не Mach-O (скрипт, обфусцированный
  контейнер) или файл зашифрован (App Store DRM). Проверь `file` и первые 16 байт.

## Ограничения

Статический разбор показывает **карту**, но не поведение: что именно делает код, видно
только в отладчике. Подписи/шифрование App Store мешают читать `__TEXT` без снятия
DRM. А обфусцированные бинарники искажают имена символов и секции — тогда карта
формально верна, а смысл скрыт.

## Разбор: восстановление имён методов

Если символы есть, имена Objective-C методов лежат в `__objc_methname`. Их можно
вытащить списком и найти интересные:

```
$ otool -s __TEXT __objc_methname MyApp | tr -s ' ' '\n' | grep -iE 'valid|licen|unlock' | head
validate:
isPremiumUnlocked
checkLicenseKey:
```

Так, без отладчика, видно, какие методы отвечают за лицензию. Дальше их адреса берут из
`__objc_data` (таблицы классов) и ставят точки останова в LLDB. Это статический
маршрут: сначала имена, потом адреса, потом отладка.

## Entitlements: что приложению разрешено

Подпись несёт **entitlements** — права приложения (keychain-группы, aps-environment,
associated-domains). Смотреть так:

```
$ codesign -d --entitlements :- MyApp.app
<key>keychain-access-groups</key>
<array><string>ABCDE12345.*</string></array>
```

Через `keychain-access-groups` приложения делят секреты: если группа общая с чужим
приложением, оно может прочитать ваш ключ из keychain. Это находка уровня «доступ к
данным соседнего приложения».

## Ошибки при анализе Mach-O

- Читать FAT-бинарник как обычный Mach-O — сначала `lipo -thin`.
- Путать `__TEXT` (код, r-x) и `__DATA` (данные, rw-) — строки ищут в `__TEXT.__cstring`.
- Игнорировать `LC_RPATH`: `@rpath`-инъекция — популярный вектор перехвата.
- Забыть, что правка `__TEXT` ломает подпись — перепаковка требует переподписи.

## Разбор: поиск строк через strings

Быстрый способ вытащить интересное из бинарника — `strings`:

```
$ strings -a app/Payload/MyApp.app/MyApp | grep -iE 'api|token|key|secret' | head
https://api.myapp.example/v1/login
X-Api-Token
PREMIUM-UNLOCK-KEY-2024
```

`-a` сканирует весь файл, а не только `__TEXT`. Найденные строки дают зацепки: адреса
API, имена заголовков, «секретные» ключи, оставленные разработчиками. Дальше адрес
строки берут из `otool -s __TEXT __cstring` и ставят точку останова на код, который к
ней обращается. Это стандартный маршрут «строки → адрес → отладка» при анализе
iOS-бинарника без символов.

<!-- deepen-fxmm-4 -->
## Разбор: секция __objc_data и таблицы классов

`__DATA.__objc_data` хранит структуры Objective-C-классов: указатель на метакласс,
имя класса, список методов, список ivar-ов. Через неё от имени метода переходят к его
адресу. Практический маршрут:

1. найти имя класса в `__TEXT.__objc_classname`;
2. найти запись класса в `__DATA.__objc_data` по этому имени;
3. в списке методов (`__objc_const`) найти селектор и его имплементацию;
4. взять адрес имплементации и поставить точку останова в LLDB.

Так, без отладчика на старте, ты получаешь адрес нужного метода прямо из статики. Это
основа анализа iOS-приложений со стрипованными символами.
