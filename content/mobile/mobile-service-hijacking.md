## Вопрос, с которого всё начинается

Мы разбирали экспортированные сервисы на уровне манифеста. Но у сервисов есть два способа взаимодействия — `startService` и `bindService`, и второй открывает куда больше: клиент получает объект `IBinder` и может вызывать методы напрямую. Как найти уязвимый сервис и как его эксплуатировать?

## Наш пример: сервисы в fdroid.apk

Посмотрим на сервисы в манифесте `fdroid.apk`:

```
$ grep -oE '<service[^>]*android:name="[^"]*"[^>]*' fdroid_dec/AndroidManifest.xml | head
<service android:exported="false" android:name="org.fdroid.fdroid.nearby.SwapService"/>
<service android:exported="false" android:name="org.fdroid.fdroid.nearby.LocalRepoService"/>
<service android:exported="true" android:name="androidx.work.impl.background.systemjob.SystemJobService"
         android:permission="android.permission.BIND_JOB_SERVICE"/>
```

Большинство сервисов приватны. Единственный экспортированный — `SystemJobService` — защищён разрешением `BIND_JOB_SERVICE`. Разберём, как выглядел бы уязвимый сервис и как его искать.

## Шаг 1: startService против bindService

Два способа работы с сервисом:

- **`startService`** — запустить сервис «в фоне», без связи. Клиент не получает ссылку на объект.
- **`bindService`** — привязаться и получить `IBinder`, через который вызываются методы.

Для атак интереснее `bindService`: если сервис экспортирован и не требует разрешения, любой может привязаться и вызвать его методы. Именно так эксплуатируются уязвимые AIDL-сервисы.

## Шаг 2: как выглядят уязвимые сервисы

Признаки уязвимого bound service:

- `android:exported="true"` (или есть `intent-filter`) **без** `android:permission`.
- Реализует AIDL-интерфейс с методами, меняющими состояние.
- Не проверяет `getCallingUid` в методах.

Если сервис выполняет привилегированное действие (перевод, удаление, доступ к данным) и не проверяет вызывающего — это находка.

## Шаг 3: разведка сервисов

Начинаем с манифеста:

```
$ grep -oE '<service[^>]*android:exported="true"[^>]*' fdroid_dec/AndroidManifest.xml
```

Затем ищем AIDL в декомпилированном коде:

```
$ grep -rn "extends IInterface" out/ | head
```

Каждый такой класс — интерфейс сервиса. Смотрим методы: `transfer`, `getData`, `delete` и т.п.

## Шаг 4: эксплуатация через adb

Простейшая проверка — запустить или привязаться из adb:

```
$ adb shell am startservice -n com.example.app/.SyncService
$ adb shell service call example 1
```

`service call` шлёт Binder-транзакцию напрямую по номеру. Это хрупко, но быстро показывает, реагирует ли сервис.

## Шаг 5: свой клиент-приложение

Надёжнее — написать минимальный клиент, который биндится и вызывает метод через сгенерированный AIDL-стаб:

```java
bindService(intent, conn, Context.BIND_AUTO_CREATE);
// onServiceConnected:
ISyncService svc = ISyncService.Stub.asInterface(binder);
svc.sync("attacker-controlled-url");
```

Так доказывают, что метод выполняется без авторизации.

## Шаг 6: перехват неявных сервисов

Отдельный класс — **hijacking неявного сервиса**. Если приложение запускает сервис через неявный Intent (по action, без указания компонента), чужое приложение может зарегистрировать тот же action и «перехватить» вызов. Тогда данные, которые приложение отправляло своему сервису, уходят атакующему. Ищите `startService(new Intent("com.example.ACTION"))` без `setComponent`.

## Шаг 7: Messenger и защита

Сервис может использовать не AIDL, а `Messenger` — обёртку над Binder с обработкой `Message`. Принципы те же: экспортированный Messenger без проверки вызывающего позволяет слать команды.

Правильная защита:

- `android:exported="false"` для внутренних сервисов.
- `android:permission` для экспортированных.
- Проверка `getCallingUid` в методах.
- Использование явных Intent вместо неявных.

## Разбор реального сценария

Приложение-мессенджер предоставляет сервис `SyncService` с методом `sync(String url)`, который скачивает конфиг по URL. Сервис экспортирован, чтобы его мог дёргать виджет. Проверки вызывающего нет. Атакующее приложение биндится к сервису и вызывает `sync("http://evil/config")`. Приложение скачивает конфиг атакующего и применяет его. Формально прав у атакующего нет, но он действует руками привилегированного сервиса — это confused deputy на уровне Binder. Одна пропущенная строка `getCallingUid` превращает внутренний метод в публичный API.

## Полный прогон от начала до конца

Соберём эксплуатацию в один сценарий. Сначала `grep '<service'` по манифесту и список экспортированных без `android:permission`. Затем ищем `extends IInterface` и выписываем методы. Пробуем `am startservice -n` — реагирует ли. Пишем минимальный клиент, биндимся, вызываем метод. Смотрим, проверяет ли он `getCallingUid`. Если нет и метод меняет состояние — фиксируем с высоким приоритетом. Отдельно проверяем неявные `startService` на перехват.

## Частые вопросы

**«Любой экспортированный сервис — уязвимость?»** — нет, только без `android:permission` и проверки вызывающего. **«Нужен ли root?»** — нет. **«Как отличить AIDL от Messenger?»** — AIDL даёт типизированные методы, Messenger — сообщения. **«Что если сервис защищён разрешением?»** — это правильная практика, не находка. **«Как защитить?»** — `exported="false"`, `android:permission`, проверка `getCallingUid`, явные Intent.

## Практический совет

Воспринимайте bound service как REST API без аутентификации, пока не доказано обратное. Начните с самого простого: привяжитесь к сервису и вызовите метод с безобидным аргументом. Если вызов прошёл — доступ есть; дальше ищите метод с последствиями. Не углубляйтесь в разбор Parcel, пока не подтвердили, что вообще можете вызвать сервис.

## Ещё один нюанс: Binder vs Messenger

Если сервис использует `Messenger`, клиент общается с ним не типизированными методами, а сообщениями `Message`. Это не делает его безопаснее: экспортированный Messenger без проверки вызывающего принимает команды от любого. Более того, `Message` может содержать `Bundle` с произвольными данными, и если сервис их не валидирует, возможны те же проблемы. Проверяя сервис, определите сначала способ связи (AIDL или Messenger) — от этого зависит, как писать PoC-клиент.

## Итог

Сервис — это удалённый API. Если он экспортирован без разрешения и не проверяет вызывающего, любой метод становится публичным. Эксплуатация проста: привязаться и вызвать. Поэтому в отчёте важны две вещи — какой метод доступен и какое действие он выполняет. Вместе они определяют severity: чтение данных — high, изменение состояния — critical.

## Связь с другими уроками

Service hijacking — часть большой темы IPC. Он родственен intent redirection (посредник выполняет чужой Intent) и Binder-атакам (методы сервиса — удалённые вызовы). Разобрав сервисы, вы сможете систематизировать всю поверхность IPC: компоненты, deep links, провайдеры, сервисы — и перейти к её автоматизированному перебору.

## Ещё один нюанс: `onBind` и возвращаемый null

Не всякий экспортированный сервис уязвим: если `onBind` возвращает `null`, клиент не получит `IBinder` и вызвать методы не сможет. Поэтому, найдя сервис, сначала проверьте, реализован ли `onBind` и что он возвращает. Если возвращается реальный `Binder` с методами — доступ есть. Если `null` — сервис можно только запустить (`startService`), но не вызывать его методы. Это различие экономит время.

## Что мы теперь знаем

По-простому:

1. `bindService` даёт клиенту `IBinder` и доступ к методам сервиса.
2. Уязвимый сервис — экспортированный, без `android:permission`, без проверки вызывающего.
3. Разведка: манифест + поиск `extends IInterface`.
4. Эксплуатация: `am startservice`, `service call` или свой клиент.
5. Неявные сервисы можно перехватить чужим приложением.

## На что смотреть дальше

- **Ищите экспортированные сервисы** без `android:permission`.
- **Читайте AIDL-интерфейсы** — что умеют методы.
- **Проверяйте `getCallingUid`** в каждом методе.
- **Ищите неявные `startService`** — перехват.

## Рекомендации по защите

В отчёте предлагайте конкретное: сделать внутренние сервисы `exported="false"`, для экспортированных — добавить `android:permission` и проверку `getCallingUid`, заменить неявные `startService` на явные Intent с указанием компонента. Эти меры закрывают и эксплуатацию, и перехват. Если сервис действительно нужен другим приложениям, проверка вызывающего обязательна — иначе он превращается в открытый API.
