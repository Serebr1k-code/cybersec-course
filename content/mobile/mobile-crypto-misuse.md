## Вопрос, с которого всё начинается

Приложение шифрует данные — значит, они в безопасности? Не всегда. Криптография защищает ровно настолько, насколько правильно она применена. Если ключ зашит в код, а режим выбран неверно, «шифрование» превращается в декорацию, которую снимают за пять минут.

Покажем это на реальном приложении: расшифруем его секрет, вообще не имея устройства.

## Наш пример: uncrack1.apk

Возьмём `uncrack1.apk` — учебное приложение OWASP UnCrackable. Декомпилируем код и посмотрим, как оно проверяет введённый пароль:

```java
public class a {
    public static boolean a(String str) {
        byte[] bArr = sg.vantagepoint.a.a.a(
            b("8d127684cbc37c17616d806cf50473cc"),                    // ключ
            Base64.decode("5UJiFctbmgbDoLXmpL12mkno8HT4Lv8dlat8FxR2GOc=", 0) // шифртекст
        );
        return str.equals(new String(bArr));
    }
    public static byte[] b(String str) {   // hex-строка -> байты
        ...
    }
}
```

Сразу видны три вещи: **ключ `8d12...` лежит прямо в коде**, шифртекст тоже в коде, а функция расшифровки — вот она:

```java
public class a {
    public static byte[] a(byte[] key, byte[] data) {
        SecretKeySpec spec = new SecretKeySpec(key, "AES/ECB/PKCS7Padding");
        Cipher cipher = Cipher.getInstance("AES");
        cipher.init(Cipher.DECRYPT_MODE, spec);
        return cipher.doFinal(data);
    }
}
```

Ключевое слово — `ECB`. Разберём, почему это ошибка, и расшифруем секрет сами.

## Шаг 1: расшифровываем без устройства

У нас есть ключ (hex) и шифртекст (base64). Ничего больше не нужно — AES детерминирован, режим ECB не использует IV. Выполняем на компьютере:

```python
from base64 import b64decode
from Crypto.Cipher import AES

key = bytes.fromhex("8d127684cbc37c17616d806cf50473cc")
ct  = b64decode("5UJiFctbmgbDoLXmpL12mkno8HT4Lv8dlat8FxR2GOc=")
print(AES.new(key, AES.MODE_ECB).decrypt(ct))
```

Результат:

```
$ python3 decrypt.py
b'I want to believe\x0f\x0f\x0f\x0f\x0f\x0f\x0f\x0f\x0f\x0f\x0f\x0f\x0f\x0f\x0f'
```

Секрет — `I want to believe`. Байты `0f` в конце — это padding (PKCS#7), которым дополнили строку до размера блока. Мы обошли проверку полностью в статике.

## Шаг 2: почему ECB — ошибка

AES работает блоками по 16 байт. В режиме **ECB** каждый блок шифруется независимо и одинаковым ключом. Значит, одинаковые блоки открытого текста превращаются в одинаковые блоки шифртекста. Это называется **детерминированным шифрованием** и даёт две проблемы:

- **Утечка структуры.** Видно, где в данных повторяются куски (например, одинаковые поля в БД).
- **Атаки по оракулу.** Если приложение шифрует наш ввод и мы видим результат, можно побайтово восстановить секрет (byte-at-a-time ECB).

Правильный режим — **GCM** (или CBC с случайным IV), где одинаковый текст даёт разный шифртекст.

## Шаг 3: где ещё ошибаются

- **Фиксированный IV/nonce.** Если IV постоянный, GCM/CBC теряют стойкость: одинаковые сообщения снова дают одинаковый шифртекст, а в GCM повтор nonce вообще раскрывает ключ.
- **Слабое хэширование.** MD5/SHA-1 для паролей — подбираются. Пароли хранят через bcrypt/scrypt/Argon2.
- **Самодельные схемы.** «XOR с ключом», «Base64 вместо шифрования», «шифруем паролем без KDF» — всё это ломается тривиально.
- **Ключ из публичных данных.** Если ключ выводится из имени пакета или IMEI, он восстановим.

## Шаг 4: как искать криптокод в APK

```
$ jadx -d out uncrack1.apk
$ grep -rn "Cipher.getInstance\|SecretKeySpec\|IvParameterSpec\|MessageDigest" out/ | head
out/sources/sg/vantagepoint/a/a.java:  Cipher.getInstance("AES");
```

Дальше смотрим строку режима. `AES/ECB/...`, `AES` (по умолчанию ECB в старых версиях), `DES`, `MD5`, `SHA1` — красные флаги. Затем ищем, откуда берётся ключ: `const-string` рядом с `SecretKeySpec` — значит, захардкожен.

## Шаг 5: byte-at-a-time против ECB-оракула

Классическая атака, когда приложение шифрует `ваш_ввод + секрет` в ECB и отдаёт шифртекст. Идея: подбираем ввод так, чтобы секрет выравнивался по границе блока, и по совпадению блоков угадываем его побайтово. Псевдокод:

```
for each byte position:
    feed input of length (block - 1 - i)
    build dictionary of ciphertext blocks for all 256 guesses
    match the target block against the dictionary
```

Это возможно **только из-за ECB**: в GCM/CBC с случайным IV такой оракул бесполезен.

## Шаг 6: как защищать

- Использовать аутентифицированное шифрование (AES-GCM) и случайный nonce.
- Не хранить ключи в коде — генерировать в Keystore.
- Пароли хэшировать медленными функциями (Argon2id), а не MD5/SHA.
- Не изобретать схемы: применять проверенные библиотеки.

## Полный прогон от начала до конца

Соберём разбор криптографии в один сценарий:

1. **`jadx -d out uncrack1.apk`** — декомпилируем.
2. **`grep -rn "Cipher.getInstance"`** — находим криптокод.
3. **Читаем режим:** `AES` (по умолчанию ECB) — красный флаг.
4. **Ищем ключ:** `const-string` рядом с `SecretKeySpec`.
5. **Извлекаем ключ и шифртекст** из байткода.
6. **Расшифровываем** на компьютере (`pycryptodome`).
7. **Проверяем результат** — получаем `I want to believe`.

Вся атака — статическая, устройство не нужно.

## Если не сработало

- **Ключ не в коде, а в Keystore.** Тогда статика не поможет — перехватывайте `Cipher.init` через Frida.
- **Режим CBC с IV.** IV тоже ищите в коде; часто он фиксированный (тоже ошибка).
- **Данные зашифрованы производным ключом.** Ищите KDF (`SecretKeyFactory`, `PBKDF2`); слабый пароль подбирается офлайн.
- **Ключ приходит с сервера.** Перехватывайте трафик и смотрите, как он используется.
- **Самодельная схема.** XOR/перестановки разбираются руками; не бойтесь читать код.

## Что фиксировать в отчёте

- **Где ключ** (файл, строка) и как он получен.
- **Какой режим** и почему он небезопасен.
- **Что удалось расшифровать** (с доказательством).
- **Рекомендации:** GCM, случайный nonce, ключ в Keystore, Argon2id для паролей.

## Частые вопросы

**«Ключ зашифрован?»** — нет, захардкоженный ключ просто строка в байткоде. **«Нужен ли root?»** — для статического разбора нет. **«Что если AES-GCM?»** — тогда ищите повтор nonce и слабый источник случайности. **«Как быстро найти ошибку?»** — grep по `Cipher.getInstance` и `MessageDigest`. **«Что важнее: ключ или режим?»** — оба; захардкоженный ключ ломает всё независимо от режима.

## Практический совет

Начинайте с вопроса «а где ключ?». Если он в коде — дальше можно не копать: шифрование уже сломано. Если ключ в Keystore — переходите к режиму и nonce. И всегда проверяйте хэш-функции: MD5/SHA-1 для паролей означают, что база паролей подбирается офлайн за минуты.

## Что мы теперь знаем

По-простому:

1. Захардкоженный ключ = ключа нет: он есть у каждого, кто скачал APK.
2. ECB детерминирован — одинаковые блоки дают одинаковый шифртекст.
3. Реальный секрет `uncrack1` расшифрован в статике без устройства.
4. Фиксированный IV/nonce и слабые хэши — такие же ошибки.
5. Правильно: GCM + случайный nonce + ключ в Keystore.

## На что смотреть дальше

- **Ищите `Cipher.getInstance`** и читайте режим: ECB — сразу находка.
- **Смотрите, откуда ключ:** `const-string` рядом с ключом = захардкожен.
- **Проверяйте IV/nonce:** постоянный — ошибка.
- **Помните про оракул:** если есть шифрование вашего ввода, возможна byte-at-a-time атака.

## Повторное использование nonce

Отдельная и очень опасная ошибка — повтор nonce в режиме GCM. Если два сообщения зашифрованы одним ключом и одним nonce, XOR их шифртекстов даёт XOR открытых текстов, а знание одного открытого текста раскрывает второй. Более того, повтор nonce в GCM позволяет восстановить ключ аутентификации и подделывать сообщения. Поэтому ищите, откуда берётся nonce: если он постоянный или предсказуемый, это критическая находка, даже при «правильном» режиме.
