## Вопрос, с которого всё начинается

Приложение присылает push-уведомления: «У вас новое сообщение», «Подтвердите вход». За этой простой функцией стоит целая инфраструктура — **FCM** (Firebase Cloud Messaging) на Android и **APNs** (Apple Push Notification service) на iOS. Как она устроена и где тут могут быть уязвимости?

## Наш пример: push-токен и payload

Когда приложение устанавливается, оно регистрируется в системе push и получает **токен устройства** — длинную строку-адрес. На Android это токен FCM:

```
$ frida -U -n DemoApp -l hook.js
[+] FCM token: cXYZ...:APA91bH... (truncated)
```

Сервер приложения хранит этот токен и по нему отправляет уведомления. Токен — это «адрес» конкретного устройства. Если он утечёт, злоумышленник сможет слать уведомления от имени приложения.

## Шаг 1: как устроена доставка

Цепочка такая:

1. Приложение получает токен от FCM/APNs.
2. Приложение отправляет токен своему серверу.
3. Сервер шлёт запрос в FCM/APNs с payload.
4. FCM/APNs доставляет уведомление на устройство.

Payload — это JSON с данными уведомления:

```json
{
  "to": "cXYZ...:APA91bH...",
  "notification": { "title": "Новое сообщение", "body": "Привет" },
  "data": { "chat_id": "42", "type": "message" }
}
```

`notification` показывает уведомление, `data` передаёт приложению скрытые данные. Именно `data` часто управляет поведением: какой экран открыть, что загрузить.

## Шаг 2: где взять ключ сервера

Чтобы отправить push, серверу нужен **server key** (FCM) или сертификат/ключ APNs. Этот ключ — секрет. Если он утечёт (например, захардкожен в приложении), злоумышленник сможет отправлять уведомления от имени приложения:

```
$ curl -X POST https://fcm.googleapis.com/fcm/send \
    -H "Authorization: key=SERVER_KEY" \
    -H "Content-Type: application/json" \
    -d '{"to":"<token>","notification":{"title":"Взлом","body":"Нажми"}}'
```

Поиск такого ключа — стандартная проверка. Ищем в APK строки, похожие на server key, и в `google-services.json`:

```
$ unzip -p app.apk | grep -iE 'AIza|server_key|google-services'
```

## Шаг 3: что можно подделать

Даже без server key есть слабые места:

- **Перехват токена.** Если токен передаётся по HTTP или хранится в открытом виде, его можно украсть и зарегистрировать на себя (token hijacking).
- **Спуфинг отправителя.** Если приложение доверяет `data` без проверки, подделанный payload может открыть опасный экран.
- **Deep link в payload.** Если уведомление открывает deep link, а приложение не проверяет его, получаем цепочку от push к open redirect (см. `mobile-ios-urlscheme`).
- **Локальное уведомление.** Некоторые приложения показывают «уведомление» локально по данным сервера; подделка данных = подделка уведомления.

## Практика: сервер не проверяет владельца токена

Многие проблемы push начинаются на сервере. Поднимем локальный демо-эндпоинт отправки и попробуем послать уведомление на **чужой** токен, не будучи владельцем устройства:

```
$ curl -s -X POST http://127.0.0.1:18090/v1/push/send \
    -H "Content-Type: application/json" \
    -d '{"token":"fcm-token-BBB","title":"Your password was changed"}'
{"sent": true, "to": "fcm-token-BBB", "title": "Your password was changed"}
```

Сервер принял запрос и подтвердил отправку на токен `fcm-token-BBB`, хотя мы его не регистрировали. Причина — эндпоинт не проверяет, что токен принадлежит текущему пользователю. В реальном приложении это позволяет слать жертве уведомления от имени сервиса: «Подтвердите вход», «Ваш пароль изменён» — готовая основа для фишинга через push.

## Шаг 4: обработка на клиенте

Важно, как приложение обрабатывает payload. Ищем обработчик в коде:

```java
public void onMessageReceived(RemoteMessage msg) {
    String screen = msg.getData().get("screen");
    Intent i = new Intent(this, Router.class);
    i.putExtra("target", screen);
    startActivity(i);
}
```

Если `screen` из payload напрямую открывает экран или URL — это вход. Проверяем, можно ли через `data` заставить приложение открыть произвольный deep link или выполнить действие. Опасные признаки: `addJavascriptInterface` в WebView по push, `loadUrl` с параметром из payload, передача токена в URL.

## Шаг 5: push как вектор для цепочек

Уведомление — это внешний вход, который пользователь **ожидает** и потому кликает. Поэтому push часто используют в цепочках: уведомление → deep link → WebView → утечка токена. В bug bounty такие цепочки ценятся, потому что требуют минимум действий от жертвы. Проверяя push, всегда смотри, куда ведёт `data`.

## Шаг 6: что проверять

Чек-лист по push:

| Что проверяем | Признак проблемы |
|---------------|------------------|
| Server key в APK | захардкожен |
| Передача токена | по HTTP / в открытом виде |
| Обработка `data` | прямой deep link / URL |
| Проверка отправителя | нет |
| Хранение токена | `NSUserDefaults`/логи |
| Уведомления с секретами | токены в тексте push |

## Шаг 7: защита

Со стороны защиты: server key только на сервере, передача токенов по HTTPS, валидация `data` на клиенте, ограничение deep link-целей, не класть секреты в текст уведомления (он виден на экране блокировки). Для iOS — использовать APNs с аутентификацией по ключу, для Android — ограничить server key по IP.

## Шаг 8: отличия Android и iOS

Механики различаются. На Android уведомление обрабатывает `FirebaseMessagingService.onMessageReceived`, а разрешение на показ (`POST_NOTIFICATIONS`) появилось только в Android 13. На iOS уведомления идут через APNs, а обработчик — `userNotificationCenter:didReceiveNotificationResponse:`. На iOS есть ещё **silent push** (background push): он не показывается пользователю, а тихо будит приложение для фоновой синхронизации. Silent push — интересный вектор: приложение просыпается и выполняет код по данным сервера, а пользователь ничего не видит.

## Шаг 9: практический порядок

Проверяя push, действуй по шагам: получи токен (хуком), найди обработчик payload в статике, проверь, как используется `data`, поищи server key в APK, посмотри, передаётся ли токен по защищённому каналу. Если `data` ведёт к deep link или WebView — выстраивай цепочку. Так push из «второстепенной функции» превращается в полноценный вектор. И помни: уведомление видно на экране блокировки, поэтому секреты в его тексте — отдельная находка. Не забывай и про rate limiting на отправку push: без него возможен спам-вектор. Проверка push — это всегда сочетание клиентской обработки и серверной конфигурации.

## Что мы теперь знаем

- Push идёт через FCM (Android) и APNs (iOS); устройство идентифицируется токеном.
- Payload содержит `notification` (видимое) и `data` (для приложения).
- Server key — секрет; его утечка позволяет слать уведомления от имени приложения.
- Опасности: перехват токена, спуфинг, deep link в payload, локальные уведомления.
- Обработчик `data` — главное место проверки на клиенте.
- Push часто используют во вредоносных цепочках.

## Куда дальше

Мы разобрали push как ещё один серверный канал. Это завершает базовый обзор мобильных механизмов. Дальше можно углубляться в конкретные ветви: защиту приложений, цепочки эксплуатации, малварь. А пока главное запомни: push — это внешний вход, которым пользуется и пользователь, и атакующий, и проверять его нужно как любой другой вход.

## Где пригодится

- **Пентест:** анализ push-канала и его связей с deep link.
- **Bug bounty:** утёкший server key и спуфинг уведомлений — частые находки.
- **CTF:** задачи, где флаг приходит через push.
- **Аудит:** проверка хранения токенов и server key.
