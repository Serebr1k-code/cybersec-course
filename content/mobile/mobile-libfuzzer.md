## Вопрос, с которого всё начинается

В приложении есть нативная библиотека `libparser.so`, которая разбирает входной формат. Мы
подозреваем, что на кривом вводе она выходит за границы буфера, но руками такой ввод не
придумать. Как заставить компьютер **сам** перебирать миллионы вариантов и находить падение?

## Наш пример: точка входа парсера

Заглянем в библиотеку и найдём функцию разбора:

```bash
$ nm -D --defined-only libparser.so | grep -i parse
0000000000012a40 T parse_record
```

`nm` показывает таблицу символов; `T` — определённая (экспортируемая) функция. Значит, есть
`parse_record`, которая принимает буфер и длину. Фаззеру нужна ровно такая функция.

## Шаг 1: что такое harness

Фаззер не знает, что вызывать. Мы пишем **harness** — маленькую обёртку, которая берёт
случайные байты и передаёт их в нашу функцию:

```c
extern int parse_record(const uint8_t *buf, size_t len);

int LLVMFuzzerTestOneInput(const uint8_t *data, size_t size) {
    parse_record(data, size);
    return 0;
}
```

`LLVMFuzzerTestOneInput` — точка входа, которую libFuzzer вызывает сам. Каждый вызов — это
одна попытка с новым набором байтов. `return 0` означает «всё нормально, продолжай».

## Шаг 2: сборка

Компилируем harness вместе с библиотекой под нужную архитектуру, включая санитайзер адресов
(`-fsanitize=address`) и сам фаззер (`-fsanitize=fuzzer`):

```bash
$ clang --target=aarch64-linux-android -fsanitize=fuzzer,address \
    -o fuzz_parser harness.c -L. -lparser
$ file fuzz_parser
fuzz_parser: ELF 64-bit LSB shared object, ARM aarch64
```

`--target` задаёт архитектуру Android. `-fsanitize=fuzzer` добавляет движок фаззинга,
`-fsanitize=address` — детектор выхода за границы памяти. Без ASan ошибка может пройти
«тихо», не уронив процесс.

## Шаг 3: запуск и словарь

Запускаем на устройстве (или эмуляторе) и смотрим статистику:

```bash
$ adb push fuzz_parser /data/local/tmp/ && adb shell /data/local/tmp/fuzz_parser
INFO: Seed: 3829104
#2  INITED cov: 214 ft: 388 corp: 3/21b exec/s: 0
#1024 NEW  cov: 421 ft: 902 corp: 11/150b
```

`cov` — покрытие кода (сколько ветвей достигнуто), `exec/s` — сколько запусков в секунду,
`corp` — размер «корпуса», то есть набора интересных входов. Фаззер хранит их и мутирует.

## Шаг 4: словарь для форматов

Если формат начинается с «магических» байтов, фаззеру трудно их угадать. Словарь подсказывает:

```bash
$ cat parser.dict
hdr="REC0"
len="\x00\x00"
$ adb shell /data/local/tmp/fuzz_parser -dict=/data/local/tmp/parser.dict
```

Словарь — файл с токенами в формате `имя="значение"`. Это резко ускоряет прохождение
проверок формата.

## Шаг 5: читаем краш

Когда ASan ловит ошибку, он печатает отчёт:

```bash
==3110==ERROR: AddressSanitizer: heap-buffer-overflow on address 0x... 
READ of size 1 at 0x... thread T0
    #0 0x... in parse_record parser.c:57
```

`heap-buffer-overflow` — чтение за границей кучи. Указан файл и строка. libFuzzer сохраняет
вход, вызвавший краш, в файл `crash-<hash>` — его можно воспроизвести:

```bash
$ adb shell /data/local/tmp/fuzz_parser crash-abc123
```

## Шаг 6: ограничения

libFuzzer требует, чтобы функцию можно было вызвать напрямую и собрать библиотеку. Если
логика спрятана в статической сборке без символов или в обфусцированном коде, придётся
сначала восстановить точку входа (см. `mobile-reverse-native`). Тогда на помощь приходит
AFL (`mobile-afl-native`).

## Что мы теперь знаем

- Harness — обёртка с `LLVMFuzzerTestOneInput`.
- Сборка: `-fsanitize=fuzzer,address` под arm64 Android.
- `cov` и `exec/s` — покрытие и скорость фаззинга.
- Словарь ускоряет прохождение проверок формата.
- ASan-отчёт и файл `crash-*` дают воспроизводимый вход.

## Дизайн harness: что важно

Harness — это не «вызвать функцию», а аккуратно подготовить окружение. Фаззер запускает
harness **в одном процессе** миллионы раз, поэтому любое глобальное состояние накапливается.
Если harness выделяет память и не освобождает, через минуту процесс съест всю память и
упадёт — а это ложный краш, не баг библиотеки. Поэтому в конце harness освобождают всё, что
создал, и сбрасывают глобальные переменные к исходному состоянию.

Второе — **структура входа**. Случайные байты редко проходят проверки формата. Если формат
известен, вход удобно разбирать через `FuzzedDataProvider`: он берёт из случайных байтов
целые числа, строки и буферы нужного размера. Так фаззер быстрее доходит до глубокой логики.

```c
#include <FuzzedDataProvider.h>
extern int parse_record(const uint8_t *buf, size_t len);

int LLVMFuzzerTestOneInput(const uint8_t *data, size_t size) {
    FuzzedDataProvider p(data, size);
    auto len = p.ConsumeIntegralInRange<size_t>(0, 64);
    auto buf = p.ConsumeBytes<uint8_t>(len);
    if (buf.size() == len) parse_record(buf.data(), buf.size());
    return 0;
}
```

## Частые ошибки

Первая — **утечка в harness**: память не освобождается, фаззер падает по OOM. Вторая —
**общее состояние**: статический буфер не сбрасывается, и каждый следующий запуск видит
«хвост» предыдущего. Третья — **медленный harness**: если он пишет на диск или ждёт сеть,
скорость падает в сотни раз. Четвёртая — **отсутствие словаря** для форматов с магическими
байтами. Пятая — **игнорирование отчёта**: ASan показывает первую ошибку и останавливается;
после исправления прогон надо повторить, чтобы найти следующую.

## Практика: воспроизведение краша

libFuzzer сохраняет вход, вызвавший падение, в файл `crash-*`. Его можно прогнать ещё раз:

```bash
$ adb shell /data/local/tmp/fuzz_parser crash-abc123
==3110==ERROR: AddressSanitizer: heap-buffer-overflow ...
```

Так баг превращается в воспроизводимый тест-кейс: файл можно приложить к задаче на
исправление. Хорошая практика — добавить этот файл в регрессионный корпус, чтобы будущие
прогоны проверяли и его.

## Что ещё посмотреть

Для больших проектов есть OSS-Fuzz — облачный сервис, который гоняет фаззеры непрерывно.
Дополнительно включают **value profile** (подсказки по сравнению значений) и
`-use_value_profile=1`: это помогает проходить проверки вроде «эта строка равна магической».

## Разбор реального случая

Команда фаззила парсер изображений. Прогон шёл несколько часов и не находил ничего — казалось,
код безопасен. Проблема оказалась в harness: он открывал файл на диске на каждой итерации.
Диск стал узким местом, и скорость упала до сотни запусков в секунду. Harness переписали так,
чтобы данные читались из памяти, а файл открывался один раз. Скорость выросла до десятков
тысяч запусков, и краш нашёлся в тот же вечер. Мораль: **сначала измерьте exec/s**, и если
цифра маленькая — виноват harness, а не «безопасный код».

## Сравнение фаззеров

| Критерий | libFuzzer | AFL |
|----------|-----------|-----|
| Встраивание | в библиотеку, in-process | внешний процесс |
| Скорость | максимальная | ниже, зависит от режима |
| Нужны исходники | да | нет (QEMU-режим) |
| Порог входа | написать harness | подготовить корпус |
| Когда брать | своя функция/библиотека | готовый бинарник |

Выбор прост: есть возможность вызвать функцию напрямую — берите libFuzzer. Нет — AFL.

## Чек-лист

- harness сбрасывает состояние и не течёт по памяти;
- вход разбирается через FuzzedDataProvider, если формат известен;
- словарь добавлен для форматов с магическими байтами;
- exec/s измерена и приемлема;
- краши сохранены и добавлены в регрессионный корпус.

## Что мешает, если ничего не находится

Отсутствие находок — не доказательство безопасности. Прежде чем делать вывод, проверьте
четыре вещи. Первое: покрытие (`cov`). Если оно не растёт, фаззер топчется на входной
проверке и до логики не доходит — нужен словарь или структурный вход. Второе: скорость
(`exec/s`). Маленькая скорость означает медленный harness, а не отсутствие багов. Третье:
корпус. Если он пуст или однообразен, мутировать не из чего. Четвёртое: время. Часа прогона
почти всегда мало — счёт идёт на сутки. Только когда все четыре условия выполнены, «находок
нет» становится осмысленным утверждением.

## Итог

libFuzzer даёт максимальную скорость, когда функцию можно вызвать напрямую. Его сила — в
простой модели: harness плюс санитайзер. Его слабость — в требованиях: нужны исходники и
аккуратный harness без утечек и глобального состояния. Если эти требования выполнить, дальше
работает статистика: миллионы запусков находят то, что не найдёт человек.

## Как это связано с пентестом

Пентестер использует libFuzzer в двух ситуациях. Первая — когда нативная библиотека
обрабатывает внешние данные: файлы, сетевые пакеты, изображения. Вторая — когда нужно
доказать наличие ошибки памяти для отчёта: файл `crash-*` становится воспроизводимым
доказательством. Важно соблюдать рамки: фаззинг запускают на своей сборке или на тестовом
стенде, а не на боевом сервисе. И помните, что найденный краш — это ещё не эксплойт: между
падением и возможностью выполнить код может быть несколько шагов, и их надо оценить
отдельно.

Наконец, помните о дисциплине эксперимента: записывайте версию компилятора, флаги сборки и
seed прогона. Фаззинг — это воспроизводимый эксперимент, а не «оставил на ночь и повезло».
Если находку нельзя повторить на той же сборке, она бесполезна для исправления.

## Итог в трёх предложениях

libFuzzer вызывает вашу функцию снова и снова со случайными байтами; санитайзер превращает
скрытые ошибки памяти в явные падения; найденный вход сохраняется и становится
воспроизводимым тест-кейсом. Если скорость падает — виноват harness. Если находок нет —
проверьте покрытие, словарь и время прогона, прежде чем считать код безопасным.
