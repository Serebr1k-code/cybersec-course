## Вопрос, с которого всё начинается

Вы декомпилировали APK в JADX и увидели проверку лицензии — функция возвращает `false`, если
подписка не оплачена. Хочется заставить её всегда возвращать `true` и посмотреть, что будет.
Но JADX только читает: изменённый Java-код нельзя собрать обратно в APK. Нужен инструмент,
который работает на уровне, из которого APK реально собирается.

## Наш пример: app.apk и его проверка

Мы хотим пропатчить приложение так, чтобы метод `isPremium()` всегда возвращал истину. Сначала
разбираем APK:

```bash
$ apktool d app.apk -o app_out
I: Using Apktool 2.9.3
I: Copying assets and libs...
I: Decoding AndroidManifest.xml...
I: Baksmaling classes.dex...
```

`apktool` — инструмент, который разбирает APK на составляющие: ресурсы, манифест и **smali** —
человекочитаемое представление байткода DEX. Именно smali можно править и собирать обратно.

## Шаг 1: структура результата

```bash
$ ls app_out
AndroidManifest.xml  apktool.yml  assets/  lib/  res/  smali/  smali_classes2/
```

Здесь `smali/` — байткод первого DEX, `smali_classes2/` — второго (приложение было multidex).
`apktool.yml` — служебный файл, который apktool использует при сборке.

## Шаг 2: находим метод для патча

```bash
$ grep -rn "isPremium" app_out/smali* | head
app_out/smali_classes2/com/example/Premium.smali:112: .method public isPremium()Z
```

Файл найден. Открываем его и смотрим реализацию:

```smali
.method public isPremium()Z
    .locals 1
    const/4 v0, 0x0
    return v0
.endmethod
```

`.method ... ()Z` означает «метод без аргументов, возвращает boolean». `const/4 v0, 0x0`
кладёт в регистр `v0` значение 0 (ложь). `return v0` возвращает его.

## Шаг 3: патч smali

Меняем 0 на 1 (истина):

```smali
.method public isPremium()Z
    .locals 1
    const/4 v0, 0x1
    return v0
.endmethod
```

Это вся суть smali-патча: найти нужную инструкцию и заменить константу/вызов. Часто патчат
не константу, а вызов проверки — например, заменяют `invoke-static {p0}, Lcheck;->verify()Z`
на `const/4 v0, 0x1`.

## Шаг 4: обратная сборка

```bash
$ apktool b app_out -o app_patched.apk
I: Building resources...
I: Building apk file...
```

`b` — build, `-o` — имя выходного APK. Результат не подписан и поэтому пока не устанавливается.

## Шаг 5: выравнивание и подпись

Android требует, чтобы APK был выровнен (zipalign) и подписан. Выравнивание ускоряет чтение
ресурсов, подпись подтверждает авторство:

```bash
$ zipalign -p 4 app_patched.apk app_aligned.apk
$ apksigner sign --ks debug.keystore --out app_signed.apk app_aligned.apk
```

`apksigner` — официальный инструмент подписи. Можно использовать тестовый keystore, но тогда
подпись будет отличаться от оригинальной — обновить поверх установленного приложения не
получится, придётся удалить старое.

## Шаг 6: установка и проверка

```bash
$ adb uninstall com.example
$ adb install app_signed.apk
Success
```

Запускаем — проверка пройдена. Мы изменили поведение приложения без доступа к исходникам.

## Шаг 7: типичные ошибки

- `apktool b` ругается на framework — для некоторых ресурсов нужен `apktool if framework-res.apk`.
- Ошибки 9-patch и ресурсов лечатся флагом `--use-aapt2` или обновлением apktool.
- `INSTALL_FAILED_UPDATE_INCOMPATIBLE` — подпись не совпала, нужно удалить оригинал.
- Если приложение проверяет подпись в рантайме, патч smali может не помочь — тогда нужна
  Frida-обёртка, возвращающая оригинальную подпись.

## Что мы теперь знаем

- apktool разбирает APK в smali и ресурсы и собирает обратно.
- Патч smali — замена инструкции/константы.
- Собранный APK надо выровнять и подписать.
- Смена подписи мешает обновлению поверх оригинала.
- Рантайм-проверки подписи требуют динамических методов.

## Анатомия smali: регистры, типы и инструкции

Прежде чем менять код, надо понимать его форму. smali-метод состоит из директив (начинаются с `.`) и инструкций. Директива `.method` открывает метод, `.end method` закрывает, `.locals N` объявляет, сколько локальных регистров нужно методу, `.registers` — общее число (включая аргументы).

Регистры делятся на локальные (`v0`, `v1`, …) и параметры (`p0`, `p1`, …). По соглашению в **instance-методе** `p0` — это `this`, а в статическом методе `p0` — первый аргумент. В нашем примере `isPremium()` не принимает аргументов, поэтому `p0` — ссылка на объект.

Типы в smali обозначаются дескрипторами: `Z` — boolean, `I` — int, `V` — void, `Ljava/lang/String;` — строка, `[B` — массив байт. Возвращаемый тип стоит в конце сигнатуры: `()Z` значит «без аргументов, возвращает boolean».

| Инструкция | Что делает |
|-----------|------------|
| `const/4 v0, 0x1` | положить маленькое число (4 бита) в регистр |
| `const/16 v0, 0x100` | положить 16-битное число |
| `const-string v0, "x"` | положить ссылку на строку |
| `invoke-static {p0}, Lc;->m()Z` | вызвать статический метод |
| `invoke-virtual {p0}, Lc;->m()Z` | вызвать виртуальный метод |
| `move-result v0` | забрать результат вызова |
| `if-eqz v0, :cond` | переход, если значение == 0 |
| `return v0` | вернуть значение |
| `sget-object v0, Lc;->F:Lx;` | прочитать статическое поле |

## Патч не только константы: условные переходы и вызовы

Наш пример был тривиальным: метод сразу возвращал `0x0`. Реальные проверки выглядят иначе:

```smali
.method public isPremium()Z
    .locals 2
    invoke-static {p0}, Lcom/example/License;->verify(Landroid/content/Context;)Z
    move-result v0
    if-eqz v0, :locked
    const/4 v1, 0x1
    return v1
    :locked
    const/4 v1, 0x0
    return v1
.endmethod
```

Здесь три пути патча. **Первый** — заменить результат вызова: после `move-result v0` вставить `const/4 v0, 0x1`, тогда исход проверки игнорируется. **Второй** — превратить `if-eqz` в безусловный переход: заменить `if-eqz v0, :locked` на `goto :unlocked` (нужно добавить метку и ветку). **Третий** — заменить сам вызов `invoke-static ... verify` на `const/4 v0, 0x1`, убрав `move-result`. Каждый способ рабочий; выбирайте тот, что требует меньше правок.

Полезно помнить, что `const/4` умеет только 4-битные значения, то есть от -8 до 7. Для большего используйте `const/16` или `const`. И следите, чтобы регистр, который вы перезаписываете, больше не использовался дальше — иначе сломаете логику.

## Reference: команды apktool и вспомогательных утилит

| Команда | Назначение |
|---------|------------|
| `apktool d app.apk -o out` | разобрать APK |
| `apktool d -s app.apk` | не декодировать DEX (только ресурсы) |
| `apktool d -r app.apk` | не декодировать ресурсы |
| `apktool b out -o new.apk` | собрать APK обратно |
| `apktool if framework.apk` | установить framework-ресурсы |
| `zipalign -p 4 in.apk out.apk` | выровнять APK |
| `apksigner sign --ks ks --out s.apk a.apk` | подписать APK |
| `apksigner verify -v s.apk` | проверить подпись |

## Multidex и ресурсы

Когда классов больше 65 536, APK разбивается на несколько DEX. apktool раскладывает их в `smali/`, `smali_classes2/`, `smali_classes3/` и так далее. Искать метод нужно **по всем** каталогам: `grep -rn "isPremium" app_out/smali*`. Забыть про `smali_classes2` — классическая ошибка, из-за которой патч «не находится».

Ресурсы лежат в `res/`. Строки — в `res/values/strings.xml`; если проверка сравнивается со строкой из ресурсов, её тоже можно править. `AndroidManifest.xml` после разбора — обычный XML, где видно разрешения, экспортированные компоненты и точку входа (`<activity>` с `android.intent.action.MAIN`).

## Проверка подписи в рантайме

Некоторые приложения при старте читают свою подпись и сравнивают с ожидаемым хешем. Патч smali в таком случае приведёт к падению: приложение заметит несоответствие. Обходы:

- найти функцию проверки и пропатчить её так же, как `isPremium` — вернуть ожидаемый хеш;
- использовать Frida-хук, подменяющий `PackageManager.getPackageInfo` и возвращающий оригинальные `signatures`;
- подписать патч **тем же** ключом, если он утёк или известен.

Последний вариант надёжнее всего, но требует оригинального ключа. Чаще всего применяют первый.

## Если не сработало

- **APK не собирается.** Обновите apktool; добавьте `--use-aapt2`; установите framework-ресурсы через `apktool if`.
- **Собрался, но падает при запуске.** Вероятно, задели регистр или метку. Сравните с оригиналом (`diff`) и убедитесь, что изменена только нужная строка.
- **Устанавливается, но проверка всё равно не проходит.** Проверка может быть серверной или продублирована в нативном коде (`lib/*.so`). Тогда патч smali бесполезен — нужен Frida или разбор нативной библиотеки.
- **`INSTALL_FAILED_UPDATE_INCOMPATIBLE`.** Удалите оригинальное приложение перед установкой патча.

## Сравнение с другими подходами

Патч smali даёт **постоянное** изменение: работает без инструментов на устройстве, не требует root. Но он грубый: любая обфускация или проверка целостности его ломает. Frida даёт **временное** изменение, но гибкое и устойчивое к обфускации. На практике сначала исследуют поведение через Frida, а постоянный патч делают, когда логика понятна.

## Работа с `apktool.yml` и повторными сборками

Файл `apktool.yml` хранит версию apktool, версию SDK и параметры сборки. Он важен, когда вы переносите распакованную папку на другую машину: если версия apktool не совпадает, сборка может дать иной результат. Держите `apktool.yml` рядом с исходниками и не удаляйте его.

При повторных правках удобно собирать во временный файл и проверять установкой на эмуляторе. Держите чистую копию распакованного приложения: если патч сломал логику, `diff -r` покажет ровно то, что вы изменили, и откат будет мгновенным.
