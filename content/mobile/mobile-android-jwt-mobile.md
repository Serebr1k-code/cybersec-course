## Вопрос, с которого всё начинается

Перехватив трафик, ты видишь строку вида `eyJhbGciOi...`. Это **JWT** — токен доступа, который
приложение предъявляет серверу. Можно ли его подделать? Зависит от того, как он подписан и
как сервер проверяет подпись. Разберём токен целиком.

## Наш пример: захваченный токен

У нас есть токен из заголовка `Authorization`:

```bash
$ cat token.txt
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjMiLCJyb2xlIjoidXNlciJ9.K7g...
```

Весь урок ведём этот токен.

## Шаг 1: что такое JWT

**JWT** (JSON Web Token) — строка из трёх частей, разделённых точками:
`header.payload.signature`. Каждая часть — Base64url. Header описывает алгоритм подписи,
payload — данные (claims), signature — подпись первых двух частей.

```bash
$ cut -d. -f1 token.txt | base64 -d
{"alg":"HS256","typ":"JWT"}
```

`alg: HS256` — подпись симметричным ключом (HMAC). Значит, для проверки нужен общий секрет.

## Шаг 2: читаем payload

Payload не зашифрован — он лишь закодирован. Это важно: любой может прочитать claims.

```bash
$ cut -d. -f2 token.txt | base64 -d
{"sub":"123","role":"user"}
```

Мы видим роль `user`. Естественный вопрос: можно ли поднять её до `admin`?

## Шаг 3: подделка — alg: none

Классическая ошибка серверов — доверять полю `alg` из токена. Если подменить header на
`{"alg":"none"}` и убрать подпись, неаккуратный сервер примет токен без проверки:

```bash
$ printf '%s' '{"alg":"none","typ":"JWT"}' | base64 -w0
eyJhbGciOiJub25lIiwidHlwIjoiSldUIn0
```

Собираем `header.payload.` (с пустой подписью) и отправляем. Если API принимает — критическая
находка: подпись не проверяется вообще.

## Шаг 4: подделка — слабый секрет

Если сервер честно проверяет HMAC, но секрет слабый, его можно подобрать офлайн: у нас есть
известный `header.payload` и подпись, значит, мы можем перебирать секреты, пока не совпадёт.
Это делается **офлайн** (словарём), а не запросами к серверу.

```bash
$ hashcat -m 16500 token.txt wordlist.txt
eyJ...:secret123
```

Найденный секрет позволяет подписать любой payload — например, `role: admin`.

## Шаг 5: хранение токена на устройстве

Второй вопрос — где приложение хранит токен:

```bash
$ grep -rn 'getSharedPreferences\|EncryptedSharedPreferences' smali/ | head
```

Если токен лежит в обычных `SharedPreferences` (открытый XML в песочнице), на root-устройстве
или через бэкап его можно вынуть. Правильно — `EncryptedSharedPreferences` или Keystore.

## Шаг 6: проверка `alg` на сервере

Главная причина обеих атак — сервер берёт алгоритм из токена. Правильный сервер фиксирует
ожидаемый алгоритм (`HS256` или `RS256`) и **отвергает** токен с другим `alg`. Тогда `none` и
подмена HS/RS не проходят. Это первое, что проверяют при аудите JWT.

## Шаг 7: RS256 и подмена на HS256

Если сервер использует асимметричный `RS256` (подпись приватным ключом, проверка публичным),
есть атака «algorithm confusion»: подсунуть `alg: HS256` и подписать **публичным** ключом как
HMAC-секретом. Уязвимый сервер, не проверяя тип алгоритма, примет такую подпись. Защита —
жёсткая фиксация алгоритма.

## Шаг 8: claims, которые надо проверять

Кроме подписи, сервер обязан проверять claims: `exp` (срок), `iss` (кто выдал), `aud` (для
кого), `nbf` (не раньше). Если `exp` не проверяется, утекший токен живёт вечно. Если не
проверяется `aud`, токен другого приложения подходит этому.

## Шаг 9: как проверить JWT на пентесте

1. Декодировать header и payload (base64).
2. Посмотреть `alg`; попробовать `none`.
3. Если HS256 — попробовать подобрать секрет офлайн.
4. Проверить, меняются ли claims без переподписи (если да — подпись не проверяется).
5. Проверить `exp`, `iss`, `aud`.
6. Посмотреть, где токен хранится на устройстве.

## Шаг 10: как защищают правильно

Фиксировать алгоритм на сервере, использовать сильные секреты (или RS256), обязательно
проверять `exp`/`iss`/`aud`, хранить токен в Keystore/EncryptedSharedPreferences, ставить
короткий срок жизни и refresh-механизм. JWT — не «подписанная строка», а контракт: и клиент, и
сервер обязаны проверять свою часть.

## Что мы теперь знаем

- JWT = header.payload.signature, части лишь закодированы Base64url.
- `alg: none` и слабый секрет ломают подпись.
- Сервер должен фиксировать алгоритм и проверять claims.
- Токен на устройстве хранят в Keystore/EncryptedSharedPreferences.
- Подбор секрета — офлайн-задача, не штурм сервера.
