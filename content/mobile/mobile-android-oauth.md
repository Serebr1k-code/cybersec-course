## Вопрос, с которого всё начинается

Приложение логинит через «Войти через Google». Казалось бы, всё делает провайдер — приложение
только принимает результат. Но именно на стыке «приложение ↔ браузер ↔ провайдер» и живут
ошибки: неправильный `redirect_uri`, подделываемый `scheme`, отсутствие PKCE. Как это проверить?

## Наш пример: поток авторизации

Разбор приложения показал такой поток:

```bash
$ grep -rn 'redirect_uri\|oauth\|customtabs' smali/ | head
smali/com/example/auth/OAuth.smali: const-string v1, "myapp://callback"
smali/com/example/auth/OAuth.smali: const-string v2, "com.android.chrome"
```

Приложение использует `redirect_uri = myapp://callback` и открывает страницу авторизации в
Chrome (Custom Tabs). Весь урок ведём этот поток.

## Шаг 1: как устроен OAuth в мобильном

Классическая схема — **Authorization Code**:
1. Приложение открывает браузер на странице авторизации провайдера.
2. Пользователь входит и соглашается.
3. Провайдер перенаправляет браузер на `redirect_uri` с **кодом авторизации**.
4. Приложение ловит код и меняет его на токен.

В мобильных вместо обычного редиректа используют **deep link** — приложение регистрирует
схему (`myapp://`), и система открывает его по этой ссылке.

## Шаг 2: почему браузер, а не WebView

Раньше приложения показывали страницу логина во встроенном **WebView** (свой мини-браузер
внутри приложения). Это опасно: приложение видит вводимый пароль. Поэтому современный
стандарт — **Custom Tabs**: настоящий браузер поверх приложения, где пользователь видит
адресную строку и может проверить домен. Если приложение всё ещё логинит через WebView — это
находка сама по себе.

## Шаг 3: где ломается redirect_uri

Главная уязвимость — **схема без верификации**. Приложение регистрирует `myapp://callback`, но
любое другое приложение может зарегистрировать ту же схему. Тогда система спросит
пользователя, какое приложение открыть, или отдаст код вредоносному. Перехватив код, атакующий
меняет его на токен.

```xml
<!-- в манифесте приложения -->
<intent-filter>
  <data android:scheme="myapp" android:host="callback" />
</intent-filter>
```

Схема `myapp` — не защищена: она не привязана к подписи приложения.

## Шаг 4: проверка на перехват

Проверяем, можно ли перехватить код. Регистрируем свою активность на ту же схему и смотрим,
приходит ли код нам:

```bash
$ adb shell am start -a android.intent.action.VIEW -d 'myapp://callback?code=TEST'
```

Если наша активность открывается — схема не защищена. В реальной атаке код приходит от
провайдера, и его перехватывает приложение-жертва-схемы.

## Шаг 5: PKCE — защита от перехвата

**PKCE** (Proof Key for Code Exchange) спасает именно от перехвата кода: приложение генерирует
случайный `code_verifier`, шлёт его хэш (`code_challenge`) при запросе, а при обмене кода
предъявляет сам `code_verifier`. Без verifier код бесполезен. Если PKCE нет — перехват кода
даёт токен.

```bash
$ grep -rn 'code_challenge\|code_verifier' smali/
# пусто → PKCE отсутствует → находка
```

## Шаг 6: другие ошибки потока

- **`redirect_uri` без привязки к приложению**: любая схема, которую можно зарегистрировать.
- **`state` не проверяется**: CSRF в OAuth — можно подсунуть свой код.
- **Токен в URL**: утекает через историю, логи, referer.
- **Свой WebView вместо Custom Tabs**: перехват пароля.
- **`client_secret` в приложении**: секрет не может быть секретом в мобильном клиенте.

## Шаг 7: AppAuth и «правильный» поток

Библиотека **AppAuth** реализует корректный поток: Custom Tabs, PKCE, проверка `state`,
верификация редиректа. Но даже AppAuth не спасёт, если схема редиректа выбрана небезопасно
(например, `com.example.app:/oauth2redirect` — тоже перехватывается). Правильный вариант для
Android — **App Links** (`https://`-редирект с подтверждением домена через
`assetlinks.json`), которые нельзя перехватить чужой схемой.

## Шаг 8: как проверить безопасность редиректа

1. Посмотреть `redirect_uri` в коде.
2. Если схема кастомная — попробовать перехватить (шаг 4).
3. Если `https` — проверить, есть ли `assetlinks.json` и включён ли `autoVerify`.
4. Проверить наличие PKCE и `state`.

```bash
$ grep -rn 'autoVerify\|assetlinks' AndroidManifest.xml
```

## Шаг 9: как защищают правильно

Правильный мобильный OAuth: App Links (`https://`) с верификацией домена, PKCE обязательно,
проверка `state`, никаких `client_secret` в клиенте, обмен кода только по защищённому каналу.
Тогда перехватить код чужой схемой нельзя, а без `code_verifier` он бесполезен.

## Что мы теперь знаем

- Мобильный OAuth использует deep link-редирект.
- Кастомная схема (`myapp://`) перехватывается другим приложением.
- PKCE защищает от перехвата кода; без него код даёт токен.
- WebView для логина и `client_secret` в клиенте — находки.
- Правильно — App Links (`https`) + PKCE + проверка `state`.
