## Вопрос, с которого всё начинается

Приложение логинит через «Войти через Google». Казалось бы, всё делает провайдер — приложение
только принимает результат. Но именно на стыке «приложение ↔ браузер ↔ провайдер» и живут
ошибки: неправильный `redirect_uri`, подделываемый `scheme`, отсутствие PKCE. Как это проверить?

## Наш пример: поток авторизации

Разбор приложения показал такой поток:

```bash
$ grep -rn 'redirect_uri\|oauth\|customtabs' smali/ | head
smali/com/example/auth/OAuth.smali: const-string v1, "myapp://callback"
smali/com/example/auth/OAuth.smali: const-string v2, "com.android.chrome"
```

Приложение использует `redirect_uri = myapp://callback` и открывает страницу авторизации в
Chrome (Custom Tabs). Весь урок ведём этот поток.

## Шаг 1: как устроен OAuth в мобильном

Классическая схема — **Authorization Code**:
1. Приложение открывает браузер на странице авторизации провайдера.
2. Пользователь входит и соглашается.
3. Провайдер перенаправляет браузер на `redirect_uri` с **кодом авторизации**.
4. Приложение ловит код и меняет его на токен.

В мобильных вместо обычного редиректа используют **deep link** — приложение регистрирует
схему (`myapp://`), и система открывает его по этой ссылке.

## Шаг 2: почему браузер, а не WebView

Раньше приложения показывали страницу логина во встроенном **WebView** (свой мини-браузер
внутри приложения). Это опасно: приложение видит вводимый пароль. Поэтому современный
стандарт — **Custom Tabs**: настоящий браузер поверх приложения, где пользователь видит
адресную строку и может проверить домен. Если приложение всё ещё логинит через WebView — это
находка сама по себе.

## Шаг 3: где ломается redirect_uri

Главная уязвимость — **схема без верификации**. Приложение регистрирует `myapp://callback`, но
любое другое приложение может зарегистрировать ту же схему. Тогда система спросит
пользователя, какое приложение открыть, или отдаст код вредоносному. Перехватив код, атакующий
меняет его на токен.

```xml
<!-- в манифесте приложения -->
<intent-filter>
  <data android:scheme="myapp" android:host="callback" />
</intent-filter>
```

Схема `myapp` — не защищена: она не привязана к подписи приложения.

## Шаг 4: проверка на перехват

Проверяем, можно ли перехватить код. Регистрируем свою активность на ту же схему и смотрим,
приходит ли код нам:

```bash
$ adb shell am start -a android.intent.action.VIEW -d 'myapp://callback?code=TEST'
```

Если наша активность открывается — схема не защищена. В реальной атаке код приходит от
провайдера, и его перехватывает приложение-жертва-схемы.

## Шаг 5: PKCE — защита от перехвата

**PKCE** (Proof Key for Code Exchange) спасает именно от перехвата кода: приложение генерирует
случайный `code_verifier`, шлёт его хэш (`code_challenge`) при запросе, а при обмене кода
предъявляет сам `code_verifier`. Без verifier код бесполезен. Если PKCE нет — перехват кода
даёт токен.

```bash
$ grep -rn 'code_challenge\|code_verifier' smali/
# пусто → PKCE отсутствует → находка
```

## Шаг 6: другие ошибки потока

- **`redirect_uri` без привязки к приложению**: любая схема, которую можно зарегистрировать.
- **`state` не проверяется**: CSRF в OAuth — можно подсунуть свой код.
- **Токен в URL**: утекает через историю, логи, referer.
- **Свой WebView вместо Custom Tabs**: перехват пароля.
- **`client_secret` в приложении**: секрет не может быть секретом в мобильном клиенте.

## Шаг 7: AppAuth и «правильный» поток

Библиотека **AppAuth** реализует корректный поток: Custom Tabs, PKCE, проверка `state`,
верификация редиректа. Но даже AppAuth не спасёт, если схема редиректа выбрана небезопасно
(например, `com.example.app:/oauth2redirect` — тоже перехватывается). Правильный вариант для
Android — **App Links** (`https://`-редирект с подтверждением домена через
`assetlinks.json`), которые нельзя перехватить чужой схемой.

## Шаг 8: как проверить безопасность редиректа

1. Посмотреть `redirect_uri` в коде.
2. Если схема кастомная — попробовать перехватить (шаг 4).
3. Если `https` — проверить, есть ли `assetlinks.json` и включён ли `autoVerify`.
4. Проверить наличие PKCE и `state`.

```bash
$ grep -rn 'autoVerify\|assetlinks' AndroidManifest.xml
```

## Шаг 9: как защищают правильно

Правильный мобильный OAuth: App Links (`https://`) с верификацией домена, PKCE обязательно,
проверка `state`, никаких `client_secret` в клиенте, обмен кода только по защищённому каналу.
Тогда перехватить код чужой схемой нельзя, а без `code_verifier` он бесполезен.

## Шаг 10: PKCE подробнее

**PKCE** (Proof Key for Code Exchange) устроен так: приложение генерирует случайную строку
`code_verifier`, считает от неё хэш `code_challenge` и шлёт хэш при запросе авторизации. При
обмене кода на токен приложение предъявляет исходный `code_verifier`, и сервер сверяет его с
хэшем. Перехватив код, атакующий не знает `code_verifier` — и код бесполезен. Проверяя
приложение, убедись, что PKCE есть **и** что `code_verifier` действительно случаен
(используется `SecureRandom`, а не константа).

## Шаг 11: App Links и assetlinks.json

**App Links** — это `https://`-редирект, который нельзя перехватить чужой схемой: система
открывает ссылку в приложении только если домен подтверждён файлом `assetlinks.json`,
опубликованным на сервере. Проверяют: есть ли `android:autoVerify="true"`, доступен ли
`https://<host>/.well-known/assetlinks.json`, и совпадает ли отпечаток подписи приложения с
указанным в файле. Если файл неверный или отсутствует — App Link не работает, и система
открывает ссылку в браузере, что тоже ломает поток.

## Шаг 12: инъекция через Custom Tabs

Custom Tabs запускаются системой, но приложение задаёт параметры (пакет браузера, extras). Если
приложение позволяет **выбрать произвольный браузер** или не проверяет, кто вернул результат,
возможна подмена: вредоносное приложение регистрирует тот же intent и перехватывает поток
авторизации. Поэтому проверяют, жёстко ли задан пакет браузера и проверяется ли `state`.

## Шаг 13: чек-лист OAuth

1. Открывается ли логин в Custom Tabs (а не WebView)?
2. Каков `redirect_uri` — кастомная схема или App Link?
3. Есть ли PKCE и `state`?
4. Нет ли `client_secret` в клиенте?
5. Проверяется ли домен при возврате кода?

## Если не сработало

Если перехватить код не удаётся, возможно, приложение использует App Links с подтверждённым
доменом — это правильная конфигурация. Тогда проверь другие слабости потока: отсутствие PKCE,
непроверяемый `state`, токен в URL. И помни: без PKCE даже защищённый App Link оставляет окно
для CSRF, если `state` не проверяется.
## Полный прогон: перехват кода авторизации

**Шаг A.** Разбираем поток: `redirect_uri = myapp://callback`, PKCE отсутствует.

**Шаг B.** Проверяем, можно ли перехватить схему:

```bash
$ adb shell am start -a android.intent.action.VIEW -d 'myapp://callback?code=TEST'
```

Наша активность открывается — схема не защищена.

**Шаг C.** В реальной атаке вредоносное приложение регистрирует ту же схему и получает код,
когда провайдер перенаправляет браузер.

**Шаг D.** Меняем код на токен: без PKCE сервер принимает код от любого клиента, знающего
`redirect_uri`.

**Шаг E.** Фиксируем: отсутствие PKCE + кастомная схема = перехват. Правильная конфигурация —
App Links (`https://`) + PKCE + проверка `state`.

## Частые ошибки

- Считать, что раз используется провайдер, поток безопасен.
- Не проверить, включён ли PKCE (он может быть «на словах», а не в запросе).
- Путать `state` (защита от CSRF) и PKCE (защита от перехвата) — это разные механизмы.
- Игнорировать `client_secret` в клиенте: он там не должен быть.
## Как это устроено внутри

OAuth — это про делегирование: приложение не получает пароль пользователя, а получает
**разрешение** действовать от его имени. Отсюда и вся модель угроз. Браузер нужен, чтобы
пользователь видел настоящий домен провайдера и вводил пароль не приложению, а провайдеру.
Custom Tabs сохраняют эту границу, WebView её размывают.

**redirect_uri** — точка, куда провайдер возвращает результат. В вебе это доверенный
`https`-адрес, зарегистрированный у провайдера. В мобильном приложении своего «адреса» нет,
поэтому используют схему, и здесь начинается слабое место: схему регистрирует ОС, а не
провайдер, и её может занять любое приложение. App Links исправляют это, привязывая `https` к
подписи приложения через `assetlinks.json`.

**PKCE** решает проблему перехвата иначе: даже если код утёк, без `code_verifier` он бесполезен.
Поэтому современный чек-лист мобильного OAuth короткий: Custom Tabs (не WebView), App Links
(не кастомная схема), PKCE, проверка `state`, никаких секретов в клиенте. Каждый пункт закрывает
свой класс атак, и вместе они дают поток, который нельзя перехватить с другого приложения.
## Типичный сценарий на реальном устройстве

Ты тестируешь приложение с входом через провайдера. Смотришь манифест: `redirect_uri` —
кастомная схема `myapp://callback`, PKCE отсутствует. Регистрируешь свою активность на ту же
схему и убеждаешься, что система может отдать ей код. В реальной атаке вредоносное приложение
получает код и меняет его на токен, потому что без PKCE сервер не проверяет, тот ли клиент
обменивает код.

Дальше проверяешь альтернативы: используется ли WebView вместо Custom Tabs (тогда виден
пароль), проверяется ли `state` (иначе CSRF), нет ли `client_secret` в клиенте. В отчёт идёт
цепочка «кастомная схема без PKCE → перехват кода → захват аккаунта», и рекомендация
перейти на App Links с PKCE и проверкой `state`. Сценарий ценен тем, что показывает: проблема
не в провайдере, а в том, как приложение принимает результат.
## Что мы теперь знаем

- Мобильный OAuth использует deep link-редирект.
- Кастомная схема (`myapp://`) перехватывается другим приложением.
- PKCE защищает от перехвата кода; без него код даёт токен.
- WebView для логина и `client_secret` в клиенте — находки.
- Правильно — App Links (`https`) + PKCE + проверка `state`.
