## Вопрос, с которого всё начинается

Банк присылает код подтверждения в уведомлении. Через секунду деньги уходят, хотя жертва
ничего не подтверждала. Как атакующий узнал код? Через сервис, который создан ровно для
чтения уведомлений — **NotificationListenerService**. Разберём, как это работает.

## Наш пример: приложение «Оптимизатор батареи»

Пользователь ставит «оптимизатор», тот просит доступ к уведомлениям — «чтобы не беспокоить
вас лишним». В декомпилированном коде находим:

```java
public class Listener extends NotificationListenerService {
    @Override
    public void onNotificationPosted(StatusBarNotification sbn) {
        Bundle e = sbn.getNotification().extras;
        String title = e.getString(Notification.EXTRA_TITLE);
        String text  = e.getString(Notification.EXTRA_TEXT);
        upload(title + ": " + text);
    }
}
```

Метод `onNotificationPosted` вызывается на **каждое** новое уведомление в системе. `extras`
содержит заголовок и текст. Всё, что приходит в уведомлении, уходит на сервер атакующего.

## Шаг 1: как сервис получает доступ

NotificationListenerService подключается к системному `NotificationManagerService`. Чтобы он
начал получать уведомления, пользователь должен включить его в «Доступе к уведомлениям»
(Settings → Notifications → Device & app notifications). Это отдельное согласие, не
разрешение из манифеста.

В манифесте объявление выглядит так:

```xml
<service android:name=".Listener"
         android:exported="true"
         android:permission="android.permission.BIND_NOTIFICATION_LISTENER_SERVICE">
    <intent-filter>
        <action android:name="android.service.notification.NotificationListenerService"/>
    </intent-filter>
</service>
```

## Шаг 2: что именно видно

Сервис видит уведомления **всех** приложений, которые их показывают: SMS, мессенджеры, почта,
банки, менеджеры паролей. Если приложение показывает OTP в уведомлении, код попадает к
слушателю. Это делает сервис идеальным инструментом для перехвата одноразовых кодов —
основного способа подтверждения операций.

Дополнительно сервис может **отменять** уведомления (`cancelNotification`), то есть скрывать
от пользователя сообщения о списании средств. Пользователь не видит тревожного уведомления,
пока деньги уже ушли.

## Шаг 3: фильтрация по нужному приложению

Малварь редко читает всё подряд — она фильтрует по пакету:

```java
if (sbn.getPackageName().equals("com.bank.app")) {
    String otp = extractDigits(e.getString(Notification.EXTRA_TEXT));
    sendOtp(otp);
}
```

Так из потока уведомлений вычленяется только банковский OTP. Полезно искать в коде сравнение
`getPackageName()` с конкретными пакетами банков.

## Шаг 4: как обнаружить включённый слушатель

Проверяем настройку доступа к уведомлениям:

```bash
$ adb shell settings get secure enabled_notification_listeners
com.evil/.Listener:com.evil
```

В норме там либо пусто, либо только системные/легитимные сервисы. Посторонний пакет —
красный флаг. Также полезен `dumpsys notification`:

```bash
$ adb shell dumpsys notification | grep -i listener
```

## Шаг 5: отличие от чтения SMS

Исторически малварь читала SMS напрямую (permission `READ_SMS`). Но с Android 4.4 это
разрешение доступно только приложению по умолчанию для SMS, поэтому атакующие перешли на
два обходных пути: `READ_SMS` при получении роли default-SMS, и чтение уведомлений. Второй
путь тише: не нужно становиться SMS-приложением, достаточно «доступа к уведомлениям».

## Шаг 6: как аудировать приложение

Шаги анализа:

1. Найти в манифесте сервис с `BIND_NOTIFICATION_LISTENER_SERVICE`.
2. Прочитать `onNotificationPosted`/`onNotificationRemoved`.
3. Проверить, фильтрует ли он по банковским пакетам и куда отправляет данные.
4. Посмотреть, вызывает ли `cancelNotification` (сокрытие уведомлений).
5. Оценить, оправдан ли доступ назначением приложения.

## Шаг 7: что писать в отчёте

Формулировка: приложение читает уведомления всех приложений и передаёт их на внешний сервер,
что позволяет перехватывать OTP и скрывать сообщения о транзакциях. MITRE: Collection через
Notifications, Input Capture. Отдельно отметьте, что согласие даётся пользователем вручную и
может быть отозвано — это ограничение радиуса поражения.

## Шаг 8: рекомендации

- Не выдавать доступ к уведомлениям приложениям, которым он не нужен.
- Банкам — не полагаться только на OTP из уведомлений; использовать push с криптографией.
- Платформе — показывать явное предупреждение о том, что слушатель увидит все уведомления.
- Приложениям — не показывать чувствительные коды в открытом виде в уведомлении.

## Что мы теперь знаем

- NotificationListenerService читает уведомления всех приложений.
- Это прямой путь к перехвату OTP и сокрытию уведомлений банка.
- Включается отдельным согласием в настройках, а не разрешением манифеста.
- Обнаруживается через `enabled_notification_listeners`.

## Шаг 9: как читается поток уведомлений

`NotificationListenerService` получает колбэки от системы:

```java
@Override
public void onNotificationPosted(StatusBarNotification sbn) {
    Notification n = sbn.getNotification();
    Bundle ex = n.extras;
    String title = ex.getString(Notification.EXTRA_TITLE);
    String text  = ex.getString(Notification.EXTRA_TEXT);
    String pkg   = sbn.getPackageName();
    // ...
}
```

`StatusBarNotification` даёт имя пакета и время; `extras` — заголовок, текст и (иногда) большие
текстовые блоки (`EXTRA_BIG_TEXT`). Для OTP-перехвата злоумышленнику достаточно вызвать
`onNotificationPosted` и регуляркой вытащить цифры.

## Шаг 10: практика — вылавливание OTP

Минимальный фильтр по коду подтверждения выглядит так (smali-эквивалент для статического
анализа — ищите `Pattern.compile` рядом с `EXTRA_TEXT`):

```java
Matcher m = Pattern.compile("(\\d{4,8})").matcher(text);
if (m.find()) {
    String otp = m.group(1);
    exfil(pkg, otp);          // куда-нибудь в сеть
}
```

Обратите внимание: сервис не просит доступ к SMS и не читает другие приложения напрямую — он
просто читает то, что **сама система** показала пользователю. Именно поэтому такой перехват
почти не требует разрешений и плохо заметен.

## Шаг 11: как включить и как это детектится

Включение — только с согласия пользователя: `Settings > Notifications > Device & app
notifications > <app>`. Включённые слушатели хранятся в настройке:

```bash
$ adb shell settings get secure enabled_notification_listeners
com.example.helper/.NotifListener:com.example.helper
```

Проверка списка — базовый детект. Ещё один признак — сервис объявляет
`BIND_NOTIFICATION_LISTENER_SERVICE` в манифесте. В новых версиях Android Google ужесточает
правила для сайдлоаженных слушателей, но на устройствах с более старым API поверхность остаётся.

## Шаг 12: защита

- Не кладите OTP в текст уведомления, если можете показать его только внутри приложения.
- Используйте `setLocalOnly(true)`, чтобы уведомление не уходило на часы/в облако.
- Для банков — показывайте код в самом приложении, а в шторку выводите нейтральный текст.
- При аудите ищите слушатели, которые пересылают содержимое уведомлений в сеть.

## Таблица: ключевые поля и методы

| Поле/метод | Значение |
|---|---|
| `onNotificationPosted` | вызывается на каждое новое уведомление |
| `sbn.getPackageName()` | источник уведомления |
| `EXTRA_TITLE` / `EXTRA_TEXT` | заголовок и текст |
| `onNotificationRemoved` | уведомление снято (для скрытия следов) |
| `settings get secure enabled_notification_listeners` | список активных слушателей |

## Крайние случаи и подводные камни

- Уведомление может приходить в `EXTRA_BIG_TEXT`, а не в `EXTRA_TEXT` — фильтр только по
  одному полю пропускает данные.
- Некоторые приложения используют `setPublicVersion`, и в шторку попадает урезанный текст.
- Слушатель видит уведомления **до** того, как пользователь их открыл, — задержки нет.
- Отмена уведомления слушателем (`cancelNotification`) скрывает его от жертвы.

## Что дальше / решение

Итог: `NotificationListenerService` — легальный API доступности, который превращается в
перехватчик OTP, если приложение-владелец недобросовестно. Детект прост: проверьте список
активных слушателей. В следующем уроке спустимся ещё ниже — к SELinux, который решает, что
вообще разрешено процессу на уровне ядра.

## Шаг 13: эволюция ограничений

Google постепенно сужает возможности слушателей: начиная с Android 15 запрос на роль
notification listener через `ACTION_NOTIFICATION_LISTENER_SETTINGS` для сайдлоаженных
приложений ограничивается, а явная выдача требует дополнительных условий. Но на устройствах с
более старым API и на кастомных прошивках поверхность остаётся, поэтому техника актуальна для
ретро-аудита и анализа уже установленной малвари.

## Шаг 14: чек-лист аудита приложения

1. Есть ли в манифесте `<service>` с `BIND_NOTIFICATION_LISTENER_SERVICE`?
2. Просит ли приложение `ACTION_NOTIFICATION_LISTENER_SETTINGS` при запуске?
3. Что делает `onNotificationPosted` — читает `extras`, логирует, шлёт в сеть?
4. Есть ли фильтр по пакетам банков/SMS-приложений?
5. Отменяет ли сервис уведомления (`cancelNotification`), скрывая их от жертвы?

Отрицательный ответ на 3–5 — обычный «уборщик уведомлений». Положительный хотя бы на один —
повод считать приложение потенциально вредоносным.

## Шаг 15: пример записи в отчёте

«Приложение `com.example.helper` регистрирует `NotificationListenerService`, который в
`onNotificationPosted` извлекает `EXTRA_TEXT` и отправляет совпадения регулярного выражения
`(\d{4,8})` на внешний хост. Это позволяет перехватывать одноразовые коды подтверждения
(OTP) без SMS-разрешений. Рекомендация: удалить слушателя, не размещать OTP в тексте
уведомлений.»

## Шаг 16: комбинация с другими API

По отдельности чтение уведомлений — уже перехват OTP, но в реальных банковских троянах это
лишь часть триады: **NotificationListenerService** читает код, **Accessibility Service**
нажимает кнопки в интерфейсе банка, а **overlay** (`SYSTEM_ALERT_WINDOW`) рисует поддельный
экран поверх настоящего. Вместе они позволяют провести перевод целиком без участия жертвы.

Полезные детали, которые стоит искать при реверсе:

- `onListenerConnected()` вызывается при подключении; в нём малварь часто вызывает
  `getActiveNotifications()`, чтобы сразу слить **уже висящие** в шторке уведомления.
- `getActiveNotifications()` возвращает массив `StatusBarNotification` — весь текущий поток.
- `cancelNotification(key)` скрывает уведомление от пользователя, «заметая следы» операции.
- `sbn.getPostTime()` и `getPackageName()` позволяют фильтровать только свежие сообщения от
  нужных банков, игнорируя шум.

Если приложение одновременно просит роль слушателя уведомлений и доступность, это почти
наверняка троян: легитимному приложению обе роли вместе нужны крайне редко.

## Шаг 17: как воспроизвести в лаборатории

Соберите минимальное приложение с сервисом-слушателем, включите его через настройки и
сгенерируйте тестовое уведомление:

```bash
$ adb shell cmd notification post -t 'Bank' tag 'Code 482913'
Notification posted
$ adb shell settings get secure enabled_notification_listeners
com.example.helper/.NotifListener:com.example.helper
```

Если в логах сервиса видно извлечённый код `482913`, — механизм перехвата воспроизведён.
Для аудита стороннего APK достаточно статически найти `Pattern.compile` рядом с `EXTRA_TEXT`:
это почти верный признак OTP-граббера.
