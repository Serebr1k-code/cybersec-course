## Вопрос, с которого всё начинается

В прошлом уроке мы встроили фаззер в библиотеку. Но что делать, если у нас только готовый
бинарник без исходников и без удобной функции? Пересобрать его нельзя, harness не написать.
И всё же фаззить хочется.

## Наш пример: утилита-конвертер

В приложении есть нативная утилита, которая принимает файл и что-то с ним делает:

```bash
$ file convert
convert: ELF 64-bit LSB executable, ARM aarch64, dynamically linked
$ ./convert sample.dat
parsed 12 records
```

Это отдельный процесс, а не библиотека. libFuzzer здесь не подходит — нужен фаззер,
который умеет работать с программой как с чёрным ящиком.

## Шаг 1: что такое AFL

AFL (*American Fuzzy Lop*) запускает программу снова и снова, каждый раз подсовывая новый
входной файл, и **наблюдает за покрытием**: какие ветви кода выполнились. Интересные входы
он сохраняет и мутирует дальше. Ключевое отличие от libFuzzer — AFL может работать с
готовым бинарником, а не только со встроенным harness.

## Шаг 2: два режима

- **Инструментированный** (`afl-clang-fast`): при сборке компилятор расставляет метки, и AFL
  точно знает покрытие. Быстро и точно, но нужны исходники.
- **QEMU-режим** (`afl-fuzz -Q`): AFL эмулирует процессор и наблюдает за исполнением без
  пересборки. Работает с любым бинарником, но медленнее.

Для нашего `convert` (только бинарник) берём QEMU-режим.

## Шаг 3: подготовка входов

AFL нужны начальные примеры — «семена». Положим пару корректных файлов:

```bash
$ mkdir -p in out
$ cp sample.dat in/
$ ls in/
sample.dat
```

Один-два валидных входа достаточно: AFL сам их мутирует. Но пустой корпус он не примет.

## Шаг 4: запуск

```bash
$ afl-fuzz -Q -i in -o out -- ./convert @@
american fuzzy lop 4.09c
┌─ process timing ─────────────────────────┐
│ run time : 0 days, 0 hrs, 3 min         │
│ exec speed : 812/sec                     │
├─ overall results ────────────────────────┤
│ cycles done : 1                          │
│ total paths : 47                         │
│ unique crashes : 2                       │
└──────────────────────────────────────────┘
```

`@@` — место, куда AFL подставляет имя входного файла. `total paths` — сколько путей
покрытия найдено, `unique crashes` — сколько уникальных падений. Падения лежат в
`out/default/crashes/`.

## Шаг 5: почему падения уникальны

AFL считает падения уникальными по «отпечатку» — адресу, где произошёл сбой. Два разных
бага в одном месте могут склеиться, а один баг, проявляющийся по-разному, — разойтись.
Поэтому после AFL всегда проверяют каждый файл из `crashes/` вручную или под отладчиком.

## Шаг 6: производительность на устройстве

На эмуляторе AFL в QEMU-режиме даёт сотни запусков в секунду, на реальном устройстве —
больше. Ускорить помогают: запуск под `taskset` (привязка к ядру), отключение лишних
проверок, `AFL_SKIP_CPUFREQ=1`. Главное — не гонять фаззер на боевом устройстве с данными:
падение может испортить хранилище.

## Шаг 7: связь с санитайзерами

Если исходники всё же есть, лучше собрать под `afl-clang-fast` **с ASan** — тогда AFL ловит
не только явные краши, но и тихие ошибки памяти. Это тема следующего урока.

## Что мы теперь знаем

- AFL работает с готовым бинарником в QEMU-режиме.
- Семена (корпус) обязательны, `@@` — подстановка входного файла.
- `total paths` и `unique crashes` — ключевые метрики.
- Падения лежат в `out/default/crashes/` и требуют ручной проверки.
- С ASan AFL находит больше ошибок.

## Куда дальше

В следующем уроке — `mobile-sanitizers`: как компиляторные проверки ASan и UBSan ловят
ошибки, которые сами по себе не приводят к падению. А пока запомни: AFL + семена + `@@` —
это способ фаззить то, для чего нельзя написать harness.

## Где пригодится

- **Пентест:** фаззинг готовых native-утилит.
- **Bug bounty:** падения в парсерах без исходников.
- **Разработка:** проверка собственных бинарников.
- **CTF:** автоматический поиск краша.
