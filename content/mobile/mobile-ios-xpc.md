## Вопрос, с которого всё начинается

Приложение хранит сообщения в шифрованном виде, но системный сервис умеет их синхронизировать.
Как приложение просит сервис о работе, не имея доступа к его памяти? Через **XPC** — механизм,
который прячет Mach-порты за удобным API и потому чаще встречается в реальных атаках.

## Наш пример: XPC-сервис

В бандле находим описание XPC-сервиса:

```xml
<key>XPCService</key>
<dict>
  <key>ServiceType</key><string>Application</string>
  <key>ServiceName</key><string>com.example.app.helper</string>
</dict>
```

Приложение общается с `com.example.app.helper` через `NSXPCConnection`. Сервис — отдельный
процесс со своими правами. Если он привилегированнее приложения, ошибки в нём дают повышение
привилегий.

## Шаг 1: XPC поверх Mach

XPC — слой над Mach IPC. Вместо ручной работы с портами вы открываете соединение по имени и
вызываете методы удалённого объекта. Внутри — тот же Mach: bootstrap находит порт сервиса,
сообщения ходят через порты. Но API удобнее, поэтому XPC-сервисы повсеместны — от системных
демонов до расширений.

## Шаг 2: типы XPC

| Тип | Где живёт | Кто может подключиться |
|---|---|---|
| Application XPC | внутри бандла | само приложение |
| Mach service | системный, через launchd | по правилам sandbox/entitlement |
| System XPC | системные демоны | ограниченно |
| Launch agent/daemon | отдельный процесс | по конфигу |

Наибольший интерес — **Mach services** и привилегированные helper-процессы: к ним можно
подключиться из другого процесса, если права позволяют.

## Шаг 3: проверка клиента

Ключевой вопрос: **проверяет ли сервер, кто подключился**. У клиента есть audit token, из
которого видна его подпись и entitlements:

```text
listener.shouldAcceptNewConnection = { conn in
    let token = conn.auditToken
    return validateSignature(token) && validateEntitlement(token)
}
```

Если проверки нет — любой процесс, дотянувшийся до порта, отдаёт команды. Это самая частая
уязвимость XPC.

## Шаг 4: поверхность атаки

- **Нет проверки клиента** — сервис доверяет любому подключившемуся.
- **Слабая проверка** — проверяется bundle id, который подделывается.
- **Опасные операции** — сервис выполняет привилегированные действия без валидации.
- **Type confusion** — сервер принимает объект не того класса при десериализации.

## Шаг 5: как искать XPC-сервисы

```bash
$ plutil -p /System/Library/LaunchDaemons/com.apple.example.plist | grep -i mach
  "MachServices" => { "com.apple.example.service" => 1 }
```

`MachServices` в plist показывает имя сервиса. Дальше проверяем, какие entitlements нужны для
подключения и проверяет ли сервис клиента.

## Шаг 6: пример атаки

Приложение находит привилегированный helper, подключается к его XPC-сервису и вызывает метод,
доступный только «своему» клиенту. Если сервис не проверил подпись, он выполнит привилегированную
операцию — и приложение получает то, чего не должно было.

## Шаг 7: защита

- Проверять audit token клиента на **каждом** соединении.
- Сверять подпись, а не только bundle id.
- Требовать конкретные entitlements у клиента.
- Валидировать все аргументы.
- Минимизировать привилегии сервиса.

## Что мы теперь знаем

- XPC — обёртка над Mach IPC.
- Сервисы: Application/Mach/System.
- Главная проверка — валидация клиента по audit token.
- Ошибки: нет проверки, слабая проверка, type confusion.
- MachServices в plist — карта поверхности атаки.

## Шаг 8: сериализация и NSSecureCoding

XPC передаёт между процессами не только простые значения, но и объекты — через сериализацию.
Классическая ошибка: сервер принимает объект без проверки его класса. В Objective-C для этого
используется `NSSecureCoding`, который требует явно перечислить допустимые классы. Если сервер
доверяет десериализованному объекту, атакующий может подсунуть объект другого класса и вызвать
неожиданное поведение (type confusion).

```text
// небезопасно: доверяем любому классу
id obj = [coder decodeObjectForKey:@"payload"];
// безопасно: ограничиваем классы
id obj = [coder decodeObjectOfClasses:allowedClasses forKey:@"payload"];
```

Правило простое: любой объект, пришедший из другого процесса, — недоверенный, и его класс
нужно ограничивать явно.

## Шаг 9: как искать уязвимый XPC-сервис

Практический план поиска:

1. Собрать список Mach-сервисов из `LaunchDaemons`/`LaunchAgents` и из plist приложения.
2. Для каждого найти реализацию `shouldAcceptNewConnection` и посмотреть, есть ли проверка.
3. Найти методы протокола XPC и понять, какие операции они выполняют.
4. Оценить привилегии сервиса: запущен ли он с повышенными правами.
5. Проверить, валидируются ли аргументы (особенно пути к файлам и команды).

Шаги 1–2 часто дают ответ сразу: если `shouldAcceptNewConnection` возвращает `true` без
проверки, сервис открыт любому, кто дотянулся до порта. Дальше остаётся оценить, насколько
опасны его операции — и это уже даёт серьёзную находку.

## Шаг 10: реальные кейсы и уроки

XPC-уязвимости регулярно встречаются в системных сервисах и в приложениях с привилегированными
helper-процессами. Общий сценарий: helper выполняет привилегированную операцию (например,
установку профиля или запись в защищённую директорию) и либо не проверяет клиента, либо
проверяет только bundle id. Атакующее приложение с тем же bundle id (после переподписи) или
вовсе без проверки получает возможность выполнить операцию от имени helper.

Уроки для защищающегося: проверяйте подпись клиента через audit token, ограничивайте
допустимые классы при десериализации, валидируйте пути и команды, а самому helper-процессу
давайте минимум привилегий. Уроки для атакующего: ищите сервисы, к которым можно подключиться,
и операции, которые они выполняют — самая простая цепочка «подключился → вызвал метод →
получил привилегированное действие» и есть классический XPC-баг.

## Шаг 11: XPC в расширениях и общие контейнеры

XPC тесно связан с расширениями iOS (share, widget, notification). Приложение и его расширения
— разные процессы, и общаются они через XPC или через общий контейнер App Group. Отсюда два
класса проблем. Первый: расширение может иметь **больше** прав, чем приложение (например,
доступ к определённым системным сервисам), и уязвимость в расширении даёт больше, чем в
приложении. Второй: данные, переданные через общий контейнер, не проверяются — приложение
доверяет тому, что положило расширение, и наоборот.

При аудите поэтому важно смотреть на каждое расширение отдельно: его entitlements, его
XPC-поверхность и то, какие данные оно пишет в общий контейнер. Часто именно расширение
оказывается самым слабым звеном, потому что ему уделяют меньше внимания, чем основному
приложению, а прав у него может быть не меньше.

## Шаг 12: что запомнить про XPC

XPC — это удобный фасад над Mach, и потому именно через него проходит большинство реальных
атак на iOS-приложения. Ключевой вопрос безопасности XPC всегда один: **проверяет ли сервер
клиента**. Проверка делается по audit token (подпись + entitlements), а не по имени или PID.
Дополнительно важно ограничивать классы при десериализации и валидировать все аргументы.
Поверхность атаки видна из plist (`MachServices`) и из кода (`shouldAcceptNewConnection`).
Практический вывод: ищите привилегированные helper-процессы и проверяйте, есть ли у них
проверка клиента — это самый прямой путь к находке высокого уровня.

## Шаг 13: итог и переход к рантайму

XPC замыкает практическую часть IPC: именно здесь привилегированные helper-процессы
подвергаются атаке чаще всего. Проверка клиента по audit token, ограничение классов при
десериализации и валидация аргументов — три столпа безопасного XPC-сервиса. Если хотя бы один
отсутствует, сервис превращается в путь повышения привилегий. В следующем уроке мы сменим
плоскость: от межпроцессного взаимодействия перейдём к **внутреннему устройству рантайма** —
как Objective-C ищет методы и почему динамика языка сама создаёт класс уязвимостей. Это
дополнит картину: IPC — про связь между процессами, а рантайм — про то, как устроен код внутри
одного процесса.

## Шаг 14: разбор реального XPC-дизайна

Разберём, как выглядит правильно спроектированный XPC-сервис, чтобы был эталон для сравнения.
Привилегированный helper регистрирует Mach-сервис и в обработчике нового соединения первым делом
извлекает audit token клиента. Затем он получает объект подписи через `SecCodeCopyGuestWithAttributes`
и проверяет два условия: подпись валидна и клиент имеет ожидаемый entitlement. Только после
этого соединение принимается. Каждый метод протокола дополнительно валидирует аргументы: пути
приводятся к каноническому виду и проверяются на выход за пределы разрешённой директории,
команды сверяются со списком допустимых, размеры ограничиваются.

Ошибки в такой конструкции встречаются в трёх местах. Первое — проверка делается один раз при
подключении, но не при каждом вызове, а соединение живёт долго, и клиент может сменить состояние.
Второе — проверяется только подпись, но не entitlements, поэтому любой подписанный Apple клиент
проходит. Третье — валидация путей делается «на глаз», без учёта символических ссылок и `..`,
что открывает path traversal. Все три — типичные находки, и все три проверяются чтением кода
обработчика. Поэтому при аудите XPC не достаточно найти `shouldAcceptNewConnection`; нужно
пройти по каждому методу протокола и убедиться, что аргументы валидируются на входе, а не
предполагаются доверенными.

## Шаг 15: вывод по XPC

Главная мысль урока: XPC-сервис — это доверенная сторона, и вся его безопасность сводится к
вопросу «проверяю ли я клиента и его данные». Проверка клиента — по audit token; проверка
данных — валидация аргументов и ограничение классов при десериализации. Привилегированный
helper без этих проверок — прямой путь к повышению привилегий, и именно поэтому XPC остаётся
одной из самых «урожайных» областей для находок в iOS.
