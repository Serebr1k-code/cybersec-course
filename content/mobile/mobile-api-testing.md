## Что такое тестирование мобильного API

Мобильное приложение — это клиент к серверному API. Многие уязвимости живут не в клиенте, а на сервере: сломанный контроль доступа (IDOR/BOLA), недостатки авторизации, инъекции, слабая валидация. Поскольку клиент можно распаковать, вы узнаёте все endpoint'ы, ключи и форматы запросов, что упрощает тестирование API. Цель модуля — научиться перехватывать, анализировать и атаковать мобильное API.

## Перехват трафика

Настройте прокси (mitmproxy/Burp), обойдите pinning (см. отдельный модуль), и все запросы приложения пойдут через вас. Далее:

- сохраните все endpoint'ы и методы;
- обратите внимание на заголовки авторизации (токены, API-ключи);
- изучите форматы запросов/ответов.

```bash
mitmproxy -p 8080
# или Burp: Proxy → Options → Add
```

Экспортируйте запросы в файл и импортируйте в Postman/Insomnia для удобной работы.

## Поиск endpoint'ов статически

Ещё до запуска можно найти все URL в APK:

```bash
grep -rhoE 'https?://[a-zA-Z0-9./?=_%:-]+' app_java | sort -u
grep -rhoE '"/api/[a-zA-Z0-9/_-]+"' app_java | sort -u
```

Это даёт карту API, даже если приложение не запускается.

## IDOR / BOLA

Broken Object Level Authorization — самая частая уязвимость API. Приложение запрашивает `/api/users/123`, а сервер не проверяет, что `123` принадлежит текущему пользователю. Тестирование: меняйте идентификаторы (числовые, UUID, email) и смотрите, отдаёт ли сервер чужие данные.

```bash
curl -H "Authorization: Bearer $TOKEN" https://api.example.com/users/124
```

Пробуйте: последовательные ID, чужие ID, отрицательные, большие, строковые.

## BFLA и авторизация

Broken Function Level Authorization — доступ к функциям, которые должны быть у админа. Проверяйте админские endpoint'ы обычным пользователем: `/api/admin/...`. Также проверяйте, что клиентские проверки роли дублируются на сервере (часто нет).

## Аутентификация и токены

- **JWT** — проверьте алгоритм (`none`, HS256 при RS256), слабый секрет, отсутствие проверки подписи.
- **OAuth** — redirect_uri, state, PKCE.
- **Сессии** — предсказуемость, отсутствие инвалидации.

```bash
# декодировать JWT
echo $JWT | cut -d. -f2 | base64 -d 2>/dev/null
```

## Инъекции и логика

Тестируйте параметры на SQL/NoSQL-инъекции, SSRF, command injection. В мобильном API часто встречаются NoSQL-инъекции (MongoDB): `{"$ne": null}` в поле пароля. Также проверяйте бизнес-логику: обход лимитов, повторное использование купонов, отрицательные суммы.

## Rate limiting и перебор

API часто не ограничивает попытки. Проверяйте перебор OTP, паролей, купонов. Но помните: онлайн-перебор большими словарями — EV-отрицательно; используйте точечные попытки и логику.

## Типичные ошибки и подводные камни

- **Не обойти pinning** — не увидите трафик.
- **Смотреть только клиент** — уязвимость на сервере.
- **Забыть про IDOR** — самая частая уязвимость.
- **Игнорировать заголовки** — токены и ключи там.
- **Не проверить админские endpoint'ы** — BFLA.
- **Верить клиентским проверкам** — сервер может их не дублировать.
- **Не тестировать логику** — обход лимитов часто overlooked.

## Что дальше / решение

План: обойдите pinning, перехватите трафик, соберите карту API, затем тестируйте IDOR/BOLA, BFLA, JWT, инъекции и логику. Используйте Postman/Insomnia для удобной работы с запросами. Помните: клиентские проверки не защищают — ищите серверные слабости. Мобильное API — самая «жирная» часть пентеста, потому что именно там сосредоточены реальные данные.

## Практический пример: IDOR в мобильном API

Разберём сквозной сценарий. Приложение показывает профиль пользователя, делая запрос `GET /api/v1/users/me` с токеном. Шаг 1: перехватываем запрос в Burp, видим структуру. Шаг 2: пробуем заменить `me` на числовой ID: `GET /api/v1/users/1`, `2`, `100`. Если сервер отдаёт чужие профили — IDOR. Шаг 3: меняем токен на токен другого аккаунта (создаём два) и проверяем, что данные не пересекаются. Шаг 4: пробуем админские endpoint'ы (`/api/v1/admin/users`) обычным токеном — BFLA. Шаг 5: проверяем параметры на NoSQL-инъекцию: отправляем `{"email": {"$ne": null}, "password": {"$ne": null}}` в логин.

Этот маршрут — стандартный для тестирования мобильного API: перехват → карта endpoint'ов → IDOR/BFLA → инъекции → логика. Часто именно здесь лежит флаг: чужие данные, админ-функция или обход лимита.

## Работа с JWT

Если API использует JWT, проверьте: алгоритм (`alg: none`), слабый секрет (брут по словарю), путаницу алгоритмов (HS256, подписанный публичным ключом RS256). Декодируйте payload, посмотрите поля ролей и ID — их подмена может дать доступ.

## Частые вопросы

«Не вижу трафик?» — обойдите pinning. «Токен не подходит?» — проверьте формат заголовка (`Bearer`). «IDOR не срабатывает?» — сервер проверяет владельца; пробуйте другие объекты. «Как тестировать быстро?» — импортируйте запросы в Postman. «Rate limit?» — не спамить; используйте точечные попытки.

## Расширенный чек-лист по тестированию мобильного API

Порядок. Первое: настройте прокси и обойдите pinning, чтобы видеть трафик. Второе: соберите карту endpoint'ов — из перехвата и статически (`grep` по URL в APK). Третье: изучите авторизацию — какой заголовок, какой формат токена. Четвёртое: тестируйте IDOR/BOLA — меняйте идентификаторы объектов (числовые, UUID, email) и проверяйте, отдаёт ли сервер чужие данные. Пятое: тестируйте BFLA — вызывайте админские функции обычным пользователем. Шестое: проверяйте JWT (alg=none, слабый секрет, путаница алгоритмов). Седьмое: проверяйте инъекции (NoSQL, SQL, SSRF) и логику (обход лимитов, повторное использование купонов). Восьмое: проверяйте rate limiting и перебор OTP/паролей — точечно, без мега-словарей.

## Создание двух аккаунтов

Для теста IDOR/BFLA удобно иметь два аккаунта: свой и «жертвы». Зарегистрируйте оба, сохраните токены, и проверяйте, может ли токен A получить данные B. Это самый надёжный способ выявить сломанный контроль доступа.

## Частые вопросы

«Трафик зашифрован?» — pinning. «Нет доступа к API без приложения?» — используйте токен из перехвата. «IDOR не срабатывает?» — объект проверяется по владельцу; пробуйте другие. «Как быстро перебирать?» — Postman коллекции + Newman. «Rate limit мешает?» — точечные попытки, распределение по времени.

## Что дальше / решение

Итог: API — самая «жирная» часть мобильного пентеста. Обойдите pinning, соберите карту, тестируйте IDOR/BFLA/JWT/инъекции/логику с двумя аккаунтами. Держите Postman/Insomnia для удобной работы. Клиентские проверки не защищают — ищите серверные слабости, именно там реальные данные и авторизация.

## Расширенный чек-лист по мобильному API

Соберите всё: endpoint'ы, заголовки, токены, форматы. Затем пройдите по классам уязвимостей. IDOR/BOLA — меняйте идентификаторы объектов и проверяйте доступ к чужим данным (два аккаунта). BFLA — вызывайте админ-функции обычным токеном. JWT — проверьте `alg`, секрет, подпись. Инъекции — NoSQL (`{"$ne": null}`), SQL, SSRF в URL-параметрах. Логика — обход лимитов, отрицательные суммы, повторное использование купонов, race condition на балансе. Аутентификация — предсказуемые токены, отсутствие инвалидации, слабые OTP. Rate limiting — проверьте, ограничен ли перебор.

## Инструменты

Postman/Insomnia — для удобной работы с запросами и коллекциями. `jwt_tool` — для тестов JWT. `ffuf`/Burp Intruder — для перебора параметров. Не забывайте: онлайн-перебор большими словарями EV-отрицателен; используйте точечные попытки и логику.

## Частые вопросы

«Как найти все endpoint'ы?» — перехват + `grep` по APK. «Токен из перехвата?» — да, используйте его напрямую. «Два аккаунта зачем?» — для IDOR/BFLA. «Rate limit?» — точечно. «Как автоматизировать?» — Newman + коллекция Postman.

## Что дальше / решение

Итог: мобильное API — самая «жирная» часть пентеста. Обойдите pinning, соберите карту, тестируйте IDOR/BFLA/JWT/инъекции/логику с двумя аккаунтами. Держите Postman и `jwt_tool`. Клиентские проверки не защищают — ищите серверные слабости.
