## Вопрос, с которого всё начинается

Мобильное приложение — это тонкий клиент: вся логика и данные на сервере. Значит, самое интересное лежит не в APK, а в **API**. Как перейти от перехваченного трафика к систематическому тестированию серверной части?

## Наш пример: API приложения DemoApp

В статике мы нашли адрес API. Посмотрим на строки приложения:

```
$ strings -a DemoApp | grep -iE 'api\.|/v[0-9]/|endpoint'
https://api.demo.example/v2
https://api.demo.example/v2/users
https://api.demo.example/v2/orders
```

Теперь понятна структура: базовый адрес `https://api.demo.example/v2`, ресурсы `/users`, `/orders`. Это отправная точка для тестирования API.

## Шаг 1: получаем трафик

Прежде чем что-то тестировать, нужен живой трафик. Порядок: настроить прокси (Burp/mitmproxy), установить и доверить CA-сертификат, снять pinning (`mobile-ssl-killswitch`, `mobile-ssl-pinning`). После этого приложение отдаёт запросы в открытом виде. Сохраним их в файл:

```
$ curl -s -x http://127.0.0.1:8080 https://api.demo.example/v2/users \
    -H "Authorization: Bearer eyJhbGciOiJIUzI1NiJ9.demo"
{"users":[{"id":1,"email":"alice@demo.example"}]}
```

Теперь мы можем воспроизводить запросы вручную — это ключ к систематическому тестированию.

## Шаг 2: инвентаризация эндпоинтов

Соберём список всех эндпоинтов и методов. Источники: перехваченный трафик, `strings` по APK, документация (если есть). Для каждого записываем: метод, путь, параметры, авторизацию, ответ. Получается карта API:

| Метод | Путь | Авторизация | Назначение |
|-------|------|-------------|-----------|
| GET | /v2/users/me | Bearer | профиль |
| GET | /v2/orders | Bearer | заказы |
| POST | /v2/orders | Bearer | создать заказ |
| GET | /v2/admin/users | Bearer? | админ-функция |

Уже из этой таблицы видно подозрительное: админ-эндпоинт, защищённый тем же токеном, что и обычный.

## Шаг 3: аутентификация и токены

Разбираем, как устроена авторизация. Смотрим на токен:

```
$ python3 -c "import base64;print(base64.urlsafe_b64decode('eyJhbGciOiJIUzI1NiJ9.demo' + '=='))"
b'{\"alg\":\"HS256\"}'
```

Если токен — JWT, проверяем его на слабости: алгоритм `none`, слабый секрет, отсутствие проверки подписи. Дальше — важные вопросы: истекает ли токен, отзывается ли при выходе, можно ли использовать refresh-токен повторно. Частая находка — токен живёт годами и не отзывается.

## Шаг 4: BOLA — доступ к чужим объектам

**BOLA** (Broken Object Level Authorization) — самая частая уязвимость мобильных API. Суть: эндпоинт не проверяет, принадлежит ли объект пользователю. Пример:

```
$ curl -s https://api.demo.example/v2/orders/1024 -H "Authorization: Bearer <alice>"
{"id":1024,"user_id":2,"total":199.99}
```

Мы запросили заказ `1024`, а он принадлежит пользователю `2`. Если сервер не проверил владельца — мы читаем чужие заказы. Это классический IDOR/BOLA. Проверять нужно перебором идентификаторов на каждом объектном эндпоинте.

## Шаг 5: массовое присваивание и параметры

**Mass assignment** — когда сервер принимает больше полей, чем нужно. Например, при обновлении профиля:

```
$ curl -s -X PATCH https://api.demo.example/v2/users/me \
    -H "Authorization: Bearer <alice>" -d '{"role":"admin"}'
```

Если сервер применит `role`, мы повысили себе права. Другой класс — скрытые параметры: `debug=true`, `admin=1`. Их ищут в статике (`strings`) и перебором.

## Практика: проверяем на живом API

Теория понятна — посмотрим на реальные ответы. Поднимем локальный демо-API с двумя пользователями (Алиса с токеном `tok-A`, Боб с `tok-B`) и запросим **чужой** профиль своим токеном:

```
$ curl -s -H "Authorization: Bearer tok-A" http://127.0.0.1:18080/v1/users/1002/profile
{"id": "1002", "email": "bob@example.com", "role": "user", "balance": 5000}
```

Мы получили данные Боба (`id=1002`), хотя авторизованы как Алиса (`1001`). Сервер проверил лишь наличие токена, но не то, что объект `1002` принадлежит нам, — это и есть BOLA. Доказательство строится на паре запросов: свой объект против чужого.

Теперь mass assignment — допишем в тело поле, которого клиенту менять не положено:

```
$ curl -s -X PATCH http://127.0.0.1:18090/v1/users/me \
    -H "Authorization: Bearer tok-A" -H "Content-Type: application/json" \
    -d '{"role":"admin"}'
{"id": "1001", "phone": "+70000000001", "email": "alice@example.com", "role": "admin", "balance": 999999, "device_id": "dev-alice"}
```

Поле `role` в ответе стало `admin`, хотя мы не администратор: сервер вслепую скопировал присланные поля в объект. Это mass assignment с повышением привилегий.

## Шаг 6: слабости бизнес-логики

API-тестирование не только про авторизацию. Проверяем:

- **rate limiting** — можно ли перебирать пароли/OTP без блокировки;
- **последовательность** — можно ли пропустить шаг (оплатить, не подтвердив);
- **целостность** — можно ли подменить сумму заказа;
- **утечки в ответах** — возвращает ли API лишние поля (пароли, токены, PII).

Последнее особенно часто: сервер отдаёт объект целиком, включая внутренние поля. Сравниваем ответы разных эндпоинтов.

## Шаг 7: автоматизация

Ручной перебор быстро надоедает. Для API используют:

- **Burp Intruder** — перебор параметров и идентификаторов;
- **ffuf** — фаззинг эндпоинтов и параметров;
- **скрипты** — собственные проверки на Python/requests.

Пример проверки BOLA скриптом:

```python
import requests
for oid in range(1000, 1030):
    r = requests.get(f"https://api.demo.example/v2/orders/{oid}",
                     headers={"Authorization": f"Bearer {token}"})
    if r.status_code == 200:
        print("leak", oid, r.json().get("user_id"))
```

Так за секунды проверяются десятки объектов.

## Шаг 8: что писать в отчёте

API-находка — это конкретный запрос и конкретный результат. В отчёте указывай: метод и путь, заголовки авторизации, тело, ответ, и что это доказывает (например, «пользователь A получил заказ пользователя B»). Без воспроизводимого запроса находка не считается.

## Шаг 9: сравнение платформ

Полезно сравнить поведение iOS- и Android-версий одного API. Иногда сервер доверяет одной платформе больше: например, iOS-клиент получает расширенный набор полей, а Android — нет. Или проверка целостности есть только в одной версии. Тестируя обе платформы, ты находишь «дыру» там, где защита слабее.

Ещё один приём — старые версии приложения. Если сервер поддерживает устаревший API-версии (`/v1/`), они часто менее защищены. Ищи в трафике номер версии и пробуй понизить его.

## Шаг 10: чек-лист

Собери проверку API в один список: аутентификация (токен, срок, отзыв), авторизация (BOLA), параметры (mass assignment, скрытые поля), логика (rate limit, последовательность), утечки (лишние поля в ответах). Прогон по этому списку на каждом эндпоинте даёт систематическое покрытие.

Записывай результаты в таблицу — так легко увидеть, где проверка не сделана, и не забыть перепроверить после изменений на сервере. Хорошая привычка — хранить коллекцию запросов (например, в Burp или как curl-скрипт), чтобы повторять проверку одной командой. Это экономит время при повторном тестировании после исправлений. Коллекция запросов — фактически исполняемая документация твоих находок, и её можно передать коллеге для повторной проверки.

## Что мы теперь знаем

- Мобильное приложение — тонкий клиент; основное лежит в API.
- Начинают с перехвата трафика и инвентаризации эндпоинтов.
- Токены проверяют на слабости JWT, срок жизни и отзыв.
- BOLA — доступ к чужим объектам из-за отсутствия проверки владельца.
- Mass assignment — сервер принимает лишние поля.
- Проверяют rate limiting, последовательность и утечки в ответах.
- Автоматизируют перебор через Burp Intruder, ffuf, скрипты.
