## Вопрос, с которого всё начинается

Телефон найден разблокированным? Нет — экран заблокирован, а внутри почта, мессенджеры
и корпоративные токены. Задача пентеста: **добраться до данных, не зная PIN**. Это не
одна кнопка, а набор путей, каждый из которых зависит от конфигурации устройства.
Разберём их по порядку.

## Наш пример: тестовый телефон с 4-значным PIN

У нас есть устройство `Pixel-lab`, на нём PIN из четырёх цифр, включена отладка по USB.
Посмотрим, что вообще можно сделать, начав с самого простого.

## Шаг 1: проверяем ADB

Если отладка по USB включена и компьютер уже был авторизован, ADB работает даже на
заблокированном экране:

```bash
$ adb devices
List of devices attached
2B091FDH2004AJ  device
$ adb shell dumpsys window | grep -i mDreamingLockscreen
mDreamingLockscreen=false
```

Статус `device` (а не `unauthorized`) означает доверенное подключение. Через ADB можно
читать часть файлов, ставить приложения, снимать скриншоты — то есть блокировка экрана
уже почти не мешает. Это первый и самый частый «обход»: администратор забыл выключить
отладку.

## Шаг 2: Smart Lock и доверенные места

Android умеет сам снимать блокировку в «доверенных» условиях: доверенное Bluetooth-
устройство, доверенное место (геозона), доверенное лицо. Если злоумышленник знает это
условие, он его воспроизводит.

```bash
$ adb shell dumpsys trust | grep -i trust
TrustAgent: SmartLock (enabled)
  Trusted devices: [AA:BB:CC:11:22:33]
```

Достаточно поднести «доверенные» наушники рядом — и экран откроется. Проверка: есть ли
у устройства включённые агенты доверия.

## Шаг 3: подмена биометрии через Frida

Часто приложение банка доверяет не PIN, а результату `BiometricPrompt`. Тогда цель —
не обойти систему, а **сказать приложению, что аутентификация прошла**. На rooted-
устройстве это делает Frida:

```javascript
// перехватываем колбэк успешной аутентификации
Java.perform(function () {
  var Auth = Java.use("android.hardware.biometrics.BiometricPrompt$AuthenticationCallback");
  Auth.onAuthenticationSucceeded.implementation = function (result) {
    console.log("[*] biometric spoofed");
    return this.onAuthenticationSucceeded(result);
  };
});
```

Скрипт не подделывает отпечаток — он вызывает обработчик «успех» напрямую. Защита от
этого — проверять `BiometricPrompt` через `CryptoObject` с аппаратным ключом, тогда
подмена колбэка ничего не даёт.

## Шаг 4: офлайн-перебор PIN

Если данных достаточно, экран блокировки можно обойти «грубой силой». Внутри
`/data/system/` лежат файлы, из которых выводятся производные от PIN
(`gatekeeper.password.key`, `locksettings.db`). На копии раздела их перебирают
офлайн — без ограничений на количество попыток, которые действуют на живом экране.

```bash
$ adb pull /data/system/locksettings.db
$ sqlite3 locksettings.db "select name,value from locksettings where name like '%pin%';"
lockscreen.password_type|262144
```

4-значный PIN — это 10 000 вариантов, а на GPU-ферме — секунды. Отсюда правило:
длина и сложность PIN важнее, чем кажется.

## Шаг 5: когда ничего не работает

На современном устройстве с выключенной отладкой, без Smart Lock и с 8-значным PIN
простых путей нет. Тогда остаются только уязвимости прошивки (CVE в загрузчике или
TrustZone) — это уже отдельная тема уровня ядра. Важно понимать: «обход блокировки» —
это не одна техника, а перебор конфигураций, и защита держится на всех звеньях сразу.

## Шаг 6: что видно и без разблокировки

Иногда обходить блокировку не нужно — часть данных доступна прямо с локскрина.
Первое, что смотрим, — уведомления:

```bash
$ adb shell dumpsys notification --noredact | grep -i "android.title" | head
android.title=Код подтверждения
android.text=4821 — никому не сообщайте
```

Флаг `--noredact` показывает содержимое уведомлений без маскировки. Если приложение
не помечает уведомление как секретное (`setVisibility(VISIBILITY_SECRET)`), код
подтверждения утекает на заблокированный экран.

Второе — файлы, доступные до ввода пароля. Это **device-encrypted (DE)** зона: часть
системных данных читается сразу после загрузки. Проверить, что попало в DE, можно
так:

```bash
$ adb shell ls /data/misc/apexdata/ 2>/dev/null
$ adb shell getprop ro.crypto.state
encrypted
```

Третье — `adb backup`. Если в манифесте выставлен `android:allowBackup="true"`, часть
данных приложения выгружается без разблокировки:

```bash
$ adb backup -noapk com.example.app
```

На современных версиях Android этот путь сильно урезан, но на старых устройствах он
работает.

## Если не сработало

* Отладка выключена, Smart Lock выключен, PIN длинный — простых путей нет; остаются
  только уязвимости прошивки.
* Устройство в **lockdown mode** (на новых Android отключает биометрию и уведомления) —
  тогда и ADB, и уведомления закрыты.
* После нескольких неудачных попыток система может стереть данные (`wipe after N
  failed attempts`); проверяй политику, прежде чем перебирать на живом экране.

## Что мы теперь знаем

- Включённый ADB на доверенном компьютере — прямой путь мимо экрана.
- Smart Lock открывает устройство в «доверенных» условиях, которые можно воспроизвести.
- Биометрию в приложении подделывают через Frida, обходя колбэк.
- Офлайн-перебор PIN упирается в длину и сложность, а не в число попыток.
- Реальный обход зависит от конфигурации; защита — это совокупность мер.

## Куда дальше

Блокировка — это вход. Дальше разберём, что происходит после **сброса устройства**:
Factory Reset Protection, которая должна мешать воспользоваться украденным телефоном.
А пока запомни: **экран блокировки защищает лишь настолько, насколько закрыты все
обходные пути — ADB, доверие и стойкость PIN**.
