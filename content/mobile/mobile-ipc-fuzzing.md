## Вопрос, с которого всё начинается

Мы разобрали по отдельности все классы IPC-уязвимостей: экспортированные компоненты, deep links, сервисы, провайдеры, intent redirection. В реальном приложении компонентов десятки, и проверять каждый вручную долго. Как автоматизировать поиск IPC-уязвимостей и не пропустить цель?

## Наш пример: поверхность атаки fdroid.apk

Начнём с того, что соберём всю поверхность в одном месте. Из манифеста `fdroid.apk`:

```
$ grep -oE '<(activity|service|receiver|provider)[^>]*android:exported="true"[^>]*' \
    fdroid_dec/AndroidManifest.xml | sed -E 's/.*android:name="([^"]*)".*/\1/' | sort -u
androidx.profileinstaller.ProfileInstallReceiver
androidx.work.impl.background.systemjob.SystemJobService
androidx.work.impl.diagnostics.DiagnosticsReceiver
org.fdroid.IconActivity
org.fdroid.IconCalculatorActivity
org.fdroid.MainActivity
org.fdroid.fdroid.panic.CalculatorActivity
org.fdroid.ui.panic.PanicActivity
org.fdroid.ui.panic.PanicResponderActivity
org.fdroid.ui.repositories.UpdateRepoActivity
```

Десять компонентов — уже неплохо для ручного разбора. А если их сотни? Тогда нужна автоматизация.

## Шаг 1: Drozer — карта поверхности

Drozer подключается к агенту на устройстве и перечисляет атакуемую поверхность:

```
$ adb forward tcp:31415 tcp:31415
$ drozer console connect
dz> run app.package.attacksurface org.fdroid.fdroid
Attack Surface:
  6 activities exported
  2 broadcast receivers exported
  2 services exported
  0 content providers exported
```

Дальше — детали по каждому типу:

```
dz> run app.activity.info -a org.fdroid.fdroid
dz> run app.broadcast.info -a org.fdroid.fdroid
dz> run app.provider.info -a org.fdroid.fdroid
```

Drozer не находит уязвимости сам, но строит карту и позволяет вызывать компоненты.

## Шаг 2: ручные команды adb

Без drozer многое делается напрямую:

```
$ adb shell am start -n pkg/.Activity              # Activity
$ adb shell am startservice -n pkg/.Service        # Service
$ adb shell am broadcast -n pkg/.Receiver          # Receiver
$ adb shell content query --uri content://pkg/...  # Provider
$ adb shell service call pkg 1                     # Binder
```

Это базовый набор для проверки каждого компонента.

## Шаг 3: фаззинг Intent

Ручной перебор не масштабируется. Фаззинг Intent автоматически варьирует extras, action, data и смотрит, что падает или ведёт себя неожиданно. Идея: подавать компоненту неожиданные данные (пустые, огромные, неверного типа) и искать исключения.

Инструменты и подходы:

- **`drozer`-модули** для перебора extras.
- **Скрипты на `am`** с разными типами данных.
- **Intent fuzzer** (например, `IntentFuzzer`) для автоматической генерации.

Падение компонента — уже находка (DoS), но интереснее логические эффекты: обход проверок, утечка.

## Шаг 4: перебор extras и типов

Многие компоненты ждут extra определённого типа. Если подать не тот тип, возможен обход проверки или краш:

```
$ adb shell am start -n pkg/.Activity --es url "file:///etc/passwd"
$ adb shell am start -n pkg/.Activity --ei user_id 0
$ adb shell am start -n pkg/.Activity --ez is_admin true
```

Здесь `--es` — строка, `--ei` — int, `--ez` — boolean. Подставляя разные значения, ищут компонент, который доверяет данным.

## Шаг 5: Content Provider фаззинг

Для провайдеров фаззят пути и параметры:

```
$ adb shell content query --uri content://pkg/../../etc/passwd
$ adb shell content query --uri content://pkg/table --where "1=1) OR (1=1"
$ adb shell content call --uri content://pkg/ --method evil --arg x
```

Цель — найти path traversal, SQL-инъекцию и незащищённый `call`.

## Шаг 6: автоматизация на Frida

Динамически удобно логировать вызовы компонентов. Хук на `onCreate`, `onReceive`, `onStartCommand` показывает, какие данные приходят:

```javascript
Java.perform(function () {
  var Activity = Java.use('android.app.Activity');
  Activity.getIntent.implementation = function () {
    var i = this.getIntent();
    console.log('[intent] ' + i);
    return i;
  };
});
```

Так видно, доходит ли ваш фаззинг до компонента.

## Шаг 7: как организовать работу

План:

1. Собрать поверхность (`drozer`/grep).
2. Классифицировать компоненты по типу и защите.
3. Прогнать базовые `am`-команды по каждому.
4. Фаззить extras/пути/параметры.
5. Логировать через Frida, чтобы видеть обработку.
6. Отдельно разобрать найденные аномалии руками.

## Разбор реального сценария

Приложение имеет тридцать экспортированных компонентов. Вручную проверять каждый — дни. Drozer строит карту за минуты, а базовый набор `am`-команд отсеивает компоненты без защиты. Затем фаззинг extras автоматически подаёт компонентам неожиданные типы и значения: где-то приложение падает, где-то обходит проверку. Так за час находится то, что при ручном переборе заняло бы неделю. Автоматизация не заменяет анализ, но указывает, куда смотреть.

## Полный прогон от начала до конца

Соберём IPC-аудит в один сценарий. Сначала `drozer` собирает поверхность и классифицирует компоненты. Затем по каждому — базовые команды (`am start`, `am broadcast`, `content query`, `service call`). Дальше фаззинг: перебор extras, путей, типов. Параллельно Frida логирует обработку, чтобы видеть, доходят ли данные. Аномалии разбираем руками: падение → DoS, обход проверки → доступ, утечка → данные. Итог — список подтверждённых находок с PoC.

## Частые вопросы

**«Drozer находит уязвимости?»** — нет, он строит карту; уязвимости подтверждает человек. **«Нужен ли агент на устройстве?»** — да, drozer требует установки агента и `adb forward`. **«Фаззинг заменяет ручной разбор?»** — нет, он сужает круг кандидатов. **«Что считать находкой?»** — обход проверки и утечку, а не только падение. **«Как защитить?»** — явный `exported`, `android:permission`, проверка вызывающего.

## Практический совет

Стройте работу от карты к кандидатам: сначала соберите поверхность, отсеките защищённые компоненты, и только потом фаззьте оставшиеся. Фаззинг «вслепую» по всем компонентам даёт шум. И всегда держите рядом логирование — без него непонятно, дошёл ли ваш ввод до кода или компонент его отбросил.

## Ещё один нюанс: ложные срабатывания

Автоматизация любит давать ложные срабатывания. Падение компонента при фаззинге может быть безобидным (неверный тип данных в UI), а «открытый» компонент — защищённым на уровне системы. Поэтому каждую находку подтверждайте руками: воспроизведите минимальным запросом, проверьте, есть ли эффект, и убедитесь, что дело не в среде. Отчёт с ложной находкой хуже, чем отсутствие находки: он подрывает доверие ко всему тесту.

## Итог

IPC-фаззинг — это способ не пропустить цель в большом приложении. Drozer строит карту, `am`-команды дают быструю проверку, фаззинг расширяет охват, а Frida показывает обработку. Но финальное слово всегда за ручным подтверждением: автоматика указывает кандидатов, человек доказывает уязвимость. Такой подход масштабируется на приложения с десятками компонентов.

## Покрытие и приоритизация

Не все компоненты равны по ценности. Сначала проверяйте те, что работают с данными и меняют состояние: провайдеры, сервисы, Activity входа и оплаты. Компоненты вроде «О программе» можно отложить. Такой порядок экономит время и повышает шанс найти серьёзную находку раньше. Ведите список проверенных компонентов, чтобы не повторяться и видеть покрытие.
