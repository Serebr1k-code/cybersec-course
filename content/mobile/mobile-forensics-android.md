## Вопрос, с которого всё начинается

В прошлом уроке мы вытащили данные приложения. Но «вытащить» и «разобрать» — разные вещи. У нас на руках сотни файлов: базы, XML, кэш, логи. Как из этого хаоса собрать ответ на конкретный вопрос — например, «какой токен сессии был у пользователя и когда он входил»?

Это и есть Android-форензика: извлечение и анализ артефактов.

## Наш пример: дамп приложения

Представим, что мы сняли дамп приложения (через `adb backup`, `run-as` или root-образ). Работать будем с двумя реальными наборами данных: декодированным деревом `fdroid.apk` и реальной базой из `lichess.apk`. Начнём с инвентаризации — что вообще есть:

```
$ find fdroid_dec -type d | head
fdroid_dec
fdroid_dec/assets
fdroid_dec/res
fdroid_dec/smali
fdroid_dec/smali_classes2
fdroid_dec/smali_classes3
fdroid_dec/lib
```

Первым делом форензик смотрит, **где данные и какие они**: `databases/`, `shared_prefs/`, `files/`, `cache/`, `assets/`.

## Шаг 1: базы данных — главный источник

Базы SQLite — самый информативный артефакт. Достанем реальную базу из `lichess.apk` и посмотрим, что внутри:

```
$ unzip -o lichess.apk 'assets/flutter_assets/assets/chess_openings.db' -d lic
$ sqlite3 lic/assets/flutter_assets/assets/chess_openings.db ".tables"
Openings

$ sqlite3 lic/assets/flutter_assets/assets/chess_openings.db ".schema Openings"
CREATE TABLE Openings (
  name TEXT, eco TEXT, fen TEXT, moves TEXT, ...
);

$ sqlite3 lic/assets/flutter_assets/assets/chess_openings.db \
    "SELECT name,eco FROM Openings LIMIT 3;"
Alekhine Defense|B02
Alekhine Defense: Modern Variation|B04
Alekhine Defense: Scandinavian Variation|B02
```

У рантайм-баз структура та же. Форензик смотрит на имена таблиц (`users`, `sessions`, `messages`, `accounts`), на поля с датами (`created_at`, `last_login`) и на текстовые колонки, где оседают токены.

## Шаг 2: SharedPreferences и файлы

Настройки и токены часто лежат в XML:

```
$ cat fdroid_dec/assets/logback.xml | head -3
<configuration>
  <appender name="FILE" class="ch.qos.logback.core.FileAppender">
```

А в приватной директории — `shared_prefs/*.xml`. Ключи вроде `token`, `session`, `user_id` — то, что ищет форензик. Проверяем содержимое:

```
$ grep -rInE 'token|session|password|secret' fdroid_dec/assets/*.json | head
fdroid_dec/assets/default_repos.json:  "address": "https://f-droid.org/repo",
```

## Шаг 3: поиск секретов по всему дампу

Универсальный приём — рекурсивный поиск по ключевым словам:

```
$ grep -rInE 'flag|token|secret|password|api[_-]?key' fdroid_dec/ | head
```

Дополняем поиском по бинарникам (`strings`), потому что секрет может быть в `.so` или в базе:

```
$ strings -n 8 lic/assets/flutter_assets/assets/chess_openings.db | grep -iE 'token|key' | head
```

## Шаг 4: автоматизация — ALEAPP

Ручной разбор не масштабируется. Для Android есть **ALEAPP** (Android Logs Events And Protobuf Parser) — он принимает дамп и сам разбирает артефакты: аккаунты, историю Wi-Fi, SMS, уведомления, базы приложений:

```
$ python3 aleapp.py -t fs -i dump/ -o out/
$ ls out/
2026-10-12_.../  index.html
```

На выходе — HTML-отчёт с таймлайном и разложенными по категориям артефактами. Форензик всё равно проверяет находки руками, но ALEAPP экономит часы.

## Шаг 5: таймлайн и цепочка

Разрозненные артефакты связывают временем. У каждого файла есть `mtime`, у записей в базах — поля времени. Соберём таймлайн:

```
$ find dump -type f -printf '%TY-%Tm-%Td %TH:%TM  %p\n' | sort | tail -5
2026-10-12 09:14  dump/databases/app.db
2026-10-12 09:15  dump/shared_prefs/session.xml
2026-10-12 09:15  dump/cache/http/response.bin
```

По времени видно последовательность: приложение писало сессию, потом кэшировало ответ. Так восстанавливают, что делал пользователь.

## Шаг 6: цепочка сохранности (chain of custody)

Форензика — про доказуемость. Перед анализом считают хэш образа:

```
$ sha256sum device_dump.tar
9f2c...  device_dump.tar
```

Хэш фиксирует, что образ не менялся. Все дальнейшие действия — над **копией**, а не над оригиналом. Без этого результат нельзя предъявить.

## Если артефактов мало

- **Только APK, без устройства.** Работайте по статике: `apktool`, `jadx`, `strings`; ищите секреты в ресурсах и `assets`.
- **Дамп без баз.** Смотрите `shared_prefs` и `files` — токены часто и там.
- **Всё зашифровано.** Ищите ключ в коде или перехватывайте `Cipher.init` через Frida.
- **Нет доступа к устройству.** `adb backup` и `content query` дают часть данных без root.
- **Слишком много файлов.** Сначала фильтруйте по времени (`find -mtime`) и по расширениям (`.db`, `.xml`, `.json`).

## Что фиксировать в отчёте

Форензик-отчёт должен быть воспроизводимым:

- **Как получен дамп** (метод, устройство, время) и его хэш.
- **Какие артефакты изучены** и что в них найдено.
- **Таймлайн событий** с цитатами из данных.
- **Ограничения** — что расшифровать не удалось и почему.

Без этого находку нельзя предъявить: «я нашёл токен» без указания, откуда именно, не является доказательством.

## Инструменты Android-форензики

- **ALEAPP** — автоматический разбор артефактов в HTML-отчёт.
- **`sqlite3`** — ручная работа с базами (`cellebrite`/`autopsy` для тяжёлых случаев).
- **`strings`/`grep`** — быстрый поиск секретов по бинарникам и файлам.
- **`apktool`/`jadx`** — разбор статики, если дамп неполный.
- **`adb`** — извлечение данных с живого устройства.

Инструмент не заменяет понимание: он находит кандидатов, а форензик проверяет их и связывает с контекстом.

## Практикум: поиск токена в дампе

Порядок действий на конкретном примере:

1. `find dump -iname '*.db'` — находим базы.
2. `sqlite3 app.db ".tables"` — смотрим таблицы.
3. `SELECT * FROM sessions;` — читаем сессии.
4. Если в базе пусто — `grep -rInE 'eyJ|token' dump/` по всему дереву.
5. Найденный JWT проверяем на `jwt.io`-подобный разбор и смотрим `exp`.

Так от «есть дамп» переходят к «есть подтверждённый токен с временем жизни».

## Частые вопросы

**«С чего начать разбор?»** — с инвентаризации директорий и списка баз. **«Где искать токены?»** — в `shared_prefs`, базах и кэше HTTP. **«Мало данных?»** — добирайте `adb backup` и `content query`. **«Как не потерять доказательность?»** — считайте хэш образа до анализа. **«Что делать с сотнями файлов?»** — фильтруйте по времени и расширениям, затем `grep` по ключевым словам.

## Что мы теперь знаем

По-простому:

1. Форензика начинается с инвентаризации: `databases`, `shared_prefs`, `files`, `cache`.
2. SQLite-базы — главный источник; смотрят таблицы, поля времени и текстовые колонки.
3. Секреты ищут `grep`-ом по ключевым словам и `strings` по бинарникам.
4. ALEAPP автоматически разбирает артефакты в отчёт.
5. Таймлайн связывает артефакты, а хэш фиксирует целостность образа.

## Практический совет

Не пытайтесь разобрать дамп целиком за один проход. Сначала ответьте на узкий вопрос («где токен?»), потом расширяйте. Форензик — это не «прочитать всё», а «доказать конкретный факт». Каждую находку сразу фиксируйте: файл, строка, время. Это сэкономит часы при подготовке отчёта и не даст потерять важное среди сотен файлов.

## На что смотреть дальше

- **Начинайте с баз:** таблицы `users`/`sessions` — самое ценное.
- **Не забывайте про кэш:** HTTP-ответы в `cache/` хранят токены.
- **Считайте хэш до анализа** — иначе результат недоказуем.
- **Автоматизируйте** (ALEAPP), но проверяйте находки руками.

## Инструменты и их роль

Разные инструменты закрывают разные задачи: `adb` извлекает данные с живого устройства, `ALEAPP` автоматически разбирает артефакты, `sqlite3` даёт точный доступ к базам, `apktool`/`jadx` помогают понять статику приложения. Форензик выбирает инструмент под вопрос, а не наоборот. Начинайте с самого простого способа, который даёт ответ, и усложняйте только при необходимости.

## Куда дальше

Мы разобрали разбор локального дампа. В следующем уроке — **облачная форензика**: что синхронизируется в iCloud и Google, как это сопоставить с устройством и где искать следы.
