## Вопрос, с которого всё начинается

Ты открыл APK в jadx, нашёл метод проверки — а у него нет тела:

```java
public boolean check_code(String str) { return bar(str.getBytes()); }
private native boolean bar(byte[] bArr);
```

Слово `native` означает: код этого метода написан не на Java, а на C/C++ и лежит в отдельной библиотеке внутри APK. В jadx его не будет. Как добраться до логики проверки, если её исходников нет?

## Наш пример: UnCrackable Level 2

Возьмём реальное учебное приложение OWASP MSTG — **UnCrackable Level 2**. В нём пароль проверяется нативным кодом. Разберём его от APK до функции сравнения — это и есть навык, который отличает «умею открыть jadx» от «умею реверсить приложение».

## Шаг 1: где вообще лежит нативный код

APK — это ZIP-архив. Посмотрим его содержимое:

```
$ unzip -l uncrack2.apk | grep -E 'lib/|classes'
   720084  1980-00-00 00:00   classes.dex
    14176  1980-00-00 00:00   lib/arm64-v8a/libfoo.so
    13948  1980-00-00 00:00   lib/armeabi-v7a/libfoo.so
    13788  1980-00-00 00:00   lib/x86/libfoo.so
    14440  1980-00-00 00:00   lib/x86_64/libfoo.so
```

Нативные библиотеки — это файлы `.so` («shared object», разделяемая библиотека, аналог `.dll` в Windows) в каталоге `lib/<abi>/`. `<abi>` — архитектура процессора: `arm64-v8a` (современные телефоны), `armeabi-v7a` (старые 32-битные ARM), `x86`/`x86_64` (эмуляторы). Логика в них одна, но скомпилирована под каждую архитектуру отдельно.

Вытащим библиотеку и посмотрим, что это за файл:

```
$ unzip uncrack2.apk 'lib/x86/*' -d out
$ file out/lib/x86/libfoo.so
out/lib/x86/libfoo.so: ELF 32-bit LSB shared object, Intel i386,
    version 1 (SYSV), dynamically linked, for Android 19,
    built by NDK r18b, BuildID[sha1]=1adb8eb0..., stripped
```

`ELF` — формат исполняемых файлов Linux/Android. `stripped` — из файла удалены имена внутренних функций (частая защита). Но это не мешает: связь с Java всё равно видна.

## Шаг 2: находим мост Java ↔ native

Когда Java-метод объявлен `native`, система ищет в библиотеке функцию со специальным именем. Правило: `Java_` + пакет с заменой точек на подчёркивания + `_` + класс + `_` + метод. Посмотрим, что экспортирует наша библиотека:

```
$ nm -D out/lib/x86/libfoo.so | grep Java_
00000f60 T Java_sg_vantagepoint_uncrackable2_CodeCheck_bar
00000f30 T Java_sg_vantagepoint_uncrackable2_MainActivity_init
```

`nm -D` показывает динамические символы — имена, которые библиотека «отдаёт наружу». Читаем: класс `sg.vantagepoint.uncrackable2.CodeCheck`, метод `bar` — ровно тот `native boolean bar`, что мы видели в jadx. Значит, проверка пароля — внутри `Java_sg_vantagepoint_uncrackable2_CodeCheck_bar`.

Символы бывают двух видов: **именованные** (как здесь, `Java_...`) и **динамические** через `RegisterNatives` — тогда имя в таблице символов не появится, а метод регистрируется в рантайме. Об этом — в уроке `mobile-native-so-deep`.

## Шаг 2б: как JNI передаёт аргументы

Прежде чем читать код функции, нужно понимать её сигнатуру. Любая JNI-функция получает первые два аргумента неявно:

- `JNIEnv*` — указатель на таблицу функций, через которую нативный код общается с виртуальной машиной Java;
- `jobject` (или `jclass` для статического метода) — ссылка на Java-объект, для которого вызван метод.

Аргументы самого метода идут следом. Наш `bar(byte[] bArr)` принимает массив байт — он придёт третьим аргументом как `jbyteArray`. А в Java-строку нативный код смотрит через `GetStringUTFChars(env, str, 0)` — в декомпиляции это заметная цепочка вызовов, по ней легко найти место, где обрабатывается пользовательский ввод. В 64-битных ARM и x86 первые аргументы лежат в регистрах (x86: `esp+0`, `esp+4`; ARM64: `x0`, `x1`), а не в стеке — дизассемблер это показывает.

## Шаг 3: читаем, что делает функция

Даже без Ghidra видно многое. Строки в бинарнике лежат в секции данных, а сравнение входа с секретом обычно идёт через `strcmp`/`strncmp`. Найдём и то, и другое:

```
$ strings out/lib/x86/libfoo.so | grep -iE 'strncmp|Java_'
Java_sg_vantagepoint_uncrackable2_CodeCheck_bar
Java_sg_vantagepoint_uncrackable2_MainActivity_init
strncmp
```

Функция сравнивает ввод с чем-то через `strncmp`. Посмотрим дизассемблер этой функции — он показывает машинные инструкции:

```
$ objdump -d --disassemble=Java_sg_vantagepoint_uncrackable2_CodeCheck_bar out/lib/x86/libfoo.so
00000f60 <Java_..._CodeCheck_bar@@Base>:
     f8e:  movl  $0x6e616854,(%esp)
     f95:  movl  $0x6620736b,0x4(%esp)
     f9d:  movl  $0x6120726f,0x8(%esp)
     fa5:  movl  $0x74206c6c,0xc(%esp)
     fad:  movw  $0x6568,0x10(%esp)
     fb4:  movl  $0x73696620,0x12(%esp)
     fbc:  movw  $0x68,0x16(%esp)
```

Это готовится строка: в стек кладут 32-битные числа. Процессоры x86 хранят числа «младшим байтом вперёд», поэтому `0x6e616854` = байты `54 68 61 6e` = `Than`. Собираем по кусочкам: `Than` + `ks f` + `or a` + `ll t` + `he` + ` fis` + `h` = **`Thanks for all the fish`**. Это и есть ожидаемый секрет.

Вот и весь приём: сравнение делается не с внешней строкой, а со строкой, собранной прямо в коде. Дизассемблер показал её без всякой обфускации.

## Шаг 3б: когда `strings` пусто и символов нет

На учебном примере всё видно, но в реальных приложениях так бывает не всегда. Если `strings` не показывает ни секрета, ни путей, значит строки зашифрованы и расшифровываются в рантайме. Тогда находят **функцию-декриптор** — она вызывается при инициализации и возвращает готовые строки; её перехватывают и логируют результат. А если JNI-имён в `nm -D` нет — используется `RegisterNatives`: методы регистрируются динамически в `JNI_OnLoad`, и в таблице символов остаётся только `JNI_OnLoad` (он экспортируется всегда). Внутри него лежит таблица из пар «имя, сигнатура, указатель на функцию» — перехватив `RegisterNatives`, её можно выгрузить и получить адреса всех нативных методов.

## Шаг 3в: декомпилятор вместо дизассемблера

Ассемблер читается медленно. Для восстановления логики берут **декомпилятор** — он превращает машинный код в псевдо-C. Бесплатный вариант — Ghidra: импортируем `.so`, выбираем архитектуру (для `arm64-v8a` — AArch64), и она восстанавливает функции. Плагин `d810` снимает обфускацию OLLVM (control-flow flattening), при которой поток управления специально запутан. Строку «Thanks for all the fish» Ghidra показала бы как `strncmp(input, "Thanks for all the fish", 0x17)` — то же, что мы собрали вручную, но за секунды. Для быстрой разведки подойдёт и radare2: `r2 -A libfoo.so`, затем `afl` (список функций) и `pdf @ sym.Java_..._CodeCheck_bar` (дизассемблер одной функции).

## Шаг 4: как ускориться динамикой

Читать ассемблер долго. Часто быстрее — перехватить сравнение в работающем приложении. Frida (`Interceptor.attach`) подменяет вызов функции на свою: можно вывести оба аргумента `strcmp` и узнать, что с чем сравнивают:

```javascript
Interceptor.attach(Module.getGlobalExportByName("strncmp"), {
  onEnter(args) {
    console.log("arg1 = " + args[0].readUtf8String());
    console.log("arg2 = " + args[1].readUtf8String());
  }
});
```

Механику такого хука мы разберём вживую на настоящей программе в уроке `mobile-dynamic-frida` — там будет реальный вывод перехвата `strcmp`. Идея та же: вместо чтения кода мы смотрим, какие значения доходят до сравнения.

## Что мы теперь знаем

По-простому:

1. Логика с пометкой `native` лежит в `.so` внутри `lib/<abi>/`, а не в Java.
2. Имя JNI-функции собирается из пакета, класса и метода: `Java_<pkg>_<Class>_<method>`.
3. `nm -D` показывает экспортируемые функции, `strings` — строки и имена библиотечных вызовов.
4. Ожидаемый секрет часто собирается прямо в коде — его видно в дизассемблере.
5. Вместо полного реверса можно перехватить сравнение через Frida.

## На что смотреть дальше

- **Всегда проверяйте все ABI.** Нужная библиотека может отличаться по защитам между `arm64-v8a` и `x86`.
- **Ищите `strcmp`/`memcmp`.** Большинство проверок сводится к сравнению.
- **`stripped` — не приговор.** JNI-имена сохраняются, пока не используется `RegisterNatives`.
- **Дизассемблер читается по частям.** Не пытайтесь понять всё сразу — идите от сравнения.
