## Что такое Android native/JNI

Не вся логика Android-приложения написана на Java/Kotlin. Критичные части (криптография, проверки, анти-анализ) часто вынесены в нативные библиотеки на C/C++ — файлы `.so` в `lib/<abi>/`. Они вызываются из Java через JNI (Java Native Interface). Нативный код не виден в `jadx`, его нужно реверсить отдельно (Ghidra/IDA/radare2). В CTF и на пентестах нативный код часто содержит проверку флага. Цель модуля — научиться находить и реверсить `.so`.

## Как найти нативный код

```bash
find app_smali/lib -name '*.so'
unzip -l app.apk | grep '\.so'
```

Признаки в Java: `System.loadLibrary("native")`, `native`-методы, классы с JNI-именами. Связь Java↔нативный код — через имена функций вида `Java_com_example_app_MainActivity_nativeCheck`.

```bash
grep -rn 'loadLibrary\|native ' app_java | head
nm -D lib/arm64-v8a/libnative.so | grep Java_
```

## Реверс в Ghidra

Загрузите `.so` в Ghidra, выберите архитектуру (ARM64/AArch64). Начните с экспортируемых JNI-функций (`Java_...`). Посмотрите их логику: сравнения, вызовы крипто-функций, строки. Если функция обфусцирована, ищите строковые константы и точки выхода.

```bash
strings -n 6 libnative.so | grep -iE 'flag|key|error|correct'
```

## JNI-конвенции

JNI-функции принимают `JNIEnv*` и `jobject` первыми двумя аргументами. Строки Java передаются как `jstring`; их содержимое получают через `GetStringUTFChars`. Аргументы и результат видны в декомпиляции. Понимание этих конвенций ускоряет анализ.

## Динамический анализ нативного кода

Frida умеет хукать нативные функции:

```javascript
var fn = Module.findExportByName('libnative.so', 'nativeCheck');
Interceptor.attach(fn, {
    onEnter: function (args) { console.log('arg:', args[0]); },
    onLeave: function (ret) { console.log('ret:', ret); ret.replace(1); }
});
```

Это позволяет подменить результат без реверса. Для неэкспортируемых функций найдите смещение в Ghidra и используйте `Module.findBaseAddress('libnative.so').add(offset)`.

## Строки и константы

Нативный код хранит строки в `.rodata`. Если строки зашифрованы, найдите функцию их расшифровки (обычно вызывается при старте). Если строка флага собирается посимвольно, анализируйте циклы. XOR-обфускация — самая частая.

## Обфускация нативного кода

- **OLLVM** — control-flow flattening, bogus control flow, инструкционные замены.
- **Стриппинг символов** — `strip` удаляет имена; используйте сигнатуры.
- **Шифрование строк** — расшифровка в рантайме.

Обход: анализ рантайма, поиск строк, деобфускация OLLVM (`d810`, скрипты для IDA/Ghidra).

## Типичные ошибки и подводные камни

- **Искать логику только в `jadx`** — она в `.so`.
- **Не проверить все ABI** — нужная может быть только под arm64.
- **Игнорировать строки** — `.rodata` часто содержит подсказки.
- **Забыть про JNI-конвенции** — неправильная интерпретация аргументов.
- **Не использовать динамику** — хук быстрее реверса.
- **Сдаваться на обфускации** — рантайм и d810 помогают.
- **Стриппинг символов** — ищите по строкам и вызовам.

## Практический пример: реверс нативной проверки

Разберём сквозной сценарий. `jadx` показывает `nativeCheck(String)` без реализации — логика в `libnative.so`. Шаг 1: находим функцию: `nm -D libnative.so | grep Java_` — видим `Java_com_example_app_MainActivity_nativeCheck`. Шаг 2: `strings -n 6 libnative.so | grep -iE 'flag|correct|wrong'` — возможно, там подсказки. Шаг 3: загружаем в Ghidra, переходим к `Java_..._nativeCheck`, разбираем логику: сравнение входа с чем-то. Шаг 4: если сравнение посимвольное, извлекаем ожидаемые байты; если через крипто — воспроизводим. Шаг 5: если реверс сложен (обфускация), хукаем функцию через Frida и смотрим аргументы/результат при разных входах, подбирая верный.

Это типичный путь: символика → строки → Ghidra → при необходимости динамика. Нативная проверка — классическая финальная часть мобильной задачи.

## Понимание JNI-аргументов

JNI-функция получает `(JNIEnv* env, jobject thiz, ...)`. Строка — `jstring`, которую превращают в C-строку через `GetStringUTFChars`. В декомпиляции это видно как вызовы `(*env)->GetStringUTFChars(env, str, 0)`. Зная это, вы легко находите, где обрабатывается пользовательский ввод.

## Частые вопросы

«Логика обфусцирована (OLLVM)?» — используйте `d810` для IDA/Ghidra и анализ рантайма. «Символы стёрты?» — ищите по строкам и вызовам. «Не тот ABI?» — берите arm64-v8a. «Хук не срабатывает?» — функция не экспортирована; найдите смещение. «Строки зашифрованы?» — найдите функцию расшифровки.

## Расширенный чек-лист по нативному коду

Порядок. Первое: найдите `.so` (`find lib -name '*.so'`, `unzip -l`). Второе: посмотрите экспортируемые JNI-функции (`nm -D | grep Java_`). Третье: извлеките строки (`strings -n 6`) — часто там подсказки и сообщения об ошибке. Четвёртое: загрузите в Ghidra/IDA, выберите ABI (arm64-v8a), разберите JNI-функции. Пятое: если быстро нужно подменить результат — Frida `Interceptor.attach` по имени или смещению. Шестое: если строки зашифрованы — найдите функцию расшифровки. Седьмое: если обфускация OLLVM — `d810` и анализ рантайма. Восьмое: проверьте все ABI — нужная библиотека может быть только под arm64.

## Поиск неэкспортируемых функций

Если функция не экспортируется, найдите её смещение в Ghidra (адрес минус база модуля) и хукайте через `Module.findBaseAddress('libnative.so').add(offset)`. Для поиска функции по поведению используйте трассировку (`frida-trace -U -i 'strcmp'`), чтобы понять, где сравнивается ввод.

## Частые вопросы

«Символы стёрты?» — ищите по строкам и вызовам `strcmp`/`memcmp`. «OLLVM?» — `d810` + рантайм. «Хук не работает?» — не тот экспорт или смещение. «Строки зашифрованы?» — функция расшифровки при старте. «Не тот ABI?» — arm64-v8a.

## Что дальше / решение

Итог: нативный код реверсится комбинацией статики (Ghidra/IDA) и динамики (Frida). Ищите JNI-функции, строки, сравнения; для обфускации — `d810` и рантайм. Умение реверсить `.so` обязательно для серьёзных мобильных задач.

## Практический пример: находим сравнение в нативном коде

Разберём сценарий. Функция `nativeCheck` обфусцирована, и Ghidra показывает запутанный поток. Шаг 1: трассируем вызовы `strcmp`/`memcmp` через Frida: `frida-trace -U -i 'strcmp' -i 'memcmp'` — видим, какие строки сравниваются. Шаг 2: если сравнение с ожидаемым флагом — просто читаем аргументы. Шаг 3: если XOR — находим ключ рядом. Шаг 4: если функция собирает строку посимвольно, смотрим цикл и константы. Шаг 5: если всё сложно — подменяем результат функции на «успех» через `Interceptor` и смотрим, что приложение делает дальше (часто показывает флаг).

Этот приём — «трассировка сравнений» — один из самых быстрых способов понять нативную проверку без полного реверса.

## Понимание ABI и вызовов

ARM64 ABI передаёт первые аргументы в регистрах `x0`-`x7`. В Ghidra это видно как параметры. JNI-функции: `x0` = `JNIEnv*`, `x1` = `jobject`, далее — аргументы Java. Зная это, вы правильно интерпретируете сигнатуру и находите пользовательский ввод.

## Частые вопросы

«OLLVM мешает?» — `d810` и трассировка сравнений. «Символы стёрты?» — `frida-trace` по известным функциям. «Хук не срабатывает?» — не тот экспорт/смещение. «Строки зашифрованы?» — функция расшифровки. «Нужен флаг?» — подмена результата проверки.
