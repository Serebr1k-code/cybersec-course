## Вопрос, с которого всё начинается

Вы скачали приложение, а это не один APK, а папка: `base.apk`, `config.arm64_v8a.apk`,
`config.xxhdpi.apk` и другие. JADX открывает только base — кода меньше, чем ожидалось. Что это
за файлы и как собрать их в одно целое?

## Наш пример: набор сплитов

```bash
$ ls
base.apk  config.arm64_v8a.apk  config.en.apk  config.xxhdpi.apk
$ unzip -l config.arm64_v8a.apk | head
  lib/arm64-v8a/libfoo.so
```

Видно, что `config.arm64_v8a` содержит нативные библиотеки, а base — код и ресурсы. Это split
APK.

## Шаг 1: зачем split

Размер приложения важен. Если отдавать всем один APK со всеми архитектурами и языками, он
раздут. Поэтому Google Play разбивает приложение: base (общий код) плюс сплиты под конкретное
устройство (архитектура, плотность экрана, язык). Устройство получает только нужные части.

## Шаг 2: что внутри base и сплитов

- **base** — основной код (DEX), манифест, общие ресурсы.
- **config.<abi>** — нативные библиотеки под архитектуру (arm64, armeabi).
- **config.<dpi>** — ресурсы под плотность экрана.
- **config.<lang>** — строки под язык.

Для анализа это означает: код может ссылаться на `.so` из другого сплита, которого нет в base.

## Шаг 3: установка набора

Устанавливают все сплиты одной командой:

```bash
$ adb install-multiple base.apk config.arm64_v8a.apk config.xxhdpi.apk
```

`install-multiple` — установка нескольких APK как одного приложения. Обычный `adb install` один
APK из набора не примет.

## Шаг 4: слияние в один APK

Для анализа удобно объединить всё в один APK. Это делает APKEditor:

```bash
$ java -jar APKEditor.jar m -i . -o merged.apk
$ jadx -d out merged.apk
```

`m` — merge. После слияния JADX видит и код, и нативные библиотеки, и все ресурсы — картина
полная.

## Шаг 5: анализ с учётом сплитов

Даже без слияния важно помнить: если в коде есть `System.loadLibrary`, библиотека лежит в
config-сплите. Отсутствие `.so` в base — не значит, что его нет вообще. Проверяйте все сплиты.

## Шаг 6: защита и особенности

Некоторые приложения кладут проверки целостности в отдельный сплит, рассчитывая, что аналитик
его пропустит. Другие используют split для динамической доставки. Поэтому при реверсе всегда
проверяют полный набор, а не только base.

## Шаг 7: практика

Типовой порядок: собрать все сплиты → объединить в merged.apk → анализировать как единое
приложение. Это снимает путаницу «код есть, а библиотеки нет».

## Что мы теперь знаем

- Split APK — разбиение приложения на base и конфиг-части.
- Сплиты делят код, нативные библиотеки, ресурсы, языки.
- Устанавливают их через install-multiple.
- APKEditor сливает набор в один APK.
- Анализировать нужно весь набор, а не только base.

## Как Android грузит сплиты

Split APK — это механизм, при котором одно приложение состоит из нескольких APK-файлов,
устанавливаемых вместе. При установке система регистрирует их как части одного пакета. В
рантайме они «склеиваются» в единое приложение: ресурсы, нативные библиотеки и код видны так,
будто лежат в одном APK.

С точки зрения процесса это выглядит так: `base.apk` даёт код и манифест, а конфиг-сплиты
добавляют то, чего не хватает конкретному устройству. Система выбирает нужные сплиты по
конфигурации: архитектура процессора, плотность экрана, язык.

Важно для анализа: если вы открыли только `base.apk`, вы видите **часть** приложения. Код может
ссылаться на ресурс или библиотеку, которых в base нет, — они в сплите.

## Что реально внутри каждого сплита

```bash
$ unzip -l base.apk | awk '{print $4}' | grep -E 'dex|so|resources' | head
classes.dex
resources.arsc
AndroidManifest.xml

$ unzip -l config.arm64_v8a.apk | awk '{print $4}' | head
lib/arm64-v8a/libnative.so

$ unzip -l config.en.apk | awk '{print $4}' | head
resources.arsc
```

`base.apk` содержит DEX, манифест и общий `resources.arsc`. `config.<abi>.apk` — только нативные
библиотеки под архитектуру. `config.<lang>.apk` и `config.<dpi>.apk` — урезанные `resources.arsc`
с нужными языками/плотностями. Код приложения при этом весь в base (или в feature-модулях AAB).

## Установка и извлечение через adb

Установить набор целиком можно одной командой:

```bash
$ adb install-multiple base.apk config.arm64_v8a.apk config.en.apk config.xxhdpi.apk
```

Обычный `adb install` примет только один APK и не соберёт набор. Чтобы вытащить уже
установленные сплиты с устройства:

```bash
$ adb shell pm path com.example
package:/data/app/~~AbC==/com.example-XyZ==/base.apk
package:/data/app/~~AbC==/com.example-XyZ==/split_config.arm64_v8a.apk
package:/data/app/~~AbC==/com.example-XyZ==/split_config.en.apk
```

`pm path` печатает пути всех частей приложения. Дальше `adb pull` вытягивает каждую. Так получают
набор, который реально работает на конкретном устройстве.

## Слияние: APKEditor и альтернативы

Для анализа удобно объединить сплиты в один APK. Это делает APKEditor:

```bash
$ java -jar APKEditor.jar m -i ./splits -o merged.apk
$ jadx -d out merged.apk
```

`m` — merge: инструмент склеивает манифесты, ресурсы, DEX и библиотеки в единый APK. После этого
JADX видит полную картину.

Альтернатива — анализировать по отдельности: `jadx` для base, `readelf`/`nm` для библиотек из
ABI-сплита, `aapt2 dump resources` для ресурсов. Это дольше, но иногда точнее, потому что вы
контролируете, что именно смотрите.

## Таблица типов сплитов

| Имя сплита | Содержимое | Зачем |
|---|---|---|
| base | код, манифест, общие ресурсы | всегда |
| config.arm64_v8a | lib/arm64-v8a/*.so | ABI |
| config.armeabi_v7a | lib/armeabi-v7a/*.so | ABI |
| config.xxhdpi | ресурсы под плотность | экран |
| config.en | строки языка | локализация |
| feature_* | динамический модуль | доставка по требованию |

## Если не сработало

Если `adb install-multiple` падает с `INSTALL_FAILED_INVALID_APK`, — проверьте, что все части
одной версии и подписаны одним ключом. Смешивать сплиты разных сборок нельзя.

Если APKEditor merge падает, — попробуйте обновить инструмент: он чувствителен к версии формата
ресурсов. Иногда помогает предварительно разобрать и собрать через `apktool` (но apktool хуже
работает со сплитами).

Если после merge JADX не видит библиотеку, — возможно, merge не перенёс `lib/`. Проверьте
`unzip -l merged.apk | grep '\.so'` и при необходимости добавьте библиотеки вручную.

## Ограничения

Split APK существует ради размера: устройство скачивает только нужное. Обратная сторона — анализ
усложняется, потому что «приложение» размазано по файлам, и без слияния легко упустить часть
кода или ресурсов.

Некоторые приложения намеренно кладут проверки в отдельный сплит, рассчитывая, что аналитик
посмотрит только base. Поэтому при реверсе всегда проверяйте полный набор, а не только
`base.apk`. Правило простое: если в коде есть `System.loadLibrary`, соответствующая `.so` лежит в
ABI-сплите — ищите её там.

## Мини-практика: собрать и проверить набор сплитов

Разберём полный цикл на устройстве и на диске.

На устройстве. Смотрим, из каких частей состоит установленное приложение:

```bash
$ adb shell pm path com.example
package:/data/app/~~x==/com.example-y==/base.apk
package:/data/app/~~x==/com.example-y==/split_config.arm64_v8a.apk
package:/data/app/~~x==/com.example-y==/split_config.ru.apk
```

Вытягиваем все части:

```bash
$ adb shell pm path com.example | sed 's/package://' | xargs -I{} adb pull {}
$ ls *.apk
base.apk  split_config.arm64_v8a.apk  split_config.ru.apk
```

На диске. Если у вас уже есть набор файлов, объединяем:

```bash
$ mkdir splits && cp base.apk config.*.apk splits/
$ java -jar APKEditor.jar m -i splits -o merged.apk
$ unzip -l merged.apk | grep -c '\.so'
```

Счётчик `.so` подтверждает, что библиотеки из ABI-сплита попали в merged APK. Теперь JADX видит
и код, и нативную часть.

## Частые ошибки

Ошибка первая — открыть в JADX только `base.apk` и решить, что нативных библиотек нет. Они лежат
в `config.<abi>.apk`. Всегда проверяйте полный набор.

Ошибка вторая — смешивать сплиты разных версий. `install-multiple` упадёт с
`INSTALL_FAILED_INVALID_APK`, если части из разных сборок или подписаны разными ключами.

Ошибка третья — считать, что `config.ru.apk` содержит код. Нет: это ресурсы локализации, кода там
не бывает.

Ошибка четвёртая — забыть, что сплиты можно доставлять динамически. Часть ресурсов может
отсутствовать в базовом наборе и подгружаться позже (asset delivery).

## Что это даёт при реверсе

Понимание сплитов снимает самую частую путаницу: «код ссылается на `.so`, а его нет». Правило
простое — если в коде есть `System.loadLibrary`, библиотека лежит в `config.<abi>.apk`. Проверьте
все сплиты, объедините в merged APK, и картина станет полной.

## Шпаргалка: сплиты и команды

| Задача | Команда |
|---|---|
| пути установленных сплитов | `adb shell pm path <pkg>` |
| вытащить все части | `adb pull` по путям из `pm path` |
| установить набор | `adb install-multiple base.apk config.*.apk` |
| слить в один APK | `APKEditor m -i splits -o merged.apk` |
| проверить библиотеки | `unzip -l merged.apk \| grep '\.so'` |
| разобрать ресурсы | `aapt2 dump resources base.apk` |

Этой таблицы достаточно, чтобы провести полный цикл «получить → слить → проанализировать». Держите
её под рукой: сплиты — рутинная часть современного реверса Android.

## Почему это стоит запомнить

Сплиты — не деталь, а норма современного Android. Если вы научились собирать набор, сливать его и
проверять содержимое, вы снимаете целый класс ложных выводов вроде «кода нет» или «библиотеки
нет». Это база, на которую опирается всё дальнейшее: анализ DEX, нативного слоя и ресурсов.
