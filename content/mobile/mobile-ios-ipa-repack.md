## Вопрос, с которого всё начинается

Иногда нужно не просто поставить чужое приложение, а **изменить** его: добавить свой код,
внедрить Frida Gadget, поправить проверку или подменить ресурс. Для этого IPA вскрывают,
меняют содержимое и подписывают заново. Разберём полный цикл на одном приложении.

## Наш пример: внедряем Frida Gadget

Возьмём `MyApp.ipa` и внедрим в него `FridaGadget.dylib`, чтобы получить хукинг без jailbreak.
Это сквозной пример: от распаковки до запуска на устройстве.

## Шаг 1: распаковка IPA

IPA — это ZIP-архив с каталогом `Payload`:

```bash
$ unzip -o MyApp.ipa -d work
$ ls work/Payload/MyApp.app
MyApp  Info.plist  Frameworks/  embedded.mobileprovision
```

`Info.plist` — метаданные приложения, `MyApp` — бинарник, `Frameworks/` — встроенные
библиотеки.

## Шаг 2: правка Info.plist

Некоторые проверки (например, запрет отладки) живут в `Info.plist`. Править удобно через
`plutil`:

```bash
$ plutil -replace UIFileSharingEnabled -bool YES work/Payload/MyApp.app/Info.plist
$ plutil -p work/Payload/MyApp.app/Info.plist | grep UIFileSharing
  "UIFileSharingEnabled" => 1
```

Так же включают file-sharing, меняют bundle id или добавляют разрешённые схемы.

## Шаг 3: внедрение Frida Gadget

Копируем библиотеку в `Frameworks/` и добавляем её в зависимости бинарника. Для arm64 это
делают инструментом `insert_dylib` или патчем load-команд:

```bash
$ cp FridaGadget.dylib work/Payload/MyApp.app/Frameworks/
$ insert_dylib --strip-codesig --inplace     @executable_path/Frameworks/FridaGadget.dylib work/Payload/MyApp.app/MyApp
Added LC_LOAD_DYLIB to MyApp
```

Проверить, что зависимость появилась, можно через `otool -L` — мы уже видели этот приём в уроке
про Mach-O.

## Шаг 4: повторная подпись

Правка ломает подпись, поэтому бандл подписывают заново. Сначала — все вложенные бинарники и
библиотеки, затем основной:

```bash
$ codesign --force --sign "Apple Development: dev@example.com"     work/Payload/MyApp.app/Frameworks/FridaGadget.dylib
$ codesign --force --deep --sign "Apple Development: dev@example.com"     work/Payload/MyApp.app
```

Затем IPA собирают обратно:

```bash
$ cd work && zip -qr ../MyApp-patched.ipa Payload
```

## Шаг 5: установка и проверка хука

Ставим перепакованный IPA через ideviceinstaller или AltStore. При запуске Gadget ждёт
подключения Frida:

```bash
$ frida-ps -U | grep MyApp
1234  MyApp (Gadget)
```

Если процесс виден с пометкой Gadget — внедрение удалось.

## Шаг 5: проверка внедрения

После правки убеждаемся, что Gadget действительно попал в бандл и в load-команды:

```bash
$ otool -L work/Payload/MyApp.app/MyApp | grep -i frida
  @executable_path/Frameworks/FridaGadget.dylib (compatibility version 0.0.0, current version 0.0.0)
$ ls work/Payload/MyApp.app/Frameworks/
FridaGadget.dylib
```

Первая команда показывает, что бинарник ссылается на библиотеку; вторая — что файл на месте.
Если ссылки нет, значит `insert_dylib` не сработал и Gadget не загрузится.

## Шаг 6: переупаковка и установка

Собираем IPA обратно и ставим на устройство:

```bash
$ cd work && zip -qr ../MyApp-patched.ipa Payload
$ ideviceinstaller -i ../MyApp-patched.ipa
Install: Complete
$ frida-ps -U | grep -i gadget
MyApp (Gadget)
```

`zip` должен складывать именно каталог `Payload` в корень архива — иначе установщик не найдёт
бандл. Строка `MyApp (Gadget)` в `frida-ps` — признак того, что инструментирование активно.

## Шаг 7: типичные ошибки подписи

| Ошибка | Причина | Решение |
|---|---|---|
| `code object is not signed at all` | пропущена подпись | подписать вложенные + основной |
| `invalid signature` | подписали до копирования Gadget | порядок: сначала правки, потом подпись |
| `no such file` при установке | неверная структура ZIP | `Payload` в корне архива |
| приложение не запускается | профиль не для этого устройства | добавить UDID в профиль |

Правило порядка: сначала **все** правки файлов, затем подпись вложенных библиотек, затем
основного бинарника, и только потом упаковка и установка.

## Шаг 8: отладка загрузки Gadget

Если приложение падает при старте, смотрим логи устройства:

```bash
$ idevicesyslog | grep -iE 'Frida|Gadget|dyld'
dyld: Library not loaded: @executable_path/Frameworks/FridaGadget.dylib
```

`dyld` сообщает, какую библиотеку не смог загрузить. Чаще всего причина — Gadget скопирован, но
не добавлен в load-команды, либо подпись библиотеки не совпадает с подписью приложения.

## Ограничения метода

Перепаковка ломает исходную подпись, поэтому приложение не обновится из App Store и может
проверять свою целостность (сравнивать хеш бандла или проверять наличие лишних load-команд).
Для защиты от таких проверок Gadget внедряют скрытно, а проверки патчат в бинарнике. Кроме того,
некоторые приложения проверяют `codesign` изнутри — тогда одной перепаковки мало, нужен ещё и
обход этих проверок.

## Практический вывод

Перепаковка IPA — базовый навык мобильного пентеста: она позволяет внедрить инструментацию без
jailbreak. Ключ к успеху — порядок операций (правки → подпись вложенных → подпись основного →
упаковка → установка) и внимательное чтение ошибок `codesign`/`dyld`. Один раз отработав цикл на
тестовом приложении, дальше вы повторяете его на любом IPA.

## Шаг 9: подпись с нужными entitlements

Иногда приложению нужны особые права (например, `get-task-allow` для отладки). Их задают при
подписи:

```bash
$ cat ent.plist
<key>get-task-allow</key><true/>
$ codesign --force --sign "Apple Development: dev@example.com" --entitlements ent.plist     work/Payload/MyApp.app/MyApp
```

`get-task-allow` позволяет подключить отладчик к приложению — это удобно для динамического
анализа. Важно, чтобы entitlements совпадали с профилем: если профиль их не разрешает, установка
или запуск упадут.

## Что делать с проверками целостности

Приложение может проверять свою подпись, хешировать бандл или искать лишние load-команды. Тогда
после перепаковки оно откажется работать. Способы борьбы:

- найти и пропатчить функцию проверки (по строкам ошибок и вызовам `codesign`/`SecStaticCode`);
- хукать проверку через Frida Gadget, если он уже внедрён;
- проверить, не сверяет ли приложение `_CodeSignature/CodeResources` с содержимым.

Часто достаточно найти вызов `SecStaticCodeCheckValidity` и заставить его вернуть «успех».

## Чек-лист по перепаковке

- IPA распакован, бандл найден.
- Правки внесены до подписи.
- Вложенные библиотеки подписаны первыми.
- Основной бинарник подписан, entitlements заданы.
- Архив собран с `Payload` в корне.
- Приложение установилось и запускается.
- Gadget виден в `frida-ps`.

## Практический сценарий целиком

Полный цикл перепаковки: распаковать IPA (`unzip`), найти бандл в `Payload/`, внести правки —
поправить `Info.plist` через `plutil`, скопировать `FridaGadget.dylib` в `Frameworks/`, добавить
зависимость через `insert_dylib`. Затем подписать всё заново: сначала вложенные библиотеки, потом
основной бинарник с нужными entitlements. Собрать архив так, чтобы `Payload` лежал в корне, и
установить через `ideviceinstaller`. Наконец, проверить, что приложение запускается и Gadget
виден в `frida-ps`. Если приложение падает, читаем `idevicesyslog` и ищем причину в `dyld`.

## Что писать в отчёте

Указывают: что именно внедрялось (Gadget, патч проверки, правка ресурса), какие правки в
`Info.plist`, какие entitlements использовались, как обходились проверки целостности. Отмечают,
что перепакованный бандл теряет исходную подпись и не обновляется из App Store. Для PoC-сборок
описывают воспроизводимые шаги, чтобы результат можно было повторить.

## Типичные ошибки при перепаковке

Первая и самая частая — подписать бандл до копирования Gadget: тогда подпись не покрывает
изменённый файл, и приложение падает при загрузке. Вторая — забыть подписать вложенные
библиотеки: `codesign --deep` иногда пропускает их, и `dyld` не находит Gadget. Третья —
неправильная структура архива: если `Payload` не в корне, установщик не находит бандл. Четвёртая
— несовпадение entitlements с профилем, из-за чего приложение не запускается. Пятая — забыть про
проверки целостности: приложение сверяет хеш и отказывается работать. Все эти ошибки видны в
`idevicesyslog`, поэтому первое, что стоит сделать при сбое, — прочитать лог `dyld` и `codesign`.

## Итоговая мысль

Перепаковка — это навык, который окупается сразу: один раз отработав цикл «распаковать → изменить
→ подписать → установить», вы можете инструментировать любое приложение без jailbreak. Главное —
дисциплина порядка операций и умение читать ошибки подписи. Не бойтесь экспериментировать на
тестовом приложении: сбои здесь безопасны, а понимание, которое вы получаете, переносится на
реальные задачи. Со временем вы научитесь предугадывать, где приложение проверяет целостность, и
готовить обход заранее.

## Когда перепаковка не нужна

Не всегда стоит лезть в бандл. Если приложение уже содержит Frida Gadget, установленный другим
способом, или устройство имеет jailbreak с работающим Frida, перепаковка только добавит рисков:
вы измените подпись и можете задеть проверки целостности. Перед тем как браться за перепаковку,
проверьте, нельзя ли достичь цели менее инвазивно — через динамический анализ на подготовленном
устройстве. Перепаковка оправдана, когда другого пути нет: например, нужно добавить свой код или
подменить ресурс.

## Что мы теперь знаем

- IPA — ZIP с `Payload/<App>.app`.
- `Info.plist` правится `plutil`; бинарник — внедрением dylib.
- Правка ломает подпись; подпись идёт изнутри наружу (`--deep`).
- Перепакованный IPA ставится как обычный sideload.

## Если не сработало

Если приложение падает сразу после запуска, проверьте, что Gadget подписан тем же сертификатом
и что путь `@executable_path/Frameworks/...` верен. Если `codesign --deep` не помогает на
сложных бандлах, подписывайте вложенные компоненты вручную по порядку. Если установка
отклоняется, сверьте bundle id с provisioning-профилем.

## Частые вопросы

**Зачем `--deep`?** Он рекурсивно подписывает вложенные бинарники; но ручной порядок надёжнее.

**Можно ли внедрить без jailbreak?** Да, через Frida Gadget и переподпись.

**Ломает ли это целостность?** Да, хеши меняются — но подпись накладывается заново.
