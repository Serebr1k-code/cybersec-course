## Вопрос, с которого всё начинается

Ты разобрал Appium и понял: это сервер, который издалека управляет устройством. Но что,
если тебе нужен не «издалека», а изнутри самого приложения — быстро, точно и без сети?
Именно так работают тесты, которые пишут разработчики Android. Этот инструмент называется
**Espresso**.

## Почему «изнутри» — это другое

Appium общается с приложением по HTTP через драйвер. Espresso — нет. Espresso-тест
компилируется **в тот же APK**, что и приложение, и запускается в том же процессе. Он видит
виджеты напрямую, как объекты в памяти, а не как картинки на экране. Отсюда три следствия:

- **Быстро** — не нужно гонять данные по сети и ждать отрисовки.
- **Точно** — тест знает реальный идентификатор виджета, а не угадывает по координатам.
- **Хрупко по-своему** — тест ломается при переименовании виджета, потому что он завязан
  на внутренние имена.

Для пентестера это означает: Espresso-тесты встречаются в исходниках приложения, и их можно
**дописать** — превратить в оружие для воспроизведения уязвимости.

## Наш пример: читаем отчёт

Мы не всегда пишем тесты сами. Часто перед нами **отчёт** чужого прогона. Вот фрагмент
`espresso_report.txt` (ровно его ты разберёшь в практике):

```
com.example.bank.LoginTest > loginWithWrongPassword FAILED
    java.lang.AssertionError: expected balance screen but got intent:
        com.example.bank.ACTION_DEBUG
        at com.example.bank.LoginTest.loginWithWrongPassword(LoginTest.java:42)
Tests run: 2, Failures: 1
```

Читаем глазами пентестера. Тест `loginWithWrongPassword` ожидал, что после **неверного**
пароля покажется экран баланса (то есть тест сам по себе странный — он проверял, что вход
всё равно пройдёт). Но получил intent `com.example.bank.ACTION_DEBUG`. Уже тут видно
две вещи: во-первых, в приложении есть **отладочный action**; во-вторых, неверный пароль
почему-то ведёт к нему. Это и есть та «лишняя» строка, где в практике спрятан флаг.

## Шаг 1: анатомия Espresso-теста

Минимальный тест выглядит так:

```java
@Test
public void loginShowsBalance() {
    onView(withId(R.id.login)).perform(typeText("alice"));
    onView(withId(R.id.password)).perform(typeText("hunter2"));
    onView(withId(R.id.submit)).perform(click());
    onView(withId(R.id.balance)).check(matches(isDisplayed()));
}
```

Три глагола: `onView` — «найди виджет», `perform` — «сделай действие», `check` — «проверь
условие». Виджет ищется **матчером**: `withId`, `withText`, `withContentDescription`.
Никаких координат и XPath — только реальные свойства.

## Шаг 2: чем Espresso отличается от UiAutomator

Внутри Android есть ещё **UiAutomator** — тоже нативный фреймворк. Разница в области:

- **Espresso** видит только своё приложение (тот же процесс).
- **UiAutomator** видит **весь экран**, включая системные диалоги и чужие приложения.

Отсюда правило: проверяешь свои экраны — Espresso; нужно нажать «Разрешить» в системном
диалоге или выйти за пределы приложения — UiAutomator. Часто их комбинируют.

## Шаг 3: где Espresso уязвим как инструмент

Espresso-тест — это код внутри приложения. Если тестировщик оставил в тестовой сборке
**отладочные точки входа** (как `ACTION_DEBUG` в нашем примере) и они уехали в релиз — это
находка. Правило: читая Espresso-отчёт, ищи в стектрейсах имена action-ов, URL и токенов,
которых в нормальном приложении быть не должно.

## Шаг 4: запуск

Тест запускается так:

```
$ ./gradlew connectedAndroidTest
```

`connectedAndroidTest` собирает тестовый APK, ставит его на подключённое устройство и
прогоняет все тесты. В выводе — та самая сводка `Tests run: N, Failures: M`, которую мы
читали выше. Обрати внимание: тест ставится как **отдельный** APK, но с тем же `sharedUserId`
в тестовой сборке, поэтому и видит приложение изнутри.

## Что мы теперь знаем

- Espresso работает внутри процесса приложения — отсюда скорость и точность.
- Тест состоит из `onView` + `perform` + `check` и матчеров.
- Espresso видит только своё приложение, UiAutomator — весь экран.
- Отчёт о падении — источник находок: отладочные action-ы, URL, токены.
- Запуск — `./gradlew connectedAndroidTest`.

## Практика: читаем стектрейс и вытаскиваем находку

В отчёте из примера нас интересует строка с action-ом. Посмотрим на неё внимательнее:

```
$ grep -nE 'ACTION_|http|token|Intent' espresso_report.txt
12:        com.example.bank.ACTION_DEBUG
18:        extra: debug_url=http://10.0.0.7:8080/admin
```

Две находки сразу: недокументированный `ACTION_DEBUG` и отладочный URL в extra-данных
intent-а. Оба уехали в **тестовую сборку** и, судя по отчёту, доступны. Это классика:
отладочные точки входа, забытые в релизе, — прямой путь к скрытой функциональности.

## Таблица: матчеры Espresso

| Матчер | Что находит | Пример |
|--------|-------------|--------|
| `withId(R.id.x)` | по идентификатору ресурса | `onView(withId(R.id.login))` |
| `withText("...")` | по видимому тексту | кнопка «Войти» |
| `withContentDescription` | по описанию доступности | иконки без текста |
| `withClassName` | по типу виджета | `Button`, `EditText` |
| `allOf(...)` / `anyOf(...)` | комбинация условий | виджет с id и текстом |

Матчеры опираются на **реальные свойства** виджета, а не на координаты, — поэтому
Espresso-тест надёжнее «клик по пикселю». Для пентестера это означает: тест можно
дописать и он стабильно воспроизведёт уязвимость.

## Дописываем тест как оружие

Если у нас есть исходники теста, добавим проверку, которая «прощупывает» логику:

```java
@Test
public void probeDebugAction() {
    Intent i = new Intent("com.example.bank.ACTION_DEBUG");
    i.putExtra("debug_url", "http://attacker.example");
    // отправляем intent и смотрим, что приложение сделает
    onView(withId(R.id.debug)).perform(click());
    onView(withText("debug_url")).check(matches(isDisplayed()));
}
```

Так тест превращается из проверки в **воспроизводимый PoC**: он документирует, как
приложение реагирует на скрытый action. В отчёте такой тест — сильнее скриншота.

## Если сработало / не сработало

- **Сработало:** тест воспроизводит уязвимость стабильно, стектрейс указывает на
  отладочный action/URL. Зафиксируй имя action-а и путь в отчёте.
- **Не сработало:** тест падает по таймауту — виджет не найден. Проверь, что тест
  запускается на **нужной** сборке (debug, а не release): отладочные точки обычно
  вырезаны из релиза.
- **Тест «зелёный» там, где ждали падения:** значит, приложение уже обработало случай
  корректно; ищи другой путь (другой action, другой extra).

## Ограничения

Espresso видит **только своё приложение**: системные диалоги и чужие окна ему
недоступны — для них нужен UiAutomator. Кроме того, тест завязан на внутренние
идентификаторы виджетов и ломается при их переименовании. Поэтому Espresso хорош для
точного воспроизведения внутри приложения, но не для исследования «всего экрана».

## Разбор: почему тест «висит» — idling resource

Espresso синхронизируется с UI через **idling resources**: он ждёт, пока очередь
сообщений главного потока пуста. Если приложение держит фоновую задачу (сеть, анимация),
тест бесконечно ждёт и падает по таймауту:

```
androidx.test.espresso.AppNotIdleException: Looped for 5 iterations over 60s.
```

Для пентестера это важно: такой таймаут в отчёте — сигнал, что приложение что-то
делает в фоне (возможно, сетевой запрос к подозрительному хосту). Обратная сторона:
если проверка уязвимости идёт в фоне, тест может «пройти» раньше, чем она завершится.

## Чтение отчёта: FAILED против ERROR

Различай два вида падения в сводке:

| Статус | Смысл | Что искать |
|--------|-------|------------|
| `FAILED` | утверждение не выполнено | ожидаемый экран не совпал с реальным |
| `ERROR` | тест не смог выполниться | исключение, отсутствие виджета, таймаут |

`FAILED` часто даёт находки (реальность отличается от ожидания), `ERROR` — обычно
проблемы окружения. В нашем отчёте был `FAILED` с `AssertionError` — то есть приложение
вело себя не так, как ждал тест, и в этом «не так» спрятан `ACTION_DEBUG`.

## Ошибки при работе с Espresso

- Запускать тест на release-сборке и удивляться, что отладочные точки недоступны.
- Игнорировать `ERROR`-падения, хотя часть из них — про сеть и утечки.
- Пытаться управлять системными диалогами через Espresso (нужен UiAutomator).
- Считать «зелёный» тест доказательством безопасности: он проверяет только то, что
  в нём написано.

принцип «изнутри», но для iOS. А пока запомни: Espresso-отчёт — это не только «упало/не
упало», это карта отладочных входов приложения.

- Разбор чужих CI-отчётов Android-приложения: поиск утёкших отладочных точек входа.
