## Вопрос, с которого всё начинается

Приложение запускается медленно, а через минуту работы становится быстрым. Или наоборот:
на эмуляторе ведёт себя иначе, чем на устройстве. Причина — **JIT**: Android компилирует
код прямо во время работы. Разберёмся, как это устроено и почему аналитику важно об
этом знать.

## Наш пример: «холодный» и «горячий» запуск

Замерим время двух запусков одного и того же приложения:

```bash
$ adb shell am start -W com.example.app/.MainActivity | grep TotalTime
TotalTime: 820
$ adb shell am force-stop com.example.app
$ adb shell am start -W com.example.app/.MainActivity | grep TotalTime
TotalTime: 410
```

Второй запуск вдвое быстрее. Это не совпадение: за первый запуск ART скомпилировал
горячие методы, и второй раз они уже в нативном коде.

## Шаг 1: что такое JIT

**JIT** (just-in-time) — компиляция «в момент исполнения». Когда ART замечает, что метод
вызывается часто, он компилирует его в нативный код и подменяет точку входа. Дальше
вызовы идут напрямую в машинный код, а не через интерпретатор.

Плюс: не нужно компилировать всё при установке, приложение ставится быстрее. Минус:
первые запуски медленнее, потому что код ещё «холодный».

## Шаг 2: профили

JIT и AOT связаны через **профили**. Когда метод становится горячим, ART записывает это
в профиль. Система позже читает профиль и компилирует горячее заранее (AOT). Так
достигается **profile-guided optimization** (PGO): компилируется то, что реально
используется.

```bash
$ adb shell dumpsys package com.example.app | grep -i "profile"
```

Профиль — это ответ на вопрос «что скомпилировано». Если приложение долго работало,
большая часть горячих методов уже в нативном коде.

## Шаг 3: как это меняет анализ

Три следствия для реверса и хукинга:

1. **Код меняется со временем.** Метод, который вчера интерпретировался, сегодня
   скомпилирован. Статический анализ этого не видит.
2. **Хук на байткоде может промахнуться.** Если метод уже нативный, перехват на уровне
   dex не сработает.
3. **Производительность — индикатор.** Резкое ускорение подсказывает, какие методы
   горячие, а значит, важные для логики.

## Шаг 4: ручное управление компиляцией

На rooted-устройстве можно управлять компиляцией вручную:

```bash
$ adb shell cmd package compile -m speed -f com.example.app
Success
$ adb shell cmd package compile -m verify -f com.example.app
Success
```

`speed` компилирует максимум, `verify` — только проверяет байткод. Аналитику полезно
уметь переключать режим: иногда удобнее работать, когда код интерпретируется (проще
хукать), иногда — когда скомпилирован (видно натив).

## Шаг 5: практический вывод

Если поведение приложения отличается на разных запусках, не ищи «магию» — проверь
прогрев. Сделай холодный запуск, потом горячий, сравни. Если различия есть, дело в
JIT/AOT. Для стабильного анализа иногда полезно очистить профиль:

```bash
$ adb shell cmd package compile --reset com.example.app
```

## Baseline-профили и предсказуемость

Отдельный вид профилей — **baseline profile**. Разработчик может заранее записать
профиль типичного использования и положить его в APK. Тогда даже первый запуск после
установки компилирует нужные методы сразу, без прогрева. Это делает поведение
приложения более предсказуемым — и для пользователя, и для аналитика.

```bash
$ unzip -l com.example.app.apk | grep -i profile
  assets/dexopt/baseline.prof
```

Наличие baseline-профиля означает, что часть кода скомпилирована уже при первом
запуске. Для хукинга это важно: рассчитывать на «интерпретируемый» код не всегда
получится, потому что разработчик сам позаботился о компиляции.

Обратная сторона — **разогрев через профиль**. Если приложение специально «прогревает»
методы при старте, оно может маскировать логику: к моменту анализа всё уже в нативном
коде, и хуки на dex промахиваются. Тогда перехват ставят на уровне нативного кода или
используют инструменты, умеющие работать с обоими состояниями.

## Что проверить на реальном устройстве

Сравни холодный и горячий запуск: если разница большая, JIT/AOT активно работает.

```bash
$ adb shell am start -W com.example.app/.MainActivity | grep TotalTime
$ adb shell am force-stop com.example.app
$ adb shell am start -W com.example.app/.MainActivity | grep TotalTime
```

Посмотри, есть ли в APK baseline-профиль, и оцени, насколько код уже скомпилирован.

```bash
$ unzip -l com.example.app.apk | grep -i prof
```

И проверь, как приложение ведёт себя под хуком: если хук на байткоде не срабатывает,
причина почти всегда в том, что метод скомпилирован. Тогда либо сбрасывай профиль
(`cmd package compile --reset`), либо переноси перехват на нативный уровень.

## Типичное заблуждение: эмулятор равен устройству

Частая ошибка — анализировать приложение на эмуляторе и переносить выводы на реальное
устройство. Поведение может отличаться, и одна из причин — **компиляция**. Эмулятор и
устройство имеют разные профили, разный набор скомпилированных методов и разную
производительность. То, что на эмуляторе интерпретируется, на телефоне уже в нативном
коде, и наоборот.

Это влияет и на хуки, и на замеры, и на поведение защиты. Приложение может детектировать
эмулятор именно по косвенным признакам — например, по тому, как быстро выполняются
методы или какие профили есть в системе. Поэтому выводы, полученные на эмуляторе, надо
перепроверять на реальном устройстве, желательно того же класса.

Практическое правило: если поведение «плавает» между запусками и средами, первым делом
исключи факторы рантайма — прогрев, профили, компиляцию. И только потом ищи в коде
логику, которая могла бы объяснить разницу. Это экономит много времени.

И помни: нестабильность поведения — не всегда баг приложения. Иногда это честная работа рантайма, которую аналитик обязан уметь отличить от настоящей логики, иначе выводы будут ошибочными.

## Почему это важно на практике

На первый взгляд JIT — деталь реализации, не имеющая отношения к безопасности. Но это
не так. От прогрева зависит, какие методы уже скомпилированы, а значит, где сработает
перехват. От профилей зависит, насколько приложение предсказуемо ведёт себя на разных
устройствах. От рантайма зависит, отличается ли поведение на эмуляторе и на телефоне.
Если аналитик не учитывает эти факторы, он легко примет артефакт рантайма за логику
приложения и сделает неверный вывод. Поэтому знание JIT и профилирования — это не
академический интерес, а рабочий инструмент: оно помогает отделять существенное от
случайного и строить воспроизводимые эксперименты.

## Что мы теперь знаем

- JIT компилирует горячие методы во время работы приложения.
- Профили связывают JIT и AOT, обеспечивая PGO.
- Код меняется со временем: метод может стать нативным.
- Хук на байткоде промахивается, если метод уже скомпилирован.
- Компиляцией можно управлять через `cmd package compile`.
