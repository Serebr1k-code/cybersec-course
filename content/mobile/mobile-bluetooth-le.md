## Зачем тестировать BLE-канал

Многие мобильные приложения — это пульт к устройству: трекер активности, умный замок, медицинский датчик, автозапуск автомобиля. Приложение устанавливает BLE-соединение и обменивается командами. Если канал не защищён, злоумышленник может: перехватить данные, отправить ложную команду (открыть замок), подменить устройство и «уговорить» приложение работать с ним. Для пентестера это отдельный класс находок, который не виден при тесте только APK.

Bluetooth Low Energy (BLE) устроен проще классического Bluetooth, но имеет свою модель: **центральное устройство** (central, обычно телефон) сканирует **периферию** (peripheral, устройство) и подключается. Обмен идёт через **GATT** (Generic Attribute Profile): иерархию сервисов, характеристик и дескрипторов.

## GATT: сервисы, характеристики, дескрипторы

- **Service** — логическая группа (например, Battery Service, Device Information).
- **Characteristic** — значение, которое можно читать/писать/подписываться (notify).
- **Descriptor** — метаданные характеристики (например, `Client Characteristic Configuration` для включения notify).

Каждый элемент имеет 16-битный (стандартный) или 128-битный (кастомный) UUID. Приложения обычно используют кастомные 128-битные UUID вида `0000fff1-0000-1000-8000-00805f9b34fb`.

Способы обмена:
- **Read** — центральное читает значение характеристики.
- **Write** — пишет (с ответом или без, `Write Without Response`).
- **Notify/Indicate** — периферия сама присылает обновления (для датчиков).

## Спаривание и bonding

BLE предлагает несколько режимов безопасности:
- **Just Works** — без аутентификации, уязвимо к MITM.
- **Passkey/PIN** — сравнение или ввод кода.
- **OOB (Out Of Band)** — обмен ключами по другому каналу (NFC).
- **LESC (LE Secure Connections)** — ECDH-обмен с защитой от MITM.

При bonding ключи сохраняются, и повторные соединения шифруются автоматически. Проблемы:
- Приложение/устройство использует **Just Works** для удобства — MITM возможен.
- Ключи хранятся в открытом виде на Android (`/data/misc/bluetooth/`) на root.
- Некоторые устройства «спариваются» без аутентификации, а чувствительные команды всё равно шлют.

## Инструменты

- **nRF Connect** (Android/iOS) — сканирование, подключение, чтение/запись характеристик вручную.
- **nRF Sniffer** (hardware + Wireshark) — пассивный перехват BLE-трафика.
- **Ubertooth One** — сниффер BLE (и классического BT) с открытым ПО.
- **btlejack** — сниффинг/подмена с Micro:Bit.
- **Bettercap** — модуль BLE для активных атак.
- **Frida** — перехват BLE-API приложения (`BluetoothGatt`, `CoreBluetooth`).

## Сканирование и подключение

С телефона через `nRF Connect` вы видите список устройств, их адреса и RSSI. Для автоматизации — `bluetoothctl` на Linux (для теста с адаптером):

```bash
bluetoothctl
[bluetooth]# scan on
[NEW] Device AA:BB:CC:DD:EE:FF MyLock
[bluetooth]# connect AA:BB:CC:DD:EE:FF
[MyLock]# menu gatt
[MyLock]# list-attributes
```

Через `gatttool` (устаревший, но показательный):

```bash
gatttool -b AA:BB:CC:DD:EE:FF -I
> connect
> primary          # список сервисов
> characteristics  # характеристики
> char-read-hnd 0x0016
```

## Сниффинг BLE-трафика

Пассивный перехват — ключ к пониманию протокола. С nRF Sniffer:

1. Прошить sniffer-прошивку на nRF52840 Dongle.
2. Установить плагин в Wireshark (`nrf_sniffer_for_bluetooth_le`).
3. Выбрать канал (или advertising channels 37/38/39).
4. Запустить захват и воспроизвести действие в приложении.

```bash
# после захвата — фильтры в Wireshark
btatt                # только ATT (GATT-обмен)
btle                 # advertising
btatt.opcode == 0x52 # write command
```

Если соединение **не** зашифровано, вы увидите команды в открытом виде: `write` на характеристику `fff1` со значением `01` (открыть) или `00` (закрыть). Если зашифровано (LESC) — нужен захват момента спаривания, чтобы получить ключи, что сложнее.

## Подмена периферии

Зная протокол, можно подменить устройство. С `btlejack`:

```bash
btlejack -s            # сканирование
btlejack -f <addr> -c  # перехват соединения
btlejack -f <addr> -j  # глушение/подмена
```

Или эмулировать периферию на Linux с BlueZ:

```python
# эмуляция GATT-сервера через bless (Python)
from bless import BlessServer
import asyncio

async def run():
    server = BlessServer(name="MyLock")
    await server.start()
    # добавить сервис/характеристику с теми же UUID, что у реального устройства

asyncio.run(run())
```

Приложение подключится к «вашему замку» и отдаст команды — так можно проверить, доверяет ли оно устройству без аутентификации.

## Перехват BLE-API приложения (Frida)

Android:

```javascript
Java.perform(function () {
  var Gatt = Java.use("android.bluetooth.BluetoothGatt");
  Gatt.writeCharacteristic.overload('android.bluetooth.BluetoothGattCharacteristic')
    .implementation = function (ch) {
      console.log("[BLE write] " + ch.getUuid() + " = " + bytesToHex(ch.getValue()));
      return this.writeCharacteristic(ch);
    };
  function bytesToHex(b) { return Array.from(b).map(x => ('0'+ (x & 0xff).toString(16)).slice(-2)).join(''); }
});
```

iOS (CoreBluetooth):

```javascript
var CBCentralManager = ObjC.classes.CBCentralManager;
Interceptor.attach(CBCentralManager['- centralManager:didDiscoverPeripheral:advertisementData:RSSI:'].implementation, {
  onEnter: function (args) {
    var p = new ObjC.Object(args[3]);
    console.log("[BLE] discovered " + p.name() + " " + p.identifier());
  }
});
```

## Типовые уязвимости BLE-канала

- **Отсутствие шифрования** — команды видны в сниффере.
- **Just Works pairing** — MITM и подмена.
- **Фиксированные ключи** — одинаковы на всех устройствах, есть в прошивке.
- **Отсутствие аутентификации команды** — любой, кто подключился, шлёт `open`.
- **Replay** — команда без nonce повторяется.
- **Утечка секретов в APK** — ключ шифрования BLE зашит в приложении.

## Частые ошибки и подводные камни

- **Сниффер не видит трафик** — устройство подключено на другом канале; следите за hopping или фиксируйте канал.
- **Захват есть, но данные зашифрованы** — нужен захват спаривания или ключ из прошивки.
- **Frida не хукает** — BLE-стек в отдельном процессе/нативном коде; хукайте нативно.
- **Подмена не удаётся** — устройство привязывается по MAC (адрес фиксирован у периферии).
- **nRF Connect не пишет** — характеристика только для чтения или требует notify.

## Работа с nRF Connect по шагам

nRF Connect — основной инструмент ручного исследования. Порядок работы: откройте сканер, отфильтруйте по имени/сервису, подключитесь к устройству. Вкладка **Services** покажет все сервисы и характеристики с UUID и свойствами (Read/Write/Notify). Разверните характеристику, нажмите стрелку «вниз» для чтения — увидите hex-значение. Для включения notify нажмите три стрелки рядом с характеристикой — приложение подпишется, и обновления будут приходить в реальном времени. Кнопка «вверх» (стрелка) пишет значение; выберите формат (hex/UTF-8) и введите данные.

Практический приём: включайте notify и параллельно выполняйте действие на физическом устройстве (нажмите кнопку на замке) — так вы увидите, какая характеристика и какое значение соответствуют событию. Записывая наблюдения в таблицу (UUID → действие → значение), вы быстро восстановите протокол.

## Как восстановить протокол по трафику

Восстановление протокола — это сопоставление «действие ↔ пакет». Методика:

1. Захватите трафик при одном действии (например, «открыть»), сохраните pcap.
2. Повторите другое действие («закрыть»), снова захватите.
3. Сравните: различающиеся байты — это команда.
4. Повторите действие дважды, чтобы найти изменяющиеся поля (счётчик/nonce).
5. Проверьте, есть ли контрольная сумма/CRC — попробуйте изменить значение и посмотреть, отвергнет ли устройство.

Пример: в первом захвате `write` на `fff1` = `01 00 00 00`, во втором — `00 00 00 00`. Вывод: первый байт — команда (1 = open, 0 = close), остальное — резерв. Если при повторе того же действия меняется последний байт — это, вероятно, счётчик (защита от replay). Отсутствие счётчика — находка.

## Эмуляция периферии: практический пример

Соберём минимальный GATT-сервер на Python через `bless`, повторяющий замок:

```python
from bless import BlessServer
import asyncio

async def main():
    server = BlessServer(name="MyLock")
    server.read_request_func = lambda c: b"\x00"
    server.write_request_func = lambda c, v: print("write", c, v.hex())
    await server.start()
    # добавить сервис fff0 с характеристикой fff1 (write) и fff2 (notify)
    await server.add_new_service("0000fff0-0000-1000-8000-00805f9b34fb")
    await server.add_new_characteristic(
        "0000fff0-0000-1000-8000-00805f9b34fb",
        "0000fff1-0000-1000-8000-00805f9b34fb",
        0x08,  # write
        b"\x00", None)
    while True:
        await asyncio.sleep(1)

asyncio.run(main())
```

Затем в приложении-жертве отсканируйте устройство — оно должно показать «MyLock». Подключитесь и отправьте команду. Если приложение принимает команду от вашего поддельного устройства без аутентификации — это находка об отсутствии проверки подлинности периферии. Многие приложения доверяют устройству по имени или MAC-адресу, что подделывается.

## Юридические и этические границы

Сниффинг BLE — активное вмешательство в радиоэфир. Тестируйте только свои устройства или устройства в рамках авторизованного пентеста. Подмена периферии в общественном месте (например, эмуляция чужого замка) недопустима. В отчёте фиксируйте: какие данные передавались открыто, какие команды не аутентифицированы, есть ли защита от replay и MITM. Рекомендации: использовать LE Secure Connections, привязывать команды к сессии (nonce), не полагаться на MAC/имя как на аутентификатор, хранить ключи не в APK.
