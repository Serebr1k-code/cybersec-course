## Вопрос, с которого всё начинается

Многие мобильные приложения — это пульт к устройству: трекер активности, умный замок, медицинский датчик, автосигнализация. Приложение соединяется с устройством по Bluetooth и шлёт ему команды. Если канал не защищён, злоумышленник может перехватить данные, отправить ложную команду («открой замок») или подменить устройство так, что приложение само отдаст ему команды.

Этот канал не виден, если тестировать только APK, — его надо смотреть «в эфире». В этом уроке мы возьмём реальный Bluetooth-адаптер, просканируем окружение и разберём, как устроен обмен, — а потом посмотрим на ту же тему со стороны приложения.

## Наш пример: Bluetooth-адаптер и приложение F-Droid

Два объекта: наш собственный Bluetooth-адаптер `hci0` (через него мы будем смотреть эфир) и реальное приложение `fdroid.apk` (клиент каталога F-Droid, у которого есть функция обмена по Bluetooth). Сначала — терминология, без неё дальше не разобраться.

**BLE (Bluetooth Low Energy)** — облегчённый Bluetooth для устройств с батарейкой. У него две роли: **central** (центральное, обычно телефон — оно сканирует и подключается) и **peripheral** (периферия — устройство, к которому подключаются). Обмен идёт через **GATT** (Generic Attribute Profile) — иерархию из **сервисов** (логических групп), **характеристик** (значений, которые можно читать/писать) и **дескрипторов** (их метаданных). Каждый элемент имеет **UUID** — идентификатор: 16-битный у стандартных или 128-битный у кастомных.

## Шаг 1: смотрим на адаптер

В Linux BLE управляется через `bluetoothctl`. Начнём с состояния адаптера:

```
$ bluetoothctl show
Controller 68:7A:64:95:80:A7 (public)
	Manufacturer: 0x0002 (2)
	Version: 0x0b (11)
	Name: archlinux
	Powered: yes
	Discoverable: no
	Pairable: yes
	UUID: Generic Access Profile      (00001800-0000-1000-8000-00805f9b34fb)
	UUID: Generic Attribute Profile   (00001801-0000-1000-8000-00805f9b34fb)
	UUID: Device Information          (0000180a-0000-1000-8000-00805f9b34fb)
	Roles: central
```

Читаем: адаптер включён (`Powered: yes`), его адрес — `68:7A:64:95:80:A7` (это **MAC-адрес**, уникальный идентификатор интерфейса). В списке `UUID` — уже знакомые стандартные профили: `Generic Access` (0x1800) и `Generic Attribute` (0x1801) — базовые сервисы, которые есть у любого BLE-устройства. Строка `Roles: central` говорит, что адаптер может выступать центральным, то есть сканировать и подключаться. Это то, что нам нужно.

## Шаг 2: сканируем эфир

Команда `scan on` заставляет адаптер слушать **advertising-пакеты** — короткие объявления, которыми периферия сообщает о себе. Смотрим десять секунд:

```
$ bluetoothctl --timeout 12 scan on
[NEW] Device F8:DF:15:0E:87:73 SRS-XB31
[NEW] Device 3C:38:24:D6:FA:29 Redmi Note 14 Pro
[NEW] Device 1B:2A:BF:28:95:C9 1B-2A-BF-28-95-C9
[NEW] Device 62:65:D5:47:58:74 62-65-D5-47-58-74
[NEW] Device 0B:9D:1B:08:40:2E 0B-9D-1B-08-40-2E
```

Мы видим реальные устройства: колонку `SRS-XB31` и телефон `Redmi Note 14 Pro`. Обрати внимание на последние три: у них имя совпадает с MAC-адресом. Так выглядят устройства, которые не задали «дружелюбное» имя, — а ещё так часто выглядят **трекеры-метки** и умные датчики, у которых в эфир уходит только адрес.

## Шаг 3: подключаемся и читаем GATT

Выберем телефон и попросим подробности о нём:

```
$ bluetoothctl info 3C:38:24:D6:FA:29
Device 3C:38:24:D6:FA:29 (public)
	Name: Redmi Note 14 Pro
	Class: 0x005a020c (5898764)
	Icon: phone
	Paired: no
	Bonded: no
	Trusted: no
	Connected: no
	RSSI: 0xffffffb4 (-76)
```

Полезных полей здесь несколько. `Class` — класс устройства (`0x005a020c` — смартфон). `Paired: no` и `Bonded: no` — устройство не спарено с нами. `RSSI` (Received Signal Strength Indicator) — уровень сигнала; значение `-76` дБм означает «умеренно далеко», примерно несколько метров с препятствиями. RSSI полезен для грубой оценки расстояния: если ты видишь чужой трекер с RSSI около нуля, он лежит рядом.

Дальше — самое интересное: подключение и перечисление GATT. Это делается так:

```
$ bluetoothctl
[bluetooth]# connect 3C:38:24:D6:FA:29
[Redmi Note 14 Pro]# menu gatt
[Redmi Note 14 Pro]# list-attributes
```

`list-attributes` выводит сервисы, характеристики и дескрипторы с их UUID и «ручками» (handle) — числовыми адресами внутри соединения. Читать и писать значения можно по этим handle. Мы намеренно не подключаемся к чужому телефону — это было бы неэтично; сама механика от этого не меняется.

## Шаг 4: спаривание и bonding

Прежде чем писать команды, устройства обычно **спариваются** — обмениваются ключами шифрования. Если после этого ключи сохраняются, это **bonding**: при повторном соединении канал шифруется автоматически. У BLE несколько режимов:

- **Just Works** — без аутентификации. Самый удобный и самый опасный: стороны не доказывают, кто они, поэтому возможна атака «человек посередине» (MITM).
- **Passkey / PIN** — сравнение или ввод кода на обоих устройствах.
- **OOB (Out Of Band)** — обмен ключами по другому каналу, например через NFC.
- **LESC (LE Secure Connections)** — обмен по эллиптической криптографии с защитой от MITM.

Слабое место: разработчики часто выбирают Just Works «чтобы не усложнять», а потом всё равно шлют по каналу чувствительные команды. Тогда любой рядом стоящий может подключиться и повторить команду.

## Шаг 5: смотрим на ту же тему из приложения

Теперь сторона приложения. Разберём `fdroid.apk` — у клиента F-Droid есть обмен по Bluetooth. Декодируем манифест и выпишем Bluetooth-разрешения:

```
$ java -jar apktool.jar d fdroid.apk -o fd
$ grep -oE 'android.permission.BLUETOOTH[A-Z_]*' fd/AndroidManifest.xml | sort -u
android.permission.BLUETOOTH
android.permission.BLUETOOTH_ADMIN
android.permission.BLUETOOTH_ADVERTISE
android.permission.BLUETOOTH_CONNECT
android.permission.BLUETOOTH_SCAN
```

Разберём их: `BLUETOOTH` и `BLUETOOTH_ADMIN` — старые разрешения на работу с адаптером; `BLUETOOTH_SCAN` — сканирование; `BLUETOOTH_CONNECT` — подключение к устройствам; `BLUETOOTH_ADVERTISE` — **реклама**, то есть устройство само может объявлять о себе как периферия. Последнее особенно интересно: приложение, которое умеет и сканировать, и рекламировать, может эмулировать устройство.

## Шаг 6: перехват трафика

Пассивно перехватить BLE-трафик можно аппаратным сниффером (nRF Sniffer, Ubertooth) или, если тестируешь своё Android-устройство, встроенным **HCI snoop log**. Второй вариант включается в настройках разработчика, после чего весь HCI-трафик пишется в файл:

```
# в developer options включаем Bluetooth HCI snoop log
$ adb bugreport bugreport.zip
$ unzip bugreport.zip
$ tshark -r btsnoop_hci.log | head
```

В Wireshark тот же файл фильтруется по `btatt` (обмен GATT) и `btle` (реклама). Если соединение не зашифровано, команды видны в открытом виде — например, запись `01` в характеристику `fff1` означает «открыть». Если канал защищён LESC, в захвате будет шифротекст, и тогда либо ловят момент спаривания, либо ищут ключ в прошивке или в самом APK.

## Что мы теперь знаем

1. BLE связывает **central** (телефон) и **peripheral** (устройство) через иерархию GATT: сервисы → характеристики → дескрипторы, каждый со своим UUID.
2. Адаптер виден командой `bluetoothctl show`, эфир — командой `scan on`, подробности об устройстве — `info`.
3. RSSI показывает уровень сигнала (грубо — расстояние), `Paired`/`Bonded` — статус спаривания.
4. Режим **Just Works** не аутентифицирует стороны, поэтому уязвим к MITM.
5. Со стороны приложения смотрят Bluetooth-разрешения: `SCAN`, `CONNECT`, `ADVERTISE`.
6. Трафик перехватывают сниффером или HCI snoop log; незашифрованные команды видны в открытом виде.
