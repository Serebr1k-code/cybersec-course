## Вопрос, с которого всё начинается

Приложение шлёт на `/graphql` один POST с телом вида `{"query":"..."}`. В отличие от REST, здесь
нет отдельных эндпоинтов — есть один, и вся структура данных описана в **схеме**. Как узнать,
что вообще можно запросить, и где авторизация «забыта»?

## Наш пример: один эндпоинт

Перехваченный запрос:

```bash
$ cat req.txt
POST /graphql
{"query":"{ me { id name } }"}
```

Один эндпоинт, тело — GraphQL-запрос. Весь урок ведём его.

## Шаг 1: что такое GraphQL

**GraphQL** — язык запросов к API. Вместо множества URL есть одна точка входа и **схема**,
описывающая типы и поля. Клиент сам указывает, какие поля ему нужны. Плюс для разработки —
один запрос вместо десяти; риск для безопасности — одна точка, из которой видно всё.

## Шаг 2: интроспекция

GraphQL умеет рассказать о себе: специальный запрос `__schema` возвращает всю схему. Если
интроспекция открыта, мы получаем карту API:

```bash
$ curl -s -X POST https://api.example.com/graphql -H 'Content-Type: application/json' \
  -d '{"query":"{__schema{types{name fields{name}}}}"}' | head -c 300
{"data":{"__schema":{"types":[{"name":"User","fields":[{"name":"id"},{"name":"email"},...
```

Интроспекция — первый шаг пентеста GraphQL. В продакшене её часто оставляют открытой, и это
сама по себе находка (раскрытие схемы).

## Шаг 3: собираем список полей

Из схемы выписываем интересное: `User.email`, `User.role`, `Admin.*`, мутации (`mutation`).

```bash
$ grep -oE '"[a-zA-Z_]+"' graphql_schema.txt | sort -u | head
```

Поля `role`, `email`, `token` — кандидаты на проверку авторизации.

## Шаг 4: авторизация на уровне полей

Ключевая ошибка GraphQL — проверка авторизации на **эндпоинте**, а не на **поле**. Запрос
`me` разрешён, но если вложить в него поле другого пользователя, сервер может отдать его без
проверки:

```graphql
{ user(id: 2) { email role } }
```

Если `user(id: 2)` отдаёт данные чужого пользователя — это BOLA/IDOR, только через GraphQL.

## Шаг 5: вложенность и «прыжки» по графу

GraphQL позволяет ходить по связям: `me { friends { posts { comments { author { email } } } } }`.
Один запрос может вытащить данные, до которых в REST пришлось бы идти отдельными проверками.
Часто проверка стоит на верхнем уровне, а вложенные поля отдаются без неё.

## Шаг 6: мутации и массовые операции

Кроме чтения (`query`), GraphQL умеет писать (`mutation`). Проверяем: можно ли изменить чужой
объект, обойти лимиты, выполнить mass-assignment. Иногда одна мутация `updateUser` принимает
произвольные поля — включая `role`.

```graphql
mutation { updateUser(id: 1, role: "admin") { id role } }
```

## Шаг 7: обход лимитов и «тяжёлые» запросы

GraphQL не ограничивает вложенность сам по себе. Запрос с рекурсией или множеством алиасов
кладёт сервер (DoS) или обходит rate-limit. Проверяют, есть ли лимит глубины и стоимости
запроса.

## Шаг 8: как искать GraphQL-эндпоинты

Обычные адреса: `/graphql`, `/api/graphql`, `/v1/graphql`, `/query`. Признак — ответ на
`{"query":"{__typename}"}`. Иногда интроспекция отключена, но ошибки всё равно раскрывают
имена полей.

## Шаг 9: как защищают правильно

Правильная защита: отключить интроспекцию в продакшене, проверять авторизацию на **каждом**
поле/резолвере, ограничивать глубину и стоимость запроса, валидировать входы мутаций
(allowlist полей), логировать аномальные запросы. GraphQL не «безопаснее» REST — он требует
тех же проверок, только в другом месте.

## Что мы теперь знаем

- GraphQL — один эндпоинт и схема.
- Интроспекция раскрывает всю схему — это находка.
- Авторизацию надо проверять на каждом поле, а не на эндпоинте.
- Вложенные запросы вытягивают данные через «прыжки» по графу.
- Мутации могут допускать mass-assignment; нужны лимиты глубины.
