## Вопрос, с которого всё начинается

Приложение шлёт на `/graphql` один POST с телом вида `{"query":"..."}`. В отличие от REST, здесь
нет отдельных эндпоинтов — есть один, и вся структура данных описана в **схеме**. Как узнать,
что вообще можно запросить, и где авторизация «забыта»?

## Наш пример: один эндпоинт

Перехваченный запрос:

```bash
$ cat req.txt
POST /graphql
{"query":"{ me { id name } }"}
```

Один эндпоинт, тело — GraphQL-запрос. Весь урок ведём его.

## Шаг 1: что такое GraphQL

**GraphQL** — язык запросов к API. Вместо множества URL есть одна точка входа и **схема**,
описывающая типы и поля. Клиент сам указывает, какие поля ему нужны. Плюс для разработки —
один запрос вместо десяти; риск для безопасности — одна точка, из которой видно всё.

## Шаг 2: интроспекция

GraphQL умеет рассказать о себе: специальный запрос `__schema` возвращает всю схему. Если
интроспекция открыта, мы получаем карту API:

```bash
$ curl -s -X POST https://api.example.com/graphql -H 'Content-Type: application/json' \
  -d '{"query":"{__schema{types{name fields{name}}}}"}' | head -c 300
{"data":{"__schema":{"types":[{"name":"User","fields":[{"name":"id"},{"name":"email"},...
```

Интроспекция — первый шаг пентеста GraphQL. В продакшене её часто оставляют открытой, и это
сама по себе находка (раскрытие схемы).

## Шаг 3: собираем список полей

Из схемы выписываем интересное: `User.email`, `User.role`, `Admin.*`, мутации (`mutation`).

```bash
$ grep -oE '"[a-zA-Z_]+"' graphql_schema.txt | sort -u | head
```

Поля `role`, `email`, `token` — кандидаты на проверку авторизации.

## Шаг 4: авторизация на уровне полей

Ключевая ошибка GraphQL — проверка авторизации на **эндпоинте**, а не на **поле**. Запрос
`me` разрешён, но если вложить в него поле другого пользователя, сервер может отдать его без
проверки:

```graphql
{ user(id: 2) { email role } }
```

Если `user(id: 2)` отдаёт данные чужого пользователя — это BOLA/IDOR, только через GraphQL.

## Шаг 5: вложенность и «прыжки» по графу

GraphQL позволяет ходить по связям: `me { friends { posts { comments { author { email } } } } }`.
Один запрос может вытащить данные, до которых в REST пришлось бы идти отдельными проверками.
Часто проверка стоит на верхнем уровне, а вложенные поля отдаются без неё.

## Шаг 6: мутации и массовые операции

Кроме чтения (`query`), GraphQL умеет писать (`mutation`). Проверяем: можно ли изменить чужой
объект, обойти лимиты, выполнить mass-assignment. Иногда одна мутация `updateUser` принимает
произвольные поля — включая `role`.

```graphql
mutation { updateUser(id: 1, role: "admin") { id role } }
```

## Шаг 7: обход лимитов и «тяжёлые» запросы

GraphQL не ограничивает вложенность сам по себе. Запрос с рекурсией или множеством алиасов
кладёт сервер (DoS) или обходит rate-limit. Проверяют, есть ли лимит глубины и стоимости
запроса.

## Шаг 8: как искать GraphQL-эндпоинты

Обычные адреса: `/graphql`, `/api/graphql`, `/v1/graphql`, `/query`. Признак — ответ на
`{"query":"{__typename}"}`. Иногда интроспекция отключена, но ошибки всё равно раскрывают
имена полей.

## Шаг 9: как защищают правильно

Правильная защита: отключить интроспекцию в продакшене, проверять авторизацию на **каждом**
поле/резолвере, ограничивать глубину и стоимость запроса, валидировать входы мутаций
(allowlist полей), логировать аномальные запросы. GraphQL не «безопаснее» REST — он требует
тех же проверок, только в другом месте.

## Шаг 9: batching и алиасы

GraphQL позволяет отправить **несколько операций** в одном запросе (batching) и использовать
**алиасы** — несколько копий одного поля под разными именами:

```graphql
{ a: user(id: 1) { email } b: user(id: 2) { email } c: user(id: 3) { email } }
```

Один запрос тянет данные многих объектов. Это удобно для атакующего и опасно для сервера: если
нет лимита стоимости, перебор ID идёт пачками. Проверяют, ограничено ли число операций и
алиасов.

## Шаг 10: persisted queries

Некоторые серверы принимают только **persisted queries** — заранее сохранённые хэши запросов.
Тогда произвольный запрос отправить нельзя, и интроспекция обычно закрыта. Проверяют, можно ли
выполнить свой запрос (признак — сервер принимает текст `query`, а не только хэш). Если
принимает — persisted-режим не enforced.

## Шаг 11: лимиты глубины и стоимости

Стандартная защита — ограничение **глубины** (сколько уровней вложенности) и **стоимости**
(сколько «весит» запрос). Без них рекурсивный или широкий запрос кладёт сервер. Проверяют
экспериментально: постепенно увеличивай вложенность и смотри, где сервер отказывает. Если
отказа нет — находка (DoS-риск).

## Шаг 12: инструменты

Для работы с GraphQL удобны специализированные клиенты (GraphiQL, Altair) и перехват прокси.
Полезно: выгрузить схему в файл и искать по ней поля `admin`, `token`, `email`, мутации
`delete*`, `update*`. Схема — это карта, по которой дальше идёт проверка авторизации.

## Если не сработало

Если интроспекция закрыта, попробуй достать имена полей из ошибок: неверный запрос часто
возвращает подсказку «Did you mean ...». Если сервер требует persisted queries — ищи, может ли
клиент запросить произвольный хэш или есть эндпоинт для их регистрации. И помни: даже закрытая
интроспекция не означает закрытую авторизацию — проверяй поля точечно.
## Полный прогон: от интроспекции до чужих данных

**Шаг A.** Проверяем интроспекцию:

```bash
$ curl -s -X POST https://api.example.com/graphql -H 'Content-Type: application/json' \
  -d '{"query":"{__typename}"}'
{"data":{"__typename":"Query"}}
```

**Шаг B.** Выгружаем схему запросом `__schema` и ищем поля `email`, `role`, `token`.

**Шаг C.** Проверяем авторизацию на уровне полей:

```graphql
{ user(id: 2) { email role } }
```

Если отдаёт данные чужого пользователя — BOLA.

**Шаг D.** Проверяем вложенность и мутации: можно ли изменить чужой объект или подставить
`role: admin`.

**Шаг E.** Проверяем лимит глубины: рекурсивный запрос не должен класть сервер.

## Частые ошибки

- Считать, что «GraphQL сложный, значит безопасный».
- Проверять авторизацию только на верхнем уровне запроса.
- Не тестировать мутации, ограничившись чтением.
- Не проверять лимиты глубины и стоимости.
## Как это устроено внутри

GraphQL устроен как **граф**: типы связаны полями, и запрос — это обход графа. Именно поэтому
модель угроз отличается от REST. В REST каждый эндпоинт — отдельная дверь, и её можно охранять
отдельно. В GraphQL дверь одна, а «комнаты» — это поля и резолверы. Если проверять авторизацию
на двери, но не в комнатах, любой запрос дойдёт до данных, до которых в REST было бы не
добраться.

Отсюда три свойства, важные для пентеста. Первое — **интроспекция**: схема рассказывает о
себе сама, если её не выключить. Второе — **вложенность**: один запрос может пройти по связям
на много уровней, минуя проверки, расставленные на верхнем уровне. Третье — **стоимость**:
глубокий или широкий запрос нагружает сервер, и без лимита это DoS.

Правильная защита отражает эту структуру: интроспекция выключена в проде, авторизация
проверяется в каждом резолвере, входы мутаций валидируются по allowlist, а глубина и стоимость
запроса ограничены. То есть GraphQL требует не меньше дисциплины, чем REST, а больше — потому
что одна точка входа скрывает множество путей.
## Типичный сценарий на реальном устройстве

Ты перехватываешь запрос приложения к `/graphql`. Отправляешь `{"query":"{__typename}"}` —
сервер отвечает, значит, GraphQL есть. Запрашиваешь `__schema` и получаешь полную схему: типы
`User`, `Order`, `Admin` и их поля. Видишь поле `Admin.token`. Пробуешь запросить его от
обычного пользователя — и получаешь токен, потому что авторизация стоит на верхнем уровне
запроса, а не на поле.

Дальше ты проверяешь вложенность: запрашиваешь `orders { user { email } }` и получаешь данные
чужих заказов. Это уже BOLA через граф. В отчёт идут три отдельные находки: открытая
интроспекция, отсутствие авторизации на полях, отсутствие лимита глубины. Каждая имеет свою
рекомендацию. Такой аудит показывает, что GraphQL — не «сложный REST», а другая модель
доступа, и проверять её надо по графу, а не по эндпоинтам.
## Что важно не перепутать

Не путай **интроспекцию** и **доступ к данным**: открытая схема — это раскрытие структуры, но
ещё не утечка; утечка появляется, когда нет авторизации на полях. Не путай **проверку на
эндпоинте** и **проверку в резолвере**: первая не защищает вложенные поля. И не путай
**глубину** запроса с его **стоимостью**: глубокий запрос может быть дешёвым, а широкий — дорогим;
лимиты нужны оба. В отчёте разделяй находки: «интроспекция открыта», «нет авторизации на поле
`Admin.token`», «нет лимита глубины» — это три разные проблемы с тремя разными рекомендациями.
Смешивать их в одну — значит терять точность, из-за которой разработчик не поймёт, что чинить.
## Итоговая мысль

GraphQL — это не «сложный REST», а другая модель доступа: один вход и граф полей. Поэтому
проверять его надо по графу — интроспекция, авторизация каждого поля, вложенность, лимиты
стоимости. Ошибка на любом уровне открывает данные, до которых в REST было бы не добраться.
Точные, раздельные находки по каждому уровню — то, что отличает полезный отчёт от общего
предупреждения «GraphQL может быть опасен».
## Что мы теперь знаем

- GraphQL — один эндпоинт и схема.
- Интроспекция раскрывает всю схему — это находка.
- Авторизацию надо проверять на каждом поле, а не на эндпоинте.
- Вложенные запросы вытягивают данные через «прыжки» по графу.
- Мутации могут допускать mass-assignment; нужны лимиты глубины.
