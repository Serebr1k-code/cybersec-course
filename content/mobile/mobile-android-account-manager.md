## Вопрос, с которого всё начинается

Приложение хранит логин пользователя и «не спрашивает пароль заново» — оно берёт токен у системы.
За это отвечает `AccountManager`. Но если токен может получить любое приложение, вся схема рушится.
Как это работает и где ломается?

## Наш пример: аккаунт и токен

Код приложения добавляет аккаунт:

```java
Account account = new Account("user@example.com", "com.example");
AccountManager am = AccountManager.get(this);
am.addAccountExplicitly(account, password, null);
am.setAuthToken(account, "full_access", token);
```

`AccountManager` — системный сервис, который хранит список аккаунтов устройства и связанные с ними
токены. Дальше любое приложение может спросить: «дай мне токен для аккаунта типа
`com.example`».

## Шаг 1: что такое account type и authenticator

**Account type** — строка вида `com.example` (обычно обратный домен). С ней связан
**Authenticator** — компонент, который умеет проверять логин/пароль и выдавать токены. Всё вместе
даёт систему единого входа: приложение хранит аккаунт, а токен можно переиспользовать.

## Шаг 2: как выдаётся токен

```java
Bundle result = am.getAuthToken(account, "full_access", null, activity, callback, null);
```

`getAuthToken` возвращает токен в callback. Ключевой вопрос: проверяет ли `Authenticator`
**вызывающего**? Если нет — токен получит любое приложение, зная account type. Это и есть уязвимость.

## Шаг 3: утечка токена

Сценарий: приложение регистрирует account type и хранит `full_access`-токен. Атакующее приложение
знает тип и вызывает `getAuthToken` от своего имени. Если аутентификатор не проверяет подпись
вызывающего (`checkSignature`), токен уходит атакующему. Далее — доступ к API от имени
пользователя.

```bash
$ adb shell am start -n com.evil/.StealActivity
# внутри — getAuthToken(account, "full_access", ...)
```

## Шаг 4: подмена account type

Второй вектор — **account type spoofing**. Атакующий регистрирует свой аутентификатор на чужой
account type (если система позволяет), и тогда именно его код вызывается при запросе токена. Он
возвращает жертве «свой» токен или забирает введённый пароль. На современных Android регистрация
аутентификатора на существующий тип ограничена, но на старых версиях это работало.

## Шаг 5: где ещё текут данные

- `addAccountExplicitly` сохраняет пароль, если передать его третьим аргументом.
- `peekAuthToken` возвращает токен без запроса к серверу.
- Кастомные `AccountManagerCallback` могут логировать токены.
- Токены попадают в `dumpsys account`.

## Шаг 6: аудит

```bash
$ adb shell dumpsys account | grep -A4 'com.example'
  Accounts: 1
    Account {name=user@example.com, type=com.example}
      authToken: full_access
```

Если `dumpsys account` показывает токены, значит они лежат в системе и потенциально доступны.
Дальше проверяем аутентификатор: есть ли проверка вызывающего перед выдачей.

## Шаг 7: защита

- Проверять подпись вызывающего в `Authenticator.getAuthToken`.
- Не хранить пароль в AccountManager.
- Использовать короткоживущие токены и обновлять их.
- Ограничивать типы токенов и не выдавать `full_access` без нужды.

## Что мы теперь знаем

- AccountManager хранит аккаунты и токены.
- `getAuthToken` без проверки вызывающего = утечка.
- Account type spoofing подменяет аутентификатор.
- Аудит: `dumpsys account`, проверка аутентификатора.
- Защита: проверка подписи, короткие токены, без паролей.

## Шаг 8: как устроен Authenticator

`Authenticator` — это сервис, наследующий `AbstractAccountAuthenticator`, плюс `Service`, который
его отдаёт по `BIND_AUTHENTICATOR`. Метод `getAuthToken` получает `AccountAuthenticatorResponse`
и должен либо вернуть токен, либо запросить у пользователя пароль. Ключевая проверка — в начале
метода: узнать, кто вызвал (`Binder.getCallingUid()`), и сравнить подпись с ожидаемой. Без этой
проверки любой `getAuthToken` с нужным account type получит токен. Именно эту проверку ищут в
аудите.

## Шаг 9: как проверить вызывающего

Стандартный приём — `PackageManager.checkSignatures(callingUid, myUid)`. Если результат не
`SIGNATURE_MATCH`, запрос отклоняется. Некоторые реализации вместо этого проверяют имя пакета —
это ненадёжно, имя можно подделать. Другие полагаются на `android:permission` у сервиса
аутентификатора — но тогда важно, чтобы разрешение было `signature`. В отчёте полезно показать,
что именно проверяется (или не проверяется) в `getAuthToken`.

## Шаг 10: реальный кейс

Находка из bug bounty: приложение-мессенджер регистрировало account type и хранило токен
`full_access`. Аутентификатор не проверял вызывающего, поэтому вспомогательное приложение могло
вызвать `getAuthToken` и получить доступ к API мессенджера — читать сообщения и отправлять их от
имени пользователя. Уязвимость классифицировали как high, потому что давала полноценный доступ к
аккаунту без пароля.

## Шаг 11: чек-лист

- Какие account type зарегистрированы.
- Проверяет ли `getAuthToken` подпись вызывающего.
- Какие токены выдаются и как долго живут.
- Не хранится ли пароль в AccountManager.
- Что попадает в `dumpsys account`.

## Частые вопросы

**Всегда ли AccountManager хранит пароль?** Нет, пароль сохраняется только если его явно передали
в `addAccountExplicitly`; лучше этого не делать.

**Можно ли обойтись без AccountManager?** Да, можно хранить токены в KeyStore, но тогда теряется
единый вход между приложениями вендора.

**Что важнее — проверка пакета или подписи?** Подписи. Имя пакета подделывается, подпись — нет.

## Шаг 12: AccountManager против KeyStore

Хранение токенов в AccountManager удобно для единого входа, но у него есть слабое место: токены
лежат в системной базе и доступны по account type. Более безопасный путь — Android Keystore:
ключ генерируется в аппаратном хранилище и не покидает его, а токен можно шифровать ключом,
который нельзя экспортировать. В аудите стоит проверять, не лежат ли долгоживущие токены в
AccountManager там, где можно было использовать Keystore. Для крипто-темы смотрите
`mobile-keystore` и `mobile-android-crypto-deep`.

## Шаг 13: жизненный цикл токена

Хорошая практика — короткоживущий access-токен плюс refresh-токен, хранимый в Keystore.
Плохая практика — один долгоживущий `full_access`-токен, который не отзывается. В аудите
проверяйте: сколько живёт токен, можно ли его отозвать, обновляется ли он, и что произойдёт,
если его украдут. Долгоживущий токен без отзыва превращает любую утечку в постоянный доступ.

## Шаг 14: `dumpsys account` и что он показывает

```bash
$ adb shell dumpsys account
  Accounts: 2
    Account {name=user@example.com, type=com.example}
      authToken: full_access (present)
    Account {name=user@gmail.com, type=com.google}
```

Наличие токена в дампе не всегда означает, что его получит любое приложение, — но это первый
признак, что стоит проверить аутентификатор. Если приложение хранит токен, а `getAuthToken` не
проверяет вызывающего, цепочка «дамп → запрос → доступ» становится реальной.

## Шаг 15: реальный кейс и рекомендации

Кейс из практики: корпоративное приложение регистрировало account type и хранило
`full_access`-токен к внутреннему API. Аутентификатор проверял только имя пакета, а не подпись.
Вспомогательное приложение с тем же именем пакета в другом магазине получало токен и доступ к
корпоративным данным. Рекомендации: проверять подпись (`checkSignatures`), использовать
короткоживущие токены, хранить refresh-токен в Keystore, не возвращать `full_access` без
необходимости и логировать выдачу токенов.

## Частые вопросы

**Хранит ли AccountManager пароль?** Только если вы передали его в `addAccountExplicitly`.

**Проверка пакета надёжна?** Нет, имя пакета подделывается; нужна проверка подписи.

**Где искать токены?** В `dumpsys account` и в коде вокруг `getAuthToken`/`peekAuthToken`.

**Можно ли обойтись без AccountManager?** Да — KeyStore + собственное хранилище, но без единого входа.

## Шаг 16: AccountManager и OAuth на Android

На практике AccountManager часто используют как хранилище для OAuth-токенов: приложение получает
токен через Custom Tabs/AppAuth, а затем кладёт его в аккаунт. Проблема в том, что хранение в
AccountManager делает токен доступным по account type, если аутентификатор не проверяет
вызывающего. Более безопасный вариант — держать токен в памяти/KeyStore, а в AccountManager
хранить только метаданные аккаунта. В аудите смотрите, что именно кладётся в аккаунт: если
долгоживущий refresh-токен — риск выше.

## Шаг 17: как проверить проверку вызывающего

В коде аутентификатора ищите начало `getAuthToken`:

```java
public Bundle getAuthToken(AccountAuthenticatorResponse r, Account a,
        String authTokenType, Bundle options) {
    if (PackageManager.checkSignatures(Binder.getCallingUid(), Process.myUid())
            != PackageManager.SIGNATURE_MATCH) {
        // отклонить
    }
}
```

Если этой проверки нет — токен может получить любое приложение, знающее account type. Это и есть
ядро находки. В отчёте приводите метод и строку без проверки.

## Шаг 18: реальный кейс и рекомендации

Кейс: приложение-банк хранило `full_access`-токен в AccountManager, а аутентификатор проверял
только имя пакета. Вспомогательное приложение из стороннего магазина с тем же именем получало
токен и доступ к счетам. Рекомендации: проверять подпись (`checkSignatures`), не хранить
`full_access` без нужды, использовать короткоживущие токены, хранить refresh-токен в Keystore,
логировать выдачу и предусмотреть отзыв.

## Частые вопросы

**Можно ли подделать проверку по имени пакета?** Да, имя пакета не уникально между магазинами.

**Что надёжнее — permission или checkSignatures?** Оба хороши, если разрешение объявлено как
signature; checkSignatures работает и без объявления разрешения.

**Как быстро найти проблему?** Откройте `getAuthToken` и посмотрите, проверяется ли вызывающий.

## Шаг 19: итог

AccountManager — удобное, но опасное хранилище токенов. Всё решает проверка вызывающего в
аутентификаторе: с ней схема безопасна, без неё — любой получает доступ к аккаунту. Проверяйте
`getAuthToken`, объём выдаваемых прав и срок жизни токенов. На этом блок фонового выполнения
закончен.

Помните: аккаунт без проверки вызывающего — это открытая дверь к API от имени пользователя.
Проверяйте не только наличие проверки, но и её качество: подпись надёжнее имени пакета, а
короткий токен безопаснее долгоживущего `full_access`.
