## Вопрос, с которого всё начинается

Приложение обращается к серверу, но в прокси вместо привычных JSON-запросов — поток непонятных
бинарных байт с заголовком `content-type: application/grpc`. Прочитать тело глазами не выходит.
Это **gRPC** — бинарный RPC. Разберём, как его читать и подменять.

## Наш пример: запрос, который не читается

Ловим трафик приложения и видим:

```http
POST /bank.BankService/GetBalance HTTP/2
content-type: application/grpc
te: trailers

<бинарные байты>
```

Путь `/bank.BankService/GetBalance` — это имя сервиса и метода. Тело — **Protocol Buffers**,
бинарный формат сериализации. Чтобы читать такие запросы, нужна схема (`.proto`) и инструмент.
Весь урок мы будем вести этот вызов `GetBalance` — от сырых байтов до подменённого ответа.

## Шаг 1: что такое gRPC

**gRPC** — фреймворк удалённого вызова процедур: клиент вызывает метод на сервере так, будто он
локальный. Транспорт — HTTP/2, формат сообщений — Protocol Buffers. Сервер и клиент договариваются
о схеме в файле `.proto`. В отличие от REST с JSON, тут нет человекочитаемого текста: всё
бинарное и компактное. Это удобно разработчикам (меньше трафика, строгие типы) и неудобно
пентестеру (нельзя просто прочитать тело).

## Шаг 2: откуда взять схему

Схема либо лежит в приложении как ресурс, либо встроена в нативный код. Ищем `.proto` и
сгенерированные классы:

```bash
$ unzip -l app.apk | grep -iE 'proto|grpc'
   18442  assets/bank_service.proto
  102344  classes.dex
```

Если `.proto` в ассетах — отлично, у нас есть имена сообщений и полей. Если нет — восстанавливаем
по именам в `classes.dex`:

```bash
$ grep -a -o 'bank\.BankService[a-zA-Z]*' classes.dex | sort -u
bank.BankService
bank.BankServiceGrpc
```

## Шаг 3: чтение вызова

Ставим прокси с поддержкой gRPC (например, `mitmproxy` с плагином или `grpcurl` для ручного
вызова). Для `mitmproxy` схема подгружается, и вызовы раскрываются в читаемый вид:

```bash
$ grpcurl -plaintext -d '{"account":"123"}' bank.example:443 bank.BankService/GetBalance
{
  "balance": "1000.00"
}
```

Теперь вместо байтов видим поля. Это и есть цель: превратить бинарный вызов в понятный. Обратите
внимание, что имя метода в пути (`bank.BankService/GetBalance`) — уже половина информации: оно
говорит, что именно делает вызов.

## Шаг 4: подмена сообщения

Когда вызов читаем, можно менять параметры: подставлять чужой `account`, менять сумму, добавлять
недостающие поля. Через прокси это делается модификацией тела, через `grpcurl` — просто новым
запросом. Часто именно здесь находится IDOR: сервер доверяет `account` из запроса, а не берёт его
из сессии.

```bash
$ grpcurl -plaintext -d '{"account":"999"}' bank.example:443 bank.BankService/GetBalance
{
  "balance": "250000.00"
}
```

Если на чужой `account` вернулся чужой баланс — это уже подтверждённый IDOR.

## Шаг 5: реверс схемы без .proto

Если схемы нет, поля восстанавливают по «проволочному» формату Protobuf: каждое поле — это тег
(номер) и тип. Дамп байтов плюс перебор тегов дают структуру. Инструменты `protobuf-inspector`
и плагины для Burp помогают сопоставить теги со значениями. Числовые теги стабильны между
версиями, поэтому восстановленная схема переносится на другие методы сервиса.

## Шаг 6: потоковые вызовы

gRPC поддерживает не только «запрос-ответ», но и потоки: серверный streaming (сервер шлёт много
ответов), клиентский и двунаправленный. Это важно для чатов, торгов, телеметрии. В прокси потоковый
вызов выглядит как несколько сообщений в одном HTTP/2-стриме. Читать их нужно по кадрам: каждое
сообщение предваряется 5-байтовым заголовком (сжатие + длина). Инструменты с поддержкой gRPC
разбирают это автоматически.

## Шаг 7: метаданные и аутентификация

Кроме тела, у gRPC есть **метаданные** — аналог HTTP-заголовков. Туда кладут токены:

```bash
$ grpcurl -plaintext -H 'authorization: Bearer eyJ...' -d '{}' \
    bank.example:443 bank.BankService/GetBalance
```

Проверьте: не принимает ли сервер запрос без метаданных, не доверяет ли заголовку, который легко
подделать, не отдаёт ли лишние поля. Частая находка — сервер проверяет токен, но не проверяет
права на конкретный объект.

## Шаг 8: защита и что смотреть

gRPC сам по себе не защищает от подмены параметров — вся логика на сервере. На что смотреть:
проверяет ли сервер права на объект (не только аутентификацию), валидирует ли вход, не отдаёт ли
лишние поля. На клиенте — доверяет ли он ответу без проверки.

## Частые вопросы

**Обязательно ли нужна схема?** Для комфортного чтения — да. Без неё можно подменять сырые байты,
но сложнее понимать смысл полей.

**Чем gRPC лучше REST для атакующего?** Ничем «лучше» — он просто другой. Но из-за бинарности многие
пентестеры пропускают gRPC-эндпоинты, и там чаще остаются незакрытые IDOR.

**Что такое trailers?** Дополнительные метаданные в конце потока; в них gRPC передаёт статус.

## Шаг 9: потоковые вызовы подробнее

В gRPC четыре режима: unary (один запрос — один ответ), server streaming (один запрос — поток
ответов), client streaming (поток запросов — один ответ) и bidirectional (оба потока). В дампе
каждое сообщение предваряется 5-байтовым префиксом: флаг сжатия и длина. Зная это, можно вручную
разрезать тело на сообщения:

```bash
$ xxd -l 16 body.bin
00000000: 00 00 00 00 1a 0a 06 31 32 33 31 32 33 ...
```

Первый байт `00` — без сжатия, следующие четыре — длина (0x1a = 26 байт). Дальше идёт Protobuf.
Инструменты разбирают это автоматически, но понимание формата помогает, когда автоматика молчит.

## Шаг 10: сравнение gRPC и REST

REST обычно отдаёт JSON по HTTP/1.1 и читается глазами. gRPC компактнее, строже типизирован и
быстрее, но непрозрачен. Для атакующего разница в том, что многие сканеры ищут только JSON-эндпоинты
и пропускают gRPC. Поэтому gRPC-методы чаще остаются без проверки авторизации — и это первое, что
стоит тестировать.

## Шаг 11: как инструменты раскрывают gRPC

`mitmproxy` с gRPC-аддоном и схемой показывает вызовы как структурированные сообщения. Burp с
плагином умеет редактировать отдельные поля. `grpcurl` работает и как сканер: с флагом `-list` он
перечисляет методы сервиса, если включена reflection:

```bash
$ grpcurl -plaintext bank.example:443 list
bank.BankService
grpc.reflection.v1alpha.ServerReflection
$ grpcurl -plaintext bank.example:443 list bank.BankService
bank.BankService.GetBalance
bank.BankService.Transfer
```

Включённая reflection — сама по себе находка: она отдаёт схему сервиса любому.

## Мини-практика

Возьмите APK с gRPC и выполните `grep -a -o '[a-z]*\.[A-Z][a-zA-Z]*Service' classes.dex | sort -u`.
Вы получите имена сервисов. Затем попробуйте `grpcurl -plaintext -list <host>:443` против тестового
стенда. Если reflection включена — вы увидите все методы без всякой схемы.

## Шаг 12: тестирование авторизации в gRPC

Основная работа с gRPC — не чтение, а проверка прав. Составьте список методов (`grpcurl list`),
затем для каждого вызовите его с токеном низкопривилегированного пользователя, а параметры
подставьте чужие. Проверьте три вещи: принимает ли сервер вызов без токена, отдаёт ли данные по
чужому идентификатору, и можно ли через один метод дотянуться до объектов другого тенанта. Часто
именно gRPC-методы остаются без проверки, потому что их не видно в обычных сканерах.

## Шаг 13: частые ошибки новичков

Первая ошибка — считать, что «бинарное = защищённое». Protobuf не шифрует, он лишь компактно
сериализует. Вторая — забывать про метаданные: токен может лежать не в теле, а в заголовке, и его
тоже можно подделать. Третья — не проверять reflection: если сервер её включил, схема доступна
любому, и восстановление `.proto` становится ненужным. Четвёртая — путать код ответа: gRPC передаёт
статус в trailers, а не в HTTP-коде, поэтому «200 OK» ничего не значит.

## Что мы теперь знаем

- gRPC — RPC поверх HTTP/2 с бинарными сообщениями Protobuf.
- Схема `.proto` позволяет читать вызовы.
- Инструменты с поддержкой gRPC раскрывают тело в поля.
- Подмена параметров — типовой источник IDOR.
- Без схемы структуру восстанавливают по тегам.
