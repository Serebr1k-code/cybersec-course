## Вопрос, с которого всё начинается

Приложение обращается к серверу, но в прокси вместо привычных JSON-запросов — поток непонятных
бинарных байт с заголовком `content-type: application/grpc`. Прочитать тело глазами не выходит.
Это **gRPC** — бинарный RPC. Разберём, как его читать и подменять.

## Наш пример: запрос, который не читается

Ловим трафик приложения и видим:

```http
POST /bank.BankService/GetBalance HTTP/2
content-type: application/grpc
te: trailers

<бинарные байты>
```

Путь `/bank.BankService/GetBalance` — это имя сервиса и метода. Тело — **Protocol Buffers**,
бинарный формат сериализации. Чтобы читать такие запросы, нужна схема (`.proto`) и инструмент.

## Шаг 1: что такое gRPC

**gRPC** — фреймворк удалённого вызова процедур: клиент вызывает метод на сервере так, будто он
локальный. Транспорт — HTTP/2, формат сообщений — Protocol Buffers. Сервер и клиент договариваются
о схеме в файле `.proto`. В отличие от REST с JSON, тут нет человекочитаемого текста: всё
бинарное и компактное.

## Шаг 2: откуда взять схему

Схема либо лежит в приложении как ресурс, либо встроена в нативный код. Ищем `.proto` и
сгенерированные классы:

```bash
$ unzip -l app.apk | grep -iE 'proto|grpc'
   18442  assets/bank_service.proto
  102344  classes.dex
```

Если `.proto` в ассетах — отлично, у нас есть имена сообщений и полей. Если нет — восстанавливаем
по именам в `classes.dex` (`grep -a 'BankService' classes.dex`).

## Шаг 3: чтение вызова

Ставим прокси с поддержкой gRPC (например, `mitmproxy` с плагином или `grpcurl` для ручного
вызова). Для `mitmproxy` схема подгружается, и вызовы раскрываются в читаемый вид:

```bash
$ grpcurl -plaintext -d '{"account":"123"}' bank.example:443 bank.BankService/GetBalance
{
  "balance": "1000.00"
}
```

Теперь вместо байтов видим поля. Это и есть цель: превратить бинарный вызов в понятный.

## Шаг 4: подмена сообщения

Когда вызов читаем, можно менять параметры: подставлять чужой `account`, менять сумму, добавлять
недостающие поля. Через прокси это делается модификацией тела, через `grpcurl` — просто новым
запросом. Часто именно здесь находится IDOR: сервер доверяет `account` из запроса.

## Шаг 5: реверс схемы без .proto

Если схемы нет, поля восстанавливают по «проволочному» формату Protobuf: каждое поле — это тег
(номер) и тип. Дамп байтов плюс перебор тегов дают структуру. Инструменты `protobuf-inspector`
и плагины для Burp помогают сопоставить теги со значениями.

## Шаг 6: защита и что смотреть

gRPC сам по себе не защищает от подмены параметров — вся логика на сервере. На что смотреть:
проверяет ли сервер права на объект (не только аутентификацию), валидирует ли вход, не отдаёт ли
лишние поля. На клиенте — доверяет ли он ответу без проверки.

## Что мы теперь знаем

- gRPC — RPC поверх HTTP/2 с бинарными сообщениями Protobuf.
- Схема `.proto` позволяет читать вызовы.
- Инструменты с поддержкой gRPC раскрывают тело в поля.
- Подмена параметров — типовой источник IDOR.
- Без схемы структуру восстанавливают по тегам.
