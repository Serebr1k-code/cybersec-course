## Вопрос, с которого всё начинается

Для многих атак нужны **две сессии одного приложения одновременно**: чтобы проверить IDOR или BOLA, нужно быть «пользователем A» и «пользователем B» в одно время. Но Android не даёт поставить один APK дважды: система идентифицирует приложение по `packageName`, и второй экземпляр с тем же именем просто не установится.

Как запустить вторую копию приложения — и почему защищённые приложения этому сопротивляются?

## Наш пример: клонируем fdroid.apk

Возьмём реальный APK `fdroid.apk` и попробуем поставить его вторым экземпляром. Сначала посмотрим, под каким именем он зарегистрирован:

```
$ apktool d -f -o fdroid_dec fdroid.apk
$ grep -o 'package="[^"]*"' fdroid_dec/AndroidManifest.xml | head -1
package="org.fdroid.fdroid"
```

Имя пакета — `org.fdroid.fdroid`. Попытка установить тот же APK поверх уже установленного даст ошибку «уже существует». Значит, нужен способ дать приложению **отдельную личность и отдельное хранилище**.

## Шаг 1: способы клонирования

Есть три принципиально разных подхода:

- **Multi-user.** Android поддерживает несколько пользователей, у каждого свой набор приложений и своя директория `/data/user/<id>/`.
- **Work Profile.** Отдельный управляемый профиль (создаётся приложениями вроде Island/Shelter через `DevicePolicyManager`).
- **VirtualApp-подобные среды** (Parallel Space, Dual Space). Они запускают чужой APK **внутри себя**, подменяя контекст и UID.

Первый и второй — «честные» системные механизмы. Третий — виртуальная среда, которую приложения легко детектят.

## Шаг 2: клон через multi-user

Самый чистый способ — второй пользователь Android:

```
$ adb shell pm create-user tester
Success: created user id 10

$ adb install --user 10 fdroid.apk
Success

$ adb shell am start --user 10 -n org.fdroid.fdroid/.MainActivity
Starting: Intent { cmp=org.fdroid.fdroid/.MainActivity }
```

Теперь у нас две копии: одна у пользователя 0, вторая — у пользователя 10. Данные полностью изолированы: каждая копия пишет в свой `/data/user/<id>/org.fdroid.fdroid/`. Именно это и нужно для теста API между двумя аккаунтами.

## Шаг 3: почему приложение может отказаться работать в клоне

Банки и DRM-приложения не хотят работать в клонированной среде — иначе злоумышленник запустит их в подконтрольном окружении для автоматизации. Поэтому они проверяют признаки клона:

- **UID.** `Process.myUid()` в виртуальной среде чужой, вне диапазона приложений (10000–19999).
- **Путь к данным.** `getFilesDir()` возвращает не `/data/data/<pkg>/`, а путь виртуальной среды.
- **Список процессов.** Наличие `com.lbe.parallel`, `io.va` и подобных.
- **Число пользователей.** `UserManager.getUserCount() > 1`.
- **Package info.** `getPackageInfo(getPackageName())` возвращает чужой путь установки.

Пример проверки на Java:

```java
String dataDir = getApplicationInfo().dataDir;
if (!dataDir.equals("/data/data/" + getPackageName())) {
    // запущено в клоне
}
int uid = android.os.Process.myUid();   // ожидаем 10000..19999
```

## Шаг 4: обход детекта через Frida

Вернём проверкам «правильные» значения:

```javascript
Java.perform(function () {
  var pkg = "org.fdroid.fdroid";
  var correct = "/data/data/" + pkg;

  var Process = Java.use("android.os.Process");
  Process.myUid.implementation = function () { return 10123; };

  var UM = Java.use("android.os.UserManager");
  UM.getUserCount.implementation = function () { return 1; };

  var PM = Java.use("android.app.ApplicationPackageManager");
  var GIP = PM.getPackageInfo.overload('java.lang.String', 'int');
  GIP.implementation = function (name, flags) {
    var info = GIP.call(this, name, flags);
    if (name === pkg) {
      info.applicationInfo.value.dataDir.value = correct;
    }
    return info;
  };
});
```

Теперь приложение «видит» одного пользователя, свой обычный путь и нормальный UID.

## Шаг 5: нативные проверки

Java-хуки обходят не всё. Часто проверка написана на C/C++ и читает файловую систему напрямую:

```c
char path[256];
ssize_t n = readlink("/proc/self/exe", path, sizeof(path)-1);
if (n > 0 && strstr(path, "parallel")) return JNI_TRUE; // детект клона
```

Тогда перехватываем нативные вызовы через `Interceptor`:

```javascript
["readlink", "open", "openat", "stat"].forEach(function (name) {
  var addr = Module.findExportByName(null, name);
  if (!addr) return;
  Interceptor.attach(addr, {
    onEnter: function (args) { this.path = args[1].isNull() ? "" : args[1].readCString(); },
    onLeave: function (retval) {
      if (this.path && this.path.indexOf("virtual") !== -1) retval.replace(-1);
    }
  });
});
```

Любая проверка, основанная на файловой системе или идентификаторах процесса, обходится подменой результата.

## Полный прогон от начала до конца

Соберём клонирование в один сценарий для теста двух аккаунтов в приложении с API:

1. **Узнаём package name** — `grep package= AndroidManifest.xml`.
2. **Создаём второго пользователя** — `adb shell pm create-user tester` (получим `id 10`).
3. **Ставим APK во второго пользователя** — `adb install --user 10 app.apk`.
4. **Устанавливаем CA-сертификат во второй профиль** — без него трафик не перехватится.
5. **Запускаем оба экземпляра** — `am start --user 0 ...` и `--user 10 ...`.
6. **Логинимся разными аккаунтами** и фиксируем два токена.
7. **В Repeater подменяем** `user_id`/`order_id` в запросе одного и смотрим, вернёт ли данные другого.

Если приложение детектит второй профиль — подключаем Frida с хуками на `getUserCount` и `dataDir` и повторяем.

## Если не сработало

- **`adb install --user 10` падает** — APK уже установлен у другого пользователя. Добавьте `-r` или тестируйте на чистом профиле.
- **Приложение падает в клоне** — нативная библиотека не находит своё хранилище. Проверьте, не сломал ли хук `dataDir`.
- **Frida не видит процесс клона** — процесс в другом user. `frida-ps -U` покажет его, но для спавна может понадобиться указать пользователя.
- **Детект остаётся** — проверка идёт из нативного кода или из отдельного процесса. Расширяйте перехват на файловую систему.
- **Work profile не создаётся** — на устройстве уже есть managed profile, или производитель это блокирует. Тогда используйте multi-user.

## Клонирование как атака

Клон — это не только барьер, но и вектор:

- **Среда-клон видит данные гостя.** Parallel Space читает буфер обмена и файлы склонированного приложения.
- **Изоляция не абсолютна.** Внутри одной виртуальной среды приложения могут читать чужое хранилище.
- **Intent-перехват.** Клон может перехватывать неявные intent'ы оригинала.
- **Обход FLAG_SECURE.** Некоторые клоны не пробрасывают защиту экрана в гостя.

Отсюда практический вывод: если приложение пишет токены во внешнее хранилище, клон-среда может их прочитать.

## Что мы теперь знаем

По-простому:

1. Один APK нельзя поставить дважды под одним `packageName`.
2. Multi-user и Work Profile дают честную изоляцию данных (`/data/user/<id>/`).
3. Виртуальные среды (Parallel Space) — самый детектируемый способ.
4. Приложения детектят клон по UID, dataDir, userCount, списку процессов.
5. Детект обходится хуками Frida — и на Java, и на нативном уровне.

## На что смотреть дальше

- **Для теста двух аккаунтов** хватит multi-user: `pm create-user` + `install --user`.
- **Для обхода виртуального детекта** готовьте хуки на UID, dataDir и `UserManager`.
- **Помните про CA-сертификат:** он привязан к пользователю, для второго профиля ставьте отдельно.
- **Проверяйте нативный детект:** Java-хуки не помогут, если проверка в C/C++.

Мы научились запускать вторую копию приложения и обходить детект клона. В следующем уроке разберём **backup**: как `adb backup` и авто-бэкап позволяют извлечь данные приложения, и почему это один из самых недооценённых каналов.
