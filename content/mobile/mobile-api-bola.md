## Что такое BOLA/IDOR в мобильном API

BOLA (Broken Object Level Authorization) — это доступ к чужим объектам по прямому идентификатору, а IDOR (Insecure Direct Object Reference) — более общий случай. В мобильных приложениях это самая частая и самая ценная находка: клиент шлёт запросы к API с идентификаторами (`user_id`, `order_id`, `account`), и если сервер не проверяет, **принадлежит ли объект текущему пользователю**, вы читаете/меняете чужие данные. Мобильный контекст усиливает проблему: API часто «тонкий» (нет веб-фронтенда с дополнительными проверками), а идентификаторы предсказуемы (последовательные числа, UUID из ответов).

Ментальная модель: авторизация должна проверяться на **каждый объект на сервере**. Если проверка есть только на клиенте (скрытие кнопок) или только на уровне «аутентифицирован ли пользователь», но не «владеет ли он этим объектом», — это BOLA.

## Как находить: трафик и эндпоинты

Начните с перехвата трафика (`mobile-mitm-burp`) и инвентаризации эндпоинтов. Ищите параметры-идентификаторы:

```bash
# из mitmproxy-flow сохранить URL и параметры
mitmdump -p 8080 -w flows.mitm
grep -oE "https?://[^ ]+/[a-z0-9_/-]+\?[^ ]+" flows.txt | sort -u | head -50
```

Типичные «горячие» места: `/v1/users/{id}`, `/v1/orders?user_id=`, `/v1/messages/{mid}`, `/v1/documents/{doc}`, `/v1/accounts/{acc}/balance`. Обращайте внимание на GraphQL (`node(id:)`, `user(id:)`) и на идентификаторы в теле POST.

## Тестирование IDOR вручную

Самый простой метод — взять токен пользователя A и подставить идентификатор пользователя B.

```bash
# 1. логинимся как A, получаем токен и свой id (1001)
# 2. пробуем запросить объект B (1002)
curl -s -H "Authorization: Bearer $TOKEN_A" \
     "https://api.target.example/v1/users/1002/profile"
# 200 + данные B -> IDOR
# 403/404 -> проверка есть (но проверьте другие методы/эндпоинты)
```

Проверяйте не только GET, но и PUT/PATCH/DELETE/POST: чтение может быть защищено, а изменение — нет. Также пробуйте менять вложенные идентификаторы (`/users/1001/orders/5002`).

## BOLA на объектах и функциях

Различайте два уровня:

- **Object-level (BOLA):** доступ к чужому объекту (`/orders/5002`).
- **Function-level (BFLA):** вызов чужой функции/роли (`/admin/deleteUser`, `/internal/debug`).

BFLA часто прячется за мобильными «админскими» экранами. Проверьте, какие эндпоинты вызывают админские экраны приложения (в трафике), и попробуйте их с обычным токеном. Также пробуйте менять роль в токене (если JWT — проверьте подпись, `jwt_analyze`).

## Привязка к устройству (device binding) и её обход

Некоторые API «привязывают» сессию к устройству через `device_id`, `X-Device-Id`, отпечаток, аттестацию (SafetyNet/Play Integrity). Это дополнительный слой авторизации. Ошибки: device_id **передаётся клиентом** и не проверяется на сервере (можно подставить чужой); привязка есть только для части запросов; устройство можно «переиграть» (replay).

```bash
# украденный токен с чужого устройства: подставляем device_id жертвы
curl -H "Authorization: Bearer $TOKEN" -H "X-Device-Id: $VICTIM_DEVICE" \
     "https://api.target.example/v1/me"
```

Если сервер доверяет заголовку — привязка обходится. Аттестация (SafetyNet) проверяется криптографически, но часто сервер лишь «смотрит на флаг», а не валидирует подпись.

## Массовое тестирование

Ручной перебор идентификаторов автоматизируется mitmproxy-скриптом или `ffuf`:

```python
# addons.py — автоматически перебрать user_id в запросах к /profile
from mitmproxy import http
class Enum:
    def request(self, flow: http.HTTPFlow):
        if "/v1/users/" in flow.request.path:
            import re
            uid = re.search(r"/users/(\d+)", flow.request.path)
            if uid:
                flow.request.path = flow.request.path.replace(uid.group(1), "1002")
def load(l): l.add(Enum())
```

```bash
# или ffuf с одним токеном и перебором id
ffuf -u "https://api.target.example/v1/users/FUZZ/profile" \
     -H "Authorization: Bearer $TOKEN_A" \
     -w ids.txt -mc 200 -fs 0
```

Осторожно: массовый перебор может быть замечен (rate-limit, бан). Тестируйте точечно и в рамках правил программы.

## Роли: горизонтальная и вертикальная эскалация

- **Горизонтальная:** пользователь A получает данные пользователя B (тот же уровень).
- **Вертикальная:** пользователь получает права администратора (BFLA, подмена роли).

Проверяйте оба направления: создайте два аккаунта (A и B), затем A-токеном запрашивайте B-объекты; для вертикальной — попробуйте админские эндпоинты из трафика админ-экранов с обычным токеном.

## Разобранный пример: IDOR → чтение чужих заказов

```bash
$ curl -s -H "Authorization: Bearer $A" "https://api.target.example/v1/orders?user_id=1001"
{"orders":[{"id":5001,"item":"Book","addr":"..."}]}
$ curl -s -H "Authorization: Bearer $A" "https://api.target.example/v1/orders?user_id=1002"
{"orders":[{"id":5002,"item":"Laptop","addr":"ул. Пушкина 1"}]}   # чужие данные!
$ curl -s -X DELETE -H "Authorization: Bearer $A" "https://api.target.example/v1/orders/5002"
HTTP/1.1 204 No Content   # ещё и удаление чужого заказа
```

Найден BOLA с чтением и удалением. Impact — утечка PII и деструктивное действие.

## Справочная таблица: где искать BOLA

| Признак | Что тестировать |
|---------|-----------------|
| Последовательные id | подмена id, ±1, чужие диапазоны |
| UUID из ответов | подставить UUID чужого объекта |
| `user_id`/`account` в query | заменить на чужой |
| Вложенные пути `/a/{id}/b/{id2}` | менять оба id |
| GraphQL `node(id:)` | запросить чужие узлы |
| Админские эндпоинты | вызов обычным токеном (BFLA) |
| `device_id` в заголовке | подставить чужой |

## Типовые ошибки новичка

- **Тестировать только GET.** Изменение/удаление часто не защищено.
- **Ограничиться одним id.** Пробуйте диапазоны и «края» (0, -1, огромные).
- **Игнорировать device binding.** Если запрос «не работает» с чужого устройства — это и есть проверка; поищите обход.
- **Не проверять GraphQL.** `node(id:)`/`user(id:)` — частый источник BOLA.
- **Шуметь.** Массовый перебор приведёт к бану; работайте точечно.

## Что дальше / решение

Порядок: перехватить трафик → инвентаризировать эндпоинты и идентификаторы → создать два аккаунта → точечно проверить чтение/изменение чужих объектов → проверить админские функции (BFLA) → проверить device binding. Связанные уроки: `mobile-api-testing`, `mobile-mitm-burp`, `mobile-account-takeover`. Решение — когда подтверждён доступ к чужому объекту (или функции) с воспроизводимым запросом.

## Практический чек-лист поиска BOLA/IDOR

1. Собрать эндпоинты из трафика; отметить все с идентификаторами (`id`, `user_id`, `uuid`, `node(id:)`).
2. Создать два аккаунта (A и B) с разными данными.
3. Токеном A запросить объекты B (чтение) — GET.
4. Токеном A изменить/удалить объекты B — PUT/PATCH/DELETE/POST.
5. Проверить вложенные и составные идентификаторы.
6. Проверить GraphQL-узлы и мутации.
7. Проверить админские эндпоинты обычным токеном (BFLA).
8. Проверить привязку к устройству: подставить чужой `device_id`/отпечаток.
9. Зафиксировать PoC-запросы и impact.

## Типовые ошибки (продолжение)

- **Считать 403 достаточной защитой.** Проверяйте другие методы и эндпоинты того же объекта.
- **Забыть про «косвенные» id.** Иногда объект берётся по имени/email — тоже подставляйте чужое.
- **Не проверять массовое назначение (mass assignment).** Лишние поля в PUT (`role`, `isAdmin`) могут эскалировать права.
- **Игнорировать кэш.** Иногда сервер отдаёт чужой объект из кэша по id.
- **Шуметь.** Rate-limit/бан — работайте в рамках правил программы.
