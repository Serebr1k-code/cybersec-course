## Вопрос, с которого всё начинается

Мы уже перехватывали трафик мобильного приложения и видели, что оно ходит в свой API: `GET /v1/orders?user_id=1001`, `GET /v1/users/1001/profile`. Вопрос новичка: «а что будет, если я подставлю чужой `user_id`?» Чаще всего — ничего хорошего для владельца сервиса. Ошибка, при которой пользователь получает доступ к **чужому объекту** по прямому идентификатору, называется **BOLA** (Broken Object Level Authorization — «сломанная авторизация на уровне объекта»). Более старое имя — **IDOR** (Insecure Direct Object Reference). В мобильном API это самая частая и самая дорогая находка.

Разберём это не на словах, а на живом API, который мы поднимем локально.

## Наш пример: API магазина и два аккаунта

У нас есть мобильный бэкенд `http://127.0.0.1:18080` с двумя пользователями: Алиса (`id=1001`, токен `tok-A`) и Боб (`id=1002`, токен `tok-B`). У каждого свои заказы. Мы играем за Алису — наш единственный токен `tok-A`.

**Токен** — это строка, которой приложение доказывает серверу, кто пользователь; сервер проверяет её и достаёт из неё `id`. Запрос «покажи мой профиль» выглядит так:

```
$ curl -s -H "Authorization: Bearer tok-A" \
       "http://127.0.0.1:18080/v1/users/1001/profile"
{"id": "1001", "email": "alice@example.com", "role": "user", "balance": 100}
```

Всё логично: `id=1001` — это мы, сервер отдал наши данные. Теперь главный вопрос урока: сервер проверил, что **объект принадлежит нам**, или только что «мы вообще аутентифицированы»?

## Шаг 1: подставляем чужой идентификатор

Меняем `1001` на `1002`, оставляя наш токен:

```
$ curl -s -i -H "Authorization: Bearer tok-A" \
       "http://127.0.0.1:18080/v1/users/1002/profile"
HTTP/1.0 200 OK
Content-Type: application/json

{"id": "1002", "email": "bob@example.com", "role": "user", "balance": 5000}
```

`200 OK` и данные Боба. Мы получили **чужой объект своим токеном** — это и есть BOLA на чтение. Сервер проверил только «есть ли валидный токен», но не «владеет ли этот пользователь объектом `1002`».

Запомним ментальную модель: авторизация должна проверяться **на каждый объект**, а не только на вход. Скрытие кнопок на клиенте — не защита.

## Шаг 2: то же самое на списках и вложенных путях

Часто идентификатор передаётся не в пути, а в параметре. Здесь `user_id` тоже не проверяется:

```
$ curl -s -H "Authorization: Bearer tok-A" \
       "http://127.0.0.1:18080/v1/orders?user_id=1002"
{"orders": [{"id": 5002, "item": "Laptop", "addr": "ул. Пушкина 1"}]}
```

Мы видим заказ Боба — «Laptop» и его адрес. Это утечка персональных данных (PII). Проверять надо и вложенные конструкции вида `/users/1001/orders/5002`, где меняется второй идентификатор.

## Шаг 3: чтение — это ещё полбеды

Новички часто проверяют только `GET`. А изменение и удаление сплошь и рядом не защищены. Попробуем удалить чужой заказ нашим токеном:

```
$ curl -s -i -X DELETE -H "Authorization: Bearer tok-A" \
       "http://127.0.0.1:18080/v1/orders/5002"
HTTP/1.0 204 No Content
```

`204 No Content` — сервер молча удалил заказ Боба. Такой **write-BOLA** опаснее чтения: это уже деструктивное действие над чужими данными, и в отчёте он идёт как critical. Всегда пробуйте `GET`, `POST`, `PUT`, `PATCH` и `DELETE` по одному и тому же объекту.

## Шаг 4: привязка к устройству (device binding)

Некоторые API «привязывают» сессию к устройству: вместе с токеном приложение шлёт `X-Device-Id` (или отпечаток, или результат аттестации Play Integrity). Идея — украденный токен не сработает на другом телефоне.

Ошибка в том, что `device_id` приходит **от клиента** и сервер ему доверяет. Подставим чужой идентификатор устройства:

```
$ curl -s -H "Authorization: Bearer tok-A" -H "X-Device-Id: victim-device-999" \
       "http://127.0.0.1:18080/v1/me"
{"id": "1001", "device": "victim-device-999", "email": "alice@example.com"}
```

Сервер принял любой `device_id`. Значит, привязка обходится подстановкой значения жертвы — она ничего не защищает. Аттестация же безопасна только если сервер **криптографически проверяет подпись**, а не просто смотрит на флаг «прошло».

## Шаг 5: как перебирать идентификаторы, не «шуметь»

Когда эндпоинт с идентификатором найден, его перебирают по диапазону. Проще всего циклом по числам, подставляя их в путь:

```
$ for id in 1001 1002 1003 1004; do
    curl -s -o r.json -w "$id -> HTTP %{http_code}  " \
      -H "Authorization: Bearer tok-A" \
      "http://127.0.0.1:18080/v1/users/$id/profile"; cat r.json; echo
  done
1001 -> HTTP 200  {"id": "1001", "email": "alice@example.com", "role": "user", "balance": 100}
1002 -> HTTP 200  {"id": "1002", "email": "bob@example.com", "role": "user", "balance": 5000}
1003 -> HTTP 200  {"id": "1003", "email": "carol@example.com", "role": "user", "balance": 42}
1004 -> HTTP 404  {"error": "not found"}
```

Мы за один проход получили данные сразу трёх пользователей — это уже массовая утечка. В продакшене вместо цикла берут `ffuf` или скрипт-аддон к mitmproxy, который на лету подменяет `user_id` в каждом запросе приложения. Но помните: массовый перебор легко ловится rate-limit’ом и приводит к бану. Тестируйте точечно, в рамках правил программы, и фиксируйте только воспроизводимые запросы.

## Шаг 6: горизонтальная и вертикальная эскалация

Различайте два направления:

- **Горизонтальная** — Алиса читает данные Боба (тот же уровень доступа). Это то, что мы уже сделали.
- **Вертикальная** — обычный пользователь получает права администратора.

Для вертикальной ищут «админские» эндпоинты из трафика админ-экранов (`/admin/deleteUser`, `/internal/debug`) и вызывают их обычным токеном. Отдельный случай — подмена роли в токене (если это JWT, проверьте подпись: слабый секрет или `alg: none`).

## Полный прогон от начала до конца

Маршрут по нашему API:

1. **Перехват** — собрать эндпоинты из трафика (mitmproxy/Burp), отметить все, где есть `id`, `user_id`, `uuid`.
2. **Два аккаунта** — завести A и B с разными данными.
3. **Чтение** — токеном A запросить объекты B (`/v1/users/1002/profile`). `200` + данные → BOLA.
4. **Изменение** — `DELETE /v1/orders/5002` токеном A. `204` → write-BOLA.
5. **Device binding** — подставить чужой `X-Device-Id`.
6. **Фиксация** — сохранить пару запросов (свой объект и чужой) как PoC: именно разница между ними доказывает уязвимость.

## Если не сработало

`403` или `404` на чужом объекте ещё не значит «безопасно». Проверьте: другие HTTP-методы по тому же пути, вложенные идентификаторы, GraphQL (`node(id:)`, `user(id:)`), косвенные ключи (email, username вместо числового id), и разные эндпоинты того же ресурса. Иногда чтение закрыто, а изменение — нет, или наоборот. И наоборот: `403` может быть признаком rate-limit — не «долбите» перебором, работайте точечно.

## Что мы теперь знаем

1. BOLA/IDOR — доступ к чужому объекту, когда сервер не проверяет владельца, а только факт аутентификации.
2. Проверять надо каждый объект и каждую функцию, на сервере.
3. Тестируют двумя аккаунтами: своим токеном запрашивают чужой идентификатор.
4. Проверяют не только `GET`, но и `POST`/`PUT`/`PATCH`/`DELETE` — write-BOLA опаснее.
5. `device_id`/отпечаток, приходящий от клиента, — не защита; обходится подстановкой.
6. Доказательство — воспроизводимая пара запросов «свой объект vs чужой».

## Куда дальше

Мы научились получать чужой объект. В следующем уроке `mobile-mass-assignment` разберём, как те же «лишние» поля в теле запроса позволяют не просто прочитать чужое, а **подменить роль или баланс** — повышение привилегий на сервере. А пока запомни главное: авторизация проверяется на каждый объект, и доказывается она парой запросов «свой vs чужой».

## Где пригодится

- **CTF Mobile:** доступ к чужому объекту или флагу через API — частый шаг цепочки.
- **Bug bounty:** BOLA/IDOR — самая частая и высокооплачиваемая находка в мобильном API.
- **Пентест:** аудит объектной авторизации мобильного бэкенда (OWASP API1:2023).
- **Работа:** ревью API на проверку владельца объекта перед выдачей данных.
