## Вопрос, с которого всё начинается

Запускаешь приложение в эмуляторе — оно отказывается работать. Ставишь на реальный телефон — работает, но при попытке перехватить трафик снова закрывается. Приложение детектит **среду анализа**: эмулятор, прокси, отладчик. Как оно это понимает и как заставить его работать в тестовой среде?

## Наш пример: приложение, не желающее работать в эмуляторе

Возьмём приложение с защитой от анализа. Оно проверяет несколько признаков эмулятора и завершается, если находит хотя бы один. Разберём проверки и обход каждой.

## Шаг 1: признаки эмулятора

Эмулятор (AVD, Genymotion, QEMU) отличается от реального устройства рядом свойств:

- **`Build`-поля.** `Build.FINGERPRINT` содержит `generic`, `Build.MODEL` — `sdk`/`Emulator`, `Build.MANUFACTURER` — `Genymotion`/`Google`, `Build.HARDWARE` — `goldfish`/`ranchu`.
- **Файлы.** `/dev/socket/qemud`, `/dev/qemu_pipe`, `/system/lib/libc_malloc_debug_qemu.so` присутствуют только в эмуляторе.
- **Телефония.** `TelephonyManager.getNetworkOperatorName()` возвращает `Android`, а `getDeviceId()` — нули или `000000000000000`.
- **Датчики.** У эмулятора ограниченный набор сенсоров.
- **CPU.** Некоторые эмуляторы не выставляют `armeabi` корректно.
- **Системное свойство `ro.kernel.qemu`.** Классический признак: в эмуляторе на базе QEMU оно равно `1`, на реальном устройстве его нет. Проверка `SystemProperties.get("ro.kernel.qemu")` встречается не реже, чем проверка `Build`-полей, и её легко пропустить.

В коде это выглядит так:

```java
public static boolean isEmulator() {
    return Build.FINGERPRINT.startsWith("generic")
        || Build.MODEL.contains("google_sdk")
        || Build.MODEL.contains("Emulator")
        || Build.MANUFACTURER.contains("Genymotion")
        || Build.HARDWARE.contains("goldfish")
        || Build.PRODUCT.contains("sdk");
}
```

## Шаг 2: обход через Frida — подменяем Build

Самый прямой путь — перехватить чтение полей `Build` и подставить «реальные» значения:

```javascript
Java.perform(function () {
  var Build = Java.use("android.os.Build");
  Build.FINGERPRINT.value = "google/sdk_gphone/.../release-keys";
  Build.MODEL.value = "Pixel 5";
  Build.MANUFACTURER.value = "Google";
  Build.HARDWARE.value = "redfin";
  Build.PRODUCT.value = "redfin";
});
```

Здесь мы не «запускаем на реальном телефоне» — мы врём приложению о свойствах среды. После подмены проверка `isEmulator()` вернёт `false`, и приложение продолжит работу.

Если проверка читает свойства системы (`SystemProperties.get`), перехватываем и его, возвращая нужные значения для ключей `ro.product.*`, `ro.hardware`.

## Шаг 3: детект прокси

Второй слой — проверка, не работает ли приложение через прокси. Признаки:

- системное свойство `http.proxy` непустое;
- `System.getProperty("http.proxyHost")` задан;
- доступен порт прокси (проверка соединения);
- активен VPN-интерфейс (см. `mobile-mitm-advanced`).

Обход: подменить чтение свойств прокси на пустые значения, либо использовать **transparent proxy**, который приложение не видит (трафик перехватывается на уровне сети, а не через настройку). Второй вариант надёжнее: приложение не может «увидеть» то, чего нет в его конфигурации.

## Шаг 4: детект отладчика и Frida

Третий слой пересекается с анти-Frida (см. `mobile-frida-detection`): проверка `TracerPid`, строк `frida` в `/proc/self/maps`, порта `27042`. Обход — хук соответствующих чтений и нестандартный порт.

Здесь важно, что детекты **комбинируются**: приложение может проверять эмулятор, прокси и Frida сразу, и обойти один признак недостаточно. Поэтому обход начинают с **логирования**: перехватывают чтение файлов и свойств и смотрят, что именно проверяется, — а потом нейтрализуют по очереди.

## Шаг 5: аппаратные устройства и «продвинутые» проверки

Иногда обход хуками невозможен: проверка реализована в нативном коде, использует аппаратные признаки (сенсоры, GPU, TEE) или уходит на сервер (аттестация). Тогда варианты:

- **Реальное устройство.** Самый надёжный путь: на физическом телефоне эмуляторных признаков нет. Остаются root/прокси/Frida — их обходят отдельно.
- **«Закалённый» эмулятор.** Настройка эмулятора так, чтобы свойства соответствовали реальному устройству (переименование, подмена GPU). Трудоёмко и хрупко.
- **Хук нативных проверок.** Если детект в `.so`, перехватывают нативную функцию.

Практический вывод: чем сильнее детект, тем чаще анализ переносят на реальное устройство — эмулятор остаётся для быстрых проверок, а сложные случаи решают на «железе».

## Шаг 6: порядок обхода

1. **Логируйте, что читает приложение.** Перехват `open`, `openat`, `SystemProperties.get`, `getprop` показывает все проверки.
2. **Начните с Build-полей.** Это самый частый и самый простой детект.
3. **Подмените свойства прокси** или перейдите на transparent.
4. **Закройте анти-Frida** (порт, строки).
5. **Если не помогает — реальное устройство.**

## Шаг 7: логирование проверок на практике

Ключевой приём — **увидеть**, что именно читает приложение. Перехватываем системные вызовы и свойства:

```javascript
Java.perform(function () {
  // какие системные свойства читает приложение
  var SP = Java.use("android.os.SystemProperties");
  SP.get.overload("java.lang.String").implementation = function (key) {
    var v = this.get(key);
    console.log("[prop] " + key + " = " + v);
    return v;
  };
  // какие файлы открываются (в т.ч. признаки QEMU)
  var FIS = Java.use("java.io.FileInputStream");
  FIS.$init.overload("java.lang.String").implementation = function (path) {
    console.log("[file] " + path);
    return this.$init(path);
  };
});
```

Прогоняем приложение и смотрим лог: если оно читает `ro.hardware` или открывает `/dev/qemu_pipe` — это и есть проверка эмулятора. Теперь мы знаем точку, которую нужно подменить, вместо слепого перебора.

## Шаг 8: типичные ошибки

- **Обойти один признак.** Проверки комбинируются: закрыли `Build.MODEL` — сработал файл QEMU. Обходить нужно все.
- **Подменить поле только один раз.** Некоторые приложения читают `Build` повторно; статическая подмена значения в Frida (`.value = ...`) надёжнее, чем одноразовая.
- **Забыть про нативные проверки.** Детект может быть в `.so`; тогда Java-хуки не помогут.
- **Игнорировать прокси-детект.** Приложение может падать не из-за эмулятора, а из-за активного прокси — проверяйте оба.
- **Полагаться только на эмулятор.** Для сильных детектов реальное устройство экономит время, даже если кажется «сложнее».
- **Не логировать проверки.** Без лога вы обходите наугад и тратите часы.
- **Забыть про свойства системы.** `SystemProperties.get("ro.hardware")` — частая проверка наравне с `Build`.
- **Не проверить отладочную сборку.** Если `android:debuggable="true"`, анализ сильно упрощается.
- **Смешивать причины.** Падение приложения может быть из-за прокси, а не эмулятора — проверяйте оба.

## Шаг 9: набор признаков для самопроверки

Собери список проверок, которые стоит пройти на своём стенде, — тогда сразу видно, что именно сработает. Типовые индикаторы эмулятора: `Build.FINGERPRINT`/`Build.MODEL` содержат `generic`, `sdk`, `vbox`; есть узлы `/dev/socket/qemud`, `/dev/qemu_pipe`; свойства `ro.kernel.qemu=1`, `ro.hardware=goldfish`/`ranchu`; отсутствуют телеметрия и датчики. Прокси детектится через системное свойство `http.proxy` и переменную окружения `http_proxy`. Отладчик и Frida — по `/proc/<pid>/status` (поле `TracerPid != 0`), порту `27042` и именам потоков. Прогоняя этот чек-лист до запуска таргета, ты заранее понимаешь, какие хуки писать.

## Что мы теперь знаем

По-простому:

1. Эмулятор детектится по `Build`-полям, файлам QEMU, телефонии и сенсорам.
2. Прокси детектится по системным свойствам и активному VPN.
3. Frida/отладчик — по `TracerPid`, строкам в памяти и порту.
4. Обход — подмена значений хуком; детекты комбинируются, обходить нужно все.
5. Самый надёжный путь для сильных детектов — реальное устройство.

## На что смотреть дальше

- **Сначала логируйте.** Без списка проверок обход — угадывание.
- **Build-поля — приоритет №1.** Самый распространённый детект.
- **Transparent proxy не виден приложению.** Лучше подмены свойств.
- **Реальное устройство — крайняя мера.** Когда хуки не справляются.
