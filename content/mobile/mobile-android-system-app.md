## Вопрос, с которого всё начинается

Некоторые приложения на телефоне умеют то, что обычным запрещено: читают SMS всех
приложений, меняют системные настройки, перезагружают устройство. Почему им можно?
Потому что они **системные**. И если такое приложение уязвимо, атакующий получает
привилегии, недоступные обычному коду. Разберём, откуда эти права берутся.

## Наш пример: предустановленное приложение из priv-app

Возьмём приложение из `/system/priv-app`, которое умеет читать журнал звонков без
разрешения. Посмотрим, что делает его особенным.

## Шаг 1: где живут системные приложения

Обычные приложения ставятся в `/data/app`. Предустановленные лежат в двух каталогах:

```bash
$ adb shell ls /system/app | head
$ adb shell ls /system/priv-app | head
Bluetooth  Settings  SystemUI  VendorService
```

`/system/app` — обычные системные приложения. `/system/priv-app` — **привилегированные**:
именно они могут получать разрешения уровня `signature|privileged`.

## Шаг 2: разрешения уровня privileged

Обычное приложение не может запросить, скажем, `WRITE_SECURE_SETTINGS`. А приложение из
`priv-app` — может, если это разрешение помечено как `privileged`:

```bash
$ adb shell dumpsys package com.vendor.service | grep -i requested
requested permissions:
  android.permission.READ_LOGS
  android.permission.WRITE_SECURE_SETTINGS
```

`READ_LOGS` обычно недоступно сторонним приложениям, но привилегированному — да. Так
одно только расположение в `priv-app` даёт огромные возможности.

## Шаг 3: платформенная подпись

Есть разрешения, выдаваемые только приложениям, подписанным **тем же ключом**, что и
система (`protectionLevel="signature"`). Это платформенная подпись. Она нужна, например,
для `INSTALL_PACKAGES` или для доступа к некоторым внутренним API.

```bash
$ adb shell dumpsys package com.vendor.service | grep -i signatures
signatures=PackageSignatures{... cert=platform}
```

Если приложение подписано платформенным ключом, оно фактически часть системы. Подделать
эту подпись нельзя — ключ есть только у производителя.

## Шаг 4: почему это поверхность атаки

Системные приложения — лакомая цель, потому что они уже привилегированы. Уязвимость в
них превращается в привилегированное выполнение:

* экспортированный компонент системного приложения без проверки вызывающего;
* обработка недоверенных данных (файлы, интенты, сеть) в привилегированном процессе;
* избыточные разрешения, которые приложение на самом деле не использует.

```bash
$ adb shell dumpsys package com.vendor.service | grep -A5 "exported=true"
```

Если системное приложение отдаёт наружу компонент, меняющий состояние, — это находка
уровня high.

## Шаг 5: как это проверять

Порядок работы: выписать системные и привилегированные приложения, посмотреть их
разрешения, найти экспортированные компоненты, оценить обработку входа. Дальше — как
обычно: манифест, декомпиляция, ручной вызов.

```bash
$ adb shell pm list packages -s | head
$ adb shell pm list packages -p | head
```

`-s` показывает системные, `-p` — только привилегированные. С этого списка и
начинается аудит прошивки.

## Избыточные привилегии и shared system uid

Помимо расположения в `priv-app`, есть ещё один механизм усиления прав — **shared uid**.
Несколько приложений могут объявить один и тот же `android:sharedUserId`, и тогда
система запускает их в одном процессе с общими данными. Если одно из них — системное
или привилегированное, остальные получают его уровень доступа.

```xml
<manifest android:sharedUserId="android.uid.system">
```

Это исторически использовалось для «связанных» приложений производителя, но при
неаккуратном проектировании превращается в дыру: слабое приложение в той же группе
открывает доступ к данным привилегированного.

Второй источник избыточности — разрешения, которые приложение запрашивает, но не
использует. Их наличие расширяет поверхность атаки: если приложение скомпрометировано,
атакующий получает все эти права. При аудите полезно сверять заявленные разрешения с
реально используемыми API.

```bash
$ adb shell dumpsys package com.vendor.service | grep -A20 "requested permissions"
```

Так из одного списка разрешений вырастает целая карта риска: какие права есть, какие
из них привилегированные, и что произойдёт, если приложение сломают.

## Что проверить на реальном устройстве

Начни со списка привилегированных пакетов и их разрешений. Дальше ищи среди них
экспортированные компоненты — именно они превращают «привилегированное, но закрытое»
в «привилегированное и доступное».

```bash
$ adb shell pm list packages -p
$ adb shell dumpsys package com.vendor.service | grep -E "exported|permission"
```

Обрати внимание на общий uid: если приложение делит `sharedUserId` с другими, оцени,
насколько безопасны соседи. Слабое звено в группе обесценивает защиту всей группы.

И проверь подпись. Приложение с платформенной подписью — часть системы; приложение из
`priv-app` без неё — всё ещё мощная цель. Различай эти случаи: от них зависит, какие
API доступны и насколько серьёзна находка.

## Типичное заблуждение: системное = неизменное

Раз приложение в `/system`, кажется, что его нельзя обновить или подменить. На
современных устройствах это не так. Системные приложения **обновляются через магазин**:
новая версия ставится в `/data`, а старая остаётся в `/system` как резерв. Значит, код
приложения может быть свежим и содержать новые ошибки, которых не было в прошивке.

Это важно для аудита: поверхность системного приложения — это не то, что зашили при
сборке прошивки, а то, что стоит на устройстве **сейчас**, вместе со всеми
обновлениями. Проверять надо актуальную версию, а не ту, что лежит в образе.

Отсюда же следует, что «системное» не означает «безопасное». Системные приложения
пишут обычные разработчики, они наследуют код сторонних библиотек и тоже ошибаются.
Разница лишь в том, что их ошибки сразу дают привилегии. Поэтому список системных
пакетов — не формальность, а первый фильтр аудита прошивки: именно там ищут
экспортированные компоненты и избыточные права.

Держи этот список под рукой при каждом аудите прошивки: системные и привилегированные пакеты — самый вероятный источник привилегированных уязвимостей, и именно с них стоит начинать, а не с пользовательских приложений.

## Как строить аудит прошивки

Работа с системным слоем требует дисциплины, иначе список из сотен пакетов парализует.
Начни с фильтра по привилегированности: приложения из `priv-app` и пакеты с
платформенной подписью — первый эшелон. Затем отфильтруй те, у которых есть
экспортированные компоненты: закрытое приложение недоступно снаружи, и его уязвимость
требует отдельного вектора. После этого остаётся короткий список реальных целей, и его
уже можно разбирать по одному. Такой порядок экономит время и не даёт утонуть в деталях.
Записывай для каждого кандидата три вещи: какие права у него есть, что он обрабатывает
из недоверенного входа и можно ли до него дотянуться из твоего uid.

## Что мы теперь знаем

- Системные приложения лежат в `/system/app` и `/system/priv-app`.
- `priv-app` даёт доступ к разрешениям уровня `privileged`.
- Платформенная подпись открывает `signature`-разрешения и внутренние API.
- Уязвимость в системном приложении = привилегированное выполнение.
- Аудит начинается со списка системных и привилегированных пакетов.
