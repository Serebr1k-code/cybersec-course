## Вопрос, с которого всё начинается

В коде приложения вы видите `Class.forName(...)` и `getMethod(...)`, а прямых вызовов нужной
функции нет. Логика будто «растворена». Это reflection: вызовы делаются по именам-строкам,
которые можно собрать из частей, и статически их не видно. Как разобрать такой код?

## Наш пример: app.apk с reflection

```java
Class<?> c = Class.forName("com.example." + "Sec" + "urity");
Method m = c.getMethod("che" + "ck", String.class);
Object r = m.invoke(null, input);
```

Имена склеены из частей, чтобы их не нашёл простой `grep`. Класс и метод загружаются по строке
в рантайме.

## Шаг 1: что такое reflection

Reflection — механизм Java, позволяющий в рантайме получать информацию о классах и вызывать
методы по имени (в виде строки). Обычно `obj.method()` компилируется в прямой вызов, но при
reflection имя метода — это данные, и его можно формировать динамически. Для обфускации это
золотая жила: статически не видно, что вызывается.

## Шаг 2: почему это прячет логику

Статический анализ видит `Class.forName(name)`, но не знает значения `name`, если оно
собирается в рантайме. `grep` по имени метода ничего не найдёт. Аналитику приходится либо
эмулировать вычисление строк, либо перехватывать вызов в рантайме.

## Шаг 3: как найти

Ищем признаки reflection:

```bash
$ grep -rn -E 'Class.forName|getDeclaredMethod|getMethod|getField' out/sources | head
Loader.java:22: Class.forName(part1 + part2)
```

Дальше смотрим, как формируется имя: из констант, из ресурсов, из расшифровки. Часто это
конкатенация частей — её можно вычислить вручную или скриптом.

## Шаг 4: деобфускация

Простой путь — собрать строку вручную, подставив части. Если частей много, пишут скрипт,
который эмулирует вычисление (или используют Frida, чтобы перехватить результат `Class.forName`):

```javascript
Java.perform(function () {
  var C = Java.use('java.lang.Class');
  C.forName.overload('java.lang.String').implementation = function (n) {
    console.log('forName: ' + n);
    return this.forName(n);
  };
});
```

Так мы видим реальные имена классов и методов в момент вызова.

## Шаг 5: перехват вызовов

Аналогично перехватывают `Method.invoke`, чтобы видеть, что и с какими аргументами вызывается.
Это даёт полную картину скрытой логики без ручной эмуляции.

## Шаг 6: автоматизация

Для сложных случаев строки вычисляются целой функцией — тогда её эмулируют (Unicorn) или
трассируют (Stalker). Цель — получить значения строк, которые уходят в reflection.

## Шаг 7: защита

Обфускаторы (DexGuard, Stringer) комбинируют reflection с шифрованием строк и вычислением имён
на ходу. Это повышает стоимость анализа, но принцип тот же: в рантайме имя становится известным,
и его можно перехватить.

## Шаг 8: раскрытие строк из частей скриптом

Когда имя метода склеено из десятка кусков, вручную считать неудобно — пишем скрипт. Сначала
достаём все строковые константы и порядок операций из smali, затем складываем их:

```python
parts = ['com.example.', 'Sec', 'urity']
name = ''.join(parts)
print(name)          # com.example.Security
```

Если куски берутся из ресурсов или из результата decrypt-функции, скрипт вызывает ту же функцию
(или эмулирует её через Unicorn), чтобы получить финальную строку. Цель одна — восстановить
значение, которое уходит в `Class.forName`.

## Шаг 9: перехват конструкторов и полей

Reflection не ограничивается методами. Перехватывают также поля и конструкторы:

```javascript
Java.perform(function () {
  var Field = Java.use('java.lang.reflect.Field');
  Field.get.overload('java.lang.Object').implementation = function (o) {
    var v = this.get(o);
    console.log('Field.get ' + this.getName() + ' = ' + v);
    return v;
  };
});
```

`Field.get` даёт значения полей по имени, `Constructor.newInstance` — созданные объекты. Полная
картина скрытой логики складывается из трёх перехватов: `Class.forName`, `Method.invoke` и
`Field.get`.

## Как это выглядит в smali

В smali reflection виден явными вызовами:

```smali
const-string v0, "com.example.Security"
invoke-static {v0}, Ljava/lang/Class;->forName(Ljava/lang/String;)Ljava/lang/Class;
move-result-object v0
const-string v1, "check"
invoke-virtual {v0, v1, ...}, Ljava/lang/Class;->getMethod(...)
```

`invoke-static` для `forName`, `invoke-virtual` для `getMethod` и `invoke-virtual` для
`Method.invoke`. Grep по этим трём сигнатурам находит все точки reflection в приложении за секунды.

## Практический сценарий: расшифровка check()

1. `grep -rn 'Class.forName' out/sources` — находим точку загрузки класса.
2. Смотрим, как формируется имя: константы, ресурсы, decrypt-функция.
3. Складываем части скриптом либо перехватываем `forName` через Frida.
4. Получаем имя класса и метода, находим их в декомпилированном коде.
5. Читаем `check()` напрямую — теперь это обычный статический анализ.

На шаге 3 Frida удобнее, когда имя строится в рантайме: перехват показывает фактическую строку,
и дальше работа идёт уже с найденным методом.

## Таблица API reflection

| Вызов | Что делает | Что перехватывать |
|---|---|---|
| `Class.forName` | загрузка класса по имени | `Class.forName(String)` |
| `getMethod` / `getDeclaredMethod` | поиск метода | `Class.getMethod` |
| `Method.invoke` | вызов метода | `Method.invoke` |
| `getField` / `getDeclaredField` | доступ к полю | `Field.get` / `Field.set` |
| `Constructor.newInstance` | создание объекта | `Constructor.newInstance` |

## Ограничения

Перехват работает, только если приложение уже загрузило нужный класс. Для reflection из нативного
кода (через JNI `CallObjectMethod`) Frida-хук по Java-API не сработает — нужен перехват JNI
(`RegisterNatives`) или трассировка нативного вызова. Также anti-Frida проверки (RASP) могут
сорвать подключение — тогда сначала нейтрализуют детект, и лишь затем ставят хуки.

## Шаг 10: dynamic proxies

Ещё один приём обфускации — `java.lang.reflect.Proxy`: вызовы идут через объект-посредник,
который перенаправляет их в `InvocationHandler`. Статически видно лишь `invoke(proxy, method, args)`,
а реальная логика — в обработчике. Перехватываем так:

```javascript
Java.perform(function () {
  var P = Java.use('java.lang.reflect.Proxy');
  var H = Java.use('java.lang.reflect.InvocationHandler');
  H.invoke.implementation = function (proxy, method, args) {
    console.log('proxy->' + method.getName() + '(' + args + ')');
    return this.invoke(proxy, method, args);
  };
});
```

Так восстанавливается цепочка «кто кого вызывает» за прокси. Это дополняет перехват
`Class.forName` и `Method.invoke`.

## Расшифровка строк из ресурсов

Иногда имя метода лежит не в коде, а в `strings.xml` или в ассетах. Тогда путь такой: найти
идентификатор ресурса, достать значение, подставить в вызов. Команда для быстрого поиска:

```bash
$ aapt2 dump resources app.apk | grep -i 'check\|secret'
resource 0x7f0b0012 string/check_name: "check"
```

Получив строку, сопоставляем её с вызовом `getMethod("check")` — и вот скрытая точка входа найдена.
Автоматизируют это скриптом: собирают все строки из ресурсов и все `forName/getMethod` из smali,
а затем ищут пересечения.

## Как автоматизировать сбор имён

Для крупных приложений пишут разбор по всем smali-файлам:

```bash
$ grep -rn 'const-string' out/sources | grep -iE 'method|class|check' | wc -l
142
```

Затем скрипт складывает конкатенации (`const-string` + `StringBuilder.append`) и выводит готовые
строки. Так получают список всех имён, уходящих в reflection, без ручного перебора. Результат
сверяют с декомпилированным кодом — теперь методы видны статически.

## Проверка результата

Критерий успеха — имя метода больше не «секрет»: вы нашли класс, нашли метод и читаете его
логику напрямую. Если после перехвата имена всё ещё обрывочны, значит строки собираются целой
функцией-расшифровщиком; тогда её эмулируют или трассируют, а полученные строки логируют в файл,
чтобы использовать офлайн.

## Чек-лист по раскрытию reflection

- Найти точки `Class.forName` / `getMethod` / `getField`.
- Понять, как формируется имя (константы, ресурсы, decrypt).
- Сложить имя скриптом или перехватить в рантайме.
- Сопоставить имя с декомпилированным методом.
- Прочитать логику уже как обычный код.

## Что делать, если перехват не срабатывает

Если Frida-хук не видит вызов, проверьте три вещи: класс ещё не загружен (поставьте хук до
создания объекта), используется нативный JNI-вызов (нужен перехват `RegisterNatives`), либо
работает anti-Frida-защита (сначала нейтрализуйте детект). В последнем случае помогает перехват
`dlopen`/`dlsym` и проверка карты памяти процесса на наличие `frida-agent`.

## Reflection в нативном коде

Reflection бывает и на уровне JNI: нативный код вызывает `CallObjectMethod` по имени, полученному
из C-строки. Java-хуки здесь не видят вызов. Тогда перехватывают JNI-таблицу: `FindClass`,
`GetMethodID`, `CallObjectMethod`. Через Frida это делается по адресам из `JNIEnv`, а через
статику — поиском `GetMethodID` в декомпиляции `.so`. Результат тот же: мы видим имя метода и
класс, к которому он относится, и дальше работаем с ними напрямую. Так закрывается последний
пробел, когда часть логики уехала в нативный слой ради сокрытия от анализа DEX.

## Практический вывод по reflection

Reflection — это способ спрятать логику, но не способ её удалить. В рантайме все имена становятся
известны, и именно на этом строится вся работа. Начинаем с поиска точек reflection в smali и
декомпиляции; затем выясняем, как формируется имя — константами, ресурсами или функцией-расшифровщиком.
Для простых случаев хватает скрипта, складывающего части; для сложных — перехват `Class.forName`
и `Method.invoke` через Frida. Полученные имена сопоставляем с кодом и читаем его уже статически.
Если часть логики ушла в нативный слой, перехватываем JNI-таблицу. В итоге «растворённая» логика
снова становится набором обычных методов, которые можно анализировать привычными инструментами.

## Что мы теперь знаем

- Reflection вызывает методы по имени-строке.
- Имя можно формировать динамически — статически не видно.
- Признаки — Class.forName/getMethod/getField.
- Имена раскрывают скриптом, Frida или эмуляцией.
- Обфускаторы комбинируют reflection с шифрованием строк.
