## Зачем дампить DEX из памяти

Упаковщик (packer, «shell», «защита от реверса») решает одну задачу: не дать вам увидеть настоящий байткод. В APK лежит маленький загрузчик, который при старте расшифровывает реальные DEX и отдаёт их виртуальной машине Android — но делает это в памяти, а не на диске. Статический `jadx` показывает вам только загрузчик: десятки классов с именами вроде `StubApp`, `ShellApplication`, `a.a.a`. Реальная логика — в расшифрованных DEX, которые лежат в heap-памяти запущенного процесса.

Идея дампа проста: если VM уже загрузила классы, значит валидные DEX-структуры существуют в памяти. Достаточно найти их там и записать на диск. `frida-dexdump` — самый удобный инструмент для этого: он подключается к процессу, сканирует память в поисках заголовка DEX (`dex\n035\0`), валидирует структуру по размеру из заголовка и сохраняет каждый найденный DEX отдельным файлом.

Важно понимать, что упаковщики делятся на два лагеря. «Мягкие» просто зашифровали DEX и расшифровывают целиком — такие дампятся за один проход. «Жёсткие» (например, коммерческие DexGuard-подобные, а также VMP) декодируют методы лениво, по мере вызова, и в памяти никогда не лежит полный DEX. Для них дамп тоже работает, но только для уже вызванных методов, поэтому часто нужно «прогреть» приложение — пройти по всем экранам, чтобы код загрузился.

## Инструменты и их отличия

- **frida-dexdump** — обёртка над Frida, сканирует память по magic DEX, работает из коробки: `frida-dexdump -U -f com.target.app`.
- **DexHunter** — Xposed-модуль, перехватывает загрузку классов и собирает DEX по мере декодирования; хорош для «жёстких» упаковщиков.
- **FART / Youpk** — модифицированные ART-рантаймы (собираются под AOSP), дампят на уровне `OpenDexFile`; самый надёжный, но требует кастомной прошивки.
- **objection** — `objection -g com.target.app explore` и затем `android hooking list classes`; полезен, чтобы понять, загрузились ли реальные классы.
- **Frida-скрипт вручную** — если готовые тулы падают, вы пишете свой сканер памяти через `Memory.scan`.

## Установка и подготовка

```bash
pip install frida-tools
pip install frida-dexdump
# проверим связку
frida --version
adb devices
# приложение должно быть установлено; запускать лучше без анти-хука
adb shell pm list packages | grep target
```

Если на устройстве анти-Frida (см. `mobile-frida-detection`), сначала нейтрализуйте его или используйте gadget-режим: подмените `libfrida-gadget.so` в APK и пересоберите (`apktool d`/`b`, затем подпись `apksigner`). В CTF чаще всего устройство не защищено, но на реальном пентесте защита — норма.

## Базовый сценарий: frida-dexdump

```bash
# -f: запустить приложение через frida (spawn), -U: USB-устройство
frida-dexdump -U -f com.example.protected -d /tmp/dex_out
```

Типичный вывод:

```
[*] Spawned com.example.protected (pid 4123)
[*] Searching memory for dex files...
[*] Found 4 dex files
[+] Saved: /tmp/dex_out/4123/0x7f3a0000.dex (size=1824KB)
[+] Saved: /tmp/dex_out/4123/0x7f5b0000.dex (size=352KB)
[+] Saved: /tmp/dex_out/4123/0x7f610000.dex (size=64KB)
[+] Saved: /tmp/dex_out/4123/0x7f630000.dex (size=12KB)
```

Первый, самый крупный файл — почти всегда основной код приложения. Проверяем magic:

```bash
for f in /tmp/dex_out/4123/*.dex; do
  printf '%s: ' "$f"; head -c 8 "$f" | xxd | head -1
done
# 00000000: 6465 780a 3033 3500  -> dex\n035\0
```

Теперь декомпилируем крупнейший:

```bash
jadx -d /tmp/jadx_src /tmp/dex_out/4123/0x7f3a0000.dex
# или сразу открыть в jadx-gui
jadx-gui /tmp/dex_out/4123/0x7f3a0000.dex
```

## Дамп при «жёстком» упаковщике

Если `frida-dexdump` находит только загрузчик, делаем «прогрев»:

```bash
# 1) подключаемся и держим процесс живым
frida -U -f com.example.protected --no-pause
# 2) в Frida-консоли прогреваем классы
%resume
# 3) вручную пройти по всем экранам приложения (автоматизация через adb input)
adb shell input tap 540 1200
adb shell input swipe 900 1500 100 1500 300
# 4) параллельно повторяем дамп
frida-dexdump -U -n com.example.protected -d /tmp/dex_out2
```

Для совсем упрямых случаев используем перехват загрузки:

```javascript
// hook_dex.js — печатаем путь к каждому открытому dex
Java.perform(function () {
  var DexFile = Java.use("dalvik.system.DexFile");
  DexFile.$init.overload('java.io.File').implementation = function (f) {
    console.log("[DexFile] " + f.getAbsolutePath());
    return this.$init(f);
  };
  var PathClassLoader = Java.use("dalvik.system.PathClassLoader");
  PathClassLoader.$init.overload('java.lang.String', 'java.lang.ClassLoader').implementation = function (p, c) {
    console.log("[PCL] " + p);
    return this.$init(p, c);
  };
});
```

```bash
frida -U -f com.example.protected -l hook_dex.js --no-pause
```

Иногда проще вытащить расшифрованный DEX прямо из `/data/data/<pkg>/` — некоторые упаковщики пишут его во внутренний каталог и забывают удалить:

```bash
adb shell run-as com.example.protected ls -la files/
adb shell run-as com.example.protected cat files/classes.dex > /tmp/leaked.dex
```

## Починка и валидация дампа

Дамп из памяти может быть «обрезан»: заголовок декларирует размер, но реально скопировано меньше. Проверяем и тримим по размеру из заголовка:

```python
import struct
data = open("/tmp/dex_out/4123/0x7f3a0000.dex","rb").read()
assert data[:4] == b"dex\n"
file_size = struct.unpack_from("<I", data, 0x20)[0]  # offset 32
print("declared:", file_size, "actual:", len(data))
open("/tmp/fixed.dex","wb").write(data[:file_size])
```

Также проверяем контрольную сумму (Adler-32) и подпись SHA-1 в заголовке — при несовпадении jadx ругается, но часто всё равно декомпилирует. Если DEX «склеен» с мусором, magic может встречаться несколько раз — `frida-dexdump` ищет все вхождения, но иногда валидным оказывается второе.

## Разбор дампа и анти-обфускация

После успешного дампа открываем в `jadx-gui`, включаем:
- **Deobfuscation** (переименование `a`, `b` в осмысленные),
- **Show bad code** (иногда помогает увидеть структуру),
- экспорт `.java` и поиск по строкам (`Ctrl+F`): URL, ключи, `http`, `api_key`.

Часто дамп содержит несколько DEX — мультидекс (метод >65k). Тогда логику разбивают между ними, и `jadx` умеет объединять: `jadx -d out file1.dex file2.dex`.

## Частые ошибки и подводные камни

- **Дамп пустой/только загрузчик** — не прогрет код или упаковщик ленивый: гоняйте по экранам и хукайте `DexFile`.
- **Frida не видит процесс** — приложение анти-Frida, или неправильная архитектура frida-server (проверьте `getprop ro.product.cpu.abi`).
- **Падает jadx на «invalid dex»** — обрежьте по `file_size` из заголовка и проверьте checksum.
- **Сохранён только один DEX** — увеличьте таймаут сканирования (`--timeout`) и повторите.
- **Классы есть, методов нет** — VMP: тела методов нативные/виртуализированы, дамп тут не поможет, нужен динамический анализ (`mobile-hooking-internals`).

## Сравнение подходов

| Инструмент | Метод | Плюсы | Минусы |
|------------|-------|-------|--------|
| frida-dexdump | скан памяти по magic | прост, без рута упаковщика | не видит ленивые методы |
| DexHunter | Xposed-хук загрузки | ловит «жёсткие» упаковщики | нужен Xposed/LSPosed |
| FART/Youpk | патч ART | максимальная полнота | кастомная прошивка |
| run-as + files/ | чтение внутреннего каталога | тривиально, если повезёт | работает редко |

## Что дальше / решение

Дамп DEX — это вход, а не выход. После извлечения: декомпилируйте в `jadx`, найдите ключевую логику (проверки лицензии, криптографию, endpoint'ы), а нативные части (`lib/*.so`) разбирайте отдельно (`mobile-native-so-deep`). Если код виртуализирован (VMP), переходите к динамике: хук методов и трассировка (`mobile-hooking-internals`). Для автоматизации прогрева и дампа в CI соберите скрипт: `adb shell monkey -p <pkg> 500` + периодический `frida-dexdump`.

## Автоматизация дампа и работа в CI

Ручной дамп быстро надоедает, если приложений много. Соберём скрипт, который ставит APK, прогревает приложение monkey-командами и периодически дампит память. Такой подход полезен на пентесте, когда нужно обработать десяток сборок, и в CTF, когда приложение долго грузит свои модули.

```bash
#!/usr/bin/env bash
set -euo pipefail
PKG="${1:?usage: dump.sh <package> <apk>}"
APK="$2"
OUT="/tmp/dexdump_$(date +%s)"

adb install -r "$APK"
# прогреваем приложение: случайные тапы и свайпы
adb shell monkey -p "$PKG" -v 500 >/dev/null 2>&1 &
MONKEY_PID=$!

# несколько проходов дампа с интервалом
for i in $(seq 1 5); do
  sleep 6
  frida-dexdump -U -n "$PKG" -d "$OUT/pass$i" || true
done
kill "$MONKEY_PID" 2>/dev/null || true

# собираем все уникальные dex по хешу
mkdir -p "$OUT/unique"
find "$OUT" -name '*.dex' -print0 | xargs -0 sha256sum | sort -u -k1,1 | awk '{print $2}' | while read -r f; do
  cp "$f" "$OUT/unique/$(basename "$f")"
done
echo "unique dex: $(ls "$OUT/unique" | wc -l)"
```

Несколько проходов важны, потому что упаковщик может расшифровывать код по частям: в первом проходе вы получите один набор методов, во втором — другой. Дедупликация по SHA-256 убирает одинаковые DEX, которые упаковщик держит в памяти постоянно.

## Дамп через FART и Youpk (продвинутый сценарий)

Когда Frida не справляется (сильный анти-хук, виртуализация), применяют модифицированные ART-рантаймы. **FART** — это пропатченный `libart.so`, который при каждом `OpenDexFile`/`DefineClass` сохраняет декодированный байткод на диск. **Youpk** делает то же самое, но автоматизирует сбор и поддерживает новые версии Android.

Процесс установки (упрощённо):
1. Скачиваем исходники Youpk под нужную версию AOSP.
2. Собираем пропатченный `libart.so` и пушим в `/system/lib64/`.
3. Перезагружаем устройство в режиме, где ART подменён.
4. Запускаем приложение — дампы появляются в `/data/data/<pkg>/` или в `/sdcard/`.

Плюс подхода — он видит даже ленивые методы, которые расшифровываются только при первом вызове. Минус — нужен root, кастомный рантайм и совместимость с версией Android. В CTF это редкость, но на серьёзном пентесте банковского приложения с VMP — рабочий вариант.

## Работа с мультидексом, odex и vdex

Современные приложения почти всегда мультидексные: методов больше 65536, и код разбит на `classes.dex`, `classes2.dex`, ... Для дампа это означает, что логика размазана по нескольким файлам. При декомпиляции передавайте их вместе, чтобы `jadx` собрал полную картину:

```bash
jadx -d /tmp/all_src /tmp/dex_out/unique/*.dex
```

Дополнительно на устройстве есть **odex/vdex** — результат AOT-компиляции. Иногда удобнее дампить не DEX, а вытащить уже скомпилированный машинный код из `oat` и дизассемблировать его (Ghidra, `objdump -D`). Это актуально, когда DEX обфусцирован, а скомпилированный код — нет. Но помните: AOT-код генерируется из того же DEX, поэтому восстановление логики из машинного кода сложнее, чем из байткода.

Ещё один путь — `vdex` содержит проверенный байткод, и если упаковщик не перешифровал его повторно, можно вытащить `classes.dex` прямо оттуда через `vdexExtractor`:

```bash
vdexExtractor -i /data/app/.../base.vdex -o /tmp/vdex_out --deps
```
