## Вопрос, с которого всё начинается

Упакованное приложение: на диске зашифрованный DEX, а настоящий код распаковывается в память при запуске. Ты знаешь, что код там, но как его оттуда достать — целиком, в пригодном для `jadx` виде?

## Наш пример: выгрузка DEX из памяти

Возьмём упакованное приложение и пройдём путь от запуска до готового к анализу DEX-файла. Инструмент — `frida-dexdump`, но сначала разберёмся, **как** он находит код, чтобы понимать его ограничения.

## Шаг 1: зачем дампить DEX

При статическом анализе упакованного APK мы видим только загрузчик. Настоящие классы появляются лишь в памяти — после того, как загрузчик расшифрует и загрузит DEX. Дамп решает две задачи:

- **Получить код** для `jadx`, которого нет на диске.
- **Увидеть то, что скрыто** от статического анализа: динамически подгружаемые модули, расшифрованные строки.

Дамп памяти — стандартный обход упаковщиков, применимый и к защитным, и к вредоносным приложениям.

## Шаг 2: как находят DEX в памяти

DEX-файл имеет строгий формат: он начинается с **магических байтов** — `dex\n` и версии (например, `035`), за которыми следует контрольная сумма и размер. По этой сигнатуре DEX ищут в памяти процесса:

1. Frida перечисляет диапазоны памяти (`Process.enumerateRanges`).
2. В каждом диапазоне ищет сигнатуру `64 65 78 0a` (`dex\n`).
3. Проверяет, что найденный заголовок согласован (размер, смещения).
4. Выгружает содержимое DEX в файл.

Такой поиск находит DEX независимо от того, как он был зашифрован на диске, — важен только факт, что он распакован в памяти.

## Практика: сканируем блоб сами

`frida-dexdump` — удобная обёртка, но принцип простой, и его стоит увидеть своими глазами. Представим «память» как один большой блоб байтов: в середине лежит настоящий DEX, вокруг — мусор. Найдём DEX по сигнатуре:

```python
import re, struct
data = b"\x00"*4096 + open("u1.dex","rb").read() + b"\x00"*2048
sig = b"dex\n035\x00"
for m in re.finditer(re.escape(sig), data):
    off = m.start()
    file_size = struct.unpack_from("<I", data, off+32)[0]
    print(f"found DEX magic at offset 0x{off:x}, header file_size={file_size}")
```

Вывод:

```
$ python3 scan.py
found DEX magic at offset 0x1000, header file_size=5528
```

Мы нашли сигнатуру на смещении `0x1000` и прочитали из заголовка реальный размер — `5528` байт. По паре «смещение + размер» DEX вырезается из блоба. Именно это и делает `frida-dexdump`: перечисляет диапазоны памяти процесса, ищет `dex\n` и выгружает найденное. В живой памяти сигнатур бывает много, часть — мусор, поэтому инструмент дополнительно проверяет согласованность заголовка. Убедимся, что вырезанный файл — настоящий DEX:

```
$ file u1.dex
u1.dex: Dalvik dex file version 035
```

## Шаг 3: запуск frida-dexdump

`frida-dexdump` автоматизирует весь процесс. Устанавливается через pip:

```
$ pip install frida-dexdump
```

Запуск по имени пакета (приложение будет запущено заново):

```
$ frida-dexdump -U -f com.target.app
```

Флаг `-U` означает «устройство по USB», а `-f` перезапускает приложение с самого старта — так перехватывается распаковка в первые секунды.

Или по уже работающему процессу:

```
$ frida-dexdump -U -n com.target.app
```

Инструмент перебирает диапазоны памяти, находит DEX и сохраняет их в текущую директорию с именами вида `com.target.app_12345.dex`. Если приложение использует упаковщик с анти-Frida — сначала обходят детект (см. `mobile-frida-detection`), иначе приложение закроется до распаковки.

## Шаг 4: проверка дампа

После дампа проверяем результат:

```
$ file com.target.app_*.dex
com.target.app_12345.dex: Dalvik dex file version 035
```

`file` должен опознать Dalvik DEX. Дальше открываем в `jadx`:

```
$ jadx -d out com.target.app_12345.dex
```

Если `jadx` показывает настоящие классы приложения (а не обёртку) — дамп удался. Критерий простой: посчитайте классы и посмотрите имена пакетов. На живом примере:

```
$ jadx --no-res -d out dump.dex
$ find out -name '*.java' | wc -l
5
$ find out -name '*.java' | head -2
out/sources/sg/vantagepoint/uncrackable1/MainActivity.java
out/sources/sg/vantagepoint/uncrackable1/a.java
```

Осмысленные имена пакетов и десятки классов — признак успеха. Если же `jadx` показал один класс-загрузчик, значит дамп неполный или это ещё не распакованный код. Если файл повреждён или пуст — переходим к починке.

## Шаг 5: починка дампа

Иногда дамп неполный: упаковщик портит заголовок DEX или разбивает код на несколько сегментов. Признаки — `jadx` ругается на заголовок, файл обрезан, классы «битые». Что делать:

- **Собрать DEX из нескольких дампов.** Один логический DEX может лежать в памяти частями — их объединяют.
- **Починить заголовок.** Магические байты и размеры можно восстановить, зная формат DEX.
- **Снять защиту и дампить снова.** Иногда дамп получается корректным только после обхода анти-тампер/анти-debug.
- **Использовать альтернативные инструменты** (DexHunter, FART), которые умеют собирать DEX из ART-структур, а не по сигнатуре.

Для учебных и большинства реальных задач достаточно `frida-dexdump`; починка нужна для усиленных упаковщиков.

Разница между подходами принципиальная. Поиск по сигнатуре (`frida-dexdump`) работает, пока заголовок DEX цел. Инструменты, собирающие DEX из структур ART (`DexHunter`, `FART`), читают уже загруженный класс, поэтому находят код даже при испорченном заголовке — но сложнее в настройке и медленнее.

## Шаг 6: типичные проблемы

- **Дамп пустой.** Упаковщик распаковывает код позже — дайте приложению поработать и повторите дамп.
- **Приложение закрывается.** Сработала анти-Frida/анти-тампер — обходите защиты.
- **Много мелких DEX.** Нормально для упаковщиков; смотрите их вместе.
- **`jadx` не открывает.** Проверьте магические байты; возможно, нужна починка.
- **Строки зашифрованы.** Дамп даёт код, но строки могут расшифровываться позже — смотрите их в памяти отдельно.

## Шаг 7: полный рабочий процесс

1. **Убедиться, что APK упакован** (см. `mobile-android-packers`).
2. **Обойти анти-Frida** (нестандартный порт, spawn).
3. **Запустить `frida-dexdump`.**
4. **Проверить дампы** через `file` и `jadx`.
5. **Починить/объединить** при необходимости.
6. **Проанализировать** полученный код.

## Что мы теперь знаем

По-простому:

1. Дамп DEX нужен, когда код есть только в памяти упакованного приложения.
2. DEX находят по магическим байтам (`dex\n`) в диапазонах памяти.
3. `frida-dexdump` автоматизирует поиск и выгрузку.
4. Дамп проверяют через `file` и `jadx`, при необходимости чинят.
5. Сначала обходят анти-Frida/анти-тампер, потом дампят.

## На что смотреть дальше

- **Дайте приложению распаковаться.** Дамп сразу после старта может быть пустым.
- **Обходите анти-Frida.** Иначе приложение закроется.
- **Проверяйте каждый дамп.** Часть из них — мусор: сигнатура `dex\n` может встретиться и в случайных данных, поэтому сверяйте размер из заголовка.
- **Починка — для усиленных упаковщиков.** Обычно хватает готового дампа.
