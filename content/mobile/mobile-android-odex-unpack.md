## Вопрос, с которого всё начинается

В прошлом уроке мы выяснили, что байткод лежит в `.vdex`. Теперь конкретная задача:
у нас на руках системное приложение, у которого в APK нет `classes.dex` (или он
обрезан), а рядом лежит `base.vdex`. **Как получить из него читаемый dex и открыть в
jadx?**

## Наш пример: системное приложение без dex в APK

Скопируем с устройства пару файлов:

```bash
$ adb pull /system/priv-app/SecretApp/SecretApp.apk .
$ adb pull /system/priv-app/SecretApp/oat/arm64/SecretApp.vdex .
```

Смотрим APK: `unzip -l SecretApp.apk` показывает ресурсы, но `classes.dex` отсутствует
или содержит заглушку. Значит, код — в `.vdex`.

## Шаг 1: чем распаковывают vdex

Инструмент называется **vdexExtractor**. Он читает контейнер `.vdex` и извлекает
вложенные dex-файлы:

```bash
$ vdexExtractor -i SecretApp.vdex -o out/ --deps
[+] Processing 'SecretApp.vdex'
[+] Extracted 2 dex files to 'out/'
$ ls out/
SecretApp_classes.dex  SecretApp_classes2.dex
```

На выходе — настоящие dex-файлы. Теперь их открывает любой декомпилятор:

```bash
$ jadx -d src out/SecretApp_classes.dex
```

## Шаг 2: если есть только odex

Иногда `.vdex` не сохранился, а есть `.odex` (формат OAT). Тогда порядок такой:
сначала из `.odex` вытаскивают встроенный dex. Для этого есть несколько путей:
`vdexExtractor` умеет работать и с oat-контейнером, а старые артефакты разбирают
`oat2dex`:

```bash
$ oat2dex out/SecretApp.odex out/
$ ls out/
SecretApp.dex
```

Важно: результат зависит от версии Android и формата OAT. Если инструмент не понимает
контейнер, смотри версию в заголовке:

```bash
$ xxd -l 8 SecretApp.odex
00000000: 6f61 7403 3033 3900                      oat.039.
```

`oat` в начале и номер версии подскажут, какой инструмент подойдёт.

## Шаг 3: почему dex может быть неполным

Бывает, что `.vdex` содержит только **часть** классов, а остальные компилируются
позже. Причина — профильная компиляция: система держит в байткоде то, что редко
вызывается. Тогда полный код собирают из двух источников: dex из APK плюс dex из
`.vdex`. Проверяй оба и сверяй хеши классов.

## Шаг 4: deodex и пересборка

Если цель — **модифицировать** приложение (например, пропатчить проверку), извлечённый
dex нужно вернуть в APK. Процесс называют **deodex**:

```bash
$ zip -j SecretApp.apk out/SecretApp_classes.dex
$ apktool b SecretApp -o patched.apk
```

Но помни: системные приложения подписаны платформенным ключом, и просто пересобрать их
с обычной подписью не выйдет — установка будет отклонена. Deodex нужен скорее для
анализа, чем для подмены.

## Шаг 5: практический чек-лист

1. Есть `.vdex` → `vdexExtractor`, сразу получаешь dex.
2. Есть только `.odex` → сначала определить версию OAT, потом `oat2dex`/`vdexExtractor`.
3. Код неполный → сложить dex из APK и из vdex.
4. Нужен анализ → jadx/Ghidra; нужна подмена → deodex + пересборка (с оговорками).

## Шаг 6: split APK и multidex

Современные приложения почти никогда не состоят из одного dex. Их код разбит на
несколько файлов — **multidex**, — а ресурсы и нативные библиотеки вынесены в
отдельные **split APK**:

```bash
$ unzip -l SecretApp.apk | grep -E "classes|split"
  4021234  classes.dex
  3012345  classes2.dex
```

Каждый `classesN.dex` — отдельный кусок кода. Если декомпилировать только
`classes.dex`, половина классов не найдётся. Поэтому при извлечении из `.vdex`
получается сразу несколько файлов, и их надо анализировать вместе:

```bash
$ ls out/
SecretApp_classes.dex  SecretApp_classes2.dex
```

Дальше — либо открыть оба в jadx (он умеет объединять), либо конвертировать в исходник
и работать с обоими каталогами.

Отдельная тонкость — **соответствие версий**. Если `.vdex` снят с версии 3.1, а APK —
от 3.2, имена классов разойдутся, и анализ запутается. Перед началом всегда сверяй
`versionName`/`versionCode` из манифеста с тем, что на устройстве.

## Если не сработало

* Инструмент не понимает контейнер — проверь заголовок (`xxd -l 8`) и версию OAT;
  для новых версий бери свежий `vdexExtractor`, для старых — `oat2dex`.
* Dex обфусцирован — извлечение даст код, но с именами вида `a`, `b`, `c`; это норма,
  дальше нужен динамический анализ или деобфускатор.
* Классы всё равно не находятся — возможно, код грузится динамически
  (`DexClassLoader`), и в статике его просто нет.

## Что проверить на реальном устройстве

Рабочий порядок такой: сначала найди все артефакты, затем определи версию контейнера,
затем подбери инструмент. Не начинай с инструмента — начинай с инвентаря. Собери
`.apk`, `.vdex` и `.odex` одного и того же приложения и одной версии.

```bash
$ adb shell ls /data/app/~~x/com.example.app-y/oat/arm64/
$ adb pull /data/app/~~x/com.example.app-y/oat/arm64/base.vdex .
```

После извлечения dex обязательно сверь, что получилось столько файлов, сколько
`classesN.dex` было в APK. Если меньше — часть кода осталась в другом артефакте, и
надо доизвлечь. Если больше — возможно, vdex содержит и динамически загружаемые dex.

Дальше открывай результат в декомпиляторе и проверяй полноту: ищи классы, которые
ожидаешь увидеть (Activity, сервисы, сетевой слой). Если их нет, значит, код приходит
из другого места — например, из динамической загрузки или из split-модуля.

## А если код зашифрован

Бывает так, что ни в APK, ни в `.vdex` читаемого кода нет: приложение упаковано
защитным обфускатором, и настоящий dex собирается уже в памяти при запуске. Тогда
статический путь бессилен — сколько ни извлекай из `.vdex`, там будет только
загрузчик. Решение — динамическое: запустить приложение под отладчиком и снять дамп
памяти в тот момент, когда оно расшифровало свой код. После этого dex вытаскивают из
дампа по сигнатуре `dex\n035` и открывают в декомпиляторе. Это отдельная тема, но
полезно знать: `.vdex` — источник байткода только тогда, когда код не расшифровывается
на лету.

## Итог по инструментам

Запомни связку: `.vdex` разбирает `vdexExtractor`, `.odex` (OAT) — `oat2dex` или
свежий `vdexExtractor`, а полученный dex открывают `jadx` или `Ghidra`. Этого набора
хватает в большинстве практических задач. Если инструмент не понимает контейнер,
дело почти всегда в версии формата: смотри заголовок и бери подходящую сборку. Так
ты никогда не останешься без кода, даже если в APK его нет.

Проверяй результат на каждом шаге: если dex извлёкся неполным, вернись и добавь второй источник, а не двигайся дальше с дырявым набором классов.

## Что мы теперь знаем

- `vdexExtractor` извлекает dex из `.vdex`; `oat2dex` работает с `.odex`.
- Версию контейнера видно в заголовке (`oat.039`).
- Байткод может быть разделён между APK и vdex.
- Deodex позволяет вернуть dex в APK, но системную подпись не подделать.
- Для реверса достаточно извлечь dex и открыть в декомпиляторе.

Мы научились доставать код из любых артефактов. Дальше посмотрим на нестандартную
поставку — **Instant Apps**, где приложение не устанавливают целиком. А пока запомни:
**`.vdex` — источник dex; vdexExtractor + jadx закрывают вопрос «где код»**.
