## Вопрос, с которого всё начинается

Ты нашёл в приложении проверку, которая блокирует нужную функцию: например, «premium=false» или
«root_detected=true». Нужно, чтобы приложение думало иначе. Переписывать APK с нуля — не вариант.
Есть проверенный конвейер: декомпилировать, поправить один байткод, собрать обратно и подписать.
Разберём его по шагам на конкретном примере.

## Наш пример: флаг платной функции

У нас есть `app.apk`. В декомпилированном виде находим метод, который возвращает признак
«платный аккаунт». Мы хотим, чтобы он всегда возвращал «да». Начинаем с декомпиляции:

```bash
$ apktool d app.apk -o app_src
I: Using Apktool 2.9.3
I: Loading resource table...
I: Decoding AndroidManifest.xml...
I: Copying assets and libs...
```

`apktool d` распаковал APK в каталог `app_src`: там лежат `smali/` (байткод в читаемом виде),
`res/` (ресурсы) и `AndroidManifest.xml`. Разберём, что такое smali и как его править.

## Шаг 1: что такое smali

**Smali** — текстовое представление байткода Dalvik. Каждая инструкция DEX записана строкой
ассемблера. Это не исходник на Java, но читается достаточно понятно: видно вызовы методов,
сравнения, возвраты. Правка smali = правка байткода напрямую.

```bash
$ sed -n '1,12p' app_src/smali/com/example/app/Premium.smali
.method public isPremium()Z
    .locals 1
    const/4 v0, 0x0
    return v0
.end method
```

Метод `isPremium` возвращает `0x0` — «ложь». Ровно то, что нам мешает.

## Шаг 2: правим байткод

Чтобы метод всегда возвращал «истина», меняем константу `0x0` на `0x1`:

```bash
$ sed -i 's/const\/4 v0, 0x0/const\/4 v0, 0x1/' app_src/smali/com/example/app/Premium.smali
$ sed -n '1,5p' app_src/smali/com/example/app/Premium.smali
.method public isPremium()Z
    .locals 1
    const/4 v0, 0x1
    return v0
.end method
```

Одна строка — и метод «всегда premium». Так же правят проверки root, jailbreak, отладки,
лицензии. Главное — найти нужный метод и понять, что он возвращает.

## Шаг 3: собираем обратно

```bash
$ apktool b app_src -o app_patched.apk
I: Building resources...
I: Building apk file...
```

На выходе — `app_patched.apk`. Но его **нельзя** поставить как есть: подпись apktool невалидна
(сборка изменена), и Android откажется устанавливать. Нужен следующий шаг.

## Шаг 4: выравнивание zipalign

**zipalign** выравнивает несжатые данные в APK по границам, чтобы система читала их быстрее.
Современный Android требует выравнивания для установки. Делаем до подписи:

```bash
$ zipalign -p -f 4 app_patched.apk app_aligned.apk
```

Теперь архив выровнен, можно подписывать.

## Шаг 5: подпись apksigner

```bash
$ apksigner sign --ks my.keystore --ks-pass pass:secret \
    --out app_signed.apk app_aligned.apk
$ apksigner verify app_signed.apk
Verifies
Verified using v2 scheme (APK Signature Scheme v2): true
```

`apksigner` подписывает APK нашим ключом. Проверка `verify` подтверждает, что подпись валидна.
Важно: подпись будет **другой**, чем у оригинала (другой ключ), поэтому приложения с проверкой
подписи заметят подмену — это мы разбирали в `mobile-android-signature-spoof`.

## Шаг 6: установка и подводные камни

```bash
$ adb install -r app_signed.apk
Success
```

`-r` переустанавливает поверх. Частые проблемы: подпись не совпадает со старой (нужно удалить
приложение), приложение защищено от перепаковки (проверка подписи/хеша), используется split-APK
(нужно ставить все части). Для обхода защиты комбинируют патч smali с хуками в рантайме.

## Шаг 7: практика

В файле `smali_patch.txt` — фрагмент пропатченного метода. Одна строка содержит флаг (метка
патча). Найди её через `grep` и запиши флаг в `found.txt`.

## Шаг 8: как найти нужный метод

Прежде чем патчить, метод нужно найти. Ориентиры: строки в `strings.xml` и `smali/` («premium»,
«license», «root», «tamper»), вызовы системных API (`PackageManager`, `Build.TAGS`, `File.exists`),
имя класса, которое выдаёт назначение. Часто помогает `grep -rn 'const/4 v0, 0x0' smali/` — поиск
методов, возвращающих «ложь», среди которых прячется проверка. Полезно сопоставлять smali с
декомпилированным Java (jadx) — так логика видна быстрее, а правку всё равно делают в smali.

## Шаг 9: правка не только констант

Патчить можно не только возвращаемое значение. Можно инвертировать условие (`if-eqz` → `if-nez`),
заменить вызов `System.exit` на `return-void`, удалить проверку целиком, вернуть ранний `return`.
Иногда нужно вставить вызов логгера, чтобы понять, что происходит, — в smali это делается
добавлением `const-string` и `invoke-static` на `Log.d`. Главное правило: сохранять сигнатуру метода
и количество регистров, иначе верификатор байткода (dalvik verifier) отвергнет APK при установке.

## Шаг 10: про `.locals` и регистры

Строка `.locals N` в начале метода объявляет число локальных регистров. Если ты добавляешь
инструкции, использующие новые регистры, увеличь `.locals`. Ошибка здесь — классическая причина
`INSTALL_FAILED_DEXOPT` или падения при запуске. Также помни, что регистры нумеруются с конца:
`.locals 1` даёт `v0`. Когда метод использует и параметры, и локальные, применяют `.registers` —
общее число регистров, включая аргументы. Понимание этой арифметики отличает аккуратный патч от
случайного.

## Шаг 11: подпись, версии схем и совместимость

`apksigner` умеет подписывать схемами v1, v2, v3 и v4. v2/v3 подписывают APK целиком и быстрее
проверяются, v1 — по записям ZIP. Для старых устройств нужна v1, для новых достаточно v2/v3.
Если приложение проверяет отпечаток сертификата, любая переподпись другим ключом это заметит — тут
на помощь приходит динамический обход. Ещё нюанс: некоторые сборки содержат несколько APK
(split), и подписывать/ставить нужно **все** части согласованно.

## Шаг 12: когда патч не работает

Бывает, что после патча приложение всё равно ведёт себя как раньше. Причины: проверка дублируется
в нативном коде (`.so`), значение вычисляется на сервере, включена защита от перепаковки
(проверка подписи/хеша), используется обфускация, где имена методов неочевидны. Тогда переходят
на комбинированный подход: патч smali для клиентской логики плюс хуки в рантайме для нативных и
серверных проверок. Именно поэтому уроки про нативный хукинг идут сразу следом.

## Разбор глубже: чтение smali как навык

Правка smali требует умения его читать. Начни с простого: найди метод, посмотри его `.locals`,
пройди по инструкциям. `const/4 v0, 0x1` кладёт единицу в регистр, `return v0` возвращает её.
`if-eqz v0, :cond` — переход, если регистр равен нулю; `:cond` — метка. `invoke-virtual` вызывает
метод объекта, `invoke-static` — статический. Этого минимума хватает, чтобы понимать большинство
проверок и правок. Полный набор инструкций Dalvik описан в документации, но на практике 90%
работы — это константы, условия и вызовы.

Полезный приём — параллельно смотреть декомпилированный Java (jadx): логика читается быстрее, а
точную правку делают в smali. Сопоставляя одно с другим, ты быстро учишься узнавать паттерны:
проверка флага, сравнение строк, вызов `System.exit`, возврат булева значения.

## Разбор глубже: как не сломать APK

Три частые причины поломки: неверное число регистров (`.locals`/`.registers`), некорректный тип
инструкции для регистра (например, `move` вместо `move-object`), разрезанный посередине метод.
После сборки `apktool b` иногда полезно прогнать `apktool` ещё раз (декодировать результат) —
если он читается, структура цела. А `apksigner verify` подтверждает, что подпись валидна. Хорошая
привычка: сначала собрать **без правок** и убедиться, что исходный APK собирается и подписывается;
только потом вносить изменения — так ты сразу отделяешь ошибку инструмента от ошибки патча.

## Разбор глубже: этика и границы

Перепаковка и патч — мощные приёмы, но применять их можно только в рамках разрешённого теста.
На реальных приложениях это может нарушать лицензию и закон. В учебной среде и CTF это
нормальная практика, и именно там отрабатываются навыки. Запомни разделение: техника — это
инструмент, а законность определяет контекст. Пентестер всегда работает в рамках договора и
скоупа, а не «потому что получилось».

## Что мы теперь знаем

- apktool d распаковывает APK в smali, ресурсы и манифест.
- Smali — читаемое представление байткода Dalvik.
- Патч проверки = правка одной инструкции (например, `const/4 v0, 0x1`).
- apktool b собирает APK обратно, но он не подписан.
- zipalign выравнивает, apksigner подписывает — тогда установка проходит.
- Переподпись меняет отпечаток; защита от перепаковки это заметит.
