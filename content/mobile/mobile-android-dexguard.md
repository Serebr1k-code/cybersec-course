## Вопрос, с которого всё начинается

JADX выдал код, в котором нет ни одного осмысленного имени: классы `a.a`, методы `b()`. Строки
не читаются, часть кода «пропала». Вы подозреваете коммерческий обфускатор. Как понять, что
это DexGuard, и как всё-таки добраться до логики?

## Наш пример: app.apk, защищённый DexGuard

Первые наблюдения:

```bash
$ jadx -d out app.apk 2>&1 | tail -3
INFO - done
$ find out/sources -name '*.java' | head
out/sources/a/a.java
out/sources/a/b.java
```

Имена — одна буква. Логика спрятана. Разберём слои защиты.

## Шаг 1: что защищает DexGuard

DexGuard — коммерческий обфускатор для Android. Он делает несколько вещей: шифрует строки,
переименовывает классы и методы, удаляет отладочную информацию, вставляет проверки среды (RASP —
Runtime Application Self-Protection), иногда шифрует ресурсы. Каждый слой надо снимать отдельно.

## Шаг 2: строки

Строки шифруются, и в коде остаются вызовы дешифратора. Найти его сложно из-за переименования,
но помогает динамика: перехватываем частые вызовы и смотрим, где возвращается читаемый текст.
Иногда DexGuard оставляет нативный дешифратор — тогда идём в `.so`.

## Шаг 3: имена

Переименование не мешает, если работать по структуре: кто вызывает `Runtime.exec`, `Cipher`,
`HttpURLConnection`. Поэтому анализ ведут от системных API, а не от имён. Помогает и
`--deobf` в JADX, и сопоставление с оригинальной библиотекой.

## Шаг 4: рантайм-дамп

Самый надёжный путь против обфускации строк и скрытых классов — дамп в рантайме. Frida-скрипт
обходит все загруженные классы и печатает их методы; а `frida-dexdump` выгружает DEX прямо из
памяти процесса, где строки уже расшифрованы:

```bash
$ frida-dexdump -U -f com.example
```

Так получают «распакованный» DEX, который затем читают JADX.

## Шаг 5: RASP

DexGuard вставляет проверки: root, отладчик, хуки, эмулятор. При обнаружении приложение
завершается. Обход: хукать сами проверки (вернуть «чисто»), либо патчить их. Сначала надо найти
проверку — она часто срабатывает при старте, поэтому ловят момент завершения и идут назад.

## Шаг 6: автоматизация

Собирают скрипт, который: обходит проверки RASP, дампит строки, выгружает DEX. Это стандартный
пайплайн для защищённых приложений. Frida-скрипты комбинируют в один.

## Шаг 7: границы

DexGuard повышает стоимость анализа, но не делает его невозможным: расшифровка всё равно
происходит в рантайме, и мы можем её перехватить. Поэтому защита — про время и усилия, а не
абсолютная.

## Что мы теперь знаем

- DexGuard шифрует строки, переименовывает, ставит RASP.
- Анализ ведут от системных API, не от имён.
- Рантайм-дамп даёт расшифрованный DEX.
- RASP-проверки хукают или патчат.
- Защита повышает стоимость, но обходится.

## Слои DexGuard и правильный порядок снятия

DexGuard накладывает несколько независимых слоёв, и снимать их надо в правильном порядке, иначе
один слой будет мешать работать с другим.

1. **RASP** — проверки среды. Их снимают первыми, иначе приложение завершится под инструментом.
2. **Шифрование строк** — дешифратор нужно либо перехватить, либо найти.
3. **Переименование** — не мешает исполнению, но мешает читать; снимают деобфускацией.
4. **Удаление отладочной информации** — затрудняет отладку; обходят динамикой.

Если начать с деобфускации имён, но не снять RASP, — приложение закроется при первом запуске под
Frida. Поэтому порядок «среда → строки → имена» экономит время.

## Деобфускация имён: --deobf и mapping

Переименованные классы `a.a` и методы `b()` не несут смысла, но структура кода остаётся. JADX
умеет генерировать осмысленные синтетические имена флагом `--deobf`.

```bash
$ jadx --deobf -d out app.apk
```

Если у вас есть `mapping.txt` (файл соответствий, который разработчик хранит для расшифровки
стектрейсов), деобфускация становится точной: `retrace` и подобные инструменты восстанавливают
оригинальные имена.

```bash
$ retrace mapping.txt obfuscated_stacktrace.txt
```

На практике `mapping.txt` в открытом виде почти не встречается, поэтому основной приём — работать
от системных API. Кто вызывает `Runtime.exec`, `Cipher.getInstance`, `HttpURLConnection` — вот где
логика, независимо от имён.

## Строки: нативный и Java-дешифратор

DexGuard шифрует строковые константы, оставляя в коде вызовы дешифратора. Найти его можно двумя
путями.

Первый — Java-дешифратор. Он выглядит как метод, который принимает массив байт или строку и
возвращает строку, часто вызываемый повсеместно. Найти его помогает частотный анализ: метод,
который вызывается тысячи раз, — почти наверняка дешифратор.

```bash
$ grep -rn 'new String(' out/sources | wc -l
```

Второй — нативный дешифратор в `.so`. Тогда строки расшифровываются в C-коде, и в DEX видны только
вызовы нативных методов. Здесь анализ уходит в нативную библиотеку: ищем `JNIEXPORT`-функции,
которые возвращают строку, и разбираем их в Ghidra/IDA.

Самый быстрый способ обойти оба варианта — дамп в рантайме, когда строки уже расшифрованы (см.
ниже).

## RASP в DexGuard и его нейтрализация

Проверки DexGuard — это обычно вызовы, которые возвращают «среда чистая/грязная» и в зависимости
от этого завершают приложение. Типовые места: проверка root, отладчика, наличия хуков, эмулятора
и целостности APK.

Практический приём: поймать момент завершения и пойти назад по стеку. Запустите приложение под
Frida с хуком на `System.exit` и `Process.killProcess` — и увидите, кто вызвал завершение.

```javascript
Java.perform(function () {
  var S = Java.use('java.lang.System');
  S.exit.implementation = function (code) {
    console.log('exit(' + code + ')');
    console.log(Java.use('android.util.Log').getStackTraceString(
      Java.use('java.lang.Exception').$new()));
  };
});
```

Стек покажет метод-проверку. Дальше его либо хукают (возвращают «чисто»), либо патчат в smali.

## Рантайм-дамп как универсальный обход

Когда слоёв много, самый надёжный путь — не снимать их по одному, а дампнуть DEX из памяти, где
строки уже расшифрованы, а классы загружены.

```bash
$ frida-dexdump -U -f com.example
[+] Dumped classes.dex (2.1 MB)
```

Полученный DEX читают JADX — и строки в нём часто оказываются в открытом виде, потому что дамп
берёт состояние памяти после дешифровки. Это не отменяет переименование, но снимает слой строк
целиком.

## Таблица: слой и инструмент

| Слой DexGuard | Признак | Инструмент/приём |
|---|---|---|
| RASP | завершение под Frida | хук System.exit, возврат «чисто» |
| строки | вызовы дешифратора | дамп памяти, частотный анализ |
| имена | a.a, b() | jadx --deobf, mapping.txt |
| отладка | нет имён в стектрейсах | динамика, Frida |
| целостность | проверка хеша/подписи | патч ожидаемого значения |

## Если не сработало

Если приложение завершается даже до вашего хука `System.exit`, — проверка срабатывает раньше, чем
Frida успевает подгрузить скрипт. Используйте `--no-pause` и спавн-режим (`-f`), либо ранний хук
через `frida-gadget`, встроенный в APK.

Если деобфускация `--deobf` не помогает читать код, — это ожидаемо: имена синтетические, а не
оригинальные. Читайте по структуре и системным вызовам.

Если строки всё равно нечитаемы после дампа, — вероятно, они расшифровываются по мере
использования (лениво). Поживите в приложении, пройдите по экранам и дампите позже.

## Ограничения

DexGuard повышает стоимость анализа, но не делает его невозможным: расшифровка происходит в
рантайме, и её можно перехватить. Цель защиты — не абсолютная стойкость, а увеличение времени и
усилий атакующего.

Важно и то, что обход защиты — законная часть авторизованного пентеста или анализа собственного
приложения. Использовать эти приёмы для распространения взломанных сборок или обхода лицензий
нельзя.

## Мини-практика: снять строки и имена за один проход

Разберём практический пайплайн: сначала строки, потом имена, затем чтение логики.

Строки. Если дешифратор нативный, самый быстрый путь — дамп после дешифровки. Если Java-метод —
его можно перехватить и печатать результаты.

```javascript
Java.perform(function () {
  var cls = Java.use('a.a');
  // метод-дешифратор обычно вызывается очень часто
  cls.a.implementation = function (arg) {
    var out = this.a(arg);
    console.log('decrypted: ' + out);
    return out;
  };
});
```

Вывод покажет расшифрованные строки по мере использования — включая URL, ключи и сообщения.

Имена. После того как строки видны, ориентируемся на системные вызовы, а не на имена. Ищем, кто
работает с `Cipher`, `HttpURLConnection`, `Runtime.exec`. По окружению восстанавливаем смысл
метода.

```bash
$ grep -rn 'Cipher.getInstance' out/sources | head
a/b.java:44: Cipher.getInstance("AES/GCM/NoPadding")
```

Теперь мы знаем, что `a.b` — крипто-код, хотя имя ничего не говорит.

## Частые ошибки

Ошибка первая — пытаться восстановить оригинальные имена без `mapping.txt`. Это невозможно:
переименование необратимо без файла соответствий. `--deobf` даёт синтетические имена, а не
исходные.

Ошибка вторая — начинать со статики, не сняв RASP. Приложение закроется, и вы не поймёте, что
часть кода вообще не отработала.

Ошибка третья — считать, что «все строки зашифрованы». Часть остаётся открытой, и именно по ним
часто находят дешифратор: рядом с открытой строкой-маркером сидит вызов расшифровки.

## Итог по DexGuard

DexGuard — про увеличение стоимости анализа. Он не делает реверс невозможным, но заставляет
работать в рантайме и читать код по структуре. Ключевая идея: расшифровка всё равно происходит в
памяти, и её можно перехватить. Поэтому рантайм-дамп — универсальный приём, который снимает сразу
несколько слоёв.
