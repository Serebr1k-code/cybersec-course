## Вопрос, с которого всё начинается

Открываешь APK мобильной игры в jadx — там почти нет логики: только тонкая обёртка вокруг
нативной библиотеки. Где же сам геймплей, магазин, проверки покупок? Он внутри движка **Unity**,
и способ достать его зависит от того, на каком бэкенде собрана игра. Разберём оба.

## Наш пример: игра «PixelQuest»

В APK находим папку `lib/arm64-v8a/` и видим два разных мира:

```bash
$ unzip -l pixelquest.apk | grep -E 'libmono|libil2cpp|Managed|metadata'
  1234567  lib/arm64-v8a/libil2cpp.so
    54321  lib/arm64-v8a/libmono.so
  9876543  assets/bin/Data/Managed/Metadata/global-metadata.dat
```

Наличие `libil2cpp.so` вместе с `global-metadata.dat` означает бэкенд **IL2CPP**: C#-код
скомпилирован в C++ и затем в машинный код, а метаданные (имена классов, методов, полей)
вынесены в отдельный файл. Если бы был `libmono.so` и `assets/bin/Data/Managed/*.dll` — это
бэкенд **Mono**, где код лежит в управляемых сборках.

## Шаг 1: отличаем Mono от IL2CPP

Правило простое:

- `libmono.so` + `Assembly-CSharp.dll` в `Managed/` → **Mono** (код читается почти как исходник).
- `libil2cpp.so` + `global-metadata.dat` → **IL2CPP** (нужен дампер).

Проверить `Assembly-CSharp.dll` можно так:

```bash
$ unzip -l pixelquest.apk | grep Assembly-CSharp
  2097152  assets/bin/Data/Managed/Assembly-CSharp.dll
```

## Шаг 2: путь Mono — dnSpy/ILSpy

Для Mono достаточно декомпилировать DLL:

```bash
$ ilspycmd Assembly-CSharp.dll -o ./src
$ grep -rn "isPremium\|UnlockAll\|CheckPurchase" ./src | head
```

Управляемый код почти читаем: видно классы магазина, проверки покупок, а иногда и вшитые
секреты. Правка возможна обратной компиляцией DLL и пересборкой APK.

## Шаг 3: путь IL2CPP — Il2CppDumper

Для IL2CPP имена и структуры восстанавливают дампером:

```bash
$ Il2CppDumper libil2cpp.so global-metadata.dat out/
Initializing metadata...
Detected metadata version 29
Dumping... 48213 methods
Output: out/dump.cs, out/script.json, out/il2cpp.h
```

`dump.cs` содержит имена классов и методов с адресами; `script.json` подключают к IDA/Ghidra,
чтобы нативные функции получили читаемые имена. После этого ищем игровую логику:

```bash
$ grep -n "IsPremium\|UnlockAll\|VerifyPurchase" out/dump.cs | head
```

## Шаг 4: ассеты и строки

Помимо кода интересны ресурсы: `strings` по `libil2cpp.so` и `global-metadata.dat` часто
выдаёт URL, ключи, названия флагов. Ассеты (текстуры, тексты) лежат в `assets/bin/Data/` и
распаковываются AssetRipper/AssetStudio.

```bash
$ strings -n 6 global-metadata.dat | grep -iE 'http|secret|flag|token' | head
```

## Шаг 5: хукинг через Frida

Динамически можно перехватывать методы движка. Для IL2CPP удобны экспорты `il2cpp_*`:
находят класс по имени, метод по имени, затем ставят хук. Для Mono проще цепляться к
управляемым методам через уже готовые скрипты. Смысл один: увидеть аргументы проверки
(например, `VerifyPurchase`) в момент вызова.

## Таблица: что где лежит

| Бэкенд | Код | Метаданные | Инструмент |
|---|---|---|---|
| Mono | Assembly-CSharp.dll | в DLL | dnSpy / ILSpy |
| IL2CPP | libil2cpp.so | global-metadata.dat | Il2CppDumper |
| Ассеты | assets/bin/Data | — | AssetRipper |

## Крайние случаи и подводные камни

- Версия метаданных должна поддерживаться дампером; для новых Unity нужна свежая версия
  Il2CppDumper, иначе имена не восстановятся.
- Обфускация (Beebyte, Obfuscar) заменяет имена на `a`, `b`, `c` — придётся идти по строкам и
  поведению, а не по именам.
- Часть игр шифрует `global-metadata.dat` — тогда его сначала расшифровывают в памяти.
- Проверки покупок часто дублируются на сервере: патч клиента может не дать результата.

## Что дальше / решение

Итог: сначала определите бэкенд, затем выберите инструмент — ILSpy для Mono, Il2CppDumper для
IL2CPP. Секреты ищите не только в коде, но и в строках метаданных и ассетах. В следующем уроке
разберём Unreal — полностью нативный движок с контейнерами `.pak`.


## Шаг 6: что делать с найденной проверкой

Допустим, в `dump.cs` мы нашли `Player.IsPremium` и `Store.VerifyPurchase`. Прежде чем что-то
патчить, надо понять, **где принимается решение**. Есть три принципиально разных случая.

Первый — проверка чисто клиентская: `IsPremium` читает локальный флаг, сервер о покупке не
спрашивает. Тогда обход тривиален: в Mono правят управляемый метод, в IL2CPP — нативный код
или обёртку. Второй — проверка серверная: клиент отправляет чек, а премиум выдаёт сервер.
Патч клиента тут бесполезен, и это важный вывод для отчёта. Третий — смешанный случай:
локальный флаг есть, но периодически сверяется с сервером; тогда патч работает лишь до
следующей синхронизации.

## Практический сценарий: обход клиентской проверки

Самый быстрый путь для Mono-игры — декомпилировать, поправить и собрать обратно:

```bash
$ ilspycmd Assembly-CSharp.dll -o ./src
$ grep -rn "return false" ./src/Store.cs
$ ilspycmd -p -o ./patched ./src   # пересобрать проект
```

После правки DLL её кладут обратно в APK, пересобирают и подписывают:

```bash
$ apktool b pixelquest -o pixelquest-patched.apk
$ zipalign -p 4 pixelquest-patched.apk aligned.apk
$ apksigner sign --ks debug.keystore aligned.apk
```

Для IL2CPP путь сложнее: правят smali-обёртку, которая вызывает нативный метод, либо
перехватывают вызов через Frida, не меняя APK вовсе. Второй вариант предпочтительнее в
пентесте: он не ломает подпись и легче откатывается.

## Что мы теперь знаем

- Бэкенд Unity определяется по наличию `libmono.so`/`Assembly-CSharp.dll` (Mono) или
  `libil2cpp.so` + `global-metadata.dat` (IL2CPP).
- Mono разбирается ILSpy, IL2CPP — Il2CppDumper.
- Секреты живут не только в коде, но и в строках метаданных и в ассетах.
- Клиентский патч имеет смысл только если проверка не дублируется на сервере.

## Разбор реального кейса: магазин внутри игры

Представим типовую ситуацию из пентеста мобильной игры. Заказчик жалуется, что игроки
получают платный контент бесплатно, и просит оценить, насколько надёжна защита. Начинаем с
того, что определяем бэкенд: в нашем случае это IL2CPP, значит, читаемого C# в APK не будет,
и нам понадобится дампер. После восстановления имён мы ищем классы, связанные с магазином, и
видим метод, который проверяет флаг премиум-статуса. Дальше ключевой вопрос — кто источник
истины. Если метод просто читает локальное поле, игра доверяет клиенту, и защита иллюзорна.
Если же он делает сетевой запрос и ждёт подтверждения от сервера, клиентский обход не даст
ничего: сервер по-прежнему не выдаст платный контент. В отчёте это формулируется как оценка
модели угроз, а не как «есть/нет уязвимость». Мы показываем заказчику, что конкретно можно
сделать атакующему и что для этого нужно, — например, наличие root, ручная установка
перепакованного APK или просто модифицированный клиент без установки. Отдельно оцениваем,
обнаружит ли игра подмену: многие проекты проверяют подпись APK и целостность нативных
библиотек, и тогда патч перестаёт работать после первого же обновления или проверки.

## Типичные ошибки при реверсе Unity

Первая ошибка — начать с jadx и решить, что логики нет. В Unity-играх управляемая обёртка
почти пуста, и настоящий код лежит в DLL или в нативной библиотеке. Вторая ошибка — пытаться
разобрать IL2CPP без метаданных: без `global-metadata.dat` в дампере будут только адреса без
имён, и навигация станет мучительной. Третья — игнорировать версию формата метаданных: если
дампер не поддерживает версию, имена не восстановятся, и надо обновить инструмент, а не
упрощать задачу. Четвёртая — считать, что найденный в строках ключ обязательно рабочий:
многие строки остались от отладочных сборок и давно не используются. Пятая — патчить клиент
и забывать про серверную проверку, из-за чего выводы отчёта оказываются неверными. Наконец,
шестая ошибка — не проверять, есть ли у игры защита целостности: обход, который работает на
тестовом устройстве с root, может быть бесполезен на реальном устройстве пользователя.

## Как это выглядит в отчёте

Когда разбор закончен, находку нужно описать так, чтобы заказчик понял риск и смог его
устранить. Формулировка «в игре есть проверка премиума, которую можно обойти» слишком общая.
Правильнее указать цепочку: какой именно артефакт разобран, где найдена логика, какая
проверка оказалась клиентской и что конкретно позволяет атакующему. Если проверка серверная,
это тоже находка — положительная: её стоит отметить как работающий контроль. Хороший отчёт
разделяет наблюдения и выводы: сначала факт (метод `IsPremium` читает локальный флаг), затем
следствие (клиент доверяет своему состоянию), затем риск (игрок получает платный контент
бесплатно) и, наконец, рекомендация (перенести выдачу премиума на сервер и подтверждать чек
независимо). Для IL2CPP стоит отдельно упомянуть, что имена были восстановлены дампером, —
это показывает воспроизводимость метода. И не забудьте про защиту целостности: если игра
проверяет подпись или нативные библиотеки, отметьте, что это повышает порог для атакующего,
даже когда сама логика клиентская.

## Словарь терминов

- **Mono** — бэкенд Unity, где C#-код остаётся управляемым и лежит в DLL.
- **IL2CPP** — бэкенд, где C# транслируется в C++ и компилируется в нативный код.
- **global-metadata.dat** — файл с именами классов, методов и полей для IL2CPP.
- **dump.cs** — результат дампера: восстановленные имена с адресами.
- **AssetRipper** — инструмент извлечения ассетов Unity.
