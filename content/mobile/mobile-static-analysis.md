## Вопрос, с которого всё начинается

Ты умеешь распаковать APK и знаешь, что внутри — манифест, код, ресурсы. Но как провести **систематический** статический анализ: ничего не пропустить, быстро найти секреты и уязвимые компоненты, не читая вручную тысячи классов?

В этом уроке мы пройдём полный маршрут статического анализа одного приложения: от декомпиляции до проверки конфигураций безопасности.

## Наш пример: app.apk

Наш объект — `app.apk`. Мы хотим ответить на три вопроса: что приложение умеет, где его секреты и какие компоненты доступны снаружи. Действуем инструментами, каждый из которых закрывает свой вопрос.

## Шаг 1: распаковка apktool

`apktool` декодирует ресурсы и манифест в читаемый вид:

```
$ apktool d app.apk -o app_decoded
I: Loading resource table...
I: Decoding AndroidManifest.xml with resources...
I: Copying assets and libs...
```

Теперь у нас есть `AndroidManifest.xml` в виде XML и декодированные ресурсы. С них и начинаем.

## Шаг 2: декомпиляция jadx

`jadx` превращает DEX-байткод обратно в Java:

```
$ jadx -d app_src app.apk
INFO - loading dex files
INFO - done
```

На выходе — дерево пакетов с `.java`-файлами. Читать всё не нужно: ищем подозрительные места — работу с сетью, криптографию, проверки лицензии, строки.

## Шаг 3: автоматизация с MobSF

**MobSF** (Mobile Security Framework) делает автоматический статический анализ и выдаёт отчёт: найденные секреты, уязвимые компоненты, небезопасные настройки.

```
$ docker run -it -p 8000:8000 opensecurity/mobile-security-framework-mobsf
```

Загружаем APK через веб-интерфейс и получаем отчёт с оценкой. MobSF не заменяет ручной анализ, но за минуты показывает, куда смотреть.

## Шаг 4: охота за секретами

Главная ручная задача — найти захардкоженные секреты. Ищем по ключевым словам:

```
$ grep -rEn 'api[_-]?key|secret|password|token|Bearer|AKIA' app_src | head
app_src/com/example/app/Api.java:12: private static final String API_KEY = "sk_live_51H...";
app_src/com/example/app/Api.java:13: private static final String BASE_URL = "https://api.example.com/v2";
```

Так же проверяем ресурсы и нативные библиотеки:

```
$ grep -rEn 'http|key|secret' app_decoded/res/values/strings.xml
$ strings app_decoded/lib/arm64-v8a/libnative.so | grep -iE 'key|token'
```

Секреты в клиенте доступны каждому, кто скачал приложение.

## Шаг 5: анализ манифеста

Манифест рассказывает, какие компоненты доступны снаружи:

```
$ grep -E 'exported|permission|debuggable|cleartext' app_decoded/AndroidManifest.xml
<activity android:name=".SecretActivity" android:exported="true"/>
<application android:debuggable="true" android:usesCleartextTraffic="true">
```

Опасные признаки:

- `exported="true"` у активности/сервиса/ресивера — доступ снаружи.
- `debuggable="true"` — можно отлаживать и внедряться.
- `usesCleartextTraffic="true"` — разрешён HTTP без шифрования.
- Слабые `permission` — например, `android:protectionLevel="normal"`.

## Шаг 6: конфигурация безопасности сети

Современные приложения описывают сетевые правила в `network_security_config.xml`:

```
$ cat app_decoded/res/xml/network_security_config.xml
<network-security-config>
  <base-config cleartextTrafficPermitted="true"/>
  <domain-config>
    <domain includeSubdomains="true">api.example.com</domain>
    <trust-anchors><certificates src="user"/></trust-anchors>
  </domain-config>
</network-security-config>
```

Читаем: разрешён незашифрованный трафик, а для `api.example.com` доверяются **пользовательские** сертификаты. Второе означает, что приложение легко перехватить через прокси — pinning здесь нет.

## Как ускорить анализ: что искать в первую очередь

Статический анализ легко утопить в тысячах классов. Держите приоритеты:

- **Сетевой слой:** классы с `Retrofit`, `OkHttp`, `HttpURLConnection` — там адреса и заголовки.
- **Криптография:** `Cipher`, `SecretKeySpec`, `MessageDigest` — самодельные шифры и ключи.
- **Проверки:** `isRooted`, `checkSignature`, `isDebuggerConnected` — защиты и их обход.
- **Хранилище:** `SharedPreferences`, `getFilesDir` — что пишется на диск.
- **WebView:** `loadUrl`, `addJavascriptInterface` — потенциальный RCE.

Эти пять тем закрывают большинство находок.

## Разбор экспортированных компонентов

Экспортированный компонент — самая частая уязвимость Android. Если активность экспортирована, любое приложение на устройстве может её запустить и передать свои данные:

```
$ adb shell am start -n com.example.app/.SecretActivity --es token "attacker"
```

Если активность доверяет входным данным без проверки, это может привести к обходу авторизации или утечке. Ресиверы (`BroadcastReceiver`) и сервисы (`Service`) работают так же — проверяйте `exported` и `permission` у каждого.

## Секреты в строковых ресурсах

Разработчики часто выносят ключи в `strings.xml`, думая, что «так безопаснее»:

```
$ grep -rEn 'AIza|sk_|ghp_|AKIA' app_decoded/res/
```

Это ключи Google API (`AIza`), Stripe (`sk_`), GitHub (`ghp_`), AWS (`AKIA`). Наличие такого префикса — почти гарантированная находка.

## Диффинг версий

Полезный приём — сравнить две версии приложения. Появившиеся строки выдают новую функциональность, исчезнувшие — «спрятанное»:

```
$ diff -r app_v1_src app_v2_src | head
```

Так находят отладочные флаги и тестовые эндпоинты.

## Как писать отчёт по статическому анализу

Результат анализа нужно оформить. Держите структуру отчёта: приложение и версия, разрешения, экспортированные компоненты, найденные секреты, сетевые настройки, хранение данных. Для каждой находки указывайте файл и строку — так отчёт проверяем.

## Чем статика отличается от динамики

Статический анализ читает код, не запуская приложение. Динамический — запускает и наблюдает.

| | Статика | Динамика |
|---|---------|----------|
| Что видит | весь код, включая редкие ветки | реальное поведение |
| Не видит | runtime-данные, расшифрованный код | непройденные ветки |
| Инструменты | jadx, apktool, MobSF | Frida, эмулятор |

Их комбинируют: статика подсказывает, что перехватить в динамике.

## Проверка подписи и пересборка

Иногда нужно пересобрать APK (например, чтобы вставить Frida-гаджет). После правок подпись ломается, и приложение не установится. Решение — переподписать своим ключом:

```
$ apksigner sign --ks my.keystore app_patched.apk
```

Если приложение проверяет свою подпись (signature check), придётся обойти и эту проверку. Такие проверки ищут по строкам `signature`, `getPackageInfo`, `SIGNATURE`.

## Что искать в нативном коде

Даже если основная логика в Java, часть проверок может быть в `.so`. Ищите там строки:

```
$ strings app_decoded/lib/arm64-v8a/*.so | grep -iE 'flag|key|secret|root'
```

Нативные библиотеки сложнее анализировать, но строки в них часто остаются открытыми.

## Готовые правила поиска секретов

Соберите grep-набор: `api[_-]?key`, `secret`, `token`, `password`, `passwd`, `Bearer`, `AIza`, `AKIA`, `sk_live`, `ghp_`, `-----BEGIN`. Прогоняйте его по `app_src`, `app_decoded/res`, `app_decoded/assets` и по `strings` от `.so`. Этот набор ловит почти все утечки.

## Что делать с найденным секретом

Найденный ключ надо проверить: жив ли он и что даёт. Но делать это можно только в рамках правил программы (bug bounty) или авторизации. Не используйте найденные ключи вне разрешённого периметра — это уже не анализ, а несанкционированный доступ.

## Итог по статике

Статический анализ APK — это четыре шага: распаковать (`apktool`), декомпилировать (`jadx`), найти секреты (`grep`) и проверить конфигурации (манифест, network config). Этого достаточно для большинства находок.

## Что мы теперь знаем

По-простому:

1. `apktool` декодирует манифест и ресурсы.
2. `jadx` декомпилирует код в Java.
3. MobSF автоматизирует первый проход.
4. Секреты ищут `grep` по ключевым словам в коде, ресурсах и `.so`.
5. Манифест и `network_security_config` показывают открытые компоненты и слабую сеть.

## На что смотреть дальше

- **Начинайте с манифеста.** `exported` и `debuggable` — быстрые находки.
- **Grep по ключевым словам.** `api_key`, `secret`, `token`, `AKIA`.
- **Проверяйте `.so`.** Секреты прячут и в нативных строках.
- **Читайте network config.** Он говорит, можно ли перехватить трафик.
