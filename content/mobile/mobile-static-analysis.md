## Статический анализ APK: с чего начать

Статический анализ — это изучение приложения без его запуска. Для Android он даёт быстрый результат: распаковали APK, декомпилировали, нашли строки, секреты, подозрительные вызовы. Цель модуля — научиться извлекать максимум информации из APK только статическими методами: декомпиляция, поиск секретов, чтение манифеста, анализ ресурсов и нативного кода.

## Шаг 1: базовая разведка

```bash
file app.apk
unzip -l app.apk | head -40
apktool d -f app.apk -o app_smali
jadx -d app_java --deobf app.apk
```

Флаг `--deobf` у `jadx` пытается восстановить имена, испорченные обфускацией. Изучите структуру: сколько DEX-файлов, какие нативные библиотеки, какие ABI.

## Шаг 2: манифест

```bash
cat app_smali/AndroidManifest.xml
grep -nE 'exported|scheme|host|permission|debuggable|allowBackup' app_smali/AndroidManifest.xml
```

Ищите экспортированные компоненты, deep links, слабые permissions. Экспортированный `android:exported="true"` без защиты — потенциальная точка входа.

## Шаг 3: поиск секретов

```bash
grep -rInE 'api[_-]?key|secret|passw|token|Bearer|BEGIN [A-Z ]*PRIVATE KEY' app_java app_smali/res app_smali/assets
```

Также ищите URL'ы и endpoint'ы:

```bash
grep -rhoE 'https?://[a-zA-Z0-9./?=_%:-]+' app_java | sort -u | head -50
```

Часто в приложении зашиты ключи сторонних сервисов (Firebase, Google Maps, analytics), которые дают доступ к бэкенду.

## Шаг 4: строки и ресурсы

`res/values/strings.xml`, `res/raw/`, `assets/` — частые места для секретов:

```bash
find app_smali/assets -type f -exec file {} \;
strings -n 5 app_smali/assets/* 2>/dev/null | grep -i flag
```

Если строки зашифрованы, найдите функцию расшифровки: обычно это Base64/XOR, и вы можете воспроизвести её.

## Шаг 5: анализ кода

Откройте `jadx-gui` и идите по точкам входа: `MainActivity.onCreate`, классы с именами `Auth`, `Login`, `Crypto`, `Network`. Ищите:

- сравнения паролей (`equals`, `==`),
- вызовы криптографии (`Cipher`, `MessageDigest`),
- загрузку нативных библиотек (`System.loadLibrary`),
- использование `WebView` (`addJavascriptInterface`).

```bash
grep -rn 'loadLibrary\|addJavascriptInterface\|Cipher\|MessageDigest' app_java | head
```

## Шаг 6: нативный код

```bash
find app_smali/lib -name '*.so'
strings -n 6 app_smali/lib/arm64-v8a/libnative.so | grep -iE 'flag|key|error'
```

Нативные библиотеки анализируйте в Ghidra/radare2. Часто там прячут проверку флага.

## Шаг 7: сертификат и подпись

```bash
keytool -printcert -jarfile app.apk
```

Иногда в сертификате есть подсказки (CN, O).

## Типичные ошибки и подводные камни

- **Смотреть только `classes.dex`** — бывает несколько DEX.
- **Игнорировать `assets/`** — там конфиги и ключи.
- **Не использовать `--deobf`** — имена нечитаемы.
- **Пропустить нативные библиотеки** — там логика проверки.
- **Искать только «flag»** — ищите ключи, токены, endpoint'ы.
- **Не проверить манифест** — теряете точки входа.
- **Верить `jadx` безоговорочно** — сверяйтесь со smali.

## Справочная таблица

```bash
apktool d -f app.apk -o smali
jadx -d java --deobf app.apk
grep -rInE 'key|secret|token' java smali/assets
strings -n 6 lib/*/*.so | grep -i flag
keytool -printcert -jarfile app.apk
```

## Что дальше / решение

План: распакуйте и декомпилируйте, изучите манифест, проведите поиск секретов и endpoint'ов, прочитайте ключевые классы, проверьте нативные библиотеки и сертификат. Статический анализ даёт 80% ответов в типовых CTF-задачах; если логика скрыта обфускацией или проверяется в рантайме — переходите к динамике (Frida). Держите `jadx-gui` открытым для навигации по коду.

## Автоматизация поиска секретов

Ручной `grep` хорош, но для больших приложений используйте специализированные инструменты. `trufflehog` и `gitleaks` умеют искать секреты по известным паттернам в исходниках. Также полезны:

```bash
# поиск всех URL
grep -rhoE 'https?://[^"'"'"' ]+' app_java | sort -u
# поиск ключей по энтропии (высокая энтропия = ключ)
grep -rhoE '[A-Za-z0-9+/]{32,}={0,2}' app_java | sort -u | head
```

Firebase-конфиги (`google-services.json`), ключи Google API, токены аналитики часто зашиты и дают доступ к бэкенду. Проверяйте их отдельно: открытый Firebase Realtime Database или Storage — частая находка.

## Анализ обфускации

Если код обфусцирован (имена вида `a`, `b`, `c`), стратегии такие: ищите строковые константы (они остаются), ищите вызовы стандартных API (Crypto, Http, Reflection), идите от точек входа. `jadx` с `--deobf` и `--show-bad-code` помогает. Иногда обфускация — это только ProGuard (переименование), и логика восстанавливается по строкам и структуре. В тяжёлых случаях переходите к динамике.

## Работа с зашифрованными строками

Если строки зашифрованы, найдите функцию расшифровки. Признак — массив байт + операция XOR/Base64/AES + вызов из множества мест. Воспроизведите функцию локально на Python: извлеките зашифрованные байты из smali/ресурсов и примените ту же логику. Часто ключ тоже лежит рядом.

## Частые вопросы

«Как быстро найти endpoint'ы?» — `grep` по `http`. «Где хранятся ключи Firebase?» — `google-services.json`, `strings.xml`. «Что если всё в `.so`?» — Ghidra. «Как искать по энтропии?» — regex по длинным base64-строкам. «Обфускация мешает?» — идите от строк и точек входа.

## Что дальше / решение

Итог: сочетайте ручной `grep` со специализированными сканерами секретов, проверяйте Firebase/Google-конфиги, при обфускации опирайтесь на строки и стандартные API, для зашифрованных строк воспроизводите функцию расшифровки. Статический анализ в связке с этими приёмами даёт подавляющую часть находок ещё до запуска приложения.

## Разбор типичной CTF-задачи на статику

Рассмотрим задачу: дан APK, при вводе неверного пароля приложение показывает «Wrong», при верном — «Correct» и выводит флаг. Мы не хотим брутить вручную, поэтому читаем логику. Открываем `jadx-gui`, ищем класс с кнопкой (`Button`, `onClick`). Находим метод, который сравнивает ввод с результатом функции `decrypt(...)`. Смотрим `decrypt`: это XOR с ключом, зашитым в `strings.xml`. Извлекаем ключ, воспроизводим XOR в Python, получаем пароль, вводим — флаг на экране. Если проверка в нативном коде, тот же подход, но через Ghidra: находим `Java_..._decrypt`, разбираем константы.

Главное — идти от UI к логике проверки и воспроизводить её локально, а не пытаться угадать. Часто задача специально построена так, что проверка тривиальна, если её прочитать.

## Работа с ресурсами и таблицей ресурсов

Помимо `strings.xml`, секреты прячут в `res/raw/`, `assets/`, а также в самой таблице ресурсов `resources.arsc` (например, в неиспользуемых строках). `apktool` декодирует таблицу, и вы можете просмотреть все строки:

```bash
apktool d -f app.apk -o smali
grep -rn '<string' smali/res/values/strings.xml | head -50
```

Иногда флаг «нарисован» в нескольких строках или разбит по ресурсам — собирайте по частям.

## Частые вопросы

«Проверка в нативном коде — как читать?» — Ghidra, ищите `JNI`-функции. «Строки зашифрованы?» — найдите функцию расшифровки и воспроизведите. «Как понять, какой метод вызывается при нажатии?» — ищите `setOnClickListener`. «Что если обфускация сильная?» — идите от строк и UI.

## Что дальше / решение

Итог: статический анализ APK — это методичный поиск: манифест → строки → классы-точки-входа → нативный код. Воспроизводите проверки локально на Python, а не угадывайте. Держите `jadx-gui` для навигации, `apktool` для smali и патча, Ghidra для `.so`. Этого набора хватает для подавляющего большинства задач.

## Где пригодится

- **CTF:** Mobile — быстрый поиск флага в ресурсах, smali, assets и нативных строках.
- **Bug bounty:** утечки API-ключей и внутренних URL в мобильном клиенте — частый источник наград.
- **Пентест:** обязательный этап статического анализа по OWASP MASTG (STORAGE, CRYPTO, CODE).
- **Работа:** CI-проверки релизного APK, автоматический поиск секретов перед публикацией.
