## Вопрос, с которого всё начинается

Пользователь нажимает ссылку — и приложение открывается **мгновенно**, хотя оно не
установлено. Потом иконка исчезает. Это **Instant Apps**. Удобно — но если код приходит
по ссылке и запускается почти без установки, то **где здесь граница доверия и что
можно подсунуть пользователю?**

## Наш пример: ссылка, открывающая «мгновенное» приложение

Есть магазин, у которого есть обычное приложение и Instant-версия. Ссылка вида
`https://shop.example.com/item/42` открывает карточку товара, не устанавливая
приложение целиком.

```bash
$ adb shell pm list packages | grep instant
(пусто — пока не запускали)
```

Запустим ссылку и посмотрим, что изменилось:

```bash
$ adb shell am start -a android.intent.action.VIEW -d https://shop.example.com/item/42
Starting: Intent { act=android.intent.action.VIEW dat=https://shop.example.com/item/42 }
$ adb shell pm list packages | grep instant
package:com.example.shop.instant
```

Появился пакет `.instant`. Приложение загрузилось по ссылке.

## Шаг 1: из чего состоит Instant App

Instant App — это **не один APK**, а набор модулей: базовый плюс «фичи». При запуске
скачивается только нужная фича — поэтому быстро. Установка в обычном смысле не
происходит: код кладётся во временное хранилище и живёт ограниченное время.

```bash
$ adb shell pm path com.example.shop.instant
package:/data/app/~~tmp/com.example.shop.instant-1/base.apk
```

Ключевое: приложение живёт в ограниченной песочнице с урезанными разрешениями.

## Шаг 2: App Links — мост из браузера в приложение

Связь «ссылка → приложение» держится на **Android App Links**: приложение заявляет
домены, которые умеет открывать, и система проверяет их через `assetlinks.json` на
сайте.

```bash
$ adb shell dumpsys package domain-preferred-apps | grep -A3 shop
Package: com.example.shop
  Domains: shop.example.com
  Status: verified
```

Если верификация не проходит, система может спросить пользователя, каким приложением
открыть ссылку. Именно здесь появляется поверхность: **чужое приложение может
претендовать на тот же домен**, если проверка домена не настроена.

## Шаг 3: где ломается доверие

Три типовые проблемы Instant-приложений:

1. **Непроверенные App Links.** Если `assetlinks.json` отсутствует или неверен,
   система не гарантирует, что ссылку откроет именно нужное приложение. Злоумышленник
   регистрирует обработчик и получает переходы.
2. **Параметры deep-link без валидации.** Instant App разбирает URL и сразу выполняет
   действие. Если `?redirect=` или путь передаётся дальше без проверки — возможен
   переход на чужой экран или утечка токена.
3. **Доверие к «временному» контексту.** Раз приложение не установлено, часть проверок
   целостности может быть мягче; разработчики иногда ослабляют защиту в Instant-версии.

## Шаг 4: как это проверять

Практический чек-лист:

```bash
# какие ссылки приложение заявляет
$ adb shell dumpsys package com.example.shop.instant | grep -i -A2 "intent-filter"
# проверка assetlinks
$ curl -s https://shop.example.com/.well-known/assetlinks.json | head
```

Дальше — руками: собрать ссылки с неожиданными параметрами (`?redirect=`, `?url=`,
подмена пути) и посмотреть, что открывается. Инструмент тут не решает — решает
понимание потока «ссылка → разбор → действие».

## Шаг 5: защита и верификация

Главная защита Instant App — правильно настроить связь «домен → приложение». Файл
`assetlinks.json` должен быть опубликован по адресу
`https://<домен>/.well-known/assetlinks.json` и содержать отпечаток подписи
приложения:

```json
[{
  "relation": ["delegate_permission/common.handle_all_urls"],
  "target": {
    "namespace": "android_app",
    "package_name": "com.example.shop.instant",
    "sha256_cert_fingerprints": ["AB:CD:...:EF"]
  }
}]
```

Если отпечаток не совпадает или файл недоступен, система считает связь
неверифицированной — и ссылку может перехватить другое приложение. Проверка
отпечатка обязательна: разработчики часто меняют ключ подписи и забывают обновить
файл.

Второй слой защиты — **валидация параметров deep-link**. Любой параметр из URL
(`redirect`, `url`, `path`, `token`) должен проверяться на стороне приложения:
разрешённый список хостов, отказ от внешних переходов, никаких «открыть что угодно».

```text
Плохо:  ?redirect=https://evil.example/steal
Хорошо: разрешён только https://shop.example.com/*
```

Третий слой — не доверять «временному» контексту. То, что приложение запущено как
Instant, не повод ослаблять проверку целостности или пропускать аутентификацию.

## Если не сработало

* Домен верифицирован и `assetlinks.json` корректен — перехватить ссылку чужим
  приложением не выйдет; ищи слабости в разборе параметров.
* Приложение использует Play App Signing — отпечаток в `assetlinks.json` может
  отличаться от локального; сверяй с тем, что реально на устройстве.
* Instant-версия часто урезана и просто не содержит опасного кода — тогда смотри
  обычную (устанавливаемую) версию того же приложения.

## Что проверить на реальном устройстве

Аудит начинается с инвентаря ссылок. Посмотри, какие домены и пути заявляет
приложение, и какие из них ведут в Instant-версию:

```bash
$ adb shell dumpsys package com.example.shop | grep -i -A2 "android.intent.action.VIEW"
```

Затем проверь верификацию домена. Скачай `assetlinks.json` и сверь отпечаток подписи
с реальным. Рассинхрон отпечатков — типовая ошибка, из-за которой домен остаётся
неверифицированным, а ссылку может перехватить чужое приложение.

После этого переходи к параметрам. Собери список всех query-параметров, которые
приложение читает из URL, и проверь каждый: подставляй внешние хосты, пути, значения
с управляющими символами. Цель — найти переход, который приложение выполняет без
проверки.

И оцени роль Instant-версии в целом: иногда она урезана и безопаснее обычной, а
иногда содержит те же ручки, но с ослабленными проверками. Сравни обе версии, прежде
чем делать вывод.

## А если ссылка ведёт не туда

Отдельный сценарий — не перехват домена, а **подмена цели внутри легитимной ссылки**.
Приложение получает параметр с адресом и открывает его во встроенном WebView, не
проверяя хост. Тогда злоумышленнику не нужно регистрировать домен: достаточно
подсунуть пользователю ссылку, где внешний адрес спрятан в параметре. Проверять это
надо так же, как обычный open redirect: подставлять внешние хосты в каждый параметр и
смотреть, не откроется ли чужой сайт внутри доверенного приложения. Это особенно
опасно, когда WebView имеет JS-мост к нативному коду.

## Вывод для практики

Instant App удобно разбирать как **ссылку, а не как приложение**: всё начинается с
URL и заканчивается действием, которое этот URL запускает. Поэтому и проверять надо
ссылку — её домен, верификацию и параметры. Если домен проверен, а параметры
валидируются, поверхность резко сужается. Если нет — перед тобой открытый канал,
через который чужой контент попадает в доверенный контекст приложения.

## Что мы теперь знаем

- Instant App запускается по ссылке без установки, состоит из модулей.
- Работает в ограниченной песочнице с урезанными разрешениями.
- Связь с доменом держится на Android App Links и `assetlinks.json`.
- Непроверенный домен и невалидированные параметры — основные слабости.
- Проверять надо `dumpsys` + `assetlinks.json` + ручной перебор параметров ссылки.
