## Задача

Приложение машины умеет открыть двери, завести двигатель, показать заряд и климат. Это значит,
что где-то есть **токен доступа к автомобилю**. Найдём его и оценим, чем грозит его утечка.

## Наш пример: лог мобильного API

У нас есть лог запросов приложения к телематическому API производителя. Проследим, как
приложение авторизуется и найдём флаг рядом с утёкшим токеном.

## Шаг 1: два канала управления

* **Локальный** — цифровой ключ: телефон общается с машиной напрямую по BLE или UWB (CCC Digital
  Key). Здесь важен proximity (расстояние).
* **Удалённый** — телематика: приложение идёт в облако производителя, а тот — в машину. Здесь
  важен **токен**.

## Шаг 2: цифровой ключ

CCC Digital Key использует BLE для обнаружения и UWB для точного измерения расстояния (secure
ranging). Ключ хранится в защищённом элементе телефона. Атаки:

* **Relay** — удлинить канал (если нет secure ranging).
* **Компромисс ключа** — вытащить ключ из приложения/устройства.
* **Ошибки логики** — открыть до проверки расстояния.

## Шаг 3: телематический API

Типичный поток:

1. Приложение логинится по паролю/OAuth.
2. Получает **access token** (и refresh token).
3. Вызывает API: `POST /vehicles/{id}/command` с командой `unlock`/`start`.

```bash
$ cat car_api_log.txt
POST /oauth/token  grant_type=password  -> access_token=eyJ...
GET  /vehicles/42/status           -> {"battery": 78}
POST /vehicles/42/command          {"cmd":"unlock"}   Authorization: Bearer eyJ...
note: refresh_token stored in plaintext prefs
```

## Шаг 4: где искать слабое место

* **Токен в открытом виде** — в `SharedPreferences`, логах, бэкапах.
* **Долгий срок жизни** токена/refresh token.
* **Отсутствие подтверждения** для опасных команд (`start`, `unlock`).
* **API без rate limit** — можно перебирать `vehicle id` (IDOR).
* **Статический ключ** в приложении.

В лаборатории найди утёкший токен и флаг.

## Шаг 5: что проверять в пентесте

1. Как приложение хранит токены (защищённое хранилище или prefs).
2. Есть ли второй фактор на опасные команды.
3. Проверяются ли права на конкретную машину (IDOR).
4. Логируется ли удалённый доступ.
5. Как реализован локальный ключ (secure ranging или нет).

## Что мы теперь знаем

- Управление машиной идёт по локальному (BLE/UWB) и удалённому (API) каналу.
- CCC Digital Key хранит ключ в защищённом элементе и использует secure ranging.
- Телематический API авторизуется токеном; его утечка = доступ к машине.
- Слабые места: токен в открытом виде, долгий срок, нет 2FA на команды, IDOR.
- Проверять: хранение токенов, права, подтверждение команд, логирование.

## Куда дальше

Дальше — дроны: там приложение управляет не только доступом, но и полётом. А пока главное:
**токен к машине — это физический доступ**, и хранить его нужно как ключ.

## Где пригодится

- **Пентест automotive:** цифровые ключи и телематика.
- **Аудит API:** IDOR и подтверждение команд.
- **Анализ приложений:** хранение токенов.


## Шаг 6: фазы цифрового ключа

CCC Digital Key описывает фазы: **pairing** (владелец выдаёт ключ устройству), **provisioning**
(ключ записывается в защищённый элемент), **use** (открытие/запуск), **revocation** (отзыв
ключа). Ошибки на любой фазе опасны: слабое pairing даёт лишний ключ, слабый revocation —
оставляет доступ уволенному пользователю.

## Шаг 7: PKES и relay

**PKES** (Passive Keyless Entry and Start) — «ключ в кармане»: машина сама открывается, когда
владелец рядом. Это классическая цель **relay-атаки**: два ретранслятора удлиняют канал, и
машина «думает», что ключ рядом. Защита — UWB secure ranging и motion-sensor в ключе.

## Шаг 8: дизайн телематического API

Хороший API: короткоживущий токен, подтверждение для опасных команд, проверка прав на конкретную
машину, rate limit, аудит. Плохой: долгий токен, нет 2FA, IDOR по `vehicle id`. В пентесте
проверяют именно эти свойства.

## Шаг 9: что утекает из приложения

Кроме токена, из приложения утекают: VIN, привязка аккаунта, ключи push-уведомлений, иногда
статические API-ключи. Всё это помогает атакующему связать человека с машиной.

## Шаг 10: чек-лист

Проверяют: где хранится токен, срок его жизни, наличие 2FA на команды, проверку прав, логирование
доступа, реализацию локального ключа (secure ranging) и процедуру отзыва.

## Шаг 11: пример атаки

1. Приложение хранит refresh token в открытом виде.
2. Атакующий получает файл prefs (через бэкап или малварь).
3. Меняет токен на свежий access token.
4. Вызывает `/vehicles/{id}/command` с командой `unlock`.

Если API не требует подтверждения для опасных команд — машина открывается удалённо. Это уже не
«теоретическая» уязвимость, а реальный физический доступ.

## Шаг 12: защита

Хорошая реализация: короткоживущие токены в защищённом хранилище, обязательное подтверждение
(биометрия/PIN) для `unlock`/`start`, проверка прав на конкретную машину, rate limit и аудит.
Локальный ключ — secure ranging и хранение в защищённом элементе.

## Шаг 13: что проверять

Проверяют: хранение токенов, срок жизни, 2FA на команды, IDOR по vehicle id, логирование,
реализацию цифрового ключа и процедуру отзыва. Всё это — стандартный набор для automotive-аудита.

## Шаг 14: цифровой ключ и телефон

Цифровой ключ хранится в защищённом элементе телефона и не покидает его. Приложение лишь
запрашивает операцию, а подпись делает чип. Значит, украсть ключ «из файла» нельзя — но можно
перехватить саму операцию через инструментирование приложения.

## Шаг 15: облако производителя

Даже локальный ключ обычно требует регистрации в облаке производителя (привязка к аккаунту). Если
аккаунт скомпрометирован, ключ можно отозвать или перевыпустить на устройство атакующего — это
уже социальная инженерия, но с физическими последствиями.

## Шаг 16: что проверяют в аудите

Проверяют: где хранятся токены и ключи, срок жизни, наличие 2FA на опасные команды, проверку прав
на конкретную машину, логирование доступа, реализацию secure ranging и процедуру отзыва ключа.

## Шаг 17: итог

Автомобильный компаньон — это мост между цифровым аккаунтом и физической машиной. Слабое место
чаще в токенах и логике, чем в радио. Токен к машине нужно защищать как физический ключ.
