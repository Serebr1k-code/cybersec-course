## Задача

eSIM — это профиль, который скачивается по воздуху, а не вставляется руками. Ты хочешь понять
путь профиля: от кода активации до установленного на устройстве. И заодно — что помешает
злоумышленнику скачать профиль жертвы на свой телефон.

## Наш пример: установка профиля по коду

У нас есть activation code вида `LPA:1$smdp.example.com$MATCHING-ID` и лог установки профиля на
устройстве. Проследим все шаги и найдём флаг рядом с моментом установки.

## Шаг 1: участники

* **eUICC** — встроенный чип, который хранит профили. В отличие от пластиковой SIM, может
  держать несколько профилей и переключаться между ними.
* **EID** (eUICC Identifier) — уникальный идентификатор чипа.
* **SM-DP+** — сервер подготовки профиля. Готовит зашифрованный профиль и отдаёт его устройству.
* **SM-DS** — сервер обнаружения. Сообщает устройству, что для него есть профиль.
* **LPA** (Local Profile Assistant) — компонент на устройстве, который ведёт диалог с серверами.

## Шаг 2: activation code

Код активации указывает, откуда брать профиль:

```
LPA:1$smdp.example.com$04386-AGYFT-A74Y8-3F815
```

* `LPA:1` — версия схемы;
* `smdp.example.com` — адрес SM-DP+;
* `04386-...` — **matching ID**, по которому сервер найдёт именно этот профиль.

## Шаг 3: RSP — Remote SIM Provisioning

Установка профиля (RSP) идёт так:

1. Устройство по коду активации идёт на **SM-DP+**.
2. Сервер проверяет, что устройство (EID) — то самое, и отдаёт **зашифрованный профиль**.
3. LPA расшифровывает профиль (ключ выводится из общего секрета) и ставит его в eUICC.
4. Профиль активируется: устройство получает «номер».

```bash
$ cat lpa_log.txt
LPA: activation code LPA:1$smdp.example.com$MATCH-1234
RSP: TLS handshake with smdp.example.com
RSP: profile package downloaded (encrypted)
RSP: profile installed to eUICC (ICCID 89012...)
RSP: profile enabled, IMSI bound
```

## Шаг 4: почему это защищено

Профиль передаётся **зашифрованным**, а ключ известен только SM-DP+ и конкретному eUICC. Просто
перехватив трафик, профиль не поставить на другой чип. Привязка идёт к **EID** — идентификатору
чипа.

## Шаг 5: где слабые места

* **Повторное использование activation code** — если код утёк, его можно попробовать применить
  (если сервер не ограничил повторную установку).
* **Кража eUICC/устройства** — тогда профиль уходит вместе с чипом.
* **Социальная инженерия** — оператор перевыпускает профиль на чужое устройство (это уже
  SIM-swap, см. отдельный урок).
* **Ошибки LPA** — плохая проверка сертификата сервера.

В лаборатории в логе найди момент установки профиля и флаг.

## Шаг 6: что проверять в аудите

* Одноразовый ли activation code;
* проверяет ли LPA сертификат SM-DP+;
* не попадает ли профиль/ключи в бэкапы;
* есть ли журнал перевыпуска профиля у оператора.

## Что мы теперь знаем

- eUICC хранит профили; EID — идентификатор чипа.
- SM-DP+ готовит профиль, SM-DS сообщает о нём, LPA устанавливает.
- Activation code `LPA:1$server$matching-id` указывает, где взять профиль.
- Профиль передаётся зашифрованным и привязан к EID.
- Слабости: повтор кода, кража чипа, социальная инженерия, ошибки LPA.

## Куда дальше

Дальше — носимые устройства. А пока главное: **профиль зашифрован и привязан к чипу**, поэтому
провижининг ломают через процедуру, а не через перехват байтов.

## Где пригодится

- **Телеком-безопасность:** понимание RSP.
- **Forensics:** артефакты активации профиля.
- **Аудит MFA:** перевыпуск профиля как обход.


## Шаг 7: состояния профиля

Профиль в eUICC проходит состояния: **disabled** (есть, но выключен), **enabled** (активен,
даёт номер), **deleted** (помечен на удаление). Устройство может держать несколько профилей и
переключаться между ними. Это удобно для путешествий, но создаёт риск: если профиль можно
включить без согласия владельца — это уже перехват номера.

## Шаг 8: SM-DS и обнаружение

Иногда устройство не знает, что для него есть профиль. Тогда используется **SM-DS** (Discovery
Server): устройство периодически спрашивает SM-DS, нет ли события, и SM-DS указывает на нужный
SM-DP+. Так работает «тихая» доставка профиля — например, при покупке тарифа в приложении
оператора.

## Шаг 9: LPA и его режимы

**LPA** бывает двух видов: **LPAd** (device LPA, работает в модеме/системе) и **LPAe** (eUICC
LPA, работает на чипе). Разные режимы по-разному проверяют сертификаты и хранят ключи. Ошибки в
проверке сертификата SM-DP+ — классическая уязвимость, позволяющая подсунуть профиль с чужого
сервера.

## Шаг 10: инструменты

Для разбора используют логи LPA (на Android — `logcat` по тегу eSIM), APDU-трейс к eUICC и
иногда PC/SC-ридер с поддержкой eUICC. Ключевые артефакты: activation code, EID, ICCID, лог
TLS-сессии.

## Шаг 11: чек-лист

Проверяют: одноразовость activation code, проверку сертификата SM-DP+, хранение ключей, наличие
журнала перевыпуска, возможность повторного провижининга без участия владельца.

## Шаг 12: пример провижининга по шагам

Проследим полный путь:

1. Пользователь вводит activation code (сканирует QR).
2. LPA устанавливает TLS-соединение с SM-DP+.
3. SM-DP+ аутентифицирует устройство по EID и отдаёт профиль.
4. Профиль расшифровывается на eUICC общим секретом.
5. Профиль устанавливается и включается — номер активен.

На каждом шаге есть точки проверки: сертификат сервера, привязка к EID, одноразовость кода.

## Шаг 13: типовые ошибки

* **Повтор activation code** — если сервер не помечает код использованным.
* **Нет проверки сертификата SM-DP+** — можно подсунуть свой сервер.
* **Профиль в бэкапе** — ключи утекают вместе с резервной копией.
* **Перевыпуск без 2FA** — злоумышленник получает профиль по звонку в поддержку.

## Шаг 14: что писать в отчёте

Фиксируют: одноразовость кода, проверку сертификата, хранение ключей, наличие журнала перевыпуска,
возможность повторного провижининга. Каждый пункт — с логом или трассой.

## Шаг 15: как защищён профиль

Профиль передаётся зашифрованным, ключ известен только SM-DP+ и целевому eUICC. Это значит, что
перехват трафика бесполезен: без ключа чипа профиль не расшифровать. Защита держится на привязке к
**EID** и на сертификатах сервера.

## Шаг 16: где ломается

Ломается не криптография, а процедура: повтор activation code, отсутствие проверки сертификата,
профиль в бэкапе, перевыпуск без 2FA. Поэтому в аудите смотрят на процесс, а не только на
алгоритмы.

## Шаг 17: как выглядит атака

Типичная атака: злоумышленник убеждает оператора выдать профиль на другое устройство (или
повторно использует утёкший код). Профиль ставится, номер переходит к нему, все SMS и звонки —
его. Это уже SIM-swap, но через провижининг.

## Шаг 18: чек-лист

Проверяют: одноразовость кода, проверку сертификата SM-DP+, хранение ключей, наличие журнала
перевыпуска, возможность повторного провижининга без участия владельца, попадание профиля в
бэкап.
