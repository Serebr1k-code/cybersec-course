## Вопрос, с которого всё начинается

Современный автомобиль — это компьютер на колёсах. **Android Auto** проецирует экран телефона на дисплей машины, а **Android Automotive (AAOS)** — это полноценный Android, встроенный прямо в авто. Обе платформы расширяют поверхность атаки за пределы телефона: добавляются USB, Bluetooth, Wi-Fi и автомобильные API. Вопрос урока: как приложение объявляет себя «автомобильным» и где искать слабые места в этой связке.

Разберём на учебном APK, который поддерживает автомобиль.

## Наш пример: car.apk

Возьмём приложение `car.apk` и декодируем его манифест:

```
$ java -jar apktool.jar d -f -o car_an car.apk
$ grep -oE '<uses-(feature|permission)[^>]*>' car_an/AndroidManifest.xml
<uses-feature android:name="android.hardware.type.automotive" android:required="false"/>
<uses-feature android:name="android.software.car.templates_host" android:required="false"/>
<uses-permission android:name="android.permission.INTERNET"/>
<uses-permission android:name="android.permission.ACCESS_FINE_LOCATION"/>
```

Разбираем. `<uses-feature android:name="android.hardware.type.automotive">` объявляет, что приложение умеет работать на встроенном Android Automotive. `android.software.car.templates_host` — что оно использует **шаблоны** (готовые автомобильные экраны) для отрисовки на дисплее машины. `ACCESS_FINE_LOCATION` — доступ к точной геолокации, типичный для навигации.

## Шаг 1: два разных мира

Важно не путать:

- **Android Auto (проекция)** — телефон подключается к машине (по USB или Wi-Fi), а машина лишь **отображает** экран телефона. Логика — на телефоне.
- **Android Automotive (AAOS)** — Android работает **внутри** машины, приложения устанавливаются прямо в неё.

В обоих случаях приложение объявляет поддержку автомобиля в манифесте, и именно это объявление — точка входа для анализа.

## Шаг 2: как приложение сообщает, что оно автомобильное

Ключ — мета-данные, указывающие на XML-описание:

```
$ grep -oE '<meta-data[^>]*>' car_an/AndroidManifest.xml
<meta-data android:name="com.google.android.gms.car.application"
           android:resource="@xml/automotive_app_desc"/>
```

Этот мета-тег говорит системе: «это автомобильное приложение, вот его описание». Содержимое `@xml/automotive_app_desc` определяет, что приложение умеет в машине (медиа, навигация, шаблоны):

```xml
<automotiveApp>
    <uses name="media"/>
    <uses name="template"/>
</automotiveApp>
```

Если приложение объявляет `template`, оно рисует интерфейс на экране машины через шаблоны. Ошибки в обработке шаблонов и данных, приходящих из машины, — частая поверхность.

## Шаг 3: сервисы и каналы

Дальше смотрим компоненты:

```
$ grep -oE '<service[^>]*>' car_an/AndroidManifest.xml
<service android:exported="true" android:name="com.example.cardemo.CarService">
```

`exported="true"` — сервис доступен снаружи. В автомобильном контексте это значит, что к нему может обратиться другой компонент (в том числе из машины). Каналы, по которым идут данные:

- **USB** — проводная проекция; физический доступ к порту даёт подключение.
- **Bluetooth** — hands-free, контакты, сообщения; те же риски, что в `mobile-bluetooth-le`.
- **Wi-Fi** — беспроводная проекция; атака «злого двойника» (evil twin) точки доступа.
- **Automotive API** — доступ к свойствам машины (скорость, двери, климат).

Каждый канал нужно проверять отдельно: что передаётся, проверяется ли отправитель, есть ли аутентификация.

## Шаг 4: риски автомобильных приложений

Типовые проблемы:

- **Доверие к данным из машины/телефона** — если приложение принимает команды из автомобильного канала без проверки, их можно подменить.
- **Экспортированные компоненты** — как и в обычном Android, но последствия серьёзнее: в зоне риска функции авто.
- **Утечка геолокации** — `ACCESS_FINE_LOCATION` в связке с незащищённым каналом.
- **Обновление прошивки** — если приложение умеет обновлять ПО машины, подмена источника критична.
- **Слепое доверие USB** — подключившись к порту, атакующий может эмулировать устройство.

## Справочная таблица: что смотреть в автомобильном APK

| Признак в манифесте | Что означает |
|---------------------|--------------|
| `uses-feature ...type.automotive` | поддержка Android Automotive |
| `uses-feature ...car.templates_host` | отрисовка через автомобильные шаблоны |
| `meta-data ...gms.car.application` | ссылка на `automotive_app_desc` |
| `<uses name="media"/>` | воспроизведение медиа в машине |
| `<uses name="template"/>` | шаблонный интерфейс на дисплее |
| `exported="true"` у сервиса | компонент доступен из машины |

## Типовые риски и что проверять

- **Доверие к данным из автомобильного канала** — принимает ли приложение команды без проверки.
- **Экспортированные сервисы** — доступны ли они другому процессу и что делают.
- **Геолокация** — `ACCESS_FINE_LOCATION` в связке с незащищённым каналом.
- **Обновление ПО** — подписан ли образ и проверяется ли подпись.
- **USB-проекция** — что можно сделать, подключившись к порту как устройство.
- **Wi-Fi-проекция** — уязвимость к подмене точки доступа (evil twin).

Отдельно отметьте **привилегии**: автомобильное приложение может запрашивать доступ к свойствам машины (скорость, двери, климат) — это `CarPropertyManager`. Если такое приложение экспортирует компонент, через который эти свойства читаются или меняются, последствия выходят за пределы телефона. Проверяйте не только сам APK, но и то, какие системные разрешения ему выдали в машине.

## Полный прогон от начала до конца

1. **`apktool d`** — декодируем манифест автомобильного приложения.
2. **`grep uses-feature`** — определяем automotive/templates_host.
3. **`grep meta-data`** — находим `automotive_app_desc` и читаем его.
4. **`grep service`** — ищем экспортированные компоненты и их intent-filter’ы.
5. **Разбор каналов** — USB/Bluetooth/Wi-Fi, что и как передаётся.
6. **Проверка доверия** — валидирует ли приложение данные из машины.
7. **Фиксация** — сохраняем команду/сценарий, доказывающий проблему.

## Если не сработало

Приложение только для проекции — значит, логика на телефоне, смотрите её API (как в `mobile-api-testing`). Automotive API недоступен без машины — анализируйте статически, что приложение запрашивает. Канал зашифрован — ищите ошибки аутентификации или подмены устройства. Нет физического доступа к порту — переходите к Wi-Fi-проекции (evil twin).

Важно не путать **уровни анализа**: приложение на телефоне (Auto) и приложение внутри машины (AAOS) — это разные поверхности. В первом случае вы анализируете обычный APK, который лишь выводит интерфейс на дисплей. Во втором — у вас есть доступ к самому автомобильному Android, и тогда стоит смотреть `adb`-доступ, установленные сервисы и Automotive-свойства. Если на машине включён отладочный режим или открыт `adb`, это самостоятельная находка: через неё можно добраться до системных свойств авто.

## Что мы теперь знаем

1. Android Auto проецирует телефон на дисплей; Android Automotive — это Android внутри машины.
2. Приложение объявляет себя автомобильным через `uses-feature` и мета-данные `automotive_app_desc`.
3. `templates_host` и `<uses name="template">` означают отрисовку через шаблоны.
4. Каналы (USB/Bluetooth/Wi-Fi) и Automotive API расширяют поверхность атаки.
5. Главные риски — доверие к данным из машины, экспортированные компоненты, утечка геолокации.
6. Анализ = манифест + описание + каналы + проверка доверия.
7. В AAOS поверхность шире: доступ к самому автомобильному Android и его свойствам.
