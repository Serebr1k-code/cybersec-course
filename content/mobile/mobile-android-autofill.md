## Вопрос, с которого всё начинается

Менеджер паролей сам подставляет логин и пароль в нужные поля. Для этого он должен *видеть*, что
на экране есть поля логина и пароля. Значит, у него есть доступ к структуре чужого интерфейса.
Что если этот доступ получит не менеджер паролей, а малварь?

## Наш пример: сервис автозаполнения

В манифесте видим:

```xml
<service android:name=".MyAutofillService"
         android:permission="android.permission.BIND_AUTOFILL_SERVICE"
         android:exported="true">
  <intent-filter>
    <action android:name="android.service.autofill.AutofillService"/>
  </intent-filter>
</service>
```

`AutofillService` — компонент, который система вызывает, когда пользователь фокусируется на поле.
Сервис получает `AssistStructure` — описание всего экрана: какие поля есть, их типы, подсказки
`autofillHints`, иногда значения.

## Шаг 1: как работает автозаполнение

Пользователь выбирает сервис автозаполнения в настройках (обычно менеджер паролей). Когда
появляется форма, система собирает структуру экрана и отдаёт её сервису в `onFillRequest`. Сервис
решает, что предложить, и возвращает `Dataset` с данными для заполнения. Пользователь выбирает
dataset — поля заполняются.

## Шаг 2: что видит сервис

`AssistStructure` содержит `ViewNode` для каждого view: `className`, `idEntry`, `hint`,
`autofillHints`, `isFocused`, и (если разрешено) текст. Этого достаточно, чтобы понять, где логин,
где пароль, и предложить их. Легитимный менеджер паролей использует это для пользы пользователя;
вредоносный — чтобы собрать данные.

## Шаг 3: злоупотребление

- **Поддельный сервис автозаполнения.** Пользователя уговаривают включить «удобное
  автозаполнение», а сервис собирает все поля всех приложений.
- **Подмена dataset.** Сервис предлагает dataset, который выглядит как менеджер паролей, но ведёт
  на фишинговый экран.
- **Чтение без заполнения.** Сервис может просто читать структуру и ничего не заполнять.

## Шаг 4: ограничения и защита

Android ограничивает автозаполнение: сервис должен быть выбран пользователем; для паролей
используются `autofillHints` и `importantForAutofill`; с Android 11 есть проверка на
«подозрительные» сервисы. Приложение может запретить автозаполнение на чувствительных полях:

```xml
<EditText
    android:importantForAutofill="noExcludeDescendants"
    android:autofillHints="" />
```

или на уровне окна через `setImportantForAutofill`.

## Шаг 5: аудит

- Какие сервисы автозаполнения включены на устройстве.
- Есть ли в приложении `BIND_AUTOFILL_SERVICE`.
- Правильно ли размечены поля (`autofillHints`, `importantForAutofill`).
- Не помечены ли чувствительные поля как обычные.
- Есть ли `FLAG_SECURE` на экранах с паролями.

## Шаг 6: защита

- Помечать чувствительные поля и не отдавать их автозаполнению без нужды.
- Использовать `FLAG_SECURE` на экранах с секретами.
- Проверять, какой сервис автозаполнения включён у пользователя.
- Для собственных форм — явно указывать `autofillHints`, чтобы не отдавать лишнее.

## Что мы теперь знаем

- AutofillService получает структуру экрана и поля.
- Вредоносный сервис = сбор всех полей.
- `autofillHints`/`importantForAutofill` управляют разметкой.
- `FLAG_SECURE` защищает экран от захвата.
- Аудит: включённые сервисы и разметка полей.

## Шаг 7: AssistStructure подробнее

`AssistStructure` — это дерево `ViewNode`. У каждого узла есть `className` (например,
`android.widget.EditText`), `idEntry` (имя ресурса), `hint`, `autofillHints` и флаг `isFocused`.
Если приложение разрешило, узел содержит и текст (`getText()`). Из этих данных сервис понимает
семантику экрана: где логин, где пароль, где поле одноразового кода. Легитимно это удобно;
опасно — потому что любой включённый сервис получает ту же картину во всех приложениях.

## Шаг 8: важность разметки

`autofillHints` — строки вроде `username`, `password`, `creditCardNumber`, `otp`. Приложение может
их указывать, чтобы помочь менеджеру паролей, а может, наоборот, скрыть чувствительное поле от
автозаполнения через `importantForAutofill="no"`. Плохая практика — оставлять поля паролей без
разметки вообще: тогда менеджер паролей не сможет корректно заполнить, а вредоносный сервис всё
равно прочитает структуру. Хорошая практика — явно указывать типы и отключать автозаполнение там,
где оно не нужно.

## Шаг 9: FLAG_SECURE и скриншоты

`FLAG_SECURE` запрещает скриншоты, запись экрана и отображение содержимого в превью задач.
Приложения с паролями и платёжными данными обязаны его ставить. В аудите проверяйте, есть ли
`FLAG_SECURE` на экранах ввода секретов: его отсутствие — находка «sensitive screen not
protected», которая даёт утечку через скриншоты и recent apps. Для смежной темы смотрите
`mobile-android-screenshots`.

## Шаг 10: реальный кейс

Кейс: приложение-«клавиатура» с функцией автозаполнения собирало поля из банковских приложений.
Пользователи включили сервис ради удобства, а он отправлял логины и пароли на сервер. Формально
пользователь дал согласие на «автозаполнение», но не на сбор данных. В аудите такое ловится по
наличию `BIND_AUTOFILL_SERVICE` и сетевой активности сервиса.

## Шаг 11: чек-лист

- Какие сервисы автозаполнения включены.
- Есть ли у приложения свой AutofillService.
- Разметка полей (`autofillHints`, `importantForAutofill`).
- `FLAG_SECURE` на чувствительных экранах.
- Не утекает ли структура наружу.

## Частые вопросы

**Можно ли отключить автозаполнение в приложении?** Да, через `importantForAutofill="no"` на поле
или окне.

**Autofill видит пароли?** Он видит поля; текст — только если приложение/система его отдаёт.

**Что надёжнее — разметка или FLAG_SECURE?** Это разные защиты: разметка управляет
автозаполнением, FLAG_SECURE — захватом экрана.

## Шаг 12: AutofillManager API

Системная сторона автозаполнения — это `AutofillManager`:

```java
AutofillManager afm = getSystemService(AutofillManager.class);
boolean enabled = afm.isAutofillSupported() && afm.isEnabled();
```

Приложение может управлять участием в автозаполнении: включать/отключать его для конкретного
view (`setImportantForAutofill`), помечать поля, а на Android 12+ скрывать содержимое от сервисов.
Если приложение оставляет чувствительные поля «обычными», любой включённый сервис получит их
структуру. В аудите это проверяется по разметке и по наличию `FLAG_SECURE`.

## Шаг 13: аутентификация dataset

Когда сервис предлагает пароль, он может потребовать аутентификацию (`Dataset.Builder
.setAuthentication`), чтобы заполнить только после биометрии или ПИН. Это защита от того, что
вредоносный сервис молча подставит данные. В аудите смотрите, требует ли легитимный сервис
подтверждения, и не предлагает ли подозрительный сервис заполнять без него. Отсутствие
аутентификации — признак, что данные могут быть перехвачены или подставлены.

## Шаг 14: пересечение с Accessibility

Автозаполнение и Accessibility Service часто работают рядом: Accessibility читает дерево
интерфейса и может заполнять поля, а автозаполнение делает это «официально». Комбинация обоих
разрешений у одного приложения — сильный сигнал: оно видит и может подменять ввод везде. В аудите
проверяйте, не просит ли приложение оба разрешения без очевидной причины. Для Accessibility
смотрите `mobile-android-accessibility`.

## Шаг 15: реальный кейс

Кейс: клавиатура с функцией автозаполнения собирала данные из банковских приложений и отправляла
их на сервер. Пользователь включил сервис ради удобства, но не давал согласия на сбор. Находка
описывается как «сервис автозаполнения с неограниченным доступом к полям и сетевой эксфильтрацией».
Рекомендации: ограничить области, где сервис работает, требовать аутентификацию, не отправлять
данные наружу.

## Шаг 16: чек-лист

- Включённые сервисы автозаполнения на устройстве.
- Собственный AutofillService приложения.
- Разметка полей и `importantForAutofill`.
- `FLAG_SECURE` на экранах с секретами.
- Требуется ли аутентификация dataset.
- Не просит ли приложение Accessibility вместе с автозаполнением.

## Частые вопросы

**Можно ли полностью запретить автозаполнение в приложении?** Да, через разметку полей и окна.

**Видит ли сервис введённый текст?** Поля — да; текст — только если приложение/система его отдаёт.

**Что делать с полями OTP?** Помечать `autofillHints="smsOTPCode"` и требовать подтверждение.

## Шаг 17: как атакующий включается в цепочку

Чтобы сервис автозаполнения заработал, пользователь должен его включить. Поэтому атака начинается
с социальной инженерии: «включите наше удобное автозаполнение, чтобы не вводить пароли». После
включения сервис получает структуру всех форм. Дальше — либо сбор данных, либо подмена: сервис
предлагает dataset, который выглядит как привычный менеджер, но ведёт на фишинговый экран. Защита
пользователя — проверять, кто предлагает включить автозаполнение, и не включать неизвестные
сервисы.

## Шаг 18: как это выглядит в системе

Включённые сервисы автозаполнения перечисляются в настройках и видны через `dumpsys`:

```bash
$ adb shell settings get secure autofill_service
com.evil.autofill/.EvilService
```

Если в системе включён сервис, которого пользователь не узнаёт, — это красный флаг. Приложение с
собственным `BIND_AUTOFILL_SERVICE` при этом может быть и легитимным (свой менеджер паролей), но
тогда важно, чтобы оно не собирало данные за пределами заявленной функции.

## Шаг 19: итог

Autofill — официальный механизм, который даёт сервису широкий обзор пользовательского ввода.
Риск возникает, когда сервис нелегитимен или когда приложение не помечает чувствительные поля и не
ставит `FLAG_SECURE`. Проверяйте включённые сервисы, разметку полей и защиту экранов с секретами —
эти три пункта закрывают большинство находок в этой теме.

Практический вывод: автозаполнение — это доверие, которое пользователь выдаёт сервису. Проверяйте,
какой сервис включён, как размечены поля и защищены ли экраны с секретами, — этого достаточно,
чтобы закрыть тему в отчёте.
