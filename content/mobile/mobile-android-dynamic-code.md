## Вопрос, с которого всё начинается

Вы разобрали APK, но приложение делает что-то, чего в этом коде нет. Логика будто «дополняется»
во время работы. Значит, код загружается динамически. Как его достать?

## Наш пример: app.apk с загрузчиком

В коде находится:

```java
DexClassLoader loader = new DexClassLoader(dexPath, optDir, null, getClassLoader());
Class<?> c = loader.loadClass("com.example.Payload");
```

`DexClassLoader` — класс Android, который загружает DEX-файл в рантайме. Код `Payload` берётся
не из APK, а из `dexPath`.

## Шаг 1: что такое DexClassLoader

Обычно все классы приложения уже в APK. Но иногда код грузят позже: из скачанного файла, из
расшифрованного блоба, из assets. `DexClassLoader` позволяет загрузить DEX из произвольного
пути и создать классы. Это и гибкость, и поверхность атаки.

## Шаг 2: откуда берётся DEX

Источники динамического DEX:

- файл в `assets` или во внутреннем каталоге;
- скачанный по сети (обновление логики);
- расшифрованный из блоба (защита);
- собранный/сгенерированный на устройстве.

Первый шаг анализа — понять, откуда.

## Шаг 3: как найти загрузку

```bash
$ grep -rn -E 'DexClassLoader|loadDex|PathClassLoader|InMemoryDexClassLoader' out/sources
PayloadLoader.java:31: new DexClassLoader(dexPath, ...)
```

Нашли загрузчик. Смотрим, как формируется `dexPath`: где файл создаётся, что в него пишется.
Если пишется из расшифрованного массива — идём к расшифровке.

## Шаг 4: дамп динамического DEX

Самый надёжный путь — выгрузить DEX из памяти, как при распаковке:

```bash
$ frida-dexdump -U -f com.example
```

Он находит все DEX в памяти, включая динамически загруженные. Так получают код, которого нет в
APK.

## Шаг 5: анализ

Полученный DEX читают JADX. Часто это как раз «интересная» часть: проверки, платёжка, защита.
Именно её и прятали.

## Шаг 6: RCE-риски

Если приложение грузит код из внешнего источника без проверки подписи, злоумышленник может
подсунуть свой DEX — это путь к удалённому исполнению кода. Поэтому безопасная реализация
проверяет подпись/хеш динамического кода. При пентесте это проверяют в первую очередь.

## Шаг 7: практика

Типовой порядок: найти DexClassLoader → понять источник DEX → дампнуть из памяти → прочитать.
Если источник внешний — проверить, валидируется ли он.

## Что мы теперь знаем

- DexClassLoader грузит DEX в рантайме.
- Источник может быть файлом, сетью, блобом.
- Загрузку находят по имени класса-загрузчика.
- Динамический DEX дампят из памяти.
- Внешний код без проверки — риск RCE.

## InMemoryDexClassLoader: код вообще без файла

В прошлом разборе мы загружали DEX с диска. Но начиная с Android 8 (API 26) появился
`InMemoryDexClassLoader` — он принимает DEX не путём к файлу, а прямо в виде буфера в памяти.

```java
ByteBuffer buf = ByteBuffer.wrap(decryptedDexBytes);
InMemoryDexClassLoader loader = new InMemoryDexClassLoader(buf, getClassLoader());
Class<?> c = loader.loadClass("com.example.Payload");
```

Это важно для аналитика по двум причинам. Во-первых, на диске DEX может вообще не появляться —
только в оперативной памяти, и тогда дамп из файловой системы ничего не даёт. Во-вторых, код в
таком случае часто расшифровывается в тот же буфер, что и грузится, — значит, момент сразу после
расшифровки и есть точка перехвата.

Проверять наличие обоих классов стоит вместе:

```bash
$ grep -rn -E 'DexClassLoader|InMemoryDexClassLoader|PathClassLoader' out/sources
Payload.java:12: new InMemoryDexClassLoader(buf, cl)
```

## Определяем источник DEX по окружающему коду

Одного имени загрузчика мало — нужно понять, откуда приходит код, потому что от этого зависит
стратегия. Смотрим на код вокруг вызова и на то, как формируется аргумент.

Признаки источника по типичным вызовам:

- `getAssets().open("x.dex")` — DEX лежит в assets APK, статически доступен.
- `new File(getFilesDir(), "payload.dex")` — файл во внутреннем каталоге, мог быть записан из сети
  или расшифрован ранее.
- `openFileInput`/`FileOutputStream` рядом с `Cipher.getInstance` — расшифровка блоба перед
  записью или загрузкой.
- `HttpURLConnection`/`OkHttp` + запись в файл + загрузка — динамическая доставка кода по сети.

```bash
$ grep -rn -E 'getAssets|Cipher\.getInstance|openFileOutput|HttpURLConnection' out/sources/Payload.java
Payload.java:20: InputStream in = getAssets().open("p.bin")
Payload.java:26: Cipher c = Cipher.getInstance("AES/CBC/PKCS5Padding")
```

Здесь картина ясна: `p.bin` из assets расшифровывается AES и, вероятно, грузится. Дальше читаем
ключ и режим — и при необходимости расшифровываем файл вне приложения.

## Дамп: frida-dexdump и ручной поиск сигнатуры

Основной инструмент — `frida-dexdump`. Он подключается к процессу, сканирует память в поисках
сигнатуры DEX (`dex\n0`) и сохраняет каждый найденный файл.

```bash
$ frida-dexdump -U -f com.example -d
[*] Searching dex in memory...
[+] Found 4 dex files
[+] Saved classes.dex ... classes3.dex
```

Флаг `-d` включает глубокий поиск: он сканирует больше областей памяти и ловит DEX, которые
загрузчик мог разместить нестандартно. Иногда полезно запускать дамп после того, как приложение
прожило несколько секунд, — часть кода грузится лениво, при первом обращении.

Если по каким-то причинам инструмент недоступен, можно найти сигнатуру вручную: подключиться
через Frida и пройти по картам памяти, проверяя первые байты на `64 65 78 0a` (`dex\n`). Это
медленнее, но даёт понимание, где именно лежит код.

## Родственный механизм: нативная загрузка

Динамический код бывает не только в виде DEX. Приложение может держать логику в нативной
библиотеке и подгружать её в рантайме тем же приёмом — расшифровать и записать `.so`, затем
вызвать `System.load`.

```java
File lib = new File(getFilesDir(), "libpayload.so");
System.load(lib.getAbsolutePath());
```

Тогда дамп DEX ничего не покажет, потому что логика не в DEX. Здесь смотрят на файловую систему
во время работы (`/data/data/<pkg>/`), ловят запись `.so` и анализируют библиотеку как обычный
нативный код. Признак тот же — вызовы загрузчика и работа с шифром рядом.

## Таблица: источники динамического DEX и что делать

| Источник | Признак в коде | Как достать |
|---|---|---|
| assets | `getAssets().open` | распаковать APK, взять файл |
| внутренний файл | `getFilesDir()` + запись | посмотреть `/data/data/<pkg>/` |
| сеть | HTTP + запись | MITM, затем файл |
| расшифрованный блоб | `Cipher` перед загрузкой | найти ключ, расшифровать |
| в памяти | `InMemoryDexClassLoader` | дамп памяти (`frida-dexdump -d`) |
| native `.so` | `System.load` файла | дамп/анализ `.so` |

## Если не сработало

Если `frida-dexdump` не находит DEX, а приложение явно грузит код, — возможно, включён anti-dump:
заголовок DEX в памяти затирается сразу после загрузки. Тогда дамп делают «на лету»: перехватывают
нативный дешифратор и сохраняют буфер в момент, когда он ещё целый.

Если дампенные файлы не открываются в JADX, — вероятно, заголовки повреждены. Часть инструментов
умеет восстанавливать их по остаточным данным; иногда проще дампить сразу несколько раз в разные
моменты и взять наиболее полный экземпляр.

Если `grep` по загрузчикам ничего не находит, — либо код обфусцирован (имена классов
переименованы), либо загрузка спрятана в нативной части. Тогда ищите по системным вызовам, а не по
именам.

## Ограничения

Динамическая загрузка — не всегда признак зловредности. Легальные приложения грузят код для
обновлений, плагинов, A/B-тестов и обхода ограничений размера. Опасность появляется тогда, когда
источник внешний и не проверяется по подписи или хешу: именно это превращает механизм в путь к
удалённому исполнению кода.

Проверка целостности — правильная защита: приложение считает хеш загруженного DEX и сравнивает с
ожидаемым, а также проверяет подпись источника. При пентесте первым делом смотрят, есть ли такая
проверка и можно ли её обойти подменой ожидаемого значения.

## Мини-практика: восстановить DEX из assets вручную

Часть приложений кладёт зашифрованный или сжатый DEX прямо в `assets`. Если шифрование простое,
его можно воспроизвести вне приложения и получить читаемый файл.

Сначала достаём блоб:

```bash
$ unzip -o app.apk assets/payload.bin -d unpack
$ file unpack/assets/payload.bin
unpack/assets/payload.bin: data
```

`data` — не DEX, значит содержимое закодировано. Смотрим код загрузчика, чтобы понять алгоритм.
Часто это XOR с константой, AES с ключом в коде или просто инвертированные байты.

```java
byte[] raw = readAll(getAssets().open("payload.bin"));
for (int i = 0; i < raw.length; i++) raw[i] ^= 0x5a;  // простой XOR
```

Зная ключ, повторяем операцию локально:

```bash
$ python3 -c "d=open('unpack/assets/payload.bin','rb').read(); open('out.dex','wb').write(bytes(b^0x5a for b in d))"
$ file out.dex
out.dex: Dalvik dex file version 035
```

Получили обычный DEX — открываем JADX. Это самый быстрый путь, когда шифрование не слишком
сложное. Если алгоритм нативный, идём в `.so` или дампим память.

## Частые ошибки

Ошибка первая — искать DEX только по расширению. Блоб может называться `.bin`, `.dat`, `.jar`,
`classes.jar` или вообще без расширения. Ориентируйтесь на код, а не на имя файла.

Ошибка вторая — считать, что `DexClassLoader` всегда пишет файл на диск. На новых версиях чаще
используют `InMemoryDexClassLoader`, и файла нет. Тогда нужен дамп памяти.

Ошибка третья — пропускать проверку подписи. Многие думают, что «внешний код = сразу RCE», но
если приложение проверяет хеш/подпись загружаемого DEX, простого подсовывания своего кода
недостаточно. Сначала смотрите, есть ли проверка.

## Связь с обфускацией и упаковкой

Динамическая загрузка часто идёт рука об руку с обфускацией. Приложение может расшифровать DEX,
загрузить его и вдобавок переименовать классы. Тогда даже успешный дамп даст обфусцированный код,
и анализ придётся вести от системных API.

Отличие от упаковщика (shielding): упаковщик прячет **весь** DEX приложения и загружает его
целиком при старте, а динамическая загрузка обычно добавляет **отдельный модуль** (плагин,
обновление) к уже работающему коду. Признаки похожи, но масштаб разный.
