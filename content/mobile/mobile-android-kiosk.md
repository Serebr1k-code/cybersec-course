## Вопрос, с которого всё начинается

Терминал на складе показывает только одно приложение: сканирование товара. Кнопок «домой» и
«назад» нет. Это **kiosk-режим**. Но действительно ли из него нельзя выйти? Проверим, как
устроена блокировка и где у неё слабые места.

## Наш пример: снимок lock task

```bash
$ adb shell dumpsys activity activities | grep -i 'lockTask\|LockTask'
  mLockTaskModeState=LOCKED
  mLockTaskPackages=[com.acme.scanner]
```

Видно, что устройство в режиме Lock Task и заперто на пакете `com.acme.scanner`. Весь урок
ведём этот снимок.

## Шаг 1: что такое Lock Task / kiosk

**Kiosk** (или **COSU** — Corporate Owned, Single Use) — устройство, запертое в одном
приложении. В Android это реализует **Lock Task mode**: система скрывает системный UI,
блокирует кнопки «домой»/«недавние» и запускает только разрешённые пакеты. Включает его DPC
(Device Owner) — сам пользователь так устройство не запрёт.

## Шаг 2: уровни блокировки

| Уровень | Кто может выйти |
|---|---|
| Screen pinning | пользователь (жест/кнопки) |
| Lock Task (не pinned) | только через DPC/настройки |
| Lock Task + Device Owner | только DPC/перезагрузка с политикой |

Разница принципиальна: обычный screen pinning — временная заморозка для пользователя, а
Lock Task под управлением Device Owner — настоящий киоск.

## Шаг 3: как проверять состояние

```bash
$ adb shell dumpsys activity activities | grep -i 'LockTask'
  mLockTaskModeState=LOCKED
  mLockTaskPackages=[com.acme.scanner]
$ adb shell dumpsys device_policy | grep -i 'LOCK_TASK\|kiosk'
```

`mLockTaskModeState=LOCKED` означает, что режим активен. Список пакетов показывает, что
разрешено запускать. Это база для аудита.

## Шаг 4: классические обходы

Обходы kiosk — это про то, как вырваться из запертого приложения к системным функциям:

| Вектор | Суть |
|---|---|
| Share/intent из приложения | открыть чужой компонент, если он разрешён |
| Уведомление | тап по уведомлению открывает другое приложение |
| URL/веб-ссылка | переход в браузер или системный диалог |
| Помощник/голос | запуск Google Assistant поверх киоска |
| Экстренный вызов | системный экран, из которого бывают выходы |
| Настройки через намерение | если пакет настроек не запрещён |

Ключевая причина успеха — приложение само предоставляет «дверь» (share, ссылку, deep link).
Поэтому пентест kiosk начинается с аудита **всех интентов и внешних ссылок** приложения.

## Шаг 5: проверка на практике

```bash
$ aapt dump badging com.acme.scanner.apk | grep -i 'intent\|scheme'
$ adb shell am start -a android.intent.action.VIEW -d 'https://example.com'
```

Если команда открывает браузер поверх киоска — блокировка дырявая. Также проверяют,
разрешён ли системный UI (`STATUS_BAR`, `HOME`, `OVERVIEW` restrictions).

## Шаг 6: правильный kiosk

Хороший киоск запрещает всё лишнее через Device Owner: `DISALLOW_CREATE_WINDOWS`,
`LOCK_TASK_FEATURE_*`, скрывает уведомления и запрещает системные интенты. Аудит показывает
именно разницу между «заперли иконку» и «заперли устройство».

## Шаг 7: dedicated device и COSU

Kiosk — частный случай **dedicated device** (устройство под одну задачу). В Android
Enterprise это режим, при котором устройство целиком отдано одному сценарию: терминал,
сканер, информационная панель. Управляет им Device Owner, а не пользователь. Dedicated
устройства обычно не имеют аккаунтов пользователей и настраиваются через zero-touch — поэтому
киоск и zero-touch идут рядом в реальных развёртываниях.

## Шаг 8: lock task features

При включении Lock Task можно тонко настроить, что именно разрешено. Флаги
`LOCK_TASK_FEATURE_*` управляют доступом к системным элементам: панели уведомлений, кнопке
«домой», обзору приложений, глобальным действиям. Хорошо настроенный киоск выключает их все;
плохо настроенный оставляет «двери». Именно набор флагов и определяет реальную прочность
блокировки.

```bash
$ adb shell dumpsys device_policy | grep -i 'LOCK_TASK_FEATURE'
```

## Шаг 9: screen pinning как слабая альтернатива

Пользователь может включить **screen pinning** — временно закрепить приложение. Это не
киоск: выход делается удержанием кнопок, а после разблокировки режим снимается. В аудите
важно не спутать: `mLockTaskModeState=LOCKED` под Device Owner — это настоящий киоск, а
pinning — пользовательская заморозка. Вывод о «безопасности киоска» делается только по
первому.

## Шаг 10: отладка и adb

На управляемом устройстве `adb` обычно отключён политикой — и это часть защиты. Если же
отладка разрешена, проверяющий может выйти из киоска командами (`am start`, `input keyevent`).
Поэтому в отчёте фиксируют: включена ли отладка, разрешены ли системные интенты, можно ли
запустить посторонний компонент поверх киоска.

## Шаг 11: правильный аудит kiosk

Чек-лист: (1) состояние Lock Task; (2) список разрешённых пакетов; (3) набор
`LOCK_TASK_FEATURE_*`; (4) все внешние ссылки и интенты приложения; (5) доступность
уведомлений, ассистента и экстренного вызова; (6) отключена ли отладка. Каждый открытый
пункт — потенциальный выход из киоска, и его надо проверить на практике, а не предполагать.

## Шаг 12: dedicated против fully managed

Dedicated device — это киоск: устройство под одну задачу, без личного профиля. Fully managed
— корпоративное устройство целиком, но с обычным интерфейсом. Разница важна для оценки: у
dedicated нет «личной жизни», поэтому его задача — не выпустить наружу, а у fully managed —
разделить работу и личное. Аудит начинается с определения режима, иначе чек-листы перепутаются.

## Шаг 13: обход через системные диалоги

Даже при включённом Lock Task остаются системные диалоги: экстренный вызов, диалог включения
Wi-Fi, разрешения, «открыть в браузере». Иногда из них можно выйти в настройки или запустить
другой компонент. Проверяют все системные переходы: экстренный вызов, уведомления, ассистент,
диалоги разрешений. Именно системный диалог, а не само приложение, часто и есть «дверь».

## Шаг 14: что разрешено приложению

Приложение в киоске может само предлагать переходы: «открыть в браузере», «поделиться»,
«позвонить». Каждый такой переход — потенциальный выход. Аудит интентов приложения: какие
схемы (`scheme`) оно принимает, какие активности экспортирует, какие компоненты может
запустить. Экспортированная активность без проверки — прямой путь наружу.

## Шаг 15: чек-лист аудита kiosk

(1) Определён режим (dedicated/fully managed); (2) проверено состояние Lock Task;
(3) собран список разрешённых пакетов; (4) проверены `LOCK_TASK_FEATURE_*`; (5) перебраны
все внешние ссылки и интенты приложения; (6) проверены системные диалоги и экстренный вызов;
(7) проверена доступность отладки; (8) в отчёте — каждый открытый выход.

## Шаг 16: пример выхода через ссылку

Разберём типичный обход. Киоск показывает экран с «открыть инструкцию». Ссылка ведёт на
`https://...`, и приложение открывает её через системный браузер. Если браузер не запрещён
политикой, поверх киоска появляется полноценный браузер — и из него можно уйти в настройки,
магазин и т.д. Проверка: пробуем открыть внешнюю ссылку, смотрим, запустился ли браузер.
Находка — незакрытая «дверь» через внешнюю ссылку.

## Шаг 17: как защищают kiosk

Правильный киоск запрещает всё лишнее через Device Owner: отключает системный UI, уведомления,
ассистента, установку приложений, доступ к настройкам, а также сам браузер и «открыть в
другом приложении». Список разрешённых пакетов минимален. Аудит проверяет, что «двери»
действительно закрыты, а не просто спрятаны за интерфейсом.

## Шаг 18: отчёт по kiosk

В отчёте по киоску важны не только находки, но и модель: какие функции оставлены намеренно
(например, экстренный вызов) и какие — по недосмотру. Разница принципиальна: первое —
осознанный компромисс, второе — уязвимость. Пентестер разделяет эти два случая и даёт
рекомендации, не ломая назначение устройства.

## Если не сработало

Если команды `am start` не выполняются, значит, отладка отключена политикой — и это правильная
конфигурация, а не ваша ошибка. В таком случае проверку выхода проводят вручную, через сам
интерфейс: нажимают все доступные кнопки, пробуют ссылки, уведомления, экстренный вызов.
Если и это заблокировано, вывод — киоск настроен корректно. Не пытайтесь обойти защиту
разрушительными методами (сброс, прошивка): аудит безопасности не должен ломать устройство.
Фиксируйте наблюдения и рекомендации.

## Практический итог по kiosk

Порядок аудита: определить режим (dedicated/fully managed); проверить состояние Lock Task;
собрать список разрешённых пакетов; проверить `LOCK_TASK_FEATURE_*`; перебрать все внешние
ссылки и интенты приложения; проверить системные диалоги и экстренный вызов; проверить
доступность отладки. В отчёте разделяют намеренно оставленные функции и недосмотры. Ключевой
навык — не ломать устройство: аудит kiosk делается наблюдением и легальными командами, а не
сбросом и прошивкой. Найденные «двери» описывают и рекомендуют закрыть.

## Итоговая мысль

Kiosk — это история про «двери». Устройство запирается в одном приложении, но приложение и
система оставляют переходы: ссылки, share, уведомления, системные диалоги. Аудит kiosk — это
последовательный перебор всех дверей и проверка, закрыты ли они. При этом важно не спутать
намеренно оставленные функции (например, экстренный вызов) с недосмотрами. Правильный вывод
перечисляет и то, и другое, и даёт рекомендации, сохраняющие назначение устройства.

## Что мы теперь знаем

- Kiosk = Lock Task mode, включается DPC (Device Owner).
- Состояние видно в `dumpsys` (`mLockTaskModeState`, список пакетов).
- Screen pinning и Lock Task — разные уровни.
- Обходы используют «двери» самого приложения (share, ссылки, уведомления).
- Правильный kiosk запрещает системные функции через restrictions.
