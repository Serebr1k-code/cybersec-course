## Вопрос, с которого всё начинается

В нативной библиотеке есть функция расшифровки: на вход байты, на выход — строка. Запускать
всё приложение на устройстве ради одной функции долго, а читать ассемблер вручную — нудно.
Хочется просто «вызвать» эту функцию в песочнице и получить результат. Для этого есть эмулятор
процессора.

## Наш пример: функция расшифровки в libcrypto.so

Из Ghidra мы знаем адрес функции `decrypt` (например, `0x1f40`). Хотим выполнить её без
устройства и получить расшифрованные байты.

## Шаг 1: что такое эмуляция процессора

**Unicorn** — это библиотека, которая эмулирует процессор (ARM, x86, MIPS и др.): вы даёте ей
машинный код и память, она исполняет инструкции одну за другой. Никакой ОС, никакого реального
устройства — только CPU и память. Это идеально для изолированных функций.

## Шаг 2: карта памяти

Эмулятору нужно сказать, где лежат код и данные:

```python
from unicorn import Uc, UC_ARCH_ARM64, UC_MODE_ARM
from unicorn.arm64_const import UC_ARM64_REG_X0, UC_ARM64_REG_PC

mu = Uc(UC_ARCH_ARM64, UC_MODE_ARM)
BASE = 0x1000
mu.mem_map(BASE, 0x10000)          # 64 КиБ памяти
```

`mem_map` выделяет регион памяти. `UC_ARCH_ARM64` — целевая архитектура (AArch64).

## Шаг 3: загрузка кода и данных

```python
code = open('decrypt.bin','rb').read()      # машинный код функции
mu.mem_write(BASE, code)
mu.mem_write(BASE + 0x8000, b'\x11\x22\x33\x44')  # зашифрованные байты
```

Мы кладём в память машинный код функции и входные данные. `decrypt.bin` — это извлечённые
байты функции (их можно вырезать из `.so` по адресу и размеру).

## Шаг 4: аргументы и запуск

По соглашению вызова ARM64 первый аргумент — в регистре `X0`, второй — `X1`:

```python
mu.reg_write(UC_ARM64_REG_X0, BASE + 0x8000)  # указатель на данные
mu.emu_start(BASE, BASE + len(code))
```

`emu_start(начало, конец)` запускает исполнение до конечного адреса. Эмулятор пройдёт
инструкции и остановится.

## Шаг 5: хуки и результат

Чтобы видеть промежуточные значения, вешаем хук на инструкции:

```python
def on_code(mu, address, size, user_data):
    print('exec at', hex(address))
mu.hook_add(UC_HOOK_CODE, on_code)
```

А чтобы забрать результат — читаем память после остановки:

```python
out = mu.mem_read(BASE + 0x8000, 16)
print(out)
```

## Шаг 6: типичные подводные камни

- Функция может вызывать другие — их надо подгрузить или захукать заглушкой.
- Нужен правильный стек: без выделенного стека вызовы упадут.
- Данные могут требовать выравнивания.
- Если функция обращается к `JNIEnv`, эмуляция усложняется — иногда проще Frida.

## Шаг 7: альтернативы

Кроме Unicorn есть Qiling (эмулятор с поддержкой ОС) и Frida Stalker (трассировка реального
процесса). Выбор зависит от задачи: изолированная функция — Unicorn; целая программа —
Qiling/Frida.

## Шаг 8: как вырезать функцию из .so

Чтобы эмулировать функцию, нужно знать её смещение и размер. Смещение берётся из символа, размер —
из таблицы функций или из дизассемблера:

```bash
$ readelf -sW libcrypto.so | grep decrypt
  1234: 0000000000001f40   180 FUNC    GLOBAL DEFAULT   12 decrypt
$ objdump -d --start-address=0x1f40 --stop-address=0x1ff4 libcrypto.so | tail -3
  1ff0: d65f03c0  ret
```

`readelf -sW` показывает адрес (`0x1f40`) и размер (`180` байт). Затем вырезаем ровно эти байты:

```bash
$ dd if=libcrypto.so of=decrypt.bin bs=1 skip=$((0x1f40)) count=180
```

Это и есть `decrypt.bin` для эмуляции. Важно брать настоящий размер: лишние байты могут завести
исполнение в соседнюю функцию.

## Шаг 9: полный рабочий скрипт

Соберём всё вместе — с выделенным стеком и чтением результата:

```python
from unicorn import Uc, UC_ARCH_ARM64, UC_MODE_ARM, UC_HOOK_CODE
from unicorn.arm64_const import UC_ARM64_REG_X0, UC_ARM64_REG_SP, UC_ARM64_REG_LR

mu = Uc(UC_ARCH_ARM64, UC_MODE_ARM)
CODE, DATA, STACK = 0x1000, 0x2000, 0x8000
mu.mem_map(0x1000, 0x10000)
code = open('decrypt.bin', 'rb').read()
mu.mem_write(CODE, code)
mu.mem_write(DATA, b'\x11\x22\x33\x44')
mu.reg_write(UC_ARM64_REG_X0, DATA)      # указатель на шифртекст
mu.reg_write(UC_ARM64_REG_SP, STACK + 0x4000)
mu.reg_write(UC_ARM64_REG_LR, 0)         # куда «вернуться»
mu.emu_start(CODE, CODE + len(code))
print(mu.mem_read(DATA, 16))
```

Ключевой момент — регистр `LR`: когда функция выполнит `ret`, эмулятор перейдёт по адресу из `LR`.
Если записать туда `0` и позволить исполнению дойти до него, Unicorn остановится с ошибкой
чтения — это ожидаемый признак завершения. Многие оборачивают это в хук на адрес `0`.

## Шаг 10: вызовы внешних функций и заглушки

Функция часто вызывает `memcpy`, `malloc` или другие. В эмуляции их нет, и первый же вызов уйдёт
в никуда. Решение — перехватить неотображённую память и подставить реализацию:

```python
def on_unmapped(mu, access, addr, size, value, ud):
    print('unmapped call to', hex(addr))
    return False
mu.hook_add(UC_HOOK_MEM_UNMAPPED, on_unmapped)
```

Более управляемый путь — заранее узнать адрес вызова (например, через PLT) и захукать его,
вернув нужный результат и не давая исполнению уйти в библиотеку.

## Таблица типичных ошибок

| Ошибка | Причина | Решение |
|---|---|---|
| `Invalid memory read` | не замаплен регион | расширить `mem_map` |
| `UC_ERR_FETCH_UNMAPPED` | код не записан по адресу | сверить `BASE` |
| `Invalid instruction` | неверная архитектура/режим | ARM64 vs ARM/Thumb |
| зависание | бесконечный цикл | ограничить `count` в `emu_start` |

## Когда эмуляция не подходит

Если функция активно работает с `JNIEnv`, вызывает Java-методы или системные вызовы, Unicorn
потребует воссоздать окружение — это трудоёмко. В таких случаях берут Qiling (эмулятор с
частичной поддержкой ОС) или Frida (трассировка реального процесса). Правило простое: чем меньше
внешних зависимостей у функции, тем дешевле эмуляция.

## Пример: расшифровка строки нативной функцией

Типовая задача — в `.so` есть функция, которая по ключу выдаёт расшифрованную строку. Эмулируем
её, чтобы не запускать приложение:

```python
key = b'MySecretKey12345'
mu.mem_write(DATA, key)
mu.reg_write(UC_ARM64_REG_X0, DATA)          # указатель на ключ
mu.reg_write(UC_ARM64_REG_X1, len(key))      # длина
mu.emu_start(CODE, CODE + len(code))
out = mu.mem_read(DATA + 0x100, 32)          # куда функция положила результат
print(out.split(b'\x00')[0])
```

Функция читает ключ, раскладывает его по алгоритму и пишет результат в буфер. Зная соглашение о
вызове (куда передаётся выходной буфер), читаем его после остановки. Так за один прогон получают
все строки, которые приложение расшифровывает в рантайме.

## Проверка результата

Убедиться, что эмуляция верна, можно тремя способами: сверить результат с тем, что приложение
печатает в лог на устройстве; сравнить с результатом того же алгоритма, реализованного вручную;
прогнать эмуляцию дважды с разными входами и проверить, что выход меняется ожидаемо. Если все три
сходятся — эмуляция воспроизводит функцию корректно.

## Сравнение подходов к исполнению кода

| Подход | ОС/зависимости | Скорость старта | Когда выбирать |
|---|---|---|---|
| Unicorn | нет | мгновенно | изолированная функция |
| Qiling | частично | секунды | нужны syscalls/файлы |
| Frida | реальный процесс | зависит от app | нужен живой контекст |
| QEMU-user | полный | быстро | целый бинарь другой арх. |

Правило выбора: чем меньше функция зависит от окружения, тем ниже уровень эмулятора. Unicorn —
самый лёгкий и быстрый, но и самый требовательный к «чистоте» функции.

## Чек-лист по эмуляции

- Взять смещение и размер функции из `readelf`.
- Замапить код, данные и стек.
- Положить аргументы в регистры (X0, X1, ...).
- Выставить `LR` на адрес-заглушку возврата.
- Забрать результат из памяти после остановки.
- Подгрузить или захукать внешние вызовы.

## Когда лучше Frida

Если функция активно вызывает Java через JNI или зависит от системных вызовов, воссоздавать
окружение в Unicorn дольше, чем подключиться к живому процессу. В таких задачах Frida выигрывает:
она работает внутри приложения, где всё окружение уже есть. Эмуляция хороша там, где нужна
повторяемость и полный контроль над входом-выходом, а не живой контекст.

## Эмуляция как инструмент массовой расшифровки

Главная сила эмуляции — повторяемость. Если приложение расшифровывает сотни строк одной функцией,
не нужно запускать приложение сто раз: достаточно один раз подготовить окружение и прогнать
функцию в цикле по всем входам. Так за секунды получают таблицу «шифртекст → открытый текст»,
которая затем используется офлайн. Именно поэтому эмуляция — стандартный первый шаг при разборе
защищённых приложений: она превращает медленный ручной реверс в автоматический процесс, а
результат можно проверить и переиспользовать.

## Практический вывод по эмуляции

Эмуляция хороша там, где нужно изолированно исполнить функцию и получить результат, не поднимая
устройство. Порядок работы: найти смещение и размер функции, вырезать байты, замапить код, данные
и стек, положить аргументы в регистры и запустить. Ключевые детали — правильный регистр `LR`
(чтобы функция «вернулась» в заглушку) и обработка внешних вызовов, которых в эмуляции нет.
Результат читаем из памяти после остановки. Если функция тянет за собой JNI и системные вызовы,
выгоднее перейти на Frida или Qiling. Но для «чистых» крипто-функций эмуляция даёт максимальную
скорость и повторяемость: один раз настроив окружение, вы расшифровываете сотни входов в цикле и
получаете готовые таблицы для офлайн-анализа.

## Что мы теперь знаем

- Unicorn эмулирует CPU и память без устройства.
- Нужно замапить память, записать код и данные.
- Аргументы передаются через регистры (X0, X1).
- Хуки показывают промежуточные значения.
- Сложные функции требуют подгрузки зависимостей.
