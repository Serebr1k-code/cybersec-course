## Вопрос, с которого всё начинается

Ты нашёл баг: при вводе специальной строки в поле логина приложение открывает отладочное
меню. Чтобы показать это команде, надо воспроизвести сценарий — раз, другой, на другом
устройстве. Писать код на Python с Appium или на Java с Espresso долго. А что, если описать
сценарий простыми английскими словами и запустить одной командой?

## Что такое Maestro

**Maestro** — инструмент, в котором сценарий (его называют **flow**) описывается обычным
текстовым файлом в формате **YAML** (структурированный текст, где отступы задают вложенность).
Никакого программирования: ты пишешь «запусти приложение», «нажми на Логин», «введи alice»,
«проверь, что видно Баланс». Maestro сам переводит это в действия на устройстве.

Это делает Maestro идеальным для пентестера: воспроизведение бага превращается в файл на
десять строк, который можно приложить к отчёту.

## Наш пример: читаем flow и его прогон

Вот YAML-сценарий (в практике ты разберёшь его вместе с выводом прогона):

```yaml
appId: com.example.bank
---
- launchApp
- tapOn: 'Логин'
- inputText: 'alice'
- tapOn: 'Пароль'
- inputText: 'hunter2'
- tapOn: 'Войти'
- assertVisible: 'Баланс'
```

Строка `appId` говорит, какое приложение запускать. Дальше — список шагов, каждый с новой
строки и с дефиса. `launchApp` — запуск, `tapOn` — нажатие по тексту или id, `inputText` —
ввод, `assertVisible` — проверка, что элемент виден.

А вот вывод прогона (из файла `maestro_output.txt`):

```
✅ tapOn 'Войти'
❌ assertVisible 'Баланс' — got 'DEBUG MENU: com.example.bank/.DebugActivity'
1 flow, 1 failure
```

Читаем глазами пентестера. Все шаги прошли, но последний **провалился**: вместо экрана
баланса появилось отладочное меню `DebugActivity`. То есть в приложении есть отладочная
активность, и обычный вход каким-то образом её открывает. Это находка, и ровно в ней в
практике спрятан флаг.

## Шаг 1: почему YAML — это удобно

Сравни три подхода к одному и тому же сценарию:

- Espresso — Java-код, нужны исходники и сборка;
- Appium — Python-код, нужен сервер и драйверы;
- Maestro — YAML-файл, нужен только сам инструмент.

Чем проще описать сценарий, тем больше людей в команде смогут его прочитать. Для пентеста
это критично: сценарий воспроизведения бага должен быть понятен даже заказчику.

## Шаг 2: как Maestro находит элементы

Maestro ищет по **тексту на экране**, по id и по accessibility-метке. Тебе не нужно знать
внутренние идентификаторы — достаточно того, что видит пользователь: `tapOn: 'Войти'`.
Это одновременно и плюс (просто), и минус (хрупко, если текст локализован). Поэтому в
серьёзных флоу рядом с текстом указывают id: `tapOn: {id: 'btn_submit'}`.

## Шаг 3: полезные шаги

Кроме базовых, Maestro умеет:

- `swipe` — свайп в заданном направлении;
- `takeScreenshot` — снимок экрана (удобно прикладывать к отчёту);
- `runFlow` — вызвать другой flow (переиспользование);
- `assertNotVisible` — проверить, что чего-то **нет** (например, отладочного меню в релизе).

Последний шаг — прямой инструмент пентестера: напиши `assertNotVisible: 'DEBUG'` и убедись,
что релизная сборка действительно не показывает отладку.

## Шаг 4: запуск

```
$ maestro test login.yaml
```

Одна команда — весь сценарий. Вывод построчный, с ✅/❌ напротив каждого шага, как в
примере выше. Такой отчёт легко приложить к тикету.

## Что мы теперь знаем

- Maestro описывает сценарий декларативно, в YAML, без программирования.
- Шаги: `launchApp`, `tapOn`, `inputText`, `assertVisible` и другие.
- Элементы ищутся по тексту, id или accessibility-метке.
- `assertNotVisible` — прямой способ проверить отсутствие отладки в релизе.
- Прогон — `maestro test <flow>.yaml`, вывод построчный с ✅/❌.

## Анатомия flow: заголовок и шаги

Файл Maestro состоит из двух частей, разделённых строкой `---`. Верхняя часть — **заголовок**: там задают `appId`, при необходимости `tags`, `env` (переменные) и `name`. Нижняя часть — **список шагов**, каждый начинается с дефиса.

```yaml
appId: com.example.bank
env:
  USER: alice
  PASS: hunter2
---
- launchApp:
    clearState: true
- tapOn: 'Логин'
- inputText: ${USER}
- tapOn: 'Пароль'
- inputText: ${PASS}
- tapOn: 'Войти'
```

Здесь видны три важные детали. `clearState: true` запускает приложение «с чистого листа», стирая прежнее состояние — это делает прогон воспроизводимым. Секция `env` задаёт переменные, а `${USER}` подставляет их в шаги — удобно, чтобы не дублировать значения и легко менять тестовые данные. Шаг может быть и коротким (`- tapOn: 'Войти'`), и с параметрами-объектом (`- launchApp: {clearState: true}`) — YAML допускает оба вида.

## Reference: шаги Maestro

| Шаг | Назначение |
|-----|------------|
| `launchApp` | запустить приложение (можно с `clearState`) |
| `stopApp` | остановить приложение |
| `tapOn` | нажать по тексту/id/точке |
| `inputText` | ввести текст в активное поле |
| `eraseText` | стереть N символов |
| `assertVisible` | проверить, что элемент виден |
| `assertNotVisible` | проверить отсутствие элемента |
| `scroll` | прокрутить до элемента |
| `swipe` | свайп в направлении |
| `takeScreenshot` | сделать скриншот |
| `runFlow` | выполнить вложенный flow |
| `repeat` | повторить блок N раз |
| `evalScript` | выполнить JS-выражение |

Этого набора хватает для большинства сценариев. Комбинируя `scroll` и `assertVisible`, можно проверять длинные списки; `repeat` позволяет прогонять действие много раз (полезно для поиска состояния гонки).

## Продвинутые приёмы

**Выбор элемента по id.** Если текст локализован или меняется, надёжнее адресовать элемент по идентификатору:

```yaml
- tapOn:
    id: 'btn_submit'
```

**Переиспользование flow.** Общий сценарий входа выносят в `login.yaml`, а в других файлах вызывают:

```yaml
- runFlow: login.yaml
- assertVisible: 'Баланс'
```

**Условия.** Maestro умеет ветвиться через `runFlow: when:`. Например, закрыть баннер, если он виден:

```yaml
- runFlow:
    when:
      visible: 'Разрешить уведомления'
    commands:
      - tapOn: 'Разрешить'
```

Такой приём делает flow устойчивым к вариациям UI на разных устройствах и версиях приложения.

**Скриншоты как улики.** `takeScreenshot` сохраняет снимок в каталог прогона. Для пентест-отчёта это прямая улика: видно состояние экрана в момент проверки. Комбинируйте с `assertNotVisible`, чтобы зафиксировать отсутствие отладочного экрана в релизе.

## Maestro в CI и параллельный прогон

Maestro запускается одной командой и возвращает ненулевой код при провале — это делает его пригодным для конвейера:

```bash
$ maestro test flows/ --format junit --output report.xml
```

`--format junit` даёт отчёт в формате JUnit, который читают CI-системы. Каталог `flows/` прогоняется целиком. Для параллельного запуска на нескольких устройствах Maestro умеет работать с фермой эмуляторов: несколько инстансов гоняют один и тот же набор на разных API-уровнях. Это ловит баги, зависящие от версии Android/iOS.

В CI такой прогон ставят на каждый pull request: если новый коммит сломал сценарий или вернул отладочное меню, сборка падает. Так безопасность становится частью процесса, а не разовой проверкой.

## Когда Maestro не подходит

Maestro — инструмент «чёрного ящика»: он управляет UI и не видит внутреннее состояние. Поэтому он не подходит, когда нужно:

- проверить логику, не отображаемую на экране (шифрование, хранение ключей);
- перехватить сетевые вызовы (для этого — прокси и Frida);
- разобрать нативный код (нужен Ghidra/IDA);
- протестировать API напрямую (нужен HTTP-клиент).

Ещё одно ограничение — хрупкость: тексты локализованы, элементы перерисовываются. Чем больше в flow привязки к id, тем устойчивее прогон.

## Если не сработало

- **Элемент не найден.** Возможно, текст отличается (локализация) или элемент не виден без прокрутки. Добавьте `scroll` или перейдите на `id`.
- **Flow падает на старте.** Проверьте `appId` (точное имя пакета/bundle) и что устройство видно Maestro (`maestro devices`).
- **Ввод не попадает в поле.** Сначала надо сфокусировать поле (`tapOn`), затем `inputText`. Иногда помогает `eraseText` перед вводом.
- **Прогон нестабилен.** Приложение анимируется; добавьте `waitForAnimationToEnd` или `extendedWaitUntil`.
- **Устройство занято.** Maestro работает с одним устройством за раз; закройте другие сессии ADB/симулятора.

## Ограничения

Декларативность — сила и слабость Maestro. Flow читается человеком и легко поддерживается, но не даёт тонкого контроля: нельзя вызвать произвольный метод, прочитать память или перехватить функцию. Поэтому Maestro хорошо закрывает «воспроизведение пользовательского сценария», а для глубокого анализа его комбинируют с Frida и инструментами реверса.

## Сравнение с Espresso и Appium

| Свойство | Maestro | Espresso | Appium |
|----------|---------|----------|--------|
| Формат сценария | YAML | Java-код | код + WebDriver |
| Нужны исходники | нет | да | нет |
| Порог входа | низкий | высокий | средний |
| Контроль | грубый | тонкий | средний |
| Кросс-платформа | да | нет | да |

Для быстрого воспроизведения бага выбирайте Maestro; для тонкой проверки внутри процесса — Espresso; для единого кросс-платформенного набора с гибким контролем — Appium.

## Где пригодится

- Быстрое воспроизведение найденного бага без написания кода.
- Проверка релизной сборки на отсутствие отладочных экранов (`assertNotVisible`).
- Приложение к отчёту: читаемый сценарий + построчный лог прогона.
