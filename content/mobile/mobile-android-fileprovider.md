## Вопрос, с которого всё начинается

С Android 7 приложение больше не может просто отдать файл по `file://` — система бросает
`FileUriExposedException`. Вместо этого используют **FileProvider** и `content://`-URI.
Задумано это ради безопасности. Но если конфиг написан неаккуратно, провайдер начинает
отдавать **любой** файл приложения. Разберём, как это происходит.

## Наш пример: «поделиться PDF»

Приложение-сканер умеет делиться отсканированным PDF. В манифесте:

```xml
<provider android:name="androidx.core.content.FileProvider"
          android:authorities="com.example.scanner.fileprovider"
          android:exported="false"
          android:grantUriPermissions="true">
    <meta-data android:name="android.support.FILE_PROVIDER_PATHS"
               android:resource="@xml/file_paths"/>
</provider>
```

Провайдер не экспортирован — напрямую его никто не вызовет. Но `grantUriPermissions="true"`
означает, что приложению можно выдать разовое право на конкретный URI. А какие URI он
умеет отдавать — определяет `file_paths.xml`.

## Шаг 1: как устроен file_paths.xml

Файл описывает соответствия «псевдоним → реальный путь внутри приложения»:

```xml
<paths>
    <files-path name="scans" path="scans/"/>
    <cache-path name="cache" path="."/>
    <external-path name="ext" path="."/>
</paths>
```

- `files-path` → `/data/data/<pkg>/files/`
- `cache-path` → `/data/data/<pkg>/cache/`
- `external-path` → внешнее хранилище приложения

Поле `path` — это подкаталог. `path="."` означает **весь** соответствующий каталог. Вот тут
и начинаются проблемы.

## Шаг 2: где возникает traversal

FileProvider сам по себе фильтрует `..` в запрошенном URI — наивный `../` через URI не
пройдёт. Но ошибка обычно в **конфиге**: слишком широкий `path` делает доступным больше, чем
задумано. Например, `<external-path path="."/>` отдаёт всё внешнее хранилище, включая чужие
файлы, если они оказались в области приложения.

Второй вариант — `root-path`:

```xml
<root-path name="root" path="."/>
```

`root-path` указывает на корень файловой системы `/`. Если провайдер отдаёт по нему файлы и
приложение (или атакующий через grant) может запросить произвольный путь — читаются файлы
вне песочницы. Это классическая конфигурационная ошибка.

## Шаг 3: эксплуатация через grant

Сценарий: жертвенное приложение само вызывает `Intent` с `FLAG_GRANT_READ_URI_PERMISSION` и
подставляет URI, которым управляет атакующий (например, через deeplink или экспортированную
Activity). Если URI указывает на `root-path`-псевдоним, атакующий получает чтение файла,
который не должен был покидать приложение.

Проверка конфига — первый шаг анализа:

```bash
$ cat res/xml/file_paths.xml
<paths>
    <root-path name="root" path="."/>
</paths>
```

Такая запись — почти гарантированная находка.

## Шаг 4: как искать в APK

Распаковываем и ищем провайдеры FileProvider и их конфиги:

```bash
$ grep -rn "FileProvider" decompiled/AndroidManifest.xml
$ aapt2 dump xmltree app.apk --file res/xml/file_paths.xml | grep -i path
```

Дальше — проверить, какие Activity/Service умеют принимать внешний URI и передавать его
дальше с grant-флагом. Именно эта цепочка превращает конфиг в уязвимость.

## Шаг 5: как чинится

- Указывать **конкретный** подкаталог, а не `path="."`.
- Никогда не использовать `root-path`, если в этом нет острой необходимости.
- Не принимать URI от внешних компонентов и не передавать их дальше с grant.
- Проверять `getCanonicalPath()` результата на принадлежность разрешённому корню.

## Что мы теперь знаем

- FileProvider отдаёт файлы по `content://`, список — в `file_paths.xml`.
- `path="."` и `root-path` расширяют доступ до небезопасного уровня.
- Уязвимость раскрывается в связке «широкий конфиг + grant чужому URI».
- Искать: FileProvider в манифесте + конфиг путей + передача URI с grant-флагом.

## Шаг 6: как устроен URI внутри

URI, который отдаёт FileProvider, выглядит так:

```
content://com.example.scanner.fileprovider/scans/invoice.pdf
```

Здесь `com.example.scanner.fileprovider` — authority из манифеста, `scans` — псевдоним из
`file_paths.xml`, `invoice.pdf` — относительный путь внутри каталога `scans/`. Провайдер
склеивает корень (`files-path` → `/data/data/<pkg>/files/`) с подкаталогом и именем файла,
затем проверяет, что результат остался внутри корня.

Именно эта проверка и ломается, когда конфиг слишком широкий. Если корень — `/`, то «внутри
корня» означает «где угодно в системе».

## Шаг 7: сценарии с grant

`FLAG_GRANT_READ_URI_PERMISSION` при выдаче Intent даёт получателю разовое право прочитать
конкретный URI. Возникают три сценария злоупотребления:

1. **Приложение передаёт grant атакующему.** Жертва вызывает экспортированную Activity
   атакующего с флагом grant; атакующий читает URI.
2. **Атакующий подставляет свой URI.** Экспортированный компонент жертвы принимает URI извне
   и передаёт его дальше с grant — а URI ведёт в `root-path`.
3. **URI переиспользуется.** Grant живёт до перезагрузки; если URI записан в лог или
   clipboard, право можно применить позже.

## Шаг 8: инструменты проверки

Распаковка и извлечение конфигов:

```bash
$ apktool d app.apk -o app_dec
$ find app_dec/res/xml -name '*file*paths*' -exec cat {} \;
```

Автоматизированный поиск grant-цепочек:

```bash
$ grep -rn "FLAG_GRANT_READ_URI_PERMISSION\|setDataAndType\|startActivity" app_dec/smali/
```

Если экспортированная Activity принимает `Intent.getData()` и пробрасывает его в
`startActivity` с grant-флагом — это кандидат в находку. Проверяем, какой authority и какой
псевдоним он использует.

## Шаг 9: крайние случаи

- Провайдер может быть не `FileProvider`, а кастомным наследником `ContentProvider` с похожей
  логикой — тогда фильтрации `..` может не быть вовсе.
- На старых Android (до 7) `file://` ещё работал, и там traversal был тривиальным.
- Некоторые приложения отдают через провайдер **свои** внутренние БД — тогда утекают токены
  и сессии, а не только пользовательские файлы.
- Кэш-каталог (`cache-path`) часто содержит временные копии, которые приложение считает
  удалёнными.

## Шаг 10: рекомендации

Минимальный безопасный конфиг: отдельный подкаталог под каждый тип файла, никаких `root-path`
и `external-path path="."`. Если файл отдаётся наружу — только по явному URI, выданному через
`FileProvider.getUriForFile()`, и только с `FLAG_GRANT_READ_URI_PERMISSION`. В коде — проверка
`getCanonicalPath()` на префикс разрешённого корня перед `openFile`. Для отчёта достаточно
показать, какой именно файл вне задуманного каталога становится доступен и по какому пути.

## Шаг 11: как выглядит безопасный код

Правильная выдача файла наружу выглядит так:

```java
File dir = new File(getFilesDir(), "scans");
File file = new File(dir, "invoice.pdf");
Uri uri = FileProvider.getUriForFile(this,
        "com.example.scanner.fileprovider", file);
Intent share = new Intent(Intent.ACTION_SEND);
share.setType("application/pdf");
share.putExtra(Intent.EXTRA_STREAM, uri);
share.addFlags(Intent.FLAG_GRANT_READ_URI_PERMISSION);
startActivity(Intent.createChooser(share, "Поделиться"));
```

Здесь важно всё: каталог ограничен `scans/`, URI строится только для конкретного файла,
grant выдаётся лишь на время и только на чтение. Если бы вместо этого приложение принимало
URI от внешнего вызывающего и пробрасывало его дальше с grant — это и была бы уязвимость.

## Шаг 12: почему `..` не всегда работает напрямую

FileProvider нормализует путь и сравнивает канонический результат с корнем, поэтому «в лоб»
через `..` в URI обычно не выйти. Это создаёт ложное чувство безопасности. Реальные баги
живут в **конфиге**: если корень правила — `root-path path="."` или `external-path path="."`,
то любой файл внутри этого корня легален, и никакой `..` не нужен. Поэтому анализ начинается
не с попыток обхода, а с чтения `file_paths.xml`.

## Шаг 13: связка с deeplinks

Часто grant-цепочка замыкается через deeplink. Приложение принимает ссылку вида
`scanner://open?uri=content://...`, парсит параметр `uri` и передаёт его в `startActivity` с
grant-флагом. Атакующий подставляет в ссылку URI с широким псевдонимом и получает чтение.
Поэтому при аудите deeplink-обработчиков всегда проверяйте, что происходит с переданным URI:
валидируется ли authority, ограничивается ли псевдоним, снимается ли grant-флаг.

## Шаг 14: инструменты и их вывод

Помимо `aapt2`, полезен `apktool` для извлечения ресурсов и `jadx` для чтения кода, который
строит URI:

```bash
$ apktool d app.apk -o app_dec
$ cat app_dec/res/xml/file_paths.xml
$ jadx -d out app.apk
$ grep -rn "getUriForFile\|FLAG_GRANT_READ_URI_PERMISSION" out/sources/ | head
```

Дальше руками проследите, откуда приходит URI и кому он отдаётся. Автоматика находит
провайдер, но связку «внешний URI → grant» подтверждает только ручной разбор.

## Шаг 15: почему это серьёзно

FileProvider-утечки редко дают RCE, зато дают **чтение произвольных файлов приложения**: базы
с токенами, кэш с временными копиями документов, конфиги с ключами API. В bug bounty такие
находки обычно оценивают как high, потому что утечка секретов часто конвертируется в
дальнейшую компрометацию аккаунта пользователя.

## Шаг 16: мини-чек-лист

Найдите провайдер в манифесте: какой authority, включён ли `grantUriPermissions`. Откройте
`file_paths.xml`: есть ли `root-path`, есть ли `path="."`. Затем поищите, кто вызывает
`getUriForFile` и кто принимает внешний URI. Если широкий конфиг сочетается с приёмом
внешнего URI и grant-флагом — это рабочая уязвимость, а не теоретическая.

## Шаг 17: практический эксперимент

Соберите тестовый APK, в котором ваша Activity принимает `Intent.getData()`, логирует URI и
пробует открыть его через `getContentResolver().openInputStream()`. Передайте в неё URI
жертвенного приложения по очереди для каждого псевдонима из `file_paths.xml`. Если хотя бы
один псевдоним отдаёт файл, который не должен покидать приложение, — вы воспроизвели утечку.
Такой эксперимент превращает статическую догадку в доказанный факт, а его результат — в
скриншот для отчёта. Не забудьте проверить и обратный сценарий: жертва сама выдаёт grant на
URI, которым управляет атакующий.

## Шаг 18: как оценивают серьёзность

Серьёзность FileProvider-находки зависит от того, что именно утекает. Если через широкий
провайдер доступны только общедоступные картинки из кэша — это low. Если база с токенами
сессии или файл с приватным ключом — high или critical. Поэтому в отчёте всегда уточняйте
конкретный файл и его содержимое. Полезно пройти по всем псевдонимам из конфига и для каждого
описать, какой каталог он открывает и что в нём лежит. Так рекомендация становится
предметной: не «сузьте конфиг», а «уберите `root-path`, оставьте только `scans/`, потому что
именно там лежат документы, а в `files/` — база с токенами».

```quiz
- question: Зачем появился FileProvider?
  options:
    - Чтобы ускорить чтение файлов
    - Чтобы заменить небезопасный file://-обмен на content://
    - Чтобы шифровать файлы
    - Чтобы запретить доступ к SD-карте
  answer: 1
  explanation: С Android 7 прямой file://-обмен запрещён; FileProvider даёт безопасный content://.
- question: Какой конфиг file_paths.xml наиболее опасен?
  options:
    - <files-path name="scans" path="scans/"/>
    - <root-path name="root" path="."/>
    - <cache-path name="c" path="cache/"/>
    - <files-path name="f" path="f/"/>
  answer: 1
  explanation: root-path с path="." открывает корень файловой системы.
- question: Почему провайдер с exported=false всё равно может быть уязвим?
  options:
    - Он не может быть уязвим
    - Из-за grantUriPermissions он получает разовое право на URI
    - Потому что он root
    - Потому что он кэширует файлы
  answer: 1
  explanation: Grant-право открывает доступ к конкретному URI даже неэкспортированному провайдеру.
- question: Как корректно ограничить FileProvider?
  options:
    - Использовать root-path
    - Указать конкретный подкаталог и не использовать root-path
    - Отключить content://
    - Дать путь "/"
  answer: 1
  explanation: Конкретный подкаталог + проверка canonical path = безопасный минимум.
```
