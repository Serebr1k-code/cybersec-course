## Вопрос, с которого всё начинается

Мы разобрали открытую базу Telegram. Signal устроен иначе: его база зашифрована на уровне
SQLite — библиотекой **SQLCipher**. Даже с файлом базы на руках `sqlite3` её не откроет.
Где взять ключ и как всё-таки прочитать переписку?

## Наш пример: файлы Signal

```bash
$ ls -l /data/data/org.thoughtcrime.securesms/
-rw-r--r-- 1 u0_a789 u0_a789   12288 databases/signal.db
-rw-r--r-- 1 u0_a789 u0_a789    4096 databases/signal.db-wal
$ ls /data/data/org.thoughtcrime.securesms/shared_prefs/
org.thoughtcrime.securesms_preferences.xml
```

База — `signal.db`, а рядом в `shared_prefs` лежит XML с настройками. Весь урок ведём эти
два файла.

## Шаг 1: что такое SQLCipher

**SQLCipher** — это расширение SQLite, которое прозрачно шифрует всю базу: страницы данных,
индексы, журнал. Файл остаётся форматом SQLite, но его содержимое — шифротекст. Чтобы открыть,
нужно подать пароль. Проверим, что база действительно зашифрована:

```bash
$ sqlite3 databases/signal.db ".tables"
Error: file is not a database
```

Обычный SQLite ругается — значит, перед нами зашифрованный файл.

## Шаг 2: где ключ

Signal хранит ключ базы в обычном preferences-файле приложения. Открываем XML:

```bash
$ grep -i -A1 'encryption_key\|database' shared_prefs/org.thoughtcrime.securesms_preferences.xml
<string name="pref_database_encryption_key">MDEyMzQ1Njc4OWFiY2RlZjAxMjM0NTY3ODlhYmNkZWY=</string>
```

Значение — **base64** от 32 байт (AES-256). Декодируем:

```bash
$ echo 'MDEyMzQ1Njc4OWFiY2RlZjAxMjM0NTY3ODlhYmNkZWY=' | base64 -d | xxd
00000000: 3031 3233 3435 3637 3839 6162 6364 6566  0123456789abcdef
00000010: 3031 3233 3435 3637 3839 6162 6364 6566  0123456789abcdef
```

Ключ у нас. Как и у WhatsApp, он лежит рядом — защита от копирования файла, не от доступа к
песочнице.

## Шаг 3: расшифровка через SQLCipher

Используем `sqlcipher` (или сборку SQLite с поддержкой SQLCipher):

```bash
$ sqlcipher databases/signal.db
sqlite> PRAGMA key = "x'3031323334353637383961626364656630313233343536373839616263646566'";
sqlite> ATTACH DATABASE 'signal_plain.db' AS plaintext KEY '';
sqlite> SELECT sqlcipher_export('plaintext');
sqlite> DETACH DATABASE plaintext;
```

Команда `sqlcipher_export` выгружает расшифрованное содержимое в новую базу `signal_plain.db`.
Теперь это обычный SQLite.

## Шаг 4: чтение сообщений

```bash
$ sqlite3 signal_plain.db ".tables"
message  thread  recipient  ...
$ sqlite3 signal_plain.db "SELECT date, body FROM message ORDER BY date LIMIT 3;"
1756720511000|привет
1756720499000|как дела?
1756720480000|секрет: nto{...}
```

Таблица `message` хранит сообщения, `thread` — диалоги, `recipient` — собеседников. Поля
`date` (миллисекунды), `body` (текст), `type` (направление).

## Шаг 5: почему это «правильный» мессенджер

Signal шифрует базу целиком, а ключ хранит в защищённом хранилище (в свежих версиях — в
Android Keystore, а не в открытом XML). На разблокированном устройстве с root или из полного
дампа ключ всё равно извлекается, но именно поэтому Signal — эталон: переписка не остаётся
в открытом виде. Для форензики вывод простой: без ключа база бесполезна, а ключ живёт ровно
столько, сколько живёт доступ к устройству.

## Шаг 6: если ключ не в XML

В новых версиях ключ может быть завёрнут в Android Keystore. Тогда его достают хукингом
рантайма (перехватывают момент, когда приложение само расшифровывает базу) либо из дампа
памяти. Это уже динамическая форензика, и она опирается на инструменты из ветки Frida.

## Шаг 7: ключ в Keystore и как его достают

В старых версиях Signal ключ базы лежал в `shared_prefs` обычным base64. В новых его
«заворачивают» в Android Keystore: сам ключ никогда не покидает защищённое хранилище, а
приложение просит Keystore расшифровать данные. Это правильная защита — но и её обходят, когда
есть доступ к устройству. Есть три пути. Первый — хукинг рантайма: перехватить момент, когда
приложение получает расшифрованную базу или ключ, и вытащить их из памяти. Второй — дамп
памяти процесса и поиск ключевого материала. Третий — полный образ с последующей эмуляцией
TrustZone. Все три — динамические техники, и они требуют root или физического доступа.

## Шаг 8: SQLCipher и журнал

SQLCipher шифрует не только основную базу, но и журнал `-wal`. Поэтому при расшифровке важно
работать с полным набором файлов: если забрать только `signal.db`, вы потеряете последние
сообщения, которые ещё не перенесены из WAL. Правильный порядок: скопировать `signal.db`,
`signal.db-wal` и `signal.db-shm` вместе, затем расшифровать с ключом. Экспорт
`sqlcipher_export` корректно переносит и содержимое журнала в расшифрованную копию.

## Шаг 9: вложения и disappearing messages

Сообщения — не только текст. Signal хранит вложения в каталоге приложения, а база ссылается на
них. Отдельная тема — **исчезающие сообщения** (disappearing messages): приложение удаляет их
по таймеру, но на диске они какое-то время остаются. В форензике это окно возможностей: чем
раньше снят дамп, тем больше «исчезнувшего» ещё читается. Также стоит помнить, что исчезающие
сообщения могут сохраняться в уведомлениях и в кэше системы.

## Шаг 10: привязка Signal Desktop

Signal может быть связан с настольным клиентом. Тогда часть переписки синхронизируется на
компьютер, где она хранится уже иначе — в зашифрованной базе `db.sqlite` в профиле
пользователя. Для полной картины проверяют все связанные устройства: телефон может быть
вычищен, а десктоп — нет. Это типичная ошибка неполного анализа: «на телефоне ничего нет» не
значит «ничего нет вообще».

## Шаг 11: вывод для аудита

Signal — эталон защищённого мессенджера: база зашифрована, ключ в Keystore, переписка не
остаётся открытой. Для пентеста это означает, что локальный дамп без ключа почти бесполезен, и
ценность смещается к динамическим методам и к связанным устройствам. В отчёте фиксируют:
зашифрована ли база, где ключ, удалось ли его извлечь и каким методом, а также что удалось
прочитать.

## Шаг 12: сравнение трёх мессенджеров

Полезно свести в таблицу то, что мы разобрали, потому что на интервью и в отчётах это
спрашивают постоянно.

| Мессенджер | База | Шифрование | Ключ |
|---|---|---|---|
| WhatsApp | msgstore.db.crypt15 | весь файл | файл key / Keychain |
| Telegram | cache4.db | нет (кэш открыт) | — |
| Signal | signal.db | SQLCipher | shared_prefs / Keystore |

Вывод простой: чем «правильнее» мессенджер, тем меньше вы достаёте из файла и тем больше — из
памяти и связанных устройств. Это фундаментальное следствие end-to-end шифрования.

## Шаг 13: целостность и хэши

Работа с зашифрованной базой — это всегда работа с копией. Снимают хэши исходных файлов,
расшифровывают в отдельный файл, а оригинал не трогают. Для SQLCipher это особенно важно:
`sqlcipher_export` создаёт новую базу, и если случайно выполнить его поверх оригинала, можно
потерять доказательство. Хэши и журнал действий (кто, когда, что запускал) — обязательная
часть форензического отчёта.

## Шаг 14: вложения и уведомления

Signal хранит вложения в песочнице, а база ссылается на них. Дополнительный источник —
системные уведомления: их текст попадает в `logcat` и в системные базы, даже если само
сообщение исчезло. Так восстанавливают «исчезнувшие» сообщения, которых уже нет в базе.
Проверяйте оба источника: базу приложения и системный журнал уведомлений.

## Шаг 15: чек-лист Signal-форензики

(1) Хэши `signal.db`, `-wal`, `-shm`; (2) найдено место хранения ключа; (3) база расшифрована
в копию через SQLCipher; (4) выгружены `message`, `thread`, `recipient`; (5) проверены
вложения и уведомления; (6) проверены связанные устройства (Desktop); (7) указано, был ли
ключ в Keystore и как извлекался.

## Шаг 16: что не удаётся достать

Даже с расшифрованной базой есть пределы. Исчезающие сообщения, уже удалённые по таймеру, в
базе отсутствуют. Вложения, не докачанные до конца, отсутствуют. Ключи, «завёрнутые» в
аппаратное хранилище, без динамических методов не извлекаются. Это не неудача, а граница
метода, и её надо честно указать в отчёте: заказчик должен понимать, что «нет данных» здесь
означает «недоступны этим методом», а не «не существовали».

## Шаг 17: почему Keystore меняет правила

Android Keystore хранит ключи в аппаратно-защищённой области и не отдаёт их приложению — оно
может только попросить «расшифруй вот это». Поэтому копирование файла базы и файла ключа не
даёт результата: ключ физически не лежит в файловой системе. Достать его можно только
динамически, в момент, когда приложение легитимно расшифровывает данные. Это принципиальный
сдвиг: статическая форензика уступает место динамической.

## Шаг 18: привязка к номеру телефона

Signal регистрируется по номеру телефона, и номер — это ключевой идентификатор. В базе есть
идентификаторы собеседников, связанные с номерами. При построении картины номер связывают с
контактами устройства и с журналом звонков/SMS: так восстанавливают, кто есть кто. Учитывайте,
что Signal использует «номера-псевдонимы» для скрытия настоящего номера — это тоже факт,
который стоит отметить.

## Если не сработало

Бывает, что ключ в XML отсутствует, а база всё равно не открывается. Тогда возможны три
причины. Первая: ключ «завёрнут» в Keystore — статически его не достать, нужен хукинг рантайма
или дамп памяти. Вторая: база повреждена (оборвалась запись, есть только часть журнала) —
тогда работают с тем, что есть, и явно отмечают потерю. Третья: вы используете `sqlite3` без
поддержки SQLCipher — проверьте сборку (`PRAGMA cipher_version`). Для каждой причины свой
следующий шаг: динамика, восстановление, смена инструмента. Главное — не объявлять «данных
нет», пока не проверены все три.

## Что мы теперь знаем

- Signal шифрует базу через SQLCipher; `sqlite3` её не открывает.
- Ключ базы лежит в `shared_prefs/*.xml` (base64) или в Keystore.
- `PRAGMA key` + `sqlcipher_export` дают расшифрованную копию.
- Сообщения — в таблице `message`, диалоги — в `thread`.
- Без ключа база бесполезна; ключ защищён хранилищем.
