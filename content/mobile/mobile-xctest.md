## Вопрос, с которого всё начинается

На Android у нас был Espresso — тест внутри процесса. У Apple своя пара инструментов:
**XCTest** для юнит-тестов и **XCUITest** для тестов интерфейса. Ты получил от команды
файл `.xcresult` — дамп прогона тестов, — и надо понять, что там внутри. Заодно проверить,
не утекло ли что-нибудь в приложенные скриншоты и логи.

## Что такое XCTest и XCUITest

**XCTest** — это фреймворк Apple для написания тестов на Swift или Objective-C. Тесты
бывают двух видов:

- **юнит-тесты** — проверяют функции и классы напрямую, без интерфейса;
- **UI-тесты (XCUITest)** — управляют приложением через **accessibility**-слой: находят
  кнопки и поля по их меткам и водят «палец» по экрану.

Ключевое отличие от Espresso: XCUITest **не живёт внутри процесса** приложения. Он
работает как отдельный процесс-«водитель» и общается с приложением через систему
доступности. Это ближе к Appium, чем к Espresso.

## Наш пример: дамп .xcresult

`.xcresult` — это папка-пакет, где лежат результаты: статусы тестов, тайминги и
**вложения** (attachments). Вот текстовый дамп (в практике ты разберёшь его):

```
Test Case '-[BankUITests testTransfer]' failed (0.412 seconds).
  Attachments:
    - nto{xcu1t3st_4tt4chm3nt_l34k}.png (screenshot on failure)
    - console.txt
Executed 1 test, with 1 failure
```

Читаем. Тест `testTransfer` упал, и система на падении **сохранила скриншот**. Имя
вложения — это и есть флаг в практике. Для пентестера важнее другое: вложения XCUITest
почти всегда содержат **скриншоты экрана и консольный лог** на момент падения. Если в этот
момент на экране были секретные данные (токен, номер карты), они окажутся в отчёте.

## Шаг 1: анатомия XCUITest

Тест на Swift выглядит так:

```swift
func testLogin() {
    let app = XCUIApplication()
    app.launch()
    app.textFields["login"].tap()
    app.textFields["login"].typeText("alice")
    app.secureTextFields["password"].typeText("hunter2")
    app.buttons["submit"].tap()
    XCTAssertTrue(app.staticTexts["balance"].waitForExistence(timeout: 3))
}
```

Здесь `XCUIApplication` — приложение под управлением теста, а элементы ищутся по
accessibility-меткам: `textFields["login"]`, `buttons["submit"]`. `XCTAssertTrue` — проверка,
которая при провале сохраняет скриншот.

## Шаг 2: где взять дамп отчёта

Из командной строки результаты прогона достаются так:

```
$ xcrun xcresulttool get --path Bank.xcresult --format json
```

`xcresulttool` — утилита Apple для чтения `.xcresult`. JSON удобно фильтровать через
`jq`. Именно так ты достанешь список вложений и поймёшь, какие скриншоты и логи уехали в
отчёт.

## Шаг 3: XCUITest и пентест

Три практических вывода:

1. **Тест — воспроизведение.** Написав XCUITest, ты можешь за минуты прогонять сложный
   сценарий (ввод данных, переходы) и смотреть, что утекает на экран.
2. **Accessibility-метки — это карта.** XCUITest ищет элементы по меткам; если метка
   осмысленная (`secureTextFields["password"]`), ты быстро поймёшь структуру экрана.
3. **Вложения — риск.** Скриншоты на падении часто содержат то, что видеть в отчёте не
   должны.

## Шаг 4: запуск

```
$ xcodebuild test -scheme Bank -destination 'platform=iOS Simulator,name=iPhone 15'
```

`xcodebuild test` собирает приложение и прогоняет тесты на выбранном симуляторе или
устройстве. Результат складывается в `.xcresult`, который мы и разбирали.

## Что мы теперь знаем

- XCTest — юнит-тесты, XCUITest — тесты интерфейса через accessibility.
- XCUITest не живёт внутри процесса приложения, в отличие от Espresso.
- `.xcresult` хранит статусы, тайминги и вложения (скриншоты, логи).
- Вложения на падении — частый источник утечек на пентесте.
- Читать отчёт — `xcrun xcresulttool get`.

## Внутренняя структура `.xcresult`

`.xcresult` — не один файл, а пакет каталогов. Внутри лежат `Info.plist` с метаданными прогона, `Data/` с бинарными результатами и `Content/` с вложениями. Прямой обход каталога через `find Bank.xcresult -type f` сразу показывает, сколько там скриншотов и текстовых логов. Часто этого достаточно, чтобы оценить объём утечки.

Метаданные прогона включают дату, хост, версию Xcode, имя схемы и конфигурацию (`Debug`/`Release`). Для пентестера важны два поля: список тестов и время их выполнения. Если в дампе есть тест, которого нет в публичном наборе, возможно, вы смотрите на внутренний, не отданный наружу прогон.

## `xcresulttool` на практике

Простейший разбор начинается с общей сводки:

```bash
$ xcrun xcresulttool get --path Bank.xcresult --format json | jq '.actions[].actionResult'
```

Поле `actionResult` содержит итог: сколько тестов прошло, сколько упало, сколько пропущено. Дальше идём за вложениями. Вложения адресуются по идентификаторам, поэтому их вытаскивают в два шага: сначала получают список ссылок, затем экспортируют каждую:

```bash
$ xcrun xcresulttool get --path Bank.xcresult --format json \
    | jq -r '..|objects|select(.attachments?)|.attachments[]?.payloadRef.id' | sort -u
$ xcrun xcresulttool export --path Bank.xcresult --id <id> --output-path shot.png --type file
```

На старых версиях Xcode формат ответа отличается (`get --format json` без вложенных `actions`), поэтому команды стоит проверять по `--help` своей версии. На новых есть подкоманда `get object` с `--id` для конкретного узла дерева результатов.

## Reference: что искать во вложениях

| Тип вложения | Что там может быть |
|--------------|--------------------|
| Скриншот экрана | введённые данные, токены, номера карт, PII |
| Скриншот элемента | содержимое конкретного поля/таблицы |
| Консольный лог (`console.txt`) | отладочные сообщения, URL, ответы API |
| Дамп иерархии UI | полное дерево accessibility с текстами |
| Файл-артефакт | сохранённый в тесте документ/изображение |
| Метрики производительности | длительности, размеры, иногда пути |

Отдельно стоит искать **UI-иерархию**: `xcrun simctl io booted screenshot` — не единственный способ увидеть экран, тесты часто прикладывают полное дерево элементов. Из него видно все тексты на экране в момент падения, даже те, что не попали в скриншот.

## Написание XCUITest для воспроизведения сценария

Тест-«водитель» — это воспроизводимый пентест. Пример сценария, который логинится, открывает переводы и снимает экран на подозрительном шаге:

```swift
func testDumpTransfer() {
    let app = XCUIApplication()
    app.launchArguments = ["-UITest"]
    app.launch()
    app.textFields["login"].tap()
    app.textFields["login"].typeText("alice")
    app.secureTextFields["password"].tap()
    app.secureTextFields["password"].typeText("hunter2")
    app.buttons["submit"].tap()
    app.buttons["transfer"].tap()
    let shot = XCTAttachment(screenshot: app.screenshot())
    shot.name = "transfer-screen"
    shot.lifetime = .keepAlways
    add(shot)
}
```

Ключевое отличие от Espresso — элементы ищутся не по идентификаторам View, а по **accessibility**. Это значит, что тест переживает смену фреймворка UI, но ломается, если разработчик переименовал метку.

## Accessibility-метки как карта приложения

XCUITest видит только то, что приложение объявило доступным. Если разработчик ставит осмысленные метки, тест читается как документация: `secureTextFields["password"]`, `buttons["submit"]`, `cells["account-row-3"]`. При реверсе это подсказывает структуру экранов без дизассемблера.

Обратная сторона — безопасность. Метка не должна раскрывать смысл данных (`cells["admin-token"]` — плохая практика). Проверьте, не объявлены ли accessibility-идентификаторы для секретных элементов: по ним данные можно автоматически извлекать, в том числе инструментами скринридера.

## Как читать упавший тест

Падение — это момент, когда приложение оказалось в неожиданном состоянии. Именно поэтому система сохраняет скриншот и лог. Порядок разбора: сначала статус (`failed`/`passed`), затем сообщение об ошибке (`XCTAssertTrue failed - balance not found`), затем вложения. Сообщение часто прямо называет проверяемый элемент, а вложения показывают, что было на экране.

Если тест упал из-за таймаута (`waitForExistence(timeout:)` истёк), скриншот покажет, на каком экране застряло приложение — это может быть экран ошибки с чувствительным текстом.

## Если не сработало

- **`xcresulttool` ругается на формат.** Версия инструмента не совпадает с версией Xcode, создавшей отчёт. Укажите нужный тулчейн через `xcrun --toolchain` или откройте отчёт в Xcode.
- **Вложений нет.** В тесте не вызывался `add(...)`, а автоматический скриншот на падении отключён флагом. Проверьте настройки схемы.
- **Скриншоты пустые/чёрные.** Устройство блокировалось во время прогона (secure screen). Тогда используйте дамп UI-иерархии.
- **Тест не находит элемент.** Метка изменилась или элемент недоступен. Снимите дерево через `app.debugDescription` и сверьте метки.

## Ограничения подхода

XCUITest даёт детерминированное воспроизведение, но медленнее и тяжелее юнит-тестов: каждый шаг — межпроцессное взаимодействие. Для массового сканирования состояний он не подходит. Зато для точечного воспроизведения сложного сценария, где важно зафиксировать момент утечки, ему нет равных.

## Сравнение XCUITest, Espresso и Appium

Три инструмента автоматизации решают одну задачу, но по-разному. Espresso живёт внутри процесса Android-приложения и обращается к объектам View напрямую — поэтому быстрый, но хрупкий. XCUITest работает как внешний процесс-водитель через accessibility — устойчивее к смене UI, но медленнее. Appium объединяет оба мира через протокол WebDriver и умеет и Android, и iOS, ценой ещё одного слоя.

| Свойство | Espresso | XCUITest | Appium |
|----------|----------|----------|--------|
| Где работает | в процессе | вне процесса | вне процесса |
| Как ищет элементы | объекты View | accessibility | accessibility/View |
| Платформа | Android | iOS | обе |
| Скорость | высокая | средняя | низкая |

Для пентеста это означает: если нужно быстро перебрать состояния Android-приложения — Espresso; если зафиксировать утечку в iOS-сценарии — XCUITest; если нужен единый кросс-платформенный набор — Appium. Выбор инструмента диктуется задачей, а не привычкой.
