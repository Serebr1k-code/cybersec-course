## Вопрос, с которого всё начинается

Ты вводишь пароль от банка — а на устройстве установлена «умная» клавиатура со словарём и
облачной синхронизацией. Видит ли она твой пароль? Если это сторонний **IME** — да, видит
каждое нажатие. Как это обнаружить и что может противопоставить приложение?

## Наш пример: список клавиатур

Смотрим установленные IME:

```bash
$ adb shell ime list -a | grep -E 'mId|packageName'
com.example.smartkb/.SmartKbIme
com.android.inputmethod.latin/.LatinIME
```

Первая — сторонняя «умная» клавиатура. Весь урок ведём её.

## Шаг 1: что такое IME

**IME** (Input Method Editor) — системный компонент, который обрабатывает ввод с клавиатуры.
Когда ты печатаешь, символы проходят через IME: он может дополнять слова, исправлять опечатки,
предлагать эмодзи. По определению он видит всё, что вводится в любое поле любого приложения —
включая пароли.

## Шаг 2: как IME читает ввод

IME реализует `InputMethodService` и получает **InputConnection** — канал к полю ввода. Через
него он читает текст (`getTextBeforeCursor`), вставляет символы, узнаёт контекст. Всё, что
видит IME, он может записать и отправить.

```java
@Override public void onStartInput(EditorInfo info, boolean restarting) {
    // info.inputType подсказывает, что за поле (текст, пароль, число)
}
```

## Шаг 3: признак парольного поля

В `EditorInfo.inputType` есть флаг `TYPE_TEXT_VARIATION_PASSWORD` (и `..._VISIBLE_PASSWORD`,
`..._WEB_PASSWORD`). Хороший IME при виде этого флага **отключает** обучение словаря и
синхронизацию. Плохой — продолжает логировать. Поэтому проверяют, обрабатывает ли IME этот
флаг.

## Шаг 4: как найти клавиатуру-кейлоггер

- Анализ APK IME: искать запись ввода (`getTextBeforeCursor`, `commitText` в логи/сеть).
- Разрешения: `INTERNET` у клавиатуры — тревожный признак.
- Сетевые вызовы из IME.
- Наличие словаря/телеметрии.

```bash
$ grep -rn 'getTextBeforeCursor\|commitText\|INTERNET' ime_apk_smali/ | head
```

## Шаг 5: что может приложение

Приложение не может запретить сторонний IME (пользователь выбирает его сам). Но может:
- помечать поля как парольные (`TYPE_TEXT_VARIATION_PASSWORD`), чтобы честный IME отключил
  обучение;
- использовать `setPrivateImeOptions` / `IME_FLAG_NO_PERSONALIZED_LEARNING` для чувствительных
  полей;
- для самых критичных случаев — собственный ввод (своя цифровая клавиатура внутри приложения),
  не отдающий данные системному IME.

```java
editText.setImeOptions(EditorInfo.IME_FLAG_NO_PERSONALIZED_LEARNING);
```

## Шаг 6: собственная клавиатура

Банки часто рисуют свою цифровую клавиатуру для PIN: ввод не идёт через системный IME, и
сторонняя клавиатура его не видит. Минус — неудобство и доступность. Это компромисс между
безопасностью и удобством, и он должен быть осознанным.

## Шаг 7: автозаполнение и буфер

Рядом с IME — **Autofill** (системное заполнение паролей) и **буфер обмена**. Все три —
каналы ввода/вывода секретов. Пароль, скопированный в буфер, читается другими приложениями;
автозаполнение может предлагать пароль не тому приложению. Аудит рассматривает их вместе.

## Шаг 8: как оформить находку

«Сторонняя клавиатура `com.example.smartkb` с разрешением INTERNET логирует вводимый текст
(`getTextBeforeCursor` → сеть), включая поля паролей; приложение не помечает парольные поля
флагами, отключающими обучение.» Указывают IME, код и отсутствие защиты на стороне приложения.

## Шаг 9: как защищают правильно

Приложение: помечать парольные поля, отключать персонализированное обучение, для критичных
секретов — собственный ввод, не копировать секреты в буфер. Пользователь: доверенные
клавиатуры, минимум разрешений, проверка списка IME. Система: изоляция IME и индикаторы.
Ни один из уровней не абсолютен, поэтому важны все три.

## Шаг 10: категории IME

IME бывают системные (от производителя) и сторонние (из магазина). Сторонние несут больше
риска: они обрабатывают ввод и часто имеют доступ к сети. Проверяют: список активных IME,
какой выбран по умолчанию, какие у них разрешения. Клавиатура без необходимости в сети — не
должна иметь `INTERNET`.

```bash
$ adb shell ime list -s
$ adb shell dumpsys package com.example.smartkb | grep -i 'permission\|INTERNET'
```

## Шаг 11: автозаполнение и буфер

Рядом с IME — **Autofill** и **буфер обмена**. Autofill подставляет пароли из менеджера: если
приложение не помечает поля, пароль может уехать не туда. Буфер обмена читается другими
приложениями: скопированный пароль доступен. Аудит ввода рассматривает IME, Autofill и буфер
как один набор каналов и проверяет их вместе.

## Шаг 12: своя клавиатура против доступности

Собственная клавиатура защищает от стороннего IME, но ухудшает **доступность** (скринридеры,
специальные возможности) и может быть неудобна. Поэтому решение должно быть осознанным:
для PIN — своя клавиатура, для обычных полей — системный IME с правильными флагами. Аудит
отмечает, где компромисс сделан осознанно, а где просто забыли пометить поле.

## Шаг 13: что писать в отчёте

«Сторонняя клавиатура `com.example.smartkb` с разрешением `INTERNET` читает вводимый текст
(`getTextBeforeCursor`) и передаёт его в сеть; приложение не помечает парольные поля флагами,
отключающими персонализированное обучение». Указывают IME, код и отсутствие защиты.

## Если не сработало

Если клавиатура не логирует ввод и не имеет лишних разрешений — это нормальный IME, зафиксируй
это. Тогда проверь Autofill и буфер обмена: секрет может утекать через них. И помни: полностью
защититься от ввода можно только своей клавиатурой, но это всегда компромисс с удобством и
доступностью.
## Полный прогон: поиск кейлоггера

**Шаг A.** Смотрим активные IME:

```bash
$ adb shell ime list -s
com.example.smartkb/.SmartKbIme
com.android.inputmethod.latin/.LatinIME
```

**Шаг B.** Проверяем разрешения сторонней клавиатуры:

```bash
$ adb shell dumpsys package com.example.smartkb | grep -i INTERNET
android.permission.INTERNET
```

**Шаг C.** Анализируем APK: читает ли `getTextBeforeCursor` и шлёт ли данные в сеть.

**Шаг D.** Проверяем, помечает ли приложение парольные поля флагами, отключающими обучение.

**Шаг E.** Вывод: сторонняя клавиатура с сетью и логированием ввода — канал утечки;
рекомендация — помечать поля и использовать свою клавиатуру для PIN.

## Частые ошибки

- Считать, что клавиатура «просто вводит текст».
- Не проверять разрешение INTERNET у IME.
- Игнорировать Autofill и буфер обмена.
- Не проверять флаги парольных полей в приложении.
## Как это устроено внутри

IME — это посредник между пользователем и полем ввода. Когда ты печатаешь, символы идут не
напрямую в `EditText`, а через `InputMethodService`, который получает `InputConnection` к
активному полю. Через этот канал IME читает контекст (что уже введено), предлагает варианты и
вставляет текст. Это необходимо для автокоррекции и словарей — и это же даёт полный доступ к
вводимому.

Ключевой сигнал для IME — `EditorInfo.inputType` активного поля. Флаг
`TYPE_TEXT_VARIATION_PASSWORD` говорит: «это пароль». Добросовестная клавиатура при виде флага
перестаёт обучаться и синхронизироваться. Недобросовестная — продолжает. Поэтому аудит IME
сводится к вопросу, обрабатывает ли он этот флаг и не уходит ли ввод в сеть.

Приложение не контролирует, какую клавиатуру выбрал пользователь. Но оно может помечать
чувствительные поля и, для самых критичных секретов, рисовать **свою** клавиатуру, не отдавая
ввод системному IME. Это компромисс с удобством и доступностью, и он должен быть осознанным.
Рядом стоят Autofill и буфер обмена — ещё два канала того же типа; их проверяют вместе с IME,
потому что секрет может утечь не через нажатия, а через них.
## Типичный сценарий на реальном устройстве

Ты проверяешь устройство, на котором установлена «умная» клавиатура из магазина. Смотришь её
разрешения — есть `INTERNET`. Разбираешь APK: клавиатура читает ввод через `getTextBeforeCursor`
и отправляет его на сервер вместе с именем пакета активного приложения. То есть она видит не
только текст, но и в какое приложение он вводится.

Дальше ты проверяешь, помечает ли банковское приложение парольные поля: открываешь экран входа
и смотришь, отключается ли у клавиатуры обучение. Если нет — пароль уходит в сеть. В отчёт идут
две находки: клавиатура-кейлоггер и приложение, не защитившее ввод. Рекомендации разные:
пользователю — сменить клавиатуру, разработчику — помечать поля и использовать свою клавиатуру
для PIN. Этот сценарий хорошо показывает, что безопасность ввода — совместная ответственность
системы, приложения и пользователя, и ни один уровень не абсолютен.
## Что важно не перепутать

Не путай **клавиатуру** и **приложение**: приложение не может запретить сторонний IME, но может
защитить ввод флагами и собственной раскладкой. Не путай **ввод** и **уведомления**: OTP может
прийти в панель уведомлений, где его прочитает слушатель, даже если клавиатура чиста. И не
путай **неудобство** с **небезопасностью**: своя клавиатура защищает ввод, но ухудшает
доступность — это осознанный компромисс, а не однозначное «правильно». В отчёте разделяй
ответственность уровней: система (изоляция IME), приложение (флаги и своя раскладка),
пользователь (выбор доверенной клавиатуры). Находка должна указывать, какой именно уровень не
сработал, иначе рекомендация получится размытой.
## Итоговая мысль

Ввод — это канал, и он не защищён по умолчанию: любая установленная клавиатура видит то, что
ты печатаешь. Защита складывается из трёх уровней: система изолирует IME, приложение помечает
секретные поля и при необходимости рисует свою раскладку, пользователь выбирает доверенную
клавиатуру. Ни один уровень не абсолютен, поэтому в отчёте важно показать, какой именно не
сработал, и не путать неудобство с уязвимостью.
## Что мы теперь знаем

- IME видит весь вводимый текст, включая пароли.
- Хороший IME отключает обучение на парольных полях.
- Признаки кейлоггера: чтение ввода, INTERNET, сетевые вызовы.
- Приложение может помечать поля и рисовать свою клавиатуру.
- Autofill и буфер обмена — соседние каналы утечки.
