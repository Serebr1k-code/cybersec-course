## Вопрос, с которого всё начинается

В APK лежат нативные библиотеки `lib/arm64-v8a/*.so`. Кто и когда их загружает? Как Java-код
вызывает C-функцию? И — главное для атакующего — можно ли подсунуть приложению свою библиотеку
вместо настоящей? Разберём жизненный цикл нативного кода.

## Наш пример: libfoo.so из app.apk

Смотрим, что за библиотека:

```bash
$ readelf -h libfoo.so | grep -E 'Type|Machine'
  Type: DYN (Shared object file)
  Machine: AArch64
```

`readelf` — инструмент для разбора ELF-файлов (формат исполняемых файлов Linux/Android). `DYN`
означает, что это разделяемая библиотека (shared object), а не исполняемый файл.

## Шаг 1: как Java загружает библиотеку

В Java-коде приложения:

```java
static { System.loadLibrary("foo"); }
```

`System.loadLibrary("foo")` заставляет систему найти `libfoo.so` и загрузить её в процесс.
Дальше Java может вызывать нативные методы, объявленные как `native`.

## Шаг 2: JNI-мост

Связь Java и C — через JNI. Java объявляет метод:

```java
public static native int check(String s);
```

А в C есть функция с именем, закодированным из класса и метода:

```c
JNIEXPORT jint JNICALL Java_com_example_NativeChecker_check(JNIEnv *env, jclass c, jstring s)
```

`JNIEXPORT`/`JNICALL` — макросы, `JNIEnv*` — таблица функций для работы с Java. По имени
`Java_...` система сопоставляет вызов.

## Шаг 3: чтение символов

```bash
$ nm -D libfoo.so | grep -i check
0000000000012a40 T Java_com_example_NativeChecker_check
$ readelf -s libfoo.so | grep FUNC | head
```

`nm -D` показывает динамические символы, `T` — определённый (экспортированный) символ. Так
находят точки входа, которые можно хукать.

## Шаг 4: инъекция через dlopen

`dlopen` — функция, которая загружает библиотеку в уже работающий процесс. Если приложение
уязвимо (например, загружает `.so` из внешнего каталога), можно подсунуть свою. Более
контролируемый путь — Frida:

```javascript
var dlopen = Module.findExportByName(null, 'dlopen');
```

## Шаг 5: подмена библиотеки

Самый простой приём на rooted-устройстве — заменить `libfoo.so` в каталоге приложения своей
версией (с той же архитектурой). Тогда при следующем запуске загрузится наш код. Это требует
доступа к каталогу данных приложения.

## Шаг 6: LD_PRELOAD на Android

На Linux `LD_PRELOAD` подставляет библиотеку до всех остальных. На Android он работает только
для процессов, запущенных с соответствующим окружением (обычно через `setprop wrap.<pkg>`),
поэтому чаще используют Frida или патч загрузчика.

## Шаг 7: защита

Разработчики защищаются: проверяют хеши `.so`, подписи, целостность загрузки, используют
anti-hook. Поэтому инъекция — это гонка: чем сложнее проверка, тем больше усилий на обход.

## Что мы теперь знаем

- `.so` — разделяемая библиотека, загружается через System.loadLibrary.
- JNI связывает Java-метод с C-функцией по имени.
- Символы читают через nm/readelf.
- Инъекция возможна через dlopen/подмену/Frida.
- Защита — проверки целостности и anti-hook.

## Откуда берётся путь библиотеки

`System.loadLibrary("foo")` не содержит пути — система сама ищет `libfoo.so`. Мест поиска
несколько, и от конфигурации зависит, откуда библиотека загрузится.

- Внутри APK: `lib/<abi>/libfoo.so`, где `<abi>` — `arm64-v8a`, `armeabi-v7a`, `x86`, `x86_64`.
- На диске после установки: каталог `nativeLibraryDir` приложения (если `extractNativeLibs=true`).
- В системных каталогах (`/system/lib64/`) — для системных библиотек.

Если в манифесте стоит `android:extractNativeLibs="false"`, библиотеки не распаковываются на
диск, а загружаются прямо из APK. Это влияет на анализ: файла `libfoo.so` в каталоге приложения
может не быть, хотя библиотека работает.

```bash
$ unzip -l app.apk | grep 'lib/'
  lib/arm64-v8a/libfoo.so
  lib/armeabi-v7a/libfoo.so
```

## Таблица: инструменты и что они дают

Для нативного анализа важен правильный инструмент под задачу.

| Инструмент | Что показывает | Пример |
|---|---|---|
| readelf -h | тип и архитектура | Type: DYN, Machine: AArch64 |
| readelf -s | таблица символов | адреса функций |
| readelf -d | зависимости (NEEDED) | libc.so, liblog.so |
| nm -D | динамические символы | экспортируемые функции |
| objdump -T | динамические символы | альтернатива nm |
| strings | строки-маркеры | пути, сообщения |

Комбинация `readelf -d` + `strings` часто сразу показывает, с чем библиотека работает: какие
системные библиотеки ей нужны и какие строки она содержит.

## Разбор JNI и динамическая регистрация

Связь Java и C бывает двух видов. Первый — статическая: имя C-функции кодирует класс и метод.

```c
JNIEXPORT jint JNICALL Java_com_example_NativeChecker_check(JNIEnv *env, jclass c, jstring s)
```

Здесь всё видно в символах: `nm -D` покажет `Java_com_example_NativeChecker_check`.

Второй — динамическая регистрация. В этом случае функция называется произвольно, а связь
устанавливается в `JNI_OnLoad` через `RegisterNatives` с таблицей `JNINativeMethod`.

```c
static const JNINativeMethod methods[] = {
  {"check", "(Ljava/lang/String;)I", (void*)my_check_impl},
};
JNIEXPORT jint JNICALL JNI_OnLoad(JavaVM *vm, void *reserved) {
  // ... RegisterNatives(env, clazz, methods, 1);
  return JNI_VERSION_1_6;
}
```

Для аналитика это означает: если `nm -D` не показывает `Java_...`-функций, ищите `JNI_OnLoad` и
таблицу `RegisterNatives` — именно там сопоставление имён. Это же приём обфускации: имена методов
не выдают логику.

## Инъекция: Frida Interceptor и подмена экспорта

Самый гибкий способ вмешаться в нативный код — перехватить функцию и подменить её результат или
аргументы.

```javascript
var addr = Module.findExportByName('libfoo.so', 'Java_com_example_NativeChecker_check');
Interceptor.attach(addr, {
  onEnter: function (args) { this.s = args[2]; },
  onLeave: function (retval) { retval.replace(0); }
});
```

`findExportByName` находит адрес экспортированной функции, `Interceptor.attach` ставит хук,
`onLeave` меняет возвращаемое значение. Так нейтрализуют нативные проверки, не трогая файл.

Если функция не экспортирована (внутренняя), её находят по смещению: базовый адрес библиотеки
плюс офсет из дизассемблера.

## Проверка целостности .so

Разработчики защищаются от подмены: считают хеш библиотеки при загрузке и сравнивают с
ожидаемым, проверяют подпись APK, контролируют карту памяти на посторонние модули. Обход:

- подменить ожидаемое значение хеша (патч константы в коде);
- заставить функцию проверки вернуть «ок» (хук);
- загрузить свой код так, чтобы он не появлялся в `/proc/self/maps` (сложнее).

Готовые инструменты (например, anti-root/anti-debug скрипты) часто уже содержат такие обходы.

## Если не сработало

Если `System.loadLibrary` падает с `UnsatisfiedLinkError`, — библиотеки нет под текущую
архитектуру или имя не совпадает. Проверьте `unzip -l app.apk | grep 'lib/<abi>'`.

Если `nm -D` не показывает нужных символов, — либо они не экспортированы, либо включена
динамическая регистрация. Ищите `JNI_OnLoad`.

Если хук не срабатывает, — возможно, библиотека ещё не загружена в момент установки хука. Ставьте
хук после загрузки (`dlopen`-хук) или используйте `Module.load`-событие в Frida.

## Ограничения

Нативный слой сложнее Java: нет байткода, есть машинный код и архитектуры. Полноценный анализ
требует дизассемблера (Ghidra, IDA) и понимания ABI.

Кроме того, инъекция в чужое приложение — это часть авторизованного теста или анализа
собственного кода. Подмена библиотек в чужих приложениях для распространения вредоносных сборок
недопустима.

Наконец, помните про разные архитектуры: код, отлаженный на `x86_64` (эмулятор), может
отличаться от `arm64-v8a` (устройство). Сверяйте ABI при анализе.

## Мини-практика: разобрать JNI-библиотеку

Пройдём путь от `.so` до конкретной функции.

Шаг 1. Определяем архитектуру и зависимости:

```bash
$ readelf -h libfoo.so | grep -E 'Machine|Type'
  Type: DYN (Shared object file)
  Machine: AArch64
$ readelf -d libfoo.so | grep NEEDED
 0x0000000000000001 (NEEDED)  Shared library: [liblog.so]
 0x0000000000000001 (NEEDED)  Shared library: [libc.so]
```

Шаг 2. Ищем экспортируемые JNI-функции:

```bash
$ nm -D libfoo.so | grep ' T Java_'
0000000000012a40 T Java_com_example_NativeChecker_check
```

Шаг 3. Если `Java_`-функций нет, ищем динамическую регистрацию:

```bash
$ nm -D libfoo.so | grep -i 'JNI_OnLoad'
0000000000011000 T JNI_OnLoad
$ strings libfoo.so | grep -iE 'check|verify|root'
```

`JNI_OnLoad` плюс строки-маркеры указывают, что имена методов регистрируются в таблице
`RegisterNatives`, и связь надо искать там.

Шаг 4. Открываем библиотеку в Ghidra/IDA, находим `JNI_OnLoad`, смотрим таблицу методов и
переходим к реализации.

## Частые ошибки

Ошибка первая — искать только `Java_`-функции. При динамической регистрации их нет, и можно
ошибочно решить, что JNI-моста нет вовсе.

Ошибка вторая — путать `nm` и `nm -D`. Первый показывает все символы (включая отладочные), второй
— только динамические. Для разделяемой библиотеки обычно нужен `-D`.

Ошибка третья — забыть про архитектуру. Офсет функции на `arm64` не совпадёт с `x86_64`; хуки по
смещению надо считать под ту архитектуру, что на устройстве.

## Зачем это нужно на практике

Понимание нативного слоя открывает доступ к логике, которую часто прячут в `.so`: проверки
лицензии, криптографию, anti-tamper. Разобрав JNI-мост, вы получаете точку входа — конкретную
функцию, которую можно хукать или анализировать. Без этого нативная часть остаётся чёрным
ящиком.

## Шпаргалка: команды для .so

| Задача | Команда |
|---|---|
| архитектура | `readelf -h libfoo.so` |
| зависимости | `readelf -d libfoo.so` |
| экспорты | `nm -D libfoo.so` |
| динамическая регистрация | `nm -D libfoo.so \| grep JNI_OnLoad` |
| строки-маркеры | `strings libfoo.so` |
| все символы | `readelf -s libfoo.so` |

Порядок разбора прост: `readelf -h` → `readelf -d` → `nm -D` → `strings`. Если `Java_`-функций нет,
ищите `JNI_OnLoad` и таблицу `RegisterNatives` — там сопоставление Java-методов и нативного кода.
