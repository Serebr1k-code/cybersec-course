## Вопрос, с которого всё начинается

Ты поставил прокси, установил свой CA в системное хранилище, обошёл Java-пиннинг — а трафик
всё равно не идёт. Приложение рвёт соединение с тем же сообщением «certificate pinning failure».
Значит, проверка сертификата живёт не в Java, а глубже — в **нативном коде**. Как её найти и
чем обойти?

## Наш пример: .so с собственной проверкой

У нас есть APK банковского приложения. Разберём его нативную библиотеку:

```bash
$ unzip -o app.apk 'lib/*' -d app_native
$ file app_native/lib/arm64-v8a/libnative-lib.so
app_native/lib/arm64-v8a/libnative-lib.so: ELF 64-bit LSB shared object, ARM aarch64, ...
```

Внутри — библиотека на C/C++, собранная под ARM64. Именно туда приложение перенесло проверку
сертификата. Весь урок ведём этот `.so`.

## Шаг 1: как вообще устроен пиннинг

**Пиннинг** (pinning) — привязка доверия к конкретному сертификату или публичному ключу
сервера, а не к любому, подписанному доверенным CA. В Java это делают через
`X509TrustManager` или `CertificatePinner` (OkHttp). Но злоумышленник может подменить Java-код
хуком — поэтому приложения переносят проверку в **нативный слой**.

**Нативный код** — это код, скомпилированный в машинные инструкции (`.so`), который Java
вызывает через **JNI** (Java Native Interface). Хукнуть Java-метод легко; хукнуть функцию
внутри `.so` сложнее, потому что там нет имён методов, только адреса.

## Шаг 2: находим проверку в .so

Смотрим, какие функции библиотека импортирует — это подсказки о том, что она делает:

```bash
$ strings -a app_native/lib/arm64-v8a/libnative-lib.so | grep -i 'ssl\|verify\|pin'
SSL_CTX_set_verify
X509_verify_cert
sha256
pin_expected
```

Строки `SSL_CTX_set_verify` и `X509_verify_cert` — верный признак: библиотека сама проверяет
цепочку сертификатов через OpenSSL/BoringSSL. Функция `SSL_CTX_set_verify` задаёт callback,
который вызывается на каждом сертификате; если callback вернёт 0 — соединение разорвётся.

## Шаг 3: почему Java-хук не работает

Обход Java-пиннинга (Frida-скрипт, подменяющий `TrustManager`) меняет поведение Java-слоя. Но
наш `.so` вызывает `SSL_CTX_set_verify` **напрямую** и не спрашивает Java. Поэтому Java-хук
проходит мимо: проверка идёт в C, до или в обход Java. Это классическая причина «трафик не
идёт, хотя пиннинг вроде обойдён».

## Шаг 4: перехватываем нативную функцию

Frida умеет хукать и нативные функции по адресу или по имени экспорта. Подменяем callback
верификации так, чтобы он всегда возвращал «успех»:

```javascript
// hook_native_pin.js
const f = Module.findExportByName('libnative-lib.so', 'SSL_CTX_set_verify');
Interceptor.attach(f, {
  onEnter(args) {
    // args[1] — режим verify, args[2] — callback; заставим доверять всему
    this.mode = args[1];
    args[1] = ptr(0); // SSL_VERIFY_NONE
  },
  onLeave() { send('native verify disabled'); }
});
```

Запуск:

```bash
$ frida -U -f com.example.bank -l hook_native_pin.js --no-pause
[*] native verify disabled
```

Теперь приложение считает соединение валидным, и прокси видит трафик.

## Шаг 5: если функция не экспортируется

Часто callback — статическая функция без имени, найти её по экспорту нельзя. Тогда ищут по
вызову: находят адрес `SSL_CTX_set_verify` и смотрят аргумент-callback, либо патчат саму
`X509_verify_cert`, возвращая 1. В Ghidra ищут функцию, которая читает ожидаемый отпечаток
(`pin_expected`) и сравнивает с SHA-256 сертификата.

```bash
$ strings -a libnative-lib.so | grep -i sha
sha256
```

Алгоритм подсказывает: сравнивается SHA-256. Значит, обойти можно либо отключив verify, либо
подменив результат сравнения.

## Шаг 6: что ещё проверяют нативно

Нативный пиннинг — не только проверка сертификата. Встречаются: проверка отпечатка
**публичного ключа** (SPKI), проверка на уровне сокета, проверка, что в цепочке ровно один
сертификат. Каждая — отдельная функция. Поэтому обход «в один хук» не всегда работает: надо
перечислить все места, где вызывается verify.

## Шаг 7: диагностика — трафик или проверка?

Прежде чем хукать, убедись, что проблема в проверке, а не в прокси. Признаки нативного
пиннинга: соединение рвётся сразу после рукопожатия; в логах — сообщение приложения о
пиннинге; Java-хук не помогает. Если трафик вообще не появляется — возможно, приложение
использует QUIC/HTTP3 или свой сокет.

## Шаг 8: правильный порядок обхода

1. Убедиться, что Java-хук не помогает (значит, слой нативный).
2. Найти в `.so` вызовы `SSL_CTX_set_verify` / `X509_verify_cert`.
3. Подменить режим verify или результат проверки.
4. Проверить трафик на прокси.
5. Если остались разрывы — искать вторую проверку (SPKI, отпечаток ключа).

## Шаг 9: почему это защита, а не панацея

Нативный пиннинг усложняет MITM, но не делает его невозможным: любой код на устройстве
исполняется, пока устройство под твоим контролем. Он лишь поднимает порог: нужен нативный
реверс и хукинг. Это и есть реальность мобильного пентеста — защиты не абсолютны, а
дополнительны.

## Шаг 10: как защищают по-настоящему

Разработчику нативный пиннинг стоит дополнять: несколькими отпечатками (ключ + сертификат),
проверкой целостности своего `.so`, обфускацией имён и **attestation** — серверным
подтверждением, что запрос идёт из неперепрошитого приложения на настоящем устройстве.
Пиннинг без attestation обходится хуком; attestation без пиннинга — подделкой клиента. Вместе
они дают заметно более высокий порог.

## Что мы теперь знаем

- Пиннинг бывает в Java и в нативном коде (`.so`).
- Нативный пиннинг ищут по строкам `SSL_CTX_set_verify`, `X509_verify_cert`, `sha256`.
- Java-хук его не обходит — нужен хук нативной функции.
- Обход: подмена режима verify или результата `X509_verify_cert`.
- Правильная защита — пиннинг + целостность + attestation.
