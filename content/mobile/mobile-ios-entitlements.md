## Вопрос, с которого всё начинается

Два приложения из App Store установлены рядом. Одно читает вашу геолокацию, другое — нет.
Одно пишет в общий Keychain-контейнер с другим приложением, другое изолировано. Почему?
Потому что каждое приложение **заявило** свои права в подписи — entitlements. Разберём, как
это работает и где искать опасные заявления.

## Наш пример: приложение с группой Keychain

Открываем entitlements тестового приложения:

```bash
$ codesign -d --entitlements :- example.app
<dict>
  <key>application-identifier</key><string>ABCDE12345.com.example.app</string>
  <key>keychain-access-groups</key>
  <array><string>ABCDE12345.com.example.shared</string></array>
  <key>com.apple.developer.associated-domains</key>
  <array><string>applinks:example.com</string></array>
</dict>
```

Здесь три заявления: идентификатор приложения, группа доступа к Keychain (общий контейнер
`shared`) и связанные домены (для Universal Links). Каждое из них даёт реальные возможности,
которые невозможно получить без соответствующего entitlement.

## Шаг 1: что такое entitlement

Entitlement — это **заявленное право**, которое подписано вместе с приложением. В отличие от
разрешений Android (которые запрашиваются в рантайме), entitlement фиксируется заранее, и
система доверяет ему, потому что он защищён подписью Apple. Если права нет в подписи — его
нельзя получить, даже имея код, который его требует.

## Шаг 2: категории entitlements

Условно их можно разделить так:

| Категория | Примеры | Что даёт |
|---|---|---|
| Приложение | application-identifier, team-identifier | идентичность |
| Данные | keychain-access-groups, app-groups | общие контейнеры |
| Возможности | associated-domains, aps-environment | push, deep links |
| Отладка | get-task-allow, task_for_pid-allow | отладка/инъекция |
| Приватные | com.apple.private.* | только для Apple/системы |

Последняя категория — самая интересная: `com.apple.private.*` заявляют системные приложения.
Если стороннее приложение может заявить такое право, это серьёзная уязвимость.

## Шаг 3: sandbox и entitlements

iOS-sandbox ограничивает приложение его контейнером. Entitlements «пробивают» sandbox в
разрешённых местах: общий Keychain, общие контейнеры App Groups, доступ к системным сервисам.
Например, `keychain-access-groups` позволяет двум приложениям одного разработчика читать
общие секреты — это by design, но при ошибке в группе секреты утекают к чужому приложению.

```bash
$ security cms -D -i embedded.mobileprovision | grep -A2 Entitlements
  <key>keychain-access-groups</key>
  <array><string>ABCDE12345.*</string></array>
```

Профиль может разрешать группу с wildcard `*` — тогда любое приложение команды может попасть
в общий контейнер. Это законно, но требует аккуратности.

## Шаг 4: task_for_pid и отладка

`get-task-allow` и `task_for_pid-allow` — entitlements отладки. Первый позволяет подключить
отладчик, второй — получать порты задач других процессов (по сути, читать их память).
В релизе их быть не должно.

```bash
$ codesign -d --entitlements :- example.app | grep -E 'task_for_pid|get-task-allow'
  <key>get-task-allow</key><true/>
```

Если в релизной сборке стоит `get-task-allow = true`, приложение можно отлаживать и
инъектировать без джейлбрейка — это находка.

## Шаг 5: как entitlement проверяется в рантайме

Когда приложение обращается к системному сервису (например, к Keychain), сервис смотрит
entitlements процесса и решает, разрешить ли доступ. Если заявление подделать нельзя (а оно
защищено подписью), то и обойти проверку нельзя — только переподписаться своим сертификатом
с нужным профилем, а это требует, чтобы Apple выдала такое право.

## Шаг 6: аудит entitlements

При оценке приложения смотрим:

1. Есть ли `get-task-allow` / `task_for_pid-allow` в релизе.
2. Не слишком ли широка группа Keychain (wildcard).
3. Нет ли `com.apple.private.*` в стороннем приложении.
4. Корректно ли ограничены associated-domains.

```bash
$ codesign -d --entitlements :- example.app | grep -c 'com.apple.private'
0
```

Ноль приватных прав — хорошо. Любое ненулевое значение — повод разобраться, как оно получено.

## Шаг 7: entitlements и серверная проверка

Сервер не видит entitlements напрямую, но видит результат: например, приложение с
`associated-domains` может открывать Universal Links. Если сервер полагается на то, что
«только наше приложение может так делать», его можно обмануть, переподписав приложение с тем
же доменом. Поэтому серверная защита снова упирается в аттестацию.

## Что мы теперь знаем

- Entitlement — подписанное заявление о праве.
- Категории: идентичность, данные, возможности, отладка, приватные.
- Entitlements расширяют sandbox в разрешённых местах.
- Опасные для релиза: get-task-allow, task_for_pid-allow, com.apple.private.*.
- Подделать entitlement нельзя — только переподписаться своим профилем.

## Шаг 8: App Groups и общие контейнеры

Помимо Keychain, приложения одного разработчика могут делить файловый контейнер через
`com.apple.security.application-groups`. Это используется для обмена данными между
приложением и его расширениями (виджеты, share-расширения). Право выглядит так:

```bash
$ codesign -d --entitlements :- Widget.appex
  <key>com.apple.security.application-groups</key>
  <array><string>group.com.example.shared</string></array>
```

Общий контейнер лежит по пути, начинающемуся с `group.`. Ошибка здесь — положить в общий
контейнер чувствительные данные (токены, ключи), к которым получают доступ все приложения
группы. Если хотя бы одно из них скомпрометировано, секреты утекают. Поэтому аудит должен
проверить, что именно лежит в общем контейнере, и нет ли там того, что должно быть приватным.

## Шаг 9: entitlement как цель атаки

Entitlements — не только защита, но и цель. Представим: приложение заявляет
`associated-domains` для `applinks:bank.example`. Сервер полагает, что открывать ссылки в
этом домене может только официальное приложение. Атакующий переподписывает свою сборку с тем
же `associated-domains` и bundle id — и серверные проверки, основанные только на домене,
обходятся.

Отсюда правило: **entitlements подтверждают возможности, но не личность**. Всё, что можно
переподписать, нельзя считать доказательством. Именно поэтому сильные схемы добавляют
аппаратную аттестацию, которая привязывает запрос к ключу в Secure Enclave и хешу конкретной
сборки.

## Шаг 10: чек-лист аудита entitlements

Практический список, по которому удобно проходить приложение:

1. Выгрузить все entitlements (`codesign -d --entitlements :-`).
2. Отметить отладочные права (`get-task-allow`, `task_for_pid-allow`) — в релизе их быть не
   должно.
3. Проверить группы Keychain и App Groups на предмет избыточной ширины (wildcard).
4. Убедиться, что нет `com.apple.private.*` у стороннего приложения.
5. Сверить entitlements в подписи и в профиле — расхождение подозрительно.
6. Для каждой возможности подумать, не полагается ли на неё сервер как на доказательство.

Такой проход занимает минуты, но регулярно выявляет как минимум избыточные права, а иногда и
серьёзные дыры в дизайне.

## Шаг 11: entitlement и расширения

Отдельный случай — расширения (app extensions). У каждого расширения свой набор entitlements
и свой sandbox. Общие данные между приложением и расширением передаются через App Groups или
общий Keychain. Ошибка в конфигурации группы приводит к тому, что расширение получает больше
доступа, чем нужно, — а расширения часто менее защищены и чаще содержат уязвимости. При
аудите полезно смотреть entitlements каждого `.appex` отдельно, а не только основного бандла.

## Шаг 12: entitlement и защита данных

Есть ещё один слой, тесно связанный с entitlements, — **Data Protection**. Каждый файл в
контейнере приложения имеет класс защиты, определяющий, когда он доступен: всегда, только при
разблокированном устройстве, только после ввода пароля. Приложение без специального
entitlement (`com.apple.developer.default-data-protection`) получает класс по умолчанию —
обычно `NSFileProtectionCompleteUntilFirstUserAuthentication`, то есть файл доступен после
первой разблокировки.

```bash
$ # класс защиты файла виден в атрибутах
$ ls -l@ Documents/secret.db
  com.apple.protection: NSFileProtectionComplete
```

Ошибка здесь — хранить чувствительные данные в файле с классом «доступен всегда». Тогда даже
заблокированный телефон отдаёт эти данные при физическом извлечении. При аудите полезно
проверять, какие классы защиты выставлены для баз данных, кэшей и токенов, и соответствует ли
класс чувствительности данных.

## Шаг 13: что запомнить про entitlements

Entitlements — это подписанные заявления, которые система превращает в реальные возможности:
доступ к общим контейнерам, к системным сервисам, к отладке. Они не запрашиваются в рантайме
и не подделываются — только переподписываются своим профилем, а приватные права и вовсе
недоступны сторонним разработчикам. Поэтому аудит entitlements — быстрый и информативный шаг:
он показывает, что приложение **может** делать, ещё до анализа кода. А серверная сторона должна
помнить: entitlement подтверждает возможность, но не личность, и всё, что можно переподписать,
нельзя считать доказательством.

## Шаг 14: entitlements и приватные API

Отдельная тема — использование приватных API. Некоторые возможности iOS доступны только через
непубличные методы, а часть из них дополнительно защищена entitlement вида
`com.apple.private.*`. Стороннее приложение не может заявить такое право, поэтому попытка
использовать приватный API без него обычно заканчивается отказом или крашем.

Однако в анализе это важно по двум причинам. Во-первых, если в стороннем приложении всё же
встречается приватный API, это признак либо переподписи с системным профилем (что подозрительно
само по себе), либо уязвимости, позволяющей обойти проверку. Во-вторых, понимание того, какие
возможности защищены entitlement, помогает оценить поверхность атаки: всё, что защищено
подписью, нельзя просто «включить» в рантайме.

```bash
$ codesign -d --entitlements :- example.app | grep -c 'com.apple.private'
0
$ strings example_binary | grep -i 'private_framework' | head
```

Если строки приватного фреймворка есть, а соответствующего entitlement нет — стоит разобраться,
как приложение рассчитывает его использовать. Часто это остатки отладочного кода, но иногда —
признак более глубокой проблемы. Такой сигнал полезно фиксировать в отчёте: он направляет
дальнейший анализ туда, где защита может не сработать.
