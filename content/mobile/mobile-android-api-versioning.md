## Вопрос, с которого всё начинается

Приложение обновилось до `/v3/`, добавило проверки, закрыло дыры. Но старые клиенты ещё в
магазине, и сервер обязан их поддерживать. Значит, `/v1/` и `/v2/` живы — и живут со старыми
правилами. Как этим воспользоваться?

## Наш пример: три версии

Собираем из трафика и документации карту версий:

```bash
$ cat api_versions.txt
v1: /v1/user/{id}     — auth: none
v2: /v2/user/{id}     — auth: session
v3: /v3/user/{id}     — auth: token + scope
```

Текущая — `v3`. Но `v1` не требует аутентификации. Весь урок ведём эту карту.

## Шаг 1: зачем вообще версии

API меняется, а старые приложения уже установлены на телефонах. Сломать их нельзя — поэтому
эндпоинты версионируют: `/v1/`, `/v2/`, `/v3/`. Версия — это «контракт» между клиентом и
сервером. Проблема в том, что контракт у каждой версии свой, и проверки, добавленные в новую,
часто не переносят в старую.

## Шаг 2: почему старая версия остаётся

Причины: старые клиенты в проде, лень, «внутренние» потребители, микросервисы, которые ещё
зовут `v1`. Через год про `v1` забывают, но она работает. Для пентестера это подарок: логика
та же, а защит нет.

## Шаг 3: находим версии

Способы:
- Разбор трафика: какой путь зовёт приложение.
- Перебор: `/v1/`, `/v2/`, `/v3/`, `/api/v1/`, `/v1.0/`.
- Документация, Swagger, GraphQL-схема.
- Ответы сервера: заголовки, тексты ошибок.

```bash
$ curl -s -o /dev/null -w '%{http_code}\n' https://api.example.com/v1/user/1
200
```

`200` без токена — тревожный знак.

## Шаг 4: сравниваем защиты

Ключевой приём — **дифференциальный тест**: один и тот же запрос к разным версиям.

```bash
$ curl -s https://api.example.com/v3/user/1      # 401 Unauthorized
$ curl -s https://api.example.com/v1/user/1      # 200 {"id":1,"email":"..."}
```

Если `v1` отдаёт данные без токена — находка. Если `v1` принимает старый формат токена без
проверки scope — тоже находка.

## Шаг 5: версия в других местах

Версия может быть не только в пути: в заголовке `Accept: application/vnd.api+json;version=1`,
в query `?version=1`, в поддомене `v1.api.example.com`, в поле тела. Проверяют все варианты —
часто защита стоит на пути, а «старую» версию достают через заголовок.

## Шаг 6: старый формат аутентификации

Иногда старая версия принимает другой токен: JWT без подписи, сессионную cookie, API-ключ из
приложения. Это обход новой схемы аутентификации через «совместимость». Проверяют: какой
токен принимает каждая версия и что она с ним делает.

## Шаг 7: что искать в старой версии

- Отсутствие аутентификации.
- Отсутствие авторизации (доступ к чужому объекту).
- Устаревшие форматы (XML вместо JSON — XXE).
- Отладочные параметры (`?debug=1`).
- Более широкие поля в ответе (лишние данные).

## Шаг 8: как защищают правильно

Держать только нужные версии, явно выводить из эксплуатации старые, переносить проверки во
все поддерживаемые версии, использовать единый слой авторизации перед версиями, а не дублировать
проверки в каждой. Версия — про формат, а не про безопасность.

## Шаг 9: как это оформить в отчёте

Находка формулируется точно: «Эндпоинт `/v1/user/{id}` версии 1 доступен без аутентификации и
возвращает персональные данные; текущая версия `/v3` требует токен». Сравнение версий — сильное
доказательство: видно, что защита есть, но не применена.

## Шаг 10: порядок проверки

1. Собрать список версий из трафика и перебора.
2. Сравнить один запрос по всем версиям.
3. Проверить аутентификацию и авторизацию каждой.
4. Проверить альтернативные способы указать версию.
5. Зафиксировать разницу как находку.

## Шаг 11: версия в заголовке и query

Версия не обязана быть в пути. Частые варианты:
- заголовок `Accept: application/vnd.example.v2+json`;
- заголовок `X-API-Version: 2`;
- query `?api-version=2.0`;
- поддомен `v2.api.example.com`.

Проверяй все: защиту часто ставят на путь (`/v3/`), а «старую» версию достают заголовком,
который сервер обрабатывает отдельной веткой кода. Один и тот же эндпоинт может вести себя
по-разному в зависимости от заголовка.

## Шаг 12: жизненный цикл API

У API есть жизненный цикл: разработка → стабильная → устаревшая (deprecated) → вывод. Проблемы
живут на этапе «устаревшая»: формально ещё поддерживается, фактически никто не смотрит. При
аудите полезно составить карту: какие версии объявлены устаревшими, есть ли дата отключения,
перенесены ли в них проверки. «Deprecated, но работает» — типичная находка.

## Шаг 13: как находить версии системно

1. Разбери трафик приложения: какие пути и заголовки оно использует.
2. Перебери соседние версии: `/v1/`, `/v2/`, `/v0/`, `/v1.0/`, `/api/v1/`.
3. Проверь поддомены: `v1.`, `api-v1.`, `legacy.`.
4. Посмотри документацию и ошибки сервера.
5. Сравни ответы одинаковым запросом.

## Шаг 14: что писать в отчёте

Формулировка должна показывать разницу: «Запрос к `/v3/user/1` без токена возвращает `401`, а к
`/v1/user/1` — `200` с персональными данными. Старая версия не переняла проверку
аутентификации из `v3`». Конкретное сравнение двух версий — самое убедительное доказательство.

## Если не сработало

Если старые версии недоступны, возможно, их действительно вывели из эксплуатации — это
правильная конфигурация. Тогда проверь альтернативные способы указать версию (заголовки,
query). Если и там всё закрыто, зафиксируй это как положительный результат и переходи к другим
эндпоинтам.
## Полный прогон: поиск забытой версии

**Шаг A.** Из трафика узнаём текущий путь: `/v3/user/1`.

**Шаг B.** Пробуем соседние версии:

```bash
$ for v in v1 v2 v3; do
    printf '%s -> ' "$v"; curl -s -o /dev/null -w '%{http_code}\n' https://api.example.com/$v/user/1;
  done
v1 -> 200
v2 -> 401
v3 -> 401
```

**Шаг C.** `v1` отдаёт данные без токена — проверяем тело:

```bash
$ curl -s https://api.example.com/v1/user/1
{"id":1,"email":"a@example.com"}
```

**Шаг D.** Проверяем, работает ли это для других ID (авторизация отсутствует вовсе).

**Шаг E.** Фиксируем разницу: `v3` требует токен, `v1` — нет. Находка готова.

## Частые ошибки

- Проверять только текущую версию API.
- Не сравнивать ответы одинаковым запросом.
- Забыть про версию в заголовке или поддомене.
- Считать `200` без данных «не находкой» — проверяй тело ответа.
## Как это устроено внутри

Версионирование — это про контракт и время. Когда API меняется несовместимо, добавляют новую
версию, а старую оставляют работать, пока её используют клиенты. Так возникает разрыв: старая
версия заморожена в том состоянии, в котором её выпустили, а проверки безопасности продолжают
развиваться в новой. Через год `/v1/` работает по правилам позапрошлого года.

Проблема усиливается тем, что версия — это **маршрут**, а не отдельный сервис. Часто это одна
и та же логика с флагом версии, но иногда — отдельный старый код, до которого не дошли руки.
Поэтому дифференциальный тест так эффективен: он сравнивает не «есть ли защита», а «одинакова
ли защита в двух версиях», и разница видна сразу.

Правильный подход — не дублировать проверки в каждой версии, а вынести авторизацию в общий
слой перед маршрутизацией и явно выводить старые версии из эксплуатации по расписанию. Тогда
версия определяет только формат ответа, а не уровень доступа. Пока этого нет, старые версии
остаются самым предсказуемым местом для находок.
## Типичный сценарий на реальном устройстве

Ты тестируешь мобильный API банка. Из трафика знаешь, что приложение ходит на `/v3/`. Перебирая
соседние версии, обнаруживаешь, что `/v1/` отвечает на запрос без токена. Ты сравниваешь тела
ответов: `v3` требует аутентификацию, `v1` отдаёт профиль. Дальше проверяешь, что это не
разовая аномалия: меняешь ID и получаешь профили других пользователей — то есть в старой
версии нет ни аутентификации, ни авторизации.

Такой сценарий особенно убедителен в отчёте, потому что показывает не «эндпоинт доступен», а
«защита есть в новой версии и отсутствует в старой». Разработчику это даёт точную задачу:
перенести проверку или вывести версию из эксплуатации. И, что важно, сценарий не требует
экзотических инструментов — достаточно цикла по нескольким путям. Поэтому проверку версий
стоит делать в начале тестирования API: она быстро даёт находки и карту поверхности.
## Что важно не перепутать

Не путай **версию API** и **версию приложения**: первая определяет контракт сервера, вторая —
сборку клиента; старый клиент ходит в старую версию API, но не наоборот. Не путай **устаревшую**
(deprecated) и **отключённую** версию: первая ещё работает, вторая возвращает ошибку — и вся
проблема именно в первой. И не путай **формат ответа** и **уровень доступа**: версия должна
менять форму данных, а не правила авторизации. В отчёте показывай разницу одинаковым запросом:
это снимает любые сомнения и делает находку объективной. «Старая версия без проверок» — это
факт, подтверждённый сравнением, а не мнение.
## Итоговая мысль

Версии API — это про время и совместимость, и именно поэтому старые версии так часто
оказываются слабым звеном: их заморозили, а проверки продолжали развивать только в новых.
Дифференциальный тест «одна версия против другой» вскрывает это быстрее всего. И вывод простой:
авторизация должна быть общей и не зависеть от версии, а старые версии — выводиться из
эксплуатации по расписанию, а не жить годами.
## Что мы теперь знаем

- Версии API нужны для совместимости со старыми клиентами.
- Старые версии часто не получают новые проверки.
- Дифференциальный тест «v3 vs v1» быстро вскрывает разницу.
- Версия может быть в заголовке, query, поддомене.
- Защита — единый слой авторизации и вывод старых версий.
