## Вопрос, с которого всё начинается

Ты нашёл эндпоинт с 4-значным кодом подтверждения. Перебираешь — а сервер через несколько
попыток отвечает `429 Too Many Requests`. Защита от перебора — это хорошо, но её часто считают
по ключу, который атакующий контролирует. Проверим, по чему считает лимит наш API.

## Наш пример: ответы с заголовками

Смотрим ответы сервера на серию запросов:

```bash
$ curl -si -X POST https://api.example.com/verify -d 'code=1234' | grep -i 'HTTP\|ratelimit\|x-'
HTTP/2 200
X-RateLimit-Limit: 10
X-RateLimit-Remaining: 3
```

Заголовки `X-RateLimit-*` показывают, что лимит есть. Весь урок ведём этот ответ.

## Шаг 1: что такое rate-limit и зачем

**Rate-limit** — ограничение числа запросов за промежуток времени. Защищает от перебора паролей,
кодов, токенов, от DoS. Считается по **ключу**: чаще всего по IP-адресу, по аккаунту/токену, по
устройству. Проблема в том, что не все ключи уникальны и не все атакующий не может подделать.

## Шаг 2: определяем ключ

Меняем параметры и смотрим, когда счётчик сбрасывается:
- Меняем пароль, но не IP → счётчик растёт (ключ — IP).
- Меняем IP (через прокси) → счётчик сбрасывается (ключ — IP).
- Меняем `X-Forwarded-For` → счётчик сбрасывается (ключ — доверенный заголовок).

```bash
$ curl -si -H 'X-Forwarded-For: 1.2.3.4' -X POST https://api.example.com/verify -d 'code=1' \
  | grep -i 'x-ratelimit-remaining'
X-RateLimit-Remaining: 10
```

Счётчик вернулся к 10 — значит, лимит привязан к IP, а IP сервер берёт из заголовка, который
мы контролируем. Это и есть обход.

## Шаг 3: подделка заголовков

Самая частая причина обхода — сервер за обратным прокси берёт клиентский IP из
`X-Forwarded-For`, `X-Real-IP`, `X-Client-IP`, `Forwarded`. Если прокси не вычищает эти
заголовки, каждый запрос с новым значением — «новый клиент».

```bash
$ for i in $(seq 1 50); do curl -s -H "X-Forwarded-For: 10.0.0.$i" ... ; done
```

## Шаг 4: смена «устройства»

Если лимит привязан к устройству (device ID, установочный ID), помогает сброс идентификатора:
переустановка, очистка данных, подмена заголовка с device ID. В мобильном API это часто
контролируемый клиентом параметр.

## Шаг 5: другие ключи

- По аккаунту: если перебор идёт по многим аккаунтам, лимит на один аккаунт не мешает
  (**password spraying**).
- По эндпоинту: обход через старую версию API или альтернативный путь.
- По токену: если токен можно создать много, лимит не работает.

## Шаг 6: логика вместо ключа

Иногда лимит есть, но сбрасывается при успешной операции, при смене тела, при добавлении
пробела/регистра. Тогда его обходят вариациями запроса. Важно: это не «взлом шифра», а
недоработка счётчика.

## Шаг 7: как понять, что обход сработал

Признак — сервер перестал отвечать `429` и продолжает обрабатывать запросы. Правильный тест:
серия из N запросов, где N заведомо больше лимита. Если все прошли — лимит обойдён.

```bash
$ for i in $(seq 1 30); do
    code=$(curl -s -o /dev/null -w '%{http_code}' -H "X-Forwarded-For: 10.0.0.$i" ...);
    echo "$i:$code";
  done | grep -c 429
0
```

Ноль ответов `429` при 30 запросах — обход подтверждён.

## Шаг 8: почему это критично

Обход rate-limit сам по себе не даёт доступ, но **снимает защиту от перебора**. Вместе с
коротким кодом или слабым паролем он превращается в захват аккаунта. Поэтому это находка
высокой важности, даже если «просто» лимит.

## Шаг 9: как защищают правильно

Считать лимит по нескольким ключам (IP + аккаунт + устройство), брать IP из доверенного
источника (реальный peer, а не заголовок от клиента), чистить `X-Forwarded-For` на прокси,
использовать экспоненциальную задержку, капчу, блокировку после N неудач. И не полагаться
только на IP — за NAT он общий.

## Шаг 10: порядок проверки

1. Найти эндпоинт с ограничением (логин, verify, reset).
2. Определить ключ лимита (менять IP/заголовок/аккаунт).
3. Проверить подделку заголовков.
4. Проверить альтернативные ключи и версии.
5. Оформить: сколько запросов прошло сверх лимита.

## Шаг 11: спрей против брутфорса

Два разных сценария. **Брутфорс** — много попыток по одному аккаунту: ломается лимитом на
аккаунт. **Password spraying** — по одному популярному паролю на множество аккаунтов: лимит на
аккаунт не мешает, а общий лимит по IP обходится сменой IP. При аудите смотри, какой лимит
стоит и от чего он защищает. Часто защита от брутфорса есть, а от спрея — нет.

## Шаг 12: лимиты на OTP

Одноразовые коды — самое опасное место: код короткий (4–6 цифр), и без лимита он перебирается
за минуты. Проверяют: ограничено ли число попыток ввода кода, привязан ли лимит к сессии/коду,
инвалидируется ли код после N ошибок, есть ли блокировка. Если лимита нет или он обходится —
это критическая находка.

## Шаг 13: прокси и распределённый перебор

Если лимит честно привязан к реальному IP, обходят пулом прокси или мобильных IP: каждый
запрос — с нового адреса. Это дороже и заметнее (аномальный трафик), но работает. При аудите
это уже не «обход одной команды», а полноценная атака; её упоминают как риск, а не
демонстрируют массово.

## Шаг 14: что писать в отчёте

«Эндпоинт `/verify` ограничивает 10 запросов на IP, но IP берётся из заголовка
`X-Forwarded-For`, который клиент контролирует. 30 запросов с разными значениями заголовка
прошли без единого `429`». Указывают ключ лимита, способ обхода и число прошедших запросов.

## Если не сработало

Если `429` приходит стабильно и заголовки не помогают — лимит, скорее всего, считается по
неподделываемому ключу (сессия, устройство). Тогда проверь другие ключи: аккаунт, токен,
эндпоинт. Если и они защищены — это хороший результат; зафиксируй, что защита работает, и не
трать бюджет на прокси-пулы.
## Полный прогон: снимаем защиту от перебора

**Шаг A.** Определяем, что лимит есть:

```bash
$ curl -si -X POST https://api.example.com/verify -d 'code=1' | grep -i ratelimit
X-RateLimit-Limit: 10
X-RateLimit-Remaining: 9
```

**Шаг B.** Ищем ключ лимита. Меняем только заголовок `X-Forwarded-For`:

```bash
$ curl -si -H 'X-Forwarded-For: 1.2.3.4' -X POST https://api.example.com/verify -d 'code=2' \
  | grep -i ratelimit-remaining
X-RateLimit-Remaining: 10
```

Счётчик вернулся к 10 — лимит привязан к контролируемому заголовку.

**Шаг C.** Подтверждаем обход серией запросов:

```bash
$ for i in $(seq 1 30); do
    curl -s -o /dev/null -w '%{http_code}\n' -H "X-Forwarded-For: 10.0.0.$i" \
      -X POST https://api.example.com/verify -d 'code=3';
  done | grep -c 429
0
```

**Шаг D.** Ноль ответов `429` при 30 запросах — обход подтверждён.

**Шаг E.** Формулируем находку: ключ лимита подделывается, защита от перебора снята.

## Частые ошибки

- Проверять лимит одним-двумя запросами — нужна серия больше лимита.
- Считать, что лимит по IP защищает от спрея.
- Не проверять альтернативные заголовки (`X-Real-IP`, `Forwarded`).
- Забывать, что обход лимита — это про перебор, а не про доступ.
## Как это устроено внутри

Rate-limit — это счётчик. У счётчика есть **ключ** (к чему привязан) и **окно** (за какой
промежуток). Защита ровно настолько хороша, насколько хорош ключ: если ключ подделывается или
не уникален, счётчик бесполезен. Отсюда вся тактика обхода — найти ключ и посмотреть, кто им
управляет.

Типичная ошибка возникает на стыке «приложение за прокси». Прокси видит реальный адрес
клиента, а приложение — адрес прокси. Чтобы приложение знало настоящий IP, прокси добавляет
заголовок `X-Forwarded-For`. Если приложение берёт IP из этого заголовка, но прокси его не
вычищает, клиент может подставить любой адрес — и счётчик обнуляется на каждом запросе. Это не
«взлом», а ошибка конфигурации доверия.

Поэтому правильная защита считает лимит по нескольким ключам сразу (IP + аккаунт + устройство),
берёт IP из доверенного источника, а не из заголовка, который пришёл от клиента, и добавляет
задержку или капчу после серии неудач. Ни один ключ не идеален: IP общий за NAT, аккаунт можно
создать, устройство подделать. Но несколько ключей вместе делают перебор экономически
бессмысленным — а именно этого и добивается защита.
## Типичный сценарий на реальном устройстве

Ты находишь эндпоинт подтверждения номера с четырёхзначным кодом. Делаешь десять попыток —
сервер отвечает `429`. Смотришь заголовки ответа: лимит десять. Меняешь `X-Forwarded-For` —
счётчик сбрасывается. Подтверждаешь серией из тридцати запросов с разными значениями
заголовка: ни одного `429`. Лимит обойдён, а значит, четырёхзначный код перебирается за минуты.

Дальше ты проверяешь, нет ли других ключей: привязки к сессии, к самому коду, к устройству. В
отчёт идёт находка с точным ключом (заголовок) и числом прошедших запросов. Это сильное
доказательство, потому что оно воспроизводимо и не требует массового перебора — достаточно
показать, что защита не держит. И, что важно, ты не доводишь до захвата аккаунта: доказательства
обхода лимита достаточно, чтобы описать риск.
## Что мы теперь знаем

- Rate-limit считается по ключу: IP, аккаунт, устройство, токен.
- Если IP берётся из `X-Forwarded-For`, лимит обходится заголовком.
- Смена «устройства» и старые версии API — тоже обходы.
- Обход лимита снимает защиту от перебора.
- Правильная защита — несколько ключей и доверенный источник IP.
