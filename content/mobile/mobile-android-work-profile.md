## Вопрос, с которого всё начинается

Сотрудник установил корпоративный почтовик — и на телефоне появился «рабочий» набор
приложений с отдельным значком. Рабочие данные должны быть изолированы от личных. Но так ли
это? И что мешает приложению из одного профиля прочитать данные другого?

## Наш пример: два профиля — два пользователя

```bash
$ adb shell pm list users
Users:
    UserInfo{0:Owner:13} running
    UserInfo{10:Work profile:30} running
```

Android реализует work profile как **отдельного пользователя** (здесь id 10). Значит, у
рабочих приложений своя песочница `/data/user/10/`. Весь урок ведём эти два «пользователя».

## Шаг 1: как устроен work profile

Android Enterprise создаёт управляемый профиль как отдельного пользователя с отдельным
набором данных. Рабочие приложения живут в `/data/user/10/`, личные — в `/data/user/0/`.
Разделение на уровне UID и файловой системы — это и есть изоляция. Profile Owner управляет
именно профилем 10.

## Шаг 2: как выглядит изоляция

```bash
$ adb shell ls /data/user/10/
com.acme.mail  com.acme.portal
$ adb shell ls /data/user/0/ | head
com.android.chrome  com.whatsapp  ...
```

Личные приложения не видят `/data/user/10` без root, и наоборот. Это базовая гарантия BYOD:
личные данные не смешиваются с рабочими.

## Шаг 3: где граница «протекает»

Изоляция не абсолютна — есть легальные каналы между профилями:

| Канал | Что переносится |
|---|---|
| Share intent | файлы/текст по выбору пользователя |
| Cross-profile intents | явные вызовы между профилями |
| Уведомления | тексты рабочих уведомлений на личном экране |
| Буфер обмена | при разрешении политикой |
| `crossProfileApps` | запуск приложения другого профиля |

Если приложение обрабатывает share-intent небрежно, оно может принять файл из другого
профиля и записать его в общий кэш — утечка. Проверяем, какие каналы включены:

```bash
$ adb shell dumpsys device_policy | grep -i 'CrossProfile\|clipboard'
  mCrossProfileCopyPasteEnabled: true
```

## Шаг 4: интенты через границу

Ключевой вектор — **cross-profile intent**. Приложение может запустить активность в другом
профиле или отправить туда данные, если система разрешит. Опасность: приложение из личного
профиля получает рабочий файл и сохраняет его туда, откуда он потом утечёт. Смотрим
`android:crossProfile` в манифесте и фильтры:

```bash
$ aapt dump xmltree app.apk AndroidManifest.xml | grep -i 'crossProfile\|permission'
```

## Шаг 5: буфер обмена и уведомления

Политика может разрешать копирование между профилями (`CROSS_PROFILE_COPY_PASTE`). Если
разрешено — текст из рабочего почтовика можно вставить в личное приложение. Аналогично
уведомления рабочего профиля показываются на личном экране и могут содержать чувствительные
данные. Это не баг, а осознанный компромисс, но пентестер обязан его отметить.

## Шаг 6: как проверять

Практический чек: (1) какие приложения в профиле 10; (2) какие каналы между профилями
включены; (3) есть ли приложения с `crossProfile`-фильтрами; (4) пробрасываются ли секреты
через share/clipboard. Всё это доступно через `pm list users`, `dumpsys device_policy` и
разбор манифестов — без root.

## Шаг 7: как создаётся профиль

Work profile создаётся DPC при настройке: система заводит нового пользователя (обычно id 10),
устанавливает туда управляемые приложения и связывает профиль с аккаунтом организации.
Пользователь видит рабочие приложения с «портфельным» значком. Технически это отдельный
пользователь, поэтому у него свои `pm list packages --user 10`, свои разрешения и своя
песочница. Проверить содержимое можно так:

```bash
$ adb shell pm list packages --user 10
package:com.acme.mail
package:com.acme.portal
```

## Шаг 8: work challenge

Отдельная защита — **work challenge**: на рабочий профиль можно поставить отдельный пароль,
отличный от пароля разблокировки устройства. Это уменьшает риск, что, разблокировав телефон,
злоумышленник сразу получит рабочие данные. При аудите проверяют, включён ли work challenge и
насколько строги его требования, — отсутствие отдельного пароля часто является находкой.

## Шаг 9: crossProfileApps и запуск

API `crossProfileApps` позволяет приложению из одного профиля запустить активность в другом
(с разрешения пользователя или политики). Это легальный механизм, но и вектор: если
приложение рабочего профиля можно запустить из личного контекста, а оно обрабатывает данные
небрежно, возможна утечка. Смотрят, какие приложения объявили поддержку cross-profile и какие
активности доступны для запуска.

## Шаг 10: app cloning и дубликаты

На одном устройстве могут сосуществовать «одно и то же» приложение в личном и рабочем
профилях — это разные пакеты в разных пользователях. Это усложняет анализ: одинаковое имя
пакета встречается дважды. При сборе артефактов всегда указывайте `--user`, иначе получите
данные не того профиля.

## Шаг 11: как тестировать

Для легального тестирования используют официальные инструменты: **Test DPC** (демонстрационный
DPC от Google) и режим рабочего профиля на тестовом устройстве. Это позволяет воспроизвести
политики, каналы между профилями и ограничения, не трогая продакшн. В отчёте фиксируют: какие
каналы между профилями включены, есть ли work challenge, какие приложения cross-profile, и
какие данные реально пересекают границу.

## Шаг 12: политики профиля

Profile Owner управляет профилем через набор политик: обязательный пароль, запрет
скриншотов, запрет установки приложений, ограничения на камеру и буфер обмена. Часть из них
видна в `dumpsys device_policy` как `UserRestrictions`. При аудите важно понять, какие
политики реально включены в профиле, а какие только заявлены: неактивное ограничение — это
потенциальная находка.

## Шаг 13: данные в уведомлениях

Уведомления рабочего профиля показываются на личном экране, и их текст может содержать
чувствительные данные (коды, суммы, имена). Это ещё один канал утечки, который легко
недооценить: пользователь видит рабочие уведомления, а значит, их видит и любой, кто смотрит
на экран. Политика может скрывать содержимое уведомлений — проверяют, включено ли это.

## Шаг 14: тестирование и Test DPC

Для воспроизведения сценариев используют **Test DPC** — официальный демонстрационный
контроллер политик. Он позволяет создать рабочий профиль на тестовом устройстве, включить
ограничения и проверить, как ведёт себя приложение. Это законный способ аудита: вы видите
поведение в реальной конфигурации, а не предполагаете его.

## Шаг 15: чек-лист аудита work profile

(1) Найден id рабочего профиля; (2) перечислены приложения профиля (`pm list packages
--user`); (3) собраны активные политики; (4) проверены каналы между профилями (share,
clipboard, cross-profile); (5) проверен work challenge; (6) проверены уведомления на предмет
утечки; (7) в отчёте — какие данные пересекают границу.

## Шаг 16: пример перехвата через share

Разберём сценарий. Приложение рабочего профиля принимает файлы через share-intent и
сохраняет их в свой кэш. Если фильтр интента слишком широкий, личное приложение может
отправить туда произвольный файл, а рабочее — записать его в доступное место. Проверка:
смотрим `intent-filter` и обработчик, пробуем отправить файл из личного профиля, проверяем,
куда он попал. Находка — утечка данных через границу профилей.

## Шаг 17: managed apps на iOS

На iOS аналог рабочего профиля — управляемые приложения (**managed apps**) и **managed open
in**. Политика решает, какие приложения могут обмениваться документами. Логика та же:
граница есть, но каналы (open-in, share, pasteboard) её пересекают. Сравнение полезно в
отчёте: часть находок платформенно-специфична, часть — общая для обеих ОС.

## Шаг 18: как оформить вывод

Для work profile вывод строят вокруг одного вопроса: «какие данные пересекают границу
рабочее/личное и под чьим контролем». Перечисляют каналы (share, clipboard, cross-profile
intents, уведомления), для каждого — включён ли он и что через него проходит. Так заказчик
видит не список технических деталей, а понятную модель риска BYOD.

## Если не сработало

Если профиль 10 не виден или кажется пустым, проверьте: во-первых, есть ли вообще рабочий
профиль (`pm list users`); во-вторых, тот ли это id (он может быть 11 или другим); в-третьих,
не смотрите ли вы данные владельца вместо профиля — команды без `--user` показывают только
user 0. Если профиль существует, но приложения не видны, возможно, у вас нет прав на чтение
его данных, и это ожидаемо без root. Тогда работайте через официальные интерфейсы (dumpsys,
`pm`) и фиксируйте, что доступно без привилегий.

## Практический итог по work profile

Порядок аудита: найти id рабочего профиля; перечислить приложения профиля; собрать активные
политики; проверить каналы между профилями (share, clipboard, cross-profile intents,
уведомления); проверить work challenge; проверить уведомления на утечку. Вывод строится вокруг
одного вопроса: какие данные пересекают границу рабочее/личное и под чьим контролем. Это и
есть суть BYOD-риска: изоляция есть, но каналы её пересекают, и задача аудита — показать, какие
именно и что через них проходит.

## Итоговая мысль

Work profile — хороший пример того, как платформенная изоляция работает «в целом», но не
абсолютно. Данные разделены на уровне пользователей и UID, однако между профилями есть
легальные каналы, и именно они становятся предметом аудита. Пентестер не ломает изоляцию, а
проверяет, что через каналы не утекает лишнее. Такой подход даёт заказчику реалистичную
картину: BYOD безопасен ровно настолько, насколько настроены каналы и закрыт work challenge.

## Что мы теперь знаем

- Work profile — отдельный пользователь Android (обычно id 10).
- Данные изолированы на уровне UID и файловой системы.
- Между профилями есть легальные каналы (share, intents, clipboard, уведомления).
- Небрежная обработка share-intent ведёт к утечке.
- Каналы проверяются через dumpsys и разбор манифестов.
