## Вопрос, с которого всё начинается

JADX открыл APK — а внутри почти нет классов: только маленький загрузчик. Настоящий код где-то
прячется и появляется только во время работы. Это упаковщик (shielding). Как достать настоящий
код?

## Наш пример: app.apk с упаковщиком

```bash
$ unzip -l app.apk | grep -E 'classes.*dex'
  64   classes.dex
$ jadx -d out app.apk
$ find out/sources -name '*.java' | wc -l
7
```

Всего 7 классов и крошечный `classes.dex` — явный признак упаковщика. Настоящий код загружается
из зашифрованного блоба.

## Шаг 1: что такое шилдинг

Упаковщик (protector) шифрует оригинальный DEX и прячет его внутри APK (в assets или нативной
библиотеке). При запуске загрузчик расшифровывает DEX и подгружает его в память, после чего
работает обычный код. Статически виден только загрузчик.

## Шаг 2: жизненный цикл упаковщика

1. Приложение стартует с классом-загрузчиком.
2. Загрузчик читает зашифрованный DEX.
3. Расшифровывает его в память.
4. Создаёт `DexClassLoader` и загружает настоящие классы.
5. Передаёт управление реальному коду.

Ключевой момент — шаг 3–4: расшифрованный DEX существует в памяти, и его можно выгрузить.

## Шаг 3: поиск загрузчика

В манифесте `application android:name` указывает на класс-загрузчик. В JADX он выглядит как
`attachBaseContext`/`onCreate`, который читает ассеты и что-то расшифровывает. Это наша точка
входа.

## Шаг 4: дамп из памяти

Самый надёжный путь — дамп уже расшифрованного DEX:

```bash
$ frida-dexdump -U -f com.example
[+] Searching dex in memory
[+] Dumped 3 dex files
```

Инструмент сканирует память процесса в поисках сигнатуры DEX (`dex\n035`) и сохраняет найденные
файлы. Это обходит шифрование: мы берём код уже после расшифровки.

## Шаг 5: пересборка

Полученные DEX можно прочитать JADX напрямую. Если классы разбросаны по нескольким DEX —
объединяют или анализируют по отдельности. Иногда требуется починить заголовки — для этого есть
скрипты.

## Шаг 6: anti-dump

Продвинутые упаковщики противодействуют дампу: стирают заголовки DEX в памяти, запускают
проверки, искажают память. Тогда дамп делают «на лету» — перехватывают момент сразу после
расшифровки, до искажения. Для этого хукают нативный дешифратор.

## Шаг 7: практика

Типовой пайплайн: определить упаковщик по структуре APK → найти загрузчик → запустить приложение
под Frida → дампнуть DEX → проанализировать в JADX. Это стандартный способ вскрытия защищённых
приложений.

## Что мы теперь знаем

- Шилдинг шифрует DEX и грузит его в рантайме.
- Статически виден только загрузчик.
- Расшифрованный DEX можно дампнуть из памяти.
- frida-dexdump находит DEX по сигнатуре.
- Продвинутые упаковщики мешают дампу.

## Признаки упаковщика: как отличить от обфускации

Упаковщик и обфускатор решают разные задачи, и признаки у них разные. Обфускатор переименовывает
и запутывает код, но код остаётся в DEX. Упаковщик прячет весь DEX целиком — статически кода
почти нет.

Первый признак — аномально маленький `classes.dex`. Второй — имя класса приложения в манифесте
(`android:name`) указывает на неизвестный класс-загрузчик. Третий — в `assets/` или в
`lib/<abi>/` лежит подозрительный файл: зашифрованный блоб или нативная библиотека с именем
упаковщика.

```bash
$ unzip -l app.apk | grep -E 'assets/|lib/'
  assets/classes.jar.bin
  lib/arm64-v8a/libjiagu.so
```

Файл `libjiagu.so` — характерный признак упаковщика Qihoo 360 Jiagu. Другие распространённые
имена: `libprotectClass.so` (Bangcle), `libDexHelper.so` (Baidu), `libshella.so`,
`libexec.so`, `libmobisec.so`.

## Где прячется зашифрованный DEX

Зашифрованный DEX может лежать в нескольких местах, и от этого зависит способ извлечения.

- В `assets/` под произвольным именем (`.bin`, `.jar`, `.dat`). Расшифровывается в рантайме.
- В нативной библиотеке как массив байт внутри `.rodata`. Тогда дешифратор — нативный.
- В ресурсах (`res/raw/`) или в `classes.dex` как добавочные данные после конца валидного DEX.
- Загружается из сети при первом запуске.

```bash
$ binwalk assets/classes.jar.bin
DECIMAL       HEXADECIMAL     DESCRIPTION
0             0x0             AES encrypted data, ...
```

Энтропия близка к максимуму (AES-блоб выглядит как случайные данные) — верный признак
шифрования. Если бы это был обычный DEX, `binwalk` нашёл бы сигнатуру `dex\n` в начале.

## Продвинутый дамп: перехват до anti-dump

Продвинутые упаковщики затирают заголовок DEX в памяти сразу после загрузки, чтобы дамп по
сигнатуре не сработал. Тогда дампить нужно «на лету»: перехватить момент, когда расшифрованный
буфер ещё целый.

Технически это делают хуком на функции, через которые проходит расшифрованный код. Например,
хукают `open`/`read` (если DEX сначала пишется в файл) или нативный дешифратор. Frida позволяет
сохранить буфер прямо в момент вызова:

```javascript
var openPtr = Module.findExportByName(null, 'open');
Interceptor.attach(openPtr, {
  onEnter: function (args) {
    var path = args[0].readUtf8String();
    if (path && path.indexOf('.dex') >= 0) { send('open ' + path); }
  }
});
```

Если приложение пишет расшифрованный DEX во временный файл, дамп сводится к чтению этого файла.
Если грузит из памяти — сохраняем буфер на входе в `DexClassLoader`/`InMemoryDexClassLoader`.

## Автоматизация: Frida + dexdump + починка заголовков

Рабочий пайплайн состоит из трёх шагов. Первый — снять RASP-проверки (иначе приложение закроется
под Frida). Второй — дампнуть DEX из памяти. Третий — починить заголовки, если упаковщик их
испортил.

```bash
$ frida -U -f com.example -l bypass.js
$ frida-dexdump -U -f com.example
$ jadx -d out classes.dex
```

Если JADX ругается на повреждённый заголовок, часть инструментов умеет восстанавливать поля
(размер файла, таблицы) по остаточным данным. Иногда помогает дампить несколько раз в разные
моменты: в один из них заголовок ещё целый.

## Таблица упаковщиков и признаков

| Признак | Упаковщик (пример) | Что делать |
|---|---|---|
| libjiagu.so | Qihoo 360 Jiagu | дамп памяти |
| libDexHelper.so | Baidu | дамп памяти |
| libprotectClass.so | Bangcle | дамп + починка |
| assets/*.bin (высокая энтропия) | разный | найти дешифратор |
| крошечный classes.dex | любой | не доверять статике |

## Если не сработало

Если приложение закрывается сразу под Frida, — активна RASP-проверка. Сначала нейтрализуйте
проверку, потом дампите; порядок важен, иначе дамп не успеет сработать.

Если дампенный DEX не содержит нужных классов, — возможно, код грузится лениво, и в момент дампа
ещё не загружен. Поживите в приложении подольше, пройдите по экранам, которые инициируют загрузку,
и повторите дамп.

Если дамп ловит только маленький загрузочный DEX, а «настоящий» не появляется, — упаковщик может
держать код зашифрованным до конкретного действия. Ищите триггер загрузки (открытие экрана,
авторизация) и дампите после него.

## Ограничения

Распаковка — это гонка вооружений. Каждое усложнение упаковщика (затирание заголовков, искажение
памяти, проверка целостности Frida) увеличивает стоимость обхода, но не делает его невозможным:
расшифрованный код в какой-то момент всё равно существует в памяти, и его можно перехватить.

Стоит помнить и о юридической стороне: обход защиты допустим в рамках авторизованного теста или
анализа собственного/свободно распространяемого приложения, но не для обхода лицензий или
распространения взломанных сборок.

## Мини-практика: определить упаковщик по следам в APK

Определить конкретный упаковщик полезно: под каждый есть свой набор приёмов распаковки. Разбор
начинается с содержимого APK.

```bash
$ unzip -l app.apk | grep -E 'lib/|assets/' 
  4213  classes.dex
  88210 assets/classes.jar.bin
  1902336 lib/arm64-v8a/libjiagu.so
```

Три сигнала сразу. Маленький `classes.dex` (4 КБ) — почти нет кода. Блоб
`assets/classes.jar.bin` — вероятно, зашифрованный DEX. Библиотека `libjiagu.so` — характерное
имя упаковщика Qihoo 360 Jiagu. Комбинации имён библиотек — самый надёжный указатель:

```bash
$ for f in $(unzip -l app.apk | awk '{print $4}' | grep '\.so$'); do
    strings "app.apk:$f" 2>/dev/null | grep -m1 -iE 'jiagu|legu|bangcle|dexhelper|shell';
  done
```

Зная упаковщик, выбирают тактику: для одних хватает `frida-dexdump`, для других нужен перехват
нативного дешифратора.

## Частые ошибки

Ошибка первая — путать упаковщик с обфускатором. Обфускатор оставляет код в DEX (виден в JADX,
хоть и переименован), упаковщик убирает код из DEX целиком. Если JADX показывает 7 классов и
крошечный `classes.dex` — это упаковка, а не обфускация.

Ошибка вторая — дампить слишком рано. Если приложение грузит код лениво (после входа или открытия
экрана), дамп сразу после старта даст только загрузчик. Нужно дождаться триггера загрузки.

Ошибка вторая (продолжение) — дампить, не сняв RASP. Приложение закроется под Frida, и дамп не
сработает. Сначала обход проверок, потом дамп.

Ошибка третья — не починить заголовки. Повреждённый заголовок DEX не даст JADX прочитать файл,
хотя байткод внутри целый.

## Что делать дальше: типовой порядок

1. Определить упаковщик по имени `.so` и структуре APK.
2. Запустить приложение под Frida и снять RASP-проверки.
3. Дампнуть DEX из памяти (`frida-dexdump -d`).
4. При необходимости — починить заголовки.
5. Прочитать результат в JADX.

Этот порядок одинаков для большинства упаковщиков; меняются только детали обхода проверок и
момент дампа.

## Шпаргалка: упаковщики

| Признак в APK | Вероятный упаковщик |
|---|---|
| `libjiagu.so` | Qihoo 360 Jiagu |
| `libDexHelper.so` | Baidu |
| `libprotectClass.so` | Bangcle |
| `assets/*.bin`, высокая энтропия | любой (шифрованный DEX) |
| `classes.dex` в несколько КБ | любой |

Порядок действий: определить по имени `.so` → снять RASP → дампнуть память (`frida-dexdump -d`) →
при необходимости починить заголовки → открыть в JADX. Ключевая мысль: расшифрованный код всегда
существует в памяти, и его можно перехватить.
