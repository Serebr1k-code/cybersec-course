## Вопрос, с которого всё начинается

Рекламные SDK хотят отслеживать пользователя между приложениями. Apple это ограничила
механизмом **App Tracking Transparency (ATT)**: приложение обязано спросить разрешение. Но что
именно оно спрашивает, что получает при отказе и как разработчики пытаются обойти отказ?
Разберём ATT изнутри.

## Наш пример: запрос разрешения на трекинг

Приложение при первом запуске показывает диалог «Разрешить отслеживание?». Разберём, что стоит
за этим диалогом и как меняется поведение при отказе.

## Шаг 1: идентификаторы

- **IDFA** (Identifier for Advertisers) — рекламный идентификатор, общий для всех приложений,
  используется для кросс-приложенческого трекинга. Доступен только при разрешении ATT.
- **IDFV** (Identifier for Vendor) — идентификатор вендора, общий для приложений одного
  разработчика. Доступен всегда, но не для кросс-вендорного трекинга.

При отказе в ATT `IDFA` становится нулевым (`00000000-0000-0000-0000-000000000000`).

## Шаг 2: запрос ATT

Запрос делается через `ATTrackingManager`:

```swift
ATTrackingManager.requestTrackingAuthorization { status in
    switch status {
    case .authorized: /* IDFA доступен */
    case .denied:     /* IDFA недоступен */
    default: break
    }
}
```

Обязательно нужен ключ `NSUserTrackingUsageDescription` в `Info.plist` — иначе диалог не
покажется.

## Шаг 3: что видит приложение при отказе

При отказе приложение не получает IDFA. Но оно всё ещё может использовать:

- `IDFV` — для своих приложений;
- рекламный атрибуционный токен (SKAdNetwork) — агрегированную атрибуцию без идентификатора;
- собственные идентификаторы в Keychain.

Именно поэтому отказ ATT не означает полного отсутствия аналитики.

## Шаг 4: обход отказа — фингерпринтинг

Часть разработчиков обходит ATT через **фингерпринтинг**: набор косвенных признаков (модель
устройства, версия ОС, набор шрифтов, разрешение экрана, часовой пояс) образует устойчивый
отпечаток без IDFA. Apple это запрещает и требует удалять такой код, но на практике он
встречается.

Признаки фингерпринтинга в приложении: сбор десятков системных параметров, хеширование набора
характеристик, отправка отпечатка на сервер.

## Шаг 5: как анализировать

- Проверьте `NSUserTrackingUsageDescription` и наличие запроса ATT.
- Посмотрите, не собирается ли фингерпринт вместо/в дополнение к IDFA.
- Сравните поведение при `authorized` и `denied` (прокси + подмена ответа).
- Сверьтесь с Privacy Manifest: заявлен ли трекинг.

## Шаг 6: атрибуция без IDFA — SKAdNetwork

Когда ATT запрещён, кросс-приложенческий трекинг по IDFA невозможен, но рекламную атрибуцию
(«установил ли пользователь приложение после клика по объявлению») можно получить через
**SKAdNetwork**. Схема такая: рекламная сеть подписывает клик, приложение при установке
регистрируется, а Apple возвращает атрибуцию агрегированно — без раскрытия личности. Это
законный путь: он не требует IDFA и работает даже при отказе в ATT.

```swift
SKAdNetwork.registerAppForAdNetworkAttribution()
```

Так приложение участвует в атрибуции, не собирая идентификатор пользователя.

## Шаг 7: Privacy Manifest и required reason API

Apple обязала приложения декларировать сбор данных в **Privacy Manifest** (`PrivacyInfo.xcprivacy`).
Там указывают: какие категории данных собираются, используются ли трекинговые домены и зачем
вызываются «required reason» API (например, чтение системного времени или диска). Для аудита это
отличная точка входа: если манифест говорит «трекинга нет», а приложение собирает фингерпринт —
это явное нарушение.

```bash
$ plutil -p MyApp.app/PrivacyInfo.xcprivacy | head
{
  "NSPrivacyTracking" => 0
  "NSPrivacyCollectedDataTypes" => [ ... ]
}
```

## Шаг 8: как проверить поведение при отказе

Самый наглядный метод — поставить прокси между приложением и сервером и сравнить трафик при
разных статусах ATT. Если при `denied` запросы с идентификатором всё равно уходят — либо
используется IDFV/свой идентификатор, либо собирается фингерпринт. На jailbreak-устройстве можно
напрямую подменить статус:

```bash
$ frida -U -f com.example.app -l att_bypass.js
```

где скрипт хукает `trackingAuthorizationStatus` и возвращает `.authorized`. Так проверяют, как
приложение ведёт себя в каждом режиме, не меняя системные настройки.

## Таблица идентификаторов iOS

| Идентификатор | Нужен ATT | Область | Сброс |
|---|---|---|---|
| IDFA | да | между приложениями | «Ограничение трекинга» |
| IDFV | нет | один вендор | удалить все приложения вендора |
| UDID | — | устройство | недоступен приложениям |
| SKAdNetwork | нет | агрегированная атрибуция | — |
| Keychain ID | нет | самоподписанный | удалить Keychain |

## Практический вывод

ATT — это про информированное согласие, а не про запрет аналитики. При отказе исчезает только
IDFA; IDFV, SKAdNetwork и собственные идентификаторы остаются. Поэтому при аудите важно не
ограничиваться фактом запроса ATT, а проверить, что приложение делает при отказе: собирает ли
косвенные признаки, декларирует ли трекинг в Privacy Manifest, совпадает ли заявленное с
фактическим. Расхождение между манифестом и поведением — самый весомый аргумент в отчёте.

## Шаг 9: как Apple проверяет соблюдение ATT

Apple проверяет приложения и вручную, и автоматически: анализирует трафик, смотрит Privacy
Manifest, ищет запрещённые API. Приложение, которое собирает фингерпринт или использует IDFA без
разрешения, рискует отклонением и удалением из App Store. Для аудитора это полезный ориентир:
если приложение прошло ревью, значит заявленное поведение хотя бы правдоподобно. Но на практике
нарушения встречаются, особенно в сторонних SDK, которые подключают как готовый модуль.

## Что делать при аудите трекинга

1. Найти в бинарнике строки `ATTrackingManager` и `NSUserTrackingUsageDescription`.
2. Посмотреть, вызывается ли запрос разрешения и что происходит в каждом статусе.
3. Проверить, собирается ли фингерпринт: список системных API, хеширование, отправка на сервер.
4. Сверить с Privacy Manifest: заявлен ли трекинг, какие категории данных.
5. Сравнить трафик при `authorized` и `denied` через прокси.

## Чек-лист по ATT и приватности

- Диалог ATT показывается (ключ на месте, вызов есть).
- При отказе IDFA не используется.
- Фингерпринтинг не собирается (или заявлен).
- Privacy Manifest соответствует поведению.
- Сторонние SDK не собирают данные в обход.

## Практический сценарий: проверка приложения на трекинг

Начнём с бинарника: ищем `ATTrackingManager` и `NSUserTrackingUsageDescription`. Если ключа нет,
диалог не покажется вовсе — это уже нарушение. Дальше запускаем приложение через прокси и
смотрим трафик: уходит ли идентификатор, какой именно. Затем сравниваем поведение при
`authorized` и `denied`, подменяя статус через Frida или меняя настройки приватности. Ищем
признаки фингерпринтинга: сбор десятков системных параметров и их хеширование. В конце сверяем
всё с Privacy Manifest. Если приложение заявляет отсутствие трекинга, а по факту собирает
отпечаток — это главная находка аудита.

## Что писать в отчёте

Фиксируют: показывается ли диалог ATT, что происходит при отказе, какие идентификаторы
используются (IDFA/IDFV/свой), собирается ли фингерпринт, соответствует ли Privacy Manifest
поведению. Отдельно перечисляют сторонние SDK, которые ведут себя иначе, чем основное
приложение, — именно они чаще всего нарушают правила приватности.

## Частые заблуждения о приватности iOS

Первое заблуждение: «ATT запрещает всю аналитику». На деле запрещён только кросс-приложенческий
трекинг по IDFA; IDFV, SKAdNetwork и собственные идентификаторы остаются доступными. Второе:
«IDFV нельзя сбросить». Его можно сбросить, удалив все приложения вендора, — этим пользуются
тестировщики. Третье: «фингерпринтинг невозможен на iOS». Он возможен, просто запрещён правилами,
и встречается в сторонних SDK. Четвёртое: «Privacy Manifest гарантирует отсутствие трекинга».
Манифест — это декларация; она может расходиться с фактическим поведением. Именно поэтому аудит
строится на наблюдении за трафиком, а не на доверии к манифесту.

## Итоговая мысль

ATT — это не технический барьер, а механизм согласия. Он убирает IDFA, но оставляет разработчику
множество других сигналов, и задача аудитора — увидеть, какие из них реально используются. Самая
ценная находка при проверке приватности — не сам факт запроса разрешения, а расхождение между
заявленным и фактическим поведением: Privacy Manifest говорит одно, трафик показывает другое.
Чтобы это поймать, недостаточно прочитать манифест — нужно понаблюдать за приложением в обоих
режимах и сравнить. Такой подход превращает формальную проверку в содержательный аудит.

## Как отличить законную аналитику от слежки

Не всякий сбор данных — нарушение. Аналитика для улучшения продукта (сколько раз открыли экран,
где произошла ошибка) законна, если она не связывает пользователя между приложениями и заявлена
в манифесте. Слежка начинается там, где появляется кросс-приложенческий идентификатор или
устойчивый отпечаток устройства, переданный третьей стороне. Граница проходит по цели и по
связыванию, а не по самому факту сбора. Поэтому при аудите полезно для каждой передачи данных
ответить на два вопроса: связана ли она с личностью пользователя и заявлена ли она честно.

## Что мы теперь знаем

- ATT требует разрешения на трекинг; без него IDFA недоступен.
- IDFV и SKAdNetwork доступны и без разрешения.
- Обход ATT — фингерпринтинг, запрещённый Apple.
- Анализ: запрос ATT, поведение при отказе, признаки отпечатка.

## Если не сработало

Если диалог ATT не появляется, проверьте ключ `NSUserTrackingUsageDescription` и что
`requestTrackingAuthorization` реально вызывается. При отказе в настройках запрос повторно не
показывается. Для теста меняйте статус сбросом настроек приватности или подменой ответа прокси.

## Частые вопросы

**ATT блокирует всю аналитику?** Нет, только кросс-приложенческий трекинг по IDFA.

**IDFV можно сбросить?** Да, удалением всех приложений вендора.

**Фингерпринтинг законен?** Apple его запрещает, но технически возможен.
