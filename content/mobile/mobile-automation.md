## Вопрос, с которого всё начинается

Ты протестировал одно приложение: распаковал, посмотрел манифест, поискал секреты, снял pinning, дампнул Keychain. Теперь у тебя десять приложений, и делать то же самое вручную — часы рутины. Как автоматизировать повторяющиеся шаги, чтобы оставить себе только анализ?

## Наш пример: скрипт сканирования APK

Автоматизация начинается с самого скучного — поиска секретов. Возьмём реальный скрипт `scan_apk.py`, который распаковывает APK, перебирает интересные файлы и ищет «отпечатки» ключей по регуляркам:

```python
import sys, zipfile, re
PATTERNS = {
    "google_api": r"AIza[0-9A-Za-z_\-]{35}",
    "aws_key":    r"AKIA[0-9A-Z]{16}",
    "firebase":   r"[a-z0-9\-]+\.firebaseio\.com",
    "stripe":     r"sk_live_[0-9a-zA-Z]{24}",
    "jwt":        r"eyJ[A-Za-z0-9_\-]+\.[A-Za-z0-9_\-]+\.[A-Za-z0-9_\-]+",
}
apk = sys.argv[1]
with zipfile.ZipFile(apk) as z:
    names = z.namelist()
    print(f"[+] {apk}: {len(names)} entries")
```

Скрипт перебирает `*.dex`, `*.so`, `*.json`, `*.xml`, `*.properties` и печатает найденные совпадения. Запустим на реальном APK:

```
$ python3 scan_apk.py uncrack1.apk
[+] uncrack1.apk: 13 entries
[+] interesting files: 4
```

На `uncrack1` ничего не найдено — это учебное приложение. А на большом реальном APK:

```
$ python3 scan_apk.py fdroid.apk
[+] fdroid.apk: 973 entries
[+] interesting files: 547
```

973 файла, 547 «интересных» — вручную это долго, а скрипт пробегает за секунды. Это и есть принцип автоматизации: **массовый, дешёвый шаг отдаём машине, а решения оставляем себе**.

## Шаг 1: что автоматизируют

Разделим задачи по уровню автоматизации:

| Задача | Инструмент |
|--------|-----------|
| Статический скан (секреты, manifest) | свой скрипт, MobSF |
| Динамические обходы | Frida-скрипты, Objection |
| Массовый дамп трафика | mitmproxy + скрипты |
| Прогон тест-кейсов UI | Appium |
| Отчёт | шаблоны + автоматический сбор |

Ключевая идея: у каждого этапа есть «механическая» часть, которую можно заскриптовать.

## Шаг 2: автоматизация динамики через Frida

Frida позволяет описать обходы один раз и переиспользовать. Например, скрипт, который сразу снимает root/jailbreak-детект, pinning и логирует токены:

```javascript
// отключаем проверки файлов, похожих на root/jailbreak
var fe = Module.findExportByName(null, 'access');
Interceptor.attach(fe, {
  onEnter: function (args) {
    this.p = args[0].readUtf8String();
  },
  onLeave: function (ret) {
    if (this.p && /(su$|magisk|Cydia|\/var\/jb)/.test(this.p)) ret.replace(-1);
  }
});
```

Такой скрипт запускается одинаково на Android и iOS (с поправкой на API), и его можно хранить как «стартовый набор» для любого приложения. Это экономит часы на каждом новом таргете.

## Шаг 3: MobSF — комбайн статики

**MobSF** (Mobile Security Framework) — инструмент, который автоматически прогоняет статический анализ APK/IPA: разбирает манифест, ищет небезопасные настройки, встроенные секреты, опасные разрешения, известные CVE в библиотеках — и формирует отчёт. Запуск в Docker:

```
$ docker run -it -p 8000:8000 opensecurity/mobile-security-framework-mobsf
```

Через веб-интерфейс загружаешь APK — и получаешь отчёт за минуты. MobSF не заменяет ручной анализ, но быстро закрывает базовые проверки.

## Шаг 4: автоматизация на уровне UI — Appium

Когда нужно прогнать пользовательские сценарии (логин, переход по экранам), используют **Appium** — фреймворк автоматизации UI. Тест описывается кодом:

```python
from appium import webdriver
caps = {"platformName": "Android", "appPackage": "com.demo.secapp",
        "appActivity": ".MainActivity"}
d = webdriver.Remote("http://localhost:4723", caps)
d.find_element("id", "edit_text").send_keys("s3cr3t")
d.find_element("id", "button").click()
```

Appium управляет реальным устройством или эмулятором и позволяет воспроизводить сценарии в цикле. Это полезно для регрессионного тестирования защиты и для массового прогона.

## Шаг 5: автоматизация перехвата

Перехват трафика тоже автоматизируют. **mitmproxy** умеет запускать скрипты на каждый запрос/ответ, фильтровать и сохранять данные:

```python
def response(flow):
    if "api.demo.example" in flow.request.pretty_url:
        print(flow.request.url, flow.response.status_code)
```

В связке с Frida-обходом pinning это даёт полностью автоматизированный конвейер: приложение работает, трафик собирается, скрипт ищет аномалии.

## Шаг 6: сборка пайплайна

Хороший пайплайн выглядит так. Шаг 1: автоматический статический скан (MobSF + свой скрипт) — быстрый обзор. Шаг 2: динамика с готовыми Frida-скриптами — обход защит. Шаг 3: автоматический перехват трафика. Шаг 4: ручной анализ только тех мест, где скрипты нашли «интересное». Так ты не тратишь время на рутину и фокусируешься на нестандартном.

## Шаг 7: что не автоматизировать

Автоматизация не всесильна. Бизнес-логику, цепочки уязвимостей и креативные обходы по-прежнему делает человек. Скрипт найдёт секрет в строке, но не поймёт, что токен можно переиспользовать для захвата аккаунта. Поэтому автоматизацию применяют как **фильтр**, а не как замену аналитика.

## Шаг 8: воспроизводимость через контейнеры

Чтобы автоматизация работала у всей команды одинаково, инструменты упаковывают в контейнеры. MobSF уже поставляется как Docker-образ, Frida ставится скриптом, mitmproxy — тоже. Тогда «у меня не работает» превращается в «запусти вот эту команду». Воспроизводимость — половина успеха автоматизации: скрипт, который работает только на одной машине, бесполезен для команды.

Полезно завести один репозиторий со скриптами: сканер APK, набор Frida-обходов, скрипты mitmproxy и шаблон отчёта. Тогда на новом таргете ты не пишешь всё заново, а подключаешь готовые модули.

## Шаг 9: как измерить пользу

Автоматизацию стоит оценивать по времени, которое она экономит. Если ручной скан APK занимает 20 минут, а скрипт — 10 секунд плюс минута на разбор вывода, выигрыш очевиден. Но если ты пишешь сложный скрипт три часа ради одной задачи, это не автоматизация, а самоцель. Правило простое: автоматизируй то, что повторяется. И держи скрипты простыми: сложный скрипт труднее поддерживать, чем сделать шаг вручную, и он быстрее ломается при обновлении инструментов. Начни с одного маленького скрипта — например, поиска секретов — и добавляй модули по мере надобности. Главное — чтобы скрипт было легко прочитать и поправить. Плохой признак — скрипт, который никто, кроме автора, не может запустить: значит, автоматизация не работает как командный инструмент.

## Шаг 10: минимальный CI-шаг для мобильного скана

Автоматизацию удобно начинать с одного шага в CI. Вот фрагмент GitHub Actions, который поднимает MobSF в контейнере, загружает APK и забирает отчёт:

```yaml
- name: Start MobSF
  run: docker run -d -p 8000:8000 opensecurity/mobile-security-framework-mobsf
- name: Upload & scan
  run: |
    curl -s -X POST http://localhost:8000/api/v1/upload \
      -H "Authorization: $MOBSF_API_KEY" -F "file=@app.apk"
- name: Pull report
  run: curl -s http://localhost:8000/api/v1/report_json -H "Authorization: $MOBSF_API_KEY" -o report.json
```

Здесь важно: API-ключ MobSF (`MOBSF_API_KEY`) кладут в секреты CI, а не в репозиторий; результат сканирования сравнивают с базовым, чтобы пайплайн падал только на **новых** проблемах, а не на всём списке. Такой шаг даёт быструю обратную связь разработчику, но не заменяет ручной динамический анализ — статика не видит runtime-логику.

## Что мы теперь знаем

- Автоматизация отдаёт машине массовые шаги, а решения — человеку.
- Свой скрипт быстро ищет секреты по регуляркам в APK.
- Frida-скрипты переиспользуются для обхода защит на разных таргетах.
- MobSF даёт быстрый статический отчёт по APK/IPA.
- Appium автоматизирует UI-сценарии.
- mitmproxy со скриптами автоматизирует перехват трафика.
- Бизнес-логику и цепочки автоматизировать нельзя.
