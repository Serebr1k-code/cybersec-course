## Вопрос, с которого всё начинается

Приложение вы собираете из своего кода — но в APK оказываются десятки чужих библиотек: аналитика,
реклама, крашлитика, платежи. Каждая из них имеет доступ к тем же данным, что и приложение.
Что если одна из них собирает лишнее или содержит уязвимость? Разберём риски сторонних SDK и
как их инвентаризировать.

## Наш пример: разбор зависимостей

```bash
$ unzip -l app.apk | grep -E 'lib/.*\.so' | head
  lib/arm64-v8a/libflutter.so
  lib/arm64-v8a/libanalytics.so
  lib/arm64-v8a/libads.so
$ aapt dump badging app.apk | grep -i permission
uses-permission: name='android.permission.INTERNET'
uses-permission: name='android.permission.ACCESS_FINE_LOCATION'
```

Уже видно, что в приложении есть сторонние нативные библиотеки и что оно просит доступ к
геолокации. Вопрос — кто именно её использует: приложение или SDK.

## Шаг 1: что такое сторонний SDK

SDK (software development kit) — готовая библиотека, которую разработчик подключает, чтобы не
писать функциональность самому: аналитика, реклама, push, платежи, крашлитика. Плюс — скорость
разработки. Минус — вы доверяете чужому коду доступ к своим данным и разрешениям.

## Шаг 2: риски

| Риск | Что значит |
|---|---|
| Избыточный сбор данных | SDK отправляет на сервер больше, чем нужно |
| Лишние разрешения | SDK требует доступ, не нужный приложению |
| Уязвимости | в старой версии SDK есть известные CVE |
| Динамическая загрузка | SDK догружает код в рантайме (обход проверок) |
| Supply-chain | SDK скомпрометирован или подменён |

Особенно опасна динамическая загрузка: SDK может подгрузить код, которого не было при
проверке, — и никакая статическая проверка его не увидит.

## Шаг 3: инвентаризация SDK

Соберите список SDK из трёх источников: нативные библиотеки (`lib/*.so`), Java-пакеты (имена
классов) и сетевые домены (которые SDK шлёт данные). Сопоставив их, вы поймёте, какие SDK
присутствуют и что каждый из них может.

```bash
$ strings libads.so | grep -iE 'https?://[a-z0-9.-]+' | sort -u | head
https://ads.example.com/v1/collect
```

## Шаг 4: сетевой анализ

Перехват трафика показывает, что SDK реально отправляет. Это самый честный источник: SDK может
заявлять одно, а отправлять другое. Обращайте внимание на идентификаторы устройства,
геолокацию и то, уходит ли это на домены, не связанные с основным функционалом.

## Шаг 5: известные уязвимости

Проверяйте версии SDK по CVE. Часто в приложении остаётся старая версия библиотеки с известной
уязвимостью (например, в SDK для push или рекламы). Инвентаризация с версиями — обязательный
шаг аудита.

## Шаг 6: рекомендации

- Минимизировать число SDK.
- Обновлять SDK и следить за CVE.
- Ограничивать разрешения на уровне приложения.
- Проверять, не догружает ли SDK код.
- Документировать, какие данные и куда уходят.

## Что мы теперь знаем

- Сторонние SDK — чужие библиотеки в приложении.
- Риски: данные, разрешения, CVE, динамическая загрузка, supply-chain.
- Инвентаризация — по .so, классам и доменам.
- Сетевой анализ — самый честный источник.

## Шаг 7: юридические и приватностные аспекты

Сторонние SDK — не только техническая, но и юридическая тема. Регламенты (GDPR, CCPA) требуют,
чтобы разработчик знал, какие данные собираются и кому передаются. SDK, который отправляет
идентификатор устройства на сторонний сервер, делает разработчика ответственным за эту
передачу — даже если он не писал этот код. Поэтому инвентаризация SDK нужна не только
безопасникам, но и юристам.

Практический вывод: при аудите фиксируйте не только «какие SDK есть», но и «какие данные
каждый из них отправляет и куда». Это превращает технический отчёт в документ, пригодный для
оценки соответствия.

## Шаг 8: как SDK обходят ограничения

Интересная категория — SDK, которые ведут себя агрессивнее, чем ожидает разработчик. Некоторые
динамически загружают код, чтобы обойти статические проверки магазина; некоторые собирают
данные, не заявленные в политике; некоторые регистрируют свои компоненты (сервисы, ресиверы)
и работают в фоне. Всё это видно при анализе манифеста: сторонние `service`, `receiver`,
`provider` — частый признак «тяжёлого» SDK.

```bash
$ aapt dump xmltree app.apk AndroidManifest.xml | grep -iE 'service|receiver' | head
```

Если компонент принадлежит чужому пакету, стоит понять, зачем он и что делает. Иногда это
легитимная аналитика, иногда — избыточный сбор данных.

## Шаг 9: практический чек-лист инвентаризации

1. Список нативных библиотек (`lib/*.so`) и их назначение.
2. Список Java-пакетов сторонних вендоров (по именам классов).
3. Список сетевых доменов, к которым обращается приложение.
4. Версии SDK и известные CVE для них.
5. Компоненты манифеста, принадлежащие SDK.
6. Наличие динамической загрузки кода.

Пройдясь по этим пунктам, вы получите полную картину присутствующих SDK и их влияния на
безопасность и приватность приложения.

## Шаг 10: связь с supply-chain

Риски SDK — часть общей проблемы supply-chain. Атака на популярный SDK (или на его обновление)
компрометирует сразу тысячи приложений. Поэтому зрелые команды: фиксируют версии SDK, проверяют
их происхождение, следят за уведомлениями безопасности и минимизируют зависимости. Для
пентеста это означает, что находка «в приложении устаревший SDK с известной CVE» — не мелочь,
а реальный риск, который нужно зафиксировать с указанием версии и CVE. Так технический аудит
смыкается с управлением зависимостями, и обе стороны выигрывают от одной и той же
инвентаризации.

## Шаг 11: как отличить легитимный SDK от проблемного

Не всякий сторонний SDK — риск. Различие в прозрачности и объёме. Легитимный SDK: заявляет
собираемые данные, не требует лишних разрешений, не догружает код, обновляется. Проблемный:
собирает больше заявленного, регистрирует скрытые компоненты, подгружает код, использует
устаревшие версии с CVE. Практический признак — сопоставьте заявленные в политике данные с
тем, что реально уходит в трафике. Расхождение и есть находка.

Ещё один сигнал — разрешения. Если приложение просит доступ к контактам или SMS, а
функциональность этого не требует, стоит выяснить, не SDK ли это тянет. Часто именно рекламные
или аналитические SDK вынуждают разработчика запрашивать избыточные разрешения.

## Шаг 12: автоматизация инвентаризации

Ручной разбор десятков SDK утомителен, поэтому его автоматизируют. Инструменты вроде MobSF
дают отчёт о библиотеках, разрешениях и сетевых вызовах; сканеры зависимостей сопоставляют
версии с базами CVE. Практический конвейер: распаковать APK, собрать список `.so` и пакетов,
прогнать через сканер уязвимостей, сопоставить домены с трафиком. Это даёт воспроизводимый
отчёт, который можно приложить к аудиту.

Автоматизация важна и потому, что SDK меняются: обновление приложения может добавить новый
SDK. Поэтому инвентаризацию стоит встроить в CI — тогда появление проблемной зависимости
ловится до релиза, а не после.

## Шаг 13: приватность как часть безопасности

В современном аудите приватность и безопасность идут рука об руку. Утечка данных через SDK —
это и инцидент безопасности, и нарушение регламента. Поэтому отчёт по SDK должен отвечать на
два вопроса: «может ли этот SDK навредить безопасности» и «соответствует ли сбор данных
заявленному». Оба ответа опираются на одну и ту же инвентаризацию, но адресованы разным
заинтересованным сторонам — безопасникам и юристам.

## Шаг 14: итог по сторонним SDK

Сторонние SDK — неизбежная часть мобильной разработки и одновременно источник рисков:
избыточный сбор данных, лишние разрешения, известные уязвимости, динамическая загрузка кода и
supply-chain-атаки. Управление этими рисками начинается с инвентаризации: собрать список SDK
по нативным библиотекам, пакетам и доменам, проверить версии по CVE, проанализировать трафик и
компоненты манифеста. Автоматизация делает этот процесс регулярным. А главный практический
вывод: разработчик отвечает за весь код в приложении, включая чужой, — и потому обязан знать,
что делают подключённые SDK.

## Шаг 15: практический вывод

Главное про сторонние SDK: разработчик отвечает за весь код в приложении, включая чужой.
Поэтому аудит SDK — это не формальность, а способ управлять рисками данных, разрешений и
supply-chain. Начните с инвентаризации (библиотеки, пакеты, домены), проверьте версии по CVE,
сопоставьте трафик с заявленной политикой и посмотрите компоненты манифеста. Этого достаточно,
чтобы выявить большинство проблем и обосновать рекомендации — обновить, ограничить или убрать
конкретный SDK.

## Шаг 16: как встроить аудит SDK в процесс

Разовый аудит мало что даёт, если зависимости меняются каждую неделю. Поэтому зрелый подход —
встроить проверку в CI: при сборке собирать список зависимостей, сверять версии с базой CVE,
запрещать сборку при появлении критичной уязвимости. Это смещает обнаружение проблем влево, к
разработчику, и снижает стоимость исправления. Дополнительно полезно вести реестр одобренных
SDK: какой вендор, какие данные, кто ответственный. Тогда новый SDK проходит проверку до
попадания в приложение, а не после инцидента. Так технический аудит превращается в управляемый
процесс, а не в разовую находку.

## Шаг 17: итог

Подводя черту: знайте свои зависимости, проверяйте их версии, следите за трафиком и
компонентами. Это базовая гигиена мобильной разработки, которая защищает и пользователей, и
репутацию приложения.

## Шаг 18: финальная мысль

Инвентаризация — не разовое мероприятие, а привычка: возвращайтесь к ней при каждом обновлении
зависимостей, и проблемные SDK будут ловиться до релиза, а не после инцидента.
