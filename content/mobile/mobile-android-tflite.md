## Вопрос, с которого всё начинается

В APK лежит файл `model.tflite`. Это не картинка и не код — что внутри и как это прочитать?
И главное: если модель можно заменить, что произойдёт с приложением, когда оно её загрузит?

## Наш пример: файл модели

Находим модель в APK:

```bash
$ unzip -l app.apk | grep tflite
  1048576  assets/model.tflite
$ file model.tflite
model.tflite: data
```

`file` не распознаёт формат — он не текстовый и не стандартный контейнер. Значит, нужен
специализированный взгляд.

## Шаг 1: FlatBuffers

`.tflite` — это **FlatBuffers**: формат сериализации, где данные лежат в одном буфере, а
доступ к полям идёт по смещениям без распаковки. Для нас важно: структура описана схемой, и
по ней можно прочитать граф модели. На верхнем уровне у файла есть «магические» байты
`TFL3`, по которым его узнают инструменты.

## Шаг 2: граф и тензоры

Внутри — **граф** вычислений: список операций (свёртка, активация, сложение) и **тензоры** —
многомерные массивы, которые эти операции читают и пишут. Веса модели тоже лежат здесь
(часто в сжатом виде). Инструмент для чтения — `flatc` со схемой или Python-интерпретатор:

```python
import tensorflow as tf
interp = tf.lite.Interpreter(model_path='model.tflite')
interp.allocate_tensors()
for op in interp._get_ops_details():
    print(op['op_name'], op['inputs'], op['outputs'])
```

Вывод — список операций с их входами и выходами. Это карта модели.

## Шаг 3: интерпретатор

**Интерпретатор** — это код, который исполняет граф. Стандартные операции реализованы в
самой библиотеке TensorFlow Lite. Приложение загружает модель и вызывает интерпретатор:
модель — это данные, интерпретатор — программа. Разделение важно: атака может быть либо на
данные (подменить модель), либо на программу (эксплуатировать баг интерпретатора).

## Шаг 4: кастомные операции

Если разработчику нужна операция, которой нет в стандартном наборе, он регистрирует
**кастомную операцию** — свой код на C++, который интерпретатор вызовет по имени. В графе
такая операция помечена как `Custom`. Вот здесь и появляется риск: имя кастомной операции
из модели связывается с кодом приложения. Если приложение доверяет модели и подставляет
произвольное имя, может возникнуть путаница или, в худшем случае, выполнение кода.

## Шаг 5: подмена модели

Практический сценарий: модель лежит в `assets/`, её можно заменить, пересобрав APK
(см. `mobile-android-smali-patch`). Что произойдёт? Если приложение проверяет хеш модели —
подмена провалится. Если нет — приложение загрузит нашу модель. Это либо обход логики
(например, классификатор всегда возвращает «разрешено»), либо попытка вызвать кастомную
операцию с неожиданными параметрами.

## Шаг 6: защита и её слабости

Разработчики защищают модель шифрованием и проверкой хеша. Но интерпретатор всё равно должен
её расшифровать перед загрузкой, поэтому в памяти модель появляется в открытом виде — её
можно вытащить дампом. А проверка хеша, если она в самом приложении, обходится патчем.
Вывод: модель — это данные, а данные, которые приложение исполняет, всегда стоят проверки.

## Что мы теперь знаем

- `.tflite` — FlatBuffers с графом и тензорами, опознаётся по `TFL3`.
- Граф = операции + тензоры; веса лежат внутри файла.
- Интерпретатор исполняет граф; стандартные операции встроены.
- Кастомные операции расширяют поверхность: имя из модели связывается с кодом.
- Подмена модели и дамп памяти — основные практические атаки.
