## Вопрос, с которого всё начинается

Мы разобрали экспортированные компоненты. Но под ними лежит более глубокий слой — **Binder**, механизм межпроцессного взаимодействия (IPC) в Android. Почти любой вызов между приложениями в итоге превращается в Binder-транзакцию. Понимание Binder нужно, чтобы видеть атаки, которые не видны на уровне манифеста. Как это устроено?

## Наш пример: сервис с Binder-интерфейсом

Вернёмся к манифесту `fdroid.apk`. Среди сервисов есть такой:

```
$ grep -oE '<service[^>]*SystemJobService[^>]*' fdroid_dec/AndroidManifest.xml
<service android:exported="true" android:name="androidx.work.impl.background.systemjob.SystemJobService"
         android:permission="android.permission.BIND_JOB_SERVICE"/>
```

Сервис экспортирован, но защищён разрешением `BIND_JOB_SERVICE`. Это типичный пример Binder-сервиса: к нему можно привязаться (`bindService`) и получить объект `IBinder`, через который идут вызовы. Разберём, что это значит.

## Шаг 1: что такое Binder

Binder — это драйвер и протокол, через который процессы обмениваются сообщениями. Когда приложение вызывает метод другого процесса, аргументы упаковываются в **Parcel** (поток байт) и отправляются Binder-транзакцией. На той стороне Parcel распаковывается, и вызывается метод.

Ключевые понятия:

- **IBinder** — ссылка на удалённый объект.
- **Parcel** — сериализованные данные (аргументы и результат).
- **Транзакция** — сам вызов (номер кода метода + данные).
- **AIDL** — язык описания интерфейсов, по которому генерируются заглушки.

Именно потому, что аргументы приходят из другого процесса, их **нельзя доверять**: чужое приложение может прислать произвольный Parcel.

## Шаг 2: как найти bound service

Ищем в манифесте сервисы с экспортом и без защиты:

```
$ grep -oE '<service[^>]*android:exported="true"[^>]*' fdroid_dec/AndroidManifest.xml
```

Если у сервиса есть `android:permission` — доступ ограничен. Если нет — к нему может привязаться любое приложение. Дальше смотрим AIDL-интерфейс: какие методы он предоставляет. Интерфейсы лежат в `.aidl`-файлах при сборке и превращаются в сгенерированные Java-классы; в декомпилированном коде их видно как `Stub`/`Proxy`.

## Шаг 3: чтение AIDL-интерфейса

В декомпилированном коде ищем `extends IInterface.Stub`:

```
$ grep -rn "extends IInterface" out/ | head
out/sources/com/example/IPaymentService.java
```

Смотрим метод:

```java
public interface IPaymentService extends IInterface {
    void transfer(String to, int amount) throws RemoteException;
    String getBalance() throws RemoteException;
}
```

Такой интерфейс — это «API» сервиса. Если `transfer` не проверяет, кто вызвал (`getCallingUid`), любое приложение может перевести деньги.

## Шаг 4: вызов через adb (service call)

Низкоуровневый способ — `service call`, который напрямую посылает Binder-транзакцию по номеру:

```
$ adb shell service list | grep example
$ adb shell service call example 1 s16 "attacker" i32 1000
```

Здесь `1` — номер транзакции (код метода), далее аргументы. Номера транзакций соответствуют порядку методов в AIDL. Этот способ хрупкий (зависит от версии), но полезен, когда нет своего клиента.

## Шаг 5: свой клиент-приложение

Надёжнее написать маленькое приложение, которое биндится к сервису и вызывает методы через сгенерированный AIDL-стаб:

```java
Intent i = new Intent();
i.setComponent(new ComponentName("com.example.app", "com.example.PaymentService"));
bindService(i, conn, Context.BIND_AUTO_CREATE);
// в onServiceConnected:
IPaymentService svc = IPaymentService.Stub.asInterface(service);
svc.transfer("attacker", 1000);
```

Так проверяют, действительно ли метод выполняет действие без авторизации.

## Шаг 6: атака на недоверенный Parcel

Самый глубокий класс атак — когда сервис разбирает Parcel без проверки. Известные проблемы включают:

- **Parcel desynchronization** — лишние/недостающие поля сбивают парсер, и он читает из следующей транзакции.
- **Некорректные размеры массивов** — приводят к падению или чтению чужой памяти.
- **`readStrongBinder` на непроверенном объекте** — позволяет подсунуть свой Binder и получить обратный вызов в контексте жертвы.

Такие атаки требуют понимания формата Parcel и часто ведут к утечке данных или повышению привилегий.

## Шаг 7: проверка вызывающего

Правильная защита Binder-сервиса — проверять, кто вызвал:

```java
int uid = Binder.getCallingUid();
if (uid != MY_UID) throw new SecurityException("denied");
```

Если такой проверки нет, а метод значим — уязвимость. Дополнительно проверяют `Binder.getCallingPid()` и разрешения вызывающего.

## Почему Binder недооценён

Большинство мобильных пентестов останавливаются на уровне манифеста: нашли экспортированный компонент, вызвали, отчитались. Binder лежит на слой ниже и потому часто остаётся незамеченным. А между тем именно через Binder проходит **весь** IPC в Android — от системных сервисов до обмена между приложениями. Если разработчик написал свой bound service и ошибся в проверке вызывающего, уязвимость не видна в манифесте и не ловится простым `am start`.

Именно поэтому Binder — тема для тех, кто хочет находить то, что пропускают другие. Атаки на недоверенный Parcel, desync-транзакции, подмена `IBinder` — это класс уязвимостей, который требует понимания формата данных и часто даёт серьёзные последствия: утечку памяти, обход авторизации, повышение привилегий.

## Разбор реального сценария

Приложение предоставляет сервис `IPaymentService` с методом `transfer(to, amount)`. Сервис экспортирован (чтобы его мог вызвать виджет), но проверки `getCallingUid` в методе нет. Атакующее приложение биндится к сервису, получает стаб и вызывает `transfer("attacker", 1000)`. Формально у атакующего нет никаких прав — но он действует руками привилегированного сервиса. Это confused deputy на уровне Binder: без проверки вызывающего любой метод становится публичным API.

## Частые вопросы

**«Binder — это только для системных сервисов?»** — нет, любое bound service использует Binder. **«Как найти уязвимость?»** — экспортированный сервис без `android:permission` и без `getCallingUid`. **«Сложно ли это?»** — базовый уровень (вызов метода) прост, атаки на Parcel — сложны. **«Нужен ли root?»** — нет. **«Как защитить?»** — проверять `getCallingUid`/`getCallingPid` и требовать разрешение.

## Практический совет

Воспринимайте bound service как REST API без аутентификации, пока не доказано обратное. Читайте AIDL, выписывайте методы, и для каждого спрашивайте: «проверяет ли он, кто вызвал?». Если нет и метод меняет состояние — фиксируйте. Начинайте с простого вызова метода из своего клиента: это доказывает доступ, а уже потом углубляйтесь в разбор Parcel, если хотите большего.

## Полный прогон от начала до конца

Соберём проверку Binder-сервиса в один сценарий. Сначала `grep '<service'` по манифесту и список экспортированных. Для каждого — есть ли `android:permission`. Затем `grep "extends IInterface"` в декомпилированном коде и выписываем методы. Дальше биндимся к сервису из своего приложения или пробуем `service call`. Смотрим, проверяет ли метод `getCallingUid`. Итог — либо подтверждённый доступ к привилегированному методу, либо защищённый сервис. Если метод меняет состояние и проверки нет — фиксируем с высоким приоритетом.

## Ещё один нюанс: обратные вызовы

Binder работает в обе стороны: сервис может вызвать `readStrongBinder` и получить ссылку на объект вызывающего, чтобы потом позвать его методы. Если сервис делает это с непроверенным Parcel, атакующий подсовывает **свой** Binder и получает обратный вызов в контексте сервиса. Это менее очевидный, но мощный вектор: код сервиса сам вызывает ваш объект, и вы оказываетесь в его процессе. Проверяйте, где сервис читает `IBinder` из входящих данных.

## Что мы теперь знаем

По-простому:

1. Binder — транспорт IPC; вызовы идут транзакциями с Parcel.
2. Аргументы из другого процесса недоверенны по определению.
3. Экспортированный сервис без `android:permission` доступен любому приложению.
4. AIDL описывает интерфейс; `Stub`/`Proxy` — точки входа.
5. Защита — проверка `getCallingUid` и разрешений.
