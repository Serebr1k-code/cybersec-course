## Вопрос, с которого всё начинается

Банковское приложение требует подтвердить перевод, а мошенник получает доступ к счёту, не
зная пароля. Как? Через сервис, который сам Google позиционирует как инструмент доступности
для людей с ограничениями — **Accessibility Service**. Разберём, почему он стал любимым
оружием мобильной малвари.

## Наш пример: приложение-«помощник»

На устройстве жертвы установлено приложение, которое при первом запуске просит включить
«специальные возможности». В декомпилированном манифесте видим:

```xml
<service android:name=".HelperService"
         android:exported="true"
         android:permission="android.permission.BIND_ACCESSIBILITY_SERVICE">
    <intent-filter>
        <action android:name="android.accessibilityservice.AccessibilityService"/>
    </intent-filter>
    <meta-data android:name="android.accessibilityservice"
               android:resource="@xml/accessibility_config"/>
</service>
```

Само по себе объявление легально. Опасность — в том, что делает `HelperService`.

## Шаг 1: что видит Accessibility Service

Обычное приложение видит только себя. Accessibility Service получает от системы **дерево
доступности** активного окна: все видимые элементы, их текст, координаты, а иногда и
содержимое полей ввода. Метод `onAccessibilityEvent` вызывается при каждом изменении UI.

Это значит:

- **Что видно:** заголовки экранов, тексты кнопок, значения полей, уведомления.
- **Что можно:** выполнять `ACTION_CLICK`, `ACTION_SET_TEXT`, скроллить, нажимать «Назад».

Формально это ровно то, что нужно человеку, который не может вести пальцем по экрану.
Фактически — это доступ к содержимому любого приложения.

## Шаг 2: почему это кейлоггер

Если сервис фильтрует события по `TYPE_VIEW_TEXT_CHANGED`, он получает каждый введённый
символ. В коде это выглядит безобидно:

```java
public void onAccessibilityEvent(AccessibilityEvent e) {
    if (e.getEventType() == AccessibilityEvent.TYPE_VIEW_TEXT_CHANGED) {
        log(e.getText().toString());
    }
}
```

Так реализуется **кейлоггинг**: логин, пароль, номер карты, OTP — всё, что пользователь
печатает, попадает к атакующему. Никаких root-прав для этого не нужно.

## Шаг 3: overlay и «автоклик»

Второй сценарий — **overlay-атаки**. Сервис может рисовать поверх банковского приложения
свой экран (или, если доступна `SYSTEM_ALERT_WINDOW`, накладывать окно). Жертва думает, что
вводит данные в банк, а на деле — в форму атакующего.

Третий сценарий — **автоматические нажатия**: получив событие «открылся экран подтверждения
перевода», сервис сам вызывает `ACTION_CLICK` на кнопке «Подтвердить». Жертва даже не
успевает понять, что произошло.

## Шаг 4: как искать злоупотребление

Статически — ищем объявление accessibility-сервиса и смотрим, какие события он обрабатывает
и что делает:

```bash
$ grep -rn "onAccessibilityEvent" decompiled/smali/ | head
decompiled/smali/com/evil/HelperService.smali: ...
$ grep -rn "TYPE_VIEW_TEXT_CHANGED\|ACTION_CLICK\|setText" decompiled/smali/com/evil/HelperService.smali
```

Динамически — через `adb` смотрим, какие сервисы доступности включены:

```bash
$ adb shell settings get secure enabled_accessibility_services
com.evil/.HelperService
```

Любой accessibility-сервис, который не является известным помощником (TalkBack, Switch
Access), — повод присмотреться.

## Шаг 5: как защищаются приложения

С Android 12+ банки используют `AccessibilityService`-detection: приложение проверяет,
включён ли подозрительный сервис, и блокирует чувствительные операции. Также помогает
`setFilterTouchesWhenObscured(true)` против tapjacking и `FLAG_SECURE` против скриншотов.

Но защита неполна: сервис доступности всё равно видит дерево, если пользователь его включил.
Поэтому последняя линия — информировать пользователя и не полагаться только на технику.

## Шаг 6: вывод для пентеста

В отчёте злоупотребление Accessibility описывают как **«небезопасное использование
специальных возможностей»**: приложение не проверяет, кто именно включил сервис, и
доверяет вводу/нажатиям, пришедшим из дерева доступности. Для малвари это способ обойти
sandbox без root.

## Что мы теперь знаем

- Accessibility Service получает дерево UI активного окна и может действовать за пользователя.
- `TYPE_VIEW_TEXT_CHANGED` = кейлоггер без root.
- Overlay и автоклики превращают его в инструмент банковского фрода.
- Искать: объявление сервиса + `onAccessibilityEvent` + чувствительные действия.

## Шаг 7: конфигурация сервиса

Поведение Accessibility Service описывает XML-ресурс, указанный в `meta-data`. Типичный
`accessibility_config.xml`:

```xml
<accessibility-service
    android:accessibilityEventTypes="typeAllMask"
    android:accessibilityFeedbackType="feedbackGeneric"
    android:canRetrieveWindowContent="true"
    android:accessibilityFlags="flagDefault"/>
```

Ключевые атрибуты:

- `accessibilityEventTypes` — какие события получать. `typeAllMask` означает «все» — это
  избыточно и подозрительно для «помощника», которому хватило бы пары типов.
- `canRetrieveWindowContent="true"` — разрешает читать дерево окна. Без него кейлоггинг
  невозможен.
- `accessibilityFlags` — например, `flagRequestFilterKeyEvents` добавляет доступ к нажатиям
  клавиш на уровне ввода, что усиливает кейлоггер.

Чем шире маска событий и больше флагов, тем мощнее сервис и тем важнее проверить, зачем это
приложению.

## Шаг 8: отличие от обычного overlay

Можно спутать accessibility-абуз с `SYSTEM_ALERT_WINDOW` (permission для рисования поверх
других окон). Это разные механизмы:

- `SYSTEM_ALERT_WINDOW` даёт **рисовать** поверх экрана, но не читать содержимое чужого окна.
- Accessibility Service даёт **читать** и **действовать**, но рисует только ограниченно
  (через `TYPE_ACCESSIBILITY_OVERLAY`).

Сильнее всего они вместе: overlay показывает поддельный экран, а accessibility-сервис
считывает, что пользователь в него ввёл. В банковских троянах это стандартная связка.

## Шаг 9: как отличить легитимный сервис

Легитимный сервис обычно:

- обрабатывает узкий набор событий (например, только уведомления мессенджера);
- не читает текстовые поля паролей;
- не делает сетевых запросов с собранным текстом;
- не запрашивает `canRetrieveWindowContent` без необходимости.

Признаки абуза: `typeAllMask`, чтение `TYPE_VIEW_TEXT_CHANGED`, отправка текста на внешний
сервер, автоклик по кнопкам подтверждения, обфускация имён методов.

## Шаг 10: динамическая проверка

Помимо `settings get secure enabled_accessibility_services`, полезно посмотреть, какие
приложения вообще объявляют такие сервисы:

```bash
$ adb shell pm list packages -f | wc -l
$ adb shell dumpsys accessibility | head -40
```

`dumpsys accessibility` показывает зарегистрированные сервисы, их флаги и активные
подписки на события. Если сервис подписан на все типы событий, но приложение — «фонарик»,
это красный флаг.

## Шаг 11: правовой и этический аспект

Злоупотребление доступностью — это не просто технический баг, а часто признак **stalkerware**
и банковского фрода. При анализе важно не только доказать возможность, но и оценить,
использует ли приложение сервис легитимно. В отчёте это разделяют: «небезопасный дизайн»
против «явное злоупотребление». Для пентеста достаточно продемонстрировать, что сервис может
прочитать пароль или подтвердить операцию без ведома пользователя.

## Шаг 12: цепочка банковского трояна целиком

Разберём, как отдельные техники складываются в реальную атаку — это помогает понять, почему
accessibility-абуз так ценен для малвари.

1. **Доставка.** Троян приходит как «мод» или «оптимизатор» и просит включить специальные
   возможности — формально добровольно.
2. **Разведка.** Сервис слушает `TYPE_WINDOW_STATE_CHANGED` и определяет, какое банковское
   приложение открыто, по имени пакета в событии.
3. **Overlay.** Поверх банка рисуется поддельный экран «подтвердите операцию», а сервис
   читает введённый PIN через `TYPE_VIEW_TEXT_CHANGED`.
4. **Автоклик.** Настоящий экран перевода подтверждается кликом, который сервис делает сам,
   пока жертва смотрит на фальшивку.
5. **Эксфильтрация.** Собранные данные уходят на C2-сервер обычным HTTPS-запросом.

Ни на одном шаге не нужен root. Именно поэтому Google и банки вкладываются в детект.

## Шаг 13: как детектят и как его обходят

Способы детекта на стороне приложения:

- проверка `enabled_accessibility_services` на список «своих» сервисов;
- эвристика: если событий слишком много и они приходят от незнакомого сервиса — блокировать
  ввод;
- `setFilterTouchesWhenObscured(true)` — игнорировать касания, если окно перекрыто другим.

Обход со стороны атакующего: скрывать факт подписки, мимикрировать под системный сервис,
добавлять задержки и рандомизацию событий. Это гонка вооружений, и в отчёте её важно описать
как ограничение: детект снижает, но не устраняет риск.

## Шаг 14: что фиксировать в отчёте

Опишите: объявление сервиса (класс, маска событий, флаги), какие данные он читает, какие
действия выполняет, куда уходят данные. Отдельно — можно ли было обойтись без таких широких
разрешений. Для малвари добавьте MITRE-маппинг: Collection через Accessibility, Input Capture
через `TYPE_VIEW_TEXT_CHANGED`, Abuse of Accessibility Features как техника уклонения.

## Шаг 15: мини-чек-лист

Объявлен ли accessibility-сервис? Какая у него маска событий — узкая или `typeAllMask`?
Читает ли он `TYPE_VIEW_TEXT_CHANGED`? Делает ли сетевые запросы с собранным текстом? Есть
ли автоклик по кнопкам подтверждения? Если на большинство вопросов «да» — перед вами либо
кейлоггер, либо очень плохо спроектированный «помощник». В обоих случаях это находка.

## Шаг 16: как это выглядит в трафике и логах

Даже когда сервис не рисует overlay, его работа заметна. В `adb logcat` видны сообщения
самого приложения о прочитанных событиях, если разработчик оставил отладочный вывод. В
сетевом трафике — периодические POST-запросы на незнакомый домен сразу после ввода текста в
банковском приложении. Корреляция «пользователь ввёл пароль — ушёл POST» — сильный признак
кейлоггера. При анализе полезно запустить приложение на тестовом устройстве, ввести
контрольную строку в любое поле и посмотреть, не появится ли эта строка в исходящем запросе.
Это прямой эксперимент, который почти всегда подтверждает злоупотребление, если оно есть.

## Шаг 17: почему пользователь соглашается

Ключевая причина живучести этой техники — социальная инженерия. Пользователю показывают
системный экран «Специальные возможности» и просят включить сервис ради «экономии батареи»
или «ускорения телефона». Экран настоящий, предупреждение настоящее, и человек нажимает
«Включить». После этого вредоносное приложение получает больше возможностей, чем получило бы
даже при root. Именно поэтому в отчёте важно различать техническую уязвимость и вектор
доставки: часто самое слабое звено — не код, а интерфейс согласия. Защита строится на двух
уровнях: приложение должно детектить чужие accessibility-сервисы и блокировать ввод, а
платформа — предупреждать, что включённый сервис сможет видеть всё, что вы делаете на экране.

## Шаг 18: итог

Accessibility Service — двойственный инструмент: он честно помогает людям с ограничениями и
одновременно даёт полный обзор экрана любому, кто получил согласие пользователя. Понимание
этого баланса и есть ключ к анализу: вы смотрите не на «плохой код», а на несоответствие
заявленной цели и реальных возможностей сервиса.

## Квиз

Проверь себя.

```quiz
- question: Что получает Accessibility Service от системы?
  options:
    - Только имя активного приложения
    - Дерево доступности активного окна с текстом и координатами
    - Полный root-доступ
    - Только уведомления
  answer: 1
  explanation: Сервис видит элементы UI: текст, кнопки, поля ввода.
- question: Какое событие превращает сервис в кейлоггер?
  options:
    - TYPE_WINDOW_STATE_CHANGED
    - TYPE_VIEW_TEXT_CHANGED
    - TYPE_VIEW_CLICKED
    - TYPE_NOTIFICATION_STATE_CHANGED
  answer: 1
  explanation: Изменение текста в поле = введённый символ.
- question: Как сервис может подтвердить перевод без участия жертвы?
  options:
    - Через root-шелл
    - Вызвав ACTION_CLICK на кнопке подтверждения
    - Перезагрузив устройство
    - Через Bluetooth
  answer: 1
  explanation: Сервис может выполнять действия, включая клики, за пользователя.
- question: Где посмотреть включённые сервисы доступности?
  options:
    - adb shell settings get secure enabled_accessibility_services
    - adb shell ls /sdcard
    - adb logcat -c
    - adb shell pm list packages
  answer: 0
  explanation: Эта настройка перечисляет активные accessibility-сервисы.
```
