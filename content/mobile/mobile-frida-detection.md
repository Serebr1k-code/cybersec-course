## Вопрос, с которого всё начинается

Только подключаешь Frida — приложение мгновенно закрывается или выдаёт ошибку. Инструментация есть, но использовать её нельзя. Как приложение понимает, что его анализируют, и как это переиграть?

## Наш пример: приложение, которое «чувствует» Frida

Возьмём защищённое приложение, которое при подключении Frida завершается. Разберём, какие сигналы оно проверяет, и по очереди нейтрализуем их. Цель — довести инструментацию до состояния, когда приложение работает и мы видим его методы.

## Шаг 1: что вообще выдаёт инструментацию

Frida оставляет несколько следов в процессе:

1. **Строки в памяти.** В карте памяти (`/proc/self/maps`) появляются сегменты с именами вроде `frida-agent-64.so`, `gum-js-loop`, `frida-gadget`.
2. **Открытый порт.** Frida-сервер слушает TCP-порт (по умолчанию `27042`). Приложение может попытаться к нему подключиться.
3. **Потоки.** У Frida характерные имена потоков (`gmain`, `gdbus`, `pool-frida`).
4. **Задержки.** Инструментация замедляет выполнение — по таймингам можно заподозрить хук.

Каждый сигнал — отдельная проверка, и их обычно комбинируют.

## Шаг 2: проверка через /proc/self/maps

Самая частая — чтение своей карты памяти и поиск строки `frida`:

```c
// псевдокод нативной проверки
FILE *f = fopen("/proc/self/maps", "r");
char line[512];
while (fgets(line, sizeof(line), f)) {
    if (strstr(line, "frida") || strstr(line, "gum-js")) {
        return DETECTED;
    }
}
```

Обход — перехватить чтение этого файла и вырезать из результата строки Frida. Но проще: если проверка нативная, хук ставится раньше (spawn), и в момент, когда приложение читает `/proc/self/maps`, нужных строк там ещё/уже нет.

## Шаг 3: проверка порта Frida

Второй приём — попытка подключиться к порту `27042`:

```java
// приложение проверяет, слушает ли кто-то стандартный порт Frida
try {
    new Socket("127.0.0.1", 27042);
    return DETECTED;
} catch (IOException e) {
    return CLEAN;
}
```

Обход — запустить Frida-сервер на нестандартном порту:

```
$ frida-server -l 0.0.0.0:12345
$ frida -H 127.0.0.1:12345 -f com.target.app -l hook.js
```

Тогда стандартный порт пуст, и проверка не срабатывает. Это один из самых простых и надёжных приёмов.

## Шаг 4: ptrace и отладчик

Проверка отладчика обычно нативная. Классика — `ptrace(PTRACE_TRACEME)`:

```c
if (ptrace(PTRACE_TRACEME, 0, 0, 0) == -1) {
    return DEBUGGER_DETECTED;   // уже кто-то трассирует
}
```

Если процесс уже под отладчиком, вызов вернёт ошибку. Обход — подменить `ptrace` на заглушку, всегда возвращающую 0:

```javascript
var ptrace = Module.getGlobalExportByName("ptrace");
Interceptor.replace(ptrace, new NativeCallback(
    function () { return 0; }, 'long', ['int','int','pointer','pointer']));
```

Аналогично перехватывают чтение `/proc/self/status` (там поле `TracerPid`) и заменяют вывод.

## Шаг 5: проверка через тайминги

Более тонкий метод — измерить время выполнения операции. Если код внезапно стал медленнее (из-за хуков), приложение делает вывод, что его инструментируют. Обход — не перехватывать «горячие» функции без необходимости и ставить хуки точечно.

Стоит помнить: чем больше хуков, тем заметнее замедление. Поэтому минимизируйте инструментацию.

## Шаг 6: почему хук «не встаёт»

Если приложение падает **до** того, как хук сработал, значит проверка выполняется раньше. Решения:

- **Spawn вместо attach.** `frida -f <package>` запускает процесс и ставит хуки до первого кода приложения.
- **Хук на раннем этапе.** Перехватить `JNI_OnLoad` или конструктор, чтобы успеть до проверки.
- **Маскировка.** Переименовать агент Frida, чтобы строки `frida` в памяти не появлялись.

Проверить, что хук встал, можно так же, как в уроке про динамический анализ: вывести адрес найденной функции. Если адрес не выводится — функция не найдена, и хук не поставлен.

## Шаг 7: обход через систему, а не через Frida

Когда Frida обнаруживается настолько надёжно, что обход хуков не помогает, меняют подход: обходят защиты **без Frida**.

- **Патч APK.** Убрать вызовы проверок из кода и пересобрать приложение. Тогда инструментация не нужна вовсе.
- **Magisk/Zygisk-модули.** Скрывают root и следы инструментации на уровне системы.
- **Эмуляция.** Запуск в контролируемой среде, где сигналы подделываются.

Это компромисс: патч APK требует переупаковки и может сломать проверку подписи, а системные модули — root-устройства. Но иногда это единственный путь.

## Шаг 8: порядок действий при «Frida ловится»

Если приложение закрывается при подключении, действуйте по порядку от простого к сложному:

1. **Смените порт Frida-сервера** на нестандартный. Это нейтрализует проверку порта без единой строчки кода.
2. **Перейдите на spawn** (`frida -f`), чтобы хуки вставали раньше проверок.
3. **Определите, какая проверка срабатывает.** Логируйте открытия файлов (`/proc/self/maps`, `/proc/self/status`) и вызовы `ptrace`, `fopen`, `socket` — так видно, что именно читает приложение.
4. **Перехватите эту проверку** — верните «чистый» результат.
5. **Если не помогает** — патч APK или системное сокрытие.

Пункт 3 — ключевой: прежде чем обходить, нужно **увидеть**, какая проверка сработала. Перехват системных вызовов (`openat`, `read`, `connect`) показывает путь к файлу и порт, которые интересуют приложение. Это превращает обход из угадывания в точную работу.

## Шаг 9: почему важно знать нативную сторону

Большая часть anti-Frida реализована в нативном коде, а не в Java. Причина: Java-проверку легко перехватить через `Java.use`, а нативную — сложнее. Поэтому, если в jadx вы не находите проверок, а приложение всё равно падает, ищите их в `.so`:

```
$ nm -D lib/arm64-v8a/libprotect.so | grep -iE 'detect|debug|frida|anti'
$ strings lib/arm64-v8a/libprotect.so | grep -iE 'frida|gum|ptrace|TracerPid'
```

Найденные имена и строки указывают на функции проверки. Дальше их либо реверсят, либо перехватывают по смещению. Это связывает тему с уроками про нативный реверс и `mobile-hooking-internals`.

## Что мы теперь знаем

По-простому:

1. Frida выдаёт себя строками в памяти, портом, потоками и задержками.
2. Проверки бывают Java (порт) и нативные (maps, ptrace).
3. Обход порта — нестандартный порт Frida-сервера.
4. Обход `ptrace`/`maps` — хук соответствующей функции.
5. Если хук опаздывает — используйте spawn; если Frida ловится всегда — патч APK или системные модули.

## На что смотреть дальше

- **Стандартный порт — первая улика.** Смените его сразу.
- **Spawn спасает от опоздания.** Проверки на старте обгоняют attach.
- **Не переусердствуйте с хуками.** Больше хуков — больше задержек и следов.
- **Патч APK — крайний случай.** Помните про проверку подписи.
- **Логируйте системные вызовы.** Это быстрее, чем угадывать, какая проверка сработала.
- **Нативная защита — норма.** Если в Java проверок нет, ищите их в `.so`.
- **Проверяйте по шагам.** Сменили порт — проверьте, не падает ли приложение; только потом ставьте хуки.

## Обнаружение через тайминги и инструкции

Приложение может измерять время между инструкциями: отладчик и хуки замедляют
исполнение, и аномалия выдаёт инструментацию. На нативном уровне используют счётчик
тактов (`rdtsc` на x86, `cntvct` на ARM) или `clock_gettime`:

```c
uint64_t t1 = clock_gettime_nsec_np(CLOCK_MONOTONIC_RAW);
/* ... подозрительный участок ... */
uint64_t t2 = clock_gettime_nsec_np(CLOCK_MONOTONIC_RAW);
if ((t2 - t1) > THRESHOLD) { /* debugger detected */ }
```

Такую проверку трудно перехватить точечно: она не опирается на конкретный файл или
символ. Обход — либо вернуть «нормальное» время (хук на функцию времени), либо
минимизировать число хуков, чтобы задержка не выходила за порог.

## Серверный детект: приложение «жалуется» на бэкенд

Иногда приложение не падает, а тихо отправляет на сервер признак «под инструментацией».
Внешне это выглядит как «всё работает», но часть API перестаёт отвечать. Ищите исходящие
запросы с полями вроде `integrity`, `debug`, `rooted`:

```bash
$ tcpdump -i any -A 'tcp port 443' | grep -iE 'integrity|rooted|debug'
```

Перехватив такой запрос, подмените значение на «чистое». Это важнее, чем обход клиентских
проверок: серверная реакция (блокировка функций) незаметна на клиенте.

## Системное сокрытие: Magisk, Zygisk, DenyList

Корень виден приложению через `/proc`, `getprop`, наличие `su`. Magisk прячет корень, а
Zygisk с DenyList исключает выбранное приложение из своей среды:

```bash
$ magisk --denylist add com.example.app
$ magisk --denylist ls
```

Добавьте приложение в DenyList и перезапустите его — многие проверки (`su`, `magisk`)
перестанут срабатывать. Но Frida-сервер Zygisk не прячет: для него нужны отдельные модули
или gadget в режиме, не оставляющем следов в памяти.

## Frida Gadget вместо сервера

Сервер Frida (`frida-server`) оставляет процесс и открытый порт — это первое, что ищут
проверки. Gadget встраивают прямо в APK как библиотеку и загружают из кода приложения:

```bash
$ objection patchapk --source app.apk --gadget libfrida-gadget.so
```

Тогда отдельного процесса и порта нет, и «стандартные» проверки не срабатывают. Цена —
пересборка и переподпись APK, а также необходимость загружать библиотеку (иногда через
`System.loadLibrary` в `attachBaseContext`). Это самый надёжный путь, когда сервер ловится
всегда.

## Как отличить anti-debug от anti-Frida

Проверки бывают нацелены на разные инструменты, и обход у них разный. Прежде чем что-то
хукать, определите, что именно сработало:

| Признак в поведении | Что ищут | Что делать |
|---------------------|----------|-----------|
| Приложение падает сразу после `attach` | отладчик, `ptrace` | `spawn`, хук `ptrace` |
| Падает при `frida -U -n` | процесс/порт Frida | сменить порт, gadget |
| Работает, но функции пусты | серверный детект | подменить запрос |
| Падает через пару секунд | тайминги | хук времени, меньше хуков |

Отладчик (`ptrace`) и Frida оставляют разные следы: первый виден по `TracerPid`, вторая —
по строкам `frida`/`gum` в памяти и по нестандартному потоку. Разделяя эти случаи, вы не
тратите время на обход того, чего приложение не проверяет.

## Куда дальше

Теперь ты знаешь, как приложение ловит инструментацию и как её прятать. В следующем уроке разберём ещё один слой защиты — проверки целостности среды (SafetyNet/Play Integrity и аттестацию) — и научимся их обходить. А пока главное: anti-Frida — это набор сигналов, каждый из которых нейтрализуется либо хуком, либо сменой способа инструментации.

## Где пригодится

- **CTF Mobile:** обход анти-Frida для перехвата защищённых методов.
- **Анализ malware:** вредоносные приложения активно прячутся от анализа.
- **Пентест:** инструментация приложений с сильной защитой.
- **Работа:** понимание границ того, что вообще можно инструментировать.
