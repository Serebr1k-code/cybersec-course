## Вопрос, с которого всё начинается

Мы получили root на устройстве. Но root после перезагрузки исчезает — а нужно закрепиться так,
чтобы код запускался при каждой загрузке, до приложений и часто до обнаружения. Первое место,
куда смотрит атакующий, — процесс `init` и его конфигурация. Разберём, как это устроено.

## Наш пример: служба, которая запускается при загрузке

Мы хотим, чтобы наш бинарник запускался при каждой загрузке системы. Разберём путь от файла
`init.rc` до реально работающей службы.

## Шаг 1: что такое init

`init` — первый процесс пользовательского пространства (PID 1). Он монтирует разделы, запускает
`zygote`, `servicemanager` и все системные службы. Его поведение описано в `.rc`-файлах
(`/system/etc/init/`, `/vendor/etc/init/`).

## Шаг 2: структура .rc-файла

Файл состоит из **действий** (`on`) и **служб** (`service`):

```text
service mysvc /system/bin/mysvc
    class main
    user root
    seclabel u:r:magisk:s0
    oneshot

on boot
    start mysvc
```

`service` описывает программу, `on boot` — когда её запускать. `seclabel` задаёт SELinux-контекст,
от которого зависят права.

## Шаг 3: триггеры и порядок

Действия срабатывают по **триггерам**: `early-init`, `init`, `late-init`, `boot`,
`property:ro.debuggable=1`. Порядок триггеров определяет, что успеет запуститься раньше. Это
важно: запуск на `early-init` происходит очень рано.

## Шаг 4: как закрепиться

На root-устройстве злоумышленник (или пентестер) добавляет свой `.rc`-файл и службу. Типичные
точки:

- `/system/etc/init/` (или через Magisk overlay);
- `/vendor/etc/init/`;
- сервис в `class main`, запускаемый на `boot`.

```bash
$ cat /system/etc/init/persist.rc
service persist /data/local/tmp/persist.sh
    class main
    user root
    oneshot
```

## Шаг 5: маскировка и обнаружение

Персистентность часто маскируют под системные имена (`logd-helper`, `vendor.qti.*`). При
форензике ищут:

- службы с путями в `/data/` или `/data/local/tmp`;
- нестандартные `seclabel`;
- `.rc`-файлы, не принадлежащие вендору;
- бинарники без подписи вендора.

## Что мы теперь знаем

- `init` (PID 1) запускает систему по `.rc`-файлам.
- `.rc` содержит `service` и `on <trigger>` действия.
- Триггеры задают момент запуска (вплоть до early-init).
- Персистентность = своя служба + `.rc`; её выдают пути в `/data` и чужой seclabel.

## Если не сработало

Если служба не запускается, проверьте SELinux-контекст: без разрешающей политики `init`
убьёт процесс. Если раздел `/system` только для чтения, используйте Magisk-overlay или
`/data/adb/`. Проверьте `dmesg`/`logcat` на отказ `init`.

## Частые вопросы

**init.rc можно править без root?** Нет, нужен доступ к системному разделу.

**Как обнаружить такую персистентность?** Сравнением `.rc`-файлов с эталоном прошивки.

**Это работает на современных Android?** Да, но с учётом SELinux и verified boot.

## Полный жизненный цикл init и порядок триггеров

Чтобы закрепиться через `init`, нужно точно знать, когда сработает ваша служба. `init` проходит
через последовательность триггеров, и порядок фиксирован.

Сначала идут `early-init` и `init` — здесь настраивается самое базовое: монтируются ранние
разделы, поднимается `property_service`. Затем `late-init` запускает очередь действий:
`early-fs`, `fs`, `post-fs`, `post-fs-data`, `late-fs`, `early-boot`, `boot`. Именно на `boot`
запускается большинство служб `class main`.

```text
early-init -> init -> late-init -> fs -> post-fs -> post-fs-data -> boot
```

Практический вывод: служба на `early-init` стартует очень рано, до многих подсистем, и может не
иметь нужного окружения. Служба на `boot` стартует позже, но уже после того, как поднялись
основные сервисы. Для персистентности обычно выбирают `boot`, а для максимального сокрытия —
более ранние триггеры.

## Разбор реального .rc: не только service и on

Блок `service` умеет больше, чем «бинарник + пользователь». Разберём полный набор типовых
опций на примере.

```text
service mysvc /system/bin/mysvc
    class main
    user root
    group root system
    seclabel u:r:magisk:s0
    socket mysvc stream 660 root system
    capabilities NET_ADMIN NET_RAW
    priority -20
    oneshot
    disabled

on boot
    start mysvc
```

Здесь: `class main` привязывает службу к триггеру `boot`; `user`/`group` задают права процесса;
`seclabel` — SELinux-контекст; `socket` создаёт unix-сокет для связи; `capabilities` даёт
дополнительные привилегии (например, работу с сетью); `priority` повышает приоритет; `oneshot`
означает «запустить и не перезапускать»; `disabled` — служба не стартует автоматически, её
запускают явно (`start mysvc`).

Обратите внимание на `socket` и `capabilities`: вредоносная служба, которой нужен доступ к сети
или к сетевым настройкам, укажет их. Наличие `NET_ADMIN` у несистемной службы — красный флаг.

## Как читать /system/etc/init/ и /vendor/etc/init/

На современных Android главный файл `init.rc` вынесен в `/system/etc/init/hw/init.rc`, а
дополнительные фрагменты лежат отдельными файлами в каталогах:

- `/system/etc/init/` — службы системы;
- `/vendor/etc/init/` — службы вендора (драйверы, модем);
- `/data/adb/` — точка монтирования модулей Magisk, которые добавляют свои `.rc`.

Каждый файл — это отдельный фрагмент, который `init` подхватывает при загрузке. Поэтому
вредоносный `.rc` не нужно вписывать в главный файл: достаточно положить его в один из каталогов.

## Обнаружение через сравнение с эталоном

Самое надёжное обнаружение — сравнить набор `.rc`-файлов с эталонной прошивкой той же версии.
Отличия и есть добавленное. Смотрим на файлы, которые не принадлежат вендору, и на службы с
путями вне системных разделов.

```bash
$ grep -rn 'service ' /system/etc/init/ /vendor/etc/init/ | grep -vE '/system/(bin|xbin)/'
/data/adb/modules/hide/etc/init/persist.rc: service persist /data/local/tmp/.p.sh
```

Служба, запускающая скрипт из `/data/local/tmp`, — почти наверняка закладка. Системные службы так
не запускаются.

## Таблица триггеров и что на них запускать

| Триггер | Когда срабатывает | Типичное применение |
|---|---|---|
| early-init | очень рано | низкоуровневые патчи |
| init | базовая инициализация | property_service |
| post-fs-data | после монтирования /data | скрипты Magisk |
| boot | после старта систем | большинство служб |
| property: | при смене свойства | запуск по флагу |

## Если не сработало

Если служба не стартует, проверьте три вещи. Первое — SELinux: без разрешающей политики `init`
убьёт процесс, и в `dmesg`/`logcat` будет отказ (`avc: denied`). Второе — права на файл: бинарник
должен быть исполняемым и доступным по пути. Третье — триггер: служба с `disabled` не стартует
сама, нужен явный `start`.

Если раздел `/system` только для чтения (verified boot, dm-verity), правка невозможна напрямую —
используют overlay через Magisk или размещают `.rc` в `/data/adb/`.

## Ограничения

Современный Android защищает систему от модификации: verified boot проверяет целостность
разделов, а AVB не даст загрузиться с изменённым `/system`. Поэтому классический «правь init.rc»
работает в основном на устройствах с разблокированным загрузчиком и на кастомных прошивках.

Кроме того, `init` строго следует SELinux. Даже с root без корректного `seclabel` ваша служба не
получит нужных прав — либо не запустится вовсе. Это не баг, а защита: `init` — доверенный процесс,
и расширять его полномочия произвольному коду нельзя.

## Мини-практика: добавить службу и проверить её статус

Разберём полный цикл: добавить `.rc`-фрагмент, запустить службу и убедиться, что она работает.

Кладём файл на устройстве с root:

```bash
$ cat /system/etc/init/demo.rc
service demo /data/local/tmp/demo.sh
    class main
    user root
    oneshot

on boot
    start demo
```

Перезагружаемся и смотрим, запустился ли процесс:

```bash
$ adb shell ps -A | grep demo
root      4211  1   ... S /system/bin/sh /data/local/tmp/demo.sh
```

Если процесса нет — смотрим `logcat` и `dmesg` на предмет отказа. Частая причина: `init` не смог
запустить скрипт из-за SELinux или прав на файл.

Проверить статус службы напрямую можно через свойство `init.svc.*`:

```bash
$ adb shell getprop init.svc.demo
running
```

Значение `running` подтверждает, что служба жива. Если `stopped` — она завершилась или не
стартовала.

## Частые ошибки

Ошибка первая — забыть про SELinux. Даже корректный `.rc` не запустит процесс, если у него нет
подходящего домена. Симптом — запись `avc: denied` в `dmesg`.

Ошибка вторая — неверный путь. Системные службы живут в `/system/bin/` и `/system/xbin/`; путь в
`/data/local/tmp/` мгновенно выдаёт нештатную службу и может быть заблокирован политикой.

Ошибка третья — путать триггеры. Служба с `class main` стартует на `boot`, а не сразу после
монтирования данных. Если нужен ранний запуск — выбирайте другой триггер, но учтите, что
окружение может быть не готово.

## Сравнение с другими механизмами персистентности

`init` — не единственный способ закрепиться. Понимание альтернатив помогает и при атаке, и при
обнаружении.

- `init`-службы: запуск процесса при загрузке; требуют доступа к системному разделу.
- Magisk-модули: скрипты `post-fs-data.sh`/`service.sh` в `/data/adb/modules/`; не трогают
  системный раздел.
- Автозапуск приложения: `BroadcastReceiver` на `BOOT_COMPLETED`; доступно любому приложению, но
  легко заметно в манифесте.

Для форензики важно проверять все три места: модифицированный `.rc`, модули Magisk и
`BOOT_COMPLETED`-ресиверы. Злоумышленник может использовать любую комбинацию.

## Шпаргалка: .rc-файлы и init

| Задача | Команда/приём |
|---|---|
| найти службы | `grep -rn 'service ' /system/etc/init/` |
| подозрительные пути | `grep -vE '/system/(bin\|xbin)/'` |
| статус службы | `getprop init.svc.<name>` |
| отказ SELinux | `dmesg \| grep avc` |
| логи init | `logcat \| grep init` |
| ранний запуск | триггер `early-init` |

Помните: служба стартует на своём триггере, путь в `/data/` — признак закладки, а SELinux может
убить процесс даже при корректном `.rc`. Эти три правила покрывают большинство случаев при
анализе персистентности.
