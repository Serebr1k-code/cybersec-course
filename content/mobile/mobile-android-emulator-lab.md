## Вопрос, с которого всё начинается

Ты хочешь разобрать мобильное приложение, но жалко ставить root на личный телефон, а под рукой нет отдельного устройства. Что делать? Ответ — **эмулятор**: виртуальное Android-устройство, которое запускается на компьютере, поддерживает root «из коробки» и откатывается к снапшоту за секунды.

## Наш пример: собираем лабораторию

Наша цель — рабочий стенд: эмулятор Android с root, установленным Frida и перехватом трафика. Начнём с установки **AVD** (Android Virtual Device) — конфигурации виртуального устройства.

## Шаг 1: создаём AVD

Эмулятор управляется утилитой `emulator`, а образы скачиваются через `sdkmanager`. Сначала создадим устройство:

```
$ sdkmanager "system-images;android-34;google_apis;x86_64"
$ avdmanager create avd -n lab -k "system-images;android-34;google_apis;x86_64" -d pixel_6
```

Здесь важно выбрать образ с **google_apis** (а не `google_apis_playstore`): образы без Play Store допускают `adb root`. Устройства с Play Store имеют заблокированный `adbd` и root на них не получить.

## Шаг 2: запускаем с нужными флагами

Запуск эмулятора с записью и «чистым» состоянием:

```
$ emulator -avd lab -no-snapshot -writable-system &
$ adb wait-for-device
$ adb shell getprop ro.product.cpu.abi
x86_64
```

Флаг `-writable-system` разрешает изменять системный раздел — это нужно для установки системного CA. `-no-snapshot` гарантирует, что мы стартуем с чистого состояния, а не с предыдущего снапшота.

## Шаг 3: включаем root

На образе `google_apis` root включается одной командой:

```
$ adb root
restarting adbd as root
$ adb shell id
uid=0(root) gid=0(root)
```

Теперь у нас полный доступ: можно читать `/data/data/*`, ставить модули, подключать Frida. Никакой разблокировки загрузчика и никакого риска для реального устройства.

## Шаг 4: ставим Frida

Frida состоит из двух частей: `frida` на хосте и `frida-server` на устройстве. Версии должны совпадать. Скачиваем сервер под архитектуру эмулятора (`x86_64`):

```
$ frida --version
17.23.3
$ adb push frida-server-17.23.3-android-x86_64 /data/local/tmp/
$ adb shell "chmod 755 /data/local/tmp/frida-server-17.23.3-android-x86_64"
$ adb shell "/data/local/tmp/frida-server-17.23.3-android-x86_64 &"
$ frida-ps -U | head
```

`frida-ps -U` покажет список процессов — значит, связь есть. Теперь можно хукать приложения (см. `mobile-dynamic-frida`).

## Шаг 5: системный CA для перехвата

Начиная с Android 7 пользовательские CA не принимаются большинством приложений. На эмуляторе с `-writable-system` можно положить сертификат в системное хранилище:

```
$ adb remount
$ adb push burp_ca.pem /system/etc/security/cacerts/9a5ba575.0
$ adb shell chmod 644 /system/etc/security/cacerts/9a5ba575.0
$ adb reboot
```

Имя файла — subject hash сертификата (`openssl x509 -subject_hash_old`). После перезагрузки Burp-сертификат доверенный, и часть приложений отдаёт трафик без обхода pinning.

## Шаг 6: снапшоты — главное преимущество

Ключевая фишка эмулятора — **снапшоты**. Ты настраиваешь стенд один раз (root, Frida, CA) и сохраняешь состояние:

```
$ adb emu avd snapshot save clean-lab
```

Теперь после «грязного» эксперимента можно вернуться к чистому состоянию:

```
$ adb emu avd snapshot load clean-lab
```

Это то, чего нет на реальном устройстве: мгновенный откат. Особенно полезно при анализе малвари — запустил образец, посмотрел, откатил.

## Шаг 7: ограничения эмулятора

Эмулятор хорош, но не идеален. Часть приложений **детектит** эмулятор (`Build.FINGERPRINT` содержит `generic`, наличие `/dev/socket/qemud`, свойства `ro.kernel.qemu`) и отказывается работать. Некоторые проверки целостности (Play Integrity) на эмуляторе не проходят. Кроме того, эмулятор не воспроизводит поведение реального Secure Enclave и аппаратных функций. Поэтому для защищённых приложений иногда всё же нужно физическое устройство.

## Шаг 8: автоматизация запуска

Лабораторию удобно поднимать скриптом. Типовой старт: проверить, что AVD существует, запустить эмулятор, дождаться загрузки, включить root, поднять `frida-server`, положить CA. Вот фрагмент такого скрипта:

```bash
#!/bin/bash
set -e
adb wait-for-device
adb root
adb wait-for-device
adb shell "chmod 755 /data/local/tmp/frida-server-17.23.3-android-x86_64"
adb shell "/data/local/tmp/frida-server-17.23.3-android-x86_64 &"
frida-ps -U | head
```

Такой скрипт экономит минуты при каждом перезапуске и исключает забытые шаги.

## Шаг 9: сеть эмулятора

У эмулятора своя виртуальная сеть, и это влияет на перехват. Адрес хоста изнутри эмулятора — `10.0.2.2` (эмулятор сам — `10.0.2.15`). Поэтому прокси на хосте указывают как `10.0.2.2:8080`, а не `127.0.0.1`. DNS эмулятора (`10.0.2.3`) тоже виртуальный. Если приложение обращается к `localhost`, оно попадёт на само устройство, а не на хост, — частая причина «прокси не видит трафик».

Кроме того, эмулятор умеет менять «геолокацию» и подделывать GPS, что полезно при тестировании функций, привязанных к местоположению.

## Шаг 10: что ставить в лабораторию

Минимальный набор инструментов на стенде: `frida-server` (динамика), Burp/mitmproxy на хосте (перехват), системный CA (доверие), при необходимости — LSPosed (хуки) и `objection`. Собрав это один раз и сохранив снапшот, ты получаешь повторяемую среду для любого мобильного таргета.

## Шаг 11: чистое состояние и повторяемость

Главная ценность лаборатории — повторяемость. Один раз настроив снапшот `clean-lab` с root, Frida и CA, ты возвращаешься к нему после любого эксперимента. Это особенно важно при анализе малвари: образец мог изменить систему, и без отката результаты следующего запуска будут искажены. Заведи привычку: перед экспериментом — `snapshot load clean-lab`, после — при необходимости `snapshot save` нового состояния. Так лаборатория всегда остаётся предсказуемой, а ты не тратишь время на переустановку. Если снапшот «поехал», всегда можно удалить AVD и создать заново по документированным шагам — именно поэтому их стоит записать. Документируй флаги запуска: `-writable-system`, образ `google_apis` — от них зависит вся работа стенда. Тогда воспроизвести лабораторию сможет любой коллега, а не только автор скрипта. Это и есть признак хорошей инженерной работы.

## Шаг 12: как получается имя файла CA

В шаге 5 сертификат лёг как `9a5ba575.0`. Это не произвольное имя, а **subject hash** — хеш субъекта сертификата, который Android использует для файлов в `cacerts`. Посчитаем его для нашего CA:

```
$ openssl req -x509 -newkey rsa:2048 -keyout ca.key -out ca.pem -days 365 -nodes -subj "/CN=Burp Proxy CA/O=PortSwigger"
$ openssl x509 -in ca.pem -subject_hash_old -noout
3a4f44b7
```

На устройстве файл должен называться `3a4f44b7.0`. Важно: Android использует **старый** алгоритм, поэтому берём именно `-subject_hash_old`; новый (`-subject_hash`) дал бы `50d0bdf5`, и с таким именем Android файл проигнорирует. Если хеш посчитан неверно, Burp запущен и порт открыт, но трафик «не виден» — потому что CA не доверенный. После копирования проверь, что файл на месте: `adb shell ls -l /system/etc/security/cacerts/ | grep 3a4f44b7`.

## Что мы теперь знаем

- Эмулятор (AVD) — безопасная альтернатива реальному устройству.
- Образ `google_apis` допускает `adb root`, а `google_apis_playstore` — нет.
- `-writable-system` позволяет ставить системный CA.
- Frida ставится как `frida-server` под архитектуру эмулятора.
- Снапшоты дают мгновенный откат состояния.
- Эмулятор детектится частью приложений; для них нужно устройство.
