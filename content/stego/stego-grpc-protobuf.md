## Вопрос, с которого всё начинается

Тебе дали `msg.pb` — бинарное protobuf-сообщение. Protobuf — это формат
сериализации, который используют gRPC и множество API. В отличие от JSON, он не
читается глазами: это байты. Где в нём прячут данные? Оказывается, protobuf допускает
**неизвестные поля** — получатель их игнорирует, но они передаются. Разберём.

## Наш пример: файл msg.pb

```bash
xxd msg.pb
```

```text
00000000: 0a16 6e74 6f7b 6772 7063 5f70 7230 7430  ..nto{grpc_pr0t0
00000010: 6275 665f 666c 3467 7d                   buf_fl4g}
```

Видим `0a` в начале. Это **тег поля**: старшие биты — номер поля, младшие 3 бита —
тип. `0a` = `0000 1010`: номер поля 1, wire-type 2. Дальше `16` — длина (varint) = 22,
затем 22 байта данных. Прочитаем.

## Шаг 1: wire-format protobuf

Protobuf кодирует данные как последовательность полей. Каждое поле:

```
[ тег(varint) ][ данные ]
```

**Тег** — это число `(номер_поля << 3) | wire_type`. Wire-type бывает:

| Wire-type | Значение | Пример |
|---|---|---|
| 0 | varint | int32, bool, enum |
| 1 | 64-bit | fixed64, double |
| 2 | length-delimited | string, bytes, вложенные |
| 5 | 32-bit | fixed32, float |

Для wire-type 2 после тега идёт **varint-длина**, затем данные.

## Шаг 2: varint

**Varint** — кодирование целых чисел переменной длиной: 7 бит на байт, старший бит =
«есть продолжение». Маленькие числа — 1 байт, большие — больше.

```bash
python3 - <<'PY'
def read_varint(d, p):
    val = 0; shift = 0
    while True:
        b = d[p]; p += 1
        val |= (b & 0x7f) << shift
        if not (b & 0x80):
            break
        shift += 7
    return val, p
PY
```

Именно varint делает protobuf компактным: `1` — один байт `01`, а `300` — два байта
`ac 02`.

## Шаг 3: разбираем сообщение вручную

```bash
python3 - <<'PY'
def read_varint(d, p):
    val = 0; shift = 0
    while True:
        b = d[p]; p += 1
        val |= (b & 0x7f) << shift
        if not (b & 0x80):
            break
        shift += 7
    return val, p

d = open('msg.pb','rb').read()
p = 0
while p < len(d):
    tag, p = read_varint(d, p)
    field = tag >> 3
    wt = tag & 7
    if wt == 2:
        ln, p = read_varint(d, p)
        data = d[p:p+ln]; p += ln
        print('field', field, data)
    else:
        break
PY
```

```text
field 1 b'nto{grpc_pr0t0buf_fl4g}'
```

## Шаг 4: где ещё прячут в protobuf/gRPC

- **Неизвестные поля** — получатель игнорирует поля, которых нет в схеме.
- **Порядок полей** — protobuf не требует фиксированного порядка.
- **Вложенные сообщения** — можно добавить «лишний» вложенный объект.
- **gRPC metadata** — заголовки HTTP/2 (`grpc-*`) с произвольными значениями.
- **HTTP/2 заголовки** — `:path`, `user-agent`, кастомные `-bin` заголовки (base64).

## Шаг 5: инструменты

```bash
protoc --decode_raw < msg.pb       # «сырой» разбор без схемы
tshark -r capture.pcap -Y 'http2' -V
grpcurl                            # gRPC-клиент
```

`protoc --decode_raw` — лучший друг: он разбирает protobuf без `.proto`-схемы.
Именно так находят неизвестные поля. Для gRPC поверх HTTP/2 используй `tshark`.

## Шаг 6: почему protobuf удобен для сокрытия

Protobuf спроектирован так, что **неизвестные поля сохраняются и передаются дальше**.
Это нужно для эволюции схем: старый сервер не ломается от нового поля. Но это же
значит, что «лишнее» поле не считается ошибкой. А gRPC поверх HTTP/2 добавляет ещё
слой метаданных, где можно положить произвольные значения.

## Шаг 7: частые ошибки

Первая — путать тег и данные: тег — это `(номер<<3)|type`, а не номер. Вторая —
неверно читать varint (забыть про продолжение). Третья — считать, что без `.proto`
нельзя разобрать: `decode_raw` и ручной парсер работают без схемы. Четвёртая — забыть,
что строки length-delimited и требуют длины.

## Практика: вложенные сообщения и map

Protobuf позволяет вкладывать сообщения: поле wire-type 2 может содержать не строку,
а другое сообщение. Тогда внутри него снова идут теги и значения. Закладку можно
спрятать во «вложенном» поле, которого нет в схеме.

```bash
python3 - <<'PY'
def rv(d, p):
    v=0; s=0
    while True:
        b=d[p]; p+=1; v|=(b&0x7f)<<s
        if not b&0x80: return v,p
        s+=7
d = open('msg.pb','rb').read()
p = 0
while p < len(d):
    tag,p = rv(d,p); field=tag>>3; wt=tag&7
    if wt==2:
        ln,p = rv(d,p); body=d[p:p+ln]; p+=ln
        print('field', field, 'body', body)
        # попробуем разобрать body как вложенное сообщение
        try:
            t2,q = rv(body,0)
            print('   nested field', t2>>3, 'wt', t2&7)
        except Exception:
            pass
    elif wt==0:
        v,p = rv(d,p); print('field', field, 'varint', v)
    else:
        break
PY
```

Map-поля кодируются как повторяющиеся вложенные сообщения с ключом и значением.
«Лишняя» пара ключ/значение — тоже канал.

## gRPC поверх HTTP/2

gRPC — это protobuf поверх HTTP/2. Каждый вызов — поток HTTP/2 с заголовками
`:method: POST`, `:path: /пакет.Сервис/Метод`, `content-type: application/grpc` и
кастомными `grpc-*` заголовками. Заголовки, оканчивающиеся на `-bin`, несут
base64-значения — произвольные байты. Это ещё один носитель помимо protobuf.

```bash
tshark -r capture.pcap -Y 'http2.headers' -T fields -e http2.header.name -e http2.header.value | head
```

## Итоговая стратегия для protobuf/gRPC

Разбери сообщение поле за полем (тег → тип → данные); для wire-type 2 проверь, не
вложенное ли это сообщение; ищи неизвестные номера полей; проверь `grpc-*`-заголовки
и `-bin`-метаданные. `protoc --decode_raw` ускоряет разбор без схемы. И помни: varint —
основа всего; ошибёшься в нём — «съедет» весь разбор.

## Практика: порядок и повтор полей

Protobuf не требует, чтобы поля шли в порядке номеров, и разрешает повторять поля
(для repeated-полей). Это два дополнительных канала:

- **Порядок полей** можно переставлять — получатель соберёт сообщение правильно.
- **Повтор одного поля** можно использовать как «лишние» значения.

```bash
python3 - <<'PY'
def rv(d,p):
    v=0;s=0
    while True:
        b=d[p];p+=1;v|=(b&0x7f)<<s
        if not b&0x80:return v,p
        s+=7
d = open('msg.pb','rb').read()
p=0; order=[]
while p<len(d):
    tag,p=rv(d,p); order.append(tag>>3)
    wt=tag&7
    if wt==2:
        ln,p=rv(d,p); p+=ln
    elif wt==0:
        _,p=rv(d,p)
    else:
        break
print('field order:', order)
PY
```

Если порядок «необычный» или поле повторяется — это может быть закладка.

## Как отличить закладку от реального API

В настоящем protobuf-трафике поля соответствуют схеме `.proto`. Признаки закладки:

- **Поле с номером вне схемы** (высокие номера, зарезервированные диапазоны).
- **Строка, декодируемая как ASCII/base64**, в бинарном поле.
- **Слишком длинное поле** для своего типа.
- **Лишние повторения** там, где repeated не ожидается.

Практический приём: если есть `.proto`-схема — сверь поля с ней; если нет — используй
`protoc --decode_raw` и ищи «неестественные» значения. Для gRPC дополнительно проверь
`-bin`-заголовки: они специально для произвольных байтов.

## Почему бинарные форматы не защищают данные

Есть распространённое заблуждение: «protobuf непонятен, значит данные защищены».
На деле формат полностью документирован, а `decode_raw` разбирает его без схемы.
Единственная «защита» — что аналитик не знает структуры. Как только структура
понята (тег, wire-type, varint), разбор занимает минуты. Именно поэтому стеганография
в protobuf — это не «спрятать в нечитаемом», а «положить в поле, которое не проверяют».

## Чек-лист по protobuf/gRPC

1. Разбери сообщение поле за полем: `тег → wire-type → данные`.
2. Для wire-type 0 читай varint; для 1/5 — фиксированные 4/8 байт; для 2 — длину и
   данные.
3. Для wire-type 2 проверь, не вложенное ли это сообщение (попробуй разобрать body).
4. Ищи неизвестные номера полей, необычные длины, текстовые данные.
5. Для gRPC проверь HTTP/2-заголовки и `-bin`-метаданные.
6. Используй `protoc --decode_raw`, если нет схемы.

Такой конвейер решает и CTF-задачу, и реальный разбор gRPC-трафика. Помни: varint —
основа формата, и ошибка в нём ломает весь дальнейший разбор.

## Ещё один носитель: длина сообщения gRPC

gRPC оборачивает каждое сообщение в 5-байтный префикс: 1 байт флага сжатия и 4 байта длины. Длина — открытая, и её младшие биты можно использовать как канал, если получатель знает схему. Это тот же принцип, что и во всех «полевых» форматах: служебное число, которое не проверяется на «нормальность».

## Заключительная мысль

Protobuf и gRPC — пример того, как удобство развития схемы (сохранение неизвестных полей) превращается в канал сокрытия. Получатель обязан игнорировать незнакомое, а значит, незнакомое можно добавлять. Для аналитика это означает: разбирай сообщение до конца, а не только «известные» поля — закладка живёт именно среди неизвестных.

## Что мы теперь знаем

- Protobuf-поле: `тег(varint) + данные`; тег = `(номер<<3)|wire_type`.
- Wire-type 2 — length-delimited (строка/байты).
- Varint: 7 бит на байт, старший бит = продолжение.
- Неизвестные поля, порядок, metadata HTTP/2 — каналы сокрытия.
- Инструменты: `protoc --decode_raw`, `tshark`, `grpcurl`.
