## Вопрос, с которого всё начинается

Ты открываешь файл — обычная картинка, всё в порядке. Но размер файла заметно больше, чем должен быть у такого изображения. Или тебе прямо сказали: «флаг в хвосте». Что это значит и как его достать?

Речь о самом частом виде файловой стеганографии — **дописанных данных** (appended data). Это когда после корректного конца файла дописан второй файл: архив, картинка, что угодно. В этом уроке мы разберём один такой файл и вытащим из него флаг.

## Наш пример: файл postcard.png

Возьмём конкретный файл `postcard.png`. Первым делом — что это за файл и сколько он весит.

```
$ file postcard.png
postcard.png: PNG image data, 200 x 200, 8-bit/color RGB, non-interlaced
$ ls -l postcard.png
-rw-r--r-- 1 analyst analyst 312480 postcard.png
```

Читаем: PNG 200×200, три канала (RGB). Несжатая такая картинка занимала бы 200×200×3 = 120 000 байт. Но файл весит 312 480 байт — почти втрое больше. А картинка на вид однотонная, значит, сжатие должно было сделать её совсем маленькой, в десятки килобайт. Откуда лишние 300 КБ?

Гипотеза: после конца PNG что-то дописано.

## Шаг 1: где «конец» картинки

Чтобы понять, где заканчивается изображение, нужно знать устройство PNG. PNG — это последовательность **чанков** (chunks): блоков, у каждого есть 4-байтная длина, 4-байтное имя и данные. Первый чанк всегда `IHDR` (заголовок изображения), последний — `IEND` (конец изображения). Всё, что лежит **после `IEND`**, уже не картинка.

Посмотрим на последние байты файла (`xxd` показывает hex и ASCII рядом):

```
$ xxd postcard.png | tail -3
0004c4c0: 0000 0000 4945 4e44 ae42 6082 504b 0304  ....IEND.B`.PK..
0004c4d0: 1400 0000 0800 0000 2126 3f6d 0a00 0000  ........!&?m....
0004c4e0: 666c 6167 2e74 7874 0500 0000 0000 0000  flag.txt........
```

Видим: `4945 4e44` — это `IEND`, конец PNG. А сразу за ним `504b 0304`. Байты `50 4B 03 04` — магические байты ZIP (`PK\x03\x04`). А ещё дальше прямо читается `flag.txt`. Загадка решена: после картинки дописан ZIP-архив.

## Шаг 2: ищем сигнатуры вручную

Полезно знать магические байты основных форматов — по ним файл узнаётся даже без расширения.

| Формат | Магические байты |
|---|---|
| ZIP | `50 4B 03 04` (`PK..`) |
| PNG | `89 50 4E 47` |
| JPEG | `FF D8 FF` |
| GIF | `47 49 46 38` (`GIF8`) |
| PDF | `25 50 44 46` (`%PDF`) |
| gzip | `1F 8B` |
| ELF | `7F 45 4C 46` |

Найдём смещение ZIP-сигнатуры через `grep`: `-a` — искать в бинарном файле, `-b` — печатать смещение, `-o` — выводить только совпадение.

```
$ grep -abo $'PK\x03\x04' postcard.png
312320:PK
```

Число 312320 — смещение, с которого начинается архив. Ровно там, где закончилась картинка.

## Шаг 3: binwalk делает это сам

`binwalk` — инструмент, который сканирует файл по десяткам сигнатур и сразу показывает смещения и типы встроенного.

```
$ binwalk postcard.png
DECIMAL       HEXADECIMAL     DESCRIPTION
0             0x0             PNG image, 200 x 200, 8-bit/color RGB, non-interlaced
312320        0x4C400         Zip archive data, at offset 0x4C400, name: flag.txt
```

Две записи: сама картинка и архив на смещении `0x4C400` (= 312320). `binwalk` даже подсказал, что внутри архива лежит `flag.txt`.

## Шаг 4: извлекаем данные

Самый предсказуемый способ — вырезать хвост начиная со смещения через `dd`. `bs=1` заставляет читать по одному байту, `skip` — пропустить столько байт от начала.

```
$ dd if=postcard.png of=hidden.zip bs=1 skip=312320
640+0 records in
640+0 records out
640 bytes copied
$ unzip -o hidden.zip
Archive:  hidden.zip
  inflating: flag.txt
$ cat flag.txt
flag{appended_zip}
```

Готово. Маршрут: заметили несоответствие размера → нашли сигнатуру → вырезали `dd` → распаковали.

Альтернатива `dd` — флаг `-e` у `binwalk`: он сам извлечёт всё найденное в папку рядом.

```
$ binwalk -e postcard.png
$ ls _postcard.png.extracted/
4C400.zip  flag.txt
```

## Шаг 5: почему это работает

Парсеры форматов читают файл по внутренней структуре. Просмотрщик PNG идёт от чанка к чанку и останавливается на `IEND`. А `unzip` ищет **центральный каталог** архива в конце файла (End of Central Directory, сигнатура `PK\x05\x06`). Каждый инструмент смотрит свою часть файла и не замечает «чужую». Поэтому один файл спокойно может быть сразу картинкой и архивом.

Важно знать «концы» популярных форматов: PNG — `IEND`, JPEG — `FF D9`, GIF — `3B`, PDF — последний `%%EOF`. Всё после них — кандидат на закладку.

## Где ещё прячут «лишнее»

Дописать файл можно не только в самый хвост:

- **slack space** — неиспользуемый остаток последнего кластера на диске (для образов дисков);
- **padding** — «пустые» байты между структурами внутри формата;
- **«мёртвые» поля** формата, которые парсер игнорирует.

Для образов дисков slack space извлекают инструментами Sleuth Kit:

```
$ blkls -s disk.img > slack.bin     # только slack-пространство
$ strings -n 8 slack.bin | grep -i flag
```

## Частые ловушки

- **Открыть и пересохранить файл** — редактор перезапишет картинку и уничтожит хвост. Работай только с копией оригинала.
- **Доверять расширению** — `.png` ничего не гарантирует; всегда проверяй `file`.
- **Не смотреть размер** — именно несоответствие размера и выдаёт закладку.
- **Забыть про склеенные архивы** — если два ZIP склеены (`cat a.zip b.zip`), внутри их несколько, а не один.

## Что мы теперь знаем

1. Дописанные данные — это файл после логического конца другого файла.
2. Признак закладки — размер больше ожидаемого.
3. Находят по сигнатурам (`grep -abo`, `binwalk`), извлекают `dd` или `binwalk -e`.
4. У каждого формата свой «конец»: PNG — `IEND`, JPEG — `FFD9`, GIF — `3B`, PDF — `%%EOF`.
5. Работает потому, что каждый парсер читает только «свою» часть файла.

## Шаг 6: проверяем конец файла программно

Глазами хвост смотреть удобно, но для больших файлов быстрее посчитать «ожидаемый» конец формата и сравнить его с фактическим размером. У PNG чанки идут подряд: 8 байт сигнатуры, затем каждый чанк = 4 байта длины + 4 байта типа + данные + 4 байта CRC. Суммируем — получаем, где должно закончиться изображение:

```python
import struct
raw = open('postcard.png', 'rb').read()
i = 8
while i < len(raw):
    ln = struct.unpack('>I', raw[i:i+4])[0]
    typ = raw[i+4:i+8]
    i += 12 + ln
    if typ == b'IEND':
        break
print('ожидаемый конец:', i, 'фактический размер:', len(raw), 'хвост:', len(raw) - i)
```

```
$ python3 check.py
ожидаемый конец: 312320 фактический размер: 312480 хвост: 160
```

160 «лишних» байт — вот и дописанный архив. Такой расчёт полезен, когда `binwalk` «переусердствует» и находит ложные сигнатуры: точная арифметика по чанкам сразу показывает настоящую границу.

Для остальных форматов конец ищут по маркеру:

| Формат | Маркер конца | Как найти |
|---|---|---|
| PNG | `IEND` | чанк после `IHDR` |
| JPEG | `FF D9` | последний `FFD9` |
| GIF | `3B` | трейлер |
| PDF | `%%EOF` | последний `%%EOF` |
| ZIP | EOCD (`PK\x05\x06`) | читается с конца |
| MP4 | конец `mdat` | после боксов |

Смещение маркера даёт `grep -abo`, например `grep -abo $'\xff\xd9' img.jpg | tail -1`.

## Шаг 7: ёмкость и сценарии применения

Дописанные данные дают **неограниченную ёмкость**: можно дописать файл любого размера. Поэтому канал используют, когда нужно спрятать большой payload — архив, второе изображение, исполняемый файл. Признак в задаче: файл-носитель «слишком большой» для своего содержимого. В CTF так прячут целые архивы с флагами, в реальных атаках — полезные нагрузки.

Инструменты carving стоит знать в лицо: `binwalk` (обзор по сигнатурам), `foremost` (carving по типам), `scalpel` (быстрый настраиваемый), `dd` (точное извлечение по смещению) и Sleuth Kit (`blkls`/`dls` для дисков). Комбинируй: `binwalk` — для обзора, `dd` — для точного извлечения.

## Практика: находим «хвост» программно

Ручной поиск сигнатур утомителен, поэтому напишем быстрый скрипт, который показывает всё,
что лежит после объявленного конца:

```
$ python3 - <<'EOF'
raw = open('postcard.png','rb').read()
iend = raw.rfind(b'IEND')
print('file size', len(raw), 'IEND at', iend)
tail = raw[iend+8:]          # 4 байта CRC + 4 байта длины после IEND
print('tail size', len(tail))
open('tail.bin','wb').write(tail)
EOF
file size 20480 IEND at 15392
tail size 5080
$ file tail.bin
tail.bin: Zip archive data
```

5 КБ «мусора» после `IEND` оказались вложенным ZIP — типовая задача.

## Практика: ёмкость и как её оценить

Сколько можно дописать в файл, не сломав его? Для PNG/JPEG — сколько угодно: парсеры
останавливаются на маркере конца. Для форматов с длиной (например, RIFF/WAV) дописывание
ломает файл, и данные нужно прятать внутри чанка. Оценка проста:

```
$ stat -c %s postcard.png
20480
$ python3 -c "print('payload bytes:', 20480-15392-8)"
payload bytes: 5080
```

Практическое правило: если `file` показывает один формат, а `binwalk` — несколько, у файла
есть «хвост».

## Сравнение с другими каналами

| Канал | Где живёт | Ломает ли файл | Инструмент |
|-------|-----------|----------------|------------|
| Append после EOI/IEND | хвост файла | нет | `binwalk`, `tail` |
| EXIF-комментарий | метаданные | нет | `exiftool` |
| LSB пикселей | данные изображения | нет | `zsteg` |
| RIFF-чанк | внутри структуры | нет | `xxd`/`ffmpeg` |

## Если не сработало

- **`file` показывает только PNG.** Хвост мог быть сжат или зашифрован — ищите по энтропии,
  а не по сигнатуре.
- **Файл «чистый».** Данные могли быть дописаны *до* начала и удалены из видимой части;
  сравните размеры с эталонным образцом.
- **Несколько IEND.** Валидный PNG содержит один `IEND`; лишний — маркер вложенных данных.

## Ограничение: валидаторы

Некоторые строгие валидаторы (например, проверка целостности в браузере) могут ругаться на
данные после конца. В реальных атаках «хвост» дописывают именно потому, что большинство
парсеров его игнорируют — но это не универсально.

## Куда дальше

В следующем уроке мы посмотрим на файлы, у которых **оба** формата «настоящие» — не дописанный хвост, а полноценный полиглот, который открывается и как картинка, и как архив. А пока запомни главное: сравни размер с ожидаемым, найди сигнатуру (`grep -abo`/`binwalk`) и вырежи хвост через `dd`.

## Где пригодится

- **CTF (Steganography/Forensics):** дописанные данные — одна из самых частых закладок после LSB.
- **Forensics:** carving файлов из дампов и образов дисков.
- **Malware-анализ:** поиск вложенных полезных нагрузок в «безобидных» файлах.
- **Blue team:** определение несоответствия заявленного формата и реального содержимого.
