## Вопрос, с которого всё начинается

В задаче дан `font.ttf` — шрифт, который используется в PDF. Ты открываешь PDF, читаешь текст — обычная статья, флага нет. Открываешь шрифт — видишь знакомые буквы. Как в шрифте может быть спрятано сообщение?

Ответ: шрифт — это тоже **контейнер**: файл содержит контуры глифов, метрики, кернинг и десятки таблиц, и каждый слой можно модулировать. Разберём это на нашем шрифте.

## Наш пример: font.ttf

**Шрифт** (TTF/OTF/WOFF) хранит форму каждой буквы (**глиф**) и правила её размещения. Всё это разбито на **таблицы**: `glyf` (контуры), `cmap` (какая буква какому глифу), `name` (имена), `kern`/`GPOS` (кернинг).

Дамп всех таблиц в XML одной командой:

```bash
$ ttx font.ttf
$ ls font.ttx
```

`ttx` из `fontTools` превращает шрифт в читаемый XML. Теперь можно смотреть каждый слой.

## Шаг 1: данные в таблице name

Скрытый текст часто лежит в метаданных шрифта:

```bash
$ ttx -t name font.ttf -o name.ttx
$ grep -iE 'flag|base64|copyright|version' name.ttx
<string>flag{font_name}</string>
```

Таблица **name** хранит copyright, версию, название — туда легко дописать строку, и её никто не проверяет.

## Шаг 2: контуры глифов

Если в `name` пусто — смотрим **координаты точек контуров**. Младший бит координаты — аналог LSB, но в векторной графике:

```python
from fontTools.ttLib import TTFont
f = TTFont("font.ttf")
glyf = f["glyf"]
bits = []
for gname in f.getGlyphOrder():
    g = glyf[gname]
    if g.isComposite():          # составной глиф ссылается на другие
        continue
    for x, y in g.coordinates:
        bits.append(x & 1)
bits = bits[: len(bits)//8*8]
msg = bytes(int("".join(map(str, bits[i:i+8])), 2)
            for i in range(0, len(bits), 8))
print(msg)
```

```bash
$ python3 glyf.py
b'flag{font_contour}'
```

Меняя младший бит координаты на единицу, форму буквы визуально не меняешь.

## Шаг 3: кернинг и GPOS

**Кернинг** — расстояние между конкретными парами символов. Продвинутый кернинг в OpenType живёт в таблице `GPOS`: пары `(глиф1, глиф2) → сдвиг`. Значения сдвига можно варьировать на доли единицы, кодируя биты.

```python
from fontTools.ttLib import TTFont
f = TTFont("font.ttf")
print(f.get("GPOS"))
```

## Шаг 4: кернинг в документах (fingerprinting)

На уровне документа (PDF, DOCX) кернинг и трекинг между парами символов варьируют на доли пункта — глаз не заметит, а парсер извлечёт биты. Это классический метод **отслеживания** документа: у каждого получателя свой узор, по утечке находят источник.

```bash
$ pdftotext -layout doc.pdf -      # позиции/пробелы могут выдать узор
$ mutool draw -F txt doc.pdf       # координаты глифов
```

В DOCX кернинг живёт в настройках run (`w:spacing`).

## Шаг 5: форматы и таблицы

- **TrueType (TTF)** — квадратичные кривые, таблицы `glyf`/`loca`;
- **OpenType (OTF)** — CFF или обёртка TrueType;
- **WOFF/WOFF2** — веб-шрифты, обычно сжатые.

Основные таблицы и каналы:

| Канал | Где | Ёмкость | Заметность |
|---|---|---|---|
| Контуры глифов | координаты | высокая | очень низкая |
| Таблица name | строки | низкая | низкая |
| Кастомная таблица | OTF | высокая | низкая |
| Кернинг | пары глифов | средняя | очень низкая |
| Порядок глифов | cmap/post | средняя | средняя |

## Сквозной разбор: реальный шрифт

Возьмём настоящий шрифт из системы — `DejaVuSerif-Bold.ttf` — и пройдём тот же маршрут, что и с `font.ttf`.

Сначала выгружаем таблицу `name` и смотрим, что в ней лежит:

```bash
$ ttx -t name -o name.ttx DejaVuSerif-Bold.ttf
Dumping "DejaVuSerif-Bold.ttf" to "name.ttx"...
Dumping 'name' table...
$ grep -A1 'nameID="5"\|nameID="6"' name.ttx
    <namerecord nameID="5" platformID="1" ...>
      Version 2.37
    <namerecord nameID="6" platformID="1" ...>
      DejaVuSerif-Bold
```

`nameID=5` — версия, `nameID=6` — PostScript-имя. Это ровно те поля, куда дописывают строку-метку: они попадают в документ, но не видны в тексте.

Теперь контуры. Посчитаем, сколько вообще есть точек — от этого зависит ёмкость канала:

```bash
$ python3 -c "from fontTools.ttLib import TTFont; f=TTFont('DejaVuSerif-Bold.ttf'); \
  g=f['glyf']; s=[n for n in f.getGlyphOrder() \
  if not g[n].isComposite() and g[n].numberOfContours>0]; \
  print(len(s),'glyphs,',sum(len(g[n].coordinates) for n in s),'points')"
1930 glyphs, 57985 points
```

Почти 58 тысяч координат — значит, младшие биты дают «полку» около 7 КБ. Проверим встраивание и извлечение на этом же шрифте:

```bash
$ python3 glyf_demo.py
embedded 18 bytes -> 144 low bits of glyph coordinates
extracted: b'flag{font_contour}'
```

Важная тонкость API: у простого глифа точки берутся из `g.coordinates`, но у пустого глифа (`numberOfContours == 0`) и у составного (`g.isComposite()`) этого поля нет — скрипт обязан их пропускать, иначе падает с `AttributeError`. В старых примерах встречается обращение напрямую к `g.coordinates` без проверки — на реальном шрифте это не сработает.

Встраивание 18 байт изменило 144 младших бита — это 0.25% всех точек. Ни форма букв, ни растеризация не меняются, `ots-sanitize` такой шрифт пропускает.

## Если не сработало

- **Смотришь только текст, не сам шрифт** — данные могут быть в контурах.
- **Игнорируешь `name`** — там чаще всего и лежит строка.
- **Забыл про кернинг документа** — он не виден в текстовом извлечении.
- **Ломаешь валидность** — грубая правка шрифта делает его нерабочим (`ots-sanitize`).
- **Пропускаешь составные глифы** — composite ссылаются на другие.
- **Не проверяешь несколько таблиц** — данные могут быть размазаны по слоям.

## Встраивание данных: практика

Мини-пример: спрятать байты в младших битах координат контура.

```python
from fontTools.ttLib import TTFont
f = TTFont("font.ttf")
glyf = f["glyf"]
secret = b"HI"
bits = "".join(f"{b:08b}" for b in secret)
i = 0
for gname in f.getGlyphOrder():
    g = glyf[gname]
    if g.isComposite():
        continue
    coords = list(g.coordinates)
    for k in range(len(coords)):
        x, y = coords[k]
        if i < len(bits):
            x = (x & ~1) | int(bits[i]); i += 1
            coords[k] = (x, y)
    g.coordinates = coords
f.save("stego.ttf")
```

Извлечение — обратная операция: собрать младшие биты в том же порядке.

## Инструменты

| Инструмент | Назначение |
|---|---|
| `ttx` | шрифт ↔ XML, все таблицы |
| `fontTools` | разбор/правка в Python |
| `FontForge` | визуальное редактирование |
| `ots-sanitize` | валидация шрифта |
| `mutool` | координаты глифов из PDF |
| `pdftotext -layout` | сохранение раскладки (кернинг) |

## Ограничения

- **Хрупкость**: правка контуров ломает хинтинг и растеризацию;
- **Валидация**: `ots-sanitize` отбросит некорректный шрифт;
- **Документы нормализуются**: при печати/конвертации кернинг теряется;
- **Размер**: большой объём данных требует много глифов.

## Что мы теперь знаем

1. Шрифт — контейнер из **таблиц**; каждая таблица — потенциальный канал.
2. **`name`** хранит метаданные — частый тайник.
3. **Контуры глифов** дают LSB-канал в координатах.
4. **Кернинг/GPOS** кодирует биты в сдвигах пар.
5. **Вёрстка документов** несёт водяные знаки (fingerprinting).
