## Вопрос, с которого всё начинается
Ты нашёл каталог `.git` или бэкап репозитория. В истории нет ничего секретного —
но в объектах Git может висеть **отсоединённый blob**: файл, который когда-то
добавили и удалили. Он не виден в `git log`, но лежит в `.git/objects` как
zlib-сжатый объект. Задача: достать его.

## Наш пример
Возьмём `blob.bin` — сырой Git-объект (как он лежит в `.git/objects/ab/cdef...`).
Разберём его формат и извлечём содержимое.

## Шаг 1: модель объектов Git
Git хранит всё как объекты четырёх типов: `blob` (файл), `tree` (каталог),
`commit`, `tag`. Объект — это строка заголовка `<тип> <длина>\0`, за которой идут
данные, всё вместе сжато zlib. Имя объекта — SHA-1 от **несжатого** содержимого.
Файл объекта лежит по пути `.git/objects/<первые2>/<остальные38>`.

## Шаг 2: формат blob
```
$ xxd -l 16 blob.bin
00000000: 789c 4b4c 4a06 00cb 3f01 8b05 0000 00    x.LJ...?.......
```

`78 9c` — заголовок zlib. Распакуем:

```python
import zlib
raw = zlib.decompress(open('blob.bin','rb').read())
print(raw)
```

Вывод:

```
b'blob 22\x00nto{git_dangling_blob}'
```

Заголовок `blob 22\0` сообщает тип и длину; дальше — содержимое.

## Шаг 3: где искать «висячие» объекты
- `git fsck --lost-found` — находит достижимые и висячие объекты.
- `git cat-file -p <sha>` — показать объект.
- `.git/logs/` (reflog) — история перемещений HEAD.
- `git stash list`, удалённые ветки — объекты остаются.

Даже после `git rm` и commit объект живёт, пока не собран `git gc`.

## Шаг 4: packfiles
В «упакованном» репозитории объекты лежат в `.git/objects/pack/*.pack` — с
дельтами и индексом `.idx`. Извлечь объект: `git verify-pack -v` + `git cat-file`,
или `git unpack-objects`. Формат pack сложнее, но принцип тот же.

## Шаг 5: стеганография в Git
- **Blob с мусором.** В объект можно дописать байты после полезного содержимого —
  Git их сохранит.
- **Сообщения коммитов.** Метаданные (author/committer, message) — произвольный
  текст, легко кодирует данные.
- **`.git/objects/info/alternates`** — путь к другому хранилищу.
- **`.gitattributes`/hooks** — служебные файлы.

## Полный разбор: висячий объект и восстановление

Git хранит данные как объекты: blob (содержимое файла), tree (каталог), commit, tag. Каждый объект адресуется SHA-1 (SHA-256 в новых репозиториях) от содержимого. «Висячие» (dangling) объекты — те, на которые не ссылается ни одна ветка/тег, но они остались в `.git/objects`. Именно там чаще всего прячут данные.

```bash
git fsck --lost-found            # найти dangling-объекты
git cat-file -p <sha>            # прочитать объект
git cat-file --batch-all-objects --batch-check | head
```

Практика: `git fsck` покажет `dangling blob <sha>`. Читаешь его `git cat-file -p` — и видишь содержимое (возможно, флаг). Если объектов много, перебирай все: `git cat-file --batch-all-objects --batch-check` даёт список, дальше фильтруй по типу `blob` и читай каждый.

## Packfiles: как распаковать и найти данные

Со временем объекты упаковываются в **packfile** (`.git/objects/pack/*.pack`) со сжатием дельт. Тогда «просто посмотреть файлы» не получится: нужно распаковать. `git verify-pack -v <pack>.idx` показывает объекты внутри, `git unpack-objects` разворачивает их обратно в loose-объекты.

```bash
ls .git/objects/pack/
git verify-pack -v .git/objects/pack/pack-*.idx | head
git unpack-objects < .git/objects/pack/pack-*.pack
```

В packfile также может лежать «мусор» — объекты, которые не нужны репозиторию, но физически присутствуют. Формат packfile: заголовок `PACK`, объекты (с дельта-сжатием), трейлер с SHA-1. Для глубокого разбора — `git verify-pack`, а при необходимости — парсер на Python (структура объекта описана в документации Git).

## Стеганография в Git и практика

Каналы в Git: (1) dangling-объекты; (2) данные в старых коммитах (история хранит всё, включая удалённые секреты); (3) данные в тегах/аннотациях; (4) `.git/config`, `hooks`, `refs`; (5) мусор в packfile; (6) данные в `.gitignore`/`.gitattributes` (необычные паттерны). Самый частый CTF-сценарий — репозиторий, в котором флаг лежит в объекте, недостижимом из текущей ветки.

```bash
git log --all --oneline
git reflog
git rev-list --objects --all | wc -l
```

Практика: начни с `git log --all` (все ветки), затем `git fsck --lost-found`, затем проверь packfile. Инструменты: `git`, `git-dumper` (для выкачивания `.git` с сайта), `gitfsck`-парсеры. Помни: удаление коммита не удаляет объект сразу — он остаётся до сборки мусора (`git gc`), и именно это окно используют для сокрытия данных.

## Расширенный разбор: форензика Git-репозитория

Полный маршрут по Git-репозиторию. Начни с истории: `git log --all --oneline`, `git reflog`, `git branch -a`. Затем — недостижимые объекты: `git fsck --lost-found` покажет `dangling blob/tree/commit`. Читай каждый `git cat-file -p <sha>`. Если объектов много, `git cat-file --batch-all-objects --batch-check` даёт список с типами и размерами — фильтруй по типу `blob` и размеру (крупные подозрительнее).

Дальше — packfile. Объекты могут быть упакованы в `.git/objects/pack/*.pack` со сжатием дельт. `git verify-pack -v <idx>` покажет объекты и их размеры; `git unpack-objects < <pack>` развернёт их в loose. В packfile может лежать мусор — объекты, недостижимые из refs, но физически присутствующие. Формат packfile: заголовок `PACK`, поток объектов (с дельта-сжатием), трейлер с SHA-1.

Отдельные каналы: `.git/config` (remote, hooks-пути), `.git/hooks/*` (скрипты), `.git/refs/*`, `.git/COMMIT_EDITMSG`, `.git/ORIG_HEAD`. Данные могут лежать и в коммит-сообщениях (`git log -p`), и в аннотациях тегов (`git tag -n99`).

Инструменты: `git`, `git-dumper` (выкачать `.git` с веб-сайта через открытые пути), `gitfsck`, `gitcat-file`, а при необходимости — парсер packfile на Python. Практика: удаление коммита не удаляет объект сразу — он остаётся до `git gc`, и это окно используется для сокрытия.

## Пошаговое упражнение с Git

Дано: каталог `.git` (или веб-сайт с открытым `.git`). Шаг первый — история: `git log --all --oneline`. Шаг второй — недостижимое: `git fsck --lost-found`. Шаг третий — чтение найденного: `git cat-file -p <sha>`. Шаг четвёртый — packfile: `git verify-pack -v .git/objects/pack/*.idx` и `git unpack-objects`.

```bash
git log --all --oneline
git fsck --lost-found
git cat-file --batch-all-objects --batch-check | grep blob | head
git cat-file -p <sha>
```

Если `.git` доступен по HTTP, но не целиком, используй `git-dumper <url> out/` — он соберёт репозиторий из открытых путей. Затем повтори шаги выше.

## Почему Git так удобен для сокрытия

Git хранит неизменяемые объекты по содержимому, и удаление ссылки не удаляет объект. Поэтому «удалённый» коммит или файл живёт в `.git/objects` до сборки мусора. Это делает Git естественным контейнером для сокрытия: данные выглядят как часть истории, но недостижимы из текущей ветки. Плюс packfile может содержать объекты, не связанные ни с одним ref.

Практический вывод: любой аудит Git-репозитория должен включать `git fsck` и разбор packfile, а не только `git log` текущей ветки. И наоборот, для атакующего это значит: перед публикацией репозитория убедись, что в истории и объектах нет секретов — удаление файла коммитом их не убирает.

## Расширенный практикум по Git

Сценарий первый: флаг в старом коммите. `git log --all -p` покажет диффы; если в истории был коммит с флагом, а потом его «убрали», флаг всё равно в объекте. Ищи по всем коммитам: `git log --all -S "nto{" --oneline` (поиск по добавлению/удалению строки).

Сценарий второй: флаг в packfile-мусоре. `git verify-pack -v <idx>` покажет все объекты, включая недостижимые. Если объект есть в pack, но не в `git log`, это мусор — читай его `git cat-file -p`.

Сценарий третий: флаг в refs. `find .git/refs -type f` и `.git/packed-refs` — иногда создают ref с именем, содержащим данные. Четвёртый: флаг в `.git/config` или hooks.

Пятый: флаг в объекте, замаскированном под обычный файл — например, blob с расширением `.txt`, но бинарным содержимым. Перебирай все blob по размеру.

Инструменты: `git`, `git-dumper`, `gitfsck`, `git-cat-file`. Ключевая мысль: Git хранит всё, и «удалённое» не исчезает мгновенно. Поэтому аудит всегда включает `git fsck` и разбор packfile, а не только `git log`.

## Итог и связь с VCS-форматами

Git — не единственная система контроля версий, но самая распространённая. Его модель «неизменяемые объекты по содержимому» означает, что данные практически не исчезают: удалённый коммит остаётся, пока не сработает сборка мусора. Это делает Git естественным каналом сокрытия.

Родственные системы (Mercurial, SVN) устроены иначе, но принцип «история хранит всё» сохраняется: удалённые версии файлов и метаданные остаются. Поэтому аудит любого репозитория включает проверку истории и «мусорных» объектов, а не только текущего дерева.

Для атакующего это напоминание: перед публикацией репозитория убедись, что в истории нет секретов. Удаление файла коммитом их не убирает; нужен `git filter-repo` или перезапись истории. И наоборот, для решателя CTF: `git fsck` и разбор packfile обязательны.

## Что мы теперь знаем
- Git-объекты — это zlib-сжатые `<тип> <длина>\0<данные>`.
- Удалённые файлы остаются как висячие blob до `git gc`.
- `git fsck --lost-found` и `git cat-file` — основные инструменты.
- Метаданные коммитов — дополнительный канал.
