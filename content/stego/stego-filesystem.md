## Вопрос, с которого всё начинается

В задаче дан `disk.dd` — образ диска. Ты монтируешь его, видишь пару обычных файлов, читаешь их — ничего. `strings` по образу даёт только обычный текст. Но флаг где-то на диске. Как спрятать данные так, что ни `ls`, ни проводник их не покажут?

Ответ: **между файлами**. Файловая система хранит данные не только в содержимом — остаются «щели»: файловый slack, неиспользуемые записи, скрытые потоки. Разберём это на нашем образе.

## Наш пример: disk.dd

**Файловая система** (ФС) — способ организовать данные на диске: она делит пространство на **кластеры** (блоки), ведёт таблицу «какой файл где лежит». Данные, которых нет в этой таблице, обычные средства не покажут. Сначала — образ и определение типа ФС:

```bash
$ fsstat disk.dd | head
File System Type: NTFS
```

`fsstat` из набора **sleuthkit** показывает структуру ФС. Всегда работай с **образом** (`dd`), а не с оригиналом — иначе можно безвозвратно изменить улики.

## Шаг 1: файловый slack

**Slack** — пространство между концом файла и концом последнего выделенного кластера. Файл размером 1 КБ занимает кластер 4 КБ — 3 КБ остаются «пустыми» и могут нести данные, невидимые для самого файла.

```bash
$ blkls -A disk.dd > unallocated.bin
$ foremost -i unallocated.bin -o out/
```

`blkls -A` извлекает **неразмеченное** пространство, `foremost` карвит из него файлы по сигнатурам. Затем ищем строки:

```bash
$ strings -n 8 unallocated.bin | grep -iE 'flag|base64'
```

## Шаг 2: ADS в NTFS

NTFS поддерживает несколько **потоков данных** на файл: основной `file.txt` и дополнительные `file.txt:secret`. Проводник и многие инструменты показывают только основной. **ADS** (Alternate Data Streams) — классическое место сокрытия в Windows.

```bash
$ ntfsls --streams disk.dd
file.txt  secret
$ ntfscat disk.dd -s secret file.txt
flag{ntfs_ads}
```

`ntfsls --streams` показывает потоки, `ntfscat -s secret` читает конкретный. Флаг найден в потоке, которого не видно в дереве файлов.

## Шаг 3: скрытые разделы и HPA/DCO

Данные могут лежать в разделах, которых нет в таблице разделов, либо в областях, скрытых самим накопителем (**HPA** — host-protected area, **DCO** — device configuration overlay).

```bash
$ mmls disk.dd                  # заявленная таблица разделов
$ testdisk disk.dd              # поиск потерянных разделов
$ fls -r -p disk.dd | head      # дерево файлов
```

## Шаг 4: журналы и временные метки

Современные ФС ведут **журналы** (ext4 journal, NTFS `$LogFile`), где могут остаться копии «удалённых» данных. А **временные метки** (MACB: Modify, Access, Change, Birth) хранят время с наносекундной точностью — их младшие разряды можно использовать как канал.

```bash
$ stat file.txt                 # наносекундная точность
$ debugfs -R "logdump -a" disk.img | head
```

```python
import os
st = os.stat("file.txt")
print(st.st_mtime_ns % 1000)    # младшие разряды — потенциальный канал
```

## Шаг 5: восстановление удалённых

Удаление файла в большинстве ФС не стирает содержимое — кластеры лишь помечаются свободными. Пока они не перезаписаны, данные восстановимы:

```bash
$ fls -d -r disk.dd | head      # удалённые записи
$ icat disk.dd <inode> > recovered.bin
```

## Шаг 6: чек-лист и инструменты

| Канал | Где | Обнаружение |
|---|---|---|
| File slack | конец кластера | `blkls`, карвинг |
| ADS | доп. потоки NTFS | `ntfsls --streams` |
| Скрытый раздел | вне таблицы | `testdisk`, `mmls` |
| HPA/DCO | скрыт накопителем | `hdparm`, `dcfldd` |
| Удалённые файлы | свободные кластеры | `fls -d`, `icat` |

Порядок для CTF: `fsstat` → `fls -r` → `ntfsls --streams` → `fls -d` → `blkls -A` + карвинг → `strings | grep`.

## Сквозной разбор: удалённый файл на ext4

Проверим восстановление на реальном образе. Соберём маленький ext4, положим файл, удалим его и попробуем достать обратно — ровно так выглядит задача «найди удалённое».

```bash
$ dd if=/dev/zero of=fs.img bs=1M count=8 status=none
$ mkfs.ext4 -q fs.img
$ printf 'flag{deleted_inode}\n' > secret.txt
$ debugfs -w -R "write secret.txt /secret.txt" fs.img   # пишем внутрь образа
$ debugfs -w -R "rm /secret.txt" fs.img                 # удаляем
```

Теперь смотрим, что видит sleuthkit. Живое дерево удалённый файл не показывает:

```bash
$ fls -r fs.img
d/d 11:	lost+found
r/r * 13:	secret.txt
V/V 2049:	$OrphanFiles
```

Звёздочка `*` перед номером inode означает «удалён». Запись сохранилась, потому что ФС лишь пометила inode свободным. Читаем содержимое по номеру inode напрямую:

```bash
$ icat fs.img 13
flag{deleted_inode}
```

`istat` подтверждает статус: `Not Allocated`, `num of links: 0` — данные по-прежнему на месте. И даже не заглядывая в дерево, их видно в неразмеченном пространстве:

```bash
$ blkls -A fs.img | wc -c
6699008
$ blkls -A fs.img | strings -n 6 | grep -i flag
flag{deleted_inode}
```

Вывод: пока кластеры не перезаписаны, «удалённое» читается и через inode (`icat`), и через карвинг неразмеченного (`blkls` + `strings`).

## Если не сработало

- **Ищешь только файлы** — данные живут в slack и неразмеченном пространстве.
- **Игнорируешь ADS на NTFS** — проводник их не показывает.
- **Считаешь таблицу разделов истиной** — бывают скрытые HPA/DCO.
- **Работаешь с оригиналом** — всегда делай образ (`dd`).
- **Забыл про несколько потоков** — их может быть много.
- **Путаешь slack с потерянными файлами** — это разные классы.

## Зарезервированные и служебные области

Помимо slack и ADS, есть загрузочная область (boot sector), `$MFT`-записи NTFS (неиспользуемые атрибуты), inode ext4 (неиспользуемые поля), superblock backup и переназначенные (bad) сектора.

```bash
$ istat disk.dd <inode>     # поля inode
$ fsstat disk.dd | head     # структура ФС
```

## Скрытые тома и правдоподобное отрицание

VeraCrypt/TrueCrypt позволяют создать **скрытый том** внутри свободного места внешнего. Снаружи он выглядит как случайные данные, и доказать его существование без пароля нельзя. Признаки: внешний том почти заполнен «случайными» байтами при малом объёме реальных файлов.

## Сравнение инструментов

| Задача | Инструмент |
|---|---|
| Образ диска | `dd`, `dcfldd`, `ddrescue` |
| Дерево файлов | `fls`, `ntfsls` |
| Неразмеченное | `blkls`, `bulk_extractor` |
| Метаданные узла | `istat`, `fls -l` |
| Карвинг | `foremost`, `scalpel` |
| Разделы | `mmls`, `testdisk` |

## Что мы теперь знаем

1. ФС хранит данные и **вне файлов**: slack, неразмеченное пространство, потоки.
2. **ADS** (NTFS) — дополнительный поток, невидимый для проводника.
3. Разделы бывают **скрытыми** (вне таблицы, HPA/DCO).
4. **Журналы** и **timestamps** — источники восстановимых данных.
5. Всегда работай с **образом**, а не оригиналом.
