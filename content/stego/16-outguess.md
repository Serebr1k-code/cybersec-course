## Вопрос, с которого всё начинается

У тебя есть JPEG, и ты почти уверен, что внутри что-то спрятано. Но `zsteg` молчит, `binwalk` чист, `strings` пусто. Остаются «парольные» инструменты — **steghide** и **OutGuess**. Они прячут данные в коэффициентах и требуют пароль. Как их применять и что делать, если пароль неизвестен?

Разберём на одном файле.

## Наш пример: cover.jpg

Сначала проверим, есть ли вообще данные. У `steghide` для этого есть команда `info`:

```
$ file cover.jpg
cover.jpg: JPEG image data, JFIF standard 1.01
$ steghide info cover.jpg
"cover.jpg": contains embedded data (size 0.1 KB)
```

`steghide info` отвечает: данные есть, размер 0.1 КБ. Теперь нужен пароль. Первое, что стоит попробовать, — **пустой пароль** (очень частая закладка):

```
$ steghide extract -sf cover.jpg -p ''
wrote extracted data to "flag.txt"
$ cat flag.txt
flag{steghide_empty_pass}
```

Готово. Если бы пароль был не пустой, перешли бы к `stegseek`:

```
$ stegseek cover.jpg rockyou.txt
[i] Found passphrase: "s3cr3t" -> wrote "flag.txt"
```

## Шаг 1: как работает steghide

`steghide` прячет данные в JPEG/BMP/WAV/AU. В JPEG он строит **пары взаимозаменяемых коэффициентов** — таких, между которыми разница незаметна, — и кодирует бит выбором одного из пары. Пароль задаёт порядок обхода через криптографическую функцию.

Важные следствия:

- без пароля данные не извлечь (пароль может быть пустым);
- `steghide info` может показать наличие и размер данных **без** пароля;
- PNG **не поддерживается** — это принципиально.

## Шаг 2: почему steghide не работает с PNG

`steghide` использует статистику DCT-коэффициентов (JPEG) и сэмплов (WAV/AU). У PNG нет ни того, ни другого в нужном виде: пиксели хранятся как значения каналов, сжатие без потерь. Для PNG применяют методы, рассчитанные на пиксели (`zsteg`, `stegsolve`).

Выбор инструмента диктуется форматом:

| Формат | Инструменты |
|---|---|
| PNG | `zsteg`, `stegsolve` |
| JPEG | `steghide`, `outguess`, `jsteg`, `stegseek` |
| WAV/AU | `steghide`, DeepSound |
| BMP | `steghide` |

## Шаг 3: OutGuess — статистически прозрачный метод

**OutGuess** (Нильс Провос) — исследовательский инструмент для JPEG. Версия 0.13 просто писала данные в младшие биты DCT-коэффициентов (пропуская 0 и ±1), а версия **0.2** делает качественный скачок: после встраивания она **корректирует остальные коэффициенты** так, чтобы гистограмма вернулась к естественному виду.

Именно поэтому OutGuess 0.2 классический хи-квадрат не ловит. Важнейшая идея: **стеганография может быть статистически прозрачной**, и «аномалий не нашли» не значит «данных нет».

```
$ outguess -r cover.jpg out.txt              # без ключа
$ outguess -k hunter2 -r cover.jpg out.txt   # с ключом
```

Если `outguess -r` даёт мусор, вероятны две причины: нужен ключ или данные встроены другим инструментом.

## Шаг 4: как определить, что контейнер — OutGuess, а не steghide

Прежде чем брутить, пойми, каким инструментом сделан контейнер:

- **steghide**: `steghide info` сразу отвечает «contains embedded data»;
- **OutGuess 0.2**: файл чуть больше ожидаемого, `stegdetect` может показать `outguess`;
- **JSteg/jphide**: `stegdetect` распознаёт по типу.

```
$ stegdetect -t jopi cover.jpg     # j=jsteg o=outguess p=jphide i=invisible
```

Если `stegdetect` говорит `outguess`, а `steghide info` — «no data», значит контейнер сделан OutGuess.

## Шаг 5: порядок действий

1. Определи формат (`file`).
2. `steghide info` — есть ли данные и сколько.
3. Попробуй пустой пароль, пароли из метаданных/условия/имени файла.
4. Если не вышло — `stegseek` с разумным словарём (не мега-листом).
5. Если это JPEG и `steghide` молчит — `outguess -r` (с ключом или без).
6. Ничего — `jsteg`/`jphide` и структурные каналы (`APP`/`COM`).

## Шаг 6: встраивание «наоборот» — для практики

Полезно уметь воспроизвести закладку, чтобы понимать её свойства:

```bash
$ echo "flag{test}" > s.txt
$ steghide embed -cf cover.jpg -ef s.txt -p pass123
$ steghide info cover.jpg
$ outguess -k pass123 -d s.txt -t cover.jpg stego.jpg
$ outguess -k pass123 -r stego.jpg out.txt
```

Практикуясь так, ты быстро начинаешь «чувствовать», какие изменения оставляет каждый инструмент.

## Ёмкость JPEG-методов

Ёмкость JPEG-методов мала по сравнению с PNG-LSB:

- **steghide**: ~1 бит на ненулевой коэффициент;
- **OutGuess 0.2**: ~1 бит на коэффициент, часть уходит на восстановление статистики;
- **F5**: матричное кодирование, эффективнее по числу изменений.

Поэтому в JPEG прячут флаги и ключи, а не архивы. Если задача ожидает большой payload в JPEG — вероятно, использован дописанный хвост или метаданные, а не DCT-метод.

## Если не сработало

- Не применяй `outguess`/`steghide` к PNG — не поддерживают.
- Не бруть, не проверив `steghide info` — тратишь время зря.
- Помни про пустой пароль — самая частая закладка.
- Не пересохраняй JPEG — данные погибнут.
- Пароль ищи в `exiftool`, `strings`, соседних артефактах.

## Что мы теперь знаем

1. steghide и OutGuess — «парольные» инструменты для JPEG (steghide ещё BMP/WAV/AU).
2. Без пароля/ключа извлечение невозможно; пароль может быть пустым.
3. OutGuess 0.2 статистически прозрачен — хи-квадрат его не ловит.
4. `steghide info` показывает данные без пароля.
5. Выбор инструмента диктуется форматом.

## Шаг 7: ёмкость JPEG-методов

Ёмкость JPEG-методов мала по сравнению с PNG-LSB:

- **steghide** — ~1 бит на ненулевой DCT-коэффициент;

- **OutGuess 0.2** — файл чуть больше ожидаемого, `stegdetect` может показать `outguess`;

## Шаг 9: почему steghide не работает с PNG

`steghide` использует статистику DCT-коэффициентов (JPEG) и сэмплов (WAV/AU). У PNG нет ни того, ни другого в нужном виде — пиксели хранятся как значения каналов, сжатие zlib без потерь. Поэтому для PNG применяют методы, рассчитанные на пиксели (`zsteg`, `stegsolve`). Это принципиальное различие форматов: lossy-носители (JPEG) прячут в коэффициентах, lossless (PNG) — в пикселях.

## Реальная сессия: steghide против outguess

Разберём перебор инструментов на одной картинке. Начинаем с `steghide` — он быстр и покрывает большинство CTF-контейнеров:

```bash
$ steghide info cover.jpg
"cover.jpg":
  format: jpeg
  capacity: 3.2 KB
  embedded file "flag.txt":   # -> данные точно есть
    size: 42.0 Byte
$ steghide extract -sf cover.jpg -p ''
```

Если `steghide info` говорит «не найдено данных», а задание явно про JPEG-стего, переходим к `outguess`:

```bash
$ outguess -r cover.jpg out.txt
Reading cover.jpg....
Extracting usable bits: ...
$ cat out.txt
flag{...}
```

Порядок перебора — от простого к сложному: `steghide` → `outguess` → `jsteg` → `jphide`/`jpseek` → ручной анализ DCT. Каждый инструмент встраивает данные по-своему, поэтому один не найдёт то, что спрятал другой.

## Ёмкость и артефакты

Ёмкость JPEG-методов зависит от размера картинки и коэффициента сжатия. Ориентир: `steghide` встраивает примерно **1 байт на 100 байт** файла; `outguess` — ещё меньше, потому что резервирует часть коэффициентов под «статистическую маскировку». Практически для картинки 500 КБ ожидайте 3–5 КБ полезной нагрузки. Важное следствие: если задание даёт маленький JPEG (10–20 КБ), объём флага должен быть крошечным — иначе данные физически не поместятся.

Артефакты, по которым определяют метод: `steghide` меняет часть DCT-коэффициентов и может оставить ненулевые «хвосты»; `outguess` стремится сохранить гистограмму и потому незаметнее для статистических детекторов (`stegdetect`). Именно поэтому в CTF, где стоит детектор, ожидайте `outguess`, а не `steghide`.

## Как отличить контейнеры на практике

| Признак | steghide | outguess |
|---------|----------|----------|
| Работает с | JPEG, BMP, WAV, AU | только JPEG |
| Пароль | обязателен (можно пустой) | нет |
| Ёмкость | ~1/100 файла | меньше |
| Детектируемость | выше | ниже |
| Тип команды | `extract -sf` | `-r` |

Если ни один инструмент не сработал, проверьте: файл действительно JPEG (не PNG с расширением `.jpg`), нет ли в файле **вложенного** архива (`binwalk`), и не спрятаны ли данные в **метаданных** (`exiftool`). Частая ошибка — гонять `steghide` по PNG: он с ним просто не работает.
