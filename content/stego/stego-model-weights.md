## Вопрос, с которого всё начинается

Тебе дали `model.safetensors` — файл с весами нейросети. Это просто набор чисел:
миллионы float, из которых состоит модель. Где тут спрятать сообщение? Оказывается,
у весов есть **заголовок с метаданными**, и он — текст. С него и начнём, а потом
посмотрим на сами числа.

## Наш пример: файл model.safetensors

```bash
xxd -l 96 model.safetensors
```

```text
00000000: 8000 0000 0000 0000 7b22 5f5f 6d65 7461  ........{"__meta
00000010: 6461 7461 5f5f 223a 7b22 666f 726d 6174  data__":{"format
00000020: 223a 2270 7422 2c22 666c 6167 223a 226e  ":"pt","flag":"n
00000030: 746f 7b73 3466 3374 336e 7330 7273 5f6d  to{s4f3t3ns0rs_m
```

Первые 8 байт — `80 00 ...` (little-endian `0x80` = 128) — длина JSON-заголовка.
Дальше 128 байт JSON, и в нём видно `"flag":"nto{...}"`. Разберём формат.

## Шаг 1: формат safetensors

**safetensors** — безопасный формат весов, придуманный Hugging Face. В отличие от
`pickle` (который может выполнить код при загрузке), safetensors — просто данные.
Структура:

```
[ 8 байт: длина заголовка N (u64, little-endian) ]
[ N байт: JSON-заголовок ]
[ остальное: сырые данные тензоров ]
```

JSON-заголовок описывает каждый тензор:

```json
{"weight":{"dtype":"F32","shape":[2],"data_offsets":[0,8]},
 "__metadata__":{"format":"pt","flag":"nto{...}"}}
```

Ключ **`__metadata__`** — произвольные метаданные (строки). Идеальное место закладки:
потребитель модели их не проверяет.

## Шаг 2: читаем заголовок вручную

```bash
python3 - <<'PY'
import struct, json
d = open('model.safetensors','rb').read()
n = struct.unpack('<Q', d[:8])[0]
hdr = json.loads(d[8:8+n])
print(json.dumps(hdr, indent=2, ensure_ascii=False))
PY
```

```text
{
  "__metadata__": {"format": "pt", "flag": "nto{s4f3t3ns0rs_m3t4_fl4g}"},
  "weight": {"dtype": "F32", "shape": [2], "data_offsets": [0, 8]}
}
```

Флаг достали из `__metadata__`. Это самый частый вариант задачи на safetensors.

## Шаг 3: где ещё прячут в весах

- **Младшие биты весов** — как LSB в изображении, только float. Меняешь последний бит
  мантиссы — модель работает так же.
- **«Лишние» тензоры** — тензор, который не используется при инференсе.
- **Паддинг в заголовке** — JSON выравнивают пробелами; пробелы можно заменить.
- **Порядок ключей** в JSON — перестановочный канал.
- **Точные значения `data_offsets`** — «щели» между тензорами.

## Шаг 4: другие форматы весов

- **GGUF** (llama.cpp) — набор KV-блоков: тип, ключ, значение. Метаданные в
  текстовых ключах, произвольные значения.
- **ONNX** — protobuf-файл: метаданные в `metadata_props`, а сам граф — protobuf.
- **PyTorch `.pt`/`.pth`** — обычно pickle; опасен и разбирается как pickle.
- **TF SavedModel** — набор файлов с `saved_model.pb` (protobuf).

Общий принцип: у каждого формата есть «метаданные», и они текстовые/произвольные.

## Шаг 5: инструменты

```bash
safetensors-view model.safetensors     # если установлен
python3 -c "from safetensors import safe_open; ..."
gguf-dump model.gguf                   # llama.cpp
onnxruntime / netron                   # визуализация
strings model.safetensors | grep nto
```

`strings` часто находит флаг сразу: метаданные — это текст. Для GGUF есть `gguf-dump`,
для ONNX — `netron`. Но ручной разбор заголовка надёжнее и не требует библиотек.

## Шаг 6: почему модели — удобный носитель

Веса — это огромный файл (гигабайты), который никто не проверяет побайтово. Изменение
нескольких младших бит весов не влияет на качество модели, но даёт мегабайты
скрытого места. Метаданные же легальны и не считаются аномалией. Получается канал,
который трудно обнаружить: чтобы найти закладку, нужно знать, что искать.

## Шаг 7: частые ошибки

Первая — считать safetensors pickle-файлом: это чистые данные, и это его смысл.
Вторая — неверно читать длину заголовка (u64 little-endian, а не big-endian).
Третья — забыть, что JSON выровнен пробелами (длина включает паддинг). Четвёртая —
искать только в данных, пропуская `__metadata__`.

## Практика: младшие биты весов

Метаданные — самый простой канал, но не единственный. Веса — это float32/float16, и
их младшие биты почти не влияют на модель. Изменив последний бит мантиссы, ты
поменяешь число на доли процента — качество не изменится, а биты поедут.

```bash
python3 - <<'PY'
import struct
d = open('model.safetensors','rb').read()
n = struct.unpack('<Q', d[:8])[0]
data = d[8+n:]
bits = []
for i in range(0, len(data)//4*4, 4):
    v = struct.unpack('<f', data[i:i+4])[0]
    u = struct.unpack('<I', data[i:i+4])[0]
    bits.append(u & 1)
print('first 16 weight LSBs:', bits[:16])
PY
```

Собрав младшие биты всех весов и сгруппировав по 8, можно прочитать сообщение — как
в LSB-стеганографии изображений, только носитель — тензор.

## GGUF и ONNX в деталях

**GGUF** (формат llama.cpp) состоит из KV-блоков:

```
[ тип(4) ][ ключ: len(8) + строка ][ значение ]
```

Ключи — текстовые (`general.name`, `llama.context_length`), значения — числа, строки,
массивы. Добавить «лишний» ключ с флагом просто: загрузчик его проигнорирует.

**ONNX** — protobuf-файл. В нём есть `metadata_props` — словарь строк. Флаг кладут
туда. Разбирается как protobuf (см. урок про gRPC/protobuf).

```bash
strings model.gguf | grep -iE 'nto|flag'
python3 -c "import onnx; m=onnx.load('m.onnx'); print(m.metadata_props)"
```

## Как отличить закладку в весах

Признаки: необычные ключи в `__metadata__`/`metadata_props`; строки, декодируемые как
ASCII/base64; «лишние» тензоры, не используемые графом; аномальный размер заголовка.
Практический приём — сравнить метаданные с типичными для модели того же семейства:
настоящие метаданные предсказуемы (`format`, `version`), закладка вносит «странное».
И помни: `strings` по файлу весов — быстрый способ найти текстовый флаг.

## Почему supply-chain моделей — новая граница

Модели скачивают с публичных хабов и запускают локально. Если в весах спрятана
закладка (или вредоносный код в pickle), она попадёт в твою инфраструктуру вместе с
моделью. Именно поэтому safetensors и был придуман: он не исполняет код при загрузке.
Но даже safetensors не защищает от **стеганографии**: младшие биты весов можно
изменить, и модель продолжит работать.

Для специалиста по безопасности это означает новый класс задач: проверять не только
«нет ли кода», но и «нет ли скрытых данных». Метаданные — первый подозреваемый,
младшие биты — второй. В CTF это отражается в задачах на файлы `*.safetensors`,
`*.gguf`, `*.onnx` с «лишними» полями.

## Практика: поиск вложенных файлов

Модель — большой файл, и в неё можно встроить целый архив. `binwalk` найдёт
сигнатуры вложенных данных:

```bash
binwalk model.safetensors
strings -n 6 model.safetensors | grep -iE 'nto|PK|flag'
```

Если внутри есть ZIP-архив (`PK\x03\x04`) или PNG (`\x89PNG`), `binwalk` это покажет.
Часто закладка — не «сообщение в метаданных», а целый вложенный файл с подсказкой.
Проверяй оба варианта: и текстовые метаданные, и вложенные бинарные данные.

## Чек-лист по весам модели

1. `xxd -l 64` — посмотри начало; определи формат (`safetensors`, `GGUF`, pickle).
2. Для safetensors — прочитай JSON-заголовок, проверь `__metadata__`.
3. `strings` по всему файлу — быстрый поиск текста.
4. `binwalk` — вложенные файлы.
5. Для GGUF — KV-блоки; для ONNX — `metadata_props`.
6. Младшие биты весов — если метаданные чисты.

Такой конвейер покрывает почти все CTF-задачи на весах моделей.

## Итоговая стратегия для весов модели

Определи формат по первым байтам (`{` после 8-байтной длины — safetensors; `GGUF` —
GGUF; `\x80\x02` — pickle). Для safetensors разбери JSON-заголовок и `__metadata__`.
Для GGUF пройди KV-блоки. Для ONNX разбери `metadata_props`. Затем `strings` и
`binwalk` по всему файлу. И только в конце — младшие биты весов. В девяти случаях из
десяти закладка лежит в метаданных или во вложенном файле, и лишь в десятом — в самих
числах. Помни: веса — это данные, а данные всегда можно переосмыслить как носитель.

## Замечание о float и о том, что «незаметно»

Почему изменение младшего бита float так трудно заметить? Float32 хранит число как
знак, экспоненту и 23-битную мантиссу. Младший бит мантиссы соответствует изменению
числа примерно в 2^-23 раз. Для веса порядка единицы это изменение порядка 0.0000001 —
намного меньше, чем разница, которую замечает обучение. Именно поэтому такие закладки
не ломают модель и остаются незамеченными. Единственный способ их найти — статистика
или знание, что искать. В CTF это отражается в задачах, где «модель работает, но
внутри что-то есть» — и решение в разборе метаданных или младших битов.

## Ещё одна мысль

Проверять модели на стеганографию стоит и в реальной работе: модель из ненадёжного источника может нести не только вредоносный код (pickle), но и скрытые данные. Полная проверка включает метаданные, `strings`, `binwalk` и, при необходимости, статистический анализ весов. В CTF же чаще всего достаточно первых трёх шагов.

## Итог

Веса моделей — это гигабайты чисел плюс метаданные. Метаданные легальны и текстовы, поэтому закладка в них находится за секунды; младшие биты весов — второй, более тонкий канал. Разбор начинается с формата файла и заголовка, а заканчивается статистикой только тогда, когда всё остальное чисто.

## Что мы теперь знаем

- safetensors: `[8 байт длины][JSON][данные]`; метаданные в `__metadata__`.
- GGUF, ONNX, pickle — другие форматы весов со своими метаданными.
- Каналы: метаданные, младшие биты весов, «лишние» тензоры, порядок ключей.
- Инструменты: `safetensors`, `gguf-dump`, `netron`, `strings`.
