## Вопрос, с которого всё начинается

У тебя есть `pic.webp` — современный формат, который сегодня отдают почти все сайты. Внешне обычная картинка. Но где в ней вообще можно что-то спрятать, если это не PNG?

WebP устроен как **контейнер**: внутри него лежат блоки с разными данными — сжатое изображение, прозрачность, метаданные. И в каждом из них может быть секрет. Разберём `pic.webp` от начала до конца.

## Наш пример: файл pic.webp

Смотрим тип:

```bash
exiftool pic.webp | grep -iE 'file type|width|height'
```

```text
File Type                       : Extended WEBP
File Type Extension             : webp
Image Width                     : 48
Image Height                    : 48
```

**Extended WEBP** — это WebP с дополнительными блоками (метаданные, прозрачность). Значит, есть куда смотреть.

## Шаг 1: RIFF-контейнер

WebP построен на формате **RIFF** — том же принципе, что и WAV из аудио-уроков. Файл начинается с сигнатуры `RIFF`, затем идёт общий размер, затем метка `WEBP`, а дальше — последовательность **чанков** (блоков). Каждый чанк: 4 байта имени, 4 байта размера, данные (при необходимости с выравниванием до чётного размера).

Разбираем чанки вручную:

```python
import struct
d = open('pic.webp', 'rb').read()
print('RIFF sig:', d[:4], 'WEBP:', d[8:12], 'size:', struct.unpack('<I', d[4:8])[0])
off = 12
while off < len(d):
    fourcc = d[off:off+4].decode('latin1')
    sz = struct.unpack('<I', d[off+4:off+8])[0]
    print(f'{fourcc} size={sz}')
    off += 8 + sz + (sz & 1)          # +1, если размер нечётный (выравнивание)
```

```text
RIFF sig: b'RIFF' WEBP: b'WEBP' size: 1952
VP8X size=10
VP8  size=1864
EXIF size=50
```

Три чанка: `VP8X` (заголовок расширенного WebP), `VP8` (сжатое изображение) и `EXIF` (метаданные). Последний — сразу подозрителен.

## Шаг 2: читаем метаданные

Чанк `EXIF` хранит метаданные в том же формате, что и JPEG. Читаем их:

```bash
exiftool pic.webp
```

```text
Image Width                     : 48
Image Height                    : 48
Image Description               : flag{w3bp_r1ff_chunk5}
```

Флаг найден прямо в описании изображения. Это самый частый случай в CTF на WebP: секрет лежит в метаданных, а не в пикселях.

## Шаг 3: какие бывают чанки WebP

Полезно знать типы чанков:

- **`VP8 `** — сжатие с потерями (как JPEG).
- **`VP8L`** — сжатие без потерь (как PNG).
- **`VP8X`** — расширенный заголовок (появляется, когда есть метаданные/прозрачность).
- **`ALPH`** — прозрачность.
- **`ICCP`** — цветовой профиль.
- **`EXIF`**, **`XMP `** — метаданные.

Данные прячут в любом из них: в `EXIF`/`XMP` — как текст, в `VP8L` — в пикселях, а в `ALPH` — как в альфа-канале PNG (`stego-alpha`).

## Шаг 4: VP8L и LSB

Если метаданные чисты, смотрим `VP8L` — режим без потерь. В нём пиксели хранятся близко к исходным, поэтому LSB-стеганография работает. Проблема в том, что `VP8L` использует собственное сжатие, и просто «взять младшие биты» из файла нельзя — сначала нужно декодировать изображение в обычные пиксели (это делает PIL или `dwebp`), а уже потом извлекать биты:

```bash
# распаковать WebP в PNG, затем работать как с PNG
dwebp pic.webp -o pic.png
```

После этого применяем скрипты из уроков про LSB и бит-плоскости.

## Шаг 5: инструменты

Для WebP удобны: **`webpinfo`** (показывает чанки и их размеры), **`dwebp`** (декодирует в PNG), **`exiftool`** (метаданные). Общий инструмент **`binwalk`** находит встроенные файлы — если внутри WebP лежит ZIP или ещё одна картинка, `binwalk` это покажет:

```bash
binwalk pic.webp
```

## Выравнивание RIFF и скрытые хвосты

RIFF требует, чтобы каждый чанк начинался с **чётного** смещения. Если размер данных нечётный, после них добавляется один байт-заполнитель (padding), который не учитывается в размере. В нашем скрипте это `+ (sz & 1)`: если размер нечётный, `sz & 1` равен 1, и мы пропускаем лишний байт. Забыть про выравнивание — классическая ошибка: тогда все последующие чанки «съезжают», и вы видите мусор вместо имён.

Само выравнивание — тоже щель для стего. Байт-заполнитель формально должен быть нулём, но никто его не проверяет. Поэтому туда можно записать данные, и парсеры их проигнорируют. Если в WebP много чанков с нечётными размерами, посмотрите на байты-заполнители — иногда там спрятан текст.

Отдельный случай — **данные после последнего чанка**. Как и в PNG, декодер читает чанки по их размерам и доходит до конца; всё, что дописано после, он просто не замечает. Проверяйте, совпадает ли общий размер RIFF с реальной длиной файла: расхождение означает хвост с секретом.

## WebP без потерь и тонкости метаданных

Режим **`VP8L`** (без потерь) хранит пиксели точнее, поэтому в нём возможны LSB-данные. Но есть нюанс: `VP8L` использует предсказание и палитру, поэтому «сырые» байты потока не соответствуют пикселям один в один. Единственный надёжный путь — декодировать изображение в обычные пиксели (через `dwebp` или PIL) и работать с ними, как с PNG.

Метаданные тоже хитрят. Чанк `EXIF` может содержать **несколько** полей, и секрет бывает не в описании, а в необычном поле вроде «Software» или в пользовательском теге. А `XMP ` — это XML, куда можно записать произвольную строку. Иногда метаданные **сжаты** (в `XMP` с флагом сжатия), и тогда их нужно распаковать перед чтением.

Наконец, помните про **конвертацию**: пересохранение WebP в JPEG уничтожит и `ALPH`, и часть метаданных. Работайте с оригиналом.

## Полный прогон: от файла к флагу

```text
pic.webp
  → exiftool → Extended WEBP
  → разбор RIFF-чанков → VP8X, VP8, EXIF
  → EXIF → flag{w3bp_r1ff_chunk5}
  → при пустых метаданных — dwebp → PNG → LSB
  → итог: данные в EXIF-чанке
```

## Если не сработало

- **Метаданные пусты** — декодируйте в PNG (`dwebp`) и проверьте LSB и бит-плоскости.
- **Есть чанк `XMP `** — там может быть развёрнутый XML с секретом.
- **Подозрительный `ALPH`** — извлекайте как альфа-канал.
- **Внутри что-то ещё** — прогоните `binwalk`: возможно, в WebP встроен архив или файл.

## Что мы теперь знаем

- **WebP** — это **RIFF-контейнер** с чанками.
- Чанки: `VP8` (с потерями), `VP8L` (без потерь), `VP8X`, `ALPH`, `EXIF`, `XMP`.
- Метаданные в `EXIF`/`XMP` — первый подозреваемый.
- Для LSB в `VP8L` сначала декодируем в PNG.
- **`dwebp`**, `webpinfo`, `exiftool`, `binwalk` — основные инструменты.
- Принципы RIFF те же, что в WAV.
- **Байты-заполнители** (padding) и данные после последнего чанка — тоже скрытые каналы.
