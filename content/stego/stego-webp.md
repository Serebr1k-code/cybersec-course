WebP — формат Google, который браузеры отдают по умолчанию вместо JPEG/PNG, поэтому он всё чаще попадается в веб-CTF и при анализе кэшей. С точки зрения стеганографии это прежде всего **RIFF-контейнер**: внутри лежит последовательность чанков, и «лишние» чанки — `EXIF`, `XMP `, `ICCP`, `ALPH` — регулярно несут скрытые данные. Дополнительный бонус: WebP существует в лосслесс-режиме (VP8L), где LSB-приёмы работают так же, как в PNG.

## Структура RIFF

WebP начинается с 12-байтного RIFF-заголовка, затем идут чанки. Каждый чанк — это 4-байтный FourCC, 4-байтная длина (little-endian) и данные с выравниванием до чётного размера (pad-байт `\x00` при нечётной длине).

| Смещение | Поле | Размер | Значение |
|---|---|---|---|
| 0x00 | `RIFF` | 4 | сигнатура контейнера |
| 0x04 | size | 4 | размер всего файла минус 8 |
| 0x08 | `WEBP` | 4 | тип RIFF |
| 0x0C | chunk FourCC | 4 | `VP8 `, `VP8L`, `VP8X`, `ALPH`, `EXIF`, `XMP `, `ICCP` |
| 0x10 | chunk size | 4 | длина данных чанка |
| 0x14 | chunk data | var | полезная нагрузка (+ pad) |

```bash
# базовая идентификация
file image.webp
xxd image.webp | head -4
# вывод:
# 00000000: 5249 4646 3a01 0000 5745 4250 5650 3858  RIFF:...WEBPVP8X
# 00000010: 0a00 0000 0000 0000 0000 0000            ............

# перечислить все RIFF-чанки (WebP-специфичный парсер)
webpinfo -summary image.webp
webpinfo -diag image.webp          # диагностика: перечислит все чанки
```

`webpinfo` (пакет `webp`) — главный инструмент: `-summary` даёт сводку по чанкам, `-diag` — полный список. Если его нет, чанки прекрасно видны в `xxd` или `strings`.

## VP8 vs VP8L vs VP8X

Первый чанк после `WEBP` определяет тип:

- **`VP8 ` (с пробелом)** — lossy (сжатие с потерями, как VP8-видео).
- **`VP8L`** — lossless; пиксели упакованы энтропийно, но при распаковке дают точные значения — LSB здесь работает.
- **`VP8X`** — расширенный контейнер; за ним следуют `ALPH` (альфа-канал), `ICCP`, `EXIF`, `XMP ` и уже потом `VP8 `/`VP8L`. Именно здесь чаще всего живут «лишние» чанки.

```bash
# определить подтип
xxd image.webp | head -2 | grep -o 'VP8[ LX]'
# VP8L -> lossless, можно применять LSB
# VP8  -> lossy, смотри метаданные и структуру, а не младшие биты
```

## Скрытые каналы в WebP

- **`EXIF` / `XMP ` чанки:** контейнер-в-контейнере. Достань чанк и прогони через `exiftool` — там могут быть комментарии, GPS, а иногда прямо флаг.
- **`ICCP`:** ICC-профиль — большой блок, в хвосте которого удобно дописать данные.
- **`ALPH`:** альфа-канал как отдельный носитель — стеганография в прозрачности.
- **Pad-байты:** выравнивание до чётного размера — до 1 байта мусора на чанк, редко, но встречается.
- **Хвост файла после последнего чанка:** дописанные данные (как в PNG `IEND`).
- **VP8L lossless:** классический LSB в распакованных пикселях.

```bash
# извлечь EXIF-чанк и прочитать его exiftool-ом
python3 - <<'PY'
import struct
d=open('image.webp','rb').read()
i=12
while i+8<=len(d):
    fourcc=d[i:i+4].decode('latin1'); size=struct.unpack('<I',d[i+4:i+8])[0]
    print(fourcc, size, 'at', hex(i))
    if fourcc in ('EXIF','XMP '):
        open(f'chunk_{fourcc.strip()}.bin','wb').write(d[i+8:i+8+size])
    i += 8 + size + (size & 1)   # pad до чётного
PY
exiftool chunk_EXIF.bin
```

## Разобранный пример

CTF-задача: файл `challenge.webp`, на вид — обычная картинка.

```bash
$ file challenge.webp
challenge.webp: RIFF (little-endian) data, Web/P image

$ webpinfo -summary challenge.webp
Chunk VP8X at offset 12, length 10
Chunk ALPH at offset 30, length 1024
Chunk VP8  at offset 1062, length 4096
Chunk EXIF at offset 5166, length 128

$ python3 - <<'PY'
import struct
d=open('challenge.webp','rb').read()
i=12
while i+8<=len(d):
    fc=d[i:i+4].decode('latin1'); sz=struct.unpack('<I',d[i+4:i+8])[0]
    if fc=='EXIF':
        print(d[i+8:i+8+sz].decode('latin1',errors='replace'))
    i+=8+sz+(sz&1)
PY
flag{webp_chunks_are_not_invisible}
```

Флаг лежал прямо в `EXIF`-чанке. Если бы его там не было, следующий шаг — распаковать `VP8L` в пиксели и применить LSB.

```bash
# конвертация WebP -> PNG для дальнейшего LSB-анализа
dwebp challenge.webp -o challenge.png
zsteg challenge.png
# или напрямую через Pillow
python3 -c "from PIL import Image; Image.open('challenge.webp').convert('RGBA').save('ch.png')"
```

## Краевые случаи и подводные камни

- **`VP8 ` (lossy) не даёт чистый LSB:** артефакты сжатия разрушают младшие биты; ищи данные в метаданных, а не в пикселях.
- **Регистр и пробелы в FourCC:** `VP8 ` с пробелом, `XMP ` тоже с пробелом — парсеры, завязанные на точное сравнение, легко пропустить.
- **Выравнивание:** не забывай pad-байт при нечётной длине, иначе поедешь по всему файлу.
- **Анимированный WebP:** ANIM/ANMF-чанки — кадры; смотри их как GIF-кадры.
- **Двойное расширение:** файл может быть `.png` с WebP-содержимым — всегда проверяй `file`, а не имя.

## Что дальше / решение

Базовый пайплайн для WebP: `file` → `webpinfo -summary` → перебрать чанки скриптом → `exiftool` по `EXIF`/`XMP ` → конвертировать в PNG (`dwebp`/Pillow) и применить `zsteg`/StegSolve. Если задача «пустая», проверь хвост после последнего чанка и анимированный режим. Всё это — тот же навык, что и для PNG: читать контейнер, а не доверять расширению.

## Справочные таблицы

| Чанк | Назначение | Интерес для стего |
|---|---|---|
| `VP8 ` | lossy-изображение | низкий (артефакты) |
| `VP8L` | lossless-изображение | высокий (LSB в пикселях) |
| `VP8X` | расширенный контейнер | индикатор доп. чанков |
| `ALPH` | альфа-канал | высокий (стего в прозрачности) |
| `ICCP` | ICC-профиль | средний (хвост блока) |
| `EXIF` | метаданные | высокий (комментарии/флаг) |
| `XMP ` | метаданные XMP | высокий (текст) |
| `ANIM`/`ANMF` | анимация | средний (кадры) |

## Анимированный WebP: ANIM и ANMF

Анимированный WebP хранит кадры в чанках `ANIM` (глобальные параметры: фон, число циклов) и `ANMF` (по одному на кадр: смещение, размер, длительность, blob с данными кадра). Для стеганографии это значит, что перед вами фактически GIF-подобная структура: данные могут лежать в отдельном кадре, в поле длительности кадра или в неиспользуемых байтах блоба кадра.

- `ANIM` содержит background color и loop count — редко, но используют как канал.
- `ANMF` содержит `x`, `y`, `width`, `height`, `duration`, `blending`, `disposal` и вложенный `VP8 `/`VP8L`.
- Каждый кадр — отдельное изображение; прогоняйте их по отдельности.

```bash
# разобрать анимированный WebP на кадры
anim_dump -folder out anim.webp 2>/dev/null || true
# универсальный путь через ffmpeg
ffmpeg -i anim.webp frame_%04d.png
zsteg frame_*.png
```

Тайминги кадров (`duration`) — тоже канал: аномальные значения (нулевые или огромные) часто кодируют биты. Сравните распределение `duration` со «здоровым» файлом того же размера.

## Сравнение с PNG и JPEG: где быстрее результат

| Признак | WebP | PNG | JPEG |
|---|---|---|---|
| Контейнер | RIFF | чанки | маркеры |
| Метаданные | EXIF/XMP-чанки | tEXt/zTXt | APP1 |
| LSB в пикселях | в VP8L | да | нет |
| Быстрый первый шаг | webpinfo | zsteg | exiftool |

Практический вывод: для WebP первый шаг — `webpinfo -summary`, затем разбор чанков, затем (если `VP8L`) LSB. Для JPEG сразу метаданные и DCT, LSB не трогаем. Для PNG — `zsteg` почти всегда первым.

## Автоматизация: скрипт полного разбора

```python
import struct
def riff_chunks(path):
    d=open(path,'rb').read(); i=12; out=[]
    while i+8<=len(d):
        fc=d[i:i+4].decode('latin1'); sz=struct.unpack('<I',d[i+4:i+8])[0]
        out.append((fc,sz,i)); i+=8+sz+(sz&1)
    return out
for fc,sz,off in riff_chunks('image.webp'):
    print(repr(fc), 'size', sz, 'offset', hex(off))
```

Скрипт печатает карту чанков, по которой видно, есть ли «лишние» (`EXIF`/`XMP `/`ICCP`) и где они. Дальше извлеките их и прогоните через `exiftool`/`strings`. Автоматизация экономит время, когда файлов много.

## Краевые случаи, которых нет в базовом разборе

- **Файл `.webp`, который на самом деле PNG:** проверяйте `file`, а не расширение.
- **Обрезанный RIFF:** поле `size` в заголовке может не совпадать с фактической длиной — доверяйте концу файла.
- **Вложенный EXIF в анимированном WebP:** чанк метаданных может стоять после кадров, а не перед ними.
- **Несколько `ICCP`:** редкий, но валидный случай; проверяйте все, а не первый.

## Хвост файла и перепаковка

У WebP, как и у PNG, после последнего валидного чанка может остаться «хвост» — байты, которые не описаны ни одним чанком. Многие просмотрщики игнорируют их, а данные там живут спокойно. Проверяйте разницу между суммой чанков и реальным размером файла.

```bash
python3 - <<'PY'
import struct
d=open('image.webp','rb').read(); i=12; end=12
while i+8<=len(d):
    fc=d[i:i+4].decode('latin1'); sz=struct.unpack('<I',d[i+4:i+8])[0]
    end=i+8+sz+(sz&1); i=end
print('declared end', end, 'file size', len(d), 'tail', len(d)-end)
print(d[end:end+64])
PY
```

Если `tail` > 0 — вытащите хвост (`dd`/срез) и проверьте на архивы/строки. Второй приём — «перепаковка»: файл могли прогнать через `cwebp`, и старые метаданные исчезли, но новый чанк `EXIF` мог появиться. Сравнивайте набор чанков с эталоном: лишний чанк — повод копать.
