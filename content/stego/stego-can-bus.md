## Вопрос, с которого всё начинается

Тебе дали `candump.log` — лог CAN-шины автомобиля. CAN — это сеть, по которой блоки
управления (двигатель, тормоза, кузов) обмениваются короткими сообщениями. Каждый
кадр — максимум 8 байт данных. Где тут спрятать сообщение? Оказывается, можно
растянуть его на несколько кадров, а можно использовать ID или тайминги. Разберём лог.

## Наш пример: файл candump.log

```bash
cat candump.log
```

```text
(1710000000.000000) can0 123#6e746f7b63616e5f
(1710000000.010000) can0 123#6275735f63307633
(1710000000.020000) can0 123#72747d
```

Формат `candump`: время, интерфейс, `ID#ДАННЫЕ`. Если декодировать hex-данные:

```bash
python3 - <<'PY'
for line in open('candump.log'):
    data = line.split('#')[1].strip()
    print(bytes.fromhex(data).decode('latin-1'), end='')
print()
PY
```

```text
nto{can_bus_c0v3rt}
```

Сообщение растянуто на три кадра. Это классика CAN-стеганографии.

## Шаг 1: как устроен CAN

CAN (Controller Area Network) — шина с **арбитражом**: узлы «соревнуются» за доступ,
и побеждает тот, у кого ID меньше (логический ноль доминирует). Кадр содержит:

- **ID** — 11 бит (стандарт) или 29 бит (расширенный). Это не адрес, а приоритет +
  идентификатор сообщения.
- **DLC** — сколько байт данных (0..8).
- **Data** — до 8 байт полезной нагрузки.
- **CRC** — контрольная сумма.

Именно эти 8 байт — основное место для данных. Но и ID, и тайминги подходят.

## Шаг 2: почему CAN удобен для сокрытия

CAN-кадры короткие и передаются постоянно. Получатель (блок управления) реагирует
только на «свои» ID. Значит:

- Кадры с «неиспользуемым» ID можно заполнять произвольными данными — никто на них
  не смотрит.
- Данные «своего» сообщения можно размазать по младшим битам, сохраняя смысл.
- Интервалы между кадрами (тайминг) можно модулировать.

## Шаг 3: разбираем лог вручную

```bash
python3 - <<'PY'
import re
data = {}
for line in open('candump.log'):
    m = re.search(r'(\w+)#([0-9A-Fa-f]+)', line)
    if not m:
        continue
    cid, hexd = m.group(1), m.group(2)
    data.setdefault(cid, bytearray()).extend(bytes.fromhex(hexd))
for cid, b in data.items():
    print(cid, b)
PY
```

```text
123 bytearray(b'nto{can_bus_c0v3rt}')
```

Мы собрали данные всех кадров одного ID подряд. Так работают почти все задачи на
CAN-логи.

## Шаг 4: где ещё прячут в CAN

- **Младшие биты данных** — при сохранении «правдоподобных» значений.
- **ID кадра** — перестановочный/числовой канал.
- **DLC** — заявленная длина может не совпадать с реальной.
- **Тайминги** — интервалы между кадрами кодируют биты.
- **«Лишние» кадры** — кадры, которые блоки управления игнорируют.

## Шаг 5: инструменты

```bash
candump can0                      # чтение шины в реальном времени
can-utils                         # candump/cansend/cangen
canbusload can0@500000            # загрузка шины
python-can                        # библиотека для скриптов
```

`can-utils` — стандартный набор для Linux. В CTF чаще дают готовый лог (`candump`
вывод), и разбор идёт обычным `grep`/Python. `python-can` умеет читать разные форматы
логов.

## Шаг 6: почему CAN — «физический» канал

CAN — это не файл, а сигнал на двух проводах. Но лог `candump` — это уже текст, и
разбирать его просто. Разница с файловыми форматами лишь в том, что «кадр» короткий
и закладку приходится растягивать. Это заставляет думать о таймингах и о том, какие
ID «свободны».

## Шаг 7: частые ошибки

Первая — декодировать только первый кадр: сообщение растянуто, надо собрать все.
Вторая — путать hex и ASCII: данные в candump — hex-строка. Третья — не учитывать,
что у разных ID разные данные, и смешивать их нельзя. Четвёртая — забывать про
расширенный формат (29-битные ID), где длина ID-поля другая.

## CAN FD и расширенные идентификаторы

Классический CAN несёт до 8 байт данных. Современный **CAN FD** (Flexible Data-rate)
позволяет до 64 байт и переменную скорость передачи данных. Для стеганографии это
означает: больше места в одном кадре, но и больше полей, которые можно модулировать.

Кроме того, ID бывает **стандартным (11 бит)** и **расширенным (29 бит)**. В логах
`candump` расширенный ID помечается иначе, и длина поля другая. Если парсер ждёт
11-битный ID, а кадр расширенный, он прочитает неверное значение. Всегда смотри на
формат ID, прежде чем собирать данные.

## Практика: тайминг-канал в CAN

Если данные кадров «обычные», а закладки нет, смотри на время. В `candump` каждая
строка начинается с таймстампа. Разница между соседними кадрами одного ID — это
интервал. Его чётность или величина может кодировать биты.

```bash
python3 - <<'PY'
import re
ts = []
for line in open('candump.log'):
    m = re.match(r'\(([\d.]+)\)', line)
    if m:
        ts.append(float(m.group(1)))
bits = [int(round((ts[i+1]-ts[i])*1000)) & 1 for i in range(len(ts)-1)]
print(bits)
PY
```

В нашем логе интервалы ровные (10 мс), поэтому тайминг-канал не используется — но в
задаче с «неровными» интервалами этот скрипт покажет, есть ли в них закономерность.

## Диагностика OBD-II

В автомобилях CAN используют для диагностики через **OBD-II**: стандартные ID
(например, `7DF` — запрос, `7E8` — ответ) и PID-параметры. Стеганография здесь может
прятаться в «нестандартных» PID или в ответах, которые блок не должен выдавать.
При разборе автомобильного лога полезно знать стандартные ID, чтобы отличить
«нормальный» трафик от подозрительного.

## Итоговая стратегия для CAN

Собери данные по каждому ID; декодируй hex; если в данных нет текста — проверь ID,
DLC и тайминги; посмотри на кадры с «неиспользуемыми» ID. Для CAN FD учти больший
размер данных и другой формат ID. И помни: `candump` — это текст, поэтому базовый
разбор делается `grep` и Python без специальных инструментов.

## Как отличить закладку от штатного трафика

В реальном автомобиле CAN-шина загружена: сотни кадров в секунду от десятков блоков.
Чтобы понять, где закладка, нужно знать «нормальные» ID и их частоту. Признаки
аномалии:

- **Неизвестный ID.** Кадры с ID, которого нет в документации машины.
- **Странная частота.** ID, который обычно молчит, вдруг передаётся регулярно.
- **Данные, не соответствующие ID.** Блок с ID двигателя передаёт ASCII.
- **DLC-аномалия.** Заявленная длина не совпадает с «нормальной» для этого ID.

В CTF обычно дают небольшой лог, и «лишний» ID виден сразу: он один, и данные в нём
читаемы. В реальной форензике приходится строить профиль трафика и искать отклонения.

## Практика: восстановление сообщения по кадрам

Главный навык — собрать данные одного ID в правильном порядке. Порядок задаётся либо
номером кадра (по времени), либо полем в данных. В нашем примере порядок — по времени:

```bash
python3 - <<'PY'
import re
frames = []
for line in open('candump.log'):
    m = re.search(r'\(([\d.]+)\).*?(\w+)#([0-9A-Fa-f]+)', line)
    if m:
        frames.append((float(m.group(1)), m.group(2), bytes.fromhex(m.group(3))))
frames.sort()
buf = b''.join(f[2] for f in frames)
print(buf.decode('latin-1'))
PY
```

Если ID несколько, сначала сгруппируй по ID, потом сортируй по времени внутри группы.
Частая ошибка — смешать ID: тогда байты «перемешаются» и текст не прочитается.

## Почему CAN-стеганография важна для безопасности

CAN не имеет аутентификации: любой узел на шине может отправлять кадры с любым ID.
Это делает его и уязвимым (спуфинг), и удобным для сокрытия. Исследователи
показывали, как через CAN прятать данные между ECU, не нарушая работу машины. Для
CTF это означает: задача про CAN — это всегда про внимательный разбор лога и
понимание, что «нормальный» трафик маскирует «лишний». Тот же принцип, что и в
сетевых covert-каналах, только на 8 байтах и с жёсткими ограничениями длины.

## Ещё один ориентир

В автомобильном логе один и тот же ID передаётся с фиксированной частотой. Если «тихий» ID вдруг начинает передаваться регулярно, это аномалия. Полезно построить частотную карту ID по логу и найти выбивающиеся: именно там обычно и прячется закладка.

## Заключение

CAN — короткие кадры и жёсткие ограничения, поэтому закладку приходится растягивать или прятать в служебных полях. Разбор лога начинается со сбора данных по ID, а заканчивается проверкой таймингов и «лишних» кадров.

## Итог

CAN-стеганография учит главному: даже в самом ограниченном формате есть поле, на которое получатель не смотрит. Здесь это данные «чужого» ID и тайминги между кадрами. Навык разбора лога — базовый и переносимый на любые полевые шины.

В реальной форензике этот же подход применяют к дампам с автомобилей: строят профиль трафика и ищут отклонения от него. Для CTF достаточно помнить, что закладка почти всегда в одном «лишнем» ID с читаемыми данными.

Помни: в CAN закладка живёт там, где её никто не ждёт — в «чужих» ID, в таймингах или в неиспользуемых байтах данных.

## Что мы теперь знаем

- CAN-кадр: ID (11/29 бит), DLC, до 8 байт данных, CRC.
- Основное место закладки — данные, собранные по кадрам одного ID.
- Дополнительные каналы: ID, DLC, тайминги, «лишние» кадры.
- `candump` формат: `(время) интерфейс ID#HEX`.
- Инструменты: `can-utils`, `python-can`.
