## Вопрос, с которого всё начинается

В задаче дали два файла: `a.bmp` и `b.bmp`. Открываешь оба — выглядят одинаково, размер одинаковый, «глазами» разницы не видно. Инструменты вроде `zsteg` и `binwalk` молчат. Как понять, что в одном из них что-то спрятано?

Ответ: спуститься на уровень байтов и **сравнить файлы побайтово**. Всё, что отличается, — это и есть спрятанные данные. Разберём это на нашем примере.

## Наш пример: a.bmp и b.bmp

Начнём с того, что вообще за файлы нам дали. Для этого есть команда `file` — она читает «магические» первые байты и говорит формат:

```bash
$ file a.bmp
a.bmp: PC bitmap, Windows 3.x format, 128 x 128 x 24, image size 49152, resolution 3780 x 3780 px/m, cbSize 49206, bits offset 54
```

**BMP** — простой растровый формат: изображение хранится как «сырые» байты пикселей, без сжатия. Это важно: в сжатых форматах (PNG, JPEG) изменение одного пикселя переписывает весь сжатый поток, а в BMP правка байта меняет ровно один байт в файле. Поэтому для побайтового анализа BMP — идеальный «учебный» носитель.

## Шаг 1: читаем структуру через xxd

**hex-дамп** — это распечатка файла в шестнадцатеричном виде. Команда `xxd` слева показывает смещение (offset — номер байта от начала), в середине — байты в hex, справа — их ASCII-«печать».

```bash
$ xxd a.bmp | head -2
00000000: 424d 36c0 0000 0000 0000 3600 0000 2800  BM6.......6...(.
00000010: 0000 8000 0000 8000 0000 0100 1800 0000  ................
```

Что тут видно: первые два байта `42 4d` — это ASCII `BM`, **сигнатура** (метка формата) BMP. Дальше `28 00` — размер заголовка, `80 00 00 00` дважды — ширина и высота (0x80 = 128 пикселей). То есть даже «шапка» файла рассказывает его устройство.

Искать интересное в дампе удобно через `tail` — данные часто дописаны в конец:

```bash
$ xxd a.bmp | tail -2
0000bfe0: ... 
```

Приём простой: смотрим начало (сигнатура и заголовок) и конец (данные после «официального» конца файла — частая закладка).

## Шаг 2: cmp — побайтовый diff двух файлов

**diff** — сравнение двух версий и показ различий. Для бинарников есть `cmp` с флагом `-l` («list»): он печатает только различающиеся байты — их позицию (в десятичном виде, с 1) и два значения в **восьмеричной** системе:

```bash
$ cmp -l a.bmp b.bmp
 1001 265 146
 1101 301 154
 1201 102 141
 1301 260 147
 1401  20 173
 1501 313 150
 1601 303 145
 1701  62 170
 1801 243 137
 1901 141 144
 2001 207 151
 2101 124 146
 2201 352 146
 2301  67 175
```

Считаем строки:

```bash
$ cmp -l a.bmp b.bmp | wc -l
14
```

Ровно **14 различий** — подозрительно ровное число для картинки из «шумовых» пикселей. И позиции идут с шагом 100 байт (1001, 1101, 1201…). Такая регулярность — уже сама по себе сигнал: данные встроены не случайно, а по алгоритму.

## Шаг 3: переводим восьмеричные байты в ASCII

Третий столбец `cmp -l` — значение байта во **втором** файле (b.bmp), записанное в восьмеричной системе (base-8, цифры 0–7). Например, `146` в восьмеричной = 1·64 + 4·8 + 6 = 102 = ASCII-символ `f`. Соберём третий столбец и раскодируем:

```bash
$ cmp -l a.bmp b.bmp | awk '{printf "%s ", $3}' | python3 -c "import sys; print(bytes(int(x,8) for x in sys.stdin.read().split()))"
b'flag{hex_diff}'
```

Готово. Что произошло: `awk` взял третье поле каждой строки, `int(x,8)` перевёл восьмеричное в число, `bytes(...)` собрал из чисел строку. Флаг `flag{hex_diff}` — доказательство, что различие байтов и есть закладка.

## Шаг 4: когда эталона нет — ищем сигнатуры

Diff работает, когда у нас есть **cover** (чистый файл-носитель) для сравнения. Если дали только один файл, ищем **встроенные контейнеры** — по их сигнатурам прямо в дампе. `grep` с `-a` (считать бинарным), `-b` (печатать смещение) и `-o` (только совпадение):

```bash
$ grep -aboP 'PK\x03\x04' b.bmp
$ grep -aboP '\x89PNG' b.bmp
```

Пусто — значит, целого вложенного архива нет. Но можно искать читаемые строки:

```bash
$ strings -n 6 b.bmp | grep -iE 'flag|ctf|base64'
```

`strings` вытаскивает подряд идущие печатаемые символы. Если флаг лежит текстом (пусть и разорванный), это его покажет.

## Шаг 5: энтропия — где искать аномалии

**Энтропия** — мера «хаотичности» данных: 0 у одинаковых байтов, 8 у полностью случайных. Сжатые и зашифрованные блоки дают энтропию, близкую к 8, — их видно на фоне текста (4–5) или гладкого изображения (6–7). Посчитаем по блокам:

```python
import math, collections
def entropy(b):
    c = collections.Counter(b); n = len(b)
    return -sum((v/n)*math.log2(v/n) for v in c.values())
data = open("suspicious.bin","rb").read()
for i in range(0, len(data), 8192):
    e = entropy(data[i:i+8192])
    if e > 7.5:
        print(hex(i), round(e,2))
```

Всплеск энтропии там, где ожидался предсказуемый участок, — признак встроенного сжатого или зашифрованного блока. Его вырезают (`dd`) и распаковывают.

## Шаг 6: чек-лист аномалий

Ручной hex-анализ — это не «листать дамп наугад», а проверять короткий список типовых закладок. Вот на что смотреть в первую очередь:

- **Данные после конца файла.** После PNG-маркера `IEND`, JPEG-маркера `FFD9`, `%%EOF` в PDF — часто дописан целый контейнер.
- **Несоответствие размеров.** В заголовке одно число, а файл весит больше — значит, есть хвост.
- **Странные чанки и сегменты.** Нестандартные имена (`tEXt`, `zTXt`, лишний `APPn` в JPEG) — кандидаты на данные.
- **Повторяющиеся сигнатуры.** Несколько `PK` или `PNG` внутри одного файла — признак полиглота.
- **Аномальная энтропия.** Блоки с энтропией 7.9+ там, где ожидался текст.
- **Регулярность в младших битах.** Изменения «через один байт», ровное число различий — как наши 14.

Полезно помнить «норму» формата: у PNG обязательны `IHDR`, `IDAT`, `IEND`; у BMP — заголовок `BM` и таблица цветов (или её отсутствие для 24-битного). Всё лишнее — потенциальный канал.

## Шпаргалка по командам

| Задача | Команда |
|---|---|
| определить формат | `file f` |
| hex-дамп | `xxd f` |
| найти сигнатуру со смещением | `grep -aboP 'PK\x03\x04' f` |
| строки | `strings -n 6 f` |
| побайтовый diff | `cmp -l a b` |
| восьмеричные байты → текст | `int(x,8)` → `bytes(...)` |
| вырезать по смещению | `dd if=f bs=1 skip=N count=M` |
| энтропия | Python по блокам |

## Что мы теперь знаем

1. `file` определяет формат по сигнатуре; BMP хранит пиксели без сжатия — удобен для побайтового анализа.
2. `xxd` даёт hex-дамп: смещения, байты, ASCII.
3. `cmp -l a b` печатает различающиеся байты — позицию и значения в **восьмеричном** виде.
4. Различия легко перевести в ASCII: `int(x,8)` → `bytes`.
5. Нет эталона — ищем сигнатуры (`grep -aboP`) и строки (`strings`).
6. Аномальная энтропия выдаёт сжатый или зашифрованный встроенный блок.

## Куда дальше

Мы научились видеть данные на уровне байтов. Дальше разберём конкретный алгоритм, который прячет биты в младших разрядах пикселей, и почему наивный LSB легко вычислить статистикой. А пока запомни: инструменты молчат — открывай `xxd` и делай `cmp` с эталоном.

## Где пригодится

- **CTF:** Stego/Forensics — нестандартное встраивание, «инструменты молчат».
- **Forensics:** carving встроенных файлов, анализ артефактов, поиск дописанных данных.
- **Malware analysis:** разбор подозрительных контейнеров и оверлеев.
