## Вопрос, с которого всё начинается

У тебя есть `appended.png`. Картинка открывается, но файл весит больше, чем должен для такого размера. Писать скрипты каждый раз не хочется — какие инструменты дают быстрый результат?

В этом уроке мы пройдём по **готовым инструментам** для анализа изображений: от метаданных до поиска встроенных файлов. Разберём на `appended.png`, как за пару команд найти секрет, а затем посмотрим на парольную стеганографию.

## Наш пример: файл appended.png

Начинаем с самых простых вопросов — что за файл и нет ли в нём метаданных:

```bash
exiftool appended.png | grep -iE 'file type|width|height|comment'
```

```text
File Type                       : PNG
Image Width                     : 32
Image Height                    : 32
```

Метаданные чистые. Тогда смотрим размер и ищем «лишнее»:

```bash
ls -l appended.png
```

```text
3308 appended.png
```

Картинка 32×32 должна весить около 3 КБ — и мы близки, но давайте проверим, нет ли встроенного файла.

## Шаг 1: strings — быстрый поиск текста

**`strings`** вытаскивает из любого файла последовательности печатных символов. Это самый быстрый способ увидеть, есть ли внутри текст:

```bash
strings appended.png | grep -i flag
```

```text
secret.txtflag{4pp3nd3d_z1p}PK
```

Видно сразу три подсказки: имя `secret.txt`, флаг и сигнатуру **`PK`** — начало ZIP-архива. Значит, в конец PNG дописан ZIP.

## Шаг 2: находим смещение встроенного файла

Сигнатура ZIP — `PK\x03\x04`. Находим её позицию в файле:

```python
d = open('appended.png', 'rb').read()
print('PK header offset:', d.find(b'PK\x03\x04'), 'file size:', len(d))
```

```text
PK header offset: 3172 file size: 3308
```

Архив начинается с байта 3172 — сразу после «нормального» PNG. Такой приём называется **file appending**: данные дописывают в конец, и большинство просмотрщиков их игнорируют.

## Шаг 3: извлекаем встроенный файл

Отрезаем хвост начиная со смещения и открываем как ZIP:

```python
import zipfile, io
d = open('appended.png', 'rb').read()
z = zipfile.ZipFile(io.BytesIO(d[3172:]))
print('names:', z.namelist())
print('content:', z.read(z.namelist()[0]).decode())
```

```text
names: ['secret.txt']
content: flag{4pp3nd3d_z1p}
```

Флаг извлечён. Заметь: мы даже не «ломали» картинку — просто нашли границу и отрезали хвост.

## Шаг 4: инструменты для метаданных и файлов

Основные утилиты, которые стоит держать под рукой:

- **`exiftool`** — метаданные изображений, документов, аудио.
- **`strings`** — печатный текст внутри любого файла.
- **`binwalk`** — поиск встроенных файлов по сигнатурам (в некоторых сборках может требовать настройки зависимостей).
- **`foremost`** / **`scalpel`** — восстановление файлов по сигнатурам.
- **`file`** — определение типа.

Если `binwalk` не работает, ручной поиск сигнатуры (как выше) решает задачу не хуже.

## Шаг 5: парольная стеганография — steghide, outguess, stegseek

Отдельный класс — инструменты, которые прячут данные в пикселях **с паролем**. Классика — **steghide** (работает с JPEG/BMP/WAV) и **outguess** (JPEG). Извлечение:

```bash
steghide extract -sf image.jpg -p '' -xf out.txt
```

Флаг `-p ''` задаёт пустой пароль, `-xf` — файл, куда писать. Если пароль неизвестен, его подбирают словарём. Быстрее всего это делает **stegseek**:

```bash
stegseek image.jpg /usr/share/wordlists/rockyou.txt
```

`stegseek` перебирает пароли на порядок быстрее, чем `steghide` через цикл, и сразу печатает найденный пароль и содержимое. Это стандартный шаг для JPEG-задач.

## exiftool глубже: что искать в метаданных

`exiftool` — не только «показать дату съёмки». Метаданные хранят массу полей, и секрет часто прячут именно в необычных. Стоит смотреть на: **Comment** и **ImageDescription** (частое место для текста), **Software** (могли записать строку), **Artist/Copyright** (автор), **XP-теги** (Windows-специфичные поля), а также **GPS** (координаты). Полезно запускать `exiftool` без фильтров целиком и просматривать глазами: иногда флаг лежит в поле, которого вы не ожидали.

Отдельно проверяйте **XMP** — расширенный блок метаданных в формате XML. В нём может быть произвольная строка, а иногда и целый вложенный документ. Если поле выглядит как base64 или hex — декодируйте. Если как сжатые данные — распакуйте.

Ещё один нюанс: метаданные могут быть **удалены** из видимой части, но остаться в «мусорных» областях или в старых версиях файла. Инструменты вроде `exiftool -a -u` показывают в том числе необычные и дублирующиеся теги.

## Как работает парольная стеганография

`steghide`, `outguess` и подобные прячут данные **в пикселях** и шифруют их паролем. Это значит, что без пароля данные не просто «спрятаны», а **криптографически защищены**: извлечь их нельзя, даже зная метод. Поэтому для таких файлов основной приём — подбор пароля.

`steghide` встраивает данные, слегка меняя яркость пикселей, и использует пароль как ключ шифрования. `outguess` работает с JPEG и умеет сохранять статистику, чтобы встраивание было менее заметным. Оба инструмента требуют форматов без сильного сжатия (JPEG, BMP, WAV), иначе данные не переживут пересохранение.

`stegseek` ускоряет подбор за счёт того, что не запускает `steghide` заново на каждый пароль, а проверяет кандидатов быстрее. На практике это превращает перебор словаря из «часов» в «минуты». Если словарь не помог — возможно, пароль нестандартный, и тогда остаётся только целевой подбор или поиск подсказки в задании.

Важно: парольная стего **не определяется** по размеру или сигнатуре — файл выглядит абсолютно нормально. Поэтому в задачах на JPEG сначала пробуют `stegseek`, и только потом ищут другие каналы.

## Полный прогон: от файла к флагу

```text
appended.png
  → exiftool → чистые метаданные
  → strings | grep flag → secret.txt + flag + PK
  → поиск сигнатуры PK\x03\x04 → смещение 3172
  → zipfile → secret.txt → flag{4pp3nd3d_z1p}
  → при пароле — stegseek/steghide
```

## Если не сработало

- **strings ничего не дал** — данные могут быть в пикселях (LSB, `stego-bitplane`) или сжаты.
- **`binwalk` падает** — используйте ручной поиск сигнатур и `foremost`.
- **steghide не открывает** — пароль неверный; запустите `stegseek` со словарём.
- **Файл — WebP/GIF** — там свои чанки (`stego-webp`, `stego-gif`).

## Что мы теперь знаем

- **`exiftool`** — первый шаг: метаданные.
- **`strings`** мгновенно показывает печатный текст внутри файла.
- **File appending** — данные дописаны в конец; находятся по сигнатуре.
- **`steghide`/`outguess`** прячут данные с паролем.
- **`stegseek`** быстро подбирает пароль по словарю.
- Если `binwalk` недоступен, ручной поиск сигнатуры — надёжная замена.

## Почему PNG и JPEG устроены по-разному для стего

Формат определяет, **какие каналы сокрытия вообще существуют**. PNG — это сжатие без потерь (DEFLATE) и **чанки**: файл состоит из именованных блоков (IHDR, IDAT, IEND и др.), и данные можно спрятать в дополнительных чанках (`tEXt`, `zTXt`, `iTXt`) или в LSB пикселей. Поскольку сжатие без потерь, изменения пикселей сохраняются точно — LSB-стеганография здесь работает надёжно.

JPEG — сжатие **с потерями** на основе DCT (дискретного косинусного преобразования). Пиксели восстанавливаются приблизительно, поэтому LSB пикселей не выживает. Зато выживают **коэффициенты DCT**: их можно слегка менять (JSteg, F5, OutGuess), и это не так заметно. Именно поэтому для JPEG используют частотные методы, а для PNG/BMP — пространственные (LSB).

Отдельный класс — **дописанные данные**: и в PNG, и в JPEG, и в GIF после «конца» файла (IEND/EOI) можно дописать целый архив или файл. Парсеры, читающие только до маркера конца, его не заметят. Это самый частый CTF-приём, и его находит банальный `binwalk`, `foremost` или сравнение заявленного размера со фактическим.

Понимание формата экономит время: прежде чем крутить стего-инструменты, посмотрите, **что это за контейнер** — от этого зависит и метод, и набор инструментов.

## Частые вопросы

**Как быстро понять, есть ли дописанные данные?** Сравните размер файла с размером, до которого его читает парсер (`pngcheck`, `identify`), и прогоните `binwalk`/`foremost`.

**Что делать с PNG, где LSB-анализ ничего не дал?** Проверьте чанки (`pngcheck -v`), метаданные (`exiftool`), палитру и порядок цветов; иногда данные в нестандартных чанках.

**Почему steghide/outguess не работают на PNG?** steghide поддерживает JPEG/BMP/WAV/AU, outguess — JPEG; для PNG нужны `zsteg`, `stegsolve` или ручной LSB.

**Что такое zsteg?** Инструмент для LSB-анализа PNG/BMP: перебирает битовые плоскости и порядки, ищет встроенный текст/архив.

## Практика: zsteg и stegoveritas для PNG/BMP

Когда `strings` и `exiftool` пусты, а `steghide` не подходит (PNG), на помощь приходит
**`zsteg`** — он перебирает битовые плоскости, порядки и каналы и сам подсказывает, где
осмысленный текст:

```bash
zsteg cover.png
```

```text
b1,rgb,lsb,xy       .. text: "nto{lsb_png}"
b2,r,msb,xy         .. file: Zip archive data
```

Строки `b1,rgb,lsb,xy` читаются как: бит-плоскость 1, каналы rgb, порядок lsb, обход xy.
`zsteg -a` (all) перебирает все комбинации, `zsteg -E 'b1,rgb,lsb,xy'` извлекает
конкретный канал. Если `zsteg` находит ZIP — сохраняйте поток и распаковывайте.

Для «широкого» прохода есть **`stegoveritas`**: он гоняет десятки проверок (метаданные,
бит-плоскости, цветовые каналы, палитру) и складывает результаты в каталог. Это удобно,
когда не знаешь, какой канал задействован, и не хочешь помнить десяток команд.

| Ситуация | Инструмент |
|----------|------------|
| JPEG, пароль неизвестен | `stegseek` со словарём |
| PNG/BMP, нужен LSB | `zsteg` |
| Неясно, где данные | `stegoveritas`, `binwalk` |
| Метаданные | `exiftool -a -u` |
