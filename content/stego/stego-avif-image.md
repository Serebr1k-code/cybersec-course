## Вопрос, с которого всё начинается

`image.avif` — современное изображение. AVIF сегодня хвалят за качество при малом
размере, и он основан на **AV1** — том же кодеке, что и видео. Значит, его контейнер
устроен как видеофайл. Посмотрим, что это даёт для стеганографии: в MP4-подобных
контейнерах мест для «лишних» данных едва ли не больше, чем в PNG.

## Наш пример: файл image.avif

```bash
file image.avif
xxd -l 64 image.avif
```

```text
image.avif: ISO Media, AVIF Image
00000000: 0000 0018 6674 7970 6176 6966 0000 0000  ....ftypavif....
00000010: 6176 6966 6d69 6631 0000 000c 6d65 7461  avifmif1....meta
00000020: 0000 0000 0000 001e 464c 4720 6e74 6f7b  ........FLG nto{
00000030: 3476 3166 5f31 736f 626d 6666 5f66 6c34  4v1f_1s0bmff_fl4
```

Первые байты — `ftyp` (file type), как в MP4. Дальше `meta`, потом — бокс `FLG `,
которого в спецификации AVIF нет.

## Шаг 1: AVIF — это ISOBMFF, а не «картинка»

**ISOBMFF** (ISO Base Media File Format) — это контейнер, в котором живут MP4, HEIF,
AVIF, 3GP. Всё внутри — **боксы** одинакового вида:

```
[ размер(4, big-endian) ][ тип(4) ][ данные ]
```

Есть «контейнерные» боксы (`meta`, `moov`), внутри которых лежат другие боксы, и
«листовые» (`mdat`, `iloc`). Понимая ISOBMFF один раз, ты читаешь и MP4, и HEIC, и
AVIF.

## Шаг 2: ключевые боксы AVIF

- **`ftyp`** — тип файла: `avif` (основной бренд) и список совместимых (`mif1`, `miaf`).
- **`meta`** — метаданные: `hdlr` (тип), `iloc` (где лежат данные), `iinf`/`infe`
  (описания элементов), `iprp`/`ipco` (свойства: размер, цвет), `pitm` (главный элемент).
- **`mdat`** — «media data»: сами сжатые AV1-кадры. Именно сюда указывает `iloc`.
- **`free`/`skip`** — «свободные» области; спецификация разрешает их, и они идеальны
  для закладок: ничего не ломают.

В нашем файле есть `meta`, а `FLG ` — явно самодельный бокс. Читаем его.

## Шаг 3: парсер боксов и извлечение

```bash
python3 - <<'PY'
import struct
d = open('image.avif','rb').read()
i = 0
while i + 8 <= len(d):
    size = struct.unpack('>I', d[i:i+4])[0]
    typ = d[i+4:i+8]
    print(f'{i:>6}  {size:>6}  {typ}')
    if size == 0:
        break
    i += size
PY
```

```text
     0      24  b'ftyp'
    24      12  b'meta'
    36      30  b'FLG '
```

Три бокса. `FLG ` не из спецификации — достаём данные:

```bash
python3 - <<'PY'
import struct
d = open('image.avif','rb').read()
i = 36
size = struct.unpack('>I', d[i:i+4])[0]
print(d[i+8:i+size].decode())
PY
```

```text
nto{4v1f_1s0bmff_fl4g}
```

## Шаг 4: где ещё прячут в AVIF

- **`free` / `skip`** — штатные пустые боксы. Данные в них никто не проверяет.
- **`uuid`** — частное расширение, как в JP2.
- **`Exif` / `XMP`** — в `meta` могут быть `iinf`-элементы типа Exif/XMP.
  `exiftool -a -G1 image.avif` их покажет.
- **appended data** — хвост после последнего бокса.
- **внутри `mdat`** — LSB в декодированных AV1-кадрах или в остаточных коэффициентах
  (сложно, требует декодера).

## Шаг 5: инструменты

```bash
exiftool -a -G1 image.avif | grep -iE 'Comment|XML|Exif|Item'
mp4box -info image.avif 2>/dev/null | head
binwalk image.avif
```

`mp4box` (GPAC) показывает дерево ISOBMFF-боксов и очень помогает: он перечислит
`meta`, `iloc`, `mdat` и заметит незнакомый бокс. `ffprobe image.avif` покажет
потоковые параметры.

## Шаг 6: вложенность боксов meta

Бокс `meta` — контейнерный: внутри него лежат `hdlr`, `pitm`, `iloc`, `iinf`, `iprp`
и другие. Это значит, что «плоский» парсер, который просто идёт по длинам верхнего
уровня, увидит `meta` как один большой блок и не заглянет внутрь. Чтобы найти закладку
внутри, нужно рекурсивно спускаться.

Типовой сценарий CTF: в `meta` добавлен `iinf`-элемент с описанием `infe`, который
ссылается на `iloc`, а тот указывает на область в `mdat`, где лежит флаг. Без
рекурсивного разбора это выглядит как «обычный AVIF».

```bash
python3 - <<'PY'
import struct
def walk(d, base, depth):
    i = base
    while i + 8 <= len(d):
        size = struct.unpack('>I', d[i:i+4])[0]
        typ = d[i+4:i+8]
        print('  '*depth, typ, size)
        if typ in (b'meta', b'moov', b'trak'):
            walk(d, i+12, depth+1)   # meta имеет 4 байта версии/флагов
        if size == 0:
            break
        i += size
walk(open('image.avif','rb').read(), 0, 0)
PY
```

## Шаг 7: iloc и ссылки на данные

`iloc` — «item location»: таблица, которая говорит, где лежат данные каждого элемента.
Обычно она указывает в `mdat`. Но ничто не мешает указать на бокс `free` или на
область за пределами «нормальных» данных. При разборе AVIF полезно сверять: куда
указывают смещения `iloc` и что реально лежит по этим адресам.

Если смещение выходит за границы `mdat` или попадает в нестандартный бокс — это
красный флаг. Иногда именно так прячут полезную нагрузку.

## Шаг 8: сравнение с HEIC

HEIC и AVIF — «родственники»: оба ISOBMFF, оба используют `meta`/`iloc`/`mdat`.
Разница в кодеке: HEIC — HEVC (H.265), AVIF — AV1. Для стеганографии это почти
неважно: контейнерные закладки ищутся одинаково. Если у тебя есть парсер ISOBMFF,
он работает и с HEIC, и с AVIF, и с MP4.

Практический вывод: не пиши отдельный инструмент под каждый формат. Напиши один
рекурсивный обходчик боксов — и применяй его ко всему семейству.

## Шаг 9: чек-лист по ISOBMFF

1. `xxd -l 32` — проверь `ftyp` и бренд.
2. Рекурсивно обойди боксы, включая контейнерные (`meta`, `moov`).
3. Найди боксы не из спецификации (не `ftyp/meta/mdat/free/…`).
4. Проверь `free`/`skip` — там может лежать что угодно.
5. Проверь `iloc` на смещения вне `mdat`.
6. Проверь appended data и `uuid`-боксы.
7. Только потом — декодируй пиксели.

## Второй пример: закладка в free-боксе

Бокс `free` (в некоторых контейнерах — `skip`) спецификация разрешает использовать
как «заполнитель»: он ничего не значит и может быть любого размера. Разработчики
иногда кладут туда отладочную информацию, а CTF-авторы — флаг. Найти его просто:
перебрать боксы и посмотреть содержимое всех `free`.

```bash
python3 - <<'PY'
import struct
d = open('image.avif','rb').read()
i = 0
while i + 8 <= len(d):
    size = struct.unpack('>I', d[i:i+4])[0]
    typ = d[i+4:i+8]
    if typ in (b'free', b'skip'):
        body = d[i+8:i+size]
        print('free block', size-8, 'bytes:', body[:64])
    i += size if size else len(d) - i
PY
```

Если внутри `free` лежит сжатый blob — попробуй `zlib.decompress`, `base64 -d` или
`strings`. Если лежит ещё один файл — его найдёт `binwalk`. `free`-бокс особенно
коварен тем, что инструменты вроде `mp4box -info` могут его просто пропустить,
показывая «чистый» файл.

## Частые ошибки при разборе AVIF

Первая и самая дорогая ошибка — пытаться читать AVIF как картинку, а не как контейнер.
Соблазн велик: открыл, увидел изображение, решил, что файл «нормальный». Но AVIF — это
ISOBMFF, и вся структура лежит в боксах, которые никак не видны при просмотре. Пока
ты не обойдёшь боксы, ты не знаешь о файле почти ничего.

Вторая ошибка — не учитывать вложенность. `meta` и `moov` — контейнерные боксы. Если
парсер не спускается внутрь, он пропустит `iinf`/`iloc`/`iprp`, где и живёт структура
файла. А закладка может быть в самом «глубоком» углу этой иерархии.

Третья ошибка — путать `iloc` со «ссылкой на файл». `iloc` указывает на смещения
внутри `mdat`. Если смещение выходит за границы `mdat` или попадает в `free`-бокс,
это аномалия. Всегда сверяй, что реально лежит по указанному адресу.

Четвёртая ошибка — забывать про хвост. ISOBMFF-парсеры часто останавливаются на
последнем известном боксе, а данные после него никто не проверяет. `binwalk` и
`xxd` с конца файла обязательны.

## Что роднит AVIF с видео

AVIF использует интра-кадры AV1 — то есть по сути «один кадр видео». Это значит, что
навыки разбора AVIF напрямую переносятся на видеофайлы MP4/AV1: те же боксы, те же
`meta`/`mdat`, та же логика `iloc`. Если ты понял AVIF, ты готов к видеостеганографии
следующего уровня, где добавятся межкадровые предсказания и motion vectors.

## Итоговая стратегия поиска в AVIF

Практический порядок для `.avif`/`.heic`: посмотри `ftyp` и бренд, затем рекурсивно
обойди боксы, включая контейнерные. Выпиши все нестандартные типы, все `free`/`skip`,
все `uuid`. Проверь `iloc` на смещения вне `mdat`. Проверь хвост файла. Затем —
`exiftool -a -G1` и `mp4box -info` для перекрёстной проверки.

Такой конвейер переносится на `.mp4`, `.mov`, `.m4a` без изменений: везде ISOBMFF,
везде те же приёмы. Освоив один контейнер, ты получаешь целое семейство форматов.

## Что мы теперь знаем

- AVIF — это ISOBMFF-контейнер (`ftyp`, `meta`, `mdat`) с AV1-интра внутри.
- Боксы — `размер(4, big-endian) + тип(4) + данные`.
- `free`/`skip`/`uuid`/`Exif` и appended data — типовые места закладок.
- Один парсер ISOBMFF работает и для MP4/HEIC/AVIF.
- `mp4box`/`exiftool`/`binwalk` ускоряют разбор, но не заменяют ручной парсер.
