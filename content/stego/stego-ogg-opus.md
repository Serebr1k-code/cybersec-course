## Вопрос, с которого всё начинается

`voice.opus` — голосовое сообщение в формате Opus внутри Ogg-контейнера. Ogg — это
**потоковая** обёртка: данные нарезаны на «страницы», каждую можно передавать отдельно.
Где тут прячут? Оказывается, у Ogg есть комментарии (как теги), а у самих страниц —
поля, которые плеер не проверяет. Разберём файл.

## Наш пример: файл voice.opus

```bash
file voice.opus
xxd -l 64 voice.opus
```

```text
voice.opus: Ogg data, Opus audio
00000000: 4f67 6753 0002 0000 0000 0000 0001 0000  OggS............
00000010: 0000 0000 0000 0000 0001 1301 4f70 7573  ............Opus
00000020: 4865 6164 0102 3801 80bb 0000 0000 4f67  Head..8.......Og
00000030: 6753 0002 0000 0000 0000 0001 0000 0001  gS..............
```

Видим `OggS` дважды — это две страницы. Внутри первой — `OpusHead`, во второй
будет `OpusTags` с комментариями. Разберём устройство страницы.

## Шаг 1: страница Ogg

Каждая страница Ogg начинается с 4 байт `OggS` и фиксированного заголовка:

```
OggS(4)
version(1)
header_type(1)     — 0x02 = начало потока (BOS), 0x04 = конец (EOS)
granule_position(8) — позиция в потоке (little-endian)
serial_number(4)   — ID логического потока (little-endian)
page_sequence(4)   — номер страницы (little-endian)
CRC(4)             — контрольная сумма всей страницы
segment_count(1)   — сколько сегментов (0..255)
segment_table(n)   — длины сегментов
```

Затем идут данные: их длина = сумма значений из сегментной таблицы. Сегмент длиной
255 означает «продолжение» — данные переносятся на следующую страницу.

**Granule position** — это «номер сэмпла» на момент конца страницы. Плеер использует
его для перемотки. Младшие биты granule никто строго не проверяет — типичный канал.

## Шаг 2: полезная нагрузка Opus

Первая страница (BOS) содержит `OpusHead`: версию, число каналов, pre-skip, частоту,
усиление, маппинг каналов. Вторая — `OpusTags`:

```
OpusTags(8)
vendor_length(4, LE)
vendor_string
comment_count(4, LE)
[ comment_length(4, LE) + comment ] * count
```

Комментарии — пары вида `КЛЮЧ=значение` (`TITLE=...`, `ARTIST=...`). Флаг прячут в
произвольный комментарий, например `FLAG=nto{...}`.

## Шаг 3: достаём комментарий вручную

```bash
python3 - <<'PY'
d = open('voice.opus','rb').read()
i = 0
while i < len(d):
    assert d[i:i+4] == b'OggS'
    nsegs = d[i+26]
    segs = d[i+27:i+27+nsegs]
    body = d[i+27+nsegs:i+27+nsegs+sum(segs)]
    if body[:8] == b'OpusTags':
        p = 8
        vl = int.from_bytes(body[p:p+4],'little'); p += 4 + vl
        cnt = int.from_bytes(body[p:p+4],'little'); p += 4
        for _ in range(cnt):
            cl = int.from_bytes(body[p:p+4],'little'); p += 4
            print(body[p:p+cl].decode('utf-8')); p += cl
    i += 27 + nsegs + sum(segs)
PY
```

```text
FLAG=nto{0gg_0pu5_c0mm3nt}
```

## Шаг 4: другие места сокрытия в Ogg

- **Granule position.** Младшие биты — тайминг-канал; изменения незаметны.
- **Пустые страницы.** Страница без данных (segment_count=0) легальна и может нести
  данные в сегментной таблице.
- **Порядок/лишние поля комментариев.** Произвольные пары ключ=значение.
- **CRC.** Теоретически можно спрятать, но плееры его проверяют, поэтому редко.
- **Vorbis vs Opus.** У Vorbis свой заголовок и `vorbis_comment`; структура та же —
  little-endian длины.

## Шаг 5: инструменты

```bash
opusinfo voice.opus            # комментарии и структура (из opus-tools)
ffprobe -hide_banner voice.opus
vorbiscomment -l voice.opus    # для Vorbis/Opus (если поддерживается)
strings voice.opus | grep -iE 'nto|FLAG'
```

`opusinfo` покажет теги прямо; `strings` ловит `FLAG=nto{`. Ручной парсер нужен,
когда тег нестандартный или инструмент не установлен.

## Шаг 6: granule position как тайминг-канал

Granule position — это 64-битное число в заголовке каждой страницы (little-endian).
Для аудио это «номер сэмпла» на конец страницы. Плеер использует его для перемотки,
но не требует строгой монотонности на каждой странице. Значит, младшие биты granule
можно слегка «шевелить» — это тайминг-канал, который почти никто не проверяет.

Тот же приём работает и с **page sequence**: номер страницы должен расти, но
пропуски или «лишние» страницы обычно не критичны.

## Шаг 7: пустые и служебные страницы

Страница с `segment_count = 0` легальна: она не несёт данных, но занимает место в
потоке. Такие «пустые» страницы — идеальный носитель. Проверить их просто: парсер
перебирает страницы и смотрит, у каких нет данных, но есть нестандартные поля.

Кроме того, `serial_number` позволяет мультиплексировать несколько логических потоков
в одном файле. Можно добавить «лишний» поток, который ничего не играет, но хранит
данные.

## Шаг 8: Vorbis против Opus

У Vorbis и Opus одна и та же обёртка Ogg, но разные заголовки:

| | Vorbis | Opus |
|---|---|---|
| Первая страница | `\x01vorbis` | `OpusHead` |
| Комментарии | `\x03vorbis` | `OpusTags` |
| Частота | в идентификаторе | в `OpusHead` |

Комментарии в обоих случаях — Vorbis-comment с little-endian длинами. Так что парсер
комментариев у них общий, меняется только имя блока.

## Шаг 9: что делать, если комментарии чистые

- Проверь granule и sequence на аномалии.
- Посмотри сегментные таблицы: сегмент 255 = продолжение; лишние сегменты = данные.
- Проверь CRC: если он не совпадает, возможно, файл правили вручную.
- Прогони `binwalk voice.opus` — вдруг внутри ещё один файл.
- Посмотри хвост после последней страницы (EOS).

Ogg — потоковый формат, поэтому «хвост» и «пустые страницы» здесь встречаются чаще,
чем в файловых контейнерах вроде FLAC.

## Второй пример: пустая страница-носитель

Покажем, как выглядит пустая страница. У неё `segment_count = 0` и нет данных, но
заголовок на месте. Иногда в такой странице прячут данные прямо в неиспользуемых
полях, например в `serial_number` или `granule`.

```bash
python3 - <<'PY'
d = open('voice.opus','rb').read()
i = 0
n = 0
while i < len(d):
    assert d[i:i+4] == b'OggS'
    nsegs = d[i+26]
    segs = d[i+27:i+27+nsegs]
    body = d[i+27+nsegs:i+27+nsegs+sum(segs)]
    print('page', n, 'segs', nsegs, 'body', len(body))
    if nsegs == 0:
        print('  EMPTY page — check serial/granule')
    i += 27 + nsegs + sum(segs)
    n += 1
PY
```

Пустая страница в середине потока — почти наверняка закладка: обычные кодировщики её
не создают. Если она есть, извлеки из её заголовка granule/serial и проверь, не
складываются ли они в ASCII.

## Частые ошибки при разборе Ogg

Первая ошибка — считать страницу фиксированного размера. Размер страницы зависит от
сегментной таблицы: сумма длин сегментов и есть длина данных. Сегмент длиной 255
означает «продолжение»: данные переносятся на следующую страницу. Парсер, который
не учитывает это, развалится на длинных данных.

Вторая ошибка — игнорировать CRC. Ogg хранит контрольную сумму каждой страницы. Если
CRC не совпадает, страницу могли править вручную — а это признак закладки. Правда,
сам CRC вычислить нетривиально (алгоритм с полиномом 0x04c11db7), но факт несовпадения
`oggz`/`opusinfo` покажет.

Третья ошибка — не различать BOS/EOS. Первая страница потока помечена `header_type=2`
(BOS), последняя — `4` (EOS). Данные между ними — это поток. Если после EOS есть ещё
страницы — это appended data, потенциальная закладка.

## Ogg как универсальный контейнер

Ogg умеет нести не только аудио: существуют Ogg-видео (Theora), Ogg-текст (Kate) и
даже Ogg-приложения. Каждый поток имеет свой `serial_number`, поэтому в одном файле
могут сосуществовать несколько логических потоков. Для стеганографии это значит:
можно добавить «тихий» поток, который ничего не играет, но хранит данные. Проверяй
все серии, а не только первую.

## Итоговая стратегия поиска в Ogg

Для незнакомого `.ogg`/`.opus`: посмотри `xxd -l 32` и убедись, что это `OggS`.
Затем перебери все страницы и выпиши `header_type`, `granule`, `serial`, `sequence`
и длину данных. Найди страницы BOS/EOS и всё, что после EOS. Далее — разбери
`OpusTags`/`vorbis_comment` и выпиши комментарии. И только потом — проверяй granule
на тайминг-канал.

Такой конвейер покрывает практически все CTF-задачи на Ogg. Дополнительный уровень —
поиск вложенных файлов через `binwalk`, если комментарии и страницы чистые.

## Что проверять в последнюю очередь

Если ни комментарии, ни granule, ни пустые страницы не дали результата, стоит
заглянуть в сами аудиоданные Opus. Поток состоит из фреймов, каждый со своим
заголовком; младшие биты полей можно модулировать, но это уже полноценная
аудиостеганография, требующая декодера. В CTF до этого доходят редко — почти
всегда закладка лежит на уровне контейнера, который мы и разобрали.

Ещё один ориентир: если размер страницы не совпадает с суммой сегментов из таблицы, файл правили вручную — это почти наверняка закладка, и стоит прочитать содержимое такой страницы целиком.

## Что мы теперь знаем

- Ogg — поток **страниц** `OggS` с granule, serial, sequence, CRC и сегментной таблицей.
- Первая страница (BOS) — `OpusHead`, вторая — `OpusTags` с комментариями.
- Комментарии — пары `КЛЮЧ=значение` с little-endian длинами.
- Granule и пустые страницы — дополнительные каналы.
- Vorbis устроен так же, меняется только заголовок.
