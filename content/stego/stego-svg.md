## Вопрос, с которого всё начинается

В задаче дали файл `logo.svg` — простую векторную картинку. Открываешь в браузере: синий круг на светлом фоне, ничего лишнего. Где тут может быть флаг?

В **SVG**. В отличие от PNG или JPEG, SVG — это не «сжатые пиксели», а **обычный текст на XML**. Его можно прочитать глазами, и данные прячут прямо в разметке. Разберём это на нашем файле.

## Наш пример: logo.svg

Смотрим, что за файл:

```bash
$ file logo.svg
logo.svg: SVG Scalable Vector Graphics image
```

SVG — это **векторная** графика: не сетка пикселей, а инструкции «нарисуй круг, залей прямоугольник». Хранится всё в XML-документе. Посмотрим его содержимое:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<svg xmlns="http://www.w3.org/2000/svg" width="200" height="200">
  <!-- ZmxhZ3tzdmdfY29tbWVudHN9 -->
  <rect x="0" y="0" width="200" height="200" fill="#eef"/>
  <circle cx="100" cy="100" r="60" fill="#39c"/>
</svg>
```

Прямо в тексте видна подозрительная строка внутри `<!-- ... -->`.

## Шаг 1: комментарий с base64

`<!-- ... -->` — это **XML-комментарий**: текст, который парсеры и рендереры игнорируют. Идеальное место для данных. Строка `ZmxhZ3tzdmdfY29tbWVudHN9` выглядит как **base64** — способ записи байтов буквами и цифрами. Извлечём комментарий и раскодируем:

```bash
$ grep -oP '(?s)<!--.*?-->' logo.svg
<!-- ZmxhZ3tzdmdfY29tbWVudHN9 -->

$ grep -oP '(?s)<!--\s*\K[A-Za-z0-9+/=]+' logo.svg | base64 -d
flag{svg_comments}
```

Флаг получен. Обрати внимание на флаги `grep`: `-o` печатает только совпадение, `-P` включает регулярные выражения Perl, а `(?s)` заставляет `.` захватывать и переводы строк — иначе многострочный комментарий не найдётся.

## Шаг 2: path-координаты как битовый канал

Комментарий — самый простой случай. Возьмём второй файл, `chart.svg` — визуально обычный график, комментариев нет. Смотрим на числа в атрибуте `d` тега `<path>` (это координаты линий):

```bash
$ python3 -c "import re;print(re.findall(r'\.\d{4,}', open('chart.svg').read())[:12])"
['.0000000', '.0000001', '.0000001', '.0000000', '.0000000', '.0000001', '.0000001', '.0000000', '.0000000', '.0000001', '.0000001', '.0000000']
```

Координаты записаны с избыточной точностью: `10.0000000`, `13.0000001`… Человек разницы не увидит, а **младшая цифра дробной части кодирует бит**. Соберём эти цифры и упакуем в байты:

```python
import re
svg = open("chart.svg").read()
bits = "".join(n[-1] for n in re.findall(r'\.(\d{4,})', svg))
print(bytes(int(bits[i:i+8], 2) for i in range(0, len(bits)-7, 8)))
```

```
b'flag{svg_path_bits}'
```

`n[-1]` берёт последнюю цифру каждого длинного дробного числа, `int(...,2)` превращает 8 бит в байт. Приём незаметен визуально и переживает обычную проверку XML.

## Шаг 3: вложенный растр и data: URI

SVG может нести внутри **растровую** картинку, закодированную как base64 прямо в атрибуте:

```xml
<image href="data:image/png;base64,iVBORw0KGgoAAAANS..."/>
```

`data:` URI — это встроенные данные. После декода получаем обычный PNG, к которому применимы все растровые техники (`zsteg`, `stegsolve`). Извлечь его можно так:

```python
import re, base64
svg = open("logo.svg").read()
for m in re.finditer(r'data:image/(png|jpeg|gif);base64,([A-Za-z0-9+/=]+)', svg):
    data = base64.b64decode(m.group(2))
    open(f"embedded.{m.group(1)}", "wb").write(data)
    print("wrote embedded." + m.group(1), len(data))
```

Если файл нашёлся — прогоняй по нему весь пайплайн изображений.

## Шаг 4: metadata, CSS и entities

Ещё несколько каналов, которые легко пропустить:

- **`<metadata>`** — служебный тег для произвольного XML/текста; читается через `xmllint --xpath '//*[local-name()="metadata"]/text()'`.
- **CSS и SMIL.** Внутри `<style>` прячут комментарии и переменные, а в `<animate values="...">` — данные в значениях анимации.
- **XML-entities.** Данные могут быть закодированы как `&#102;&#108;&#97;&#103;` — раскрываются через `xmllint --noent`.
- **CDATA.** `<![CDATA[...]]>` скрывает содержимое от XML-парсеров.

Общий скрипт-обходчик соберёт комментарии, base64-подобные строки и длинные дробные числа за один прогон:

```python
import re, base64
svg = open("logo.svg", encoding="utf-8").read()
for m in re.findall(r'<!--(.*?)-->', svg, re.S):
    print("COMMENT:", m.strip()[:200])
for s in re.findall(r'[A-Za-z0-9+/]{24,}={0,2}', svg):
    try:
        dec = base64.b64decode(s)
        if all(32 <= b < 127 for b in dec):
            print("B64:", dec[:120])
    except Exception:
        pass
print("PATH NUMS:", re.findall(r'\.\d{5,}', svg)[:20])
```

## Шаг 5: XXE и SSRF — отдельный вектор

SVG — это XML, а значит, к нему применимы XML-атаки. Внешние сущности (**XXE**) позволяют читать файлы, а ссылки на внешние ресурсы — делать **SSRF** (запросы с сервера):

```xml
<?xml version="1.0"?>
<!DOCTYPE svg [<!ENTITY xxe SYSTEM "file:///etc/passwd">]>
<svg xmlns="http://www.w3.org/2000/svg"><text>&xxe;</text></svg>
```

```bash
$ grep -iE 'DOCTYPE|ENTITY|SYSTEM' image.svg
$ xmllint --noent image.svg 2>/dev/null | head -20
```

Если SVG загружается и обрабатывается сервером, это уже реальная уязвимость, а не CTF-трюк. Фиксируй такие находки отдельно от стеганографии.

## Шаг 6: подводные камни

- **`.svgz`** — это gzip-сжатый SVG. Если `head` показывает нечитаемые байты, проверь первые байты `\x1f\x8b` и распакуй.
- **Минифицированный SVG** — всё в одной строке; `grep` без `(?s)` не найдёт комментарий. Используй `xmllint --format`.
- **Entities вместо текста** — применяй `xmllint --noent`.
- **Namespace-префиксы** — тег может быть `<svg:metadata>`; учитывай префиксы в XPath.

## Шаг 7: пайплайн разбора и инструменты

SVG — самый «текстовый» из графических форматов, поэтому разбор почти всегда сводится к нормальному парсингу. Вот инструменты, которые нужны на каждом шаге:

| Инструмент | Команда | Назначение |
|---|---|---|
| `file` | `file x.svg` | SVG это или gzip (`.svgz`) |
| `xmllint` | `--format` | форматирование минифицированного файла |
| `xmllint` | `--noent` | раскрытие entities |
| `xmllint` | `--xpath` | выбор узла (`<metadata>`) |
| `grep` | `-ozP '(?s)<!--.*?-->'` | многострочные комментарии |
| `base64` | `-d` | декод `data:` URI и base64-строк |

Порядок такой: `file` → распаковка при необходимости → `xmllint --format` → поиск комментариев → поиск base64 и `data:` → `<metadata>` и entities → анализ длинных координат `path` → проверка CSS/SMIL и внешних ссылок. Такой проход закрывает и текстовые, и «числовые» каналы SVG за один заход.

Отдельно стоит помнить про безопасность при приёме SVG на сервере: запрещай `DOCTYPE`, фильтруй `<script>` и внешние ссылки — иначе получишь XXE, SSRF или XSS. Это тот редкий случай, когда «стеганография в формате» и «уязвимость формата» — две стороны одной монеты.

## Что мы теперь знаем

1. SVG — это текстовый XML, поэтому данные прячут прямо в разметке.
2. Комментарий `<!-- -->` может нести base64; извлекается через `grep -oP '(?s)<!--.*?-->'`.
3. Координаты `path` с лишней точностью кодируют биты в младших цифрах.
4. `data:` URI несёт вложенный растр — отдельный носитель.
5. `<metadata>`, CSS, SMIL, entities и CDATA — дополнительные каналы.
6. SVG — ещё и XML, поэтому к нему применимы XXE/SSRF.

## Мини-кейс: флаг в атрибуте id и в SMIL-анимации

Комментарии ищут все, поэтому в реальных задачах данные часто кладут туда, куда никто не смотрит. Возьмём файл без комментариев, зато с подозрительным `id` и анимацией:

```xml
<svg xmlns="http://www.w3.org/2000/svg" width="120" height="120">
  <rect id="ZmxhZ3tzdmdfaWQ1fQ==" width="120" height="120" fill="#eee"/>
  <animate attributeName="opacity" values="0.0000011;0.0000000;0.0000001;0.0000001"
           dur="1s" repeatCount="indefinite"/>
</svg>
```

Два канала: `id` — это base64 (`flag{svg_id5}`), а `values` анимации — те же «лишние цифры», что и в `path`. Разбираем оба:

```python
import re, base64
svg = open("anim.svg", encoding="utf-8").read()

# канал 1: base64 в любом атрибуте
for name, val in re.findall(r'(\w[\w:-]*)="([A-Za-z0-9+/]{12,}={0,2})"', svg):
    try:
        print("ATTR", name, "->", base64.b64decode(val))
    except Exception:
        pass

# канал 2: младшие цифры в values/координатах
bits = "".join(v[-1] for v in re.findall(r'\.(\d{5,})', svg))
print("BITS", bytes(int(bits[i:i+8], 2) for i in range(0, len(bits)-7, 8)))
```

```text
ATTR id -> b'flag{svg_id5}'
BITS b'flag{svg_smil}'
```

Приём работает по всем текстовым атрибутам: `id`, `class`, `values`, `d`, `fill`. Общее правило — любой длинный «странный» атрибут стоит декодировать как base64 или прочитать его младшие цифры.

## Справочная таблица: канал → сигнатура → извлечение

| Канал | Сигнатура в файле | Чем извлечь |
|-------|-------------------|-------------|
| Комментарий | `<!--` | `grep -ozP '(?s)<!--.*?-->'` |
| base64 в атрибуте | `[A-Za-z0-9+/]{16,}={0,2}` | `base64 -d` |
| `data:` URI | `data:image/…;base64,` | `base64 -d` → растр |
| path/SMIL-биты | `\.\d{5,}` | младшая цифра → биты |
| metadata | `<metadata>` | `xmllint --xpath` |
| entities | `&#\d+;` / `&name;` | `xmllint --noent` |
| CDATA | `<![CDATA[` | чтение текста |
| gzip-контейнер | `\x1f\x8b` | `gunzip` (`.svgz`) |

Таблица закрывает все текстовые каналы SVG: пройди по строкам сверху вниз — и один из них даст результат.

## Границы применимости SVG-стего

SVG — **текстовый** формат, поэтому данные в нём лежат почти открыто: комментарий, base64-строка, лишний атрибут. Это плюс (легко искать) и минус (легко обнаружить автоматическим грепом). Минификаторы (`svgo`) удаляют комментарии, схлопывают атрибуты и пересчитывают координаты — канал в `path` при этом исчезает. Сжатие в `.svgz` текст сохраняет (gzip сжимает, но не переписывает содержимое), поэтому данные выживают, если только файл не прошёл через оптимизатор. И помни: SVG-стего в CTF почти всегда простой — комментарий, base64 или вложенный файл, — и не требует статистического анализа, в отличие от растра.

## Практика: извлечение данных из SVG скриптом

SVG — текстовый XML, поэтому разбор начинается с обычного просмотра. Но осмысленные данные прячутся не в видимой части, а в комментариях, неиспользуемых атрибутах и координатах.

```bash
# 1) комментарии
grep -o '<!--.*-->' logo.svg

# 2) data:URI — декодируем base64
grep -o 'data:[^;]*;base64,[A-Za-z0-9+/=]*' logo.svg | cut -d, -f2 | base64 -d

# 3) «пустые» элементы и нестандартные атрибуты
xmllint --xpath '//@*' logo.svg 2>/dev/null | tr ' ' '\n' | sort -u

# 4) вся разметка как текст, ищем аномалии
python3 -c "import re;s=open('logo.svg').read();print(re.findall(r'[A-Za-z0-9+/=]{40,}',s))"
```

Второй канал — **координаты path**. Команды `d="M x y L x y ..."` содержат числа; их дробные части или младшие биты удобно использовать как битовый поток.

```python
import re
svg = open("logo.svg").read()
d = re.search(r'd="([^"]+)"', svg).group(1)
nums = re.findall(r'-?\d+\.\d+', d)          # берём дробные координаты

bits = []
for n in nums:
    frac = n.split(".")[1]
    bits.append(int(frac[-1]) & 1)            # младший бит дробной части

out = bytearray()
for i in range(0, len(bits) - 7, 8):
    b = 0
    for j in range(8):
        b = (b << 1) | bits[i + j]
    out.append(b)
print(bytes(out))
```

Порядок бит (MSB-first или LSB-first) — первое, что стоит проверить при «мусоре» на выходе: попробуйте оба варианта и сравните с ожидаемым префиксом флага.

## Каналы сокрытия в SVG

| Элемент/атрибут | Как прячут | Как найти |
|---|---|---|
| XML-комментарий | base64/ASCII прямо в `<!-- -->` | `grep -o '<!--.*-->'` |
| `d` (path) | LSB/дробная часть координат | парсинг чисел регуляркой |
| `data:` URI | вложенный растр/скрипт | `grep base64 | base64 -d` |
| неиспользуемые атрибуты | `id`, `data-*`, `xml:*` | `xmllint --xpath '//@*'` |
| `<metadata>` / RDF | произвольный XML | `xmllint --xpath '//metadata'` |
| CSS `style` | скрытые правила, `content:` | `grep -o 'style="[^"]*"'` |
| XML-entities | раскрытие сущностей (XXE) | разбор DTD |
| пустые `<text>`/`<title>` | невидимый текст | `grep -o '<text[^>]*>[^<]*'` |

## Инструменты

```bash
# рекурсивно распаковать вложенные data:URI
grep -o 'data:[^,]*,\([A-Za-z0-9+/=]*\)' logo.svg | while read l; do echo "$l" | base64 -d > out.bin; done
# проверить на XXE-уязвимость (осторожно, только на своём стенде)
xmllint --noent --debug logo.svg
```

`xmllint`, `xmlstarlet` и обычный `grep` покрывают большинство задач. Для вложенных растров удобно извлечь `data:URI`, декодировать и прогнать тем же пайплайном, что и обычную картинку (`zsteg`, `binwalk`).

## Краевые случаи

- **Минификация.** Генераторы убирают пробелы и переводы строк, поэтому не рассчитывайте на читаемый вид — ищите по паттернам, а не по строкам.
- **Сжатие.** Некоторые SVG хранят `data:gzip;base64,...` — декодируйте и распаковывайте.
- **Кодировки.** XML-entities (`&#x41;`) маскируют ASCII; раскрывайте их перед анализом.
- **Порядок чисел в path.** Команды `d` могут быть относительными (`m`, `l`) — абсолютные координаты восстанавливаются только после применения смещений.
- **Вложенность.** `<image>` внутри `<image>` с data:URI — проверяйте рекурсивно, пока не кончится.
