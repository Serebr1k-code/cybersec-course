## Вопрос, с которого всё начинается
Все знают JPEG, PNG и WebP. Но существует ещё **JPEG XR** (он же HD Photo) —
формат Microsoft, стандартизованный как ISO/IEC 29199. Он редко встречается в
вебе, но именно поэтому удобен как носитель: инструментов для него мало, а
структура позволяет прятать данные и в метаданных, и в коэффициентах. Ты получил
файл `image.jxr` — как в нём вообще ориентироваться?

## Наш пример
Возьмём `image.jxr` — контейнер в стиле TIFF. Мы разберём его заголовок, найдём
структуру тайлов и посмотрим, где в JPEG XR живут «лишние» поля, которые никто
не проверяет.

## Шаг 1: контейнер в стиле TIFF
JPEG XR использует контейнер IFD (Image File Directory), как TIFF: последовательность
тегов `[тег(2)][тип(2)][счётчик(4)][значение/смещение(4)]`. Первый байт файла —
порядок байт (`II` = little-endian, `MM` = big-endian), затем магическое число и
смещение на первый IFD.

```
$ xxd -l 32 image.jxr
00000000: 4949 bc01 0000 2000 0000 0000 0000 0000  II.... .........
00000010: 0000 0000 0000 0000 0000 0000 0000 0000  ................
```

`49 49` — little-endian. `bc 01` — версия кодека. Далее смещение на каталог тегов.

## Шаг 2: каталог тегов и полезные поля
В IFD нас интересуют теги:
- `0xBC01` — PixelFormat (тип пикселей, каналы, bit depth);
- `0xBC80` — ImageWidth, `0xBC81` — ImageHeight;
- `0xBC04` — ImageOffset (смещение на сжатые данные);
- `0xBC05` — AlphaOffset;
- пользовательские теги (0xBExx) — производитель вправе добавить свои.

Именно в произвольных тегах и «padding» между блоками прячут данные: парсеры
читают только известные теги и пропускают остальное.

## Шаг 3: тайлы и частотные полосы
Внутри сжатые данные разбиты на **тайлы** (tile) и **макро-блоки**. Коэффициенты
разложены по полосам: DC (постоянная составляющая), LP (low-pass), HP (high-pass)
и, при наличии альфы, отдельная плоскость. Каждая полоса — это уже готовая
структура для встраивания в младшие разряды коэффициентов.

## Шаг 4: чтение тега вручную
```python
import struct
d = open('image.jxr','rb').read()
end = '<' if d[:2] == b'II' else '>'
ifd = struct.unpack_from(end + 'I', d, 4)[0]
count = struct.unpack_from(end + 'H', d, ifd)[0]
p = ifd + 2
for _ in range(count):
    tag, typ, cnt, val = struct.unpack_from(end + 'HHII', d, p)
    print(hex(tag), typ, cnt, val)
    p += 12
```

Вывод на нашем файле:

```
0xbc01 1 1 12
0xbc80 4 1 512
0xbc81 4 1 512
0xbc04 4 1 4096
0xbeef 1 32 8192
```

Тег `0xbeef` — не стандартный. По смещению 8192 лежат 32 байта «мусора»,
которые на самом деле и есть наша закладка.

## Шаг 5: почему JPEG XR удобен как носитель
- **Мало инструментов.** `exiftool` читает базовые теги, но не пользовательские.
- **Сложная структура.** Тайлы, полосы, альфа-плоскость — много «свободного места».
- **Совместимость.** Формат открывается браузером/просмотрщиком, картинка видна,
  а данные — нет.

## Шаг 6: практические инструменты
- `exiftool image.jxr` — метаданные и теги.
- `jpegxr` / `JxrDecApp` (jpegxrlib) — декодер из пакета libjxr.
- `xxd`, `binwalk` — ручной разбор контейнера.

## Полный разбор контейнера JPEG XR

JPEG XR (ранее HD Photo) — формат Microsoft, контейнер которого устроен как TIFF. Начинается он с сигнатуры `II` (little-endian) или `MM` (big-endian), затем идёт магическое число `0xBC` и смещение на каталог тегов (IFD). Каталог — это последовательность записей: `[tag(2)][type(2)][count(4)][value/offset(4)]`.

```bash
xxd image.jxr | head -8
exiftool -v3 image.jxr | head -60
```

Каждый тег описывает свойство изображения: размеры, цветовое пространство, параметры тайлов, метаданные. Ключевая особенность — TIFF-подобная расширяемость: можно добавить собственный тег с произвольными данными, и стандартные просмотрщики его проигнорируют. Именно поэтому JPEG XR удобен как носитель стего.

Разбор ведут «от каталога»: сначала прочитать IFD, понять, какие теги есть, какие нестандартные, и что лежит по их смещениям. Инструменты: `exiftool` (читает многие теги), `tiffinfo` (если контейнер достаточно TIFF-подобен), `python3` + `struct` для ручного разбора. Если тег ссылается на данные за пределами ожидаемых размеров изображения — это и есть канал.

## Тайлы, частотные полосы и где прячут данные

JPEG XR кодирует изображение блоками — **тайлами** (tiles), которые делятся на частотные полосы (frequency bands). Структура тайлов описана в метаданных: размер тайла, число полос, их длины. Канал сокрытия — несоответствие заявленных длин полос и фактического потока: если после последней полосы есть «лишние» байты, там данные.

```text
container: II BC <offset-to-IFD>
IFD entry: tag | type | count | value/offset
tile: index -> bands -> entropy-coded data
```

Практически: найди в метаданных таблицу тайлов, вычисли конец последнего тайла и сравни с размером файла. Разница — overlay или скрытая полоса. Второй приём — избыточные тайлы: тайлов больше, чем нужно для заявленных размеров, и «лишние» несут данные. Третий — нестандартные частотные полосы: полоса с аномальной длиной или именем.

Для чтения конкретного тега вручную: возьми смещение из IFD, прочитай `count * sizeof(type)` байт и интерпретируй согласно типу (1=BYTE, 2=ASCII, 3=SHORT, 4=LONG). Так ты достанешь значение, которое не показывает `exiftool`.

## Практические инструменты и ограничения

Инструменты: `exiftool` (основной для тегов и метаданных), `xxd` (сырые байты), `binwalk` (поиск вложенного/дописанного), `python3`+`struct` (точный разбор IFD), `file`/`identify` (идентификация). Для генерации JPEG XR — `jxrlib`/`jpegxr`; это позволяет экспериментировать с каналами в контролируемой среде.

Ограничения: JPEG XR редко встречается «в дикой природе», поэтому задачи на него — скорее учебные. Стандартные просмотрщики могут вообще не открыть файл, поэтому проверка «открывается ли» бесполезна. `exiftool` читает не все теги, поэтому для полного разбора нужен ручной парсер IFD.

Практический вывод: JPEG XR — пример того, что контейнер важнее кодека. Даже если само сжатие сложное, метаданные (TIFF-подобный каталог) дают простой канал для сокрытия. При разборе любого незнакомого формата первым делом смотри, есть ли в нём расширяемый каталог метаданных — почти всегда есть, и почти всегда туда можно что-то дописать.

## Практика: читаем тег вручную

Разберём конкретный тег. Пусть в каталоге есть запись `tag=0x8000, type=1(BYTE), count=32, offset=0x120`. Это нестандартный тег: он ссылается на 32 байта по смещению `0x120`. Читаем их и проверяем, что там.

```python
import struct
d = open("image.jxr","rb").read()
assert d[:2] == b"II"          # little-endian TIFF-подобный
ifd_off = struct.unpack_from("<I", d, 4)[0]
n = struct.unpack_from("<H", d, ifd_off)[0]
for i in range(n):
    base = ifd_off + 2 + i*12
    tag, typ, cnt, val = struct.unpack_from("<HHII", d, base)
    print(hex(tag), typ, cnt, hex(val))
```

Если тег нестандартный и его данные содержат читаемый текст или флаг — это канал. Именно так разбирают JPEG XR вручную, когда `exiftool` не показывает нужный тег.

## Сравнение с TIFF и защита

JPEG XR наследует TIFF-структуру каталога, но не все TIFF-инструменты его понимают (другой кодек). Поэтому для метаданных используй `exiftool`, а для структуры — ручной парсер. Защита от сокрытия в JPEG XR — та же, что и для любых контейнеров с расширяемыми метаданными: нормализовать файл (пере-сохранить без лишних тегов), проверять нестандартные теги и аномальные размеры, валидировать структуру.

Практический вывод: любой формат с каталогом метаданных (TIFF, JPEG XR, PNG-чанки, HEIF-боксы) даёт канал сокрытия. Поэтому при форензике проверяют не только пиксели, но и метаданные — часто именно там лежит ответ.

## Расширенный разбор: JPEG XR как носитель

JPEG XR — редкий формат, но показательный: контейнер устроен как TIFF, с каталогом тегов (IFD). Это значит, что к нему применимы все приёмы TIFF-стего: нестандартные теги, данные по смещению тега, лишние записи в каталоге.

Разбор: прочитать заголовок (`II`/`MM`, магия `0xBC`, смещение IFD), затем IFD — последовательность записей `[tag][type][count][value/offset]`. Для каждого тега понять, стандартный он или нет, и что лежит по смещению. Нестандартный тег с читаемыми данными — канал.

```python
import struct
d = open("image.jxr","rb").read()
off = struct.unpack_from("<I", d, 4)[0]
n = struct.unpack_from("<H", d, off)[0]
for i in range(n):
    t,ty,c,v = struct.unpack_from("<HHII", d, off+2+i*12)
    print(hex(t), ty, c, hex(v))
```

Помимо тегов, каналы — тайлы (блоки кодирования): лишние тайлы, нестандартные частотные полосы, данные после последнего тайла. Сравни вычисленный конец данных с размером файла.

## Итог по JPEG XR

JPEG XR = TIFF-подобный контейнер + собственный кодек. Каналы: нестандартные теги, данные по смещениям, лишние тайлы/полосы, overlay. Инструменты: `exiftool`, `xxd`, `python3`+`struct`, `binwalk`. Урок общий: контейнер важнее кодека — расширяемые метаданные дают простой канал независимо от сложности сжатия.

## Что мы теперь знаем
- JPEG XR — TIFF-подобный контейнер с каталогом тегов (IFD).
- Данные прячут в нестандартных тегах, padding и младших разрядах коэффициентов.
- Малоинструментальность формата — сама по себе защита закладки.
- Разбор начинается с порядка байт и смещения на первый IFD.
