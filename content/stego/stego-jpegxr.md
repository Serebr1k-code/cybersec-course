## Вопрос, с которого всё начинается
Все знают JPEG, PNG и WebP. Но существует ещё **JPEG XR** (он же HD Photo) —
формат Microsoft, стандартизованный как ISO/IEC 29199. Он редко встречается в
вебе, но именно поэтому удобен как носитель: инструментов для него мало, а
структура позволяет прятать данные и в метаданных, и в коэффициентах. Ты получил
файл `image.jxr` — как в нём вообще ориентироваться?

## Наш пример
Возьмём `image.jxr` — контейнер в стиле TIFF. Мы разберём его заголовок, найдём
структуру тайлов и посмотрим, где в JPEG XR живут «лишние» поля, которые никто
не проверяет.

## Шаг 1: контейнер в стиле TIFF
JPEG XR использует контейнер IFD (Image File Directory), как TIFF: последовательность
тегов `[тег(2)][тип(2)][счётчик(4)][значение/смещение(4)]`. Первый байт файла —
порядок байт (`II` = little-endian, `MM` = big-endian), затем магическое число и
смещение на первый IFD.

```
$ xxd -l 32 image.jxr
00000000: 4949 bc01 0000 2000 0000 0000 0000 0000  II.... .........
00000010: 0000 0000 0000 0000 0000 0000 0000 0000  ................
```

`49 49` — little-endian. `bc 01` — версия кодека. Далее смещение на каталог тегов.

## Шаг 2: каталог тегов и полезные поля
В IFD нас интересуют теги:
- `0xBC01` — PixelFormat (тип пикселей, каналы, bit depth);
- `0xBC80` — ImageWidth, `0xBC81` — ImageHeight;
- `0xBC04` — ImageOffset (смещение на сжатые данные);
- `0xBC05` — AlphaOffset;
- пользовательские теги (0xBExx) — производитель вправе добавить свои.

Именно в произвольных тегах и «padding» между блоками прячут данные: парсеры
читают только известные теги и пропускают остальное.

## Шаг 3: тайлы и частотные полосы
Внутри сжатые данные разбиты на **тайлы** (tile) и **макро-блоки**. Коэффициенты
разложены по полосам: DC (постоянная составляющая), LP (low-pass), HP (high-pass)
и, при наличии альфы, отдельная плоскость. Каждая полоса — это уже готовая
структура для встраивания в младшие разряды коэффициентов.

## Шаг 4: чтение тега вручную
```python
import struct
d = open('image.jxr','rb').read()
end = '<' if d[:2] == b'II' else '>'
ifd = struct.unpack_from(end + 'I', d, 4)[0]
count = struct.unpack_from(end + 'H', d, ifd)[0]
p = ifd + 2
for _ in range(count):
    tag, typ, cnt, val = struct.unpack_from(end + 'HHII', d, p)
    print(hex(tag), typ, cnt, val)
    p += 12
```

Вывод на нашем файле:

```
0xbc01 1 1 12
0xbc80 4 1 512
0xbc81 4 1 512
0xbc04 4 1 4096
0xbeef 1 32 8192
```

Тег `0xbeef` — не стандартный. По смещению 8192 лежат 32 байта «мусора»,
которые на самом деле и есть наша закладка.

## Шаг 5: почему JPEG XR удобен как носитель
- **Мало инструментов.** `exiftool` читает базовые теги, но не пользовательские.
- **Сложная структура.** Тайлы, полосы, альфа-плоскость — много «свободного места».
- **Совместимость.** Формат открывается браузером/просмотрщиком, картинка видна,
  а данные — нет.

## Шаг 6: практические инструменты
- `exiftool image.jxr` — метаданные и теги.
- `jpegxr` / `JxrDecApp` (jpegxrlib) — декодер из пакета libjxr.
- `xxd`, `binwalk` — ручной разбор контейнера.

## Что мы теперь знаем
- JPEG XR — TIFF-подобный контейнер с каталогом тегов (IFD).
- Данные прячут в нестандартных тегах, padding и младших разрядах коэффициентов.
- Малоинструментальность формата — сама по себе защита закладки.
- Разбор начинается с порядка байт и смещения на первый IFD.
