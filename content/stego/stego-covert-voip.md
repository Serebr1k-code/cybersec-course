VoIP — голос поверх IP: поток разбивается на пакеты RTP, которые идут через сеть с почти постоянным интервалом. Это создаёт несколько слоёв для сокрытия: служебные поля RTP, поле LACK (для обратной связи по потерям), вариации джиттера, длительность пауз в разговоре и даже сам голосовой кодек. Голосовой трафик терпим к небольшим искажениям, поэтому модификации редко замечаются пользователем.

## RTP и где в нём прячут данные

Заголовок RTP содержит: версию, padding, extension, CSRC count, marker, payload type, sequence number, timestamp, SSRC и список CSRC.

Каналы сокрытия:

- **Sequence number.** 16 бит на пакет; нарушение порядка детектируется, но малые модуляции возможны.
- **Timestamp.** 32 бита; инкремент обычно кратен размеру сэмпла — отклонения кодируют данные.
- **SSRC.** 32 бита идентификатора потока — можно закодировать часть сообщения.
- **Marker bit / padding.** Свободные биты.
- **CSRC list.** Дополнительные идентификаторы, редко проверяются.
- **Extension header.** Расширения RTP — произвольные данные.
- **LACK (RFC 5166).** Обратная связь по потерям: поля можно переиспользовать как канал.

## Инструменты и команды

- **`tshark`** — разбор RTP и SIP, вывод полей.
- **`scapy`** — сборка RTP-пакетов.
- **`sox`/`ffmpeg`** — работа с декодированным аудио.
- **`sipdump`**, **`wireshark`** — анализ VoIP-сессий.
- **`pcap2wav`** — восстановление аудио из RTP.

Показать RTP-поток:

```bash
tshark -r voip.pcap -Y "rtp" -T fields \
  -e ip.src -e rtp.seq -e rtp.timestamp -e rtp.ssrc -e rtp.marker
```

Найти SIP-сессию (кто с кем и какие кодеки):

```bash
tshark -r voip.pcap -Y "sip" -T fields -e sip.Method -e sip.From -e sip.To
```

## Разобранный пример: данные в SSRC

Пусть разные SSRC-значения несут по 4 байта:

```bash
$ tshark -r voip.pcap -Y rtp -T fields -e rtp.ssrc | uniq
0x666c6167
0x7b7274705f
```

Соберём байты:

```python
vals = ["666c6167", "7b7274705f"]
out = b"".join(bytes.fromhex(v) for v in vals)
print(out.decode(errors="replace"))
```

## Джиттер и паузы

Сеть не гарантирует идеально равномерный поток: задержки варьируются. Но когда вариации становятся **бимодальными** (две явные группы задержек), это может быть тайминговым каналом: короткая пауза = `0`, длинная = `1`. Аналогично длительные паузы в разговоре (молчание) могут нести биты.

Проверить интервалы:

```bash
tshark -r voip.pcap -Y rtp -T fields -e frame.time_delta | head -20
```

## Сокрытие в кодеке

Кодек (G.711, G.729, Opus) сжимает голос. Методы стеганографии на уровне кодека:

- **LSB в декодированных сэмплах** (для несжатых, G.711/PCM).
- **Модуляция параметров кодека** (выбор задержки LPC, квантование — G.729).
- **Подмена намеренно «тихих» кадров** — данные в паузах.

Для G.711 (μ-law/A-law) полезен подход «декодировать → LSB → закодировать обратно».

## LACK как канал

LACK (Loss Acknowledgment, RFC 5166) — расширение RTP для обратной связи по потерям. Формат LACK-пакетов менее жёстко проверяется, а поля `packet loss rate`, `bitmask of lost packets` можно переиспользовать для передачи данных. В CTF LACK встречается как «экзотический» канал — ищите RTP с payload type, не совпадающим с обычным аудио, и полями, похожими на ASCII.

## Обнаружение и анализ

1. `tshark -z io,phs` — есть ли RTP/SIP вообще.
2. SIP-диалог: `-Y sip` — кодеки и адреса.
3. RTP-поля: `rtp.ssrc`, `rtp.timestamp` — на ASCII/аномалии.
4. Джиттер: `frame.time_delta` — бимодальность.
5. Декодировать аудио (`pcap2wav`) и прогнать обычный аудио-пайплайн.

```bash
tshark -r voip.pcap -Y rtp -T fields -e rtp.payload | head
```

## Частые ошибки и подводные камни

- **Считать RTP «просто аудио».** Заголовок RTP — отдельный канал.
- **Игнорировать SSRC/timestamp.** Там чаще всего и лежит сообщение.
- **Пропустить джиттер.** Если поля чистые — смотрите интервалы.
- **Не декодировать аудио.** Флаг может быть в самом голосе.
- **Путать RTP и SIP.** SIP — сигнализация, RTP — медиапоток.
- **Забыть про несколько потоков.** Разговор = два RTP-потока.

## Таблица каналов в VoIP

| Канал | Ёмкость | Заметность | Комментарий |
|---|---|---|---|
| SSRC | 4 байта/поток | низкая | удобно для заголовка сообщения |
| Timestamp | ~биты/пакет | средняя | ломает синхронизацию при грубости |
| Sequence | ~биты/пакет | средняя | нарушение порядка заметно |
| Extension header | десятки байт | низкая | редко валидируется |
| Джиттер/паузы | 1 бит/интервал | очень низкая | медленно |
| Кодек (LSB) | зависит от кодека | низкая | требует декодирования |

## Что дальше / решение

- Проверьте наличие RTP/SIP: `tshark -z io,phs`.
- Разберите `rtp.ssrc`/`rtp.timestamp` на ASCII.
- Оцените джиттер (`frame.time_delta`) на бимодальность.
- Декодируйте аудио (`pcap2wav`) и примените аудио-пайплайн.
- Если пусто — ищите LACK и нестандартные payload type.

## SIP как отдельный канал

SIP — сигнальный протокол VoIP: он устанавливает, изменяет и завершает сессии, а также передаёт метаданные (кодеки, адреса, имена). SIP текстовый, похож на HTTP, и это делает его удобным носителем: произвольные заголовки (`X-*`), поля `Via`, `Contact`, `User-Agent` можно набивать данными.

```bash
tshark -r voip.pcap -Y "sip" -T fields -e sip.From -e sip.User-Agent -e sip.rport | head
```

Типичное место сокрытия — параметры `Via`/`Contact` (там длинные строки) и кастомные заголовки. Для извлечения декодируйте base64/hex из подозрительных значений.

## Голосовые кодеки и их уязвимость к стего

Разные кодеки дают разную «свободу» для сокрытия:

- **G.711 (PCM, A-law/μ-law)** — несжатый, 64 Кбит/с; LSB в сэмплах работает напрямую.
- **G.729** — параметрический, 8 Кбит/с; данные прячут в параметрах квантования.
- **Opus/AMR** — современные, с переменным битрейтом; можно модулировать выбор режима.
- **Silence suppression (DTX/CN)** — паузы кодируются CN-пакетами; в них удобно прятать данные.

Для G.711 путь такой: декодировать RTP-payload в PCM, применить LSB-извлечение, собрать байты. Пакет `pcap2wav` восстанавливает WAV из RTP, после чего работает обычный аудио-пайплайн.

```bash
pcap2wav -r voip.pcap -f out.wav
sox out.wav -n spectrogram -o spec.png
```

## RTP: разбор полей

Заголовок RTP минимален (12 байт), но каждое поле — потенциальный канал:

- **V, P, X, CC** — версия, padding, extension, число CSRC.
- **M** — marker bit.
- **PT** — payload type (7 бит).
- **Seq** — 16 бит.
- **Timestamp** — 32 бита.
- **SSRC** — 32 бита.
- **CSRC list** — до 15 идентификаторов.

Extension header (`X=1`) добавляет произвольные данные — это самый удобный канал, поскольку его содержимое задаёт приложение.

## Джиттер-буфер как канал

Приёмник VoIP использует джиттер-буфер: он задерживает воспроизведение, компенсируя неравномерность сети. Размер буфера и моменты его изменения можно использовать как канал: серия «буфер расширяется/сужается» кодирует биты. На стороне анализа это видно как корреляции между задержками и последующим поведением.

## Готовые инструменты и флаги

- **`tshark`**: `-Y rtp`, `-e rtp.ssrc`, `-e rtp.timestamp`, `-z rtp,streams`.
- **`sipdump`**: `-i` (интерфейс), `-o` (вывод) — перехват SIP-сессий.
- **`pcap2wav`**: `-r` (pcap), `-f` (wav) — восстановление аудио.
- **`sox`**: `spectrogram`, `stat` — спектр и статистика.
- **`oreka`/`voiphopper`** — анализ и VLAN-hopping VoIP.

```bash
tshark -r voip.pcap -z rtp,streams -q | head
```

Команда покажет все RTP-потоки, их SSRC и статистику потерь — с неё стоит начинать разбор.

## Практический чек-лист VoIP-задачи

1. `tshark -z io,phs` — есть ли RTP/SIP.
2. `tshark -Y sip` — восстановить диалог и кодеки.
3. `tshark -Y rtp -e rtp.ssrc -e rtp.timestamp` — поля на ASCII/аномалии.
4. `pcap2wav` → `sox spectrogram` — аудио-пайплайн.
5. `frame.time_delta` — джиттер на бимодальность.
6. Проверить extension header и CSRC.

Если все шаги пусты, вероятно, канал в самом кодеке (модуляция параметров) — это уже исследовательский уровень.
