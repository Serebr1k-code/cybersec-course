## Вопрос, с которого всё начинается

В задаче дан `voip.pcap` — запись разговора по IP-телефонии. Ты восстанавливаешь аудио и слушаешь: обычная речь, ничего лишнего. Но флаг точно где-то есть. Как разговор может нести данные, если сами звуки чистые?

Ответ: в **служебных полях RTP** и в таймингах голосовых пакетов. Голосовой трафик терпим к небольшим искажениям, поэтому модификации почти не замечаются. Разберём это на нашем pcap.

## Наш пример: voip.pcap

**VoIP** — голос поверх IP. Поток разбивается на пакеты **RTP** (Real-time Transport Protocol), которые идут через сеть с почти постоянным интервалом. Отдельно есть **SIP** — сигнализация (кто кому звонит, какие кодеки).

Заголовок RTP содержит: версию, padding, marker, **payload type**, **sequence number**, **timestamp**, **SSRC** и список CSRC. Начнём с обзора потоков:

```bash
$ tshark -r voip.pcap -z rtp,streams -q | head
Streams: 2
  SSRC=0x666c6167  packets=1024
  SSRC=0x7b7274705f  packets=990
```

`-z rtp,streams` показывает все RTP-потоки, их SSRC и статистику. Значения SSRC выглядят как ASCII — это первый сигнал.

## Шаг 1: данные в SSRC

**SSRC** — 32-битный идентификатор потока, в норме случайный. Соберём значения:

```bash
$ tshark -r voip.pcap -Y rtp -T fields -e rtp.ssrc | uniq
0x666c6167
0x7b7274705f
```

Преобразуем hex в байты:

```python
vals = ["666c6167", "7b7274705f"]
out = b"".join(bytes.fromhex(v) for v in vals)
print(out.decode(errors="replace"))
```

```bash
$ python3 ssrc.py
flag{rtp_
```

Половина флага в SSRC. Другая часть может быть в `timestamp` или в extension-заголовке.

## Шаг 2: SIP как отдельный канал

SIP текстовый, похож на HTTP, и это делает его удобным носителем: произвольные заголовки (`X-*`), поля `Via`, `Contact`, `User-Agent` можно набивать данными.

```bash
$ tshark -r voip.pcap -Y "sip" -T fields -e sip.From -e sip.User-Agent | head
```

Типичное место сокрытия — параметры `Via`/`Contact` (там длинные строки) и кастомные заголовки. Декодируй base64/hex из подозрительных значений.

## Шаг 3: джиттер и паузы

Сеть не гарантирует равномерный поток: задержки варьируются. Но когда вариации становятся **бимодальными** (две явные группы задержек), это может быть тайминговым каналом: короткая пауза = `0`, длинная = `1`.

```bash
$ tshark -r voip.pcap -Y rtp -T fields -e frame.time_delta | head -20
```

Аналогично длительные паузы в разговоре (молчание, кодируемое CN-пакетами) могут нести биты.

## Шаг 4: сокрытие в кодеке

**Кодек** — алгоритм сжатия голоса. Разные кодеки дают разную «свободу» для сокрытия:

- **G.711** (PCM, несжатый) — LSB в сэмплах работает напрямую;
- **G.729** — параметрический; данные прячут в параметрах квантования;
- **Opus/AMR** — можно модулировать выбор режима;
- **Silence suppression** — данные в CN-пакетах пауз.

Путь для G.711: декодировать RTP-payload в PCM, применить LSB-извлечение. Инструмент `pcap2wav` восстанавливает WAV из RTP:

```bash
$ pcap2wav -r voip.pcap -f out.wav
$ sox out.wav -n spectrogram -o spec.png
```

Дальше работает обычный аудио-пайплайн.

## Шаг 5: LACK как канал

**LACK** (Loss Acknowledgment, RFC 5166) — расширение RTP для обратной связи по потерям. Его поля (`packet loss rate`, `bitmask of lost packets`) менее жёстко проверяются и их можно переиспользовать для данных. В CTF LACK встречается как экзотический канал — ищите RTP с payload type, не совпадающим с обычным аудио.

## Шаг 6: чек-лист и детект

1. `tshark -z io,phs` — есть ли RTP/SIP;
2. `tshark -Y sip` — восстановить диалог и кодеки;
3. `tshark -Y rtp -e rtp.ssrc -e rtp.timestamp` — поля на ASCII;
4. `pcap2wav` → `sox spectrogram` — аудио-пайплайн;
5. `frame.time_delta` — джиттер на бимодальность;
6. проверить extension header и CSRC.

## Сквозной разбор: SSRC в настоящем pcap

Соберём pcap с RTP-пакетами, у которых SSRC кодирует ASCII, и прочитаем его через `tshark`. RTP-заголовок — 12 байт: `V/P/X/CC`, `M/PT`, `Seq` (16 бит), `Timestamp` (32 бита), `SSRC` (32 бита):

```python
import struct
from scapy.all import Ether, IP, UDP, Raw, wrpcap
pkts=[]
for i,ssrc in enumerate([0x666c6167, 0x7b727470]):   # "flag", "{rtp"
    hdr = struct.pack("!BBHII", 0x80, 0x00, i, 160*i, ssrc)
    pkts.append(Ether()/IP(src="10.0.0.9",dst="10.0.0.1")/UDP(sport=5004,dport=5004)/Raw(load=hdr+b"\x00"*160))
wrpcap("voip.pcap", pkts)
```

UDP-порт 5004 не опознаётся как RTP автоматически — говорим `tshark` декодировать его как RTP:

```bash
$ tshark -r voip.pcap -d udp.port==5004,rtp -Y rtp -T fields -e rtp.ssrc | uniq
0x666c6167
0x7b727470
$ python3 -c "print(bytes.fromhex('666c6167')+bytes.fromhex('7b727470'))"
b'flag{rtp'
```

`-z rtp,streams` покажет то же самое таблицей — SSRC, кодек (`g711U`), число пакетов, джиттер.

Тонкость: **SSRC — ровно 32 бита**, то есть 4 байта или 8 hex-символов. Значение вида `0x7b7274705f` (10 символов) физически не помещается в поле — если видишь такое «в задании», это либо склейка двух полей, либо ошибка. Полное сообщение собирают из нескольких 4-байтовых SSRC разных потоков.

## Если не сработало

- **Считаешь RTP «просто аудио»** — заголовок RTP отдельный канал.
- **Игнорируешь SSRC/timestamp** — там чаще всего и лежит сообщение.
- **Пропустил джиттер** — если поля чистые, смотри интервалы.
- **Не декодировал аудио** — флаг может быть в самом голосе.
- **Путаешь RTP и SIP** — SIP сигнализация, RTP медиапоток.
- **Забыл про два потока** — разговор = два RTP-потока.

## Таблица каналов в VoIP

| Канал | Ёмкость | Заметность | Комментарий |
|---|---|---|---|
| SSRC | 4 байта/поток | низкая | удобно для заголовка сообщения |
| Timestamp | ~биты/пакет | средняя | ломает синхронизацию при грубости |
| Sequence | ~биты/пакет | средняя | нарушение порядка заметно |
| Extension header | десятки байт | низкая | редко валидируется |
| Джиттер/паузы | 1 бит/интервал | очень низкая | медленно |
| Кодек (LSB) | зависит от кодека | низкая | требует декодирования |

## RTP: разбор полей

Заголовок RTP минимален (12 байт), но каждое поле — потенциальный канал: `V, P, X, CC` (версия, padding, extension, число CSRC), `M` (marker), `PT` (payload type, 7 бит), `Seq` (16 бит), `Timestamp` (32 бита), `SSRC` (32 бита), `CSRC list` (до 15 идентификаторов). Extension header (`X=1`) добавляет произвольные данные — самый удобный канал, поскольку его содержимое задаёт приложение.

## Готовые инструменты

- **`tshark`**: `-Y rtp`, `-e rtp.ssrc`, `-z rtp,streams`;
- **`sipdump`**: `-i` (интерфейс), `-o` (вывод) — перехват SIP-сессий;
- **`pcap2wav`**: `-r` (pcap), `-f` (wav) — восстановление аудио;
- **`sox`**: `spectrogram`, `stat` — спектр и статистика.

## Что мы теперь знаем

1. Голос идёт в **RTP**-пакетах; **SIP** — сигнализация.
2. **SSRC**, **timestamp**, **extension header** — каналы в заголовке RTP.
3. **Джиттер** и паузы кодируют биты.
4. **Кодек** (G.711 LSB, параметры G.729) — канал в самом голосе.
5. `pcap2wav` + `sox` подключают обычный аудио-пайплайн.
