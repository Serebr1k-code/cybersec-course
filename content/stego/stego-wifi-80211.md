## Вопрос, с которого всё начинается

Тебе дали `frame.bin` — один кадр Wi-Fi (802.11). В эфире постоянно летают такие
кадры: beacon, probe, data. Где в них прячут сообщения? Wi-Fi устроен как набор
«тегов», и один из них — vendor-specific — предназначен для произвольных данных.
С него и начнём, но сначала разберём кадр целиком.

## Наш пример: файл frame.bin

```bash
xxd frame.bin
```

```text
00000000: 8000 0000 0000 0000 0000 0000 0000 0000  ................
00000010: 0000 0000 0000 0000 0000 0000 0003 6c61  ..............la
00000020: 62dd 116e 746f 7b77 3166 315f 3165 5f66  b..nto{w1f1_1e_f
00000030: 6c34 677d                                l4g}
```

Первые 24 байта — заголовок кадра (в нашем случае management-кадр). Дальше идут
теги: `00 03 6c 61 62` — SSID «lab», и `dd 11 ...` — vendor-specific IE с флагом.

## Шаг 1: структура кадра 802.11

Кадр 802.11 начинается с **MAC-заголовка** (обычно 24 байта):

- **Frame Control** (2 байта): версия, тип, подтип, флаги.
- **Duration/ID** (2 байта).
- **Address 1/2/3** (по 6 байт): MAC-адреса (получатель, отправитель, BSSID).
- **Sequence Control** (2 байта).

После заголовка у management-кадров идут **information elements (IE)** — «теги».
Каждый IE устроен как:

```
[ id(1) ][ длина(1) ][ данные ]
```

## Шаг 2: типы information elements

| ID | Значение |
|---|---|
| 0 | SSID (имя сети) |
| 1 | Supported Rates |
| 3 | DS Parameter (канал) |
| 48 | RSN (параметры безопасности) |
| 221 | Vendor Specific |

**ID 221 (0xDD)** — vendor-specific. Первые 3 байта — OUI (идентификатор
производителя), дальше — что угодно. Сканеры показывают их как «unknown». Это
прямой аналог manufacturer data в BLE.

## Шаг 3: разбираем IE вручную

```bash
python3 - <<'PY'
d = open('frame.bin','rb').read()
i = 24   # пропускаем MAC-заголовок
while i + 2 <= len(d):
    eid = d[i]
    ln = d[i+1]
    data = d[i+2:i+2+ln]
    print(eid, data)
    i += 2 + ln
PY
```

```text
0 b'lab'
221 b'nto{w1f1_1e_fl4g}'
```

SSID — «lab», а vendor-specific IE несёт флаг. Достали.

## Шаг 4: где ещё прячут в 802.11

- **SSID** — имя сети может быть длинной строкой с данными (часто до 32 байт).
- **Supported Rates / Extended Rates** — список скоростей можно переставлять.
- **Порядок IE** — перестановочный канал (спецификация порядок не фиксирует).
- **Поля MAC-заголовка** — Duration, Sequence Control можно модулировать.
- **Паддинг** — неиспользуемые байты в конце кадра.
- **Скрытые SSID** — пустой SSID тоже несёт информацию (нулевая длина).

## Шаг 5: инструменты

```bash
aircrack-ng -w list capture.pcap      # анализ
tshark -r capture.pcap -V             # разбор кадров
wireshark                             # визуальный разбор
iw dev wlan0 scan | grep SSID         # сканирование
```

Wireshark разбирает IE человекочитаемо; `tshark -V` печатает все теги. Но для CTF
ручной парсер надёжнее: он покажет и нестандартные, и «битые» IE.

## Шаг 6: почему Wi-Fi удобен для стеганографии

Wi-Fi-кадры широковещательны (beacon виден всем), а vendor-specific IE легален и не
проверяется. Более того, порядок IE спецификацией не зафиксирован — значит, даже
перестановка легальных тегов может нести данные. Получается «открытый канал»,
неотличимый от обычной сети.

## Шаг 7: частые ошибки

Первая — неверно определить длину MAC-заголовка: у data-кадров он может быть 24 или
30 байт (с QoS), а у management — 24. Вторая — забыть про FCS (4 байта контрольной
суммы в конце), которые могут попасть в последний IE. Третья — путать кадры разных
типов (management/data/control) — IE есть только у management и части data. Четвёртая —
считать, что SSID всегда есть: у скрытых сетей он нулевой длины.

## Типы и подтипы кадров 802.11

802.11 делит кадры на три типа, и это важно, потому что structure отличается:

- **Management** (type 0): beacon, probe request/response, association. Именно здесь
  больше всего information elements.
- **Control** (type 1): RTS, CTS, ACK — короткие, служебные.
- **Data** (type 2): сами данные; тоже могут нести IE (например, QoS).

В Frame Control (первые 2 байта) закодированы тип и подтип. Например, `80 00` —
это management/beacon. Если дать тебе кадр, первым делом посмотри на эти байты,
чтобы понять, есть ли там вообще IE.

## Практика: разбор pcap через tshark

Реальные захваты Wi-Fi сохраняются в pcap/pcapng. Разберём без Wireshark:

```bash
tshark -r capture.pcap -Y 'wlan.fc.type==0' -T fields \
  -e wlan.ssid -e wlan.tag.number -e wlan.tag.length | head
```

Это выведет SSID и список IE. Если увидишь тег 221 (vendor specific) с длинным
значением — это кандидат. Можно выгрузить конкретное поле:

```bash
tshark -r capture.pcap -Y 'wlan.tag.number==221' -T fields -e wlan.tag.oui -e data
```

Дальше декодируй `data` из hex. Ручной парсер (как в примере) удобнее, когда кадр
нестандартный и `tshark` не разбирает его до конца.

## Скрытые сети и пустой SSID

Интересный случай — сеть со скрытым SSID. В beacon-кадре SSID присутствует, но
нулевой длины: тег `00 00`. Это уже «информация»: имя сети не показывается. В
стеганографии пустой SSID используют как признак или как место: за ним можно
добавить «лишние» IE, которые никто не проверяет.

Ещё один приём — **SSID из непечатаемых символов**: имя выглядит «пустым», но несёт
байты. Такие сети встречаются в CTF как раз потому, что их не видно в списке сетей.

## Итоговая стратегия для Wi-Fi

Определи тип/подтип кадра по Frame Control; если management — обойди IE; ищи тег 221
(vendor specific), тег 0 (SSID) и вообще все «странные» теги; проверь порядок IE;
декодируй найденные байты. Если кадров много — используй `tshark` с фильтром по
тегам. И помни про FCS в конце: 4 байта контрольной суммы могут «съесть» последний IE.

## Как отличить закладку от штатных IE

Wi-Fi-кадры содержат десятки легальных IE: supported rates, RSN, country, vendor
specific от реальных производителей (Apple, Microsoft, Cisco). Поэтому «тег 221» сам
по себе не аномалия. На что смотреть:

- **OUI.** Первые 3 байта vendor IE — идентификатор производителя. Если OUI
  `00:00:00` или несуществующий — это не настоящий вендор, а подделка.
- **Содержимое.** ASCII-текст, base64 или сигнатура флага внутри vendor IE.
- **Длина.** Vendor IE необычно большой для своего OUI.
- **Дубли.** Несколько одинаковых vendor IE подряд — признак ручной правки.

Практический приём: сравни beacon-кадры одной сети. Настоящие IE стабильны, закладка
может отличаться или быть «лишней».

## Практика: ручной разбор без tshark

Если нет pcap, а есть только hex-дамп кадра, разбор делается вручную:

```bash
python3 - <<'PY'
d = bytes.fromhex('8000000000000000000000000000000000000000000000000000000000036c6162dd116e746f7b773166315f31655f666c34677d')
i = 24
while i + 2 <= len(d):
    eid = d[i]; ln = d[i+1]
    print(eid, d[i+2:i+2+ln])
    i += 2 + ln
PY
```

Такой скрипт показывает все IE и их содержимое. Это тот же парсер, что и в примере,
но с кадром, заданным hex-строкой — удобно для CTF, где кадр дан в тексте.

## Почему Wi-Fi-закладки сложно найти

Wi-Fi-трафик огромен: в эфире постоянно летают тысячи кадров от десятков сетей.
Закладка в одном vendor IE одного beacon-кадра теряется в этом потоке. Более того,
спецификация разрешает производителям любые vendor IE, поэтому наличие «странного»
тега не считается ошибкой. Именно поэтому защитные системы редко анализируют
содержимое IE: они смотрят на SSID, канал и безопасность, а не на байты внутри тегов.
Для стеганографии это идеальные условия: канал широковещательный, легальный и
непроверяемый. В CTF это отражается в задачах вида «дан pcap с одной сетью, найди
сообщение» — решение всегда в тегах.

## Что мы теперь знаем

- Кадр 802.11 = MAC-заголовок (24 байта) + information elements.
- IE: `id + длина + данные`; ID 221 — vendor-specific.
- SSID, vendor IE, порядок IE и поля заголовка — каналы сокрытия.
- FCS (4 байта) в конце может мешать парсеру.
- Инструменты: Wireshark, `tshark`, `aircrack-ng`.
