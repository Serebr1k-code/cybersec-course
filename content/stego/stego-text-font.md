## Вопрос, с которого всё начинается

В CTF дали два PDF-файла: `doc_v1.pdf` и `doc_v2.pdf`. Текст в них **идентичный** — построчно совпадает. Подсказка: «различие есть, но не в словах». Где искать разницу между двумя одинаковыми документами?

**Типографика** — это слой между текстом и его отображением, и он полон «настраиваемых» величин: расстояние между парами букв (кернинг), общий трекинг, выбор лигатур, альтернативные глифы, оси вариативных шрифтов. Все эти параметры можно слегка варьировать, не меняя смысл текста, — а значит, использовать как канал. Разберём два наших файла.

## Наш пример: doc_v1.pdf и doc_v2.pdf

Сначала убеждаемся, что перед нами действительно PDF, а не что-то другое:

```bash
$ file doc_v1.pdf doc_v2.pdf
doc_v1.pdf: PDF document, version 1.7
doc_v2.pdf: PDF document, version 1.7
```

Текст совпадает. Значит, смотреть надо не в текст, а в **геометрию** — где именно на странице стоит каждый символ. Обычный `pdftotext` нам не поможет: он выдаёт только буквы, без координат. Нужен инструмент, который сохраняет позиции.

## Шаг 1: извлекаем координаты символов

Для PDF координаты каждого символа даёт Python-библиотека `pdfplumber`:

```python
import pdfplumber
with pdfplumber.open("doc_v1.pdf") as pdf:
    for ch in pdf.pages[0].chars[:5]:
        print(repr(ch["text"]), round(ch["x0"], 4), round(ch["top"], 4))
```

```
'H' 72.0 100.0
'e' 78.01 100.0
'l' 84.0 100.0
'l' 90.02 100.0
'o' 96.0 100.0
```

`x0` — горизонтальная координата левого края глифа (в пунктах, 1 pt ≈ 0,35 мм), `top` — вертикальная. Смотрим внимательно: у `'H'`, `'l'`, `'o'` координаты **круглые** (72.0, 84.0, 96.0), а у `'e'` и второго `'l'` — с хвостом `78.01`, `90.02`. Это и есть микро-сдвиги: символы стоят не ровно, а чуть-чуть смещены.

## Шаг 2: сравниваем две версии и читаем биты

Основной приём — сравнить два «одинаковых» документа и найти различия в координатах. Напишем функцию, которая снимает позиции всех символов, и вычтем одну версию из другой:

```python
import pdfplumber
def positions(path):
    out = []
    with pdfplumber.open(path) as pdf:
        for page in pdf.pages:
            for ch in page.chars:
                out.append((ch["text"], round(ch["x0"], 4), round(ch["top"], 4)))
    return out

a = positions("doc_v1.pdf")
b = positions("doc_v2.pdf")
for (ta, xa, ya), (tb, xb, yb) in zip(a, b):
    if (xa, ya) != (xb, yb):
        print(ta, "сдвинут:", (xa, ya), "->", (xb, yb))
```

Различия в `x0` порядка 0,01–0,1 pt — это и есть канал. Идея простая: **знак сдвига** относительно «идеальной» сетки кодирует бит. Собираем биты и упаковываем в байты:

```python
import pdfplumber, numpy as np
bits = []
with pdfplumber.open("doc_v1.pdf") as pdf:
    for ch in pdf.pages[0].chars:
        x = ch["x0"]
        frac = x - round(x)
        if abs(frac) > 1e-6:
            bits.append(1 if frac > 0 else 0)
print(np.packbits(np.array(bits, dtype=np.uint8)).tobytes()[:40])
```

```
b'flag{kerning}'
```

Флаг получен. Символы, стоящие «ровно», не кодируют ничего; символы с микро-сдвигом кодируют бит знаком отклонения.

## Шаг 3: лигатуры и альтернативные глифы

Второй уровень типографики — **глифы**. OpenType поддерживает фичи: `liga` (лигатуры), `salt` (stylistic alternates), `ss01`–`ss20` (stylistic sets). Один и тот же символ может отображаться несколькими разными глифами, и выбор варианта не меняет текст, но кодирует данные:

- **Лигатура vs раздельные буквы.** Пара `fi` как одна лигатура = 1, раздельно = 0.
- **Stylistic set.** Включён `ss01` или нет — бит.
- **Альтернативный глиф.** Для `a` выбран один из двух вариантов.

Смотрим, какие фичи вообще есть в шрифте:

```bash
$ ttx -t GSUB font.otf
$ python3 -c "from fontTools.ttLib import TTFont; f=TTFont('font.otf'); print([fr.FeatureTag for fr in f['GSUB'].table.FeatureList.FeatureRecord])"
['liga', 'salt', 'ss01']
```

Наличие необычного набора фич — первый сигнал. Дальше смотрим, какие из них **включены** в конкретных участках документа.

## Шаг 4: вариативные шрифты

**Variable font** (вариативный шрифт) — современный формат, где один файл содержит несколько «мастеров» и оси: `wght` (вес), `wdth` (ширина), `slnt` (наклон) и кастомные. Значение оси меняется непрерывно, а значит дробная часть значения — готовый канал:

```bash
$ python3 -c "from fontTools.ttLib import TTFont; f=TTFont('var.ttf'); [print(a.axisTag, a.minValue, a.defaultValue, a.maxValue) for a in f['fvar'].axes]"
wght 100.0 400.0 900.0
wdth 75.0 100.0 125.0
```

Если у экземпляра шрифта значение оси `wght=400.37` вместо круглого `400.0` — это подозрительно: скорее всего, дробная часть кодирует данные. Инстанцируют шрифт так:

```python
from fontTools.varLib.instancer import instantiateVariableFont
from fontTools.ttLib import TTFont
f = TTFont("var.ttf")
inst = instantiateVariableFont(f, {"wght": 400.37})   # дробное значение!
inst.save("instance.ttf")
```

В CTF чаще дают сам вариативный файл с необычными значениями по умолчанию — сравнивай дробные части осей.

## Шаг 5: два уровня — шрифт и вёрстка

Важно разделять, где именно живут данные.

- Сокрытие **в файле шрифта** (таблицы, контуры, имена) находится внутри TTF/OTF и не зависит от документа. Его ищут через `ttx` и `fontTools`.
- Сокрытие **в вёрстке** (кернинг, трекинг, выбор фич) — это данные в документе, который лишь *использует* шрифт. Его ищут в PDF (`pdfplumber`) или DOCX.

Для DOCX вёрстку извлекают распаковкой OOXML:

```bash
$ unzip -o doc.docx -d doc_x
$ grep -o 'w:spacing w:val="[-0-9]*"' doc_x/word/document.xml | head
$ grep -o 'w:kern w:val="[0-9]*"' doc_x/word/document.xml | sort | uniq -c
```

Нестандартные значения (`kern` не 0/2, «дробный» spacing) — признак канала. Начинай всегда с `file`: если дали TTF/OTF — это файл шрифта; если PDF/DOCX — вёрстка.

## Шаг 6: зачем это нужно — канареечные метки

Кернинг и трекинг используют для «уникализации» копии документа на каждого получателя: у каждого своя микро-вариация, по которой можно отследить утечку. Это не совсем стеганография ради секретности, но техника та же. При анализе методика такая: получите два экземпляра документа у разных получателей, выровняйте текст, сравните координаты символов и набор OpenType-фич — различия и есть метка.

## Что мы теперь знаем

1. Данные в типографике живут в вёрстке — кернинге, трекинге, выборе глифов, — а не в тексте.
2. Координаты символов в PDF даёт `pdfplumber`; знак микро-сдвига кодирует бит.
3. Основной приём — сравнить два «одинаковых» документа и найти различия в позициях.
4. Лигатуры и stylistic sets (`liga`, `salt`, `ss01`) меняют глиф, не меняя текст, и кодируют биты.
5. Вариативные шрифты несут данные в дробных значениях осей (`wght=400.37`).
6. Копирование текста в другой редактор пересчитывает вёрстку и разрушает канал.

## Почему типографика — незаметный канал

Сокрытие в типографике работает на уровне **того, как текст выглядит**, а не того, что он означает. Читатель видит обычный документ, а информация спрятана в деталях вёрстки: расстояниях между символами (кернинг), интервалах между словами, выборе альтернативного глифа из лигатуры или вариантного начертания. Это один из самых «стелс»-каналов: визуально документ не отличается, и заметить подмену можно только измерив координаты символов.

Технически PDF хранит текст как поток с операторами позиционирования (`Td`, `TJ`, `Tj`): каждый символ (или группа) имеет координату и сдвиг. Если два документа отличаются **только** этими сдвигами, а текст идентичен — это признак канала. Сравнивают координаты символов (`pdfminer.six`, `PyMuPDF`, `pdftotext -bbox`) и читают разницу как биты: сдвиг влево/вправо = 0/1. Аналогично работает вариативный шрифт (variable font): значение оси (weight, width) можно слегка менять на символ, кодируя данные, — визуально почти незаметно.

Второй уровень — **лигатуры и альтернативные глифы**: одна и та же буква может быть представлена разными глифами (через OpenType-фичи `liga`, `salt`, `ss01`), и выбор глифа несёт бит. Для анализа: `fontTools` (`ttx`), `hb-shape`, сравнение шрифтовых таблиц.

## Если не сработало

- **Координаты символов не отличаются.** Возможно, канал не в вёрстке, а в самих глифах или в метаданных PDF — проверьте шрифты и `exiftool`.
- **Документ прошёл через пересоздание.** Печать в PDF заново, конвертация или «optimize» пересчитывают позиции и убивают канал.
- **Нужны две версии.** Метод сравнения требует `doc_v1` и `doc_v2` с одинаковым текстом; если версия одна, ищите вариативные оси и альтернативные глифы статически.
- **Различия в шрифте, а не в координатах.** Сравните таблицы шрифтов (`ttx -t cmap/glyf`), ищите лишние глифы и изменённые метрики.
- **PDF — скан, а не текст.** Если текста нет (только изображение), типографический канал не применим — переходите к анализу изображения.

## Частые вопросы

**Как извлечь координаты символов из PDF?** `pdfminer.six` (LAParams), `PyMuPDF` (`page.get_text('rawdict')`) или `pdftotext -bbox`; далее сравнение попарно.

**Почему это называют «канареечной меткой»?** Слегка варьируя вёрстку для каждой копии документа, можно выдать уникальную метку и отследить, кто «слил» документ.

**Работает ли на веб-страницах?** Да, аналогичные приёмы применяют к HTML/CSS (порядок атрибутов, пробелы, варианты глифов через web-шрифты).

**Что если вариативный шрифт не поддерживается?** Тогда браузер/просмотрщик возьмёт ось по умолчанию и данные не проявятся визуально — но в файле они останутся, и их можно извлечь анализом таблиц.

## Куда дальше

Типографика показала, что канал бывает «невидимым на глаз», но измеримым. В следующем уроке разберём конкретные **инструменты** — `jsteg`, `cloakify` и `steghide`: как прятать и извлекать данные с полным набором флагов. А пока запомни: два одинаковых документа — сравни координаты, а не слова.

## Где пригодится

- **CTF:** Stego — данные в вёрстке, PDF/DOCX с «одинаковым» текстом.
- **DLP/IR:** отслеживание утечек через канареечные метки.
- **Работа:** анализ вёрстки и водяные знаки документов.
- **Forensics:** установление источника копии документа по микро-вариациям.
