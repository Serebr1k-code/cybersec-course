## Вопрос, с которого всё начинается

`image.jxl` — файл JPEG XL. Chrome и многие сайты уже отдают его как «лучший JPEG».
Формат новый (стандарт 2021), инструменты для стегоанализа под него почти не написаны.
Но устроен он по тем же принципам: контейнер плюс сжатие. Значит, разобрать его можно
вручную. Сначала посмотрим, что у него в начале.

## Наш пример: файл image.jxl

```bash
file image.jxl
xxd -l 48 image.jxl
```

```text
image.jxl: JPEG XL codestream
00000000: 0000 000c 4a58 4c20 0d0a 870a 0000 0014  ....JXL ........
00000010: 6674 7970 6a78 6c20 0000 0000 6a78 6c20  ftypjxl ....jxl
00000020: 0000 001d 464c 4720 6e74 6f7b 6a78 6c5f  ....FLG nto{jxl_
00000030: 346e 735f 6230 785f 666c 3467 7d              4ns_b0x_fl4g}
```

Видим сигнатуру: 4 байта длины `00 00 00 0c`, ASCII `JXL `, затем `0d 0a 87 0a`.
Это «магический» маркер контейнера JPEG XL. Дальше `ftyp`, потом бокс `FLG `.

## Шаг 1: два вида файла JPEG XL

Важно не путать:

- **raw codestream** — начинается с двух байт `FF 0A`. Это «голый» поток сжатия.
- **container** — начинается с бокса-сигнатуры `JXL ` (как наш файл). Внутри —
  боксы `ftyp`, `jxlc` (сжатый код), `jxlp` (частичные коды), `jbrd` (превью),
  `Exif`, `xml ` и произвольные.

`file` может сказать `JPEG XL codestream` даже для контейнера — не доверяй только
ему, смотри первые байты. Наш файл — контейнер, потому что начинается с `00 00 00 0c
JXL `.

## Шаг 2: сжатие — модульный режим и VarDCT

JPEG XL умеет два режима:

- **Modular** (модульный) — lossless-сжатие, похожее на PNG/FLIF: предсказание
  пикселей, затем энтропийное кодирование. Применяется для lossless и для
  «маленьких» картинок.
- **VarDCT** — lossy-режим, наследник DCT, но с адаптивным размером блока и
  перцептивной моделью.

Энтропийный кодер — **ANS** (Asymmetric Numeral Systems). В отличие от хаффмана,
ANS кодирует символы с дробными вероятностями и очень близок к энтропийному пределу.
Для стеганографии это значит: «дописать бит в код» без слома потока сложнее, чем в
PNG, поэтому закладки чаще кладут в **контейнер** или в **метаданные**.

## Шаг 3: разбираем боксы вручную

```bash
python3 - <<'PY'
import struct
d = open('image.jxl','rb').read()
i = 0
while i + 8 <= len(d):
    size = struct.unpack('>I', d[i:i+4])[0]
    typ = d[i+4:i+8]
    print(f'{i:>6}  {size:>6}  {typ}')
    if size == 0:
        break
    i += size
PY
```

```text
     0      12  b'JXL '
    12      20  b'ftyp'
    32      29  b'FLG '
```

Бокс `FLG ` снова не из спецификации. Достаём данные:

```bash
python3 - <<'PY'
import struct
d = open('image.jxl','rb').read()
i = 32
size = struct.unpack('>I', d[i:i+4])[0]
print(d[i+8:i+size].decode())
PY
```

```text
nto{jxl_4ns_b0x_fl4g}
```

## Шаг 4: где ещё прячут данные в JXL

- **`jxlc` / `jxlp`** — сам код изображения. В `jxlp` частичные коды можно дополнить
  произвольным хвостом; парсер, читающий ровно `size`, хвост не увидит.
- **`Exif` и `xml ` (XMP)** — штатные боксы метаданных. `exiftool -a -G1` покажет
  их; флаг в `UserComment` — типовой CTF-приём.
- **`jbrd`** — JPEG-реконструкция (для обратной совместимости). Полезные данные
  можно спрятать в её байтах.
- **appended data** — байты после последнего бокса.

## Шаг 5: инструменты

```bash
exiftool -a -G1 image.jxl | grep -iE 'Comment|XML|Exif'
djxl --print_read_bytes image.jxl 2>/dev/null | head
binwalk image.jxl
```

`djxl` (из libjxl) умеет печатать структуру. Если закладка внутри `jxlc`, придётся
декодировать код и смотреть пиксели/коэффициенты — но это уже редкость для CTF.

## Шаг 6: как устроены боксы jxlc и jxlp

Основной код изображения лежит в боксе **`jxlc`** (весь код целиком) или в нескольких
боксах **`jxlp`** (частичные коды, когда поток пишется порциями). Каждый `jxlp`
начинается с 4-байтного счётчика и флага «последний», а затем идёт кусок кода.

Почему это интересно для стеганографии:

- Парсер изображения читает ровно столько байт, сколько указано в размере бокса.
  Если после «настоящего» кода в `jxlp` дописать лишнее и увеличить размер, декодер
  может это проигнорировать, а мы — прочитать.
- Порядок `jxlp`-боксов можно перемешать; изображение всё равно соберётся, а порядок
  может кодировать биты (перестановочный канал).
- Бокс `jbrd` (JPEG-реконструкция) содержит «резервную» JPEG-версию картинки; её
  байты почти никогда не проверяются.

## Шаг 7: метаданные Exif и XMP

Штатные боксы метаданных — самый простой путь. JPEG XL поддерживает `Exif` (двоичный
Exif) и `xml ` (XMP, текстовый XML). В XMP можно положить произвольное свойство:

```xml
<x:xmpmeta xmlns:x="adobe:ns:meta/">
  <rdf:RDF><rdf:Description>
    <ns:comment>nto{jxl_m3t4d4t4}</ns:comment>
  </rdf:Description></rdf:RDF>
</x:xmpmeta>
```

`exiftool -a -G1 image.jxl` покажет это как `XMP-comment`. Типовой CTF-приём: флаг в
`UserComment` или в кастомном XMP-пространстве имён.

## Шаг 8: практический чек-лист по JPEG XL

1. `file image.jxl` — но не доверяй слепо, проверь первые байты `xxd -l 16`.
2. Если начинается с `FF 0A` — это raw codestream, боксов нет.
3. Если с `00 00 00 0C 4A 58 4C 20` — контейнер, парси боксы.
4. Перечисли боксы и найди незнакомые типы.
5. Проверь `Exif`/`xml `/`jbrd` штатными инструментами (`exiftool`, `djxl`).
6. Проверь хвост файла на appended data (`binwalk`, `xxd` с конца).

## Шаг 9: почему новый кодек — не проблема

Главная мысль урока: **смена кодека не меняет принципов**. Контейнер, метаданные,
appended data, коэффициенты — эти четыре «слоя» есть в любом формате изображений.
Как только ты научился разбирать боксы одного формата, ты разберёшь боксы любого
ISOBMFF-подобного контейнера. Разница — только в именах полей и порядке байтов.

Именно поэтому в этом модуле мы идём от JPEG 2000 к JPEG XL и AVIF: структура одна,
детали разные. К концу модуля ты сможешь открыть незнакомый формат, посмотреть на
первые 64 байта и понять, где искать.

## Второй пример: порядок jxlp-боксов как канал

Когда изображение пишется порциями, коды лежат в нескольких боксах `jxlp`. Каждый
начинается с 4-байтного счётчика (номер порции + флаг «последняя»). Декодер собирает
порции по номерам, а не по порядку в файле. Значит, **порядок боксов в файле не важен**
для картинки — а это готовый перестановочный канал: можно упорядочить боксы так, чтобы
их номера кодировали сообщение.

Проверить это просто: соберём список счётчиков и посмотрим, не совпадает ли их порядок
с ожидаемым.

```bash
python3 - <<'PY'
import struct
d = open('image.jxl','rb').read()
i = 0
while i + 8 <= len(d):
    size = struct.unpack('>I', d[i:i+4])[0]
    typ = d[i+4:i+8]
    if typ in (b'jxlc', b'jxlp'):
        ctr = struct.unpack('>I', d[i+8:i+12])[0] if typ == b'jxlp' else None
        print(typ, size, 'counter=', ctr)
    i += size if size else len(d) - i
PY
```

Аномальный порядок счётчиков или их значения — повод копать дальше. В CTF из таких
номеров иногда собирают флаг побитово.

## Частые ошибки при разборе JXL

Главная ловушка — перепутать raw codestream и контейнер. Первые два байта `FF 0A`
означают «голый поток», и никаких боксов там нет — искать `JXL ` бессмысленно. И
наоборот: если файл начинается с `00 00 00 0C 4A 58 4C 20`, это контейнер, и внутри
надо идти по боксам. `file` иногда называет контейнер «codestream», поэтому всегда
сверяйся с `xxd`.

Вторая ловушка — считать, что `exiftool` покажет всё. `exiftool` знает про штатные
боксы `Exif` и `xml `, но про нестандартный бокс он ничего не скажет: для него это
просто «неизвестные данные». Ручной обход боксов обязателен, если хочешь найти то,
чего нет в спецификации.

Третья ловушка — игнорировать порядок. В JPEG XL порядок `jxlp`-боксов не влияет на
изображение, но может нести информацию. Если ты видишь, что счётчики порций идут не
по возрастанию, это не ошибка кодировщика, а сигнал.

## Сравнение JXL с JPEG и WebP

Смысл сравнения — перенести навык. JPEG хранит данные сегментами, WebP — RIFF-чанками,
JPEG XL — боксами. Во всех трёх случаях у тебя есть «метаданные» и «полезная нагрузка»,
и во всех трёх метаданные — самое простое место для закладки. Разница только в именах:
у JPEG это `COM`, у WebP — `EXIF`/`XMP`, у JXL — `Exif`/`xml `/`jbrd`.

Освоив один формат, ты переносишь метод на остальные: посмотреть на первые байты,
определить контейнер, обойти блоки, найти лишнее. Именно поэтому этот модуль идёт
кластером: три урока — один навык.

## Что мы теперь знаем

- JPEG XL бывает raw (`FF 0A`) и контейнерным (`JXL ` + боксы).
- Контейнерные боксы устроены как в JP2: `размер(4, big-endian) + тип(4) + данные`.
- ANS-энтропия делает пиксельные закладки сложнее — контейнер проще.
- Штатные боксы `Exif`, `xml `, `jbrd`, `jxlc`/`jxlp` — кандидаты на сокрытие.
- Парсер боксов пишется в несколько строк и находит нестандартные типы.
