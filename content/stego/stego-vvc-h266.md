## Вопрос, с которого всё начинается

`clip.vvc` — видео в кодеке VVC (Versatile Video Coding, он же H.266). Это самый
новый стандарт сжатия видео: он на 40–50% эффективнее H.265. Новый кодек — снова
вопрос: где в нём прячут данные? Ответ ожидаемый: контейнер, метаданные и структура
сжатия. Но у VVC есть свои особенности, и о них стоит знать.

## Наш пример: файл clip.vvc

```bash
file clip.vvc
xxd -l 64 clip.vvc
```

```text
clip.vvc: ISO Media, MP4 Base Media v1
00000000: 0000 0018 6674 7970 7676 6331 0000 0000  ....ftypvvc1....
00000010: 7676 6331 6973 6f6d 0000 0020 464c 4720  vvc1isom... FLG 
00000020: 6e74 6f7b 7676 635f 6832 3636 5f63 3064  nto{vvc_h266_c0d
00000030: 3363 5f66 6c34 677d                        3c_fl4g}
```

`ftyp` с брендом `vvc1` — это VVC. Контейнер тот же ISOBMFF, что и у AV1/AVIF. Бокс
`FLG ` — нестандартный. Но разберём и сам кодек.

## Шаг 1: что такое VVC

VVC (H.266) — стандарт, разработанный JVET (Joint Video Experts Team) в 2020 году.
Он продолжает линию H.264 → H.265 → H.266. Главные новшества:

- **QUAD-дерево и MTT.** CTU (coding tree unit) до 128×128 разбивается не только
  на четыре части (quadtree), но и на две-три (multi-type tree): горизонтально,
  вертикально, с разными пропорциями. Это даёт гибкое разбиение под контент.
- **ALF (Adaptive Loop Filter).** Адаптивный контурный фильтр, который подбирается
  для каждого кадра: коэффициенты фильтра передаются в потоке.
- **Аффинное движение.** Блок можно не только сдвигать, но и масштабировать/
  поворачивать — motion vector становится набором параметров.

Для стеганографии важны два слоя: **структура разбиения** (порядок и типы разбиения
CTU можно переупорядочить) и **коэффициенты ALF** (их можно модулировать).

## Шаг 2: как устроен поток VVC

VVC-поток — это **NAL-юниты** (Network Abstraction Layer units), как в H.264/H.265.
Каждый NAL имеет заголовок и полезную нагрузку. Типы: `VPS`/`SPS`/`PPS`
(параметры), `IDR`/`CRA` (кадры), `SEI` (дополнительная информация).

**SEI** (Supplemental Enhancement Information) — аналог OBU `metadata` в AV1: сюда
можно положить произвольные «пользовательские» сообщения. Это штатное место для
закладок, которое декодеры игнорируют.

## Шаг 3: контейнер ISOBMFF

Наш файл — ISOBMFF. Структура та же:

- **`ftyp`** с брендом `vvc1`;
- **`moov`** → `trak` → `stbl` → `stsd` с описанием кодека `vvc1`;
- **`mdat`** с NAL-юнитами;
- **`free`/`skip`/`uuid`** — свободные области.

Практический вывод: если ты умеешь обходить боксы (а ты умеешь после уроков про AVIF
и AV1), VVC-контейнер тебе знаком. Меняется только бренд и тип сэмплов.

## Шаг 4: разбираем боксы вручную

```bash
python3 - <<'PY'
import struct
d = open('clip.vvc','rb').read()
i = 0
while i + 8 <= len(d):
    size = struct.unpack('>I', d[i:i+4])[0]
    typ = d[i+4:i+8]
    print(f'{i:>6}  {size:>6}  {typ}')
    if typ == b'FLG ':
        print('  ->', d[i+8:i+size].decode('latin-1'))
    i += size if size else len(d) - i
PY
```

```text
     0      24  b'ftyp'
    24      32  b'FLG '
  -> nto{vvc_h266_c0d3c_fl4g}
```

## Шаг 5: где ещё прячут в VVC

- **SEI-сообщения** — штатные «пользовательские данные»; самый простой носитель.
- **Коэффициенты ALF** — их можно модулировать; фильтр всё равно «подстраивается».
- **Порядок и типы разбиения CTU** — перестановочный канал.
- **Аффинные motion vectors** — параметры движения как биты.
- **Appended data** и `free`/`uuid` в контейнере.

## Шаг 6: инструменты

```bash
ffprobe -hide_banner clip.vvc
mp4box -info clip.vvc 2>/dev/null | head
vvdecapp -b clip.vvc -o /dev/null 2>/dev/null | head
binwalk clip.vvc
```

`ffprobe` покажет кодек. `mp4box -info` — дерево боксов. `vvdecapp` (эталонный
декодер VVC) умеет печатать статистику потока. Для глубокого анализа ALF/motion
нужны специализированные инструменты, но в CTF почти всегда хватает контейнера и SEI.

## Шаг 7: сравнение H.265 и VVC

| | H.265/HEVC | VVC/H.266 |
|---|---|---|
| Разбиение | quadtree | quadtree + MTT |
| CTU | до 64×64 | до 128×128 |
| Фильтр | deblock + SAO | deblock + SAO + ALF |
| Движение | трансляция | трансляция + аффинное |
| Контейнер | MP4/TS | MP4/TS |

Видно, что VVC — эволюция, а не революция: те же слои, больше вариантов. Значит, и
приёмы стеганографии переносятся без изменений.

## Шаг 8: частые ошибки

Первая — считать VVC «экзотикой, которая не встречается». Он уже используется в
вещании 8K и постепенно приходит в стриминг. Вторая — искать бокс `vvc1` в `ftyp`
не там: бренд может быть `vvc1` или `vvi1` в зависимости от профиля. Третья —
забывать про `SEI`: если контейнер чист, следующий шаг — разбор NAL-юнитов и поиск
SEI-сообщений с произвольными данными.

## Шаг 9: профили и уровни VVC

VVC, как и другие кодеки, имеет **профили** (наборы инструментов) и **уровни**
(ограничения по размеру и скорости). Профиль может быть Main 10, Main 4:4:4 и так
далее. В контейнере профиль отражается в бренде `ftyp`: например, `vvc1` — Main
profile, `vvi1` — Main 10. Для разбора это значит: не удивляйся, если бренд не
ровно `vvc1` — проверяй оба варианта.

Уровни влияют на размеры CTU и максимальные motion vectors. Для стеганографии это
неважно: где бы ни лежала закладка, разбирать её надо на уровне контейнера или NAL.

## Практика: поиск SEI-сообщений

SEI — это NAL-юнит специального типа. Его payload начинается с типа сообщения
(например, `user_data_unregistered`, тип 5) и содержит произвольные байты. Найти SEI
можно, перебирая NAL-юниты в `mdat`:

```bash
python3 - <<'PY'
d = open('clip.vvc','rb').read()
j = d.find(b'mdat')
p = j + 4
while p < len(d) - 1:
    # в MP4 перед NAL стоит 4-байтная длина
    if p + 4 > len(d):
        break
    n = int.from_bytes(d[p:p+4], 'big')
    if n == 0 or p + 4 + n > len(d):
        break
    nal = d[p+4:p+4+n]
    if nal and (nal[0] >> 1) == 0:
        print('possible SEI/user-data at', p, 'len', n)
    p += 4 + n
PY
```

Точные номера типов NAL зависят от профиля, но `user_data_unregistered` почти всегда
несёт произвольную нагрузку. Это прямой аналог OBU `metadata` в AV1.

## VVC в реальном мире

VVC пока не так распространён, как AV1, но уже применяется в вещании (DVB, 8K) и
тестируется в стриминге. В CTF он появляется как «следующий кодек после AV1» — задача
проверяет, умеешь ли ты переносить навык разбора ISOBMFF на новый бренд. Если ты
прошёл AVIF и AV1, VVC не добавит ничего принципиально нового: те же боксы, те же
метаданные, тот же принцип «ищи лишнее».

## Итоговая стратегия для VVC

Посмотри `ftyp` и бренд, обойди боксы, проверь `free`/`uuid`/appended data. Затем —
`ffprobe`/`mp4box -info` для параметров. Если контейнер чист, ищи SEI-сообщения в
NAL-потоке. И только потом — коэффициенты ALF и разбиение CTU, для которых нужен
эталонный декодер. Контейнер — всегда первый шаг.

## Ещё одна деталь: кодирование без потерь в VVC

VVC поддерживает режим lossless (трансформант-скип): блок кодируется без преобразования и квантования. В этом режиме коэффициенты сохраняются точно, и младшие биты можно менять, не теряя данные — как во FLAC для аудио. Это делает VVC lossless потенциально более удобным носителем, чем lossy-режимы, где кодек сам округляет коэффициенты.

Кроме того, VVC наследует **tiles** и **slices** — независимо декодируемые области. Каждую можно декодировать отдельно, а значит, «лишняя» tile может нести данные, не влияя на остальной кадр. При разборе потока полезно смотреть, сколько tiles объявлено в SPS и нет ли среди них неиспользуемой.

## Почему VVC важен для стеганографии

Чем сложнее кодек, тем больше в нём «служебных» параметров, которые передаются в потоке, но не влияют напрямую на видимую картинку: режимы разбиения, коэффициенты фильтров, параметры аффинного движения, метаданные. Каждый такой параметр — потенциальный носитель. VVC как самый сложный из массовых кодеков даёт наибольшее число таких каналов. Именно поэтому анализ VVC-потока — перспективное направление: классические детекторы (хи-квадрат, RS) на нём не работают, а контейнерные и параметрические закладки остаются незамеченными. Для практика вывод прост: сначала контейнер, потом NAL-уровень, и только затем — глубокий разбор параметров.

## Что мы теперь знаем

- VVC/H.266 — новейший видеокодек, эволюция H.265.
- Разбиение — QUAD-дерево плюс MTT; фильтрация — ALF; движение — аффинное.
- Поток состоит из NAL-юнитов; SEI — штатное место для метаданных.
- В файле VVC лежит в ISOBMFF (бренд `vvc1`), разбирается тем же парсером.
- Приёмы стеганографии в VVC — те же, что в AV1/H.265.
