## Вопрос, с которого всё начинается

У тебя есть файл `app.db`. Открываешь — обычная база SQLite с таблицей пользователей,
ничего лишнего. Но в задаче сказано, что там спрятаны данные. Куда их можно спрятать
так, чтобы обычный `SELECT * FROM users` их не показал?

Ответ: SQLite — это **файл с фиксированными страницами**, и в нём есть места, которые
SQL-движок не читает: свободные страницы, «дыры» внутри страниц, остатки удалённых
записей. Разберёмся, как это устроено.

## Наш пример

Смотрим на файл:

```
$ file app.db
app.db: SQLite 3.x database, last written using SQLite version 3040001
$ sqlite3 app.db .tables
users  sessions
$ sqlite3 app.db "SELECT * FROM users;"
1|alice|user
2|bob|user
```

Ничего подозрительного. Но у базы есть «внутренности», которые мы ещё не смотрели.

## Шаг 1: страничная структура

SQLite хранит всё **страницами** фиксированного размера (по умолчанию 4096 байт).
Первая страница (offset 0) — заголовок файла (100 байт), где записан `page_size`.

```
$ python3 db_info.py
page_size: 4096
page_count: 16
freelist_count: 3
```

Ключевой параметр — **`freelist_count`**: число страниц в списке свободных. Когда
строку удаляют, страница может попасть во **freelist** — движок её больше не читает,
но **данные в ней остаются**, пока страница не будет перезаписана. Это классическое
unallocated-пространство.

```
$ sqlite3 app.db "PRAGMA freelist_count;"
3
```

## Шаг 2: unallocated внутри страницы

Даже в **используемой** странице данные занимают не всю её целиком. Ячейки (cells)
растут с начала страницы, а указатели на них — с конца; между ними остаётся «дыра» —
**unallocated space**. Движок туда не пишет, но и не очищает. Именно поэтому старые
(удалённые) записи часто остаются в файле и находятся через `strings`.

```
$ strings app.db | grep -i nto
nto{sql1t3_fr33l1st_h1dd3n}
```

Обрати внимание: `strings` нашёл флаг, хотя `SELECT` его не возвращал — он лежит в
неиспользуемом пространстве.

## Шаг 3: удалённые записи и WAL

Два частых источника скрытого:

1. **Удалённые строки.** `DELETE FROM users WHERE id=2;` не обнуляет байты — запись
   остаётся в странице до перезаписи (vacuum). Форензика БД часто строится на
   восстановлении таких записей.
2. **WAL (Write-Ahead Log).** Если база в режиме WAL, рядом есть файл `app.db-wal` с
   последними изменениями. Старые версии строк могут лежать и там, и в `app.db-shm`.

```
$ ls -la
-rw-r--r-- 1 user user 65536 app.db
-rw-r--r-- 1 user user 16512 app.db-wal
```

## Шаг 4: как прячут намеренно

Осознанная стеганография в SQLite выглядит так:

- **Payload в свободную страницу.** Взять страницу из freelist и записать туда данные
  напрямую, минуя SQL. Движок её не читает, `SELECT` её не видит.
- **Payload в BLOB-поле.** Легально положить большой `BLOB` в таблицу и спрятать данные
  в его хвосте/неиспользуемых байтах.
- **Payload в поле, которое приложение игнорирует** (например, в `comments` или
  служебный `metadata`).
- **Обфускация в текстовых полях** (zero-width символы — как в текстовой стеганографии).

## Шаг 5: пайплайн разбора

1. `sqlite3 app.db .tables` и `SELECT` — что видно легально.
2. `PRAGMA page_size; PRAGMA freelist_count;` — сколько «свободного» места.
3. `strings app.db | grep -i -E 'nto|flag|key'` — быстрый поиск по всему файлу.
4. `xxd app.db | grep -i ...` или скрипт, читающий страницы из freelist по списку.
5. Не забыть `app.db-wal` и `app.db-shm`.

Важный нюанс: `grep` в лабораторном движке ищет **литерально**, поэтому ищи точную
подстроку (`nto{`), а не регулярку.

## Что мы теперь знаем

- SQLite — файл из **страниц** фиксированного размера.
- **Freelist** — свободные страницы, данные в них не читаются SQL, но остаются.
- **Unallocated space** внутри страниц хранит остатки удалённых записей.
- **WAL/SHM** — отдельные файлы с версиями строк.
- Намеренно прячут в свободные страницы, BLOB-хвосты и игнорируемые поля.
- Разбор: `PRAGMA` + `strings`/`xxd` по всему файлу.

## Куда дальше

Мы научились смотреть «внутрь» базы данных. Дальше — сокрытие в **HTML/CSS**: как
невидимые для браузера символы и правила кодируют данные прямо в веб-странице. А пока
главное запомни: **база данных — это файл**, и в нём есть пространство, которое SQL
не показывает.

## Где пригодится

- **CTF Forensics:** скрытые данные и удалённые записи в БД.
- **Форензика:** восстановление удалённого из SQLite и WAL.
- **Работа:** аудит приложений, где в БД могут утекать секреты.
- **Bug bounty:** поиск забытых токенов и ключей в клиентских базах.
