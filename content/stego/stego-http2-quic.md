## Вопрос, с которого всё начинается

В уроке про HTTP-скрытые каналы мы прятали данные в заголовках, cookies и chunked-
кодировании. Но современный веб всё чаще работает по **HTTP/2** и **HTTP/3 (QUIC)**.
Там заголовки — уже не текст, а бинарные структуры. Значит, и каналы другие. Где
прячутся данные в этих протоколах?

## Наш пример

Дан дамп `http2.pcap`. Смотрим на него:

```
$ tshark -r http2.pcap
1  0.000000  10.0.0.5 → 203.0.113.10  TCP  74 51234 → 443 [SYN]
2  0.000210 203.0.113.10 → 10.0.0.5   TCP  74 443 → 51234 [SYN, ACK]
...
6  0.001900  10.0.0.5 → 203.0.113.10  HTTP2 98 HEADERS[1]
7  0.002100 203.0.113.10 → 10.0.0.5   HTTP2 86 HEADERS[1]
```

Никакого `GET / HTTP/1.1` — трафик бинарный. Разберём, где тут можно спрятать биты.

## Шаг 1: HTTP/2 — бинарные кадры

HTTP/2 разбит на **кадры** (frames). У каждого кадра есть заголовок из 9 байт:
длина (24 бита), тип (8 бит), флаги (8 бит), идентификатор потока (31 бит). Типы кадров:
`DATA`, `HEADERS`, `PRIORITY`, `RST_STREAM`, `SETTINGS`, `PING`, `GOAWAY`, `WINDOW_UPDATE`,
`CONTINUATION`.

Потенциальные каналы:

1. **Padding.** Кадры `DATA` и `HEADERS` имеют **padding length** и байты заполнения —
   их можно менять, и содержимое не повлияет на смысл. Классический канал: длина
   паддинга кодирует биты.
2. **`PRIORITY` и `WINDOW_UPDATE`.** Служебные числа (веса, размеры окна) можно
   переставлять в допустимых пределах — тайминг/числовые covert-каналы.
3. **Порядок и дублирование заголовков.** HTTP/2 допускает несколько `cookie` и
   псевдозаголовков `:method`, `:path` в определённом порядке — порядок кодирует биты.

## Шаг 2: HPACK и Huffman-паддинг

Заголовки в HTTP/2 сжимаются **HPACK**. Он использует статическую и динамическую таблицы
и **Huffman-кодирование** строк. Ключевая деталь: Huffman-код может дополняться до
границы байта — это **padding**, который декодер обязан игнорировать. Значит, в этих
битах можно спрятать данные.

```
$ python3 hpack_analyze.py http2.pcap
HEADERS frame #1
  :method = GET
  :path = /
  :authority = example.com
  padding bits after Huffman: 01101110 01110100 ...
  -> nto{h2_hp4ck_p4dding}
```

Идея: сообщение режется на куски, каждый кусок «упаковывается» в хвост Huffman-кода
заголовка. Декодер HPACK их игнорирует, а наш парсер — извлекает.

## Шаг 3: HTTP/3 и QUIC

HTTP/3 работает поверх **QUIC** (UDP). QUIC — это набор **кадров** внутри **потоков**,
мультиплексированных по **connection ID**.

Каналы:

1. **Connection ID.** Идентификатор соединения произвольной длины (0–20 байт) и его
   смена в процессе — можно менять и прятать данные.
2. **`PADDING` кадр.** Явный кадр-заполнитель — идеальное место: его содержимое не
   интерпретируется.
3. **`STREAM` кадры.** Данные приложения — прямой канал (но это уже «обычный» туннель).
4. **Длина потоков и порядок кадров.** Числовые/тайминговые covert-каналы.

```
$ tshark -r quic.pcap -Y quic
1  0.000000 10.0.0.5 → 203.0.113.10  QUIC 1356 Initial, DCID=8a3f...
2  0.000300 203.0.113.10 → 10.0.0.5   QUIC 1180 Initial, SCID=...
$ python3 quic_padding.py quic.pcap
PADDING frames: 3
decoded: nto{qu1c_p4dding_c0v3rt}
```

## Шаг 4: почему это тяжелее обнаружить

- Трафик **бинарный** и часто **зашифрован** (TLS 1.3 в HTTP/2, встроенное шифрование
  в QUIC). DPI видит только размеры, тайминги и метаданные.
- **Паддинг легален** — его используют и «нормальные» клиенты для защиты от
  трафик-анализа. Отличить стеганографический паддинг от защитного сложно.
- **HPACK/Huffman-паддинг** — микроскопический канал (несколько бит на заголовок), но
  при большом числе запросов даёт приличную пропускную способность.

## Шаг 5: пайплайн разбора

1. `tshark -r dump.pcap -Y http2` — есть ли HTTP/2.
2. Экспорт TLS-ключей (если есть `SSLKEYLOGFILE`) → расшифровка, иначе анализ метаданных.
3. Скрипт по кадрам: собрать padding length, посмотреть распределение (аномально
   большой/регулярный паддинг — подозрительно).
4. Для QUIC — проверить PADDING-кадры и длину connection ID.
5. Помнить: без ключей шифрования содержимое недоступно, но **метаданные** (размеры,
   тайминги, число кадров) остаются.

## Что мы теперь знаем

- HTTP/2 — **бинарные кадры**; каналы: padding, PRIORITY/WINDOW_UPDATE, порядок заголовков.
- **HPACK** использует Huffman с паддингом — микро-канал на каждый заголовок.
- HTTP/3 работает поверх **QUIC**: каналы — connection ID, `PADDING`-кадры, длины потоков.
- Современный трафик зашифрован; DPI видит только **метаданные**.
- Легальный паддинг маскирует стеганографический.

## Куда дальше

Мы разобрали современные сетевые каналы. Дальше — **электронная почта**: как прячут
данные в MIME-структуре, заголовках SMTP и вложениях. А пока главное запомни:
**бинарные протоколы прячут данные в служебных полях**, а легальный паддинг отлично
маскирует канал.
