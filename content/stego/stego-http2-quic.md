## Вопрос, с которого всё начинается

В уроке про HTTP-скрытые каналы мы прятали данные в заголовках, cookies и chunked-
кодировании. Но современный веб всё чаще работает по **HTTP/2** и **HTTP/3 (QUIC)**.
Там заголовки — уже не текст, а бинарные структуры. Значит, и каналы другие. Где
прячутся данные в этих протоколах?

## Наш пример

Дан дамп `http2.pcap`. Смотрим на него:

```
$ tshark -r http2.pcap
1  0.000000  10.0.0.5 → 203.0.113.10  TCP  74 51234 → 443 [SYN]
2  0.000210 203.0.113.10 → 10.0.0.5   TCP  74 443 → 51234 [SYN, ACK]
...
6  0.001900  10.0.0.5 → 203.0.113.10  HTTP2 98 HEADERS[1]
7  0.002100 203.0.113.10 → 10.0.0.5   HTTP2 86 HEADERS[1]
```

Никакого `GET / HTTP/1.1` — трафик бинарный. Разберём, где тут можно спрятать биты.

## Шаг 1: HTTP/2 — бинарные кадры

HTTP/2 разбит на **кадры** (frames). У каждого кадра есть заголовок из 9 байт:
длина (24 бита), тип (8 бит), флаги (8 бит), идентификатор потока (31 бит). Типы кадров:
`DATA`, `HEADERS`, `PRIORITY`, `RST_STREAM`, `SETTINGS`, `PING`, `GOAWAY`, `WINDOW_UPDATE`,
`CONTINUATION`.

Потенциальные каналы:

1. **Padding.** Кадры `DATA` и `HEADERS` имеют **padding length** и байты заполнения —
   их можно менять, и содержимое не повлияет на смысл. Классический канал: длина
   паддинга кодирует биты.
2. **`PRIORITY` и `WINDOW_UPDATE`.** Служебные числа (веса, размеры окна) можно
   переставлять в допустимых пределах — тайминг/числовые covert-каналы.
3. **Порядок и дублирование заголовков.** HTTP/2 допускает несколько `cookie` и
   псевдозаголовков `:method`, `:path` в определённом порядке — порядок кодирует биты.

## Шаг 2: HPACK и Huffman-паддинг

Заголовки в HTTP/2 сжимаются **HPACK**. Он использует статическую и динамическую таблицы
и **Huffman-кодирование** строк. Ключевая деталь: Huffman-код может дополняться до
границы байта — это **padding**, который декодер обязан игнорировать. Значит, в этих
битах можно спрятать данные.

```
$ python3 hpack_analyze.py http2.pcap
HEADERS frame #1
  :method = GET
  :path = /
  :authority = example.com
  padding bits after Huffman: 01101110 01110100 ...
  -> nto{h2_hp4ck_p4dding}
```

Идея: сообщение режется на куски, каждый кусок «упаковывается» в хвост Huffman-кода
заголовка. Декодер HPACK их игнорирует, а наш парсер — извлекает.

## Шаг 3: HTTP/3 и QUIC

HTTP/3 работает поверх **QUIC** (UDP). QUIC — это набор **кадров** внутри **потоков**,
мультиплексированных по **connection ID**.

Каналы:

1. **Connection ID.** Идентификатор соединения произвольной длины (0–20 байт) и его
   смена в процессе — можно менять и прятать данные.
2. **`PADDING` кадр.** Явный кадр-заполнитель — идеальное место: его содержимое не
   интерпретируется.
3. **`STREAM` кадры.** Данные приложения — прямой канал (но это уже «обычный» туннель).
4. **Длина потоков и порядок кадров.** Числовые/тайминговые covert-каналы.

```
$ tshark -r quic.pcap -Y quic
1  0.000000 10.0.0.5 → 203.0.113.10  QUIC 1356 Initial, DCID=8a3f...
2  0.000300 203.0.113.10 → 10.0.0.5   QUIC 1180 Initial, SCID=...
$ python3 quic_padding.py quic.pcap
PADDING frames: 3
decoded: nto{qu1c_p4dding_c0v3rt}
```

## Шаг 4: почему это тяжелее обнаружить

- Трафик **бинарный** и часто **зашифрован** (TLS 1.3 в HTTP/2, встроенное шифрование
  в QUIC). DPI видит только размеры, тайминги и метаданные.
- **Паддинг легален** — его используют и «нормальные» клиенты для защиты от
  трафик-анализа. Отличить стеганографический паддинг от защитного сложно.
- **HPACK/Huffman-паддинг** — микроскопический канал (несколько бит на заголовок), но
  при большом числе запросов даёт приличную пропускную способность.

## Шаг 5: пайплайн разбора

1. `tshark -r dump.pcap -Y http2` — есть ли HTTP/2.
2. Экспорт TLS-ключей (если есть `SSLKEYLOGFILE`) → расшифровка, иначе анализ метаданных.
3. Скрипт по кадрам: собрать padding length, посмотреть распределение (аномально
   большой/регулярный паддинг — подозрительно).
4. Для QUIC — проверить PADDING-кадры и длину connection ID.
5. Помнить: без ключей шифрования содержимое недоступно, но **метаданные** (размеры,
   тайминги, число кадров) остаются.

## Что мы теперь знаем

- HTTP/2 — **бинарные кадры**; каналы: padding, PRIORITY/WINDOW_UPDATE, порядок заголовков.
- **HPACK** использует Huffman с паддингом — микро-канал на каждый заголовок.
- HTTP/3 работает поверх **QUIC**: каналы — connection ID, `PADDING`-кадры, длины потоков.
- Современный трафик зашифрован; DPI видит только **метаданные**.
- Легальный паддинг маскирует стеганографический.

## HTTP/2: кадры, флаги и SETTINGS

Каждый кадр HTTP/2 — 9-байтовый заголовок: длина (24 бита), тип (8), флаги (8),
stream id (31). Типы кадров и их «гибкие» поля:

- **`DATA`** — тело; флаги `END_STREAM`, `PADDED`; при `PADDED` есть длина паддинга.
- **`HEADERS`** — заголовки; `END_HEADERS`, `PRIORITY`, `PADDED`.
- **`PRIORITY`** — вес потока (1–256) и зависимость; числа в допустимых пределах
  можно переставлять.
- **`SETTINGS`** — параметры соединения (`MAX_FRAME_SIZE`, `INITIAL_WINDOW_SIZE` и
  др.); легально варьируются.
- **`WINDOW_UPDATE`** — размер окна (31 бит); числовой канал.
- **`PING`** — 8 байт произвольных данных, которые обязаны быть эхом возвращены!

Последнее — отдельный подарок: `PING` несёт 8 байт opaque-данных, а сервер обязан
вернуть их же. Это готовый двусторонний канал.

## HPACK: таблицы и Huffman

Заголовки в HTTP/2 сжаты **HPACK**. Две таблицы: **статическая** (61 предопределённая
пара, например `:method GET` = индекс 2) и **динамическая** (обновляется по ходу
соединения). Строки кодируются либо индексом, либо литералом, либо **Huffman-кодом**.

Ключевая деталь для сокрытия: Huffman-код занимает **нецелое** число байт, поэтому
его дополняют до границы байта **EOS-паддингом**, который декодер обязан
игнорировать. Эти «лишние» биты — микро-канал. На каждый заголовок — несколько бит,
но при тысячах запросов набегает прилично.

```
$ python3 hpack_analyze.py http2.pcap
HEADERS frame #1 (stream 1)
  :method = GET
  :path = /
  :authority = example.com
  huffman padding bits: 01101110 01110100 ...
  -> nto{h2_hp4ck_p4dding}
```

## QUIC: потоки, connection ID и кадры

HTTP/3 работает поверх QUIC (UDP). У QUIC своя модель:

- **Connection ID** — 0–20 байт, произвольной длины; клиент может **менять** его в
  процессе, что и используется для сокрытия.
- **Потоки** — независимые, с номерами; данные приложения идут в `STREAM`-кадрах.
- **Кадры** — `PADDING`, `PING`, `ACK`, `CRYPTO`, `STREAM`, `MAX_DATA`,
  `NEW_CONNECTION_ID`, `RETIRE_CONNECTION_ID` и др.

Идеальные каналы: **`PADDING`** (содержимое не интерпретируется) и **`NEW_CONNECTION_ID`**
(новый ID может быть произвольным). Плюс `PING`-кадры, увеличивающие «шум» размеров.

```
$ tshark -r quic.pcap -Y quic
1  10.0.0.5 → 203.0.113.10  QUIC 1356 Initial, DCID=8a3f9c..., SCID=...
2  203.0.113.10 → 10.0.0.5  QUIC 1180 Initial, DCID=..., SCID=4b21...
$ python3 quic_padding.py quic.pcap
PADDING frames: 3, decoded: nto{qu1c_p4dding_c0v3rt}
```

## Инструменты

- **`tshark -r d.pcap -Y http2`** / `-Y quic` — фильтр по протоколу.
- **`tshark -r d.pcap -T fields -e http2.header.name -e http2.header.value`** —
  выгрузить заголовки в поля.
- **`nghttp` / `nghttp2-client`** — отправить HTTP/2-запрос, `-v` покажет кадры.
- **`h2spec`** — проверка соответствия HTTP/2 (видно, какие поля «гибкие»).
- **`curl --http2` / `curl --http3`** — запрос с выбором версии.
- **`SSLKEYLOGFILE=keys.log`** + настройка `tshark -o tls.keylog_file:keys.log` —
  расшифровка TLS 1.3 для HTTP/2.

## Edge cases и подводные камни

- **Шифрование.** HTTP/2 и HTTP/3 всегда идут по TLS. Без ключей доступны только
  метаданные (размеры, тайминги, число кадров).
- **`PADDED` vs паддинг внутри.** Паддинг бывает на уровне кадра HTTP/2 и на уровне
  Huffman — это **разные** каналы, не путай.
- **Размер кадра.** Если длина паддинга больше длины кадра — кадр невалиден; скрывать
  можно только в допустимых пределах.
- **QUIC Initial.** Часть полей Initial-пакета расшифровывается (по DCID) — не всё
  так «непрозрачно», как кажется.
- **Легальный паддинг.** Клиенты используют padding для защиты от traffic-analysis;
  отличить стеганографию от «нормального» паддинга сложно.

## Что дальше / решение

Сквозной пример: `tshark -Y http2` показывает бинарные кадры; `hpack_analyze.py`
собирает Huffman-паддинг и отдаёт `nto{h2_hp4ck_p4dding}`; для QUIC `quic_padding.py`
читает `PADDING`-кадры и отдаёт `nto{qu1c_p4dding_c0v3rt}`. Без ключей — анализ
метаданных и статистики паддинга.

## Шпаргалка: каналы HTTP/2 и QUIC

| Протокол | Поле/кадр | Тип канала | Заметность |
|----------|-----------|------------|------------|
| HTTP/2 | `PING` data (8 б) | полезная нагрузка | низкая |
| HTTP/2 | Huffman-паддинг | микро-биты | очень низкая |
| HTTP/2 | `PRIORITY` вес | числовой | низкая |
| HTTP/2 | `WINDOW_UPDATE` | числовой | низкая |
| HTTP/2 | порядок заголовков | перестановочный | средняя |
| QUIC | `PADDING` | содержимое | очень низкая |
| QUIC | Connection ID | произвольные байты | низкая |
| QUIC | длины потоков | числовой/тайминг | низкая |

## Полезная привычка

Всегда сохраняй дамп (`tshark -w`) до расшифровки и сравнивай размеры кадров: ровные,
регулярные «ступеньки» паддинга — сильный признак рукотворного канала.

## Куда дальше

Мы разобрали современные сетевые каналы. Дальше — **электронная почта**: как прячут
данные в MIME-структуре, заголовках SMTP и вложениях. А пока главное запомни:
**бинарные протоколы прячут данные в служебных полях**, а легальный паддинг отлично
маскирует канал.
