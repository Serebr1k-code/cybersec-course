## Вопрос, с которого всё начинается

Тебе дали файл `mystery.bin` без описания. Ни формата, ни имени, ни подсказки. Ты
открываешь его — ничего. Как подступиться? Хаотично пробовать инструменты — плохо.
Нужен **системный триаж**: порядок действий, который за несколько шагов говорит,
что это за файл и где в нём данные. Разберём этот порядок.

## Наш пример: файл mystery.bin

```bash
file mystery.bin
```

```text
mystery.bin: PNG image data, 16 x 16, 8-bit/color RGB, non-interlaced
```

Уже первая команда дала зацепку: это PNG, хотя расширение `.bin` нас путало. Это
классическая ловушка: **расширение ничего не значит**, формат определяет
содержимое.

## Шаг 1: почему начинаем с file

`file` читает **магические байты** — первые байты файла, по которым определяется
формат. PNG начинается с `89 50 4E 47`, JPEG — с `FF D8 FF`, ZIP — с `PK\x03\x04`.
Именно поэтому `file` — первая команда триажа: она мгновенно говорит, что перед
нами.

```bash
xxd -l 32 mystery.bin
```

```text
00000000: 8950 4e47 0d0a 1a0a 0000 000d 4948 4452  .PNG........IHDR
```

Подтверждаем: сигнатура PNG на месте.

## Шаг 2: строим карту сигнатур

Дальше нужен инструмент, который покажет **все** сигнатуры внутри файла, а не
только первую. Это `binwalk`:

```bash
binwalk mystery.bin
```

```text
DECIMAL       HEXADECIMAL     DESCRIPTION
0             0x0             PNG image, 16 x 16
1186          0x4A2           Zip archive data, at least v2.0
1450          0x5AA           End of Zip archive
```

Карта говорит: внутри PNG есть **ZIP-архив**. Это вложенный контейнер — типичный
приём CTF. Теперь мы знаем, где искать.

## Шаг 3: энтропия как дополнительный сигнал

`binwalk -E` рисует карту энтропии. Сжатые и зашифрованные участки дают высокую
энтропию (близко к 8 бит/байт). Если видишь резкий всплеск — там, скорее всего,
сжатый контейнер. Это помогает, когда сигнатур нет, но данные явно «не текстовые».

## Шаг 4: достаём вложенное

Есть два пути: извлечь через `binwalk -e` или вручную по смещению. Вручную
надёжнее и понятнее:

```bash
dd if=mystery.bin bs=1 skip=1186 2>/dev/null | file -
```

```text
/dev/stdin: Zip archive data, at least v2.0
```

Мы подтвердили, что по смещению `1186` начинается ZIP. Дальше — распаковка.

## Шаг 5: разбираем содержимое

```bash
binwalk -e mystery.bin
```

```text
Extracted 1 file
$ cat _mystery.bin.extracted/note.txt
nto{unkn0wn_tr1ag3}
```

Внутри ZIP лежал текстовый файл с флагом. Цепочка: неизвестный файл → PNG → ZIP →
текст.

## Шаг 6: если бы сигнатур не было

Иногда `binwalk` не находит ничего. Тогда:

- `strings mystery.bin | grep -i nto` — поиск текстовых зацепок;
- `xxd mystery.bin | tail` — данные после конца контейнера;
- проверка каждого канала/битовой плоскости (если изображение);
- проверка метаданных (`exiftool`).

Отсутствие сигнатур не значит «пусто»: данные могли встроить в пиксели или
зашифровать.

## Шаг 7: фиксируем процесс

Порядок триажа, который работает почти всегда:

1. `file` — формат;
2. `xxd -l 64` — подтвердить сигнатуру;
3. `binwalk` — карта вложенного;
4. `strings | grep nto` — быстрые зацепки;
5. `xxd | tail` — хвост;
6. профильный инструмент по формату.

Этот порядок не зависит от того, что именно спрятано: он всегда даёт следующую
гипотезу.

## Шаг 8: полный разбор с нуля

Пройдём триаж ещё раз, подробно и с рассуждениями. Файл `mystery.bin` неизвестен.
Первое, что мы делаем, — не открываем его, а смотрим байты. `file mystery.bin`
говорит PNG. Почему это важно? Потому что формат определяет весь дальнейший план:
для PNG работают `pngcheck`/`zsteg`, для JPEG — `jpegtran`, для архива — `unzip`.
Ошибиться с форматом — значит выбрать неверные инструменты и потерять время.

Второй шаг — `xxd -l 64 mystery.bin`. Мы подтверждаем сигнатуру своими глазами и
заодно видим первые байты заголовка. Здесь можно заметить подделку: если сигнатура
выглядит «почти правильной», но отличается на байт — это anti-tool (см. отдельный
урок). Третий шаг — `binwalk mystery.bin`: он показывает все сигнатуры внутри, а не
только первую. Именно здесь мы узнаём о вложенном ZIP.

## Шаг 9: как читать вывод binwalk

Вывод `binwalk` — таблица из трёх колонок: десятичное смещение, шестнадцатеричное
смещение и описание. Читать надо сверху вниз. Первая строка — обычно сам файл
(PNG). Следующие — вложенные объекты. Важно: `binwalk` может ошибаться на
сжатых данных (ложные сигнатуры), поэтому найденное стоит подтверждать.

Если в выводе несколько объектов, начни с того, что ближе к началу: он, скорее
всего, содержит остальные. Если видишь «Zip archive» — это почти всегда контейнер
с данными.

## Шаг 10: ручное извлечение против binwalk -e

`binwalk -e` удобен, но иногда извлекает не то или ломается на нестандартном
файле. Ручной `dd` надёжнее, потому что ты сам задаёшь смещение и длину:

```bash
dd if=mystery.bin bs=1 skip=1186 of=inner.zip 2>/dev/null
unzip -l inner.zip
```

```text
Archive:  inner.zip
  Length      Name
       23  note.txt
```

Так ты контролируешь процесс. Особенно это важно, когда в файле несколько
вложенных объектов и автоматика путает границы.

## Шаг 11: что делать с текстовыми зацепками

Иногда флаг не в отдельном файле, а прямо в бинарнике как строка. Тогда
`strings mystery.bin | grep -i nto` даёт результат мгновенно. Но будь осторожен с
приманками: строка может выглядеть как флаг, но быть частью задачи-обманки.
Проверяй, что формат совпадает с ожидаемым (например, `nto{...}`), и что флаг
осмысленный.

## Шаг 12: хвосты и данные после конца

Очень частый приём — данные **после** конца контейнера. Для PNG это байты после
`IEND`, для JPEG — после `FFD9`. Их не видит ни один парсер, потому что «файл
закончился». Смотри хвост:

```bash
xxd mystery.bin | tail -5
```

Если после сигнатуры конца идёт что-то осмысленное — это вложенные данные. Их
достают по смещению.

## Шаг 13: чек-лист триажа

Составим чек-лист, которым можно пользоваться всегда:

1. `file` — формат;
2. `xxd -l 64` — сигнатура глазами;
3. `binwalk` — карта сигнатур;
4. `strings | grep nto` — текстовые зацепки;
5. `xxd | tail` — хвост;
6. `exiftool` — метаданные;
7. профильные инструменты по формату.

Этот чек-лист не заменяет мышление, но гарантирует, что ты не пропустил очевидное.

## Шаг 14: частые ошибки

Первая — доверять расширению файла. Вторая — не смотреть хвост. Третья — не
проверять вложенность (ZIP в PNG). Четвёртая — использовать только один инструмент
и сдаваться. Пятая — не фиксировать результат (флаг нашёл, но не записал).

## Шаг 15: почему триаж — навык

Триаж — это не про конкретный инструмент, а про **порядок мышления**. Ты всегда
начинаешь с самого дешёвого и информативного действия (формат), затем расширяешь
картину (сигнатуры, хвост), затем углубляешься (профильные инструменты). Такой
подход работает для любого артефакта — изображения, аудио, архива, дампа.

## Шаг 16: разбор примера с несколькими слоями

Представь более сложный артефакт: `challenge.dat`, внутри — JPEG, внутри JPEG —
base64-строка, после декодирования — ZIP с флагом. Триаж выглядит так. `file
challenge.dat` — JPEG (по сигнатуре, несмотря на расширение). `binwalk` — одна
сигнатура JPEG. `strings | grep` — base64-строка. Декодируем base64 → получаем ZIP.
`unzip` → флаг. Каждый слой открывает следующий. Умение вести цепочку, не теряя
шаги, — ключевой навык.

## Шаг 17: ведение заметок

В многослойных задачах легко запутаться. Веди короткие заметки: что нашли на каждом
шаге, какой инструмент, какой результат. Это особенно важно под таймером и при
командной работе. Заметки также помогают вернуться на шаг назад, если гипотеза не
подтвердилась.

## Шаг 18: что делать при тупике

Если триаж не дал результата, вернись к базовым вопросам. Точно ли определён формат?
Нет ли подделки сигнатуры? Не пропущен ли хвост? Не зашифрованы ли данные (тогда
нужен пароль)? Тупик почти всегда означает, что пропущено простое действие, а не
что «данных нет».

## Шаг 19: итог по триажу

Триаж — фундамент всей стего-работы. Он даёт карту артефакта за минуты и не даёт
утонуть в переборе. Освоив порядок (формат → сигнатуры → хвост → профильные
инструменты), ты решаешь большинство задач уверенно и быстро.

## Шаг 20: заключение

Триаж — это привычка начинать с простого и информативного. Формат, сигнатуры,
хвост, метаданные — четыре шага, которые закрывают большинство задач. Дальше
остаётся только углубиться в конкретный формат. Держи этот порядок в голове, и
незнакомый файл перестанет пугать.

## Шаг 21: заметка о кодировках

Иногда данные внутри контейнера закодированы (base64, hex). Тогда `strings` покажет
«странные» строки, а не флаг напрямую. Учись распознавать кодировки: длинные строки
из `A–Z a–z 0–9 +/` — base64, строки из `0–9 a–f` чётной длины — hex. Декодируй их
и ищи флаг в результате. Это часто последний шаг триажа.

## Что мы теперь знаем

- Расширение файла ничего не значит; формат определяют магические байты.
- `file` + `xxd` дают формат; `binwalk` — карту вложенных сигнатур.
- Энтропия подсказывает сжатые/зашифрованные участки.
- Вложенное достают `binwalk -e` или вручную через `dd` по смещению.
- Системный порядок действий важнее перебора инструментов.
