## Вопрос, с которого всё начинается

В CTF дали `video.mp4` — сжатое H.264-видео. Пиксельный LSB по кадрам ничего не даёт: сохраняешь кадр в PNG, читаешь младшие биты — сплошной шум. `binwalk` чист, потоки обычные. Но подсказка говорит, что флаг «внутри видеокодека».

Ответ: данные спрятаны не в пикселях, а в **параметрах сжатия** — векторах движения и режимах предсказания. Покадровый LSB в lossy-видео обречён (декодер не восстановит младшие биты точно), а вот сами параметры передаются как есть и декодируются детерминированно. Разберём, как туда попасть.

## Наш пример: video.mp4

Современные кодеки (H.264/AVC, H.265/HEVC) не хранят кадры как картинки. Они хранят **разницу** между кадрами. Для каждого блока изображения кодер ищет похожий блок в опорном кадре и записывает **вектор движения** (motion vector) — пару чисел, куда «сдвинулся» этот блок. Плюс остаточные коэффициенты. Именно эти числа — векторы, режимы, квантованные коэффициенты — «шумные» сами по себе, и их правка не разрушает видео.

Начнём с типов кадров. Видео состоит из трёх видов кадров: **I** (ключевой, кодируется целиком), **P** (предсказан от прошлого), **B** (предсказан от прошлого и будущего). Смотрим их через `ffprobe`:

```bash
$ ffprobe -v error -show_frames -select_streams v:0 \
  -show_entries frame=pict_type -of csv=p=0 video.mp4 | tr '\n' ' '
I P B B P B B P B B P
```

Строка `I P B B P B B...` — это последовательность кадров. Она уже может нести информацию: если порядок P/B нестандартный, это канал (см. шаг про GOP).

## Шаг 1: достаём сырой поток

`ffprobe` показывает метаданные контейнера, но сами биты кодека — векторы движения, режимы — лежат в **NAL-юнитах** (Network Abstraction Layer units), из которых собран H.264-поток. В MP4 они упакованы в боксы, поэтому сначала распаковываем в «сырой» поток битфильтром `h264_mp4toannexb`:

```bash
$ ffmpeg -i video.mp4 -c:v copy -bsf:v h264_mp4toannexb -f h264 raw.h264
$ ls -l raw.h264
-rw-r--r-- 1 user user 1843200 raw.h264
```

Опция `-c:v copy` опять обязательна: перекодирование пересчитало бы все параметры и стёрло канал. Теперь у нас есть байты кодека, а не «контейнер поверх них».

## Шаг 2: почему параметры сжатия — хороший носитель

Сравним два подхода таблицей:

| Метод | Устойчивость к перекодированию | Ёмкость | Сложность |
|---|---|---|---|
| Покадровый LSB | очень низкая | высокая | низкая |
| Различия кадров | низкая | средняя | средняя |
| Векторы движения | средняя | средняя | высокая |
| Режимы предсказания | высокая | низкая | очень высокая |
| DCT/DST-коэффициенты | средняя | высокая | высокая |

Вывод: чем глубже метод уходит в кодек, тем он устойчивее и незаметнее — и тем сложнее его реализовать и извлечь. Покадровый LSB проигрывает, потому что сжатие с потерями не гарантирует точного восстановления младших бит.

## Шаг 3: данные в чётности векторов движения

Идея: компонента вектора `mv_x` — целое число (сдвиг блока по горизонтали). Стеганография меняет его на соседнее значение, отличающееся на 1, — картинка почти не меняется, а **чётность** (`mv_x % 2`) кодирует бит. Собираем чётности по порядку блоков в строку бит и группируем по 8:

```python
# mv_x_list — список компонент x векторов движения по порядку блоков
bits = "".join(str(abs(x) % 2) for x in mv_x_list)
msg = "".join(chr(int(bits[i:i+8], 2)) for i in range(0, len(bits)//8*8, 8))
print(msg)
```

Если первые байты `msg` читаемы — канал найден. Получить сам `mv_x_list` можно только парсером битстрима: `ffprobe` векторы движения не показывает. Варианты парсеров: `h264bitstream` (C), `PyAV` (Python-обёртка над libavcodec), кастомный код на libavcodec. Частичный дамп NAL доступен через отладочный лог:

```bash
$ ffmpeg -loglevel debug -i raw.h264 -f null - 2>&1 | grep -i 'mv' | head
```

## Шаг 4: режимы предсказания и partition

Для каждого блока кодер выбирает режим: **intra** (кодировать сам блок, как картинку) или **inter** (сослаться на другой кадр). Если два режима дают почти одинаковую ошибку, кодер волен выбрать любой — и эта «свобода выбора» кодирует бит. Детектировать почти невозможно: решение выглядит как результат обычной оптимизации rate-distortion.

То же с **partition modes** — размером блока: 16×16 или 8×8 при близкой стоимости. Выбор одного из равнозначных вариантов — бит. Такие каналы устойчивы к перекодированию, но вмещают мало.

## Шаг 5: GOP-структура

**GOP** (Group of Pictures) — шаблон чередования I/P/B-кадров. Стандартный `IBBPBBP` можно варьировать: переставлять P и B, менять число B-кадров, вставлять лишний I. Каждый выбор кодирует биты, а декодер всё равно восстановит корректный поток. Это «структурный» канал — он не трогает пиксели, только организацию. Строка типов кадров из шага 0 и есть материал для такого анализа.

## Инструменты визуализации

Иногда проще увидеть канал глазами. У `ffplay` есть флаг экспорта векторов движения:

```bash
$ ffplay -flags2 +export_mvs -i video.mp4
```

`+export_mvs` заставляет декодер вытащить векторы движения — их накладывают на кадр, и аномальный «шум» канала становится заметен. Плюс GUI-анализаторы вроде Elecard StreamEye рисуют карту блоков и векторов.

## Ограничения метода

Кодирующие каналы требуют либо исходного (не пережатого) файла, либо знания конкретного алгоритма встраивания. Универсального инструмента «найти всё в векторах» не существует: каждый метод извлекается своим скриптом. Поэтому в CTF такие задачи дают с подсказкой (какой кодек, какие параметры), а «слепой» взлом — исследовательская работа. Если задача кажется неразрешимой — вернись к более простым каналам: контейнерным потокам (`stego-video-audio-mux`) и покадровому анализу (`stego-video-frames`).

## Если не сработало

Если `ffprobe` не показал лишних потоков, а векторы движения недоступны, проверь по порядку: не перекодировано ли видео (сравни битрейт и кодек с оригиналом); нет ли аномалий в последовательности типов кадров (нестандартный GOP); экспортируй векторы (`-flags2 +export_mvs`) — иногда «шум» видно глазами; проверь более простые каналы — метаданные контейнера и субтитры. Кодирующие каналы капризны: без подсказки о конкретном алгоритме «слепое» извлечение почти всегда упирается в стену, и тогда разумно вернуться к контейнерным и покадровым методам.

## Что мы теперь знаем

1. H.264/HEVC хранят разницу кадров, а не картинки; параметры сжатия — носитель для стего.
2. Покадровый LSB в lossy-видео не работает: младшие биты не восстанавливаются.
3. Векторы движения прячут данные в чётности `mv_x`/`mv_y`.
4. Режимы предсказания и partition кодируют биты через выбор «равнозначного» варианта.
5. Сырой поток достают через `-bsf:v h264_mp4toannexb`; `-c copy` обязателен.
6. Перекодирование уничтожает канал; `ffprobe` показывает не всё — нужен парсер битстрима.
