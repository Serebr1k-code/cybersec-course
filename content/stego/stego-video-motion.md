Современные видеокодеки (H.264/AVC, H.265/HEVC) не хранят кадры как картинки. Они хранят **разницу** между кадрами: для каждого блока кодируется вектор движения (motion vector), ссылающийся на похожий блок в опорном кадре, и остаточные коэффициенты. Именно эти параметры — векторы движения, режимы предсказания, квантованные коэффициенты — являются богатым и устойчивым носителем для стеганографии: они и так «шумные», а их модификация не разрушает видео.

## Почему компрессионные параметры лучше пикселей

Покадровый LSB в сжатом видео не работает: декодер восстанавливает кадр с потерями, и младшие биты «плывут». Зато сами параметры сжатия передаются как есть и декодируются детерминированно. Модулируя их (например, чётность вектора движения), можно встроить данные, которые переживут декодирование и останутся незаметны глазу.

Каналы:

- **Векторы движения (motion vectors).** Чётность/младший бит компоненты `mv_x`, `mv_y`.
- **Режимы предсказания.** Выбор между несколькими «эквивалентными» режимами кодирует бит.
- **Квантованные DCT/DST-коэффициенты.** Классика, как в JPEG-стеганографии (F5 и др.).
- **Размер и разбиение блоков.** Варианты partition (16×16, 8×8, 4×4) кодируют данные.
- **Структура GOP / I/P/B-кадров.** Редкие перестановки кодируют биты.

## Инструменты и команды

- **`ffmpeg`/`ffprobe`** — демуксинг, извлечение кадров, анализ потоков.
- **`ffprobe -show_frames`** — типы кадров и их параметры.
- **`h264bitstream`/`h26x-extractor`** — разбор NAL-юнитов и синтаксиса.
- **`OpenCV`** — оценка движения (`calcOpticalFlowFarneback`) для сравнения.
- **`Elecard StreamEye`** (GUI) — визуализация векторов движения.
- **`tranco`/исследовательские скрипты** — академические реализации.

Разбор структуры кадров:

```bash
ffprobe -v error -show_frames -select_streams v:0 \
  -show_entries frame=pict_type,coded_picture_number video.mp4 | head -20
```

Извлечь NAL-юниты (сырой H.264):

```bash
ffmpeg -i video.mp4 -c:v copy -bsf:v h264_mp4toannexb -f h264 raw.h264
```

## Разобранный пример: данные в векторах движения

В учебном примере вектор движения по горизонтали (`mv_x`) принимает значения, чья чётность кодирует биты. Извлекаем последовательность `mv_x` через исследовательский парсер (или `ffprobe` с `-show_frames` там, где экспонируются motion-поля):

```bash
$ ffprobe -v error -show_frames -show_entries frame=pkt_size,pict_type video.mp4 | head
pict_type=I
pkt_size=5231
pict_type=P
pkt_size=1832
```

Если доступен парсер битстрима, собираем чётность:

```python
# mv_x_list — список компонент x векторов движения по порядку блоков
bits = "".join(str(abs(x) % 2) for x in mv_x_list)
# группируем по 8 бит
msg = "".join(chr(int(bits[i:i+8], 2)) for i in range(0, len(bits)//8*8, 8))
print(msg)
```

## Межкадровое предсказание и режимы

H.264/HEVC выбирают для каждого блока режим: intra (кодировать сам блок) или inter (ссылаться на другой кадр). Если два режима дают почти одинаковую ошибку, кодер может выбрать любой — это «свобода выбора», которую использует стеганография: бит кодируется тем, какой из равнозначных режимов выбран. Детектировать сложно, потому что решение выглядит как результат обычной оптимизации.

Аналогично **partition modes**: 16×16 vs 8×8 при близкой стоимости — канал.

## Извлечение через битстрим

Практический путь в CTF:

1. `ffmpeg -bsf:v h264_mp4toannexb` — получить сырой поток.
2. Разобрать NAL-юниты (`h264bitstream`, `ffmpeg -loglevel debug`).
3. Найти slice-заголовки и motion-векторы.
4. Собрать чётность/младшие биты и декодировать.

```bash
ffmpeg -i video.mp4 -c:v copy -bsf:v h264_mp4toannexb -f h264 raw.h264
xxd raw.h264 | head -5
```

## Сравнение с покадровым подходом

| Метод | Устойчивость к перекодированию | Ёмкость | Сложность |
|---|---|---|---|
| Покадровый LSB | очень низкая | высокая | низкая |
| Данные в различиях кадров | низкая | средняя | средняя |
| Motion vectors | средняя | средняя | высокая |
| Режимы предсказания | высокая | низкая | очень высокая |
| DCT/DST-коэффициенты | средняя | высокая | высокая |

Вывод: чем глубже в кодек уходит метод, тем он устойчивее и незаметнее, но тем сложнее реализация и извлечение.

## Частые ошибки и подводные камни

- **Пытаться LSB по декодированным кадрам сжатого видео** — потеряете данные.
- **Забыть про B-кадры.** Векторы движения зависят от порядка предсказания.
- **Не учитывать перекодирование.** Оно пересчитывает параметры и уничтожает канал.
- **Игнорировать `-bsf:v h264_mp4toannexb`.** Без него NAL-юниты не собрать.
- **Путать пиксельное движение с векторами кодека.** Это разные вещи.
- **Считать, что ffprobe покажет всё.** Многие поля motion-векторов доступны только битстрим-парсерам.

## Что дальше / решение

- Убедитесь, что видео не перекодировано (сравните с оригиналом).
- Извлеките сырой поток: `-bsf:v h264_mp4toannexb`.
- Разберите битстрим и соберите чётность motion-векторов.
- Проверьте режимы предсказания и partition на «равнозначные» выборы.
- Если сложно — вернитесь к более простым каналам (`stego-video`, `stego-video-frames`).

## Внутрикадровое предсказание и его свобода выбора

HEVC и H.264 кодируют блок не только межкадрово, но и внутри кадра: intra-предсказание выбирает направление (DC, planar, 33 угловых режима в HEVC). Если два направления дают почти одинаковую ошибку, кодер выбирает любое — эта «свобода» и есть канал. Бит кодируется тем, какой из равнозначных режимов выбран. Детектировать сложно, потому что решение выглядит как результат оптимизации rate-distortion.

Аналогично работают **transform skip** (флаг пропуска DCT) и **CABAC-контексты**: изменение контекста кодирования меняет битовую длину, что можно использовать как канал.

## GOP-структура и её модуляция

Группа кадров (GOP) задаёт порядок I/P/B-кадров. Стандартный шаблон (например, IBBPBBP) можно варьировать: переставлять P и B, менять число B-кадров, вставлять дополнительный I-кадр. Каждый выбор кодирует биты, а декодер всё равно восстановит корректный поток. Это «структурный» канал: он не трогает пиксели, только организацию потока.

```bash
ffprobe -v error -show_frames -select_streams v:0 \
  -show_entries frame=pict_type -of csv=p=0 video.mp4 | tr '\n' ' '
```

Последовательность типов кадров (I/P/B) — это уже строка, которую можно анализировать на паттерны.

## Извлечение через исследовательские парсеры

Для реального извлечения нужен парсер битстрима. Варианты:

- **`h264bitstream`** (C) — разбор синтаксиса H.264, доступ к motion vectors.
- **`ffmpeg`** с `-loglevel debug` — частичный дамп NAL.
- **`libavcodec`** через кастомный код — доступ к MVs из декодера.
- **Python-обёртки** (например, `PyAV`) — удобный доступ к кадрам и метаданным.

```bash
ffmpeg -i video.mp4 -c:v copy -bsf:v h264_mp4toannexb -f h264 raw.h264
ffmpeg -loglevel debug -i raw.h264 -f null - 2>&1 | grep -i 'mv' | head
```

Собрав компоненты векторов, считают их чётность и собирают байты — так извлекается сообщение.

## Стойкость к перекодированию

Главная слабость кодирующих каналов — перекодирование. Если видео пересжали (сменили битрейт, разрешение, кодек), параметры пересчитываются и канал разрушается. Методы повышения стойкости:

- **Встраивать в «устойчивые» решения** — те, что сохранятся при пережатии.
- **Использовать избыточность и ECC.**
- **Прятать в структурные элементы** (GOP, метаданные уровня потока), которые перекодирование не всегда меняет.
- **Комбинировать** с аудиоканалом для резервирования.

## Практический разбор: CTF-сценарий

Типовой ход:

1. `ffprobe` — убедиться, что видео не перекодировано (сравнить битрейт/кодек).
2. `ffmpeg -bsf:v h264_mp4toannexb` — получить сырой поток.
3. Найти slice-заголовки и векторы движения парсером.
4. Собрать чётность `mv_x`/`mv_y` в биты.
5. Декодировать биты (ASCII/base64), проверить длину-префикс.

Если готового парсера нет, а задача «учебная», часто достаточно анализа типов кадров и размеров (`pkt_size`) — аномалии выдают канал.

## Инструменты визуализации

- **Elecard StreamEye** — карта векторов движения и блоков.
- **`ffplay` с `-v debug`** — визуальный контроль.
- **`veejay`/`shotdetect`** — анализ структуры кадров.

```bash
ffplay -flags2 +export_mvs -i video.mp4
```

Флаг `+export_mvs` заставляет ffmpeg экспортировать векторы движения — их можно наложить на кадр и увидеть «шум» канала глазами.

## Ограничения метода

Кодирующие каналы требуют либо исходника (не пережатого), либо знания конкретного алгоритма. В отличие от метаданных контейнера, здесь нет «универсального» инструмента: каждый метод извлекается своим скриптом. Поэтому в CTF такие задачи дают вместе с подсказкой (архитектура кодера, параметры встраивания), а «слепой» взлом — исследовательская задача.
