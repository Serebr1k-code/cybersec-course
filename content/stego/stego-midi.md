## Вопрос, с которого всё начинается

Тебе дали `tune.mid` — MIDI-файл. Это не звук: в нём нет сэмплов, только «нажми
ноту до первой октавы, держи 200 мс». Где в таком файле вообще можно спрятать
сообщение? Оказывается, в MIDI полно «служебных» полей, которые плееры не играют,
но хранят. Разберём файл от начала.

## Наш пример: файл tune.mid

```bash
file tune.mid
xxd -l 64 tune.mid
```

```text
tune.mid: Standard MIDI data (format 0) using 1 track at 1/480
00000000: 4d54 6864 0000 0006 0000 0001 01e0 4d54  MThd..........MT
00000010: 726b 0000 0018 00ff 0114 6e74 6f7b 6d31  rk........nto{m1
00000020: 6431 5f74 3378 745f 3376 336e 747d       d1_t3xt_3v3nt}
```

Видим `MThd` — заголовок файла, затем `MTrk` — трек, а внутри трека ASCII-текст
`nto{...}`. Значит, закладка — в **мета-событии**. Разберём, как это устроено.

## Шаг 1: структура Standard MIDI File

SMF (Standard MIDI File) — это «партитура», а не звук. Файл состоит из **чанков**:

- **`MThd`** — заголовок. После 4 байт типа и 4 байт длины идут: формат (0/1/2),
  число треков и **division** (сколько «тиков» в четвертной ноте; у нас `01e0` = 480).
- **`MTrk`** — трек: 4 байта типа, 4 байта длины, затем поток **событий**.

Длина в SMF — **big-endian** (как в JP2/ISOBMFF). Заголовок всегда 6 байт данных.

## Шаг 2: события трека

Каждое событие начинается с **дельта-времени** — сколько тиков подождать до него
(переменная длина, 7 бит на байт, старший бит = «продолжение»). Затем идёт тип:

- `8n` — note off, `9n` — note on (n — канал).
- `An` — полифоническое давление, `Bn` — контроллер (громкость, панорама).
- `Cn` — смена инструмента, `Dn` — давление канала, `En` — pitch bend.
- **`FF <тип> <длина> <данные>`** — **мета-событие**. Тип `01` — текст, `02` —
  copyright, `03` — имя трека, `04` — название инструмента, `05` — текст песни
  (лирика), `06` — маркер, `07` — cue point, `2F` — конец трека.

В нашем файле после дельты `00` идёт `FF 01 14` — мета-событие «текст» длиной
`0x14` = 20 байт. Следующие 20 байт и есть `nto{m1d1_t3xt_3v3nt}`.

## Шаг 3: достаём текст вручную

```bash
python3 - <<'PY'
d = open('tune.mid','rb').read()
i = d.find(b'MTrk') + 8
while i < len(d):
    # читаем дельта-время (переменная длина)
    while d[i] & 0x80:
        i += 1
    i += 1
    if d[i] == 0xFF:
        typ = d[i+1]
        ln = d[i+2]
        data = d[i+3:i+3+ln]
        if typ == 0x01:
            print(data.decode('latin-1'))
        i += 3 + ln
        if typ == 0x2F:
            break
    else:
        break
PY
```

```text
nto{m1d1_t3xt_3v3nt}
```

Это самый частый MIDI-приём: флаг прячут в текстовом или лирическом мета-событии.

## Шаг 4: другие места сокрытия в MIDI

- **Ноты и velocity.** Младшие биты номеров нот или значений скорости (`9n <нота>
  <velocity>`) могут нести биты. На слух это почти незаметно.
- **Дельта-времена.** Длительности пауз — отличный тайминг-канал: чётное/нечётное
  число тиков кодирует 0/1.
- **Порядок/лишние треки.** Добавленный пустой трек с данными.
- **Хвост после `2F` (End of Track)** — парсеры часто не читают дальше.
- **`Cn` (instrument) и `Bn` (controller)** — произвольные значения.

## Шаг 5: инструменты

```bash
strings tune.mid | grep -iE 'nto|flag|comment'
xxd tune.mid | grep -i '6e74 6f7b'   # 'nto{'
midicsv tune.mid > tune.csv && grep -i text tune.csv
```

`midicsv` (из пакета `midicsv`) превращает MIDI в CSV, где все события видны
строками. `strings` ловит читаемый текст, `xxd` + grep — конкретные сигнатуры.

## Шаг 6: сокрытие в нотах и velocity

Если текстовых событий нет, смотрим на сами ноты. Событие Note On — это `9n <нота>
<velocity>`: `n` — канал, нота — номер (0..127), velocity — скорость нажатия (0..127).
Младший бит номера ноты или velocity можно использовать как бит сообщения. На слух
разница между нотой 60 и 61 — это полтона, что заметно, а вот velocity 100 против
101 — практически неразличимо.

Ещё тоньше — **дельта-времена**. Каждое событие предваряется паузой в тиках. Если
закодировать биты чётностью числа тиков, получится тайминг-канал: плеер играет почти
так же, а данные едут. Именно так работают «музыкальные» стегосистемы.

## Шаг 7: структура SMF в деталях

Соберём всё вместе. Формат 0 — один трек, формат 1 — несколько синхронных треков,
формат 2 — независимые. Division задаёт сетку: `01e0` = 480 тиков на четверть (это
стандарт для большинства DAW). Переменная длина дельты кодирует большие паузы:
продолжение обозначается старшим битом.

Порядок разбора трека всегда один: читаем дельту → читаем тип события → если мета,
читаем тип/длину/данные → повторяем до `FF 2F 00` (End of Track). Всё, что лежит
после End of Track, спецификацией не описано — и часто остаётся непрочитанным.

## Шаг 8: мини-справочник мета-событий

| Тип | Значение |
|---|---|
| `00` | номер последовательности |
| `01` | произвольный текст |
| `02` | copyright |
| `03` | имя трека |
| `04` | имя инструмента |
| `05` | текст песни (лирика) |
| `06` | маркер |
| `07` | cue point |
| `2F` | конец трека |

Именно `01`, `05` и `06` — любимые места для флагов: их никто не проверяет, а
текстовые редакторы показывают как «комментарии».

## Шаг 9: что делать, если файл «чистый»

Если ни текст-событий, ни странных нот нет — попробуй:

- выгрузить `midicsv` и отсортировать события по времени, поискать аномалии;
- проверить палитру инструментов (`Cn`) на нестандартные значения;
- посмотреть, не спрятан ли за флагом ещё один файл (appended data);
- прогнать `strings -n 4` по всему файлу, а не только по заголовку.

MIDI — маленький формат, поэтому почти всегда закладка лежит в тексте. Если её нет,
значит, задача про тайминги или про вложенный файл.

## Второй пример: тайминг-канал в дельта-временах

Предположим, текстовых событий нет. Тогда смотрим на паузы. Соберём все дельта-времена
подряд и проверим их чётность — если из чётных/нечётных складывается ASCII, это
тайминг-канал.

```bash
python3 - <<'PY'
d = open('tune.mid','rb').read()
i = d.find(b'MTrk') + 8
bits = []
while i < len(d):
    val = 0
    while d[i] & 0x80:
        val = (val << 7) | (d[i] & 0x7f)
        i += 1
    val = (val << 7) | d[i]
    i += 1
    bits.append(val & 1)
    if d[i] == 0xFF and d[i+1] == 0x2F:
        break
    # пропускаем событие (упрощённо: один байт статуса + 2 байта данных)
    i += 3
# собираем биты в байты
out = bytearray()
for k in range(0, len(bits)//8*8, 8):
    out.append(int(''.join(map(str, bits[k:k+8])), 2))
print(out)
PY
```

Если в выводе читается `nto{...}` — канал найден. Такие задачи реже, но встречаются:
они требуют понимания переменной длины дельты. Заметь, что пропуск события в скрипте
упрощён — в реальном файле надо корректно определять длину каждого события по его
типу (мета — с длиной, обычные — фиксированное число байт).

## Частые ошибки при разборе MIDI

Первая ошибка — считать MIDI звуком. Это не так: MIDI — это инструкции («нажми
ноту»), а не сэмплы. Поэтому в нём нет ни LSB сэмплов, ни спектрограмм. Зато есть
события, и всё сокрытие живёт в них.

Вторая ошибка — неверно читать переменную длину. Дельта-время и некоторые другие
поля кодируются переменным числом байт: старший бит означает «продолжение». Если
читать фиксированно по одному байту, парсер съедет уже на первом большом значении и
дальше будет читать мусор. Именно поэтому в примере выше есть цикл `while d[i] & 0x80`.

Третья ошибка — забыть, что мета-события имеют поле длины, а обычные — нет. У `FF`
всегда есть тип и длина; у `9n` (note on) длина фиксированная (два байта данных).
Смешаешь — получишь неверный сдвиг.

## Как устроен «формат 1»

Наш файл — формат 0 (один трек). Формат 1 — несколько синхронных треков: например,
один для каждой партии инструмента. В таком файле закладку можно спрятать в «лишнем»
треке, которого нет в исходной композиции. Проверять надо все `MTrk`-чанки, а не
только первый. Формат 2 — независимые треки; встречается редко, но принцип тот же:
перебрать все треки и найти тот, что не играет.

## Что мы теперь знаем

- MIDI — это чанки `MThd`/`MTrk`, а не звук; длины big-endian.
- События = дельта-время + тип; `FF` — мета-события (текст, лирика, маркеры).
- Текст/лирика — самый частый носитель флага.
- Ноты, velocity и дельта-времена тоже можно использовать как биты.
- Хвост после End-of-Track часто остаётся непрочитанным.
