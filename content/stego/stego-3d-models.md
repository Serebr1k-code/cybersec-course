## Вопрос, с которого всё начинается

Тебе дали файл `model.obj`. Это 3D-модель — набор вершин и граней. Никаких пикселей,
никаких цветов. Где тут вообще можно спрятать сообщение? Оказывается, 3D-модели —
один из самых удобных носителей: в них огромные массивы чисел с плавающей точкой,
которые можно незаметно шевелить.

## Наш пример

Смотрим на файл:

```
$ file model.obj
model.obj: ASCII text
$ head -12 model.obj
# Blender v3.6 OBJ File: 'cube'
# www.blender.org
mtllib cube.mtl
o Cube
v 1.000000 1.000000 -1.000000
v 1.000000 -1.000000 -1.000000
v 1.000000 1.000000 1.000000
v -1.000000 1.000000 1.000000
...
f 1 2 3
f 1 3 4
```

OBJ — **текстовый** формат: строки `v` (вершина), `f` (грань), `vt` (текстурные
координаты), `#` — комментарий. Уже здесь видно первое место для сокрытия —
комментарии и служебные строки.

## Шаг 1: текстовые форматы — самое простое

В OBJ/PLY/ASCII-STL данные можно спрятать так:

1. **Комментарии.** Строка `# ...` не влияет на геометрию. Классический трюк:
   ```
   # export_key: nto{0bj_c0mm3nt_h1dd3n}
   ```
2. **Порядок вершин.** Перестановка строк `v` не меняет модель (пока грани ссылаются
   верно), но кодирует биты перестановкой.
3. **Форматирование чисел.** `1.000000` и `1.000001` визуально одинаковы; последние
   знаки можно менять. Аналогично — количество знаков после точки (`1.0` vs `1.000000`)
   как бит.
4. **Лишние пробелы/табы** в конце строк — как в текстовой стеганографии.

Для PLY (формат с явным заголовком `ply` / `end_header`) то же самое, плюс можно
добавить произвольные **properties** в заголовке.

## Шаг 2: бинарные форматы — LSB в координатах

Бинарный STL — это заголовок 80 байт, число треугольников (4 байта), затем на каждый
треугольник 12 чисел `float` (нормаль + 3 вершины) и 2 байта атрибутов. **Числа
`float`** — идеальное место для LSB-стеганографии: изменение младшего бита мантиссы
сдвигает координату на ~10⁻⁷ единицы — это в тысячи раз меньше точности 3D-печати.

```
$ python3 stl_lsb.py
80-byte header: "Exported by tool v2 ..."
triangles: 12
LSB payload: nto{stl_fl04t_lsb}
```

glTF (`.gltf` — JSON + `.bin`, или `.glb` — один бинарный контейнер) хранит геометрию
в **буферах** (accessor → bufferView → buffer). Младшие биты `float`-координат в буфере
работают так же. Плюс в glTF есть JSON-часть: `extras`, `name`, произвольные поля —
ещё один канал.

## Шаг 3: атаки на 3D-печать

Отдельный класс — сокрытие **в процессе печати**. Слайсер превращает модель в G-code
(команды движения экструдера). G-code — текст: комментарии, координаты, скорости.
Можно встроить данные в:

- комментарии слайсера,
- порядок перемещений (travel moves),
- микросдвиги координат (`G1 X10.0001`).

Это уже «физическая» стеганография: напечатанная деталь выглядит обычно, а данные
живут в управляющей программе.

## Шаг 4: как искать

Пайплайн разбора 3D-модели:

```
$ file model.obj
model.obj: ASCII text
$ strings model.obj | grep -i nto
# export_key: nto{0bj_c0mm3nt_h1dd3n}
```

Если формат текстовый — начать с `strings` и `grep`. Для бинарного STL:

```
$ xxd -l 84 model.stl
00000000: 4578 706f 7274 6564 2062 7920 746f 6f6c  Exported by tool
...
```

Дальше — скрипт, читающий `float` и собирающий младшие биты. Полезные библиотеки:
`numpy` (быстрый разбор буферов), `trimesh` (универсальный загрузчик STL/OBJ/PLY/glTF).

## Шаг 5: почему это работает

Причина проста: **3D-модели содержат избыточную точность**. Координата хранится как
`float32` (~7 значащих цифр), но для отображения или печати хватает 3–4. Оставшиеся
биты — свободное место. Плюс форматы терпимы к «мусорным» полям (комментарии,
`extras`, атрибуты), которые парсеры игнорируют.

## Что мы теперь знаем

- Текстовые форматы (OBJ/PLY/ASCII-STL): комментарии, порядок вершин, форматирование чисел.
- Бинарные (STL/GLB): **LSB в float-координатах** — почти незаметно для глаза и печати.
- glTF: JSON-поля (`extras`, `name`) и бинарные буферы — два канала сразу.
- G-code: данные можно спрятать в управляющей программе печати.
- Разбор: `strings`/`grep` для текста, скрипт по `float` — для бинарного.
