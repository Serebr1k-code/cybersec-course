## Вопрос, с которого всё начинается

Тебе дали файл `model.obj`. Это 3D-модель — набор вершин и граней. Никаких пикселей,
никаких цветов. Где тут вообще можно спрятать сообщение? Оказывается, 3D-модели —
один из самых удобных носителей: в них огромные массивы чисел с плавающей точкой,
которые можно незаметно шевелить.

## Наш пример

Смотрим на файл:

```
$ file model.obj
model.obj: ASCII text
$ head -12 model.obj
# Blender v3.6 OBJ File: 'cube'
# www.blender.org
mtllib cube.mtl
o Cube
v 1.000000 1.000000 -1.000000
v 1.000000 -1.000000 -1.000000
v 1.000000 1.000000 1.000000
v -1.000000 1.000000 1.000000
...
f 1 2 3
f 1 3 4
```

OBJ — **текстовый** формат: строки `v` (вершина), `f` (грань), `vt` (текстурные
координаты), `#` — комментарий. Уже здесь видно первое место для сокрытия —
комментарии и служебные строки.

## Шаг 1: текстовые форматы — самое простое

В OBJ/PLY/ASCII-STL данные можно спрятать так:

1. **Комментарии.** Строка `# ...` не влияет на геометрию. Классический трюк:
   ```
   # export_key: nto{0bj_c0mm3nt_h1dd3n}
   ```
2. **Порядок вершин.** Перестановка строк `v` не меняет модель (пока грани ссылаются
   верно), но кодирует биты перестановкой.
3. **Форматирование чисел.** `1.000000` и `1.000001` визуально одинаковы; последние
   знаки можно менять. Аналогично — количество знаков после точки (`1.0` vs `1.000000`)
   как бит.
4. **Лишние пробелы/табы** в конце строк — как в текстовой стеганографии.

Для PLY (формат с явным заголовком `ply` / `end_header`) то же самое, плюс можно
добавить произвольные **properties** в заголовке.

## Шаг 2: бинарные форматы — LSB в координатах

Бинарный STL — это заголовок 80 байт, число треугольников (4 байта), затем на каждый
треугольник 12 чисел `float` (нормаль + 3 вершины) и 2 байта атрибутов. **Числа
`float`** — идеальное место для LSB-стеганографии: изменение младшего бита мантиссы
сдвигает координату на ~10⁻⁷ единицы — это в тысячи раз меньше точности 3D-печати.

```
$ python3 stl_lsb.py
80-byte header: "Exported by tool v2 ..."
triangles: 12
LSB payload: nto{stl_fl04t_lsb}
```

glTF (`.gltf` — JSON + `.bin`, или `.glb` — один бинарный контейнер) хранит геометрию
в **буферах** (accessor → bufferView → buffer). Младшие биты `float`-координат в буфере
работают так же. Плюс в glTF есть JSON-часть: `extras`, `name`, произвольные поля —
ещё один канал.

## Шаг 3: атаки на 3D-печать

Отдельный класс — сокрытие **в процессе печати**. Слайсер превращает модель в G-code
(команды движения экструдера). G-code — текст: комментарии, координаты, скорости.
Можно встроить данные в:

- комментарии слайсера,
- порядок перемещений (travel moves),
- микросдвиги координат (`G1 X10.0001`).

Это уже «физическая» стеганография: напечатанная деталь выглядит обычно, а данные
живут в управляющей программе.

## Шаг 4: как искать

Пайплайн разбора 3D-модели:

```
$ file model.obj
model.obj: ASCII text
$ strings model.obj | grep -i nto
# export_key: nto{0bj_c0mm3nt_h1dd3n}
```

Если формат текстовый — начать с `strings` и `grep`. Для бинарного STL:

```
$ xxd -l 84 model.stl
00000000: 4578 706f 7274 6564 2062 7920 746f 6f6c  Exported by tool
...
```

Дальше — скрипт, читающий `float` и собирающий младшие биты. Полезные библиотеки:
`numpy` (быстрый разбор буферов), `trimesh` (универсальный загрузчик STL/OBJ/PLY/glTF).

## Шаг 5: почему это работает

Причина проста: **3D-модели содержат избыточную точность**. Координата хранится как
`float32` (~7 значащих цифр), но для отображения или печати хватает 3–4. Оставшиеся
биты — свободное место. Плюс форматы терпимы к «мусорным» полям (комментарии,
`extras`, атрибуты), которые парсеры игнорируют.

## Что мы теперь знаем

- Текстовые форматы (OBJ/PLY/ASCII-STL): комментарии, порядок вершин, форматирование чисел.
- Бинарные (STL/GLB): **LSB в float-координатах** — почти незаметно для глаза и печати.
- glTF: JSON-поля (`extras`, `name`) и бинарные буферы — два канала сразу.
- G-code: данные можно спрятать в управляющей программе печати.
- Разбор: `strings`/`grep` для текста, скрипт по `float` — для бинарного.

## Форматы детально: OBJ, PLY, STL, glTF

**OBJ** — текстовый. Строки: `v` (вершина), `vt` (текстурные координаты), `vn`
(нормаль), `f` (грань), `o`/`g` (объект/группа), `mtllib`/`usemtl` (материалы), `#`
(комментарий). Комментарии и лишние пробелы — первый канал.

**PLY** — текстовый или бинарный, с явным заголовком:

```
$ head -8 model.ply
ply
format ascii 1.0
element vertex 8
property float x
property float y
property float z
end_header
```

В заголовок можно добавить **произвольное `comment`** или `property` — парсеры их
либо игнорируют, либо хранят как «extra».

**STL** — бинарный (80 байт заголовка + 4 байта числа треугольников + по 50 байт
на треугольник) или ASCII (`solid`/`facet`/`endsolid`). В бинарном заголовке — 80
байт свободного текста (часто пишут «Exported by ...»), идеальное место.

**glTF** — `.gltf` (JSON + внешний `.bin`) или `.glb` (единый бинарный контейнер).
Структура: `asset` → `buffers` → `bufferViews` → `accessors` → `meshes`. JSON-часть
даёт каналы `extras`, `name`, произвольные ключи; бинарные буферы — LSB в координатах.

## LSB в float: полный скрипт

Координаты — `float32`. Меняем младший бит мантиссы: сдвиг ~10⁻⁷, невидим для глаза
и для 3D-печати. Читаем треугольники STL и собираем биты:

```python
import struct

def read_stl(path):
    d = open(path, 'rb').read()
    n = struct.unpack('<I', d[80:84])[0]
    vals = []
    for i in range(n):
        off = 84 + i * 50
        # 12 float: нормаль (3) + 3 вершины по 3
        vals += struct.unpack('<12f', d[off:off + 48])
    return vals

def lsb_extract(vals):
    bits = [int.from_bytes(struct.pack('<f', v), 'little') & 1 for v in vals]
    out = bytearray()
    for i in range(0, len(bits) - 7, 8):
        out.append(int(''.join(map(str, bits[i:i+8])), 2))
    return bytes(out)

print(lsb_extract(read_stl('model.stl')))
```

```
$ python3 stl_lsb.py
b'nto{stl_fl04t_lsb}\x00\x00'
```

Обрати внимание на порядок: биты собираем из **little-endian** представления float,
иначе payload не прочитается. Если не сработало — перебери: big-endian, чтение по
каждому float с конца, пропуск нормалей (первые 3 из 12).

## G-code: печать как канал

Слайсер превращает модель в **G-code** — текстовые команды движения:

```
$ head -8 model.gcode
; generated by PrusaSlicer
M104 S210 ; set nozzle temp
G28 ; home all axes
G1 X10.000 Y10.000 Z0.200 E0.500
G1 X20.000 Y10.000 Z0.200 E1.000
```

Каналы: комментарии `; ...`, порядок `travel`-перемещений (холостые ходы), микро-
сдвиги координат (`X10.0001`), скорости `F`. Напечатанная деталь выглядит обычно, а
данные живут в управляющей программе.

## Инструменты

- **`trimesh`** — универсальный загрузчик STL/OBJ/PLY/glTF; `trimesh.load('m.obj')`.
- **`numpy`** — быстрый разбор буферов: `np.frombuffer(d, dtype='<f4')`.
- **`meshlab` / `meshlabserver`** — конвертация и просмотр, «очистка» модели.
- **`assimp` (`assimp info m.glb`)** — информация о сцене glTF.
- **`blender --background --python script.py`** — headless-обработка.
- **`xxd`** — ручной просмотр заголовков STL/GLB.

## Edge cases и подводные камни

- **Порядок вершин.** Перестановка `v` не меняет геометрию, **пока** грани `f`
  ссылаются на новые индексы. Если автор переставил строки и **не** поправил `f` —
  модель «поедет», но данные извлекутся.
- **Число знаков после точки.** `1.0` vs `1.000000` — бит, но менять формат
  рискованно: некоторые парсеры строги.
- **GLB-выравнивание.** Блоки в `.glb` выровнены по 4 байта; лишние паддинг-байты —
  тоже канал.
- **ASCII-STL.** Тоже текст: `strings | grep` работает.
- **Сжатие.** `.glb` не сжимается, но glTF с `EXT_meshopt_compression` — да; тогда
  бинарный буфер надо распаковать.

## Что дальше / решение

Сквозной пример: `strings model.obj | grep nto` находит комментарий
`nto{0bj_c0mm3nt_h1dd3n}`. Для бинарного STL — `stl_lsb.py` собирает младшие биты
float и отдаёт `nto{stl_fl04t_lsb}`. Если формат glTF — проверяем JSON-поля
`extras`/`name` и LSB в буфере.

## Шпаргалка: 3D-носители

| Формат | Тип | Канал | Инструмент |
|--------|-----|-------|------------|
| OBJ | текст | комментарий, порядок `v` | `strings`, `grep` |
| PLY | текст/бин | `comment`, `property` | `strings`, Python |
| STL (bin) | бинарный | заголовок 80 б, LSB float | Python, `xxd` |
| STL (ascii) | текст | `solid`/`facet` строки | `strings` |
| glTF | JSON+bin | `extras`, `name`, буфер | Python, `jq` |
| GLB | бинарный | JSON-чанк, буфер | Python, `xxd` |
| G-code | текст | комментарии, travel | `grep`, `strings` |

## Быстрый чек-лист по формату

Первым делом `file model.*` — текст или бинарь? Для текста сразу `strings | grep`,
для бинарного — `xxd -l 128` (заголовок) и скрипт по float. Не забывай: расширение
не гарантирует формат — `file` и первые байты надёжнее.
