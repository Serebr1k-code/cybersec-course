## Вопрос, с которого всё начинается

В задаче дан `archive.gz` — обычный gzip-архив. Ты распаковываешь его и видишь короткий текст: «Nothing to see here». `strings` ничего не находит, `binwalk` молчит, LSB-инструменты пусты. Но флаг где-то есть. Где можно спрятать данные так, что даже распаковка не показывает ничего лишнего?

Ответ: **в самом механизме сжатия**. Для одного и того же содержимого сжатие допускает несколько «равнозначных» представлений, и выбор между ними — это бит информации. Разберём это на нашем архиве.

## Наш пример: archive.gz

**Сжатие** (компрессия) — способ записать данные меньшим числом байт, убрав избыточность: одинаковые куски заменяются ссылками, частые символы — короткими кодами. **DEFLATE** — алгоритм, который лежит внутри gzip, PNG и ZIP; **Huffman** — способ кодирования символов кодами разной длины по их частоте.

Начнём с осмотра:

```bash
$ file archive.gz
archive.gz: gzip compressed data, from Unix
$ zcat archive.gz
Nothing to see here
$ python3 -c "d=open('archive.gz','rb').read(); print(d.count(b'\x1f\x8b\x08'))"
2
```

`zcat` показал только первый поток. Но счётчик нашёл **два** заголовка `1f 8b 08` — сигнатуру gzip. Значит, в файле склеены **два** архива, и второй мы просто не увидели.

## Шаг 1: concatenated-контейнеры

**Concatenated** (склеенный) контейнер — несколько потоков одного формата, идущих подряд. Стандарт gzip разрешает так делать, и многие инструменты распакуют все потоки как один — но `zcat` в нашем случае остановился на первом. Разделим их вручную:

```python
data = open('archive.gz','rb').read()
magic = b'\x1f\x8b\x08'
idx = [i for i in range(len(data)) if data.startswith(magic, i)]
print(idx)                      # смещения начала каждого потока
part2 = data[idx[1]:]           # второй поток
open('part2.gz','wb').write(part2)
```

```bash
$ zcat part2.gz
flag{deflate_layers}
```

Это самый частый «приземлённый» вид компрессионной стеганографии в CTF: данные не изменены, просто упакованы в **отдельный слой**, о котором наивный `zcat` не сообщает.

## Шаг 2: padding-биты DEFLATE

Второй приём — **padding**. DEFLATE кодирует данные **битами**, а не байтами, и в конце потока добивает последний байт до границы. Эти добивочные биты декодер игнорирует — их можно использовать под сообщение. Ёмкость крошечная (несколько бит на поток), поэтому так прячут короткие значения: ключ, номер.

```bash
# gzip-поток: последние биты после конца данных
$ python3 -c "
import zlib
d=open('archive.gz','rb').read()
print('tail bits:', bin(d[-1]))"
tail bits: 0b10000111
```

Практический вывод: если после распаковки «всё чисто», но файл на пару байт длиннее ожидаемого — посмотри на хвост потока.

## Шаг 3: эквивалентные Huffman-коды (теория)

Теперь главная идея. При Huffman-кодировании строится дерево: частые символы получают короткие коды, редкие — длинные. Если два символа имеют **равную частоту**, их листья в дереве можно менять местами — и декодирование не изменится. Выбор «какой из двух равнозначных кодов поставить» кодирует один бит.

```
символ A — код 010, символ B — код 011  (равные частоты)
поменяли местами: A=011, B=010
файл декодируется ровно так же, но биты в потоке другие → 1 бит данных
```

Ёмкость здесь — примерно по одному биту на каждую пару равновесных листьев, то есть **доли процента** от размера файла. Много данных так не спрятать, но флаг или ключ — легко.

## Шаг 4: модельная и арифметическая стеганография

**Арифметическое кодирование** записывает всю последовательность символов как одну дробь в интервале `[0,1)`. Любое число внутри «своего» интервала декодируется в то же сообщение — значит, младшие биты этой дроби свободны. Модельная стеганография («model-based», MB) делает то же в JPEG: не трогает коэффициенты, а **подгоняет статистическую модель** под данные, чтобы распределение осталось естественным.

Именно поэтому гистограммные тесты (например, хи-квадрат), которые ловят LSB, здесь бессильны: распределение символов не меняется — меняется лишь выбор внутри допустимого.

## Шаг 5: JPEG и таблицы Хаффмана

В JPEG есть сегменты **DHT** — таблицы Хаффмана для коэффициентов. В них бывают «неиспользуемые» коды, которые можно переопределить, не ломая картинку:

```bash
$ djpeg -verbose image.jpg > /dev/null 2>&1 | grep -i huffman
$ exiftool -b -HuffmanTables image.jpg | head -c 120 | xxd | head
```

Признак аномалии — нестандартные или избыточные DHT-таблицы, коды, которые не встречаются в данных.

## Шаг 6: почему это трудно детектировать

Компрессионная стеганография сохраняет распределение символов и остаётся **корректным** сжатым потоком. Пересжатие её не убивает (в отличие от LSB), а обычный стегоанализ по энтропии не работает: энтропия и так высока. Единственные зацепки — аномалии в таблицах, лишние байты и несовпадение длины.

| Метод | Что меняется | Ёмкость | Заметность |
|---|---|---|---|
| LSB | младшие биты пикселей | высокая | средняя |
| DCT (JPEG) | коэффициенты | средняя | высокая |
| Компрессионная | код сжатия | низкая | очень высокая |

## Если не сработало

- **Ищешь пиксельный LSB** там, где данные в коде сжатия — инструменты не помогут, нужен ручной разбор потока.
- **Не распаковал IDAT** в PNG — половина задач решается уже на этом шаге.
- **Игнорируешь padding** в конце потоков.
- **Считаешь «идеальную» статистику отсутствием данных** — наоборот, это подсказка.
- **Путаешь** компрессионную стеганографию с обычным вложенным ZIP (когда в PNG просто лежит архив).

## Инструменты и мини-чек-лист

- **`file`/`binwalk`** — найти склеенные/вложенные потоки;
- **`zlib`/`gzip` в Python** — распаковка и анализ;
- **`pngcheck`** — структура PNG и IDAT-потоки;
- **`djpeg -verbose`** — таблицы Хаффмана в JPEG.

Порядок действий: `file`/`binwalk` → посчитать число потоков (`d.count(b'\x1f\x8b\x08')`) → распаковать все → вырезать IDAT в PNG и распаковать вручную → посмотреть DHT в JPEG → сравнить размер и энтропию с ожидаемыми.

## Расчёт ёмкости

Ёмкость компрессионного канала зависит от числа эквивалентных представлений. Для Huffman с `k` парами равновесных листьев это примерно `k` бит; для модельной стеганографии — доли процента от размера. Практический ориентир: **если данных много, это не компрессионная стеганография**. Она хороша для короткого сообщения (флаг, ключ), а не для архива. Поэтому в CTF чистые компрессионные задачи редки и часто совмещены с другими каналами.

## Что мы теперь знаем

1. Компрессионная стеганография использует **свободу кодера**, а не порчу данных.
2. Самый частый вид в CTF — **concatenated** потоки (несколько gzip подряд).
3. **Padding-биты** дают мало ёмкости — для коротких сообщений.
4. Равновесные Huffman-листья и арифметический интервал — теоретический канал.
5. Детект — по аномалиям таблиц, длине и структуре потоков, а не по энтропии.

## Куда дальше

Компрессия часто идёт рука об руку с **шифрованием**: данные не только сжимают, но и закрывают паролем. В следующем уроке разберём многослойные цепочки «стего → архив → крипто» и как их распутывать. А пока запомни: если `zcat` показал мало, посчитай заголовки — потоков может быть больше.

## Где пригодится

- **CTF Stego:** теоретические и парные задачи.
- **Forensics:** понимание каналов, устойчивых к пересжатию.
- **Исследования:** watermarking и скрытые каналы.
- **Работа:** оценка стойкости каналов эксфильтрации.
