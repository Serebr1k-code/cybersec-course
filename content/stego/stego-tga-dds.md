## Вопрос, с которого всё начинается

В задаче из игры вытащили два файла: `tex.tga` и `skybox.dds` — текстуры. Просмотрщик показывает обычную шумную картинку, `zsteg` молчит. Но в `file` для TGA видно что-то странное: после размеров идёт строка с флагом. Как её достать и почему DDS устроен иначе?

TGA и DDS — **низкоуровневые игровые форматы**. Их редко проверяют, поэтому данные в них хорошо «живут». Разберём оба на наших файлах.

## Наш пример: tex.tga

Смотрим файл:

```bash
$ file tex.tga
tex.tga: Targa image data - RGB 64 x 64 x 24 "flag{tga_id_block}..."
```

Уже на этом шаге видно флаг — `file` прочитал **ID-блок** сразу после заголовка. Но давай разберёмся, почему он там оказался.

## Шаг 1: 18-байтный заголовок TGA

**TGA** (Truevision) — предельно простой формат: 18-байтный заголовок, затем опциональный ID-блок, палитра (для индексированных) и «сырые» или RLE-сжатые пиксели. Ключевые поля заголовка:

| Смещение | Поле | Описание |
|---|---|---|
| 0x00 | ID length | длина ID-блока (байт) |
| 0x02 | Image type | 2 = RGB, 3 = grayscale, 10/11 = RLE |
| 0x0C | Width/Height | размеры |
| 0x10 | BPP/Descriptor | бит на пиксель + порядок строк |

Прочитаем заголовок нашего файла:

```python
d = open("tex.tga", "rb").read()
print("IDlen", d[0], "type", d[2], "bpp", d[16])
```

```
IDlen 18 type 2 bpp 24
```

`type=2` — несжатый RGB, `bpp=24` — три байта на пиксель. А `IDlen=18` — необычно: у обычной текстуры ID-блока нет, то есть длина должна быть 0.

## Шаг 2: ID-блок — канал

**ID-блок** — произвольные байты длиной `ID length`, которые лежат сразу после заголовка. Рендереры их **игнорируют**, поэтому туда пишут всё что угодно. Достаём его:

```python
print(d[18:18+d[0]])
```

```
b'flag{tga_id_block}'
```

Вот и флаг. Приём простой, но эффективный: поле официально существует, но никто его не смотрит. Вторая зона TGA — **дескриптор** (байт 0x11): несколько бит в нём «неиспользуемые», и туда тоже можно закодировать данные.

## Шаг 3: DDS — заголовок и FourCC

**DDS** (DirectDraw Surface) — контейнер текстур, пришедший из DirectX. Начинается с magic `DDS `, за которым идёт 124-байтный заголовок. Смотрим:

```python
d = open("tex.dds", "rb").read()
print(d[:4], "fourcc", d[0x54:0x58])
```

```
b'DDS ' fourcc b'DXT1'
```

`DXT1` в поле FourCC — это указание на **блочное сжатие** (Block Compression, BC1). Именно оно определяет, как хранятся пиксели, и почему здесь не работает обычный LSB.

```bash
$ file tex.dds
tex.dds: Microsoft DirectDraw Surface (DDS): 64 x 64, compressed using DXT1
```

## Шаг 4: DXT/BC — почему LSB не работает

В TGA пиксели лежат «сырыми» байтами — можно менять младшие биты напрямую. В DDS с DXT-сжатием пиксели хранятся **блоками**: DXT1-блок — 8 байт, внутри два 16-битных «опорных» цвета и 32 бита индексов (по 2 бита на пиксель). Каждый блок — не отдельные пиксели, а сжатое представление 4×4 пикселей.

```python
import struct
d = open("tex.dds", "rb").read()
off = 128                      # после заголовка (0x80)
c0, c1, bits = struct.unpack("<HHI", d[off:off+8])
print("color0=%04x color1=%04x idx=%08x" % (c0, c1, bits))
```

```
color0=d927 color1=0f39 idx=9a8edbbe
```

`c0` и `c1` — опорные цвета (RGB565), `idx` — 32 бита индексов для 16 пикселей блока.

Поэтому «поменять младший бит пикселя» здесь нельзя — он не лежит в файле как отдельный байт. Зато можно кодировать данные в **неиспользуемых битах блоков** (например, в индексах, которые рендерер не различает) или в резервных полях заголовка.

## Шаг 5: overlay — данные после конца

Самый частый приём для DDS — дописать данные **после** текстуры. Возьмём второй файл, `skybox.dds`, и поищем сигнатуры вложенных файлов:

```bash
$ grep -aboP 'PK\x03\x04' skybox.dds
2872:PK
```

`PK\x03\x04` — начало ZIP-архива, и он начинается на смещении 2872, после конца текстуры. Вырезаем хвост и распаковываем:

```python
d = open("skybox.dds", "rb").read()
i = d.find(b"PK\x03\x04")
open("hidden.zip", "wb").write(d[i:])
import zipfile
print(zipfile.ZipFile("hidden.zip").read("flag.txt"))
```

```
b'flag{dds_overlay_zip}\n'
```

Данные были дописаны как ZIP. Просмотрщик текстуры их не видит — для него файл заканчивается на пиксельных данных.

## Шаг 6: cubemap и mipmap

DDS умеет хранить не одну текстуру, а несколько: **cubemap** (6 граней для отражений), **volume** (3D) и **mipmap**-цепочку (уменьшенные копии). Каждый уровень — отдельное изображение, и данные могут быть в любой грани. Признак cubemap — флаги в поле `dwCaps2`:

```python
import struct
caps2 = struct.unpack("<I", d[0x70:0x74])[0]
print(hex(caps2))          # у нашего tex.dds -> 0x0 (обычная 2D-текстура)
                           # 0xfe00 -> все 6 граней cubemap
```

Извлекают грани через `convert "tex.dds[$i]" face_$i.png` (ImageMagick понимает индексы) или библиотекой, а затем прогоняют `zsteg` по каждой. Если смотреть только «первую» грань, флаг легко пропустить.

## Шаг 7: RLE и порядок строк

Если `type` в заголовке TGA равен 10 или 11, пиксели **RLE-сжаты**: данные идут не по пикселю, а «сериями». Прежде чем искать LSB, файл нужно распаковать — иначе «сырые» байты дадут мусор. Проще всего открыть TGA через Pillow: библиотека сама распакует и отдаст пиксели.

```python
from PIL import Image
im = Image.open("tex.tga").convert("RGB")
bits = "".join(str(p[0] & 1) for p in im.getdata())
print(bytes(int(bits[i:i+8], 2) for i in range(0, len(bits)-7, 8)))
```

Ещё одна тонкость TGA — **origin**: бит 5 дескриптора говорит, хранится изображение сверху вниз или снизу вверх. Если данные читаются «почти правильно, но перевёрнуты», поменяй порядок строк. Итоговый чек-лист: `file`/`identify` → TGA: ID-блок, дескриптор, распаковка RLE; DDS: FourCC, caps (cubemap/volume/mipmap); `grep -aboP`/`binwalk` на overlay; `convert` в PNG и `zsteg` по каждому изображению. В играх текстуры часто лежат внутри proprietарных контейнеров (Unity `.assets`, Unreal `.pak`) — сначала распакуй контейнер, потом применяй этот пайплайн к извлечённым DDS/TGA. Формат контейнера определяй по сигнатуре через `file` и `binwalk`, а извлечённые текстуры прогоняй по тому же чек-листу рекурсивно.

## Что мы теперь знаем

1. TGA: 18-байтный заголовок, затем ID-блок и пиксели; `type=2` — несжатый RGB.
2. ID-блок — произвольные байты, которые рендереры игнорируют; наш флаг был там.
3. DDS начинается с magic `DDS `; FourCC (`DXT1`/`DXT5`/`DX10`) задаёт сжатие.
4. DXT/BC — блочное сжатие: LSB по пикселям неприменим, данные прячут в битах блоков.
5. Overlay (дописанный ZIP после текстуры) — самый частый приём; ищи `grep -aboP 'PK\x03\x04'`.
6. Cubemap/volume/mipmap — несколько изображений в одном файле; проверяй все.
