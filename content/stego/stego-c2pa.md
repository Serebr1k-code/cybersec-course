## Вопрос, с которого всё начинается

Тебе дали `photo.jpg`. Обычная картинка — но в ней есть **Content Credentials**
(C2PA): манифест, который описывает происхождение контента (кто создал, чем, что
менял). Этот манифест — структурированные данные, встроенные в файл. Где он живёт и
можно ли использовать его для сокрытия? Разберём файл.

## Наш пример: файл photo.jpg

```bash
xxd -l 64 photo.jpg
```

```text
00000000: ffd8 ffeb 0021 4a50 0001 6332 7061 6e74  .....!JP..c2pant
00000010: 6f7b 6332 7061 5f6d 346e 3166 3373 745f  o{c2pa_m4n1f3st_
00000020: 666c 3467 7dff d9                        fl4g}...
```

`ff d8` — начало JPEG. Затем `ff eb` — маркер **APP11**, длина `00 21` = 33 байта.
Внутри — `JP` (идентификатор JUMBF), затем `c2pa` и ASCII-флаг. Разберём.

## Шаг 1: структура JPEG-сегментов

JPEG — поток **сегментов**:

```
[ FF ][ маркер(1) ][ длина(2, big-endian) ][ данные ]
```

Маркер `D8` — начало изображения (SOI), `D9` — конец (EOI), `DA` — начало сканирования
(SOS), `FE` — комментарий (COM), `E0`–`EF` — APP0..APP15. **APP11** (`EB`) зарезервирован
под JUMBF — контейнер метаданных, в котором и лежит C2PA.

## Шаг 2: что такое C2PA и JUMBF

**C2PA** (Coalition for Content Provenance and Authenticity) — стандарт для описания
происхождения медиа. Манифест C2PA содержит утверждения (claims): кто создал, каким
инструментом, какие правки. Он упакован в **JUMBF** (JPEG Universal Metadata Box
Format) — боксированный формат:

```
[ размер(4, big-endian) ][ тип(4) ][ данные ]
```

Типы: `jumb` (superbox), `jumd` (описание), `json` (манифест), `cbor`, `uuid`.

## Шаг 3: извлекаем данные вручную

```bash
python3 - <<'PY'
d = open('photo.jpg','rb').read()
i = 2
while i + 4 <= len(d):
    if d[i] != 0xFF:
        break
    marker = d[i+1]
    if marker == 0xD9:
        break
    ln = int.from_bytes(d[i+2:i+4],'big')
    data = d[i+4:i+2+ln]
    if marker == 0xEB:
        print('APP11:', data)
    i += 2 + ln
PY
```

```text
APP11: b'JP\x00\x01c2panto{c2pa_m4n1f3st_fl4g}'
```

## Шаг 4: где ещё живёт C2PA

- **JPEG** — APP11-сегмент.
- **PNG** — чанк `caBX`.
- **ISOBMFF (MP4/AVIF)** — бокс `uuid` или `jumb` в `meta`.
- **WebP** — RIFF-чанк `C2PA`.
- **PDF** — объект метаданных.

Общий принцип: манифест — это **встроенные структурированные данные**, и его можно
разбирать как контейнер.

## Шаг 5: где прячут внутри манифеста

- **Пользовательские утверждения** — произвольные JSON-поля в манифесте.
- **`uuid`-боксы** JUMBF — частные расширения.
- **Паддинг** — JUMBF выравнивают; «лишние» байты.
- **Подпись** — бинарный blob; формально проверяется, но «неправильные» подписи часто
  игнорируются.
- **Порядок боксов** — перестановочный канал.

## Шаг 6: инструменты

```bash
c2patool photo.jpg                 # официальный инструмент C2PA
exiftool -a -G1 photo.jpg | grep -i c2pa
binwalk photo.jpg
```

`c2patool` покажет манифест человекочитаемо (JSON). `exiftool` извлечёт JUMBF как
блоб. Но ручной разбор надёжнее: манифест может быть «неправильным», и инструмент
откажется его показывать.

## Шаг 7: почему C2PA удобен для сокрытия

C2PA-манифест — это **легальные метаданные**, которые есть у многих медиафайлов.
Никто не считает их аномалией. Внутри — JSON, куда можно добавить произвольные поля.
Плюс JUMBF-контейнер допускает `uuid`-боксы и паддинг. Всё это — знакомые нам приёмы,
только применённые к новому формату.

## Шаг 8: частые ошибки

Первая — путать APP11 с APP0/APP1: C2PA именно APP11. Вторая — неверно читать длину
JPEG-сегмента (2 байта big-endian, включая саму длину). Третья — останавливаться на
первом сегменте: APP11 может быть не первым. Четвёртая — считать, что подпись C2PA
защищает содержимое: подпись можно не проверять.

## Практика: JUMBF в деталях

JUMBF-контейнер — это боксы, как в ISOBMFF. Верхний бокс `jumb` содержит описание
`jumd` (тип содержимого, метка) и полезную нагрузку (`json`, `cbor`, `uuid`). Манифест
C2PA — JSON внутри `json`-бокса. Разберём структуру:

```bash
python3 - <<'PY'
import struct
d = open('photo.jpg','rb').read()
# найдём APP11 и в нём — боксы JUMBF
i = 2
while i + 4 <= len(d):
    if d[i] != 0xFF: break
    m = d[i+1]; ln = int.from_bytes(d[i+2:i+4],'big')
    if m == 0xEB:
        body = d[i+4:i+2+ln]
        p = 4  # пропускаем 'JP' + версия
        while p + 8 <= len(body):
            sz = int.from_bytes(body[p:p+4],'big')
            typ = body[p+4:p+8]
            print(typ, sz, body[p+8:p+8+sz-8][:48])
            if sz == 0: break
            p += sz
    i += 2 + ln
PY
```

Так ты увидишь типы боксов JUMBF (`jumb`, `jumd`, `json`, `cbor`, `uuid`) и их
содержимое. Закладка чаще всего в `json` (произвольные поля манифеста) или в `uuid`.

## C2PA в PNG и ISOBMFF

C2PA не привязан к JPEG. В **PNG** манифест лежит в чанке `caBX` (структура чанка
обычная: длина + тип + данные + CRC). В **ISOBMFF** (MP4/AVIF) — в боксе `uuid` или
`jumb` внутри `meta`. В **WebP** — в RIFF-чанке `C2PA`.

Общий принцип: где бы ни лежал манифест, это **боксы/чанки с JSON внутри**. Поэтому
навык разбора контейнеров (PNG, ISOBMFF, RIFF) напрямую переносится на C2PA. Найди
контейнер, дойди до JSON, прочитай поля.

## Как отличить закладку в C2PA

Настоящий манифест C2PA содержит предсказуемые поля: `claim_generator`, `assertions`,
`signature`, `ingredients`. Признаки закладки:

- **Лишние утверждения** с произвольным содержимым.
- **UUID-боксы**, которых нет в стандарте C2PA.
- **Подпись, которая не проверяется** (или её отсутствие).
- **ASCII-текст** внутри бинарных полей (подпись, хэши).

Практический приём: извлеки JSON манифеста и поищи строки, декодируемые как флаг
(`nto{...}`, base64). Если `c2patool` отказывается показывать манифест — это повод
разобрать его вручную, потому что «сломанный» манифест часто и есть закладка.

## Почему провенанс важен и опасен

C2PA придуман, чтобы бороться с дезинформацией: манифест подтверждает, кто создал
контент и что с ним делали. Но любой стандарт метаданных — это ещё и носитель.
Манифест подписан, однако подпись часто не проверяется (или проверяется только
«наличие»), а внутри — JSON, куда можно добавить что угодно. Получается, что
«доверенные» метаданные могут нести недоверенные данные.

Для специалиста по безопасности это означает: проверять подпись C2PA недостаточно;
надо смотреть содержимое манифеста. В CTF это отражается в задачах, где в `photo.jpg`
лежит «странный» C2PA-манифест с флагом внутри. Решение — разобрать APP11/JUMBF
вручную, потому что `c2patool` может отказаться от «невалидного» манифеста.

## Практика: разбор JSON манифеста

Если внутри APP11 есть `json`-бокс JUMBF, его содержимое — обычный JSON. Разберём:

```bash
python3 - <<'PY'
import struct, json
d = open('photo.jpg','rb').read()
i = 2
while i + 4 <= len(d):
    if d[i] != 0xFF: break
    m = d[i+1]; ln = int.from_bytes(d[i+2:i+4],'big')
    if m == 0xEB:
        body = d[i+4:i+2+ln]
        p = 4
        while p + 8 <= len(body):
            sz = int.from_bytes(body[p:p+4],'big'); typ = body[p+4:p+8]
            if typ == b'json':
                print(json.loads(body[p+8:p+8+sz-8]))
            if sz == 0: break
            p += sz
    i += 2 + ln
PY
```

Так ты увидишь поля манифеста и сможешь найти «лишнее» утверждение с флагом.

## Чек-лист по C2PA

1. `xxd -l 64` — найди APP11 (`FF EB`) в JPEG (или `caBX` в PNG).
2. Разбери сегмент/чанк, дойди до JUMBF-боксов.
3. Найди `json`/`cbor`/`uuid` боксы; декодируй JSON.
4. Ищи произвольные утверждения, ASCII-текст, `nto{...}`.
5. Проверь подпись — если её нет, манифест точно правили.
6. `c2patool`/`exiftool` — для перекрёстной проверки.

Такой конвейер решает и CTF, и реальную проверку подлинности медиа.

## Итоговая стратегия для C2PA

Найди контейнер манифеста (APP11 в JPEG, `caBX` в PNG, `uuid`/`jumb` в ISOBMFF).
Разбери его как боксы/чанки. Найди `json`-бокс и декодируй манифест. Ищи произвольные
утверждения и ASCII-флаг. Проверь наличие подписи: её отсутствие — признак правки.
Помни: C2PA — это легальные метаданные, поэтому закладка в них не выглядит аномалией,
пока не разберёшь содержимое. Именно поэтому провенанс-поля — привлекательный канал
для сокрытия данных в современном медиапотоке.

## Замечание о доверии метаданным

C2PA задуман как «паспорт» контента, которому можно доверять. Но доверие строится на
подписи, а подпись проверяют не все инструменты. Если подпись не проверяется,
метаданные становятся обычным контейнером, в который можно положить что угодно. Это
общий урок: любой механизм «доверенных метаданных» — это ещё и канал, если проверка
неполная. Для аналитика вывод прост: разбирай содержимое, а не полагайся на флаг
«подписано».

## Ещё одна мысль

Манифест C2PA может содержать вложенные `ingredients` — описания исходных файлов. Каждое из них — тоже структура с полями, и в них можно спрятать данные. Поэтому разбор манифеста стоит вести рекурсивно, а не останавливаться на верхнем уровне.

## Что мы теперь знаем

- JPEG — поток сегментов `FF маркер длина данные`; APP11 = JUMBF/C2PA.
- C2PA — манифест происхождения; JUMBF — боксированный контейнер.
- C2PA бывает в JPEG (APP11), PNG (`caBX`), ISOBMFF (uuid/jumb).
- Внутри — JSON с произвольными полями и `uuid`-боксами.
- Инструменты: `c2patool`, `exiftool`, `binwalk`.
