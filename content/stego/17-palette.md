## Вопрос, с которого всё начинается

У тебя есть `palette.png` — картинка из нескольких десятков цветов, простая, как иконка. LSB по каналам RGB ничего не даёт: в палитровом PNG пиксели хранят **не цвета**, а номера. Где искать данные в таком файле?

Ответ — в самой палитре. У индексированного изображения есть **таблица цветов** (`PLTE`), и в ней часто есть записи, которые картинка вообще не использует. Вот туда и прячут секрет. Разберём на `palette.png`.

## Наш пример: файл palette.png

Смотрим тип файла:

```bash
exiftool palette.png | grep -iE 'color type|width|height'
```

```text
Image Width                     : 32
Image Height                    : 32
Color Type                      : Palette
```

**Palette** (индексированный цвет) означает, что вместо RGB-чисел в пикселях лежат **индексы** — номера строк в таблице цветов. Например, индекс 5 означает «взять пятый цвет из палитры». Такая схема экономит место: палитра до 256 цветов, а каждый пиксель — один байт.

## Шаг 1: что такое палитра

**Палитра** — это список цветов, пронумерованный от 0. В PNG он хранится в чанке `PLTE` как последовательность троек «красный, зелёный, синий». Пиксель хранит только номер.

Ключевое наблюдение для стего: картинка часто использует **не все** 256 записей. Если картинка состоит из 16 цветов, а в палитре их 256, то 240 записей **никем не используются** — их значения можно заполнить чем угодно, и это никак не повлияет на изображение. Идеальное место для секрета.

## Шаг 2: читаем палитру

Достаём таблицу цветов через PIL:

```python
from PIL import Image
im = Image.open('palette.png')
pal = im.getpalette()            # плоский список: R0,G0,B0, R1,G1,B1, ...
print('mode:', im.mode, 'entries:', len(pal)//3)
```

```text
mode: P entries: 256
```

Палитра содержит все 256 записей, хотя картинка 32×32 использует лишь первые 16. Значит, остальные можно исследовать.

## Шаг 3: находим данные в неиспользуемых записях

Смотрим значения в записях, начиная с 16-й:

```python
chars = [pal[i*3] for i in range(16, 36)]      # красные компоненты
print('hidden:', bytes(chars).split(b'\x00')[0])
```

```text
hidden: b'flag{p4l3tt3_0rd3r}'
```

Флаг найден. Здесь каждый неиспользуемый цвет хранил в красном компоненте один символ кода ASCII, а нулевой байт служил терминатором. На картинке это никак не отразилось — эти записи просто не задействованы.

## Шаг 4: порядок палитры как канал

Ещё один приём — играть на **порядке** записей. Если поменять местами два близких цвета в палитре, картинка визуально почти не изменится, но последовательность индексов или сама таблица изменится. Данные кодируют в том, какие цвета идут первыми: например, наличие или отсутствие перестановки кодирует бит.

Это устойчивый метод: он переживает конвертации, которые разрушают LSB. Проверяют его, сравнивая палитру подозрительного файла с «эталонной»: любые необъяснимые перестановки — сигнал.

## Шаг 5: LSB индексов

Данные можно прятать и в самих **индексах пикселей**, а не в палитре. Пиксель хранит номер цвета; младший бит номера можно менять так, чтобы соседние цвета были похожи. Тогда картинка не изменится заметно, а младшие биты индексов понесут секрет. Извлекают их так же, как обычный LSB, только вместо значений каналов берут индексы:

```python
import numpy as np
from PIL import Image
idx = np.array(Image.open('palette.png'))       # индексы пикселей
bits = ''.join(str(int(p) & 1) for p in idx.reshape(-1))
out = bytes(int(bits[i:i+8], 2) for i in range(0, len(bits)-7, 8))
print(out[:40])
```

## Почему палитра — надёжный носитель

Палитровые изображения хороши для стего тем, что палитра — это **отдельная структура**, не связанная напрямую с пикселями. Пиксель ссылается на запись по номеру; если картинка не использует какую-то запись, её содержимое вообще ни на что не влияет. Значит, можно писать в «мёртвые» записи любой объём данных, и изображение останется побайтово совпадающим по внешнему виду.

Более того, даже **используемые** записи можно слегка менять: если два цвета в палитре визуально близки, подмена одного на другой почти не заметна, а данные в палитре — сохранены. Это делает метод устойчивее, чем LSB: пересохранение картинки в PNG не разрушит палитру, если редактор не пересчитает цвета.

Слабость тоже есть: если кто-то **оптимизирует** палитру (удалит неиспользуемые цвета или пересортирует их), данные пропадут. Поэтому в реальной стеганографии палитру заполняют так, чтобы «лишние» записи выглядели правдоподобно — например, плавными оттенками, а не случайными байтами.

## Палитра в GIF и чанк tRNS

Тот же принцип работает в **GIF**: это тоже индексированный формат, у него есть глобальная и локальная палитры, и в них можно прятать данные точно так же. GIF дополнительно умеет анимировать, поэтому данные можно распределять по кадрам — но это уже тема `stego-gif-animation`.

В PNG у палитры есть спутник — чанк **`tRNS`**, задающий прозрачность для отдельных индексов. Если картинка использует прозрачность, `tRNS` тоже становится каналом для сокрытия: его байты можно менять, не затрагивая цвета. А ещё бывает, что заявленное число цветов в `PLTE` меньше фактического — тогда «лишние» тройки байтов после таблицы являются скрытыми данными.

Практический вывод: разбирая палитровый файл, смотрите не только на пиксели, но и на все структуры вокруг них — `PLTE`, `tRNS`, а в GIF — на палитры кадров.

```text
  → итог: данные в «лишних» цветах палитры
```

## Если не сработало

- **Все записи палитры используются** — смотрите порядок цветов и LSB индексов пикселей.
- **Палитра выглядит нормально** — данные могут быть в чанке `tRNS` (прозрачность палитры) или в `PLTE` после заявленного числа цветов.
- **Картинка в GIF** — принцип тот же: GIF тоже индексированный, палитра может нести данные.
- **Пусто** — вернитесь к чанкам (`stego-png-chunks`) и бит-плоскостям (`stego-bitplane`).

## Что мы теперь знаем

- В **палитровом** PNG пиксели хранят **индексы**, а не цвета.
- Таблица цветов лежит в чанке **`PLTE`**.
- **Неиспользуемые записи** палитры — удобное место для секрета.
- **Порядок** записей тоже может кодировать данные.
- Секрет может быть и в **младших битах индексов** пикселей.
- GIF работает по тем же принципам.
- **`tRNS`** и «лишние» тройки после `PLTE` — тоже каналы для скрытых данных.

## Полный скрипт: палитра → флаг

Соберём разбор палитрового PNG в один прогон: сначала пробуем неиспользуемые записи, потом LSB индексов.

```python
from PIL import Image
import numpy as np

im = Image.open('palette.png')
pal = im.getpalette()                              # R0,G0,B0, R1,G1,B1, ...
used = set(np.array(im).reshape(-1).tolist())      # реально используемые индексы

# 1) неиспользуемые записи: красный компонент как байт
hidden = bytes(pal[i*3] for i in range(256) if i not in used)
print('unused:', hidden.split(b'\x00')[0])

# 2) LSB индексов пикселей
bits = ''.join(str(int(p) & 1) for p in np.array(im).reshape(-1))
out = bytes(int(bits[i:i+8], 2) for i in range(0, len(bits)-7, 8))
print('lsb   :', out[:40])
```

```text
unused: b'flag{p4l3tt3_0rd3r}'
lsb   : b'\x00\x00...'          # в этом файле данных нет
```

Первый канал сработал, второй пуст. Так и должно быть: в одном файле обычно спрятан **один** секрет, а остальные каналы служат отвлекающими.

## Справочная таблица: где искать в палитровых файлах

| Структура | Что несёт | Инструмент |
|-----------|-----------|-----------|
| `PLTE`, неиспользуемые записи | байты секрета | PIL `getpalette()` |
| `PLTE`, порядок записей | бит (перестановка) | сравнение с эталоном |
| Индексы пикселей LSB | поток битов | numpy + распаковка бит |
| `tRNS` | прозрачность как байты | `info['transparency']` |
| «Лишние» тройки после `PLTE` | сырые данные | парсер чанков вручную |

## Ограничения палитрового канала

Палитра — хрупкий носитель: любой редактор, который **оптимизирует** картинку (удаляет неиспользуемые цвета, пересортировывает записи, конвертирует в true-color), стирает данные без следа. Поэтому в реальной стеганографии «мёртвые» записи заполняют плавными оттенками, похожими на настоящую палитру, чтобы оптимизатор их не тронул. Ещё ограничение — объём: 256 записей × 3 байта = максимум 768 байт в самой палитре, поэтому длинные сообщения прячут в LSB индексов или распределяют по нескольким изображениям. И помни про индексацию: `getpalette()` возвращает плоский список, а не список троек, — не перепутай `pal[i*3]` с `pal[i]`.

## Проверка палитры на «испорченность»

Прежде чем искать данные, проверь, не прошёл ли файл через оптимизатор — это объясняет «пустые» каналы:

```bash
$ pngcheck -v palette.png | grep -E 'PLTE|tRNS'
PLTE chunk: 768 bytes (256 entries)
tRNS chunk: 256 bytes
$ python3 -c "from PIL import Image;i=Image.open('palette.png');print(i.mode,len(i.getpalette())//3)"
P 256
```

Если число записей `PLTE` меньше 256, а картинка использует все — «мёртвых» записей нет, и канал сместился в `tRNS` или в порядок цветов. Если `PLTE` занимает ровно `used_colors * 3` байт, палитру «сжал» оптимизатор, и данные из неиспользуемых записей уже потеряны.

## Практика: полный скрипт извлечения из палитры

Разберём рабочий сценарий от файла до флага. Первый шаг — прочитать палитру и найти записи, которые **не используются** ни одним пикселем: именно туда удобнее всего класть данные.

```python
from PIL import Image

im = Image.open("palette.png").convert("P")   # индексированный режим
pal = im.getpalette()                          # [r,g,b, r,g,b, ...]
idx = list(im.getdata())                       # индексы пикселей
n_colors = len(pal) // 3

used = set(idx)
unused = [i for i in range(n_colors) if i not in used]
print("записей в палитре:", n_colors, "неиспользовано:", len(unused))

# 1) данные в неиспользуемых записях
data = bytes(pal[i*3 + k] for i in unused for k in range(3))
print(data[:64])

# 2) LSB индексов пикселей
bits = [i & 1 for i in idx]
out = bytearray()
for b in range(0, len(bits) - 7, 8):
    byte = 0
    for j in range(8):
        byte = (byte << 1) | bits[b + j]
    out.append(byte)
print(bytes(out[:64]))
```

Если в `unused` лежит осмысленный ASCII или base64 — данные найдены. Если нет, переходите к LSB индексов: в палитровых изображениях изменение младшего бита индекса меняет цвет на «соседний» в палитре, который визуально почти неотличим.

## Различия носителей: PNG, GIF, BMP

Палитровый канал есть у нескольких форматов, и работа с ними отличается.

| Формат | Где палитра | Особенности | Инструмент |
|---|---|---|---|
| PNG | чанк `PLTE` | порядок записей, `tRNS` для прозрачности | Pillow, `pngcheck` |
| GIF | Global/Local Color Table | до 256 записей, LZW-сжатие | Pillow, `gifsicle` |
| BMP | 8-битная палитра | фиксированный порядок BGRX | Pillow, `xxd` |
| TIFF | цветовая карта | редко, но встречается | `tiffinfo`, Pillow |

Порядок записей в палитре сам по себе канал: если поменять местами две неиспользуемые записи, изображение не изменится, а порядок закодирует бит. На этом строится приём «палитра как перестановка»: сравниваем палитру с эталонной и читаем перестановку как число.

## Инструменты и автоматизация

```bash
# посмотреть чанки PNG и найти PLTE
pngcheck -v palette.png

# дампнуть палитру в hex
python3 -c "from PIL import Image; print(Image.open('palette.png').getpalette())"

# искать аномалии в записях палитры
zsteg palette.png
```

`zsteg` автоматически перебирает десятки каналов, включая палитровые, и часто выдаёт готовый флаг без ручного скрипта. Но на CTF, где данные лежат «нестандартно» (например, в порядке записей), полезнее собственный скрипт: он видит именно тот канал, который задумал автор задачи.

## Краевые случаи

- **Палитра больше, чем пикселей.** Неиспользуемые записи могут быть не «мусором», а специально оставленным каналом — не отбрасывайте их.
- **`tRNS` и альфа.** В GIF прозрачность — отдельная таблица; данные иногда прячут именно в ней, а не в `PLTE`.
- **Дубликаты цветов.** Две одинаковые записи палитры визуально неразличимы — идеальное место для бита.
- **Порядок записей и паддинг.** Некоторые генераторы дописывают палитру до 256 записей нулями; данные могут быть в «хвосте».
- **Конвертация формата.** `convert("P")` в Pillow может пересобрать палитру — для анализа читайте исходные байты чанка напрямую, а не пересохранённый файл.
