TCP-заголовок содержит множество полей, часть которых на практике «случайна» или редко проверяется. Именно поэтому TCP — богатый источник скрытых каналов: биты можно кодировать в начальном номере последовательности (ISN), в неиспользуемых флагах, в опциях, в размере окна и даже в порядке следования пакетов. Такие каналы требуют доступа к уровню, где виден сам заголовок, но зато крайне плохо детектируются прикладными средствами.

## Поля TCP, пригодные для сокрытия

- **ISN (Initial Sequence Number).** 32 бита при установке соединения. Обычно случайны — идеальное место для данных, если обе стороны договорились.
- **Sequence / Acknowledgment.** 32+32 бита на пакет, но сдвиг должен оставаться согласованным.
- **Флаги.** Поле flags 9 бит, из них реально используются ~6; редкие комбинации (`URG`+`PSH`) могут кодировать биты.
- **TCP options.** Опции переменной длины: padding, экспериментальные опции, `NOP`-последовательности.
- **Window size.** 16 бит, значение можно модулировать.
- **Urgent pointer.** Используется редко, может нести данные.
- **Тайминги и порядок.** Межпакетные задержки и перестановки кодируют биты.

Важное свойство: многие поля должны быть **согласованы** (иначе соединение порвётся), поэтому кодируют данные так, чтобы «смысловая» часть оставалась корректной, а избыточная несла сообщение.

## Инструменты и команды

- **`tshark`** — вывод конкретных полей TCP.
- **`scapy`** — сборка пакетов с произвольными полями.
- **`hping3`** — ручная генерация TCP с настраиваемыми флагами/seq.
- **`tcpdump -X`** — сырой hex-дамп заголовка.
- **`nmap`** — не для канала, но для понимания поведения ISN (`--seq-index`).

Извлечь ISN всех SYN-пакетов:

```bash
tshark -r tcp.pcap -Y "tcp.flags.syn==1 && tcp.flags.ack==0" \
  -T fields -e ip.src -e tcp.srcport -e tcp.seq
```

Показать опции TCP:

```bash
tshark -r tcp.pcap -Y tcp -T fields -e tcp.options
```

## Разобранный пример: данные в ISN

Пусть три SYN-пакета несут по 4 байта в поле `tcp.seq`:

```bash
$ tshark -r isn.pcap -Y 'tcp.flags.syn==1 && tcp.flags.ack==0' -T fields -e tcp.seq
1734437990
1953653108
1684957028
```

Преобразуем каждое число в 4 байта big-endian и соберём ASCII:

```python
vals = [1734437990, 1953653108, 1684957028]
out = b"".join(v.to_bytes(4, "big") for v in vals)
print(out.decode(errors="replace"))
```

Так из «случайных» ISN собирается осмысленная строка. Именно поэтому в CTF ISN-канал часто маскируют под обычное сканирование портов.

## Данные во флагах и опциях

Поле флагов можно использовать как 6-битное значение. Например, комбинация флагов в каждом пакете задаёт по одному символу base64-алфавита. Разбор:

```bash
tshark -r flags.pcap -Y tcp -T fields -e tcp.flags -e tcp.flags.str | head
```

Опции TCP — отдельная ниша: padding-опции (`Kind=0` EOL, `Kind=1` NOP) обычно не несут смысла, и в них можно закодировать данные. Экспериментальные опции (`Kind=253/254`) редко фильтруются.

```bash
tshark -r opts.pcap -Y "tcp.options" -T fields -e tcp.options \
  | tr ',' '\n' | sort | uniq -c
```

## Сборка канала через scapy

Задать конкретный ISN:

```python
from scapy.all import IP, TCP, send
send(IP(dst="10.0.0.5")/TCP(dport=80, flags="S", seq=0x676c66), verbose=False)
```

Задать флаги и опции:

```python
from scapy.all import IP, TCP, send
pkt = IP(dst="10.0.0.5")/TCP(dport=80, flags="S",
      options=[(253, b"\x66\x6c\x61\x67")])
send(pkt, verbose=False)
```

Получатель читает `tcp.options` и восстанавливает данные.

## Тайминговые каналы TCP

Если менять поля нельзя (их проверяет NAT/IDS), кодируют интервалы между пакетами: короткая пауза — `0`, длинная — `1`. Такой канал медленный (единицы бит в секунду), но практически невидим для анализа содержимого. Детект строится на статистике межпакетных интервалов:

```bash
tshark -r timing.pcap -Y tcp -T fields -e frame.time_delta | head
```

Аномально регулярные или бимодальные интервалы — признак таймингового канала.

## Обнаружение и анализ

1. `tshark -z io,stat,1` — всплески и ритм трафика.
2. ISN: собрать `tcp.seq` SYN-пакетов, проверить на ASCII/энтропию.
3. Флаги: найти редкие комбинации (`tcp.flags.str`).
4. Опции: нестандартные Kind, длинный padding.
5. Тайминги: распределение `frame.time_delta`.

```bash
tshark -r tcp.pcap -Y tcp -T fields -e tcp.flags.str | sort | uniq -c | sort -rn
```

## Частые ошибки и подводные камни

- **Путать sequence и ISN.** Данные обычно в ISN при установке, а не в каждом пакете.
- **Ломать согласованность.** Менять seq/ack «в лоб» нельзя — соединение порвётся.
- **Игнорировать опции.** Padding — частое и незаметное место.
- **Забыть про порядок.** Перестановка пакетов тоже кодирует биты.
- **Считать ISN всегда случайным.** В CTF он намеренно структурирован.
- **Не проверять флаги.** Редкие комбинации — прямой сигнал.

## Таблица каналов в TCP

| Канал | Биты на пакет | Согласованность | Заметность |
|---|---|---|---|
| ISN | 32 | только при handshake | средняя |
| Sequence/Ack | 64 | строгая | низкая |
| Флаги | ~6 | свободная | средняя |
| Options/padding | десятки | свободная | низкая |

## Что дальше / решение

- Соберите SYN-пакеты и проверьте `tcp.seq` на ASCII (`scapy`/`xxd`).
- Просмотрите `tcp.flags.str` на редкие комбинации.
- Проверьте `tcp.options` на нестандартные Kind и padding.
- Оцените `frame.time_delta` — нет ли таймингового канала.
- Если TCP чист — переходите к каналам по длине (`stego-covert-length`).

## Установление соединения и его роль

Скрытый канал в TCP удобнее всего строить на этапе установления соединения (three-way handshake). Именно там передаётся ISN, а окно возможностей велико: клиент и сервер обмениваются SYN, SYN-ACK, ACK, и ни одно из полей не несёт смысла, кроме согласования. Если обе стороны — свои, они могут договориться: «младшие 16 бит ISN — это данные». Промежуточные устройства видят лишь обычный handshake.

Обратная сторона: канал на handshake «одноразовый» — чтобы передать много данных, нужно много соединений, что само по себе аномально (сотни SYN к одному порту). Поэтому в реальных туннелях чаще комбинируют: немного данных в ISN, остальное — в опциях и таймингах уже установленного соединения.

## TCP options детально

Опции TCP идут после заголовка и имеют формат `Kind-Length-Data`. Стандартные: MSS (2), Window Scale (3), SACK Permitted (4), Timestamps (8), NOP (1), EOL (0). Пространство для сокрытия:

- **Padding** — опции выравнивают до 4 байт, добавляя `NOP`; их количество может кодировать биты.
- **Экспериментальные Kind** (253, 254) — редко валидируются, идеальны для данных.
- **Timestamps** — 32-битные значения, если отключена синхронизация, можно модулировать.
- **MSS** — нестандартные значения (например, 1420 vs 1460) кодируют биты.

```bash
tshark -r opts.pcap -Y "tcp.options" -T fields -e tcp.options.mss_val -e tcp.options.kind | head
```

Получатель читает опции из каждого пакета и собирает поток.

## Детект на стороне защиты

IDS/IPS ловят TCP-каналы по признакам:

- **Редкие флаги** — комбинации, которых не бывает у настоящего стека (`FIN+SYN`, `URG+PSH+SYN`).
- **Нестандартные опции** — экспериментальные Kind, странный padding.
- **Аномальный ISN** — если ISN не выглядит случайным (монотонный, ASCII).
- **Ритм** — бимодальные межпакетные интервалы.
- **Размер окна** — постоянный, хотя должен варьироваться.

Правило `alert tcp any any -> any any (msg:"covert"; tcp.flags:FPU!; ...)` — пример сигнатуры на редкие флаги.

## Практический разбор: ISN-канал в CTF

Порядок действий для pcap-задачи:

1. `tshark -r tcp.pcap -Y 'tcp.flags.syn==1 && tcp.flags.ack==0' -T fields -e tcp.seq`.
2. Преобразовать значения в 4 байта big-endian.
3. Проверить, печатаются ли символы (ASCII-диапазон 0x20–0x7E).
4. Если да — собрать строку; если нет — проверить base64/hex.

```python
seqs = [1734437990, 1953653108, 1684957028]
raw = b"".join(s.to_bytes(4, "big") for s in seqs)
print(raw)                 # b'flag...'
```

## Сборка канала через hping3

`hping3` позволяет задать почти любое поле вручную:

```bash
# SYN с заданным ISN и payload
hping3 -S -p 80 -s 12345 -M 1734437990 -d 0 10.0.0.5
# с определёнными флагами
hping3 -F -P -U -p 80 10.0.0.5
```

Флаг `-M` задаёт sequence number, `-d` — размер данных. Так проверяют, как цель реагирует на аномальные поля, и строят канал.

## Ограничения и почему это редкость

TCP-каналы на практике редки: они требуют доступа к уровню, где можно произвольно менять заголовки (нужен raw socket или своя ОС), и легко ломаются NAT/файрволами, которые нормализуют заголовок. Поэтому в CTF они встречаются как «умные» задачи, а в реальной эксфильтрации чаще используют payload-каналы (DNS, HTTP), где не надо бороться с нормализацией.
