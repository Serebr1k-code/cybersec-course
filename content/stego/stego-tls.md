## Вопрос, с которого всё начинается

Тебе дали `clienthello.bin` — сырой TLS ClientHello, первый пакет HTTPS-соединения.
TLS шифрует содержимое, поэтому кажется, что «смотреть нечего». Но заголовки и
рукопожатие передаются **открыто**, и в них полно полей, которые никто не проверяет.
Где спрятать сообщение? Разберём пакет с самого начала.

## Наш пример: файл clienthello.bin

```bash
xxd -l 64 clienthello.bin
```

```text
00000000: 1603 0100 4e01 0000 4a03 0335 d922 e67e  ....N...J..5.".~
00000010: 65df dcd4 39e5 5728 b945 e05f e872 7278  e...9.W(.E._.rrx
00000020: 9dc3 1484 0b94 0776 6839 0000 0213 0101  .......vh9......
00000030: 0000 1f00 0000 0600 056c 6162 00fd e800  .........lab....
```

Видим `16 03 01` — TLS record (тип 0x16 = handshake, версия 0x0301 = TLS 1.0 в
записи). Дальше `01` — тип handshake (ClientHello). В конце видим `fd e8` — тип
расширения `0xFDE8`, а после него — данные. Разберём структуру.

## Шаг 1: структура TLS-записи

TLS-трафик состоит из **записей** (records). Каждая запись:

```
[ тип(1) ][ версия(2) ][ длина(2) ][ данные ]
```

Тип: `0x16` — handshake, `0x17` — application data, `0x15` — alert, `0x14` —
change cipher spec. Версия в записи обычно `0x0301` (для совместимости), а реальная
версия — внутри handshake.

Внутри handshake-записи идёт **handshake-сообщение**:

```
[ тип(1) ][ длина(3) ][ тело ]
```

Тип `0x01` — ClientHello, `0x02` — ServerHello, `0x0B` — Certificate.

## Шаг 2: тело ClientHello

ClientHello содержит:

- `legacy_version` (2 байта, обычно `0x0303`);
- `random` (32 байта — случайные данные);
- `session_id` (длина 1 байт + данные);
- `cipher_suites` (длина 2 байта + список);
- `compression_methods` (длина 1 байт + список);
- **`extensions`** (длина 2 байта + список расширений).

**Расширения** — самое интересное:

```
[ тип(2) ][ длина(2) ][ данные ]
```

Их десятки: `0x0000` — server_name (SNI), `0x0010` — ALPN, `0x002B` — supported
versions, `0x0033` — key_share. А диапазон `0xFF00`–`0xFFFF` — «private use»: для
экспериментов. Именно там и прячут.

## Шаг 3: достаём расширение вручную

```bash
python3 - <<'PY'
d = open('clienthello.bin','rb').read()
p = 5 + 4 + 2 + 32          # record + handshake header + version + random
sid = d[p]; p += 1 + sid
cs = int.from_bytes(d[p:p+2],'big'); p += 2 + cs
cm = d[p]; p += 1 + cm
elen = int.from_bytes(d[p:p+2],'big'); p += 2
end = p + elen
while p + 4 <= end:
    et = int.from_bytes(d[p:p+2],'big')
    ln = int.from_bytes(d[p+2:p+4],'big')
    data = d[p+4:p+4+ln]
    if et == 0xFDE8:
        print(data.decode('latin-1'))
    p += 4 + ln
PY
```

## Шаг 4: где ещё прячут в TLS

- **SNI** (`0x0000`) — имя сервера; можно положить длинную «странную» строку.
- **Session ticket** — в TLS 1.2 это непрозрачный blob; в TLS 1.3 он шифруется.
- **Порядок расширений** — перестановочный канал.
- **Паддинг** (`0x0015`) — штатное расширение с нулями; внутрь можно положить данные.
- **ALPN** — список протоколов; «лишние» строки.

## Шаг 5: инструменты

```bash
tshark -r capture.pcap -Y 'tls.handshake.type==1' -V | head -80
openssl s_client -connect host:443 -msg
tls-parser / ja3
```

`tshark` разбирает расширения человекочитаемо. `openssl s_client -msg` печатает
handshake при подключении. JA3 — «отпечаток» TLS, который тоже можно модулировать.

## Шаг 6: почему TLS удобен для сокрытия

TLS шифрует **полезную нагрузку**, но рукопожатие — открыто, иначе соединение не
состоится. Значит, всё, что в ClientHello/ServerHello, видно посреднику. Расширения
private use легальны, а сервер их игнорирует, если не понимает. Получается канал,
который выглядит как обычный HTTPS, но несёт данные в открытом виде.

## Шаг 7: частые ошибки

Первая — путать версию в записи и версию handshake: в записи почти всегда `0x0301`.
Вторая — неверно считать длину session_id (1 байт, а не 2). Третья — забыть, что
длина расширений — общая, а внутри — отдельные длины. Четвёртая — считать, что без
ключей «ничего не видно»: заголовки и handshake видны всегда.

## Практика: ServerHello и session ticket

Закладка бывает не только на клиенте. Разберём ответ сервера. ServerHello имеет ту же
структуру handshake, но в нём нет списка шифров, зато есть выбранные параметры и
расширения. Один из самых удобных носителей — **session ticket** (расширение
`0x0023` в TLS 1.2). Это «билет», который сервер выдаёт клиенту, чтобы не хранить
сессию у себя. Формально его содержимое — непрозрачный blob, и клиент не проверяет,
что внутри. Если сервер и клиент сговорились, в билет можно положить произвольные
данные.

```bash
python3 - <<'PY'
# разбор расширений ServerHello (после 5+4+2+32+sessionid+2+cs+1+cm)
d = open('serverhello.bin','rb').read()
p = 5 + 4 + 2 + 32
sid = d[p]; p += 1 + sid
cs = int.from_bytes(d[p:p+2],'big'); p += 2 + cs
cm = d[p]; p += 1 + cm
elen = int.from_bytes(d[p:p+2],'big'); p += 2
end = p + elen
while p + 4 <= end:
    et = int.from_bytes(d[p:p+2],'big')
    ln = int.from_bytes(d[p+2:p+4],'big')
    print(hex(et), ln, d[p+4:p+4+ln][:40])
    p += 4 + ln
PY
```

## Как отличить закладку от штатных расширений

TLS-расширений десятки, и многие содержат «случайные» байты (key_share, random).
Признаки закладки:

- **Private-use тип** (`0xFF00`–`0xFFFF`) — если он есть, это почти наверняка вручную.
- **ASCII внутри бинарного расширения** — session ticket и key_share бинарны; текст
  в них подозрителен.
- **Слишком длинное расширение** для своего типа.
- **Повторяющиеся расширения** — спецификация запрещает дубли.

Практический приём: сравни ClientHello разных соединений того же клиента. Настоящий
набор расширений стабилен (одинаковый JA3); закладка вносит «лишнее».

## Итоговая стратегия для TLS

Разбери запись, затем handshake, затем расширения. Ищи private-use и необычно
большие расширения. Проверь SNI, ALPN, session ticket и padding. Если трафик
зашифрован (TLS 1.3), заголовки всё равно видны: тип записи, длины, размеры
шифротекста. И помни: `tshark` покажет расширения, но ручной парсер надёжнее для
нестандартных типов.

## TLS 1.3: что изменилось для стеганографии

В TLS 1.3 большая часть рукопожатия шифруется: после ServerHello всё, включая
сертификат, идёт в зашифрованном виде. Session ticket тоже шифруется ключом сервера.
Это сужает открытые поля, но не убирает их:

- **ClientHello** остаётся открытым (иначе сервер не поймёт, что хочет клиент).
- **Расширения ClientHello** видны полностью, включая private-use.
- **Длины записей** и их количество видны и могут нести информацию (тайминг-канал).
- **SNI** виден, если не используется ECH (Encrypted Client Hello).

Получается, что даже в самом современном TLS у атакующего есть открытый канал в
ClientHello. В CTF задачи на TLS почти всегда строятся на ClientHello и его
расширениях — именно потому, что это единственная стабильно открытая часть.

## Сравнение с HTTP-заголовками

В уроке про HTTP мы прятали данные в заголовках: `User-Agent`, `Cookie`, `X-*`. TLS
работает на уровень ниже, но принцип тот же: **поле, которое получатель
интерпретирует свободно**. Разница в том, что HTTP-заголовки — текст, а TLS —
бинарный формат с длинами. Соответственно, в HTTP закладку видно глазами, а в TLS
нужен парсер. Зато TLS-канал «невидимее»: прокси и балансировщики часто разбирают
HTTP, но не лезут в расширения TLS.

## Практика: JA3 и «отпечатки»

JA3 — это хэш от набора параметров ClientHello (версия, шифры, расширения). Он
используется для фингерпринтинга клиентов. Для стеганографии важно, что JA3 зависит
от порядка и состава расширений — значит, меняя «лишнее» расширение, ты меняешь и
отпечаток. Это палка о двух концах: закладка меняет JA3, и система может заметить
аномалию. В CTF на это обычно не смотрят, но в реальной атаке это надо учитывать.

## Чек-лист по TLS-дампу

1. Определи границы записей (`тип + версия + длина`).
2. Если тип `0x16` — разбери handshake (`тип + длина(3) + тело`).
3. Для ClientHello/ServerHello найди блок расширений (после session_id, шифров,
   сжатия).
4. Перечисли все расширения и их типы; обрати внимание на `0xFF00`–`0xFFFF`.
5. Проверь SNI, ALPN, padding, session ticket на текстовые/странные данные.
6. Декодируй найденные байты как ASCII/base64/zlib.
7. Если TLS 1.3 — смотри только ClientHello (остальное зашифровано).

Такой порядок покрывает и CTF, и реальный анализ. Главное — не «сдаваться» из-за
шифрования: рукопожатие открыто всегда.

## Что мы теперь знаем

- TLS-запись: `тип + версия + длина + данные`.
- Handshake: `тип + длина(3) + тело`; ClientHello содержит расширения.
- Расширение: `тип(2) + длина(2) + данные`; `0xFDE8` — private use.
- SNI, session ticket, паддинг, порядок расширений — каналы.
- Заголовки TLS видны без ключей; шифруется только полезная нагрузка.
