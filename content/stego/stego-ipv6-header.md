## Вопрос, с которого всё начинается

Тебе дали `packet.bin` — один IPv6-пакет. IPv6-заголовок больше IPv4 и умеет
«расширяться»: после базового заголовка идут extension headers с опциями. Где тут
спрятать сообщение? Оказывается, опции можно добавлять — и стандарт разрешает
«неизвестные» типы, которые получатель обязан пропустить. Разберём пакет.

## Наш пример: файл packet.bin

```bash
xxd packet.bin
```

```text
00000000: 6000 0000 0020 3c40 2001 0000 0000 0000  `.... <@........
00000010: 0000 0000 0000 0000 2001 0000 0000 0000  ........ .......
00000020: 0000 0000 0000 0000 3b03 1e16 6e74 6f7b  ........;...nto{
00000030: 3170 7636 5f30 7074 3130 6e73 5f66 6c34  1pv6_0pt10ns_fl4
00000040: 6764 7d00 0000 0000                      gd}.....
```

Первые 40 байт — базовый IPv6-заголовок. Байт `3c` (60) в поле Next Header означает
**Destination Options**. Дальше — заголовок опций, а в нём ASCII-флаг. Разберём.

## Шаг 1: базовый IPv6-заголовок

IPv6-заголовок **фиксированный — 40 байт**:

- **Version/Traffic Class/Flow Label** (4 байта): версия = 6.
- **Payload Length** (2 байта) — длина всего после заголовка.
- **Next Header** (1 байт) — тип следующего заголовка.
- **Hop Limit** (1 байт) — аналог TTL.
- **Source Address** (16 байт).
- **Destination Address** (16 байт).

Поле Next Header = `6` (TCP), `17` (UDP), `58` (ICMPv6), `60` (Destination Options),
`43` (Routing), `44` (Fragment), `0` (Hop-by-Hop). Если Next Header — extension, то
в extension есть свой Next Header, и так выстраивается цепочка.

## Шаг 2: extension headers

Extension header устроен так:

```
[ Next Header(1) ][ Hdr Ext Len(1) ][ данные ]
```

`Hdr Ext Len` — длина в 8-байтных блоках, **не считая** первых 8 байт. Внутри данных
для Destination Options и Hop-by-Hop лежат **опции**:

```
[ Option Type(1) ][ Option Data Len(1) ][ Option Data ]
```

Старшие два бита Option Type задают поведение при неизвестной опции: `00` — пропустить,
`01` — отбросить, `10` — отбросить и ICMP, `11` — отбросить и ICMP (если не multicast).
Типы `0x1E`-подобные (00xxxxxx) — «пропустить», идеальны для закладки.

## Шаг 3: разбираем опции вручную

```bash
python3 - <<'PY'
d = open('packet.bin','rb').read()
nh = d[6]                      # Next Header базового заголовка
p = 40
while nh not in (6, 17, 58, 59) and p + 2 <= len(d):
    nh2 = d[p]; extlen = d[p+1]
    # опции: для 60/0 идём по опциям
    if nh in (0, 60):
        q = p + 2
        end = p + 8 + extlen*8
        while q + 2 <= end:
            ot = d[q]; ol = d[q+1]
            data = d[q+2:q+2+ol]
            if ot == 0x1E:
                print(data.decode('latin-1'))
            q += 2 + ol
    p = p + 8 + extlen*8
    nh = nh2
PY
```

```text
nto{1pv6_0pt10ns_fl4g}
```

## Шаг 4: где ещё прячут в IPv6

- **Flow Label** (20 бит) — можно модулировать младшие биты.
- **Hop-by-Hop options** — то же, что Destination, но обрабатываются каждым роутером.
- **Routing header** — список адресов; можно добавить «лишние».
- **Fragment header** — поля идентификатора фрагмента.
- **Порядок extension headers** — спецификация ограничивает, но не жёстко.

## Шаг 5: инструменты

```bash
tshark -r capture.pcap -Y 'ipv6' -V | head -80
scapy                            # Python для разбора/сборки
ip -6 route
```

`tshark` покажет extension headers и опции. `scapy` удобен для ручного разбора и
сборки тестовых пакетов: `IPv6()/IPv6ExtHdrDestOpt()/...`.

## Шаг 6: почему IPv6 удобен для сокрытия

IPv6 проектировался с расчётом на расширяемость: extension headers можно добавлять,
а неизвестные опции — пропускать. Это легальный механизм, а не баг. Значит, пакет с
«лишней» опцией не считается аномалией: маршрутизаторы обязаны его обработать. Для
стеганографии это идеальные условия — открытый, стандартный, непроверяемый канал.

## Шаг 7: частые ошибки

Первая — считать extension headers частью базового: базовый всегда 40 байт. Вторая —
неверно считать Hdr Ext Len: это число 8-байтных блоков минус 1. Третья — путать
Option Type и Option Data Len. Четвёртая — не дойти до конца цепочки extension headers
(их может быть несколько подряд).

## Практика: цепочка extension headers

Extension headers можно выстроить в цепочку: Hop-by-Hop → Routing → Fragment →
Destination Options. Каждый указывает на следующий через своё поле Next Header.
Парсер должен идти по цепочке, пока не встретит «конечный» протокол (TCP/UDP/ICMPv6).

```bash
python3 - <<'PY'
d = open('packet.bin','rb').read()
nh = d[6]; p = 40
while nh not in (6, 17, 58, 59):
    print('ext header at', p, 'next =', d[p])
    extlen = d[p+1]
    nh = d[p]
    p += 8 + extlen*8
print('payload at', p, 'proto', nh)
PY
```

Закладку можно спрятать в любом из звеньев цепочки. Часто её кладут в «лишний»
extension header, которого в норме быть не должно, — например, два Destination Options
подряд.

## Как отличить закладку от штатных опций

IPv6-опции имеют строгие назначения: Pad1, PadN, Router Alert, Jumbo Payload. Их типы
известны. Признаки закладки:

- **Неизвестный тип опции** (особенно в диапазоне «пропустить» 00xxxxxx).
- **Текстовая нагрузка** в опции — стандартные опции бинарны.
- **Опция нестандартной длины** для известного типа.
- **Лишний extension header**, не нужный для маршрутизации.

Практический приём: сравни пакеты одного потока. Настоящие опции повторяются; закладка
вносит «лишнее».

## Итоговая стратегия для IPv6

Проверь Next Header базового заголовка; если это extension — обойди цепочку; внутри
Destination/Hop-by-Hop разбери опции; ищи неизвестные типы и текстовые данные. Проверь
Flow Label на модуляцию. И помни: база всегда 40 байт, а `Hdr Ext Len` считает
8-байтные блоки минус 1.

## Hop-by-Hop против Destination Options

Два самых удобных для закладки extension headers — Hop-by-Hop (Next Header 0) и
Destination Options (60). Разница в том, кто их обрабатывает:

- **Hop-by-Hop** обязан обработать **каждый** маршрутизатор на пути. Поэтому он должен
  идти сразу после базового заголовка, и многие роутеры его фильтруют.
- **Destination Options** обрабатывает только конечный получатель (и узлы из routing
  header). Поэтому он «проходит» через сеть свободнее.

Для стеганографии это значит: Destination Options надёжнее — его реже режут
firewall'ы. Hop-by-Hop хорош, когда закладка должна быть видна на промежуточных узлах
(например, в лабораторной сети).

## Практика: модуляция Flow Label

Flow Label — 20-битное поле в базовом заголовке, предназначенное для пометки потока.
Спецификация требует, чтобы оно было одинаковым для всех пакетов потока, но на
практике многие стеки его не проверяют. Значит, младшие биты можно использовать как
канал, а «потеря» нескольких бит не влияет на маршрутизацию.

```bash
python3 - <<'PY'
d = open('packet.bin','rb').read()
flow = ((d[1] & 0x0f) << 16) | (d[2] << 8) | d[3]
print('flow label', hex(flow), 'lsb', flow & 1)
PY
```

Если собрать младшие биты Flow Label множества пакетов — получится ещё один канал.

## Почему IPv6 в CTF встречается реже IPv4

IPv4 проще: заголовок 20 байт, опции редки. IPv6-пакеты обычно «чистые»: без
extension headers. Поэтому задача на IPv6-стеганографию — это почти всегда «явно
дан пакет с extension header, найди в нём данные». Ключ к решению — знать, что
Next Header может указывать на extension, а не на TCP/UDP. Многие, увидев пакет,
сразу ищут TCP-заголовок по смещению 40 и не понимают, почему «мусор». На самом
деле там extension header.

## Чек-лист по IPv6-пакету

1. Прочитай базовый заголовок (40 байт), запомни Next Header.
2. Если Next Header — extension (0, 43, 44, 60, 51), иди по цепочке.
3. Для Hop-by-Hop/Destination разбери опции (`тип + длина + данные`).
4. Ищи неизвестные типы опций и текстовые данные.
5. Проверь Flow Label и Routing header на «лишние» значения.
6. Если цепочка кончается на TCP/UDP — payload начинается там.

Для CTF этого достаточно: закладка почти всегда в опции Destination Options. Для
реальной форензики добавь сравнение пакетов одного потока и профиль типичных
extension headers.

## Итог

IPv6-заголовок — самый «расширяемый» из сетевых заголовков: extension headers и опции позволяют добавить почти произвольные данные, не нарушая стандарт. В CTF это отражается в задачах, где «обычный» пакет несёт лишний Destination Options header. Ключевой навык — уметь идти по цепочке Next Header и разбирать опции вручную.

## Заключительная мысль

Расширяемость IPv6 — не баг, а задуманная возможность. Именно поэтому «лишний» extension header не считается аномалией, а опции произвольного типа разрешены. Для стеганографии это идеальный канал: стандартный, открытый и не проверяемый по содержимому.

## Что мы теперь знаем

- Базовый IPv6-заголовок — 40 байт; Next Header задаёт следующий.
- Extension header: `Next Header + Hdr Ext Len + данные`.
- Опция: `тип + длина + данные`; типы 00xxxxxx пропускаются.
- Flow Label, routing, fragment — дополнительные каналы.
- Инструменты: `tshark`, `scapy`.
