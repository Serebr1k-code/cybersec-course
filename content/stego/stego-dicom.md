## Вопрос, с которого всё начинается

Ты получил файл `scan.dcm`. Команда `file` говорит загадочное «DICOM medical imaging
data». Это не PNG и не JPEG, которые мы разбирали раньше. Внутри — медицинский
снимок, и, возможно, в нём что-то спрятано. Как вообще устроен этот формат и где в
нём можно спрятать данные?

## Наш пример

Открываем файл:

```
$ file scan.dcm
scan.dcm: DICOM medical imaging data
```

DICOM (Digital Imaging and Communications in Medicine) — стандарт обмена медицинскими
изображениями. Файл — это последовательность **тегов** (data elements): каждый тег
имеет группу и элемент, длину и значение. Первые байты — преамбула из 128 нулей и
сигнатура `DICM`.

## Шаг 1: структура файла

```
$ dcmdump scan.dcm
(0002,0000) UL 208                                      # FileMetaInformationGroupLength
(0002,0002) UI "1.2.840.10008.5.1.4.1.1.7"              # MediaStorageSOPClassUID (Secondary Capture)
(0002,0003) UI "1.2.826.0.1.3680043.8.498.1234"         # MediaStorageSOPInstanceUID
(0008,0060) CS "OT"                                     # Modality
(0010,0010) PN "DOE^JOHN"                               # PatientName
(0010,0020) LO "P1234567"                               # PatientID
(0028,0010) US 256                                      # Rows
(0028,0011) US 256                                      # Columns
(7FE0,0010) OW ...                                      # PixelData
```

Ключевые вещи для нас:

- **Теги** вида `(GGGG,EEEE)` — группа и элемент. `0010,xxxx` — данные пациента
  (PHI: имя, ID, дата рождения).
- **`(7FE0,0010) PixelData`** — сами пиксели. Это либо сырой массив, либо сжатый
  (JPEG/JPEG2000) поток.
- **`(60xx,3000) OverlayData`** — «overlay»-плоскости: однобитные маски поверх
  изображения (используются для разметки, но могут нести данные).
- **Приватные теги** — группы с нечётным номером (например, `(0009,xx)`): их
  назначение определяется производителем, стандарт их не описывает.

## Шаг 2: где прячут данные

DICOM — удобный контейнер, потому что в нём много «свободных» мест:

1. **LSB в PixelData.** Классика: младшие биты значений пикселей. Если снимок 16-битный
   (тип `OW`), на каждый пиксель приходится 2 байта — места вдвое больше, чем в 8-битном PNG.
2. **Приватные теги.** Можно добавить `(0009,0010) LO "..."` с произвольным текстом —
   валидаторы его игнорируют.
3. **Overlay-плоскости.** `OverlayData` — битовая карта; если она не используется для
   разметки, в ней можно спрятать произвольные биты.
4. **Padding.** У тегов с нечётной длиной добавляется байт-заполнитель (`\0`); злоупотребление
   им даёт канал.
5. **Свободные/неиспользуемые теги.** Например, `(0028,0120) PixelPaddingValue`.

Извлекаем через Python:

```
$ python3 extract.py
(0028,0010) Rows = 256
(0028,0011) Columns = 256
LSB payload: nto{d1c0m_p1x3l_lsb_h1dd3n}
```

## Шаг 3: PHI — самая реальная угроза

В CTF интересен флаг, но в реальности главная проблема DICOM — **утечка PHI**
(Protected Health Information). Теги `(0010,xxxx)` содержат имя, ID, дату рождения
пациента. Если медицинский снимок утекает в открытый доступ **без деидентификации**,
это инцидент приватности.

Простая деидентификация: удалить/заменить теги группы `0010` и `0008` (дата, врач).
Но есть ловушка: **приватные теги и PixelData могут содержать «выжженные» в
изображении подписи** (burned-in annotation) — имя пациента, впечатанное прямо в
пиксели. Тег `(0028,0301) BurnedInAnnotation` предупреждает об этом.

## Шаг 4: поиск скрытого на практике

Пайплайн разбора DICOM:

```
$ strings scan.dcm
DICM
1.2.840.10008.5.1.4.1.1.7
DOE^JOHN
P1234567
...
$ python3 dump_tags.py
```

`dump_tags.py` (упрощённо) перебирает теги и печатает те, что не в стандартном
списке, — там и прячется необычное. Также полезно сравнить размер файла с
ожидаемым: если PixelData «толще», чем нужно для 256×256×2 байт, в файл что-то
дописали.

## Шаг 5: инструменты

- **`dcmdump`** (пакет `dcmtk`) — печать всех тегов.
- **`pydicom`** (Python) — полноценный разбор: `ds = pydicom.dcmread('scan.dcm')`,
  затем `ds.PixelData`, перебор `ds.iterall()`.
- **`dcmtk`/`gdcm`** — конвертация, анонимизация (`gdcmanon`).
- **`hexdump`/`xxd`** — ручной поиск после тегов.

Типичный приём: `python3 -c "import pydicom; d=pydicom.dcmread('scan.dcm'); print(d)"`
покажет все теги, включая приватные.

## Что мы теперь знаем

- DICOM — формат из **тегов** `(GGGG,EEEE)`; начало — преамбула 128 байт + `DICM`.
- Данные прячут в **PixelData (LSB)**, **приватных тегах**, **overlay-плоскостях** и
  padding.
- Теги группы `0010` — это **PHI**, самая чувствительная часть.
- Разбирают через `dcmdump`/`pydicom`; подозрительное — приватные и нестандартные теги.
- «Выжженные» подписи в пикселях обходят удаление тегов.

## Куда дальше

Мы разобрали медицинский формат. Дальше — ещё более экзотические носители: **3D-модели**
(STL/OBJ/PLY), где данные прячут в координатах вершин и комментариях. А пока главное
запомни: **DICOM — это теги, а не картинка**, и прятать в нём можно и в пикселях, и в
метаданных.

## Где пригодится

- **CTF:** задачи с необычным форматом-контейнером.
- **Форензика:** разбор медицинских данных, поиск утечек PHI.
- **Работа:** аудит деидентификации в PACS и защита медицинских изображений.
- **Bug bounty:** утечки снимков через открытые хранилища.
