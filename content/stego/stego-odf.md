## Вопрос, с которого всё начинается
OpenDocument (ODT/ODS/ODP) — открытый формат LibreOffice и многих госструктур.
Как и EPUB, это ZIP. Но у него есть особенность: служебные XML-файлы, которые
редактор не показывает. Один из них — `meta.xml` — принимает **пользовательские
поля** произвольной длины. Идеальное место для закладки.

## Наш пример
Возьмём `doc.odt` — минимальный документ. Разберём его ZIP-структуру и найдём
закладку в `meta.xml`.

## Шаг 1: структура ODF
```
$ unzip -l doc.odt
  Length      Name
        39  mimetype
       900  META-INF/manifest.xml
      1200  content.xml
       600  styles.xml
       420  meta.xml
       300  settings.xml
```

`mimetype` — `application/vnd.oasis.opendocument.text` (первая запись, без
сжатия). Далее — XML-файлы:
- `content.xml` — текст и разметка;
- `styles.xml` — стили;
- `meta.xml` — метаданные (автор, дата, **пользовательские поля**);
- `settings.xml` — настройки окна;
- `META-INF/manifest.xml` — список файлов и типов.

## Шаг 2: пользовательские поля в meta.xml
Стандарт ODF определяет элемент `meta:user-defined` с атрибутом `meta:name` и
произвольным текстовым значением. Никто его не отображает — это «техническое»
поле:

```xml
<meta:user-defined meta:name="BuildID">bnRve29kZl9tZXRhX2ZpZWxkfQ==</meta:user-defined>
```

Значение — base64. Редактор сохранит его, читатель не увидит.

## Шаг 3: другие каналы в ODF
- **Лишние файлы.** Запись ZIP, не указанная в `manifest.xml`, — невидима.
- **`content.xml` пробелы.** Как в JSON: незначащие пробелы между тегами.
- **Встроенные объекты.** `Thumbnails/thumbnail.png` — картинка, в пикселях
  которой можно спрятать данные.
- **`settings.xml`.** Произвольные пары ключ-значение.

## Шаг 4: извлечение вручную
```python
import zipfile, base64, re
z = zipfile.ZipFile('doc.odt')
meta = z.read('meta.xml').decode()
m = re.search(r'meta:user-defined[^>]*>([^<]+)<', meta)
print(base64.b64decode(m.group(1)).decode())
```

Вывод:

```
nto{odf_meta_field}
```

## Шаг 5: инструменты
- `unzip -l doc.odt`, `unzip -p doc.odt meta.xml`.
- `odfpy` / `python3 -c 'from odf.opendocument import load'` — программный разбор.
- `libreoffice --headless --convert-to` — нормализация (перезапись файла убивает
  лишние поля).

## Полный разбор ODF

ODF (ODT/ODS/ODP) — ZIP-контейнер. Структура: `mimetype` (первый, несжатый), `META-INF/manifest.xml`, `content.xml` (содержимое), `styles.xml`, `meta.xml` (метаданные), `settings.xml`, `Pictures/`, `Thumbnails/`.

```bash
unzip -l doc.odt
unzip -o doc.odt -d odt/
cat odt/meta.xml | python3 -m xml.dom.minidom | head -40
```

Каналы сокрытия: первый — **пользовательские поля в `meta.xml`** (`<meta:user-defined>`) — прямое место для данных. Второй — **файлы вне манифеста**: как в EPUB, файл в архиве, не упомянутый в `META-INF/manifest.xml`, игнорируется. Третий — **комментарии** в `content.xml`. Четвёртый — **невидимый текст** (белый, `font-size:0`, скрытый слой). Пятый — **`Thumbnails/`**: превью может отличаться от содержимого (или содержать данные).

## Извлечение и инструменты

```bash
unzip -l doc.odt | grep -viE "content|styles|meta|settings|manifest|mimetype"
grep -rniE "nto\{|flag|secret" odt/ | head
grep -n "user-defined" odt/meta.xml
```

Сравни список файлов с манифестом (`META-INF/manifest.xml`): расхождение — канал. Проверь `content.xml` на комментарии и невидимые элементы. Инструменты: `unzip`, `zipinfo -v` (комментарии архива), `exiftool`, `python3` + XML-парсер, `binwalk` (вложенность).

ODF близок к OOXML (DOCX/XLSX/PPTX) по принципу: ZIP + XML + манифест. Освоив один, разбираешь остальные. Ключевое отличие — свои имена файлов и пространства имён XML, но логика «файлы вне манифеста и метаданные» одна и та же.

## Расширенный разбор: ODF как контейнер

ODF — это не «документ», а архив из нескольких XML-файлов. Разбирать его нужно послойно. Первый слой — ZIP: `unzip -l doc.odt` покажет список файлов, а `zipinfo -v doc.odt` — комментарии и порядок. Второй слой — `mimetype`: он должен быть первым и несжатым; нарушение порядка — признак пересборки.

Третий слой — `META-INF/manifest.xml`: список всех файлов с их типами. Любой файл в архиве, не упомянутый здесь, — канал. Сравни списки программно, не глазами.

Четвёртый слой — `content.xml`: основное содержимое. Тут ищут невидимый текст (белый цвет, нулевой кегль, скрытые абзацы), комментарии XML, нестандартные элементы. Пятый слой — `meta.xml`: метаданные, включая пользовательские поля `<meta:user-defined>`, куда можно записать что угодно.

Шестой слой — `styles.xml`/`settings.xml`: стили могут скрывать текст (например, `fo:display="none"`), а настройки — содержать нестандартные значения. Седьмой слой — `Thumbnails/thumbnail.png`: превью может отличаться от содержимого или нести данные. Восьмой — `Pictures/`: встроенные изображения проверяют на стего-каналы отдельно.

```bash
unzip -l doc.odt
python3 - <<PY
import re, os
man = open("odt/META-INF/manifest.xml").read()
listed = set(re.findall(r'full-path="([^"]+)"', man))
for root,_,files in os.walk("odt"):
    for f in files:
        p = os.path.relpath(os.path.join(root,f),"odt")
        if p not in listed and p != "mimetype":
            print("unlisted:", p)
PY
```

Такой послойный разбор универсален для всех ZIP+XML-документов: ODF, OOXML, EPUB. Отличаются имена файлов и пространства имён, но принцип один: структура описана манифестом, а всё, что вне него, — канал.

## Практические сценарии и итог

Сценарий первый: флаг в `<meta:user-defined>` в `meta.xml`. Открываешь файл, находишь пользовательское поле — читаешь значение. Это самый простой канал, и его часто пропускают, потому что смотрят только на содержимое документа.

Сценарий второй: лишний файл в архиве. `flag.txt` лежит рядом с `content.xml`, но не упомянут в манифесте. `unzip -l` его покажет, и он читается напрямую. Третий: текст белым цветом на белом фоне — виден только в XML (`fo:color="#FFFFFF"`). Четвёртый: скрытый абзац (`fo:display="none"`). Пятый: данные в комментариях `<!-- ... -->`.

Шестой: нестандартный `mimetype` (например, с лишним содержимым) или его отсутствие. Седьмой: вложенный архив внутри `Pictures/`. Восьмой: превью, не соответствующее документу.

Инструменты: `unzip`, `zipinfo -v`, `exiftool`, `python3` (XML-парсер и скрипт сравнения), `binwalk` (вложенность), `libreoffice --headless --convert-to txt` (но конвертация теряет каналы — не полагайся на неё).

Итог: ODF — удобный контейнер для сокрытия, потому что структура сложная, а просмотрщики показывают только отрендеренный документ. Правильный подход — работать с архивом напрямую, сверять манифест с содержимым и проверять метаданные.

## Дополнительные приёмы разбора ODF

Есть ещё несколько мест в ODF, которые стоит проверить. Первое — `settings.xml`: настройки просмотра могут содержать нестандартные значения, а также данные о последнем открытом файле. Второе — `styles.xml`: определения стилей, среди которых встречаются скрывающие текст (например, `fo:display="none"` или прозрачный цвет). Третье — `content.xml` может содержать несколько `<office:body>` или дублирующиеся элементы.

Четвёртое — связи между частями документа (`<office:annotation>` — комментарии-примечания, которые видны в интерфейсе, но не в тексте). Пятое — встроенные объекты (`<draw:object>`), которые могут содержать вложенные документы. Шестое — `Manifest` может указывать на файлы с нестандартными типами.

Седьмое — числа и даты в `meta.xml` (`meta:creation-date`, `meta:editing-cycles`) могут нести данные через нестандартные значения. Восьмое — `Thumbnails/` может содержать несколько превью, и «лишние» — канал.

Практический подход — пройтись по всем XML-файлам архива и поискать: нестандартные атрибуты, комментарии, невидимый текст, пользовательские поля, ссылки на несуществующие элементы. Скрипт, который рекурсивно парсит XML и печатает все комментарии и значения пользовательских полей, экономит время.

Итог: ODF — сложный контейнер с множеством каналов, поэтому его всегда разбирают архивом, а не через офисный редактор. Редактор покажет только отрендеренный документ и скроет все каналы.

## Резюме по ODF

ODF — ZIP + XML + манифест. Каналы: пользовательские поля в `meta.xml`, файлы вне манифеста, комментарии, невидимый текст, `Thumbnails/`, встроенные объекты. Инструменты: `unzip`, `zipinfo -v`, `exiftool`, `python3`, `binwalk`. Разбирай архивом, а не редактором, и сверяй манифест с содержимым.

## Дополнительные примеры

Сценарий с невидимым текстом: в `content.xml` ищем `fo:color="#FFFFFF"` (белый текст) или `fo:font-size="2pt"` (нечитаемо мелкий). Сценарий с встроенным объектом: `Pictures/` или `Object N/` может содержать вложенный документ/архив, который находят `binwalk`. Сценарий с лишним файлом: сравнение списка архива с `manifest.xml`.

## Финальные замечания по ODF

Помни главное: ODF — это архив, а не документ. Любой офисный редактор показывает только отрендеренный результат и скрывает все каналы (файлы вне манифеста, пользовательские поля, невидимый текст, комментарии). Поэтому единственный надёжный путь — распаковать `.odt` как ZIP и пройтись по XML. Начни с `unzip -l`, затем сравни манифест с содержимым, затем проверь `meta.xml` и `content.xml`. Этого достаточно для большинства задач; сложные случаи требуют разбора встроенных объектов и превью.

## Ещё раз о порядке разбора

Порядок разбора ODF: `unzip -l` → сравнение с `META-INF/manifest.xml` → `meta.xml` (пользовательские поля) → `content.xml` (невидимый текст, комментарии) → `styles.xml`/`settings.xml` → `Thumbnails/` → вложенные объекты. Если найти файл вне манифеста, читай его напрямую. Если ничего — проверь невидимые Unicode-символы в тексте и вложенность через `binwalk`.

## Итог

ODF — ZIP + XML + манифест. Каналы: файлы вне манифеста, пользовательские поля в `meta.xml`, комментарии, невидимый текст, встроенные объекты, `Thumbnails/`. Разбирай архивом, а не редактором, и сверяй манифест с содержимым.

## Что мы теперь знаем
- ODF — ZIP с `mimetype` и XML-файлами (`content`, `styles`, `meta`, `settings`).
- `meta:user-defined` — штатное поле для произвольных данных.
- Лишние файлы и встроенные миниатюры — дополнительные каналы.
