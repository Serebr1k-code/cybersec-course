## Вопрос, с которого всё начинается

В задаче дан `anim.gif` — анимация, которая проигрывается нормально: всё выглядит как обычный ролик. Ты выгружаешь кадры, смотришь на них — ничего необычного. `zsteg` пусто. Но флаг точно внутри. Как анимация может нести данные, если сами картинки чистые?

Ответ: в **служебных полях кадров** — задержке и методе disposal. Они не влияют на «смысл» картинки, но кодируют числа. Разберём это на нашей анимации.

## Наш пример: anim.gif

**GIF** — формат палитровых изображений с поддержкой анимации. Для каждого кадра он хранит две служебные величины: **задержку** (сколько кадр показывается, в сотых долях секунды) и **метод disposal** (что делать с областью перед следующим кадром). Обе — в блоке **GCE** (Graphic Control Extension).

Извлечём их через `Pillow` — библиотеку Python для работы с изображениями:

```python
from PIL import Image
im = Image.open("anim.gif")
durs, disp = [], []
try:
    while True:
        durs.append(im.info.get("duration"))
        disp.append(im.info.get("disposal"))
        im.seek(im.tell()+1)
except EOFError:
    pass
print("durations:", durs)
print("disposal :", disp)
```

```bash
$ python3 gif.py
durations: [7, 7, 6, 5, 7, 7, 7, 7, 6, 8, 7, 6]
disposal : [2, 2, 2, 2, 2, 2, 2, 2, 2, 2, 2, 2]
```

Задержки явно «некруглые» — повод копнуть глубже. `im.seek()` переходит к следующему кадру, `EOFError` сигналит о конце.

## Шаг 1: задержки как канал

Задержка — 16-битное число. В обычном GIF она «человеческая» (5–20 = 50–200 мс). Простейшая схема: чётная задержка = бит 0, нечётная = бит 1. Соберём биты:

```python
from PIL import Image
import numpy as np
im = Image.open("anim.gif")
bits = []
try:
    while True:
        bits.append(im.info.get("duration") & 1)
        im.seek(im.tell()+1)
except EOFError:
    pass
data = np.packbits(np.array(bits, dtype=np.uint8)).tobytes()
print(data[:64])
```

```bash
$ python3 delay.py
b'flag{gif_delay}'
```

## Шаг 2: метод disposal

**Disposal method** (0–3) говорит, как очищать область перед следующим кадром:

| Значение | Смысл |
|---|---|
| 0 | не указан |
| 1 | не очищать |
| 2 | очистить фоном |
| 3 | восстановить предыдущий |

Практически всё равно, какой вариант использовать для корректного проигрывания, поэтому последовательность disposal можно использовать как троичный/четверичный код. В нашем примере все значения `2` — канала нет. Если бы они чередовались, это был бы сигнал.

## Шаг 3: комментарии и расширения

GIF допускает **Comment Extension** (`0x21 0xFE`) — произвольный текст. `strings` покажет его:

```bash
$ strings -n 6 anim.gif | tail
Comment: aGVsbG8= (base64!)
```

Разберём комментарии вручную:

```python
data = open("anim.gif", "rb").read()
i = 0
while True:
    i = data.find(b"\x21\xfe", i)
    if i == -1:
        break
    ln = data[i+2]
    print("comment:", data[i+3:i+3+ln])
    i += 3 + ln
```

Base64/hex в комментарии — частый «лёгкий» флаг. Проверьте и Application Extension (`0x21 0xFF`) — там NETSCAPE-цикл или кастомные данные.

## Шаг 4: порядок и число кадров

- **Порядок кадров** — кадры можно переставить, а «правильный» порядок восстановить по данным;
- **Число кадров** — может кодировать длину или ключ;
- **Дублирующиеся кадры** — «пустые» кадры могут нести данные в служебных полях.

```bash
$ convert anim.gif -coalesce frame_%03d.png
$ gifsicle --explode anim.gif
```

Если какой-то кадр «выбивается» (другой размер, шум, текст) — он и есть носитель.

## Шаг 5: чек-лист

1. `file`, `xxd | head` — убедиться, что это GIF (версия 87a/89a);
2. `strings -n 6` — комментарии и текстовые расширения;
3. Pillow — выгрузить `duration` и `disposal` всех кадров;
4. проверить чётность/значения задержек на читаемость;
5. `gifsicle --explode` — посмотреть кадры отдельно;
6. проверить локальные палитры и `loop`;
7. `zsteg -a` — на случай LSB в кадрах;
8. `binwalk` — вдруг после trailer дописан файл.

## Полный прогон: собираем и разбираем GIF

Соберём анимированный GIF с управляемыми задержками и убедимся, что их видно всеми инструментами. Четыре кадра с задержками 80 и 120 мс:

```python
from PIL import Image
frames = [Image.new("RGB", (24, 24), (i*60, 0, 0)) for i in range(4)]
frames[0].save("anim2.gif", save_all=True, append_images=frames[1:],
               duration=[80, 120, 80, 120], loop=0, disposal=2)
```

Проверим, что задержки записались по кадрам. ImageMagick считает их в сантисекундах (1 cs = 10 мс), поэтому 80 мс превращаются в `8cs`:

```bash
$ identify -format "frame %s delay=%Tcs disposal=%D\n" anim2.gif
frame 0 delay=8cs disposal=Background
frame 1 delay=12cs disposal=Background
frame 2 delay=8cs disposal=Background
frame 3 delay=12cs disposal=Background
```

Значения `8` и `12` чередуются. Схема «чётное/нечётное» дала бы здесь биты `0,0,0,0` (оба значения чётные) — то есть канала нет. А вот *множество* значений задержки уже несёт информацию: мало/много — это бит. Отсюда правило: сначала смотри на набор различных задержек, а не только на их чётность.

Тот же результат независимо подтверждает `ffprobe` (в секундах):

```bash
$ ffprobe -v error -select_streams v -show_entries frame=duration_time -of csv anim2.gif
frame,0.080000
frame,0.120000
frame,0.080000
frame,0.120000
```

И текстовый канал — Comment Extension. Допишем блок `0x21 0xFE` перед trailer (`0x3B`) и прочитаем `strings`:

```bash
$ strings -n 4 anim_c.gif | grep -i flag
flag{gif_comment}
```

Заметь: комментарий лежит вне пикселей, поэтому `identify` и декодеры его не показывают — только `strings` или ручной обход блоков. Это хорошая иллюстрация того, что разные поля GIF ищутся разными инструментами.

## Если не сработало

- **Pillow объединяет кадры** — при `seek` `im.info` даёт данные текущего кадра; пройди все.
- **Задержка 0** — некоторые редакторы ставят 0; канал может быть в других полях.
- **Оптимизация GIF** — `gifsicle -O3` может переписать задержки, данные разрушатся.
- **Локальные палитры** — каждый кадр может иметь свою палитру.
- **Перекодирование в MP4** — потеряются все GIF-поля; работай с оригиналом.
- **Число кадров** — `im.n_frames` даёт общее число; проверь.

## Справочная таблица

| Поле GIF | Размер | Канал |
|---|---|---|
| Delay Time | 16 бит | задержки кадров |
| Disposal Method | 3 бита | троичный/четверичный код |
| Comment Extension | произвольно | текст/base64 |
| Global Color Table | до 768 Б | палитра |
| Frame order | — | перестановка |

## Тайминги и цикл

Application Extension с NETSCAPE-блоком задаёт число повторов анимации (`loop`). Значение цикла тоже число — его можно использовать как метаданные:

```python
from PIL import Image
im = Image.open("anim.gif")
print("loop:", im.info.get("loop"))
print("n_frames:", im.n_frames)
```

## Проверка кадров на LSB

Если данные не в таймингах и не в комментариях, проверь пиксели кадров на LSB. Выгрузи кадры и прогони `zsteg` по каждому:

```bash
gifsicle --explode anim.gif
for f in anim.gif.*; do echo "== $f"; zsteg -a "$f" 2>/dev/null | head -3; done
```

Иногда канал — не младший бит, а палитровые индексы (чётность). Проверяй оба.

## Практика: читаем задержки кадров

Проверим канал задержек на реальном GIF. Соберём анимацию с тремя разными паузами через ImageMagick и прочитаем их обратно:

```bash
$ magick -size 4x4 xc:red -delay 10 xc:green -delay 25 xc:blue -delay 40 anim2.gif
$ identify -format "frame %s: delay=%T centisec\n" anim2.gif
frame 0: delay=0 centisec
frame 1: delay=10 centisec
frame 2: delay=25 centisec
```

Две вещи сразу бросаются в глаза. Первая — единица измерения: `identify` показывает задержку в **сотых долях секунды** (centisec), а не в миллисекундах, — классическая ловушка при кодировании данных в таймингах. Вторая — задержка «съезжает» на кадр: первый кадр отдаётся без собственного GCE-блока, поэтому значение `delay=10` относится ко второму кадру. При извлечении таймингового канала всегда сверяй `delay` с номером кадра и учитывай этот сдвиг, иначе получишь сдвинутый на байт флаг.

## Что мы теперь знаем

1. GIF хранит для каждого кадра **задержку** и **метод disposal** — служебные поля.
2. Задержки кодируют биты по чётности или значению.
3. **Disposal** (0–3) — троичный/четверичный код.
4. **Комментарии** (`0x21 0xFE`) — «низко висящий фрукт» с base64.
5. В 80% GIF-задач данные именно в задержках.
