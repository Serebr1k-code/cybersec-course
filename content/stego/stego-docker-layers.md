## Вопрос, с которого всё начинается
Docker-образ — это набор слоёв. Каждый слой — tar-архив с изменениями файловой
системы. Ты запускаешь контейнер, видишь приложение. Но в образе могут лежать
файлы, которых нет в работающем контейнере: удалённые (whiteouts), лишние, или
данные в метаданных слоя. Задача: найти их.

## Наш пример
Возьмём `layer.tar.gz` — один слой образа. Разберём его как tar и найдём
необычный файл.

## Шаг 1: образ = манифест + слои
Современный образ (`docker save` / OCI) — это tar-архив, содержащий:
- `manifest.json` — список слоёв и конфига;
- `config.json` — метаданные (env, cmd, labels, история);
- `layer.tar` — собственно слои (часто сжатые gzip).

Каждый слой — самостоятельный tar с файлами. Слои накладываются друг на друга.

## Шаг 2: whiteouts — «удалённые» файлы
Docker удаляет файл из слоя, создавая **whiteout**: пустой файл
`.wh.<имя>`. Сам файл при этом может остаться в предыдущем слое. Данные,
«удалённые» таким образом, никуда не исчезают — они в нижних слоях.

## Шаг 3: где прячут данные в слоях
- **Лишние файлы.** Любой файл в слое, не нужный приложению, — носитель.
- **Мусор в нижних слоях.** Файл, «удалённый» в следующем слое, всё ещё читается
  из предыдущего.
- **`config.json`.** Labels, `created_by` (история сборки) — произвольный текст.
- **Метаданные tar.** Расширенные заголовки (pax) и padding блоков.
- **Неиспользуемые blob в registry.** Слои, на которые не ссылается манифест.

## Шаг 4: извлечение вручную
```python
import tarfile
t = tarfile.open('layer.tar.gz', 'r:gz')
for m in t.getmembers():
    if m.name.endswith('secret'):
        print(t.extractfile(m).read().decode())
```

Вывод:

```
nto{docker_layer_extra_file}
```

## Шаг 5: инструменты
- `docker save img -o img.tar` + `tar tf img.tar`.
- `dive img` — визуальный анализ слоёв и мусора.
- `crane`/`skopeo` — работа с registry и слоями.
- `tar tvf layer.tar` — список файлов.

## Извлечение слоёв вручную: полный разбор

Разберём образ `app.tar`. Сначала манифест: `tar -xf app.tar` распакует в каталог, где будут `manifest.json`, `repositories` и папки слоёв (или один `layer.tar` для старого формата). Манифест описывает порядок слоёв и их digest-и.

```bash
mkdir img && tar -xf app.tar -C img
cat img/manifest.json | python3 -m json.tool | head
for l in img/*/layer.tar; do echo "== $l"; tar -tvf "$l" | head; done
```

Каждый `layer.tar` — это дельта: он содержит добавленные/изменённые файлы и **whiteouts** (файлы вида `.wh.<name>`, означающие удаление). Чтобы восстановить финальную ФС, применяй слои по порядку из манифеста, обрабатывая whiteouts как удаление. Но для стего интереснее обратное: whiteouts и старые версии файлов **остаются** в промежуточных слоях, даже если в финальном их «нет». Именно там и прячут данные.

## Whiteouts и «удалённые» файлы на практике

Whiteout `.wh.secret.txt` означает: в этом слое файл `secret.txt` удалён из более раннего слоя. В финальном контейнере файла нет, но **в предыдущем слое он есть**. Поэтому при форензике образа сначала перечисляют whiteouts, а затем ищут в более ранних слоях файлы с этими именами.

```bash
for l in img/*/layer.tar; do echo "== $l"; tar -tf "$l" | grep -E "\.wh\." ; done
# затем найти сам файл в более раннем слое
tar -tf img/<early-layer>/layer.tar | grep secret.txt
```

Обратный трюк — «hidden in whiteout»: атакующий добавляет файл, а затем в следующем слое удаляет его whiteout-ом; в финальном образе файла нет, но он лежит в промежуточном слое и извлекается тривиально. Это распространённый приём сокрытия данных в образах.

## Метаданные и история образа

Помимо слоёв, образ несёт метаданные: `manifest.json` (порядок и digest), `config` JSON (env, cmd, entrypoint, история сборки), `repositories`. В `config` часто есть `history` с командами сборки — по ним видно, как создавался образ, и иногда там остаются секреты (например, `RUN export TOKEN=...`). Отдельно — env-переменные и метки (labels), куда тоже прячут данные.

```bash
cat img/manifest.json | jq .
cat img/<config>.json | jq ".history[]?.created_by" | head
cat img/<config>.json | jq ".config.Env"
```

Инструменты для глубокого разбора: `dive` (интерактивно показывает слои и изменения), `docker save` + ручной `tar`, `skopeo` (скачивание без демона), `umoci` (работа с OCI-образами). Для стего важно помнить: данные могут быть в любом слое, а не только в финальном, поэтому образ всегда разбирают послойно.

## Расширенный разбор: практика форензики образа

Полный маршрут форензики Docker-образа. Первое — получить образ: `docker save app -o app.tar` или `skopeo copy docker://registry/app oci:app:latest`. Второе — распаковать архив и прочитать `manifest.json` (порядок слоёв) и `config` (история, env, labels). Третье — перечислить содержимое каждого слоя по порядку, чтобы понять, что добавлялось и удалялось.

Четвёртое — найти whiteouts: `.wh.<name>` (удаление файла) и `.wh..wh..opq` (непрозрачный каталог — «удалить всё, что было раньше»). Каждый whiteout указывает на файл, который существовал в более раннем слое, — это готовый маршрут к «скрытым» данным. Пятое — извлечь эти файлы из ранних слоёв и посмотреть содержимое.

Шестое — проверить метаданные: `config.history` содержит команды сборки, среди которых иногда остаются секреты (`ENV TOKEN=...`, `RUN ... --password ...`). Седьмое — env-переменные и labels: туда тоже прячут данные. Восьмое — сравнить слои между собой: файл, изменённый в нескольких слоях, может содержать данные в промежуточных версиях.

Инструменты: `dive` (интерактивный просмотр слоёв и их diff), `umoci` (работа с OCI-образами), `skopeo`, `tar`, `jq`. Для защиты от таких находок образы собирают многостадийно (multi-stage), чтобы секреты и промежуточные файлы не попадали в финальный образ; но даже тогда промежуточные слои могут утекать, если они публикуются.

## Пошаговое упражнение с образом

Дано: `app.tar` (результат `docker save`). Шаг первый — распаковать и прочитать манифест. Шаг второй — перечислить слои и найти whiteouts. Шаг третий — извлечь файлы, скрытые whiteout-ами, из ранних слоёв. Шаг четвёртый — проверить config (history, env, labels).

```bash
mkdir img && tar -xf app.tar -C img
cat img/manifest.json | jq .
for l in img/*/layer.tar; do echo "== $l"; tar -tf "$l" | grep -E "\.wh\." ; done
cat img/*.json | jq ".history[]?.created_by" | head
```

Пятый шаг — сравнить слои: если один и тот же файл менялся несколько раз, промежуточные версии содержат данные. Шестой — проверить env и labels на секреты.

## Защита: как не утекать через образы

Основная мера — многостадийная сборка (multi-stage build): в финальный образ попадают только артефакты, а промежуточные слои с секретами и исходниками отбрасываются. Второе — не писать секреты в `ENV`/`RUN` (они остаются в истории config). Третье — использовать build secrets (BuildKit `--secret`), которые не сохраняются в слоях. Четвёртое — `.dockerignore`, чтобы не копировать лишнее. Пятое — сканировать образ (`dive`, `trivy`) на секреты и лишние файлы перед публикацией.

## Что мы теперь знаем
- Docker-образ — tar из манифеста, конфига и слоёв-тар.
- Whiteout-файлы «удаляют» файл, не стирая данные в нижних слоях.
- Лишние файлы и метаданные слоя — каналы.
- `dive` — удобный инструмент анализа слоёв.
