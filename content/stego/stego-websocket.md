## Вопрос, с которого всё начинается

Тебе дали `ws.bin` — один WebSocket-фрейм. WebSocket — это протокол «постоянного
соединения»: чаты, тикеры, игры. Клиент и сервер шлют друг другу фреймы. Где тут
спрятать сообщение? Оказывается, payload фрейма может быть любым, а маскирование —
это не шифрование, а просто XOR. Разберём фрейм.

## Наш пример: файл ws.bin

```bash
xxd ws.bin
```

```text
00000000: 8193 1234 5678 7a40 3903 6507 340b 2257  ...4.xz@9.e.4."W
00000010: 3d4b 666b 3014 2653 2b                   =Kfk0.&S+
```

Видим `81` — первый байт: FIN=1, opcode=1 (text). Второй байт `93`: MASK=1, длина =
0x13 = 19. Дальше 4 байта маски `12 34 56 78` и 19 байт замаскированного payload.
Снимем маску.

## Шаг 1: структура WebSocket-фрейма

Фрейм начинается с двух байт:

```
[ FIN(1) RSV(3) opcode(4) ][ MASK(1) длина(7) ]
```

- **FIN** — последний ли фрейм сообщения.
- **opcode** — `1` text, `2` binary, `8` close, `9` ping, `10` pong.
- **MASK** — бит маски (клиент обязан маскировать).
- **длина** — если 0..125, это и есть длина; если 126 — следующие 2 байта; если 127 —
  следующие 8 байт.

Если MASK=1, после длины идут **4 байта маски**, затем payload, замаскированный XOR
с этой маской по кругу.

## Шаг 2: маскирование — не шифрование

Маска — это просто XOR каждого байта payload с соответствующим байтом 4-байтной
маски (циклически). Снять её тривиально, зная маску — а маска лежит **открыто** в
самом фрейме. То есть WebSocket-маскирование не защищает данные, а лишь «перемешивает»
их, чтобы прокси не путали фреймы.

## Шаг 3: снимаем маску вручную

```bash
python3 - <<'PY'
d = open('ws.bin','rb').read()
mask = d[2:6]
ln = d[1] & 0x7f
payload = d[6:6+ln]
out = bytes(payload[i] ^ mask[i % 4] for i in range(len(payload)))
print(out.decode('latin-1'))
PY
```

```text
nto{w3bs0ck3t_fl4g}
```

## Шаг 4: где ещё прячут в WebSocket

- **Расширенная длина** (126/127) — старшие байты длины можно модулировать.
- **opcode** — «лишние» ping/pong-фреймы как сигнал.
- **Порядок фреймов** — перестановочный канал.
- **RSV-биты** — зарезервированы, но если расширение их использует, можно прятать.
- **HTTP-заголовки рукопожатия** — `Sec-WebSocket-Protocol`, cookies.

## Шаг 5: инструменты

```bash
tshark -r capture.pcap -Y 'websocket' -V
wireshark                         # декодирует ws/wss
python3 -c "import websocket"     # клиент
```

Wireshark показывает фреймы и снимает маску автоматически. Но в CTF обычно дают
«сырой» фрейм, и снять маску надо вручную.

## Шаг 6: почему WebSocket удобен для сокрытия

WebSocket — двунаправленный и «долгоживущий»: после рукопожатия фреймы летят туда-
сюда без HTTP-оверхеда. Каждый фрейм может нести произвольный payload, и никто не
проверяет его содержимое. Для стеганографии это означает: можно добавлять «лишние»
фреймы или прятать данные в неиспользуемых полях.

## Шаг 7: частые ошибки

Первая — не заметить MASK-бит: если он 0 (сервер → клиент), маски нет, и payload
читается напрямую. Вторая — неверно прочитать длину: 126 и 127 меняют формат. Третья —
забыть, что маска циклическая (i % 4). Четвёртая — перепутать opcode: текстовый
payload и бинарный обрабатываются одинаково при извлечении.

## Практика: разбор рукопожатия WebSocket

WebSocket начинается как HTTP-запрос с заголовком `Upgrade: websocket`. Сервер
отвечает `101 Switching Protocols`, и дальше идут фреймы. В рукопожатии есть
`Sec-WebSocket-Key` (base64 от 16 случайных байт) и `Sec-WebSocket-Protocol` (список
подпротоколов). Оба — потенциальные носители: ключ можно сгенерировать с «закладкой»
(но сервер его проверяет, поэтому это редко), а список протоколов — свободное поле.

```bash
printf 'GET /chat HTTP/1.1\r\nHost: lab\r\nUpgrade: websocket\r\nConnection: Upgrade\r\nSec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==\r\nSec-WebSocket-Version: 13\r\n\r\n' | nc lab 80
```

После рукопожатия сервер и клиент обмениваются фреймами. Клиентские фреймы всегда
маскированы, серверные — нет.

## Как отличить закладку от штатного трафика

WebSocket-фреймы несут данные приложения (JSON, protobuf, текст). Признаки закладки:

- **«Лишние» ping/pong-фреймы** — opcode 9/10, которые приложение не использует.
- **Текстовый payload в бинарном канале** (или наоборот).
- **Фреймы нулевой длины** или с необычной длиной.
- **RSV-биты установлены** без согласованного расширения (по стандарту запрещено).

Практический приём: собери все payload'ы одного соединения и поищи среди них
аномальный. В CTF обычно дают один фрейм, и он весь — сообщение.

## Итоговая стратегия для WebSocket

Определи, есть ли маска (MASK-бит); сними маску XOR; прочитай payload; проверь
opcode и RSV; посмотри рукопожатие на `Sec-WebSocket-Protocol`. Для pcap используй
`tshark -Y websocket`. И помни: маскирование — не шифрование, а лишь XOR с открытой
маской; никакой «защиты» оно не даёт.

## Практика: фрагментация сообщений

Одно WebSocket-сообщение может быть разбито на несколько фреймов: первый имеет
opcode 1 или 2, остальные — opcode 0 (continuation), а последний помечен FIN=1.
Это разрешает передавать большие сообщения и создаёт дополнительный канал: порядок
и размер фрагментов можно модулировать.

```bash
python3 - <<'PY'
d = open('ws.bin','rb').read()
i = 0
while i + 2 <= len(d):
    b0 = d[i]; b1 = d[i+1]
    fin = b0 >> 7; op = b0 & 0x0f; masked = b1 >> 7; ln = b1 & 0x7f
    p = i + 2
    if ln == 126:
        ln = int.from_bytes(d[p:p+2],'big'); p += 2
    elif ln == 127:
        ln = int.from_bytes(d[p:p+8],'big'); p += 8
    print('fin', fin, 'opcode', op, 'masked', masked, 'len', ln)
    if masked:
        p += 4
    p += ln
    i = p
PY
```

Такой парсер обходит все фреймы в дампе и показывает их параметры — полезно, когда
закладка не в payload, а в структуре (размеры, opcode, FIN).

## Как отличить закладку от реального приложения

Реальный WebSocket-трафик зависит от приложения: чат шлёт JSON-строки, тикеры —
короткие бинарные пакеты. Признаки закладки:

- **Payload не соответствует ожидаемому формату** (текст там, где ждут бинарный).
- **Фреймы с opcode ping/pong**, которых приложение не шлёт.
- **RSV-биты**, установленные без расширения.
- **Фрагменты «не по делу»** — сообщение разбито без причины.

Практический приём: собери payload'ы по opcode и посмотри, нет ли «выпадающего».
В CTF обычно дают один фрейм, и он весь — сообщение; в реальном дампе ищи аномалию.

## Почему маскирование не мешает анализу

Маскирование в WebSocket придумано, чтобы промежуточные прокси не принимали данные
фрейма за начало HTTP-ответа (cache poisoning). Это не защита, а «разметка». Маска
передаётся в открытом виде, поэтому снять её может кто угодно. Для стеганографии это
означает: WebSocket-фрейм — это просто контейнер с XOR-обфускацией, и разбор
тривиален. Не путай маскирование с шифрованием `wss` — вот оно уже настоящая защита
(TLS), но и там заголовки рукопожатия видны.

## Чек-лист по WebSocket-дампу

1. Определи границы фреймов (`b0`, `b1`, расширенная длина, маска, payload`).
2. Если MASK=1 — сними маску XOR по кругу.
3. Прочитай payload; проверь opcode и RSV.
4. Разбери рукопожатие (если есть) на `Sec-WebSocket-Protocol` и `Sec-WebSocket-Key`.
5. Ищи «лишние» ping/pong и фрагментацию без причины.
6. Для pcap используй `tshark -Y websocket`.

Помни: маскирование — не защита; payload читается сразу после XOR. Единственное, что
может «спрятать» данные — это `wss` (TLS), но и там структура фреймов частично
наблюдаема.

## Про `wss` и шифрование

Когда WebSocket работает поверх TLS (`wss://`), весь обмен фреймами шифруется. Снаружи видны только TLS-записи, а внутри — уже знакомые нам фреймы, которые расшифровываются на концах. Для стеганографии это означает: если у тебя есть ключи (например, из CTF-задачи или из `SSLKEYLOGFILE`), можно расшифровать трафик и разобрать фреймы как обычно. Если ключей нет — остаются только размеры и тайминги записей, что тоже канал, но менее удобный.

## Заключительная мысль

WebSocket-стеганография показывает важный принцип: даже протоколы, которые «маскируют» данные, маскируют их лишь формально. Маска открыта, формат документирован, и разбор занимает минуты. Настоящая защита — только шифрование, но и оно оставляет открытыми заголовки и структуру. Поэтому любой сетевой протокол стоит рассматривать как потенциальный носитель, а не как «чёрный ящик».

## Ещё один канал: размер фрейма

Помимо содержимого, информативен размер фрейма. Приложение обычно шлёт фреймы предсказуемой длины (например, JSON фиксированной структуры). Если среди них попадаются фреймы с «нестандартной» длиной, это может быть канал: получатель знает, что такие фреймы — служебные. В сочетании с тайминговым каналом (интервалы между фреймами) это даёт устойчивый скрытый канал, неотличимый от обычного обмена для внешнего наблюдателя.

Размер фрейма — такой же полноценный носитель, как и его содержимое, и его стоит проверять наряду с payload.

## Что мы теперь знаем

- WebSocket-фрейм: `FIN/opcode + MASK/длина + [маска] + payload`.
- Маскирование — XOR с 4-байтной маской, не шифрование.
- Расширенная длина (126/127), opcode, RSV — дополнительные каналы.
- Инструменты: Wireshark, `tshark`.
