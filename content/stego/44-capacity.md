## Вопрос, с которого всё начинается

Ты анализируешь инцидент: с рабочей станции утёк секретный архив на 250 КБ, и единственный подозрительный файл — `suspect.png` размером 1024×768. Можно ли вообще спрятать 250 КБ в такой картинке? Или надо искать другой носитель?

Чтобы ответить, не нужно извлекать данные — нужно **посчитать ёмкость** канала. Это быстрый способ отсечь невозможные варианты и понять, где искать. Разберём на этом примере.

## Наш пример: suspect.png 1024×768

Любая стегосистема балансирует **три свойства**: **ёмкость** (сколько данных влезает), **незаметность** (насколько изменения не видны) и **робастность** (устойчивость к сжатию и обрезке). Улучшение одного обычно ухудшает другое.

| Свойство | Что означает | Цена |
|---|---|---|
| Ёмкость | объём скрываемых данных | больше ёмкость → заметнее |
| Незаметность | невидимость изменений | выше незаметность → меньше ёмкость |
| Робастность | устойчивость к сжатию/обрезке | выше робастность → меньше ёмкость |

## Шаг 1: считаем ёмкость изображения

**LSB** (Least Significant Bit, младший бит) прячет один бит в самом незаметном бите каждого цветового канала. У RGB-картинки 3 канала на пиксель, значит на один пиксель приходится 3 бита.

Формула: `W × H × каналы / 8` байт (при 1 LSB на канал).

```python
from PIL import Image
im = Image.open('suspect.png')
w, h = im.size
ch = len(im.getbands())          # 3 = RGB, 4 = RGBA
print('channels:', ch)
print('1 LSB/ch:', w*h*ch//8, 'bytes')
```

```bash
$ python3 capacity.py
channels: 3
1 LSB/ch: 294912 bytes
```

`294912` байт ≈ 288 КБ. Наш секрет — 250 КБ, значит **влезает с запасом**. Вывод: данные, скорее всего, в LSB RGB, а не в метаданных (там ёмкость — сотни байт). Это сужает поиск.

## Шаг 2: ёмкость аудио и видео

Для **аудио PCM** (несжатый звук) формула — `частота × длительность × каналы / 8`. Для 44100 Гц, моно, 60 секунд при 1 LSB:

```bash
$ python3 -c "print(44100*60*1//8, 'bytes')"
330750 bytes
```

Для видео ёмкость умножается на число кадров: 300 кадров по 288 КБ — это уже ~86 МБ. Поэтому большие секреты прячут именно в видео и аудио.

| Носитель | Формула (1 бит/элемент) | Пример |
|---|---|---|
| Изображение RGB | W×H×3/8 | 1024×768 → 288 КБ |
| Изображение RGBA | W×H×4/8 | 1024×768 → 384 КБ |
| 8-бит палитра | W×H/8 | 1024×768 → 96 КБ |
| Аудио PCM | samples×channels/8 | 44100×60 → 330 КБ |
| Видео | frames × W×H×3/8 | 300 кадров → ~86 МБ |

## Шаг 3: незаметность — сколько LSB безопасно

Ёмкость не бесплатна: чем больше бит на пиксель, тем сильнее искажение. Меру искажения измеряют **PSNR** (Peak Signal-to-Noise Ratio) — чем выше, тем меньше заметны изменения.

```python
import numpy as np
from PIL import Image
a = np.asarray(Image.open('orig.png').convert('RGB'), float)
b = np.asarray(Image.open('stego.png').convert('RGB'), float)
mse = ((a-b)**2).mean()
psnr = 10*np.log10(255**2/mse) if mse else float('inf')
print('PSNR dB:', round(psnr, 2))
```

- **1 LSB/канал** — PSNR > 50 дБ, искажение практически незаметно;
- **2–3 LSB** — PSNR ~40–45 дБ, заметно на гладких областях (небо, стена);
- **адаптивные схемы** прячут в «шумных» областях (края, текстуры), где искажение маскируется — ёмкость растёт без роста заметности.

## Шаг 4: робастность против ёмкости

Если данные должны пережить пересжатие или обрезку, используют методы, устойчивые к обработке, — но ёмкость у них ниже.

| Метод | Ёмкость | Робастность | Заметность |
|---|---|---|---|
| LSB RGB | высокая | низкая | низкая |
| LSB палитры | средняя | низкая | низкая |
| DCT (JPEG) | средняя | высокая | средняя |
| Spread-spectrum | низкая | очень высокая | низкая |
| Эхо (аудио) | низкая-средняя | средняя | низкая |

Правило простое: **жертвуешь ёмкостью ради робастности** (или наоборот).

## Шаг 5: как это сужает поиск

Оценка ёмкости — это «фильтр невозможного»:

- **Payload 50 КБ, PNG 800×600** (ёмкость ~180 КБ) → влезает → ищи в LSB RGB.
- **Payload 5 МБ, картинка 200 КБ** → не влезает → нужен аудио/видео-контейнер.
- **Данные пережили пересжатие** → вероятно DCT/spread-spectrum, а не LSB.
- **Нужна максимальная незаметность** → 1 LSB, адаптивно.

Для отчёта IR удобна готовая формула: `ёмкость_байт = (элементов × бит_на_элемент) / 8`. Для изображения элементов = `W×H×каналы`, для аудио = `частота × длительность × каналы`, для видео = `кадры × W×H×каналы`. Умножив на число бит (1, 2, 3), получаешь верхнюю границу.

## Если не сработало

- **Ищешь большой payload в малом канале** (текст, метаданные) — ёмкость там байты, а не килобайты.
- **Считаешь «больше бит = лучше»** — растёт заметность.
- **Не учитываешь сжатие** — JPG/MP3 ломают LSB.
- **Путаешь ёмкость и размер файла** — это разные числа.
- **Отладка:** сравни размер payload с расчётной ёмкостью — это мгновенно отсекает невозможные каналы.

## Разобранные примеры

**1. Сужаем поиск.** PNG 800×600, blob 50 КБ. Ёмкость LSB ≈ 180 КБ → 50 КБ влезает → ищем в LSB RGB, а не в метаданных.

**2. Не влезает.** Payload 5 МБ, картинка 200 КБ → LSB не подходит → ищите видео/аудио-контейнер.

**3. Робастность.** Данные пережили пересжатие → вероятно DCT/spread-spectrum, а не LSB.

## Шпаргалка: оценка за секунды

```python
from PIL import Image

print('1 LSB/ch:', w*h*ch//8, 'bytes')
```

В отчёте фиксируйте формулу, расчёт и вывод о канале — это обоснование того, почему вы ищете именно там, а не в другом месте.

## Что мы теперь знаем

1. Стегосистема балансирует **ёмкость, незаметность, робастность** — улучшение одного ухудшает другие.
2. Ёмкость изображения LSB = `W×H×каналы/8` байт.
3. Аудио и видео дают в разы больше ёмкости, чем картинка.
4. **PSNR** измеряет незаметность; безопасно ~1 LSB/канал.
5. Оценка ёмкости мгновенно сужает поиск канала.

## Почему триада несовместима

Любая стего-система живёт в треугольнике: **ёмкость** (сколько можно спрятать), **незаметность** (насколько трудно обнаружить) и **робастность** (выживет ли встроенное после сжатия, кадрирования, перекодирования). Улучшение одной характеристики почти всегда ухудшает другую — это фундаментальный компромисс, а не недоработка конкретного алгоритма.

Хотите больше ёмкости — придётся трогать больше пикселей/коэффициентов; каждый изменённый элемент — потенциальная улика, значит незаметность падает. Хотите робастность (выжить после JPEG-перекодирования) — встраивайте в устойчивые к сжатию компоненты (например, DC-коэффициенты или средние значения блоков), но таких компонентов мало, поэтому ёмкость падает. Хотите максимальную незаметность — прячьте в наименее значимые биты или используйте адаптивные схемы (WOW, HUGO), которые выбирают «шумные» области, но это снижает и ёмкость, и робастность.

Практический вывод для анализа: **оценка ёмкости сужает поиск**. Зная размер контейнера и требуемый размер сообщения, вы понимаете, какой метод мог быть применён. Если сообщение большое, а контейнер маленький — LSB с малым числом бит или сжатие перед встраиванием. Если важна робастность — ищите не в LSB, а в устойчивых компонентах.

## Частые вопросы

**Сколько LSB можно менять безопасно?** Один-два младших бита на канал незаметны; при 3–4 изменения становятся видны, а статистические детекторы срабатывают почти всегда.

**Как посчитать ёмкость быстро?** Для изображения: `ширина × высота × каналов × бит_на_канал / 8` байт. Для аудио: `сэмплов × каналов × бит/8`. Для видео умножают на число кадров.

**Почему в задаче контейнер «слишком маленький» для флага?** Возможно, данные сжаты (zip/gzip) или закодированы плотнее (base-N), либо использованы не все каналы — проверьте альфа-канал и метаданные.

**Что важнее для CTF?** Обычно незаметность не важна — важен факт извлечения; поэтому в задачах часто применяют простые методы (LSB, дописанные данные), а не адаптивные схемы.
