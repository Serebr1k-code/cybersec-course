## Вопрос, с которого всё начинается

В задаче дали PNG, который выглядит как обычный шумный узор из цветных точек. `zsteg` ничего не находит, `binwalk` — тоже. Но в `file` написано «8-bit colormap» — то есть это **палитровое** изображение. И именно в палитре спрятан флаг. Где его искать?

Разберём палитровые трюки на нашем примере.

## Наш пример: palette_hole.png

Откроем файл и посмотрим на его формат:

```bash
$ file palette_hole.png
palette_hole.png: PNG image data, 128 x 128, 8-bit colormap, non-interlaced
```

«8-bit colormap» — значит, пиксели хранят не сами цвета, а **индексы** в таблицу цветов. Это ключ ко всей задаче.

## Шаг 1: что такое палитра

Палитровый формат хранит не RGB каждого пикселя, а **индекс** — номер строки в таблице цветов. Таблица (**палитра**, в PNG это чанк `PLTE`) — список до 256 записей RGB. У нашего файла палитра полная:

```python
import numpy as np
from PIL import Image
p = np.array(Image.open("palette_hole.png").getpalette()).reshape(-1, 3)
print("entries:", len(p))
print("first 8:", p[:8].tolist())
```

```
entries: 256
first 8: [[78, 204, 64], [34, 16, 250], [233, 32, 103], [122, 13, 204], [138, 172, 208], [127, 124, 100], [12, 151, 222], [203, 251, 153]]
```

В файле лежит ровно 256 записей. Но картинка — шум из точек; сколько цветов она реально использует?

## Шаг 2: почему порядок палитры — канал

Два важных факта:

1. **Порядок записей произволен.** Если переставить цвета в палитре и синхронно пересчитать индексы пикселей, картинка не изменится. Значит, порядок — свободный канал для данных.
2. **Не все записи используются.** Палитра может содержать 256 цветов, а пиксели ссылаться, скажем, только на 200. Тогда 56 «лишних» записей — чистый контейнер: их RGB-значения никто не видит.

Проверим, сколько записей реально задействовано:

```python
im = Image.open("palette_hole.png")
idx = np.array(im)
used = set(np.unique(idx).tolist())
unused = [i for i in range(len(p)) if i not in used]
print("used indices:", len(used), "unused entries:", len(unused))
```

```
used indices: 200 unused entries: 56
```

Пиксели используют индексы 0–199, а записи 200–255 не используются. Вот и «дырка» на 56 записей.

## Шаг 3: находим флаг в неиспользуемых записях

Данные часто лежат именно в RGB-значениях «мёртвых» записей. Соберём их подряд и посмотрим:

```python
msg = b""
for i in unused:
    msg += bytes(p[i].tolist())
print(msg[:18])
```

```
b'flag{palette_hole}'
```

Флаг найден. Смотрим на конкретные записи, чтобы убедиться:

```python
print(p[200:206].tolist())
```

```
[[102, 108, 97], [103, 123, 112], [97, 108, 101], [116, 116, 101], [95, 104, 111], [108, 101, 125]]
```

Читаем байты как ASCII: `[102,108,97]` = `f`,`l`,`a`; `[103,123,112]` = `g`,`{`,`p`; и так далее — флаг разложен по RGB-тройкам неиспользуемых записей. Ни один пиксель на них не ссылается, поэтому картинка не выдаёт закладку.

## Шаг 4: сортировка палитры и инверсии

Второй приём — **порядок** записей. Часто палитру сортируют по яркости, а данные кодируют «нарушениями» сортировки. Возьмём файл `palette_sorted.png`:

```python
p = np.array(Image.open("palette_sorted.png").getpalette()).reshape(-1, 3)
k = 0.299*p[:,0] + 0.587*p[:,1] + 0.114*p[:,2]     # яркость (luminance)
inv = [i for i in range(len(p)-1) if k[i] > k[i+1]]
print("inversions at:", inv)
```

```
inversions at: [10, 40]
```

Палитра почти отсортирована по яркости, но в двух местах порядок нарушен — на позициях 10 и 40. Эти инверсии и есть канал: их позиции (или их число) кодируют данные. Если палитра «почти отсортирована» с несколькими перестановками — это классический признак скрытых бит.

## Шаг 5: порядок индексов — это отдельный канал

Не путай два канала палитрового изображения:

- **палитровый канал** — содержимое или порядок самой таблицы `PLTE` (наши «дырки» и инверсии);
- **индексный канал** — последовательность индексов пикселей: фактически LSB по индексам.

Второй проверяется так:

```python
bits = (np.array(im) & 1).astype(np.uint8)
print(np.packbits(bits.ravel()).tobytes()[:16])
```

Если данные «не в палитре», а картинка шумная — почти наверняка это индексный LSB. Порядок разбора: сначала палитра (дырки/порядок/tRNS), потом индексы.

## Шаг 6: подводные камни

- **Конвертация в RGB убивает палитру.** `im.convert("RGB")` разворачивает индексы в цвета — палитра исчезает, данные теряются. Работай в режиме `P`.
- **Локальные палитры GIF.** Каждый кадр может иметь свою палитру — проверяй все.
- **tRNS.** Массив прозрачности для палитры (PNG) — тоже канал.
- **`zsteg` не всё видит.** Палитровые трюки иногда пропускаются — делай вручную.

## Шаг 7: сравнение двух палитр

Если в задаче есть **cover** (чистый носитель) и stego — самый быстрый путь это прямой diff палитр:

```python
a = np.array(Image.open("cover.png").getpalette()).reshape(-1, 3)
b = np.array(Image.open("stego.png").getpalette()).reshape(-1, 3)
diff = np.where((a != b).any(axis=1))[0]
print("changed entries:", diff)
print("stego colors:", b[diff].tolist())
```

Если изменённые записи содержат читаемые ASCII-коды (`102,108,97,103` = `flag`) — задача решена. Если изменён только **порядок** записей, а не их содержимое — это перестановочный канал: сравнивай позиции.

## Шаг 8: палитра в разных форматах

Палитра лежит в разных местах в зависимости от формата, и путь к ней отличается:

| Формат | Палитра | Особенности |
|---|---|---|
| PNG | чанк `PLTE` + `tRNS` | до 256 записей, тип цвета 3 |
| GIF | GCT + LCT | палитра может быть на каждый кадр |
| BMP | массив после заголовка | при bitcount ≤ 8 |
| TIFF | тег `ColorMap` | отдельный тег |

Для GIF палитра кадра может отличаться от глобальной — проверяй `im.info` при `im.seek(кадр)`. Для TIFF `ColorMap` читается через библиотеку `tifffile`. Практический порядок разбора: `file` → `pngcheck -v` (или разбор чанков вручную) → палитра (порядок/дырки/tRNS) → индексы (LSB/чётность).

Отдельно про `tRNS`: в PNG это массив прозрачности, по одному значению альфы на запись палитры. Значения альфы для неиспользуемых записей можно модулировать так же, как RGB, — это ещё один канал, который проверяющие часто пропускают. Читается он через `Image.open(...).info.get("transparency")`. Начинай разбор всегда с неиспользуемых записей, затем tRNS, затем порядок — это порядок от самого «дешёвого» канала к самому тонкому.

## Что мы теперь знаем

1. Палитровые форматы хранят **индексы** в таблицу цветов (`PLTE` в PNG).
2. Порядок палитры произволен — это свободный канал.
3. Неиспользуемые записи — контейнер: их RGB никто не проверяет.
4. Наш флаг лежал в записях 200–205 как ASCII по тройкам RGB.
5. Сортировка с инверсиями (позиции 10, 40) — второй палитровый приём.
6. Индексный LSB — отдельный канал; проверяй его после палитры.
