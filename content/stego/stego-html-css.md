## Вопрос, с которого всё начинается

У тебя есть файл `index.html`. Открываешь в браузере — обычная страница с текстом.
Но в задаче сказано: данные спрятаны **внутри** страницы, и браузер их не показывает.
Как страница может нести информацию, не отображая её?

HTML — текстовый формат, а значит, к нему применимы все приёмы **текстовой**
стеганографии. Плюс у него есть собственные «невидимые» конструкции. Разберём их.

## Наш пример

Открываем страницу:

```
$ file index.html
index.html: HTML document, ASCII text
$ head -8 index.html
<!DOCTYPE html>
<html>
<head>
  <meta charset="utf-8">
  <title>Отчёт за квартал</title>
  <!-- build: 2024-06-01 -->
  <link rel="stylesheet" href="style.css">
</head>
```

Выглядит как обычный HTML. Начнём с самого очевидного канала — **комментариев**.

## Шаг 1: HTML-комментарии

Комментарий `<!-- ... -->` браузер полностью игнорирует, но он остаётся в файле.

```
$ grep -o '<!--.*-->' index.html
<!-- build: 2024-06-01 -->
<!-- note: nto{html_c0mm3nt_st4sh} -->
```

Это базовый приём. Часто данные кладут не целиком, а **частями** в разные комментарии,
чтобы `grep` по `nto{` не сработал сразу.

## Шаг 2: zero-width символы

Между видимыми буквами можно вставить **невидимые** символы Unicode:

- `U+200B` ZERO WIDTH SPACE
- `U+200C` ZERO WIDTH NON-JOINER
- `U+200D` ZERO WIDTH JOINER
- `U+FEFF` ZERO WIDTH NO-BREAK SPACE (BOM)

Браузер их не рисует, но в исходнике они есть. Два разных zero-width символа кодируют
бит (0/1), а весь текст становится носителем. Извлечение — скриптом:

```
$ python3 zw_extract.py index.html
found 480 zero-width chars
decoded: nto{z3r0_w1dth_1n_html}
```

Важно: в терминале их не видно, поэтому `cat` не поможет — нужен `hexdump`/`xxd` или
скрипт.

## Шаг 3: порядок атрибутов и правил

В HTML порядок атрибутов в теге **не важен** для рендеринга:

```
<a href="/a" class="btn" id="x">
```

и

```
<a class="btn" id="x" href="/a">
```

отображаются одинаково. Значит, **перестановкой атрибутов** можно кодировать биты
(перестановочная стеганография). То же в CSS: порядок независимых правил и свойств
внутри блока не влияет на результат.

## Шаг 4: CSS-специфичные приёмы

CSS даёт дополнительные каналы:

1. **Свойство `content`** в `::before`/`::after` может добавлять невидимый текст:
   ```css
   .x::after { content: "nto{css_c0nt3nt}"; font-size: 0; }
   ```
   `font-size: 0` делает символы невидимыми, но они в DOM.
2. **Кастомные переменные** `--key: value;` — произвольные строки в стилях.
3. **`display:none` / `visibility:hidden`** — скрытые элементы, видимые в исходнике.
4. **`color` в точности `#ffffff` на белом фоне** — «невидимый» текст (не стеганография,
   но классический трюк).
5. **data-URI** в `background-image` — картинка прямо в CSS, куда встроен payload.

## Шаг 5: пайплайн разбора

1. `file index.html` — текстовый?
2. `grep -o '<!--.*-->' index.html` — комментарии.
3. `python3 zw_extract.py index.html` — zero-width символы (или `xxd` и глазами по `e2 80 8b`).
4. Просмотреть `style.css` на `content`, кастомные переменные, скрытые селекторы.
5. Проверить `display:none` элементы и невидимый текст.
6. Помнить: браузер **нормализует** разметку, поэтому смотреть надо **исходник**, а не
   «Inspect Element» (DOM может отличаться от файла).

## Что мы теперь знаем

- HTML-комментарии — простейший канал.
- **Zero-width символы** кодируют биты, невидимы в браузере.
- **Порядок атрибутов/правил** не влияет на рендеринг — годится для битов.
- CSS даёт каналы через `content`, кастомные переменные, скрытые элементы, data-URI.
- Разбирать нужно **исходный файл**, а не DOM в инспекторе.

## Полный скрипт: извлечение zero-width и невидимых символов

Терминал не рисует zero-width символы, поэтому глазами их не найти — нужен скрипт.
Вот минимальный декодер, который переводит пары «пробел ↔ non-joiner» в биты:

```python
import sys

# Отображение: какой символ кодирует какой бит.
ZW = {'\u200b': '0', '\u200c': '1'}   # ZWSP -> 0, ZWNJ -> 1

def decode(path):
    text = open(path, encoding='utf-8', errors='replace').read()
    bits = ''.join(ZW[c] for c in text if c in ZW)
    out = bytearray()
    for i in range(0, len(bits) - 7, 8):
        out.append(int(bits[i:i + 8], 2))
    return bytes(out)

sys.stdout.write(decode(sys.argv[1]).decode('utf-8', 'replace'))
```

Запуск и вывод:

```
$ python3 zw_decode.py index.html
nto{z3r0_w1dth_1n_html}
```

Важно: скрипт **не угадывает** соответствие символов — оно задано заранее. Если
автор закодировал иначе (три символа вместо двух, обратный порядок бит, старший
бит вперёд), декодер вернёт мусор. Тогда перебираем варианты: поменять местами
`0`/`1`, читать по 7 бит, читать с конца. Это нормальная практика — сигнатура
`nto{` в первых байтах подскажет, что направление выбрано верно.

## Проверка «глазами»: xxd и поиск по байтам

Быстро понять, есть ли вообще невидимые символы, помогает поиск их UTF-8 байтов:

```
$ xxd index.html | grep -E 'e2 80 8b|e2 80 8c|e2 80 8d'
00000210: 6e20 e280 8be2 808b e280 8c20 7420 e280  n ......... t ..
```

Байты `e2 80 8b` — это `U+200B` (ZWSP), `e2 80 8c` — `U+200C` (ZWNJ),
`e2 80 8d` — `U+200D` (ZWJ). Если видишь такую «мешанину» там, где её быть не
должно, — это почти наверняка канал. Кодировка важна: в UTF-8 все три символа
занимают по три байта, в UTF-16 — по два (`200b`, `200c`, `200d`).

## CSS-каналы: от комментариев до @font-face

CSS — тоже текст, и каналов в нём не меньше, чем в HTML:

1. **Комментарии** `/* ... */` — видны только в исходнике.
2. **`content` с `font-size: 0`** — невидимый текст в псевдоэлементах.
3. **Кастомные свойства** `--token: "..."` — произвольные строки.
4. **`@font-face` с `unicode-range`** — можно подключить «шрифт», который отрисует
   невидимые глифы; сами данные лежат в файле шрифта.
5. **Порядок независимых правил** — как порядок атрибутов, кодирует биты.
6. **Селекторы-пустышки** `.a1, .a2, ...` — имена классов могут кодировать данные.

Практический разбор:

```
$ grep -o '/\*.*\*/' style.css
/* theme: dark */
/* checksum: 3f9a1c */
$ grep -n -- '--' style.css
22:  --brand-hint: "nto{css_v4r_ch4nn3l}";
```

## Скрытое в data-URI

В `background-image: url("data:image/png;base64,...")` лежит **настоящий файл**,
закодированный в base64. Это полноценный контейнер: внутри может быть PNG со
своим LSB-каналом. Извлекаем и разбираем как обычную картинку:

```
$ grep -o 'data:image/[a-z]*;base64,[A-Za-z0-9+/=]*' style.css | head -1 > d.txt
$ sed 's#.*base64,##' d.txt | base64 -d > embedded.png
$ file embedded.png
embedded.png: PNG image data, 64 x 64, 8-bit/color RGBA
```

Дальше `embedded.png` разбирается инструментами `zsteg`, `binwalk`, `steghide` —
всё, что мы проходили для изображений.

## Анти-DOM: почему Inspect Element обманывает

Браузер **нормализует** разметку: убирает лишние пробелы, приводит теги к нижнему
регистру, переставляет атрибуты, строит DOM-дерево. Поэтому данные, спрятанные в
**порядке атрибутов** или в **лишних пробелах**, в инспекторе исчезают. Работаем
только с исходником, скачанным «как есть»:

```
$ curl -s --compressed http://target/index.html -o page.html
$ file -i page.html
page.html: text/html; charset=utf-8
```

## Edge cases и подводные камни

- **Сжатие.** Если сервер отдаёт gzip/brotli, скачивай несжатый ответ — `curl
  --compressed` распакует прозрачно, иначе канал не увидишь.
- **Кодировка.** Файл может быть не UTF-8 (например, windows-1251) — тогда байты
  zero-width «поплывут». Проверяй `file -i`.
- **BOM.** Ведущий `U+FEFF` иногда добавляет редактор случайно — не всегда это канал.
- **Внешние ресурсы.** Данные часто лежат не в самом HTML, а в `style.css`,
  `app.js`, шрифтах — проверь все подключённые файлы.
- **Динамика.** Если контент приходит из JavaScript, статика его не покажет —
  нужен анализ JS-бандла.

## Что дальше / решение

Сквозной пример решается так: находим комментарий `nto{html_c0mm3nt_st4sh}` через
`grep`, затем zero-width — скриптом `zw_decode.py`. Если оба канала пусты, идём в
подключённые CSS/JS и в data-URI. Общий принцип: **искать в байтах файла, а не в
том, что показывает браузер**.

## Шпаргалка: каналы HTML/CSS

| Канал | Как найти | Сложность |
|-------|-----------|-----------|
| HTML-комментарий | `grep -o '<!--.*-->'` | низкая |
| Zero-width | `xxd` + скрипт-декодер | средняя |
| Порядок атрибутов | сравнить исходник с нормализованным | высокая |
| CSS `content` | `grep 'content:'` | низкая |
| Кастомные переменные | `grep -- '--'` | низкая |
| data-URI | `grep 'base64,'` + `base64 -d` | средняя |
| Скрытый текст | `display:none`, цвет = фон | низкая |

## Практика: автоматизированный перебор каналов

Когда каналов много, удобно прогнать один скрипт-«комбайн», который проверяет всё
сразу. Логика: скачать исходник, вытащить комментарии, найти data-URI, посчитать
zero-width, сравнить исходник с нормализованным вариантом.

```bash
# 1. комментарии и data-URI
grep -o '<!--.*-->' page.html
grep -o 'base64,[A-Za-z0-9+/=]*' page.html | sed 's/base64,//' | base64 -d | file -

# 2. невидимые символы (только их количество)
python3 -c "t=open('page.html',encoding='utf-8').read(); \
print(sum(t.count(c) for c in '\u200b\u200c\u200d\ufeff'))"

# 3. нормализация для сравнения порядка атрибутов
python3 -c "import html5lib,html; d=html5lib.parse(open('page.html').read()); \
print(html5lib.serialize(d))" > normalized.html
diff <(head -50 page.html) <(head -50 normalized.html)
```

Если `diff` показывает перестановку атрибутов в теге, где геометрия/вид не
меняется, — это перестановочная стеганография. Аналогично сравниваем CSS:
порядок независимых правил не важен, но может кодировать биты.

## Расширение или готовая утилита?

Для браузера есть плагины, подсвечивающие невидимые символы (например, «Zero Width
Characters Highlighter»), но в CTF надёжнее командная строка: она не нормализует и
не скрывает ничего. Из готового: `stegoveritas` умеет вытаскивать из HTML/CSS
комментарии и скрытые вставки, `binwalk` найдёт вложенные файлы, `exiftool` — если
носитель ещё и картинка. Помни: плагин смотрит **DOM**, а не байты файла — для
порядка атрибутов и лишних пробелов он бесполезен.
