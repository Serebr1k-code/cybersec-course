## Вопрос, с которого всё начинается

Один секрет — одна точка отказа. Если приватный ключ хранится у одного человека, его кража компрометирует всё. Как «размазать» ключ по нескольким участникам так, чтобы любые `t` из них могли им воспользоваться, а любые `t-1` — нет? Это **пороговая криптография**, и в её основе — разделение секрета. Разберём его вживую и сразу увидим типичную ошибку реализации.

## Наш пример

Схема Шамира `(3, 5)`: секрет — свободный член полинома степени 2, доли — значения полинома в точках. Соберём доли и восстановим секрет интерполяцией Лагранжа.

```python
import random
P = 2**127 - 1                      # большое простое поле
def poly_eval(coeffs, x, p=P):
    return sum(c * pow(x, i, p) for i, c in enumerate(coeffs)) % p

def lagrange_at_zero(points, p=P):
    s = 0
    for i, (xi, yi) in enumerate(points):
        num = den = 1
        for j, (xj, _) in enumerate(points):
            if i == j: continue
            num = (num * (-xj)) % p
            den = (den * (xi - xj)) % p
        s = (s + yi * num * pow(den, -1, p)) % p
    return s

secret = 0xDEADBEEF
coeffs = [secret, random.randrange(P), random.randrange(P)]
shares = [(i, poly_eval(coeffs, i)) for i in range(1, 6)]
```

Реальный прогон:

```
восстановлено по 3 долям: 0xdeadbeef | верно: True
f1(3)-f2(3) = 0x7fffffffffffffffffffffffffff7777 | s1-s2 = 0x7fffffffffffffffffffffffffff7777 | утечка: True
```

Первая строка — корректное восстановление по любым 3 долям из 5. Вторая — **утечка** из-за переиспользования полинома, о ней ниже.

## Шаг 1: как работает схема Шамира

Секрет `s` — свободный член полинома `f(x)` степени `t-1`; доли — значения `f(i)` в точках `i = 1..n`. Любые `t` точек однозначно восстанавливают полином **интерполяцией Лагранжа**, а `t-1` — нет: через них проходит бесконечно много полиномов. Отсюда порог: любые `t` долей дают секрет, любые `t-1` не дают ничего.

Варианты: **Blakley** (гиперплоскости), **CRT-схема** (китайская теорема об остатках), **additive sharing** (`t = n`, секрет — сумма долей; примитив в MPC).

## Шаг 2: типичные ошибки реализации

- **Переиспользование полинома.** Если для двух секретов `s1, s2` взять одинаковые коэффициенты, кроме свободного члена, то `f1(i) - f2(i) = s1 - s2` для всех `i` — разность секретов известна сразу. Именно это показала вторая строка вывода: разность долей равна разности секретов.
- **Слабый генератор** для коэффициентов полинома.
- **Хранение долей без аутентификации** — можно подсунуть фальшивую долю.

## Шаг 3: пороговые подписи

Вместо восстановления ключа (что сводит пороговость на нет) хотят **распределённую подпись**: `t` участников совместно формируют подпись, не собирая ключ в одном месте.

- **Threshold ECDSA** (GG18/GG20) — самая сложная: ECDSA нелинейна (нужна инверсия `k`), требуется MPC для вычисления `k^{-1}`. Используется в кастоди-кошельках.
- **FROST** — пороговая подпись Шнорра: каждый даёт частичную подпись, агрегатор собирает финальную. Проще и эффективнее.
- **Threshold BLS** — благодаря билинейности спариваний сумма частичных подписей = подпись; популярна в блокчейн-валидаторах.

Атаки: **rogue-key** (злоумышленник выбирает ключ так, что агрегированная подпись подконтрольна; лечится proof-of-possession), **отказ участника**, **повтор nonce** между сессиями.

## Шаг 4: MPC — oblivious transfer и garbled circuits

Базовый примитив MPC — **oblivious transfer (OT)**: отправитель имеет `m0, m1`, получатель — бит `b`; в результате получатель узнаёт `m_b`, но не `m_{1-b}`, а отправитель не узнаёт `b`.

- **Garbled circuits (Yao)** — для двух участников: одна сторона «шифрует» булеву схему таблицами, другая вычисляет, не видя входов первой.
- **GMW** — для нескольких участников: секретное разделение каждого бита + OT для умножения.
- **SPDZ и др.** — secret-sharing-based MPC, быстрые на арифметических схемах.

Для CTF чаще всего встречается «игрушечный» MPC: 2–3 участника, простая функция и ошибка в протоколе.

## Шаг 5: VSS — проверяем доли

Простая схема Шамира не проверяет доли: испорченная доля даёт неверный секрет, и никто не знает, кто виноват. **Verifiable Secret Sharing (VSS)** решает это: дилер публикует обязательства к коэффициентам полинома, и каждый проверяет свою долю, не зная остальных.

- **Feldman VSS** — использует `g^{a_i}`; проверка `g^{f(i)} == ∏ (g^{a_j})^{i^j}`. Просто, но публикует `g^s`.
- **Pedersen VSS** — два генератора и случайность; обязательство скрывающее (hiding).

Практический вывод для аудита: если доли **не проверяются** — это красный флаг. Отсутствие VSS — одна из самых частых щелей в самодельных пороговых схемах, и на CTF именно она даёт подсунуть фальшивую долю.

## Шаг 6: сводка атак и моделей угроз

- **Переиспользование nonce/полинома** — утечка разности или полное восстановление секрета.
- **Rogue-key** в агрегации подписей — подконтрольная подпись; лечится proof-of-possession.
- **Malicious participants** — без VSS участник подсовывает фальшивую долю; нужны verifiable secret sharing и аутентификация.
- **Side-channel в MPC** — timing/power утечки даже в «безопасном» протоколе (см. `crypto-timing`).
- **Fault-атаки** — сбой в одном участнике раскрывает чужие доли (аналог Bellcore).
- **Слабая случайность** — предсказуемый nonce или коэффициенты ломают всю схему.

Отдельно стоит упомянуть модель угроз: получестные протоколы не защищают от активного обманщика, а протокол безопасен только при выполнении своей модели (честное большинство, синхронность, аутентификация). «MPC» — это не магическая безопасность, а набор гарантий при явных предположениях.

## Что мы теперь знаем

- Схема `(t, n)`: любые `t` долей восстанавливают секрет, `t-1` — нет.
- Переиспользование полинома раскрывает разность секретов.
- Пороговые подписи (ECDSA, FROST, BLS) подписывают без сборки ключа.
- OT — базовый примитив MPC; garbled circuits и GMW строятся на нём.
- Без VSS вредоносный участник искажает восстановление.
- Слабая случайность ломает всю схему.
