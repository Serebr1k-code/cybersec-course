## Вопрос, с которого всё начинается

RSA и ECDSA сломает квантовый алгоритм Shor (ты видел его в `crypto-shor-grover`). Значит, нужны подписи, стойкие к квантовому компьютеру. Решётчатые схемы (Dilithium) ты уже видел в `crypto-post-quantum`. Но есть более консервативный путь: построить подпись **только на хэш-функции** — тогда её стойкость не зависит ни от факторизации, ни от решёток, только от криптостойкости хэша. Такие схемы называются **hash-based signatures**, и они уже стандартизованы (XMSS, LMS, SPHINCS+).

## Наш пример: одноразовая подпись Лэмпорта

Начнём с кирпичика — схемы **Лэмпорта** (Lamport one-time signature, OTS). Идея проста. Для подписи одного бита сообщения генерируем два случайных секретных значения `(s0, s1)`, публикуем их хэши `(H(s0), H(s1))`. Чтобы подписать бит `b`, раскрываем `s_b`. Проверяющий хэширует `s_b` и сверяет с `H(s_b)`.

Для сообщения из 256 бит нужно 256 таких пар. Публичный ключ — 512 хэшей. Подпись — 256 секретных значений. Работает, но подписать можно **только один раз**: если раскрыть и `s0`, и `s1` для одного бита, атакующий подделает любой бит. Отсюда «one-time».

## Шаг 1: от одноразовой — к дереву Меркл

Чтобы подписывать много сообщений, строят **дерево Меркл** (ты знаешь его из `crypto-merkle-tree`). Листья — хэши одноразовых публичных ключей `OTS_1..OTS_N`. Корень дерева — это публичный ключ всей схемы. Чтобы подписать сообщение, берут один ещё не использованный лист `OTS_i`, подписывают им сообщение и прикладывают **путь аутентификации** — хэши соседей от листа до корня. Проверяющий восстанавливает корень и сверяет.

Так устроены **XMSS** (eXtended Merkle Signature Scheme) и **LMS** (Leighton-Micali Signature). У них есть состояние: каждую одноразовую подпись можно использовать один раз, и индекс надо хранить. Потеря состояния = повторное использование OTS = полная компрометация.

## Шаг 2: SPHINCS+ — без состояния

Состояние — большая проблема: синхронизировать счётчик между репликами сервиса тяжело. **SPHINCS+** (читается «сфинкс плюс») решает это, делая подпись **stateless**. Идея: выбрать лист по хэшу самого сообщения. Верхний слой — «гипердерево» из деревьев XMSS; для сообщения детерминированно выбирается путь вниз, и подпись включает подписи XMSS на каждом уровне.

```
sign(msg):
    R = PRF(seed, msg)                 # рандомизатор, детерминированный
    leaf = H(R || pub_seed || msg)     # выбираем лист без состояния
    подписываем XMSS-деревьями вдоль пути leaf → root
    return R || путь подписей
```

Размер подписи SPHINCS+ — килобайты (больше, чем у Dilithium), зато нет состояния и нет доверия к сложным математическим задачам — только хэш.

## Шаг 3: сравнение

- **XMSS/LMS:** маленькие подписи, но **stateful** — надо аккуратно хранить счётчик; подходят для прошивок и долгоживущих устройств.
- **SPHINCS+:** stateless, крупные подписи, медленнее; подходит там, где состояние вести нельзя.
- Все три опираются только на стойкость хэш-функции — это их главный плюс перед решётками.

## Полный прогон

В лабе дан `ots.txt` с одноразовыми секретами и сообщением, `tree.txt` с листьями и скрипт `xmss.py`. Скрипт подписывает сообщение листом, собирает путь аутентификации до корня и выводит корень:

```
$ cat ots.txt
message_bits = 10110100...
secret_0 = 3f...
secret_1 = a2...

$ python3 xmss.py
leaf_OTS = 6c1f...
auth_path = [8a3d..., d20e..., ...]
root = nto{sp1ncs_w0ts_0n3_t1m3_s1gn4tur3}
```

Корень здесь равен флагу: студент видит, что подпись действительно ведёт к публичному ключу.

## Если не сработало

Если корень не сходится, проверь порядок листьев в дереве — Меркл чувствителен к порядку. Если попытаться подписать два сообщения одним листом, атакующий восстановит секреты (для Лэмпорта — покажет, что для какого-то бита раскрыты оба значения). Если размер подписи огромный — это нормально для SPHINCS+, он жертвует размером ради stateless.
