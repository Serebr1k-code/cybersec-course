## Идея CBC и её слабость

Вспомним, как CBC расшифровывает: каждый блок открытого текста получается XOR-ом результата расшифрования текущего шифротекста с **предыдущим шифротекстом**.

```
P_i = D_K(C_i) ⊕ C_{i-1}       (C_0 = IV)
```

Здесь `C_{i-1}` — это данные, которые атакующий **видит в токене и может менять**. Ключевое наблюдение: результат `D_K(C_i)` атакующему неизвестен (нужен ключ), но он **фиксирован** для данного `C_i`. Значит, если мы изменим `C_{i-1}` на известную разницу `Δ`, то `P_i` изменится ровно на ту же `Δ`:

```
изменяем C_{i-1} на Δ  =>  P_i меняется на Δ
```

Это свойство называется **CBC malleability** (ковкость). Оно превращает голый CBC в схему, где атакующий без ключа может целенаправленно менять расшифрованный текст — при условии, что он знает (или угадывает) исходный открытый текст и что нет MAC.

Важно понимать границы: bit-flipping **не расшифровывает** секрет и **не даёт ключ**. Он позволяет только *модифицировать* уже известные/угадываемые поля. Это идеальный инструмент для «role=guest → role=admin», «amount=100 → amount=999», «admin=0 → admin=1».

## Атака на IV (первый блок)

Первый блок расшифровывается как `P_0 = D_K(C_0) ⊕ IV`. IV обычно передаётся открыто — часто прямо в cookie перед шифротекстом или как отдельное поле. Значит, `P_0` можно менять **произвольно и без побочных эффектов**, подменив IV:

```
новый_IV = старый_IV ⊕ старый_P0 ⊕ желаемый_P0
```

**Классический сценарий:** cookie = `base64(IV || ciphertext)`, где открытый текст начинается с `user=guest`. Хотим `user=admin`. Знаем и старый, и новый текст, поэтому XOR-разница вычисляется точно.

```python
import base64

old_pt = b"user=guest"       # знаем структуру первого блока
new_pt = b"user=admin"       # хотим получить
iv = bytearray(cookie[:16])
ct = cookie[16:]

for i in range(len(old_pt)):
    iv[i] ^= old_pt[i] ^ new_pt[i]

new_cookie = base64.b64encode(bytes(iv) + ct)
print(new_cookie.decode())
```

Сервер расшифрует, получит `user=admin` и ничего не заметит — если не проверяет целостность.

## Атака на произвольный блок

Для блока `i > 0` менять IV нельзя — на его роль претендует `C_{i-1}`, который является **результатом шифрования** предыдущего блока. Изменение `C_{i-1}`:

- **предсказуемо меняет** `P_i` (это то, что нам нужно),
- **непредсказуемо портит** `P_{i-1}` (побочный эффект — предыдущий блок превращается в мусор).

Поэтому атака на «средний» блок применяется, когда:

- порча предыдущего блока **не важна** (он не проверяется приложением), или
- мы атакуем **последний** блок (портим предпоследний, но это может быть безразлично), или
- структура данных позволяет «пожертвовать» одним блоком (например, в JSON есть длинное строковое поле, которое можно испортить).

```python
def flip_cbc(ct, block_idx, known_pt_block, desired_pt_block):
    # меняем C_{block_idx-1}, чтобы P_block_idx стал desired_pt_block
    ct = bytearray(ct)
    prev = (block_idx - 1) * 16
    for i in range(16):
        ct[prev + i] ^= known_pt_block[i] ^ desired_pt_block[i]
    return bytes(ct)
```

Обратите внимание: чтобы атака сработала, `known_pt_block` и `desired_pt_block` должны быть **точно выровнены по блокам**. Если поле пересекает границу блока, нужно аккуратно работать с двумя блоками.

## Практический пример: «admin=true» в cookie

Сервер выдаёт cookie: `base64(IV || AES_CBC("role=user&name=..."))`. Известно, что первый блок содержит `role=user`.

```python
import base64

cookie = base64.b64decode(token)
iv, ct = cookie[:16], cookie[16:]

old = b"role=user"          # 9 байт; блок добит чем-то, но нас интересуют первые 9
new = b"role=root"
iv = bytearray(iv)
for i in range(len(old)):
    iv[i] ^= old[i] ^ new[i]

forged = base64.b64encode(bytes(iv) + ct)
print(forged.decode())
```

Если сервер не проверяет целостность (нет HMAC) — мы «повысили» роль. Заметьте: мы не расшифровывали ничего и не знаем ключ; мы лишь знали структуру первого блока.

Если целевое поле лежит не в первом блоке, придётся «пожертвовать» предыдущим блоком. Часто это приемлемо: например, если предыдущий блок — это поле-заполнитель, которое приложение игнорирует, или комментарий в JSON, который не влияет на логику.

## Атака при неизвестном тексте

Если открытый текст неизвестен, но есть **оракул**, сообщающий, валиден ли padding, bit-flipping комбинируется с padding oracle (см. `crypto-padding-oracle`). Схема: сначала padding oracle восстанавливает открытый текст, затем bit-flipping модифицирует нужные байты. Без оракула и без знания текста bit-flipping напрямую не применить — нужна хотя бы одна опора.

## Bit-flipping против padding oracle: что выбирать

Эти две атаки часто идут рука об руку, но решают разные задачи и требуют разных условий.

| Условие | Подходящая атака |
|---|---|
| Знаем структуру/текст, хотим изменить поле | bit-flipping (этот урок) |
| Текст неизвестен, есть оракул padding | padding oracle (восстановить текст) |
| Текст неизвестен и оракула нет | ни то, ни другое напрямую |
| Есть оракул padding + нужно изменить поле | padding oracle → затем bit-flipping |
| Шифротекст защищён HMAC | обе не работают |

Логика выбора проста. Bit-flipping — атака *целостности*: она не даёт новых знаний, а использует уже известное, чтобы «подкрутить» данные. Padding oracle — атака *конфиденциальности*: она вытаскивает неизвестный текст. Если вам нужно и то и другое (восстановить неизвестный секрет и подменить его), комбинируйте: сначала восстановите текст padding oracle, затем модифицируйте нужные байты bit-flipping. Обе атаки требуют, чтобы не было MAC/AEAD — иначе любое изменение шифротекста будет отвергнуто до расшифрования.

Отдельно стоит помнить про **CBC cut-and-paste** (см. `crypto-cut-and-paste`): если приложение склеивает блоки из разных шифротекстов, можно переставлять целые блоки, не зная их содержимого. Это ещё одно проявление отсутствия целостности.

## Ограничения

- **Нужно знать старый открытый текст** (хотя бы целевой блок) — иначе не вычислить XOR-разницу.
- **Портится предыдущий блок** (кроме случая атаки на IV). Приложение может это заметить, если поле проверяется.
- **Не работает против AEAD.** Если CBC дополнен HMAC (encrypt-then-MAC), любое изменение шифротекста ломает MAC → сервер отвергнет запрос ещё до расшифрования.
- **Выравнивание критично.** Поля должны совпадать по позиции в блоке; иначе придётся менять два блока и жертвовать целым блоком.
- **Серверная нормализация.** Если приложение парсит `user=admin&user=guest` и берёт последнее значение, атака может дать неожиданный результат.

## Защита

- **Encrypt-then-MAC** (HMAC поверх шифротекста) — классический стандарт: сначала проверяем MAC, потом расшифровываем.
- **AEAD-режимы** (GCM, ChaCha20-Poly1305) вместо голого CBC — тег целостности включён в схему.
- **Проверка целостности** перед использованием данных; никогда не расшифровывать и не доверять данным до проверки тега/MAC.
- **Не использовать IV/шифротекст как доверенные данные.** Всё, что пришло от клиента, — недоверенно.
- **Связывать контекст (AAD):** роль, ID пользователя и т. п. должны аутентифицироваться вместе с данными, чтобы их нельзя было переставить.

## Как не застрять

- **Ищите IV в токене.** Если cookie начинается с 16 байт, которые «не меняются» при смене данных — это почти наверняка IV.
- **Знайте структуру текста.** `user=`, `role=`, `is_admin=`, JSON-поля — обычно угадываются или видны в других местах приложения.
- **Атакуйте первый блок через IV** — это чище всего (без порчи предыдущего блока).
- **Проверьте, есть ли MAC.** Если есть — bit-flipping не пройдёт; переходите к поиску других уязвимостей.
- **Если текст неизвестен** — сначала padding oracle, потом модификация.
- **Считайте XOR точно.** `новый = старый ⊕ old_pt ⊕ new_pt`; проверяйте на локальном дешифровании, если возможно.
- **Учитывайте PKCS#7.** В последнем блоке часть байт — padding; не «портите» его случайно.

## Инструменты и команды

```python
# Полный рабочий скрипт атаки на IV
import base64, sys

def bitflip_iv(token_b64, old, new):
    raw = base64.b64decode(token_b64)
    iv = bytearray(raw[:16]); ct = raw[16:]
    assert len(old) == len(new)
    for i in range(len(old)):
        iv[i] ^= old[i] ^ new[i]
    return base64.b64encode(bytes(iv) + ct).decode()

# пример
print(bitflip_iv(sys.argv[1], b"user=guest", b"user=admin"))
```

```bash
# Ручная проверка: расшифровать локально (если известен ключ — для отладки)
openssl enc -d -aes-128-cbc -K 30313233343536373839616263646566 -iv $(python3 -c "print('00'*16)") -in ct.bin -out pt.bin
xxd pt.bin | head
```

Для отладки удобно поднять локальный сервер-заглушку с известным ключом и прогнать атаку end-to-end, прежде чем бить по боевому оракулу.

## Разобранный пример end-to-end

1. Получаем токен: `curl -s 'http://target/login' -d 'u=guest' -c jar` → cookie `session=AbCd...==`.
2. Декодируем: `raw = base64.b64decode(cookie)`; видим `len(raw) % 16 == 0`.
3. Проверяем, что первый блок «плавает» при смене пользователя → это IV.
4. Угадываем структуру: `username=guest;role=user` (по полям формы).
5. Меняем `guest`→`admin` (или `user`→`root`) через IV по формуле выше.
6. Отправляем подделанный токен, проверяем доступ к админ-эндпоинту.
7. Если сервер отверг — значит есть MAC/AEAD; фиксируем `record_vector` и ищем другой путь.

## Частые ошибки

- **Менять `C_i` вместо `C_{i-1}`.** Чтобы изменить `P_i`, нужно трогать **предыдущий** блок.
- **Забыть, что портится `P_{i-1}`.** Приложение может валидировать предыдущее поле и отклонить запрос.
- **Неверное выравнивание.** Смещение поля внутри блока приводит к порче соседних байт.
- **Считать, что base64 — это шифрование.** Нет; base64 лишь кодирует `IV||ct`.
- **Игнорировать PKCS#7.** При расшифровке последнего блока нужно помнить про padding.
- **Атаковать при наличии HMAC.** Бесполезно; сначала проверьте, что целостность не защищена.
