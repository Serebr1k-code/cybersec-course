## Вопрос, с которого всё начинается

У нас есть две подписи DSA на разные сообщения, и в обеих совпала компонента `r`. Это не совпадение — значит, для обеих подписей использовали **один и тот же nonce** `k`. А повтор nonce в схемах на дискретном логарифме означает, что приватный ключ восстанавливается из двух уравнений за секунды. Разберём это на реальных числах.

## Наш пример

Сгенерируем маленький DSA-набор и подпишем два сообщения одним `k`:

```python
from sympy import nextprime
import hashlib, random
q = nextprime(2**31); p = nextprime(2**64)
while True:
    h = random.randrange(2, p-1); g = pow(h, (p-1)//q, p)
    if g != 1: break
x = 0x12345678            # приватный ключ
k = 0xdeadbeef            # nonce (один и тот же!)
h1 = int.from_bytes(hashlib.sha256(b'hello').digest(), 'big') % q
h2 = int.from_bytes(hashlib.sha256(b'world').digest(), 'big') % q
r = pow(g, k, p) % q
s1 = (pow(k, -1, q) * (h1 + x*r)) % q
s2 = (pow(k, -1, q) * (h2 + x*r)) % q
```

У нас есть `(r, s1)` и `(r, s2)`. Вопрос: как восстановить `x`, не зная `k`?

## Шаг 1: ElGamal, DSA и Schnorr — три схемы

Все три строятся на дискретном логарифме, но формулы разные:

- **ElGamal:** `r = g^k`, `s = (H(m) − x·r)·k^{−1} mod (q−1)`.
- **DSA:** `r = (g^k mod p) mod q`, `s = k^{−1}(H(m) + x·r) mod q`.
- **Schnorr:** `r = g^k`, `e = H(r ‖ m)`, `s = k + e·x mod q`.

Общее — одноразовый секретный `k` (nonce). Именно он должен быть случайным и **никогда** не повторяться.

## Шаг 2: атака на повтор nonce в DSA

Структура `s = k^{−1}(H(m) + x·r)` даёт два уравнения с двумя неизвестными `k` и `x`:

```
s1 = k^{−1}(h1 + x·r)  mod q
s2 = k^{−1}(h2 + x·r)  mod q
```

Вычитаем: `s1 − s2 = k^{−1}(h1 − h2)`. Отсюда находим `k`, а затем `x`:

```python
kk = ((h1 - h2) * pow(s1 - s2, -1, q)) % q
xx = ((s1*kk - h1) * pow(r, -1, q)) % q
print("k recovered:", kk == k % q, " x recovered:", xx == x)
```

```
k recovered: True  x recovered: True
```

Ключ восстановлен. `x = 0x12345678` — ровно наш приватный ключ. Теперь можно подписать любое сообщение от имени владельца.

## Шаг 3: почему одинаковый r = одинаковый k

В DSA `r = (g^k mod p) mod q` зависит только от `k`. Если `r` совпало — совпало и `k` (с точностью до маловероятной коллизии). Поэтому первый шаг анализа любой задачи на подписи: **посмотрите, нет ли двух подписей с одинаковым `r`**. Если есть — задача решена.

## Шаг 4: смещённый и короткий nonce

Повтор — не единственная слабость. Если `k` не равномерный:

- **Смещённый/частично известный nonce** → решёточная атака (hidden number problem). Зная младшие биты `k`, LLL/BKZ восстанавливает `x`.
- **Усечённый nonce** (например, 32-битный) → перебор плюс решётка.
- **Предсказуемый nonce** (слабый RNG) → воспроизведение `k` и восстановление `x`.

Общий принцип: **любой недостаток энтропии `k` конвертируется в утечку `x`**. Поэтому первый шаг в любой задаче на подписи — собрать как можно больше подписей и поискать закономерности в `r` и `s`.

## Шаг 5: защита — RFC 6979 и EdDSA

Главная защита от атак на nonce — **RFC 6979**, детерминированная генерация `k` из приватного ключа и сообщения через HMAC-DRBG: `k = HMAC_DRBG(x, H(m))`. Тогда для одного сообщения `k` всегда одинаков, а для разных — различен и непредсказуем без знания `x`. Нет ни повтора, ни зависимости от RNG.

**EdDSA** идёт дальше: nonce выводится из ключа и сообщения хэшем, без отдельного RNG. Именно поэтому EdDSA считают «защищённым от ошибок nonce по построению». Но детерминированный nonce не спасает от **утечки** `k` через side-channel — нужны constant-time реализации.

## Шаг 6: сравнение схем

| Схема | Группа | Формула `s` | Особенность |
|-------|--------|-------------|-------------|
| ElGamal | `Z_p^*` | `(H(m)−x·r)·k^{−1}` | классика |
| DSA | подгруппа `q` | `k^{−1}(H(m)+x·r)` | стандарт FIPS |
| Schnorr | любая | `k + e·x` | агрегация, доказуемость |
| ECDSA | кривая | `k^{−1}(H(m)+x·r)` | эллиптический DSA |
| EdDSA | кривая Эдвардса | `k + e·x` | детерминированный nonce |

Структурно **ECDSA = DSA над кривой**, **EdDSA = Schnorr над кривой**. Поэтому все атаки на nonce переносятся один в один.

## Шаг 7: агрегация и MuSig

Одно из больших преимуществ Schnorr — **линейность**: подписи можно складывать. Это позволяет **агрегировать** подписи нескольких участников в одну — критично для блокчейна и пороговых схем. **MuSig** — протокол агрегации Schnorr: несколько участников с ключами `y_i` хотят получить одну подпись, валидную для агрегированного ключа `Y = Σ y_i`.

Наивная сумма ключей уязвима к **rogue-key атаке**: последний участник подбирает свой ключ так, чтобы агрегат оказался подконтрольным ему. MuSig решает это через мультипликативные коэффициенты: каждый ключ умножается на `H(Y, y_i)`, что делает подбор «вредного» ключа невозможным без знания чужих. Практический вывод: если видите агрегацию ключей простым сложением без proof-of-possession — это уязвимость, и подпись от имени группы подделывается.

## Что мы теперь знаем

- ElGamal, DSA, Schnorr строятся на дискретном логарифме.
- Одинаковый `r` означает одинаковый `k` → **ключ восстанавливается из двух подписей**.
- Формула восстановления: `k = (h1−h2)/(s1−s2)`, затем `x = (s1·k − h1)/r`.
- Смещённый/короткий nonce ломается решётками.
- Защита — **RFC 6979** (детерминированный nonce) или EdDSA.
- ECDSA = DSA над кривой, EdDSA = Schnorr над кривой.

## На что смотреть дальше

- **Повтор `k`** — фатально; проверяйте совпадение `r` в первую очередь.
- **Слабый RNG** — предсказуемый `k` ломает ключ.
- **Не хэшировать сообщение** — атаки на подпись.
- **Путать порядок `q` и модуль `p`** в вычислениях по модулю.
- **Считать DSA «устаревшим, но безопасным»** — при правильном nonce он стоек, но ошибки реализации часты.
- **Забыть про RFC 6979** — правильная практика для DSA/ECDSA.

## Таблица: сравнение схем подписей

Разные схемы по-разному относятся к nonce, детерминизму и агрегации. Таблица помогает выбрать, куда смотреть при аудите.

| Схема | Nonce | Детерминизм | Агрегация | Классическая проблема |
|-------|-------|-------------|-----------|------------------------|
| ElGamal | случайный `k` | нет | нет | повтор `k` → раскрытие ключа |
| DSA | случайный `k` | нет | нет | повтор/смещение `k` → HNP |
| ECDSA | случайный `k` | нет (RFC 6979 — да) | нет (MuSig) | утечка бит `k` → lattice |
| Schnorr | случайный `k` | да (RFC 6979) | **да** (линейна) | nonce reuse → ключ |
| EdDSA | детерминированный | **да** | нет | требует качественного хэша |
| BLS | нет | нет | **да** | требует pairing, hash-to-curve |

Ключевое различие: **Schnorr/EdDSA линейны** — из-за этого возможна агрегация подписей (MuSig) и пороговая подпись (FROST). DSA/ECDSA нелинейны (`s = k^{-1}(z + rd)`), поэтому агрегация требует дополнительных раундов.

## Рабочий пример: восстановление nonce по двум подписям с общим r

Если в DSA/ECDSA два сообщения подписаны с одинаковым `k`, то `r` совпадает, и `k` вычисляется напрямую. Покажем вывод формул и скрипт.

Пусть `s1 = k^{-1}(z1 + r·d)` и `s2 = k^{-1}(z2 + r·d)`. Вычитаем:

```
s1 - s2 = k^{-1}(z1 - z2)  =>  k = (z1 - z2) / (s1 - s2) mod n
d = (s1·k - z1) / r mod n
```

```python
n = 0xFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFEBAAEDCE6AF48A03BBFD25E8CD0364141  # secp256k1
z1, s1 = 0x...aa, 0x...11
z2, s2 = 0x...bb, 0x...22
r = 0x...cc   # одинаковое r у обеих подписей

k = (z1 - z2) * pow(s1 - s2, -1, n) % n
d = (s1 * k - z1) * pow(r, -1, n) % n
print(hex(d))   # приватный ключ
```

Если `r` различается, но nonce частично известен (утекли старшие биты), задача превращается в hidden number problem и решается решёткой (LLL) — см. `crypto-ecdsa-nonce`.

## Ограничения и типичные ошибки

- **Общий `r` — верный признак reuse.** Первое, что проверяют при аудите подписей: повторяется ли `r` между сообщениями.
- **`z` — это хэш сообщения, а не само сообщение.** Для DSA `z = H(m) mod n`; для ECDSA — усечённый хэш. Ошибка в `z` даёт неверный `d`.
- **Модульная арифметика `mod n`, а не `mod p`.** Все операции — в порядке подгруппы `n`, а не в поле `p`.
- **EdDSA не подвержена reuse.** Nonce выводится детерминированно из ключа и сообщения; но плохой хэш ломает схему.
- **Агрегация требует защиты от rogue-key.** В MuSig2 нужен proof-of-possession, иначе злоумышленник подбирает ключ под чужой.

## Обязательная проверка восстановленного ключа

Формулы выше (см. «Рабочий пример») дают кандидата в приватный ключ, но **никогда не доверяйте ему без проверки**. Типичная причина «ключа, который ничего не подписывает» — неверный `z` или модуль. Проверка занимает три строки: строим из кандидата подписывающий ключ, подписываем тестовое сообщение и верифицируем его публичным ключом `Q = d·G`:

```python
from ecdsa import SigningKey, SECP256k1
sk = SigningKey.from_secret_exponent(d, curve=SECP256k1)
vk = sk.verifying_key
assert vk.verify(sk.sign(b"test"), b"test")
print("ключ подтверждён")
```

Если assert проходит — ключ верный, и можно подписывать любые сообщения. Если нет — перепроверьте `z` (для ECDSA это левые `n` бит `H(m)`, а не само сообщение), модуль (порядок подгруппы `n`, а не поле `p`) и порядок подписей (`s1`/`s2` должны соответствовать `z1`/`z2`). Та же проверка применима к DSA (`mod q`) и ElGamal — меняется лишь формула `s`, но контроль результата один и тот же.

Полезный инструмент — библиотека `ecdsa` в Python: `SigningKey.from_secret_exponent` и `verifying_key` позволяют подтвердить кандидата, а `fpylll`/Sage подключают при смещённом nonce, где задача превращается в решёточную.

## Таблица: какой nonce-дефект какой атакой ломается

| Дефект nonce | Что видно | Атака | Инструмент |
|--------------|-----------|-------|-----------|
| Повтор `k` | одинаковый `r` у двух подписей | линейное восстановление `k`, `d` | формулы, `ecdsa` |
| Смещённые старшие биты `k` | много подписей, `k` «почти» известен | hidden number problem (решётка) | fpylll, Sage |
| Усечённый `k` (мало бит) | подписи с коротким nonce | перебор + решётка | Sage |
| Предсказуемый RNG | `k` из слабого PRNG | воспроизведение `k` | `python-random` / MT19937 |
| Утечка `k` (side-channel) | тайминг/кэш-сигнал | восстановление `k` по утечке | отладчик, анализ |

Общее правило: **любая частичная информация о `k` превращается в информацию о `d`**. Чем больше подписей собрано, тем меньше нужна утечка на каждую.

## Ограничения и тонкости

- **`z` — это хэш, а не сообщение.** Для ECDSA `z` — усечённый до длины `n` хэш `H(m)`; взять `int(m,16)` вместо `H(m)` — классическая ошибка, дающая неверный ключ.
- **Модуль — порядок подгруппы `n`, а не поле `p`.** В ECDSA/DSA все деления идут `mod n`; `pow(x, -1, p)` даст мусор.
- **Общий `r` — не всегда общий `k`.** Теоретически возможна коллизия `r` при разных `k` (крайне маловероятно, но проверяйте `k` через верификацию).
- **EdDSA/Schnorr с детерминированным nonce** не имеют этой слабости; но при реализации «с нуля» без RFC 6979 даже Schnorr ломается на повторе `k`.
- **Малый порядок кривой.** Если `n` гладкий или кривая кастомная, ключ восстанавливается и без nonce-дефекта (см. `crypto-ecdsa-advanced`).

## Куда дальше

Мы разобрали схемы подписей и атаки на nonce. Дальше — атака на связанные сообщения в RSA: когда два шифротекста под одним ключом связаны линейно. В уроке **crypto-rsa-franklin-reiter** мы восстановим сообщение через gcd полиномов. А пока главное: **одинаковый `r` = одинаковый `k` = потерянный ключ; защита — RFC 6979 или EdDSA.**
