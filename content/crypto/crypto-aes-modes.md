## Вопрос, с которого всё начинается

RSA мы разобрали — он шифрует по одному большому числу. Но большинство данных шифруют **симметрично**: быстро, одним и тем же ключом туда-обратно. Главный современный симметричный шифр — AES. Сам по себе он шифрует блок ровно 16 байт. Как же им зашифровать сообщение произвольной длины? Ответ — **режим работы**, и именно в выборе режима кроются самые частые CTF-уязвимости.

## Наш пример

Зашифруем строку, в которой **есть повторы**: 32 буквы `A`, затем 16 букв `B`, затем снова 16 букв `A`. Ключ и IV фиксированы, чтобы результат был воспроизводим:

```python
from Crypto.Cipher import AES
key = b"0123456789abcdef"
iv  = b"abcdefghijklmnop"
msg = b"A"*16 + b"A"*16 + b"B"*16 + b"A"*16
```

Сначала разберёмся, что такое блочный шифр, а потом посмотрим, как разные режимы его применяют.

## Шаг 1: блочный шифр и зачем режим

AES — это функция `E(key, block) → block`, где блок всегда 16 байт. Дайте ей 16 одинаковых байт — получите 16 одинаковых байт на выходе при одном ключе. Шифр **детерминирован**: одинаковый вход → одинаковый выход.

Чтобы шифровать длинные сообщения, блоки надо как-то связать между собой. Способ связи и есть **режим**. Разные режимы дают разную безопасность — и разные атаки.

## Шаг 2: ECB — и его катастрофа

Самый простой режим — **ECB** (Electronic Codebook): каждый блок шифруется **независимо**. Проверим:

```python
ecb = AES.new(key, AES.MODE_ECB)
ct = ecb.encrypt(msg)
print(ct.hex())
```

Вывод (разбит по 16 байт для наглядности):

```
block0: 3bfd04cc0d7ed55358e2cbe19de21383
block1: 3bfd04cc0d7ed55358e2cbe19de21383
block2: 64d87547cf781a845aa4b1e907e82051
block3: 3bfd04cc0d7ed55358e2cbe19de21383
```

Блоки 0, 1 и 3 **идентичны**, потому что исходные блоки одинаковы (`A`×16). ECB ничего не скрывает о структуре данных: если в открытом тексте два блока совпали, они совпадут и в шифротексте. Для изображений это даёт пресловутую «картинку-пингвина» с угадываемыми контурами.

Это и есть первая атака: **детектор ECB**. Если в шифротексте встречаются повторяющиеся 16-байтовые блоки — режим ECB:

```python
def is_ecb(ct, bs=16):
    blocks = [ct[i:i+bs] for i in range(0, len(ct), bs)]
    return len(blocks) != len(set(blocks))

print(is_ecb(ct))   # True
```

## Шаг 3: CBC — сцепление блоков

**CBC** (Cipher Block Chaining) борется с этим так: перед шифрованием каждый блок **складывают по XOR** с предыдущим шифроблоком. Для первого блока вместо «предыдущего» используют **IV** — случайный вектор инициализации.

```
C0 = E(P0 ^ IV)
C1 = E(P1 ^ C0)
C2 = E(P2 ^ C1)
```

Проверим:

```python
cbc = AES.new(key, AES.MODE_CBC, iv)
ct2 = cbc.encrypt(msg)
print(ct2.hex())
```

Вывод:

```
0cc1b3ead44ebfa1124955e24008083a606bc2ba579e1039d0c1676427fe99271b31465e45bd3460e8b5fc7aaa1674968eb6abfaed2bb56e33486e4f5a1129b9
```

Теперь **все четыре блока разные** — повторы исчезли. Роль IV: он должен быть **случайным и уникальным**. Если IV фиксирован или предсказуем, одинаковые начала сообщений дают одинаковые начала шифротекстов, и это снова утечка.

Важный факт для будущих атак: в CBC **изменение байта в шифроблоке `Ci` предсказуемо искажает блок `Pi+1`** (потому что он XOR-ится с `Ci`). Это основа атаки **CBC bit-flipping** из урока `crypto-cbc-bitflip`.

## Шаг 4: CTR и GCM — потоковые режимы

**CTR** превращает блочный шифр в потоковый: шифруют не данные, а счётчик `nonce || counter`, получая **keystream**, и складывают его с сообщением по XOR. Это роднит CTR с OTP из урока `crypto-xor-otp` — и с его слабостями: **повтор nonce = повтор keystream = XOR двух текстов**. Отсюда атаки `crypto-iv-reuse`.

**GCM** — это CTR плюс код аутентификации (тег), который проверяет целостность. Но и у него есть своя ахиллесова пята: при повторном использовании nonce атакующий восстанавливает ключ аутентификации (forbidden attack, урок `crypto-gcm`).

Итоговая таблица режимов:

| Режим | Тип | Случайность | Слабость при ошибке |
|---|---|---|---|
| ECB | блочный | нет | повторы блоков → утечка структуры |
| CBC | блочный | IV | фиксированный IV; bit-flip |
| CTR | потоковый | nonce | повтор nonce → XOR текстов |
| GCM | потоковый+MAC | nonce | повтор nonce → восстановление ключа MAC |

## Шаг 5: как определить режим по данным

Практический алгоритм для задачи:

1. Длина кратна 16 и есть повторяющиеся блоки → **ECB**.
2. Длина кратна 16, блоков много, повторов нет → вероятно **CBC** (проверь, известен ли IV).
3. Есть отдельный тег/проверка целостности → **GCM** или CCM.
4. Данные такой же длины, как сообщение, и никакого padding → **CTR** или другой потоковый режим.

Оракул, который шифрует ваш ввод и возвращает шифротекст, — прямой путь к ECB oracle: подайте строку с повторами и посмотрите, отражаются ли они в выходе. Если сервер разрешает влиять на часть открытого текста перед секретом, повторы блоков позволяют восстанавливать секрет побайтово — это урок `crypto-ecb-oracle`. А если сервер возвращает разные ошибки при неверном padding, почти наверняка перед тобой padding oracle.

## Padding: зачем он нужен

Блочные режимы (ECB, CBC) требуют, чтобы длина сообщения была **кратна 16**. Но реальные данные почти никогда такой длины не имеют. Проблему решает **padding** — дописывание байтов до кратности блоку. Стандарт PKCS#7 устроен просто: если не хватает `k` байтов, дописывают `k` байтов, каждый со значением `k`.

```python
from Crypto.Util.Padding import pad, unpad
print(pad(b"hello", 16))         # b'hello' + 11 байт 0x0b
print(unpad(pad(b"hello", 16), 16))  # b'hello'
```

Почему это важно для атак: при расшифровке сервер должен **проверить** корректность padding. Если он по-разному отвечает на «padding неверный» и «padding верный, но данные битые», возникает **padding oracle** — и через него можно побайтово расшифровать весь текст (урок `crypto-padding-oracle`). Потоковые режимы (CTR, GCM) padding не требуют: они работают с данными любой длины. Запомни связку: есть padding и проверка его корректности — думай про padding oracle; нет padding, длина равна исходной — думай про потоковый режим и повтор nonce.

## Инструмент: openssl — крипто-швейцарский нож

`openssl` — консольный набор для шифрования, хеширования и работы с сертификатами. В лаборатории им проверяют алгоритм и параметры.

Ключи, которые пригодятся:
* `openssl enc -d -aes-128-ecb -K <hex> -in <файл>` — расшифровать файл (режим и ключ — по задаче);
* `openssl enc -d -aes-128-cbc -K <hex> -iv <hex> -in <файл>` — CBC требует IV;
* `openssl x509 -in cert.pem -text -noout` — разобрать сертификат;
* `openssl dgst -sha256 <файл>` — посчитать хеш.

### Рабочий пример (как в лаборатории)

```
$ openssl openssl enc -d -aes-256-cbc -K ... -iv ... -in cipher.bin
nto{…}
```

Подсказка из лаборатории: `openssl enc -d -aes-256-cbc -K <hex> -iv <hex> -in <файл> (вывод реального openssl)`.

## Что мы теперь знаем

- AES шифрует блок 16 байт; режим задаёт, как связать блоки.
- ECB детерминирован: одинаковые блоки → одинаковый шифротекст; ловится детектором повторов.
- CBC сцепляет блоки через XOR с IV; IV должен быть случайным.
- CTR — потоковый режим; повтор nonce катастрофичен.
- GCM = CTR + аутентификация, но и он падает при повторе nonce.
- Режим определяется по длине, повторам блоков и наличию тега.

## Куда дальше

Мы увидели, что режим решает всё. В следующем уроке **crypto-hashing** мы перейдём к односторонним функциям: разберём, почему хэш нельзя «расшифровать», как его подбирают по словарю и как атака удлинением сообщения (length-extension) ломает наивную схему `H(secret || msg)`. А пока главное: **одинаковый вход при одном ключе должен давать разный выход — иначе режим тебя выдаст**.

## Где пригодится

- **CTF** — ECB oracle, CBC bit-flip, padding oracle, IV reuse — целый пласт задач.
- **Web-пентест** — «зашифрованные» cookies и токены часто сделаны на ECB или CTR с повтором nonce.
- **Анализ протоколов** — проверка выбора режима и уникальности IV/nonce в TLS, VPN, дисках.
- **Разработка** — понимание, почему ECB запрещён, а nonce нельзя повторять.
