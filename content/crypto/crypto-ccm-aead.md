## Вопрос, с которого всё начинается

В прошлом уроке мы сломали AES-GCM, когда сервер переиспользовал nonce. Возникает
вопрос: это беда только GCM или свойство **всех** современных AEAD? И есть ли
режим, который такому не подвержен? В этом уроке мы разберём два других
популярных AEAD — **AES-CCM** и **ChaCha20-Poly1305** — и увидим, что у каждого
своя механика, но уязвимость к повтору nonce общая. А заодно проведём атаку на
**Poly1305** и подделаем тег.

## Наш пример: два перевода с одним nonce

Представим банковский сервис: он принимает зашифрованные команды перевода и
аутентифицирует их тегом Poly1305. Из-за ошибки сервер использует **один и тот же
nonce** для всех сообщений. Мы перехватили два запроса — открытые тексты обоих
известны:

```
m1 = b'transfer 100 usd'  t1 = 0x920745ff35d7b138a18ce57cd96b82e8
m2 = b'transfer 999 usd'  t2 = 0xf0f4ea85649380b4d59324ac05b20f99
```

Наша цель — подделать тег для произвольного сообщения так, чтобы сервер принял
его как подлинное. Ключа `(r, s)` у нас нет.

## Шаг 1: что такое AEAD и как устроен CCM

**AEAD** (Authenticated Encryption with Associated Data) — это режим, который
одновременно **шифрует** данные (конфиденциальность) и **аутентифицирует** их
(целостность и подлинность). На вход он получает ключ, уникальный nonce,
открытый текст, **AAD** — сопутствующие данные, которые не шифруются, но
защищаются тегом (заголовки, номер сессии, метаданные), — и выдаёт шифротекст с
тегом.

**AES-CCM** (Counter with CBC-MAC) — это сборка из двух частей обычного AES:

- **CTR** — для шифрования: генерируем keystream и складываем с текстом по XOR;
- **CBC-MAC** — для тега: цепочка, где каждый блок «впитывает» предыдущий.

Из-за последовательного CBC-MAC режим **не параллелится** при подсчёте тега и
требует двух проходов по данным. Зато он используется там, где есть аппаратный
AES: Wi-Fi (WPA2 CCMP), Bluetooth LE, Zigbee, TLS. CCM принимает nonce 7–13 байт
и тег 4–16 байт; короткий тег (например, 64 бита в WPA2) означает вероятность
подделки `2^-64` за попытку.

## Шаг 2: ChaCha20-Poly1305 и одноразовый Poly1305

**ChaCha20-Poly1305** (RFC 8439) устроен иначе: шифрует потоковым шифром
**ChaCha20** (быстрый в софте, без аппаратного AES), а аутентифицирует
**Poly1305**.

Poly1305 — это **одноразовый MAC** (one-time authenticator). У него два ключа:
`r` и `s`. Сообщение режется на блоки по 16 байт, к каждому дописывается
единичный бит, и результат считается как значение многочлена в точке `r` по
модулю простого числа `2^130 − 5`:

```
tag = ( (c1·r^q + c2·r^(q-1) + ... + cq·r) mod (2^130−5) + s ) mod 2^128
```

`r` обязательно **«зажимается»** (clamping) — определённые биты обнуляются,
чтобы арифметика была корректной. Ключ `(r, s)` для каждого сообщения выводится
из **первых 32 байт keystream ChaCha20**. Отсюда — критическое правило: **ключ
Poly1305 одноразовый**. Повтор nonce → повтор `(r, s)` → катастрофа, ровно как у
GCM.

## Шаг 3: восстанавливаем ключ r из двух тегов

Оба тега посчитаны с одним и тем же `(r, s)`. Вычтем их (по модулю `2^128`):

```
t1 − t2 ≡ f1(r) − f2(r)   (mod 2^128)
```

У нас сообщения по одному блоку, поэтому `f(r) = (m + 2^128)·r`. Разность даёт
**линейное** уравнение относительно `r`:

```
(m1 − m2)·r ≡ d   (mod 2^130 − 5)
```

где `d` — разность тегов. Осталось поделить на `(m1 − m2)` по модулю `2^130−5`.
Одна тонкость: тег усечён до 128 бит, поэтому возможны четыре значения `d`
(`+0`, `+2^128`, `+2·2^128`, `+3·2^128`) — перебираем их и берём то, при котором
оба тега сходятся. Именно так это решается в CTF-задачах «два сообщения, один
nonce».

## Шаг 4: подделываем тег

Найдя `r`, из первого тега получаем и `s = t1 − f1(r) (mod 2^128)`. Теперь для
**любого** сообщения `m'` считаем корректный тег:

```
t' = ( f(m', r) + s ) mod 2^128
```

Сервер вычислит ровно то же самое — и примет подделку.

## Полный прогон от начала до конца

```
$ python3 poly_demo.py
m1 = b'transfer 100 usd'  t1 = 0x920745ff35d7b138a18ce57cd96b82e8
m2 = b'transfer 999 usd'  t2 = 0xf0f4ea85649380b4d59324ac05b20f99
recovered r = 0x806d5400e52447c036d555408bed685
recovered s = 0x4fd6f3dd1fb1f04af6394d1fb3030e58
forged tag  = 0xf0f4ea85649380b4d59324ac05b20f99
server tag  = 0xf0f4ea85649380b4d59324ac05b20f99
ACCEPTED? True
```

Мы восстановили и `r`, и `s` (заметь: `recovered r` — это уже «зажатое» значение,
поэтому оно короче исходного секрета), затем подделали тег для нового сообщения,
и сервер его принял. Целостность AEAD сломана полностью — снова из-за повтора
nonce.

## Сравнение AEAD-режимов

| Режим | Шифрование | Аутентификация | Nonce | Особенности |
|---|---|---|---|---|
| AES-GCM | CTR | GHASH (GF(2^128)) | 96 бит | быстрый, аппаратный; nonce-reuse → forbidden attack |
| AES-CCM | CTR | CBC-MAC | 7–13 байт | два прохода, MAC не параллелится |
| ChaCha20-Poly1305 | ChaCha20 | Poly1305 | 96 бит | софтверный; nonce-reuse фатален |
| AES-GCM-SIV | CTR | POLYVAL | 96 бит | **устойчив к nonce-misuse** |
| AES-SIV | CTR | CMAC | произвольный | детерминированный, nonce-misuse-resistant |

Вывод простой: **SIV-семейство** (AES-GCM-SIV, AES-SIV) устойчиво к повтору
nonce — его берут там, где уникальность nonce не гарантирована (клонирование VM,
снапшоты, слабый RNG). GCM, CCM и ChaCha20-Poly1305 — **не устойчивы**.

## Что мы теперь знаем

- AEAD даёт и шифрование, и тег; CCM = CBC-MAC + CTR, ChaCha20-Poly1305 =
  ChaCha20 + Poly1305.
- Poly1305 — одноразовый MAC с ключом `(r, s)`; ключ выводится из keystream и
  обязан быть уникальным.
- Повтор nonce ломает конфиденциальность (XOR текстов) и целостность
  (восстановление `r`, подделка тега).
- Зная два тега с одним nonce, `r` находится из линейного уравнения по модулю
  `2^130−5`.
- Усечённые теги (как в WPA2 CCMP) дополнительно снижают стойкость к подделке.
- Если уникальность nonce не гарантируется — брать SIV-режим.

## Почему повтор nonce убивает Poly1305

Poly1305 — это **одноразовый** MAC (one-time authenticator). Его ключ `r` обновляется для каждого сообщения: `r = clamp(nonce-derived key)`. Стойкость держится на том, что при фиксированном `r` атакующий не может подделать тег, не зная ключ. Но если `r` переиспользован (а это происходит ровно при повторе nonce в ChaCha20-Poly1305), два сообщения с тегами `t1` и `t2` дают систему уравнений на полиномиальные коэффициенты, из которой `r` восстанавливается алгебраически — как в атаке на GCM при повторе nonce.

Математика: тег — это значение многочлена от сообщения, вычисленное по модулю `2^130 − 5` с коэффициентом `r`. Два тега для двух сообщений — два уравнения с одним неизвестным `r`; решаем и получаем `r`. Зная `r`, можно подделать тег для **любого** сообщения. Поэтому nonce в AEAD — это не «уникальность для красоты», а обязательное условие: один nonce = один ключ = один MAC. В ChaCha20-Poly1305 nonce и ключ задают и поток, и `r`; повтор nonce ломает сразу и конфиденциальность (XOR keystream'ов), и целостность (восстановление `r`).

Практический вывод для аудита: ищите места, где nonce генерируется счётчиком, константой или из предсказуемого источника. Именно так падают реальные системы: перезапуск процесса, сброс счётчика, RNG, возвращающий одно и то же.

## Если не сработало

- **nonce не повторяется.** Проверьте счётчики и RNG: повтор может быть редким (после reboot, при ветвлении потоков). Ищите два сообщения с одинаковым `(key, nonce)`.
- **Восстановление `r` не сходится.** Убедитесь, что сообщения действительно под одним ключом и nonce; иначе система несовместна.
- **Тег не проверяется вообще.** Тогда атака не нужна — достаточно подменить шифротекст; но это отдельная уязвимость (отсутствие integrity).
- **CCM, а не ChaCha.** В CCM повтор nonce ломает CTR-часть и CBC-MAC, но математика другая; не смешивайте формулы Poly1305 и CCM.
- **Усечённый тег.** Если тег усечён, восстановление `r` усложняется, но не исчезает — возможно, нужны дополнительные пары.

## Частые вопросы

**Как правильно выбирать nonce?** Случайно с большим запасом (96 бит) или монотонным счётчиком, который **никогда** не переиспользуется для одного ключа. XChaCha20 позволяет случайный 192-битный nonce.

**Чем CCM отличается от GCM?** CCM = CBC-MAC + CTR (два прохода, AES только для шифрования), GCM = GHASH + CTR (один проход, аппаратно быстрый). Оба ломаются при повторе nonce.

**Почему ChaCha20-Poly1305 выбирают на мобильных?** Нет аппаратного AES — ChaCha быстрее; Poly1305 дешёв. На серверах с AES-NI чаще берут AES-GCM.

## Куда дальше

Мы закрыли тему AEAD-режимов: GCM, CCM, ChaCha20-Poly1305 и их общую слабость —
nonce. В следующем уроке (`crypto-block-analysis`) мы спустимся на уровень ниже и
посмотрим, как атакуют **сам блочный шифр**, а не режим: дифференциальный и
линейный криптоанализ. А главное запомни: **AEAD защищает от подделки только пока
nonce уникален; повтор nonce — это конец и для GCM, и для CCM, и для Poly1305**.

## Где пригодится

- **CTF crypto** — задачи на AEAD с повторным nonce и подделкой тегов.
- **Bug bounty / пентест** — анализ протоколов на nonce-ошибки.
- **Аудит кода / разработка** — выбор AEAD и корректная генерация nonce.
- **SOC / IR** — понимание инцидентов с nonce reuse (снапшоты VM, слабый RNG).
- **Исследования** — современные AEAD-конструкции (SIV, OCB).
