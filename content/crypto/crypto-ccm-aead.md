## Что такое AEAD

**AEAD** (Authenticated Encryption with Associated Data) — режим, который одновременно обеспечивает **конфиденциальность** (шифрование) и **целостность/подлинность** (тег). Он принимает:

- `key` — секретный ключ,
- `nonce` — уникальное (но не секретное) значение,
- `plaintext` — данные для шифрования,
- `AAD` (Associated Data) — данные, которые НЕ шифруются, но аутентифицируются (заголовки, номера пакетов, метаданные),
- `tag` — тег аутентификации, вычисляемый по `ciphertext` и `AAD`.

Правильное использование AEAD — современный стандарт. Но у каждого режима есть свои границы и характерные ошибки, которые и становятся основой CTF-задач.

## CCM: CBC-MAC + CTR

CCM (Counter with CBC-MAC, RFC 3610) — это «сборка» из двух примитивов блочного шифра:

- **Режим CTR** — для шифрования (потоковый, без padding).
- **CBC-MAC** — для аутентификации, но не «сырой», а с кодированием длины (`10*` padding, аутентификация длины и AAD).

Схема обработки: сначала вычисляется тег `T = CBC-MAC(N, AAD, P)`, затем всё (включая тег) шифруется в CTR. CCM используется в Wi-Fi (WPA2 CCMP), Bluetooth LE, TLS (AES-CCM), Zigbee.

**Особенности CCM:**

- **Не параллелится** для шифрования при вычислении MAC (CBC-MAC последовательный), хотя CTR-часть параллелизуема.
- Требует **двух проходов** по данным (один для MAC, один для CTR).
- Тег короткий (обычно 8 или 16 байт).
- Nonce и длина должны быть известны заранее (кодируются в первом блоке).

```python
from Crypto.Cipher import AES
# AES-CCM в pycryptodome
key = b"0123456789abcdef"
nonce = b"0123456789ab"          # 7-13 байт
cipher = AES.new(key, AES.MODE_CCM, nonce=nonce)
cipher.update(b"header")          # AAD
ct, tag = cipher.encrypt_and_digest(b"secret message")
# проверка
c2 = AES.new(key, AES.MODE_CCM, nonce=nonce)
c2.update(b"header")
pt = c2.decrypt_and_verify(ct, tag)
```

## ChaCha20-Poly1305

ChaCha20-Poly1305 (RFC 8439) — AEAD, где:

- **ChaCha20** — потоковый шифр (ARX: add-rotate-xor) для шифрования.
- **Poly1305** — **одноразовый** MAC (one-time authenticator) с ключом `(r, s)`.

Это стандарт TLS 1.3, WireGuard, SSH, Google QUIC. Устройство Poly1305 важно: это полиномиальный MAC по простому числу `2^130 − 5`.

```
tag = ((c1·r^q + c2·r^(q-1) + ... + cq·r) mod (2^130−5) + s) mod 2^128
```

где `r` — ключ (обязательно с «зажатыми» битами), `s` — второй ключ, `c_i` — блоки сообщения. Ключ `(r, s)` выводится из **первых 32 байт keystream ChaCha20** для данного nonce. Отсюда критическое правило: **Poly1305-ключ одноразовый**. Повтор nonce → повтор ключа `(r, s)` → катастрофа.

## Атака 1: повтор nonce

Если два сообщения зашифрованы ChaCha20-Poly1305 с одним `(key, nonce)`:

1. Keystream совпадает → `C1 ⊕ C2 = P1 ⊕ P2` (утечка XOR текстов, как в CTR).
2. **Ключ Poly1305 `(r, s)` совпадает** для обоих тегов. Зная один из открытых текстов (или угадав его), можно восстановить `r`, а затем **подделывать теги для произвольных сообщений** — полный взлом целостности.

Восстановление `r`: имея два тега `t1, t2` и соответствующие многочлены `f1(r)`, `f2(r)`, получаем `t1 − t2 = f1(r) − f2(r) (mod 2^130−5)`. Это полиномиальное уравнение относительно `r`, которое решается (малый degree, можно перебором/факторизацией). Именно так работает **forgery на Poly1305 при nonce reuse**.

## Атака 2: подделка тега при утечке `r` или `s`

- Если атакующий знает `s` (например, утечка через побочный канал), он может подделывать теги, зная `r`.
- Если известен `r`, для нового сообщения вычисляется корректный тег.
- Poly1305 **не защищает** от перебора, если `r` слаб (реализация без зажатия битов); но в стандарте биты зажимаются.

## Атака 3: слабые/усечённые теги

Некоторые реализации усекают тег (например, 64 бита). Тогда вероятность случайной подделки — `2^-64`, а brute-force-подделка становится возможной при достаточном числе запросов. Для CCM с 8-байтным тегом это реальная проблема в беспроводных протоколах.

## Сравнение AEAD-режимов

| Режим | Шифрование | Аутентификация | Nonce | Особенности |
|---|---|---|---|---|
| AES-GCM | CTR | GHASH (GF(2^128)) | 96 бит | быстрый, аппаратный; nonce-reuse → forbidden attack |
| AES-CCM | CTR | CBC-MAC | 7-13 байт | два прохода, без параллелизма MAC |
| ChaCha20-Poly1305 | ChaCha20 | Poly1305 | 96 бит | софтверный, быстрый без AES-NI; nonce-reuse фатален |
| AES-GCM-SIV | CTR | POLYVAL | 96 бит | **устойчив к nonce-misuse** |
| AES-SIV | CTR | CMAC | произвольный | детерминированный, nonce-misuse-resistant |

Ключевой вывод: **SIV-семейство** (AES-GCM-SIV, AES-SIV) устойчиво к повтору nonce — это важно там, где нельзя гарантировать уникальность nonce (VM-снапшоты, слабый RNG, клонирование). GCM/CCM/ChaCha20-Poly1305 — **не устойчивы**.

## Практический пример: восстановление `r` при nonce reuse

```python
# Упрощённо: два тега с одним (r,s) для разных сообщений
# t = (poly(msg, r) + s) mod 2^128, где poly — многочлен mod (2^130-5)
P = (1 << 130) - 5

def poly_eval(blocks, r):
    acc = 0
    for b in blocks:
        acc = (acc + int.from_bytes(b,'little')) * r % P
    return acc

# Зная t1, t2, msg1, msg2 (открытый текст известен), решаем
# poly_eval(m1,r) - poly_eval(m2,r) = t1 - t2 (mod 2^128)
# -> полином degree 1: (A1-A2)*r + (B1-B2) = 0 mod P
# откуда r = -(B1-B2) * inverse(A1-A2, P) mod P
```

На практике для nonce-reuse в Poly1305 решают именно так — через разность многочленов и обратный элемент по модулю `2^130−5`. Это стандартный приём CTF-задач «два сообщения, один nonce».

## Частые ошибки

- **Повтор nonce.** Убивает и конфиденциальность (XOR), и целостность (forgery).
- **Не проверять тег до использования данных.** Сначала `decrypt_and_verify`, потом доверять.
- **Использовать один ключ для AEAD и чего-то ещё** без разделения (key separation).
- **Усечённые теги** там, где важна стойкость к подделке.
- **Считать, что «AEAD = защищено от всего».** Nonce-misuse, утечки ключей и слабый RNG остаются.
- **CCM с маленьким nonce + большим числом сообщений** — риск повторной генерации nonce.

## Управление nonce: как не повторять

Главная практическая задача AEAD — гарантировать уникальность nonce. Варианты:

- **Счётчик (детерминированный):** nonce = инкрементирующийся счётчик, сохраняемый на диске/в БД. Уникален, пока счётчик не сбросится. Опасность — рестарт/восстановление из бэкапа сбрасывает счётчик → повтор.
- **Случайный (random 96 бит):** риск коллизии растёт как `q²/2^97` при `q` сообщениях (birthday). Для `q = 2^32` сообщений вероятность повтора ~`2^-33` — приемлемо, но не бесконечно.
- **XChaCha20 (192-бит nonce):** практически исключает случайный повтор даже при больших объёмах.
- **Nonce-misuse-resistant (SIV):** AES-GCM-SIV выводит nonce детерминированно из содержимого, поэтому повтор «случайного» nonce не фатален.

Опасные сценарии из практики: **клонирование VM** (RNG-состояние дублируется → одинаковые «случайные» nonce), **снапшоты/бэкапы** (счётчик откатывается), **форк процессов** (дети наследуют состояние RNG). Именно так случались реальные инциденты с GCM/ChaCha20.

## AAD и порядок проверки

AAD (Associated Data) — это данные, которые аутентифицируются, но не шифруются: номера пакетов, версии протокола, ID сессии, заголовки. Правило: **всё, что влияет на смысл сообщения, должно быть в AAD**. Если ID сессии не входит в тег, атакующий может переставить зашифрованные полезные данные между сессиями — тег совпадёт, потому что он не покрывает сессию. Типичная ошибка — аутентифицировать только тело, забыв про метаданные. Второе правило: **проверяйте тег до использования данных** — `decrypt_and_verify` (не `decrypt`, затем `verify`). Многие библиотеки по умолчанию именно так и делают, но при ручной реализации порядок легко перепутать, и это открывает утечки (аналог padding oracle).

## Итог: как выбирать AEAD

Для нового кода: **AES-GCM** (если есть AES-NI) или **ChaCha20-Poly1305** (софтверно), nonce 96 бит уникальный. Если уникальность nonce не гарантируется (репликация, снапшоты, слабый RNG) — **AES-GCM-SIV**. Для ресурсо-ограниченных устройств с AES-ускорителем — **AES-CCM**. Никогда не собирайте шифрование+MAC вручную: используйте готовый AEAD-API.

## CCM на практике: параметры и ловушки

CCM принимает nonce длиной 7–13 байт (чем короче nonce, тем больше места под длину сообщения). Длина тега — 4, 6, 8, 10, 12, 14 или 16 байт. В WPA2-CCMP используется 48-битный packet number как nonce и 8-байтный тег (MIC). Короткий тег (64 бита) означает, что вероятность подделки `2^-64` за попытку — а для беспроводных атак с миллионами попыток это значимо. Поэтому в задачах с CCMP/Bluetooth ищите и **усечённый тег**, и **повтор nonce** (сброс packet number при переассоциации — реальный вектор в WPA2).

## Как не застрять

- **Ищите повтор nonce.** Это атака №1 для GCM/CCM/ChaCha20-Poly1305.
- **Сравнивайте два шифротекста:** XOR даёт `P1⊕P2` при совпадении keystream.
- **Зная один открытый текст** — восстановите keystream, расшифруйте второй.
- **Для forgery** нужен либо ключ Poly1305 `r`, либо утечка `s`.
- **Проверьте длину тега.** Усечённые теги — путь к подделке перебором.
- **Если nonce-misuse-resistant нужен** — смотрите на SIV-режимы.
