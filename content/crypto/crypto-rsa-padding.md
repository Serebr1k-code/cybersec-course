## Зачем нужен padding

Textbook RSA детерминирован и мультипликативен. Чтобы получить семантическую стойкость (одинаковые сообщения дают разные шифротексты) и устранить мультипликативные атаки, перед шифрованием сообщение **дополняют** (padding) до длины модуля. Стандарты: **PKCS#1 v1.5** (старый) и **OAEP** (современный, безопасный).

Правильное использование padding критично: неправильная реализация приводит к padding oracle атакам (Блейхенбахер, Manger).

## PKCS#1 v1.5

Структура закодированного сообщения `EM` (для `k`-байтного модуля):

```
EM = 0x00 || 0x02 || PS || 0x00 || M
```

где `PS` — случайные **ненулевые** байты (не менее 8). Первый байт `0x00` обеспечивает, что число `EM < n`. При расшифровке проверяют: первый байт `0x00`, второй `0x02`, наличие `0x00`-разделителя не раньше 8-го байта.

**Слабость:** проверка padding — это **оракул**. Если сервер по-разному реагирует на «padding корректен» и «некорректен» (по коду ошибки, времени, поведению), применима атака Блейхенбахера.

## OAEP (Optimal Asymmetric Encryption Padding)

OAEP использует хэш-функцию и **MGF** (mask generation function) для рандомизации:

```
EM = 0x00 || maskedSeed || maskedDB
```

где `maskedDB` содержит хэш сообщения и нулевую строку, а маскирование — через MGF от seed и DB. OAEP **доказуемо** безопасен (IND-CCA2) при правильных предположениях. Для OAEP существует **свой** oracle — Manger (см. `crypto-rsa-oracle`), но он требует другой утечки (старший байт == 0).

## Атака Блейхенбахера (million message)

Если сервер (oracle) различает «padding корректен» и «некорректен», атакующий восстанавливает `M` за ~`10^6` запросов:

1. Выбираем множители `s`, чтобы `(c·s^e) mod n` при расшифровке давало валидный padding.
2. Каждый «валидный» ответ сужает интервал `[a, b]`, в котором лежит `M` (начинается с `0x00 0x02`).
3. Повторяем с новыми `s` — интервал сжимается до одного значения.

Ключевая идея: padding-проверка — это утечка **одного бита** («структура верна?») на запрос. Как и parity oracle, это позволяет **бинарно сужать** интервал возможных `M`. Формально — вариант chosen-ciphertext атаки.

```python
# Схема (упрощённо)
# B = 2^(8*(k-2)) для k-байтного модуля
# Начальный интервал: [2B, 3B-1]
# Шаг 1: ищем s с валидным padding -> обновляем интервал
# Шаг 2: уточняем s в узком диапазоне, снова сужаем
# Шаг 3: повторяем, пока a == b
# При a == b: M = a
```

Полная реализация — сотни строк; на практике берут готовые скрипты (`robots.txt`/`tlsfuzzer`/Bleichenbacher PoC).

## ROBOT и реальные системы

**ROBOT (Return Of Bleichenbacher's Oracle Threat, 2017)** — набор реальных реализаций TLS/почты/API, всё ещё уязвимых к вариантам Блейхенбахера (разные коды ошибок, разные тайминги). Проверка:

```bash
python3 robot-detect.py -H target.example.com
# или tlsfuzzer
```

Признак уязвимости: сервер по-разному реагирует на некорректный padding и на прочие ошибки расшифровки.

## Варианты

- **Marvin (2023)** — timing-вариант на OpenSSL RSA, восстановление сообщения по времени.
- **Klima / ORACLE-варианты** — модификации при разных проверках.
- **Интерактивные версии** — когда oracle доступен только по таймингу, а не по коду ошибки.
- **Manger** — аналог для OAEP.

## Распознавание

**Признак CTF:**

- сервер расшифровывает RSA и отвечает «padding valid/invalid» (или разным временем);
- дано `n, e`, целевой `c`;
- сказано «oracle», «PKCS#1 v1.5», «million message».

## Разобранный пример

```python
# oracle(c) -> True если расшифровка даёт валидный PKCS#1 v1.5 padding
# 1) найти s0: oracle((c * s^e) % n) == True
# 2) инициализировать интервал [2B, 3B-1]
# 3) итеративно сужать интервал новыми s
# 4) при a == b: M = a
# Проверка: pow(M, e, n) == c (с точностью до padding)
```

Для отладки используйте локальный сервер-заглушку с известным ключом.

## Частые ошибки

- **Нет oracle.** Атака требует различения «padding valid/invalid».
- **Шумный/нестабильный oracle.** Тайминги плывут — нужна статистика.
- **Неправильные границы интервала.** `B = 2^(8*(k-2))` для `k`-байтного модуля.
- **Мало запросов.** Нужно ~`10^6`.
- **Считать OAEP неуязвимым.** Для OAEP есть Manger.
- **Игнорировать constant-time.** Разные ответы = oracle.

## PKCS#1 v1.5 для подписи (RSASSA)

Для подписи используется **другая** структура (`EMSA-PKCS1-v1_5`):

```
EM = 0x00 || 0x01 || 0xFF...FF || 0x00 || DigestInfo(hash)
```

`DigestInfo` включает OID хэш-алгоритма. Здесь нет случайности (подпись детерминирована). Опасность — **Bleichenbacher-подпись** и атаки на слабую проверку: если верификатор не проверяет строго структуру `DigestInfo`, можно подделать подпись (подсунуть произвольный хэш). Реальные баги: отсутствие проверки padding, парсинг `DigestInfo` с нестрогим поиском.

```python
# Проверка: digest внутри EM должен соответствовать OID
# Уязвимые реализации ищут "\x00" и берут всё после, не проверяя OID
```

## Оракул по времени (timing) и constant-time

Даже если код ответа одинаков, **время обработки** может различаться: ветвление `if padding_valid` создаёт timing-сигнал. Для устранения:

- Вычислять проверку **всегда полностью** (без early-return).
- Использовать **constant-time** сравнения и арифметику.
- Возвращать единый ответ об ошибке.

Известные timing-атаки: **Marvin** (OpenSSL RSA, 2023) восстанавливала сообщение по времени расшифрования за миллионы запросов. Это показывает, что «constant-time» — не формальность.

## Bleichenbacher на практике: шаги

1. **Соберите oracle.** Определите, как сервер различает padding (код, время, длина ответа).
2. **Blinding.** Если `c` не даёт валидный padding, найдите `s0`.
3. **Итерации.** Сужайте интервалы по алгоритму (см. `crypto-rsa-bleichenbacher`).
4. **Сходимость.** Когда `a == b`, `M` найден.
5. **Извлечение.** Уберите padding, получите сообщение.

Инструмент — готовые PoC (например, на основе `python-rsa-bleichenbacher` или скриптов из ROBOT).

## Почему OAEP безопасен

OAEP доказуемо IND-CCA2 при условии, что базовая перестановка RSA — однонаправленная, а хэш/MGF — «случайные оракулы». Структура:

```
DB = lHash || PS || 0x01 || M
maskedDB = DB ⊕ MGF(seed)
maskedSeed = seed ⊕ MGF(maskedDB)
EM = 0x00 || maskedSeed || maskedDB
```

Любое изменение `EM` «лавинно» меняет `maskedSeed` и `DB`, поэтому структура проверяется целиком. Но **Manger** атакует OAEP через oracle старшего байта (см. `crypto-rsa-oracle`), если реализация различает «первый байт 0».

## Как не застрять

- **Ищите разницу в ответах/времени** на неверный padding.
- **Определите схему** (v1.5 или OAEP).
- **Для v1.5** — Блейхенбахер; **для OAEP** — Manger.
- **Возьмите готовый PoC**, не пишите с нуля.
- **Соберите статистику** при timing-oracle.
- **Проверяйте сходимость** (`pow(M,e,n)==c`).
