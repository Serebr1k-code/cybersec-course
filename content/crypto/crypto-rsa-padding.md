## Вопрос, с которого всё начинается

Textbook RSA из прошлого урока был детерминирован: одно и то же сообщение всегда давало один и тот же шифротекст, и его можно было «перемножать». Чтобы это исправить, перед шифрованием сообщение **дополняют** (padding) до размера модуля. Вопрос новичка: «Раз padding добавлен, чтобы всё было безопасно, как его отсутствие-то ломают?» Ответ: ломает не сам padding, а **реакция сервера** на неправильный padding. Проследим это на живом оракуле.

## Наш пример

У нас есть сервер: он принимает шифротекст `c`, расшифровывает его закрытым ключом RSA и проверяет padding по схеме PKCS#1 v1.5. Мы знаем только публичный ключ `(n, e)` и то, что на неверный padding сервер отвечает ошибкой, а на верный — молчит. Прогоним против него атаку Блейхенбахера и достанем исходное сообщение, ничего не зная о закрытом ключе.

## Шаг 1: как выглядит PKCS#1 v1.5

Закодированное сообщение `EM` для `k`-байтного модуля собирается так:

```
EM = 0x00 || 0x02 || PS || 0x00 || M
```

где `PS` — не менее 8 **ненулевых** случайных байт. Первый байт `0x00` гарантирует, что число `EM < n`. При расшифровке проверяют: первый байт `0x00`, второй `0x02`, и что разделитель `0x00` стоит **не раньше** 10-го байта (после минимум 8 байт `PS`). Реализуем ровно эту проверку как оракул:

```python
def oracle(c):
    m = pow(c, d, n)              # сервер знает d, мы — нет
    b = m.to_bytes(k, "big")
    if b[0] != 0 or b[1] != 2:
        return False
    return b.find(b"\x00", 2) >= 10
```

## Шаг 2: проверка padding — это оракул

Ключевое наблюдение: функция `oracle` возвращает **один бит** — «padding структурно верен или нет». Этого бита достаточно, чтобы восстановить сообщение. Проверим, что наш легитимный шифротекст проходит проверку:

```python
print(oracle(c))
```

```
True
```

Теперь трюк. Если умножить шифротекст на `s^e mod n`, то после расшифровки мы получим `m·s mod n` (потому что `(c·s^e)^d = c^d·s = m·s`). Перебирая `s`, мы получаем «повёрнутые» версии `m`, про каждую из которых сервер сообщает один бит: попало ли `m·s mod n` в диапазон `[2B, 3B−1]`, где `B = 2^(8(k−2))`. Значит, каждый запрос сообщает, **в каком интервале** относительно `n` лежит `m·s mod n`.

## Шаг 3: как сужается интервал

Обозначим `B = 2^(8(k−2))`. Валидный padding означает `2B ≤ m·s mod n ≤ 3B−1`. Атакующий хранит множество интервалов `M`, в которых может лежать `m`. Начинаем с `M = {[2B, 3B−1]}`. Смысл в том, что «валидный padding» — это не просто флаг, а **утверждение о величине** `m·s mod n`: он лежит в узкой полосе шириной `B` из `n`. Каждый запрос добавляет одно такое ограничение, и вместе они отсекают всё, кроме истинного `m`. Затем:

1. Ищем `s`, при котором `oracle(c·s^e mod n)` истинно.
2. Для каждого интервала `[a, b]` и каждого `r` вычисляем пересечение `[a,b]` с `[(2B + r·n)/s, (3B−1 + r·n)/s]` — это уточнённый интервал.
3. Повторяем, пока в `M` не останется **одно** число: `a == b`, и тогда `m = a`.

Каждый «валидный» ответ отсекает часть пространства — это бинарное сужение, как в parity oracle. Схема шага уточнения выглядит так:

```python
for a, b in M:
    rlo = ceildiv(a*s - 3*B + 1, n)
    rhi = (b*s - 2*B) // n
    for r in range(rlo, rhi + 1):
        lo = max(a, ceildiv(2*B + r*n, s))
        hi = min(b, (3*B - 1 + r*n) // s)
        if lo <= hi: newM.append((lo, hi))
```

## Шаг 4: полный прогон

Запускаем цикл против нашего оракула (ключ маленький, 256 бит, — чтобы прогон занял секунды):

```python
m, rounds, calls = attack(c)
print("rounds:", rounds, "oracle calls:", calls)
print("recovered:", m.to_bytes(k, "big"))
```

```
rounds: 214 oracle calls: 267680
recovered: b'\x00\x02\xbe\xa7\xed\x88\x08\xd8x\xc7\xf2@\xa7\x0e\xe7)\x1d`y\x00flag{oracle}'
```

Сообщение восстановлено: `flag{oracle}`. Обратите внимание на масштаб — **267 680 запросов** к оракулу. Для настоящего 2048-битного ключа счёт идёт на миллионы, отсюда название **million message attack**. И всё это — без единого бита закрытого ключа, только по факту «padding верен / неверен». Важно, что атакующему не нужен ни закрытый ключ, ни даже знание сообщения: достаточно того, что сервер честно отвечает, верна ли структура. Любая реализация, которая обрабатывает неверный padding иначе, чем верный, превращается в такой оракул.

## Шаг 5: OAEP и его собственный оракул

**OAEP** (Optimal Asymmetric Encryption Padding) — современная схема. Вместо предсказуемой структуры она использует хэш и **MGF** (функцию генерации маски), перемешивая сообщение со случайным seed. Изменение любого байта «лавинно» меняет всю структуру, поэтому проверить её по частям нельзя, и OAEP доказуемо стоек (IND-CCA2) при стандартных предположениях.

Но и у OAEP есть свой оракул — **Manger**: если реализация различает «первый байт расшифровки равен нулю» и «не равен», сообщение восстанавливается аналогичным сужением интервала. Мораль: безопасность даёт не название схемы, а **отсутствие утечки одного бита**.

## Шаг 6: подписи и constant-time

Для **подписи** PKCS#1 v1.5 использует другую структуру (`EMSA-PKCS1-v1_5`):

```
EM = 0x00 || 0x01 || 0xFF...FF || 0x00 || DigestInfo(hash)
```

Здесь нет случайности — подпись детерминирована. Опасность в нестрогой проверке: если верификатор ищет `0x00` и берёт всё после него, не сверяя `DigestInfo` и OID, подпись можно подделать.

И отдельно — **время**. Даже если код ответа одинаков, ветвление `if padding_valid` создаёт timing-сигнал: неверный padding обрабатывается чуть быстрее. Лечится так: проверять **всегда полностью** (без early-return), использовать constant-time сравнения и возвращать единый ответ об ошибке. Реальность сурова: атака **Marvin** (2023) восстанавливала сообщения OpenSSL именно по времени.

## Что мы теперь знаем

- Padding устраняет детерминизм и мультипликативность textbook RSA.
- **PKCS#1 v1.5**: `0x00 0x02 PS 0x00 M`; проверка структуры — это **оракул**.
- **Блейхенбахер**: каждый запрос даёт один бит («padding верен?»), интервалы сужаются до `m`; ~`10⁶` запросов.
- **OAEP** устойчив, но у него свой оракул — **Manger**.
- Для подписи структура другая (`EMSA`), опасна нестрогая проверка `DigestInfo`.
- Защита: **constant-time**, единый ответ, переход на OAEP.

## Куда дальше

Мы превратили одну ошибку реализации — «разный ответ на плохой padding» — в полное восстановление сообщения. Дальше — родственная атака на **OAEP**: в уроке **crypto-rsa-oracle** мы разберём оракул Manger и научимся отличать его от Блейхенбахера по тому, какой именно бит утекает. А пока главное: **padding безопасен только тогда, когда сервер не различает верный и неверный padding ни по коду, ни по времени.**
