## Вопрос, с которого всё начинается

Хэш с `n`-битным выходом имеет `2^n` возможных дайджестов. Казалось бы, чтобы найти коллизию, нужно перебрать порядка `2^n` сообщений. Но это не так — и в этом главная контринтуитивная идея криптографии хэшей. Из-за **парадокса дней рождения** коллизия находится уже среди `~2^(n/2)` значений. Для 128-битного хэша это `2^64` — граница, которую современные кластеры проходят. Отсюда правило: для `k`-битной стойкости нужен выход `2k` бит.

## Наш пример: 32-битный хэш

`birthday.py` задаёт детерминированную 32-битную функцию

```
H(x) = ((x·2654435761) ⊕ (x >> 13)) mod 2^32
```

и ищет коллизию, генерируя случайные `x` и запоминая дайджесты. При 32-битном выходе ожидаемое число запросов — `~2^16 = 65536`. Прогоним:

```
$ python3 birthday.py
queries to find a collision: 62512 (~2^16 = 65536 expected)
H(505869112) == H(2097928481) == 317411471 : True
birthday bound ~2^(n/2) confirmed: True
flag: nto{b1rthd4y_c0ll1s10n_2_p0w_n_0v3r_2}
```

62 512 запросов — чуть меньше ожидаемых 65 536. Это и есть birthday-граница в действии: мы нашли коллизию не за `2^32`, а за `2^16`.

## Шаг 1: парадокс дней рождения

В классе из 23 человек вероятность совпадения дней рождения > 50%. Причина: пар не 23, а `23·22/2 = 253`, и каждая может совпасть. Аналогично, если мы сгенерировали `q` значений `n`-битного выхода, число **пар** ~`q²/2`. Когда `q²/2 ≈ 2^n`, появляется коллизия, то есть `q ≈ 2^(n/2)`. Отсюда — квадратичный выигрыш по сравнению с наивными `2^n`.

## Шаг 2: meet-in-the-middle и структура

Birthday-атаку часто называют meet-in-the-middle, потому что мы «идём с двух сторон»: генерируем значения и проверяем, не встречалось ли такое же раньше (или ищем пересечение двух списков). Есть две реализации:

- **Хранение в таблице**: генерируем `q` значений, пишем дайджест→вход в хэш-таблицу, ищем повтор. Память `O(q)`, время `O(q)`.
- **Rho-метод Флойда**: без памяти, «черепаха и заяц» по детерминированной цепочке `x → H(x)`, находят цикл за `O(q)` времени и `O(1)` памяти.

Наш `birthday.py` использует первый вариант — таблицу.

## Шаг 3: rho-метод без памяти

Rho-метод полезен, когда памяти мало. Определяем функцию перехода `g(x) = H(x)` и идём по цепочке `x0, g(x0), g(g(x0)), ...`. Цепочка конечна (выход `n` бит), значит, зацикливается — и вход в цикл даёт коллизию `H(a) = H(b)` с `a ≠ b`. «Черепаха и заяц» находят цикл за `O(2^(n/2))` шагов без хранения таблицы. Это стандарт для атак на усечённые хэши в CTF.

## Шаг 4: сколько бит достаточно

Практические следствия. Если выход хэша 64 бита, birthday-атака стоит `2^32` — минуты на одном компьютере. 80 бит → `2^40` — часы. 128 бит → `2^64` — годы на кластере. 160 бит (SHA-1) → `2^80` — считалось недостижимым, но структурные атаки (chosen-prefix) сломали SHA-1 дешевле. Отсюда современный стандарт: **не меньше 256 бит** для долгоживущих систем. И помните: это про **коллизии**; для preimage стойкость `2^n`, поэтому 128-битный выход всё ещё «ок» для многих задач.

## Шаг 5: birthday не только для хэшей

Парадокс дней рождения универсален. Он бьёт: усечённые MAC-и, «одноразовые» токены с коротким случайным полем, выбор nonce случайно из маленького пространства, генераторы сессионных ID. Любое место, где два случайных `n`-битных значения могут совпасть, требует `2^(n/2)` попыток, а не `2^n`. Это частая ошибка в реализациях: «мы используем 32-битный случайный токен, значит перебор `2^32`» — нет, коллизию найдём за `2^16`.

## Если не сработало

Если коллизия не находится быстро, проверьте: (1) не инъективна ли функция — для перестановки коллизий нет вообще; (2) достаточно ли широкий выход — если 64+ бит, `2^32` запросов могут не уложиться в бюджет; (3) правильно ли выбрано пространство входов. И не путайте: birthday-атака даёт **любую** коллизию, а не second-preimage для заданного сообщения — для второго нужно `2^n`.

## Meet-in-the-middle для хэшей

Meet-in-the-middle (MITM) применим к конструкциям с двумя независимыми частями: если функция `H = f(x) ⊕ g(y)` или результат зависит от двух ключей независимо, можно перебрать каждую часть отдельно (2^n + 2^n вместо 2^2n). Для хэшей это работает на **усечённых** версиях или на специальных конструкциях.

```text
H(x,y) = f(x) + g(y): store f(x) for all x; find y s.t. g(y) matches -> 2^n
```

Классический пример — атака на 2-key triple-DES, а также на некоторые хэш-схемы с двумя «половинами».

## Практика: где применимо

Применимо, когда: (1) функция разложима на две независимые части, (2) есть достаточно памяти для таблицы, (3) пространство каждой части перебираемо. Для хэшей это значит — усечённый выход, слабое перемешивание или специальная конструкция. Инструменты: скрипты на Python/C, хэш-таблицы.

```python
table = {f(x): x for x in range(2**n)}
for y in range(2**n):
    if g(y) in table: return table[g(y)], y
```

Практика: оцени, разложима ли функция; если да — MITM снижает сложность вдвое по показателю.

## Практика и защита

Вывод: MITM — про структуру, а не про слабость отдельной функции. Для устойчивости хэш должен перемешивать все входы зависимо (без «двух половин»). Для аудита: если встречается самописная хэш-схема с двумя частями — проверь её на MITM.

```text
defense: full diffusion; no separable halves
```

Это одна из причин, почему стандартные хэши используют полное перемешивание на каждом раунде.

## Дополнительно: MITM в блочных шифрах

Классический MITM — атака на 2-key triple-DES: перебирают ключ `K1` и `K2` независимо (2^56 + 2^56 вместо 2^112). Для хэшей MITM применяют к конструкциям с разложимым выходом. Практика: оцени разложимость и доступную память; MITM требует хранения таблицы.

```text
2-key 3DES: MITM 2^56 + 2^56 << 2^112
```

Вывод: MITM показывает, почему независимые ключи не удваивают стойкость линейно.

## Что мы теперь знаем

- Birthday: коллизия находится среди `~2^(n/2)` значений.
- Причина — число пар растёт квадратично.
- Meet-in-the-middle хранит таблицу, rho-метод — нет.
- Для `k`-битной стойкости нужен выход `2k` бит.
- 32-битный выход ломается за `2^16`.
- Birthday бьёт любые короткие случайные поля, не только хэши.

## Rho-метод без памяти: как это работает

Табличный вариант birthday-атаки требует `O(2^(n/2))` памяти — для 128-битного хэша это неподъёмно. Спасает **rho-метод Флойда** («черепаха и заяц»). Определим детерминированную функцию перехода `g(x) = H(x)`, где `H` — целевой хэш (можно зафиксировать часть входа, чтобы `g` отображала `n`-битные значения в себя). Идём по цепочке `x0 → g(x0) → g(g(x0)) → ...`. Поскольку пространство значений конечно (размер `2^n`), цепочка обязательно зациклится, и вход в цикл даёт коллизию: два разных `x`, попавших в одну точку.

Алгоритм «черепаха и заяц»: черепаха делает один шаг, заяц — два. Когда они встретятся (внутри цикла), мы нашли цикл. Затем второй проход: сбрасываем черепаху в начало и идём с той же скоростью, что заяц, — точка встречи и есть вход в цикл. Наконец, находим два разных предшественника этой точки: это и есть коллизия `H(a) = H(b)`. Память — `O(1)`, время — `O(2^(n/2))`. Именно так ломают усечённые хэши на CTF: если в задаче хэш обрезан до 48-64 бит, rho-метод находит коллизию за минуты на одном компьютере. Важный нюанс: `g` должна быть «случайной», иначе циклы могут быть короткими или отсутствовать.

На практике rho-метод удобен ещё и тем, что легко параллелится: запускают несколько «черепах» с разных стартовых точек на разных ядрах, и коллизия находится ещё быстрее. Это стандартный подход в инструментах для поиска коллизий на усечённых хэшах (например, в задачах, где выход обрезан до 40-56 бит). Единственное требование — функция перехода должна быть детерминированной и «перемешивающей»; если она оставляет много коротких циклов, метод может зациклиться раньше времени, и тогда помогает рандомизация старта.

Дополнительно проверь, не комбинируются ли два независимых хэша/ключа в одну конструкцию: именно такие «двойные» схемы чаще всего уязвимы к meet-in-the-middle.

Для отчёта опиши, какие конструкции разложимы на независимые части, и оцени, снижает ли это эффективную стойкость вдвое по показателю.

Практический вывод: MITM снижает сложность для конструкций с независимыми частями; избегай «двойных» схем и используй полное перемешивание.

Проверь также, не хранятся ли ключи/состояния в предсказуемом виде, что облегчает построение таблицы MITM и снижает практическую сложность атаки.

Для отчёта приведи оценку сложности MITM в сравнении с полным перебором, чтобы показать реальное снижение стойкости.

Практический вывод: избегай конструкций с независимыми частями и используй полное перемешивание — это фундаментальная причина, по которой стандартные хэши перемешивают всё на каждом раунде.
