## Вопрос, с которого всё начинается

Приложение выдаёт cookie вида `user=guest&admin=false` и рядом «подпись» —
`sha256(secret + cookie)`, где `secret` знает только сервер. Идея: подделать
cookie нельзя, ведь для новой подписи нужен секрет. Вопрос: действительно ли
нельзя? Можем ли мы **достроить** сообщение так, чтобы подпись осталась
валидной, не зная `secret`?

Оказывается, для хэшей семейства **Merkle–Damgård** (MD5, SHA-1, SHA-256) —
можем. Атака называется **length extension**, и ниже мы проведём её на реальном
SHA-256, реализовав хэш с нуля.

## Наш пример: подпись `sha256(secret || msg)`

Сервер проверяет целостность так:

```python
secret = b"supersecretkey!!"          # 16 байт, знает только сервер
msg    = b"user=guest&admin=false"
sig    = sha256(secret + msg)         # это и есть «MAC»
```

Нам известны `msg` и `sig` (они в cookie), но не `secret`. Наша цель — сделать
так, чтобы сервер принял сообщение с `admin=true`. Сначала посмотрим, как вообще
устроен SHA-256.

## Шаг 1: конструкция Merkle–Damgård

MD5, SHA-1 и SHA-256 обрабатывают сообщение блоками фиксированного размера
(SHA-256 — по 64 байта), поддерживая **внутреннее состояние**:

```
h_0 = IV (фиксированное)
h_i = f(h_{i-1}, m_i)       для каждого блока m_i
digest = h_n
```

Здесь `f` — **компрессионная функция**: она берёт текущее состояние и очередной
блок и выдаёт новое состояние. Ключевое свойство: **финальный дайджест — это
просто последнее внутреннее состояние `h_n`**, «замороженное» без финального
преобразования (в отличие от sponge-конструкции SHA-3).

Следствие: если мы знаем дайджест `H(secret || msg)`, мы знаем **внутреннее
состояние** после обработки `secret || msg`. Значит, можно продолжить
вычисление с этого состояния, обрабатывая новые блоки, — **не зная `secret`**.

Именно поэтому «замороженное» состояние и есть ахиллесова пята: хэш не отличает
«конец сообщения» от «середина сообщения». Sponge-конструкция (SHA-3) устроена
иначе — там финальное преобразование перемешивает состояние так, что продолжить
его нельзя.

## Шаг 2: padding и почему нужна длина секрета

Прежде чем «заморозить» состояние, хэш **дополняет** сообщение по схеме
Merkle–Damgård: `msg || 0x80 || 0x00... || len(msg)*8`, где длина — 64-битное
число в битах. Padding выбирается так, чтобы итог был кратен 64 байтам.

Чтобы достроить, атакующему нужно знать эту padding-строку. Она зависит **только
от длины** `secret || msg`, не от содержимого. Значит, достаточно знать **длину
секрета** (не сам секрет!) — а её обычно легко угадать (8, 16, 32 байта) или
подобрать по числу запросов.

```python
import struct
def md_pad(nbytes, block=64):
    return b"\x80" + b"\x00"*((56-(nbytes+1))%block) + struct.pack(">Q", nbytes*8)
```

## Шаг 3: продолжаем с внутреннего состояния

План атаки:

1. Вычисляем `pad = md_pad(len(secret) + len(msg))`.
2. Берём старый дайджест и трактуем его как **начальное состояние** (для SHA-256
   это 8 слов по 32 бита).
3. Продолжаем хэширование, обрабатывая блоки `extra` (наш `&admin=true`).
4. В финальном padding'е указываем **полную** длину
   `len(secret)+len(msg)+len(pad)+len(extra)`.

При этом **новое сообщение** для сервера выглядит так:
`msg || pad || extra`. Сервер посчитает `sha256(secret || msg || pad || extra)` —
и получит ровно наш новый MAC. Подпись валидна без знания ключа.

## Полный прогон от начала до конца

Реализуем SHA-256 с возможностью задать начальное состояние и «уже обработанную»
длину (это то, что внутри делают `hashpump`/`hash_extender`):

```
$ python3 lext_demo.py
MAC = sha256(secret||msg) = 69c493476afabf4127d25c22f31f31802a398fd4ed3cb044992527e79dba44a7
длина секрета (угадана) = 16
forged new_msg = b'user=guest&admin=false\x80\x00\x00...\x010&admin=true'
forged MAC     = 01110d0907aa98700639fdacd36939ebbad4ea6c4eebc635e7e12e8dcee1c90e
сервер: sha256(secret||new_msg) = 01110d0907aa98700639fdacd36939ebbad4ea6c4eebc635e7e12e8dcee1c90e
ПРИНЯТО? True
```

Обрати внимание: в `new_msg` появились «мусорные» байты `\x80\x00...` — это тот
самый padding, который хэш добавлял к `secret||msg`. Мы его «зашили» прямо в
сообщение, поэтому сервер, доходя до конца, обрабатывает те же блоки, что и мы.
Итог: сервер принял наше расширенное сообщение с его подписью, хотя секрет мы так
и не узнали.

## Что мы теперь знаем

- Merkle–Damgård-хэши (MD5/SHA-1/SHA-256) хранят внутреннее состояние, а дайджест
  — это и есть состояние.
- По `H(secret || msg)` можно достроить `H(secret || msg || pad || extra)`, зная
  только **длину** секрета.
- Padding обязателен в новом сообщении; в финальном padding'е указывается полная
  длина.
- Атака ломает наивные MAC вида `H(secret || message)` — в cookie, API-токенах,
  самописных подписях.
- Инструменты: `hashpump`, `hash_extender`, `hashpumpy`.
- SHA-3 (sponge) и BLAKE2/HAIFA этой атаке не подвержены.

## Инструменты: hashpump и hash_extender

Вручную собирать продолжение не обязательно — есть готовые инструменты:

```bash
pip install hashpumpy
# hashpump -s <sig> -d <orig_data> -a <append> -k <secret_len>
hashpump -s "6f5c..." -d "user=guest" -a "&role=admin" -k 16
# New signature: <hex>
# New data: user=guest\x80\x00...\x00&role=admin
```

```bash
# hash_extender поддерживает SHA-256 явно
hash_extender --data "user=guest" --append "&admin=1" \
  --signature "abcd..." --format sha256 --secret-length 16
```

Оба возвращают новую подпись и новое «сообщение» (с padding-байтами внутри).
Отправляйте их как есть — сервер посчитает `H(secret || new_data)` и получит тот
же MAC.

## Если не сработало

- **Секрет длиннее, чем вы думали.** Padding зависит от длины — переберите 8..64
  и смотрите, на каком варианте сервер возвращает `200`.
- **Это HMAC, а не `H(secret||msg)`.** Тогда length extension невозможен —
  ищите слабый ключ или alg confusion (см. `crypto-jwt-crypto`).
- **Хэш — SHA-3 или BLAKE2.** Sponge-конструкция и HAIFA не дают «продолжаемого»
  состояния; атака неприменима.
- **Сервер нормализует вход** (например, обрезает по разделителю) — padding-байты
  могут сломать парсинг; подбирайте `extra` аккуратно.

## Почему HMAC защищён

HMAC использует **два прохода** и внешний хэш:

```
HMAC(K, m) = H( (K⊕opad) || H( (K⊕ipad) || m ) )
```

Внутренний хэш `H((K⊕ipad)||m)` передаётся **внутрь** внешнего хэша, а не
является финальным дайджестом. Продолжить с него нельзя, потому что внешний хэш
начинается с секрета `(K⊕opad)`, которого атакующий не знает, и финализация
«закрывает» состояние. Поэтому **никогда не стройте MAC как `H(key || message)`** —
берите HMAC или AEAD.

## Куда дальше

Мы увидели, как «правильный» хэш превращается в уязвимый MAC, если собрать его
неправильно. В следующем уроке (`crypto-cbc-mac`) мы разберём родственную тему —
подделку **CBC-MAC и CMAC**, включая length extension на MAC и порядок
MAC-then-Encrypt. А главное запомни: **`H(secret || data)` — это не MAC; любой
признак такой проверки на сервере означает, что подпись можно достроить**.

## Где пригодится

- **CTF crypto/web** — подписанные cookie, токены, «проверка целостности» — частый вектор.
- **Bug bounty / пентест** — обход подписи в самописных API и сессиях.
- **Аудит кода** — выявление `H(secret‖data)` вместо HMAC.
- **SOC / IR** — понимание инцидентов с подделкой токенов.
- **Разработка** — почему стандарт требует именно HMAC.
