## Вопрос, с которого всё начинается

Сервер принимает зашифрованные сообщения и проверяет их подлинность: если хоть
один бит изменён, он отвечает `MAC check failed`. Шифр — AES-GCM, считается
«современным и безопасным»: он шифрует **и** сразу аутентифицирует данные. Ключа
у нас нет, но мы заметили, что сервер использует **один и тот же nonce** для
разных сообщений. Вопрос: достаточно ли этого, чтобы не только расшифровать
чужие данные, но и **подделать** сообщение так, что сервер его примет?

Оказывается, да. Эта атака называется **forbidden attack**, и ниже мы проведём её
целиком на реальном примере: восстановим секретный ключ аутентификации `H` и
склепаем тег, который сервер примет как настоящий.

## Наш пример: два сообщения с одним nonce

У нас есть два перехваченных сообщения — открытый текст первого известен
(`attack at dawn!!`), второй текст нам неизвестен. Оба зашифрованы одним ключом
и, что фатально, **одним nonce**:

```
c1 = 8f8648c71851c5d6d7cbeace651d8c77 t1 = 38a8dcd81853808d7c2c8efa32afee69
c2 = 9c9748d41e5b9197c29faecb6700c677 t2 = 3409a1bac661a29911574412c6991f20
```

Здесь `c` — шифротекст, `t` — **тег** (16 байт аутентификации). Оба сообщения по
16 байт. Дальше мы из этих четырёх hex-строк вытащим `H` и подделаем тег.

## Шаг 1: как GCM устроен внутри

GCM (Galois/Counter Mode) — это **AEAD**: Authenticated Encryption with Associated
Data, то есть шифрование, которое сразу даёт и конфиденциальность, и целостность.
Собирается он из двух частей.

**Шифрование — это CTR.** Берётся счётчик, шифруется ключом `E_K` и даёт
**keystream** (поток случайных байт), который складывается с текстом по XOR:
`C = P XOR keystream`. Расшифровка — та же операция. Ключевое свойство CTR: при
**одинаковом** счётчике keystream одинаков, а значит `C1 XOR C2 = P1 XOR P2`.

**Аутентификация — это GHASH.** Отдельно вычисляется **тег** — короткая метка,
доказывающая, что данные не менялись. GHASH работает так: сначала из ключа
выводится секрет `H = E_K(0^128)` (шифруем нулевой блок — получаем 128-битное
число). Затем все блоки данных (шифротекст и AAD — «сопутствующие данные»,
которые аутентифицируются, но не шифруются) трактуются как коэффициенты
многочлена, и он вычисляется в точке `H`:

```
GHASH_H(X) = X_1·H^m ⊕ X_2·H^(m-1) ⊕ ... ⊕ X_m·H
```

Умножение `·` и сложение `⊕` — это арифметика в **GF(2^128)** — поле из `2^128`
элементов, где «сложение» это XOR, а умножение — «беспереносное» умножение
полиномов с редукцией по `x^128 + x^7 + x^2 + x + 1`. Финальный тег:
`T = E_K(J0) ⊕ GHASH_H(...)`, где `J0` — блок, выведенный из nonce.

Критично вот что: **`H` зависит только от ключа и не зависит от nonce.** А nonce
мы переиспользовали.

## Шаг 2: повтор nonce даёт нам XOR открытых текстов

Раз nonce один, счётчики и keystream совпадают. Значит

```
c1 XOR c2 = (P1 XOR ks) XOR (P2 XOR ks) = P1 XOR P2
```

Проверим прямо в Python:

```
>>> c1 = bytes.fromhex("8f8648c71851c5d6d7cbeace651d8c77")
>>> c2 = bytes.fromhex("9c9748d41e5b9197c29faecb6700c677")
>>> p1 = b"attack at dawn!!"
>>> bytes(a ^ b for a, b in zip(c1, c2))          # = P1 XOR P2
b'\x13\x11\x00\x13\x06\nTA\x15TD\x05\x02\x1dJ\x00'
>>> bytes(a ^ b ^ c for a, b, c in zip(c1, c2, p1))   # знаем P1 -> получаем P2
b'retreat at dusk!'
```

Итак, зная один открытый текст, мы читаем второй. Но это только
конфиденциальность. Целостность всё ещё «держится» на теге — и вот тут в дело
вступает `H`.

## Шаг 3: восстанавливаем ключ аутентификации H

Оба тега посчитаны с одним и тем же `H`. Запишем GHASH для одного блока
шифротекста без AAD:

```
GHASH_H(C) = (C·H) ⊕ L) · H = C·H^2 ⊕ L·H
```

где `L` — служебный блок длины. У наших сообщений **одинаковая длина**, значит
`L1 = L2`, и при вычитании (XOR) тегов этот член исчезает:

```
T1 ⊕ T2 = (C1 ⊕ C2) · H^2
```

Отсюда `H^2 = (T1 ⊕ T2) / (C1 ⊕ C2)` — обычное деление в GF(2^128), а затем
`H = √(H^2)`. В поле характеристики 2 квадратный корень извлекается возведением
в степень `2^127`. Всё это — несколько строк арифметики:

```python
num = int.from_bytes(xor(t1, t2), "big")
den = int.from_bytes(xor(c1, c2), "big")
H2  = gf_mul(num, gf_inv(den))
H   = gf_pow(H2, 1 << 127)      # sqrt в GF(2^128)
```

Если длины сообщений разные, член с `H` не пропадает и получается квадратное
уравнение; его тоже решают, но это чуть больше алгебры.

## Шаг 4: подделываем тег

Теперь у нас есть `H`. Из одного валидного сообщения находим неизвестную
константу `S = E_K(J0) = T1 ⊕ GHASH_H(C1)`. Дальше для **любого** нового
шифротекста `C'` считаем правильный тег:

```
T' = S ⊕ GHASH_H(C')
```

Сервер не отличит его от настоящего — ведь он считает тег ровно так же.

## Полный прогон от начала до конца

Собираем всё вместе и проверяем на локальном сервере:

```
$ python3 gcm_demo.py
c1 = 8f8648c71851c5d6d7cbeace651d8c77 t1 = 38a8dcd81853808d7c2c8efa32afee69
c2 = 9c9748d41e5b9197c29faecb6700c677 t2 = 3409a1bac661a29911574412c6991f20
recovered H = fde4fbae4a09e020eff722969f83832b
S (E_K(J0)) = 39564b6064379fd806a1977c5d6bef85
forged ct = 899b4ac35b578097d783eb8f741fcc31 tag = 7ee7300a5671f7fd986f0a80a24d0513
SERVER ACCEPTS forged message: b'give me the flag'
```

Обрати внимание: `recovered H` совпал с истинным `H` (для этого ключа он равен
`fde4fbae…`), а сервер принял полностью выдуманное нами сообщение `give me the
flag` как подлинное. Мы одновременно **подделали данные и подписали их** — то
есть полностью сломали целостность AEAD. И всё из-за одного повторённого nonce.

## Что мы теперь знаем

- GCM = CTR для шифрования + GHASH для аутентификации; тег доказывает
  целостность.
- `H = E_K(0^128)` зависит только от ключа и **одинаков** для всех nonce.
- Повтор nonce ломает конфиденциальность (`C1 XOR C2 = P1 XOR P2`) и целостность
  (даёт уравнение на `H`).
- Два тега с одним nonce позволяют восстановить `H`; зная `H` и один валидный
  тег, можно подделать тег для любого сообщения.
- Защита одна: **никогда не повторять nonce**; там, где это не гарантировано,
  брать AES-GCM-SIV.

## Почему GHASH линеен и как это ломает

GHASH — это аутентификатор GCM, работающий в поле `GF(2^128)`: он вычисляет `Y = (X1·H^m ⊕ X2·H^{m−1} ⊕ … ⊕ Xm·H) ⊕ len`, где `H = E_K(0)` — ключ аутентификации, а `Xi` — блоки данных. Ключевое свойство — **линейность** по `H`: тег — это многочлен от `H` степени, равной числу блоков. Линейность даёт сразу две атаки.

Первая: если **nonce повторён**, два сообщения шифруются одним keystream'ом, и `C1 ⊕ C2 = P1 ⊕ P2` — это восстановление открытых текстов через crib-dragging (как в потоковом шифре). Вторая, страшнее: два тега для одного nonce дают два значения одного многочлена от `H`. Их XOR — это многочлен, корнем которого является `H`; решаем его в `GF(2^128)` и получаем **ключ аутентификации `H`**. С `H` на руках можно подделать тег для любого сообщения — целостность GCM полностью рушится.

Именно поэтому в GCM повтор `(key, nonce)` — фатальная ошибка, а не «небольшая неаккуратность». Отсюда требование: 96-битный случайный nonce или строго монотонный счётчик, никогда не повторяющийся для одного ключа. Это же свойство делает GCM уязвимым, если nonce генерируется предсказуемо или сбрасывается при перезапуске — реальные инциденты именно такие.

## Если не сработало

- **Nonce не повторяется.** Проверьте источники: счётчики, RNG после reboot, ветвление потоков. Ищите две записи с одинаковым `(key, nonce)`.
- **`H` не восстанавливается.** Нужны минимум два тега с одним nonce; одного недостаточно. Проверьте, что оба под одним ключом.
- **Модуль/поле не то.** GHASH работает в `GF(2^128)` с конкретным неприводимым многочленом; используйте правильную реализацию (например, из `pycryptodome` или `galois`), а не обычную арифметику.
- **Тег усечён.** Если тег обрезан, восстановление `H` усложняется, но с несколькими парами всё ещё возможно.
- **AES-GCM-SIV или nonce-misuse-resistant схема.** Тогда повтор nonce не ломает целостность — это осознанная защита, а не «не сработало».

## Частые вопросы

**Почему GCM вообще допустил такую зависимость?** GCM проектировался под предположение уникального nonce; это его явное требование безопасности, а не баг. Nonce-reuse-resistant варианты (GCM-SIV) появились позже.

**Чем GCM-SIV отличается?** Он детерминированно выводит nonce из ключа и сообщения (SIV-конструкция), поэтому повтор nonce не даёт двух тегов одного ключа — целостность сохраняется.

**Что использовать в новом коде?** AES-GCM с гарантированно уникальным nonce, либо ChaCha20-Poly1305, либо GCM-SIV там, где nonce может повториться. Никогда не хардкодить nonce.

## Куда дальше

Мы разобрали GCM — самый популярный AEAD. В уроке `crypto-ccm-aead` мы посмотрим
на его родственников: CCM (где аутентификация CBC-MAC, а шифрование CTR) и
ChaCha20-Poly1305, а также на то, как подделывают Poly1305 при повторе nonce.
Главное запомни: **в GCM nonce — это не «вектор», который можно переиспользовать;
это одноразовое число, и его повтор обнуляет всю защиту AEAD**.

- **Исследования** — криптоанализ GHASH и AEAD-конструкций.
