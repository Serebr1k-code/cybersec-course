## Вопрос, с которого всё начинается

Ты первый раз подключаешься к серверу, и SSH спрашивает: «The authenticity of host can't be established... Are you sure you want to continue connecting?». Почему SSH так боится за первый контакт, хотя дальше весь трафик шифруется? Ответ — в устройстве transport layer: сессионный ключ даёт только шифрование, но **не** подтверждает, что ты говоришь с нужным сервером. За это отвечает **host key**, и именно поэтому при первом контакте его надо проверить вручную.

## Наш пример: соединение и его ключи

Разберём одно подключение к `server.example`. Сначала посмотрим, как SSH договаривается о алгоритмах и что за ключи участвуют.

```
$ ssh -vvv user@server.example 2>&1 | grep -E 'kex|host key|KEX'
debug1: kex: algorithm: curve25519-sha256
debug1: kex: host key algorithm: ssh-ed25519
debug1: kex: server->client cipher: chacha20-poly1305@openssh.com
```

Читаем: для обмена ключами выбран `curve25519-sha256`, host key — `ssh-ed25519`, шифр — ChaCha20-Poly1305. Дальше разберём каждый.

## Шаг 1: обмен ключами (KEX)

**KEX** (key exchange) — этап, где стороны договариваются о сессионном ключе. `curve25519-sha256` — это ECDH на кривой Curve25519. Каждая сторона генерирует свою пару (приватный/публичный), шлёт публичный ключ и считает общий секрет. Это тот же DH, что в Noise, только «сырой».

Ключевая деталь: SSH считает общий секрет не как голое число, а прогоняет через хэш **вместе со всеми параметрами сессии**:

```
K = DH-секрет
H = SHA256( version_string || kex_init || kex_reply || host_key || e || f || K )
```

где `e`, `f` — публичные ключи сторон. `H` — **exchange hash**. Он связывает сессию с конкретными версиями, алгоритмами и host key. Если MITM-атакующий подменит хоть что-то, `H` изменится, и подпись host key перестанет сходиться.

## Шаг 2: подпись host key

Сервер подписывает `H` своим приватным host-ключом, а клиент проверяет подпись публичным. Это единственный момент, когда SSH подтверждает, что сервер — тот, за кого себя выдаёт. Если публичный ключ сервера ещё не известен, клиент его показывает:

```
$ ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
256 SHA256:qD2n...8fQ root@server (ED25519)
```

Отпечаток (`SHA256:...`) — короткий хэш публичного ключа. Его-то и надо сверить по независимому каналу при первом подключении. Дальше SSH пишет ключ в `~/.ssh/known_hosts`, и при следующих подключениях сверяет автоматически. Если ключ сменился — знаменитое предупреждение о возможном MITM.

## Шаг 3: вывод сессионных ключей

Из общего секрета `K` и exchange hash `H` выводятся ключи шифрования для каждого направления:

```
ключи = HASH( K || H || 'A' || session_id )   # направление A→B
ключи = HASH( K || H || 'B' || session_id )   # направление B→A
```

Буквы `'A'`/`'B'` — доменная сепарация: чтобы ключи двух направлений не совпали. `session_id` — это первый `H`; он остаётся неизменным при ре-кейинге (перевыпуске ключей в рамках одной сессии), поэтому новые ключи отличаются, а идентификатор сессии — нет.

## Шаг 4: аутентификация пользователя

После transport layer наступает очередь **userauth**. Здесь host key больше не участвует: пользователь доказывает право входа своим ключом (подпись) или паролем (внутри уже зашифрованного канала). Важно понимать разделение: host key — «это правильный сервер», user key — «это правильный пользователь». Это две независимые проверки, и путать их — классическая ошибка.

## Полный прогон

В лабе дан `kex.txt` с публичными ключами и параметрами сессии, `hostkey.pub` и скрипт `ssh_kex.py`. Скрипт повторяет вывод ключей: считает `K`, exchange hash `H`, проверяет «подпись» host key и печатает session id:

```
$ cat kex.txt
client_pub = 5f3a...
server_pub = a91c...
version    = SSH-2.0-OpenSSH_9.6

$ python3 ssh_kex.py
K = 3b7e... (32 bytes)
H = e1d0... (32 bytes)
host key verified: OK
session_id = nto{ssh_k3x_curv325519_sh4r3d_s3cr3t}
```

## Если не сработало

Если `H` не совпадает, проверь порядок полей в конкатенации — SSH строго фиксирует их. Если подпись не сходится, возможно, host key не тот, что в `known_hosts` (это и есть сигнал MITM). Если ключи направлений совпали — потеряна доменная сепарация `'A'`/`'B'`.

## SSH: согласование алгоритмов

SSH при подключении согласует алгоритмы: KEX (key exchange), host key, cipher, MAC, compression. Клиент и сервер выбирают первый общий из своих списков. Слабые настройки: `diffie-hellman-group1-sha1` (KEX), `ssh-rsa`/`ssh-dss` (host key), `aes128-cbc`/`3des-cbc` (cipher), `hmac-md5`/`hmac-sha1` (MAC).

```bash
ssh -Q kex; ssh -Q cipher; ssh -Q mac; ssh -Q key
```

Аудит: сравни список поддерживаемых алгоритмов с рекомендованными (Mozilla Modern). Устаревшие — находка.

## Атаки и слабости

Атаки: (1) **Terrapin** (CVE-2023-48795) — атака на префикс в SSH, позволяющая удалить часть сообщений (лечится strict KEX); (2) **weak KEX** — групповой обмен с малой энтропией; (3) **ssh-rsa (SHA-1)** — подпись host key слабая; (4) **CBC-cipher** — атаки на CBC; (5) **перебор паролей** (если нет ключей). Инструменты: `ssh-audit`, `nmap --script ssh2-enum-algos`.

```bash
ssh-audit host
```

Типичная находка — поддержка legacy-алгоритмов для совместимости.

## Практика и защита

Практика: прогони `ssh-audit` по всем SSH-серверам, найди legacy-алгоритмы и отключи их. Защита: современные KEX (curve25519-sha256), Ed25519 host key, AEAD-ciphers (chacha20-poly1305, aes-gcm), strict KEX, ключевой доступ вместо паролей, MFA. Инструменты: `ssh-audit`, конфиг `sshd_config`.

```text
recommend: curve25519, ed25519, chacha20-poly1305, strict kex
```

Вывод: SSH-аудит — быстрая и результативная проверка, часто выявляющая legacy-алгоритмы.

## Куда дальше

Мы разобрали transport layer SSH: KEX, host key и вывод ключей. Дальше — PAKE: протокол, который решает похожую задачу, но вместо ключей использует пароль, не давая атакующему офлайн-оракул. Запомни главное: в SSH host key и user key — это два разных доверия, и первое проверяется только при первом контакте.
