## Вопрос, с которого всё начинается

Ты первый раз подключаешься к серверу, и SSH спрашивает: «The authenticity of host can't be established... Are you sure you want to continue connecting?». Почему SSH так боится за первый контакт, хотя дальше весь трафик шифруется? Ответ — в устройстве transport layer: сессионный ключ даёт только шифрование, но **не** подтверждает, что ты говоришь с нужным сервером. За это отвечает **host key**, и именно поэтому при первом контакте его надо проверить вручную.

## Наш пример: соединение и его ключи

Разберём одно подключение к `server.example`. Сначала посмотрим, как SSH договаривается о алгоритмах и что за ключи участвуют.

```
$ ssh -vvv user@server.example 2>&1 | grep -E 'kex|host key|KEX'
debug1: kex: algorithm: curve25519-sha256
debug1: kex: host key algorithm: ssh-ed25519
debug1: kex: server->client cipher: chacha20-poly1305@openssh.com
```

Читаем: для обмена ключами выбран `curve25519-sha256`, host key — `ssh-ed25519`, шифр — ChaCha20-Poly1305. Дальше разберём каждый.

## Шаг 1: обмен ключами (KEX)

**KEX** (key exchange) — этап, где стороны договариваются о сессионном ключе. `curve25519-sha256` — это ECDH на кривой Curve25519. Каждая сторона генерирует свою пару (приватный/публичный), шлёт публичный ключ и считает общий секрет. Это тот же DH, что в Noise, только «сырой».

Ключевая деталь: SSH считает общий секрет не как голое число, а прогоняет через хэш **вместе со всеми параметрами сессии**:

```
K = DH-секрет
H = SHA256( version_string || kex_init || kex_reply || host_key || e || f || K )
```

где `e`, `f` — публичные ключи сторон. `H` — **exchange hash**. Он связывает сессию с конкретными версиями, алгоритмами и host key. Если MITM-атакующий подменит хоть что-то, `H` изменится, и подпись host key перестанет сходиться.

## Шаг 2: подпись host key

Сервер подписывает `H` своим приватным host-ключом, а клиент проверяет подпись публичным. Это единственный момент, когда SSH подтверждает, что сервер — тот, за кого себя выдаёт. Если публичный ключ сервера ещё не известен, клиент его показывает:

```
$ ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
256 SHA256:qD2n...8fQ root@server (ED25519)
```

Отпечаток (`SHA256:...`) — короткий хэш публичного ключа. Его-то и надо сверить по независимому каналу при первом подключении. Дальше SSH пишет ключ в `~/.ssh/known_hosts`, и при следующих подключениях сверяет автоматически. Если ключ сменился — знаменитое предупреждение о возможном MITM.

## Шаг 3: вывод сессионных ключей

Из общего секрета `K` и exchange hash `H` выводятся ключи шифрования для каждого направления:

```
ключи = HASH( K || H || 'A' || session_id )   # направление A→B
ключи = HASH( K || H || 'B' || session_id )   # направление B→A
```

Буквы `'A'`/`'B'` — доменная сепарация: чтобы ключи двух направлений не совпали. `session_id` — это первый `H`; он остаётся неизменным при ре-кейинге (перевыпуске ключей в рамках одной сессии), поэтому новые ключи отличаются, а идентификатор сессии — нет.

## Шаг 4: аутентификация пользователя

После transport layer наступает очередь **userauth**. Здесь host key больше не участвует: пользователь доказывает право входа своим ключом (подпись) или паролем (внутри уже зашифрованного канала). Важно понимать разделение: host key — «это правильный сервер», user key — «это правильный пользователь». Это две независимые проверки, и путать их — классическая ошибка.

## Полный прогон

В лабе дан `kex.txt` с публичными ключами и параметрами сессии, `hostkey.pub` и скрипт `ssh_kex.py`. Скрипт повторяет вывод ключей: считает `K`, exchange hash `H`, проверяет «подпись» host key и печатает session id:

```
$ cat kex.txt
client_pub = 5f3a...
server_pub = a91c...
version    = SSH-2.0-OpenSSH_9.6

$ python3 ssh_kex.py
K = 3b7e... (32 bytes)
H = e1d0... (32 bytes)
host key verified: OK
session_id = nto{ssh_k3x_curv325519_sh4r3d_s3cr3t}
```

## Если не сработало

Если `H` не совпадает, проверь порядок полей в конкатенации — SSH строго фиксирует их. Если подпись не сходится, возможно, host key не тот, что в `known_hosts` (это и есть сигнал MITM). Если ключи направлений совпали — потеряна доменная сепарация `'A'`/`'B'`.

## SSH: согласование алгоритмов

SSH при подключении согласует алгоритмы: KEX (key exchange), host key, cipher, MAC, compression. Клиент и сервер выбирают первый общий из своих списков. Слабые настройки: `diffie-hellman-group1-sha1` (KEX), `ssh-rsa`/`ssh-dss` (host key), `aes128-cbc`/`3des-cbc` (cipher), `hmac-md5`/`hmac-sha1` (MAC).

```bash
ssh -Q kex; ssh -Q cipher; ssh -Q mac; ssh -Q key
```

Аудит: сравни список поддерживаемых алгоритмов с рекомендованными (Mozilla Modern). Устаревшие — находка.

## Атаки и слабости

Атаки: (1) **Terrapin** (CVE-2023-48795) — атака на префикс в SSH, позволяющая удалить часть сообщений (лечится strict KEX); (2) **weak KEX** — групповой обмен с малой энтропией; (3) **ssh-rsa (SHA-1)** — подпись host key слабая; (4) **CBC-cipher** — атаки на CBC; (5) **перебор паролей** (если нет ключей). Инструменты: `ssh-audit`, `nmap --script ssh2-enum-algos`.

```bash
ssh-audit host
```

Типичная находка — поддержка legacy-алгоритмов для совместимости.

## Практика и защита

Практика: прогони `ssh-audit` по всем SSH-серверам, найди legacy-алгоритмы и отключи их. Защита: современные KEX (curve25519-sha256), Ed25519 host key, AEAD-ciphers (chacha20-poly1305, aes-gcm), strict KEX, ключевой доступ вместо паролей, MFA. Инструменты: `ssh-audit`, конфиг `sshd_config`.

```text
recommend: curve25519, ed25519, chacha20-poly1305, strict kex
```

Вывод: SSH-аудит — быстрая и результативная проверка, часто выявляющая legacy-алгоритмы.

## Разбор: exchange hash из байтов

Покажем, как `H` реально собирается из байтов, чтобы стало ясно, почему подмена любого поля ломает аутентификацию. Формат из RFC 4253 — это конкатенация length-prefixed строк:

```
string   V_C        version клиента
string   V_S        version сервера
string   I_C        payload KEXINIT клиента
string   I_S        payload KEXINIT сервера
string   K_S        публичный host key сервера
string   e          публичный ключ клиента
string   f          публичный ключ сервера
mpint    K          общий DH-секрет
```

Каждое поле — не «сырые байты», а `uint32 length || bytes`. Если поменять порядок или забыть длину, `H` разойдётся, и подпись сервера не проверится. Это не формальность: именно строгий формат делает атаку подстановки KEXINIT заметной. Проверим на маленьком примере:

```
$ python3 ssh_kex.py --dump
V_C = SSH-2.0-OpenSSH_9.6
V_S = SSH-2.0-OpenSSH_9.6
K_S = ssh-ed25519 AAAA...
e   = 5f3a...  (32 bytes)
f   = a91c...  (32 bytes)
K   = 3b7e...  (32 bytes)
H   = SHA256(V_C||V_S||I_C||I_S||K_S||e||f||K) = e1d0...
```

`H` подписывается приватным host-ключом. Клиент, имеющий публичный host-ключ (из `known_hosts`), проверяет подпись над `H`. Если MITM переиграл `e` или `f` — изменится `H`, и подпись перестанет сходиться. Именно поэтому SSH не даёт «незаметно» вклиниться, даже когда сессионный ключ ещё не аутентифицирован.

## Таблица: алгоритмы SSH и их статус

| Категория | Устаревшее / небезопасно | Рекомендуется |
|---|---|---|
| KEX | `diffie-hellman-group1-sha1`, `group14-sha1` | `curve25519-sha256`, `sntrup761x25519-sha512` (PQ) |
| Host key | `ssh-dss`, `ssh-rsa` (SHA-1) | `ssh-ed25519`, `rsa-sha2-512` |
| Cipher | `3des-cbc`, `aes*-cbc`, `arcfour` | `chacha20-poly1305`, `aes*-gcm` |
| MAC | `hmac-md5`, `hmac-sha1` | `hmac-sha2-256-etm`, `umac-128-etm` |

Проверить свой сервер: `ssh -Q kex`, `ssh -Q cipher`, `ssh -Q key`, а со стороны аудитора — `ssh-audit host`. Типичная находка при пентесте — legacy-алгоритмы, включённые «для совместимости» со старыми клиентами.

## Границы и подводные камни

- **Host key — не пользователь.** Подпись host-ключа доказывает только личность сервера; право входа — отдельная проверка в userauth. Пентест-ошибка — считать, что «раз host key верен, канал безопасен».
- **Strict KEX закрывает Terrapin.** CVE-2023-48795 эксплуатирует расширение `SSH_MSG_EXT_INFO` до включения шифрования; фикс — режим strict KEX, где номера последовательностей фиксируются. Без него активный MITM может удалить часть первых сообщений.
- **Первый контакт доверия не даёт.** `known_hosts` заполняется при первом подключении без проверки — если первое подключение перехвачено, MITM фиксируется навсегда. Поэтому в чувствительных средах отпечаток сверяют вручную или через DNSSEC/SSHFP.
- **`ssh-rsa` — это про подпись, а не про длину.** Ключ RSA может быть 4096 бит, но подпись SHA-1 (`ssh-rsa`) всё равно уязвима; нужен `rsa-sha2-256/512`.
- **CBC-режимы не AEAD.** Они уязвимы к атакам на padding-oracle и требуют отдельного MAC; AEAD-шифры (`chacha20-poly1305`, `aes-gcm`) аутентифицируют данные «из коробки».

## Сколько стоит аудит: быстрый чек-лист

Полный аудит SSH-сервиса укладывается в несколько команд. Сначала собери баннер и версию: `nc host 22` даёт строку `SSH-2.0-OpenSSH_9.6`. Затем прогони `ssh-audit host` — он перечислит kex, host-key, cipher и MAC, отметив небезопасные. Если нужен ручной контроль, `nmap -p22 --script ssh2-enum-algos host` вернёт те же списки в структурированном виде. Отдельно проверь, разрешён ли вход по паролю (`PasswordAuthentication`) и root-логин (`PermitRootLogin`) — это конфигурационные находки, а не криптографические, но именно они чаще всего превращают найденную слабость в реальный доступ.

## Полный числовой прогон вывода ключей

Разберём вывод сессионных ключей по шагам. Пусть после KEX у сторон получился общий секрет `K` и exchange hash `H`. SSH выводит ключи из HKDF-подобной функции, где в качестве «информации» выступает буква направления и `session_id`. Упрощённо:

```
IV_C2S   = HASH(K || H || "A" || session_id)
KEY_C2S  = HASH(K || H || "B" || session_id)
IV_S2C   = HASH(K || H || "C" || session_id)
KEY_S2C  = HASH(K || H || "D" || session_id)
```

Возьмём игрушечные входы, чтобы увидеть, что смена одной буквы меняет весь ключ:

```
K = 3b7e1a90…  H = e1d0c4f2…  session_id = e1d0c4f2…  (первый H)

KEY_C2S = SHA256(K || H || "B" || sid) = 8f2c…
KEY_S2C = SHA256(K || H || "D" || sid) = a1d7…
```

Даже если бы `K` и `H` совпали, разные буквы дают полностью несвязанные ключи. Это и есть **доменная сепарация**: она гарантирует, что ключ «клиент→сервер» никогда не совпадёт с ключом «сервер→клиент», и что один и тот же секрет не даст одинаковых ключей в двух разных ролях.

## Ре-кейинг и постоянство session_id

Долгая SSH-сессия периодически делает **rekey**: стороны заново прогоняют KEX и получают новый `K'` и новый `H'`. Ключи пересчитываются, но `session_id` **не меняется** — это всегда первый exchange hash сессии. Зачем так? `session_id` служит устойчивым идентификатором сессии: он привязывает все ключи (включая новые после rekey) к одному рукопожатию и используется в аутентификации. Так сервер не путает пользователя, который «перезашёл», с тем же пользователем, у которого просто обновились ключи.

## Сравнение алгоритмов SSH

| Категория | Устаревшее (находка) | Современное (рекомендация) |
|---|---|---|
| KEX | `diffie-hellman-group1-sha1`, `group14-sha1` | `curve25519-sha256`, `sntrup761x25519-sha512` (PQ) |
| Host key | `ssh-rsa` (SHA-1), `ssh-dss` | `ssh-ed25519`, `rsa-sha2-512` |
| Cipher | `3des-cbc`, `aes128-cbc` | `chacha20-poly1305`, `aes256-gcm` |
| MAC | `hmac-md5`, `hmac-sha1` | `hmac-sha2-256-etm`, AEAD-режимы |

Правило чтения: всё с `sha1`, `md5`, `cbc`, `group1`, `group14` в имени — кандидаты на находку. AEAD-шифры (`gcm`, `chacha20-poly1305`) уже включают MAC, поэтому отдельный `hmac-*` для них не согласуется.

## Terrapin и strict KEX

В 2023 году обнаружили **Terrapin** (CVE-2023-48795): атакующий-посредник может выборочно выбросить часть сообщений начального обмена, чтобы понизить защиту (например, отключить защиту от keystroke-timing). Лечится **strict KEX**: расширение, которое привязывает последовательность сообщений к `H` и запрещает любые пропуски или вставки в начальной фазе. Проверить поддержку можно через `ssh -Q kex` (наличие `strict-kex`) и `ssh-audit`, который явно сообщает о Terrapin.

```
$ ssh-audit server.example | grep -iE 'terrapin|strict'
# (recommendation) strict KEX enabled: yes
```

## Крайние случаи и ограничения

- **Первый контакт доверия не даёт.** Без проверки отпечатка по независимому каналу SSH уязвим к MITM ровно на первом подключении — это не баг, а следствие модели доверия.
- **known_hosts можно отравить.** Если атакующий ранее подменил ключ и пользователь принял его, дальше предупреждений не будет.
- **Host key ≠ user key.** Смена host key не влияет на аутентификацию пользователя, и наоборот; путать эти два доверия — типовая ошибка в конфигурациях.
- **`StrictHostKeyChecking=no`** автоматически принимает новые ключи — удобно в автоматизации, но полностью снимает защиту от MITM.
- **Короткие ключи.** `ssh-rsa` с ключом 1024 бита ломается по факторизации; Ed25519 фиксированно 256-битный и не требует «выбора длины».

## Практический аудит: ssh-audit и sshd_config

Быстрый аудит одного сервера:

```
$ ssh-audit -p 22 10.0.0.5 | head -40
# (gen) banner: SSH-2.0-OpenSSH_8.2
# (kex) diffie-hellman-group14-sha1  -- [fail] using weak hashing algorithm
# (key) ssh-rsa                       -- [warn] using weak hashing algorithm
# (enc) aes128-cbc                    -- [fail] removed (insecure) cipher
```

Харденинг `sshd_config` сводится к явному списку разрешённого:

```
KexAlgorithms curve25519-sha256
HostKeyAlgorithms ssh-ed25519
Ciphers chacha20-poly1305@openssh.com,aes256-gcm@openssh.com
MACs hmac-sha2-256-etm@openssh.com
PasswordAuthentication no
```

Вывод: аудит SSH — дешёвая проверка с высокой отдачей: legacy-алгоритмы находятся почти всегда, а исправление — один блок в конфиге.

## Куда дальше

Мы разобрали transport layer SSH: KEX, host key и вывод ключей. Дальше — PAKE: протокол, который решает похожую задачу, но вместо ключей использует пароль, не давая атакующему офлайн-оракул. Запомни главное: в SSH host key и user key — это два разных доверия, и первое проверяется только при первом контакте.

## Где пригодится

- **CTF Crypto:** задачи на восстановление session id или проверку host key.
- **Bug bounty:** аудит SSH-сервисов и их алгоритмов.
- **Пентест:** MITM-атаки на SSH и слабые KEX-алгоритмы.
- **Работа:** харденинг SSH и управление ключами.
