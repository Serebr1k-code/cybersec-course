## Вопрос, с которого всё начинается

Представь игру по переписке: два игрока должны одновременно вскрыть свои ходы, чтобы никто не мог подстроиться под противника. Как «зафиксировать» свой ход так, чтобы его нельзя было изменить, но при этом до вскрытия никто его не знал? Ответ — **commitment** (обязательство), криптографический «запечатанный конверт». Из него вырастают доказательства с нулевым разглашением (ZK), а сигма-протокол Schnorr + Fiat-Shamir — это почти готовая подпись (в том числе EdDSA). В CTF это класс задач «сервер бросает challenge, я отвечаю», где ломается предсказуемый nonce или отсутствие привязки.

## Наш пример

Возьмём сигма-протокол **Schnorr**: доказательство знания дискретного логарифма `x` для `X = g^x mod p`, не раскрывая `x`. Секрет у нас будет маленький, чтобы всё прогонялось за секунду:

```python
p = 2**127 - 1            # простое Мерсенна
q = p - 1                 # порядок мультипликативной группы
g = 3
x = 0x5ec4e1              # секрет (< q)
X = pow(g, x, p)          # открытый ключ
```

Схема состоит из трёх шагов, отсюда название «сигма» (Σ). Сначала разберём, из чего вообще состоит commitment, а потом прогоним протокол и сломаем его.

## Шаг 1: что такое commitment

Схема commitment состоит из двух фаз:

- **Commit:** фиксируешь `m`, публикуя `c = Commit(m, r)`.
- **Reveal:** раскрываешь `(m, r)`, и проверяющий убеждается, что `c` соответствует `m`.

Требуются два свойства: **hiding** — по `c` нельзя узнать `m` (до раскрытия), и **binding** — нельзя раскрыть `c` как другое `m'` (после commit). Идеальные hiding и binding одновременно недостижимы — это принципиальный компромисс.

Простейшая схема — **хэш-commitment**: `c = H(r || m)`, где `r` — случайная соль. Hiding даёт соль, binding — стойкость хэша к коллизиям. Если `r` нет, а `m` из малого множества (например, «орёл/решка»), его подбирают перебором. Если хэш уязвим к length extension — commit можно «продлить» (см. `crypto-hmac`).

## Шаг 2: сигма-протокол Schnorr

Доказательство знания `x` для `X = xG` (в мультипликативной записи `X = g^x`):

1. **Commit:** доказывающий выбирает случайный `r`, отправляет `R = g^r`.
2. **Challenge:** проверяющий бросает случайный `c`.
3. **Response:** доказывающий отправляет `s = r + c·x mod q`.
4. **Verify:** проверяющий убеждается, что `g^s == R · X^c`.

Корректность: `g^s = g^(r+cx) = g^r · (g^x)^c = R · X^c`. Знание `x` не раскрывается: `s` маскирован случайным `r`. Свойства: **completeness** (честный проходит), **soundness** (обманщик не проходит), **zero-knowledge** (проверяющий не узнаёт ничего сверх утверждения).

## Шаг 3: прогоняем протокол

```python
from hashlib import sha256
r  = 0x9f1c3b             # nonce (должен быть случаен!)
R  = pow(g, r, p)
c  = int.from_bytes(sha256(f"{R}{X}".encode()).digest(), "big") % q
s  = (r + c * x) % q
print("verify OK:", pow(g, s, p) == (R * pow(X, c, p)) % p)
```

```
verify OK: True
```

Здесь `c` мы получили как хэш транскрипта `R||X` — это уже **преобразование Fiat-Shamir**: оно превращает интерактивный протокол в неинтерактивный (в подпись). Хэшировать нужно **весь** транскрипт, включая `R`, иначе возможна подделка (об этом ниже).

## Шаг 4: ломаем — переиспользование nonce

Главная практическая атака: если `r` повторился, секрет восстанавливается из двух ответов. Допустим, доказывающий использовал один и тот же `R` для двух разных challenge `c1 ≠ c2`:

```
s1 = r + c1·x
s2 = r + c2·x
=> s1 - s2 = (c1 - c2)·x  =>  x = (s1 - s2) / (c1 - c2) mod q
```

Прогоним:

```python
c1, c2 = 0x1111, 0x2222
s1, s2 = (r + c1 * x) % q, (r + c2 * x) % q
x_rec = ((s1 - s2) * pow(c1 - c2, -1, q)) % q
print("x      =", hex(x))
print("x_rec  =", hex(x_rec))
```

```
x      = 0x5ec4e1
x_rec  = 0x5ec4e1
```

Секрет восстановлен без единого перебора. Это ровно атака «nonce reuse», как в ECDSA (`crypto-ecdsa-nonce`).

## Шаг 5: Fiat-Shamir и его ловушки

Чтобы сделать протокол неинтерактивным, challenge заменяют хэшем транскрипта: `c = H(R || X || m)`. Ловушки:

- **Забыли включить `R` в хэш** → `c = H(m)`; тогда атакующий выбирает произвольные `s, c`, вычисляет `R = g^s · X^{-c}` и отправляет `(R, s)` — проверка `g^s == R·X^c` выполняется тождественно, а знания `x` не требуется. Это **weak Fiat-Shamir**. Покажем это кодом:

```python
import random
s = random.randrange(q)
c = 0xABCD                      # сервер вычислит c = H(m); подбираем m или атакуем иначе
R = (pow(g, s, p) * pow(pow(X, c, p), -1, p)) % p   # R = g^s * X^{-c}
assert pow(g, s, p) == (R * pow(X, c, p)) % p       # проходит без знания x
```

  Если сервер считает `c = H(R || X || m)`, подделка невозможна: изменение `R` меняет `c`. Отсюда правило — в Fiat-Shamir хэшируется **весь** транскрипт, включая commitment.
- **Не привязали контекст** → **replay**: доказательство, валидное в одном приложении, принимается в другом (классика «frozen heart»).
- **Слабый хэш** → коллизии позволяют подделать.
- **Предсказуемый `r`** (из известного seed) → та же атака, что выше, даже без повтора.

Дополнительно уязвимы: **Pedersen commitment** `c = mG + rH` (гомоморфный — основа range-proofs и Bulletproofs), **малые подгруппы** (если `G` не проверяется, ответы «сворачиваются», см. `crypto-invalid-curve`) и **повтор challenge** при отсутствии учёта выданных `c`.

## Что мы теперь знаем

- Commitment фиксирует значение (binding), не раскрывая его (hiding).
- Schnorr — трёхшаговый сигма-протокол доказательства знания `x`.
- Fiat-Shamir делает протокол неинтерактивным через хэш транскрипта.
- Повтор `r`/`R` восстанавливает секрет из двух ответов — как в ECDSA.
- Weak Fiat-Shamir (хэш без `R`) позволяет подделать доказательство без ключа.
- Хэшируй **весь** транскрипт и привязывай контекст.

Мы собрали commitment и сигма-протокол, увидели атаку на повтор `r` и подделку weak Fiat-Shamir.
