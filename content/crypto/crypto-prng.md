## Вопрос, с которого всё начинается

Вся криптография держится на случайности: ключи, nonce, токены, сброс пароля. Но компьютеры не умеют быть по-настоящему случайными — они используют **генераторы псевдослучайных чисел**. Вопрос новичка: «Если генератор детерминирован, значит, его выход можно предсказать?» Да — и для некоторых генераторов это делается по нескольким десяткам значений. Разберём, как именно.

## Наш пример

Приложение выдаёт «случайные» токены через Python `random`. Мы собрали 624 подряд идущих 32-битных значения и хотим предсказать следующее. Прогоним атаку и посмотрим, совпадёт ли предсказание с реальностью.

## Шаг 1: PRNG и CSPRNG

**PRNG** (pseudo-random number generator) детерминирован: по внутреннему состоянию он выдаёт последовательность, и если состояние восстановлено — вся последовательность (и прошлая, и будущая) известна. **CSPRNG** (cryptographically secure PRNG) спроектирован так, чтобы по выходу нельзя было восстановить состояние: это `os.urandom`, `/dev/urandom`, `secrets`, `getrandom()`. Для ключей, токенов и nonce используйте **только** CSPRNG. Ошибка №1 в реальном коде — использовать `random` (Python), `Math.random()` (JS) или `rand()` (C) для генерации секретов. Все они **не** криптостойкие.

## Шаг 2: MT19937 и Python random

Python `random` использует **Mersenne Twister (MT19937)**: состояние — 624 32-битных слова (19937 бит), а генерация — линейная операция над GF(2). Ключевой факт: **624 последовательных 32-битных выхода полностью определяют состояние.** Каждый выход проходит через обратимое преобразование **tempering**, которое можно отменить функцией `untemper`. Восстановив 624 слова состояния, мы подставляем их в новый генератор и предсказываем всё.

## Шаг 3: полный прогон — клонируем генератор

```python
def untemper(y):
    y = unshift_right(y, 18)
    y = unshift_left(y, 15, 0xefc60000)
    y = unshift_left(y, 7, 0x9d2c5680)
    y = unshift_right(y, 11)
    return y

r = random.Random(12345)
outs = [r.getrandbits(32) for _ in range(624)]
next_real = r.getrandbits(32)
state = [untemper(x) for x in outs]
clone = random.Random()
clone.setstate((3, tuple(state + [624]), None))
print(clone.getrandbits(32))
```

```
real next: 4171722749
predicted: 4171722749  match: True
```

Предсказание совпало! Мы полностью клонировали генератор и знаем все его будущие значения. Заметьте: `untemper` — не «взлом алгоритма», а просто обратная операция к открытому преобразованию. Именно линейность MT19937 и делает его непригодным для секретов. Если приложение выдаёт токены сброса пароля или OTP через `random`, они предсказуемы.

## Шаг 4: восстановление seed

Иногда состояние недоступно, но известен **диапазон seed** — например, `random.seed(int(time.time()))`. Тогда seed перебирается:

```python
random.seed(999); target = random.getrandbits(32)
for t in range(900, 1100):
    random.seed(t)
    if random.getrandbits(32) == target:
        print("seed found:", t); break
```

```
seed found: 999
```

Признак такой задачи — seed из timestamp, PID или user ID: пространство маленькое и перебирается за секунды. Часто достаточно окна ±несколько часов вокруг известного времени.

## Шаг 5: LCG — линейный конгруэнтный генератор

Другой частый генератор — **LCG**: `x_{i+1} = (a·x_i + c) mod m`. Его рекуррентность линейна, поэтому по нескольким последовательным выходам параметры восстанавливаются: модуль `m` находится как `gcd` разностей, а `a`, `c` — из системы линейных уравнений. LCG используется в Java `Random` (48-битное состояние, предсказуем по двум выходам), в glibc `rand()`, в старых языках.

## Шаг 6: другие PRNG и подход через Z3

Java `Random` — 48-битный LCG; `java.util.Random` не криптостойкий, нужен `SecureRandom`. glibc `rand()` — аддитивный генератор, предсказуем по нескольким десяткам выходов. PHP `mt_rand()` — тот же MT19937. JS `Math.random()` в V8 — xorshift128+, тоже ломается. Если выход **усечён** (например, `randint(0, 255)` даёт 8 бит за раз), строят систему битовых уравнений MT19937 и решают через Z3. Это мощный подход для «частичных» утечек, когда полные 32 бита недоступны. Готовая библиотека `randcrack` умеет восстанавливать MT19937 по 624 значениям автоматически.

## Шаг 7: как не застрять

Чек-лист: определите **генератор** (Python random, LCG, кастомный); соберите **достаточно выходов** (624 для MT19937, 2 для Java Random); примените `untemper` и клонирование; проверьте **seed-перебор** при малом пространстве; для LCG решите систему. И главное: если генератор **криптостойкий** (`os.urandom`/`secrets`), предсказание **не работает** — ищите другой вектор: утечку состояния, reuse ключа/IV, состояние после форка. Не тратьте время на «предсказание» CSPRNG.

## Почему MT19937 предсказуем — что значит «линейный»

Слово «линейный» здесь ключевое. MT19937 — это линейный регистр сдвига с обобщённой обратной связью над GF(2): каждое новое состояние получается из предыдущего операциями XOR и сдвига. Выход проходит через tempering — тоже обратимое преобразование из XOR и сдвигов. Ни одна операция не «перемешивает» биты так, чтобы потерять информацию. Поэтому 624 выхода не «угадываются», а **точно** обращаются в исходное состояние. Именно отсутствие нелинейности отличает MT19937 от криптостойких генераторов: у ChaCha20-базированного `os.urandom` выход зависит от секретного ключа через нелинейные операции, и обратить его нельзя. Запомните правило: если генератор описывается линейными операциями над битами, его выход предсказуем; если внутри есть криптографический примитив с секретом — нет.

## Практический пример: предсказание OTP

Самое частое применение атаки — одноразовые коды. Приложение генерирует OTP через `random.randint(0, 999999)` и не использует CSPRNG. Если у нас есть канал, по которому утекают «случайные» значения (например, публичные ID или сами OTP), мы собираем 624 значения `getrandbits(32)`, восстанавливаем состояние и предсказываем следующий код. Библиотека `randcrack` делает это одной строкой на выход: `rc.submit(x)` для каждого значения, затем `rc.predict_getrandbits(32)`. Если выход усечён, значения всё равно можно скормить через Z3-модель. Мораль простая: **любой секрет, сгенерированный `random`, `Math.random()` или `rand()`, считается скомпрометированным.**

## Итог: где искать слабую случайность

При аудите ищите в коде вызовы `random`, `Math.random`, `rand`, `mt_rand`, `java.util.Random` — там, где ожидается секрет. Особенно опасны: генерация токенов сброса пароля, сессионных идентификаторов, OTP, ключей шифрования, nonce. Все они должны идти через `secrets`/`os.urandom`/`SecureRandom`. Полезно также проверять seed: если он берётся из времени, PID или предсказуемого значения, даже «криптостойкий» генератор становится слабым. И помните: в задачах с «угадай следующее число» почти всегда достаточно собрать нужное количество выходов и обратить генератор — не нужно ломать математику, достаточно увидеть линейность.

## Что мы теперь знаем

- **PRNG** детерминирован; **CSPRNG** устойчив к восстановлению состояния.
- Python `random` = **MT19937**; **624** 32-битных выхода дают состояние целиком.
- `untemper` отменяет tempering; `setstate` клонирует генератор.
- **Seed** из timestamp/PID перебирается; окно ±часы обычно достаточно.
- **LCG** ломается линейно (gcd разностей → `a, c, m`).
- Для CSPRNG предсказание не работает — ищите другой вектор.
