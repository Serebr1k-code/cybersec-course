## Вопрос, с которого всё начинается

Обычный сервер хранит хэш пароля и при входе сравнивает хэш присланного пароля. Проблема: если базу украли, атакующий перебирает пароли **офлайн**, без обращений к серверу, и словарь из миллиарда слов проверяется на GPU за часы. Хочется протокол, где сервер не хранит ничего, что позволяет офлайн-перебор, и где даже подслушавший рукопожатие не получает оракула. Это и есть **PAKE** (Password-Authenticated Key Exchange). Разберём SRP — самый распространённый.

## Наш пример: регистрация и вход в SRP

**SRP** (Secure Remote Password) устроен так. При регистрации клиент выбирает пароль `p` и соль `s`, считает:

```
x = H(s || H(user || ':' || p))     # «приватный» показатель из пароля
v = g^x mod N                        # верификатор
```

Сервер хранит `(s, v)` — соль и верификатор. Обрати внимание: сервер **не** хранит ни пароль, ни его обычный хэш — только `v = g^x`. Чтобы восстановить пароль из `v`, надо решить задачу дискретного логарифма (ты её знаешь из `crypto-discrete-log`) — это и защищает от офлайн-перебора в лоб. Но есть нюанс: если пароль слабый, атакующий всё равно может перебрать его, потому что для каждого кандидата считает `v' = g^x'` и сравнивает с украденным `v`. Это и есть офлайн-атака по словарю — PAKE её не отменяет, а лишь не даёт **подслушивающему** оракул.

## Шаг 1: клиент шлёт A

Клиент генерирует случайный `a`, считает публичный `A = g^a mod N` и шлёт `A`. Сервер шлёт свою соль `s` и `B = k·v + g^b mod N`, где `b` — случайный, `k = H(N || g)`.

Термины: `A`, `B` — публичные «половинки» DH, `k` — множитель, который подмешивает верификатор в `B`. Из-за него сервер не может вычислить общий секрет без `v`, а клиент — без пароля.

## Шаг 2: обе стороны считают общий секрет

Клиент знает `x` (из пароля), поэтому может «отделить» `v` от `B`:

```
S_client = (B - k·g^x)^(a + u·x) mod N
```

Сервер знает `v` и `b`:

```
S_server = (A · v^u)^b mod N
```

где `u = H(A || B)`. Математика подобрана так, что `S_client = S_server`. Оба получают общий секрет `S` — и из него через KDF выводят сессионный ключ. Дальше они обмениваются подтверждениями `M1`, `M2` (HMAC от `S` и транскрипта), чтобы убедиться, что пароль у обоих совпал.

## Шаг 3: почему нет офлайн-оракула

Подслушавший видит `A`, `B`, `s`, `M1`, `M2`, но не может проверить догадку о пароле без **взаимодействия с сервером или клиентом**: каждая догадка требует живого обмена, а сервер может ограничить число попыток. Это ключевое свойство PAKE. Если же атакующий украл `v` из базы — офлайн-перебор возможен, потому что `v` детерминированно зависит от пароля. Поэтому PAKE не спасает от слабых паролей и утечки верификаторов.

## Шаг 4: другие PAKE

- **SPAKE2** — проще SRP: обе стороны «сдвигают» свои DH-ключи на `H(password)` и обмениваются ими; не требует верификатора на сервере, поэтому подходит для симметричных PAKE.
- **OPAQUE** — самый современный: сервер хранит не верификатор, а **OPRF**-обёртку (oblivious pseudorandom function), поэтому даже утечка базы не даёт офлайн-оракула. Клиент никогда не отправляет пароль, а получает «зашифрованный» ключ.

## Полный прогон

В лабе даны `srp.txt` (N, g, соль, A, B, u) и скрипт `srp.py`. Скрипт считает общий секрет `S` для известного словарного пароля и печатает флаг:

```
$ cat srp.txt
N = ...
g = 2
s = 8f2c...
A = ...
B = ...
u = ...

$ python3 srp.py
candidate password: hunter2
S = 4d1a... (32 bytes)
M1 = ...
flag: nto{srp_v3r1f13r_0ffl1n3_4tt4ck}
```

Здесь показан именно сценарий утечки верификатора: зная `v` (или подбирая его по словарю) и перехватив `A`/`B`, атакующий восстанавливает `S` — потому что пароль слабый. Урок: PAKE защищает канал, но не слабый пароль.

## Если не сработало

Если `S` не совпадает, проверь формулу `u` и порядок `A || B`. Если сервер не хранит `v` (как в OPAQUE) — офлайн-атака по словарю не пройдёт, и нужно искать другую уязвимость. Если протокол использует `k = H(N || g)`, не забудь его в `B` — иначе `S` не сойдётся.

## Полная алгебра SRP-6a

Соберём все формулы SRP-6a в одном месте. Параметры: большое простое `N`, генератор `g`, хэш `H`. Регистрация:

```
x = H(s || H(I || ':' || P))        # I — логин, P — пароль, s — соль
v = g^x mod N                        # верификатор, хранится на сервере
```

Рукопожатие:

```
A = g^a mod N                        # клиент -> сервер
k = H(N || g)                        # общий множитель
B = (k*v + g^b) mod N                # сервер -> клиент
u = H(A || B)                        # скремблер
S_client = (B - k*g^x)^(a + u*x) mod N
S_server = (A * v^u)^b mod N         # S_client == S_server
K = H(S)                             # сессионный ключ
M1 = H(H(N) XOR H(g) || H(I) || s || A || B || K)   # доказательство клиента
M2 = H(A || M1 || K)                 # доказательство сервера
```

Проверка: `(B − k·g^x) = g^b` в поле, значит `S_client = g^(b(a+ux))`, а `S_server = (g^a·g^(ux))^b = g^(b(a+ux))` — совпало. Любая ошибка в `u` (порядок `A||B`) или в `k` (порядок `N||g`) даёт расхождение `S` и провал `M1`.

## Практика: srptools и spake2

```
$ pip install srptools
$ python3 - <<'PY'
from srptools import SRPContext, SRPClientSession, SRPServerSession
ctx = SRPContext('alice', 'hunter2')
username, password_verifier, salt = ctx.get_user_credentials()
client = SRPClientSession(SRPContext('alice', 'hunter2'))
server = SRPServerSession(SRPContext('alice', verifier=password_verifier, salt=salt))
A = client.compute_public()
B = server.compute_public(A, salt)
c_shared, M1 = client.compute_shared_key(salt, B, server.compute_public.__self__.k)
print(M1.hex())
PY
```

Для SPAKE2 есть `spake2` (из `python-spake2`): стороны вызывают `start()` и `finish()`, а пароль передаётся строкой. Обе библиотеки следуют спецификации, поэтому не изобретай велосипед.

## SPAKE2 детально

SPAKE2 не требует верификатора: сервер не хранит ничего, кроме соли и, опционально, отпечатка. Обе стороны сдвигают свои DH-ключи на точку, зависящую от пароля:

```
Alice: X = g^x + H(pw)·M          # M — фиксированная точка
Bob:   Y = g^y + H(pw)·N          # N — другая фиксированная точка
```

Обменявшись `X` и `Y`, каждая сторона «вычитает» свою парольную часть и получает общий секрет. Точки `M`, `N` должны быть выбраны так, чтобы их дискретные логарифмы были неизвестны никому — иначе протокол ломается. SPAKE2 подходит для симметричного сценария (обе стороны знают пароль), а его вариант SPAKE2+ добавляет серверный верификатор, как в SRP.

## OPAQUE: OPRF и почему база не даёт оракула

**OPAQUE** — самый современный aPAKE. Сервер хранит не верификатор пароля, а **OPRF**-обёртку (oblivious pseudorandom function, обычно на базе OPRF-схемы VOPRF): сервер вычисляет `F_k(H(pw))` слепым способом, не видя `H(pw)`, и клиент получает «обёрнутый» ключ, которым расшифровывает свою ключевую пару. При утечке базы атакующий получает только `k` и обёртки; для офлайн-перебора ему нужно выполнить OPRF для каждого кандидата — а это дороже, чем один хэш. Поэтому OPAQUE — стандарт IETF (RFC 9807) и рекомендуется для новых систем.

## Атаки: словарь, precomputation и MITM

- **Офлайн-словарь при утечке верификатора:** в SRP `v = g^x` детерминирован — перебор пароля офлайн возможен. PAKE этого не отменяет.
- **Precomputation:** атакующий заранее строит таблицу `x → v` для популярных паролей; спасает только соль (уникальная для каждого пользователя).
- **MITM при отсутствии аутентификации сервера:** SRP/SPAKE2 аутентифицируют **обе** стороны (сервер доказывает знание `v` через `M2`), но если клиент не проверяет `M2` — MITM проходит.
- **Слабая группа:** если `N` составное или `g` малого порядка, секрет утекает; бери стандартную группу из RFC 5054.

## Что дальше / решение

PAKE — это про то, как доказать знание пароля, не дав подслушивающему офлайн-оракул. SRP прост и вездесущ, но при утечке верификатора слабый пароль всё равно перебирается; OPAQUE устраняет и это. Выбирай по задаче: SRP для совместимости, SPAKE2 для симметричного случая, OPAQUE для новых систем.

| Схема | Хранит сервер | Офлайн-оракул при утечке | Стандарт |
|---|---|---|---|
| SRP-6a | соль + v | да (по словарю) | RFC 5054 |
| SPAKE2 | соль | нет | RFC 9382 |
| SPAKE2+ | соль + верификатор | ограничен | RFC 9383 |
| OPAQUE | соль + OPRF-обёртка | нет | RFC 9807 |
