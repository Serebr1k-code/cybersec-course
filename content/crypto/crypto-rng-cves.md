## Вопрос, с которого всё начинается

Что если ключи сгенерированы «почти случайно»? Именно так произошло несколько раз, и последствия были катастрофическими: миллионы ключей оказались слабыми. Разберём одну из атак — общий простой множитель — на конкретном примере двух RSA-ключей.

## Наш пример: два ключа с общим множителем

У нас `keys.txt` с двумя RSA-модулями `n1` и `n2`. Из-за нехватки энтропии генератор выдал один и тот же простой множитель `p`.

```
$ cat keys.txt
n1 = 32317006071311...
n2 = 32317006071311...
```

## Шаг 1: атака через GCD

Если `n1 = p*q1` и `n2 = p*q2`, то наибольший общий делитель `gcd(n1, n2) = p` (при условии `q1 != q2`). Это вычисляется алгоритмом Евклида за логарифмическое время — даже для 2048-битных чисел мгновенно.

```python
from math import gcd
p = gcd(n1, n2)   # общий простой множитель
```

```
$ python3 gcd.py
shared prime found: True
p bit_length = 512
flag: nto{sh4r3d_pr1m3_br34ks_b0th_k3ys}
```

## Шаг 2: batch-GCD и реальный масштаб

Атака масштабируется: имея **миллионы** публичных ключей, можно найти **все** пары с общим множителем, вычисляя произведение всех `n_i` и применяя «batch-GCD» (произведение по дереву). Так находят слабые ключи в интернете: сканируют TLS-сертификаты и SSH-ключи, затем считают GCD попарно. В 2012 году так нашли десятки тысяч слабых ключей.

## Шаг 3: Debian OpenSSL (2006-2008)

Самая известная катастрофа. Разработчик Debian закомментировал строку в OpenSSL, которая добавляла «неинициализированную память» в пул энтропии (это убрало предупреждение valgrind, но и лишило генератор энтропии). В результате OpenSSL стал генерировать ключи только из **PID** — всего 32768 возможных ключей для каждого типа. Все SSH- и TLS-ключи, созданные на Debian/Ubuntu в те годы, оказались предсказуемыми. Атака: перебрать 32768 ключей и проверить совпадение с публичным.

## Шаг 4: Android SecureRandom (2013) и ROCA (2017)

- **Android SecureRandom**: баг в `SecureRandom` (Android 4.1-4.3) приводил к повторению «случайных» значений для Bitcoin-кошельков; злоумышленники украли сотни BTC.
- **ROCA** (CVE-2017-15361): библиотека Infineon генерировала RSA-ключи с **структурной** слабостью — простые множители имели специальную форму, что позволяло факторизовать ключ быстрее (Coppersmith). Затронуты миллионы смарт-карт, TPM и YubiKey 4.

## Полный прогон от начала до конца

1. `cat keys.txt` — два модуля.
2. Считаем `gcd(n1, n2)`.
3. Находим общий простой множитель.
4. `python3 gcd.py | grep nto > found.txt`.

## Если не сработало

Если `gcd == 1` — ключи не делят множитель, ищи другую слабость (ROCA-детект, маленький `d`, общий `p` в пределах одной организации). Если модули разной длины, GCD всё равно работает. Для ROCA есть готовые детекторы (проверка формы простого множителя); для batch-GCD — инструменты вроде `badkeys` или собственный скрипт на GMP.

## ROCA детальнее

ROCA (Return of Coppersmith's Attack) — уязвимость генератора простых чисел Infineon, обнаруженная в 2017 году. Библиотека генерировала простые числа специального вида: `p = k * M + 65537`, где `M` — произведение первых простых чисел. Такая структура означает, что `p mod M = 65537` **всегда** — то есть младшие биты простого числа предсказуемы.

Атака: зная структуру, можно применить **метод Копперсмита** (поиск малых корней полиномов по модулю) и факторизовать ключ значительно быстрее, чем перебор. Практически: 2048-битный ключ ROCA факторизуется за недели на кластере — недостижимо для честного RSA, но реально. Затронуты миллионы смарт-карт, TPM, YubiKey 4, некоторые Estonian ID-карты.

Детект: проверяется, имеет ли модуль `n` вид, характерный для ROCA (тест по «отпечатку»). Готовые детекторы есть в `badkeys` и `roca-detect`.

## Как детектировать слабые ключи массово

Современный подход к аудиту ключей:

1. **Batch-GCD**: собрать все публичные ключи (сертификаты, SSH, PGP), вычислить попарные GCD через дерево произведений. Находит общие множители.
2. **ROCA-детект**: проверить каждый модуль на структурный отпечаток.
3. **Проверка малого `d`**: атака Винера/Боне-Дюрфе (см. `crypto-rsa-wiener-bonedurfee`).
4. **Проверка Ферма**: если `p` и `q` близки, `n` факторизуется разностью квадратов.
5. **Проверка энтропии seed**: если ключ сгенерирован детерминированно, его можно воспроизвести.

Инструмент `badkeys` объединяет эти проверки и сканирует наборы ключей. Для bug bounty и аудита инфраструктуры это стандартная процедура.

## Уроки из катастроф

- **Энтропия важна не меньше алгоритма.** Слабый seed ломает даже 2048-битный RSA.
- **Ошибки в библиотеках масштабируются.** Один баг в OpenSSL/Infineon затронул миллионы систем.
- **Массовый детект работает.** Слабые ключи находятся партиями, а не по одному.
- **Не изобретай генератор.** Используй проверенный CSPRNG и стандартные библиотеки.

## Разбор: факторизация структурно слабого ключа

Покажем, как структурная слабость ускоряет факторизацию. Пусть простой множитель имеет вид `p = k*M + c`, где `M` известно, а `c` мало. Тогда `n = p*q`, и мы знаем `p mod M = c mod M`. Это даёт систему, которую решает **метод Копперсмита**: находим малый корень полинома `f(x) = (M*x + c) mod n`. Если корень достаточно мал, он находится за полиномиальное время.

```python
# псевдокод Coppersmith для малого корня
# f(x) = M*x + c  (mod n), ищем x0 < n^(1/2) такое что gcd(f(x0), n) > 1
```

Именно так ломается ROCA: структура `p mod M = 65537` даёт полином с известными коэффициентами, и Копперсмит находит `p`. Без структуры это было бы эквивалентно обычной факторизации.

Вывод: **недостаточно, чтобы числа были «простыми»** — они должны быть **неструктурированными**. Генератор, который добавляет предсказуемость (общий модуль, фиксированные биты), разрушает RSA.

## Частые вопросы

**Что делать, если gcd(n1,n2)=1?** Значит, эти два ключа не делят множитель. Но в наборе из миллионов ключей пары найдутся. Для одиночного ключа ищи другие слабости: малый `d` (Винер), близкие `p` и `q` (Ферма), ROCA-структуру, малую энтропию seed.

**Насколько реальна атака shared primes?** Очень. Исследования сканировали TLS/SSH-ключи и находили десятки тысяч слабых. Причина — виртуальные машины, клонированные образы и слабые RNG. Если два устройства использовали один seed (например, при клонировании VM), их ключи делят множитель.

**Почему ROCA не поймали раньше?** Структура была тонкой: `p mod M = 65537` для большого `M`. Проверка простоты такие числа проходит, а RSA работает — пока не применяешь Копперсмита. Уязвимость нашлась только в 2017 году после планомерного анализа.

**Как защититься?** Использовать проверенные библиотеки с качественным RNG, проверять ключи инструментами (`badkeys`), ротировать ключи, сгенерированные до известных фиксов (Debian, ROCA).

## Что мы теперь знаем

- Общий простой множитель ломает оба ключа через `gcd`.
- Batch-GCD находит слабые ключи в масштабе интернета.
- Debian OpenSSL свёл энтропию к PID (32768 ключей).
- Android SecureRandom и ROCA — реальные катастрофы.
- Слабые ключи детектируются массово (badkeys, ROCA-детектор).
