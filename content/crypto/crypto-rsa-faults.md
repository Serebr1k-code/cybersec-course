## Вопрос, с которого всё начинается

Сервер подписывает сообщения RSA-CRT — быстрее, чем обычный RSA, но ценой хрупкости. Одна из выданных подписей **не проходит проверку**: `pow(s, e, n) != c`. Казалось бы, мелочь — но именно эта «испорченная» подпись мгновенно выдаёт факторизацию модуля `n`. Разберём атаку Bellcore на реальном примере.

## Наш пример

Сгенерируем RSA-ключ и подпишем сообщение CRT-методом, а затем внесём ошибку в одну из половин:

```python
from sympy import nextprime
from math import gcd
p = nextprime(2**256); q = nextprime(2**257)
n = p*q; e = 65537
d = pow(e, -1, (p-1)*(q-1))
msg = 0x41424344; c = pow(msg, e, n)

dp = d % (p-1); dq = d % (q-1); qinv = pow(q, -1, p)
mp = pow(c, dp, p); mq = pow(c, dq, q)
mp_bad = (mp + 1) % p          # сбой в одной половине!
s_bad = (mq + q * ((qinv * (mp_bad - mq)) % p)) % n
```

Получили подпись `s_bad`. Вопрос: как по ней и по `c` восстановить `p` и `q`?

## Шаг 1: как работает RSA-CRT

RSA-CRT ускоряет подпись вдвое, считая возведение по модулям `p` и `q` раздельно:

```
d_p = d mod (p−1),  d_q = d mod (q−1),  q_inv = q^{−1} mod p
m_p = c^{d_p} mod p
m_q = c^{d_q} mod q
s = m_q + q·(q_inv·(m_p − m_q) mod p)      # mod n
```

Затем собирает результат по китайской теореме об остатках. Именно эта раздельность — источник уязвимости.

## Шаг 2: одна ошибка ломает всё

Пусть в `m_p` произошла ошибка: `m_p' = m_p + Δ`. Тогда:

```
s' = m_q + q·(q_inv·(m_p' − m_q) mod p)
```

Проверим на числах:

```python
print("signature invalid:", pow(s_bad, e, n) != c)
g = gcd(pow(s_bad, e, n) - c, n)
print("gcd factor == q:", g == q)
```

```
signature invalid: True
gcd factor == q: True
```

Подпись действительно не проходит проверку, и `gcd` мгновенно дал `q`. Почему? Потому что `s'^e ≡ c (mod q)`, но `s'^e ≢ c (mod p)` — ошибка была только в `p`-половине. Значит, `s'^e − c` делится на `q`, но не на `p`, и их общий делитель с `n = p·q` — ровно `q`.

## Шаг 3: восстановление ключа

Дальше всё стандартно:

```python
p_rec = n // g
phi = (p_rec - 1) * (q - 1)
d_rec = pow(e, -1, phi)
m = pow(c, d_rec, n)
print(m.to_bytes(4, 'big'))
```

```
b'ABCD'
```

Мораль: ошибка в одном модульном возведении «протекает» через тот множитель, который **не** был испорчен.

## Шаг 4: как вносят сбой

- **Аппаратно:** провал питания (voltage glitch), сбой клока, лазер, EM-импульс (ChipWhisperer).
- **Программно:** если сервис подписывает «испорченным» кодом (округление, переполнение, race).
- **CTF:** обычно дают `(n, e, c, s)` с подсказкой «одна из подписей неверна».
- **Обнаружение:** проверьте `pow(s, e, n) == c` для каждой подписи; неверная — цель.

## Шаг 5: несколько подписей

На практике дают пачку подписей, и лишь одна «сломана». Алгоритм — перебрать все:

```python
def try_factor(n, e, pairs):
    for c, s in pairs:
        if pow(s, e, n) == c:
            continue                     # подпись валидна
        g = gcd(pow(s, e, n) - c, n)
        if 1 < g < n:
            return g, n // g
    return None
```

Если `gcd` вернул `1` или `n` — сбой был «двусторонним» (испорчены обе половины) или подпись валидна. Перебирайте все подписи: в CTF часто лишь одна из многих ошибочна.

## Шаг 6: варианты и контрмеры

- **Ошибка в `d_p`** (не в `m_p`) — GCD даёт множитель через другое соотношение, идея та же.
- **Boneh-DeMillo-Lipton** — общая теория: сбой в любой реализации с проверкой даёт факторизацию.
- **Fault в padding/OAEP** — может дать Bleichenbacher-подобный оракул.
- **Fault + partial key** — комбинируется с `crypto-rsa-partial-key`.

Контрмеры: **верификация подписи перед выдачей** (`pow(s, e, n) == c`), redundant computation (считать дважды и сравнить), счётчики сбоев, защита от glitch на уровне железа. Именно проверка перед выдачей — самая дешёвая и эффективная: ошибочная подпись просто не покинет устройство.

## Чек-лист и быстрые рецепты

Признаки fault-задачи:

- даны подписи, одна из которых **не проходит** `pow(s, e, n) == c`;
- в условии «подпись с ошибкой», «faulty signature», «glitch»;
- доступен оракул подписи, и можно «сбоить»;
- несколько подписей одного/разных сообщений.

Быстрая проверка: прогоните все подписи через `pow(s, e, n) == c`; для неверной возьмите `gcd(pow(s, e, n) − c, n)`. Если gcd даёт простой множитель — задача решена. Если gcd = 1 или `n` — сбой был двусторонним, ищите другую пару. Ошибка в `dp` вместо `mp` даёт другой gcd, но идея та же: ищите `gcd(что-то, n)`.

Отдельно стоит помнить: атака Bellcore работает и в обратную сторону — если сервер **проверяет** подписи, но не сверяет их перед выдачей, ошибочная подпись всё равно уходит клиенту, и клиент (или мы) может факторизовать модуль. Поэтому в реальных устройствах подпись обязательно верифицируют **перед** возвратом, а само вычисление дублируют (redundant computation) для детекции сбоя.

## Что мы теперь знаем

- Одна ошибочная CRT-подпись RSA даёт **факторизацию** `n`.
- Атака: `gcd(pow(s, e, n) − c, n)` → множитель.
- Ошибка в `p`-половине протекает через `q` (и наоборот).
- Атака называется **Bellcore** (Boneh-DeMillo-Lipton).
- Сбой вносят питанием/клоком/лазером/EM; в CTF его «дают» в условии.
- Контрмера — верификация подписи **перед** выдачей.

## На что смотреть дальше

- **Не проверить, какая подпись ошибочна** — gcd по верной даст `n`.
- **Использовать `s^e − c` без `mod n`** — вычисляйте `pow(s, e, n) − c`, затем `gcd(..., n)`.
- **Обе половины испорчены** — тогда gcd = 1; ищите другую пару.
- **Путать `d` и `d_p`** — ошибка в `d_p` даёт множитель, в `d` — иногда тоже, но иначе.
- **Считать, что нужен полный сбой** — достаточно односторонней ошибки.
- **Игнорировать подсказку** — «подпись с ошибкой» почти всегда Bellcore.
