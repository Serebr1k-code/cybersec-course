## Вопрос, с которого всё начинается

Хэш-функции первого поколения (MD5, SHA-1, SHA-2) уязвимы к **length-extension**: зная `H(m)`, можно вычислить `H(m || padding || extra)`, не зная `m`. Именно поэтому нельзя использовать `H(secret || msg)` как MAC. Но SHA-3 построен принципиально иначе и к length-extension устойчив. Разберём, как устроена **sponge-конструкция** и в чём её отличие.

## Наш пример

Возьмём одну строку `hello` и посмотрим, как её хэшируют три функции:

```python
import hashlib
print("sha256  :", hashlib.sha256(b'hello').hexdigest())
print("sha3_256:", hashlib.sha3_256(b'hello').hexdigest())
print("shake16 :", hashlib.shake_256(b'hello').hexdigest(16))
```

```
sha256  : 2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824
sha3_256: 3338be694f50c5f338814986cdf0686453a888b84f424d792af4b9202398f392
shake16 : 1234075ae4a1e77316cf2d8000974581
```

`sha256` и `sha3_256` дают разные хэши — ожидаемо, это разные функции. Но `shake` — особенный: он выдаёт **сколько угодно** байт. Вопрос: почему SHA-3 устроен иначе и чем это важно для безопасности?

## Шаг 1: как устроен sponge

Sponge работает с **состоянием** из `b` бит (для SHA-3 `b = 1600`). Состояние делится на две части:

- **rate** `r` — часть, которая «взаимодействует» с сообщением (скорость);
- **capacity** `c` — внутренняя часть, обеспечивающая безопасность.

Причём `b = r + c`. Есть функция `f` — **перестановка** состояния: детерминированная, обратимая, но нелинейная и «хаотичная» (в Keccak — 24 раунда).

## Шаг 2: absorbing и squeezing

Процесс состоит из двух фаз. **Absorbing (впитывание):** состояние обнуляется; сообщение дополняется до кратности `r`; каждый блок `r` бит XOR-ится с rate-частью; применяется перестановка `f`; повтор для всех блоков. **Squeezing (отжим):** выход берётся из rate-части; если нужно больше — применяется `f` и снова берётся rate-часть.

Именно поэтому `shake` может выдать сколько угодно байт: это XOF (extendable output function). Проверим, что выходы разной длины **префикс-согласованы**:

```python
print(hashlib.shake_256(b'hello').hexdigest(32))
```

```
1234075ae4a1e77316cf2d8000974581a343b9ebbca7e3d1db83394c30f22162
```

Первые 16 байт совпадают с `shake16` — это и есть «отжим» одной и той же губки на разную длину.

## Шаг 3: почему length-extension не работает

В Merkle–Damgård `H(m)` — это **финальное состояние**, совпадающее с внутренним. Поэтому `H(m || pad || extra)` вычисляется продолжением с `H(m)` как «IV». В sponge выход — это лишь **часть** состояния (rate), а capacity остаётся секретом. Атакующий, зная `H(m)`, не знает capacity и не может корректно продолжить absorbing. Поэтому `H(secret || msg)` в sponge не даёт length-extension. Но это **не значит**, что так можно делать MAC: используйте HMAC или KMAC.

## Шаг 4: rate, capacity и безопасность

Стойкость sponge определяется **capacity**, а скорость — rate:

| Вариант | `b` | `r` | `c` | Стойкость |
|---------|-----|-----|-----|-----------|
| SHA3-224 | 1600 | 1152 | 448 | 112 |
| SHA3-256 | 1600 | 1088 | 512 | 128 |
| SHA3-384 | 1600 | 832 | 768 | 192 |
| SHA3-512 | 1600 | 576 | 1024 | 256 |

Больше rate — быстрее, но меньше capacity и слабее. Именно поэтому SHA3-512 медленнее SHA3-256: у него rate меньше, а capacity больше.

## Шаг 5: атака на слабый capacity

В CTF часто дают **самодельный** sponge с крошечным capacity. Тогда скрытую часть состояния можно просто перебрать. Соберём игрушечную губку с `b = 16`, `r = 12`, `c = 4` бита:

```python
B, R, C, MASK = 16, 12, 4, (1 << 16) - 1
def f(s):
    s = (s ^ (s >> 2)) & MASK
    return (s * 0x9E37 + 0x1234) & MASK
def absorb(msg, st=0):
    for b in msg:
        st ^= (b & ((1 << R) - 1)) << C
        st = f(st)
    return st
def squeeze(st, n):
    out = []
    for _ in range(n):
        out.append((st >> C) & ((1 << R) - 1)); st = f(st)
    return out
```

Подаём два байта и смотрим выходы:

```python
st = absorb([0xAB, 0xCD])
outs = squeeze(st, 3)
print("outs:", [hex(o) for o in outs])
```

```
outs: ['0x825', '0x3eb', '0x1ad']
```

Атакующий видит `outs` и не знает младшие `c = 4` бита состояния. Переберём все `2^4` вариантов и оставим те, что дают тот же выход:

```python
for cand in range(1 << C):
    guess = (outs[0] << C) | cand
    if squeeze(guess, 3) == outs:
        print("recovered state: %04x" % guess)
```

```
recovered state: 8252
```

Состояние восстановлено, потому что capacity всего 4 бита. Вывод: **стойкость sponge определяется capacity**; малый `c` фатален, даже если выход длинный.

## Шаг 6: Keccak изнутри

Перестановка Keccak-f[1600] — это 24 раунда, каждый из которых применяет пять шагов: `θ` (theta, XOR-смешивание по столбцам), `ρ` (rho, циклические сдвиги), `π` (pi, перестановка дорожек), `χ` (chi, единственная нелинейная операция) и `ι` (iota, XOR раундовой константы). Нелинейность даёт именно `χ`, остальные шаги — диффузию. Полный Keccak стоек; атаки касаются только редуцированных версий с малым числом раундов.

## Шаг 7: sponge — это не только хэш

Режим **duplex** позволяет чередовать absorbing и squeezing, и из него строят AEAD-шифрование (например, Ascon, выбранный NIST для lightweight-криптографии), MAC (KMAC), KDF/PRF (cSHAKE, KMAC) и XOF (SHAKE). Одна и та же перестановка используется и для хэша, и для шифрования — меньше кода, меньше багов. Отдельная тонкость — **доменное разделение через padding**: SHA-3 использует `0x06`, SHAKE — `0x1F`, cSHAKE добавляет строку домена. Если реализация путает padding, один вход в разных режимах может дать связанные выходы. Поэтому при аудите самодельных sponge первым делом проверяйте именно padding-байты.

## Что мы теперь знаем

- Sponge работает с состоянием `b = r + c`; безопасность даёт **capacity**.
- **Absorbing** XOR-ит блоки в rate-часть, **squeezing** выдаёт выход из rate-части.
- Выход sponge — только часть состояния, поэтому **length-extension невозможен**.
- SHA-3 — это Keccak с padding `0x06`; SHAKE — XOF.
- Малый capacity → состояние восстанавливается перебором.
- Отсутствие length-extension ≠ «можно `H(secret||msg)` как MAC».

## На что смотреть дальше

- **Путать rate и capacity** — безопасность даёт capacity, скорость — rate.
- **Считать SHA-3 «просто другим SHA-2»** — конструкция принципиально иная.
- **Использовать `H(secret||msg)` как MAC** — отсутствие length-extension не делает это безопасным.
- **Игнорировать padding** — неверный padding даёт неоднозначность и связанные выходы.
- **Малый `c` в самодельных sponge** — самая частая CTF-ловушка.
