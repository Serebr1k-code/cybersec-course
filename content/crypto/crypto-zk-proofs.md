## Зачем это нужно

**Доказательство с нулевым разглашением (ZK)** позволяет доказать утверждение («я знаю секрет», «сумма лежит в диапазоне»), не раскрывая сам секрет. Это ядро современной приватности: ZK-аутентификация, ZK-rollups в блокчейне, range proofs в конфиденциальных транзакциях, доказательства корректности в MPC. И, что важно для нас, ZK-протоколы регулярно ломаются на практике — из-за слабого nonce, повторно используемых челленджей, ошибок в Fiat–Shamir или отсутствия привязки к контексту.

На CTF ZK встречается в двух видах: (1) «даны транскрипты, восстанови секрет» (обычно из-за повторного nonce) и (2) «обойди проверку» (из-за ошибки в преобразовании или отсутствия проверок). Понимание сигма-протоколов даёт ключ к обоим.

## Интерактивные доказательства и Sigma-протоколы

Классический ZK — интерактивный, с тремя шагами (отсюда «сигма», Σ):

1. **Commitment**: доказывающий посылает `a` (обязательство).
2. **Challenge**: проверяющий посылает случайный `c`.
3. **Response**: доказывающий посылает `z`, и проверяющий проверяет соотношение.

Свойства: **completeness** (честный проходит), **soundness** (обманщик не проходит с высокой вероятностью), **zero-knowledge** (проверяющий не узнаёт ничего сверх утверждения — существует симулятор, порождающий неотличимые транскрипты).

Ключевое требование — **челлендж `c` должен быть непредсказуем и свеж** для каждой сессии. Если `c` предсказуем или переиспользуется, симулятор «утекает» в реальность, и секрет восстанавливается.

## Schnorr: доказательство знания дискретного логарифма

Пусть `g` — образующий группы порядка `q`, `y = g^x` — открытый ключ, `x` — секрет. Schnorr доказывает знание `x`:

1. Доказывающий выбирает случайный `k`, посылает `a = g^k`.
2. Проверяющий посылает случайный `c`.
3. Доказывающий посылает `z = k + c*x mod q`.
4. Проверяющий проверяет `g^z == a * y^c`.

Корректность: `g^z = g^(k+cx) = g^k * (g^x)^c = a * y^c`.

**Атака при переиспользовании `k`**: если доказывающий использует один и тот же `k` для двух разных `c1, c2`, то

```
z1 = k + c1*x
z2 = k + c2*x
z1 - z2 = (c1 - c2)*x  →  x = (z1 - z2) / (c1 - c2) mod q
```

Это ровно та же алгебра, что в ECDSA с повторным nonce. Классическая CTF-задача: даны два транскрипта с одинаковым `a = g^k` — восстановить `x` за одну формулу.

```python
def recover_x(z1, z2, c1, c2, q):
    return ((z1 - z2) * pow(c1 - c2, -1, q)) % q
```

## Fiat–Shamir и его ловушки

Чтобы сделать доказательство неинтерактивным, челлендж заменяют на хэш транскрипта: `c = H(a || context)`. Это **преобразование Фиата–Шамира**. Оно превращает интерактивный протокол в подпись (Schnorr-подпись — это ровно Fiat–Shamir от Schnorr-протокола).

Ловушки:

- **Забыли включить `a` в хэш** → доказывающий может подобрать `a` после выбора `c` (нет soundness).
- **Не привязали контекст** (сообщение, домен, идентификатор) → **replay**: доказательство для одного контекста принимается в другом. Классика — «frozen heart»: переиспользование доказательства между разными применениями.
- **Слабый хэш** → коллизии позволяют подделать.
- **Предсказуемый `k`** → та же атака, что выше, даже без повтора (если `k` выводится из известного seed).

## Инструменты и команды

- **SageMath** — арифметика в группе, восстановление `x`, проверки.
- **Python + `ecdsa`/`py_ecc`** — Schnorr и эллиптические версии.
- **`zkproof`/`circom`/`snarkjs`** — для zk-SNARK (не для CTF-формул, но полезно знать).
- **`fiat-shamir`-фреймворки** — библиотеки, где ошибки преобразования встречаются.

Пример проверки Schnorr:

```python
q = 2**252 + 27742317777372353535851937790883648493
def verify(g, y, a, c, z, q):
    return pow(g, z, q) == (a * pow(y, c, q)) % q
```

## Разобранный пример: восстановление секрета из двух транскриптов

Дано: `g = 5`, `q` — простое, `y = g^x`. Два транскрипта: `(a, c1, z1)` и `(a, c2, z2)` с одинаковым `a`.

1. Проверяем, что `a` совпадает — значит, `k` переиспользован.
2. Вычисляем `x = (z1 - z2) * (c1 - c2)^{-1} mod q`.
3. Проверяем: `g^x == y`.

```python
g, q = 5, 101
y = pow(g, 42, q)              # секрет x = 42
k = 17
a = pow(g, k, q)
c1, z1 = 3, (k + c1_secret)    # в задаче даны
# ... считаем x и сверяем
```

В реальной задаче числа большие, но формула та же. Это один из самых частых сюжетов ZK-задач.

## Другие атаки на ZK

- **Replay/frozen heart**: доказательство, валидное в одном контексте, принимается в другом.
- **Malicious challenge**: проверяющий выбирает `c` так, чтобы извлечь информацию (например, `c = 0` даёт `z = k`, раскрывая `a`).
- **Weak Fiat–Shamir**: `c` не зависит от `a` — можно подделать.
- **Small subgroup**: если `y` в малой подгруппе, можно вычислить `x` по модулю порядка подгруппы (аналог invalid-curve).
- **Nonce bias**: если `k` «почти случайный» (мало энтропии), работает решёточная атака (hidden number problem).

## Применения ZK в реальном мире

ZK-доказательства перестали быть академической экзотикой и лежат в основе нескольких крупных технологических направлений.

**zk-SNARK и zk-STARK.** Это неинтерактивные доказательства с **сукцинктивным** размером (от нескольких сотен байт) и быстрой проверкой. Они позволяют доказать корректность вычисления, не раскрывая входы. Главное применение — **ZK-rollups** в блокчейне: тысячи транзакций сворачиваются в одну, и доказательство подтверждает их корректность. Разница: SNARK требует доверенного setup (или универсального, как у PLONK), STARK — прозрачный, но крупнее.

**Range proofs (Bulletproofs).** Доказательство, что скрытое значение лежит в диапазоне (например, сумма транзакции неотрицательна), без раскрытия самого значения. Используется в конфиденциальных транзакциях (Monero, Mimblewimble). Именно отсутствие range proof в наивной гомоморфной агрегации позволяет «проголосовать» большим числом — см. `crypto-homomorphic`.

**ZK-аутентификация.** Протоколы типа Schnorr/Fiat–Shamir позволяют доказать знание пароля/ключа, не передавая сам ключ. Это устраняет утечку через перехват и снижает риск replay (при правильной привязке контекста).

**Приватные вычисления.** В `crypto-threshold-mpc` ZK используется, чтобы участники доказывали корректность своих шагов, не раскрывая входы — так строится защита от вредоносных участников.

Для пентестера важно понимать: во всех этих системах ZK **не делает** вас анонимным и не защищает от ошибок **вне** протокола (утечка через timing, слабый setup, отсутствие проверок входов). Часто «ZK-систему» ломают не математически, а через side-channel или ошибку реализации. Ищите именно такие щели: предсказуемые nonce, отсутствие привязки контекста, доверенный setup с утечкой «токсичных отходов» (toxic waste).

## Атака «frozen heart» подробнее

Frozen heart — не один баг, а целый класс уязвимостей неинтерактивных ZK-доказательств (Schnorr, GQ, Bulletproofs, zk-SNARK в некоторых реализациях), при котором доказательство, валидное в одном контексте, принимается в другом. Название отсылает к «замороженному» доказательству, которое можно разморозить в неподходящем месте.

Классический пример: протокол проверяет `g^z == a * y^c` с `c = H(a)`, не включая в хэш **назначение** доказательства. Тогда одно и то же `(a, z)` подходит и для входа в систему, и для подписи транзакции, и для доказательства владения ключом. Атакующий, получив доказательство в «безобидном» контексте, переиспользует его там, где это даёт выгоду.

Лечение стандартно и обязательно: **доменно-разделённый хэш**. Вместо `c = H(a)` используют `c = H(a || purpose || message || nonce)`, где `purpose` — уникальный идентификатор применения, `message` — привязка к данным, а `nonce`/timestamp исключает повтор. В современных библиотеках это оформлено как «transcript» или «context string», который должен быть **уникален для каждого применения** и **различаться между протоколами**.

Практический совет: при аудите ZK-кода ищите формулу челленджа. Если она хэширует только `a` (или только сообщение), без домена и контекста, — перед вами frozen heart. На CTF это часто и есть решение: доказательство, «украденное» из одного эндпоинта, принимается в другом.

## Частые ошибки и подводные камни

- **Повтор `k`** — мгновенная компрометация секрета.
- **Не включать `a` в хэш Fiat–Shamir** — теряется soundness.
- **Не привязывать контекст** — replay.
- **Проверять только часть уравнения** — пропуск множителя `y^c`.
- **Использовать предсказуемый генератор** для `k` — неявная утечка.
- **Считать, что ZK = анонимность** — ZK скрывает знание секрета, но не обязательно личность.

## Контрмеры и защита

- Генерируйте `k` криптостойким ГПСЧ, никогда не переиспользуйте.
- В Fiat–Shamir хэшируйте **весь** транскрипт плюс домен-разделитель и контекст.
- Проверяйте `y` на принадлежность правильной подгруппе (защита от small subgroup).
- Используйте проверенные библиотеки, а не самописные ZK-протоколы.
- Для доказательств корректности — стандартные конструкции (Bulletproofs, Groth16) вместо ручных.

## Что дальше / решение

ZK-протоколы — основа `crypto-threshold-mpc` (доказательства корректности) и `crypto-pki-signatures` (Schnorr-подписи). Дальше: `crypto-pairing` (BLS, zk-SNARK-кривые), `crypto-lattice` (ZK на решётках). На CTF ищите повтор `a`/`k` и слабый Fiat–Shamir — это два самых частых вектора.

## Справочные таблицы

| Протокол | Утверждение | Атака при ошибке |
|----------|-------------|------------------|
| Schnorr | знание `x` в `y=g^x` | повтор `k` → `x` |
| Fiat–Shamir | неинтерактивность | нет `a` в хэше → подделка |
| Bulletproofs | range proof | слабая случайность |
| Groth16 | произвольное | доверие к setup |

| Понятие | Смысл |
|---------|-------|
| completeness | честный проходит |
| soundness | обманщик не проходит |
| zero-knowledge | не узнаёт секрет |
| frozen heart | replay между контекстами |
