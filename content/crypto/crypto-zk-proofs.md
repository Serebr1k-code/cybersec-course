## Вопрос, с которого всё начинается

Как доказать, что ты знаешь секрет, **не показывая его**? Например, аутентифицироваться по приватному ключу, не отправляя ключ по сети, где его могут перехватить. Ответ — **доказательство с нулевым разглашением (ZK)**: ты доказываешь утверждение («я знаю секрет»), не раскрывая сам секрет. Это ядро ZK-аутентификации, ZK-rollups в блокчейне, range proofs в конфиденциальных транзакциях. И, что важно для нас, ZK-протоколы регулярно ломаются на практике — из-за слабого nonce, переиспользуемых челленджей или ошибок в Fiat–Shamir. Разберём два самых частых вектора на одном протоколе.

## Наш пример

Возьмём протокол **Schnorr** — доказательство знания `x` для `y = g^x mod p`. Числа учебные, чтобы всё считалось за секунду:

```python
p = 2**127 - 1
q = p - 1
g = 3
x = 0xDEADBEEF
y = pow(g, x, p)
```

## Шаг 1: что такое сигма-протокол

Классический ZK интерактивен и состоит из трёх шагов (отсюда «сигма», Σ):

1. **Commitment**: доказывающий посылает `a = g^k` (обязательство).
2. **Challenge**: проверяющий посылает случайный `c`.
3. **Response**: доказывающий посылает `z`, проверяющий проверяет соотношение.

Свойства: **completeness** (честный проходит), **soundness** (обманщик не проходит), **zero-knowledge** (проверяющий не узнаёт ничего сверх утверждения). Ключевое требование — челлендж `c` должен быть **непредсказуем и свеж** для каждой сессии.

## Шаг 2: прогоняем Schnorr

Пусть `g` — образующий, `y = g^x` — открытый ключ, `x` — секрет:

1. Доказывающий выбирает случайный `k`, посылает `a = g^k`.
2. Проверяющий посылает случайный `c`.
3. Доказывающий посылает `z = k + c·x mod q`.
4. Проверяющий проверяет `g^z == a · y^c`.

Корректность: `g^z = g^(k+cx) = g^k · (g^x)^c = a · y^c`. Знание `x` не раскрывается — `z` маскирован случайным `k`.

## Шаг 3: атака — переиспользование k

Если доказывающий использует один и тот же `k` для двух разных `c1, c2`, то

```
z1 = k + c1·x
z2 = k + c2·x
=> z1 - z2 = (c1 - c2)·x  =>  x = (z1 - z2) / (c1 - c2) mod q
```

Прогоним:

```python
k = 0x1234
a = pow(g, k, p)
c1, z1 = 0x1111, (k + 0x1111 * x) % q
c2, z2 = 0x2222, (k + 0x2222 * x) % q
x_rec = ((z1 - z2) * pow(c1 - c2, -1, q)) % q
print("recovered x:", hex(x_rec), "== x:", x_rec == x, "  g^x==y:", pow(g, x_rec, p) == y)
```

```
recovered x: 0xdeadbeef == x: True   g^x==y: True
```

Секрет восстановлен за одну формулу — это ровно та же алгебра, что в ECDSA с повторным nonce. Классическая CTF-задача: даны два транскрипта с одинаковым `a = g^k` — восстановить `x`.

## Шаг 4: Fiat–Shamir и его ловушки

Чтобы сделать доказательство неинтерактивным, челлендж заменяют хэшем транскрипта: `c = H(a || context)`. Это **преобразование Фиата–Шамира**; Schnorr-подпись — ровно Fiat–Shamir от Schnorr-протокола. Ловушки:

- **Забыли включить `a` в хэш** → доказывающий подбирает `a` после выбора `c` (нет soundness).
- **Не привязали контекст** (сообщение, домен, идентификатор) → **replay**: доказательство для одного контекста принимается в другом. Классика — «frozen heart».
- **Слабый хэш** → коллизии позволяют подделать.
- **Предсказуемый `k`** → та же атака, что выше, даже без повтора.

Покажем подделку weak Fiat–Shamir: если сервер считает `c = H(m)` **без** `a`, атакующий выбирает произвольные `z, c` и вычисляет `a = g^z · y^{-c}` — проверка проходит без знания `x`:

```python
z_f = 0x1234567
c_f = 0xABCD
a_f = (pow(g, z_f, p) * pow(pow(y, c_f, p), -1, p)) % p   # a = g^z * y^{-c}
print("forged accepted:", pow(g, z_f, p) == (a_f * pow(y, c_f, p)) % p)
```

```
forged accepted: True
```

Если сервер вычисляет `c = H(a || y || m)`, подделка невозможна: изменение `a` меняет `c`.

## Шаг 5: атака «frozen heart» подробнее

Frozen heart — не один баг, а класс уязвимостей неинтерактивных ZK-доказательств (Schnorr, GQ, Bulletproofs), при котором доказательство, валидное в одном контексте, принимается в другом. Пример: протокол проверяет `g^z == a · y^c` с `c = H(a)`, не включая в хэш **назначение** доказательства. Тогда одно и то же `(a, z)` подходит и для входа в систему, и для подписи транзакции.

Лечение стандартно: **доменно-разделённый хэш**. Вместо `c = H(a)` используют `c = H(a || purpose || message || nonce)`, где `purpose` — уникальный идентификатор применения, `message` — привязка к данным, `nonce`/timestamp исключает повтор. В современных библиотеках это оформлено как «transcript» или «context string». При аудите ZK-кода ищите формулу челленджа: если она хэширует только `a` (или только сообщение), без домена и контекста, — перед вами frozen heart.

## Шаг 6: применения и другие атаки

**zk-SNARK/zk-STARK** — неинтерактивные доказательства с сукцинктивным размером и быстрой проверкой; главное применение — ZK-rollups. **Range proofs (Bulletproofs)** — доказательство, что скрытое значение в диапазоне (используется в Monero, Mimblewimble). **ZK-аутентификация** доказывает знание ключа, не передавая его.

Другие атаки: **malicious challenge** (проверяющий выбирает `c=0`, получая `z=k`), **small subgroup** (если `y` в малой подгруппе, `x` вычисляется по модулю её порядка), **nonce bias** (почти случайный `k` ломается решёточной атакой — hidden number problem). Важно помнить: ZK **не делает** вас анонимным и не защищает от ошибок **вне** протокола — side-channel, слабый setup, отсутствие проверок входов.

## Что мы теперь знаем

- ZK-протокол доказывает знание секрета, не раскрывая его.
- Schnorr — трёхшаговый сигма-протокол: `a`, `c`, `z = k + c·x`.
- Повтор `k` восстанавливает секрет из двух транскриптов — как в ECDSA.
- Fiat–Shamir делает протокол неинтерактивным через хэш транскрипта.
- Weak Fiat–Shamir (хэш без `a`) позволяет подделать доказательство без ключа.
- **Frozen heart** — replay доказательства между контекстами; лечится доменно-разделённым хэшем.

## Почему Sigma-протокол не раскрывает секрет

Сигма-протокол — это три шага: `commit`, `challenge`, `response`. В Schnorr доказывающий знает `x` (дискретный логарифм `X = g^x`) и хочет доказать это, не выдавая `x`. Он выбирает случайное `k`, посылает `R = g^k` (commit). Проверяющий бросает случайный вызов `c` (challenge). Доказывающий отвечает `s = k + c·x mod q` (response). Проверяющий убеждается, что `g^s = R · X^c`.

Почему это zero-knowledge: `s` — это `k + c·x`, и по одному `s` нельзя выделить `x`, потому что `k` случаен. Более того, существует **симулятор**, который без знания `x` выдаёт тройки `(R, c, s)`, неотличимые от настоящих: выбираешь `s` и `c`, вычисляешь `R = g^s · X^{-c}`. Значит, протокол не передаёт знания о `x` — только подтверждает владение им. Почему это proof of knowledge: из двух разных ответов на **один и тот же** `R` с разными `c` можно вывести `x = (s1 − s2)/(c1 − c2) mod q`. Именно поэтому `k` нельзя переиспользовать.

Преобразование **Fiat–Shamir** делает протокол неинтерактивным: вызов `c` заменяется хэшем `c = H(R || message)`. Это работает, потому что хэш «связывает» `R` с сообщением и ведёт себя как случайный оракул. Но если `R` не подмешать в хэш, атакующий подбирает `R` после `c` — и подделывает доказательство. Классический тому пример — **frozen heart**: сервер принимает любые параметры, включая сгенерированные с «замороженным» nonce, и подпись подделывается.

## Если не сработало

- **Подпись не подделывается.** Проверьте, подмешан ли `R` (и контекст) в `H(...)`; если да — Fiat–Shamir корректен, ищите другой баг.
- **Нет двух подписей с одним `k`.** Для атаки на переиспользованный nonce нужны ровно два сообщения с одинаковым `R` (или одинаковым `k`); иначе `x` не выводится.
- **Проверяющий принимает `R = 0`.** Edge-case: нулевые/специальные точки ломают проверку; фильтруйте их.
- **«Frozen heart» не проходит.** Нужна реализация, принимающая атакующие параметры (малые подгруппы); в корректной библиотеке такой возможности нет.
- **Replay.** Если у протокола нет привязки к сессии/сообщению, старую подпись можно переиграть — это отдельная уязвимость.

## Частые вопросы

**Почему нельзя переиспользовать `k`?** Как в ECDSA: два ответа с одним `k` дают `x = (s1 − s2)/(c1 − c2)`. Утечка `k` = утечка ключа.

**Чем Schnorr отличается от ECDSA?** Оба — сигма-подобные, но Schnorr линеен (проще агрегировать и делать threshold-подписи), ECDSA использует обратный элемент. Schnorr — основа FROST и Taproot.

**Что такое «frozen heart»?** Уязвимость реализаций (GnuTLS, OpenSSL), где не проверялись параметры криптосистемы; атакующий подставлял замороженные значения и подделывал подписи.
