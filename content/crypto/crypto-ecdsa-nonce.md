## Вопрос, с которого всё начинается

В ECDSA подпись зависит от секретного одноразового числа `k`, которое называют **nonce** («number used once»). Если подписать два разных сообщения одним и тем же `k`, приватный ключ восстанавливается из двух подписей **за секунды**, без всякого перебора. Эта ошибка встречалась в реальных устройствах (PlayStation 3, кошельки Bitcoin) и постоянно попадается в CTF. Разберём её на числах.

## Наш пример

Возьмём два сообщения, подписанных одним ключом с одним и тем же `k`. Вот подписи:

```
r  = 0xdeadbeef123456789abcdef02222333344445555666677778888
s1 = 0x4ac9e04b62058e1bdcbd153a40d353fa44e49bef2a7bf8915df8616c394d7d2
s2 = 0x9593c090d52b6f4b098e7e935e61406addfb48dd43e5ceff88bc7e931d4493e
```

Нужно восстановить приватный ключ `d`. Обрати внимание: у обеих подписей одинаковое `r` — это и есть «запах» переиспользованного nonce.

## Шаг 1: формула подписи ECDSA

Подпись ECDSA сообщения с хэшем `z` строится так:

```
r = (k·G).x mod n
s = k⁻¹ · (z + r·d) mod n
```

Здесь `n` — порядок базовой точки, `d` — приватный ключ, `k` — одноразовый секрет, `G` — базовая точка. Всё арифметическое — по модулю `n`.

Из первой строки видно: если `k` один и тот же, то и `r` один и тот же. Именно так мы и распознали проблему.

## Шаг 2: почему одинаковое r — это катастрофа

Запишем вторую строку для двух сообщений с одинаковым `k`:

```
s1 = k⁻¹ · (z1 + r·d) mod n
s2 = k⁻¹ · (z2 + r·d) mod n
```

Вычтем одно из другого:

```
s1 − s2 = k⁻¹ · (z1 − z2) mod n
```

Приватный ключ `d` из разности **исчез** — остались только известные `s1, s2, z1, z2` и неизвестное `k`. Отсюда `k` находится одним обращением по модулю:

```
k = (z1 − z2) / (s1 − s2) mod n
```

## Шаг 3: восстанавливаем k и d

Вычислим `k`, а затем подставим в формулу подписи и выразим `d`:

```
d = (s1·k − z1) / r mod n
```

Запускаем на наших числах:

```
recovered k = 0xdeadbeef123456789abcdef02222333344445555666677778888  correct: True
recovered d = 0x5eedfacecafebabe123456789abcdef0111122223333444455556666  correct: True
```

Оба секрета восстановлены точно. Никакого перебора — только школьная алгебра по модулю `n`. Это и есть атака **nonce reuse**.

## Шаг 4: смещённый nonce и решётки

Если `k` не повторяется, но **предсказуем** — например, его старшие биты всегда нули, — атака тоже работает. Это уже **biased nonce attack** на основе **Hidden Number Problem (HNP)**.

Из `s = k⁻¹(z + r·d)` выражают `k = s⁻¹(z + r·d)`. Если известно, что `k` лежит в узком диапазоне (мало «энтропии»), то каждое уравнение даёт линейное условие на `d` с маленькой ошибкой. Собирают много подписей, строят **решётку** и находят `d` редукцией LLL (та же идея, что в уроке про решётки).

На практике утечка даже нескольких бит `k` на подпись позволяет восстановить ключ по сотням подписей. Именно поэтому nonce обязан быть криптографически случайным (или детерминированным по RFC 6979 — хэш от сообщения и ключа).

## Шаг 5: как распознать в CTF

Признаки задачи на ECDSA-nonce:

- несколько подписей и у **двух одинаковое `r`** → мгновенно nonce reuse;
- подписи с маленьким `k` или `k`, генерируемым слабым PRNG (LCG) → HNP/решётка;
- в условии сказано «сервер подписал много сообщений» → скорее всего biased nonce;
- даны только `r, s, z` и публичный ключ → классическая формула выше.

Готовые инструменты: библиотека `ecdsa`, скрипты на Sage для HNP, модуль `faultyis` и подобные.

## Шаг 6: полный скрипт атаки

Соберём атаку в одном месте — её можно применить к любой паре подписей с общим `r`. Вход: `r, s1, s2, z1, z2` и порядок `n`.

```python
n = 0xFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFEBAAEDCE6AF48A03BBFD25E8CD0364141  # secp256k1
def inv(x): return pow(x, -1, n)

# 1) восстанавливаем одноразовый секрет k
k = ((z1 - z2) * inv(s1 - s2)) % n

# 2) восстанавливаем приватный ключ d
d = ((s1 * k - z1) * inv(r)) % n
print(hex(d))
```

Проверка корректности: подставь `d` и `k` обратно в формулу подписи — обе подписи должны сойтись. Если сошлись, ключ настоящий.

Обрати внимание на порядок операций: сначала `k`, потом `d`. Первый шаг не требует `r` вообще — он работает даже если `r` тебе неизвестно, лишь бы подписи были сделаны одним `k`. Второй шаг использует `r` и `s1`, чтобы «привязать» `k` к ключу.

Если `z1 = z2` (одно и то же сообщение подписано дважды), формула `k = (z1−z2)/(s1−s2)` даёт `0/0` — деление не определено. Это не значит, что атака невозможна: в этом случае `s1 = s2` (подписи идентичны), и восстановить `k` из одной подписи нельзя. Но на практике подписывают разные сообщения, так что `z1 ≠ z2` почти всегда.

## Что мы теперь знаем

- Подпись ECDSA: `r = (k·G).x`, `s = k⁻¹(z + r·d) mod n`.
- Одинаковое `r` у двух подписей = **переиспользованный nonce**.
- При повторном `k` приватный ключ находится из `k = (z1−z2)/(s1−s2)` и `d = (s1·k − z1)/r`.
- При смещённом `k` ключ восстанавливают решёткой (HNP).
- Nonce должен быть случайным или детерминированным (RFC 6979).

## На что смотреть дальше

- **Решётки: LLL** — движок, на котором стоит HNP.
- **Эллиптические кривые** — откуда берётся формула подписи.
- **Продвинутые подписи** — Schnorr, EdDSA и их защита от nonce-атак.
- **Fault attacks** — ошибочная подпись тоже выдаёт `d` через `gcd`.

## Куда дальше

В следующем уроке мы вернёмся к **Diffie–Hellman** и разберём продвинутые атаки: малые подгруппы, invalid-curve для ECDH и Logjam. А пока запомни главное: **nonce в ECDSA нельзя повторять или делать предсказуемым — иначе приватный ключ восстанавливается из двух подписей**.

## Где пригодится

- **CTF (crypto)** — задачи с повторным или слабым nonce.
- **Аудит кошельков и подписей** — проверка генерации nonce.
- **Разбор инцидентов** — PS3 и криптокошельки ломались именно так.
- **Проектирование протоколов** — понимание, почему nonce критичен.
