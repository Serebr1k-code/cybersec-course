## Вопрос, с которого всё начинается

Приложение хранит профиль пользователя в шифрованном токене: `email=...&uid=10&role=user`. Мы можем зарегистрировать любой email, но роль `user` приклеена сервером. Как получить `role=admin`, если мы не знаем ключ шифрования? Оказывается, шифротекст без проверки целостности можно **резать и склеивать**, как мозаику. Разберём это на реальном оракуле.

## Наш пример

Возьмём классический ECB-оракул: он шифрует строку, которую мы контролируем лишь частично:

```python
from Crypto.Cipher import AES
from Crypto.Util.Padding import pad
KEY = b"0123456789abcdef"

def enc(pt):
    return AES.new(KEY, AES.MODE_ECB).encrypt(pad(pt, 16))

def profile_for(email):
    assert "&" not in email and "=" not in email
    return "email=" + email + "&uid=10&role=user"
```

`profile_for` запрещает `&` и `=`, поэтому роль подделать «в лоб» нельзя. Вопрос: можно ли собрать `role=admin` из блоков?

## Шаг 1: почему ECB позволяет резать

В режиме **ECB** каждый 16-байтный блок шифруется **независимо** от остальных. Одинаковый открытый текст в одном и том же блоке даёт одинаковый шифротекст. Значит, блоки можно копировать и вставлять, как детали конструктора: расшифровка собранной строки будет корректной. Именно это делает ECB «небезопасным по умолчанию» — он не скрывает структуру.

(В CBC так не выйдет: там каждый блок связан с предыдущим шифротекстом, и свободная перестановка «портит» следующий блок. Для CBC техника другая — битфлип; вернёмся к нему ниже.)

## Шаг 2: «выращиваем» блок с admin

Сначала нужен блок, который расшифруется ровно в `admin` с корректным padding. Подберём email так, чтобы после префикса `email=` (6 байт) осталось 10 байт до границы блока, и сразу за ними пошло `admin`:

```python
email1 = "A"*10 + "admin" + chr(11)*11
ct1 = enc(profile_for(email1).encode())
admin_block = ct1[16:32]
print("admin_block:", admin_block.hex())
```

```
admin_block: 8282df0042d58e3767a05d9ef72cb5d7
```

Что произошло: `email=` + 10 букв `A` занимают ровно первый блок (16 байт). Второй блок — это `admin` (5 байт) плюс одиннадцать байт `0x0b`. Одиннадцать — не случайность: PKCS#7 требует, чтобы байт дополнения повторялся столько раз, сколько байт не хватает (16 − 5 = 11). Значит, этот блок сам по себе — валидный «хвост» блока. Мы его вырезали.

## Шаг 3: выравниваем и подставляем

Теперь нужен токен, где роль стоит последней и начинается на границе блока. Подберём длину email: `email=` (6) + email + `&uid=10&role=` (13) должно дать 32 байта, значит email из 13 символов:

```python
email2 = "B"*13
ct2 = enc(profile_for(email2).encode())
forged = ct2[:32] + admin_block
print(AES.new(KEY, AES.MODE_ECB).decrypt(forged))
```

```
b'email=BBBBBBBBBBBBB&uid=10&role=admin\x0b\x0b\x0b\x0b\x0b\x0b\x0b\x0b\x0b\x0b\x0b'
```

Первые 32 байта — это два легитимных блока `email=...&uid=10&role=`. Мы отбросили третий блок (там было `user` + padding) и на его место вставили вырезанный `admin`-блок. Расшифровка дала `role=admin`. Сервер, если он не проверяет MAC, примет этот токен.

## Шаг 4: а если CBC — тогда битфлип

В CBC блоки связаны: `P_i = D_K(C_i) ⊕ C_{i-1}`. Свободно переставлять нельзя, зато можно **менять содержимое**: если поменять байты в `C_{i-1}`, то `P_i` изменится предсказуемо — на ту же XOR-разницу. Чтобы превратить `guest` в `admin`, правим предыдущий блок:

```
новый_C_{i-1} = старый_C_{i-1} ⊕ "guest" ⊕ "admin"
```

Цена — блок `P_{i-1}` при этом полностью «портится» (становится мусором). Поэтому в CBC часто строят **цепочку битфлипов**: правят несколько предыдущих блоков, а испорченный блок стараются выбрать так, чтобы он содержал поле, которое приложение игнорирует. Для сериализованных структур (JSON, PHP `serialize()`) это особенно удобно: порядок полей часто неважен.

## Шаг 5: почему это работает и как защититься

Обе техники опираются на одно: **шифрование без аутентификации не защищает целостность**. Шифротекст можно менять, не зная ключа, а приложение видит только результат расшифровки.

Правильная защита:

- **AEAD** (GCM, ChaCha20-Poly1305) — целостность встроена, любая правка отвергается.
- **Encrypt-then-MAC** — MAC по шифротексту ловит изменение **до** расшифровки.
- **AAD** — включайте роль, ID, версию в тег, тогда блоки нельзя переносить между сессиями.
- **Каноническая сериализация + подпись** — уменьшает поверхность атаки.

## Шаг 6: пошаговый план на ECB

1. **Соберите оракул.** Функция шифрует `prefix + ваш_ввод + suffix` в ECB.
2. **Определите выравнивание.** Подберите длину ввода так, чтобы нужное поле начиналось на границе блока.
3. **«Вырастите» целевой блок.** Сформируйте ввод, при котором желаемое значение (`admin`) окажется в отдельном блоке с padding.
4. **Вырежьте блок.** Возьмите из шифротекста только блок с `admin`.
5. **Соберите подделку.** Подставьте его вместо блока с `role=user` в легитимном токене.
6. **Отправьте** и проверьте, что приложение приняло новую роль.

Шаги 2–3 — самые кропотливые: нужно точно рассчитать длину префикса и padding. Начните с функций `find_block_size` и `find_prefix_len` из урока `crypto-ecb-oracle`.

## Шаг 7: где это встречается в реальности

Cut-and-paste — не только упражнение. Исторически:

- **ASP.NET ViewState** без `ViewStateMAC` (до 2014) позволял подделывать и переставлять поля — отсюда массовые RCE.
- **Java/PHP-сериализация** объектов, зашифрованных без MAC, позволяла подменять поля (например, `role`) перестановкой или битфлипом.
- **TLS CBC** (класс BEAST/POODLE) — искажение блоков в комбинации с padding oracle.
- **Самописные «шифрованные» токены** в мобильных API и IoT — самая частая находка на пентестах.

Почему структуры так уязвимы? Многие форматы (JSON, PHP `serialize()`, Java ObjectStream) имеют переменную длину полей и самоописывающие маркеры. Атакующий может либо изменить длину (и подправить число битфлипом), либо переставить поля — многие парсеры не заботятся о порядке. Поэтому правильный дизайн — **каноническая сериализация плюс подпись** либо AEAD со связыванием контекста. Общий урок: шифрование без аутентификации — это обфускация данных, а не их защита.

## Что мы теперь знаем

- **ECB** позволяет свободно копировать и переставлять блоки — самая чистая форма cut-and-paste.
- **CBC** требует битфлипа: правка `C_{i-1}` меняет `P_i` предсказуемо, но портит `P_{i-1}`.
- Выравнивание по границам блоков — ключ к тому, чтобы целевое поле попало в отдельный блок.
- PKCS#7-дополнение позволяет «вырастить» валидный хвостовой блок с нужным значением.
- Атака невозможна при наличии MAC или AEAD.
- Шифрование без аутентификации — это обфускация, а не защита.

## На что смотреть дальше

- **Определите режим.** ECB → cut-and-paste блоками; CBC → битфлип/перестановка. От этого зависит весь план.
- **Проверьте MAC.** Если целостность есть — сначала ищите другой вектор.
- **Не забудьте про порчу предыдущего блока** при битфлипе.
- **Следите за выравниванием.** Поля должны попадать на границы блоков, иначе нужны сдвиги.
- **PKCS#7 нельзя «сломать»** — последний блок содержит padding, его правка ломает расшифровку.
- **Не путайте перестановку и модификацию.** Первая копирует готовые блоки, вторая меняет байты.

## Разбор битфлипа CBC на конкретных байтах

Формула `P_i = D_K(C_i) ⊕ C_{i-1}` даёт прямой рецепт правки. Пусть блок `P_i` содержит строку `role=user`, а нам нужно `role=admi` — та же длина, меняются только последние байты. Тогда:

```
C'_{i-1} = C_{i-1} ⊕ "role=user" ⊕ "role=admi"
```

Разберём численно. Пусть `C_{i-1} = 9f 3a 11 04 7c e2 55 90 ...`, а разница `"role=user" ⊕ "role=admi"` = `00 00 00 00 00 1e 1b 0b ...` (первые пять байт совпадают, дальше идёт XOR). Применяем XOR поэлементно и получаем новый предыдущий блок. Отправляем изменённый шифротекст — сервер расшифрует `P_i` как `role=admi`. Ключ не нужен: мы «подкрутили» ровно ту XOR-разницу, которую видит дешифратор.

Важно, что при этом блок `P_{i-1}` станет мусором: `D_K(C'_{i-1})` даст случайные байты. Если в `P_{i-1}` лежит поле, которое приложение не проверяет (комментарий, необязательный параметр), атака незаметна. Если там `uid` — сервер может отбросить запрос, и тогда строят цепочку из нескольких битфлипов, подбирая «жертвенный» блок с безразличным содержимым.

## Ограничения и граничные случаи

| Ситуация | Что делать |
|---|---|
| Есть MAC/AEAD | Атака не работает — ищи другой вектор |
| Последний блок | Padding ломается; правь не его, а предпоследний |
| Поле на границе блоков | Сдвинь выравнивание подбором длины ввода |
| Поле меняет длину | Одним битфлипом не обойтись — нужен `%n`-подобный примитив или перестановка |
| CBC с рандомным IV | IV — обычный блок, его тоже можно битфлипать |
| CTR/OFB | Блоки независимы, «битфлип» = XOR в любую позицию потока |

Отдельная ловушка — **самосинхронизирующиеся форматы**: если приложение после расшифровки считает CRC или HMAC по открытому тексту, любая правка обнаружится. Именно поэтому защита строится на MAC **по шифротексту** (Encrypt-then-MAC), а не по открытому тексту (MAC-then-Encrypt).

## Куда дальше

Мы научились подделывать структуры в блочных шифрах. Дальше — атака на **композицию шифров**: почему «зашифровать дважды» не удваивает стойкость. В уроке **crypto-mitm** мы разберём meet-in-the-middle и атаки на 2DES/3DES. А пока главное: **шифрование без аутентификации — открытая дверь; ECB режется, CBC битфлипается.**

## Где пригодится

- **CTF crypto:** зашифрованные cookie/токены, подделка сериализованных структур.
- **Bug bounty / пентест:** атаки на самописную криптографию в веб-приложениях.
- **Аудит кода / разработка:** почему нужно AEAD/EtM.
- **Работа (SOC/IR):** детекция манипуляций с зашифрованными сессиями.
- **Исследования:** композиционная стойкость и целостность.
