## Идея cut-and-paste

Если шифрование не аутентифицировано, шифротекст можно **переставлять и комбинировать**, как кусочки мозаики. Атака cut-and-paste (перестановка/вырезание-вставка блоков) эксплуатирует тот факт, что в CBC (и ECB) каждый блок расшифровывается независимо от смысла данных — приложение не замечает, что блоки «пришли» из другого сообщения. Это позволяет собирать поддельные структуры из легитимных фрагментов.

Cut-and-paste — естественное продолжение `crypto-cbc-bitflip` (там мы искажали байты) и родственник `crypto-ecb-oracle` (там мы собирали блоки для восстановления секрета). Здесь цель — **подделать валидную структуру**, а не прочитать секрет.

## Почему в CBC можно переставлять блоки

Вспомним расшифрование CBC:

```
P_i = D_K(C_i) ⊕ C_{i-1}
```

Блок `P_i` зависит только от `C_i` и `C_{i-1}`. Значит:

- Если поменять местами блоки `C_i` и `C_j`, то **все они расшифруются** (в мусор, кроме первого), но приложение, если оно разбирает структуру «по полям» и не проверяет целостность, может принять часть из них.
- Первый блок, который следует за переставленным, станет мусором (из-за неверного `C_{i-1}`), но если это поле можно испортить — атака работает.

Ключевое: **приложение, разбирающее сериализованную структуру, видит только результат расшифрования**, а CBC даёт атакующему возможность влиять на то, какие байты там окажутся.

## Классический сценарий: «role» в cookie

Приложение выдаёт cookie, где открытый текст — что-то вроде:

```
role=guest;name=AAA...
```

и шифрует в CBC с IV. Есть два легитимных cookie:

- Cookie A: `role=guest;...` (для гостя)
- Cookie B: `role=admin;...` (для админа) — но мы его не имеем.

Если бы мы имели **другой** токен, где `admin` появляется в известной позиции (например, от другого пользователя), можно было бы вырезать нужный блок и вставить в свой. Но чаще применяется **битфлип** (изменение `C_{i-1}`), чтобы превратить `guest` в `admin`:

```
новый_C_{i-1} = старый_C_{i-1} ⊕ "guest" ⊕ "admin "
```

Аналогично «user» → «root », `is_admin=0` → `is_admin=1`, `amount=100` → `amount=999`.

## ECB cut-and-paste (классика Cryptopals 13)

Отдельная, очень чистая версия атаки — на **ECB**. Сценарий: оракул шифрует профиль вида `email=<user>@x.com&role=user&uid=10`. Мы можем регистрировать пользователей с произвольным email, но не можем задать роль.

Идея:

1. Зарегистрировать email, который выравнивает блок так, чтобы слово `admin` (полученное из email) попало в отдельный блок. Например, email = `AAAAAAAAAadmin` (11 символов + `admin`), чтобы `admin` оказался в начале блока.
2. Из полученного шифротекста **вырезать** блок, содержащий `admin` (с padding), и **вставить** его вместо блока, содержащего `role=user` в нашем целевом токене.
3. Собрать `email=...&role=<admin-блок>&uid=10` — сервер расшифрует и увидит `role=admin`.

```python
# Упрощённо (Cryptopals #13)
def profile_for(email):
    assert "&" not in email and "=" not in email
    return "email=" + email + "&uid=10&role=user"

# 1. Найти выравнивание: email такой длины, чтобы "admin" (с PKCS#7) встал в отдельный блок
email = "A"*(16 - len("email=") - 4) + "admin" + "\x0b"*11   # "admin" + padding 0x0b*11
ct_admin = oracle(profile_for(email))
admin_block = ct_admin[16:32]        # блок с "admin\x0b\x0b...\x0b"

# 2. email, чтобы "role=" заканчивалось на границе блока
email2 = "B"*(16 - len("email="))     # "email=" + 10*"B" = 16 байт
ct2 = oracle(profile_for(email2))     # блок1: "email=BBBBBBBBBB", блок2: "&uid=10&role=", блок3: "user"+pad
# 3. заменяем блок3 (role=user) на admin_block
forged = ct2[:32] + admin_block
# сервер увидит: email=...&uid=10&role=admin
```

Это ровно задача Cryptopals 13. Она показывает: **ECB позволяет собирать структуры из блоков**, как из конструктора.

## Цепочки битфлипов для сериализованных структур

Часто одной правки недостаточно: нужно изменить несколько полей, идущих подряд. Тогда строят **цепочку битфлипов**: для каждого целевого блока `i` меняют `C_{i-1}`. Побочный эффект — порча `P_{i-1}` — можно иногда компенсировать или «пожертвовать» неважным полем.

Пример: JSON `{"user":"guest","role":"user","admin":false}`. Хотим `{"user":"guest","role":"root ","admin":true }`. Меняем соответствующие байты в предыдущих блоках; блок, который станет мусором, стараемся выбрать так, чтобы он содержал поле, игнорируемое приложением.

## Практический пример: перестановка блоков в CBC

```python
import base64

raw = base64.b64decode(token)
iv, ct = raw[:16], raw[16:]
blocks = [ct[i:i+16] for i in range(0, len(ct), 16)]

# Хотим поставить блок "role=admin..." на первое место
# (если он есть в другом токене)
target = blocks[2]        # блок с нужным полем
forged_ct = target + b"".join(blocks[:2] + blocks[3:])
# при расшифровке первый блок станет мусором (C_{-1} не тот),
# поэтому часто нужен ещё IV-битфлип для компенсации
forged = base64.b64encode(iv + forged_ct)
```

На практике «чистая» перестановка редко даёт валидную структуру с первого раза — приходится комбинировать с битфлипом IV и подбирать выравнивание.

## Защита

- **AEAD** (GCM, ChaCha20-Poly1305) — целостность встроена, перестановка/подмена отвергается.
- **Encrypt-then-MAC** — MAC по шифротексту ловит любое изменение до расшифрования.
- **Связывание контекста (AAD):** включайте в MAC/тег роль, ID, версию — тогда перестановка блоков между сессиями ломает тег.
- **Не сериализовать доверенные поля в шифротекст без аутентификации.** Лучше подписывать структуру целиком.
- **Детерминированная нормализация** (canonical serialization) плюс подпись — уменьшает поверхность атаки.

## Инструменты и команды

```python
# Разбор токена на блоки и перестановка
def split_blocks(data, bs=16):
    return [data[i:i+bs] for i in range(0, len(data), bs)]

# Битфлип произвольного блока
def flip(ct, block_idx, old, new):
    ct = bytearray(ct)
    prev = (block_idx - 1) * 16
    for i in range(min(len(old), 16)):
        ct[prev + i] ^= old[i] ^ new[i]
    return bytes(ct)
```

## Частые ошибки

- **Забыть про порчу предыдущего блока.** Перестановка «портит» блок перед вставленным.
- **Неверное выравнивание.** Поля должны попадать на границы блоков; иначе нужны сдвиги.
- **Считать, что ECB-трюк сработает в CBC.** В CBC блоки связаны; техника другая (bit-flip).
- **Атаковать при наличии MAC/AEAD.** Не пройдёт; сначала убедитесь, что целостности нет.
- **Игнорировать PKCS#7.** Последний блок содержит padding — его нельзя «сломать».
- **Путать перестановку и модификацию.** Перестановка копирует готовые блоки; битфлип меняет байты.

## Реальные проявления cut-and-paste

Cut-and-paste — не только CTF-упражнение. Исторически:

- **ASP.NET ViewState** без `ViewStateMAC` (до 2014) позволял подделывать и переставлять зашифрованные/подписанные поля — отсюда массовые RCE.
- **Java/PHP-сериализация** объектов, зашифрованных без MAC, позволяла подменять поля (например, `role`) перестановкой блоков или битфлипом.
- **TLS CBC (BEAST/POODLE-класс)** — перестановка/искажение блоков в комбинации с padding oracle.
- **Самописные «шифрованные» токены** в мобильных API и IoT — самая частая находка на пентестах.

Общий урок: **шифрование без аутентификации — это не защита данных, а лишь их обфускация.** Любая структура, зашифрованная в ECB/CBC/CTR без MAC/AEAD, потенциально подделываема.

## Сериализация: почему структуры так уязвимы

Многие форматы сериализации (JSON, PHP `serialize()`, Java ObjectStream, Python pickle) имеют **переменную длину полей** и **самоописывающие маркеры**. Это даёт атакующему две возможности:

1. **Изменение длины.** Если поле начинается с числа (например, `s:5:"guest";`), изменение длины без правки числа ломает парсер — но CBC/CTR bit-flip позволяет подправить и число.
2. **Перестановка полей.** Многие парсеры не заботятся о порядке, поэтому перестановка блоков с полями часто «сходит с рук».

Именно поэтому **каноническая сериализация + подпись** (или AEAD со связыванием контекста) — правильный дизайн. Если вы аудируете приложение, ищите: шифруется ли структура целиком, проверяется ли MAC **до** разбора, включается ли роль/ID в AAD/подпись.

## ECB против CBC для cut-and-paste

Важно не путать техники: в **ECB** блоки независимы, поэтому можно свободно копировать готовые блоки (как кубики конструктора) — это самая чистая форма cut-and-paste. В **CBC** блоки связаны через предыдущий шифротекст, поэтому «вставленный» блок расшифруется корректно только если его `C_{i-1}` тоже на месте; иначе первый байт(ы) испортятся. Поэтому в CBC чаще применяют комбинацию: **bit-flip** для изменения содержимого плюс **перестановку** для сборки. Начинайте с определения режима — это определяет весь дальнейший план.

## Пошаговый план cut-and-paste на ECB

1. **Соберите оракул.** Функция шифрует `prefix + user_data + suffix` в ECB.
2. **Определите выравнивание.** Подберите длину ввода так, чтобы нужное поле (например, `role=`) начиналось на границе блока.
3. **«Вырастите» целевой блок.** Сформируйте ввод, при котором желаемое значение (`admin`) окажется в отдельном блоке с padding.
4. **Вырежьте блок.** Из шифротекста возьмите только блок с `admin`.
5. **Соберите подделку.** Подставьте вырезанный блок вместо блока с `role=user` в легитимном токене.
6. **Отправьте** и проверьте, что приложение приняло `role=admin`.

Шаги 2–3 — самая кропотливая часть: нужно рассчитать длину префикса и padding. Начните с функции `find_block_size` и `find_prefix_len` из урока `crypto-ecb-oracle`.

## Как не застрять

- **Определите режим.** ECB → cut-and-paste блоками; CBC → битфлип/перестановка.
- **Найдите границы блоков.** Выровняйте поля так, чтобы целевые данные попали в блок.
- **Есть ли оракул шифрования?** Тогда можно «выращивать» блоки с нужным содержимым.
- **Проверьте MAC.** Если его нет — атака реализуема.
- **Комбинируйте техники.** Часто нужен и битфлип, и перестановка.
- **Тестируйте на локальном ключе**, если возможно.
