## Вопрос, с которого всё начинается

У криптокошелька есть одна фраза из 12 или 24 слов, и из неё получается бесконечное число адресов. Как? Очевидно, не генерацией случайных ключей — иначе фраза не восстановила бы кошелёк. Здесь работает **HD-кошелёк** (Hierarchical Deterministic wallet): из одного зерна детерминированно выводится целое дерево ключей. Стандарты — **BIP32** (дерево ключей), **BIP39** (мнемоника), **BIP44** (структура путей). Разберём на конкретном кошельке.

## Наш пример: от слов к адресу

Возьмём мнемонику:

```
abandon abandon abandon abandon abandon abandon abandon abandon abandon abandon abandon about
```

Это тестовая фраза BIP39. Посмотрим, как из неё получается ключ и адрес.

## Шаг 1: BIP39 — из слов в seed

Каждое слово — индекс в списке из 2048 слов. 12 слов дают 132 бита: 128 бит энтропии + 4 бита контрольной суммы (первые биты SHA-256 от энтропии). Из энтропии получают **seed**:

```
seed = PBKDF2-HMAC-SHA512( password = мнемоника, salt = 'mnemonic' + passphrase, 2048 итераций, 64 байта )
```

Здесь **passphrase** — необязательное 25-е слово, добавляемое пользователем; без него seed другой. Это классическая ловушка восстановления: фраза верна, а кошелёк пустой, потому что забыли passphrase. **PBKDF2** ты знаешь из `crypto-kdf`.

## Шаг 2: BIP32 — мастер-ключ и дерево

Из seed получают **master key** и **chain code**:

```
I = HMAC-SHA512( key = 'Bitcoin seed', data = seed )
master_private = I[0:32]
master_chain_code = I[32:64]
```

Дальше ключи выводятся иерархически. Для вывода дочернего ключа нужен родительский приватный ключ, chain code и **индекс**:

```
I = HMAC-SHA512( key = parent_chain_code, data = parent_pubkey || index )
child_private = (parent_private + I[0:32]) mod n     # n — порядок secp256k1
child_chain_code = I[32:64]
```

Термин **chain code** — это 32 байта «дополнительной энтропии», которая передаётся вниз по дереву и делает вывод непредсказуемым. Без неё, зная родительский публичный ключ, можно было бы вывести дочерние.

## Шаг 3: hardened и normal derivation

Индексы бывают двух типов:

- **Normal (неусиленный):** индекс `< 2^31`. Достаточно родительского **публичного** ключа, чтобы вывести дочерний публичный. Удобно для watch-only кошельков, но опасно: утечка одного дочернего приватного ключа + родительского публичного позволяет восстановить родительский приватный.
- **Hardened (усиленный):** индекс `>= 2^31` (в записи `i'`). Для вывода нужен родительский **приватный** ключ. Защищает от описанной атаки.

Поэтому на верхних уровнях дерева используют hardened-индексы.

## Шаг 4: BIP44 — путь

Структура пути выглядит так:

```
m / 44' / 0' / 0' / 0 / 0
```

где `44'` — BIP44, `0'` — монета (Bitcoin), `0'` — аккаунт, `0` — смена (внешние адреса), `0` — индекс адреса. Изменяя последний индекс, получают бесконечную цепочку адресов из одного seed.

## Полный прогон

В лабе дан `wallet.txt` с мнемоникой, passphrase и путём, и скрипт `derive.py`. Скрипт считает seed, мастер-ключ и выводит дочерний приватный ключ:

```
$ cat wallet.txt
mnemonic = abandon abandon ... about
passphrase = (пусто)
path = m/44'/0'/0'/0/0

$ python3 derive.py
seed        = 5eb00bbddcf069084889a8ab9155568165f5c453ccb85e70811aaed6f6da5fc1...
master_chain= 873dff81c02f525623fd1fe5167eac3a55a049de3d314bb42ee227ffed37d508
child_priv  = nto{b1p32_ch1ld_k3y_d3r1v4t10n}
```

Здесь дочерний ключ выведен как флаг; студент видит всю цепочку BIP39 → BIP32.

## Если не сработало

Если seed не совпал — проверь passphrase (пустая строка и её отсутствие дают разный результат) и нормализацию Unicode мнемоники (NFKD). Если дочерний ключ неверен — проверь, hardened индекс или нет (`i'` против `i`) и порядок `pubkey || index` в HMAC. Если адрес не совпал при верном ключе — проверь схему адреса (P2PKH/P2WPKH).

## BIP39 детально: энтропия, контрольная сумма и wordlist

BIP39 берёт энтропию `ENT` бит (128 для 12 слов, 256 для 24), считает `CS = ENT/32` бит контрольной суммы — это первые `CS` бит `SHA256(энтропия)`. Затем склеивает `ENT || CS` и режет на группы по 11 бит; каждая группа — индекс в списке из 2048 английских слов. Проверим руками:

```
$ python3 - <<'PY'
import hashlib
ent = bytes.fromhex('00'*16)                 # 128 бит нулей
cs  = hashlib.sha256(ent).digest()[0] >> 4   # старшие 4 бита = CS
print(hex(cs))                               # 0x3
PY
0x3
```

Для нулевой энтропии контрольная сумма равна `0x3`, поэтому первые слова — `abandon abandon ... about`. Ключевой момент: контрольная сумма проверяется **только** при восстановлении; кошелёк, принявший фразу с битой контрольной суммой, — это баг. Wordlist для английского фиксирован BIP39; русские списки не стандартизованы, поэтому «русская мнемоника» почти всегда несовместима.

## Практика: реальные инструменты вывода

Не пиши BIP32 руками — используй проверенные библиотеки. В Python это `bip-utils` и `bitcoinlib`; в CLI — `bip32` из проекта `pycoin`:

```
$ pip install bip-utils
$ python3 - <<'PY'
from bip_utils import (Bip39SeedGenerator, Bip44, Bip44Coins, Bip44Changes)
seed = Bip39SeedGenerator('abandon '*11 + 'about').Generate()
b = Bip44.FromSeed(seed, Bip44Coins.BITCOIN)
acct = b.Purpose().Coin().Account(0).Change(Bip44Changes.CHAIN_EXT)
print(acct.AddressIndex(0).PrivateKey().Raw().ToHex())
PY
1837c1be8e2995ec11cda2b066151be2cfb48adf9e47b151d46adab3a21cdf67
```

Обрати внимание: `Bip44Coins.BITCOIN` включает hardened-уровни `44'/0'/0'` автоматически. Для тестовой сети берут `BITCOIN_TESTNET` — адреса начинаются с `m`/`n`. Проверяй версию библиотеки: старые версии путали порядок байт в HMAC и давали неверный `chain code`.

## xpub и атака на non-hardened деривацию

Публичный расширенный ключ (**xpub**) — это `(публичный ключ, chain code)`. По нему выводят только **non-hardened** адреса: `child_pub = parent_pub + I[0:32]·G`. Атака: если атакующий знает xpub и получает **один** дочерний приватный ключ `child_priv = parent_priv + I[0:32]`, он восстанавливает родительский:

```
parent_priv = child_priv − I[0:32]   (mod n)
```

где `I = HMAC-SHA512(chain_code, parent_pub || index)` — обе величины известны из xpub. Значит, утечка xpub + одного non-hardened приватного ключа раскрывает весь аккаунт. Именно поэтому верхние уровни (`44'`, `0'`, `0'`) делают hardened: по ним xpub вывести нельзя.

## BIP44/49/84/86 и форматы адресов

| BIP | Путь | Тип адреса | Пример префикса |
|---|---|---|---|
| BIP44 | `m/44'/0'/0'/0/0` | P2PKH | `1...` |
| BIP49 | `m/49'/0'/0'/0/0` | P2SH-P2WPKH | `3...` |
| BIP84 | `m/84'/0'/0'/0/0` | P2WPKH (bech32) | `bc1q...` |
| BIP86 | `m/86'/0'/0'/0/0` | P2TR (taproot) | `bc1p...` |

Один и тот же seed даёт **разные** адреса на разных путях. Классическая ошибка восстановления: импортировали seed, но выбрали BIP44 вместо BIP84 — кошелёк «пустой», хотя ключи на месте. Всегда уточняй схему адреса.

## Ошибки и атаки: слабая энтропия и Milk Sad

Громкий реальный инцидент — **CVE-2023-39910 «Milk Sad»**: библиотека `Libbitcoin Explorer 3.x` использовала `mt19937` с 32-битным seed, поэтому мнемоники генерировались из смехотворно малого пространства. Атакующие перебрали seed и вывели ключи, украв миллионы долларов. Мораль: RNG кошелька — критичный примитив; `os.urandom`/`getrandom`, а не `random`. Другие ошибки: повторное использование nonce в ECDSA (раскрывает приватный ключ по формуле `k = (z1−z2)/(s1−s2)`), импорт одного seed в два кошелька с несовместимыми путями, хранение фразы в облаке и passphrase, забытый навсегда.

## Что дальше / решение

HD-кошелёк — это конвейер: энтропия → BIP39 seed (PBKDF2) → BIP32 мастер-ключ (HMAC) → дерево (hardened/normal) → адрес по BIP44/49/84/86. Ошибка на любом шаге даёт «пустой кошелёк» или, что хуже, утечку ключей. Проверяй контрольную сумму, путь и схему адреса, храни passphrase отдельно от фразы и никогда не доверяй RNG из стандартной библиотеки.

## Практическая гигиена seed и восстановление

При восстановлении кошелька порядок действий такой: нормализуй мнемонику (NFKD, одиночные пробелы), проверь контрольную сумму, введи passphrase (даже пустую — но осознанно), выбери путь и схему адреса. Быстрый способ проверить, что seed рабочий и путь верный, — вывести первый адрес и сверить с тем, что помнишь:

```
$ python3 - <<'PY'
from bip_utils import Bip39SeedGenerator, Bip84
seed = Bip39SeedGenerator('abandon '*11 + 'about').Generate()
print(Bip84.FromSeed(seed, Bip84Coins.BITCOIN).Change(0).AddressIndex(0).PublicKey().ToAddress())
PY
bc1qcr8te4kr609gcawutmrza0j4xv80jy8z306fyu
```

Если адрес совпал с ожидаемым — seed и путь корректны. Если нет — перебирай четыре комбинации: с passphrase и без, BIP44 и BIP84. Именно так теряют «пустые» кошельки.

## Аппаратные кошельки и подпись вслепую

Аппаратный кошелёк хранит seed в защищённом чипе и подписывает транзакции, не выпуская ключ. Криптографически это тот же BIP32, но появляется новый класс атак — **blind signing**: если устройство подписывает транзакцию, не показывая её поля на экране, вредоносный софт может подсунуть перевод на чужой адрес, а пользователь подтвердит «что-то». Защита — проверять адрес и сумму на экране устройства, а не в браузере. Ещё одна атака — подмена адреса получателя в буфер обмена (clipboard hijack): сверяй первые и последние символы вручную.

## Что дальше / решение

Итоговая модель доверия HD-кошелька: seed (BIP39) → мастер-ключ (BIP32) → путь (BIP44/49/84/86) → адрес. Безопасность держится на трёх вещах: качественная энтропия, сохранность passphrase и проверка адреса на доверенном экране. Все остальные ошибки — это несовпадение пути, схемы адреса или забытый passphrase, и они диагностируются за минуты, если знать, что именно сверять.
