## Вопрос, с которого всё начинается

В `crypto-shamir` мы делили секрет на доли и собирали его по порогу. Но там была дыра: если раздающий (dealer) — мошенник, он может выдать участникам несогласованные доли. Тогда при реконструкции каждый получит разное «секретное» значение, и никто не поймёт, кто виноват. Нужен способ **проверить** доли, не раскрывая секрет. Это **VSS** (Verifiable Secret Sharing). Разберём два классических варианта: Feldman и Pedersen.

## Наш пример: полином и доли

Как и в Shamir, секрет `s` — свободный член полинома степени `t−1`:

```
f(x) = s + a1·x + a2·x² + ... + a_{t−1}·x^{t−1}  (mod q)
```

Доля участника `i` — это `f(i) mod q`. Задача: дать участнику `i` возможность проверить, что его доля согласована с обязательствами раздающего, но при этом не дать ему узнать `s`.

## Шаг 1: Feldman VSS (commitment на дискретном логе)

Раздающий публикует **commitment** к каждому коэффициенту:

```
C_0 = g^s,  C_1 = g^{a1},  ...,  C_{t−1} = g^{a_{t−1}}   (mod p)
```

Участник `i` проверяет своё:

```
g^{f(i)} == C_0 · C_1^i · C_2^{i²} · ... · C_{t−1}^{i^{t−1}}   (mod p)
```

Почему работает: `g^{f(i)} = g^{s + a1·i + a2·i² + ...}`. По свойствам показателей это и есть произведение `C_j^{i^j}`. Термин **commitment** ты знаешь из `crypto-commitment`: это «печать», которая фиксирует значение, не раскрывая его. Проверка доказывает согласованность долей.

Минус Feldman: `C_0 = g^s` — это **публичное** обязательство к секрету. Для стойкости нужен `g^s` над группой, где дискретный логарифм труден (то есть `s` нельзя восстановить), но для некоторых приложений даже этого мало — обязательство к секрету может быть нежелательно.

## Шаг 2: Pedersen VSS (два базиса)

Pedersen использует **два** независимых базиса `g`, `h` (никто не знает `log_g h`). Обязательство к коэффициенту `a`:

```
C(a) = g^a · h^r   (r — случайная маска)
```

Такое обязательство **совершенно скрывающее** (hiding): при любом `a` распределение `C(a)` равномерно, потому что `r` случаен. При этом оно **связывающее** (binding): раскрыть `a` двумя способами нельзя, иначе получишь `log_g h`. Участник проверяет долю, комбинируя обязательства по степеням `i`. Pedersen VSS дороже (нужны маски), но не публикует обязательство к самому секрету.

## Шаг 3: DKG — распределённая генерация ключей

VSS — строительный блок для **DKG** (Distributed Key Generation). Вместо одного раздающего **каждый** участник `j` генерирует свой полином `f_j` и рассылает доли `f_j(i)` остальным, приложив Feldman/Pedersen-обязательства. Итоговый секрет — сумма всех полиномов:

```
F(x) = Σ_j f_j(x),   секрет = F(0) = Σ_j f_j(0)
```

Никто не знает полного секрета, но любые `t` участников могут восстановить его (или, в пороговых подписях, совместно подписать, не собирая секрет вообще). Так рождаются пороговые подписи ECDSA/Schnorr (например, FROST): ключ никогда не существует целиком ни на одной машине.

## Шаг 4: атаки и ошибки

- Если проверка долей пропущена, злонамеренный участник сдвинет итоговый ключ.
- Если базисы `g`, `h` зависимы (`log_g h` известен кому-то) — Pedersen становится связывающим неверно и секрет можно подделать.
- Если в Feldman `C_0` утекает смысл секрета — выбирай Pedersen.

## Полный прогон

В лабе дан `vss.txt` с `p`, `g`, обязательствами `C_j` и долей участника, и скрипт `vss.py`. Скрипт проверяет долю и восстанавливает секрет по порогу:

```
$ cat vss.txt
p = ...
g = 2
C = [C0, C1, C2]
share_i = (3, 1798...)

$ python3 vss.py
Feldman check: OK
reconstructed secret = nto{f3ldm4n_vss_c0mm1tm3nt_v3r1fy}
```

## Если не сработало

Если проверка не проходит, проверь, что `g^{f(i)}` считается по тому же модулю `p`, что и `C_j`. Если восстановленный секрет неверен, возможно, доли выданы разными полиномами (нет VSS). Если Pedersen «раскрывает» секрет — базисы `g`, `h` зависимы.

## VSS: разделение секрета с проверкой

VSS (Verifiable Secret Sharing) — расширение схемы Шамира: дилер раздаёт доли, и участники могут **проверить**, что доли согласованы (лежат на полиноме степени `t−1`), не раскрывая секрет. Схемы: Feldman VSS (проверка через дискретный логарифм, но утекает `g^s`), Pedersen VSS (скрывает секрет, использует два генератора).

```text
share_i = f(i); commitment to coefficients; verify share_i against commitments
```

Применение: пороговые подписи, распределённые ключи, MPC, DKG.

## Пороговые схемы и DKG

**Пороговая подпись** (threshold signature): ключ распределён между `n` сторонами, подпись требует `t` из них, и никто не знает полный ключ. **DKG** (Distributed Key Generation) — генерация ключа без дилера: участники совместно строят доли через VSS, и компромисс одного узла не раскрывает ключ.

```text
n parties, threshold t; any t can sign, < t learns nothing
```

Применение: криптовалютные кастоди, HSM-кластеры, распределённые подписи.

## Практика: атаки и защита

Атаки: (1) **evil dealer** — дилер раздаёт несогласованные доли (лечится VSS); (2) **malicious participant** в DKG — вносит искажения (лечится верификацией и complaints); (3) **срыв реконструкции** — меньше `t` участников (нужен план); (4) утечка через Feldman-commitment `g^s` (используй Pedersen). Инструменты: анализ протокола, тесты на некорректные доли.

```text
evil dealer -> inconsistent shares; use VSS + complaints
```

Практика: проверяй, что VSS реально верифицирует доли, и что DKG устойчив к вредоносным участникам.

## Разбор: проверяем долю Feldman руками

Чтобы увидеть проверку не в символах, а в числах, возьмём крошечное поле. Пусть `q = 101`, `g = 2`, порог `t = 3`, а секрет `s = 42`. Раздающий выбрал полином:

```
f(x) = 42 + 7·x + 5·x²  (mod 101)
```

Он публикует обязательства `C_j = g^{a_j} mod 101`:

```
C_0 = 2^42 mod 101 = 97
C_1 = 2^7  mod 101 = 27
C_2 = 2^5  mod 101 = 32
```

Участнику `i = 2` достаётся доля `f(2) = 42 + 14 + 20 = 76 mod 101`. Он не знает коэффициентов, но может проверить:

```
левая часть:  2^76 mod 101 = 56
правая часть: C_0 · C_1^2 · C_2^4
            = 97 · 27^2 · 32^4
            = 97 · 729 · 1048576  mod 101
            = 97 · 22 · 32  mod 101
            = 56
```

Совпало — доля согласована. Заметь: участник перемножает именно степени `i^j`, то есть `C_2` возводит в `i² = 4`, а не просто умножает на `i`. Если раздающий подменит `C_2`, правая часть изменится и проверка провалится. Скрипт в лабе делает ровно это и печатает `Feldman check: OK` — тот же арифметический тест, только над большим `p`.

Почему проверка вообще возможна: она опирается на то, что `g^{a+b} = g^a · g^b`. Гомоморфизм показателей превращает «вычисление полинома» в «перемножение обязательств». Это ровно та же идея, что в `crypto-pairing` и в обязательствах Педерсена, — необратимость `log` прячет коэффициенты, а аддитивность показателей позволяет считать по ним.

## Таблица: Feldman, Pedersen и DKG

| Схема | Что публикуется | Скрытие секрета | Стойкость держится на | Стоимость |
|---|---|---|---|---|
| Feldman VSS | `C_j = g^{a_j}` | слабое: `g^s` открыт | сложности дискретного лога | одна экспонента на коэффициент |
| Pedersen VSS | `C_j = g^{a_j} h^{r_j}` | совершенное (hiding) | DL + binding через `log_g h` | две экспоненты на коэффициент |
| DKG (на VSS) | обязательства каждого участника | секрет нигде не собирается | порог `t` из `n` | `n²` долей и раунды с complaints |

Практическое правило: если утечка `g^s` допустима (например, `s` — уже публично проверяемый хэш), Feldman дешевле и проще. Если секрет должен остаться скрытым от всех, включая проверяющего, — только Pedersen, потому что в Feldman `C_0` — это буквально «запертый» секрет, и вся стойкость держится на сложности дискретного логарифма.

## Границы применимости и подводные камни

- **Проверка ≠ отсутствие сговора.** VSS доказывает согласованность долей с обязательствами, но если раздающий сговорился с `t` участниками, они всё равно восстановят секрет. VSS защищает от «кривых» долей, а не от порога.
- **Нужен безопасный базис.** Для Pedersen `h` генерируется как `h = g^κ`, и если `κ` известен раздающему, он сможет открыть обязательство двумя способами (нарушение binding). `h` должен выводиться «nothing-up-my-sleeve»-процедурой.
- **Модуль должен быть простым и безопасным.** В лабе `q = 101` удобно для счёта, но для реальной стойкости нужен `p`, где `(p−1)/2` простое, или кривая с большим простым порядком — иначе дискретный логарифм считается за секунды.
- **Feldman не скрывает.** Если протокол требует, чтобы даже обязательства не выдавали информации о секрете (например, при доказательстве знания), Feldman непригоден — `g^s` само является «половиной» ответа.
- **DKG чувствителен к порядку раундов.** Если complaints не собираются и не исключают вредоносных участников, один сбойный узел сдвинет итоговый ключ у всех; нужен явный протокол исключения.

## Полный числовой прогон Feldman VSS

Чтобы проверка перестала быть абстракцией, возьмём крошечные числа и посчитаем всё руками. Важное правило: полином `f(x)` живёт над полем порядка `q` (порядок группы), а обязательства `C_j` — в группе по модулю `p`. Для простоты возьмём `p = 47`, `q = 23` (порядок генератора) и генератор `g = 25` порядка 23 (проверяется: `25^23 ≡ 1 mod 47`).

```
p = 47, q = 23, g = 25
секрет s = 5, коэффициенты a1 = 1, a2 = 2   (t = 3)
f(x) = 5 + 1·x + 2·x²  (mod 23)
```

Доли и обязательства:

```
f(1) = 5 + 1 + 2   = 8   (mod 23)
f(2) = 5 + 2 + 8   = 15  (mod 23)
f(3) = 5 + 3 + 18  = 26 ≡ 3 (mod 23)

C0 = g^s  = 25^5 mod 47 = 12
C1 = g^a1 = 25^1        = 25
C2 = g^a2 = 25^2        = 14   (625 mod 47 = 14)
```

Теперь проверим каждую долю по формуле `g^{f(i)} == C0 · C1^i · C2^{i²} (mod p)`:

```
i=1: 25^8  = 17          C0·C1·C2   = 12·25·14 = 4200 ≡ 17  ✔
i=2: 25^15 = 36          C0·C1²·C2⁴ = 12·14·17 = 2856 ≡ 36 ✔
i=3: 25^3  = 21          C0·C1³·C2⁹ = 12·21·4  = 1008 ≡ 21 ✔
```

Все три доли прошли проверку — значит, дилер честно выдал доли одного полинома. Реконструкция по Лагранжу в точке `x = 0` из долей `(1,8), (2,15), (3,3)` даёт `24 − 45 + 3 = −18 ≡ 5 (mod 23)`, то есть исходный секрет `s = 5`. Обрати внимание на подводный камень: показатель степени редуцируется по модулю `q = 23`, а не по `p = 47`. Если случайно считать доли `mod p`, проверка сломается — это классическая ошибка реализации.

## Почему секрет не восстанавливается из обязательств

Обязательства `C_j = g^{a_j}` публичны, и злоумышленник видит `C0 = g^s`. Но чтобы достать `s`, нужно решить задачу дискретного логарифмирования в группе порядка `q`. Пока `q` — большое простое (в реальных схемах 2048+ бит), это вычислительно неосуществимо. Однако здесь кроется тонкость Feldman: `g^s` — это именно обязательство к секрету, а не к случайной величине. Если схема используется как строительный блок там, где утечка `g^s` опасна (например, в некоторых MPC-протоколах, где по `g^s` можно проверить гипотезу о малом `s`), Feldman не подходит. Именно поэтому существует Pedersen.

## Pedersen VSS: два базиса и маски

Pedersen берёт два независимых базиса `g`, `h`, для которых никто не знает `log_g h` (например, `h` получают хэшированием `g` в группу). Обязательство к коэффициенту `a_j` с маской `r_j`:

```
C_j = g^{a_j} · h^{r_j}
```

Проверка доли повторяет Feldman, но вместо одного базиса используется произведение двух. Свойство **hiding** (скрывающее) достигается потому, что `r_j` равномерно случаен: при любом `a_j` распределение `C_j` одинаково, и `a_j` из обязательства не извлекается даже вычислительно. Свойство **binding** (связывающее) держится на предположении, что `log_g h` неизвестен: если бы дилер мог открыть `C_j` двумя разными `(a_j, r_j)`, он получил бы `log_g h`. В DKG это критично, потому что недоверенные участники генерируют полиномы сами.

## Сравнение Feldman и Pedersen

| Свойство | Feldman | Pedersen |
|---|---|---|
| Базисы | один `g` | два: `g`, `h` |
| Скрывающее (hiding) | нет (`g^s` публично) | да (маска `r`) |
| Связывающее (binding) | да (дискретный лог) | да (при неизвестном `log_g h`) |
| Размер обязательства | 1 элемент группы | 1 элемент группы |
| Стоимость проверки | дешевле | дороже (маски) |
| Где применяют | быстрые проверки, DKG | когда нельзя светить `g^s` |

## DKG: раунды и жалобы

Полноценный DKG без дилера (например, в Joint-Feldman) идёт в несколько раундов:

1. **Раздача.** Каждый участник `j` строит свой полином `f_j`, рассылает долю `f_j(i)` участнику `i` и публикует обязательства `C_{j,k}`.
2. **Проверка.** Участник `i` проверяет полученную долю по обязательствам участника `j`. Не прошла — рассылает **жалобу** (complaint).
3. **Разрешение.** Обвинённый участник раскрывает долю публично, и все проверяют её. Если и публичная доля неверна — участника дисквалифицируют (пересчитывают группу и порог).
4. **Финализация.** Итоговая доля участника `i` — сумма `Σ_j f_j(i)`, а итоговый секрет — `Σ_j f_j(0)`. Никто не знает полного секрета, но любые `t` участников могут его восстановить или совместно подписать.

## Крайние случаи и ограничения

- **Меньше `t` участников.** Секрет не восстановить никогда — нужен план на потерю узлов, иначе ключ потерян навсегда.
- **Зависимые базисы.** Если `log_g h` известен хотя бы одному участнику, Pedersen теряет binding: он сможет подделать обязательство.
- **Ошибочная редукция.** Показатели редуцируются по порядку группы `q`, коэффициенты полинома — тоже `mod q`; путаница `p`/`q` — самая частая ошибка.
- **Сговор.** `t` участников знают секрет по определению схемы — порог нельзя ставить «с запасом» без понимания модели угроз.
- **Необратимость.** После генерации ключа состав участников зафиксирован: замена узла требует нового DKG или proactive re-sharing.

## Куда дальше

Дальше — пороговые подписи (FROST) и другие MPC-примитивы на основе VSS. Запомни главное: VSS превращает «поверь раздающему» в «проверь математически», а DKG убирает единственную точку компрометации ключа.
