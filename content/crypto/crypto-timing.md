Timing-атака эксплуатирует не математику алгоритма, а **время его выполнения**. Если время зависит от секрета (ветвление по секретному биту, ранний выход из сравнения, разная длина модульного умножения), атакующий по тысячам замеров восстанавливает ключ. Это одна из немногих атак, которая работает **дистанционно** — по сети, по HTTPS, без какого-либо доступа к коду. Здесь — полный практический цикл: от теории Кохера до удалённого статистического анализа.

## Модель угроз: что утекает

Утечка возникает, когда **поток управления** или **обращения к памяти** зависят от секрета:

- **Ветвление по секретному биту** — например, «если бит ключа = 1, сделай лишнее умножение».
- **Ранний выход из сравнения** — `memcmp(a,b)` останавливается на первом несовпавшем байте.
- **Разные ветки алгоритма** — `if (x < N) ...` в модульной редукции.
- **Кэш-эффекты** — табличный AES (T-tables), доступ к S-box зависит от ключа.
- **Длина/размер данных** — переменное время хэширования пароля.

Атака бывает **локальной** (мы и процесс на одной машине — точные замеры `rdtsc`/`perf`) и **удалённой** (замеры по сети — шумно, нужна статистика).

## Атака Кохера на RSA

Классический результат (Kocher, 1996): в наивной реализации `RSA decrypt` используется **квадрат-и-умножай**:

```
result = 1
for bit in bits(d):          # d — секретная экспонента
    result = result^2 mod N
    if bit == 1:
        result = result * m mod N   # <-- лишнее умножение только для 1
```

Если `d` содержит `1`, выполняется дополнительное умножение — операция дороже, чем квадрат (умножение на большое `m` против возведения в квадрат). По времени ответа для подобранных `m` восстанавливают биты `d` слева направо: для каждого кандидата-префикса предсказывают время и сравнивают с замером.

## Утечка через сравнение строк

`memcmp`/`strcmp`/самописное сравнение останавливаются на первом несовпадении:

```python
def bad_compare(secret, guess):
    for i in range(len(secret)):
        if secret[i] != guess[i]:
            return False        # ранний выход -> утечка длины совпавшего префикса
    return True
```

Атакующий подбирает байт за байтом: правильный первый байт делает сравнение дольше на один шаг. Это база атак на MAC-проверки, API-токены, «magic bytes», password-фильтры.

## Статистика: как отделить сигнал от шума

Удалённые тайминги — это распределение с тяжёлыми хвостами. Практика:

1. Соберите **много** замеров на каждый кандидат (сотни–тысячи).
2. Используйте не среднее, а **медиану** или **усечённое среднее** (робастность к выбросам).
3. Уберите сетевой джиттер: **чередуйте** замеры кандидатов (A,B,A,B,...), а не измеряйте блоками.
4. Применяйте **Welch t-test** для проверки значимости различия распределений.
5. Достаточная разница — единицы микросекунд при тысячах замеров; при локальной атаке — наносекунды.

```python
import statistics as st
def welch(a, b):
    na, nb = len(a), len(b)
    va, vb = st.variance(a), st.variance(b)
    t = (st.mean(a) - st.mean(b)) / ((va/na + vb/nb) ** 0.5)
    return t     # |t| > ~4.5 -> различие значимо
```

## Инструменты и команды

- **Python + `time.perf_counter_ns`** — точные локальные замеры.
- **`requests`/`aiohttp`** — удалённые замеры (лучше с keep-alive, без прокси).
- **`tcpdump`/Wireshark** — если нужно исключить влияние TLS (например, при компрессии).
- **`perf stat`/`rdtsc`** — локальные циклы точнее.
- **`dudect`** — статистический фреймворк для обнаружения тайминговых утечек в реализации.

```bash
# локальный замер времени вызова
python3 - <<'EOF'
import time
t0 = time.perf_counter_ns()
target_function(guess)
print(time.perf_counter_ns() - t0)
EOF

# удалённый: тысячи замеров, чередуя кандидатов
for i in $(seq 1 2000); do
  curl -s -o /dev/null -w "%{time_total}\n" "http://target/api?token=$CAND"
done
```

## Разобранный пример: удалённый подбор токена

Сервер проверяет токен посимвольно с ранним выходом. Подбираем байт за байтом:

```python
import requests, statistics as st, time

URL = "http://target/api"
known = ""

for pos in range(32):
    best, best_t = None, -1
    for c in "0123456789abcdef":
        guess = known + c
        samples = []
        for _ in range(300):
            t0 = time.perf_counter_ns()
            requests.get(URL, params={"token": guess})
            samples.append(time.perf_counter_ns() - t0)
        med = st.median(samples)
        if med > best_t:
            best_t, best = med, c
    known += best
    print(pos, known)
```

Если медиана для правильного префикса стабильно выше — символ угадан. Практические тонкости: keep-alive сессия, отключить `gzip`, брать `time_total` из `curl` или замер вокруг одного `send`, а не всего соединения.

## Варианты и родственные каналы

- **Cache-timing** — доступ к памяти зависит от секрета (Prime+Probe, Flush+Reload); табличный AES, RSA с большими таблицами.
- **Power/EM (SPA/DPA)** — см. `crypto-power`.
- **Spectre/Meltdown** — спекулятивные утечки через кэш; тоже тайминговые по природе.
- **Lucky 13** — тайминговая атака на TLS CBC MAC (сравнение MAC).
- **Bleichenbacher** — оракул на padding, часто реализуется через тайминг (`crypto-rsa-bleichenbacher`).
- **Compression side-channel (CRIME/BREACH)** — размер ответа как «время-подобный» канал.

## Контрмеры (constant-time)

- **Constant-time сравнение** — XOR всех байт и проверка накопленного OR, без раннего выхода:

```python
def ct_compare(a, b):
    if len(a) != len(b):
        return False
    r = 0
    for x, y in zip(a, b):
        r |= x ^ y
    return r == 0
```

- **Constant-time возведение в степень** — Montgomery ladder вместо ветвления по битам; «blinding» экспоненты и модуля.
- **Фиксированное время по входу** — паддинг до постоянной длины.
- **Отсутствие секретных индексов** — не использовать секрет как индекс массива.
- **Рандомизация** — blinding (RSA), маскирование (AES), чтобы усреднение шума убивало сигнал.
- **Проверка тестами** — `dudect`, `valgrind --tool=cachegrind` для выявления ветвлений.

## Частые ошибки и тупики

- **Мало замеров.** 10–20 замеров не отделят сигнал; нужны сотни–тысячи.
- **Измерять всё соединение.** DNS/TLS/handshake добавляют шум — используйте keep-alive и замер вокруг полезной нагрузки.
- **Среднее вместо медианы.** Выбросы сети искажают среднее.
- **Блочные замеры.** Замер всех A потом всех B ловит дрейф нагрузки; чередуйте.
- **Забыть про компрессию/прокси.** Они выравнивают или добавляют задержку.
- **Считать, что constant-time = медленно.** Правильная реализация почти не уступает по скорости.
- **Путать с брутфорсом.** Тайминг — это *утечка*, а не перебор; он даёт по одному биту/байту.

## Что дальше (decision)

1. Локальный доступ к процессу → `rdtsc`/`perf`, замеры в циклах, cache-timing.
2. Удалённый сервис → статистика (медиана, t-test), чередование кандидатов.
3. Сравнение токенов/MAC → атакуйте префикс байт за байтом.
4. RSA-дешифрование → атака Кохера или Bleichenbacher по таймингу.
5. Энергопотребление/ЭМИ доступны → `crypto-power`.
6. Всё constant-time → ищите другую утечку (размер ответа, ошибки).

## Где пригодится

- **CTF (hard):** тайминговые оракулы, подбор токенов, «сервер отвечает дольше».
- **Bug bounty:** утечка через сравнение секретов, Lucky13 на TLS, timing-оракулы.
- **Пентест:** аудит реализаций crypto-проверок.
- **Работа (SOC/IR):** детект аномального числа запросов (признак тайминговой атаки).
- **Разработка:** написание constant-time кода, ревью криптобиблиотек.
