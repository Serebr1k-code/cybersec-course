## Вопрос, с которого всё начинается

Сервер проверяет токен доступа. Мы отправляем неверный токен — получаем `invalid`. Отправляем другой неверный — снова `invalid`. Ответ одинаковый, ничего не утекает? Но задержка ответа **разная**. Может ли злоумышленник, который видит только ответы и их время, восстановить правильный токен?

Да, если сервер сравнивает токены наивно. Это **timing-атака**: эксплуатируется не математика алгоритма, а время его работы.

## Наш пример

Возьмём функцию проверки токена, которая сравнивает строки посимвольно и **выходит на первом несовпадении**:

```python
def check(guess):
    for i in range(min(len(guess), len(SECRET))):
        work()                       # «стоимость» проверки одного байта
        if guess[i] != SECRET[i]:
            return False             # ранний выход
    if len(guess) == len(SECRET):
        work()                       # при успехе сервер делает ещё операцию
        return True
    return False
```

Термин: **ранний выход** — цикл прерывается на первом расхождении. Чем длиннее совпавший префикс, тем больше байт успели сравнить, тем дольше работает функция. Зависимость времени от секрета называется **side-channel** (побочный канал). Токен у нас `a3f9`, но атакующий его не знает.

## Шаг 1: почему время зависит от секрета

Время выполнения определяется **потоком управления** и **обращениями к памяти**, а они зависят от данных:

- **ветвление по секрету** — «если бит ключа = 1, сделай лишнее умножение»;
- **ранний выход из сравнения** — `memcmp`/`strcmp`/самописный цикл;
- **разные ветки редукции** — `if (x < N) ...` в модульной арифметике;
- **обращения к таблицам** — табличный AES (об этом в уроке про cache-атаки);
- **длина/размер данных** — переменное время хэширования пароля.

Каналы бывают **локальные** (мы и процесс на одной машине — точные `rdtsc`/`perf`) и **удалённые** (замеры по сети — шумно, нужна статистика). Наш пример удалённый по духу: мы измеряем время функции, не заглядывая внутрь.

## Шаг 2: как измерять правильно

Наивно «замерить один раз» не выйдет — нужна статистика:

1. Собрать **много** замеров на каждого кандидата (сотни–тысячи).
2. Брать не среднее, а **медиану** или усечённое среднее — они устойчивы к сетевым выбросам.
3. **Чередовать** замеры кандидатов (A, B, A, B…), а не мерить блоками: так дрейф нагрузки не перекосит сравнение.
4. Оценивать значимость — например, **Welch t-test** (о нём ниже).
5. Помнить масштаб: локально сигнал — наносекунды, по сети — единицы микросекунд при тысячах замеров.

Ключевая тонкость нашего примера: сравнивать нужно **полной длины** строки. Тогда время = «длина совпавшего префикса + 1», и правильный символ отличается от неправильного ровно на один «шаг работы».

## Шаг 3: подбираем символ за символом

```python
import time, statistics as st

def measure(guess, n=60):
    s = []
    for _ in range(n):
        t0 = time.perf_counter_ns()
        check(guess)
        s.append(time.perf_counter_ns() - t0)
    return st.median(s)

known = ""
for pos in range(len(SECRET)):
    best, best_t = None, -1
    for c in "0123456789abcdef":
        guess = (known + c).ljust(len(SECRET), "x")   # полная длина!
        med = measure(guess)
        if med > best_t:
            best_t, best = med, c
    known += best
    print(f"pos {pos}: '{best}' -> '{known}' (медиана {best_t/1000:.0f} мкс)")
```

Реальный прогон (функция `work()` — цикл на 20000 операций, эмуляция «дорогого» сравнения):

```
pos 0: 'a' -> 'a' (медиана 1478 мкс)
pos 1: '3' -> 'a3' (медиана 2212 мкс)
pos 2: 'f' -> 'a3f' (медиана 2972 мкс)
pos 3: '9' -> 'a3f9' (медиана 3663 мкс)
Восстановлено: a3f9 | верно: True
```

Обрати внимание на медианы: они растут с каждым угаданным символом (1478 → 2212 → 2972 → 3663). Это и есть утечка: каждый правильный символ увеличивает время на один шаг. Последний символ отличается потому, что при полном совпадении сервер делает дополнительную операцию (создаёт сессию).

## Шаг 4: проверяем значимость, а не «на глаз»

Разница в один шаг тонет в шуме. Для проверки, что распределения действительно различаются, считают **Welch t-test** — статистику, которая учитывает и средние, и разброс:

```python
def welch(a, b):
    na, nb = len(a), len(b)
    va, vb = st.variance(a), st.variance(b)
    return (st.mean(a) - st.mean(b)) / ((va/na + vb/nb) ** 0.5)
```

Если `|t|` больше примерно `4.5`, различие значимо. При удалённой атаке вместо `perf_counter_ns` вокруг одного вызова берут `time_total` из `curl` (keep-alive сессия, без gzip), но принцип тот же.

## Шаг 5: где ещё течёт время

- **Атака Кохера на RSA.** В «квадрат-и-умножай» лишнее умножение выполняется только для бита `1` секретной экспоненты. По времени восстанавливают биты `d` слева направо.
- **Lucky 13** — тайминговая атака на сравнение MAC в TLS CBC.
- **Bleichenbacher** — оракул на padding, часто реализуется именно через тайминг.
- **CRIME/BREACH** — размер сжатого ответа как «время-подобный» канал.
- **Cache-timing** — доступ к памяти зависит от секрета (Prime+Probe, Flush+Reload).

## Контрмера: constant-time

Защита — писать код, время которого не зависит от секрета. Сравнение — через XOR всех байт без раннего выхода:

```python
def ct_compare(a, b):
    if len(a) != len(b):
        return False
    r = 0
    for x, y in zip(a, b):
        r |= x ^ y
    return r == 0
```

Плюс: Montgomery ladder вместо ветвления по битам, blinding экспоненты и модуля (RSA), фиксированное время по входу, отсутствие секретных индексов. Проверять такие реализации помогают `dudect` и `valgrind --tool=cachegrind`.

## Что мы теперь знаем

- Timing-атака использует **время работы**, а не математику шифра.
- Утечка возникает, когда поток управления или обращения к памяти зависят от секрета.
- Удалённо нужна **статистика**: много замеров, медиана, чередование, t-test.
- Сравнение строк с ранним выходом течёт по **длине совпавшего префикса**.
- Constant-time сравнение (XOR без выхода) закрывает утечку.
- Тайминг даёт по одному биту/байту — это **утечка**, а не брутфорс.

## Почему сравнение строк течёт

Самый частый timing-баг — не в криптоалгоритме, а в проверке. Функции сравнения вроде `memcmp`, `strcmp` и наивный цикл `if (a[i] != b[i]) return 0;` **выходят на первом различии**. Значит, время проверки зависит от того, сколько байт совпало. Если сервер сравнивает присланный MAC или токен с эталоном так, атакующий перебирает байт за байтом: правильный префикс заставляет сравнение работать дольше, и по микросекундной разнице байт восстанавливается.

Та же логика работает и для секретов, где сравнение замаскировано: `hmac.compare_digest`, `crypto.timingSafeEqual`, `secrets.compare_digest` существуют именно потому, что обычное `==` непригодно для секретов. Обратите внимание: утечка — не в том, что «ключ угадан», а в том, что **позиция первого несовпадения** выдаёт информацию. Отсюда правило: любая функция, которая трогает секрет, обязана выполняться за время, не зависящее от данных.

## Если не сработало

- **Сигнал тонет в шуме.** Удалённые измерения шумят сетью; нужны сотни замеров на кандидата, медиана, а не среднее, и статистический тест (Mann–Whitney, а не «на глаз»).
- **Сервер кэширует или балансируется.** Разные узлы и кэш ответов размывают сигнал; проверяйте, что бьёте в один и тот же бэкенд.
- **Утечка не в этом сравнении.** Возможно, время зависит от длины входа, от ветвления по секрету или от табличного доступа — смотрите не только на `memcmp`.
- **JIT/интерпретатор съел сигнал.** В managed-языках JIT выравнивает ветвления; утечка может исчезнуть или переехать.
- **Контрмера уже стоит.** `compare_digest` или фиксированное время делают атаку невозможной — это не «не сработало», а «закрыто».

## Частые вопросы

**Отличима ли timing-атака от сетевого шума?** Да, если накопить статистику: смещение порядка микросекунд при тысячах замеров становится значимым. Именно поэтому `dudect` сравнивает распределения, а не средние.

**Помогает ли добавление случайной задержки?** Плохо: усреднение по многим замерам её снимает. Правильная контрмера — постоянное время, а не шум.

**Как писать constant-time код?** Убирайте ветвления и индексацию по секрету: заменяйте `if` на маски/умножения, `a[i]` на выбор через bitwise-операции, сравнивайте через XOR-накопление (`acc |= a[i] ^ b[i]`) без раннего выхода.

## Куда дальше

Мы научились читать секрет по времени и закрывать эту утечку constant-time кодом. Дальше — самый практичный подкласс side-channel: **cache-атаки** (Flush+Reload и Prime+Probe), где утекает не время, а обращения к кэшу, и они ломают табличные реализации AES. А пока главное: **если время зависит от секрета, секрет утекает — и закрывается это constant-time кодом, а не «ускорением».**

## Где пригодится

- **CTF (hard):** тайминговые оракулы, подбор токенов, «сервер отвечает дольше на верный префикс».
- **Bug bounty:** утечка через сравнение секретов, Lucky13 на TLS, timing-оракулы.
- **Пентест:** аудит реализаций криптографических проверок.
- **Работа (SOC/IR):** детект аномального числа запросов — признак тайминговой атаки.
- **Разработка:** написание constant-time кода и ревью криптобиблиотек.
