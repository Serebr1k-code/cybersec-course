В потоковых режимах (CTR, OFB, CFB) шифротекст — это открытый текст, «сложенный по XOR» с ключевым потоком. Если IV/nonce повторяется, ключевой поток тоже повторяется, и два шифротекста дают XOR двух открытых текстов — классический **many-time pad**. В GCM повтор nonce ещё хуже: он ломает не только конфиденциальность, но и аутентичность, позволяя подделывать сообщения. Эта глава — как распознать и как ломать.

## Правило уникальности IV/nonce

Для CTR/OFB/CFB/GCM/CCM: **IV (nonce) должен быть уникален для каждого сообщения под данным ключом**. Не «случаен», а именно уникален. В GCM рекомендация — 96-битный nonce, уникальный (счётчик), иначе — повтор и катастрофа. В CBC уникальность IV нужна для семантической стойкости; повтор IV в CBC тоже опасен, но ломает иначе (см. `crypto-cbc-bitflip`).

## CTR: XOR двух сообщений

CTR шифрует: `C_i = P_i XOR KS_i`, где `KS_i = E_k(nonce || counter_i)`. При одинаковом nonce/счётчике `KS` совпадает:

```
C1 = P1 XOR KS
C2 = P2 XOR KS
=> C1 XOR C2 = P1 XOR P2
```

Ключевой поток сокращается. Получаем XOR двух открытых текстов — «many-time pad». Дальше:

- **Crib-dragging:** предполагаем фрагмент `P1` (например, `"flag{"`, `"GET /"`), вычисляем `P2` в тех же позициях, проверяем осмысленность. Итерируем, пока не восстановим оба.
- **Статистика:** если один текст — английский/русский, частотный анализ и пробелы (пробел XOR буква меняет регистр) помогают.

```python
def xor(a, b):
    return bytes(x ^ y for x, y in zip(a, b))

x = xor(C1, C2)          # = P1 XOR P2
# crib-drag
for i in range(len(x) - len(crib) + 1):
    guess = xor(x[i:i+len(crib)], crib)   # кандидат P2
    if all(32 <= c < 127 for c in guess):
        print(i, guess)
```

## OFB и CFB

- **OFB:** ключевой поток генерируется повторным шифрованием IV; повтор IV → тот же поток → тот же XOR-эффект.
- **CFB:** шифротекст влияет на поток, но при **одинаковом** IV и **одинаковом** первом блоке открытого текста совпадёт; при разных — частичная утечка. Полный many-time pad — при совпадении IV и общем префиксе.
- **Практический признак:** два шифротекста с одинаковым IV → `C1 XOR C2` даёт структуру открытых текстов.

## GCM: переиспользование nonce катастрофично

GCM — AEAD (шифрование + тег аутентичности). Его CTR-часть даёт `C_i = P_i XOR KS_i`, а тег считается от `H = E_k(0)` и длин данных. При повторе nonce:

- **Конфиденциальность:** `C1 XOR C2 = P1 XOR P2` (как CTR).
- **Аутентичность:** зная один `(P1, C1, T1)`, можно подделать теги для других сообщений с тем же nonce — **forbidden attack**. Атакующий вычисляет `H` (из двух сообщений с одним nonce) и генерирует валидный тег для произвольного сообщения.

```python
# forbidden attack (идея): из двух сообщений с одним nonce
# строим полином от H и находим H как gcd двух полиномов, затем подделываем тег
```

Именно поэтому в GCM nonce **обязан** быть уникальным; «случайный 96-битный» — допустимо только при малом объёме сообщений (birthday bound).

## Практический пример: фиксированный IV

Сервер шифрует каждый ответ с `IV = b'\x00'*16` (или статичным). Собираем несколько шифротекстов, XOR-им их между собой, crib-drag-им известные фрагменты (HTTP-заголовки, `"flag{"`, JSON-структуру) и восстанавливаем открытые тексты. Один из них содержит флаг.

## Практический пример: cookie с IV в открытом виде

Токен = `IV || CTR_encrypt(data)`. Если IV не меняется (или повторяется), два токена дают XOR данных. Если структура данных известна (например, `user=guest`), восстанавливаем секретную часть и подделываем токен.

## Как распознать в коде

- `AES.new(key, AES.MODE_CTR, nonce=...)` с константным/фиксированным nonce.
- Счётчик, сбрасываемый при рестарте процесса.
- IV, генерируемый слабым PRNG (предсказуем).
- «Случайный» IV, но короткий (birthday-коллизии при больших объёмах).
- В GCM — повтор nonce из-за ошибки в счётчике.

## Частые ошибки и как не застрять

- **Путать IV и ключ.** Ключ уникален по определению; IV — должен быть уникален на сообщение.
- **Использовать фиксированный IV для отладки и оставить в проде.** Классика.
- **Считать CBC-повтор безобидным.** В CBC другой эффект (bit-flip), но тоже уязвимость.
- **Не найти crib.** Начните с известных форматов: `flag{`, HTTP-методы, JSON-ключи, `admin`.
- **Забыть про GCM forbidden attack.** Повтор nonce ломает и целостность.
- **Игнорировать усечение.** Если XOR даёт «мусор», возможно, тексты разной длины/структуры.
- **Ограничиться двумя текстами.** Чем больше сообщений с одним потоком, тем легче crib-drag.

## Что дальше (decision)

1. Два шифротекста с одинаковым IV → XOR и crib-drag.
2. GCM с повтором nonce → forbidden attack (подделка тегов).
3. CBC с повтором IV → `crypto-cbc-bitflip`.
4. IV из слабого PRNG → предскажите (`crypto-python-random`, `crypto-lcg`).
5. Один текст, ключ неизвестен → XOR не помогает, ищите другой вектор.
6. Нужна защита → уникальный nonce (счётчик), AEAD с корректным nonce management.

## Справочная таблица

| Режим | Повтор IV/nonce | Последствие |
|-------|:---------------:|-------------|
| CTR | да | many-time pad (XOR текстов) |
| OFB | да | many-time pad |
| CFB | частично | утечка при общем префиксе |
| CBC | да | предсказуемость/bit-flip |
| GCM | да | many-time pad + подделка тегов |
| CCM | да | аналогично GCM |

## Полный разбор: forbidden attack на GCM

Повтор nonce в GCM ломает аутентичность. Идея: тег GCM вычисляется как полином от `H = E_k(0)`:

```
T = GHASH(H, AAD, C) XOR E_k(J0)
```

Если два сообщения используют **один** nonce, то `E_k(J0)` одинаково, а значит разность тегов даёт полином от `H` с известными коэффициентами (из шифротекстов). Имея две пары `(C1,T1)`, `(C2,T2)`, строим два полинома и берём их **gcd** — он равен `H` (с точностью до множителя). Зная `H`, атакующий подделывает тег для любого сообщения с тем же nonce:

```python
# Sage: forbidden attack (скелет)
# 1) построить полиномы f1, f2 от H из (C1,T1),(C2,T2)
# 2) g = gcd(f1, f2) -> линейный множитель -> H
# 3) вычислить валидный тег для произвольного C'
```

Практический вывод: повтор nonce в GCM — это не «потеря конфиденциальности», а **полная потеря целостности**. Один и тот же nonce на двух сообщениях достаточен для подделки. Поэтому nonce в GCM должен быть уникальным (счётчик), а не «случайным».

## Быстрые рецепты для CTF

- **Два шифротекста, один IV** → XOR и crib-drag.
- **GCM с повтором nonce** → forbidden attack (подделка тега).
- **CBC с повтором IV** → `crypto-cbc-bitflip`.
- **IV из слабого PRNG** → `crypto-python-random`, `crypto-lcg`.
- **Crib не находится** → пробуйте `flag{`, HTTP-заголовки, JSON-ключи.
