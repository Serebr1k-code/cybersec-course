## Вопрос, с которого всё начинается

Веб-приложение выдаёт ссылку для сброса пароля с токеном вида `?token=b5acb9c6`. Токен выглядит случайным, но если он сгенерирован модулем `random`, а не `secrets`, — он предсказуем. Мы получим свой токен и попробуем предсказать чужой. Для этого нужно понять, что внутри у `random` и как из наблюдений вытащить состояние.

## Наш пример

Приложение генерирует токен так:

```python
import random
def reset_token():
    return ''.join(random.choice('0123456789abcdef') for _ in range(8))
```

Запустим его с фиксированным seed `1337` и посмотрим на три токена подряд:

```python
random.seed(1337)
print([reset_token() for _ in range(3)])
```

```
['b5acb9c6', 'b3dc2bcc', '90b3e75a']
```

Вопрос: зная первый токен, можно ли получить третий? Если известен seed — да. Если seed неизвестен, но утекает по времени — тоже да. А если seed «настоящий» случайный, придётся восстанавливать состояние генератора.

## Шаг 1: что внутри random

Модуль `random` — это **Mersenne Twister** (MT19937), тот самый генератор из `crypto-mt19937-deep`. Он держит состояние из **624 32-битных слов** и после каждого выхода делает обратимое перемешивание. Отсюда три следствия:

- **624 подряд идущих 32-битных выхода** → состояние восстанавливается однозначно.
- **Меньше 624** → недоопределено, но при частичных наблюдениях помогает Z3.
- **Seed** — 32-битное число (или `os.urandom`, если seed не задан), поэтому по одному–двум выходам seed перебирается за секунды.

Python добавляет свои нюансы: `random.random()` возвращает 53-битное число, склеенное из **двух** выходов MT (27 и 26 бит), а `randint` маскирует выход. Это усложняет сбор ровно 624 полных слов, но не отменяет атаку.

## Шаг 2: восстановление seed по времени

Самый частый сценарий: приложение делает `random.seed(int(time.time()))` при старте. Тогда seed — это метка времени, и её окно крошечное. У нас есть известный токен; перебираем секунды вокруг «сейчас» и сравниваем:

```python
import random, time
t0 = int(time.time())
random.seed(t0)
known = reset_token()
for s in range(t0 - 300, t0 + 300):
    random.seed(s)
    if reset_token() == known:
        print("seed:", s, "known:", known)
        break
```

```
seed: 1791785691 known: 22b53240
```

Нашли seed. Теперь можно перемотать генератор и выдать **следующий** токен — тот, который сервер отдаст жертве. Достаточно `random.seed(s)` и вызова `reset_token()` ещё раз.

## Шаг 3: полное восстановление через randcrack

Если seed действительно случайный, остаётся путь через состояние. Нужны **624 значения по 32 бита**. Например, сервис отдаёт «случайные» 32-битные ID рядом с токеном — собираем их и подаём в библиотеку `randcrack`:

```bash
pip install randcrack
```

```python
from randcrack import RandCrack
rc = RandCrack()
for _ in range(624):
    rc.submit(server_getrandbits32())   # ровно 32-битные значения
print(rc.predict_getrandbits(32))
print(rc.predict_randint(0, 99))
print(rc.predict_random())               # следующий random()
```

Важно: `RandCrack.submit` принимает только 32-битные выходы. Если у вас `random()` (float) или `randint`, их нужно предварительно «распаковать» — иначе восстановление «съедет».

## Шаг 4: распаковка float и randint

`random()` — это 53 бита из двух слов. Чтобы скормить их в `RandCrack`, разложите каждое значение на верхние 27 и нижние 26 бит и подайте как два отдельных слова:

```python
hi = int(x * 2**27)
lo = int(x * 2**53) & 0x3ffffff
rc.submit(hi); rc.submit(lo)
```

Для `randint(0, 9)` выход ещё короче — около 3.3 бита. `RandCrack` тут не подойдёт, зато работает Z3: кодируем состояние как битовые векторы и добавляем наблюдения (см. `crypto-mt19937-deep`). Именно такой случай — наш поток цифр из введения.

## Шаг 5: где встречается на практике

Слабый `random` протекает в самые разные места:

- **Токены сброса и сессий.** Если используется `random`, а не `secrets`, токены предсказуемы.
- **OTP/2FA.** Шестизначный код — это ~20 бит; по нескольким кодам состояние восстанавливается.
- **`uuid.uuid4` на random.** `uuid1` утекает время и MAC, `uuid4` на `random` предсказуем.
- **Игровые последовательности.** «Угадай число» ломается после 624 наблюдений.
- **Перемешивание.** `random.shuffle` восстанавливается, если известны индексы.

## Шаг 6: инструменты и таблица наблюдений

Что собирать — зависит от того, какой примитив использует приложение:

| Примитив | Что даёт | Сколько нужно |
|----------|----------|---------------|
| `getrandbits(32)` | полное 32-битное слово | 624 |
| `random()` | 53 бита (2 слова: 27+26) | ~1250 вызовов |
| `randint(a, b)` | усечённый диапазон | больше 624 |
| `random.randbytes(n)` | `n` байт из слов | ~2496 байт |
| `choice`/`shuffle` | индексы | восстанавливается сложнее |

Инструменты: `randcrack` — для 624 полных выходов; `z3-solver` — для частичных; `mersenne-twister-predictor` — готовые обёртки; собственный `untemper` — когда нужен полный контроль над реализацией. Ставятся одной командой:

```bash
pip install randcrack z3-solver mersenne-twister-predictor
```

Практическая ловушка: `shuffle` необратим по выходам, поэтому собирайте **индексы** перестановок, а не итоговый порядок. И помните про версию: `randbytes` появился только в Python 3.9.

## Шаг 7: полный прогон от начала до конца

Соберём всю атаку в одну историю. Сервер выдаёт токен сброса и «случайный» 32-битный ID рядом. Мы регистрируемся сто раз и видим, что `random` не сидится явно — значит, seed неизвестен, идём через состояние.

1. Собираем 624 значения `getrandbits(32)` из поля ID.
2. Подаём их в `RandCrack`.
3. Просим у генератора предсказать следующий ID — он совпадает с тем, что сервер отдаст на 625-м запросе.
4. Теперь предсказываем токен: узнав состояние, воспроизводим последовательность `choice` и получаем токен чужого сброса.

Единственное условие — между нашими наблюдениями генератор не должен трогаться другими запросами. Если сервер в фоне вызывает `random` сам (например, для логов), поток сдвигается и нужно учитывать эти вызовы. Поэтому в реальной атаке сначала проверяют: генерируется ли токен тем же экземпляром генератора, что и наблюдаемые ID, или отдельным.

## Что мы теперь знаем

- Python `random` — это MT19937, а не криптостойкий генератор.
- **624** выхода по 32 бита → полное восстановление состояния (`randcrack`).
- `random()` = 53 бита из двух слов; перед подачей их надо распаковывать.
- Малый `randint` → Z3, а не `RandCrack`.
- Seed из времени → перебор окна `time.time()`.
- Стойкие генераторы — `secrets` и `os.urandom`; `random` ими не является.

## На что смотреть дальше

- **Считать `random()` одним 32-битным выходом** — это ошибка сборки; распаковывайте 27+26.
- **Смешивать генераторы** — у каждого `Random()` своё состояние, у модульного `random` — одно глобальное.
- **Пропускать вызовы** — любой промежуточный `random()` сдвигает поток, учитывайте все.
- **`randint` включительно** — `randint(a, b)` это `randrange(a, b+1)`; границы важны.
- **`seed=None`** — тогда seed берётся из `os.urandom` и неизвестен; нужен путь через состояние.

## Почему secrets, а не random

Разница между `random` и `secrets` — не стилистическая, а фундаментальная. `random` построен на Mersenne Twister: он **детерминирован** и оптимизирован под скорость и статистическое качество, а не под непредсказуемость. `secrets` берёт энтропию из `os.urandom`, то есть из CSPRNG ядра, и не восстанавливается по выходам.

| Свойство | `random` | `secrets` |
|----------|----------|-----------|
| Основа | MT19937 (детерминирован) | `os.urandom` (CSPRNG) |
| Восстановление состояния | да, по 624 выходам | нет |
| Seed | 32 бита / системное время | энтропия ядра |
| Для чего | моделирование, игры, выборка | токены, пароли, ключи |

Перевод кода обычно тривиален: `random.choice('0123456789abcdef')` → `secrets.choice('0123456789abcdef')`, `random.getrandbits(128)` → `secrets.token_hex(16)`, `random.randint` → `secrets.randbelow`. Ещё есть `random.SystemRandom()` — тонкая обёртка над `os.urandom`, совместимая по API с `random`; её берут, когда нужны методы вроде `shuffle`, но на криптостойкой основе.

Правило для аудита: если токен, пароль или ключ сессии сгенерирован через `random` (или `uuid.uuid4()` на нестандартной реализации), это **находка**. Для CSRF-токенов и сессионных cookie ищите `secrets`, `os.urandom` или фреймворковый CSPRNG.

## Восстановление состояния из randint через Z3

Когда приложение отдаёт не полные 32-битные слова, а усечённые значения (`randint(0, 999999)` для OTP), `RandCrack` не работает: ему нужны ровно 32 бита. Здесь помогает **Z3**. Идея — смоделировать MT19937 как систему битовых векторов и добавить наблюдения как ограничения.

Модель строится по шагам:

1. Состояние — 624 вектора по 32 бита (`BitVec('s%d' % i, 32)`).
2. Темперирование (`untemper`) записывается битовыми операциями: XOR, сдвиги, AND с масками.
3. Каждое наблюдение даёт ограничение вида `(temper(s[t]) >> k) == observed`, где `k` — сдвиг для усечения.
4. Решатель ищет любое состояние, удовлетворяющее всем наблюдениям.

```python
from z3 import *
s = [BitVec(f's{i}', 32) for i in range(624)]
# ... unwind temper + twist ...
sol = Solver()
for i, val in enumerate(observed):
    sol.add(Extract(31, 0, temper(s[i])) == val)
print(sol.check())
```

Тонкость: усечённое наблюдение теряет старшие биты, поэтому ограничений нужно больше 624, и решатель может найти несколько состояний. Проверяйте кандидата на **следующих** известных значениях — так отсеиваются ложные решения. Для OTP в 6 цифр (~20 бит) обычно хватает нескольких сотен наблюдений.

## Как отличить random от CSPRNG по чёрному ящику

Иногда исходников нет — есть только поток значений с сервера. Как понять, предсказуем ли он? Прямая проверка — собрать подряд идущие значения и попробовать восстановить MT:

- **Признак MT:** значения не имеют длинных повторов, но статистически «слишком хороши». Заберите 624 32-битных числа и проверьте, восстанавливается ли следующее через `RandCrack`. Если да — это `random`.
- **Признак времени:** сгенерируйте локально поток от `seed=int(time.time())` и поищите совпадение с первым значением сервера в окне ±несколько минут. Совпадение — сервер сидирует по времени.
- **Признак CSPRNG:** восстановление по 624 выходам не даёт следующего значения, а корреляция со временем отсутствует.

Помните про артефакты вывода: если сервер отдаёт токен как hex-строку, приложение могло вызвать `choice` на алфавите — тогда «сырых» 32-битных слов нет, и сначала нужно перевести строки в индексы. Для OTP, собранных как десятичные цифры, сработает тот же приём: моделируйте `randint` через Z3, а не через `RandCrack`.
