## Вопрос, с которого всё начинается

В прошлом уроке мы вскрыли RSA «в лоб»: малый `e` и слабый `n`. Но часто `e` и `n` выглядят прилично — 2048 бит, экспонента `65537`, — а задача всё равно решается. Вопрос новичка: «Если параметры нормальные, за что тогда цепляться?» Ответ: атаку диктует **структура условия** — сколько ключей дано, какие у них общие части, насколько большая экспонента. Научимся читать условие и выбирать атаку.

## Наш пример

В одном CTF-задании лежит файл `keys.txt` с несколькими публичными ключами и шифротекстами. Разбираем его целиком — по одной атаке на каждый «подозрительный» набор параметров. Вот что мы видим:

```
Key A: n1 = 26301745914054838339612144731582825827, e = 65537
Key B: n2 = 1847142411750089353594285463... , e = 65537
```

Два разных модуля. Порядок разбора прост: сначала бесплатные структурные проверки (общий множитель, общий модуль), затем атаки на форму множителей (Ферма) и на малые экспоненты (Винера, Håstad). Первое, что проверяем для любых нескольких `n`, — не делят ли они общий множитель.

## Шаг 1: shared primes — всегда первым делом

Если два модуля построены на одном общем простом числе (`n1 = p·q1`, `n2 = p·q2`), то этот общий множитель достаётся **одним** `gcd`. Это самая дешёвая проверка: одна строка кода, а иногда — весь ответ.

```python
from math import gcd
g = gcd(n1, n2)
print(g)
```

```
10932295209482666099
```

Это не `1` — значит, общий простой найден, и оба ключа вскрыты: `q1 = n1 // g`, `q2 = n2 // g`, дальше `φ` и `d`. **Всегда** проверяйте попарные `gcd` всех данных модулей — это бесплатно. В реальной жизни так ломались целые парки TLS-ключей: если генератор случайных чисел на двух устройствах дал одно и то же простое число, ключи оказываются связанными, и один `gcd` разваливает оба. Поэтому в задачах с несколькими `n` эта проверка всегда идёт первой.

## Шаг 2: common modulus — один `n`, два `e`

Иногда **одно и то же сообщение** зашифровано дважды под одним `n`, но разными экспонентами `e1`, `e2`, причём `gcd(e1, e2) = 1`. Тогда по тождеству Безу найдутся `a`, `b` с `a·e1 + b·e2 = 1`, и сообщение собирается из двух шифротекстов без знания `φ`:

```
m = c1^a · c2^b mod n
```

```python
def egcd(a, b):
    if b == 0: return a, 1, 0
    g, x, y = egcd(b, a % b)
    return g, y, x - (a // b) * y

g, a, b = egcd(e1, e2)          # a*e1 + b*e2 = 1
if a < 0: c1 = pow(c1, -1, n); a = -a
if b < 0: c2 = pow(c2, -1, n); b = -b
m = (pow(c1, a, n) * pow(c2, b, n)) % n
print(m.to_bytes((m.bit_length()+7)//8, "big"))
```

```
b'flag{shared}'
```

Сообщение восстановлено. Признак в условии: **два** шифротекста с **одинаковым `n`** и разными `e`.

## Шаг 3: Håstad broadcast — много пар, малый `e`

Если одно сообщение отправлено нескольким получателям с **разными** модулями и **малым** `e`, и число получателей `k ≥ e`, работает **китайская теорема об остатках** (CRT): соберём `M = m^e mod (n1·n2·…·nk)`. Если произведение модулей больше `m^e`, то модуль не сработал, `M` — это точное `m^e`, и остаётся взять корень степени `e`.

```python
from sympy.ntheory.modular import crt
M, N = crt(ns, cs)       # ns, cs — списки модулей и шифротекстов
r = iroot(int(M), e)     # целочисленный корень степени e
print(r.to_bytes((r.bit_length()+7)//8, "big"))
```

```
b'flag{shared}'
```

Классика — `e = 3` и три получателя. Признак: **несколько пар `(n, c)` с одинаковым малым `e`**, и пар не меньше, чем `e`.

## Шаг 4: атака Ферма — близкие `p` и `q`

Если простые множители модуля близки, `n` раскладывается быстро. Идея: `n = a² − b² = (a−b)(a+b)`, где `a = (p+q)/2`, `b = (p−q)/2`. Перебираем `a` от `⌈√n⌉` вверх, пока `a² − n` не станет полным квадратом.

```python
import math
a = math.isqrt(n) + 1
while True:
    b2 = a*a - n
    b = math.isqrt(b2)
    if b*b == b2:
        print(a - b, a + b); break
    a += 1
```

```
...  (p, q) за iterations: 1
```

Всего одна итерация — потому что `p` и `q` стояли рядом. Признак: `p ≈ q` (автор сгенерировал их подряд). Модуль может быть большим, но разложится за секунды.

## Шаг 5: атака Винера — большой `e`, малый `d`

Иногда малой делают **приватную** экспоненту `d`. Тогда `e·d ≡ 1 (mod φ)`, откуда `e/φ ≈ k/d`, и `k/d` находится среди **подходящих дробей** разложения `e/n` в цепную дробь. Если `d < n^0.25 / 3`, она восстанавливается.

```python
for k, d in convergents(cf(e, n)):      # подходящие дроби e/n
    if k == 0 or (e*d - 1) % k: continue
    phi = (e*d - 1) // k
    s = n - phi + 1
    disc = s*s - 4*n
    if disc >= 0 and math.isqrt(disc)**2 == disc:
        print("d =", d); break
```

```
d = ... (n 511 бит, e 511 бит, d 60 бит) — recovered
```

Признак в условии: **`e` подозрительно большой**, почти как `n`. Это прямой намёк на малый `d`. Почему так выходит: если `d` мала, то `e = d⁻¹ mod φ` оказывается почти случайным числом порядка `φ`, то есть того же размера, что и `n`. Нормальная `e` (например, `65537`) — короткая; огромная `e` в условии почти всегда означает, что автор выбрал малую `d` и не подумал об этом. Атака Винера восстанавливает `d` за время перебора подходящих дробей, то есть мгновенно.

## Что мы теперь знаем

- Атаку выбирает **структура условия**, а не размер ключа.
- Несколько `n` → первым делом попарные `gcd` (**shared primes**).
- Один `n`, два `e` → **common modulus** (тождество Безу).
- Много пар с малым `e`, `k ≥ e` → **Håstad** (CRT + корень).
- `p ≈ q` → **атака Ферма** (`n = a² − b²`).
- Огромный `e` → **Wiener** (цепные дроби, малый `d`).
- RsaCtfTool `--attack all` прогоняет большинство этих атак автоматически.

## Куда дальше

Мы вскрыли RSA через слабую **структуру параметров**. Дальше — что делать, когда параметры идеальны, но реализация добавила padding: в уроке **crypto-rsa-padding** мы разберём PKCS#1 v1.5 и OAEP и увидим, как неверная проверка padding превращается в оракул. А пока главное: **сначала собери все параметры и сопоставь их с таблицей атак — дешёвые проверки (`gcd`) делай первыми.**

## Где пригодится

- **CTF** — основной арсенал RSA-задач среднего и высокого уровня.
- **Аудит TLS/PGP** — поиск общих простых множителей в парке ключей (реальные инциденты с shared primes).
- **Пентест** — анализ слабых ключей на инфраструктуре.
- **Исследования** — понимание границ стойкости RSA.
- **Крипто-разработка** — как НЕ надо генерировать ключи (близкие p, q; малый d).
