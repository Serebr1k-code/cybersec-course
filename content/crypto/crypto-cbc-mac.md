## Зачем отдельный MAC для блочного шифра

HMAC — это MAC на основе хэш-функции. Но иногда нужен MAC **на основе блочного шифра** — например, когда в системе есть только AES-примитив, или когда нужно использовать один и тот же ключ/железо. CBC-MAC и его стандартизованная версия CMAC (RFC 4493, он же OMAC1) — именно такие конструкции. Их понимание критично, потому что CBC-MAC при неправильном применении ломается **очень легко**, а ошибка MAC-then-Encrypt унесла множество реальных систем (TLS ≤ 1.2, SSL).

MAC (Message Authentication Code) даёт **целостность и подлинность**: зная ключ `K`, можно проверить, что сообщение не изменено и создано владельцем ключа. MAC не даёт конфиденциальности — для неё нужно шифрование.

## Как строится CBC-MAC

CBC-MAC — это просто CBC-режим с **нулевым IV**, где в качестве тега берётся **последний блок** шифротекста (остальные отбрасываются):

```
C_0 = E_K(M_0)
C_i = E_K(M_i ⊕ C_{i-1})
tag = C_n
```

Для сообщения, длина которого кратна размеру блока, это работает как «сжимающая функция», стойкая к коллизиям — при условии **фиксированной длины** сообщений. Именно на этом условии всё и держится.

## Атака: length extension / extension attack

Проблема CBC-MAC: он **не защищает длину**. Для двух сообщений `m1` и `m2` (каждое — целое число блоков) выполняется:

```
CBC-MAC(m1 || (m2 ⊕ CBC-MAC(m1))) = CBC-MAC(m2)
```

Почему: после обработки `m1` внутреннее состояние равно `tag(m1)`. Если подать следующий блок `x`, то `C = E_K(x ⊕ tag(m1))`. Выбрав `x = m2_0 ⊕ tag(m1)`, мы получаем ровно `E_K(m2_0)` — то есть первый шаг CBC-MAC для `m2`. Продолжая, получаем тег `m2`. Итого, зная тег `m1`, атакующий строит валидный тег для `m1 || (m2 ⊕ tag(m1))` **без ключа**.

**Сценарий атаки:**

1. Атакующий имеет валидный `(m1, tag1)`, где `m1` — легитимное сообщение (например, «перевод 100»).
2. Он хочет тег для `m1' = m1 || (m2 ⊕ tag1)`, где `m2` — полезное для него продолжение.
3. Он вычисляет `tag2 = CBC-MAC(m2)`... нет, ему не нужен ключ для `m2` напрямую — если он может **запросить тег `m2`** у оракула (oracle-сценарий), то получает `tag2` и предъявляет пару `(m1', tag2)` как валидную.
4. Система проверяет `CBC-MAC(m1')` и получает `tag2` — подпись проходит.

Дополнительный «подарок»: если используется **нулевой padding** (дописывание нулей до границы блока), то `m` и `m || 0x00...0x00` дают одинаковый тег — ещё одна коллизия.

## Как CMAC это чинит

CMAC (RFC 4493) устраняет extension-атаку двумя приёмами:

1. **Субключи `K1`, `K2`** выводятся из `K` (умножение в GF(2^128) с полиномом `x^128 + x^7 + x^2 + x + 1`).
2. **Последний блок** обрабатывается по-разному в зависимости от того, полный он или нет: для полного XOR с `K1`, для неполного — padding `10*` и XOR с `K2`.

Это делает тег **зависящим от точной длины** и ломает extension-атаку: нельзя «продолжить» тег, потому что последний блок всегда обрабатывается специальным образом. CMAC — стандартный выбор для блочного MAC и используется, например, в AES-CCM (как CBC-MAC с длиной).

```python
# Псевдокод CMAC (упрощённо)
def cmac(K, msg, block=16):
    L = AES_ECB_encrypt(K, b"\x00"*block)
    K1 = gf_dbl(L)
    K2 = gf_dbl(K1)
    if len(msg) % block == 0 and len(msg) > 0:
        last = msg[-block:] ^ K1
        prefix = msg[:-block]
    else:
        # padding 10*
        pad = b"\x80" + b"\x00"*(block - (len(msg)%block) - 1)
        last = (msg[-(len(msg)%block):] + pad) ^ K2 if len(msg)%block else pad ^ K2
        prefix = msg[:len(msg) - (len(msg)%block)]
    C = b"\x00"*block
    for i in range(0, len(prefix), block):
        C = AES_ECB_encrypt(K, C ^ prefix[i:i+block])
    return AES_ECB_encrypt(K, C ^ last)
```

## Порядок шифрования и MAC: три схемы

Когда нужно и шифрование, и аутентификация, порядок операций критичен. Существуют три классические композиции:

| Схема | Описание | Безопасность |
|---|---|---|
| **Encrypt-then-MAC (EtM)** | Сначала шифруем, потом MAC по шифротексту | **Рекомендуется** |
| **MAC-then-Encrypt (MtE)** | Сначала MAC по тексту, потом шифруем `(text, MAC)` | Опасно |
| **Encrypt-and-MAC (E&M)** | MAC по тексту, шифротекст и MAC передаются рядом | Опасно |

**EtM безопасен**, потому что MAC покрывает шифротекст: любое изменение отвергается **до** расшифрования. Именно так работают AEAD (GCM/CCM) и IPsec/SSH.

**MtE опасен** из-за порядка проверок. При расшифровании приложение сначала **снимает padding**, и только потом проверяет MAC. Это открывает **padding oracle**: атакующий подбирает байты так, чтобы отличать «padding неверен» от «padding верен, но MAC не сошёлся» — и восстанавливает открытый текст (см. `crypto-padding-oracle`). Именно так работает POODLE и класс атак на TLS CBC.

**E&M опасен** потому что MAC по открытому тексту может утекать информацию о тексте и допускает атаки на каналы.

## Практический пример: подделка CBC-MAC

```python
from Crypto.Cipher import AES

K = b"0123456789abcdef"
def cbc_mac(msg):
    c = b"\x00"*16
    for i in range(0, len(msg), 16):
        c = AES.new(K, AES.MODE_ECB).encrypt(xor(c, msg[i:i+16]))
    return c

def xor(a, b): return bytes(x ^ y for x, y in zip(a, b))

# Оракул даёт тег легитимного m1
m1 = b"user=guest;act=view" + b"\x00"*4   # 20 байт? выровняем до 32
m1 = b"user=guest;act=view;pad=xxx"
m1 = m1[:32]
tag1 = cbc_mac(m1)

# Атакующий хочет тег для m1 || m2'
m2 = b"admin=true;xxxx"       # его продолжение (16 байт)
# запрашиваем у оракула тег m2 (если оракул разрешает произвольный ввод)
tag2 = cbc_mac(m2[:16])

# forged: m1 || (m2 XOR tag1)
forged = m1 + xor(m2[:16], tag1)
assert cbc_mac(forged) == tag2   # подпись валидна без знания K!
```

Это ровно extension-атака. На реальных системах она применяется к токенам, cookie и протоколам, использующим CBC-MAC без защиты длины.

## Частые ошибки

- **Использовать CBC-MAC для сообщений переменной длины.** Это прямая дорога к extension-атаке; нужен CMAC.
- **Нулевой padding в CBC-MAC.** Даёт коллизию `m` vs `m||0...0`.
- **Выбирать MAC-then-Encrypt.** Открывает padding oracle.
- **Сравнивать теги оператором `==`.** Утечка по времени; нужен constant-time compare (`hmac.compare_digest`).
- **Использовать один ключ для шифрования и MAC.** В общем случае не рекомендуется; лучше разные ключи (key separation).
- **Путать MAC и подпись.** MAC — симметричный (общий ключ), подпись — асимметричная.

## CBC-MAC, HMAC или AEAD: что выбирать

Когда нужен MAC на основе блочного шифра, выбор такой:

| Конструкция | Основа | Когда применять |
|---|---|---|
| CBC-MAC | блочный шифр | только фиксированная длина; иначе небезопасно |
| CMAC (OMAC1) | блочный шифр | стандарт для блочного MAC (RFC 4493) |
| HMAC | хэш-функция | когда есть хэш; универсальный стандарт |
| GMAC | GCM (GHASH) | внутри GCM для аутентификации |
| Poly1305 | Poly1305 | внутри ChaCha20-Poly1305 |

Практическое правило: если доступен HMAC — используйте HMAC. Если нужно на блочном шифре — используйте CMAC, а не «сырой» CBC-MAC. Если нужна и конфиденциальность, и целостность — берите AEAD (GCM/CCM/ChaCha20-Poly1305), а не собирайте схему вручную. Ручная композиция — источник ошибок (порядок MtE/EtM, разделение ключей, constant-time сравнение).

## Почему CBC-MAC всё ещё встречается

Несмотря на уязвимость «сырого» CBC-MAC, его модификации живут повсюду: AES-CCM (Wi-Fi WPA2, Bluetooth) использует CBC-MAC с кодированием длины; Zigbee, TLS (CCM-шифры), IPsec — тоже. Понимание CBC-MAC нужно, чтобы: (а) узнавать задачи, где «длина не защищена», и (б) понимать, почему стандарты добавляют кодирование длины (`10*`-padding, явное поле длины). Если в задаче CBC-MAC применяется к сообщениям разной длины без кодирования длины — это красный флаг и почти наверняка вектор атаки.

## Мини-чеклист по MAC-задачам

1. Сообщения переменной длины? → проверяйте extension-атаку на CBC-MAC.
2. Есть оракул тега? → можно реализовать extension end-to-end.
3. В коде `verify` до `unpad`? → padding oracle (MtE).
4. Используется `H(key‖msg)`? → length extension (см. `crypto-merkle`).
5. Сравнение тега `==`? → timing-утечка.

## Как не застрять

- **Спросите: сообщения фиксированной длины?** Если нет — CBC-MAC уязвим; ищите extension.
- **Есть ли оракул тегов?** Тогда extension-атака реализуема end-to-end.
- **Проверьте порядок в коде.** `verify_mac()` до или после `unpad()` — это разница между безопасностью и padding oracle.
- **Для подделки нужен валидный `(m1, tag1)`** — получите его легитимно (например, зарегистрировавшись).
- **Если видите CMAC/EtM/AEAD — атака не пройдёт;** ищите другой вектор.
- **Тег всегда сравнивайте в constant-time.**
