## Вопрос, с которого всё начинается

В прошлом уроке мы ломали MAC, собранный как `H(secret || msg)`. Но бывает, что
под рукой нет хэш-функции — только блочный шифр (AES). Тогда MAC строят прямо из
AES: это **CBC-MAC**. Он выглядит солидно: тег — результат цепочки шифрований, без
ключа не воспроизвести. Вопрос: так ли он прочен, если сообщения бывают **разной
длины**?

Оказывается, «сырой» CBC-MAC ломается на удивление легко: зная тег одного
сообщения, можно достроить сообщение с валидным тегом. Разберём атаку и то, как
стандартный **CMAC** её закрывает.

## Наш пример: CBC-MAC на платёжном запросе

Сервер аутентифицирует запросы так: берёт текст, считает CBC-MAC и сравнивает с
присланным тегом. У нас есть легитимный запрос (32 байта, ровно 2 блока) и его
тег, а также оракул, который вернёт тег для любого введённого сообщения:

```
m1   = b'user=guest;act=view;amount=100  '
tag1 = 842e81c82e1f8672ef554149a843eaa4
tag2 = 9cd1c55bbcb5440064b080c9da7b2aaa      # тег m2 от оракула
```

Наша цель — подделать тег для запроса, где `act=edit` и сумма побольше.

## Шаг 1: как строится CBC-MAC

CBC-MAC — это обычный CBC-режим с **нулевым IV**, у которого оставляют только
**последний блок** шифротекста (остальные отбрасывают):

```
C_0 = E_K(M_0)
C_i = E_K(M_i ⊕ C_{i-1})
tag = C_n
```

Смысл: каждый блок «впитывает» предыдущий, поэтому изменить середину, не сломав
тег, нельзя. Для сообщений **фиксированной длины** это стойкая сжимающая функция.
Вся проблема в словах «фиксированной длины».

## Шаг 2: extension-атака — достраиваем без ключа

Посмотрим, что будет, если после обработки сообщения `m1` подать ещё один блок
`x`. Внутреннее состояние после `m1` равно `tag1`, поэтому первый блок
продолжения даст `E_K(x ⊕ tag1)`. Выберем

```
x = m2 ⊕ tag1
```

Тогда `E_K(x ⊕ tag1) = E_K(m2)` — ровно первый шаг CBC-MAC для `m2`. Продолжая,
получаем тег `m2`. Формально:

```
CBC-MAC( m1 || (m2 ⊕ tag1) ) = CBC-MAC(m2)
```

То есть, зная `tag1` и запросив у оракула `tag2`, атакующий строит **валидную**
пару `(m1 || (m2 ⊕ tag1), tag2)` — без знания ключа. Система проверит её CBC-MAC и
получит `tag2`.

Отдельный «подарок»: если padding нулевой (дописывание нулей до границы блока),
то `m` и `m || 0x00…00` дают одинаковый тег — ещё одна коллизия.

## Полный прогон от начала до конца

```
$ python3 cbcmac_demo.py
m1   = b'user=guest;act=view;amount=100  '
tag1 = 842e81c82e1f8672ef554149a843eaa4
tag2 = 9cd1c55bbcb5440064b080c9da7b2aaa
CBC-MAC extension: m1 || (m2 XOR tag1)
  forged   = b'user=guest;act=view;amount=100  \xf1]\xe4\xba\x13~\xe2\x1f\x86;z(\xcb7\xd7\xc1'
  CBC-MAC(forged) = 9cd1c55bbcb5440064b080c9da7b2aaa
  совпал с tag2?  True

CMAC(forged_c) = 1cec2330a59f5c4239288676711ee748
CMAC(m2)       = f55f4491fe3f28c668a8eaad11db8548
CMAC подделка сработала? False
```

Первая половина — успешная подделка: `CBC-MAC(forged)` в точности равен `tag2`.
Мы «приклеили» своё продолжение к чужому сообщению, и тег сошёлся. Вторая
половина — почему тот же трюк не проходит на CMAC (разберём ниже).

## Шаг 3: как CMAC закрывает дыру

**CMAC** (RFC 4493, он же OMAC1) — стандартизованная замена «сырого» CBC-MAC. Он
добавляет два приёма:

1. Из ключа выводятся **субключи** `K1` и `K2` (умножение в `GF(2^128)`).
2. **Последний блок** обрабатывается по-разному: если он полный — XOR с `K1`;
   если неполный — padding `10*` и XOR с `K2`.

Это делает тег **зависящим от точной длины** сообщения. «Продолжить» тег нельзя:
последний блок всегда обрабатывается специальным образом, и вычисление
`CBC-MAC(forged)` больше не совпадает с `tag2`. В нашем прогоне CMAC-подделка дала
`False` — атака не прошла.

## Шаг 4: extension-атака в коде

Покажем атаку целиком, чтобы её можно было воспроизвести. Нам нужен `tag1` (известен) и оракул,
возвращающий `tag2` для `m2`. Форж строится XOR'ом:

```python
def xor(a, b): return bytes(x ^ y for x, y in zip(a, b))

m1   = b'user=guest;act=view;amount=100  '
tag1 = bytes.fromhex('842e81c82e1f8672ef554149a843eaa4')
m2   = b'act=edit;amount=9999999         '   # 2 блока, ровно 32 байта
tag2 = oracle(m2)                            # тег от оракула

forged = m1 + xor(m2, tag1)                  # 3 блока
assert cbcmac(forged) == tag2                # True — подделка удалась
```

`forged` состоит из трёх блоков: исходный `m1` и продолжение `m2 ⊕ tag1`. Внутреннее состояние после
`m1` равно `tag1`, поэтому первый блок продолжения даёт `E_K((m2⊕tag1) ⊕ tag1) = E_K(m2)` — то есть
продолжение вычисляет CBC-MAC от `m2`. Знание ключа не требуется.

Важное условие: **длины должны быть кратны блоку**, иначе padding вмешается в вычисление. На практике
атакующий подбирает `m2` так, чтобы её можно было «приклеить» без padding'а.

## Как это видят защитники

Подделка MAC видна по расхождению «сообщение ↔ тег» и по структуре протокола:

- **сообщения переменной длины** с CBC-MAC без кодирования длины — первопричина extension-атаки;
- **проверка MAC после расшифрования** (MtE) — открывает padding oracle;
- **сравнение тега через `==`** — timing-утечка; нужно `compare_digest`;
- **нулевой padding** — коллизия `m` vs `m || 0…0`.

Защита: использовать **CMAC** (зависит от длины) или **AEAD**; композиция **encrypt-then-MAC**;
сравнение тегов постоянным временем (`hmac.compare_digest`). Если в задаче CBC-MAC применяют к
сообщениям разной длины без явного поля длины — это красный флаг.

## Шаг 5: как правильно кодировать длину

Есть два способа закрыть extension-атаку, и оба встречаются в реальных стандартах:

1. **CMAC** — субключи `K1/K2` делают тег зависящим от длины (RFC 4493).
2. **Явное кодирование длины** — перед сообщением передают его длину (или добавляют блок с длиной).
   Так делает, например, AES-CCM: длина сообщения подмешивается в вычисление.

Почему второе работает: extension-атака опирается на то, что CBC-MAC от `m1` — это то же внутреннее
состояние, что и начало CBC-MAC от `m1 || x`. Если длина входит в вычисление, то состояние после `m1`
зависит ещё и от длины `m1`, и «приклеенное» продолжение уже не совпадёт.

Отсюда критерий для аудита: если видишь CBC-MAC (нулевой IV, последний блок как тег) и сообщения
переменной длины **без** кодирования длины и **без** CMAC-субключей — это уязвимая схема, и
extension-атака почти наверняка сработает.

## Что мы теперь знаем

- CBC-MAC — это CBC с нулевым IV, где тег — последний блок; он безопасен только
  для **фиксированной** длины.
- Extension-атака: `CBC-MAC(m1 || (m2 ⊕ tag1)) = CBC-MAC(m2)` — достраивание без
  ключа.
- Нулевой padding даёт коллизию `m` vs `m || 0…0`.
- CMAC чинит это субключами `K1/K2` и особым последним блоком; он зависит от длины.
- «Сырой» CBC-MAC нельзя применять к сообщениям переменной длины.
- Extension-атака реализуется end-to-end, если есть оракул тега и длины кратны блоку.
- Тег надо сравнивать постоянным временем (`hmac.compare_digest`), а не через `==`.
- «Сырой» CBC-MAC безопасен только при **фиксированной** длине сообщений.

## Порядок шифрования и MAC: три схемы

Когда нужны и шифрование, и аутентификация, порядок операций критичен.

| Схема | Описание | Безопасность |
|---|---|---|
| **Encrypt-then-MAC (EtM)** | Сначала шифруем, потом MAC по шифротексту | **Рекомендуется** |
| **MAC-then-Encrypt (MtE)** | Сначала MAC по тексту, потом шифруем `(text, MAC)` | Опасно |
| **Encrypt-and-MAC (E&M)** | MAC по тексту, шифротекст и MAC рядом | Опасно |

**EtM безопасен**: MAC покрывает шифротекст, любое изменение отвергается **до**
расшифрования — так работают AEAD (GCM/CCM) и IPsec/SSH. **MtE опасен** из-за
порядка проверок: при расшифровке приложение сначала снимает padding и только
потом проверяет MAC, что открывает **padding oracle** (см. `crypto-padding-oracle`);
именно так работают POODLE и класс атак на TLS CBC. **E&M** тоже опасен: MAC по
открытому тексту утекает информацию.

## Инструменты и почему CBC-MAC всё ещё встречается

```bash
pip install pycryptodome
python3 -c "from Crypto.Hash import CMAC; from Crypto.Cipher import AES; \
c=CMAC.new(b'0123456789abcdef', ciphermod=AES); c.update(b'msg'); print(c.hexdigest())"
```

Несмотря на уязвимость «сырого» CBC-MAC, его модификации живут повсюду: AES-CCM
(Wi-Fi WPA2, Bluetooth) использует CBC-MAC с кодированием длины; Zigbee, TLS и
IPsec — тоже. Понимание CBC-MAC нужно, чтобы (а) узнавать задачи, где «длина не
защищена», и (б) понимать, зачем стандарты добавляют `10*`-padding и явное поле
длины. Если в задаче CBC-MAC применяется к сообщениям разной длины без кодирования
длины — это почти наверняка вектор атаки.

Мини-чеклист по MAC-задачам:

1. Сообщения переменной длины? → проверяйте extension-атаку на CBC-MAC.
2. Есть оракул тега? → extension реализуется end-to-end.
3. В коде `verify` стоит до `unpad`? → padding oracle (MtE).
4. Используется `H(key‖msg)`? → length extension (см. `crypto-merkle`).
5. Сравнение тега оператором `==`? → timing-утечка, нужен `compare_digest`.

## Куда дальше

Мы прошли тему MAC: HMAC, `H(secret||msg)`, CBC-MAC/CMAC и порядки композиции.
Дальше ветвь crypto уходит в прикладные протоколы (`crypto-shamir`,
`crypto-tls-attacks`) и реальные системы. А главное запомни: **если CBC-MAC
применён к сообщениям разной длины без кодирования длины — это красный флаг;
«сырой» CBC-MAC небезопасен, используйте CMAC или AEAD**.
