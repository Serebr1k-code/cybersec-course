## Вопрос, с которого всё начинается

Мы умеем проверять целостность хэшем. Но голый хэш не доказывает, **кто** прислал данные: любой может пересчитать хэш. Нужен ключ — так появляется **MAC** (Message Authentication Code). Вопрос новичка: «Почему бы просто не хэшировать секрет вместе с сообщением?» Потому что такую конструкцию ломает length extension. Разберём правильную — HMAC — и атакуем её применение.

## Наш пример

У нас есть JWT-токен с `alg: HS256` и известным слабым секретом `secret`. Задача — подделать токен на `role=admin`. По пути разберём, как устроен HMAC и почему он устойчив там, где наивный MAC ломается.

## Шаг 1: зачем HMAC — наивный MAC не годится

Наивный MAC вида `H(secret ‖ message)` уязвим к **length extension**: зная `H(secret ‖ msg)` и длину секрета, атакующий может достроить сообщение и получить валидный MAC, не зная секрета (см. `crypto-merkle`). Это прямое следствие структуры Merkle–Damgård. HMAC (RFC 2104) решает проблему, используя хэш-функцию и ключ особым образом.

HMAC используется повсюду: JWT (HS256), подписи API (AWS SigV4), TLS (PRF), верификация webhook, PBKDF2, подписанные cookies.

## Шаг 2: конструкция ipad/opad

```
HMAC(K, m) = H((K' ⊕ opad) ‖ H((K' ⊕ ipad) ‖ m))
```

где `K'` — ключ, дополненный до размера блока хэша (64 байта для SHA-256), `ipad = 0x36`, `opad = 0x5C` (повторённые до размера блока). Почему это работает: **внешний хэш** начинается снова с секрета `(K' ⊕ opad)`, поэтому атакующий не может «продолжить» внутреннее состояние — финальный дайджест не является промежуточным состоянием Merkle–Damgård. Двойной проход с ключом — ключ к устойчивости. Забавно, но даже HMAC-MD5 остаётся стойким: коллизии MD5 не ломают его, потому что атакующий не контролирует внутреннее состояние (там секрет).

## Шаг 3: полный прогон

Посчитаем HMAC и сравним с наивным `H(K‖m)`:

```python
import hmac, hashlib
key, msg = b"secret", b"user=guest&role=user"
print(hmac.new(key, msg, hashlib.sha256).hexdigest())
print(hashlib.sha256(key + msg).hexdigest())
```

```
HMAC-SHA256: c3738138b6467e67af0755a377116af85cadd0b38cc933faadb3c9602ec01550
H(K||m)     : fe90ca013917ae06c91fbe987afce3a52cfe88eeadc55a3686261ff9b083d3b4
```

Значения разные, и именно первое устойчиво к length extension. Теперь подделаем JWT, зная секрет:

```python
signing = (header + "." + payload).encode()
sig = base64.urlsafe_b64encode(hmac.new(key, signing, hashlib.sha256).digest())
```

```
forged JWT: eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ1c2VyIjoiYWRtaW4iLCJyb2xlIjoiYWRtaW4ifQ.fZW5BJrerUcdVniII_an...
```

Токен с `role=admin` готов. HMAC как конструкция не сломан — сломано его **применение**: секрет оказался словарным.

## Шаг 4: атаки — слабый ключ и timing

HMAC сам по себе стоек, но применений с ошибками много:

1. **Слабый/короткий ключ.** JWT HS256 с секретом `secret` или `123456` ломается словарём: `hashcat -m 16500 jwt.txt rockyou.txt`. Найдя секрет, подделываем любой токен.
2. **Timing attack при неверном сравнении.** Если сервер сравнивает MAC оператором `==`, сравнение идёт побайтово с ранним выходом — и по времени ответа MAC подбирается побайтово. Лечится `hmac.compare_digest` (постоянное время):

```python
print(hmac.compare_digest(mac, mac))
```

```
compare_digest: True
```

3. **Усечённый MAC.** Некоторые реализации принимают первые 8 байт — стойкость падает до `2^64`.
4. **Key reuse.** Один ключ для MAC и шифрования без разделения — опасно.
5. **`H(K‖m)` вместо HMAC.** Тогда снова применим length extension.
6. **Порядок аргументов.** `HMAC(K, m) ≠ HMAC(m, K)`; путаница даёт уязвимость.

## Шаг 5: HMAC в JWT и других протоколах

JWT с `alg: HS256` подписывается `HMAC(secret, base64url(header) + "." + base64url(payload))`. Атаки: **подбор секрета** (если слабый); **`alg: none`** (если сервер принимает — подпись не проверяется); **алгоритм-конфузия** RS256→HS256 (публичный RSA-ключ подставляется как HMAC-секрет).

В реальных протоколах HMAC встречается в TLS PRF, **AWS SigV4** (цепочка ключей date→region→service), JWT HS256/384/512, IPsec/SSH, PBKDF2 и webhook-верификации (`X-Hub-Signature-256` у GitHub и Stripe). Аудит этих мест — поиск слабого секрета, `H(K‖m)` вместо HMAC, отсутствия проверки подписи и timing-сравнения.

## Шаг 6: аудит и как не застрять

Чек-лист: проверьте **ключ** (слабый → подбор `hashcat -m 16500`); проверьте **сравнение** (не constant-time → timing); проверьте **конструкцию** (`H(K‖m)` → length extension); проверьте **алгоритм** JWT (`none`/RS256→HS256). Для length extension нужна длина ключа. И главное: **HMAC сам по себе стоек — атакуйте его применение, а не конструкцию.** Если видите в коде `hashlib.sha256(secret + msg)` для проверки подписи — это находка.

## Почему HMAC устойчив — на пальцах

Представьте, что хэш-функция — это «мясорубка», которая перемалывает сообщение блок за блоком, поддерживая внутреннее состояние. При length extension атакующий берёт это состояние и «докручивает» его своим довеском. HMAC ломает этот трюк: внешний хэш перемалывает не сообщение напрямую, а результат внутреннего хэша, и начинается снова с секретного значения. Атакующий, даже зная промежуточное состояние внутреннего хэша, не может посчитать внешний, потому что для этого нужен ключ. Именно поэтому HMAC остаётся стойким, хотя использует «сломанный» MD5: коллизии в MD5 требуют контроля над сообщением, а в HMAC сообщение «заперто» под секретом. Этот принцип — **двойное использование ключа через ipad/opad** — и есть суть конструкции.

## Как HMAC применяют на практике

HMAC — самый универсальный MAC, потому что для него нужен только хэш, а хэш есть везде. В TLS до 1.2 он входит в PRF; в AWS SigV4 подпись запроса — это цепочка HMAC от даты к региону и сервису; JWT HS256/384/512 подписываются HMAC; IPsec и SSH используют его для целостности пакетов; PBKDF2 построен на HMAC как на базовом примитиве; GitHub и Stripe подписывают webhook-тела через `X-Hub-Signature-256`. Альтернативы — CMAC (на блочном шифре), GMAC (в GCM), Poly1305 (в ChaCha20-Poly1305), KMAC (на SHA-3) — дают то же свойство, но требуют других примитивов. При аудите ищите именно применение: слабый секрет, `H(K‖m)` вместо HMAC, отсутствие проверки подписи, сравнение через `==`.

## Итог

HMAC — это редкий случай, когда сама конструкция надёжна, а ломается только её использование. Поэтому в реальном аудите почти никогда не нужно «ломать HMAC» — нужно найти слабый ключ, неверное сравнение или неправильную конструкцию MAC. Держите в голове три признака уязвимости: секрет-словарное слово (ломается hashcat), `==` вместо `compare_digest` (timing), и `hash(secret + msg)` вместо HMAC (length extension). Любой из них превращает «стойкую подпись» в открытую дверь.

## Что мы теперь знаем

- Наивный `H(secret‖msg)` уязвим к **length extension**.
- **HMAC** = `H((K'⊕opad)‖H((K'⊕ipad)‖m))`; внешний хэш начинается снова с секрета.
- HMAC стоек даже с MD5; атакуют **применение**: слабый ключ, timing, усечение, `H(K‖m)`.
- Сравнивать MAC только через **`hmac.compare_digest`**.
- В JWT: слабый секрет → подделка; `alg: none` и конфузия алгоритмов — отдельные дыры.
- Правило: если в коде есть `hash(secret + message)` для проверки — это уязвимость.

## Куда дальше

Мы научились аутентифицировать сообщения ключом. Дальше — генераторы случайности, на которых держится вся криптография: в уроке **crypto-prng** мы разберём, что происходит, когда «случайные» числа на самом деле предсказуемы, и как это ломает ключи. А пока главное: **HMAC стоек, но его применение — нет; слабый секрет и неверное сравнение ломают подпись.**

## Где пригодится

- **CTF** — подделка API-токенов, JWT-секреты, length-extension.
- **Web-пентест** — HMAC в cookies, API-подписях, webhook-верификации.
- **Реверс/анализ API** — понимание схем подписи запросов (AWS SigV4, мобильные API).
- **Крипто-разработка** — правильная аутентификация сообщений.
- **Forensics** — проверка подлинности артефактов.
