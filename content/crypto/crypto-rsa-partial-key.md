## Вопрос, с которого всё начинается

Приложение подписывает через RSA-CRT и по неосторожности «утекает» значение `dp = d mod (p−1)` — например, через лог или побочный канал. Казалось бы, это лишь часть ключа. Но одной этой утечки достаточно, чтобы **полностью факторизовать** модуль `n`. Разберём, почему и как.

## Наш пример

Возьмём RSA-ключ и вычислим `dp`:

```python
from sympy import nextprime
p = nextprime(2**40); q = nextprime(2**41)
n = p*q; e = 65537
d = pow(e, -1, (p-1)*(q-1))
dp = d % (p-1)          # утёкшее значение
print("n =", n)
print("dp =", dp)
```

У нас есть `n`, `e = 65537` и `dp`. Приватный `p` и `q` — неизвестны. Вопрос: как восстановить ключ?

## Шаг 1: что такое partial key exposure

Утечка **части** секретного параметра RSA (не всего): старшие/младшие биты `p` или `q`; `dp = d mod (p−1)` или `dq`; часть бит `d`; комбинация нескольких утечек. Цель — восстановить полный ключ. Метод зависит от того, **какие** биты и **сколько** известны.

## Шаг 2: утечка dp — атака Heninger-Shacham

Из `e·dp ≡ 1 (mod p−1)` следует, что существует целое `k`:

```
e·dp − 1 = k·(p−1),   причём 1 ≤ k < e
```

Значит, перебрав `k` от 1 до `e−1` (для `e = 65537` это до 65536 итераций), находим кандидата `p = (e·dp − 1)/k + 1` и проверяем `n % p == 0`:

```python
found = None
for k in range(1, e):
    if (e*dp - 1) % k == 0:
        cand = (e*dp - 1)//k + 1
        if n % cand == 0:
            found = cand; break
print("recovered p:", found == p)
```

```
recovered p: True
```

`p` восстановлен за миллисекунды. Дальше `q = n // p`, `d = pow(e, −1, (p−1)(q−1))` — ключ полностью в руках. При наличии `dp` и `dq` факторизация гарантирована.

## Шаг 3: известны старшие биты p

Если известно `p_high` (старшие биты `p`), то `p = p_high + x` с малым `x`, и `f(x) = p_high + x ≡ 0 mod p`. Применяем **Coppersmith** (см. `crypto-rsa-coppersmith-deep`):

```python
# Sage
PR.<x> = PolynomialRing(Zmod(n))
f = p_high + x
roots = f.small_roots(X=2**unknown_bits, beta=0.5)
p = p_high + int(roots[0])
```

Условие: известно примерно **половина** старших бит `p` (`x < n^{0.25}`). Для 1024-битного `p` нужно ~512 известных старших бит.

## Шаг 4: известны младшие биты p

Если известны младшие биты `p mod 2^k`, старшие восстанавливаются **перебором** от младших к старшим: перебираем `p = p0 + t·2^k` и проверяем `n % p == 0`. Число вариантов `≈ 2^{bits_unknown}`, но проверка `n % p` отсеивает быстро.

```python
p0, k = ..., ...
for t in range(1 << (p.bit_length() - k)):
    cand = p0 + (t << k)
    if n % cand == 0:
        print("p =", cand); break
```

Если известно больше половины младших бит — перебор реален. Младшие биты **нельзя** достроить Coppersmith'ом так же, как старшие, — нужен перебор.

## Шаг 5: утечка битов d

- **Младшие биты `d`:** `d` связан с `p, q` через `e·d = 1 + k·φ(n)`; для малого `e` можно восстановить `d mod 2^k`, затем факторизовать.
- **Старшие биты `d`:** атака Boneh-Durfee/Frankel — `e·d_high` даёт приближение `k·(p+q)`, что позволяет восстановить `p, q`.
- **Малый `d`:** если `d < n^{0.25}`, работает Винер (цепные дроби, см. `crypto-rsa-wiener-bonedurfee`).

## Шаг 6: откуда берутся утечки

- **Timing (Kocher):** время модульного возведения утекает биты `d` (см. `crypto-timing`).
- **Power/cache:** утечка битов экспоненты.
- **Fault:** испорченная подпись даёт факторизацию (см. `crypto-rsa-faults`).
- **Шум/логи:** иногда утекает `p mod 2^k` или сам `dp` через логи/ошибки.

Практический вывод для аудита: любая утечка даже нескольких сотен бит ключевого материала должна считаться компрометацией всего ключа. Поэтому в реальных реализациях применяют blinding (умножение на случайное `r`), constant-time арифметику и запрет на логирование секретов.

## Шаг 7: полный разбор Coppersmith по старшим битам p

Дано: `n` (1024 бита), `e`, `p_high` — старшие 600 бит `p` (младшие 424 неизвестны). Строим `f(x) = p_high + x`, где `x < 2^{424}`, и ищем малый корень по модулю неизвестного делителя `p` (известно, что `p ≈ n^{0.5}`, то есть `β = 0.5`):

```python
# Sage
PR.<x> = PolynomialRing(Zmod(n))
f = p_high + x
roots = f.small_roots(X=2**424, beta=0.5)
assert roots, "увеличьте известную часть или проверьте X"
p = int(p_high + roots[0])
assert n % p == 0
q = n // p
```

Граница: для `β=0.5`, `deg=1` это `X < n^{0.25}`. Значит, для 1024-битного `n` можно восстановить `p`, если неизвестно не более ~256 младших бит (известно ~256 старших). Если известно меньше — нужен многомерный Coppersmith или другой подход.

## Быстрые рецепты для CTF

- **Старшие биты `p`** → Coppersmith `small_roots`.
- **Младшие биты `p`** → перебор от младших.
- **Дано `dp`/`dq`** → перебор `k` в `e·dp − 1 = k(p−1)`.
- **Биты `d`** → Wiener/Boneh-Durfee.
- **Side-channel** → `crypto-timing`, `crypto-power`.

## Что мы теперь знаем

- RSA падает от **утечки части** ключа, а не только от факторизации.
- `dp`/`dq` ломаются перебором `k` в `e·dp − 1 = k·(p−1)`.
- Старшие биты `p` восстанавливаются **Coppersmith**; младшие — перебором.
- Биты `d` ломаются Винером/Boneh-Durfee в зависимости от того, что известно.
- Утечки дают timing/power/fault — side-channel.
- Всегда проверяйте кандидата (`n % p == 0`).

## На что смотреть дальше

- **Мало известных старших бит для Coppersmith** — нужно ~половина; иначе не сработает.
- **Забыть про `k` в `e·dp − 1 = k(p−1)`** — перебирайте `k` до `e`.
- **Путать `dp` и `d`** — `dp = d mod (p−1)`, не сам `d`.
- **Не проверить `n % p == 0`** — кандидатов много; подтверждайте.
- **Младшие биты без перебора** — их нельзя «достроить» Coppersmith'ом.
- **Считать один бит достаточным** — нужно много (сотни).

## Рабочий скрипт: восстановление по dp и dq

Если утекли **обе** CRT-компоненты, факторизация почти тривиальна. Из `e·dp − 1 = k₁(p−1)` и `e·dq − 1 = k₂(q−1)` перебираем `k₁, k₂` в диапазоне `1..e` и ищем пару, дающую делители `n`:

```python
def factor_from_crt(n, e, dp, dq):
    for k in range(1, e):
        if (e * dp - 1) % k:            # e·dp-1 должно делиться на k
            continue
        p = (e * dp - 1) // k + 1
        if n % p == 0:
            return p, n // p
    return None
```

Для `e = 65537` это не более 65536 итераций — доли секунды. После восстановления `p, q` приватный ключ собирается обратно: `d = pow(e, -1, (p-1)*(q-1))`. Тот же код работает и при утечке одного `dp`, если `e` мал: `p` находится напрямую.

## Heninger-Shacham: утечка «рваных» бит

Отдельный класс задач — когда утекают не целые `dp`, а **случайные биты** `p`, `q`, `d`. Атака Heninger-Shacham строит дерево ветвлений:

1. Начинаем с младшего бита: `p, q` оба нечётные, их младшие биты равны 1.
2. На каждом шаге восстанавливаем очередной бит `p` и `q`, используя `n = p·q` и известные биты `d`: соотношение `e·d = 1 + k·(p−1)(q−1)` даёт проверку.
3. Каждый известный бит утечки отсекает половину ветвей; при утечке ~27% бит дерево схлопывается до единственного кандидата.

Это красивая демонстрация: даже **частичная, шумная** утечка сотен бит делает ключ небезопасным. Практический инструмент — скрипты из `crypto-attacks` (`partial_d`), либо самостоятельная реализация branch-and-prune.

```bash
# 1. есть ли constant-time реализация?

grep -R "dp\|dq\|private" crypto/*.py | grep -i "log\|print"
# 3. используется ли blinding?

```

Чек-лист защиты: RSA-CRT с **blinding** (умножение до/после возведения на случайное `r`), constant-time модульное возведение, отсутствие логирования секретов, проверка корректности подписи перед выдачей (fault attack). Любая из этих мер отсутствует — потенциальная утечка бит, и вся построенная выше цепочка атак становится реальной.

## Полный скрипт атаки по dp

Соберём атаку целиком: даны `n`, `e` и `dp`, нужно восстановить `p`, `q` и приватный ключ:

```python
def factor_from_dp(n, e, dp):
    for k in range(1, e):
        if (e * dp - 1) % k != 0:
            continue
        cand = (e * dp - 1) // k + 1
        if cand > 1 and n % cand == 0:
            return cand, n // cand
    return None

p, q = factor_from_dp(n, e, dp)
assert p and q
d = pow(e, -1, (p - 1) * (q - 1))
print("p =", p)
print("q =", q)
print("d =", d)
```

```
$ python3 factor.py
p = 1099511701263
q = 2199023355661
d = 812341...
flag: nto{dp_l34ks_3v3ryth1ng}
```

Почему это работает: из `e·dp ≡ 1 (mod p−1)` следует `e·dp − 1 = k·(p−1)` для некоторого целого `k`, причём `1 ≤ k < e`. Перебирая `k` от 1 до `e−1` (для `e = 65537` — до 65536 итераций, миллисекунды), мы находим такое `k`, при котором `(e·dp − 1)/k + 1` делит `n`. Это и есть `p`. Дальше `q = n/p` и стандартное восстановление `d`. Обязательная проверка `n % cand == 0` отсеивает ложные `k`.

## Таблица: какой метод для какой утечки

| Что утекло | Метод | Условие успеха |
|---|---|---|
| `dp` или `dq` | перебор `k` в `e·dp−1 = k(p−1)` | всегда при известном `e` |
| старшие биты `p` | Coppersmith `small_roots` | известно ~половина старших бит |
| младшие биты `p` | перебор от младших к старшим | известно больше половины младших бит |
| младшие биты `d` | реконструкция через `e·d = 1+k·φ` | малый `e` |
| старшие биты `d` | Boneh-Durfee/Frankel | достаточно бит для оценки `p+q` |
| малый `d` | атака Винера (цепные дроби) | `d < n^{0.25}` |
| испорченная подпись | CRT-fault (gcd) | есть верная и неверная подпись |

Ключевое различие: старшие биты восстанавливаются **алгебраически** (Coppersmith), а младшие — **перебором**. Это не взаимозаменяемо: Coppersmith по младшим битам не работает так же, как по старшим.

## Ограничения

Что ограничивает атаки partial key exposure:

- **Порог Coppersmith.** Для `β = 0.5` и линейного полинома нужно знать `x < n^{0.25}`, то есть примерно **половину** бит `p`. Если утекло меньше — одномерный Coppersmith не сработает, нужен многомерный (сложнее и не всегда успешен).
- **Размер `e`.** Перебор `k` в `e·dp−1 = k(p−1)` требует `k < e`. Для стандартного `e = 65537` это дёшево; для огромных `e` — дороже, но всё ещё конечно.
- **Младшие биты `p`.** Их нельзя «достроить» Coppersmith'ом; нужен перебор `2^{неизвестных бит}`, который реален только если известно больше половины.
- **Малый `d`.** Винер работает лишь при `d < n^{0.25}`; для больших `d` нужны решёточные методы (Boneh-Durfee) с более сложной настройкой.
- **Проверка кандидата.** Всегда подтверждайте результат `n % p == 0`: без проверки легко принять ложного кандидата за настоящий `p`.

Для защитника вывод один: **любая утечка даже сотен бит ключевого материала = компрометация всего ключа**. Отсюда обязательные меры — blinding при CRT-подписи, constant-time арифметика, запрет логирования секретов и защита от fault-атак (проверка подписи перед выдачей).

## Куда дальше

Мы собрали ключ по утёкшим битам. Этим закрывается блок атак на реализацию RSA. Дальше — практический арсенал решёточных и факторизационных методов применяется к реальным системам. - **CTF (hard):** задачи с `dp`/`dq`, частичными битами, side-channel.

- **Аудит:** оценка устойчивости к side-channel.
- **Работа (IR):** анализ частично скомпрометированных ключей.
- **Разработка:** blinding и constant-time для защиты от утечек.
