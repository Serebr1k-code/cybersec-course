## Вопрос, с которого всё начинается

Приложение подписывает через RSA-CRT и по неосторожности «утекает» значение `dp = d mod (p−1)` — например, через лог или побочный канал. Казалось бы, это лишь часть ключа. Но одной этой утечки достаточно, чтобы **полностью факторизовать** модуль `n`. Разберём, почему и как.

## Наш пример

Возьмём RSA-ключ и вычислим `dp`:

```python
from sympy import nextprime
p = nextprime(2**40); q = nextprime(2**41)
n = p*q; e = 65537
d = pow(e, -1, (p-1)*(q-1))
dp = d % (p-1)          # утёкшее значение
print("n =", n)
print("dp =", dp)
```

У нас есть `n`, `e = 65537` и `dp`. Приватный `p` и `q` — неизвестны. Вопрос: как восстановить ключ?

## Шаг 1: что такое partial key exposure

Утечка **части** секретного параметра RSA (не всего): старшие/младшие биты `p` или `q`; `dp = d mod (p−1)` или `dq`; часть бит `d`; комбинация нескольких утечек. Цель — восстановить полный ключ. Метод зависит от того, **какие** биты и **сколько** известны.

## Шаг 2: утечка dp — атака Heninger-Shacham

Из `e·dp ≡ 1 (mod p−1)` следует, что существует целое `k`:

```
e·dp − 1 = k·(p−1),   причём 1 ≤ k < e
```

Значит, перебрав `k` от 1 до `e−1` (для `e = 65537` это до 65536 итераций), находим кандидата `p = (e·dp − 1)/k + 1` и проверяем `n % p == 0`:

```python
found = None
for k in range(1, e):
    if (e*dp - 1) % k == 0:
        cand = (e*dp - 1)//k + 1
        if n % cand == 0:
            found = cand; break
print("recovered p:", found == p)
```

```
recovered p: True
```

`p` восстановлен за миллисекунды. Дальше `q = n // p`, `d = pow(e, −1, (p−1)(q−1))` — ключ полностью в руках. При наличии `dp` и `dq` факторизация гарантирована.

## Шаг 3: известны старшие биты p

Если известно `p_high` (старшие биты `p`), то `p = p_high + x` с малым `x`, и `f(x) = p_high + x ≡ 0 mod p`. Применяем **Coppersmith** (см. `crypto-rsa-coppersmith-deep`):

```python
# Sage
PR.<x> = PolynomialRing(Zmod(n))
f = p_high + x
roots = f.small_roots(X=2**unknown_bits, beta=0.5)
p = p_high + int(roots[0])
```

Условие: известно примерно **половина** старших бит `p` (`x < n^{0.25}`). Для 1024-битного `p` нужно ~512 известных старших бит.

## Шаг 4: известны младшие биты p

Если известны младшие биты `p mod 2^k`, старшие восстанавливаются **перебором** от младших к старшим: перебираем `p = p0 + t·2^k` и проверяем `n % p == 0`. Число вариантов `≈ 2^{bits_unknown}`, но проверка `n % p` отсеивает быстро.

```python
p0, k = ..., ...
for t in range(1 << (p.bit_length() - k)):
    cand = p0 + (t << k)
    if n % cand == 0:
        print("p =", cand); break
```

Если известно больше половины младших бит — перебор реален. Младшие биты **нельзя** достроить Coppersmith'ом так же, как старшие, — нужен перебор.

## Шаг 5: утечка битов d

- **Младшие биты `d`:** `d` связан с `p, q` через `e·d = 1 + k·φ(n)`; для малого `e` можно восстановить `d mod 2^k`, затем факторизовать.
- **Старшие биты `d`:** атака Boneh-Durfee/Frankel — `e·d_high` даёт приближение `k·(p+q)`, что позволяет восстановить `p, q`.
- **Малый `d`:** если `d < n^{0.25}`, работает Винер (цепные дроби, см. `crypto-rsa-wiener-bonedurfee`).

## Шаг 6: откуда берутся утечки

- **Timing (Kocher):** время модульного возведения утекает биты `d` (см. `crypto-timing`).
- **Power/cache:** утечка битов экспоненты.
- **Fault:** испорченная подпись даёт факторизацию (см. `crypto-rsa-faults`).
- **Шум/логи:** иногда утекает `p mod 2^k` или сам `dp` через логи/ошибки.

Практический вывод для аудита: любая утечка даже нескольких сотен бит ключевого материала должна считаться компрометацией всего ключа. Поэтому в реальных реализациях применяют blinding (умножение на случайное `r`), constant-time арифметику и запрет на логирование секретов.

## Шаг 7: полный разбор Coppersmith по старшим битам p

Дано: `n` (1024 бита), `e`, `p_high` — старшие 600 бит `p` (младшие 424 неизвестны). Строим `f(x) = p_high + x`, где `x < 2^{424}`, и ищем малый корень по модулю неизвестного делителя `p` (известно, что `p ≈ n^{0.5}`, то есть `β = 0.5`):

```python
# Sage
PR.<x> = PolynomialRing(Zmod(n))
f = p_high + x
roots = f.small_roots(X=2**424, beta=0.5)
assert roots, "увеличьте известную часть или проверьте X"
p = int(p_high + roots[0])
assert n % p == 0
q = n // p
```

Граница: для `β=0.5`, `deg=1` это `X < n^{0.25}`. Значит, для 1024-битного `n` можно восстановить `p`, если неизвестно не более ~256 младших бит (известно ~256 старших). Если известно меньше — нужен многомерный Coppersmith или другой подход.

## Быстрые рецепты для CTF

- **Старшие биты `p`** → Coppersmith `small_roots`.
- **Младшие биты `p`** → перебор от младших.
- **Дано `dp`/`dq`** → перебор `k` в `e·dp − 1 = k(p−1)`.
- **Биты `d`** → Wiener/Boneh-Durfee.
- **Side-channel** → `crypto-timing`, `crypto-power`.

## Что мы теперь знаем

- RSA падает от **утечки части** ключа, а не только от факторизации.
- `dp`/`dq` ломаются перебором `k` в `e·dp − 1 = k·(p−1)`.
- Старшие биты `p` восстанавливаются **Coppersmith**; младшие — перебором.
- Биты `d` ломаются Винером/Boneh-Durfee в зависимости от того, что известно.
- Утечки дают timing/power/fault — side-channel.
- Всегда проверяйте кандидата (`n % p == 0`).

## На что смотреть дальше

- **Мало известных старших бит для Coppersmith** — нужно ~половина; иначе не сработает.
- **Забыть про `k` в `e·dp − 1 = k(p−1)`** — перебирайте `k` до `e`.
- **Путать `dp` и `d`** — `dp = d mod (p−1)`, не сам `d`.
- **Не проверить `n % p == 0`** — кандидатов много; подтверждайте.
- **Младшие биты без перебора** — их нельзя «достроить» Coppersmith'ом.
- **Считать один бит достаточным** — нужно много (сотни).

## Куда дальше

Мы собрали ключ по утёкшим битам. Этим закрывается блок атак на реализацию RSA. Дальше — практический арсенал решёточных и факторизационных методов применяется к реальным системам. А пока главное: **`dp` ломается перебором `k`; старшие биты `p` — Coppersmith; младшие — перебор; защита — blinding и constant-time.**

## Где пригодится

- **CTF (hard):** задачи с `dp`/`dq`, частичными битами, side-channel.
- **Bug bounty:** утечки ключей через ошибки/тайминги.
- **Аудит:** оценка устойчивости к side-channel.
- **Работа (IR):** анализ частично скомпрометированных ключей.
- **Разработка:** blinding и constant-time для защиты от утечек.
