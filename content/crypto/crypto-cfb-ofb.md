## Вопрос, с которого всё начинается

Блочный шифр работает блоками по 16 байт и требует padding — неудобно для сетевого потока. Поэтому есть **потоковые режимы** (CFB, OFB, CTR), которые превращают блочный шифр в генератор ключевого потока. Вопрос новичка: «Три режима делают одно и то же — в чём разница и какой из них ломается?» Разница в том, что подаётся на вход блочного шифра, а ломаются они по-разному. Разберём на одном примере.

## Наш пример

Возьмём один и тот же ключ и IV и зашифруем одну фразу в трёх режимах:

```
transfer=100&to=alice
```

Посмотрим, как отличаются длины, чем режимы похожи и как на каждом из них провести атаку. Это наш сквозной пример.

## Шаг 1: зачем превращать блочный шифр в потоковый

Блочный шифр даёт фиксированные блоки; чтобы зашифровать произвольную длину, нужно padding, а он «раздувает» данные и требует аккуратной обработки. Потоковый режим вырабатывает **ключевой поток** (keystream) — последовательность байт, которая складывается по XOR с открытым текстом. Плюсы: длина шифротекста равна длине текста, padding не нужен, можно шифровать поток и произвольный доступ. Общий минус всех трёх: **требуется уникальный IV/nonce** — иначе keystream повторится и защита рухнет.

Все три режима — это разные способы получить keystream из блочного шифра. Проще всего их запомнить по тому, что подаётся на вход блочного шифра на каждом шаге: счётчик (CTR), предыдущий выход (OFB) или предыдущий шифротекст (CFB). От этого свойства и зависят все дальнейшие различия — параллелизм, произвольный доступ, распространение ошибок.

## Шаг 2: CTR — keystream из счётчика

```
O_i = E_K(nonce ‖ counter_i)
C_i = P_i ⊕ O_i
```

На вход блочного шифра подаётся `nonce ‖ counter`, счётчик растёт на каждый блок. Плюсы: **полностью параллелизуемо**, есть произвольный доступ (блок `i` расшифровывается независимо). Минус: повтор пары `(key, nonce)`.

## Шаг 3: OFB — keystream из итераций

```
O_0 = E_K(IV)
O_i = E_K(O_{i-1})
C_i = P_i ⊕ O_i
```

OFB итерирует блочный шифр от **предыдущего выхода**. Keystream не зависит от данных, поэтому ошибка в одном бите шифротекста портит ровно один бит открытого текста (нет распространения). Но генерацию keystream нельзя параллелить (это цепочка), и повтор IV даёт тот же поток.

## Шаг 4: CFB — keystream из предыдущего шифротекста

```
C_i = P_i ⊕ E_K(C_{i-1})      (C_0 = IV)
```

CFB берёт на вход предыдущий **шифротекст**. Здесь keystream **зависит от данных**, и ошибка в байте шифротекста портит байт в текущем блоке и «сдвигает» следующий — распространение ошибок есть. Расшифровка симметрична: `P_i = C_i ⊕ E_K(C_{i-1})`. CFB тоже требует уникального IV. Исторические варианты CFB-8 и CFB-1 обрабатывают по байту или биту за шаг; в современных системах их заменили CTR и AEAD.

## Шаг 5: полный прогон

Зашифруем нашу фразу в трёх режимах и сравним длины:

```python
for mode, name in [(AES.MODE_CTR,"CTR"), (AES.MODE_OFB,"OFB"), (AES.MODE_CFB,"CFB")]:
    ...
    print(name, "len(ct)=", len(ct))
```

```
CTR len(ct)= 21
OFB len(ct)= 21
CFB len(ct)= 21
```

Все три дали длину, равную длине открытого текста (`21`), без padding — это и есть главный практический плюс потоковых режимов. Обратите внимание: в pycryptodome у CFB по умолчанию `segment_size=8` (историческое поведение); для блочного CFB указывайте `segment_size=128`.

## Шаг 6: две атаки

**Атака первая — повтор IV/nonce.** Если два сообщения зашифрованы одним ключом и одним nonce, keystream совпадает: `C1 ⊕ C2 = P1 ⊕ P2`. Проверим:

```python
c1 = AES.new(key, AES.MODE_CTR, nonce=b"\x00"*8).encrypt(b"GET /index.html HTTP/1.1")
c2 = AES.new(key, AES.MODE_CTR, nonce=b"\x00"*8).encrypt(b"GET /secret?x=flag{reuse}")
x = bytes(a ^ b for a, b in zip(c1, c2))
print(x[:16].hex())
```

```
reused-nonce XOR: 00000000001a0b07171d5a07171d5a... 
```

Видите нули в начале? Это позиции, где символы обоих текстов совпали — прямое доказательство повтора потока. Дальше crib-dragging восстанавливает оба текста (см. `crypto-iv-reuse`).

**Атака вторая — битовый флип.** Ни один из режимов не аутентифицирует данные. В CTR/OFB `P_i` меняется ровно на ту же дельту, что и `C_i`:

```python
ct = bytearray(ct); i = pt.index(b"100")
for k in range(3):
    ct[i+k] ^= b"100"[k] ^ b"999"[k]
print(AES.new(key, AES.MODE_CTR, nonce=iv[:8]).decrypt(bytes(ct)))
```

```
CTR bitflip -> b'transfer=999&to=alice'
```

Мы поменяли сумму перевода, не зная ключа. В CFB флип сложнее (keystream зависит от данных), но отсутствие целостности остаётся. Вывод: голые потоковые режимы всегда комбинируйте с MAC (encrypt-then-MAC) или берите AEAD (GCM/ChaCha20-Poly1305).

## Шаг 7: как выбрать режим и не застрять

При анализе неизвестного шифра: длина не кратна 16 → потоковый режим; есть два шифротекста → XOR и смотрите на осмысленность; первые 16 байт неизменны → это IV; есть тег → AEAD; ключ и nonce известны из кода → воспроизведите keystream локально. И помните о границах: **все три режима требуют уникального IV/nonce**; **ни один не даёт целостности**; **OFB/CFB нельзя параллелить** при генерации потока; **CTR опасен при переполнении счётчика** (32-битный счётчик заворачивается после 64 ГБ — известный баг реализаций).

## Обнаружение повторного IV на практике

Как понять, что где-то переиспользуется IV? Есть несколько эвристик. Первая — два шифротекста одинаковой длины: если `C1 ⊕ C2` даёт много нулевых байт в позициях, где символы текстов совпали, — почти наверняка keystream повторён. Практический тест прост: посчитайте долю нулевых байт в `C1 ⊕ C2`; для осмысленных текстов она заметно выше случайной `1/256`. Вторая — структура протокола: если nonce передаётся открыто (`nonce ‖ ciphertext`) и не меняется между запросами, это дыра. Третья — счётчик CTR, который стартует с нуля при каждом рестарте процесса: рестарт даёт повтор keystream. И наконец, фиксированный IV как «ошибка проектирования»: разработчики иногда берут IV = timestamp или константу, «чтобы не хранить состояние», и тем самым позволяют сравнивать префиксы двух сообщений. Всегда генерируйте IV случайно и передавайте вместе с шифротекстом.

## Что мы теперь знаем

- Потоковые режимы дают keystream; длина шифротекста = длине текста, padding не нужен.
- **CTR** — из счётчика (параллелизуемо, произвольный доступ); **OFB** — из итераций; **CFB** — из предыдущего шифротекста (зависит от данных).
- Повтор IV/nonce → `C1 ⊕ C2 = P1 ⊕ P2` (many-time pad) во всех трёх.
- Ни один режим не аутентифицирует данные → возможны **битовые флипы**.
- Защита: уникальный nonce + MAC или AEAD.
