## Зачем превращать блочный шифр в потоковый

Блочный шифр работает с 16-байтными блоками и требует padding, что неудобно для потоков данных (сеть, файлы, телеметрия). **Потоковые режимы** (CFB, OFB, CTR) превращают блочный шифр в генератор keystream: они вырабатывают поток байт, который XORится с открытым текстом. Плюсы: длина шифротекста равна длине текста, не нужен padding, можно работать с потоками и произвольным доступом. Минус — **все три требуют уникального IV/nonce**, иначе keystream повторяется и вся защита рушится.

Все три режима — это, по сути, разные способы получить «хороший» keystream из блочного шифра. Отличаются они тем, что подаётся на вход блочного шифра на каждом шаге.

## CTR: keystream из счётчика

```
O_i = E_K(nonce || counter_i)
C_i = P_i ⊕ O_i
```

На вход блочного шифра подаётся `nonce || counter` (обычно 96-битный nonce + 32-битный счётчик). Счётчик инкрементируется на каждый блок. Плюсы: **полностью параллелизуемо**, произвольный доступ (можно расшифровать блок `i` независимо), простой и быстрый. Минус — повтор `(key, nonce)`.

## OFB: keystream из итераций

```
O_0 = E_K(IV)
O_i = E_K(O_{i-1})
C_i = P_i ⊕ O_i
```

OFB итерирует блочный шифр от предыдущего выхода. Keystream **не зависит от данных** — это важно: ошибка в одном бите шифротекста портит ровно один бит открытого текста (нет распространения). Но OFB **нельзя параллелить** при генерации keystream (цепочка), и повтор IV даёт одинаковый keystream.

## CFB: keystream из предыдущего шифротекста

```
C_i = P_i ⊕ E_K(C_{i-1})      (C_0 = IV)
```

CFB использует предыдущий **шифротекст** как вход. Здесь keystream зависит от данных, и ошибка в байте шифротекста портит байт в текущем блоке и «сдвигает» следующий — то есть распространение ошибок есть. Расшифрование: `P_i = C_i ⊕ E_K(C_{i-1})` — операция симметрична. CFB тоже требует уникального IV.

Существуют варианты CFB с частичной обратной связью (CFB-8, CFB-1), где сдвиг идёт побайтово/побитово — они исторически использовались для потоков, но менее эффективны.

## Сравнительная таблица

| Свойство | CTR | OFB | CFB |
|---|---|---|---|
| Вход блочного шифра | nonce‖counter | предыдущий выход | предыдущий шифротекст |
| Параллелизм (шифр.) | да | нет | нет |
| Произвольный доступ | да | нет | нет |
| Распространение ошибки | 1 бит | 1 бит | 1 байт + сдвиг блока |
| Зависит от данных | нет | нет | да |
| Требует уникального IV | да | да | да |

## Главная атака: повтор IV/nonce

Если два сообщения зашифрованы одним ключом и **одним IV/nonce**, keystream совпадает:

```
C1 ⊕ C2 = (P1 ⊕ O) ⊕ (P2 ⊕ O) = P1 ⊕ P2
```

Это **many-time pad** (см. `crypto-xor-otp` и `crypto-iv-reuse`). Зная один из текстов (или угадав его crib-dragging-ом), второй восстанавливается мгновенно. Это работает для CTR, OFB и CFB одинаково — все три «текут» при повторе IV.

```python
# Восстановление XOR двух текстов при reused keystream
c1 = bytes.fromhex(open("c1.hex").read().strip())
c2 = bytes.fromhex(open("c2.hex").read().strip())
xor = bytes(a ^ b for a, b in zip(c1, c2))   # = P1 ^ P2
print(xor)
# дальше crib-dragging: подставляем угаданные слова
```

## Отсутствие аутентификации: битовые флипы

Ни один из CFB/OFB/CTR не аутентифицирует данные. Значит, атакующий может **целенаправленно менять** открытый текст, зная его структуру: `P_i` меняется ровно на ту же дельту, что и `C_i` (в CTR/OFB — побитово; в CFB — сложнее из-за зависимости keystream от данных). Для CTR/OFB это классический bit-flip:

```
новый_C = старый_C ⊕ старый_P ⊕ желаемый_P
```

Поэтому голые потоковые режимы всегда нужно комбинировать с MAC (encrypt-then-MAC) или использовать AEAD (GCM/ChaCha20-Poly1305).

## Практический пример: анализ потока с reused nonce

```python
# Дано: два ciphertext'а CTR с одинаковым nonce
# 1. XOR -> P1 ^ P2
# 2. crib-dragging: предполагаем, что P1 начинается с "HTTP/1.1 200"
known = b"HTTP/1.1 200"
p1_guess = known
partial = bytes(a ^ b for a, b in zip(xor[:len(known)], p1_guess))
# partial = восстановленный префикс P2
print(partial)
```

Именно так решаются многие задачи «given two ciphertexts encrypted with same nonce». Инструмент `xortool` автоматизирует подбор длины ключа и частотный анализ для repeating-key XOR.

## Частые ошибки

- **Переиспользовать IV/nonce.** Самая частая и фатальная ошибка.
- **Считать, что «AES = безопасно».** Без уникального nonce любой потоковый режим ломается.
- **Ожидать от CFB/OFB/CTR целостности.** Её нет; нужен MAC/AEAD.
- **Параллелить OFB/CFB.** Нельзя при генерации keystream (цепочка).
- **Путать режимы.** CFB зависит от данных, OFB/CTR — нет; ошибки распространяются по-разному.
- **Сбрасывать счётчик CTR при рестарте.** Это даёт повтор nonce.

## Обнаружение повторного IV на практике

Как понять, что где-то переиспользуется IV? Есть несколько эвристик.

- **Два шифротекста одинаковой длины.** Если `C1 ⊕ C2` даёт много байт, похожих на печатный текст (частотный анализ по XOR-потоку показывает «пробелы» в позициях), — почти наверняка reused keystream. Для ASCII-текстов XOR двух текстов имеет много `0x00` в позициях, где символы совпали.
- **Структура протокола.** Если nonce передаётся в открытом виде (например, `nonce || ciphertext`) и не меняется между запросами — это дыра.
- **Счётчик CTR.** Если счётчик стартует с 0 при каждом рестарте процесса и nonce фиксирован (или отсутствует) — рестарт даёт повтор keystream.

Практический тест — посчитать долю нулевых байт в `C1 ⊕ C2`: для осмысленных текстов она заметно выше `1/256`.

## Потоковые режимы и произвольный доступ

CTR (и в меньшей степени OFB) позволяют **расшифровать блок `i` независимо**, вычислив keystream-блок с нужным счётчиком. Это удобно для больших файлов и БД (шифрование «постранично»). Но именно это свойство делает CTR опасным при ошибке в управлении счётчиком: если счётчик «заворачивается» или повторяется (например, 32-битный счётчик переполняется после 2^32 блоков = 64 ГБ), keystream начинает повторяться в пределах одного сообщения. Для больших объёмов это реальная проблема (известный баг в некоторых реализациях с 32-битным счётчиком). Рекомендуется 64-битный счётчик или ротация ключа.

## CFB-8, CFB-1 и частичная обратная связь

Исторические варианты CFB с сегментом меньше блока (CFB-8, CFB-1) обрабатывают по одному байту или биту за шаг. Их использовали в протоколах, где важна побитовая потоковость (например, терминалы, устаревшие VPN). Недостатки: медленно (одно шифрование на 1 байт) и слабее, потому что keystream обновляется по чуть-чуть. В современных системах их заменяют CTR или AEAD. Если задача содержит «CFB-8» или `segment_size=8` — это подсказка, что keystream зависит от данных более «плавно», и bit-flip даёт предсказуемый эффект только на уровне бита.

## Детерминированный IV как ошибка проектирования

Иногда разработчики берут IV = счётчик пользователей, timestamp или константу — «чтобы не хранить состояние». Это классическая ошибка: предсказуемый IV позволяет сравнивать префиксы двух сообщений (если IV фиксирован, одинаковые префиксы дают одинаковый первый блок keystream). Для CTR с фиксированным nonce и счётчиком, начинающимся с нуля при каждом шифровании, два сообщения с одинаковым началом дают `C1 ⊕ C2 = P1 ⊕ P2` на всём общем префиксе — мгновенная утечка. Всегда генерируйте IV случайно (`os.urandom(16)`) и передавайте вместе с шифротекстом.

## Практический чек-лист по режиму

При анализе неизвестного шифра:

1. **Длина кратна 16?** Нет → потоковый (CTR/OFB/CFB).
2. **Есть два шифротекста?** XOR → осмысленно? → reused keystream.
3. **Есть IV в токене?** Первые 16 байт неизменны при смене текста → IV.
4. **Есть тег?** Да → AEAD; нет → возможны флипы.
5. **Ключ и nonce известны из кода?** Воспроизведите keystream локально и сравните.

## Практическая реализация и сравнение на Python

```python
from Crypto.Cipher import AES
import os

key = os.urandom(16)
iv  = os.urandom(16)
pt  = b"A"*32 + b"secret-payload"

for mode, name in [(AES.MODE_CTR, "CTR"), (AES.MODE_OFB, "OFB"), (AES.MODE_CFB, "CFB")]:
    if mode == AES.MODE_CTR:
        c = AES.new(key, mode, nonce=iv[:8])
    else:
        c = AES.new(key, mode, iv=iv)
    ct = c.encrypt(pt)
    print(name, len(ct), ct[:16].hex())
# CTR/OFB/CFB дают длину == len(pt) (без padding)
```

Обратите внимание: в CTR pycryptodome по умолчанию использует `nonce` + внутренний счётчик; длина nonce настраивается. В CFB есть параметр `segment_size` (по умолчанию 8 бит — исторически!). Для блочного CFB указывайте `segment_size=128`.

## Как не застрять

- **Сравните два шифротекста.** Если `C1⊕C2` даёт осмысленный текст — reused keystream.
- **Ищите IV/nonce в протоколе.** Часто передаётся открыто рядом с шифротекстом.
- **Знаете один текст** — получите keystream: `O = C ⊕ P`, расшифруйте остальное.
- **Не знаете текст** — crib-dragging и частотный анализ (`xortool`).
- **Проверьте, есть ли MAC.** Если есть — флипы не пройдут.
- **Длина не кратна 16** — это признак потокового режима.
