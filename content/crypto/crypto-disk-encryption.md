## Вопрос, с которого всё начинается

Шифрование диска защищает данные «at rest»: если ноутбук украли, без пароля данные
недоступны. Данные шифруются режимом XTS — мы знаем, что он стоек. Тогда в чём
слабое звено? Вопрос: если у нас есть образ зашифрованного диска, как извлечь из
него содержимое?

Ответ: почти всегда ломают **не шифр**, а **KDF и управление ключами**. Разберём
это, создав настоящий LUKS-контейнер и разобрав его заголовок.

## Наш пример: образ disk.img

Пусть у нас есть файл-образ `disk.img`. Первое, что нужно, — понять, что это
вообще за формат. Смотрим на первые байты:

```
$ xxd disk.img | head -1
00000000: 4c55 4b53 babe 0001 6165 7300 0000 0000  LUKS....aes.....
```

Байты `4c55 4b53 babe` — это ASCII `LUKS` и магия `\xba\xbe`. Значит, перед нами
**LUKS** (Linux Unified Key Setup). Дальше `0001` — версия 1, `aes` — шифр.

## Шаг 1: что внутри LUKS

LUKS устроен так:

1. **LUKS header** — в начале раздела: магия, версия, набор шифров, UUID и
   **keyslots**.
2. **Keyslots** — 8 слотов (в LUKS1) или 32 (в LUKS2). Каждый слот содержит
   **зашифрованный мастер-ключ**.
3. **Мастер-ключ** — случайный ключ, которым реально шифруются данные (XTS).
4. Пароль пользователя **не** шифрует данные напрямую: он разворачивает keyslot, а
   из него достаётся мастер-ключ.

Схема такая:

```
пароль --PBKDF2/Argon2--> keyslot-key --расшифровка--> master-key --XTS--> данные
```

Вывод ключа из пароля: LUKS1 — **PBKDF2**, LUKS2 — **Argon2** (memory-hard).

## Шаг 2: разбираем заголовок

`cryptsetup luksDump` показывает всё нужное:

```
$ cryptsetup luksDump disk.img
Version:        1
Cipher name:    aes
Cipher mode:    xts-plain64
Hash spec:      sha256
Payload offset: 4096
MK bits:        256
UUID:           b182a0cc-fe20-4355-9bcf-3a0e83dddbf6

Key Slot 0: ENABLED
        Iterations:             8692858
        Salt:                   80 54 1c 0b ...
        Key material offset:    8
        AF stripes:             4000
Key Slot 1: DISABLED
...
```

Читаем: данные шифруются `aes-xts-plain64` с 256-битным мастер-ключом; активен
только keyslot 0; для вывода ключа используется PBKDF2 с **8 692 858 итерациями**.
Это число подобрано `cryptsetup` так, чтобы разворачивание занимало ~1–2 секунды
на данной машине — именно оно делает офлайн-подбор дорогим.

## Шаг 3: проверяем пароль

Проверить пароль, не монтируя том, можно через `--test-passphrase`:

```
$ echo -n "hunter2" | cryptsetup open --test-passphrase disk.img -
correct pass -> exit 0
$ echo -n "password123" | cryptsetup open --test-passphrase disk.img -
No key available with this passphrase.
wrong pass   -> exit 2
```

Правильный пароль развернул keyslot (код возврата 0), неправильный — нет. Это ровно
то, что делает атакующий в цикле: перебирает кандидатов, для каждого выводит ключ
из keyslot и проверяет, получился ли валидный мастер-ключ (у LUKS в keyslot есть
контрольная сумма/магия).

## Полный прогон от начала до конца

1. `file disk.img` / `xxd` — определяем формат (LUKS).
2. `cryptsetup luksDump disk.img` — версия, KDF, cipher, keyslots.
3. Извлекаем заголовок и keyslot в формат hashcat.
4. Подбираем словарём/масками (`hashcat -m 14600` для LUKS).
5. `cryptsetup open disk.img myvol` → вводим пароль.
6. `mount /dev/mapper/myvol /mnt` → читаем содержимое.

Важно: LUKS2 с Argon2 на GPU подбирается **очень медленно** (memory-hard) — это
осознанная защита; LUKS1 с PBKDF2 — заметно быстрее.

## Что мы теперь знаем

- Формат шифрованного образа определяют по **магии** (`LUKS\xba\xbe` — LUKS).
- Пароль защищает **keyslot** с зашифрованным мастер-ключом, а не сами данные.
- Данные шифрует мастер-ключ режимом XTS; XTS стоек, атака идёт на KDF.
- LUKS1 использует PBKDF2, LUKS2 — Argon2 (memory-hard).
- Проверить пароль можно через `cryptsetup open --test-passphrase`.
- Офлайн-подбор — это перебор кандидатов с проверкой разворачивания keyslot.

## BitLocker и VeraCrypt

**BitLocker** (Windows) шифрует том AES-XTS. Иерархия ключей: **FVEK** (шифрует
данные) ← **VMK** (защищает FVEK) ← **key protectors** (TPM, пароль, 48-значный
recovery key, смарт-карта). Если protector — пароль или recovery key, материал
извлекается и подбирается офлайн; если только TPM (без PIN), офлайн-подбор
невозможен без доступа к TPM или дампа памяти. Инструменты: `dislocker`,
`libbde`/`bdemount`.

**VeraCrypt** — форк TrueCrypt. Том имеет **header** (512 байт, иногда backup),
содержащий соль и зашифрованный мастер-ключ; пароль разворачивает header через KDF
(PBKDF2/RIPEMD-160 и др.), число итераций зависит от версии и **PIM** (Personal
Iterations Multiplier). Много алгоритмов (AES, Serpent, Twofish, каскады), скрытые
тома. Атака — извлечь header (`dd` первых 512 байт) и подбирать
(`hashcat -m 13721` для RIPEMD160).

## Утечки ключей вне криптографии

Криптография дискового шифрования стойкая, поэтому реальные компромиссы
происходят **вне** неё:

- **Hibernation и swap.** При гибернации содержимое RAM (включая ключи) пишется на
  диск, иногда незашифрованным; swap тоже может содержать фрагменты ключей.
- **Cold boot.** Ключи остаются в RAM после выключения ещё несколько секунд
  (дольше при охлаждении) — атакующий с физическим доступом читает модули.
- **DMA-атаки.** Через Thunderbolt/PCIe (PCILeech) можно читать память работающей
  системы и вытащить ключи; защита — IOMMU/VT-d.
- **Забытые копии.** Backup-образы, снапшоты VM, кэши часто **не** зашифрованы.

Вывод для пентеста: если перед вами зашифрованный диск с сильным паролем, не
тратьте силы на подбор — ищите ключ в памяти или незашифрованную копию.

## Контейнеры против полнодискового шифрования

Различайте сценарии. **FDE** (полнодисковое шифрование) шифрует весь раздел, ключ
разворачивается при загрузке; незашифрованными остаются загрузчик и метаданные, а
пока система работает — ключ в памяти (cold boot, DMA, hibernation).
**Контейнеры** (VeraCrypt-том, LUKS-файл) шифруют **весь** файл целиком, включая
заголовок; наружу виден только размер. На CTF обычно дают именно контейнер — один
файл удобно передать в условии.

## Справочные таблицы

| Формат | KDF | Режим данных | Магия |
|--------|-----|--------------|-------|
| LUKS1 | PBKDF2 | aes-xts-plain64 | `LUKS\xba\xbe` |
| LUKS2 | Argon2 | aes-xts-plain64 | `LUKS\xba\xbe` |
| BitLocker | PBKDF2/дисперсия | AES-XTS/CBC | `-FVE-FS-` |
| VeraCrypt | PBKDF2 (RIPEMD/SHA) | AES/Serpent/Twofish | нет |

| Инструмент | Назначение |
|-----------|-----------|
| cryptsetup | LUKS (open/dump) |
| dislocker | BitLocker |
| libbde/bdemount | BitLocker |
| veracrypt | VeraCrypt |
| hashcat | подбор всех форматов |

## Почему полнодисковое шифрование не спасает в запущенной системе

LUKS/BitLocker/VeraCrypt защищают данные **в покое**: пока диск выключен, содержимое — это шифротекст, и ключ защищён паролем (через KDF) и, возможно, TPM. Но как только система загрузилась, мастер-ключ лежит в оперативной памяти, и шифрование прозрачно: любой процесс с нужными правами читает файлы как обычно. Значит, «зашифрованный диск» не защищает от атак на живую систему.

Отсюда практические векторы: **cold boot** (вынести память и найти ключ), **DMA-атаки** (Thunderbolt/PCIe читают RAM напрямую), **evil maid** (подмена загрузчика или initramfs — например, фейковый экран ввода пароля), **hibernation-файл** (в нём ключ в открытом виде), дампы памяти и `/proc`. BitLocker с TPM без PIN особенно уязвим к evil maid: TPM отдаёт ключ при неизменённых измерениях загрузки, а атакующий может их подделать.

Практический вывод для аудита: смотрите не только на «включён ли LUKS», но и на конфигурацию — pre-boot-аутентификация, TPM+PIN, Secure Boot, отключение DMA, шифрование hibernation, отсутствие ключей в swap. Часто уязвимость не в шифре, а в том, что ключ утекает мимо него.

## Если не сработало

- **Пароль не подбирается.** LUKS использует PBKDF2/Argon2 с большим числом итераций — перебор медленный; цель — слабый пароль. Проверьте, что хеш извлечён из заголовка (`cryptsetup luksDump`, затем `hashcat -m 14600`).
- **BitLocker не открывается офлайн.** `dislocker`/`bdemount` работают, если есть recovery key или пароль; с TPM-only без ключа офлайн-путь закрыт.
- **VeraCrypt не берётся.** Разные версии заголовков и PIM; укажите PIM, если он нестандартный, иначе KDF посчитается неверно.
- **Данные не читаются даже после подбора.** Возможно, повреждён заголовок LUKS (есть backup в `luksHeaderBackup`) или это не тот keyslot.
- **Ключ вне криптографии.** Ищите swap, hibernation, core dumps, `/proc/kcore` — там ключ в открытом виде, подбор не нужен.

## Частые вопросы

**Защищает ли LUKS от злоумышленника с физическим доступом?** Только когда машина выключена. При включённой системе нужны доп. меры: pre-boot PIN, отключение DMA, Secure Boot, шифрование swap/hibernation.

**Почему TPM без PIN слабее?** TPM отдаёт ключ, если измерения загрузки совпали; атакующий с физическим доступом может подменить загрузчик, не меняя измеряемое, — classic evil maid.

**Что лучше — контейнер или полнодисковое шифрование?** FDE защищает всё, включая систему; контейнер проще и не мешает загрузке, но защищает только свои файлы. Для ноутбуков обычно FDE + отдельный контейнер для особо чувствительного.

## Куда дальше

Дисковое шифрование соединяет `crypto-xts-mode`, `crypto-kdf` и `crypto-real-world`.
Дальше ветвь идёт в `crypto-kerberos-crypto` — «инфраструктурную» криптографию
корпоративных сетей. А главное запомни: **XTS стоек; ломают KDF и управление
ключами, а ключ чаще всего лежит вне диска**.

## Где пригодится

- **CTF** — шифрованные образы дисков, LUKS/VeraCrypt-контейнеры.
- **Bug bounty** — оценка защиты данных at rest в продуктах.
- **Пентест** — криминалистика, работа с изъятыми дисками, оценка политик.
- **Работа** — внедрение и аудит дискового шифрования, управление ключами.
