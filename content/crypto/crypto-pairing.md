## Вопрос, с которого всё начинается

Обычное умножение на скаляр в ECC — аддитивное: `a·P` это «сложить `P` `a` раз». А что если нужна функция, которая **перемножает** скаляры — `e(aP, bQ) = e(P, Q)^{ab}`? Такая функция существует и называется **спариванием**. На ней держится целая ветвь криптографии: BLS-подписи, агрегация тысяч подписей в одну, zk-SNARK. Разберёмся, как это устроено и где ломается.

## Наш пример

Возьмём определение спаривания и проверим его главное свойство. Спаривание `e` отображает пару точек `(P ∈ G1, Q ∈ G2)` в элемент мультипликативной группы `GT`:

```
e(aP, bQ) = e(P, Q)^{ab}
```

Именно это позволяет проверять равенства без раскрытия скаляров. В `py_ecc` (кривая alt_bn128) билинейность проверяется так:

```python
from py_ecc.bn128 import G1, G2, pairing, multiply, curve_order
a, b = 7, 11
lhs = pairing(multiply(G2, b), multiply(G1, a))       # e(aG1, bG2)
rhs = pairing(G2, multiply(G1, (a*b) % curve_order))  # e((ab)G1, G2)
print(lhs == rhs)     # True — по билинейности
```

Обе стороны дают один и тот же элемент `GT`. Вопрос: зачем это нужно и какие кривые подходят?

## Шаг 1: три свойства спаривания

- **Билинейность:** `e(aP, bQ) = e(P, Q)^{ab}` для любых скаляров `a, b`.
- **Невырожденность:** `e(P, Q) ≠ 1` для ненулевых `P, Q`.
- **Вычислимость:** `e` считается эффективно (Miller's algorithm).

Интуиция: спаривание превращает «умножение на скаляр» в «возведение в степень» — аддитивную структуру ECC в мультипликативную структуру `GT`.

## Шаг 2: pairing-friendly кривые и embedding degree

Не любая кривая годится. Нужно, чтобы подгруппа порядка `r` из `E(F_q)` содержалась в `E(F_{q^k})`, и **embedding degree** `k` был мал, иначе спаривание невычислимо. Стандартные семейства:

- **BN-кривые** (Barreto-Naehrig) — `k = 12`, Ethereum (alt_bn128).
- **BLS-кривые** — `k = 12`, например BLS12-381 (Zcash, Ethereum 2).
- **MNT, KSS** — `k = 4..6`.

Важно: **secp256k1 не pairing-friendly** (у неё `k` огромно), а alt_bn128 и BLS12-381 — да.

## Шаг 3: Weil и Tate

- **Weil pairing** — спаривание над дивизорами, требует функций на кривой.
- **Tate pairing** — проще в реализации (Miller's algorithm), чаще используется. `e_T(P, Q)` считается через итеративный подсчёт `f_{r,P}(Q)` и финальное возведение в `(q^k − 1)/r`.

На практике почти всегда берут Tate (или его оптимизации — Ate, optimal Ate), потому что он быстрее.

## Шаг 4: BLS-подписи

BLS (Boneh-Lynn-Shacham) — подпись, которая «сжимается»:

- **KeyGen:** приватный `x`, публичный `X = x·G1`.
- **Sign:** `σ = x·H(m)` (хэш в точку `G2`).
- **Verify:** `e(G1, σ) == e(X, H(m))`.

Главное свойство — **агрегация**: `σ_agg = σ_1 + σ_2 + …`. Проверка одной парой спариваний:

```
e(G1, σ_agg) == e(X_1, H(m_1)) · e(X_2, H(m_2)) · …
```

Тысячи подписей сжимаются в одну точку. Поэтому BLS любят блокчейны (Ethereum consensus, Filecoin): подписи валидаторов агрегируются, экономя место в блоке.

## Шаг 5: атаки

- **MOV.** Если embedding degree `k` мал, ECDLP переносится в `GT` (мультипликативную группу `F_{q^k}`), где работает субэкспоненциальный index calculus. Для нормальных кривых `k` огромно и MOV неприменима; для слабых/самодельных — ломает (см. `crypto-ecdsa-advanced`).
- **Rogue-key (BLS).** Злоумышленник регистрирует ключ `X' = X_target − X_own`, и агрегат подписей подделывается. Защита — **proof of possession** (подпись на своём ключе) или коэффициенты `H(X_i)`.
- **Invalid-curve / small-subgroup** при проверке без валидации точки.
- **Подделка агрегата** при отсутствии привязки сообщений: сообщения должны хэшироваться вместе с ключом/сообщением, иначе «перестановка» подписей.

## Шаг 6: threshold, KZG, IBE

- **Threshold BLS.** Подпись собирается из `t` из `n` долей (комбинация с `crypto-shamir`).
- **KZG commitments.** `C = [f(s)]·G1`; проверка через `e(C − [f(z)]G1, G2) == e(π, [s]G2 − [z]G2)` — основа zk-SNARK (Groth16, PLONK).
- **IBE (Boneh-Franklin).** Публичный ключ = идентификатор (`email`), приватный выдаёт доверенный центр через спаривание.
- **Короткие подписи.** BLS-подпись — одна точка (48/96 байт), короче RSA/ECDSA.

KZG-проверка работает именно благодаря билинейности: обе стороны «умножаются» на один и тот же `(s − z)`, и `s` не раскрывается.

## Полный разбор: KZG-проверка

KZG (Kate-Zaverucha-Goldberg) — полиномиальный коммитмент на спариваниях, основа zk-SNARK. Доверенная установка даёт `[s]G1` и `[s]G2` для секретного `s` (его значение никому не раскрывается).

- **Commit:** для полинома `f` публикуется `C = [f(s)]G1`.
- **Open:** для точки `z` вычисляется `q(x) = (f(x) − f(z))/(x − z)`; proof `π = [q(s)]G1`.
- **Verify:** проверяем

```
e(C − [f(z)]G1, G2) == e(π, [s]G2 − [z]G2)
```

Билинейность делает проверку возможной, не раскрывая `s`: обе стороны «умножаются» на один и тот же `(s − z)`. Именно так доказывают корректность вычислений в Groth16/PLONK. В CTF «сломать KZG» обычно означает либо найти способ обойти проверку при известном `s` (скомпрометированная установка), либо эксплуатировать отсутствие валидации точки.

## Что мы теперь знаем

- Спаривание `e: G1×G2→GT` билинейно: `e(aP, bQ) = e(P, Q)^{ab}`.
- Нужны **pairing-friendly** кривые с малым embedding degree `k`.
- **BLS** — короткая подпись с агрегацией через спаривания.
- **MOV** ломает ECDLP при малом `k`.
- **Rogue-key** подделывает агрегат без proof of possession.
- KZG/zk-SNARK и threshold/IBE строятся на спариваниях.

## На что смотреть дальше

- **Пытаться применить спаривание к secp256k1** — она не pairing-friendly.
- **Игнорировать порядок аргументов** — тип групп у `e` важен.
- **Забыть про hash-to-curve** — наивный `hash·G` уязвим.
- **Нет proof of possession** — rogue-key ломает агрегацию.
- **Считать MOV всегда применимой** — только при малом `k`.
- **Путать `GT` и `G1`/`G2`** — это разные группы.

## Собираем BLS-агрегацию вручную

Проверим агрегацию на числах, чтобы увидеть, что «сжатие тысяч подписей в одну» — это буквально сложение точек. Возьмём `py_ecc` на alt_bn128:

```python
from py_ecc.bn128 import G1, G2, pairing, multiply, add, curve_order, FQ12

# три «валидатора» с ключами x1, x2, x3
keys = [5, 9, 13]
X = [multiply(G1, x) for x in keys]                 # публичные ключи
msgs = [b"block-1", b"block-2", b"block-3"]

def hash_to_G2(m):                                   # упрощённый hash-to-curve
    return multiply(G2, int.from_bytes(m, "big") % curve_order)

sigs = [multiply(hash_to_G2(m), x) for m, x in zip(msgs, keys)]
agg = sigs[0]
for s in sigs[1:]:
    agg = add(agg, s)                                # сумма подписей

# проверка одной парой произведений спариваний
lhs = pairing(G2, agg)
rhs = FQ12.one()
for Xk, m in zip(X, msgs):
    rhs = rhs * pairing(hash_to_G2(m), Xk)
print(lhs == rhs)                                    # True
```

Обратите внимание на порядок аргументов: в `py_ecc` `pairing(Q_in_G2, P_in_G1)`. Перестановка групп — классическая ошибка: `e` определена на `G1 × G2`, и аргументы **не взаимозаменяемы** без явной симметрии.

## Агрегация: что экономится

| Схема | Размер подписи | Проверка `n` подписей | Агрегация |
|-------|----------------|------------------------|-----------|
| ECDSA | ~64 байта каждая | `n` отдельных проверок | нет (нативно) |
| Schnorr | ~64 байта | линейна по `n` | только мультиподпись одного ключа |
| BLS | 48/96 байт | 2 спаривания + `n` умножений | **полная**, одна точка |

Именно поэтому BLS выбирают для консенсуса: в блоке Ethereum десятки тысяч аттестаций сжимаются в один агрегат, а проверка остаётся дешёвой.

## Rogue-key на числах

Покажем, почему нужен proof of possession. Злоумышленник хочет подделать агрегат под жертву с ключом `X_victim = x_v·G1`. Он выбирает свой «ключ» как `X_att = X_victim − X_own`, где `X_own = x_o·G1`. Тогда агрегат публичных ключей:

```
X_att + X_own = (X_victim − X_own) + X_own = X_victim
```

и подпись злоумышленника `σ = x_o·H(m)` проходит проверку как подпись жертвы. Защита — требовать **proof of possession**: при регистрации ключа злоумышленник обязан доказать знание `x_o` (подписать своим ключом), тогда поддельный `X_att` он подписать не сможет.

## Ограничения и подводные камни

- **MOV работает не всегда.** Даже pairing-friendly кривая безопасна, если `k` достаточно велико, а `r` — большое простое. MOV опасна только для самодельных кривых с малым `k` (supersingular, `k=2`).
- **hash-to-curve обязателен.** Наивное `hash(m)·G` даёт предсказуемую точку и позволяет атаку через связь сообщений; нужен полноценный hash-to-curve (RFC 9380).
- **Валидация точек.** Проверка `e(G1,σ)==e(X,H(m))` без проверки, что `X ∈ G1`, `σ ∈ G2` и точки не в малой подгруппе, открывает invalid-curve/small-subgroup атаки.
- **Домен сообщений.** Агрегированная проверка должна привязывать каждое сообщение к своему ключу (hash `(pk||m)`), иначе перестановка подписей между сообщениями даёт подделку.

## Таблица: Weil, Tate и ate — чем отличаются

Все три — билинейные спаривания на эллиптических кривых, но вычислительно и по свойствам они различаются. В реализации чаще всего встречается Tate/ate, потому что он дешевле.

| Спаривание | Область | Цена | Где используется |
|------------|---------|------|------------------|
| Weil | `E[n] × E[n] → μ_n` | дороже (две функции Миллера) | учебники, симметричные протоколы |
| Tate | `E(F_q)[n] × E(F_{q^k})/nE → μ_n` | дешевле | BLS, KZG, практические схемы |
| ate | `G2 × G1 → μ_n` | самый дешёвый при малом `k` | BN/BLS12-кривые, zk-SNARK |
| optimal ate | `G2 × G1 → μ_n` | оптимизированный ate | стандарт для pairing-friendly кривых |

Для BLS-подписи `e: G1 × G2 → GT` важна именно билинейность: `e(aP, bQ) = e(P, Q)^{ab}`. Это позволяет проверять агрегированную подпись без раскрытия ключей.

## Рабочий пример: проверка BLS-подписи в Sage

Соберём маленькую pairing-friendly кривую и проверим подпись `σ = sk·H(m)` публичным ключом `pk = sk·G`.

```python
# Маленькая BN-подобная кривая (учебная)
p = 631; r = 5
E = EllipticCurve(GF(p), [1, 0])
G = E(0, 1)                      # генератор G1
assert G.order() == r
# Спаривание Weil на подгруппе порядка r
def H(m):                        # хэш в точку (детерминированно для примера)
    return E.lift_x(ZZ(hash(m)) % p)
sk = 3
pk = sk * G
m = "hello"
sig = sk * H(m)
# Проверка: e(G, sig) == e(pk, H(m))
lhs = G.weil_pairing(sig, r)
rhs = pk.weil_pairing(H(m), r)
print("valid:", lhs == rhs)      # True
```

Билинейность даёт равенство `e(G, sk·H(m)) = e(sk·G, H(m))`. Если проверка `lhs == rhs` проходит — подпись верна. На реальных кривых вместо `weil_pairing` используют optimized ate из библиотек (blst, mcl, py_ecc).

## Ограничения и типичные ошибки

- **Путать порядок аргументов.** Для ate-спаривания `G1 × G2 → GT`, а для Weil порядок важен; перестановка даёт другой результат или ошибку.
- **Не проверять, что точки в правильной подгруппе.** Атака с малой подгруппой (`crypto-invalid-curve`) ломает протокол, если валидация пропущена.
- **Считать, что спаривание «бесплатно».** Для 128-битной стойкости нужна кривая с большим полем — цена проверки BLS на порядки выше ECDSA.
- **Забыть про `k`.** Если embedding degree велик, спаривание невозможно вычислить эффективно — проверьте, что кривая специально pairing-friendly.
- **Ошибка в хэшировании в точку.** Для BLS нужен hash-to-curve (RFC 9380); простое `lift_x` не даёт равномерного распределения и открывает атаки.
