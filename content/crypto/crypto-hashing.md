## Вопрос, с которого всё начинается

Мы разобрали шифры, которые можно «повернуть обратно» ключом. Но есть функции, у которых ключа нет вовсе, а обратного преобразования не существует. Как тогда на них строят проверку паролей и целостности? И почему «захешировать пароль» — это ещё не значит «защитить»?

Разберём на конкретной уязвимой схеме, которую регулярно находят в веб-приложениях.

## Наш пример

Сервер выдаёт cookie вида `auth = md5(SECRET + username)`, где `SECRET` — неизвестный серверный ключ. При входе он проверяет, что `md5(SECRET + "user")` совпадает с cookie. Вопрос: можно ли, зная только `md5(SECRET + "user")`, подделать cookie для другого имени — например, `admin`?

## Шаг 1: хэш — односторонняя функция

**Хэш-функция** берёт данные любой длины и выдаёт значение фиксированной длины (дайджест). Свойства:

- **односторонность** — по дайджесту нельзя восстановить вход;
- **детерминизм** — одинаковый вход всегда даёт одинаковый выход;
- **лавинность** — малейшее изменение входа меняет весь дайджест;
- **устойчивость к коллизиям** — трудно найти два разных входа с одним дайджестом.

Посчитаем MD5 от `password`:

```bash
$ echo -n 'password' | md5sum
5f4dcc3b5aa765d61d8327deb882cf99  -
```

Обратно из `5f4dcc3b5aa765d61d8327deb882cf99` получить `password` нельзя — но можно угадать.

## Шаг 2: определяем тип хэша по длине

Алфавит у хэша всегда `0-9a-f` (hex), поэтому различают их по **длине**:

| Хэш | Длина (hex) | Байт |
|---|---|---|
| MD5 | 32 | 16 |
| SHA-1 | 40 | 20 |
| SHA-256 | 64 | 32 |
| SHA-512 | 128 | 64 |

Увидел 32 символа — почти наверняка MD5. Это первая зацепка в любой задаче с хэшем. Иногда рядом с хэшем дают соль (`md5(salt + password)`) или формат вроде `sha256$<salt>$<hash>` — тогда подбор идёт уже по схеме «соль + слово», и словарь надо модифицировать под неё, а не гнать как есть.

## Шаг 3: подбор по словарю

Раз «расшифровать» нельзя, хэш **подбирают**: считают дайджесты популярных слов и сравнивают. В учебном масштабе это делается на Python:

```python
import hashlib
h = "5f4dcc3b5aa765d61d8327deb882cf99"
for w in ["123456", "password", "admin", "letmein", "qwerty"]:
    if hashlib.md5(w.encode()).hexdigest() == h:
        print("cracked:", w)   # cracked: password
```

Для реальных задач берут **hashcat** или **john** и словарь вроде `rockyou.txt`. Признак слабости: пароль захеширован **один раз** без соли. Соль (случайная добавка к паролю) убивает словарный подбор — именно поэтому в современных системах используют bcrypt/scrypt/Argon2 с солью и замедлением.

## Шаг 4: атака удлинением сообщения (length-extension)

Вернёмся к cookie `md5(SECRET + user)`. Почему это плохо? Потому что MD5 (и SHA-1, SHA-256) построены по схеме **Merkle–Damgård**: сообщение разбивается на блоки, и хэш считается **итеративно**, передавая внутреннее состояние из блока в блок. Итоговый дайджест — это просто финальное состояние.

Отсюда атака: если знать `H(SECRET + user)` и **длину** `SECRET`, можно **продолжить** вычисление с этого состояния, добавив свои данные, и получить корректный хэш для `SECRET + user + padding + extra` — не зная самого `SECRET`.

Идея в коде: восстанавливаем внутреннее состояние из известного дайджеста и «докармливаем» ему новые блоки.

```python
# state = дайджест, разобранный на 4 слова по 4 байта
state = [struct.unpack('<I', bytes.fromhex(orig_hash[i:i+8]))[0] for i in range(0, 32, 8)]
glue = md5_pad(orig_len)              # padding, который "съел" сервер
data = append + md5_pad(orig_len + len(glue) + len(append))
for i in range(0, len(data), 64):
    state = md5_compress(state, data[i:i+64])
forged = ''.join(struct.pack('<I', x).hex() for x in state)
```

Прогоняем с `SECRET = "SECRETKEY"`, `user = "user"` (длина секрета 9):

```text
real   md5(SECRET||"user")            = 4a58750de5c5d148b6b19b4ae6a5daee
glue   (padding)                      = 80000000000000000000000000000000...6800000000000000
forged cookie (байты)                 = user<glue>admin
forged md5                            = 59d24fbf647a8e546d83d9f97bf5070c
```

Проверка: `hashlib.md5(SECRET + newmsg).hexdigest()` даёт ровно `59d24fbf647a8e546d83d9f97bf5070c` — **подделка сходится**. Мы добавили `admin` в конец сообщения, не зная секрета. Знание длины `SECRET` обязательно: без неё не построить правильный padding.

## Шаг 5: как защититься — HMAC

Правильная схема проверки целостности — **HMAC**, который оборачивает хэш так, что length-extension неприменим:

```
HMAC(K, m) = H((K ^ opad) || H((K ^ ipad) || m))
```

Здесь секрет стоит и в начале, и в конце, а внешний хэш «запечатывает» результат. Для проверки MAC всегда используй `hmac.compare_digest`, а не `==` (чтобы избежать атак по времени). Про HMAC подробно — в уроке `crypto-hmac`.

Коллизии — отдельная история: для MD5 и SHA-1 они **найдены**, поэтому подпись, построенная на «найти два файла с одинаковым хэшем», ломается. SHA-256 и SHA-3 на сегодня устойчивы.

## bcrypt, scrypt, Argon2: почему они медленные

Быстрые хэши (MD5, SHA-256) хороши для целостности, но **катастрофичны для паролей**: видеокарта считает миллиарды MD5 в секунду. Поэтому для паролей придумали «медленные» функции:

- **bcrypt** — намеренно медленный, с солью внутри;
- **scrypt** — медленный и требует много памяти, что мешает GPU/ASIC-подбору;
- **Argon2** — победитель конкурса Password Hashing Competition, регулирует время, память и параллелизм.

Проверить, чем захеширован пароль, можно по формату строки: `$2b$12$…` — bcrypt, `$argon2id$…` — Argon2. Признак правильной системы: соль уникальна для каждого пользователя и встроена в хэш, поэтому радужные таблицы бесполезны.

```bash
$ hashid '$2b$12$R9h/cIPz0gi.URNNX3kh2OPST9/PgBkqquzi.Ss7KIUgO2t0jWMUW'
# [+] bcrypt
```

## Коллизии: когда находят два разных входа

Отдельный класс атак — не восстановление входа, а **поиск коллизии**: двух разных сообщений с одинаковым хэшем. Для MD5 и SHA-1 такие пары **реально построены** (атаки chosen-prefix). Последствие: если целостность файла проверяется по MD5, злоумышленник может подменить файл, сохранив тот же дайджест. Именно поэтому подписи сертификатов давно ушли на SHA-256.

Практический вывод для CTF: «одинаковый MD5» двух файлов — это не совпадение, а спланированная коллизия; SHA-256 и SHA-3 на сегодня устойчивы. Если задача просит подписать два разных сообщения одним хэшем — ищи именно коллизию, а не подбор.

## Что мы теперь знаем

- Хэш односторонний: «расшифровать» нельзя, можно подобрать.
- Тип хэша определяется по длине (32/40/64/128 hex).
- Без соли хэши паролей ломаются словарём; bcrypt/Argon2 это исправляют.
- Merkle–Damgård-хэши уязвимы к length-extension при схеме `H(secret || msg)`.
- HMAC устраняет эту уязвимость; для сравнения MAC нужен `compare_digest`.
- Коллизии MD5/SHA-1 реальны; для новых систем — SHA-256/SHA-3.

## Куда дальше

Мы разобрали односторонние функции и их главную атаку. В следующем уроке **crypto-stream-ciphers** мы вернёмся к потоковым шифрам — RC4 и LFSR — и увидим, как слабости генератора keystream приводят к восстановлению секрета. - **CTF** — length-extension, коллизии, подбор хэшей паролей.
- **Веб-пентест** — подделка подписанных cookies и токенов, построенных на `H(secret||data)`.

- **Разработка** — правильный выбор хэша и HMAC вместо самодельных схем.
