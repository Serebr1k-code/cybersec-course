## Вопрос, с которого всё начинается

В задаче даны не один, а несколько публичных ключей. Часто это подсказка: ключи сгенерированы одним слабым генератором, и у них есть **общая часть**. Тогда один `gcd` или одна комбинация шифротекстов ломает сразу всё. Разберём два классических случая — общий простой множитель и общий модуль — и посмотрим, как они ломаются на реальных числах.

## Наш пример

Сгенерируем два модуля, которые случайно делят один простой множитель `pa`:

```python
from sympy import nextprime
from math import gcd
pa = nextprime(2**512); qa = nextprime(2**511); qb = nextprime(2**510)
n1 = pa*qa
n2 = pa*qb
print("shared:", gcd(n1, n2) == pa, "pa bits:", pa.bit_length())
```

```
shared: True pa bits: 513
```

Вопрос: как понять, что у двух ключей общий множитель, и что это даёт?

## Шаг 1: shared primes — один gcd

Если `n1 = p·q1` и `n2 = p·q2` с общим простым `p`, то `p = gcd(n1, n2)`. Один вызов — и оба ключа сломаны: `q1 = n1/p`, `q2 = n2/p`, дальше стандартное восстановление `d`.

```python
import itertools
for n1, n2 in itertools.combinations(all_moduli, 2):
    g = gcd(n1, n2)
    if 1 < g < n1:
        print("shared prime!", g)
```

**Всегда проверяйте попарные `gcd` всех модулей** — это бесплатно и часто срабатывает. Реальные инциденты: плохой RNG у встроенных устройств генерировал ключи с общими множителями, и исследователи ломали тысячи сертификатов.

## Шаг 2: common modulus — один n, разные e

Другой сценарий: одно сообщение `m` зашифровано **одним и тем же `n`**, но разными `e1, e2`, причём `gcd(e1, e2) = 1`:

```
c1 = m^e1 mod n
c2 = m^e2 mod n
```

По тождеству Безу найдутся `a, b` с `a·e1 + b·e2 = 1`. Тогда `m = c1^a · c2^b mod n`. Для `e1 = 3, e2 = 5` подходят `a = 2, b = −1`:

```python
n = pa*qa; m = 0x1234567890abcdef
c1 = pow(m, 3, n); c2 = pow(m, 5, n)
rec = (pow(c1, 2, n) * pow(pow(c2, -1, n), 1, n)) % n
print("recovered:", rec == m)
```

```
recovered: True
```

Сообщение восстановлено без знания `φ`. Если `gcd(e1, e2) = g > 1`, получаем `m^g` — дальше корень `g`-й степени или Coppersmith.

## Шаг 3: атака Ферма для близких p и q

Если `p` и `q` близки, `n = a² − b² = (a−b)(a+b)`, где `a = (p+q)/2`, `b = (p−q)/2`. Перебираем `a` от `⌈√n⌉` вверх, пока `a² − n` не станет полным квадратом:

```python
from sympy import integer_nthroot
def fermat(n, limit=10**7):
    a = integer_nthroot(n, 2)[0] + 1
    for _ in range(limit):
        b2 = a*a - n; b = integer_nthroot(b2, 2)[0]
        if b*b == b2: return a - b, a + b
        a += 1
```

**Признак:** `p` и `q` сгенерированы подряд — `n` почти квадрат. Проверять Ферма дёшево, делайте это всегда, когда `n` не поддаётся другим атакам.

Если `|p − q|` велик, но не огромен, обычный Ферма медленный — тогда помогает **обобщённый Ферма**: ищем `a` с `a² − n = b²·k` для малых `k`, или применяем метод Харта с быстрой сходимостью. Для `|p − q|` в пределах нескольких миллионов обычный Ферма всё ещё работает за секунды.

## Шаг 4: мультипростой RSA и его слабости

`n = p1·p2·…·pk` с `k > 2`. Это ускоряет расшифрование (через CRT), но **снижает стойкость**. При фиксированном размере `n` увеличение `k` уменьшает каждый `p_i`, а факторизация методом ECM зависит от размера наименьшего множителя. Если `k` велик (например, десять простых по 100 бит), ECM находит множители за реальное время. Плюс при утечке одного `p_i` (общего с другим ключом) снова работает shared primes.

**Признак:** `n` «круглого» размера, но факторизация распадается на много частей, либо задача прямо говорит «multi-prime».

## Шаг 5: порядок действий

from math import gcd

# 1. shared primes — всегда первым, дёшево
for a, b in itertools.combinations(all_moduli, 2):
    g = gcd(a, b)
    if 1 < g < a: print("shared prime:", g)

# 2. common modulus — один n, разные e

## Шаг 6: shared primes на большом парке

Реальный инцидент: устройства с плохим RNG генерировали RSA-ключи, у которых попарный `gcd` не равен 1. Собрав публичные ключи (SSH, TLS) и посчитав все `gcd`, исследователи ломали тысячи ключей. Скрипт масштабируется на любой парк:

```python
from math import gcd
import itertools, glob
moduli = [int(open(f).read().strip()) for f in glob.glob("keys/*.n")]
vuln = 0
for a, b in itertools.combinations(moduli, 2):
    g = gcd(a, b)
    if 1 < g < a:
        vuln += 1
        print("vuln key, shared prime:", g)
print("total vulnerable:", vuln)
```

Важно: проверять нужно **попарно все** модули, а не только «соседние». Два ключа могут быть сгенерированы в разное время, но с общим простым, если RNG переиспользовал состояние. Это одна из самых дешёвых и результативных атак на больших наборах ключей.

## Что мы теперь знаем

- **Shared primes:** общий множитель двух `n` находится через `gcd(n1, n2)`.
- **Common modulus:** одно сообщение с одним `n` и разными `e` восстанавливается через egcd.
- При `gcd(e1, e2) = g > 1` получаем `m^g` — нужен корень или Coppersmith.
- **Ферма** ломает `n` с близкими `p, q`.
- **Мультипростой** RSA слабеет при большом `k` (маленькие `p_i`).
- Первый дешёвый шаг — попарные `gcd` всех модулей.

## На что смотреть дальше

- **Не проверять gcd всех `n`** — самая частая недоработка.
- **Считать Ферма бесполезным для больших `n`** — он работает при близких `p, q`.
- **Путать common modulus и shared primes** — разные условия и разные атаки.
- **Забыть про случай `gcd(e1,e2) > 1`** — тогда нужен корень `g`-й степени.
- **Не собирать все параметры** из условия — теряются ключи к атаке.
- **Игнорировать multi-prime** при `n` с маленькими множителями.

## Куда дальше

Мы научились ломать RSA по нескольким ключам. Дальше — атаки на **малую экспоненту** `e`: когда сообщение короткое или отправлено нескольким получателям. В уроке **crypto-rsa-small-e-hastad** мы применим CRT и извлечём корень. А пока главное: **соберите все `n` и посчитайте `gcd` — общий множитель ломает ключи одним вызовом.**

## Где пригодится

- **CTF (hard)** — задачи с несколькими ключами; самая частая «RSA-связка».
- **Bug bounty** — аудит генерации ключей, слабый RNG у нескольких сертификатов.
- **Пентест инфраструктуры** — сбор публичных ключей (SSH/TLS) и поиск общих множителей.
- **Работа** — расследование инцидентов с утечкой ключей.
- **Крипто-разработка** — почему нельзя повторно использовать `p` между ключами.
