## Зачем это нужно

Диск шифруется посекторно, и в отличие от сетевого трафика, здесь нельзя позволить себе случайный IV на каждый блок: нужна возможность читать/писать **отдельные сектора в произвольном порядке**, не расшифровывая весь диск. ECB для этого формально подходит (позиционное шифрование), но катастрофически небезопасен: одинаковые сектора дают одинаковый шифротекст, и по диску видны паттерны. CBC требует цепочки и ломает произвольный доступ. Решение — **tweakable-режим XTS** (XEX-based Tweaked-codebook mode with ciphertext Stealing), стандарт IEEE 1619 и де-факто стандарт для LUKS, BitLocker, VeraCrypt и FileVault.

Ключевая идея: вместо случайного IV используется **tweak** — открытое значение, привязанное к позиции (номер сектора и смещение внутри сектора). Разные позиции → разное шифрование, даже при одинаковом открытом тексте и одном ключе. При этом каждый сектор независим, что даёт произвольный доступ.

## Tweakable-блочные шифры и конструкция XEX

Tweakable-блочный шифр — это `E(K, T, P)`, где `T` — публичный tweak. XTS строит его из обычного блочного шифра через XEX (XOR-Encrypt-XOR):

```
C = E_K(P ⊕ T) ⊕ T
```

где `T = E_{K1}(i) · α^j` — «затравка» из номера сектора `i` и позиции блока `j` внутри сектора, а `α` — примитивный элемент `GF(2^128)` (умножение на `x` в поле). XTS использует **два ключа**: `K1` для шифрования tweak и `K2` (данные) для самих блоков. Это важно: если использовать один ключ на оба, теряется часть стойкости.

```python
# концептуальная схема XTS для сектора
def xts_encrypt_sector(data, key1, key2, sector_num):
    tweak = aes_encrypt(key1, sector_num.to_bytes(16, 'little'))
    out = b''
    for j in range(0, len(data), 16):
        block = data[j:j+16]
        t = gf_mul_alpha_pow(tweak, j // 16)
        c = aes_encrypt(key2, xor(block, t))
        out += xor(c, t)
    return out
```

## Роль tweak и ciphertext stealing

Сектор диска — не всегда кратен 16 байтам (например, 520 или 528 байт в некоторых SSD). XTS решает это **ciphertext stealing (CTS)**: последний неполный блок шифруется так, что размер шифротекста равен размеру открытого текста, без padding. Алгоритм:

1. Шифруем полные блоки обычным XEX.
2. Для последних двух блоков (предпоследний полный `P_{m-1}` и последний неполный `P_m`) применяем CTS: берём первые `len(P_m)` байт `C_{m-1}` как хвост, а оставшиеся байты дополняем байтами `C_m`.

Это позволяет шифровать данные произвольной длины с сохранением длины — критично для дисков и файловых систем.

## Инструменты и команды

- **cryptsetup** — создание/открытие LUKS-томов с `--cipher aes-xts-plain64`.
- **OpenSSL** — режим `aes-256-xts` (в некоторых сборках) с указанием IV.
- **Python `cryptography`** — `modes.XTS(tweak)`.
- **`cryptsetup benchmark`** — замер скорости.

Пример создания XTS-тома:

```bash
cryptsetup luksFormat --cipher aes-xts-plain64 --key-size 512 --hash sha256 disk.img
cryptsetup luksDump disk.img | head -20
```

В дампе видно `cipher: aes-xts-plain64`, `key size: 512` (это два 256-битных ключа XTS).

## Разобранный пример: почему ECB виден на диске, а XTS нет

Представьте два сектора, содержащих одни нули. В ECB `E_K(0)` одинаков для обоих секторов — по диску видны длинные одинаковые области. В XTS каждый сектор имеет свой tweak (номер сектора), поэтому шифротексты различаются.

```python
import os
from cryptography.hazmat.primitives.ciphers import Cipher, algorithms, modes

key = os.urandom(32)
zeros = b'\x00' * 16
# ECB: одинаковый вход → одинаковый выход
c = Cipher(algorithms.AES(key), modes.ECB()).encryptor()
print(c.update(zeros) == c.update(zeros))   # True — катастрофа

# XTS: разные tweak → разный выход
def xts_enc(block, tweak):
    enc = Cipher(algorithms.AES(key), modes.XTS(tweak)).encryptor()
    return enc.update(block) + enc.finalize()
print(xts_enc(zeros, b'\x01'*16) == xts_enc(zeros, b'\x02'*16))  # False
```

Вывод:

```
True
False
```

Именно поэтому XTS применяется для дисков, а ECB — нет.

## Атаки: переиспользование tweak/ключа

XTS **детерминирован**: одинаковый сектор с одинаковым tweak даёт одинаковый шифротекст. Это осознанный компромисс — защита от «перестановки секторов» слабее, чем у случайного IV. Из этого следуют атаки:

- **Cut-and-paste секторов**: атакующий может скопировать сектор с одной позиции на другую, и если tweak при этом не изменится (ошибка реализации), получится валидная копия.
- **Переиспользование tweak** (один и тот же номер сектора на разных областях) даёт ECB-подобную утечку.
- **Одноразовый ключ**: если `K1 = K2`, XEX теряет часть стойкости; некоторые реализации ошибочно так делают.
- **Атака на малый tweak-space**: если номеров секторов мало и они повторяются, растёт вероятность коллизий.

На CTF это выглядит как задача: «дан образ диска с XTS, два сектора совпадают → восстанови структуру». Проверяйте, совпадают ли tweak и ключи.

## XTS в реальных системах: LUKS, BitLocker, FileVault

Понимание XTS нужно не в вакууме, а потому что именно он стоит за дисковым шифрованием в реальных продуктах. Разберём, как его применяют.

**LUKS (Linux Unified Key Setup)** — стандарт для шифрования разделов Linux. По умолчанию LUKS1 использует `aes-xts-plain64` с 256-битным или 512-битным ключом. «plain64» означает, что tweak — это 64-битный little-endian номер сектора, дополненный нулями до 128 бит. Ключевой материал хранится в заголовке LUKS, зашифрованном мастер-ключом, который, в свою очередь, защищён паролем через PBKDF2 или Argon2. То есть XTS шифрует данные, а KDF защищает ключ XTS. Важно: заголовок LUKS содержит «keyslots» — именно их атакуют офлайн-подбором, а не сами данные.

**BitLocker (Windows)** — использует AES в режиме XTS (в новых версиях; в старых — CBC с Elephant diffuser, от которого отказались). Tweak строится из номера сектора и «diffuser», который был убран после анализа. Ключи могут храниться в TPM, что делает офлайн-атаку без дампа памяти или TPM-обхода невыполнимой.

**FileVault 2 (macOS)** — также XTS с ключами, разворачиваемыми через TPM-подобный чип или пароль пользователя. Заголовок содержит завернутый ключ.

**VeraCrypt** — поддерживает XTS как основной режим; тома имеют заголовок с солью и зашифрованным мастер-ключом, что делает VeraCrypt-тома мишенью для офлайн-подбора и для атак на слабые пароли.

Практический вывод для пентеста: если у вас есть образ шифрованного диска, вы не «ломаете XTS» — вы подбираете пароль к заголовку (LUKS/VeraCrypt) или пытаетесь извлечь ключ из TPM/памяти (BitLocker/FileVault). XTS сама по себе криптостойка; слабое звено — KDF и управление ключами.

## Производительность и аппаратное ускорение

XTS проектировался под аппаратную реализацию: XEX сводится к одному вызову блочного шифра на блок плюс дешёвые XOR и умножение на `α`. Это позволяет использовать AES-NI и достигать гигабайт в секунду, что критично для шифрования всего диска. Параллелизм есть внутри сектора (блоки независимы при известном tweak), но сектора обрабатываются независимо — поэтому XTS хорошо масштабируется на многоядерных системах. Для сравнения: CBC последователен и плохо параллелится, а GCM быстр, но требует уникального nonce, которого на диске нет. Именно сочетание «скорость + произвольный доступ + детерминизм» сделало XTS стандартом.

## Частые ошибки и подводные камни

- **Использовать ECB для диска** — классическая ошибка, приводящая к видимым паттернам.
- **Один ключ вместо двух** — XTS требует `K1 ≠ K2`; некоторые самодельные реализации берут один.
- **Неверный порядок байт tweak** — номер сектора должен быть little-endian в XTS-«plain64».
- **Забыть про CTS** — данные, не кратные 16, будут либо дополнены (сломает длину), либо обрезаны.
- **Переиспользование tweak** между разделами/файлами — теряется уникальность позиции.
- **Считать XTS аутентифицированным** — это не AEAD: целостность не защищена, нужен отдельный MAC (например, dm-verity).

## Контрмеры и защита

- Всегда используйте **два независимых ключа** XTS (cryptsetup делает это автоматически при key-size 512).
- Tweak = номер сектора в little-endian; не переиспользуйте номера.
- Для целостности добавляйте аутентификацию (dm-verity, подпись) — XTS её не даёт.
- Не храните ключ рядом с диском; используйте TPM/HSM для разворачивания.

## Что дальше / решение

XTS — инженерная надстройка над блочным шифром. Дальше логично: `crypto-disk-encryption` (заголовки LUKS/BitLocker), `crypto-aes-modes` (сравнение со «своими» режимами), `crypto-integral-cryptanalysis` (атаки на сам шифр). Для CTF держите под рукой `cryptsetup` и знание, что XTS не аутентифицирован.
