## Вопрос, с которого всё начинается

Диск нужно зашифровать так, чтобы можно было читать и писать **отдельные сектора
в произвольном порядке**, не расшифровывая весь диск. ECB формально это
позволяет — каждый блок шифруется независимо. Но возьмём два сектора, забитых
нулями, и зашифруем их. Что мы увидим на диске? Одинаковые байты — то есть
диск превращается в карту, по которой видно, где пусто, а где данные. Вопрос:
какой режим даёт произвольный доступ, **но при этом** не выдаёт паттерны?

Ответ — **XTS**. Ниже мы сравним его с ECB на реальном примере и разберём, как
он это делает.

## Наш пример: два пустых сектора

Возьмём ключ и один блок нулей, а затем два «сектора» — с номерами 1 и 2.
Зашифруем блок в ECB и в XTS и посмотрим на байты.

```
ECB(0)==ECB(0): True -> f29000b62a499fd0a9f39a6add2e7780
XTS(0,sector1): a8ce33a288a211258599d867beceaf25
XTS(0,sector2): 17b6f9fb9d33c286e4415167546ca494
XTS(0,s1)==XTS(0,s2): False
XTS(0,s1)==XTS(0,s1): True
```

Разберём каждую строку. В ECB одинаковый вход дал одинаковый выход — на диске
это «дырка», по которой всё видно. В XTS один и тот же блок нулей в **разных**
секторах дал **разный** шифротекст — паттерн исчез. И при этом тот же сектор
зашифровался детерминированно (последняя строка `True`) — это нужно, чтобы диск
можно было перечитать.

## Шаг 1: почему ECB не годится, а CBC тоже не подходит

ECB шифрует каждый блок **независимо и одинаково**: `C = E_K(P)`. Отсюда две
беды: одинаковые блоки дают одинаковый шифротекст (видна структура), и блоки
можно **переставлять** местами. Простой пример — картинка «пингвин Tux»,
зашифрованная ECB: силуэт остаётся узнаваемым, потому что однотонные области
превращаются в одинаковые пятна.

CBC решает проблему паттернов, но вводит **цепочку**: каждый блок зависит от
предыдущего. Значит, чтобы прочитать сектор в середине диска, придётся
расшифровать всё до него. Произвольный доступ пропадает. Нужен режим, который
уникализирует шифрование **по позиции**, не связывая блоки.

## Шаг 2: tweak — позиция вместо случайного IV

Идея XTS: вместо случайного IV (который надо где-то хранить и который ломает
детерминизм) использовать **tweak** — открытое значение, привязанное к позиции
данных: номер сектора и номер блока внутри сектора. Tweak не секретен, но он
разный для разных позиций, поэтому одинаковые блоки в разных местах шифруются
по-разному.

Технически tweakable-шифрование строится через конструкцию **XEX** (XOR-Encrypt-
XOR):

```
C = E_K(P ⊕ T) ⊕ T
```

Здесь `T` — «затравка», вычисляемая из номера сектора. В XTS она получается так:
сначала номер сектора шифруется отдельным ключом, а затем для каждого
следующего блока сектора умножается на `α` в `GF(2^128)` (умножение на `x` в
поле). Это дёшево и даёт разным блокам разные `T`.

## Шаг 3: два ключа и ciphertext stealing

Два важных инженерных решения XTS.

**Два ключа.** XTS использует `K1` для вычисления tweak и `K2` для шифрования
данных. Если взять один ключ на оба, часть стойкости теряется. Поэтому
`cryptsetup` при `--key-size 512` берёт два 256-битных ключа.

**Ciphertext stealing (CTS).** Сектор диска не всегда кратен 16 байтам (бывают
520 или 528 байт). Обычный блочный режим потребовал бы padding, который изменил
бы длину, — а диск обязан сохранять размер. CTS решает это: последний неполный
блок шифруется так, что **размер шифротекста равен размеру открытого текста**.
Проверим:

```
XTS len: 40 (вход 40 )
```

Мы зашифровали 40 байт (два с половиной блока) и получили ровно 40 байт — без
padding'а.

## Полный прогон от начала до конца

Собираем всё вместе в Python (библиотека `cryptography`, режим `modes.XTS`):

```python
from cryptography.hazmat.primitives.ciphers import Cipher, algorithms, modes
key = bytes.fromhex("000102...1e1f")
def xts(block, tweak):
    enc = Cipher(algorithms.AES(key), modes.XTS(tweak)).encryptor()
    return enc.update(block) + enc.finalize()
t1 = (1).to_bytes(16, "little")      # tweak = номер сектора (little-endian)
t2 = (2).to_bytes(16, "little")
```

Именно этот код дал вывод в начале урока: ECB выдал одинаковые байты, XTS —
разные для разных секторов и одинаковые для одного и того же. Так работает
шифрование диска в LUKS, BitLocker, FileVault и VeraCrypt.

## Что мы теперь знаем

- ECB на диске виден: одинаковые блоки → одинаковый шифротекст; CBC ломает
  произвольный доступ.
- XTS уникализирует шифрование по **позиции** через tweak (номер сектора), а не
  через случайный IV.
- Внутри XTS — конструкция XEX: `C = E_K(P ⊕ T) ⊕ T`.
- Используются два ключа: `K1` (tweak) и `K2` (данные).
- Ciphertext stealing сохраняет длину для данных, не кратных 16 байтам.
- XTS **детерминирован** и **не аутентифицирован**: это осознанный компромисс
  ради произвольного доступа и скорости.

## Атаки: переиспользование tweak и ключа

Раз XTS детерминирован, у него есть характерные слабости:

- **Cut-and-paste секторов.** Сектор с одной позиции можно скопировать на
  другую; если tweak при этом не меняется (ошибка реализации), получится
  валидная копия.
- **Переиспользование tweak.** Один номер сектора на разных областях даёт
  ECB-подобную утечку — одинаковые блоки снова совпадают.
- **Один ключ вместо двух.** Если `K1 = K2`, XEX теряет часть стойкости.
- **Малый tweak-space.** Мало номеров секторов → растёт вероятность коллизий.

Важно для пентеста: XTS **сама по себе криптостойка**. Если у вас образ
шифрованного диска, вы не «ломаете XTS» — вы подбираете пароль к заголовку
(LUKS/VeraCrypt) или пытаетесь извлечь ключ из TPM/памяти (BitLocker/FileVault).
Слабое звено — KDF и управление ключами, а не режим.

## Справочные таблицы

| Свойство | ECB | CBC | XTS |
|----------|-----|-----|-----|
| Произвольный доступ | да | нет | да |
| Скрывает паттерны | нет | да | да |
| IV/tweak | нет | IV на цепочку | tweak на сектор |
| Длина = исходной | да | с padding | да (CTS) |
| Аутентификация | нет | нет | нет |

| Параметр | Значение |
|----------|----------|
| Стандарт | IEEE 1619 |
| Ключей | 2 (`K1` tweak, `K2` данные) |
| Умножение | на `α` в `GF(2^128)` |
| Tweak | номер сектора (LE) + позиция блока |

## Почему tweak должен быть уникален

XTS строится на конструкции **XEX** (XOR-Encrypt-XOR): блок шифруется как `C = E_K(P ⊕ T) ⊕ T`, где `T` — «tweak», зависящий от номера сектора и умноженный в поле `GF(2^128)`. Tweak — это не ключ и не секрет; он должен быть **уникален для каждой позиции данных**. Смысл: один и тот же блок на разных позициях даёт разный шифротекст, поэтому ECB-подобная утечка «одинаковые блоки видны» исчезает.

Почему именно позиция, а не случайный IV? Диск нельзя переписать целиком, а IV пришлось бы хранить рядом с каждым сектором. Номер сектора уже есть в адресе — он и служит tweak'ом, детерминированно. Так работает и шифрование дисков (XTS-AES), и это делает шифрование **перестановочно-безопасным** для отдельных секторов: правка сектора не портит соседние.

Главная опасность — **переиспользование tweak'а или ключа**. Если два разных сектора шифруются одним `(K, T)`, то `C1 ⊕ C2 = P1 ⊕ P2` — снова утечка XOR. Ещё серьёзнее: если один ключ XTS используется для двух дисков с одинаковой нумерацией, одинаковые сектора дают одинаковый шифротекст. Отсюда правило: ключ XTS должен быть уникален на том/диск, а tweak — уникален на сектор. Ciphertext stealing решает проблему последнего неполного блока, не теряя данных.

## Если не сработало

- **Одинаковые сектора дают одинаковый шифротекст.** Проверьте, не переиспользован ли ключ между томами/дисками или не сброшен ли tweak.
- **Повреждён последний блок.** Ciphertext stealing требует корректной длины; при ручной реализации легко потерять байты — проверьте round-trip.
- **Сектор не читается целиком.** XTS шифрует посекторно; частичное чтение требует расшифровать весь сектор. Учитывайте размер сектора (обычно 512 или 4096).
- **XTS для не-дисковых данных.** XTS не AEAD: он не даёт целостности. Для сетевого/файлового шифрования нужен AEAD, а не XTS.
- **Ключ слишком короткий.** XTS-AES использует два ключа (или один, развёрнутый); 256-битный XTS — это два 128-битных ключа. Не путайте с размером одного ключа AES.

## Частые вопросы

**Почему для дисков XTS, а не GCM?** GCM требует уникального nonce и добавляет тег (расширяет данные), а при ошибке тега теряется весь том. XTS детерминирован, не расширяет данные и позволяет править отдельные секторы — то, что нужно диску.

**Что будет, если два сектора получат одинаковый tweak?** Утечка XOR между ними: `C1 ⊕ C2 = P1 ⊕ P2`. Внутри одного диска это не грозит, если нумерация уникальна; при копировании дисков — грозит.

**Даёт ли XTS аутентификацию?** Нет. Атакующий может подменить блоки, и система не заметит. Для целостности нужны отдельные механизмы (например, dm-verity).

## Куда дальше

XTS — инженерная надстройка над блочным шифром. В следующем уроке
(`crypto-integral-cryptanalysis`) мы вернёмся к атакам на сам шифр и разберём
интегральный (Square) метод. А ещё нас ждёт `crypto-disk-encryption`, где мы
разберём заголовки LUKS/BitLocker и офлайн-подбор пароля. Главное запомни:
**XTS даёт произвольный доступ и скрывает паттерны, но не аутентифицирует
данные — целостность защищают отдельно (dm-verity, подписи)**.
