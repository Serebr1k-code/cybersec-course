## Зачем это нужно

Kerberos — основа аутентификации в Active Directory, а значит, в большинстве корпоративных сетей. Его криптография устроена так, что **сам протокол** надёжен, но **офлайн-подбор** паролей из перехваченных тикетов — стандартная и очень эффективная атака. Понимание того, какие ключи выводятся из пароля, как тикеты защищены и где утекает материал для подбора, — обязательный навык для любого, кто работает с AD.

Для CTF Kerberos-задачи обычно дают `hashcat`-хэш из тикета или `.kirbi`-файл и требуют восстановить пароль/подделать тикет. Для пентеста это ежедневный инструмент латерального движения.

## Kerberos и типы шифрования

Протокол выдаёт тикеты: **TGT** (Ticket Granting Ticket) от KDC после аутентификации и **TGS** (service ticket) для доступа к сервису. Каждый тикет зашифрован ключом, выведенным из пароля владельца (для TGT) или сервисной учётки (для TGS).

**Типы шифрования (etype)**:

- **23 (RC4-HMAC)** — ключ = `NT hash` (MD4 пароля). Слабее, быстрее подбирается, поддерживает «pass-the-key».
- **17 (AES128-CTS-HMAC-SHA1-96)** и **18 (AES256-CTS-HMAC-SHA1-96)** — ключ выводится из пароля через **PBKDF2** (соль = домен+username, 4096 итераций). Медленнее подбирать.

Ключевое: в RC4 ключ тикета — это **NT hash**, поэтому перехват RC4-тикета = перехват NT-хэша, который затем можно использовать без подбора. В AES — нужно подбирать пароль.

## AS-REP roasting

Если у учётной записи отключена **предварительная аутентификация** (pre-auth, `DONT_REQ_PREAUTH`), KDC отдаёт AS-REP **без проверки**, что клиент знает пароль. В ответе — часть, зашифрованная ключом из пароля пользователя. Атакующий запрашивает AS-REP для такого пользователя и подбирает пароль офлайн.

```bash
# найти пользователей без pre-auth
impacket-GetNPUsers domain.local/ -usersfile users.txt -no-pass -dc-ip 10.0.0.1
# получить хэш и подобрать
hashcat -m 18200 asrep_hash.txt wordlist.txt
```

`-m 18200` — AS-REP etype 23 (RC4); `-m 19800/19900` — AES128/256. Успех = пароль пользователя.

## Kerberoasting

Любой аутентифицированный пользователь может запросить **TGS** для сервиса по его **SPN**. TGS зашифрован ключом сервисной учётной записи (или machine account). Атакующий запрашивает TGS и подбирает пароль сервисной учётки **офлайн**.

```bash
# запросить TGS для всех SPN
impacket-GetUserSPNs domain.local/user:pass -request -dc-ip 10.0.0.1
# подбор
hashcat -m 13100 tgs_hash.txt wordlist.txt
```

`-m 13100` — Kerberos 5 TGS-REP etype 23; `-m 19600/19700` — AES128/256. Kerberoasting особенно опасен, потому что:
- Не требует привилегий (любой доменный пользователь).
- Сервисные учётки часто имеют слабые пароли и высокие права.
- Тикеты долгоживущие — можно собрать и подбирать неторопливо.

**Targeted Kerberoasting**: если у учётки нет SPN, но есть права на её изменение, можно **добавить SPN** и затем запросить TGS — снова офлайн-подбор.

## PAC и подписи

**PAC** (Privilege Attribute Certificate) — структура внутри тикета, содержащая группы/права пользователя. KDC подписывает PAC ключом `krbtgt` (для TGT) или сервисным ключом. Это создаёт атаки:

- **Golden ticket**: зная ключ `krbtgt`, можно подделать любой TGT с произвольными правами (включая Domain Admin). Ключ `krbtgt` получают через DCSync.
- **Silver ticket**: зная ключ сервисной учётки, подделать TGS для этого сервиса (доступ без обращения к KDC).
- **PAC forgery / MS14-068**: историческая уязвимость проверки PAC.

Для CTF «золотой тикет» — задача: дан `krbtgt`-хэш, сгенерировать TGT и получить доступ. Инструмент — `impacket-ticketer`.

```bash
impacket-ticketer -nthash <krbtgt_nt> -domain-sid S-1-5-21-... -domain domain.local administrator
```

## Инструменты и команды

- **`impacket`** — `GetNPUsers`, `GetUserSPNs`, `ticketer`, `secretsdump` (DCSync).
- **`hashcat`** — режимы 13100/18200 (RC4), 19600-19900 (AES).
- **`john`** — `krb5tgs`/`krb5asrep` форматы.
- **`kerbrute`** — user enumeration и password spraying.
- **`Rubeus`** — Windows-инструмент для Kerberos-атак.
- **`bloodhound`** — поиск Kerberoastable-учёток.

## Разобранный пример: Kerberoasting от начала до конца

1. Получаем доменного пользователя (или используем существующего).
2. Перечисляем SPN: `impacket-GetUserSPNs domain.local/user:pass -dc-ip DC`.
3. Запрашиваем TGS: добавляем `-request`, получаем хэш `$krb5tgs$23$...`.
4. Определяем etype (23 = RC4, 17/18 = AES).
5. Подбираем: `hashcat -m 13100 hash.txt rockyou.txt`.
6. При успехе — пароль сервисной учётки; проверяем её права (часто админские).

Если учётка — machine account (заканчивается на `$`), пароль обычно 120 случайных символов — подбор нереален. Ищите **человеческие** сервисные учётки.

## Delegation и Kerberos-крипто

Kerberos в AD поддерживает **делегирование**: сервис может действовать от имени пользователя, обращаясь к другому сервису. Это мощный механизм и одновременно источник серьёзных атак, тесно связанных с криптографией тикетов.

**Unconstrained delegation**: сервис может делегировать любые учётные данные, и при обращении пользователя в память сервиса попадает его **TGT** (полный тикет). Атакующий, получивший контроль над таким сервисом (или приманив к нему пользователя через PrinterBug/PetitPotam), забирает TGT и переиспользует его — это «pass-the-ticket» на уровне TGT. Криптографически здесь нет взлома: тикет уже выдан KDC, и атакующий просто им пользуется.

**Constrained delegation**: сервис может делегировать только к заранее указанным SPN. Использует расширение **S4U2Self/S4U2Proxy**. Если разрешение задано через `AllowedToDelegateTo`, атакующий может запросить тикет к целевому сервису от имени администратора — снова без подбора паролей, только через злоупотребление выдачей тикетов.

**Resource-based constrained delegation (RBCD)**: разрешение задаётся на **целевом** объекте (кто может делегировать к нему). Атакующий, имеющий право изменять атрибут `msDS-AllowedToActOnBehalfOfOtherIdentity` (например, через `GenericWrite`), может настроить RBCD на машине и получить доступ к ней от имени администратора. Это чистая логическая атака на конфигурацию, опирающаяся на корректно выданные Kerberos-тикеты.

Практический вывод: в AD криптография Kerberos обычно **не ломается** — тикеты выдаются легитимно. Атаки идут через **делегирование, права на объекты и подделку тикетов при утечке ключей**. Понимание etype нужно, чтобы знать, где возможен офлайн-подбор, а понимание делегирования — чтобы знать, где пароли вообще не нужны.

## Детект и логирование Kerberos-атак

Защитникам важно знать, как эти атаки выглядят в логах, потому что почти все они оставляют следы:

- **Kerberoasting**: множество событий `4769` (запрос TGS) с разными SPN от одного пользователя, часто с etype RC4 (0x17). Аномалия — запросы TGS без последующего использования сервиса.
- **AS-REP roasting**: события `4768` (запрос TGT) без предварительной аутентификации (`PreAuthType=0`) для учёток с `DONT_REQ_PREAUTH`.
- **Golden ticket**: событие `4769` с аномальным временем жизни тикета, отсутствием соответствующих `4768`, или тикет для пользователя, который не логинился.
- **DCSync**: события репликации (`4662` с правом `DS-Replication-Get-Changes-All`) от не-DC хоста.
- **RBCD/делегирование**: изменения атрибута `msDS-AllowedToActOnBehalfOfOtherIdentity` (событие `5136`).

Для CTF это редко нужно, но для пентеста — обязательно: понимание логов помогает и обходить детект (выбирать «тихие» атаки), и отчитываться о последствиях. Например, Kerberoasting «громкий» (много 4769), а Silver ticket «тихий» (обращается не к KDC, а сразу к сервису).

Отдельная тема — **AES-only домены**. Если RC4 запрещён, все тикеты используют AES (etype 17/18), и офлайн-подбор резко замедляется (PBKDF2 + AES). Это правильная защита, но она не мешает делегированию и RBCD, потому что те не требуют подбора. Поэтому в современном AD крипто-атаки сместились от «подбери пароль» к «злоупотреби выдачу тикетов».

## Частые ошибки и подводные камни

- **Путать AS-REP и TGS-REP**: AS-REP — для учёток без pre-auth, TGS-REP — для сервисов с SPN.
- **Неверный режим hashcat**: RC4 (13100) vs AES (19600+) — подбор не запустится или будет неэффективен.
- **Пытаться подобрать machine account**: пароли длинные и случайные.
- **Игнорировать AES**: если в домене запрещён RC4, хэши будут AES — подбор медленнее.
- **Забыть про pre-auth**: учётки с включённой pre-auth не дадут AS-REP.
- **Считать golden ticket «безопасным»**: он живёт до смены `krbtgt` (дважды).

## Контрмеры и защита

- Включить предварительную аутентификацию для всех учёток.
- Использовать **managed service accounts** (gMSA) с автоматической ротацией паролей — они не подбираются.
- Запретить RC4, оставить AES (etype 17/18).
- Длинные случайные пароли для сервисных учёток.
- Мониторить запросы TGS с аномальными SPN (детект Kerberoasting).
- Регулярная (двойная) ротация `krbtgt`; защита DCSync.
- Least privilege: сервисные учётки не должны быть администраторами.

## Что дальше / решение

Kerberos-крипто соединяет `crypto-hmac` (HMAC/PBKDF2) и AD-атаки. Дальше: `playbook-ad` (полный AD-плейбук), `crypto-tls-attacks` (LDAPS/EWS), `crypto-disk-encryption` (защита DC). На практике: сначала найдите Kerberoastable-учётки, запросите тикеты, подберите офлайн — это самый быстрый путь к повышению привилегий в AD.
