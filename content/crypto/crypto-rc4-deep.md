## Вопрос, с которого всё начинается

RC4 — потоковый шифр: он генерирует поток байт (**keystream**) и складывает его с
открытым текстом по XOR. Ключ в RC4 необратимо перемешивает внутренний S-бокс,
поэтому по одному keystream ключ не восстановить. Но что, если keystream **не
вполне случаен**? Тогда, собрав много шифротекстов, можно вытащить открытый текст
статистикой.

Именно так и есть: у RC4 есть знаменитые **смещения** (biases) — отдельные байты
keystream принимают некоторые значения чаще, чем «честные» `1/256`. Разберём это
на реальном примере и восстановим байт секрета.

## Наш пример: один запрос, много ключей

Представим сервер, который шифрует один и тот же запрос RC4, но каждый раз с
**новым случайным ключом** (так делают, например, при шифровании cookie в сессии).
Открытый текст начинается с `secret`. Мы собрали 30000 таких шифротекстов и
хотим восстановить первый байт секрета. Прямой подбор ключа невозможен — но
статистика поможет.

## Шаг 1: KSA и PRGA

RC4 работает с S-боксом из 256 байт в два этапа.

**KSA** (Key Scheduling Algorithm) — перемешивание S-бокса ключом:

```python
def ksa(key):
    S = list(range(256)); j = 0
    for i in range(256):
        j = (j + S[i] + key[i % len(key)]) & 0xff
        S[i], S[j] = S[j], S[i]
    return S
```

**PRGA** (Pseudo-Random Generation Algorithm) — генерация keystream:

```python
def prga(S):
    i = j = 0
    while True:
        i = (i + 1) & 0xff
        j = (j + S[i]) & 0xff
        S[i], S[j] = S[j], S[i]
        yield S[(S[i] + S[j]) & 0xff]
```

Шифрование: `C = P ⊕ keystream`. Слабость зарыта в KSA: первые шаги почти не
перемешивают S, поэтому начальные байты keystream **коррелируют с ключом** — это
и есть источник смещений.

## Шаг 2: смещения (biases)

Идеальный потоковый шифр даёт равномерный keystream: каждый байт равен любому
значению с вероятностью `1/256`. У RC4 это не так. Знаменитейшее смещение:
**второй байт keystream равен нулю** с вероятностью примерно `2/256` — вдвое
выше случайной. Измерим это на 200000 случайных ключей:

```
P(ks[1]==0) = 0.00779   (случайное 1/256 = 0.00391)
выше случайного в 1.99 раза
```

Вот оно: вместо `1/256 ≈ 0.0039` получаем `≈ 0.0078`. Смещение маленькое, но
**стабильное** — а значит, накапливается при большом числе наблюдений.

## Шаг 3: атака по моде

Как из смещения извлечь открытый текст? Если один и тот же байт `P[1]`
шифруется много раз разными ключами, то `C[1] = P[1] ⊕ ks[1]`. Когда `ks[1] = 0`
(а это случается чаще нормы), `C[1]` **равно самому `P[1]`**. Значит, самое частое
значение шифротекста на позиции 1 — это и есть байт открытого текста:

```python
counts = [Counter() for _ in range(len(plain))]
for c in samples:
    for i, b in enumerate(c): counts[i][b] += 1
mode = counts[1].most_common(1)[0][0]      # мода позиции 1
```

Мы восстановили байт `e` из «зашифрованного» потока, не зная ни одного ключа —
только по статистике 30000 сессий. Именно так работают реальные атаки на RC4:
нужно много сессий с повторяющимся фрагментом открытого текста (cookie, токен).

## Что мы теперь знаем

- RC4 = KSA (перемешивание S ключом) + PRGA (генерация keystream); шифрование — XOR.
- У RC4 есть **смещения**: `P(ks[1]==0) ≈ 2/256` вместо `1/256`.
- Смещения стабильны и накапливаются: при повторяющемся открытом тексте мода
  шифротекста выдаёт байт открытого текста.
- Ключ по одному keystream не восстанавливается — нужны либо много сессий
  (статистика), либо **связанные ключи** (WEP).
- RC4 запрещён в TLS (RFC 7465), но живёт в legacy: WEP, WPA-TKIP, старый RDP.

## FMS, WEP и NOMORE

**FMS-атака на WEP.** WEP использует RC4 с ключом `IV || K`, где `IV` (3 байта)
передаётся открыто, а `K` фиксирован. Это **связанные ключи**: меняя IV, атакующий
получает корреляции первого байта keystream с байтами `K`. Собрав миллионы пакетов
с «слабыми» IV, для каждого байта ключа берут самое частое значение — так WEP
ломается за минуты (aircrack-ng).

**RC4 NOMORE.** Атака 2015 года на RC4 в TLS: смещения в первых ~256 байтах
позволяют восстанавливать cookie при большом числе запросов (`~2^26–2^32`). Именно
она стала одной из причин полного запрета RC4.

**Дроп первых байт.** Некоторые реализации отбрасывают 256/768/3072 первых байт
(«RC4-drop»), снижая смещения, но не устраняя их полностью.

## Инструменты и как не застрять

```bash
python3 -c "from Crypto.Cipher import ARC4; print(ARC4.new(b'key').encrypt(b'hi').hex())"
aircrack-ng -b <bssid> capture.cap        # WEP: FMS/KoreK
```

Порядок действий в задаче на RC4:

1. Определите RC4 по контексту (WEP, старый TLS, RDP, самодельный протокол).
2. Соберите **много** шифротекстов: с одним ключом (тогда `C1⊕C2 = P1⊕P2`) или с
   разными ключами при повторяющемся открытом тексте (тогда работает мода).
3. Используйте известный/угаданный текст, чтобы перейти к keystream.
4. Применяйте статистику: мода по позициям; помните про смещение второго байта.
5. Для WEP — `aircrack-ng` с миллионами пакетов и связанными IV.
6. Проверьте дроп первых байт: реализация может отбрасывать 256/768/3072 байта.

## Как отличить RC4 от случайного

Смещение можно использовать и просто для **детекта** RC4: если на позиции 1 байт
`0` встречается заметно чаще `1/256`, поток почти наверняка от RC4 (или его
варианта). Аналогично смещены и другие позиции первых 256 байт, что даёт
статистический отпечаток шифра даже без знания ключа.

## Почему смещения вообще возникают

Идеальный потоковый шифр обязан давать keystream, неотличимый от честной случайности: каждый байт — равномерно из 256 значений, и никакая позиция не выделяется. RC4 к этому не стремится. Его KSA выполняет всего 256 обменов, а первые из них почти не перемешивают массив: пока счётчик `i` маленький, он трогает лишь начало `S`, и структура «почти отсортированного» массива сохраняется. После KSA перестановка смещена в сторону тождественной — это и есть корень всех смещений.

Mantin и Shamir показали, что **второй байт** keystream равен нулю с вероятностью примерно `2/256`, а не `1/256`. Есть и парные смещения (Fluhrer–McGrew): пара `(0, 0)` на соседних позициях встречается чаще, чем `1/256²`. Roos нашёл, что после KSA вероятность `S[1] = 0` аномально высока. Все эти эффекты — следствие того, что ранние выходы PRGA линейно зависят от первых байт ключа: пока `i` не прошёл по всему массиву, swap'ы не успели «затереть» связь с ключом.

Именно на этих смещениях строятся и FMS-атака на WEP, и атака на второй байт, и RC4 NOMORE. Понимание механики важно: смещение — не баг конкретной реализации, а свойство самого алгоритма, поэтому «правильная» реализация RC4 тоже уязвима, и единственный надёжный выход — сменить шифр.

## Если не сработало

Мода по позиции не сходится к байту открытого текста — почти всегда одна из четырёх причин:

- **Мало наблюдений.** Смещение всего вдвое выше случайного, поэтому нужны десятки тысяч сессий; на сотне выборок шум победит.
- **Ключ один и тот же.** Тогда keystream одинаков, и статистика «моды» не работает — зато работает XOR двух шифротекстов: `C1 ⊕ C2 = P1 ⊕ P2`, то есть crib-dragging по известному фрагменту.
- **Отброшены первые байты (RC4-drop).** Реализация может пропускать 256, 768 или 3072 байта, и тогда смещение второго байта исчезло. Ищите смещения на более глубоких позициях или другой канал.
- **Повторяющийся фрагмент не выровнен.** Если поверх шифра лежит base64 или сжатие, байты «плывут»; мода даст мусор. Сначала снимите кодировку.

Ещё проверьте, что открытый текст на интересующей позиции действительно **постоянен** во всех сессиях: если байт меняется, самое частое значение шифротекста не имеет смысла.

## Частые вопросы

**Можно ли восстановить сам ключ, а не открытый текст?** По одному keystream — нет: перебрать `256!` состояний S-бокса невозможно. Ключ достают либо через связанные ключи (WEP, где IV стоит перед `K`), либо через утечку из KSA. Статистика по разным ключам восстанавливает именно открытый текст.

**Сколько сессий нужно на практике?** Для смещения `2/256` — десятки тысяч; для FMS на WEP — миллионы пакетов со «слабыми» IV, что как раз и делает WEP ломаемым за минуты.

**Почему бы не взять просто XOR двух шифротекстов?** Это работает только при **одинаковом** ключе. При разных ключах XOR даёт `P1 ⊕ P2 ⊕ ks1 ⊕ ks2`, то есть шум; здесь и нужна статистика.

## Куда дальше

RC4 — пример того, как «простой и быстрый» шифр проигрывает статистике. Дальше мы
разберём **LFSR и Berlekamp–Massey** (`crypto-lfsr`) — линейные регистры, где
предсказуемость ещё сильнее, а затем **ChaCha20** (`crypto-chacha`) — современную
замену RC4. А главное запомни: **смещение keystream — это утечка; повторяющийся
открытый текст плюс много сессий = восстановленный секрет**.

## Где пригодится

- **CTF crypto** — задачи с RC4 и статистическими утечками.
- **Bug bounty / пентест** — аудит Wi-Fi (WEP/WPA) и старых TLS.
- **Аудит кода / разработка** — запрет RC4, миграция на AEAD.
- **SOC / IR** — понимание инцидентов с WEP/RDP/RC4.
- **Исследования** — статистический криптоанализ потоковых шифров.
