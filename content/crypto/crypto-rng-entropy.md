## Вопрос, с которого всё начинается

Представь, что сервер генерирует токены сброса пароля так: `random.seed(int(time.time()))`. На первый взгляд — случайно. Но время предсказуемо, и пространство seed крошечное. Атакующий перебирает его и восстанавливает все токены. Разберём это на конкретном примере.

## Наш пример: токен от random с seed=время

У нас `token.txt` с токеном, и мы знаем, что seed — это `int(time.time())` в окне `1697000000..1697000100`.

```
$ cat token.txt
token = 2751748589
```

## Шаг 1: почему время — плохой seed

`time.time()` возвращает секунды с эпохи. Если атакующий знает примерное время генерации (а он знает — из заголовка письма, логов или просто «сегодня»), пространство seed сужается до нескольких тысяч. Python `random` — **Mersenne Twister**: полностью детерминирован от seed. Значит, зная seed, атакующий воспроизводит **всю** последовательность.

## Шаг 2: перебор seed

Перебираем seed в окне и для каждого сравниваем первый выход с известным токеном:

```python
import random
token = 2751748589
for s in range(1697000000, 1697000101):
    if random.Random(s).getrandbits(32) == token:
        print('seed =', s)
        break
```

Как только seed найден, все последующие значения (токены сессий, ключи) восстанавливаются:

```
$ python3 crack_seed.py
seed = 1697000000  next secret = 3071214311
flag: nto{t1m3_s33d_1s_n0t_3ntr0py}
```

## Шаг 3: /dev/random vs /dev/urandom

- **/dev/random** — блокируется, когда пул энтропии исчерпан; на ранних системах это вызывало «зависание» при генерации ключей.
- **/dev/urandom** — CSPRNG на базе ChaCha20 (в современном Linux), **не блокируется**. Считается безопасным для ключей после инициализации.
- **getrandom()** — системный вызов, блокируется только до инициализации пула.

Правило: используй `getrandom()`/`os.urandom()`/`secrets`, а не время/PID/`random`.

## Шаг 4: измерение энтропии

Энтропия измеряется в битах: сколько «неопределённости» в seed. Время в окне 100 секунд даёт ~7 бит. PID даёт ~15 бит. Их сумма — ~22 бита, что перебирается мгновенно. Хороший seed — 128+ бит из аппаратного источника. Атака seed-recovery ищет **любой** источник с низкой энтропией: время, PID, счётчик, `Math.random`, `rand()`.

## Полный прогон от начала до конца

1. `cat token.txt` — токен.
2. Перебираем seed в известном окне.
3. Находим seed, воспроизводим следующий выход.
4. `python3 crack_seed.py | grep nto > found.txt`.

## Если не сработало

Если окно времени неизвестно — расширяй диапазон (дни, недели), но это дороже. Если используется `getrandbits(32)`, а не `randint`, учитывай, как именно извлекаются биты. Если seed включает PID, перебирай и его. И помни: Mersenne Twister восстанавливается даже **без** seed — по 624 выходам (см. `crypto-mt19937-deep`).

## Как измеряют энтропию

Энтропия — это мера неопределённости в битах. Формально для распределения `X` энтропия Шеннона `H(X) = -Σ p(x) log2 p(x)`. Для источника с `2^n` равновероятными состояниями `H = n` бит. Время в окне `W` секунд даёт `log2(W)` бит; PID даёт ~15 бит; MAC-адрес — ~24 бита (если известен производитель). Сумма таких «источников» растёт медленно.

На практике энтропию пула измеряют по событиям (прерывания клавиатуры, тайминги дисков) и смешивают в CSPRNG. Проблема возникает, когда систему запускают в «стерильном» окружении (виртуалка, контейнер) без этих событий — тогда пул пуст и генератор выдаёт предсказуемые значения. Это причина «boot-time entropy» проблем и уязвимости CVE-2008-0166 (Debian).

## Другие источники слабого seed

Помимо времени и PID, слабые seed дают:

- **Счётчики** — если seed = порядковый номер запроса, всё предсказуемо.
- **MAC-адрес** — если ключ выводится из MAC, атакующий знает его из трафика.
- **Номер процесса в контейнере** — маленький и повторяющийся.
- **`srand(0)` / фиксированный seed** — классическая ошибка разработчиков.
- **Аппаратный RNG без энтропии** — если TRNG «залип» на константе (бывает при виртуализации).

Атака всегда одна: найти **любой** источник с низкой энтропией и перебрать его.

## Практика: как защищаться

Правила: (1) использовать `getrandom()`/`os.urandom()`/`secrets` — они берут энтропию из ядра; (2) не сеять CSPRNG вручную; (3) проверять доступность энтропии при старте (не генерировать ключи до инициализации пула); (4) на виртуалках обеспечить источник энтропии (virtio-rng, `haveged`); (5) для токенов — минимум 128 бит энтропии. Аудит должен искать `random.seed(time...)`, `srand(pid)`, `Math.random` в коде генерации ключей.

## Разбор: PHP mt_rand с seed по времени

Классическая веб-уязвимость. PHP `mt_rand()` сеется автоматически при первом вызове, но многие приложения делают `mt_srand(time())`. Атака:

1. Узнать примерное время генерации токена (по заголовку `Date` ответа или логам).
2. Перебрать seed в окне ±несколько секунд.
3. Для каждого seed воспроизвести последовательность `mt_rand()` и сравнить с известным токеном.

```php
// уязвимый код
mt_srand(time());
$token = mt_rand();
```

В Python восстановление делается через библиотеку, воспроизводящую PHP Mersenne Twister (у PHP своя реализация MT с `mt_rand` и особенностями). Если токен получен из `mt_rand() % N`, атакующий восстанавливает и остальные значения. Реальная эксплуатация: предсказание токенов сброса пароля, cookie сессий, CSRF-токенов.

Защита: использовать `random_bytes()` / `random_int()` (CSPRNG), а не `mt_rand`. Для токенов — минимум 128 бит.

## Частые вопросы

**Что делать, если окно времени большое?** Расширяй диапазон постепенно: сначала часы, потом сутки. Если это дорого, используй структуру: например, если токен получен через `randint(0, 10**6)`, ты можешь отбросить большинство seed по первому выходу. Ещё вариант — восстановить состояние Mersenne Twister напрямую по 624 выходам, не зная seed.

**Как отличить CSPRNG от PRNG по выходам?** Статистические тесты (NIST STS, dieharder) проверяют равномерность и отсутствие корреляций. Но неcryptographic PRNG могут пройти статистику и всё равно быть предсказуемыми — статистика не ловит линейность. Поэтому важнее смотреть на **код**, а не на выходы.

**Что если приложение сеет CSPRNG временем?** Это всё ещё уязвимо: CSPRNG детерминирован от seed. Если seed = время, атакующий воспроизводит весь поток. Правильно — вообще не сеять вручную, а брать энтропию из ядра.

**Почему `/dev/random` иногда «виснет»?** На старых ядрах он блокировался до набора энтропии. Современный `/dev/random` использует ту же ChaCha20-схему, что `/dev/urandom`, и блокируется только до инициализации. Для ключей безопасно и то, и другое.

**Как проверить, что ключ сгенерирован правильно?** Проверь, что он не повторяется между запусками, что источник — `getrandom`, и что нет ручного `seed(time)`/`srand(pid)`.

## Что мы теперь знаем

- Время/PID — плохие seed: пространство мало.
- Mersenne Twister детерминирован от seed.
- seed-recovery перебором восстанавливает все токены.
- `/dev/urandom`/`getrandom` — правильные источники.
- Энтропия измеряется в битах; 128+ — норма.
- Не сеять CSPRNG вручную: `os.urandom`/`secrets` берут энтропию из ядра.
- На виртуалках нужен источник энтропии (virtio-rng, haveged), иначе пул пуст.
