## Вопрос, с которого всё начинается

В `crypto-homomorphic` мы видели частично гомоморфные схемы: Paillier складывает, RSA-HE умножает. Но чтобы посчитать над шифротекстами произвольную программу — и сложение, и умножение, и снова сложение — нужна схема, которая поддерживает **оба** действия неограниченно долго. Это **FHE** (Fully Homomorphic Encryption). Идея: облако считает по твоим зашифрованным данным, ничего не видя. Разберём, почему это вообще возможно и где спрятана сложность.

## Наш пример: шум в решётчатой схеме

Современные FHE (BFV, BGV, CKKS, TFHE) — решётчатые. Шифротекст — это пара многочленов, а «полезный» сигнал спрятан в **шуме**. Упрощённо для BFV:

```
ct = (c0, c1),   c0 = -a·s + e + Δ·m (mod q)
```

где `s` — секретный ключ, `a` — публичный, `e` — маленький шум, `m` — сообщение, `Δ` — масштаб. Расшифровка: `c0 + c1·s = Δ·m + e`. Если шум `e` мал, `Δ·m` читается однозначно.

Проблема: **шум растёт** при каждой операции. Сложение растёт медленно, умножение — сильно. Когда шум превышает запас, сообщение теряется. Частично гомоморфные схемы (Paillier) живут с этим, поддерживая одно действие. FHE должна уметь «обнулять» шум.

## Шаг 1: relinearization

При умножении двух шифротекстов размер пары растёт (получается три компоненты). **Relinearization** — процедура, которая сжимает результат обратно в две компоненты, используя **evaluation key** (перешифрованный секретный ключ). Без неё шифротексты растут при каждом умножении и работа становится невозможной.

## Шаг 2: bootstrapping

Главная идея FHE, придуманная Гентом (2009): **bootstrapping**. Если шум стал большим, но ещё позволяет расшифровать, можно «перезапустить» шифротекст: гомоморфно вычислить функцию расшифровки над самим шифротекстом, используя зашифрованный секретный ключ. Результат — новый шифротекст того же сообщения, но с маленьким шумом. Так можно считать неограниченно долго, платя за это производительностью.

```
ct_шумный --[гомоморфная расшифровка]--> ct_свежий (шум мал)
```

## Шаг 3: семейства

- **BFV / BGV:** точная арифметика над целыми/модулем; BFV чуть проще, BGV эффективнее по уровням.
- **CKKS:** приближённая арифметика над **вещественными/комплексными** числами — для ML и статистики, где нужны дроби, а не точные целые.
- **TFHE:** булевы схемы и очень быстрый bootstrapping на каждый бит — для логики и сравнений.

Выбор схемы — это выбор типа данных: целые (BFV/BGV), дробные (CKKS) или биты (TFHE).

## Шаг 4: откуда берётся стойкость

Шум `e` и секрет `s` малы; задача восстановления `s` по публичным `(a, c0)` — это **LWE/Ring-LWE** (Learning With Errors). Ты видел LWE в `crypto-post-quantum`. Именно она даёт пост-квантовую стойкость: FHE одновременно и гомоморфна, и устойчива к Shor.

## Полный прогон

В лабе дан `bfv.txt` с параметрами `q`, `Δ`, публичным `a` и двумя шифротекстами, и скрипт `fhe.py`. Скрипт перемножает шифротексты, расшифровывает и печатает результат:

```
$ cat bfv.txt
q = ...
delta = ...
a = ...
ct1 = (c0_1, c1_1)   # шифрует 6
ct2 = (c0_2, c1_2)   # шифрует 7

$ python3 fhe.py
dec(ct1) = 6
dec(ct2) = 7
dec(ct1 * ct2) = nto{bfv_h0m0m0rph1c_mult1ply}
```

Флаг — результат гомоморфного умножения (как строка), студент видит, что произведение посчитано без расшифровки.

## Если не сработало

Если расшифровка даёт мусор, проверь масштаб `Δ` и запас шума: возможно, шум превысил бюджет. Если результат «съехал» на небольшое число — это CKKS-подобная приближённая схема, ошибка нормальна. Если шифротекст не сжимается — забыта relinearization.

## Параметры BFV и шумовой бюджет

Разберём, как читать параметры реальной схемы. В BFV задаются: `n` — степень многочлена-модуля (обычно 4096–16384), `q` — модуль шифротекста (большое число), `t` — модуль открытого текста (обычно 2 или 1024). Масштаб считается как `Δ = ⌊q/t⌋`. Расшифровка возвращает `Δ·m + e`; чтобы прочитать `m`, нужно `|e| < Δ/2`. «Шумовой бюджет» измеряют в битах: `log2(Δ/2) − log2(σ·√(2n))`, где `σ` — стандартное отклонение шума. Каждое умножение съедает около `log2(n)` бит бюджета, каждое сложение — почти ничего. Отсюда правило: глубину схемы (multiplicative depth) планируют заранее, а когда бюджет кончается — делают bootstrapping.

```
# параметры (пример, не для продакшена)
n = 4096, log2(q) = 109, t = 2
delta = floor(q / t)
noise_budget = log2(delta/2) - log2(sigma * sqrt(2*n))   # ~30 бит для свежего ct
```

## Практика: SEAL, OpenFHE и TenSEAL

Настоящие FHE-библиотеки: **Microsoft SEAL**, **OpenFHE** (преемник PALISADE) и **TenSEAL** (обёртка над SEAL для Python). Ставим и проверяем версию:

```
$ pip install tenseal
$ python3 -c "import tenseal as ts; print(ts.__version__)"
0.3.14
```

Простейшая CKKS-операция выглядит так:

```python
import tenseal as ts
ctx = ts.context(ts.SCHEME_TYPE.CKKS, poly_modulus_degree=8192,
                 coeff_mod_bit_sizes=[60, 40, 40, 60])
ctx.generate_galois_keys(); ctx.global_scale = 2**40
enc = ts.ckks_vector(ctx, [1.5, 2.5, 3.5])
res = (enc * enc).sum().decrypt()   # [16.5]
```

Здесь `coeff_mod_bit_sizes` — это «цепочка уровней»: после каждого умножения уровень тратится, а `global_scale` задаёт точность. В SEAL то же самое делается через `Evaluator::multiply`, а `Decryptor::invariant_noise_budget` возвращает оставшийся бюджет в битах — им удобно отлаживать глубину схемы.

## CKKS: масштаб, rescale и точность

В CKKS сообщение кодируется в полином, а «точка» ставится масштабом `Δ = 2^40`. Умножение двух шифротекстов даёт масштаб `Δ²`, поэтому сразу после умножения вызывают **rescale** — деление на последний уровень цепочки, возвращающее масштаб к `Δ`. Если забыть rescale, следующий уровень «съест» точность, и результат превратится в шум. Точность CKKS примерно равна `log2(Δ) − log2(число операций)` бит: после 20 умножений 40-битный масштаб оставляет ~20 верных бит мантиссы. Для ML этого достаточно, для точных целых — нет; там берут BFV/BGV.

## TFHE и программируемый bootstrapping

**TFHE** работает над битами и делает bootstrapping **на каждый гейт** — отсюда «gate bootstrapping». Каждый булев вентиль (NAND) — это гомоморфное вычисление LUT (lookup table) через **PBS** (programmable bootstrapping): зашумлённый вход «обнуляется» и одновременно применяется таблица истинности. Это даёт произвольную глубину без ручного управления шумом, но каждая операция дороже. TFHE удобен для сравнений, знаков и условных переходов — там, где BFV/CKKS неудобны. В OpenFHE переключение схем (BFV→TFHE) используется для гибридных вычислений, например при вычислении нелинейных активаций нейросети.

## Атаки и ошибки параметров

- **Слишком маленький `q`** относительно `n`: Ring-LWE становится разрешимой атакой редукции базиса (BKZ) — параметры берут по таблицам HomomorphicEncryption.org, а не на глаз.
- **Decryption oracle:** если сервис возвращает «ошибку расшифровки» на произвольный шифротекст, атакующий может уточнять шум и восстанавливать сообщение (атака класса IND-CPA-D). Никогда не отдавай результат decryption наружу.
- **Повтор секретного ключа между пользователями** и отсутствие domain separation в KDF ломает мультиключевые схемы и пороговую расшифровку.
- **Noise flooding:** при пороговой расшифровке нужно добавлять свежий шум, иначе шум раскрывает доли секрета.

## Что дальше / решение

FHE — это три оси: тип данных (целые BFV/BGV, дробные CKKS, биты TFHE), глубина схемы (шумовой бюджет) и стоимость bootstrapping. На практике схему выбирают под задачу, а параметры — по стандарту HomomorphicEncryption.org. Помни: расшифровывать может только владелец ключа, и ни один результат decryption не должен утекать наружу.

| Схема | Данные | Bootstrapping | Типичное применение |
|---|---|---|---|
| BFV | целые mod t | есть | точные вычисления, БД |
| BGV | целые mod t | есть (эффективнее по уровням) | вложенные схемы |
| CKKS | вещественные | есть | ML, статистика |
| TFHE | булевы | на каждый гейт | логика, сравнения |

## Приватное агрегирование и мультиключевое FHE

Отдельное применение FHE — считать сумму данных нескольких клиентов, не раскрывая отдельные вклады. Простейшая схема: каждый клиент шифрует своё значение открытым ключом агрегатора, сервер **складывает шифротексты** (сложение гомоморфно даже без evaluation key, потому что это покомпонентная операция над парами `(c0,c1)`), а агрегатор расшифровывает один результат. Это основа приватной аналитики и федеративного обучения. Осторожно: по двум суммам, отличающимся одним вкладом, восстанавливается этот вклад, поэтому к результату добавляют шум дифференциальной приватности (Лапласа или Гаусса) с параметром `ε`. Без него «приватное» агрегирование утекает.

## Чек-лист выбора параметров

1. Тип данных: целые → BFV/BGV, вещественные → CKKS, биты → TFHE.
2. Оцени multiplicative depth — длину самой глубокой цепочки умножений в программе.
3. Возьми параметры (`n`, `q`, цепочку уровней) из таблиц HomomorphicEncryption.org под security level 128 бит.
4. Прогони тестовую схему и проверь `invariant_noise_budget` — он не должен подходить к нулю.
5. Если глубины не хватает — включи bootstrapping или перепиши вычисление на меньшую глубину.

Типичная ошибка новичка — взять параметры «как в туториале» и не проверить, что фактическая программа укладывается в бюджет. Второй по частоте промах — перепутать `t` (модуль открытого текста) с `Δ`: для BFV при `t=1024` нужен больший `q`, иначе шум «съедает» старшие биты сообщения и результат тихо неверен, без исключения.
