## Зачем это нужно

PKI (Public Key Infrastructure) — это то, что заставляет HTTPS работать: браузер доверяет серверу не потому, что «так написано», а потому что сертификат сервера подписан доверенным удостоверяющим центром (CA), а цепочка доверия ведёт к корню, вшитому в систему. Как только проверка цепочки или расширений делается неверно, появляется возможность MITM. Именно поэтому ошибки в валидации X.509 — один из самых «урожайных» классов багов.

Для CTF X.509 встречается в задачах «подделай сертификат», «обойди проверку», «найди флаг в сертификате». Для пентеста — при анализе TLS, VPN, клиентских сертификатов и систем аутентификации.

## Структура X.509

Сертификат X.509 — это подписанная структура ASN.1 DER, содержащая:

- **tbsCertificate** (to-be-signed): версия, серийный номер, подпись-алгоритм, **issuer** (кто подписал), **validity** (notBefore/notAfter), **subject** (кому выдан), **subjectPublicKeyInfo** (открытый ключ), **extensions**.
- **signatureAlgorithm** — алгоритм подписи.
- **signatureValue** — сама подпись.

Ключевой момент: сертификат **не содержит** поле «hostname» в явном виде. Имя сервера проверяется через расширение **SAN** (Subject Alternative Name), а **CN** (Common Name) — устаревшее и не должно использоваться для проверки. Это источник многих багов: реализации, проверяющие CN вместо SAN, ломаются на сертификатах с пустым CN или неверным SAN.

Просмотр:

```bash
openssl x509 -in cert.pem -noout -text
# видим Issuer, Subject, Validity, X509v3 extensions: SAN, KeyUsage, BasicConstraints...
```

## Расширения, которые важны

- **Subject Alternative Name (SAN)** — список имён (DNS, IP, email), которым соответствует сертификат. **Единственный** корректный источник hostname.
- **Basic Constraints** (`CA:TRUE/FALSE`) — является ли сертификат CA (может ли подписывать другие).
- **Key Usage / Extended Key Usage** — для чего годится ключ (serverAuth, clientAuth).
- **Name Constraints** — ограничения на поддомены/имена, которые может подписывать промежуточный CA. Ошибки в их проверке — классика (сертификат для `example.com` подписывает `evil.com`).
- **CRL Distribution Points / OCSP** — отзыв.

Проверка цепочки должна учитывать **все** эти расширения. Пропуск любого — потенциальный баг.

## Цепочки доверия и валидация

Цепочка: `leaf (сервер) → intermediate CA → root CA (в trust store)`. Валидация:

1. Проверить подпись каждого звена вышестоящим.
2. Проверить сроки (validity).
3. Проверить, что leaf соответствует имени (SAN) и назначению (EKU).
4. Проверить Basic Constraints и Name Constraints по всей цепочке.
5. Проверить отзыв (CRL/OCSP) — часто пропускается.
6. Убедиться, что корень в trust store.

Типичные ошибки: доверие к **любому** сертификату из цепочки как к корню, отсутствие проверки Basic Constraints (лист может подписать другой лист), игнорирование Name Constraints, отсутствие hostname-проверки (или проверка CN вместо SAN).

## Certificate Transparency

**Certificate Transparency (CT)** — публичные логи всех выданных сертификатов, построенные на деревьях Меркла (см. `crypto-merkle-tree`). Каждый CA обязан логировать выданные сертификаты; браузеры требуют наличие SCT (Signed Certificate Timestamp). Это позволяет детектировать **misissuance** (неправильно выданные сертификаты) и атаки на CA. Для пентеста CT-логи — источник информации о доменах и поддоменах.

```bash
# поиск сертификатов для домена
curl -s "https://crt.sh/?q=example.com&output=json" | jq '.[].name_value'
```

## Типичные атаки на PKI

- **CN vs SAN**: если проверяется CN, можно выпустить сертификат с нужным CN и любым SAN.
- **Null byte injection**: исторически `CN=good.com\0.evil.com` обходил проверку (исправлено).
- **Wildcard-злоупотребление**: `*.example.com` не должен покрывать `example.com` или `a.b.example.com`.
- **Доверие к самоподписанным**: клиент принимает любой сертификат — MITM тривиален.
- **Отсутствие проверки отзыва**: отозванный сертификат принимается.
- **Name Constraints bypass**: сертификат промежуточного CA выходит за разрешённые имена.
- **Rogue CA**: скомпрометированный CA подписывает что угодно (DigiNotar, 2011).
- **Weak signature**: MD5/SHA-1 коллизии (см. `crypto-hash-forge`) позволяют подделать подпись CA.

## Инструменты и команды

- **`openssl`** — просмотр, проверка, генерация.
- **`certtool`** (GnuTLS), **`cfssl`** — работа с сертификатами.
- **`testssl.sh`**, **`sslscan`** — оценка цепочек.
- **`crt.sh`**, **`certspotter`** — CT-поиск.
- **`x509sak`** — статический анализ X.509-кода.

Примеры:

```bash
# проверить цепочку
openssl verify -CAfile ca.pem -untrusted intermediate.pem leaf.pem
# посмотреть SAN
openssl x509 -in leaf.pem -noout -ext subjectAltName
# извлечь цепочку с сервера
openssl s_client -connect host:443 -showcerts </dev/null
```

## Разобранный пример: обход проверки имени

Пусть приложение проверяет hostname по **CN**, а не по SAN. Атакующий:

1. Выпускает/подделывает сертификат, где `CN = target.example.com`, но `SAN = attacker.example.com` (или SAN отсутствует).
2. Подставляет его в MITM.
3. Приложение смотрит на CN, видит нужное имя и принимает сертификат.

Проверка: `openssl x509 -text` покажет, что реальный SAN не совпадает. Правильный клиент должен отклонять такой сертификат. Это классическая ошибка, встречающаяся в мобильных приложениях, IoT и самописных клиентах.

Другой пример: промежуточный CA без проверки Name Constraints подписывает сертификат для чужого домена — и цепочка «валидна», хотя должна быть отклонена.

## Отзыв сертификатов: CRL, OCSP и их проблемы

Сертификат может быть скомпрометирован до истечения срока действия, и тогда его нужно **отозвать**. Для этого существуют два механизма, и оба проблемны — что делает их частым источником уязвимостей.

**CRL (Certificate Revocation List)** — подписанный CA список отозванных серийных номеров. Клиент должен скачать CRL и проверить, нет ли там сертификата. Проблемы: CRL растут огромными (миллионы отозванных), часто устаревают, а многие клиенты их **не проверяют** (soft-fail) — если CRL не удалось загрузить, сертификат всё равно принимается.

**OCSP (Online Certificate Status Protocol)** — клиент спрашивает у OCSP-респондера статус конкретного сертификата. Проблемы: дополнительный запрос к серверу (задержка, приватность — CA видит, какие сайты вы посещаете), soft-fail по умолчанию (если респондер недоступен — принимаем), и **OCSP stapling** как решение: сервер сам приносит подписанный ответ, избавляя клиента от запроса.

Ключевая уязвимость — **soft-fail**: почти все браузеры при недоступности CRL/OCSP считают сертификат валидным. Атакующий может заблокировать доступ к респондеру (DNS/сеть) и использовать отозванный сертификат. Лечится hard-fail (принимать только при успешной проверке) или, радикально, переходом к короткоживущим сертификатам (Let's Encrypt с 90-дневным сроком) и **CRLite**/push-моделям.

Отдельная проблема — **OCSP-респондеры как точка отказа**: их компрометация позволяет пометить валидный сертификат как отозванный (DoS) или, наоборот, скрыть отзыв. Поэтому в 2020-х индустрия движется к **Certificate Transparency + короткие сроки + CRLite**, отказываясь от онлайн-проверки.

Практический вывод: при аудите клиента проверяйте, как он обрабатывает недоступность отзыва. Если soft-fail и нет pinning — перед вами потенциальная MITM-уязвимость с отозванным сертификатом. На CTF это редко, но в реальных мобильных приложениях встречается часто.

## Практика: генерация собственного CA для тестов

Для пентеста и CTF часто нужно поднять свой CA и выпустить сертификаты — например, для MITM-прокси (mitmproxy, Burp) или для evil-twin. Это делается через `openssl`:

```bash
# корневой ключ и сертификат
openssl req -x509 -newkey rsa:4096 -keyout ca.key -out ca.crt -days 3650 -nodes \
  -subj "/CN=Test CA"
# ключ и CSR для сервера
openssl req -newkey rsa:2048 -keyout srv.key -out srv.csr -nodes \
  -subj "/CN=target.local"
# подпись с SAN
openssl x509 -req -in srv.csr -CA ca.crt -CAkey ca.key -CAcreateserial \
  -out srv.crt -days 365 -extfile <(printf "subjectAltName=DNS:target.local")
```

Такой сертификат будет принят клиентом, который доверяет `ca.crt` — но **не** обычным браузером, пока CA не добавлен в trust store. На CTF это используется, когда задача даёт «доверенный» CA и просит подделать сертификат. При аудите клиента проверяйте, не доверяет ли он пользовательскому/самоподписанному CA.

## Частые ошибки и подводные камни

- **Проверять CN вместо SAN** — устаревшая и опасная практика.
- **Не проверять hostname вообще** — MITM.
- **Доверять всей цепочке** — любой сертификат как корень.
- **Игнорировать Basic Constraints** — лист подписывает лист.
- **Не проверять отзыв** — отозванные сертификаты принимаются.
- **Хардкод корня в приложении** без pinning — компрометация CA ломает всё.
- **Игнорировать wildcard-правила** — `*.example.com` покрывает слишком много.

## Контрмеры и защита

- Проверяйте hostname **только** по SAN; CN не используйте.
- Полная валидация цепочки: подписи, сроки, Basic/Name Constraints, EKU.
- Проверяйте отзыв (OCSP stapling, CRL).
- Certificate pinning для критичных клиентов.
- Мониторьте CT-логи на подозрительные сертификаты для своих доменов.
- Откажитесь от MD5/SHA-1 в подписях сертификатов.

## Что дальше / решение

X.509 соединяет `crypto-rsa-basics` (подписи), `crypto-hash-forge` (коллизии) и `crypto-tls-attacks` (транспорт). Дальше: `crypto-signature-schemes` (DSA/Schnorr), `crypto-real-world` (TLS/Kerberos). На практике для оценки PKI используйте `openssl verify`, `testssl.sh` и CT-поиск.
