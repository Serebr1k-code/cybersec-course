## Зачем это нужно

Дерево Меркла — это структура, которая позволяет эффективно доказать, что элемент входит в большой набор, зная только **корень** дерева. Это фундамент блокчейна (транзакции в блоке), распределённых систем (Git, IPFS, Cassandra, DynamoDB-антиэнтропия), систем целостности и протоколов синхронизации. Дерево Меркла надстраивается над обычной хэш-функцией, и потому в нём могут появляться уязвимости, которых нет в самой хэш-функции — что делает его отличной темой для CTF и для аудита.

Понимание дерева Меркла важно по двум причинам. Во-первых, это практичный инструмент: Merkle proof в разы меньше, чем сам набор, и потому широко применяется. Во-вторых, наивные реализации уязвимы к **second-preimage** атаке, и эту ошибку повторяют до сих пор.

## Устройство дерева Меркла

Дерево Меркла — бинарное дерево, где:

- **Листья** — хэши элементов данных: `leaf_i = H(data_i)`.
- **Внутренние узлы** — хэш конкатенации двух детей: `parent = H(left || right)`.
- **Корень** — единственное значение, представляющее весь набор.

Если данных нечётное число, последний лист обычно дублируется (или используется другая стратегия — об этом ниже).

Пример для четырёх элементов `A, B, C, D`:

```
        root = H(hAB || hCD)
       /                    \
   hAB = H(hA||hB)      hCD = H(hC||hD)
   /        \            /        \
 hA        hB          hC        hD
 A         B           C         D
```

Любое изменение любого элемента меняет его хэш, затем родителя, и в итоге корень. Поэтому корень — это «отпечаток» всего набора, который можно безопасно публиковать.

## Доказательство включения (Merkle proof)

Чтобы доказать, что элемент `C` входит в дерево, достаточно предоставить **путь** от листа к корню: для каждого уровня — хэш «брата». Для `C` это `hD`, `hAB`, и корень вычисляется как `H(hAB || H(hC || hD))`. Проверяющий пересчитывает корень и сравнивает с известным.

Размер доказательства — `O(log n)` хэшей. Для миллиона элементов это всего 20 хэшей вместо миллиона. Именно это делает деревья Меркла незаменимыми в блокчейне и распределённых системах.

```python
import hashlib

def H(*parts):
    h = hashlib.sha256()
    for p in parts:
        h.update(p)
    return h.digest()

def merkle_root(leaves):
    if len(leaves) == 1:
        return leaves[0]
    if len(leaves) % 2:
        leaves = leaves + [leaves[-1]]   # дублирование последнего
    nxt = [H(leaves[i], leaves[i+1]) for i in range(0, len(leaves), 2)]
    return merkle_root(nxt)

def merkle_proof(leaves, index):
    proof = []
    while len(leaves) > 1:
        if len(leaves) % 2:
            leaves = leaves + [leaves[-1]]
        sib = index ^ 1
        proof.append(leaves[sib])
        leaves = [H(leaves[i], leaves[i+1]) for i in range(0, len(leaves), 2)]
        index //= 2
    return proof
```

Проверка:

```python
def verify(leaf, proof, root, index):
    h = leaf
    for sib in proof:
        if index % 2 == 0:
            h = H(h, sib)
        else:
            h = H(sib, h)
        index //= 2
    return h == root
```

## Second-preimage и CVE-2012-2459

Наивное дублирование последнего листа создаёт уязвимость. Если узел имеет только одного ребёнка, и реализация дублирует его, то `H(x || x)` может совпасть для разных структур. В Bitcoin это привело к **CVE-2012-2459**: атакующий мог сформировать два разных списка транзакций с одинаковым корнем Меркла, что ломало проверки (в частности, возможность «сжечь» блок или обойти валидацию).

Причина — **отсутствие доменного разделения**: лист и внутренний узел хэшируются одинаково, и `H(H(a)||H(b))` для внутреннего узла может быть равен `H(leaf)` для подходящего листа. Правильные реализации добавляют префиксы:

```
leaf  = H(0x00 || data)
node  = H(0x01 || left || right)
```

Это гарантирует, что лист и внутренний узел никогда не дадут одинаковый хэш, и атака second-preimage не проходит. Именно так сделано в RFC 6962 (Certificate Transparency) и в современных Merkle-реализациях.

Другой источник проблем — **неоднозначность длины**: если `H(a||b)` конкатенирует данные без разделителя, разные пары могут дать коллизию при переменной длине. Префиксы и фиксированные длины решают это.

## Применение в блокчейне и распределённых системах

- **Bitcoin/Ethereum**: корень Меркла транзакций в заголовке блока; Merkle proof позволяет SPV-клиенту доказать включение транзакции без полной цепочки.
- **Git**: каждый объект — хэш; дерево каталогов — это фактически Merkle-структура (tree objects), что даёт целостность репозитория.
- **IPFS**: контент адресуется по хэшу; DAG строится из хэшей блоков.
- **Cassandra/DynamoDB**: Merkle-деревья для антиэнтропии (сравнение реплик) — различающиеся поддеревья синхронизируются, совпадающие пропускаются.
- **Certificate Transparency**: лог сертификатов с Merkle-деревом, доказательства включения и непротиворечивости.

Общая идея одна: заменить сравнение/передачу всего набора сравнением `O(log n)` хэшей.

## Инструменты и команды

- **Python** — собственная реализация (см. выше) или библиотеки `merkletools`, `pymerkle`.
- **`merkle-proof`** — CLI для генерации/проверки.
- **Ethereum-инструменты** — `ethers.js`/`web3.py` для Merkle proof в контрактах.
- **`ct`-логи** — Certificate Transparency API для доказательств.

Пример с `pymerkle`:

```python
from pymerkle import MerkleTree
t = MerkleTree()
for x in [b'A', b'B', b'C', b'D']:
    t.append_entry(x)
print(t.get_root_hash().hex())
proof = t.prove_inclusion(b'C')
print(t.verify_inclusion(b'C', proof))
```

## Разобранный пример: атака на наивное дерево

Пусть дерево реализовано без префиксов: `leaf = H(data)`, `node = H(l || r)`. Для набора из двух элементов `[A, B]` корень = `H(H(A) || H(B))`. Атакующий подбирает `A', B'` так, что `H(A') = H(A) || H(B)`... — на практике это требует second-preimage хэша (сложно), но при **дублировании** и переменной длине появляются более простые неоднозначности: набор `[A, B, C]` и `[A, B, C, C]` могут дать одинаковый корень из-за дублирования `C`. Это и есть класс CVE-2012-2459.

Практический вывод: при аудите Merkle-реализации проверяйте (1) есть ли доменное разделение leaf/node, (2) как обрабатывается нечётное число листьев, (3) нет ли неоднозначности из-за дублирования. Отсутствие любого из этих пунктов — потенциальная уязвимость.

## Лёгкие клиенты и Merkle proof в действии

Главная практическая ценность дерева Меркла — возможность **лёгкого клиента**. Полный узел блокчейна хранит весь блок и все транзакции; лёгкий (SPV) клиент хранит только заголовки блоков (по сути, корни Меркла). Когда ему нужно убедиться, что транзакция включена в блок, полный узел присылает **Merkle proof** — путь из `log n` хэшей. Клиент пересчитывает корень и сравнивает с тем, что в заголовке. Если совпало — транзакция действительно в блоке, и всё это без загрузки мегабайтов данных.

Эта же идея лежит в основе **антиэнтропии** распределённых баз (Cassandra, DynamoDB, Riak). Две реплики сравнивают корни своих деревьев; если корни совпадают — данные идентичны, синхронизация не нужна. Если нет — они спускаются по различающимся подветвям, пока не найдут конкретные расходящиеся элементы. Вместо передачи всей таблицы передаются только различия — колоссальная экономия.

**Certificate Transparency** применяет деревья Меркла к логам сертификатов: каждый сертификат — лист, корень публикуется, а любой желающий может проверить, что сертификат включён в лог (proof of inclusion) и что новые версии лога согласованы со старыми (proof of consistency). Это позволяет детектировать подозрительные сертификаты.

Общий принцип для всех применений: дерево Меркла заменяет «сравнить/передать всё» на «сравнить `O(log n)` хэшей». Понимание этого принципа помогает и строить системы, и находить в них ошибки: почти все баги Merkle-реализаций — это либо отсутствие доменного разделения, либо неверная обработка нечётного числа листьев, либо путаница между proof of inclusion и proof of consistency.

## Частые ошибки и подводные камни

- **Отсутствие доменного разделения** leaf/node — second-preimage.
- **Наивное дублирование последнего листа** — CVE-2012-2459.
- **Конкатенация без разделителя/длины** — коллизии при переменной длине.
- **Путать Merkle proof и полный набор** — proof доказывает включение, но не полноту.
- **Не проверять порядок** `left || right` — proof должен знать, с какой стороны брат.
- **Использовать слабый хэш** (MD5) — коллизии ломают дерево.

## Контрмеры и защита

- Доменное разделение: `H(0x00||data)` для листьев, `H(0x01||l||r)` для узлов.
- Явная обработка нечётного числа листьев без неоднозначного дублирования.
- Фиксированная длина полей или явные разделители.
- Криптостойкая хэш-функция (SHA-256, SHA-3).
- Проверка proof относительно доверенного корня, а не относительно самого proof.

## Что дальше / решение

Деревья Меркла — мост к блокчейн-криптографии и системам целостности. Дальше: `crypto-sponge` (другая структура хэширования), `crypto-hash-forge` (коллизии), `crypto-pairing` (ZK-конструкции на деревьях). На CTF ищите отсутствие доменного разделения и ошибки дублирования — это самые частые «щели» в Merkle-задачах.
