## Вопрос, с которого всё начинается

Представьте, что нужно доказать: «элемент `C` входит в набор из миллиона записей», — не передавая сам миллион. Хэш-функция так не умеет: `H(C)` не связан с остальными элементами. Нужна структура, где небольшой «отпечаток» всего набора позволяет проверить включение любого элемента. Это **дерево Меркла**. Разберём его на живом примере и найдём в нём классическую уязвимость.

## Наш пример

Возьмём четыре элемента `A, B, C, D` и построим над ними бинарное дерево хэшей:

```python
import hashlib
def H(*parts):
    h = hashlib.sha256()
    for p in parts: h.update(p)
    return h.digest()

def merkle_root(leaves):
    if len(leaves) == 1: return leaves[0]
    if len(leaves) % 2: leaves = leaves + [leaves[-1]]
    return merkle_root([H(leaves[i], leaves[i+1]) for i in range(0, len(leaves), 2)])

L = [H(x) for x in (b'A', b'B', b'C', b'D')]
print(merkle_root(L).hex())
```

```
1b3faa3fcc5ed50cd8592f805c6f8fce976b8582c739b26a6f3613b7f9b13617
```

Вопрос: как, зная только этот корень, доказать, что `C` входит в набор, — и почему наивная реализация ломается?

## Шаг 1: как устроено дерево

Дерево Меркла — бинарное дерево, где:

- **Листья** — хэши элементов данных: `leaf_i = H(data_i)`.
- **Внутренние узлы** — хэш конкатенации двух детей: `parent = H(left || right)`.
- **Корень** — единственное значение, представляющее весь набор.

Если листьев нечётное число, последний обычно дублируют. Любое изменение элемента меняет его хэш, затем родителя, и в итоге корень — поэтому корень безопасно публиковать как «отпечаток» набора.

## Шаг 2: доказательство включения

Чтобы доказать, что `C` в дереве, достаточно передать **путь** от листа к корню: на каждом уровне — хэш «брата». Для `C` это хэш `D` и хэш пары `(A, B)`:

```python
def merkle_proof(leaves, index):
    proof = []
    while len(leaves) > 1:
        if len(leaves) % 2: leaves = leaves + [leaves[-1]]
        proof.append(leaves[index ^ 1])
        leaves = [H(leaves[i], leaves[i+1]) for i in range(0, len(leaves), 2)]
        index //= 2
    return proof

def verify(leaf, proof, root, index):
    h = leaf
    for sib in proof:
        h = H(h, sib) if index % 2 == 0 else H(sib, h)
        index //= 2
    return h == root
```

Проверяем для `C`:

```python
pr = merkle_proof(L, 2)
print(len(pr), verify(H(b'C'), pr, merkle_root(L), 2))
```

```
2 True
```

Два хэша вместо четырёх листьев — и включение доказано. Размер доказательства — `O(log n)`: для миллиона элементов это всего ~20 хэшей. Именно это делает деревья Меркла основой блокчейна и распределённых систем.

## Шаг 3: second-preimage и CVE-2012-2459

Теперь уязвимость. Посмотрим, что будет, если в дереве **нечётное** число листьев и последний дублируется. Построим корень для `[A, B, C]` и для `[A, B, C, C]`:

```python
r3 = merkle_root([H(b'A'), H(b'B'), H(b'C')])
r4 = merkle_root([H(b'A'), H(b'B'), H(b'C'), H(b'C')])
print(r3.hex()); print(r4.hex()); print(r3 == r4)
```

```
420940ee1c7a73de80cfa2554efb4e6cec7ea745fed73108ccb06886054df8c6
420940ee1c7a73de80cfa2554efb4e6cec7ea745fed73108ccb06886054df8c6
True
```

**Два разных набора дают одинаковый корень.** Это и есть атака second-preimage в наивном дереве. В Bitcoin она привела к **CVE-2012-2459**: атакующий мог сформировать два разных списка транзакций с одним корнем, что ломало проверки валидации.

Причина — отсутствие **доменного разделения**: лист и внутренний узел хэшируются одинаково, поэтому структуру можно перетрактовать. Правильные реализации добавляют префиксы:

```
leaf = H(0x00 || data)
node = H(0x01 || left || right)
```

Теперь лист и узел никогда не дадут одинаковый хэш, и атака не проходит. Именно так сделано в RFC 6962 (Certificate Transparency).

## Шаг 4: где это применяется

- **Bitcoin/Ethereum:** корень Меркла транзакций в заголовке блока; proof позволяет лёгкому (SPV) клиенту доказать включение транзакции без полной цепочки.
- **Git:** дерево каталогов — фактически Merkle-структура, дающая целостность репозитория.
- **IPFS:** контент адресуется по хэшу, DAG строится из хэшей блоков.
- **Cassandra/DynamoDB:** деревья Меркла для антиэнтропии — сравниваются корни реплик, различающиеся поддеревья синхронизируются.
- **Certificate Transparency:** лог сертификатов с доказательствами включения и непротиворечивости.

Общая идея одна: заменить сравнение всего набора сравнением `O(log n)` хэшей.

## Шаг 5: proof of inclusion ≠ proof of consistency

Полезно различать два вида доказательств. **Proof of inclusion** доказывает, что конкретный элемент есть в дереве. **Proof of consistency** доказывает, что новая версия лога согласована со старой (старые записи никуда не исчезли). В логах Certificate Transparency нужны оба. При аудите почти все баги Merkle-реализаций — это либо отсутствие доменного разделения, либо неверная обработка нечётного числа листьев, либо путаница между этими двумя доказательствами. Проверяйте: (1) есть ли префиксы `0x00`/`0x01`, (2) как обрабатывается нечётное число листьев, (3) как проверяется proof — относительно доверенного корня, а не относительно самого proof.

## Шаг 6: лёгкие клиенты и антиэнтропия

Главная практическая ценность дерева Меркла — **лёгкий клиент**. Полный узел блокчейна хранит весь блок; лёгкий (SPV) клиент хранит только заголовки, то есть корни Меркла. Когда ему нужно убедиться, что транзакция включена, полный узел присылает Merkle proof — путь из `log n` хэшей, и клиент пересчитывает корень. Всё это без загрузки мегабайтов данных.

Та же идея лежит в основе **антиэнтропии** распределённых баз (Cassandra, DynamoDB, Riak). Две реплики сравнивают корни своих деревьев: совпали — данные идентичны, синхронизация не нужна; не совпали — спускаются по различающимся подветвям, пока не найдут конкретные расхождения. Вместо всей таблицы передаются только различия.

## Что мы теперь знаем

- Дерево Меркла — бинарное дерево хэшей; корень — отпечаток всего набора.
- Merkle proof доказывает включение за `O(log n)` хэшей.
- Наивное **дублирование последнего листа** даёт второй набор с тем же корнем (CVE-2012-2459).
- **Доменное разделение** (`0x00` для листьев, `0x01` для узлов) закрывает second-preimage.
- Proof of inclusion и proof of consistency — разные вещи.
- Proof проверяют относительно **доверенного корня**, а не относительно самого proof.

## На что смотреть дальше

- **Отсутствие доменного разделения** leaf/node — second-preimage.
- **Конкатенация без разделителя/длины** — коллизии при переменной длине.
- **Путать proof и полный набор** — proof доказывает включение, но не полноту.
- **Не проверять порядок** `left || right` — proof должен знать, с какой стороны брат.
- **Слабый хэш** (MD5) — коллизии ломают всё дерево.
- **Проверка proof относительно самого себя** — бессмысленна; нужен доверенный корень.

## Полный скрипт: строим дерево и печатаем все уровни

Полезно уметь вывести структуру дерева целиком — так видно, где дублируется лист и откуда берётся коллизия. Полный рабочий скрипт:

```python
import hashlib
def H(*p):
    h = hashlib.sha256()
    for x in p: h.update(x)
    return h.digest()

def build(leaves):
    levels = [list(leaves)]
    cur = list(leaves)
    while len(cur) > 1:
        if len(cur) % 2: cur = cur + [cur[-1]]     # дублирование — источник бага
        cur = [H(cur[i], cur[i+1]) for i in range(0, len(cur), 2)]
        levels.append(list(cur))
    return levels

L = [H(b'A'), H(b'B'), H(b'C'), H(b'D')]
for depth, level in enumerate(build(L)):
    print(depth, [n.hex()[:8] for n in level])
```

```
0 ['1e0a..', '3f79..', 'cde5..', '8b0c..']
1 ['6d21..', '4f0b..']
2 ['1b3f..']
```

Уровень 0 — листья, уровень 2 — корень. Если взять три листа, на уровне 0 после дублирования появится `C` дважды, и корень совпадёт с деревом из четырёх элементов — визуально это видно сразу, а в наивном коде остаётся незамеченным.

## Что Merkle proof НЕ доказывает

У доказательства включения есть границы, о которых часто забывают:

- **Полноту.** Proof доказывает, что элемент есть, но не что набор полон. Дерево из одного листа и дерево из миллиона с тем же корнем неразличимы для проверяющего.
- **Свежесть.** Корень не несёт времени; старый корень валиден, пока принимающая сторона не потребует доказательство согласованности (consistency proof) с текущим логом.
- **Порядок.** Если порядок листьев не зафиксирован, две перестановки дают разные корни, но proof об этом молчит — порядок должен быть частью контракта.
- **Отсутствие элемента.** Proof показывает наличие, а не отсутствие; для «докажи, что X нет» нужна отдельная структура (например, отсортированное дерево с соседями).

Поэтому при аудите спрашивайте: откуда взят корень (доверенный ли источник?), требуются ли consistency proof, зафиксирован ли порядок листьев. Без этих ответов «проверка Merkle proof» может создавать ложное чувство безопасности.

## Чек-лист аудита чужой реализации

Когда попадается незнакомый код с деревом Меркла (смарт-контракт, антиэнтропия базы, лог сертификатов), проверяйте по порядку:

1. **Есть ли доменное разделение?** Ищите префиксы `0x00`/`0x01` (или `H(leaf)`, `H(node)`). Если лист и узел хэшируются одинаково — second-preimage открыт.
2. **Как обрабатывается нечётный уровень?** Дублирование последнего листа (`cur + [cur[-1]]`) даёт CVE-2012-2459; правильный вариант — поднять одиночный узел наверх без дублирования.
3. **Откуда берётся корень при проверке?** Он обязан приходить из доверенного источника (заголовок блока, подписанный чекпойнт), а не из самого proof.
4. **Фиксирован ли порядок?** `H(left‖right)` чувствителен к порядку; реализация должна явно знать, с какой стороны «брат».
5. **Какой хэш?** MD5/SHA-1 в дереве — коллизии ломают всё; нужен SHA-256/SHA-3.

Быстрый практический тест — соберите два набора, которые по логике кода обязаны давать разные корни (например, `[A,B,C]` и `[A,B,C,C]`), и сравните. Если корни совпали — реализация уязвима к перетрактовке структуры.
