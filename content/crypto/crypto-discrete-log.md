## Вопрос, с которого всё начинается

В протоколе Диффи–Хеллмана и в схеме ElGamal открытый ключ — это `h = g^x mod p`, а секрет — показатель `x`. Восстановить `x` из `g`, `h` и `p` — это задача **дискретного логарифмирования** (dlog). При больших правильно выбранных параметрах она нерешаема. Но в CTF параметры почти всегда слабые, и тогда `x` находится. Разберём три метода, которые покрывают 90% таких задач.

## Наш пример

Возьмём конкретную задачу:

```
p = 1000003  g = 2  h = 435147
```

Нужно найти `x`, такое что `2^x mod 1000003 = 435147`. Проверим сначала порядок `g` — сколько разных значений он порождает.

## Шаг 1: перебор — почему это дорого

Наивный способ — считать `g^0, g^1, g^2, …`, пока не совпадёт с `h`. В худшем случае это `order` шагов. Для нашего примера:

```
order of g = 1000002
```

Миллион операций — терпимо для демонстрации, но при `p` в 80 бит перебор занимает миллиарды лет. Нужны методы со сложностью порядка `√order`, а не `order`.

## Шаг 2: метод «шаг младенца — шаг великана» (BSGS)

Идея: представить `x = i·m + j`, где `m ≈ √order`. Тогда

```
g^x = g^(i·m + j) = h   ⟺   g^j = h · (g^(−m))^i
```

Слева — значения, зависящие только от `j` (их «маленькие шаги»), справа — только от `i` («великанские»). Строим таблицу всех `g^j` для `j = 0…m−1`, затем перебираем `i`, умножая `h` на `g^(−m)`, и ищем совпадение в таблице.

Память — `√order`, время — `√order`. Запускаем:

```
BSGS recovered x = 123456  match: True
```

Миллион шагов заменился тысячей. Обрати внимание: BSGS требует памяти `O(√n)` — если памяти мало, берут метод Полларда rho (та же скорость, но без хранения таблицы).

## Шаг 3: гладкий порядок и Полига–Хеллман

Самое важное в dlog — **порядок группы**. Если `order` раскладывается на маленькие простые множители, задача распадается на несколько лёгких. Для нашего `g`:

```
factorization of order: {2: 1, 3: 1, 166667: 1}
```

Алгоритм **Полига–Хеллмана** работает так:

1. Для каждого простого множителя `q^k` порядка решаем dlog в маленькой подгруппе (можно даже перебором, если `q` мал).
2. Получаем `x mod q^k` для всех `q`.
3. Собираем `x` из этих остатков по **китайской теореме об остатках (CRT)**.

Сложность определяется **самым большим** простым множителем порядка, а не самим порядком. Если `order = 2·3·166667`, то всё сводится к dlog в подгруппе размера 166667 — а это `√166667 ≈ 408` шагов. Именно поэтому в реальных протоколах требуют, чтобы порядок подгруппы был большим простым числом (или содержал большой простой множитель).

## Шаг 4: index calculus — когда порядок не гладкий

Если порядок — большое простое число, Полига–Хеллман не помогает. Тогда для мультипликативной группы простого поля работает **index calculus**:

- выбирают **факторную базу** — множество маленьких простых чисел;
- ищут соотношения, где `g^k mod p` раскладывается на эту базу (это линейные уравнения на логарифмы базы);
- решают систему по модулю `order` и получают логарифм `h`.

Сложность субэкспоненциальная. Для эллиптических кривых аналога нет — поэтому ECC при меньшем ключе даёт ту же стойкость, что RSA/DH. Практически в CTF index calculus почти не встречается (слишком сложен), но знать, что он существует, нужно: именно он делает DH в поле `F_p` слабее, чем ECC того же размера.

## Шаг 5: как распознать метод

Порядок действий при виде `g^x = h mod p`:

1. Проверь `p`: если маленькое — перебор или BSGS.
2. Разложи порядок `g` на множители: если гладкий — Полига–Хеллман (обычно это и есть ответ).
3. Если порядок большой и простой, а `p` небольшое (до ~90 бит) — index calculus или готовые тулзы (`sage`, `cado-nfs`).
4. Если `g` порождает маленькую подгруппу — это уже не dlog, а атака на малую подгруппу (отдельный урок про DH).

## Шаг 6: полный прогон от начала до конца

Соберём всё в одну историю. Дано `p = 1000003`, `g = 2`, `h = 435147`.

1. **Проверяем порядок.** Считаем, за сколько шагов `g` возвращается в 1: `order = 1000002`. Это подсказка: число `1000002` имеет вид `2 · 3 · 166667`.
2. **Разлагаем порядок.** `166667` — простое. Значит, самая тяжёлая подзадача — dlog в подгруппе размера `166667`.
3. **Решаем BSGS.** Берём `m = ⌈√1000002⌉ = 1001`. Строим таблицу `2^j` для `j = 0…1000`, затем идём «великанами»: умножаем `h` на `2^(−1001)` и ищем совпадение. Находим `x = 123456`.
4. **Проверяем.** `pow(2, 123456, 1000003) = 435147` — верно.

Если бы порядок был гладким, шаг 3 заменился бы на Полига–Хеллмана: решаем dlog в каждой маленькой подгруппе отдельно (там хватит перебора) и собираем ответ по CRT. Именно поэтому «гладкий порядок = слабый dlog».

## Шаг 7: Полларда rho — та же скорость, но без памяти

BSGS хранит таблицу из `√order` элементов. При большом `order` это сотни мегабайт. Метод
**Полларда rho** решает dlog за то же `O(√order)` времени, но почти без памяти — он ищет
**коллизию** в последовательности вида `g^a · h^b`:

```python
from math import gcd
def pollard_rho(g, h, p, order):
    def f(x, a, b):
        if x % 3 == 0: return (x*x % p, 2*a % order, 2*b % order)
        if x % 3 == 1: return (x*g % p, (a+1) % order, b)
        return (x*h % p, a, (b+1) % order)
    x, a, b = 1, 0, 0
    X, A, B = x, a, b
    while True:
        x, a, b = f(x, a, b)
        X, A, B = f(*f(X, A, B))
        if x == X:                       # g^a h^b == g^A h^B
            num, den = (a - A) % order, (B - b) % order
            if gcd(den, order) == 1:
                return num * pow(den, -1, order) % order
```

Идея та же, что в «парадоксе дней рождения»: последовательность «зацикливается» за ~`√order` шагов, и
первая коллизия даёт уравнение на `x`. Памяти нужно константно. На практике `rho` используют, когда
`order` большой, но всё же поддаётся `√`-атаке (до ~2^80).

## Как это видят защитники

Стойкость dlog — это вопрос **выбора параметров**, и защита проверяет именно их:

- **размер `p`** — для DH/ElGamal в `F_p` рекомендуется `p ≥ 2048` бит;
- **порядок подгруппы** — должен содержать большой простой множитель (не гладкий), иначе
  Полига–Хеллман ломает за секунды;
- **safe prime** — `p = 2q + 1`, чтобы гладкая часть была минимальной;
- **не использовать экспортные группы** (512/1024 бит) — они ломаются.

Для атакующего это чек-лист: сначала разложи порядок, и только если он содержит большой простой
множитель — переходи к `rho`/index calculus. «Слабый dlog» почти всегда означает «гладкий порядок».

## Шаг 8: выбираем метод по условию

Сведём выбор метода в одну таблицу — так решение задачи занимает минуты:

| Что видим | Метод |
|---|---|
| маленькое `p` (до 2^40) | BSGS или перебор |
| гладкий порядок `g` | Полига–Хеллман |
| большой порядок, но ≤ 2^80 | Полларда rho (без памяти) |
| порядок — большое простое, `p` ≤ 90 бит | index calculus (`sage`, `cado-nfs`) |
| `g` малого порядка | атака на малую подгруппу (не dlog) |

Практический порядок: сначала **разложи порядок `g`**. Если он гладкий — Полига–Хеллман решает всё.
Если нет, но `p` малое — BSGS/rho. Только если оба условия против тебя, переходи к index calculus.

## Что мы теперь знаем

- **Dlog** — восстановление показателя `x` из `g^x = h mod p`.
- **BSGS** решает задачу за `O(√order)` по времени и памяти.
- **Полига–Хеллман** разбивает задачу по простым множителям порядка и собирает ответ через CRT.
- Стойкость DH зависит от **наибольшего простого множителя порядка**, а не от размера `p`.
- **Index calculus** работает только в мультипликативных группах полей, не в ECC.
- **Полларда rho** даёт ту же `O(√order)`, что BSGS, но без хранения таблицы — выбор при нехватке памяти.

## На что смотреть дальше

- **Продвинутый DH** — малые подгруппы, invalid-curve и Logjam.
- **Эллиптические кривые** — dlog на кривой и почему он труднее.
- **Метод Полларда rho** — `√n` без памяти.

## Куда дальше

В следующем уроке мы перейдём к **эллиптическим кривым**: научимся складывать точки, считать скалярное умножение и поймём, почему ECDLP труднее обычного dlog. А пока запомни главное: **сложность dlog определяется наибольшим простым множителем порядка группы**, и слабые параметры в CTF ломаются за секунды.

## Где пригодится

- **CTF (crypto)** — большинство задач на DH и ElGamal решаются BSGS или Полига–Хеллманом.
- **Аудит протоколов** — проверка, что порядок подгруппы содержит большой простой множитель.
- **Понимание ECC** — dlog на кривой — та же задача, но в другой группе.
- **Исторические атаки** — Logjam и слабые DH-параметры эксплуатируют именно гладкость порядка.
