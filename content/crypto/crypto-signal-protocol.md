## Вопрос, с которого всё начинается

Ты пользуешься мессенджером, и он обещает, что даже сервер не прочитает переписку. Но у сторон нет общего пароля — только ключи, которые они опубликовали заранее. Как из «чужих публичных ключей» получить один общий секрет так, чтобы сервер, видевший все сообщения, его не узнал? Ответ даёт протокол **X3DH** (Extended Triple Diffie-Hellman) — часть Signal. Разберём его на конкретном рукопожатии.

## Наш пример: одно рукопожатие

Представим, что Алиса хочет написать Бобу. У каждого есть долговременный **identity key** (IK) — это его «личный» асимметричный ключ, аналог публичного ключа в PGP. Кроме него у Боба на сервере лежат заранее загруженные ключи:

```
IK_B  identity key Боба
SPK_B signed prekey Боба (подписан IK_B)
OPK_B one-time prekey Боба (одноразовый, стирается после использования)
```

Алиса генерирует свой одноразовый ключ `EK_A` (ephemeral) и считает четыре общих секрета Диффи-Хеллмана. Термин **DH** (Diffie-Hellman) ты уже знаешь: двое поднимают общий секрет `g^(ab)` по обмену `g^a` и `g^b`. Здесь DH считается сразу несколько раз — это и есть «triple/quadruple DH».

## Шаг 1: считаем DH-ы

X3DH задаёт четыре комбинации (по мотивам спецификации):

```
DH1 = DH(IK_A, SPK_B)
DH2 = DH(EK_A, IK_B)
DH3 = DH(EK_A, SPK_B)
DH4 = DH(EK_A, OPK_B)
```

Зачем четыре? Каждый даёт разную гарантию. `DH1` привязывает Алису к долговременному ключу Боба, `DH2` — Боба к долговременному ключу Алисы, `DH3`/`DH4` добавляют эфемерность. Вместе они означают: чтобы вычислить секрет, нужен **хотя бы один приватный ключ**, который сервер не знает. Сервер видел только публичные ключи и `EK_A` — общий секрет ему недоступен.

Возьмём маленькие числа, чтобы посчитать руками. Пусть `p = 2^521 - 1` (простое Мерсенна), `g = 2`. В реальном Signal используется Curve25519, но арифметика DH одинакова.

## Шаг 2: склеиваем и прогоняем через KDF

Четыре общих секрета нельзя просто сложить — их конкатенируют и пропускают через **KDF** (key derivation function), здесь HKDF-SHA256:

```
SK = HKDF( F || DH1 || DH2 || DH3 || DH4 )
```

где `F` — строка доменной сепарации из 32 байт `0xFF`, чтобы этот общий секрет нельзя было перепутать с секретом из другого протокола. **Доменная сепарация** — это когда в хэш подмешивают метку «это именно X3DH, версия 1», чтобы один и тот же ключ не переиспользовался в двух контекстах. Без неё возможны атаки подстановки между протоколами.

## Шаг 3: Double Ratchet

Получив начальный `SK`, стороны переходят к **Double Ratchet** — механизму, который меняет ключ шифрования на каждое сообщение. Идея: после каждого сообщения ключ «прокручивается» через хэш (симметричный ratchet), а при каждой смене направления добавляется новый DH (DH ratchet). В терминах: **forward secrecy** — если ключ украли сегодня, прошлые сообщения не прочитать, потому что старые ключи уже стёрты; **post-compromise security** — после следующего DH-шага атакующий, знавший старый ключ, теряет доступ.

Ключевое: цепочка ключей однонаправленна. Из текущего ключа легко получить следующий (`k' = HMAC(k, 0x02)`), а из следующего предыдущий — нет (HMAC необратим). Поэтому украденный сегодня ключ не отматывает историю.

## Полный прогон

В лабе даны `dh.txt` с параметрами и публичными ключами, `msg.enc` (шифротекст, XOR с keystream из HKDF) и скрипт `x3dh.py`. Скрипт считает четыре DH, конкатенирует с `F`, выводит `SK` через HKDF и расшифровывает сообщение:

```
$ python3 x3dh.py
DH1 = ...
DH2 = ...
DH3 = ...
DH4 = ...
SK  = 7c1e... (32 bytes)
plaintext: nto{x3dh_d0ubl3_r4tch3t_sh4r3d_s3cr3t}
```

## Если не сработало

Если вместо четырёх DH в протоколе используется один (упрощённый DH), проверь, не потерялась ли эфемерность — тогда компрометация долговременного ключа раскроет всю сессию. Если HKDF даёт другой результат, сверь порядок конкатенации и наличие `F`: порядок байтов критичен. Если сервер может вычислить секрет — значит, в списке DH остался только публичный материал.

## Signal: двойной ratchet

Signal использует **двойной ratchet**: (1) **Diffie-Hellman ratchet** — при обмене новыми DH-ключами обновляется корневой ключ (forward secrecy); (2) **symmetric ratchet** — цепочка симметричных ключей для каждого сообщения (KDF chain), что даёт post-compromise security. Каждое сообщение шифруется своим ключом.

```text
root key + DH ratchet -> chain keys -> message keys (per message)
```

Свойства: **forward secrecy** (старые сообщения не читаются после компромисса) и **post-compromise security** (после смены ключей связь восстанавливается).

## X3DH и установка сессии

X3DH (Extended Triple Diffie-Hellman) устанавливает общий секрет из нескольких DH-обменов: identity key, signed prekey, one-time prekey. Это даёт аутентификацию и forward secrecy с самого начала, даже если получатель офлайн (его prekeys лежат на сервере).

```text
DH1..DH4 -> shared secret SK; init double ratchet
```

Ключевое: сервер хранит только публичные prekeys, а сессия устанавливается без онлайн-участия получателя.

## Практика: атаки и ограничения

Атаки/ограничения: (1) **компромисс устройства** даёт доступ к текущим сообщениям (не к старым — forward secrecy); (2) **метаданные** не защищены (кто, когда, сколько); (3) **слабый RNG** ломает всю схему; (4) **компромисс сервера** даёт список prekeys и метаданные. Инструменты: анализ реализации (libsignal), тесты.

```text
device compromise -> current msgs; metadata always visible
```

Практика: проверяй генерацию ключей, обработку prekeys, защиту метаданных (sealed sender).

## Разбор: четыре DH и HKDF по шагам

Посчитаем на маленьком поле, чтобы увидеть, что именно склеивается в общий секрет. Возьмём `p = 101`, `g = 2` (в реальности — Curve25519, но арифметика та же).

```
Приватные ключи (игрушечные):
IK_A = 5   EK_A = 7                 (у Алисы)
IK_B = 11  SPK_B = 13  OPK_B = 17   (у Боба)

Публичные: IK_A_pub = 2^5 = 32, EK_A_pub = 2^7 = 27, ...
```

Теперь четыре DH. `DH(X, Y_pub) = Y_pub^X mod p`:

```
DH1 = DH(IK_A, SPK_B) = 13^5 mod 101 = 79
DH2 = DH(EK_A, IK_B)  = 11^7 mod 101 = 30
DH3 = DH(EK_A, SPK_B) = 13^7 mod 101 = 82
DH4 = DH(EK_A, OPK_B) = 17^7 mod 101 = 72
```

Каждую сторону можно посчитать двумя способами: Алиса — своим приватным ключом, Боб — своим. Например, `DH1 = SPK_B^{IK_A} = (g^{spk_b})^{IK_A} = g^{spk_b·IK_A}`, и то же самое Боб получает как `IK_A_pub^{spk_b}`. Общий секрет:

```
SK = HKDF-SHA256( F(0xFF*32) || 79 || 30 || 82 || 72 )
```

`F` из 32 байт `0xFF` — доменная сепарация: она не даёт этому секрету совпасть с секретом из любого другого протокола, даже если DH-значения случайно совпали. Дальше `SK` инициализирует корневой ключ Double Ratchet.

## Таблица: что даёт каждый DH

| Компонент | Выражение | Что гарантирует | Если убрать |
|---|---|---|---|
| DH1 | `DH(IK_A, SPK_B)` | привязка к долговременному ключу Боба | Алиса не аутентифицирует Боба |
| DH2 | `DH(EK_A, IK_B)` | привязка к долговременному ключу Алисы | Боб не аутентифицирует Алису |
| DH3 | `DH(EK_A, SPK_B)` | эфемерность со стороны Алисы | теряется forward secrecy первой сессии |
| DH4 | `DH(EK_A, OPK_B)` | одноразовость (prekey стирается) | теряется защита от replay prekey |

Если все четыре урезать до одного (`DH1`), протокол деградирует до обычного аутентифицированного DH: нет forward secrecy, и компрометация долговременного ключа раскрывает всю переписку. Именно комбинация «identity + ephemeral + one-time» даёт Signal его свойства.

## Границы и подводные камни

- **Prekey-истощение.** `OPK` одноразовые; если сервер отдал их все, новая сессия строится без `DH4` — безопасность падает, но не ломается. Атакующий может намеренно «сжечь» prekeys, чтобы заставить систему работать в ослабленном режиме.
- **Слабый RNG ломает всё.** Если `EK_A` сгенерирован предсказуемо, все DH с участием `EK_A` вычисляются атакующим, и forward secrecy исчезает. Это классический вектор против мобильных реализаций.
- **Метаданные не защищены.** X3DH/Double Ratchet скрывают содержимое, но не «кто с кем и когда». От этого защищает отдельный слой — sealed sender.
- **Компромисс устройства — не конец.** После следующего DH-шага (post-compromise security) атакующий, знавший старый ключ, теряет доступ, если честный узел обновит ratchet раньше.
- **Один DH в упрощённых схемах — красный флаг.** Если аудируемый мессенджер смешивает только identity-ключи, он не даёт ни forward secrecy, ни post-compromise security — это типичная находка при ревью.

## Полный числовой прогон X3DH

Соберём общий секрет вручную на игрушечных числах, чтобы увидеть, как склеиваются DH-ы. Возьмём малое простое `p = 23`, генератор `g = 5` и «приватные» ключи:

```
IK_A = 6   (identity key Алисы, приватная часть)
IK_B = 15  (identity key Боба)
SPK_B = 7  (signed prekey Боба)
OPK_B = 4  (one-time prekey Боба)
EK_A  = 3  (эфемерный ключ Алисы)
```

Публичные части — это `g^x mod p`. Считаем четыре общих секрета (`DH(x, Y) = Y^x mod p`):

```
pub_IK_B  = 5^15 mod 23 = 19
pub_IK_A  = 5^6  mod 23 = 8
pub_SPK_B = 5^7  mod 23 = 17
pub_OPK_B = 5^4  mod 23 = 4

DH1 = DH(IK_A, SPK_B) = 17^6 mod 23 = 12
DH2 = DH(EK_A, IK_B)  = 19^3 mod 23 = 6
DH3 = DH(EK_A, SPK_B) = 17^3 mod 23 = 11
DH4 = DH(EK_A, OPK_B) = 4^3  mod 23 = 18
```

Теперь конкатенируем с доменной строкой `F = 0xFF…` и прогоняем через HKDF-SHA256:

```
SK = HKDF( F || 12 || 6 || 11 || 18 )
```

Ни один из этих четырёх секретов по отдельности не даёт полного `SK`, а сервер, видевший только публичные ключи, не может вычислить ни одного из них без приватного ключа хотя бы одной из сторон.

## Аутентификация: подпись SPK и проверка

Почему Боб доверяет, что `SPK_B` действительно его? Потому что `SPK_B` **подписан** identity-ключом `IK_B`, а `IK_B` Алиса знает заранее (получила по независимому каналу или из проверенного каталога). Схема проверки:

```
signature = Ed25519_sign(IK_B_priv, SPK_B_pub)
Alice:    Ed25519_verify(IK_B_pub, SPK_B_pub, signature)  -> OK?
```

Если подпись верна, значит `SPK_B` аутентичен, и `DH1`, `DH3` привязывают сессию к подлинному долговременному ключу Боба. Именно поэтому X3DH даёт **взаимную аутентификацию** без онлайн-участия получателя: `OPK_B` и `SPK_B` лежат на сервере, но подпись `SPK_B` проверяема офлайн.

## Метаданные и sealed sender

X3DH и Double Ratchet защищают **содержимое**, но не **метаданные**: кто с кем, когда и как часто переписывается. Сервер видит получателя и время. Для сокрытия отправителя в Signal применяется **sealed sender**: отправитель шифрует свой сертификат вместе с сообщением, и сервер доставляет пакет, не зная, кто отправил. Это отдельный слой поверх Double Ratchet, и он напоминает, что криптография канала не равна приватности переписки.

## Сравнение Signal, TLS и WireGuard

| Свойство | Signal (X3DH+DR) | TLS 1.3 | WireGuard (Noise) |
|---|---|---|---|
| Тип | асинхронный E2E | канал клиент–сервер | канал хост–хост |
| Число DH на рукопожатие | 4 (X3DH) | 1 (или 0 с PSK) | 2 |
| Ротация ключей | на каждое сообщение | на соединение | на рекейинг |
| Forward secrecy | да | да | да |
| Post-compromise security | да (DH ratchet) | нет | ограниченно |
| Аутентификация | identity keys | сертификаты | статические ключи |

## Крайние случаи и ограничения

- **Исчерпание one-time prekeys.** Сервер выдаёт по одному `OPK` на сессию; когда они кончаются, используется только `SPK`, и `DH4` пропадает — защита слабеет. Клиент обязан периодически пополнять запас.
- **Повторное использование `OPK`.** Если сервер отдал один и тот же `OPK` двум инициаторам, часть секрета повторяется — прямая утечка.
- **Слабый RNG.** Любая эфемерная величина `EK_A` должна быть непредсказуемой; слабый генератор обрушивает всё рукопожатие.
- **Компромисс устройства.** Даёт доступ к текущим ключам и будущим сообщениям до следующего DH-шага, но не к истории (forward secrecy).
- **Аутентификация первого контакта.** `IK_B` надо получить доверенным путём, иначе MITM подставит свой ключ на самом первом шаге.

## Ротация prekeys и практика реализации

Реализация на стороне клиента сводится к циклу: загрузить на сервер пачку `OPK` и один `SPK` (с подписью), а после каждой входящей сессии удалить использованный `OPK`. Проверка состояния обычно выглядит так:

```
$ python3 prekey_status.py
signed prekey: present (rotated 2d ago)
one-time prekeys remaining: 87 / 100
recommendation: upload 13 more prekeys
```

Практика аудита: проверяй, что `OPK` действительно удаляются после использования, что `SPK` периодически ротируется, и что клиент отказывается инициировать сессию без валидного `SPK`.
