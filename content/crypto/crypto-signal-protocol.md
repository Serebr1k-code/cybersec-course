## Вопрос, с которого всё начинается

Ты пользуешься мессенджером, и он обещает, что даже сервер не прочитает переписку. Но у сторон нет общего пароля — только ключи, которые они опубликовали заранее. Как из «чужих публичных ключей» получить один общий секрет так, чтобы сервер, видевший все сообщения, его не узнал? Ответ даёт протокол **X3DH** (Extended Triple Diffie-Hellman) — часть Signal. Разберём его на конкретном рукопожатии.

## Наш пример: одно рукопожатие

Представим, что Алиса хочет написать Бобу. У каждого есть долговременный **identity key** (IK) — это его «личный» асимметричный ключ, аналог публичного ключа в PGP. Кроме него у Боба на сервере лежат заранее загруженные ключи:

```
IK_B  identity key Боба
SPK_B signed prekey Боба (подписан IK_B)
OPK_B one-time prekey Боба (одноразовый, стирается после использования)
```

Алиса генерирует свой одноразовый ключ `EK_A` (ephemeral) и считает четыре общих секрета Диффи-Хеллмана. Термин **DH** (Diffie-Hellman) ты уже знаешь: двое поднимают общий секрет `g^(ab)` по обмену `g^a` и `g^b`. Здесь DH считается сразу несколько раз — это и есть «triple/quadruple DH».

## Шаг 1: считаем DH-ы

X3DH задаёт четыре комбинации (по мотивам спецификации):

```
DH1 = DH(IK_A, SPK_B)
DH2 = DH(EK_A, IK_B)
DH3 = DH(EK_A, SPK_B)
DH4 = DH(EK_A, OPK_B)
```

Зачем четыре? Каждый даёт разную гарантию. `DH1` привязывает Алису к долговременному ключу Боба, `DH2` — Боба к долговременному ключу Алисы, `DH3`/`DH4` добавляют эфемерность. Вместе они означают: чтобы вычислить секрет, нужен **хотя бы один приватный ключ**, который сервер не знает. Сервер видел только публичные ключи и `EK_A` — общий секрет ему недоступен.

Возьмём маленькие числа, чтобы посчитать руками. Пусть `p = 2^521 - 1` (простое Мерсенна), `g = 2`. В реальном Signal используется Curve25519, но арифметика DH одинакова.

## Шаг 2: склеиваем и прогоняем через KDF

Четыре общих секрета нельзя просто сложить — их конкатенируют и пропускают через **KDF** (key derivation function), здесь HKDF-SHA256:

```
SK = HKDF( F || DH1 || DH2 || DH3 || DH4 )
```

где `F` — строка доменной сепарации из 32 байт `0xFF`, чтобы этот общий секрет нельзя было перепутать с секретом из другого протокола. **Доменная сепарация** — это когда в хэш подмешивают метку «это именно X3DH, версия 1», чтобы один и тот же ключ не переиспользовался в двух контекстах. Без неё возможны атаки подстановки между протоколами.

## Шаг 3: Double Ratchet

Получив начальный `SK`, стороны переходят к **Double Ratchet** — механизму, который меняет ключ шифрования на каждое сообщение. Идея: после каждого сообщения ключ «прокручивается» через хэш (симметричный ratchet), а при каждой смене направления добавляется новый DH (DH ratchet). В терминах: **forward secrecy** — если ключ украли сегодня, прошлые сообщения не прочитать, потому что старые ключи уже стёрты; **post-compromise security** — после следующего DH-шага атакующий, знавший старый ключ, теряет доступ.

Ключевое: цепочка ключей однонаправленна. Из текущего ключа легко получить следующий (`k' = HMAC(k, 0x02)`), а из следующего предыдущий — нет (HMAC необратим). Поэтому украденный сегодня ключ не отматывает историю.

## Полный прогон

В лабе даны `dh.txt` с параметрами и публичными ключами, `msg.enc` (шифротекст, XOR с keystream из HKDF) и скрипт `x3dh.py`. Скрипт считает четыре DH, конкатенирует с `F`, выводит `SK` через HKDF и расшифровывает сообщение:

```
$ python3 x3dh.py
DH1 = ...
DH2 = ...
DH3 = ...
DH4 = ...
SK  = 7c1e... (32 bytes)
plaintext: nto{x3dh_d0ubl3_r4tch3t_sh4r3d_s3cr3t}
```

## Если не сработало

Если вместо четырёх DH в протоколе используется один (упрощённый DH), проверь, не потерялась ли эфемерность — тогда компрометация долговременного ключа раскроет всю сессию. Если HKDF даёт другой результат, сверь порядок конкатенации и наличие `F`: порядок байтов критичен. Если сервер может вычислить секрет — значит, в списке DH остался только публичный материал.

## Куда дальше

Теперь ты знаешь, как Signal смешивает несколько DH в один секрет. В следующем уроке — Noise Protocol Framework: тот же принцип, но оформленный как язык, из которого WireGuard собирает своё рукопожатие. Запомни главное: каждый DH добавляет свою гарантию, а доменная сепарация не даёт ключам «протечь» между протоколами.
