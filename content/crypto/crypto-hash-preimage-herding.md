## Вопрос, с которого всё начинается

Когда говорят «хэш стойкий», обычно имеют в виду одно из трёх разных свойств. Найти по дайджесту исходное сообщение — это *preimage*. Найти **другое** сообщение с тем же дайджестом, имея одно — это *second-preimage*. Найти **любые два** сообщения с одинаковым дайджестом — это *collision*. Это не одно и то же, и сложности у них разные. Плюс есть коварная атака *herding*, где атакующий коммитится к дайджесту заранее. Разберём все.

## Наш пример: игрушечный 6-битный хэш

`multicoll.py` задаёт хэш с 6-битным состоянием. Компрессия блока (одного байта) неинъективна:

```
C(h, b) = (h·131 + b·7 + 13) mod 64
```

Начальное состояние `0`. Для любого фиксированного `h` все 256 значений байта `b` отображаются в 64 значения — значит, **гарантированно есть коллизии** (в среднем 4 прообраза на выход). Это упрощённая модель: настоящий хэш тоже неинъективен, только найти коллизию в нём трудно.

## Шаг 1: три уровня стойкости

Сложности атак для `n`-битного хэша: preimage — `2^n` (перебрать все входы), second-preimage — `2^n` (то же, но с учётом фиксированного первого сообщения), collision — `2^(n/2)` (по парадоксу дней рождения, о нём — в уроке `crypto-hash-mitm`). Обратите внимание: коллизию найти **вдвое проще по экспоненте**, чем прообраз. Поэтому SHA-1 с 160 битами уже мёртв для коллизий (`2^80`), но всё ещё «неплох» для preimage.

## Шаг 2: что такое herding

Herding — это атака на схему, где жертва **сначала** публикует дайджест, а **потом** выбирает сообщение. Атакующий (или жертва) заранее строит структуру, позволяющую для любого будущего сообщения подобрать «префикс» так, чтобы итоговый дайджест совпал с опубликованным. Классический пример — «Nostradamus-предсказание»: публикуем хэш, потом находим подходящее пророчество. Herding опирается на существование структур (multicollisions), поэтому для идеального хэша он не работает.

## Шаг 3: Joux-мультиколлизия

В 2004 году Antoine Joux заметил: если для хэша можно найти **одну** коллизию в компрессионной функции, то, склеивая `k` таких коллизий, получают `2^k` сообщений с одинаковым хэшем — при стоимости всего `k` коллизий, а не `2^k`. Схема: находим пару `(b0, b1)` с `C(h0, b0) = C(h0, b1) = h1`, затем для нового состояния `h1` снова пару, и так далее. Каждый «слой» удваивает число сообщений.

## Шаг 4: строим 256 коллизий

Прогоним `multicoll.py`, который делает 8 слоёв:

```
$ python3 multicoll.py
number of messages built: 256 (= 2^8)
distinct hashes          : 1 (all collide)
multicollision works     : True
flag: nto{j0ux_mult1c0ll1s10n_2_pow_k_m3ss4g3s}
```

Все 256 сообщений (каждое — 8 байт, по одному выбору на слой) дают **один** хэш. Стоимость — 8 поисков коллизий, а не `2^8 = 256` сообщений перебора. На реальном хэше это означало бы: одна коллизия (уже найденная для MD5/SHA-1) немедленно даёт `2^k` коллизий для любого `k`.

## Шаг 5: почему это страшно

Joux-мультиколлизия ломает наивные конструкции, где хэш используется для «неподделываемой» привязки. Если атакующий может сгенерировать `2^k` сообщений с одинаковым хэшем, то любая система, различающая сообщения только по хэшу, теряет смысл: под одним дайджестом скрывается экспоненциально много разных документов. Именно поэтому в 2005-2008 годах MD5 и SHA-1 «добили» chosen-prefix коллизиями — и почему для подписей перешли на SHA-2/SHA-3.

## Если не сработало

Если мультиколлизия не строится, проверьте: (1) неинъективна ли компрессия — если для каждого `h` отображение `b → C(h,b)` инъективно, коллизий нет; (2) правильно ли передаётся состояние между слоями; (3) достаточно ли байтов для поиска пары. Для реальных хэшей прямой поиск коллизий не по силам — нужны найденные ранее дифференциалы (MD5, SHA-1) или birthday-атака на коротких версиях.

## Herding: идея

Herding attack («Nostradamus») строит «commitment» — хэш `H_c`, такой что для любого будущего сообщения можно найти суффикс, приводящий к `H_c`. Так атакующий фиксирует хэш заранее и затем подгоняет сообщение. Это атака на **вторую прообразную стойкость** в контексте обязательств.

```text
commit H_c; later: given M, find suffix s.t. H(M || suffix) = H_c
```

Сложность зависит от ширины выхода: для 256-битного хэша herding непрактична, для усечённых — возможна.

## Diamond structure

Основной приём — **diamond structure**: строится граф, где из 2^k начальных значений сходятся в одно `H_c`. Предвычисление требует 2^(n/2+...) работы и памяти, но затем каждое новое сообщение «загоняется» в структуру быстро. Это расширение атаки Жу (Joux) на конкатенацию.

```text
2^k chaining values -> diamond -> single H_c
```

Практика: herding интересна для протоколов, где хэш фиксируется до выбора сообщения (таймстампы, обязательства).

## Практика и защита

Вывод: herding показывает, что «зафиксировать хэш заранее» не гарантирует уникальность сообщения, если хэш нестойкий к таким атакам. Защита: достаточно широкий выход (≥256 бит), случайная соль/контекст, использование HMAC вместо голого хэша для обязательств.

```text
defense: wide output + domain separation
```

Для аудита: проверь, используются ли голые хэши как обязательства, и нет ли усечения.

## Дополнительно: практическая значимость

Herding важна для протоколов, где хэш фиксируется заранее (обязательства, таймстампы, выборы). Если хэш усечён или слабый, атакующий может зафиксировать «правильный» хэш и позже подогнать сообщение. Практика: проверяй, используется ли голый хэш как обязательство, и есть ли усечение выхода.

```text
commitment = H(msg) -> herding risk if truncated/weak
```

Защита: доменная сепарация, соль, HMAC, широкий выход. Вывод: herding — про обязательства, а не про взлом хэша как такового.

## Что мы теперь знаем

- Preimage, second-preimage и collision — разные задачи.
- Коллизию искать проще (`2^(n/2)`), чем прообраз (`2^n`).
- Herding позволяет коммититься к дайджесту заранее.
- Joux-мультиколлизия даёт `2^k` сообщений за `k` коллизий.
- Мультиколлизии ломают «привязку по хэшу».
- MD5/SHA-1 мертвы для коллизий.

## Nostradamus и herding на практике

Herding-атака звучит абстрактно, но у неё есть яркая иллюстрация — «предсказание Нострадамуса». Идея: публикуем хэш `H(prediction)`, не раскрывая само предсказание. Позже, когда происходит некое событие, мы хотим предъявить «предсказание», хэш которого совпадает с опубликованным. Если хэш уязвим к herding, мы можем построить такое «предсказание» **после** события: берём её текст, подбираем префикс из заранее построенной структуры мультиколлизий так, чтобы итоговый дайджест совпал с опубликованным. Получается, что мы «предсказали» событие, которого не знали.

Формально herding опирается на существование **expandable message** — сообщения, из которого можно получить сообщение любой длины с тем же промежуточным состоянием. Joux-мультиколлизия как раз даёт такую структуру: `k` коллизий порождают `2^k` сообщений с одинаковым хэшем, и из них можно «вырастить» нужную длину. Отсюда практический вывод: herding возможен для любого хэша, где найдена коллизия в компрессионной функции (MD5, SHA-1). Для SHA-2/SHA-3 с их стойкостью к коллизиям herding не практичен. На CTF это встречается в задачах вида «вот опубликованный хэш и событие — предъявите предсказание», и решается построением expandable message. В реальной жизни herding — теоретическая угроза для систем «commit-then-reveal», построенных на слабых хэшах.

Стоит отметить и практическую сторону: построение expandable message требует, чтобы коллизии находились **дешёво** и в больших количествах. Для MD5 это давно так (chosen-prefix коллизии стоят секунды), поэтому MD5 категорически нельзя использовать ни для целостности, ни для commit-reveal. Для SHA-1 коллизии тоже найдены (SHAttered, 2017), так что и он непригоден. Для SHA-256 и SHA-3 таких результатов нет, и именно поэтому они остаются стандартом. Общий вывод: если вы строите протокол «сначала опубликую хэш, потом раскрою значение», берите SHA-256/SHA-3 и обязательно фиксируйте длину и формат сообщения, чтобы исключить неоднозначности разбора.

Дополнительно оцени, используется ли хэш для обязательств без доменной сепарации — в этом случае herding и related-атаки становятся актуальны, и это надо отметить как слабость дизайна протокола.

Для отчёта опиши, где хэш используется как обязательство и есть ли доменная сепарация; при её отсутствии herding становится реальным риском для протокола.
