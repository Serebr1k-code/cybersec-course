## Вопрос, с которого всё начинается

Современный автомобиль — это не только CAN. Камеры, радары и блоки управления соединены **Automotive Ethernet**, и поверх него работает **SOME/IP** — протокол «сервис-ориентированной» шины. В дампе ты видишь пакеты UDP с непонятными числами и службу `SOME/IP-SD`. Что это и как это читать?

## Наш пример: сообщение SOME/IP

Возьмём кадр из дампа `someip.pcap`:

```
$ tshark -r someip.pcap -nn -T fields -e someip.service -e someip.method -e someip.length -e someip.client
0x1234  0x0001  16  0x0002
```

Здесь `someip.service=0x1234` — идентификатор сервиса, `method=0x0001` — метод внутри сервиса, `client=0x0002` — кто вызвал. Разберём, откуда эти числа и почему они так устроены.

## Шаг 1: зачем сервис-ориентированность

CAN — это широковещательные кадры с ID: «кто-то отправил обороты». SOME/IP иначе: он описывает **сервисы** и **методы**, как RPC. Клиент вызывает метод сервиса, сервер отвечает. Такая модель ближе к веб-API, чем к шине.

Причины две. Первая — сложность: сотни сигналов трудно описывать плоским списком ID. Вторая — переиспользование: один сервис «камера» доступен нескольким потребителям без дублирования.

## Шаг 2: структура сообщения

SOME/IP-сообщение начинается с 16-байтного заголовка. Поля по порядку:

- **Message ID** (4 байта) — Service ID (старшие 2) + Method ID (младшие 2);
- **Length** (4 байта) — длина после заголовка;
- **Request ID** (4 байта) — Client ID + Session ID;
- **Protocol Version** (1 байт), **Interface Version** (1 байт);
- **Message Type** (1 байт) — запрос, ответ, уведомление;
- **Return Code** (1 байт) — код результата.

Message Type говорит, что это: `0x00` — REQUEST, `0x80` — RESPONSE, `0x02` — NOTIFICATION (событие), `0x01` — REQUEST_NO_RETURN (fire-and-forget).

## Шаг 3: Service Discovery

Прежде чем вызвать метод, клиент должен найти сервис. Этим занимается **SOME/IP-SD** — отдельный протокол поверх UDP (обычно порт 30490) с multicast. Сообщения SD:

- **OfferService** — «я предоставляю сервис 0x1234»;
- **FindService** — «кто умеет сервис 0x1234?»;
- **SubscribeEventgroup** — «подпиши меня на события группы X»;
- **SubscribeEventgroupAck** — подтверждение.

```
$ tshark -r someip.pcap -Y "someip.sd" -T fields -e someip.sd.type -e someip.service
0x01  0x1234
0x07  0x1234
```

Тип `0x01` — OfferService, `0x07` — SubscribeEventgroupAck. Всё это по multicast, то есть видно любому в сегменте.

## Шаг 4: методы, события и поля

Три способа взаимодействия:

- **Method** — RPC: клиент зовёт, сервер отвечает (или не отвечает при NO_RETURN).
- **Event** — сервер сам шлёт уведомления подписчикам (например, «изменилась скорость»).
- **Field** — комбинация: getter/setter как методы плюс уведомление при изменении.

События — ключевая поверхность атаки: подписка не всегда проверяется, и подписчик может получать данные, которые ему не предназначены.

## Шаг 5: собираем пакет сами

SOME/IP несложно собрать вручную — заголовок фиксированный. `scapy` умеет его:

```
$ python3
>>> from scapy.all import *
>>> pkt = IP(dst="224.244.224.245")/UDP(sport=30490,dport=30490)/SOMEIP(service=0x1234, method=0x0001, mtype=0x00)
>>> pkt.show2()
###[ SOMEIP ]###
  service= 0x1234
  method= 0x1
  length= 8
  client= 0x0
  session= 0x0
  mtype= REQUEST
```

Так воспроизводится любой сценарий: подписка, вызов метода, инъекция события.

## Шаг 6: атаки

Что проверяют на пентесте автомобильной Ethernet-сети:

- **спуфинг OfferService** — объявить поддельный сервис и перехватить клиентов;
- **инъекция Event** — послать уведомление от имени сервиса (например, ложную скорость);
- **подписка без авторизации** — получить поток событий;
- **DoS через NO_RETURN** — залить сервер запросами без ответа;
- **подмена Return Code** — сбить логику клиента.

```
$ python3
>>> sendp(Ether()/IP(dst="224.244.224.245")/UDP(dport=30490)/SOMEIP(service=0x1234,method=0x8001,mtype=0x02)/Raw(b"\x00"*8), iface="eth0")
```

## Шаг 7: что искать в дампе

Начни со сводки SD-сообщений — по ним строится карта сервисов. Затем смотри Message Type: NOTIFICATION-потоки идут от серверов к подписчикам. Ищи клиентов, которые подписались на «чужие» события. И помни про multicast: SD виден всем, а значит, карта сервисов доступна без аутентификации.

## Что мы теперь знаем

- SOME/IP — RPC-модель поверх Automotive Ethernet.
- Message ID = Service ID + Method ID; есть типы REQUEST/RESPONSE/NOTIFICATION.
- Service Discovery анонсирует сервисы по multicast.
- События и подписка — основная поверхность атаки.

## Если не сработало

Если `tshark` не разбирает SOME/IP — укажи порт: `-d udp.port==30490,someip`. Если дамп только SD — фильтруй `-Y someip.sd`. Если метод «неизвестен» — сопоставь его с описанием интерфейса (IDL) от производителя.

## SOME/IP рядом с CAN и D-Bus

Полезно поставить SOME/IP в один ряд с другими шинами. CAN — широковещательные кадры с коротким ID, без адресации и без запросов. SOME/IP — RPC с адресацией и ответами. D-Bus (в Linux) — тоже RPC, но локальный, на одном хосте. SOME/IP занимает нишу «сетевого RPC для автомобиля».

Отсюда следует разница в атаках. В CAN достаточно вбросить кадр с нужным ID. В SOME/IP нужно знать Service ID, Method ID, а часто и Client/Session ID, чтобы ответ прошёл проверку. Но и там есть слабое место: **Session ID** часто просто инкрементируется, и его легко предсказать.

## Транспорт: UDP, TCP и сериализация

SOME/IP работает и по UDP, и по TCP. UDP — для событий и коротких вызовов (быстро, без установки соединения). TCP — для больших данных и надёжных методов. Порт 30490 — типичный для SOME/IP-SD.

Данные внутри сериализуются по правилам SOME/IP: порядок полей задаётся описанием интерфейса (IDL), а не самим протоколом. Это значит, что без IDL ты видишь «сырые» байты. Практический приём: сопоставить длины и структуру payload с документацией сервиса; часто в открытых проектах (например, в AUTOSAR-стендах) IDL есть.

```
$ tshark -r someip.pcap -Y "someip.method == 0x0001" -T fields -e someip.payload
0000003c00000001
```

Так выглядит ответ метода: первые байты — значение, дальше — служебные поля.

## E2E-защита и почему её мало

В automotive есть механизм **E2E Protection** (end-to-end): к данным добавляется счётчик и CRC, чтобы принимающая сторона отбрасывала повторы и подделки. Если он включён, простая инъекция события не пройдёт — счётчик не совпадёт.

Проблема в том, что E2E применяют выборочно и часто только к «критичным» сигналам. Диагностические и информационные сервисы остаются без защиты. Поэтому на пентесте сначала смотрят, есть ли в payload признаки счётчика/CRC, и только потом делают вывод о возможности инъекции.

## Типичные ошибки

Первая — путать SOME/IP с SOME/IP-SD: это разные протоколы, SD — только discovery. Вторая — читать Length как длину всего пакета; на самом деле это длина после заголовка. Третья — считать, что раз есть multicast, значит есть широковещательная доставка данных: SD идёт по multicast, а сами вызовы часто unicast. Четвёртая — забывать про TCP-вариант SOME/IP, ища только UDP.

## Разбор SD-сообщения по полям

SOME/IP-SD — это тоже SOME/IP-сообщение, но с Method ID `0x8100` и своим набором «опций». Внутри — записи:

- **Type 0x01** — OfferService;
- **Type 0x00** — FindService;
- **Type 0x06** — SubscribeEventgroup;
- **Type 0x07** — SubscribeEventgroupAck.

```
$ tshark -r someip.pcap -Y "someip.sd" -V | grep -E 'Type|Service|TTL|Endpoint'
        Type: OfferService (0x01)
        Service ID: 0x1234
        TTL: 3
        IPv4 Endpoint Option: 10.0.0.20:30501
```

Из TTL видно, как часто сервис переанонсируется: пока TTL не истёк, сервис считается живым. Если подделать OfferService с большим TTL, можно надолго «занять» сервис. А Endpoint Option прямо говорит, куда слать вызовы, — подмена этого поля уводит трафик на атакующего.

## Инструменты и стенд

Для практики нужен SOME/IP-трафик. Его даёт открытый стенд на `vsomeip` (эталонная реализация) или эмуляция в `scapy`. Минимальный цикл:

```
$ python3
>>> from scapy.all import *
>>> sendp(Ether()/IP(dst="224.244.224.245")/UDP(dport=30490)/SOMEIP(service=0x1234,method=0x8100,mtype=0x02)/Raw(b"\x01\x00\x00\x00\x00\x00\x00\x10"), iface="veth0")
```

Для чтения используй `tshark -d udp.port==30490,someip` и фильтры `someip.sd`. Стенд на `veth`-паре безопасен и полностью воспроизводит описанные атаки — от спуфинга OfferService до инъекции события.

## SOME/IP рядом с DoIP

В автомобильной Ethernet рядом с SOME/IP живёт **DoIP** (ISO 13400) — диагностика поверх IP. Разница ролей: DoIP возит диагностические запросы (UDS) к блокам, SOME/IP — рабочий обмен между сервисами. Оба идут по Ethernet, но порты и семантика разные.

Для анализа это важно: если в дампе порт 13400, скорее всего DoIP, а не SOME/IP. И наоборот, SD-мультикаст на 30490 однозначно указывает на SOME/IP. Разделив их, ты не запутаешься в дампе автомобиля.

Защита тоже общая: сегментация, шлюзы и, где возможно, аутентификация на уровне сообщений.

## Шпаргалка по типам сообщений
