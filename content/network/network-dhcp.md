## Вопрос, с которого всё начинается

Когда ноутбук подключается к сети, он откуда-то получает IP-адрес, шлюз и DNS. Кто ему это выдаёт? Протокол **DHCP**. И если в сети появится **второй** DHCP-сервер — чей ответ возьмёт жертва?

Разберём DHCP и то, как через него захватывают сегмент.

## Наш пример: ноутбук получает адрес

Пусть клиент `10.0.0.5` (MAC `aa:bb:cc:00:11:22`) только подключился к сети и ещё не имеет IP. Он рассылает **broadcast**-запрос. DHCP-обмен состоит из четырёх шагов, по первым буквам — **DORA**:

- **Discover** — клиент: «есть тут DHCP-сервер?»;
- **Offer** — сервер: «могу дать тебе адрес»;
- **Request** — клиент: «беру вот этот»;
- **Ack** — сервер: «подтверждаю».

Поймаем первые два пакета:

```
$ tshark -r dhcp.pcap
    1  0.000000  0.0.0.0 → 255.255.255.255  DHCP 292 DHCP Discover - Transaction ID 0x0
    2  0.000461  10.0.0.1 → 10.0.0.5          DHCP 310 DHCP Offer    - Transaction ID 0x0
```

Обрати внимание: Discover уходит с `0.0.0.0` на broadcast `255.255.255.255` — клиент ещё не знает ни своего адреса, ни адреса сервера. Работает по **UDP**: клиент на порту `68`, сервер на `67`.

## Шаг 1: что именно выдаёт сервер

Разберём Offer подробнее — там самое интересное.

```
$ tshark -r dhcp.pcap -V | grep -iE "Message Type|Server Identifier|Router|Domain Name Server|Lease Time"
    Option: (53) DHCP Message Type (Offer)
    Option: (54) DHCP Server Identifier (10.0.0.1)
    Option: (51) IP Address Lease Time: 1 day (86400)
    Option: (3) Router: 10.0.0.1
    Option: (6) Domain Name Server: 10.0.0.1
```

Ключевые **опции**:

- **53** — тип сообщения (Offer);
- **54** — идентификатор сервера (`10.0.0.1`);
- **51** — время аренды (lease) адреса;
- **3** — **шлюз** (Router);
- **6** — **DNS-сервер**.

Вот и корень всех DHCP-атак: сервер выдаёт клиенту **шлюз и DNS**. Кто контролирует эти опции — контролирует, куда пойдёт трафик жертвы.

## Шаг 2: rogue DHCP-сервер

**Rogue-сервер** («враждебный») — это наш собственный DHCP-сервер в сети. Когда клиент рассылает Discover (broadcast), его видят **все** серверы. Если мы ответим **быстрее** настоящего, клиент может взять наш адрес.

В своём ответе мы указываем:
- `Router` (опция 3) = **наш** IP;
- `DNS` (опция 6) = **наш** IP.

Клиент послушно настраивает шлюз и DNS на нас. Результат — полноценный MITM **без ARP-спуфинга**: весь трафик жертвы идёт через нас, потому что она сама так настроена.

Поднять такой сервер можно `dnsmasq` или `isc-dhcp-server` — они и адрес выдадут, и нужные опции подставят.

## Шаг 3: DHCP starvation

Есть нюанс: если в сети есть настоящий сервер, клиент может выбрать **его** ответ. Как это обойти? Атака **starvation** («истощение»): атакующий рассылает тысячи Discover с **разными поддельными MAC-адресами**, заставляя настоящий сервер выдать все свободные адреса из пула.

```
$ sudo dhcpstarv -i eth0
```

Когда пул исчерпан, настоящий сервер больше не может ответить, и клиенты (и настоящие, и наши) получают ответ только от **нашего** rogue-сервера. Это классическая комбинация: сначала starvation, потом rogue.

## Шаг 4: что это даёт

Через DHCP-атаку атакующий получает:

- **Контроль шлюза** — весь исходящий трафик через нас;
- **Контроль DNS** — можно подделывать ответы (DNS-спуфинг);
- **Позицию MITM** — видим HTTP, DNS, незашифрованные протоколы;
- **Перенаправление** — жертва может попасть на подставной сервер.

Всё это — без единого ARP-пакета. Именно поэтому DHCP считают одним из самых «прибыльных» векторов на канальном уровне.

## Шаг 5: защита

Защита на коммутаторах:

- **DHCP snooping** — коммутатор помечает порты как «доверенные» (где стоит настоящий сервер) и «недоверенные». DHCP-ответы с недоверенных портов **отбрасываются**. Это закрывает и rogue, и starvation.
- **Port security** — ограничивает число MAC на порту, мешая starvation.
- **Rate limiting** — лимит на DHCP-пакеты от порта.
- **802.1X** — не даёт неавторизованному устройству подключиться.

Дополнительно:

- **Static IP** для критичных устройств;
- **Мониторинг:** второй DHCP-сервер в сети, всплеск Discover, ответы из неожиданных портов.

## Про DHCPv6 и SLAAC

Стоит знать, что рядом с «обычным» DHCP живёт его IPv6-версия — **DHCPv6**, а также **SLAAC** (Stateless Address Autoconfiguration). В IPv6 адрес часто формируется **автоматически** из префикса роутера и MAC устройства — без всякого сервера. А **Router Advertisement** (RA) сообщает клиентам префикс и шлюз.

Отсюда аналог rogue-DHCP: **rogue RA**. Если в сети появится фальшивый роутер, рассылающий RA, клиенты настроят маршрут через него. Защита — **RA Guard** на коммутаторах. Важно: IPv6 часто включён по умолчанию и не мониторится, поэтому rogue RA — реальный, а не теоретический вектор. Для SOC это повод завести правило на неожиданные ICMPv6 RA.

## Шаг 6: мини-практика — читаем DHCP в дампе

Покажем, как самостоятельно разобрать DHCP-обмен. Первый шаг — посмотреть, какие сообщения есть в захвате:

```
$ tshark -r dhcp.pcap -T fields -e dhcp.option.dhcp
1
2
```

Числа — это типы сообщений: `1` = Discover, `2` = Offer (дальше `3` = Request, `5` = Ack). Мы видим начало обмена.

Теперь вытащим выданные параметры:

```
$ tshark -r dhcp.pcap -T fields -e dhcp.option.router -e dhcp.option.domain_name_server
10.0.0.1
10.0.0.1
```

Оба значения — `10.0.0.1`, то есть и шлюз, и DNS указывают на один адрес. Если бы это был **наш** rogue-сервер, здесь стоял бы IP атакующего. Проверка простая: сравнить адрес в опциях с адресом настоящего шлюза.

Ещё полезный приём — посмотреть, **сколько разных** серверов отвечали. Если в дампе несколько Offer с разными `dhcp.option.server_id` — в сети работает больше одного DHCP-сервера, что почти всегда аномалия.

## Что мы теперь знаем

- DHCP работает по UDP/67-68 и проходит четыре шага DORA.
- Сервер выдаёт клиенту IP, **шлюз (опция 3)** и **DNS (опция 6)**.
- Rogue-сервер отвечает быстрее и подставляет свой шлюз/DNS — MITM без ARP.
- Starvation исчерпывает пул настоящего сервера поддельными MAC.
- Защита — DHCP snooping, port security, rate limiting, 802.1X.

## Разбираем DHCP-обмен по шагам: DORA

Наш ноутбук получил адрес, но в дампе видно не два пакета, а четыре. Это классический **DORA**:

| Шаг | Сообщение | Кто шлёт | Что означает |
|---|---|---|---|
| D | DHCPDISCOVER | клиент | «есть тут сервер?» (broadcast, src 0.0.0.0) |
| O | DHCPOFFER | сервер | «предлагаю адрес X» |
| R | DHCPREQUEST | клиент | «беру X» (снова broadcast) |
| A | DHCPACK | сервер | «закреплено» |

Ключевой нюанс для безопасности: и DISCOVER, и REQUEST — **широковещательные**. Их видит любой в сегменте, в том числе злоумышленник. А раз запрос клиента не аутентифицирован, любой может ответить первым — это и есть основа rogue-сервера.

Посмотрим обмен целиком:

```
$ tshark -r dhcp.pcap -Y bootp -T fields -e frame.number -e bootp.option.dhcp -e ip.src -e ip.dst
1  1  0.0.0.0    255.255.255.255
2  2  10.0.0.1   255.255.255.255
3  3  0.0.0.0    255.255.255.255
4  5  10.0.0.1   255.255.255.255
```

Здесь `bootp.option.dhcp` — это тип сообщения DHCP (1=DISCOVER, 2=OFFER, 3=REQUEST, 5=ACK). Уже по этой колонке виден весь разговор.

## Что именно приезжает в OFFER/ACK

В ответе сервер отдаёт не только IP. Набор **опций** определяет, как клиент будет жить в сети:

| Опция | Номер | Что задаёт |
|---|---|---|
| Subnet Mask | 1 | маска подсети |
| Router | 3 | **шлюз по умолчанию** |
| DNS Servers | 6 | резолверы |
| Domain Name | 15 | суффикс домена |
| Lease Time | 51 | срок аренды |
| WPAD | 252 | авто-настройка прокси |

Опасны здесь опции 3, 6 и 252. Подсунув свой шлюз (3) и свой DNS (6), атакующий превращает весь трафик жертвы в MITM — и жертва об этом не узнает. Именно поэтому rogue-DHCP — не «выдача левого IP», а полноценный перехват.

Проверим, что реально приехало клиенту:

```
$ tshark -r dhcp.pcap -Y 'bootp.option.dhcp==5' -T fields -e bootp.option.router -e bootp.option.dns -e bootp.option.ip_address_lease_time
10.0.0.1  8.8.8.8  86400
```

Шлюз `10.0.0.1`, DNS `8.8.8.8`, аренда сутки. Если бы здесь стоял адрес атакующего — это был бы захват.

## DHCP snooping и Option 82 в деталях

Защита строится на коммутаторе. Включаем **DHCP snooping** и объявляем порты:

```
$ show ip dhcp snooping
DHCP snooping is enabled.
Trusted ports: Gi0/1 (uplink to real DHCP)
Untrusted ports: Gi0/2-24
```

Смысл: DHCP-ответы принимаются **только** с доверенного порта. Rogue-сервер, воткнутый в обычный порт, просто не сможет ответить.

Дополнительный механизм — **Option 82** (relay agent information). Коммутатор вставляет в запрос номер порта и VLAN, с которых он пришёл. Реальный сервер видит, откуда клиент физически подключён, и может выдать адрес по политике. А при **DHCP starvation** (лавина DISCOVER с поддельными MAC) защитой служит rate-limit на DHCP-пакеты и port security — иначе пул адресов кончится, и новые клиенты останутся без сети.

| Атака | Механизм | Защита |
|---|---|---|
| Rogue DHCP | свой сервер отвечает первым | DHCP snooping (trusted-порт) |
| Starvation | исчерпание пула поддельными MAC | rate-limit + port security |
| Подмена шлюза/DNS | опции 3/6 в своём OFFER | snooping + мониторинг опций |

## Если не сработало: DHCP не виден в дампе

Бывает, что трафик идёт, а DHCP-пакетов нет. Проверь: клиент мог получить адрес **статически** или по **APIPA** (`169.254.x.x` — значит сервер не ответил). Если видишь только DISCOVER без OFFER — запросы уходят, но ответы режет фильтр или сервер недоступен. И не путай DHCPv4 с **SLAAC/DHCPv6**: в IPv6 адрес может назначаться без сервера вовсе (через Router Advertisement), и тогда привычного DORA в дампе не будет.
