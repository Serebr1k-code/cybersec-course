## Вопрос, с которого всё начинается

Сотрудник подключается к корпоративной сети через VPN. Ты видишь в дампе зашифрованный поток и хочешь понять: какой это VPN, что в нём видно, и нет ли ошибок в его настройке. Современные VPN — **WireGuard** и **IPsec** — устроены по-разному, и анализировать их надо по-разному.

Разберём, как читать их handshake и что искать в конфигурациях.

Этот урок опирается на [`network-tcpip`](network-tcpip) и [`network-tls-inspection`](network-tls-inspection).

## Наш пример: загадочный UDP-трафик

В дампе есть поток по UDP на нестандартном порту. Посмотрим на него:

```
$ tshark -r vpn.pcap -Y 'udp.port==51820' -T fields -e data | cut -c1-2 | sort | uniq -c
     14 01
      7 02
    380 04
```

Первый байт payload — `01`, `02`, `04`. Это **WireGuard**: тип сообщения кодируется первым байтом. Порт 51820 — стандартный для него. Разберём, что означают эти типы.

## Шаг 1: WireGuard — минимализм

WireGuard — это около 4000 строк кода (против сотен тысяч у OpenVPN/IPsec). Он использует **Noise IK handshake** на базе Curve25519, ChaCha20-Poly1305 и BLAKE2s, работает поверх **UDP**. У каждого peer пара ключей: приватный и публичный.

Ключевые свойства:

- **Stateless** — нет «соединения» в классическом смысле, есть ключи с таймаутом.
- **Roaming** — пакет аутентифицирован ключом, поэтому peer может менять IP.
- **Только UDP**, обычно один порт (51820).
- **Нет логина/пароля** — только ключи.

## Шаг 2: handshake по шагам

1. Инициатор шлёт **Handshake Initiation** (тип 1): эфемерный публичный ключ, зашифрованный статический ключ инициатора, timestamp.
2. Ответчик шлёт **Handshake Response** (тип 2): свой эфемерный ключ, зашифрованный статический ключ ответчика.
3. Обе стороны выводят сессионные ключи.
4. **Transport Data** (тип 4) — зашифрованные данные.

Handshake повторяется примерно каждые 120 секунд (rekey). В трафике видны четыре типа сообщений — по первому байту пакета.

## Шаг 3: что видно, а что нет

Что видно: IP и порты peer'ов, размеры и частоту handshake. Что **не** видно: содержимое и идентификаторы — они зашифрованы. Пассивный анализ ограничен — WireGuard не раскрывает metadata так, как это делают некоторые VPN. Сообщение типа 3 (**Cookie**) — ответ на перегрузку: под нагрузкой ответчик требует вернуть MAC, вычисленный на адресе отправителя; это защита от подделки source-IP и DoS.

Важное следствие: перехваченный handshake **бесполезен для оффлайн-подбора**, потому что в нём нет ни логина, ни пароля, ни проверяемого материала. Единственный способ войти — обладать **приватным ключом** peer'а. Поэтому реальная атака сводится к **краже ключа** (файл конфига, Git, бэкап), а не к криптоанализу.

## Шаг 4: аудит конфига WireGuard

Типичный «утекающий» конфиг клиента:

```ini
[Interface]
PrivateKey = aBcD...=           # приватный ключ в открытом файле
Address = 10.8.0.2/24

[Peer]
PublicKey = XyZ...=
Endpoint = vpn.corp.local:51820
AllowedIPs = 0.0.0.0/0, ::/0     # весь трафик в туннель
PersistentKeepalive = 25
```

Что видим:

- **Приватный ключ** лежит в файле. Утечка файла = полный доступ к VPN.
- **`AllowedIPs = 0.0.0.0/0`** — весь трафик идёт в туннель. Если ключ один на всех клиентов — нет персональной атрибуции.
- **Endpoint раскрыт** — атакующий знает адрес сервера.

Проверка утечек (traffic/DNS leak):

```
$ curl -s https://ifconfig.me
203.0.113.55
$ resolvectl status | grep -i dns
```

Если внешний IP не из VPN-диапазона — трафик утекает мимо туннеля (обычно из-за `AllowedIPs` или отсутствия kill-switch).

## Шаг 5: IPsec — сложнее

IPsec использует:

- **IKE** (UDP 500/4500) — установка ключей;
- **AH** (IP-протокол 51) — только аутентификация;
- **ESP** (IP-протокол 50) — шифрование.

IKEv1 имеет фазы: **Phase 1** (Main или Aggressive mode) создаёт IKE SA; **Phase 2** (Quick mode) — ESP/AH SA. Опасен **Aggressive mode**: часть данных, включая identity, идёт в открытом виде — материал для оффлайн-подбора PSK.

```
$ nmap -sU -p 500,4500 10.0.0.5
$ ike-scan -A -P handshake.txt 10.0.0.5
$ psk-crack -d wordlist.txt handshake.txt
```

## Шаг 6: сравнение и защита

| Критерий | WireGuard | IPsec |
|---|---|---|
| Транспорт | UDP (один порт) | UDP 500/4500, proto 50/51 |
| Криптография | фиксированная (Noise) | набор алгоритмов |
| Аутентификация | только ключи | PSK / сертификаты |
| Типовые баги | утечка ключей, AllowedIPs | PSK, aggressive mode, weak DH |

Защита: WireGuard — уникальные ключи на peer, ограничить `AllowedIPs`, хранить ключи в менеджере секретов. IPsec — перейти на IKEv2, сертификаты вместо PSK, сильные DH-группы, включить PFS.

## Если не сработало

VPN не удаётся определить или проанализировать? Проверь:

- **Нестандартный порт.** WireGuard часто переносят с 51820 — тогда ориентируйся по первому байту payload (1/2/4), а не по номеру порта.
- **Маскировка под 443.** Некоторые VPN прячутся под TCP/443 — по TLS-handshake всё ещё узнаваемы, но фильтр по порту не поможет.
- **IKEv2 вместо IKEv1.** Тогда `psk-crack` нечего перебирать — IKEv2 с сертификатами оффлайн не брутится.
- **Нет утечки.** Если внешний IP из VPN-диапазона, значит, split tunneling настроен корректно.

Полезно уметь читать состояние туннеля на хосте:

```
$ sudo wg show
interface: wg0
  peer: XyZ...=
  latest handshake: 42 seconds ago
  allowed ips: 10.8.0.0/24
$ ip route get 10.8.0.1
```

## Что мы теперь знаем

- WireGuard использует Noise IK поверх UDP; типы сообщений кодируются первым байтом (1/2/3/4).
- Handshake бесполезен для оффлайн-подбора — атака сводится к краже ключа.
- `AllowedIPs = 0.0.0.0/0` отправляет весь трафик в туннель; утечки проверяют по внешнему IP.
- IPsec использует IKE (500/4500) и ESP (proto 50); Aggressive mode IKEv1 отдаёт хэш PSK.
- Защита — уникальные ключи, ограниченные AllowedIPs, IKEv2 с сертификатами и PFS.
- Обнаружить VPN в дампе можно по сигнатуре handshake: WireGuard — регулярные 148-байтовые initiation, IPsec — IKE_SA_INIT/IKE_AUTH.

## Разбор handshake побайтно

Первое, что стоит уметь делать с WireGuard в дампе, — раскладывать пакет handshake на поля. Формат фиксированный и читается без расшифровки.

Сообщение Handshake Initiation (тип 1) всегда длиной **148 байт**:

```
$ tshark -r wg.pcap -Y 'udp.port==51820 && data.len==148' -T fields -e data | head -1
01000000e8a1f3c2<...32 байта ephemeral...><...48 байт encrypted_static...>\
<...28 байт encrypted_timestamp...><...16 байт mac1...><...16 байт mac2...>
```

Поля идут строго в таком порядке:

| Смещение | Размер | Поле |
|---|---|---|
| 0 | 1 | type (1 = initiation) |
| 1 | 3 | reserved (нули) |
| 4 | 4 | sender index (LE) |
| 8 | 32 | ephemeral public key |
| 40 | 48 | encrypted static key |
| 88 | 28 | encrypted timestamp |
| 116 | 16 | MAC1 |
| 132 | 16 | MAC2 |

Смещение `sender index` в initiation (4 байта) и `receiver index` в response/data (4 байта) позволяют связать пакеты в один сеанс, даже если peer меняет адрес. Именно так работает roaming: ключ аутентифицирует пакет, а индекс — сессию.

Handshake Response (тип 2) короче — **92 байта**: type(1) + reserved(3) + sender(4) + receiver(4) + ephemeral(32) + encrypted_nothing(16) + mac1(16) + mac2(16). Здесь нет статического ключа: он уже известен обеим сторонам после initiation.

Transport Data (тип 4) — это 4 байта заголовка (type + reserved), 4 байта receiver, 8 байт счётчика (counter, для защиты от replay) и затем зашифрованная полезная нагрузка с тегом Poly1305. Счётчик увеличивается на каждом пакете — по его монотонности в дампе видно, что сессия «живая» и не переигрывается.

Знание этих смещений полезно и при отладке туннеля (`wg show` не всегда под рукой), и при написании правил детекта: например, правило IDS «первый байт = 0x01 и длина = 148 на нестандартном порту» ловит WireGuard-инициации независимо от номера порта. А вот содержимое — эфемерные и статические ключи, timestamp — зашифровано на Curve25519, и без приватного ключа peer'а из этих байтов не извлечь ничего.

## Как WireGuard выглядит для DPI

Для системы обнаружения вторжений WireGuard — почти невидимый протокол: содержимое зашифровано, заголовков прикладного уровня нет. Единственные зацепки — поведенческие.

Первая: **регулярность handshake**. Раз в ~120 секунд в потоке появляется пара пакетов 148 и 92 байта, затем тишина или равномерный поток данных. Такая «пульсация» на одном UDP-порту — характерный отпечаток. Вторая: **фиксированные длины**. Initiation всегда 148 байт, response — 92, cookie reply — 64. Если DPI видит на нестандартном порту UDP пакеты именно этих размеров, он может пометить поток как WireGuard.

Обход в реальных развёртываниях строится не на изменении формата (он фиксирован криптографией), а на маскировке: перенос на порт 443, инкапсуляция в другой протокол или проксирование через obfuscator. Для пентестера это означает: не полагайтесь на номер порта — смотрите на длины и ритм пакетов. Для защищающегося — наоборот: детект по длинам работает даже при смене порта.
