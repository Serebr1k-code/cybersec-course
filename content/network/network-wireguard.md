WireGuard и IPsec — два современных VPN, которые надо уметь анализировать: и как защитник (что видно в трафике), и как пентестер (мисконфиги, утечки, слабые ключи). Этот урок — про протоколы, handshake, типовые ошибки и методы анализа.

Разберём, чем WireGuard отличается от IPsec, как читать их handshake, и что искать в конфигурациях.

## WireGuard: минимализм как принцип

WireGuard — это ~4000 строк кода против сотен тысяч у OpenVPN/IPsec. Он использует **Noise IK handshake** (на базе Curve25519, ChaCha20-Poly1305, BLAKE2s) и работает поверх **UDP**. Каждый peer имеет пару ключей: приватный и публичный.

Ключевые свойства:

- **Stateless**: нет «соединения» в классическом смысле, есть криптоключи с таймаутом.
- **Roaming**: пакет аутентифицирован ключом, поэтому peer может менять IP — это и фича, и потенциальная проблема.
- **Только UDP**: один порт (по умолчанию 51820), никакого TCP-fallback.
- **Нет встроенной аутентификации по логину/паролю** — только ключи.

## Handshake WireGuard по шагам

1. Инициатор шлёт **Handshake Initiation** (тип 1): эфемерный публичный ключ, зашифрованный статический ключ инициатора, timestamp.
2. Ответчик шлёт **Handshake Response** (тип 2): свой эфемерный ключ, зашифрованный статический ключ ответчика.
3. Обе стороны выводят сессионные ключи (транспортные).
4. **Transport Data** (тип 4) — зашифрованные данные с counter.

Handshake повторяется каждые ~120 секунд (rekey). В трафике видны четыре типа сообщений — по первому байту пакета (`1`, `2`, `3`, `4`).

## Анализ WireGuard в трафике

```bash
# захват
tcpdump -ni eth0 -X 'udp port 51820'
# определить тип сообщения по первому байту payload
tshark -r wg.pcap -Y 'udp.port==51820' -T fields -e data | cut -c1-2 | sort | uniq -c
# 1  → initiation, 2 → response, 4 → transport
```

Что видно: IP/порт peer'ов, размеры и частота handshake. Что НЕ видно: содержимое, идентификаторы (они зашифрованы). Пассивный анализ ограничен — WireGuard не раскрывает metadata так, как это делают некоторые VPN.

## Атаки и мисконфиги WireGuard

| Проблема | Суть | Последствие |
|---|---|---|
| Утечка приватного ключа | ключ в конфиге/бэкапе/скрипте | полный доступ к VPN |
| `AllowedIPs = 0.0.0.0/0` у клиента | весь трафик в туннель | утечка, если сервер не фильтрует |
| Нет `PersistentKeepalive` | NAT закрывает маппинг | обрывы, но и меньше заметности |
| Один ключ на всех | нет персональной атрибуции | компромисс одного = компромисс всех |
| Endpoint раскрыт | атакующий знает адрес | targeted DoS/сканирование |

Приватный ключ WireGuard (`PrivateKey`) — это и есть аутентификатор. Если он утёк (GitHub, бэкап, конфиг), вы подключаетесь как легитимный peer.

## IPsec: два режима и два протокола

IPsec сложнее. Он использует:

- **IKE** (Internet Key Exchange, UDP 500/4500) для установки ключей;
- **AH** (IP-протокол 51) — только аутентификация;
- **ESP** (IP-протокол 50) — шифрование (+аутентификация).

Режимы:

- **Transport mode** — шифруется только payload (host-to-host).
- **Tunnel mode** — шифруется весь исходный пакет (site-to-site, remote access).

## IKE-фазы

- **IKE Phase 1 (Main/Aggressive mode)**: стороны аутентифицируются (PSK, сертификаты, RSA) и создают IKE SA. В **Aggressive mode** часть данных (включая identity) идёт в открытом виде — классическая уязвимость для оффлайн-подбора PSK.
- **IKE Phase 2 (Quick mode)**: создаются ESP/AH SA для конкретного трафика (selectors).

```bash
# идентификация IPsec (NAT-T на 4500, IKE на 500)
nmap -sU -p 500,4500 10.0.0.5
# перебор PSK IKE (ike-scan + psk-crack)
ike-scan -A -M 10.0.0.5
ike-scan -A -P handshake.txt 10.0.0.5
psk-crack -d wordlist.txt handshake.txt
```

## Типовые мисконфиги IPsec

| Мисконфиг | Риск |
|---|---|
| PSK (общий пароль) | оффлайн-подбор, компромисс всех peers |
| Aggressive mode | раскрытие identity, утечка хэша |
| Слабые DH-группы (modp768/1024) | downgrade, ослабление |
| Широкие selectors (`0.0.0.0/0`) | туннель больше нужного |
| Отключена PFS | компромисс одного ключа раскрывает больше |
| IKEv1 legacy | множество старых CVE |

## Сравнение WireGuard и IPsec

| Критерий | WireGuard | IPsec |
|---|---|---|
| Кодовая база | ~4k строк | сотни тысяч |
| Транспорт | UDP (один порт) | UDP 500/4500, proto 50/51 |
| Криптография | фиксированная (Noise) | набор алгоритмов (negotiated) |
| Аутентификация | только ключи | PSK / cert / RSA |
| Аудит | простой | сложный, много параметров |
| Типовые баги | утечка ключей, AllowedIPs | PSK, aggressive mode, weak DH |

## Обнаружение VPN-трафика

- WireGuard: UDP на нестандартном порту, четыре типа сообщений, регулярный handshake каждые ~2 минуты.
- IPsec: UDP 500/4500 или IP-протоколы 50/51 — сразу видно в `tshark`.
- OpenVPN: UDP/TCP 1194 + TLS handshake.
- Маскировка: VPN на 443 (OpenVPN over TCP/443), WireGuard на 53/443 — сложнее, но по поведению handshake всё ещё узнаваем.

## Частые ошибки

- Считать WireGuard «невидимым» — handshake-паттерн узнаваем по типу сообщений.
- Искать в WireGuard то, чего там нет (логины/пароли) — аутентификация только по ключам.
- Забыть про `AllowedIPs` у клиента — трафик утекает мимо туннеля.
- Игнорировать IKE aggressive mode — там утекает identity и хэш PSK.
- Хранить приватные ключи в Git — самая частая реальная утечка.

## Что дальше / решение

Практика: `tcpdump -X udp port 51820` → определить типы сообщений WireGuard; `ike-scan -A` + `psk-crack` для IPsec PSK. Для защиты: WireGuard — сгенерировать уникальные ключи на peer, ограничить `AllowedIPs`; IPsec — перейти на IKEv2, сертификаты вместо PSK, сильные DH-группы, PFS. VPN — это не «чёрный ящик»: handshake и конфиг говорят о нём почти всё.

## Разобранный пример: аудит WireGuard-конфига

Типичный «утекающий» конфиг клиента:

```ini
[Interface]
PrivateKey = aBcD...=           # ← приватный ключ в открытом файле
Address = 10.8.0.2/24
DNS = 10.8.0.1

[Peer]
PublicKey = XyZ...=
Endpoint = vpn.corp.local:51820
AllowedIPs = 0.0.0.0/0, ::/0     # весь трафик в туннель
PersistentKeepalive = 25
```

Что видим:

- Приватный ключ лежит в файле. Утечка файла = полный доступ к VPN.
- `AllowedIPs = 0.0.0.0/0` — весь трафик идёт в туннель (проверить, куда реально маршрутизируется).
- Один и тот же `PublicKey` сервера у всех клиентов — норм, но если приватный ключ один на всех клиентов, атрибуции нет.

Проверка утечек (DNS/traffic leak):

```bash
curl -s https://ifconfig.me        # какой внешний IP видит интернет
curl -s https://1.1.1.1/cdn-cgi/trace | grep -E 'ip=|warp='
resolvectl status | grep -i dns
```

Если внешний IP не из VPN-диапазона — трафик утекает мимо туннеля (обычно из-за `AllowedIPs` или отсутствия kill-switch).

## Reference-таблица: типы сообщений WireGuard

| Тип | Направление | Содержит |
|---|---|---|
| 1 Initiation | инициатор → ответчик | эфемерный ключ, зашифр. статический ключ, timestamp |
| 2 Response | ответчик → инициатор | эфемерный ключ, зашифр. статический ключ |
| 3 Cookie | ответчик → инициатор | cookie для DoS-защиты |
| 4 Transport | обе стороны | зашифрованные данные + counter |

## Чек-лист аудита VPN

1. Определить тип VPN по портам/протоколам (`tcpdump`, `tshark`).
2. WireGuard: проверить `AllowedIPs`, уникальность ключей, утечки DNS/IP.
3. IPsec: режим IKE (v1/v2), PSK vs cert, aggressive mode, DH-группа, PFS.
4. OpenVPN: TLS-версия, сертификаты, tls-auth, сжатие.
5. Искать приватные ключи в Git/бэкапах/скриптах.
6. Проверить наличие kill-switch и утечек при обрыве туннеля.

## Noise_IK под микроскопом: почему WireGuard «нечего брутить»

Handshake WireGuard построен на паттерне **Noise_IK** (`I` — инициатор знает статический ключ ответчика, `K` — ключ ответчика передаётся заранее). Из эфемерных и статических ключей обе стороны выводят цепочку симметричных ключей через HKDF (на базе BLAKE2s). Внутри используются:

- **Curve25519** — для DH-обмена эфемерными и статическими ключами.
- **ChaCha20-Poly1305** — AEAD для шифрования и аутентификации.
- **BLAKE2s** — хэш и KDF.
- **TAI64N** — монотонный timestamp для защиты от replay.

Из этого следует важный практический вывод: перехваченный handshake **бесполезен для оффлайн-подбора**, потому что в нём нет ни логина, ни пароля, ни проверяемого материала. Единственный способ войти — обладать приватным ключом peer'а. Поэтому вся реальная атака сводится к **краже ключа** (файл конфига, Git, бэкап, менеджер секретов), а не к криптоанализу.

Cookie-сообщение (тип 3) — это ответ на перегрузку: под `load` ответчик требует, чтобы инициатор вернул MAC, вычисленный на адресе отправителя. Это защита от подделки source-IP и DoS, и её тоже видно в трафике.

## IPsec IKEv2: что проверять в конфиге и на проводе

IKEv2 (RFC 7296) упростил обмен до двух пар сообщений (`IKE_SA_INIT`, `IKE_AUTH`) и почти всегда использует UDP/4500 (NAT-T). В отличие от IKEv1, здесь нет aggressive mode в старом виде, но остаются типовые слабости:

| Параметр | Плохо | Хорошо |
|---|---|---|
| Аутентификация | PSK (общий пароль) | сертификаты (RSA/ECDSA) или EAP |
| DH-группа | modp768/1024 | modp2048+, ECP256/384 |
| PFS | выключен | включён (esp dh-group) |
| Шифр | 3DES, DES | AES-GCM-256 |
| Хэш | MD5/SHA1 | SHA-256/384 |

```bash
# определить IKEv2 и предложенные трансформы (не атака — fingerprint)
sudo nmap -sU -p 500,4500 --script ike-version 10.0.0.5
# ike-scan с явным IKEv2
ike-scan -2 -M 10.0.0.5
# проверить PSK-подбор только для IKEv1 aggressive
ike-scan -A -P hs.txt 10.0.0.5 && psk-crack -d rockyou.txt hs.txt
```

Ключевое отличие: **IKEv2 + сертификаты** практически нечего брутить оффлайн (нет PSK-хэша), а вот legacy-конфиг с PSK и aggressive mode — это готовый материал для `psk-crack`. На проводе IKE виден как UDP 500/4500, а данные — как IP-протокол 50 (ESP) или 51 (AH).

## Разобранный пример: определить тип VPN только по PCAP

```bash
# 1. какие нестандартные протоколы/порты вообще есть
tshark -r vpn.pcap -T fields -e ip.proto -e udp.dstport -e tcp.dstport | sort | uniq -c | sort -rn | head
# 2. WireGuard — первый байт payload 1/2/4 на UDP
tshark -r vpn.pcap -Y 'udp.length>32' -T fields -e udp.dstport -e data | cut -c1-2 | sort | uniq -c
# 3. IPsec — протоколы 50/51 или IKE на 500/4500
tshark -r vpn.pcap -Y 'ip.proto==50 || ip.proto==51 || udp.port==500 || udp.port==4500' | head
# 4. OpenVPN — TLS handshake на 1194 (или 443 при маскировке)
tshark -r vpn.pcap -Y 'tcp.port==1194 || udp.port==1194' | head
```

По одной только сигнатуре handshake можно уверенно назвать продукт: WireGuard выдаёт себя регулярным 148-байтовым initiation каждые ~2 минуты; IPsec — парой IKE_SA_INIT/IKE_AUTH; OpenVPN — TLS ClientHello с характерным набором расширений.

## Эксплуатационные команды: состояние, пиры, маршруты

Для защиты и диагностики полезно уметь читать состояние WireGuard на хосте, а для атаки — понять, куда ведёт туннель и что разрешено:

```bash
sudo wg show                 # пиры, handshake, transfer, allowed-ips
sudo wg showconf wg0         # полный конфиг интерфейса
ip route get 10.8.0.1        # каким интерфейсом пойдёт трафик (проверка split-tunnel)
ip rule show                 # policy routing, kill-switch
# найти конфиги с ключами на диске
grep -rIl 'PrivateKey' /etc /home /opt 2>/dev/null
```

Если `wg show` показывает `latest handshake` давно (часы), peer, вероятно, за NAT без `PersistentKeepalive` — туннель «уснул». Это не ошибка безопасности, но частая причина инцидентов «VPN не работает».
