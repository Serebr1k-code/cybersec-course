Маршрутизация — это «клей» интернета: именно протоколы маршрутизации решают, куда пойдёт каждый пакет. Они исторически доверяют соседям и почти не проверяют правдоподобность анонсов, поэтому перехват трафика на маршрутном уровне (BGP hijack) остаётся рабочей техникой и в 2020-х. Этот урок разбирает, как устроены BGP, OSPF и EIGRP, где у них слабые места и как их эксплуатируют — от лабораторного стенда до реальных инцидентов.

## Модель угроз и уровни маршрутизации

Различайте три плоскости:

- **Внутренняя (IGP):** OSPF, IS-IS, EIGRP, RIP — работают внутри одной автономной системы (AS), строят карту сети.
- **Внешняя (EGP):** BGP — обменивается маршрутами между AS, формирует маршрутизацию интернета.
- **Локальная:** статические маршруты, ICMP Redirect — то, что можно подменить в одном сегменте.

Атакующий целится либо в **управляющую плоскость** (подсунуть ложный маршрут), либо в **плоскость данных** (перехватить уже маршрутизируемый трафик). BGP-хайджекинг — атака на управляющую плоскость с последствиями в данных. Внутренние IGP-атаки обычно требуют присутствия в L2-сегменте или уже установленного adjacency; BGP-атаки возможны извне, если у вас есть peer-сессия.

## BGP: как устроен и почему ломается

BGP — протокол на **TCP/179**. Соседи (peers) устанавливают сессию (FSM: Idle → Connect → OpenSent → OpenConfirm → Established) и обмениваются анонсами: «префикс X доступен через меня, длина AS-path = N». Лучший маршрут выбирается по набору атрибутов, ключевые из которых:

| Атрибут | Смысл | Злоупотребление |
|---|---|---|
| AS_PATH | список AS на пути | короче путь = предпочтительнее → подделка «короткого» пути |
| NEXT_HOP | следующий маршрутизатор | подмена для чёрной дыры или перехвата |
| LOCAL_PREF | локальное предпочтение | приоритет внутри AS |
| MED | подсказка соседней AS | влияние на входящий трафик |
| Communities | теги маршрута | манипуляция политикой |
| ORIGIN | источник (IGP/EGP/incomplete) | редко, но влияет на выбор |

Порядок выбора (упрощённо): **weight → LOCAL_PREF → локально origin → AS_PATH (короче) → ORIGIN → MED → eBGP над iBGP → IGP-метрика → router-id**. Атакующий манипулирует ранними критериями — длиной AS_PATH и origin.

Ключевая слабость: **BGP по умолчанию не аутентифицирует источник анонса**. Любой peer может объявить чужой префикс — и мир поверит, если путь выглядит выгоднее. Защита RPKI/ROA появилась, но покрытие неполное.

### Техники BGP-хайджекинга

- **Префикс-хайджекинг:** объявить более специфичный префикс (`/25` вместо `/24`) — он всегда выигрывает по longest-prefix-match.
- **Путь-хайджекинг:** анонсировать тот же префикс с более коротким AS_PATH.
- **BGP-легитимизация:** анонсировать адресное пространство жертвы со своего IP, чтобы поднять доверие сервисов (обход email/ACL-фильтров по IP).
- **Route leak:** некорректная реклама транзитного маршрута, затягивающая трафик в чужую AS.
- **Sub-prefix hijack:** разбить чужой `/24` на `/25`-блоки и объявить их.

## OSPF и EIGRP: инъекция маршрутов внутри AS

OSPF — link-state протокол поверх IP-протокола **89**. EIGRP — протокол Cisco поверх IP-протокола **88**. Оба по умолчанию полагаются на доверие внутри домена и на простую аутентификацию (или её отсутствие).

- **OSPF:** если атакующий в том же сегменте, он может поднять adjacency, анонсировать фальшивые **LSA** (Router/Network/Summary LSA) и стать точкой притяжения трафика. Классический трюк — подделать Router LSA с большим приоритетом и стать DR (Designated Router). Пакеты: Hello (224.0.0.5), DBD, LSR, LSU, LSAck.
- **EIGRP:** инъекция Update-пакетов с лучшей метрикой меняет топологию; возможен и сброс соседства через фальшивый Hello/K-значения mismatch.
- **RIP:** простейший — анонс маршрута с меньшей метрикой (hop count) мгновенно уводит трафик; RIPv2 multicast 224.0.0.9.

Инструменты: `Loki`, `Yersinia`, `Scapy`, `FRRouting`, `GNS3`/`EVE-NG` для стенда.

## Инструменты и команды

Лаборатория на одном хосте через сетевые namespace:

```bash
# создаём два изолированных узла
sudo ip netns add victim
sudo ip netns add attacker
sudo ip link add veth0 type veth peer name veth1
sudo ip link set veth0 netns victim
sudo ip link set veth1 netns attacker
sudo ip netns exec victim ip addr add 10.0.0.1/24 dev veth0
sudo ip netns exec attacker ip addr add 10.0.0.2/24 dev veth1
sudo ip netns exec victim ip link set veth0 up
sudo ip netns exec attacker ip link set veth1 up
```

Просмотр таблицы маршрутизации и сессий BGP (FRRouting):

```bash
vtysh -c "show ip route"
vtysh -c "show bgp summary"
vtysh -c "show bgp ipv4 unicast 203.0.113.0/24"
vtysh -c "show ip ospf neighbor"
vtysh -c "show ip ospf database"
```

Инъекция OSPF-анонса через Scapy (упрощённо, только в своей лаборатории):

```python
from scapy.all import *
from scapy.contrib.ospf import OSPF_Hdr, OSPF_Hello
sendp(Ether()/IP(proto=89)/OSPF_Hdr()/OSPF_Hello(), iface="veth1")
```

Мониторинг маршрутов извне (без доступа к роутеру):

```bash
# публичные коллекторы BGP: RIPE RIS, RouteViews, BGPStream
curl -s 'https://stat.ripe.net/data/bgp-state/data.json?resource=198.51.100.0/24' | head -40
whois -h whois.radb.net -- '-i origin AS65001' | head        # анонсы AS (IRR)
```

## Разобранный пример: «префикс-хайджекинг» в мини-стенде

Сценарий: две AS — AS65001 (жертва, префикс `198.51.100.0/24`) и AS65002 (атакующий). Между ними транзит.

1. Жертва анонсирует `198.51.100.0/24` через AS65001.
2. Атакующий объявляет `198.51.100.0/25` — более специфичный префикс. Все роутеры выбирают его по longest-prefix-match.
3. Трафик к половине адресов уходит в AS атакующего. Там можно сделать чёрную дыру (отбросить) или перехватить и просмотреть (MITM на маршрутном уровне).
4. Проверка: на транзитном роутере `show ip bgp 198.51.100.0/25` покажет путь через AS65002.

```bash
# в стенде FRR атакующий анонсирует более специфичный префикс
vtysh -c "conf t" -c "router bgp 65002" -c "network 198.51.100.0/25"
# проверяем, что сосед выбрал наш путь
vtysh -c "show bgp ipv4 unicast 198.51.100.0/25"
# BGP routing table entry for 198.51.100.0/25, bestpath
#   65002, (received from ...), valid, best
```

В реальном мире так были инциденты с утечкой трафика крупных сервисов; защита — RPKI-валидация и фильтрация анонсов (`prefix-list`, `max-prefix`).

## Обнаружение и защита

- **RPKI/ROA:** криптографическая привязка префикса к AS; отклонение невалидных анонсов. Проверка: `whois -h whois.ripe.net -i origin AS65001` и `rpki-validator`.
- **BGPsec:** подпись пути (покрытие низкое).
- **Фильтрация:** `prefix-list` и `route-map` на границе, `max-prefix` для защиты от утечек, TTL-security (GTSM) на BGP-сессиях.
- **Мониторинг:** сервисы вроде BGPStream, RIPE RIS, RouteViews — детект аномальных анонсов; алерты на новые origin префикса.
- **OSPF/EIGRP:** включить MD5/SHA аутентификацию, passive-interface на краевых портах, отключить ненужные протоколы.

## Частые ошибки

- **Путать IGP и EGP.** OSPF-атака работает только внутри одного домена; для глобального перехвата нужен BGP.
- **Забывать про longest-prefix-match.** Атака «тем же префиксом» не сработает так надёжно, как более специфичным.
- **Игнорировать TTL/фильтры.** Инъекция IGP требует доступа в тот же L2-сегмент или adjacency; извне сегмента пакеты не дойдут.
- **Считать RPKI панацеей.** RPKI валидирует origin, но не весь путь — path-хайджекинг с валидным origin всё ещё возможен.
- **Путать route leak и hijack.** Leak — ошибка конфигурации (транзит утекает), hijack — намеренный анонс чужого префикса.
- **Забывать про входящий/исходящий трафик.** Анонс влияет на трафик К ВАМ; исходящий маршрут контролируется вашими LOCAL_PREF/MED.

## Что дальше / решение

Пошаговый план в лаборатории и при аудите:

1. **Понять топологию**: кто ваши соседи, какие AS, какие префиксы анонсируются (IRR/`whois`).
2. **Проверить наличие аутентификации**: `show run` на BGP/OSPF — есть ли `neighbor ... password`, MD5, GTSM, `prefix-list`.
3. **Смоделировать в FRR/Scapy**: поднять стенд namespace, воспроизвести hijack/leak, посмотреть выбор пути.
4. **Проверить RPKI-покрытие** своего префикса (`rpki-validator`, RIPE Stat).
5. **Настроить мониторинг** (BGPStream/RIS) и `max-prefix`, `prefix-list` на границе.
6. **Задокументировать риск**: перехват/чёрная дыра, влияние на доступность.

Решение-эвристика: если цель — перехватить чужой трафик глобально, ищите BGP-сессию и слабую фильтрацию; если вы внутри AS — атакуйте OSPF/EIGRP (нет MD5-аутентификации → подделка LSA/Update).

## Резюме

Маршрутизация доверяет анонсам. BGP ломается через более специфичный префикс или короткий AS_PATH; OSPF/EIGRP — через инъекцию LSA/Update внутри сегмента. Защита: RPKI/ROA, prefix-list, max-prefix, GTSM, MD5-аутентификация IGP, мониторинг аномалий через RIS/RouteViews.

## BGP-communities и трафик-инжиниринг

**Communities** — 32-битные теги, которые AS прикрепляют к маршрутам и по которым соседи принимают политики. Атакующий может подделать community, чтобы получить более выгодную обработку или заставить соседа не анонсировать маршрут. Часто используемые well-known communities: `NO_EXPORT` (0xFFFFFF01), `NO_ADVERTISE` (0xFFFFFF02), `BLACKHOLE` (0xFFFF029A). Знание локальных communities чужой AS (утекают в IRR/блогах) даёт рычаг влияния.

## Route leak: как распознать

**Route leak** — анонс транзитного маршрута тому, кому его рекламировать нельзя. Признаки в мониторинге:

- AS_PATH, где через вас идёт путь, не соответствующий вашей роли (вы стали транзитом для двух крупных AS).
- Резкий рост числа префиксов от одного соседа (`max-prefix` должен ловить).
- Изменение best-path на большом числе префиксов в короткое окно.

```bash
# Проверка префикса через публичные данные
curl -s 'https://stat.ripe.net/data/routing-status/data.json?resource=198.51.100.0/24' | head -60
# Аномалии анонсов через BGPStream (пример CLI)
bgpstream -p routeviews -w 60 -f "prefix 198.51.100.0/24" 2>/dev/null | head
```

Защита от leak: `prefix-list` «что я имею право анонсировать», `max-prefix` на соседях, `route-map` с фильтром по AS_PATH (не пропускать пути, где вы в середине), RPKI origin-валидация.

## Где пригодится

- **CTF:** задачи на восстановление топологии по PCAP, маршрутные петли, «почему трафик ушёл не туда».
- **Bug bounty / Red team:** оценка риска перехвата трафика на уровне провайдера и границ AS.
- **Пентест:** аудит внутренней маршрутизации (OSPF/EIGRP без аутентификации) и краевых фильтров BGP.
- **Работа (SOC/NOC/IR):** детект аномальных анонсов, реакция на route leak и хайджекинг.
