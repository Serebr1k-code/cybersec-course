Иногда нужно не просто прочитать дамп, а **воспроизвести** трафик: проверить, воспроизводим ли запрос, повторить аутентификацию, отправить модифицированный пакет. Реплей — это мост между пассивным анализом и активной атакой. Но у него есть принципиальные ограничения: sequence numbers, TLS, nonce, одноразовые токены. Понимание этих ограничений отличает «скопировал пакет» от реальной эксплуатации.

## Зачем реплеить трафик

- **Проверка воспроизводимости** запросов (есть ли защита от replay).
- **Повтор аутентификации/токенов** (если нет anti-replay).
- **Отправка модифицированных пакетов** в протокол без шифрования.
- **Нагрузочное тестирование** и фаззинг кастомных протоколов.
- **CTF:** «воспроизведи запрос и получи флаг».

## tcpreplay и его семейство

`tcpreplay` отправляет записанные пакеты обратно в сеть. Сопутствующие утилиты:

- **tcprewrite** — меняет MAC/IP/порты, пересчитывает контрольные суммы;
- **tcpprep** — размечает пакеты на client/server (для направлений);
- **tcpbridge** — «переигрывание» между интерфейсами.

```bash
# Переписать адреса под нашу сеть
tcprewrite --infile=orig.pcap --outfile=rewritten.pcap \
  --srcipmap=10.0.0.0/24:192.168.1.0/24 --dstipmap=10.0.1.0/24:192.168.2.0/24
# Проиграть на интерфейс с реальной скоростью
sudo tcpreplay -i eth0 --mbps=10 rewritten.pcap
# Только определённые пакеты (по разметке tcpprep)
sudo tcpreplay -i eth0 --cache-file=cache.pcap rewritten.pcap
```

## Модификация через Scapy

Scapy позволяет не только проиграть, но и **изменить** любой байт. Читаем дамп, модифицируем поле, отправляем:

```python
from scapy.all import *
pkts = rdpcap("orig.pcap")
p = pkts[3]
p[IP].dst = "192.168.1.50"          # новый получатель
p[TCP].dport = 8080                 # новый порт
del p[IP].chksum; del p[TCP].chksum # пересчитать контрольные суммы
send(p)
```

Если нужно воспроизвести сессию, придётся заново установить соединение и подставить актуальные seq/ack (см. `network-tcp-hijacking`).

## MITM-прокси

Для HTTP(S) удобнее прокси, который модифицирует трафик «на лету»:

- **mitmproxy / mitmdump / mitmweb** — перехват, скрипты-аддоны, повтор запросов.
- **bettercap** — HTTP/HTTPS-прокси, `http.proxy`, инъекция.
- **Burp/ZAP** — для веб-приложений.

```bash
# mitmproxy: прозрачный режим, модификация ответов
mitmproxy --mode transparent --showhost
# Повтор запроса из истории (replay)
# в mitmproxy: нажать 'r' на запросе
```

mitmproxy умеет **replay** любого запроса с изменёнными параметрами — это и есть «умный реплей» для HTTP.

## Разобранный пример: реплей и модификация

1. Захватываем HTTP-запрос аутентификации (Basic/Bearer) в дампе.
2. Воспроизводим через mitmproxy: подставляем тот же токен, меняем тело запроса.
3. Если сервер отвечает 200 и выполняет действие — есть replay-уязвимость.
4. Меняем `id` в запросе на чужой — проверяем авторизацию (IDOR).
5. Для бинарного протокола берём пакет в Scapy, меняем поле, отправляем заново.
6. Фиксируем в отчёте: воспроизводимость и отсутствие anti-replay.

## Реплей аутентификации и токенов

| Механизм | Реплеится? | Почему |
|---|---|---|
| HTTP Basic | Да | Статичный заголовок |
| Bearer JWT (без jti/nonce) | Да, до истечения | Нет одноразовости |
| Session cookie | Да, пока жива | Привязка к сессии |
| NTLM/Kerberos | Нет (напрямую) | Требует релеинга |
| OAuth code | Нет | Одноразовый code |
| HMAC с nonce/timestamp | Нет | Anti-replay |
| TLS-сессия | Нет | Ключи сессии |

## Ограничения реплея

- **Sequence numbers.** TCP-пакет с «прошлым» seq будет отброшен.
- **TLS.** Зашифрованный трафик не воспроизвести без ключей.
- **Nonce/timestamp.** Anti-replay-механизмы ломают прямой реплей.
- **Состояние сервера.** Одноразовые токены/коды сгорают.
- **Сетевые адреса.** Нужен tcprewrite или правильная позиция в канале.

## Защита

| Мера | Против чего |
|---|---|
| Nonce + timestamp в токенах | Реплей |
| Одноразовые коды/сессии | Повтор аутентификации |
| TLS везде | Модификация и реплей |
| Привязка токена к IP/UA/сессии | Кража и повтор |
| Короткий TTL токенов | Окно реплея |
| Идемпотентность + контроль | Повтор действий |

## Частые ошибки и подводные камни

- **Забывать пересчитать контрольные суммы.** Scapy делает это при `send`, но при ручной сборке — нет.
- **Пытаться реплеить TLS без ключей.** Бесполезно.
- **Игнорировать seq/ack.** Пакет уйдёт, но не будет принят.
- **Реплеить на прод без разрешения.** Это активное воздействие.
- **Считать, что «200 OK» = уязвимость.** Проверяйте, выполнилось ли действие (изменение состояния).
- **Путать реплей и релеинг.** Релеинг — пересылка живой аутентификации, реплей — повтор записанной.

## Что дальше / решение

Реплей — практический мост к активной эксплуатации. Свяжите с `network-tcp-hijacking`, `network-mitm` и веб-веткой (IDOR, CSRF). Для защиты вводите anti-replay (nonce/timestamp), короткие TTL и TLS. Для CTF тренируйтесь в `tcprewrite`/Scapy и в mitmproxy-replay.

## Реплей в бинарных протоколах и TCP-сессиях

Для кастомных бинарных протоколов (промышленные, игровые, IoT) реплей — основной метод исследования. Процесс:

1. Захватить легитимную сессию (клиент + сервер).
2. Восстановить структуру сообщений: заголовок (magic, длина, тип), тело, контрольная сумма.
3. Воспроизвести «руками» через `nc`/Scapy, подставив корректные seq/ack и пересчитав CRC.
4. Менять по одному полю и наблюдать реакцию — так находится команда управления.

Если протокол поверх TCP, одного `send()` мало: нужно установить соединение (SYN/SYN-ACK/ACK) или вклиниться в существующую сессию (см. `network-tcp-hijacking`). Иногда проще написать клиент на Scapy/socket, чем реплеить пакеты.

```python
# Простейший TCP-клиент для реплея сообщения
import socket, struct
s = socket.create_connection(("10.0.0.5", 9999))
msg = b"\x01\x02" + struct.pack("<H", 4) + b"PING"
s.sendall(msg)
print(s.recv(1024))
```

## Инструменты помимо tcpreplay

- **`socat`/`nc`** — ручной обмен, если протокол текстовый/простой.
- **`mitmproxy`/`mitmweb`** — HTTP(S)-реплей и модификация.
- **`bettercap`** — HTTP-прокси и инъекция в реальном времени.
- **`Burp Repeater`/`ZAP`** — веб-реплей с полным контролем.
- **`Scapy`** — любая модификация на уровне пакетов.
- **`boofuzz`/`sulley`** — фаззинг на основе записанных сообщений.

## Лаборатория: реплей аутентификации

1. Поднимите уязвимое веб-приложение с Basic-аутентификацией и эндпоинтом действия.
2. Захватите запрос в mitmproxy (или Burp).
3. Повторите его через `curl` с тем же заголовком `Authorization`:
   ```bash
   curl -u user:pass -X POST http://target/action -d 'amount=100'
   ```
4. Выполните ещё раз — если действие повторяется, есть replay-уязвимость.
5. Добавьте в приложение anti-replay (nonce/CSRF-токен) и повторите — запрос должен отвергаться.
6. Для бинарного протокола повторите тот же цикл через Scapy-клиент.

Это прямой путь от анализа к доказательству уязвимости и её исправлению.
