## Вопрос, с которого всё начинается

Ты видишь трафик на необычном порту, и в нём короткие заголовки с полем «тип пакета». Это не TCP и не UDP. Причём у протокола есть управление перегрузкой, как у TCP, но передаёт он датаграммы, как UDP. Что это?

Это **DCCP** — Datagram Congestion Control Protocol, тема модуля [`network-module-transport-alt`](network-module-transport-alt). Разберём его.

## Наш пример: установка DCCP-соединения

```
Request   port=5000  Service Code=0x00000001
Response  port=5000  ack=1
Data      seq=1
```

Три пакета. Разберём, почему их всего три и что за «Service Code».

## Шаг 1: зачем ещё один транспорт

UDP быстр, но не имеет управления перегрузкой — если все начнут «лить» UDP, сеть упадёт. TCP вежлив, но он поток байтов: если приложению нужны **сообщения** (аудио, игры, телеметрия), TCP мешает (head-of-line blocking, буферизация). DCCP — компромисс: **датаграммы + congestion control**. Плюс он поддерживает разные алгоритмы управления перегрузкой (CCID2 как у TCP, CCID3 для потокового медиа).

## Шаг 2: типы пакетов

DCCP использует небольшой набор типов (поле Type в заголовке):

| Type | Пакет | Смысл |
|------|-------|-------|
| 0 | Request | запрос соединения |
| 1 | Response | ответ, соединение установлено |
| 2 | Data | данные |
| 3 | Ack | подтверждение |
| 4 | DataAck | данные + подтверждение |
| 5 | CloseReq | запрос закрытия |
| 6 | Close | закрытие |
| 7 | Reset | сброс |

Установка — **двухсторонняя**: `Request → Response`. Никакого трёхстороннего рукопожатия, как в TCP.

## Шаг 3: короткий заголовок

Когда в заголовке нет опций (поле **X=0**), он занимает всего **16 байт**:

| Поле | Размер | Смысл |
|------|--------|-------|
| Src/Dst port | 4 | порты |
| Data Offset | 1 | длина заголовка |
| CCVal/CsCov/Checksum | 3 | контроль перегрузки + checksum |
| Type/Reserved/X | 1 | тип пакета и флаг X |
| Sequence Number | 6 | 48-битный номер (опционально) |

48-битный номер последовательности — заметная редкость.

## Шаг 4: согласование фич

Перед данными стороны договариваются о **фичах** (Feature Negotiation): например, `CCID` (алгоритм перегрузки), `Sequence Window`, `Allow Short Seqnos`. Фича кодируется парой «номер фичи + значение», и её можно менять в обе стороны. Именно здесь рождаются расхождения: если одна сторона поддерживает фичу, а другая нет — соединение может не подняться.

## Шаг 5: безопасность и почему DCCP не взлетел

RFC 5595 добавил **аутентификацию** (challenge/response на основе пароля), но она опциональна. Из-за сложности, слабой поддержки в ОС и NAT-проблем DCCP почти не используется. Именно поэтому трафик DCCP **редко логируется** — и потому его любят как транспорт для обходов и скрытых каналов.

## Полный прогон: разбираем дамп

```
$ cat dccp.log
DCCP Request  port=5000 Service Code=0x00000001
DCCP Response port=5000 ack=1
DCCP feature:bnRve2RjY3BfZjM0dHVyM19uM2cwdH0=
$ grep feature: dccp.log | cut -d: -f2 | base64 -d
nto{dccp_f34tur3_n3g0t}
```

Мы нашли согласование фич (в логе поле `feature:` в base64) и декодировали флаг. Запиши его в `answer.txt` и набери `check`.

## Что мы теперь знаем

- DCCP — датаграммы + управление перегрузкой, с разными CCID.
- Установка соединения — Request/Response (два пакета).
- Короткий заголовок (X=0) — 16 байт; есть 48-битный номер последовательности.
- Фичи согласуются; аутентификация опциональна; DCCP редок и потому удобен для обходов.

## Сравнение транспортов: TCP, UDP, SCTP, DCCP

Чтобы понять место DCCP, полезно поставить четыре протокола рядом.

| Свойство | TCP | UDP | SCTP | DCCP |
|---|---|---|---|---|
| Соединение | да | нет | да (ассоциация) | да |
| Гарантия доставки | да | нет | да | нет |
| Порядок | да | нет | да (по потокам) | нет |
| Контроль перегрузки | да | нет | да | да |
| Границы сообщений | нет | да | да | да |
| Мультихоминг | нет | нет | да | нет |

Видно «нишу» DCCP: там, где нужны границы сообщений и контроль перегрузки, но не нужны повторы — например, интерактивное видео. UDP такой трафик пропускает, но не тормозит при перегрузке; TCP тормозит, но копит задержку повторами.

## Как DCCP проходит через NAT и фильтры

Практическая проблема DCCP — **NAT**. Большинство домашних и офисных NAT-устройств знают только TCP и UDP. DCCP-пакет для них — «неизвестный IP-протокол», и они либо отбрасывают его, либо не создают трансляцию. Из этого следуют два вывода.

Первый: DCCP почти не работает «из дома», поэтому в интернете его мало. Второй, важный для пентеста: если политика периметра сформулирована как «разрешить известное», DCCP пройдёт молча. Это классическая слепая зона.

```
$ nmap -sO -p 33 10.0.0.9 -Pn
33/ip  protocol  open
```

Ответ `open` означает, что хост отвечает на DCCP (или на ICMP protocol-unreachable не пришёл). Если в ответ тишина — протокол, скорее всего, не поддерживается.

## Практика: чтение DCCP-заголовка

DCCP-заголовок начинается как у TCP — с портов. Дальше идёт байт с типом пакета (старшие 4 бита) и flags. Минимальный заголовок — 16 байт для Data (порты 4, тип 1, sequence 6, ...). Полезно запомнить: если в hex на месте, где TCP имел бы SEQ/ACK, лежит что-то короткое — перед тобой, возможно, DCCP.

```
$ tshark -r dccp.pcap -V | sed -n '/DCCP/,/Data/p' | head -12
    Datagram Congestion Control Protocol
    Source Port: 5001
    Destination Port: 5001
    Type: Request (0)
    Sequence Number: 0
    Feature: CCID (mandatory, 3)
```

Ключевое отличие от TCP — наличие **features** вместо options и отсутствие флагов в привычном смысле.

## Типичные ошибки

Первая — считать, что «если не TCP/UDP, то ICMP»: есть ещё SCTP, DCCP, GRE, ESP. Вторая — думать, что раз протокол редкий, он «безопасен»: редкое хуже инспектируется. Третья — путать DCCP Request/Response с TCP SYN/SYN-ACK: семантика и набор параметров другие. Четвёртая — не проверять поддержку протокола на хосте перед выводами о фильтрации.

## Шаг 6: CCID и управление перегрузкой

DCCP параметризуется **CCID** (Congestion Control ID). `CCID2` — алгоритм, близкий к TCP (AIMD), подходит для интерактивных приложений. `CCID3` — «TCP-Friendly Rate Control» для потокового медиа: он сглаживает скорость, чтобы не «дёргать» видео. Стороны согласуют CCID как **фичу** при установке соединения.

Смысл в том, что приложению не нужно само реализовывать вежливость к сети — она встроена в транспорт. Это главное отличие DCCP от UDP, где управление перегрузкой (если оно есть) лежит на приложении.

## Шаг 7: атаки и обход

- **согласование фич** — если стороны по-разному понимают фичу, соединение может «зависнуть» или принять неверные параметры;
- **редкость транспорта** — DCCP часто не разбирается IDS/файрволами, поэтому через него удобно проксировать трафик;
- **NAT-проблемы** — многие NAT не умеют DCCP, что само по себе создаёт нестабильность;
- **аутентификация опциональна** — без неё соединение можно подделать.

Практический вывод: DCCP — нишевый, но «невидимый» транспорт. В пентесте его используют для обхода фильтров, в SOC — как индикатор нестандартной активности.

## Разбор реального дампа: типы и фичи

```
$ cat dccp.log
DCCP Request  port=5000 Service Code=0x00000001
DCCP Response port=5000 ack=1
DCCP feature:bnRve2RjY3BfZjM0dHVyM19uM2cwdH0=
```

`Request`/`Response` — установка соединения; `Service Code` — «порт» прикладного уровня (как у RTP/телефонии). Строка с `feature:` — согласование фичи, содержимое в base64.

## Инструменты и защита

- `tshark -r dump.pcap -Y dccp -T fields -e dccp.type` — типы пакетов;
- `iperf3 --dccp` (где поддерживается) — проверка транспорта;
- `nmap -sU -p 5000` — поиск открытых портов.

Защита: блокировать DCCP на периметре, если он не используется; включать аутентификацию (RFC 5595); мониторить появление DCCP как аномалию. Для SOC — правило на IP-протокол 33 в недоверенных сегментах.

## Когда DCCP всё-таки встречается

DCCP применяли в исследовательских и медиа-проектах, но массовым он не стал. Встретить его можно в: специализированных медиа-серверах, тестовых стендах, редких P2P-приложениях и в учебных дампах. Для CTF это удобный «экзотический» транспорт: он есть в Wireshark, но редко узнаётся с первого взгляда. Понимая его заголовок и типы, ты сможешь быстро сориентироваться там, где остальные ищут TCP/UDP и не находят ничего.

## Практический чек-лист разбора DCCP

1. **Опознай протокол.** `tshark -r dump.pcap -Y dccp`; если пусто — попробуй фильтр по IP-протоколу 33.
2. **Определи тип.** `-T fields -e dccp.type`: Request/Response/Data/Ack/Close.
3. **Прочитай Service Code.** Он играет роль порта прикладного уровня.
4. **Найди фичи.** Согласование CCID и других параметров — начало сессии.
5. **Проверь аутентификацию.** Есть ли challenge (RFC 5595) или нет — от этого зависит подделываемость.
6. **Оцени контекст.** DCCP в обычной корпоративной сети — почти наверняка аномалия или обход.

Результат: подтверждение нестандартного транспорта и, если есть, параметры сессии. Для защищающегося — блокировка DCCP на периметре и правило на протокол 33; для пентеста — способ пройти мимо фильтров, которые «знают» только TCP/UDP.
