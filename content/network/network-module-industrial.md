## Вопрос, с которого всё начинается

На заводе, в энергосети и в умном здании работают **PLC** (программируемые логические контроллеры) — маленькие компьютеры, которые читают датчики и дёргают реле. Общаются они по протоколам, придуманным для надёжности, а не для безопасности. Если атакующий дотянется до сети контроллеров, он может не «украсть данные», а **изменить физический процесс**: закрыть клапан, отключить питание, сорвать технологический цикл.

Этот модуль — про четыре самых распространённых ICS-протокола и про то, как их читать и защищать. Опирается на [`network-module-embedded`](network-module-embedded).

## Общая картина ICS

Промышленная сеть делится на уровни (модель Purdue): датчики и приводы → контроллеры (PLC/RTU) → SCADA/HMI → корпоративная сеть. Каждый уровень говорит своим протоколом:

| Протокол | Домен | Транспорт | Особенность |
|---|---|---|---|
| BACnet | здания (HVAC, доступ) | UDP 47808 | объекты и свойства, broadcast |
| IEC 60870-5-104 | энергетика, телеметрия | TCP 2404 | APCI/ASDU, обмен «станция-контроллер» |
| IEC 61850 (MMS/GOOSE) | подстанции | TCP 102 / L2 | GOOSE — по Ethernet, без IP |
| S7comm | Siemens PLC | TCP 102 (ISO-TSAP) | read/write/stop, загрузка логики |

## Почему это опасно

Все четыре протокола исторически **не имеют аутентификации**. У BACnet достаточно знать объект и свойство, чтобы прочитать или записать значение. У S7comm функция «Stop» останавливает PLC одним пакетом. У IEC 104 команда `C_SC_NA_1` (single command) может переключить выключатель. А **GOOSE** в IEC 61850 передаётся прямо в Ethernet-кадре, поэтому его легко подделать из той же L2-сети.

## Как это выглядит в дампе

```
$ tshark -r ics.pcap -Y "bacnet" -T fields -e ip.src -e bacnet.object.type -e bacnet.property.id
10.0.0.20	0	85
$ tshark -r iec.pcap -Y "iec60870_asdu.typeid==45" -T fields -e ip.dst -e iec60870_asdu.ioa
10.0.0.5	1
$ tshark -r s7.pcap -Y "s7comm.param.func==0x05" -T fields -e ip.src
10.0.0.7
```

`bacnet.object.type==0` — Analog Input, `iec60870_asdu.typeid==45` — одиночная команда (C_SC_NA_1), `s7comm.param.func==0x05` — функция Write Var. Такие фильтры — основа и разбора CTF-дампов, и правил детекта в SOC.

## Правила работы в OT

- **Пассивно**: сначала зеркалируйте трафик, не сканируйте.
- **Read-only**: если нужно активное — только чтение, с согласия заказчика.
- **Не валить**: даже «просто скан» портов может уронить старый PLC.
- **Изолировать**: пентест OT обычно ведут в отдельном сегменте или на стенде-двойнике.

## Протоколы ICS и их поверхность

Основные протоколы ICS: **Modbus** (простой, read/write регистров без аутентификации), **PROFINET** (промышленный Ethernet), **EtherNet/IP** (CIP поверх TCP/UDP), **DNP3** (энергетика, есть secure-вариант), **IEC 61850** (подстанции), **OPC UA** (современный, есть безопасность). Каждый работает поверх TCP/UDP, чаще всего без шифрования.

```text
Modbus/TCP:502  EtherNet/IP:44818  DNP3:20000  OPC UA:4840
```

Поверхность атаки: анонимное чтение (разведка), анонимная запись (воздействие), DoS (flood), эксплойты парсеров. Инструменты инвентаризации — NSE-скрипты nmap: `modbus-discover`, `enip-info`, `bacnet-info`, `opcua-info`.

## Модель Purdue и сегментация

Модель Purdue делит сеть на уровни: L0 (физический процесс), L1 (контроллеры), L2 (supervisory/SCADA), L3 (operations), L3.5 (DMZ), L4/L5 (IT). Между уровнями — межсетевые экраны. Атака «сверху вниз» из IT в OT возможна, если сегментация слабая.

```text
L4/L5 IT --DMZ-- L3 ops -- L2 SCADA -- L1 PLC -- L0 field
```

Ключевые находки аудита: отсутствие DMZ, прямой маршрут IT→OT, общие учётки, открытые порты протоколов в IT-сегменте. Защита — строгая сегментация, DMZ с прокси, мониторинг трафика между уровнями.

## Как выглядит дамп ICS и что искать

В дампе ICS ты видишь периодические запросы SCADA к ПЛК (read registers) и управляющие записи. Разбор: `tshark -Y "modbus || enip || bacnet"`. Что искать: какие регистры читаются/пишутся, кто инициатор, есть ли аномальные записи.

```bash
tshark -r ot.pcap -Y modbus -T fields -e ip.src -e modbus.func_code | sort | uniq -c
```

Практический вывод: даже пассивный анализ даёт карту процесса и точки воздействия. Активные проверки — только чтение. Записывай всё в отчёт: устройства, протоколы, периодичность, отсутствие сегментации.

## Как проводить аудит ICS-сети

Методика: (1) собрать инвентарь активов (активно — осторожно, пассивно — из трафика); (2) определить протоколы и порты; (3) построить карту «кто с кем говорит»; (4) оценить сегментацию (IT↔OT); (5) проверить аутентификацию (обычно её нет); (6) оценить возможность записи; (7) сформулировать риски для производства и безопасности людей.

```bash
tshark -r ot.pcap -T fields -e ip.src -e ip.dst -e _ws.col.Protocol | sort | uniq -c
```

Пассивный анализ безопасен и даёт 80% картины. Активные проверки (чтение identity) — только с согласованием и в окно работ. Запись — никогда на продакшне.

## Инструменты и отчёт по ICS

Инструменты: `nmap` с ICS-скриптами (`modbus-discover`, `s7-info`, `enip-info`, `bacnet-info`), `wireshark`/`tshark` для разбора, `plcscan`, `modbus-cli`, `GRASSMARLIN` для карты сети. Отчёт: список устройств, протоколы, отсутствие сегментации, открытая запись, риски для производства, рекомендации (DMZ, сегментация, мониторинг, патч-менеджмент).

```bash
nmap -sT -Pn -p 502,102,44818,47808 --script modbus-discover,s7-info <subnet>
```

Важно: в OT-отчёте всегда указывай влияние на непрерывность производства и безопасность людей, а не только техническую критичность.

## Разбор примера: Modbus-запись

Разберём, как выглядит запись в ПЛК по Modbus/TCP. Функция `0x06` (Write Single Register) или `0x10` (Write Multiple Registers) меняет регистр. В дампе это `tshark -Y "modbus.func_code == 6 || modbus.func_code == 16"`.

```text
Modbus/TCP: [MBAP header][func 0x06][addr][value]
```

Если в дампе есть записи от SCADA — это легитимное управление. Если появляются записи от неизвестного IP — аномалия. Именно так детектируют компромисс SCADA.

Для пентеста: достаточно показать, что запись технически возможна (нет аутентификации) и какие регистры управляют процессом. Реальную запись не выполняй.

## Разбор примера: DNP3 в энергетике

DNP3 — протокол энергетики. В дампе видны `Read`/`Write`/`Operate` к outstation. Классическая атака — `Operate` (управление выключателем). DNP3 Secure Authentication (SAv5) добавляет HMAC, но включают её редко.

```bash
tshark -r dnp3.pcap -Y "dnp3" | head
```

Что искать: незащищённые `Operate`, открытые порты 20000, отсутствие аутентификации. В энергетике последствия особенно серьёзны, поэтому работа — только пассивная.

## Практический чек-лист аудита ICS

1. Инвентарь устройств (пассивно из трафика + осторожный nmap).
2. Протоколы и порты (Modbus 502, PROFINET 102, EtherNet/IP 44818, DNP3 20000, OPC UA 4840).
3. Карта «кто с кем говорит» (SCADA↔PLC, HMI↔PLC).
4. Сегментация IT↔OT (есть ли DMZ, прямой маршрут).
5. Аутентификация (обычно нет).
6. Возможность записи (управляющие регистры).
7. Риски для производства и безопасности людей.

```bash
tshark -r ot.pcap -T fields -e ip.src -e ip.dst -e _ws.col.Protocol | sort | uniq -c | sort -rn | head
```

Отчёт: устройства, протоколы, отсутствие сегментации, открытая запись, рекомендации (DMZ, сегментация, мониторинг, патчи). Всегда указывай влияние на непрерывность производства.

## Итог по ICS

ICS — сеть, где приоритет доступность и безопасность людей. Протоколы без аутентификации, legacy-устройства, слабая сегментация. Подход: инвентарь → пассивный анализ → осторожные проверки → отчёт. Инструменты: `nmap` (NSE), `tshark`, `GRASSMARLIN`. Запись — только на стенде.

## Расширенный разбор: аномалии в ICS-трафике

Базовая линия ICS-трафика стабильна: SCADA периодически опрашивает одни и те же регистры. Аномалия — новый инициатор, новая периодичность, записи от неизвестного IP, сканирование портов. Такие отклонения — признак компромисса.

```text
baseline: PLC <- SCADA (read, 1Hz)
anomaly:  PLC <- unknown (write)  -> compromise
```

Для детекта нужна базовая линия (обычно её нет) и мониторинг (NetFlow, IDS с ICS-правилами, например Suricata с Modbus/DNP3). Для пентеста — фиксируй аномалии, которые ты создаёшь, чтобы не «потерять» их в шуме.

## Резюме по ICS

ICS-аудит: инвентарь → протоколы → карта связей → сегментация → аутентификация → возможность записи → риски. Приоритет — доступность и безопасность людей, поэтому активные действия минимальны. Инструменты: `nmap` NSE, `tshark`, `GRASSMARLIN`. В отчёте указывай влияние на производство.

## Что запомнить

В ICS приоритет — непрерывность производства и безопасность людей, а не конфиденциальность данных. Поэтому аудит начинается с инвентаря и пассивного анализа, а активные действия (даже чтение) согласовываются и выполняются в окно работ. Типичные находки — отсутствие сегментации IT↔OT, анонимное чтение/запись в ПЛК, legacy-устройства без патчей. Отчёт должен связывать техническую находку с последствием для процесса: «запись в регистр X меняет уставку насоса» звучит сильнее, чем «порт 502 открыт».

## Куда дальше

Дальше начнём с BACnet — протокола умных зданий, где объекты читаются и пишутся почти без защиты. А пока запомни: ICS-протоколы не имеют аутентификации, и в OT-пентесте безопасность процесса важнее полноты скана.

## Где пригодится

- **CTF:** категория Network — ICS-дампы (BACnet/IEC/S7comm).
- **Пентест:** АСУ ТП, SCADA, промышленные сети.
- **Работа (SOC):** детект команд записи и остановки PLC.
- **Карьера:** OT-security, промышленная кибербезопасность.
