BGP — протокол маршрутизации между автономными системами (AS), на котором держится весь интернет. В отличие от внутренних протоколов, BGP доверяет соседям: если сосед объявил маршрут к чужому префиксу, по умолчанию никто не проверяет, имеет ли он право на него. Это и есть корень большинства «инцидентов маршрутизации» — от случайных утечек до целенаправленного перехвата трафика.

## Основы BGP для безопасника

BGP-сессия устанавливается между двумя маршрутизаторами (обычно по TCP/179) и обменивается **анонсами** (announce) и **отзывами** (withdraw) префиксов. Каждый маршрут несёт атрибуты; важнейшие:

- **AS_PATH** — последовательность AS, через которые прошёл анонс. Используется для выбора лучшего пути (короткий предпочтительнее) и для петель.
- **NEXT_HOP** — куда слать пакеты.
- **LOCAL_PREF** — приоритет внутри AS (eBGP обычно перекрывает).
- **MULTI_EXIT_DISC (MED)** — подсказка соседней AS.
- **COMMUNITY** — метки, которыми соседи управляют политикой.

**Правило выбора BGP** (упрощённо): самый длинный совпадающий префикс выигрывает в таблице форвардинга; при равной длине — по весу, local-pref, длине AS_PATH, origin, MED, eBGP над iBGP и т.д.

| Атрибут | Смысл |
|---|---|
| AS_PATH | Путь через AS, влияет на выбор |
| NEXT_HOP | Следующий хоп |
| LOCAL_PREF | Приоритет внутри AS |
| MED | Пожелание соседу |
| COMMUNITY | Политические метки |

## Классы атак на BGP

- **Prefix hijack** — AS объявляет префикс, ей не принадлежащий. Если анонс «длиннее» (более специфичный), он выигрывает у легитимного: например, `1.2.3.0/25` перебивает `1.2.3.0/24`.
- **Sub-prefix hijack** — атака через более специфичный префикс; не требует отзыва чужого маршрута.
- **Route leak** — AS по ошибке (или злонамеренно) переотдаёт маршруты, полученные от одного провайдера, другому. Классический пример — инцидент 2008 года с Pakistan Telecom и YouTube.
- **AS-path manipulation** — вставка/удаление AS в пути для обхода фильтров или притягивания трафика.
- **BGP session reset** — RST-инъекция в TCP-сессию BGP (без MD5/AO) для сброса соседства и перестройки маршрутов.
- **BGP hijack для MITM** — перехват трафика на себя с последующей пересылкой (для прослушки/подмены).

## Инструменты и команды

- **whois / bgp.he.net** — ASN, префиксы, апстримы.
- **Team Cymru whois** — маппинг IP → ASN.
- **bgpdump / MRT-парсеры** — анализ архивов RouteViews/RIPE RIS.
- **RIPE RIS / RouteViews** — исторические таблицы маршрутизации.
- **BGPStream** — потоковый мониторинг аномалий.
- **RPKI-валидаторы** (`routinator`, `rpkivalidator`, `rpki-client`).

Проверить принадлежность префикса и апстримы:

```bash
whois -h whois.cymru.com " -v 8.8.8.8"
whois -h whois.radb.net -- '-i origin AS15169'
# на bgp.he.net: https://bgp.he.net/AS15169
```

Анализ MRT-дампа из RouteViews:

```bash
bgpdump -m rib.20240101.0000.bz2 | grep '8.8.8.0/24'
# вывод: BGP4MP|...|A|8.8.8.0/24|8.8.8.0|15169 3356 ...|IGP|...
```

## Разобранный пример: детект sub-prefix hijack

1. Берём два снимка таблицы (t0 и t1) из RouteViews для интересующего префикса.
2. Ищем в t1 маршрут к под-префиксу, которого не было в t0, с origin-AS, отличным от легитимного:
   ```bash
   bgpdump -m ris.2024*.bz2 | awk -F'|' '$6 ~ /^203\.0\.113\.0\/2[5-9]/ {print $5,$6}'
   ```
3. Сверяем origin AS с записью в IRR/ROA. Если ROA нет или origin не совпадает — это кандидат в hijack.
4. Для валидации используем RPKI: `routinator vrps` и сопоставляем. Статус **Invalid** у анонса — сильный сигнал.

## Защита: RPKI, ROA, фильтрация

| Механизм | Что делает |
|---|---|
| ROA (Route Origin Authorization) | Крипто-подпись: какой AS вправе анонсировать префикс |
| RPKI | PKI-инфраструктура, распространяющая ROA |
| ROV (Route Origin Validation) | Маршрутизатор отбрасывает Invalid-анонсы |
| IRR-фильтрация | Фильтр по базе зарегистрированных объектов |
| Max-prefix limit | Ограничение числа анонсов от соседа |
| Peer-lock / prefix-list | Жёсткие списки разрешённых префиксов |
| TCP-MD5 / TCP-AO | Защита сессии BGP от RST-инъекции |

RPKI сегодня развёрнута у крупных операторов, но покрытие ROA неполное — поэтому hijack всё ещё возможен. На практике наиболее эффективны **фильтры префиксов у соседей** и **ROV**.

## Частые ошибки и подводные камни

- **Считать, что «интернет сам исправится».** Пока легитимный оператор не отзовёт/переанонсирует, трафик может идти через хайджекинутый путь часами.
- **Путать route leak и hijack.** Leak — переотдача чужих маршрутов; hijack — анонс чужого префикса как своего.
- **Игнорировать более специфичные префиксы.** `/25` всегда выиграет у `/24`, даже если это «незаконно».
- **Полагаться только на RPKI.** ROA защищает origin, но не AS_PATH; path-манипуляции RPKI не ловит.
- **Забывать про MOAS.** Несколько origin AS для одного префикса (multi-origin) — норма, но и почва для атак.

## Что дальше / решение

BGP-безопасность — это про мониторинг и фильтрацию: разверните RPKI-валидацию, ведите prefix-list у пиров, включите max-prefix и TCP-AO. Для анализа инцидентов освойте BGPStream и MRT. Дальше смотрите `network-routing` и `network-ntp-attacks` — вместе они дают картину атак на инфраструктуру. Для CTF/лабораторий поднимайте виртуальную топологию (GNS3/Containerlab) с FRR/BIRD и эмулируйте hijack, чтобы увидеть выбор пути вживую.

## История реальных инцидентов

Понимание угрозы лучше всего строится на реальных случаях:

- **2008, Pakistan Telecom vs YouTube.** Оператор, пытаясь заблокировать YouTube у себя, анонсировал `208.65.153.0/24` в мир. Из-за ошибки фильтрации анонс ушёл апстриму, и глобальный трафик YouTube на время ушёл в Пакистан. Классический route leak/hijack.
- **2018, Amazon Route 53 / MyEtherWallet.** Хайджекинг DNS/BGP-инфраструктуры привёл к перенаправлению пользователей на фишинговый сайт — пример атаки через маршрутизацию на крипто-кошельки.
- **2019, анонс множества префиксов небольшой AS.** Из-за ошибки конфигурации один оператор «всосал» трафик к десяткам тысяч префиксов; часть сервисов деградировала.
- **2021, Facebook outage.** Не hijack, но показательный пример: сбой отзыва BGP-маршрутов отрезал дата-центры Facebook от интернета — демонстрирует, насколько критична маршрутизация.

Из этих кейсов следуют выводы: (1) route leak часто случается из-за неверных `prefix-list`/`route-map`; (2) hijack может быть целенаправленным и служить MITM; (3) последствия глобальны и устраняются часами.

## Лаборатория: симуляция hijack

Чтобы увидеть выбор пути своими глазами, поднимите топологию из четырёх AS в **Containerlab** или GNS3 с FRR (или BIRD). Пример на FRR:

```
! на AS100 (жертва) анонсируем 203.0.113.0/24
router bgp 100
  network 203.0.113.0/24
! на AS200 (атакующий) анонсируем тот же префикс, но /25
router bgp 200
  network 203.0.113.0/25
```

Подключите обе AS к общей AS300 (наблюдатель). Наблюдайте в `show ip bgp 203.0.113.0/25`: маршрут к /25 придёт от AS200, а /24 — от AS100. Трафик к адресам из диапазона /25 уйдёт к атакующему. Затем включите RPKI: создайте ROA для /24 с origin AS100, поднимите `routinator`, включите ROV на AS300 — анонс /25 от AS200 станет **Invalid** и будет отброшен. Так вы на практике видите, что даёт RPKI и чего он **не** ловит (path-манипуляции остаются).

## Мониторинг и алертинг

Постоянный мониторинг строится на потоке MRT-данных из RouteViews/RIPE RIS. Практический стек:

```bash
# скачиваем последний RIB и updates, парсим bgpdump
curl -s https://archive.routeviews.org/route-views2/bgpdata/.../updates.*.bz2 | bgpdump -m -
# ищем аномалии: новый origin для префикса, всплеск withdraw
```

BGPStream (CAIDA) позволяет в реальном времени подписаться на обновления и применять фильтры: префикс, AS, тип сообщения. Сервисы вроде BGPmon/Cloudflare Radar дают визуализацию hijack-событий. Для своей AS полезно писать собственные «sanity checks»: (a) origin-AS не из ожидаемого набора, (b) AS_PATH содержит запрещённые AS, (c) внезапный рост числа анонсов от пира (признак leak), (d) более специфичные префиксы внутри своих /24. Эти четыре проверки ловят большинство инцидентов.

## Где пригодится

- **Пентест/red team:** понимание перехвата трафика на уровне оператора, оценка устойчивости клиента.
- **Работа/SOC:** анализ инцидентов маршрутизации, мониторинг аномалий BGP.
- **CTF:** задачи на выбор пути и анализ MRT-дампов.
- **Сертификации:** сетевые/операторские треки (CCNP/CCIE-безопасность, JNCIS).
