## Вопрос, с которого всё начинается

У тебя есть foothold `10.10.10.50` и SSH-доступ к нему. Ты поднял динамический порт (`ssh -D`), но половина твоих инструментов «не понимает» SOCKS и лезет в сеть напрямую. Как вообще работает прокси под капотом — и как протащить через него любой инструмент?

Прокси — самый доступный способ pivoting: он не требует прав на инкапсуляцию и часто разрешён наружу. Разберём два главных протокола — **SOCKS** и **HTTP CONNECT**.

## Наш пример: прокси на foothold

Поднимаем SOCKS-прокси через скомпрометированный хост:

```
$ ssh -D 1080 -N -f user@10.10.10.50
$ ss -ltnp | grep 1080
tcp LISTEN 0 128 127.0.0.1:1080 0.0.0.0:* users:(("ssh",pid=4421,fd=6))
```

Теперь `127.0.0.1:1080` — это SOCKS-прокси, за которым видно внутреннюю сеть. Но что именно происходит при соединении?

## Шаг 1: SOCKS — что за ним стоит

Прокси — посредник: клиент адресует запрос прокси, а тот сам соединяется с целью и релеит данные. Бывает **forward proxy** (для клиентов, наш случай) и **reverse proxy** (для серверов).

**SOCKS5** — прикладной протокол. Клиент здоровается тремя байтами: версия, число методов, метод. Проверим руками:

```
$ printf '\x05\x01\x00' | nc -w1 127.0.0.1 1080 | xxd
00000000: 0500                                     ..
```

`05 00` — сервер принял: `VER=5`, метод `0` (без аутентификации). Затем клиент шлёт запрос: `CMD=connect`, тип адреса, адрес и порт. `SOCKS4` умел только TCP/IPv4 и без аутентификации; `SOCKS5` добавил UDP, IPv6 и методы аутентификации (none, user/pass, GSSAPI).

## Шаг 2: HTTP CONNECT

Если наружу открыт только HTTP-прокси, работает метод **CONNECT**. Он превращает прокси в TCP-релей:

```
$ printf 'CONNECT internal.local:443 HTTP/1.1\r\nHost: internal.local:443\r\n\r\n' | nc proxy 3128
HTTP/1.1 200 Connection established
```

После ответа `200` прокси просто пропускает байты в обе стороны. Это стандартный путь для HTTPS через прокси — и удобный канал для туннелирования произвольного TCP.

## Шаг 3: проксификация инструментов через proxychains

Не все инструменты умеют SOCKS. `proxychains` перехватывает сетевые вызовы и заворачивает их в прокси:

```
$ cat /etc/proxychains4.conf
strict_chain
proxy_dns
[ProxyList]
socks5 127.0.0.1 1080

$ proxychains4 nmap -sT -Pn -p 22,80,445 10.10.20.0/24
PORT     STATE SERVICE
10.10.20.5 22/tcp  open  ssh
10.10.20.5 445/tcp open  microsoft-ds
$ proxychains4 curl http://10.10.20.5/
```

Два подводных камня. Первый: `nmap` без `-sT` (SYN-скан) через прокси не работает — прокси даёт только готовые TCP-соединения. Второй: `proxy_dns` (или `socks5h`) нужен, чтобы DNS-резолвинг тоже шёл через прокси, иначе имена утекают напрямую.

## Шаг 4: чем прокси отличается от туннеля

| Протокол | TCP | UDP | Аутентификация |
|---|---|---|---|
| SOCKS4 | да | нет | нет |
| SOCKS4a | да | нет | имена на прокси |
| SOCKS5 | да | да | none/user-pass |
| HTTP CONNECT | да | нет | basic |

Прокси работает на прикладном уровне и **не шифрует** — он только релеит. Туннель (например, SSH `-w` или GRE) работает на сетевом уровне и может нести любой IP-протокол. Поэтому SOCKS5 через SSH — универсальный выбор, HTTP CONNECT — когда наружу открыт только прокси, а для UDP нужен именно SOCKS5.

## Шаг 5: детект и защита

Прокси-pivoting виден по поведению. Ищем CONNECT-запросы к внутренним адресам и SOCKS-рукопожатия:

```
$ tshark -r cap.pcap -Y 'http.request.method=="CONNECT"' \
    -T fields -e http.host -e ip.dst | sort | uniq -c | sort -rn | head
$ tshark -r cap.pcap -Y 'tcp.len>0 && tcp.port==1080' -T fields -e tcp.payload | head
```

Признаки: один источник обращается к множеству внутренних адресов, CONNECT к нестандартным портам (22, 445, 3389), SOCKS-рукопожатия внутри сети. Защита — запретить CONNECT к внутренним подсетям, требовать аутентификацию прокси и мониторить необычные цели.

## Продвинутая настройка proxychains

Цепочки нужны, когда путь идёт через несколько прокси. Режимы `proxychains`:

- `strict_chain` — строгий порядок, все прокси обязательны;
- `dynamic_chain` — пропускает мёртвые прокси;
- `random_chain` — рандомизирует порядок (для обхода корреляции).

```
$ cat /etc/proxychains4.conf
dynamic_chain
proxy_dns
[ProxyList]
socks5 127.0.0.1 1080
socks5 127.0.0.1 1081
```

Инструменты, которые не умеют SOCKS, заворачиваются так:

```
$ proxychains4 curl http://10.10.20.5/
$ proxychains4 smbclient -L 10.10.20.5
$ proxychains4 hydra -L users -P pass ssh://10.10.20.5
```

Важно: `proxychains` перехватывает `connect()` через `LD_PRELOAD`, поэтому статические бинарники и сырые сокеты (SYN-скан) его обходят.

## Чек-лист прокси-pivoting

1. Какой прокси разрешён наружу (SOCKS/CONNECT)?
2. Есть ли аутентификация (или прокси открыт)?
3. Настроен ли DNS через прокси (`socks5h`/`proxy_dns`)?
4. Работает ли connect-скан (`-sT`)?
5. Нужен ли UDP (тогда SOCKS5)?
6. Сколько звеньев цепочки нужно?

```
$ curl -v --socks5 127.0.0.1:1080 http://example.com 2>&1 | head
$ proxychains4 -q curl -s ifconfig.me
```

Вывод: SOCKS5 через SSH — универсальный выбор; HTTP CONNECT — когда наружу открыт только прокси; для UDP — SOCKS5.

## Детект и защита прокси-pivoting

Прокси-pivoting виден по поведению. CONNECT-запросы к внутренним адресам и SOCKS-рукопожатия — прямые признаки:

```
$ tshark -r cap.pcap -Y 'http.request.method=="CONNECT"' \
    -T fields -e http.host -e ip.dst | sort | uniq -c | sort -rn | head
$ tshark -r cap.pcap -Y 'tcp.len>0 && tcp.port==1080' -T fields -e tcp.payload | head
```

| Мера | Эффект |
|---|---|
| Запретить CONNECT к внутренним подсетям | ломает pivoting |
| Аутентификация прокси | закрывает open proxy |
| Egress-allowlist | ограничивает туннели наружу |
| Сегментация + межсегментный firewall | ограничивает охват |

Прокси-pivoting трудно устранить полностью (наружу часто разрешён HTTPS), но можно резко ограничить: запретить CONNECT к внутренним адресам, требовать аутентификацию и мониторить необычные цели.

## Что мы теперь знаем

- SOCKS5 — прикладной прокси: TCP, UDP, IPv6, аутентификация.
- HTTP CONNECT превращает HTTP-прокси в TCP-релей.
- `proxychains` заворачивает инструменты в SOCKS, но `nmap` только в `-sT`.
- `proxy_dns`/`socks5h` не дают утечь DNS-запросам.
- Прокси не шифрует; туннель работает уровнем ниже и несёт любой протокол.

## Куда дальше

Мы разобрали прикладные прокси. Дальше — сетевые туннели уровнем ниже: GRE и VXLAN, которые несут любой протокол и потому не зависят от ограничений SOCKS. А пока запомни: **прокси релеит соединения, но не шифрует — и его легко заметить по CONNECT и SOCKS-рукопожатиям.**
