Промышленные сети (OT/ICS) управляют физическим миром: датчиками, приводами, реле. Протоколы (Modbus, DNP3, S7) проектировались для **надёжности и простоты**, а не безопасности — в них часто нет ни аутентификации, ни шифрования. Анализ их на проводе позволяет понять состояние процесса и найти опасные операции. Урок опирается на [`network-protocol-reversing`](network-protocol-reversing) и [`network-pcap-analysis`](network-pcap-analysis).

## Особенности OT-мира

- Приоритет: **availability** > integrity > confidentiality.
- Протоколы **без аутентификации/шифрования** (историческое наследие).
- Смешение IT и OT (конвергенция) расширяет поверхность атаки.
- Воздействие **физическое**: ошибка может остановить производство/навредить.
- Устаревшие ОС/устройства, которые нельзя быстро пропатчить.

## Основные протоколы

| Протокол | Порт | Особенности |
|----------|------|-------------|
| **Modbus/TCP** | 502 | простой, request/response, функция + данные |
| **DNP3** | 20000 | используется в энергетике, есть аутентификация (SAv5) опционально |
| **S7comm** | 102 | Siemens, поверх ISO-TSAP (TPKT/COTP) |
| **EtherNet/IP** | 44818 | Rockwell/Allen-Bradley |
| **BACnet** | 47808 | здания/HVAC |
| **IEC 60870-5-104** | 2404 | энергетика |

## Modbus на проводе

Кадр Modbus/TCP = **MBAP-заголовок** (7 байт: transaction, protocol, length, unit id) + **PDU** (function code + data).

Функции:

- `0x01` read coils, `0x02` read discrete inputs
- `0x03` read holding registers, `0x04` read input registers
- `0x05` write single coil, `0x06` write single register
- `0x0F` write multiple coils, `0x10` write multiple registers

```bash
# Фильтр Modbus в Wireshark/tshark
tshark -r ot.pcap -Y 'modbus' -T fields -e modbus.func_code -e modbus.reference_num
# Только запись (опасные операции)
tshark -r ot.pcap -Y 'modbus.func_code==6 or modbus.func_code==16'
```

Запись (0x05/0x06/0x0F/0x10) — самая опасная категория: она меняет состояние процесса. В анализе трафика всегда отделяйте чтения от записей.

## Инструменты и команды

```bash
# Сканирование Modbus
nmap -p502 --script modbus-discover 10.0.0.5
# Чтение/запись (mbtget / pymodbus)
mbtget -r 0 -n 10 -a 1 10.0.0.5
python3 - <<'PY'
from pymodbus.client import ModbusTcpClient
c = ModbusTcpClient("10.0.0.5")
print(c.read_holding_registers(0, 10, unit=1))
PY
# DNP3 / S7
nmap -p20000 --script dnp3-info 10.0.0.5
# Разбор в Wireshark: dissectors modbus, dnp3, s7comm
```

Помимо nmap, в OT популярны `plcscan`, `modbus-cli`, `s7scan`, `smbtget` и Python-библиотеки (`pymodbus`, `pys7`). Но помните: любой **активный** запрос к PLC — это потенциальное воздействие на процесс.

## Разобранный пример: разведка PLC через Modbus

```bash
# 1. Находим Modbus
nmap -p502 10.0.0.0/24
# 2. Читаем регистры (состояние процесса)
tshark -r ot.pcap -Y 'modbus.func_code==3' -T fields -e modbus.reference_num -e modbus.value
# 3. Ищем опасные записи
tshark -r ot.pcap -Y 'modbus.func_code==6 or modbus.func_code==16' -V | head -40
# 4. Читаем напрямую (в лаборатории!)
python3 -c "from pymodbus.client import ModbusTcpClient as M; print(M('10.0.0.5').read_holding_registers(0,5,unit=1))"
```

Регистры (holding/input) хранят значения процесса: уровень, температуру, уставки. Coils/discrete inputs — дискретные сигналы (реле, клапаны). Прочитав карту регистров, вы понимаете логику установки, а найдя write-функции в дампе — какие команды вообще принимаются.

## DNP3, EtherNet/IP и BACnet

- **DNP3** (порт 20000): request/response + unsolicited responses; функции `READ`, `WRITE`, `OPERATE`, `DIRECT_OPERATE`, `COLD_RESTART`. **SAv5** добавляет аутентификацию, но её часто не включают.
- **EtherNet/IP** (44818): CIP-объекты; `ListIdentity` раскрывает модель/версию.
- **BACnet** (47808/UDP): здания/HVAC; `Who-Is`/`I-Am`, чтение/запись свойств.
- **IEC 60870-5-104** (2404): энергетика, ASDU-кадры.

```bash
# Идентификация устройств (пассивно по PCAP)
tshark -r ot.pcap -Y 'dnp3' -T fields -e dnp3.src -e dnp3.dst -e dnp3.al.func
tshark -r ot.pcap -Y 'enip' -T fields -e enip.command
tshark -r ot.pcap -Y 'bacapp' -T fields -e bacapp.object_type
```

## Реверс протокола по PCAP

Если протокол неизвестен:

```bash
# 1. Определить порт/паттерн
tshark -r ot.pcap -q -z io,phs
# 2. Посмотреть первые байты
tshark -r ot.pcap -x | head -40
# 3. Найти повторяющуюся структуру (заголовок + функция + данные)
# 4. Сопоставить с открытыми спецификациями (Modbus/DNP3 публичны)
```

Большинство OT-протоколов **документированы** — реверс чаще сводится к распознаванию формата, а не к полному анализу с нуля. Начните с `io,phs` (иерархия протоколов), затем углубитесь в конкретный dissector.

## Безопасность OT: модель Purdue

Уровни Purdue: 0 (физический) → 1 (контроллеры) → 2 (SCADA/HMI) → 3 (операции) → 3.5 (DMZ) → 4-5 (IT/корпоративный). Правила:

- **Никаких прямых соединений** IT↔OT; только через DMZ.
- **Data diode** для односторонних потоков.
- **Сегментация** по зонам и conduits (IEC 62443).
- **Пассивный мониторинг** (SPAN/TAP), не активный скан.
- Строгий change control.

## Защита

- **Сегментация** IT/OT, **DMZ** между ними.
- **Unidirectional gateway (data diode)** для критичных потоков.
- **Мониторинг** пассивный (без активного сканирования!) — OT-устройства чувствительны.
- **Патчи** там, где возможно; компенсирующие контроли.
- **Аутентификация** там, где протокол поддерживает (DNP3 SAv5, IEC 62351).
- Инвентаризация и baselining нормального трафика.

## Этика OT

Активные действия в OT **опасны** — можно остановить производство или повредить оборудование. Только пассивный анализ, только согласованные действия, в присутствии заказчика. Даже безобидный `nmap -p502` может сбить чувствительный PLC с ритма, поэтому начинайте с SPAN-порта и анализа существующего трафика.

## Что писать в отчёте

- Карта устройств и протоколов (без активного скана).
- Опасные операции, замеченные в трафике (write-функции).
- Отсутствие аутентификации/шифрования.
- Рекомендации: сегментация, DMZ, data diode, SAv5/IEC 62351, мониторинг.

## Частые ошибки

- **Активно сканировать OT** — можно «уронить» PLC; сначала пассивный анализ.
- **Считать «нет пароля = нет риска»** — риск физический.
- **Путать регистры и coils** — разные функции.
- **Игнорировать DNP3 SAv5** — аутентификация опциональна и часто выключена.
- **Вносить изменения** в процесс без согласования — недопустимо.
- **Забывать про смешение IT/OT** — путь атаки часто через IT.

## Что дальше / решение

Маршрут: **пассивный анализ PCAP (`io,phs` → dissector) → карта устройств и протоколов → выделение write-операций → отчёт с рекомендациями (сегментация, DMZ, data diode, SAv5)**. Никогда не начинайте с активного скана: в OT это может нарушить процесс. Дальше — [`network-protocol-reversing`](network-protocol-reversing), [`network-pcap-analysis`](network-pcap-analysis) и [`network-firewall-piercing`](network-firewall-piercing).

## S7comm и ISO-TSAP под капотом

S7comm (Siemens) не работает напрямую поверх TCP — он инкапсулирован в **ISO-TSAP** (порт 102), который сам состоит из TPKT (RFC 1006) и COTP. Разбор по слоям: `TPKT` даёт длину, `COTP` — тип PDU и номера TSAP (которые идентифицируют конкретную PLC/rack/slot), `S7comm` — код функции (`0x04` read var, `0x05` write var, `0x1A`/`0x1F` — обмен блоками/диагностика). Практически это значит, что в Wireshark кадр S7 «разворачивается» в три уровня, и опасная операция — это `S7comm` write var или загрузка/старт/стоп блока (`PLC Stop`). Умение читать TSAP позволяет адресовать нужный контроллер в стойке. В дампе фильтруйте `s7comm` и смотрите `s7comm.param.func`.

## Инструменты OT-анализа

Для разведки и мониторинга OT используют специализированный инструментарий:

- **Zeek** с OT-парсерами (Modbus, DNP3) превращает трафик в структурированные логи — идеально для пассивного анализа.
- **GRASSMARLIN** — визуализация топологии ICS из пассивного захвата.
- **Wireshark/tshark** — диссекторы `modbus`, `dnp3`, `s7comm`, `enip`, `bacapp`, `iec60870_104`.
- **plcscan / s7scan / modbus-cli** — активная идентификация (в лаборатории!).
- **Shodan / FOFA / Censys** — поиск открытых Modbus (порт 502) и других OT-сервисов в интернете: полезно для оценки рисков периметра (но не для сканирования чужих сетей).

```bash
# Пассивная инвентаризация из PCAP через Zeek
zeek -r ot.pcap /opt/zeek/share/zeek/policy/protocols/modbus
# Иерархия протоколов
tshark -r ot.pcap -q -z io,phs
```

## Реальные атаки на OT и уроки

Крупные инциденты задают контекст: **Stuxnet** (2010) — червь, менявший уставки центрифуг через S7; **Industroyer/CrashOverride** (2016) — отключение питания через IEC 60870-5-101/104; **TRITON/Trisis** (2017) — атака на safety-контроллеры (SIS) Schneider; **Colonial Pipeline** (2021) — IT-компрометация остановила физическую поставку. Общий урок: путь атаки почти всегда идёт **через IT в OT**, а защита — это сегментация, видимость трафика и невозможность «дотянуться» из корпоративной сети до контроллеров. Для пентеста это означает: сначала IT-периметр, затем — крайне осторожное исследование OT-сегмента.

## Мониторинг OT: что считать нормой

Базовая линия (baseline) OT-трафика сильно отличается от IT: узкий набор «разговоров» master↔slave, стабильные интервалы опроса (polling), предсказуемые функции. Аномалии: **новый источник** опроса PLC, неожиданные write-функции от HMI, смена прошивки/старт-стоп контроллера, всплески `ListIdentity`/`Who-Is` (сканирование), обращение к контроллерам из IT-подсети. Именно по этим признакам работают OT-IDS (например, Suricata с OT-правилами, Nozomi, Claroty). В отчёте фиксируйте: какие функции используются, кто инициатор, есть ли write в нерабочее время.

## Термины OT для точного отчёта

**PLC** — программируемый логический контроллер (исполнительный уровень); **RTU** — Remote Terminal Unit (телеметрия, энергетика); **HMI** — Human-Machine Interface (пульт оператора); **SCADA** — диспетчерское управление; **SIS** — Safety Instrumented System (противоаварийная защита, цель TRITON); **conduit** (IEC 62443) — защищённый канал между зонами. Разделяйте эти понятия: путаница PLC/RTU/HMI в отчёте снижает доверие к выводам, а неверная классификация SIS как обычного контроллера умаляет серьёзность риска.
