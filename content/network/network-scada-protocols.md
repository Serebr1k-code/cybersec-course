## Вопрос, с которого всё начинается

В промышленной сети (АСУ ТП, завод, ЖКХ) крутятся контроллеры — **PLC** (Programmable Logic Controller). Они общаются по протоколам вроде Modbus, DNP3, S7. Эти протоколы проектировали для надёжности и скорости, а не для безопасности: **аутентификации в них исторически нет**.

Разберёмся, как читать такой трафик и почему запись одного числа может остановить производство.

## Наш пример: запрос Modbus

Пусть система управления `10.0.0.50` читает данные из контроллера `10.0.0.20` по **Modbus/TCP** (порт `502`). Поймаем запрос.

```
$ tshark -r modbus.pcap
    1  0.000000  10.0.0.50 → 10.0.0.20  Modbus/TCP 66  Query: Trans: 1; Unit: 1, Func: 3: Read Holding Registers
```

`tshark` уже распознал протокол и перевёл его на человеческий язык. Разберём структуру.

## Шаг 1: MBAP-заголовок

Modbus/TCP начинается с заголовка **MBAP** (Modbus Application Protocol). В нём:

- **Transaction ID** — номер запроса, чтобы сопоставить ответ (`Trans: 1`);
- **Protocol ID** — всегда 0 для Modbus;
- **Length** — длина;
- **Unit ID** — адрес устройства на шине (`Unit: 1`).

Дальше идёт **PDU** (Protocol Data Unit) — сама команда. Первый байт PDU — **функциональный код** (Function Code).

Посмотрим глубже:

```
$ tshark -r modbus.pcap -V | grep -iE "Function Code|Reference Number|Word Count|Register"
    Function Code: Read Holding Registers (3)
    Reference Number: 0
    Word Count: 10
```

Здесь `Func: 3` = **Read Holding Registers** — «прочитать регистры хранения». `Reference Number: 0` — с какого адреса, `Word Count: 10` — сколько регистров. То есть система спрашивает: «дай мне 10 значений, начиная с регистра 0».

## Шаг 2: ответ с данными

Контроллер отвечает:

```
$ tshark -r modbus.pcap
    2  0.000258  10.0.0.20 → 10.0.0.50  TCP 79 502 → 51001 [PSH, ACK] Len=25
```

В PDU ответа тот же код `3`, затем **байт количества** и сами значения. По значениям регистров видно состояние процесса: температуру, давление, положение задвижки. В сырых числах — реальные измерения.

## Шаг 3: функциональные коды — язык Modbus

Modbus минималистичен. Основные коды:

| Код | Смысл |
|-----|-------|
| 1 | Read Coils — читать дискретные выходы |
| 2 | Read Discrete Inputs — читать входы |
| 3 | Read Holding Registers — читать регистры |
| 4 | Read Input Registers — читать входные регистры |
| 5 | Write Single Coil — записать один выход |
| 6 | Write Single Register — записать один регистр |
| 15 | Write Multiple Coils |
| 16 | Write Multiple Registers |

Обрати внимание: **чтение и запись — это просто разные коды**. Никакого «логина» перед записью нет. Кто может достучаться до порта 502, тот может и **писать**.

## Шаг 4: почему это опасно

Вот ключевой момент для OT-безопасности. Запись регистра или катушки в PLC — это **физическое действие**: открыть клапан, запустить насос, изменить уставку. То есть сетевой запрос превращается в движение механизма.

Опасные последствия:

- **Изменение уставок** — процесс уходит за допустимые пределы;
- **Остановка оборудования** — запись в управляющий регистр;
- **Физический ущерб и угроза людям** — в отличие от ИТ, ошибка тут может стоить дорого.

Поэтому на пентесте OT действует железное правило: **не писать ничего в контроллер без явного разрешения**. Чтение (enumeration) — обычно безопасно; запись — потенциально разрушительна.

## Шаг 5: DNP3 и S7

**DNP3** (Distributed Network Protocol) — распространён в энергетике (США, ЖКХ). Работает по TCP/20000 (и UDP). У него есть понятие **link layer** с адресами, а аутентификация (Secure Authentication, SAv5) появилась лишь в новых версиях и часто **не включена**. DNP3 умеет читать и управлять точками (аналоговыми и дискретными).

**S7** (Siemens S7comm) — протокол Siemens, порт **102**. Обмен идёт по ISO-TSAP поверх TCP. Через S7 можно читать/писать память PLC, включая область, отвечающую за логику. Известные CVE (например, Stuxnet-эпохи) били именно по таким протоколам.

Общий признак у всех: **отсутствие аутентификации и шифрования в базовом режиме**, простые бинарные команды, предсказуемые порты.

## Шаг 6: как анализировать OT-трафик

Инструменты и приёмы:

- `tshark` с диссекторами Modbus/DNP3/S7 (встроены) — читать поля;
- `nmap` NSE-скрипты `modbus-discover`, `s7-info` — опросить контроллер и получить идентификацию;
- **пассивный анализ** — подключить зеркало порта и собрать карту «кто с кем говорит», не отправляя ни одного пакета (самый безопасный метод в OT).

Пример опроса Modbus-устройства:

```
$ nmap -p502 --script modbus-discover 10.0.0.20
```

Скрипт вернёт идентификатор устройства и список поддерживаемых функций. Для S7 есть `s7-info` — покажет модель и версию прошивки PLC.

## Шаг 7: защита OT

Промышленные сети защищают иначе, чем ИТ, потому что остановить оборудование нельзя:

- **Сегментация и зонирование** (модель Purdue): PLC не должен быть доступен из офисной сети;
- **Промышленный файрвол/DPI** — понимающий Modbus/DNP3, разрешающий только нужные функции;
- **Односторонние шлюзы** (data diode) для вывода телеметрии;
- **Инвентаризация** — знать все PLC и их адреса;
- **Мониторинг** — пассивный, чтобы не мешать процессу; детект аномальных функциональных кодов (запись там, где её быть не должно).

Для SOC сигнал: неожиданный `Func: 5/6/15/16` (запись) из необычного источника — серьёзное событие.

## Шаг 8: правило «сначала понять, потом трогать»

В OT есть простое правило, которое стоит запомнить накрепко: **сначала понять процесс, потом что-либо делать**. Прежде чем отправить хотя бы один пакет в сторону PLC, нужно знать, какой это контроллер, чем он управляет, есть ли резерв и что произойдёт при остановке. Часто правильный результат аудита — это отчёт о видимости и доступности, **без единого запроса** к оборудованию. Пассивный анализ через зеркало порта даёт почти всё, что нужно для оценки риска, и при этом не трогает работающий процесс.

## Что мы теперь знаем

- Modbus/TCP (502) использует MBAP-заголовок и функциональные коды PDU.
- Коды чтения и записи — просто разные числа, без аутентификации.
- Запись в PLC = физическое действие, поэтому в OT опасно писать без разрешения.
- DNP3 (энергетика) и S7 (Siemens, порт 102) устроены похоже и тоже без базовой аутентификации.
- Защита — сегментация, промышленный DPI, пассивный мониторинг.

## Куда дальше

Мы закрыли блок «реверс и сервисы». Дальше спустимся на канальный уровень — разберём ARP и DNS, протоколы, которые связывают адреса и имена и легко подделываются. А пока главное запомни: в OT сеть — это продолжение физического мира, и «просто прочитать регистр» может быть безопасно, а «просто записать» — нет.
