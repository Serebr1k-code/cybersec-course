## Вопрос, с которого всё начинается

Современный автомобиль — это десятки компьютеров (**ECU**, electronic control unit), соединённых проводами. Когда ты нажимаешь на тормоз, «нажатие» превращается в короткое сообщение в шине, которое читают все блоки сразу. Как только у тебя есть доступ к этой шине (через разъём **OBD-II**), ты можешь читать, а нередко и подделывать сообщения. Именно так работают и легальные диагностические сканеры, и атакующие.

Этот модуль — про то, как устроены внутриавтомобильные сети и как их исследовать. Опирается на [`network-module-embedded`](network-module-embedded).

## Четыре уровня автомобильной связи

- **CAN** (Controller Area Network) — основная шина. Дифференциальная витая пара, до 1 Мбит/с, короткие кадры по 8 (или 64 в CAN-FD) байт. Все узлы слышат всех.
- **LIN** (Local Interconnect Network) — дешёвая однопроводная шина для медленных устройств (стеклоподъёмники, датчики дождя).
- **UDS** (Unified Diagnostic Services) — протокол диагностики **поверх** CAN (ISO 14229). Это язык, на котором сервисный сканер общается с ECU.
- **DoIP** (Diagnostics over IP) — тот же UDS, но поверх Ethernet/IP (ISO 13400), для современных машин и прошивок.

## Почему CAN так легко атаковать

В CAN **нет адресов узлов и нет аутентификации**. Идентификатор в кадре — это не «кому», а «о чём» (например, `0x0C0` — «обороты двигателя»). Кто угодно, подключившийся к шине, может отправить кадр с любым ID, и остальные его примут. Отсюда классические атаки: инъекция ложных данных, реплей, глушение шины (bus-off), сброс ECU.

## Как это выглядит в дампе

CAN удобно читать через `candump` (Linux, SocketCAN) или `can-utils`:

```
$ candump can0
  can0  0C0   [8]  1A 2B 3C 4D 5E 6F 70 80
  can0  1A0   [8]  00 00 0F A0 00 00 00 00
```

`0C0` — идентификатор кадра, `[8]` — длина данных (DLC), дальше — 8 байт. Чтобы понять, что это за сигнал, нужен DBC-файл (описание разметки), который у каждого производителя свой.

## CAN на уровне битов и арбитраж

CAN — широковещательная шина с арбитражем по ID: когда два узла начинают передачу одновременно, побеждает кадр с меньшим ID (доминантный бит «перебивает» рецессивный). Это определяет приоритеты: аварийные сообщения имеют малый ID. Кадр: SOF, ID (11 или 29 бит), DLC, данные (0–8 байт, 0–64 в FD), CRC, ACK, EOF. Бит-стаффинг после 5 одинаковых битов.

```text
SOF | ID | RTR | IDE | DLC | DATA | CRC | ACK | EOF
```

Атаки: инъекция кадра с любым ID (нет аутентификации), реплей, flood (bus-off). Арбитраж означает, что атакующий с малым ID может «перебить» легитимные сообщения.

## Инструменты автомобильной сети

Стенд: `can-utils` (`candump`, `cansend`, `canplayer`), `python-can`, `Scapy` с `CANSocket`, виртуальная шина `vcan` для тестов, USB-CAN адаптеры (CANable, PCAN). Для диагностики — `python-uds`, `udsoncan`, `can-isotp`; для DoIP — `doipclient`.

```bash
modprobe vcan; ip link add dev vcan0 type vcan; ip link set vcan0 up
candump vcan0 &
cansend vcan0 0C0#1A2B3C4D5E6F7080
```

Работать только на стенде: инъекция в CAN реального авто управляет тормозами, рулевым, двигателем.

## Куда идти в модуле и зачем

Модуль покрывает четыре уровня: CAN (шина), LIN (дешёвая шина), UDS (диагностика), DoIP (диагностика по IP). Порядок изучения: сначала CAN (основа), затем LIN (master-slave), затем UDS (сервисы поверх CAN/ISO-TP), затем DoIP (поверх IP).

Практическая ценность: автомобильные сети — растущая область пентеста (телематика, OTA, ключи доступа). Понимание CAN/ UDS нужно для аудита ECU, а DoIP — для современных машин с Ethernet-архитектурой. Инструменты и этика: только стенд или согласованный тест.

## CAN, LIN, UDS, DoIP: связи между уровнями

Четыре уровня связаны: CAN — основная шина; LIN — подчинённая (подключается через CAN-LIN шлюз); UDS — диагностика поверх CAN (ISO-TP); DoIP — та же диагностика поверх IP/Ethernet. То есть UDS-сервисы доступны и по CAN (через ISO-TP), и по Ethernet (через DoIP).

```text
LIN --gateway--> CAN --ISO-TP--> UDS
Ethernet --DoIP--> UDS (те же сервисы)
```

Понимание связей важно: атака на CAN может дать доступ к UDS (диагностика ECU), а DoIP — к тем же сервисам по сети. Часто UDS SecurityAccess (seed/key) — единственная «защита», и она обходится.

## Практика: от дампа к диагнозу

Маршрут практики: (1) записать CAN-трафик (`candump`), (2) найти диагностические кадры (обычно ID 0x7DF/0x7E0-0x7E7 для UDS), (3) разобрать ISO-TP, (4) декодировать UDS-сервисы. Инструменты: `python-uds`, `udsoncan`, `can-isotp`.

```bash
candump -L can0 | grep 7E
python3 -c "from udsoncan.client import Client; ..."   # чтение DTC/данных
```

Что искать: незащищённый SecurityAccess, доступные сервисы (0x22 read data, 0x2E write, 0x31 routine, 0x34 request download), возможность прошивки. Всё — на стенде.

## Этика и безопасность работ

Автомобильные сети — область, где ошибка может привести к аварии. Правила: (1) только стенд (bench) или согласованный тест-автомобиль, (2) никогда не работать на движущемся авто, (3) не писать в управляющие ID/сервисы без понимания последствий, (4) использовать `vcan` для экспериментов, (5) документировать всё.

```bash
modprobe vcan; ip link add dev vcan0 type vcan; ip link set vcan0 up
```

Практическая ценность: аудит телематики, ключей доступа, OTA-обновлений, диагностики. Навыки CAN/UDS/DoIP применимы и в CTF, и в реальных аудитах.

## Итог по automotive

Автомобильные сети: CAN (шина без аутентификации), LIN (master-slave), UDS (диагностика), DoIP (диагностика по IP). Атаки: инъекция, реплей, обход SecurityAccess, прошивка. Инструменты: `can-utils`, `python-uds`, `doipclient`. Этика: только стенд. Ценность: аудит телематики, ключей, OTA.

## Разбор примера: диагностический сеанс

Полный диагностический сеанс: клиент открывает сессию (`0x10`), запрашивает данные (`0x22`), проходит SecurityAccess (`0x27` seed/key), выполняет действие (`0x2E`/`0x31`), закрывает сеанс. В дампе это видно как обмен по ISO-TP.

```text
10 03 (extended session) -> 50 03
27 01 (request seed) -> 67 01 <seed>
27 02 <key> -> 67 02 (accepted)
```

Слабость — алгоритм seed/key часто восстанавливается из прошивки ECU. Для пентеста: показать, что SecurityAccess обходится, и какие сервисы после этого доступны.

## Итог и практика

Автомобильная сеть: CAN (шина), LIN (подчинённая), UDS (диагностика), DoIP (диагностика по IP). Практика: записать трафик, найти диагностику, разобрать UDS-сеанс, проверить SecurityAccess. Инструменты: `can-utils`, `udsoncan`, `doipclient`, `vcan`. Только стенд; документировать; учитывать безопасность.

## Расширенный разбор: реверс шины без документации

Когда DBC нет, семантику восстанавливают эмпирически: записывают трафик, выполняют действия (нажать кнопку, повернуть руль), ищут изменившиеся кадры. Кадры с постоянной частотой — heartbeat; с плавными изменениями — датчики; скачкообразные — события.

```bash
candump -L can0 > before.txt; # действие; candump -L can0 > after.txt
diff <(cut -d" " -f2- before.txt | sort -u) <(cut -d" " -f2- after.txt | sort -u)
```

Так находят управляющие ID. Дальше — реплей (на стенде) для подтверждения. Документируй каждый шаг: это основа отчёта по автомобильной сети.

## Резюме по automotive

CAN/LIN/UDS/DoIP: шина без аутентификации, диагностика с обходимым SecurityAccess. Практика — стенд (`vcan`, `can-utils`, `udsoncan`). Ценность — телематика, ключи, OTA. Никогда не работать на движущемся авто.

## Что запомнить

Автомобильные сети — область, где ошибка приводит к аварии, поэтому все эксперименты только на стенде (`vcan`, тестовый автомобиль). CAN не аутентифицирован: любой узел может слать кадры; UDS SecurityAccess обходится реверсом алгоритма. Практическая ценность — аудит телематики, ключей доступа и OTA-обновлений. Документируй каждый шаг: запись трафика, поиск диагностики, разбор UDS-сеанса, проверка SecurityAccess.

Помни: любой автомобильный тест начинается с записи трафика и заканчивается отчётом, а не инъекцией в живую шину.

Каждый эксперимент фиксируй в журнале: ID кадра, время, действие и наблюдаемый эффект — это и есть воспроизводимый результат для отчёта.
