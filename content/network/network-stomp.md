## Вопрос, с которого всё начинается

В сети торчит порт 61613. Подключаешься `nc`-ом, и сервер отвечает текстом, будто это чат: `CONNECTED`, `MESSAGE`, `RECEIPT`. Это **STOMP** — Simple (Streaming) Text Oriented Messaging Protocol. Простой настолько, что его можно набирать руками, — и это же делает его удобной целью.

## Наш пример: сессия STOMP

Откроем соединение:

```
$ nc 10.0.0.30 61613
CONNECT
accept-version:1.2
host:localhost

^@
CONNECTED
version:1.2
session:session-1
heart-beat:0,0

^@
```

Мы отправили кадр `CONNECT` и получили `CONNECTED`. Ни логина, ни пароля. Разберём, из чего состоит кадр и что можно сделать дальше.

## Шаг 1: структура кадра

Кадр STOMP — это текст:

```
COMMAND
header1:value1
header2:value2

тело сообщения
^@
```

То есть: команда, строки заголовков, пустая строка, тело, и завершающий NUL-байт (`^@`, `\x00`). Никакой бинарной длины — границы определяет NUL. Это упрощает парсинг, но и открывает возможности для инъекции.

## Шаг 2: команды

Основные команды:

- `CONNECT` / `CONNECTED` — установка соединения;
- `SEND` — отправить сообщение в destination;
- `SUBSCRIBE` / `UNSUBSCRIBE` — подписка на destination;
- `MESSAGE` — доставка подписчику;
- `ACK` / `NACK` — подтверждение;
- `BEGIN` / `COMMIT` / `ABORT` — транзакции;
- `DISCONNECT` — разрыв.

Destination — имя очереди или топика. Именно от него зависит, чьи сообщения ты получишь.

## Шаг 3: подписка и wildcard

Подписка выглядит так:

```
SUBSCRIBE
id:0
destination:/queue/orders

^@
```

Отсюда вопрос: а можно ли подписаться на всё? У многих брокеров есть **wildcard**-destination. В ActiveMQ, например, `/queue/>` или `/topic/>` захватывает все очереди/топики. Если брокер не ограничивает права на чтение, ты читаешь весь трафик интеграции — заказы, платёжные события, внутренние команды.

```
SUBSCRIBE
id:1
destination:/topic/>
ack:auto

^@
MESSAGE
destination:/topic/payments
message-id:ID:host-1

{"amount":100,"card":"4111..."}
^@
```

Так одной подпиской раскрывается вся шина.

## Шаг 4: отправка и инъекция

`SEND` позволяет писать в destination:

```
SEND
destination:/queue/orders
content-type:application/json

{"orderId":42,"action":"refund","amount":10000}
^@
```

Если брокер не проверяет, кто пишет, — ты можешь инжектировать сообщения, которые будут приняты как легитимные. Классический сценарий: подделать команду «вернуть деньги», «сбросить пароль», «выполнить задачу». Это уже не сетевая атака, а **business logic** — и она опаснее.

## Шаг 5: заголовки и инъекция кадров

Текстовый формат даёт ещё одну возможность. Если значение заголовка попадает в другой контекст (лог, SQL, команду), возможна инъекция. А если приложение позволяет задать тело с NUL-байтом внутри, можно попробовать **разорвать кадр** и вставить свои команды — правда, корректные парсеры этого не допускают, поэтому сначала проверяют, как именно сервер трактует вложенные NUL.

Практический приём: отправляй граничные значения и смотри, где меняется поведение. Это база любого протокольного фаззинга.

## Шаг 6: атаки и разведка

Что проверяют:

- **открытый брокер** — доступ без аутентификации (порт 61613);
- **wildcard-подписка** — чтение чужих сообщений;
- **инъекция SEND** — подделка команд;
- **DoS** — тысячи подписок или большие сообщения;
- **перебор паролей** — если брокер требует, но дефолты не сменены.

```
$ nmap -p61613 --script banner 10.0.0.30
$ python3 -c "import stomp; c=stomp.Connection([('10.0.0.30',61613)]); c.connect(wait=True); print('open')"
```

## Шаг 7: защита

Что должно быть сделано: аутентификация и авторизация на брокере (STOMP поддерживает `login`/`passcode` в CONNECT), разграничение прав по destination, запрет wildcard для непривилегированных, сетевой ACL, TLS (порт 61614). Брокер сообщений — это «нервная система» приложения, и её нельзя держать открытой.

## Что мы теперь знаем

- STOMP — текстовый кадровый протокол обмена сообщениями.
- Destination задаёт очередь/топик; wildcard может раскрыть всё.
- CONNECT может не требовать аутентификации.
- SEND позволяет инжектировать команды в бизнес-логику.

## Если не сработало

Если `nc` не видит ответа — брокер ждёт NUL в конце кадра: нажми Ctrl-@ или отправь `\x00`. Если CONNECT отклонён — нужен `login`/`passcode`. Если MESSAGE не приходит — проверь destination и `ack`. Если это не STOMP — возможно, перед тобой AMQP или MQTT.

## STOMP рядом с AMQP и MQTT

Три messaging-протокола решают похожую задачу, но по-разному. **MQTT** — лёгкий pub-sub для IoT, с брокером и топиками. **AMQP** — тяжёлый, с очередями, маршрутизацией и богатой семантикой. **STOMP** — минималистичный текстовый «конверт» для тех же брокеров.

Разница важна на пентесте. В AMQP сложнее подделать сообщение: много полей и типов. В STOMP проще — текст, минимум проверок. MQTT часто закрыт ACL на брокере. Поэтому STOMP-порт (61613) — лёгкая цель: подключился, подписался, прочитал.

## Транзакции и подтверждения

STOMP поддерживает транзакции:

```
BEGIN
transaction:tx1

SEND
destination:/queue/orders
transaction:tx1

COMMIT
transaction:tx1

^@
```

Пока не пришёл `COMMIT`, сообщения не отправлены. Это используется для атомарности. Для атакующего транзакции — способ отложить или отменить чужую операцию, если права позволяют.

Подтверждения (`ack`) работают так: подписчик получает `MESSAGE` с `message-id`, затем шлёт `ACK` (или `NACK`). Если `ack:client`, брокер ждёт подтверждения; если `ack:auto`, сообщение считается доставленным сразу. Режим `auto` опасен тем, что при сбое подписчика сообщения теряются — и наоборот, злоумышленник может «съесть» их.

## Практика: стенд на ActiveMQ

Развернём брокер для экспериментов. ActiveMQ включает STOMP из коробки:

```
$ docker run -d -p 61613:61613 -p 8161:8161 apache/activemq
$ nc localhost 61613
CONNECT
accept-version:1.2
host:localhost

^@
```

Дальше подпишись на `/topic/>` и отправь пару сообщений в другой терминал — увидишь весь цикл. На этом стенде безопасно проверить и wildcard-подписку, и инъекцию, и поведение при отсутствии аутентификации. Включи логин на брокере — и увидишь, как меняется ответ на CONNECT.

## Типичные ошибки

Первая — забывать NUL в конце кадра: без него сервер молчит. Вторая — путать `/queue/` и `/topic/`: у первого доставка одному потребителю, у второго — всем подписчикам. Третья — считать, что раз порт открыт, аутентификации нет: иногда CONNECT просто требует `login`/`passcode`. Четвёртая — не проверять права на запись: чтение может быть открыто, а SEND — запрещён.

## Разбор MESSAGE и заголовков

Когда подписка оформлена, брокер шлёт `MESSAGE`. Разберём его поля:

```
MESSAGE
subscription:0
message-id:ID:broker-1-3
destination:/queue/orders
content-type:application/json

{"orderId":7}
^@
```

`subscription` — какой подписке соответствует, `message-id` — уникальный идентификатор (нужен для ACK), `destination` — откуда пришло, `content-type` — как трактовать тело. Если подписался на несколько destination, различай их по полю `destination`.

Практический нюанс: `message-id` в ActiveMQ содержит имя брокера и счётчик. По нему видно, сколько сообщений прошло, — полезно для оценки объёма данных, которые ты читаешь.

## Инструменты

Ручной `nc` хорош для разведки, но для массовой работы есть библиотеки. Python-модуль `stomp.py`:

```
$ pip install stomp.py
$ python3 - <<'EOF'
import stomp
c = stomp.Connection([('10.0.0.30', 61613)])
c.connect(wait=True)
c.subscribe('/topic/>', id=1)
EOF
```

Так подписка на wildcard оформляется в пару строк. Для защиты полезно прогнать `nmap -p61613 --script banner` и проверить, отвечает ли брокер без `login`/`passcode`. Если да — это находка уровня «высокий»: брокер сообщений — прямой доступ к бизнес-логике.

## Как отличить STOMP от MQTT и AMQP в дампе

Порты подсказывают, но не всегда. Полезно узнавать протокол по содержимому.

- **STOMP** — первый байт — ASCII-команда (`CONNECT`, `SEND`, `SUBSCRIBE`). В потоке видно открытый текст заголовков. Признак: строки вида `destination:` и NUL-байты как разделители кадров.
- **MQTT** — первый байт — тип и флаги (0x10 = CONNECT), затем бинарная длина. Строк `destination:` нет, есть `topic` в бинарном виде.
- **AMQP** — начинается с `AMQP\x00\x00\x09\x01` (protocol header). Явная сигнатура.

```
$ tshark -r mq.pcap -T fields -e tcp.payload | head -1
434f4e4e4543540a
```

`434f4e4e454354` — это `CONNECT`, значит STOMP. Так, глядя на первые байты, ты определяешь протокол без документации.

Практический вывод: в одном сегменте могут работать несколько messaging-протоколов. Инвентаризируй все, а не только тот, который ожидаешь увидеть. Забытый брокер — самая частая причина утечки.

## Шпаргалка по командам STOMP

| Команда | Роль |
|---|---|
| CONNECT | установить сессию |
| SEND | отправить сообщение |
| SUBSCRIBE | подписаться |
| MESSAGE | доставка |
| ACK / NACK | подтвердить/отклонить |
| BEGIN / COMMIT / ABORT | транзакция |
| DISCONNECT | разорвать |

Кадр завершается NUL-байтом — без него сервер не ответит.

## Итог по протоколу

Главное: у STOMP нет встроенной защиты, и вся безопасность держится на конфигурации брокера. Проверяй аутентификацию, права на destination и отсутствие wildcard-подписок — это три пункта, которые закрывают большинство проблем.

## Ещё один практический нюанс

Если брокер требует аутентификации, попробуй гостевой доступ: некоторые конфигурации разрешают CONNECT без пароля на чтение, но запрещают SEND. Такой режим тоже опасен — он раскрывает содержимое очередей, а запись закрыта лишь формально.
