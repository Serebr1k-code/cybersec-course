NTP — один из старейших интернет-протоколов, и одновременно один из самых эксплуатируемых для отражённых DDoS. Он работает по UDP/123, легко спуфится (source IP не проверяется), а некоторые команды возвращают ответ в сотни раз больше запроса. Плюс ко всему, если атакующий подменит время, он ломает TLS, Kerberos, логирование и репликацию. Поэтому NTP — обязательная тема для сетевого пентеста и для анализа DDoS-инцидентов.

## Как работает NTP

NTP-серверы образуют иерархию **страт** (stratum): stratum 0 — эталонные часы (GPS, атомные), stratum 1 — серверы, подключённые к ним напрямую, stratum 2 — синхронизируются с stratum 1, и так далее. Клиент отправляет UDP-датаграмму (48 байт заголовка) и получает ответ с текущим временем. Ключевые поля заголовка:

- **LI/VN/Mode** — версия и режим (client=3, server=4, symmetric=1/2, control=6, private=7);
- **Stratum** — удалённость от эталона;
- **Poll** — интервал опроса;
- **Precision** — точность;
- **Reference ID**, **Reference Timestamp**, **Origin/Receive/Transmit Timestamp**.

Для атак важны режимы **mode 6 (control)** и **mode 7 (private)** — исторически они позволяли запрашивать состояние сервера (`monlist`, `readvar`), и именно они дают амплификацию.

| Mode | Назначение |
|---|---|
| 1 | Symmetric active |
| 2 | Symmetric passive |
| 3 | Client |
| 4 | Server |
| 5 | Broadcast |
| 6 | NTP control (ntpq) |
| 7 | NTP private (ntpdc, monlist) |

## monlist и UDP-амплификация

Команда `monlist` (mode 7) возвращала список последних клиентов сервера — до 600 записей в одном ответе. Запрос — около 234 байт, ответ — до десятков килобайт, то есть **коэффициент амплификации ~200×** (а с учётом множественных запросов — сотни раз). При спуфинге source IP атакующий шлёт тысячи таких запросов от имени жертвы, и жертва тонет в ответах серверов. Это основа крупнейших DDoS 2014–2016 годов.

Проверить, открыт ли monlist:

```bash
sudo nmap -sU -p123 --script ntp-monlist 192.0.2.10
# или старым ntpdc
ntpdc -n -c monlist 192.0.2.10
```

Современные версии ntpd (4.2.7p26+) **отключили monlist по умолчанию** (`disable monitor` в конфиге), но legacy-устройства (камеры, роутеры, старые серверы) всё ещё уязвимы. Также используют `readvar`/`getvar` для амплификации меньшего масштаба.

## Спуфинг времени и последствия

NTP не аутентифицирует ответы (если не используется NTS/autokey). Атакующий в позиции MITM может подменить время. Последствия:

- **TLS** — если системное время сильно уходит, сертификаты выглядят «просроченными» или «ещё не действительными»; валидация ломается, а иногда — ослабляется (некоторые клиенты откатываются на небезопасные пути).
- **Kerberos** — допускает расхождение времени по умолчанию **5 минут**; сдвиг больше ломает аутентификацию (DoS) или, при комбинированных атаках, помогает манипулировать тикетами.
- **Логи и форензика** — искажённые таймстемпы рушат корреляцию событий.
- **Криптография** — TOTP/2FA, JWT `exp`/`nbf`, подписи с временем.

Особенно опасен «сдвиг назад» — он может «оживить» отозванные сертификаты или истёкшие токены.

## Разобранный пример: проверка амплификации

1. Определяем открытые NTP-серверы в диапазоне (осторожно, это громко):
   ```bash
   sudo nmap -sU -p123 --open -iL targets.txt -oG ntp.gnmap
   ```
2. Для найденных проверяем monlist и оцениваем размер ответа:
   ```bash
   sudo nmap -sU -p123 --script ntp-monlist,ntp-info 192.0.2.10
   ```
   Если `ntp-monlist` вернул список клиентов — сервер пригоден для амплификации.
3. Оцениваем коэффициент: сравниваем длину запроса и ответа в tcpdump:
   ```bash
   sudo tcpdump -i eth0 -nn -v 'udp port 123' -c 10
   ```
   Строки с `length` покажут 234 → 4820 и больше.
4. В отчёте это фиксируется как **уязвимость конфигурации** (UDP-амплификация), а не как «взлом».

## KoD и rate-limiting

NTP-серверы защищаются от перегрузки механизмом **Kiss-o'-Death (KoD)**: пакет с кодом (например, `RATE`, `DENY`) просит клиента снизить частоту или прекратить запросы. Это не защита от спуфинга (жертва всё равно получает ответы), но ограничивает нагрузку. Дополнительно:

- **`disable monitor`** — отключить monlist;
- **`restrict default kod limited nomodify noquery`** — запретить запросы контроля/статуса извне;
- **rate limiting** на уровне ntpd (`restrict ... limited`);
- **файрвол**: разрешать UDP/123 только от известных клиентов.

## Защита и NTS

Главная современная мера — **NTS (Network Time Security, RFC 8915)**: аутентификация сервера и шифрование обмена через TLS-хендшейк с последующими аутентифицированными cookies. NTS поддерживают chrony и ntpd-rs. Дополнительно:

| Мера | Против чего |
|---|---|
| NTS | Спуфинг, MITM |
| `disable monitor` | monlist-амплификация |
| `restrict ... noquery` | Запросы статуса извне |
| ACL по IP | Отражённые атаки |
| egress-фильтрация UDP/123 | Использование вас как отражателя |
| BCP38/uRPF | Спуфинг source IP |

## Частые ошибки и подводные камни

- **Сканировать UDP-порт 123 агрессивно.** Это легко детектируется и может завалить сервер; используйте `--max-rate` и таймауты.
- **Считать monlist «мёртвым».** В IoT и встроенных системах он жив.
- **Игнорировать хронометрию в форензике.** Если время узла могло быть подменено — таймстемпы логов ненадёжны, это надо указывать в отчёте.
- **Путать stratum и точность.** Высокий stratum — не «плохо», это просто дальше от эталона.
- **Забывать про broadcast-режим.** В некоторых ЛВС NTP раздаётся широковещательно и легко подменяется.

## Что дальше / решение

Свяжите NTP со спуфингом DHCP/ARP (`network-dhcp`, `network-arp-deep`): в локальной сети вы можете подменить и шлюз, и время, и DNS — это полный контроль над клиентом. Дальше изучайте `network-kerberos` (чувствительность к времени) и `network-dns-attacks`. Для защиты разверните NTS, отключите запросы статуса извне и добавьте egress-фильтр UDP/123, чтобы ваша сеть не участвовала в отражённых атаках.

## Амплификация: расчёт и этика

Коэффициент амплификации (BAF, bandwidth amplification factor) считается как отношение байт ответа к байтам запроса, умноженное на число ответов на один запрос. Для monlist это исторически ~206× (запрос 234 Б, ответ ~48 КБ). Для `readvar` — порядка 3–10×, для `getvar` — ещё меньше. DDoS-сервисы строят списки открытых рефлекторов и комбинируют NTP с DNS, memcached, CLDAP и SSDP. С точки зрения пентеста важно: **вы не запускаете атаку**, вы фиксируете конфигурационную уязвимость и приводите расчёт. В отчёте указывают: IP сервера, порт/протокол, команду, размер запроса/ответа, коэффициент и рекомендацию. Никогда не отправляйте трафик от чужого source IP — это уже атака, а не тест. Для валидации достаточно одного запроса с вашего адреса и измерения ответа.

## Лаборатория: поднимаем уязвимый NTP

Разверните старый ntpd в контейнере (или соберите из исходников версию ниже 4.2.7p26) и включите monitor:

```
# /etc/ntp.conf
restrict default nomodify
restrict 127.0.0.1
enable monitor
```

Затем с другой машины проверьте `ntpdc -c monlist <ip>` — увидите список клиентов. Сравните размер ответа в tcpdump (`-v`). После этого добавьте `disable monitor` и повторите — команда перестанет работать. Так вы наглядно показываете разницу «уязвимо/исправлено» и тренируетесь в аккуратной валидации. Дополнительно можно поднять chrony и убедиться, что NTS-клиент отвергает неаутентифицированный ответ: это современный «правильный» стенд.
