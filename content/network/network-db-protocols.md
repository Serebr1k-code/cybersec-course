## Вопрос, с которого всё начинается

Ты на пентесте нашёл открытый порт `3306`. Сканер написал «MySQL». Но что дальше? Пароля нет, брутфорс запрещён. Прежде чем ломиться, стоит понять: а что вообще эта база рассказывает о себе ещё до входа?

У баз данных, как и у людей, есть «приветствие» — первое, что сервер говорит клиенту при подключении. В этом уроке мы поймаем этот обмен для трёх популярных СУБД и посмотрим, что из него можно выудить, не зная ни одного пароля.

## Наш пример: клиент стучится в MySQL

Пусть машина `10.0.0.5` подключается к серверу MySQL на `10.0.0.9:3306`. Перехватим трафик (`tcpdump`/`tshark` мы разбирали в уроке про анализ PCAP) и посмотрим первый пакет — он летит **от сервера к клиенту**.

```
$ tshark -r mysql.pcap
    1  0.000000  10.0.0.9 → 10.0.0.5  MySQL 132 Server Greeting  proto=10 version=8.0.36
```

Уже из одной строки мы знаем: версия сервера `8.0.36`, протокол `10`. Разберём пакет глубже — добавим `-V` (verbose).

```
$ tshark -r mysql.pcap -V | grep -iE "Server Version|Protocol|Thread|Salt"
        Protocol: 10
        Thread ID: 12
        Salt: abcdefgh
        Server Version: 8.0.36
```

Три вещи, которые сервер выдал бесплатно:

- **версия** `8.0.36` — по ней ищут известные CVE;
- **thread id** — идентификатор соединения;
- **salt** (его ещё называют *nonce* — одноразовое случайное число) — часть данных для проверки пароля.

## Шаг 1: почему salt — это не утечка пароля

Может показаться: сервер отдал «соль», значит, пароль почти у нас. Нет. `Salt` в MySQL — это случайные байты, которые сервер придумывает **на каждое подключение**. Клиент берёт твой пароль, солит им и хэширует по схеме `mysql_native_password` (SHA1), и отправляет серверу результат.

Смысл в том, что по сети **не идёт ни пароль, ни его постоянный хэш**. Даже если ты перехватишь весь обмен, восстановить пароль из ответа клиента напрямую нельзя — можно только подбирать оффлайн, пересчитывая кандидатов с той же солью. Это уже гораздо дороже, чем «прочитать пароль из трафика».

Вывод для атакующего: **сам по себе MySQL-handshake пароль не отдаёт**. Но версию — отдаёт, и это первый шаг разведки.

## Шаг 2: PostgreSQL — StartupMessage

PostgreSQL устроен иначе. У него нет «приветствия сервера»: клиент сам первым шлёт `StartupMessage` — пакет, в котором уже написано, кто он и какую базу хочет.

```
$ tshark -r pg.pcap
    1  0.000000  10.0.0.5 → 10.0.0.9  PGSQL 114 >?
```

`>?` — это и есть StartupMessage. Смотрим содержимое:

```
$ tshark -r pg.pcap -V | grep -iE "Type:|version|Parameter"
    Type: Startup message
    Protocol major version: 3
    Protocol minor version: 0
    Parameter name: user
    Parameter value: postgres
    Parameter name: database
    Parameter value: appdb
```

Вот и всё: **имя пользователя `postgres` и имя базы `appdb` ушли открытым текстом**, ещё до всякой аутентификации. Это нормальное поведение протокола — сервер должен знать, кого и куда пускать.

Для нас это ценно: мы получили валидное имя пользователя. Брутфорс «вслепую» по логину и паролю — плохая идея (медленно и шумно), а вот перебрать пароли **к известному пользователю `postgres`** — уже точечная задача. Если включён `trust`-метод (доверие по IP без пароля), нас вообще пустят без пароля — это одна из самых частых мисконфигураций.

## Шаг 3: MSSQL — TDS pre-login

Microsoft SQL Server говорит на протоколе **TDS** (Tabular Data Stream). Первое, что происходит при подключении, — **pre-login**: клиент и сервер обмениваются пакетами, чтобы договориться о версиях и шифровании.

В pre-login-пакете клиент присылает список поддерживаемых версий TDS и флаг шифрования. Видно, использует ли сервер `encrypt=on`. Если нет — **весь логин и запросы идут открытым текстом**, включая хэш пароля в login7-пакете. Это классический перехват: в корпоративной сети MSSQL-трафик без TLS легко «читается» снифером на пути.

## Шаг 4: что видно без TLS

Сведём в таблицу, что доступно перехватчику, когда шифрование выключено.

| СУБД | Что в открытом виде | Пароль? |
|------|---------------------|---------|
| MySQL | версия, thread id, salt | нет, но ответ клиента можно брутить оффлайн |
| PostgreSQL | логин, имя БД, версия | зависит от метода (`md5` — хэш+соль, `scram` — устойчив) |
| MSSQL | pre-login, login7 (логин + хэш) | хэш NTLM-подобный, часто релеится |

Общий вывод: **без TLS протоколы БД сливают метаданные и создают материал для оффлайн-атак**. Пароли «в лоб» обычно не текут, но имена пользователей, баз и хэши — текут регулярно.

## Шаг 5: как это эксплуатируют на практике

Из перехваченного handshake рождаются три сценария:

1. **Точечный брутфорс.** Мы знаем логин (`postgres`, `root`, `sa`) — перебираем небольшой список дефолтов и утёкших паролей. Никогда не «миллион слов»: онлайн-перебор по сети — медленный и шумный, его место — оффлайн.
2. **Оффлайн-крекинг.** Перехватили ответ MySQL-клиента или md5-хэш PostgreSQL → считаем кандидатов локально на GPU (hashcat). Это уже дёшево.
3. **Релей.** MSSQL без подписи/шифрования позволяет «пробросить» аутентификацию жертвы на другую цель — но это отдельная большая тема (NTLM-релей).

## Шаг 6: что делать, чтобы не попасться

Защита строится на трёх уровнях:

- **Шифрование.** Включить TLS/SSL для всех подключений (`sslmode=require` в PostgreSQL, `--ssl` в MySQL, `encrypt=on` в MSSQL). Тогда handshake перестаёт быть читаемым.
- **Сегментация.** Базы не должны слушать `0.0.0.0`. Пусть принимают подключения только от прикладного сервера, а не от всей сети.
- **Аутентификация.** Отключить `trust`, использовать `scram-sha-256` вместо `md5`, не хранить учётки в конфигах открытым текстом.

Для SOC полезный сигнал: всплеск подключений к `3306/5432/1433` из необычных подсетей или короткие «рукопожатия» без последующих запросов — типичный признак сканирования и брутфорса.

## Что мы теперь знаем

- Базы данных «здороваются» при подключении, и это приветствие часто читается без пароля.
- MySQL отдаёт версию и соль, PostgreSQL — логин и имя базы, MSSQL — параметры pre-login.
- Пароли обычно не идут в открытом виде, но создаётся материал для оффлайн-атак.
- Лечение — TLS, сегментация и отказ от `trust`/`md5`.

## Разбираем MySQL handshake побайтово

Вернёмся к нашему клиенту. При подключении сервер первым шлёт **Initial Handshake Packet**. В нём есть строка версии, 8-байтный **scramble** (случайная соль) и список поддерживаемых методов аутентификации. Посмотрим:

```
$ tshark -r mysql.pcap -Y mysql -T fields -e mysql.packet_length -e mysql.server_version -e mysql.auth_plugin_name
74 5.7.34-log  mysql_native_password
```

Соль (`scramble`) нужна, чтобы пароль **никогда не шёл по сети открытым текстом**. Клиент считает `SHA1(password)` дважды, примешивает соль и отправляет результат. Значит, перехватив handshake, ты получаешь не пароль, а **challenge-response** — материал для оффлайн-подбора или для релея. Это принципиально: в старом протоколе MySQL «пароль в дампе» — миф, но «хэш для подбора» — реальность.

## PostgreSQL: StartupMessage и параметры

У PostgreSQL нет приветствия сервера — диалог начинает **клиент**. Первое сообщение — `StartupMessage`, и в нём уже открытым текстом лежит имя пользователя и базы:

```
$ tshark -r pg.pcap -Y pgsql -T fields -e pgsql.startup.user -e pgsql.startup.database
alice  appdb
```

Дальше сервер выбирает метод аутентификации: `md5` (соль + двойной MD5) или `SCRAM-SHA-256` (современный, устойчив к перехвату без активного MITM). При `trust` в `pg_hba.conf` пароль не спрашивают вовсе — и это самая частая мисконфигурация внутренних БД. В дампе `trust` выглядит как успешная аутентификация без challenge: клиент сразу получает `AuthenticationOk`.

## MSSQL: TDS Pre-Login и логин-пакет

MSSQL работает по **TDS**. Сначала идёт **Pre-Login** — обмен возможностями (версия, шифрование), затем **Login7** с именем пользователя и зашифрованным паролем (TDS «переворачивает» байты и XOR-ит с солью). Пользователь виден открытым текстом:

```
$ tshark -r tds.pcap -Y tds -T fields -e tds.type -e tds.login.user_name
18  sa
```

`tds.type 18` — Login7. Логин `sa` сразу подсказывает, что кто-то ходит под суперпользователем — а это либо админский скрипт, либо перебор дефолтных учёток.

## Таблица: порты, шифрование и что видно без TLS

| СУБД | Порт | Шифрование по умолчанию | Видно без TLS |
|---|---|---|---|
| MySQL | 3306 | нет | логин, соль, challenge-response |
| PostgreSQL | 5432 | нет | логин, имя БД, метод auth |
| MSSQL | 1433 | Pre-Login, часто TLS | логин, тип auth |
| Oracle | 1521 | нет | SID/сервис, версия |

Вывод: **до включения TLS/SSL вся metadata-часть открыта**. Пароль в чистом виде не утекает (он всегда challenge-response), но список учёток, БД и версий — да. А если включён устаревший `mysql_native_password`/`md5`, перехваченный обмен даёт материал для оффлайн-атаки.

## Если не сработало: трафика нет, хотя БД работает

Проверь три вещи. Первое — **порт**: приложение может ходить не на 3306/5432, а на кастомный или через unix-socket (тогда в сети вообще ничего нет). Второе — **шифрование**: если включён TLS, `tshark` покажет только `TLS` поверх TCP, и поля СУБД не разберутся без `SSLKEYLOGFILE`. Третье — **пул соединений**: современные приложения держат долгоживущий пул, поэтому в дампе может быть всего один handshake за весь захват. Тогда смотри именно начало сессии, а не середину.

## Почему это важно для защиты

Раз metadata-часть открыта, минимум для внутренней БД — **включить TLS** и требовать его для всех подключений (`REQUIRE SSL` в MySQL, `hostssl` в PostgreSQL). Дальше — сегментация: БД не должна быть доступна из пользовательского VLAN. И третье — не использовать `sa`/`postgres` с дефолтными паролями: перебор таких учёток в дампе виден сразу, а успех даёт RCE через `xp_cmdshell`/`COPY TO PROGRAM`.

## Куда дальше

В следующем уроке мы поднимемся выше по стеку — разберём HTTP/2 и HTTP/3, где вместо понятных строк идут бинарные фреймы и HPACK, и посмотрим, какие атаки это порождает. А пока главное запомни: даже не зная пароля, база данных рассказывает о себе достаточно, чтобы спланировать точечную атаку.

## Где пригодится

- **CTF:** задачи, где в дампе трафика лежит подключение к БД — извлечь логины, версии, иногда пароли.
- **Пентест:** точечный перебор паролей к известному пользователю, оффлайн-крекинг перехваченных хэшей.
- **Работа:** аудит настроек шифрования и `pg_hba.conf`, сегментация БД.
- **SOC:** детект сканирования и брутфорса БД по всплеску коротких подключений.
