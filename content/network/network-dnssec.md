DNSSEC добавляет к DNS криптографическую подпись записей — казалось бы, конец спуфингу. Но DNSSEC защищает только от подделки **данных**; он не шифрует и не защищает конфиденциальность, а его развёртывание полно ошибок, которые позволяют обойти валидацию. Этот урок разбирает механику и остающиеся атаки.

## Ключевые записи

| Запись | Смысл |
|---|---|
| RRSIG | подпись набора записей (RRset) приватным ключом зоны |
| DNSKEY | публичный ключ зоны (KSK и ZSK) |
| DS | делегирование доверия: хэш DNSKEY дочерней зоны в родительской |
| NSEC/NSEC3 | аутентифицированное отрицание («записи нет») |

Верификация — это **цепочка доверия**: корневая зона → TLD → домен. Родитель подписывает хэш ключа ребёнка записью DS; так доверие спускается вниз.

## Цепочка доверия и валидация

1. Резолвер знает trust anchor (корневой KSK).
2. Получает DNSKEY зоны и проверяет его по DS из родителя.
3. Проверяет RRSIG на запрошенных RRset этим ключом.
4. Для «записи нет» — проверяет NSEC/NSEC3.

Если хотя бы одно звено не сходится — ответ считается поддельным (SERVFAIL). Ключевой момент: **валидация происходит только если резолвер её включил и цепочка не разорвана**.

## Атаки и обходы

- **Downgrade / strip:** атакующий в пути удаляет RRSIG/DS или отвечает без подписи. Невалидирующий резолвер примет ответ как обычный DNS. Поэтому DNSSEC бесполезен без **strict validation** на резолвере.
- **Отсутствие DS у дочерней зоны:** если родитель не публикует DS, зона «не подписана» с точки зрения цепочки — валидация не применяется.
- **Слабые ключи/алгоритмы:** устаревшие алгоритмы (RSASHA1, короткие ключи) уязвимы.
- **NSEC zone walking:** NSEC (без «white lies»/NSEC3) позволяет перечислить все имена зоны — утечка внутренней структуры.
- **Replay и подмена NSEC3:** при слабых параметрах возможен перебор хэшей.

## Инструменты и команды

Проверка подписи и цепочки:

```bash
# получить DNSKEY и RRSIG
dig +dnssec example.com DNSKEY
dig +dnssec example.com A

# проверить валидацию через публичный валидирующий резолвер
dig @8.8.8.8 +dnssec example.com A
# при подделке/разрыве — SERVFAIL

# диагностика (dnsviz)
dnsviz probe example.com
dnsviz graph -Thtml example.com
```

Проверка NSEC-walking:

```bash
# перечисление имён (если зона отдаёт NSEC без NSEC3)
nsec3walker example.com
```

## Разобранный пример: strip-атака в лаборатории

Сценарий: в сегменте есть резолвер, который заявляет поддержку DNSSEC, но не выполняет strict validation.

1. Настраиваем MITM-позицию (ARP-спуфинг из `network-arp-deep`).
2. Перехватываем DNS-ответы и **удаляем RRSIG/DS** из ответа, оставляя только A-запись с поддельным IP.
3. Резолвер без strict validation принимает ответ — валидация не сработала, потому что подписи просто нет.
4. Подтверждаем: `dig @resolver example.com` возвращает поддельный IP.
5. Вывод: DNSSEC без обязательной валидации на резолвере не защищает; нужна конфигурация `dnssec-validation yes/auto` и проверка на клиентах.

## Защита

- **Strict validation** на всех рекурсивных резолверах; отказ отвечать без валидации.
- **Подписывать зоны целиком**, публиковать DS у родителя, следить за сроком RRSIG.
- **Современные алгоритмы** (ECDSA P-256, Ed25519), ротация ключей.
- **NSEC3 с salt** или «white lies» против zone walking.
- **Мониторинг:** алерты на SERVFAIL-всплески, истекающие подписи, пропавшие DS.

## Частые ошибки

- **Думать, что DNSSEC шифрует DNS.** Он только подписывает — конфиденциальности нет.
- **Оставлять валидацию выключенной.** Без неё RRSIG игнорируется.
- **Забывать про NSEC.** Он раскрывает все имена зоны, если не используется NSEC3.
- **Игнорировать срок подписи.** Просроченный RRSIG = SERVFAIL у валидирующих резолверов.

## Криптография DNSSEC: что именно подписывается

DNSSEC не шифрует DNS — он даёт **целостность и аутентичность** ответов. Каждый RRset (набор записей одного типа с одним именем) подписывается приватным ключом зоны; подпись лежит в RRSIG. Чтобы проверить подпись, нужен публичный ключ зоны (DNSKEY), а его хэш «заякорен» в родительской зоне (DS-запись), вплоть до корневого KSK.

Ключевые типы ключей:

| Тип | Назначение | Подписывает |
|-----|-----------|-------------|
| ZSK (Zone Signing Key) | подпись RRset в зоне | A, AAAA, MX, CNAME… |
| KSK (Key Signing Key) | подпись DNSKEY-набора | DNSKEY (в т.ч. ZSK) |
| CSK (Combined) | ZSK+KSK в одном | всё сразу |

Ротация ZSK делается часто (ежедневно/еженедельно), KSK — редко. NSEC/NSEC3 доказывают **отсутствие** записи (аутентифицированный «нет такого имени»), закрывая возможность подсунуть NXDOMAIN.

## NSEC vs NSEC3: доказательство отсутствия

NSEC перечисляет следующее имя в зоне — это позволяет «прочесть» зону через **zone walking** (`ldns-walk`, `nsec3map`). NSEC3 хэширует имена (с солью и итерациями), предотвращая простой обход, но остаётся уязвим к **offline-подбору** при слабых/повторяющихся именах.

```bash
# zone walking при NSEC (если зона его отдаёт)
ldns-walk example.com
# сбор NSEC3-хэшей для офлайн-крекинга имён
nsec3map --zone example.com --output hashes.txt
hashcat -m 8300 hashes.txt names.txt     # NSEC3 (RFC 5155)
```

NSEC3 с малым числом итераций и постоянной солью — частая ошибка: он даёт атакующему пространство для перебора поддоменов офлайн.

## Цепочка доверия по шагам

1. Резолвер получает корневой KSK (trust anchor, RFC 5011 — автообновление).
2. Проверяет RRSIG корневого DNSKEY корневым KSK.
3. Берёт DS-запись TLD, проверяет её подпись корневым ключом.
4. Спускается к зоне второго уровня: DS → DNSKEY → RRSIG → RRset.
5. Любой разрыв цепочки (нет DS, истёкшая подпись) → `SERVFAIL`.

Проверка вручную:

```bash
dig +dnssec example.com A @1.1.1.1        # флаг ad в ответе = validated
dig +dnssec +cd example.com A            # +cd отключает проверку у резолвера
delv @8.8.8.8 example.com A              # валидатор от BIND, показывает разбор
```

## Подводные камни: подписи, TTL и время

- **Истёкшие/не созревшие подписи (RRSIG inception/expiration).** Если время на сервере сбито, подпись «не созрела» → SERVFAIL. Проверяйте `date -u` и NTP.
- **TTL и max TTL подписи.** Резолвер кэширует отрицательный ответ не дольше, чем до истечения RRSIG.
- **Размер ответов и фрагментация.** DNSKEY+RRSIG раздувают ответ; при `+bufsize` меньше нужного — фрагментация UDP, которую фильтруют. TCP fallback обязателен.
- **Алгоритм 5 (RSASHA1) устарел**, алгоритм 8/13/14 (RSA-SHA256/ECDSA) — актуальны; некоторые резолверы отвергают deprecated алгоритмы.

## Атаки и обходы (расширенно)

| Атака | Условие | Результат |
|-------|---------|-----------|
| Strip (понижение до plain DNS) | резолвер не валидирует | ответ без ad, подделка возможна |
| Replay старой подписи | истёкшая/не созревшая RRSIG | зависит от валидатора |
| Zone walking (NSEC) | NSEC, а не NSEC3 | полная карта зоны |
| NSEC3 hash offline crack | слабые имена, фикс. соль | перебор поддоменов |
| Key rollover race | ошибка в смене KSK | SERVFAIL на период |
| Algorithm downgrade | валидатор без строгих алгоритмов | принятие слабой подписи |

Отдельно — **DNSSEC и DDoS**: большие подписанные ответы + ANY/amp-запросы дают усиление. Реальный отказ в обслуживании часто приходит от чужой зоны с большим DNSKEY, а не от цели.

## Разобранный пример 2: strip-атака через свой резолвер

Продолжение практики из основного урока. В лаборатории:

```bash
# Поднимаем unbound без валидации — модель «ленивого» резолвера
cat /etc/unbound/unbound.conf.d/lab.conf
# server:
#   interface: 127.0.0.1
#   do-validate: no          # <-- ключевое: без валидации
sudo systemctl restart unbound
# Теперь ответ для подписанной зоны приходит БЕЗ ad-флага
dig +dnssec bank.example A @127.0.0.1 | grep -E 'flags|RRSIG'
```

Наблюдение: подпись приходит, но `ad` отсутствует, и unbound принимает подделанный ответ, если его подсунуть на пути. Вывод: DNSSEC помогает только когда **каждый** резолвер в пути валидирует — при отключённой проверке защита не действует.

## Защита: чек-лист оператора

- Подписывать зону, публиковать DS у родителя, следить за rollover.
- Использовать NSEC3 с **случайной солью** и малым числом итераций (или NSEC, если walking допустим).
- Валидировать на рекурсивных резолверах (`do-validate: yes`, `dnssec-enable`), требовать `ad`.
- Включать TCP/EDNS0, чтобы большие ответы не резались.
- Мониторить expiration RRSIG (Zabbix/Nagios), алерт за сутки до истечения.
- Не полагаться на DNSSEC как на конфиденциальность — он про целостность, не про сокрытие имён.
