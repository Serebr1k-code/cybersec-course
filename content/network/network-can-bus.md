## Вопрос, с которого всё начинается

Ты подключаешь ноутбук к диагностическому разъёму **OBD-II** машины и запускаешь `candump`. Экран заполняется строками — десятки сообщений в секунду от блоков управления. Часть из них «штатные»: обороты, скорость, положение руля. Но в потоке есть кадр, которого быть не должно. Как его заметить и что вообще означает каждая строка?

В прошлом модуле ([`network-module-automotive`](network-module-automotive)) мы разобрали, что CAN — это широковещательная шина без аутентификации. Теперь спустимся на уровень кадра и посмотрим, как он устроен изнутри.

## Наш пример: одна строка candump

Вот как выглядит вывод `candump -a can0` (флаг `-a` просит печатать данные ещё и в ASCII):

```
  can0  0C0   [8]  1A 2B 3C 4D 5E 6F 70 80   '..<M^op.'
  can0  1A0   [8]  00 00 0F A0 00 00 00 00   '........'
```

Разберём эту строку по полям, слева направо. Именно из этих четырёх частей и состоит любой кадр CAN.

## Шаг 1: что означают поля кадра

- `can0` — **интерфейс** (имя шины в Linux). У машины их может быть несколько.
- `0C0` — **идентификатор кадра** (CAN ID), обычно 11-битный, в hex.
- `[8]` — **DLC** (Data Length Code): сколько байт данных в кадре. Классический CAN — максимум 8.
- `1A 2B …` — **данные**, ровно DLC байт.
- `'..<M^op.'` — то же в ASCII (`-a`); нечитаемые байты печатаются точками.

Главное, что нужно усвоить: **CAN ID — это не адрес получателя**. Он говорит, *о чём* кадр (например, `0x0C0` — «обороты двигателя»), а слушают его все узлы одновременно. Никакого «кому» в CAN нет.

## Шаг 2: арбитраж — почему ID так важен

Шина CAN — общая «шина-монополия»: одновременно передавать может только один узел. Если несколько узлов начали говорить разом, побеждает тот, у кого **меньший числовой ID**. Это называется **арбитраж** и решается прямо на уровне битов: доминирующий бит `0` перебивает рецессивный `1`.

Отсюда две практические вещи:

1. **Приоритет = важность.** Аварийные сообщения (тормоз, подушка) имеют маленькие ID и всегда «продавливают» остальных.
2. **Атакующий может давить шину.** Отправляя кадры с ID `0x000`, можно монополизировать шину и заглушить полезный трафик (это уже отказ в обслуживании).

Посмотреть, какие ID вообще есть в дампе, можно так:

```
$ cut -d' ' -f3 candump.log | sort -u
0C0
1A0
7DF
```

## Шаг 3: почему кадр можно подделать

В CAN нет полей «кто отправитель» и нет подписи. Есть только CRC — контрольная сумма целостности, которая ловит случайные искажения, но **не** защищает от подделки: атакующий посчитает корректный CRC для своего кадра. Значит, любой, кто физически подключился к шине (через OBD-II, USB-CAN адаптер или скомпрометированный блок), может отправить кадр с любым ID и любыми данными — остальные его примут.

Классические атаки на CAN:

| Атака | Что делает | Последствие |
|---|---|---|
| Инъекция | шлёт кадр с чужим ID | блоки видят ложные данные |
| Реплей | повторяет записанный кадр | открытие замка, повтор команды |
| Bus-off / DoS | заваливает шину кадрами | узел отключается от шины |
| Sniffing | пассивно читает шину | утечка данных о машине |

## Полный прогон от начала до конца

В нашей задаче `candump.log` содержит поток кадров, а в `task.md` перечислены «штатные» ID блока. Один кадр использует ID **не из списка** и несёт поле `payload:<base64>`. Это и есть инъекция.

```
$ cat task.md
Разрешённые ID блока: 0C0 (обороты), 1A0 (скорость), 2F1 (руль).
Любой другой ID — посторонний.

$ grep 7DF candump.log
  can0  7DF   [8]  payload:bnRve2M0bl9idTVfMW5qM2N0MTBufQ==

$ grep 7DF candump.log | cut -d: -f2 | base64 -d
nto{c4n_bu5_1nj3ct10n}
```

Мы нашли посторонний кадр, вырезали base64-полезную нагрузку (`cut -d: -f2`) и декодировали её (`base64 -d`). Осталось записать флаг в `answer.txt` и набрать `check`.

## Если не сработало

- **Видишь несколько посторонних ID?** Проверь `task.md` внимательно: «штатных» может быть больше, чем кажется.
- **`cut` вернул не то?** Убедись, что делишь по `:` — в нашем логе base64 идёт после `payload:`.
- **Флаг не похож на `nto{...}`?** Значит, декодировал не ту строку: поле `payload:` есть только у поддельного кадра.

## Что мы теперь знаем

- Кадр CAN = ID + DLC + до 8 байт данных; ID говорит «о чём», а не «кому».
- Арбитраж решает конфликт по меньшему ID; маленькие ID = высокий приоритет.
- В CAN нет аутентификации: CRC защищает от помех, но не от подделки.
- `candump -a` показывает и байты, и ASCII; посторонний ID — первый признак инъекции.

## Кадр CAN на уровне битов

То, что `candump` печатает одной строкой, на проводе — последовательность полей. Классический кадр (CAN 2.0A) выглядит так:

| Поле | Длина | Смысл |
|---|---|---|
| SOF | 1 бит | Start Of Frame, доминирующий `0` |
| ID | 11 бит | идентификатор (тема сообщения) |
| RTR | 1 бит | 0 = данные, 1 = запрос данных (remote frame) |
| IDE | 1 бит | 0 = стандартный 11-битный ID |
| r0 | 1 бит | зарезервирован |
| DLC | 4 бита | длина данных 0…8 |
| Data | 0–8 байт | полезная нагрузка |
| CRC | 15 бит + 1 | контрольная сумма |
| ACK | 2 бита | любой принявший узел ставит доминирующий бит |
| EOF | 7 бит | End Of Frame, рецессивные `1` |

Обрати внимание на **ACK**: подтверждение ставит *любой* узел, который корректно принял кадр, а не конкретный получатель. В CAN нет понятия «доставлено адресату» — только «кто-то на шине услышал». Это ещё раз подчёркивает: аутентификации в протоколе нет.

## DBC и как из байтов получаются значения

Сырые байты вроде `00 00 0F A0` ничего не говорят, пока не известна **раскладка сигналов**. Её описывают в файле **DBC**: для каждого ID указано, какие биты какому сигналу принадлежат, порядок байтов (Intel/little-endian или Motorola/big-endian), смещение и масштаб.

Пример записи DBC (упрощённо):

```
BO_ 320 EngineData: 8 ECU
 SG_ EngineSpeed : 16|16@1+ (0.25,0) [0|16383.75] "rpm" Vector__XXX
 SG_ CoolantTemp : 0|8@1+ (1,-40) [-40|215] "degC" Vector__XXX
```

Читается так: `EngineSpeed` — 16 бит, начиная с бита 16, little-endian, множитель 0.25. Если в кадре `0x1A0` байты 2–3 равны `0F A0`, то little-endian значение = `0xA00F` = 40975, а после масштаба 0.25 → 10243.75 rpm. Без DBC ты видишь только `0F A0` — с DBC видишь физическую величину.

Отсюда практический вывод для пентеста: **найди DBC** (часто лежит в открытых репозиториях, на форумах владельцев, в телематике) — и инъекция станет осмысленной. Иначе ты вбрасываешь байты наугад.

## Реплей: почему записанный кадр опасен

Самая недооценённая атака — не инъекция, а **реплей**. Многие команды кузова (открыть багажник, снять блокировку) не имеют ни nonce, ни счётчика: достаточно повторно послать ранее записанный кадр. Порядок действий:

```
# 1) записать трафик в момент легитимного действия
$ candump -l can0

# 2) найти нужный кадр и отфильтровать
$ grep -i 0x2F1 candump-*.log

# 3) воспроизвести его
$ cansend can0 2F1#0102030405060708
```

Защита от реплея — только на уровне приложения (счётчик, подпись), в самом CAN её нет. Поэтому современные шлюзы добавляют SecOC (Secure Onboard Communication) — MAC на кадр, — но это отдельный слой, и он есть далеко не везде.

## Краевые случаи: CAN FD, перегрузка и шум

- **CAN FD** расширяет данные до 64 байт и поднимает скорость в фазе данных. В `candump` он печатается так же, но DLC больше 8 — не пугайся `[64]`.
- **Bus-off.** Если узел слишком часто проигрывает арбитраж или ловит ошибки, контроллер уходит в bus-off и отключается от шины. Атакующий может спровоцировать это намеренно — «глушение» узла без физического доступа к нему.
- **Error frames.** При нарушении формата шина рассылает error frame. В логе это видно как всплеск ошибок — признак и помехи, и инъекции с неверным форматом.
- **Одиночный сэмпл ≠ картина.** Сигнал может меняться по расписанию (циклические кадры раз в 10/100 мс). Чтобы отличить инъекцию от штатного кадра, смотри частоту: посторонний ID обычно появляется «пачкой» или, наоборот, однократно.

## Куда дальше

Дальше возьмём [`network-uds`](network-uds) — диагностический протокол, который работает *поверх* CAN: те самые сервисы, которыми сервисный сканер читает и стирает ошибки, а атакующий — перепрошивает блоки. А пока запомни: CAN — это широковещательная шина без аутентификации, где ID задаёт смысл и приоритет.

## Где пригодится

- **CTF:** категория Network — CAN-дампы, декодирование сигналов.
- **Пентест:** автомобильная электроника, OBD-II, телематика.
- **Работа (SOC):** детект посторонних ID и аномальной частоты кадров.
- **IoT:** шлюзы CAN↔IP и телематические блоки.
