Фрагментация IP задумана как полезная функция: если пакет больше MTU канала, маршрутизатор режет его на части, а принимающая сторона собирает обратно. Но именно эта «сборка на хосте» создаёт расхождение между тем, что видит промежуточный фильтр (IDS/фаервол), и тем, что в итоге получает конечная система. На этом расхождении строятся классические атаки — от DoS-«teardrop» до тонкого обхода сигнатур.

## Как устроена фрагментация IPv4

IPv4-заголовок содержит три поля, управляющих фрагментацией:

- **Identification (ID)** — 16-бит номер; все фрагменты одного пакета имеют одинаковый ID.
- **Flags** — три бита: `Reserved`, `DF` (Don't Fragment) и `MF` (More Fragments). MF=1 означает «за этим фрагментом есть ещё».
- **Fragment Offset** — 13-бит смещение данных фрагмента в исходном пакете, **измеряется в 8-байтовых блоках**.

Ключевое правило: фрагментируется только полезная нагрузка. Каждый фрагмент несёт свой полный IP-заголовок (со своим offset/MF), а L4-заголовок (TCP/UDP) целиком попадает лишь в **первый** фрагмент (offset=0). Смещения, не кратные 8, невозможны — последний фрагмент «добивается» и его реальная длина берётся из поля Total Length.

```
Фрагмент 0: [IP hdr | TCP hdr + первые данные] MF=1 offset=0
Фрагмент 1: [IP hdr | данные]                  MF=1 offset=185 (1480/8)
Фрагмент 2: [IP hdr | хвост]                   MF=0 offset=370
```

Промежуточные устройства, которые фильтруют «по порту», часто смотрят только первый фрагмент (там есть L4-заголовок) — остальные фрагменты для них бесструктурный payload.

## Классы атак на фрагментацию

| Атака | Механизм | Эффект |
|---|---|---|
| Teardrop | Фрагменты с перекрывающимися/отрицательными offset | Падение ядра при сборке |
| Overlapping fragments | Два фрагмента пишут в один диапазон, но с разными данными | Обход IDS, подмена данных |
| Tiny fragment | Первый фрагмент крошечный, L4-заголовок разорван между фрагментами | Обход правил по порту |
| Fragment flood | Масса неполных фрагментов | Исчерпание буфера сборки (DoS) |
| Fragment ID evasion | Смена ID / рандомизация | Уклонение от реконструкции |

Самая практичная для пентеста — **overlapping fragments**: IDS собирает поток одним способом, а целевая ОС (BSD/Windows/Linux) — другим. Если политика сборки различается, сигнатура не срабатывает, а полезная нагрузка всё равно доставляется.

## Инструменты: Scapy и nmap

Ручная сборка — через Scapy. Пример «tiny fragment»: разрываем TCP-заголовок так, что первый фрагмент содержит только 8 байт TCP, а порт назначения попадает во второй.

```python
from scapy.all import *
ip = IP(dst="10.0.0.5", id=12345)
payload = b"GET / HTTP/1.1\r\nHost: victim\r\n\r\n"
# первый фрагмент: 8 байт данных, offset 0
f1 = ip / Raw(load=payload[:8]); f1.flags = "MF"; f1.frag = 0
# второй фрагмент: остаток, offset 1 (8 байт)
f2 = ip / Raw(load=payload[8:]); f2.frag = 1
send(f1); send(f2)
```

Nmap умеет фрагментировать свои probe-пакеты для обхода фильтров:

```bash
# -f режет пакеты на 8-байтовые фрагменты; -ff — на 16-байтовые
sudo nmap -sS -Pn -f -p 22,80,443 10.0.0.5
sudo nmap -sS -Pn --mtu 16 -p 445 10.0.0.5   # кратно 8
```

`--mtu` должен быть кратен 8, иначе nmap выдаст ошибку. `-f` — это сокращение для `--mtu 8`.

## Разобранный пример: teardrop в PCAP

Классическая CTF-задача: дан дамп, где атакующий шлёт перекрывающиеся фрагменты, а флаг спрятан в том фрагменте, который «победит» при сборке на конкретной ОС.

1. Открываем дамп и группируем по `ip.id`:
   ```
   tshark -r frag.pcap -Y "ip.flags.mf==1 || ip.frag_offset>0" \
     -T fields -e ip.id -e ip.flags.mf -e ip.frag_offset -e ip.len -e data.data
   ```
   Вывод покажет, что offset-ы перекрываются:
   ```
   0x3039  1  0     1500  ...
   0x3039  0  185   40    ...   # смещение 185*8=1480 — перекрытие с первым
   ```
2. Wireshark по умолчанию склеивает фрагменты по алгоритму, близкому к Linux. Если флаг «не влезает», меняем политику: `Edit → Preferences → Protocols → IPv4 → Reassemble fragmented IPv4 datagrams` и смотрим, какой фрагмент реально перезаписывает данные.
3. Для быстрой проверки «что увидит целевая ОС» используем scapy-реконструкцию с ручной политикой first-wins/last-wins.

## Обход IDS и что видят фильтры

Большинство сетевых IDS (Snort/Suricata) включают препроцессор дефрагментации (`defrag`/`stream`). Но конфигурация «target-based» задаёт политику сборки: `first`, `last`, `linux`, `bsd`, `windows`, `solaris`. Если политика IDS не совпадает с ОС жертвы — появляется **evasion-окно**. Практический тест — отправить два перекрывающихся фрагмента и проверить, срабатывает ли алерт:

- `first` — выигрывает фрагмент, пришедший первым;
- `last` — выигрывает пришедший последним;
- `linux`/`bsd`/`windows` — нюансы по границам и «дыркам» (gaps).

## Частые ошибки и подводные камни

- **Считать, что фрагментация «устарела».** Она по-прежнему встречается при IPv6 (extension header Fragment), в туннелях и при малом MTU; для IPv6 фрагментирует только источник.
- **Забывать про `DF`.** Если установлен Don't Fragment, маршрутизатор не режет пакет, а шлёт ICMP «fragmentation needed» — это основа PMTUD и вектор атаки на него (ICMP blackhole).
- **Путать offset в байтах и в 8-байтовых блоках.** В заголовке — блоки; в tshark поле `ip.frag_offset` тоже в блоках, а не в байтах.
- **Ловить перекрытие по «номеру», а не по диапазону.** Перекрытие определяется пересечением `[offset*8, offset*8+len)`.
- **Игнорировать таймаут сборки.** Неполная фрагментация сбрасывается через 30–60 секунд; flood именно это и эксплуатирует.

## Что дальше / решение

Фрагментация — не самоцель, а инструмент. Дальше стоит посмотреть на **IPv6-фрагментацию** (extension header 44), **ICMP-атаки на PMTUD** и **evasion в целом** (пересечение с `network-idps-evasion`). Для защиты: включить target-based дефрагментацию на IDS с политикой, совпадающей с ОС хостов, ограничить частоту фрагментов на границе (`iptables -f`, `nf_conntrack_frag6`), и по возможности блокировать фрагментированный трафик на периметре, если он не нужен. Для CTF — тренируйтесь реконструировать фрагменты вручную в Scapy: это навык, который окупается и в PCAP-задачах.

|---|---|
| `-f` | Фрагменты по 8 байт (`--mtu 8`) |

| `--mtu N` | Свой размер, кратный 8 |

## Фрагментация IPv6

В IPv6 фрагментирует **только отправитель** — промежуточные маршрутизаторы не дробят пакеты (иначе ломается PMTUD и End-to-End принцип). Фрагментация выполняется через **extension header 44 (Fragment Header)**, который содержит:

- **Fragment Offset** — тоже в 8-байтовых блоках, но 13 бит;
- **M** (More Fragments) — аналог MF;
- **Identification** — 32-бит (в отличие от 16-бит в IPv4).

Минимальный MTU IPv6 — 1280 байт; ниже — фрагментация на источнике. Атаки аналогичны IPv4 (overlap, flood), плюс появилось понятие **atomic fragment** (offset=0, M=0) — пакет с fragment-заголовком, но без реального дробления; его часто используют для обхода фильтров, а RFC 6946 разрешает такие фрагменты дропать. В tshark фильтр: `ipv6.nxt==44` или `ipv6.fraghdr`. Многие сканеры (nmap `-6`) и evasion-инструменты умеют строить v6-фрагменты, а IDS для IPv6 требует отдельного препроцессора — частая слепая зона.

## DoS через фрагментацию и буфер сборки

Ядро держит **буфер сборки** (reassembly buffer) для неполных датаграмм до таймаута (в Linux — параметр `net.ipv4.ipfrag_time`, по умолчанию 30 с; в новых ядрах с nftables — `nf_conntrack_frag*`). Атакующий шлёт множество «дырявых» фрагментов с разными ID, и таблица сборки переполняется — легитимные фрагментированные пакеты начинают отбрасываться. Это классический ресурсный DoS. Смягчение:

```bash
# Ограничить число фрагментов и скорость на границе
sudo iptables -A INPUT -f -m limit --limit 100/s --limit-burst 200 -j ACCEPT
sudo iptables -A INPUT -f -j DROP
# Отключить сборку фрагментов там, где она не нужна (устаревающий путь)
sysctl net.ipv4.ipfrag_high_thresh
```

Для IPv6 лимиты задаются `net.ipv6.ip6frag_*` и nftables `frag`-модулем. Важно понимать: полностью запрещать фрагменты рискованно (сломается легитимный трафик с малым MTU и туннели), поэтому чаще ставят rate-limit, а не DROP.

## Практическая лаборатория

Соберите стенд из трёх контейнеров (атакующий — жертва — снифер) в `containerlab` или GNS3 с MTU 1500 на одном линке и 1280 на другом. Скрипт на Scapy, который шлёт перекрывающиеся фрагменты, и сниффер, который показывает, как Wireshark/tshark собирает их по разным политикам. Меняя `Preferences → IPv4 → reassembly`, вы наблюдаете, как «флаг» меняется в зависимости от того, какой фрагмент считается победителем — это ровно то, что проверяют на CTF. Дополнительно запустите Suricata в режиме IDS с `defrag: yes` и политикой `linux`, затем поменяйте политику на `bsd` — увидите расхождение в алертах. Такой стенд даёт понимание, почему target-based дефрагментация критична.

## Где пригодится

- **CTF:** задачи Network/PCAP, где флаг собирается из перекрывающихся фрагментов.
- **Пентест:** обход межсетевых экранов и IDS при сканировании и доставке полезной нагрузки.
- **Работа/SOC:** понимание аномалий фрагментации помогает писать и тюнить правила Snort/Suricata.
- **Сертификации:** OSCP/OSEP — evasion-техники на сетевом уровне.
