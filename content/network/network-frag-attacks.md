## Вопрос, с которого всё начинается

Тебе дали дамп и сказали: «тут спрятан флаг, он разбит на части». Открываешь — а вместо целых пакетов куча обрывков с одинаковым номером. Это **фрагментация IP**: если пакет больше, чем пропускает канал (MTU), маршрутизатор режет его на части, а принимающая сторона собирает обратно.

И вот в чём фокус: **промежуточный фильтр и конечная система видят разное**. Фильтр (IDS, фаервол) смотрит на куски, а жертва — на собранный пакет. На этом расхождении строятся и классические DoS-атаки, и тонкий обход сигнатур. Разберём.

Этот урок опирается на [`network-tcpip`](network-tcpip).

## Наш пример: дамп из обрывков

Смотрим фрагментированный трафик и группируем куски по номеру пакета:

```
$ tshark -r frag.pcap -Y "ip.flags.mf==1 || ip.frag_offset>0" \
  -T fields -e ip.id -e ip.flags.mf -e ip.frag_offset -e ip.len
0x3039    1    0      1500
0x3039    0    185    40
```

Два фрагмента с одним `ip.id = 0x3039`. Первый: `MF=1` (есть продолжение), `offset=0`, длина 1500. Второй: `MF=0` (последний), `offset=185`, длина 40. Разберём, что означают эти поля.

## Откуда берётся фрагментация: MTU и флаг DF

Прежде чем нырять в поля, разберёмся, почему пакет вообще режется. У каждого канала есть **MTU** (Maximum Transmission Unit) — максимальный размер кадра, который он пропускает; в Ethernet это обычно 1500 байт. Если пакет больше MTU, отправитель режет его сам (при `DF=0`) либо получает ошибку.

Флаг **DF** (Don't Fragment) запрещает фрагментацию. Современные ОС по умолчанию ставят `DF=1` и используют **PMTUD** (Path MTU Discovery): посылают пакет максимального размера с `DF=1`, и если он упирается в узкое место, маршрутизатор возвращает ICMP «fragmentation needed» с меньшим MTU. Хост запоминает его и шлёт мельче.

Отсюда два следствия:

- Легитимный трафик почти не фрагментируется, поэтому фрагменты сами по себе — аномалия, заметная сенсору.
- Если заблокировать ICMP «fragmentation needed», PMTUD ломается — это «чёрная дыра» (PMTUD blackhole), из-за которой часть соединений зависает.

Именно потому, что фрагментация редка и подозрительна, её и берут на вооружение для обхода: фильтр, не пересобирающий фрагменты, не видит в них структуру.

## Шаг 1: три поля, управляющие фрагментацией

В IPv4-заголовке за фрагментацию отвечают:

- **Identification (ID)** — 16-битный номер. Все фрагменты одного пакета имеют **одинаковый** ID, чтобы приёмник мог их собрать.
- **Flags** — три бита: `Reserved`, `DF` (Don't Fragment — не фрагментировать) и `MF` (More Fragments — есть ещё).
- **Fragment Offset** — смещение данных этого фрагмента в исходном пакете, **в 8-байтовых блоках** (не в байтах!).

Ключевое правило: фрагментируется только **полезная нагрузка**. Каждый фрагмент несёт свой полный IP-заголовок, а заголовок TCP/UDP целиком попадает лишь в **первый** фрагмент (`offset=0`).

```text
Фрагмент 0: [IP hdr | TCP hdr + первые данные] MF=1 offset=0
Фрагмент 1: [IP hdr | данные]                  MF=1 offset=185 (1480/8)
Фрагмент 2: [IP hdr | хвост]                   MF=0 offset=370
```

Вот почему фильтры «по порту» часто смотрят только первый фрагмент: в остальных нет заголовка TCP, для них это бесструктурные данные.

## Шаг 2: классы атак на фрагментацию

| Атака | Механизм | Эффект |
|---|---|---|
| **Teardrop** | перекрывающиеся или «отрицательные» offset | падение ядра при сборке |
| **Overlapping fragments** | два фрагмента пишут в один диапазон с разными данными | обход IDS, подмена данных |
| **Tiny fragment** | первый фрагмент крошечный, L4-заголовок разорван | обход правил по порту |
| **Fragment flood** | масса неполных фрагментов | исчерпание буфера сборки (DoS) |
| **Fragment ID evasion** | смена/рандомизация ID | уклонение от реконструкции |

Самая практичная для пентеста — **overlapping fragments**: IDS собирает поток по одной политике, а целевая ОС (Linux/BSD/Windows) — по другой. Если политики различаются, сигнатура не срабатывает, а нагрузка доставляется.

## Шаг 3: собираем фрагменты в Scapy

Разберём, что именно «увидит» жертва. В Scapy собираем пакет вручную:

```python
from scapy.all import *
ip = IP(dst="10.0.0.5", id=12345)
payload = b"GET / HTTP/1.1\r\nHost: victim\r\n\r\n"
f1 = ip / Raw(load=payload[:8]); f1.flags = "MF"; f1.frag = 0
f2 = ip / Raw(load=payload[8:]); f2.frag = 1
send(f1); send(f2)
```

Здесь первый фрагмент содержит только 8 байт (крошечный), второй — остаток. `frag` задаётся в блоках, поэтому `frag=1` — это смещение 8 байт.

Nmap умеет фрагментировать свои probe-пакеты для обхода фильтров:

```
$ sudo nmap -sS -Pn -f -p 22,80,443 10.0.0.5
```

`-f` режет пакеты на 8-байтовые фрагменты, `-ff` — на 16-байтовые, `--mtu N` задаёт свой размер (кратный 8).

## Шаг 4: где именно окно обхода

Большинство IDS (Snort/Suricata) умеют дефрагментировать поток. Но их политика сборки задаётся вручную: `first` (побеждает первый фрагмент), `last` (последний), `linux`, `bsd`, `windows`. Если политика IDS **не совпадает** с ОС жертвы, появляется **evasion-окно**: IDS видит безобидный пакет, а жертва — совсем другой.

```
$ tshark -r frag.pcap -T fields -e ip.frag_offset -e data.data
0    474554202f...
185  0d0a0d0a...
```

Проверка простая: отправить два перекрывающихся фрагмента и посмотреть, сработает ли алерт на IDS и что соберёт жертва. Расхождение = уязвимость.

## Шаг 5: DoS через буфер сборки

Ядро держит **буфер сборки** для неполных датаграмм, пока не истечёт таймаут (в Linux `net.ipv4.ipfrag_time`, по умолчанию 30 с). Атакующий шлёт много «дырявых» фрагментов с разными ID — таблица сборки переполняется, и легитимные фрагментированные пакеты начинают отбрасываться.

Смягчение — ограничить частоту фрагментов на границе, а не запрещать их полностью (иначе сломается легитимный трафик с малым MTU):

```
$ sudo iptables -A INPUT -f -m limit --limit 100/s --limit-burst 200 -j ACCEPT
$ sudo iptables -A INPUT -f -j DROP
```

## Шаг 6: фрагментация IPv6 — коротко

В IPv6 фрагментирует **только отправитель** (маршрутизаторы не дробят), через **extension header 44**. Поля похожи, но ID — 32-битный. Минимальный MTU IPv6 — 1280 байт. Есть особый случай **atomic fragment** (`offset=0`, `M=0`) — пакет с fragment-заголовком, но без реального дробления; его часто используют для обхода фильтров. Фильтр в tshark: `ipv6.nxt==44`. Многие IDS для IPv6 требуют отдельного препроцессора дефрагментации — частая слепая зона.

## Практикум: собираем флаг из фрагментов

В CTF флаг часто «размазан» по фрагментам, и его нужно собрать обратно. Wireshark делает это сам: при включённой опции **Reassemble fragmented IPv4 datagrams** (включена по умолчанию) он склеивает фрагменты в один пакет. Найти нужный поток проще по фильтру:

```
$ tshark -r frag.pcap -Y "ip.flags.mf==1 || ip.frag_offset>0" -T fields -e frame.number -e ip.id
1  0x3039
2  0x3039
```

Оба кадра имеют один `ip.id = 0x3039` — это один пакет, разрезанный надвое. Теперь смотрим «склеенный» результат: в нём целиком видна полезная нагрузка.

```
$ tshark -r frag.pcap -Y "ip.id==0x3039" -T fields -e data.data
474554202f...
```

Если автосборка мешает (например, флаг спрятан именно в **перекрытии**, где у одних и тех же байт два разных значения), её отключают флагом `-o ip.defragment:FALSE` и собирают вручную. Тогда видны оба варианта, и флаг может оказаться в том, который «побеждает» на конкретной ОС — это и есть учебная модель evasion-окна.

## Teardrop: почему сам по себе он уже не работает

**Teardrop** — историческая DoS-атака 1997 года. Она опиралась на ошибку сборки: если подобрать offset так, что фрагменты перекрываются с «неправильной» длиной, ядро считало размер буфера неверно и падало. Современные ядра проверяют границы и корректно отбрасывают такие датаграммы, поэтому сегодня teardrop не роняет систему.

Но идея жива в двух формах:

- **Асимметрия сборки** — перекрытия используют не для падения, а для расхождения с IDS (см. Шаг 4).
- **Fragment flood** — не падение, а исчерпание ресурса: тысячи «дырявых» датаграмм с разными ID держат таблицу сборки заполненной, и легитимные фрагменты отбрасываются.

Проверить устойчивость к teardrop-классу можно через Scapy, но это уже стрельба по живому — только в авторизованной лаборатории.

## Что мы теперь знаем

- Фрагментация режет полезную нагрузку; каждый фрагмент несёт свой IP-заголовок с ID, MF и offset.
- Fragment Offset измеряется в 8-байтовых блоках; заголовок TCP/UDP — только в первом фрагменте.
- Перекрывающиеся фрагменты дают evasion, когда политика сборки IDS ≠ политика ОС.
- Teardrop ломает сборку, fragment flood переполняет буфер сборки.
- Защита — target-based дефрагментация на IDS с политикой, совпадающей с хостами, и rate-limit фрагментов.

## Куда дальше

Мы разобрали, как один пакет распадается на части и как это расхождение используют. Дальше — UDP: транспорт без состояния, где спуфинг источника тривиален, а амплификация превращает крошечный запрос в гигантский ответ. А пока запомни: **фильтр и жертва могут видеть разные пакеты — этим и пользуются.**

## Где пригодится

- **CTF:** задачи Network/PCAP, где флаг собирается из перекрывающихся фрагментов.
- **Пентест:** обход межсетевых экранов и IDS при сканировании и доставке полезной нагрузки.
- **Работа/SOC:** понимание аномалий фрагментации помогает писать и тюнить правила Snort/Suricata.
- **Сертификации:** OSCP/OSEP — evasion-техники на сетевом уровне.
