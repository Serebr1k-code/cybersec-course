## Вопрос, с которого всё начинается

Ты в сегменте `10.0.0.0/24`, и трафик в другой сегмент идёт «сам собой» — его направляет маршрутизация. Но маршруты не берутся из ниоткуда: маршрутизаторы обмениваются ими по динамическим протоколам, и во многих конфигурациях **без аутентификации**. Значит, атакующий в сегменте может подсунуть ложный маршрут и увести чужой трафик через себя.

Этот модуль — про то, как маршрутизатор выбирает путь и как этот выбор можно подменить. Он опирается на [`network-routing`](network-routing) и [`network-bgp-hijack`](network-bgp-hijack) и ведёт к [`network-rip-eigrp`](network-rip-eigrp) и [`network-mpls-vrf`](network-mpls-vrf).

## Наш пример: маршрут до 10.20.30.40

Возьмём хост `10.0.0.5` и посмотрим, куда он на самом деле отправит пакет до адреса `10.20.30.40`:

```
$ ip route get 10.20.30.40
10.20.30.40 via 10.0.0.1 dev eth0 src 10.0.0.5 uid 1000
    cache
```

Читается так: пакет уйдёт на шлюз `10.0.0.1` через интерфейс `eth0`. Но откуда хост знает про сеть `10.20.30.0/24`? Посмотрим таблицу:

```
$ ip route show
default via 10.0.0.1 dev eth0
10.0.0.0/24 dev eth0 proto kernel scope link src 10.0.0.5
10.20.30.0/24 via 10.0.0.1 dev eth0 proto ospf metric 20
```

Строка `proto ospf` — ключ. Маршрут до `10.20.30.0/24` пришёл не вручную, а по протоколу **OSPF**. Дальше разберём, как это работает и как этим злоупотребить.

## Шаг 1: как маршрутизатор выбирает путь

Все маршруты хранятся в **RIB** (Routing Information Base) — таблице маршрутов. Если к одной сети ведут несколько путей, выбор идёт по трём правилам по порядку:

1. **Longest prefix match** — побеждает самый специфичный префикс. Маршрут `/32` точнее, чем `/24`, и перекроет его.
2. **Administrative Distance (AD)** — мера доверия к источнику маршрута.
3. **Метрика** — «стоимость» пути внутри одного протокола.

## Шаг 2: Administrative Distance — кому верить

AD — число, показывающее, насколько мы доверяем источнику маршрута. Меньше — приоритетнее:

| Источник | AD (Cisco) |
|---|---|
| Connected | 0 |
| Static | 1 |
| eBGP | 20 |
| EIGRP | 90 |
| OSPF | 110 |
| RIP | 120 |
| iBGP | 200 |

Именно здесь кроется атака: если подсунуть маршрут от источника с меньшим AD **или более специфичный префикс**, он победит легитимный. Например, объявление сети `10.20.30.0/25` (специфичнее, чем `/24`) уведёт половину адресов.

## Шаг 3: OSPF на проводе

**OSPF** — link-state протокол: каждый маршрутизатор рассылает описание своих связей, и все строят одинаковую карту сети. Соседи находят друг друга через **Hello**-пакеты на multicast-адрес `224.0.0.5`:

```
$ sudo tcpdump -i eth0 -nn 'ip proto 89' -c 4
16:02:11 IP 10.0.0.1 > 224.0.0.5: OSPFv2, Hello, length 44
16:02:21 IP 10.0.0.2 > 224.0.0.5: OSPFv2, Hello, length 44
```

OSPF использует IP-протокол **89** (не TCP/UDP). Через Hello выбирается **DR** (Designated Router) — узел, через который идёт основной обмен. Подделав Hello с большим Router Priority, можно стать DR, а затем рассылать поддельные **LSA** (Link State Advertisement) и уводить трафик.

## Шаг 4: другие протоколы

- **RIP** — дистанционно-векторный, метрика = число хопов, максимум 15. Простой, медленный, без аутентификации по умолчанию.
- **EIGRP** — гибридный (Cisco), метрика по bandwidth/delay; атакуется поддельными update.
- **BGP** — внешняя маршрутизация между автономными системами (AS); здесь работают hijack и route leak (см. [`network-bgp-hijack`](network-bgp-hijack)).

## Шаг 5: MPLS и VRF — сегментация

**MPLS** коммутирует по меткам (label), а не по IP: путь определяется заранее и называется **LSP** (Label Switched Path). **VRF** (Virtual Routing and Forwarding) создаёт несколько независимых таблиц маршрутов на одном устройстве — так провайдер изолирует клиентов. Утечка между VRF (**route leak**) — серьёзная атака. Подробно — в [`network-mpls-vrf`](network-mpls-vrf).

## Шаг 6: метрика OSPF и лаборатория

OSPF считает стоимость пути как `reference bandwidth / interface bandwidth`. По умолчанию reference = 100 Мбит/с, поэтому 100 Мбит/с и выше дают одинаковую стоимость 1 — частая ошибка проектирования.

| Скорость | Cost (ref 100 Мбит) | Cost (ref 10 Гбит) |
|---|---|---|
| 10 Мбит/с | 10 | 1000 |
| 100 Мбит/с | 1 | 100 |
| 1 Гбит/с | 1 | 10 |
| 10 Гбит/с | 1 | 1 |

Поднять OSPF на Linux удобно через FRR:

```
$ sudo vtysh -c 'configure terminal' -c 'router ospf' -c 'network 10.0.0.0/24 area 0'
$ sudo vtysh -c 'show ip ospf neighbor'
Neighbor ID     Pri State           Address         Interface
10.0.0.1          1 Full/DR         10.0.0.1        eth0
```

Соседство устанавливается через Hello-пакеты на multicast `224.0.0.5`. Поддельный Hello с большим приоритетом делает тебя DR, а поддельные LSA уводят трафик.

## Инструмент: whois — регистрационные данные

`whois` запрашивает регистрационные записи: домены, IP-блоки и автономные системы (AS). Незаменим, чтобы связать адрес или префикс с оператором.

Ключи, которые пригодятся:
* `whois <домен>` — регистратор, даты, NS, контакты;
* `whois <IP>` — какой диапазон и организация владеют адресом;
* `whois AS<номер>` — данные автономной системы: имя, организация, маршруты;
* в BGP-задачах по `as-name`/`descr` видно, кто «увёл» префикс.

### Рабочий пример (как в лаборатории)

```
$ whois AS65002
aut-num:        AS65002
as-name:        ROGUE-TRANSIT
org:            ORG-RA1-RIPE
descr:          hijacked-prefix operator - nto{…}
country:        ZZ
```

Подсказка из лаборатории: `whois AS<номер> — информация об автономной системе (эмуляция)`.

## Что мы теперь знаем

- Маршрут выбирается по longest prefix match, затем по AD, затем по метрике.
- AD — доверие к источнику; меньше AD = приоритетнее.
- OSPF/RIP/EIGRP часто работают без аутентификации — маршрут можно подсунуть.
- OSPF — IP-протокол 89, соседи через Hello на `224.0.0.5`.
- MPLS/VRF сегментируют L3, но route leak между VRF возможен.

| Симптом | Вероятная причина |
|---|---|
| Трафик идёт «не туда» | поддельный маршрут / неверный AD |
| Сеть периодически «моргает» | flapping-линк, нестабильные update |
| Появился новый next hop | инъекция маршрута |
| Маршрут исчез после перезагрузки | нет статики/аутентификации |
| Асимметрия путей | разная метрика на концах |
| Петля маршрутизации | ошибка summary/redistribute |

## Если защита мешает

- **Включена аутентификация (MD5/ключ).** Подделать объявление сложнее — но если пароль слабый или одинаковый на всех, он перебирается офлайн.
- **passive-interface на краях.** Маршрутных пакетов на «крайних» портах нет — тогда в сегменте нечего слушать.
- **Мониторинг RIB.** Изменение таблицы маршрутов ловится по логам — атака становится заметной.
- **Фильтрация маршрутов на периметре.** Внешние объявления отсекаются по prefix-list.

## Практика: что слушать и что проверять

```
$ sudo tcpdump -i eth0 -nn 'ip proto 89 or udp port 520 or tcp port 179'
$ ip route show
$ ip -6 route show
$ traceroute -n 10.20.30.40
```

`ip proto 89` — OSPF, `udp port 520` — RIP, `tcp port 179` — BGP. Снимок `ip route show` берём как baseline: стабильность пути между запросами — простой тест на flapping и инъекцию.
