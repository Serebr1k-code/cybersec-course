## Вопрос, с которого всё начинается

Wireshark хорош, когда дамп у тебя уже есть и он небольшой. Но представь сеть, где трафик идёт непрерывно: гигабайты в час, сотни хостов. Ты не будешь открывать это в GUI и скроллить пакеты. Нужен подход, при котором инструмент сам смотрит трафик и складывает результат в **логи** — текстовые записи «кто, когда, куда и сколько».

Именно для этого придуман **Zeek** (раньше он назывался Bro). В этом уроке мы разберём, чем лог-подход отличается от пакетного, и проследим его на нашем дампе `http.pcap`.

## Наш пример: что бы Zeek увидел в http.pcap

У нас есть дамп `http.pcap`, где хост `10.0.0.5` скачал файл и залогинился. Zeek на этой машине не установлен, поэтому «магию» мы разберём по частям: сначала сами вытащим те же факты консольным `tshark`, а потом посмотрим, в каком виде Zeek их сохраняет.

Сначала — как выглядит один TCP-разговор на уровне метаданных. `tshark` умеет печатать «конверсии» — пары адресов и объём:

```
$ tshark -r http.pcap -q -z conv,tcp
TCP Conversations
                                               |       <-      | |       ->      |
10.0.0.5:51234         <-> 93.184.216.34:80         4 168 bytes        3 1151 bytes
```

Это ровно то, что Zeek пишет в свой `conn.log`: одна строка на **соединение** (connection) с адресами, портами, временем начала, длительностью, числом и объёмом байт в каждую сторону. Не содержимое, а «кто с кем говорил и сколько» — метаданные. Их в сотни раз меньше, чем пакетов, и по ним уже можно искать аномалии.

## Шаг 1: Zeek разбивает трафик на события

Как Zeek понимает, что делать? Он не хранит пакеты, а прогоняет их через **событийную модель**. Каждый протокол порождает события: началось соединение, пришёл HTTP-запрос, обнаружен TLS-хендшейк. Встроенные скрипты (на языке Zeek) подписаны на эти события и пишут записи в логи.

Вот основные логи и что в них:

| Лог | Что записывает |
|-----|----------------|
| `conn.log` | каждое соединение: адреса, порты, длительность, байты |
| `http.log` | HTTP-запросы: метод, хост, URI, user-agent, код ответа |
| `dns.log` | DNS-запросы: имя, тип, ответ |
| `ssl.log` | TLS-соединения: версия, SNI, сертификат |
| `files.log` | переданные файлы: тип, размер, хеш, кто передал |
| `notice.log` | сработавшие предупреждения (то, что похоже на атаку) |

Формат записи — **TSV** (значения через табуляцию) с шапкой из полей. Строка `conn.log` по смыслу выглядит так (поля: время, uid, источник, порт источника, назначение, порт назначения, протокол, длительность, байт вниз, байт вверх):

```
1728806582.788600  Cx1y2z  10.0.0.5  51234  93.184.216.34  80  tcp  0.001  1151  168
```

Так одну сетевую сессию сжимают в одну строку, которую потом можно искать `grep`-ом, грузить в Elastic или в RITA.

## Шаг 2: то же самое, но вручную — чтобы понять логику

Посмотрим, как эти же факты достаются из нашего дампа обычным `tshark` — это буквально то, что Zeek делает автоматически:

```
$ tshark -r http.pcap -Y http.request -T fields -e ip.src -e http.host -e http.request.uri -e http.user_agent
10.0.0.5	files.example.com	/secret.zip	curl/8.4.0
```

Строка в точности повторяет содержание `http.log`: источник, хост, путь, user-agent. А вот передача файла — это то, что Zeek вынес бы в `files.log` с хешем:

```
$ tshark -r http.pcap --export-objects http,./zeek_out
$ sha256sum zeek_out/secret.zip
<sha256-сумма>  zeek_out/secret.zip
```

Zeek считает хеш файла автоматически и записывает его в `files.log` — это удобно: по хешу можно сопоставить файл с базой вирусов или с уже виденным ранее.

## Шаг 3: notice.log — где Zeek «сам предупреждает»

Самое ценное — Zeek не просто логирует, а **детектирует** шаблоны и пишет их в `notice.log`. Примеры встроенных срабатываний: сканирование портов, подозрительные DNS-запросы, сертификаты с несовпадением имени. Пишешь свой скрипт — и Zeek предупреждает о том, что важно именно тебе.

Пример логики на языке Zeek (упрощённо): «если один источник обращается к более чем 20 портам одного получателя за минуту — это скан, запиши notice». На нашем `http.pcap` скан не спрятан, но в дампе `scan.pcap` (тоже из этой серии) хост `10.0.0.9` за секунду стучится в порты 22, 80, 443, 3306, 8080 — типичный признак сканирования:

```
$ tshark -r scan.pcap -Y 'tcp.flags.syn==1 && tcp.flags.ack==0' -T fields -e ip.src -e tcp.dstport
10.0.0.9	22
10.0.0.9	80
10.0.0.9	443
10.0.0.9	3306
10.0.0.9	8080
```

Такую же картину Zeek заметил бы и записал notice.

## Шаг 4: где Zeek применяют на практике

Zeek ставят не на рабочую станцию, а на **сенсор** — машину, которой отдают копию трафика (через зеркальный порт коммутатора или сетевой TAP). Дальше логи уезжают в хранилище:

- **Filebeat / Logstash → Elasticsearch → Kibana** — поиск и дашборды по всем логам.
- **RITA** — аналитика поверх Zeek-логов: находит beaconing (регулярные «пинги» C2) и DNS-туннели.
- **Arkime (Moloch)** — хранит пакеты, а Zeek даёт по ним индексы для поиска.

## Шаг 5: как Zeek запускают

Zeek можно запустить в двух режимах. Первый — «прочитать готовый дамп и написать логи», удобно для обучения и разбора инцидента задним числом:

```
$ zeek -r http.pcap
$ ls *.log
conn.log  dns.log  files.log  http.log  packet_filter.log
```

Ключ `-r` говорит Zeek читать pcap вместо живого интерфейса; после прогона в текущем каталоге появляются логи. Второй режим — живой: Zeek слушает интерфейс (`zeek -i eth0`) и пишет логи непрерывно, а ротацией занимается `zeekctl` (демон-менеджер с командами `deploy`, `status`, `restart`).

Свои сценарии пишут на языке Zeek в файлах `.zeek` и подключают ключом `-s` или через каталог `site/local.zeek`. Так добавляют собственные проверки — например, «предупреждать, если кто-то обратился к домену из чёрного списка».

## Что мы теперь знаем

По-простому:

1. Zeek превращает трафик в логи-метаданные, а не хранит пакеты.
2. Один разговор — одна строка в `conn.log`; HTTP — в `http.log`; файлы — в `files.log`.
3. Формат логов — TSV, удобный для `grep` и SIEM.
4. `notice.log` — автоматические предупреждения о подозрительном.
5. Zeek ставится на сенсор с копией трафика, логи уходят в Elastic/RITA.

## На что смотреть дальше

- **Не путай Zeek и IDS.** Zeek — про богатые логи; сигнатурный детект — у Suricata (следующий урок).
- **Сравни с пакетным подходом.** Если нужен сам файл — Zeek его тоже может извлекать, но тяжелее.
- **Проверь поля логов.** По `conn.log` удобно ловить длинные соединения и большой объём — признак эксфильтрации.

## Куда дальше

## Где пригодится

- **Работа / SOC:** постоянный сетевой мониторинг и охота по логам.

- **CTF:** задачи, где дан набор Zeek-логов вместо pcap.
