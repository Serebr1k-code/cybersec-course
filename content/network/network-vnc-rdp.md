## Вопрос, с которого всё начинается

Сканер нашёл открытые `5900` и `3389` — это VNC и RDP, удалённый доступ к рабочему столу. Для защитника это «дверь в дом», для атакующего — желанная цель. Разберёмся, как устроена их аутентификация и за что можно зацепиться.

## Наш пример: VNC-сервер на 10.0.0.9:5900

VNC работает по протоколу **RFB** (Remote Framebuffer). Начнём с простого: подключимся `netcat` и прочитаем приветствие.

```
$ nc 10.0.0.9 5900
RFB 003.008
```

Строка `RFB 003.008` — версия протокола: `003.008` означает RFB 3.8. По версии видно, какие методы аутентификации возможны. Сразу после неё сервер присылает **список методов безопасности** — набор байтов. Разберём, что они значат.

## Шаг 1: методы аутентификации VNC

Наиболее важный байт — это выбранный метод:

- `1` — **None**: соединение **без пароля**. Кто угодно видит экран и может управлять мышью/клавиатурой.
- `2` — **VNC Authentication**: пароль проверяется по классической схеме.
- `18` и др. — расширения (TLS и т. п.).

Если сервер предложил `None` (или ты можешь выбрать его), доступ уже получен. Это частая мисконфигурация: VNC настроили «для удобства» и забыли про пароль.

## Шаг 2: как устроена VNC-аутентификация

Метод `2` исторически слабый, и вот почему. Схема такая:

1. Сервер шлёт клиенту 16 случайных байт — **challenge** (вызов).
2. Клиент шифрует их **паролем VNC** (первые 8 символов, ключ DES) и отправляет обратно **response**.
3. Сервер проделывает то же и сравнивает.

Проблема — длина пароля: **максимум 8 символов**, и ключ DES из них получается усечением. Это делает оффлайн-подбор очень дешёвым: перехватив challenge и response, можно восстановить пароль на обычной машине. Считай, 8-символьный пароль — это не защита, а формальность.

## Шаг 3: где лежат пароли VNC

На Windows VNC-серверы (TightVNC, RealVNC, UltraVNC) часто хранят пароль в реестре, зашифрованный **фиксированным ключом** (всем известным). То есть если у тебя есть доступ к файловой системе/реестру, пароль расшифровывается одной командой.

Отсюда классический сценарий: получил любой локальный доступ → вытащил VNC-пароль из реестра → подключился к «соседней» машине по VNC. Пароль не менялся годами и используется на нескольких хостах.

## Шаг 4: RDP — порт 3389

RDP (Remote Desktop Protocol) от Microsoft — совсем другой уровень. Он гораздо сложнее и обычно включает шифрование. Ключевые понятия:

- **NLA** (Network Level Authentication) — сервер требует аутентификации **до** установки полноценной сессии. Это защищает от ряда атак и от «предварительного» расхода ресурсов.
- **CredSSP** — механизм, которым RDP передаёт учётные данные для NLA.
- **TLS** — транспорт, поверх которого обычно идёт RDP.

Проверить, включён ли NLA, можно сканером:

```
$ nmap -p3389 --script rdp-enum-encryption <target>
```

Если NLA выключен, возможны атаки вроде перебора по сессии и известные CVE.

## Шаг 5: BlueKeep (CVE-2019-0708)

**BlueKeep** — критическая уязвимость в RDP, позволяющая **выполнить код до аутентификации** (pre-auth RCE), то есть без пароля вообще. Она в классе **червеобразных**: эксплойт мог бы распространяться сам по сети. Затронуты старые версии Windows (до патча 2019 года).

Проверяется осторожно (эксплуатация может уронить сервис):

```
$ nmap -p3389 --script rdp-vuln-ms12-020 <target>
```

Практический вывод: RDP на периметре — почти всегда плохая идея. Если он нужен, то только через VPN/RD Gateway и с NLA.

## Шаг 6: брутфорс и защита

RDP/VNC часто брутфорсят (особенно из интернета). Для теста используют `hydra`/`ncrack`, но помним правило: **небольшой осмысленный список**, а не миллионы слов — онлайн-перебор по сети медленный и шумный.

Защита:

- **VNC:** пароль сложный (но помни про лимит 8 символов — лучше вообще не использовать VNC через сеть), туннелировать через SSH, не хранить пароль в реестре, использовать методы с TLS.
- **RDP:** NLA + TLS, VPN/RD Gateway, MFA, ограничение по IP, блокировка по числу попыток.
- **Общее:** не выставлять `5900/3389` в интернет; сегментация.

Для SOC: всплески неудачных RDP-логинов (Event ID 4625), новые VNC-подключения, сканирование `3389/5900` — явные сигналы.

## Почему удалённый рабочий стол — приоритетная цель

Стоит понимать, почему `3389` и `5900` так ценят атакующие. В отличие от веб-приложения, удалённый рабочий стол — это **прямой доступ к операционной системе**: файлы, буфер обмена, установленные программы, сохранённые пароли в браузере. Получив доступ к RDP, атакующий часто сразу получает и учётные данные, и путь к дальнейшему движению по сети.

Обратная сторона — **логирование**. RDP оставляет следы: события входа (успешные и неуспешные), создание сессии. Для защитника это означает, что брутфорс RDP виден; для атакующего — что нужно вести себя тише. Поэтому при пентесте RDP проверяют не «в лоб по словарю», а точечно: сначала NLA и версии, потом аккуратные проверки.

## Шаг 7: практическая проверка VNC и RDP

Соберём процедуру проверки, чтобы было чем руководствоваться.

Для **VNC**:

1. Подключиться `nc 10.0.0.9 5900` — увидеть версию RFB.
2. Проверить, предлагает ли сервер метод `None` (вход без пароля).
3. Если нужен пароль — попробовать небольшой список дефолтов (не «миллион слов»).
4. Найти пароль в реестре, если есть локальный доступ.

Для **RDP**:

1. Сканером определить версию и наличие NLA.
2. Проверить известные CVE (`rdp-vuln-ms12-020`, а по BlueKeep — осторожно, без опасной эксплуатации).
3. Оценить, доступен ли порт из интернета.

Важное правило: **VNC-пароли и RDP-сессии — это доступ к рабочему столу**, то есть к данным и файлам. Даже «просто посмотреть экран» может быть нарушением границ, поэтому в пентесте это делают только в рамках согласованного объёма.

## Что мы теперь знаем

- VNC (RFB) приветствует строкой вида `RFB 003.008` и предлагает методы аутентификации.
- Метод `None` — вход без пароля; метод `2` — слабая DES-схема с лимитом 8 символов.
- Пароли VNC часто хранятся в реестре с фиксированным ключом.
- RDP использует NLA/CredSSP/TLS; без NLA он уязвимее.
- BlueKeep — pre-auth RCE в RDP, червеобразная.
- Защита — туннели, NLA, MFA, сегментация.
