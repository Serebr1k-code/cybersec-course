## Вопрос, с которого всё начинается

В дампе телеком-шлюза — трафик не на TCP и не на UDP, а на каком-то третьем протоколе, и внутри него «чанки». Что это и зачем понадобился ещё один транспорт?

Это **SCTP** — Stream Control Transmission Protocol, тема модуля [`network-module-transport-alt`](network-module-transport-alt). Разберём его.

## Наш пример: одна SCTP-ассоциация

```
INIT      src=5060 dst=5060 vtag=0x1a2b3c4d
INIT-ACK  cookie=...
DATA      chunk=0 stream=0 payload:...
```

Три пакета — установка ассоциации и передача данных. Разберём поля.

## Шаг 1: зачем SCTP, если есть TCP и UDP

TCP даёт поток байтов, UDP — датаграммы без гарантий. SCTP взял лучшее: **сообщения** (как у UDP, но с сохранением границ), надёжность и упорядочивание (как у TCP), плюс два новых свойства:

- **multihoming** — одна ассоциация может использовать несколько IP-адресов;
- **multi-streaming** — несколько независимых потоков внутри одной ассоциации (блокировка одного не блокирует другие).

Именно поэтому SCTP выбрали для сигнализации (SS7-over-IP).

## Шаг 2: общий заголовок

Каждый SCTP-пакет начинается с 12-байтового общего заголовка:

| Поле | Размер | Смысл |
|------|--------|-------|
| Src port | 2 | порт отправителя |
| Dst port | 2 | порт получателя |
| Verification Tag | 4 | защита от «слепых» пакетов |
| Checksum | 4 | CRC-32c |

**Verification Tag** — ключевое отличие: он уникален для ассоциации и меняется в зависимости от направления, поэтому подсунуть пакет вслепую сложно.

## Шаг 3: чанки

После общего заголовка идёт список **чанков**, каждый — TLV с полем type:

| Type | Чанк | Смысл |
|------|------|-------|
| 0 | DATA | данные пользователя |
| 1 | INIT | инициализация |
| 2 | INIT-ACK | ответ инициализации |
| 3 | SACK | подтверждение |
| 4 | HEARTBEAT | проверка живости пути |
| 6 | ABORT | аварийное закрытие |

Один пакет может нести несколько чанков, склеенных вместе, — это оптимизация.

## Шаг 4: рукопожатие с cookie

Установка ассоциации — **четырёхсторонняя**: `INIT → INIT-ACK (со state cookie) → COOKIE-ECHO → COOKIE-ACK`. Cookie защищает от SYN-флуда: сервер не хранит состояние до прихода COOKIE-ECHO. Это заметно надёжнее, чем у TCP.

## Шаг 5: SIGTRAN

Поверх SCTP работает **SIGTRAN** — перенос классической телефонной сигнализации (SS7) в IP. Два главных протокола: **M3UA** (адаптация MTP3) и **SUA** (адаптация SCCP). Поэтому SCTP-трафик на портах 2905/3097 — это часто телеком-сигнализация, и она представляет интерес для атакующего.

## Полный прогон: разбираем дамп

```
$ cat sctp.log
SCTP INIT     src=5060 dst=5060 vtag=0x1a2b3c4d
SCTP INIT-ACK cookie=0xdeadbeef
SCTP DATA     chunk=0 stream=0 payload:bnRvezVjdHBfY2h1bmtfZDR0NH0=
$ grep payload: sctp.log | cut -d: -f2 | base64 -d
nto{5ctp_chunk_d4t4}
```

Мы нашли DATA-чанк (в логе поле `payload:` в base64) и декодировали флаг. Запиши его в `answer.txt` и набери `check`.

## Что мы теперь знаем

- SCTP — транспорт с сообщениями, multihoming и multi-streaming.
- Общий заголовок: порты, Verification Tag, CRC-32c.
- Данные и служебные сообщения — в чанках (INIT/DATA/SACK/…).
- Рукопожатие 4-стороннее с cookie; поверх SCTP работает SIGTRAN (M3UA/SUA).

## Мультихоминг на практике: как выглядит смена пути

В дампе мультихоминг виден как разные пары адресов внутри одной ассоциации. Сторона объявляет список адресов в INIT, и трафик может идти по любому из них.

```
$ tshark -r sctp.pcap -nn -T fields -e ip.src -e ip.dst -e sctp.srcport -e sctp.chunk_type
10.0.0.5  10.0.0.9  2905  1
10.0.0.9  10.0.0.5  2905  2
10.0.0.5  10.0.0.9  2905  0
10.0.1.5  10.0.0.9  2905  0
```

Третий и четвёртый пакеты — одна ассоциация (порт 2905), но адрес источника сменился с `10.0.0.5` на `10.0.1.5`. Это признак мультихоминга: хост переключил путь. При этом verification tag не менялся — ассоциация та же.

Полезный приём мониторинга: если «один и тот же» поток внезапно меняет адрес, это либо легитимный мультихоминг, либо попытка перехвата. Отличить можно по tag: у легитимного он совпадает, у поддельного — нет.

## SIGTRAN: SS7 поверх SCTP

Телеком-сигнализация исторически шла по отдельным линиям SS7. Со временем её «завернули» в IP — так появился SIGTRAN. Транспортом выбрали SCTP: он даёт надёжность, контроль перегрузки и мультихоминг, критичные для сигнализации.

Над SCTP работают адаптационные слои:

- **M3UA** — переносит сообщения MTP-3 (маршрутизация) между узлами SS7 и шлюзами;
- **M2UA/M2PA** — работают на уровне MTP-2;
- **IUA** — переносит ISDN Q.921.

```
$ tshark -r sigtran.pcap -Y "m3ua" -T fields -e m3ua.message_class -e m3ua.si
Transfer  3
MGMT      3
```

`sctp.port` 2905 — типичный порт M3UA. Если ты видишь SCTP между двумя IP-адресами оператора, почти наверняка внутри M3UA, а дальше — SS7/MAP (тот самый, через который отслеживают местоположение абонента).

## Диагностика и инструменты

В Linux SCTP реализован модулем ядра `sctp` (проект lksctp). Проверить:

```
$ lsmod | grep sctp
$ sysctl net.sctp
$ ss --sctp
```

`ss --sctp` показывает ассоциации так же, как `ss -t` показывает TCP. Для генерации трафика есть утилита `sctp_darn` из lksctp-tools: она умеет поднимать сервер и клиент, что удобно для лаборатории.

В `tshark` диссектор SCTP включён по умолчанию; для прикладных протоколов иногда нужно указать порт: `-d sctp.port==2905,m3ua`.

## Типичные ошибки

Первая — путать SCTP с TCP и искать флаги SYN/ACK: у SCTP их нет, есть типы чанков. Вторая — игнорировать verification tag и считать, что пакет «подходит», только по портам. Третья — забыть, что в одном SCTP-пакете может быть несколько чанков разных типов. Четвёртая — считать мультихоминг экзотикой: в телекоме это норма.

## Шаг 6: фрагментация и потоки

В SCTP данные режутся на **фрагменты** (chunks), которые собираются в сообщения. Каждый DATA-чанк несёт номер потока (**stream id**) и порядковый номер (**SSN**) внутри потока. Благодаря этому потоки независимы: потеря в одном не блокирует остальные — в отличие от TCP, где head-of-line blocking тормозит всё соединение.

Фрагментация нужна, чтобы уложиться в MTU: большое сообщение разбивается на несколько чанков и собирается на приёмнике по флагам B/E (begin/end). Это ещё одна точка, где неаккуратный парсер может ошибиться.

## Шаг 7: атаки на SCTP и SIGTRAN

- **Verification Tag** усложняет «слепую» инъекцию, но если он известен (например, из дампа), можно подсунуть пакет;
- **multihoming** расширяет поверхность: ассоциация живёт на нескольких адресах, и блокировка одного не рвёт связь;
- **SIGTRAN (M3UA/SUA)** переносит SS7 — атаки на телефонную сигнализацию (перехват, подмена абонента) становятся сетевыми;
- **HEARTBEAT** используется для проверки пути; flood HEARTBEAT — простой вектор DoS.

Отдельная тема — **DSCP/порты 2905/3097**: их появление в неожиданной сети часто означает телеком-оборудование, которое стоит изучить отдельно.

## Разбор реального дампа: чанки и ассоциация

```
$ cat sctp.log
SCTP INIT     src=5060 dst=5060 vtag=0x1a2b3c4d
SCTP INIT-ACK cookie=0xdeadbeef
SCTP DATA     chunk=0 stream=0 payload:bnRvezVjdHBfY2h1bmtfZDR0NH0=
```

Сначала `INIT` (инициализация), затем `INIT-ACK` с cookie — сервер не хранит состояние до `COOKIE-ECHO`. Затем DATA-чанк потока 0. Поле `payload:` в логе — base64 с данными.

## Инструменты и защита

- `tshark -r dump.pcap -Y sctp -T fields -e sctp.chunk_type` — типы чанков;
- `sctp_test` / `lksctp-tools` — поднять ассоциацию;
- `ss -S` — SCTP-сокеты на хосте.

Защита: фильтровать SCTP на периметре, если он не нужен; для SIGTRAN — изолировать сигнальную сеть, применять IPsec/DTLS и мониторить аномальные INIT/ABORT. Для SOC — правило на неожиданный SCTP-трафик.

## SCTP против TCP: таблица сравнения

| Свойство | TCP | SCTP |
|----------|-----|------|
| Модель данных | поток байтов | сообщения |
| Установка | 3-way handshake | 4-way + cookie |
| Адреса | один | multihoming |
| Потоки | один | multi-streaming |
| Голова линии | блокирует всё | блокирует только поток |
| Транспорт | IP | IP (протокол 132) |

Из таблицы видно, зачем SCTP придумали: там, где нужны независимые потоки и устойчивость к отказу пути. Для телекома это критично, поэтому SS7 переехал на SCTP. Для атакующего это означает: сломать «одну ногу» multihoming недостаточно, а детект должен учитывать протокол 132.

## Практический чек-лист разбора SCTP

1. **Отдели SCTP.** `tshark -r dump.pcap -Y sctp` — это уже редкость сама по себе.
2. **Прочитай общий заголовок.** Порты, Verification Tag, checksum.
3. **Перечисли чанки.** `-T fields -e sctp.chunk_type`: INIT/INIT-ACK/DATA/SACK/HEARTBEAT/ABORT.
4. **Найди ассоциацию.** INIT + INIT-ACK с cookie = начало; DATA с потоком и SSN — данные.
5. **Проверь SIGTRAN.** Порты 2905/3097 и M3UA/SUA в полезной нагрузке — телеком-сигнализация.
6. **Оцени multihoming.** Несколько адресов в ассоциации — устойчивость к блокировке одного пути.

Результат: карта ассоциации и, при SIGTRAN, подтверждение телеком-трафика. Для защищающегося — необходимость фильтровать SCTP на периметре и изолировать сигнальную сеть; для пентеста — редкий, плохо логируемый транспорт.
