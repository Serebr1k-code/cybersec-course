## Вопрос, с которого всё начинается

Ты получил первый доступ к хосту `10.10.10.5` внутри сети. С него виден следующий сегмент `10.10.20.0/24`, но твоя машина туда не дотянется — прямого маршрута нет. Как просканировать и атаковать то, что видно только «оттуда»?

Ответ — туннель. Это способ **перенести один протокол внутри другого**, чтобы дотянуться до сети, куда нет прямого пути. Этот модуль — про то, как устроены туннели и оверлеи, чем они отличаются друг от друга и как выбрать подходящий. Он опирается на [`network-tunneling`](network-tunneling) и [`network-ssh-tunnel`](network-ssh-tunnel) и ведёт к [`network-socks-http-connect`](network-socks-http-connect) и [`network-gre-vxlan`](network-gre-vxlan).

## Наш пример: футхолд и невидимый сегмент

У нас есть SSH-доступ на `10.10.10.5` (назовём его **футхолд** — первый захваченный хост, с которого начинается движение вглубь). Проверяем, что видит он, а не мы:

```
$ ssh user@10.10.10.5 'ip route; nmap -sn 10.10.20.0/24'
default via 10.10.10.1 dev eth0
10.10.20.0/24 dev eth1 proto kernel scope link src 10.10.20.5
Nmap scan report for 10.10.20.7
Host is up (0.0012s latency).
```

Футхолд имеет второй интерфейс в `10.10.20.0/24` и видит хост `10.10.20.7`. Мы — нет. Дальше мы протащим к себе этот сегмент тремя способами и разберём, чем они отличаются.

## Шаг 1: прокси или туннель — в чём разница

Прежде чем строить, разберёмся с уровнем работы.

- **Прокси** работает на **прикладном уровне**: клиент сам шлёт запрос прокси («соедини меня с X:Y»), а прокси пересылает. Примеры: SOCKS, HTTP CONNECT.
- **Туннель** работает на **сетевом уровне**: пакеты заворачиваются целиком, приложение о туннеле не знает. Примеры: GRE, IPsec, VXLAN.

Практический вывод: прокси проще настроить, но о нём должно знать приложение; туннель прозрачнее — он несёт любой трафик, включая чужой.

## Шаг 2: SOCKS — «соедини меня с любым TCP»

**SOCKS** — прокси-протокол, работающий с любым TCP (а SOCKS5 — ещё и с UDP). SSH умеет поднимать такой прокси одной командой:

```
$ ssh -D 1080 -N -f user@10.10.10.5
$ curl --socks5 127.0.0.1:1080 http://10.10.20.7/
<!DOCTYPE html><title>Router admin</title>
```

`-D 1080` — локальный порт, на котором SSH открывает SOCKS5. `-N` — не запускать шелл (нужен только туннель). `-f` — уйти в фон. Теперь `curl --socks5` ходит в `10.10.20.0/24` через футхолд.

Чтобы этим пользовались обычные инструменты, их направляют через SOCKS утилитой `proxychains`:

```
$ proxychains4 -q nmap -sT -Pn -n -p 22,80,445 10.10.20.7
Nmap scan report for 10.10.20.7
22/tcp   open  ssh
80/tcp   open  http
445/tcp  closed
```

Важно: `-sT` (полное TCP-соединение) обязателен — сырые пакеты (`-sS`) через SOCKS не пойдут, потому что прокси умеет только «установи соединение».

## Шаг 3: HTTP CONNECT — туннель через разрешённый прокси

**HTTP CONNECT** — метод HTTP, превращающий прокси в TCP-релей. Клиент шлёт строку `CONNECT host:port`, прокси устанавливает соединение и дальше просто пропускает байты. Так как CONNECT разрешён на периметре (через него ходит HTTPS на 443), это удобный канал для обхода:

```
$ curl -x http://proxy:3128 -p https://internal.local/
$ printf 'CONNECT internal.local:443 HTTP/1.1\r\nHost: internal.local:443\r\n\r\n' | nc proxy 3128
HTTP/1.1 200 Connection established
```

Вторая команда показывает суть вручную: мы попросили прокси открыть соединение, он ответил `200 Connection established` — и дальше через это соединение пойдёт любой протокол.

## Шаг 4: GRE — инкапсуляция на сетевом уровне

**GRE** (Generic Routing Encapsulation, IP-протокол 47) заворачивает произвольный протокол в IP. Он **не шифрует и не аутентифицирует** — только инкапсулирует.

```
$ sudo ip tunnel add gre1 mode gre remote 192.0.2.1 local 10.0.0.2 ttl 64
$ sudo ip link set gre1 up
$ sudo ip addr add 172.16.0.1/30 dev gre1
```

После этого появляется интерфейс `gre1`, и по нему идёт трафик к `192.0.2.1`. GRE часто используют для site-to-site и как транспорт для других протоколов.

## Шаг 5: VXLAN — L2 поверх L3

**VXLAN** (Virtual Extensible LAN) строит виртуальную L2-сеть поверх L3: кадры Ethernet инкапсулируются в UDP (обычно порт 4789). Идентификатор сети — **VNI** (24 бита, до 16 млн сегментов), а точки инкапсуляции называются **VTEP**.

```
+--------+--------+-------+--------+------------------+
| IP hdr | UDP    | VXLAN | VNI    | Original Ethernet|
+--------+--------+-------+--------+------------------+
                     dst 4789
```

```
$ sudo ip link add vx0 type vxlan id 100 remote 192.0.2.1 dstport 4789 dev eth0
$ sudo ip link set vx0 up
$ sudo bridge fdb append 00:00:00:00:00:00 dev vx0 dst 192.0.2.1
```

Для защитника VXLAN — источник «невидимого» L2-трафика: ACL, настроенный по IP, его не разбирает.

## Что видно на проводе

| Технология | Инкапсуляция | Признак в дампе |
|---|---|---|
| SOCKS | TCP-релей | прикладной протокол внутри |
| HTTP CONNECT | TCP-релей | `CONNECT ...` в начале |
| GRE | proto 47 | внешний IP + GRE-заголовок |
| VXLAN | UDP/4789 | VNI + Ethernet внутри |
| IP-in-IP | proto 4 | двойной IP-заголовок |

```
$ sudo tcpdump -i eth0 -nn 'ip proto 47 or udp port 4789'
$ tshark -r cap.pcap -Y 'vxlan' -T fields -e vxlan.vni | sort -u
100
```

Так туннель и находят: по протоколу 47, по UDP/4789 или по строке `CONNECT` в начале потока.

## Что мы теперь знаем

- Туннель переносит один протокол внутри другого; прокси — на прикладном уровне, туннель — на сетевом.
- SOCKS через `ssh -D` — самый простой способ протащить TCP в недоступный сегмент.
- HTTP CONNECT превращает разрешённый прокси в TCP-релей.
- GRE (proto 47) и VXLAN (UDP/4789) — сетевые/канальные инкапсуляции, они **не шифруют**.
- Фильтры по IP не разбирают инкапсуляцию — поэтому туннель обходит сегментацию.

## Если защита мешает

- **SOCKS не проходит через принудительный прокси.** Тогда — HTTP CONNECT или `chisel` (туннель поверх HTTP).
- **Брандмауэр режет исходящие порты.** Прячь туннель в разрешённый канал: 443 (CONNECT), DNS, ICMP.
- **Сырые пакеты не идут.** Через прокси — только `-sT`; `-sS`/UDP не пройдут.
- **MTU.** Инкапсуляция уменьшает полезный размер; проверяй: `ping -M do -s 1400 <inner-host>`.

## Практика: полная цепочка pivoting

```
$ ssh -D 1080 -N -f user@10.10.10.5
$ proxychains4 -q nmap -sT -Pn -n -p 22,80,445,3389 10.10.20.0/24
$ ssh -D 1081 -N -f user@10.10.20.7
```

Два SOCKS-порта (`1080`, `1081`) соединяются в цепочку через `strict_chain` в конфиге proxychains — так доходят до сегмента за вторым футхолдом.
