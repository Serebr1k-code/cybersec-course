## Вопрос, с которого всё начинается

Ты — защитник. Каждую секунду через сеть идут тысячи пакетов, и где-то среди них сканирование, эксплойт или эксфильтрация. Смотреть вручную невозможно. Нужен инструмент, который сам сравнивает трафик с правилами и кричит, когда что-то похоже на атаку. Это и есть **IDS** — система обнаружения вторжений.

Классический IDS — **Suricata**. В этом уроке мы разберём, как пишутся её правила, что такое сигнатурный и поведенческий детект, и как атакующий эти правила обходит.

## Наш пример: скан в дампе scan.pcap

У нас есть дамп `scan.pcap`, где хост `10.0.0.9` за доли секунды стучится в пять портов `10.0.0.20`. Посмотрим на это глазами анализатора:

```
$ tshark -r scan.pcap -Y 'tcp.flags.syn==1 && tcp.flags.ack==0' -T fields -e ip.src -e tcp.dstport
10.0.0.9	22
10.0.0.9	80
10.0.0.9	443
10.0.0.9	3306
10.0.0.9	8080
```

Мы видим только SYN-пакеты (запрос на соединение) без завершения — типичный признак сканирования: атакующий проверяет, какие порты открыты, и не доводит соединения до конца. Suricata на машине нет, поэтому правило мы разберём синтаксически, а саму картину трафика показали реальным `tshark`.

## Шаг 1: как устроено правило Suricata

Правило — одна строка с тремя частями: **action** (что делать), **header** (какой трафик), **options** (условия и сообщение). Пример правила, которое ловит нашу активность:

```
alert tcp any any -> any any (msg:"Possible TCP SYN scan"; \
  flags:S; threshold:type both, track by_src, count 20, seconds 10; \
  sid:1000001; rev:1;)
```

Разберём по частям:

- `alert` — действие: записать предупреждение. Бывает ещё `drop` (в режиме IPS — заблокировать).
- `tcp any any -> any any` — заголовок: протокол, источник, порт, направление, назначение. Здесь «любой TCP откуда угодно куда угодно».
- `msg:"..."` — текст предупреждения.
- `flags:S` — искать пакеты с установленным флагом SYN.
- `threshold:type both, track by_src, count 20, seconds 10` — порог: если один источник (`by_src`) за 10 секунд сгенерирует 20 таких пакетов — сработать.
- `sid` и `rev` — уникальный номер правила и его версия.

Порог (`threshold`) и есть переход от «поймать один пакет» к «поймать поведение». Один SYN — норма; двадцать SYN к разным портам за десять секунд — скан.

## Шаг 2: сигнатурный против поведенческого

Правила бывают двух типов, и оба нужны:

- **Сигнатурный детект** — ищем известный признак: строку эксплойта, конкретный user-agent брутфорсера, байты известного CVE. Точно, но бесполезно против нового.
- **Поведенческий (anomaly) детект** — ищем отклонение от нормы: скан (много портов), beaconing (регулярность), большой объём ночью. Ловит новое, но даёт ложные срабатывания.

Suricata — прежде всего сигнатурный движок (с дополнительными возможностями для аномалий). Поведенческий слой часто строят поверх её логов в SIEM.

## Шаг 3: куда пишутся срабатывания

Когда правило срабатывает, Suricata пишет запись в `eve.json` — журнал событий в формате JSON (по строке на событие). Поля записи тревоги такие:

| Поле | Значение |
|------|----------|
| `timestamp` | когда сработало |
| `event_type` | тип события, для тревоги — `alert` |
| `src_ip`, `dest_ip` | адреса |
| `alert.signature` | текст `msg` из правила |
| `alert.signature_id` | `sid` правила |
| `alert.severity` | важность |
| `proto` | протокол |

Формат `eve.json` удобен тем, что его сразу грузят в Elastic/Kibana: тревоги становятся строчками в таблице, по которым строят дашборды и алерты.

## Шаг 4: обход детекта (взгляд атакующего)

Пентестеру важно понимать, как не попасть под правило. Основные приёмы:

- **Снизить скорость.** Медленный скан (`-T2` в nmap) не превышает порог «20 за 10 секунд» — правило молчит.
- **Сменить паттерн.** Сканировать не подряд, а по одному порту с паузами; использовать разные источники.
- **Шифровать и легитимизировать.** Атака внутри разрешённого HTTPS неотличима от обычного трафика без TLS-инспекции.
- **Размыть сигнатуру.** Разбить полезную нагрузку так, чтобы сигнатурная строка не встречалась целиком (для поведенческого детекта это не помогает).

Это гонка вооружений: обороняющиеся тюнят правила, атакующие снижают заметность. Задача пентеста — показать, что текущие правила пропускают.

## Шаг 5: Suricata и Zeek вместе

Suricata и Zeek часто путают, но роли у них разные, и в зрелом SOC работают обе:

- **Zeek** пишет богатые логи обо всём, что видел, — даже если атаки не было. Это «запись наблюдений».
- **Suricata** срабатывает только когда трафик совпал с правилом. Это «сигнал тревоги».

Проще говоря: Zeek отвечает на вопрос «что происходило в сети», Suricata — «было ли что-то опасное». Логи Zeek используют для расследования постфактум, алерты Suricata — для немедленной реакции. Многие ставят оба движка на один сенсор и читают их логи из одного SIEM.

## Шаг 6: тюнинг правил

Наивная установка IDS даёт лавину ложных срабатываний — правило «SYN-скан» будет срабатывать на каждый порт-сканер в сети, включая легитимный инвентаризационный. Тюнинг — обязательная часть работы. Основные приёмы:

- **Порог.** Подобрать `threshold` так, чтобы обычная активность не дотягивала, а атака — да.
- **Исключения.** Внести известные сканеры и мониторинговые системы в `pass`-список.
- **Домашняя сеть.** В `suricata.yaml` задать `HOME_NET` — тогда правила различают «внутрь» и «наружу».
- **Приоритеты.** Важные правила помечать высоким приоритетом, шумные — понижать, чтобы аналитик видел главное.
- **Обновление баз.** Сигнатуры устаревают за дни; нужен регулярный подтягивающий механизм.

Плохо тюненный IDS хуже отсутствия IDS: аналитик перестаёт реагировать на алерты. Хорошо тюненный — реально ловит.

## Что мы теперь знаем

По-простому:

1. IDS сравнивает трафик с правилами и предупреждает об атаках.
2. Правило Suricata = action + header + options; `msg`, `flags`, `threshold`, `sid`.
3. `threshold` превращает детект одного пакета в детект поведения (скан, брутфорс).
4. Сигнатурный детект точный, но не ловит новое; поведенческий — наоборот.
5. Срабатывания пишутся в `eve.json` и уезжают в SIEM.
6. Обход: снизить скорость, размыть сигнатуру, спрятаться в шифре.

## На что смотреть дальше

- **Проверь оба слоя.** Если есть только сигнатуры — поведенческие атаки пройдут мимо.
- **Следи за порогами.** Слишком строгие — лавина ложных; слишком мягкие — пропуск.
- **Помни про TLS.** Без инспекции содержимое зашифрованного трафика для IDS невидимо.

## Разбор срабатываний: fast.log и eve.json

`fast.log` — компактная строка на тревогу: время, 5-tuple и сигнатура. `eve.json` —
полный JSON. Быстрый триаж:

```bash
$ head -n 3 fast.log
03/01/2024-12:00:00 [**] [1:1000001:1] Possible TCP SYN scan [**] {TCP} 10.0.0.9:54321 -> 10.0.0.20:22
$ jq -r 'select(.event_type=="alert")|"\(.timestamp) \(.src_ip) \(.alert.signature)"' eve.json | sort | head
```

Классификация (`ET SCAN`, `Attempted Information Leak`) сразу подсказывает тип атаки, а
`Priority` помогает расставить алерты по важности.

## Правило под конкретную атаку (HTTP)

Сигнатурный детект удобно показать на HTTP: ищем строку эксплойта в URI:

```bash
alert http any any -> $HOME_NET any (msg:"Possible LFI attempt"; \
  flow:to_server,established; content:"/etc/passwd"; http_uri; \
  sid:1000010; rev:1;)
```

`flow:to_server,established` ограничивает правило установленными соединениями, а
`http_uri` — только URI, что резко снижает ложные срабатывания по сравнению с поиском по
всему пакету.

## Ограничения IDS

- **Шифрование.** Без TLS-инспекции содержимое HTTPS невидимо — детект только по
  метаданным (SNI, объём, регулярность).
- **Фрагментация и evasion.** Атакующий разбивает payload, чтобы сигнатура не совпала.
- **Производительность.** При перегрузке IDS может пропускать пакеты.
- **Ложные срабатывания.** Плохой тюнинг превращает IDS в генератор шума.

## Если не сработало

- Правило не срабатывает → проверьте `HOME_NET`/`EXTERNAL_NET` в `suricata.yaml`.
- Слишком много алертов → добавьте `threshold` или `flow` и исключите известные сканеры.
- Нужного события нет в `fast.log` → смотрите `eve.json` (там больше типов событий).
- Содержимое не видно → трафик зашифрован; нужна TLS-инспекция или метаданные.

## Zeek-логи: что смотреть

Zeek пишет отдельные логи по типам: `conn.log`, `http.log`, `dns.log`, `ssl.log`,
`notice.log`. Они нормализованы (TSV) и удобны для grep:

```bash
$ cat conn.log | zeek-cut id.orig_h id.resp_h id.resp_p proto | head
$ cat dns.log | zeek-cut query | sort | uniq -c | sort -rn | head
```

`zeek-cut` выбирает поля по имени — так из «сырых» логов получают таблицы для анализа
beaconing (регулярных соединений к C2).

## Проверка правил без живого трафика

Правило можно протестировать офлайн на дампе — удобно при тюнинге:

```bash
$ suricata -r scan.pcap -S local.rules -l ./logs
$ cat logs/fast.log
```

## Время в логах

Suricata и Zeek пишут время в UTC (для Suricata — epoch). Для сопоставления событий из
разных источников приводите всё к единому поясу, иначе цепочка «скан → вход → эксфильтрация»
разъедется на часы.
