## Вопрос, с которого всё начинается

В 4G SS7 заменили на **Diameter** — современный протокол сигнализации, работающий поверх TCP/SCTP. Он соединяет узлы ядра: MME спрашивает у HSS данные абонента, PCRF управляет политиками, OCS считает деньги. И, как SS7, он доверяет пирам.

Разберём Diameter на примере одного запроса.

## Наш пример: запрос к HSS

Вот упрощённый Diameter-обмен:

```
Diameter: Command Code=316 (Authentication-Information-Request)
  Application-Id: 16777251 (S6a)
  Session-Id: host.example;1;1
  Destination-Realm: epc.mnc001.mcc250.3gppnetwork.org
  User-Name: 250010000000001
  Visited-PLMN-Id: 25001
Diameter: Command Code=318 (Authentication-Information-Answer)
  Result-Code: 2001 (DIAMETER_SUCCESS)
  Authentication-Info: ... (RAND, AUTN, XRES)
```

Разберём поля — из них состоит любой Diameter-запрос.

## Шаг 1: база и приложения

Diameter состоит из **базового протокола** (общие заголовки, маршрутизация, session) и **приложений** — наборов команд для конкретной задачи:

| Application | Интерфейс | Назначение |
|---|---|---|
| S6a | MME ↔ HSS | данные абонента, аутентификация |
| Gx | PCEF ↔ PCRF | политики (QoS, правила) |
| Gy | PCEF ↔ OCS | онлайн-тарификация |
| Rx | AF ↔ PCRF | запросы приложений к политикам |
| S9 | PCRF ↔ PCRF | роуминг-политики |

В нашем дампе `Application-Id: 16777251 (S6a)` — значит, это диалог MME с HSS про аутентификацию. `Command Code=316` — Authentication-Information-Request.

## Шаг 2: AVP — единица данных

Каждое поле Diameter — это **AVP** (Attribute-Value Pair): код, флаги, длина, значение. Примеры: `User-Name`, `Destination-Realm`, `Visited-PLMN-Id`, `Result-Code`.

`Result-Code: 2001` означает успех (коды 2xxx — успешные, 3xxx — протокольные ошибки, 4xxx — транзиентные, 5xxx — постоянные). По `Result-Code` в дампе сразу видно, чем закончился запрос.

`Destination-Realm` — домен, куда адресован запрос, обычно в формате `epc.mncXXX.mccYYY.3gppnetwork.org`. По нему маршрутизируют между операторами.

## Шаг 3: relay-агенты и роуминг

Между операторами Diameter-запросы проходят через **relay-агенты** (иногда через сторонние компании-хабы). Relay смотрит на `Destination-Realm` и пересылает дальше.

Проблема: relay часто **не проверяет содержимое** — только адресацию. Значит, если оператор не фильтрует конкретные команды, атакующий через relay может:

- слать запросы «от имени» другой сети;
- выпытывать данные абонента;
- абьюзить тарификацию.

## Шаг 4: типовые атаки

- **Подмена ответа.** Встав в путь, ответить на запрос раньше HSS — тогда MME получит подставные ключи/данные.
- **Фрод.** Через Gy/Ro исказить учёт, чтобы не платить за трафик.
- **DoS.** Флуд запросами, чтобы HSS/MME исчерпали ресурсы.
- **Утечка.** Запросы, раскрывающие местоположение и IMSI абонента.

Многие атаки SS7 «портированы» в Diameter, потому что корень один — доверие между операторами.

## Шаг 5: инструменты и дампы

Для анализа используют tshark (dissector `diameter`) и специализированные фаззеры:

```
$ tshark -r dia.pcap -Y 'diameter.cmd.code == 316' -T fields     -e diameter.Session-Id -e diameter.User-Name -e diameter.Result-Code
host.example;1;1    250010000000001    2001
```

Эта команда вытаскивает из всех запросов аутентификации сессию, абонента и результат. Так быстро оценивают, сколько запросов шло и с каким исходом.

```
$ tshark -r dia.pcap -Y 'diameter.flags.request == 0' | head
```

Фильтр `request == 0` оставляет только ответы — удобно искать подозрительные/дублирующиеся.

## Шаг 6: защита

- **Типовая фильтрация** на Diameter Edge Agent (DEA): разрешить только нужные приложения и команды.
- **Проверка `Origin-Host`/`Origin-Realm`** — запрос должен прийти от ожидаемого узла.
- **Мониторинг аномалий**: необычные Application-Id, всплески запросов, ответы без запроса.
- **TLS/SCTP-безопасность** и строгий контроль хабов роуминга.

## Что мы теперь знаем

- Diameter = база + приложения (S6a, Gx, Gy, Rx, S9).
- Поля Diameter — это AVP; Result-Code 2xxx = успех.
- Relay-агенты маршрутизируют по realm и часто не фильтруют команды.
- Атаки: подмена ответа, фрод тарификации, DoS, утечка.
- Защита: фильтрация на DEA, проверка Origin, мониторинг.

## Шаг 7: справочник команд Diameter

Команды Diameter задаются числовым `Command Code`. Ниже — ключевые, которые чаще всего попадают в дампы:

| Command Code | Команда | Приложение | Смысл |
|---|---|---|---|
| 316/318 | Authentication-Information | S6a | получить векторы аутентификации |
| 317/319 | Update-Location | S6a | регистрация в HSS |
| 318 | Cancel-Location | S6a | снять регистрацию |
| 272/273 | Credit-Control | Gy/Ro | онлайн-тарификация |
| 258/258 | Gx CCR/CCA | Gx | политики QoS |
| 275/275 | Gx RAR/RAA | Gx | переприменение политик |
| 280/280 | Rx AAR/AAA | Rx | запрос от приложения |
| 8388622 | S6a-Notification | S6a | уведомление об изменении |

Зная коды, ты читаешь дамп без документации: `316` в сторону HSS — попытка получить ключи, `272` — попытка тарифицировать. Аномально частые `316` по одному абоненту могут быть brute-попыткой или сканированием.

## Шаг 8: разбор одной сессии целиком

Возьмём полную S6a-сессию и разберём её от начала до конца:

```
AIR:  Session-Id=host.example;1;1  Command=316  Destination-Realm=epc.mnc001.mcc250...
      User-Name=250010000000001  Visited-PLMN-Id=25001  Requested-EUTRAN-Auth-Info=1
AIA:  Result-Code=2001  Authentication-Info: RAND=..., AUTN=..., XRES=...
ULR:  Session-Id=...;2;1  Command=317  User-Name=...  RAT-Type=EUTRAN
ULA:  Result-Code=2001  Subscription-Data: ...
```

Это классическая цепочка: сначала MME получает векторы аутентификации (`AIR`/`AIA`), затем регистрирует абонента (`ULR`/`ULA`). Наблюдая такую пару, ты понимаешь, что абонент только что подключился.

Если видишь `ULR` без предшествующей `AIR` или с чужим `Origin-Realm` — это подозрительно: возможно, узел-самозванец.

## Шаг 9: Relay, Proxy и Redirect

В Diameter есть три роли посредников, и важно их различать:

- **Relay Agent** — маршрутизирует по realm, не изменяя содержимое.
- **Proxy Agent** — может изменять AVP (например, добавлять политику).
- **Redirect Agent** — не пересылает, а отвечает «иди туда» (Redirect-Indicator).

Опаснее всего Proxy: он способен модифицировать сообщения на лету. Если у оператора стоит чужой proxy-агент, доверять дампу нельзя — данные могли быть изменены по пути.

## Шаг 10: практический разбор — ищем фрод

Задача: проверить, не абьюзит ли кто-то тарификацию. Смотрим Credit-Control:

```
$ tshark -r dia.pcap -Y 'diameter.cmd.code == 272' -T fields \
    -e ip.src -e diameter.User-Name -e diameter.CC-Request-Type
10.0.0.77    250010000000001    1
10.0.0.77    250010000000001    1
...
```

Множество `CCR` с типом `1` (INITIAL) от одного узла без завершающих сессий — признак либо сбоя, либо попытки накрутить/обнулить счёт. Дополнительно смотрят `Multiple-Services-Credit-Control` и `Granted-Service-Unit`: расхождение запрошенного и выданного — красный флаг.

## Шаг 11: что писать в отчёте

Для Diameter-находки фиксируй: Application-Id и Command Code, `Origin-Host`/`Origin-Realm`, `Destination-Realm`, `Result-Code`, частоту и абонента. Рекомендации формулируй как правила на DEA: «запретить приложение X из внешних realm», «требовать проверку Origin-Host», «ограничить частоту запросов на абонента». Так отчёт закрывает и обнаружение, и защиту.

## Практика: разбор дампа шаг за шагом

Чтобы закрепить материал, пройди типовой сценарий целиком на своём стенде.

Сначала подготовь окружение: подними виртуальную сеть и запусти захват. Затем воспроизведи легитимный обмен, чтобы понять «как выглядит норма» — без этого аномалию не увидишь. Норма — это предсказуемая последовательность сообщений с ожидаемыми адресами и кодами результата.

Дальше внеси контролируемое отклонение: подделай один параметр (адрес инициатора, код операции или результат) и посмотри, как это отразится в дампе. Зафиксируй, по какому именно полю детектируется отклонение. Это ключевой навык: находить признак, а не просто «читать протокол».

Собери мини-отчёт из четырёх пунктов: что за сессия, кто инициатор, что аномального, какая рекомендация. Такой формат пригодится и в CTF (ответ на вопрос задачи), и в реальном пентесте (находка с доказательством).

## Типичные ошибки при анализе

Разберём, на чём чаще всего спотыкаются.

Первая ошибка — смотреть только на один пакет. Сигнализация контекстна: смысл сообщения определяется предыдущими и последующими. Всегда собирай всю сессию, а не отдельный кадр.

Вторая — путать стороны. У каждого запроса есть инициатор и ответчик; перепутав их, легко сделать неверный вывод о том, «кто атакует». Проверяй адреса и роли.

Третья — игнорировать коды результата. Успех, ошибка и отказ выглядят похоже, но означают разное. Всегда смотри код и только потом интерпретируй.

Четвёртая — верить дампу как истине. Если в пути стоит посредник, данные могли быть изменены. Отмечай, где снят дамп, и учитывай это в выводах.

## Ссылки на спецификации и дальнейшее чтение

Телеком-протоколы описаны в спецификациях 3GPP и ITU — это первоисточник, к которому стоит обращаться, когда дамп непонятен. Полезно знать, где что лежит.

Для SS7 и MAP: ITU-T Q.700-серия описывает MTP, Q.711-716 — SCCP, Q.771-775 — TCAP, а MAP определён в 3GPP TS 29.002. Для Diameter базовый протокол — RFC 6733, приложения S6a/Gx/Gy — в TS 29.272/29.212/32.299. Для GTP — TS 29.060 (GTPv1) и TS 29.274 (GTPv2-C), GTP-U — TS 29.281.

Для IMS базовый SIP — RFC 3261, а профиль для 3GPP — TS 24.229; SDP описан в RFC 4566. Для 5G ядро — TS 23.501 (архитектура), NAS — TS 24.501, SBI — TS 29.500-серия.

Практический приём: когда видишь незнакомое поле или код, ищи его имя в соответствующей спецификации. Регулярно это делать полезно, потому что dissector в Wireshark показывает ровно те имена, что и стандарт.

Наконец, для тренировки поднимай открытые стенды: srsRAN и OpenAirInterface для радио, free5GC и Open5GS для ядра, Kamailio для IMS/SIP. На них безопасно воспроизводится почти любая описанная здесь атака — и, что важнее, видна реакция сети на неё.
