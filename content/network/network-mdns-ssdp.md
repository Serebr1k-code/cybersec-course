## Вопрос, с которого всё начинается

Ты в новой сети и хочешь понять, что тут вообще есть: принтеры, камеры, телевизоры, NAS, роутер. Можно сканировать порты — долго и шумно. А можно просто **послушать**: многие устройства сами, добровольно и регулярно, рассказывают о себе всему сегменту. За это отвечают протоколы обнаружения — **mDNS** и **SSDP/UPnP**.

Удобно для пользователя. И очень удобно для атакующего: это готовая карта сети, а иногда — возможность **перепрограммировать роутер**. Разберём, как этим пользуются.

Этот урок опирается на [`network-basics`](network-basics) и [`network-mitm`](network-mitm).

## Наш пример: слушаем, кто что объявляет

Подключаемся и захватываем только discovery-трафик:

```
$ sudo tcpdump -i eth0 -nn -s0 'udp port 5353 or udp port 1900' -c 20
14:01:02.101 192.168.1.50.5353 > 224.0.0.251.5353: 0 [3q] PTR? _airplay._tcp.local.
14:01:02.203 192.168.1.1.1900 > 239.255.255.250.1900: NOTIFY * HTTP/1.1
14:01:02.310 192.168.1.77.5353 > 224.0.0.251.5353: 0 [1q] A? printer.local.
```

Мы видим две «семьи» запросов: mDNS на multicast `224.0.0.251:5353` и SSDP на `239.255.255.250:1900`. Разберём каждую.

## Шаг 1: mDNS — DNS без сервера

**mDNS** (multicast DNS) разрешает имена в домене `.local` **без центрального DNS**: устройства шлют multicast-запрос, а владелец имени отвечает. Используется в Bonjour (Apple), Avahi (Linux) и части Windows — для принтеров, AirPlay, Chromecast, файлообмена.

Важно: помимо имён, mDNS отдаёт **TXT-записи** с метаданными — модель, версию, иногда серийники. Это ценная разведка. Перечислим все сервисы:

```
$ avahi-browse -a -t -r
+ eth0 IPv4 Printer HP LaserJet _ipp._tcp    local
   hostname = [printer.local]
   address = [192.168.1.77]
   txt = ["ty=HP LaserJet M404" "usb_MDL=M404dn"]
```

Мы узнали имя, IP и точную модель принтера — без единого пакета сканирования.

## Шаг 2: SSDP — обнаружение UPnP-устройств

**SSDP** — часть стека UPnP. Устройства периодически рассылают `NOTIFY`, а клиенты шлют `M-SEARCH` и получают ответ с URL описания (`LOCATION`):

```
M-SEARCH * HTTP/1.1
HOST: 239.255.255.250:1900
MAN: "ssdp:discover"
MX: 1
ST: ssdp:all
```

По этому URL лежит XML с типом устройства, версией, списком сервисов и **controlURL** — адресом, по которому вызываются действия. Перечислим устройства:

```
$ upnpc -l
upnp://192.168.1.1:5000/rootDesc.xml
  ...
  Service: WANIPConnection
  ControlURL: /ctl/IPConn
```

Роутер `192.168.1.1` управляется через UPnP. Смотрим, какие пробросы портов уже есть:

```
$ upnpc -l | grep -A2 'Forwarding'
 0 TCP   3389->192.168.1.50:3389  'RDP'   ...
```

Ого: RDP внутренней машины уже проброшен наружу. Это не редкость на домашних и малых офисных роутерах.

## Шаг 3: атака — пробрасываем свой порт

Теперь самое опасное. Если UPnP включён и не защищён, **любой** в сегменте может открыть порт из интернета на свой хост. Проверим (только в своей лаборатории!):

```
$ upnpc -a 192.168.1.100 4444 4444 TCP
ExternalIPAddress = 203.0.113.7
AddPortMapping(4444, 4444, 192.168.1.100) : SUCCESS
```

Снаружи порт `4444` внешнего адреса теперь ведёт на внутренний `192.168.1.100`. Это критическая находка: заражённое устройство может открыть себе доступ извне, минуя NAT.

Другие действия через UPnP: `DeletePortMapping` (снять чужой проброс — DoS), `GetGenericPortMappingEntry` (перечислить все пробросы), `SetConnectionType` (сменить режим WAN).

## Шаг 4: SSRF к SSDP

Классика на веб-стендах: заставить **сервер** обратиться к `239.255.255.250:1900`. Если у веб-приложения есть SSRF (Server-Side Request Forgery — сервер делает запрос по указанному нами адресу), мы просим его отправить M-SEARCH и вернуть список внутренних устройств. Так из внешнего мира видят внутреннюю сеть.

Отдельно SSDP используют для **амплификации** в DDoS: ответ (описание устройства) в разы больше запроса, поэтому с подделанного адреса жертвы можно усилить поток.

## Шаг 5: mDNS-спуфинг

mDNS так же неаутентифицирован, как LLMNR/NBT-NS ([`network-netbios-llmnr`](network-netbios-llmnr)), и его можно отравить. Клиент ищет `printer.local` — атакующий отвечает «это я», и клиент идёт к нему. Сценарии: подмена принтера/файлового сервера (выманить данные), подмена сервера обновлений, отравление AirPlay/Chromecast, DoS через конфликт имён. Технически это тот же приём, что и в LLMNR: перехватить multicast-запрос и ответить первым — защита тоже общая (отключение протокола и сегментация).

## Шаг 6: защита

| Мера | Против чего |
|---|---|
| Отключить UPnP на роутерах | Port-mapping, rogue-устройства |
| Отключить mDNS/SSDP, где не нужны | Утечки активов |
| Сегментация IoT | Боковое перемещение |
| Фильтровать multicast на границе | Утечка наружу |
| Ограничить SSDP-ответы | Амплификация |
| Мониторинг аномальных M-SEARCH | SSRF и сканирование |

## Если не сработало

Устройства «молчат»? Проверь по порядку:

- **Окно слишком короткое.** Устройства объявляют о себе периодически, иногда раз в несколько минут — слушай дольше.
- **Только IPv6.** mDNS работает и по `ff02::fb`; IPv4-фильтр его не покажет.
- **Multicast-фильтрация.** В правильно сегментированной сети discovery может быть ограничен — тогда остаётся активный запрос `M-SEARCH`.
- **UPnP выключен.** Тогда port-mapping не пройдёт, но перечисление mDNS всё ещё может работать.

Сравни три родственных протокола, чтобы не путаться в фильтрах:

| Протокол | Порт | Multicast |
|---|---|---|
| mDNS | 5353/udp | `224.0.0.251`, `ff02::fb` |
| SSDP | 1900/udp | `239.255.255.250` |
| LLMNR | 5355/udp | `224.0.0.252` |

## Лаборатория: карта сети и её защита

1. Подними в изолированной сети Linux-машину с Avahi и роутер с UPnP (или OpenWrt с `miniupnpd`).
2. `avahi-browse -a -t -r` — собери mDNS-сервисы и их TXT-метаданные.
3. `upnpc -l` — перечисли пробросы и controlURL.
4. Создай проброс: `upnpc -a 192.168.1.100 4444 4444 TCP` — и проверь доступ снаружи.
5. Отключи UPnP (останови `miniupnpd`) и повтори — проброс не создастся.
6. Отключи Avahi (`systemctl disable --now avahi-daemon`) — mDNS-утечки прекратятся.

Так ты своими глазами увидишь, как безобидное «обнаружение» превращается в экспозицию и как её закрыть.

## Что мы теперь знаем

- mDNS (`224.0.0.251:5353`) и SSDP (`239.255.255.250:1900`) — протоколы обнаружения без аутентификации.
- mDNS отдаёт имена и TXT-метаданные; SSDP — XML-описание с controlURL.
- UPnP port-mapping позволяет открыть внутренний порт наружу без аутентификации.
- SSDP годится для SSRF и амплификации в DDoS.
- mDNS можно отравить так же, как LLMNR/NBT-NS.
- Защита — отключить UPnP и ненужный discovery, сегментировать IoT.
## Разбираем mDNS-ответ в дампе

Вернёмся к нашей «тихой» сети. mDNS — это DNS без сервера: запросы уходят на multicast `224.0.0.251:5353`, и любой, кто знает ответ, отвечает. Разберём ответ:

```
$ tshark -r mdns.pcap -Y "mdns.flags.response==1" -T fields -e mdns.name -e dns.a -e dns.txt -c 3
printer.local  _ipp._tcp.local  192.168.1.42
nas.local      _smb._tcp.local  192.168.1.50
```

Читается так: в сети есть принтер `192.168.1.42` и NAS `192.168.1.50`. Без единого скана портов мы уже знаем, какие устройства есть и какие сервисы они предоставляют. **TXT-записи** особенно ценны — в них часто лежит модель, версия прошивки и даже путь к веб-панели:

```
$ tshark -r mdns.pcap -Y "mdns.txt" -T fields -e mdns.txt
model=HP LaserJet 400; firmware=20211001; admin=/hp/device
```

Версия прошивки — прямой вход в поиск CVE.

## SSDP: как обнаруживают UPnP

SSDP работает на `239.255.255.250:1900` и имеет два типа сообщений:

| Сообщение | Кто шлёт | Смысл |
|---|---|---|
| M-SEARCH | клиент | «кто умеет UPnP?» (multicast) |
| NOTIFY | устройство | «я тут, вот моя страница описания» |
| HTTP 200 OK | устройство | ответ на M-SEARCH (unicast) |

Разница с mDNS: SSDP — это HTTP-подобный текст, и в ответе приходит ссылка на XML-описание устройства (`LOCATION`). По этой ссылке лежит список сервисов, включая **WANIPConnection** — тот самый, что управляет пробросом портов на роутере.

```
$ tshark -r ssdp.pcap -Y "http.request.method==M-SEARCH" -T fields -e http.request.uri -c 1
*  ST: ssdp:all  MX: 1
```

## Атака: пробрасываем порт на роутере через UPnP

Если на роутере включён UPnP без аутентификации, любой в локальной сети может попросить его открыть порт наружу. Это делают утилиты вроде `upnpc`:

```
$ upnpc -l
...
$ upnpc -a 192.168.1.100 22 2222 TCP
ExternalIPAddress = 203.0.113.77
```
Здесь мы просим роутер перебросить внешний порт `2222` на наш внутренний SSH `22`. Роутер послушно добавляет правило. Результат: внутренний сервис становится доступен из интернета — классический выход из изолированной сети и способ обойти NAT.

## SSRF к SSDP: когда приложение само открывает порт

Отдельный вектор — когда веб-приложение позволяет сделать запрос по URL, а внутри — SSDP. Отправь серверу запрос к `http://239.255.255.250:1900/` с телом M-SEARCH, и он сам обратится к роутеру. Так SSRF превращается в манипуляцию сетевой инфраструктурой, хотя атакующий «всего лишь» подставил URL.

## Разбор реального случая: утечка модели принтера

Представь, что нужно понять, что за принтер в сети. Пассивный mDNS отдаёт модель без всякого сканирования:

```
$ tshark -r office.pcap -Y "mdns.txt" -T fields -e mdns.txt | grep -i model
model=Brother HL-L2350DW; cmd=PRINT; admin=192.168.1.42/general/status.html
```

Теперь у нас есть модель, адрес админ-панели и сервис. Дальше — поиск известных уязвимостей под эту модель. Всё это — из кадра, который принтер сам разослал в сеть.

## Защита и границы

mDNS/SSDP нужны для «zero-config» — печати, медиа, NAS. Но в корпоративной сети их обычно **не должно быть**: это лишняя поверхность и утечка инвентаря. Меры: отключить UPnP на роутерах, заблокировать multicast `224.0.0.251`/`239.255.255.250` между VLAN, сегментировать IoT-устройства. Для детекта — мониторить, не появились ли в сети новые `NOTIFY`/`M-SEARCH` от неизвестных устройств.
