TCP — это соединение с состоянием. Каждая сторона ведёт счётчики sequence number (seq) и acknowledgement number (ack), и ядро отбрасывает сегмент, у которого seq вне окна приёма. Значит, чтобы вклиниться в чужую сессию, атакующему нужно не только видеть пакеты (MITM), но и **угадать или перехватить** актуальные номера. Понимание этого механизма — ключ и к атакам, и к защите.

## Модель соединения и номера

При установке соединения (three-way handshake) каждая сторона выбирает **начальный sequence number (ISN)**:

```
Client → Server : SYN      seq=c_isn
Server → Client : SYN/ACK  seq=s_isn, ack=c_isn+1
Client → Server : ACK      seq=c_isn+1, ack=s_isn+1
```

Дальше seq увеличивается на число байт данных (SYN и FIN тоже «съедают» по одному номеру). Сегмент принимается, если его seq попадает в окно приёма `[rcv_nxt, rcv_nxt + window)`. Именно это окно делает «слепую» инъекцию сложной: без знания текущего seq вставить данные почти невозможно.

| Поле | Роль |
|---|---|
| seq | Номер первого байта данных сегмента |
| ack | Номер следующего ожидаемого байта от собеседника |
| window | Размер окна приёма |
| flags | SYN, ACK, RST, FIN, PSH, URG |

## Виды хайджекинга

- **On-path (MITM) hijacking** — атакующий видит трафик, знает актуальные seq/ack и может вставлять/менять данные. Самый надёжный вариант, но требует позиции в канале (ARP-спуфинг, evil twin, скомпрометированный шлюз).
- **Blind hijacking** — трафик не виден; нужно угадать ISN и текущий seq. Реально только при слабой рандомизации ISN (историческая атака Mitnick на TCP-хайджекинг 1994 года).
- **RST/FIN injection** — вместо вставки данных атакующий рвёт соединение, подобрав seq для RST. Классика для сброса BGP-сессий и «great firewall»-подобных сценариев.
- **Desynchronization** — атакующий рассинхронизирует стороны (например, инъекцией), после чего вклинивается в поток.

## Инструменты и команды

- **Scapy** — ручная сборка сегментов (основной инструмент для CTF и лаб).
- **hping3** — генерация пакетов с произвольными seq/ack/flags.
- **ettercap / bettercap** — on-path перехват и инъекция в GUI/CLI.
- **tcpdump / tshark** — снятие актуальных seq для on-path атаки.
- **nmap** — `--ip-options`, спуфинг, проверка фильтрации.

Снять актуальные номера из живого канала (при MITM):

```bash
sudo tcpdump -i eth0 -nn -S -c 20 'tcp port 23'
# -S показывает абсолютные seq, а не относительные
```

Blind-инъекция через Scapy (нужны правильные seq/ack):

```python
from scapy.all import *
sport, dport = 40000, 23
sport_r, dport_r = dport, sport
ip = IP(src="10.0.0.5", dst="10.0.0.9")
# клиент→сервер: свой seq, ack = ожидаемый байт сервера
seg = TCP(sport=sport, dport=dport, flags="PA", seq=SEQ, ack=ACK) / b"id\r\n"
send(ip/seg, verbose=0)
```

RST-сброс: отправляем сегмент с флагом RST и правдоподобным seq — ядро принимает RST, если seq попадает в окно.

## Разобранный пример: инъекция в Telnet-сессию в лабе

1. Поднимаем «жертву» (telnet-сервер) и «клиента» в одной сети; атакующий — в середине через ARP-спуфинг (см. `network-arp-deep`).
2. Включаем перехват:
   ```bash
   sudo arpspoof -i eth0 -t 10.0.0.9 -r 10.0.0.5   # клиент<->сервер
   sudo tcpdump -i eth0 -nn -S 'tcp port 23' -w mitm.pcap
   ```
3. Из дампа достаём последние seq/ack. В Wireshark: `tcp.flags.push==1` и смотрим `tcp.seq`/`tcp.ack`.
4. Инъектируем команду от имени клиента (spoofed source IP клиента), попадая в окно приёма:
   ```python
   send(IP(src="10.0.0.9",dst="10.0.0.5")/TCP(sport=43210,dport=23,flags="PA",seq=CUR_SEQ,ack=CUR_ACK)/b"cat /flag\r\n")
   ```
5. Сервер выполняет команду и отвечает — но ответ уходит настоящему клиенту. Чтобы прочитать ответ, атакующий должен уметь читать трафик (on-path) или применить full-duplex MITM.

## Защита и как её проверяют

| Защита | Что ломает |
|---|---|
| Рандомизация ISN (RFC 6528) | Blind-хайджекинг |
| Шифрование (TLS/SSH) | Инъекция осмысленных данных |
| TCP-MD5 / TCP-AO (BGP, LDP) | RST-инъекция в сессию маршрутизации |
| Строгий `rp_filter` (anti-spoofing) | Спуфинг source IP |
| Сегментация и DAI (Dynamic ARP Inspection) | ARP-спуфинг, on-path позиция |
| Port security / 802.1X | Подключение в середину |

Проверка в пентесте: убедиться, что ОС рандомизирует ISN (nmap `-O` и анализ SYN/ACK в tcpdump), что на коммутаторах включены DAI/port-security, что критичные протоколы (BGP) защищены MD5/AO.

## Частые ошибки и подводные камни

- **Забывать про offload (GSO/TSO).** При захвате на своей машине ядро показывает «свои» seq, а не сетевые — для честного перехвата используйте внешний снифер или отключите offload.
- **Не учитывать relative vs absolute seq.** `tcpdump` без `-S` показывает относительные номера; для инъекции нужны абсолютные.
- **Игнорировать окно приёма.** Даже верный seq вне окна будет отброшен — окно может быть маленьким (zero-window) при перегрузке.
- **Пытаться blind-инъекцию в современные ОС.** Рандомизация ISN делает её нереалистичной; в CTF blind-задачи почти всегда дают подсказку/утечку seq.
- **Путать хайджекинг и спуфинг.** Спуфинг — подмена адреса; хайджекинг — захват существующей сессии с корректными номерами.

## Что дальше / решение

Разберитесь, как связаны хайджекинг и **ARP-спуфинг** (`network-arp-deep`) — это путь к on-path позиции. Дальше логично изучить **NTLM relay** (`network-ntlm-relay`) и **TLS-атаки** (`network-tls-attacks`): в современном мире именно relay и downgrade заменяют «голый» TCP-хайджекинг. Для защиты от RST-инъекции в маршрутизацию используйте TCP-MD5/AO и фильтрацию TTL. Для CTF потренируйтесь писать scapy-скрипт, который по PCAP находит последний seq/ack и инъектирует команду — это типовое задание.

## RST-флуд и сброс соединений

Отдельный сценарий — не вставка данных, а **принудительный разрыв** соединений подбором seq. Если атакующий видит сессию (on-path) или угадывает seq, он шлёт RST-сегмент от имени одной из сторон. Ядро, получив RST с seq в окне приёма, немедленно закрывает соединение. Массово это применяют для:

- сброса длинных сессий (SSH, RDP, VPN) в «captive portal»-сценариях;
- срыва установки TLS-соединений;
- атаки на BGP (если нет TCP-MD5/AO);
- DoS на балансировщиках и прокси.

Детект RST-флуда: аномально много сегментов с флагом RST и без предшествующего FIN, часто со спуфированными source IP. В tshark:

```bash
tshark -r cap.pcap -Y "tcp.flags.reset==1" -T fields -e ip.src -e tcp.dstport | sort | uniq -c | sort -rn | head
```

Смягчение — `rp_filter`/uRPF (отбрасывает спуфинг), ограничение скорости RST на границе, шифрование и сегментация.

## Практическая лаборатория: полный цикл

1. **Стенд:** три контейнера в одной L2-сети (клиент 10.0.0.9, сервер 10.0.0.5, атакующий 10.0.0.66). На сервере — telnetd или nc-обёртка, которая по команде печатает флаг.
2. **Позиция:** `sudo arpspoof -i eth0 -t 10.0.0.9 -r 10.0.0.5` (атакующий в середине), `sysctl -w net.ipv4.ip_forward=1`.
3. **Сбор:** `tcpdump -i eth0 -nn -S -w mitm.pcap 'tcp port 23'`.
4. **Анализ:** в tshark вытащить последний обмен: `tshark -r mitm.pcap -Y "tcp.len>0" -T fields -e ip.src -e tcp.seq -e tcp.ack -e tcp.len | tail -5`.
5. **Инъекция:** scapy-скрипт берёт последний `seq`/`ack` от клиента, прибавляет `len` и шлёт сегмент с флагом PA от spoofed IP клиента. Если окно позволяет — сервер исполнит команду.
6. **Чтение ответа:** для full-duplex нужен форвардинг с одновременным сниффом — атакующий читает ответ сервера из канала, а не ждёт его у себя.
7. **Защита:** включите DAI/port-security, убедитесь, что telnet заменён на SSH, и повторите — инъекция осмысленных данных без знания ключа становится невозможной.

Такой цикл — типовое задание на курсах по сетевой безопасности и хороший полигон для понимания seq/ack.

## Где пригодится

- **CTF:** задачи на перехват/модификацию сессии, «вклинись и получи флаг».
- **Пентест:** демонстрация риска при отсутствии сегментации и шифрования в ЛВС.
- **Работа/SOC:** детект RST-флуда и аномальных seq как признаков атаки.
- **Сертификации:** OSCP/OSWE — понимание сетевого уровня для web-эксплуатации.
