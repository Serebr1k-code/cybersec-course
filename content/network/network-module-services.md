## Вопрос, с которого всё начинается

Ты просканировал хост и увидел открытые порты. Но порт — это только номер. За ним стоит **сервис**: программа, которая слушает этот порт, отвечает по своему протоколу и имеет свою версию, свою аутентификацию и свои слабости. Один открытый порт сам по себе ничего не говорит, пока ты не понял, что за ним.

Этот модуль — про путь «порт → сервис → слабость» для классических сервисов (FTP, Telnet, VNC, RDP) и IoT-протоколов (MQTT, CoAP, AMQP). Он опирается на [`network-service-enum`](network-service-enum) и ведёт к [`network-ftp-tftp`](network-ftp-tftp), [`network-telnet-rservices`](network-telnet-rservices), [`network-vnc-rdp`](network-vnc-rdp) и [`network-iot-messaging`](network-iot-messaging).

## Наш пример: один хост, пять сервисов

Берём лабораторный хост `10.0.0.1` и смотрим, что на нём открыто:

```
$ nmap -sV -p 21,23,3389,5900,1883 10.0.0.1
PORT     STATE SERVICE        VERSION
21/tcp   open  ftp            vsftpd 3.0.3
23/tcp   open  telnet         Linux telnetd
3389/tcp open  ms-wbt-server  Microsoft Terminal Services
5900/tcp open  vnc            RealVNC 5.3.2
1883/tcp open  mqtt           Mosquitto 2.0.11
```

Флаг `-sV` заставляет nmap не просто сказать «порт открыт», а **отправить сервису несколько пробных запросов и определить, что это за программа и какой версии**. Строка `21/tcp open ftp vsftpd 3.0.3` читается так: порт 21 открыт, там FTP, реализация — vsftpd версии 3.0.3.

Дальше мы пройдём по каждому сервису и зададим три вопроса: **есть ли аутентификация**, **есть ли шифрование**, **есть ли известные уязвимости**.

## Шаг 1: FTP — есть ли анонимный вход

**FTP** (File Transfer Protocol, порт 21) — старый протокол передачи файлов. У него есть режим **анонимного доступа**: логин `anonymous`, пароль — любой. Это часто оставляют «для удобства», и это первое, что проверяют.

У nmap есть готовые скрипты (**NSE** — Nmap Scripting Engine, набор проверок на Lua):

```
$ nmap -p 21 --script ftp-anon 10.0.0.1
PORT   STATE SERVICE
21/tcp open  ftp
| ftp-anon: Anonymous FTP login allowed (FTP code 230)
|_drwxr-xr-x   2 ftp      ftp          4096 backup
```

`ftp-anon` подтвердил: анонимный вход разрешён, и видна директория `backup`. Если бы сервис ещё и разрешал запись, это был бы прямой путь к подмене файлов.

## Шаг 2: Telnet — данные идут открытым текстом

**Telnet** (порт 23) — удалённый доступ, как SSH, но **без шифрования**. Логин, пароль и все команды идут по сети в открытом виде. Достаточно послушать трафик:

```
$ sudo tcpdump -i eth0 -A -nn 'tcp port 23' -c 8
23:14:02 IP 10.0.0.5.41288 > 10.0.0.1.23: Flags [P.], length 12
E..<.@.@..............l.....
..login: admin
..Password: hunter2
```

Здесь видно и логин `admin`, и пароль `hunter2`. Поэтому Telnet в проде — красный флаг сам по себе, независимо от версии.

## Шаг 3: VNC — пароль на 8 символов

**VNC** (Virtual Network Computing, порты 5900+) — удалённый рабочий стол по протоколу RFB. Пароль в старых версиях обрезается до **8 символов** и часто бывает пустым.

```
$ nmap -p 5900 --script vnc-info 10.0.0.1
PORT     STATE SERVICE
5900/tcp open  vnc
| vnc-info:
|   Protocol version: 3.8
|   Security types:
|_    VNC Authentication (2)
```

`VNC Authentication` означает вход по паролю (не «без пароля»), но версия 3.8 — старая. Если бы в списке был тип `None`, доступ был бы вообще без пароля.

## Шаг 4: RDP — NLA и CVE

**RDP** (Remote Desktop Protocol, порт 3389) — «рабочий стол» Windows. У него есть режим **NLA** (Network Level Authentication): сервер требует аутентификацию до создания сессии. Если NLA выключен, атакующему доступна страница входа, а старые версии уязвимы к **BlueKeep** (CVE-2019-0708) — удалённое выполнение кода без аутентификации.

```
$ nmap -p 3389 --script rdp-enum-encryption,rdp-ntlm-info 10.0.0.1
PORT     STATE SERVICE
3389/tcp open  ms-wbt-server
| rdp-enum-encryption:
|   Security layer
|     CredSSP (NLA): SUCCESS
|     RDP: SUCCESS
|_  CredSSP (NLA) with TLS 1.0/1.1/1.2
| rdp-ntlm-info:
|   Target_Name: CORP
|_  NetBIOS_Domain_Name: CORP
```

NLA включён (`SUCCESS`) — значит, слепая эксплуатация BlueKeep не пройдёт, но перебор учётных данных остаётся.

## Шаг 5: MQTT — брокер без пароля

**MQTT** (Message Queuing Telemetry Transport, порт 1883) — лёгкий протокол обмена сообщениями для IoT по модели **pub/sub** (публикация/подписка). Устройства публикуют данные в **топики** (иерархические адреса вида `home/kitchen/temp`), а брокер рассылает их подписчикам. Если брокер без аутентификации — любой может читать и публиковать.

```
$ mosquitto_sub -h 10.0.0.1 -t '#' -v
home/kitchen/temp 21.5
home/door/lock locked
factory/plc1/cmd open_valve
```

Подписка `-t '#'` означает «все топики». Здесь видно телеметрию и, что важнее, команду `factory/plc1/cmd`. Открытый брокер = контроль над обменом IoT.

## Шаг 6: UDP-сервисы, которые легко пропустить

TCP-скан не покажет сервисы на UDP. А там — целый пласт:

- **TFTP** (порт 69/udp) — передача файлов **вообще без аутентификации**; удобно для загрузки конфигов, но и для их подмены.
- **CoAP** (порт 5683/udp) — REST-подобный протокол для датчиков; часто без DTLS, а ресурсы бывают записываемыми.
- **AMQP** (порт 5672) — очереди сообщений; классика — дефолтные `guest/guest`.

```
$ nmap -sU -p 69,5683 10.0.0.1
PORT     STATE SERVICE
69/udp   open  tftp
5683/udp open  coap
```

Проверять UDP нужно отдельно: `-sU` медленнее, поэтому его гоняют по конкретным портам, а не по всему диапазону.

## Что мы теперь знаем

- За каждым портом стоит конкретный сервис с версией — их находит `nmap -sV`.
- Для каждого сервиса проверяют три вопроса: аутентификация, шифрование, известные CVE.
- FTP/TFTP могут пускать анонимно; Telnet/r-services не шифруют; VNC часто слабый; RDP опасен без NLA; MQTT без пароля — полный контроль.
- Готовые проверки дают NSE-скрипты (`ftp-anon`, `vnc-info`, `rdp-enum-encryption`).
- UDP-сервисы (TFTP, CoAP) не видны в TCP-скане — их проверяют отдельно.

| Сервис | Порт | Шифрование | Типовая слабость |
|---|---|---|---|
| FTP | 21 | нет | анонимный вход, запись |
| TFTP | 69/udp | нет | нет аутентификации |
| Telnet | 23 | нет | перехват паролей |
| VNC | 5900+ | слабое | пароль ≤8, без пароля |
| RDP | 3389 | TLS/NLA | перебор, BlueKeep |
| MQTT | 1883 | опц. TLS | открытый брокер |
| CoAP | 5683/udp | опц. DTLS | запись ресурсов |

## Если защита мешает

Наивный скан «в лоб» видит не всё. Что делать:

- **Баннер врёт.** Версия подделывается тривиально (`220 (vsFTPd 3.0.3)` может отдавать что угодно). Проверяй поведение, а не только строку версии.
- **NSE-скрипты блокируются.** Если сервис рвёт соединения от nmap, шли ручной баннер: `printf '\r\n' | nc -nv 10.0.0.1 21`.
- **Порт закрыт, но сервис жив.** Сервис может слушать нестандартный порт — сверяйся с полным `-p-` сканом.
- **TLS поверх сервиса.** Если MQTT/CoAP на TLS/DTLS, содержимое не видно — тогда работают по метаданным и по слабостям аутентификации.

## Практика: конвейер энумерации

Полный цикл от портов до проверок:

```
$ nmap -sV -sC -p- 10.0.0.1 -oA scan
$ grep -oE '^[0-9]+/tcp' scan.nmap | cut -d/ -f1 > ports.txt
$ nmap -p $(paste -sd, ports.txt) --script 'default,safe' 10.0.0.1
```

Первый скан находит открытые порты и версии, второй прогоняет безопасные NSE-скрипты уже по найденным портам. `-oA scan` сохраняет результат в трёх форматах — удобно для последующего разбора.
