## Вопрос, с которого всё начинается

Когда абонент выходит в интернет, его пакеты должны дойти от базовой станции до шлюза и дальше. В сотовых сетях для этого используют **GTP** (GPRS Tunnelling Protocol): пакет заворачивают в туннель и везут по инфраструктуре оператора.

GTP — это не сигнализация про абонента, а «дорога» для данных. И у неё свои уязвимости.

## Наш пример: пакет в туннеле

Возьмём пакет, снятый на интерфейсе N3/Gn:

```
Outer IP:  10.0.0.1 -> 10.0.0.9   UDP 2152 (GTP-U)
GTP-U:  flags=0x30  msgType=255 (G-PDU)  length=...  TEID=0x0a1b2c3d
Inner IP:  10.45.0.7 -> 8.8.8.8    ICMP echo request
```

Разберём: снаружи — обычный UDP-пакет на порт 2152, внутри — пакет абонента. Между ними — заголовок GTP-U с полем **TEID**.

## Шаг 1: два протокола — C и U

- **GTP-C** (control) — управление сессиями: создать/изменить/удалить туннель. Ходит на порт **2123**.
- **GTP-U** (user) — перенос пользовательских данных. Ходит на порт **2152** (и 2153 для IPv6).

`TEID` (Tunnel Endpoint Identifier) — числовой идентификатор туннеля. Один конец туннеля помечает пакеты своим TEID, другой — своим. В нашем дампе `TEID=0x0a1b2c3d`.

## Шаг 2: как создаётся туннель

Туннель создаётся через GTP-C:

```
GTP-C: Create Session Request   imsi=250010000000001  msisdn=79991234567
       f-TEID=0x0a1b2c3d  apn=internet  ratType=EUTRAN
GTP-C: Create Session Response  cause=16 (Request accepted)
       f-TEID=0x11223344  ip=10.45.0.7
```

SGSN/MME просит создать сессию, PGW/UPF отвечает и выдаёт абоненту IP. Оба узла обмениваются TEID — «ключами» своих концов туннеля.

## Шаг 3: атака — спуфинг и инъекция

Если GTP-U не защищён, атакующий, зная TEID, может:

1. **Инъектировать** свои пакеты в чужой туннель — абонент получит поддельные данные.
2. **Спуфить TEID** и направить чужой трафик себе.
3. **Подделать GTP-C** и создать/удалить туннель (отказ в обслуживании).

Классический сценарий: находясь в той же сети, что и операторский транспорт, сканируют UDP/2152, собирают валидные TEID и вбрасывают трафик.

## Шаг 4: инструменты

Для аудита GTP есть открытые утилиты:

```
$ gtp-scan -i eth0 -p 2152 -r 10.0.0.0/24
[+] GTP-U response from 10.0.0.9  TEID=0x11223344
```

`gtp-scan` ищет узлы, отвечающие на GTP, и собирает TEID. Для GTP-C есть `gtp_scan`/собственные скрипты на Scapy:

```
>>> from scapy.contrib.gtp import GTPHeader
>>> p = IP(dst='10.0.0.9')/UDP(dport=2152)/GTPHeader(gtp_type=255, teid=0x11223344)/IP(dst='8.8.8.8')/ICMP()
>>> send(p)
```

Это прямая инъекция пакета в туннель с заданным TEID — ядро атаки.

## Шаг 5: GTP в 5G

В 5G GTP-U остался — на интерфейсе **N3** между gNB и UPF. GTP-C частично заменён на PFCP (интерфейс N4), но идея туннеля та же. Значит, векторы (спуфинг, инъекция) переносятся, меняется лишь управление.

## Шаг 6: защита

- **Изоляция транспортной сети** от недоверенных сегментов.
- **Фильтрация UDP/2123 и 2152** на границах.
- **Проверка TEID и адресов** (ingress filtering) на шлюзах.
- **IPsec** на интерфейсах S1-U/N3 там, где это возможно.
- **Мониторинг**: пакеты с неизвестными TEID, всплески GTP-C.

## Что мы теперь знаем

- GTP-C (2123) управляет сессиями, GTP-U (2152) несёт данные.
- TEID — идентификатор туннеля, ключ к инъекции.
- Атаки: спуфинг TEID, инъекция в туннель, подделка GTP-C.
- В 5G GTP-U живёт на N3, управление частично ушло в PFCP.
- Защита: изоляция, фильтрация портов, проверка TEID, IPsec.

## Шаг 7: справочник типов сообщений GTP

Для быстрого чтения дампа полезно знать основные типы сообщений:

| Протокол | Msg Type | Название | Смысл |
|---|---|---|---|
| GTP-C | 32 | Create Session Request | создать сессию |
| GTP-C | 33 | Create Session Response | ответ |
| GTP-C | 34 | Modify Bearer Request | изменить |
| GTP-C | 36 | Delete Session Request | удалить |
| GTP-C | 26 | Delete PDN Connection | разорвать |
| GTP-C | 1 | Echo Request | проверка живости |
| GTP-U | 255 | G-PDU | пользовательский пакет |
| GTP-U | 1 | Echo Request | проверка туннеля |
| GTP-U | 254 | End Marker | завершение потока |

`Echo Request` (тип 1) — самый безобидный способ найти GTP-узел: он отвечает, подтверждая, что порт открыт. С него начинается разведка.

## Шаг 8: разбор полного туннеля

Проследим жизненный цикл туннеля абонента:

```
1. GTP-C Create Session Request  imsi=25001...  f-TEID=0x0a1b2c3d
2. GTP-C Create Session Response cause=16  f-TEID=0x11223344
3. GTP-U G-PDU  TEID=0x11223344  inner: 10.45.0.7 -> 8.8.8.8  (запрос)
4. GTP-U G-PDU  TEID=0x11223344  inner: 8.8.8.8 -> 10.45.0.7  (ответ)
5. GTP-C Delete Session Request  teid=0x0a1b2c3d
6. GTP-C Delete Session Response cause=16
```

Здесь видно всё: создание, обмен данными, удаление. Для атаки важен шаг 3–4: зная `TEID=0x11223344` и адреса, можно вбросить свой пакет в поток.

## Шаг 9: DoS через GTP

GTP-C — протокол без аутентификации в базовой версии. Это открывает отказ в обслуживании:

1. **Флуд Create Session** — узел исчерпает таблицу сессий.
2. **Фальшивые Delete** — разрыв чужих сессий (абонент «теряет интернет»).
3. **Echo-флуд** — исчерпание ресурсов на обработке служебных сообщений.

Защита строится на rate-limit и проверке источника: GTP-C должен приниматься только от доверенных узлов, а не из произвольной сети.

## Шаг 10: практический разбор — поиск активных туннелей

Задача: понять, какие абоненты сейчас онлайн. Смотрим GTP-U:

```
$ tshark -r gtp.pcap -Y 'gtp.message == 255' -T fields \
    -e ip.src -e gtp.teid -e ip.dst
10.0.0.9    0x11223344    10.0.0.1
10.0.0.9    0x55667788    10.0.0.1
```

Каждый уникальный `TEID` — активный туннель. По `ip.src` видно шлюз, а по числу TEID — сколько сессий он обслуживает. Резкий рост числа TEID за короткое время — признак массового подключения или флуда.

## Шаг 11: что писать в отчёте

Для GTP-находки фиксируй: тип сообщения, TEID, адреса сторон, абонента (если виден) и результат (`cause`). Рекомендации: «фильтровать UDP/2123 и 2152 на периметре», «проверять источник GTP-C», «включить rate-limit и мониторинг неизвестных TEID». Отдельно отметь, если транспорт оператора достижим из недоверенной сети — это корень проблемы.

## Практика: разбор дампа шаг за шагом

Чтобы закрепить материал, пройди типовой сценарий целиком на своём стенде.

Сначала подготовь окружение: подними виртуальную сеть и запусти захват. Затем воспроизведи легитимный обмен, чтобы понять «как выглядит норма» — без этого аномалию не увидишь. Норма — это предсказуемая последовательность сообщений с ожидаемыми адресами и кодами результата.

Дальше внеси контролируемое отклонение: подделай один параметр (адрес инициатора, код операции или результат) и посмотри, как это отразится в дампе. Зафиксируй, по какому именно полю детектируется отклонение. Это ключевой навык: находить признак, а не просто «читать протокол».

Собери мини-отчёт из четырёх пунктов: что за сессия, кто инициатор, что аномального, какая рекомендация. Такой формат пригодится и в CTF (ответ на вопрос задачи), и в реальном пентесте (находка с доказательством).

## Типичные ошибки при анализе

Разберём, на чём чаще всего спотыкаются.

Первая ошибка — смотреть только на один пакет. Сигнализация контекстна: смысл сообщения определяется предыдущими и последующими. Всегда собирай всю сессию, а не отдельный кадр.

Вторая — путать стороны. У каждого запроса есть инициатор и ответчик; перепутав их, легко сделать неверный вывод о том, «кто атакует». Проверяй адреса и роли.

Третья — игнорировать коды результата. Успех, ошибка и отказ выглядят похоже, но означают разное. Всегда смотри код и только потом интерпретируй.

Четвёртая — верить дампу как истине. Если в пути стоит посредник, данные могли быть изменены. Отмечай, где снят дамп, и учитывай это в выводах.

## Ссылки на спецификации и дальнейшее чтение

Телеком-протоколы описаны в спецификациях 3GPP и ITU — это первоисточник, к которому стоит обращаться, когда дамп непонятен. Полезно знать, где что лежит.

Для SS7 и MAP: ITU-T Q.700-серия описывает MTP, Q.711-716 — SCCP, Q.771-775 — TCAP, а MAP определён в 3GPP TS 29.002. Для Diameter базовый протокол — RFC 6733, приложения S6a/Gx/Gy — в TS 29.272/29.212/32.299. Для GTP — TS 29.060 (GTPv1) и TS 29.274 (GTPv2-C), GTP-U — TS 29.281.

Для IMS базовый SIP — RFC 3261, а профиль для 3GPP — TS 24.229; SDP описан в RFC 4566. Для 5G ядро — TS 23.501 (архитектура), NAS — TS 24.501, SBI — TS 29.500-серия.

Практический приём: когда видишь незнакомое поле или код, ищи его имя в соответствующей спецификации. Регулярно это делать полезно, потому что dissector в Wireshark показывает ровно те имена, что и стандарт.

Наконец, для тренировки поднимай открытые стенды: srsRAN и OpenAirInterface для радио, free5GC и Open5GS для ядра, Kamailio для IMS/SIP. На них безопасно воспроизводится почти любая описанная здесь атака — и, что важнее, видна реакция сети на неё.

## Что проверить в первую очередь

Начиная разбор реального дампа, держи в голове короткий порядок: определи протокол и его версию, найди инициатора сессии, собери всю цепочку сообщений целиком, отметь коды результата и только затем ищи отклонение. Такой порядок экономит время и не даёт утонуть в деталях. А если что-то в поле непонятно — открой соответствующую спецификацию и найди имя поля: dissector показывает те же имена, что и стандарт, поэтому поиск почти всегда успешен.
