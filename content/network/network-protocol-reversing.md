## Вопрос, с которого всё начинается

В CTF дали `capture.pcap`, внутри — трафик на необычный порт `9000`. Никаких HTTP или TLS, просто куча байтов. Как из этого набора понять, что за протокол, и вытащить данные?

В этом уроке мы разберём **методологию реверса протокола** на конкретном примере: выделим границы сообщений, найдём поля, определим их смысл и соберём простой парсер.

## Наш пример: странный трафик на порт 9000

Начнём с общего взгляда. Посмотрим список пакетов и их размеры.

```
$ tshark -r custom.pcap
    1  0.000000  10.0.0.5 → 10.0.0.9  TCP 73 40000 → 9000 [PSH, ACK] Seq=1 Ack=1 Len=19
    2  0.000259  10.0.0.9 → 10.0.0.5  TCP 70 9000 → 40000 [PSH, ACK] Seq=1 Ack=20 Len=16
```

`Len=19` и `Len=16` — это длины **полезной нагрузки** (payload) TCP. Значит, в первом пакете 19 байт, во втором 16. TCP сам по себе границы сообщений не сохраняет — это **поток байтов**. Поэтому наша первая задача: понять, как приложение размечает свои сообщения внутри этого потока.

## Шаг 1: смотрим сырые байты

Соберём TCP-поток и посмотрим на данные как на текст и как на hex.

```
$ tshark -r custom.pcap -z follow,tcp,ascii,0
Node 0: 10.0.0.5:40000
Node 1: 10.0.0.9:9000
19
XPRT....HELLO:admin
    16
XPRT....OK:admin
```

Уже видно: оба сообщения начинаются с `XPRT`, дальше идут «нечитаемые» байты, потом ASCII-строка. Похоже, `XPRT` — это **магия** (magic): фиксированная метка, по которой распознаётся начало сообщения.

## Шаг 2: выделяем заголовок

Посмотрим те же данные в hex, чтобы точно посчитать поля.

```
$ tshark -r custom.pcap -T fields -e data.data
58505254010003...
```

Расшифруем байты первого сообщения: `58 50 52 54` = `XPRT`, затем `01 00 03 00 0b`, затем `HELLO:admin`.

Сопоставим с длиной. Полезная нагрузка 19 байт: `4` (магия) + `5` (заголовок?) + `10` (`HELLO:admin`). Строка `HELLO:admin` — 11 символов. Проверим: `H E L L O : a d m i n` = 11. Тогда 4 + 5 + ... не сходится. Значит, одно из «полей» — это **длина** строки.

## Шаг 3: угадываем поля и эндианность

У нас остались байты `01 00 03 00 0b`. Естественная гипотеза для бинарного протокола:

- `01` — версия;
- `00 03` — код команды (или `03 00` — зависит от порядка байтов);
- `00 0b` — длина полезной строки = 11.

`0x0b` = 11 — совпадает с длиной `HELLO:admin`! Значит, длина записана в **big-endian** (старший байт первым): `00 0b`. И команда `00 03` тоже big-endian.

Проверим на ответе. Второе сообщение: `58 50 52 54 01 00 83 00 09 4f 4b 3a 61 64 6d 69 6e` (16 байт). Разбор:

- `XPRT` — магия;
- `01` — версия;
- `00 83` — команда (ответ);
- `00 09` — длина = 9;
- `OK:admin` — 8 символов... снова на единицу больше.

Хм, `OK:admin` = 8 байт, а поле говорит 9. Здесь либо длина включает завершающий ноль, либо мы ошиблись на байт. Такие расхождения — **норма** при реверсе: гипотезу надо уточнять на нескольких сообщениях. Возможно, длина считается вместе с терминатором `\x00`.

## Шаг 4: методология (обобщаем приём)

Из этого упражнения выводится рабочий алгоритм реверса:

1. **Собери поток.** В Wireshark — `Follow → TCP Stream`; в командной строке — `tshark -z follow,tcp,ascii,0`.
2. **Найди магию.** Ищи повторяющийся префикс в начале сообщений — это якорь.
3. **Определи границы.** Если есть поле длины — вычисли, к чему оно относится (всё сообщение? только payload? с терминатором?).
4. **Определи эндианность.** Возьми маленькое значение и посмотри оба порядка байтов: `00 0b` = 11 (big-endian) логичнее, чем `0b 00` = 2816.
5. **Составь таблицу полей** и проверь её на **всех** сообщениях — гипотеза должна объяснять каждое.
6. **Восстанови семантику.** Сопоставь коды команд с поведением: `00 03` → запрос, `00 83` → ответ (часто старший бит = «ответ»).

## Шаг 5: пишем парсер

Когда формат восстановлен, его описывают кодом. На Python со `scapy` и модулем `struct` это выглядит так:

```python
import struct

def parse(buf):
    magic, ver, cmd, ln = struct.unpack(">4sBBH", buf[:8])
    body = buf[8:8+ln]
    return magic, ver, cmd, body
```

`>4sBBH` означает big-endian (`>`): 4 байта строки, два однобайтовых поля, одно двухбайтовое. Такой парсер сразу превращает сырые байты в понятную структуру.

Дальше можно написать **клиент**: взять чужой протокол, отправлять свои команды и смотреть ответы — это часто и есть цель CTF-задачи («обойтись с сервисом как с API»).

## Шаг 6: когда протокол сложнее

В реальности встретятся дополнительные трудности:

- **Сжатие и шифрование** внутри — тогда сначала ищи, где ключ/алгоритм.
- **Переменная длина заголовка** — например, с TLV-полями (Type-Length-Value).
- **Мультиплексирование** — несколько логических потоков в одном TCP.
- **Текстовые смеси** — часть полей ASCII, часть бинарные.
- **Контрольные суммы** — если менять данные, надо пересчитать.

Общий принцип не меняется: **найти якорь → определить границы → проверить гипотезу на всех данных → описать кодом**.

## Шаг 7: полезные привычки при реверсе

Несколько привычек, которые экономят часы. **Ведите таблицу полей** в текстовом файле: смещение, размер, предполагаемый смысл, уверенность. **Сортируйте сообщения** по типу и длине — так быстрее заметите закономерность. **Проверяйте на границах**: возьмите самое короткое и самое длинное сообщение и убедитесь, что формат объясняет оба. **Не доверяйте одной реализации**: если есть несколько версий клиента, сравните их обмен — иногда поле «зарезервировано» в одной версии и используется в другой. И **сохраняйте дампы** — к удачной записи вы вернётесь ещё не раз.

## Что мы теперь знаем

- TCP — это поток байтов; границы сообщений задаёт само приложение.
- Магия (повторяющийся префикс) — якорь для поиска начала сообщений.
- Поле длины и порядок байтов (эндианность) восстанавливаются сравнением с реальными длинами.
- Гипотезу о формате нужно проверять на всех сообщениях, а не на одном.
- Восстановленный формат описывают парсером и превращают в клиент.

## Разбираем заголовок побайтово: длина и эндианность

Вернёмся к нашему «странному трафику на порт 9000». Мы уже поняли, что первые байты — заголовок. Теперь найдём в нём поле длины. Смотрим начало полезной нагрузки в hex:

```
$ tshark -r proto.pcap -T fields -e data -c 2
0c00000041424344
0c00000045464748
```

Читаем: `0c 00 00 00` — четыре байта, затем `41 42 43 44` (`ABCD`). Если `0c` = 12 — это длина всего кадра. Порядок байт `0c 00 00 00` означает **little-endian** (младший байт вперёд). Если бы было `00 00 00 0c` — **big-endian**. Это первый ключевой вывод: формат числа говорит о платформе и о том, как писать парсер.

Проверим гипотезу на втором кадре: длина снова `0c`, данные `EFGH`. Значит, поле длины повторяется и корректно описывает полезную нагрузку. Гипотеза подтверждена — можно строить парсер.

## Таблица: как угадывать назначение полей

| Наблюдение | Вероятный смысл поля |
|---|---|
| Постоянное значение во всех кадрах | версия/магия |
| Растёт на 1 от кадра к кадру | sequence number |
| Меняется произвольно | идентификатор/флаг |
| Равно длине остатка | длина |
| 2 байта, меняются попарно | порт/код |
| Повторяется 4 раза | IPv4-адрес |

Это эвристики, а не догма. Настоящая проверка — **изменить** байт и посмотреть, что ответит сервер. Если увеличить поле длины на 1, а сервер отдаст ошибку «bad length» — поле найдено верно.

## Продолжаем парсер: разбор кадра целиком

Дополним наш парсер так, чтобы он читал длину и проверял её:

```python
import struct
from scapy.all import rdpcap, TCP

def parse(payload):
    length = struct.unpack('<I', payload[:4])[0]   # little-endian uint32
    body = payload[4:4 + length - 4]
    return {'length': length, 'body': body}

pkts = rdpcap('proto.pcap')
for p in pkts:
    if p.haslayer(TCP) and p[TCP].dport == 9000:
        print(parse(bytes(p[TCP].payload)))
```

Запуск даёт:

```
{'length': 12, 'body': b'ABCD'}
{'length': 12, 'body': b'EFGH'}
```

Теперь у нас есть структура: 4 байта длины + данные. Дальше так же угадываются поля внутри `body` — команда, флаги, аргументы.

## Когда протокол сложнее

Если в дампе нет ни магии, ни длины, есть ещё приёмы:

- **Энтропия.** Высокая энтропия байтов = шифрование или сжатие; низкая = структурированные данные.
- **Сравнение с бинарником.** Если есть клиент, ищи в нём строки-ошибки и константы — они ведут к структурам.
- **Мутация.** Меняй один байт за раз и смотри на реакцию — так находят «границы» полей.
- **Частотный анализ.** Многобайтовые поля часто имеют предсказуемые значения.

## Если не сработало: сервер молчит на мутации

Частая ситуация: меняешь байт — соединение рвётся. Это не ошибка, а сигнал: поле защищено (checksum, MAC) либо сервер валидирует строго. Тогда порядок такой: сначала найди **контрольную сумму** (она обычно в конце кадра и меняется при мутации), пересчитай её после правки, и только потом мутируй поля. Если протокол шифрован — реверс «с нуля» бесполезен, нужен либо ключ, либо анализ клиента (динамический, через отладчик).
