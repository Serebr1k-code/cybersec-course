Иногда в дампе нет знакомых протоколов — только поток байтов между двумя портами. Нужно понять структуру кастомного протокола, чтобы извлечь данные или воспроизвести обмен. Это аналитическая задача без готовых инструментов.

## Стратегия реверса протокола

Порядок действий:

1. **Изолировать поток.** Найти TCP/UDP-сессию (`tcp.stream eq N`), выгрузить payload.
2. **Найти границы сообщений.** Определить, где начинается и заканчивается одно сообщение.
3. **Определить поля.** Найти длины, типы, идентификаторы, счётчики.
4. **Проверить гипотезу.** Изменяя трафик/воспроизводя, подтвердить структуру.
5. **Написать парсер.** Восстановить данные или собрать клиент.

## Извлечение структуры из трафика

Выгрузи payload потока в hex и смотри повторы/закономерности:

```bash
tshark -r cap.pcap -q -z follow,tcp,hex,3
# или в сыром виде
tshark -r cap.pcap -q -z follow,tcp,raw,3 | tail -n +7 | xxd -r -p > stream.bin
xxd stream.bin | head -40
```

Признаки структуры:

- **Постоянные байты** в начале каждого сообщения → магическое число (magic) или тип.
- **Растущие значения** → счётчик или sequence.
- **Поле, значение которого равно длине остатка** → поле длины.
- **Повторяющиеся подстроки** → строки/идентификаторы.

Полезно разбить на «сообщения» по известной длине и сравнить:

```bash
xxd -c 16 stream.bin | less
```

## Определение границ сообщений

Самое сложное — где заканчивается одно сообщение. Подходы:

- **По полю длины**: если найден байт/слово, равное размеру хвоста, — это length.
- **По magic/типу**: одинаковые стартовые байты делят поток на кадры.
- **По разделителю**: символ `\n`, `\0`, `;` между сообщениями.
- **По протокольным маркерам**: фиксированный размер кадра (например, 64 байта).
- **Эмпирически**: если поток без остатка делится по гипотезе — границы верны.

```python
# проверить гипотезу "[len:2 BE][data:len]" на всём потоке
import struct
data = open('stream.bin','rb').read()
i = 0
while i < len(data):
    ln = struct.unpack('>H', data[i:i+2])[0]
    payload = data[i+2:i+2+ln]
    print(ln, payload[:40])
    i += 2 + ln
print('consumed', i, 'of', len(data))
```

Если `consumed == len(data)` — структура почти наверняка верна.

## Формат данных и эндианность

Типичные поля:

| Тип | Размер | Признак |
|---|---|---|
| uint8/16/32 | 1/2/4 | небольшие растущие значения |
| length | 2/4 | равно размеру хвоста |
| string | переменный | ASCII/UTF-8, часто с префиксом длины |
| magic | 2/4 | константа в начале |

**Эндианность** (порядок байт) — частая ловушка. `00 00 01 00` = 256 (big-endian) или 65536 (little-endian). Проверяй оба:

```python
import struct
data = open('stream.bin','rb').read()
print(struct.unpack('>I', data[0:4]))   # big-endian
print(struct.unpack('<I', data[0:4]))   # little-endian
```

**Length-prefixed строки** — классика: 1–2 байта длины, затем сама строка.

## Пример разбора

Допустим, поток содержит повторяющиеся блоки:

```
01 00 05 68 65 6c 6c 6f ...
02 00 03 66 6f 6f ...
01 00 05 77 6f 72 6c 64 ...
```

Гипотеза: `[type:1][len:1][data:len]`. Проверяем: `01 00 05` → type=1, len=5, data=`hello` (5 байт). Следующий блок начинается сразу после — гипотеза подтверждается.

Парсер:

```python
data = open('stream.bin','rb').read()
i = 0
while i < len(data):
    typ = data[i]; ln = data[i+1]
    payload = data[i+2:i+2+ln]
    print(typ, payload)
    i += 2 + ln
```

Если границы совпали со всем потоком — структура верна.

## Работа с бинарными полями глубоко

- **Поля переменной длины**: ищите префикс длины перед строкой/блобом.
- **Битовые поля/флаги**: одно байт-значение может кодировать набор флагов (`& 0x01`, `>> 1`).
- **Выравнивание (padding)**: после строки могут быть нули до 4-байтной границы.
- **Контрольные суммы/CRC**: если в кадре есть 2/4 байта, меняющиеся «случайно», проверьте CRC32.
- **Сжатие/шифрование**: если payload выглядит энтропийно — возможно, сжат (zlib/gzip) или XOR-нут.

```python
import zlib
try:
    print(zlib.decompress(payload))
except Exception as e:
    print('not zlib:', e)
```

## Воспроизведение и проверка

Собрав структуру, можно:

- восстановить переданные файлы (склеить payload'ы);
- собрать клиент на `scapy`/`socket` и проиграть обмен;
- найти уязвимость (переполнение длины, отсутствие проверок) для эксплуатации сервиса.

```python
from scapy.all import *
# replay
send(IP(dst="10.0.0.5")/TCP(dport=4444, flags="PA")/b"\x01\x00\x05hello")
```

## Инструменты и флаги

| Инструмент | Назначение |
|---|---|
| `tshark -z follow,tcp,raw` | выгрузить payload потока |
| `xxd` / `hexdump` | просмотр структуры |
| Scapy | парсинг/отправка пакетов |
| Python `struct` | распаковка полей |
| Wireshark «Follow Stream» | TCP-реассемблинг |
| Kaitai Struct | декларативное описание формата |

## Частые ошибки

- **Игнорировать TCP-реассемблинг.** Одно сообщение может быть разбито на несколько сегментов — соберите поток (Follow Stream) до разбора полей.
- **Забыть про endianness и выравнивание.** Поля бывают little- и big-endian, иногда с padding — проверяйте гипотезу на нескольких примерах, а не на одном.
- **Не искать поле длины.** Оно чаще всего объясняет границы кадра; находите его первым, чтобы резать поток на сообщения.
- **Строить парсер на одном примере.** Проверяйте на всём потоке (consumed == length).

## Что делать дальше / решение

- **Нужны границы** → ищите length/magic → проверяйте делением потока.
- **Нужны поля** → `struct` big/little, флаги, выравнивание.
- **Нужен payload** → zlib/XOR/сжатие.
- **Нужен клиент** → Scapy replay → уязвимости.

## Практический разбор: UDP-протокол и восстановление файла

Часто кастомный протокол работает поверх UDP, где нет потока — каждое сообщение самостоятельное. Методика:

1. **Сгруппировать датаграммы** по направлению (`udp.srcport`/`dstport`).
2. **Выгрузить payload'ы** каждой датаграммы: `tshark -r cap.pcap -Y 'udp.port==4444' -T fields -e data`.
3. **Найти поля** (magic, seq, total, length) — часто есть номер последовательности и общее число частей.
4. **Собрать файл** в правильном порядке и распаковать (zlib/gzip), если данные сжаты.

```python
import subprocess, binascii, zlib
out = subprocess.check_output([
    'tshark','-r','cap.pcap','-Y','udp.port==4444',
    '-T','fields','-e','udp.payload']).decode().split()
chunks = {}
for line in out:
    raw = binascii.unhexlify(line.replace(':',''))
    seq = raw[1]           # гипотеза: [magic:1][seq:1][data:]
    chunks[seq] = raw[2:]
data = b''.join(chunks[k] for k in sorted(chunks))
try:
    data = zlib.decompress(data)
except Exception:
    pass
open('recovered.bin','wb').write(data)
```

Проверка: если после сборки файл открывается (сигнатура в начале) — гипотеза о формате верна. Так восстанавливают переданные картинки, архивы и флаги.

## Быстрая шпаргалка

```bash
# TCP: собрать поток и выгрузить payload
tshark -r cap.pcap -q -z follow,tcp,raw,N | tail -n +7 | xxd -r -p > s.bin
# UDP: выгрузить payload'ы датаграмм
tshark -r cap.pcap -Y 'udp.port==PORT' -T fields -e udp.payload
# разложить байты
xxd s.bin | head
```

Алгоритм: magic/тип → длина → payload → проверка «consumed == total». Затем `struct` big/little, флаги, zlib. Подтверждайте гипотезу на всём потоке, а не на одном кадре.
