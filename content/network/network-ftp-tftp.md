## Вопрос, с которого всё начинается

Сканер показал открытый порт `21` и сервис FTP. Что это за протокол, чем он опасен спустя столько лет и как проверить, не отдаёт ли он файлы кому угодно? Плюс рядом часто живёт TFTP на порту `69` — ещё более древний и без паролей вообще.

Разберём оба протокола на конкретном примере: подключимся к FTP-серверу и посмотрим, что он расскажет.

## Наш пример: FTP-сервер 10.0.0.9:21

Начнём с простого: подсоединимся `netcat` и посмотрим приветствие.

```
$ nc 10.0.0.9 21
220 (vsFTPd 3.0.3)
```

Строка `220` — это код ответа «сервис готов», а `vsFTPd 3.0.3` — **баннер** с реализацией и версией. По версии ищут известные уязвимости. Дальше FTP говорит «текстовыми командами», каждая команда — ответ с числовым кодом.

## Шаг 1: анонимный вход

Первое, что проверяют на любом FTP, — **анонимный доступ**. Многие серверы настроены отдавать файлы без пароля (для публичного обмена). Логин — `anonymous`, пароль — любой (традиционно e-mail).

```
$ ftp 10.0.0.9
Name: anonymous
331 Please specify the password.
Password:
230 Login successful.
```

Код `331` — «нужен пароль», `230` — «вход выполнен». Если анонимный вход разрешён, мы уже внутри и можем читать содержимое.

## Шаг 2: активный и пассивный режимы

Здесь важная деталь архитектуры FTP, из-за которой он необычен. FTP использует **два соединения**:

- **управляющее** (порт 21) — команды и ответы;
- **данных** — по нему идут файлы и листинги.

Есть два способа поднять второе соединение:

- **Активный режим (PORT)** — сервер сам **подключается к клиенту** на указанный порт. Проблема: клиент за NAT/файрволом этот порт не примет.
- **Пассивный режим (PASV)** — клиент просит сервер открыть порт и подключается сам. Работает через NAT, поэтому сегодня по умолчанию используют его.

Посмотрим, как это выглядит в командах:

```
ftp> ls
227 Entering Passive Mode (10,0,0,9,195,80).
150 Here comes the directory listing.
-rw-r--r--    1 0        0            1024 Jan 10 09:00 backup.zip
drwxr-xr-x    2 0        0            4096 Jan 10 09:01 configs
226 Directory send OK.
```

Строка `227 Entering Passive Mode (10,0,0,9,195,80)` — это ответ PASV: сервер сообщает адрес и порт для соединения данных. Числа `195,80` — порт в виде двух байт: `195*256 + 80 = 50000`. Клиент подключается туда.

Коды `150` («открываю соединение данных»), `226` («передача завершена») сопровождают передачу.

## Шаг 3: скачиваем и замечаем запись

Дальше — `get backup.zip`. Но интереснее другое: если у анонима есть **права на запись**, можно залить файл (`put`). Это уже серьёзно: часто FTP-каталог совпадает с каталогом веб-сервера, и загрузка `.php`/`.jsp` даёт **выполнение кода** (webshell).

Проверка простая: пробуем `put` безобидный файл и смотрим код ответа.

```
ftp> put test.txt
200 PORT command successful.
150 Ok to send data.
226 Transfer complete.
```

Если бы было `550 Permission denied` — записи нет. А `226` после `put` означает, что файл лёг.

## Шаг 4: FTP bounce

**FTP bounce** — менее известная, но красивая техника. В активном режиме клиент командой `PORT` указывает, **куда** серверу подключаться. Если сервер не проверяет этот адрес, можно заставить его подключиться к **третьему** хосту, а не к нам.

```
ftp> PORT 10,0,0,50,0,25
200 PORT command successful.
ftp> LIST
```

Здесь мы просим FTP-сервер открыть соединение данных к `10.0.0.50:25` (SMTP). Сервер выступает «ретранслятором» и заодно позволяет **сканировать** чужие порты через него: разный ответ на `150`/`425` выдаёт, открыт порт или нет. Так обходят сетевые ограничения — источник запросов выглядит как доверенный FTP-сервер.

## Шаг 5: TFTP — FTP без паролей и без рук

**TFTP** (Trivial FTP) работает по **UDP/69** и предельно прост: нет аутентификации, нет листинга каталогов, есть только `read` и `write` файла по имени. Его используют для загрузки прошивок и конфигов (сетевые устройства, PXE-загрузка).

Читаем файл, зная имя:

```
$ tftp 10.0.0.9
tftp> get running-config
Received 4096 bytes in 0.1 seconds
tftp> quit
```

Если у нас есть **запись**, можно подменить конфиг или прошивку — классическая атака на сетевое оборудование. TFTP не аутентифицирует вообще ничего, поэтому защита — только сетевая (ACL, отдельный сегмент).

## Шаг 6: как защищаться

- **FTP:** запретить анонимный вход, ограничить запись, отдать файлы через HTTPS, использовать FTPS/SFTP.
- **FTP bounce:** на сервере проверять, что адрес в `PORT` совпадает с адресом клиента.
- **TFTP:** не выставлять наружу, ограничить доступ ACL, использовать только в доверенном сегменте.
- **Мониторинг:** аномально частые `put`, листинги из необычных подсетей, вход `anonymous` — сигналы для SOC.

## Шаг 7: как проверить FTP системно

Практическая проверка FTP-сервера идёт по списку:

1. **Баннер.** `nc 10.0.0.9 21` — версия и реализация.
2. **Анонимный вход.** Логин `anonymous`, любой пароль; код `230` = пустили.
3. **Листинг.** `ls` — что вообще лежит, нет ли `backup`, `config`, `.git`.
4. **Права на запись.** `put` безобидного файла; код `226` = запись разрешена.
5. **Активный режим.** Попробовать `PORT` на свой адрес; если работает и адрес не проверяется — возможен bounce.
6. **TFTP.** Отдельно проверить UDP/69 на чтение (`get`) и запись (`put`) известных имён.

Помимо ручных шагов, стоит проверить `SITE`-команды и `STAT`: некоторые серверы отдают список файлов через `STAT` даже при закрытом листинге, а `SITE HELP` раскрывает дополнительные возможности сервера.

Не забывай про **перебор имён файлов**: FTP не всегда даёт листинг, но конкретные файлы (`config.xml`, `passwords.txt`, `id_rsa`) могут отдаваться. Это уже задача фаззинга, а не ручного перебора.

## Шаг 8: автоматизация проверки (nmap NSE)

Ручной разбор хорош для понимания, но в реальном тесте FTP-проверки делают скриптами. У nmap есть готовые NSE:

```
$ nmap -p21 --script ftp-anon,ftp-bounce,ftp-vsftpd-backdoor 10.0.0.9
PORT   STATE SERVICE
21/tcp open  ftp
| ftp-anon: Anonymous FTP login allowed (FTP code 230)
|_drwxr-xr-x   2 0 0  4096 configs
| ftp-bounce: Server allows FTP bounce (PORT to third-party host)
|_ftp-vsftpd-backdoor: VULNERABLE (vsFTPd 2.3.4 backdoor)
```

`ftp-anon` сам логинится анонимно и отдаёт листинг, `ftp-bounce` проверяет, принимает ли сервер `PORT` на чужой адрес, а отдельные скрипты ловят известные бэкдоры (vsFTPd 2.3.4 — знаменитый `:)`-бэкдор). Это быстрее и надёжнее ручного тыканья.

## Шаг 9: FTPS и SFTP — что выбрать

FTP устарел не потому, что «старый», а потому что **не шифрует** ни пароль, ни данные. Есть два пути исправления, и их часто путают:

| Вариант | Транспорт | Что шифрует | Порт |
|---|---|---|---|
| **FTPS** | FTP + TLS | канал (явный/неявный TLS) | 21/990 |
| **SFTP** | SSH-подсистема | всё (пароль, данные, команды) | 22 |

FTPS — тот же FTP, обёрнутый в TLS: два соединения остаются, NAT по-прежнему мешает. SFTP — часть SSH: один канал, ни портов данных, ни bounce. Поэтому сегодня стандарт — **SFTP**, а не FTPS.

Проверить, что сервер реально шифрует, можно так:

```
$ openssl s_client -connect 10.0.0.9:990 -quiet
```

Если handshake проходит и сертификат валиден — FTPS включён; если соединение отбивается — сервер отдаёт данные открытым текстом.

## Если не сработало

- **Анонимный вход отклонён (`530`).** Значит, анонимка выключена — переходи к перебору учёток (`hydra -L users -P pass ftp://...`), но только малым словарём.
- **`put` даёт `550`.** Запись закрыта; ищи другой каталог или используй чтение/bounce.
- **TFTP не отвечает.** Проверь UDP (не TCP): `tftp` молчит, если порт фильтруется, а не закрыт.
- **Листинг пуст.** Каталог не расшарен, но конкретные имена файлов могут отдаваться — переходи к фаззингу имён.

## Что мы теперь знаем

- FTP говорит текстовыми командами с числовыми кодами (`220`, `331`, `230`, `150`, `226`).
- Анонимный вход (`anonymous`) — первое, что проверяют.
- FTP использует два соединения; PASV — современный режим, PORT — активный.
- Права на запись в FTP-каталог могут дать webshell.
- FTP bounce превращает сервер в ретранслятор и сканер.
- TFTP — UDP/69 без аутентификации, опасен чтением и записью.
- FTP-проверки автоматизируются NSE-скриптами: `ftp-anon`, `ftp-bounce`.
- Порт данных в PASV закодирован двумя байтами: `195,80` = 195*256+80 = 50000.
- FTPS — FTP в TLS (два канала), SFTP — часть SSH (один канал); стандарт сегодня — SFTP.
- `STAT`/`SITE HELP` иногда раскрывают листинг и возможности при закрытом `ls`.
- Запись по TFTP на сетевое оборудование = подмена конфига или прошивки.

## Куда дальше

Дальше разберём ещё более старый класс сервисов — Telnet и r-services, где пароли и данные идут открытым текстом, а доверие строится на файлах `.rhosts`. А пока главное запомни: древние протоколы передачи файлов часто не имеют ни шифрования, ни нормальной аутентификации.

## Где пригодится

- **CTF:** задачи с анонимным FTP, записью файлов, TFTP-конфигами.
- **Пентест:** проверка анонимного доступа и прав на запись, bounce-сканирование.
- **Работа:** аудит FTP/TFTP, перевод обмена на SFTP/HTTPS.
- **SOC:** детект анонимных входов и необычных загрузок.
