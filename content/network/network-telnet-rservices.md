## Вопрос, с которого всё начинается

Ты нашёл хост с открытыми портами `23` (Telnet) и `513/514` (r-services). Эти протоколы придумали ещё до того, как шифрование стало нормой. Чем они плохи настолько, что их выпиливают из сетей?

Ответ простой и жёсткий: **всё, что ты печатаешь, включая пароль, идёт по сети открытым текстом**. Разберём, как это выглядит на проводе и что из этого следует.

## Наш пример: сессия Telnet

Сначала посмотрим, как Telnet вообще начинается. При подключении клиент и сервер обмениваются управляющими байтами **IAC** (Interpret As Command) — это `0xFF`, за которым идёт команда. Так стороны договариваются об опциях (терминал, эхо, размер экрана).

Поймаем первый обмен:

```
$ tshark -r telnet.pcap
    1  0.000000  10.0.0.5 → 10.0.0.9  TELNET 66 Do Terminal Type, Do Terminal Speed,
                                                 Do X Display Location, Do New Environment Option
```

`tshark` расшифровал IAC-байты и показал, что клиент запрашивает четыре опции. В hex это выглядело бы как `ff fd 18 ff fd 20 ff fd 23 ff fd 27`, где `ff fd` = «IAC Do». **Do** значит «включи опцию у себя», а **Will** — «я буду использовать». Эта фаза нужна, чтобы терминал работал правильно.

## Шаг 1: а где же пароль

Дальше начинается обычный обмен символами. И тут — ключевой момент. Telnet **не шифрует** ничего. Когда пользователь вводит логин и пароль, они уходят как есть. Перехватив поток, мы просто читаем:

```
$ tshark -r telnet.pcap -z follow,tcp,ascii,0
login: admin
Password: S3cr3t!
$ whoami
admin
```

Никакого «взлома» не нужно — данные лежат в дампе открытым текстом. Именно поэтому Telnet недопустим в любой сети, где трафик может пройти через чужое устройство.

## Шаг 2: r-services — доверие вместо пароля

`r-services` — это семейство из трёх команд:

- `rlogin` (порт 513) — удалённый вход;
- `rsh` (порт 514, TCP) — удалённое выполнение команд;
- `rexec` (порт 512) — удалённое выполнение с паролем.

Их особенность — механизм **доверия** через файлы `.rhosts` (в домашнем каталоге пользователя) и `/etc/hosts.equiv`. В них перечислены хосты и пользователи, которым разрешён вход **без пароля**.

```
$ cat ~/.rhosts
trusted-host.example.com admin
```

Такая строка означает: если запрос придёт с `trusted-host.example.com` от имени `admin`, пускать без пароля. Проблема в том, что проверка идёт по **имени/IP**, а подделать источник (или просто зайти с доверенного хоста) часто возможно. Это классический **trust-based access** — доверие вместо аутентификации.

## Шаг 3: как это эксплуатируют

Три сценария:

1. **Перехват пароля.** Если Telnet/rlogin используется в сегменте, где мы в позиции MITM, — пароль просто читается из трафика.
2. **Злоупотребление доверием.** Нашли `.rhosts`, видим доверенный хост — если он сам скомпрометирован (или его IP можно подделать), входим без пароля.
3. **Brute / дефолты.** Telnet часто оставляют с дефолтными учётками (роутеры, коммутаторы, IP-камеры). Небольшой список дефолтов + анонимный доступ — и мы внутри.

Для проверки `rsh` без пароля есть готовая команда:

```
$ rsh -l admin 10.0.0.9 id
uid=1000(admin) gid=1000(admin)
```

Если вернулось `id` — доверие работает и пароль не спросили.

## Шаг 4: почему legacy-сервисы живут до сих пор

Логичный вопрос: зачем это всё ещё включено? Причины прозаичны:

- **Старое оборудование** (коммутаторы, АТС, промышленные контроллеры) умеет только Telnet.
- **«Работает — не трогай»** — сервис настроили 15 лет назад и забыли.
- **Внутренняя сеть кажется безопасной** — ошибочное допущение, что внутри «все свои».

Именно поэтому пентест внутренней сети почти всегда находит Telnet где-нибудь в углу.

## Шаг 5: как защищаться

- **Заменить на SSH.** Для любого интерактивного доступа — только SSH с ключами.
- **Отключить r-services.** Они не нужны почти нигде; если нужны — только по строгому `hosts.equiv` и в изолированном сегменте.
- **Сегментация и ACL.** Даже legacy-устройства не должны быть доступны из пользовательской сети.
- **Сменить дефолты.** Пароли по умолчанию — прямой вход.
- **Мониторинг.** Для SOC: Telnet-сессии в дампах, вход `rsh` без пароля, обращения к портам `23/512/513/514` — сигналы.

## Как найти legacy-сервисы в сети

Прежде чем что-то перехватывать, эти сервисы надо найти. Сканирование по портам — первый шаг: `nmap -p23,512,513,514 <подсеть>`. Ответ на `23` часто содержит баннер с моделью устройства (`RouterOS`, `Linux telnetd`), а порты `512-514` выдают r-services.

Полезно помнить про **нестандартные порты**: администраторы иногда переносят Telnet на другой порт «для безопасности», но протокол от этого не шифруется. Поэтому в дополнение к сканированию портов смотрят, какие сервисы вообще отвечают на нестандартных портах (`nmap -sV` по диапазону).

Ещё один признак — **трафик в дампе**: Telnet-сессии видны как текстовый поток с IAC-байтами, и их легко заметить при анализе. Для SOC это повод завести правило: любое обращение к `23/512/513/514` — событие.

## Шаг 6: как перехватить сессию на практике

Разберём, как выглядит перехват по шагам, чтобы закрепить понимание. Предположим, мы в позиции MITM (например, встали между клиентом и сервером через ARP-спуфинг, как в уроках про MITM).

1. **Захват.** Пишем трафик на порт 23: `tcpdump -i eth0 -A 'tcp port 23'`. Ключ `-A` печатает содержимое в виде текста — именно то, что нам нужно.
2. **Поиск логина.** В дампе ищем приглашение `login:` — сразу за ним идёт имя пользователя.
3. **Поиск пароля.** Строка `Password:` — и следующий ввод и есть пароль.
4. **Проверка.** Подключаемся сами с найденными данными: `nc 10.0.0.9 23`.

Есть и более удобный путь — Wireshark с фильтром `telnet` и функцией `Follow → TCP Stream`: он покажет весь диалог целиком, включая управляющие IAC-последовательности. Для `rlogin`/`rsh` принцип тот же, только порты другие (`512/513/514`).

Отдельно стоит упомянуть **snooping** в коммутаторах и **зеркалирование портов**: если у тебя есть доступ к управлению коммутатором, можно зеркалировать трафик нужного порта и читать всё без ARP-спуфинга. Это подчёркивает главный урок: незашифрованный протокол + доступ к каналу = перехват.

## Что мы теперь знаем

- Telnet передаёт всё, включая пароль, открытым текстом.
- В начале Telnet идёт IAC-согласование опций (`Do`/`Will`).
- r-services используют доверие по `.rhosts`/`hosts.equiv` вместо пароля.
- Доверие по имени/IP легко подделать или обойти через компрометацию доверенного хоста.
- Лечение — SSH, отключение r-services, сегментация и смена дефолтов.
