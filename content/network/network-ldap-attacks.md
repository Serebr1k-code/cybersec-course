## Вопрос, с которого всё начинается

В корпоративной сети есть **каталог** — база, где хранятся пользователи, группы, компьютеры и их атрибуты. В Windows-домене это Active Directory, и общается она по протоколу **LDAP** (порт 389). Если каталог отвечает анонимно или плохо фильтрует запросы, из него можно выкачать всю структуру домена — имена пользователей, почту, группы.

В этом уроке мы разберём LDAP-обмен на уровне пакетов и покажем, как из каталога утекает информация.

## Наш пример: LDAP-запрос в дампе ldap.pcap

У нас есть дамп `ldap.pcap`, снятый на клиенте. Откроем его и посмотрим, что за сообщения ушли на сервер каталога:

```
$ tshark -r ldap.pcap -T fields -e ldap.messageID -e ldap.protocolOp
1	0
2	3
```

Два сообщения. Число `protocolOp` — это код операции: `0` — **bind** (привязка, аутентификация), `3` — **search** (поиск в каталоге). Разберём их подробнее:

```
$ tshark -r ldap.pcap -V
Lightweight Directory Access Protocol
    LDAPMessage bindRequest(1) "cn=admin,dc=corp,dc=local"
        messageID: 1
        protocolOp: bindRequest (0)
            bindRequest
                version: 3
                name: cn=admin,dc=corp,dc=local
```

Термины:

- **LDAP** (Lightweight Directory Access Protocol) — протокол доступа к каталогу. Данные в нём — дерево записей.
- **DN** (distinguished name) — полный путь записи. `dc=corp,dc=local` — домен `corp.local`; `cn=admin,dc=corp,dc=local` — пользователь `admin`.
- **bind** — операция аутентификации: клиент предъявляет DN и пароль (или остаётся анонимным).

Второе сообщение — поиск:

```
    LDAPMessage searchRequest(2) "dc=corp,dc=local"
        messageID: 2
        protocolOp: searchRequest (3)
            searchRequest
                baseObject: dc=corp,dc=local
                scope: wholeSubtree (2)
```

**baseObject** — с какой записи начинать поиск, **scope** — глубина: `wholeSubtree` означает «всё дерево ниже». То есть клиент запросил обход всего домена.

## Шаг 1: анонимный bind

Ключевой вопрос: разрешает ли сервер **анонимный bind** — привязку без имени и пароля? В Active Directory это исторически включено по умолчанию, и это первая проверка при пентесте.

Проверяется обычным `ldapsearch`:

```
$ ldapsearch -x -H ldap://10.0.0.60 -b "dc=corp,dc=local"
```

Ключи: `-x` — простая аутентификация (без SASL), `-H` — адрес сервера, `-b` — база поиска. Если сервер вернул записи — анонимный доступ разрешён, и можно выкачивать каталог. (На этой машине `ldapsearch` не установлен, поэтому команда приведена как справочная.)

## Шаг 2: дамп каталога

Если анонимный bind работает, дальше каталог дампится целиком. Типовые инструменты:

- **ldapsearch** — базовый, есть везде.
- **windapsearch** — удобные запросы к AD (пользователи, группы, компьютеры, GPO).
- **ldapdomaindump** — выгружает весь домен в HTML/JSON и сразу показывает, кто в каких группах.

Приём из пентеста: искать записи, у которых в описании (`description`) или другом атрибуте лежит **пароль** — администраторы иногда хранят его там. Атрибут `userPassword` в AD не читается, но `description`, `info`, поля в `userParameters` часто выдают секреты.

## Шаг 3: LDAP-инъекция

LDAP-фильтры — это строки запроса вида `(&(objectClass=user)(cn=admin))`. Если приложение подставляет в фильтр пользовательский ввод без экранирования, возникает **LDAP-инъекция** — аналог SQL-инъекции для каталога.

Классика — обход аутентификации. Приложение строит фильтр:

```
(&(uid=$user)(userPassword=$pass))
```

Если подставить в `$user` значение `*)(uid=*))(|(uid=*`, фильтр сломается так, что условие станет всегда истинным — и вход пройдёт без пароля. Спецсимволы LDAP (`*`, `(`, `)`, `\`, NUL) нужно экранировать; если этого не делают — есть инъекция.

## Шаг 4: что видно в трафике

LDAP без TLS (порт 389) передаёт bind-запросы **открытым текстом**. В дампе видно и DN, и пароль. Причём простой bind отправляет пароль в открытом виде, а не хешем. Поэтому:

- Перехват LDAP без шифрования = перехват учётных данных.
- Защита — **LDAPS** (LDAP over TLS, порт 636) или StartTLS.
- Аналитику в дампе стоит искать `ldap.bindRequest` с непустым паролем.

## Шаг 5: защита каталога

- Отключить анонимный bind.
- Требовать подписывание и шифрование LDAP (LDAPS/StartTLS).
- Ограничить, кто может читать атрибуты; убрать лишние права у обычных пользователей.
- Экранировать пользовательский ввод в фильтрах (никогда не собирать фильтр конкатенацией).
- Мониторить массовые search-запросы — это признак дампа каталога.

## Шаг 6: как LDAP-атаки выглядят в детекте

Сетевому аналитику важно узнавать эти атаки в трафике. Признаки в дампе:

- **Массовые searchRequest.** Один клиент за короткое время делает сотни запросов с `scope: wholeSubtree` — это дамп каталога:

```
$ tshark -r ldap.pcap -Y 'ldap.protocolOp == 3' -T fields -e ip.src | sort | uniq -c | sort -rn
   612 10.0.0.77
     3 10.0.0.15
```

612 поисковых запросов с одного адреса против трёх обычных — очевидная аномалия.

- **Анонимные bind.** `bindRequest` с пустым `name` и простой аутентификацией:

```
$ tshark -r ldap.pcap -Y 'ldap.bindRequest && ldap.name == ""' -c 1
    Lightweight Directory Access Protocol
        bindRequest(1) "" simple(0)
```

- **Пароли в открытом виде.** На порту 389 простой bind несёт пароль как есть — ищем поле `simple` с непустым значением. Если же трафик идёт на 636 (LDAPS) или через StartTLS, содержимое зашифровано и в дампе видны только метаданные — это уже хороший знак.

На стороне защиты это превращается в правила: алерт на анонимный bind, порог по числу search на источник, обязательный LDAPS. Но детект вторичен — сначала каталог нужно закрыть, иначе правила сработают уже после утечки. Аналитику полезно держать эти три признака под рукой, чтобы отличать разведку каталога от штатной работы домена.

## Что мы теперь знаем

По-простому:

1. LDAP — протокол каталога (AD) на порту 389; bind — аутентификация, search — поиск.
2. `protocolOp` 0 — bind, 3 — search; DN задаёт путь записи.
3. Анонимный bind разрешает чтение каталога без пароля.
4. Каталог дампят `ldapsearch`/`windapsearch`/`ldapdomaindump`.
5. LDAP-инъекция ломает фильтр и обходит аутентификацию.
6. Без TLS пароли видны в трафике; защита — LDAPS и экранирование.

## На что смотреть дальше

- **Проверь анонимный bind первым.** Это самая частая и самая дешёвая находка.
- **Ищи секреты в атрибутах.** description/info/userParameters.
- **Смотри, есть ли LDAPS.** Порт 636 вместо 389 меняет всю картину.

## Разбираем LDAP bind в дампе

Вернёмся к нашему `ldap.pcap`. Первая операция почти всегда — **bind**: клиент представляется серверу. Простой bind виден целиком:

```
$ tshark -r ldap.pcap -Y ldap -T fields -e ldap.messageID -e ldap.protocolOp -e ldap.name -e ldap.authentication
1  0  cn=admin,dc=example,dc=local  0
```

Читается так: `ldap.protocolOp 0` — это bindRequest, `ldap.name` — кто представляется, а последний `0` — тип аутентификации **simple** (пароль открытым текстом, если без TLS!). Если бы стоял `3`, это был бы SASL (GSSAPI/Kerberos). Именно поэтому LDAP без `ldaps://`/StartTLS — источник учётных данных прямо в дампе.

## Инъекция в фильтр: как выглядит и почему работает

LDAP-фильтр строится из строк, и если приложение вставляет пользовательский ввод без экранирования, можно изменить логику запроса. Классический обход аутентификации:

```
(&(uid=alice)(userPassword=$PASS))
```

Если вместо `$PASS` подставить `*)(|(userPassword=*`, фильтр превращается в «пользователь alice с любым паролем» и bind проходит. Полезные символы инъекции:

| Символ | Смысл в фильтре |
|---|---|
| `*` | подстановка любого значения |
| `)(` | закрыть/открыть условие |
| `|` | логическое ИЛИ |
| `&` | логическое И |
| `!` | отрицание |
| `\` | экранирование (обойти не всегда можно) |

В трафике инъекция видна как bindRequest с «рваным» именем — много скобок и звёздочек вместо аккуратного DN. Для SOC это хороший сигнал.

## Что видно в трафике при дампе каталога

Анонимный или null-bind позволяет **искать** без учётки. Инструмент `ldapsearch` делает серию `searchRequest`, и в ответ приходит `searchResEntry`:

```
$ ldapsearch -x -H ldap://10.0.0.1 -b "dc=example,dc=local" "(objectClass=user)" sAMAccountName
# ...
dn: CN=Alice,CN=Users,DC=example,DC=local
sAMAccountName: alice
```

В дампе это выглядит как поток searchRequest/searchResEntry с атрибутами. Пассивно ты видишь, какие объекты и атрибуты запрашивали, — то есть можешь восстановить, что именно «слили» из каталога, даже не имея доступа.

| Операция | protocolOp | Что даёт атакующему |
|---|---|---|
| bindRequest | 0 | представление (проверка учёток) |
| searchRequest | 3 | перечисление объектов/атрибутов |
| modifyRequest | 6 | изменение каталога |
| addRequest | 8 | добавление объектов |

## Если не сработало: LDAP не отвечает

Если `ldapsearch` молчит, проверь порт: 389 — plain, 636 — LDAPS (TLS). Если сервер требует `ldaps://`, обычный bind уйдёт в отказ. Второй случай — сервер отвергает **анонимный** bind (это правильная настройка), тогда нужны хоть какие-то учётные данные. Третий — в трафике вообще нет LDAP, потому что приложение ходит к домену по **Kerberos** (порт 88), а не к каталогу напрямую. И не путай LDAP с **Global Catalog** (порт 3268/3269) — на нём часть атрибутов доступна иначе.

## Почему это важно

LDAP — это «справочная» домена: пользователи, группы, компьютеры, политики. Анонимный bind и слабые фильтры превращают справочную в карту сети для атакующего. Базовая защита — запретить анонимный bind, требовать LDAPS, включать **LDAP signing** (защита от релея) и мониторить аномально широкие фильтры (`(objectClass=*)` с большим числом записей).
