## Вопрос, с которого всё начинается

В сети есть камера. Ты знаешь её адрес, но не знаешь пароля. Как получить видеопоток и как вообще узнать, что камера умеет? Для этого есть два протокола: **RTSP** (доставка потока) и **ONVIF** (управление и разведка). Вместе они открывают камеру почти целиком.

## Наш пример: RTSP-сессия

Подключаемся к камере по RTSP:

```
$ curl -s rtsp://10.0.0.20:554/ -X OPTIONS -v 2>&1 | grep -iE 'RTSP/1.0|Public'
< RTSP/1.0 200 OK
< Public: OPTIONS, DESCRIBE, SETUP, PLAY, PAUSE, TEARDOWN, GET_PARAMETER
```

Камера отвечает списком поддерживаемых методов. Уже отсюда видно: DESCRIBE (описание потока), SETUP (подготовка), PLAY (запуск). Разберём, что дальше.

## Шаг 1: методы RTSP

RTSP — это «пульт» для медиапотока, похожий на HTTP, но с состоянием сессии.

- **OPTIONS** — какие методы поддерживаются;
- **DESCRIBE** — получить описание потока в формате SDP (кодеки, адреса RTP);
- **SETUP** — подготовить транспорт (куда слать RTP);
- **PLAY / PAUSE / TEARDOWN** — старт, пауза, разрыв;
- **GET_PARAMETER** — иногда используется как keep-alive.

Важно: DESCRIBE отвечает **SDP** — текстом, где видно, какие потоки есть и по каким портам пойдёт RTP.

## Шаг 2: аутентификация RTSP

По умолчанию многие камеры отвечают `401 Unauthorized` и заголовком `WWW-Authenticate`:

```
$ curl -s rtsp://10.0.0.20:554/stream1 -X DESCRIBE -v 2>&1 | grep -i www-authenticate
< WWW-Authenticate: Digest realm="IP Camera", nonce="abc123"
```

**Digest** — challenge-response: пароль не уходит открыто. **Basic** — отправляет base64(user:password), то есть фактически открыто; при этом Basic поверх RTSP/HTTP без TLS легко перехватить.

Классический вход в камеру — дефолтные учётки (`admin:admin`, `admin:12345`, `root:pass`). Перебор — только по небольшому списку дефолтов, не по мегасловарю.

## Шаг 3: получаем поток

С Digest-аутентификацией:

```
$ ffplay -rtsp_transport tcp "rtsp://admin:admin@10.0.0.20:554/stream1"
```

`ffplay`/`ffmpeg` выполняют DESCRIBE → SETUP → PLAY автоматически. Если поток пошёл — ты внутри. Дальше кадры идут по **RTP** (обычно UDP, часто поверх того же соединения по TCP при `-rtsp_transport tcp`).

## Шаг 4: ONVIF — управление и разведка

**ONVIF** — стандарт управления камерами поверх SOAP/HTTP (порт 80/8080). Он умеет больше, чем RTSP: узнать модель, получить URL потока, настроить, перезагрузить. Основные вызовы:

- `GetDeviceInformation` — производитель, модель, версия прошивки;
- `GetProfiles` — профили (разрешение, кодек);
- `GetStreamUri` — готовый RTSP-URL потока;
- `GetSystemDateAndTime` — **без аутентификации** у многих камер.

Последний пункт — важная деталь: `GetSystemDateAndTime` часто отвечает **до** аутентификации. Это позволяет подтвердить ONVIF и узнать время камеры, не имея учётки.

```
$ curl -s http://10.0.0.20/onvif/device_service \
  -H 'Content-Type: application/soap+xml' \
  --data @getinfo.xml | grep -i 'Manufacturer\|Model'
```

## Шаг 5: ONVIF-аутентификация

ONVIF использует **WS-UsernameToken**: логин, nonce, timestamp и **PasswordDigest** = base64(SHA1(nonce + created + password)). Пароль не уходит открыто, но схема слабая: если nonce и timestamp перехвачены, возможен replay в пределах окна. Плюс часть камер принимает **Basic** для совместимости — а это открытый текст.

## Шаг 6: атаки

Что проверяют на пентесте камер:

- **дефолтные креды** — самый частый вход;
- **открытые потоки** — камеры, отдающие RTSP без аутентификации;
- **Basic-перехват** — сняв трафик, получить base64(user:pass);
- **SSRF через ONVIF** — некоторые вызовы принимают URL, куда камера сама сходит;
- **path traversal** в веб-интерфейсе ONVIF;
- **DoS** — заваливание DESCRIBE/PLAY открывает много сессий.

Инструмент для разведки — `nmap`:

```
$ nmap -p554 --script rtsp-url-brute 10.0.0.20
```

Скрипт перебирает типовые пути (`/stream1`, `/h264`, `/live`) и сообщает, какие отвечают.

## Шаг 7: защита

Что должно быть сделано: сменены дефолтные пароли, RTSP только с Digest/через TLS, ONVIF-интерфейс не выставлен наружу, сегментация камер в отдельный VLAN, отключены лишние сервисы (часто рядом живут telnet/SSH с дефолтами).

## Что мы теперь знаем

- RTSP управляет потоком (OPTIONS/DESCRIBE/SETUP/PLAY).
- DESCRIBE отвечает SDP; медиа идёт по RTP.
- ONVIF — SOAP-управление, умеет выдавать RTSP-URL.
- Частая точка входа — дефолтные учётки и Basic-аутентификация.

## Если не сработало

Если RTSP не отвечает — проверь порт (554, иногда 8554). Если `curl` не умеет RTSP — используй `ffprobe`/`ffplay`. Если ONVIF недоступен — попробуй порт 80/8080 и путь `/onvif/device_service`. Если поток есть, но чёрный — неверный профиль или кодек.

## Разбор SDP из DESCRIBE

После успешного DESCRIBE сервер присылает SDP — текстовое описание потоков. Вот типичный ответ:

```
$ ffprobe -v error -show_streams "rtsp://admin:admin@10.0.0.20:554/stream1"
codec_name=h264
width=1920
height=1080
r_frame_rate=25/1
```

`ffprobe` разбирает SDP и показывает параметры: кодек H.264, 1920×1080, 25 кадров в секунду. Это уже полноценная разведка — ты знаешь качество и кодек, не скачивая видео.

Если смотреть сырой SDP, там будут строки `m=video 0 RTP/AVP 96` (медиапоток), `a=rtpmap:96 H264/90000` (кодек и тактовая частота), `a=control:` (путь потока). Именно из `a=control` берётся URL для SETUP.

## ONVIF-разведка по шагам

ONVIF удобно исследовать по порядку. Сначала — есть ли сервис и какая модель:

```
$ curl -s http://10.0.0.20/onvif/device_service \
  -H 'Content-Type: application/soap+xml' \
  --data-binary @getdeviceinfo.xml | grep -iE 'Manufacturer|Model|FirmwareVersion'
<Manufacturer>Acme</Manufacturer>
<Model>AC-1234</Model>
<FirmwareVersion>1.2.3</FirmwareVersion>
```

Дальше — `GetProfiles`, чтобы увидеть профили, и `GetStreamUri`, чтобы получить готовый RTSP-адрес. Эти вызовы требуют аутентификации, но `GetSystemDateAndTime` часто нет — с него и начинают.

Есть инструменты, которые делают это автоматически: `onvif-cli`, скрипты `nmap`, `wsdls`. Они экономят время на парке камер.

## Сравнение с другими камерами

Разные вендоры по-разному закрывают интерфейсы. У одних ONVIF-порт открыт всем, у других — только с определённых подсетей. У части камер рядом с RTSP живут telnet/SSH с дефолтными паролями, а также веб-интерфейс с уязвимостями (например, path traversal). Поэтому аудит камеры — это не только RTSP/ONVIF, но и полный скан портов.

Полезно смотреть версию прошивки (из ONVIF или веб-интерфейса) и сверять с известными уязвимостями вендора. Часто обновление прошивки — единственный способ закрыть дыру.

## Типичные ошибки

Первая — считать, что DESCRIBE без пароля невозможен: часть камер отдаёт поток анонимно. Вторая — путать RTSP и RTP: первый управляет, второй несёт медиа. Третья — использовать `curl` без `-X` для методов RTSP: синтаксис отличается от HTTP. Четвёртая — забывать, что ONVIF — это SOAP: нужен корректный XML и правильный `Content-Type`.

## Полный цикл RTSP вручную

Разберём сессию по шагам, чтобы увидеть каждый метод. Начнём с DESCRIBE (с Digest-аутентификацией её обычно делает клиент):

```
$ ffprobe -v trace -i "rtsp://admin:admin@10.0.0.20:554/stream1" 2>&1 | grep -E 'DESCRIBE|SETUP|PLAY|200 OK|401'
DESCRIBE rtsp://10.0.0.20:554/stream1 RTSP/1.0
RTSP/1.0 200 OK
SETUP rtsp://10.0.0.20:554/stream1/track1 RTSP/1.0
RTSP/1.0 200 OK
PLAY rtsp://10.0.0.20:554/stream1 RTSP/1.0
RTSP/1.0 200 OK
```

Порядок такой: DESCRIBE получает SDP, SETUP готовит транспорт для каждого потока (в SDP их может быть два — видео и аудио), PLAY запускает. `TEARDOWN` завершает сессию. Обрати внимание на `Session:` — идентификатор сессии; он нужен во всех последующих запросах.

Если видишь `401`, значит нужна аутентификация: посмотри заголовок `WWW-Authenticate` и повтори с Digest.

## Инструменты и стенд

Для практики нужна камера или её эмуляция. Самый безопасный путь — поднять RTSP-сервер из медиафайла: `mediamtx` (бывший rtsp-simple-server) отдаёт поток по RTSP без железа.

```
$ ./mediamtx &
$ ffmpeg -re -stream_loop -1 -i sample.mp4 -c copy -f rtsp rtsp://localhost:8554/stream1
$ ffprobe rtsp://localhost:8554/stream1
```

На этом стенде проверяются все методы, Digest/Basic и даже ONVIF-совместимый интерфейс (у `mediamtx` есть HTTP API). Сними трафик `tcpdump -w rtsp.pcap 'port 554'` и разбери в `tshark` — увидишь SDP и RTP своими глазами.

## ONVIF и WS-Discovery

Камеры умеют объявлять себя сами через **WS-Discovery** — multicast-протокол на UDP 3702. Клиент рассылает `Probe`, камера отвечает `ProbeMatch` со своим адресом и типами.

```
$ tshark -r wsdisco.pcap -Y "wsdd" -T fields -e ip.src -e wsdd.types
10.0.0.20  dn:NetworkVideoTransmitter
```

Так ты находишь все камеры в сегменте, не сканируя порты. Тип `NetworkVideoTransmitter` — это камера, `NetworkVideoDisplay` — монитор. Один multicast-запрос даёт инвентарь видеонаблюдения.

Практический вывод: обнаружение камер не требует даже доступа к их портам — достаточно быть в сегменте. Поэтому сегментация камер в отдельный VLAN важна не меньше, чем смена паролей.

## Шпаргалка по методам RTSP

| Метод | Назначение |
|---|---|
| OPTIONS | список методов |
| DESCRIBE | получить SDP |
| SETUP | подготовить транспорт |
| PLAY | запустить поток |
| PAUSE | пауза |
| TEARDOWN | разорвать сессию |
| GET_PARAMETER | keep-alive/параметры |

Запомни порядок: DESCRIBE → SETUP → PLAY.

## Коды ответов RTSP и что они говорят при разведке

RTSP отвечает первой строкой вида `RTSP/1.0 200 OK` с `CSeq`, который
соответствует номеру запроса. Код ответа — это бесплатный источник информации о
состоянии камеры ещё до аутентификации.

| Код | Значение | Что это значит при разведке |
|---|---|---|
| 200 OK | успех | метод принят, можно продолжать |
| 401 Unauthorized | нужна аутентификация | в `WWW-Authenticate` видно Basic или Digest |
| 403 Forbidden | доступ запрещён | аутентификация прошла, но прав нет |
| 404 Not Found | потока/ресурса нет | угадали URL неверно |
| 405 Method Not Allowed | метод не поддержан | помогает очертить реализацию |
| 454 Session Not Found | сессия истекла | нужно заново SETUP |
| 461 Unsupported Transport | транспорт не поддержан | обычно при неверном RTP-профиле |
| 500 Internal Server Error | ошибка на стороне камеры | иногда следствие нештатного запроса |

Практический порядок действий такой: сначала отправь `OPTIONS` **без**
аутентификации. Многие камеры возвращают список разрешённых методов и заголовок
`Public:`, даже не требуя пароля. Затем `DESCRIBE` по URL потока: ответ `401`
покажет схему аутентификации, а `200` — сразу отдаст SDP с параметрами
кодирования. Если приходит `454`, значит предыдущий SETUP устарел: у большинства
камер сессия живёт 30–60 секунд, и после паузы её нужно создавать заново.
Ответ `461` почти всегда означает, что запрошенный транспорт (`RTP/AVP/TCP`)
камерой не поддержан — попробуй UDP или наоборот.
