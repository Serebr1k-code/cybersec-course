## Вопрос, с которого всё начинается

Тебе дали дамп трафика из локальной сети и просят объяснить, что в нём происходит. Ты открываешь его и видишь кадры с длинными адресами вида `08:00:27:aa:bb:cc` — не IP, не порт, а что-то ещё. Чтобы двигаться дальше (разбирать ARP-спуфинг, MAC-flooding, VLAN hopping), нужно понимать **самый нижний уровень** — как устроен кадр и как коммутатор решает, куда его отправить.

Этот урок — практическая база модуля [`network-module-l2`](network-module-l2). Он опирается на [`network-basics`](network-basics).

## Наш пример: разбираем один кадр

Возьмём один кадр из дампа и посмотрим на него целиком — с MAC-адресами и типом:

```
$ sudo tcpdump -i eth0 -e -nn -c 3
14:22:01.101 08:00:27:aa:bb:cc > 52:54:00:11:22:33, ethertype IPv4 (0x0800), length 74
14:22:01.202 ff:ff:ff:ff:ff:ff > 08:00:27:aa:bb:cc, ethertype ARP (0x0806), length 42
14:22:01.203 52:54:00:11:22:33 > 08:00:27:aa:bb:cc, ethertype IPv4 (0x0800), length 74
```

Первая строка читается так: отправитель `08:00:27:aa:bb:cc`, получатель `52:54:00:11:22:33`, внутри — IPv4. Во второй строке отправитель — `ff:ff:ff:ff:ff:ff` (широковещательный адрес), а внутри ARP. Разберём, из чего вообще состоит такой кадр.

## Шаг 1: поля кадра Ethernet II

Современная сеть использует формат **Ethernet II**:

| Поле | Размер | Назначение |
|---|---|---|
| Preamble + SFD | 8 байт | синхронизация приёмника (не данные) |
| Dst MAC | 6 | адрес получателя |
| Src MAC | 6 | адрес отправителя |
| EtherType | 2 | тип протокола внутри |
| Payload | 46–1500 | данные |
| FCS | 4 | контрольная сумма (CRC-32) |

Поле **EtherType** — то самое, что показал `tcpdump` как `ethertype IPv4`. Частые значения: `0x0800` — IPv4, `0x0806` — ARP, `0x86DD` — IPv6, `0x8100` — VLAN-тег, `0x88CC` — LLDP. Именно по нему приёмник понимает, какому протоколу отдать содержимое.

**FCS** — контрольная сумма. Если она не сходится, кадр **молча отбрасывается**. Отсюда классический эффект «пакет пропал»: на проводе он был, но был битым.

## Шаг 2: типы MAC-адресов

MAC — это 48 бит, записанные как `aa:bb:cc:dd:ee:ff`. Различаются они по двум битам первого октета:

- **unicast** — адрес одного получателя; младший бит первого октета = 0;
- **multicast** (групповой) — младший бит = 1, например `01:00:5e:...` для IPv4-multicast;
- **broadcast** — все единицы: `ff:ff:ff:ff:ff:ff` (второй кадр в нашем примере);
- **локально администрируемый** — второй бит первого октета = 1.

Последний тип — важный для нас. Он означает «адрес задан вручную, а не прошит производителем». Именно поэтому атакующий может выставить себе **любой** MAC — это и есть **MAC spoofing** (подмена MAC-адреса).

Первые три октета (OUI) выдают производителя. По ним в дампе видно, виртуалка перед нами или железо:

```
$ macchanger -l | grep -iE 'vmware|virtualbox'
00:50:56 - VMware, Inc.
08:00:27 - PCS Systemtechnik GmbH (VirtualBox)
```

В нашем дампе `08:00:27` — VirtualBox, `52:54:00` — QEMU/KVM. Обе стороны — виртуальные машины.

## Шаг 3: как коммутатор решает, куда отправить кадр

Коммутатор — устройство уровня L2. Он не смотрит на IP, он работает по MAC и следует трём правилам:

1. **Learning (обучение)** — запомнить пару `Src MAC` ↔ порт, с которого пришёл кадр.
2. **Forwarding (пересылка)** — найти `Dst MAC` в таблице; найден → отдать в нужный порт.
3. **Flooding (заливка)** — если получатель неизвестен, или это broadcast/multicast → разослать во все порты, кроме входного.
4. **Filtering (фильтрация)** — если входной и выходной порт совпадают, кадр отбрасывается.

Таблица `MAC → порт` называется **CAM** (Content-Addressable Memory). Запись в ней «стареет» — если трафика нет, она удаляется (обычно через 300 секунд). Посмотреть её на Linux-бридже:

```
$ bridge fdb show br br0
52:54:00:11:22:33 dev vnet0 master br0
08:00:27:aa:bb:cc dev vnet1 master br0
```

## Шаг 4: почему коммутатор иногда превращается в хаб

Второе правило (flooding) — ключ к большинству L2-атак. Пока коммутатор не знает MAC получателя, он рассылает кадр **всем**. Если злоумышленник переполнит CAM-таблицу поддельными адресами, коммутатор перестанет помнить реальные и начнёт флудить всё подряд — как простой хаб. Это **MAC-flooding**:

```
$ sudo macof -i eth0 -n 100000
$ sudo tcpdump -i eth0 -nn -e 'not arp' -c 5
14:31:02.001 aa:11:22:33:44:55 > 08:00:27:aa:bb:cc, ethertype IPv4 (0x0800), length 74
```

Заметь: кадр адресован конкретному `08:00:27:...`, но пришёл к нам — значит, коммутатор его флудит. Другой признак переполнения — лавина кадров с быстро меняющимися Src MAC.

**Broadcast storm** — родственное явление: при петле без STP широковещательные кадры размножаются экспоненциально и кладут сеть за секунды. Защита — **storm control** (порог на broadcast/multicast/unknown-unicast) и STP.

## Шаг 5: duplex, MTU и прочие грабли

- **Half duplex** — передача по очереди, возможны коллизии; **full duplex** — приём и передача одновременно. Ошибка автосогласования даёт **duplex mismatch** → ошибки CRC и потеря пакетов.
- **Jumbo-кадры** поднимают MTU до 9000 на датацентровых линках. Если один хост шлёт jumbo, а другой нет — крупные кадры молча дропаются, TCP «зависает» на больших данных.

Проверить ошибки и MTU интерфейса:

```
$ ip -s link show eth0 | grep -A1 'RX:'
    RX: bytes  packets  errors  dropped
    1048576    2048     0       0
$ ip link show eth0 | grep mtu
2: eth0: <BROADCAST,MULTICAST,UP> mtu 1500 qdisc fq_codel state UP
```

## Что мы теперь знаем

- Кадр Ethernet II состоит из Dst/Src MAC, EtherType, данных и FCS.
- EtherType говорит, что внутри: `0x0800` IPv4, `0x0806` ARP, `0x8100` VLAN.
- MAC бывает unicast, multicast и broadcast; адрес легко подделать (U/L-бит).
- OUI первых трёх октетов выдаёт производителя — по нему видно виртуалки.
- Коммутатор учится по Src MAC и флудит, когда получатель неизвестен — это основа L2-атак.

## Куда дальше

Теперь мы понимаем кадр и коммутацию. Дальше разберём служебные протоколы, которыми коммутаторы сами рассказывают о себе соседям — LLDP и CDP, готовую карту сети без активного сканирования. А пока запомни: **коммутатор знает только MAC и порт; кто управляет этой таблицей — управляет тем, кто что видит.**

## Где пригодится

- **CTF:** задачи с hex-дампом кадра, поиск вендора по OUI, VLAN-теги.
- **Пентест:** база для MAC-spoofing, MAC-flooding и ARP-атак.
- **SOC:** чтение L2-дампов, детект штормов и дубликатов MAC.
- **Инженерия:** диагностика duplex mismatch и ошибок CRC.
