## Вопрос, с которого всё начинается

Два датацентра соединены **оверлеем** VXLAN. Ты находишься на хосте в DC1, а цель `10.10.10.5` живёт в сегменте DC2, куда прямой IP-доступ закрыт ACL. Но оверлейный трафик между площадками ходит свободно. Можно ли «проехать» внутри инкапсуляции?

Инкапсуляция — основа оверлеев: GRE прячет произвольный протокол в IP, VXLAN строит L2-сеть поверх L3. Для пентестера это способ обойти сегментацию и инъецировать трафик в чужой оверлей, для SOC — источник «невидимых» потоков.

## Наш пример: видим оверлей в дампе

Слушаем наш провод и сразу замечаем подозрительный UDP-трафик:

```
$ sudo tcpdump -i eth0 -nn 'udp port 4789' -c 2
10:20:01.100 10.0.0.2.52341 > 192.0.2.1.4789: VXLAN, flags [I] (0x08), vni 100
10:20:01.101 10.0.0.2.52342 > 192.0.2.1.4789: VXLAN, flags [I] (0x08), vni 100
```

Это VXLAN: Ethernet-кадры, упакованные в UDP-порт 4789, с идентификатором сети **VNI 100**. Внешние адреса — `10.0.0.2` и `192.0.2.1` (это **VTEP**, VXLAN Tunnel Endpoint). А что внутри — сейчас разберём.

## Шаг 1: GRE — базовая инкапсуляция

**GRE** (Generic Routing Encapsulation) — это IP-протокол **47**. Он инкапсулирует любой протокол в IP и **не шифрует**. Поднимаем туннель:

```
$ sudo ip tunnel add gre1 mode gre remote 192.0.2.1 local 10.0.0.2 ttl 64
$ sudo ip link set gre1 up
$ sudo ip addr add 172.16.0.1/30 dev gre1
$ sudo tcpdump -i eth0 -nn 'ip proto 47' -c 2
10.0.0.2 > 192.0.2.1: GREv0, proto IP (0x0800), length 88
```

В дампе видно внешний IP с протоколом 47 и внутри — `proto IP`. GRE-заголовок несёт поле **protocol type**, которое говорит, что именно внутри. GRE часто служит транспортом для других протоколов (например, PPTP) и несёт multicast между сайтами.

## Шаг 2: VXLAN — L2 поверх L3

**VXLAN** инкапсулирует Ethernet-кадры в **UDP/4789**. Устройства на концах туннеля — **VTEP**. Поднимаем VXLAN-интерфейс:

```
$ sudo ip link add vx0 type vxlan id 100 remote 192.0.2.1 dstport 4789 dev eth0
$ sudo ip link set vx0 up
$ sudo bridge fdb append 00:00:00:00:00:00 dev vx0 dst 192.0.2.1
$ tshark -r vx.pcap -Y 'vxlan' -T fields -e vxlan.vni | sort -u
100
```

Заголовок VXLAN — 8 байт:

| Поле | Размер | Смысл |
|---|---|---|
| Flags | 1 | I-бит = VNI валиден |
| Reserved | 3 | зарезервировано |
| VNI | 3 | идентификатор сети (24 бита) |
| Reserved | 1 | зарезервировано |

Именно **VNI** различает сегменты оверлея — аналог VLAN, но в другом пространстве.

## Шаг 3: почему оверлей обходит сегментацию

Ключевой момент: снаружи видны только адреса VTEP. Внутренние адреса (`10.10.10.5`, его MAC) спрятаны внутри инкапсуляции, и ACL по внешнему IP их не фильтрует.

```
$ tshark -r vx.pcap -Y 'vxlan' -V | grep -A2 'Internet Protocol' | head
```

Внутренние адреса проявляются только после разбора. Значит, трафик в оверлее **не матчится** правилами, которые смотрят лишь на внешний IP.

## Шаг 4: инъекция в оверлей

Если ты можешь достучаться до VTEP и знаешь VNI, можно **вложить свой кадр** в инкапсуляцию и доставить его в чужой сегмент. В лаборатории это делается вручную:

```python
from scapy.all import *
pkt = IP(dst="192.0.2.1")/UDP(dport=4789)/VXLAN(vni=100)/Ether()/IP(dst="10.10.10.5")/ICMP()
send(pkt)
```

Внутренний IP `10.10.10.5` атакующий выбирает сам — VTEP распакует кадр и доставит его в сегмент VNI 100, как будто он пришёл оттуда.

## Шаг 5: детект и защита

Оверлеи выдают себя по протоколу и порту. Ищем их и аномальные VNI:

```
$ tshark -r cap.pcap -T fields -e ip.proto | sort | uniq -c | sort -rn | head
$ tshark -r vx.pcap -Y 'vxlan' -T fields -e ip.src -e vxlan.vni | sort | uniq -c | sort -rn
```

| Мера | Против чего |
|---|---|
| Фильтрация UDP/4789 и proto 47 на границе | инъекции извне |
| Аутентификация VTEP (IPsec/MACsec) | MITM/спуфинг |
| Список разрешённых VNI/VTEP | инъекция в чужой оверлей |
| Сегментация под VTEP | lateral movement |
| Мониторинг оверлеев | детект аномалий |

Общий вывод: GRE и VXLAN — мощные оверлеи **без встроенной безопасности**. Их защита целиком ложится на фильтрацию на границе, аутентификацию VTEP и мониторинг VNI.

## Сравнение оверлеев

| Оверлей | Инкапсуляция | Единица | Порт/прото | Шифрование |
|---|---|---|---|---|
| GRE | IP в IP | туннель | 47 | нет |
| VXLAN | Ethernet в UDP | VNI | 4789 | нет |
| Geneve | Ethernet в UDP | VNI | 6081 | нет |
| IP-in-IP | IP в IP | туннель | 4 | нет |
| WireGuard | IP в UDP | peer | 51820 | да |
| IPsec | IP в ESP | SA | 50 | да |

## Что мы теперь знаем

- GRE (proto 47) инкапсулирует произвольный протокол и не шифрует.
- VXLAN несёт Ethernet в UDP/4789, сегменты различает VNI (24 бита).
- VTEP — концы туннеля; внешние ACL не видят внутренние адреса.
- Подделав VNI и VTEP, можно инъецировать кадр в чужой сегмент.
- Защита: фильтрация на границе, аутентификация VTEP, мониторинг VNI.

## Разбираем VXLAN-кадр побайтово

Вернёмся к оверлею. Снаружи пакет выглядит как обычный UDP на порт 4789, но внутри — целый Ethernet-кадр. Разберём его послойно:

```
$ tshark -r vxlan.pcap -Y vxlan -V -c 1 | grep -E 'Outer|Inner|VXLAN Network Identifier|Src|Dst' | head -12
Outer IPv4: 192.0.2.1 -> 192.0.2.2
UDP: 48210 -> 4789
VXLAN Network Identifier (VNI): 101
Inner Ethernet: 08:00:27:aa:bb:cc -> 52:54:00:11:22:33
Inner IPv4: 10.10.10.5 -> 10.10.10.20
```

Читается так: два физических хоста (`192.0.2.1/2`) несут внутри себя трафик «виртуальной» сети (`10.10.10.5/20`). **VNI 101** — это идентификатор оверлея; по нему VTEP-устройства понимают, в какую изолированную сеть отнести кадр. Для внешнего наблюдателя видны только внешние адреса — то, что внутри, скрыто на уровне инкапсуляции, а не шифрования. Это важно: VXLAN **не шифрует** трафик, он его лишь **прячет** от тех, кто не знает про оверлей.

## GRE: что внутри заголовка

У GRE заголовок проще. Посмотрим:

```
$ tshark -r gre.pcap -Y gre -T fields -e ip.src -e ip.dst -e gre.proto -e ip.proto
192.0.2.1  192.0.2.2  0x0800  47
```

`gre.proto 0x0800` говорит, что внутри инкапсулирован IPv4, а `ip.proto 47` — что внешний IP-пакет несёт GRE. Дальше идёт внутренний пакет целиком. GRE удобен для туннелей, но, как и VXLAN, ничего не шифрует — поэтому «GRE поверх IPsec» (GRE+ESP) стал классикой для защиты туннелей.

## Таблица: оверлеи и их транспорты

| Технология | Внешний транспорт | Внутри | Шифрование |
|---|---|---|---|
| GRE | IP proto 47 | любой (L2/L3) | нет (нужен IPsec) |
| VXLAN | UDP/4789 | Ethernet | нет (нужен MACsec/IPsec) |
| GENEVE | UDP/6081 | Ethernet | нет |
| IP-in-IP | IP proto 4 | IPv4 | нет |
| IPsec ESP | IP proto 50 | любой | да |
| WireGuard | UDP | IP | да |

Общее правило: **оверлей сам по себе не защищает**, он только переносит. Защиту даёт либо шифрующий транспорт (IPsec/WireGuard), либо сегментация на VTEP.

## Почему это обходит сегментацию

Ключевой эффект для пентеста: межсетевой экран, настроенный на адреса и порты **физической** сети, ничего не знает про VNI и внутренние `10.10.10.0/24`. Инкапсулированный трафик идёт одним UDP-потоком между двумя VTEP, и внутри него может ехать что угодно. Если атакующий получает доступ к VTEP или к хосту с оверлейным интерфейсом, он оказывается «внутри» всех сетей, которые через этот VTEP проходят.

Практический признак в дампе — UDP/4789 между адресами, которые не являются обычными серверами. Второй признак — MTU-странности: инкапсуляция добавляет 50+ байт, и крупные пакеты начинают фрагментироваться или дропаться.

## Если не сработало: оверлей не виден

Если `tshark` не находит VXLAN, возможны три причины. Первая — **не тот порт**: некоторые реализации используют 8472 (Linux OVS) вместо 4789. Вторая — трафик идёт не через твою точку: VTEP-обмен может быть во внутренней сети, недоступной из твоего сегмента. Третья — **шифрование**: если поверх оверлея поднят IPsec/WireGuard, ты увидишь ESP или UDP-WireGuard, а не VXLAN. Проверь порты 4789/8472/6081 и протокол 47 в фильтре: `tshark -r dump.pcap -Y "udp.port==4789 || udp.port==8472 || ip.proto==47"`.
