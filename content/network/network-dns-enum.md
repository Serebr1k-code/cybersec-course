## Вопрос, с которого всё начинается

Ты разведываешь домен `example.com`. Сканировать порты рано — сначала нужен список **имён**: поддомены указывают на staging-среды, внутренние сервисы и забытые ресурсы, которые ты иначе не найдёшь. Откуда взять эти имена?

Перечисление DNS — первый шаг разведки. Пройдём полный цикл: от зонной передачи до брутфорса и валидации.

## Наш пример: пробуем zone transfer

Самый быстрый способ получить всю зону — **AXFR** (зонная передача). Сначала найдём авторитетные серверы:

```
$ dig example.com NS +short
ns1.example.com.
$ dig AXFR example.com @ns1.example.com
; Transfer failed.
```

Зонная передача закрыта. Часто её разрешают только «своим» вторичным серверам — значит, идём другим путём.

## Шаг 1: пассивные источники

Имена можно собрать, не создавая трафика к цели. **Certificate Transparency** (публичный лог TLS-сертификатов) отдаёт все имена, для которых выпускались сертификаты:

```
$ curl -s 'https://crt.sh/?q=%25.example.com&output=json' | jq -r '.[].name_value' | sed 's/\*\.//' | sort -u
dev.example.com
vpn.example.com
www.example.com
```

Заметь: запросы уходят к `crt.sh`, а не к `example.com` — цель об этом не узнает.

## Шаг 2: проверка wildcard

Прежде чем брутить, надо понять, нет ли **wildcard**-записи (`*.example.com` резолвится на что угодно). Иначе брутфорс выдаст мусор:

```
$ dig +short no-such-$(date +%s).example.com
```

Пусто — wildcard нет, брутфорс осмыслен. Если бы что-то вернулось, пришлось бы фильтровать результаты по «эталонному» wildcard-адресу.

## Шаг 3: брутфорс поддоменов

Теперь подбираем имена по словарю:

```
$ gobuster dns -d example.com -w subdomains-top1million-5000.txt -t 50 -q
www.example.com
mail.example.com
git.example.com
```

`gobuster dns` шлёт DNS-запросы по словарю и печатает только те имена, что резолвятся. `-t 50` — 50 потоков. Для больших объёмов используют `dnsx` и `puredns`.

## Шаг 4: резолвинг и дедупликация

Собираем результаты из пассивного и активного источников и превращаем имена в адреса:

```
$ cat ct.txt brute.txt | sort -u | dnsx -a -resp
dev.example.com [203.0.113.20]
git.example.com [203.0.113.40]
vpn.example.com [203.0.113.30]
```

`dnsx -a -resp` резолвит список имён и показывает ответы. Дедупликация обязательна: `crt.sh` не полон, а брутфорс пересекается с ним.

## Шаг 5: SRV и обратные имена

Иногда быстрее зайти с другой стороны — спросить про сервисы и обратные имена:

```
$ dig _ldap._tcp.example.com SRV +short
0 100 389 dc01.example.com.
$ dnsrecon -r 203.0.113.0/24 | grep PTR
PTR vpn.example.com 203.0.113.30
```

`_ldap._tcp` выдал контроллер домена, а обратный брутфорс (PTR) — имя VPN-хоста. Полезные префиксы для словаря: `dev`, `staging`, `test`, `admin`, `vpn`, `git`, `jenkins`, `api`, `internal`, `old`, `backup`.

## Шаг 6: проверка на takeover

Финальный шаг — проверить найденные CNAME на «повисшие» цели:

```
$ while read h; do c=$(dig +short CNAME $h); [ -n "$c" ] && echo "$h -> $c -> $(dig +short $c)"; done < resolved.txt
dev.example.com -> old-bucket.s3.amazonaws.com. ->
```

Пустой последний элемент — цель не резолвится, ресурс освободился. Это потенциальный **subdomain takeover**: bucket можно занять.

## Мутации и словари

Словарь — не единственный источник имён. Когда базовые поддомены найдены, их **мутируют**: комбинируют префиксы и суффиксы, получая варианты, которых нет ни в одном словаре.

```
$ grep -Eo '^[a-z]+' resolved.txt | sort | uniq -c | sort -rn | head
     12 dev
      8 api
      5 git
```

Здесь видно, что в зоне часто встречается `dev` и `api`. Генерируем кандидатов по этим паттернам:

```
$ for env in dev staging test uat; do for app in api web git; do echo "$env-$app"; echo "$app-$env"; done; done | head
dev-api
api-dev
```

Инструменты вроде `dnsgen` и `altdns` автоматизируют это: они берут известные имена и порождают десятки перестановок (`api-dev`, `dev-api`, `api2`). Так ловятся имена, которых нет в словаре.

| Словарь | Размер | Когда |
|---|---|---|
| subdomains-top1million-5000 | 5000 | быстрый старт |
| subdomains-top1million-110000 | 110k | глубже |
| кастомный | свои префиксы | целевой |

Стратегия: сначала пассивные источники, затем быстрый брутфорс топ-5000, затем мутации по найденным паттернам.

## Детект перечисления

На стороне SOC перечисление видно по аномалиям DNS:

- всплеск **NXDOMAIN** с одного источника — брутфорс;
- много запросов разных имён за короткое время;
- AXFR-запрос от неожиданного клиента;
- обратный брутфорс PTR по диапазону.

```
$ tshark -r cap.pcap -Y 'dns.flags.rcode==3' -T fields -e ip.src | sort | uniq -c | sort -rn | head
$ tshark -r cap.pcap -Y 'dns.qry.type==252' -T fields -e ip.src
```

Второй фильтр (`dns.qry.type==252`) ловит AXFR-запросы. Защита симметрична: закрыть AXFR (`allow-transfer` только для вторичных), включить rate-limiting, убрать лишний wildcard и мониторить NXDOMAIN.

## Чек-лист перечисления

1. Проверен ли wildcard (`dig random...`)?
2. Использованы ли пассивные источники (crt.sh, архивы)?
3. Найден ли AXFR?
4. Прошлись ли по SRV и обратке?
5. Настроен ли rate-limit, чтобы не забанили?
6. Дедуплицированы ли результаты?
7. Проверены ли найденные имена на takeover?

```
$ wc -l resolved.txt
$ cut -d. -f1 resolved.txt | sort | uniq -c | sort -rn | head
```

## Вывод

Перечисление эффективно, когда сочетает пассивные источники, брутфорс, мутации и обратку — и всегда валидирует wildcard. Ключ — дедупликация: без неё результат тонет в мусоре. А защита симметрична: закрыть AXFR, ограничить rate, убрать лишний wildcard, мониторить NXDOMAIN и AXFR-запросы.

И не забывай проверять найденные имена на takeover: dangling CNAME всплывают именно на этапе перечисления, когда ты впервые видишь поддомен, о котором не знал. Поэтому перечисление и аудит записей стоит проводить регулярно, а не один раз при входе в проект.

## Что мы теперь знаем

- AXFR отдаёт всю зону одним запросом — если разрешён.
- Пассивные источники (crt.sh) дают имена без трафика к цели.
- Перед брутфорсом обязательно проверяют wildcard.
- `gobuster dns`/`dnsx`/`puredns` перебирают и резолвят поддомены.
- SRV и PTR раскрывают сервисы и внутренние имена; CNAME проверяют на takeover.

## Реальный прогон: dnsx и gobuster dns

Разберём полный практический прогон перечисления поддоменов на домене `corp.example.com`, чтобы увидеть, как инструменты дополняют друг друга.

Шаг 1. **Пассивный сбор.** До любых активных запросов собираем имена из публичных источников — сертификатных логов, архивов, поисковиков:

```
$ curl -s 'https://crt.sh/?q=%25.corp.example.com&output=json' | jq -r '.[].name_value' | tr ',' '\n' | sort -u > subs.txt
$ wc -l subs.txt
37 subs.txt
```

37 имён — уже неплохая база, но пассивные источники неполны.

Шаг 2. **Активный брутфорс** словарём. `gobuster dns` перебирает имена из списка и резолвит их:

```
$ gobuster dns -d corp.example.com -w /usr/share/seclists/Discovery/DNS/subdomains-top1million-5000.txt -q
www.corp.example.com
api.corp.example.com
staging.corp.example.com
gitlab.corp.example.com
```

Шаг 3. **Дедупликация и резолвинг.** Объединяем пассивные и активные находки и прогоняем через `dnsx`, оставляя только живые:

```
$ cat subs.txt <(gobuster ... -q) | sort -u | dnsx -a -silent
api.corp.example.com [203.0.113.31]
gitlab.corp.example.com [198.51.100.9]
staging.corp.example.com [203.0.113.44]
www.corp.example.com [203.0.113.10]
```

Из 37+5000 кандидатов осталось несколько живых — это и есть карта. Отдельно фиксируем имена, которые есть в источниках, но не резолвятся: кандидаты на dangling CNAME.

Шаг 4. **Проверка wildcard.** Если `*.corp.example.com` резолвится в один и тот же адрес, любой словарь даст «всё подряд»:

```
$ dig +short random-nonsense-123.corp.example.com
203.0.113.10
```

Совпало с адресом `www` — значит, wildcard есть, и результаты брутфорса надо фильтровать: убрать все записи с этим адресом.

Шаг 5. **Takeover-проверка.** Для каждого CNAME смотрим цель и её HTTP-ответ:

```
$ dig +short staging.corp.example.com CNAME
old-staging.s3-website.eu-west-1.amazonaws.com.
$ curl -s -o /dev/null -w '%{http_code}\n' http://staging.corp.example.com
404
```

`404` от S3 с текстом `NoSuchBucket` — почти наверняка захватываемо: бакет освобождён, а CNAME остался. Это находка высокого приоритета.

Шаг 6. **Детект.** Активный брутфорс шумен: тысячи NXDOMAIN в секунду видны в логах резолвера. Тише — пассивные источники плюс медленный прогон по редким именам. Для защищающегося признак атаки — всплеск запросов на несуществующие имена от одного источника; для атакующего — распределение запросов по времени и резолверам, чтобы не попасть в порог алерта.

Итог прогона — не просто список имён, а приоритезированный список: живые сервисы (куда идти дальше), wildcard (что фильтровать) и dangling-кандидаты (что захватывать).

## Что делать с результатами перечисления

Список живых поддоменов — это не отчёт, а вход в следующие этапы. Правильная обработка результатов экономит время на всём пентесте.

**Приоритезация по имени.** Имена вроде `staging`, `dev`, `test`, `old`, `backup` почти всегда менее защищены, чем `www`. `admin`, `vpn`, `jenkins`, `gitlab`, `grafana` — это поверхности с аутентификацией, где стоит проверить дефолтные учётки и известные CVE. Начинайте с них.

**Группировка по адресу.** Несколько имён на одном IP — один хост с виртуальными хостами. Несколько имён на адресах одного провайдера/ASN — одна инфраструктура. Это подсказывает, где искать общий вход.

**Отдельный список dangling.** Имена с CNAME на освобождённые ресурсы (S3, Azure, Heroku, GitHub Pages) — кандидаты на takeover. Их проверяют сразу, потому что захват подтверждается быстро и даёт реальное влияние.

**Отдельный список wildcard.** Если домен отдаёт wildcard-ответ, все «находки» с этим адресом надо вычеркнуть, иначе отчёт раздуется ложными поддоменами.

**Сохранение артефактов.** Итоговые списки (живые имена, адреса, CNAME-цели) фиксируются как артефакты разведки: они понадобятся и при перечислении виртуальных хостов, и при проверке сертификатов, и при составлении scope для последующих сканов. Без них каждый следующий агент будет переделывать ту же работу.
