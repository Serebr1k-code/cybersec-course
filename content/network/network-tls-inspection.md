TLS защищает почти весь современный трафик. В CTF и на пентесте важно уметь: (1) понять параметры TLS без расшифровки, (2) расшифровать трафик, если есть ключ, (3) заметить MITM по сертификату.

## Что защищает TLS

TLS обеспечивает три свойства:

- **Конфиденциальность** — трафик шифруется симметричным ключом (AES/ChaCha20).
- **Целостность** — защита от модификации (AEAD/MAC).
- **Аутентификация** — сервер подтверждает личность сертификатом (и, при mTLS, клиент).

Handshake (упрощённо):

```
Client → Server: ClientHello (версии, шифры, SNI, случайное число)
Server → Client: ServerHello, Certificate, ServerHelloDone
Client → Server: обмен ключами (ECDHE), Finished
Server → Client: Finished
→ дальше симметричное шифрование
```

Начиная с **TLS 1.3** сертификат в ServerHello зашифрован — пассивно его уже не увидеть.

## TLS 1.3 и forward secrecy

Ключевое отличие TLS 1.3 — **forward secrecy** по умолчанию: сессионные ключи выводятся через эфемерный обмен (ECDHE) и **не** могут быть восстановлены из долговременного ключа сервера. Следствия:

- Приватный ключ сервера **не** расшифровывает прошлый трафик (если только не использовался статический RSA key exchange — этого в TLS 1.3 нет).
- Единственный путь к расшифровке — **сессионные ключи** (SSLKEYLOGFILE) или активный MITM.
- Handshake в 1.3 компактнее (1-RTT), сертификат и большинство расширений шифруются.

Это важно понимать: в CTF с TLS 1.3 вы ищете не ключ сервера, а файл ключей клиента.

## Сертификаты: что и зачем

Сертификат X.509 содержит: subject (домен), issuer (кто подписал), публичный ключ, срок действия, SAN (список домённых имён), расширения.

```bash
# получить цепочку сертификатов
openssl s_client -connect example.com:443 -showcerts </dev/null

# разобрать сертификат
openssl s_client -connect example.com:443 </dev/null 2>/dev/null \
  | openssl x509 -noout -text

# только SAN (какие домены покрыты)
openssl s_client -connect example.com:443 </dev/null 2>/dev/null \
  | openssl x509 -noout -ext subjectAltName
```

SAN — золотая жила для разведки: сертификат с wildcard или множеством имён выдаёт другие поддомены. Проверка истечения/самоподписи:

```bash
openssl s_client -connect example.com:443 -verify_return_error </dev/null
```

**Самоподписанный сертификат** в корпоративной сети — классический признак MITM-прослойки (прозрачного прокси).

## Расшифровка TLS

**Способ 1 — SSLKEYLOGFILE (TLS 1.2/1.3).** Если есть возможность задать переменную окружения клиенту (браузер, curl), он запишет сессионные ключи:

```bash
export SSLKEYLOGFILE=/tmp/keys.log
curl https://example.com   # ключи попадут в /tmp/keys.log
```

В Wireshark: **Preferences → Protocols → TLS → (Pre)-Master-Secret log filename** → указать `keys.log`. После этого HTTPS-трафик расшифровывается.

**Способ 2 — приватный RSA-ключ сервера.** Работает только для старых шифров без (EC)DHE (RSA key exchange). В Wireshark: TLS → RSA keys list → добавить `ip:port,protocol,keyfile`.

```bash
# конвертировать ключ
openssl rsa -in server.key -out server_dec.key
```

Для современных ECDHE-шифров приватный ключ сервера НЕ помогает — нужен SSLKEYLOGFILE.

**Способ 3 — MITM-прокси** (mitmproxy) с подменой сертификата: расшифровывает трафик «на лету», но требует доверия к CA прокси на клиенте.

## Инспекция без расшифровки

Даже без ключей видно многое:

- **SNI** в ClientHello — какой домен запрашивается (TLS 1.2 в открытом виде; в 1.3 — опционально).
- **JA3/JA3S** — хеш параметров ClientHello/ServerHello, фингерпринт клиента (полезно для детекта malware).
- **Размеры и тайминги** — метаданные, иногда выдающие содержимое (padding/анализ трафика).
- **DNS-запросы** — если не DoH/DoT, они открыты и показывают, куда идёт клиент.

```bash
tshark -r cap.pcap -Y 'tls.handshake.type==1' -T fields -e tls.handshake.extensions_server_name
```

## JA3/JA4: фингерпринтинг клиентов

Отпечаток TLS-клиента строится из параметров ClientHello (версии, шифры, расширения, эллиптические кривые). Одинаковый JA3 — вероятно, одна и та же библиотека/приложение:

- **Malware detection**: редкий JA3 у «браузера» — подозрительно.
- **Fingerprinting сервисов**: разные JA3 у разных бэкендов.
- **Обход**: некоторые инструменты подделывают JA3, чтобы выглядеть как браузер.

```bash
tshark -r cap.pcap -Y 'tls.handshake.type==1' -T fields \
  -e ip.src -e tls.handshake.ja3
```

## Практический разбор

Задача: в PCAP есть HTTPS-сессия, нужно понять, что передавалось.

1. `tshark -r cap.pcap -Y 'tls' -T fields -e tls.handshake.extensions_server_name` → узнаём домен (SNI).
2. `openssl s_client -connect <ip>:443 -servername <sni>` → смотрим сертификат, SAN, issuer (MITM?).
3. Если есть `SSLKEYLOGFILE` → подключаем в Wireshark → видим HTTP внутри.
4. Если ключа нет → анализируем метаданные: JA3, размеры, тайминги, DNS.
5. Для TLS 1.3 — помним, что сертификат скрыт, и SNI может быть зашифрован (ECH).

## Инструменты и флаги

| Инструмент | Назначение |
|---|---|
| `openssl s_client` | ручное TLS-соединение, сертификат |
| `openssl x509 -text` | разбор сертификата |
| `tshark -Y 'tls'` | фильтры по TLS-полям |
| Wireshark + SSLKEYLOGFILE | расшифровка |
| `mitmproxy` | активный MITM-прокси |
| `testssl.sh` | аудит конфигурации TLS |

## Частые ошибки

- **`SSLKEYLOGFILE` задан слишком поздно.** Переменная должна быть установлена ДО запуска клиента, и клиент обязан её поддерживать (браузеры, curl — да; часть библиотек — нет).
- **Пытаться расшифровать ECDHE/TLS 1.3 приватным ключом сервера.** Из-за forward secrecy это не сработает — нужны ключи сессии (SSLKEYLOGFILE).
- **Путать типы обмена ключами.** Приватный ключ RSA расшифровывает только RSA key exchange, а не эфемерные (DHE/ECDHE) сессии.
- **Забывать про TLS 1.3-шифрование handshake.** Сертификат и SNI могут быть не видны пассивно.

## Что делать дальше / решение

- **Нужны поддомены** → SAN из сертификатов (`openssl s_client`).
- **Нужно содержимое** → SSLKEYLOGFILE (или mitmproxy при активном тесте).
- **Нужен MITM-детект** → самоподписанный/чужой issuer.
- **Нужен фингерпринт** → JA3/JA4.

## Частые сценарии CTF и IR

В CTF и при разборе инцидентов TLS встречается в типовых задачах:

- **«Расшифруй HTTPS в PCAP»** → ищите рядом файл `sslkeylog`/`keys.log` (иногда он спрятан в архиве или отдан вместе с дампом); подключаете его в Wireshark и читаете HTTP.
- **«Что за домен?»** → SNI из ClientHello; если TLS 1.3 и SNI зашифрован — смотрите DNS или сертификат при активном соединении.
- **«Есть ли MITM?»** → сравниваете issuer сертификата с ожидаемым; самоподписанный или корпоративный CA = прослойка.
- **«Извлеки данные»** → после расшифровки — HTTP/WebSocket/кастомный протокол поверх TLS.
- **«Поддельный сертификат»** → сверяете SAN, срок, цепочку; часто флаг в подписи/issuer.

Порядок: определить версию TLS → найти SNI → проверить сертификат → искать ключи → расшифровать → разобрать прикладной протокол.

## Быстрая шпаргалка

```bash
# сертификат и SAN
openssl s_client -connect host:443 -servername host </dev/null 2>/dev/null \
  | openssl x509 -noout -text | grep -A1 'Subject Alternative Name'
# SNI из PCAP
tshark -r cap.pcap -Y 'tls.handshake.type==1' -T fields -e tls.handshake.extensions_server_name
# расшифровка
export SSLKEYLOGFILE=/tmp/keys.log   # ДО запуска клиента
# Wireshark: Preferences → Protocols → TLS → (Pre)-Master-Secret log
```

Запомните: TLS 1.3 прячет сертификат, forward secrecy убивает «расшифровку ключом сервера», а SNI/JA3 остаются видимыми метаданными.
