## Вопрос, с которого всё начинается

В прошлых уроках мы разбирали трафик `tcpdump`-ом и видели HTTP в открытом виде. Но сегодня почти весь трафик — это **HTTPS**, то есть HTTP, завёрнутый в шифрование **TLS**. Открываешь такой pcap в Wireshark — и вместо запросов видишь только строки `Application Data` и `Encrypted Handshake Message`.

Как вообще понять, что там внутри, если всё зашифровано? Ответ зависит от того, что у тебя есть: иногда достаточно **сертификата**, иногда нужны **ключи сессии**, а иногда ничего не расшифруешь, но метаданные всё равно расскажут историю.

## Наш пример: дамп https.pcap

У нас есть `https.pcap`, где клиент `10.0.0.5` ходил на сайт. Первым делом — что вообще за домен:

```
$ tshark -r https.pcap -Y 'tls.handshake.type==1' -T fields -e ip.src -e tls.handshake.extensions_server_name
10.0.0.5	files.example.com
```

Поле `tls.handshake.extensions_server_name` — это **SNI** (Server Name Indication), имя запрашиваемого домена, которое клиент передаёт в первом сообщении **ClientHello**. Вот ключевой факт: даже без расшифровки мы уже знаем, куда клиент шёл.

## Шаг 1: что защищает TLS

TLS даёт три свойства, и полезно держать их в голове:

- **Конфиденциальность** — содержимое шифруется симметричным ключом (AES/ChaCha20).
- **Целостность** — защита от подмены (AEAD/MAC).
- **Аутентификация** — сервер доказывает личность **сертификатом**.

Соединение начинается с **handshake** — рукопожатия, где стороны договариваются о версии, шифрах и ключах. Упрощённо:

```
Client → Server: ClientHello (версии, шифры, SNI, случайное число)
Server → Client: ServerHello, Certificate, ServerHelloDone
Client → Server: обмен ключами (ECDHE), Finished
Server → Client: Finished
→ дальше симметричное шифрование
```

Обрати внимание: начиная с **TLS 1.3** всё после ServerHello шифруется — включая сертификат. Значит, пассивно «подсмотреть» его уже не получится.

## Шаг 2: смотрим сертификат и вытаскиваем SAN

Сертификат — это удостоверение сервера. В нём: домен (**subject**), кто подписал (**issuer**), публичный ключ, срок действия и — самое интересное для разведки — **SAN** (Subject Alternative Name), список всех домённых имён, которые сертификат покрывает.

Подключимся к серверу вручную через `openssl s_client` и попросим показать только SAN:

```
$ openssl s_client -connect files.example.com:443 -servername files.example.com </dev/null 2>/dev/null \
  | openssl x509 -noout -ext subjectAltName
X509v3 Subject Alternative Name:
    DNS:files.example.com, DNS:cdn.example.com, DNS:api.example.com
```

Вот и поддомены: `cdn.example.com` и `api.example.com`. Один сертификат выдал нам новые цели — классический приём разведки.

А теперь проверим, кто подписал сертификат:

```
$ openssl s_client -connect files.example.com:443 </dev/null 2>/dev/null | openssl x509 -noout -issuer
issuer=C = US, O = Let's Encrypt, CN = R3
```

`Let's Encrypt` — норма. Но если бы здесь стоял **самоподписанный** сертификат или неизвестный корпоративный CA — это тревожный признак **MITM** (man-in-the-middle, «человек посередине»): кто-то вставил свою прослойку и подменяет сертификат.

## Шаг 3: расшифровка через SSLKEYLOGFILE

Если нужен не домен, а содержимое, понадобятся ключи. В современном TLS 1.3 включён **forward secrecy** (прямая секретность): сессионные ключи выводятся из эфемерного обмена **ECDHE** и не восстанавливаются из долговременного ключа сервера. Поэтому приватный RSA-ключ сервера тут не поможет — нужен файл сессионных ключей клиента.

Его пишет сам клиент, если задать переменную окружения `SSLKEYLOGFILE` **до** запуска:

```
$ export SSLKEYLOGFILE=/tmp/keys.log
$ curl https://files.example.com/secret.zip -o /dev/null
$ head -1 /tmp/keys.log
CLIENT_RANDOM 5c8a... 9f3b...
```

Файл `/tmp/keys.log` — это и есть «ключ ко всему». В Wireshark его подключают через **Preferences → Protocols → TLS → (Pre)-Master-Secret log filename**, после чего Wireshark расшифровывает HTTPS и показывает обычный HTTP внутри.

```
$ tshark -r https.pcap -o tls.keylog_file:/tmp/keys.log -Y 'http.request' \
    -T fields -e http.host -e http.request.uri
files.example.com	/secret.zip
```

Так мы увидели путь `/secret.zip`, который был скрыт за шифрованием.

## Шаг 4: когда ключа нет — читаем метаданные

Ключей может не быть. Но и без расшифровки видно много:

- **SNI** — домен (если TLS 1.3 без шифрования SNI/ECH).
- **JA3** — хеш параметров ClientHello, отпечаток клиента.
- **Размеры и тайминги** пакетов — по ним иногда угадывают содержимое.
- **DNS-запросы** — если они не через DoH/DoT, показывают, куда идёт клиент.

**JA3** строится из версии, списка шифров, расширений и кривых в ClientHello. Одинаковый JA3 — вероятно, одна и та же библиотека:

```
$ tshark -r https.pcap -Y 'tls.handshake.type==1' -T fields -e ip.src -e tls.handshake.ja3
10.0.0.5	cd08e31494f9531f560d64c695473da9
```

Редкий JA3 у «браузера» — подозрительно (так ловят malware), а инструменты вроде `curl` можно настраивать подделывать JA3 под Chrome.

## Шаг 5: старый способ — ключ сервера

Есть и второй путь: приватный ключ сервера. Но он работает **только** для старых шифров с обменом RSA (без DHE/ECDHE). В Wireshark: TLS → RSA keys list → добавить `ip:port,protocol,keyfile`.

```
$ openssl rsa -in server.key -out server_dec.key
```

Для современных ECDHE-сессий и TLS 1.3 этот способ **не работает** — forward secrecy специально устроена так, чтобы утечка ключа сервера не раскрывала прошлый трафик.

## Шаг 6: активный MITM вместо расшифровки

Иногда пассивного дампа мало и ключей нет. Тогда TLS вскрывают **активно**: ставят прокси между клиентом и сервером, который подменяет сертификат своим. Инструмент `mitmproxy` делает это «на лету»:

```
$ mitmproxy --mode transparent --showhost
```

Прокси устанавливает с клиентом своё TLS-соединение (подписанное его CA), а с сервером — отдельное. Всё расшифровывается на лету. Условие одно: клиент должен **доверять** CA прокси — в корпоративных сетях его ставят в хранилище через GPO. Именно поэтому самоподписанный или корпоративный issuer в сертификате — маркер такой прослойки.

## Что мы теперь знаем

По-простому:

1. TLS шифрует трафик, но SNI (домен) часто виден в открытом виде.
2. Сертификат даёт SAN — список домённых имён, и issuer — признак MITM.
3. Для расшифровки современного TLS нужны **сессионные ключи** из `SSLKEYLOGFILE`, а не ключ сервера.
4. Без ключей остаются метаданные: SNI, JA3, размеры, DNS.
5. В TLS 1.3 сертификат зашифрован, а приватный ключ сервера бесполезен из-за forward secrecy.

## На что смотреть дальше

- **Проверь issuer.** Неожиданный CA или самоподпись — признак корпоративной MITM-прослойки.
- **Ищи файл ключей рядом с дампом.** В CTF `sslkeylog`/`keys.log` часто прячут в том же архиве.
- **Помни про ECH.** В новых версиях SNI тоже шифруется — тогда остаётся только DNS и сертификат активного соединения.

## Разбираем сертификат из дампа

Вернёмся к нашему `https.pcap`. Даже без ключей в TLS-handshake **открыто** идёт сертификат сервера. Извлечём его и посмотрим поля:

```
$ tshark -r https.pcap -Y "tls.handshake.type==11" -T fields \
  -e x509sat.uTF8String -e x509ce.dNSName -e x509af.notBefore -e x509af.notAfter -c 1
CN=shop.example.com   shop.example.com,www.shop.example.com   2024-01-10   2025-01-09
```

Читается так: сертификат выдан на `shop.example.com`, покрывает ещё `www.shop.example.com`, действует год. Из этого — без расшифровки — уже понятно, **какой сайт** посещают и какая у него инфраструктура. Колонка SAN (`dNSName`) особенно полезна: она перечисляет все домены, которые «знает» этот сертификат, — то есть дополнительные хосты для разведки.

## Что видно без ключа, а что нет

| Данные | Без ключа | С ключом |
|---|---|---|
| SNI | да | да |
| Сертификат (CN, SAN, срок) | да | да |
| Версия TLS, шифры | да | да |
| Заголовки HTTP | нет | да |
| Тело (пароли, токены) | нет | да |
| Размер ответа | приблизительно | точно |

Ключевой вывод: **метаданные открыты всегда**. Даже при идеальном шифровании пассивный наблюдатель знает, куда идут соединения и какой сертификат используется.

## Расшифровка через SSLKEYLOGFILE

Если у тебя есть доступ к клиенту, самый простой путь — заставить его писать ключи:

```
$ SSLKEYLOGFILE=/tmp/keys.log firefox &
$ tshark -r https.pcap -o tls.keylog_file:/tmp/keys.log -Y http
GET /login HTTP/1.1
Host: shop.example.com
```

Так виден весь HTTP поверх TLS — включая заголовки и формы. Это работает для TLS 1.2 и 1.3 (в 1.3 через key log берутся session-ключи).

## Если не сработало: ключ есть, а не расшифровывается

Причины. Первая — **несовпадение версии**: ключи от TLS 1.3 не расшифруют сессию TLS 1.2, и наоборот. Вторая — ключ взят **после** начала сессии: key log должен писаться с момента старта клиента. Третья — используется **PFS без лога** (тогда ключ сервера бесполезен). Четвёртая — трафик идёт через **QUIC**, и нужен `-d udp.port==443,quic` плюс тот же keylog. Пятая — пакеты **не собраны полностью** (потеряны сегменты) — `tshark` не может reassemble.

## Старый способ: приватный ключ сервера

Если есть **приватный ключ** сервера (RSA), можно расшифровать сессии с RSA key exchange (без PFS). Для этого в Wireshark указывают `RSA keys list`:

```
$ tshark -r https.pcap -o tls.keys_list:"10.0.0.20,443,http,server.key" -Y http
```

Но у современного TLS 1.3 и ECDHE этот способ **не работает** — потому что сессионные ключи не выводятся из ключа сервера. Это и есть смысл Perfect Forward Secrecy: украденный ключ не открывает прошлые сессии.

## Куда дальше

В следующем уроке мы разберём протокол **QUIC** — «TLS поверх UDP», где всё устроено ещё необычнее. А пока главное запомни: TLS прячет содержимое, но SNI, SAN и issuer часто выдают достаточно, чтобы понять, что происходит.

## Где пригодится

- Расшифровка HTTPS — ключевой навык разбора защищённого трафика в CTF и IR.
- Анализ сертификатов — источник поддоменов и индикатор MITM в корпоративных сетях.
