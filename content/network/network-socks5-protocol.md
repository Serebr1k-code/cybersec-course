## Вопрос, с которого всё начинается

У тебя есть доступ к SOCKS5-прокси. Через него кто-то ходит во внутреннюю сеть. Дамп есть, но он не текстовый: в нём бинарные байты. Как понять, **куда** именно прокси открывал соединения и под каким пользователем?

SOCKS5 — второй по счёту протокол в этом модуле, где граница сообщения задаётся **явной длиной поля**, а не переводом строки. Он опирается на [`network-tcpip`](network-tcpip) и [`network-module-proto-wire`](network-module-proto-wire).

## Наш пример: SOCKS5-сессия в hex

Держи дамп одного соединения клиент → прокси (порт 1080):

```
05 01 00                     # приветствие клиента
05 00                        # ответ прокси
05 01 00 03 0d 696e7465726e616c2e636f72702e6c6f63616c 00 50
```

Пока это просто байты. Разберём их по шагам.

## Шаг 1: зачем SOCKS, если есть HTTP-прокси

HTTP-прокси понимает только HTTP. А если нужно проксировать произвольный TCP (SSH, RDP, базу данных)? Для этого придумали **SOCKS** — прокси на уровне транспортного соединения: клиент говорит «соедини меня с хост X:порт Y», и прокси просто перекладывает байты. Версия 5 работает и с TCP, и с UDP.

## Шаг 2: приветствие и выбор метода

Первое, что шлёт клиент, — **greeting**:

```
05 01 00
│  │  └─ METHODS: один метод — 0x00 (без аутентификации)
│  └──── NMETHODS: 1
└─────── VER: 5
```

Прокси выбирает один из предложенных методов и отвечает двумя байтами `05 00` (версия 5, выбран метод 0x00). Методы: `0x00` — no-auth, `0x01` — GSSAPI, `0x02` — логин/пароль, `0x03` — устаревший CHAP.

## Шаг 3: запрос CONNECT

После рукопожатия клиент шлёт **запрос**:

```
05 01 00 03 0d 696e7465726e616c2e636f72702e6c6f63616c 00 50
│  │  │  │  │  └─ DST.ADDR: домен "internal.corp.local"
│  │  │  │  └──── ATYP: 3 = доменное имя
│  │  │  └─────── RSV: 0
│  │  └────────── CMD: 1 = CONNECT
│  └───────────── VER: 5
└──────────────── CMD-байт: 0x01
```

За доменом идёт 2-байтовый порт `00 50` = 80. Команды: `CONNECT` (1) — установить TCP-соединение, `BIND` (2) — принять входящее, `UDP ASSOCIATE` (3) — открыть UDP-релей. Ответ прокси начинается с `05 00 00 01 <bind-addr> <bind-port>`: REP=0 значит «успех».

## Шаг 4: UDP ASSOCIATE

Для UDP (например, DNS через прокси) клиент шлёт `CMD=3`. Прокси отвечает адресом и портом **релей-сокета**, куда клиент шлёт UDP-датаграммы, обёрнутые в SOCKS5-заголовок. Это популярный путь для туннелирования DNS и игрового трафика.

## Полный прогон: разбираем дамп

```
$ cat socks.log
05 01 00
05 00
05 01 00 03 dst:bnRve3MwY2s1X2Mwbm4zY3RfMW50M3JuNGx9 00 50
$ grep dst: socks.log | cut -d: -f2
bnRve3MwY2s1X2Mwbm4zY3RfMW50M3JuNGx9
$ grep dst: socks.log | cut -d: -f2 | base64 -d
nto{s0ck5_c0nn3ct_1nt3rn4l}
```

Мы нашли в запросе CONNECT адрес назначения (в логе он подписан как `dst:` в base64) и декодировали флаг. Запиши его в `answer.txt` и набери `check`.

## Что мы теперь знаем

- SOCKS5 — бинарный протокол; границы полей заданы явной длиной.
- Сессия: greeting (VER, NMETHODS, METHODS) → выбор метода → запрос (CMD, ATYP, DST.ADDR, DST.PORT).
- CMD: CONNECT (1), BIND (2), UDP ASSOCIATE (3).
- Метод `0x00` — без аутентификации; `0x02` — логин/пароль.

## Шаг 5: как выглядит ответ прокси

На запрос CONNECT прокси отвечает по той же схеме «VER + REP + RSV + ATYP + BND.ADDR + BND.PORT». Поле **REP** — код результата:

| REP | Значение |
|-----|----------|
| 0x00 | succeeded |
| 0x01 | general SOCKS server failure |
| 0x02 | connection not allowed by ruleset |
| 0x03 | network unreachable |
| 0x04 | host unreachable |
| 0x05 | connection refused |
| 0x07 | command not supported |
| 0x08 | address type not supported |

`BND.ADDR`/`BND.PORT` — адрес, с которого прокси пошёл к цели. Атакующему он интересен: по нему видно исходящий интерфейс прокси и иногда топологию внутренней сети. Если REP не ноль, соединение не установлено, и это тоже сигнал: например, `0x02` означает, что правило доступа прокси запретило адрес — то есть прокси используется как фильтр.

## Шаг 6: аутентификация по логину/паролю

Если прокси выбирает метод `0x02`, начинается отдельный обмен по RFC 1929. Клиент шлёт подnegotiation-сообщение:

```
01 <ulen> <uname> <plen> <passwd>
```

Первый байт — версия sub-negotiation (всегда `01`), затем длина и имя пользователя, затем длина и пароль. Всё — **открытым текстом**, без шифрования. Прокси отвечает двумя байтами: `01 00` — успех, `01 01` — неверные данные. Это важный вывод: SOCKS5 сам по себе не шифрует ни пароль, ни трафик. Если нужно шифрование, его кладут сверху (TLS, SSH) или используют SOCKS-over-TLS.

## Разбор реального дампа: от приветствия до соединения

Разберём полную сессию с ошибкой, чтобы увидеть обе ветки:

```
$ cat socks.log
05 02 00 02          # greeting: 2 метода — no-auth и user/pass
05 02                # прокси выбрал user/pass
01 05 61646d696e 06 736563726574   # admin / secret
01 00                # аутентификация успешна
05 01 00 03 dst:... 00 50          # CONNECT к домену, порт 80
05 00 00 01 0a000005 1f90          # успех, bind 10.0.0.5:8080
```

Здесь видно всё сразу: два предложенных метода, выбранный метод, учётные данные в открытом виде и успешный CONNECT. В логе адрес цели подписан `dst:` и закодирован, чтобы при разборе приходилось декодировать байты.

## Инструменты: как ходить и как перехватывать

- `curl --socks5 127.0.0.1:1080 http://internal/` — HTTP через SOCKS5 с локальным резолвом;
- `curl --socks5-hostname 127.0.0.1:1080 ...` — резолв имени **на стороне прокси**;
- `ssh -D 1080 user@host` — поднять SOCKS5-прокси динамическим форвардингом;
- `proxychains4 -f proxychains.conf curl ...` — завернуть произвольный клиент в SOCKS;
- `tshark -r dump.pcap -Y socks` — отфильтровать SOCKS-трафик.

Отдельно про DNS: при `--socks5` имя резолвит клиент, и утечка идёт мимо прокси; при `--socks5-hostname` — прокси. Это различие важно и для приватности, и для пентеста: видно, кто и куда ходит.

## SOCKS4 против SOCKS5

Предыдущая версия, **SOCKS4**, умела только TCP и только IPv4. Её запрос был проще: версия (`4`), команда `CONNECT`, порт и IP — и всё. Не было ни списка методов аутентификации, ни доменных имён, ни UDP. **SOCKS4a** добавила доменные имена через «фиктивный» IP `0.0.0.x`, а **SOCKS5** переписала протокол целиком: методы аутентификации, ATYP (IPv4/IPv6/домен), UDP ASSOCIATE.

Практический вывод при разборе дампа: если после установки TCP сразу идёт `04 01 <port> <ip> <user>\0`, это SOCKS4; если `05 ...` — SOCKS5. Понимая разницу, ты не спутаешь версии и правильно найдёшь поле адреса.

## Ограничения и типовые ошибки реализации

SOCKS5 сам по себе **не шифрует** трафик и не даёт аутентификации «из коробки» кроме простого логина/пароля в открытом виде. Отсюда частые ошибки:

- **утечка DNS** — при локальном резолве имена уходят мимо прокси;
- **отсутствие аутентификации** — метод `0x00` оставляет прокси открытым (классическая находка: открытый SOCKS5-прокси для анонимного pivoting);
- **неполная поддержка UDP** — некоторые прокси принимают `UDP ASSOCIATE`, но не релеют данные;
- **проверка только VER** — прокси, который не проверяет RSV/ATYP, можно смутить нестандартными запросами.

Для пентеста открытый SOCKS5-прокси — это готовый вход во внутреннюю сеть: он сам резолвит имена и ходит от своего IP, скрывая атакующего.

## Практический чек-лист разбора SOCKS5

1. **Отдели SOCKS от полезной нагрузки.** `tshark -r dump.pcap -Y socks` покажет только управляющие сообщения.
2. **Прочитай приветствие.** Версия должна быть `05`, дальше — число и список методов. Метод `0x00` без аутентификации — сразу находка.
3. **Найди выбранный метод.** Два байта ответа: `05 <метод>`. Если метод `0x02`, дальше идёт логин/пароль открытым текстом.
4. **Разбери запрос.** CMD (CONNECT/BIND/UDP ASSOCIATE), ATYP (1/3/4), адрес и порт. Адрес назначения — главный результат разбора.
5. **Проверь REP в ответе.** `0x00` — успех; остальные коды подскажут, что запрещено правилами прокси.
6. **Смотри DNS.** Если имена резолвит клиент, DNS-запросы идут отдельно от прокси — это и есть утечка.

Итог разбора — таблица «кто, через какой прокси, куда ходил». Для пентеста это карта внутренних целей, доступных через прокси; для SOC — список несанкционированных прокси в сети.

## Итог: почему SOCKS5 важен для пентеста

SOCKS5 — это мост между «снаружи» и «внутри». Взломщик, получивший доступ к хосту с открытым SOCKS5-прокси, превращает его в точку pivoting: все запросы идут от имени прокси, имена резолвит сам прокси, а внутренние сервисы видят соединение с легитимного адреса. Именно поэтому открытый SOCKS5-прокси — самостоятельная критичная находка.

При разборе дампа важно ответить на три вопроса: **кто** пользовался прокси (метод аутентификации и логин), **куда** он ходил (адреса из CONNECT) и **что** это дало (успешные соединения по REP=0). Ответы складываются в карту внутренней сети, доступной через прокси, — ровно то, что нужно для планирования lateral movement.

Для защищающейся стороны выводы не менее конкретны: прокси должны требовать аутентификацию (метод `0x02` как минимум, лучше — поверх TLS), логировать адреса назначения и не резолвить имена в обход внутренних политик. А появление SOCKS5 там, где его не должно быть, — сигнал компрометации.
