UDP — минимальный транспорт: 8 байт заголовка, никакого состояния. Эта простота даёт скорость и одновременно открывает двери для спуфинга и амплификации. Понимание UDP обязательно и для сканирования сервисов (DNS, SNMP, NTP), и для защиты от DDoS. Урок продолжает [`network-module-ip`](network-module-ip).

## Заголовок UDP

```text
+----------------+----------------+--------+----------+
| Source Port(2) | Dest Port(2)   | Length | Checksum |
+----------------+----------------+--------+----------+
```

Всё. Нет флагов, нет sequence/ack, нет соединения. Приложение само решает, как обеспечивать надёжность (или не обеспечивать).

```bash
# Разбор UDP-пакета
tcpdump -i eth0 -nn -v -c 3 'udp'
```

## Почему спуфинг источника тривиален

Так как UDP не устанавливает соединение, сервер просто отвечает на **src-адрес из пакета**. Подделать его можно свободно — ответ уйдёт жертве, а не атакующему. Именно поэтому:

- UDP-амплификация работает (запрос мал, ответ велик);
- UDP-скан неоднозначен (нет SYN/RST);
- UDP-сервисы часто защищают случайным transaction ID/портом.

## Амплификация и отражение

Схема: атакующий шлёт маленький запрос с **поддельным src = жертва**. Сервер отвечает большим ответом жертве. Коэффициент усиления = размер ответа / размер запроса.

| Протокол | Порт | Коэффициент | Замечание |
|---|---|---|---|
| DNS | 53 | 50–100× | `ANY`, большие TXT |
| NTP | 123 | 500×+ | `monlist` (устаревшая уязвимость) |
| memcached | 11211 | до 50000× | UDP включён по ошибке |
| SSDP | 1900 | ~30× | UPnP-устройства |
| SNMP | 161 | ~6× | GetBulk |
| CharGen | 19 | ~350× | устарел |
| DNS (RRSIG) | 53 | высокий | DNSSEC-ответы |

```bash
# Проверить, отвечает ли DNS на ANY (лаборатория, только свой сервер)
dig ANY example.com @10.0.0.53
# NTP monlist (устаревшие серверы)
ntpdc -n -c monlist 10.0.0.1
```

## UDP-сканирование

UDP-скан сложнее TCP: нет рукопожатия, статус выводится из ICMP port unreachable (закрыт) или отсутствия ответа (открыт/фильтруется).

```bash
# Быстрый UDP-скан топ-портов
sudo nmap -sU --top-ports 50 10.0.0.1
# Комбинированный TCP+UDP
sudo nmap -sS -sU -p T:22,80,443,U:53,123,161 10.0.0.1
# Признак открытого UDP-порта — ответ приложения
nmap -sU -p 161 --script snmp-info 10.0.0.1
```

Ключевая проблема: rate-limiting ICMP и потеря пакетов дают ложные «open|filtered». Используйте `--version-intensity` и повторные попытки.

## UDP-протоколы и их роль

- **DNS (53)** — разрешение имён, туннели, амплификация.
- **DHCP (67/68)** — назначение адресов.
- **NTP (123)** — время, амплификация.
- **SNMP (161/162)** — управление устройствами.
- **TFTP (69)** — передача файлов без аутентификации.
- **QUIC (443/udp)** — современный транспорт.
- **RTP (16384+)** — голос/видео.
- **mDNS (5353)** — локальное обнаружение.

```bash
# Одним дампом посмотреть UDP-порты
tshark -r cap.pcap -Y 'udp' -T fields -e udp.srcport -e udp.dstport | sort | uniq -c | sort -rn | head
```

## Спуфинг и сессионные протоколы

Некоторые UDP-протоколы (DNS, NTP, RADIUS) используют транзакционные идентификаторы. Если они предсказуемы, возможен **off-path спуфинг**: атакующий угадывает ID+порт и подсовывает ответ. Защита — случайные ID/порт (source port randomization).

```bash
# Оценить предсказуемость DNS txid (для своего резолвера)
for i in $(seq 1 20); do dig +short +noall +comments @10.0.0.53 test.local | grep -o 'id: [0-9]*'; done
```

## Детект амплификации и аномалий

- **Огромные ответы от публичных сервисов** на маленькие запросы;
- **много запросов с одного src на разные серверы** (отражение);
- **несоответствие src-порта и ожидаемого** (спуфинг);
- **всплеск UDP на 53/123/11211** — амплификация.

```bash
# Соотношение размеров запрос/ответ для DNS
tshark -r cap.pcap -Y 'dns' -T fields -e udp.length | sort -n | tail
# Топ dst-портов по числу пакетов
tshark -r cap.pcap -Y 'udp' -T fields -e udp.dstport | sort | uniq -c | sort -rn | head
```

## Защита

| Мера | Против чего |
|---|---|
| Отключить неиспользуемые UDP-сервисы | амплификация (memcached, chargen) |
| Rate-limit по протоколам | флуд/амплификация |
| BCP38 (anti-spoofing на периметре) | подделка src |
| Source port randomization | off-path спуфинг |
| Не открывать memcached/SSDP наружу | гигантское усиление |
| Мониторинг ответов > запросов | детект отражения |

## Частые ошибки

- **Считать UDP-скан надёжным** — статус «open|filtered» неоднозначен.
- **Забывать про ICMP port unreachable** — им помечается закрытый порт.
- **Игнорировать спуфинг** — UDP не проверяет src.
- **Открывать memcached наружу** — коэффициент до 50000×.
- **Доверять transaction ID** — при слабом PRNG возможен off-path.
- **Путать отражение и амплификацию** — первое про адрес, второе про размер.
- **Не считать baseline** — всплеск UDP легко пропустить.

## UDP-заголовок и контрольная сумма

UDP-заголовок минимален, но **checksum** опционален (в IPv4; в IPv6 обязателен). Нулевая контрольная сумма означает «не проверять» — некоторые реализации этим пользуются, а некоторые атаки полагаются на то, что битый UDP-пакет доставят.

```bash
# Разбор UDP с длиной и checksum
tshark -r cap.pcap -Y 'udp' -T fields -e udp.srcport -e udp.dstport -e udp.length -e udp.checksum | head
```

Длина `udp.length` = 8 + размер полезной нагрузки. Аномально большой UDP без фрагментации — редкость, поэтому размер часто используют как признак туннеля.

## Практика: UDP-скан и верификация сервисов

«Открыт» UDP-порт нельзя утверждать без ответа приложения. Поэтому после скана — верификация:

```bash
# 1. Скан
sudo nmap -sU -p 53,67,69,123,161,500 10.0.0.1
# 2. Верификация сервисов
dig @10.0.0.1 version.bind CH TXT      # DNS
snmpwalk -v2c -c public 10.0.0.1       # SNMP
ntpq -p 10.0.0.1                       # NTP
tftp 10.0.0.1 -c get test.txt          # TFTP
# 3. ISAKMP (IPsec) на 500/udp
sudo nmap -sU -p 500 --script ike-version 10.0.0.1
```

Если приложение ответило — порт точно открыт. Если нет — он может быть «open|filtered»: либо фильтр, либо сервис молчит на нестандартный запрос.

## Лаборатория: воспроизведение амплификации

```bash
# Поднять локальный DNS (dnsmasq) и замерить усиление
sudo dnsmasq --no-daemon --interface=lo &
# Запрос с большим ответом (TXT)
dig +short TXT large.example @127.0.0.1 | wc -c
# Запрос с поддельным src (только в изолированной лабе!)
sudo hping3 --udp -s 53 -p 53 -a 10.0.0.5 -d 50 -c 3 10.0.0.1
# Наблюдать ответ, уходящий «жертве»
sudo tcpdump -i any -nn 'udp port 53'
```

Так наглядно видно суть отражения: ответ уходит на поддельный адрес, а коэффициент усиления равен отношению размеров. В реальной сети это масштабируется до гигабит, если открыт memcached/DNS с большими ответами.
