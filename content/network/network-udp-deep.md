## Вопрос, с которого всё начинается

В TCP, прежде чем передать данные, стороны жмут друг другу руки (SYN, SYN-ACK, ACK) — и уже поэтому подделать отправителя сложно: ответ придёт не туда, и рукопожатие не состоится. А теперь представь транспорт **без** рукопожатия и без состояния. В нём отправитель просто кладёт адрес в пакет и шлёт — и сервер честно отвечает на этот адрес, даже если он поддельный.

Это **UDP**. Его минимализм даёт скорость, но открывает двери для спуфинга и амплификации. Разберём.

Этот урок продолжает [`network-module-ip`](network-module-ip) и опирается на [`network-portscan`](network-portscan).

## Наш пример: крошечный запрос — огромный ответ

Смотрим на UDP-трафик и его размеры:

```
$ tshark -r amp.pcap -Y 'dns' -T fields -e ip.src -e ip.dst -e udp.length -e dns.qry.name
203.0.113.5    10.0.0.53    78     anything.example
10.0.0.53      203.0.113.5  3120   anything.example
```

Запрос — 78 байт, ответ — 3120 байт, причём ушли они на **разные** адреса: запрос «от» `203.0.113.5`, а ответ — «на» `203.0.113.5`. Похоже на отражение. Чтобы понять, что тут происходит, начнём с самого заголовка.

## Шаг 1: заголовок UDP — 8 байт

```text
+----------------+----------------+--------+----------+
| Source Port(2) | Dest Port(2)   | Length | Checksum |
+----------------+----------------+--------+----------+
```

И всё. Ни флагов, ни sequence/ack, ни установления соединения. Приложение само решает, нужно ли ему обеспечивать надёжность.

## Шаг 2: почему спуфинг источника тривиален

Раз соединение не устанавливается, сервер просто отвечает на **src-адрес из пакета**. Подделать его можно свободно — ответ уйдёт жертве, а не атакующему. Именно поэтому защита строится не на самом UDP, а на фильтрации по границам сети. Из этого следуют сразу три вещи:

- **UDP-амплификация работает**: маленький запрос → большой ответ, уходящий жертве.
- **UDP-скан неоднозначен**: нет SYN/RST, статус выводится косвенно.
- **UDP-сервисы защищают** случайным transaction ID и портом.

## Шаг 3: амплификация и отражение

Схема атаки: атакующий шлёт маленький запрос с **поддельным src = жертва**. Сервер отвечает большим ответом жертве. Отношение размеров — **коэффициент усиления**.

| Протокол | Порт | Коэффициент | Замечание |
|---|---|---|---|
| DNS | 53 | 50–100× | запрос `ANY`, большие TXT |
| NTP | 123 | 500×+ | `monlist` (устаревшая уязвимость) |
| memcached | 11211 | до 50000× | UDP включён по ошибке |
| SSDP | 1900 | ~30× | UPnP-устройства |
| SNMP | 161 | ~6× | GetBulk |
| CharGen | 19 | ~350× | устарел |

Проверить на **своём** сервере, отвечает ли он большим ответом:

```
$ dig ANY example.com @10.0.0.53
;; ANSWER SECTION:
example.com. 3600 IN TXT "...очень длинная запись..."
```

Если публичный резолвер так умеет и не ограничивает частоту — он годится для отражения.

## Шаг 4: UDP-сканирование

UDP-скан сложнее TCP: нет рукопожатия, статус выводится из **ICMP port unreachable** (закрыт) или из отсутствия ответа (открыт/фильтруется).

```
$ sudo nmap -sU --top-ports 50 10.0.0.1
PORT     STATE         SERVICE
53/udp   open          domain
123/udp  open|filtered ntp
```

Проблема: rate-limiting ICMP и потеря пакетов дают ложные «open|filtered». Поэтому «открытость» нужно **подтверждать ответом приложения**, а не доверять статусу сканера:

```
$ dig @10.0.0.1 version.bind CH TXT
version.bind. 0 CH TXT "9.11.3"
$ snmpwalk -v2c -c public 10.0.0.1 | head -3
SNMPv2-MIB::sysDescr.0 = STRING: Linux router 5.4.0
```

Ответил — порт точно открыт. Молчит — либо фильтр, либо сервис не понял запрос.

## Шаг 5: спуфинг и сессионные протоколы

Некоторые UDP-протоколы (DNS, NTP, RADIUS) используют транзакционные идентификаторы. Если ID предсказуем, возможен **off-path спуфинг**: атакующий угадывает ID и порт и подсовывает жертве свой ответ. Защита — **рандомизация** ID и source-порта: чем больше пространство перебора, тем меньше шанс угадать. Именно поэтому современные резолверы рандомизируют и номер запроса, и исходящий порт для каждого запроса.

## Шаг 6: детект и защита

Что искать в трафике: огромные ответы на маленькие запросы, много запросов с одного src к разным серверам (отражение), всплеск UDP на 53/123/11211.

| Мера | Против чего |
|---|---|
| Отключить неиспользуемые UDP-сервисы | амплификация (memcached, chargen) |
| Rate-limit по протоколам | флуд/амплификация |
| BCP38 (anti-spoofing на периметре) | подделка src |
| Рандомизация source port и ID | off-path спуфинг |
| Не открывать memcached/SSDP наружу | гигантское усиление |
| Мониторинг «ответ > запрос» | детект отражения |

## Если не сработало

Скан UDP дал сплошное «open|filtered»? Это нормально — протокол неоднозначен. Что делать:

- **Верифицируй приложением.** Не верь статусу `nmap` — отправь настоящий запрос сервису (DNS/NTP/SNMP). Ответил — порт открыт.
- **Замедлись.** При высокой скорости ICMP rate-limit срабатывает и ответы теряются — снизь `--max-rate` и увеличь таймауты.
- **Повтори с `--version-intensity`.** Молчащий на стандартный запрос сервис может ответить на другой.
- **Учти спуфинг.** Если сервис отвечает нестабильно, возможно, кто-то уже спуфит src — проверь BCP38 на периметре.

## Лаборатория: воспроизведение амплификации

1. Подними локальный DNS (`dnsmasq`) и замерь усиление на большом ответе: `dig +short TXT large.example @127.0.0.1 | wc -c`.
2. Отправь запрос с поддельным src (только в изолированной лабе!): `sudo hping3 --udp -s 53 -p 53 -a 10.0.0.5 -d 50 -c 3 10.0.0.1`.
3. Смотри, как ответ уходит «жертве»: `sudo tcpdump -i any -nn 'udp port 53'`.

Так видно суть отражения: ответ уходит на поддельный адрес, а коэффициент усиления равен отношению размеров. В реальной сети это масштабируется до гигабит, если открыт memcached или DNS с большими ответами.

## Что мы теперь знаем

- UDP — транспорт без состояния, 8 байт заголовка.
- Спуфинг источника тривиален: сервер отвечает на src из пакета.
- Амплификация = отражение (поддельный src) + усиление (ответ больше запроса).
- UDP-скан неоднозначен; открытость подтверждают ответом приложения.
- Защита — BCP38, рандомизация ID/порта, rate-limit, закрытие лишних сервисов.

## Реальные кейсы амплификации: DNS, NTP, memcached

Коэффициент амплификации — это отношение размера ответа к размеру запроса. Разберём три исторических кейса, которые определяли масштаб DDoS-атак.

**DNS (порт 53).** Запрос `ANY` или `TXT` весит десятки байт, а ответ может быть в сотни раз больше:

```
$ dig ANY isc.org @203.0.113.53 +bufsize=4096
;; ANSWER SECTION:
isc.org.  60  IN  TXT  "v=spf1 ..." (много записей)
```

Исторический коэффициент — до 70x. Современные резолверы отключают `ANY` и ограничивают `+bufsize`, что снизило масштаб, но открытые рекурсивные резолверы всё ещё находятся массовым сканированием.

**NTP (порт 123).** Команда `monlist` (mode 6, запрос 6) возвращает список последних клиентов сервера — до 600 адресов в одном ответе. Коэффициент до 550x:

```
$ ntpdc -n -c monlist 203.0.113.123 | head
remote address          port  local address          count ...
```

Именно `monlist` обеспечил атаки 2014 года рекордного тогда масштаба. Патчи NTP выключили `monlist` по умолчанию, но непропатченные серверы остаются в интернете.

**memcached (порт 11211).** Самый разрушительный кейс: команда `stats` на UDP отдаёт мегабайты данных при запросе в десятки байт. Коэффициент — до 51000x. Знаменитая атака 2018 года давала пики под 1.3 Тбит/с:

```
$ echo -en "\x00\x00\x00\x00\x00\x01\x00\x00stats\r\n" | nc -u -w1 203.0.113.50 11211
STAT pid 1234
STAT uptime 999999
STAT version 1.4.35
... (тысячи строк)
```

Ключ здесь — всего один байт команды плюс спуфинг source IP: ответ уходит жертве, а атакующий его не видит.

Как это проверять в пентесте безопасно: **не** отправляйте амплифицирующий запрос с подделанного адреса. Достаточно послать один обычный запрос со своего IP и оценить размер ответа — если ответ во много раз больше запроса, сервис участвует в амплификации. Для защиты: закрыть сервис файрволом от интернета, отключить рекурсию/`monlist`/UDP-порт memcached, включить rate-limiting и BCP38-фильтрацию на своём периметре.

## Почему UDP-скан ненадёжен

Сканирование UDP принципиально сложнее TCP, и это надо учитывать в отчётах, чтобы не выдать ложный результат.

**Нет рукопожатия — нет однозначного «закрыто».** В TCP закрытый порт отвечает RST. В UDP закрытый порт либо отвечает ICMP port-unreachable, либо молчит — зависит от файрвола. `nmap -sU` поэтому трактует молчание как `open|filtered`: открытый и отфильтрованный порт неотличимы.

```
$ nmap -sU -p 53,123,161,500 203.0.113.10
53/udp   open|filtered  domain
123/udp  open|filtered  ntp
161/udp  open|filtered  snmp
500/udp  closed         isakmp
```

**Потери пакетов искажают картину.** UDP не повторяет потерянные датаграммы, а сети теряют их охотно. Без ретраев скан пропустит открытые порты:

```
$ nmap -sU -p 161 --max-retries 3 --host-timeout 120s 203.0.113.10
161/udp  open  snmp
```

Именно поэтому для UDP нужны `--max-retries 3` и увеличенные таймауты.

**Скорость.** UDP-скан медленный: нет возможности слать пакеты пачками, как SYN-скан. Полный прогон 65535 UDP-портов может занять часы, поэтому сканируют список приоритетных портов (DNS 53, DHCP 67/68, NTP 123, SNMP 161/162, IKE 500/4500, mDNS 5353, SSDP 1900, memcached 11211).

**Rate-limiting.** Многие UDP-сервисы (DNS, NTP) сами ограничивают частоту ответов и начинают молчать под нагрузкой. Быстрый скан получает ложные «filtered».

Практический вывод: `open|filtered` нельзя выдавать за открытый сервис. Подтверждать надо сервис-специфичным запросом — `dig` для 53, `snmpwalk` для 161, `ntpdate -q` для 123 — и только тогда фиксировать находку.
