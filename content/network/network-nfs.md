## Вопрос, с которого всё начинается

Ты просканировал хост и видишь открытыми порты `111` и `2049`. Это RPC и NFS — **сетевая файловая система**: диск, расшаренный по сети. Такие шары часто настраивают «чтобы работало», и тогда через них можно не только читать чужие файлы, но и получить полный доступ к хосту.

В этом уроке разберём, как устроены NFS-шары, как их перечислить и как ошибка настройки `no_root_squash` превращается в захват машины.

## Наш пример: хост с открытым NFS

У нас есть хост `10.0.0.20`, на котором открыты RPC (111) и NFS (2049). Инструменты `showmount` и `rpcinfo` на этой машине не установлены, поэтому команды я привожу как справочные — их вывод на сервере с NFS имеет описанную ниже структуру, а логику разберём по шагам.

## Шаг 1: что такое RPC и NFS

**NFS** (Network File System) — протокол, позволяющий монтировать каталог с удалённой машины как локальный. Работает он не на фиксированном порту, а через **RPC** (remote procedure call) — механизм вызова процедур на удалённой машине. Служба `rpcbind` (порт 111) подсказывает клиенту, на каком порту сейчас живёт NFS.

Схема такая:

- Порт `111` — `rpcbind`: «спроси у меня, где NFS».
- Порт `2049` — сам NFS.
- Порт `20048` — `mountd`: служба, которая сообщает список **экспортов** (расшаренных каталогов).

## Шаг 2: перечисляем экспорты

Экспорт — это каталог, который сервер отдал по сети. Посмотреть их можно командой `showmount`:

```
$ showmount -e 10.0.0.20
Export list for 10.0.0.20:
/home/user  *
/var/backups 10.0.0.0/24
```

Разбор вывода: первый столбец — путь на сервере, второй — кому разрешено монтировать. Звёздочка `*` означает «**всем**» — это и есть главная ошибка администрирования: шара открыта любому, кто дотянется до порта.

Без `showmount` список иногда достают напрямую через RPC (`rpcinfo -p 10.0.0.20` показывает, какие RPC-программы зарегистрированы и на каких портах).

## Шаг 3: монтируем шару

Зная экспорт, его монтируют локально:

```
$ mkdir -p /mnt/nfs && mount -t nfs 10.0.0.20:/home/user /mnt/nfs
$ ls -la /mnt/nfs
```

Теперь содержимое чужого `/home/user` видно как обычный каталог. Если в нём есть файлы с ключами, конфигами или бэкапами — они твои.

## Шаг 4: UID/GID и главная ошибка — no_root_squash

Здесь ключевой момент. В NFS права доступа определяются **числовыми UID и GID**, а не именами. Когда ты создаёшь файл на шаре, сервер записывает твой UID. Но клиент может **подделать** UID: если у тебя есть root на своей машине, ты можешь создавать файлы «от имени» любого UID, включая `0` (root) и любой пользовательский.

Защита от этого называется **root_squash**: сервер «приземляет» root-UID клиента (0) до анонимного пользователя, чтобы клиент не мог писать файлы от имени root. Но если в `/etc/exports` указано **`no_root_squash`**, защиты нет — и тогда:

1. Монтируешь шару.
2. Создаёшь файл от имени root (ты и есть root на своём хосте).
3. Файл на сервере получает владельца `root`.

## Шаг 5: от шары к root на сервере

Наличие `no_root_squash` даёт два классических пути эскалации:

- **SSH authorized_keys.** Если шара — это домашний каталог пользователя (или `/root`), положи туда `~/.ssh/authorized_keys` со своим публичным ключом от имени root. После этого заходишь на сервер по SSH как root без пароля.
- **Cron.** Если шара — `/etc` или каталог, откуда читает `cron`, положи туда скрипт от имени root. Следующий запуск cron выполнит его с правами root.

Оба приёма — про одно: **запись файла с чужим UID на доверенный каталог**. Отсюда правило защиты: NFS монтируют только в доверенных сетях, с `root_squash` (по умолчанию) и без экспорта домашних каталогов «всем».

## Шаг 6: как защититься

Меры простые и хорошо известны:

- Экспортировать только нужные каталоги и только нужным подсетям (не `*`).
- Никогда не отключать `root_squash`.
- Использовать `all_squash` для общих шар, где UID не важен.
- Не расшаривать `/home`, `/root`, `/etc`.
- Закрыть порты 111/2049 файрволом от внешнего мира.
- По возможности использовать NFSv4 с Kerberos.

## Шаг 7: полный прогон — от скана до root

Соберём путь целиком, как он выглядит в реальном пентесте.

```
$ nmap -sV -p 111,2049,20048 10.0.0.20
PORT      STATE SERVICE VERSION
111/tcp   open  rpcbind 2-4 (RPC #100000)
2049/tcp  open  nfs     3-4 (RPC #100003)
20048/tcp open  mountd  1-3 (RPC #100005)
```

Три порта подтверждают стек: rpcbind, NFS, mountd. Дальше — экспорты:

```
$ showmount -e 10.0.0.20
Export list for 10.0.0.20:
/home/user  *
```

Монтируем и смотрим владельцев — так проверяют `no_root_squash`:

```
$ mkdir -p /mnt/nfs && mount -t nfs 10.0.0.20:/home/user /mnt/nfs
$ ls -ln /mnt/nfs
-rw-r--r-- 1 1000 1000  220 .bash_logout
drwx------ 2 1000 1000 4096 .ssh
```

UID `1000` — обычный пользователь. Проверяем `no_root_squash` просто: создаём файл и смотрим, чей UID он получил.

```
$ touch /mnt/nfs/probe && ls -ln /mnt/nfs/probe
-rw-r--r-- 1 0 0 0 probe
```

Файл получил владельца `0` (root) — значит, `no_root_squash` включён и запись «от имени root» работает. Теперь кладём ключ в `.ssh/authorized_keys` (шара — домашний каталог), заходим по SSH как root и забираем машину. Если бы шара указывала на `/etc`, тот же приём сработал бы через cron.

## Если не сработало

- **`showmount` пуст, но 2049 открыт.** Экспорты могут быть скрыты; пробуй RPC-запросы напрямую или перебор частых путей.
- **Файлы принадлежат `nobody`.** Значит, включён `root_squash` — эскалация через владельца не выйдет.
- **Монтирование висит.** Возможно, не совпала версия NFS; добавь `-o vers=3` или `vers=4`.

## Что мы теперь знаем

По-простому:

1. NFS — сетевая ФС; работает через RPC (порт 111) и NFS (2049).
2. `showmount -e` показывает экспорты; `*` — доступ всем.
3. Шару монтируют командой `mount -t nfs`.
4. Права в NFS — по числовым UID/GID, и клиент может подделать UID.
5. `no_root_squash` позволяет писать от имени root → SSH-ключи или cron → root на сервере.
6. Защита: `root_squash`, узкие экспорты, файрвол, NFSv4+Kerberos.

## На что смотреть дальше

- **Проверь оба порта.** 111 без 2049 — rpcbind есть, но NFS может быть не запущен.
- **Смотри права.** Шара с `no_root_squash` — красный флаг.
- **Думай о цели записи.** Куда можно положить файл, чтобы он выполнился?

## Разбираем RPC-перечисление NFS

Вернёмся к нашему хосту с открытым NFS. NFS использует **RPC** (Remote Procedure Call) — механизм вызова процедур на удалённой машине. Номера программ регистрирует **portmapper/rpcbind** на порту 111. Сначала смотрим, что вообще зарегистрировано:

```
$ rpcinfo -p 10.0.0.20
   program vers proto   port  service
    100000    4   tcp    111  portmapper
    100003    3   tcp   2049  nfs
    100003    4   tcp   2049  nfs
    100005    3   udp    892  mountd
    100021    4   tcp   2049  nlockmgr
```

Читается так: работает NFS версий 3 и 4, а также `mountd` (служба монтирования). Уже из этого видно, что порт 2049 открыт и NFS отвечает. Дальше — какие каталоги экспортированы:

```
$ showmount -e 10.0.0.20
Export list for 10.0.0.20:
/home     *
/srv/data 10.0.0.0/24
```

Первая строка — красный флаг: `*` означает «экспорт для **всех**». Вторая ограничена подсетью.

## Версии NFS и их особенности

| Версия | Транспорт | Особенности | Защита |
|---|---|---|---|
| NFSv2 | UDP | нет блокировок, только 32-бит | нет |
| NFSv3 | TCP/UDP | есть mountd на отдельном порту | `sec=krb5` |
| NFSv4 | TCP | единый порт 2049, встроенный mount | `sec=krb5p` |

Ключевое отличие: в v3 служба `mountd` висит на случайном порту и должна быть доступна, поэтому фильтровать её сложнее. В v4 всё идёт через 2049, и можно спрятать всё за одним портом.

## Как работает uid/gid spoofing

NFS **не проверяет пароль**. Он доверяет числам `uid`/`gid`, которые прислал клиент. Если ты подключился как локальный пользователь с uid `1000`, сервер считает, что ты — пользователь `1000` на сервере. Значит, создав у себя пользователя с нужным uid, ты получишь его файлы:

```
$ sudo mount -t nfs 10.0.0.20:/home /mnt/nfs
$ ls -la /mnt/nfs/alice/
-rw------- 1 1001 1001 ... secret.txt   # чужой файл, но uid совпал
```

А **`no_root_squash`** отключает защиту от root: без него uid `0` превращается в `nobody` (**root_squash**), а с ним — остаётся `0`, и ты можешь писать где угодно. Именно так NFS превращается в путь к root на сервере:

```
$ sudo mount -t nfs -o vers=3 10.0.0.20:/srv/data /mnt/data
$ echo 'ssh-ed25519 AAAA...' | sudo tee -a /mnt/data/../../root/.ssh/authorized_keys
```

Если экспорт ведёт в каталог, доступный root-у сервера, ты дописываешь свой ключ и заходишь по SSH как root.

## Если шара не монтируется

Причины по порядку. Первая — **версия**: попробуй явно `-o vers=3` или `-o vers=4`. Вторая — **firewall** на стороне сервера режет порт 111 или 2049, тогда `showmount` тоже пуст. Третья — **`root_squash` включён** (правильная настройка), и запись от root уходит в `nobody` — тогда ты можешь только читать, что доступно `nobody`. Четвёртая — экспорт разрешён **только** определённым подсетям, и твоего IP там нет. И проверь `nfsvers` в `/proc/mounts` — иногда ядро по умолчанию берёт v4, который требует больше предусловий.

## Почему это приоритетная находка

Открытый NFS без ограничений — это часто прямой путь к учётным данным (домашние каталоги, `.ssh`, конфиги) и к root через `no_root_squash`. В отчёте фиксируй: список экспортов, наличие `*`, версии, и **доказательство** доступа (прочитанный файл), а не только открытый порт.
