## Вопрос, с которого всё начинается

Провайдер подключает дом к интернету, и на роутере в настройках ты видишь логин и пароль для «подключения к провайдеру». Что это за подключение и почему для него нужен пароль? Речь о **PPPoE** — способе передать PPP-сессию (как при старом дозвоне) поверх обычного Ethernet. Многие провайдеры используют его до сих пор.

А где пароль ходит по проводу — там его можно перехватить. Плюс ко всему PPPoE добавляет свою накладку: 8 байт заголовка съедают часть MTU, из-за чего крупные пакеты иногда теряются. Разберём и инкапсуляцию, и слабости, и типичные сбои.

Этот урок опирается на [`network-tcpip`](network-tcpip).

## Наш пример: смотрим на PPPoE-трафик

Захватываем трафик на мосту (в лабораторном сегменте) и фильтруем PPPoE:

```
$ sudo tcpdump -i br0 -nn -e 'pppoes or pppoed' -c 6
14:01:00.001 08:00:27:aa:bb:cc > ff:ff:ff:ff:ff:ff, ethertype PPPoE D (0x8863), PPPoE PADI
14:01:00.002 52:54:00:11:22:33 > 08:00:27:aa:bb:cc, ethertype PPPoE D (0x8863), PPPoE PADO
14:01:00.003 08:00:27:aa:bb:cc > 52:54:00:11:22:33, ethertype PPPoE S (0x8864), PPP LCP
```

Два разных EtherType: `0x8863` (discovery) и `0x8864` (session). И два разных этапа: сначала поиск сервера, потом сама сессия. Разберём.

## Шаг 1: инкапсуляция и фазы

PPPoE встраивает PPP-кадр внутрь Ethernet:

```text
Ethernet | PPPoE header | PPP | PPP payload (IP)
```

Работает это в несколько фаз:

1. **Discovery (PPPoE).** Клиент рассылает `PADI` (Active Discovery Initiation) broadcast'ом; серверы отвечают `PADO` (Offer); клиент выбирает и шлёт `PADR` (Request); сервер завершает `PADS`, выдавая **Session ID**.
2. **LCP (PPP).** Согласование параметров канала — MRU, magic number, метод аутентификации.
3. **Аутентификация.** PAP или CHAP — вот здесь утекают учётные данные.
4. **IPCP.** Согласование IP и DNS (аналог DHCP внутри PPP).
5. **Data.** Собственно IP-трафик.

Посмотреть фазы в дампе:

```
$ tshark -r pppoe.pcap -Y 'pppoed' -T fields -e pppoe.code -e pppoe.session_id
0x09    0x0000
0x07    0x0000
```

`0x09` — PADI, `0x07` — PADO. Ошибка новичка — считать, что PPPoE «это просто Ethernet»: внутри есть отдельная фаза согласования и своя адресация.

## Шаг 2: аутентификация — PAP против CHAP

| Метод | Как работает | Слабость |
|---|---|---|
| **PAP** | логин/пароль в открытом виде | перехват пароля из PCAP |
| **CHAP** | сервер шлёт challenge, клиент отвечает MD5(challenge+secret) | оффлайн-перебор, MITM-релей |
| **MS-CHAPv2** | вариант CHAP от Microsoft | из ответа восстанавливается NT-хэш пароля |

Посмотрим, как выглядит утечка PAP. Фильтруем по протоколу PAP (`0xc023`):

```
$ tshark -r pppoe.pcap -Y 'ppp.protocol==0xc023' -T fields -e ppp.peer_id -e ppp.password
login@isp    SecretPass123
```

Логин и пароль — **в открытом виде**. Это прямой путь к компрометации учётной записи доступа.

## Шаг 3: MS-CHAPv2 и оффлайн-атака

С CHAP в кадре только challenge и хэш-ответ — пароль в открытом виде не виден. Но MS-CHAPv2 всё равно слаб: из перехваченного handshake восстанавливается NT-хэш пароля (атака «chapcrack»). Дальше хэш перебирается оффлайн:

```
$ chapcrack -f pppoe.pcap -o hs.txt
$ hashcat -m 5500 hs.txt rockyou.txt
```

Режим `5500` — MSCHAPv2. Если пароль из корпоративного словаря, подбор быстрый. Альтернатива — **релей**: поднять фальшивый сервер доступа (rogue AC) и переслать challenge жертве.

## Шаг 4: где ещё слабо

- **PPTP** — PPP поверх GRE (IP-протокол 47), управляющий канал TCP/1723. Исторически сломан: MS-CHAPv2 + слабое шифрование MPPE.
- **L2TP** — сам не шифрует, работает только с IPsec.
- **SSTP** — PPP поверх HTTPS (TCP/443), маскируется под обычный TLS.

Захват данных PPTP: помни, что данные идут в GRE, а не в TCP/1723 — без фильтра `gre` их не увидишь.

## Шаг 5: MTU и типичные сбои

PPPoE добавляет 8 байт заголовка (6 PPPoE + 2 PPP), поэтому полезный MTU уменьшается с 1500 до **1492**. Если это не учесть, крупные пакеты с флагом `DF` теряются — классическая проблема «сайты грузятся частично». Лечится **MSS clamping** на роутере:

```
$ sudo iptables -t mangle -A FORWARD -p tcp --tcp-flags SYN,RST SYN \
  -j TCPMSS --clamp-mss-to-pmtu
```

## Шаг 6: защита

- **Отказ от PAP и MS-CHAPv2** — только EAP-TLS/PEAP с сертификатами.
- **IPsec для L2TP** — сильный PSK или сертификаты.
- **Изоляция:** PPPoE только на портах доступа, discovery не пропускать на транзит.
- **Port security / 802.1X:** не давать постороннему хосту встать в сегмент доступа.
- **Мониторинг:** аномальные PADI-флуды, смена Session ID, появление второго сервера доступа.

Отдельно стоит проверить MTU/MSS: неправильный размер ломает крупные сессии и выглядит как «проблема провайдера», хотя лечится одной строкой на роутере.

## Если не сработало

Не видишь PPPoE-трафик? Проверь:

- **Фильтр слишком узкий.** Данные идут не в TCP/1723, а в GRE или в PPPoE-сессию — используй фильтры `pppoes`/`pppoed`/`gre`, иначе увидишь только управляющие пакеты.
- **Discovery вместо сессии.** Учётки находятся в фазе аутентификации (PAP/CHAP), а не в PADI/PADO — не путай этапы.
- **Только шифрованный канал.** Если поверх идёт IPsec/TLS (L2TP/IPsec, SSTP), открытых учёток в дампе не будет по определению.

Для подъёма собственного клиента в лаборатории удобны `pppoeconf`/`pon dsl-provider`, а для разбора — Scapy (`PPPoE()`/`PPP()`) и `pppoe-discovery`, которым можно проверить, не отвечает ли на порту лишний сервер доступа.

## Шаг 7: полный разбор — от discovery до пароля

Соберём весь путь атакующего на одном дампе. Мы в сегменте доступа провайдера и видим PPPoE.

1. **Находим сессии.** Фильтруем PPPoE:
```
$ tshark -r pppoe.pcap -Y 'pppoes' -T fields -e eth.src -e pppoe.session_id | head
08:00:27:aa:bb:cc   0x0001
```
2. **Достаём учётки.** Если провайдер использует PAP — пароль прямо в кадре:
```
$ tshark -r pppoe.pcap -Y 'ppp.protocol==0xc023' -T fields -e ppp.peer_id -e ppp.password
login@isp   SecretPass123
```
3. **Если CHAP — собираем handshake и перебираем оффлайн:**
```
$ chapcrack -f pppoe.pcap -o hs.txt
$ hashcat -m 5500 hs.txt rockyou.txt
```
4. **Проверяем MTU.** Крупные пакеты не проходят — значит, нужен MSS clamping (см. Шаг 5).

Так один дамп в сегменте доступа отдаёт либо пароль в открытом виде, либо материал для оффлайн-подбора.

## Rogue Access Concentrator

PPPoE-discovery не аутентифицирован: клиент рассылает PADI broadcast'ом и верит **первому** PADO. Это позволяет поднять **поддельный Access Concentrator** и перехватить сессию:

- ответить на PADI быстрее настоящего сервера (PADO-race);
- завершить discovery и выдать свой Session ID;
- запросить аутентификацию и собрать PAP/CHAP-ответ жертвы.

Инструменты вроде `pppoe-server` (пакет `pppoe`) позволяют поднять такой сервер в лаборатории. Защита — изоляция портов доступа (port security, 802.1X), чтобы посторонний хост не встал в сегмент, и мониторинг PADI-флудов и «вторых» PADO.

## PPPoE в разведке: что искать

PPPoE встречается на доступе провайдера и в старых установках. Что проверять:

- **EtherType.** `0x8863` — discovery, `0x8864` — session; фильтры `pppoed`/`pppoes` в tshark.
- **Метод аутентификации.** PAP (`0xc023`) — пароль открыт; CHAP — нужен оффлайн-перебор.
- **Активный AC.** Отвечает ли на PADI больше одного сервера (`pppoe-discovery`).
- **MTU.** Крупные пакеты теряются — признак отсутствия MSS clamping.

Собрав это, ты знаешь и метод аутентификации, и потенциальную уязвимость доступа, не делая ни одного «активного» запроса кроме фильтрации трафика.

## Что мы теперь знаем

- PPPoE несёт PPP поверх Ethernet и проходит фазы Discovery → LCP → Auth → IPCP → Data.
- Учётные данные утекают в фазе аутентификации, а не в discovery.
- PAP отдаёт пароль открытым текстом; MS-CHAPv2 — challenge/response для оффлайн-подбора.
- PPTP сломан, L2TP нужен только с IPsec, SSTP маскируется под HTTPS.
- PPPoE уменьшает MTU до 1492 — нужен MSS clamping.
- Учётки утекают только там, где нет шифрования сверху (IPsec/TLS), — в остальных случаях их видно в дампе.
- Rogue AC эксплуатирует отсутствие аутентификации в PPPoE-discovery (PADO-race).
- PPTP несёт данные в GRE (proto 47), а не в TCP/1723 — фильтруй `gre`.
- SSTP маскируется под HTTPS/443; L2TP без IPsec не шифрует вообще.
- PAP-пароль виден прямо в `ppp.password`; для CHAP — chapcrack + hashcat -m 5500.
- PPPoE добавляет 8 байт заголовка: MTU падает с 1500 до 1492.
- Discovery (PADI/PADO/PADR/PADS) — это поиск сервера, а не аутентификация.
- Клиент верит первому PADO — поэтому PADO-race и поддельный AC вообще работают.
- MSS clamping лечит «частичную загрузку» сайтов за PPPoE одной строкой на роутере.
