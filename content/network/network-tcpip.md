Понимание формата пакета — база всей сетевой безопасности. Пока вы не умеете «прочитать» байты на проводе, любые атаки и защиты остаются заклинаниями. Этот урок — про ручной разбор Ethernet, IP, TCP и UDP, про то, какие поля за что отвечают, и про то, как эти поля эксплуатируют.

Разберём инкапсуляцию, все ключевые поля каждого заголовка, ручной разбор байтов, TCP-состояния и трёхстороннее рукопожатие, флаги и их применение в сканировании.

## Инкапсуляция: что во что вложено

Данные приложения спускаются по стеку и обрастают заголовками:

```
[ Ethernet 14B ][ IPv4 20B ][ TCP 20B ][ Payload ... ]
[ Ethernet 14B ][ IPv4 20B ][ UDP 8B  ][ Payload ... ]
```

Ethernet — канальный уровень (L2), IP — сетевой (L3), TCP/UDP — транспортный (L4). Уровни независимы: смена IP-заголовка не требует пересборки TCP, но капсулирование всегда вложенное. Понимание этой вложенности — ключ к разбору `tcpdump -e -X`.

## Ethernet-заголовок (14 байт)

| Поле | Размер | Смысл |
|---|---|---|
| Destination MAC | 6 | MAC получателя |
| Source MAC | 6 | MAC отправителя |
| EtherType | 2 | `0x0800` = IPv4, `0x86DD` = IPv6, `0x0806` = ARP |
| (VLAN 802.1Q) | +4 | если есть тег: TPID `0x8100`, priority, VID |

EtherType — «переключатель» разбора: по нему ядро решает, какой обработчик звать. Атаки на L2 (MAC-flooding, ARP-спуфинг) работают именно с этими полями.

## IPv4-заголовок (минимум 20 байт)

| Поле | Смысл | Атака/нюанс |
|---|---|---|
| Version/IHL | версия и длина заголовка | IHL<5 — некорректно, часть IPS ловит |
| Total Length | вся длина пакета | рассинхрон с реальной длиной → evasion |
| Identification | ID фрагмента | используется для фрагментации |
| Flags + Fragment Offset | флаги и смещение | `MF`, `DF`; overlap-фрагментация обходит IDS |
| TTL | время жизни (hop limit) | OS fingerprinting по начальному TTL (64/128/255) |
| Protocol | `6` TCP, `17` UDP, `1` ICMP | выбор L4-обработчика |
| Header Checksum | контрольная сумма заголовка | |
| Source/Dest IP | адреса | спуфинг источника |

Фрагментация — классический вектор обхода фильтров: маленькие фрагменты могут пройти там, где целый пакет блокируется, а перекрывающиеся фрагменты сбивают реконструкцию у IPS (evasion через overlap).

## TCP-заголовок (минимум 20 байт) и флаги

| Поле | Смысл |
|---|---|
| Source/Dest Port | порты приложения |
| Sequence Number | номер байта в потоке |
| Acknowledgment Number | ожидаемый номер следующего байта |
| Data Offset | длина TCP-заголовка (×4) |
| Flags | URG ACK PSH RST SYN FIN (+ ECE CWR NS) |
| Window | размер окна приёма |
| Checksum | контрольная сумма с псевдозаголовком |
| Options | MSS, Window Scale, SACK, Timestamps |

Флаги — сердце сканирования:

- **SYN** — открыть соединение. `nmap -sS` шлёт SYN и по ответу (SYN/ACK vs RST) судит об открытости порта, не завершая рукопожатие.
- **FIN, XMAS (FIN+PSH+URG), NULL** — сканы «без SYN»; на закрытый порт приходит RST, на открытый — тишина (у многих ОС).
- **RST** — сброс. Активное «закрытие» и способ понять фильтрацию.
- **ACK** — используется для определения firewall-правил (`-sA`): RST vs drop.

**Трёхстороннее рукопожатие:** `SYN → SYN/ACK → ACK`. Все последующие данные идут с флагом ACK. Понимание SEQ/ACK нужно для TCP-хайджекинга, инъекции и RST-атак.

## UDP-заголовок (8 байт)

| Поле | Смысл |
|---|---|
| Source/Dest Port | порты |
| Length | длина UDP-датаграммы |
| Checksum | опциональна в IPv4, обязательна в IPv6 |

UDP не устанавливает соединение, поэтому сканирование (`nmap -sU`) ненадёжно: нет ответа ≠ порт закрыт. Но UDP несут DNS, SNMP, NTP, DHCP, QUIC — критичные сервисы.

## Ручной разбор: tcpdump и Scapy

Захват с hex-выводом:

```bash
tcpdump -ni eth0 -e -X -c 3 tcp port 80
```

Фрагмент вывода (сокращённо):

```
12:00:01.123456  aa:bb:cc:00:00:01 > 11:22:33:44:55:66, ethertype IPv4 (0x0800), length 74
  0x0000:  4500 003c 1c46 4000 4006 b1e6 c0a8 0001  E..<.F@.@.......
  0x0010:  c0a8 0002 9c40 0050 ...                    .....@.P.
```

Здесь `4500` — version 4, IHL 5; `4000` — DF-флаг; `4006` — TTL 64, protocol 6 (TCP); далее адреса. Порт назначения `0050` = 80.

Разбор в Scapy (Python) — позволяет не только читать, но и собирать пакеты:

```python
from scapy.all import IP, TCP, Ether, sendp, sniff

# собрать SYN вручную
pkt = Ether()/IP(dst="10.0.0.5")/TCP(dport=80, flags="S", seq=1000)
sendp(pkt, iface="eth0")

# разобрать поля принятого пакета
def show(p):
    if IP in p:
        print(p[IP].src, p[IP].ttl, p[IP].proto)
        if TCP in p:
            print("flags:", p[TCP].flags, "seq:", p[TCP].seq)
sniff(iface="eth0", prn=show, count=5)
```

Scapy — инструмент для спуфинга, фрагментации и кастомных сканов; именно так «руками» воспроизводят редкие атаки.

## Практика: разбор SYN-скана глазами

```bash
# видим, как nmap шлёт SYN и что приходит обратно
tcpdump -ni eth0 'tcp[tcpflags] & (tcp-syn|tcp-rst) != 0' -c 20
```

Ожидаемая картина: `S` (SYN) от сканера → `S.` (SYN/ACK) от открытого порта, `R` (RST) от закрытого. По разнице и строится таблица портов. Если ответа нет — порт `filtered` (съеден firewall).

## Фрагментация и обход фильтров

```bash
# отправить пакет мелкими фрагментами (nmap)
nmap -f -sS -p 80 10.0.0.5
# double-fragment
nmap -ff -sS -p 80 10.0.0.5
```

Некоторые IDS не собирают фрагменты корректно и пропускают полезную нагрузку. Перекрывающиеся фрагменты (overlap) позволяют подсунуть разные данные разным системам (Tevan/teardrop-подобные техники).

## TCP-состояния и почему это важно

Диаграмма состояний: `LISTEN → SYN_SENT → SYN_RECEIVED → ESTABLISHED → FIN_WAIT/CLOSE_WAIT → TIME_WAIT → CLOSED`. Знание переходов нужно для:

- диагностики «повисших» соединений (полуоткрытые, SYN-flood);
- атак через `RST` (обрыв чужой сессии, TCP-хайджекинг);
- сканирования, которое должно быть незаметным (`-sN`, `-sF`, `-sX` не завершают соединение).

## Частые ошибки

- Смотреть `tcpdump` без `-e`/`-X` и не видеть L2/L3-поля.
- Путать SEQ и ACK: в SYN задаёт начальный SEQ, в SYN/ACK — свой SEQ и ACK=SEQ+1.
- Забыть, что TCP-заголовок может быть больше 20 байт (options) — тогда `Data Offset` > 5.
- Считать, что «нет ответа = закрыто» — для UDP и для фильтрованных портов это неверно.
- Игнорировать checksum — при ручной сборке пакета его надо пересчитывать (Scapy делает это сам).

## Что дальше / решение

Следующий шаг — научиться читать пакеты автоматически: `tshark -V`, `scapy`-скрипты, `zeek`-логи. Для атак — фрагментация и кастомные флаги; для защиты — нормализация трафика (defragmentation, reassembly) на периметре, чтобы evasion не работал. Ручной разбор заголовков — фундамент: без него вы не поймёте ни сканирование, ни MITM, ни туннели.

## Итоговый разбор одного пакета целиком

Возьмём реальный HTTP-запрос и разберём каждый уровень по байтам. Захват: `tcpdump -ni eth0 -e -X 'tcp port 80 and tcp[13] & 2 != 0'`. Видим Ethernet (dst/src MAC, EtherType `0800`), затем IP: `45` (v4, IHL 5), total length, ID, flags `40` (DF), TTL `40`=64, protocol `06` (TCP), checksum, src/dst. Затем TCP: src port, dst port `0050`=80, seq, ack, `5018` — data offset 5 (20 байт) и флаг `18`=PSH+ACK, window, checksum, urgent pointer. Всё, что дальше — payload HTTP.

Умение прочитать эту строку «на глаз» отличает специалиста, который понимает, что делает инструмент, от того, кто просто нажимает кнопки.

## Reference-таблица: как поля заголовков используются в атаках

| Поле | Техника | Инструмент |
|---|---|---|
| EtherType | инкапсуляция/двойное тегирование VLAN | Scapy, `vconfig` |
| IP ID | фингерпринт ОС, idle-скан | `nmap -O`, `-sI` |
| IP Flags/Offset | обход IDS фрагментацией | `nmap -f/-ff`, fragroute |
| TTL | фингерпринт по начальному TTL | `nmap -O` |
| IP src | спуфинг источника | Scapy, hping3 |
| TCP Flags | типы сканов (SYN/FIN/NULL/XMAS) | `nmap -sS/-sF/-sN/-sX` |
| TCP seq/ack | инъекция, RST-обрыв, хайджекинг | Scapy, `hping3` |
| TCP options | фингерпринт, MSS-манипуляции | `nmap -O` |
| UDP checksum | манипуляции с датаграммами | Scapy |

Эта таблица — шпаргалка: почти любая сетевая атака трогает одно из этих полей. Понимая поле, вы понимаете и вектор, и способ защиты (нормализация, defragmentation, TCP-инспекция).

## Контрольные вопросы для самопроверки разбора

Прежде чем идти дальше, убедитесь, что можете ответить без подсказок:

- По какому полю Ethernet ядро понимает, что внутри лежит IPv4, а не IPv6 или ARP?
- Чем `SYN`-скан отличается от `connect`-скана на уровне завершения рукопожатия?
- Почему `Data Offset` умножается на 4 и что это значит для заголовка с options?
- Как отличить фильтрованный TCP-порт от закрытого при `-sS`?
- Почему UDP-скан ненадёжен и какие протоколы от этого страдают?

Если хотя бы один вопрос вызывает сомнение — вернитесь к соответствующей таблице выше и разберите поле руками в Scapy. Понимание формата пакета окупается на всех последующих темах: сканировании, MITM, туннелях и анализе трафика.
