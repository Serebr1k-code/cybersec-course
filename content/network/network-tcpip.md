## Вопрос, с которого всё начинается

В первом уроке мы разобрали пакет «по слоям» и увидели матрёшку Ethernet → IP → TCP → HTTP. Но что именно лежит в каждом слое? Если дать тебе пакет в виде строки байтов, сможешь ли ты сказать, куда он идёт и что несёт?

Умение читать пакет «по байтам» — базовый навык сетевого специалиста. Оно нужно, когда Wireshark недоступен, когда нужно проверить инструмент, или когда данные спрятаны в полях заголовка. В этом уроке мы разберём один пакет из hex-дампа вручную.

## Наш пример: пакет в hex

У нас есть один пакет, записанный байтами. Вот он:

```
52 54 00 12 34 56 00 0c 29 ab cd ef 08 00
45 00 00 54 1c 46 40 00 40 06 b1 e6 0a 00 00 05 5d b8 d8 22
c8 34 00 50 00 00 00 01 00 00 00 01 50 18 01 f6
```

Три строки — это три слоя: Ethernet, IP и TCP. Разберём каждый байт.

## Шаг 1: Ethernet-заголовок (14 байт)

Первые 14 байт — канальный слой:

```
52 54 00 12 34 56   ← MAC получателя
00 0c 29 ab cd ef   ← MAC отправителя
08 00               ← тип протокола
```

Читаем:

- Первые 6 байт — **MAC-адрес получателя** (`52:54:00:12:34:56`).
- Следующие 6 — **MAC-адрес отправителя** (`00:0c:29:ab:cd:ef`).
- Последние 2 — **EtherType**, тип вложенного протокола. `0x0800` означает «внутри IPv4». Другие значения: `0x0806` — ARP, `0x86DD` — IPv6.

MAC-адреса работают только внутри одной локальной сети. Как только пакет выходит за её пределы, MAC меняется, а IP остаётся.

## Шаг 2: IPv4-заголовок (20 байт)

Дальше идёт сетевой слой:

```
45 00 00 54 1c 46 40 00 40 06 b1 e6 0a 00 00 05 5d b8 d8 22
```

Разберём поля по порядку:

- `45` — версия и длина заголовка. Старшая тетрада `4` — версия IPv4, младшая `5` — длина заголовка в 32-битных словах (5 × 4 = 20 байт).
- `00 00` — тип обслуживания (DSCP), обычно нули.
- `00 54` — общая длина пакета: `0x0054` = 84 байта.
- `1c 46` — идентификатор пакета (для сборки фрагментов).
- `40 00` — флаги и смещение фрагмента; `40` означает «не фрагментировать».
- `40` — **TTL** (Time To Live): 64. Каждый маршрутизатор уменьшает его на 1; когда станет 0, пакет отбрасывается.
- `06` — **протокол**: `6` означает TCP. Другие: `17` — UDP, `1` — ICMP.
- `b1 e6` — контрольная сумма заголовка.
- `0a 00 00 05` — **IP-адрес отправителя**: `10.0.0.5`.
- `5d b8 d8 22` — **IP-адрес получателя**: `93.184.216.34`.

Теперь мы точно знаем: пакет идёт с `10.0.0.5` на `93.184.216.34`, внутри — TCP.

## Шаг 3: TCP-заголовок (20 байт)

Транспортный слой:

```
c8 34 00 50 00 00 00 01 00 00 00 01 50 18 01 f6
```

- `c8 34` — **порт отправителя**: `0xC834` = 51252 (случайный порт клиента).
- `00 50` — **порт получателя**: `0x0050` = 80 (веб-сервер).
- `00 00 00 01` — порядковый номер (sequence number): 1.
- `00 00 00 01` — номер подтверждения (acknowledgment): 1.
- `50` — длина заголовка и флаги: старшая тетрада `5` → 20 байт заголовка.
- `18` — **флаги TCP**: `0x18` = `0001 1000` — установлены биты `PSH` и `ACK`.
- `01 f6` — размер окна: `0x01f6` = 502 байта.
- Последние 4 байта (в нашем дампе усечены) — контрольная сумма и указатель срочности.

Порт получателя `80` подтверждает: это HTTP-запрос к веб-серверу.

## Шаг 4: читаем флаги TCP

Байт флагов — самый информативный. Каждый бит означает своё:

| Бит | Флаг | Значение |
|-----|------|----------|
| 0x01 | FIN | завершение соединения |
| 0x02 | SYN | установка соединения |
| 0x04 | RST | сброс соединения |
| 0x08 | PSH | передать данные сразу |
| 0x10 | ACK | подтверждение |
| 0x20 | URG | срочные данные |

Наш байт `0x18` = `0x10 | 0x08` = ACK + PSH. Значит, это обычная передача данных с подтверждением. Установка соединения выглядела бы как `0x02` (SYN) или `0x12` (SYN+ACK).

Умение читать флаги важно при анализе трафика: сканирование портов, например, оставляет характерные SYN-пакеты без завершения.

## Шаг 5: TCP против UDP

В поле протокола IP мы видели `6` (TCP). Но бывает и `17` — UDP. Чем они отличаются:

- **TCP** — соединение: три шага рукопожатия (SYN, SYN-ACK, ACK), гарантия доставки и порядка. Используется там, где важна надёжность: HTTP, SSH, почта.
- **UDP** — без соединения: отправил и забыл, порядок не гарантирован. Используется там, где важна скорость: DNS, видео, игры.

В UDP-заголовке всего 8 байт: порт источника, порт получателя, длина и контрольная сумма. Никаких флагов и номеров последовательности.

## Как получить такой дамп самостоятельно

Пакет в hex можно получить несколькими способами. В `tcpdump` флаг `-X` печатает содержимое в hex и ASCII. В Wireshark правый клик по слою → Copy → «…as Hex Stream». А из скрипта — библиотека `scapy`:

```python
from scapy.all import rdpcap
pkt = rdpcap("capture.pcap")[0]
print(pkt.summary())
```

`scapy` разбирает пакет на те же слои и позволяет обратиться к любому полю по имени: `pkt[IP].ttl`, `pkt[TCP].flags`. Это удобно, когда нужно обработать тысячи пакетов скриптом, а не глазами.

## Инструмент: tshark — Wireshark в консоли

`tshark` — это Wireshark без графики: он читает дамп (`-r файл.pcap`) и печатает ровно то, что ты попросишь. Главный инструмент, когда графической оболочки нет или разбор надо автоматизировать.

Ключи, которые пригодятся:
* `-r <файл.pcap>` — читать дамп (без него tshark слушает живой интерфейс);
* `-nn` — не резолвить имена/порты: видно «как есть» и быстрее;
* `-Y '<фильтр>'` — display-фильтр, оставить только нужные пакеты (`http.request`, `dns`, `eapol`, `ospf`);
* `-T fields -e <поле>` — вместо сводки печатать значения полей (`-e ip.src -e tcp.dstport -e http.host`);
* `-q -z follow,tcp,ascii,N` — собрать TCP-поток номер N и показать его как текст.

### Рабочий пример (как в лаборатории)

```
$ tshark -r tcpip.pcap -T fields -e tcp.flags
0x0002
0x0012
0x0010
```

Подсказка из лаборатории: `tshark -r <pcap> [-nn] [-V] [-Y <фильтр>] [-T fields -e <поле>] — разбор дампа (эмуляция: реальный вывод tshark)`.

## Что мы теперь знаем

По-простому:

1. Пакет — это последовательность байтов, разбитая на слои.
2. Ethernet (14 байт) — MAC-адреса и тип.
3. IPv4 (20 байт) — адреса, TTL, протокол.
4. TCP (20 байт) — порты, номера, флаги.
5. Флаги TCP (`SYN`, `ACK`, `PSH`) говорят, что происходит в соединении.

## На что смотреть дальше

- **Начинайте с Ethernet-типа.** `0x0800` → IPv4, `0x0806` → ARP, `0x86DD` → IPv6.
- **Проверяйте TTL.** Необычный TTL выдаёт ОС и помогает фингерпринтингу.
- **Читайте флаги.** SYN без ответа — сканирование; RST — отказ.
- **Считайте длину.** Если длина заголовка не 20 байт, есть опции — их тоже надо прочесть.

## Разбор ICMP и ARP в дампе

TCP и UDP — не всё, что встретится. Возьмём ICMP-пакет и разберём его по слоям. После
Ethernet и IPv4 (протокол `01` = ICMP) идёт ICMP-заголовок:

```
08 00 3f 5c 12 34 00 01
```

- `08` — **тип** (type): `8` = Echo Request (ping), `0` = Echo Reply, `3` = Destination
  Unreachable, `11` = Time Exceeded (TTL истёк).
- `00` — **код** (code): уточняет тип (например, для `3` — «сеть недоступна», «порт
  недоступен»).
- `3f 5c` — **контрольная сумма**.
- `12 34` — **идентификатор** (для сопоставления запроса и ответа).
- `00 01` — **порядковый номер** эхо-пакета.

Тип и код — самое информативное. `Type 3, Code 3` (Port Unreachable) в ответ на твой запрос
подтверждает, что **хост жив, но порт закрыт**; `Type 3, Code 13` — что пакет отфильтрован
фаерволом. Это позволяет различать «закрыто» и «отфильтровано» без TCP-флагов.

**ARP** — вообще без IP-слоя: Ethernet-тип `0x0806`, дальше 28 байт ARP. Ключевые поля:
`Opcode` (`1` = Request, `2` = Reply), `Sender MAC/IP`, `Target MAC/IP`. ARP-запрос — это
широковещательный `ff:ff:ff:ff:ff:ff`. Аномалии в ARP — основа для детекта ARP-spoofing:
если один MAC объявляет себя владельцем **разных** IP, а `Sender MAC` не совпадает с
реальным — это подмена.

## Типичные значения EtherType и протокола IP

Держи таблицу под рукой: по двум байтам EtherType и одному байту IP-протокола определяется,
что читать дальше.

| EtherType | Внутри |
|-----------|--------|
| `0x0800` | IPv4 |
| `0x0806` | ARP |
| `0x8100` | VLAN (802.1Q) — далее снова EtherType |
| `0x86DD` | IPv6 |

| IP protocol | Протокол |
|-------------|----------|
| `1` | ICMP |
| `6` | TCP |
| `17` | UDP |
| `47` | GRE |
| `50`/`51` | ESP/AH (IPsec) |

Практический приём: если после Ethernet видишь `0x8100`, пакет помечен VLAN — сначала прочти
4 байта 802.1Q-тега, и только потом настоящий EtherType. Пропуск этого шага — частая ошибка
при разборе корпоративных дампов, где тегирование включено.
