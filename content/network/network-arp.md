ARP связывает IP-адрес с MAC в локальном сегменте, DNS — имя с IP. Оба протокола исторически **не аутентифицируют ответы**, поэтому их легко подделать. Это фундамент атак канального уровня и MITM. Урок опирается на [`network-intro`](network-intro).

## ARP: как работает

- Хост хочет отправить пакет на `10.0.0.1`, но знает только IP. Он шлёт **ARP-request** (broadcast): «у кого 10.0.0.1?».
- Владелец отвечает **ARP-reply** (unicast) со своим MAC.
- Результат кэшируется в **ARP-таблице** (`ip neigh` / `arp -a`).

```bash
ip neigh show
arp -a
# Запрос вручную
arping -I eth0 10.0.0.1
```

Проблема: ARP доверяет **любому** ответу — даже незапрошенному (**gratuitous ARP**). Кэш перезаписывается без проверки, а запись живёт десятки секунд-минут, поэтому достаточно периодически «обновлять» отравление.

## DNS: как работает

- Резолвер спрашивает у DNS-сервера запись (A/AAAA/MX/TXT).
- Ответ кэшируется по TTL.
- Классический DNS (без DNSSEC) не проверяет подлинность ответа.

```bash
dig example.com A
dig @10.0.0.1 example.com A
nslookup example.com
```

Уязвимости: подмена ответа на пути (MITM), отравление кэша резолвера, спуфинг source-port/transaction-ID. Последнее — классика: если угадать transaction ID (16 бит) и source port, можно «опередить» настоящий ответ и подсунуть свой.

## ARP-спуфинг

Атакующий шлёт жертве поддельные ARP-reply: «10.0.0.1 — это мой MAC». Трафик жертвы к шлюзу идёт через атакующего.

```bash
# Включить forwarding, иначе жертва потеряет связь
echo 1 | sudo tee /proc/sys/net/ipv4/ip_forward
# Отравляем обе стороны
sudo arpspoof -i eth0 -t 10.0.0.7 10.0.0.1
sudo arpspoof -i eth0 -t 10.0.0.1 10.0.0.7
# Или через bettercap (см. network-mitm)
sudo bettercap -iface eth0 -eval "set arp.spoof.targets 10.0.0.7; arp.spoof on; net.sniff on"
```

Двусторонний спуфинг нужен, чтобы перехватить и запросы, и ответы. Без `ip_forward` жертва останется без сети — атака станет заметной и приведёт к отказу в обслуживании.

## DNS-спуфинг

После занятия позиции MITM подменяем DNS-ответы: жертва идёт на подконтрольный IP.

```bash
# bettercap
set dns.spoof.domains example.com
set dns.spoof.address 10.0.0.99
dns.spoof on
# Классический dnsspoof
echo '10.0.0.99 example.com' > hosts.txt
sudo dnsspoof -i eth0 -f hosts.txt
```

Цель — фишинг (фейковая страница логина), подмена обновлений, перенаправление на эксплойт.

## ARP в IPv6: NDP

В IPv6 роль ARP играет **NDP** (Neighbor Discovery Protocol, ICMPv6): `Neighbor Solicitation`/`Neighbor Advertisement` заменяют ARP-request/reply, а `Router Solicitation`/`Router Advertisement` — часть DHCP. Спуфинг работает так же:

- **Rogue RA** — поддельный Router Advertisement делает атакующего шлюзом (или сбрасывает конфигурацию).
- **NA-спуфинг** — подмена Neighbor Advertisement для перехвата.

```bash
# RA-флуд (в лаборатории): mitm6 / fake_router6
# NDP-таблица
ip -6 neigh show
# Захват ICMPv6
tcpdump -i eth0 -n 'icmp6'
```

Защита: **RA Guard**, **NDP Inspection** (аналог DAI), фильтрация ICMPv6-типов на access-портах. В корпоративных сетях с Windows `mitm6` (RA + WPAD) — стандартный вектор получения NTLM-хэшей без ARP.

## Диагностика и детект

- **`ip neigh` / `arp -a`**: дубликаты MAC у разных IP или «прыгающий» MAC шлюза — признак отравления.
- **`arpwatch`**: уведомляет о смене привязок MAC↔IP.
- **Всплеск gratuitous ARP**: нормальный хост объявляет себя редко; атакующий — постоянно.
- **IDS-правила** на частые ARP-reply без запросов.

```bash
sudo arpwatch -i eth0
ip neigh show | awk '{print $5}' | sort | uniq -d   # дубли MAC
```

## ARP в контейнерах и виртуализации

- В **Linux bridge** и **veth**-парах ARP работает прозрачно; контейнеры в одном bridge — в одном L2-домене.
- **MACVLAN/IPVLAN** меняют поведение ARP.
- В **Kubernetes** CNI (Calico/Cilium) часто проксирует ARP (proxy_arp) — классический ARP-спуфинг может не сработать между подами.
- Для перехвата в контейнерной среде нужен доступ к bridge/host network.

```bash
# Интерфейсы и bridge
ip -br link; bridge link show
# Proxy ARP
sysctl net.ipv4.conf.all.proxy_arp
```

## ARP-таблицы: как читать состояние

```bash
# Linux
ip neigh show
cat /proc/net/arp
# Windows
arp -a
# Признаки отравления: один MAC у нескольких IP, MAC шлюза сменился
ip neigh show | awk '{print $5}' | sort | uniq -d   # дубли MAC
```

## DNS-кэш и его роль

```bash
# Посмотреть кэш (если есть локальный резолвер)
systemd-resolve --statistics 2>/dev/null
# Очистить кэш (для теста)
resolvectl flush-caches 2>/dev/null
```

Кэш DNS живёт по TTL; подмена работает до истечения. Для устойчивого перехвата атакующий отвечает на **каждый** запрос, а не один раз.

## Защита

- **Dynamic ARP Inspection (DAI)** + **DHCP snooping** (таблица привязок IP↔MAC).
- **Статические ARP-записи** для критичных хостов.
- **DNSSEC** — криптографическая подпись DNS-записей.
- **DoH/DoT** — шифрование DNS-запросов.
- **802.1X**, сегментация, мониторинг ARP-аномалий.

## Частые ошибки

- **Забыть `ip_forward`** — жертва теряет связь, атака заметна.
- **Думать, что ARP «лечится» на хосте** — нужны меры на коммутаторе.
- **Путать ARP- и DNS-спуфинг** — разные уровни (L2 vs L7).
- **Считать DNS безопасным** — без DNSSEC ответ легко подменить.
- **Не смотреть `ip neigh`** — следы отравления (дубликаты MAC).
- **Игнорировать TTL** — кэш истекает, нужна периодичность.

## Резюме практики

1. Убедиться, что мы в одном L2-домене с целью.
2. Включить forwarding и двусторонний спуфинг.
3. Перехватить/модифицировать трафик (bettercap/mitmproxy).
4. Восстановить ARP после атаки (послать корректные ответы).
5. Для IPv6 — проверить NDP/RA-вектор отдельно.

## Что дальше / решение

Маршрут: **ARP-спуфинг → MITM → DNS-спуфинг → перехват/модификация (bettercap/mitmproxy) → восстановление ARP**. Защита — DAI + DHCP snooping, DNSSEC, DoH/DoT, статические записи и мониторинг; IPv6 (NDP/RA) уязвим аналогично. Дальше — [`network-mitm`](network-mitm), [`network-arp-deep`](network-arp-deep) и [`network-dhcp`](network-dhcp).

## Механика ARP-спуфинга под капотом

Когда вы запускаете `arpspoof -i eth0 -t 10.0.0.7 10.0.0.1`, утилита каждые ~2 секунды отправляет жертве (`10.0.0.7`) ARP-reply: «IP `10.0.0.1` находится на MAC атакующего». Пакет идёт на **MAC жертвы** (unicast), поэтому коммутатор доставляет его только ей — остальные хосты ничего не замечают. Жертва обновляет ARP-кэш и начинает слать шлюзовой трафик на атакующий MAC. Вторая команда делает то же для шлюза: теперь шлюз думает, что IP жертвы — за атакующим. Получается «прозрачный мост»: атакующий принимает кадры, при необходимости модифицирует (например, меняет DNS-ответ) и пересылает дальше. Ключевой момент — **регулярность**: кэш истекает (Linux ~30-60 с, Windows может «липнуть» до минут), и без повторов связь восстановится. Именно поэтому `arpspoof` работает в цикле, а не однократно.

Вариант **half-duplex** (только одна сторона) полезен, когда нужно лишь подсмотреть исходящий трафик жертвы, не рискуя сломать обратный поток. Полный **full-duplex** даёт модификацию в обе стороны, но требует forwarding и аккуратной настройки, иначе половина сессии «повиснет».

## ARP в Wi-Fi и недоверенных средах

В беспроводной сети с общим ключом (WPA2-PSK) клиенты находятся в одном L2-домене, поэтому ARP-спуфинг работает так же, как в проводном сегменте: любой клиент с ключом может отравить соседа. В enterprise-WPA (802.1X) клиенты часто изолированы (client isolation), и спуфинг между ними не пройдёт. Если сеть использует **client isolation** или **private VLAN**, ARP-спуфинг блокируется на уровне инфраструктуры — тогда остаются атаки на сам AP (rogue AP/evil twin, см. [`network-evil-twin`](network-evil-twin)).

## Комбинированные цепочки

На практике ARP-спуфинг — это «вход», а не финал. Типовые цепочки: ARP-спуфинг + DNS-спуфинг → фишинг; ARP-спуфинг + SSL-strip/HTTP-инъекция → перехват cookie; ARP-спуфинг + WPAD → NTLM-хэши; ARP-спуфинг + DHCP-спуфинг (отдать свой шлюз/DNS) → полный контроль маршрутизации жертвы. В IPv6 цепочка `mitm6` + `ntlmrelayx` даёт релей без единого ARP-пакета — только RA/NDP.

## OPSEC и восстановление

Активный ARP-спуфинг заметен: `arpwatch` и DAI на коммутаторе его поймают, а неаккуратный спуфинг «уронит» сеть. Меры осторожности: отравляйте только нужные пары (не весь сегмент), включайте forwarding, ограничивайте объём перехвата и по завершении **восстановите ARP** — отправьте корректные ответы (`arpspoof` с реальными MAC или просто дождитесь истечения кэша, но лучше явно «вылечить» пары, чтобы не оставить сегмент в нерабочем состоянии). На пентесте фиксируйте время начала/конца отравления для отчёта.

## Быстрая диагностика: Linux и Windows

```bash
# Linux: соседи и дубли MAC
ip neigh show
ip neigh show | awk '{print $5}' | sort | uniq -d
# Windows: таблица и сброс
arp -a
netsh interface ip delete arpcache
# Проверить, что трафик действительно идёт через нас
tcpdump -i eth0 -n host 10.0.0.7 and not arp
```

Если после отравления `tcpdump` на атакующем **не** видит трафик жертвы, вероятные причины: другой L2-домен, client isolation, статическая ARP-запись на жертве или DAI на коммутаторе.

## Терминология для отчёта

Различайте термины, чтобы отчёт был точным: **ARP-poisoning** — активное отравление кэша поддельными ответами; **gratuitous ARP** — незапрошенный ответ (может быть и легитимным, при смене NIC); **ARP-flooding** — поток ответов со случайных IP (часто часть CAM-flooding); **half/full-duplex spoofing** — одна или обе стороны перехвата. **DAI** (Dynamic ARP Inspection) валидирует ARP по таблице DHCP snooping, а **NDP Inspection** делает то же для IPv6. Эти формулировки пригодятся в разделе «методика» и в рекомендациях.
