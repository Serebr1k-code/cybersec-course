## Вопрос, с которого всё начинается

Ты знаешь IP-адрес нужной машины, но как пакет находит её физически? И наоборот: как имя `example.com` превращается в IP? Оба ответа дают протоколы, которые **не проверяют подлинность ответов**. Именно поэтому их легко подделать — и на этом строится перехват в локальной сети.

Разберём на конкретном примере, как машина ищет соседа.

## Наш пример: кто такой 10.0.0.1?

Пусть машина `10.0.0.5` хочет поговорить с роутером `10.0.0.1` в той же локальной сети. На канальном уровне (Ethernet) адреса — это **MAC-адреса** (например, `aa:bb:cc:00:11:22`), а не IP. Значит, нужно выяснить, какой MAC у `10.0.0.1`.

Этим занимается **ARP** (Address Resolution Protocol). Машина рассылает широковещательный вопрос «кто владеет `10.0.0.1`?». Поймаем этот пакет:

```
$ tshark -r arp.pcap
    1  0.000000  aa:bb:cc:00:11:22 → Broadcast  ARP 42 Who has 10.0.0.1? Tell 10.0.0.5
```

Строка читается буквально: «Кто имеет `10.0.0.1`? Скажите `10.0.0.5`». Владелец отвечает:

```
    2  0.000215  de:ad:be:ef:00:01 → aa:bb:cc:00:11:22  ARP 42 10.0.0.1 is at de:ad:be:ef:00:01
```

Теперь `10.0.0.5` знает MAC роутера и запоминает его в **ARP-кэше** — маленькой таблице «IP → MAC», чтобы не спрашивать каждый раз.

## Шаг 1: разбираем ARP по полям

Посмотрим тот же запрос в подробном виде.

```
$ tshark -r arp.pcap -V | grep -iE "Opcode|Sender MAC|Sender IP|Target MAC|Target IP"
    Opcode: request (1)
    Sender MAC address: aa:bb:cc:00:11:22
    Sender IP address: 10.0.0.5
    Target MAC address: 00:00:00:00:00:00
    Target IP address: 10.0.0.1
```

Ключевое поле — **Opcode**: `1` = запрос, `2` = ответ. `Target MAC` в запросе пустой (`00:00:...`) — мы же его ещё не знаем, именно за ним и пришли.

Вот здесь и корень уязвимости: **в ARP нет аутентификации**. Любая машина может послать ответ, даже если её никто не спрашивал. И жертва ему поверит.

## Шаг 2: gratuitous ARP

Особый вид — **gratuitous ARP** («бесплатный ARP»): ответ, который шлётся без запроса, обычно всем (`Broadcast`). Его используют, чтобы объявить свой адрес при подключении. Но точно так же его может использовать атакующий.

```
    3  0.000332  de:ad:be:ef:00:01 → Broadcast  ARP 42 Gratuitous ARP for 10.0.0.1 (Reply)
```

Здесь `de:ad:be:ef:00:01` объявляет: «`10.0.0.1` — это я». Если машины поверят и обновят кэш, весь трафик к роутеру пойдёт **не к роутеру**, а к этому MAC. Это и есть **ARP-спуфинг** — основа перехвата (MITM) в локальной сети.

## Шаг 3: DNS — то же самое, но с именами

Пока машина внутри сети ищет MAC по IP, для внешнего мира нужно обратное: имя → IP. Этим занимается **DNS** (Domain Name System). Ты пишешь `example.com`, а резолвер возвращает `93.184.216.34`.

DNS-запрос выглядит так:

```
$ dig example.com +short
93.184.216.34
```

А полный ответ содержит вопрос и **ответные записи**:

```
$ dig example.com A
;; QUESTION SECTION:
;example.com.   IN  A
;; ANSWER SECTION:
example.com.  300  IN  A  93.184.216.34
```

Ключевое поле — **TTL** (`300` секунд): сколько ответ можно держать в кэше. И снова проблема: классический DNS (без DNSSEC) **не проверяет подлинность ответа**. Кто первый прислал ответ — тому и поверят.

## Шаг 4: DNS-спуфинг

Отсюда **DNS-спуфинг**: атакующий в позиции MITM подделывает ответ DNS, и жертва идёт не на настоящий сайт, а на подставной. Классический сценарий — подменить ответ на запрос к банку и показать фейковую страницу логина.

Есть и родственные техники:

- **Cache poisoning** — отравить кэш резолвера, чтобы обманывать всех его клиентов;
- **DNS rebinding** — заставить браузер обратиться к внутреннему адресу, меняя ответ между запросами.

Важно: DNS-спуфинг требует либо позиции MITM, либо уязвимого резолвера. Просто «перехватить» чужой ответ из другого сегмента нельзя.

## Шаг 5: как это используют вместе

Комбинация ARP-спуфинга и DNS-спуфинга — рабочая связка для MITM:

1. ARP-спуфингом встаём между жертвой и роутером;
2. перехватываем её DNS-запросы;
3. отвечаем поддельным IP;
4. жертва подключается к нашему серверу.

Дальше — уже тема следующего урока: как перехватывать и модифицировать трафик инструментами вроде `bettercap`.

## Шаг 6: защита

- **Dynamic ARP Inspection (DAI)** на коммутаторах — отбрасывает подозрительные ARP;
- **DHCP snooping** — строит доверенную таблицу «IP → MAC → порт»;
- **Static ARP** для критичных узлов (неудобно, но надёжно);
- **DNSSEC** — криптографическая подпись DNS-ответов;
- **DoH/DoT** — шифрование DNS, чтобы его нельзя было подделать по пути;
- **Мониторинг:** много gratuitous ARP, смена MAC у одного IP, конфликты адресов — сигналы.

## ARP в мире IPv6

Раз уж мы разобрали ARP, стоит упомянуть, что в IPv6 его нет. Там ту же роль играет **NDP** (Neighbor Discovery Protocol) — набор сообщений ICMPv6, которые разрешают адреса и объявляют о себе. Проблема сохраняется: NDP тоже не аутентифицирует ответы, и есть аналог спуфинга — **rogue router advertisement** и **NDP spoofing**. Логика ровно та же: устройство верит тому, кто первым прислал ответ.

Для практики это значит: если в сети есть IPv6 (а он часто включён «по умолчанию» и забыт), ARP-спуфинг можно обойти, но появляется NDP-спуфинг. Защита — **RA Guard** и **IPv6 First-Hop Security** на коммутаторах, аналогично DAI для IPv4.

## Шаг 7: мини-практика — смотрим ARP-кэш

Полезный навык — уметь посмотреть, что машина «думает» о соседях. В Linux ARP-кэш показывается так:

```
$ ip neigh
10.0.0.1 dev eth0 lladdr de:ad:be:ef:00:01 REACHABLE
10.0.0.9 dev eth0 lladdr aa:bb:cc:00:11:22 STALE
```

Каждая строка — пара «IP → MAC» и состояние записи (`REACHABLE` — недавно подтверждена, `STALE` — устарела). Если у `10.0.0.1` внезапно окажется **другой** MAC, чем раньше, — это повод насторожиться: возможно, кто-то отравил кэш.

Сравнить текущий кэш с ожидаемым можно так: записать вывод `ip neigh` до и после, либо вести эталонный список для шлюза. На коммутаторах для этой же цели смотрят таблицу MAC-адресов (`show mac address-table`) — если один порт вдруг «владеет» множеством адресов, это признак флудинга или спуфинга.

## Что мы теперь знаем

- ARP переводит IP в MAC внутри локальной сети и хранит результат в ARP-кэше.
- Opcode `1` — запрос, `2` — ответ; в ARP нет аутентификации.
- Gratuitous ARP без запроса позволяет подменить «владельца» IP (ARP-спуфинг).
- DNS переводит имя в IP и тоже не проверяет ответы без DNSSEC.
- ARP + DNS-спуфинг вместе дают полноценный MITM.
- Защита — DAI, DHCP snooping, DNSSEC, DoH/DoT.
