## Вопрос, с которого всё начинается

Сотрудник заходит в корпоративную сеть через VPN, и ты видишь зашифрованный поток. Задача: понять, какой это VPN, что в нём видно снаружи и есть ли ошибки в настройке, которые позволяют перехватить сессию. Возьмём **OpenVPN** — популярный VPN поверх TLS.

Он прячет трафик в TLS, но конфигурация решает, насколько хорошо. Разберём.

Этот урок опирается на [`network-tcpip`](network-tcpip) и [`network-tls-inspection`](network-tls-inspection).

## Наш пример: загадочный UDP-поток

В дампе — UDP-трафик на нестандартном порту. Смотрим, какие пакеты по нему идут:

```
$ tshark -r vpn.pcap -Y openvpn -T fields -e openvpn.opcode | sort | uniq -c
     38 7
     12 10
    410 9
```

Числа — это **opcode** (тип пакета OpenVPN), и они видны! Значит, control-канал не зашифрован. Разберём, что это значит.

## Шаг 1: как устроен OpenVPN

- **Control-канал** — TLS-handshake (обмен ключами, аутентификация).
- **Data-канал** — шифрование полезной нагрузки (AES-GCM/ChaCha20).
- **Транспорт** — UDP/1194 (типично) или TCP/443 (обход фильтров).
- **Аутентификация** — сертификаты (mTLS) + опционально логин/пароль.
- **tls-auth / tls-crypt** — дополнительная защита control-канала.

## Шаг 2: что видно в трафике

- **UDP/1194** (или нестандартный порт) — первый признак.
- **TLS-handshake**: версия, шифры, размеры.
- **Без tls-crypt** — видны `P_CONTROL`-пакеты (opcode 7/8), трафик легко отличить от обычного TLS.
- **Сертификаты** в handshake (CN, issuer), если не зашифрованы.

Посмотрим opcode и сертификаты:

```
$ tshark -r vpn.pcap -Y 'tls.handshake.type==11' -V | grep -i 'CN='
        CN=openvpn-server
```

Мы видим имя сертификата сервера. В нашем случае opcode видны — значит, **tls-crypt не включён**.

## Шаг 3: чем это плохо — MITM

Разберём опасный сценарий. Если у клиента нет опции проверки сертификата сервера (`remote-cert-tls server` / `verify-x509-name`), он примет **любой** сертификат. Тогда атакующий поднимает свой OpenVPN-сервер, и клиент подключается к нему.

Ещё хуже, если утёк **CA-ключ** (`ca.key` — например, лежит в git или на веб-сервере). Тогда можно выпустить сертификат, которому клиент точно доверяет:

```
$ openssl req -new -key srv.key -out srv.csr -subj "/CN=openvpn-server"
$ openssl x509 -req -in srv.csr -CA ca.crt -CAkey ca.key -CAcreateserial -out srv.crt -days 30
```

С этим сертификатом поднимаем свой сервер — и весь трафик клиента идёт через нас. Дальше — перехват учётных данных внутренних сервисов.

## Шаг 4: аудит конфигурации

Проверим клиентский `.ovpn` на опасные директивы:

```
$ grep -Ei 'verify-x509-name|remote-cert-tls|tls-crypt|tls-auth|comp-lzo' client.ovpn
remote-cert-tls server
```

Если `remote-cert-tls server` есть — MITM-сервер отклонится. Если нет — уязвимо. Отсутствие `tls-crypt` означает, что control-канал виден.

Типовые мисконфигурации:

- **Нет `verify-x509-name`/`remote-cert-tls server`** — MITM-сервер принимается.
- **Утечка `ca.key`** — можно выпустить произвольного клиента.
- **Слабый data-cipher** (BF-CBC, DES) — устаревшее шифрование.
- **Нет `tls-crypt`** — control-канал виден, DoS и фингерпринт.
- **`comp-lzo`** — уязвимость VORACLE (сжатие + MITM).

## Шаг 5: tls-auth против tls-crypt

| Свойство | tls-auth | tls-crypt |
|---|---|---|
| Что делает | HMAC control-пакетов | HMAC **и** шифрование control |
| Видны ли opcode | да | нет |
| Защита от DoS | частичная | сильнее |
| Рекомендация | устаревает | предпочтительно |

Разница практическая: если видишь opcode — стоит `tls-auth` или ничего; если видишь только `P_DATA_V*` — включён `tls-crypt`.

## Шаг 6: защита

- **tls-crypt** (или tls-auth) для control-канала.
- **verify-x509-name + remote-cert-tls server** на клиентах.
- **AES-256-GCM / ChaCha20-Poly1305**, отключить BF/DES.
- Хранить `ca.key` оффлайн; короткоживущие сертификаты + CRL.
- Отключить сжатие, включить MFA и логирование.

## Разбор OpenVPN по opcode

OpenVPN кодирует тип пакета в **opcode**. Без `tls-crypt` они видны и позволяют классифицировать трафик даже на нестандартном порту:

- `P_CONTROL_HARD_RESET_CLIENT_V2/V3` — начало сессии (клиент);
- `P_CONTROL_HARD_RESET_SERVER_V2/V3` — ответ сервера;
- `P_CONTROL_V1` — управляющие;
- `P_ACK_V1` — подтверждения;
- `P_DATA_V1/V2` — данные (шифрованные).

Если видите только `P_DATA_V*` без control — вероятно, включён `tls-crypt`.

## Если не сработало

OpenVPN не удаётся проанализировать? Проверь:

- **Нестандартный порт.** Порт легко сменить — ориентируйся по opcode, а не по 1194.
- **Включён tls-crypt.** Тогда control-канал зашифрован и opcode не видны — видно только зашифрованные данные.
- **Сертификат проверяется.** Если есть `remote-cert-tls server`, MITM не сработает — это и есть защита.
- **Уже IKEv2/WireGuard.** Возможно, ты смотришь не на OpenVPN; сверь сигнатуру.

## Практика пентеста VPN

- **Определить VPN** по порту и сигнатуре (`nmap -sU -p1194 --script openvpn-info`).
- **Искать конфиги** клиента на скомпрометированных хостах (`.ovpn`, ключи, `auth-user-pass`).
- **Проверять проверку сертификата** (поднять свой сервер с тем же CA).
- **Брутить логин/пароль**, если включён `auth-user-pass` — только малый список, онлайн-перебор дорог.
- **Не ломать туннель** — VPN часто критичен для бизнеса.

## Практический сценарий: MITM через утёкший CA

Если `ca.key` утёк (лежит на веб-сервере, в git, в бэкапе), можно выпустить **своего клиента** и поднять сервер, которому доверяет жертва:

1. Находим утёкший CA: `ca.crt` + `ca.key` — можно подписывать сертификаты.
2. Выпускаем серверный сертификат, подписанный тем же CA (команды `openssl` выше).
3. Поднимаем свой OpenVPN-сервер; клиент (без `verify-x509-name`) подключается.
4. Весь трафик клиента идёт через нас — MITM внутренних сервисов.

Даже без `ca.key` клиент без `remote-cert-tls server` примет **любой** сертификат — достаточно самоподписанного.

## Логи и диагностика

```
$ openvpn --config client.ovpn --verb 4
$ ip addr show tun0
$ ip route | grep tun0
```

Типовые ошибки: `AUTH_FAILED` (сертификат/пароль), `TLS handshake failed` (несовпадение крипто), `Cannot open TUN/TAP` (нет прав/модуля).

## Что мы теперь знаем

- OpenVPN использует TLS: control-канал и data-канал.
- Без `tls-crypt` видны opcode и сертификаты — трафик легко классифицируется.
- Клиент без `remote-cert-tls server`/`verify-x509-name` принимает MITM-сервер.
- Утёкший `ca.key` позволяет выпустить доверенный сертификат.
- Защита — tls-crypt, проверка сертификата, современные шифры, оффлайн `ca.key`.
- Для пентеста важны: определение сервиса, поиск клиентских конфигов и проверка устойчивости к MITM.
- OpenVPN безопасен ровно настолько, насколько верна его конфигурация.

## Опкоды управляющего канала: разбираем P_CONTROL

OpenVPN на проводе узнаётся не по порту, а по первому байту полезной нагрузки, где упакованы **opcode** (5 бит) и **key-id** (3 бита). Умение читать опкод позволяет отличить управляющий канал от канала данных даже на нестандартном порту.

Шаг 1. Раскладываем первый байт. Значение байта `0x38` = `00111000`: старшие 5 бит `00111` = 7 (opcode), младшие 3 бита `000` = key-id 0. Раскладка опкодов OpenVPN:

| Opcode | Значение | Канал |
|---|---|---|
| 4 | P_CONTROL_V1 | управление (TLS) |
| 5 | P_ACK_V1 | подтверждение |
| 6 | P_DATA_V1 | данные |
| 7 | P_CONTROL_HARD_RESET_CLIENT_V2 | старт клиента |
| 8 | P_CONTROL_HARD_RESET_SERVER_V2 | ответ сервера |
| 9 | P_DATA_V2 | данные (с peer-id) |

Шаг 2. Смотрим распределение опкодов в дампе:

```
$ tshark -r ovpn.pcap -Y 'udp.port==1194' -T fields -e data | cut -c1-2 | sort | uniq -c | sort -rn
    612 40
    288 48
     96 38
     12 30
```

`40` = 0x40 = `01000000` → opcode 8 (HARD_RESET_SERVER_V2). `48` = 0x48 → `01001000` → opcode 9 (P_DATA_V2). `38` = 0x38 → opcode 7 (HARD_RESET_CLIENT_V2). `30` = 0x30 → opcode 6 (P_DATA_V1). Картина типична для сессии: сначала обмен hard-reset, затем поток данных с редкими control/ack.

Шаг 3. Что это даёт безопаснику. Во-первых, идентификация: если раньше вы не знали, что это OpenVPN, распределение опкодов с «магическими» значениями 7/8 в начале сессии — надёжная сигнатура. Во-вторых, оценка конфигурации: наличие **P_DATA_V1** (opcode 6) вместо V2 (9) означает, что сервер не поддерживает peer-id и `float` — старый режим, где для роуминга клиента требуется сброс сессии. В-третьих, детект MITM: перехватчик, не имеющий ключа tls-crypt, не сможет подделать control-пакеты, и в логе будут видны повторные hard-reset — признак вмешательства.

Шаг 4. Связь с защитой. Если в конфиге включён `tls-crypt`, весь управляющий канал (все P_CONTROL_*) зашифрован статическим ключом, и по первому байту виден только тип, но не содержимое. Если включён лишь `tls-auth`, control-пакеты аутентифицированы HMAC, но TLS handshake виден — из него утекают версия TLS, набор шифров и иногда данные клиента. Именно поэтому `tls-crypt` предпочтительнее: он скрывает и метаданные, и защищает от простого оффлайн-анализа управляющего канала. Для проверки в дампе достаточно сравнить долю читаемых control-пакетов: при `tls-auth` видны TLS-записи внутри P_CONTROL, при `tls-crypt` — только случайные байты.
