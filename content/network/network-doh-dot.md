DNS исторически открыт и виден всем: провайдер, корпоративный шлюз и любой в середине канала знают, какие домены вы запрашиваете. Чтобы это скрыть, появились **DNS over HTTPS (DoH)**, **DNS over TLS (DoT)** и **DNS over QUIC (DoQ)**. Для приватности это плюс, для корпоративной безопасности — проблема: фильтрация и логирование DNS по именам перестают работать, а злоумышленник получает удобный шифрованный канал для эксфильтрации.

## DoH, DoT, DoQ: что это

- **DoT** (RFC 7858) — DNS поверх TLS на порту **853**; отдельное соединение, легко узнаётся по порту.
- **DoH** (RFC 8484) — DNS-запрос как обычный HTTPS (обычно `POST /dns-query`, `application/dns-message`), порт **443**; сливается с обычным веб-трафиком.
- **DoQ** (RFC 9250) — DNS поверх QUIC (UDP/853); быстрее, но тоже узнаётся по порту.

Разница принципиальна: DoT/DoQ легко блокируются по порту, а DoH неотличим от HTTPS без глубокого анализа (SNI/сертификата).

| Протокол | Порт | Транспорт | Видимость |
|---|---|---|---|
| DoT | 853 | TLS/TCP | Порт узнаваем |
| DoH | 443 | HTTPS | Сливается с веб |
| DoQ | 853 | QUIC/UDP | Порт узнаваем |
| Classic DNS | 53 | UDP/TCP | Полностью виден |

## Почему это ломает фильтрацию и мониторинг

Корпоративные политики часто основаны на **DNS-фильтрации**: блокируют домены (malware, соцсети) по именам. Если браузер использует DoH, он спрашивает свой резолвер (Cloudflare/Google) напрямую, и корпоративный DNS не видит запросов. Возможные последствия:

- обход блокировок и родительского контроля;
- потеря логов DNS для SOC/IR;
- работа malware, который резолвит C2 через DoH;
- эксфильтрация данных в DNS-запросах внутри TLS.

## Инструменты

- **dnscrypt-proxy** — клиент с DoH/DoT/ODoH, локальный прокси.
- **cloudflared** — DoH-прокси.
- **kdig / dog / q** — запросы DoT/DoH из CLI.
- **dnsproxy (AdGuard)** — локальный резолвер с DoH/DoT.
- **tshark** — детект по SNI/порту.
- **Zeek** — анализ DNS и DoH-потоков.

```bash
# DoT-запрос
kdig @1.1.1.1 +tls example.com
# DoH-запрос
curl -s -H 'accept: application/dns-json' \
  'https://cloudflare-dns.com/dns-query?name=example.com&type=A'
# dog с DoH
dog example.com @https://cloudflare-dns.com/dns-query
```

## Разобранный пример: детект DoH в дампе

1. Захватываем трафик клиента с включённым DoH.
2. Ищем HTTPS-соединения к известным DoH-эндпоинтам по SNI:
   ```bash
   tshark -r cap.pcap -Y 'tls.handshake.extensions_server_name' \
     -T fields -e ip.dst -e tls.handshake.extensions_server_name | sort -u
   ```
   Увидите `cloudflare-dns.com`, `dns.google`, `mozilla.cloudflare-dns.com`.
3. Если SNI зашифрован (ECH), смотрим на поведение: частые короткие POST-запросы к одному хосту, `content-type: application/dns-message`.
4. Для DoT: фильтр по порту 853: `tcp.port==853`.
5. В отчёте фиксируем обход фильтрации; политика — блокировать известные DoH-эндпоинты и/или форсировать корпоративный резолвер.

## Скрытые каналы через DoH

DoH можно использовать как канал эксфильтрации: данные кодируются в поддомены запроса (`<base32data>.attacker.com`), а ответы — в TXT/AAAA-записях. Внутри TLS это невидимо для DPI по содержимому. Признаки: аномально много DNS-запросов к одному домену, длинные поддомены, энтропийные метки. Детект — на уровне резолвера (если DoH форсирован) или по статистике TLS-потоков (Zeek `ssl`/`dns`). См. также `network-dns-tunnel` и `network-covert`.

## Частые ошибки и подводные камни

- **Считать, что DoH полностью скрывает DNS.** Метаданные (SNI, IP, тайминги, размеры) остаются.
- **Блокировать порт 853, забывая про DoH на 443.** DoH пройдёт.
- **Форсировать DoH внутри компании без логирования.** Вы теряете видимость — нужен свой DoH-резолвер с логами.
- **Игнорировать ECH.** Encrypted Client Hello скрывает SNI, усложняя детект.
- **Путать DoH-резолвер и DoH-прокси.** Первое — DNS, второе — общий HTTPS-прокси.

## Что дальше / решение

DoH/DoT — часть темы «DNS как канал и как цель». Свяжите с `network-dns-attacks`, `network-dns-tunnel`, `network-covert` и `network-tls-inspection`. Для защиты форсируйте корпоративный резолвер, блокируйте публичные DoH-эндпоинты и ведите логи. Для CTF потренируйтесь извлекать данные из DoH-дампов и строить собственный DoH-клиент.

## DoH в браузерах и приложениях

Современные браузеры (Firefox, Chrome, Edge) умеют DoH «из коробки» и часто включают его автоматически при определённых настройках. В Firefox это `network.trr.mode` (0 — off, 2 — fallback, 3 — DoH only, 5 — off by choice). Chrome использует «Secure DNS» с автоапгрейдом. Мобильные ОС (Android 9+, iOS 14+) поддерживают DoH/DoT на уровне системы, а многие приложения (Telegram, Signal, banking) — свои резолверы.

Для пентеста это означает: даже если вы заблокировали DNS на шлюзе, приложение может резолвить через DoH. Проверка:

```bash
# В Linux: перехватить и посмотреть, куда идут DNS-запросы
sudo tcpdump -i any -nn 'udp port 53 or tcp port 53 or tcp port 853 or (tcp port 443 and (host 1.1.1.1 or host 8.8.8.8))'
```

Если видите трафик на 1.1.1.1/8.8.8.8:443 и ничего на 53 — приложение использует DoH. Для форсирования своего резолвера применяют firewall-правила, DNAT на 53 и блокировку известных DoH-IP, а также GPO.

## ECH и будущее DNS-приватности

**Encrypted Client Hello (ECH)** шифрует SNI в TLS-хендшейке, поэтому DPI больше не видит, к какому домену идёт соединение. В связке с DoH это делает DNS-трафик почти невидимым. Детект смещается на другие признаки: IP-адреса назначения, тайминги, размеры, сертификаты (если они не скрыты), поведенческие эвристики. Для SOC это означает переход от «смотри имена доменов» к «анализируй метаданные и репутацию IP». ECH пока разворачивается постепенно, но тренд очевиден: видимость DNS будет только падать, и защита должна строиться на endpoint-контроле, а не только на сети.

## Лаборатория: собственный DoH-резолвер

1. Поднимите `dnscrypt-proxy` или AdGuard `dnsproxy` с DoH-апстримом.
2. Настройте его как системный резолвер и убедитесь, что `dig` работает.
3. Захватите трафик: убедитесь, что на 53 ничего не идёт, а на 443 — POST к `dns-query`.
4. Заблокируйте DoH-эндпоинт на шлюзе — резолвинг сломается (если нет fallback).
5. Настройте корпоративный резолвер с логированием и форсируйте его через firewall; убедитесь, что все запросы видны.

Это показывает и приватность, и цену потери видимости.
