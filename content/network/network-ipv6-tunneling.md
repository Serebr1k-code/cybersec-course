## Вопрос, с которого всё начинается

Ты скомпрометировал хост во внутренней сети. Egress-firewall режет всё лишнее: наружу проходит только несколько «рабочих» протоколов, а произвольный TCP душится. Но ты замечаешь, что у хоста включён двойной стек, а правила firewall написаны только под IPv4.

Вопрос урока: можно ли пронести IPv6-трафик наружу, даже если «настоящего» IPv6 в сети нет, — и как этот канал выглядит на проводе.

## Наш пример: хост с двойным стеком

Смотрим, что у хоста с IPv6:

```
$ ip -6 addr show scope global
$ ip -6 route show
fe80::/64 dev eth0 proto kernel metric 256 pref medium
```

Global-адресов нет, в маршрутах только link-local. То есть «настоящего» IPv6-провайдера нет. Но это не значит, что IPv6 недоступен: его можно **пронести через IPv4** с помощью переходного механизма. А блокировки для него может и не быть.

## Шаг 1: зачем нужны переходные механизмы

Пока не весь интернет на IPv6, нужны способы «пронести» IPv6 через IPv4-инфраструктуру:

- **6in4** — IPv6 в явном IPv4-туннеле (IP-протокол 41).
- **6to4** — автоматический туннель, префикс `2002::/16`, адрес встраивает IPv4.
- **Teredo** — IPv6 через UDP/3544 (обходит NAT).
- **ISATAP** — IPv6 внутри интрасети, адрес содержит IPv4 хоста.

Каждый из них — потенциальный канал в обход IPv4-фильтров.

## Шаг 2: поднимаем 6in4-туннель

Самый простой механизм: IPv6-пакеты инкапсулируются в IPv4 с **Protocol=41**. Многие firewall пропускают «неизвестный» протокол 41, не заглядывая внутрь.

```
$ sudo ip tunnel add tun6 mode sit remote 192.0.2.1 local 10.0.0.2 ttl 64
$ sudo ip link set tun6 up
$ sudo ip -6 addr add 2001:db8:1::2/64 dev tun6
$ sudo ip -6 route add ::/0 via 2001:db8:1::1 dev tun6
$ ip -6 addr show dev tun6
    inet6 2001:db8:1::2/64 scope global
       valid_lft forever preferred_lft forever
```

У нас появился global IPv6-адрес `2001:db8:1::2`, хотя сети IPv6 нет. `sit` — это тип туннеля «IPv6 в IPv4»; `remote` — брокер, который несёт наш IPv6 в мир.

## Шаг 3: видим инкапсуляцию на проводе

Проверяем, что трафик действительно уходит наружу как IPv4-пакеты с протоколом 41:

```
$ ping6 -c2 2001:4860:4860::8888
$ sudo tcpdump -i eth0 -nn 'ip proto 41' -c 2
10.0.0.2 > 192.0.2.1: IP6 2001:db8:1::2 > 2001:4860:4860::8888: ICMP6, echo request
192.0.2.1 > 10.0.0.2: IP6 2001:4860:4860::8888 > 2001:db8:1::2: ICMP6, echo reply
```

Внешний заголовок — IPv4 (`10.0.0.2 > 192.0.2.1`), а внутри — целый IPv6-пакет. Если firewall не смотрит proto 41, канал проходит. Для SOC это красный флаг: **proto 41 на периметре** почти всегда нелегитимен.

## Шаг 4: 6to4, Teredo, ISATAP — автоматика

Три механизма поднимаются без явного брокера:

- **6to4** — префикс `2002::/16`, адрес выводится из публичного IPv4 (hex). Трафик идёт через relay-маршрутизаторы, аутентификации нет.
- **Teredo** — префикс `2001:0000::/32`, IPv6 внутри **UDP/3544**. Обходит NAT, потому что это обычный UDP, который часто разрешён наружу.
- **ISATAP** — интерфейсный идентификатор `::5efe:A.B.C.D`, IPv6 внутри интрасети.

У каждого — узнаваемый префикс или порт, и это ключ к детекту:

| Механизм | Префикс / признак |
|---|---|
| 6to4 | `2002::/16` (встраивает IPv4) |
| Teredo | `2001:0000::/32`, UDP/3544 |
| ISATAP | интерфейсный ID `::5efe:A.B.C.D` |
| 6in4 | proto 41, адреса брокера |
| NAT64 | `64:ff9b::/96` |

## Шаг 5: почему это обходит периметр

- **Firewall настроен на IPv4** — IPv6-политики нет или она «allow all».
- **Протокол 41 не инспектируется** — 6in4 проходит как «неизвестный».
- **UDP/3544 разрешён** — Teredo маскируется под UDP.
- **Двойной стек** — хост сам поднимает туннель без ведома администратора.

Итог: скомпрометированный хост поднимает 6to4/Teredo-туннель и получает IPv6-канал в интернет, минуя IPv4-фильтры и логи.

## Шаг 6: детект и защита

Ищем не-IPv4 протоколы и характерные префиксы в дампе:

```
$ tshark -r cap.pcap -T fields -e ip.proto | sort | uniq -c | sort -rn | head
   8412	6
    233	41
     57	17
```

Протокол `41` (это и есть 6in4) в обычном офисе — повод для расследования. Дальше:

```
$ tshark -r cap.pcap -Y 'udp.port==3544' -T fields -e ip.src -e ip.dst | head
$ tshark -r cap.pcap -Y 'ipv6' -T fields -e ipv6.src | grep -E '^2002:'
```

Защита — это, прежде всего, **явная IPv6-политика** вместо «allow all», блокировка proto 41 и UDP/3544 на периметре и отключение авто-туннелей на хостах:

```
$ sudo sysctl -w net.ipv6.conf.all.disable_ipv6=1
```

## Сравнение переходных механизмов

| Механизм | Инкапсуляция | Аутентификация | Префикс/порт |
|---|---|---|---|
| 6in4 | IPv6 в IPv4 (proto 41) | нет | адрес брокера |
| 6to4 | автоматически в IPv4 | нет | 2002::/16 |
| Teredo | IPv6 в UDP | нет | 2001:0::/32, 3544 |
| ISATAP | IPv6 в IPv4 интрасеть | нет | ::5efe:A.B.C.D |
| NAT64 | IPv6 в IPv4 | операторская | 64:ff9b::/96 |

Общее у всех — отсутствие аутентификации и зависимость от внешней инфраструктуры (relay/брокер). Это делает их удобными для обхода и одновременно заметными при правильном мониторинге.

## Модель угроз и чек-лист

Для пентеста внутренней сети:

1. Проверить, включён ли двойной стек (`ip -6 addr`, `ip -6 route`).
2. Найти, разрешён ли наружу proto 41 и UDP/3544.
3. Попробовать поднять 6in4/Teredo и проверить связность IPv6.
4. Проверить, применяется ли IPv6-политика firewall (часто «allow all»).
5. Оценить, логируется ли IPv6-трафик.
6. Для защиты: блокировать авто-туннели, задать явную политику, мониторить proto 41/Teredo.

```
$ ip -6 addr show scope global
$ sysctl net.ipv6.conf.all.forwarding net.ipv6.conf.all.accept_ra
```

Если IPv6-адрес есть, а политики нет — это готовый канал в обход IPv4-фильтров, который стоит проверить и закрыть.

## Что мы теперь знаем

- Переходные механизмы несут IPv6 внутри IPv4: 6in4 (proto 41), 6to4, Teredo, ISATAP.
- Подняв 6in4-туннель, хост получает global IPv6 без IPv6-сети.
- Teredo идёт через UDP/3544 и потому часто проходит NAT и фильтры.
- У каждого механизма есть узнаваемый префикс или порт — это основа детекта.
- Защита: явная IPv6-политика, блокировка proto 41/UDP 3544, отключение авто-туннелей.

## Разбираем 6in4-туннель в дампе

Мы подняли туннель — теперь посмотрим, как он выглядит на проводе. Снаружи это IPv4 с протоколом 41 (IPv6-in-IPv4):

```
$ tshark -r tunnel.pcap -Y "ip.proto==41" -T fields -e ip.src -e ip.dst -e ipv6.src -e ipv6.dst -c 2
203.0.113.10  203.0.113.20  2001:db8:1::10  2001:db8:1::20
```

Читается так: два IPv4-адреса (границы туннеля) несут внутри полноценный IPv6-пакет с другими адресами. Для межсетевого экрана это просто «IP proto 41» — если правило не написано явно, такой трафик может пройти незамеченным или, наоборот, быть заблокирован «на всякий случай».

Важное следствие: **внешний фильтр проверяет IPv4-заголовок**, а вся логика доступа — во внутреннем IPv6. Ты можешь быть заблокирован «снаружи» и при этом иметь полный доступ «внутри».

## Teredo и ISATAP: автоматика опаснее ручного туннеля

Ручной 6in4 требует настройки, а вот **Teredo** и **ISATAP** поднимаются сами. Teredo инкапсулирует IPv6 в **UDP/3544**, поэтому проходит даже там, где IP-протокол 41 закрыт. Адрес Teredo кодирует внешний IPv4 прямо внутри `2001:0::/32`:

```
2001:0:4136:e378:8000:63bf:3fff:fdd2
```

В этом адресе зашифрованы IP Teredo-сервера и порт клиента — то есть видно, откуда и куда идёт канал, но сам канал «легитимен» с точки зрения UDP. ISATAP использует суффикс `:0:5efe:<IPv4>` внутри адреса и ходит по протоколу 41.

## Таблица: переходные механизмы

| Механизм | Транспорт | Адресный префикс | Авто-настройка |
|---|---|---|---|
| 6in4 | IP proto 41 | любой | нет (ручной) |
| 6to4 | IP proto 41 | 2002::/16 | да |
| Teredo | UDP/3544 | 2001:0::/32 | да |
| ISATAP | IP proto 41 | :0:5efe: | да |
| NAT64/DNS64 | IPv4 | 64:ff9b::/96 | да |

Видно общий паттерн: автоматические механизмы (Teredo, 6to4, ISATAP) включаются без ведома администратора и живут годами. Именно они — «вторая дверь» в периметр.

## Почему это обходит периметр

Причина в **асимметрии правил**. Администратор пишет политики для IPv4: «закрыть всё, кроме 443». Но если на хосте включён Teredo, он сам открывает исходящий UDP/3544 и получает полноценный IPv6-стек. Через этот канал хост может обращаться к IPv6-адресам в интернете, минуя IPv4-политику. Ещё опаснее — если хосту через такой туннель выдают **RA**: он начинает считать атакующего шлюзом (см. rogue RA в уроке про IPv6).

Практический вывод для пентеста: наличие переходных механизмов — это **находка**, её фиксируют с доказательством (адрес туннеля + тип). Для обороны — отключить неиспользуемые механизмы (`netsh interface teredo set state disabled`, `netsh interface isatap set state disabled`) и блокировать IP proto 41 и UDP/3544 на периметре.

## Если не сработало: туннель не поднимается

Если 6in4 не работает, чаще всего виноват протокол 41, который режет пограничный firewall. Тогда варианты: перейти на Teredo (UDP/3544), использовать NAT64/DNS64 или поднять полноценный VPN с IPv6-транспортом. Если `ping6` уходит, а ответа нет — проверь обратный маршрут: у туннеля обе стороны должны знать друг о друге, иначе ответные пакеты уйдут в никуда. И держи в голове MTU: инкапсуляция съедает 40+ байт, поэтому туннельные интерфейсы обычно ставят MTU 1480 или ниже.

## Куда дальше

Мы увидели, как IPv6 «протекает» через IPv4-периметр. Дальше разберём, как адреса и параметры IPv6 выдаются автоматически — SLAAC и DHCPv6, — и почему rogue-сервер в сегменте так опасен. А пока запомни: **если периметр защищён только по IPv4, IPv6 станет обходным путём.**

## Где пригодится

- **CTF:** задачи с IPv6-туннелями и нестандартными протоколами.
- **Пентест:** обход IPv4-фильтров, скрытый канал.
- **SOC:** детект proto 41, Teredo, 6to4.
- **Инженерия:** явная IPv6-политика, отключение авто-туннелей.
