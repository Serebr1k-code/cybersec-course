IPv6 не разворачивается мгновенно, поэтому существуют **переходные механизмы**, позволяющие передавать IPv6 через IPv4-сети. Для пентестера это подарок: многие фильтры настроены только на IPv4, а IPv6-трафик проскакивает. Урок — часть [`network-module-ip`](network-module-ip) и продолжает [`network-ipv6`](network-ipv6).

## Зачем нужны переходные механизмы

Пока не весь интернет на IPv6, нужны способы «пронести» IPv6 через IPv4-инфраструктуру:

- **6in4** — IPv6 в явном IPv4-туннеле (протокол 41).
- **6to4** — автоматический туннель, префикс `2002::/16`, адрес встраивает IPv4.
- **Teredo** — IPv6 через UDP/3544 (обходит NAT).
- **ISATAP** — IPv6 внутри интрасети, адрес содержит IPv4 хоста.
- **DS-Lite / 464XLAT** — обратные сценарии (IPv4 через IPv6).

Каждый из них — потенциальный канал в обход IPv4-фильтров.

## 6in4 и протокол 41

Самый простой: IPv6-пакеты инкапсулируются в IPv4 с **Protocol=41**. Многие firewall пропускают «неизвестный» протокол 41 или не проверяют его содержимое.

```bash
# Настроить 6in4-туннель к брокеру (пример)
sudo ip tunnel add tun6 mode sit remote 192.0.2.1 local 10.0.0.2 ttl 64
sudo ip link set tun6 up
sudo ip -6 addr add 2001:db8:1::2/64 dev tun6
sudo ip -6 route add ::/0 via 2001:db8:1::1 dev tun6
```

## 6to4: автоматический туннель

Префикс `2002:V4ADDR::/48`, где V4ADDR — публичный IPv4-адрес (hex). Пакеты идут через relay-маршрутизаторы. Проблема: нет аутентификации, легко подделать, зависит от relay.

```bash
# Проверить, есть ли 6to4-адрес
ip -6 addr show | grep 2002:
# Проверить доступность 6to4-relay
ping6 2002:c058:6301::1   # 192.88.99.1
```

## Teredo: IPv6 через UDP/3544

Teredo инкапсулирует IPv6 в **UDP-пакеты на порт 3544** — обходит NAT, так как это обычный UDP. Адрес начинается с `2001:0000::/32`. Teredo-сервер помогает установить связь.

```bash
# Проверить наличие Teredo (Windows)
# netsh interface teredo show state
# Linux: miredo
sudo miredo
ip -6 addr show teredo
```

Опасность: UDP/3544 часто разрешён наружу, и через Teredo проходит IPv6-трафик в обход IPv4-политик.

## ISATAP: IPv6 внутри интрасети

ISATAP-адрес содержит IPv4 хоста: `fe80::5efe:A.B.C.D` или `2001:db8::5efe:A.B.C.D`. Используется внутри организации для «островов» IPv6.

```bash
# Включить ISATAP-интерфейс (пример)
sudo ip tunnel add isatap0 mode isatap local 10.0.0.2
sudo ip link set isatap0 up
```

## Почему это обходит периметр

- **Firewall настроен на IPv4** — IPv6-политики нет или она «allow all».
- **Протокол 41 не инспектируется** — 6in4 проходит как «неизвестный».
- **UDP/3544 разрешён** — Teredo маскируется под UDP.
- **Двойной стек** — хост сам поднимает туннель без ведома админа.

Атака: скомпрометированный хост поднимает 6to4/Teredo-туннель и получает IPv6-канал в интернет, минуя IPv4-фильтры и логи.

## Практика: обнаружить туннели

```bash
# Протокол 41 (6in4) в дампе
sudo tcpdump -i eth0 -nn 'ip proto 41'
# Teredo (UDP/3544)
sudo tcpdump -i eth0 -nn 'udp port 3544'
# 6to4-адреса
ip -6 addr show | grep -E '2002:|2001:0:'
# Маршруты IPv6
ip -6 route show
```

## Детект в SOC

- **proto 41** и **UDP/3544** на периметре — почти всегда нелегитимны;
- **6to4-префикс 2002::/16** в трафике;
- **Teredo 2001:0::/32**;
- **неожиданные IPv6-адреса** у хостов без IPv6-политики;
- **DNS-запросы AAAA** к неизвестным доменам (подготовка туннеля).

```bash
# Сводка не-IPv4 протоколов
tshark -r cap.pcap -T fields -e ip.proto | sort | uniq -c | sort -rn | head
```

## Защита

| Мера | Против чего |
|---|---|
| Явная IPv6-политика (не «allow all») | обход через IPv6 |
| Блокировка proto 41 на периметре | 6in4 |
| Блокировка UDP/3544 | Teredo |
| Отключение 6to4/ISATAP на хостах | авто-туннели |
| Мониторинг proto 41 / Teredo | детект |
| Инвентаризация IPv6-адресов | нелегитимные туннели |

```bash
# Отключить IPv6-туннели на Linux
sysctl -w net.ipv6.conf.all.disable_ipv6=1
```

## Частые ошибки

- **Считать, что «IPv6 выключен»** — двойной стек часто активен.
- **Игнорировать proto 41** — firewall его пропускает.
- **Забывать про Teredo** — UDP/3544 маскируется под обычный UDP.
- **Не иметь IPv6-политики** — «default allow» для IPv6.
- **Путать 6to4 и Teredo** — разные префиксы и порты.
- **Доверять host-based firewall** — туннель поднимается на хосте.
- **Не логировать IPv6** — атака остаётся невидимой.

## Префиксы и адресация туннелей

Каждый переходный механизм имеет узнаваемый префикс — это ключ к детекту:

| Механизм | Префикс / признак |
|---|---|
| 6to4 | `2002::/16` (встраивает IPv4) |
| Teredo | `2001:0000::/32`, UDP/3544 |
| ISATAP | интерфейсный ID `::5efe:A.B.C.D` |
| 6in4 | proto 41, адреса из брокера |
| NAT64 | `64:ff9b::/96` |
| ULA | `fc00::/7` |

Зная эти префиксы, вы за секунды определяете по дампу, какой туннель используется.

## Практика: поднять 6in4 и увидеть трафик

```bash
# 1. Создать sit-туннель
sudo ip tunnel add tun6 mode sit remote 192.0.2.1 local 10.0.0.2 ttl 64
sudo ip link set tun6 up
sudo ip -6 addr add 2001:db8:1::2/64 dev tun6
# 2. Маршрут по умолчанию через туннель
sudo ip -6 route add ::/0 via 2001:db8:1::1 dev tun6
# 3. Увидеть инкапсуляцию (proto 41)
sudo tcpdump -i eth0 -nn 'ip proto 41' -c 5
# 4. Проверить связность
ping6 -c2 2001:4860:4860::8888
```

В дампе видно: внешний IPv4-заголовок с **Protocol=41** и внутри — полноценный IPv6-пакет. Если firewall не смотрит proto 41, трафик проходит.

## Лаборатория: детект proto 41 и Teredo

```bash
# Сводка протоколов L3 — ищем 41
tshark -r cap.pcap -T fields -e ip.proto | sort | uniq -c | sort -rn
# Teredo: IPv6 внутри UDP/3544
tshark -r cap.pcap -Y 'udp.port==3544' -T fields -e ip.src -e ip.dst | head
# 6to4-адреса
tshark -r cap.pcap -Y 'ipv6' -T fields -e ipv6.src | grep -E '^2002:' | head
# ISATAP-идентификаторы
tshark -r cap.pcap -Y 'ipv6' -T fields -e ipv6.src | grep -i '5efe' | head
```

Практическое правило для SOC: **proto 41 и UDP/3544 на периметре** почти всегда означают либо нелегитимный туннель, либо забытую конфигурацию. Оба случая — повод для расследования.

## Сравнение переходных механизмов

| Механизм | Инкапсуляция | Аутентификация | Префикс/порт |
|---|---|---|---|
| 6in4 | IPv6 в IPv4 (proto 41) | нет | адрес брокера |
| 6to4 | автоматически в IPv4 | нет | 2002::/16 |
| Teredo | IPv6 в UDP | нет | 2001:0::/32, 3544 |
| ISATAP | IPv6 в IPv4 интрасеть | нет | ::5efe:A.B.C.D |
| DS-Lite | IPv4 в IPv6 | операторская | AFTR |

Общее у всех — **отсутствие аутентификации** и зависимость от внешней инфраструктуры (relay/брокер). Это делает их удобными для обхода и одновременно заметными при правильном мониторинге.

## Модель угроз и практический чек-лист

Для пентеста внутренней сети:

1. Проверить, включён ли **двойной стек** (`ip -6 addr`, `ip -6 route`).
2. Найти, разрешён ли наружу **proto 41** и **UDP/3544**.
3. Попробовать поднять 6in4/Teredo и проверить связность IPv6.
4. Проверить, применяется ли **IPv6-политика** firewall (часто «allow all»).
5. Оценить, логируется ли IPv6-трафик.
6. Для защиты: блокировать авто-туннели, задать явную IPv6-политику, мониторить proto 41/Teredo.

```bash
# Быстрая проверка окружения
ip -6 addr show scope global
ip -6 route show
sysctl net.ipv6.conf.all.forwarding net.ipv6.conf.all.accept_ra
```

Если IPv6-адрес есть, а политики нет — это готовый канал в обход IPv4-фильтров, который стоит проверить и закрыть.

## Где пригодится

- **CTF:** задачи с IPv6-туннелями и нестандартными протоколами.
- **Пентест:** обход IPv4-фильтров, скрытый канал.
- **SOC:** детект proto 41, Teredo, 6to4.
- **Инженерия:** явная IPv6-политика, отключение авто-туннелей.
