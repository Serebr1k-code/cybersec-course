Bluetooth — не «ещё один Wi-Fi», а отдельный стек с собственными протоколами, профилями и историей уязвимостей. Классический Bluetooth (BR/EDR) до сих пор живёт в гарнитурах, автомобилях, принтерах, медицинских приборах и промышленном оборудовании. Ошибки pairing и отсутствие шифрования на прикладном уровне делают его лёгкой целью для перехвата и несанкционированного управления.

## Bluetooth Classic: стек и профили

Bluetooth Classic работает в диапазоне 2.4 ГГц, использует **FHSS** (перескок частот) и делится на уровни: радио, baseband, LMP (Link Manager Protocol), L2CAP, RFCOMM, SDP и профили. Ключевые профили:

- **HFP/HSP** — гарнитуры (телефония);
- **A2DP/AVRCP** — аудио;
- **HID** — клавиатуры, мыши, геймпады;
- **OBEX/FTP/OPP** — передача файлов;
- **SPP** — последовательный порт (RFCOMM);
- **PAN** — сеть;
- **MAP/PBAP** — доступ к сообщениям и телефонной книге.

Для пентеста важны HID (инъекция нажатий), OPP (кража/подбрасывание файлов) и MAP/PBAP (выгрузка контактов и SMS).

| Слой | Назначение |
|---|---|
| LMP | Управление звеном |
| L2CAP | Мультиплексирование каналов |
| RFCOMM | Эмуляция последовательного порта |
| SDP | Обнаружение сервисов |
| Профили | Прикладные сценарии |

## Обнаружение устройств

```bash
# Включить адаптер и сканировать
bluetoothctl
> power on
> scan on
> devices
> info AA:BB:CC:DD:EE:FF
# Классический инструмент
hcitool scan
hcitool inq
# SDP: какие сервисы предлагает устройство
sdptool browse AA:BB:CC:DD:EE:FF
```

Вывод `sdptool browse` покажет каналы RFCOMM и доступные профили — с них начинается любая атака.

## Pairing: legacy и SSP

- **Legacy pairing** — 4-значный PIN, обмен по E0-шифру с **слабым** ключом; PIN перебирается за секунды.
- **Secure Simple Pairing (SSP)** — режимы: **Just Works** (без подтверждения, уязвим к MITM), **Numeric Comparison** (с подтверждением), **Passkey Entry**, **Out of Band** (NFC). Just Works — самый распространённый и небезопасный.

Ключевая проблема: даже при SSP pairing-обмен можно перехватить и провести **MITM**, если устройство не требует Numeric Comparison.

## Известные атаки

| Атака | Суть |
|---|---|
| BlueBorne (2017) | RCE/инфо-утечка через L2CAP/SDP без pairing |
| BlueSmack | DoS через oversized L2CAP-пакет (Ping of Death) |
| KNOB (2019) | Снижение энтропии ключа шифрования до 1 байта |
| BIAS (2020) | Impersonation в SSP-аутентификации |
| Bluesnarfing | Чтение данных (контакты, SMS) через OBEX |
| Bluebugging | Управление телефоном (звонки, SMS) |
| Bluejacking | Отправка нежелательных сообщений |
| Car Whisperer | Инъекция аудио в авто-систему |

## Инструменты

- **bluesnarfer** — выгрузка данных через OBEX.
- **spooftooph** — клонирование имени/MAC Bluetooth-устройства.
- **btlejack** — аппаратный перехват BLE (для Classic частично).
- **ubertooth** — аппаратный снифер Bluetooth.
- **bettercap** — модули BLE.
- **Bluescanner / btscanner** — GUI-разведка.

```bash
# Выгрузить телефонную книгу (если уязвимо)
bluesnarfer -b AA:BB:CC:DD:EE:FF -r 1-200
# Спуфинг имени/адреса
sudo spooftooph -i hci0 -a 11:22:33:44:55:66 -n "JBL Speaker"
```

## Разобранный пример: разведка и попытка Bluesnarfing

1. Включаем адаптер и сканируем: `hcitool scan` — получаем список устройств с именами.
2. Для интересующего адреса смотрим сервисы: `sdptool browse <mac>` — ищем OBEX Object Push, PBAP, MAP.
3. Пробуем выгрузку контактов через OBEX (в лабе с собственным устройством):
   ```bash
   bluesnarfer -b <mac> -r 1-100
   ```
4. Если устройство требует pairing — оцениваем, Just Works ли оно: подключаемся и смотрим, был ли запрос подтверждения.
5. Для MITM используем две карты или Ubertooth: одна подключается к жертве, другая — к цели; анализируем, проверяет ли устройство ключи.

## Защита

| Мера | Против чего |
|---|---|
| Выключать Bluetooth, когда не нужен | Любая атака |
| Отключить discoverable/видимость | Обнаружение |
| Требовать Numeric Comparison / Passkey | MITM, Just Works |
| Обновлять прошивки (BlueBorne) | RCE |
| Ограничить видимость профилей (HID/OBEX) | Инъекция, кража |
| Использовать BLE с secure connections | Перехват |
| Изолировать критичные устройства | Общий риск |

## Частые ошибки и подводные камни

- **Путать Classic и BLE.** Это разные стеки; инструменты и атаки отличаются (см. `network-ble-attacks`).
- **Забывать про pairing.** Многие атаки требуют спаренного/подтверждённого устройства.
- **Игнорировать аппаратные ограничения.** Один дешёвый адаптер не даёт полноценного MITM; нужны Ubertooth/две карты.
- **Считать Bluetooth «локальным».** Радиус — десятки метров, но направленные антенны увеличивают его.
- **Тестировать чужие устройства без разрешения.** Это нарушение закона и этики.

## Что дальше / решение

Bluetooth — часть беспроводного пентеста наряду с Wi-Fi (`network-wireless-80211`, `network-wpa3`) и BLE (`network-ble-attacks`). Для защиты: выключайте Bluetooth, требуйте подтверждение pairing, обновляйте прошивки. Для CTF/Hardware потренируйтесь на собственных устройствах и Ubertooth. Дальше изучите NFC/RFID (hardware-ветка) — это родственные радио-технологии.

## BlueBorne и уязвимости стека в деталях

BlueBorne (2017) — это не одна уязвимость, а набор из восьми, затронувших Android, iOS, Windows и Linux. Ключевые из них: **CVE-2017-1000251** (переполнение в стеке L2CAP ядра Linux, RCE), **CVE-2017-1000250** (info-leak в SDP-сервере), **CVE-2017-0781/0782/0785** (RCE и info-leak в Android Bluetooth). Опасность в том, что эксплуатировать их можно **без сопряжения и без пользовательского взаимодействия** — устройство просто должно быть включено. Сканер BlueBorne (`blueborne-scanner`) определяет уязвимые устройства в эфире.

Механика: L2CAP-запрос с некорректной длиной вызывал переполнение буфера в ядре; SDP-ответ позволял утекать памяти. Это напоминает сетевые RCE, только по радио. Урок для защиты: **регулярно обновлять прошивки и стек Bluetooth**, а также ограничивать discoverable-режим. Аналогичные проблемы были в KNOB (снижение энтропии ключа до 1 байта через манипуляцию LMP-согласованием) и BIAS (подмена роли в SSP-аутентификации, позволяющая выдать себя за уже сопряжённое устройство).

## RFCOMM/SPP и эксплуатация

Многие устройства (принтеры, Arduino, промышленные адаптеры) отдают **последовательный порт** через RFCOMM. Если pairing слабый, можно подключиться и отправлять команды напрямую:

```bash
# Найти RFCOMM-канал через SDP
sdptool browse AA:BB:CC:DD:EE:FF | grep -A3 RFCOMM
# Привязать локальный порт и подключиться
sudo rfcomm connect /dev/rfcomm0 AA:BB:CC:DD:EE:FF 1
screen /dev/rfcomm0 9600
```

После этого вы общаетесь с устройством как с UART: можно слать AT-команды, менять настройки, иногда — выполнять код. Это типовой вектор в hardware-пентесте. Часто SPP вообще не требует pairing или использует фиксированный PIN (0000/1234) — перебирается мгновенно.

## Лаборатория: полный цикл

1. Купите/подготовьте два дешёвых USB-Bluetooth-адаптера и старую гарнитуру/Arduino с HC-05.
2. `hcitool scan` → найдите устройство; `sdptool browse` → определите сервисы (HID/SPP/OPP).
3. Оцените pairing: подключитесь и проверьте, спрашивает ли устройство подтверждение (Just Works vs Numeric Comparison).
4. Для SPP привяжите `rfcomm` и отправьте команды — убедитесь, что контроль над устройством получен.
5. Для MITM поставьте Ubertooth: перехватите pairing-обмен и проанализируйте энтропию ключа.
6. Включите обязательный Numeric Comparison / отключите discoverable — повторите, убедитесь, что атака усложнилась.

Так вы проходите путь от обнаружения до эксплуатации и защиты.
