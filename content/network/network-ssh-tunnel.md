## Вопрос, с которого всё начинается

У тебя есть учётка на bastion-хосте `203.0.113.10` — единственной легальной точке входа во внутреннюю сеть. Внутри живёт MySQL `10.0.0.5:3306`, который снаружи недоступен. Как достучаться до него, имея только SSH?

SSH умеет **перенаправлять порты**: одна легитимная сессия превращается в канал доступа к внутренним сервисам. Это базовый инструмент pivoting, и его главное достоинство — трафик выглядит как обычный SSH и редко блокируется.

## Наш пример: сервис, доступный только с bastion

Сначала убедимся, что цель видна **с bastion**, но не с нашей машины:

```
$ nc -vz 10.0.0.5 3306
nc: connect to 10.0.0.5 port 3306 (tcp) failed: Connection timed out
$ ssh analyst@bastion 'nc -vz 10.0.0.5 3306'
Connection to 10.0.0.5 3306 port [tcp/mysql] succeeded!
```

MySQL доступен с bastion и недоступен нам. Значит, надо «протянуть» его через SSH-сессию.

## Шаг 1: три вида перенаправления

| Тип | Флаг | Смысл |
|-----|------|-------|
| **Локальный** | `-L lport:host:port` | локальный порт → удалённая цель через SSH-сервер |
| **Удалённый** | `-R rport:host:port` | удалённый порт → локальная/третья цель |
| **Динамический** | `-D port` | локальный SOCKS-прокси через SSH |

Ключ к пониманию: `-L` открывает порт **локально** (у тебя) и ведёт к цели **с точки зрения SSH-сервера**; `-R` открывает порт **на сервере** и ведёт к цели с твоей стороны. Это различие — источник большинства ошибок.

## Шаг 2: локальный форвард (`-L`)

Пробрасываем MySQL на локальный порт `3307`:

```
$ ssh -N -L 3307:10.0.0.5:3306 analyst@bastion &
$ ss -ltnp | grep 3307
tcp LISTEN 0 128 127.0.0.1:3307 0.0.0.0:* users:(("ssh",pid=1234,fd=5))
$ mysql -h 127.0.0.1 -P 3307 -u app -p
```

`-N` говорит «не выполнять команду, только туннель» — без него SSH откроет shell, и туннель закроется вместе с сессией. Теперь `127.0.0.1:3307` — это на самом деле `10.0.0.5:3306`. Обрати внимание: адрес `10.0.0.5` разрешается **на стороне bastion**, а не нашей.

## Шаг 3: динамический форвард (`-D`)

Когда целей много, поднимаем **SOCKS-прокси** и ходим через него любым инструментом:

```
$ ssh -N -D 1080 analyst@bastion &
$ curl --socks5-hostname 127.0.0.1:1080 http://10.0.0.7/
$ proxychains4 -q nmap -sT -Pn -p22,80,445 10.0.0.0/24
PORT     STATE SERVICE
10.0.0.7 80/tcp open  http
10.0.0.9 445/tcp open  microsoft-ds
```

`--socks5-hostname` (или `socks5h`) заставляет резолвить имена **через прокси**, чтобы не утекли DNS-запросы. Важно: `nmap` через SOCKS работает только в режиме `-sT` (полноценное TCP-соединение); сырые SYN- и UDP-сканы прокси не пропускает.

## Шаг 4: удалённый форвард (`-R`)

Иногда нужно наоборот — опубликовать **свой** сервис на удалённом хосте:

```
$ ssh -N -R 8080:127.0.0.1:8080 analyst@bastion
```

Теперь `bastion:8080` ведёт к нашему локальному `8080`. Это reverse-доступ: полезно, когда входящие к нам закрыты, а исходящий SSH разрешён. По умолчанию `-R` слушает только `localhost` на сервере; чтобы открыть наружу, на сервере нужен `GatewayPorts yes`.

## Шаг 5: надёжность туннеля

Туннель, который молча отваливается, хуже отсутствия туннеля. Держим его живым:

```
$ ssh -N -D 1080 analyst@bastion \
    -o ServerAliveInterval=30 -o ExitOnForwardFailure=yes
$ autossh -M 0 -N -D 1080 analyst@bastion -o ServerAliveInterval=30
```

`ServerAliveInterval` шлёт keepalive-пакеты, `ExitOnForwardFailure` не даёт оставить «полутуннель» (когда SSH жив, а проброс не поднялся). `autossh` перезапускает сессию при обрыве.

## Продвинутые схемы

Когда цепочка из нескольких хостов, используют `ProxyJump` или `ProxyCommand`:

```
$ ssh -J user1@jump1,user2@jump2 user3@internal
$ ssh -o ProxyCommand='ssh -W %h:%p user1@jump1' user2@internal
```

`-W %h:%p` передаёт сырой поток до цели через jump — это то же stdio-перенаправление, что и при `-L`, но без локального порта. Когда нужна прозрачная маршрутизация подсети, а не SOCKS, помогает `sshuttle`:

```
$ sshuttle -r user@jump 10.0.0.0/24
```

Он проксирует трафик к подсети по правилам, поддерживает DNS и не требует `proxychains`.

## OPSEC: что видно защите

SSH-туннели легитимны и потому малозаметны, но следы остаются. В логах `sshd` видны каналы `direct-tcpip` (это и есть проброс) и `session`. Длительные SOCKS-сессии и множественные `direct-tcpip` от одного пользователя — индикатор. Администратору стоит ограничить перенаправление:

```text
Match Group contractors
    AllowTcpForwarding no
    PermitOpen none
```

А `GatewayPorts yes` вместе с `-R` на внешний адрес — потенциальный backdoor, который надо аудировать. И помни: логи `sshd` пишут каналы `direct-tcpip`, поэтому подозрительно длинная сессия или множество пробросов от одного пользователя легко заметны при мониторинге. Для нескольких туннелей через одно соединение помогает мультиплексирование:

```
$ ssh -o ControlMaster=auto -o ControlPersist=10m user@jump
```

## Диагностика проблем

Туннель открылся, но сервис недоступен — типичная ситуация. Порядок проверки:

```
$ ss -ltnp | grep 3307                            # слушает ли локальный порт
$ ssh -v -N -L 3307:10.0.0.5:3306 user@bastion    # подробный лог
$ ssh user@bastion 'nc -vz 10.0.0.5 3306'          # видит ли цель сам bastion
```

Частые причины: цель доступна только с bastion (нужен проброс **с** bastion, а не к нему), либо сервер запрещает forwarding (`AllowTcpForwarding no`). Проверить конфиг сервера можно так:

```
$ grep -iE 'AllowTcpForwarding|PermitOpen|GatewayPorts' /etc/ssh/sshd_config
```

Ещё один нюанс: `-L` и `-R` разрешают адрес цели по-разному. В `-L` цель (`10.0.0.5:3306`) разрешается **на стороне сервера** — смотреть её надо глазами bastion. В `-R` цель разрешается на твоей стороне. Путаница здесь — источник половины «неработающих» туннелей. Если туннель нужен постоянно, оформи его как systemd-юнит с `Restart=always` или оберни в `autossh`: тогда он переживёт обрыв связи и смену сети, и ты не останешься без доступа посреди работы.

## Что мы теперь знаем

- `-L` — локальный форвард (внутренний сервис к себе), `-R` — обратный, `-D` — SOCKS.
- Цель в `-L` разрешается на стороне сервера, в `-R` — на нашей.
- `-D` даёт SOCKS-прокси, через который ходят `curl`/`nmap` (`-sT`)/`proxychains`.
- `-N` обязателен, чтобы туннель не зависел от интерактивной сессии.
- Keepalive и `ExitOnForwardFailure` делают туннель надёжным.

## Туннель как pivot: практический сценарий

Разберём типовой пентест-сценарий, где SSH-туннель — не «ещё одна команда», а рабочий инструмент доступа к закрытому сегменту.

Дано: есть shell на bastion-хосте `10.10.0.5` в DMZ. Внутренняя подсеть `192.168.50.0/24` с bastion не видна снаружи, но с самого bastion доступна. Нужно просканировать внутреннюю сеть.

Шаг 1. Одиночный порт. Пробрасываем конкретный сервис локально:

```
$ ssh -f -N -L 8080:192.168.50.20:8080 user@10.10.0.5
$ ss -tlnp | grep 8080
LISTEN 0  128  127.0.0.1:8080  0.0.0.0:*  users:(("ssh",pid=3121,fd=5))
$ curl -s http://127.0.0.1:8080/ | head -1
<!DOCTYPE html>
```

Флаг `-f` уводит ssh в фон после аутентификации, `-N` говорит «не выполнять команду», `-L` создаёт локальный форвард. Проверка через `ss` обязательна: если `ExitOnForwardFailure` не выставлен, ssh молча поднимет сессию без порта, и вы решите, что сервис недоступен.

Шаг 2. Целый сегмент через SOCKS. Вместо десятков `-L` поднимаем динамический прокси:

```
$ ssh -f -N -D 1080 user@10.10.0.5
$ ss -tlnp | grep 1080
LISTEN 0  128  127.0.0.1:1080  0.0.0.0:*  users:(("ssh",pid=3184,fd=4))
$ proxychains4 -q nmap -sT -Pn -n -p 22,80,443,445,3389 192.168.50.0/24
Nmap scan report for 192.168.50.20
22/tcp   open  ssh
445/tcp  open  microsoft-ds
```

Важно: через SOCKS работает только полное TCP-соединение (`-sT`), а не raw-пакеты SYN (`-sS`), поэтому сканирование медленнее — зато не требует root и переживает NAT.

Шаг 3. Надёжность. Пентест-сессии рвутся от таймаутов и потери сети. Боевые флаги:

```
$ ssh -o ServerAliveInterval=30 -o ServerAliveCountMax=3 \
      -o ExitOnForwardFailure=yes -o TCPKeepAlive=yes \
      -f -N -D 1080 user@10.10.0.5
```

`ServerAliveInterval` шлёт keepalive каждые 30 секунд, `ExitOnForwardFailure=yes` заставляет ssh упасть, если форвард не поднялся (а не «висеть впустую»). Для долгих операций удобно обернуть всё в `autossh -M 0 -N -D 1080 user@10.10.0.5`, который переподнимает туннель после обрыва.

Шаг 4. Обратный туннель, когда инициатива должна идти изнутри. Если прямой доступ к bastion закрыт файрволом, но с bastion можно дотянуться до вашего слушателя, используйте `-R`:

```
# на attacker: nc -lvnp 4444
$ ssh -N -R 4444:127.0.0.1:4444 user@10.10.0.5
# теперь bastion может: nc 127.0.0.1 4444
```

Так туннель обходит ingress-фильтрацию: соединение инициирует «внутренний» хост, а вы лишь принимаете его на своей стороне.

## Ошибки, которые ломают туннель

Три классические проблемы, из-за которых SSH-туннель «есть, но не работает».

**Первый: `AllowTcpForwarding no` на сервере.** Если администратор запретил форвардинг в `sshd_config`, локальный `-L` и динамический `-D` не поднимутся, а обратный `-R` будет отклонён. Проверяется по логу сервера: `refused local port forward`. Обходной путь — `-R` на сторону, где форвардинг разрешён, либо другой транспорт.

**Второй: привязка к интерфейсу.** По умолчанию `-L` слушает `127.0.0.1`. Если нужно, чтобы порт был доступен другим хостам, добавляют `-g` (gateway ports) или явный bind-адрес `-L 0.0.0.0:8080:target:8080`. Забыть про это — типичная ошибка, когда туннель работает локально, но «не виден» соседнему контейнеру.

**Третий: DNS внутри SOCKS.** `proxychains` умеет резолвить имена через прокси (`proxy_dns`), но по умолчанию часть инструментов резолвит имена локально — и запрос уходит не в туннель, а напрямую. Если внутренние имена не резолвятся снаружи, используйте IP или включите `proxy_dns` в конфиге proxychains и проверьте, что `nmap -n` не подставляет имена.

Диагностика всегда одинаковая: `ss -tlnp` — поднялся ли порт; `ssh -v` — прошла ли аутентификация и форвард; `tcpdump -i lo` на стороне клиента — доходят ли пакеты до локального порта.

## Куда дальше

Мы научились превращать SSH-сессию в канал доступа. Дальше разберём сами прокси-протоколы — SOCKS и HTTP CONNECT — и как через них протаскивать инструменты, не умеющие работать с прокси. А пока запомни: **один легитимный SSH-доступ — это мост ко всем сервисам, которые видит сервер.**

## Где пригодится

- **CTF:** pivot к внутренним сервисам через одну SSH-сессию.
- **Пентест:** доступ к БД и панелям в закрытых сегментах.
- **Работа:** безопасный удалённый доступ, jump-хосты.
- **Red team:** скрытые каналы через легитимный SSH.
- **Администрирование:** защита SSH от злоупотребления туннелями.
