Covert-каналы прячут данные там, где их не ждут. Помимо явных туннелей (DNS/ICMP), существуют **timing**-каналы (данные в интервалах между пакетами) и **storage**-каналы (данные в полях заголовков, размерах, padding). Они не меняют полезную нагрузку, поэтому особенно трудно детектируются и почти не видны DPI. Урок опирается на [`network-covert`](network-covert) и [`network-pcap-analysis`](network-pcap-analysis).

## Классификация covert-каналов

- **Storage-каналы**: данные в **полях** заголовков (IP ID, TTL, TCP-опции, window size, порядок), в **размерах** пакетов, в **padding**, в **именах** (DNS), в HTTP-заголовках.
- **Timing-каналы**: данные в **интервалах** между пакетами (задержка = бит 0/1) или в **скорости** потока (bitrate encoding).
- **Гибридные**: комбинация (например, размер пакета + тайминг), адаптивные схемы, меняющие кодировку на лету.

Ещё одно измерение — **среда**: сетевой канал (L3/L4), прикладной (HTTP/DNS), файловая система (slack space, ADS), медиа (аудио/видео стеганография).

## Timing-канал: математика

Простейшая схема — **двухуровневая** (бит 0 = короткая пауза `t0`, бит 1 = длинная `t1`). Получатель измеряет интервалы и порогом делит их на два класса.

```text
пакет, пауза ~100 мс  -> 0
пакет, пауза ~300 мс  -> 1
```

Свойства:

- **Пропускная способность** = 1 / (t_avg) бит/с. При t≈200 мс это ~5 бит/с — байт в ~1.6 с.
- Устойчив к DPI (payload «нормальный»).
- Ломается при **нормализации** (shaping, выравнивание задержек, буферизация).
- Требует **синхронизации**: получатель должен знать начало и разметку.

Многоуровневая кодировка (3+ задержек) повышает плотность, но сильнее страдает от jitter. Иногда кодируют **в двух потоках** (присутствие пакета = 1) — это уже storage/timing-гибрид.

## Storage-каналы в деталях

- **IP ID**: обычно инкрементный (Linux) или случайный (современные ОС). Если значения образуют паттерн/последовательность — кодируют данные.
- **TTL**: младшие биты, редко валидируются.
- **TCP options / window size / ISN**: редко проверяются.
- **Размер пакета**: прямое кодирование байта (например, 100+n байт = байт n).
- **Padding**: Ethernet-минимум (60 байт), TLS padding, поля приложений.
- **HTTP**: `Cookie`, `User-Agent`, `X-*`, URL-параметры.

```bash
# IP ID и TTL по потоку
tshark -r cap.pcap -T fields -e ip.id -e ip.ttl | head -40
# Распределение размеров пакетов (storage по размеру)
tshark -r cap.pcap -T fields -e frame.len | sort -n | uniq -c | head
# TCP window size как носитель
tshark -r cap.pcap -T fields -e tcp.window_size_value | head -40
```

## Инструменты и команды

```bash
# 1. Анализ интервалов (timing) для одного потока
tshark -r cap.pcap -Y 'ip.src==10.0.0.5' -T fields -e frame.time_relative | \
  awk 'NR>1{print $1-prev} {prev=$1}' | head -40
# 2. Гистограмма интервалов (ищем бимодальность)
tshark -r cap.pcap -Y 'udp' -T fields -e frame.time_relative | \
  awk 'NR>1{d=$1-prev; printf "%.3f\n",d} {prev=$1}' | sort -n | uniq -c | head
# 3. Размеры пакетов
tshark -r cap.pcap -T fields -e frame.len | sort -n | uniq -c | head
# 4. Поля заголовков
tshark -r cap.pcap -T fields -e ip.id -e ip.ttl | head -40
# 5. Энтропия payload (для кодированных каналов)
tshark -r cap.pcap -T fields -e data | head
```

Полезны `capinfos` (общая статистика), `tshark -z io,stat`, `-z endpoints`.

## Разобранный пример: поиск timing-канала в PCAP

```bash
# 1. Выделяем один источник и один протокол
tshark -r cap.pcap -Y 'ip.src==10.0.0.5 and icmp' -T fields -e frame.time_relative | head -60
# 2. Считаем интервалы и решаем: >0.2 c = "1", иначе "0"
tshark -r cap.pcap -Y 'ip.src==10.0.0.5 and icmp' -T fields -e frame.time_relative | \
  awk 'NR>1{d=$1-prev; print (d>0.2?"1":"0")} {prev=$1}' | tr -d '\n'
# -> 01001000 01100101 01101100 01101100 01101111 = "Hello"
# 3. Автоматически: порог по двум кластерам
python3 - <<'PY'
ts=[float(x) for x in open('t.txt')]
d=[ts[i+1]-ts[i] for i in range(len(ts)-1)]
thr=(min(d)+max(d))/2
bits=''.join('1' if x>thr else '0' for x in d)
bs=[bits[i:i+8] for i in range(0,len(bits)-7,8)]
print(bytes(int(b,2) for b in bs))
PY
# 4. Проверяем storage-версию (размеры)
tshark -r cap.pcap -Y 'icmp' -T fields -e data.len | sort | uniq -c | head
```

Порог подбирают по гистограмме: если интервалы образуют **два кластера**, это почти наверняка канал. Иногда биты инвертированы или используют >2 уровней.

## Storage-канал: пошаговое извлечение

```bash
# 1. Собрать поле-носитель (например, IP ID) по порядку времени
tshark -r cap.pcap -T fields -e frame.time_epoch -e ip.id | sort -n | awk '{print $2}' > ids.txt
# 2. Гипотеза: младший байт IP ID кодирует байт
python3 - <<'PY'
vals=[int(x) for x in open('ids.txt')]
print(bytes(v & 0xff for v in vals[:64]))
PY
# 3. Или размер пакета минус базовая длина
tshark -r cap.pcap -Y 'ip.dst==10.0.0.5' -T fields -e frame.len | \
  python3 -c "import sys;print(bytes(int(l)-40 for l in sys.stdin if l.strip())[:64])"
```

## Детект (для SOC)

- **Бимодальное распределение** интервалов (два кластера = биты 0/1).
- **Аномальная регулярность/периодичность** пакетов (beaconing-подобно).
- **Однотипные пакеты** с малым payload и высокой частотой.
- **Монотонные/структурированные** IP ID/TTL/window.
- **Размеры пакетов** как код (ограниченный алфавит размеров).
- **Низкая энтропия payload** при высокой частоте.

```bash
# Проверка периодичности: стандартное отклонение интервалов
tshark -r cap.pcap -Y 'ip.src==10.0.0.5' -T fields -e frame.time_relative | \
  awk 'NR>1{d=$1-prev; s+=d; ss+=d*d; n++} {prev=$1} END{m=s/n; print "mean",m,"std",sqrt(ss/n-m*m)}'
```

## Защита

- **Нормализация трафика**: shaping, выравнивание задержек и размеров, перезапись полей (IP ID random, TTL fix).
- **Padding** до фиксированного размера; убрать неиспользуемые поля.
- **Ограничение частоты** мелких пакетов.
- **ML-детект** аномалий тайминга/размеров на baseline трафика.
- **Терминирующие прокси** (нормализуют поток), где это применимо.

## Частые ошибки

- **Искать данные только в payload** — timing/storage не там.
- **Смотреть смешанный поток** — нужен один источник/поток.
- **Забывать про единицы** — секунды vs миллисекунды.
- **Игнорировать регулярность** — канал часто «слишком ровный».
- **Путать нормальный jitter с каналом** — нужен baseline.
- **Не проверять размеры пакетов** — storage-канал часто там.
- **Забыть про оба направления** — данные могут идти и в ответах.

## Комбинированные и адаптивные каналы

Продвинутые схемы меняют транспорт, кодировку и тайминги адаптивно, чтобы уйти от детекта: смена протоколов, случайные «пустышки», подмешивание легитимного трафика. Признаки — нестабильная статистика и «слишком регулярные» паузы на фоне нормального шума. Для детекта нужны ML-модели на baseline.

## Сравнение типов каналов

| Тип | Где данные | Пропускная способность | Детект |
|-----|-----------|------------------------|--------|
| Timing | интервалы | низкая (бит/с) | бимодальность, регулярность |
| Storage (поле) | заголовки | средняя | структура поля |
| Storage (размер) | длины пакетов | средняя | алфавит размеров |
| Payload | содержимое | высокая | DPI/энтропия |
| Туннель DNS/ICMP | запросы/ответы | средняя | объём, энтропия меток |

## Что дальше / решение

- Нужен **явный туннель** (не метаданные) → `network-dns-tunnel` (iodine/dnscat2) или `network-covert` (ICMP).
- Данные прячутся в **таймингах** → стройте baseline и ищите два кластера интервалов.
- Данные в **полях/размерах** → переберите все поля заголовков и гистограмму длин.
- Нужна **защита** → нормализация (shaping, перезапись полей) + ML-детект.
- Дальше по теме стеганографии в сети → `network-traffic-analysis-ctf`, `network-pcap-analysis`.

Решение (алгоритм): 1) выделить один поток/источник; 2) посчитать интервалы и их распределение; 3) проверить поля заголовков и размеры; 4) собрать биты (порог/кластеры); 5) декодировать (base2/base32/base64/hex); 6) если пусто — сменить гипотезу (другое поле/направление/кодировка).

## Синхронизация и помехоустойчивость

Timing-канал бесполезен без **синхронизации начала**: получатель должен понять, где стартует поток и как размечать биты. Распространённые приёмы:

- **Преамбула** из фиксированной последовательности (например, `10101010`) для калибровки порога.
- **Маркер начала/конца** сообщения отдельным паттерном интервалов.
- **CRC/контрольная сумма** в конце для проверки целостности.
- **Избыточное кодирование** (повтор бита 3 раза, мажоритарное декодирование) против потерь.
- **Адаптивный порог** по скользящему окну (медиана интервалов).

Сетевой jitter — главный враг: маршрутизаторы и очереди вносят задержки, размывая кластеры. Поэтому тайминговые каналы работают лучше на **коротких, стабильных** участках (LAN, один маршрут) и хуже через интернет.

```bash
# Оценка шума: стандартное отклонение интервалов baseline
tshark -r base.pcap -Y 'ip.src==10.0.0.5' -T fields -e frame.time_relative | \
  awk 'NR>1{d=$1-prev; s+=d; ss+=d*d; n++} {prev=$1} END{m=s/n; print "mean",m,"std",sqrt(ss/n-m*m)}'
```

Если `std` сравним с разницей между битами — канал неустойчив, нужен избыточный код.

## Практическая лаборатория

Соберите собственный канал в изолированной среде, чтобы понять обе стороны:

```bash
# Отправитель: кодируем "Hi" паузами 0.1/0.3 c через ICMP
python3 - <<'PY'
import subprocess, time
msg="Hi"
bits=''.join(f"{b:08b}" for b in msg.encode())
for bit in bits:
    subprocess.run(["ping","-c1","-W1","10.0.0.5"],stdout=subprocess.DEVNULL)
    time.sleep(0.3 if bit=="1" else 0.1)
PY
# Получатель: захват и декодирование
sudo tcpdump -i eth0 -n icmp -w timing.pcap -c 40
# Декодирование (порог по гистограмме)
```

Дальше усложняйте: добавьте преамбулу, CRC, повтор бита, многоуровневую кодировку — и посмотрите, как меняется устойчивость к добавленному jitter (например, через `tc netem delay`).

## Сравнение каналов по заметности

| Канал | Что меняет | Ломается о | Пример детекта |
|-------|-----------|------------|----------------|
| Timing | интервалы | shaping/buffering | бимодальность |
| IP ID | поле заголовка | нормализация IP ID | паттерн значений |
| Размер пакета | длину | padding/normalize | алфавит размеров |
| HTTP-заголовки | текст | DPI на L7 | аномальные поля |
| Padding | мусорные байты | канонизация | энтропия хвоста |

## Что искать в первую очередь в PCAP

Порядок гипотез при разборе неизвестного «странного» трафика: 1) выделить один поток; 2) посмотреть интервалы (timing); 3) гистограмму размеров (storage по длине); 4) поля IP ID/TTL/window; 5) содержимое HTTP-заголовков/URL; 6) хвостовой padding. Чаще всего канал находится на шаге 2 или 3.
