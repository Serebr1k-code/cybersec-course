## Вопрос, с которого всё начинается

Между двумя коммутаторами проложили **два** кабеля — на случай обрыва. Но стоит их включить без защиты, и через пару секунд сеть ложится: широковещательный кадр попадает в петлю и начинает бесконечно размножаться. Коммутатор L2, в отличие от маршрутизатора, не умеет уменьшать «время жизни» кадра — он просто пересылает его дальше, и по кругу.

Решает проблему **STP** (Spanning Tree Protocol — протокол связующего дерева): он логически отключает лишние пути, оставляя один. Но тот же механизм — отличная цель для атаки. Разберём его изнутри.

Этот урок — часть модуля [`network-module-l2`](network-module-l2); опирается на [`network-ethernet`](network-ethernet) и [`network-layer2-attacks`](network-layer2-attacks).

## Наш пример: слушаем BPDU

Мы подключены к порту коммутатора. STP-коммутаторы постоянно обмениваются служебными кадрами — их называют **BPDU** (Bridge Protocol Data Unit). Захватим их:

```
$ sudo tcpdump -i eth0 -nn -e 'ether dst 01:80:c2:00:00:00'
14:55:01.001 00:1b:0d:aa:bb:cc > 01:80:c2:00:00:00, STP 802.1w, Rapid STP, ...
14:55:03.001 00:1b:0d:aa:bb:cc > 01:80:c2:00:00:00, STP 802.1w, Rapid STP, ...
```

Видно: кадры уходят каждые 2 секунды на multicast-адрес `01:80:c2:00:00:00`, версия — Rapid STP. Разберём, что в них и почему это так важно для перехвата.

## Шаг 1: как выбирается корневой мост

У каждого коммутатора есть **Bridge ID** — 8 байт: приоритет (2 байта, по умолчанию `32768`) плюс его MAC-адрес. Корнем дерева становится коммутатор с **наименьшим** Bridge ID. Порядок правил такой:

1. **Root Bridge** — минимальный Bridge ID (сначала приоритет, при равенстве — MAC).
2. **Root Port** — у каждого коммутатора порт с минимальной стоимостью пути к корню.
3. **Designated Port** — на каждом сегменте ближайший к корню порт.
4. Все остальные порты — в **Blocking/Discarding** (заблокированы).

Стоимость пути зависит от скорости: 10 Мбит/с = 100, 100 Мбит/с = 19, 1 Гбит/с = 4, 10 Гбит/с = 2. Посмотрим роли в дампе:

```
$ tshark -r stp.pcap -Y 'stp' -T fields -e stp.root.priority -e stp.root.ext -e stp.bridge.priority
32768    00:1b:0d:aa:bb:cc    32768
32768    00:1b:0d:aa:bb:cc    32768
```

Здесь `root.priority = 32768` и `root.ext` — MAC корня. Если у какого-то устройства приоритет окажется **ниже** 32768, оно и станет корнем.

## Шаг 2: BPDU — что внутри

BPDU — обычный L2-кадр, но с полями управления: Root ID, Bridge ID, Root Path Cost, Port ID и таймеры. Именно они позволяют коммутаторам договориться, кто корень. Отправляются каждые 2 секунды; если BPDU не приходит дольше `max_age` (20 с), топология перестраивается.

Таймеры по умолчанию:

| Таймер | Значение | Роль |
|---|---|---|
| Hello | 2 с | период отправки BPDU |
| Max Age | 20 с | сколько ждать BPDU до перестройки |
| Forward Delay | 15 с | время в состояниях Listening/Learning |
| Ageing | 300 с | время жизни записи в MAC-таблице |

## Шаг 3: эволюция — STP, RSTP, MSTP

Классический STP сходится медленно (30–50 секунд). Современные варианты быстрее:

| Протокол | Стандарт | Сходимость | Идея |
|---|---|---|---|
| STP | 802.1D | 30–50 с | один экземпляр |
| RSTP | 802.1w | < 1 с | роли Alternate/Backup, edge-порты |
| MSTP | 802.1s | < 1 с | несколько экземпляров, VLAN→instance |
| PVST+ | Cisco | < 1 с | свой STP на каждый VLAN |

В RSTP появился **edge-порт** (portfast) — порт к конечному устройству переходит в forwarding мгновенно. Логично: за компьютером коммутатора нет, петли быть не может. Но если на такой порт **случайно** прилетит BPDU — это опасность: логика сломается.

## Шаг 4: атака — стать корнем

Теперь главное. Атакующий вбрасывает BPDU с **минимальным приоритетом** (например, `0`) и своим MAC. Коммутаторы пересчитывают дерево и направляют трафик через порт атакующего — он становится **корнем** и видит весь L2-трафик:

```
$ python3 - <<'PY'
from scapy.all import sendp, Ether, LLC, STP
pkt = Ether(dst="01:80:c2:00:00:00")/LLC()/STP(rootid=0, bridgeid=0, rootpathcost=0, portid=1)
sendp(pkt, iface="eth0", loop=1, inter=2)
PY
```

Приоритет `0` гарантированно «выигрывает» у любого легитимного моста (`32768`). После захвата включают IP-форвардинг и читают трафик — это полноценный MITM на канальном уровне. В RSTP захват происходит почти мгновенно.

Есть и «шумные» варианты: **BPDU flood** (непрерывно слать BPDU, чтобы дерево постоянно перестраивалось) и инъекция **topology change** — коммутаторы начинают часто чистить MAC-таблицы, вызывая всплески флудинга.

## Шаг 5: защита

| Механизм | Что делает | Против чего |
|---|---|---|
| **BPDU Guard** | выключает порт (err-disable), если пришёл BPDU | BPDU на edge-порту |
| **Root Guard** | не даёт порту стать корнем | захват корневого моста |
| **Loop Guard** | блокирует порт при пропаже BPDU | петли из-за одностороннего линка |
| **BPDU Filter** | не шлёт/не обрабатывает BPDU на edge | шум на портах доступа |
| **PortFast** | мгновенный forwarding для edge | ускорение подключения |

Настройка на Cisco:

```text
spanning-tree portfast bpduguard default
interface Gi0/1
 spanning-tree guard root
```

## Шаг 6: как заметить атаку в дампе

- **Неожиданный корень.** У «конечного» устройства root priority ниже, чем у настоящего корня.
- **Частые Topology Change.** Если в дампе постоянно идут TC-кадры — кто-то перестраивает дерево.

```
$ tshark -r stp.pcap -Y 'stp.flags.tc==1' | wc -l
47
$ tshark -r stp.pcap -T fields -e stp.root.priority | sort -n | head -1
0
```

Приоритет корня `0` — почти наверняка атака.

## Что мы теперь знаем

- STP строит дерево без петель, выбирая корень по минимальному Bridge ID (priority + MAC).
- BPDU — служебные кадры на `01:80:c2:00:00:00` каждые 2 секунды.
- RSTP/MSTP сходятся быстрее; edge-порт переходит в forwarding сразу, но не терпит BPDU.
- Атакующий становится корнем, вбросив BPDU с приоритетом `0`, и перехватывает трафик.
- Защита — BPDU Guard, Root Guard, Loop Guard; признак атаки — аномально низкий приоритет корня.

## Разбираем BPDU побайтово

Вернёмся к нашим BPDU. Это кадры к multicast `01:80:c2:00:00:00` с EtherType `0x0026` (STP) или `0x0027` (RSTP). Внутри — набор полей, по которым выбирается корень. Посмотрим:

```
$ tshark -r stp.pcap -Y stp -V -c 1 | grep -E 'Protocol Identifier|Bridge Identifier|Root|Cost|Hello|Max Age|Forward Delay' | head -8
Protocol Identifier: 0x0000
Bridge Identifier: 32768/52:54:00:11:22:33
Root Identifier: 32768/52:54:00:00:00:01
Root Path Cost: 4
Hello Time: 2.000000 seconds
Max Age: 20.000000 seconds
Forward Delay: 15.000000 seconds
```

Читается так: у моста приоритет `32768` и MAC `52:54:00:11:22:33`; корнем он считает мост `52:54:00:00:00:01` с приоритетом `32768`. Кто корень — определяется парой (приоритет, MAC): **меньше — лучше**.

## Как атакующий становится корнем

Всё, что нужно, — прислать BPDU с **меньшим** приоритетом, чем у текущего корня. Тогда остальные мосты пересчитают дерево и начнут считать **нас** корнем. Инструмент `yersinia` делает это одной командой:

```
$ sudo yersinia -I
# выбираем STP → sending BPDUs → claiming root role
```

В дампе это выглядит как BPDU с подозрительно низким приоритетом (`0` или `1`) и нашим MAC. После «сходимости» дерева трафик между сегментами пойдёт через наш хост — MITM на уровне L2.

| Поле | Обычное значение | Подозрительное |
|---|---|---|
| Bridge Priority | 32768 или 4096 | 0/1 |
| Root Identifier | реальный коммутатор | наш MAC |
| Root Path Cost | растёт с расстоянием | 0 |
| Hello Time | 2 с | нестандартное |

## Эволюция: STP, RSTP, MSTP

| Протокол | Сходимость | Особенность |
|---|---|---|
| STP (802.1D) | 30–50 с | медленный, один экземпляр |
| RSTP (802.1w) | <1 с | быстрые роли, edge-порты |
| MSTP (802.1s) | <1 с | несколько деревьев на VLAN-группы |

Для атакующего RSTP «удобнее» — дерево сходится быстро, и результат виден почти сразу. Для защитника RSTP-атаку легче заметить по частым сменам ролей портов.

## Если не сработало: тебя не пускают в дерево

Причины. Первая — **BPDU Guard** на порту: как только на порт прилетит BPDU от конечного устройства, порт уходит в **err-disabled** — и ты теряешь доступ. Вторая — **Root Guard**: порт, откуда приходит «слишком хороший» корень, блокируется. Третья — **Loop Guard** против односторонних отказов. Четвёртая — тебя просто отключили физически. Проверяй состояние порта: если после отправки BPDU линк упал — сработал BPDU Guard, и это сигнал, что сеть настроена правильно.

## Почему STP — приоритетная цель

STP решает, **куда** физически идёт трафик. Захватив корень, атакующий получает возможность видеть и менять трафик между VLAN/сегментами, не поднимая никаких MITM-инструментов поверх. Поэтому в защите L2 механизмы вокруг STP (BPDU Guard, Root Guard) стоят в одном ряду с DAI и DHCP snooping — это базовый набор.

## Куда дальше

Мы разобрали L2-инфраструктуру: кадр, discovery, VLAN и дерево. Дальше ветка уходит в перехват — начнём с классической атаки на имя в сети Windows, NBT-NS/LLMNR, и с релеинга аутентификации. А пока запомни: **STP защищает от петель, но доверяет любому, кто скажет «я корень» — и это используют для перехвата.**

## Где пригодится

- **CTF:** задачи с BPDU в дампе, определение корня.
- **Пентест:** перехват трафика на L2 через захват root bridge.
- **SOC:** детект поддельных BPDU и топологических атак.
- **Инженерия:** настройка BPDU Guard/Root Guard, диагностика петель.
