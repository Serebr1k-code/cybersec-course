## Вопрос, с которого всё начинается

Ты разбираешь дамп, снятый на шлюзе. Внутри — обычная работа с сайтом: браузер что-то запросил, сервер ответил. Но в одном месте на один TCP-поток приходятся **два** HTTP-запроса, и один из них выглядит так, будто его вписал кто-то другой. Как вообще понять, где кончается один запрос и начинается следующий, если протокол текстовый и «поля» в нём разделены переводами строк?

Этот модуль — про **границы сообщений**. Он опирается на [`network-tcpip`](network-tcpip) (как устроен TCP-поток) и ведёт к [`network-http1-deep`](network-http1-deep), [`network-socks5-protocol`](network-socks5-protocol), [`network-telnet-protocol`](network-telnet-protocol) и [`network-tftp-protocol`](network-tftp-protocol).

## Наш пример: один TCP-поток — два запроса

Возьмём дамп `http1.pcap` и «склеим» один TCP-поток обратно в текст:

```
$ tshark -r http1.pcap -q -z follow,tcp,ascii,0
GET /index.html HTTP/1.1
Host: portal.corp.local
Connection: keep-alive

GET /api/profile HTTP/1.1
Host: portal.corp.local
Transfer-Encoding: chunked
X-Token: bnRve2h0dHAxX2NodW5rM2RfNW11Z2dsM30=
```

Два запроса в одном потоке. Прежде чем что-то с ними делать, надо понять, как сервер решает, где заканчивается первый.

## Шаг 1: из чего состоит HTTP-запрос

HTTP/1.1 — **текстовый** протокол. Запрос состоит из трёх частей:

- **стартовая строка** — метод, путь, версия: `GET /index.html HTTP/1.1`;
- **заголовки** — пары `Имя: значение`, по одному в строке;
- **пустая строка** — сигнал «заголовки кончились»;
- **тело** (необязательно) — данные.

Ключевой момент: пустая строка отделяет заголовки от тела, но **не говорит, какой длины тело**. Без этого сервер не знал бы, где кончается запрос и начинается следующий.

## Шаг 2: Content-Length задаёт длину тела

Самый простой способ — заголовок `Content-Length: N`. Сервер читает ровно `N` байт тела и считает запрос законченным.

```
POST /login HTTP/1.1
Host: portal.corp.local
Content-Length: 27

user=admin&pass=hunter2
```

Здесь всё однозначно: 27 байт — и точка. Проблема начинается, когда длину заранее посчитать нельзя (например, сервер генерирует ответ на лету).

## Шаг 3: chunked — тело, разбитое на куски

Для потоковой отдачи придумали `Transfer-Encoding: chunked`. Тело передаётся **чанками**, и каждый чанк предваряется его размером в **шестнадцатеричном** виде:

```
4
Wiki
5
pedia
0

```

Читается так: `4` → 4 байта данных `Wiki`; `5` → `pedia`; `0` → конец тела. Завершающий `0` — это и есть признак «тело кончилось». Так граница сообщения задаётся не длиной, а маркером.

## Шаг 4: почему границы — вопрос безопасности

Если фронтенд (прокси) и бэкенд определяют границу запроса **по-разному**, рождается **request smuggling**: один запрос «протекает» в другой. Классический случай — когда есть и `Content-Length`, и `Transfer-Encoding`: одни реализации верят длине, другие — чанкам. Атакующий подбирает тело так, что за «концом» первого запроса прячется второй.

В нашем дампе второй запрос несёт заголовок `X-Token` — это и есть отметка о том, что кто-то добавил свой запрос в чужой поток.

## Полный прогон: разбираем дамп

```
$ tshark -r http1.pcap -q -z follow,tcp,ascii,0
... (видим два запроса) ...
$ tshark -r http1.pcap -q -z follow,tcp,ascii,0 | grep -o 'bnRve[A-Za-z0-9+/=]*' | base64 -d
nto{http1_chunk3d_5muggl3}
```

Мы разобрали поток, нашли base64 в заголовке второго запроса и декодировали. Запиши флаг в `answer.txt` и набери `check`.

## Что мы теперь знаем

- HTTP/1.1 — текстовый протокол; запрос = строка + заголовки + пустая строка + тело.
- `Content-Length` задаёт длину тела в байтах, `chunked` — маркер конца (`0`).
- keep-alive позволяет слать много запросов в одном TCP-потоке.
- Разное понимание границ фронтом и бэком = request smuggling.
