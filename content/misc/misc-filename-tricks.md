## Вопрос, с которого всё начинается

Ты распаковываешь присланный архив и запускаешь `ls`. На экране мешанина: часть файлов не видна, один назван `-rf`, ещё один выглядит как два разных имени. Потом твой скрипт делает `rm *` — и сносит лишнее. Проблема не в скрипте, а в **именах файлов**. Разберём, почему имя — это опасно.

## Наш пример

Создадим файл с ведущим дефисом: `touch -- -rf`. Теперь `rm -rf` (без `--`) попытается удалить **всё**, потому что `-rf` будет прочитан как флаг, а не как имя. Имя файла стало аргументом команды. Это и есть **argument injection**.

## Шаг 1: имя — это аргумент

В shell команда и её аргументы разделяются пробелами. Имя файла, содержащее пробел, распадается на два аргумента, если не закавычить. Имя с ведущим дефисом (`-rf`, `--help`) читается утилитой как **опция**, а не как путь. Отсюда правило: всегда ставь `--` перед списком путей — он говорит «дальше только имена».

## Шаг 2: ведущий дефис

Команда `ls -la` выведет список, но если среди файлов есть `-la`, то `ls *` может его подхватить. Опаснее всего там, где имя попадает в команду без `--`: `rm *`, `chmod`, `cat`, `tar`. Классический баг: скрипт делает `rm $file`, а `$file` начинается с `-`.

## Шаг 3: пробелы и переводы строк

Имя файла может содержать пробел и даже перевод строки (`\n`). Тогда в выводе `ls` один файл выглядит как два, а скрипт, читающий список построчно (`while read line`), обработает части неверно. Так ломают парсеры списков и обходят проверки «сколько файлов в архиве».

## Шаг 4: Unicode и нормализация

Имена с гомоглифами (урок `misc-homoglyph`) и разными формами нормализации (NFC/NFD) выглядят одинаково, но различаются байтами. На macOS, где ФС нормализует имена, а Linux — нет, один и тот же файл в архиве может «исчезнуть» или «размножиться». Отсюда атаки на сравнение имён в бэкапах и синхронизациях.

## Шаг 5: escape-коды в имени

Имя может содержать ANSI-escape (урок `misc-terminal-escape`). Тогда `ls` раскрасит вывод и подделает имена: ты видишь один список, а в каталоге другой. Поэтому подозрительные каталоги смотрят через `ls -b` (экранирует непечатаемые) или `find -print0`.

## Шаг 6: путь как инъекция

Имя вида `../../etc/passwd` — это уже path traversal: если приложение склеивает каталог и «имя файла» без проверки, оно выйдет за пределы каталога. Имя — первая точка, где пользователь влияет на путь, поэтому именно здесь живёт большинство файловых уязвимостей.

## Шаг 7: как безопасно работать

- Используй `--` перед путями: `rm -- "$file"`.
- Кавычь переменные: `"$file"`, а не `$file`.
- Читай списки через `find ... -print0` + `xargs -0`, а не через `for`.
- Проверяй имена на `..`, `/`, ведущий `-`, непечатаемые символы.
- В архивах отклоняй абсолютные пути и `..`.

## Шаг 8: практический разбор

Получив архив, не распаковывай его сразу: сначала `tar -tvf archive.tar` покажет имена. Если видишь `../`, абсолютный путь, ведущий дефис или escape — это атака. Распаковывай в изолированный каталог и через `--no-same-owner`, а не в домашний.

## Частые ошибки

- `rm *` без `--` при файлах с дефисом.
- `for f in $(ls)` — ломается на пробелах и переводах строк.
- Доверять именам из архива как «просто строкам».
- Сравнивать имена без учёта Unicode-нормализации.

## Что мы теперь знаем

- Имя файла — это аргумент, а значит потенциальная инъекция.
- Ведущий дефис превращает имя в опцию; лечится `--`.
- Пробелы и `\n` ломают парсеры списков.
- Unicode-нормализация и escape-коды делают имена обманчивыми.
- Безопасные приёмы: `--`, кавычки, `find -print0`, валидация.

## Практика: как выглядит опасное имя в выводе

Обычный `ls` прячет проблему. Сравни два вывода на одном каталоге:

```
$ ls
invoice.pdf  readme.txt  -rf

$ ls -b
invoice.pdf  readme.txt  \ -rf

$ find . -maxdepth 1 -print0 | xargs -0 -n1 printf '[%s]\n'
[.]
[./invoice.pdf]
[./readme.txt]
[./-rf]
```

`ls -b` показывает непечатаемые символы экранированными (пробел — как `\ `, перевод
строки — как `\n`). `find -print0` разделяет записи нулевым байтом, поэтому имя с
пробелом или переводом строки не распадётся на части. Именно так безопасно перечисляют
файлы: не по строкам, а по нулевым разделителям.

## Таблица: символ → риск → защита

| Символ в имени | Чем опасен | Как защититься |
|----------------|-----------|----------------|
| ведущий `-` | читается как флаг | `--` перед путями |
| пробел / таб | рвёт разбор по словам | кавычки, `find -print0` |
| перевод строки | ломает `while read` | `IFS= read -r`, `-print0` |
| `..` / `/` | path traversal, zip-slip | валидация, распаковка в sandbox |
| непечатаемые/ANSI | подделка вывода | `ls -b`, `cat -v` |
| bidi/zero-width | скрывает код в диффе | линтер невидимых символов |

Эта таблица — короткий чек-лист: получив каталог извне, прогони по нему именно эти
классы символов, прежде чем что-то делать с файлами.

## Архивы: проверка до распаковки

Zip-slip — это имя вида `../../etc/cron.d/x` внутри архива, из-за которого распаковка
пишет за пределы целевого каталога. Проверяй состав архива **до** распаковки:

```
$ tar -tvf suspicious.tar | grep -E '(^|/)\.\.|^/'
-rw-r--r-- user/user  ../.ssh/authorized_keys
```

Любое имя с `..` или начинающееся с `/` — красный флаг. Распаковывай только в
изолированный каталог и с `--no-same-owner`, а для Python — используй
`tarfile`/`zipfile` с проверкой каждого элемента перед извлечением.

## Если сработало / не сработало

- **Сработало:** `tar -tvf` показал `../` или абсолютный путь, либо `ls -b` вскрыл
  непечатаемые символы — значит, источник недоверенный и приём применим.
- **Не сработало:** имена выглядят чисто, но приложение всё равно читает файл за
  пределами каталога — ищи не сам архив, а склейку `dir + name` в коде: там могла
  пропасть нормализация (`os.path.realpath` + проверка префикса).
- **Ложное срабатывание:** имя содержит пробел, но это легитимный файл. Пробел сам
  по себе не атака — атака там, где имя попадает в команду без кавычек.

## Ограничения темы

Имя файла — только одна точка входа. Если приложение не выводит имена наружу и не
строит из них команд, эти приёмы бесполезны. Также часть трюков зависит от
файловой системы: на macOS имена нормализуются, на Linux — нет, поэтому один и тот же
архив ведёт себя по-разному. Всегда проверяй, **где** именно имя попадает в логику.

## Как именно ломается `for f in $(ls)`

Классическая ошибка новичка — перебирать файлы так:

```
$ mkdir t && cd t && touch 'a b.txt' 'c d.txt'
$ for f in $(ls); do echo "[$f]"; done
[a]
[b.txt]
[c]
[d.txt]
```

Один файл с пробелом распался на два «имени». Скрипт, который внутри делал
`rm "$f"`, попытался бы удалить `a` и `b.txt` — то есть не то, что задумано. Правильно:

```
$ find . -maxdepth 1 -type f -print0 | while IFS= read -r -d '' f; do echo "[$f]"; done
[./a b.txt]
[./c d.txt]
```

`-print0` и `read -d ''` работают с нулевым разделителем, поэтому пробелы и переводы
строк в именах больше не рвут разбор. Это правило стоит запомнить как рефлекс:
перечисляешь файлы — разделяй нулём, а не новой строкой.

## Распаковка в Python: zip-slip в коде

Опасность проявляется и в коде. Наивная распаковка:

```python
import zipfile
with zipfile.ZipFile("in.zip") as z:
    z.extractall("/dest")          # ОПАСНО: доверяет именам из архива
```

Если внутри есть `../../etc/cron.d/x`, `extractall` запишет файл вне `/dest`.
Безопасный вариант проверяет каждый элемент:

```python
import zipfile, os
dest = os.path.realpath("/dest")
with zipfile.ZipFile("in.zip") as z:
    for name in z.namelist():
        target = os.path.realpath(os.path.join(dest, name))
        if not target.startswith(dest + os.sep):
            raise ValueError(f"zip-slip: {name}")
        z.extract(name, "/dest")
```

Проверка через `realpath` + префикс ловит и `..`, и абсолютные пути, и симлинки.

## Чек-лист безопасной работы с именами

| Шаг | Действие |
|-----|----------|
| 1 | получил каталог — сначала `ls -b` и `find -print0` |
| 2 | архив — `tar -tvf`/`zipinfo` до распаковки |
| 3 | распаковка — только в изолированный каталог |
| 4 | команды — пути через `--` и в кавычках |
| 5 | код — валидация каждого имени через `realpath` |
