## Вопрос, с которого всё начинается

Мы научились определять формат по байтам. Теперь формат известен — это **структурированный текст**: JSON, YAML или XML. Кажется, всё просто: данные в понятной форме. Но каждый из этих форматов допускает двусмысленности, и разные парсеры трактуют одни и те же байты **по-разному**.

А это уже баг: то, что проверяющая система считает «безопасным», исполнитель видит как «опасное». Разберём это на конкретном API.

## Наш пример: API, проверяющий роль

Есть эндпоинт, который принимает JSON и отдаёт секрет только администратору. Логика такая: валидатор строго проверяет `role == "user"`, а потом код авторизации читает ту же структуру. Попробуем обычный запрос:

```bash
$ curl -s -X POST http://chal/api -H 'Content-Type: application/json' \
    -d '{"role":"admin"}'
{"error":"forbidden"}
```

Отказано. Ломать нечего — значит, надо найти вход, который валидатор и исполнитель **прочитают по-разному**.

## Шаг 1: дубликаты ключей в JSON

Спецификация JSON **не запрещает** повторяющиеся ключи. Что возьмёт парсер — зависит от реализации:

```json
{"role": "user", "role": "admin"}
```

- Python `json.loads` берёт **последнее** значение (`admin`);
- многие строгие парсеры — **первое** (`user`);
- некоторые вообще падают с ошибкой.

Отсюда классический обход: если валидатор берёт первое значение, а логика — последнее, отправляем:

```bash
$ curl -s -X POST http://chal/api -H 'Content-Type: application/json' \
    -d '{"role":"user","role":"admin"}'
{"secret":"flag{dup_k3ys}"}
```

Валидатор увидел `user` и пропустил; логика взяла `admin` и отдала секрет. Это реальный класс уязвимостей, а не только CTF-трюк.

## Шаг 2: Unicode-экранирование ключей

Тот же эффект даёт экранирование. Ключ `"\u0072ole"` — это ровно `"role"`, но фильтр, ищущий подстроку `role`, его не поймает:

```json
{"\u0072ole": "admin"}
```

Парсер декодирует `\u0072` в `r` и получит ключ `role`, а наивная проверка по сырому тексту — нет. Это тот же принцип, что и Unicode-трюки из `misc-unicode`: сравнивать надо **после** разбора.

## Шаг 3: JSON-инъекция через конкатенацию

Если приложение строит JSON-строку склейкой:

```python
payload = '{"user":"' + user_input + '"}'
```

то ввод `x","admin":true,"z":"` даёт валидный `{"user":"x","admin":true,"z":""}`. Это **JSON-инъекция**. Лечится не склейкой, а нормальной сериализацией.

## Шаг 4: YAML — мощь и опасность

YAML богаче JSON: поддерживает теги, якоря и **произвольные объекты**. Небезопасная десериализация в PyYAML (`yaml.load` без `SafeLoader`) исполняет код:

```yaml
!!python/object/apply:os.system ["id"]
```

Или реверс-шелл:

```yaml
!!python/object/apply:subprocess.check_output
  - ["/bin/sh", "-c", "cat /flag"]
```

Правило: парсить **данные**, а не код. Используйте `yaml.safe_load`. Но даже `safe_load` уязвим к **billion laughs** — экспоненциальному раздуванию через якоря:

```yaml
a: &a ["x","x","x","x","x","x","x","x","x"]
b: &b [*a,*a,*a,*a,*a,*a,*a,*a,*a]
c: &c [*b,*b,*b,*b,*b,*b,*b,*b,*b]
```

Каждый уровень умножает размер на 9 — сотня байт раздувается до гигабайт, память кончается (DoS).

## Шаг 5: XML — XXE и billion laughs

XML поддерживает **внешние сущности**. Если парсер не отключил DTD, атакующий читает файлы и делает SSRF:

```xml
<?xml version="1.0"?>
<!DOCTYPE foo [
  <!ENTITY xxe SYSTEM "file:///etc/passwd">
]>
<root>&xxe;</root>
```

Сервер подставит содержимое `/etc/passwd` вместо `&xxe;`. Защита — отключить DTD и внешние сущности:

```python
parser = etree.XMLParser(resolve_entities=False, no_network=True)
```

Billion laughs в XML работает так же: сущности ссылаются друг на друга, и каждый уровень умножает текст на 10.

## Шаг 6: почему расхождение парсеров — это уязвимость

Ключевая идея урока: **если два компонента по-разному парсят один вход, между ними есть «зазор»**. Этот класс называют parser differential. Реальные CVE строились на разной обработке `\u0000`, дубликатов заголовков, нормализации Unicode.

| Трюк | Что эксплуатирует |
|------|-------------------|
| Дубликат ключа | Разные приоритеты first/last |
| Unicode-escape ключа | Фильтр по строке не срабатывает |
| YAML-тег | RCE при небезопасном load |
| YAML-якоря | Billion laughs (DoS) |
| XXE | Чтение файлов / SSRF |
| Комментарии/пробелы | Обход простого regex |

В CTF задача часто даёт «валидатор» и «исполнитель» — и надо найти вход, который они интерпретируют по-разному. Инструментально это исследуют, подавая один вход в оба компонента и сравнивая результат.

## Шаг 7: числа, комментарии и BOM

Ещё несколько зазоров:

- **Числа и типы.** `1`, `1.0` и `1e0` разные парсеры дадут как `int`, `float` или строку. А `NaN`, `Infinity`, `-Infinity` — не валидный JSON по RFC, но Python и JS их принимают. Очень большие числа теряют точность в JS (`Number.MAX_SAFE_INTEGER`).
- **Комментарии и пробелы.** Некоторые парсеры (JSON5, конфиги) допускают комментарии и висячие запятые — это тоже расхождение.
- **BOM (`\ufeff`) и пробелы перед `{`.** Одни парсеры их отбрасывают, другие падают — это тоже «зазор».
- **`\u0000`.** Строка может «обрезаться» на null-байте в одном слое и не обрезаться в другом.

Все эти различия — тот же принцип: вход, который два компонента видят по-разному.

## Шаг 8: десериализация в разных языках

Опасная грань YAML — создание **произвольных объектов**. Это есть не только в Python:

- Ruby: `Psych.load` (безопасен) против `unsafe_load`;
- Java: SnakeYAML с небезопасным конструктором;
- .NET: аналогичные десериализаторы.

Правило одно: **парсите данные, а не код**. Используйте `safe_load`/`SafeConstructor` и, где можно, схемы (JSON Schema, XSD). XML добавляет `XInclude` (`<xi:include href="file:///etc/passwd"/>`) даже при отключённых внешних сущностях — отключайте его явно (`defusedxml`).

## Что мы теперь знаем

- JSON допускает дубликаты ключей, и парсеры берут первое/последнее значение по-разному — это зазор для обхода.
- Unicode-экранирование ключа обходит наивный фильтр по подстроке.
- YAML-теги (`!!python/object/...`) дают RCE при `yaml.load` без `SafeLoader`.
- Якоря YAML/XML дают billion laughs — экспоненциальный DoS, даже под `safe_load`.
- XML с DTD даёт XXE: чтение файлов и SSRF; защита — `resolve_entities=False`.
- Правило: парсите данные, а не код; сравнивайте после разбора.

## На что смотреть дальше

- **`yaml.load` без `SafeLoader`** — прямой RCE.
- **Считать «валидный JSON» однозначным** — дубликаты и числа зависят от реализации.
- **Открывать чужой XML/HTML в браузере** — сработает XXE/SSRF.
- **BOM и пробелы перед `{`** — одни парсеры падают, другие нет.
- **`\u0000`** — строка может «обрезаться» на null-байте в одном слое.
- **Считать, что `safe_load` защищает от DoS** — billion laughs работает и там.
