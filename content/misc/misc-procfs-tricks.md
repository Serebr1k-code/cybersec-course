## Вопрос, с которого всё начинается

В задаче есть чтение файлов по имени, но не классический LFI: путь проверяется. Ты замечаешь, что можно попросить прочитать файл с абсолютным путём вроде `/proc/self/environ`. Почему это опасно и что вообще лежит в `/proc`?

## Наш пример: карты памяти процесса

Посмотрим, что процесс рассказывает о себе:

```
$ cat /proc/self/maps
55d8f1a00000-55d8f1a01000 r--p 00000000 08:01 1234567 /usr/bin/cat
7f2b3c000000-7f2b3c021000 r-xp 00000000 08:01 7654321 /usr/lib/libc.so.6
7fff5a000000-7fff5a021000 rw-p 00000000 00:00 0 [stack]
```

Здесь видно, какие библиотеки загружены, где код, где стек. Из `/proc` любой процесс (с достаточными правами) может узнать о другом почти всё. Разберём, что именно.

## Шаг 1: что такое /proc

**/proc** — виртуальная файловая система: файлов на диске нет, ядро генерирует их содержимое по запросу. Каталог `/proc/<pid>` описывает процесс с номером `<pid>`: его командную строку, окружение, открытые файлы, карты памяти. `/proc/self` — псевдоним «текущего» процесса, то есть того, кто читает.

## Шаг 2: cmdline и environ

```
$ cat /proc/self/cmdline | tr '\0' ' '
cat /proc/self/cmdline
$ cat /proc/self/environ | tr '\0' '\n' | head
PATH=/usr/bin
HOME=/root
```

`cmdline` — аргументы запуска, `environ` — переменные окружения. В окружении часто лежат секреты: токены, пароли, ключи. Отсюда классический трюк: если приложение пишет логи с ошибками окружения или отдаёт файлы, `/proc/self/environ` становится источником утечки.

## Шаг 3: maps — карта памяти

Из `maps` видно адреса библиотек и их версии. Это нужно и для отладки, и для эксплуатации: узнав адрес `libc`, можно строить ROP-цепочку (мост к `misc-rop-misc`). Каждая строка — диапазон адресов, права (`r-xp`), смещение и путь файла.

## Шаг 4: fd — открытые дескрипторы

```
$ ls -l /proc/self/fd
lrwx------ 1 root root 64 ... 0 -> /dev/pts/0
lrwx------ 1 root root 64 ... 3 -> /home/app/secret.env
```

Каждый дескриптор — символическая ссылка на файл, с которым процесс работает. Если у процесса уже открыт секретный файл, его можно прочитать через `/proc/<pid>/fd/<n>`, даже не зная пароля к самому файлу. Это частый обход прав: доступ к файлу идёт через дескриптор, а не через путь.

## Шаг 5: root и cwd

Две символические ссылки, которые многие недооценивают:

- `/proc/<pid>/cwd` — текущий рабочий каталог;
- `/proc/<pid>/root` — корень файловой системы процесса.

Если процесс работает в другом mount namespace (например, в контейнере), `/proc/<pid>/root` открывает его корень. А при попытке побега из chroot каталог `/proc/self/root` может обойти ограничение, если chroot не изолирован как следует.

## Шаг 6: трюк с /proc/self/root при побеге

Классический приём: если программа в `chroot`, но у неё остался доступ к внешнему `/proc`, можно попытаться выйти через `/proc/1/root` (корень процесса снаружи) или через открытый дескриптор. Именно поэтому изоляцию часто делают через namespaces, а не только chroot: `misc-namespace-deep` объясняет, почему mount namespace надёжнее.

## Шаг 7: /sys и sysrq

**/sys** — другая виртуальная ФС, описывающая устройства и параметры ядра. Особо опасен `/proc/sysrq-trigger`: запись в него может перезагрузить машину, синхронизировать диски или убить процессы. Если приложение позволяет писать файлы по произвольному пути, `/proc/sysrq-trigger` — прямой путь к разрушению системы.

## Шаг 8: /proc/sys и параметры ядра

`/proc/sys` (он же `sysctl`) содержит настройки ядра: `kernel.randomize_va_space`, `net.ipv4.ip_forward`, `kernel.io_uring_disabled`. Через них можно узнать конфигурацию (включён ли ASLR) и, при правах, менять её. В задачах это способ определить, какие техники применимы.

## Шаг 9: утечки через /proc

Типичные источники данных:

- `/proc/<pid>/cmdline` и `environ` — секреты в аргументах и окружении;
- `/proc/<pid>/maps` — версии библиотек и адреса;
- `/proc/<pid>/fd/*` — доступ к открытым файлам;
- `/proc/net/*` — таблицы соединений и сокетов.

Каждый из них — потенциальная утечка, если приложение позволяет читать произвольные пути.

## Шаг 10: защита

Что реально помогает:

- не хранить секреты в аргументах и окружении;
- запрещать доступ к `/proc` для непривилегированных (hidepid);
- использовать mount namespaces для изоляции;
- проверять пути по белому списку, а не по чёрному (иначе `/proc/self/...` проходит).

## Шаг 11: как это выглядит в задаче

Дано: сервис читает файл по имени и отдаёт содержимое, но запрещает путь со словом `flag`. Решение: читать через дескриптор (`/proc/self/fd/N`) или через окружение, обходя фильтр имён. Смысл урока — фильтр по строке пути обходится, потому что у одного файла много имён.

## Шаг 12: /proc в контейнерах

В контейнере `/proc` показывает процессы контейнера, но через host `/proc` (если он смонтирован) видно всё. Отсюда правило: не монтировать host `/proc` в контейнер и не давать `CAP_SYS_PTRACE`, иначе `environ` и `maps` чужих процессов становятся доступны.

## Статус и лимиты процесса

Файл `/proc/<pid>/status` — сводка: имя, состояние, идентификаторы, размеры памяти, а также уже знакомые строки `Seccomp:` и `CapEff` (эффективные capabilities). Из `status` видно, какие права есть у процесса: наличие `cap_sys_admin` сразу расширяет список возможных атак. Ещё есть `/proc/<pid>/limits` — жёсткие лимиты (число файлов, стек, память), по которым понятно, что процессу разрешено.

## /proc/net: сеть без инструментов

Каталог `/proc/net` показывает сетевые структуры ядра:

- `/proc/net/tcp` — активные TCP-соединения (адреса в hex);
- `/proc/net/udp` — UDP-сокеты;
- `/proc/net/arp` — таблица ARP;
- `/proc/net/route` — маршруты.

Это «netstat без netstat»: если привычные утилиты недоступны (урезанный контейнер), данные всё равно лежат в `/proc/net`. В задачах это быстрый способ узнать, куда идёт трафик.

## Скрытые данные: mem и page-map

`/proc/<pid>/mem` даёт доступ к памяти процесса, а `/proc/<pid>/maps` — к её карте. С `CAP_SYS_PTRACE` можно читать чужую память прямо из этого файла, без `ptrace`. А `/proc/kcore` — образ памяти ядра (только для root). Всё это — источники секретов и ключей, поэтому доступ к `/proc` ограничивают.

## hidepid и монтирование

Опция монтирования `hidepid` управляет видимостью чужих процессов:

```
$ mount | grep ' /proc '
proc on /proc type proc (rw,nosuid,nodev,noexec,relatime,hidepid=2)
```

`hidepid=2` скрывает каталоги чужих процессов — непривилегированный пользователь видит только свои. Без этой опции любой пользователь может читать `cmdline` и `environ` соседей (если позволяет ядро и права). Проверка `hidepid` — первый шаг при аудите утечек через `/proc`.

## /proc/self — почему это важно для фильтров

`/proc/self` — не отдельный каталог, а ссылка на процесс, который сейчас читает. Это ломает многие «умные» фильтры: строка пути не содержит конкретного PID, но ведёт к текущему процессу. Аналогично `/proc/thread-self` указывает на текущий поток. Поэтому проверка «запретить /proc/<числа>» недостаточна — обход идёт через `self`.

## Файлы ядра как разведка

Помимо настроек, `/proc` отдаёт версии и состояние: `/proc/version` (версия ядра), `/proc/cpuinfo` (флаги CPU, важные для выбора техник), `/proc/mounts` (что смонтировано). Сбор этих файлов — стандартная разведка после получения доступа: они подсказывают, какие уязвимости и приёмы применимы.

## Разбор примера по шагам

Вернёмся к нашей карте памяти и прочитаем её внимательно:

```
55d8f1a00000-55d8f1a01000 r--p 00000000 08:01 1234567 /usr/bin/cat
7f2b3c000000-7f2b3c021000 r-xp 00000000 08:01 7654321 /usr/lib/libc.so.6
7fff5a000000-7fff5a021000 rw-p 00000000 00:00 0 [stack]
```

- левый столбец — диапазон адресов памяти;
- `r--p` / `r-xp` / `rw-p` — права: чтение/запись/исполнение и «private»;
- `08:01` — устройство, `1234567` — inode файла;
- справа — путь файла или имя региона (`[stack]`, `[heap]`).

Отсюда два вывода. Первый: видно, какие библиотеки загружены (и их версии — по пути). Второй: видно адреса, где они лежат, — это нужно для эксплуатации (адрес `libc` в примере — `7f2b3c000000`).

## Почему ASLR видно, но не «ломает» идею

Адреса в `maps` меняются при каждом запуске из-за ASLR (`misc-aslr-bypass`), но саму утечку это не отменяет: если приложение отдаёт `/proc/self/maps`, ты получаешь актуальные адреса именно этого запуска. То есть ASLR защищает от угадывания, но не от утечки. Поэтому «дать прочитать `/proc/self/maps`» — почти всегда дыра.

## Как отличить утечку от шума

Не всякий файл в `/proc` опасен. Признаки реальной утечки:

- в содержимом есть то, чего пользователь не должен знать (пароли, токены, адреса);
- доступ к файлу не требует root;
- файл читается через тот же механизм, что и обычные данные приложения.

Если все три условия выполнены — перед тобой находка, а не «служебная информация».

## Итог ветки

Мы прошли четыре механизма «внутрь ядра»: eBPF (программы в ядре), bpftrace (трассировка), io_uring (асинхронный ввод-вывод) и `/proc` (наблюдение за процессом). Общее у них одно — все они показывают, что ядро знает о процессе гораздо больше, чем видно снаружи. Умение читать эту информацию и есть навык низкоуровневого разбора.

## Что мы теперь знаем

- `/proc/<pid>` описывает процесс: cmdline, environ, maps, fd, root, cwd.
- `/proc/self` — псевдоним текущего процесса.
- Дескрипторы и `/proc/<pid>/root` позволяют обходить проверки путей.
- `/proc/sysrq-trigger` опасен при записи.
- Защита: не хранить секреты в окружении, ограничивать доступ, использовать namespaces.
