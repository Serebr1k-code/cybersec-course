## Вопрос, с которого всё начинается

В Solidity токен — это запись в маппинге контракта. В Move токен — это **ресурс**, который нельзя скопировать или потерять: компилятор не даст. Звучит как гарантия от целого класса багов — и это правда. Но новая модель порождает свои ошибки, и в CTF их эксплуатируют так же охотно.

## Наш пример: структура монеты

```move
module coin::mycoin {
    struct Coin has key, store { value: u64 }

    public fun split(c: &mut Coin, amount: u64): Coin {
        assert!(c.value >= amount, EINSUFFICIENT);
        c.value = c.value - amount;
        Coin { value: amount }
    }
}
```

Функция «отщипывает» часть монеты. Разберём, что здесь может пойти не так, и почему вообще компилятор что-то проверяет.

## Шаг 1: что такое ресурс

В Move тип с `has key, store` ведёт себя как линейный: значение можно **переместить**, но не скопировать и не удалить молча. `Coin { value: amount }` создаёт новый ресурс — и старый обязан быть учтён. Если функция создаёт монеты «из воздуха», не уничтожив столько же, компилятор это поймает — но только если абстракция полная.

```
error[E01002]: unexpected token
  │ cannot copy a resource type
```

Эта ошибка — то, ради чего Move придумывали. Она спасает от двойной траты на уровне типов. В Solidity эквивалента нет: там `mapping` можно испортить одной строкой, и компилятор промолчит.

## Шаг 2: abilities и их последствия

`has key` — объект хранится в глобальном хранилище по адресу. `has store` — его можно вложить в другой ресурс. `has copy` — можно копировать (для монет это запрещено!). `has drop` — можно удалить без учёта (тоже запрещено для монет).

Баг начинается там, где разработчик **выдаёт ресурсу лишнюю ability**. Дать монете `copy` — значит разрешить её дублирование. Дать `drop` — разрешить «сжигать» без записи. Оба — фатальны.

```move
struct Coin has key, store, copy {}   // СЕРЬЁЗНАЯ ОШИБКА
```

С такой структурой `split` выше может вернуть копию, а оригинал остаться нетронутым — двойная трата «на уровне типов», которую компилятор разрешил.

## Шаг 3: Sui-специфика — объекты и transfer

В Sui ресурсы — это **объекты** с уникальным ID. Их передают функциями `transfer::transfer` или `transfer::public_transfer`. Классический баг — забыть проверить владельца объекта перед изменением:

```move
public fun withdraw(coin: &mut Coin, ctx: &mut TxContext) {
    // нет проверки, что ctx.sender() — владелец coin
    let v = coin.value;
    transfer::public_transfer(coin::take(coin, v), tx_context::sender(ctx));
}
```

Если проверки нет, любой, кому передан объект по ссылке (например, через shared object), может вывести чужие средства. В Sui различают **owned** и **shared** объекты; shared-объекты доступны всем, и защита ложится на логику.

## Шаг 4: entry-функции и public

`entry`-функции вызываются извне транзакции. `public` — вызываются другими модулями. `public(friend)` — только «друзьями». Ошибка — сделать внутреннюю функцию `public` и обойти проверки, которые есть в `entry`-обёртке. Всегда проверяйте, что опасная логика не вызывается в обход entry-point.

```move
entry fun admin_only(...) { ... }        // есть проверка внутри
public fun _admin_only(...) { ... }      // та же логика без проверки — дыра
```

## Шаг 5: capability-паттерн

Capability-паттерн (`struct AdminCap has key`) — это «право», объект-ключ. Если он `store` и передаётся кому угодно, права утекают. Capability должен создаваться один раз и храниться так, чтобы его нельзя было получить публичной функцией без проверки.

```move
struct AdminCap has key { id: UID }

public fun mint_cap(ctx: &mut TxContext) {
    // если это доступно любому — привилегии захвачены
    transfer::transfer(AdminCap { id: object::new(ctx) }, tx_context::sender(ctx));
}
```

## Шаг 6: где искать баги

| Место | Что искать |
|---|---|
| `has copy` на ресурсе | нельзя для монет |
| `has drop` на монете | сжигание без учёта |
| `entry` vs `public` | обход проверок |
| shared object | кто может вызвать |
| `public_transfer` | проверен ли владелец |
| Capability-объекты | не подделать ли |

## Полный прогон: подделка capability

Задача: модуль хранит `AdminCap`, и любой, кто им владеет, может менять параметры. Если `AdminCap` можно получить через публичную функцию без проверки — привилегии захватываются.

```
$ sui client call --function mint_cap --module vuln --args ...
# вместо проверки "только админ" — любой может вызвать
flag: nto{m0v3_c4p4b1l1ty_c0nfus10n}
```

Move защищает от «случайной» двойной траты, но **не** от логических ошибок в правах доступа. Это ключевое различие: компилятор проверяет типы, но не намерения.

## Если не сработало

Если компилятор не даёт создать монету из воздуха, ищите обход через `public`-функции, которые обходят проверки, или через shared-объекты, доступные всем. Иногда достаточно найти одну функцию без `assert!`, чтобы добраться до привилегий.

## Инструменты

- `sui move build` / `sui move test` — сборка и тесты.
- `move-prover` — формальная верификация (редко в CTF, но полезно).
- `sui client` — вызовы в тестовой сети.

## Что мы теперь знаем

- Move-ресурс — линейный тип: перемещается, но не копируется.
- `copy`/`drop` на монете — фатальная ошибка.
- Sui различает owned и shared объекты; shared доступны всем.
- `entry`/`public` — разные пути входа, обход одного открывает дыру.
- Capability-объект — это право; его утечка = захват привилегий.

## Как читать Move/Sui-модуль

Сначала — объявления `struct` и их abilities. Затем — все `entry` и `public` функции. Затем — кто проверяет `ctx.sender()`. Именно на стыке «что доступно» и «что проверено» живут эксплойты.

## Сравнение с EVM: что даёт линейность

Главное отличие Move от Solidity — не синтаксис, а **линейная логика**. В Solidity «баланс» — это число в маппинге, и никто не мешает записать в него что угодно. В Move монета — это значение, которое существует ровно в одном месте. Если функция возвращает `Coin`, вызывающий обязан его куда-то деть: сохранить, передать или явно уничтожить (`destroy`). Компилятор следит за этим.

Это убирает целый класс багов: нельзя случайно «создать» монету из ниоткуда, нельзя «потерять» её, нельзя скопировать. Но остаются логические ошибки: неверные проверки доступа, неверные abilities, обход `entry`-точек. Именно они и составляют большинство CTF-задач по Move/Sui.

## Разбор второго примера: казначейство с capability

```move
module treasury::vault {
    use sui::object::{Self, UID};
    use sui::transfer;
    use sui::tx_context::{Self, TxContext};

    struct AdminCap has key { id: UID }
    struct Vault has key { id: UID, balance: u64 }

    public entry fun withdraw(cap: &AdminCap, vault: &mut Vault, amount: u64, ctx: &mut TxContext) {
        assert!(vault.balance >= amount, ENOUGH);
        vault.balance = vault.balance - amount;
        // перевод вызывающему
        let _ = ctx;
    }
}
```

Здесь защита держится на том, что `withdraw` требует `&AdminCap`. Если `AdminCap` невозможно подделать и его нельзя получить без проверки — контракт безопасен. Но если рядом есть функция:

```move
public entry fun claim_cap(ctx: &mut TxContext) {
    transfer::transfer(AdminCap { id: object::new(ctx) }, tx_context::sender(ctx));
}
```

— то любой вызывает `claim_cap` и получает права. Это типичная ошибка: разработчик вынес «выдачу cap» в публичную функцию, не подумав, что она станет входной точкой для всех.

## Как Sui отличается от оригинального Move

Изначальный Move (Diem) хранил ресурсы в «глобальном хранилище» под аккаунтами. Sui переосмыслил модель: объекты имеют глобально уникальные ID и передаются как параметры транзакции. Это меняет и класс багов: в Sui особенно важна разница между **owned** и **shared** объектами. Owned-объект принадлежит одному адресу и недоступен другим; shared-объект может изменять любой, и вся защита — в коде. Если разработчик случайно сделал объект shared (или оставил публичную функцию, возвращающую ссылку), привилегии утекают.

## Частые вопросы новичков

Что такое `UID`? Это поле `id: UID`, которое делает структуру объектом Sui: по нему объект получает уникальный адрес. Зачем `has store`, если объект и так в хранилище? `store` нужен, чтобы объект можно было **вложить** в другой ресурс; без него его нельзя хранить внутри структуры. Можно ли вернуть монету, не сохранив? Нет — компилятор заставит либо передать, либо явно уничтожить её функцией с `drop`.

## Практика без лаборатории

Напишите модуль с монетой и намеренно добавьте `copy` в её abilities — компилятор `sui move build` выдаст ошибку `E01002`. Затем уберите `copy` и добавьте публичную функцию, выдающую `AdminCap`; напишите `sui move test`, который вызывает её от «атакующего» адреса, и убедитесь, что права захватываются. Это закрепит понимание линейной модели лучше любого текста.

## Итог по модели угроз

Соберём картину целиком. Move защищает от класса ошибок, связанных с **владением значением**: двойная трата, потеря ресурса, случайное копирование. Это достигается линейной системой типов и abilities. Но Move ничего не знает о ваших **намерениях**: он не проверяет, что `withdraw` вызывает только админ, что `AdminCap` нельзя получить публично, что shared-объект защищён логикой. Поэтому в аудите Move/Sui вы ищете именно логические пропуски, а не «дыры в памяти». Запомните три вопроса: какие abilities у ресурса, какие функции публичны, кто проверяет отправителя. Ответы на них покрывают большинство задач.
