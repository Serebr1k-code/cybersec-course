## Вопрос, с которого всё начинается

Приложение хранит данные в `app.db` — это SQLite. Ты открываешь базу и видишь: таблица пуста. Но приложение точно что-то хранило. Куда делись записи и можно ли их вернуть?

Можно. SQLite — это файл, а удаление в файле почти никогда не стирает байты. Это урок про восстановление удалённого в SQLite.

## Наш пример: пустая база

```
$ sqlite3 app.db ".tables"
users
$ sqlite3 app.db "select * from users;"
$ sqlite3 app.db "select count(*) from users;"
0
```

Таблица есть, строк нет. Но размер файла подозрительно большой:

```
$ ls -l app.db
-rw-r--r-- 1 user user 12288 app.db
```

12 КБ на пустую таблицу — значит, данные внутри остались.

## Шаг 1: как устроен файл SQLite

Файл SQLite разбит на **страницы** фиксированного размера (обычно 4096 байт). Первая страница — заголовок базы с магией `SQLite format 3\0` и размером страницы. Каждая таблица — **B-tree**: дерево страниц, где листья хранят записи.

Удаление строки не трогает байты: SQLite просто помечает место свободным и добавляет страницу в **freelist** — список освобождённых страниц для повторного использования. Пока страница не перезаписана, старые данные читаются.

## Шаг 2: WAL и journal

Два журнала ускоряют и защищают запись:

- **rollback journal** (`app.db-journal`) — старая схема: перед изменением страницы копируются в журнал, при откате восстанавливаются.
- **WAL** (`app.db-wal`) — Write-Ahead Log: изменения сначала пишутся в WAL, потом переносятся в основную базу.

Для форензики важно: в WAL и journal лежат **свежие** версии данных, иногда уже удалённые из основной базы. Если файл `-wal` есть — читай и его.

```
$ ls -l app.db*
-rw-r--r-- 1 user user 12288 app.db
-rw-r--r-- 1 user user  4152 app.db-wal
```

## Шаг 3: восстановление через .recover

SQLite умеет восстанавливать сам:

```
$ sqlite3 app.db ".recover" | sqlite3 recovered.db
$ sqlite3 recovered.db "select * from users;"
1|admin|nto{sq11t3_fr33l1st}
```

`.recover` обходит B-tree и freelist, вытаскивая всё, что похоже на записи. Это самый быстрый путь.

## Шаг 4: ручной разбор страниц

Если `.recover` не помог, читаем страницы вручную. Ищем сигнатуры записей — часто это читаемые строки:

```
$ strings -a app.db | grep -i nto
nto{sq11t3_fr33l1st}
$ xxd app.db | grep -A1 '6e74 6f7b'
```

`nto{` — это ASCII `6e 74 6f 7b`. Найдя его в дампе, читаем окрестность: часто рядом лежат поля записи.

Более структурно: определить размер страницы (из заголовка), пройти по всем страницам, для каждой найти «cell pointer array» и декодировать записи. Удалённые ячейки остаются в freelist-страницах.

## Шаг 5: инструменты

- **sqlite3** — `.recover`, `.dump`, `.schema`.
- **undark** — Python-инструмент для извлечения удалённых записей из freelist.
- **sqlite-forensics** — утилиты для page-level анализа.
- **strings/xxd** — грубый, но быстрый способ.

```
$ python3 -m undark app.db
$ sqlite3 app.db "pragma freelist_count;"
3
```

`freelist_count` показывает, сколько страниц свободно — там и лежат удалённые данные.

## Шаг 6: почему данные остаются

SQLite оптимизирован под скорость: перезаписывать байты при удалении дорого. Поэтому запись «удалена» — это лишь запись в служебную структуру. Реальная очистка происходит при `VACUUM`, который пересобирает базу. Поэтому:

- до `VACUUM` — удалённое читается;
- после `VACUUM` — часто нет (страницы перезаписаны).

Это ключевая деталь для CTF и для реальной форензики.

## Полный прогон

```
$ sqlite3 app.db ".recover" | sqlite3 rec.db
$ sqlite3 rec.db ".tables"
users
$ sqlite3 rec.db "select * from users;"
1|admin|nto{sq11t3_fr33l1st}
```

Флаг извлечён из удалённой строки.

## Что мы теперь знаем

- SQLite — файл со страницами и B-tree.
- Удаление помечает место свободным, но не стирает байты.
- Freelist хранит освобождённые страницы с данными.
- WAL/journal содержат свежие версии записей.
- `.recover`, undark и ручной разбор восстанавливают удалённое.

## Заголовок базы в деталях

Первые 100 байт файла SQLite — заголовок. Ключевые поля: магия `SQLite format 3\0` (16 байт), размер страницы (смещение 16, обычно 4096), число страниц, версия формата, счётчик изменений (used для WAL). Зная размер страницы, можно резать файл на страницы и разбирать каждую. Это основа любого ручного восстановления: без заголовка не понять структуру.

## Как устроена B-tree страница

Страница B-tree начинается с заголовка: тип (interior/leaf), число ячеек, смещение первой свободной ячейки, массив указателей на ячейки. Каждая ячейка — запись с полями: для leaf — `payload length`, `rowid`, `record`; для interior — указатель на дочернюю страницу. Записи (records) хранят значения столбцов в формате varint. Освоив этот разбор, ты читаешь данные напрямую из страниц, минуя SQL.

## Типы страниц и overflow

Страницы бывают: **leaf** (данные), **interior** (узлы дерева), **overflow** (продолжение больших записей). Большое значение не влезает в страницу — тогда часть хранится на overflow-странице, а в ячейке остаётся указатель. Для восстановления это важно: удалённая запись может целиком лежать в overflow, и её нужно собирать из нескольких страниц.

## Чтение WAL

Если рядом есть `-wal`, в нём — свежие страницы, ещё не перенесённые в основную базу. Формат WAL: заголовок (магия, размер страницы, salt), затем кадры «номер страницы + данные». Применяя кадры по порядку, получаешь актуальное состояние. Иногда именно в WAL лежит запись, которой уже нет в основной базе — это частая CTF-деталь.

## Инструменты и сравнение

`.recover` — встроенный и самый простой; идёт по B-tree и freelist. `undark` — вытаскивает удалённое из freelist более агрессивно. `sqlite-forensics` — page-level утилиты. `strings`/`xxd` — грубо, но всегда под рукой. Порядок действий: сначала `.recover`, если мало — undark, если и это не помогло — ручной разбор страниц.

## Где лежат базы в реальных системах

SQLite повсюду: браузеры (история, cookies), мобильные приложения (настройки, кэш), мессенджеры (локальные копии чатов), desktop-приложения. Поэтому анализ SQLite — не только CTF, а базовый навык в форензике мобильных устройств и реагировании на инциденты.

## Что делать с повреждённой базой

Если база повреждена (битый заголовок, оборванные страницы), SQLite откажется открывать её. Тогда работают page-level: сканируют файл на сигнатуры записей, собирают строки по эвристикам, применяют `sqlite3 .recover` с флагом игнорирования ошибок. Иногда помогает копирование только валидных страниц в новую базу.

## Пример: восстановление чата мессенджера

Мобильный мессенджер хранит сообщения в SQLite. Удалённое сообщение остаётся в freelist или WAL. Сценарий: `.recover` даёт таблицу `messages`, где есть строка, которой нет в интерфейсе. Сопоставив её с полем `timestamp`, восстанавливаешь контекст переписки. Это классическая задача форензики мобильных устройств, и она решается теми же командами, что разбирали.

## Тонкости varint в записях

Внутри record-формата SQLite целые кодируются **varint** (как в Protobuf): старший бит — флаг продолжения. Разбирая запись вручную, сначала читаешь длину заголовка, затем типы столбцов, затем значения. Ошибка на один байт сдвигает всё, поэтому удобно писать парсер и сверять его с `.dump`. Понимание varint связывает этот урок с `misc-protobuf`.

## Анти-форензика

Продвинутые приложения противодействуют восстановлению: вызывают `VACUUM` после удаления, перезаписывают свободные страницы нулями, шифруют базу (SQLCipher). Признаки шифрования — высокая энтропия и отсутствие магии `SQLite format 3`. Тогда нужен ключ (из памяти процесса, из конфига) — а это уже другая ветка анализа.

## Шпаргалка

`sqlite3 db ".recover" | sqlite3 rec.db`; `sqlite3 db ".dump"`; `sqlite3 db "pragma freelist_count;"`; `sqlite3 db "pragma page_size;"`; `strings -a db | grep -i nto`; `python3 -m undark db`. Проверь также `-wal` и `-journal` — часто именно там свежие данные.

## Разбор record-формата на примере

Возьмём ячейку и разберём её вручную. После заголовка страницы идёт массив указателей; указатель ведёт на ячейку. В ячейке leaf-страницы: varint длины payload, varint rowid, затем запись. Запись начинается с varint длины заголовка, потом идут serial-типы каждого столбца (1 = 8-битное целое, 2 = 16-битное, и так далее), затем значения. Прочитав типы, ты знаешь, сколько байт занимает каждое значение, и можешь собрать строку целиком. Этот разбор — ядро восстановления, когда `.recover` не справляется.

## Почему freelist важен именно для удалённого

Когда строка удаляется, SQLite может освободить всю страницу или только ячейку. Если страница целиком ушла в freelist, её байты не трогаются до переиспользования — там лежат все прежние записи. Если освобождена лишь ячейка, свободное место помечается в заголовке страницы, но сами байты остаются. В обоих случаях `strings` и page-разбор находят удалённое. Отсюда правило: не делай `VACUUM` и не пиши в базу, если хочешь сохранить удалённое.

## Сравнение с восстановлением в других СУБД

В PostgreSQL удалённые строки остаются в «мёртвых» кортежах до `VACUUM`; в MySQL InnoDB — в undo-логах и свободных страницах. Принцип общий: СУБД оптимизированы и не перезаписывают данные сразу. SQLite проще всех: один файл, понятные страницы. Освоив его, легче читать и другие СУБД.

## Итог

SQLite-форензика держится на трёх фактах: удаление не стирает байты; freelist и WAL хранят прошлое; страницы разбираются вручную. `.recover` решает большинство задач, но понимание структуры нужно, когда он бессилен. Это базовый навык, потому что SQLite лежит почти везде.
