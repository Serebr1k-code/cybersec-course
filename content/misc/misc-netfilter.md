## Вопрос, с которого всё начинается

Ты запускаешь сервис, а соединение снаружи не устанавливается, хотя приложение слушает порт и локально всё работает. Пакет доходит до машины, но дальше не проходит. Кто-то его отбрасывает — и почти всегда это **netfilter**, встроенный в ядро firewall.

## Наш пример: список правил

Посмотрим правила:

```
$ nft list ruleset
table inet filter {
	chain input {
		type filter hook input priority 0; policy drop;
		tcp dport { 22, 80, 443 } accept
		iif "lo" accept
		ct state established,related accept
	}
}
```

Читаем: таблица `inet filter`, цепочка `input`, политика по умолчанию — `drop` (отбросить всё). Разрешены порты 22, 80, 443, петлевой интерфейс и уже установленные соединения. Всё остальное — мимо. Разберём, как это устроено.

## Шаг 1: что такое netfilter

**Netfilter** — подсистема ядра, через которую проходят все сетевые пакеты. В определённых точках стека ядро вызывает обработчики, которые могут пакет принять, отбросить или изменить. На netfilter построены firewall, NAT и балансировка. Правила задаются утилитами `iptables`/`nft`.

## Шаг 2: пять точек (hooks)

Пакет проходит фиксированные точки:

- **prerouting** — сразу после прихода, до решения о маршруте (здесь часто делают DNAT);
- **input** — для пакетов, адресованных самой машине;
- **forward** — для транзитных пакетов (машина как роутер);
- **output** — для исходящих от машины;
- **postrouting** — перед отправкой (здесь делают SNAT/masquerade).

Поняв, в какой точке смотреть, ты поймёшь, почему пакет не доходит: например, отброшен в `forward`, а не в `input`.

## Шаг 3: таблицы, цепочки, правила

Иерархия: **таблица** → **цепочка** → **правила**. Таблица — набор цепочек для семейства адресов (`ip`, `ip6`, `inet` — сразу оба). Цепочка привязана к hook и имеет политику по умолчанию. Правила проверяются по порядку; первое подходящее решает судьбу пакета. Если ни одно не подошло — действует политика цепочки.

## Шаг 4: nftables против iptables

`iptables` — старый интерфейс (несколько таблиц с разными наборами цепочек). `nftables` — новый: единый синтаксис, одна таблица, лучше производительность, поддержка множеств и карт. Ядро одно (netfilter), но интерфейс разный. В задачах встречаются оба; важно уметь читать `nft list ruleset` и `iptables -S`.

## Шаг 5: сопоставления

Правило состоит из сопоставления и действия. Сопоставлять можно:

- адрес и порт (`ip saddr`, `tcp dport`);
- интерфейс (`iif`, `oif`);
- состояние соединения (`ct state`);
- заголовки протоколов, метки пакетов.

Действия: `accept`, `drop`, `reject` (с ответом), `jump`/`goto` (перейти в другую цепочку), `dnat`/`snat`/`masquerade`.

## Шаг 6: conntrack

**conntrack** — отслеживание соединений. Netfilter помнит таблицу установленных соединений и позволяет правилу `ct state established,related accept` пропускать ответные пакеты, не описывая их отдельно. Именно поэтому в нашем примере ответы на разрешённые соединения проходят, хотя входящих правил для них нет. Без понимания conntrack правила кажутся магией.

## Шаг 7: NAT

NAT меняет адреса. **SNAT/masquerade** подменяет источник (чтобы ответы вернулись на роутер) — обычно в `postrouting`. **DNAT** подменяет назначение (проброс порта на внутренний сервер) — обычно в `prerouting`. Отсюда типичная задача: снаружи порт открыт, а внутри сервис на другом порту — смотри DNAT.

## Шаг 8: как читать правила

Порядок разбора:

1. Найди цепочку для нужной точки (`input`/`forward`).
2. Посмотри политику по умолчанию — она решает судьбу «прочего».
3. Просмотри правила сверху вниз — первое подходящее побеждает.
4. Проверь conntrack-правила — они могут «пропускать» ответы.
5. Ищи NAT в `prerouting`/`postrouting`.

Так гипотеза «пакет отброшен» превращается в конкретное правило.

## Шаг 9: обход фильтрации

Фильтр по адресу и порту обходится разными способами:

- **фрагментация** — разбить пакет так, чтобы заголовки не совпали с правилом (современные ядра собирают фрагменты до фильтрации, но старые конфигурации уязвимы);
- **туннелирование** — спрятать трафик внутри разрешённого протокола (DNS, ICMP);
- **исходная маршрутизация** и подмена адреса;
- **raw-сокеты** и ручная сборка пакетов в обход обычного стека.

В задачах это значит: правило «запретить порт» не гарантирует, что до порта нельзя добраться.

## Шаг 10: netfilter в контейнерах

Docker и Kubernetes активно используют netfilter: проброс портов, изоляция сетей, балансировка. Отсюда — множество правил в цепочках `DOCKER`, `KUBE-*`. Если контейнер «не видит» сеть, причина часто в этих цепочках, а не в приложении. При аудите смотрят, нет ли слишком широких правил `accept`.

## Шаг 11: правила как подсказка в CTF

Список правил — источник информации о системе: какие порты открыты наружу, куда идёт проброс, какие сети разрешены. Иногда флаг достаётся не «взломом», а чтением конфигурации firewall. Умение читать `nft list ruleset` и `iptables -S` — базовый навык сетевой задачи.

## Шаг 12: приоритеты и несколько цепочек

У hook есть приоритет: несколько цепочек могут висеть на одной точке, и выполняются они по возрастанию приоритета. Поэтому порядок может быть неочевиден. Если правила противоречат друг другу, смотри приоритеты цепочек и порядок внутри каждой.

## Полный разбор примера

Вернёмся к нашему правилу и разберём, что произойдёт с входящим пакетом на порт 8080:

```
table inet filter {
	chain input { type filter hook input priority 0; policy drop;
		tcp dport { 22, 80, 443 } accept
		iif "lo" accept
		ct state established,related accept }
}
```

Пакет приходит, попадает в hook `input`. Цепочка проверяет правила по порядку: порт 8080 не входит в множество `{22,80,443}` — не подходит; интерфейс не `lo` — не подходит; это новый пакет, а не established — не подходит. Ни одно правило не сработало, значит применяется политика цепочки — `drop`. Пакет отброшен без ответа. Теперь «почему не работает» имеет точный ответ.

## Логирование пакетов

Чтобы увидеть, что реально происходит, в цепочку добавляют правило с действием `log`:

```
nft add rule inet filter input tcp dport 8080 log prefix "drop8080 "
```

Теперь каждый отброшенный пакет оставляет запись в журнале ядра. Это стандартный приём диагностики: сначала логировать, потом ужесточать. В задачах наличие таких записей подсказывает, какие порты пробовали.

## Множества и карты в nftables

nftables умеет **множества** (`{ 22, 80, 443 }`) и **карты** (сопоставление ключа значению). Это позволяет одним правилом описать десятки портов или адресов. Например, карта может сопоставлять входящий порт целевому серверу для DNAT. При чтении правил обращай внимание на множества: они компактны, но скрывают много значений.

## Маршрутизация и метки

Netfilter может помечать пакеты (`meta mark set`) и использовать метки в правилах маршрутизации — так строят policy-based routing. Это ещё один слой, который легко пропустить: пакет может быть принят фильтром, но отправлен «не туда» маршрутом. Если соединение устанавливается, но данные идут странным путём, смотри метки и таблицы маршрутизации.

## Почему netfilter так важен

Через netfilter проходит каждый пакет, поэтому именно он определяет, что вообще достижимо в сети. Firewall, NAT, балансировка, изоляция контейнеров — всё это netfilter. Поняв его, ты перестаёшь угадывать, «почему не коннектится», и начинаешь читать конфигурацию как карту доступных путей.

## Почему правила пишут по-разному

В одном проекте ты встретишь `iptables -S`, в другом — `nft list ruleset`, в третьем — правила, которые генерирует Docker. Синтаксис разный, но модель одна: точки, цепочки, сопоставления, действия, conntrack. Как только ты держишь в голове эту модель, любой формат читается одинаково — меняются только слова. Это и есть цель урока: не заучить флаги, а понимать устройство.

## Итог

netfilter — это конвейер из точек в сетевом стеке, а nftables — язык описания правил. Умение читать правила сверху вниз, учитывать политику и conntrack и искать NAT — базовый навык разбора сетевых задач и аудита firewall.

## Как проверить гипотезу

Быстрый способ понять, виноват ли netfilter: временно добавить правило с действием `log` перед политикой и посмотреть журнал. Если пакет появляется в логе и дальше отбрасывается — дело в правилах цепочки; если не появляется вовсе — пакет не доходит до этой точки (проблема выше: маршрут, интерфейс, NAT). Так ты за один шаг сужаешь поиск до конкретной точки конвейера.

## Частые ошибки разбора

- смотреть только `input`, забыв про `forward` (транзитный трафик);
- игнорировать политику цепочки — а именно она решает судьбу «прочего»;
- не учитывать conntrack и удивляться, почему ответы проходят;
- путать `reject` (с ответом) и `drop` (молча) — при `drop` клиент висит в таймауте;
- не проверить NAT в `prerouting`/`postrouting`.

Каждый пункт — реальная причина «пакет не туда идёт» в задачах и на практике.

## Что мы теперь знаем

- netfilter — подсистема ядра, обрабатывающая все пакеты.
- Точки: prerouting, input, forward, output, postrouting.
- Иерархия: таблица → цепочка → правило; политика решает «прочее».
- conntrack пропускает ответы; NAT меняет адреса.
- Фильтр можно обойти фрагментацией, туннелями и raw-сокетами.
