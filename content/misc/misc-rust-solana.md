## Вопрос, с которого всё начинается

В Solana нет «контрактов, хранящих состояние». Есть **программы** (stateless-код) и **аккаунты** (состояние). Программе явно передают список аккаунтов, и она читает/пишет их. Это необычно: если передать не тот аккаунт — программа может изменить чужие данные. Отсюда целый класс багов — **account confusion**.

## Наш пример: программа перевода

```rust
#[derive(Accounts)]
pub struct Transfer<'info> {
    #[account(mut)]
    pub from: Account<'info, TokenAccount>,
    #[account(mut)]
    pub to: Account<'info, TokenAccount>,
    pub authority: Signer<'info>,
}

pub fn transfer(ctx: Context<Transfer>, amount: u64) -> Result<()> {
    let from = &mut ctx.accounts.from;
    let to = &mut ctx.accounts.to;
    from.amount -= amount;
    to.amount += amount;
    Ok(())
}
```

Читается как обычный перевод. Разберём, чего здесь не хватает.

## Шаг 1: аккаунты — это вход, а не «поля объекта»

`Context<Transfer>` — набор аккаунтов, переданных транзакцией. `#[account(mut)]` говорит, что аккаунт будет изменён. Ключевой момент: программа **не проверяет**, что `from` действительно принадлежит `authority`. Если проверки нет, любой подпишет транзакцию и спишет с чужого `from`, лишь бы тот передал свой аккаунт.

Правильно — `has_one = authority` или `constraint = from.owner == authority.key()`:

```rust
#[account(mut, has_one = authority)]
pub from: Account<'info, TokenAccount>,
```

## Шаг 2: PDA и подписывание

PDA (Program Derived Address) — адрес, выведенный из seeds и program id. Программа может «подписывать» за PDA через `seeds`/`bump`. Баг — не проверять seeds:

```rust
#[account(mut, seeds = [b"vault"], bump)]
pub vault: Account<'info, Vault>,
```

Если seeds слишком общие (например, только `b"vault"` без адреса пользователя), все пользователи разделяют один vault. Нужно включать уникальный ключ (например, `user.key().as_ref()`):

```rust
#[account(mut, seeds = [b"vault", user.key().as_ref()], bump)]
pub vault: Account<'info, Vault>,
```

## Шаг 3: account confusion

Самая известная ошибка: программа принимает два аккаунта одного типа, но не проверяет, что это **разные** аккаунты. Атакующий передаёт один и тот же аккаунт дважды:

```rust
// from == to -> перевод сам в себя, но с побочным эффектом
```

В более сложных случаях подменяют `to` на аккаунт атакующего. Защита — проверки `constraint` и явная сверка ключей:

```rust
#[account(mut, constraint = from.key() != to.key())]
pub to: Account<'info, TokenAccount>,
```

## Шаг 4: missing signer check

`Signer<'info>` гарантирует подпись. Но если поле объявлено просто как `AccountInfo` без `Signer`, проверки подписи нет. Классический баг — «админ» объявлен как `UncheckedAccount`, и любой может вызвать привилегированную функцию.

```
error: AccountNotSigner
```

Так выглядит ошибка, когда проверка есть. Когда её нет — ошибки не будет, а будет эксплойт.

## Шаг 5: Anchor-аннотации как защита

Anchor (`#[derive(Accounts)]`) автоматически проверяет многое: владельца, дискриминатор, seeds, signer. Но только если вы их указали. `UncheckedAccount` отключает проверки — используйте его осознанно.

| Аннотация | Что проверяет |
|---|---|
| `mut` | аккаунт будет изменён |
| `has_one = X` | поле X равно ключу аккаунта |
| `constraint = EXPR` | произвольное условие |
| `seeds`/`bump` | PDA выведен правильно |
| `Signer` | есть подпись |
| `owner = prog` | владелец аккаунта |

## Шаг 6: остаток аккаунта и close

Ещё один класс багов — «воскрешение» закрытого аккаунта. Когда аккаунт закрывают через `close`, он должен быть помечен; если этого не сделать, атакующий может повторно использовать его в той же транзакции. Anchor делает это через `#[account(mut, close = destination)]`, но при ручной работе легко забыть.

## Полный прогон: подмена получателя

Задача: программа переводит токены с `from` на `to`, но не сверяет `to.owner` с отправителем. Атакующий подставляет свой аккаунт как `to`.

```
$ solana program invoke transfer --from victim --to attacker
flag: nto{s0l4n4_4cc0unt_c0nfus10n}
```

Программа выполнила ровно то, что в коде. Эксплойт — в отсутствии проверки, которую Anchor мог бы сделать за вас, если бы её попросили.

## Если не сработало

Если `has_one` и `constraint` стоят, ищите более тонкие вещи: PDA с недостаточно специфичными seeds, отсутствие `close`-проверки, или `remaining_accounts`, которые Anchor не валидирует. Часто дыра — в динамически переданных аккаунтах.

## Что мы теперь знаем

- Solana-программа stateless: состояние — в аккаунтах.
- Аккаунты передаются явно, их нужно проверять.
- `has_one`/`constraint` — ключевые защиты Anchor.
- PDA seeds должны быть уникальными на пользователя.
- `Signer` и `UncheckedAccount` — граница между безопасностью и дырой.
- Закрытый аккаунт нужно помечать, иначе возможно «воскрешение».

## Как читать Solana-программу

Смотрите на структуру `Accounts`: у каждого поля — есть ли `mut`, `has_one`, `constraint`, `seeds`. Затем — на проверки в теле: сверяется ли `authority` с владельцем. Почти все эксплойты Solana — это не хватает одной аннотации.

## Сравнение с EVM: почему аккаунты — это вход

В EVM состояние контракта «принадлежит» контракту: `mapping` живёт по адресу контракта, и обратиться к чужому состоянию нельзя. В Solana всё иначе: состояние живёт в отдельных аккаунтах, и программа не «владеет» ими. Ей просто передают список аккаунтов в транзакции, и она читает/пишет то, что ей передали. Отсюда фундаментальное следствие: **корректность программы зависит от корректности переданных аккаунтов**, а их проверка — целиком на разработчике.

Именно поэтому Anchor (`#[derive(Accounts)]`) так популярен: он генерирует проверки декларативно. Но проверяет он только то, что вы объявили. `UncheckedAccount` и `AccountInfo` — это «я сам проверю», и там живут дыры.

## Разбор второго примера: shared vault без уникальных seeds

```rust
#[derive(Accounts)]
pub struct Deposit<'info> {
    #[account(mut, seeds = [b"vault"], bump)]
    pub vault: Account<'info, Vault>,
    #[account(mut)]
    pub user: Signer<'info>,
    pub system_program: Program<'info, System>,
}

pub fn deposit(ctx: Context<Deposit>, amount: u64) -> Result<()> {
    let vault = &mut ctx.accounts.vault;
    vault.balance += amount;
    Ok(())
}
```

Seeds здесь — только `b"vault"`, без адреса пользователя. Значит, PDA один на всю программу, и все пользователи депозитят в один общий vault. Если логика вывода потом проверяет «сколько положил я», но хранит только общий баланс, — учёт ломается. Правильно — включить `user.key().as_ref()` в seeds, чтобы у каждого был свой vault.

## Частые вопросы новичков

Почему у аккаунта есть «дискриминатор»? Anchor добавляет к каждому аккаунту 8-байтовый префикс типа, чтобы нельзя было подсунуть аккаунт другого типа. Почему `Signer` важен? Потому что без него программа не знает, что владелец аккаунта действительно дал согласие на операцию. Что такое `remaining_accounts`? Это аккаунты, переданные сверх объявленных в структуре; Anchor их не проверяет, и там легко спрятать подмену.

## Практика без лаборатории

Разверните `solana-test-validator` и `anchor test`. Напишите программу с `#[account(mut)] pub to: Account<'info, TokenAccount>` без `has_one`, затем вызовите её с чужим `from`. Убедитесь, что перевод проходит. Добавьте `has_one = authority` и повторите — теперь Anchor отклонит транзакцию. Это самый быстрый способ прочувствовать, что в Solana безопасность — это список явных проверок, а не свойства языка.

## Итог по модели угроз

Solana-программа — это функция, которая получает аккаунты и меняет их. У неё нет «своего» состояния, которое она могла бы защитить языковыми средствами. Значит, вся безопасность — в проверках, которые вы объявили в структуре `Accounts` и в теле функции. Anchor превращает эти проверки в декларативные аннотации, но не добавляет ничего «сверх»: нет `has_one` — нет проверки владельца, нет `constraint` — нет сверки ключей, нет `Signer` — нет требования подписи. Запомните порядок аудита: сначала структура `Accounts` (все аннотации), затем тело функции (все проверки и переходы), затем динамические аккаунты (`remaining_accounts`). Девять из десяти эксплойтов Solana находятся на первом шаге.

## Разбор программы по шагам

Чек-лист аудита Solana-программы. Шаг первый: выпишите структуру `Accounts` для каждой инструкции и отметьте, у каких полей стоят `mut`, `has_one`, `constraint`, `seeds`, `Signer`, `owner`. Шаг второй: для каждого «чувствительного» аккаунта (тот, что держит деньги или права) проверьте, есть ли связь с подписантом. Шаг третий: посмотрите, не могут ли два поля быть одним и тем же аккаунтом (account confusion). Шаг четвёртый: проверьте seeds PDA — уникальны ли они на пользователя. Шаг пятый: посмотрите на `close` и убедитесь, что закрытый аккаунт помечается. Шаг шестой: проверьте, нет ли `remaining_accounts`, которые обходят валидацию. Семь из десяти эксплойтов Solana ловятся на первых двух шагах; остальные три — на оставшихся. Держите этот список под рукой при чтении любой программы на Anchor.

## Почему это важно именно для DeFi на Solana

Большая часть денег в Solana-DeFi лежит в аккаунтах, которые программы меняют по инструкции. Ошибка в одной аннотации `#[account(...)]` означает, что чужие средства можно перевести себе, просто передав не тот аккаунт. Именно так происходили крупнейшие инциденты: программа работала «как написано», но написанное не содержало проверки. Поэтому аудит Solana — это в первую очередь чтение структуры `Accounts`, а не дизассемблирование байткода.
