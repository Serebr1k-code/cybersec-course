## Вопрос, с которого всё начинается

Ты читаешь из файла 4 байта: `01 00 00 00`. Ожидаешь число 1, а получаешь 1 — ок. Но в другом файле те же байты означают 16777216. Почему? Из-за **порядка байтов**. Разберём, как машина раскладывает число на байты.

## Наш пример

Возьмём 32-битное число `0x12345678`. В памяти оно может лежать двумя способами:

```
little-endian: 78 56 34 12
big-endian:    12 34 56 78
```

Первым идёт либо младший байт (little), либо старший (big). Оба варианта правильны — это соглашение.

## Шаг 1: что такое endianness

**Endianness** — порядок байтов многобайтового числа в памяти. **Little-endian** (младший первым) — x86, большинство ARM по умолчанию. **Big-endian** (старший первым) — сетевой порядок (network byte order), некоторые RISC и старые платформы. Одно число — две раскладки.

## Шаг 2: почему это важно

Если ты читаешь байты как есть, а файл записан в другом порядке, число «перевернётся». `01 00 00 00` как little-endian = 1, как big-endian = 16777216. Отсюда баги в парсерах и «магические» значения, которые не сходятся.

## Шаг 3: сетевой порядок

В TCP/IP договорились: числа в заголовках — big-endian. Поэтому функции `htons`/`htonl` (host-to-network short/long) меняют порядок перед отправкой, а `ntohs`/`ntohl` — после приёма. Игнорирование этого даёт неверно прочитанные порты и длины.

## Шаг 4: как увидеть

Hex-дамп покажет байты как есть:

```
$ printf '\x01\x00\x00\x00' | xxd
00000000: 0100 0000                                ....
```

Читая дамп, всегда помни: байты идут в порядке записи, а число зависит от интерпретации. Python-структуры (`struct`) явно указывают порядок: `<I` (little), `>I` (big).

## Шаг 5: где встречается

- Бинарные форматы (ELF, PE, PNG) — обычно little-endian.
- Сетевые протоколы — big-endian.
- Сериализация (protobuf, msgpack) — big-endian для многобайтовых.
- Файлы, созданные на разных платформах.
- CTF: «прочитай число из файла» с подвохом на порядок.

## Шаг 6: как конвертировать

В Python: `int.from_bytes(b, 'little')` / `'big'`. В C: `ntohs`/`htons`. В шелле: `xxd -e` (little) против `xxd` (порядок). Вручную: переставить байты (`b[::-1]`).

## Шаг 7: BOM и маркеры

Порядок байтов проявляется и в тексте: **BOM** (Byte Order Mark) в UTF-16 — это `FE FF` (big) или `FF FE` (little). Маркер говорит, как читать остальные байты. Пропустить его — получить «кракозябры» или сдвинутый текст.

## Шаг 8: практический чек-лист

- Какой платформой создан файл?
- Какой порядок у формата (спека)?
- Читаешь ли ты число через явную конвертацию?
- Есть ли BOM/магия, задающие порядок?

## Частые ошибки

- Читать многобайтовое число без указания порядка.
- Забывать про network byte order в протоколах.
- Путать `xxd` (big-вид) и `xxd -e` (little).
- Игнорировать BOM.

## Разбор кейса: читаем поле из бинарного файла

Пусть в файле лежит заголовок: 4 байта magic, 4 байта длины, 4 байта смещения. Прочитаем их правильно.

```python
import struct
data = open('file.bin', 'rb').read(12)
magic = data[:4]                       # байты как есть, порядок не важен
length, offset = struct.unpack('<II', data[4:12])   # little-endian
print(hex(length), hex(offset))
```

`<` означает little-endian, `>` — big-endian. Если не указать порядок явно, `struct` по умолчанию использует **нативный** порядок машины (`@`), и парсер «сработает у тебя, но не у меня». Именно поэтому во всех форматах порядок прописан в спецификации. Проверим разницу:

```python
>>> struct.unpack('<I', b'\x01\x00\x00\x00')[0]
1
>>> struct.unpack('>I', b'\x01\x00\x00\x00')[0]
16777216
```

Одни и те же байты — два разных числа. Если твой парсер выдаёт «магические» значения вида `0x00000001` вместо `0x01000000`, ты читаешь не тем порядком.

## Таблица: где какой порядок байтов

| Контекст | Порядок | Как задаётся |
|---|---|---|
| x86/x86-64, большинство ARM | little | аппаратный по умолчанию |
| Сетевые протоколы (TCP/IP) | big (network order) | `htons`/`htonl` |
| ELF | по байту `e_ident[EI_DATA]` | обычно little |
| PNG (длины чанков) | big | спецификация PNG |
| BMP, GIF (некоторые поля) | little | спецификация |
| protobuf, msgpack | little (protobuf) / big (msgpack) | спецификация |
| UTF-16 текст | по BOM | `FE FF` / `FF FE` |
| Java `DataOutputStream` | big | `writeInt` |
| Rust `to_le_bytes`/`to_be_bytes` | явно | API |

Вывод: «порядок байтов» — это не свойство числа, а свойство формата. Одно и то же число разные форматы пишут по-разному.

## struct в Python: форматы и примеры

`struct` — основной инструмент разбора бинарных данных. Основные коды: `b`/`B` (1 байт), `h`/`H` (2 байта), `i`/`I` (4), `q`/`Q` (8), `f`/`d` (float/double), `s` (строка байт). Префиксы порядка: `<` little, `>` big, `=` нативный стандартный размер, `!` сетевой (big).

```python
>>> struct.pack('<H', 0x1234)
b'4\x12'
>>> struct.pack('>H', 0x1234)
b'\x124'
>>> struct.unpack('<h', b'\xff\xff')[0]
-1                              # знаковое: 0xffff = -1
>>> struct.unpack('<H', b'\xff\xff')[0]
65535                           # беззнаковое: 0xffff = 65535
```

Обрати внимание на знаковость: те же байты как `h` дают `-1`, как `H` — `65535`. При разборе длины из файла это критично: отрицательная «длина» из знакового чтения часто и есть вход в уязвимость.

## BOM на практике

BOM (Byte Order Mark) — первые байты текстового файла, сообщающие порядок. В UTF-16 это `FE FF` (big-endian) или `FF FE` (little-endian); в UTF-8 BOM — `EF BB BF` (порядок не важен, но маркер иногда мешает парсерам). Если пропустить BOM, получишь «сдвинутый» текст или «кракозябры».

```bash
$ file text.txt
text.txt: Unicode text, UTF-16, little-endian text, with BOM
$ xxd text.txt | head -1
00000000: fffe 4800 6500 ...        # FF FE = UTF-16 LE
```

## Если не сработало

- **Число «перевёрнуто».** Поменяй `<` на `>` (или наоборот) и перечитай; сверься со спецификацией формата.
- **Парсер работает на одной машине и падает на другой.** Ты использовал нативный порядок (`@` или без префикса). Задай порядок явно.
- **`xxd` и `xxd -e` дают разный вид.** `xxd` печатает байты в порядке файла, `xxd -e` — как little-endian группы. Помни, какой смотришь.
- **Строка читается со сдвигом на байт.** Вероятно, не учтён BOM или выравнивание (padding) между полями.
- **Float читается мусором.** Проверь и порядок, и размер: `f` (4 байта) против `d` (8), а также `struct` требует байтового выравнивания для нативных форматов.

## Ещё: битовые поля и выравнивание

Порядок байтов — не единственная ловушка бинарного разбора. Компиляторы выравнивают структуры (padding), и «логическая» раскладка полей не совпадает с байтовой. Если в C есть `struct { uint8_t a; uint32_t b; }`, между `a` и `b` окажется три байта padding, чтобы `b` был выровнен по 4. При чтении такого файла в Python нужно учитывать эти пропуски, иначе поля «съезжают». Порядок битов внутри байта — отдельная тема: битовые поля (`bitfield`) в C упаковываются по-разному в зависимости от компилятора и порядка байтов, поэтому для сетевых протоколов биты задают явно, а не через `struct`. Хорошая практика при разборе незнакомого формата — сначала сверить размеры полей и выравнивание по спецификации, а потом уже читать числа.

## Итоговый чек-лист

- Порядок байтов — свойство формата, а не числа; смотри спецификацию.
- В Python задавай порядок явно: `<` little, `>` big, `!` сетевой.
- Знаковость меняет результат: `h` vs `H` на тех же байтах.
- `xxd` печатает в порядке файла, `xxd -e` — little-endian группами.
- Сетевые протоколы — big-endian; x86/ARM — little.
- Не забывай BOM (`FE FF` / `FF FE`) и padding между полями.
- Если число «перевёрнуто» — поменяй порядок и сверься со спецификацией.

## Кратко: что запомнить

Порядок байтов задаётся форматом, а не числом: x86/ARM и большинство бинарных форматов — little, сеть и PNG — big. В Python всегда указывай порядок явно (`<`/`>`/`!`). Знаковость и выравнивание меняют результат так же сильно, как порядок. Если число «перевёрнуто» или парсер работает на одной машине и не работает на другой — почти всегда виноват неявный нативный порядок.

## Практика: быстрый разбор hex-дампа

Частая задача — из дампа вытащить число. Разберём на примере: в дампе `78 56 34 12`. Прочитаем его двумя способами.

```python
>>> b = bytes.fromhex('78563412')
>>> hex(int.from_bytes(b, 'little'))
'0x12345678'
>>> hex(int.from_bytes(b, 'big'))
'0x78563412'
```

Если в спецификации сказано «little-endian uint32», ответ — `0x12345678`; если «big-endian» — `0x78563412`. Именно поэтому первым делом при разборе незнакомого формата смотрят спецификацию, а не гадают. Второй полезный приём — определить порядок по «магии» файла: если первые байты должны быть `7f 45 4c 46` (ELF), а в дампе `46 4c 45 7f`, значит байты переставлены целиком (редкий случай), а не только числа. Третий — не забыть про выравнивание: между полями структуры могут быть байты-заполнители, которых нет в «логическом» описании. Для сложных форматов удобнее библиотека с описанием структуры (`construct`, `kaitai`), где порядок и выравнивание заданы явно и читаемо, чем россыпь `struct.unpack`.

## Что мы теперь знаем

- Endianness — порядок байтов числа в памяти.
- Little-endian: младший первым; big-endian: старший первым.
- Сеть использует big-endian (network byte order).
- Конвертация: `struct`, `int.from_bytes`, `hton*`/`ntoh*`.
- BOM в UTF-16 задаёт порядок текста.
