## Вопрос, с которого всё начинается

Тебе дали веб-сервис. Он выдаёт токен так:

```
token = md5('секретный_префикс' + 'user=guest')
```

Сервер принимает токен обратно, пересчитывает хеш и, если совпало, пускает тебя. Ты не знаешь секрет, но тебе нужно получить права `admin`. Наивный ответ — «нельзя, ведь хеш необратим». И он неверный: схема ломается **без** знания секрета. Разберём почему.

## Наш пример: сервер с MD5-«подписью»

Смотрим на серверный код:

```
$ cat verify.py
import hashlib
SECRET = open('secret.txt','rb').read()
def sign(user):
    return hashlib.md5(SECRET + ('user=' + user).encode()).hexdigest()
def check(user, token):
    return sign(user) == token
```

Сервер доверяет данным только потому, что может пересчитать хеш. Секрет приклеен **слева**. Это и есть корень проблемы.

## Шаг 1: что такое MAC и зачем он тут

**MAC** (Message Authentication Code) — короткое значение, доказывающее, что данные пришли от владельца секрета и не менялись. Правильный MAC — это HMAC. Здесь же вместо HMAC взяли «хеш от секрета и данных» — распространённая самоделка. Она кажется рабочей, но ломается.

## Шаг 2: как хешируют длинное сообщение

MD5 и SHA-1 устроены по схеме **Меркла–Дамгора**: сообщение режут на блоки по 64 байта и «прогоняют» через сжимающую функцию. Состояние после каждого блока становится входом для следующего. В конце добавляют **паддинг** — байт `0x80`, нули и длину сообщения (в битах), чтобы вышло кратно блоку.

Важное следствие: **хеш зависит только от итогового состояния**. Если мы знаем состояние после `SECRET + 'user=guest'`, мы можем продолжить хеширование с любого места — как будто начали с этого состояния. Знание секрета для этого не нужно.

## Шаг 3: почему это ломает схему

Хеш `md5(SECRET + 'user=guest')` — это ровно состояние после обработки первых блоков. Мы можем дописать свои данные и пересчитать хеш от этого состояния. Получится подпись для сообщения:

```
SECRET + 'user=guest' + ПАДДИНГ + '&user=admin'
```

Сервер увидит в конце `user=admin` и пустит нас. Нам нужно лишь знать **длину** секрета, чтобы построить правильный паддинг.

## Шаг 4: паддинг в деталях

Паддинг для сообщения длиной `L` байт: `0x80`, затем нули, затем 8 байт длины `L*8` (для MD5). Например, если `len(SECRET + data) = 14`, добиваем до 56 байт и пишем длину `112` в 8 байт. В шестнадцатеричном виде это `\x80` и нули.

Мы не знаем секрет, но перебираем его длину (обычно 8–32). Для каждой длины строим свой паддинг и проверяем — одна из них даст верную подпись.

## Шаг 5: собираем подделку вручную

Ключевая операция — **продолжить MD5 от заданного состояния**. В Python это делают, задавая `h` (состояние) и подсовывая хвост:

```
$ python3
>>> import struct
>>> known = '5f4dcc3b5aa765d61d8327deb882cf99'  # чужой токен
>>> h = [int(known[i:i+8],16) for i in range(0,32,8)]
>>> h = [x for x in h]  # 4 слова состояния
```

Затем реализуем функцию `md5_continue(state, extra)` — сжимаем только `extra` с начальным состоянием `state` и учитываем «уже съеденную» длину. Это 40 строк кода; ниже — через готовый инструмент.

## Шаг 6: готовый инструмент

Ручной код нужен для понимания, но в CTF используют `hash_extender` (или `hashpump`):

```
$ hash_extender --data 'user=guest' --secret 14 \
    --append '&user=admin' --format md5 \
    --signature 5f4dcc3b5aa765d61d8327deb882cf99
New signature: 9c1f...   # новая подпись
New string   : 7573...   # новые данные (с паддингом)
```

`--secret 14` — предполагаемая длина секрета. Инструмент перебирает: дай ему диапазон, и один вариант сработает.

## Полный прогон от начала до конца

```
$ curl -s 'http://vault.ctf/?user=guest'
token=5f4dcc3b5aa765d61d8327deb882cf99
$ hash_extender --data 'user=guest' --secret 14 \
    --append '&user=admin' --format md5 --signature 5f4dcc3b5aa765d61d8327deb882cf99
New signature: 9c1f0d2a...
$ curl -s 'http://vault.ctf/?user=guest<паддинг>&user=admin&token=9c1f0d2a...'
Welcome, admin! nto{l3ng4h_3xt3ns10n_4nd_md5}
```

Флаг получен без знания секрета.

## Если не сработало

- Длина секрета неизвестна — перебери 1–64.
- Алгоритм SHA-1/SHA-256 — поменяй `--format`.
- Сервер использует HMAC — эта атака не работает, HMAC устроен иначе.
- Данные URL-кодируются — паддинг тоже придётся кодировать (`%80%00...`).

## Что мы теперь знаем

- `H(secret + data)` — не MAC; правильный вариант — HMAC.
- Схема Меркла–Дамгора позволяет продолжить хеш от известного состояния.
- Для подделки достаточно знать длину секрета.
- Есть готовые инструменты (hash_extender, hashpump).
- Защита — HMAC, а не «приклеить секрет к данным».

## Шаг 7: то же самое для SHA-1 и SHA-256

MD5 — не единственный алгоритм по схеме Меркла–Дамгора. SHA-1 и SHA-256 устроены так же, только блок и паддинг другие: у SHA-1/SHA-256 блок 64 байта, а длина пишется в 8 байт (SHA-256 пишет 64-битную длину). Значит, атака работает и с ними:

```
$ hash_extender --data 'user=guest' --secret 16 \
    --append '&user=admin' --format sha256 --signature 9b74c9897bac770ffc029102a200c5de
New signature: 1f3c2a...
New string   : 7573...800000...
```

Разница только в `--format`. Если в задаче токен выглядит как 40 hex-символов — это SHA-1; 64 — SHA-256; 32 — MD5. По длине подписи легко определить алгоритм.

Важная деталь: паддинг зависит от длины уже «съеденного» сообщения. Для SHA-1/SHA-256 длина записывается как big-endian 8 байт, а не 4, как у MD5. Инструменты учитывают это сами, но если пишешь свой код — легко ошибиться и «промахнуться» мимо состояния.

## Шаг 8: почему HMAC устойчив

HMAC — это не «приклеить ключ», а двухслойная конструкция:

```
HMAC(K, m) = H((K' XOR opad) || H((K' XOR ipad) || m))
```

Здесь `ipad` и `opad` — фиксированные байты (`0x36` и `0x5c`), повторённые до длины блока. Смысл в том, что **внутренний хеш целиком** становится сообщением для **внешнего** хеша, и внешний слой тоже зависит от ключа. Даже если ты продолжишь внутренний хеш, внешний слой ты не пересчитаешь без ключа. Поэтому length-extension на HMAC не работает.

Проверим руками:

```
$ python3 -c "import hmac,hashlib; print(hmac.new(b'key', b'user=guest', hashlib.md5).hexdigest())"
9b74c9897bac770ffc029102a200c5de
```

Атака, которая ломала `md5(key+data)`, здесь просто не проходит — состояние внутреннего хеша не является MAC-ом.

## Шаг 9: где это встречалось в реальной жизни

Length-extension — не академическая игрушка. Классические случаи:

- **Flickr API (2009)** — подпись `md5(secret + params)`; исследователи подделали права.
- **vBulletin** — самодельная подпись админ-куки.
- **Разные SAML-реализации** — подпись XML через хеш с секретом.
- **Самодельные JWT** — когда вместо HMAC пишут «хеш от ключа и полезной нагрузки».

В CTF это один из самых частых сюжетов в категории misc: даётся сервис с токеном, и надо стать админом, не зная секрета. Признак: подпись = хеш, секрет неотделим от данных, длина подписи 32/40/64 hex.

## Шаг 10: собственный эксплойт целиком

Чтобы не быть заложником готовых инструментов, напишем продолжение MD5 сами. Идея — прогнать только хвост, начав с сохранённого состояния:

```
$ cat md5cont.py
import struct

def md5_continue(state_hex, extra, prev_len):
    a,b,c,d = [int(state_hex[i:i+8],16) for i in (0,8,16,24)]
    # prev_len = длина секрет+данные (в байтах), паддинг уже "съеден"
    data = extra
    total = prev_len
    # ... здесь полная реализация раундов MD5 ...
    return '%08x%08x%08x%08x' % (a,b,c,d)
```

Ключевой момент: `prev_len` — это длина `SECRET + 'user=guest'`, округлённая до границы блока **вместе с паддингом**. Мы перебираем `prev_len` (8..32) и для каждого варианта считаем новую подпись, затем проверяем её на сервере. Один из вариантов совпадёт.

Полный прогон с перебором длины:

```
$ for n in $(seq 8 32); do
    sig=$(python3 md5cont.py --state 5f4dcc... --extra '&user=admin' --len $n)
    code=$(curl -s -o /dev/null -w '%{http_code}' \
        "http://vault.ctf/?user=guest<pad>&user=admin&token=$sig")
    [ "$code" = 200 ] && echo "secret length = $n, token=$sig"
  done
secret length = 14, token=9c1f0d2a...
```

## Шаг 11: защита

Разработчику достаточно двух правил:

1. **Не изобретать MAC.** Для подписи — `HMAC`, `AEAD`, или готовый JWT-либа с HS256.
2. **Если сравниваешь секреты — константное время.** `hmac.compare_digest`, а не `==`.

Дополнительно: не принимать лишние данные от клиента, валидировать длину и формат, не логировать секреты. Length-extension не появится, если ты не склеиваешь секрет с данными вручную.

## Шаг 12: типичные ошибки при эксплуатации

- **Неверная длина секрета** — самая частая. Всегда перебирай диапазон.
- **URL-кодирование паддинга.** `0x80` в query-строке нужно кодировать как `%80`, нули — как `%00` (если сервер их не режет).
- **Сервер режет нулевые байты.** Тогда часть паддинга «съедается» — иногда помогает перебор.
- **Алгоритм определён по длине неверно.** 32/40/64 — это MD5/SHA-1/SHA-256, но бывают и усечённые варианты.

Если совсем не сходится — распечатай, какой именно паддинг ты отправляешь, и сравни с тем, что «съел» бы хеш.

## Мини-практика: определи длину секрета

Отдельная маленькая задача, которую решают перед основной атакой. Дано: `sign('user=guest')` и сервис. Надо найти длину секрета.

```
$ for n in 1 4 8 12 16 20 24 32; do
    sig=$(hash_extender --data 'user=guest' --secret $n --append '&x=1' \
        --format md5 --signature 5f4dcc3b5aa765d61d8327deb882cf99 | grep 'New signature' | cut -d' ' -f3)
    code=$(curl -s -o /dev/null -w '%{http_code}' "http://vault.ctf/?user=guest&x=1&token=$sig")
    echo "len=$n http=$code"
  done
len=14 http=200
```

Единственный `200` выдаёт длину. Дальше — подделка. Такой перебор занимает секунды.

## Шпаргалка по length-extension

- Формат: подпись = `H(SECRET || message)`, где `H` — MD5/SHA-1/SHA-256.
- Что нужно: длина секрета (перебирается), сам хеш, желаемый «хвост».
- Инструменты: `hash_extender`, `hashpump`, свой `md5_continue`.
- Ключевая формула: продолжаем хеш от состояния `H(SECRET || message)`.
- Защита: HMAC. `HMAC(k,m) = H((k^opad) || H((k^ipad) || m))`.
- Признак в CTF: 32/40/64 hex-символа подписи и данные, склеенные с секретом.

Запомни порядок действий: 1) получить подпись, 2) перебрать длину секрета, 3) собрать паддинг, 4) отправить новое сообщение с подписью.
