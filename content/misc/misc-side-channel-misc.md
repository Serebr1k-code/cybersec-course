## Вопрос, с которого всё начинается

В задаче есть сервис, который проверяет пароль. Ответ всегда один — «неверно». Но почему-то условие намекает на «утечку». Как узнать пароль, если сервис никогда не говорит «да»? Ответ: смотреть не на **что** он отвечает, а на **как долго** он это делает. Побочный канал (side channel) — это утечка секрета не через сам алгоритм, а через физические характеристики его выполнения: время, потребление энергии, обращения к кэшу, ошибки.

## Наш пример: проверка пароля по времени

Пусть проверка устроена так: сравниваем введённое с секретом посимвольно и **прерываемся** на первом несовпадении:

```python
import time, statistics

def check(pw):
    secret = "s3cr3t!"
    for i, c in enumerate(pw):
        if i >= len(secret) or c != secret[i]:
            return False
        time.sleep(0.002)      # «стоимость» каждого верного байта
    return len(pw) == len(secret)
```

Если первый символ угадан, цикл делает на один шаг больше — и ответ приходит **чуть позже**. Время ответа кодирует, сколько байт совпало. Это и есть канал.

## Тайминговая атака: подбираем побайтово

Измеряем медиану времени для каждого кандидата на очередной байт и берём самый «долгий»:

```python
def measure(pw, rounds=200):
    ts = []
    for _ in range(rounds):
        t = time.perf_counter()
        check(pw)
        ts.append(time.perf_counter() - t)
    return statistics.median(ts)

known = ""
while True:
    times = {c: measure(known + c) for c in "abcdefghijklmnopqrstuvwxyz0123456789!"}
    best = max(times, key=times.get)
    known += best
    print("prefix:", known)
    if times[best] - min(times.values()) < 1e-4:
        break
```

`time.perf_counter()` даёт монотонный таймер с высокой точностью, а `statistics.median` устойчив к выбросам. Мы восстанавливаем секрет **по одному символу**, не зная его заранее.

## Защита: сравнение за постоянное время

Классическая контрмера — сравнивать **всё** и не выходить раньше:

```python
diff = 0
for a, b in zip(user_input, secret):
    diff |= ord(a) ^ ord(b)     # накапливаем разницу, не прерываемся
```

Итог проверяется один раз в конце, поэтому время не зависит от числа совпавших байт. На практике берут готовое:

```python
import hmac
hmac.compare_digest(user_input, secret)   # постоянное время
```

Если в задаче видишь `==` или `strcmp` при сравнении секретов — проверь тайминг. Это первое, что смотрят в подобных CTF.

## Кэш-атаки: Flush+Reload и Prime+Probe

Кэш процессора быстрее памяти, и обращение к «закэшированному» адресу заметно быстрее. Атакующий измеряет время доступа и делает вывод, к каким адресам обращалась жертва:

- **Flush+Reload** — атакующий сбрасывает (`clflush`) общую с жертвой строку кэша, ждёт её выполнения и замеряет время повторного доступа. Быстро — значит, жертва загрузила строку. Требует **общей памяти**.
- **Prime+Probe** — общей памяти не требует: атакующий «заполняет» кэш своими данными и смотрит, какие вытеснены жертвой.

В CTF это задачи про «секретный индекс»: жертва обращается к таблице по секретному индексу, а мы восстанавливаем индекс по таймингам.

## Питание, ЭМИ и ошибки

- **SPA/DPA/CPA** — анализ трассы питания: SPA визуально, DPA/CPA статистически по многим трассам. **EMA** — то же по электромагнитному излучению. В CTF это чаще hardware-задачи (нужен осциллограф или ChipWhisperer).
- **Fault injection** — сбой (пропуск инструкции, битфлип) заставляет код пойти по «редкому» пути, например обойти проверку подписи.
- **Rowhammer** — многократные обращения к строке памяти «переворачивают» биты в соседних.
- **Утечки через ошибки** — разные сообщения об ошибке для разных причин (padding oracle) позволяют восстановить открытый текст.

## Спектр (Spectre/Meltdown) — кратко

Спекулятивное исполнение и кэш создают канал, по которому можно прочитать память, к которой нет доступа. **Meltdown** читает память ядра из пользовательского процесса, **Spectre** обманывает предсказание ветвлений. Для CTF важно понять механизм: спекулятивная загрузка оставляет след в кэше, а Flush+Reload его измеряет.

## Как измерять правильно

- **Медиана, а не среднее.** Выбросы (GC, планировщик) искажают среднее; медиана устойчивее.
- **Много повторов.** Чем слабее сигнал, тем больше замеров — сотни и тысячи запусков.
- **Стабильная среда.** Отключи фоновые процессы, зафиксируй частоту CPU, избегай шумных виртуалок.
- **Разностный подход.** Сравнивай две группы (гипотеза верна/неверна) по распределениям, а не абсолютные значения.
- **Порог значимости.** Прежде чем делать вывод, убедись, что разница воспроизводима и превышает дрожание. Если разница меньше наносекунд — софтовый тайминг не сработает, нужны аппаратные методы.

## Практикум: восстанавливаем секретный индекс по кэшу

Типичная CTF-задача с кэш-каналом: жертва обращается к массиву по секретному индексу, а нам нужно его узнать. Логика Flush+Reload:

1. **Сброс.** Для каждого элемента массива сбрасываем его строку кэша (`clflush`).
2. **Триггер.** Заставляем жертву выполнить обращение по секретному индексу.
3. **Замер.** По очереди обращаемся ко всем элементам и замеряем время. Быстро — значит, жертва только что загрузила эту строку, и это и есть её индекс.

На псевдокоде это выглядит так:

```c
for (i = 0; i < N; i++) _mm_clflush(&table[i]);   // 1. сброс
victim_access();                                  // 2. триггер
for (i = 0; i < N; i++) {                          // 3. замер
    t = time_access(&table[i]);
    if (t < THRESHOLD) hit = i;                    // быстрый доступ = секрет
}
```

Порог `THRESHOLD` подбирается экспериментально: закэшированный доступ к памяти в разы быстрее промаха. Повторяй замер много раз и бери медиану — одиночный замер утонет в шуме.

## Что мы теперь знаем

- Побочный канал — утечка секрета через **время, кэш, питание, ЭМИ, ошибки**.
- Ранний выход при сравнении даёт тайминговую атаку; лечится constant-time compare.
- Flush+Reload требует общей памяти, Prime+Probe — нет.
- Fault injection и Rowhammer «ломают» выполнение, padding oracle утекает через ошибки.
- Спектр использует спекуляцию + кэш как канал.
- Сигнал тонет в шуме: нужны **медиана** и много повторов.

## На что смотреть дальше

- **Ищи ранние выходы.** Любой `return`/`break` по несовпадению — потенциальный тайминг-канал.
- **Много замеров и медиана.** Одиночный замер бесполезен: сигнал тонет в шуме планировщика и GC.
- **Сравнивай распределения, а не значения.** Разница между двумя группами надёжнее абсолютных чисел.
- **Знай предел софта.** Разница меньше наносекунд требует аппаратных методов (осциллограф, ChipWhisperer).
- **Не забывай про ошибки.** Разные сообщения об ошибке — тоже канал (padding oracle).
