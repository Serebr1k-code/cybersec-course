## Что такое побочные каналы

Побочный канал (side channel) — это утечка секрета не через сам алгоритм, а через **физические характеристики** его выполнения: время работы, потребление энергии, электромагнитное излучение, обращения к кэшу, ошибки. Криптография может быть математически безупречной, но её реализация «выдаёт» ключ через время или кэш. В CTF это задачи вида «подбери пароль по времени ответа» или «вытащи ключ из кэш-таймингов».

## Тайминговые атаки

Идея: разные входные данные приводят к разному времени выполнения. Если код рано завершает работу при неверном префиксе (как `memcmp` в некоторых реализациях), можно подбирать секрет побайтово, измеряя время.

```python
import time, statistics

def check(pw):
    secret = "s3cr3t!"
    for i, c in enumerate(pw):
        if i >= len(secret) or c != secret[i]:
            return False
        time.sleep(0.002)      # «стоимость» каждого верного байта
    return len(pw) == len(secret)

def measure(pw, rounds=200):
    ts = []
    for _ in range(rounds):
        t = time.perf_counter()
        check(pw)
        ts.append(time.perf_counter() - t)
    return statistics.median(ts)

# подбираем байт за байтом по максимуму времени
known = ""
while True:
    times = {c: measure(known + c) for c in "abcdefghijklmnopqrstuvwxyz0123456789!"}
    best = max(times, key=times.get)
    known += best
    print("prefix:", known)
    if times[best] - min(times.values()) < 1e-4:
        break
```

В реальных задачах сигнал слабее, поэтому берут медиану по многим запускам и сравнивают распределения, а не отдельные замеры.

## Атаки на сравнение строк

Классическая уязвимость — сравнение секретов посимвольно с ранним выходом. Контрмеры:

- сравнивать **за постоянное время** (`constant-time compare`): `diff |= a[i] ^ b[i]`, где итог проверяется в конце;
- использовать хеши с фиксированным временем сравнения (`hmac.compare_digest`).

```python
import hmac
hmac.compare_digest(user_input, secret)   # постоянное время
```

Если в задаче есть `==` или `strcmp`, стоит проверить тайминг — это первое, что смотрят в подобных CTF.

## Кэш-атаки: Flush+Reload и Prime+Probe

Кэш-тайминги эксплуатируют то, что обращение к данным в кэше быстрее, чем к памяти. Атакующий измеряет время доступа к разделяемой памяти и делает выводы о том, к каким адресам обращался жертва.

- **Flush+Reload** — атакующий сбрасывает (`clflush`) общую строку кэша, ждёт, пока жертва выполнится, и замеряет время повторного доступа. Быстро — значит, жертва загрузила строку.
- **Prime+Probe** — не требует общей памяти: атакующий «заполняет» кэш своими данными и смотрит, какие из них вытеснены жертвой.

В CTF кэш-атаки встречаются в задачах на «секретный индекс»: жертва обращается к таблице по секретному индексу, а атакующий восстанавливает индекс по таймингам.

## Атаки по питанию и электромагнитному излучению

Потребление энергии зависит от выполняемых операций: умножение «тяжелее» сложения, а обработка бита ключа может давать различимый след. Классы:

- **SPA** (Simple Power Analysis) — визуальный анализ трассы питания;
- **DPA/CPA** (Differential/Correlation Power Analysis) — статистический анализ по многим трассам;
- **EMA** (Electromagnetic Analysis) — тот же принцип, но по излучению.

В CTF это чаще «hardware»-задачи (нужен осциллограф/Proxmark), но понимание принципа полезно и для софтовых утечек.

## Атаки по ошибкам и памяти

- **Fault injection** — сбой (пропуск инструкции, битфлип) заставляет код пойти по «редкому» пути; например, обойти проверку подписи.
- **Rowhammer** — многократные обращения к строке памяти «переворачивают» биты в соседних строках.
- **Утечки через ошибки** — разные сообщения об ошибке для разных причин (padding oracle) позволяют восстановить открытый текст.

## Спектр (Spectre/Meltdown) — кратко

Спекулятивное исполнение и кэш создают канал, по которому можно прочитать память, к которой нет доступа. **Meltdown** читает память ядра из пользовательского процесса, **Spectre** — обманывает предсказание ветвлений. Для CTF важно понимать механизм: спекулятивная загрузка оставляет след в кэше, а Flush+Reload его измеряет.

## Инструменты и код

- **time / perf_counter** — тайминги в Python; `statistics.median` для устойчивости.
- **perf** — счётчики производительности Linux (`perf stat`, `perf c2c`).
- **valgrind --tool=cachegrind** — профилирование кэша.
- **rdtsc** — точный счётчик тактов в C.
- **ChipWhisperer** — аппаратные измерения питания/ЭМИ.
- **Flush+Reload примеры** — на C с `clflush`/`rdtsc`.

## Разобранный пример: кэш-тайминг

Упрощённая модель «секретного индекса»: функция обращается к элементу массива по секретному индексу, а мы измеряем время обращения.

```python
import time
secret_index = 7
table = [0] * 256

def victim():
    _ = table[secret_index]      # обращение по секрету

def probe():
    # прогреваем все строки, затем смотрим, какая быстрее
    pass
```

В реальности между «прогревом» и «замером» вклинивается вызов жертвы, а атакующий восстанавливает индекс по разнице времени. В CTF это оформляют как локальный процесс, с которым взаимодействует ваш код.

## Частые ошибки и подводные камни

- **Одиночный замер.** Тайминговый сигнал тонет в шуме; нужны сотни измерений и медиана.
- **Шум от системы.** Фоновые процессы, частота CPU, троттлинг искажают замеры; отключайте лишнее.
- **Предположение о детерминизме.** JIT, GC и кэш делают время нестабильным.
- **Слишком маленький сигнал.** Если разница меньше наносекунд, софтовый тайминг не сработает — нужны аппаратные методы.
- **Непостоянное сравнение в «защищённом» коде.** Всегда проверяйте, действительно ли используется constant-time compare.

## Что дальше / решение

1. Определите канал: время, кэш, питание, ошибки.
2. Для тайминга — соберите много замеров, берите медиану, сравнивайте распределения.
3. Для сравнения строк — проверьте наличие раннего выхода; подбирайте префикс побайтово.
4. Для кэша — реализуйте Flush+Reload/Prime+Probe по шагам.
5. Помните: сигнал должен быть устойчиво выше шума, иначе нужен аппаратный подход.

## Тайминговые атаки на хеш-таблицы и пароли

Кроме сравнения строк, тайминг утекает через структуры данных. В некоторых языках поиск в хеш-таблице по коллизирующим ключам занимает больше времени — это основа **hash-flooding** и тайминговых атак на `dict`/`HashMap`. В задачах на «угадай ключ» иногда достаточно измерять время обработки запроса.

Отдельный класс — атаки на **парольные хеши с ранним выходом**. Если проверка пароля сравнивает хеши побайтово и прерывается на первом несовпадении, время ответа кодирует число совпавших байт. Защита — сравнивать хеши целиком за постоянное время (`hmac.compare_digest`), а не через `==`.

## Практические советы по измерению

- **Медиана, а не среднее.** Выбросы (GC, планировщик) искажают среднее; медиана устойчивее.
- **Много повторов.** Чем слабее сигнал, тем больше замеров; сотни-тысячи запусков.
- **Стабильная среда.** Отключите фоновые процессы, зафиксируйте частоту CPU, избегайте виртуалок с шумным соседством.
- **Разностный подход.** Сравнивайте две группы входов (гипотеза верна/неверна) и смотрите на разницу распределений, а не абсолютные значения.
- **Порог значимости.** Прежде чем делать вывод, убедитесь, что разница воспроизводима и превышает дрожание.

## Аппаратные каналы в CTF

В hardware-задачах те же принципы применяют к реальному железу: осциллограф снимает трассу питания, EM-зонд — излучение, а статистика (CPA) восстанавливает биты ключа AES. Для софтовых misc-задач достаточно понимать аналогию: **любая зависимость выполнения от секрета — это канал**. Ваша задача — найти такую зависимость и превратить её в измеримый сигнал.

## Итог по побочным каналам

Ключевая мысль: **любая зависимость выполнения от секрета — это канал**. Ищите ранние выходы, разные ветки по секрету, обращения к памяти по индексу, зависящему от ключа. Затем превращайте зависимость в измеримый сигнал: много замеров, медиана, сравнение распределений. Для софтовых задач хватает `perf_counter` и статистики; для аппаратных — осциллограф и CPA. И помните о контрмерах: constant-time сравнение, нормализация, устранение ветвлений по секрету.

## Тайминговые атаки на сравнение хешей и токенов

Современные фреймворки обычно используют constant-time сравнение, но самописные проверки — нет. Если сервер отвечает быстрее при большем совпавшем префиксе токена, вы можете восстановить токен побайтово. Проверка простая: отправьте запросы с разными префиксами и сравните медианы времени ответа. Даже разница в микросекунды при тысячах запросов становится различимой. Это же касается сравнения HMAC-подписей и «секретных вопросов».
