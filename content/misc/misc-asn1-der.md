## Вопрос, с которого всё начинается

Открой любой сертификат сайта — увидишь нечитаемую бинарную структуру. Это **DER** — кодирование данных, описанных языком **ASN.1**. На нём стоят сертификаты, TLS, LDAP, SNMP и многое другое. И именно парсеры ASN.1 исторически давали самые громкие уязвимости.

## Наш пример: сертификат

```
$ openssl x509 -in cert.pem -outform DER -out cert.der
$ xxd -l 16 cert.der
00000000: 30 82 03 21 30 82 02 89 a0 03 02 01 02 02 09 00  0..!0...........
```

Разберём первые байты: `30` — тип SEQUENCE, `82 03 21` — длина 0x0321 = 801 байт. Дальше идёт содержимое.

## Шаг 1: TLV — tag, length, value

ASN.1-данные кодируются как **TLV**:

- **Tag** — тип: SEQUENCE (0x30), INTEGER (0x02), OID (0x06), UTF8String (0x0c), SET (0x31).
- **Length** — длина значения: короткая (один байт, если < 128) или длинная (`0x81`/`0x82` + байты длины).
- **Value** — само значение.

В примере `30 82 03 21`: tag=SEQUENCE, length-форма `0x82` (два байта длины) = `0x0321` = 801. Значит, весь сертификат — SEQUENCE из 801 байта.

## Шаг 2: OID — идентификаторы алгоритмов

**OID** (Object Identifier) — уникальное имя алгоритма или расширения. Кодируется как последовательность чисел, упакованных в байты: первые два числа в один байт (`40*a + b`), остальные — varint-подобно. Пример: OID `1.2.840.113549.1.1.11` — это `sha256WithRSAEncryption`.

Именно по OID вы определяете, каким алгоритмом подписан сертификат, — что пригодится в PQC-задачах.

## Шаг 3: структура X.509

Сертификат — это вложенные SEQUENCE:

```
Certificate ::= SEQUENCE {
    tbsCertificate       TBSCertificate,
    signatureAlgorithm   AlgorithmIdentifier,
    signatureValue       BIT STRING
}
```

`tbsCertificate` («to be signed») содержит версию, серийный номер, издателя, сроки, субъекта и публичный ключ. Подпись считается именно от `tbsCertificate` в DER-кодировке.

## Шаг 4: классические уязвимости ASN.1

- **Parsing differentials.** BER допускает неоднозначности (неопределённая длина, неканонические длины), а DER их запрещает. Если один компонент парсит BER, а другой — DER, они увидят разные данные.
- **Length confusion.** Заявленная длина не совпадает с реальной; парсеры по-разному её обрабатывают.
- **Recursion depth.** Глубоко вложенные структуры переполняют стек.
- **OID confusion.** Подмена алгоритма на более слабый при неверной проверке.

Исторические примеры: CVE в OpenSSL, Java, Windows CryptoAPI — все связаны с ASN.1.

## Шаг 5: инструменты разбора

```
$ openssl asn1parse -in cert.der -i
    0:d=0  hl=4 l= 801 cons: SEQUENCE
    4:d=1  hl=4 l= 649 cons: SEQUENCE
    8:d=2  hl=2 l=   3 cons: cont [ 0 ]
   10:d=3  hl=2 l=   1 prim: INTEGER           :02
   13:d=2  hl=2 l=   9 prim: INTEGER           :00...
   ...
```

`openssl asn1parse` показывает дерево с уровнями (`d=`), длинами (`l=`) и типами. Это первый инструмент для любого сертификата.

## Полный прогон: находим флаг в расширении

```
$ python3 asn1_walk.py cert.der
SEQUENCE
  SEQUENCE (tbsCertificate)
    ...
    SEQUENCE (extensions)
      OID 1.2.3.4.5 (custom)
      OCTET STRING -> nto{4sn1_tlv_p4rs1ng}
```

Флаг спрятан в кастомном расширении сертификата. Задача — пройти дерево TLV и извлечь OCTET STRING.

## Что мы теперь знаем

- ASN.1 описывает данные, DER/BER кодируют их как TLV.
- OID идентифицирует алгоритмы; по нему читают подпись.
- X.509 — вложенные SEQUENCE с подписью от tbsCertificate.
- Расхождения BER/DER — источник серьёзных уязвимостей.
- `openssl asn1parse` — базовый инструмент.

## Разбор сертификата по слоям

Возьмём реальный сертификат и пройдём по дереву:

```
$ openssl asn1parse -in cert.der -i | head -20
    0:d=0  hl=4 l= 801 cons: SEQUENCE
    4:d=1  hl=4 l= 649 cons: SEQUENCE          <- tbsCertificate
    8:d=2  hl=2 l=   3 cons: cont [ 0 ]        <- version
   10:d=3  hl=2 l=   1 prim: INTEGER           :02
   13:d=2  hl=2 l=   9 prim: INTEGER           :00d1...  <- serial
   24:d=2  hl=2 l=  13 cons: SEQUENCE          <- signature alg
   26:d=3  hl=2 l=   9 prim: OBJECT            :sha256WithRSAEncryption
   37:d=2  hl=2 l=  30 cons: SEQUENCE          <- issuer
   69:d=2  hl=2 l=  30 cons: SEQUENCE          <- validity
   71:d=3  hl=2 l=  13 prim: UTCTIME           :250101000000Z
   86:d=3  hl=2 l=  13 prim: UTCTIME           :260101000000Z
```

Столбцы: смещение (`d=` — глубина), `hl=` — длина заголовка, `l=` — длина значения, `cons`/`prim` — составной/примитив. Так читается вся структура.

## OID подробнее

OID кодируется не как строка чисел, а компактно: первые два числа объединяются в один байт как `40*a + b`, остальные кодируются в base-128. Например, `1.2.840.113549` начинается с байта `0x2a` (1*40+2), затем `0x86 0x48` (840), затем `0x86 0xf7 0x0d` (113549).

Знание OID позволяет мгновенно определить алгоритм: `1.2.840.113549.1.1.11` — sha256WithRSA, `1.2.840.10045.4.3.2` — ecdsa-with-SHA256, `2.16.840.1.101.3.4.3.17` — ML-DSA-65.

## BER-неоднозначности на примере

BER допускает три способа закодировать длину 5: `0x05` (короткая), `0x81 0x05` (длинная, один байт), `0x82 0x00 0x05` (длинная, два байта). DER разрешает только первый. Если сервер валидирует сертификат по DER, а другой компонент — по BER, они могут увидеть разные данные при одних байтах.

Именно на таких расхождениях строились атаки на TLS и PKI. Правило: всегда канонизируйте к DER перед проверкой подписи.

## Исторические CVE

- **CVE-2015-0286** (OpenSSL): неверная обработка ASN.1 в `d2i_X509` вела к обходу проверки.
- **CVE-2016-2108** (OpenSSL): переполнение при декодировании ASN.1.
- Уязвимости в Java `X509Certificate` и Windows CryptoAPI того же класса.

Общая причина — сложность формата и множество «легальных» кодировок.

## Инструменты

- `openssl asn1parse` — дерево структуры.
- `dumpasn1` — альтернативный просмотрщик.
- Python `asn1crypto`, `pyasn1` — программный разбор.
- `certlint` — проверка каноничности сертификата.

## Частые вопросы

**Что такое BIT STRING vs OCTET STRING?** BIT STRING хранит биты (используется для подписи и ключей), OCTET STRING — байты.

**Почему подпись считается от tbsCertificate?** Так задумано X.509: подписывается «тело», а не весь сертификат.

**Можно ли подделать сертификат через BER?** Только если проверяющая сторона не канонизирует к DER.

## Где ещё используется ASN.1

Помимо X.509, ASN.1 лежит в основе:

- **LDAP** — каталоги и их запросы.
- **SNMP** — управление сетью.
- **PKCS#7/CMS** — подписанные сообщения и S/MIME.
- **Kerberos** — билеты и сообщения аутентификации.
- **GSM/3GPP** — телеком-протоколы.

Поэтому парсер ASN.1 нужен не только для сертификатов. Ошибка в нём — потенциальный вход в любую из этих систем.

## Практический приём: fuzzing ASN.1

Именно фаззинг ASN.1-парсеров находил большинство CVE в OpenSSL. Приёмы: мутировать длины (завышать/занижать), менять теги, добавлять вложенность, использовать BER-неоднозначности. Если пишете свой парсер — обязательно фаззьте его на этих случаях.

## Итог по ASN.1/DER

ASN.1 описывает данные, BER/DER кодируют их как TLV. OID идентифицируют алгоритмы, X.509 строится из вложенных SEQUENCE. Главная опасность — расхождения между BER и DER и сложность парсеров, что исторически давало критические CVE. Канонизация к DER и аккуратная обработка длин — обязательны.

## Разбор подписи и её проверка

`signatureValue` — это BIT STRING с подписью. Проверка: взять байты `tbsCertificate`, посчитать хеш указанным в `signatureAlgorithm` алгоритмом и проверить подпись публичным ключом издателя. Если хотя бы один байт `tbsCertificate` изменён, подпись не сойдётся. Поэтому атаки на ASN.1 нацелены на то, чтобы два парсера «увидели» разные `tbsCertificate` при одних байтах.

## Name и Distinguished Name

Поля issuer/subject — это SEQUENCE из Relative Distinguished Names (RDN), каждое из SET пар (OID, строка). Порядок RDN значим, порядок пар внутри SET — нет. Это ещё одна точка неоднозначности: некоторые парсеры сравнивают DN как строки, другие — как структуры, и «эквивалентные» DN могут считаться разными.

## Расширения и их критика

Расширения X.509 (basicConstraints, keyUsage, subjectAltName) помечены как critical или non-critical. Если критическое расширение неизвестно парсеру, он обязан отвергнуть сертификат; если игнорирует — возможен обход. В CTF флаг часто прячут в кастомном расширении с неизвестным OID.

## Генерация тестовых структур

```
$ openssl asn1parse -genconf struct.cnf -out test.der
$ xxd test.der
```

`-genconf` позволяет собрать произвольную ASN.1-структуру из конфигурации — удобно для фаззинга и для создания учебных примеров.

## Реальные последствия

ASN.1-баги приводили к обходу проверки сертификатов, подделке подписей и удалённому выполнению кода. Класс ошибок стабилен: неоднозначность формата + доверие к заявленным длинам. Зная это, вы читаете любой такой CVE с пониманием.

## Итог

ASN.1/DER — формальный и строгий, но именно строгость порождает расхождения между реализациями. TLV, OID, X.509 и BER/DER — базовый словарь. Канонизация и аккуратные границы — защита. В CTF ищите данные в расширениях и не забывайте про вложенность.
