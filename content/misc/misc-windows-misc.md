## Вопрос, с которого всё начинается

У тебя есть образ диска Windows `win.img`. Вопрос задачи: «какую программу запускал пользователь и что она делала?». Файлов на диске тысячи, и просто искать по имени бесполезно — нужного файла может уже не быть.

Windows оставляет **следы** почти везде: в реестре, в файлах Prefetch, в журналах, в списках «недавних документов». Умение читать эти следы и восстанавливать «кто, что и когда» — это Windows-форензика. Весь урок — на одном образе `win.img`.

## Наш пример: ищем запущенную программу

Первым делом собираем «говорящие» артефакты — те, что прямо записывают запуски. Один из самых ценных — **Prefetch**. Это файлы в `C:\Windows\Prefetch\` с расширением `.pf`: при каждом запуске программы Windows запоминает её имя и путь. Разбирает их утилита `PECmd` (из набора Eric Zimmerman Tools):

```
$ PECmd.exe -d Prefetch/ --csv prefetch.csv
$ cat prefetch.csv | head
Run time,Executable name,Path
2024-03-15 09:00:00,update.exe,C:\Users\user\AppData\Local\Temp\update.exe
2024-03-15 08:59:40,explorer.exe,C:\Windows\explorer.exe
```

Читаем: 15 марта в 09:00 запускался `update.exe` из папки `AppData\Local\Temp`. Это сразу подозрительно — обычные программы не живут в `Temp`. Но Prefetch не говорит, что программа **сделала**. Идём дальше.

## Шаг 1: реестр — что делал пользователь

**Реестр** — база настроек Windows, разбитая на «ульи» (hives) — отдельные файлы:

- **SAM** — локальные учётные записи (там же хеши паролей);
- **SYSTEM** — настройки системы, история USB;
- **SOFTWARE** — установленные программы;
- **NTUSER.DAT** — настройки конкретного пользователя, включая историю.

Нас интересует `NTUSER.DAT` и ключ **UserAssist** — счётчик запущенных программ с временем последнего запуска. Разбирает его `regripper`:

```
$ regripper -r NTUSER.DAT -f userassist
...
update.exe (3) 2024-03-15 09:00:00
cmd.exe (12) 2024-03-15 08:59:12
```

В скобках — сколько раз запускалась программа. `update.exe` запускался трижды; `cmd.exe` — двенадцать раз, прямо перед ним. Картина складывается: пользователь открыл командную строку и запустил подозрительный файл.

## Шаг 2: ярлыки — какие файлы открывали

Windows хранит **LNK** — ярлыки на недавно открытые файлы и папки, а также **Jump Lists** — списки «недавнего» по программам. В них бывают путь к файлу и даже **MAC-адрес** тома и серийник диска, что связывает активность с конкретным носителем. Разбирает их `LECmd`:

```
$ LECmd.exe -d lnk/ --csv lnk.csv
$ grep -i 'flag\|secret' lnk.csv
Source path: C:\Users\user\Desktop\secret.txt
```

Ярлык указывает на `secret.txt` на рабочем столе. Но самого файла может уже не быть — его удалили. И тут на сцену выходит третий артефакт.

## Шаг 3: что помнит журнал изменений

**USN Journal** — журнал изменений тома NTFS: он фиксирует создание, удаление и переименование файлов. А **$MFT** — главная таблица файлов, где у каждой записи есть имя и времена. Даже если файл удалён, запись в MFT и USN часто остаётся. Смотрим:

```
$ fls -r -m / win.img > body.txt
$ grep -i secret body.txt
0|/Users/user/Desktop/secret.txt|128|...|1710493200|...
```

`fls` показывает запись `secret.txt` — файл существовал. Достаём содержимое по inode:

```
$ icat win.img 128
FLAG{w1nd0ws_k33ps_m0r3_th4n_y0u_th1nk}
```

Флаг в удалённом файле. Мы нашли его, сопоставив три независимых артефакта: Prefetch (запуск), UserAssist (кто запускал), MFT (что открывали).

## Шаг 4: журналы событий (EVTX)

Отдельный пласт — **Event Logs** (`Security.evtx`, `System.evtx`). Это структурированные журналы событий, где у каждого события есть числовой **Event ID**. Ключевые для нас:

| Event ID | Что означает |
|----------|--------------|
| 4624 | успешный вход в систему |
| 4625 | неудачный вход |
| 4688 | создание процесса (запуск программы) |
| 7045 | установлена новая служба |

Читать EVTX можно через `evtx_dump`:

```
$ python3 -m evtx_dump Security.evtx | grep -i '4688' -A2 | head
EventID: 4688
NewProcessName: C:\Users\user\AppData\Local\Temp\update.exe
```

Событие 4688 подтверждает запуск того же `update.exe`, что мы видели в Prefetch. Два независимых источника совпали — можно не сомневаться.

## Шаг 5: где программа «закрепляется»

Если программа возвращается после перезагрузки, у неё есть механизм **persistence** — автозапуска. Ищем его в реестре:

- **Run/RunOnce** — запуск при входе пользователя;
- **Службы** — `HKLM\SYSTEM\...\Services`;
- **Задачи планировщика** — `C:\Windows\System32\Tasks\`;
- **Startup-папка** — `%APPDATA%\...\Startup`.

```
$ regripper -r SOFTWARE -f run
...
[HKCU\Software\Microsoft\Windows\CurrentVersion\Run]
update = C:\Users\user\AppData\Local\Temp\update.exe
```

Запись `Run` указывает на файл в `Temp` — классический признак вредоносного закрепления.

## Шаг 6: следы, которые не зависят от Prefetch

Prefetch можно отключить — тогда на помощь приходят другие источники:

- **PowerShell Operational Log (EVTX)** — хранит полный текст выполненных скриптов (Event ID 4104). Если злоумышленник работал через PowerShell, здесь видно каждый блок кода;
- **WMI** — постоянные подписки (`__EventFilter`, `CommandLineEventConsumer`) как механизм закрепления;
- **BITS** — фоновая передача файлов, иногда используется для загрузки полезной нагрузки;
- **SRUM** — статистика использования ресурсов: какое приложение сколько сети и диска потратило;
- **Amcache / ShimCache** — следы выполнения бинарников, включая их хеши.

Особенно ценен **ShimCache** (`AppCompatCache` в улье `SYSTEM`): он помнит бинарники, которые **существовали** на диске, даже если их уже удалили. Это позволяет доказать запуск программы, которой на диске давно нет.

## Кейс: ищем механизм закрепления

Механизмы автозапуска в Windows удобно проверять по списку:

| Механизм | Где искать |
|----------|-----------|
| Run / RunOnce | `HKLM\...\CurrentVersion\Run` |
| Службы | `HKLM\SYSTEM\...\Services` |
| Планировщик | `C:\Windows\System32\Tasks\` |
| WMI-подписки | `OBJECTS.DATA` |
| Startup-папка | `%APPDATA%\...\Startup` |

```
$ regripper -r SOFTWARE -f run
$ regripper -r SYSTEM -f services
```

Подозрительная запись обычно указывает на файл в нестандартном месте (`AppData`, `Temp`, `ProgramData`). Именно такая запись и ведёт к полезной нагрузке — и к флагу.

## Что мы теперь знаем

По-простому:

1. **Prefetch** — какие программы запускались (имя, путь, время).
2. **UserAssist** — что запускал пользователь (со счётчиком).
3. **LNK/Jump Lists** — какие файлы и папки открывали.
4. **USN/MFT** — что создавалось и удалялось (помнят удалённое).
5. **EVTX** — события системы с Event ID (входы, запуски).
6. Ни один артефакт не полон — картина складывается из **сопоставления**.

## На что смотреть дальше

- **Не путайте ульи.** `SYSTEM` и `SOFTWARE` — разные файлы, у каждого свои ключи.
- **Времена в UTC.** Prefetch и USN хранят время в UTC — учитывайте пояс.
- **Проверяйте удалённое.** USN и Shellbags помнят объекты, которых уже нет на диске.
- **Ищите нестандартные пути.** `Temp`, `AppData`, `ProgramData` — частые места полезной нагрузки.
- **Сопоставляйте источники.** Один артефакт ошибается, два совпавших — почти доказательство.

## Куда дальше

Мы научились восстанавливать «кто, что и когда» по артефактам Windows: Prefetch, UserAssist, LNK, MFT/USN и EVTX. Дальше логично закрепить это на практических образах (например, публичные датасеты с `win.img`) и перейти к ветке `misc-encoding` — там разбираются сами форматы данных, которые встречаются внутри этих артефактов. А пока главное: один артефакт почти всегда неполон, а хронология собирается из **сопоставления** нескольких независимых источников.

## Где пригодится

- **CTF forensics/misc:** задачи с дампом диска или реестра Windows.
- **Инцидент-реагирование:** восстановление хронологии запусков и входов.
- **Форензика:** работа с Prefetch, USN, MFT, EVTX и ульями реестра.
- **Пентест:** понимание артефактов, остающихся после действий на хосте.
