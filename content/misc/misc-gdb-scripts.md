## Вопрос, с которого всё начинается

Ты отлаживаешь эксплойт и в сотый раз вручную вводишь одни и те же команды: поставить breakpoint, посмотреть регистры, прочитать память, продолжить. Это можно автоматизировать. **gdb** встроенно поддерживает Python — и это меняет всё. Разберём, как писать скрипты отладки.

## Наш пример: breakpoint, который печатает состояние

```python
# save as script.py, run: gdb -x script.py ./challenge
import gdb

class ShowRDI(gdb.Breakpoint):
    def stop(self):
        rdi = int(gdb.parse_and_eval('$rdi'))
        print('RDI =', hex(rdi))
        return False   # не останавливаться

ShowRDI('system')
gdb.execute('run')
```

Такой скрипт печатает `rdi` при каждом вызове `system` — идеально для проверки аргумента эксплойта.

## Шаг 1: API gdb

Основные объекты: `gdb.execute('команда')` — выполнить команду gdb; `gdb.parse_and_eval('$rax')` — вычислить выражение; `gdb.selected_inferior().read_memory(addr, n)` — прочитать память; `gdb.Breakpoint` — свой breakpoint с хуком.

## Шаг 2: breakpoints с хуком

Наследуй `gdb.Breakpoint` и переопредели `stop()`. Возврат `True` останавливает выполнение, `False` — продолжает. Так делают «логирующие» точки останова, которые не прерывают программу, а собирают данные.

## Шаг 3: чтение памяти и регистров

```python
rax = int(gdb.parse_and_eval('$rax'))
inf = gdb.selected_inferior()
data = inf.read_memory(rax, 16).tobytes()
print(data.hex())
```

Это позволяет автоматически дампить буферы, строки, структуры — без ручного `x/16xb`.

## Шаг 4: пользовательские команды

Можно определить свои команды gdb:

```python
class MyCmd(gdb.Command):
    def __init__(self):
        super().__init__('dumpstack', gdb.COMMAND_USER)
    def invoke(self, arg, tty):
        print(gdb.execute('x/8gx $rsp', to_string=True))
MyCmd()
```

Теперь `dumpstack` — твоя команда, доступная в любой сессии.

## Шаг 5: связка с pwndbg/pwntools

Если установлен pwndbg, доступны команды `vis_heap_chunks`, `bins`, `telescope`. Из pwntools можно запускать gdb через `gdb.debug()` и передавать `gdbscript` — тогда отладка и эксплойт живут в одном файле.

## Шаг 6: практические сценарии

- Логировать все вызовы функции с аргументами.
- Дампнуть память по адресу из регистра при срабатывании условия.
- Автоматически находить оффсет (перебором длин).
- Трассировать изменения конкретного адреса.

## Если не сработало

- Скрипт не запускается → проверь, что запускаешь через `gdb -x script.py`.
- `parse_and_eval` падает → символ/регистр недоступен в текущем контексте.
- Breakpoint не срабатывает → адрес не исполняется; проверь, что функция вызывается.

## Частые ошибки

- Забыть `return False` для логирующих breakpoints.
- Читать память по невалидному адресу (нужна проверка).
- Путать `gdb.execute` без `to_string=True` (печатает в консоль).

## Что мы теперь знаем

- gdb встроенно поддерживает Python.
- `gdb.Breakpoint` с хуком `stop()` — логирующие точки останова.
- `read_memory`/`parse_and_eval` дают доступ к памяти и регистрам.
- Свои команды и связка с pwntools/pwndbg автоматизируют рутину.

## Шаг 7: символы и типы

Из gdb можно обращаться к символам и типам: `gdb.parse_and_eval('main')`, `gdb.lookup_type('struct foo')`. Это позволяет писать скрипты, которые знают структуру программы и автоматически разбирают объекты. Для C++ можно достать vtable и поля объектов — полезно при анализе.

## Шаг 8: трассировка изменений памяти

Watchpoint с хуком: подпишись на изменение адреса и печатай старое/новое значение. Так находят, кто портит переменную, или подтверждают, что переполнение достигло цели. В скрипте это делается через `gdb.Breakpoint` с `wp` или через команду `watch` и обработчик.

## Шаг 9: автоматический поиск оффсета

Классическая рутина — найти, сколько байт до возвратного адреса. Скрипт перебирает длины payload, ставит breakpoint на `ret` и смотрит, перезаписал ли он `rip`. Такой скрипт экономит десятки ручных запусков. В pwntools для этого есть `cyclic`/`cyclic_find`, но понимать механику важно.

## Шаг 10: интеграция с pwntools

`gdb.debug(..., gdbscript=...)` и `gdb.attach(p, gdbscript=...)` связывают отладчик с эксплойтом. Можно остановить программу в нужный момент, осмотреть память скриптом и продолжить — всё из одного Python-файла. Это самый продуктивный режим работы над pwn-задачей.

## Шаг 11: полезные команды pwndbg

Если установлен pwndbg, доступны: `vis_heap_chunks` (карта чанков), `bins` (содержимое списков), `telescope` (разыменование стека), `got`/`plt` (таблицы), `vmmap` (карта памяти). В скрипте их можно вызывать через `gdb.execute('bins', to_string=True)` и парсить результат.

## Шаг 12: мини-чек-лист gdb-скриптинга

- Скрипт запускается через `gdb -x`?
- Логирующие breakpoints возвращают `False`?
- Чтение памяти защищено от невалидных адресов?
- Используется `to_string=True` для захвата вывода?
- Есть ли автоматизация повторяющихся действий?
- Связан ли скрипт с pwntools (`gdb.debug`/`attach`)?

## Шаг 13: почему скриптовать отладку

Отладка — это цикл «остановись, посмотри, продолжи». Когда цикл повторяется вручную десятки раз, ты тратишь время на механику, а не на анализ. Python-скрипт убирает механику: он сам останавливается в нужных точках, собирает данные и продолжает. В результате ты думаешь о задаче, а не о наборе команд.

Особенно это важно в pwn, где нужно многократно проверять, дошёл ли payload до нужной точки и что лежит в регистрах.

## Шаг 14: как устроен API gdb

API gdb даёт доступ к: выполнению команд (`gdb.execute`), вычислению выражений (`gdb.parse_and_eval`), памяти (`selected_inferior().read_memory`), символам (`lookup_symbol`), точкам останова (`gdb.Breakpoint`), событиям (`gdb.events.stop`). Освоив эти пять групп, ты покрываешь почти все задачи автоматизации.

## Шаг 15: события и хуки

Подписка на события (`gdb.events.stop.connect(handler)`) позволяет реагировать на остановки: печатать состояние, сохранять дамп, менять регистры. Это мощнее отдельных breakpoints, потому что даёт единую точку обработки всех остановок.

## Шаг 16: работа с памятью

Чтение памяти в скрипте: `inf.read_memory(addr, n).tobytes()`. Запись: `inf.write_memory(addr, data)`. Так можно дампить буферы, патчить значения, проверять гипотезы. Обязательно проверяй валидность адреса, иначе получишь исключение.

## Шаг 17: разбор структур

`gdb.lookup_type('struct foo')` и `gdb.parse_and_eval('(struct foo*)addr')` позволяют работать с типами: читать поля по именам, а не по смещениям. Для C++ это особенно удобно — можно достать vtable и вызываемые методы.

## Шаг 18: автоматизация перебора

Скрипт может перебирать параметры: длины payload, значения байтов, адреса. Каждая итерация — запуск, остановка в точке, проверка. Это превращает «угадывание» в систематический поиск и часто находит решение там, где ручной перебор утомителен.

## Шаг 19: связка с pwntools

`gdb.debug('./bin', gdbscript=script)` запускает бинарь под отладкой и возвращает tube. Теперь скрипт эксплойта и скрипт отладки — один файл. Можно остановиться, осмотреть память через gdb API, продолжить и тут же отправить payload. Это самый продуктивный режим работы.

## Шаг 20: полезные мелочи

`gdb.execute('info registers', to_string=True)` возвращает регистры строкой. `gdb.selected_frame()` даёт текущий фрейм. `gdb.newest_frame()` — самый свежий. Эти мелочи экономят много строк кода при написании собственных команд.

## Шаг 21: типичные ошибки

Первая — забыть `return False` в логирующем breakpoint (программа остановится). Вторая — читать невалидную память. Третья — забыть `to_string=True` и получить вывод в консоль вместо строки. Четвёртая — не проверять, что символ существует.

## Шаг 22: мини-проект

Напиши gdb-скрипт, который автоматически находит оффсет до возвратного адреса: перебирает длины payload, ставит breakpoint на `ret`, смотрит, перезаписался ли `rip`. Это упражнение объединяет breakpoints, память, перебор и отладку.

## Шаг 23: итог

gdb — это не только интерактивный отладчик, но и программируемая платформа. Python-скрипты превращают рутинную отладку в автоматический анализ, а связка с pwntools делает работу над pwn-задачей цельной. Помни главное: если ты вводишь одну и ту же команду дважды — это кандидат на скрипт.

## Шаг 24: gdb-скрипты в реальных задачах

В реальных pwn-задачах gdb-скриптинг экономит часы: автоматический поиск оффсета, логирование вызовов функций, дампы памяти в точках останова. В реверсе он помогает трассировать изменения переменных и находить логику проверки. Один раз написанный скрипт переиспользуется в десятках задач.

## Шаг 25: как учиться дальше

Читай примеры скриптов в документации gdb и в репозиториях CTF-команд. Начни с простого: логирующий breakpoint, затем пользовательская команда, затем связка с pwntools. Каждый шаг добавляет по одному инструменту к твоему набору.

## Шаг 26: финальный совет

Отладка — это не «нажимать si сто раз», а задавать вопросы и автоматически получать ответы. Если ты задаёшь один и тот же вопрос вручную — напиши скрипт. Так отладка превращается из рутины в исследование, а исследование — в решённые задачи.

## Шаг 27: частые вопросы

Почему скрипт работает под `gdb -x`, но не в pwntools? Потому что pwntools запускает gdb через API, и часть команд недоступна без `api=True`. Почему breakpoint не срабатывает? Скорее всего, адрес не исполняется или функция инлайнится. Почему память «пустая»? Адрес невалиден или ещё не инициализирован. Все три вопроса решаются отладочным выводом внутри скрипта.

## Шаг 28: практический пример — логирование вызовов

Предположим, нужно понять, с какими аргументами программа вызывает `read`. Скрипт:

```python
class LogRead(gdb.Breakpoint):
    def stop(self):
        buf = int(gdb.parse_and_eval('$rsi'))
        n = int(gdb.parse_and_eval('$rdx'))
        print('read(buf=%#x, n=%d)' % (buf, n))
        return False
LogRead('read')
gdb.execute('continue')
```

Запустив это, ты увидишь все вызовы `read` с аргументами — без единого ручного шага. Такой лог сразу показывает, куда программа пишет ввод и сколько байт ждёт. Это одна из самых частых задач при отладке эксплойта.

## Шаг 29: закрепление

Напиши скрипт, который при каждом вызове целевой функции печатает её аргументы и первые 16 байт памяти по указателю. Прогони на учебном бинаре и убедись, что видишь поток данных. Это упражнение закрепляет breakpoints, чтение памяти и `parse_and_eval` — три опоры gdb-скриптинга.
