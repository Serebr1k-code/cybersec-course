## Что такое git-форензика

Git-форензика — это восстановление информации из репозитория, включая данные, которые «удалили». Ключевая особенность git в том, что он почти ничего не удаляет по-настоящему: коммиты остаются в reflog и как «висячие» объекты, старые версии файлов живут в объектной базе, а секреты, случайно закоммиченные и затем удалённые, всё ещё извлекаемы. В CTF и в реальном пентесте это золотая жила: разработчики часто коммитят пароли, ключи, токены, а потом «чистят» историю, не понимая, что данные остались.

## Базовая разведка репозитория

```bash
git log --oneline --all --graph          # вся история, все ветки
git reflog                               # журнал перемещений HEAD
git branch -a                            # все ветки, включая удалённые
git tag -l                               # теги
git stash list                           # спрятанные изменения
git fsck --lost-found                    # висячие объекты
```

`git reflog` — важнейший источник: он показывает коммиты, которые уже недостижимы из веток, но всё ещё в базе.

## Просмотр объектов напрямую

Git хранит всё как объекты: blob (содержимое файла), tree (каталог), commit, tag. Их можно читать напрямую:

```bash
git cat-file -t <sha>          # тип объекта
git cat-file -p <sha>          # содержимое
git rev-list --objects --all   # все объекты истории
git rev-list --objects --all | git cat-file --batch-check='%(objecttype) %(objectname) %(rest)'
```

Если вы нашли висячий blob, читайте его через `git cat-file -p`.

## Поиск секретов в истории

```bash
# искать строки во всех версиях всех файлов
git log -p --all | grep -iE 'password|secret|token|api[_-]?key|BEGIN (RSA|OPENSSH)'

# искать в конкретном файле по всей истории
git log -p --all -- config.php | grep -i pass

# перебрать все блобы на предмет секретов
git rev-list --all --objects | awk '{print $1}' \
  | git cat-file --batch | strings | grep -iE 'flag\{|password'
```

Специализированные инструменты: `trufflehog`, `gitleaks`, `git-secrets` — они сканируют всю историю на известные паттерны.

## Извлечение удалённого файла

Если файл существовал в старом коммите, но удалён:

```bash
git log --all --full-history -- path/to/secret.txt
git show <commit>:path/to/secret.txt > recovered.txt
```

Для файла из висячего объекта:

```bash
git fsck --unreachable | grep blob
git cat-file -p <blob-sha>
```

## Анализ packfiles

Объекты git часто упакованы в `.git/objects/pack/*.pack`. Их можно распаковать:

```bash
git verify-pack -v .git/objects/pack/*.idx | sort -k3 -n | tail
git unpack-objects < .git/objects/pack/*.pack
```

`verify-pack` покажет все объекты с размерами; большие блобы часто и есть искомый секрет.

## Восстановление из reflog

```bash
git reflog
# e.g. HEAD@{3}: commit: add config
git show HEAD@{3}
git checkout HEAD@{3}
```

Даже если ветку удалили, `reflog` помнит её вершину, и коммит можно вернуть.

## Типичные ошибки и подводные камни

- **Искать только в текущем дереве** — секрет обычно в истории.
- **Игнорировать reflog** — там самые «свежие» удалённые коммиты.
- **Не проверять удалённые ветки** — `git fetch --all` перед анализом.
- **Забыть про stash** — `git stash list` и `git stash show -p`.
- **Смотреть только текстовые файлы** — секреты бывают в бинарях.
- **Путать blob и путь** — blob не имеет имени, имя даёт tree.

## Что дальше / решение

План действий: получив репозиторий, прогоните `git log --all`, `git reflog`, `git fsck`, `git branch -a`, `git stash list` — это покроет 80% находок. Затем поиск секретов по всей истории (`git log -p --all | grep`), а для глубокого анализа — `trufflehog`/`gitleaks`. Удалённые файлы восстанавливайте через `git show SHA:path`. Помните: git почти ничего не забывает, и ваша задача — найти то, что спрятали, но не удалили по-настоящему.

## Практический пример: восстановление пароля из истории

Разберём сквозной сценарий. Вам дали архив с репозиторием, где флаг спрятан в удалённом конфиге. Порядок действий: распаковываем архив, заходим в каталог, запускаем `git log --all --oneline` — видим пять коммитов. Делаем `git reflog`, и там оказывается коммит, которого нет в ветках: `HEAD@{2}: commit: remove secrets`. Читаем его содержимое: `git show HEAD@{2}` — видим удалённый `config.ini` с паролем. Если бы его не было в reflog, шли бы через `git fsck --lost-found`, нашли висячий blob и прочитали его через `git cat-file -p`. Ещё один путь — `git log -p --all | grep -i password`, который просто печатает все строки всех версий файлов, где встречается слово «password».

Этот пример показывает главное: одну и ту же находку обычно можно достать несколькими способами, и правильная стратегия — идти от простого к сложному: сначала `log/reflog/grep`, затем `fsck`, затем ручной разбор объектов и packfiles. Не начинайте с самого сложного — это тратит время.

## Частые вопросы

Первый вопрос, который возникает: «а если `.git` перепакован и старые объекты недостижимы?» Даже после `git gc` объекты обычно остаются, если на них есть ссылки в reflog; полностью они исчезают только при `gc --prune=now --aggressive`. Второй вопрос: «как искать секрет, если он в бинарном файле?» — извлекайте blob через `git cat-file -p` и прогоняйте `strings`. Третий: «что если репозиторий не открывается git'ом?» — распаковывайте объекты вручную через `zlib`. Четвёртый: «как не сломать улики?» — всегда работайте на копии.

## Что дальше / решение

Итог практики: используйте каскад инструментов (log → reflog → fsck → ручной разбор), сохраняйте промежуточные находки, работайте на копии репозитория. Помните, что git — это объектное хранилище по хешам, и «удаление» в нём почти всегда условно. Навык читать объекты напрямую отличает специалиста по git-форензике от пользователя, который знает лишь `git log`.

## Частые вопросы по git-форензике

«Историю переписали — всё потеряно?» — нет, смотрите reflog и `refs/original`. «Как найти удалённую ветку?» — `git reflog` → `git branch name <sha>`. «А если объекты перепакованы?» — `git verify-pack` и `git unpack-objects`. «Что если `.git` повреждён?» — распаковывайте объекты вручную через `zlib`. «Как не сломать улики?» — работайте на копии. «Помогает ли `git log -p`?» — да, это самый быстрый способ найти секреты в истории. Главное правило: git почти ничего не удаляет по-настоящему, поэтому «удалённое» почти всегда восстановимо.
