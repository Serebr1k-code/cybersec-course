## Вопрос, с которого всё начинается

Задача даёт архив с репозиторием `project/`. В условии сказано: «разработчик случайно закоммитил пароль, потом удалил файл». Открываешь — в рабочем дереве никакого пароля нет. Где его искать?

## Наш пример: репозиторий project

Распаковываем архив и заходим внутрь:

```
$ unzip project.zip && cd project
$ ls -a
.  ..  .git  README.md
```

Видим только `README.md` и скрытый каталог `.git`. Смотрим историю коммитов:

```
$ git log --oneline --all
a1b2c3d (HEAD -> main) remove secrets
f4e5d6c add config
```

Два коммита. Второй называется `remove secrets` — уже подозрительно. Но команда `git log` показывает только те коммиты, что достижимы из веток. Секрет может лежать глубже, поэтому идём дальше.

## Шаг 1: что вообще хранит git

Ключевая мысль: git — это база данных объектов, а не просто «контроль версий». Каждый коммит, каждый файл и каждый каталог — отдельный объект, адресуемый хэшем. И git почти **ничего не удаляет по-настоящему**: коммит, ставший недостижимым, остаётся в базе как «висячий» (dangling), пока не сработает агрессивная сборка мусора.

Объекты четырёх типов:

- **blob** — содержимое файла;
- **tree** — каталог: список имён и ссылок на blob/tree;
- **commit** — снимок: ссылка на tree, родители и метаданные;
- **tag** — аннотированный тег.

Поэтому «удалённый» пароль обычно никуда не делся.

## Шаг 2: reflog — журнал перемещений

Самое ценное — **reflog**: журнал всех перемещений указателя `HEAD`. Даже если коммит пропал из ветки после `reset`, `amend` или `rebase`, запись о нём остаётся:

```
$ git reflog
a1b2c3d (HEAD -> main) HEAD@{0}: commit: remove secrets
f4e5d6c HEAD@{1}: commit: add config
9d8e7f6 HEAD@{2}: commit: remove secrets
```

Здесь видно `HEAD@{2}` — коммит `9d8e7f6`, которого нет ни в одной ветке. Читаем его:

```
$ git show 9d8e7f6
commit 9d8e7f6...
    add config

diff --git a/config.ini b/config.ini
+db_password = S3cr3tP@ss
```

Пароль найден. Команда `git show <ref>` печатает и метаданные коммита, и его изменения.

## Шаг 3: ищем по всей истории

Если reflog уже почищен, идём через `git fsck`, которая проверяет целостность базы и показывает недостижимые объекты:

```
$ git fsck --lost-found
dangling blob 3f1a2b4c...
dangling commit 7c8d9e0f...
```

Найденные объекты читаются напрямую:

```
$ git cat-file -p 3f1a2b4c...
DB_PASSWORD=supersecret
```

`git cat-file -p <хэш>` печатает содержимое объекта. Для blob это просто данные файла, для commit — метаданные и tree.

Ещё один быстрый путь — искать строку по всем версиям всех файлов:

```
$ git log -p --all | grep -iE 'password|secret|token|api[_-]?key'
+db_password = S3cr3tP@ss
```

Флаг `-p` печатает патчи (изменения) каждого коммита, `--all` берёт все ветки. Так секрет виден, даже если файл уже удалён из текущего дерева.

## Шаг 4: восстанавливаем удалённый файл

Когда нужно вернуть сам файл, а не строку:

```
$ git show f4e5d6c:config.ini > recovered.ini
$ cat recovered.ini
db_password = S3cr3tP@ss
```

Конструкция `<коммит>:<путь>` достаёт файл по указанному пути в указанном коммите. Для висячего blob файл берут через `git cat-file -p <хэш>`.

## Шаг 5: если объекты в packfile

Иногда после `git gc` объекты упакованы в `.git/objects/pack/*.pack`. Они по-прежнему доступны:

```
$ git verify-pack -v .git/objects/pack/pack-*.idx | sort -k3 -n | tail -3
3f1a2b4c... blob   42 51 1234
7c8d9e0f... commit 220 300 5678
```

Третья колонка — размер объекта; крупные blob'ы часто и есть искомые файлы. Распаковать всё обратно в отдельные объекты можно командой `git unpack-objects < pack-*.pack`.

## Шаг 6: если утёк только .git

В web-задачах каталог `.git` иногда оказывается доступен по HTTP: `http://target/.git/`. Тогда репозиторий целиком скачивают и анализируют локально:

```
$ git-dumper http://target/.git/ out/
$ cd out && git log --all --oneline
```

Утилита `git-dumper` рекурсивно обходит `.git` и собирает объекты, ссылки и `config`. После этого работают все обычные команды. Это классическая утечка: `.git` в web-root отдаёт исходники и секреты.

## Полный прогон от начала до конца

Соберём всё в одну историю. На входе — `project/`, где пароль «удалили».

1. `git log --all --oneline` — видим коммит `remove secrets`.
2. `git reflog` — находим `HEAD@{2}` с потерянным коммитом.
3. `git show HEAD@{2}` — читаем патч, находим пароль.
4. Если reflog пуст: `git fsck --lost-found` → висячий blob → `git cat-file -p`.
5. Если ничего не видно: `git log -p --all | grep -i password`.
6. Файл нужен целиком: `git show <коммит>:config.ini`.

Порядок «от простого к сложному» (log → reflog → grep → fsck → ручной разбор) экономит время: не начинайте с самого сложного пути.

## Шаг 7: точечный поиск по строке

Когда известно, что искать (например, имя переменной `db_password`), помогает «pickaxe» — флаг `-S` у `git log` ищет коммиты, где менялось число вхождений строки:

```
$ git log -S 'db_password' --all --oneline
f4e5d6c add config
```

Так сразу видно, в каком коммите строка появилась. Близкий вариант — `-G` с регулярным выражением, он ловит любое изменение по шаблону. Это мощнее обычного `grep` по истории: pickaxe не печатает тонны лишнего, а указывает точный коммит.

Ещё один источник — метаданные. `git log --format='%h %an %ad %s'` даёт компактную сводку авторов и дат, по которой восстанавливают хронологию: кто и когда закоммитил секрет. Дата и автор — неизменяемые без перезаписи хэша улики, поэтому им можно доверять.

## Что мы теперь знаем

По-простому:

1. Git хранит данные как объекты по хэшам и почти ничего не удаляет.
2. `reflog` помнит коммиты, пропавшие из веток после `reset`/`amend`/`rebase`.
3. `git fsck --lost-found` находит висячие объекты; `git cat-file -p` их читает.
4. `git log -p --all | grep` быстро ищет секреты по всей истории.
5. `git show <коммит>:<путь>` восстанавливает удалённый файл.

## На что смотреть дальше

- **Искать только в рабочем дереве** — секрет почти всегда в истории, а не в текущих файлах.
- **Игнорировать reflog** — там самые «свежие» удалённые коммиты.
- **Забыть про stash** — `git stash list` и `git stash show -p` показывают отложенные изменения.
- **Не смотреть все ветки** — без `--all` теряются коммиты удалённых веток; перед анализом `git fetch --all`.
- **Считать, что packfile всё спрятал** — объекты в нём живы, их видно через `verify-pack`.

## Packfile: как искать в упакованных объектах

После `git gc` объекты схлопываются в `.pack`-файл, и просто «посмотреть файл» не
получится. Перечислить содержимое и найти нужный объект:

```bash
$ git verify-pack -v .git/objects/pack/pack-*.idx | head
$ git cat-file --batch-all-objects --batch-check | grep blob | wc -l
```

`verify-pack` показывает список объектов с типами и смещениями, `--batch-all-objects`
даёт перебор всех объектов. Чтобы найти секрет, соедините оба: получите список blob-хешей
и прогоните по ним `git cat-file -p` с фильтром по ключевым словам.

## git bisect: находим коммит-виновника

Когда неизвестно, в каком коммите что-то сломалось или появилось, помогает бинарный поиск:

```bash
$ git bisect start
$ git bisect bad HEAD
$ git bisect good v1.0
# git сам переключает коммиты; вы помечаете good/bad
$ git bisect reset
```

Для автоматизации пишут скрипт, который возвращает 0/1, и запускают
`git bisect run ./check.sh`. Это превращает поиск по сотням коммитов в считанные
проверки — быстрее, чем перебирать `git log -p` вручную.

## Теги и удалённые ветки

Секреты часто живут в ветках, которые «удалили» только локально. Всегда смотрите полную
картину:

```bash
$ git fetch --all
$ git branch -a
$ git tag -l
$ git log --all --oneline | head
```

Без `--all` и `fetch --all` вы видите лишь текущую ветку. Аннотированные теги хранят
коммит-объект с сообщением и датой — иногда в сообщении тега остаётся «временный» пароль.
Проверяйте и `git show <tag>`.

## .git/config и утечки

Сам конфиг репозитория — источник данных: URL с логином/паролем, имена remote, настройки
хуков:

```bash
$ cat .git/config
[remote "origin"]
    url = https://user:password@git.example.com/project.git
$ ls .git/hooks/*.sample
```

Учётные данные прямо в URL remote — частая находка при утечке `.git`. Если утёк только
каталог `.git` без рабочего дерева, объекты всё равно восстанавливаются (`git checkout .`
или `git cat-file`), поэтому `.git` на веб-сервере — это утечка всей истории, а не одного
файла.

## Работа с bare-репозиторием и объектами вне веток

Иногда на диске остаётся только `bare`-репозиторий (`project.git`) без рабочего дерева.
Он полностью пригоден для анализа:

```bash
$ git --git-dir=project.git log --all --oneline
$ git --git-dir=project.git cat-file -p HEAD
```

Объекты, не достижимые ни из одной ветки (после `filter-branch`, `rebase`, `gc`), лежат в
`lost-found` и в `refs/original`. Проверьте их отдельно:

```bash
$ git --git-dir=project.git fsck --unreachable
$ git --git-dir=project.git show <dangling-commit>
```

Даже если ветку удалили, объекты живут до следующего `gc` с `prune`. Поэтому «мы удалили
секрет и сделали force-push» почти никогда не означает, что секрет исчез из клона —
он остаётся в объектах до принудительной сборки мусора.

## Сканеры секретов: gitleaks и trufflehog

Ручной grep хорош, но для больших репозиториев есть специализированные сканеры, которые
проходят **всю** историю и знают шаблоны ключей:

```bash
$ gitleaks detect --source . --report-format json --report-path leaks.json
$ trufflehog git file://. --only-verified
```

`gitleaks` даёт отчёт с коммитом и строкой, `trufflehog` дополнительно проверяет, «живой»
ли найденный ключ. Это быстрее и полнее, чем `git log -p | grep`.

## Как правильно удалить секрет из истории

Если секрет всё-таки утёк, простого `git rm` недостаточно — объект остаётся в истории.
Удаляют перезаписью всей истории:

```bash
$ git filter-repo --invert-paths --path config.ini
$ git reflog expire --expire=now --all && git gc --prune=now --aggressive
```

После этого секрет нужно **сменить**: пока он в чужих клонах, перезапись не помогает.

## Что доказывает Git-форензика

Git — это **атрибутируемая** база: каждый объект подписан хэшем, а коммит хранит автора,
почту и дату. `git log --format` даёт неизменяемые (без перезаписи) улики — кто и когда
добавил секрет:

```bash
$ git log --all --format='%h %an %ae %ad %s' | head
```

## Если не сработало

- `git log` пуст → репозиторий склонирован без истории (`--depth 1`); ищите в `.git/objects`.
- reflog пуст → ищите через `git fsck --unreachable`.
- Объекты в pack → `git verify-pack` + `git cat-file --batch-all-objects`.
- Секрет в другом форке → сверьте `git remote -v` и историю удалённых веток.

## Куда дальше
