## Вопрос, с которого всё начинается

В CTF дают файл `polyglot.png`. Он честно открывается как картинка — `file` показывает PNG. Но в условии сказано, что внутри спрятан флаг. Как в картинке может лежать архив? Ответ — **полиглот**: файл, который **одновременно является валидным в нескольких форматах**. Один и тот же поток байт парсер PNG читает как изображение, а парсер ZIP — как архив, потому что они смотрят на разные участки файла.

Разберём это и соберём полиглот своими руками.

## Наш пример: polyglot.png

Сначала посмотрим на файл обычными инструментами:

```
$ file polyglot.png
polyglot.png: PNG image data, 1347093252 x 335544320, 0-bit grayscale
```

`file` распознал PNG по первым байтам. Но обрати внимание на «размеры» — числа абсурдные. `file` просто дочитал заголовок до байтов, которые на самом деле принадлежат **другому** формату. Значит, в файле есть вторая структура. Проверим архивную интерпретацию:

```
$ unzip -l polyglot.png
Archive:  polyglot.png
  Length      Date    Time    Name
---------  ---------- -----   ----
       14  2026-10-12 15:26   flag.txt
---------                     -------
       14                     1 file
```

Тот же файл `unzip` видит как ZIP с файлом `flag.txt`. Двойственность подтверждена.

## Шаг 1: почему файл бывает двумя форматами сразу

Форматы различаются тем, **откуда** парсер начинает читать:

- **PNG/JPEG/GIF** читаются **с начала**: первые байты — сигнатура (magic bytes). Всё, что идёт после корректной картинки, эти парсеры часто игнорируют.
- **ZIP** читается **с конца**: парсер ищет структуру **End of Central Directory** в хвосте файла и по ней находит все записи.
- **PDF** тоже ищется с конца (`%%EOF`), а мусор в начале допустим.

Отсюда классика: **картинка + ZIP** — картинка валидна с начала, архив валиден с конца. Никто не мешает одному файлу быть тем и другим.

## Шаг 2: собираем полиглот PNG+ZIP

Соберём полиглот программно: возьмём картинку и допишем к ней ZIP-архив с флагом.

```python
import zipfile, io
buf = io.BytesIO()
with zipfile.ZipFile(buf, "w") as z:
    z.writestr("flag.txt", "FLAG{p0lygl0t}")
png = open("cover.png", "rb").read()
open("polyglot.png", "wb").write(png + buf.getvalue())
```

Порядок принципиален: **ZIP дописывается в конец**, потому что его парсер ищет структуру с конца файла. Если поставить архив в начало, он сломает PNG-сигнатуру.

## Шаг 3: находим границу между форматами

Чтобы убедиться, что вторая структура есть, ищем сигнатуру ZIP (`PK\x03\x04`) внутри картинки:

```
$ grep -abo 'PK' polyglot.png | head -1
16:PK
```

Смещение `16` — ровно после PNG-заголовка (сигнатура PNG — 8 байт, плюс начало IHDR). Всё, что до `16`, — «картинка», всё после — «архив». `binwalk` сделал бы то же самое автоматически:

```
$ binwalk polyglot.png
DECIMAL    HEXADECIMAL   DESCRIPTION
0          0x0           PNG image, ...
16         0x10          Zip archive data
```

## Шаг 4: извлекаем вторую интерпретацию

Достаём файл из архивной интерпретации:

```
$ unzip -o polyglot.png flag.txt
Archive:  polyglot.png
 extracting: flag.txt
$ cat flag.txt
FLAG{p0lygl0t}
```

`unzip` предупредит про «16 extra bytes at beginning» — это как раз картинка перед архивом; он честно «попытается обработать всё равно» и извлечёт `flag.txt`. Альтернатива — вырезать архив вручную по смещению из `binwalk`:

```bash
$ dd if=polyglot.png bs=1 skip=16 of=out.zip
$ unzip out.zip
```

## Шаг 5: скриптовые полиглоты

Полиглотами бывают не только бинарные форматы, но и скрипты. Один файл может быть валидным и для `sh`, и для Python, если использовать строки-комментарии, которые «съедаются» в одном языке и активны в другом:

```python
#!/bin/sh
""":"
echo "я запустился как shell"
exit 0
" """
print("я запустился как python")
```

Как `sh`: первая строка — shebang, затем `""":"` открывает строку и печатает… на самом деле `sh` видит `echo`, выводит текст и делает `exit 0`. Как Python: вся конструкция `""":" … " """` — это одна строка в тройных кавычках, которую интерпретатор игнорирует, и выполняется `print`. Проверяй обе интерпретации: `sh file` и `python3 file`.

## Шаг 6: полиглоты в обходе загрузки файлов

Полиглот — не только CTF-игрушка. При загрузке файлов сервис часто проверяет **одно** свойство: расширение, `Content-Type` или магические байты. Если валидатор видит картинку, а исполнитель — скрипт, получается обход:

1. валидатор читает первые байты и видит `GIF89a` — «это картинка, пропускаем»;
2. сервер сохраняет файл и раздаёт его с исполнением (старый PHP `AddHandler`);
3. внутри — валидный код, который исполняется.

Исторический пример — **GIFAR**: GIF-файл, одновременно валидный как JAR-архив (ZIP). Браузер по MIME видел картинку, а Java-плагин — апплет. Вывод для тестирования: всегда проверяй, **какой именно** контроль стоит — по имени, по MIME, по сигнатуре или по содержимому целиком. Полиглот обходит контроли, которые смотрят только «начало» или только «расширение».

## Шаг 7: методика обнаружения

Для подозрительного файла действуй по порядку:

```bash
$ file suspect.bin              # что видит система
$ binwalk suspect.bin           # все вложенные сигнатуры
$ grep -abo 'PK' suspect.bin    # нет ли ZIP внутри
$ strings -n 6 suspect.bin | head
$ xxd suspect.bin | tail -5     # не спрятан ли архив в конце
```

Если `grep -abo 'PK'` находит смещение ZIP внутри картинки — перед тобой почти наверняка полиглот. Веди список проверок (`unzip -l`, `pdfinfo`, `identify`, `python3 -c`), и как только какая-то «оживает» — вторая интерпретация найдена.

## Если не сработало

Полиглот — файл, валидный в нескольких форматах. Не всегда вторая интерпретация очевидна. Разберём.

**Вторая сигнатура не находится.** Полиглоты бывают не только «два формата подряд», но и «пересекающиеся»: байты одного формата одновременно являются полями другого. Тогда ищи не вторую сигнатуру, а *смещение*, с которого файл читается иначе: `binwalk`, `foremost`, ручной осмотр по смещениям.

**ZIP-полиглот не распаковывается.** ZIP читается от **конца** (запись EOCD), поэтому его можно дописать после картинки. Но `unzip` может ругаться на «лишние» байты впереди. Используй `python -c "import zipfile; zipfile.ZipFile('f').extractall()"` — он читает корректно. Или `7z`, `bsdtar`.

**PDF-полиглот ломается.** PDF читается от начала и до `%%EOF`; лишние байты после могут игнорироваться или ломать просмотрщик. Проверь, что структура цела: `pdfid`, `qpdf --check`.

**Скриптовый полиглот не исполняется.** Формат-полиглот (картинка+ZIP) требует, чтобы интерпретатор скрипта игнорировал бинарный префикс (как `#!`-shebang). Если префикс ломает синтаксис — используй комментарии или строковые литералы, поглощающие мусор.

**Обход загрузки файлов не срабатывает.** Сервер может проверять не только magic bytes, но и структуру (парсит изображение). Тогда полиглот должен быть *валидным* изображением: реальный PNG с корректными чанками, внутри которого спрятан payload. Собирай не «мусор+ZIP», а настоящую картинку с внедрёнными данными.

## Частые вопросы

**Что такое полиглот простыми словами?** Один файл, который разные программы читают по-разному. Картинка, которая одновременно является архивом, или скрипт, который ещё и валидный PDF.

**Почему ZIP можно дописать после картинки?** ZIP ищет своё оглавление (EOCD) с конца файла. Картинки читают с начала и игнорируют хвост. Оба довольны.

**Как найти границу между форматами?** `binwalk` показывает смещения сигнатур. Можно резать файл (`dd`) по этим смещениям и проверять каждый кусок.

**Полиглоты реально используются в атаках?** Да — для обхода проверок загрузки (валидная картинка с вредоносным содержимым) и для доставки payload через фильтры, которые проверяют только начало файла.

## Как собирать и проверять полиглоты

Сборка идёт от формата, который читается с конца (ZIP), к формату, который читается с начала (PNG/PDF/GIF): сначала готовишь валидный «начальный» файл, затем дописываешь «конечный». Проверяешь каждый формат своим инструментом: `file`, `pngcheck`, `unzip -l`, `pdfinfo`. Если один из них ругается — полиглот собран неверно.

Для обхода проверок загрузки помни: сервер может валидировать не только magic bytes, но и структуру. Тогда полиглот должен быть *настоящим* изображением — с корректными чанками и размерами, внутри которого спрятан payload. Проверяй на том же парсере, что использует цель, — разные библиотеки терпимы к разному. И фиксируй точные смещения, чтобы воспроизвести сборку.

## Что мы теперь знаем

- **Полиглот** — файл, валидный в нескольких форматах одновременно.
- Форматы различаются точкой чтения: PNG/JPEG/GIF — **с начала**, ZIP/PDF — **с конца**.
- **PNG + ZIP**: картинка валидна с начала, архив — с конца; ZIP дописывают в конец.
- Границу между форматами находят по сигнатуре (`grep -abo PK`, `binwalk`).
- Вторую интерпретацию извлекают `unzip` или `dd` по смещению.
- **Скриптовые полиглоты** валидны для `sh` и `python` одновременно.
- В атаках полиглот обходит контроли загрузки, смотрящие только «начало» или «расширение».

## На что смотреть дальше

Помни, что `file` показывает только **первый** распознанный формат — полиглот их несколько. Всегда смотри и начало, и конец файла. Осторожно с сервисами, которые «нормализуют» или пережимают картинки: они уничтожают вторую интерпретацию, и полиглот не сработает. Дальше — `misc-side-channel-misc` и `misc-esoteric-obfuscation`.
