## Вопрос, с которого всё начинается

PCAP — это файл с записанными сетевыми пакетами. В сетевом пентесте его анализируют инструментами, но в CTF и misc он интересен с другой стороны: как **формат**, в котором можно спрятать данные и в котором встречаются нестандартные протоколы. Задача часто звучит так: «в дампе есть кастомный протокол — восстанови передачу». Разберём структуру PCAP и подход к нестандартным протоколам.

## Наш пример: заголовок .pcap

```
$ xxd -l 32 capture.pcap
00000000: d4c3 b2a1 0200 0400 0000 0000 0000 0000  ................
00000010: ffff 0000 0100 0000                      ........
```

`d4c3b2a1` — magic (little-endian PCAP). Далее — версия, таймзона, snaplen, link-type. Разберём, как читать пакеты.

## Шаг 1: структура PCAP

PCAP: глобальный заголовок (24 байта) и последовательность записей. Каждая запись: `ts_sec`, `ts_usec`, `incl_len`, `orig_len`, затем данные пакета. Link-type определяет, как интерпретировать данные (Ethernet, raw IP, Linux SLL и т.д.). Ошибка в link-type — частая причина «непонятного» дампа.

## Шаг 2: PCAPNG

Современный формат — PCAPNG: блоки (`SHB`, `IDB`, `EPB`, `SPB`, `NRB`), где интерфейсы описываются отдельно. Он богаче: несколько интерфейсов, комментарии, метаданные. Для разбора: `tshark`, `scapy`, `capinfos`. В CTF PCAPNG может содержать комментарии с данными или «неиспользуемые» блоки.

## Шаг 3: инкапсуляция

Внутри записи — кадр. Для Ethernet: MAC-адреса, ethertype, затем IP, затем TCP/UDP. IP может быть IPv4 или IPv6; транспорт — TCP/UDP/ICMP/другое. Для кастомных протоколов часто используется UDP с нестандартным портом, и «полезная нагрузка» — это и есть данные задачи.

## Шаг 4: нестандартные протоколы

В CTF любят «самодельные» протоколы: свой magic-байт, свой заголовок, своя логика (например, «каждый пакет несёт один символ»). Подход: отфильтровать поток по IP/порту (`tshark -Y`, `-z follow`), извлечь payload, посмотреть на структуру, найти паттерн. Часто данные кодируются в поле sequence number, в TTL, в размере пакета или в порядке пакетов.

## Шаг 5: скрытые каналы в pcap

Данные можно спрятать: в младших битах TTL, в опциях IP/TCP, в поле sequence, в размере пакетов, в порядке отправки, в «лишних» байтах после полезной нагрузки. Также можно спрятать файл в отдельном потоке (например, HTTP-ответ) или в комментарии PCAPNG. Всё это — covert channels, и pcap — их естественный носитель.

## Шаг 6: где искать баги

| Место | Что искать |
|---|---|
| link-type | неверная интерпретация |
| длины | несоответствие incl/orig |
| кастомный протокол | структура payload |
| скрытые каналы | TTL/seq/размер |
| комментарии | PCAPNG-блоки |
| несколько потоков | не тот поток |

## Полный прогон: кастомный протокол

Задача: в дампе есть UDP-поток на нестандартном порту, каждый пакет несёт один символ в первом байте payload. Нужно собрать сообщение.

```
$ tshark -r capture.pcap -Y 'udp.port==4444' -T fields -e udp.payload
6e 74 6f 7b ...
$ python3 collect.py
nto{pcap_cust0m_pr0t0c0l_r3c0v3r}
flag: nto{pcap_cust0m_pr0t0c0l_r3c0v3r}
```

Фильтрация по потоку + извлечение payload — базовый приём анализа дампов.

## Если не сработало

Если протокол «не тот», проверьте link-type (`capinfos`), другие порты, IPv6, фрагментацию, TCP-реассемблирование (`tshark -z follow,tcp`). Иногда данные в скрытых каналах: TTL, sequence, размеры. Проверьте PCAPNG-комментарии.

## Инструменты

- `tshark`/`wireshark` — основной анализ.
- `scapy` — разбор и генерация.
- `capinfos` — сводка о дампе.
- `tcpflow`/`ngrep` — извлечение потоков.

## Что мы теперь знаем

- PCAP: глобальный заголовок + записи пакетов.
- Link-type определяет интерпретацию кадра.
- PCAPNG — блочный формат с комментариями.
- Нестандартные протоколы ищут по потоку и payload.
- Скрытые каналы: TTL, seq, размер, порядок.
- `tshark -z follow` собирает потоки.

## Как читать pcap

Сначала `capinfos` (link-type, число пакетов). Затем — фильтрация по протоколу/порту. Затем — извлечение payload и поиск структуры. Для скрытых каналов — смотрите поля, которые обычно игнорируются.

## PCAPNG подробнее

PCAPNG состоит из блоков. Первый — Section Header Block (`SHB`, type `0x0A0D0D0A`), задающий порядок байтов и версию. Затем Interface Description Block (`IDB`, `0x00000001`) — описывает интерфейс (link-type, snaplen). Enhanced Packet Block (`EPB`, `0x00000006`) — сам пакет: interface id, timestamp, captured/original length, данные, плюс **опции** (комментарии, флаги). Simple Packet Block (`SPB`) — упрощённый. Name Resolution Block (`NRB`) — соответствия адресов именам. Ключевое для CTF: в **опциях** блоков можно хранить произвольные комментарии (`opt_comment`), которые не видны при обычном просмотре пакетов. `tshark` покажет их как `frame.comment`, но многие анализаторы игнорируют. Поэтому проверяйте опции и «неиспользуемые» блоки.

## Скрытые каналы в дампе

Помимо «пряток» в комментариях, есть классические covert channels. Первый: TTL — младшие биты кодируют байты (TTL обычно 64, 128; его младшие биты можно менять). Второй: TCP sequence number — произвольное 32-битное поле, в которое можно вписать данные. Третий: размер пакета — padding или изменение длины. Четвёртый: порядок пакетов — перестановка кодирует биты. Пятый: временные метки — интервалы кодируют данные. Шестой: опции IP/TCP. Седьмой: неиспользуемые биты в заголовках. Для обнаружения: сравнивайте поля с «нормальными» значениями, ищите закономерности, стройте гистограммы. `tshark -T fields -e ip.ttl` быстро покажет все TTL.

## Подход к нестандартному протоколу

Алгоритм: `capinfos` (link-type, число пакетов) → `tshark -q -z io,phs` (иерархия протоколов) → фильтрация по подозрительному потоку (`ip.addr==`, `udp.port==`) → извлечение payload (`-T fields -e data.data` или `-e udp.payload`) → анализ структуры. Часто payload имеет свой magic, длину, тип. Если данные «побиты» по пакетам, соберите их по порядку (seq/номер). Если используется TCP, примените `follow,tcp` для реассемблирования. Если IPv6 — не забудьте про расширенные заголовки. Если фрагментация — соберите фрагменты. Так вы восстановите любую передачу.

## Мини-практика: извлечение и сборка

Сгенерируйте в `scapy` дамп: несколько UDP-пакетов, каждый с одним символом флага в payload. Сохраните в pcap. Затем напишите скрипт: читает pcap (`rdpcap`), фильтрует по порту, сортирует по времени, собирает байты в строку. Убедитесь, что получился флаг. Затем усложните: спрячьте данные в TTL и напишите извлекатель. Это упражнение покрывает 90% CTF-задач с pcap.

## Итог

PCAP — контейнер записей пакетов, PCAPNG — блочный формат с опциями/комментариями. Link-type определяет интерпретацию. Нестандартные протоколы ищут по потоку и payload; данные могут лежать в скрытых каналах (TTL, seq, размер, порядок, timestamps, опции). Инструменты — `capinfos`, `tshark`, `scapy`. Для CTF достаточно научиться фильтровать поток и извлекать payload.

## Реассемблирование и фрагментация

Реальные дампы редко дают данные «одним куском». TCP-поток нужно реассемблировать: `tshark -z follow,tcp,ascii,0` собирает поток по сессии. IP-фрагменты нужно собрать по полю offset; `tshark` делает это автоматически, но при нестандартных заголовках может не справиться — тогда собирайте вручную. UDP не имеет реассемблирования, поэтому приложение само нумерует данные (в своём заголовке). Если данные «побиты», ищите в payload номер последовательности. IPv6-дампы могут содержать расширенные заголовки (Hop-by-Hop, Routing, Fragment) — их тоже нужно учитывать. Всё это — часть «разбора нестандартного протокола», и навык реассемблирования критичен для CTF.

## Сравнение с сетевым анализом

Важно отличать «misc»-подход к pcap от «network»-подхода. В сетевом пентесте pcap анализируют, чтобы найти атаку, креды, C2-трафик. В misc/CTF pcap — это носитель: данные спрятаны в структуре, в скрытых каналах, в кастомном протоколе. Инструменты одни (`tshark`, `scapy`), но цель разная. Поэтому в misc сначала смотрите на **формат** (link-type, блоки, поля), а потом на **содержимое** (payload, потоки). Часто задача решается на уровне формата, а не «сетевого смысла».

## Практический чек-лист

Проверьте: `capinfos` (link-type, формат); иерархию протоколов (`-z io,phs`); подозрительные потоки/порты; PCAPNG-опции и комментарии; скрытые каналы (TTL, seq, размер, порядок, timestamps); реассемблирование TCP; сборку фрагментов; IPv6-заголовки. Для CTF: найдите поток, извлеките payload, соберите данные. Это покрывает подавляющее большинство задач с дампами.

## Итог по формату

PCAP — контейнер записей, PCAPNG — блочный формат с опциями. Link-type определяет, как читать кадр. В misc-подходе pcap — это носитель: кастомные протоколы, скрытые каналы, комментарии. Инструменты — `capinfos`, `tshark`, `scapy`; базовые приёмы — фильтрация потока, извлечение payload, реассемблирование. Научившись собирать данные из дампа, вы решите большинство CTF-задач с трафиком.

## Последнее замечание

Отдельно стоит упомянуть «сырые» link-type: Linux SLL, SLL2, raw IP, 802.11. Если дамп снят не на Ethernet, а на loopback или на беспроводном интерфейсе, структура кадра другая, и парсер, ожидающий Ethernet-заголовок, «съедет». Всегда проверяйте link-type в `capinfos` прежде, чем интерпретировать байты. Это самая частая причина «непонятного» дампа в CTF и в реальной работе. И ещё: некоторые дампы обрезаны (snaplen), поэтому payload может быть короче исходного пакета — учитывайте это при сборке данных, иначе соберёте неполное сообщение.
