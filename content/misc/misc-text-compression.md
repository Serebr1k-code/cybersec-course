## Вопрос, с которого всё начинается

Тебе дали файл, в котором `file` говорит «data», `strings` ничего не находит, а размер подозрительно маленький. Похоже, текст сжат, но заголовка (как у gzip) нет. Как понять, чем он сжат, и распаковать? Разберём текстовые компрессоры.

## Наш пример

Возьмём строку `the quick brown fox`. Обычные компрессоры (gzip) хранят её как поток с заголовком `1f 8b`. А **smaz** — компрессор для коротких строк — кодирует частые слова как один байт. Заголовка нет: результат выглядит как случайные байты. Наша задача — научиться их узнавать.

## Шаг 1: зачем отдельный компрессор для текста

Общие компрессоры (zlib, gzip, lzma) рассчитаны на большие данные и добавляют заголовок с метаданными. Для **коротких** строк (URL, названия, SMS) накладные расходы заголовка больше выигрыша. Поэтому появились smaz и shrinker: они держат словарь частых подстрок и заменяют их кодами без заголовка. Сжатие хуже, зато результат компактный и без служебных байтов.

## Шаг 2: как распознать сжатие без заголовка

Признаки:
- **Энтропия**. Сжатые/зашифрованные данные имеют энтропию близко к 8 бит/байт. Текст — 4–5.
- **Отсутствие магии**. `file` не узнаёт формат.
- **Размер**. Меньше, чем ожидаемый текст.
- **Байтовое распределение**. В smaz-выводе много байтов с высокими значениями (часть словаря), мало пробелов.

Считаем энтропию скриптом на Python — это первый шаг.

## Шаг 3: smaz

smaz — словарный компрессор: ~250 частых подстрок кодируются одним байтом. Декомпрессор тривиален: читаешь байт, смотришь в таблице соответствующую строку, конкатенируешь. Если байт — код слова, берёшь слово; если — литерал, берёшь сам байт. Никаких заголовков и контрольных сумм.

## Шаг 4: shrinker и другие

Аналогично устроены другие текстовые компрессоры: словарь + код. Узнать конкретный можно по длине алфавита и по тому, какие байты встречаются. Часто проще всего: попробовать декомпрессоры по очереди и смотреть, получился ли осмысленный текст.

## Шаг 5: где это встречается

- CTF misc: «вот blob, распакуй».
- Мобильные приложения: smaz для экономии трафика.
- Форензика: сжатые поля в бинарных форматах.
- IoT: компактные протоколы.

## Шаг 6: как подходить

1. Посчитай энтропию — убедись, что это сжатие.
2. Проверь известные магии (`1f8b` gzip, `78 9c` zlib, `42 5a` bzip2, `fd 37 7a` xz).
3. Если магии нет — перебирай текстовые компрессоры (smaz, shrinker).
4. Пробуй `binwalk`, но помни: без заголовка он не поможет.

## Шаг 7: как защищаться

Защита тут не про атаку, а про устойчивость: если формат данных нестандартный, документируй его. Для безопасности важно другое: не доверять длине, проверять границы при распаковке (декомпрессия может «раздуться» — zip-bomb).

## Шаг 8: практический скрипт

Мини-детектор: читает файл, считает энтропию, выводит её и первые байты. Если энтропия > 7.5 и нет магии — вероятно, сжатие/шифрование. Если энтропия ~5, но текст не читается — вероятно, словарный компрессор. Это быстрая сортировка гипотез.

## Частые ошибки

- Ждать заголовок у каждого сжатого файла.
- Путать сжатие с шифрованием (оба дают высокую энтропию).
- Не считать энтропию, а сразу гадать формат.

## Что мы теперь знаем

- Сжатый текст может не иметь заголовка.
- Энтропия — главный признак сжатия/шифрования.
- smaz/shrinker — словарные компрессоры для коротких строк.
- Распознавание = энтропия + проверка магии + перебор декомпрессоров.
- Декомпрессия может раздуваться (риск zip-bomb).

## Точный расчёт энтропии Шеннона

Энтропия измеряет, сколько бит в среднем несёт один байт. Формула — `H = -Σ p_i · log2(p_i)`, где `p_i` — доля байтов со значением `i`. Для равномерно распределённых данных все 256 значений встречаются одинаково часто, `p_i = 1/256`, и `H = 8` бит. Для английского текста `H ≈ 4.2–5`, потому что буквы распределены неравномерно.

Считаем на Python:

```python
import math, collections
def entropy(b):
    c = collections.Counter(b)
    n = len(b)
    return -sum((v/n) * math.log2(v/n) for v in c.values())

data = open('blob.bin','rb').read()
print('entropy=%.2f' % entropy(data), 'first=', data[:16].hex())
```

Практические пороги: `H < 6` — скорее всего текст или структурированные данные; `6 < H < 7.5` — сжатый текст, словарный компрессор или частично структурированный бинарник; `H > 7.5` — почти наверняка сжатие общего назначения или шифрование. Это не приговор, а сортировка гипотез: сначала считаем энтропию, потом выбираем направление.

## Reference: магические заголовки компрессоров

Перед тем как перебирать, проверяем известные сигнатуры — они экономят массу времени:

| Формат | Первые байты (hex) |
|--------|--------------------|
| gzip | `1f 8b` |
| zlib | `78 01` / `78 9c` / `78 da` |
| bzip2 | `42 5a 68` (`BZh`) |
| xz | `fd 37 7a 58 5a 00` |
| zstd | `28 b5 2f fd` |
| lz4 | `04 22 4d 18` |
| lzma (raw) | часто `5d 00 00` |
| brotli | без магии, обычно `0b`/`1b`-подобные префиксы |
| smaz | магии нет |
| shrinker | магии нет |

Наличие магии сразу даёт команду (`gunzip`, `unxz`, `zstd -d`). Отсутствие — путь к словарным компрессорам.

## Как устроен smaz внутри

Словарь smaz — это таблица из ~254 записей. Коды `0x00`–`0xFE` (или близкий диапазон) указывают на подстроку словаря; специальный код `0xFF` (в оригинале — escape) означает «следующий байт — литерал», то есть сырой символ, которого нет в словаре. Декомпрессор читает поток и конкатенирует:

```python
def smaz_decompress(data, table):
    out = bytearray()
    for byte in data:
        if byte == 0xFF:
            continue  # следующий байт — литерал, обрабатываем ниже
        out += table[byte]
    return bytes(out)
```

Настоящая реализация обрабатывает escape-последовательности и многобайтовые коды, но идея именно такая: **таблица подстановки + редкие литералы**. Отсюда и признаки smaz-вывода: много байтов с высокими значениями (коды слов) и редкие «сырые» символы с escape.

## Worked example: распознаём неизвестный blob

Дано: файл 37 байт, `file` говорит `data`, `strings` пусто. Разбор по шагам:

```bash
$ wc -c blob.bin
37 blob.bin
$ xxd blob.bin | head -2
00000000: c1 83 41 02 9f 1d 44 ...
```

1. Энтропия оказалась 6.4 — не 8, значит не шифрование, а словарное сжатие.
2. Магии нет — gzip/zlib/bzip2 отпадают.
3. Байты распределены неравномерно, много значений > 0x80 — похоже на коды словаря.
4. Пробуем декомпрессор smaz → получаем осмысленный текст `the quick brown fox`.

Вывод: это smaz. Такой линейный разбор работает в 90 % случаев.

## Сжатие против шифрования

Оба дают высокую энтропию, и это главная путаница. Различия:

- **Структура.** Сжатые данные часто имеют повторяющиеся паттерны на больших смещениях; шифротекст статистически неотличим от случайного.
- **Длина.** Шифрование сохраняет длину (примерно) и добавляет IV/тег; сжатие обычно уменьшает.
- **Контекст.** Если рядом лежит ключ или описание формата — вероятно шифрование; если поле подписано «compressed» — сжатие.
- **Тесты.** Пробуем распаковать известными декомпрессорами: успех — сжатие; провал — шифрование.

На практике проверяют так: если `zlib.decompress` бросает ошибку на всех вариантах, но энтропия высокая — вероятно, шифрование или словарный компрессор.

## Zip-bomb: почему распаковка небезопасна

Декомпрессия может «раздуться» экспоненциально: 42 килобайта данных могут дать несколько гигабайт. Классический пример — вложенные gzip-архивы, где каждый слой распаковывается в следующий. Если распаковывать недоверенный файл «в лоб», можно исчерпать диск или память.

Защита: распаковывать в память с жёстким лимитом (`zlib.decompressobj().decompress(data, max_length=1<<20)`), ограничивать число слоёв, использовать таймаут. Никогда не распаковывайте недоверенные данные в файловую систему без контроля размера.

## Если не сработало

- **Ни один декомпрессор не подошёл.** Возможно, это не компрессия, а нестандартная кодировка (base85, braille) или шифрование. Вернитесь к этапу опознания алфавита.
- **Декомпрессор выдал мусор.** Попробуйте другой порядок байтов или другой вариант таблицы — словарные компрессоры часто имеют версии.
- **Энтропия ниже 4.** Это не сжатие — скорее всего текст или код, просто с непечатаемыми байтами. Посмотрите на структуру через `xxd`.
- **`binwalk` ничего не нашёл.** Ожидаемо: у словарных компрессоров нет сигнатур. `binwalk` ищет магии, а не энтропию.

## Ограничения

Энтропия — статистическая мера, она не доказывает тип сжатия. Высокая энтропия не отличает сжатие от шифрования, а низкая не исключает сжатия слабоструктурированных данных. Поэтому вывод всегда строится на совокупности признаков: энтропия, магия, распределение байтов, контекст и результат пробной декомпрессии.

## Итоговый алгоритм опознания

Соберём всё в короткий чек-лист, которым удобно пользоваться на задании: посчитать энтропию и длину; вывести первые 16 байт и сверить с таблицей магии; если магии нет и энтропия средняя — пробовать словарные декомпрессоры; если ни один не дал осмысленного текста — переходить к опознанию кодировки или шифрования. Такой порядок не даёт пропустить простые случаи и экономит время на сложных.
