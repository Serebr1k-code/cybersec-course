## Вопрос, с которого всё начинается

Сервис исполняет JavaScript в **Deno** — современном рантайме, который по умолчанию не даёт доступ ни к файлам, ни к сети. Пользовательский код запущен с `--allow-read=/tmp`. Задача: прочитать `/flag`. Прямое чтение запрещено. Есть ли выход?

Это урок про Deno, Bun и модель разрешений.

## Наш пример: Deno с ограничениями

```
$ deno run --allow-read=/tmp script.js
$ cat script.js
console.log(Deno.readTextFileSync('/flag'));
$ deno run --allow-read=/tmp script.js
error: Uncaught PermissionDenied: Requires read access to "/flag"
```

Deno отказал: `/flag` вне разрешённого каталога. Модель прав работает.

## Шаг 1: модель разрешений Deno

Deno по умолчанию **небезопасен наружу**: без флагов скрипт не может ни читать файлы, ни ходить в сеть, ни запускать процессы. Права выдаются явно:

| Флаг | Что разрешает |
|---|---|
| --allow-read[=path] | чтение файлов |
| --allow-write[=path] | запись файлов |
| --allow-net[=host] | сеть |
| --allow-env[=key] | переменные окружения |
| --allow-run[=cmd] | запуск процессов |
| --allow-ffi | вызов нативных библиотек |

Это **capability-модель**: не чёрный список, а белый. Поэтому обход — это поиск того, что флаг не покрыл, или того, что разрешено «слишком широко».

## Шаг 2: слишком широкие права

Права можно выдать шире, чем нужно. `--allow-read` без пути разрешает **всё**. `--allow-net` без хоста — любой домен. `--allow-run` — любую команду. Первая проверка песочницы: нет ли у скрипта прав, которые он не должен иметь. Часто в задачах дают `--allow-read=/` «для удобства» — и это уже не песочница.

## Шаг 3: FFI — дверь наружу

`--allow-ffi` разрешает вызывать нативные библиотеки, как в PHP/Java. Через FFI можно вызвать `system()` из libc и получить полный доступ:

```
const lib = Deno.dlopen('libc.so.6', { system: { parameters: ['buffer'], result: 'i32' } });
lib.symbols.system(new TextEncoder().encode('cat /flag\0'));
```

FFI обходит и файловые, и сетевые права: ограничения Deno не действуют на нативный код. Поэтому `--allow-ffi` почти всегда равен «без песочницы».

## Шаг 4: Node-совместимость

Deno и Bun поддерживают Node-API (`node:fs` и др.). Права при этом всё равно проверяются, но есть тонкости: некоторые пути Node-совместимости могут обходить проверки Deno (исторически такие баги находили). Для аудита важно: любые `node:`-модули — дополнительная поверхность.

## Шаг 5: Bun и его отличия

**Bun** — другой рантайм, быстрее, но модель безопасности иная: он ближе к Node и **не имеет** такой строгой песочницы по умолчанию. То есть «Deno-стиль» разрешений в Bun не работает. Если сервис на Bun, изоляция строится снаружи (контейнер, seccomp). Не путай: `--allow-*` — это Deno, не Bun.

## Шаг 6: импорт из сети

Deno умеет импортировать модули по URL (`import x from "https://..."`). Если это разрешено (нужен `--allow-net`), скрипт может подгрузить произвольный код. Это ещё один канал: не «прочитать флаг», а «исполнить чужой код», который затем обойдёт остальное.

## Полный прогон

```
$ cat perms.txt
deno run --allow-read=/tmp --allow-ffi script.js
$ # FFI разрешён -> нативный system() читает /flag
nto{d3n0_ff1_3sc4p3}
```

Ключ: `--allow-ffi` сделал файловые права бессмысленными.

## Как защищаться

- **Не давать `--allow-ffi`** и `--allow-run` без крайней необходимости.
- **Выдавать узкие пути** (`--allow-read=/tmp/app`), а не `--allow-read`.
- **Изолировать процесс** (контейнер/seccomp) — на случай обходов.
- **Bun изолировать снаружи** — у него нет Deno-песочницы.
- **Аудит `node:`-совместимости** — ищи обходы проверок.

## Что мы теперь знаем

- Deno использует capability-модель: права выдаются явно.
- Широкие права (`--allow-read`, `--allow-ffi`) ломают песочницу.
- FFI обходит все права, как в PHP/Java.
- Bun не имеет Deno-песочницы — изолируй снаружи.
- Импорт по URL — ещё один канал исполнения кода.

## Что реально покрывают права

Важно понимать границы каждого флага. `--allow-read=/tmp` разрешает читать только `/tmp`, но `--allow-read=/tmp,/etc` — уже два каталога. `--allow-net=api.example.com` разрешает соединения лишь к этому хосту, а `--allow-net` — ко всем. `--allow-env=HOME` даёт одну переменную, `--allow-env` — все. Каждый флаг без аргумента — это «разрешить всё в этой категории», и именно так песочницы чаще всего ломают: не обходом, а слишком широкой выдачей.

## Обход через --allow-run

Если разрешён запуск хотя бы одной программы, часто этого достаточно: разрешённая команда может сама читать файлы и сеть. `--allow-run=cat` даёт чтение любого файла, `--allow-run=sh` — почти полный контроль. Поэтому `--allow-run` почти так же опасен, как FFI, и его надо рассматривать как «песочницы нет».

## Утечка через переменные окружения

`--allow-env` без ключа выдаёт все переменные, включая токены и ключи. Даже без сети секрет можно вывести в stdout, а если есть `--allow-write` — записать в файл. Проверяй, что именно доступно скрипту: `Deno.env.toObject()`. В аудите это первый шаг после инвентаризации флагов.

## Сеть и DNS как каналы

При `--allow-net` скрипт может не только читать, но и отправлять данные — эксфильтрация. Если сеть закрыта, но разрешён `--allow-run`, данные уходят через запущенную команду. А если ничего не разрешено — остаётся только вывод в stdout, который видит вызывающий. Понимание каналов определяет, куда «утечёт» флаг в задаче.

## Как аудировать Deno-скрипт

Порядок: прочитай команду запуска и выпиши флаги; определи, какие из них «широкие»; проверь, использует ли скрипт FFI, `node:`-модули, импорт по URL; посмотри, есть ли `--allow-run`. Затем смоделируй: что скрипт может прочитать, куда записать, куда отправить. Часто вывод очевиден уже на шаге «выписал флаги».

## Bun: риски Node-совместимости

Bun стремится к совместимости с Node, а Node исторически не имеет песочницы. Значит, Bun-скрипт может использовать `child_process`, `fs`, `net` без явных разрешений — как в Node. Если сервис на Bun, изоляция обязана быть внешней. Не путай это с Deno: там те же модули требуют прав.

## Практический чеклист

Проверь по пунктам: нет ли `--allow-ffi`; нет ли `--allow-run` без нужды; узкие ли пути у read/write; ограничены ли хосты у net; выданы ли только нужные env; есть ли внешняя изоляция процесса. Каждый «нет» — конкретная рекомендация по ужесточению.

## Сравнение Deno, Node и Bun

Deno: безопасен по умолчанию, права явные, FFI опасен. Node: небезопасен по умолчанию, изоляция только внешняя. Bun: как Node, но быстрее; песочницы нет. Из этой таблицы следует простое правило: Deno можно ограничить изнутри, Node и Bun — только снаружи.

## Как проверить права в рантайме

Deno даёт API `Deno.permissions.query({name: "read", path: "/flag"})`, который вернёт `granted`, `denied` или `prompt`. Это удобно и для аудита, и для атаки: скрипт может сам узнать, что ему разрешено, и выбрать путь обхода. Если `--allow-ffi` включён, проверка прав становится бессмысленной, потому что нативный код обходит любые запросы. Поэтому первый вопрос при разборе: какой набор прав выдан и есть ли среди них «широкие».

## Практическая задача: утечка через stdout

В задачах Deno часто нельзя ни читать файлы, ни ходить в сеть, но можно печатать. Тогда флаг достаётся иначе: скрипт получает данные извне (например, через `--allow-env` или через аргументы), обрабатывает и печатает. Разбор начинается с вопроса «какой канал вывода доступен» — stdout всегда открыт. Если же разрешена запись, флаг можно сохранить в файл, который прочитает вызывающий.

## Изоляция на уровне ОС для Deno/Bun

Даже у Deno-песочницы есть слабые места, поэтому надёжнее добавить внешний слой: запускать процесс в контейнере без сети, с read-only корнем, непривилегированным пользователем, ограничением по памяти и seccomp-профилем. Тогда обход `--allow-*` (или отсутствие песочницы в Bun) не приведёт к утечке. Это тот же принцип, что и для Go: язык не гарантирует изоляцию — её даёт ОС.

## Ошибки конфигурации, которые всё ломают

Три частые ошибки: `--allow-read` без пути (читает всё); `--allow-ffi` «для плагинов»; `--allow-run` без указания команды. Любая из них сводит модель разрешений на нет. В аудите эти ошибки ищут в первую очередь — они встречаются чаще, чем реальные обходы. Исправление простое: сузить права до конкретных путей, хостов и команд.

## Итог и связь с другими песочницами

Deno — пример capability-модели: лучше чёрного списка, но не абсолют. Bun — пример «как Node»: песочницы нет. Общий вывод для всей ветки: языковая песочница полезна, но её всегда дополняют внешней изоляцией. Сравни этот урок с PHP и Java — увидишь, что проблема одна: язык богаче списка ограничений.

## Практический вывод для защитника

Если ты отвечаешь за сервис на Deno, начни с ревизии флагов запуска: убери `--allow-ffi` и `--allow-run`, сузь пути и хосты, выдай минимум env. Затем добавь внешний слой — контейнер без сети и с read-only корнем. Такой набор защищает даже от будущих обходов, потому что обход песочницы языка не даёт выйти за пределы ОС-изоляции. Запомни порядок: сначала сузить права, потом изолировать процесс.

## Что проверить в Bun-сервисе

Для Bun ревизия другая: там нет флагов разрешений, поэтому смотри, какие модули использует код (`child_process`, `fs`, `net`). Любой вызов процессов или сети — потенциальный канал. Изоляция обязательна внешняя: контейнер, непривилегированный пользователь, egress-фильтр. Не полагайся на «безопасность по умолчанию» — в Bun её нет.

## Частый сценарий CTF

В задаче обычно дан `perms.txt` или команда запуска, и нужно понять, какое право лишнее. Ответ — то, которое «широкое»: `--allow-read` без пути, `--allow-ffi`, `--allow-run`. Дальше описываешь путь атаки: FFI вызывает `system`, или запущенная команда читает файл. Так задача решается анализом конфигурации, а не эксплуатацией.

## Итог урока

Deno даёт capability-модель, Bun — нет. Обе песочницы (и их отсутствие) обходятся либо широкими правами, либо FFI. Надёжная защита — узкие права плюс внешняя изоляция. Этот вывод объединяет весь модуль: языковая песочница — лишь один слой, и полагаться только на неё нельзя.
