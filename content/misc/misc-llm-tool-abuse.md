## Вопрос, с которого всё начинается

Современный LLM-агент не просто отвечает текстом — он **вызывает инструменты**: читает файлы, делает HTTP-запросы, отправляет письма, запускает команды. Модель решает, какой инструмент вызвать и с какими аргументами, а аргументы она берёт из диалога. Если аргументы не проверяются, пользователь может «попросить» агента прочитать чужой файл или сходить по внутреннему адресу. Как устроен этот канал и где он ломается?

## Наш пример: трасса агента

Вот лог вызовов агента:

```
$ cat agent_trace.txt
tool=read_file args={"path": "/home/user/notes.txt"} status=ok
tool=fetch_url args={"url": "https://example.com"} status=ok
tool=run_shell args={"cmd": "id"} status=denied
```

Каждая строка — один **вызов инструмента**: имя, аргументы (JSON) и статус. Здесь `read_file` отработал, `fetch_url` сходил в сеть, а `run_shell` отклонён. Теперь разберём механику.

## Шаг 1: что такое tool call

**Tool call** (вызов инструмента) — это структурированный запрос, который модель генерирует вместо обычного текста. Модель не выполняет действие сама — она формирует вызов, который исполняет **хост-приложение** (runtime агента). Формат обычно такой: имя функции и аргументы в JSON. Хост решает, доверять ли вызову.

## Шаг 2: откуда берутся аргументы

Ключевой момент: **аргументы приходят из пользовательского текста**. Пользователь пишет «прочитай файл `../../etc/passwd`», модель извлекает путь и формирует `read_file({"path": "../../etc/passwd"})`. Если хост слепо исполняет вызов, получается **path traversal** — выход за пределы разрешённого каталога. То же с URL: пользователь подсказывает внутренний адрес — и агент делает **SSRF**.

## Шаг 3: типовые уязвимости

- **Инъекция в аргументы** — пользователь управляет значением, которое попадает в опасное поле (путь, URL, команда).
- **Path traversal** — путь `../` выводит за пределы песочницы файлового инструмента.
- **SSRF** — `fetch_url` ходит на `localhost`/внутренние адреса, доступные только серверу.
- **Command injection** — если инструмент собирает команду из аргумента без экранирования.
- **Confused deputy** — агент имеет больше прав, чем пользователь, и выполняет привилегированное действие по просьбе непривилегированного.

## Шаг 4: confused deputy подробнее

Агент часто работает от имени **сервиса** с широкими правами (доступ к базе, к внутренней сети). Пользователь прав таких не имеет, но может «попросить» агента сделать что-то за него. Агент — это «заместитель», которого запутали: он использует свои полномочия по чужой указке. Это классическая проблема и в вебе, и в агентах.

## Шаг 5: цепочки инструментов

Опасность растёт, когда инструменты соединяют: один читает данные, другой отправляет их наружу. Атака становится цепочкой: «прочитай секрет» → «отправь его на мой сервер». Даже если каждый инструмент по отдельности «безопасен», вместе они образуют канал утечки.

## Шаг 6: защита

- **Валидация аргументов** — проверять тип, формат, диапазон, а не доверять модели.
- **Allow-list** — разрешать конкретные пути/домены, а не «любые».
- **Отдельные права** — у агента должно быть ровно столько прав, сколько нужно (least privilege).
- **Подтверждение** — опасные действия (запуск команд, отправка) требуют явного согласия.
- **Изоляция** — выполнять вызовы в песочнице (см. seccomp/namespaces).

## Шаг 7: практический порядок разбора

1. Собрать список инструментов и их аргументов.
2. Для каждого аргумента спросить: управляет ли им пользователь?
3. Проверить валидацию: путь, URL, команда.
4. Искать цепочки «прочитать → отправить».
5. Оценить права агента (confused deputy).

## Что мы теперь знаем

- Tool call — структурированный вызов функции, который исполняет хост.
- Аргументы приходят из пользовательского текста — это точка атаки.
- Типовые дыры: path traversal, SSRF, command injection, confused deputy.
- Цепочки инструментов образуют канал утечки.
- Защита: валидация, allow-list, least privilege, подтверждение, изоляция.
