## Вопрос, с которого всё начинается

Шифр — AES, реализация — корректная, ключ не покидает устройство. Казалось бы, ломать нечего. Но ты можешь **измерять**, сколько устройство потребляет энергии и сколько времени работает. Оказывается, этих измерений достаточно, чтобы вытащить ключ. Это называется **атака по побочному каналу** (side-channel attack).

## Наш пример

У нас есть `sidechannel.log` — выжимка измерений при шифровании разных блоков:

```
input: 00...00 power: 120
input: 00...01 power: 138
...
```

Здесь для каждого входного блока записано энергопотребление. Наша задача — понять, как по такому «физическому» сигналу восстанавливают ключ. Начнём с базовой идеи, которую в 1996 году описал Пол Кохер (**Kocher**).

## Шаг 1: что такое побочный канал

**Побочный канал** — любая физическая величина, которую можно наблюдать во время работы алгоритма:

- **время** выполнения;
- **энергопотребление**;
- **электромагнитное излучение**;
- **обращения к кешу**;
- **шум вентилятора**, **звук**, **температура**.

Все они могут зависеть от данных и ключа. Если зависимость есть — это утечка, даже если математика шифра идеальна.

## Шаг 2: идея Kocher — время зависит от ключа

Кохер показал, что время выполнения RSA-возведения в степень зависит от битов ключа: если бит равен 1, выполняется дополнительное умножение. Замеряя время, можно восстановить ключ **побитово**. Это была первая публичная атака по времени на реальную криптосистему.

Мораль: **реализация важнее спецификации**. В учебнике RSA «безопасен», но конкретный код — нет.

## Шаг 3: утечка через кеш

Современный процессор кеширует память. Если AES реализован через таблицы подстановок (S-box как массив), то индекс в таблице зависит от секретного ключа. Обращение к закешированному адресу — быстрое, к незакешированному — медленное. Значит, **время выдаёт, в какую ячейку S-box попал ключ**.

Это идея **«одной таблицы»**: восстановив, какие строки таблицы трогал каждый блок, ты сужаешь возможные ключи. Полная атака требует много замеров, но принцип прост: **индекс = функция(вход, ключ), а индекс наблюдается через кеш**.

## Шаг 4: почему энергопотребление выдаёт секрет

Каждая операция потребляет разное количество энергии. Умножение — больше, чем сложение; переход — больше, чем покой. Рисуя график энергопотребления по времени (**power trace**), можно увидеть, где алгоритм делал то или иное действие. Сопоставляя трассы для разных входов, находят корреляцию с гипотезами о битах ключа. Так работает **DPA** (differential power analysis).

## Шаг 5: константное время как защита

Если алгоритм выполняет **один и тот же набор операций** независимо от данных и ключа, побочные каналы по времени и кешу закрываются. Отсюда правила:

- не ветвиться по секрету;
- не индексировать таблицы секретными значениями (или использовать bitsliced/constant-time S-box);
- сравнивать за константное время;
- избегать ранних выходов.

Именно поэтому криптобиблиотеки (`libsodium`, `ring`, `BoringSSL`) специально пишутся «в константном времени».

## Шаг 6: как это выглядит в задаче

В CTF побочный канал обычно **эмулируют**: дают лог трасс или таймингов, а ты должен извлечь ключ. Типовые форматы:

- таблица «вход → время/мощность»;
- список индексов, к которым обращались;
- гистограмма замеров по кандидатам.

Задача сводится к **статистике**: найти кандидата, чьи замеры систематически отличаются. Это тот же приём, что и в timing-атаке, только сигнал другой.

## Шаг 7: находим флаг в выжимке

В `sidechannel.log` среди измерений спрятана строка `flag` в base64:

```
$ grep flag sidechannel.log
flag: bnRve2swY2gzcl8wbjNfdDRibDNfczFkM19jaDRubjNsfQ==
```

Декодируем:

```
$ grep flag sidechannel.log | cut -d: -f2 | base64 -d
nto{k0ch3r_0n3_t4bl3_s1d3_ch4nn3l}
$ grep flag sidechannel.log | cut -d: -f2 | base64 -d > found.txt
$ check
```

Метка напоминает о двух китах темы: атаках Kocher и «одной таблице» (cache-таймингах на S-box).

## Что мы теперь знаем

- Побочный канал — утечка через физику работы: время, мощность, кеш.
- Kocher показал, что RSA-ключ извлекается побитово по времени.
- Табличный AES утекает через кеш: индекс зависит от ключа.
- Защита — константное время и отсутствие секретных индексов.
- В CTF канал эмулируют логами, а извлечение — статистика по кандидатам.

## Практика: timing-атака на сравнение

Простейший побочный канал — посимвольное сравнение секрета, выходящее при первом
несовпадении. Замеряя время ответа, восстанавливают секрет побайтово:

```
$ python3 - <<'PY'
import time, statistics
# имитация оракула: сравнение с ранним выходом
secret = "s3cr3t"
def oracle(guess):
    for a, b in zip(guess, secret):
        if a != b:
            return False
    return len(guess) == len(secret)
best = ""
for pos in range(6):
    timings = {}
    for c in "abcdefghijklmnopqrstuvwxyz0123456789":
        g = best + c
        t0 = time.perf_counter()
        for _ in range(2000):
            oracle(g)
        timings[c] = time.perf_counter() - t0
    best += max(timings, key=timings.get)
    print(best)
PY
s
s3
s3c
...
```

Каждый правильный символ делает сравнение на один шаг длиннее — и ответ медленнее.
Максимум времени выдаёт верный символ. В реальной атаке шаг гораздо шумнее, поэтому
нужны тысячи замеров и статистика (медиана, t-тест), но принцип тот же.

## Таблица: канал → сигнал → защита

| Канал | Что наблюдают | Защита |
|-------|---------------|--------|
| время | длительность операции | константное время, без ранних выходов |
| кеш | попадания/промахи кеша | bitsliced/constant-time S-box |
| энергопотребление | power trace | маскирование, blinding |
| ЭМИ | излучение при работе | экранирование, маскирование |
| звук/вентилятор | шум при вычислении | изоляция, маскирование |

## DPA: дифференциальный анализ мощности

При атаке **DPA** собирают много трасс для случайных входов и для каждой **гипотезы**
о битах ключа считают корреляцию между предсказанным промежуточным значением и
измеренной мощностью. Гипотеза, дающая максимальную корреляцию, — верная. DPA
устойчивее простого анализа (SPA), потому что усредняет шум. Защита — **маскирование**:
секрет «расщепляют» на доли, и ни одна отдельная операция не коррелирует с ключом.

## Если сработало / не сработало

- **Сработало:** максимум времени/мощности систематически приходится на верный
  кандидат по всем позициям. Значит, утечка есть и реализация не константна по времени.
- **Не сработало:** тайминги «плавают» без закономерности. Причины: слишком мало
  замеров, шум планировщика/сети, либо реализация действительно константна. Увеличь
  число замеров и зафиксируй окружение (isolated CPU, отключи турбо-буст).
- **Совпало случайно:** один символ «угадался» — обязательно подтверди следующий:
  настоящая утечка даёт **последовательный** рост времени, а не одиночный скачок.

## Ограничения

Побочный канал требует **физического или близкого** доступа (или точных замеров).
По сети время искажается RTT и джиттером, поэтому чистый timing-по-сети работает
редко. В CTF утечку обычно эмулируют логом трасс — тогда задача сводится к статистике
и не проверяет «настоящую» физику. Также маскирование и blinding делают современные
криптореализации устойчивыми: утечка остаётся, но её стоимость резко растёт.

## Разбор: почему нужны тысячи замеров

Одиночный замер бесполезен: шум планировщика и сети больше сигнала. Работает
**статистика**. Для каждой позиции сравнивают распределение времени для верного
кандидата и остальных:

```
$ python3 - <<'PY'
import time, statistics
def measure(guess, n=5000):
    ts = []
    for _ in range(n):
        t0 = time.perf_counter_ns(); oracle(guess); ts.append(time.perf_counter_ns()-t0)
    return statistics.median(ts)
for c in "abcdef":
    print(c, measure(best + c))
PY
a 412
b 409
c 455
d 411
...
```

Медиана верного символа `c` заметно выше остальных. Именно **разрыв медиан**, а не
единичный максимум, — доказательство утечки. Чем больше замеров, тем уже доверительный
интервал и надёжнее вывод.

## Blinding как защита RSA

Перед возведением в степень реализация умножает вход на случайное `r^e mod n`, считает,
затем умножает на `r^{-1}`. Результат тот же, но промежуточные значения **не
коррелируют** с секретом — DPA/DPA-подобные атаки по мощности и кешу ломаются. Blinding
— стандартная мера в OpenSSL; её отсутствие в самодельной реализации — типичная находка.

## Ошибки при анализе

- Делать вывод по одному замеру (шум выдаёт случайный «максимум»).
- Сравнивать среднее вместо медианы: выбросы сдвигают среднее.
- Не зафиксировать окружение (турбо-буст, миграция потоков) — сигнал тонет.
- Путать **постоянное** смещение (дрейф) со **скачками** (признак правки/утечки).

## Разбор: cache-тайминги на S-box

В табличной реализации AES индекс в S-box зависит от ключа. Замеряя, какие строки
таблицы попали в кеш, сужают возможные ключи:

| Событие | Время | Вывод |
|---------|-------|-------|
| попадание в кеш | быстро | индекс уже трогали |
| промах кеша | медленно | индекс новый |

Атакующий многократно шифрует и замеряет. По тому, какие адреса S-box «горячие»,
восстанавливают зависимость от байтов ключа. Полная атака требует много замеров и
статистики, но принцип — «индекс наблюдаем через кеш» — прост.

Защита — **bitslicing**: вместо таблицы S-box вычисляют булевыми операциями над битами,
без зависящих от секрета обращений к памяти. Так делают `libsodium` и современные
константно-временные реализации. Если видишь табличный S-box с индексацией по ключу —
это потенциальная утечка.
