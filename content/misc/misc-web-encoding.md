В вебе данные проходят через несколько слоёв кодирования: URL-encoding, HTML-entities, JS-escape, base64. Каждый слой — это и возможность представить один и тот же символ по-разному. Расхождение между «проверкой» и «использованием» после декодирования — источник багов. В misc это встречается в задачах про обход фильтров и WAF.

## URL-encoding

`%XX` — hex-код байта. `%41` = `A`, `%20` = пробел, `%2F` = `/`, `%00` = null.

```bash
python3 -c "import urllib.parse;print(urllib.parse.quote('/etc/passwd'))"
# %2Fetc%2Fpasswd
python3 -c "import urllib.parse;print(urllib.parse.unquote('%2Fetc%2Fpasswd'))"
# /etc/passwd
```

Особенности:

- `+` в `application/x-www-form-urlencoded` означает пробел;
- двойное кодирование: `%252F` → после первого декода `%2F` → после второго `/`;
- серверы декодируют по-разному: некоторые один раз, некоторые несколько.

## HTML-entities

В HTML символы можно записать как `&amp;`, `&#65;` (`A`), `&#x41;` (`A`). Браузер декодирует их при рендеринге. Если валидатор проверяет «сырой» ввод, а браузер декодирует — обход.

```html
&lt;script&gt;alert(1)&lt;/script&gt;
&#x3c;script&#x3e;alert(1)&#x3c;/script&#x3e;
```

## JS-кодирование

В JavaScript строки можно записать через `\x41` (`A`), `\u0041` (`A`), `\u{41}`. Это используется для обхода фильтров, которые ищут буквальные символы.

```javascript
\u0061lert(1)       // alert(1)
\x61lert(1)
String.fromCharCode(97,108,101,114,116)
```

## Base64 и его варианты

В web base64 прячется в data-URL, JWT, cookie. Варианты: base64url (`-`/`_`), отсутствие padding, двойной base64. В задачах проверяйте длину (кратна 4) и алфавит.

## Юникод-нормализация

Один и тот же символ можно представить разными код-пойнтами; после нормализации (NFC/NFKC) они становятся одинаковыми. Это ломает фильтры:

```python
import unicodedata
s1 = "admin"                       # обычные буквы
s2 = "аdmin"                       # первая буква — кириллическая 'а'
print(s1 == s2)                    # False
print(unicodedata.normalize('NFKC', s2) == s1)  # зависит от символов
```

Также: гомоглифы (визуально похожие символы), zero-width символы (`\u200b`), RTL-override (`\u202e`) для «переворота» текста.

## Обход WAF и фильтров

| Фильтр | Обход |
|--------|-------|
| `../` | `..%2f`, `..%252f`, `....//`, `..\/` |
| `<script>` | `&#x3c;script&#x3e;`, `\u003cscript` |
| пробел | `%20`, `+`, `\t`, `${IFS}` |
| кавычки | юникод-эквиваленты, backticks |
| ключевое слово | регистр, комментарии `/**/`, конкатенация |
| `SELECT` | `SeLeCt`, `SEL/**/ECT` |
| `%00` | обрезка в C-функциях (null-byte) |

## Разобранный пример

Задача: path traversal, но `../` фильтруется.

```bash
curl 'http://chal.local/read?file=../../etc/passwd'
# blocked
curl 'http://chal.local/read?file=..%2f..%2fetc%2fpasswd'
# blocked (декодируется и проверяется)
curl 'http://chal.local/read?file=..%252f..%252fetc%252fpasswd'
# flag — двойное кодирование обошло проверку
```

Проверяющий слой декодировал один раз (увидел `%2f`, не `/`), а файловая система/бэкенд декодировал второй раз и получил `../`.

## Инструменты

- Burp Suite (Repeater, Intruder) — ручной перебор кодировок.
- `ffuf` с wordlist кодировок.
- Python `urllib`, `html`, `codecs` — преобразования.
- CyberChef — цепочки декодирований.

```bash
python3 - <<'EOF'
import urllib.parse
payload = '../../etc/passwd'
for n in range(1,4):
    payload = urllib.parse.quote(payload, safe='')
    print(n, payload)
EOF
```

## Частые ошибки и подводные камни

- Декодировать только один раз, когда сервер делает два (или наоборот).
- Забывать про `+` как пробел в form-encoding.
- Игнорировать регистр и юникод-эквиваленты.
- Не проверять, какой слой декодирует первым (WAF vs backend).
- Считать, что `%00` везде обрезает строку — зависит от языка/функции.
- Путать HTML-entities (клиент) и URL-encoding (сервер) — разные контексты.

## Дополнительная теория: канонизация и двойное декодирование

В основе всех этих обходов лежит понятие **канонизации** — приведения входа к единственному «нормальному» виду перед проверкой. Если канонизация неполная или порядок операций неверен, между проверкой и использованием появляется зазор. Классический пример — двойное декодирование: WAF декодирует URL один раз и проверяет результат, а бэкенд декодирует ещё раз и получает опасный символ. Отсюда `%252e%252e%252f` превращается в `../`. Другой пример — **Unicode-нормализация**: строка `%c0%ae` (overlong-кодирование точки) в некоторых реализациях нормализуется в `.`, обходя фильтр, который ищет буквальную точку.

Порядок операций критичен. Если система сначала проверяет длину, потом декодирует — можно передать короткий закодированный payload, который развернётся в длинный. Если сначала декодирует, потом проверяет длину — это безопаснее. Понимание конвейера «приём → декодирование → проверка → использование» позволяет предсказать, где искать дыру. В CTF полезно нарисовать этот конвейер и отметить, какие преобразования применяет каждый слой.

## Таблицы кодировок и совместимость

Разные контексты ожидают разные кодировки. В URL-пути `/` можно закодировать как `%2f`, но некоторые серверы не декодируют `%2f` в пути, чтобы не путать сегменты. В query-параметрах `+` означает пробел, в пути — буквальный `+`. В JSON-строках `\u0041` — это `A`, но `\x41` невалидно. В HTML атрибутах кавычки экранируются как `&quot;`, а в тексте — как `&amp;`. В JavaScript внутри `<script>` опасны `</script>`, поэтому их кодируют как `\u003c/script\u003e`. Знание того, какой декодер сработает в каком контексте, — ключ к построению рабочего payload.

Отдельно стоит **base64 в контексте**: data-URI `data:image/png;base64,...`, JWT-сегменты, cookie. Здесь важно помнить про padding и URL-safe вариант. А **HTML numeric character references** (`&#65;`, `&#x41;`) декодируются браузером, но не сервером — поэтому обход XSS-фильтров через них работает только на клиенте.

## Разбор ошибок и отладка

Если payload «не проходит», изолируйте слой. Отправьте запрос напрямую бэкенду (в обход WAF), чтобы понять, фильтрует ли он вообще. Сравните ответы с закодированным и незакодированным вводом. Используйте Burp Repeater: меняйте по одному преобразованию и смотрите реакцию. Если сервер возвращает 403 на `../`, но 200 на `..%2f`, значит фильтр смотрит на сырую строку. Если оба 403, но `..%252f` проходит — фильтр декодирует один раз. Ведите матрицу «вход → код ответа», она быстро покажет уровень декодирования. И не забывайте про регистр: `%2F` и `%2f` обычно эквивалентны, а `..` и `..` с юникод-точками — нет.

## Частые вопросы

**Почему один и тот же payload работает на одном сервере и не работает на другом?** Потому что конвейер декодирования различается: nginx, Apache, IIS, Tomcat и прикладные фреймворки декодируют в разном порядке и разное число раз. Например, Apache исторически не декодирует `%2f` в пути (чтобы не создавать `/`), а другие серверы декодируют. Всегда тестируйте на конкретном стеке, а не по памяти.

**Как понять, сколько раз сервер декодирует?** Отправьте payload с разным уровнем кодирования и сравните ответы: `..`, `%2e%2e`, `%252e%252e`, `%25252e%25252e`. То, что проходит, показывает уровень. Полезно также посмотреть на редиректы: если сервер декодирует и редиректит на «нормализованный» путь, это видно в `Location`.

**Помогает ли кодирование против современного WAF?** Иногда — но современные WAF тоже декодируют несколько раз и нормализуют Unicode. Против них эффективнее комбинировать техники: разрыв токенов комментариями, нестандартные пробелы, регистр, альтернативные функции. Кодирование — лишь один инструмент в наборе.

**Что делать, если фильтр режет все кодировки?** Ищите другой контекст: возможно, уязвимость не в этом параметре. Иногда помогает передать данные в заголовке (заголовки декодируются иначе), в пути (а не в query), или в теле (JSON vs form). Смена контекста часто обходит фильтр, заточенный под конкретное место.

## Практический разбор: XSS-обход через кодирование

Дано: фильтр, который удаляет `<script>` из ввода. Пробуем варианты:

```html
&#x3c;script&#x3e;alert(1)&#x3c;/script&#x3e;     <!-- entities -->
<img src=x onerror=alert(1)>                     <!-- без script -->
<svg onload=alert(1)>
<script>alert(1)</script >                       <!-- пробел перед > -->
<scr<script>ipt>alert(1)</script>                <!-- вложенность обходит наивную замену -->
```

Если фильтр декодирует entities до проверки, а браузер — ещё раз, можно обойти двойным кодированием. Если фильтр удаляет `alert`, используйте `confirm`, `prompt`, `eval`, `Function`, `top['al'+'ert']`. Если контекст — атрибут, кодируйте кавычки (`&quot;`, `&#39;`) и закрывайте атрибут. Ключ — понять **контекст** (HTML-текст, атрибут, JS-строка, CSS) и подобрать кодирование под него. Всегда тестируйте в реальном браузере, а не только в ответе сервера: браузер может декодировать иначе. Для авто-поиска используйте `xsstrike`, `dalfox`.
