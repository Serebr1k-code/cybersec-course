## Что такое sandbox escape и зачем он нужен

Песочница (sandbox) — это изолированная среда, в которой программа может выполняться, не имея доступа к системе за своими пределами. В CTF вам часто дают такой «отсек»: интерпретатор с урезанными возможностями, чёрным списком функций или ограничением по времени и памяти. Задача — выйти за пределы песочницы, прочитать файл с флагом или выполнить произвольный код. В реальной безопасности песочницы защищают браузеры, мобильные приложения, облачные функции и CI-системы, поэтому умение их ломать — ценный навык.

Ключевая идея: любая песочница строится на *допущениях* о том, что недоступно. Escape — это поиск объекта, который разработчик забыл заблокировать, и через который можно дотянуться до системы. Чаще всего это не «дыра» в языке, а логическая ошибка в фильтре.

## Уровни изоляции

Полезно различать уровни, потому что от них зависит сложность:

- **Языковая песочница** — чёрный/белый список функций внутри интерпретатора (Python `eval` с фильтром, JavaScript `vm`).
- **Процессная изоляция** — `seccomp`, `chroot`, отдельный пользователь.
- **Контейнерная изоляция** — Docker, gVisor, namespace/cgroup.
- **Виртуализация** — VM, гипервизор.

CTF-задачи чаще всего про первый и второй уровень. Именно их мы разбираем в этом модуле.

## Python-песочницы: базовые приёмы

Классика — `eval(input)` с фильтром запрещённых слов. Обход строится на доступе к объектной модели Python. Отправная точка — `().__class__.__bases__[0].__subclasses__()`, откуда находится `warnings.catch_warnings` или `subprocess.Popen`:

```python
().__class__.__base__.__subclasses__()
```

Если фильтр запрещает `__subclasses__`, используйте обход через getattr и строки:

```python
getattr(getattr(().__class__, '__base__'), '__subclasses__')()
```

Или через форматирование строк, чтобы обойти текстовый фильтр:

```python
"{0.__class__.__base__.__subclasses__}".format(())
```

Дальше ищем нужный класс и вызываем:

```python
[c for c in ().__class__.__base__.__subclasses__() if c.__name__=='Popen'][0]('cat /flag', shell=True)
```

## Обход чёрных списков

Фильтры бывают наивными (по подстрокам) и их обходят:

- **Конкатенация**: `'__sub'+'classes__'`.
- **getattr со строкой**: `getattr(o, '__cl'+'ass__')`.
- **Кодировки**: `\x5f\x5fclass\x5f\x5f`, `chr(95)*2+'class'+chr(95)*2`.
- **Альтернативные имена**: `vars()`, `globals()`, `locals()`, `__builtins__`.
- **Base64/exec**: `exec(__import__('base64').b64decode('...'))`.

Пример для фильтра, запрещающего `import`:

```python
exec(bytes.fromhex('696d706f7274206f733b6f732e73797374656d2827636174202f666c61672729'))
```

## Доступ к builtins

Если у вас есть любой объект, до builtins можно добраться так:

```python
().__class__.__base__.__subclasses__()[0].__init__.__globals__['__builtins__']
```

Оттуда — `open`, `eval`, `exec`, `__import__`. Это универсальный путь почти во всех Python-джейлах.

## JavaScript-песочницы

В Node.js частый шаблон — `vm.runInNewContext` или `eval` с фильтром. Escape обычно через `constructor`:

```javascript
this.constructor.constructor('return process')().mainModule.require('child_process').execSync('cat /flag')
```

Обход фильтров: `['con'+'structor']`, доступ через `[].filter.constructor`, шаблонные строки, `Function` вместо `eval`.

## Общие приёмы для любого интерпретатора

- **Найдите путь к «нативному» слою**: в любом языке есть способ вызвать системные функции из-под капота.
- **Используйте рефлексию**: почти везде есть получение атрибутов по имени (getattr/`Reflect`).
- **Ищите забытые модули**: иногда фильтр закрывает `os`, но оставляет `subprocess`, `pty`, `ctypes`.
- **Комбинируйте**: обход фильтра + рефлексия + выполнение.

## Инструменты и подходы

- **`python -c`** для быстрой проверки payload'ов локально.
- **`jailctf`-ресурсы** и статьи про pyjail (полезные чек-листы).
- **`node -e`** для проверки JS-песочниц.
- **`strace`** чтобы увидеть, какие системные вызовы делает ваш payload.

## Типичные ошибки и подводные камни

- **Фильтр по подстрокам** — легко обходится конкатенацией.
- **Забыть про альтернативные точки входа** — `globals`, `vars`, `__import__`.
- **Не проверить версию языка** — поведение рефлексии отличается между версиями.
- **Игнорировать вывод ошибок** — traceback часто подсказывает путь.
- **Ограничение по длине** payload — используйте сжатие/hex/base64.
- **Полагать, что «функция удалена»** — она может быть доступна через `__builtins__`.
- **Путать `eval` и `exec`** — `eval` только выражение, `exec` — операторы.

## Что дальше / решение

План: определите уровень изоляции (язык, процесс, контейнер). Для языковых песочниц идите по цепочке рефлексии к builtins/нативному слою, обходите фильтры конкатенацией, getattr и кодировками. Проверяйте payload локально, читайте traceback, помните про альтернативные модули. Для контейнерных песочниц ищите ошибки монтирования, доступ к docker.sock, привилегированные возможности — но это уже отдельная тема (см. модули по контейнерам). Главное правило: песочница ломается там, где разработчик забыл заблокировать путь, а не там, где он блокировал.

## Практический пример: обход наивной Python-песочницы

Разберём конкретную задачу. Сервис принимает выражение и исполняет его через `eval`, предварительно проверяя, что в нём нет подстрок `import`, `os`, `system`, `open`. Прямые попытки блокируются. Строим payload по шагам. Сначала убеждаемся, что доступна объектная модель: `().__class__.__base__.__subclasses__()` возвращает список классов. Находим индекс `warnings.catch_warnings`. Через `__init__.__globals__['__builtins__']` получаем настоящие builtins. Теперь `__import__('os').system('cat /flag')`. Но подстрока `import` и `os` заблокированы — собираем имена динамически: `getattr(getattr(__builtins__, '__imp'+'ort__'))('o'+'s')`. Если и `system` в списке, берём `popen`. Если и `popen` — `subprocess.check_output`. Если совсем ничего — читаем файл через `open` из builtins: `__builtins__['op'+'en']('/flag').read()`.

Этот пример иллюстрирует главный принцип: чёрный список по подстрокам обходится конкатенацией и `getattr`, а доступ к builtins — через `__globals__` любой функции из стандартной библиотеки.

## Как читать traceback в свою пользу

Когда payload падает, интерпретатор печатает traceback с именами модулей, функций и путей файлов. Это карта доступного пространства. Например, ошибка `AttributeError: 'X' object has no attribute 'Y'` подсказывает, какие атрибуты есть. Ошибка импорта — какие модули реально загружены. В песочницах, где вывод фильтруется, можно специально возбуждать исключения с данными внутри (`raise Exception(data)`) и читать их в ответе.

## Частые вопросы

«Почему нельзя просто удалить `os`?» — потому что `__import__` его вернёт. «А если `__builtins__` пустой?» — ищите функцию с `__globals__`, ведущим к настоящим builtins. «Что если `ctypes` тоже убран?» — ищите другие модули-мосты: `subprocess`, `pty`, `pickle`. «А аудит-хуки?» — ищите непокрытые события или атакуйте уже скомпилированный код.

## Что дальше / решение

Итог: в Python-песочницах идите по цепочке рефлексии к builtins, обходите строковые фильтры конкатенацией и `getattr`, используйте `ctypes` для нативного выхода. Читайте traceback как карту окружения и всегда проверяйте payload локально. Надёжная изоляция Python требует отдельного процесса с ограничениями ОС, а не языкового фильтра.

## Частые вопросы по песочницам

«Что если всё очевидное заблокировано?» — ищите неочевидные пути: `ctypes`, `pickle`, `pty`, уже загруженные модули в `sys.modules`. «Как быстро перебрать варианты?» — держите список из десяти классических payload'ов и пробуйте по очереди. «Почему payload работает локально, но не на сервере?» — другая версия Python или другая конфигурация; проверяйте `sys.version`. «Помогает ли отладчик?» — да, локальный `pdb` показывает доступные имена. «Что если фильтр по длине?» — сжимайте payload или используйте переменные. Главное правило: песочница ломается там, где остался незакрытый путь, — ваша задача методично его найти.
