## Вопрос, с которого всё начинается

Игрок сохранил игру и отправил тебе файл состояния — `state.sav`. Внутри спрятан флаг, но просто открыть файл не выйдет: это бинарный дамп. Нужно понять формат save state, распаковать его и найти данные.

## Наш пример: файл состояния

```
$ file state.sav
state.sav: data
$ xxd -l 32 state.sav
00000000: 53 41 56 53 54 41 54 45 01 9a 00 00 00 1f 8b 08  SAVSTATE........
```

Первые 8 байт — `SAVSTATE` и версия `01`. Дальше `9a 00 00 00` — длина (154), затем `1f 8b` — сигнатура gzip. Значит, тело сжато.

## Шаг 1: что хранит save state

Save state — это **сериализация всего состояния эмуляции**:

- регистры процессора (`PC`, `SP`, флаги, аккумулятор);
- всю оперативную память (RAM);
- видеопамять и состояние PPU;
- состояние звукового чипа и таймеров;
- иногда — содержимое картриджа.

Фактически это «слепок» машины в момент сохранения. Загрузив его, эмулятор продолжает с того же места.

## Шаг 2: формат файла

Типичный save state состоит из:

| Часть | Пример | Смысл |
|---|---|---|
| Magic | `SAVSTATE` | сигнатура формата |
| Version | `01` | версия схемы |
| Length | `9a 00 00 00` | длина сжатого тела |
| Body | `1f 8b ...` | gzip/zlib-сжатые данные |
| Checksum | опционально | контроль целостности |

Разные эмуляторы используют разные схемы: где-то просто zlib, где-то собственный контейнер с чанками по типу.

## Шаг 3: распаковываем тело

```
$ python3 -c "import sys,gzip; d=open('state.sav','rb').read(); print(gzip.decompress(d[12:]).decode())"
CPU: PC=0x8000 SP=0xFFFE
SCORE=1337
SECRET=nto{s4v3_st4t3_t4mp3r1ng}
```

Тело оказалось текстовым после распаковки. Флаг на месте. В реальных состояниях это бинарь, и его разбирают по структуре: смещения регистров, блоки памяти.

## Шаг 4: подмена значения

Зачем подменять save state? Чтобы обойти проверку: например, игра показывает флаг, только если счёт больше 100000. Меняем `SCORE` в распакованном теле, сжимаем обратно и загружаем:

```
$ python3 -c "
import gzip
d=open('state.sav','rb').read()
body=gzip.decompress(d[12:]).replace(b'SCORE=1337', b'SCORE=999999')
open('state2.sav','wb').write(d[:8]+len(gzip.compress(body)).to_bytes(4,'little')+gzip.compress(body))
"
```

Теперь счёт огромен, и условие сработает.

## Шаг 5: контрольные суммы и защита

Продвинутые эмуляторы защищают состояние: считают CRC32 тела и хранят его рядом. Если подменить данные и не пересчитать сумму, загрузка откажется. Тогда нужно найти поле checksum, понять алгоритм (часто CRC32 или XOR) и обновить его. Некоторые форматы ещё и шифруют состояние — тогда сначала ищут ключ.

## Полный прогон

1. `xxd -l 32` — прочитать magic, версию, длину.
2. Определить сжатие по сигнатуре (`1f 8b` — gzip, `78 9c` — zlib).
3. Распаковать и разобрать структуру.
4. Найти нужное поле (флаг или значение для подмены).
5. При необходимости пересобрать, пересчитать checksum и загрузить.

## Что мы теперь знаем

- Save state — полный слепок состояния эмуляции.
- Формат обычно: magic + версия + длина + сжатое тело.
- gzip начинается с `1f 8b`, zlib — с `78 9c`.
- Подмена значений обходит проверки игры.
- Контрольные суммы защищают от подмены, но их можно пересчитать.

## Разбор бинарного save state по структуре

В реальности тело состояния — не текст, а структура. Обычно она состоит из последовательных блоков, каждый со своим тегом и длиной:

| Блок | Содержимое |
|---|---|
| CPU | регистры, PC, SP, флаги |
| RAM | 8–64 КБ оперативной памяти |
| VRAM | видеопамять |
| APU | состояние звука |
| TIMER | счётчики |

Формат может быть «плоским» (просто поля подряд) или «чанковым» (тег + длина + данные). Плоский разбирают по смещениям, чанковый — в цикле, читая тег и длину. Чтобы найти нужное поле, ищут характерные значения: счёт, координаты, здоровье. Их подменяют и пересобирают файл.

## Форматы разных эмуляторов

- **zlib/gzip внутри контейнера** — самый частый вариант: тело сжато, сверху magic и длина.
- **Собственный чанковый формат** — например, у Dolphin состояние делится на секции с тегами.
- **Простой бинарный дамп** — без сжатия, только фиксированные смещения.
- **С шифрованием** — некоторые консольные эмуляторы шифруют состояние; тогда сначала ищут ключ в бинаре.

Определить вариант помогает `binwalk` и просмотр сигнатур сжатия.

## Практические заметки и защита

- Всегда сохраняй копию оригинала перед подменой.
- Пересчитывай контрольную сумму, если она есть: CRC32, Adler-32 или XOR.
- Помни про endianness: little-endian в большинстве форматов, но проверяй.
- Если состояние не грузится, проверь версию эмулятора: схемы меняются между версиями.
- Для защиты от подмены используют подпись или привязку к аккаунту, но в CTF это редко.

## Итоговый разбор по шагам

Начни с `xxd -l 32`: прочитай magic и определи сжатие. Распакуй тело (`gzip`, `zlib`). Разбери структуру: плоские смещения или чанки. Найди нужное поле — флаг или значение для подмены. Если есть checksum, найди его и пересчитай. Собери файл заново и проверь загрузкой в эмуляторе. Такой конвейер работает с любым save state, потому что опирается на структуру, а не на догадки.

## Работа с бинарным телом на Python

Разбор удобно автоматизировать. Пример: найти в теле все строки и вывести смещения.

```python
import gzip, re
d = open('state.sav', 'rb').read()
body = gzip.decompress(d[12:])
for m in re.finditer(rb'nto\{[^}]*\}', body):
    print(hex(m.start()), m.group().decode())
```

А так — заменить значение фиксированной длины, не ломая смещения:

```python
body = body.replace(b'SCORE=1337', b'SCORE=999999')
open('state2.sav', 'wb').write(d[:12] + gzip.compress(body))
```

Замена строка-в-строку безопасна, если длина сохраняется. Если меняешь длину, придётся пересобирать структуру и обновлять все смещения — поэтому подменяй значения той же ширины.

## Разбор примера: обход проверки счёта

Игра показывает флаг, только если счёт больше 100000. В состоянии счёт лежит как 32-битное целое по известному смещению. Находим его по значению (например, 1337 = `39 05 00 00` в little-endian), меняем на `40 42 0F 00` (1000000), пересобираем. Если есть CRC32 тела — считаем новую сумму и подставляем. После загрузки условие срабатывает, и флаг показывается. Это и есть «save-state tampering» — подмена состояния вместо взлома кода.

## Частые ошибки

- Искать флаг как текст в сжатом теле, забыв распаковать.
- Менять длину значения и не пересчитывать смещения.
- Игнорировать endianness при поиске числа.
- Забывать про контрольную сумму и удивляться, что состояние не грузится.
- Путать версии формата: состояние от другой версии эмулятора может не подойти.

## Как найти смещение нужного поля

Если структура плоская и неизвестная, поле ищут эмпирически. Сделай два сохранения с разными значениями (например, счёт 100 и 200) и сравни файлы: различающиеся байты — и есть поле счёта. Этот приём («diff двух состояний») работает почти всегда и не требует документации формата.

```python
a = open('save_a.sav','rb').read()
b = open('save_b.sav','rb').read()
for i,(x,y) in enumerate(zip(a,b)):
    if x != y:
        print(hex(i), x, y)
```

Получив смещение, подставь нужное значение и пересобери файл. Если тело сжато, распаковывай оба состояния и сравнивай уже распакованные версии — так различия видны напрямую.

## Итоговая шпаргалка

| Шаг | Инструмент |
|---|---|
| Определить сжатие | `xxd -l 16`, `binwalk` |
| Распаковать тело | `gzip`, `zlib` |
| Найти поле | diff двух состояний |
| Подменить | Python, замена той же ширины |
| Пересчитать сумму | CRC32/Adler-32/XOR |
| Проверить | загрузка в эмуляторе |

## Почему это важно за пределами игр

Сериализация состояния — не только про игры. Тот же подход используют отладчики (core dumps), виртуальные машины (snapshots), системы миграции процессов (CRIU) и даже serverless-платформы (checkpoint/restore). Везде состояние сериализуется в файл, а потом восстанавливается — и везде возникает вопрос доверия: можно ли подменить файл состояния так, чтобы восстановление дало атакующему преимущество? В CTF save state — упрощённая модель этой задачи. Освоив разбор одного формата, ты сможешь разбирать снапшоты гипервизоров и дампы памяти, потому что принципы одинаковы: magic, версия, длина, сжатие, контрольная сумма.

## Что делать, если формат неизвестен

Когда документации нет, действуй так: определи сжатие по сигнатуре, распакуй, найди повторяющиеся блоки, сравни два состояния с разными значениями, найди контрольную сумму по её изменчивости при каждом сохранении. Это методика реверса любого бинарного формата, и она применима к save state так же, как к прошивкам и дампам.

И последнее: всегда проверяй, что после правки файл остаётся валидным — неверная длина или сжатие приведут к отказу загрузки, и эмулятор просто не примет состояние. Веди разбор пошагово и сохраняй промежуточные версии, чтобы всегда можно было вернуться к рабочему варианту.
