## Вопрос, с которого всё начинается

Задача даёт бинарь, который «читает файл с байткодом и что-то проверяет». Обычный дизассемблер показывает длинный `switch` по опкодам — перед тобой **кастомная виртуальная машина**. Разберём, как её распознать, разобрать байткод и найти логику проверки.

## Наш пример: цикл диспетчеризации

Типичная VM выглядит так: есть массив «регистров» или стек, указатель на инструкции (`pc`), и цикл, который читает байт-опкод и прыгает в обработчик:

```
while (1) {
  op = code[pc++];
  switch (op) {
    case 0x01: /* push */ ...
    case 0x02: /* add  */ ...
    case 0x03: /* cmp  */ ...
    case 0xFF: return;
  }
}
```

Твой враг — не сам цикл, а **неизвестная семантика опкодов**. Задача — восстановить её.

## Шаг 1: как распознать VM

Признаки: большой `switch`/цепочка `if` по числу; массив байтов, читаемый по индексу; счётчик инструкций; таблица обработчиков; строки вроде `vm`, `opcode`. Если видишь это — почти наверняка VM.

## Шаг 2: восстановить таблицу опкодов

Сопоставь каждому `case` его поведение. Часто опкоды нумеруются подряд (0x01 push, 0x02 pop, 0x03 add...). Полезно составить таблицу:

| Опкод | Действие |
|-------|----------|
| 0x01 | push const |
| 0x02 | pop |
| 0x03 | add |
| 0x04 | cmp |
| 0x05 | jz |
| 0x06 | jnz |
| 0xFF | halt |

Дальше «дизассемблируешь» байткод вручную: читаешь опкод, смотришь аргументы, записываешь человекочитаемую программу.

## Шаг 3: восстановить логику проверки

Проверка флага в VM обычно выглядит как последовательность `cmp` между введёнными символами и константами, с ветвлением на «неверно». Восстановив байткод, ты получишь что-то вроде:

```
push input[0]; push 0x6e; cmp; jnz fail
push input[1]; push 0x74; cmp; jnz fail
...
```

Отсюда флаг читается напрямую, либо (если есть арифметика/трансформации) восстанавливается обратной операцией.

## Шаг 4: автоматизация разбора

Вместо ручного чтения напиши скрипт-дизассемблер: он читает байткод, распознаёт опкоды и печатает инструкции. Так ты быстрее поймёшь логику и сможешь «прокрутить» её мысленно или даже исполнить (написать интерпретатор VM на Python).

## Шаг 5: зачем писать свой интерпретатор

Если VM сложная (много опкодов, циклы, память), самый быстрый путь — реализовать её в Python и просто запустить байткод. Тогда ты можешь экспериментировать с входом, ставить условные точки останова и подбирать флаг. Это часто быстрее, чем восстанавливать логику вручную.

## Шаг 6: пример стратегии

1. Найти массив байткода и цикл диспетчеризации.
2. Восстановить таблицу опкодов (по `switch`).
3. Написать Python-интерпретатор с этими опкодами.
4. Запустить байткод, подсовывая разные входы.
5. Наблюдать, при каком входе проверка проходит.

## Если не сработало

- Опкоды «не сходятся» → возможно, переменная длина инструкций; учти аргументы.
- VM использует шифрование байткода → найди функцию расшифровки перед циклом.
- Слишком много опкодов → автоматизируй извлечение таблицы из `switch`.

## Частые ошибки

- Пытаться читать байткод без таблицы опкодов.
- Забывать про аргументы инструкций (меняют длину).
- Игнорировать начальную инициализацию регистров.

## Что мы теперь знаем

- Кастомная VM распознаётся по циклу диспетчеризации и `switch` по опкодам.
- Логика проверки «спрятана» в байткоде.
- Восстановление таблицы опкодов и дизассемблирование — ключ.
- Свой интерпретатор в Python часто быстрее ручного разбора.

## Шаг 7: типы VM

VM бывают стековыми и регистровыми. В **стековой** операнды берутся со стека (push/pop), а операции работают с вершиной (как JVM, CPython, EVM). В **регистровой** есть именованные регистры, и инструкции указывают их явно (как Lua VM, Dalvik). Стековая проще для разбора (меньше аргументов у инструкций), регистровая компактнее. Определив тип, ты предсказываешь формат инструкций и быстрее восстанавливаешь семантику.

## Шаг 8: пример восстановления байткода

Пусть байткод начинается с `01 6e 03 01 74 03 04 05 ...`. Читаем: `01` (push const) `6e` (`'n'`), `03` (add? или push next), `01 74` (`'t'`)... Восстановив таблицу, получаем последовательность сравнений: символ `0x6e` (`n`), затем `0x74` (`t`) — начало строки `nto{`. Так «вручную» читается флаг, если проверка линейна.

## Шаг 9: защита байткода

Продвинутые VM защищают байткод: (1) шифруют его и расшифровывают перед запуском; (2) размывают таблицу обработчиков (handler obfuscation), где каждый опкод прыгает не в свой `case`, а через вычисленный адрес; (3) используют самописный «шифр опкодов», меняющийся от запуска. Против этого помогает динамический анализ: снять расшифрованный байткод в памяти после инициализации.

## Шаг 10: инструменты

- Дизассемблер (IDA/Ghidra) — для восстановления таблицы опкодов из `switch`.
- Отладчик — чтобы снять расшифрованный байткод в памяти.
- Свой Python-интерпретатор — для исполнения и экспериментов.
- `unicorn`/`angr` — для эмуляции фрагментов VM.

## Шаг 11: мини-чек-лист VM

- Стековая или регистровая?
- Где массив байткода и цикл диспетчеризации?
- Какова таблица опкодов и длины инструкций?
- Есть ли шифрование/обфускация байткода?
- Можешь ли написать интерпретатор и запустить байткод?

## Шаг 12: почему VM любят в задачах

Кастомная VM — идеальный способ спрятать логику: дизассемблер показывает только цикл диспетчеризации и `switch`, а настоящая программа лежит в байткоде. Автор задачи рассчитывает, что ты не станешь восстанавливать семантику опкодов. Тот, кто восстанавливает, решает задачу; тот, кто пытается «угадать флаг» из строк, — нет.

Отсюда вывод: увидев `switch` по числовым опкодам, сразу планируй восстановление таблицы опкодов, а не поиск строк.

## Шаг 13: стековая VM пошагово

Разберём типичную стековую VM. Регистр `pc` указывает на текущий байт. Цикл: читать опкод, увеличить `pc`, выполнить. Для `push const`: прочитать следующий байт(ы) как константу, положить на стек, сдвинуть `pc`. Для `add`: снять два значения, сложить, положить обратно. Для `cmp`: снять два, сравнить, выставить флаг. Для `jz`: если флаг «равно», перепрыгнуть на указанный адрес.

Восстановив эти шесть-семь опкодов, ты можешь исполнить байткод мысленно или написать интерпретатор и «прокрутить» его на разных входах.

## Шаг 14: как найти проверку флага

Проверка почти всегда выглядит как серия `cmp` с последующим `jnz fail`. Если байткод сравнивает введённые символы с константами напрямую — флаг читается из констант. Если сравнивает результат трансформации (XOR, add, rotate) — нужно применить обратную операцию к константам. В обоих случаях восстановленный байткод даёт полный ответ.

Иногда проверка «размазана» по нескольким проходам: сначала все символы XOR-ятся, потом сравниваются. Тогда твой интерпретатор с логами покажет промежуточные значения, и ты восстановишь ключ.

## Шаг 15: автоматизация

Ручное чтение байткода утомительно. Напиши скрипт: он читает файл, распознаёт опкоды и печатает список инструкций с адресами. Даже простой дизассемблер (50 строк на Python) ускоряет разбор в разы и снижает шанс ошибки. Если VM использует переменную длину инструкций — учти это в скрипте.

## Шаг 16: итог

Кастомная VM — это интерпретатор с таблицей опкодов, а её «программа» — байткод. Решение задачи = восстановить таблицу, дизассемблировать байткод, найти проверку и (при трансформациях) обратить её. Быстрее всего это делается своим интерпретатором на Python, который можно запускать на разных входах. Запомни главное: **в VM логика — в байткоде, а не в дизассемблере**.

## Шаг 17: смешанные VM

В реальных задачах VM редко бывают «чистыми». Часто встречаются гибриды: часть логики в нативном коде (обработчики опкодов), часть — в байткоде. Или VM вызывает нативные функции по индексу (как «внешние» в EVM). Тогда разбор требует и реверса нативных обработчиков, и дизассемблирования байткода. Стратегия одна: сначала понять интерфейс между нативной и байткод-частями, затем разбирать каждую отдельно.

## Шаг 18: почему важно исполнить, а не только прочитать

Читая байткод глазами, легко ошибиться в трансформациях (XOR, сдвиги, арифметика над символами). Исполнив байткод своим интерпретатором, ты получаешь точный результат без ручных вычислений. Особенно это важно, когда проверка включает многошаговые преобразования: прочитать их глазами почти невозможно, а исполнить — тривиально.

## Шаг 19: мини-упражнение

Возьми любую VM-задачу и напиши для неё интерпретатор из двух частей: таблица опкодов и цикл исполнения. Прогони байткод и посмотри, что он делает на разных входах. Затем найди в байткоде сравнение с константами и восстанови флаг. Это упражнение тренирует навык, который напрямую применим и в CTF, и при анализе виртуальных обфускаторов малвари.

## Шаг 20: итог и правило

Правило: **увидел цикл диспетчеризации и switch по опкодам — перед тобой VM, и её логика в байткоде**. Восстанавливай таблицу опкодов, дизассемблируй байткод, при трансформациях — пиши интерпретатор и исполняй. Этот подход решает и учебные VM-задачи, и защищённые обфускаторы, отличаясь лишь объёмом работы по восстановлению семантики.

## Шаг 21: запомни

Кастомная VM — это интерпретатор с таблицей опкодов, а её программа — байткод. Логика проверки спрятана именно там, а не в дизассемблере. Восстанови таблицу опкодов, дизассемблируй байткод, при трансформациях напиши интерпретатор и исполни его на разных входах.
