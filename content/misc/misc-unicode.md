## Вопрос, с которого всё начинается

В прошлом уроке мы разбирали байты. Теперь дают **строку текста**, которая выглядит абсолютно нормально, но с ней что-то не так: фильтр её пропускает, хотя должен блокировать, или она подозрительно длинная.

Причина в том, что «равенство строк» и «совпадение с образцом» зависят от того, как именно записаны символы. Один и тот же видимый текст можно закодировать **разными последовательностями**, и программа, сравнивающая сырые данные, этого не заметит.

## Наш пример: строка, которая не равна себе

Возьмём две строки, которые выглядят одинаково:

```python
s1 = 'café'          # é одним символом U+00E9
s2 = 'cafe\u0301'    # e + комбинирующая акутка U+0301
print(s1 == s2)
```

```
False
```

Визуально — одно и то же слово, а для Python — разные строки. `\u0301` — **комбинирующий символ**: он не рисуется сам, а «приклеивается» к предыдущей букве. Это и есть суть Unicode-трюков.

## Шаг 1: нормализация — привести к одной форме

Чтобы такие строки стали равны, их **нормализуют** — приводят к каноническому виду. Четыре формы:

| Форма | Что делает |
|-------|-----------|
| NFC | Каноническая композиция (собирает `e`+`́` в `é`) |
| NFD | Каноническая декомпозиция (разбирает `é` на `e`+`́`) |
| NFKC | Совместимостная композиция (упрощает похожие символы) |
| NFKD | Совместимостная декомпозиция |

```python
import unicodedata
print(unicodedata.normalize('NFC', s1) == unicodedata.normalize('NFC', s2))
```

```
True
```

Теперь строки равны. Отсюда и обход фильтров: фильтр ищет подстроку `"admin"`, а вы подаёте `"ad\u0301min"` — визуально то же, но подстрока не совпадает. Если бэкенд нормализует иначе, чем фильтр, — проверка обходится.

## Шаг 2: гомоглифы — одинаковые с виду символы

**Гомоглифы** (confusables) — разные символы, которые выглядят одинаково. Классика: кириллическая `а` (U+0430) вместо латинской `a` (U+0061).

```python
s = 'pаypal'     # первая 'а' — кириллическая
import unicodedata
print([unicodedata.name(c, '?') for c in s])
```

```
['LATIN SMALL LETTER P', 'CYRILLIC SMALL LETTER A', 'LATIN SMALL LETTER Y', ...]
```

Видим «CYRILLIC» там, где ожидали латиницу. Гомоглифы используют в фишинговых доменах, обходе чёрных списков слов и подделке имён пользователей: `admin` и `аdmin` — разные строки, но выглядят идентично.

Инструмент `confusable_homoglyphs` сразу скажет, что в строке смешаны скрипты:

```python
from confusable_homoglyphs import confusables
print(confusables.is_dangerous('pаypal'))   # True
```

## Шаг 3: невидимые символы — данные без текста

Есть символы, которые **вообще не отображаются**:

- **Zero-width:** `\u200b` (ZWSP), `\u200c` (ZWNJ), `\u200d` (ZWJ), `\ufeff` (BOM).
- **Управляющие bidi:** `\u202e` (RLO), `\u202d` (LRO) — меняют направление текста.

Zero-width идеально подходят, чтобы спрятать данные: ZWSP = бит `0`, ZWNJ = бит `1`. Строка выглядит безобидной, но несёт сообщение.

```python
text = 'Hello\u200b\u200c\u200c\u200bWorld'   # невидимая вставка
ZW = {'\u200b': '0', '\u200c': '1'}
bits = ''.join(ZW[c] for c in text if c in ZW)
print(bits)                                   # 0110
```

Собираем биты по 8, переводим в байты — и читаем скрытое сообщение:

```python
data = bytes(int(bits[i:i+8], 2) for i in range(0, len(bits)-7, 8))
```

## Шаг 4: двунаправленный текст (bidi)

Символ `\u202e` (RLO) разворачивает порядок отображения текста справа налево. Так можно визуально «переставить» символы: строка в редакторе выглядит безобидно, а по факту содержит другое.

```python
s = 'abc\u202Edef'
print(repr(s))       # реальный порядок: abc, RLO, def
```

На этом построена атака **Trojan Source** (CVE-2021-42574): в исходном коде bidi-символы прячут уязвимость, которая выглядит безвредной. Для аудита кода ищут символы категории `Cf` и bidi-controls:

```bash
$ grep -rPn '[\x{202A}-\x{202E}\x{2066}-\x{2069}]' src/
```

## Шаг 5: нормализация в веб-контексте

Три типовых сценария, где Unicode ломает приложения:

- **Сравнение имён пользователей.** Если приложение не нормализует, `admin` и `аdmin` (кириллица) — разные строки, но выглядят одинаково. Это подмена учётной записи.
- **Обход чёрных списков.** NFKC «упрощает» похожие символы: `①`→`1`, `ﬁ`→`fi`, `㊙`→`秘`. Фильтр, который ищет запрещённое слово до нормализации, обходится.
- **IDN-домены.** Гомоглифные домены обходят фильтры, но браузеры показывают punycode (`xn--…`) — декодируйте его.

```python
import unicodedata
print(unicodedata.normalize('NFKC', '㊙'))    # '秘'
print(unicodedata.normalize('NFKC', 'ﬁle'))  # 'file'
```

Правило для разработчика: **перед сравнением** приводите обе строки к одной форме (`NFC` для отображения, `NFKC` для «семантического» сравнения) и проверяйте, что все символы из одного скрипта.

## Шаг 6: рабочие инструменты

- **`unicodedata`** — `normalize`, `name`, `category`, `decomposition`.
- **`confusable_homoglyphs`** — находит смешанные скрипты в строке.
- **`ftfy`** — «чинит» битый Unicode-текст.
- **`unidecode`** — транслитерация в ASCII (удобно для сравнения).
- **CyberChef** — операции «Normalize Unicode», «Strip HTML».

```bash
$ python3 -c "import unicodedata; print(unicodedata.normalize('NFKC','ﬁle'))"
file
```

Держите `unicodedata` под рукой — он входит в стандартную библиотеку и решает большинство задач.

## Шаг 7: разобранный пример — флаг из невидимых символов

Дано: строка, выглядящая абсолютно обычно, но подозрительно длинная. Смотрим кодпоинты — и находим невидимые символы:

```python
import unicodedata
s = open('text.txt').read()
for c in s:
    if ord(c) > 127 or unicodedata.category(c).startswith('C'):
        print(hex(ord(c)), unicodedata.name(c, '?'))
```

Видим чередование `ZWSP` (U+200B) и `ZWNJ` (U+200C). Собираем из них биты и переводим в байты:

```python
bits = ''.join('0' if c == '\u200b' else '1' for c in s if c in '\u200b\u200c')
n = int(bits, 2)
print(n.to_bytes((n.bit_length() + 7) // 8, 'big'))
```

```
b'flag{zer0_w1dth}'
```

Флаг был «невидимым» — в прямом смысле. Обратная задача — встроить сообщение в безобидный текст, чтобы оно прошло через редактор незаметно.

## Что мы теперь знаем

- Один видимый текст можно записать разными последовательностями кодпоинтов — сравнение сырых строк ломается.
- Нормализация NFC/NFD/NFKC/NFKD приводит строки к каноническому виду; NFKC ещё и «упрощает» похожие символы (`①`→`1`, `ﬁ`→`fi`).
- Гомоглифы (кириллица вместо латиницы) обходят фильтры и подделывают имена.
- Zero-width символы прячут биты данных, bidi-символы переставляют текст (Trojan Source).
- Проверять надо **кодпоинты**, а не визуальный вид.

## На что смотреть дальше

- **Считать разные строки равными** — NFC и NFD не равны без нормализации.
- **Забыть про NFKC** — он меняет даже «похожие» символы, это готовый обход валидации.
- **Не искать невидимые символы** — в редакторе их не видно; ищите категорию `Cf`.
- **Игнорировать bidi** — управляющие символы скрывают порядок.
- **Путать байты и кодпоинты** — длина строки зависит от представления.
- **Домены** — IDN-гомоглифы браузеры показывают как punycode (`xn--…`); декодируйте.

## Справочная таблица

| Симптом | Причина | Действие |
|---------|---------|----------|
| «Похожие» строки не равны | NFC vs NFD | нормализовать |
| Фильтр пропускает payload | NFKC-эквивалент | канонизировать вход |
| Строка длиннее ожидаемого | zero-width | смотреть кодпоинты |
| Текст отображается не так | bidi | искать `Cf`-символы |
| Домен странный | IDN-гомоглиф | punycode |
