## Вопрос, с которого всё начинается

Программа проверяет: `if (len + 1 < MAX) copy(buf, src, len)`. Ты подаёшь огромный `len`, и проверка… проходит. Потому что `len + 1` «завернулось» через ноль. Это **переполнение целых**. Разберём, как оно работает и почему это уязвимость.

## Наш пример

Возьмём 8-битное беззнаковое число. Максимум — 255. Прибавим единицу:

```
>>> (255 + 1) & 0xFF
0
```

Результат — ноль, а не 256. Число «завернулось». Это **wrap-around** беззнаковой арифметики. Именно так обходят проверки границ.

## Шаг 1: беззнаковые числа

Беззнаковое `unsigned` хранит только неотрицательные значения. В n битах диапазон `0..2^n-1`. При переполнении значение берётся по модулю `2^n` — то есть заворачивается. Это **определённое** поведение: `UINT_MAX + 1 == 0` гарантировано. Поэтому проверки вида `if (a + b < a)` используют wrap-around.

## Шаг 2: знаковые числа и UB

Знаковое `int` хранит и отрицательные. При переполнении знакового числа стандарт C говорит: **undefined behavior (UB)**. Компилятор вправе предполагать, что переполнения не бывает, и «оптимизировать» проверку. Отсюда баги, где проверка исчезает после оптимизации. Это классический источник уязвимостей (CWE-190).

## Шаг 3: как переполнение становится уязвимостью

Классический шаблон: `size = len + header`; проверяют `size < MAX`; затем `malloc(size)` и `memcpy`. Если `len + header` завернулось, `size` окажется маленьким, проверка пройдёт, а `memcpy` скопирует больше — **heap overflow**. Так работают многие CVE.

## Шаг 4: где искать

- Арифметика перед выделением памяти (`malloc(len * count)`).
- Проверки границ с `+`/`*` без проверки переполнения.
- Парсеры длины из файла/сети (`read_u16`, `read_u32`).
- Счётчики, накапливающие значения.

## Шаг 5: знаковый против беззнакового

Смешение знаковых и беззнаковых типов в сравнении — отдельный класс багов: `if (len < sizeof(buf))` при `len` отрицательном (преобразуется в огромное беззнаковое) даст неверный результат. Всегда приводи типы явно и проверяй границы **до** арифметики.

## Шаг 6: языки без переполнения

Python и многие высокоуровневые языки используют целые произвольной точности — там переполнения нет (но есть большие числа). А вот C/C++/Go/Rust (в release, без проверок) уязвимы. Rust паникует на переполнении в debug, но заворачивает в release — помни об этом.

## Шаг 7: как защищаться

- Проверяй границы до арифметики, а не после.
- Используй безопасные функции (`memcpy_s`, `__builtin_add_overflow`).
- Включай санитайзеры (`-fsanitize=undefined`).
- В Rust используй `checked_add`/`saturating_add`.
- Явно приводи типы при сравнениях.

## Шаг 8: практический разбор

В CTF: дают бинарь, где `read_int` читает длину, проверяет `< 0x100`, потом `memcpy(dst, src, len)`. При `len = 0xFFFFFFFF` (отрицательное как знаковое) проверка пропускает, копирование уходит за буфер. Решение — понять, где знаковое/беззнаковое смешение, и подобрать вход.

## Частые ошибки

- Думать, что переполнение знакового — «заворачивание» (это UB).
- Проверять границы после арифметики.
- Смешивать signed/unsigned в сравнении.

## Разбор кейса: переполнение в `malloc(n * size)`

Классический сценарий: приходит число `n` элементов, каждый размером 4 байта. Код выделяет буфер и копирует.

```c
unsigned int n = read_u32(buf);      // из сети/файла
unsigned int size = n * 4;           // может переполниться
char *p = malloc(size);              // маленький буфер
memcpy(p, data, n * 4);              // копируется n*4 байт
```

Если `n = 0x40000001`, то `n * 4 = 0x100000004`, что в 32-битном `unsigned` заворачивается в `4`. `malloc(4)` вернёт крошечный буфер, а `memcpy` попытается скопировать `0x100000004` байт (в 64-битной арифметике) — **heap overflow**. Атакующий подаёт специально подобранное `n`, чтобы обойти проверку и переполнить кучу.

Проверить гипотезу можно так:

```python
>>> (0x40000001 * 4) & 0xFFFFFFFF
4
>>> (0x40000001 * 4) & 0xFFFFFFFFFFFFFFFF
17179869188
```

Видно расхождение: в 32 битах результат «завернулся» до 4, в 64 битах остался огромным. Именно это расхождение между размером выделения и размером копирования и есть уязвимость.

## Таблица: безопасные примитивы по языкам

| Язык | Проверка перед арифметикой | Что делает |
|---|---|---|
| C (GCC/Clang) | `__builtin_add_overflow(a,b,&r)` | вернёт 1 при переполнении |
| C (GCC/Clang) | `__builtin_mul_overflow(a,b,&r)` | то же для умножения |
| C | `if (a > SIZE_MAX - b) error;` | ручная проверка сложения |
| C++ | `std::numeric_limits<T>::max()` | сравнение до операции |
| Rust | `a.checked_mul(b)` → `Option` | `None` при переполнении |
| Rust | `a.overflowing_mul(b)` → `(val, bool)` | значение + флаг |
| Go | `math.MaxInt`/явная проверка | нет встроенного checked |
| Python | не нужно | целые произвольной точности |

Правило: проверяй границы **до** арифметики, а не после. Проверка `if (n*4 < MAX)` бессмысленна — к моменту проверки `n*4` уже переполнено.

## Санитайзеры в действии

Компилятор умеет ловить переполнения на этапе тестов. Сборка с `-fsanitize=undefined` (UBSan) останавливается на знаковом переполнении и печатает стек:

```bash
$ gcc -fsanitize=undefined -g prog.c -o prog && ./prog
prog.c:7:15: runtime error: signed integer overflow: 2147483647 + 1
  cannot be represented in type 'int'
```

Для беззнакового переполнения UBSan молчит (это определённое поведение), но `-fsanitize=integer` (в Clang) ловит и его. При аудите C-кода включай санитайзеры: они превращают невидимые переполнения в громкие ошибки с точной строкой.

## Если не сработало

- **Проверка «не пропускает» переполнение.** Значит, типы уже расширены до 64 бит, либо компилятор «убрал» проверку по UB. Посмотри ассемблер: если проверки нет, компилятор считает переполнение невозможным (UB).
- **Ввод не доходит до арифметики.** Проверь, где реально читается длина: возможно, она ограничена выше и переполнение недостижимо.
- **Уязвимость есть, но эксплойт нестабилен.** Переполнение кучи зависит от аллокатора; используй кучу в детерминированном состоянии, чтобы отладка была воспроизводимой.
- **Смешение знаковых и беззнаковых.** Проверь сравнения: `if (len < sizeof(buf))` при отрицательном `len` (преобразуется в огромное беззнаковое) даст неверный результат.

## Ограничения

Переполнение целых — уязвимость C/C++ (и Go/Rust в release без проверок), но не языков с произвольной точностью: в Python переполнения нет как класса. Поэтому при чтении чужого кода важно понимать, где границы типов реальны. И помни: знаковое переполнение — это undefined behavior, а не «заворачивание»: компилятор вправе предполагать, что его не бывает, и на этом основании выкидывать проверки. Это и делает такие баги трудноуловимыми при чтении исходника.

## Ещё: сужение типа (truncation) — родственный баг

Рядом с переполнением стоит **сужение**: значение, помещающееся в широкий тип, обрезается при записи в узкий. Классика — длина `size_t` (64 бита), которую сохраняют в `int` (32 бита) или в 16-битное поле протокола:

```c
size_t len = read_len();     // из файла, может быть > 2^16
uint16_t stored = (uint16_t)len;   // обрезается до младших 16 бит
```

Если проверка границ делается по `stored`, а копирование — по `len`, атакующий подаёт `len = 0x10000 + 8`; `stored` станет `8` (проверка пройдёт), а скопируется 65544 байта — переполнение буфера. Тот же приём встречается в сетевых протоколах, где поле длины 16-битное, а реальная длина больше. Защита та же: проверять значение **до** приведения к узкому типу и использовать безопасные преобразования (в C++ — `gsl::narrow`, в Rust — `try_into`).

## Итоговый чек-лист

- Ищи арифметику перед `malloc`/`memcpy` — там живут переполнения.
- Проверяй границы **до** операции, а не после.
- Беззнаковое переполнение — определённое (wrap), знаковое — UB.
- Смешение signed/unsigned в сравнении — отдельный класс багов.
- Сужение типа (`size_t` → `int`/`uint16`) обходит проверки.
- Включай `-fsanitize=undefined` (и `integer`) при аудите.
- В Rust — `checked_add`/`try_into`; в Python переполнения нет как класса.

## Кратко: что запомнить

Переполнение целых возникает в C/C++/Go/Rust (release) и почти всегда живёт в арифметике перед выделением памяти или проверкой границ. Беззнаковое переполнение заворачивается по модулю, знаковое — undefined behavior, из-за которого компилятор может выбросить проверку. Родственный баг — сужение типа. Защита одна: проверять границы до операции и включать санитайзеры при аудите. В Python переполнения нет как класса.

## Практика: находим переполнение в бинаре

Как быстро локализовать переполнение в незнакомом бинаре. Первый шаг — искать «опасные» вызовы: `malloc`, `calloc`, `realloc`, `memcpy`, `alloca` — в дизассемблере (Ghidra, IDA, `objdump -d`) рядом с арифметикой. Второй — смотреть, где результат арифметики используется как размер. Третий — проверить, есть ли проверка границ и где она стоит: до или после операции.

```bash
$ objdump -d -M intel prog | grep -B4 -A2 'call.*memcpy'
```

Ключевой признак — `imul` (умножение) или `add` непосредственно перед `malloc`/`memcpy` без сравнения с максимумом. Если проверка есть, но использует знаковое сравнение (`jl`, `jg`) для значения, которое по смыслу беззнаковое, — это тоже баг: отрицательная «длина» пройдёт как маленькая. Наконец, полезно запустить бинарь под санитайзером, если есть исходники, или под отладчиком с большим `n`, и посмотреть, завернётся ли размер. Так от «подозрительного места» быстро переходят к конкретному входу, вызывающему переполнение.

## Что мы теперь знаем

- Беззнаковое переполнение — wrap-around по модулю 2^n.
- Знаковое переполнение в C — UB и повод для оптимизаций-багов.
- `len + header` перед malloc — классический шаблон уязвимости.
- Смешение signed/unsigned ломает сравнения.
- Защита: проверки до арифметики, sanitizer, checked-функции.
