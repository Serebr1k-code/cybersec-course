## Вопрос, с которого всё начинается

Тебе дали файл `events.ndjson` на миллион строк. Это логи сервиса. Нужно найти событие с флагом, не загружая всё в память. Как обрабатывать такой формат быстро и правильно?

Ответ: **NDJSON** (Newline Delimited JSON) — по одному JSON-объекту на строку. Он создан для потоковой обработки.

## Наш пример: поток событий

```
$ head -2 events.ndjson
{"ts":1700000000,"user":"alice","action":"login"}
{"ts":1700000001,"user":"bob","action":"read","file":"/flag"}
```

Каждая строка — самостоятельный JSON. Это и есть NDJSON (он же JSON Lines, `.jsonl`).

## Шаг 1: зачем построчный JSON

Обычный JSON — один большой массив; чтобы его прочитать, нужен весь файл (или потоковый парсер). NDJSON обходится без этого: читаешь строку за строкой, парсишь, обрабатываешь, забываешь. Идеально для логов, стриминга, больших выгрузок. Каждая строка независима — можно распараллелить.

## Шаг 2: обработка через jq

`jq` — стандартный инструмент:

```
$ jq -c 'select(.action=="read")' events.ndjson
{"ts":1700000001,"user":"bob","action":"read","file":"/flag"}
$ jq -r 'select(.file|test("nto")) | .file' events.ndjson
nto{ndjs0n_str34m}
```

`-c` — компактный вывод, `-r` — сырые строки, `select` — фильтр. Одной командой находишь нужное событие в миллионе строк.

## Шаг 3: вложенные переводы строк

Главная ловушка: если внутри JSON-строки есть **настоящий** перевод строки (не `\n`), строка «рвётся» на две, и парсер ошибается. Корректный NDJSON требует, чтобы переводы строк были экранированы. Некорректный генератор ломает разбор — и это баг, который можно эксплуатировать.

## Шаг 4: инъекции через NDJSON

Если приложение вставляет пользовательский ввод в NDJSON без экранирования, можно «сломать» структуру: закрыть объект и добавить свой. Это родственно **JSON injection** и **log injection**:

```
user = 'alice","admin":true,"x":"'
→ {"user":"alice","admin":true,"x":""}
```

Парсер увидит лишнее поле `admin`. Так обходят проверки, основанные на логах или событиях.

## Шаг 5: парсинг и производительность

Для больших файлов используют потоковые парсеры: `ijson` (Python), `jsonl`-читатели. Ключевой приём — не держать всё в памяти. Для поиска — `grep` + `jq`, для агрегации — `jq -s` (slurp) на разумных порциях.

## Шаг 6: типичные ошибки

- **Пропуск пустых строк** — они ломают парсер.
- **BOM в начале** файла.
- **Смешение форматов** (массив + NDJSON).
- **Неэкранированные переводы строк** внутри значений.

Каждая ошибка — потенциальный баг безопасности.

## Полный прогон

```
$ grep -o 'nto{[^}]*}' events.ndjson
nto{ndjs0n_str34m}
$ jq -r 'select(.file|test("flag")) | .file' events.ndjson
/flag
```

Обрати внимание: `grep -o` с regex — **литеральный** паттерн, звёздочки не работают как в PCRE. Для настоящего regex используй `jq` или `grep -E`.

## Как защищаться

- **Экранировать** пользовательский ввод перед вставкой в JSON.
- **Строго генерировать** NDJSON (один объект на строку, экранированные переводы).
- **Валидировать** каждую строку парсером, отбрасывать битые.
- **Не доверять** логам как источнику истины при авторизации.

## Что мы теперь знаем

- NDJSON — один JSON-объект на строку; удобен для потоков.
- `jq` — основной инструмент обработки.
- Некорректные переводы строк ломают разбор.
- Неэкранированный ввод даёт JSON/log injection.
- Потоковые парсеры экономят память.

## jq: основные приёмы

`jq` — язык запросов к JSON. Для NDJSON полезны: `select(cond)` — фильтр; `.field` — доступ; `test("regex")` — проверка; `-c` — компактный вывод; `-r` — сырая строка; `-s` — «slurp» (весь поток в массив). Комбинации дают мощные выборки в одну команду: например, `jq -r 'select(.action=="read") | .file'`.

## Потоковые парсеры

Для гигабайтных файлов используют потоковые парсеры: `ijson` (Python), `jsonl`-читатели, `jq --stream`. Они не держат файл в памяти. Для NDJSON достаточно читать построчно и парсить каждую строку — это уже потоково. Для агрегаций применяют `jq -s` на порциях или собственный аккумулятор.

## Валидация строк

Каждую строку стоит проверять парсером и отбрасывать битые. Иначе одна испорченная строка ломает весь процесс. В аудите это важно: невалидные строки могут быть попыткой инъекции. Логируй и считай их отдельно.

## Log injection глубже

Если система принимает ввод и пишет его в лог как NDJSON, злоумышленник может вставить свой объект или поля. Это ломает аналитику, может подделать события и, если лог используется для решений о доступе, обойти проверку. Защита — экранировать и валидировать перед записью.

## NDJSON vs JSON vs JSON-seq

Обычный JSON — один документ (нужен целиком). NDJSON — объект на строку (потоково). JSON-seq (RFC 7464) — похожий формат с маркером `0x1E` перед объектом, позволяет передавать несколько документов в потоке без перевода строки. Выбор влияет на парсер.

## Работа с большими файлами

Приёмы: `grep` для грубого поиска, `jq` для точного; `split` для разбиения; параллельная обработка (`xargs -P`, GNU parallel). Не загружай всё в память — это главное правило потоковой обработки.

## Шпаргалка

`jq -c 'select(.x==1)' f.ndjson` — фильтр; `jq -r '.field' f.ndjson` — значения; `grep -o 'nto{[^}]*}'` — грубый поиск (литеральный regex!); `wc -l` — число строк. Для потоковой обработки — читать построчно.

## Итог

NDJSON — один объект на строку, идеален для потоков. `jq` решает почти любую выборку. Опасности — неэкранированные переводы строк и инъекция. Обработка — потоковая, без загрузки в память.

## Схема и валидация

В отличие от бинарных форматов, NDJSON не несёт схему: типы полей «на совести» генератора. Поэтому валидацию строят отдельно (JSON Schema, pydantic). Без неё потребитель может получить неожиданный тип и упасть или, хуже, интерпретировать данные неверно. В аудите проверь, есть ли схема и применяется ли она.

## Сравнение с CSV

CSV — таблица, NDJSON — поток объектов. NDJSON лучше для вложенных структур и разнородных событий; CSV компактнее для однородных таблиц. Оба уязвимы к инъекции (формулы в CSV, поля в NDJSON). Выбор формата влияет на класс атак.

## Инструменты помимо jq

`jq` — универсальный, но не единственный: `gron` разворачивает JSON в плоские строки (удобно для grep), `fx`/`jid` — интерактивные просмотрщики, `ijson` — потоковый парсер в Python. Для больших файлов комбинация `grep` + `jq` обычно быстрее всего.

## Пример аудита логов

Проверь: экранируется ли ввод перед записью в NDJSON; валидируются ли строки при чтении; используются ли логи для решений о доступе; нет ли смешения форматов; есть ли лимит размера строки. Каждый «нет» — потенциальная находка (log injection, DoS, обход проверок).

## Итог урока

NDJSON — один объект на строку; идеален для потоков и логов. `jq` — основной инструмент. Главные опасности: неэкранированные переводы строк и инъекция. Обработка должна быть потоковой, а ввод — валидируемым.

## Практический сценарий CTF

Задача: в огромном `.ndjson` найти событие с флагом. Решение: `jq -r 'select(.field|test("nto")) | .field'` или `grep`. Если флаг разбит на несколько событий — собираешь по частям. Если ввод инъецируется — ищешь событие с «лишним» полем. Всё решается потоковой обработкой, без загрузки файла в память.

## Что тренирует эта тема

NDJSON учит потоковому мышлению: обрабатывать данные по мере поступления, не держа всё в памяти. Этот навык нужен при анализе логов, больших выгрузок и сетевых потоков. Плюс ты видишь, как инъекция в «безобидный» формат ломает логику.

## Частые находки в аудите

Три частые проблемы: отсутствие экранирования при записи (log injection); отсутствие валидации при чтении (падение на битой строке); использование логов для решений о доступе (обход). Исправления: экранировать ввод, валидировать строки, не строить безопасность на логах.

## Итог

NDJSON — простой, но важный формат. Один объект на строку, потоковая обработка через `jq`, экранирование переводов строк. Опасности — инъекция и битые строки. Освоив NDJSON, ты легко работаешь с любыми построчными форматами (CSV, логи, потоки).

## Расширенный пример обработки

```
$ wc -l events.ndjson
3
$ jq -c 'select(.action!="login")' events.ndjson
{"ts":1700000001,"user":"bob","action":"read","file":"/flag"}
{"ts":1700000002,"user":"eve","action":"exfil","file":"nto{ndjs0n_str34m}"}
$ jq -r '[.user, .action] | @tsv' events.ndjson
alice	login
bob	read
eve	exfil
```

Комбинации `select`, `@tsv` и `-r` дают готовые выгрузки. Для больших файлов добавляй `head`/`tail` или обрабатывай порциями, чтобы не держать всё в памяти.

## Валидация схемы

JSON Schema описывает ожидаемые поля и типы. Прогоняя каждую строку через схему, ты отсеиваешь инъекции и битые записи. Это стандартная практика для потоков событий: генератор и потребитель договариваются о схеме, а расхождения логируются как аномалии.

## Развёрнутый пример: почему потоковость критична

Пусть лог растёт на гигабайты в сутки. Загрузить его целиком нельзя — не хватит памяти. NDJSON решает это: читаешь строку, парсишь, обрабатываешь, забываешь. Инструменты вроде `jq` работают потоково и не держат файл целиком, а `ijson` позволяет читать даже частично сломанные документы. Именно поэтому NDJSON стал стандартом для логов и событийных шин: он совмещает простоту JSON с масштабируемостью построчной обработки. Побочный эффект — чувствительность к экранированию: одна неэкранированная кавычка или перевод строки «разрезает» запись и ломает разбор всей цепочки.

## Краткий итог

NDJSON остаётся самым простым способом передать поток объектов: одна строка — один объект, никакой внешней обвязки. Цена простоты — необходимость строгого экранирования и валидации. Если помнишь об этих двух вещах, формат работает без сюрпризов.
