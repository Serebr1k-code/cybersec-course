## Вопрос, с которого всё начинается

У тебя есть файл. Ты не знаешь, это текст, сжатые данные или шифротекст. Как понять по содержимому? Ответ даёт **теория информации**: она измеряет, сколько «непредсказуемости» в данных. Эта величина называется **энтропия**.

## Наш пример

У нас есть `info.log` — измерения энтропии для нескольких фрагментов:

```
sample: plain_text entropy: 4.12 bits/byte
sample: compressed entropy: 7.95 bits/byte
sample: random entropy: 8.00 bits/byte
```

Наша задача — понять, что означает каждое число и как по нему делать выводы.

## Шаг 1: что такое информация

В быту «информация» — это смысл. В теории информации Шеннона смысла нет вообще: информация — это **снятая неопределённость**. Сообщение тем ценнее, чем менее оно ожидаемо. «Завтра взойдёт солнце» несёт почти ноль информации; «завтра пойдёт снег в июле» — много.

Значит, мера информации должна зависеть от **вероятности**: чем реже событие, тем больше информации оно несёт.

## Шаг 2: количество информации одного события

Информация события с вероятностью `p` определяется как:

```
I = -log2(p)   (в битах)
```

Если `p = 1` (событие точно случится), `I = 0` — информации нет. Если `p = 1/2`, `I = 1` бит. Если `p = 1/256`, `I = 8` бит — ровно один байт. Отсюда интуиция: **один бит — это ответ на вопрос «да/нет» с равными шансами**.

## Шаг 3: энтропия источника

**Энтропия** — среднее количество информации на символ:

```
H = -Σ p_i * log2(p_i)
```

Для источника из `n` равновероятных символов `H = log2(n)`. Для байта (256 равновероятных значений) `H = 8` бит — максимум. В нашем логе `random entropy: 8.00` — идеально случайные байты. `plain_text entropy: 4.12` — английский текст: буквы распределены неравномерно, потому энтропия ниже.

## Шаг 4: избыточность

Разница между максимумом и фактической энтропией — **избыточность** (redundancy). Для английского текста она велика: буквы `e`, `t`, `a` встречаются часто, а `z`, `q` — редко. Именно избыточность позволяет сжимать текст: предсказуемые куски кодируются короче.

Формула: `R = H_max - H`. Для текста `H_max = 8`, `H ≈ 4`, значит `R ≈ 4` бита на байт — почти половина «лишняя».

## Шаг 5: как это помогает в задачах

Энтропия — быстрый способ **классифицировать данные**:

- **Текст/код/разметка**: энтропия заметно ниже 8 (обычно 3–5 бит/байт).
- **Сжатые данные** (zip, gzip, png): близко к 8, потому что сжатие уже убрало избыточность.
- **Шифротекст**: ровно ~8 — шифр делает данные неотличимыми от случайных.
- **Скрытая вставка**: локальные участки с аномальной энтропией выдают, что там «что-то есть».

Инструмент `binwalk`/`ent` считает энтропию по блокам — ищет такие аномалии.

## Шаг 6: предел сжатия

Теорема Шеннона о кодировании источника говорит: **нельзя сжать данные сильнее, чем их энтропия**. Если энтропия файла — 8 бит/байт (шифротекст или уже сжатый), дальнейшее сжатие бесполезно. Поэтому архивировать зашифрованное бессмысленно — размер не уменьшится.

Это же объясняет, почему «зашифруй и сожми» не работает: шифр уже довёл энтропию до максимума.

## Шаг 7: как это выглядит в задаче

Типовые приёмы:

- посчитать энтропию файла целиком (`ent file`);
- пройти блоками и найти участок с высокой энтропией — там, вероятно, зашифрованный или сжатый блок;
- сравнить энтропию «нормального» и подозрительного файла;
- оценить энтропию пароля/ключа по алфавиту и длине.

## Шаг 8: находим флаг в логе

В `info.log` есть строка `flag` в base64:

```
$ grep flag info.log
flag: bnRvezNudHIwcHlfMGZfNF9wNHNzdzByZH0=
```

Декодируем и пишем в файл:

```
$ grep flag info.log | cut -d: -f2 | base64 -d
nto{3ntr0py_0f_4_p4ssw0rd}
$ grep flag info.log | cut -d: -f2 | base64 -d > found.txt
$ check
```

Метка напоминает: энтропия — это мера «сколько угадывать» пароль или данные.

## Что мы теперь знаем

- Информация — снятая неопределённость; она зависит от вероятности.
- `I = -log2(p)` бит на событие; энтропия — среднее на символ.
- Для байта максимум 8 бит; текст ~3–5, шифр ~8.
- Избыточность позволяет сжимать; энтропия задаёт предел сжатия.
- Энтропия по блокам выдаёт скрытые вставки.

## Считаем энтропию сами: пошаговый разбор

Формулу `H = -Σ p_i·log2(p_i)` удобно проверить руками. Возьмём три файла по 64 КиБ и посчитаем энтропию утилитой `ent` (пакет `ent`, часто уже стоит на дистрибутивах форензики):

```
$ head -c 65536 /usr/share/dict/words > text.bin
$ head -c 65536 /dev/urandom          > rand.bin
$ gzip -c text.bin | head -c 65536    > gz.bin

$ ent text.bin | head -3
Entropy = 4.575211 bits per byte.

$ ent rand.bin | head -3
Entropy = 7.999823 bits per byte.

$ ent gz.bin | head -3
Entropy = 7.991407 bits per byte.
```

Три числа — три класса данных. Английский текст держится около 4.5 бит/байт, потому что буквы распределены крайне неравномерно. Случайные байты дают ровно 8.0 — с точностью до статистического шума на выборке конечного размера. Сжатый поток уже почти неотличим от случайного: дефляция убрала всю избыточность, и осталась только «несжимаемая» часть.

Тот же расчёт на Python без внешних пакетов:

```python
import math, collections
def H(data: bytes) -> float:
    c = collections.Counter(data)
    n = len(data)
    return -sum((v/n) * math.log2(v/n) for v in c.values())
print(round(H(open('text.bin','rb').read()), 3))   # ~4.575
```

Обратите внимание: `math.log2` — основание 2, поэтому результат в битах на символ. Если случайно взять натуральный логарифм, получите нат, и число будет ~3.17 вместо 4.575 — типичная ошибка при переносе чужого кода.

## Справочная таблица: типичная энтропия по форматам

| Тип данных | Энтропия, бит/байт | Почему |
|---|---|---|
| Исходный код / текст | 4.0–5.0 | Сильный перекос частот букв и пробелов |
| Логи, CSV | 4.5–5.5 | Больше цифр и разделителей, частоты ровнее |
| Base64-текст | 5.8–6.0 | Алфавит из 64 символов, почти равномерный |
| Сжатые данные (gzip/zstd) | 7.9–8.0 | Избыточность удалена |
| Шифротекст (AES/ChaCha) | 7.99–8.00 | Близко к идеально случайному |
| JPEG/PNG/MP3 (тело) | 7.5–8.0 | Сжатие с потерями/без, блоки энтропийного кода |
| Однородный 8-битный шум | 8.00 | Равномерное распределение байтов |

По этой таблице видно главное правило: **высокая энтропия означает «сжато или зашифровано», но не различает эти два случая**. Отличить шифр от сжатия помогает не значение, а структура: у сжатых форматов есть сигнатуры и заголовки (`1f 8b` у gzip, `PK` у ZIP), у чистого шифротекста их нет.

## Граничные случаи: когда энтропия обманывает

Метрика хорошо работает на больших однородных выборках и плохо — на коротких или неоднородных. Разберём типичные ловушки.

**Короткие фрагменты.** Энтропия 16 байт никогда не приблизится к 8.0 даже если это чистый `/dev/urandom`: на такой выборке просто не успевают появиться все 256 значений. Оценка смещена вниз. Практическое правило: считайте энтропию блоками не меньше 1–4 КиБ.

**Всё целиком vs блоками.** `ent` даёт одно число на весь файл. Но файл может быть текстом с зашитым посередине архивом — глобальная энтропия смажет локальную аномалию. Поэтому в задачах считают энтропию **скользящим окном**:

```
$ python3 - <<'PY'
data = open('suspect.bin','rb').read()
W = 1024
for off in range(0, len(data), W):
    blk = data[off:off+W]
    c = {}
    for b in blk: c[b] = c.get(b,0)+1
    import math
    n = len(blk)
    H = -sum((v/n)*math.log2(v/n) for v in c.values())
    print(f"{off:#08x}  {H:.2f}")
PY
```

Резкий скачок с 4–5 до 7.9 на конкретном смещении — это и есть граница вставки. Именно так находят **зашифрованный том внутри текстового контейнера** или PNG, дописанный в конец JPEG.

**Уже сжатые форматы маскируют данные.** Если спрятать секрет в PNG методом LSB, глобальная энтропия почти не изменится — контейнер и так ~8.0. Здесь энтропия бесполезна, и работают другие методы (стегоанализ, chi-square, RS-анализ).

**«Низкая энтропия — значит не зашифровано» — тоже неверно.** XOR-шифрование с однобайтовым ключом сохраняет распределение частот и может дать низкую энтропию. Зато избыточность исходника остаётся — и именно её ловит частотный анализ или `xortool`.

## Ограничения метода

Энтропия — описательная статистика, а не доказательство. Три ограничения, которые стоит держать в голове:

1. **Это не тест на случайность.** Высокая энтропия не означает криптостойкость. Данные могут быть «случайными» для частотного теста, но полностью предсказуемыми (например, счётчик, зашифрованный слабым потоковым шифром).
2. **Чувствительность к длине.** На коротких выборках оценка занижена и шумна — сравнивать файлы разной длины по одному числу нельзя.
3. **Не различает сжатие и шифрование.** Обе операции убирают избыточность. Различить помогает только контекст: сигнатуры, заголовки, наличие структуры.

Поэтому в реальной работе энтропию используют как **первый фильтр**: быстро отсортировать «скучное» от «подозрительного», а дальше применять прицельные инструменты — `binwalk`, `file`, `xxd`, частотный анализ.

## Разбор задачи: почему флаг был в base64, а не в шифре

Вернёмся к нашему `info.log`. Строка `plain_text entropy: 4.12` — это про обычный текст. Строка `compressed entropy: 7.95` — про сжатые данные. А строка `flag` содержала base64. Почему base64, а не «настоящий шифр»? Потому что base64 даёт энтропию около 5.8–6.0 — заметно ниже 8.0. Если бы в логе лежал AES-шифротекст, его энтропия была бы ~8.0, и никакой статистикой его не «прочитать» — понадобился бы ключ. Разработчик задачи выбрал base64 именно как обратимое, но не криптостойкое кодирование: это намёк «данные читаемы, если раскодировать». Умение отличить 6.0 от 8.0 по одному числу — прямой путь к флагу.
