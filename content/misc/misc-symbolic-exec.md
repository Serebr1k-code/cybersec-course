## Вопрос, с которого всё начинается

У тебя есть крекми: он читает строку и отвечает `OK` или `Wrong`. Внутри — десяток проверок, вложенные условия, таблицы. Перебирать вручную долго. А что если попросить компьютер **самому найти** вход, который проходит все проверки? Именно это делает символьное исполнение.

## Наш пример

У нас есть `symbolic.log` — трасса символического исполнения:

```
branch: 0x4012a0 constraint: input[0] == 0x6e
branch: 0x4012c0 constraint: input[1] ^ 0x13 == 0x7d
...
```

Здесь для каждой ветки записано **ограничение**, которое должно быть истинно, чтобы по ней пойти. Наша задача — понять, как из набора таких ограничений собирается решение. Но сначала — базовая идея.

## Шаг 1: что значит «символическое»

Обычно программа исполняется над **конкретными** числами: `input = "hello"`. **Символьное исполнение** заменяет вход на **символ** — переменную, у которой значение ещё не выбрано. Программа идёт, но вместо `if (x == 5)` движок записывает: «чтобы пойти сюда, нужно `x == 5`».

Так вдоль каждого пути накапливается **путь-условие** (path constraint) — набор ограничений, которые делают этот путь достижимым.

## Шаг 2: решатель в конце

В конце движок отдаёт ограничения **решателю** (SMT-солверу, обычно Z3): «найди значения переменных, при которых все ограничения истинны». Если решение есть — это и есть вход, ведущий по нужному пути. Если нет — путь недостижим.

Схема проста: **исполни символически → собери ограничения → реши → получи вход**.

## Шаг 3: почему это дорого

Число путей растёт экспоненциально: каждый `if` удваивает ветвления. Это называется **state explosion** (взрыв состояний). Через несколько десятков условий путь-условия становятся огромными, а решатель — медленным или неразрешимым.

Поэтому символьное исполнение применяют **точечно**: не ко всей программе, а к конкретной функции-проверке, найдя её заранее.

## Шаг 4: angr — символьное исполнение для бинарников

**angr** — фреймворк на Python, который умеет символически исполнять **машинный код** (не исходники). Типовой сценарий:

```
import angr, claripy
p = angr.Project('./crackme')
st = p.factory.entry_state()
sm = p.factory.simulation_manager(st)
sm.explore(find=0x401300, avoid=0x401200)   # ищем ветку OK
print(sm.found[0].posix.dumps(0))            # найденный stdin
```

Здесь `find` — адрес успешной ветки, `avoid` — неуспешной. angr сам собирает ограничения и зовёт Z3.

## Шаг 5: KLEE и другие

**KLEE** работает с LLVM-байткодом и популярен для символьного исполнения **исходников** на C. Для Python-задач часто хватает `z3` напрямую. Общая идея у всех одна: **ограничения + решатель**.

## Шаг 6: практические приёмы

- **Сузить цель**: найти конкретную функцию проверки и стартовать символически с неё, а не с `main`.
- **Задать вход как символ правильной ширины** (`claripy.BVS('in', 8*16)`).
- **Ограничить алфавит**: если вход — печатные символы, добавить `And(c >= 0x20, c < 0x7f)` — это резко ускоряет решатель.
- **Подсказать формат**: если знаешь префикс (`nto{`), добавь ограничение на первые байты.
- **Учесть антианализ**: циклы-«убийцы», проверки времени и `ptrace` часто ломают символическое исполнение — их обходят патчами или `avoid`.

## Шаг 7: как это выглядит в задаче

Типовая misc-задача: крекми с проверкой пароля. Решение — символически исполнить функцию проверки, задать пароль как символ и попросить решатель найти значения, при которых функция вернёт `true`. Найденный вход — флаг или ключ.

## Шаг 8: находим флаг в трассе

В `symbolic.log` есть строка `flag` в base64:

```
$ grep flag symbolic.log
flag: bnRvezRuZ3JfZjB1bmRfdGgzX3A0dGh9
```

Декодируем и пишем в файл:

```
$ grep flag symbolic.log | cut -d: -f2 | base64 -d
nto{4ngr_f0und_th3_p4th}
$ grep flag symbolic.log | cut -d: -f2 | base64 -d > found.txt
$ check
```

Метка буквально описывает результат: angr нашёл путь.

## Что мы теперь знаем

- Символьное исполнение заменяет конкретный вход переменной и копит ограничения.
- В конце решатель (Z3) находит вход, проходящий по нужному пути.
- Главная проблема — взрыв числа путей; поэтому цель сужают.
- angr работает с бинарниками, KLEE — с LLVM-байткодом.
- Ограничение алфавита и подсказка формата сильно ускоряют решение.
