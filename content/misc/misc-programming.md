## Что такое programming-задачи в CTF

Programming (или «скриптинг») — класс задач, где вам дают *данные или сервис*, требующий автоматической обработки, и ответ нужно получить **быстрее, чем вручную**. Это может быть подсчёт чего-то в большом файле, ответ на поток вопросов от бота, поиск закономерности в последовательности или реализация алгоритма. Здесь не нужны хитрые уязвимости — нужны аккуратность и скорость написания кода.

Ключевой навык: **перевести условие в формальную спецификацию** и написать минимальный корректный солвер. Чем меньше кода, тем меньше багов.

## Типовые форматы programming-задач

- **Статистика по файлу** — «сколько уникальных IP», «сумма всех чисел», «самое частое слово».
- **Потоковые вопросы** — бот задаёт N арифметических/логических вопросов, надо отвечать в реальном времени.
- **Последовательности** — «продолжи ряд», линейные рекурренты, задачи на интерполяцию.
- **Парсинг форматов** — CSV/JSON/логи/кастомный текстовый формат.
- **Алгоритмы** — BFS/DFS, ДП, теория графов, жадные задачи.
- **Побитовые/числовые** — большие числа, модульная арифметика, битовые маски.

## Быстрый старт: каркас для файловых задач

```python
import sys, re
from collections import Counter

data = open(sys.argv[1], encoding='utf-8', errors='replace').read()

# пример: топ-5 самых частых слов длиной >=4
words = re.findall(r'[A-Za-zА-Яа-я]{4,}', data.lower())
for w, c in Counter(words).most_common(5):
    print(c, w)
```

Запуск:

```bash
$ python3 solve.py access.log
18342 error
9821 request
7410 denied
```

Для больших файлов (гигабайты) читайте построчно и не держите всё в памяти:

```python
import sys
total = 0
for line in sys.stdin:
    if line.startswith('ERROR'):
        total += 1
print(total)
```

```bash
$ zcat huge.log.gz | python3 count_errors.py
412357
```

## Интерактивные сервисы: pwntools

Когда задача — `nc host port` с потоком вопросов, используйте `pwntools`. Каркас с надёжным парсингом:

```python
from pwn import *
import re
context.log_level = 'error'

io = remote('challenge.ctf', 1337)
while True:
    try:
        line = io.recvline(timeout=5)
    except EOFError:
        break
    if not line:
        break
    m = re.search(rb'(\d+)\s*([+\-*/])\s*(\d+)', line)
    if m:
        a, op, b = int(m.group(1)), m.group(2).decode(), int(m.group(3))
        ans = {'+': a+b, '-': a-b, '*': a*b, '/': a//b}[op]
        io.sendline(str(ans).encode())
    elif b'FLAG' in line:
        print(line.decode(errors='replace'))
        break
io.close()
```

Советы: всегда задавайте `timeout`, всегда логируйте сырой ответ при ошибке, тестируйте на локальном запуске сервиса, если он приложен.

## Последовательности и интерполяция

Если даны первые члены ряда, попробуйте:

1. конечные разности (полиномиальный ряд),
2. линейную рекурренту `a[n] = p*a[n-1] + q`,
3. OEIS (для известных последовательностей).

```python
from sympy import interpolate, symbols
x = symbols('x')
# точки (0, a0), (1, a1), (2, a2) ...
poly = interpolate([(0,1),(1,4),(2,9),(3,16)], x)
print(poly)          # x**2 + 2*x + 1
print(poly.subs(x, 100))  # 10201
```

## Работа с большими числами

В Python целые — произвольной точности, но `float` теряет точность. Для модульной арифметики используйте `pow(a, b, m)` (быстрое возведение в степень по модулю):

```python
>>> pow(2, 1000000, 1000000007)
305719095
```

Для задач «найди остаток» это в разы быстрее наивного цикла. Для больших факториалов и комбинаторики — `math.comb`, `math.factorial`.

## Оптимизация: как не упасть по таймауту

- Читайте вход через `sys.stdin.buffer.read()` одним куском, если он небольшой.
- Используйте `Counter`, `set`, `defaultdict` вместо вложенных циклов.
- Предвычисляйте префиксные суммы вместо повторного суммирования.
- Для поиска в графе — итеративный BFS вместо рекурсивного DFS (риск `RecursionError`).
- Профилируйте узкое место: `python -m cProfile solve.py`.

```python
# префиксные суммы: O(n) подготовка, O(1) запрос суммы [l, r)
pref = [0]
for x in arr:
    pref.append(pref[-1] + x)
def rng(l, r):
    return pref[r] - pref[l]
```

## Типичные ошибки и подводные камни

- **Off-by-one** в диапазонах и индексах — самая частая причина неверного ответа.
- **Переполнение float** — используйте int там, где нужна точность.
- **Слишком долгий ответ боту** — оптимизируйте или предвычисляйте.
- **Неверная кодировка** при чтении файла — задавайте `errors='replace'`.
- **Игнорирование формата ответа** — часто нужен ровно флаг, без лишнего текста.
- **Рекурсия** — Python по умолчанию падает на глубине ~1000; увеличивайте `sys.setrecursionlimit` или переходите на итерацию.
- **Слишком общий парсер** — регулярки должны быть привязаны к формату сервиса, иначе «поймают» лишнее.

## Отладка солвера

Полезные приёмы:

```python
# дамп сырых данных при ошибке
import traceback
try:
    solve()
except Exception:
    print("RAW:", io.recvrepeat(0.5))
    traceback.print_exc()
```

Для локального сервиса удобно использовать `process(['./server'])` из pwntools — то же API, что и `remote`, но без сети.

## Что дальше / решение

Алгоритм действий для любой programming-задачи:

1. **Пойми формат входа** — файл, stdin, сокет? Сколько данных?
2. **Определи тип** — статистика / поток / последовательность / алгоритм.
3. **Напиши минимальный каркас** и проверь на маленьком примере.
4. **Проверь краевые случаи** — пустой вход, одно значение, максимум.
5. **Оптимизируй только при таймауте**, не раньше.
6. **Зафиксируй ответ** в нужном формате.

Дальше практикуйтесь на задачах «warmup» с автопроверкой и постепенно переходите к графам и ДП.

## Как правильно читать условие programming-задачи

Большинство провалов на programming-задачах происходят не из-за слабого кода, а из-за неверно понятого условия. Поэтому первое действие — выписать на бумагу четыре вещи: что именно дано на входе, в каком формате, что требуется вернуть и как проверяется ответ. Часто в условии указан и лимит времени, и лимит памяти — эти числа определяют, какой алгоритм вы вообще имеете право выбрать. Если сказано «до 10^5 элементов и одна секунда», наивный квадратичный алгоритм гарантированно не пройдёт, и надо сразу думать про сортировку или хеш-таблицу.

Отдельно проверяйте, что считает проверяющая система: точную строку, число, флаг в формате `FLAG{...}` или множество значений. Лишний пробел, перевод строки или лишнее слово в выводе превратят корректный по сути ответ в неверный. Когда формат неоднозначен, выведите сначала «сырой» результат и сравните с ожидаемым на примере из условия.

## Выбор языка и среды

Для CTF почти всегда оптимален Python: богатая стандартная библиотека, длинная арифметика «из коробки», удобный парсинг. Быстрый прототип на Python вы напишете за минуты. Если задача упирается в скорость, есть три пути: векторизовать вычисления через `numpy`, вынести горячий цикл в `numba` или переписать критичную часть на C и вызвать из Python. Начинать всегда стоит с чистого и понятного Python, а оптимизацию подключать только когда действительно упёрлись в таймаут.

Держите под рукой заранее подготовленные сниппеты: чтение stdin, парсинг чисел регуляркой, BFS, префиксные суммы, хеширование. Тогда на задаче вы собираете решение из готовых блоков, а не пишете всё с нуля. Это экономит драгоценные минуты соревнования.

## Как проверять решение до отправки

Всегда прогоняйте солвер на маленьком примере, для которого ответ известен вручную, и только потом — на полном входе. Если сервис локально запускается, тестируйте против него: `process(['./server'])` в pwntools даёт тот же интерфейс, что `remote`, но без сети и без риска забанить себя. Добавьте пару защитных проверок: таймаут на чтение, вывод последней строки при исключении, сохранение сырого ответа сервиса в файл. Когда что-то не сходится, эти логи экономят десятки минут слепого перебора.

## Что дальше / решение

Итог по programming-задачам: сначала формализуйте условие (вход, формат, лимиты, критерий), затем пишите минимальный солвер на Python, проверяйте на маленьком примере, оптимизируйте только при реальном таймауте и всегда фиксируйте ответ строго в требуемом формате. Отдельно ведите библиотеку переиспользуемых сниппетов — со временем вы будете собирать решения из готовых блоков за считанные минуты, а весь ресурс тратить на разбор нестандартной логики конкретной задачи.
