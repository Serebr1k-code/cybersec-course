## Вопрос, с которого всё начинается

Matroska (`.mkv`) и WebM — это контейнеры на базе **EBML** (Extensible Binary Meta Language). Внутри — дерево элементов с числовыми ID и размерами переменной длины. Это не текстовый формат, и «глазами» в нём ничего не видно. В CTF и форензике Matroska используют, чтобы спрятать данные в необычных элементах, а парсеры EBML регулярно ломают. Разберём, как читать EBML с нуля.

## Наш пример: первые байты .mkv

```
$ xxd -l 32 sample.mkv
00000000: 1a45 dfa3 9f 42 86 81 01 42 f7 81 01 42 f2 81  .E..B....B...B..
00000010: 04 42 f3 81 08 42 82 88 6d 61 74 72 6f 73 6b 61  .B...B..matroska
```

Здесь `1a45dfa3` — ID элемента EBML Header, `9f` — его размер, далее вложенные элементы. Разберём, как это читается.

## Шаг 1: VINT — числа переменной длины

EBML использует VINT (variable-length integer). Первый байт задаёт длину: количество ведущих нулей до первой единицы определяет, сколько всего байтов. Например, `0x9f` = `1001 1111`: первый бит 1 → длина 1 байт, а значение — оставшиеся 7 бит (`0x1f` = 31). `0x42 0x86` — ID из двух байтов. Есть два вида VINT: для ID (значение с маркером) и для размеров (маркер отбрасывается). Непонимание этого различия — источник ошибок в парсерах.

## Шаг 2: дерево элементов

EBML — дерево. Корень — EBML Header, затем Segment, внутри — Info, Tracks, Cluster, Cues, Attachments, Chapters. Каждый элемент: ID, размер, данные. Если размер «неизвестен» (все единицы), элемент тянется до конца родителя. `Segment` часто имеет неизвестный размер — это позволяет стримить файл.

## Шаг 3: Matroska-структура

Ключевые элементы Matroska: `Info` (тайминги, длительность), `Tracks` (видео/аудио/субтитры), `Cluster` (пакеты данных с таймкодами), `Cues` (индекс), `Attachments` (вложенные файлы, например шрифты), `Chapters`, `Tags`. В `Attachments` можно положить произвольный файл — легальный способ «спрятать» данные. `Void`-элементы — пустое место, которое можно использовать как padding или носитель.

## Шаг 4: где прячут данные

Типичные места: `Void` (пустой элемент с произвольным содержимым), `Attachments` (вложенный файл), неиспользуемые `Tags`, лишние байты после `Segment`, «lacing» (упаковка нескольких фреймов в один блок), нестандартные элементы. Также данные можно спрятать, изменив таймкоды или размеры «незаметно». Парсер, который доверяет размерам, может «проглотить» канал.

## Шаг 5: уязвимости парсеров

Парсеры EBML/Matroska (ffmpeg, libmatroska, mkvparse) исторически имели баги: целочисленные переполнения при вычислении размеров, бесконечные циклы на самоссылающихся элементах, чтение за границами при неверных VINT. Правила: проверять, что размер не превышает файл, что вложенность ограничена, что VINT корректны. В CTF такие баги моделируют реже, но в реальных аудитах они серьёзны.

## Шаг 6: инструменты разбора

`mkvinfo`/`mkvextract` (MKVToolNix) показывают дерево и извлекают дорожки/вложения. `ffprobe` даёт сводку. `python` + `ebmlite`/`mkvparse` — для скриптов. Для ручного разбора достаточно `xxd` и понимания VINT.

## Полный прогон: поиск скрытого элемента

Задача: в `.mkv` спрятан `Void`-элемент с текстом. Нужно обойти дерево, найти `Void` и извлечь данные.

```
$ python3 ebml.py sample.mkv
Segment > Void (size 64)
data: nto{ebml_v1nt_h1dd3n_3l3m3nt}
flag: nto{ebml_v1nt_h1dd3n_3l3m3nt}
```

Данные лежат в легальном элементе, который плееры игнорируют.

## Если не сработало

Если `Void` пуст, смотрите `Attachments` (извлеките `mkvextract attachments`), `Tags`, байты после последнего элемента, «lacing» в блоках. Иногда данные спрятаны в неиспользуемых старших битах VINT или в порядке элементов.

## Как читать EBML

Начните с EBML Header, затем спускайтесь в Segment. Для каждого элемента читайте ID (VINT), размер (VINT), данные. Ищите `Void`, `Attachments`, «хвосты». Для больших файлов используйте `mkvinfo`.

## VINT подробнее

Разберём VINT на числах. ID-элемента EBML Header — `1a 45 df a3`. Это четыре байта, начинающиеся с `0x1a` = `0001 1010`. Первый байт имеет три ведущих нуля, значит длина ID — 4 байта. Сам ID — это все 4 байта целиком (`1a45dfa3`), включая маркер. Размер элемента кодируется иначе: маркер отбрасывается. Байт `0x9f` = `1001 1111`: один ведущий ноль до первой единицы → длина 1 байт; значение — оставшиеся 7 бит, то есть `0x1f` = 31. Байт `0x42` = `0100 0010`: длина 2 байта. Если первый байт `0xff`… — все биты единицы, это «неизвестный размер» (элемент тянется до конца родителя). Эта двойственность (ID с маркером, размер без) — классический источник ошибок: парсер, перепутавший правила, читает не те значения и «съезжает». При ручном разборе всегда выписывайте: ID (VINT с маркером), размер (VINT без маркера), затем данные.

## Matroska на практике

Типичный MKV начинается с `EBML Header` (ID `1a45dfa3`), затем `Segment` (ID `18538067`). Внутри Segment: `Info` (ID `1549a966`, содержит `TimecodeScale`, `Duration`), `Tracks` (`1654ae6b`, описывает дорожки), `Cluster` (`1f43b675`, содержит блоки данных), `Cues` (`1c53bb6b`, индекс), `Attachments` (`1941a469`), `Tags` (`1254c367`), `Chapters` (`1043a770`). `Void` имеет ID `ec`. Зная эти ID, можно вручную пройтись по файлу: читать ID, размер, рекурсивно входить в контейнерные элементы. `mkvinfo -v sample.mkv` покажет дерево с адресами, что удобно для проверки своего парсера. Для извлечения вложений: `mkvextract attachments sample.mkv`.

## Где именно прячут данные

Практика CTF показывает конкретные места. Первое: `Void`-элемент с ненулевым содержимым — плееры его игнорируют, но данные там. Второе: `Attachments` — легальный вложенный файл (например, `flag.txt`), извлекается `mkvextract`. Третье: `Tags` — произвольные пары ключ-значение, часто не проверяются. Четвёртое: байты после последнего элемента Segment — «хвост», который парсеры не читают. Пятое: неиспользуемые старшие биты в VINT. Шестое: порядок элементов или дополнительные пустые элементы. Седьмое: несколько Segment (streaming). Для поиска: `binwalk`, `xxd`, `mkvinfo`, плюс собственный обход дерева.

## Мини-практика: парсер EBML

Напишите функцию `read_vint(data, pos, keep_marker)`, которая возвращает значение и новую позицию. Затем `walk(data, start, end)`: читает ID, размер, если элемент контейнерный — рекурсия, иначе — данные. Примените к `.mkv` и сравните дерево с `mkvinfo`. Затем напишите поиск `Void`-элементов и вывод их содержимого. Это упражнение даёт полное понимание формата и пригодится для любого EBML-based контейнера (WebM, некоторые субтитры).

## Итог

EBML — дерево с VINT-числами, где ID и размеры кодируются по-разному. Matroska строится из Segment/Info/Tracks/Cluster/Attachments. Данные прячут в `Void`, `Attachments`, `Tags` и «хвостах». Парсеры уязвимы к неверным размерам и VINT. Разбор — от `xxd` до собственного обхода дерева, с проверкой через `mkvinfo`.

## Проверка собственного парсера

Когда вы напишете обход дерева, проверьте его на реальных файлах: `mkvinfo -v` покажет адреса и размеры элементов, и вы сможете сверить свой вывод. Обратите внимание на элементы с неизвестным размером (например, Segment в стриминговых файлах): ваш парсер должен корректно тянуть их до конца родителя. Проверьте вложенность: рекурсивный обход не должен уходить в бесконечность на «самоссылающихся» структурах (защита — лимит глубины). Проверьте границы: размер элемента не должен превышать файл; иначе — ошибка, а не чтение за пределами. Эти три проверки (неизвестный размер, глубина, границы) — то, что отличает надёжный парсер от уязвимого.

## Матрешка форматов

Matroska может содержать внутри другие форматы: видео (H.264/VP9/AV1), аудио (AAC/Opus/FLAC), субтитры (SRT/ASS/VTT), вложения (шрифты, картинки). Поэтому разбор MKV часто ведёт к разбору вложенных потоков. В CTF это значит: найдя подозрительный элемент, извлеките его (`mkvextract tracks`) и разбирайте отдельно. Иногда флаг лежит в субтитровой дорожке, иногда — во вложении-шрифте, иногда — в «сырых» байтах Cluster. Поэтому не останавливайтесь на первом уровне: контейнер — это матрешка, и данные могут быть глубоко.

## Практический чек-лист

Проверьте: EBML Header и Segment; элементы с неизвестным размером; `Void`; `Attachments`; `Tags`; `Chapters`; байты после последнего Segment; нестандартные ID; извлеките все дорожки (`mkvextract`) и вложения; прогоните `binwalk`. Каждый пункт — место для данных или бага. Держите `mkvinfo` под рукой как эталон при отладке своего парсера.

## Итог по формату

EBML — редкий пример формата, где «размер» и «ID» кодируются похоже, но по разным правилам. Именно это делает его и элегантным, и коварным для парсеров. Matroska строится поверх EBML как дерево из нескольких ключевых элементов, и большинство данных для CTF лежит в `Void`, `Attachments`, `Tags` и «хвостах». Навык ручного обхода EBML переносится на WebM и другие EBML-форматы. Держите под рукой таблицу ID и `mkvinfo` — этого достаточно, чтобы разобрать почти любой MKV.
