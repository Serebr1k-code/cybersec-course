## Вопрос, с которого всё начинается

Тебе дали файл `level.dat` из мира Minecraft. Это бинарные данные, но задача просит достать из них что-то конкретное — или изменить. Как читать и править формат, у которого нет текстового представления?

Ответ: это **NBT** (Named Binary Tag) — древовидный бинарный формат, на котором стоят сохранения Minecraft.

## Наш пример: level.dat

```
$ file level.dat
level.dat: gzip compressed data
$ gzip -dc level.dat | xxd | head -2
00000000: 0a00 000a 0009 4461 7461 5665 7273 696f  ......DataVersio
```

Внутри gzip — структура, начинающаяся с `0a 00 00` (тег Compound, имя длиной 0). Разберём NBT.

## Шаг 1: что такое NBT

**NBT** — дерево именованных тегов. Каждый тег: тип (байт), имя (2-байтовая длина + строка), значение. Типы:

| ID | Тип |
|---|---|
| 1 | Byte |
| 2 | Short |
| 3 | Int |
| 4 | Long |
| 5 | Float |
| 6 | Double |
| 7 | ByteArray |
| 8 | String |
| 9 | List |
| 10 | Compound (словарь) |
| 11 | IntArray |

Корень — обычно Compound (10).

## Шаг 2: разбор вручную

```
type=10 (Compound), name=""
  type=3 (Int), name="DataVersion", value=3465
  type=10 (Compound), name="Player"
    type=8 (String), name="Name", value="Steve"
```

Каждый Compound — вложенный словарь, List — массив однотипных элементов. Разбор рекурсивный: читаешь тип и имя, затем значение по типу.

## Шаг 3: сжатие

Файлы NBT обычно сжаты: `level.dat` — **gzip**, `playerdata/*.dat` — тоже, а регионы (`.mca`) — **zlib**-чанками. Поэтому первым делом распаковывают (`gzip -dc`, `zlib.decompress`), затем парсят NBT.

## Шаг 4: формат Anvil (регионы)

Мир Minecraft хранится в **регионах** — файлах `.mca`, каждый покрывает 32×32 чанка. Регион — таблица из 1024 указателей: для каждого чанка — смещение (3 байта) и размер сектора (1 байт). Чанки внутри сжаты zlib и содержат NBT. Чтобы достать чанк: прочитать указатель, распаковать, распарсить NBT.

## Шаг 5: редактирование

NBT легко менять: читаешь дерево, меняешь значение, сериализуешь обратно, сжимаешь. Так читеры правят инвентарь, координаты, здоровье. В CTF — правят данные, чтобы «разблокировать» что-то, или читают спрятанное.

## Шаг 6: инструменты

- **nbtlib** (Python) — удобный разбор и правка.
- **NBTExplorer** — графический редактор.
- **python-nbt** — альтернатива.
- **gzip/zlib** — распаковка.

```
$ python3 - <<'PY'
import nbtlib
nbt = nbtlib.load('level.dat')
print(nbt['Data']['Player']['Name'])
PY
Steve
```

## Полный прогон

```
$ python3 - <<'PY'
import gzip, nbtlib
nbt = nbtlib.File.parse(gzip.open('flag.dat','rb'))
print(str(nbt).replace('\n',' '))
PY
... String "secret" = nto{nbt_b1n4ry_tr33} ...
```

Флаг — значение одного из тегов.

## Как защищаться

- **Валидировать** размеры и глубину NBT (защита от переполнений).
- **Проверять** пределы при разборе List/Compound.
- **Не доверять** клиентским данным (инвентарь, координаты).
- **Ограничивать** вложенность рекурсии.

## Что мы теперь знаем

- NBT — дерево именованных типизированных тегов.
- Разбор рекурсивный: тип, имя, значение.
- Файлы сжаты gzip/zlib; регионы Anvil — таблица указателей.
- NBT можно читать и править (nbtlib, NBTExplorer).
- Флаг часто лежит в значении тега.

## List и типизация

List в NBT содержит элементы одного типа: сначала байт типа, затем длина (Int), затем значения. Если тип элементов разный — это уже невалидный NBT. Парсер должен проверять типы; иначе чтение выйдет за границы. В CTF «сломанный» List часто и есть место, где спрятаны данные или где ждёт уязвимость.

## Разбор чанка региона

Регион `.mca`: заголовок 8 КиБ — 1024 указателя (по 4 байта: 3 байта смещения сектора, 1 байт числа секторов). Чтобы прочитать чанк: берёшь указатель, идёшь по смещению (×4096), читаешь 4-байтовую длину, затем zlib-данные, распаковываешь, парсишь NBT. Каждый чанк содержит `Level` с блоками, сущностями и т.д.

## Правка и обратная сериализация

NBT легко менять: читаешь дерево, меняешь значение, сериализуешь и сжимаешь. Важно сохранить порядок тегов (в NBT он значим) и типы. `nbtlib` делает это прозрачно. Так правят инвентарь, координаты, достижения. В CTF — «разблокировать» сундук или изменить значение, которое проверяет игра.

## Другие форматы Minecraft

Помимо NBT/Anvil, Minecraft использует: `level.dat` (метаданные мира), `playerdata/<uuid>.dat` (данные игрока), `advancements`, `stats`. Все — NBT, часто gzip. Также есть SNBT (текстовое представление NBT) и JSON-структуры для датапаков. Понимание NBT открывает все они.

## Ограничения и защита

Опасности NBT: глубокая рекурсия (переполнение стека), огромные List/Array (переполнение памяти), неверные длины. Защита — ограничить глубину и размеры, проверять типы, не доверять клиентским данным. Сервер Minecraft именно так и делает: валидирует всё, что приходит от клиента.

## Шпаргалка

`nbtlib` (Python): `nbtlib.load(path)`, доступ как к словарю, `File.parse`. `gzip -dc level.dat`, `zlib.decompress` для регионов. NBTExplorer — GUI. Помни типы: 10 = Compound, 9 = List, 8 = String, 3 = Int.

## Итог

NBT — дерево именованных типизированных тегов; Anvil — контейнер чанков. Файлы сжаты gzip/zlib. Читать и править легко (`nbtlib`), но при разборе нужно валидировать типы, глубину и размеры. Флаг часто — значение тега.

## SNBT и датапаки

**SNBT** (Stringified NBT) — текстовое представление NBT: `{DataVersion:3465,Player:{Name:"Steve"}}`. Оно используется в командах и датапаках. Полезно тем, что позволяет читать структуру глазами и править текстом, а затем конвертировать обратно. Если в задаче есть SNBT, разбор упрощается до чтения строки.

## Разбор чанка на Python

```
import zlib, nbtlib, struct
data = open('r.0.0.mca','rb').read()
off = struct.unpack('>I', b'\x00' + data[0:3])[0] * 4096
ln = struct.unpack('>I', data[off:off+4])[0]
chunk = nbtlib.File.parse(zlib.decompress(data[off+4:off+4+ln]))
print(chunk['Level']['xPos'], chunk['Level']['zPos'])
```

Так достаётся NBT чанка из региона — основа разбора мира.

## Пример аудита

Проверь: ограничена ли глубина рекурсии; проверяются ли длины List/Array; доверяет ли сервер клиентским NBT; логируются ли аномалии. Minecraft-сервер валидирует клиентские данные именно из-за этих рисков — хороший пример защиты.

## Сравнение с другими игровыми форматами

Игровые сохранения бывают самыми разными: NBT (Minecraft), проприетарные бинарники, сжатые архивы, JSON. Общий подход: определить формат по магии/структуре, распаковать, разобрать дерево/записи. NBT — удобный учебный пример, потому что формат открытый и хорошо описан.

## Итог урока

NBT — дерево именованных типизированных тегов; Anvil — контейнер чанков мира. Файлы сжаты gzip/zlib, а читать и править их легко через `nbtlib` и NBTExplorer. При разборе валидируй типы, глубину и размеры. Флаг обычно лежит значением одного из тегов.

## Практический сценарий CTF

Задача: из мира Minecraft достать флаг. Решение: определить файл (`level.dat`, `playerdata`, регион), распаковать gzip/zlib, распарсить NBT (`nbtlib`), пройти по дереву и найти строковый тег с меткой. Если флаг спрятан в нестандартном теге — поможет полный дамп дерева.

## Что тренирует эта тема

NBT учит разбору **бинарных деревьев**: тип → имя → значение, с рекурсией для Compound/List. Это тот же навык, что нужен для ASN.1, BSON, Protobuf-структур и любых тегированных форматов. Освоив NBT, ты быстрее разбираешь любые иерархические бинарные данные.

## Частые находки в аудите

Три частые проблемы: неограниченная рекурсия (переполнение стека); отсутствие проверки длин List/Array (переполнение памяти); доверие клиентским NBT. Исправления: лимит глубины, проверка размеров, валидация на сервере.

## Итог

NBT — дерево именованных типизированных тегов; Anvil — контейнер чанков. Файлы сжаты gzip/zlib, читаются и правятся через `nbtlib`. При разборе валидируй типы, глубину и размеры. Навык разбора бинарных деревьев переносится на многие форматы.

## Разбор дерева рекурсией

```
def walk(tag, depth=0):
    print('  '*depth, type(tag).__name__, getattr(tag,'name',''), repr(tag)[:40])
    if isinstance(tag, dict):
        for v in tag.values():
            walk(v, depth+1)
```

Такой обход печатает всё дерево NBT — быстрый способ найти нужный тег. Для больших файлов ограничивай глубину, чтобы не уйти в рекурсию бесконечно (и не дать это сделать атакующему).

## SNBT для быстрой правки

Если нужно изменить одно значение, удобно выгрузить дерево в SNBT, поправить текст и загрузить обратно. Это быстрее, чем программная правка, и нагляднее. Команды Minecraft тоже принимают SNBT — так что навык полезен и за пределами разбора файлов.

## Итоговая шпаргалка

`nbtlib.load('level.dat')` — чтение; `nbtlib.File.parse(gzip.open(...))` — из сжатого; `zlib.decompress` — для региона; NBTExplorer — GUI. Помни типы: 10 Compound, 9 List, 8 String, 3 Int, 7 ByteArray. Ограничивай глубину и размеры при разборе недоверенных файлов.

## Развёрнутый пример: почему сервер не доверяет клиенту

Клиент Minecraft присылает серверу NBT с данными о себе: инвентарь, позицию, достижения. Если бы сервер доверял этому NBT без проверки, клиент мог бы прислать «бесконечный» List предметов, вызвать переполнение памяти или подделать координаты. Поэтому сервер валидирует структуру: проверяет типы, ограничивает размеры, отвергает некорректные теги. Это учебный пример принципа «не доверяй сериализованным данным от клиента»: тот же подход нужен в любом API, принимающем бинарные структуры — NBT, Protobuf, Thrift или Avro.

## Краткий итог по разбору

NBT читается рекурсией: тип, имя, значение; Compound и List вложены. После распаковки gzip/zlib дерево доступно целиком, и найти нужный тег — дело нескольких строк кода. Главное при работе с недоверенными файлами — ограничивать глубину и размеры.
