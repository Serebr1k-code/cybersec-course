## Вопрос, с которого всё начинается

Контракт на StarkNet проверяет `assert(x == y)` и, казалось бы, не даёт обойти условие. Но атакующий присылает два разных числа — и проверка проходит. Как это возможно? Потому что в Cairo все числа — элементы конечного поля, и «равенство» означает равенство по модулю, а не по значению в привычном смысле.

Если вы пришли из Solidity, вы привыкли, что `uint256` — это целое с переполнением. В Cairo переполнения «в лоб» нет, зато есть заворачивание по модулю, и это ломает наивные сравнения. Разберём это на одном конкретном контракте.

## Наш пример: вывод средств

Возьмём типичную функцию вывода:

```cairo
#[external(v0)]
fn withdraw(ref self: ContractState, amount: felt252) {
    let balance = self.balances.read(get_caller_address());
    assert(amount <= balance, 'insufficient');
    self.balances.write(get_caller_address(), balance - amount);
}
```

Читается как «нельзя снять больше баланса». Мы будем вести этот контракт до конца урока: сначала поймём, из чего он собран, потом найдём, где он ломается.

## Шаг 1: что такое felt

Базовый числовой тип Cairo — `felt252`. Это **элемент конечного поля** `F_p`, где `p` — большое простое число (порядок поля, используемого STARK-доказательствами). Диапазон значений — от `0` до `p-1`.

```
$ python3 -c "p=2**251+17*2**192+1; print(p)"
3618502788666131213697322783095070105623107215331596699973092056135872020481
```

Числа «заворачиваются» по модулю `p`: `p + 1` и `1` — это одно и то же значение. Привычное `x < y` тоже определено только внутри `[0, p)`. Именно отсюда растут баги. Слово «felt» — сокращение от «field element», элемент поля.

## Шаг 2: почему нельзя просто так переполнить

В Solidity `uint8 x = 255; x + 1;` даёт `0` — переполнение. В Cairo `felt252` не переполняется: `p-1 + 1` даёт `0`, но `p-1 + 2` даёт `1`, и никакой ошибки нет. Компилятор не предупредит: с его точки зрения это корректная арифметика поля.

```
$ python3 -c "p=3618502788666131213697322783095070105623107215331596699973092056135872020481; print((p-1+2)%p)"
1
```

Именно поэтому всякий раз, когда контракт сравнивает или проверяет границы, он обязан использовать операции, которые **разбивают число на биты** и проверяют диапазон, а не полагаться на арифметику.

## Шаг 3: сравнение через вычитание

Как контракт понимает `amount <= balance`? Компилятор реализует сравнение через **проверку диапазона** разности. Если `amount - balance` (по модулю `p`) — маленькое число, значит `amount <= balance`; если оно близко к `p`, значит наоборот. Для этого существует оператор `<=` в `core`, который внутри разбивает числа на биты и проверяет границы.

Опасность — когда разработчик пишет сравнение **вручную**, например так:

```cairo
let diff = amount - balance;   // может завернуться в огромное число
assert(diff < 1000, 'ok');     // «проверка» ничего не гарантирует
```

Здесь `diff` — элемент поля. Если `amount < balance`, `diff` станет `p - (balance - amount)` — числом, близким к `p`, и `< 1000` не выполнится. Но если `amount` специально подобран так, что разность «заворачивается» в малое число, условие обманывается. Главный практический урок: **никогда не пишите сравнения арифметикой вручную**, используйте библиотечные `<=`, которые корректно проверяют диапазон.

## Шаг 4: u256 и явные типы

Когда нужно настоящее 256-битное число (например, для суммы токенов), в Cairo есть `u256`. Но это не «родной» тип поля: `u256` — структура из двух `felt252` (low и high), и операции над ней явные:

```cairo
let a: u256 = 2_u256.pow(255);
let b: u256 = a + 1_u256;   // не заворачивается: u256 имеет проверку
```

Смешивать `felt252` и `u256` без приведения нельзя — компилятор заставит конвертировать через `TryInto`. Ошибка новичка — считать, что `felt252` и `u256` взаимозаменяемы. Это разные модели: `felt` заворачивается, `u256` проверяется.

## Шаг 5: деление и обратные элементы

В поле нет «обычного» деления: `a / b` означает `a * b^{-1} mod p`, где `b^{-1}` — обратный элемент. Если `b == 0`, обратного элемента нет, и операция паникует. Отсюда классический баг: контракт делит на «сумму вкладов», не проверив её на ноль, и любой вызов с нулевой суммой роняет контракт (DoS).

```cairo
let share = amount * total / pool;   // если pool == 0 -> panic
```

Правильно — проверять знаменатель явно и обрабатывать нулевой случай. Обратите внимание: `a * b / c` — это `(a * b) * c^{-1}`, и промежуточное произведение тоже может «завернуться», если не следить за размером.

## Шаг 6: ascii vs felt

Ещё один источник путаницы — строки. `'insufficient'` — это не `String`, а **short string**, упакованная в `felt252`. Ошибка в кавычках (`'insufficient'` vs `'insuff1cient'`) компилируется молча, потому что обе — валидные felt. В логах вы увидите только числовой код, и отладка превращается в головоломку. Для длинных строк используйте `ByteArray`, а коды ошибок держите короткими и проверяйте тестами.

## Шаг 7: где живут баги

Сводка типовых ошибок Cairo/StarkNet:

| Место | Что искать |
|---|---|
| `assert(x <= y)` | сделано ли вручную, есть ли range check |
| деление | проверен ли знаменатель на 0 |
| `felt252` под длинные данные | не должно быть — нужен `ByteArray` |
| сравнение адресов | `ContractAddress` vs `felt252` |
| переполнение | `u256` требует явных операций, `felt` заворачивается |
| storage layout | порядок слотов и `LegacyMap` |

## Полный прогон: обход сравнения

Представим задачу: контракт проверяет `amount <= balance`, но использует ручную арифметику без range check, а `balance` берётся из хранилища. Атакующий присылает `amount`, для которого разность по модулю попадает в «разрешённый» интервал.

```
$ python3 solve.py
p = 3618502788666131213697322783095070105623107215331596699973092056135872020481
balance = 5
amount  = p - 1        # "огромное" число
# подбираем amount так, чтобы (amount - balance) mod p было малым
flag: nto{c41r0_f3lt_0v3rfl0w}
```

Контракт «увидел» маленькую разность и пропустил снятие. Это не ошибка математики — это ошибка того, что разработчик считал `felt` обычным числом.

## Если не сработало

Иногда обойти проверку «в лоб» нельзя, потому что рядом стоит корректный range check. Тогда смотрите на другие места: деление на ноль, смешение `felt`/`u256`, упакованные строки. В реальных задачах комбинация двух слабых мест часто даёт эксплойт там, где каждое по отдельности безобидно.

## Что мы теперь знаем

- `felt252` — элемент конечного поля, а не 256-битное целое.
- Сравнения нельзя писать «на глаз»: нужен корректный range check.
- Деление требует проверки знаменателя на ноль.
- Строки — это упакованные felt; опечатки компилируются.
- Адреса и числа — разные типы, их нельзя смешивать.
- `u256` проверяется, `felt252` заворачивается.

## Как читать Cairo-контракт

Начинайте с типов: где `felt252`, где `u256`, где `ContractAddress`. Затем — со всех сравнений и делений. И только потом — с бизнес-логики. Большинство багов живут именно в первых двух категориях.

## Сравнение с EVM: где привычки подводят

Человек, пришедший из Solidity, приносит с собой три привычки, и все три в Cairo опасны. Первая — «число переполняется, поставлю SafeMath». В Cairo переполнения нет, но есть заворачивание по модулю, и `SafeMath` не спасёт от логической ошибки сравнения. Вторая — «`uint256` — это целое». В Cairo `felt252` — элемент поля, а `u256` — отдельная структура с явными операциями. Третья — «строки можно сравнивать». В Cairo короткие строки — это числа, и `'a' == 'a'` работает, но `'a'` и `'а'` (разные кодировки) — уже разные felt.

Отсюда практическое правило: при чтении Cairo-контракта первым делом выписывайте типы всех входов. Если видите `felt252` там, где ожидается сумма денег, — это красный флаг. Если видите `assert(a < b)` без `u256` — проверьте, не написан ли range check вручную.

## Разбор второго примера: голосование

Возьмём контракт голосования, который считает вес голоса как долю от общего числа токенов:

```cairo
fn vote(ref self: ContractState, amount: felt252) {
    let total = self.total_supply.read();
    let weight = amount * 1000 / total;   // доля в промилле
    self.votes.write(get_caller_address(), weight);
}
```

Здесь две проблемы. Первая: `amount * 1000` может «завернуться» по модулю `p`, если `amount` велик, и вес окажется произвольным. Вторая: `total` может быть нулём в момент до первого минта — деление на ноль даст панику и заблокирует голосование. Оба бага — следствие того, что разработчик мыслил в терминах «обычных» чисел.

Правильная версия использует `u256` и проверку:

```cairo
fn vote(ref self: ContractState, amount: u256) {
    let total: u256 = self.total_supply.read();
    assert(total.is_non_zero(), 'no supply');
    let weight = (amount * 1000_u256) / total;
    self.votes.write(get_caller_address(), weight);
}
```

## Частые вопросы новичков

Почему `p` такое странное? Порядок поля выбран так, чтобы STARK-доказательства были эффективны: `p = 2^251 + 17 * 2^192 + 1`. Это простое число, и все вычисления идут по этому модулю. Почему `felt252`, а не `felt256`? Потому что верхние биты заняты служебными флагами виртуальной машины, и «полных» 256 бит в одном слове нет. Что делать со строками длиннее 31 символа? Использовать `ByteArray` — динамический массив байт, который компилируется в несколько felt.

## Практика без лаборатории

Если у вас нет devnet, можно проверить арифметику поля обычным Python: `(a - b) % p` покажет, во что «завернётся» разность. Возьмите `p` из шага 1, подставьте `balance = 5`, `amount = p - 1` и посмотрите на результат. Это быстрый способ понять, почему сравнение через вычитание ненадёжно. Дальше напишите маленький Cairo-контракт с намеренно слабым сравнением и убедитесь, что `snforge`-тест на «невозможный» сценарий проходит.
