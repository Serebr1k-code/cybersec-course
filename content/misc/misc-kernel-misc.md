## Вопрос, с которого всё начинается

У тебя есть бинарь, который читает `flag.txt`, а потом печатает «nope». Или песочница, которая запрещает запускать shell. Или задача «посчитай, какие системные вызовы делает процесс». Во всех случаях ответ лежит на уровне **ядра** — в системных вызовах, `/proc` и фильтрах. Даже без настоящей эксплуатации ядра понимание этого слоя решает массу misc- и pwn-задач.

## Наш пример: бинарь, который печатает «nope»

Запускаем:

```bash
$ ./chall
nope
```

Флага нет, хотя по условию он должен читаться из `flag.txt`. Первый инструмент — `strace`: он показывает **системные вызовы** (syscalls) процесса — все обращения к ядру за файлами, памятью, сетью.

```bash
$ strace -e trace=openat,read,write ./chall
openat(AT_FDCWD, "flag.txt", O_RDONLY) = 3
read(3, "flag{...}", 64) = 33
write(1, "nope\n", 5) = 5
```

Читается так: процесс открыл `flag.txt` (получил дескриптор 3), прочитал оттуда 33 байта — это и есть флаг! — но в `stdout` вывел «nope». **Флаг уже прочитан, просто не напечатан.** Значит, задача сводится к тому, чтобы перехватить вывод.

## Перехватываем вывод в отладчике

Ставим точку останова на `write` и подменяем указатель на строку:

```bash
$ gdb ./chall
(gdb) break write
(gdb) run
(gdb) x/s $rsi      # что собирались вывести
# 0x...: "nope\n"
(gdb) set $rsi = <адрес буфера с флагом из read>
(gdb) continue
# flag{...}
```

`$rsi` — регистр со вторым аргументом `write` (что печатать). Подменив его на буфер, куда лёг флаг, мы получаем флаг, не меняя логику программы. Это типовой приём для задач «данные есть, но вывод подменён».

## /proc: окно в ядро и процессы

`strace` показывает вызовы «в моменте», а `/proc` — постоянное окно в состояние ядра. Для нашего процесса полезны:

| Путь | Что даёт |
|------|----------|
| `/proc/self/maps` | карта памяти процесса |
| `/proc/self/environ` | переменные окружения |
| `/proc/self/fd/` | открытые файловые дескрипторы |
| `/proc/self/cmdline` | аргументы запуска |
| `/proc/self/status` | состояние, включая `Seccomp` и capabilities |

```bash
$ cat /proc/self/status | grep -E 'Seccomp|Cap'
Seccomp: 2
```

`Seccomp: 2` — важнейший сигнал: значит, на процесс наложен **фильтр системных вызовов**. Если видишь это в задаче про песочницу — ищи, какие именно вызовы разрешены. Заметим: `/proc/self` — это *свой* процесс; чтобы посмотреть чужой, используй `/proc/<pid>/`.

## Syscall ABI: где лежат номер и аргументы

Чтобы понимать shellcode и фильтры, надо знать, как syscall передаётся. На x86-64 номер вызова кладётся в регистр `rax`, аргументы — в `rdi, rsi, rdx, r10, r8, r9`, а сам вызов делается инструкцией `syscall`:

```nasm
; write(1, msg, len)
mov rax, 1        ; SYS_write
mov rdi, 1        ; fd = stdout
lea rsi, [msg]
mov rdx, len
syscall
```

Обрати внимание: четвёртый аргумент — `r10`, а не `rcx` (его занимает `syscall`). Путаница в регистре — частая причина «не работает». На aarch64 всё иначе: номер в `x8`, аргументы в `x0..x5`, вызов — `svc #0`. Номера вызовов смотри в `/usr/include/asm/unistd_64.h` или через `ausyscall --dump`.

## seccomp: дампим фильтр песочницы

`seccomp` (secure computing) — механизм, который ограничивает доступные процессу syscalls. Фильтр — это BPF-программа, которая на каждый вызов возвращает `ALLOW`, `ERRNO` или `KILL`. Важно, что фильтр проверяет и **архитектуру**: типичная программа начинается с проверки `A = arch` и убивает процесс, если архитектура не совпадает, — поэтому обход через другой ABI не всегда проходит. Дамп фильтра делается утилитой `seccomp-tools`:

```bash
$ seccomp-tools dump ./chall
 line  CODE  JT  JF  K
 0009: 0x15 0x00 0x01 0x00000002  if (A != open) goto 0011
 0010: 0x06 0x00 0x00 0x7fff0000  return ALLOW
 0011: 0x06 0x00 0x00 0x00050000  return ERRNO(0)
```

Из дампа видно: `open` разрешён, а всё остальное получает ошибку. В pwn-задачах типичный фильтр — «`execve` запрещён, но `open`/`read`/`write` разрешены». Тогда shell не получить, но флаг можно прочитать, сложив из разрешённых вызовов цепочку **ORW** (open-read-write):

```python
from pwn import *
context.arch = 'amd64'
sc  = shellcraft.open('flag.txt')
sc += shellcraft.read('rax', 'rsp', 0x100)
sc += shellcraft.write(1, 'rsp', 0x100)
print(asm(sc).hex())
```

Если запрещён и `open`, а разрешён `openat` — меняем вызов на `shellcraft.openat(0, 'flag.txt', 0)`. Цикл «дамп → подбор разрешённых syscalls → ORW → проверка» решает большинство sandbox-задач. Если получаешь `SIGSYS` — значит, вызвал запрещённый вызов, сверься с дампом.

## eBPF и bpftrace

`eBPF` позволяет исполнять проверенные программы прямо в ядре. Высокоуровневый способ их писать — `bpftrace`:

```bash
$ bpftrace -e 'tracepoint:syscalls:sys_enter_openat { printf("%s %s\n", comm, str(args->filename)); }'
cat /etc/passwd
```

Это печатает, какой процесс и какой файл открывает. В задачах про «kernel misc» через `bpftrace` можно посчитать частоту syscalls (`@[probe] = count()`), перехватить `read` и подменить данные, почитать `tracefs` в `/sys/kernel/tracing/`.

## /sys и глобальные узлы /proc

Помимо `/proc/<pid>/*`, у `/proc` есть глобальные узлы, и в задачах про изоляцию они важнее всего:

| Узел | Что даёт |
|------|----------|
| `/proc/kallsyms` | адреса символов ядра (при `kptr_restrict` будут нули) |
| `/proc/modules` | загруженные модули ядра |
| `/proc/sys/*` | tunables (например, `kernel.randomize_va_space`) |
| `/proc/self/mountinfo` | точки монтирования |

`/sys` — второй интерфейс ядра: там устройства и подсистемы (`/sys/kernel/`, `/sys/fs/cgroup/`). Иногда «kernel misc» сводится не к эксплуатации ядра, а к чтению правильного узла: например, `/proc/sys/kernel/core_pattern` определяет программу обработки крашей, и через него исторически сбегали из контейнеров. Полезно помнить и про **vDSO** — отображённую ядром библиотеку, ускоряющую `gettimeofday`/`clock_gettime` без перехода в ядро: в дампе `strace` этих вызовов не будет.

Ещё один нюанс — **таблицы syscall зависят от ABI**. У x86_64, x32 и i386 разные номера вызовов. Этим пользуются в seccomp-обходах: фильтр настроен под x86_64, а вызов делается через i386 (`int 0x80`) с другими номерами и может не попасть под правило.

## Что мы теперь знаем

- `strace` показывает **системные вызовы**, `ltrace` — библиотечные функции.
- Часто данные **уже прочитаны**, но вывод подменён — спасает breakpoint на `write`.
- `/proc/<pid>/*` — окно в процесс; `Seccomp: 2` означает активный фильтр.
- На x86-64 номер syscall — в `rax`, аргументы — `rdi/rsi/rdx/r10/r8/r9`.
- `seccomp-tools dump` показывает фильтр; из разрешённых вызовов собирают **ORW**.
- `bpftrace` — трассировка на eBPF.
