## Вопрос, с которого всё начинается

HTTP кажется простым: запрос — это текст, ответ — текст. Но именно в этом тексте прячется масса misc-задач: нестандартные заголовки, дублирование, chunked-кодирование, контрабанда запросов. Часто задача звучит как «сервер ведёт себя странно — разберитесь». Ключ — научиться работать с HTTP на уровне **байтов**, а не через «умный» клиент.

Разберём это на задаче, где флаг доступен «только с localhost».

## Наш пример: флаг «только с localhost»

Эндпоинт `/flag` отдаёт секрет, если запрос пришёл будто бы с самого сервера. Обычный запрос через curl:

```
$ curl -s http://chal.ctf/flag
forbidden
```

Доступ закрыт. Нам нужно убедить сервер, что мы — он сам.

## Шаг 1: говорим с сервером сырыми байтами

`curl` — удобный, но он «причёсывает» запрос: добавляет свои заголовки, нормализует переводы строк, иногда отвергает нестандарт. Для задач, где важна каждая байта, нужен прямой разговор через `nc`:

```bash
$ printf 'GET /flag HTTP/1.1\r\nHost: chal.local\r\nConnection: close\r\n\r\n' | nc chal.ctf 80
```

Реальный ответ сервера:

```
HTTP/1.1 200 OK
Server: chal/1.0
Content-Length: 10

forbidden
```

Здесь видно, как устроен HTTP вживую: строка запроса, заголовки, пустая строка (`\r\n\r\n`) и тело. **CRLF** (`\r\n`) — обязательный перевод строки; без пустой строки сервер ждёт продолжения запроса и «висит».

## Шаг 2: подменяем IP заголовком

Сервер не видит настоящий адрес клиента, если перед ним стоит прокси. Для этого есть заголовок `X-Forwarded-For`: прокси дописывает туда исходный IP. Если приложение доверяет этому заголовку напрямую — мы можем подставить что угодно:

```bash
$ printf 'GET /flag HTTP/1.1\r\nHost: chal.local\r\nX-Forwarded-For: 127.0.0.1\r\nConnection: close\r\n\r\n' | nc chal.ctf 80
```

```
HTTP/1.1 200 OK
Server: chal/1.0
Content-Length: 19

flag{h34d3r_trust}
```

Флаг наш. Родственные заголовки, которые стоит перебирать: `X-Real-IP`, `X-Client-IP`, `X-Originating-IP`, `Forwarded`, `True-Client-IP`. Иногда проверяется не IP, а наличие внутреннего маркера (`X-Internal: 1`) или определённый `Host` (виртуальный хостинг).

## Шаг 3: chunked-кодирование

Когда сервер не знает заранее длину тела, он использует **chunked**-передачу: тело идёт блоками, каждый с размером в hex. Заголовок `Transfer-Encoding: chunked` включает этот режим:

```
POST / HTTP/1.1
Host: chal.local
Transfer-Encoding: chunked

5
hello
0

```

`5` — размер блока в hex (5 байт), `hello` — данные, `0` — конец тела. Ошибки в парсинге chunked (неверный размер, лишние `\r\n`, отрицательное значение) — источник контрабанды и DoS.

## Шаг 4: request smuggling

**Request smuggling** («контрабанда запросов») возникает, когда фронтенд и бэкенд по-разному определяют границы запроса. Два основных класса:

- **CL.TE** — фронтенд считает длину по `Content-Length`, бэкенд — по `Transfer-Encoding`;
- **TE.CL** — наоборот.

Пример CL.TE:

```
POST / HTTP/1.1
Host: chal.local
Content-Length: 13
Transfer-Encoding: chunked

0

SMUGGLED
```

Фронтенд видит тело из 13 байт и пропускает его целиком. Бэкенд читает chunked: `0` означает «конец тела», а всё после — **следующий запрос** `SMUGGLED`. Так «лишний» запрос остаётся в буфере keep-alive соединения и обрабатывается как запрос следующего пользователя. Последствия: отравление очереди, обход авторизации, утечка чужих ответов.

Инструменты: Burp «HTTP Request Smuggler», `smuggler.py`. Важно выключить авто-исправление `Content-Length` в Burp, иначе он «починит» наш запрос.

## Шаг 5: нестандартные методы и пути

Иногда дыра — в самом методе или пути:

- `OPTIONS *` — узнать доступные методы;
- `TRACE` — отражает запрос обратно (в связке с XSS это XST);
- `PUT` — иногда позволяет загрузить файл;
- обходы путей: `/admin/..;/`, `//admin`, `/%2e%2e/admin`.

```bash
$ curl -X OPTIONS -i http://chal.ctf/
$ curl -s 'http://chal.ctf/admin/..;/flag'
```

Прокси и бэкенд по-разному нормализуют путь — расхождение и даёт доступ.

## Шаг 6: cookies и подписи

Cookie часто подписаны (HMAC) или закодированы. Если секрет подписи слабый, его подбирают:

```bash
$ flask-unsign --decode --cookie 'eyJ...'
$ flask-unsign --unsign --cookie 'eyJ...' --wordlist rockyou.txt
```

Стандартные инструменты — `flask-unsign` для Flask-сессий и `jwt_tool` для JWT (подробнее — в `misc-jwt-misc`).

## Шаг 7: отравление кэша и слепой smuggling

Часто smuggling «слепой»: чужого ответа ты не видишь, но влияешь на очередь. Признаки уязвимости — необычные тайминги (запрос «зависает» и отвечает позже), смещение ответов (твой запрос получает чужой ответ), ошибки парсинга. Для обнаружения используют **дифференциальные** техники: шлют запрос, который по одному пути даёт 404, по другому — 200, и смотрят, какой ответ придёт. Burp «HTTP Request Smuggler» перебирает варианты CL.TE/TE.CL/TE.TE и умеет «провоцировать» отложенный ответ через последующий запрос.

Рядом стоит **cache poisoning**: если кэш ключуется не по всем влияющим заголовкам (`Host`, `X-Forwarded-Host`), можно отравить кэшированный ответ для других пользователей. Проверяй, какие заголовки попадают в ключ кэша, а какие отражаются в ответе.

## Если не сработало

Сырые HTTP-приёмы зависят от расхождений парсеров и конфигурации. Разберём, почему трюк может не пройти.

**Заголовок подмены IP не работает.** Приложение может доверять только последнему прокси и игнорировать `X-Forwarded-For`, либо проверять сам TCP-адрес. Пробуем весь набор: `X-Forwarded-For`, `X-Real-IP`, `X-Client-IP`, `X-Originating-IP`, `X-Remote-Addr`, `Forwarded`. Иногда помогает дублирование заголовка или значение `127.0.0.1` в списке через запятую — парсер возьмёт первое или последнее, и это расхождение как раз эксплуатируется.

**Smuggling не проходит.** Расхождение CL/TE (Content-Length против Transfer-Encoding) работает только если два компонента (фронтенд и бэкенд) по-разному выбирают длину тела. Проверяем варианты: `TE: chunked` + `CL`, `TE: xchunked`, обфускация имени заголовка (пробел или перенос перед `chunked`), двойной `CL`. Успех часто виден не сразу, а в следующем запросе, который «отравил» соединение.

**Chunked-кодирование отвергается.** Возможно, сервер требует корректный терминатор (нулевой чанк и пустая строка после него), либо запрещает `TE`. Пробуем «TE: chunked» в конце заголовков (некоторые парсеры реагируют только на последний), разные регистры.

**Нестандартный метод не проходит.** Часто помогает `POST` с `X-HTTP-Method-Override: PUT`, либо path-трюки: `/admin/..;/`, `/%2e%2e/`, двойное кодирование. Их смысл — заставить фронтенд считать путь «безопасным», а бэкенд — «админским».

**Отравление кэша не срабатывает.** Кэш ключуется не только по URL: важно, игнорирует ли он заголовки вроде `X-Forwarded-Host`. Проверяем `X-Cache: HIT`/`Age`, добавляем уникальный параметр для разделения ключей и следим, не отразился ли наш заголовок в ответе.

## Частые вопросы

**Зачем говорить с сервером «сырыми байтами»?** Инструменты вроде `curl` нормализуют запрос: убирают дубли заголовков, чинят `CL`/`TE`. Уязвимости smuggling живут именно в нештатных комбинациях, которые клиент не отправит сам.

**Что такое request smuggling простыми словами?** Это когда фронтенд и бэкенд видят *разные* границы между запросами. Лишний запрос «прилипает» к следующему и выполняется с чужими правами.

**CL/TE — это что?** Два способа задать длину тела: `Content-Length` (число байт) и `Transfer-Encoding: chunked` (тело кусками). Когда они противоречат друг другу, парсеры выбирают разное — отсюда расхождение.

**Нужен ли Burp?** Для ручной работы — да, Repeater и Turbo Intruder. Но базовые проверки делаются и `curl` с флагом `--raw`, и через `printf` в `nc`.

## Практический порядок проверок

Начинай с «безобидного»: собери заголовки (`curl -I`), посмотри, какой сервер и прокси отвечают (`Server`, `Via`, `X-Powered-By`), есть ли кэш (`X-Cache`, `Age`). Затем проверь подмену IP заголовками — это часто самый дешёвый выигрыш. И только потом переходи к smuggling: он требует понимания топологии (сколько прокси, как парсят `CL`/`TE`).

Помни о мере: smuggling и десинхронизация могут *отравить* соединения других пользователей и нарушить работу сервиса. На продакшне такие проверки согласуют и делают аккуратно. Для CTF ограничивайся своим соединением и не трогай чужие сессии. И фиксируй точные сырые запросы — воспроизводимость важнее «магического» успеха.

## Что мы теперь знаем

- Для нестандартных запросов нужен **`nc`**, а не curl: curl нормализует байты.
- **CRLF** и пустая строка обязательны; без них сервер ждёт продолжения.
- **`X-Forwarded-For`** и родственные заголовки подделывают IP, если им доверяют.
- **Chunked**-передача — блоки с размером в hex; ошибки парсинга ведут к smuggling.
- **Request smuggling** — расхождение фронтенда и бэкенда в границах запроса (CL.TE/TE.CL).
- Методы (`TRACE`/`PUT`) и обходы путей — отдельный источник доступа.

## На что смотреть дальше

Пройди лаборатории PortSwigger по request smuggling и header-инъекциям, освой Burp «HTTP Request Smuggler». Помни про HTTP/2: там границы задаются фреймами, а smuggling переезжает в конвертацию H2→HTTP/1.1 на периметре (H2.CL, H2.TE). При отладке веди журнал: полный сырой запрос, полный сырой ответ, тайминг — большинство находок рождается из наблюдения за нестандартным поведением.

Отдельно проверь **hop-by-hop** заголовки (`Connection`, `Transfer-Encoding`, `Keep-Alive`, `Upgrade`): прокси обязан их удалять, и если он этого не делает при понижении версии протокола — снова контрабанда. Ключ к любой HTTP-задаче — понять, **где именно** происходит трансляция протокола (CDN, балансировщик, reverse-proxy) и на каком стыке расходится парсинг. И помни: иногда достаточно просто отправить `OPTIONS *` или `HEAD`, чтобы увидеть скрытое поведение сервера.
