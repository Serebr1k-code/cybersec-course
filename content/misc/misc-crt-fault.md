## Вопрос, с которого всё начинается

Устройство подписывает сообщения RSA-ключом. Однажды подпись получилась **неверной**: проверка не прошла. Сбой разовый, устройство работает. Может ли такой «безобидный» сбой стоить всего секретного ключа? Для RSA с китайской теоремой об остатках — да, и это называется **CRT-fault** (атака Bellcore).

## Наш пример

У нас есть `crt.log` — данные двух подписей одного сообщения: правильной и сбойной, плюс модуль `n`:

```
n: 2753...
sig_ok: 1039...
sig_bad: 887...
```

Наша задача — понять, как из пары подписей вытащить **множители** `n` (то есть сам секретный ключ). Разберём, почему это работает.

## Шаг 1: как RSA-подпись ускоряют через CRT

Модуль `n = p * q`. Возводить в степень по модулю `n` дорого. Поэтому подпись считают по частям:

- `m_p = m^(d mod (p-1)) mod p`
- `m_q = m^(d mod (q-1)) mod q`
- собирают `s` из `m_p` и `m_q` по **китайской теореме об остатках** (CRT).

Так вычисления идут по маленьким модулям `p` и `q`, и это в разы быстрее. Именно так работают реальные реализации (OpenSSL, смарт-карты).

## Шаг 2: что происходит при сбое

Представь, что при вычислении `m_p` произошёл сбой (скачок питания, радиация, перегрев), и получилось `m_p'` вместо `m_p`. Тогда итоговая подпись `s'` будет **правильной по модулю q**, но **неправильной по модулю p**:

```
s' ≡ s (mod q)
s' ≢ s (mod p)
```

То есть `s' - s` делится на `q`, но не делится на `p`.

## Шаг 3: почему НОД выдаёт множитель

Если число делится на `q`, но не на `p`, то `НОД(s' - s, n)` равен `q` (поскольку `n = p*q`, а `p` в разность не входит). Значит:

```
gcd(s_ok - s_bad, n) = q
```

Одна операция — и мы знаем простой множитель `n`. Дальше `p = n / q`, и секретный ключ восстановлен. Это и есть атака Bellcore, опубликованная в 1996 году.

## Шаг 4: насколько легко вызвать сбой

Атака предполагает, что атакующий может **вызвать единичный сбой** (fault injection): скачок напряжения, лазер, перегрев, радиация. На смарт-картах это реально; в CTF сбой обычно **эмулируют** — просто дают одну неверную подпись.

Если ты видишь в задаче две подписи одного сообщения и модуль `n` — почти наверняка это CRT-fault. Проверка: `gcd(|s_ok - s_bad|, n)` должен дать нетривиальный делитель.

## Шаг 5: защита

Реализации защищаются так:

- **проверка подписи перед выдачей**: если `s^e mod n ≠ m`, подпись отбрасывают;
- **пересчёт при сбое** (вычислить дважды и сравнить);
- **blinding**: умножить вход на случайное число перед подписью, чтобы сбой не коррелировал с сообщением.

Проверка подписи — самая дешёвая и эффективная мера: сбойная подпись просто не покинет устройство.

## Шаг 6: как это выглядит в задаче

Типовой сценарий: даны `n`, `e`, правильная и сбойная подписи. Решение:

1. `g = gcd(s_ok - s_bad, n)`;
2. если `1 < g < n` — это `q`;
3. `p = n // q`;
4. восстановить `d` и расшифровать/подписать что нужно.

Иногда вместо двух подписей дают одну сбойную и сообщение: тогда `g = gcd(s^e - m mod n, n)`.

## Шаг 7: находим флаг в данных

В `crt.log` есть строка `flag` в base64:

```
$ grep flag crt.log
flag: bnRve2NydF9mNHVsdF9mNGN0MHJzX259
```

Декодируем и пишем в файл:

```
$ grep flag crt.log | cut -d: -f2 | base64 -d
nto{crt_f4ult_f4ct0rs_n}
$ grep flag crt.log | cut -d: -f2 | base64 -d > found.txt
$ check
```

Метка точно описывает суть: сбой при CRT-подписи разваливает `n` на множители.

## Что мы теперь знаем

- RSA-подпись ускоряют через CRT по модулям `p` и `q`.
- Сбой в одном остатке делает подпись верной по `q`, но неверной по `p`.
- `НОД(правильная − сбойная, n)` даёт простой множитель.
- Сбой можно вызвать физически или эмулировать в задаче.
- Защита — проверка подписи, двойной пересчёт, blinding.
