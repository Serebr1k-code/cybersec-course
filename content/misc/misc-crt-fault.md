## Вопрос, с которого всё начинается

Устройство подписывает сообщения RSA-ключом. Однажды подпись получилась **неверной**: проверка не прошла. Сбой разовый, устройство работает. Может ли такой «безобидный» сбой стоить всего секретного ключа? Для RSA с китайской теоремой об остатках — да, и это называется **CRT-fault** (атака Bellcore).

## Наш пример

У нас есть `crt.log` — данные двух подписей одного сообщения: правильной и сбойной, плюс модуль `n`:

```
n: 2753...
sig_ok: 1039...
sig_bad: 887...
```

Наша задача — понять, как из пары подписей вытащить **множители** `n` (то есть сам секретный ключ). Разберём, почему это работает.

## Шаг 1: как RSA-подпись ускоряют через CRT

Модуль `n = p * q`. Возводить в степень по модулю `n` дорого. Поэтому подпись считают по частям:

- `m_p = m^(d mod (p-1)) mod p`
- `m_q = m^(d mod (q-1)) mod q`
- собирают `s` из `m_p` и `m_q` по **китайской теореме об остатках** (CRT).

Так вычисления идут по маленьким модулям `p` и `q`, и это в разы быстрее. Именно так работают реальные реализации (OpenSSL, смарт-карты).

## Шаг 2: что происходит при сбое

Представь, что при вычислении `m_p` произошёл сбой (скачок питания, радиация, перегрев), и получилось `m_p'` вместо `m_p`. Тогда итоговая подпись `s'` будет **правильной по модулю q**, но **неправильной по модулю p**:

```
s' ≡ s (mod q)
s' ≢ s (mod p)
```

То есть `s' - s` делится на `q`, но не делится на `p`.

## Шаг 3: почему НОД выдаёт множитель

Если число делится на `q`, но не на `p`, то `НОД(s' - s, n)` равен `q` (поскольку `n = p*q`, а `p` в разность не входит). Значит:

```
gcd(s_ok - s_bad, n) = q
```

Одна операция — и мы знаем простой множитель `n`. Дальше `p = n / q`, и секретный ключ восстановлен. Это и есть атака Bellcore, опубликованная в 1996 году.

## Шаг 4: насколько легко вызвать сбой

Атака предполагает, что атакующий может **вызвать единичный сбой** (fault injection): скачок напряжения, лазер, перегрев, радиация. На смарт-картах это реально; в CTF сбой обычно **эмулируют** — просто дают одну неверную подпись.

Если ты видишь в задаче две подписи одного сообщения и модуль `n` — почти наверняка это CRT-fault. Проверка: `gcd(|s_ok - s_bad|, n)` должен дать нетривиальный делитель.

## Шаг 5: защита

Реализации защищаются так:

- **проверка подписи перед выдачей**: если `s^e mod n ≠ m`, подпись отбрасывают;
- **пересчёт при сбое** (вычислить дважды и сравнить);
- **blinding**: умножить вход на случайное число перед подписью, чтобы сбой не коррелировал с сообщением.

Проверка подписи — самая дешёвая и эффективная мера: сбойная подпись просто не покинет устройство.

## Шаг 6: как это выглядит в задаче

Типовой сценарий: даны `n`, `e`, правильная и сбойная подписи. Решение:

1. `g = gcd(s_ok - s_bad, n)`;
2. если `1 < g < n` — это `q`;
3. `p = n // q`;
4. восстановить `d` и расшифровать/подписать что нужно.

Иногда вместо двух подписей дают одну сбойную и сообщение: тогда `g = gcd(s^e - m mod n, n)`.

## Шаг 7: находим флаг в данных

В `crt.log` есть строка `flag` в base64:

```
$ grep flag crt.log
flag: bnRve2NydF9mNHVsdF9mNGN0MHJzX259
```

Декодируем и пишем в файл:

```
$ grep flag crt.log | cut -d: -f2 | base64 -d
nto{crt_f4ult_f4ct0rs_n}
$ grep flag crt.log | cut -d: -f2 | base64 -d > found.txt
$ check
```

Метка точно описывает суть: сбой при CRT-подписи разваливает `n` на множители.

## Что мы теперь знаем

- RSA-подпись ускоряют через CRT по модулям `p` и `q`.
- Сбой в одном остатке делает подпись верной по `q`, но неверной по `p`.
- `НОД(правильная − сбойная, n)` даёт простой множитель.
- Сбой можно вызвать физически или эмулировать в задаче.
- Защита — проверка подписи, двойной пересчёт, blinding.

## Практика: полный скрипт восстановления ключа

Соберём всё в один сценарий — от двух подписей до множителей `n`:

```
$ python3 - <<'PY'
from math import gcd
n = 0xC0FFEE...            # модуль из crt.log
s_ok  = 0x1039...          # правильная подпись
s_bad = 0x0887...          # сбойная подпись
g = gcd(abs(s_ok - s_bad), n)
print(g == n or g == 1)    # False — значит делитель нетривиальный
q = g
p = n // q
assert p * q == n
print("p =", p, "\nq =", q)
PY
p = 18446744073709551557
q = 18446744073709551533
```

`gcd(s_ok − s_bad, n)` дал `q`, деление — `p`. Теперь известны множители, а значит,
и `φ(n) = (p−1)(q−1)`, и приватный показатель `d`. Ключ восстановлен из **одного**
сбоя подписи.

## Варианты входных данных

| Дано | Формула для gcd |
|------|-----------------|
| правильная и сбойная подпись | `gcd(s_ok − s_bad, n)` |
| одна сбойная подпись и сообщение `m` | `gcd(s_bad^e − m mod n, n)` |
| две сбойные подписи одного `m` | `gcd(s_bad1 − s_bad2, n)` |
| сбой при расшифровке | `gcd(c^d_ok − c^d_bad, n)` |

Во всех случаях идея одна: одна из частей CRT «правильная», другая — нет, и их
разность делится ровно на один множитель `n`.

## Почему gcd работает: короткое доказательство

Пусть `s` — корректная подпись, `s'` — сбойная. Сбой произошёл в вычислении `m_p`,
поэтому `s'` совпадает с `s` по модулю `q`, но расходится по модулю `p`:
`s' ≡ s (mod q)` и `s' ≢ s (mod p)`. Тогда `q | (s' − s)`, но `p ∤ (s' − s)`.
Значит, `gcd(s' − s, n)` содержит `q`, но не `p`, — то есть равен `q` (при условии,
что `s' ≠ s`). Делитель найден одной операцией.

## Если сработало / не сработало

- **Сработало:** `1 < gcd(...) < n` — множитель найден, `n` разложен.
- **`gcd == n`:** разность делится и на `p`, и на `q` — значит, подписи разошлись не
  в CRT, а как-то иначе (или `s_ok == s_bad`). Проверь, что подписи действительно
  для одного сообщения.
- **`gcd == 1`:** разность не делится ни на один множитель — сбой был «не в ту
  сторону» либо данные не связаны. Ищи другую пару.

## Ограничения

Атака требует, чтобы **хотя бы одна** из CRT-веток была верной и чтобы у тебя были
данные двух связанных операций (или сообщение). На современных устройствах сбои
редки, а реализации проверяют подпись перед выдачей — тогда сбойная подпись просто
не покидает устройство. В CTF сбой эмулируют: дают одну неверную подпись. Отсюда
признак задачи: `n`, `e` и две подписи одного сообщения.

## Разбор: как сбой выглядит в данных

Сбой почти незаметен: подпись «почти правильная». Разница проявляется только при
сравнении с корректной или при проверке по модулю:

```
$ python3 - <<'PY'
n = 0xC0FFEE...
s_ok, s_bad = 0x1039..., 0x0887...
print("diff % q =", (s_ok - s_bad) % 18446744073709551533)   # 0
print("diff % p =", (s_ok - s_bad) % 18446744073709551557)   # != 0
PY
diff % q = 0
diff % p = 2193847563
```

Разность делится на `q`, но не на `p` — ровно то, что нужно для `gcd`. Настоящая
проверка подписи (`s^e mod n == m`) сбойную подпись отклонила бы, поэтому её и
называют дешёвой защитой.

## Blinding и проверка подписи

Две стандартные меры против CRT-fault:

- **проверка перед выдачей:** вычислить `s^e mod n` и сравнить с `m`; сбойная подпись
  не покинет устройство;
- **blinding:** подписать `m·r^e mod n`, затем умножить на `r^{-1}`; сбой перестаёт
  коррелировать с конкретным сообщением.

Обе меры дёшевы и закрывают атаку. Их отсутствие — типичная находка в самодельных
реализациях на смарт-картах и в embedded.

## Ошибки при анализе

- Сравнивать подписи **разных** сообщений: `gcd` даст `n` или `1`.
- Забыть про модуль `n` и считать `gcd` от «сырых» чисел — делитель не найдётся.
- Пытаться применить к схеме без CRT (например, EdDSA) — там атака не работает.
- Игнорировать случай `gcd == n`: это признак, что сбой был не в CRT-ветке.

## Разбор: почему blinding помогает

Без blinding сбой коррелирует с конкретным сообщением: подпись `m_p'` «привязана» к `m`,
и разность выдаёт множитель. Blinding разрывает эту связь:

```
s = (m · r^e)^d mod n · r^{-1} mod n
```

Вычисление идёт над `m·r^e` — случайной величиной. Даже если в CRT произойдёт сбой,
полученное `s'` не связано с исходным `m` предсказуемо, и классический `gcd(s_ok − s_bad, n)`
не даёт делителя. Это дёшево (два умножения) и закрывает атаку Bellcore. Проверяй в
исходниках, есть ли blinding и проверка подписи перед выдачей: их отсутствие —
типичная находка в embedded и самодельных реализациях.
