Регулярные выражения — не только инструмент парсинга, но и отдельный жанр головоломок: «составьте regex, который матчит ровно этот язык», «сократите regex», «почему это выражение вешает сервер». В misc такие задачи встречаются как regex-golf и как анализ ReDoS. Этот урок — про то, как думать регулярками и как их отлаживать.

## Основы, которые нужны в гольфе

Regex — формальный язык. Ключевые конструкции:

| Конструкция | Смысл |
|-------------|-------|
| `.` | любой символ (кроме `\n`) |
| `*`, `+`, `?` | 0+, 1+, 0/1 повторений |
| `{n,m}` | от n до m повторений |
| `[...]` | класс символов |
| `[^...]` | отрицание класса |
| `^`, `$` | начало/конец |
| `\b` | граница слова |
| `(...)` | группа/захват |
| `(?:...)` | незахватывающая группа |
| `\|` | альтернатива |
| `\1` | обратная ссылка |
| `(?=...)`, `(?!...)` | lookahead |
| `(?<=...)`, `(?<!...)` | lookbehind |

## Regex-гольф

Гольф — минимизация длины. Приёмы:

- **Классы вместо альтернатив**: `[abc]` короче `a|b|c`.
- **Квантификаторы**: `a{3}` = `aaa`, но короче.
- **Обратные ссылки**: `(.)\1` — два одинаковых символа.
- **Lookahead вместо пересечения**: язык «есть и a, и b»: `(?=.*a)(?=.*b)`.
- **Побитовые трюки в классах**: `[\x00-\xff]`.
- **Рекурсия PCRE**: `(?R)` для вложенных структур.

Пример: матчить строку из чётного числа `a` — `^(aa)*$`. Нечётного — `^a(aa)*$`. Строку-палиндром из `a`/`b` — рекурсия: `^(a|b|(a(?1)a)|(b(?1)b))$` (PCRE).

## Катастрофический backtracking (ReDoS)

Движок regex перебирает варианты; вложенные квантификаторы дают экспоненциальный взрыв:

```regex
^(a+)+$
```

На строке `aaaaaaaaaaaaaaaaaaaaaaaaX` движок пробует все способы разбить `a`-блоки — экспоненциально. Это ReDoS (отказ в обслуживании). Подробнее — в `misc-regex-dos`.

## Атомарные группы и possessive

Чтобы избежать backtracking, используют атомарные группы и possessive-квантификаторы:

```regex
(?>a+)+     # атомарная: не отдаёт символы назад
a++         # possessive: как a+ без backtracking
```

Они «фиксируют» совпадение и не дают движку перебирать варианты — защита от ReDoS.

## Якоря и порядок

Частые ошибки: отсутствие `^`/`$` (regex матчит подстроку), жадность (`.+` съедает больше нужного), порядок альтернатив (`(a|ab)` — при `ab` сработает `a`). В гольфе порядок и якоря критичны.

## Разобранный пример

Задача: написать regex, который матчит строки вида `1`, `11`, `111`, ... (только единицы), но не пустую строку.

```regex
^1+$
```

Задача сложнее: матчить строку из `a` и `b`, где нет двух подряд идущих `b`.

```regex
^a*(?:ba+)*b?$
```

Задача-гольф: матчить «email» простого вида `x@y.z`:

```regex
^\S+@\S+\.\S+$
```

Минимально достаточно `.+@.+\..+` при поиске, но с якорями — надёжнее.

## Разбор реального ReDoS

```regex
^(\w+\s?)*$
```

На строке из многих слов с пробелом в конце движок перебирает варианты распределения пробелов — взрыв. Исправление: `^\w+(?:\s\w+)*$` (без вложенных квантификаторов).

## Частые ошибки и подводные камни

- Забывать якоря — regex матчит подстроку, а не всю строку.
- Вложенные квантификаторы `(a+)+` — ReDoS.
- Жадные квантификаторы там, где нужны ленивые `.*?`.
- Различия движков: PCRE vs Python `re` vs RE2 (последний не поддерживает backreferences и не страдает от ReDoS).
- Не учитывать Unicode-режим: `\w` и `.` ведут себя по-разному.
- Полагать, что «короткий regex = быстрый» — нет, зависит от структуры.

## Дополнительная теория: движки и их различия

Регулярные выражения реализуются двумя принципиально разными способами. **NFA с backtracking** (PCRE, Perl, Python `re`, Java, .NET, JS) — мощные, поддерживают backreferences и lookaround, но подвержены экспоненциальному перебору. **DFA** (RE2, Go, Rust `regex`, grep) — работают за линейное время, не поддерживают backreferences и lookbehind переменной длины, зато иммунны к ReDoS. Выбор движка определяет, какие конструкции вообще доступны и как ведёт себя катастрофический backtracking. В задачах всегда уточняйте, какой движок используется: то, что работает в PCRE, может не скомпилироваться в RE2.

Есть и гибридные подходы: RE2 применяет NFA-симуляцию без возвратов; PCRE2 имеет JIT-компиляцию, ускоряющую матчинг, но не меняющую экспоненциальную сложность в худшем случае. Понимание этого важно и для гольфа (одни конструкции короче, другие недоступны), и для ReDoS (в RE2 уязвимости нет по определению).

## Приёмы сокращения выражений

Гольф — искусство убрать каждый лишний символ. Полезные приёмы: заменяйте альтернативы классами (`[abc]` вместо `a|b|c`); используйте `\d`, `\w`, `\s` вместо явных классов; объединяйте повторения через `{n,m}`; применяйте lookahead для «пересечения» условий; используйте `(?:...)` только когда нужна группировка без захвата (в гольфе иногда и захватывающая короче). Не забывайте про якоря `^`/`$`: без них выражение матчит подстроку и может «пройти» там, где не должно.

Отдельный приём — **обратные ссылки** для палиндромов и повторяющихся паттернов: `(.)\1` ловит два одинаковых символа. Для вложенных структур нужна **рекурсия PCRE**: `(?R)` или `(?1)` для повторного применения группы. Например, язык сбалансированных скобок: `^\((?:[^()]|(?R))*\)$`. В RE2 рекурсии нет, поэтому такие языки там не выразить регулярным выражением.

## Разбор ошибок и отладка

Если regex «не матчит то, что должен», проверьте жадность: `.` и `+` жадные и могут «съесть» больше нужного, тогда как `.*?` ленивый. Проверьте, включён ли многострочный режим (`m`) — иначе `^`/`$` относятся ко всей строке, а не к строкам. Проверьте Unicode-флаг: без него `\w` может не матчить кириллицу. На regex101.com можно увидеть пошаговую трассировку движка — это лучший способ понять, где backtracking уходит не туда. Если выражение вешает процесс, используйте `regexploit`, чтобы найти злой вход, и перепишите через атомарные группы.

## Частые вопросы

**Всегда ли короткий regex быстрее?** Нет. Скорость зависит от структуры, а не длины. `^(a+)+$` короткий, но экспоненциальный; длинное выражение без вложенных квантификаторов может быть линейным. Всегда оценивайте, есть ли места, где движок вынужден перебирать варианты.

**Как защититься от ReDoS, если нельзя сменить движок?** Ограничьте вход по длине до применения regex (первый рубеж), используйте атомарные группы и possessive-квантификаторы, избегайте вложенных квантификаторов и альтернатив с общим префиксом, добавьте таймауты. Иногда помогает предварительная проверка простыми строками (`indexOf`) вместо сложного regex.

**Почему `\w` не матчит кириллицу?** По умолчанию `\w` — это `[A-Za-z0-9_]`. Для Unicode-букв нужен флаг `u` (Python: `re.UNICODE` в Python 3 по умолчанию для str, но `\w` всё равно может не покрывать всё) или явный класс. В JS флаг `u` меняет поведение escapes.

**Можно ли выразить любой язык регуляркой?** Нет. Регулярные выражения (в теоретическом смысле) описывают только регулярные языки. Вложенные структуры (сбалансированные скобки, HTML, JSON) требуют большего — в PCRE это эмулируется рекурсией, но формально выходит за пределы регулярных языков. Для парсинга таких структур используйте настоящий парсер.

## Практический разбор: доказательство ReDoS и фикс

Докажем катастрофический backtracking замером. Для `^(a+)+$` на строке из `a` и «плохого» символа в конце время растёт экспоненциально:

```python
import re, time
for n in range(10, 31, 5):
    s = 'a'*n + 'X'
    t = time.time()
    re.match(r'^(a+)+$', s)
    print(n, round(time.time()-t, 4))
# 10 0.0002
# 15 0.0071
# 20 0.2203
# 25 7.0512
# 30 225.6   ← экспонента
```

Каждые +5 символов — примерно ×30. Фикс — убрать вложенность и сделать выражение линейным:

```python
re.match(r'^a+$', s)   # то же самое, но без катастрофы
```

Или через possessive/атомарную группу: `^(?>a+)+$`. Проверьте `regexploit`, чтобы найти злой вход в реальном коде. Ключевой вывод: **два выражения могут быть эквивалентны по языку, но радикально различаться по сложности**. Всегда думайте о структуре, а не только о результате.
