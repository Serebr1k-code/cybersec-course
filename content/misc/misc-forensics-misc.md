## Вопрос, с которого всё начинается

Тебе дали файл `usb.img` — «образ флешки подозреваемого». Задача: найти флаг. Внутри может быть что угодно: обычные файлы, удалённые данные, вложенный архив, спрятанная строка в метаданных. Открыть двойным кликом нельзя, и перебор инструментов наугад — плохая идея.

Форензика в misc — это про **методичный обход артефакта**: мы не гадаем, а идём по одному маршруту и на каждом шаге отвечаем на конкретный вопрос. Весь урок — на одном объекте, образе `usb.img`. Каждый ответ рождает следующий вопрос, и так мы дойдём до флага.

## Наш пример: образ usb.img

Первое, что нужно понять про любой файл — **что это на самом деле**. Имя и расширение ничего не гарантируют, поэтому смотрим на первые байты — «магические», по которым утилиты узнают формат.

```
$ file usb.img
usb.img: DOS/MBR boot sector, code offset 0x58+2, OEM-ID "mkfs.fat",
sectors/cluster 8, root entries 512, Media descriptor 0xf8,
sectors/FAT 32, sectors 65536 (volumes > 2^16 sectors), ...
```

`file` говорит: это **DOS/MBR boot sector** с файловой системой FAT — то есть загрузочный образ диска, а не просто файл. Значит, внутри есть разделы и файловая система. Вопрос меняется: «какие разделы и файлы внутри?».

## Шаг 1: разбираем разметку

У образа диска есть **таблица разделов** — служебная область, которая говорит, где начинается каждый раздел. Смотрим её через `fdisk`:

```
$ fdisk -l usb.img
Disk usb.img: 32 MiB, 33554432 bytes, 65536 sectors
Units: sectors of 1 * 512 = 512 bytes

Device     Boot Start   End Sectors  Size Id Type
usb.img1        * 2048 65535   63488   31M  b W95 FAT32
```

Читаем: один раздел, начинается с сектора 2048 (смещение `2048 × 512 = 1048576` байт) и занимает почти весь образ. Тип `b` — FAT32. Теперь мы знаем, где именно «полезная» часть.

Чтобы перечислять файлы, не монтируя образ, используем инструменты из набора **sleuthkit** (`fls` — list files):

```
$ fls -r -o 2048 usb.img
r/r 4:      secret/
r/r 6:      secret/note.txt
r/r 7:      secret/photo.jpg
r/r * 9:    secret/deleted_flag.txt
```

Ключевой момент: строка с `*` перед номером — файл **удалён**, но его запись ещё жива. `fls` умеет показывать удалённые. Именно такие файлы часто и содержат ответ. Номер после `r/r` — это **inode** (идентификатор файла), по нему содержимое достаётся командой `icat`:

```
$ icat -o 2048 usb.img 6
В этой папке лежит всё нужное. Проверь photo.jpg внимательно.
```

`note.txt` даёт подсказку: смотреть на `photo.jpg`. Читаем и его:

```
$ icat -o 2048 usb.img 9
FLAG{recovered_from_slack_space}
```

Файл `deleted_flag.txt` был удалён, но его содержимое всё ещё на месте — потому что при удалении в FAT стирается только запись в таблице, а сами данные остаются до перезаписи. Это и есть базовый приём восстановления: **не читать через файловую систему, а доставать данные по inode напрямую**.

## Шаг 2: что говорит карвинг

Иногда записи в файловой системе уже нет (файл перезаписан по метаданным), а данные остались. Тогда применяют **карвинг** — поиск файлов по сигнатурам, без опоры на файловую систему. Инструмент `foremost` ищет заголовки (`JPEG`, `PDF`, `ZIP`) и восстанавливает файл до «хвоста».

```
$ foremost -t jpg,png,pdf -i usb.img -o recovered/
$ ls -la recovered/jpg/
-rw-r--r-- 1 user user 41230 photo.jpg
-rw-r--r-- 1 user user  8192 extra.jpg
```

`foremost` нашёл два JPEG, хотя в файловой системе был только один. Второй `extra.jpg` — результат карвинга «осиротевших» данных. Часто это и есть спрятанный файл.

Полезно знать про **slack-пространство**: файл занимает целое число кластеров, и между концом данных и концом последнего кластера остаётся «хвост». Туда могут попасть фрагменты старых удалённых файлов — карвинг их тоже вытаскивает.

## Шаг 3: вложенные форматы через binwalk

Файл может быть «матрёшкой»: внутри одного формата спрятан другой. `binwalk` сканирует байты на сигнатуры вложенных форматов:

```
$ binwalk usb.img
DECIMAL       HEXADECIMAL     DESCRIPTION
--------------------------------------------------------------------------------
0             0x0             DOS/MBR boot sector
1048576       0x100000        FAT filesystem
33525632      0x1FF8000       Zip archive data, at least v2.0 to extract, name: flag.zip
33525890      0x1FF80C2       End of Zip archive
```

Видим: в самом конце образа приклеен ZIP-архив с именем `flag.zip`. Это классика CTF — данные дописаны после конца файловой системы. Извлекаем одной командой:

```
$ binwalk -e usb.img
$ cat _usb.img.extracted/flag.txt
FLAG{n3st3d_arch1ves_ar3_fun}
```

`binwalk -e` сам распознал и распаковал вложенный архив. Если бы ZIP был с паролем, дальше шли бы `zip2john` и `john`.

## Шаг 4: метаданные изображения

Вернёмся к `photo.jpg` — подсказка вела именно туда. У изображений есть **EXIF** — метаданные, которые камера пишет в файл: модель, дата, а иногда GPS-координаты и уменьшенная копия кадра (**thumbnail**).

```
$ exiftool photo.jpg
File Name      : photo.jpg
Camera Model   : Canon EOS 600D
Create Date    : 2024:03:15 14:22:01
GPS Position   : 55 deg 45' 21.00" N, 37 deg 37' 4.00" E
Comment        : the flag is in the thumbnail
Software       : Adobe Photoshop 24.0
```

Здесь сразу два сигнала: **GPS-координаты** и комментарий, указывающий на превью. Извлекаем thumbnail отдельно:

```
$ exiftool -b -ThumbnailImage photo.jpg > thumb.jpg
$ strings thumb.jpg | grep -a FLAG
FLAG{ex1f_thumbnail_holds_secrets}
```

Превью осталось от исходного кадра: фото отредактировали, а миниатюру не пересобрали — типичная ошибка автора задачи. Поле `Software: Photoshop` — намёк, что файл правили, и стоит смотреть «несоответствия».

## Что мы теперь знаем

По-простому, маршрут разбора любого образа:

1. `file` — определить реальный тип (это образ диска, а не картинка).
2. `fdisk -l` — найти разделы и их смещение.
3. `fls`/`icat` — перечислить файлы (включая удалённые) и достать данные по inode.
4. `foremost` — вытащить данные, на которые нет записи (карвинг).
5. `binwalk` — найти и извлечь вложенные форматы.
6. `exiftool` — метаданные и превью.

Каждый шаг — ответ на конкретный вопрос. Не «прогоню-ка всё подряд», а «у меня нет записи в ФС → нужен карвинг».

## На что смотреть дальше

- **Работайте с копией.** `foremost` и монтирование могут изменить образ — сначала `cp usb.img usb_copy.img`.
- **Флаг ищите по формату:** `strings -n 6 usb.img | grep -a 'FLAG\|CTF{'`, а не глазами по всему выводу.
- **Смотрите конец файла:** дописанные данные (`binwalk`, `xxd | tail`) — самый частый приём.
- **Проверяйте метаданные и превью** — флаг нередко там, а не в пикселях.
- **Не забывайте про удалённое:** `*` в выводе `fls` и «осиротевшие» файлы из `foremost`.

## Куда дальше

В следующем уроке мы возьмём тот же образ и построим **таймлайн** — упорядочим все события по времени, чтобы понять не только «что лежит», но и «что и когда происходило». А пока запомни главное: образ разбирается по маршруту `file → fdisk → fls → foremost → binwalk → exiftool`, и флаг ищут по формату, а не перебором.
