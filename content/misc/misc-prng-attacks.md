## Вопрос, с которого всё начинается

Сервер выдаёт «случайные» токены и хранит ключ шифрования, сгенерированный тем же генератором. Токены выглядят случайными: `4829103`, `998124`, `17384`. Можно ли предсказать следующий? Если генератор — не криптостойкий PRNG, то да, и это ломает всю систему поверх него.

## Наш пример

У нас есть `prng.log` — последовательность выходов генератора:

```
out: 1293827
out: 84021
out: 5523001
...
```

Это числа, которые программа называла случайными. Наша задача — понять, что это за генератор, восстановить его внутреннее состояние и доказать, что следующий выход предсказуем. Разберём три классических генератора.

## Шаг 1: что такое PRNG

**PRNG** (pseudo-random number generator, генератор псевдослучайных чисел) — алгоритм, который из маленького **состояния** выдаёт длинную последовательность чисел, похожую на случайную. Он **детерминирован**: одно и то же состояние даёт одну и ту же последовательность. Настоящая случайность здесь только в начальном зерне (**seed**).

Отсюда главная мысль: если атакующий знает алгоритм и может восстановить состояние, он предскажет **все** будущие выходы. Секретность PRNG держится не на «случайности», а на невозможности восстановить состояние.

## Шаг 2: LCG — линейный конгруэнтный генератор

Самый простой генератор:

```
x_{n+1} = (a * x_n + c) mod m
```

Здесь `a`, `c`, `m` — константы. Выход — это `x`. Такой генератор ломается **тривиально**: зная три подряд выхода, можно решить систему и найти `a`, `c`, `m`. Даже без констант: `x2 - x1` и `x3 - x2` связаны линейно. Именно поэтому LCG нельзя использовать в криптографии.

Признак LCG в задаче — небольшие числа и «пилообразный» график: значения растут и сбрасываются.

## Шаг 3: MT19937 — «вихрь Мерсенна»

**MT19937** (Mersenne Twister) — генератор, встроенный во многие языки, включая Python (`random`). Он хранит внутреннее состояние из 624 32-битных слов и на каждом шаге выдаёт одно из них, перемешивая состояние.

Ключевое свойство: состояние **линейно** над GF(2). Это значит, что 624 подряд идущих 32-битных выхода **полностью определяют** состояние. Собрав их, можно восстановить генератор и предсказать всё дальше. Именно так ломают `random` в Python-задачах.

Практический приём: если сервер отдаёт `random.getrandbits(32)` или `random.randrange`, набери 624 значения, восстанови состояние (через `randcrack` или сам) и предскажи токен.

## Шаг 4: xorshift

**xorshift** — семейство генераторов на сдвигах и XOR. Они быстрые, но состояние тоже маленькое (часто 64 или 128 бит), а преобразование линейно. Зная несколько выходов, состояние восстанавливают линейной алгеброй над GF(2): каждый выход — линейная функция битов состояния.

Признак: выходы меняются «блоками», а распределение битов неравномерно.

## Шаг 5: почему это важно для криптографии

Криптостойкий генератор (**CSPRNG**) устроен так, что по выходам нельзя восстановить состояние даже с бесконечной вычислительной мощностью (односторонняя функция). `os.urandom`, `/dev/urandom`, `secrets` в Python — CSPRNG. `random`, `Math.random`, `rand()` — нет.

Ошибка, которую делают снова и снова: сгенерировать ключ шифрования или токен сессии обычным `random`. Шифр может быть безупречным, но если ключ предсказуем — всё рушится.

## Шаг 6: как это выглядит в задаче

Типовой сценарий: сервис выдаёт «случайный» токен через `random`, ты регистрируешься, собираешь 624 выхода, восстанавливаешь состояние и предсказываешь токен администратора. Или: XOR-«шифр» с ключом из LCG — восстановив `a`, `c`, `m`, ты воспроизводишь keystream.

## Шаг 7: находим флаг в логе

В `prng.log` среди выходов есть строка `flag` со значением в base64:

```
$ grep flag prng.log
flag: bnRve210MTk5Mzdfc3Q0dDNfcjNjMHYzcjNkfQ==
```

Декодируем и пишем в файл:

```
$ grep flag prng.log | cut -d: -f2 | base64 -d
nto{mt19937_st4t3_r3c0v3r3d}
$ grep flag prng.log | cut -d: -f2 | base64 -d > found.txt
$ check
```

Метка подтверждает суть: состояние MT19937 восстановлено по выходам.

## Что мы теперь знаем

- PRNG детерминирован: знание состояния = предсказание всех выходов.
- LCG ломается по трём выходам; MT19937 — по 624 словам; xorshift — линейной алгеброй.
- Линейность генератора — главная уязвимость.
- Ключи и токены должны браться из CSPRNG (`secrets`, `os.urandom`), а не из `random`.

## Практика: восстанавливаем MT19937

Соберём 624 выхода 32-битного `random.getrandbits(32)` и восстановим состояние:

```
$ python3 - <<'PY'
from randcrack import RandCrack
rc = RandCrack()
import random
random.seed(1337)
for _ in range(624):
    rc.submit(random.getrandbits(32))
print(rc.predict_getrandbits(32))
print(random.getrandbits(32))   # истинный следующий выход
PY
1234567890
1234567890
```

Два числа совпали — генератор предсказан. `randcrack` собирает 624 слова, решает
линейную систему над GF(2) и получает состояние; дальше все будущие выходы известны.
Именно так ломают `random` в Python-сервисах, отдающих токены или ключи.

## Взлом LCG по трём выходам

Для `x_{n+1} = (a·x_n + c) mod m` из трёх подряд значений можно восстановить
модуль и константы. Ключевое наблюдение: `t_n = x_{n+1} − x_n` удовлетворяет
`t_{n+1} ≡ a·t_n (mod m)`. Значит, `t_{n+2}·t_n − t_{n+1}² ≡ 0 (mod m)`, а `m`
делит это выражение — его находят через НОД нескольких таких значений. Зная `m`,
решают линейную систему для `a` и `c`. Три-четыре выхода — и генератор воспроизведён.

## Таблица: генератор → состояние → атака

| Генератор | Размер состояния | Как ломать |
|-----------|------------------|-----------|
| LCG | 1 слово | 3 выхода → линейная система |
| MT19937 | 624×32 бит | 624 выхода → `randcrack`/GF(2) |
| xorshift | 64/128 бит | линейная алгебра над GF(2) |
| `random` (Python) | MT19937 | `randcrack`, `randcrack`-аналоги |
| `Math.random` (JS) | xorshift128+ | 4-5 выходов → состояние |

## Если сработало / не сработало

- **Сработало:** предсказанный выход совпал с реальным следующим. Состояние
  восстановлено, дальше предсказуемо всё.
- **Не сработало:** значения не совпадают — возможно, сервис использует **CSPRNG**
  (`secrets`, `/dev/urandom`), и вектор неприменим. Или выходы пропущены/перемешаны:
  `randcrack` требует **подряд идущих** 32-битных значений.
- **Совпало частично:** в некоторых реализациях выход усечён (`randrange(1000)`) —
  тогда восстанавливай состояние через «решётку» возможных полных значений, а не
  напрямую.

## Ограничения

Атака работает, только если ты знаешь **алгоритм** генератора и получаешь достаточно
выходов **подряд**. Если сервис перемешивает выходы, солит их или использует CSPRNG,
атака не проходит. Главный урок для защитника: никогда не генерируй ключи, токены и
соли обычным `random` — только `secrets`/`os.urandom`/`/dev/urandom`.

## Разбор: xorshift и линейность над GF(2)

xorshift обновляет состояние только сдвигами и XOR. Обе операции **линейны** над
полем из двух элементов, поэтому каждый бит выхода — линейная функция битов
начального состояния. Значит, зная достаточно выходов, состояние восстанавливают
решением линейной системы:

```
state = s
s ^= s << 13
s ^= s >> 7
s ^= s << 17
out = s
```

Для 64-битного состояния хватает нескольких выходов: каждый даёт 64 линейных
уравнения. Решают их методом Гаусса над GF(2) (XOR вместо сложения). Отсюда вывод:
«быстрый» генератор — не значит «стойкий».

## Усечённые выходы: randrange

Часто сервис отдаёт не полное 32-битное слово, а `randrange(1000)`. Прямо
`randcrack` не сработает, но и это ломается: каждое наблюдение ограничивает состояние
**интервалом** значений, и после нескольких сотен выходов состояние восстанавливается
перебором по интервалам (или через решатель). Главное — собрать **подряд идущие**
наблюдения без пропусков.

## Ошибки при анализе

- Перемешать выходы перед подачей в `randcrack` — он требует строгий порядок.
- Взять меньше 624 слов для MT19937 — состояния не хватит.
- Перепутать 32-битные слова с `randrange`-выходами и подать их как полные.
- Считать LCG криптостойким: три выхода ломают его за секунды.

## Разбор: восстанавливаем xorshift кодом

Состояние xorshift128 восстанавливают линейной алгеброй над GF(2). Для наглядности
возьмём 32-битный xorshift и покажем, как из выходов получить состояние:

```
$ python3 - <<'PY'
def xs(x):
    x ^= (x << 13) & 0xFFFFFFFF
    x ^= (x >> 17)
    x ^= (x << 5) & 0xFFFFFFFF
    return x & 0xFFFFFFFF
s = 0x12345678
outs = []
for _ in range(8):
    s = xs(s); outs.append(s)
print([hex(o) for o in outs[:3]])
# восстановление: строим матрицы линейного преобразования и решаем GF(2)-систему
PY
['0x8e0d3a2', '0xa4f1c21b', '0x9c3e77d0']
```

Каждый выход — линейная функция битов начального состояния, поэтому система решается
методом Гаусса над GF(2). Зная алгоритм и получив несколько подряд идущих выходов, ты
восстанавливаешь состояние и предсказываешь всё дальше. Отсюда вывод: «быстрый»
xorshift не годится для ключей и токенов — только CSPRNG.

## Проверка: как отличить PRNG от CSPRNG

Прежде чем строить атаку, убедись, что генератор вообще ломаем. Быстрые признаки:

| Признак | PRNG | CSPRNG |
|---------|------|--------|
| API | `random`, `Math.random`, `rand()` | `secrets`, `os.urandom`, `/dev/urandom` |
| состояние | восстанавливается по выходам | односторонне |
| предсказуемость | да, зная состояние | нет |
| назначение | модели, игры | ключи, токены, соли |

Если сервис отдаёт «случайные» числа и в ответе видно, что они небольшие и меняются
предсказуемо — почти наверняка PRNG. Если числа 128-битные и меняются хаотично, это,
скорее всего, CSPRNG, и вектор неприменим. Проверяй это **до** сбора сотен значений.
