## Вопрос, с которого всё начинается

Контракт нельзя «обновить» — байткод по адресу неизменяем. Но протоколы обновляются каждый день. Секрет — в **прокси**: пользователи зовут прокси, а тот через `delegatecall` выполняет код реализации, читая и записывая **свой** storage. Это мощно и опасно: одна ошибка в раскладке storage — и весь протокол захвачен.

## Наш пример: простой прокси

```solidity
contract Proxy {
    address public implementation;   // slot 0
    function _delegate(address impl) internal {
        assembly {
            calldatacopy(0, 0, calldatasize())
            let result := delegatecall(gas(), impl, 0, calldatasize(), 0, 0)
            returndatacopy(0, 0, returndatasize())
            switch result
            case 0 { revert(0, returndatasize()) }
            default { return(0, returndatasize()) }
        }
    }
}
```

Разберём, где тут может быть дыра, и почему `delegatecall` — источник большинства инцидентов.

## Шаг 1: delegatecall и контекст

`delegatecall` исполняет код `impl`, но `msg.sender`, `address(this)` и **storage** — от прокси. То есть реализация читает слоты прокси. Если реализация объявила переменную в слоте 0, а прокси там держит `implementation`, они будут читать одно и то же — с непредсказуемым результатом.

## Шаг 2: storage collision

Классический баг: прокси хранит `implementation` в слоте 0, реализация тоже начинает с переменной в слоте 0. При обновлении реализации добавляется новая переменная — и она перекрывает чужой слот.

```solidity
// Proxy: slot0 = implementation
// Impl v1: slot0 = totalSupply, slot1 = balances
// Impl v2 добавляет в slot0 = owner  -> перезаписывает implementation!
```

Решение — EIP-1967: класть `implementation` в «невычислимый» слот `keccak256("eip1967.proxy.implementation") - 1`. Тогда коллизия с обычными переменными практически невозможна.

## Шаг 3: uninitialized implementation

Второй классический баг — **неинициализированная реализация**. Прокси хранит логику отдельно, и сама реализация развёрнута по своему адресу. Если у реализации есть `initialize()`, которую можно вызвать напрямую (не через прокси), атакующий инициализирует её и становится владельцем. Затем — через `delegatecall`-механизм (например, `upgradeToAndCall`) — захватывает прокси.

Защита: вызвать `_disableInitializers()` в конструкторе реализации, чтобы её нельзя было инициализировать напрямую.

## Шаг 4: function selector clash

Прокси должен как-то различать «вызов функции прокси» (например, `upgradeTo`) и «вызов функции реализации». Transparent proxy решает это правилом: если вызывающий — админ, все вызовы идут в логику прокси; иначе — делегируются. UUPS решает иначе: логика обновления живёт **в реализации**, а прокси минимален.

Клаш возникает, когда селектор функции прокси совпадает с селектором функции реализации. Тогда поведение зависит от того, кто вызвал, и появляются обходы.

## Шаг 5: UUPS и authorization

UUPS (`ERC-1822`) держит `upgradeTo` в реализации. Опасность: если забыть `onlyOwner` на `_authorizeUpgrade`, любой может подменить реализацию на вредоносную и выполнить `selfdestruct`/вывод средств. Это самый частый критический баг UUPS.

```solidity
function _authorizeUpgrade(address) internal override onlyOwner {}
```

Без `onlyOwner` — полный захват.

## Шаг 6: diamond (EIP-2535) и storage gaps

Diamond-прокси маршрутизирует вызовы по селекторам к разным «фасетам». Опасность — коллизия селекторов между фасетами и отсутствие «storage gaps» при наследовании. Если базовый контракт добавляет переменную, наследники сдвигаются, и слоты ломаются. `uint256[N] private __gap;` резервирует место.

## Полный прогон: захват неинициализированного прокси

Задача: прокси развёрнут, реализация тоже, но `initialize()` реализации никто не защитил. Атакующий вызывает `initialize()` на адресе реализации, становится её владельцем, затем вызывает `upgradeToAndCall` и подменяет логику на вредоносную.

```
$ forge script Exploit.s.sol --rpc-url $RPC --broadcast
owner of impl: attacker
implementation upgraded -> attacker drainer
flag: nto{uups_un1n1t14l1z3d_1mpl}
```

Никакой ошибки в коде не было: контракт работал «как написано». Проблема — в пропущенной защите инициализации.

## Если не сработало

Если реализацию защитили, смотрите на storage collision (сравните раскладку прокси и реализации), на selector clash и на авторизацию `upgradeTo`. Также проверьте, не остался ли `selfdestruct` в реализации — он может уничтожить прокси.

## Что мы теперь знаем

- `delegatecall` исполняет чужой код в контексте своего storage.
- Storage collision ломает прокси при обновлении.
- EIP-1967 уводит слот implementation из общего пространства.
- Неинициализированная реализация — прямой путь к захвату.
- UUPS требует `onlyOwner` на `_authorizeUpgrade`.
- Diamond нужны storage gaps.

## Как читать прокси

Сравните раскладку storage прокси и реализации; проверьте, защищена ли инициализация; проверьте авторизацию обновления; поищите `selfdestruct`. Эти четыре проверки закрывают большинство прокси-эксплойтов.

## Реальный контекст: почему прокси так популярны

Смарт-контракт неизменяем, а протоколы должны развиваться: исправлять баги, добавлять функции, оптимизировать газ. Прокси решает это, разделяя «адрес, который знают пользователи» и «код, который по нему исполняется». Пользователи взаимодействуют с прокси, а команда обновляет реализацию. Это стандартная практика в DeFi: OpenZeppelin Upgrades, UUPS, Transparent, Beacon, Diamond.

Но каждое обновление — это окно для атаки. Если злоумышленник получит контроль над `implementation`, он подменит логику на вредоносную и выведет все средства. Поэтому аудит прокси — это в первую очередь аудит **авторизации обновления** и **раскладки storage**. Остальное вторично.

## Разбор второго примера: transparent proxy и selector clash

Transparent proxy (OpenZeppelin) использует правило: если `msg.sender` — админ, вызовы не делегируются, а обрабатываются самим прокси (например, `upgradeTo`); иначе — делегируются реализации. Проблема возникает, если селектор функции реализации совпадает с селектором админ-функции прокси. Тогда админ не сможет вызвать «свою» логику, а не-админ получит неожиданное поведение. OpenZeppelin решает это, зарезервировав `upgradeTo`/`admin` и проверяя `msg.sender` в fallback. Но самодельные прокси часто этого не делают.

## Частые вопросы

Что такое storage gap? Это массив `uint256[N] private __gap`, который резервирует слоты в базовом контракте, чтобы наследники при добавлении переменных не сдвигали раскладку. Почему EIP-1967 использует `keccak256`? Чтобы слот реализации с подавляющей вероятностью не совпал ни с одной «обычной» переменной. Можно ли обновить прокси на `selfdestruct`-реализацию? Да, если авторизация слабая, и тогда прокси (а с ним все средства) будет уничтожен — это известный класс эксплойтов. Что проверяет `forge inspect storage`? Раскладку слотов контракта — её сравнивают у прокси и реализации.

## Практика без лаборатории

Разверните в `anvil` простой прокси и реализацию через OpenZeppelin. Затем напишите вторую реализацию, добавив переменную перед существующими, и посмотрите, как `forge inspect storage` покажет сдвиг слотов. Наконец, разверните реализацию без `_disableInitializers()` и вызовите `initialize()` напрямую — убедитесь, что стали владельцем. Эти три эксперимента дают полное понимание прокси-рисков.

## Разбор ошибок из реальных аудитов

Прокси-инциденты почти всегда выглядят одинаково. Первый: реализацию не защитили `_disableInitializers()`, и её инициализировали напрямую — захват. Второй: в UUPS забыли `onlyOwner` на `_authorizeUpgrade` — любой обновил логику. Третий: storage collision из-за самодельного прокси, где `implementation` лежит в слоте 0 рядом с переменными реализации. Четвёртый: selector clash между функцией прокси и функцией реализации, из-за чего админ не может вызвать свою логику, а не-админ получает чужое поведение. Пятый: `selfdestruct` в реализации, уничтожающий прокси со всеми средствами. Шестой: отсутствие storage gap, из-за чего добавление переменной в базовый контракт сдвигает слоты наследников. Все шесть — ручные проверки, и все шесть встречались в реальных протоколах.

## Итог по модели угроз

Прокси — это shared storage между прокси и реализацией. Безопасность держится на трёх столпах: раскладка слотов (EIP-1967 + gaps), защита инициализации, авторизация обновления. Если хотя бы один столп слаб — протокол захватывается. Поэтому аудит upgradeable-контракта начинается не с логики, а именно с этих трёх вещей.

## Как выбрать паттерн прокси

Transparent proxy прост в понимании, но дороже по газу и имеет selector-clash-нюансы; его часто берут для «классических» протоколов. UUPS дешевле и оставляет логику обновления в реализации, но требует не забыть `onlyOwner` на `_authorizeUpgrade` — зато риск сосредоточен в одном месте. Beacon удобен, когда много прокси должны указывать на одну реализацию: обновляешь beacon — обновляешь всех. Diamond нужен, когда контракт превышает лимит размера (24 КБ) и его режут на фасеты; цена — сложность маршрутизации и риск коллизии селекторов. Выбор паттерна — это компромисс между газом, сложностью и поверхностью атаки. В аудите важно понять, какой паттерн перед вами, потому что классы багов у них разные.

## Практический чек-лист аудита прокси

Прежде чем читать логику, ответьте на шесть вопросов. Где хранится адрес реализации — в обычном слоте 0 или в EIP-1967-слоте? Если в слоте 0, сравните раскладку прокси и реализации: нет ли переменной, которая перекроется. Защищена ли инициализация реализации (`_disableInitializers` или `initialized`-флаг в конструкторе)? Проверяет ли функция обновления права (`onlyOwner`, роль `UPGRADER`)? Есть ли в реализации `selfdestruct` или `delegatecall` на произвольный адрес? Совпадают ли селекторы функций прокси и реализации? Если на все шесть вопросов ответы «безопасно» — прокси, скорее всего, корректен. Если хотя бы один ответ «нет» — это потенциальный критический баг, и его нужно проверить в первую очередь, до любой логики. Именно эти шесть вопросов покрывают подавляющее большинство реальных прокси-инцидентов, потому что все они — следствие одной из трёх ошибок: слабая раскладка storage, слабая инициализация, слабая авторизация обновления. Запомните их как мантру аудита upgradeable-контрактов.
