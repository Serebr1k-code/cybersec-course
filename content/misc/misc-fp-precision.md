## Вопрос, с которого всё начинается

Ты пишешь банковскую проверку: `if (balance - amount >= 0) allow()`. Спустя время баланс уходит в минус на копейку, а иногда списание проходит дважды. Причина — числа с плавающей точкой. Они не хранят десятичные дроби точно. Разберём, как это устроено.

## Наш пример

Выполним в Python:

```
>>> 0.1 + 0.2
0.30000000000000004
>>> 0.1 + 0.2 == 0.3
False
```

Три десятых, казалось бы, очевидны. Но компьютер получил `0.30000000000000004`. Это не баг Python — это IEEE-754.

## Шаг 1: как хранится float

Число с плавающей точкой по стандарту **IEEE-754** — это знак, экспонента и мантисса (дробная часть). Для 64 бит: 1 бит знака, 11 бит экспоненты, 52 бита мантиссы. Значение = ±мантисса × 2^экспонента. Дробные числа вида `0.1` в двоичной системе — бесконечная периодическая дробь, которую приходится обрезать до 52 бит. Отсюда погрешность.

## Шаг 2: почему 0.1 не точна

Десятичная `0.1` = `1/10`. В двоичной системе это `0.0001100110011...` — бесконечная дробь. В 52 битах мантиссы её можно сохранить лишь приблизительно. Суммируя два приближения, получаешь ещё более приближённый результат — тот самый `0.30000000000000004`.

## Шаг 3: сравнение на равенство

Главное правило: **никогда не сравнивай float на точное равенство**. Вместо `a == b` используй `abs(a - b) < epsilon`, где `epsilon` — допуск (например, `1e-9`). Иначе код «иногда» ломается: на одних значениях проходит, на других — нет. Это источник трудноуловимых багов.

## Шаг 4: где это уязвимость

- Финансы: накопление копеек даёт расхождение; округление в свою пользу (rounding attack).
- Проверка границ: `if (x < limit)` может пропустить `x`, «почти равный» limit.
- Накопление сумм: миллион сложений с плавающей точкой уходит от точного результата.
- NaN: `NaN != NaN`, поэтому сравнения с NaN ведут себя неинтуитивно и могут обойти проверки.

## Шаг 5: NaN и специальные значения

Кроме обычных чисел есть `+Inf`, `-Inf`, `NaN` (не число). Особенности: `NaN != NaN` истинно; любое сравнение с NaN даёт false. Если валидатор полагается на `>`/`<`, NaN может «проскочить». `Inf` тоже особый: `Inf - Inf = NaN`.

## Шаг 6: точность vs скорость

Числа с плавающей точкой быстрые (аппаратные), но неточные. Для денег и криптографии нужны **целые** (копейки в минорных единицах) или десятичная арифметика (decimal, rational). Правило: там, где важна точность, float не использовать.

## Шаг 7: как проверять

- Ищи сравнения float на `==`.
- Ищи накопление сумм в float.
- Проверяй поведение с NaN/Inf (подай их на вход).
- Смотри округления в финансовых операциях.

## Шаг 8: практический пример

Задача: найти значение, при котором `0.1 * n` «перестаёт» быть целым. Прогон в цикле показывает, что уже на малых n результат отличается от ожидаемого. В CTF так строят «невозможные» сравнения: подбирают вход, при котором float-проверка проходит, а целочисленная — нет.

## Частые ошибки

- Сравнивать float через `==`.
- Использовать float для денег.
- Забывать про NaN в сравнениях.
- Считать, что `x/y*y == x` всегда.

## Что мы теперь знаем

- Float хранится как знак + экспонента + мантисса (IEEE-754).
- Десятичные дроби не представимы точно в двоичной системе.
- Сравнение float на равенство — источник багов.
- NaN/Inf ведут себя особо и могут обойти проверки.
- Для точности — целые или decimal, не float.

## Разбираем IEEE-754 по битам

Чтобы понять погрешность, полезно увидеть, как число лежит в памяти. В Python это делается через `struct`:

```python
import struct
b = struct.pack('>d', 0.1)          # 8 байт big-endian
print(b.hex())                       # '3fb999999999999a'
print(format(0.1, '.20f'))           # '0.10000000000000000555'
```

Первый байт `3f` — знак и старшие биты экспоненты; дальше — мантисса. Запись `0.10000000000000000555` показывает, что реально хранится не 0.1, а ближайшее к нему представимое число. Именно эта разница накапливается при сложении.

Формула значения: `(-1)^s × 1.mantissa × 2^(exponent-1023)` для нормализованных чисел. Мантисса подразумевает ведущую единицу, поэтому в 52 битах хранится 53 значащих бита точности. Это даёт примерно 15–17 десятичных значащих цифр для float64 — и ни одной гарантии, что последняя цифра верна.

## Reference: диапазоны и точность

| Тип | Биты | Значащих цифр | Примерная точность |
|-----|------|---------------|--------------------|
| float16 (half) | 16 | ~3–4 | 0.001 |
| float32 (single) | 32 | ~7 | 1e-7 |
| float64 (double) | 64 | ~15–16 | 1e-16 |
| float128 | 128 | ~34 | 1e-34 |

Сравнение с `epsilon`: `1e-7` для float32, `1e-15` для float64. Но `epsilon` — палка о двух концах: слишком большой — пропустите реальные различия; слишком маленький — не спасёте от накопленной ошибки. Правильный выбор зависит от того, сколько операций выполнено над числом.

## Опасные паттерны в коде

Ищем такие конструкции при аудите:

- `if (balance - amount >= 0)` — при накоплении баланс может стать `-1e-12`, и условие ложно.
- `if (a == b)` — точное сравнение двух float.
- `total += price` в цикле — накопление ошибки.
- `if (x > limit)` где `x` приходит из float-вычисления — NaN обходит проверку.
- `Math.round(amount * 100)` — классический источник потери копейки при больших суммах.

Особенно опасны финансовые проверки, где «почти ноль» трактуется как ноль. Если валидатор сравнивает результат умножения с нулём, а результат — крошечная положительная величина, он может принять её за ноль и разрешить операцию, которая на самом деле не сходится.

## decimal и fractions: точная арифметика

Когда точность критична, используют не float:

```python
from decimal import Decimal, getcontext
getcontext().prec = 28
print(Decimal('0.1') + Decimal('0.2'))   # 0.3 — точно

from fractions import Fraction
print(Fraction(1, 10) + Fraction(2, 10)) # 3/10
```

`Decimal` хранит десятичные цифры точно и подходит для денег. `Fraction` держит рациональное число как пару числитель/знаменатель и не теряет точность вовсе. Оба медленнее float, поэтому применяются там, где ошибка недопустима. Ещё проще: храните деньги в **целых копейках** и делите на 100 только при выводе — тогда арифметика целочисленная и точная.

## NaN и Inf в проверках

Специальные значения ломают наивную логику. `NaN` не равен ничему, включая себя, а любое сравнение с ним даёт `false`:

```python
import math
n = float('nan')
print(n == n, n < 0, n > 0)     # False False False
print(n != n)                    # True
```

Если валидатор написан как `if not (x < 0 or x > limit): allow()`, то для `NaN` оба сравнения ложны, и условие `not (False or False)` истинно — доступ разрешён. Так NaN может обойти проверку диапазона. Аналогично `Inf`: `1/0.0` даёт исключение, но `1.0/float('inf')` даёт `0.0`, а `inf - inf` — `NaN`. Проверяйте вход на `math.isnan` и `math.isinf` до сравнений.

## Worked example: rounding attack

Классический сценарий: приложение округляет сумму транзакции в меньшую сторону и разницу накапливает на свой счёт. Дано: комиссия 0.5 % от 0.01. Точный результат — 0.00005, но в float32 он превращается в 0.000049999, а `floor` даёт 0. Если делать такую операцию массово, «сэкономленные» доли накапливаются. Защита — считать комиссию в целых минорных единицах и использовать банковское округление (`ROUND_HALF_EVEN`), а не усечение.

## Если не сработало

- **Проверка всё равно обходится.** Возможно, дело не в NaN, а в переполнении целых или в отрицательном нуле (`-0.0 == 0.0` истинно).
- **Сравнение с epsilon не помогает.** Ошибка накопилась больше epsilon. Считайте относительную погрешность: `abs(a-b) <= eps * max(abs(a), abs(b))`.
- **Decimal тоже даёт расхождение.** Проверьте контекст (`prec`, режим округления) и что числа создаются из строк, а не из float (`Decimal(0.1)` содержит ошибку float).
- **Значения выглядят нормально, но баг есть.** Ищите неявные преобразования float↔int, которые обрезают дробную часть.

## Ограничения

Float — не «плохой» тип, он оптимален для научных расчётов, графики и машинного обучения, где небольшая относительная погрешность допустима. Проблемы начинаются там, где точность интерпретируется как точность денег или как гарантия границы. Поэтому правило простое: выбирайте тип по смыслу величины, а не по удобству.

## Полезные функции для отладки

При разборе float-багов помогают несколько приёмов. `repr(x)` в Python показывает кратчайшее представление, а `format(x, '.17g')` — максимально точное, по которому видно реальное хранимое значение. Функция `math.nextafter(x, y)` возвращает следующее представимое число в направлении `y` — так можно измерить «шаг» сетки float в окрестности значения. `math.ulp(x)` даёт размер этого шага напрямую. Зная ulp, вы понимаете, какая минимальная разница между двумя числами вообще различима, и подбираете epsilon осмысленно, а не наугад.
