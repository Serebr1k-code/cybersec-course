## Вопрос, с которого всё начинается

Чистое символьное исполнение ломается на первом же сложном месте: циклы, косвенная адресация, вызовы библиотек. Что делать? Идея: **исполнять программу по-настоящему**, но параллельно записывать, какие ограничения встретились. Так рождается коколическое тестирование.

## Наш пример

У нас есть `concolic.log` — трасса гибридного прогона:

```
run: input=AAAA path: 0x4011a0 -> 0x4011c0
negate: 0x4011c0 -> constraint: input[2] == 0x7b
new input found: AA{A
```

Здесь видно: сначала конкретный прогон с `AAAA`, затем **отрицание** одной ветки и новый вход. Наша задача — понять этот механизм.

## Шаг 1: два имени — одна идея

Коколическое тестирование называют по-разному: **concolic** (concrete + symbolic), **DSE** (dynamic symbolic execution), **DART**, **SAGE**. Суть одна:

- программа исполняется **конкретно** (реальные значения, реальные ветки);
- одновременно **символически** собираются ограничения вдоль пройденного пути;
- затем одно ограничение **отрицается**, и решатель ищет вход, ведущий в соседнюю ветку.

## Шаг 2: почему это дешевле чистого символьного

Чистое символьное исполнение исследует **все** пути. Коколическое идёт **по одному пути за раз**, от конкретного входа, и лишь «отщипывает» соседние ветки. Циклы и библиотеки исполняются конкретно — их не нужно моделировать символьно. Это огромное упрощение.

Цена: покрытие неполное. Ты находишь то, до чего дотягиваются отрицания, а не всё сразу.

## Шаг 3: снятие ограничений вдоль пути

Во время прогона движок записывает для каждой ветки условие, при котором она выбрана. Пусть путь прошёл `input[0] == 'n'`, затем `input[1] == 't'`. Тогда путь-условие: `input[0]=='n' AND input[1]=='t'`. Отрицая последнее (`input[1] != 't'`), получаем вход в соседнюю ветку.

Именно это показано в нашем логе: `negate: 0x4011c0 -> constraint: input[2] == 0x7b` — движок «перевернул» ветку и нашёл новый вход `AA{A`.

## Шаг 4: как строится покрытие

Алгоритм примерно такой:

1. взять начальный вход (случайный или заданный);
2. исполнить конкретно, собрать путь-условия;
3. выбрать одно ограничение, **отрицать** его, решить;
4. если решение есть и вход новый — добавить в очередь;
5. повторять, пока очередь не пуста.

Так постепенно исследуются ветки. Это напоминает фаззинг, но «умный»: входы не случайны, а выведены из ограничений.

## Шаг 5: где коколика сильнее фаззинга и символьного

- **Сильнее фаззинга**: на сложных проверках (`if (crc(x)==0xDEADBEEF)`) — фаззер туда не попадёт, а решатель найдёт вход точно.
- **Сильнее символьного**: на программах с циклами и библиотеками, где чистое символьное исполнение захлёбывается.

Именно поэтому коколику (SAGE в Microsoft, angr с `concrete`-режимом) применяют для поиска багов в реальных программах.

## Шаг 6: как это выглядит в задаче

Типовой сценарий: крекми, где символьное исполнение «зависает», но коколический подход проходит: движок идёт от входа к входу, отрицая ветки, пока не дойдёт до успешной. В логе видно последовательность «прогон → отрицание → новый вход».

## Шаг 7: находим флаг в трассе

В `concolic.log` есть строка `flag` в base64:

```
$ grep flag concolic.log
flag: bnRve2MwbmMwbDFjX2czbjNyNHQzZF8xbnB1dH0=
```

Декодируем и пишем в файл:

```
$ grep flag concolic.log | cut -d: -f2 | base64 -d
nto{c0nc0l1c_g3n3r4t3d_1nput}
$ grep flag concolic.log | cut -d: -f2 | base64 -d > found.txt
$ check
```

Метка описывает результат: коколический метод сгенерировал вход.

## Что мы теперь знаем

- Коколика = конкретное исполнение + символические ограничения вдоль пути.
- Ветки «отрицаются», чтобы найти соседние входы.
- Это дешевле чистого символьного исполнения, но покрытие неполное.
- Сильнее фаззинга на сложных проверках, сильнее символьного — на циклах.
- Применяется в DSE/DART/SAGE для поиска реальных багов.

## Формализуем путь-условие

Коколику полезно понимать на уровне формул. Пусть программа содержит последовательность условий:

```c
if (input[0] == 'n') {        // ветка A
  if (input[1] == 't') {      // ветка B
    if (input[2] == 'o') {    // ветка C
      win();
    }
  }
}
```

Конкретный прогон с `input = "xyz"` не войдёт ни в одну из веток, и путь-условие будет `input[0] != 'n'`. Движок отрицает **последнее** ограничение пути: `input[0] == 'n'`. Решатель находит вход `"nxx"`. На следующем прогоне путь-условие становится `input[0] == 'n' AND input[1] != 't'`. Отрицаем последнее: `input[0]=='n' AND input[1]=='t'` → вход `"ntx"`. И так далее, пока не дойдём до `win()`.

Так работает «перебор веток по одной». Важно, что отрицается **одно** ограничение за раз, а предыдущие сохраняются — иначе движок будет ходить по кругу.

## Reference: инструменты коколики

| Инструмент | Тип | Особенность |
|-----------|-----|-------------|
| angr | Python-фреймворк | символьное + concrete-режим |
| KLEE | LLVM IR | классика символьного, есть concrete |
| SAGE | проприетарный (MS) | коколика в масштабе, x86 |
| Manticore | Python (Trail of Bits) | символьное + concrete |
| Triton | библиотека | DSE-примитивы для своих движков |
| Driller | гибрид | AFL + angr, фаззинг с решателем |

Из этого списка для CTF чаще всего используют angr (в concrete-режиме через `explore`) и Manticore. KLEE и SAGE — для программ на C/C++ и бинарников x86.

## Гибридные фаззеры: лучшее из двух

Чистый фаззер быстр, но «слеп» к сложным проверкам. Чистая коколика умна, но медленна на больших путях. **Гибрид** (Driller, QSYM) работает так: фаззер бежит по программе, собирает покрытие и находит «застрявшие» места; когда фаззер не может пройти сложную ветку, включается решатель, который строит вход под неё; вход возвращается фаззеру, и тот продолжает с новой точки.

Такая связка даёт и скорость фаззера, и точность решателя. Именно поэтому современные фаззеры (AFL++, honggfuzz) всё чаще встраивают SMT-решатель как компонент.

## Когда коколику применять, а когда нет

Коколика оправдана, когда:

- проверка сложная и случайный вход её не проходит (`crc`, хеш, сравнение длинной строки);
- программа небольшая, и путь-условия решаемы;
- нужен **конкретный** вход, а не доказательство.

Коколика плохо подходит, когда:

- вход огромный (мегабайты) — символическое отслеживание всех байтов не по силам;
- много нелинейной арифметики (умножение символов) — решатель не справляется;
- код содержит хеш-функции от символических данных — инвертировать невозможно;
- путей экспоненциально много (path explosion).

В последних случаях применяют фаззинг, трассировку или ручной реверс.

## Path explosion: главный враг

Каждая ветка удваивает число путей. Даже при «одном пути за раз» коколика ведёт **очередь** путей, и она может расти взрывно. Приёмы борьбы:

- **приоритизация** — исследовать сначала пути, ведущие к цели (по эвристике);
- **ограничение глубины** — не углубляться дальше N шагов;
- **сужение входа** — символически отслеживать только часть байтов;
- **мемоизация** — не пересчитывать одинаковые префиксы путей.

В angr это управляется через `SimulationManager`, `explore(find=..., avoid=...)` и лимиты на количество активных состояний.

## Разбор строки трассы коколики

В реальных логах встречаются поля вида `negate`, `constraint`, `new input`. Разберём их смысл:

- `run: input=... path: 0x... -> 0x...` — конкретный прогон и последовательность адресов (базовых блоков), которую он прошёл.
- `negate: 0x... -> constraint: ...` — движок выбрал ветку по этому адресу и записал её отрицание как новое ограничение.
- `new input found: ...` — решатель вернул вход, удовлетворяющий ограничению; он пойдёт в очередь на исполнение.

Читая лог сверху вниз, вы видите, как движок «ползёт» по веткам от начального входа к цели. Если цель достигнута, рядом обычно лежит сгенерированный вход (часто это и есть флаг или ключ).

## Если не сработало

- **Решатель возвращает «unsat».** Ограничение противоречиво — возможно, отрицание выбрано неверно или предыдущие ограничения потеряны.
- **Движок зависает.** Скорее всего, встретил нелинейную арифметику или хеш. Упростите задачу: замените хеш-проверку на сравнение или сузьте вход.
- **Вход найден, но программа его отвергает.** Возможно, есть вторая, независимая проверка (серверная или нативная). Коколика даёт только один слой.
- **Слишком много путей.** Включите приоритизацию и `avoid`, чтобы не тратить время на тупики.
- **Символические переменные не отслеживаются.** Проверьте, что вход помечен символически (`claripy.BVS`), а не задан конкретным значением.

## Ограничения

Коколика — компромисс: она жертвует полнотой покрытия ради вычислимости. Она не доказывает отсутствие бага, она находит входы, до которых дотягивается отрицанием. Поэтому в реальном аудите её всегда дополняют фаззингом, ручным анализом и трассировкой.

## Как закодировать вход для angr

Практический минимум для запуска коколики на бинарнике: загрузить его, объявить входные байты символическими и запустить исследование. Например, для программы, читающей строку со stdin, создают символический буфер из N байтов (`claripy.BVS`), кладут его в память по адресу входного буфера и передают менеджеру состояний. Затем `simgr.explore(find=<адрес успеха>, avoid=<адрес провала>)` перебирает пути. Найденное состояние содержит конкретные значения символических байтов — это и есть искомый вход. Такой подход покрывает случай, когда чистое символьное исполнение захлёбывается на длинных путях.
