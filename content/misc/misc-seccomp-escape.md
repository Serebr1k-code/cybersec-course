seccomp (secure computing) — механизм Linux, ограничивающий набор доступных процессу системных вызовов. В CTF его применяют в двух контекстах: как защиту (в pwn-задачах, чтобы нельзя было просто вызвать `execve('/bin/sh')`) и как саму цель («дана песочница — сбегите»). Понимание seccomp-BPF — обязательный навык для современного pwn и для задач про изоляцию.

## Что такое seccomp-BPF

Программа регистрирует фильтр через `prctl(PR_SET_SECCOMP, SECCOMP_MODE_FILTER, ...)` или `seccomp()`. Фильтр — это BPF-программа, которая на каждый syscall возвращает одно из действий:

| Действие | Значение | Смысл |
|----------|----------|-------|
| `SECCOMP_RET_ALLOW` | `0x7fff0000` | разрешить |
| `SECCOMP_RET_ERRNO` | `0x00050000` | вернуть errno |
| `SECCOMP_RET_KILL_THREAD` | `0x00000000` | убить поток |
| `SECCOMP_RET_TRAP` | `0x00030000` | SIGSYS |
| `SECCOMP_RET_TRACE` | `0x7ff00000` | передать tracer'у |
| `SECCOMP_RET_LOG` | `0x7ffc0000` | залогировать и разрешить |

Фильтр видит номер syscall (`arch`, `nr`), аргументы (`args[0..5]`), но **не может разыменовывать указатели** — только сравнивать значения. Это важно: фильтр не может проверить содержимое строки, переданной в `open`, только сам указатель.

## Дамп и чтение фильтра

```bash
seccomp-tools dump ./chall
# line  CODE  JT   JF      K
# 0000: 0x20 0x00 0x00 0x00000004  A = arch
# 0001: 0x15 0x00 0x05 0xc000003e  if (A != ARCH_X86_64) goto 0007
# 0002: 0x20 0x00 0x00 0x00000000  A = sys_number
# 0003: 0x35 0x00 0x01 0x40000000  if (A < 0x40000000) goto 0005
# 0004: 0x06 0x00 0x00 0x00000000  return KILL
# 0005: 0x15 0x00 0x01 0x00000002  if (A != open) goto 0007
# 0006: 0x06 0x00 0x00 0x7fff0000  return ALLOW
# 0007: 0x06 0x00 0x00 0x00050000  return ERRNO(0)
```

Читаем: если архитектура не x86_64 — KILL. Если `sys_number >= 0x40000000` — KILL (это защита от **x32 ABI**!). Если `open` — ALLOW, иначе ERRNO. Значит, разрешён только `open`.

## Каталог обходов

1. **ORW вместо execve.** Часто `execve` запрещён, но `open`/`read`/`write` разрешены. Тогда не нужен shell — читаем флаг и пишем в stdout: `open("flag", O_RDONLY)` → `read(fd, buf, n)` → `write(1, buf, n)`.

2. **Разрешённые «опасные» syscalls.** Если разрешён `openat` с любыми аргументами — читаем что угодно. Если разрешён `write` — пишем. Если разрешён `sendfile` — копируем файл в сокет.

3. **x32 ABI (архитектурный обход).** Номера syscalls x32 имеют бит `0x40000000`. Если фильтр проверяет только x86_64 и блокирует `>= 0x40000000`, x32 отсекается. Но если фильтр **не** проверяет старшие биты, можно вызвать x32-вариант запрещённого syscall (например, x32 `execve`) и обойти фильтр. Именно поэтому в дампе выше стоит проверка `< 0x40000000`.

4. **Arch check отсутствует.** Если фильтр не проверяет `arch`, можно переключиться на 32-битную (i386) совместимость (`int 0x80`) и вызвать syscalls с другими номерами — фильтр, настроенный на x86_64, их не узнает.

5. **TOCTOU с указателями.** Фильтр не может прочитать строку. Если он запрещает `open` по конкретному пути — не проблема, потому что он видит только указатель. TOCTOU важен для обратного: когда фильтр разрешает по указателю, а мы меняем содержимое.

6. **Обход через `openat2`.** Иногда фильтр блокирует `open`/`openat`, но забывает `openat2` — новый syscall с расширенной структурой.

7. **`ptrace`/`process_vm_readv`.** Если разрешены — читаем память другого процесса, где флаг.

## Учебная задача

```c
// sandbox: только open, read, write
seccomp_rule_add(ctx, SCMP_ACT_ALLOW, SCMP_SYS(open), 0);
seccomp_rule_add(ctx, SCMP_ACT_ALLOW, SCMP_SYS(read), 0);
seccomp_rule_add(ctx, SCMP_ACT_ALLOW, SCMP_SYS(write), 0);
seccomp_rule_add(ctx, SCMP_ACT_KILL, SCMP_SYS(execve), 0);
```

Эксплойт (shellcode-ORW):

```asm
; open("flag.txt", O_RDONLY)
mov rax, 2
lea rdi, [rip+path]
xor esi, esi
syscall
; read(fd, rsp, 0x100)
mov rdi, rax
mov rax, 0
mov rsi, rsp
mov rdx, 0x100
syscall
; write(1, rsp, 0x100)
mov rax, 1
mov rdi, 1
mov rsi, rsp
mov rdx, 0x100
syscall
```

В pwntools:

```python
from pwn import *
sc = shellcraft.open('flag.txt') + shellcraft.read('rax','rsp',0x100) + shellcraft.write(1,'rsp',0x100)
print(asm(sc))
```

## nsjail и «настоящие» песочницы

`nsjail` комбинирует namespaces, seccomp, rlimits и cgroups. Побег требует либо бага в самом nsjail, либо ослабленной конфигурации:

- разрешён `clone`/`unshare` → можно создать новый namespace и выбраться;
- разрешён `mount` → примонтировать хост-ФС;
- `/proc` смонтирован без `hidepid` → видим чужие процессы;
- лишние capabilities (`CAP_SYS_ADMIN`) → почти полный побег.

Проверка окружения:

```bash
cat /proc/self/status | grep -E 'Seccomp|CapEff|NoNewPrivs'
capsh --decode=$(grep CapEff /proc/self/status | awk '{print $2}')
```

## Частые ошибки и подводные камни

- Пытаться вызвать `execve`, когда он KILL — процесс умирает без шанса на отладку; сначала дампните фильтр.
- Забывать про `arch`-check и x32 — многие фильтры дырявые именно там.
- Считать, что фильтр «видит» пути — он видит только указатели.
- Не учитывать, что `open` может быть заблокирован, а `openat`/`openat2` — нет.
- Игнорировать наследование: дочерний процесс наследует фильтр, но иногда сбрасывает.
- Пробовать `system()` в ORW-контексте — нужен `execve`, которого нет.

## Дополнительная теория: как строится BPF-фильтр

Seccomp-фильтр — это программа на классическом BPF, которая исполняется ядром на каждом syscall. Она читает `seccomp_data`: `nr` (номер syscall), `arch` (архитектура), `instruction_pointer` и `args[0..5]`. Программа не имеет доступа к памяти процесса — только к этим полям. Логика обычно такая: загрузить `arch`, проверить, что он ожидаемый (иначе KILL); загрузить `nr`; сравнить с разрешёнными номерами; вернуть ALLOW для разрешённых и ERRNO/KILL для остальных. Уязвимости появляются, когда проверка неполна: забыт `arch`-check, не отсечены x32-номера (`>= 0x40000000`), разрешён слишком широкий набор, или проверка аргументов сделана там, где её быть не может (указатели).

Понимание структуры фильтра позволяет читать дампы `seccomp-tools` и находить дыры. Ищите: разрешён ли `openat`/`openat2`/`sendfile`/`ptrace`; есть ли `arch`-check; отсечены ли x32; что возвращается по умолчанию.

## Комбинированные песочницы

На практике seccomp редко один: его комбинируют с namespaces (см. `misc-namespace-escape`), rlimits, `no-new-privs`, AppArmor/SELinux. Побег тогда требует дыры в одном слое без компенсации в другом. Например, seccomp запрещает `execve`, но разрешает `open` — ORW решает. Или seccomp разрешает всё, но namespaces изолируют — тогда нужен namespace-побег. Классифицируйте песочницу: «логическая» (фильтр syscalls), «ресурсная» (rlimits/cgroups), «пространственная» (namespaces). Техника побега зависит от класса.

## Разбор ошибок и отладка

Если процесс умирает при вызове syscall — фильтр вернул KILL; смотрите дамп, чтобы понять, какой именно. Если syscall возвращает `EPERM`/`EINVAL` — фильтр вернул ERRNO; ищите разрешённую альтернативу (`openat` вместо `open`). Если ORW-шеллкод не работает — проверьте, что `open` разрешён и что путь валиден; используйте `strace` на локальной копии без фильтра. Если `seccomp-tools dump` показывает пустой фильтр — возможно, seccomp не активен (проверьте `Seccomp: 0` в `/proc/self/status`). Всегда сначала дампните фильтр, потом пишите эксплойт — иначе стреляете вслепую.

## Практический разбор: обход через i386 (int 0x80)

Дано: фильтр проверяет `arch == ARCH_X86_64` и блокирует `execve` по номеру x86_64 (59). Но фильтр **не отсекает** номера i386-совместимости. В 64-битном процессе можно переключиться в 32-битный режим через `int 0x80` и вызвать `execve` с i386-номером (11), который фильтр не проверял.

```asm
; 32-битный execve через int 0x80 из 64-битного процесса
mov eax, 11          ; SYS_execve (i386)
mov ebx, path
xor ecx, ecx
xor edx, edx
int 0x80
```

Проверка дампа:

```bash
seccomp-tools dump ./chall
# ищите проверку arch и наличие правила для i386
```

Если `arch`-check отсутствует вовсе, можно вызвать любой syscall с «чужим» номером, и фильтр его не узнает. Именно поэтому в дампе из урока стояла проверка `if (A != ARCH_X86_64) KILL` и отсечение `>= 0x40000000`. Отсутствие любой из них — дыра. Этот приём (ABI confusion) — классика обхода seccomp; помимо i386, есть x32 (`0x40000000`), ARM-совместимость и другие ABI. Всегда проверяйте, покрывает ли фильтр все ABI, на которых может работать процесс.
