## Вопрос, с которого всё начинается

После логина на CTF-сайте тебе выдают cookie `auth=eyJhbGciOi...`. Ты заходишь как `guest` и видишь страницу, где написано «admin only». Токен выглядит как случайная строка, но это не сессия на сервере — это **JWT** (JSON Web Token), который несёт данные о тебе прямо в себе. Если сервер проверяет его неправильно, ты можешь стать admin без всякого пароля.

Разберём подделку JWT на реальном токене.

## Наш пример: cookie с JWT

JWT состоит из трёх частей, разделённых точками: `header.payload.signature`. Все три — **base64url** (base64 с заменой `+`/`/` на `-`/`_` и без padding). Декодируем payload:

```
$ echo 'eyJ1c2VyIjoiZ3Vlc3QiLCJyb2xlIjoidXNlciJ9' | base64 -d
{"user":"guest","role":"user"}
```

Понятно: сервер верит, что мы `guest` с ролью `user`. Первая часть — **header** — говорит, каким алгоритмом подписано:

```
$ echo 'eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9' | base64 -d
{"alg":"HS256","typ":"JWT"}
```

`HS256` — подпись HMAC-SHA256 общим секретом. Третья часть — **signature** — это `HMAC(base64url(header)+"."+base64url(payload), secret)`. Если поменять payload, подпись перестанет совпадать — и в этом вся защита. Наша задача — обойти её.

## Шаг 1: полный исходный токен

Возьмём токен целиком, сгенерированный с секретом `secret123`:

```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ1c2VyIjoiZ3Vlc3QiLCJyb2xlIjoidXNlciJ9.bVaFZOeMJOMU17kew-Lva1OzV8GmDp_QZpjbM0gjvdc
```

Инструмент `jwt_tool` показывает структуру:

```
$ python3 jwt_tool.py <token>
[*] alg: HS256
[*] payload: {"user":"guest","role":"user"}
```

План атаки зависит от того, **как** сервер проверяет подпись. Пробуем векторы по очереди.

## Шаг 2: alg=none

Некоторые серверы (точнее, их библиотеки) принимают алгоритм `none` — «подписи нет». Тогда мы просто меняем header на `{"alg":"none"}`, ставим в payload `admin` и оставляем подпись пустой:

```
eyJhbGciOiJub25lIiwidHlwIjoiSldUIn0.eyJ1c2VyIjoiYWRtaW4iLCJyb2xlIjoiYWRtaW4ifQ.
```

Обрати внимание на точку в конце — третий сегмент пуст. Современные библиотеки по умолчанию отклоняют `none`, но в CTF встречаются и варианты `None`, `NONE`, `null`. Если сервер отвечает `alg not allowed` — вектор закрыт, идём дальше.

## Шаг 3: подбираем секрет (HS256)

Если `none` не прошёл, значит подпись проверяется. Но секрет HMAC может быть слабым — тогда его подбирают словарём:

```
$ hashcat -m 16500 token.txt rockyou.txt
...:secret123
```

Режим `-m 16500` — как раз JWT HS256. Для CTF часто хватает очевидных строк: `secret`, `password`, имя приложения, пустая строка. Если не нашлось — секрет случайный, и подбор бессмыслен: ищи утечку в исходниках, `.env`, GitHub.

## Шаг 4: подписываем admin

Секрет найден. Теперь мы сами можем выпускать валидные токены с любым payload:

```python
import jwt
print(jwt.encode({"user": "admin", "role": "admin"}, "secret123", algorithm="HS256"))
```

```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ1c2VyIjoiYWRtaW4iLCJyb2xlIjoiYWRtaW4ifQ.AqcptP-Uz2LR3qiCTOHOYAK15gpQ1ccQDJPd_PUJciQ
```

Подставляем cookie — и мы admin. Тот же результат даёт ручная сборка через `hmac` и `base64url`, но важно не забыть убрать padding и заменить `+`/`/` на `-`/`_`, иначе подпись не совпадёт.

## Шаг 5: алгоритмная путаница HS/RS

Иногда сервер использует асимметричную подпись `RS256`: приватным ключом подписывает, публичным проверяет. Публичный ключ доступен (например, в `/.well-known/jwks.json`). Если реализация доверяет полю `alg` из токена, можно переключить его на `HS256` и подписать **публичным ключом** как HMAC-секретом — сервер проверит тем же ключом и согласится:

```
$ python3 jwt_tool.py <token> -X k -pk public.pem
```

Это классическая **alg confusion**. Защита — фиксировать ожидаемый алгоритм на сервере и не доверять `alg` из токена.

## Шаг 6: kid и jku

Поле `kid` (key id) иногда используется как путь к файлу или подставляется в SQL. Тогда:

```json
{"alg":"HS256","kid":"../../dev/null"}
```

Если `kid` — путь, подписываем ключом из известного файла: `/dev/null` даёт пустой ключ, `/proc/self/environ` — переменные окружения. Если `kid` попадает в SQL — возможна инъекция в выбор ключа.

Поля `jku`, `x5u`, `jwk` указывают, **откуда взять ключ**. Если сервер доверяет им без allowlist, подсовываем свой JWKS:

```json
{"alg":"RS256","jku":"https://evil.example/jwks.json"}
```

Сервер скачает наш ключ и проверит подпись — обход.

## Шаг 7: claims и время

Payload — это набор **claims** (утверждений). `exp` (expiration) и `nbf` (not before) ограничивают время; если сервер игнорирует `exp`, украденный токен работает вечно. `aud` (audience) и `iss` (issuer) проверяют получателя и издателя; их отсутствие — типовая дыра в микросервисах. `sub` (subject) обычно идентификатор пользователя: подмена `sub` при слабой подписи — прямой путь к эскалации. Встречается и **type confusion**: `exp` сравнивают как строку, и `"9"` оказывается «больше» числа — токен не считается истёкшим.

## Шаг 8: где токен хранится и как отзывается

JWT **stateless**: сервер не хранит сессию, а доверяет подписи. Это удобно для масштабирования и плохо для безопасности — токен нельзя «отозвать» до истечения `exp`. Отсюда практики: короткое время жизни access-токена плюс refresh-токен, чёрный список по `jti`, смена версии ключа. В CTF встречается задача «токен украден, но истёк»: иногда `exp` проверяется нестрого (сравнение как строк), и подмена `exp` на `"9"` проходит. Отдельно смотри, где токен лежит: в cookie (риск CSRF/XSS), в `Authorization: Bearer` или в localStorage (доступен из JS при XSS). Место хранения подсказывает, какой канал угона реален.

## Что мы теперь знаем

- **JWT** — три base64url-части: `header.payload.signature`; данные лежат в самом токене.
- **alg=none** принимается слабыми реализациями — подпись не проверяется.
- **Слабый секрет HS256** подбирается `hashcat -m 16500`.
- **alg confusion HS/RS** — подпись публичным ключом как HMAC-секретом.
- **kid/jku/jwk** — инъекции в выбор ключа, если сервер им доверяет.
- **Claims** (`exp`, `aud`, `iss`, `sub`) надо проверять на сервере, а не доверять им.

## На что смотреть дальше

Пройди PortSwigger JWT-лаборатории, освой `jwt_tool` и `hashcat -m 16500`. При отладке декодируй ответ сервера: `invalid signature` означает, что подпись проверяется; `alg not allowed` — что `none` закрыт, и стоит смотреть `kid`/`jku`. Помни про base64url при ручной сборке и проверяй `exp`. И держи в голове альтернативы (PASETO, opaque-токены): иногда «JWT-подобный» формат в задаче — самодельный, и у него свои quirks. Веди журнал попыток: каждая ошибка сервера сужает пространство поиска.
