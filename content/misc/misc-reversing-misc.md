## Вопрос, с которого всё начинается

В CTF дают бинарник `crackme`. Запускаешь — он просит пароль. Вводишь что угодно — «Fail». Исходников нет, только машинный код. Как узнать правильный пароль, не подбирая миллионы вариантов? Это задача **реверс-инжиниринга** — восстановления логики программы по её бинарнику. В misc такие задачи короткие: маленький крекми или разбор нестандартного формата.

Разберём крекми на XOR целиком — с настоящим бинарником и настоящим выводом.

## Наш пример: crackme, который просит пароль

Соберём минимальный крекми на C и посмотрим на его поведение:

```
$ printf 'FLAG{xor}\n' | ./crackme
password: Win!
$ printf 'AAAAAAAAA\n' | ./crackme
password: Fail
```

Правильный ввод даёт «Win!», неправильный — «Fail». Наша задача — найти правильный ввод. Начинаем с разведки.

## Шаг 1: определяем тип и собираем строки

Первое — понять, что за файл и какие строки в нём есть:

```
$ file crackme
crackme: ELF 64-bit LSB executable, x86-64, statically linked, not stripped
$ strings -n 4 crackme | grep -iE 'pass|win|fail'
password:
Fail
Win!
```

`ELF` — формат исполняемых файлов Linux; `x86-64` — архитектура; `not stripped` означает, что имена функций сохранились (реверс легче). Строки подсказывают структуру: есть приглашение «password:», ветки «Fail» и «Win!». Значит, где-то есть сравнение ввода с эталоном.

## Шаг 2: дизассемблируем и находим проверку

Дизассемблируем и ищем подозрительную операцию — здесь это XOR с константой `0x2a`:

```
$ objdump -d crackme | grep -iE 'xor.*0x2a'
  4010f3:  83 f0 2a    xor    $0x2a,%eax
```

Команда `xor $0x2a,%eax` берёт байт ввода, складывает по XOR с `0x2a` и кладёт результат обратно. Дальше результат сравнивается с массивом-константой `enc[]`. То есть программа проверяет `input[i] XOR 0x2a == enc[i]` для каждого символа.

## Шаг 3: восстанавливаем ввод из XOR

XOR обратен сам себе: если `out = in XOR 0x2a`, то `in = out XOR 0x2a`. Достаём байты `enc[]` из бинарника и «разворачиваем»:

```python
enc = [0x6c, 0x66, 0x6b, 0x6d, 0x51, 0x52, 0x45, 0x58, 0x57]
print(bytes(b ^ 0x2a for b in enc).decode())
```

```
FLAG{xor}
```

Проверяем на самом бинарнике:

```
$ printf 'FLAG{xor}\n' | ./crackme
password: Win!
```

Ввод восстановлен. Общий рецепт для XOR-проверки: **найти константу и массив, применить XOR обратно**. Так решается большинство простых крекми.

## Шаг 4: если проверка сложная — отладчик

Когда статически разобраться трудно (проверка размазана по коду, много ветвлений), запускают программу под отладчиком `gdb` и смотрят значения в момент сравнения:

```
$ gdb ./crackme
(gdb) break *0x4010f3
(gdb) run
(gdb) x/9bx $rbx          # буфер ввода
(gdb) ni
(gdb) x/9bx $rax          # результат XOR
```

Ключевой приём — точка останова на инструкции сравнения и дамп памяти **в момент проверки**. Иногда проще смотреть `strace`/`ltrace`: они показывают, какие системные и библиотечные вызовы делает программа.

## Шаг 5: патчинг — вместо подбора меняем код

Иногда нужен не конкретный ввод, а «любой проходящий». Тогда патчат саму проверку: меняют условный переход `jne` (jump if not equal) на безусловный `jmp` — программа всегда идёт по ветке «успех»:

```
$ objdump -d crackme | grep -B2 -A2 'jne'
  4010f6:  75 0a   jne   401102 <Fail>
$ r2 -w ./crackme
[0x00401000]> /ad jne
[0x00401000]> wa jmp 0x00401020 @ 0x004010f6
```

Патчинг часто быстрее подбора ввода. Но помни: если задача просит **флаг**, а не просто «пройти», патчинг не поможет — нужен именно правильный ввод.

## Шаг 6: символическое исполнение (angr и Z3)

Когда проверка — набор арифметических и битовых условий, её решают автоматически. **angr** символически исполняет бинарник и ищет вход, ведущий к «успеху»:

```python
import angr
p = angr.Project("./crackme", auto_load_libs=False)
st = p.factory.entry_state()
sm = p.factory.simulation_manager(st)
sm.explore(find=lambda s: b"Win" in s.posix.dumps(1),
           avoid=lambda s: b"Fail" in s.posix.dumps(1))
if sm.found:
    print(sm.found[0].posix.dumps(0))
```

А когда формула видна глазами, быстрее выписать её в **Z3** — решателе ограничений:

```python
from z3 import *
flag = [BitVec(f'c{i}', 8) for i in range(9)]
s = Solver()
for c in flag: s.add(c >= 0x20, c <= 0x7e)     # печатаемые ASCII
s.add(flag[0] ^ 0x2a == 0x6c)                   # условия из бинарника
# ... остальные байты ...
print(s.check(), s.model())
```

Z3 предсказуемее angr, когда ограничения известны. Правило: **сначала пойми логику вручную, потом автоматизируй**.

## Шаг 7: разбор кастомного формата

Часть misc-задач — про формат: «дан файл неизвестного типа, извлеки данные». Первым делом — сигнатура и hex-дамп:

```
$ xxd mystery.bin | head -3
00000000: 4d59 5354 1800 0000 0102 0304  ....
```

Видим 4 байта магии `MYST`, затем little-endian длину `0x18`, затем данные. Пишем парсер:

```python
import struct
d = open("mystery.bin", "rb").read()
magic = d[:4]
(size,) = struct.unpack_from("<I", d, 4)
print(magic, size, d[8:8+size])
```

Так извлекают скрытые поля и флаги из самодельных форматов. `binwalk` помогает найти вложенные сигнатуры, `file` — определить тип.

## Если не сработало

Реверс упирается в защиту или в непонимание кода. Разберём.

**`strings` не даёт зацепок.** Значит, строки зашифрованы или обфусцированы. Ищи XOR-цикл в дизассемблере (часто ключ рядом), либо распаковщик (если файл упакован — `UPX`, кастомный). Динамический подход: запусти под отладчиком и посмотри строки в памяти после распаковки.

**Проверка пароля не находится.** Ищи не `strcmp`, а сравнение посимвольно в цикле, хеш-функцию, или проверку через арифметику. Поставь точку останова на вводе (`scanf`/`read`) и проследи, куда попадают байты.

**XOR-ключ не восстанавливается.** Возможно, ключ длиннее одного байта (повторяющийся) — тогда используй частотный анализ или известный открытый текст (флаг начинается с `FLAG{`). Для одноразового ключа — ищи утечку: ключ может быть в другом файле задачи.

**Отладчик не запускается (anti-debug).** Программа может детектить отладчик (`ptrace`, проверка таймингов) и выходить. Обходи: патчи детект-функций, `LD_PRELOAD` для перехвата `ptrace`, или используй статический анализ (`Ghidra`, `radare2`).

**Патчинг не работает.** Возможно, есть проверка целостности (контрольная сумма кода). Тогда патчь не код, а данные (пароль, ключ), либо снимай проверку целостности в первую очередь.

**`angr` не находит решение.** Символическое исполнение тяжело для больших программ. Сузь: начни с адреса после ввода, ограничь длину входа, задай известный префикс (`FLAG{`). Если всё равно медленно — используй Z3 напрямую на восстановленных ограничениях.

## Частые вопросы

**С чего начинать реверс crackme?** `file` → `strings` → `ltrace`/`strace` (какие функции вызываются) → дизассемблер. Часто проверка видна уже в `ltrace`.

**Когда отладчик, а когда дизассемблер?** Дизассемблер — для понимания логики, отладчик — для наблюдения значений в динамике. Для распаковки и anti-debug — отладчик обязателен.

**Что такое символическое исполнение?** Автоматический поиск входа, при котором программа доходит до нужной точки (например, «пароль верный»). `angr` и Z3 — основные инструменты.

**Патчить или подбирать пароль?** Патчить быстрее, если нужен только доступ. Подбирать/восстанавливать — если нужен сам пароль (иногда это и есть флаг).

## Порядок реверса

Начинай с дешёвого: `file`, `checksec` (защиты), `strings`, `ltrace`/`strace` — какие функции вызываются. Часто проверка пароля видна уже там (`strcmp`, `memcmp`, цикл сравнения). Только потом открывай дизассемблер. Это экономит часы: не нужно читать весь код, если видно нужную функцию.

Если программа упакована или обфусцирована — распакуй динамически (запусти и сними дамп памяти), прежде чем анализировать. При anti-debug обходи детект-функции или используй статический анализ. Для сложных проверок подключай символическое исполнение (`angr`) или Z3, но сначала сузь задачу: известный префикс флага, ограниченная длина, точка после ввода. И всегда проверяй, нужен ли тебе *пароль* или достаточно *доступа* — от этого зависит, патчить или восстанавливать.

## Что мы теперь знаем

- **Реверс** — восстановление логики по бинарнику; в misc это короткий крекми или формат.
- Первые шаги: `file` (тип), `strings` (текст), `objdump` (дизассемблер).
- **XOR-проверка** решается обратным XOR; константу и массив берём из кода.
- **Отладчик** (`gdb`) показывает значения в момент сравнения.
- **Патчинг** (`jne` → `jmp`) убирает проверку, но не даёт правильный ввод.
- **angr/Z3** решают сложные проверки автоматически — но после ручного понимания.
- **Кастомный формат** разбирают по сигнатуре и полям (`xxd`, `struct`).

## На что смотреть дальше

Порядок для крекми: `file` → `strings` → дизассемблер ключевой функции → при необходимости отладчик или Z3/angr. Не пиши angr-скрипт, пока не понял логику вручную. Помни про упаковку (`upx -d` перед анализом) и анти-отладку (`ptrace`). Дальше — полноценная категория `reversing` и анализ малвари. А в ветке misc — `misc-polyglots` и `misc-side-channel-misc`.

Отдельно запомни разницу между **статикой и динамикой**: статический анализ (дизассемблер) показывает код целиком, но упускает проверки, которые включаются только в рантайме; динамический (отладчик, `strace`) показывает реальное поведение, но не всё сразу. Обычно их комбинируют: сначала общая картина по дизассемблеру, затем подтверждение под отладчиком. И не забывай про проверку защиты: `checksec --file=bin` сразу скажет про PIE, NX и канарейки — это влияет и на реверс, и на последующий эксплойт.
