## Вопрос, с которого всё начинается

Тебе дали два зашифрованных сообщения от одного и того же ключа. «Один ключ — два шифртекста, что тут можно узнать?» — спрашиваешь ты. Ответ: **всё**, если при шифровании повторили nonce. Разберём, почему потоковые шифры так чувствительны к повторам.

## Наш пример: два перехваченных сообщения

```
$ cat capture.hex
c1 = 9f8b7d6c5b4a39281706f5e4d3c2b1a0...
c2 = 9f8b7d6c5b4a39281706f5e4d3c2b1a0...   # совпадает начало!
```

Первые байты совпадают — верный признак, что использован один и тот же keystream.

## Шаг 1: как работает потоковый шифр

Потоковый шифр (RC4, AES-CTR, ChaCha20) не шифрует блоки «по отдельности». Он генерирует **keystream** — псевдослучайную последовательность из ключа и nonce — и просто **XOR**-ит её с данными:

```
ciphertext = plaintext XOR keystream
```

Расшифровка — тот же XOR. Стойкость держится на том, что keystream никогда не повторяется.

## Шаг 2: что ломается при повторе nonce

Если nonce один и тот же, keystream тоже один и тот же. Тогда:

```
c1 XOR c2 = (p1 XOR ks) XOR (p2 XOR ks) = p1 XOR p2
```

Keystream сокращается! Мы получаем XOR двух открытых текстов — без ключа. Это уже утечка: XOR двух текстов часто читаем, особенно если один из них известен или предсказуем.

## Шаг 3: crib-dragging

Зная фрагмент одного сообщения (например, HTTP-заголовок `GET / HTTP/1.1`), XOR-им его с `p1 XOR p2` и получаем кусок второго. Это называют **crib-dragging**: подставляем «известные куски» и вытягиваем остальное. Английский/русский текст и структурированные форматы распознаются хорошо.

```
$ python3 crib.py --xored p1xor2.bin --crib 'GET / HTTP/1.1'
recovered: nto{nonc3_r3us3_...
```

## Шаг 4: случай RC4 в CTF

RC4 особенно любим в задачах: маленький код, часто с «солью» из конкатенации. Если сервис шифрует несколько сообщений `RC4(key + counter)` и counter сбрасывается — получаем повтор keystream. Классический сюжет: шифруются два флага/пароля, и один известен.

## Шаг 5: AES-CTR и ChaCha20

AES-CTR шифрует **счётчик**, а не данные: `keystream = AES(key, nonce || counter)`. Если nonce повторён, а счётчик начинается с нуля — keystream повторяется. ChaCha20 использует nonce + счётчик, та же логика. GCM добавляет аутентификацию, но повтор nonce в GCM катастрофичен: раскрывается и ключ аутентификации.

## Шаг 6: как отличить повтор

- Совпадающие префиксы шифртекстов — почти наверняка повтор.
- Длина шифртекста = длине открытого (потоковые шифры не выравнивают).
- Нет паддинга и «блочных» границ.

## Полный прогон от начала до конца

```
$ xxd c1.enc | head -1
00000000: 9f8b 7d6c 5b4a 3928 ...
$ xxd c2.enc | head -1
00000000: 9f8b 7d6c 5b4a 3928 ...
$ python3 xor_two.py c1.enc c2.enc > p1xor2.bin
$ python3 crib.py --xored p1xor2.bin --crib 'flag:'
recovered: flag: nto{n0nc3_r3us3_br34ks_str34m_c1ph3rs}
```

Флаг — во втором сообщении.

## Если не сработало

- Nonce разный — атака не проходит (и это правильно).
- Шифры блочные с паддингом — другой класс атак.
- Данные сжаты перед шифрованием — сначала распакуй гипотезы.
- Известного crib нет — попробуй частотный анализ XOR.

## Что мы теперь знаем

- Потоковый шифр = plaintext XOR keystream.
- Повтор nonce = повтор keystream = `c1 XOR c2 = p1 XOR p2`.
- Известный фрагмент (crib) вытягивает остальное.
- GCM при повторе nonce теряет и ключ аутентификации.
- Защита — уникальный nonce на каждое сообщение.

## Шаг 7: почему XOR-задачи так живучи в CTF

Потоковые шифры дают простую и наглядную математику: один XOR — и всё. В задачах это удобно: автор может зашифровать два сообщения одним keystream и дать оба шифртекста. Решение — заметить повтор, сложить шифртексты, вытянуть текст по известным кускам.

Типовые вариации:

- **Два шифртекста, один ключ** — `c1 XOR c2 = p1 XOR p2`.
- **Известный открытый текст** — если знаем `p1`, сразу получаем `ks = c1 XOR p1` и расшифровываем `p2`.
- **Много сообщений** — строим таблицу XOR-ов и ищем осмысленные фрагменты.

## Шаг 8: повтор nonce в реальных системах

Повтор nonce — не только CTF-выдумка:

- **WEP** — повторение IV в RC4 ломало Wi-Fi; статистические атаки восстанавливали ключ.
- **TLS** — ранние версии с RC4 и повторяющимися IV стали объектом атак (RC4 NOMORE).
- **GCM nonce reuse** — в облачных API и библиотеках повтор nonce приводил к раскрытию и ключа аутентификации.
- **Шифрование диска** — повторение tweak/IV в некоторых реализациях.

Урок один: nonce/IV должен быть **уникален для каждого сообщения под данным ключом**, а не «случаен вообще».

## Шаг 9: crib-dragging глубже

Если открытый текст — естественный язык, помогает частотный анализ XOR. Но надёжнее — **crib-dragging**: подставляем известные фрагменты.

```
$ python3
>>> x = open('p1xor2.bin','rb').read()
>>> crib = b'flag:'
>>> for i in range(0, len(x)-len(crib)):
...     frag = bytes(a^b for a,b in zip(x[i:], crib))
...     if frag.isascii() and frag.isprintable():
...         print(i, frag)
```

Для каждого смещения XOR-им crib и смотрим, получается ли осмысленный текст. Найденный кусок одного сообщения даёт кусок другого — и так по цепочке.

## Шаг 10: полный скрипт

```
$ cat xor_reuse.py
import sys
c1 = open(sys.argv[1],'rb').read()
c2 = open(sys.argv[2],'rb').read()
n = min(len(c1), len(c2))
x = bytes(a^b for a,b in zip(c1[:n], c2[:n]))
open('p1xor2.bin','wb').write(x)
print('wrote p1xor2.bin (len %d)' % n)
```

Дальше — crib-dragging или ручной разбор. Часто одного осмысленного заголовка (`GET /`, `Content-Type:`) достаточно, чтобы вытащить весь флаг.

## Шаг 11: защита

- **Уникальный nonce** на каждое сообщение (счётчик — лучший вариант).
- **Не использовать RC4** — он давно сломан.
- **Для GCM** — 96-битный случайный или счётчик-nonce, никогда не повторять.
- **AEAD** вместо «шифр + самодельная аутентификация».

## Шаг 12: как распознать

1. Два и более шифртекста одинаковой длины.
2. Совпадающие префиксы — верный признак повтора.
3. Нет паддинга, длина = длине открытого текста.
4. Один ключ на несколько сообщений без явного nonce.

Если nonce разный, XOR двух шифртекстов даст мусор — тогда ищи другой вектор.

## Мини-практика: crib по известному заголовку

Быстрый способ вытащить текст, когда один из открытых текстов начинается с предсказуемого фрагмента:

```
$ python3
>>> x = open('p1xor2.bin','rb').read()
>>> crib = b'Content-Type: '
>>> frag = bytes(a^b for a,b in zip(x, crib))
>>> frag[:32]
b'flag: nto{nonc3_r3us3_br34ks_str4m'
```

XOR известного заголовка с `p1 XOR p2` сразу даёт начало второго сообщения. Дальше подставляем следующий crib по мере восстановления текста — это и есть crib-dragging.

## Шпаргалка по повтору nonce

- Формула: `ciphertext = plaintext XOR keystream`.
- При повторе: `c1 XOR c2 = p1 XOR p2` (keystream сокращается).
- Нужно: два и более шифртекста от одного ключа/nonce.
- Приёмы: XOR двух шифртекстов, crib-dragging, частотный анализ.
- Признак: совпадающие префиксы, длина = длине открытого текста.
- Защита: уникальный nonce на сообщение, отказ от RC4, AEAD.

Порядок: 1) заметить повтор, 2) сложить шифртексты, 3) подставить известный crib, 4) восстановить флаг.

## Разбор типовой задачи целиком

Формулировка: «Перехвачены два сообщения, отправленных одним ключом. Восстанови второе». В приложении — два hex-файла.

Первый шаг — сравнить префиксы:

```
$ cmp c1.enc c2.enc | head
differ: byte 20, line 1
```

Первые 20 байт совпадают — верный признак повтора keystream.

Второй шаг — сложить шифртексты:

```
$ python3 xor_reuse.py c1.enc c2.enc
wrote p1xor2.bin (len 64)
```

Получили XOR двух открытых текстов. Сам по себе он нечитаем, но это уже утечка.

Третий шаг — crib-dragging. Предполагаем, что первое сообщение — HTTP-запрос:

```
$ python3 crib.py --xored p1xor2.bin --crib 'GET / HTTP/1.1'
offset 0: b'GET / HTTP/1.1'      -> p1[0:14] = crib
offset 0: b'flag: nto{nonc3'     -> p2[0:14] = 'flag: nto{nonc3'
```

XOR известного заголовка с `p1 XOR p2` сразу дал начало второго сообщения. Продолжаем: теперь мы знаем кусок `p2`, XOR-им его с `p1xor2.bin` и получаем кусок `p1`, и так далее.

Четвёртый шаг — собираем флаг:

```
$ python3 crib.py --xored p1xor2.bin --crib 'flag: nto{nonc3_r3us3_br34ks_str34m_c1ph3rs}'
recovered p2 = 'flag: nto{nonc3_r3us3_br34ks_str34m_c1ph3rs}'
```

Задача решена без ключа и без знания алгоритма шифрования.

## Почему это важнее, чем кажется

Повтор nonce — не «мелкая небрежность», а полная потеря конфиденциальности. В реальных системах это случалось в WEP, TLS, GCM. Причина всегда одна: nonce генерировали «случайно» или из слабого источника, и он повторялся. Урок: уникальность nonce — это не оптимизация, а условие существования шифра.

## Полезные инструменты для XOR-задач

Для разбора повторов удобно держать под рукой несколько маленьких утилит. `xortool` подбирает длину ключа и восстанавливает текст по частотному анализу — полезно, когда открытый текст неизвестен вовсе. `CyberChef` умеет XOR двух файлов и «From Hex» в браузере, что удобно на соревнованиях без окружения. Собственный `xor_reuse.py` из десяти строк — самый быстрый способ сложить два шифртекста и сохранить результат. А для визуального анализа подойдёт любой hex-редактор: одинаковые префиксы видны сразу. Помни порядок: сначала XOR двух шифртекстов, потом crib-dragging, и только если crib нет — частотный анализ.
