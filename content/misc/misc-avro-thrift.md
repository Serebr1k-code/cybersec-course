## Вопрос, с которого всё начинается

Ты перехватил ответ сервиса. Это не JSON и не Protobuf: бинарные данные, где строки чередуются с непонятными числами. Сервис работает на **Thrift** или **Avro** — двух IDL-форматах, популярных в больших системах. Как разобрать данные, если схемы нет?

## Наш пример: бинарный ответ Thrift

```
$ file response.bin
response.bin: data
$ xxd response.bin | head -3
00000000: 8001 0001 0000 0004 6e61 6d65 000b 0002  ........name....
00000010: 0000 0004 6a6f 686e 00                   ....john.
```

Разберём эти байты: здесь закодированы строки `name` и `john`. Поймём, как.

## Шаг 1: что такое IDL

**IDL** (Interface Definition Language) — язык описания структур данных. Ты пишешь схему:

```
struct User {
  1: string name,
  2: i32 age
}
```

Компилятор генерирует код для сериализации. Так же работают Protobuf, Avro, Thrift. Разница — в деталях формата и в том, как хранится схема.

## Шаг 2: Thrift binary protocol

В Thrift бинарный протокол использует **тип-теги**. Каждое поле начинается с байта типа:

| Тип | Код |
|---|---|
| BOOL | 2 |
| BYTE | 3 |
| I32 | 8 |
| STRING | 11 |
| STRUCT | 12 |

Данные: тип, ID поля (2 байта), затем значение. Строка — длина (4 байта) + байты. В нашем дампе `0b` = STRING, `0002` = поле 2, `00000004` = длина 4, `6a6f686e` = `john`.

## Шаг 3: Avro и хранение схемы

**Avro** отличается: схема хранится в JSON и обычно передаётся вместе с данными (или через реестр схем — Schema Registry). Сам формат — компактный: varint для чисел, зигзаг-кодирование для знаковых. Если у тебя есть схема, разбор тривиален; без неё — сложнее, но возможно по структуре.

## Шаг 4: эволюция схем

Сильная сторона Avro/Thrift — **эволюция схем**: поля можно добавлять и удалять, если соблюдать правила (в Avro — значения по умолчанию; в Thrift — опциональные поля). Ошибка в правилах ломает совместимость и открывает баги: например, поле с тем же ID, но другим типом, интерпретируется неверно. Это источник уязвимостей в распределённых системах.

## Шаг 5: сравнение с Protobuf

Protobuf, Thrift и Avro решают одну задачу, но по-разному. Protobuf и Thrift — теги и номера полей; Avro — схема и позиционная запись. Protobuf требует схему для чтения (но wire-формат самодостаточен); Avro без схемы почти нечитаем. Для атакующего важно: самодостаточные форматы (Protobuf/Thrift) разбираются «как есть», Avro — только со схемой.

## Шаг 6: разбор без схемы

Для Thrift без схемы: иди по полям, читай тип и ID, декодируй значение по типу. Структуры вложены, поэтому рекурсивный парсер — лучший инструмент. Для Avro: ищи схему рядом (файл `.avsc`, Schema Registry, HTTP-заголовок) — без неё придётся угадывать.

## Шаг 7: инструменты

- **Thrift**: `thrift` компилятор (для генерации), библиотеки `thrift` в Python/Java для чтения.
- **Avro**: `avro-tools`, `fastavro`, `avro` (Python).
- **Универсально**: `xxd`, `strings`, собственный парсер.

```
$ python3 -c "import fastavro; print(fastavro.reader(open('data.avro','rb')).schema)"
```

## Как защищаться

- **Валидировать схемы** и версии при эволюции.
- **Ограничивать размеры** полей (защита от переполнений).
- **Не доверять ID полей** при десериализации без проверки схемы.
- **Логировать** несовпадения версий схем.

## Что мы теперь знаем

- Avro и Thrift — IDL-форматы со схемой.
- Thrift binary protocol использует тип-теги и ID полей.
- Avro хранит схему в JSON (часто рядом с данными).
- Эволюция схем — источник багов при ошибках.
- Thrift читается без схемы, Avro — обычно нет.

## Avro: varint и зигзаг-кодирование

Avro кодирует целые компактно. Целые без знака — обычным **varint** (как в Protobuf). Знаковые — **зигзаг**-кодированием: число n отображается в `(n << 1) ^ (n >> 31)`, чтобы маленькие по модулю значения (в том числе отрицательные) занимали мало байт. Понимая это, ты читаешь числа Avro даже без схемы: varint даёт длину, зигзаг — знак. Для CTF это ключ к разбору «нечитаемых» чисел.

## Thrift: компактный протокол

У Thrift два бинарных протокола: **binary** (фиксированные размеры) и **compact** (varint и дельты). В compact ID полей кодируются дельтами, а числа — varint; это вдвое компактнее. При разборе определи протокол: binary проще, compact требует учёта дельт. Ошибка в выборе протокола даёт мусор вместо полей — типичная ловушка.

## Где искать схему

Для Avro схема почти всегда рядом: файл `.avsc`, заголовок контейнерного файла `.avro`, HTTP-эндпоинт Schema Registry. Для Thrift — `.thrift`-файл IDL в исходниках сервиса или в документации. Если схему нашёл — разбор тривиален; если нет — восстанавливай по структуре (типы и ID полей видны в Thrift).

## Рекурсивный парсер

Thrift-структуры вложены, поэтому парсер рекурсивный: читаешь тип, ID, значение; если тип — STRUCT, вызываешь себя. Это 40–60 строк на Python. Такой парсер полезен и для других тегированных форматов — принцип один: «тип → значение, вложенность через рекурсию».

## Уязвимости десериализации

Главная опасность IDL-форматов — доверие к данным. Если сервер принимает сериализованный объект и создаёт по нему классы, возможна десериализационная атака (особенно в Java Thrift). В Avro — риск в Schema Registry: подмена схемы меняет интерпретацию данных. Поэтому валидация схемы и типов — обязательна.

## Avro Schema Registry

В распределённых системах схема хранится централизованно (например, Confluent Schema Registry), а данные несут только её ID. Если атакующий может зарегистрировать свою схему или подменить ID, он меняет смысл данных для всех потребителей. Это class-уровень атаки, и защита — контроль доступа к реестру и версионирование.

## Thrift services и RPC

Thrift — не только сериализация, но и RPC: сервис описывает методы, клиент вызывает их. Данные идут теми же бинарными структурами. Для реверса важно: найдя `.thrift`, ты получаешь полное описание API — имена методов, аргументы, типы. Это карта сервиса без документации.

## Сравнительная таблица

Protobuf: теги, схема для смысла, wire самодостаточен. Thrift: теги, binary/compact, читается без схемы. Avro: схема обязательна, компактно, эволюция через defaults. Выбор формата влияет на то, насколько легко разобрать данные без исходников.

## Практический чеклист

Проверь: есть ли магия контейнера (`.avro` — `Obj\x01`); какие типы-теги у Thrift; есть ли схема рядом; какой протокол (binary/compact). Затем пиши/бери парсер и читай поля. Для CTF этого достаточно.

## Итог

Avro и Thrift — IDL-форматы со схемой. Thrift читается по тегам без схемы, Avro — со схемой. Оба компактны, оба требуют валидации при десериализации. Навык — распознать формат, найти схему и разобрать поля.

## Компактный протокол: детали дельт

В compact-протоколе Thrift ID поля кодируются не полностью, а дельтой к предыдущему. Это экономит байты, но усложняет разбор: нужно помнить последний ID. Плюс типы в compact заданы короткими кодами (не теми же, что в binary). Поэтому первое, что делают при разборе, — определяют протокол. Спутать binary и compact легко, а результат будет мусором.

## Чтение контейнерного .avro

Контейнерный файл Avro начинается с магии `Obj\x01`, затем метаданные (включая схему в JSON), затем блоки с данными. Это удобно: схема лежит внутри файла, и разбор не требует внешних данных. `fastavro.reader` читает такой файл и отдаёт словари; если библиотеки нет, схему можно извлечь вручную из заголовка.

## Практическая задача CTF

Типичная задача: дан бинарный файл, нужно найти строку с флагом. Решение: определить формат (магия/структура), разобрать поля, найти строковое поле с меткой. Thrift читается по тегам, Avro — по схеме. В обоих случаях помогает `strings` для быстрой зацепки и собственный парсер для точности.

## Сравнение с MessagePack

MessagePack — «JSON в бинарном виде», без схемы. Avro/Thrift — со схемой. Поэтому MessagePack читается почти сразу, а Avro/Thrift требуют схемы или реверса. Для атакующего самодостаточные форматы удобнее; для защищающегося — они же опаснее, потому что данные интерпретируются без явного описания.

## Итог урока

Avro и Thrift — IDL-форматы, распространённые в больших системах. Thrift binary/compact читается по тегам и ID; Avro требует схему (часто внутри `.avro`). Оба компактны, оба требуют валидации при десериализации. Навык — распознать формат и найти/восстановить схему.

## Финальная мысль

Avro и Thrift показывают, что «сериализация» — это не только формат, но и контракт между системами. Ломается контракт — ломается безопасность. Поэтому при разборе ищи не только данные, но и схему: она объясняет смысл полей и часто лежит рядом. Thrift отдаёт структуру без схемы, Avro требует её; в обоих случаях валидация — обязательна.
