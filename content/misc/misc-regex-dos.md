## Вопрос, с которого всё начинается

Ты пишешь маленькую регулярку для проверки email — и вдруг сервис, который её использует, намертво зависает на одном коротком запросе. Никакого огромного файла, никакой атаки «на миллион запросов» — просто одна строка из двадцати восьми символов. Как такое возможно?

Это **ReDoS** (Regular Expression Denial of Service) — отказ в обслуживании через «плохую» регулярку. В этом уроке мы возьмём одну такую регулярку, измерим, как её время растёт, и поймём, почему.

## Наш пример: регулярка, которая вешает сервис

Вот типичный валидатор, который «наивный программист» написал для проверки строки из букв `a`:

```python
import re
PAT = re.compile(r'(a+)+$')
def check(s):
    return bool(PAT.match(s))
```

На первый взгляд безобидно. Но попробуем подать на вход строку из нескольких `a`, за которыми идёт символ `!`, ломающий совпадение (`$` требует конца строки, а там `!`). Замерим время:

```python
import re, time
def timed(pat, s):
    p = re.compile(pat)
    t = time.perf_counter()
    p.match(s)
    return time.perf_counter() - t

for n in [18, 20, 22, 24]:
    print(n, round(timed(r'(a+)+$', 'a'*n + '!'), 4))
```

```
18 0.0099
20 0.0343
22 0.1372
24 0.5438
```

Смотри на числа: каждый раз, когда мы добавляем **два** символа, время растёт примерно **вчетверо**. Это экспоненциальный рост. При `n = 30` это уже миллиарды операций, а сервис, обрабатывающий запросы по одному потоку, встаёт.

## Шаг 1: почему это происходит — бэктрекинг

Классические движки регулярных выражений (Python `re`, PCRE, Java, JavaScript) работают методом **бэктрекинга** — «возврата с перебором». Когда шаблон не совпадает, движок пробует другой способ разбить строку и снова проверяет.

Возьмём `(a+)+$`. Внешний `+` говорит «одна или больше групп», а внутренний `a+` — «одна или больше букв `a`». Для строки `aaaa` движок может разбить её так: `[aaaa]`, `[aaa][a]`, `[aa][aa]`, `[a][aaa]`, `[a][a][aa]` и так далее. Число таких разбиений растёт экспоненциально с длиной. Когда совпадение в конце концов проваливается (из-за `!`), движок перебирает **все** варианты разбиения, прежде чем сдаться.

Ключ к пониманию: проблема не в самой строке, а в **неоднозначности** — один и тот же текст можно «собрать» из групп множеством способов.

## Шаг 2: как отличить ReDoS от просто медленной регулярки

ReDoS — это именно **экспоненциальный** бэктрекинг, а не «вообще медленно». Признак простой: время удваивается (или растёт в 3–4 раза) на каждый добавленный символ. Сравни с честной регуляркой на той же строке:

```python
import re, time
p = re.compile(r'a+$')
t = time.perf_counter()
p.match('a' * 100000 + '!')
print(round(time.perf_counter() - t, 6))
```

```
0.000473
```

Сто тысяч символов — и меньше миллисекунды. А «плохая» регулярка захлёбывается уже на 24. Разница не в длине входа, а в наличии перебора.

## Шаг 3: какие шаблоны опасны

Красный флаг — **квантификатор внутри квантифицированной группы**, где оба применяются к одному и тому же тексту:

- вложенные квантификаторы: `(a+)+`, `(a*)*`, `(.*)+`;
- альтернации с перекрытием: `(a|a)+`, `(a|ab)+`;
- повторяющаяся группа: `(\d+)+`.

В нашем email-валидаторе опасная часть — `([a-zA-Z0-9]+)+`: плюс внутри группы, которая сама под плюсом. Достаточно послать строку из повторов символа, который не даст совпадения в конце, — и сервис занят.

Возьмём конкретный пример. Пусть сервис проверяет email шаблоном `^([a-zA-Z0-9]+)+@[a-zA-Z0-9]+\.[a-z]+$`. Строка `'a'*30 + '!'` (тридцать букв `a` и восклицательный знак) не совпадёт ни при каком разбиении, но движок переберёт все способы сгруппировать тридцать `a`, прежде чем сдаться. Один такой запрос в поле ввода — и поток, обслуживающий запросы, занят на секунды. Если сервис однопоточный, он «лежит»; если многопоточный — достаточно нескольких запросов, чтобы исчерпать все потоки.

## Шаг 4: как эксплуатировать в CTF

В соревновательных задачах ReDoS подаётся двумя способами. Либо нужно «положить» сервис, послав сконструированную строку в поле, которое проверяется уязвимой регуляркой. Либо наоборот — задача содержит проверку, и её нужно обойти, поняв, что там катастрофический бэктрекинг, и подобрав вход, который формально «не проходит» шаблон, но обрабатывается мгновенно.

В обоих случаях ключ — точно понять, какой именно шаблон применяется к твоему вводу. Дальше ты управляешь длиной и составом строки: повторяющийся символ плюс «ломающий» символ в конце.

## Шаг 5: как защищаться

Стратегий три:

1. **Убрать вложенность.** `(a+)+$` → `a+$`; `(\d+)+` → `\d+`. Для email линейный `^[^@\s]+@[^@\s]+\.[^@\s]+$` достаточен и безопасен.
2. **Запретить откат.** Владеющие (possessive) квантификаторы (`a++`) и атомарные группы (`(?>...)`) в PCRE/Java фиксируют разбор и убирают перебор.
3. **Сменить движок на линейный.** Go `regexp` и Rust `regex` не используют бэктрекинг и гарантируют время, пропорциональное длине входа (ценой отказа от бэктреференций и части lookaround).

Дополнительно всегда ограничивай длину ввода до валидации и ставь таймаут на саму проверку — это последняя линия обороны.

Для аудита чужого кода есть инструменты: `regexploit` подбирает строку-триггер по шаблону, `recheck` проверяет безопасность бэктрекинга.

```
$ regexploit '(a+)+$'
```

Аудит начинается с поиска всех регулярок в коде и проверки их глазами на вложенные квантификаторы — плюс или звёздочка внутри группы, которая сама повторяется. Особенно опасны шаблоны, применяемые к пользовательскому вводу: полю формы, параметру URL, заголовку. Для каждого подозрительного шаблона запусти `regexploit`, который сам подберёт строку-триггер, или напиши простой бенчмарк, увеличивающий длину входа и замеряющий время.

Важно: проблема универсальна — движок JavaScript (V8) и Java `java.util.regex` тоже бэктрекинговые, поэтому ReDoS встречается и в вебе, и в мобильных приложениях. Обычное тестирование с типичным вводом ничего не покажет: нужно целенаправленно конструировать «плохие» строки из повторяющегося символа, за которым идёт символ, ломающий совпадение.

## Что мы теперь знаем

1. ReDoS — экспоненциальный бэктрекинг на специально подобранной строке.
2. Опасны вложенные квантификаторы и перекрывающиеся альтернации: `(a+)+`, `(a|a)+`.
3. Подтверждается замером: время растёт в разы на каждый добавленный символ.
4. Чинится переписыванием, владеющими квантификаторами или линейным движком.
5. Линейные движки (Go, Rust) к ReDoS не подвержены.

## На что смотреть дальше

- **Думать, что короткая строка безопасна.** Экспонента даёт эффект уже на 25–30 символах.
- **Тестировать без таймаута.** Можно повесить собственный терминал — оборачивай замер в `timeout`.
- **Путать с обычной медленной регуляркой.** ReDoS именно экспоненциальный, а не «вообще медленный».
- **Считать `+` в группе безобидным.** Опасна именно вложенность.
- **Игнорировать альтернации.** `(a|a)+` тоже экспоненциален.

## Полиномиальный ReDoS: менее очевидный случай

Не всякий ReDoS экспоненциален. Есть **полиномиальный** ReDoS — время растёт как `O(n²)` или `O(n³)`, и он встречается чаще, потому что его труднее заметить. Пример:

```python
PAT = re.compile(r'\s*,\s*')      # кажется безобидным
```

Проблема проявляется на строке из длинной последовательности пробелов без запятой: на каждой позиции движок заново «пробегает» все `\s*`, отсюда квадратичное время. На строке в 50 000 пробелов это уже секунды. Классические примеры полиномиального ReDoS — паттерны вида `(a|a)*`, `\s*,\s*`, `(.*a){n}`. Признак: время растёт в 4 раза при **удвоении** длины (а не в 2 раза на каждый символ).

Практический вывод: экспонента опаснее (эффект уже на 25 символах), но полиномиальный ReDoS легче проглядеть, потому что при обычных коротких входах он незаметен. Проверяйте оба класса.

## Фаззер: бинарный поиск длины триггера

Полезно уметь измерять ReDoS скриптом, а не на глаз. Найдём минимальную длину, при которой время превышает порог:

```python
import re, time

def time_for(pat, s, timeout=2.0):
    p = re.compile(pat)
    t = time.perf_counter()
    p.match(s)
    return time.perf_counter() - t

pat = r'(a+)+$'
lo, hi = 1, 40
while lo < hi:
    mid = (lo + hi) // 2
    dt = time_for(pat, 'a' * mid + '!')
    print(f"n={mid:3d}  {dt:.4f}s")
    if dt > 0.5:
        hi = mid
    else:
        lo = mid + 1
print("минимальная опасная длина:", lo)
```

Скрипт за логарифм шагов находит «точку перегиба». Тот же приём применяют при аудите: для каждой подозрительной регулярки измеряют рост времени и строят таблицу. Всегда оборачивайте запуск в `timeout` — иначе рискуете повесить свой терминал на экспоненциальном паттерне.

## ReDoS в разных движках: сравнительная таблица

| Движок | Алгоритм | ReDoS | Примечание |
|--------|----------|-------|------------|
| Python `re` | бэктрекинг | да | экспонента на `(a+)+` |
| PCRE / PHP | бэктрекинг | да | `pcre.backtrack_limit` даёт защиту |
| Java `java.util.regex` | бэктрекинг | да | встречается в Android-приложениях |
| JavaScript (V8) | бэктрекинг | да | DoS в Node.js-сервисах |
| .NET Regex | бэктрекинг | да | можно включить таймаут |
| Go `regexp` | автомат (RE2) | **нет** | линейное время |
| Rust `regex` | автомат (RE2) | **нет** | линейное время |
| RE2 / Hyperscan | автомат | **нет** | нет бэктреференций |

Ключевой вывод для выбора движка: если регулярка применяется к недоверенному вводу и может быть сложной — берите RE2-совместимый движок (Go, Rust, RE2). Если нужны бэктреференции или lookaround — оставайтесь на бэктрекинговом, но ограничивайте длину входа, ставьте таймаут и избегайте вложенных квантификаторов. Компромисс — владеющие квантификаторы и атомарные группы: они сохраняют выразительность PCRE, но убирают катастрофический откат.
