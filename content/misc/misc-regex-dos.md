## Что такое ReDoS

ReDoS (Regular Expression Denial of Service) — атака отказа в обслуживании через «плохую» регулярку. Некоторые шаблоны, особенно с вложенными квантификаторами, заставляют движок перебирать экспоненциальное число вариантов на специально подобранной строке. В результате сервис, проверяющий ввод регуляркой, зависает на одном запросе. В CTF это встречается как задача «сломай проверку» или «займи сервер», а в реальности — как уязвимость веб-приложений.

## Почему это работает: бэктрекинг

Классические движки regex (PCRE, Python `re`, Java, JavaScript) используют бэктрекинг. Для шаблона `(a+)+$` на строке из n символов `a`, за которыми нет совпадения, движок пробует все способы разбить последовательность `a` на группы — их число экспоненциально от n. При n=30 это миллиарды операций.

```python
import re, time
pat = re.compile(r'(a+)+$')
s = 'a'*28 + '!'
t = time.time()
pat.match(s)          # повиснет надолго
print(time.time() - t)
```

Здесь всего 28 символов, но вычисление занимает секунды и растёт экспоненциально.

## Какие шаблоны опасны

- Вложенные квантификаторы: `(a+)+`, `(a*)*`, `(.*)+`.
- Альтернации с перекрытием: `(a|a)+`, `(a|ab)+`.
- Повторяющаяся группа с квантификатором: `(\d+)+`.

Общее правило: **если внутри квантифицированной группы есть ещё один квантификатор, применяемый к тому же тексту — это красный флаг.**

## Демонстрация уязвимости

Пусть сервис валидирует email регуляркой:

```python
import re
EMAIL = re.compile(r'^([a-zA-Z0-9]+)+@[a-zA-Z0-9]+\.[a-z]+$')
def check(s):
    return bool(EMAIL.match(s))
```

Строка `'a'*30 + '!'` заставит `check` считать очень долго. Атакующий шлёт её в поле ввода и «кладет» сервер.

## Как измерить и подтвердить ReDoS

```python
import re, time
def timed(pat, s):
    p = re.compile(pat)
    t = time.perf_counter()
    try: p.match(s)
    except Exception: pass
    return time.perf_counter() - t

for n in range(20, 30):
    print(n, timed(r'(a+)+$', 'a'*n + '!'))
```

Время растёт примерно вдвое на каждый добавленный символ — верный признак экспоненциального бэктрекинга.

## Как защищаться: переписывание шаблона

Уберите вложенность:

```
Плохо:  (a+)+$
Хорошо: a+$
```

```
Плохо:  (\d+)+
Хорошо: \d+
```

Для email не переусложняйте: `^[^@\s]+@[^@\s]+\.[^@\s]+$` — линейный и достаточный для большинства задач.

## Другие приёмы защиты

- **Якоря** `^...$` и конкретные границы уменьшают пространство поиска.
- **Атомарные группы** `(?>...)` и possessive-квантификаторы `a++` (PCRE/Java) убирают бэктрекинг.
- **Таймаут на匹配** — оборачивайте проверку в ограничение по времени.
- **RE2/RE2-совместимые движки** (Go `regexp`, Rust `regex`) не подвержены ReDoS — они линейны по построению.
- **Ограничение длины ввода** до валидации.

## RE2 против PCRE

Ключевое отличие: RE2 (и Go `regexp`, Rust `regex`) гарантируют линейное время, потому что не используют бэктрекинг. Цена — нет бэктреференций и lookaround в полном объёме. Если вы пишете сервис и можете выбрать движок — выбирайте линейный.

## Поиск ReDoS в чужом коде

Что искать: `(X+)+`, `(X*)*`, `(X|Y)+` с перекрытием, вложенные повторы. Инструменты:

- **`redos` / `vuln-regex-detector`** — статический анализ.
- **`regexploit`** — генерирует строку-триггер из шаблона.
- **`recheck`** — проверка безопасного бэктрекинга.

```bash
pip install regexploit
regexploit '(a+)+$'
```

## ReDoS в JavaScript и Java

Проблема универсальна: JS-движок (V8) и Java `java.util.regex` тоже бэктрекинговые. В вебе ReDoS часто триггерится через поле формы, заголовок или параметр URL. В CTF-задачах «положи сервис» часто достаточно одной длинной строки.

## Типичные ошибки и подводные камни

- **Думать, что короткая строка безопасна** — экспонента даёт эффект уже при 25–30 символах.
- **Проверять на своей машине без таймаута** — рискуете повесить и свой терминал.
- **Путать с обычной медленной регуляркой** — ReDoS именно экспоненциальный.
- **Считать `+` в группе безобидным** — именно вложенность опасна.
- **Игнорировать альтернации** — `(a|a)+` тоже экспоненциален.

## Справочная таблица

| Плохой шаблон | Хороший | Причина |
|---------------|---------|---------|
| `(a+)+$` | `a+$` | вложенный `+` |
| `(a*)*b` | `a*b` | вложенный `*` |
| `(a\|aa)+` | `a+` | перекрытие альтернатив |
| `(\d+)+` | `\d+` | повтор группы цифр |
| `(.*)+(.)` | `.*.` | двойной wildcard |

## Что дальше / решение

Практический вывод: (1) в своём коде никогда не пишите вложенные квантификаторы и не валидируйте недоверенный ввод сложными шаблонами без ограничения длины; (2) предпочитайте линейные движки (RE2, Go/Rust regex); (3) для аудита используйте `regexploit`/`recheck`. В CTF ReDoS — это способ «занять» или «уронить» сервис одной строкой; в реальности — серьезная DoS-уязвимость, которую легко пропустить при код-ревью. Всегда спрашивайте себя: «может ли этот шаблон дать экспоненциальный бэктрекинг?»

## Как искать ReDoS в реальном коде

Аудит на ReDoS начинается с поиска подозрительных конструкций. Ищите в коде все регулярки и глазами проверяйте на вложенные квантификаторы: плюс или звёздочка внутри группы, которая сама повторяется. Особенно опасны шаблоны, применяемые к пользовательскому вводу — полю формы, параметру URL, заголовку. Дальше для каждого подозрительного шаблона запустите инструмент вроде `regexploit`, который сам подберёт строку-триггер, или напишите простой бенчмарк, увеличивающий длину входа и замеряющий время. Экспоненциальный рост времени на каждый добавленный символ — стопроцентное подтверждение уязвимости.

Важно понимать, что ReDoS — это не про «медленную регулярку» вообще, а именно про катастрофический бэктрекинг на специально подобранной строке. Поэтому обычное тестирование с типичным вводом ничего не покажет: нужно целенаправленно конструировать «плохие» строки, состоящие из повторяющегося символа, за которым следует символ, ломающий совпадение.

## Как чинить уязвимые шаблоны

Стратегий три. Первая — переписать шаблон без вложенности, заменив `(a+)+` на `a+`. Вторая — добавить владеющие (possessive) квантификаторы или атомарные группы, которые запрещают откат: в PCRE это `a++` и `(?>...)`. Третья — сменить движок на линейный: в Go и Rust стандартные движки регулярных выражений не используют бэктрекинг и гарантируют время, пропорциональное длине входа. Дополнительно всегда ограничивайте длину ввода до валидации и ставьте таймаут на саму проверку — это последняя линия обороны, если шаблон всё же оказался проблемным.

## ReDoS как элемент CTF-задачи

В соревновательных задачах ReDoS обычно подаётся двумя способами. Либо нужно «положить» сервис, послав специально сконструированную строку в поле, которое проверяется уязвимой регуляркой. Либо наоборот — задача содержит проверку, и её нужно обойти, поняв, что происходит катастрофический бэктрекинг, и подобрав вход, который формально «не проходит» шаблон, но обрабатывается мгновенно. В обоих случаях ключ — точно понять, какой именно шаблон применяется к вашему вводу, и затем управлять длиной и составом строки.

## Что дальше / решение

Резюмируем: ReDoS возникает из-за бэктрекинга на вложенных квантификаторах; обнаруживается статическим анализом (`regexploit`, `recheck`) и подтверждается замером экспоненциального роста времени; устраняется переписыванием шаблона, владеющими квантификаторами, линейным движком и ограничением длины входа. В своём коде считайте любую регулярку от недоверенного ввода потенциально опасной, пока не доказали обратное. В CTF используйте ReDoS как способ занять сервис или как подсказку к тому, как устроена проверка, которую требуется обойти.
