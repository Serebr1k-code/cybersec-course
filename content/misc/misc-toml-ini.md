## Вопрос, с которого всё начинается

Приложение читает `config.toml`. Ты можешь влиять на содержимое файла. Задача: заставить приложение увидеть настройку, которой ты не должен задавать, — или обмануть проверку. Как это сделать, если формат кажется простым?

Ответ: парсеры TOML и INI расходятся в деталях, и эти расхождения — уязвимость.

## Наш пример: конфиг с трюком

```
$ cat config.toml
[server]
port = 8080
debug = false

[server]
debug = true
```

Ключ `debug` задан дважды. Одни парсеры возьмут первое значение (`false`), другие — второе (`true`). Если защита проверяет одно, а исполнение использует другое — это обход.

## Шаг 1: что такое TOML

**TOML** (Tom's Obvious Minimal Language) — конфигурационный формат: пары `ключ = значение`, секции `[table]`, вложенные таблицы `[a.b]`, массивы `[[array]]`. Поддерживает строки, числа, булевы, даты, массивы.

```
[owner]
name = "Tom"
age = 42
active = true
born = 1979-05-27T07:32:00Z
```

## Шаг 2: что такое INI

**INI** — старший, менее строгий формат: секции `[section]`, пары `key=value`. Спецификации единой нет, поэтому каждый парсер трактует крайние случаи по-своему: пробелы, кавычки, комментарии (`;` или `#`), дубликаты.

## Шаг 3: дубликаты ключей

Главный источник расхождений — дубликаты. Одни парсеры берут **последнее** значение, другие **первое**, третьи — ошибка. Аналогично с дублирующимися секциями. Если разные компоненты приложения парсят файл по-разному, атакующий задаёт два значения и получает «split-brain»: проверка видит одно, логика — другое.

## Шаг 4: типы и подстановки

В TOML типы строгие: `"42"` — строка, `42` — число, `true` — булево. Но при конвертации в конфиг приложения тип может «поплыть»: строка `"true"` интерпретируется как истина. В INI все значения — строки, и приведение делает приложение. Отсюда баги: `debug = "false"` непустая строка → истина.

## Шаг 5: переменные окружения и подстановки

Некоторые библиотеки подставляют `${VAR}` в конфиг. Если значение контролируется пользователем, а подстановка выполняется — можно инъецировать переменную окружения или прочитать секрет. Это роднит TOML/INI с шаблонизаторами: данные становятся кодом.

## Шаг 6: парсер-диффы как метод

Общий приём: прогнать один и тот же файл через несколько парсеров и сравнить результат. Расхождения показывают места для атаки. Так находят баги в проверках безопасности: «парсер A говорит false, парсер B — true».

## Шаг 7: инструменты

- **TOML**: `toml` (Python), `tomlkit`, `taplo`.
- **INI**: `configparser` (Python), `inih`.
- **Сравнение**: скрипт, который парсит файл двумя библиотеками и диффит результат.

```
$ python3 - <<'PY'
import tomllib, tomlkit
d1 = tomllib.load(open('config.toml','rb'))
d2 = tomlkit.parse(open('config.toml').read())
print(d1['server']['debug'], d2['server']['debug'])
PY
False True
```

Разные парсеры — разные значения. Это и есть зацепка.

## Полный прогон

```
$ cat flag.toml
[flag]
value = "decoy"
[flag]
value = "nto{t0ml_dup_k3y}"
```

Второе значение — флаг; парсер, берущий последнее, покажет его.

## Как защищаться

- **Запрещать дубликаты** ключей/секций (строгий режим).
- **Использовать один парсер** во всех компонентах.
- **Не подставлять** пользовательские значения в конфиг.
- **Явно приводить типы**, не полагаясь на догадки.

## Что мы теперь знаем

- TOML строже INI, но оба имеют крайние случаи.
- Дубликаты ключей трактуются парсерами по-разному.
- Типы «плывут» при конвертации в настройки.
- Подстановки могут превратить данные в код.
- Парсер-диффы — метод поиска уязвимостей.

## TOML: таблицы и массивы таблиц

TOML поддерживает вложенные таблицы `[a.b.c]` и **массивы таблиц** `[[items]]`, которые дают список словарей. Это удобно, но порождает крайние случаи: порядок объявления, переопределение, конфликты ключей. Разные парсеры могут по-разному разрешать конфликт «таблица объявлена дважды». Для атаки это ещё один источник split-brain.

## TOML: даты и спецчисла

TOML нативно поддерживает даты (`1979-05-27`), время, `inf`, `nan`, шестнадцатеричные и подчёркивания в числах (`1_000`). Если приложение ожидает строку, а получает дату (или наоборот), приведение может дать неожиданный результат. Особенно опасны `inf`/`nan` в числовых настройках: они ломают сравнения.

## INI: комментарии и экранирование

В INI нет единого стандарта: комментарии бывают `;` или `#`, значения могут быть в кавычках или без, пробелы вокруг `=` трактуются по-разному. Атакующий использует это, чтобы «спрятать» строку от одного парсера и показать другому. Например, `key = value ;comment` — часть парсеров оставит комментарий в значении.

## Split-brain на практике

Сценарий: конфиг читают два компонента — сервис (проверка прав) и плагин (исполнение). Если дубликат ключа трактуется по-разному, сервис видит `admin=false`, а плагин — `admin=true`. Атакующий получает права. Именно так конфиг становится вектором привилегий.

## Config injection

Если пользовательский ввод вставляется в конфиг без экранирования, можно добавить секцию или ключ. Например, поле «имя» со значением `x\n[admin]\nenabled=true` создаёт новую секцию. Это та же логика, что SQL/JSON injection, только для конфигов.

## Подстановки и секреты

Некоторые библиотеки раскрывают `${ENV}` в значениях. Если значение контролируется пользователем, а подстановка включена, можно прочитать переменную окружения (секрет) или подставить её в опасное место. Проверяй, поддерживает ли парсер интерполяцию.

## Парсер-дифф на Python

Метод: одна и та же строка через `tomllib` и `tomlkit` (или `configparser` для INI) — сравнить результат. Расхождения сразу показывают уязвимые места. Это воспроизводимый тест, который можно встроить в аудит.

## Шпаргалка

TOML: `[table]`, `[[array]]`, `key = value`, типы строгие. INI: `[section]`, `key=value`, типы — строки. Опасности: дубликаты, конфликты таблиц, приведение типов, интерполяция, отсутствие экранирования. Инструменты: tomllib, tomlkit, configparser, taplo.

## Итог

TOML и INI кажутся простыми, но их крайние случаи создают уязвимости. Дубликаты ключей, конфликты таблиц, «плывущие» типы и подстановки — всё это источники обхода проверок. Метод защиты — строгий парсер и запрет дубликатов; метод атаки — парсер-дифф.

## TOML: inline-таблицы

Кроме секций, TOML поддерживает **inline-таблицы**: `point = { x = 1, y = 2 }`. Они компактны, но их взаимодействие с обычными секциями порождает крайние случаи: можно ли переопределить inline-таблицу секцией? Разные парсеры отвечают по-разному. В аудите это ещё одно место для split-brain.

## INI: секции и наследование

INI не поддерживает вложенность стандартно, но некоторые библиотеки добавляют «наследование» секций или подстановки `%(name)s`. Это расширения, и они различаются между реализациями. Если приложение полагается на такое расширение, а другой компонент использует строгий парсер, возникает расхождение.

## Безопасные значения по умолчанию

Правило конфигураций: значение по умолчанию должно быть **безопасным** (например, `debug = false`, `admin = false`). Тогда отсутствие ключа или ошибка парсинга не открывает дыру. Если по умолчанию `true` — любое расхождение играет на руку атакующему.

## Как писать безопасный парсер

Строгий парсер: запрещает дубликаты, отвергает неизвестные ключи (или явно их игнорирует), не выполняет подстановки, приводит типы явно, ограничивает размер. Такой парсер не даёт «двух истин» об одном файле. Для Python — `tomllib` (строгий) вместо снисходительных библиотек.

## Пример аудита

Проверь: какой парсер использует каждый компонент; есть ли дубликаты в примерах конфигов; включены ли подстановки; как приводятся типы; что происходит при неизвестном ключе. Каждый пункт — потенциальная находка. Часто уже одного «два компонента парсят по-разному» достаточно для отчёта.

## Итог урока

TOML и INI просты на вид, но полны крайних случаев: дубликаты, конфликты таблиц, inline-таблицы, расширения INI, «плывущие» типы и подстановки. Атака — найти расхождение парсеров или инъецировать структуру; защита — строгий парсер и безопасные значения по умолчанию.

## Практический сценарий CTF

В задаче даётся конфиг и описание сервиса. Нужно понять, какое значение «победит» при дубликате, или как инъецировать секцию через поле. Решение: прочитать файл двумя способами (строгий и снисходительный парсер), сравнить результат, найти расхождение. Часто флаг уже лежит во втором значении дубликата — его достаточно «увидеть» правильным парсером.

## Что тренирует эта тема

Разбор конфигов тренирует ключевой навык безопасности: **не доверять единственной интерпретации данных**. Если две системы читают один файл по-разному, между ними возникает щель. Эта мысль применима и к HTTP-парсерам, и к XML, и к JSON. TOML/INI — простой полигон для этой идеи.

## Частые находки в аудите

Три частые проблемы: дубликаты ключей без запрета; снисходительный парсер там, где нужен строгий; подстановка переменных окружения в пользовательские значения. Каждая ведёт к обходу проверок или утечке секрета. Исправления просты: строгий парсер, запрет дубликатов, отключение интерполяции.

## Итог

Конфиги — это код, влияющий на поведение. Их парсеры полны крайних случаев, а расхождения между парсерами — уязвимость. Разбирай файл несколькими парсерами, ищи split-brain, проверяй типы и подстановки. Тогда конфиг перестанет быть «просто настройками».

## Финальная проверка

Перед сдачей конфига спроси себя: запрещены ли дубликаты; используется ли один строгий парсер во всех компонентах; отключена ли интерполяция; заданы ли безопасные значения по умолчанию; ограничен ли размер файла. Если хотя бы один ответ «нет» — это потенциальная находка. Конфиг должен читаться однозначно, иначе он становится вектором атаки.

## Развёрнутый пример split-brain

Представь сервис, который читает `config.toml` дважды: при старте — для настройки логгера, и при каждом запросе — для проверки прав. Если первая библиотека берёт последнее значение дубликата, а вторая — первое, то логгер может считать `debug=false`, тогда как проверка прав увидит `debug=true` из первого вхождения. Атакующий, добавив дубликат, получает расхождение поведения без единого эксплойта памяти. Это ровно тот класс багов, который ищут в аудите конфигураций: не «поломка» парсера, а отсутствие единого источника истины для одного файла.
