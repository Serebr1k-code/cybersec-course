## Вопрос, с которого всё начинается

Cosmos-контракты — это не Solidity и не Cairo, а WASM-модуль, загруженный в блокчейн. У него три точки входа: `instantiate`, `execute`, `query`. Кажется, что песочница WASM защищает сама по себе. Но большинство эксплойтов CosmWasm — логические: неверная проверка отправителя, необработанный reply, подделка межцепочечного сообщения.

## Наш пример: контракт-казначейство

```rust
#[entry_point]
pub fn execute(deps: DepsMut, env: Env, info: MessageInfo, msg: ExecuteMsg) -> StdResult<Response> {
    match msg {
        ExecuteMsg::Withdraw { amount } => withdraw(deps, env, info, amount),
        ExecuteMsg::SetAdmin { new_admin } => set_admin(deps, info, new_admin),
    }
}

fn withdraw(deps: DepsMut, env: Env, info: MessageInfo, amount: Uint128) -> StdResult<Response> {
    let balance = deps.querier.query_balance(env.contract.address, "uatom")?;
    if amount > balance.amount { return Err(StdError::generic_err("insufficient")); }
    Ok(Response::new().add_message(BankMsg::Send {
        to_address: info.sender.to_string(),
        amount: vec![Coin { denom: "uatom".into(), amount }],
    }))
}
```

Разберём, где здесь дыра, и почему WASM тут ни при чём.

## Шаг 1: отправитель и подделка

`info.sender` — это адрес, вызвавший контракт. В Cosmos транзакции подписываются, и `sender` подделать нельзя. Но многие контракты проверяют не `info.sender`, а поле **внутри сообщения**:

```rust
ExecuteMsg::SetAdmin { new_admin } => { ... }
```

Если `new_admin` приходит в данных и не сверяется с `info.sender`, любой может назначить себя админом. Правило: **никогда не доверяйте адресам из тела сообщения**, если их можно проверить через `info.sender`.

## Шаг 2: query_balance и его ловушки

`query_balance` обращается к банковскому модулю. Ошибка — полагаться на него для проверки средств в том же блоке: между `query` и `Send` состояние может измениться (например, через другой вызов). Это разновидность TOCTOU. Надёжнее отслеживать баланс в собственном хранилище.

```rust
// плохо: проверка по внешнему состоянию
let bal = deps.querier.query_balance(env.contract.address, "uatom")?;
if amount > bal.amount { ... }
```

## Шаг 3: IBC и межцепочечные сообщения

CosmWasm силён в interchain-связях. Контракт может отправить IBC-пакет и получить `acknowledgement`. Классический баг — **не проверять канал/порт** отправителя ack:

```rust
if info.sender != env.contract.address { return Err(...); }  // ОК
// но что если ack приходит по чужому каналу?
```

Если контракт обрабатывает ack без проверки `msg.channel_id` и порта, атакующий может сфабриковать подтверждение и заставить контракт выдать средства. Всегда сверяйте `channel_id`, `port_id` и счётчик последовательности (`sequence`).

## Шаг 4: reply и submessage

`SubMsg` позволяет контракту вызвать другой контракт и обработать результат в `reply`. Ошибка — не проверять `msg.id` в `reply`: если контракт ожидает ответ на одно сообщение, а приходит ответ на другое, логика ломается. `reply` обязан различать `id`.

```rust
#[entry_point]
pub fn reply(deps: DepsMut, env: Env, msg: Reply) -> StdResult<Response> {
    match msg.id {
        1 => handle_swap_ack(deps, env, msg),
        2 => handle_transfer_ack(deps, env, msg),
        _ => Err(StdError::generic_err("unknown id")),
    }
}
```

## Шаг 5: instantiate и повторная инициализация

В CosmWasm `instantiate` вызывается один раз при создании контракта. Если разработчик добавил публичную `MigrateMsg`-функцию, которая снова пишет админа без проверки, появляется окно для захвата. Проверяйте, что миграция доступна только авторизованному адресу.

## Шаг 6: где искать баги

| Место | Что искать |
|---|---|
| адреса из тела msg | сверяются ли с `info.sender` |
| `query_balance` | не полагаться для проверок |
| IBC ack | проверены ли port/channel/sequence |
| `reply` | проверяется ли `id` |
| `instantiate`/`migrate` | можно ли переинициализировать |
| funds | проверяются ли присланные монеты |

## Полный прогон: подделка админа

Задача: контракт хранит админа и позволяет менять его через `SetAdmin { new_admin }` без сверки с `info.sender`. Атакующий вызывает `SetAdmin` и становится владельцем.

```
$ wasmd tx wasm execute $CONTRACT '{"set_admin":{"new_admin":"cosmos1attacker"}}' --from attacker
# контракт принял нового админа от кого угодно
flag: nto{c0smw4sm_1bc_4ck_c0nfus10n}
```

WASM-песочница изолировала память, но не логику. Как и везде, эксплойт — в пропущенной проверке.

## Если не сработало

Если контракт проверяет `info.sender`, ищите другие пути: `reply` без проверки `id`, ack по чужому каналу, миграцию без авторизации. Логические дыры в CosmWasm почти всегда лежат на «периферии» — в обработчиках ответов, а не в основной логике.

## Что мы теперь знаем

- CosmWasm-контракт — WASM-модуль с тремя точками входа.
- `info.sender` — единственный достоверный источник отправителя.
- `query_balance` не годится как атомарная проверка.
- IBC-подтверждения нужно сверять по порту, каналу и sequence.
- `reply` обязан различать `id`.

## Как читать CosmWasm-контракт

Смотрите на три вещи: откуда берётся отправитель, что приходит в теле сообщения и как обрабатываются ответы. Почти все реальные инциденты CosmWasm — на пересечении этих трёх.

## Сравнение с EVM: песочница и её границы

CosmWasm исполняет контракт как WASM-модуль в изолированной среде. Это даёт то, чего нет в EVM: контракт не может обратиться к произвольной памяти узла, не может выполнить системный вызов, не может выйти за пределы предоставленного API. Ошибки времени исполнения (переполнение буфера, use-after-free) в CosmWasm практически невозможны — их ловит WASM-валидатор.

Но безопасность CosmWasm — это безопасность **API**, а не памяти. Контракт получает ограниченный набор возможностей: читать/писать своё хранилище, отправлять банковские сообщения, вызывать другие контракты, работать с IBC. Все баги — в том, как контракт пользуется этими возможностями. Отсюда правило: читая CosmWasm-контракт, смотрите не на Rust-код как таковой, а на то, какие сообщения он отправляет и на основании каких данных.

## Разбор второго примера: IBC-приём

```rust
#[entry_point]
pub fn ibc_packet_ack(
    deps: DepsMut,
    env: Env,
    ack: IbcPacketAckMsg,
) -> StdResult<Response> {
    // ОПАСНО: не проверяем channel_id/port/sequence
    let parsed: AckResult = from_json(&ack.acknowledgement.data)?;
    if parsed.success {
        release_funds(deps, ack.original_packet.data)?;
    }
    Ok(Response::new())
}
```

Если контракт принимает ack без проверки канала, атакующий, контролирующий другой канал, может отправить поддельный ack с `success: true` и заставить контракт выдать средства. Правильная версия сверяет `ack.original_packet.src.channel_id` и порт с ожидаемыми и проверяет, что `sequence` совпадает с сохранённым в состоянии.

## Частые вопросы новичков

Почему `info.sender` нельзя подделать? Потому что он берётся из подписанной транзакции: узел проверяет подпись до вызова контракта, и контракт получает уже проверенное значение. Почему `query_balance` «не атомарен»? Потому что между запросом и следующим действием в той же транзакции может выполниться другой вызов, изменивший баланс; в Cosmos это реже, чем в EVM, но принцип тот же. Что такое `SubMsg`? Это сообщение, которое контракт отправляет другому контракту и на которое позже получит `Reply`; `id` в `Reply` позволяет понять, на что именно пришёл ответ.

## Практика без лаборатории

Разверните `cw-multi-test` и напишите тест: контракт хранит админа, а `SetAdmin` не сверяет `info.sender`. Вызовите `SetAdmin` от имени «атакующего» и проверьте, что админ изменился. Затем добавьте проверку `if info.sender != ADMIN { return Err(...) }` и убедитесь, что тест падает. Это ровно тот баг, который чаще всего встречается в реальных аудитах CosmWasm.

## Разбор ошибок из реальных аудитов

CosmWasm-аудиты регулярно находят одни и те же вещи. Первое — доверие адресу из тела сообщения: контракт принимает `new_admin` или `recipient` и не сверяет с `info.sender`. Второе — отсутствие проверки `channel_id`/`port_id` в IBC-обработчиках: поддельное подтверждение проходит. Третье — `reply` без разбора `id`: ответ на одно сообщение обрабатывается как ответ на другое. Четвёртое — миграция без авторизации: `MigrateMsg` может переписать админа. Пятое — использование `query_balance` для атомарных проверок. Все пять — логические, и все ловятся внимательным чтением обработчиков, а не статическим анализатором памяти. Поэтому в аудите CosmWasm главный инструмент — grep по `info.sender`, `Reply`, `IbcPacketAckMsg` и `query_balance`, а затем ручная проверка каждого совпадения.

## Разбор контракта по шагам

Вот компактный чек-лист, которым удобно идти по исходнику CosmWasm. Шаг первый: найдите все точки входа (`instantiate`, `execute`, `query`, `reply`, `migrate`, IBC-хендлеры) и выпишите их. Шаг второй: в каждой точке входа найдите, откуда берётся «личность» вызывающего — только `info.sender` считается достоверным. Шаг третий: выпишите все адреса, приходящие в теле `ExecuteMsg`, и проверьте, что каждый либо сверяется с `info.sender`, либо является публичным по замыслу. Шаг четвёртый: в IBC-хендлерах сверьте `channel_id`, `port_id` и `sequence` с сохранёнными значениями. Шаг пятый: в `reply` проверьте разбор `msg.id`. Шаг шестой: убедитесь, что `migrate` авторизован. Если все шесть шагов чисты — контракт, скорее всего, безопасен по логике доступа. Этот чек-лист родился из реальных инцидентов и покрывает большинство найденных уязвимостей.

## Почему это важно именно для interchain

Cosmos — это сеть сетей, и контракт здесь редко живёт в изоляции: он общается с другими цепочками через IBC. Каждое такое сообщение — это ещё один вход, который нужно валидировать так же строго, как обычный `ExecuteMsg`. Атакующий, контролирующий одну цепочку, может попытаться отправить контракту на другой цепочке сообщение, выглядящее легитимным. Именно поэтому проверка `channel_id`, `port_id` и `sequence` — не формальность, а обязательное условие безопасности любого interchain-контракта.
