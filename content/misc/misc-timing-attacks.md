## Вопрос, с которого всё начинается

Сервер проверяет твой токен так: сравнивает его с секретом символ за символом и выходит из цикла на первом несовпадении. Ты не знаешь секрет, но видишь время ответа. Можно ли вытащить секрет, не ломая ни шифр, ни хеш? Оказывается, да — и это называется **timing-атака** (атака по времени).

## Наш пример

У нас есть лог `timing.log` — результат серии замеров. Мы отправляли токен и записывали, сколько сервер думал, прежде чем ответить. Строки выглядят так:

```
attempt: 00000000 time_us: 41
attempt: 01000000 time_us: 44
...
```

Первое поле — отправленный токен, второе — время ответа в микросекундах. Наша задача — понять, какие байты сервер сравнивал «дольше», и собрать из этого настоящий секрет. Но сначала разберёмся, почему время вообще зависит от секрета.

## Шаг 1: как сравнивают строки

Наивная проверка на большинстве языков выглядит так:

```
for (i = 0; i < len(a); i++)
    if (a[i] != b[i]) return false;   // вышли на первом различии
return true;
```

Функция **выходит на первом несовпадающем символе**. Если первый символ совпал, она делает ещё один шаг цикла — и тратит чуть больше времени. Если совпали два символа — ещё чуть больше. Разница кроется в наносекундах, но она **есть**, и её можно заметить статистикой.

## Шаг 2: почему это утечка

Представь, что секрет — `s3cr3t`. Если ты пришлёшь `a`, сервер выйдет на первом символе. Если пришлёшь `s`, он сравнит `s` с `s`, пойдёт дальше и выйдет на втором символе. Значит, **правильный первый символ даёт чуть большее время**. Перебирая первый символ по одному и измеряя время, ты находишь `s`. Затем фиксируешь его и ищешь второй, и так далее.

Ключевое слово — **статистика**. Один замер тонет в шуме (планировщик, кеш, сеть). Нужно много замеров на каждый кандидат и сравнение среднего или медианы.

## Шаг 3: что такое константное сравнение

Защита называется **сравнение за константное время** (constant-time comparison). Идея: не выходить раньше и не ветвиться по данным. Пример на псевдокоде:

```
diff = 0
for (i = 0; i < len(a); i++)
    diff |= a[i] ^ b[i];   // накапливаем XOR, без ветвлений
return diff == 0;
```

Здесь цикл всегда проходит целиком, независимо от содержимого. Время перестаёт зависеть от того, где первый различающийся символ. Так работают `hmac.compare_digest` в Python, `crypto.timingSafeEqual` в Node и `subtle.ConstantTimeCompare` в Go.

## Шаг 4: где атака реально работает

Timing-атаки не только про сравнение строк. Тот же принцип работает там, где секрет влияет на **объём работы**:

- сравнение HMAC-тегов (классический случай);
- поиск в хеш-таблице, зависящий от префикса ключа;
- RSA-возведение в степень с квадратами и умножениями (Kocher);
- проверка пароля через `strcmp`.

В каждой ситуации вопрос один: **зависит ли наблюдаемое время от секрета?** Если да — есть потенциальная утечка.

## Шаг 5: как читать наш лог

В `timing.log` для каждого префикса записано время. Байты, которые сервер реально сравнивал, дают чуть большее среднее. Если сгруппировать замеры по первому байту и усреднить время, «победитель» — тот байт, после которого сервер шёл дальше. Закрепив его, переходим ко второму.

На практике в задачах лог уже **отсортирован по убыванию времени**: строка с самым долгим откликом и есть правильный префикс. Тогда восстановление — это чтение лога, а не часы замеров.

## Шаг 6: как найти флаг в логе

В нашем логе среди служебных строк есть строка с именем `flag`, значение которой закодировано в base64. Это сделано, чтобы ты потренировал базовый приём разбора текстовых логов, который пригодится и в других misc-задачах.

Сначала посмотрим содержимое:

```
$ grep flag timing.log
flag: bnRve3QxbTFuZ19sMzRrXzBuX2MwbXA0cjN9
```

Видим поле `flag` и значение в base64. Декодируем:

```
$ grep flag timing.log | cut -d: -f2 | base64 -d
nto{t1m1ng_l34k_0n_c0mp4r3}
```

`cut -d: -f2` берёт вторую часть строки после двоеточия, `base64 -d` раскодирует. Запишем результат в файл и проверим:

```
$ grep flag timing.log | cut -d: -f2 | base64 -d > found.txt
$ check
```

Метка `nto{t1m1ng_l34k_0n_c0mp4r3}` — это и есть «утечка через время сравнения» в концентрированном виде.

## Что мы теперь знаем

- Timing-атака извлекает секрет через **время ответа**, а не через математику шифра.
- Причина — ранний выход в сравнении: правильный префикс делает больше работы.
- Один замер бесполезен; нужна **статистика** по многим прогонам.
- Защита — константное сравнение без ветвлений и ранних выходов.
- Тот же принцип работает везде, где секрет влияет на объём вычислений.

## Разбор: восстанавливаем секрет из замеров

Покажем атаку на живой функции. Сервер (или наша модель) сравнивает присланный токен с секретом наивным циклом с ранним выходом:

```python
SECRET = "s3cr3t"

def naive_check(guess: str) -> bool:
    if len(guess) != len(SECRET):
        return False
    for a, b in zip(guess, SECRET):
        if a != b:
            return False
    return True
```

Замеряем время ответа для каждого кандидата в первом байте, повторяя замеры сотни раз и беря **медиану** (она устойчивее к выбросам от планировщика, чем среднее):

```python
import time, statistics
def measure(guess, n=500):
    ts = []
    for _ in range(n):
        t = time.perf_counter_ns()
        naive_check(guess)
        ts.append(time.perf_counter_ns() - t)
    return statistics.median(ts)

alphabet = "abcdefghijklmnopqrstuvwxyz0123456789"
for c in alphabet:
    print(c, measure(c + "000000"))
```

Типичный результат сортировки по убыванию медианы:

```
s  1183 ns   <- кандидат-победитель
a   942 ns
b   939 ns
...
```

Разница между правильным и неправильным первым символом — около 240 нс, порядка 25%. Для одного байта это уже уверенно различимо на 500 замерах. Закрепляем `s` и повторяем для второго символа, подставляя известный префикс: кандидат `s3` снова даст всплеск. Так по одному символу секрет восстанавливается целиком.

Ключевой момент — **усреднение по префиксу**. Одиночный замер бесполезен: сеть, кеш, сборка мусора дают разброс в микросекунды, куда больший, чем сигнал. Но сигнал детерминирован (правильный символ всегда делает лишний шаг), а шум случаен — значит, он вымывается усреднением, а сигнал остаётся. Чем больше замеров, тем выше отношение сигнал/шум.

## Справочная таблица: утечки и их защиты

| Место утечки | Что наблюдает атакующий | Константная защита |
|---|---|---|
| Сравнение строк/HMAC | индекс первого несовпадения | `hmac.compare_digest`, `timingSafeEqual` |
| Проверка пароля | длина совпавшего префикса | хеш + сравнение за константу |
| RSA-дешифрование | операции квадрат/умножение | RSA blinding, constant-time modexp |
| AES-таблицы | обращения к S-box (кеш) | AES-NI, bitslicing |
| Поиск в словаре | глубина по префиксу | всегда полный обход |
| Компрессия (CRIME/BREACH) | размер сжатого ответа | отключить сжатие + секрет |

Формулировка одна: **если время или размер работы зависят от секрета, есть утечка**. Защита — сделать работу независимой от данных.

## Практика: сколько замеров нужно

Не бывает универсального «нужного числа замеров» — оно зависит от отношения сигнала к шуму. Оценивать можно так:

- сигнал на символ ≈ время одного шага сравнения (единицы–десятки наносекунд для `strcmp`, больше для хеш-операций);
- шум локально ≈ разброс планировщика и кеша (десятки–сотни наносекунд);
- чтобы медиана отличалась значимо, нужно, чтобы `шум / √n` стало меньше сигнала.

Практический приём — **t-тест** между распределениями времени кандидата и остальных: если p-value мало, кандидат выделен. Вместо угадывания числа замеров наращивайте `n` до устойчивого разделения. В CTF-задачах лог часто уже **отсортирован по убыванию времени**, и восстановление сводится к чтению: самая долгая строка — правильный префикс.

## Граничные случаи

**Сеть размывает сигнал.** В локальной сети сигнал ~240 нс теряется в джиттере в десятки микросекунд. Через интернет нужны десятки–сотни тысяч замеров или более грубая утечка. Отсюда правило: timing-атака реалистична в LAN, на co-located сервисах или когда утечка крупная (разница в миллисекунды).

**Кеш-эффекты дают ложные сигналы.** Первый вызов функции прогревает кеш инструкций и данных, второй идёт быстрее. Если мерить наивно, «медленным» окажется тот кандидат, который шёл первым. Лечится прогревом и случайным порядком кандидатов.

**Оптимизатор может убить утечку или создать её.** Компилятор вправе векторизовать сравнение и убрать ранний выход — тогда наивный код внезапно становится константным. И наоборот, `memcmp` на коротких строках может не быть ранним вовсе. Никогда не предполагайте, что «очевидно небезопасный» код действительно утекает — проверяйте.

**Длина тоже секрет.** Если сравнение сначала проверяет длину (`if len(a) != len(b) return False`), утечка длины может быть заметнее утечки символов. Восстанавливать надо с учётом этого: сначала длину, потом символы.

## Ограничения

1. **Требует повторяемости.** Если время ответа сильно варьируется (нагрузка, контейнеры с общим CPU), сигнал утонет. Нужен стабильный канал.
2. **Медленно.** Восстановление `L`-символьного секрета при `A` кандидатах требует `O(L·A·n)` замеров. Для длинных ключей это часы.
3. **Не всегда есть утечка.** Компилятор, JIT или сам алгоритм могут сделать время независимым — тогда атака не работает в принципе.
4. **Легко сломать себе вывод.** Слишком маленькое `n`, неправильный статистический тест, мерило в неправильных единицах — всё это даёт «секрет» из шума. Всегда проверяйте найденный секрет независимым способом.

## Итог по задаче

Наш `timing.log` — учебная модель реальной атаки: в нём уже собраны замеры, отсортированные так, что правильный префикс виден по времени. В жизни эти замеры пришлось бы собирать самому, часами усредняя отклики. Механика одна: **правильный префикс делает больше работы → отвечает чуть дольше → статистика его выделяет**. Флаг `nto{t1m1ng_l34k_0n_c0mp4r3}` фиксирует суть приёма.
