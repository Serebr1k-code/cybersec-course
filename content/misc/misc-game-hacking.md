## Вопрос, с которого всё начинается

Тебе дали учебный бинарь-игру. Внутри — счётчик здоровья и «золото», а флаг показывается только при определённом состоянии. Читать исходники негде — есть только запущенный процесс. Как найти в чужой памяти число «здоровье», изменить его и заставить игру показать флаг? Это и есть **game hacking** — работа с памятью и процессами в реальном времени. Навыки те же, что нужны для malware analysis и реверса.

## Наш пример: игра с health и золотом

Запускаем `game` и видим на экране `HP: 100`, `Gold: 50`. Ставим цель: сделать HP бесконечным, а золота — сколько нужно для флага. Дальше работаем через Cheat Engine (CE) — программу, которая умеет искать значения в памяти другого процесса и перезаписывать их.

## Как устроена память процесса

Каждый процесс получает собственное **виртуальное адресное пространство**. Переменные игры лежат в двух местах: **static/data** (глобальные, адрес стабилен от запуска к запуску) и **heap** (динамические объекты, адрес каждый раз новый). Из-за **ASLR** (рандомизации адресов при загрузке) и динамической аллокации просто «запомнить адрес» не выйдет.

Три понятия, которые надо держать в голове:

- **Модуль** — загруженный файл (`game.exe`) или библиотека (`.dll`), у них есть базовый адрес. Адрес внутри модуля записывают как `game.exe+0x1234`.
- **Offset** — смещение внутри модуля или структуры.
- **Pointer chain** (цепочка указателей) — путь «статический указатель → … → целевое значение», устойчивый к перезапуску.

## Cheat Engine: скан значения по шагам

Приаттачиваемся к процессу (`Open Process` → выбрать `game`) и ищем здоровье по точному значению:

```text
First Scan: value = 100   → 1 200 000 hits
(в игре получаем урон, HP = 73)
Next Scan:  value = 73    → 3 hits
(ещё урон, HP = 61)
Next Scan:  value = 61    → 1 hit   ← наш адрес
```

Логика проста: каждое сканирование сужает множество адресов, оставляя те, где лежит именно наше число. Когда остался один адрес — можно перезаписать его в таблице на `9999`. Для координат, которые всегда дробные, выбирают тип `Float`/`Double`; если число неизвестно (например, зашифровано), берут `Unknown initial value` + `Increased/Decreased value`.

## Pointer chain: почему адрес «плывёт»

Адрес найден, но после перезапуска он другой — значит, переменная на куче. Делаем `Pointer scan for this address`, перезапускаем игру, находим новый адрес и жмём `Rescan memory`: CE оставит только цепочки, валидные в обоих запусках:

```
"game.exe"+0x00A1B2C0 → 0x14 → 0x2C → 0x8   (health)
```

Читается это так: от статической базы модуля `game.exe` плюс смещение `0xA1B2C0` берём указатель, к нему прибавляем `0x14`, читаем следующий указатель, к нему `0x2C`, ещё один, и уже с `+0x8` лежит здоровье. Цепочка — это «якорь», который не меняется между запусками, в отличие от сырого адреса.

## Патчим инструкцию, а не данные

Иногда проще не менять значение, а исправить **инструкцию**, которая его портит. В `Memory View` → дизассемблер наводим на `sub eax, ebx` (это вычитание урона) и через `Assemble` (Ctrl+A) заменяем на два `nop` — урон перестаёт наноситься:

```bash
# найти байты инструкции в файле
$ xxd game.exe | grep "29 d8"     # 29 d8 = sub eax, ebx
# заменить на 90 90 (две NOP)
```

Такой патч живёт, пока не сработает проверка целостности кода (CRC) — тогда патч в файле заменит игру и её «увидят». Поэтому для анти-читов чаще правят данные, а не код.

## Сохранения: XOR-обфускация

Флаг может быть в сохранении, а не в памяти. Формат часто простой — XOR по одному байту. Смотрим на файл и проверяем гипотезу перебором ключа:

```bash
$ file save.dat
save.dat: data
$ xxd save.dat | head -1
00000000: 9a3f 0c7e ...
```

```python
data = open('save.dat','rb').read()
for k in range(256):
    dec = bytes(b ^ k for b in data)
    if b'gold' in dec or b'level' in dec:
        print(k, dec[:64])
```

Как только ключ найден, видим осмысленный JSON или ZIP, правим значения (золото, уровень) и пишем файл обратно, зашифровав тем же ключом. Если сохранение заканчивается контрольной суммой — её придётся пересчитать, иначе игра отвергнет файл.

## Программный трейнер и DLL-инъекция

Чтобы менять значения кодом, а не руками, пишут трейнер: скрипт открывает процесс и разыменовывает цепочку. На Python это `ctypes` (`OpenProcess`, `ReadProcessMemory`, `WriteProcessMemory`), на C++ — внедрение DLL и **hook** (перехват) функций:

```cpp
MH_CreateHook(pTarget, &hkFunction, (LPVOID*)&origFunction);
MH_EnableHook(pTarget);
```

Популярен и **DLL sideloading**: игра грузит `foo.dll` из своей папки — подкладываем туда свою библиотеку. Те же техники применяются в malware analysis для перехвата вызовов.

## Анти-читы и как их обходят (в учебных целях)

Анти-чит может сканировать память на известные сигнатуры, проверять CRC кода, ловить дебаггер и открытые хэндлы. Простейшие приёмы: скрыть дебаггер (`ScyllaHide`, сброс флага `PEB->BeingDebugged`), менять данные вместо кода (меньше сигнатур), работать внешним аппаратным DMA-ридером. В CTF обходят только **учебные** анти-читы; обход коммерческих нарушает EULA и часто закон.

## Если скан не находит значение

Начинающих обычно останавливают три вещи. Первая — **не тот тип**: искали `int32`, а здоровье хранится как `float`; тогда перезапусти скан с другим типом. Вторая — значение **зашифровано** (частая защита): в памяти лежит не `100`, а `100 ^ key`; в этом случае помогает `Unknown initial value` и серия `Changed/Unchanged` — меняем значение в игре и смотрим, какие адреса отреагировали. Третья — **не тот процесс или разрядность**: 64-битный сканер не увидит 32-битный процесс и наоборот. И ещё: если после патча игра крашится — ты испортил критичную инструкцию, верни исходные байты из бэкапа файла. Отдельно проверь, не смотрит ли игра на **зашифрованные** значения: тогда `Exact Value` не найдёт ничего, и нужно идти через `Unknown initial value`, меняя значение в игре и отслеживая `Changed`.

## Что мы теперь знаем

- Значение в памяти ищут **многократным сканом** по изменению в игре.
- Адрес на куче «плывёт» — нужен **pointer chain** от базы модуля.
- Иногда чинят не данные, а **инструкцию** (патч `sub` → `nop`).
- Сохранения часто **XOR-обфусцированы**; ключ находится перебором одного байта.
- Анти-чит ловит патчи кода — безопаснее править данные.

## Как переменные игры лежат рядом: структура игрока

Найденное здоровье редко стоит в памяти в одиночку. Обычно это поле **структуры**
игрока, где рядом лежат другие поля: золото, уровень, координаты. Поняв структуру,
вы одним изменением получаете всё сразу. Посмотрим на найденный адрес в CE
(`Browse this memory region`) и увидим примерно такую картину:

```text
+0x00  int32   health   = 100
+0x04  int32   gold     = 50
+0x08  int32   level    = 3
+0x0C  float   pos_x    = 12.5
+0x10  float   pos_y    = -3.25
+0x14  int32   flags    = 0
```

Поля выровнены по 4 байта (для `int32`/`float`), поэтому соседи предсказуемы. Если
вы поменяете `health`, а игра покажет, что изменилось и `gold`, — значит, вы попали
в структуру, а не в одиночную переменную. Дальше можно не искать «золото» отдельно:
оно уже рядом, на смещении `+0x04`.

Осторожно с **выравниванием** (padding): 64-битные указатели внутри структуры
заставляют компилятор вставлять пустые байты, и смещения могут идти не подряд.
Если поле «не там, где ждали», — посмотрите дамп в `xxd`-подобном виде и найдите
границы по осмысленным значениям.

## Полный трейнер на Python

Соберём минимальный внешний трейнер, который сам разыменовывает pointer chain и
пишет значение. Здесь нет инъекции — только чтение/запись памяти, поэтому такой
скрипт не ловится проверками целостности кода.

```python
import ctypes as C
k32 = C.windll.kernel32

PROCESS_ALL = 0x1F0FFF
pid = 1234
h = k32.OpenProcess(PROCESS_ALL, False, pid)
base = 0x00400000                       # база модуля (из CE)

# game.exe+0xA1B2C0 -> +0x14 -> +0x2C -> +0x8 (health)
def rd(addr, size=4):
    buf = C.c_uint32()
    k32.ReadProcessMemory(h, C.c_void_p(addr), C.byref(buf), size, None)
    return buf.value

def wr(addr, val):
    k32.WriteProcessMemory(h, C.c_void_p(addr), C.byref(C.c_uint32(val)), 4, None)

p = rd(base + 0xA1B2C0, 8)
p = rd(p + 0x14, 8)
p = rd(p + 0x2C, 8)
wr(p + 0x8, 9999)                       # health = 9999
```

Логика ровно та же, что в CE: пройти по цепочке от статической базы и записать
значение по конечному адресу. Разница лишь в том, что это автоматизируется.

## Почему находят по «изменению», а не по значению

Скан по точному значению ломается, когда число зашифровано, дробное или совпадает
у десятков объектов. Тогда работает **delta scan**: CE запоминает все адреса с
некоторым значением, вы меняете состояние в игре (получаете урон, покупаете) и
жмёте `Changed value` / `Unchanged value`. Через 3–4 итерации остаётся один-два
адреса — те, что реально реагируют на игровые события. Этот метод — рабочая лошадка
реверса: он не требует знать формат числа и находит даже зашифрованные значения.

## Поиск значений неизвестного типа: float, double и диапазоны

Integer-скан (`4 bytes`) работает, пока значение целое. Но здоровье, координаты и таймеры часто хранятся как **float** (4 байта) или **double** (8 байт). Признак: скан по int «не находит» значение, хотя на экране оно видно. Тогда переключай тип в Cheat Engine на `Float`/`Double` и сканируй по отображаемому числу.

Дополнительные режимы, которые экономят время:

- **`Unknown initial value` + `Increased value` / `Decreased value`.** Когда точное число неизвестно, но ты знаешь, что оно изменилось (ударил — здоровье упало). Два-три уточнения сужают тысячи кандидатов до единиц.
- **Диапазон (`Value between…`).** Если известно примерное значение, но не точное.
- **Групповой скан (`Grouped scan`).** Несколько адресов, которые меняются синхронно (например, `x`,`y`,`z` рядом) — по их взаимному расположению вычисляется база структуры.

```text
# Типовой сценарий float-скана
1. Скан: Float, значение 100.0        -> тысячи адресов
2. Действие, уменьшающее HP до 87.0
3. Скан: Float, значение 87.0          -> единицы
4. Проверка: заморозить адрес, ударить снова
```

Практическая тонкость: **не замораживай слишком много адресов**. Один из них может быть счётчиком рендера или временным буфером — «заморозка» такого значения ломает игру. Проверяй каждый кандидат по одному.

## Форматы сохранений и защита данных

Игровые сохранения — часто самый лёгкий путь: они читаются офлайн, без отладчика. Порядок разбора:

```bash
$ file save.dat                      # текстовый? бинарный? архив?
$ strings -n 6 save.dat | head        # видны ли ключи/значения
$ xxd save.dat | head                 # заголовок, магия, размеры полей
$ binwalk save.dat                    # вложенные zlib/gzip
```

Типичные схемы защиты сохранений, от простой к сложной:

| Защита | Как снять |
|--------|-----------|
| Простой XOR с байтом | перебрать 256 значений, искать ASCII/магию |
| XOR с повторяющимся ключом | восстановить ключ по известному фрагменту |
| Base64 + gzip | декодировать цепочкой |
| zlib с обрезанным заголовком | восстановить `78 9C`, затем `zlib.decompress` |
| CRC/подпись | пересчитать после правки (или найти, где проверяется) |
| Шифрование (AES) | искать ключ в бинаре или в памяти процесса |

Частая учебная задача — сохранение, где всё зашифровано XOR'ом с **ключом из строки** (`strings` находит и ключ, и пароль). Второй по частоте — сжатый блок, у которого намеренно затёрт zlib-заголовок: `78 9C` восстанавливается вручную, и данные читаются. Если есть подпись (CRC32/hash), правка значения потребует её пересчёта — ищи в дизассемблере, где сохранение валидируется, и смотри, что именно попадает в хеш.

Правило: **сначала попробуй прочитать, не патча значение**. Понимание формата (порядок полей, типы, где подпись) приходит из чтения, и только потом правка становится осмысленной.
