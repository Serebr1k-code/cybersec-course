## Вопрос, с которого всё начинается

Ты открываешь веб-задачу CTF. Никакой классической уязвимости не видно: нет параметров, похожих на SQL, нет форм с файлами. Просто страница «Угадай число от 0 до 1 000 000 000», и где-то спрятан флаг. Такие задачи называют **misc-web**: веб-интерфейс есть, а дыра — не в стандартной категории, а в **логике** или в лимитах. Решение тут почти всегда — небольшой скрипт, а не готовый эксплойт.

Разберём типовую такую задачу целиком.

## Наш пример: игра «Угадай число» с лимитом

На эндпоинте `/guess` сервер принимает число и отвечает одним из трёх: `more`, `less` или `CORRECT`. При верном ответе отдаёт флаг. Есть защита: не больше 3 попыток с одного IP. Проверим поведение руками:

```
$ for i in 1 2 3 4; do curl -s "http://vault.ctf/guess?n=$i"; echo; done
less
less
less
RATE LIMITED
```

Первые три попытки прошли, четвёртую сервер отклонил. Наивный перебор от 0 до 10^9 бесполезен: даже без лимита это миллиард запросов. Нужно два приёма сразу — обойти лимит и сузить поиск.

## Шаг 1: обходим лимит подменой заголовка

Лимит «по IP» часто считают по заголовку, который клиент присылает сам. Заголовок `X-Forwarded-For` придуман для прокси: он говорит серверу «настоящий клиент был вот с таким IP». Если приложение доверяет ему напрямую, мы можем подставлять любой адрес и получать свежий лимит на каждую попытку:

```
$ curl -s -H 'X-Forwarded-For: 10.0.0.1' 'http://vault.ctf/guess?n=500'
less
$ curl -s -H 'X-Forwarded-For: 10.0.0.2' 'http://vault.ctf/guess?n=500'
less
```

Лимит обнулился. Родственные приёмы: новые cookie/сессии (если лимит по сессии), разные пути (`/api` и `/api/`), «мусорные» параметры, и **параллелизм** — если сервер проверяет лимит *до* его увеличения, десяток одновременных запросов пройдёт как один (об этом — в `misc-time`).

## Шаг 2: бинарный поиск вместо перебора

Диапазон 0…10^9 за 30 попыток сужается **бинарным поиском**: каждый вопрос «больше или меньше середины» вдвое уменьшает интервал. 2^30 больше миллиарда, поэтому 30 шагов всегда достаточно. Собираем скрипт, который на каждой попытке берёт новый IP:

```python
import urllib.request

def ask(n, i):
    req = urllib.request.Request(f"http://vault.ctf/guess?n={n}",
                                 headers={"X-Forwarded-For": f"10.0.0.{i}"})
    return urllib.request.urlopen(req, timeout=5).read().decode()

lo, hi, tries = 0, 10**9, 0
while lo <= hi:
    mid = (lo + hi) // 2
    tries += 1
    r = ask(mid, tries)          # свежий IP на каждую попытку
    if r == "more": lo = mid + 1
    elif r == "less": hi = mid - 1
    else:
        print("found", mid, "in", tries, "tries"); break
```

```
found 734921731 in 30 tries; last reply: CORRECT
```

30 попыток — и число найдено, хотя лимит был 3. Это типичный шаблон misc-web: **лимит обходится, а поиск сужается алгоритмом**.

## Шаг 3: а если проверка на клиенте

Иногда «капча» или «проверка ответа» живёт целиком в браузере (JavaScript). Тогда её вообще не нужно решать — надо просто отправить запрос напрямую, минуя JS:

```
$ curl -s 'http://vault.ctf/submit?answer=42'
```

Сервер, который доверяет клиентской проверке, не защищён ничем. Признак: в исходнике страницы есть JS с ответом или с логикой проверки. Всегда сначала смотри, **где** происходит проверка — на клиенте или на сервере.

## Шаг 4: логические дыры в бизнес-логике

Другой частый сюжет — «сломать правила» магазина или формы. Классика:

- **отрицательные значения** — `qty=-1` может дать «возврат» денег вместо списания;
- **неверные типы** — `price=0`, `price=null`, `price[]=0`;
- **переполнение** — огромная сумма уходит в минус;
- **скрытые поля** — подмена `role=user` на `role=admin`;
- **разные парсеры** — JSON вместо формы, дубликаты ключей, параметры-массивы.

```
$ curl -s 'http://shop.ctf/buy' -d 'item=1&qty=-100&price=9999'
{"balance": 999900, "msg": "purchase ok"}
```

Здесь сервер не проверил знак количества — и начислил нам деньги. Всегда проверяй инварианты, которые приложение считает само собой разумеющимися: «цена положительна», «количество натуральное», «роль не повышается».

## Шаг 5: гонки как «логическая дыра»

Отдельный класс — **race condition**: проверка и действие не атомарны. Про «одноразовый купон», который срабатывает несколько раз, подробно в `misc-time`; здесь важно запомнить, что гонка — это тоже логическая дыра, и лечится она параллелизмом, а не перебором.

## Шаг 6: когда всё-таки нужен браузер

Иногда без реального браузера не обойтись: состояние игры живёт в JavaScript, ответ приходит через WebSocket, а сервер ждёт корректных кликов. Тогда берут `Playwright` или `Selenium` и управляют страницей как человек:

```python
from playwright.sync_api import sync_playwright
with sync_playwright() as p:
    b = p.chromium.launch()
    pg = b.new_page(); pg.goto("http://vault.ctf/game")
    while "flag" not in pg.content():
        state = pg.inner_text("#state")
        if "go" in state:
            pg.click("#btn")
    print(pg.content())
```

Но правило простое: **если серверная логика доступна напрямую, браузер только мешает**. Сначала пробуй `requests`/`curl`; браузер — последнее средство.

## Что мы теперь знаем

- **misc-web** — задачи с веб-интерфейсом, но без классической уязвимости; решение — скрипт.
- **Rate-limit** обходится подменой `X-Forwarded-For`, новыми сессиями, путями и параллелизмом.
- **Бинарный поиск** сужает диапазон за логарифм шагов вместо линейного перебора.
- **Клиентская проверка** не защищает сервер — запрос шлют напрямую.
- **Логические дыры** — знак, тип, переполнение, скрытые поля, расхождение парсеров.
- **Гонка** — неатомарность проверки и действия.

## На что смотреть дальше

Определи природу задачи: «угадать/пройти/обойти». Пойми, где проверка — на клиенте или сервере. Напиши скрипт на `requests` (а браузер — `Playwright`/`Selenium` — только если нужен реальный JS). Проверь гонки, лимиты и предсказуемость, потом логические инварианты. Для ручного перебора и гонок удобны Burp Repeater/Intruder и Turbo Intruder. Не забудь про cookies и CSRF-токены при автоматизации. И веди журнал: какая формулировка запроса что вернула — в misc-web дыра часто находится именно на стыке двух наблюдений, а не с первого раза.

## Куда дальше

В следующем уроке `misc-time` мы возьмём самую интересную логическую дыру — **гонку** — и разберём её по-настоящему: TOCTOU, параллельные запросы и предсказуемые генераторы. А пока главное запомни: **в misc-web проверку надо искать там, где её на самом деле нет** — в клиенте, в лимите по заголовку или в неатомарном порядке действий.
