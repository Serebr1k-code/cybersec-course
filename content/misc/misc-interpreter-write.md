## Вопрос, с которого всё начинается

В задаче дан файл с текстом на языке, которого ты не знаешь, и просьба «выполнить его и получить ответ». Исходников нет. Как вообще подступиться к незнакомому языку, не имея интерпретатора?

## Наш пример: игрушечный язык

Пусть грамматика задана так:

```
program := stmt*
stmt    := IDENT '=' expr ';'
expr    := NUM | IDENT | expr OP expr
OP      := '+' | '*' | '-'
```

Прочитаем: программа — это последовательность инструкций; инструкция — это «имя = выражение;»; выражение — число, имя или два выражения с операцией. Задача: посчитать, чему равна переменная в конце. Разберём, как написать для этого интерпретатор.

## Шаг 1: что такое интерпретатор

**Интерпретатор** — программа, которая читает текст на языке и сразу выполняет его. В отличие от компилятора, она не создаёт отдельный исполняемый файл, а идёт по программе «на ходу». Внутри почти всегда одна и та же цепочка: разбить текст на токены, собрать из них дерево, вычислить дерево.

## Шаг 2: лексер (токенизация)

Первый шаг — превратить поток символов в поток **токенов** (значимых единиц): числа, имена, операции, знаки. Например, строка `x = 3 + 4;` превращается в последовательность `IDENT(x)`, `ASSIGN`, `NUM(3)`, `PLUS`, `NUM(4)`, `SEMI`. Лексер не понимает смысла — он лишь режет текст на кусочки по правилам. Ошибка здесь (например, неверная склейка `--` в комментарий) ломает всё дальше.

## Шаг 3: парсер и дерево

**Парсер** собирает токены в **дерево разбора** (AST) по грамматике. Для `x = 3 + 4;` дерево будет: присваивание, слева — `x`, справа — сумма `3 + 4`. Дерево отражает структуру, а не порядок символов. Именно на дереве видно, что `+` применяется к `3` и `4`, а результат кладётся в `x`.

## Шаг 4: приоритет операций

Грамматика должна задавать приоритет. Если написать `expr := expr OP expr` наивно, получится неоднозначность: `2 + 3 * 4` можно разобрать двумя способами. Поэтому грамматику разбивают на уровни (`term` для умножения, `expr` для сложения), и умножение «связывается крепче». Это классический приём разбора арифметики.

## Шаг 5: вычисление дерева

Интерпретация — обход дерева. Для узла-числа возвращаем число; для узла-имени — значение из **окружения** (таблицы «имя → значение»); для узла-операции — считаем детей и применяем операцию. Присваивание записывает значение в окружение. Так дерево «оживает».

## Шаг 6: окружение и переменные

**Окружение** — словарь, где хранятся значения переменных. В простом языке это один словарь; в языках с функциями и блоками — цепочка областей видимости (вложенные окружения). Понимание окружения критично: ошибка в областях видимости — источник уязвимостей в реальных интерпретаторах.

## Шаг 7: управляющие конструкции

Добавим условия и циклы: `if`, `while`. Они вычисляются иначе — по значению условия выбирается ветка или повторяется тело. Здесь интерпретатор становится «настоящим»: появляется поток управления. Но цепочка та же — токены, дерево, вычисление.

## Шаг 8: обработка ошибок

Хороший интерпретатор не падает на плохом вводе, а сообщает ошибку с позицией. В задачах это подсказка: сообщение «unexpected token at 12» говорит, что парсер дошёл до 12-го токена и не смог продолжить. По таким сообщениям восстанавливают грамматику, даже не имея описания языка.

## Шаг 9: как это решает CTF-задачу

Дана программа на незнакомом языке и требуется результат. Порядок:

1. Разобрать примеры входа и выхода.
2. Гипотеза о грамматике (по токенам и структуре).
3. Написать лексер/парсер под гипотезу.
4. Вычислить дерево и сверить с примерами.
5. Применить к целевому входу.

Часто проще эмулировать язык, чем реверсить оригинальный интерпретатор.

## Шаг 10: почему это важно

Понимая устройство интерпретатора, ты видишь, где искать баги: в токенизации (неверные границы), в приоритете операций, в областях видимости, в переполнении при вычислении. Многие уязвимости реальных языков — ровно в этих местах.

## Шаг 11: минимальный интерпретатор

В 100 строк можно уместить лексер, рекурсивный спуск и вычисление. Такой «игрушечный» интерпретатор — лучший способ закрепить теорию: ты видишь каждый этап и можешь его сломать. В задачах такой навык позволяет быстро собрать эмулятор под конкретный язык.

## Полный прогон примера

Пройдём наш пример от начала до конца. Вход: `x = 3 + 4; y = x * 2;`. Лексер выдаёт токены: `IDENT(x) ASSIGN NUM(3) PLUS NUM(4) SEMI IDENT(y) ASSIGN IDENT(x) STAR NUM(2) SEMI`. Парсер строит два узла-присваивания: `x = add(3,4)` и `y = mul(x,2)`. Вычисление: для первого узла считаем `add(3,4)=7` и кладём `x=7`; для второго берём `x` из окружения, считаем `7*2=14`, кладём `y=14`. Результат — `y=14`. Каждый шаг опирается на предыдущий; если бы лексер не отделил `x` от `*`, дерево было бы неверным.

## Рекурсивный спуск

Самый понятный способ писать парсер — **рекурсивный спуск**: на каждое правило грамматики — своя функция. Функция `parse_expr` вызывает `parse_term`, `parse_term` — `parse_factor`. Так уровни грамматики превращаются в уровни вызовов, и приоритет операций получается «сам собой»: умножение внутри сложения. Это прямой мост между грамматикой и кодом.

## Области видимости

Если добавить блоки и функции, одного словаря мало: нужна цепочка окружений. При входе в блок создаётся новое окружение, ссылающееся на внешнее; поиск имени идёт «наружу» по цепочке. Ошибки здесь — классика: переменная «протекает» из блока наружу или, наоборот, не находится. В реальных языках такие баги приводили к утечкам данных между областями.

## Почему эмулировать проще, чем реверсить

Оригинальный интерпретатор может быть обфусцирован, а язык — недокументирован. Но грамматика почти всегда проста: числа, имена, операции, скобки. Поэтому написать свой эмулятор по примерам часто быстрее, чем разбирать чужой бинарник. Ты проверяешь гипотезу о языке на примерах «вход → выход» и уточняешь грамматику, пока эмулятор не совпадёт.

## Частые ошибки

- неверная токенизация (склейка операторов, комментарии);
- игнорирование приоритета и ассоциативности;
- один общий словарь вместо цепочки окружений;
- отсутствие лимита рекурсии (глубокое выражение роняет стек);
- молчаливое проглатывание ошибок парсера.

## Как читать чужой язык по примерам

Не имея описания языка, работай от примеров: собери пары «вход → результат» и выдели закономерности. Если видишь `A B +` → число, это постфиксная запись; если `f(x)` → значение, есть вызовы. Постепенно гипотеза о грамматике уточняется, и ты пишешь эмулятор, который воспроизводит все примеры. Так незнакомый язык становится понятным без реверса бинарника.

## Стек и вызовы функций

Добавив функции, интерпретатор получает **стек вызовов**: при вызове создаётся новое окружение с параметрами, при возврате — берётся значение. Ошибка в обработке стека (неверный возврат, потеря окружения) ломает программу или открывает уязвимость. В реальных интерпретаторах переполнение стека при глубокой рекурсии — известный класс проблем.

## Безопасность интерпретаторов

Интерпретатор исполняет чужой код — значит, он сам является песочницей. Опасны: доступ к файлам/сети из «безопасных» выражений, переполнение при вычислении, неограниченная рекурсия, утечка окружения. Поэтому в задачах «эмулятор» часто ещё и граница безопасности: сломав интерпретатор, ты выходишь за его пределы.

## Итог

Интерпретатор — это цепочка «текст → токены → дерево → вычисление». Освоив её, ты можешь эмулировать любой язык, читать чужой код по примерам и видеть, где языки ломаются. Это фундамент для компиляторов, VM и разбора обфускации.

## Что мы теперь знаем

- Интерпретатор: лексер → парсер → дерево → вычисление.
- Лексер режет текст на токены, парсер собирает дерево.
- Приоритет операций задаётся уровнями грамматики.
- Окружение хранит значения переменных.
- По ошибкам парсера восстанавливают грамматику.

## Шпаргалка: минимальный интерпретатор на Python

Каркас рекурсивного спуска умещается в несколько десятков строк:

```python
def tokenize(s):
    return [t for t in re.findall(r'\d+|[()+*/-]', s)]

def parse(tokens):
    def expr():
        left = term()
        while tokens and tokens[0] in '+-':
            op = tokens.pop(0); left = (op, left, term())
        return left
    def term():
        left = factor()
        while tokens and tokens[0] in '*/':
            op = tokens.pop(0); left = (op, left, factor())
        return left
    def factor():
        t = tokens.pop(0)
        if t == '(':
            e = expr(); tokens.pop(0); return e
        return ('num', int(t))
    return expr()

def evaluate(node):
    if node[0] == 'num': return node[1]
    op, a, b = node
    a, b = evaluate(a), evaluate(b)
    return {'+': a+b, '-': a-b, '*': a*b, '/': a//b}[op]
```

Три функции — три уровня приоритета: `expr` → `term` → `factor`. Каждый уровень
«съедает» свои операторы, а скобки замыкают рекурсию.

## Отладка интерпретатора: трассировка

Когда ответ не сходится, печатайте дерево, а не результат:

```python
print(parse(tokenize('2+3*4')))
# ('+', ('num', 2), ('*', ('num', 3), ('num', 4)))
```

Дерево сразу показывает приоритет: если `*` оказался ниже `+`, значит парсер
разобрал `(2+3)*4` — ошибка в `term`.

## Безопасность интерпретаторов

Свой интерпретатор в CTF часто содержит уязвимость:

- переполнение при вычислении `int` (нет проверки границ);
- `eval`/`exec` для «удобства» — прямой RCE;
- чтение файлов по имени переменной (`open(name)`), путь не проверен;
- циклы без лимита итераций — DoS.

Проверяя чужой интерпретатор, смотрите: как обрабатываются отрицательные числа,
деление на ноль, очень длинные строки и неизвестные символы.
