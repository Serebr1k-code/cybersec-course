WebAssembly (WASM) позиционируется как безопасная песочница: линейная память, отсутствие прямого доступа к системе, типизированные вызовы. Но безопасность обеспечивает не сам WASM, а **embedder** (wasmtime, wasmer, node, wasm3) — и именно в нём чаще всего находят побеги. В CTF WASM-песочница — это «выполните байткод, но не трогайте хост».

## Модель безопасности WASM

Модуль WASM имеет:

- **линейную память** — массив байтов, к которому модуль имеет доступ; вне её — ничего;
- **таблицы** — для косвенных вызовов (`call_indirect`);
- **глобальные** — переменные;
- **импорты** — функции, которые предоставляет хост (embedder);
- **экспорты** — функции, которые видны хосту.

Модуль **не может** напрямую сделать syscall. Всё, что он может, — вызвать импортированную host-функцию. Значит, побег = либо злоупотребление host-функцией, либо баг в embedder'е/JIT.

## Импорты — первая линия

Опасные импорты:

```wat
(import "env" "memory" (memory 1))
(import "env" "system" (func $system (param i32) (result i32)))
```

Если хост экспортирует `system`, `eval`, `read_file`, `open`, — модуль может вызвать их с произвольными аргументами. Классический баг: host-функция передаёт указатель на линейную память, а модуль подсовывает другой указатель или выходит за границы.

Пример уязвимой host-функции:

```c
// embedder на C
int host_read(wasm_module_t m, int ptr, int len) {
    char *mem = wasm_memory(m);
    return read(0, mem + ptr, len);  // нет проверки границ!
}
```

Если `ptr + len` выходит за пределы линейной памяти, `read` пишет в память embedder'а — потенциальный побег.

## Векторы побега

1. **Отсутствие проверки границ в host-функции** — OOB read/write в память хоста.
2. **Use-after-free** в embedder'е при работе с памятью модуля.
3. **JIT-баги** — неправильная генерация машинного кода, позволяющая выйти за пределы.
4. **Type confusion** через `call_indirect` и таблицы.
5. **WASI-импорты** — если реализация WASI позволяет открыть не тот файл (path traversal).
6. **Совместная память** (`SharedArrayBuffer`, threads) — гонки.

## WASI и его ограничения

WASI (WebAssembly System Interface) даёт модулю «системные» функции: `fd_read`, `fd_write`, `path_open`. Хост решает, какие пути разрешены. Если реализация WASI не проверяет путь (или разрешает `..`), модуль читает чужие файлы:

```rust
// уязвимая конфигурация wasmtime: разрешён корень /
let dir = Dir::open_ambient_dir("/", ambient_authority())?;
```

С правильной конфигурацией (`--dir=.`) модуль видит только рабочую папку.

## Разобранный пример

Дано: `challenge.wasm`, embedder предоставляет импорт `write(ptr, len)`, который копирует из линейной памяти в stdout без проверки границ.

Анализ:

```bash
wasm2wat challenge.wasm | grep -A2 '(import'
# (import "env" "write" (func (param i32 i32)))
```

Если `write` читает `len` байт с `ptr`, а проверки нет — можно запросить огромный `len` и прочитать память embedder'а (утечка). Собираем вызов:

```wat
(module
  (import "env" "write" (func $w (param i32 i32)))
  (memory (export "memory") 1)
  (func (export "main")
    i32.const 65535   ;; ptr у границы
    i32.const 100000  ;; len за пределами памяти
    call $w))
```

```bash
wat2wasm leak.wat -o leak.wasm
wasmtime run --invoke main leak.wasm | xxd | head
# возможная утечка памяти embedder'а
```

Если embedder корректно проверяет границы — этот вектор закрыт, ищем JIT-баги или иные импорты.

## Практические советы

- Начните с `wasm2wat`/`wasm-decompile` — понять, что делает модуль и какие импорты использует.
- Перечислите все импорты: каждый — потенциальный примитив.
- Проверьте, проверяет ли host границы `ptr`/`len`.
- Попробуйте WASI path traversal, если модуль открывает файлы.
- Ищите версию embedder'а: известные CVE wasmtime/wasmer дают готовые побеги.

## Частые ошибки и подводные камни

- Считать, что WASM «безопасен по определению» — за безопасность отвечает embedder.
- Игнорировать импорты: без них модуль почти бессилен.
- Забывать про разницу версий: побег из wasmtime 10 не сработает на 15.
- Путать линейную память модуля и память хоста — OOB в модуле не всегда побег.
- Не проверять `call_indirect` type confusion.
- Пренебрегать WASI-конфигурацией: `--dir=/` — почти приглашение.

## Что дальше / решение

Соберите простой embedder на C/Rust с намеренно небезопасной host-функцией и найдите побег. Изучите CVE wasmtime/wasmer/wasm3. Дальше — `misc-sandbox` (общая теория), `misc-sandbox-langs` (другие песочницы) и `misc-seccomp-escape`.

## Дополнительная теория: линейная память, таблицы и валидация

WASM-модуль исполняется в **валидируемом** байткоде: перед запуском embedder проверяет типы и границы (структурная валидация). Это защищает от классических переполнений: любое обращение к памяти проверяется против её размера, косвенные вызовы — против таблицы. Однако эти проверки делает embedder, и **ошибка в их реализации** (или в JIT-компиляции в машинный код) ломает изоляцию. Именно поэтому большинство побегов из WASM — это баги в конкретном движке (wasmtime, wasmer, V8, JavaScriptCore), а не в самом стандарте.

Ключевые структуры: **linear memory** (массив байтов, `memory.grow` увеличивает), **tables** (для `call_indirect`), **globals**, **imports/exports**. `call_indirect` берёт индекс из таблицы — type confusion здесь даёт вызов функции с неверной сигнатурой. `memory.grow` может вернуть -1 при неудаче — необработанный случай ведёт к OOB. Понимание этих механизмов — основа анализа WASM-задач.

## WASI и capability-модель

WASI построен на **capability-модели**: модуль не имеет доступа к ФС/сети, пока хост не предоставит «возможность» (открытый каталог, сокет). Это принципиально безопаснее POSIX: нет глобального пространства имён, только явно выданные дескрипторы. Уязвимость появляется, когда хост выдаёт слишком широкую возможность (`--dir=/` вместо `--dir=.`) или когда реализация WASI некорректно проверяет пути (`..`, symlink traversal). В CTF проверяйте: какие `--dir`/`--mapdir` выданы, какие функции импортированы, и можно ли выйти за пределы разрешённого каталога через симлинки.

## Разбор ошибок и отладка

Если `wasmtime run` падает — читайте сообщение: часто это отсутствующий импорт (`unknown import`) или неверный тип. Если модуль «ничего не делает» — возможно, у него нет экспорта `_start`/`main`; проверьте экспорты (`wasm-objdump -x`). Если `wasm2wat` даёт нечитаемый вывод — используйте `wasm-decompile` для псевдокода. Если host-функция возвращает ошибку — проверьте аргументы (ptr/len могут быть вне границ). Если эксплойт «не течёт» — embedder мог корректно проверять границы; ищите другой вектор или версию с известным CVE. Всегда начинайте с инвентаризации импортов — это карта возможностей.

## Практический разбор: анализ импортов и OOB

Дано: `challenge.wasm`, запускается embedder'ом с импортом `read(ptr, len)`.

```bash
wasm2wat challenge.wasm | grep -A3 '(import'
# (import "env" "read" (func (param i32 i32)))
wasm-objdump -x challenge.wasm | grep -A10 Import
```

Модуль импортирует `read(ptr, len)` и `write(ptr, len)`. Проверяем, есть ли в host-функции проверка границ: если embedder написан на C и делает `memcpy(host_mem + ptr, ...)` без валидации, то `ptr` у границы памяти даёт OOB. Собираем WAT-модуль, вызывающий `read` с `ptr = 65535, len = 100000`:

```wat
(module
  (import "env" "read" (func $r (param i32 i32)))
  (memory (export "memory") 1)
  (func (export "main")
    i32.const 65535
    i32.const 100000
    call $r))
```

```bash
wat2wasm oob.wat -o oob.wasm && wasmtime run oob.wasm
```

Если embedder корректно проверяет границы — OOB закрыт, ищем другие векторы: WASI path traversal, `call_indirect` type confusion, или известный CVE версии рантайма. Всегда начинайте с инвентаризации импортов — это карта возможностей модуля, и без импортов побег почти невозможен.
