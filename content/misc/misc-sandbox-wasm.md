## Вопрос, с которого всё начинается

Тебе дают файл `challenge.wasm` и говорят: «запустите байткод, но не трогайте хост». WebAssembly (WASM) рекламируют как безопасную песочницу: у модуля есть только своя память и никакого доступа к системе. Но безопасность обеспечивает не сам WASM, а **embedder** — программа, которая его запускает. И побеги почти всегда живут в embedder'е, а не в стандарте. Разберём это на конкретном модуле.

## Наш пример: модуль challenge.wasm

**WASM** — компактный байткод, который исполняет хост-программа. У модуля есть:

- **линейная память** — массив байтов, к которому он имеет доступ; вне её — ничего;
- **таблицы** — для косвенных вызовов (`call_indirect`);
- **глобальные** переменные;
- **импорты** — функции, которые предоставляет хост;
- **экспорты** — функции, видимые хосту.

Модуль **не может** напрямую сделать системный вызов. Всё, что он умеет, — вызвать импортированную host-функцию. Значит, побег — это либо злоупотребление host-функцией, либо баг в embedder'е. Начинаем с разбора.

## Шаг 1: дизассемблируем и смотрим импорты

Переводим байткод в читаемый **WAT** (текстовый формат WASM) и ищем импорты:

```bash
$ wasm2wat challenge.wasm | grep -A3 '(import'
(import "env" "read" (func (param i32 i32)))
(import "env" "write" (func (param i32 i32)))
```

Модуль импортирует две host-функции: `read(ptr, len)` и `write(ptr, len)`. Это и есть карта его возможностей — без импортов модуль почти бессилен. `ptr` и `len` — смещение и длина в **линейной памяти** модуля.

## Шаг 2: проверяем host-функцию на границы

Ключевой вопрос: проверяет ли хост, что `ptr + len` не выходит за размер линейной памяти? Смотрим embedder (в задаче обычно дают его исходник):

```c
// уязвимый embedder на C
int host_read(wasm_module_t m, int ptr, int len) {
    char *mem = wasm_memory(m);
    return read(0, mem + ptr, len);   // нет проверки границ!
}
```

Здесь `mem + ptr` — указатель в памяти embedder'а, и `read` пишет туда `len` байт без проверки. Если модуль передаст `ptr` у самого края линейной памяти, а `len` — большой, запись уйдёт за пределы памяти модуля, в память хоста. Это **OOB** (out-of-bounds) — классический вектор побега.

## Шаг 3: собираем эксплойт на WAT

Пишем модуль, который вызывает `read` с `ptr = 65535` (край страницы памяти в 64 КиБ) и `len = 100000` (далеко за пределами):

```wat
(module
  (import "env" "read" (func $r (param i32 i32)))
  (memory (export "memory") 1)
  (func (export "main")
    i32.const 65535     ;; ptr у границы
    i32.const 100000    ;; len за пределами памяти
    call $r))
```

Собираем и запускаем:

```bash
$ wat2wasm oob.wat -o oob.wasm
$ wasmtime run oob.wasm
```

Если embedder корректно проверяет границы — вектор закрыт, идём дальше. Если нет — запись уходит в память хоста, и мы получаем примитив для дальнейшего побега. Именно так выглядит большинство WASM-задач: **не баг в WASM, а баг в host-функции**.

## Шаг 4: WASI и path traversal

Отдельный слой — **WASI** (WebAssembly System Interface): набор «системных» функций (`fd_read`, `fd_write`, `path_open`), через которые модуль работает с файлами. WASI построен на **capability-модели**: модуль не видит файловую систему, пока хост не выдаст ему «возможность» — открытый каталог. Опасность — когда каталог выдан слишком широко:

```rust
// уязвимая конфигурация wasmtime: разрешён корень /
let dir = Dir::open_ambient_dir("/", ambient_authority())?;
```

С правильной конфигурацией (`--dir=.`) модуль видит только рабочую папку. В CTF проверяй, какие `--dir`/`--mapdir` выданы, и можно ли выйти за пределы разрешённого каталога через `..` или симлинк.

## Шаг 5: JIT-баги и type confusion

Сам байткод **валидируется** перед запуском: embedder проверяет типы и границы. Поэтому классические переполнения в самом WASM невозможны — их ловит валидатор. Но эти проверки делает embedder, и **ошибка в его реализации** (или в JIT-компиляции в машинный код) ломает изоляцию. Большинство реальных побегов — баги в конкретном движке (wasmtime, wasmer, V8, JavaScriptCore), а не в стандарте. Отдельно смотри `call_indirect` с таблицами: **type confusion** там даёт вызов функции с неверной сигнатурой.

## Шаг 6: инвентаризация импортов как метод

Общий подход к любой WASM-задаче:

```bash
$ wasm2wat challenge.wasm | grep -A2 '(import'
$ wasm-objdump -x challenge.wasm | grep -A10 Import
$ wasm-decompile challenge.wasm          # псевдокод для понимания логики
```

Перечисли все импорты — каждый это потенциальный примитив. Проверь, валидирует ли хост `ptr`/`len`. Попробуй WASI path traversal, если модуль открывает файлы. И узнай версию embedder'а: у wasmtime/wasmer есть публичные CVE, дающие готовые побеги.

## Шаг 7: гонки и совместная память

Современный WASM умеет **потоки** через `SharedArrayBuffer`: несколько потоков видят одну линейную память. Это открывает класс **гонок**: если host-функция не атомарна или embedder неправильно синхронизирует доступ, можно получить несогласованное состояние и обойти проверку. Гонки в WASM-движках — редкий, но реальный вектор, и в задачах он встречается реже, чем OOB в host-функции. Всегда сначала исчерпай простые векторы (границы, WASI-пути, type confusion), а гонки оставь на потом.

## Что мы теперь знаем

- Безопасность WASM обеспечивает **embedder**, а не сам стандарт.
- Модуль взаимодействует с системой только через **импорты** — их и надо проверять.
- **OOB** возникает, когда host-функция не проверяет границы `ptr`/`len` в линейной памяти.
- **WASI** на capability-модели: широкий `--dir=/` открывает path traversal.
- **JIT-баги** и **type confusion** (`call_indirect`) — векторы побега в движке.
- Метод — **инвентаризация импортов** и проверка версии embedder'а.

## На что смотреть дальше

Собери простой embedder на C/Rust с намеренно небезопасной host-функцией и найди побег. Изучи CVE wasmtime/wasmer/wasm3. При отладке: если `wasmtime run` падает с `unknown import` — у модуля нет нужного импорта; если «ничего не делает» — проверь экспорты (`wasm-objdump -x`); если `wasm2wat` даёт нечитаемый вывод — используй `wasm-decompile`. Дальше — `misc-sandbox` (общая теория) и `misc-sandbox-langs` (песочницы языков).
