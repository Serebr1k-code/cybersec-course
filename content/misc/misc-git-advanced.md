## Вопрос, с которого всё начинается

Задача даёт репозиторий, в котором разработчик «вычистил» секрет через `git filter-branch`, переписал историю и сделал `push --force`. Обычный `git log` ничего не показывает — история выглядит чистой. Но данные почти наверняка остались. Где их искать, если базовые команды молчат?

## Наш пример: репозиторий после filter-branch

Смотрим историю:

```
$ git log --oneline --all
a1b2c3d (HEAD -> main) clean history
```

Один коммит, никаких следов секрета. Но `filter-branch` переписывает историю, создавая **новые** коммиты, а старые становятся недостижимыми. Проверяем reflog:

```
$ git reflog --all
a1b2c3d HEAD@{0}: filter-branch: rewrite
9d8e7f6 HEAD@{1}: commit: add secret
```

`reflog` — журнал всех перемещений указателей. В нём сохранился старый коммит `9d8e7f6`. Читаем его:

```
$ git show 9d8e7f6
commit 9d8e7f6...
    add secret

+api_key = sk_live_51H...
```

Секрет найден. Первое правило продвинутой git-форензики: **начинай с reflog**.

## Шаг 1: refs/original — резерв filter-branch

У `filter-branch` есть особенность: он сохраняет резервные ссылки в пространстве имён `refs/original/`:

```
$ git show-ref | grep original
9d8e7f6 refs/original/refs/heads/main
```

Это значит, что старая вершина ветки доступна целиком:

```
$ git show refs/original/refs/heads/main
```

Если эту ссылку ещё не удалили, вы получаете **всю** старую историю, а не отдельный коммит. Проверяйте `refs/original` в первую очередь при подозрении на `filter-branch`.

## Шаг 2: amend, rebase и висячие объекты

`git commit --amend` заменяет последний коммит новым, а старый остаётся **висячим** (dangling). `rebase` делает то же со всей цепочкой. Найти их помогает `git fsck` — команда проверки целостности базы:

```
$ git fsck --lost-found
dangling commit 7c8d9e0f...
dangling blob 3f1a2b4c...
```

«Висячий» — значит, на объект не ссылается ни одна ветка, тег или коммит. Но объект жив, пока не сработала агрессивная сборка мусора. Читаем его:

```
$ git cat-file -p 7c8d9e0f...
```

`git cat-file -p <хэш>` печатает содержимое объекта: для коммита — метаданные и tree, для blob — данные файла.

## Шаг 3: packfiles

После `git gc` объекты упаковываются в `.git/objects/pack/*.pack` и сжимаются дельтами (разницами между похожими объектами). Они не исчезают — просто перестают лежать отдельными файлами. Смотрим, что внутри:

```
$ git verify-pack -v .git/objects/pack/pack-*.idx | sort -k3 -n | tail -3
7c8d9e0f... commit 220 300 5678
3f1a2b4c... blob   142 180 9012
```

Третья колонка — размер. Крупные blob'ы часто и есть удалённые файлы. Распаковать всё обратно в отдельные объекты:

```
$ mkdir /tmp/unpack && cd /tmp/unpack
$ git init --bare
$ git unpack-objects < /path/to/.git/objects/pack/pack-*.pack
```

После распаковки объекты читаются обычными `cat-file` и `fsck`.

## Шаг 4: точечный поиск по содержимому

Когда нужно найти не «вообще секрет», а конкретную строку, работает **pickaxe** — флаг `-S`:

```
$ git log -S 'api_key' --all --oneline
9d8e7f6 add secret
```

`-S` находит коммиты, где менялось число вхождений строки. Близкий вариант — `-G` с регулярным выражением. Это мощнее `grep` по истории: вы сразу видите точный коммит, а не тонны патчей.

Ещё один полезный фильтр — поиск удалённых файлов:

```
$ git log --diff-filter=D --name-only --all
secret.txt
```

`--diff-filter=D` оставляет только коммиты, где файлы удалялись.

## Шаг 5: если `.git` без рабочего дерева

Иногда на входе только каталог `.git`, а файлов нет. Восстановить рабочее дерево можно из индекса или последнего коммита:

```
$ git checkout -- .        # файлы из индекса
$ git reset --hard HEAD    # из последнего коммита
```

Для конкретной версии файла — `git show <коммит>:<путь> > /tmp/file`.

## Шаг 6: полный прогон

Соберём всё в одну последовательность для репозитория после перезаписи истории:

1. `git log --all --oneline` — видим только «чистый» коммит.
2. `git reflog --all` — находим старую вершину `HEAD@{1}`.
3. `git show-ref | grep original` — проверяем `refs/original/` от `filter-branch`.
4. `git show refs/original/refs/heads/main` — при удаче получаем всю старую историю.
5. Если reflog и `refs/original` пусты — `git fsck --lost-found` для висячих коммитов.
6. `git cat-file -p <dangling-commit>` — читаем содержимое.
7. Объекты только в pack — `git verify-pack -v` и `git unpack-objects`.

Такой порядок «reflog → refs/original → fsck → packfiles» покрывает почти все случаи. Идите от дешёвого к сложному: не начинайте с распаковки packfiles, если reflog ещё хранит ответ.

## Шаг 7: работайте на копии

Продвинутая форензика легко «затирает» улики: `git gc`, `git reflog expire`, повторный `filter-branch` могут уничтожить то, что вы ищете. Поэтому первым делом делайте копию каталога:

```
$ cp -r project project_backup
```

Все эксперименты — только на копии. Оригинал остаётся нетронутым как доказательство.

## Шаг 8: читаем объект вручную

Если `git` не открывает репозиторий, объект всё равно можно прочитать — он zlib-сжатый:

```python
import zlib
print(zlib.decompress(open('.git/objects/9d/8e7f6...', 'rb').read()))
```

Первая строка вывода — `commit <размер>\0`, затем метаданные. Тот же приём работает для blob и tree. Так читают данные даже из повреждённого `.git`, где высокоуровневые команды бессильны.

## Что мы теперь знаем

По-простому:

1. `reflog` хранит перемещения HEAD — это первый источник после перезаписи истории.
2. `filter-branch` оставляет резервные ссылки в `refs/original/`.
3. `amend` и `rebase` создают висячие объекты; их находит `git fsck --lost-found`.
4. Объекты в packfiles живы и доступны через `verify-pack` / `unpack-objects`.
5. `git log -S` и `--diff-filter=D` находят нужный коммит точечно.

## На что смотреть дальше

- **Игнорировать `--all`** — теряются коммиты удалённых веток.
- **Не смотреть reflog** — пропускаются самые свежие «потерянные» коммиты.
- **Считать amend окончательным** — старый коммит остаётся висячим.
- **Забыть про packfiles** — после `gc` объекты упакованы, но живы.
- **Портить репозиторий** — работайте на копии, чтобы не потерять улики.
