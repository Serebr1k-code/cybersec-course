## Продвинутая git-форензика: зачем копать глубже

Базовые команды (`git log`, `git show`) покрывают типовые задачи, но «продвинутая» git-форензика нужна там, где историю чистили: делали `rebase`, `amend`, `filter-branch`, удаляли ветки и перепаковывали объекты. В таких случаях информация остаётся в reflog, в висячих объектах и внутри packfiles, но уже не видна обычным `git log`. Умение работать на уровне объектной базы отделяет новичка от специалиста. Цель модуля — освоить чтение git «изнутри».

## Как git хранит данные

Git — это key-value хранилище, где ключ — SHA-1 (или SHA-256) содержимого. Четыре типа объектов: blob (файл), tree (каталог со ссылками на blob/tree), commit (ссылка на tree и родителей), tag. Всё адресуется по хешу. Ветка — просто указатель на коммит, а `HEAD` — указатель на ветку или коммит. Понимание этой модели объясняет, почему «удалённые» данные остаются: пока объект есть в базе и на него есть хоть одна ссылка (в reflog, в другом коммите, в dangling-наборе), он жив.

## Работа с reflog

`reflog` фиксирует каждое перемещение `HEAD` и ссылок:

```bash
git reflog --all --date=iso
git reflog show <branch>
git show HEAD@{5}
git diff HEAD@{5} HEAD@{2}
```

Если разработчик сделал `git reset --hard`, коммит пропал из ветки, но остался в reflog на несколько дней. Восстановление:

```bash
git branch recovered HEAD@{3}
```

## Amend, rebase и «потерянные» коммиты

`git commit --amend` заменяет последний коммит новым; старый остаётся висячим. Найти его:

```bash
git fsck --lost-found
git cat-file -p <dangling-commit>
```

`rebase` переписывает историю, создавая новые коммиты, а старые становятся недостижимыми. Их ищут через `git fsck --unreachable` и читают напрямую.

## Работа с packfiles

Объекты пакуются в `.git/objects/pack/`. Индекс `.idx` описывает упакованные объекты:

```bash
git verify-pack -v .git/objects/pack/pack-*.idx | sort -k3 -n | tail -20
```

Третья колонка — размер; крупные объекты часто и есть удалённые секреты. Распаковать всё обратно в объекты:

```bash
mkdir /tmp/unpack && cd /tmp/unpack
git init --bare
git unpack-objects < /path/to/.git/objects/pack/pack-*.pack
```

После распаковки можно перебирать объекты обычными средствами.

## Восстановление удалённого файла без рабочего дерева

Если у вас только `.git` (без файлов), восстановите рабочее дерево:

```bash
git checkout -- .            # восстановить файлы из индекса
git checkout HEAD -- .       # из последнего коммита
git reset --hard HEAD
```

Для конкретной версии:

```bash
git show <commit>:<path> > /tmp/file
```

## Поиск в истории по содержимому

```bash
# найти коммит, где впервые появилась строка
git log -S 'password123' --all --oneline
# найти коммит, где строка менялась
git log -G 'regex' --all -p
# бинарный поиск виновника
git bisect start HEAD <good>
```

`-S` (pickaxe) ищет добавление/удаление строки, `-G` — любое изменение по regex. Это мощнее обычного `grep` по истории.

## Анализ .git при отсутствии git

Иногда `.git` есть, но это повреждённый архив или директория с фрагментами. Тогда работайте с объектами вручную: zlib-сжатые файлы в `.git/objects/xx/yyyy` можно распаковать:

```bash
python3 -c "import zlib,sys;print(zlib.decompress(open(sys.argv[1],'rb').read()).decode('utf-8','replace'))" .git/objects/ab/cdef...
```

Так читаются отдельные объекты, даже если `git` не может открыть репозиторий.

## Типичные ошибки и подводные камни

- **Игнорировать `--all`** — теряются коммиты удалённых веток.
- **Не смотреть reflog** — пропускаются самые свежие «потерянные» коммиты.
- **Считать amend окончательным** — старый коммит остаётся висячим.
- **Забыть про packfiles** — после `gc` объекты упакованы, но живы.
- **Портить репозиторий** — работайте на копии, чтобы не потерять доказательства.
- **Смешивать индекс и историю** — `git diff --cached` vs `git diff`.
- **Не проверять `fsck`** — именно он выдаёт unreachable/dangling.

| Задача | Команда |
|--------|---------|
| История перемещений | `git reflog --all` |
| Висячие коммиты | `git fsck --lost-found` |
| Восстановить ветку | `git branch x HEAD@{n}` |
| Объекты в pack | `git verify-pack -v *.idx` |

## Что дальше / решение

Итог: продвинутая git-форензика — это работа на уровне объектов и ссылок. Начинайте с `git reflog --all` и `git fsck`, затем читайте недостижимые коммиты через `cat-file`, распаковывайте packfiles и ищите содержимое через pickaxe (`-S`/`-G`). Всегда работайте на копии репозитория и помните, что git почти ничего не удаляет по-настоящему — даже после amend и rebase данные остаются в объектной базе, пока не сработает агрессивный `gc --prune=now`.

## Практический пример: чистили историю через filter-branch

Представим, что разработчик удалил секрет из всех коммитов через `git filter-branch`, переписал историю и сделал `git push --force`. Обычные команды ничего не покажут. Что делать. Во-первых, `git reflog` — в нём остаются ссылки на старые вершины, если репозиторий не клонировали заново. Во-вторых, `git fsck --unreachable` — старые коммиты и блобы становятся недостижимыми, но живыми. В-третьих, `git verify-pack` по индексам packfiles покажет объекты, включая крупные blob'ы, которые и есть удалённые файлы. Наконец, если у вас есть доступ к удалённому репозиторию, поищите в `refs/original/` — `filter-branch` сохраняет там резервные ссылки, и `git show refs/original/refs/heads/main` вернёт старую историю целиком.

Это ключевой приём: после `filter-branch` остаётся пространство имён `refs/original`, и оно часто не удаляется. Если его подчистили, переходите к ручному анализу packfiles и распаковке объектов.

## Работа с датами и метаданными коммитов

Коммиты содержат автора, дату и сообщение. В форензике это улики: по времени можно восстановить последовательность действий, по автору — кто именно закоммитил секрет. `git log --format='%h %an %ae %ad %s'` даёт компактную сводку. `git show --stat <sha>` покажет, какие файлы менялись. Если нужно найти коммит по конкретной дате, используйте `--since`/`--until`. Метаданные неизменяемы без перезаписи хеша, поэтому подделать их сложно — это делает их надёжным источником истины.

## Частые вопросы

«Как найти, в каком коммите появилась строка?» — `git log -S 'строка' --all --oneline`. «Как понять, что удалили?» — `git log --diff-filter=D --name-only`. «Что если объекты перепакованы?» — `git unpack-objects` или `verify-pack`. «Как восстановить удалённую ветку?» — `git reflog` → `git branch name <sha>`. «Безопасно ли трогать репозиторий?» — нет, копируйте.

## Что дальше / решение

Итог: продвинутая git-форензика — это последовательность `reflog` → `fsck` → `refs/original` → packfiles → ручной разбор объектов. Знание модели объектов и умение читать недостижимые данные напрямую позволяют восстановить то, что разработчик считал безвозвратно удалённым. Держите под рукой шпаргалку команд и работайте на копиях.

## Частые вопросы по продвинутой git-форензике

«`filter-branch` всё вычистил?» — смотрите `refs/original`. «Как найти недостижимый коммит?» — `git fsck --lost-found`. «Объекты в pack — как читать?» — `git verify-pack` и `git unpack-objects`. «Как найти, где строка появилась?» — `git log -S`. «Что если `.git` без рабочего дерева?» — `git checkout -- .` или `git reset --hard`. «Помогает ли дата коммита?» — да, `git log --format` восстанавливает хронологию. Главное правило: работайте на копии и идите от `reflog` к ручному разбору объектов.
