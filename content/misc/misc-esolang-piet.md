## Вопрос, с которого всё начинается

В прошлом уроке мы научились узнавать esolang по алфавиту символов. Но что делать, если файл — это `.png`, а не текст? Открываешь картинку — абстрактные цветные прямоугольники, ни букв, ни цифр. А в условии написано: «исполните изображение». Это Piet — язык, где программа **нарисована**.

## Наш пример: файл art.png

Задача даёт один файл — `art.png`. Начинаем, как всегда, с определения типа:

```
$ file art.png
art.png: PNG image data, 100 x 100, 8-bit/color RGB, non-interlaced
```

Обычный PNG, 100×100. Смотрим глазами (или через `convert`/просмотрщик): картинка состоит из прямоугольных блоков чистого цвета — красный, жёлтый, циан, чёрный. Градиентов нет, палитра ограничена.

Это сигнатура Piet. Название — в честь художника Пита Мондриана, чьи картины из цветных прямоугольников и вдохновили автора.

## Шаг 1: как картинка становится программой

Piet-программа состоит из **codels** — блоков одного цвета. Каждый блок несёт цвет, а цвет раскладывается на две координаты:

- **hue** (оттенок) — красный, жёлтый, зелёный, циан, синий, маджента (6 значений);
- **lightness** (светлота) — светлый, нормальный, тёмный (3 значения).

Итого 6 × 3 = 18 «рабочих» цветов. Плюс два особых: **белый** и **чёрный** — они управляют движением, а не вычислениями.

По картинке ползёт исполнитель с двумя указателями:

- **DP** (Direction Pointer) — куда движемся: вправо, вниз, влево, вверх;
- **CC** (Codel Chooser) — какой из крайних блоков выбрать, выходя за границу.

Когда исполнитель переходит из блока в блок, важна **разница цветов** между ними: Δhue и Δlightness. Именно эта пара и есть команда.

## Шаг 2: таблица команд

Каждой паре (Δhue, Δlightness) сопоставлена операция:

| Δhue | Δlightness | Операция |
|------|-----------|----------|
| 0 | 1 | push |
| 0 | 2 | pop |
| 1 | 0 | add |
| 1 | 1 | subtract |
| 1 | 2 | multiply |
| 2 | 0 | divide |
| 2 | 1 | mod |
| 2 | 2 | not |
| 3 | 0 | greater |
| 3 | 1 | pointer (повернуть DP) |
| 3 | 2 | switch (сменить CC) |
| 4 | 0 | dup |
| 4 | 1 | roll |
| 4 | 2 | in (число) |
| 5 | 0 | in (символ) |
| 5 | 1 | out (число) |
| 5 | 2 | out (символ) |

Числовые значения для `push` берутся из **размера блока** — сколько codels в нём, такое число и кладётся на стек. Поэтому в Piet важно не только «какой цвет», но и «какой он большой».

Белый цвет — «свободное место»: исполнитель скользит по нему, вращая DP/CC, пока не упрётся в цветной блок. Чёрный — «стена»: DP поворачивается. На этих правилах и держится вся визуальная запутанность Piet.

## Шаг 3: запускаем интерпретатор

Читать картинку вручную не нужно — берём эталонный интерпретатор `npiet`:

```
$ npiet art.png
Hello, world!
```

Если программа печатает текст напрямую — задача решена, в реальном CTF здесь был бы флаг.

Иногда вывод пустой или программа «висит». Это не поломка: скорее всего, она ждёт ввод (`in`) или печатает числа. Подаём ввод через pipe:

```
$ echo -n "answer" | npiet art.png
```

А если хотим понять, что происходит внутри, включаем трассировку — `-t` печатает каждый шаг:

```
$ npiet -t art.png | head -5
step 0: (0,0) color=(255,0,0) dp=right cc=left
step 1: (0,0) color=(255,0,0) -> nop
step 2: (1,0) color=(255,255,0) dHue=1 dLight=0 -> add
...
```

Здесь видно текущую позицию, цвет блока, разницу и выбранную операцию. По этому логу удобно ловить ошибки и понимать логику.

## Шаг 4: когда вывод — числа

Иногда `npiet` сыплет числами вместо текста:

```
$ npiet art.png
72 101 108 108 111
```

Это `out (number)`. Числа — коды символов. Собираем их в байты одной строкой:

```
$ npiet art.png | python3 -c "import sys;print(bytes(int(x) for x in sys.stdin.read().split()))"
b'Hello'
```

Получили текст. В задачах с флагом именно так и достают строку.

## Шаг 5: если интерпретатора нет

`npiet` ставится из пакетов (`apt install npiet`) или собирается из исходников. Но иногда окружение закрыто, а интерпретатор недоступен. Тогда два пути.

Первый — **ручная интерпретация** маленькой программы. Рисуем сетку блоков, отмечаем старт (левый верхний), записываем цвета по порядку обхода и считаем разницу между соседними блоками:

```
блок 1: красный нормальный (hue=0, light=1)
блок 2: жёлтый нормальный (hue=1, light=1)  -> Δhue=1, Δlight=0 -> add
блок 3: жёлтый тёмный   (hue=1, light=2)  -> Δhue=0, Δlight=1 -> push
```

Так по шагам восстанавливается весь поток. Трудоёмко, но на картинке из десятка блоков реально.

Второй путь — **свой мини-интерпретатор**: читаем PNG (`Pillow`), квантуем цвета к 18 палитровым, обходим блоки по правилам DP/CC. Это хорошая практика, но для CTF почти всегда быстрее поставить `npiet`.

Важно не путать Piet с обычной картинкой-стего: там данные прячут в младших битах пикселей, а здесь цвета — это **код**, который надо исполнить. Если задача говорит «исполните изображение» — это Piet; если «найдите скрытое» — скорее стего.

## Что мы теперь знаем

По-простому:

1. Piet — программа-картинка из цветных блоков (codels).
2. Смена цвета между блоками (Δhue, Δlightness) задаёт операцию.
3. Число для `push` = размер блока в пикселях-«коделах».
4. Белый — свободное движение, чёрный — поворот; за это отвечают DP и CC.
5. Запускается одной командой `npiet art.png`; числа-вывод собираются в байты.

## На что смотреть дальше

- **Палитра как подсказка.** Блоки чистого цвета, ограниченный набор, прямоугольная структура — почти наверняка Piet. Градиенты и фото — нет.
- **Не портите оригинал.** Не открывайте PNG в редакторе и не сохраняйте повторно: сжатие меняет цвета, и программа «ломается».
- **Стек пуст / деление на ноль.** `npiet` скажет об этом прямо — обычно где-то не хватает `push`.
- **Бесконечный цикл на белом.** Проверьте `-t`: если исполнитель крутится по белым блокам, возможно, нужен ввод.
- **`roll` — редкая команда.** Циклический сдвиг стека встречается нечасто, но забывать о нём не стоит.
