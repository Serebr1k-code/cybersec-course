## Вопрос, с которого всё начинается

Ты нашёл рабочий эксплойт под heap-задачу, запустил у себя — получил шелл. Отправляешь на удалённый сервер — падает с `malloc(): corrupted top size`. Или наоборот: райтап работает у автора, но не у тебя. Причина почти всегда одна: **разные версии glibc**. Разберём, что именно меняется между версиями и как заранее определить версию, чтобы не гадать.

## Наш пример: бинарь и чужой libc

Тебе выдали два файла:

```
$ file challenge
challenge: ELF 64-bit LSB pie executable, x86-64, dynamically linked, interpreter /lib64/ld-linux-x86-64.so.2
$ file libc.so.6
libc.so.6: ELF 64-bit LSB shared object, x86-64, version 1 (SYSV), dynamically linked
```

Бинарь **динамически слинкован** — он не тащит libc внутри, а ищет её на машине. Если сервер использует другую libc, оффсеты функций и внутренние структуры heap будут другими. Значит, первый вопрос: **какая именно версия libc у цели?**

## Шаг 1: как узнать версию glibc

Самый простой способ — попросить её саму:

```
$ ./libc.so.6
GNU C Library (Ubuntu GLIBC 2.31-0ubuntu9.9) stable release version 2.31.
```

Если запустить нельзя, версию даёт строка внутри библиотеки:

```
$ strings libc.so.6 | grep -i 'glibc 2'
GNU C Library (Ubuntu GLIBC 2.31-0ubuntu9.9) stable release version 2.31.
```

Если libc-файла нет, версию восстанавливают по оффсетам: берут известный оффсет (например, `system`) и по базе libc-database находят подходящую версию (сервис libc.rip делает это автоматически). Но чтобы понимать, **какой** оффсет смотреть, нужно знать, что между версиями меняется.

## Шаг 2: tcache появился в 2.26

До 2.26 у каждого потока был только **fastbins** — список мелких освобождённых чанков. В glibc 2.26 добавили **tcache** (thread-local cache): массив из 64 корзин, по одному односвязному списку на размер, до 7 чанков. Освобождение в tcache не проверяет соседей и не сливает чанки — поэтому tcache-атаки (poisoning, dup) стали классикой.

Ключевое отличие: до 2.26 `free()` мелкого чанка попадал в fastbin с проверкой размера; с 2.26 — в tcache почти без проверок. Эксплойт на fastbin dup в tcache-системе просто не сработает.

Посмотреть, есть ли tcache, можно по символу `tcache` в libc:

```
$ nm -D libc.so.6 | grep -i tcache
00000000001eb2c0 B tcache
```

Пусто — tcache нет (старая libc). Есть — версия ≥ 2.26.

## Шаг 3: safe-linking с 2.32

В 2.32 в tcache и fastbins добавили **safe-linking**. Раньше указатель `fd` свободного чанка хранился как есть — можно было записать туда адрес и получить аллокацию по произвольному адресу. Теперь `fd` хранится как `(адрес_чанка >> 12) XOR (реальный_указатель)`. Для подмены нужно знать адрес самого чанка (утечку heap): «просто записать адрес» уже недостаточно.

Проверить наличие safe-linking можно в дизассемблере `free`/`malloc` — ищи сдвиг `>> 12` и `xor`:

```
$ objdump -d libc.so.6 | grep -A4 '<free@@' | grep -E 'shr|xor' | head
```

Или эмпирически: в отладчике посмотри, как выглядит `fd` свободного чанка — если он похож на XOR-мусор, safe-linking включён.

## Шаг 4: хуки удалили в 2.34

Классикой был захват `__malloc_hook` / `__free_hook`: записал в hook адрес `system`, вызвал `malloc` — получил исполнение. В glibc 2.34 эти хуки **удалили**. Эксплойт через `__free_hook` на 2.34+ не соберётся даже с верными оффсетами — символа нет:

```
$ nm -D libc.so.6 | grep -E '__free_hook|__malloc_hook'
$   (пусто — хуков нет)
```

Современные техники идут через `_IO_FILE` (FSOP), `exit_funcs` или структуры tcache.

## Шаг 5: таблица изменений по версиям

| Версия | Что появилось | Что ломает |
|--------|---------------|------------|
| 2.23 | tcache ещё нет, хуки есть | — |
| 2.26 | tcache (64 корзины) | fastbin-only приёмы |
| 2.27 | tcache double-free detection | простой tcache dup |
| 2.29 | `tcache_key`, проверка top size | House of Force, часть Spirit |
| 2.32 | safe-linking (XOR fd) | «записать адрес в fd» |
| 2.34 | удаление `__malloc_hook`/`__free_hook` | хуки как цель |

Эта таблица — твой чек-лист: увидел версию, посмотрел, что она уже запретила.

## Шаг 6: как определить версию в CTF-задаче

1. Дан `libc.so.6` → `strings libc.so.6 | grep 'glibc 2'`.
2. Дан только оффсет → libc.rip / libc-database по оффсетам известных функций.
3. Есть доступ к процессу → `/proc/self/maps` (путь к libc) + `ldd --version`.
4. В отладчике → `p (char*)gnu_get_libc_version()`, если есть символы.
5. Из утечки: известный адрес символа минус оффсет = база libc; сверив с базой, найди версию.

## Шаг 7: запуск бинаря с чужой libc (patchelf)

Если задача даёт свой `libc.so.6`, а ты хочешь воспроизвести поведение локально, подмени интерпретатор и библиотеку:

```
$ cp challenge challenge_local
$ patchelf --set-interpreter ./ld-2.31.so --replace-needed libc.so.6 ./libc.so.6 challenge_local
$ ./challenge_local
```

Теперь локальный запуск использует ровно ту libc, что и сервер, и оффсеты совпадают. Без этого ты отлаживаешь не тот бинарь.

## Шаг 8: рабочий пример — от версии к технике

Дано: libc 2.31, есть UAF в tcache-чанке. Разбор:
1. Версия 2.31 → tcache есть, safe-linking **нет** (появился в 2.32), хуки **есть** (удалили в 2.34).
2. Значит, доступны: tcache poisoning (записать адрес в `fd`), захват `__free_hook`.
3. План: утечь heap, отравить tcache, получить аллокацию по `__free_hook`, записать `system`, затем `free("/bin/sh")`.

Если бы libc была 2.34, шаг 2 изменился бы: хуков нет, нужен FSOP через `_IO_2_1_stdout_` или `exit_funcs`. Тот же баг — другой эксплойт.

## Если не сработало

- Эксплойт падает на `free` → проверь версию: возможно, `tcache_key` (2.29+) ловит double-free.
- Аллокация «не туда» → возможно, safe-linking: `fd` XOR-ится, нужна утечка heap.
- `AttributeError: __free_hook` → версия 2.34+, цель надо менять.
- Локально работает, на сервере нет → почти всегда разные libc; подтяни серверную libc через patchelf.

## Частые ошибки

- Использовать оффсеты из райтапа, не сверив версию.
- Забыть, что `tcache` вмещает только 7 чанков на размер.
- Пытаться захватить hook на 2.34+.
- Путать `tcache` и `fastbin` (разные списки и проверки).

## Что мы теперь знаем

- Версия glibc определяет, какие heap-техники применимы.
- tcache — с 2.26; safe-linking — с 2.32; хуки удалены в 2.34.
- Один баг требует разных эксплойтов под разные версии.
- Версию находят по строке, по оффсетам (libc-database), из `/proc/self/maps` или из утечки.
- Для воспроизведения чужой libc есть patchelf.

## Шаг 9: tcache poisoning пошагово

Разберём самый частый приём на libc 2.31. Дано: use-after-free в чанке размера 0x40. Цель — получить аллокацию по адресу `target`.

1. Освобождаем чанк `A` — он уходит в tcache размера 0x40, и в первых 8 байтах (`A->fd`) появляется указатель на следующий свободный (или NULL).
2. Через UAF пишем в `A->fd` адрес `target`. На 2.31 safe-linking ещё нет — пишем как есть.
3. Делаем два `malloc(0x38)`: первый вернёт `A`, второй — `target`.
4. Теперь у нас есть запись по `target`. Если `target = __free_hook`, пишем туда `system`.
5. Вызываем `free()` на чанке с содержимым `"/bin/sh"` — срабатывает hook.

На 2.32 шаг 2 изменится: `A->fd` надо писать как `(A >> 12) XOR target`, то есть нужна утечка адреса `A`. Без утечки poisoning не сработает. А на 2.34 шаг 4 невозможен — хука нет, цель надо менять на FSOP.

## Шаг 10: инструменты: one_gadget и libc-database

- **one_gadget** — находит адреса в libc, вызов которых сразу даёт `execve("/bin/sh")` при выполнении условий. Удобно, когда не хочется строить ROP:

```
$ one_gadget libc.so.6
0xe3afe execve("/bin/sh", r15, r12)
constraints:
  [r15] == NULL || r15 == NULL
```

- **libc-database** — по оффсету символа находит подходящую версию libc:

```
$ ./find system 0x52210
```

Оба инструмента экономят время, но требуют точной версии libc — что возвращает нас к первому шагу урока.

## Шаг 11: разбор реального кейса

Задача: бинарь на libc 2.31, есть UAF. Разбор по шагам:
1. `strings libc.so.6 | grep glibc` → 2.31.
2. Символы `__free_hook` присутствуют, `tcache` есть → доступны poisoning и hook.
3. Утечка: печатаем адрес чанка через `%p` в приложении → получаем heap-базу.
4. Отравляем tcache, получаем аллокацию по `__free_hook`.
5. `one_gadget` подбирает подходящий адрес; пишем его в hook.
6. Триггерим `free` → шелл.

Каждый шаг здесь зависит от версии. Смени версию — и шаги 2, 4, 5 переписываются.

## Шаг 12: что читать в отладчике

```
pwndbg> tcachebins
pwndbg> x/8gx <chunk_addr>
pwndbg> p &__free_hook
```

`tcachebins` покажет содержимое tcache и декодированные указатели (pwndbg сам разворачивает safe-linking). Это быстрый способ убедиться, что poisoning сработал, ещё до запуска полного эксплойта.

- **CTF pwn**: выбор heap-техники под конкретную libc.
- **Эксплуатация**: понять, почему эксплойт не переносится.
- **Реверс**: сопоставить дизассемблер `free` с версией.
