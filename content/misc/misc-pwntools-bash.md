## Зачем автоматизировать CTF-задачи

Многие задачи дают интерактивный сервис или поток данных, и вручную их решать бессмысленно: ответ нужно дать за секунды, а вопросов сотни. Здесь на помощь приходит автоматизация — комбинация `pwntools` для сетевого взаимодействия и shell-однострочников для подготовки данных. Цель модуля — научиться быстро превращать ручное взаимодействие в воспроизводимый скрипт.

## pwntools: базовый каркас

`pwntools` — стандарт де-факто для работы с CTF-сервисами. Минимальный пример:

```python
from pwn import *
context.log_level = 'error'

io = remote('host', 1337)      # или process(['./server']) локально
io.recvuntil(b'>> ')
io.sendline(b'hello')
print(io.recvline())
io.close()
```

Ключевые функции: `recvuntil(delim)` ждёт разделитель, `recvline()` читает строку, `recv(n)` — n байт, `sendline(data)` отправляет с переводом строки, `interactive()` отдаёт управление вам. Всегда задавайте `timeout` в `recv*`, чтобы скрипт не висел.

## Разбор ответа и принятие решений

Реальный сервис отвечает в нестандартном формате, поэтому нужен парсер:

```python
from pwn import *
import re
io = remote('host', 1337)
for _ in range(100):
    line = io.recvline(timeout=5)
    if b'FLAG' in line:
        print(line.decode(errors='replace')); break
    nums = list(map(int, re.findall(rb'\d+', line)))
    if len(nums) == 2:
        io.sendline(str(nums[0] + nums[1]).encode())
io.close()
```

Такой цикл «прочитал — распарсил — ответил» — основа решения потоковых задач. Отлаживайте его, печатая сырые строки сервиса.

## Локальная отладка и attach к процессу

Если сервис приложен к задаче, запускайте его локально и хукайте отладчиком:

```python
io = process(['./chall'])
# в другом терминале
# gdb -p $(pgrep chall)
```

Для чистых сетевых задач удобно поднимать `socat TCP-LISTEN:1337,reuseaddr,fork EXEC:./chall` и ходить к нему как к настоящему серверу.

## Shell-однострочники, которые спасают

```bash
# извлечь все числа из потока и просуммировать
grep -oE '[0-9]+' data | paste -sd+ | bc

# top-10 самых частых строк
sort file | uniq -c | sort -rn | head

# извлечь все IPv4
grep -oE '([0-9]{1,3}\.){3}[0-9]{1,3}' log | sort -u

# декодировать hex в бинарь
xxd -r -p hex.txt out.bin

# base64 из файла
base64 -d blob.txt > out.bin
```

`paste -sd+` склеивает строки в сумму для `bc` — классический приём для «сложи все числа». `uniq -c | sort -rn` даёт частоты в одну строку.

## Конвейеры: соединяем инструменты

Сила Unix — в конвейерах. Пример: найти в логах подозрительные IP и посчитать их:

```bash
awk '{print $1}' access.log \
  | sort | uniq -c | sort -rn \
  | awk '$1 > 1000 {print $2}'
```

Здесь `awk` вырезает первое поле, `sort|uniq -c` считает повторы, второй `awk` фильтрует частые. Такие цепочки решают задачи «статистики по логу» за секунды.

## Передача бинарных данных

Когда сервис ждёт не текст, а бинарный пакет:

```python
from pwn import *
io = remote('host', 1337)
payload = p32(0xdeadbeef) + b'A'*16
io.send(payload)          # без перевода строки
```

`p32/p64` упаковывают числа в little-endian, `u32/u64` — распаковывают. Для big-endian используйте `context.endian = 'big'`.

## Типичные ошибки и подводные камни

- **Нет `timeout`** → скрипт зависает на `recv`, если сервис молчит.
- **`sendline` вместо `send`** → лишний `\n` ломает бинарный протокол.
- **Неверная кодировка** при печати ответа → используйте `errors='replace'`.
- **Гонка с таймаутом сервиса** → оптимизируйте парсинг, предвычисляйте.
- **Игнорирование приглашения** → используйте `recvuntil` по приглашению, а не фиксированное число байт.
- **Хрупкий regex** → привязывайте к формату, тестируйте на сырых ответах.
- **Потеря соединения** → оборачивайте цикл в `try/except EOFError` и переподключайтесь при необходимости.

## Отладка автоматизации

Печатайте всё, что приходит от сервиса, в сыром виде: `print(repr(line))`. Сохраняйте лог взаимодействия в файл, чтобы потом воспроизвести. Для локального процесса запускайте с `context.log_level='debug'`, чтобы видеть каждый `send`/`recv`.

## Что дальше / решение

Алгоритм автоматизации: запустите сервис (или подключитесь), вручную пройдите один цикл и запишите точный формат запроса/ответа, затем переведите это в pwntools-скрипт с таймаутами и парсером, прогоните локально и только потом — на удалённом хосте. Shell-однострочники держите под рукой для подготовки и постобработки данных. Комбинация «pwntools для интерактива + Unix-конвейеры для данных» закрывает подавляющее большинство задач на автоматизацию.

## Как организовать скрипт, чтобы он не сломался на соревновании

Автоматизация на CTF живёт по своим законам: времени мало, сервис капризный, а ошибка стоит очков. Поэтому пишите скрипт так, чтобы он был устойчив к неожиданностям. Первое правило — никогда не полагаться на фиксированное число байт в ответе: используйте маркеры (`recvuntil`) и таймауты. Второе — оборачивайте основной цикл в обработку исключений и при разрыве соединения либо переподключайтесь, либо сохраняйте накопленное состояние. Третье — логируйте сырые ответы сервиса, потому что именно в них чаще всего спрятан намёк на формат следующего вопроса.

Отдельно продумайте, что делать, если сервис отвечает медленнее вашего парсера. Если вы читаете строку, а сервис ещё формирует ответ, вы получите пустую строку и собьёте логику. Решение — читать до приглашения или до ожидаемого маркера, а не «одну строку». И всегда держите рядом ручной `nc`-сеанс: иногда полезно посмотреть на живой диалог глазами, чтобы понять, где ломается автоматизация.

## Воспроизводимость и повторные запуски

Хороший CTF-скрипт можно запустить повторно и получить тот же результат. Для этого избегайте скрытого состояния: не храните промежуточные данные только в памяти между запусками, а пишите их в файл. Если сервис выдаёт случайные числа при каждом подключении, зафиксируйте вход в лог и воспроизводите локально. Так вы сможете отлаживать логику без риска исчерпать лимит попыток на реальном сервисе. Полезно также параметризовать хост и порт через аргументы командной строки — тогда один и тот же скрипт работает и локально, и против удалённого сервиса.

## Что дальше / решение

Итог по автоматизации: стройте скрипты на маркерах и таймаутах, а не на фиксированных смещениях; обрабатывайте разрывы соединения; логируйте сырые ответы; параметризуйте хост/порт и сохраняйте состояние на диск. Комбинируйте pwntools для интерактива с Unix-конвейерами для подготовки и постобработки данных. Натренировавшись переводить ручной диалог в воспроизводимый скрипт за пару минут, вы будете стабильно забирать целый класс задач, где решает не хитрость, а скорость и аккуратность автоматизации.
