## Вопрос, с которого всё начинается

Задача даёт сервис, который задаёт тебе сто арифметических вопросов подряд и выдаёт флаг, только если ты ответишь на все за пару секунд. Вручную считать и печатать ответы — безнадёжно: пока ты вводишь третий ответ, сервис уже закрыл соединение. Такие задачи решаются только **автоматизацией**: скрипт подключается, читает вопрос, считает, отправляет ответ — и так сто раз.

В этом уроке мы автоматизируем именно такой сервис двумя способами: через библиотеку **pwntools** (для интерактивных сетевых задач) и через **bash-конвейеры** (для подготовки и обработки данных).

## Наш пример: сервис mathbot

Вот упрощённый сервис, с которым мы будем работать (он же — типичная CTF-задача):

```python
import random, sys
random.seed(1337)
print("welcome to mathbot", flush=True)
for i in range(5):
    a = random.randint(1, 100); b = random.randint(1, 100)
    print(f"{a} + {b} = ?", flush=True)
    ans = sys.stdin.readline().strip()
    if ans != str(a + b):
        print("wrong", flush=True); sys.exit(1)
print("FLAG{m4thb0t_aut0m4t3d}", flush=True)
```

Он печатает приглашение, задаёт `a + b = ?`, читает ответ и после пяти правильных ответов выдаёт флаг. В реальной задаче вопросов сто, а соединение — по сети, но принцип тот же.

## Шаг 1: подключаемся через pwntools

`pwntools` — стандарт для работы с CTF-сервисами. Он умеет одинаково работать и с локальным процессом (`process`), и с удалённым сервером (`remote`), так что скрипт легко отладить локально:

```python
from pwn import *
context.log_level = 'error'
io = process(['python3', 'chall.py'])   # или remote('host', 1337)
```

`process` запускает программу локально и подключает к её вводу/выводу; `remote` делает то же по TCP. Дальше разница не важна — функции чтения и записи одни и те же.

## Шаг 2: цикл «прочитал — посчитал — ответил»

Сердце автоматизации — цикл. Читаем до маркера `= ?`, вытаскиваем числа регуляркой, складываем, отправляем ответ:

```python
from pwn import *
import re
context.log_level = 'error'
io = process(['python3', 'chall.py'])
for _ in range(5):
    line = io.recvuntil(b'= ?')            # читать до маркера включительно
    nums = list(map(int, re.findall(rb'\d+', line)))
    io.sendline(str(nums[0] + nums[1]).encode())
print(io.recvall(timeout=5).decode())
io.close()
```

```
FLAG{m4thb0t_aut0m4t3d}
```

Разберём функции:

- `recvuntil(b'= ?')` — читает от сервиса всё **до** маркера `= ?` включительно. Не «фиксированное число байт», а именно до маркера — это устойчиво к тому, что числа разной длины.
- `recvline()` — читает одну строку; `recv(n)` — ровно `n` байт; `recvall()` — всё до закрытия соединения.
- `sendline(data)` — отправляет данные **с переводом строки**; `send(data)` — без него (для бинарных протоколов).
- `context.log_level = 'error'` — глушит лишний вывод pwntools.

Главный урок: привязывайся к **маркерам**, а не к смещениям. Сервис может ответить чуть иначе — маркер `= ?` спасёт, а «прочитать 20 байт» сломается.

## Шаг 3: всегда ставь таймауты

Если сервис замолчит, скрипт без таймаута зависнет навсегда. Поэтому у каждой функции чтения есть параметр `timeout`, а цикл оборачивают в обработку разрыва:

```python
try:
    line = io.recvline(timeout=5)
except EOFError:
    print("connection closed")
```

Правило простое: любой `recv` без таймаута — потенциальный «висяк» на соревновании.

## Шаг 4: bash-конвейеры для данных

Пока pwntools рулит интерактивом, подготовку и постобработку данных удобнее делать bash-однострочниками. Пара приёмов, которые закрывают половину misc-задач:

```
$ printf '3\n7\n11\n' > nums.txt
$ grep -oE '[0-9]+' nums.txt | paste -sd+ | bc
21
```

`grep -oE '[0-9]+'` вытаскивает все числа, `paste -sd+` склеивает их через `+` в одну строку `3+7+11`, а `bc` считает. Так «сложи все числа из файла» решается одной строкой.

Частоты — второй классический приём:

```
$ printf 'apple\nbanana\napple\ncherry\nbanana\napple\n' | sort | uniq -c | sort -rn
      3 apple
      2 banana
      1 cherry
```

`sort` группирует одинаковые строки рядом, `uniq -c` считает повторы, `sort -rn` ставит самые частые вверх.

## Шаг 5: разбор структурированных данных

Если сервис или лог отдаёт JSON, вместо `grep` берут `jq` — он понимает структуру, а не просто текст. Например, вытащить одно поле из массива объектов:

```
$ echo '[{"ip":"10.0.0.5"},{"ip":"10.0.0.7"}]' | jq -r '.[].ip'
10.0.0.5
10.0.0.7
```

А для бинарных данных пригодится `xxd`:

```
$ xxd -r -p hex.txt out.bin     # hex-текст -> бинарный файл
$ base64 -d blob.txt > out.bin  # base64 -> бинарный файл
```

В самом pwntools для упаковки чисел в байты есть `p32`/`p64` (little-endian) и обратные `u32`/`u64`. Если сервис ждёт бинарный пакет, а не текст, отправляй его через `send`, а не `sendline` — лишний перевод строки сломает протокол:

```python
payload = p32(0xdeadbeef) + b'A' * 16
io.send(payload)
```

## Шаг 6: отладка и воспроизводимость

Пиши скрипт так, чтобы его можно было перезапустить и получить тот же результат. Начни с локального процесса (`process`) — там можно включить `context.log_level = 'debug'` и видеть каждый `send`/`recv`. Когда логика работает локально, замени `process` на `remote` — и тот же код пойдёт против сервера.

Если задача даёт бинарник, а не сервис, его удобно обернуть в «псевдосервер» через `socat`, чтобы ходить к нему по TCP как к настоящему:

```
$ socat TCP-LISTEN:1337,reuseaddr,fork EXEC:./chall
```

Так ты отлаживаешь сетевой сценарий, не рискуя исчерпать лимит попыток на реальном сервисе. Хост и порт лучше передавать аргументами командной строки — тогда один скрипт работает и локально, и удалённо. И держи рядом ручной `nc`-сеанс: иногда полезно посмотреть на живой диалог глазами, чтобы понять, где именно ломается автоматизация.

## Что мы теперь знаем

1. `pwntools` одинаково работает с локальным процессом и удалённым сервером.
2. Цикл автоматизации: `recvuntil(маркер)` → парсинг → `sendline(ответ)`.
3. Всегда привязывайся к маркерам и ставь таймауты — иначе скрипт зависнет.
4. bash-конвейеры (`grep`, `paste`, `bc`, `sort|uniq -c`) решают задачи обработки данных без Python.
5. `send` для бинарных данных, `sendline` для текста; `p32`/`p64` упаковывают числа.

## На что смотреть дальше

- **Нет таймаута** → скрипт висит на `recv`, если сервис молчит.
- **`sendline` вместо `send`** → лишний `\n` ломает бинарный протокол.
- **Фиксированное число байт вместо маркера** → ломается на числах разной длины.
- **Хрупкий regex** → тестируй на сырых ответах (`print(repr(line))`).
- **Потеря соединения** → оборачивай цикл в `try/except EOFError` и переподключайся.
