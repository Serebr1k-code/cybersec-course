## Вопрос, с которого всё начинается

Задача запускает твой код «в контейнере» и просит найти файл, которого вроде бы нет. Ты видишь только пустой каталог, свой процесс имеет PID 1, а сети как будто нет. Но это не виртуальная машина — это **пространства имён**: ядро показало процессу урезанную «копию» системы. Как устроена эта изоляция и где в ней щели?

## Наш пример: карта пространств имён

Посмотрим, какие пространства имён есть у процесса. Каждый процесс видит их как символические ссылки в `/proc/<pid>/ns/`:

```
$ ls -l /proc/1234/ns/
pid -> pid:[4026531836]
net -> net:[4026532000]
mnt -> mnt:[4026531841]
uts -> uts:[4026531838]
ipc -> ipc:[4026531839]
```

Число в квадратных скобках — это **inode пространства имён**: уникальный номер. Два процесса, у которых совпадает inode для `net`, находятся в одной сети. Разные числа — разные пространства.

## Шаг 1: зачем нужны пространства имён

Процесс в Linux обращается к общим ресурсам: список процессов, сетевые интерфейсы, таблица монтирований, имя хоста. Обычно эти ресурсы одни на всю систему. **Пространство имён** (namespace) — это обёртка, дающая процессу собственную «копию» такого ресурса. Процесс думает, что он один в системе, хотя на самом деле рядом работают другие. Это и есть фундамент контейнеров.

## Шаг 2: какие бывают пространства имён

Стандартные типы:

- `pid` — своя нумерация процессов; внутри контейнера твой процесс может быть PID 1.
- `net` — свои сетевые интерфейсы, маршруты, порты.
- `mnt` — своя таблица точек монтирования (свой «корень» файловой системы).
- `uts` — своё имя хоста и домен.
- `ipc` — своя очередь сообщений и разделяемая память.
- `user` — свой маппинг UID/GID: внутри ты можешь быть root, снаружи — обычный пользователь.
- `cgroup` — своё представление иерархии cgroup.
- `time` — свои смещения часов (появилось позже).

Каждый тип можно включать отдельно — в этом гибкость.

## Шаг 3: как увидеть свои пространства

Самый простой способ — посмотреть ссылки своего процесса:

```
$ readlink /proc/self/ns/net
net:[4026532000]
```

Если сравнить с другим процессом и числа совпадут — вы в одном пространстве. Это базовый приём: карта inode показывает, кто с кем «сосед».

## Шаг 4: unshare — создать новое пространство

Команда `unshare` запускает программу в новых пространствах имён:

```
$ unshare --pid --fork --mount-proc /bin/sh
# ps
  PID TTY          TIME CMD
    1 pts/0    00:00:00 sh
    2 pts/0    00:00:00 ps
```

Внутри `ps` показывает только два процесса: новый shell стал PID 1. Так создаётся изоляция вручную. Флаг `--mount-proc` перемонтирует `/proc`, чтобы он соответствовал новому пространству процессов.

## Шаг 5: nsenter — войти в чужое пространство

Если у тебя есть доступ к чужому процессу, можно «зайти» в его пространства имён:

```
$ nsenter --target 1234 --net --pid /bin/sh
```

`nsenter` берёт пространства указанного процесса и запускает в них твою команду. Это ключ и к отладке контейнеров, и к побегу: если из своего окружения ты можешь добраться до процесса, живущего в менее ограниченном пространстве, `nsenter` перенесёт тебя туда.

## Шаг 6: как из этого получается контейнер

Контейнер — это не отдельная технология, а комбинация: процесс запускают с новыми `pid`, `net`, `mnt`, `uts`, `ipc` и часто `user` namespaces, а поверх накладывают cgroups (лимиты ресурсов). Docker/containerd/podman делают ровно это. Поэтому «побег из контейнера» — это почти всегда «найти пространство имён, которое не изолировано» или «получить доступ к чужому процессу».

## Шаг 7: выход из изоляции

Типичные векторы:

- **Общее `mnt`** — если точка монтирования хоста видна внутри, ты читаешь его файлы.
- **Привилегированный контейнер** — если контейнер запущен с расширенными правами, часть пространств не изолирована.
- **`/proc/1/root`** — в чужом (хостовом) пространстве процессов это корень хоста.
- **`nsenter` в хостовый процесс** — если доступен его PID и есть права.

Понимание inode-карты подсказывает, какое именно пространство «протекает».

## Шаг 8: практический порядок

1. `readlink /proc/self/ns/*` — понять, что изолировано.
2. Сравнить inode с другими процессами — найти «соседей».
3. Проверить `/proc/<pid>/root` и точки монтирования.
4. Если есть `nsenter` и права — войти в чужое пространство.
5. Помнить про `user` namespace: root внутри ≠ root снаружи.

## Шаг 9: симлинки /proc/<pid>/ns

Пространства имён видны как символические ссылки. Проверить, в одном ли пространстве два процесса, можно сравнением inode:

```
$ readlink /proc/self/ns/net
net:[4026532000]
$ readlink /proc/1/ns/net
net:[4026532000]
```

Совпало — один и тот же сетевой namespace. Это самый быстрый способ построить карту «кто с кем сосед» без прав root.

## Шаг 10: user namespace и маппинг UID

В `user` namespace процессы получают «фальшивый» root: внутри ты UID 0, снаружи — обычный пользователь. Маппинг виден так:

```
$ cat /proc/self/uid_map
         0       1000          1
```

Это означает: UID 0 внутри = UID 1000 снаружи. Именно на этом основаны rootless-контейнеры: даже получив root внутри, ты не получаешь его на хосте.

## Шаг 11: как из этого собирается контейнер

Docker/containerd запускают процесс с новыми `pid`, `net`, `mnt`, `uts`, `ipc` и `user` namespaces, а сверху накладывают cgroups для лимитов. Флаг `--pid=host` или `--net=host` отключает соответствующую изоляцию — тогда контейнер делит пространство с хостом. Именно такие флаги и ищут при аудите.

## Шаг 12: побег через /proc/<pid>/root

Если контейнер запущен в отдельном `pid` namespace, но видит хостовые процессы (например, из-за `--pid=host` или ошибки), то `/proc/1/root` укажет на корень хоста. Через него можно читать и записывать хостовые файлы. Это классический вектор, который ловят проверкой: видно ли внутри контейнера PID 1 хоста.

## Шаг 13: чем namespace отличается от виртуальной машины

Namespace изолирует ресурсы, но **ядро остаётся общим**: уязвимость ядра пробивает все namespaces. Виртуальная машина даёт своё ядро, поэтому изоляция сильнее. Отсюда гибриды вроде Kata Containers (см. `misc-kata-containers`), которые совмещают удобство контейнера с границей гипервизора.

## Шаг 14: частые ошибки

- Считать, что root внутри контейнера — это root хоста.
- Забыть про `--pid=host`/`--net=host` при оценке изоляции.
- Путать inode пространства с PID.
- Искать побег только в одном типе namespace, забыв про `user`/`mnt`.

## Шаг 15: чек-лист

1. `readlink /proc/self/ns/*` — что изолировано.
2. Сравнить inode с хостовыми процессами.
3. Проверить `uid_map` (user namespace).
4. Проверить `/proc/1/root` и точки монтирования.
5. Если есть `nsenter` и права — войти в чужое пространство.

## Что мы теперь знаем

- Пространство имён даёт процессу свою копию системного ресурса.
- Типы: pid, net, mnt, uts, ipc, user, cgroup, time.
- Inode в `/proc/<pid>/ns/` — «номер» пространства.
- `unshare` создаёт пространства, `nsenter` входит в чужие.
- Контейнер = namespaces + cgroups.
