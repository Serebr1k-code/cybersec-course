## Вопрос, с которого всё начинается

ZK-доказательство позволяет доказать «я знаю секрет», не раскрывая секрет. Звучит непробиваемо — но в CTF такие задачи регулярно ломают. Почему? Потому что ломают не математику, а **схему**: в ней не хватает ограничения, и доказательство проходит для неверного свидетеля.

## Наш пример: схема «докажи, что знаешь квадратный корень»

```circom
pragma circom 2.0.0;
template Sqrt() {
    signal input x;      // публичный
    signal input w;      // приватный (witness)
    signal output ok;
    w * w === x;         // ограничение
    ok <== 1;
}
component main = Sqrt();
```

Мы хотим доказать, что знаем `w` такое, что `w*w = x`. Разберём, где это может сломаться.

## Шаг 1: R1CS и ограничения

ZK-схема компилируется в **R1CS** — систему ограничений вида `A·B = C` над конечным полем. Каждое `===` в Circom добавляет ограничение. Проверяющий верит доказательству, только если все ограничения выполнены.

Ключевая идея: схема **не вычисляет** функцию для проверки, а проверяет, что witness удовлетворяет ограничениям. Если ограничений не хватает, witness может быть «неправильным», но проходящим.

## Шаг 2: underconstrained схема

Главный класс багов — **underconstrained circuit**: сигнал используется, но не связан ограничением с остальными. Пример:

```circom
signal input a;
signal input b;
signal output c;
c <== a * b;      // это ограничение есть
// но a и b нигде больше не проверяются
```

Если по замыслу `a` должно быть меньше `b`, но нет ограничения сравнения — атакующий подставит любые значения. Компилятор не подскажет: он проверяет синтаксис, а не намерение.

## Шаг 3: trusted setup и токсичные отходы

Groth16 требует **trusted setup**: церемония, порождающая proving/verification keys. Если организатор сохранил секрет церемонии («toxic waste»), он может подделывать доказательства. В CTF это иногда моделируют как утечку tau.

Проверяйте: была ли церемония многосторонней, публичны ли параметры, есть ли возможность пересоздать setup.

## Шаг 4: публичные входы и привязка

Ещё один класс багов — неправильная привязка публичных входов. Если верификатор не проверяет, что публичный сигнал действительно тот, о котором идёт речь, доказательство можно переиспользовать. Пример: proof для `x=4` проходит и для `x=9`, если `x` не включён в публичные входы.

## Шаг 5: где смотреть в Circom-аудитах

Чек-лист:

| Место | Что искать |
|---|---|
| Каждый `<--` | ручное присваивание без ограничения |
| Каждый `signal` | используется ли он в ограничении |
| Диапазоны | есть ли `Num2Bits` для проверки границ |
| Сравнения | реализованы ли они ограничениями, а не кодом |
| Публичные входы | привязаны ли они к witness |

Оператор `<--` (assign) не добавляет ограничение, в отличие от `<==`. Это самый частый источник underconstraint.

## Полный прогон: обход ограничения

В задаче схема проверяет `w*w == x`, но забывает проверить, что `w` в диапазоне. Атакующий передаёт `w = p - 1` (элемент поля), и `w*w mod p` совпадает с нужным `x`:

```
$ python3 exploit.py
p = 21888242871839275222246405745257275088548364400416034343698204186575808495617
w = p - 1
check: (w*w) % p == x  -> True
flag: nto{zk_und3rc0nstr41n3d}
```

Схема «доказала» ложь, потому что проверяла равенство по модулю, а не диапазон.

## Что мы теперь знаем

- ZK-схема — система ограничений R1CS, а не вычисление.
- Underconstrained схема пропускает неверный witness.
- `<--` не добавляет ограничение, `<==` добавляет.
- Trusted setup с утечкой ломает Groth16.
- Публичные входы должны быть привязаны к доказательству.

## Как Circom компилируется в доказательство

Пайплайн такой:

1. **Компиляция схемы** (`circom`) — из `.circom` в R1CS и WASM-свидетеля.
2. **Trusted setup** (`snarkjs groth16 setup`) — генерация proving/verification keys.
3. **Генерация доказательства** (`snarkjs groth16 prove`) — на вход witness, на выход proof.
4. **Верификация** (`snarkjs groth16 verify`) — проверка proof против публичных входов.

Ошибка на любом шаге ломает безопасность. Чаще всего — на шаге 1: схема не описывает всё, что задумано.

## Классы ZK-уязвимостей

Помимо underconstraint, есть ещё несколько:

- **Missing range check.** Сигнал объявлен как число, но не проверен на диапазон. В поле всё «число», поэтому отрицательные и огромные значения проходят.
- **Wrong signal in constraint.** Ограничение ссылается не на тот сигнал — типичная опечатка, компилятор её не поймает.
- **Unused public input.** Публичный вход объявлен, но не участвует в ограничениях — доказательство от него не зависит.
- **Aliasing.** Два сигнала по факту одно значение, но схема считает их разными.

Каждый класс нужно проверять вручную, читая схему построчно.

## Мини-пример: missing range check

```circom
template Age() {
    signal input age;
    signal output ok;
    // задумано: age >= 18, но проверки нет
    ok <== 1;
}
```

Доказательство пройдёт для `age = 0` и для `age = p-1`. Нужна явная проверка через `GreaterThan`/`LessThan`, которые внутри разбивают число на биты. Именно поэтому в реальных схемах так много `Num2Bits`.

## Инструменты аудита

- `circomspect` — статический анализ Circom на типовые баги.
- `ecne` — формальная проверка underconstraint.
- `snarkjs` — работа с proof/verify.

`ecne` строит «доказательство» ложного утверждения и показывает, какие ограничения не заданы. Это ускоряет аудит в разы.

## Что такое witness и почему он приватный

**Witness** — это набор значений всех сигналов схемы, включая приватные. Доказательство доказывает: «существует witness, удовлетворяющий всем ограничениям и дающий заданные публичные выходы», не раскрывая witness. Приватность обеспечивается тем, что proof не содержит witness, а только криптографическую выжимку.

Если схема не ограничивает сигнал, witness может быть любым — и доказательство всё равно пройдёт. Это и есть суть underconstraint.

## Полный пайплайн командой

```
$ circom sqrt.circom --r1cs --wasm --sym
$ snarkjs powersoftau new bn128 12 pot12_0000.ptau
$ snarkjs groth16 setup sqrt.r1cs pot12_final.ptau sqrt.zkey
$ snarkjs zkey export verificationkey sqrt.zkey vkey.json
$ node generate_witness.js sqrt.wasm input.json witness.wtns
$ snarkjs groth16 prove sqrt.zkey witness.wtns proof.json public.json
$ snarkjs groth16 verify vkey.json public.json proof.json
OK
```

Если последняя строка `OK`, доказательство валидно. В CTF вас просят подделать witness так, чтобы `verify` вернул `OK` для ложного утверждения — это и есть обход.

## Как искать баги систематически

Читая схему, задайте вопросы к каждому сигналу:

- В каком ограничении он участвует?
- Проверен ли его диапазон?
- Используется ли он в хеше публичных входов?
- Нет ли двух сигналов, которые должны быть равны, но не связаны?

Если хотя бы один сигнал «висит» без ограничений — это баг. Инструменты (`ecne`, `circomspect`) находят такие случаи автоматически, но ручная проверка незаменима для логики.

## Связь с реальными протоколами

ZK-доказательства лежат в основе rollup-ов (zkSync, StarkNet), миксеров и приватных голосований. Ошибка в схеме такого протокола означает возможность печатать деньги из воздуха. Поэтому аудит схем — одна из самых высокооплачиваемых ниш в Web3-безопасности.

## Почему ZK-схемы так часто ломают

Математика zk-SNARK проверена десятилетиями. Схемы — нет. Их пишут люди, и ошибка в одном ограничении рушит всю гарантию. Компилятор Circom проверяет типы и синтаксис, но не «намерение». Отсюда поток уязвимостей в ZK-протоколах.

## Где чаще всего ошибаются

- Проверка диапазона (`Num2Bits`) забыта.
- Сравнение реализовано вне ограничений.
- Хеш публичных входов не включает один из них.
- `<--` использован вместо `<==`.

Каждый пункт встречался в реальных аудитах.

## Проверка привязки публичных входов

Публичный вход должен быть частью ограничений. Если `x` объявлен публичным, но не участвует в уравнениях, доказательство для `x=1` подойдёт и для `x=2`. Проверяйте, что каждый публичный сигнал «зашит» в схему.

## Что читать дальше

Пройдите туториал `circom` и напишите схему «докажи знание прообраза хеша». Затем попробуйте намеренно ослабить ограничение и покажите, как ложный witness проходит. Это закрепит понимание.

## Практический вывод

ZK ломают не в математике, а в схеме. Каждое ограничение — это утверждение о мире; забытое ограничение означает ложное утверждение, которое проходит проверку. Читая Circom, относитесь к нему как к формальной спецификации: если чего-то нет в ограничениях, этого нет и в безопасности.

## Как формально доказать отсутствие underconstraint

Инструмент `ecne` пытается построить свидетеля, который проходит ограничения, но противоречит задуманной функции. Если ему это удаётся, схема недоопределена. Это не заменяет ручной аудит, но быстро указывает на проблемные сигналы. В реальных аудитах ZK сочетают три подхода: статический анализ (`circomspect`), формальная проверка (`ecne`) и ручное чтение схемы.

## Итоговая карта рисков ZK

Запомните четыре класса: underconstraint (не хватает ограничений), missing range check (нет проверки диапазона), unbound public input (публичный вход не участвует), trusted setup leak (утечка церемонии). Первые три ломаются на уровне схемы и ловятся аудитом Circom; четвёртый — организационный. В CTF чаще всего встречается первый класс: одно забытое ограничение открывает путь к ложному доказательству.
