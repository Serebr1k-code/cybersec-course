## Python-песочница: почему это сложно

Python — мощный язык с рефлексией, и построить на нём надёжную песочницу крайне трудно. Даже если убрать `os` и `subprocess`, почти всегда остаётся путь к нативному слою через объектную модель. Именно поэтому в CTF так много задач «убеги из Python-джейла»: они учат системно мыслить про доступ к внутренностям интерпретатора. Цель модуля — освоить продвинутые приёмы: обход `eval`, аудит-хуки и выход через `ctypes`.

## Три подхода к изоляции Python

Разработчики обычно выбирают одно из:

1. **Чёрный список** — запрет `eval`, `exec`, `import`, `os`, `open`.
2. **Ограничение builtins** — пустое `__builtins__` и явный список разрешённых функций.
3. **Аудит-хуки** — `sys.addaudithook` перехватывает опасные операции (Python 3.8+).

Каждый подход обходится по-своему, и понимание этих трёх моделей — половина успеха.

## Обход чёрного списка: базовые цепочки

Отправная точка — `().__class__.__base__.__subclasses__()`. Отсюда ищут `warnings.catch_warnings` (даёт доступ к `__builtins__` через `__init__.__globals__`):

```python
[c for c in ().__class__.__base__.__subclasses__() if c.__name__=='catch_warnings'][0]().__enter__().__class__.__init__.__globals__['__builtins__']['__import__']('os').system('sh')
```

Если фильтр запрещает подстроки, собирайте имена динамически:

```python
getattr(().__class__, '__ba'+'se__')
```

или через `chr`:

```python
getattr(o, chr(95)*2+'class'+chr(95)*2)
```

## Обход пустого __builtins__

Если `__builtins__` очищен, ищите функции, которые на него ссылаются косвенно:

```python
().__class__.__base__.__subclasses__()[X].__init__.__globals__
```

Модуль `warnings`, `importlib`, `_frozen_importlib` обычно содержат доступ к настоящим builtins. Также помогает `().__class__.__mro__[1].__subclasses__()` и перебор по имени.

## ctypes: выход на нативный уровень

`ctypes` — прямой мост к libc, и он часто не заблокирован:

```python
import ctypes
libc = ctypes.CDLL(None)
libc.system(b'cat /flag')
```

Через `ctypes` можно вызвать `system`, `execve`, `open`, `read` — то есть обойти любой запрет на Python-уровне. Это самый надёжный путь, если `ctypes` доступен.

## Аудит-хуки и их обход

С Python 3.8 можно поставить хуки, которые падают при опасных операциях:

```python
import sys
def hook(event, args):
    if event in ('exec', 'compile', 'os.system', 'subprocess.Popen'):
        raise RuntimeError('blocked')
sys.addaudithook(hook)
```

Обход аудит-хуков сложен, но не невозможен: хуки нельзя удалить, однако можно найти операции, которые они не отслеживают, или атаковать сам механизм. Иногда задача в том, чтобы вообще не триггерить событие — например, использовать уже скомпилированный код или читать память через `ctypes`.

## Работа с исключениями как источник данных

Traceback содержит имена файлов, функции и локальные переменные. Иногда фильтр забывает, что исключения раскрывают путь:

```python
raise Exception(str(open('/flag').read()))
```

Если `open` доступен, но вывод фильтруется, можно «спрятать» флаг в сообщении об ошибке.

## Ограничение длины и sandbox-фреймворки

Некоторые задачи используют готовые песочницы (`RestrictedPython`, `PyPy sandbox`). RestrictedPython компилирует код и заменяет опасные конструкции; обход обычно ищет недозакрытые встроенные объекты. Изучайте, как именно строится `_getattr_`, `_write_`, `_apply_` — часто есть дыра.

## Инструменты

- **`python3`** — локальная отладка payload'ов.
- **`audit`** — включить `python -X dev` или свой хук, чтобы увидеть события.
- **`strace`** — проверить, что реально вызывается.
- **`pwn`/`ctypes`** — нативный выход.

## Типичные ошибки и подводные камни

- **Забыть про `ctypes`** — это самый короткий путь к RCE.
- **Фильтр по подстрокам** — обходится конкатенацией/`chr`.
- **Путать `eval`/`exec`/`compile`** — каждый имеет свои особенности.
- **Не смотреть traceback** — он подсказывает доступные имена.
- **Игнорировать версию Python** — аудит-хуки только с 3.8.
- **Полагать, что очищен `__builtins__`** — он доступен косвенно.
- **Забыть про `__import__`** — он часто не в списке запретов.

## Справочная таблица

## Что дальше / решение

План: определите модель изоляции (чёрный список, очищенные builtins, аудит-хуки). Для первых двух используйте цепочку `__subclasses__` → `__globals__` → `__builtins__` и обходите фильтры конкатенацией/`chr`. Если доступен `ctypes` — идите нативным путём. Для аудит-хуков ищите непокрытые операции. Всегда проверяйте payload локально и читайте traceback. Главный вывод: Python почти невозможно изолировать на уровне языка — надёжная песочница требует отдельного процесса с ограничениями ОС.

## Практический пример: аудит-хуки и что они не ловят

Разберём продвинутый сценарий. Задача использует Python 3.11 и ставит аудит-хук, который падает на событиях `exec`, `compile`, `os.system`, `subprocess.Popen`, `open`. Прямые попытки блокируются. Что остаётся. Во-первых, `ctypes` — вызов `libc.system` идёт через нативный код и часто не порождает перехватываемого события. Во-вторых, уже скомпилированный код: если вам дают возможность передать байткод или объект-функцию, выполнение происходит без события `compile`. В-третьих, некоторые операции чтения файлов не покрыты событием `open` (например, доступ через memory-mapped файлы или через `ctypes`). В-четвёртых, можно атаковать сам механизм хуков через недокументированные внутренние структуры.

```python
import ctypes
libc = ctypes.CDLL(None)
libc.system(b'cat /flag')
```

Ключевой вывод: аудит-хуки — это фильтр на события, а не песочница. Любой путь, который не генерирует покрытого события, проходит.

## Как исследовать песочницу методично

Сначала определите версию Python и включённые хуки. Затем составьте список «примитивов» и проверьте каждый: `open`, `eval`, `exec`, `compile`, `__import__`, `ctypes`, `subprocess`, `os`, `sys.modules`. Для каждого примитива отметьте, доступен ли он напрямую, косвенно (через `__globals__`) или нативно (через `ctypes`). После этого ищите путь, не покрытый хуком. Печатайте доступные модули: `print(list(sys.modules))` — иногда там остаётся `os` под другим именем.

## Частые вопросы

«Можно ли удалить аудит-хук?» — официально нет, но можно найти непокрытые операции. «А если `ctypes` убран?» — ищите другие нативные мосты: `_ctypes`, `cffi`, `mmap`. «Что если весь `sys` очищен?» — ищите ссылки на модули через объекты. «Помогает ли traceback?» — да, он раскрывает пути и имена.

## Что дальше / решение

Итог: аудит-хуки сложны, но не абсолютны. Ищите непокрытые события, используйте `ctypes` для нативного выхода и уже скомпилированный код. Исследуйте песочницу методично: примитивы → доступ → нативный путь. Помните, что настоящая изоляция Python требует отдельного процесса с ограничениями ОС, а не только языкового хука.

## Частые вопросы по Python-песочницам

«`ctypes` убран — тупик?» — ищите другие нативные мосты: `cffi`, `mmap`, `_ctypes`. «Очищен `__builtins__`?» — ищите функцию с `__globals__`. «Аудит-хуки?» — ищите непокрытые события. «Запрещены подстроки?» — конкатенация и `chr`. «Как быстро проверить?» — запустите payload локально. «Помогает ли traceback?» — да, он раскрывает имена. «Ограничение длины?» — hex/base64 + `exec`. Главное правило: Python почти невозможно изолировать на уровне языка — надёжная песочница требует отдельного процесса с ограничениями ОС.

## Расширенный чек-лист по Python-песочницам

Составьте карту доступного: `print(list(sys.modules))`, `print(__builtins__)`, проверьте `ctypes`, `subprocess`, `os`, `open`. Затем стройте дерево «цель → примитив → доступ → обход». Для обхода фильтров используйте конкатенацию, `getattr`, `chr`, hex, base64. Если всё закрыто — ищите непокрытые аудит-хуком операции и нативные мосты. Всегда проверяйте payload локально и читайте traceback как карту окружения. Помните: надёжная изоляция Python требует отдельного процесса с ограничениями ОС.
