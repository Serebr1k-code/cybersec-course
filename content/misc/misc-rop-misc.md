## Вопрос, с которого всё начинается

Стек переполняется, но **NX** включён — записать shellcode и прыгнуть на него нельзя. Значит, надо заставить программу выполнить уже существующий код в нужном порядке. Это и есть **ROP**. Разберём, как из кусочков собирается вызов `system("/bin/sh")`.

## Наш пример: вызов system через гаджеты

Цель — выполнить `system("/bin/sh")`. В 64-бит Linux первый аргумент функции передаётся в регистре `rdi`. Значит, нам нужно: положить адрес строки `"/bin/sh"` в `rdi`, затем прыгнуть на `system`. Оба действия делаются «гаджетами».

Гаджет — это короткая последовательность инструкций, заканчивающаяся `ret`. Пример:

```
0x401234: pop rdi ; ret
```

Инструкция `pop rdi` забирает значение со стека в `rdi`, а `ret` передаёт управление на следующий адрес со стека.

## Шаг 1: как строится цепочка

Переполняя буфер, мы пишем на стек:

```
[ padding ][ pop_rdi ][ &"/bin/sh" ][ system ]
```

Как это исполняется:
1. `ret` функции возвращается на `pop_rdi`.
2. `pop rdi` берёт со стека `&"/bin/sh"` → в `rdi` адрес строки.
3. `ret` уходит на `system`.
4. `system` с аргументом `rdi = "/bin/sh"` запускает шелл.

## Шаг 2: где взять гаджеты

Гаджеты ищут автоматически. В pwntools:

```python
elf = ELF('./challenge')
rop = ROP(elf)
rop.call('system', [next(elf.search(b'/bin/sh'))])
print(rop.dump())
```

Или утилитой `ROPgadget`:

```
$ ROPgadget --binary challenge | grep 'pop rdi ; ret'
0x0000000000401213 : pop rdi ; ret
```

Гаджет `pop rdi ; ret` есть почти всегда, потому что встречается в стандартных функциях (например, в `__libc_csu_init`).

## Шаг 3: обход ASLR

Если бинарь **PIE** (адреса рандомизированы), адреса гаджетов неизвестны. Тогда нужна **утечка** адреса libc или бинаря. Типично:
1. Вызвать `puts(puts@got)` — напечатать реальный адрес `puts` из GOT.
2. Вычесть оффсет `puts` в libc → получить базу libc.
3. Вернуться в `main` (или использовать `ret` для выравнивания) и на втором проходе построить финальную цепочку с известной базой.

## Шаг 4: ret2csu и большие цепочки

Когда в бинаре мало гаджетов, на помощь приходит `__libc_csu_init` — стандартный код, содержащий последовательность `pop rbx; pop rbp; pop r12..r15; ret` и `call [r12+rbx*8]`. Это позволяет вызывать функции с несколькими аргументами. Приём называется **ret2csu** и часто спасает маленькие бинари.

## Шаг 5: выравнивание стека

Иногда `system` падает внутри `movaps` из-за невыровненного стека. Решение — вставить лишний `ret`-гаджет перед вызовом, сдвинув стек на 8 байт. Это классическая «trick: add one ret».

## Шаг 6: таблица приёмов

| Приём | Когда нужен |
|-------|-------------|
| pop rdi; ret | первый аргумент |
| ret2csu | много аргументов / мало гаджетов |
| ret2libc | есть libc-утечка |
| ret2dlresolve | нет утечки libc |
| stack pivot | мало места на стеке |

## Если не сработало

- Падение на `movaps` → добавь лишний `ret` для выравнивания.
- Адреса «не те» → PIE/ASLR: нужна утечка.
- Цепочка обрывается → проверь, что гаджеты заканчиваются именно `ret`.
- `system` не запускается → проверь, что в `rdi` реально адрес `"/bin/sh"`.

## Частые ошибки

- Забыть выравнивание стека.
- Использовать адреса из локального запуска на удалённом сервере (другая libc).
- Путать 32-бит (аргументы на стеке) и 64-бит (регистры).

## Что мы теперь знаем

- ROP переиспользует существующие гаджеты, заканчивающиеся `ret`.
- `pop rdi; ret` кладёт первый аргумент в 64-бит.
- ASLR обходится утечкой (например, через `puts@got`).
- ret2csu расширяет возможности на маленьких бинарях.

## Шаг 7: поиск гаджетов без инструментов

Иногда `ROPgadget`/pwntools недоступны (или гаджет нужен «на глаз»). Тогда гаджеты ищут прямо в дизассемблере: `objdump -d challenge | grep -B2 -A2 'ret'`. Последовательность `pop rdi` непосредственно перед `ret` даёт нужный гаджет. Особенно богат гаджетами `__libc_csu_init` — там есть и `pop rbx/rbp/r12..r15`, и `call qword ptr [r12+rbx*8]`, что покрывает вызов функций с аргументами.

Полезно помнить байтовые коды: `pop rdi` = `0x5f`, `ret` = `0xc3`. Значит, байты `5f c3` в любом месте кода — уже гаджет. Такие «случайные» гаджеты (внутри других инструкций) часто находятся именно побайтовым поиском, а не по строкам дизассемблера.

## Шаг 8: JOP и COOP кратко

Если ret-гаджетов нет (например, включён CET/Shadow Stack), на смену приходит **JOP** (Jump-Oriented Programming): цепочка из гаджетов, заканчивающихся `jmp`, а не `ret`. Управление потоком идёт через регистры-диспетчеры. Ещё дальше — **COOP** (Counterfeit Object-Oriented Programming), где переиспользуются виртуальные методы C++-объектов. Эти техники сложнее, но показывают, что идея «переиспользуй существующий код» не ограничена `ret`.

## Шаг 9: практический пример полного эксплойта

Полный сценарий на pwntools:
1. `p = process('./challenge')` (или `remote`).
2. Утечка: `p.recvline()` даёт адрес, считаешь базу libc.
3. Строишь `ROP(elf)`, добавляешь `pop rdi; ret`, адрес `"/bin/sh"`, `system`.
4. Формируешь payload: `b'A'*offset + rop.chain()`.
5. Отправляешь, получаешь интерактивный шелл (`p.interactive()`).

Ключевые точки отказа: неверный оффсет до возвратного адреса, невыровненный стек, неправильная база libc. Все три диагностируются в отладчике: посмотри, куда именно прыгнул `ret`.

## Шаг 10: как читать вывод ROPgadget

```
$ ROPgadget --binary challenge | grep -E 'pop rdi ; ret|pop rsi ; ret'
0x401213 : pop rdi ; ret
0x401215 : pop rsi ; pop r15 ; ret
```

Из вывода бери гаджеты, заканчивающиеся ровно на `ret` (без `jmp`/`call` посередине). Для второго аргумента `pop rsi` часто идёт в паре с лишним `pop` — «мусорное» значение всё равно нужно положить на стек. Чем внимательнее читаешь вывод, тем короче и надёжнее цепочка.
