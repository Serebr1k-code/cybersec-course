## Вопрос, с которого всё начинается

ROP с `ret2libc` требует утечки адреса libc. А если утечки нет вообще? Тогда на помощь приходит **ret2dlresolve** — приём, который заставляет динамический линкер разрешить символ `system` «с нуля», используя наши поддельные структуры. Разберём, как это устроено.

## Наш пример: ленивая линковка

Когда программа впервые вызывает функцию из libc (например, `printf`), она попадает в **PLT**-заглушку, которая прыгает через **GOT**. При первой вызове GOT ещё не заполнен, и управление уходит в **резолвер** динамического линкера (`_dl_runtime_resolve`), который по индексу релокации находит символ в libc и записывает его адрес в GOT.

Идея ret2dlresolve: подсунуть резолверу **свой** индекс, указывающий на поддельные структуры, в которых описан символ `system`. Резолвер добросовестно найдёт `system` и вызовет его.

## Шаг 1: три структуры

Резолвер использует:
- `Elf64_Rela` — запись релокации (где искать символ);
- `Elf64_Sym` — описание символа (имя, тип);
- строку с именем (`"system"`).

Мы размещаем их в памяти, которую контролируем (например, в `.bss` или на стеке), и подделываем индекс так, чтобы резолвер читал именно их.

## Шаг 2: как это делает pwntools

Строить это вручную долго, поэтому pwntools даёт `Ret2dlresolvePayload`:

```python
from pwn import *
elf = ELF('./challenge')
rop = ROP(elf)
dlresolve = Ret2dlresolvePayload(elf, symbol='system', args=['/bin/sh'])
rop.read(0, dlresolve.data_addr)          # читаем наши структуры
rop.ret2dlresolve(dlresolve)              # прыгаем в резолвер
payload = fit({offset: rop.chain(), dlresolve.data_addr: dlresolve.payload})
```

Здесь мы сначала записываем подготовленный payload (структуры + строка) в известный адрес, затем вызываем резолвер.

## Шаг 3: почему это обходит ASLR

Нам не нужно знать адрес `system` — его находит линкер во время выполнения. Мы используем только адреса, которые знаем без утечки: адрес `.bss`, адрес PLT-заглушки и адрес функции чтения. Поэтому ASLR не мешает.

## Шаг 4: ограничения

- Нужен примитив записи в известный адрес (часто `read`/`gets`).
- Бинарь должен использовать **ленивую** линковку (не `-Wl,-z,now`), иначе GOT заполнен заранее и резолвер не вызывается.
- Нужен гаджет для вызова PLT-заглушки и возврата.

## Шаг 5: таблица условий

| Условие | Зачем |
|---------|-------|
| lazy binding | резолвер вызывается при первом обращении |
| известный адрес записи | куда положить структуры |
| гаджет вызова PLT | передать управление резолверу |
| строка "system" | имя символа |

## Шаг 6: отладка

В `gdb` поставь breakpoint на `_dl_runtime_resolve` и посмотри аргументы: индекс релокации и адрес структур. Если индекс «не твой» — значит, подделка не попала в нужное место. pwndbg умеет показывать GOT/PLT (`got`, `plt`).

## Если не сработало

- Резолвер не вызывается → включён Full RELRO / `-z now`; техника неприменима.
- Падение в резолвере → неверные `r_offset`/индекс в поддельных структурах.
- Символ не находится → проверь имя строки и её выравнивание.
- Нет места для записи → используй `.bss` вместо стека.

## Частые ошибки

- Путать `ret2dlresolve` и `ret2libc`.
- Забыть, что при Full RELRO техника не работает.
- Ошибиться в выравнивании поддельных структур.

## Что мы теперь знаем

- Динамический линкер разрешает символы лениво, при первом вызове.
- ret2dlresolve подсовывает резолверу поддельные reloc/sym/имя.
- Техника не требует утечки libc и обходит ASLR.
- Требуется lazy binding и примитив записи в известный адрес.

## Шаг 7: разбор структур вручную

Полезно один раз собрать ret2dlresolve без pwntools, чтобы понять суть. Тебе нужны три структуры в контролируемой памяти:

- `Elf64_Sym` — описывает символ: `st_name` (смещение имени), `st_info` (тип), `st_other`, `st_shndx`.
- `Elf64_Rela` — описывает релокацию: `r_offset` (куда писать), `r_info` (индекс символа + тип), `r_addend`.
- строка `"system\0"` — имя символа.

`r_info` кодирует индекс символа в старших битах: `r_info = (sym_index << 32) | R_X86_64_JUMP_SLOT`. Резолвер прочитает `r_info`, найдёт по индексу твой `Elf64_Sym`, по `st_name` — строку `"system"`, найдёт адрес в libc и запишет по `r_offset`. Всё, что от тебя нужно — чтобы эти структуры лежали по адресам, которые резолвер вычислит из индекса.

## Шаг 8: полный пример pwntools

```python
from pwn import *
elf = ELF('./challenge')
rop = ROP(elf)
dlresolve = Ret2dlresolvePayload(elf, symbol='system', args=['/bin/sh'])
rop.read(0, dlresolve.data_addr)
rop.ret2dlresolve(dlresolve)
raw = b'A' * offset + rop.chain()
io.sendline(raw)
io.sendline(dlresolve.payload)   # записываем структуры
io.interactive()
```

Здесь `rop.read` читает наш payload (структуры) в известный адрес, а `rop.ret2dlresolve` добавляет вызов PLT-заглушки, ведущей в резолвер. Обрати внимание: мы **не знаем** адрес `system` — его находит линкер.

## Шаг 9: отладка резолвера

```
pwndbg> b _dl_runtime_resolve
pwndbg> c
pwndbg> x/4gx $rsp
pwndbg> got
```

При остановке посмотри, какой индекс релокации передаётся и куда указывает `r_offset`. `got` покажет текущее содержимое GOT. Если резолвер не вызывается вообще — вероятно, включён Full RELRO (`-z now`), и техника неприменима: проверь `checksec` и флаги линковки.
