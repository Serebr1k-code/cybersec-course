## Вопрос, с которого всё начинается

Задача даёт файл `demo.ko` — «загружаемый модуль ядра». Грузить его в реальную систему нельзя: это ядро, ошибка стоит перезагрузки. Но чтобы решить задачу, загружать и не нужно: у модуля есть **метаданные** — паспорт, который лежит прямо в файле и читается обычными инструментами. Как понять, что делает модуль, не запуская его?

## Наш пример: demo.ko

Начнём с того, что скажет сама система о файле — но только о файле, не о ядре. `modinfo` читает метаданные из секции `.modinfo` внутри `.ko` и печатает их списком «поле: значение».

```
$ modinfo demo.ko
filename:       /lib/modules/6.1.0/demo.ko
license:        GPL
author:         ctf-lab
description:    demo driver <base64>
name:           demo
vermagic:       6.1.0 SMP mod_unload
```

Строка `description` выглядит как обычный текст, но в конце — длинная строка из букв и цифр. Это base64, и мы вернёмся к нему. Сначала разберёмся, что вообще такое модуль.

## Шаг 1: что такое модуль ядра

Ядро — это программа, которая управляет железом и процессами. Добавлять в неё код «на ходу» можно с помощью **загружаемых модулей**: это отдельные файлы с расширением `.ko` (kernel object). Модуль — не обычная программа: у него нет `main`, он не запускается сам. Ядро загружает его в своё адресное пространство и вызывает функции, которые модуль экспортирует. Поэтому модуль имеет полный доступ к системе — и именно поэтому его анализ важен и для защиты, и в CTF.

## Шаг 2: modinfo — паспорт модуля

`modinfo` — первый инструмент. Он не загружает модуль, а только читает служебные поля. Каждое поле отвечает на вопрос:

- `filename` — путь к файлу (в лабе его подставляют искусственно).
- `license` — лицензия. `GPL` важна: ядро разрешает модулям без GPL использовать лишь часть символов.
- `author` / `description` — свободный текст автора; сюда часто прячут метку.
- `name` — внутреннее имя модуля.
- `vermagic` — «отпечаток» версии ядра. Если он не совпадает с текущим ядром, модуль не загрузится.

Метаданные — это те же строки, что мы видим в `description`, только без загрузки.

## Шаг 3: lsmod, insmod, rmmod, modprobe

Если бы мы работали на живой машине, порядок был бы таким:

```
$ lsmod
Module                  Size  Used by
demo                   16384  0
```

`lsmod` показывает уже загруженные модули. `insmod demo.ko` загружает конкретный файл, `rmmod demo` выгружает, а `modprobe demo` ищет модуль по имени и сам подтягивает зависимости. Разница важна: `insmod` работает с файлом и не решает зависимости, `modprobe` — с именем и решает. В CTF и в анализе чаще всего модуль **не грузят**, а разбирают.

## Шаг 4: точки входа init и exit

У модуля есть две функции, которые ядро вызывает:

- `init` (часто помечается `__init`) — вызывается при загрузке; если вернёт ошибку, загрузка отменяется;
- `exit` (часто `__exit`) — вызывается при выгрузке.

В исходнике это `module_init(demo_init)` и `module_exit(demo_exit)`. В скомпилированном `.ko` этим функциям соответствуют символы, которые видно через `strings` или таблицу символов. Поняв, что делает `init`, ты понимаешь, что модуль настраивает при загрузке.

## Шаг 5: параметры модуля

Модуль может принимать параметры во время загрузки. В исходнике их объявляют через `module_param(name, type, perm)`. В метаданных они появляются как строки `parm: count:int`. Это важно: иногда «вредоносное» поведение включается только при определённом параметре, и по метаданным видно, какие входные точки у модуля есть.

## Шаг 6: экспорт символов и зависимости

Модуль может **экспортировать** свои функции для других модулей (`EXPORT_SYMBOL`) и **использовать** чужие. В `modinfo` это поле `depends:` — список модулей, без которых наш не заработает. Пустое `depends` означает самодостаточность. Цепочка зависимостей — это граф, и он тоже читается без загрузки.

## Шаг 7: разбор .ko без загрузки

`.ko` — это обычный ELF-файл (часто сжатый). Поэтому к нему применимы привычные приёмы: `file` скажет тип, `strings` вытащит текст, `xxd` покажет байты, `readelf`/`objdump` покажут секции и символы. Ключевая секция — `.modinfo`, откуда `modinfo` и берёт поля. Если метка закодирована, её раскодируют так же, как любой base64.

## Шаг 8: безопасность и подписи

Ядро умеет требовать **подписанные** модули (Secure Boot + модульные подписи). Неподписанный модуль не загрузится, если включён режим проверки. Для аналитика это значит: подозрительный модуль можно разобрать, но не обязательно получится загрузить. И наоборот, руткиты стремятся обойти проверку подписи — это отдельная тема.

## Шаг 9: практический порядок разбора

1. `file demo.ko` — понять формат.
2. `modinfo demo.ko` (или `strings`) — прочитать метаданные.
3. Найти `init`/`exit` и параметры.
4. Посмотреть `depends` — от кого зависит.
5. Если поле похоже на base64/hex — раскодировать.

## Шаг 10: секция .modinfo изнутри

`modinfo` — не магия, а удобная обёртка. Поля модуля лежат в ELF-секции `.modinfo` строками вида `ключ=значение`. Посмотреть их напрямую можно так:

```
$ readelf -p .modinfo demo.ko
String dump of section '.modinfo':
  [     0]  license=GPL
  [     c]  description=demo driver
  [    24]  depends=
```

Тот же результат даёт `strings demo.ko`. Значит, для разбора модуля достаточно уметь читать ELF-секции: если поле нестандартное, `strings` его всё равно покажет.

## Шаг 11: сжатый .ko

Модули часто компилируют со сжатием — тогда `file` скажет «Zstandard compressed data» или «gzip compressed data». Прежде чем разбирать, обёртку снимают:

```
$ file demo.ko
demo.ko: Zstandard compressed data (v0.8+)
$ zstd -d demo.ko -o demo.raw.ko
```

Внутри окажется обычный ELF. Это типичная «первая ступень» задачи: понять, что файл сжат, и распаковать его.

## Шаг 12: сравнение с userspace-библиотекой

Модуль похож на динамическую библиотеку (`.so`): тоже формат ELF, тоже экспортирует символы. Разница — контекст загрузки. `.so` грузит загрузчик пользовательского пространства, а `.ko` — ядро, и оно даёт модулю доступ ко всей памяти без привычных защит. Поэтому анализ модуля — это анализ кода с максимальными привилегиями.

## Шаг 13: что именно проверяет подпись

Подпись модуля проверяет **целостность и источник**: файл не изменён и подписан доверенным ключом. В режиме проверки ядро откажется грузить неподписанный модуль. Для аналитика это удобно: подозрительный `.ko` можно спокойно разбирать статически, не рискуя загрузкой. Для защитника обход подписи — отдельная, серьёзная атака.

## Шаг 14: разбор примера целиком

Пусть в поле `author` лежит длинная строка. Порядок действий:

```
$ modinfo demo.ko | grep author
author:         Y3RmLWxhYg==
$ modinfo demo.ko | grep author | cut -d: -f2 | base64 -d
ctf-lab
```

Если бы это был hex, вместо `base64 -d` применили бы `xxd -r -p`. Метка достаётся без загрузки модуля.

## Шаг 15: частые ошибки

- Пытаться `insmod` там, где это опасно или невозможно (нет прав/подписи).
- Искать метку в тексте, хотя она в метаданных.
- Забыть, что поле может быть сжато или закодировано.
- Путать `depends` (от кого зависит наш модуль) с `Used by` из `lsmod` (кто зависит от него).

## Шаг 16: чек-лист по модулю

1. `file demo.ko` — формат: ELF или сжат?
2. Если сжат — распаковать.
3. `modinfo` или `readelf -p .modinfo` — поля.
4. Найти `init`/`exit`, параметры (`parm`), `depends`.
5. Декодировать подозрительные поля (base64/hex).

## Что мы теперь знаем

- Модуль ядра — файл `.ko`, который ядро загружает в своё пространство.
- `modinfo` читает паспорт модуля без загрузки.
- `init`/`exit` — точки входа; `module_param` задаёт параметры.
- `depends` описывает зависимости, `EXPORT_SYMBOL` — экспорт.
- `.ko` — ELF, поэтому разбирается `strings`, `xxd`, `readelf`.
