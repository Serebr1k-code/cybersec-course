## Вопрос, с которого всё начинается

Ты перехватил трафик gRPC или нашёл файл без расширения. `strings` показывает обрывки, но структура не читается. Скорее всего, это **Protobuf** — бинарный формат Google, на котором работают gRPC, многие API и мобильные приложения. Хорошая новость: его можно разобрать без схемы, если понимать varint.

## Наш пример: загадочный бинарник

```
$ file data.bin
data.bin: data
$ xxd -l 32 data.bin
00000000: 08 96 01 12 07 74 65 73 74 69 6e 67 1a 03 61 62  .....testin g..ab
00000010: 63                                            c
```

Разберём эти байты вручную — и увидим осмысленные поля.

## Шаг 1: varint — числа переменной длины

**Varint** кодирует целое так: каждый байт несёт 7 бит данных и старший бит-флаг «продолжение». Младшие биты идут первыми (little-endian по группам). Число 150 = `0b10010110` кодируется как `0x96 0x01`:

```
0x96 = 1001 0110 -> 7 бит: 0010110 (0x16), флаг продолжения = 1
0x01 = 0000 0001 -> 7 бит: 0000001 (0x01), флаг = 0
склеиваем: 0000001 0010110 = 10010110 = 150
```

Один байт хранит 0–127; больше — два и более. Понимая это, вы читаете любое целое.

## Шаг 2: тег и wire-тип

Каждое поле начинается с **ключа** (key): `(field_number << 3) | wire_type`. Первый байт `0x08` = `0000 1000`: field_number = 1, wire_type = 0. Wire-типы:

| Wire | Тип |
|---|---|
| 0 | varint (int, bool, enum) |
| 1 | 64-bit (fixed64, double) |
| 2 | length-delimited (string, bytes, вложенные) |
| 5 | 32-bit (fixed32, float) |

Дальше `0x96 0x01` — varint 150. Значит, поле 1 = 150.

## Шаг 3: декодируем остаток

Следующий байт `0x12` = `0001 0010`: field 2, wire 2 (length-delimited). Дальше длина `0x07` = 7, затем 7 байт `74 65 73 74 69 6e 67` = `testing`. Итого поле 2 = "testing".

Далее `0x1a` = `0001 1010`: field 3, wire 2. Длина `0x03`, байты `61 62 63` = "abc". Поле 3 = "abc".

Итог: `{1: 150, 2: "testing", 3: "abc"}`. Мы восстановили данные без `.proto`-схемы.

## Шаг 4: почему схема не нужна для чтения

Protobuf не хранит имена полей — только номера и типы. Схема нужна для семантики (что значит поле 1), но структуру читают и без неё. Поэтому дамп Protobuf — распространённая CTF-задача, и решается она парсером wire-format.

```
$ python3 - <<'PY'
data = bytes.fromhex('089601120774657374696e671a03616263')
i = 0
while i < len(data):
    key = data[i]; i += 1
    field, wire = key >> 3, key & 7
    if wire == 0:
        val = 0; shift = 0
        while True:
            b = data[i]; i += 1
            val |= (b & 0x7f) << shift
            if not b & 0x80: break
            shift += 7
        print(field, 'varint', val)
    elif wire == 2:
        ln = data[i]; i += 1
        print(field, 'bytes', data[i:i+ln]); i += ln
PY
1 varint 150
2 bytes b'testing'
3 bytes b'abc'
```

## Шаг 5: уязвимости парсеров

Формат сам по себе безопасен, но парсеры ошибаются:

- **Переполнение длины.** Если длина поля объявлена больше буфера, наивный парсер читает за границей.
- **Рекурсия.** Вложенные сообщения без ограничения глубины → переполнение стека.
- **Дублирование полей.** Одно поле может встретиться дважды; поведение зависит от парсера (последнее/первое/сумма) — источник логических багов.
- **Non-canonical varint.** Число можно закодировать избыточно (лишние байты 0x80); если два парсера трактуют это по-разному — расхождение.

Именно расхождения парсеров ломают безопасность.

## Полный прогон: от дампа к флагу

```
$ python3 proto_dump.py data.bin
field 1 (varint): 150
field 2 (string): testing
field 3 (string): abc
field 4 (bytes):  b'nto{pr0t0buf_w1r3_f0rm4t}'
```

Флаг лежит в одном из length-delimited полей. Задача — прочитать его, не имея схемы.

## Что мы теперь знаем

- Varint кодирует целые переменной длины по 7 бит.
- Ключ поля = (номер << 3) | wire-тип.
- Wire-тип 2 — length-delimited (строки, вложенные).
- Схема нужна для смысла, но не для структуры.
- Парсеры ломаются на длинах, рекурсии и дублях.

## Пишем универсальный парсер wire-format

Полноценный декодер занимает около полусотни строк и покрывает все wire-типы. Алгоритм: читаем ключ, разбираем номер и тип, затем читаем значение в зависимости от типа. Для varint — цикл по 7 бит, для length-delimited — длина и срез, для 64/32-бит — фиксированное число байт.

```
$ python3 - <<'PY'
def varint(b, i):
    v = s = 0
    while True:
        x = b[i]; i += 1
        v |= (x & 0x7f) << s
        if not x & 0x80: return v, i
        s += 7
def parse(b):
    i, out = 0, []
    while i < len(b):
        key, i = varint(b, i)
        f, w = key >> 3, key & 7
        if w == 0:
            v, i = varint(b, i); out.append((f, 'varint', v))
        elif w == 2:
            n, i = varint(b, i); out.append((f, 'bytes', b[i:i+n])); i += n
        elif w == 5:
            out.append((f, 'i32', b[i:i+4])); i += 4
        elif w == 1:
            out.append((f, 'i64', b[i:i+8])); i += 8
        else:
            raise ValueError('bad wire ' + str(w))
    return out
PY
```

Такой парсер не требует схемы и работает с любым Protobuf-дампом. Дальше остаётся сопоставить номера полей с семантикой — это уже догадки, но для CTF часто достаточно просто найти флаг в байтовом поле.

## Как отличить Protobuf от других форматов

Несколько эвристик: первый байт часто `0x08` или `0x0a` (поле 1, varint или строка); строки идут с явной длиной, поэтому в дампе видны осмысленные фрагменты; числа varint дают «рваные» байты. Если `strings` показывает куски текста с префиксами длины — почти наверняка Protobuf.

Полезно сравнить с MessagePack: там первый байт задаёт тип целиком (`0x8N` — map), а в Protobuf каждый элемент начинается с ключа поля. Если видите повторяющиеся пары «номер+тип», это Protobuf.

## Разбор gRPC-кадра

gRPC поверх HTTP/2 добавляет 5-байтовый префикс к каждому сообщению: 1 байт флага сжатия и 4 байта длины (big-endian). Убрав префикс, получаете чистый Protobuf. В Wireshark есть декодер gRPC, но если схема неизвестна, он покажет только сырые байты — и здесь пригодится ручной парсер.

## Типичные ошибки при декодировании

Первая — путать wire-типы: 2 — length-delimited, а не varint. Вторая — не учитывать, что вложенные сообщения тоже length-delimited, и пытаться парсить их как значения. Третья — игнорировать packed repeated поля: массив чисел кодируется одним length-delimited блоком. Четвёртая — считать, что номер поля не может повторяться.

## Частые вопросы

**Обязательна ли схема?** Для структуры — нет, для семантики — да.

**Что делать с неизвестными wire-типами 3 и 4?** Это устаревшие group; современные сообщения их не используют, но парсер должен корректно завершиться.

**Можно ли восстановить имена полей?** Только угадать по типу и контексту.

**Почему мой парсер падает на реальном дампе?** Скорее всего, вы не учли packed-массивы или начали не с нулевого смещения (например, оставили gRPC-префикс).

## Как Protobuf помогает в реверсе приложений

Мобильные приложения часто общаются с сервером по Protobuf/gRPC. Перехватив трафик (mitmproxy, Frida), вы видите бинарные блобы. Имея хотя бы частичную схему (её можно вытащить из APK — файлы `*.proto` иногда лежат внутри), вы расшифровываете всё. Без схемы — восстанавливаете структуру и угадываете поля по значениям.

Практический приём: замените одно поле и посмотрите, как изменится ответ сервера. Так определяют семантику: поле, меняющее поведение, — это параметр запроса. Это называется «differential probing» и работает без схемы.

## Сравнение с JSON и XML

Protobuf компактнее и быстрее JSON, но нечитаем человеком. JSON удобен для отладки, Protobuf — для продакшена. gRPC выбрал Protobuf именно за размер и скорость. В CTF это значит: если дамп маленький и бинарный — думайте про Protobuf; если текст — JSON/XML.

## Итог по Protobuf

Wire-format читается без схемы: ключ = (номер << 3) | тип, значения — varint или length-delimited. Универсальный парсер — 50 строк. Уязвимости живут в парсерах: переполнение длины, рекурсия, дубли полей и неканонические varint. Понимание формата — вход в реверс gRPC и мобильных API.

## Packed repeated поля

Массивы чисел в Protobuf кодируются «упакованно»: одно length-delimited поле содержит последовательность varint. Это экономит байты тегов. При ручном разборе легко ошибиться и принять блок за строку. Признак: длина блока кратна длине элемента, а содержимое — валидные varint.

```
$ python3 -c "print(bytes.fromhex('0a03010203'))"
b'\n\x03\x01\x02\x03'
```

Поле 1 (wire 2), длина 3, три байта `01 02 03` — это массив [1,2,3], а не строка. Различайте по контексту: если элементы — маленькие числа, это packed repeated.

## Reserved и deprecated поля

В схемах поля можно помечать `reserved` или `deprecated`. Первое запрещает повторное использование номера, второе лишь помечает. При реверсе это значит: пропуски в номерах полей — не ошибка, а зарезервированные номера. Не удивляйтесь, если поле 5 отсутствует, а 6 присутствует.

## Совместимость версий

Protobuf проектировался для эволюции схем: новые поля можно добавлять, старые клиенты их игнорируют. Это удобство, но и риск: если поле с номером 5 раньше было `int`, а стало `string`, старый клиент интерпретирует байты неверно. В аудите проверяйте совместимость типов при смене номера.

## Экономия и DoS

Protobuf компактен, но допускает «раздутые» сообщения: огромная вложенность, гигантские length-delimited поля, избыточные varint. Парсер, не ограничивающий глубину и размер, уязвим к DoS. Правило: всегда ставьте лимиты на глубину рекурсии и общий размер.

## Отладка с protoc

```
$ protoc --decode_raw < data.bin
1: 150
2: "testing"
3: "abc"
```

`--decode_raw` декодирует без схемы — быстрый способ посмотреть структуру. С схемой используйте `--decode=MyMessage`. Это два режима, которые стоит знать наизусть.

## Итог

Protobuf — компактный бинарный формат, читаемый без схемы. Ключ = (номер<<3)|тип, значения — varint или length-delimited. Понимание packed-полей, reserved-номеров и совместимости версий отличает уверенного реверс-инженера от новичка.
