## Вопрос, с которого всё начинается

Java-сервер принимает «безопасный» плагин и ограничивает его права через `SecurityManager`: плагину нельзя читать файлы и завершать JVM. В теории. На практике такие песочницы обходят снова и снова. Разберём, как устроена модель безопасности Java и почему она течёт.

## Наш пример: плагин в песочнице

```
$ java -Djava.security.manager -Djava.security.policy=sandbox.policy Run
> read /etc/passwd
AccessControlException: access denied ("java.io.FilePermission" "/etc/passwd" "read")
```

Плагин получил исключение — механизм работает. Посмотрим, что он запрещает.

## Шаг 1: что такое SecurityManager

`SecurityManager` — объект, который JVM спрашивает перед потенциально опасным действием. Когда код вызывает `new FileInputStream("/etc/passwd")`, JVM дергает менеджер: «можно?». Менеджер смотрит **политику** (`java.policy`) и либо разрешает, либо бросает `AccessControlException`.

Политика задаёт, каким кодам что можно:

```
grant codeBase "file:/opt/plugin/-" {
    permission java.util.PropertyPermission "user.dir", "read";
};
```

Коду из `/opt/plugin` разрешено читать одно свойство — и всё.

## Шаг 2: AccessController и стек

Менеджер проверяет не только текущий кадр, но весь стек вызовов: если наш код вызвал системную библиотеку, а та обратилась к файлу, проверяется и наш кадр. Для «доверенных» мест есть `AccessController.doPrivileged(...)` — он обрезает стек, объявляя участок доверенным.

Именно здесь и живёт классическая ошибка: если доверенный код читает **произвольный** путь, переданный извне, `doPrivileged` пропускает атакующего внутрь.

## Шаг 3: обход через рефлексию

Плагин хочет снять менеджер целиком. Прямой вызов `System.setSecurityManager(null)` бросит `SecurityException`. Но поле, хранящее менеджер, можно достать рефлексией:

```java
Field f = System.class.getDeclaredField("security");
f.setAccessible(true);
f.set(null, null);   // менеджер исчез
```

Если менеджер не запрещает `ReflectPermission("suppressAccessChecks")`, `setAccessible(true)` снимает инкапсуляцию, и мы меняем внутреннее поле. После этого любые проверки проходят «мимо».

## Шаг 4: обход через Unsafe

`sun.misc.Unsafe` даёт доступ к памяти и внутренним структурам в обход виртуальной машины:

```java
Unsafe u = getUnsafe();          // через рефлексию к полю theUnsafe
u.putObject(System.class, offset, null);   // обнуляем поле менеджера
```

Unsafe — «чёрный ход» JVM: он не спрашивает менеджер о большинстве операций.

## Шаг 5: обход через десериализацию

Если песочница ещё и десериализует данные (`ObjectInputStream`), то gadget-цепочки (CommonsCollections и др.) вызывают методы вне проверок или переписывают поля через `readObject`. Менеджер проверяет действия, но не то, что цепочка соберёт `Runtime.exec` из уже доверенных объектов.

## Полный прогон

1. Плагин ловит `AccessControlException` — изучаем политику.
2. Пробуем `System.setSecurityManager(null)` — отказ.
3. Рефлексия: `getDeclaredField("security")` + `setAccessible(true)` + `set(null)`.
4. Менеджер снят → читаем `/flag.txt` через `Files.readString`.
5. Пишем флаг в ответ.

## Что мы теперь знаем

- SecurityManager — точка принятия решений, опирающаяся на политику.
- `doPrivileged` обрезает стек и может стать дырой.
- Рефлексия + `setAccessible` снимает инкапсуляцию полей.
- `Unsafe` обходит проверки на уровне памяти.
- Десериализация позволяет собрать вызов в обход политики.

## Другие пути обхода

Модель безопасности Java ломали разными способами, и не все требуют рефлексии к `System.security`:

| Вектор | Идея | Условие |
|---|---|---|
| `doPrivileged` | Доверенный участок читает внешний путь | Ошибка в коде библиотеки |
| `ClassLoader` | Загрузить свой класс в доверенный контекст | Доступ к загрузчику |
| JNDI | Подставить URL и подтянуть объект | Уязвимость вида Log4Shell |
| `MethodHandles.Lookup` | Обойти проверки доступа к приватным членам | Старые JDK |
| `Unsafe` | Прямая запись в поля в обход JVM | Доступ к `sun.misc` |
| Десериализация | Собрать вызов из готовых объектов | `ObjectInputStream` |

Ключ: `SecurityManager` проверяет **действия**, а не то, как они собраны. Если действие удаётся инициировать из доверенного кода или через уже разрешённые объекты — проверка не сработает.

## Как читать политику и отлаживать проверки

JVM умеет объяснять решения менеджера:

```
$ java -Djava.security.debug=access,policy -Djava.security.manager Run
access: access denied ("java.io.FilePermission" "/etc/passwd" "read")
access: domain that failed ProtectionDomain ...
```

Флаг `access` печатает, кто именно и что запросил, `policy` — как загружена политика. `policytool` (в старых JDK) правит `java.policy`. Это превращает слепой перебор в чтение решения.

## Десериализация как мост через песочницу

Если сервис десериализует недоверенные данные, менеджер не спасает: gadget-цепочка (например, `CommonsCollections`) вызывает `Runtime.exec` через уже доверенные классы. Инструмент `ysoserial` собирает такие цепочки. Защита — не менеджер, а фильтр классов:

```
-Djdk.serialFilter=!com.sun.org.apache.xalan..;!org.apache.commons.collections..;maxdepth=10
```

## Защита и современное состояние

`SecurityManager` объявлен deprecated в Java 17 и удаляется в 21+. Современная изоляция строится иначе:

- отдельный процесс/контейнер с ограниченным пользователем;
- allow-list десериализации (`jdk.serialFilter`) или отказ от Java-сериализации;
- модульная система (`module-info.java`) вместо менеджера;
- для плагинов — отдельная JVM без доступа к сети и ФС.

## Шпаргалка

| Приём | Что делает |
|---|---|
| `getDeclaredField("security")` | Доступ к полю менеджера |
| `setAccessible(true)` | Снятие инкапсуляции |
| `Unsafe.putObject` | Запись в произвольное поле |
| `-Djava.security.debug=access` | Трассировка проверок |
| `jdk.serialFilter` | Фильтр классов при десериализации |

## Разбор реального кейса: плагин с урезанными правами

Типовая задача: сервис загружает плагин и запускает его в JVM с включённым `SecurityManager`. Политика разрешает плагину читать только одно системное свойство. Плагину нужно прочитать `flag.txt`. Разберём путь решения.

Шаг 1 — понять, что запрещено. Пробуем простое:

```
> read /flag.txt
AccessControlException: access denied ("java.io.FilePermission" "/flag.txt" "read")
```

Проверка сработала. Теперь пробуем снять менеджер напрямую:

```
> System.setSecurityManager(null)
SecurityException: not allowed to set the security manager
```

Прямой путь закрыт — менеджер сам себя защищает.

Шаг 2 — добраться до поля рефлексией. В классе `System` поле `security` приватное. Рефлексия позволяет его прочитать и записать, если не запрещено `ReflectPermission("suppressAccessChecks")`:

```
> Field f = System.class.getDeclaredField("security"); f.setAccessible(true); f.set(null, null); print("done")
done
```

`setAccessible(true)` снял инкапсуляцию, `f.set(null, null)` обнулил менеджер. Теперь проверок нет.

Шаг 3 — прочитать файл обычными средствами:

```
> Files.readString(Path.of("/flag.txt"))
nto{...}
```

## Разбор: почему это сработало

Политика не перечисляла `ReflectPermission`. `setAccessible(true)` — привилегированная операция, но если её не запретили явно, она проходит. Дальше мы поменяли внутреннее состояние `System`, и все последующие проверки видят `security == null`. Это классика: модель безопасности сильна ровно настолько, насколько полно описана политика.

## Пошаговый протокол

1. Определить, какой менеджер активен (`System.getSecurityManager()`).
2. Попробовать `System.setSecurityManager(null)` — часто запрещено.
3. Достать поле `security` рефлексией и обнулить.
4. Если рефлексия закрыта — искать `Unsafe`, JNDI, десериализацию.
5. После снятия — читать файлы обычными API.

## Частые ошибки

- Считать, что `SecurityManager` — это песочница уровня ОС: он лишь спрашивает политику.
- Забывать про `doPrivileged`: доверенный код может сделать работу за вас.
- Не проверять версию JDK: в 17+ менеджер deprecated, в 21+ его нет, и задачи строятся иначе.
- Путать `ReflectPermission("suppressAccessChecks")` с общим правом на рефлексию.

## Эволюция модели безопасности Java

Модель Java прошла три эпохи, и это важно понимать, чтобы не применять приёмы не к той версии:

1. **Эпоха SecurityManager (Java 1.x–16).** Политика `java.policy`, проверки на каждом опасном действии. Обходилась рефлексией, `Unsafe`, JNDI, десериализацией.
2. **Переходный период (Java 17).** `SecurityManager` помечен deprecated, но ещё работает. Задачи CTF этого периода совмещают менеджер и фильтры десериализации.
3. **Модульная эпоха (Java 21+).** Менеджера нет. Изоляция строится на `module-info.java`, отдельных процессах и контейнерах. Вместо «обойти менеджер» задача — «обойти модульные границы или процесс».

Если задача использует `SecurityManager`, почти всегда есть путь через рефлексию к полю `security`. Если менеджера нет — ищи десериализацию, JNDI или ошибку в самом плагине.

## Практические заметки по эксплуатации

- `System.getSecurityManager()` покажет, какой менеджер активен, или `null`.
- Поле называется по-разному в разных JDK (`security`), но всегда находится рефлексией по типу `SecurityManager`.
- `AccessController.doPrivileged` в сторонних библиотеках — частый источник дыры: ищи вызовы, где внешний путь попадает в доверенный блок.
- При десериализации проверяй `-Djdk.serialFilter`: если фильтр пустой или слабый, gadget-цепочки работают.
- Логи `-Djava.security.debug=access` прямо показывают, какое разрешение не хватило — это ускоряет перебор.

## Формулировка вывода

В отчёте важно отделить «менеджер обошли» от «менеджер не проверял это действие». Первое — баг модели, второе — баг конфигурации. Оба интересны, но чинятся по-разному: первое — обновлением JDK и отказом от менеджера, второе — точной политикой и фильтрами.

## Итоговый разбор по шагам

Соберём весь путь решения в одну последовательность, чтобы её можно было воспроизвести на любой похожей задаче. Сначала выясняем, включён ли менеджер и какая у него политика: `System.getSecurityManager()` возвращает объект или `null`. Затем пробуем очевидный `System.setSecurityManager(null)` — он почти всегда запрещён, и это нормально: запрет подтверждает, что менеджер активен. Дальше идём через рефлексию: получаем `Class` объекта `System`, достаём приватное поле `security`, вызываем `setAccessible(true)` и записываем `null`. Если политика не перечисляла `ReflectPermission("suppressAccessChecks")`, операция проходит.

После снятия менеджера работаем обычными API: `Files.readString`, `new FileInputStream`, `Runtime.getRuntime().exec`. Все они теперь не спрашивают разрешений. Если рефлексия закрыта, остаются `Unsafe`, JNDI и десериализация — каждый из них обходит модель по-своему, и в реальных задачах обычно находится хотя бы один незакрытый путь. Главное — не застревать на одном векторе и проверять конфигурацию политики, а не перебирать наугад.
