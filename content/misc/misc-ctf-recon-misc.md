## Вопрос, с которого всё начинается

В прошлом уроке мы разобрали общий процесс. Теперь применим его к первому шагу любой задачи — **разведке**. Задача даёт один файл `sound.wav` и описание из двух слов: «услышь истину». Что это значит и с чего начать?

## Наш пример: sound.wav

Сначала инвентаризация — что вообще есть на входе:

```
$ ls -la
-rw-r--r-- 1 user user 1.4M Oct 10 12:00 sound.wav
$ file sound.wav
sound.wav: RIFF (little-endian) data, WAVE audio, Microsoft PCM, 16 bit, mono 44100 Hz
```

Это WAV-аудио: 16-бит, моно, 44100 Гц. Категория — stego/misc, и описание «услышь истину» намекает на аудио-стего. Но прежде чем строить спектрограммы, сделаем самые дешёвые проверки.

## Шаг 1: читаем условие целиком

Условие — это не только текст задания, но и метаданные вокруг него:

- **название** — часто игра слов или намёк на инструмент;
- **описание** — прямо указывает категорию («аудио», «образ», «сервис»);
- **формат флага** — позволяет `grep`-ать по нему;
- **приложенные файлы** — их имена и размеры;
- **подсказки** — иногда раскрывают метод.

В нашем случае «услышь истину» — намёк на звук. Выписываем «дано: WAV; требуется: флаг».

## Шаг 2: быстрый проход

Стандартный «первый проход» — шесть дешёвых команд:

```
$ strings -n 6 sound.wav | head
RIFF...
FLAG{w4v3s_c4rry_s3cr3ts}
...
```

Уже на второй команде видим флаг — он лежит прямо в читаемых строках файла. Задача решена разведкой, без всякой спектрограммы.

Остальные команды первого прохода пригодятся, если строки ничего не дали:

```
$ exiftool sound.wav        # метаданные
$ binwalk sound.wav         # вложенные форматы
$ xxd sound.wav | head      # начало файла
$ xxd sound.wav | tail      # конец файла
```

Порядок именно такой: сначала дешёвое (`strings`), потом дороже (`exiftool`, `binwalk`, байты).

## Шаг 3: почему смотрим начало и конец

Данные часто прячут в **конец** файла — дописывают после легитимного содержимого. Формально файл остаётся WAV, но в хвосте лежит архив или текст.

```
$ xxd sound.wav | tail -2
000fffd0: 504b 0304 ...   PK..
```

Байты `50 4b` — это начало ZIP-архива (`PK`). Значит, в хвост WAV дописан архив. Извлекаем:

```
$ binwalk -e sound.wav
$ ls _sound.wav.extracted/
secret.txt
```

Проверять хвост — привычка, которая экономит массу времени.

## Шаг 4: интерпретируем подсказки

Подсказка — не «чит», а часть условия. Её нужно **интерпретировать**, а не копировать:

- «посмотри на время» → таймлайн, EXIF, тайминг;
- «это не то, чем кажется» → полиглот или стего;
- «важны детали» → байты, метаданные;
- «услышь» → аудио-стего (спектрограмма, LSB).

Имя файла тоже подсказка: `sound.wav`, `challenge.zip`, `program` сразу говорят о типе.

## Шаг 5: журнал разведки

Ведите текстовый файл заметок с самого начала:

```
# задача: sound.wav
- file: WAV 16bit mono
- strings: нашёл FLAG{w4v3s_c4rry_s3cr3ts} -> РЕШЕНО
```

Это спасает при возврате к задаче и не даёт повторять тупиковые шаги. В командной работе журнал обязателен.

## Шаг 6: если задача про сервис

Когда на входе не файл, а URL или хост, разведка идёт по другому сценарию. Сначала заголовки и тело:

```
$ curl -sI http://target/
HTTP/1.1 200 OK
Server: nginx/1.18.0
X-Powered-By: PHP/7.4
Set-Cookie: session=...
```

Заголовок `Server` говорит о веб-сервере, `X-Powered-By` — о языке. Дальше смотрим, что спрятано в стандартных местах:

```
$ curl -s http://target/robots.txt
Disallow: /secret/
```

`robots.txt` часто прямо указывает на интересные пути. Для перебора каталогов используют `ffuf` со списком из seclists:

```
$ ffuf -w /usr/share/seclists/Discovery/Web-Content/common.txt -u http://target/FUZZ -mc 200
```

Флаг `-mc 200` показывает только успешные ответы. В сетевых задачах сервисы находят через `nmap -sV -sC` и читают их баннеры.

## Шаг 7: если задача про архив-матрёшку

Многие задачи — «матрёшка»: внутри архива ещё архив, потом картинка, потом текст. Разворачивайте итеративно и следите за типом на каждом шаге:

```
$ file challenge.zip
challenge.zip: Zip archive data
$ unzip -o challenge.zip -d out/
$ file out/*
out/photo.jpg: JPEG image data
```

Если внутри снова архив — распаковывайте дальше; если картинка — переходите к стего; если скрипт — читайте его. `binwalk -e` часто делает распаковку автоматически. Архив с паролем — отдельный класс задач, там начинается подбор или поиск пароля в метаданных.

## Шаг 8: если дали дамп или pcap

Сетевой дамп (`.pcap`) разбирают по протоколам и потокам:

```
$ tshark -r capture.pcap -q -z io,phs
$ tshark -r capture.pcap --export-objects http,out/
```

Первая команда показывает иерархию протоколов, вторая выгружает все файлы, переданные по HTTP. Часто флаг лежит в HTTP-ответе или в учётных данных (HTTP Basic, FTP).

Дамп памяти (`memory.raw`) начинают со строк:

```
$ strings -n 8 memory.raw | grep -i -a 'flag\|password'
```

Это быстрый способ найти пароли и ключи; полноценный анализ — через Volatility (списки процессов, открытые файлы, дампы). Дампы памяти хороши тем, что хранят не только файлы, но и то, что в них было открыто в момент снятия: расшифрованные секреты, пароли в буферах, содержимое переписки.

## Если не сработало

Разведка — это перебор гипотез, и часть из них не подтверждается. Что делать, когда зацепка не нашлась.

**`file` не узнаёт формат.** Это не тупик, а подсказка: файл, возможно, обфусцирован, зашифрован или это кастомный контейнер. Смотрим первые байты через `xxd | head`, ищем известные сигнатуры (magic bytes) и сравниваем с базой: `PK` — ZIP, `0x89 PNG` — PNG, `0x7f ELF` — исполняемый файл Linux, `%PDF` — PDF. Иногда заголовок испорчен намеренно — тогда его восстанавливают по остальным полям.

**`strings` даёт мусор.** Проверь минимальную длину (`strings -n 6`) и кодировки (`-e l` для 16-битного little-endian, `-e b` для big-endian). Если файл сжат или зашифрован, текста не будет вовсе — тогда сначала определяем слой сжатия (`binwalk`) и распаковываем.

**Подсказка в условии непонятна.** Разбирай её буквально. «Он спрятал это в звуке» — смотри спектрограмму и младшие биты аудио. «Файл внутри файла» — `binwalk -e`. «Используй дату из названия» — возможно, это seed или пароль. Ключевые слова условия почти всегда указывают на инструмент.

**Артефакт «пустой».** Проверь размер (`ls -la`), права, не является ли он симлинком, и не лежат ли данные в **альтернативных потоках** или в метаданных (EXIF, комментарии ZIP, чанки PNG). `exiftool` и `pngcheck` показывают то, что `file` и `strings` пропускают.

**Не знаешь, с чего начать.** Заведи журнал разведки: что за файл, что показал `file`/`xxd`/`strings`, какие гипотезы проверил, что вышло. Это дисциплинирует и не даёт ходить по кругу.

## Частые вопросы

**Почему смотреть начало и конец файла?** Начало содержит сигнатуру формата, конец — часто скрытые данные, дописанные после «конца» формата (парсеры читают только заявленную длину и игнорируют хвост).

**`binwalk` ничего не нашёл — файл чистый?** Не обязательно. `binwalk` ищет сигнатуры; если данные сжаты или зашифрованы, сигнатур нет. Тогда работают энтропийный анализ (`binwalk -E`) и ручной осмотр.

**Что такое «матрёшка»?** Файл, внутри которого лежит другой файл, а внутри того — третий. Распаковывают послойно, проверяя каждый слой тем же `file`/`binwalk`.

**Когда задача про сервис, а не про файл?** Когда в условии дан адрес и порт, а не вложение. Тогда начинай с `nc`/`curl`, баннера сервиса и описания протокола в условии.

## Порядок разведки, который экономит время

Разведку удобно вести по фиксированному порядку, чтобы ничего не пропустить: определи тип (`file`, `xxd`, размер), затем собери текст и метаданные (`strings`, `exiftool`), потом ищи вложенные форматы (`binwalk`, `foremost`), и только затем применяй инструмент по категории. Такой порядок дешевле, чем сразу запускать «тяжёлый» анализ.

Полезно сразу проверять обе гипотезы — «файл» и «сервис». Если в условии есть адрес, начинай с `nc`/`curl` и баннера; если дано вложение — с сигнатур и структуры. И держи под рукой шпаргалку magic bytes: `PK`, `%PDF`, `0x7fELF`, `0x89PNG`, `RIFF`, `OggS`, `ID3`, `gzip`. Быстрое узнавание формата по первым байтам снимает половину неопределённости.

## Что мы теперь знаем

По-простому:

1. Разведка — самый дешёвый способ ускорить решение.
2. Условие и имя файла часто прямо указывают категорию.
3. Первый проход: `file`, `strings`, `binwalk`, `xxd` (начало и конец), `exiftool`.
4. Данные нередко дописаны в конец файла — смотрите хвост.
5. Подсказки нужно интерпретировать, а заметки вести с первой минуты.

## На что смотреть дальше

- **Не пропускайте метаданные.** `exiftool` часто даёт ответ напрямую.
- **Смотрите конец файла.** Дописанные данные — классика полиглотов.
- **Не запускайте бинарник на рабочей машине.** Только в песочнице.
- **Не застревайте на одном файле.** Сначала обзор всех артефактов, потом углубление.
- **Записывайте находки.** Журнал разведки — половина успеха при возврате.

## Куда дальше

Мы научились быстро осматривать артефакты. Дальше возьмём **данные** — `points.csv` с координатами, где флаг закодирован в точках, и разберём, как таблицы, статистика и визуализация вскрывают такие задачи. А пока главное запомни: шесть дешёвых команд первого прохода дают большинство зацепок.

## Где пригодится

- **CTF:** любой тип задач.
- **Форензика:** первичный осмотр артефактов.
- **Bug bounty:** разведка цели.
- **Работа:** триаж вложений.
