## Вопрос, с которого всё начинается

В CTF всё чаще дают не игру, а эмулятор: программа, которая исполняет байткод несуществующей машины, а уязвимость спрятана в её логике. Чтобы эксплуатировать такой таргет, нужно понимать, как вообще устроен эмулятор и где он обычно ошибается. Этот урок — карта таких ошибок.

## Наш пример: минимальный эмулятор

```
$ ./emu rom.bin
[emu] loaded 4096 bytes, entry=0x0000
[emu] executing...
halt
```

Мы видим, что эмулятор загрузил ROM, начал исполнение и остановился. Внутри — цикл: взять инструкцию, декодировать, исполнить. Разберём его и найдём, где он может сломаться.

## Шаг 1: цикл исполнения

Ядро любого эмулятора — три шага в цикле:

1. **Fetch** — прочитать байт (или несколько) по адресу `PC` (program counter, счётчик команд).
2. **Decode** — понять, что это за инструкция.
3. **Execute** — выполнить и сдвинуть `PC`.

```c
while (running) {
    uint8_t op = mem[pc++];          // fetch
    switch (op) {                    // decode
        case 0x01: a += mem[pc++]; break;   // execute
        case 0x00: running = 0; break;
    }
}
```

Уже здесь видно потенциальную проблему: `pc` инкрементируется без проверки границ. Если инструкция читает операнд у конца памяти — выход за массив.

## Шаг 2: карта памяти и MMU

Реальные машины разделяют адресное пространство на регионы: ROM, RAM, видеопамять, регистры устройств (MMIO). Эмулятор реализует **MMU** (memory management unit) — функцию перевода адреса в нужный буфер:

```c
uint8_t *mmu_translate(uint16_t addr) {
    if (addr < 0x8000) return &rom[addr];
    if (addr < 0xC000) return &vram[addr - 0x8000];
    return &ram[addr - 0xC000];
}
```

Ошибка в арифметике перевода — классический источник OOB: если `addr - 0x8000` не проверить, чтение уйдёт за границу `vram`.

## Шаг 3: где эмуляторы ошибаются

Типовые баги эмуляторов сведены в таблицу:

| Ошибка | Причина | Последствие |
|---|---|---|
| OOB чтение ROM | нет проверки длины | утечка памяти хоста |
| OOB запись в VRAM | неверный перевод адреса | перезапись структур |
| Целочисленное переполнение | `addr + offset` без маски | чтение по чужому адресу |
| Неверный размер банка | не доверяют заголовку ROM | heap overflow |
| Ошибка в save state load | длина из файла без проверки | произвольная запись |
| Гонка в PPU | нет синхронизации | UAF |

Общее у всех — **недоверенные данные из ROM/состояния** попадают в арифметику без валидации.

## Шаг 4: реальные CVE

История знает десятки уязвимостей эмуляторов:

- **CVE-2015-5165** — QEMU, утечка памяти в эмуляции RTL8139.
- **CVE-2020-14364** — QEMU, OOB в USB-эмуляции.
- **CVE-2019-18960** — Firecracker, OOB в virtio-очереди.
- Различные CVE в VICE, Dolphin, MAME — из-за разбора недоверенных ROM.

Схема одна: гость (ROM/VM) передаёт данные, эмулятор использует их без проверки, и атакующий выходит в **хост**.

## Шаг 5: фаззинг эмулятора

Чтобы найти такие баги, эмулятор фаззят: подают случайные ROM и смотрят на падения. Инструменты: `AFL++`, `libFuzzer`, `honggfuzz`, а для ядра — `syzkaller`. Хорошая цель — функция загрузки ROM и обработчики MMIO: они первыми принимают недоверенные данные.

```
$ afl-fuzz -i seeds/ -o out/ -- ./emu @@
```

При падении смотрят стек в отладчике и классифицируют: OOB, UAF, integer overflow.

## Шаг 6: как эксплуатировать баг эмулятора

Цель — превратить OOB в контроль над хостом. Сценарий: баг даёт запись за границей буфера; рядом лежит указатель на функцию или структура, которую использует хост; перезаписав её, получаем исполнение кода. Это та же heap-эксплуатация, только «внутри» эмулятора.

## Полный прогон

1. Запустить эмулятор на валидном ROM, понять формат.
2. Прочитать код загрузки ROM и MMU (дизассемблер, Ghidra).
3. Найти арифметику без проверки границ.
4. Собрать ROM, который её активирует (переполнение/большой адрес).
5. Получить контроль или утечку, ведущую к флагу.

## Что мы теперь знаем

- Эмулятор — цикл fetch/decode/execute плюс MMU.
- Основной источник багов — недоверенные данные из ROM.
- Типовые ошибки: OOB, integer overflow, неверный размер.
- CVE эмуляторов ведут к побегу в хост.
- Фаззинг — способ их находить.

## Разбор реального примера: OOB в загрузчике ROM

Представим конкретную уязвимость, чтобы увидеть теорию в действии. Эмулятор читает из ROM число банков и вычисляет размер:

```c
uint16_t banks = rom[4];
uint32_t size = banks * 16384;
uint8_t *buf = malloc(size);
memcpy(buf, rom + 16, size);   // читает size байт из rom
```

Если `rom` меньше, чем `size`, `memcpy` прочитает за границей входного буфера — утечка памяти хоста в буфер гостя. Атакующий управляет полем `banks` (байт 4 ROM), поэтому может запросить огромный размер. Это классический «trust the header» баг: эмулятор доверяет данным картриджа.

Починка проста — проверять, что `size` не превышает длину файла:

```c
if (size > rom_len - 16) { fprintf(stderr, "bad ROM size\n"); exit(1); }
```

Но в реальных проектах такие проверки часто забывают, и именно они становятся CVE.

## Как устроен PPU и почему тайминги важны

Кроме процессора эмулятор содержит PPU (picture processing unit) — графический чип. Он рисует сканлайн за сканлайном и генерирует прерывания. Точные тайминги критичны: игры синхронизируются с PPU. Ошибки в счётчике циклов приводят к рассинхронизации, зависаниям и, что важнее для безопасности, к гонкам в состоянии — если два «потока» эмуляции (CPU и PPU) обращаются к памяти без согласования, возможен use-after-free. Поэтому качественные эмуляторы либо исполняют всё в одном потоке, либо используют точную синхронизацию.

## Практические заметки по фаззингу

- Начинай с функций, принимающих недоверенные данные: загрузчик ROM, обработчики MMIO, загрузчик save state.
- Сохраняй вход, который привёл к падению, и минимизируй его (`afl-tmin`).
- Классифицируй падение в отладчике: OOB чтение, OOB запись, UAF, переполнение.
- Для эмулятора консоли полезно фаззить сам ROM-формат: заголовок, размеры банков, trainer.
- Если эмулятор на Rust/Go — ищи `unsafe`/cgo и фаззь именно эти места.

## Итоговый разбор по шагам

Разбор эмулятора всегда начинается с формата входа: как он читает ROM и состояние. Затем ищем арифметику по адресам и размерам — там живут OOB. После этого фаззим загрузчик и обработчики устройств. Найденное падение классифицируем и превращаем в примитив: утечку, запись или исполнение. Правильный вывод — не «я уронил эмулятор», а «вот конкретная проверка, которой не хватает, и вот как её активировать».

## Как классифицировать баги эмулятора

Когда фаззер роняет эмулятор, важно понять класс ошибки, потому что от него зависит эксплуатация. Читающее переполнение даёт утечку памяти — можно вытащить адреса и обойти ASLR. Запись за границей даёт примитив перезаписи — можно исправить указатель или структуру. Use-after-free даёт шанс переиспользовать освобождённую память под свой объект. Целочисленное переполнение часто лишь ступенька к одному из первых трёх. В отладчике смотри, какой именно доступ вызвал падение (адрес, размер, направление), и записывай это в отчёт: класс ошибки — половина решения.

## Разбор конкретной CVE по шагам

Возьмём типичную CVE эмулятора устройства. Шаги разбора: (1) находим патч-коммит в апстриме и читаем diff — он показывает, какой проверки не хватало; (2) по diff определяем функцию и входные данные; (3) собираем PoC, который подаёт эти данные через гостя; (4) проверяем падение и классифицируем. Такой подход экономит дни: вместо слепого фаззинга ты сразу знаешь уязвимую точку. Если патча нет, ищи в коде `memcpy`, `strcpy`, `malloc` рядом с разбором данных гостя — это горячие места.

## Зачем это нужно за пределами CTF

Побег из эмулятора — это побег из песочницы: браузерные движки, гипервизоры, серверлес-платформы построены на тех же принципах «гость/хост». Понимая ошибки эмуляторов, ты понимаешь ошибки любого изолятора кода. Поэтому этот урок — мост к темам виртуализации и контейнерной безопасности.

## Сравнение с реальными гипервизорами

Эмулятор игровой консоли и гипервизор — родственники: оба исполняют чужой код и должны изолировать его от хоста. Разница в масштабе и в модели угроз. У эмулятора угроза — вредоносный ROM; у гипервизора — целая гостевая ОС. Но и там, и там ошибки сосредоточены в двух местах: разбор недоверенных структур (заголовки, дескрипторы, очереди) и обработка устройств (virtio, USB, сеть). Если научиться читать эти места в эмуляторе, те же навыки переносятся на QEMU, Firecracker и облачные платформы. Поэтому в CTF эмуляторы — удобный учебный полигон для куда более серьёзных целей.

Итог: эмулятор — это обычная программа с циклом и таблицей переходов, и её безопасность определяется тем, насколько тщательно проверяются данные от гостя. Каждая забытая проверка границы — потенциальный побег из песочницы.
