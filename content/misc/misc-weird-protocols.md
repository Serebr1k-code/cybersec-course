## Вопрос, с которого всё начинается

В CTF тебе дали адрес `chal.ctf.example:1337` и больше ничего. Подключаешься — сервис молчит. Пишешь `GET /` — в ответ тишина. Это не HTTP и не FTP: сервис говорит на **самодельном протоколе** — своём наборе байтов, который надо разгадать. В этом уроке мы возьмём один такой сервис и разберём его от первого молчания до флага. Навык пригодится и в реверсе IoT-устройств, и в анализе C2-трафика малвари.

## Наш пример: сервис, который не отвечает на текст

Подключаемся обычным `nc` (netcat — утилита «открыть TCP-соединение и поговорить»):

```bash
$ nc chal.ctf.example 1337
GET / HTTP/1.1

```

Сервер не ответил и не закрыл соединение — он **ждёт чего-то другого**. Первый вопрос: что именно он хочет получить? Когда сервис молчит, ответ обычно спрятан в том, что он присылает сам сразу после подключения.

## Смотрим сырые байты, а не текст

Текст мы уже «увидели» глазами и ничего не заметили. Но протокол может быть бинарным. Смотрим байты через `xxd` (показывает hex-код и ASCII рядом):

```bash
$ nc chal.ctf.example 1337 | xxd | head -2
00000000: 5057 4e21 0100 05 ...   "PWN!..."
```

Вот оно: сервер при подключении прислал `PWN!` — это **magic-байты** (сигнатура, постоянный маркер начала протокола, как `MZ` у exe-файла). Дальше идут `01`, затем `00 05`. Мы видим структуру, но пока не знаем, что означают поля.

Важная привычка: **всегда смотри обе стороны диалога в байтах**. Текстовый вывод `nc` скрывает непечатаемые байты, а именно они и задают формат.

## Разбираем структуру: magic, op, длина, порядок байт

Типичный самодельный протокол — это заголовок из полей фиксированного размера и полезная нагрузка:

| Поле | Размер | Пример |
|------|--------|--------|
| Magic | 4–8 байт | `PWN!` |
| Opcode (тип команды) | 1 байт | `0x01` = прочитать файл |
| Length (длина payload) | 2–4 байта | `0x0005` |
| Payload | Length байт | данные |
| Checksum (контрольная сумма) | 2–4 байта | CRC16/CRC32 |

Ключевой вопрос — **порядок байт** (endianness): байты числа можно читать слева-направо (big-endian, `>`) или справа-налево (little-endian, `<`). `00 05` в big-endian — это 5; в little-endian те же байты дали бы 1280. Догадка «length = 5» согласуется со словом `flag.` — значит big-endian. **Проверяй обе гипотезы**: абсурдно большая длина почти всегда означает, что endian угадан неверно.

## Пишем клиент и получаем флаг

Теперь у нас есть гипотеза: сервер ждёт `[PWN!][op][len big-endian][payload]`, и если `op == 0x01`, он возвращает содержимое файла с именем из payload. Собираем пакет на Python — там за упаковку чисел в байты отвечает модуль `struct`:

```python
import socket, struct
s = socket.create_connection(("chal.ctf.example", 1337))
payload = b"flag.txt"
pkt = b"PWN!" + bytes([0x01]) + struct.pack(">H", len(payload)) + payload
s.sendall(pkt)
print(s.recv(4096))
```

`struct.pack(">H", 5)` — это «упаковать 5 как 2-байтовое число big-endian» (`>` = big, `H` = unsigned short). Запускаем:

```
b'flag{protocol_reversed}\n'
```

Гипотеза верна — мы разобрали протокол, не имея ни исходников, ни документации.

## TCP — это поток, а не сообщения

Отдельная ловушка: `recv(4096)` не обязан вернуть весь ответ. TCP передаёт **поток байтов** без границ сообщений, поэтому один вызов может вернуть половину пакета. Правильно — читать в цикле, пока не наберём ожидаемый объём:

```python
buf = b""
while len(buf) < 14 + length:
    chunk = s.recv(4096)
    if not chunk:
        break
    buf += chunk
```

Именно из-за этого «всё отправлено верно, а ответ обрезан». Всегда досчитывай по полю length из заголовка.

## Если сервер молчит и после этого: CRC и TLV

Две частые причины, почему «всё правильно, но не работает».

**Контрольная сумма (CRC).** Многие протоколы заканчиваются 2–4 байтами CRC — числом, посчитанным от всего пакета. Сервер молча отбрасывает пакеты с неверной суммой. Вариаций CRC десятки (разные полиномы, начальные значения, инверсии входа/выхода), поэтому не угадывай, а определи эмпирически — отправь известный пакет и сравни CRC в ответе:

```python
import crcmod
data = bytes.fromhex("50574e2101000500")
for name in ["crc-16", "crc-16/xmodem", "crc-32"]:
    print(name, hex(crcmod.predefined.mkCrcFun(name)(data)))
```

Помни и про порядок байт при записи CRC в пакет: даже верная сумма в неверном порядке не пройдёт проверку.

**TLV (Type-Length-Value).** Вместо фиксированного заголовка поля идут тройками «тег, длина, значение». Гибче, но опаснее: если парсер не проверяет длину против остатка буфера, получается чтение за границей (OOB read) или переполнение — а это уже уязвимость, которую в CTF и просят найти. Видишь повторяющиеся «тег, длина, данные» — первым делом ищи, где длина не проверяется. Родственные self-describing форматы — protobuf, msgpack, CBOR; их разбирают декодерами (`protoc --decode_raw`, `blackboxprotobuf`, `msgpack`).

## Если дали бинарь сервера

Когда есть исполняемый файл сервиса, протокол читают прямо в коде. Открываем в Ghidra/IDA, ищем `recv`/`read` и структуру, куда пишутся байты:

```c
struct msg {
    char magic[8];    // offset 0
    uint8_t ver;      // offset 8
    uint8_t op;       // offset 9
    uint32_t len;     // offset 10
    char payload[];   // offset 14
};
```

Дальше находим, где `len` попадает в `memcpy(dst, payload, len)` — это кандидат на переполнение. В CTF «странный протокол» нередко оказывается обёрткой над уязвимостью (overflow, format string, OOB read), а не самоцелью.

## UDP и raw-сокеты

UDP-сервисы не устанавливают соединение, поэтому диалог другой: отправил датаграмму — получил ответ. Проверяем:

```bash
$ echo -n "hello" | nc -u -w2 chal.ctf.example 9999
```

`-u` переключает nc в UDP, `-w2` — таймаут 2 секунды (иначе будешь ждать вечно). В UDP нет гарантии порядка и доставки: пакеты могут теряться и дублироваться — учитывай это, если протокол stateful. Для полностью кастомных пакетов на уровне IP берут Scapy, где слои и поля описываются декларативно:

```python
from scapy.all import *
class MyProto(Packet):
    fields_desc = [StrFixedLenField("magic", b"PWN!", 4),
                   ByteField("op", 1),
                   ShortField("length", 0),
                   StrLenField("payload", b"", length_from=lambda p: p.length)]
send(MyProto(op=2, payload=b"flag?", length=5), verbose=0)
```

Scapy же разбирает дампы: `pkts = rdpcap('capture.pcap')`, затем `p[MyProto].payload`.

## Что мы теперь знаем

- Когда сервис молчит, смотри **байты**, а не текст: `nc … | xxd`.
- Протокол почти всегда = **magic + тип + длина + payload (+ CRC)**.
- Первое, что путают, — **endianness**; абсурдно большая длина выдаёт ошибку порядка байт.
- TCP — поток без границ: `recv` может вернуть часть, читай в цикле по `length`.
- Сервер отбрасывает пакеты — проверь CRC; формат гибкий — это TLV, ищи непроверенную длину.
- Есть бинарь — иди в Ghidra к `recv`/`memcpy`; там обычно и уязвимость.
