В CTF часто дают сервис, который говорит на **самодельном протоколе**: не HTTP, не FTP, а поток байтов с собственной структурой. Задача — понять формат и корректно с ним поговорить. Это навык, который пригодится и в реверсе IoT-устройств, и в анализе малвари.

## Первый контакт: nc и socat

```bash
nc chal.ctf.example 1337
# ничего не видно — сервер ждёт ввода
```

Если сервер молчит, отправляем данные и смотрим ответ. Если бинарный — используем hex-режим и `xxd`:

```bash
nc chal.ctf.example 1337 | xxd | head
# 00000000: 4d45 5353 4147 4501 0000 0102  ...  "MESSAGE\x01..."
```

`xxd` показывает сырые байты: вот и заголовок `MESSAGE`, версия `01`, длина `00000102`.

## Структура бинарного протокола

Типичный кастомный протокол — это:

| Поле | Размер | Пример |
|------|--------|--------|
| Magic | 4–8 байт | `MESSAGE\x00` |
| Version | 1 байт | `0x01` |
| Opcode/type | 1–2 байта | `0x02` = запрос |
| Length | 2–4 байта (endian!) | `0x00000102` |
| Payload | Length байт | данные |
| Checksum | 2–4 байта | CRC16/CRC32 |

Ключевые вопросы: **порядок байт** (big/little endian), **выравнивание** (padding), **длина** включает заголовок или нет.

## Разбор дампа в Python

```python
import struct
data = open('capture.bin','rb').read()
magic = data[:8]
ver = data[8]
op = data[9]
length = struct.unpack('>I', data[10:14])[0]   # big-endian uint32
payload = data[14:14+length]
print(magic, ver, op, length, payload[:32])
# b'MESSAGE\x00' 1 2 258 b'...'
```

Если endian не угадан, попробуйте оба: `'>I'` (big) и `'<I'` (little). Часто длина «не сходится» именно из-за этого.

## Scapy для произвольных пакетов

Scapy позволяет описывать собственные слои и поля:

```python
from scapy.all import *

class MyProto(Packet):
    name = "MyProto"
    fields_desc = [
        StrFixedLenField("magic", b"MESSAGE\x00", 8),
        ByteField("version", 1),
        ByteEnumField("opcode", 1, {1:"HELLO", 2:"GET", 3:"PUT"}),
        IntField("length", 0),
        StrLenField("payload", b"", length_from=lambda p: p.length),
        XShortField("crc", 0),
    ]

pkt = MyProto(opcode=2, payload=b"flag?", length=5)
send(pkt, verbose=0)
```

Scapy также умеет слушать и разбирать:

```python
pkts = rdpcap('capture.pcap')
for p in pkts:
    if p.haslayer(MyProto):
        print(p[MyProto].opcode, p[MyProto].payload)
```

## Реверс сервиса по бинарю

Если дали бинарь сервера — идём в Ghidra/IDA. Ищем `recv`/`read` и структуру, куда пишутся байты:

```c
struct msg {
    char magic[8];    // offset 0
    uint8_t ver;      // offset 8
    uint8_t op;       // offset 9
    uint32_t len;     // offset 10
    char payload[];   // offset 14
};
```

Далее находим, где `len` используется (`memcpy(dst, payload, len)` — кандидат на переполнение). В CTF нередко «странный протокол» — это обёртка над уязвимостью (overflow, format string, OOB read).

## Работа с UDP и raw-сокетами

UDP-сервисы не имеют соединения, поэтому:

```bash
# отправка UDP-пакета и чтение ответа
echo -n "hello" | nc -u -w2 chal.ctf.example 9999
```

Для полностью кастомных (raw) протоколов на уровне IP — `python` + `socket(AF_INET, SOCK_RAW, ...)`, но обычно достаточно Scapy.

## Полный разобранный пример

Сервис принимает: `[4-byte magic "PWN!"][1-byte op][2-byte len big-endian][payload]` и, если `op == 0x01`, возвращает содержимое файла по имени из payload.

```python
import socket, struct
s = socket.create_connection(("chal.ctf.example", 1337))
payload = b"flag.txt"
pkt = b"PWN!" + bytes([0x01]) + struct.pack(">H", len(payload)) + payload
s.sendall(pkt)
resp = s.recv(4096)
print(resp)
# b'flag{protocol_reversed}\n'
```

## Частые ошибки и подводные камни

- Путать big/little endian — «длина» приходит абсурдно большой.
- Забывать про null-терминатор в magic (`MESSAGE\x00` — 8 байт, не 7).
- Отправлять текстовые `\n`, когда сервер ждёт бинарные байты.
- Не учитывать таймаут: `nc` закрывает соединение, а сервер ждёт ещё данных.
- Игнорировать checksum/CRC — сервер молча отбрасывает пакеты.
- Читать меньше, чем нужно: `recv(1024)` может вернуть часть пакета — нужен цикл.

## Дополнительная теория: TLV, protobuf и самодельные схемы

Многие самодельные протоколы используют **TLV** (Type-Length-Value): тип поля, длина, значение. Это гибче фиксированной структуры, но и опаснее: парсер должен корректно обрабатывать вложенные TLV и отрицательные/огромные длины. Классические баги TLV: длина не проверяется против остатка буфера (OOB read), рекурсивные TLV без ограничения глубины (stack overflow), дубликаты полей (парсер берёт не то). Если видите последовательность «тег, длина, данные» — это TLV, и первым делом ищите отсутствие проверки длины.

Родственный формат — **protobuf**, где поля помечены номерами и wire-типами, а неизвестные поля сохраняются. В CTF protobuf-задачи решают через `protoc --decode_raw` или `blackboxprotobuf` (Python), который восстанавливает схему без `.proto`. Если сервис принимает protobuf, стоит проверить, как он обрабатывает неизвестные/повторяющиеся поля и вложенные сообщения — там часто прячется логическая ошибка. Ещё один частый формат — **msgpack** и **CBOR**; оба имеют self-describing структуру и декодеры на Python (`msgpack`, `cbor2`).

## Тайминги, фрагментация и состояние

Сетевые протоколы делятся на **stateful** (сервер помнит соединение) и **stateless** (каждый пакет независим). В stateful-протоколах состояние между сообщениями — источник багов: можно отправить сообщения в неверном порядке, пропустить шаг аутентификации, «переиграть» старый пакет. В UDP-протоколах важно учитывать потерю/дублирование пакетов и порядок. Если сервис использует фрагментацию на уровне приложения (большое сообщение разбито на части), проверьте, что происходит при неверном порядке или неполной сборке — часто там переполнение буфера.

Ещё один аспект — **тайминги**: некоторые протоколы чувствительны к задержкам (heartbeat, таймауты). Замедление или ускорение отправки может привести к состоянию гонки, которое в CTF иногда и есть решение.

## Разбор ошибок и отладка

Если сервис «не отвечает», проверьте, не ждёт ли он предварительного рукопожатия (banner, magic). Отправляйте данные инкрементально и смотрите, после какого байта приходит ответ. Используйте Wireshark «Follow TCP Stream», чтобы увидеть диалог целиком. Если ответ приходит, но «нечитаем» — возможно, он бинарный или сжат; проверьте первые байты (`file`, `xxd`). Если соединение рвётся — возможно, вы отправили неверную длину или нарушили checksum. Ведите лог байтов в обе стороны: протоколы часто раскрываются при внимательном сравнении успешного и неуспешного запросов.

## Практический разбор: CRC и его ловушки

Многие самодельные протоколы заканчиваются контрольной суммой. Если сервер молча отбрасывает ваши пакеты, скорее всего, CRC не совпадает. Алгоритм CRC не всегда очевиден: вариаций десятки (CRC-16/CCITT, CRC-16/IBM, CRC-32, CRC-16/XMODEM), и они различаются полиномом, начальным значением, порядком байт и инверсией входа/выхода. Не угадывайте — определите параметры эмпирически: отправьте известный пакет, посмотрите на CRC в ответе (если сервер отвечает), затем проверьте гипотезы.

```python
import binascii, crcmod
data = bytes.fromhex("4d4553534147450100000102")
for name in ["crc-16", "crc-16/ccitt-false", "crc-16/xmodem", "crc-32"]:
    try:
        f = crcmod.predefined.mkCrcFun(name)
        print(name, hex(f(data)))
    except Exception as e:
        pass
```

Если у вас есть исходники сервиса — найдите константы полинома и начального значения в бинаре. Если нет — brute-force по известным алгоритмам (библиотека `crcmod` содержит десятки). Также помните про **order** (big/little endian) при записи CRC в пакет: даже правильная сумма в неверном порядке не пройдёт проверку. В CTF это частая причина «всё правильно, но не работает».
