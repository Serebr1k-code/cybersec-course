## Вопрос, с которого всё начинается

Jira — система управления задачами, через которую проходит вся работа IT-компании: тикеты, баги, релизы. В тикетах часто пишут то, что не должно утекать: пароли, внутренние ссылки, детали архитектуры. Плюс Jira тесно связана с Confluence и AD. И у неё есть как «утечки по дизайну», так и критические RCE. Разберём.

## Наш пример: Jira в компании

Цель — `https://jira.target.example`. Фингерпринт:

```
$ whatweb -a 3 https://jira.target.example
https://jira.target.example [200 OK] Atlassian Jira, Java, Set-Cookie[JSESSIONID], X-AUSERNAME
```

Заголовок `X-AUSERNAME` и cookie `JSESSIONID` — признаки Jira. Версию определяем:

```
$ curl -s https://jira.target.example/secure/Dashboard.jspa | grep -io 'jira [0-9.]*'
Jira 9.4.0
```

Версия **9.4.0** — сопоставляем с базой CVE (Atlassian Security Advisories). Например, CVE-2023-22527 затрагивает 8.0.x–8.5.3 и 9.0.0–9.4.0 — то есть наша версия в диапазоне.

## Шаг 1: CVE-2019-8449 — перечисление пользователей

Эта уязвимость позволяет **анонимно** получить список всех пользователей Jira через эндпоинт:

```
$ curl -s 'https://jira.target.example/rest/api/latest/user?username=admin'
$ curl -s 'https://jira.target.example/secure/QueryComponent!Default.jspa'
```

Эндпоинт `/rest/api/latest/groupuserpicker?query=a` отдаёт пользователей по подстроке. Получив список логинов и email, можно строить список целей для брутфорса или фишинга.

## Шаг 2: CVE-2023-22527 — инъекция шаблонов (Velocity)

Jira использует шаблонизатор **Velocity** для рендера страниц. Если пользовательский ввод попадает в шаблон без экранирования — выполняется **SSTI** (server-side template injection), и это ведёт к RCE.

Проверка безопасная — выражение, которое вычисляется:

```
$ curl -s 'https://jira.target.example/secure/...' --data 'field=${7*7}'
```

Если в ответе появляется `49` вместо `${7*7}` — шаблон исполняется. Дальше подставляется команда (например, через `Runtime.exec`), и получается RCE.

## Шаг 3: обход аутентификации и повышение привилегий

У Jira есть история обходов аутентификации (через специальные эндпоинты и токены). Типовой сценарий: анонимный доступ к административному API, позволяющий создать пользователя или изменить настройки. Проверка — запрос к `/rest/api/` без cookie и наблюдение ответа.

## Шаг 4: утечки через API

Jira REST API (`/rest/api/`) отдаёт многое: задачи, комментарии, пользователей, настройки. Часть эндпоинтов по умолчанию доступна анонимно (для интеграций). Если проект «открыт», через API читаются все тикеты — включая те, где в комментариях лежат секреты.

## Шаг 5: связка Jira + Confluence

Jira и Confluence часто на одном сервере и делят AD. Компрометация одной даёт данные другой (общие учётки, ссылки, интеграции). Поэтому, атакуя Jira, проверяй и соседний Confluence — и наоборот.

## Шаг 6: план атаки на Jira

1. **Версия** — точная.
2. **CVE** — сопоставление (Atlassian advisories).
3. **Перечисление пользователей** — CVE-2019-8449.
4. **SSTI** — безопасная проверка (`${7*7}`).
5. **Обход аутентификации** — проверка API.
6. **Эксплуатация** — при подтверждении.
7. **Пост-эксплуатация** — тикеты, креды, AD.

## Шаг 7: как не навредить

Jira критична: в ней — работа компании. Падение или изменение задач = ущерб и раскрытие. Поэтому: только неразрушающие проверки; не создавай тикетов/пользователей; SSTI проверяй арифметикой, а не командой. Jira под мониторингом.

## Что мы теперь знаем

- Jira узнаётся по `X-AUSERNAME` и `JSESSIONID`.
- CVE-2019-8449 перечисляет пользователей анонимно.
- CVE-2023-22527 — Velocity SSTI → RCE.
- REST API часто открыт и отдаёт тикеты/секреты.
- Jira и Confluence связаны — проверяй обе.

## Шаг 9: как читать advisories Atlassian

Atlassian публикует security-бюллетени с полями: продукт, **affected versions**, fixed versions, CVSS, требует ли аутентификации. Приоритет — **pre-auth RCE** (как CVE-2022-26134 в Confluence) и **обходы аутентификации** (как CVE-2023-22515). Сопоставив версию с affected range, ты точно знаешь, применима ли уязвимость, — и не тратишь время на PoC для пропатченной сборки.

## Шаг 10: как оценивать импакт Jira-находки

SSTI/RCE = контроль сервера (критический). Обход аутентификации = доступ к управлению задачами и проектами (высокий). Перечисление пользователей = основа для брутфорса/фишинга (средний, но усиливает другие атаки). Утечки через API = доступ к тикетам с секретами (высокий). В отчёте указывай конкретику и связь с AD.

## Шаг 11: как защититься от Jira-атак

Защита: обновление до fixed-версий; отключение анонимного доступа к `/rest/api/`; ограничение доступа к `/secure/`; мониторинг URL с шаблонными выражениями (`${...}`). Для атакующего: свежая Jira закрывает известные CVE, но конфигурация (открытые API, слабые права проектов) остаётся вектором.

## Шаг 12: как проверить Jira-версию надёжно

Кроме `/secure/Dashboard.jspa`, версию отдают: `/rest/api/2/serverInfo` (JSON с `version` и `buildNumber`), страница `/secure/AboutPage.jspa`. Точная версия (включая buildNumber) критична: CVE-2023-22527 указывает конкретные диапазоны, и «Jira 9» недостаточно.

## Шаг 13: как оформить находку в отчёте

Для Jira-находки укажи: продукт и точную версию; применимый CVE; подтверждение (например, `${7*7}` → `49`); импакт (доступ к проектам/тикетам с секретами); связь с Confluence и AD. И отдельно — найденные в тикетах секреты (пароли, токены), потому что именно они чаще всего и представляют ценность.

## Шаг 14: как связать Jira с общим планом

Jira — это «журнал работы» компании. В тикетах и комментариях часто утекают: пароли от стендов, внутренние URL, детали архитектуры, токены. Поэтому ценность Jira — не только в RCE, но и в **контенте**. После доступа (или через открытый API) ищи секреты в задачах — это часто короче, чем искать RCE.

## Шаг 15: типовые ошибки при работе с Jira

Ошибка первая — не проверить перечисление пользователей (CVE-2019-8449), а сразу гнать RCE. Вторая — проверять SSTI командой вместо арифметики (шумно и опасно). Третья — игнорировать открытый REST API, который отдаёт тикеты анонимно. Четвёртая — забыть про соседний Confluence (общая инфраструктура).
