## Вопрос, с которого всё начинается

Sitecore — одна из самых дорогих и «серьёзных» CMS. На ней сидят банки, ритейл, крупные бренды. Ломать её сложно, но находки максимально ценны: за ней персональные данные и интеграции. Sitecore — .NET-приложение, поэтому центральные векторы — **обход аутентификации** и **десериализация**. Разберём, с чего начинать.

## Наш пример: корпоративный портал на Sitecore

Цель — `https://corp.target.example`. Фингерпринт:

```
$ whatweb -a 3 https://corp.target.example
https://corp.target.example [200 OK] Sitecore, ASP.NET, Set-Cookie[.AspNetCore.Cookies=...]
```

Пути `/sitecore/`, `/sitecore/login`, `/sitecore/api/` — подписи. Версию часто отдаёт специальный эндпоинт или заголовок:

```
$ curl -sI https://corp.target.example/ | grep -i 'sitecore\|x-powered'
$ curl -s 'https://corp.target.example/sitecore/api/ssc/...' 
```

Точная версия критична: у Sitecore есть CVE с узкими диапазонами (в том числе критические обходы аутентификации).

## Шаг 1: обход аутентификации в /sitecore/api

Sitecore имеет внутренний API (`/sitecore/api/ssc/`). Исторически часть эндпоинтов не проверяла права, отвечая анонимному пользователю. Проверка — запрос без cookie:

```
$ curl -s 'https://corp.target.example/sitecore/api/ssc/aggregate/content/Items' -H 'Accept: application/json'
```

`200` с данными — обход. Через такие эндпоинты можно читать контент, настройки, а в некоторых версиях — создавать/менять объекты.

## Шаг 2: десериализация в Sitecore

Sitecore обрабатывает сериализованные структуры (настройки, рендер, кэш). Небезопасная десериализация ведёт к .NET-гаджетам. Инструмент — `ysoserial.net`:

```
$ ysoserial.exe -g TypeConfuseDelegate -f BinaryFormatter -c "cmd /c whoami"
```

Payload доставляется в параметр, который уходит в десериализацию. Точный параметр зависит от версии; его находят в исходниках или в публичных PoC.

## Шаг 3: утечки ключей и ViewState

Как и в Umbraco, `machineKey` из `web.config` позволяет подписать ViewState. Если есть чтение файлов — добываем конфиг, затем строим ViewState-payload. Это надёжный путь к RCE.

## Шаг 4: путь к RCE и закрепление

Цепочка: обход API → доступ к админ-функциям → загрузка модуля/пакета с .NET-кодом → RCE. Либо: утечка `machineKey` → ViewState → `ysoserial.net` → RCE. После RCE — закрепление (веб-шелл, scheduled task) — только при явном разрешении.

## Шаг 5: автоматизация

```
$ nuclei -u https://corp.target.example -tags sitecore -silent
[CVE-2019-XXXX] [http] [critical] https://corp.target.example/sitecore/...
```

Плюс ручная проверка обхода и версии.

## Шаг 6: как не навредить

Sitecore — критичная система крупной компании. Падение портала = реальный ущерб. Поэтому: никаких массовых деструктивных payload'ов; ViewState и десериализацию тестируй на стенде или с безобидным маркером (`id`/DNS); не создавай реальных пользователей без разрешения.

## Шаг 7: чек-лист по Sitecore

1. Версия (`/sitecore/`, заголовки).
2. Открытые `/sitecore/api/` без auth.
3. Точки десериализации.
4. Утечка `machineKey`/конфигов.
5. Возможность загрузки модуля.
6. Сопоставление с CVE.

## Sitecore: ключи, machineKey и ViewState

Sitecore — .NET-приложение на IIS, поэтому классические векторы — обход аутентификации в API и десериализация. Ключ к последней — `machineKey` из `web.config`. Sitecore исторически поставлялся с предсказуемыми/дефолтными ключами, и если админ их не сменил, ViewState можно подделать. Проверяют так: сравни `validationKey` с публично известными дефолтами Sitecore; если совпадает — это находка высокой критичности.

```bash
# web.config доступен через утечку каталога/LFI
grep -iA2 'machineKey' web.config
```

Дальше — та же схема, что и в SharePoint: собрать ViewState-полезную нагрузку `ysoserial.net` с этими ключами. Параллельно проверяют `/sitecore/api/` на неаутентифицированные эндпоинты и `Sitecore.Update` на десериализацию.

## Оценка импакта и что писать в отчёт

Импакт Sitecore-находки зависит от того, что даёт доступ. Обход аутентификации в публичном API — чтение данных, возможно изменение контента. Подделка ViewState с дефолтным `machineKey` — RCE под учёткой пула приложений, то есть контроль над сайтом и потенциально над хостом. В отчёте разделяй: подтверждённое (что реально сработало), ожидаемое (что даёт следующий шаг) и требования (какие ключи/версии нужны). Не преувеличивай: «возможен RCE при условии дефолтного ключа» — это не «RCE подтверждён».

## Sitecore: полный путь от версии до RCE

Систематический подход. Шаг 1 — версия: Sitecore отдаёт её в заголовке `X-Sitecore-Version` (иногда), в `/sitecore/shell/`, в путях `_layouts`. Шаг 2 — публичные эндпоинты: `/sitecore/api/`, `/sitecore/admin/`, `-/item/`, `-/media/`. Шаг 3 — проверка на дефолтные ключи: если `machineKey` в `web.config` совпадает с известным дефолтом, ViewState подделывается. Шаг 4 — десериализация в специфичных для Sitecore точках (анализатор трафика, экспорт/импорт контента).

```bash
curl -sk https://T/sitecore/api/ssc/aggregate/content/ -o /dev/null -w '%{http_code}\n'
curl -sk https://T/-/item/sitecore/content -o /dev/null -w '%{http_code}\n'
```

Ключевая мысль: не все Sitecore-эндпоинты должны быть анонимны. Любой, отдающий данные без аутентификации, — находка, даже без RCE.

## Sitecore: практика и безопасность

Для проверки десериализации не запускай destructive-команды. Достаточно доказать, что объект создаётся (например, вызвать вычисление, выводящее фиксированный результат, или задержку). Публичные PoC читай внимательно: они часто рассчитаны на конкретную версию и конкретные установленные модули, и слепое применение может уронить сайт. Фиксируй версию, ключи и точный эндпоинт — это основа отчёта.

## Итог по Sitecore

Sitecore сводится к двум векторам: обход аутентификации в API и десериализация через `machineKey`/ViewState. Практический маршрут — версия → эндпоинты → ключи → полезная нагрузка. Критичность зависит от ключей: дефолтный `machineKey` превращает находку в RCE, уникальный — ограничивает чтением. В отчёте разделяй подтверждённое и условное, указывай версию и точный эндпоинт.

## Мини-шпаргалка по Sitecore

Версия → `/sitecore/api/`, `/sitecore/admin/`, `-/item/` → `machineKey` в `web.config` (дефолт?) → ViewState-полезная нагрузка (`ysoserial.net`). Критичность зависит от ключей: дефолтный `machineKey` = RCE, уникальный = ограничение.

## Итог и что проверять в первую очередь

Для Sitecore приоритет такой: точная версия, затем публичные эндпоинты, затем `machineKey`. Версия определяет, какие CVE применимы. Публичные эндпоинты (`/sitecore/api/`, `/sitecore/admin/`, `-/item/`) показывают, что доступно анонимно. `machineKey` из `web.config` — ключ к ViewState-атаке: если он дефолтный, находка критическая; если уникальный, RCE через ViewState недостижим.

Рекомендации: обновить Sitecore до поддерживаемой версии; убрать анонимный доступ к админским и API-эндпоинтам; сменить `machineKey` на уникальный и ротировать его после любого инцидента; ограничить доступ к `web.config`; включить логирование десериализационных ошибок. В отчёте разделяй подтверждённое (что реально доступно анонимно) и условное (что даст RCE при дефолтном ключе).

## Что мы теперь знаем

- Sitecore узнаётся по `/sitecore/` и ASP.NET-заголовкам.
- `/sitecore/api/ssc/` исторически содержал обходы аутентификации.
- Десериализация + `ysoserial.net` = RCE.
- `machineKey` + ViewState = RCE.
- На критичных системах — только неразрушающие проверки.

## Шаг 8: как находить уязвимые версии Sitecore системно

Sitecore-версии привязаны к конкретным CVE, часто с узкими диапазонами. Определив версию, сверяй её с базой (NVD, Sitecore Security Bulletin). Полезно искать не только «Sitecore CVE», но и CVE смежных компонентов: Sitecore использует ASP.NET, Solr, собственные модули (`Sitecore.XConnect`, `Sitecore.ExperienceForms`). Уязвимость часто в модуле, а не в ядре.

```
$ nuclei -u https://corp.target.example -tags sitecore -silent
[CVE-2019-XXXX] [http] [critical] https://corp.target.example/sitecore/api/ssc/...
```

## Шаг 9: как читать публичный PoC для Sitecore

Публичные PoC для Sitecore часто выглядят как скрипт на Python/.NET, отправляющий запрос с payload. Прежде чем запускать: прочитай, куда он шлёт данные (должен на твой слушатель), что пишет на диск, не деструктивен ли. Перепиши колбэки. Учти, что Sitecore-цели часто под наблюдением (SOC), поэтому шумные PoC могут привести к блокировке.

## Шаг 10: как оценивать импакт Sitecore-находки

Обход `/sitecore/api/` без auth = доступ к контенту и, возможно, к управлению (высокий). RCE через десериализацию = полный контроль (критический). Утечка `machineKey` = RCE-путь (критический). Интеграционные ключи = выход в корпоративные системы (критический по последствиям). В отчёте — точные доказательства по каждому пункту.

## Шаг 11: где Sitecore чаще всего отдаёт данные анонимно

Помимо `/sitecore/api/ssc/`, анонимные утечки бывают в: (1) эндпоинтах поиска/индекса (Solr), (2) превью-режиме (`?sc_mode=preview`), (3) `sitecore/admin/` при отключённой защите, (4) сервисах аналитики (`/sitecore/api/ao/`). Каждый из них стоит проверить запросом без cookie и посмотреть, приходит ли `200` с данными.

## Шаг 12: как отличить реальную находку от ложной

Sitecore часто отдаёт `200` на несуществующие пути (мягкие 404). Поэтому «200» сам по себе — не доказательство. Смотри на **тело**: если пришёл JSON с данными/структурой — эндпоинт реально отвечает. Если пришла HTML-страница «не найдено» с кодом 200 — это мягкий 404, и вывод делать нельзя. Это классическая ошибка при работе с CMS на ASP.NET.

## Шаг 13: чек-лист по Sitecore

1. Версия и модули.
2. Анонимные `/sitecore/api/` (проверять тело, не только код).
3. Точки десериализации.
4. Утечка `machineKey`/конфигов.
5. Возможность загрузки модуля.
6. Сопоставление с CVE (ядро + модули).

## Шаг 14: как связать Sitecore с общим планом атаки

Sitecore — узел цифрового опыта крупной компании. За ним: CDN, поисковый кластер (Solr/Azure Search), CRM, аналитика, SSO. Компрометация Sitecore даёт доступ к **персональным данным клиентов** и к **интеграционным ключам**, которые открывают CRM и платёжные системы. Поэтому Sitecore-цель почти всегда высшего приоритета — не из-за технологии, а из-за данных.

Практический приём: после доступа к конфигам выпиши все **эндпоинты интеграций** (CRM, платежи, аналитика). Каждый — потенциальная точка расширения атаки. В отчёте покажи цепочку: сайт → конфиг → ключ интеграции → корпоративная система.

## Шаг 15: типовые ошибки при работе с Sitecore

Ошибка первая — доверять коду `200` без проверки тела (мягкие 404). Вторая — гонять тяжёлые десериализационные payload'ы на проде. Третья — игнорировать модули (CVE часто в них, а не в ядре). Четвёртая — забывать, что Sitecore-цели под SOC: шумные сканы приводят к блокировке и раскрытию. Работай точечно.
