## Вопрос, с которого всё начинается

Joomla — третья по популярности CMS после WordPress и Drupal. Её архитектура необычна: вся функциональность разбита на **компоненты** с именами вида `com_<name>`. Понимание этой схемы — ключ к Joomla: зная, какой компонент стоит и какой у него номер версии, ты почти всегда найдёшь уязвимость в публичной базе.

## Наш пример: сайт на Joomla

Цель — `https://news.target.example`. Снимем фингерпринт:

```
$ whatweb -a 3 https://news.target.example
https://news.target.example [200 OK] Joomla, MetaGenerator[Joomla! - Open Source Content Management]
```

Версию `whatweb` не показал. Joomla прячет её, но есть служебные файлы. Точную версию даёт манифест:

```
$ curl -s https://news.target.example/administrator/manifests/files/joomla.xml | grep -o '<version>[^<]*' | head -1
<version>3.9.24
```

Joomla **3.9.24** — старая ветка 3.x, у неё много известных CVE. Дальше нам нужно понять, какие **компоненты** установлены.

## Шаг 1: структура Joomla и где искать вход

Joomla обрабатывает запросы так: URL вида `index.php?option=com_<name>&task=<...>` указывает на компонент и задачу внутри него. Это значит, что **перебор компонентов** — это перебор входных точек.

Типовые служебные пути:

| Путь | Назначение |
|---|---|
| `/administrator/` | панель администратора |
| `/components/com_users/` | управление пользователями |
| `/components/com_contact/` | форма контактов |
| `/index.php?option=com_config` | конфигурация |
| `/index.php?option=com_ajax` | AJAX-точка (частый вектор RCE) |

Компонент `com_ajax` особенно интересен: он вызывает методы компонентов по имени, и если в методе нет проверки прав — выполняется чужой код.

## Шаг 2: перечисление компонентов и версий

Перечислим установленные расширения:

```
$ joomscan -u https://news.target.example
[+] Joomla version: 3.9.24
[+] Components found:
    com_contact  (3.9.24)
    com_jce      (2.8.0)   — outdated
    com_hdwplayers ...
```

`com_jce` версии 2.8.0 — редактор JCE, у него есть известные баги (в т.ч. object injection и RCE в старых версиях). Теперь у нас есть точные версии для поиска PoC.

## Шаг 3: object injection — почему это Joomla-специфика

Joomla активно использует PHP-сериализацию для хранения настроек и в компонентах. Если пользовательский ввод проходит через `unserialize()` без проверки класса, возникает **PHP Object Injection** (инъекция объекта). При наличии подходящего **gadget chain** в установленных библиотеках это приводит к RCE.

Типовой сценарий: уязвимый параметр принимает сериализованную строку; мы подставляем объект из цепочки гаджетов (например, из библиотек, которые тянет Joomla или её расширения), и при деструктуризации срабатывает магический метод `__destruct`/`__wakeup`, выполняющий наш код.

Проверка на уязвимость — отправка сериализованного объекта и наблюдение за ошибками/поведением:

```
$ curl -s 'https://news.target.example/index.php?option=com_jce&task=...&data=O:8:"stdClass":0:{}'
```

Ошибка «cannot instantiate class» сигналит, что данные десериализуются.

## Шаг 4: CVE-цепочки Joomla

У Joomla 3.x есть несколько громких цепочек:

- **CVE-2015-8562** — object injection → RCE через заголовок `User-Agent` (классика, ломала все Joomla 1.5–3.4.4).
- **CVE-2016-8869 / 8873** — повышение привилегий через регистрацию пользователя.
- **CVE-2019-10945** — обход директории в `com_media`.

Логика работы с ними одна: определяем точную версию → ищем CVE для этой версии → берём публичный PoC → читаем его → проверяем на цели. CVE-2015-8562, например, эксплуатируется одним запросом с полезной нагрузкой в `User-Agent`, потому что Joomla сериализовала его для логов и десериализовала обратно.

## Шаг 5: админка и RCE через шаблоны

Если удалось войти в `/administrator/`, дальше — как в WordPress: Joomla позволяет редактировать **шаблоны** (PHP-файлы) прямо из админки. Правка файла шаблона = исполнение кода. Тот же принцип «войти → загрузить/править код».

## Что мы теперь знаем

- Joomla строится из компонентов `com_<name>`; URL указывает на компонент и задачу.
- Точную версию даёт `/administrator/manifests/files/joomla.xml`.
- Компоненты и их версии перечисляет `joomscan`.
- Object injection — типовая Joomla-проблема (сериализация + gadget chain).
- Есть исторические CVE-цепочки (CVE-2015-8562 и др.), привязанные к версиям.
- Из админки RCE достигается правкой шаблона.

## Шаг 6: перечисление компонентов вручную

`joomscan` полезен, но не всегда доступен. Компоненты находят руками — по характерным путям. Список установленных расширений частично виден в HTML и в манифестах:

```
$ curl -s https://news.target.example/ | grep -oE 'components/com_[a-z0-9]+' | sort -u
components/com_contact
components/com_users
components/com_content
```

Дополнительно проверяют известные уязвимые расширения по их «паспортным» файлам:

```
$ for c in com_jce com_hdwplayers com_jdownloads; do
    echo -n "$c -> "
    curl -s -o /dev/null -w '%{http_code}\n' "https://news.target.example/components/$c/"
  done
com_jce -> 200
com_hdwplayers -> 404
com_jdownloads -> 403
```

`200` у `com_jce` значит, что каталог существует. Версия JCE видна в его XML-манифесте:

```
$ curl -s https://news.target.example/administrator/components/com_jce/jce.xml | grep -o '<version>[^<]*'
<version>2.8.0
```

Теперь у нас точная версия расширения — ищем CVE.

## Шаг 7: типичные ошибки и что писать в отчёт

Ошибка первая — **путать Joomla с WordPress** по слову «com_» в URL. В Joomla путь `index.php?option=com_x` — это её родная схема, а не признак чего-то ещё. Ошибка вторая — гнать `wpscan` по Joomla (бесполезно) вместо `joomscan`. Ошибка третья — считать версию ядра достаточной: в Joomla ломаются **расширения**, поэтому инвентарь компонентов обязателен.

Хорошая запись в отчёт:

- стек: Joomla 3.9.24 / PHP 8.x;
- ядро: устаревшая ветка 3.x, есть публичные CVE (перечислить подходящие по версии);
- расширение: `com_jce 2.8.0` — устаревшее, потенциально уязвимое;
- вектор: object injection в параметре расширения (требует проверки).

Как и везде, каждое утверждение подкрепляем сохранённым запросом и ответом. Для object injection достаточно зафиксировать, что данные уходят в `unserialize()` — по поведению (ошибка о классе) или по коду, если он доступен.

## Шаг 8: закрепление — Joomla-цепочка на практике

История целиком. Цель: Joomla 3.9.24. Шаг 1 — версия из манифеста. Шаг 2 — перечисление компонентов (`joomscan` или вручную). Шаг 3 — находим устаревшее расширение (например, `com_jce 2.8.0`). Шаг 4 — ищем CVE для этой версии. Шаг 5 — проверяем безопасным запросом (без деструктивных операций). Шаг 6 — при подтверждении эксплуатируем: object injection → RCE или вход в админку → правка шаблона.

Что важно усвоить: **в Joomla «версия ядра» — не приговор, приговор — версия расширения**. Свежее ядро с устаревшим `com_`-компонентом уязвимо точно так же. Поэтому инвентарь расширений обязателен, и делать его надо сразу, а не после неудачных попыток на ядре.

И правило безопасности: не запускай чужие PoC без чтения. В Joomla-мире много «эксплойтов», которые на деле стирают файлы или шлют данные автору.

## Куда дальше

Дальше — Magento и Adobe Commerce: там правят бал SQLi и цепочки вида CosmicSting, а также сложная структура модулей. А пока запомни: **в Joomla ищи компонент и его версию — остальное это CVE-поиск.**

- Пентест e-commerce и новостных сайтов на Joomla.

- CTF: задания с конкретной версией и компонентом.
