## Вопрос, с которого всё начинается

Ты собрал список поддоменов `target.com` и видишь среди них `blog.target.com`. Открываешь его в браузере — а там страница «There isn't a GitHub Pages site here». Странно: поддомен компании, а обслуживает его GitHub.

Вопрос: если этот поддомен указывает на внешний сервис, которого больше нет, — можно ли **занять** его самому? Если да, ты получаешь контроль над адресом в домене компании, не ломая ни одной уязвимости в коде. Это называется **subdomain takeover**, и сегодня мы пройдём его от `dig` до доказательства контроля.

## Наш пример

Есть компания `target.com`. Её инженеры когда-то завели блог на GitHub Pages и привязали к нему поддомен. Потом блог удалили, а DNS-запись забыли. Смотрим, куда ведёт поддомен:

```bash
$ dig +short CNAME blog.target.com
target-org.github.io.
```

`CNAME` — это запись DNS, которая говорит «это имя на самом деле указывает вон туда». Здесь `blog.target.com` указывает на `target-org.github.io` — то есть на GitHub Pages-страницу организации `target-org`.

## Шаг 1: проверяем, что цель ещё жива

CNAME сам по себе — не дыра. Нужно, чтобы сервис, на который он указывает, **не содержал ресурса**. Запрашиваем поддомен и смотрим ответ:

```bash
$ curl -s -i http://blog.target.com/ | head -5
HTTP/1.1 404 Not Found
Server: GitHub.com
...
There isn't a GitHub Pages site here.
```

Строка `There isn't a GitHub Pages site here.` — это **отпечаток** (fingerprint) сервиса: характерный текст ошибки, по которому узнают, что ресурс не привязан. GitHub отдаёт его, когда репозитория с таким именем нет. Именно это сочетание — «CNAME на GitHub + отпечаток "страницы нет"» — и делает поддомен кандидатом на захват.

## Шаг 2: подтверждаем, что имя свободно

Нам нужно понять, можно ли завести ресурс `target-org` заново. Проверяем, что аккаунт/страница на GitHub отсутствует:

```bash
$ curl -s -o /dev/null -w '%{http_code}\n' https://target-org.github.io/
404
```

`404` на корневой странице организации — имени `target-org` на GitHub сейчас никто не владеет. Значит, его можно зарегистрировать, привязать к своему репозиторию и включить GitHub Pages. С этого момента `blog.target.com` начнёт отдавать **твой** контент.

## Шаг 3: занимаем и доказываем контроль

Важно: занятие ресурса — активное действие, и делать его можно **только в рамках разрешённого scope**. В CTF ты создаёшь репозиторий `target-org.github.io`, включаешь Pages и кладёшь туда безобидный маркер:

```bash
$ echo 'taken over by pentest' > index.html
$ curl -s https://blog.target.com/
taken over by pentest
```

Ответ поддомена теперь — твой текст. Это и есть **доказательство**: DNS-запись + отпечаток «ресурса нет» + фактический контроль. В bug bounty часто достаточно первых двух — сам захват показывают осторожно, чтобы не нарушить правила.

## Почему это опасно

Захваченный поддомен — это доверие домена в чужих руках:

- **Фишинг.** `login.target.com` с формой входа выглядит абсолютно легитимно.
- **Кража cookie.** Если cookie выставлена как `Domain=.target.com`, её получит и поддомен.
- **Обход CSP.** Если `*.target.com` в белом списке `script-src`, твой поддомен исполнит скрипт.
- **OAuth `redirect_uri`.** Домены из белого списка уводят код авторизации к тебе.

Именно поэтому takeover — стабильно оплачиваемый класс находок, хотя «дыры в коде» тут нет.

## Шаг 4: как искать это массово

Вручную проверять по одному поддомену бессмысленно — их бывают сотни. Пайплайн состоит из трёх шагов.

Сначала собираем поддомены (плюс их даёт `crt.sh` — база публичных TLS-сертификатов, где видны имена):

```bash
$ subfinder -d target.com -silent > subs.txt
$ curl -s 'https://crt.sh/?q=%25.target.com&output=json' | jq -r '.[].name_value' | sort -u >> subs.txt
```

Затем резолвим записи и вытаскиваем только CNAME:

```bash
$ dnsx -l subs.txt -cname -resp -silent | tee cnames.txt
blog.target.com [target-org.github.io]
```

И наконец прогоняем сканером отпечатков:

```bash
$ subjack -w subs.txt -t 100 -timeout 30 -ssl -v
[Vulnerable] blog.target.com
$ nuclei -l subs.txt -tags takeover -silent
[takeover-github-pages] [http] https://blog.target.com
```

Каждая строка `[Vulnerable]`/`[takeover-...]` — уже подтверждённый кандидат. Список актуальных отпечатков поддерживает проект **can-i-take-over-xyz**; его стоит подтягивать в свой конфиг, потому что сервисы меняют тексты ошибок.

## Если не сработало

- Отпечаток не совпал, но CNAME ведёт на **S3**: проверь `NoSuchBucket` — если бакет удалён, имя можно пересоздать.
- `dig` не показывает CNAME, но поддомен существует: возможно, это `A`-запись на освобождённый облачный IP (см. глубокий урок про NS/MX/A-тейковер).
- Имя уже занято — takeover невозможен, но сама находка (запись на чужой ресурс) всё равно заслуживает заметки.
- **Wildcard DNS** (`*.target.com`) может маскировать висящие записи: любой несуществующий поддомен «отвечает», и отпечатки нужно смотреть внимательнее.

## Как это защищают

Понимание защиты помогает и в отчёте, и в поиске. Правильная гигиена проста:

1. Удалять DNS-запись **до** отключения внешнего сервиса, а не после.
2. Не выдавать поддомены под произвольные внешние хостинги без учёта.
3. Регулярно (по расписанию) прогонять `dnsx`/`subjack` по своему периметру — так висящую запись находят раньше атакующего.
4. Мониторить `crt.sh` на новые имена в своём домене.

Ломается всё обычно на одном и том же: команда закрывает проект в SaaS, а запись остаётся. Разовый скан тут не поможет — нужен именно **регулярный** аудит.

## Что мы теперь знаем

- Subdomain takeover — это занятие ресурса, на который указывает осиротевшая DNS-запись.
- Возникает, когда ресурс удалили, а `CNAME` оставили.
- Признак: CNAME на внешний сервис + **отпечаток** «ресурс не существует».
- Отпечатки: GitHub Pages (`There isn't a GitHub Pages site here`), S3 (`NoSuchBucket`), Heroku (`No such app`).
- Контроль подтверждают безобидным маркером на захваченном поддомене.
- Риск: фишинг, кража cookie, обход CSP и OAuth-whitelist.

## На что смотреть дальше

- Не путай «CNAME на правильный сервис» с takeover — нужен именно ответ «ресурса нет».
- Всегда проверяй, свободно ли имя: иногда его уже пересоздали.
- Ищи поддомены не только перебором, но и в CT-логах (`crt.sh`), в JS-бандлах и мобильных приложениях.
- Помни про NS/MX/A-записи — они дают ещё более серьёзный захват (это следующий урок).
- Занимай ресурс только в рамках scope: в реальном тесте достаточно доказательства.
- Проверяй не только сам поддомен, но и связанные с ним записи: `www`, `mail`, `dev`, `staging` — забытые записи чаще всего живут именно на «неважных» именах.

## Куда дальше

В следующем уроке мы углубимся: посмотрим не только на `CNAME`, но и на `NS`, `MX` и `A`-записи — они позволяют захватить **целую зону** или перехватить почту домена. А пока главное запомни: если DNS-запись ведёт туда, где ресурса уже нет, — эту запись можно занять.

## Где пригодится

- **CTF (Web):** takeover-задачи требуют найти висящий CNAME и занять сервис ради флага.
- **Bug bounty:** subdomain takeover — стабильно оплачиваемый класс (medium/high).
- **Пентест:** инвентаризация поддоменов и проверка CNAME — часть внешнего периметра.
- **Работа (AppSec/Dev):** удаление DNS-записей при выводе сервисов — базовая гигиена.
