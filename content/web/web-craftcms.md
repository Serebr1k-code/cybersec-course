## Вопрос, с которого всё начинается

Craft CMS — современная CMS на фреймворке **Yii2**, популярная у дизайнерских студий и продуктовых команд. Она аккуратнее WordPress, но у неё есть две родовые черты: **SSRF** в функциях, которые ходят по URL (обработка изображений, трансформации), и **Yii-гаджеты** — если где-то всплывёт object injection, цепочка классов Yii доведёт до RCE. Плюс свежие критические CVE. Разберём.

## Наш пример: сайт на Craft CMS

Цель — `https://craft.target.example`. Фингерпринт:

```
$ whatweb -a 3 https://craft.target.example
https://craft.target.example [200 OK] Craft CMS, X-Powered-By[PHP/8.1],
  Set-Cookie[CRAFT_CSRF_TOKEN=...]
```

Cookie `CRAFT_CSRF_TOKEN` — подпись Craft. Версию уточняем:

```
$ curl -sI https://craft.target.example/admin/login | grep -i 'x-powered\|set-cookie'
```

Craft отдаёт версию в `X-Powered-By` (иногда) или в `/admin`-странице. Точная версия критична: у Craft есть CVE с очень узкими диапазонами.

## Шаг 1: CVE-2023-41892 — критический RCE

**CVE-2023-41892** — критическая уязвимость Craft CMS (версии 4.0.0–4.4.14), позволяющая **выполнить код без аутентификации**. Она эксплуатируется через эндпоинт, который принимает параметры и подставляет их в небезопасный вызов.

Проверка и эксплуатация — публичный PoC, который шлёт специально собранный запрос на `/index.php?p=admin/actions/...`. Логика: через параметры добираемся до вызова, который выполняет PHP-код.

```
$ curl -s 'https://craft.target.example/index.php?p=admin/actions/...' \
  -d 'action=conditions/render&test[objectClass]=...'
```

Точные параметры — в публичном PoC; читай его, репойнти колбэки, не запускай слепо.

## Шаг 2: SSRF через трансформации изображений

Craft умеет тянуть изображения по URL и применять трансформации (ресайз, обрезка). Если URL приходит от пользователя, а сервер его загружает — это **SSRF**. Проверяем:

```
$ curl -s 'https://craft.target.example/actions/assets/generate-transform?url=http://169.254.169.254/latest/meta-data/'
```

Если ответ содержит данные метаданных облака — SSRF подтверждён, и мы получили временные креды роли инстанса. Это классическая связка «SSRF → облако».

Трансформации особенно опасны тем, что результат может кэшироваться и отдаваться, давая **вывод** (а не только слепое взаимодействие).

## Шаг 3: Yii gadget chains

Craft построен на Yii2. Если найден object injection (например, в небезопасной десериализации настроек), эксплуатируется через **Yii-гаджеты**: классы Yii, которые при деструктуризации вызывают `call_user_func`/запись файлов. Публичные цепочки (например, из исследований про Craft/Yii) дают RCE.

Поэтому Craft-атака часто выглядит так: SSRF/утечка → чтение `config/` → object injection → Yii gadget → RCE.

## Шаг 4: автоматизация

```
$ nuclei -u https://craft.target.example -tags craftcms -silent
[CVE-2023-41892] [http] [critical] https://craft.target.example/index.php?p=...
```

Плюс `cmseek`. Craft-цели часто за Cloudflare — учитывай возможные блокировки.

## Что мы теперь знаем

- Craft узнаётся по cookie `CRAFT_CSRF_TOKEN`.
- CVE-2023-41892 — неаутентифицированный RCE в 4.0.0–4.4.14.
- SSRF возможен через трансформации изображений (URL от пользователя).
- Object injection + Yii gadget chains = RCE.
- SSRF на Craft часто ведёт к облачным метаданным.

## Шаг 5: закрепление — цепочка Craft CMS целиком

История целиком. Цель: Craft CMS 4.4.14. Шаг 1 — cookie `CRAFT_CSRF_TOKEN` подтверждает движок. Шаг 2 — версия из `/admin`. Шаг 3 — проверка CVE-2023-41892 публичным PoC (неаутентифицированный RCE). Шаг 4 — если версия пропатчена, проверяем SSRF через трансформации изображений. Шаг 5 — SSRF к облачным метаданным за кредами. Шаг 6 — при object injection — Yii gadget chain.

Каждый шаг подтверждается доказательством: версия, ответ на PoC, данные из метаданных.

## Шаг 6: почему SSRF в Craft особенно удобен

Трансформации изображений дают **вывод** (отрендеренную картинку или текст), а не только слепое взаимодействие. Это значит, что SSRF здесь не «слепой»: результат запроса к внутреннему ресурсу возвращается нам. Отсюда прямой путь к чтению внутренних API, облачных метаданных и файлов (через поддерживаемые схемы).

Дополнительный нюанс: трансформации могут кэшироваться, и запрос к внутреннему ресурсу выполняется один раз, а результат отдаётся многократно — это снижает шум.

## Шаг 7: защита Craft

Защита: своевременное обновление (Craft выпускает security-релизы), ограничение исходящих соединений (egress) от сервера, валидация URL перед загрузкой изображений, отключение неиспользуемых функций. Для атакующего: egress-фильтр убивает SSRF к метаданным, а свежая версия закрывает CVE.

## Шаг 8: чек-лист по Craft CMS

1. Подтвердить движок (cookie).
2. Определить точную версию.
3. Проверить CVE по диапазону версий.
4. Проверить SSRF через трансформации.
5. Проверить object injection/Yii-гаджеты.
6. Сопоставить с базой уязвимостей.

## Шаг 9: как отличить Craft от других CMS на Yii

Craft — не единственная CMS на Yii2, поэтому подписью служит именно cookie `CRAFT_CSRF_TOKEN` и пути `/admin/login`, `/actions/`. Дополнительно помогает структура: Craft отдаёт `X-Powered-By` и характерные заголовки кэша. Не путай с другими Yii-приложениями: CVE у Craft специфичны, и «похожесть» на Yii ещё не значит, что применим Craft-PoC.

## Шаг 10: безопасная проверка CVE-2023-41892

Публичный PoC для CVE-2023-41892 — код, который выполняет команду. Прежде чем запускать: прочитай, куда он шлёт вывод (должен на твой слушатель), и убедись, что он не пишет файлы/не меняет данные. Безопасная проверка — команда-маркер, например `id` или DNS-запрос на подконтрольный домен. Если PoC шлёт результат на чужой хост — **перепиши** его.

## Шаг 11: как оценивать импакт Craft-находки

RCE без аутентификации (CVE-2023-41892) — максимальный импакт: полный контроль сервера, доступ к БД, интеграциям, внутренней сети. SSRF к облачным метаданным — высокий: временные креды роли инстанса выводят атаку в облако. В отчёте укажи конкретно: какой код исполнен, какие данные доступны, куда можно двигаться дальше.

## Шаг 12: как использовать SSRF-вывод на практике

SSRF через трансформации отдаёт результат, поэтому его превращают в **портсканер и файловый читатель**. Сканирование: перебирай `http://127.0.0.1:<port>/` и смотри, на каких портах ответ отличается от ошибки. Чтение файлов: если Craft поддерживает схему `file://` в URL изображения — читай локальные файлы (конфиг, `.env`).

```
$ curl -s 'https://craft.target.example/actions/assets/generate-transform?url=http://127.0.0.1:6379/'
```

Ответ (или его отсутствие) различается для открытого/закрытого порта — это и есть сигнал.

## Шаг 13: как не навредить

Трансформации кэшируются и нагружают CPU. Массовый перебор портов или больших изображений может **уронить сайт**. Поэтому: маленькие payload'ы, паузы, ограниченный список портов. На живом проде — только точечные проверки; полное сканирование — на стенде.

## Практика: подтверждаем CVE-2023-41892 безопасно

Craft CMS построен на фреймворке Yii2. Уязвимость CVE-2023-41892 (RCE через Yii-десериализацию и `Craft::createObject`) эксплуатируется POST-запросом к `/index.php?p=admin/actions/...`. Безопасный первый шаг — проверить, что инстанс вообще отвечает и является Craft:

```
$ curl -sI https://craft.target.example/admin/login | grep -iE 'set-cookie|x-powered'
Set-Cookie: CraftSessionId=...; path=/; HttpOnly
X-Powered-By: Craft CMS
```

`CraftSessionId` + `X-Powered-By: Craft CMS` — двойное подтверждение. Версию достаём из `/admin/utilities/system-report` (если открыт) или из `Craft::$app->getVersion()` в HTML футера. Только после точного сопоставления с патчем (< 4.4.15 / < 3.7.9) решаемся на эксплойт.

## Практика: SSRF через трансформации изображений

Craft умеет генерировать превью из удалённых изображений. Если в настройках включены remote-трансформации, параметр с URL картинки уходит на сервер, и Craft скачивает его. Подставив `http://169.254.169.254/latest/meta-data/iam/security-credentials/`, ты получаешь облачные креды. Это самый «тихий» вектор Craft: он не требует десериализации и часто не логируется как атака.

```
GET /actions/assets/generate-transform?url=http://127.0.0.1:6379/ HTTP/1.1
Host: craft.target.example
```

Ответ `Connection refused` против `timed out` позволяет отличить закрытый порт от фильтруемого — так строится карта внутренней сети.

## Практика: Yii gadget chains

Yii2-десериализация использует PHP-цепочки (phpggc). Для Craft подходит `phpggc Yii2/RCE1` — он генерирует сериализованный объект, который при `unserialize` вызывает `call_user_func` с твоей командой. Важно: цепочка должна соответствовать **версии Yii**, иначе `ClassNotFound`. Поэтому сначала определяем версию Yii (`/vendor/yiisoft/yii2/BaseYii.php` отдаёт версию, если открыт), затем генерируем подходящую цепочку:

```
$ phpggc -b Yii2/RCE1 system 'id' > payload.b64
```

И только потом отправляем в уязвимый параметр. Каждый неудачный вариант — это шум в логах, поэтому версию проверяем до, а не после.

## Таблица: цепочки и версии Craft/Yii

| Craft | Yii | Подходящая цепочка phpggc |
|---|---|---|
| 3.7.x | 2.0.45 | Yii2/RCE1 |
| 4.0–4.3 | 2.0.47 | Yii2/RCE1, Yii2/RCE2 |
| 4.4+ | 2.0.49 | исправлено (>= 4.4.15) |

## Как не навредить и как оформить

Craft — продакшен-сайт, и RCE через десериализацию легко превращается в падение PHP-процесса при кривой цепочке. Поэтому: (1) сначала подтверждай версию, (2) применяй минимальный безвредный payload (`id`/`whoami`), (3) фиксируй полный запрос и ответ, (4) не трогай базу и файлы. В отчёте укажи версию Craft и Yii, точный CVE, артефакт-доказательство и рекомендацию обновиться. Отдельно отметь SSRF как самостоятельную находку — он остаётся опасным даже там, где RCE уже пропатчен.

## Почему Craft — растущая цель

Craft CMS популярен среди агентств и медиа: он быстрый, «дизайнерский» и часто держит API (GraphQL) и вебхуки. Это значит, что вместе с классическими CVE (десериализация, SSRF) он даёт **GraphQL-поверхность**: интроспекция (`{__schema{types{name}}}`), батчинг запросов для обхода лимитов, глубоко вложенные запросы для DoS. Проверяй интроспекцию первым делом — если открыта, ты получаешь полную карту API. Второй момент — GraphQL часто отдаёт больше полей, чем нужно интерфейсу (утечка email, внутренних ID). Фиксируй каждую утечку отдельной находкой: в отчёте она весит меньше RCE, но вместе они дают полную картину и высокий совокупный риск.
