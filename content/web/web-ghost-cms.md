## Вопрос, с которого всё начинается

Ghost — CMS на Node.js, которую любят издатели, блогеры и продуктовые команды. Она проще «тяжёлых» enterprise-платформ, но у неё есть две родовые черты: она **ходит по URL** (импорт контента, вебхуки, интеграции) и у неё есть **Admin API** (`/ghost/api/admin/`). Первое даёт SSRF, второе — путь к захвату управления при слабых ключах. Разберём.

## Наш пример: блог на Ghost

Цель — `https://blog.target.example`. Фингерпринт:

```
$ whatweb -a 3 https://blog.target.example
https://blog.target.example [200 OK] Ghost, Node.js, X-Powered-By[Express]
```

Ghost отдаёт себя через `/ghost/`, `Content API` и мета-теги. Версию определяем по эндпоинту настроек:

```
$ curl -s 'https://blog.target.example/ghost/api/content/settings/?key=...' | head -c 200
{"settings":[{"key":"title","value":"Target Blog"},{"key":"version","value":"5.75.0"}]}
```

Версия **5.75.0**. У Ghost есть CVE, привязанные к диапазонам версий, поэтому точность важна.

## Шаг 1: Content API и утечки

Ghost делит API на **Content** (публичный, для сайта) и **Admin** (управление). Content API требует ключ, но ключи часто вшиты в JS-бандлы или видны в HTML:

```
$ curl -s https://blog.target.example/ | grep -oE 'key=[a-f0-9]{26}' | head -1
key=1a2b3c4d5e6f7a8b9c0d1e2f3a
```

С ключом Content API можно читать посты, теги, авторов, настройки — включая черновики и скрытые данные.

## Шаг 2: SSRF через импорт и вебхуки

Ghost умеет импортировать контент по URL и вызывать вебхуки. Если URL приходит от пользователя, сервер сходит по нему сам — это **SSRF**:

```
POST /ghost/api/admin/.../webhooks/  (или импорт)
{"url":"http://169.254.169.254/latest/meta-data/"}
```

В облаке это ведёт к метаданным и временным кредам. Даже без вывода (слепой SSRF) факт исходящего соединения подтверждается OOB-взаимодействием (DNS/HTTP на свой слушатель).

## Шаг 3: злоупотребление Admin API

Admin API (`/ghost/api/admin/`) защищён сессией или API-ключом. Проблемы возникают, когда:

- ключ админа утёк (в логах, в бэкапах, в JS);
- сессия предсказуема;
- эндпоинт не проверяет роль (staff-токен делает админское действие).

С Admin API можно создавать пользователей, менять настройки, публиковать контент — то есть **захватить управление сайтом**.

## Шаг 4: почему Ghost ценна для атакующего

Ghost-сайты часто связаны с **подписками и рассылками** — там база email-адресов. Утечка этой базы — персональные данные и риск рассылок от имени бренда. Плюс Admin API даёт «тихий» захват: контент меняется незаметно.

## Шаг 7: как не навредить

Вебхуки и импорт пишут данные. Массовые вызовы могут заспамить внешние системы и подписчиков. Поэтому проверяй SSRF **на свой слушатель**, а не на реальные внутренние сервисы, и не создавай реальных пользователей — только фиксируй возможность.

## Что мы теперь знаем

- Ghost узнаётся по `/ghost/`, Express и Content API.
- Версия доступна через Content API settings.
- Content API-ключ часто утекает в JS/HTML.
- SSRF возможен через импорт/вебхуки; ведёт к облачным метаданным.
- Admin API при слабых ключах = захват сайта.

## Шаг 8: как искать Content API ключ системно

Ключ Content API нужен фронтенду, поэтому он почти всегда где-то есть. Ищи в: (1) HTML-страниц (inline-скрипты), (2) JS-бандлах (`/assets/built/*.js`), (3) source maps, (4) сетевых запросах (DevTools/прокси). Регулярка — `key=[a-f0-9]{26}`:

```
$ curl -s https://blog.target.example/ | grep -oE 'key=[a-f0-9]{26}'
$ curl -s https://blog.target.example/assets/built/main.js | grep -oE 'key=[a-f0-9]{26}'
```

С ключом ты читаешь весь публичный контент, включая то, что не показано на сайте (черновики, скрытые страницы, метаданные авторов). Это разведка перед атакой на Admin API.

## Шаг 9: SSRF через OOB-подтверждение

Ghost-функции импорта/вебхуков могут быть слепыми (вывод не возвращается). Тогда факт SSRF подтверждают **OOB** (out-of-band) — исходящим соединением на твой слушатель. Подними DNS/HTTP-листенер (например, `interactsh` или `nc -lvnp 80`) и укажи его URL в функции импорта:

```
POST /ghost/api/admin/import/
{"url":"http://<твой-хост>/probe"}
```

Если пришёл запрос — SSRF есть, даже без вывода. Дальше можно целиться во внутренние адреса (`127.0.0.1`, `169.254.169.254`).

## Шаг 10: как отличить Ghost от другого Node-блога

Не путай Ghost с самописным Express-сайтом. Признаки Ghost: путь `/ghost/` (админка), эндпоинты `/ghost/api/content/` и `/ghost/api/admin/`, характерные заголовки и структура JSON. Если `/ghost/api/content/settings/` отвечает — это точно Ghost, и CVE-поиск ведётся по его версии.

## Шаг 11: почему у Ghost стоит проверять подписчиков

Ghost — издательская платформа, её главный актив — **база подписчиков** (email, имена, история рассылок). Если удалось войти в Admin API, эта база выгружается целиком. Импакт — персональные данные и возможность рассылать письма от имени бренда (фишинг на подписчиков). Поэтому в отчёте по Ghost утечка подписчиков указывается отдельным пунктом с количеством записей.

## Шаг 12: как не сломать рассылку

Ghost связан с почтовыми провайдерами. Тестовые вебхуки/импорты могут отправить реальные письма подписчикам. Поэтому: SSRF проверяй на свой слушатель, а не на внутренние сервисы; не триггерь массовые рассылки; не создавай реальных пользователей. Если сомневаешься — сначала на стенде.

## Шаг 13: чек-лист эксплуатации Ghost

1. Версия через Content API settings.
2. Content API ключ из JS/HTML.
3. SSRF (импорт/вебхуки) с OOB.
4. Admin API: роли, ключи, предсказуемость сессии.
5. Утечка подписчиков (при доступе).
6. Сопоставление версии с CVE.

## Шаг 14: как связать Ghost с общим планом веб-атаки

Ghost редко бывает конечной целью — чаще это **точка входа в контур** издателя или продуктовой команды. За блогом обычно стоят: почтовый сервис (рассылки), CDN, аналитика, а иногда и внутренние API, к которым Ghost обращается. Поэтому, получив SSRF, не останавливайся на метаданных — пройди по внутренней сети: какие сервисы доступны с сервера, есть ли там админки без аутентификации. Так «блог» превращается в «доступ к инфраструктуре».

И помни про приоритеты: если блог — единственный актив и данных в нём мало, вектор низкий. Если за ним подписчики и интеграции — высокий. Оценивай по ожидаемой ценности, а не по «интересности» технологии.

## Шаг 15: типовые ошибки при работе с Ghost

Ошибка первая — считать Ghost «простым» и пропускать Content API. Именно там ключ и версия. Ошибка вторая — проверять SSRF на реальных внутренних сервисах (можно задеть прод). Третья — путать Content API (публичный) и Admin API (привилегированный) и делать неверный вывод о доступе. Четвёртая — не читать публичный PoC перед запуском: в Node-мире встречаются «эксплойты», которые просто шлют данные автору.

## Практика: как достать Content API key

Ghost отдаёт публичный Content API по `/ghost/api/content/`. Для чтения постов нужен ключ `?key=<id>:<secret>`, и этот ключ **часто вшит в тему** — в JS-бандл. Достаём его:

```
$ curl -s https://blog.target.example/ | grep -oE 'contentKey["\x27: ]+[a-f0-9]{24}:[a-f0-9]{64}' | head -1
contentKey "6a1b2c3d4e5f6a7b8c9d0e1f:aaaaaaaa...": 
```

Или проще — из `/ghost/api/content/posts/?key=...`. Ключ публичный по дизайну, но с ним можно читать **черновики** (если `status=draft` не заблокирован) и получать `mobiledoc`/`lexical`-структуры с внутренними полями (авторы, email). Это уже утечка, которую Ghost «не считает» утечкой.

## Практика: SSRF через импорт и вебхуки

Ghost умеет импортировать контент по URL и вызывать вебхуки. Обе функции делают исходящие HTTP-запросы с сервера. Проверяем SSRF через вебхук-эндпоинт (нужен admin-токен) или через функцию импорта:

```
POST /ghost/api/admin/db/ HTTP/1.1
Host: blog.target.example
...
url=http://169.254.169.254/latest/meta-data/iam/security-credentials/
```

Если сервер — в AWS, ответ вернёт имя роли, а следующий запрос — сами креды. Даже без облака SSRF-as-portscan даёт карту внутренней сети: `http://10.0.0.5:9200/` (Elasticsearch) отвечает иначе, чем закрытый порт. Для OOB-подтверждения используй свой listener (например, `http://your-collab/`), чтобы увидеть входящий запрос.

## Практика: Admin API и его токены

Admin API (`/ghost/api/admin/`) защищён JWT, полученным на `/ghost/api/admin/session`. Проблема в том, что токены интеграций иногда утекают в: (1) исходниках темы, (2) логах, (3) публичных репозиториях, (4) CI-переменных. Найдя admin-токен, ты получаешь полный CRUD: создание постов, пользователей, изменение темы (а тема — это Handlebars, исполняемый сервером). Поэтому утечка admin-токена = потенциальный RCE через тему.

## Таблица: Ghost — что проверять

| Точка | Доступ | Что даёт |
|---|---|---|
| `/ghost/api/content/` | публичный key | посты, черновики, авторы |
| `/ghost/api/admin/` | JWT | полный CRUD, тема |
| Импорт контента | admin | SSRF |
| Вебхуки | admin | SSRF, OOB |
| Тема (Handlebars) | admin | RCE при правке |
| `/ghost/#/site` | браузер | админ-интерфейс |

## Как не сломать рассылку и как оформить

Ghost часто используют для рассылок (mailgun/sendgrid). Неосторожный импорт или правка темы может сломать отправку писем тысячам подписчиков — это репутационный и юридический риск. Поэтому: не трогай тему без согласования, не запускай массовый импорт, не удаляй посты. В отчёте разделяй находки по импакту: утечка Content API key — low/info; SSRF с доступом к metadata — high/critical; утечка admin-токена — critical (полный контроль). И всегда указывай, что **публичный Content API key не считается секретом** — это by design, поэтому не выдавай его за «утечку секрета» без доказательства доступа к закрытым данным.
