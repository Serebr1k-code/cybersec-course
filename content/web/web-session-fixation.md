В прошлом уроке мы заметили, что если сервер не меняет идентификатор сессии при логине — это опасно. Теперь разберём эту атаку как отдельную технику: **session fixation** (фиксация сессии). Она позволяет войти в чужой аккаунт, не зная пароля и не крадя cookie.

В этом уроке мы проведём **одну** атаку целиком на `shop.local`: получим анонимную сессию, навяжем её жертве и проверим, работает ли она после её логина.

## Наш пример: shop.local принимает id из URL

Проверим, принимает ли сайт идентификатор сессии из параметра URL:

```bash
$ curl -s -i 'https://shop.local/login?session=ATTACKER123' | grep -i 'set-cookie\|welcome'
Set-Cookie: session=ATTACKER123; Path=/
```

Сервер вернул нам cookie `session=ATTACKER123` — ровно то значение, что мы передали в URL. Значит, он **доверяет** идентификатору из параметра. Это и есть предпосылка атаки.

## Шаг 1: нормальный поток против уязвимого

Как должно быть: анонимный пользователь получает случайный id → логинится → сервер **выдаёт новый** id (ротация). Тогда старый id, который знал атакующий, становится бесполезен.

Как бывает: сервер принимает предложенный id и **сохраняет его** после входа. Тогда атакующий:

1. Получает валидный анонимный id (свой).
2. Навязывает его жертве.
3. Жертва логинится — id остаётся тем же.
4. Атакующий использует этот id → он внутри аккаунта жертвы.

Вся суть — в пункте 3: **ротация id при логине отсутствует**.

## Шаг 2: получаем анонимный id

Атакующий заходит на сайт и запоминает свой id:

```bash
$ curl -s -i 'https://shop.local/' | grep -i 'set-cookie'
Set-Cookie: session=ATTACKER123; Path=/
```

`ATTACKER123` — это идентификатор, который он теперь знает.

## Шаг 3: навязываем id жертве

Три классических способа доставить жертве этот id:

- **Ссылка с параметром.** Отправить жертве `https://shop.local/login?session=ATTACKER123`. Если сервер подхватывает id из URL — готово.
- **Поддомен (cookie tossing).** Если cookie действует на `.shop.local`, любой поддомен может её установить:

```js
document.cookie = "session=ATTACKER123; domain=.shop.local; path=/";
```

Скомпрометированный или уязвимый к XSS поддомен «подбрасывает» жертве наш id.
- **XSS.** Если на сайте есть XSS, а cookie без `HttpOnly`, то достаточно:

```html
<script>document.cookie="session=ATTACKER123; path=/"</script>
```

Жертва заходит на страницу, и её сессия становится нашей.

## Шаг 4: проверяем ротацию — главный тест

Это ключевой шаг. Проверяем, меняется ли `session` при логине:

```bash
# 1) заходим с навязанным id и логинимся
$ curl -s -i -b 'session=ATTACKER123' -X POST 'https://shop.local/login' \
    -d 'username=victim&password=correct' | grep -i 'set-cookie'
Set-Cookie: session=ATTACKER123; Path=/

# 2) атакующий использует тот же id
$ curl -s -b 'session=ATTACKER123' 'https://shop.local/account' | grep -o 'Добро пожаловать, [^<]*'
Добро пожаловать, victim
```

Значение `ATTACKER123` не изменилось после логина, и с ним мы попали в аккаунт `victim`. **Фиксация подтверждена.** Если бы сервер выдал новый id, шаг 2 вернул бы форму логина.

Проверять ротацию надо не только при входе, но и при **повышении привилегий** и **смене пароля**: там id тоже обязан обновляться.

## Шаг 5: защита

Правильное управление сессией перевыпускает идентификатор в момент любого изменения уровня доверия:

| Событие | Действие сервера |
|---------|------------------|
| Анонимный визит | выдать случайный id (128+ бит) |
| Успешный логин | `regenerate` id |
| Смена пароля | `regenerate` + инвалидировать прочие сессии |
| Повышение роли | `regenerate` id |
| Logout | уничтожить серверную сессию, не только cookie |

Плюс: не принимать id из URL, ставить `HttpOnly`/`Secure`/`SameSite`, не расширять `Domain`, использовать префикс `__Host-` (он запрещает установку cookie с поддомена и закрывает cookie tossing).

## Шаг 6: где именно проверять фиксацию

Фиксация проявляется на конкретных переходах состояния — проверяй их по очереди:

| Переход | Что проверять | Признак уязвимости |
|---------|---------------|--------------------|
| Аноним → логин | меняется ли `Set-Cookie` | id остался тем же |
| Логин → админ-зона | ротация сессии | id не изменился |
| Смена пароля | ротация + инвалидация | старые сессии живы |
| Logout | уничтожение серверной сессии | cookie сброшена, но сессия жива |
| SSO-вход | привязка к IdP-сессии | принимается чужой id |

Ключевой вопрос всегда один: **перевыпускает ли сервер id в момент повышения привилегий?**

## Разобранный пример: фиксация через поддомен

Иногда приложение выдаёт собственный id, и подделать его из URL нельзя. Тогда в ход идёт **cookie tossing** — «подброс» cookie с подконтрольного поддомена. Браузер позволяет поддомену ставить cookie для родительского домена, и она может перекрыть основную.

Проверим, действует ли cookie на весь домен:

```bash
$ curl -s -I 'https://shop.local/' | grep -i '^set-cookie'
set-cookie: session=...; Path=/; Domain=.shop.local
```

`Domain=.shop.local` — значит, любой поддомен может установить такую же cookie. Скомпрометированный `blog.shop.local` (или уязвимый к XSS) отдаёт жертве:

```http
Set-Cookie: session=ATTACKER123; Domain=.shop.local; Path=/
```

Браузер отправит серверу **обе** cookie `session`; если сервер возьмёт нашу — фиксация удалась. Отсутствие префикса `__Host-` — признак того, что tossing возможен: этот префикс требует установки только с точного домена и без `Domain`.

## Полный прогон атаки

1. Атакующий получает анонимный `session=ATTACKER123`.
2. Доставляет его жертве: ссылкой `?session=`, через поддомен или XSS.
3. Жертва логинится — сервер не ротирует id.
4. Атакующий приходит с `ATTACKER123` и попадает в аккаунт жертвы.

Артефакт — данные чужого аккаунта, полученные с навязанным id. Если есть доступ к исходникам, проверь, вызывается ли ротация после логина:

```php
session_regenerate_id(true);   // PHP — правильная ротация
```

```java
request.changeSessionId();     // Java Servlet
```

Отсутствие такого вызова после аутентификации — почти гарантированная фиксация.

Не путай фиксацию с **session hijacking**: при hijacking атакующий крадёт уже существующую сессию (через XSS или сеть), а при фиксации он навязывает жертве **заранее известный** ему id. Второй вариант опаснее тем, что не требует кражи в момент логина — достаточно, чтобы жертва зашла по подставленной ссылке.

## Что мы теперь знаем

- Фиксация сессии — атакующий навязывает жертве известный id, который не меняется после логина.
- Предпосылки: сервер принимает id из URL/cookie/поддомена и не ротирует его.
- Главный тест — сравнить `Set-Cookie` до и после логина.
- Навязать id можно ссылкой, поддоменом (cookie tossing) или XSS.
- Защита — регенерация id при любом изменении уровня доверия.

## На что смотреть дальше

- **Session puzzling** — переиспользование одной переменной сессии разными флоу.
- **Session donation** — обратная фиксация: атакующий отдаёт жертве свою сессию.
- **CSRF + фиксация** — связка даёт захват аккаунта без XSS.

## Куда дальше

Мы разобрали, как навязать чужую сессию. Но есть и другой долгоживущий секрет — токен «запомнить меня», который живёт неделями и часто подделывается. О нём в следующем уроке. А пока запомни: **если сервер не перевыпускает session id при логине — фиксация почти наверняка возможна.**

## Где пригодится

- **CTF (Web):** задачи на перехват сессии и «предсказуемые» id.
- **Bug bounty:** фиксация — валидный отчёт, особенно через поддомен.
- **Пентест:** аудит управления сессиями (OWASP WSTG-SESS-03).
- **Работа (AppSec):** ротация id, `HttpOnly`/`Secure`/`SameSite`, узкий `Domain`, инвалидация при logout.
