Session fixation (фиксация сессии) — атака, при которой злоумышленник **навязывает** жертве известный ему session id, а после входа жертвы использует его для захвата аккаунта. Она возможна, когда приложение принимает session id из пользовательского ввода (URL, cookie, скрытое поле) и **не ротирует** его при аутентификации. Это классика `web-cookies-sessions`; здесь — практика и чек-лист.

## Теория: где ломается

Нормальный поток: анонимный пользователь получает session id → логинится → сервер **выдаёт новый** session id (ротация). Уязвимый поток: сервер принимает предложенный id и **сохраняет его** после входа. Тогда атакующий:

1. Получает session id (свой).
2. Навязывает его жертве (ссылка `?PHPSESSID=...`, XSS-подмена cookie, метатег).
3. Жертва логинится — id остаётся тем же.
4. Атакующий использует этот id → доступ к аккаунту жертвы.

## Разобранный пример: фиксация через URL

Приложение принимает `PHPSESSID` из URL и не ротирует его.

Шаг 1 — атакующий берёт свой session id:

```bash
curl -sI "https://app.example/" | grep -i set-cookie
# Set-Cookie: PHPSESSID=attacker123
```

Шаг 2 — навязывает жертве ссылку:

```text
https://app.example/login?PHPSESSID=attacker123
```

Шаг 3 — жертва логинится; проверяем, изменился ли id (в Burp — сравнить Set-Cookie до/после).

Шаг 4 — если id не изменился, атакующий использует `PHPSESSID=attacker123` → захват.

## Разобранный пример: фиксация через поддомен

Если session-cookie имеет `Domain=.example.com`, поддомен (скомпрометированный/уязвимый к XSS) может установить cookie для основного домена:

```js
document.cookie = "PHPSESSID=attacker123; domain=.example.com; path=/";
```

Жертва логинится на `app.example.com` с этим id → захват. Проверьте `Domain`/`Path`/`SameSite`.

## Проверка ротации

Ключевой тест — **меняется ли session id после логина**:

1. Зафиксируйте cookie до входа (`pre`).
2. Залогиньтесь.
3. Посмотрите `Set-Cookie` после входа (`post`).
4. Если `pre == post` — ротации нет → потенциальная фиксация.

```bash
curl -s -c pre.txt "https://app.example/login" -o /dev/null
curl -s -b pre.txt -c post.txt -X POST "https://app.example/login" -d 'user=u&pass=p'
diff <(cut -f7 pre.txt) <(cut -f7 post.txt)   # если одинаково — плохо
```

## Смежные векторы

- **Session puzzling** — переиспользование одной переменной сессии для разных целей (см. `web-session-puzzling`).
- **Отсутствие ротации** при повышении привилегий (обычный → админ).
- **Отсутствие ротации** после смены пароля.
- **CSRF + фиксация** — комбинация усиливает захват.
- **Cookie tossing** — подмена cookie поддоменом.

## Инструменты

- **Burp** — сравнение Set-Cookie до/после.
- **`curl`** — ручная проверка ротации.
- **Browser DevTools** — cookie-флаги (`HttpOnly`, `Secure`, `SameSite`, `Domain`, `Path`).

## Что дальше / decision

1. Проверьте, принимает ли сервер session id из URL/скрытого поля.
2. Проверьте ротацию id после логина.
3. Нет ротации → фиксация через URL/XSS/поддомен.
4. Cookie без `HttpOnly`/`Secure`/`SameSite` → усиливает вектор.
5. Дальше — захват аккаунта (использовать навязанный id после входа жертвы).

## Разобранный пример: фиксация через XSS

Если на сайте есть XSS, а cookie без `HttpOnly`:

```html
<script>document.cookie="PHPSESSID=attacker123; path=/"</script>
```

Жертва получает наш session id, логинится → атакующий использует его. Комбинация XSS + фиксация + отсутствие ротации = надёжный захват.

## Чек-лист защиты (что должно быть)

- Session id **ротируется** при логине и повышении привилегий.
- Cookie: `HttpOnly`, `Secure`, `SameSite=Lax/Strict`.
- Session id не принимается из URL/скрытых полей.
- `Domain`/`Path` не шире необходимого.
- Инвалидация при logout/смене пароля.

Если хоть один пункт отсутствует — проверяйте фиксацию.

## Частые ошибки

- **Путать фиксацию и session hijacking.** Здесь id навязывается заранее.
- **Не проверить ротацию.** Это главный тест.
- **Игнорировать `Domain`/`Path`.** Поддомен может «подбросить» cookie.
- **Забыть про смену пароля.** id должен ротироваться и там.
- **Ломать прод.** Захват чужого аккаунта — только с согласия.

## Полный чек-лист: где именно тестировать фиксацию

Session fixation эксплуатируется на конкретных переходах состояния. Проверяйте их по порядку:

| Переход | Что проверять | Признак уязвимости |
|---------|---------------|--------------------|
| Анонимный визит → логин | меняется ли Set-Cookie | ID остался тем же |
| Логин → привилегированная зона | ротация сессии | ID не изменился |
| Смена пароля | ротация + инвалидация старых | старые сессии живы |
| Выход (logout) | инвалидация серверная | cookie сброшена, но сессия жива |
| SSO-вход | привязка к IdP-сессии | принимается чужой ID |
| Смена роли/прав | перевыпуск сессии | ID не меняется |

Ключевой вопрос всегда один: **перевыпускает ли сервер идентификатор сессии в момент повышения привилегий?**

## Разобранный пример: фиксация через URL-параметр

Некоторые фреймворки поддерживают передачу `jsessionid`/`PHPSESSID` в URL (для клиентов без cookie). Если приложение принимает ID из URL и не перевыпускает его — фиксация тривиальна.

```bash
# 1) атакующий генерирует ссылку с известным ему session id
https://app.example/login;jsessionid=ATTACKER_KNOWN_ID

# 2) жертва переходит и логинится; сервер принимает этот же id
# 3) атакующий заходит со своим id — он уже аутентифицирован
curl -s https://app.example/account -H 'Cookie: JSESSIONID=ATTACKER_KNOWN_ID'
# {"user":"victim","email":"victim@corp.com"}
```

Защита: (а) не принимать session id из URL; (б) обязательно вызывать `request.changeSessionId()`/`session_regenerate_id(true)` после логина.

## Разобранный пример: фиксация через cookie-tossing с поддомена

Даже если приложение выдаёт свой ID, можно «забросить» свой через **cookie tossing**. Браузер позволяет поддомену ставить cookie для родительского домена — и часто это перекрывает cookie основного приложения.

```bash
# злонамеренный поддомен отдаёт
Set-Cookie: SESSION=ATTACKER_ID; Domain=.example.com; Path=/
```

Браузер отправит оба `SESSION`-cookie (свой и наш); сервер возьмёт первый по порядку. Если порядок благоприятен — фиксация удалась. Дополнительно используют **`__Host-`/`__Secure-` префиксы**: их отсутствие — признак уязвимости.

## Смежные векторы: session puzzling, session donation

Фиксация — часть семейства атак на управление сессией:

- **Session puzzling** — повторное использование одного ID разными механизмами (например, ID сессии и ID «reset» совпадают).
- **Session donation** — атакующий даёт жертве свою (уже аутентифицированную) сессию, чтобы жертва действовала «от его имени» (обратная фиксация).
- **CSRF-комбинация** — фиксация + CSRF приводит к захвату аккаунта без XSS.
- **Cookie tossing с префиксами** — отсутствие `__Host-` у cookie делает tossing возможным.

Проверяйте флаги cookie: `HttpOnly`, `Secure`, `SameSite`, а также префиксы `__Host-`/`__Secure-`. Их отсутствие — не «баг сам по себе», но серьёзный усилитель.

## Автоматизация проверки ротации

Ротацию удобно проверять скриптом, сравнивая ID до и после логина.

```bash
# 1) получаем анонимную сессию
curl -s -i https://app.example/ | grep -i 'set-cookie'
# Set-Cookie: SESSION=ANON123; Path=/; HttpOnly

# 2) логинимся с этой cookie
curl -s -i -X POST https://app.example/login \
  -H 'Cookie: SESSION=ANON123' \
  --data 'user=a&pass=b' | grep -i 'set-cookie'
# Set-Cookie: SESSION=SAME123 ...  <-- если ID тот же -> УЯЗВИМО
```

Для массовой проверки удобен Python:

```python
import requests
s = requests.Session()
before = s.cookies.get('SESSION')
s.post('https://app.example/login', data={'user':'a','pass':'b'})
after = s.cookies.get('SESSION')
print('rotated' if before != after else 'FIXATION POSSIBLE')
```

Проверяйте не только логин, но и **выход**: после `logout` серверная сессия должна быть уничтожена, а не просто «отвязана» на клиенте.

## Что делать дальше / решение

1. **Зафиксируйте поведение.** Получите анонимный ID, залогиньтесь, сравните — изменился ли.
2. **Проверьте все переходы.** Логин, смена пароля, смена роли, SSO, logout.
3. **Проверьте источники ID.** URL (`;jsessionid`), поддомены (cookie tossing), мета-теги.
4. **Проверьте флаги cookie.** `HttpOnly`, `Secure`, `SameSite`, префиксы.
5. **Скомбинируйте с CSRF.** Часто именно связка даёт захват аккаунта.
6. **Зафиксируйте PoC.** Ссылка/запрос, после которого чужой ID аутентифицирован.

## Защита: как выглядит корректная реализация

Правильное управление сессией перевыпускает идентификатор в момент любого изменения уровня доверия. Эталонный чек-лист:

| Событие | Действие сервера |
|---------|------------------|
| Анонимный визит | выдать случайный ID (128+ бит) |
| Успешный логин | `regenerate` ID, сохранить данные сессии |
| Смена пароля | `regenerate` ID + инвалидировать все прочие сессии |
| Повышение роли | `regenerate` ID |
| Logout | уничтожить серверную сессию, не только cookie |
| Долгий простой | таймаут + повторный логин |

Флаги cookie: `HttpOnly`, `Secure`, `SameSite=Lax|Strict`, префикс `__Host-` для чувствительных сессий. `__Host-` запрещает установку с поддомена, что закрывает cookie tossing.

## Диагностика: код-сниппеты корректной ротации

Пример на разных стеках — как должна выглядеть ротация:

```php
// PHP
session_regenerate_id(true);   // true = удалить старую сессию
```

```java
// Java Servlet
request.changeSessionId();     // или invalidate() + getSession(true)
```

```python
# Django — rotate_token при логине
from django.contrib.auth import login
login(request, user)           # Django сам вызывает cycle_key()
```

Если в коде после логина нет вызова ротации, фиксация почти наверняка возможна — это первое, что стоит проверить при code review.

## Итоговая проверка за 5 минут

Быстрый порядок действий, если нужно оценить фиксацию на живом приложении:

1. Откройте DevTools → Application → Cookies, запомните текущий ID сессии.
2. Залогиньтесь и посмотрите, изменился ли ID (и появился ли новый `Set-Cookie`).
3. Откройте тот же аккаунт в приватном окне с **чужим** заранее заданным ID и проверьте, принят ли он.
4. Проверьте выход: после logout старый ID не должен работать.
5. Проверьте флаги cookie: `HttpOnly`, `Secure`, `SameSite`, префикс `__Host-`.

Если ID не меняется на шагах 2–3 и старый ID работает после шага 4 — фиксация подтверждена, и её нужно оформить как PoC с указанием конкретного перехода состояния.
