## Вопрос, с которого всё начинается

Ты нашёл форму входа, подобрал пароль — и на экране появился второй шаг: «Введите код из приложения-аутентификатора». Пароль верный, кода нет. Вход закрыт?

Почти всегда нет. Второй фактор (2FA/MFA — когда после пароля просят ещё что-то, что ты знаешь или имеешь) — это не криптография, а ещё один шаг **логики**. И почти всегда между первым шагом и вторым есть щель: сессия выдана раньше времени, проверка живёт на клиенте, состояние не привязано к пользователю.

Сегодня у нас один вход с MFA. Разберём его по шагам и найдём щель.

## Наш пример

Приложение — интернет-магазин `shop.local`. Вход состоит из двух экранов: `/login` (email + пароль) и `/mfa` (6-значный код). Включим перехват в Burp и отправим пароль:

```http
POST /login HTTP/1.1
Host: shop.local
Content-Type: application/json

{"email":"me@shop.local","password":"hunter2"}
--
HTTP/1.1 200 OK
Set-Cookie: session=eyJ...PARTIAL; Path=/
{"next":"/mfa"}
```

Заметили главное: **сервер уже выдал куку `session`**, хотя второй фактор ещё не пройден. Ответ лишь просит клиента перейти на `/mfa`. Это первая зацепка.

## Шаг 1: может, второй шаг — просто картинка?

Раз кука уже есть, проверим, что она даёт. Возьмём `session` из ответа и попробуем защищённые страницы **напрямую**, не вводя код:

```bash
$ curl -s -b 'session=eyJ...PARTIAL' https://shop.local/dashboard -o /dev/null -w '%{http_code}\n'
302
$ curl -s -b 'session=eyJ...PARTIAL' https://shop.local/api/me
{"id":1,"email":"me@shop.local","orders":3}
```

`/dashboard` вернул `302` — редирект на `/mfa`, интерфейс действительно закрыт. А вот `/api/me` вернул **данные пользователя**. Значит, кука после пароля уже почти полноценная, и часть API про второй фактор просто не знает.

Такой приём — обращаться к ресурсам в обход второго шага — называют **force-browse**. Переберём API-эндпоинты, которые видим в JS и OpenAPI:

```bash
$ for p in /api/me /api/orders /api/settings /api/admin; do
>   printf '%-14s ' "$p"; curl -s -b 'session=eyJ...PARTIAL' -o /dev/null -w '%{http_code}\n' "https://shop.local$p"
> done
/api/me        200
/api/orders    200
/api/settings  200
/api/admin     403
```

Три эндпоинта из четырёх отвечают `200`. Мы читаем заказы и настройки, не пройдя MFA. Это уже рабочий баг.

## Шаг 2: а вдруг код можно подменить в ответе?

Иногда проверка второго фактора — это отдельный запрос, ответ на который трактует клиент. Посмотрим, как выглядит `/verify_otp` с неверным кодом:

```http
POST /verify_otp HTTP/1.1
Host: shop.local
Cookie: session=eyJ...PARTIAL

{"otp":"000000"}
--
HTTP/1.1 200 OK
{"mfa":false,"token":null}
```

Ответ содержит флаг `mfa`. Что если подменить его на `true` (Burp → перехват ответа)? Если приложение доверяет ответу и само решает, что «прошло», доступ откроется без кода. **Но** проверь по-настоящему: после подмены зайди на `/dashboard` и убедись, что он реально отдаёт данные. Манипуляция ответом, которую сервер игнорирует, — косметика, а не баг.

## Шаг 3: подмена пользователя во втором шаге

Теперь второй классический разрыв. Спросим: а второй шаг вообще знает, **какому** пользователю он проверяет код? Если да — попробуем подставить чужого. У нас есть аккаунт `victim@shop.local` без MFA.

```bash
$ curl -s -X POST https://shop.local/verify_otp \
>   -b 'session=eyJ...PARTIAL' \
>   -d 'email=victim@shop.local&otp=000000'
{"ok":true,"session":"eyJ...FULL_VICTIM"}
```

Сервер выдал **полную** сессию жертвы, потому что у неё второй фактор не настроен — проверка для неё всегда «истинна». Такой разрыв («шаг 2 не связан с сессией шага 1») — прямой захват аккаунта.

## Шаг 4: гонка на проверке кода

Дальше — гонка. Если проверка «этот код уже использован?» и запись «пометить код использованным» не атомарны (не выполняются как одно неделимое действие), один код может сработать несколько раз. Отправим 20 одинаковых запросов параллельно:

```bash
$ seq 20 | xargs -P20 -I{} curl -s -o /dev/null -w '%{http_code}\n' \
>   -X POST https://shop.local/verify_otp -b 'session=eyJ...PARTIAL' -d 'otp=123456'
200
200
200
...
```

Несколько `200` при одноразовом коде — гонка. Точную синхронизацию (single-packet attack) разберём в `web-race-single-packet`.

## Шаг 5: перебор кода и лимиты

Если у кода 6 цифр, а лимита попыток нет — это миллион комбинаций, реально перебрать. Проверим, есть ли вообще ограничение:

```bash
$ for i in $(seq 1 50); do
>   curl -s -o /dev/null -w '%{http_code} ' -X POST https://shop.local/verify_otp \
>     -b 'session=eyJ...PARTIAL' -d "otp=00000$i"
> done
200 200 200 ... (ни одного 429)
```

Ни `429`, ни блокировки — перебор возможен. Рядом проверь резервные пути: **backup-коды** (часто не хешируются), «запомнить устройство» (токен не истекает), восстановление через email (см. `web-password-reset`).

## Полный прогон от начала до конца

Соберём всё в одну историю, чтобы закрепить. Заходим в `shop.local`, вводим `me@shop.local` / `hunter2`. Сервер отвечает `Set-Cookie: session=...PARTIAL` и просит `/mfa`. Мы **не** вводим код. Вместо этого берём частичную куку и стучимся в `/api/orders` — `200`, видим три заказа. Пробуем подменить `email` в `/verify_otp` на `victim@shop.local` — сервер выдаёт полную сессию жертвы. Отправляем 20 одинаковых кодов параллельно — несколько `200`, значит проверка неатомарна. Проверяем лимит — его нет.

Три разные щели в одном входе. Именно поэтому MFA-баги так ценятся: одна неверно спроектированная машина состояний даёт сразу несколько путей. Дальше остаётся только аккуратно подтвердить импакт и оформить PoC.

## Частые вопросы

**«Я обошёл MFA, но данные не отдаются — это баг?»** Если после обхода защищённый ресурс всё равно возвращает `403`, значит, серверная проверка `mfa_verified` есть, и обход был косметическим. Ищи другой эндпоинт или другое звено — например, force-browse на конкретный API.

**«Почему OTP-брут иногда не нужен?»** Потому что логические разрывы (сессия после шага 1, подмена пользователя, response manipulation) срабатывают чаще и не требуют миллиона запросов. Брут — последний вариант, и он шумный.

## Что мы теперь знаем

- После пароля сервер часто выдаёт **частичную** сессию, и часть API её принимает.
- Force-browse — обращение к ресурсам в обход второго шага.
- Второй шаг может не быть привязан к сессии → подмена пользователя.
- Гонка ломает неатомарные проверки одноразовых кодов и лимиты.
- Манипуляция ответом считается багом только если её подтверждает серверная выдача данных.

## На что смотреть дальше

- Не гоняйся только за перебором кода — логика (force-browse, подмена пользователя) срабатывает чаще.
- Всегда проверяй **API**, а не только UI: защита часто живёт в шаблоне, а не в бэкенде.
- Читай обратно (read-back): после «обхода» реально дойди до чужих данных, иначе это не баг.
- Никогда не блокируй чужие аккаунты перебором — тестируй на своём.

## Куда дальше

В следующем уроке мы возьмём другой современный фактор — passkeys (WebAuthn) — и посмотрим, где ошибается уже его реализация. А пока главное запомни: MFA ломается не на подборе кода, а на разрыве между шагами.

## Где пригодится

- **CTF (Web):** задачи на многошаговую аутентификацию.
- **Bug bounty:** обход 2FA — популярный и ценный класс.
- **Пентест:** аудит реализации MFA в приложениях.
- **Работа (AppSec):** серверный enforcement MFA, атомарные проверки, rate-limit, хеширование backup-кодов.
