## Вопрос, с которого всё начинается

Jenkins — самый популярный сервер автоматизации сборки. Он умеет запускать произвольные скрипты (по дизайну!), хранит **SSH-ключи, облачные креды и токены** к деплой-системам, а его доступность часто «внутренняя» — то есть без должной защиты. Для атакующего Jenkins — это почти гарантированный RCE, если удалось получить доступ. Разберём.

## Наш пример: Jenkins в сети

Цель — `http://jenkins.target.example:8080`. Фингерпринт:

```
$ curl -sI http://jenkins.target.example:8080/ | grep -i 'x-jenkins\|x-hudson'
X-Jenkins: 2.426.1
X-Jenkins-Session: ...
```

Заголовок `X-Jenkins` отдаёт точную версию. Дополнительно:

```
$ curl -s http://jenkins.target.example:8080/api/json
{"_class":"hudson.model.Hudson","jobs":[...]}
```

Версия **2.426.1** — сопоставляем с CVE (например, CVE-2024-23897 затрагивает до 2.441).

## Шаг 1: Script Console — прямой RCE

Если удалось войти (или Jenkins открыт анонимно с правами), путь к RCE — **Script Console** (`/script`). Это встроенный Groovy-интерпретатор:

```
GET /script
```

Вводим Groovy:

```
def cmd = "id".execute()
println cmd.text
```

Jenkins выполнит команду и вернёт вывод. Это **RCE по дизайну** — не баг, а функция для админов. Поэтому доступ к `/script` без аутентификации = полный контроль.

## Шаг 2: CVE-2024-23897 — чтение файлов через CLI

Jenkins CLI (`/cli`) поддерживает аргумент `@file`, который читает файл. Уязвимость позволяла **прочитать произвольные файлы**:

```
$ java -jar jenkins-cli.jar -s http://jenkins.target.example:8080/ help "@/etc/passwd"
```

Ключевая цель — `secrets/initialAdminPassword` (пароль первичного админа) или `credentials.xml` (зашифрованные креды). Прочитав initialAdminPassword, входишь админом и получаешь Script Console.

## Шаг 3: креды и сборки

Jenkins хранит **credentials** (SSH-ключи, пароли, токены) и передаёт их в сборки. Если есть доступ к настройкам job'ов, можно добавить шаг сборки с командой или прочитать креды через Script Console:

```
println jenkins.model.Jenkins.instance.getExtensionList(...)
```

Плюс агенты Jenkins исполняют код на других хостах — компрометация контроллера даёт доступ к агентам и к системам, куда они деплоят.

## Шаг 4: план атаки на Jenkins

1. Версия (`X-Jenkins`).
2. Проверка анонимного доступа.
3. Проверка CVE-2024-23897 (file-read).
4. Чтение `initialAdminPassword`/`credentials.xml`.
5. Вход и Script Console → RCE.
6. Пост-эксплуатация — креды, агенты, деплой.

## Шаг 5: как не навредить

Jenkins управляет сборками и деплоем; неаккуратные действия могут запустить деплой в прод. Поэтому: не запускай реальные сборки; не меняй job'ы; RCE — с безобидным маркером; Jenkins под мониторингом.

## Что мы теперь знаем

- Jenkins версию отдаёт `X-Jenkins`.
- Script Console — RCE по дизайну (Groovy).
- CVE-2024-23897 читает файлы (initialAdminPassword, credentials).
- Jenkins хранит SSH/облачные креды и управляет агентами.
- Действия в Jenkins могут задеть деплой.

## Шаг 7: как использовать Jenkins для движения дальше

Jenkins — это **контроллер**, за которым стоят агенты и деплой-системы. После доступа к Script Console можно: (1) прочитать все credentials (`credentials.xml` через Groovy); (2) посмотреть, куда деплоят job'ы (продовые серверы, облака); (3) выполнить команды на агентах (через job или Groovy). Так один Jenkins открывает доступ к парку серверов сборки и к проду.

## Шаг 8: как оценивать импакт Jenkins-находки

Script Console = RCE на контроллере (критический). CVE-2024-23897 с чтением `initialAdminPassword` = вход админом (критический). Утечка credentials = доступ к SSH/облакам (критический). В отчёте перечисли конкретные системы, к которым ведут найденные креды.

## Шаг 9: типовые ошибки при работе с Jenkins

Ошибка первая — не проверить анонимный доступ к `/script` (иногда он открыт). Вторая — запустить реальную сборку (можно задеть прод). Третья — не читать `credentials.xml` (там SSH-ключи и облачные креды). Четвёртая — игнорировать агентов: они часто имеют больше доступа, чем контроллер.

## Шаг 10: как читать публичный PoC для Jenkins

PoC для CVE-2024-23897 — это `jenkins-cli.jar` плюс команда с `@file`. Это **чтение**, не запись, поэтому относительно безопасно. Прочитай, какой файл тянет: обычно `secrets/initialAdminPassword` или `credentials.xml`. Не запускай его против job'ов — только против файлов.

## Шаг 11: как использовать Jenkins для латерального движения

Jenkins-агенты исполняют код на других хостах. Если контроллер скомпрометирован, можно: (1) прочитать SSH-ключи и облачные креды из credentials; (2) выполнить команду на агенте через Groovy (`node.getChannel()...`); (3) посмотреть, куда деплоят job'ы, и пойти туда. Так Jenkins становится трамплином в парк серверов и в прод.

## Шаг 12: как защититься от Jenkins-атак

Защита: обновление (CVE-2024-23897 закрыта в 2.442/2.426.3); запрет анонимного доступа; отключение CLI (`jenkins.CLI.disabled=true`); ограничение Script Console; аудит. Для атакующего: защищённый Jenkins требует аутентификации, но слабые пароли и открытые агенты остаются вектором.

## Шаг 13: почему Jenkins — почти гарантированный RCE

Jenkins по дизайну исполняет код (сборки, Groovy). Поэтому любой доступ с правами к `/script` или возможность добавить job = RCE. Плюс Jenkins часто развёрнут с анонимным доступом или слабым паролем (`admin/admin`). Приём: проверь `X-Jenkins`, открой `/script` — если он доступен, всё, ты внутри. Это одна из самых быстрых целей в сети.

## Шаг 14: как оформить находку

Укажи: версию Jenkins; способ доступа (анонимный `/script`, CVE-2024-23897, слабый пароль); выполненную команду (маркер); извлечённые credentials и их системы; импакт (агенты, прод). Рекомендации: обновить, закрыть анонимный доступ, отключить CLI.
