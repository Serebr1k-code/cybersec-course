## Вопрос, с которого всё начинается

Сканеры ищут уязвимости, но есть класс, который они почти не замечают: приложение можно **замедлить** легальными на вид запросами. Не эксплойтом, а просто заставив его делать много работы на маленький запрос.

Сегодня мы разберём три таких приёма на тестовом сервере. И сразу важное правило: **DoS мы проверяем безопасно** — маленькими пробами и по времени ответа, никогда не заливая прод потоком запросов. Цель — доказать, что защиты нет, а не уронить сервис.

## Наш пример

`files.local` отдаёт статические файлы и имеет эндпоинт валидации email:

```http
POST /api/validate-email HTTP/1.1
Host: files.local
Content-Type: application/json

{"email":"user@example.com"}
```

Начнём с простого: посмотрим, какие заголовки отдаёт сервер при скачивании файла.

```bash
$ curl -sI https://files.local/big.zip
HTTP/1.1 200 OK
Accept-Ranges: bytes
Content-Length: 104857600
```

`Accept-Ranges: bytes` — сервер умеет отдавать **диапазоны** (часть файла). Это и есть первая зацепка.

## Шаг 1: Range-запросы и амплификация

Диапазонный запрос просит не весь файл, а кусок:

```bash
$ curl -s -H 'Range: bytes=0-1023' https://files.local/big.zip -o /dev/null -w '%{size_download} bytes\n'
1024 bytes
```

Проблема начинается, если сервер обрабатывает **много** диапазонов в одном заголовке. Один маленький запрос заставляет сервер собирать ответ из множества кусков:

```bash
$ curl -s -H 'Range: bytes=0-0,1-1,2-2,3-3,4-4,...(тысячи)' https://files.local/big.zip \
>   -o /dev/null -w '%{size_download} bytes\n'
```

Если сервер не ограничивает число диапазонов, один такой запрос съедает память и CPU — это **амплификация**: крошечный ввод → огромная работа. Проверяй **осторожно**: один-два запроса, замеряя время, а не «в цикле до отказа».

```bash
$ time curl -s -H 'Range: bytes=0-0,1-1,2-2,...' https://files.local/big.zip -o /dev/null
real  0m2.3s
```

Выросло с миллисекунд до секунд — значит, защита отсутствует. Этого достаточно для отчёта.

## Шаг 2: катастрофический regex (ReDoS)

Теперь про валидацию email. Многие проверяют email регулярным выражением вида:

```
^([a-zA-Z0-9]+)+@example\.com$
```

Такое выражение кажется безобидным, но вложенный квантификатор `(...)+` заставляет движок перебирать экспоненциально много вариантов при почти-совпадении. Отправим строку из многих `a`, без `@`:

```bash
$ time curl -s -X POST https://files.local/api/validate-email \
>   -H 'Content-Type: application/json' \
>   -d '{"email":"aaaaaaaaaaaaaaaaaaaaaaaaaaaaa"}'
real  0m1.8s
```

Обычная строка — а сервер думал почти две секунды. Удлиняем на пару символов:

```bash
$ time curl -s -X POST https://files.local/api/validate-email \
>   -H 'Content-Type: application/json' \
>   -d '{"email":"aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa"}'
real  0m7.4s
```

Время растёт **экспоненциально** — это ReDoS (Regular expression Denial of Service). Несколько десятков таких строк положат сервер, потому что каждая занимает процессор целиком. Проверяй по таймингу и **не** отправляй длинные строки повторно — одной-двух проб хватает, чтобы доказать наличие.

## Шаг 3: измеряем безопасно

Ключевое в этом классе — **дозировка**. Правило: сначала короткая строка, потом на 2–3 символа длиннее, и стоп, как только видишь резкий рост времени. Не нужно «добивать» до минуты — это уже вредительство и может уронить прод. Фиксируй в отчёте: вход, время ответа, отсутствие лимита. Для CTF-задач, где сервис специально уязвим, допустимо больше — но и там без нужды не зли.

## Шаг 4: другие усилители

Тот же класс — «маленький ввод, большая работа» — встречается и дальше:

- **Глубокий JSON.** Тело с тысячами вложенных `[` заставляет парсер рекурсивно обходить структуру.
- **Zip bomb.** Маленький архив, разворачивающийся в гигабайты, если сервер распаковывает его без лимита.
- **Хэш-коллизии.** Специально подобранные ключи в форме попадают в один бакет хэш-таблицы.

Все они проверяются одинаково: один аккуратный запрос, замер времени и памяти.

## Полный прогон от начала до конца

Смотрим заголовки — видим `Accept-Ranges`. Шлём один Range с множеством диапазонов: время растёт. Шлём почти-совпадающую строку в `/api/validate-email`: 1.8 с, потом 7.4 с на два символа длиннее. Вывод: сервер делает экспоненциальную работу на крошечный ввод, лимитов нет. Этого достаточно, чтобы оформить отчёт, не положив сервис.

## Как искать это в своём приложении

Практический подход: собери список всех «дорогих» операций и посмотри, что в них подаётся снаружи. Регулярки — в валидаторах email, телефона, URL, пароля. Парсеры — в JSON/XML/YAML. Распаковка — в загрузке файлов. Отдача — в скачивании с Range. Для каждого найди, есть ли лимит на размер входа, глубину и число частей. Инструмент для regex — `redos-checker` или онлайн-анализаторы, которые ищут вложенные квантификаторы; для ручной проверки хватает замера времени. В отчёт всегда клади точный вход и замер — иначе «сервер медленный» не примут.

## Как оценить серьёзность

Не всякий медленный запрос — уязвимость. Смотри на три вещи. Первое — **масштаб входа**: если строка из 30 символов даёт 7 секунд, а 35 символов — минуту, это экспонента, и её видно сразу. Второе — **общий ресурс**: тормозит один воркер или весь сервер (общий пул процессов). Третье — **усилитель**: сколько таких запросов нужно, чтобы занять сервер. Если хватает одного-двух — серьёзность высокая. Если нужно тысячи — ниже, но всё ещё валидный баг. Именно поэтому в отчёте важны числа: вход, время, сколько параллельных запросов держат CPU. Без чисел это «серверу как-то плохо», а не находка.

## Где это встречается в реальности

Чаще всего — там, где пользовательский ввод попадает в «дорогую» операцию: валидация email/URL/телефона регулярками, парсинг больших JSON/XML, распаковка архивов, отдача файлов с Range, поиск по большим спискам. Достаточно одного такого места, чтобы держать CPU занятым. Поэтому при аудите собери все «тяжёлые» функции и проверь, есть ли на входе лимит на длину, глубину и число частей.

## Частые вопросы

**«Как отличить ReDoS от просто медленного сервера?»** По масштабу: если время растёт **экспоненциально** при добавлении пары символов (1.8 с → 7.4 с), это ReDoS. Если время просто колеблется — вероятно, нагрузка.

**«Можно ли проверять DoS на боевом сервисе?»** Только дозированно: один-два запроса и замер времени. Цель — доказать отсутствие защиты, а не уронить сервис. На CTF-стендах допустимо больше, но и там без нужды не зли.

## Что мы теперь знаем

- `Accept-Ranges` и множество диапазонов = амплификация.
- Вложенные квантификаторы в regex дают экспоненциальное время (ReDoS).
- Глубокий JSON, zip bomb и хэш-коллизии — тот же класс.
- Доказательство — рост времени на один запрос, а не отказ сервиса.
- Безопасность теста: дозируй, никогда не заливай потоком.
- Оценивай масштаб: экспоненциальный рост времени на пару символов — сильный сигнал.

## На что смотреть дальше

- Смотри заголовки `Accept-Ranges`, `Content-Length` и любые «собери из частей» эндпоинты.
- Ищи regex в валидаторах (email, телефон, URL) — вложенные `(...)+` и `(a|a)*` опасны.
- Пробуй глубокую вложенность JSON и распаковку архивов.
- Всегда документируй вход и время ответа — это и есть доказательство.

## Куда дальше

Дальше мы вернёмся к бизнес-логике и разберём гонки — как два почти одновременных запроса ломают проверку «проверить → изменить». А пока главное: доступность — тоже часть безопасности, и её проверяют аккуратно.
