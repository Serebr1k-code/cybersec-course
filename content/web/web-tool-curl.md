## Задача

Всё, что ты нашёл в браузере или Burp, нужно **воспроизвести одной командой**. Команда, которую можно скопировать и повторить, — это готовый PoC для отчёта. Инструмент для этого — **curl**: консольный HTTP-клиент, который говорит с сервером на уровне сырых запросов. В этом уроке мы пройдём с `curl` по реальному API: логин, авторизованный запрос, загрузка файла и проверка SSRF.

## Данные, с которыми работаем

Цель — API `https://api.example`. Начнём с простого GET и посмотрим на заголовки. Флаг `-i` показывает и заголовки ответа, `-s` убирает прогресс-бар.

```bash
$ curl -s -i 'https://api.example/v1/item?id=1'
HTTP/1.1 200 OK
Server: nginx
Content-Type: application/json
Content-Length: 22

{"id":1,"name":"Laptop"}
```

Мы видим статус `200`, сервер `nginx` и тип `application/json`. Из этого понятно, что API говорит JSON.

## Шаг 1: методы и тело запроса

GET — по умолчанию. Для POST используем `-X POST` и `-d` (данные). Если отправляем JSON, добавляем заголовок `-H`:

```bash
$ curl -s -X POST 'https://api.example/v1/login' \
    -H 'Content-Type: application/json' \
    -d '{"username":"alice","password":"hunter2"}'
{"token":"eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiJhbGljZSJ9.abc","role":"user"}
```

Сервер вернул **JWT-токен** — строку, которой подтверждается личность в последующих запросах. Разберём флаги: `-X POST` задаёт метод, `-H` добавляет заголовок, `-d` кладёт тело.

## Шаг 2: авторизованный запрос

Теперь используем токен. Его передают в заголовке `Authorization`:

```bash
$ TOKEN=eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiJhbGljZSJ9.abc
$ curl -s 'https://api.example/v1/me' -H "Authorization: Bearer $TOKEN"
{"username":"alice","email":"alice@example.com","role":"user"}
```

Вместо заголовка иногда удобнее **cookie** — тогда используем `-b` (отправить) и `-c` (сохранить ответные):

```bash
$ curl -s -c cookies.txt -X POST 'https://api.example/login-form' -d 'user=alice&pass=hunter2'
$ curl -s -b cookies.txt 'https://api.example/dashboard'
```

Флаг `-c cookies.txt` записывает сессионные куки в файл, а `-b cookies.txt` шлёт их в следующем запросе — так воспроизводится сессия целиком.

## Шаг 3: загрузка файлов

Формы с файлами отправляют **multipart**-запросом. Флаг `-F` формирует его сам:

```bash
$ curl -s -F 'file=@shell.php;type=image/png' -F 'name=avatar' 'https://api.example/upload'
{"ok":true,"url":"/uploads/ab12cd.php"}
```

`@shell.php` — читать файл с диска; `;type=image/png` — подделать `Content-Type`. Так проверяют обход проверок загрузки.

## Шаг 4: SSRF-проба

Если приложение ходит по URL, которое ты задаёшь, — это потенциальный **SSRF** (сервер делает запрос за тебя, включая внутренние адреса). Проверим, отдаёт ли сервер метаданные облака:

```bash
$ curl -s 'https://api.example/fetch?url=http://169.254.169.254/latest/meta-data/'
ami-id
instance-id
iam/
```

`169.254.169.254` — внутренний адрес метаданных облачного инстанса. Если сервер вернул их содержимое, SSRF подтверждён.

## Шаг 5: отладка и вывод

Когда непонятно, что уходит на сервер, смотришь **сырой запрос**. `-v` (verbose) печатает и запрос, и ответ; `--trace-ascii` — ещё детальнее.

```bash
$ curl -sv 'https://api.example/v1/item' 2>&1 | grep -E '^[<>]'
> GET /v1/item HTTP/2
> Host: api.example
> User-Agent: curl/8.19.0
< HTTP/2 200
< content-type: application/json
```

Полезные флаги вывода:

| Флаг | Что делает |
|------|-----------|
| `-i` | показать заголовки ответа |
| `-I` | только заголовки (HEAD-запрос) |
| `-v` | показать запрос и ответ целиком |
| `-s` | тихий режим (без прогресса) |
| `-o file` | сохранить тело в файл |
| `-w '%{http_code} %{time_total}'` | напечатать метрики |
| `--trace-ascii -` | подробный дамп трафика |

## Шаг 6: полезные приёмы

| Задача | Команда |
|--------|---------|
| Показать только статус и время | `curl -s -o /dev/null -w '%{http_code} %{time_total}s\n' URL` |
| Следовать редиректам | `curl -L URL` |
| Игнорировать TLS-ошибку | `curl -k URL` |
| Через прокси (Burp) | `curl -x http://127.0.0.1:8080 URL` |
| Ограничить время | `curl --max-time 5 URL` |
| Разные методы | `curl -X PUT -d '...' URL` |
| Basic-аутентификация | `curl -u user:pass URL` |
| Отправить cookie напрямую | `curl -H 'Cookie: a=b' URL` |

## Полный прогон от начала до конца

1. `curl -s -i /v1/item?id=1` → JSON, nginx.
2. `curl -X POST -H 'Content-Type: application/json' -d '{...}' /v1/login` → JWT.
3. `curl -H "Authorization: Bearer $TOKEN" /v1/me` → профиль alice.
4. `curl -F 'file=@shell.php;type=image/png' /upload` → файл принят.
5. `curl 'https://api.example/fetch?url=http://169.254.169.254/...'` → метаданные, SSRF.

## Сохранение и парсинг вывода

Для скриптов и отчётов важно отделять тело от метрик. `-o` пишет тело в файл, `-D` — заголовки, а `-w` печатает только нужные числа:

```bash
$ curl -s -o body.json -D headers.txt -w '%{http_code} %{size_download} %{time_total}\n' 'https://api.example/v1/item'
200 22 0.041
```

Теперь `body.json` содержит чистый JSON, `headers.txt` — заголовки, а в консоли — метрики. Для проверки списка URL удобен `--config`: он читает команды/URL из файла:

```bash
$ printf '%s\n' 'url = "https://api.example/a"' 'url = "https://api.example/b"' > urls.txt
$ curl -s --config urls.txt -o /dev/null -w '%{url_effective} %{http_code}\n'
```

Флаг `-w` поддерживает множество переменных: `%{http_code}` (код), `%{time_total}` (время), `%{size_download}` (размер), `%{url_effective}` (итоговый URL после редиректов). Это базовый способ мерить поведение сервера в слепых тестах.

## Частые ошибки

- **Забыть `-s`.** Прогресс-бар мешает парсить вывод и скриптам.
- **Путать `-d` и `-F`.** `-d` — это form-urlencoded/JSON-тело; `-F` — multipart с файлами.
- **Не указать `Content-Type`.** JSON без заголовка сервер часто не разберёт.
- **`-b` и `-c` наоборот.** `-c` **сохраняет** куки, `-b` **отправляет**.
- **Игнорировать `-k`.** На тестовых TLS-сертификатах без `-k` соединение падает.
- **Забыть `-L`.** Без него curl не идёт по редиректу и показывает 301/302.

## На что смотреть дальше

- **curl — язык доказательства.** Любой баг оформляй воспроизводимой командой.
- **`-w` — твой друг для слепых тестов:** время и код ответа говорят, что происходит.
- **`-v` показывает, что реально ушло.** Незаменимо при отладке подписи/заголовков.
- **`-x` через Burp** — можно смотреть каждый запрос в прокси.
- **`-o /dev/null -w`** — минимальный способ измерить ответ, не засоряя вывод.
- **Осторожно с SSRF-пробами.** Обращение к внутренним адресам — активное действие; только в scope.

## Разбор: curl как инструмент воспроизведения

Главная ценность curl в тестировании — не в том, что он «умеет всё», а в том, что он воспроизводит запрос ровно так, как ты его задал, без скрытых слоёв. Браузер добавляет десятки заголовков, кэш, редиректы и cookies сам; curl — нет. Поэтому когда баг воспроизводится в curl, ты точно знаешь, какие именно байты его вызывают, и можешь отдать эту команду в отчёт как минимальный PoC.

Отсюда рабочий приём: перехвати запрос в прокси, скопируй его как «curl command», а затем сокращай, пока баг не исчезнет. Каждый удалённый флаг — это сужение причины. Так из «баг есть где-то в приложении» получается точное условие, а часто и понимание, какой именно параметр или заголовок критичен.

Ещё один приём — `-w` для структурированного вывода. `-w '%{http_code} %{size_download} %{time_total}\n'` даёт машиночитаемую строку, которую удобно сравнивать между запросами. Именно так ловят слепые инъекции: сравниваешь код, размер и время для `1=1` и `1=2`, и отклонение выдаёт наличие логического канала.

## Частые вопросы

**«Как отправить тело, не ломая кавычки?»** Используй `--data-binary @file` — читай тело из файла. Тогда shell не трогает содержимое, и JSON или XML уходят байт-в-байт.

**«Почему `-d` меняет метод на POST?»** `-d`/`--data` неявно ставит POST и `Content-Type: application/x-www-form-urlencoded`. Если нужен GET с телом или другой тип, задавай метод явно (`-X`) и заголовок `-H`.

**«Как сохранить cookies между запросами?»** `-c cookies.txt` пишет, `-b cookies.txt` читает. Для сессии это надёжнее, чем руками копировать `Cookie:`.

## Защита

curl-команда из отчёта — это готовый тест-кейс для регрессии. Защищающаяся сторона берёт её и проверяет после каждого релиза: если минимальный PoC перестал срабатывать, фикс держится. Полезно складывать такие команды в регрессионный набор и прогонять в CI — тогда закрытая уязвимость не вернётся с рефакторингом.

## Границы применимости: когда curl не подходит

curl воспроизводит ровно один HTTP-обмен — и в этом его сила, но отсюда же и ограничения. Он **не исполняет JavaScript**, поэтому не поможет против приложения, где нужный запрос собирается уже в браузере (SPA, токены из `localStorage`, подписи на клиенте). Не хранит DOM и не умеет ждать асинхронную загрузку: то, что в браузере «появляется через секунду», в curl просто отсутствует в теле ответа.

curl также не инструмент массового перебора. Для фаззинга путей и параметров берут `ffuf` или `gobuster` — они распараллеливают запросы, фильтруют по коду/размеру и ведут учёт результатов; curl же последовательный и не умеет сам отбрасывать шум. Для сложных цепочек с состоянием (несколько шагов, refresh-токены, анти-CSRF) удобнее скрипт на Python `requests`, где логика видна и поддерживается.

Отдельно про протоколы: `--http2` есть, но WebSocket-диалог curl не ведёт — для него нужен `websocat` или `wscat`. Если ответ приходит через SSE или стриминг, curl покажет поток, но разобрать его придётся самому. Вывод простой: curl — это язык минимального доказательства и ручной разведки, а не универсальная замена браузеру и фаззеру. Правило — сначала воспроизведи баг одной командой curl, а автоматизируй уже потом, другим инструментом.
