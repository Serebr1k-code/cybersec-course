## Вопрос, с которого всё начинается

В Kubernetes-кластере команда использует Argo CD — GitOps-инструмент, который сам применяет манифесты из репозитория в кластер. То есть Argo CD **имеет права деплоить** в Kubernetes. Если ты подделаешь токен админа Argo CD, ты фактически получишь доступ к кластеру. Разберём, как это делается.

## Что такое Argo CD и почему это ценно

**Argo CD** — GitOps-оператор: он следит за Git-репозиторием с манифестами Kubernetes и приводит кластер в соответствие с ним. Это значит, что у Argo CD есть **kubeconfig** с правами на кластер, а его UI/API позволяют управлять приложениями.

Ценность для атакующего: (1) доступ к Argo CD = доступ к кластеру; (2) в нём хранятся креды к репозиториям и registry; (3) у него есть SSRF и слабости JWT. Argo CD — мост между CI и продом.

## Наш пример: Argo CD 2.2.0

Цель — `https://argocd.target.example`. Определяем версию:

```
$ curl -s -k https://argocd.target.example/api/version
{"Version":"v2.2.0","BuildDate":"..."}
```

Версия **2.2.0** — попадает в CVE-2022-29165 (SSRF, версии до 2.3.0). Также проверяем анонимный доступ:

```
$ curl -s -k -o /dev/null -w '%{http_code}\n' https://argocd.target.example/api/v1/applications
200
```

`200` без токена — анонимный доступ включён. Уже утечка: видны приложения и их настройки.

## Шаг 1: CVE-2022-29165 — SSRF

Argo CD умеет подключаться к Git-репозиториям по URL. В уязвимых версиях он позволяет указать **произвольный** URL и сделать запрос от своего имени. Это SSRF: из Argo CD можно обратиться к внутренним сервисам, включая Kubernetes API и metadata-сервисы.

```
$ curl -s -k -X POST 'https://argocd.target.example/api/v1/repositories' \
  -H 'Content-Type: application/json' \
  --data-binary '{"repo":"http://169.254.169.254/latest/meta-data/","name":"x"}'
```

Через это читают метаданные облака (креды инстанса) или сканируют внутреннюю сеть.

## Шаг 2: слабый JWT-секрет

Argo CD выдаёт пользователю **JWT-токен**, подписанный секретом из Kubernetes-секрета `argocd-secret`. Если секрет дефолтный или слабый, его можно подобрать или угадать — и подписать **свой** токен с ролью `role:admin`. Так получают полный админский доступ.

Проверка секрета — офлайн: берёшь свой валидный токен, пробуешь словарь секретов, проверяешь подпись. Если совпало — forge токена:

```
# payload
{"iss":"argocd","sub":"admin","role":"admin","iat":...,"exp":...}
# подпись HS256 секретом
```

Отправляем:

```
$ curl -s -k 'https://argocd.target.example/api/v1/applications' \
  -H 'Authorization: Bearer <forged>'
```

`200` с данными — токен принят, ты админ.

## Шаг 3: путь к кластеру

Админ Argo CD может: читать/менять приложения, смотреть креды репозиториев, а главное — деплоить. Через подменённый манифест можно создать pod с привилегиями, смонтировать hostPath и выбраться на ноду. Так Argo CD превращается в доступ к кластеру.

## Шаг 4: анонимный доступ и утечки

Если анонимный доступ включён (`users.anonymous.enabled: true`), видны приложения, их репозитории и параметры. Иногда там встречаются токены и внутренние URL. Даже без forge это утечка.

## Шаг 5: пост-эксплуатация

Из Argo CD достают: kubeconfig/токены кластера, креды к Git-репозиториям, креды к registry, список namespace и приложений. Это карта кластера и путь к нему. Дальше — эксплуатация Kubernetes (RBAC, pod escape).

## Шаг 6: как понять, что уязвимо

Версия + конфиг. Проверка SSRF — неразрушающим запросом к внутреннему адресу. Проверка JWT — офлайн, по подписи. Не деплой ничего без согласования: Argo CD управляет продом.

## Что мы теперь знаем

- Argo CD — GitOps-деплой в Kubernetes с правами на кластер.
- CVE-2022-29165 — SSRF (произвольный URL).
- Слабый JWT-секрет → подделка токена админа.

- Argo CD = путь к кластеру.

## Разбираем GitOps-модель и почему она расширяет удар

В классическом CI/CD деплой запускается вручную или пайплайном. В **GitOps** (Argo CD) всё иначе: состояние кластера описано в Git, а Argo CD постоянно синхронизирует кластер с репозиторием. Это значит, что **правка в Git-репозитории автоматически применяется в кластер**. Следовательно, компрометация Argo CD или репозитория = деплой произвольного манифеста = выполнение кода в кластере.

Это расширяет удар: атакующему не нужно ломать кластер напрямую — достаточно подменить манифест или получить доступ к Argo CD. Поэтому Argo CD — критичный узел, а его секреты (JWT, kubeconfig, креды репозиториев) — первоочередная цель.

## Шаг 7: как найти версию и конфиг

Версия видна по `/api/version` (часто открыта). Анонимный доступ проверяется запросом к `/api/v1/applications`. Если вернул данные — `users.anonymous.enabled: true`. Конфиг `argocd-cm` в Kubernetes-секретах содержит настройки, включая возможные слабости.

## Шаг 8: что писать в отчёте

Отчёт фиксирует: версию; CVE-2022-29165 (SSRF) или слабый JWT; доказательство SSRF (запрос к внутреннему адресу) или forge токена; импакт (админ Argo CD = доступ к кластеру); рекомендацию (патч, сменить JWT-секрет, выключить анонимный доступ, ограничить права Argo CD в кластере через RBAC).

## Ошибки и антипаттерны

Первая — деплоить что-либо для «доказательства»: это меняет кластер. Достаточно чтения. Вторая — игнорировать SSRF, считая его «неважным»: через него утекают облачные креды. Третья — не проверить RBAC Argo CD: иногда он ограничен одним namespace, и импакт меньше, чем кажется.

## Практический чек-лист по Argo CD

Порядок. Обнаружение: страница Argo CD, `/api/version`, порт 443. Версия: `/api/version`. Анонимный доступ: `/api/v1/applications`. Проверка JWT: взять свой токен и попробовать подписать секретом (офлайн). Проверка SSRF: запрос к внутреннему адресу через `/api/v1/repositories`. Доказательство: forge токена → чтение приложений; или SSRF → внутренний ответ. Пост-эксплуатация: kubeconfig, креды репозиториев, карта namespace. Отчёт: версия, CVE или слабый секрет, доказательство, импакт на кластер, рекомендация.

## Почему JWT-слабости так распространены

Многие продукты подписывают токены симметричным секретом (HS256). Если секрет дефолтный, короткий или утёк (например, попал в Git), токен можно подделать. Argo CD хранит секрет в Kubernetes-секрете `argocd-secret`; при автоматизированной установке он иногда остаётся дефолтным. Проверка такой слабости — офлайн и неразрушающа: ты не трогаешь сервер, а лишь проверяешь подпись. Это идеальный класс проверки для пентеста: доказательство без риска.

Общий урок: где есть симметричная подпись, всегда проверяй секрет на дефолт/слабость. Это относится к JWT, сессионным cookie, токенам API — везде, где секрет известен обеим сторонам.

## Разбор реального сценария

Пентест Kubernetes-среды. Argo CD 2.2.0 с анонимным доступом. Ты видишь приложения и их репозитории. Берёшь свой токен, офлайн проверяешь секрет — он дефолтный. Подписываешь JWT с `role:admin`, отправляешь — принят. Теперь ты админ Argo CD и видишь kubeconfig кластера и креды репозиториев. Ты фиксируешь: доступ к кластеру через подделку токена. Ничего не деплоишь. В отчёте — critical: Argo CD управляет продом, а слабый JWT-секрет даёт админа.

## Итог по Argo CD

Argo CD — мост между CI и продом, поэтому его компрометация равна доступу к кластеру. Два вектора: SSRF (CVE-2022-29165) и слабый JWT-секрет для подделки токена админа. Оба проверяются неразрушающе. Ключевой вывод: GitOps-инструменты надо считать критичными узлами, а их секреты — первоочередной целью.
