WebAuthn (и passkeys) — современный стандарт аутентификации без пароля, основанный на криптографии с открытым ключом. Он устойчив к фишингу и перехвату, но **не лишён ошибок реализации**, и именно они становятся точками входа. Этот урок — про то, как работает WebAuthn, какие проверки обязаны делать сервер и клиент, и где реализации ошибаются.

## Как работает WebAuthn

Клиент (браузер) при регистрации создаёт пару ключей и отправляет серверу **публичный** ключ (credential). При аутентификации сервер присылает **challenge** (случайное значение), клиент подписывает его приватным ключом, сервер проверяет подпись публичным. Ключевая идея: приватный ключ не покидает устройство, а привязка к домену (`rpId`) делает фишинг невозможным.

```js
// регистрация
const cred = await navigator.credentials.create({publicKey: {...}});
// аутентификация
const assertion = await navigator.credentials.get({publicKey: {challenge, ...}});
```

## Обязательные проверки на сервере

Сервер обязан проверять: **origin** (`clientDataJSON.origin`), **rpIdHash**, **challenge** (совпадает с выданным, одноразовый), **type** (`webauthn.create`/`webauthn.get`), **подпись**, **счётчик** (counter) и **флаги** (`UP`, `UV`, `AT`). Пропуск любой из проверок — уязвимость.

```bash
# пример структуры clientDataJSON
echo '{"type":"webauthn.get","challenge":"...","origin":"https://t"}' | base64 -d
```

Если сервер не проверяет `origin`, атакующий может провести аутентификацию с другого домена. Если не проверяет `challenge` — возможна replay-атака.

## Ошибка 1: не проверяется origin

Самая частая и опасная ошибка. Без проверки `origin` WebAuthn-регистрация/аутентификация может быть инициирована с фишингового домена (в комбинации с другими слабостями). Проверяйте, что сервер сверяет `clientDataJSON.origin` с ожидаемым.

## Ошибка 2: не проверяется challenge / replay

Challenge должен быть случайным, привязанным к сессии и одноразовым. Если он предсказуем или не проверяется, атакующий может переиспользовать подпись (replay).

```bash
# если challenge фиксирован (например, "test"), подпись можно переиспользовать
```

## Ошибка 3: не проверяется rpId

`rpId` определяет домен, к которому привязан credential. Если сервер не проверяет `rpIdHash`, можно использовать credential, созданный для другого домена, или подделать его.

## Ошибка 4: не проверяются флаги

Флаг `UV` (User Verification) означает, что пользователь подтвердил личность (биометрия/PIN). Если сервер не требует `UV`, атакующий с украденным устройством может аутентифицироваться без проверки. Флаг `UP` (User Presence) означает, что пользователь присутствовал.

## Ошибка 5: fallback и downgrade

Многие приложения оставляют **пароль как fallback** к WebAuthn. Тогда WebAuthn не повышает безопасность: атакующий атакует пароль. Проверяйте, можно ли обойти WebAuthn через пароль, сброс пароля или recovery-код. Также проверяйте, не принимает ли сервер «пустой» WebAuthn-ответ как успех.

## Ошибка 6: регистрация без аутентификации

Иногда эндпоинт регистрации credential не требует активной сессии — тогда атакующий может привязать свой ключ к чужому аккаунту, зная только идентификатор.

```bash
# если /webauthn/register не требует сессии
curl -s -X POST https://t/webauthn/register -d '{"user":"victim","credential":{...}}'
```

## Разобранный пример: обход через fallback

```bash
# 1. у жертвы включён WebAuthn, но есть и пароль
$ curl -s -X POST https://t/login -d 'email=victim@x.com&password=weakpass'
{"ok":true,"redirect":"/mfa"}
# 2. MFA можно обойти через сброс пароля (recovery)
$ curl -s -X POST https://t/forgot -d 'email=victim@x.com'
# ... получаем токен и ставим новый пароль, минуя WebAuthn
```

Артефакт — вход в аккаунт в обход WebAuthn.

## Разобранный пример: не проверяется origin

```bash
# 1. видим, что регистрация не сверяет origin (в логах/ответе)
# 2. смотрим, принимает ли сервер ответ с origin=null или чужим
$ curl -s -X POST https://t/webauthn/verify -d '{"clientDataJSON":"<base64 c origin=null>","...":"..."}'
{"ok":true}         # origin не проверен -> уязвимость
```

## Крайние случаи и подводные камни

- **Fallback-пароль** обнуляет пользу WebAuthn.
- **Recovery-коды** и сброс пароля — обход.
- **Challenge** должен быть привязан к сессии, иначе replay.
- **`origin` vs `rpId`** — разные проверки, обе обязательны.
- **Флаги `UV`/`UP`** часто игнорируются.
- **Несколько credential** — можно привязать свой к чужому аккаунту.
- **Клонирование аутентификатора** детектируется по счётчику; если не проверяется — не детектируется.

## Что делать дальше / решение

1. **Изучите флоу** — регистрация и аутентификация credential.
2. **Проверьте проверки сервера** — origin, rpId, challenge, подпись, флаги, счётчик.
3. **Проверьте fallback** — пароль, recovery, сброс.
4. **Проверьте регистрацию** — требует ли активной сессии.
5. **Проверьте challenge** — случайность и одноразовость.
6. **Соберите PoC** — обход WebAuthn или привязка своего ключа.
7. **Тупик** — переходите к MFA-bypass и OAuth.

## Глубже: почему WebAuthn устойчив, но реализации — нет

Важно понимать: сам протокол WebAuthn спроектирован хорошо. Криптография привязана к домену (`rpId`), подпись неподделываема без приватного ключа, а challenge защищает от replay. Атаки на WebAuthn — это почти всегда **ошибки интеграции**, а не взлом протокола. Разработчики забывают проверять поля, добавляют fallback, не привязывают challenge к сессии, игнорируют флаги. Именно эти места и нужно искать.

Особое внимание — полям, которые приходят от клиента. `clientDataJSON` (содержит `type`, `challenge`, `origin`) и `authenticatorData` (содержит `rpIdHash`, флаги, счётчик) формируются клиентом и должны **полностью** валидироваться сервером. Если сервер доверяет им без проверки, атакующий может подделать `origin` или `rpIdHash`. Проверяйте, декодирует ли сервер эти поля и сверяет ли их значения.

## Глубже: атаки на аккаунт-рекавери

Даже идеально реализованный WebAuthn бесполезен, если рекавери-механизм слабый. Типичные ошибки: recovery-код, который можно подобрать (короткий, без rate-limit); сброс пароля по email без второго фактора; возможность **удалить** WebAuthn-credential после входа по паролю (атакующий с паролем просто отвязывает ключ); «доверенные устройства», которые можно добавить без WebAuthn. Все это — обход, и проверять их нужно так же тщательно, как сам WebAuthn.

```bash
# можно ли удалить/добавить credential после входа по паролю?
curl -s -b jar -X DELETE https://t/webauthn/credential/1
curl -s -b jar -X POST https://t/webauthn/register -d '{...}'
# если да и без WebAuthn -> обход второго фактора
```

## Глубже: оценка и отчёт

Оценивайте находки по эффекту. Обход WebAuthn с полным захватом аккаунта — критично. Привязка своего credential к чужому аккаунту — критично. Пропуск проверки `origin` — высоко (потенциальный фишинг/обход). Пропуск `UV` — средне/высоко. Отсутствие проверки `counter` — низко (только детект клонов). В отчёте указывайте точную проверку, которую сервер пропускает, и PoC (например, запрос с подделанным `origin`). Для recovery-атак показывайте полную цепочку обхода.

- [ ] Сервер проверяет `origin` в `clientDataJSON`?

- [ ] Проверяется `type` (`webauthn.create`/`webauthn.get`)?
- [ ] Проверяется подпись публичным ключом?
- [ ] Проверяются флаги `UP`/`UV`?

- [ ] Есть ли fallback (пароль/сброс), обходящий WebAuthn?
- [ ] Можно ли привязать свой credential к чужому аккаунту?
- [ ] Можно ли удалить/добавить credential без WebAuthn?
- [ ] Recovery-коды защищены от подбора и rate-limit?

## Итог и типичные ошибки

Ключевой вывод: WebAuthn ломается не в криптографии, а в интеграции. Разработчики пропускают проверки полей, оставляют fallback, не привязывают challenge и позволяют управлять credential по паролю. Именно эти ошибки дают обход. Типичные промахи: не проверять `origin` (аутентификация с чужого домена), игнорировать `UV` (обход биометрии), принимать «пустой» ответ как успех, разрешать регистрацию credential без активной сессии, слабые recovery-коды. Проверяйте каждую из этих точек и подтверждайте обход артефактом — входом в чужой аккаунт или привязкой своего ключа.

## Практические советы по тестированию

Начните с перехвата всех запросов `/webauthn/*` в Burp и декодируйте `clientDataJSON` и `authenticatorData` — так вы увидите, какие поля реально приходят и что сервер с ними делает. Изменяйте по одному полю (origin, challenge, type, rpIdHash) и смотрите на реакцию: если сервер принимает подделку — уязвимость. Проверьте, привязан ли challenge к сессии: запросите его, затем попробуйте использовать в другой сессии. Проверьте одноразовость: используйте один assertion дважды. Затем переключитесь на обвязку — fallback-пароль, recovery-коды, добавление/удаление credential, «доверенные устройства». Большинство реальных обходов живёт именно в обвязке, а не в самом WebAuthn. И помните: для отчёта нужен воспроизводимый PoC с точной последовательностью запросов и наблюдаемым эффектом (доступ к аккаунту). Если все проверки на месте и обвязка крепкая — WebAuthn действительно повышает безопасность, и это стоит отметить в отчёте как положительную находку.
