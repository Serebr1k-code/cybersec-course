## Вопрос, с которого всё начинается

Приложение перешло на «пароли не нужны»: вход по отпечатку или ключу. На бумаге это безопаснее пароля — но только если **реализация** проверяет всё, что обязана. А реализация почти всегда что-то не проверяет.

Сегодня мы возьмём вход по passkey (это и есть WebAuthn — браузерный стандарт входа по ключу/биометрии) и посмотрим, какие проверки можно обойти руками.

## Наш пример

`id.local` — тестовый сервис с passkey. Вход состоит из двух действий: регистрация ключа и последующий вход. Включим Burp и посмотрим, что летит между браузером и сервером.

При регистрации сервер присылает «вызов» (challenge):

```http
POST /webauthn/register/begin HTTP/1.1
Host: id.local
Cookie: session=...
--
HTTP/1.1 200 OK
{"challenge":"Xz9f...","rp":{"id":"id.local","name":"ID"},"user":{"id":"dXNlcl8x","name":"me@id.local"},"pubKeyCredParams":[{"alg":-7}]}
```

Разберём слова по ходу: **challenge** — случайная строка, которую сервер выдаёт один раз и ждёт обратно в подписи; **rp.id** — «идентификатор доверяющей стороны», домен, для которого ключ действителен. Клиент (браузер) подписывает challenge приватным ключом, а сервер проверяет подпись публичным. Всё ломается там, где сервер **не проверяет** какое-то из этих полей.

## Шаг 1: проверяется ли rpId и origin?

Стандарт требует: сервер сверяет, что `clientDataJSON.origin` — ровно тот домен, что ожидается. Если нет — можно заставить жертву подписать challenge для **своего** домена и переиспользовать подпись на целевом. Посмотрим ответ входа:

```http
POST /webauthn/login/finish HTTP/1.1
Host: id.local

{"id":"dXNlcl8x","clientDataJSON":"eyJ0eXBlIjoid2ViYXV0aG4uZ2V0Iiwib3JpZ2luIjoiaHR0cHM6Ly9ldmlsLmxvY2FsIn0","signature":"..."}
```

Декодируем `clientDataJSON` — это base64 от JSON:

```bash
$ echo 'eyJ0eXBlIjoid2ViYXV0aG4uZ2V0Iiwib3JpZ2luIjoiaHR0cHM6Ly9ldmlsLmxvY2FsIn0' | base64 -d
{"type":"webauthn.get","origin":"https://evil.local"}
```

Origin — `evil.local`, а сервер всё равно вернул `200`. Значит, **origin не проверяется**: подпись, полученная на фишинговом домене, принимается на `id.local`. Это классический обход.

## Шаг 2: проверяется ли challenge?

Если сервер не хранит выданный challenge и не сверяет его, можно переиспользовать старую подпись (replay) или подставить свой фиксированный challenge. Попробуем дважды отправить один и тот же `signature` с одним `clientDataJSON`:

```bash
$ for i in 1 2; do
>   curl -s -X POST https://id.local/webauthn/login/finish \
>     -H 'Cookie: session=...' -d @login.json -o /dev/null -w '%{http_code}\n'
> done
200
200
```

Обе подписи прошли. Если бы challenge был одноразовым, второй запрос дал бы ошибку. Отсутствие проверки challenge = replay-атака.

## Шаг 3: userVerification — есть ли вообще второй фактор?

В ответе аутентификатора есть флаг `userVerification` (UV) — подтвердил ли пользователь личность биометрией/PIN. Если сервер не требует UV, то «ключ» превращается в «что-то, что у меня есть» без второго фактора. Проверяем: логинимся аутентификатором, где UV выключен, и смотрим, принимает ли сервер.

```http
HTTP/1.1 200 OK
{"ok":true,"session":"eyJ...FULL"}
```

Принимает. Значит, обещанного «второго фактора» нет — это просто пароль-заменитель. Проверяй и обратный случай: сервер требует UV только на регистрации, а на входе забывает.

## Шаг 4: регистрация чужого ключа

Самая частая дыра — не вход, а **регистрация**. Если `/webauthn/register/finish` не проверяет, что регистрируемый `user.id` принадлежит текущей сессии, можно привязать **свой** ключ к аккаунту жертвы. Меняем `user.id` в запросе:

```bash
$ curl -s -X POST https://id.local/webauthn/register/finish \
>   -b 'session=MY_SESSION' -d @my_key.json \
>   --data-urlencode 'user.id=dXNlcl92aWN0aW0'
{"ok":true}
```

Если ответ `200`, наш ключ теперь открывает аккаунт жертвы. Это прямой захват аккаунта — и без единого пароля.

## Шаг 5: downgrade до пароля

Наконец, проверь, можно ли «откатиться». Если у пользователя есть и passkey, и пароль, часто достаточно войти паролем — а если passkey навязан как «обязательный», иногда его можно просто не использовать, потому что серверная проверка «есть ли passkey у пользователя» не обязательна.

```bash
$ curl -s -X POST https://id.local/login -d 'email=victim@id.local&password=...'
# если 200 без запроса ключа — passkey не enforced
```

## Полный прогон от начала до конца

Соберём всё в одну историю. Заходим на `id.local`, регистрируем свой passkey — сервер присылает `challenge` и `rp.id`. Декодируем `clientDataJSON` из ответа: видим `origin`, который браузер подписал. Отправляем ту же подпись второй раз — сервер принимает (`challenge` не одноразовый). Смотрим флаги в `authenticatorData`: `userVerification` не требуется — значит, второго фактора нет. Пробуем `/webauthn/register/finish` с `user.id` жертвы — наш ключ привязывается к её аккаунту. Наконец, логинимся паролем без ключа — сервер пускает, потому что passkey не enforced.

Пять ошибок реализации в одном потоке. Ни одна из них не является «взломом криптографии» — все они про то, какие поля сервер забыл сверить.

## Частые вопросы

**«Почему passkey считается безопаснее пароля?»** Потому что приватный ключ не покидает устройство, а подпись привязана к домену. Но всё это работает, только если сервер проверяет origin, challenge и UV — без проверок passkey становится просто «чем-то, что у меня есть».

**«С чего начинать тест?»** С регистрации, а не входа: там проверки слабее. Декодируй `clientDataJSON` и `authenticatorData`, выпиши все поля и найди, какие сервер не сверяет.

## Что мы теперь знаем

- WebAuthn безопасен ровно настолько, насколько строг сервер: origin, rpId, challenge, UV — каждое поле обязано проверяться.
- Отсутствие проверки origin → фишинговая подпись переиспользуется.
- Отсутствие одноразовости challenge → replay.
- Нет требования userVerification → это не второй фактор.
- Непривязанная регистрация → привязка своего ключа к чужому аккаунту.
- Отсутствие downgrade-защиты → вход паролем в обход ключа.
- Каждое поле ответа `begin` — потенциальная проверка, которую можно не найти на сервере.

## На что смотреть дальше

- Декодируй `clientDataJSON` и `authenticatorData` вручную — там лежат origin, rpIdHash и флаги; сервер, который их не сверяет, виден сразу.
- Смотри в первую очередь **регистрацию**, а не вход: там проверки слабее.
- Пробуй `user.id`/`credentialId` от другого аккаунта.
- Помни: passkey — это не «магия», а набор полей, которые сервер может проверять или не проверять.

## Чем смотреть

Отдельного «WebAuthn-сканера» нет — всё делается руками через Burp. Заведи себе привычку: каждое поле ответа `begin` (challenge, rp.id, user.id, pubKeyCredParams) выпиши и найди, где оно проверяется в запросе `finish`. Поле, которое сервер принимает, но не сверяет, — и есть дыра. Полезно декодировать base64-части (`clientDataJSON`, `authenticatorData`, `attestationObject`) прямо в Burp или через `base64 -d` — так видно origin, флаги и rpIdHash. А чтобы понять, включён ли UV, посмотри `authenticatorData` бит `flags` (значение `0x04`) — если сервер его игнорирует, второй фактор не enforced.

## Структура authenticatorData по байтам

`authenticatorData` — это бинарная структура, и её полезно читать побайтово:

| Смещение | Длина | Поле | Значение |
|---|---|---|---|
| 0 | 32 | `rpIdHash` | SHA-256 от rpId, сверяется сервером |
| 32 | 1 | `flags` | биты: UP=0x01, UV=0x04, AT=0x40, ED=0x80 |
| 33 | 4 | `signCount` | счётчик подписей (детект клонов) |
| 37 | var | `attestedCredentialData` | при AT-флаге |

Флаг `UV=0x04` показывает, что пользователь подтвердил личность. Если сервер не проверяет этот бит, второй фактор не enforced. Флаг `UP=0x01` — что пользователь присутствовал (нажал кнопку). `signCount` растёт с каждой аутентификацией; если он не увеличивается, возможен клон ключа.

## Attestation и AAGUID

При регистрации аутентификатор может вернуть `attestationObject` — доказательство, что ключ создан настоящим устройством. Внутри — `fmt` (формат attestation), `authData` и подпись. `AAGUID` в `authData` идентифицирует модель аутентификатора. Ошибки: сервер принимает любой `fmt` без проверки (значит, attestation не проверяется вовсе), либо требует `attestation` там, где клиент его не даёт (ломает совместимость). Для атакующего важнее обратное: если attestation не проверяется, можно зарегистрировать **программный** аутентификатор (например, через эмуляцию) и подписывать что угодно.

## Тест-план

- Декодировать `clientDataJSON`: сверить `type` (`webauthn.create`/`get`), `challenge`, `origin`.
- Декодировать `authenticatorData`: проверить `rpIdHash`, флаги, `signCount`.
- Повторить подпись дважды — проверить одноразовость challenge.
- Сменить `origin` в `clientDataJSON` — проверить сверку.
- Отправить `user.id` чужого аккаунта при регистрации — проверить привязку к сессии.
- Войти паролем в обход ключа — проверить downgrade-защиту.

Каждый пункт — отдельная гипотеза о забытой проверке.

## Краткий чек-лист

1. Декодируй `clientDataJSON`: сверь `type`, `challenge`, `origin`.
2. Декодируй `authenticatorData`: проверь `rpIdHash`, флаги (UP/UV), `signCount`.
3. Повтори подпись дважды — challenge должен быть одноразовым.
4. Смени origin — сервер обязан отвергнуть.
5. Отправь чужой `user.id` при регистрации — проверь привязку к сессии.
6. Попробуй войти паролем в обход ключа — проверь downgrade-защиту.
7. Начинай с регистрации: там проверки слабее, чем на входе.

## Итог

WebAuthn не «взламывают» — его **недопроверяют**. Все найденные дыры (origin, challenge, UV, регистрация, downgrade) — это отсутствующие проверки на сервере, а не слабости криптографии. Поэтому тест сводится к одному вопросу: какие поля ответа `begin` сервер обязан сверить в `finish` — и сверяет ли он их на самом деле. Декодируйте base64-структуры, выпишите поля и проверьте каждое.

## Как устроен WebAuthn-обмен

Регистрация (attestation) и аутентификация (assertion) — это подписанные сообщения:

1. Сервер генерирует `challenge` (случайные байты) и отдаёт `rpId` (домен).
2. Браузер просит аутентификатор создать пару ключей; приватный ключ **не покидает** аутентификатор.
3. Аутентификатор возвращает публичный ключ + `attestationObject` (для регистрации) или `authenticatorData` + `signature` (для входа).
4. Сервер проверяет: подпись, `challenge`, `origin`, `rpId`, счётчик `signCount`.

Криптография здесь надёжна — атаки всегда на **проверках на стороне сервера**. Если сервер не проверяет `challenge`, `origin` или `rpId`, аутентификация превращается в фикцию. Именно эти четыре проверки и составляют чек-лист аудита.

## Проверка challenge: почему это критично

`challenge` — это nonce против replay. Если сервер принимает подпись без проверки, что `challenge` совпадает с выданным и не использован ранее, атакующий переигрывает перехваченную подпись (replay). Частые ошибки:

- `challenge` генерируется, но не сохраняется в сессии → нельзя сверить.
- `challenge` фиксированный или предсказуемый (счётчик, timestamp) → легко подделать.
- Проверка есть, но `challenge` не инвалидируется после использования → повторный вход тем же ответом.

Правильная реализация: сервер хранит выданный `challenge` в сессии/Redis с TTL, сверяет побайтово и удаляет после успешной проверки. Проверяйте в коде: ищите `verify` и смотрите, есть ли `assert challenge == expected`.

## Проверка origin и rpId: защита от фишинга

WebAuthn привязан к домену. Сервер **обязан** проверить, что `origin` ответа совпадает с ожидаемым, а `rpId` — с доменом. Если этого нет:

- **Origin не проверен** → подпись с фишингового домена принимается. Атакующий поднимает `evil.example.com`, регистрирует там ключ и логинится на `good.example.com`, если сервер не сверяет origin.
- **rpId не проверен** → можно использовать аутентификатор другого домена, если браузер это позволяет.
- **`rpId` поддомен-обман**: `login.example.com` с `rpId=example.com` расширяет доверие на весь домен; поддомен-подконтрольный атакующему становится точкой входа.

Проверка должна быть строгой (полное совпадение origin), а не `startsWith` — иначе `https://good.example.com.evil.com` пройдёт.

## userVerification: есть ли второй фактор

Флаг `UV` (user verification) означает, что пользователь подтвердил личность (PIN, биометрия). Если сервер **не требует** `UV=true`, то вход возможен по одному физическому ключу без PIN — а значит, украденный ключ (или его копия) даёт доступ. Проверяйте `userVerification: "required"` в `PublicKeyCredentialRequestOptions`; значение `"preferred"` позволяет аутентификатору не требовать UV.

Отдельный случай — **passwordless vs second-factor**. Если WebAuthn используется как второй фактор, но при недоступности ключа есть fallback на пароль (см. ниже), защита деградирует.

## Регистрация чужого ключа

Классический сценарий: атакующий с доступом к аккаунту (или через CSRF) регистрирует **свой** аутентификатор. Если регистрация не требует повторной аутентификации или подтверждения существующим фактором, атакующий «привязывает» свой ключ и получает постоянный доступ. Защита — step-up authentication при добавлении нового ключа и уведомление пользователя.

Ещё одна ошибка — **attestation не проверяется**: сервер принимает любой аутентификатор. В корпоративной среде это позволяет использовать недоверенное устройство (например, софтверный аутентификатор в браузере атакующего).

## Downgrade и fallback

Если рядом с WebAuthn живёт пароль, атакующий целится в **самый слабый** путь. Типичные деградации:

- «Забыли ключ?» → сброс на email, который контролируется.
- Recovery-коды, хранящиеся в открытом виде.
- Возможность отключить WebAuthn без подтверждения.
- Аккаунт без ключа вовсе (необязательная настройка).

Правило: многофакторность сильна настолько, насколько силён **резервный** канал. При аудите всегда спрашивайте: «а как ещё можно войти в этот аккаунт?»

## Чек-лист аудита WebAuthn

1. Проверяется ли `challenge` (наличие, свежесть, одноразовость)?
2. Строгая ли проверка `origin` и `rpId`?
3. Требуется ли `userVerification: required`?
4. Требуется ли step-up при регистрации нового ключа?
5. Проверяется ли `signCount` на клонирование?
6. Есть ли слабый fallback (пароль/email-сброс)?
7. Валидируется ли `attestation` (если политика требует)?
8. Хранятся ли публичные ключи и метаданные корректно (привязка к пользователю, а не к сессии)?

- **Bug bounty:** ошибки WebAuthn-реализаций — свежий и ценный класс.
- **Пентест:** аудит passkey-внедрений.
- **Работа (AppSec):** строгая проверка origin/challenge/UV, защита регистрации, отсутствие downgrade.
