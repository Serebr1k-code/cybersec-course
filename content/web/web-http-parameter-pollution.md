## Вопрос, с которого всё начинается

Что если отправить один и тот же параметр дважды? `?amount=100&amount=10000`. Казалось бы, ерунда. Но разные слои приложения — WAF, прокси, сам код — выбирают **разные** копии: кто-то берёт первую, кто-то последнюю, кто-то склеивает их в строку.

Это и есть **HPP** (HTTP Parameter Pollution) — загрязнение параметров. На нём строятся обходы фильтров и логические баги. Сегодня разберём это на одном эндпоинте.

## Наш пример

`bank.local` переводит деньги. Запрос выглядит так:

```http
POST /api/transfer HTTP/1.1
Host: bank.local
Content-Type: application/x-www-form-urlencoded

from=me&to=bob&amount=100
```

Обычный перевод на 100 проходит. Посмотрим, что будет, если добавить параметр `to` второй раз.

## Шаг 1: дублирование параметра

Отправим два значения `to`:

```bash
$ curl -s -X POST https://bank.local/api/transfer -b 'session=me' \
>   -d 'to=bob&to=eve&amount=100'
{"ok":true,"to":"eve","amount":100}
```

Деньги ушли **eve**, а не bob. Приложение берёт **последнее** значение. Теперь представим, что между нами и приложением есть валидатор, который проверяет первого получателя (`bob`), а деньги уходят второму (`eve`). Это классический HPP: фильтр и логика расходятся.

## Шаг 2: как разные парсеры читают дубликаты

Вот где корень проблемы. У разных реализаций — разное поведение при дублировании:

- **PHP / ASP.NET (request):** берут **последнее** значение.
- **Java Servlet / JSP:** берут **первое**.
- **Python (некоторые фреймворки):** собирают **список**.
- **WAF/прокси:** часто смотрят только первый параметр.

Значит, если WAF проверяет первый `amount=100`, а приложение берёт последний `amount=10000`, — лимит обойдён.

```bash
$ curl -s -X POST https://bank.local/api/transfer -b 'session=me' \
>   -d 'amount=100&amount=10000'
{"ok":true,"amount":10000}
```

## Шаг 3: обход WAF через HPP

Тот же приём прячет опасные значения от фильтра. Пусть WAF блокирует `amount=10000` (превышение лимита), но пропускает `amount=100`. Отправим оба:

```bash
$ curl -s -X POST https://bank.local/api/transfer -b 'session=me' \
>   -d 'amount=100&amount=10000' -o /dev/null -w '%{http_code}\n'
200
```

`200` — WAF проверил первую копию, приложение выполнило вторую. Иногда полезнее наоборот: положить безопасное значение **последним** для WAF, а опасное — первым для приложения. Направление зависит от того, кто как читает.

## Шаг 4: parameter smuggling

Если часть параметров идёт в URL, а часть — в теле, появляется «parameter smuggling». Приложение может прочитать параметр из URL, а WAF — из тела (или наоборот):

```bash
$ curl -s -X POST 'https://bank.local/api/transfer?amount=10000' -b 'session=me' \
>   -d 'amount=100'
{"ok":true,"amount":10000}
```

WAF смотрит на тело (`100` — безопасно), а приложение берёт значение из URL (`10000`). То же с `;` как разделителем: некоторые парсеры считают `;` границей параметра, другие — частью значения. `?a=1;b=2` читается по-разному.

## Полный прогон от начала до конца

Переводим `amount=100` — проходит. Добавляем второй `to` — деньги уходят не тому. Ставим два `amount` — приложение берёт последний, лимит обойдён. Смотрим, какой слой что читает, и подбираем порядок так, чтобы WAF видел безопасное, а логика — опасное. Пробуем URL+body smuggling — работает. Три обхода одного контроля, и все — из дублированных параметров. В отчёт идёт таблица «слой → какая копия».

## Почему это вообще возможно

HTTP не запрещает дублировать параметры — стандарт просто не говорит, что делать с дубликатами. Поэтому каждая реализация решает сама, и решения расходятся. WAF — отдельный продукт, написанный другой командой; он читает запрос своим парсером и может брать **первую** копию, тогда как приложение берёт **последнюю**. Прокси между ними — третий парсер. Получается конвейер, где каждый слой «видит» параметр по-своему, и расхождение — это и есть уязвимость. Тот же корень у request smuggling и обхода WAF через кодирование: **расхождение парсеров** — универсальный класс. Поэтому защита от HPP — не фильтрация строки, а **единый парсер** и нормализация параметров на входе, до всех проверок.

## Инструменты

Практика — **Burp Repeater**: добавляешь параметр дважды и смотришь, какое значение «победило» в ответе. Полезно вести таблицу «слой → какая копия»: WAF (первая/последняя/все), приложение, прокси. Для автоматизации дублирования — **Intruder** или простой скрипт на `requests`. Для parameter smuggling удобно сравнивать поведение при параметре в URL и в теле — снова Repeater. Не забывай про разделители: `&`, `;`, `%26`, `%3b` — разные парсеры считают границей параметра разное.

## Если не сработало

Если дубликат не «побеждает», попробуй другие формы: массив (`a[]=1&a[]=2`), JSON (`{"a":[1,2]}`), вложенные ключи (`a[b]=1`). Иногда приложение читает параметр из **cookie** или заголовка, а WAF — из тела; тогда переноси значение туда. Ещё вариант — использовать `;` вместо `&`: часть парсеров трактует его как разделитель. И проверь HTTP/2: там параметры в `:path`, и фильтр, смотрящий на строку HTTP/1.1, может их не увидеть.

## Где это встречается в реальности

HPP — не экзотика, он живёт в обычных местах. Платёжные формы, где сумма приходит и в теле, и в URL. API, где фильтр проверяет первый `role`, а приложение берёт последний. Голосования, где `vote=0&vote=1` читается по-разному. Всё это — «параметр влияет на деньги или права, а слои читают его по-разному». Поэтому, найдя любой эндпоинт, где параметр влияет на логику, попробуй продублировать его — это дешёвая и часто результативная проверка.

## Как оформить находку

HPP описывают как «какой слой что читает». Приложи таблицу: слой (WAF/прокси/приложение) → значение параметра (первое/последнее/список). Затем покажи запрос с дубликатом и результат (перевод не тому, лимит обойдён). Так баг воспроизводим и понятен без догадок.

## Частые вопросы

**«Как понять, какой слой какую копию читает?»** Отправь два разных значения (`amount=1&amount=2`) и посмотри, какое попало в результат. Так ты определишь поведение каждого слоя.

**«HPP работает без WAF?»** Да. Даже если WAF нет, расхождение между прокси и приложением или между разными частями кода даёт тот же эффект — например, валидатор проверяет первое значение, а логика берёт последнее.

## Что мы теперь знаем

- Дублированный параметр читается разными слоями по-разному.
- PHP/ASP.NET часто берут последнее, Java — первое, Python — список.
- HPP обходит WAF: фильтр видит одну копию, приложение — другую.
- Parameter smuggling — расхождение URL и тела.
- Разделители (`;`, `&`) парсятся по-разному.
- Корень проблемы — расхождение парсеров, как и в обходе WAF.
- Защита — единый парсер и нормализация до всех проверок.
- Дублирование — дешёвая проверка на любом эндпоинте с параметром, влияющим на логику.

## На что смотреть дальше

- Определи, какой слой что читает: отправь два значения и посмотри, какое «победило».
- Пробуй оба порядка: безопасное первым и опасное последним.
- Пробуй перенести параметр из тела в URL и наоборот.
- Помни: HPP — это снова расхождение парсеров, как в обходе WAF.

## Куда дальше

Дальше разберём парсинг URL — там та же идея, но уже на адресах: `@`, бэкслэши и кодирование ломают allowlist SSRF и open redirect. А пока главное: дублируй параметры и смотри, какой слой что читает.

## Где пригодится

- **CTF (Web):** обход фильтров через дублирование.
- **Bug bounty:** WAF bypass и логические баги.
- **Пентест:** тестирование рассогласования парсеров.
- **Работа (AppSec):** нормализация параметров, единый парсер, строгие схемы API.
