В прошлом уроке мы подменяли числовой ID `5501` на `5502` — легко, потому что они идут подряд. Разработчики это знают и часто переходят на **UUID** — длинные идентификаторы вида `9b1deb4d-3b7d-4bad-9bdd-2b0d7b3dcb6d`. Логика проста: «их не перебрать, значит, IDOR закрыт». Сегодня разберём, почему это не так.

Возьмём `shop.local`, где документы адресуются UUID, и покажем, что контроль доступа всё равно ломается.

## Наш пример: документ по UUID

Запросим свой документ:

```bash
$ curl -s 'https://shop.local/api/documents/9b1deb4d-3b7d-4bad-9bdd-2b0d7b3dcb6d' \
  -H 'Authorization: Bearer <alice>'
{"id":"9b1deb4d-...","owner":"alice","title":"Мой счёт","content":"..."}
```

UUID выглядит случайным. Перебрать его «в лоб» невозможно — пространство огромно. Но у нас есть три других пути: **предсказать**, **подсмотреть** и **перечислить**.

## Шаг 1: UUID не всегда случайны

UUID бывают нескольких версий, и не все из них случайны:

- **UUIDv4** — действительно случайные (кроме версии и варианта). Предсказать нельзя.
- **UUIDv1** — строится из **времени** и **MAC-адреса** машины. Это уже частично предсказуемо: зная примерное время создания и MAC, можно сузить перебор.
- **UUIDv7** — из времени (Unix-миллисекунды) + случайных бит. Первая часть отражает время, и это снова подсказка.

Посмотрим на UUID из примера внимательно:

```
9b1deb4d-3b7d-4bad-9bdd-2b0d7b3dcb6d
│        │
│        └─ «4» в третьей группе → это версия 4 (случайный)
```

Третья группа начинается с цифры **версии**. Если видим `1`, это v1 (время+MAC), если `4` — v4 (случайный), если `7` — v7 (время). Уже по этой цифре видно, стоит ли пытаться предсказывать.

## Шаг 2: предсказание UUIDv1

Если ID — это v1, он содержит **время** создания с точностью до 100 наносекунд. Значит, для документов, созданных подряд, UUID будут **близкими**: меняется лишь младшая часть. Переберём небольшой диапазон вокруг известного UUID:

```bash
$ python3 - <<'EOF'
import uuid, datetime
# берём время создания документа примерно известное (например, из поля created_at)
base = uuid.uuid1()  # для примера: генерируем v1
print("наш uuid:", base)
print("соседний  :", uuid.UUID(int=base.int + 1))
print("соседний-1:", uuid.UUID(int=base.int - 1))
EOF
```

Если API отдаёт UUIDv1, соседние значения с высокой вероятностью существуют — и часто принадлежат **другим** пользователям. Подставляем их и проверяем.

## Шаг 3: enumeration через API и GraphQL

Второй путь — не предсказывать, а **перечислять**. Многие API умеют отдавать **список** объектов, а не только один. Например, GraphQL:

```bash
$ curl -s 'https://shop.local/graphql' -H 'Authorization: Bearer <alice>' \
  -d '{"query":"{ documents { id title owner } }"}'
{"data":{"documents":[
  {"id":"9b1deb4d-...","title":"Мой счёт","owner":"alice"},
  {"id":"7c9e6679-...","title":"Счёт Боба","owner":"bob"}
]}}
```

Резолвер `documents` вернул **все** документы, включая чужой. Это типичная ошибка: авторизацию проверили на «одиночном» запросе, а на «списке» забыли. Иногда список не отдаёт `content`, но **отдаёт ID** — а с ID уже можно запросить содержимое поштучно.

## Шаг 4: утечки UUID

Третий путь — просто узнать чужой UUID. Они утекают повсюду:

- **в URL страниц**, которые шарят пользователи (ссылка на документ);
- **в ответах API** (вложенные объекты, комментарии, логи активности);
- **в кэше** и публичных страницах;
- **в письмах** и экспортах;
- **в `Referer`** при переходах.

Поиск UUID в поиске (Google, GitHub) или в публичном кэше часто даёт готовые чужие идентификаторы. Дальше — обычная проверка IDOR: подставить и посмотреть, отдаст ли сервер данные.

## Шаг 5: почему UUID «успокаивают» разработчиков

UUID дают ложное чувство безопасности: кажется, что «неперебираемый ID» = «защищённый объект». Но IDOR — это не про перебор, а про **проверку владельца**. Если сервер не проверяет, что документ принадлежит текущему пользователю, то неважно, случайный ID или последовательный: как только чужой ID попал к нам (предсказание, утечка, список), доступ получен.

Правильная защита — не «сложный ID», а **авторизация на объекте**: «имеет ли текущий пользователь право на этот документ?». ID — это лишь адрес, а не пароль.

## Шаг 6: как проверять на практике

- **Определи версию UUID** по третьей группе (`1`/`4`/`7`) — это скажет, предсказуем ли ID.
- **Ищи список**: `/api/documents`, `/api/users`, GraphQL-запросы, «поиск», «недавние».
- **Ищи утечки**: шаренные ссылки, письма, экспорты, кэш.
- **Меняй ID** в запросе на любой чужой и смотри ответ.
- **Пробуй все методы** — чтение, изменение, удаление.

## Шаг 7: как предсказать UUIDv1 на практике

Разберём предсказание подробнее, потому что это ядро урока. UUIDv1 устроен так: старшие 60 бит — количество 100-наносекундных интервалов от 1582 года, затем версия, затем 14 бит «часовой последовательности», затем 48 бит MAC-адреса. Значит, для документов, созданных в одну секунду, различаются только младшие биты времени и «последовательность». Если API отдаёт `created_at` рядом с ID, мы знаем точное время и можем **сгенерировать диапазон** UUID, которые могли быть выданы:

```bash
$ python3 - <<'EOF'
import uuid, datetime
t = datetime.datetime(2026, 10, 12, 10, 0, 0)
for us in range(0, 50):
    u = uuid.uuid1(node=0x001122334455, clock_seq=0, time=int(t.timestamp()*1e7 + 122192928000000000 + us))
    print(u)
EOF
```

Список кандидатов небольшой, и его достаточно перебрать запросами. Если среди них окажется чужой документ — IDOR подтверждён. Именно поэтому «неперебираемый» v1 на деле перебирается в считаные сотни попыток.

## Шаг 8: enumeration и утечки как основной путь

Если UUID — случайный (v4), предсказание не сработает, и на первый план выходит **enumeration** (перечисление) и **утечки**. Практический чек-лист:

- **Списки:** `/api/documents`, `/api/users`, `/api/activity`, GraphQL-поля `documents`/`allUsers` — часто отдают чужие ID.
- **Вложенные объекты:** комментарии, история, «поделились с» — там чужие ID.
- **Публичные ссылки:** шаренные документы, публичные профили, RSS.
- **Экспорты и письма:** «скачать все данные», уведомления — там ID.
- **Кэш и поисковики:** проиндексированные ссылки с UUID.
- **Метаданные:** `X-Request-Id`, логи, `Referer`.

Как только чужой UUID добыт любым из этих способов, остаётся подставить его и посмотреть, отдаст ли сервер данные. Часто одного списка достаточно, чтобы получить сразу сотни чужих идентификаторов — и тогда IDOR превращается в массовую утечку.

## Что мы теперь знаем

- **UUID** бывают v1/v7 (содержат время) и v4 (случайные).
- v1/v7 частично **предсказуемы** — соседние ID часто существуют.
- **Enumeration** через API/GraphQL отдаёт чужие объекты списком.
- UUID **утекают** в ссылках, ответах, кэше, письмах.
- IDOR — про **проверку владельца**, а не про сложность ID.

## На что смотреть дальше

- **Третья группа UUID** подскажет версию — и стоит ли предсказывать.
- **GraphQL-запросы** часто отдают больше, чем нужно: пробуй `documents`, `users`, `allX`.
- **Вложенные объекты** в JSON несут чужие ID.
- **Шаренные ссылки** — готовый источник чужих идентификаторов.
