## Вопрос, с которого всё начинается

GraphQL-запрос возвращает пользователей по фильтру: `{ users(filter: "{\"role\":\"user\"}") { name role } }`. Резолвер парсит строку фильтра и передаёт её прямо в MongoDB. Что если вместо `user` подставить оператор? Тогда фильтр перестанет ограничивать выборку, и вернутся чужие записи. Это GraphQL argument injection в NoSQL.

## Что такое GraphQL и где тут инъекция

GraphQL — язык запросов к API с единой схемой. Клиент описывает, какие поля ему нужны, и сервер отдаёт ровно их. Один эндпоинт (`/graphql`), один метод (`POST`), один формат (JSON).

Инъекция возникает не в самом GraphQL, а **в резолвере** — функции, которая выполняет поле. Типичный резолвер получает аргумент (строку, число, JSON) и строит из него запрос к базе. Если аргумент — строка JSON, которую парсят и передают в MongoDB как фильтр, операторы в ней сработают.

## NoSQL-операторы, которые меняют логику

MongoDB использует операторы в JSON-фильтре: `$ne` (не равно), `$gt`/`$lt` (сравнение), `$regex` (регулярка), `$exists`, `$in`. Если пользовательский фильтр сливается с серверным без валидации, оператор меняет смысл запроса.

Пример: приложение хочет вернуть только активных пользователей роли `user`, а ты подставляешь `{"role":{"$ne":"x"}}` — и получаешь всех, включая админов. Или `{"$where":"..."}` в старых версиях, где можно исполнять JavaScript на сервере.

## Наш пример

Договоримся о примере. Эндпоинт `POST https://app.target/graphql` принимает query. Обычный запрос:

```
$ curl -s -X POST https://app.target/graphql \
  -H 'Content-Type: application/json' \
  --data '{"query":"{ users(filter: \"{\\\"role\\\":\\\"user\\\"}\") { name role } }"}'
{"data":{"users":[{"name":"bob","role":"user"}]}}
```

Резолвер превратил фильтр в `{"role":"user"}` и передал в MongoDB. Теперь подставим оператор:

```
$ curl -s -X POST https://app.target/graphql \
  -H 'Content-Type: application/json' \
  --data '{"query":"{ users(filter: \"{\\\"role\\\":{\\\"$ne\\\":\\\"x\\\"}}\") { name role secret } }"}'
{"data":{"users":[{"name":"admin","role":"admin","secret":"..."}]}}
```

`$ne:"x"` истинно для любой роли, и вернулись все записи, включая админа со скрытым полем `secret`.

## Batching и алиасы для перебора

GraphQL умеет выполнять несколько операций в одном запросе: через **алиасы** (`a: users(...) {..} b: users(...) {..}`) и через **batching** (массив запросов). Это ускоряет перебор в разы и часто обходит rate-limit, потому что лимит считает HTTP-запросы, а не операции.

Через алиасы удобно делать слепое извлечение: десятки полей с разными фильтрами в одном запросе, и по ответу ты видишь, какие сработали. Через batching — массово проверять токены и ID.

## Introspection: сначала карта

Прежде чем строить инъекцию, получи схему. Запрос introspection:

```
$ curl -s -X POST https://app.target/graphql -H 'Content-Type: application/json' \
  --data '{"query":"{__schema{types{name fields{name args{name type{name}}}}}}"}'
```

Если introspection открыт, ты видишь все типы, поля и аргументы. Ищи резолверы, принимающие строковые фильтры, JSON, сортировку, ID. Это точки инъекции.

Если introspection закрыт, используй подсказки ошибок: GraphQL охотно сообщает «Cannot query field X» — так перебирают поля.

## Массовое присваивание в мутациях

GraphQL-мутации часто принимают объект и сохраняют его в базу. Если резолвер передаёт аргументы в ORM целиком, ты можешь добавить лишнее поле. Пример мутации:

```
mutation { updateProfile(input: {name: "bob", role: "admin"}) { id role } }
```

Если сервер не проверяет `role`, ты становишься админом. Это то же массовое присваивание, что и в REST, но выраженное через GraphQL-ввод.

## Как искать в чёрном ящике

Первый шаг — найти эндпоинт (`/graphql`, `/api`, `/v1/graphql`). Проверь `{__typename}` — если вернётся имя типа, это GraphQL.

Второй — попробуй introspection. Если открыт — читай схему.

Третий — ищи аргументы, которые выглядят как фильтры: `filter`, `where`, `query`, `search`, `sort`, `order`. Подставляй в них JSON с операторами `$ne`, `$gt`, `$regex`.

Четвёртый — проверь batching и алиасы. Если работают, у тебя есть усилитель для перебора.

Пятый — проверь массовое присваивание: передай в мутацию лишние поля, которые сервер может принять.

## Что мы теперь знаем

- GraphQL-инъекция живёт в резолвере, а не в языке.
- NoSQL-операторы (`$ne`, `$gt`, `$regex`) меняют логику фильтра.
- `$ne:null` возвращает все записи, обходя ограничения.
- Алиасы и batching ускоряют перебор и обходят rate-limit.
- Introspection даёт карту; при закрытой схеме — перебор по ошибкам.

## GraphQL vs REST: почему инъекция незаметна

В REST каждый эндпоинт имеет свою логику и свои проверки. В GraphQL — один эндпоинт и один резолвер на поле. Разработчики часто пишут резолверы «на скорость»: принимают аргумент, передают в базу, возвращают результат. Проверки, которые были бы в REST-контроллере, тут размазаны по резолверам и часто отсутствуют.

Отсюда две особенности. Первая: **аргументы часто типизированы слабо** — строка `filter` парсится как JSON и уходит в базу. Вторая: **авторизация проверяется не везде** — поле, которое должно быть доступно только админу, может отдавать данные любому, кто угадает аргумент.

GraphQL сам по себе безопасен; уязвимость создаёт резолвер. Поэтому при аудите смотри именно на резолверы: что они делают с аргументами, куда их передают, проверяют ли права.

## Слепое извлечение через GraphQL

Когда фильтр не возвращает данные напрямую, его используют как булев сигнал. Резолвер с аргументом `filter` можно превратить в оракул.

Идея: подставляешь условие, которое истинно только при определённом свойстве, и смотришь, есть ли результат. Например, `filter: "{\"name\":{\"$regex\":\"^a\"}}"` вернёт записи, чьё имя начинается на `a`. Перебирая префиксы, ты восстанавливаешь значение — по одному символу за запрос.

Алиасы ускоряют это в разы: в одном запросе можно проверить десятки префиксов, дав каждому свой алиас. Ответ покажет, какие алиасы вернули данные. Это превращает слепое извлечение в почти прямое.

Если `$regex` отфильтрован, пробуй `$gt`/`$lt` (бинарный поиск по значению), `$in` (перебор по списку), `$exists` (наличие поля).

## Как защищаться

Первое: **не передавать пользовательский JSON в базу**. Аргумент должен быть типизированным — строка, число, enum, — а фильтр строится на сервере из этих значений.

Второе: **проверять права на уровне поля**. Каждый резолвер, отдающий чувствительные данные, обязан проверить контекст (кто спрашивает). Не полагайся на то, что клиент «не угадает» поле.

Третье: **ограничить introspection** в продакшене, чтобы не отдавать карту API. Это не защита от инъекции, но снижает скорость разведки.

Четвёртое: **лимитировать сложность и batching** — ограничивать глубину запроса, число алиасов и размер батча. Это закрывает усилители перебора.

## Реальные кейсы

GraphQL-инъекции встречались в самых разных API: от стартапов до крупных сервисов. Типовые находки — резолвер, отдающий чужие заказы по `filter`, мутация, принимающая `role`, и `$where` в MongoDB, исполняющий JavaScript.

Отдельный класс — **GraphQL-утечки через ошибки**: неверный тип аргумента возвращает стектрейс с именами коллекций и полей. Это ускоряет построение слепого запроса.

Вывод: GraphQL не «безопасная замена REST». Это другой транспорт с теми же классами ошибок — и с дополнительными усилителями (introspection, batching, aliases).

## Практический сценарий: от разведки к утечке

Соберём всё в один сценарий, который проходят на реальной цели.

Шаг первый: находим GraphQL-эндпоинт. Проверяем `{__typename}`; если отвечает — это GraphQL. Пробуем introspection; если открыт — выгружаем схему и сохраняем список Query/Mutation с аргументами.

Шаг второй: выбираем резолвер, принимающий «фильтр». Обычно это `users`, `orders`, `items`, `search`. Смотрим тип аргумента: строка, JSON, `JSONString`. Строковый JSON — самый вероятный кандидат.

Шаг третий: подставляем оператор. Пробуем `{"$ne":null}`, `{"$gt":""}`, `{"$regex":"^a"}`. Смотрим, меняется ли количество и состав результатов.

Шаг четвёртый: если фильтр не отражается в выводе напрямую, строим слепой оракул через `$regex` и алиасы, восстанавливая значение по символам.

Шаг пятый: проверяем мутации на массовое присваивание — добавляем `role`, `isAdmin`, `verified` и смотрим, принялись ли.

Шаг шестой: фиксируем доказательство — конкретную запись, которую не должен был видеть, с указанием запроса. Это и есть подтверждённая находка.

Такой порядок экономит время: ты не строишь exploitation, пока не подтвердил, что аргумент вообще уходит в базу.
