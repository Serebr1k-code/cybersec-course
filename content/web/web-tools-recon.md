Прежде чем что-то ломать, надо понять **что вообще живо и как оно устроено**. Этот этап — «разведка и сканирование»: у вас есть список целей (поддомены, IP, URL), и нужно быстро получить по ним карту — какие отвечают, что за технология, какие эндпоинты и параметры есть, какие известные уязвимости и мисконфиги уже светятся. Здесь работают три инструмента: **httpx** (проба и «паспорт» хоста), **katana** (обход-паук, собирает URL и параметры) и **nuclei** (шаблонный сканер известных багов).

Этот урок — навигатор по модулю. Он не заменяет справочники, а показывает, **что делает каждый инструмент, в каком порядке их запускать и как связать в один пайплайн**.

## Что покрывает этот этап

Этап «recon / scanning» решает четыре задачи, и у каждой — свой инструмент:

| Задача | Вопрос, на который отвечаем | Инструмент |
|--------|------------------------------|-----------|
| Проба хостов | «Что из списка живёт, какой там сервер, редирект, title, технологии?» | **httpx** |
| Обход приложения | «Какие URL, эндпоинты и параметры есть у живого хоста?» | **katana** |
| Известные баги | «Есть ли тут CVE, дефолтные креды, открытые конфиги, takeover?» | **nuclei** |
| Приоритизация | «Куда смотреть в первую очередь?» | все три вместе |

Ключевая идея: **сначала отсеять мёртвое и понять стек, потом ходить по нему, и только потом сканировать по шаблонам**. Сканировать мёртвый хост бессмысленно, а обходить без списка живых — медленно.

## Карта модуля

Два практических справочника внутри модуля:

- **[web-tool-httpx-katana](web-tool-httpx-katana)** — HTTP-проба массовых списков (httpx) и краулинг (katana). Все флаги проб, матчеры/фильтры, JSON-вывод, JS-crawl, формы, пайплайны.
- **[web-tool-nuclei](web-tool-nuclei)** — шаблонный сканер: фильтрация шаблонов, rate-limit, свой YAML-шаблон, DAST/fuzzing, Interactsh OOB.

- **[web-recon-fuzzing](web-recon-fuzzing)** — методология разведки и фаззинга (что искать и зачем).
- **[web-tooling](web-tooling)** — общий пайплайн инструментов и порядок «nuclei-first».
- **[web-tools-fuzz](web-tools-fuzz)** — следующий шаг: перебор путей/параметров (ffuf, gobuster, wfuzz).

## Порядок применения: httpx → katana → nuclei

Правильная последовательность для нового списка целей:

**Шаг 1. Проба живых хостов (httpx).** Превращаем сырой список поддоменов/IP в список URL с метаданными:

```bash
subfinder -d target.com -silent | httpx -silent -sc -title -td -o alive.txt
```

**Шаг 2. Обход живых (katana).** По каждому URL собираем эндпоинты и параметры:

```bash
katana -list alive.txt -d 3 -jc -silent -o urls.txt
```

**Шаг 3. Скан по шаблонам (nuclei).** По живым хостам — известные баги и мисконфиги:

```bash
nuclei -l alive.txt -severity low,medium,high,critical -silent -j -o nuclei.jsonl
```

**Шаг 4. Приоритизация.** Находки nuclei + интересные URL из katana → в ручной анализ (Burp) и в фаззинг (ffuf).

Важно: **nuclei-first** — прогоняйте шаблонный скан **до** глубокого ручного анализа: он дешёвый и часто сразу даёт «низковисящие фрукты» (открытый `.git`, дефолтные креды, известная CVE).

## Как выбирать инструмент

| Ситуация | Инструмент | Команда-затравка |
|----------|-----------|------------------|
| Есть 10 000 поддоменов, надо понять живые | httpx | `httpx -l subs.txt -silent -sc -title` |
| Один живой хост, надо собрать все ссылки | katana | `katana -u https://t -jc -silent` |
| Надо быстро прочесать по известным CVE/мисконфигам | nuclei | `nuclei -u https://t -silent` |
| Есть SPA на JS, ссылки генерируются в JS | katana | `katana -u https://t -jc -hl` |
| Есть OpenAPI/Swagger — не нужно краулить | nuclei/ffuf | подать спецификацию в nuclei `-im openapi` |
| Нужны только ответы с кодом 200/403 | httpx | `httpx -l u.txt -mc 200,403` |
| Нужен только конкретный CVE | nuclei | `nuclei -u t -id CVE-2024-XXXX` |

## Мини-пайплайн на одной строке

Классическая связка «список поддоменов → живые → пути → находки»:

```bash
subfinder -d target.com -silent \
  | httpx -silent -sc -title -td \
  | tee alive.txt \
  | katana -silent -jc -d 3 \
  | nuclei -silent -severity medium,high,critical -o findings.txt
```

Разбор строки: `subfinder` даёт поддомены → `httpx` оставляет живые и добавляет метаданные → `tee` сохраняет промежуточный список → `katana` обходит и отдаёт URL → `nuclei` сканирует эти URL. Каждый инструмент читает stdin и пишет в stdout, поэтому связка работает «из коробки».

## Частые ошибки

- **Сканировать мёртвые хосты.** Без `httpx`-фильтрации nuclei/katana тратят время на таймауты. Сначала проба.
- **Запускать nuclei по одному URL, когда их тысяча.** Подавайте список (`-l`), а не цикл `for`.
- **Забывать про rate-limit.** По умолчанию nuclei шлёт 150 rps — на слабом сервере это DoS. Снижайте `-rl`.
- **Краулить без `-jc`.** Современные приложения строят ссылки в JS; без `-js-crawl` katana их не найдёт.
- **Слепо доверять шаблонам.** nuclei даёт кандидатов; подтверждайте вручную (curl) перед отчётом.
- **Игнорировать `-silent` в пайплайне.** Баннеры и прогресс-бары ломают разбор stdout следующей утилитой.

## Инструменты разведки: флаги и примеры

Три ключевых инструмента этапа — `httpx` (живые хосты и стек), `katana` (краулинг, в т.ч. JS) и `nuclei` (CVE и мисконфиги). Ниже — рабочие наборы флагов.

```bash
# httpx: живые хосты, код, заголовок, сервер, технологии
httpx -l subs.txt -sc -title -server -td -silent -o live.txt
# с портами и сохранением тел
httpx -l subs.txt -p 80,443,8080,8443 -sc -fr -sr -srd /tmp/bodies -silent

# katana: краулинг с JS и глубиной
katana -u https://t -jc -d 3 -silent -o urls.txt
katana -u https://t -jc -silent | grep -oE 'https?://[^"]+'

# nuclei: CVE и exposure
nuclei -l live.txt -severity critical,high -tags cve,exposure -silent -o out.txt
nuclei -u https://t -json -silent -o out.json
nuclei -update-templates
```

| Инструмент | Флаг | Что делает |
|-----------|------|-----------|
| httpx | `-sc` | код состояния |
| httpx | `-td` | tech-detect |
| httpx | `-sr -srd` | сохранить ответы |
| katana | `-jc` | краулить JS |
| katana | `-d N` | глубина |
| nuclei | `-tags` | выбрать класс |
| nuclei | `-severity` | фильтр по критичности |
| nuclei | `-json` | машинный вывод |

## Разобранный пример: полный пайплайн

```bash
$ subfinder -d target.local -silent | httpx -silent -sc -title -td
https://app.target.local [200] [App] [nginx/1.20, PHP/8.1]
https://api.target.local [401] [API] [Express]
$ cat app.target.local | katana -jc -silent | grep -oE 'https?://[^"]+' | sort -u > urls.txt
$ nuclei -l urls.txt -tags cve,misconfig -silent
[app.target.local] [CVE-2024-XXXX] [critical] ...
```

Артефакт — подтверждённая CVE (воспроизводится `curl`).

## Что делать дальше / решение

Стройте пайплайн `subfinder → httpx → katana → nuclei` и запускайте его до глубокого фаззинга: это дешёвые, но информативные проверки. Затем триажируйте находки вручную (`curl`), фиксируйте отрицательные результаты, записывайте словари. И помните: `nuclei` находит по содержимому — не грепайте шаблоны по имени продукта, просто запускайте скан и давайте ему отработать (при необходимости поднимите таймаут).

## Словари: где брать и как выбирать

Качество разведки определяется словарём не меньше, чем инструментом. Источники: **SecLists** (`Discovery/`), **Assetnote Wordlists** (из реального краулинга), собственные списки из `katana`/`gau` (URL конкретной цели — самый точный), списки под технологии. Начинайте с `raft-medium-directories.txt` для каталогов, `raft-medium-words.txt` для файлов, отдельный список для параметров и vhost. Перед запуском проверяйте, не применялся ли этот словарь к данному `host:port:tool_type` — повтор не даёт информации.

```bash
ls /usr/share/seclists/Discovery/Web-Content/ | grep -iE 'raft|common|directories'
katana -u https://t -jc -silent | sed 's#https\?://[^/]*##' | sort -u > target-dirs.txt
```

## Rate-limiting и обнаружение

Активная разведка — тысячи запросов, и она легко приводит к бану. Признаки: рост времени, `429`/`503`, капча, обрывы. Против этого — снижение `-t`, паузы (`ffuf -p 0.1`), случайный User-Agent, распределение по хостам. Важно отличать бан от «мягкого 404»: если сервер начал отдавать 200 на всё — это может быть WAF-страница. Фильтруйте по размеру/словам (`-fs`, `-fw`). Если ответы стали одинаковыми — остановитесь и проверьте руками.

## Что делать дальше / решение

Стройте разведку итеративно: живые хосты (`httpx`) → краулинг (`katana`) → CVE (`nuclei`) → контент (`ffuf`). Каждую находку триажируйте (`curl`), записывайте словари и тупики, контролируйте темп. И помните: `nuclei` находит по содержимому — не грепайте шаблоны по имени продукта, запускайте скан и давайте ему отработать.

## Чек-лист разведки

- [ ] Собраны поддомены (`subfinder`), проверены живые (`httpx`).
- [ ] Определён стек и версии (`httpx -td`).
- [ ] Скраулены URL и JS (`katana -jc`).
- [ ] Прогнан `nuclei` (cve/exposure/misconfig).
- [ ] Перебран контент (записан словарь).
- [ ] Найдены параметры/vhost.
- [ ] Каждая находка подтверждена `curl`.
- [ ] Отрицательные результаты записаны.

## Где пригодится

- **CTF (Web):** быстро понять стек и найти известный баг, не тратя время на ручной перебор.
- **Bug bounty:** стандартный пайплайн subfinder → httpx → katana → nuclei даёт карту программы за минуты.
- **Пентест:** проба и приоритизация целей перед ручным тестом; доказательства находок для отчёта.
- **Работа (AppSec/DevSecOps):** автоматизация регулярных сканов в CI и мониторинг изменений поверхности атаки.
