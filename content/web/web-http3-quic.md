HTTP/3 (QUIC) — новый транспорт поверх UDP, уже развёрнутый у крупных провайдеров. Для атакующего важны три вещи: **0-RTT replay**, **downgrade H3→H2** (рассинхрон между транспортами) и то, что WAF/прокси часто не умеют H3 — значит, часть запросов идёт мимо защиты. Это «forward-looking» тема: пока эксплуатируется редко, но поверхность растёт.

## Теория: QUIC в двух словах

- Транспорт — UDP (обычно порт 443).
- Встроенное TLS 1.3, мультиплексирование потоков без HOL-блокировки.
- **0-RTT** — возобновление соединения без полного рукопожатия (данные отправляются сразу).
- Альтернативные потоки: QPACK вместо HPACK.
- Заголовок `Alt-Svc: h3=":443"` сообщает браузеру, что доступен H3.

Определить поддержку:

```bash
curl --http3 -sI https://app.example/            # если curl собран с HTTP/3
dig +short HTTPS app.example                     # HTTPS-запись с alpn=h3
nmap -sU -p 443 --script quic-* app.example
```

## Теория: чем меняется поверхность атак

- **WAF может не парсить QUIC** → запросы по H3 обходят фильтры, которые работают на H2/H1.
- **0-RTT replay:** данные 0-RTT можно повторить (replay) — если сервер применяет их без защиты, повторяется действие (платёж, заказ).
- **Downgrade:** балансировщик терминирует H3, а бэкенд говорит по H2/H1 — заголовки/границы запроса могут разойтись → desync/request smuggling.
- **Нет `Content-Length`-семантики** как в H1 — свои фреймы.

## Теория: downgrade-цепочка

Типичная архитектура: клиент → (H3) → edge (терминирует QUIC) → (H2/H1) → бэкенд. Если edge неаккуратно конвертирует, возможны:

- Расхождение в обработке `Transfer-Encoding`/границ.
- Подмена/дублирование заголовков при конвертации.
- Обход правил, применяемых только на H3-терминаторе.

## Инструменты и команды

- **`curl --http3`** (сборка с ngtcp2/quiche) — запросы по H3.
- **`h3spec`/`quiche`** — тесты QUIC/H3.
- **`aioquic`** (Python) — кастомные QUIC-клиенты (для replay/desync).
- **`nmap`** — `quic-*` NSE-скрипты.
- **Burp** — поддержка H3 ограничена; используйте прокси/скрипты.

## Разобранный пример: 0-RTT replay

Шаг 1 — определите, что сервер поддерживает 0-RTT (`Alt-Svc`, перехват рукопожатия).
Шаг 2 — перехватите 0-RTT-данные (например, POST-платёж) через `aioquic`-скрипт.
Шаг 3 — повторите их в новой 0-RTT-сессии:

```python
# концепт на aioquic: собрать Initial+0-RTT с теми же early_data
# если сервер не защищён anti-replay -> действие применяется дважды
```

Успех: заказ/платёж применился дважды.

## Разобранный пример: desync на H3→H2 downgrade

Шаг 1 — определите, что edge терминирует H3, а бэкенд — H2.
Шаг 2 — отправьте запрос по H3 с обфусцированными заголовками (`Transfer-Encoding`/`Content-Length`-конфликт при конвертации).
Шаг 3 — наблюдайте рассинхрон: второй запрос обрабатывается как «запаздывающий» ответ первого (см. `web-request-smuggling`).

## Что дальше / decision

1. Проверьте `Alt-Svc`/HTTPS-запись — есть ли H3.
2. Если есть → попробуйте обойти WAF, отправив атаку по H3.
3. Есть 0-RTT → тестируйте replay.
4. Edge терминирует H3 → тестируйте downgrade/desync.
5. Дальше — комбинируйте с smuggling/кэш-отравлением.

## Атаки на QPACK и потоки

- **QPACK-инъекция:** расхождение в динамической таблице заголовков между клиентом и сервером может дать header confusion (аналог HPACK-атак в H2).
- **Stream priority/reset abuse:** сброс потоков (RST_STREAM) для обхода лимитов/DoS.
- **Connection migration:** смена пути (IP) в середине соединения — обход привязки к IP.

## Разобранный пример: обход WAF через H3

Шаг 1 — убедитесь, что WAF работает на H1/H2, а H3 терминируется отдельно.
Шаг 2 — отправьте инъекцию по H3:

```bash
curl --http3 -s "https://app.example/item?id=1%27%20OR%201=1--" 
```

Шаг 3 — если H3-путь не проходит через WAF — инъекция достигает бэкенда. Это особенно ценно, когда H1/H2-запросы блокируются.

## Практические ограничения

- `curl --http3` требует специальной сборки (ngtcp2/quiche) — проверьте `curl --version`.
- Burp/ZAP плохо работают с QUIC — используйте `aioquic`-скрипты.
- Многие WAF/CDN уже парсят H3 — обход не гарантирован, тестируйте.

## Частые ошибки

- **Игнорировать H3.** WAF его может не видеть.
- **Путать 0-RTT и обычный TLS.** Здесь early data можно реплеить.
- **Забыть про downgrade.** Расхождение транспортов = desync.
- **Считать H3 непроницаемым.** Это UDP-транспорт с той же семантикой.
- **Ломать прод.** Replay/desync — аккуратно.

## QUIC и HTTP/3: что важно для атакующего

QUIC — это транспорт поверх UDP с встроенным TLS 1.3, а HTTP/3 — его прикладной слой. Для тестировщика важны несколько отличий от TCP/TLS.

| Свойство | TCP+TLS | QUIC/HTTP/3 |
|----------|---------|-------------|
| Транспорт | TCP | UDP |
| Шифрование | TLS поверх | встроено (TLS 1.3) |
| Установка | TCP + TLS handshakes | 1 RTT, 0-RTT возможен |
| Мультиплексирование | HTTP/2 потоки | нативные потоки QUIC |
| Заголовки | HPACK | QPACK |
| Соединение | привязано к 4-tuple | Connection ID (миграция) |
| 0-RTT | нет | да (replay-риск) |

```bash
# проверка поддержки HTTP/3
curl --http3 -sI https://app.example/ | head -1
# определение через альтернативный сервис (Alt-Svc)
curl -sI https://app.example/ | grep -i alt-svc
# nmap UDP 443
nmap -sU -p443 app.example
```

## 0-RTT replay: детали и эксплуатация

0-RTT позволяет клиенту отправить данные сразу, без полного рукопожатия. Это открывает replay: ранние данные можно переиграть.

```text
1) клиент устанавливает соединение и получает session ticket
2) при следующем соединении отправляет 0-RTT-данные (например, POST)
3) атакующий, перехватив 0-RTT-пакет, повторяет его
4) сервер (без защиты от replay) выполняет операцию дважды
```

Защита — сервер должен отклонять 0-RTT для неидемпотентных методов (POST/PUT) или использовать anti-replay. Проверяйте, принимает ли сервер `POST` в 0-RTT.

## Desync на H3→H2 downgrade

Когда фронт-прокси принимает HTTP/3, а бэкенду отдаёт HTTP/2 (или h1), возможен smuggling.

```text
# прокси транслирует H3-запрос в H2, но по-разному обрабатывает:
# - псевдо-заголовки (:method, :path)
# - размеры фреймов
# - соединение Connection-ID
```

Атаки: рассинхрон потоков, обход `:path` через кодирование, использование разных `Host`/`:authority`. Это близко к request smuggling (см. `web-request-smuggling`).

## QPACK и потоки

QPACK (сжатие заголовков в H3) и потоки QUIC — новые поверхности.

| Механизм | Риск |
|----------|------|
| QPACK dynamic table | рассинхрон декодирования |
| Потоковые ID | предсказуемость/подмена |
| Connection ID | миграция/фиксация |
| Отмена потока | resource exhaustion |

```bash
# aioquic — Python-клиент для ручных экспериментов
python3 -m aioquic.examples.http3_client https://app.example/
# quiche — Rust-инструментарий
cargo run --bin quiche-client -- https://app.example/
```

## Разобранный пример: обход WAF через H3

Многие WAF не парсят HTTP/3, пропуская запрос «как есть».

```bash
# обычный H2-запрос блокируется WAF
curl -s 'https://app.example/?q=<script>alert(1)</script>' -o /dev/null -w '%{http_code}\n'
# тот же запрос по H3 может пройти
curl --http3 -s 'https://app.example/?q=<script>alert(1)</script>' -o /dev/null -w '%{http_code}\n'
# если коды различаются -> WAF не покрывает H3
```

Дальше — классическая эксплуатация (XSS/SQLi) через H3-канал.

## Приоритеты при тестировании HTTP/3

Начните с обнаружения: `Alt-Svc` в ответе и `curl --http3` показывают, поддерживает ли сервер H3. ## Расширенный разбор: 0-RTT и миграция соединений

Две специфичные для QUIC возможности заслуживают отдельного внимания. Первая — 0-RTT: сервер, принимающий POST в ранних данных без anti-replay, уязвим к повтору операции (покупка, перевод, отправка сообщения). Проверяется просто: перехватите 0-RTT-пакет и отправьте его повторно — если операция выполнилась дважды, replay подтверждён. Вторая — миграция соединения по Connection ID: если сервер не привязывает соединение к адресу клиента, возможна подмена/фиксация. Оба вектора редки, но в «экзотических» стеках встречаются и часто не покрыты WAF.

```bash
# проверка 0-RTT-приёма для POST
curl --http3 -s -X POST https://app.example/action -d 'x=1' -o /dev/null -w '%{http_code}\n'
# повтор того же запроса (если идемпотентность не проверяется — эффект двойной)
```

Если H3-стек нестандартный (свой сервер, редко обновляемый), именно эти два вектора стоит проверить первыми.
