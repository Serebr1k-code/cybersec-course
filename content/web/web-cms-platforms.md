## Вопрос, с которого всё начинается

Половина сайтов в интернете — не написанные с нуля приложения, а **CMS**: готовые движки, которые ставят, настраивают и дополняют плагинами. Значит, и уязвимости там живут не в уникальном коде, а в **общих местах**: ядро определённой версии, конкретный плагин, конкретная тема.

Из этого следует практический вывод: если ты научишься быстро определять, *какая* это CMS и *какой* версии, — ты сможешь подбирать готовые публичные эксплойты, а не искать баги вслепую. Сегодня мы разберём, как это делается, на четырёх самых распространённых движках.

## Что такое CMS и почему это отдельная поверхность

**CMS** (Content Management System, система управления контентом) — это приложение, которое даёт неспециалисту создавать страницы, товары, статьи через веб-интерфейс, а всю «начинку» (базу данных, шаблоны, права) берёт на себя.

Ключевая особенность для нас — **расширяемость**. Ядро CMS обычно пишут аккуратно, а вот **плагины** и **темы** пишут тысячи сторонних авторов, и именно там ломается чаще всего. По статистике уязвимостей WordPress около 90% приходятся на плагины и темы, а не на ядро.

Второй важный факт: у каждой CMS есть **предсказуемая структура URL** — `/wp-login.php`, `/administrator/`, `/user/login`. Это одновременно и подсказка для нас, и точка входа.

## Наш пример: находим CMS на цели

Дана цель `https://target.example`. Мы ещё не знаем, что там внутри. Первый шаг — снять **фингерпринт** (отпечаток стека). Начнём с универсального инструмента:

```
$ whatweb -a 3 https://target.example
https://target.example [200 OK] WordPress[6.4.2], MetaGenerator[WordPress 6.4.2],
  X-Powered-By[PHP/8.1.27], JQuery, Apache
```

Читаем: это **WordPress 6.4.2** на PHP 8.1.27 под Apache. Версия ядра видна сразу — она часто светится в мета-теге `generator` или в заголовках. Уже этого достаточно, чтобы открыть базу уязвимостей (WPScan, CVE-базы) и посмотреть, что известно для 6.4.2.

Если `whatweb` не даёт версию, её тянут из служебных файлов. У WordPress это `/feed/`, `/readme.html`, `/wp-links-opml.php`:

```
$ curl -s https://target.example/readme.html | grep -i 'version'
Version 6.4.2
```

У Drupal версию выдаёт `/CHANGELOG.txt` или `/core/CHANGELOG.txt`. У Joomla — `/administrator/manifests/files/joomla.xml`. У Magento — специальный эндпоинт `/magento_version`.

## Шаг 1: определяем CMS по «паспортным» путям

Каждая CMS оставляет узнаваемые пути. Достаточно нескольких запросов, чтобы отличить движки друг от друга:

| CMS | Сигнатура | Что вернёт |
|---|---|---|
| WordPress | `/wp-login.php`, `/wp-json/`, `/xmlrpc.php` | форму входа, JSON-API |
| Drupal | `/core/misc/drupal.js`, `/CHANGELOG.txt` | JS ядра, лог версий |
| Joomla | `/administrator/`, `/components/com_users/` | панель админа |
| Magento | `/magento_version`, `/index.php/admin` | строку версии, админку |

Проверяем по одному:

```
$ curl -sI https://target.example/wp-login.php | head -1
HTTP/2 200
$ curl -s https://target.example/wp-json/ | head -c 120
{"name":"Target Blog","description":"Just another WordPress site",...
```

`/wp-json/` ответил JSON-ом с названием сайта — это однозначный признак WordPress. Одновременно это и **API**: WordPress REST отдаёт список пользователей, постов, настроек, если права настроены неаккуратно.

## Шаг 2: где живут уязвимости — ядро, плагины, темы

Теперь важно понять **раскладку кода**. В WordPress:

- **ядро** — `/wp-includes/`, `/wp-admin/` (обновляется автоматически, свежие баги редки);
- **плагины** — `/wp-content/plugins/<имя>/` (основной источник дыр);
- **темы** — `/wp-content/themes/<имя>/`.

Значит, следующий вопрос: **какие плагины и темы стоят и каких версий**. Их перечисляют сканеры вроде `wpscan`:

```
$ wpscan --url https://target.example --enumerate vp,vt,u --no-banner
[+] URL: https://target.example/
[+] WordPress version 6.4.2 identified
[+] Plugin: contact-form-7 (version 5.8.1)  — outdated
[+] Theme: twentytwentythree (version 1.2)
[+] User(s) Identified:
    admin
    editor
```

Здесь `vp` — vulnerable plugins, `vt` — vulnerable themes, `u` — users. Мы узнали: стоит устаревший Contact Form 7 5.8.1 и есть пользователь `admin`. Оба факта — зацепки.

Для Drupal аналог — `droopescan`, для Joomla — `joomscan`, для Magento — `magescan`. Все они работают по одному принципу: перебирают известные пути и сверяют версии с базами уязвимостей.

## Шаг 3: общие точки входа, которых не ждёшь

Помимо «официальных» страниц, у CMS есть служебные скрипты, которые часто забывают закрыть:

- **`xmlrpc.php`** (WordPress) — принимает XML-RPC. Через `system.multicall` можно за один запрос перебрать сотни паролей, обходя лимиты; а `pingback.ping` превращает сайт в SSRF-прокси.
- **`wp-cron.php`** — запуск отложенных задач. Дёргается по HTTP, может быть использован для DoS или для ускорения выполнения чужого кода.
- **`/wp-json/wp/v2/users`** — перечисление пользователей в открытом виде.

Проверим перечисление пользователей:

```
$ curl -s https://target.example/wp-json/wp/v2/users | head -c 200
[{"id":1,"name":"admin","slug":"admin"},{"id":2,"name":"editor","slug":"editor"}]
```

Мы получили логины без аутентификации. Теперь можно целиться точечно.

## Шаг 4: из фингерпринта — в эксплойт

Когда известна точная версия плагина, открывают базу и ищут PoC. Например, для Contact Form 7 старых версий известны XSS; для других плагинов — SQLi и загрузка файлов. Логика одна: **версия → CVE → публичный PoC → проверка на цели**.

Важно: PoC — это чужой код. Его читают, а не запускают вслепую, и репойнтят колбэки на свой слушатель.

## Шаг 5: атака на админку и RCE

Финальная стадия CMS-атаки обычно такая: войти в админку (подбор слабого пароля, украденный хэш, обход аутентификации) → загрузить **плагин** или править **тему** через встроенный редактор → получить исполнение PHP-кода.

Именно поэтому в WordPress критично закрывать `/wp-admin/` и запрещать редактирование файлов (`DISALLOW_FILE_EDIT`). Плагин-«веб-шелл» в архиве ZIP, установленный через админку, — классический путь к RCE.

## Что мы теперь знаем

- CMS — это ядро + плагины + темы; ломается почти всегда в плагинах.
- Фингерпринт снимается через `whatweb` и «паспортные» пути (`/wp-json/`, `/CHANGELOG.txt`).
- Сканеры (`wpscan`, `droopescan`, `joomscan`) перечисляют версии плагинов и пользователей.
- Служебные скрипты (`xmlrpc.php`, `/wp-json/wp/v2/users`) — частые незакрытые двери.
- Финальная цель CMS-атаки — попасть в админку и загрузить код.

## Шаг 6: как не перепутать движок и не потратить часы впустую

Ошибка новичка — «увидел слово `wp-` и решил, что это WordPress». На деле сигнатуры пересекаются: плагины одного движка ставят на другой, кэш-плагины отдают чужой HTML, а самописные сайты копируют чужие URL. Поэтому правило простое: **подтверждай движок минимум двумя независимыми признаками**.

Разберём на примере. Сайт вернул `404` на `/wp-json/` и `200` на `/wp-login.php`. Что это значит? Второй признак сильнее: `/wp-login.php` — уникальный файл ядра WordPress, его не бывает у других. Значит, перед нами WordPress с отключённым REST (фильтр `rest_authentication_errors`). А если бы наоборот — 200 на `/wp-json/`, но 404 на `/wp-login.php`, — это мог быть любой плагин, эмулирующий API.

Ещё одна ловушка — **CDN и WAF маскируют версии**. Cloudflare переписывает заголовки, склеивает запросы, отдаёт кэшированные ответы. Если `whatweb` показал «WordPress» без версии, версию тянут из тела страницы, из `/readme.html`, из `/wp-includes/js/wp-emoji-release.min.js` (там номер версии в комментарии). Если и это закрыто — идём в статику: пути `/wp-content/themes/<тема>/style.css` содержат заголовок `Version:`.

## Шаг 7: безопасность при работе с чужими PoC и общие правила

Публичный эксплойт — это **чужой код**. Прежде чем запускать его на цели, ответь на три вопроса. Первый: что он вообще делает (прочитай!). Второй: куда он шлёт данные — если на чужой хост, это утечка, репойнти на свой слушатель. Третий: может ли он уронить сервис — деструктивные PoC (`DROP TABLE`, массовые изменения) на живом проде запрещены.

Практический порядок работы с CMS всегда один и тот же:

1. **Фингерпринт** — движок и версия (двумя признаками).
2. **Инвентарь** — плагины/темы/компоненты и их версии.
3. **Сопоставление** — версия → CVE → PoC (WPScan DB, NVD, nuclei).
4. **Проверка** — безопасный неразрушающий запрос, подтверждающий уязвимость.
5. **Эксплуатация** — только после подтверждения, с сохранением доказательств.

Нарушение порядка (сразу запустить эксплойт «наугад») приводит либо к падению сервиса, либо к ложному выводу «не работает», хотя версия была просто определена неверно.

## Шаг 8: где CMS-атаки стоят в общем плане

CMS-поверхность почти всегда **открытая** (доступна из интернета), но **не всегда самая ценная** (за ней может не быть чувствительных данных). Поэтому её место в плане — «быстрый вход»: пока идут другие работы, CMS проверяется параллельно, дешёвыми запросами.

Если CMS ведёт в админку и оттуда виден доступ к БД, интеграциям или внутренней сети — вектор повышается в приоритете, потому что открывает путь глубже. Если CMS — витрина без данных и без интеграций, её ломают «для галочки» и переходят к другим целям. Это и есть распределение усилий по ожидаемой ценности: не тратить часы на бесперспективный движок, когда рядом лежит прямой путь.

И помни про обратимость: любые изменения (загрузка плагина, правка темы) — это след. Если задача — остаться незамеченным, выбирай векторы без записи на диск (SQLi-чтение, обход аутентификации), а не RCE-загрузку.

## Куда дальше

В следующих уроках мы возьмём каждый движок по отдельности: WordPress (`xmlrpc`, REST, подделка cookie), Drupal (`Drupalgeddon`), Joomla (`com_`-компоненты) и Magento (SQLi и CosmicSting). А пока главное: **сначала фингерпринт — потом эксплойт, а не наоборот**.

## Где пригодится

- Bug bounty: почти каждая программа включает WordPress/Drupal/Joomla-сайты.
- Пентест: CMS — самый частый «вход» в корпоративные сайты.
- CTF: задания на CMS-эксплуатацию с точной версией.
