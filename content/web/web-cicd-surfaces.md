## Вопрос, с которого всё начинается

Ты смотришь на внутреннюю сеть и видишь знакомые панели: репозиторий кода, сервер сборки, хранилище артефактов, система деплоя в Kubernetes. Для инженеров это рабочие инструменты, а для атакующего — **конвейер доступа**: исходный код, токены CI, артефакты, права на деплой. Взломав одну из этих панелей, ты часто получаешь путь до продакшена, минуя всю защиту веб-приложения. Разберём, почему так.

## Что общего у CI/CD-систем

CI/CD-системы (continuous integration / continuous delivery) автоматизируют путь кода: разработчик пушит коммит — система собирает, тестирует и выкладывает его. SCM (source control management) хранит код; репозиторий артефактов — собранные пакеты; система деплоя — применяет конфигурацию в кластер.

Общее у них:

- **Они содержат секреты.** CI-переменные хранят пароли к базам, ключи облака, токены registry. SCM хранит SSH-ключи деплоя.
- **Они исполняют код.** Сервер сборки запускает произвольные скрипты (по дизайну). ArgoCD применяет манифесты в Kubernetes.
- **У них есть API и токены.** Для автоматизации каждая система даёт API-токены, часто с широкими правами.
- **Их права — высокие.** Токен CI может деплоить в прод; токен SCM может менять код.

Отсюда правило: **CI/CD-панель = потенциальный RCE и доступ в прод**. Именно поэтому они — излюбленная цель и для пентеста, и для реальных атак (SolarWinds, Codecov).

## Анатомия типового пайплайна

Проследим путь кода, чтобы понять, где что лежит:

1. Разработчик пушит код в **SCM** (Gitea, GitLab, Gogs).
2. **CI-сервер** (TeamCity, Jenkins) видит пуш, забирает код и запускает сборку. На этом шаге доступны CI-переменные с секретами.
3. Собранный артефакт кладётся в **репозиторий** (Nexus, Artifactory).
4. **CD-система** (ArgoCD) берёт манифест и применяет его в Kubernetes.

Каждый шаг — отдельная панель с собственным API, правами и CVE. Атакуя, ты выбираешь самый слабый узел, а затем двигаешься по цепочке: из SCM достаёшь токен CI, из CI — ключи облака, из облака — прод.

## Наш пример: четыре панели в подсети

Тебе дали внутренний диапазон. Прогоняем фингерпринт:

```
$ httpx -l dev.txt -title -tech-detect -status-code -silent
http://10.30.0.5:3000  [200] [Gitea]
http://10.30.0.6:8111  [200] [TeamCity]
http://10.30.0.7:8081  [200] [Nexus Repository]
http://10.30.0.8:8080  [200] [Argo CD]
```

Четыре панели — четыре вектора. Дальше — общая методика.

## Шаг 1: определить продукт и версию

- **Gitea/Gogs:** `/api/v1/version` отдаёт версию; страница `/explore`.
- **TeamCity:** `/login.html` и заголовок; версия видна в `/app/rest/server`.
- **Nexus:** `/service/rest/v1/status` и `/service/rest/v1/status/check`.
- **Artifactory:** `/artifactory/api/system/ping` и `/artifactory/api/system/version`.
- **ArgoCD:** `/api/version` и заголовок `Argocd`.

Точная версия — обязательна: у каждой системы свой список CVE.

## Шаг 2: проверить анонимный доступ

Прежде чем искать CVE, проверь, что открыто **без аутентификации**. Часто панель настроена так, что анонимный доступ разрешён:

```
$ curl -s http://10.30.0.5:3000/api/v1/repos/search | head -c 200
$ curl -s http://10.30.0.7:8081/service/rest/v1/repositories | head -c 200
```

Если репозитории и пакеты видны без логина — это уже находка: утечка исходников и артефактов. Дальше ищем в них секреты.

## Шаг 3: default-креды

Вторая частая проблема — пароли по умолчанию: `admin/admin`, `admin/admin123`, `admin/password`. Проверяй их **вручную, по одному** (не брутфорсом): три-четыре попытки, потом стоп, чтобы не заблокировать учётку.

## Шаг 4: CVE по версии

Для каждой панели — свои CVE:

- **Gitea/Gogs:** CVE-2024-6886 (XSS), CVE-2022-30781 (RCE через шаблон), обход аутентификации в старых Gogs.
- **TeamCity:** CVE-2023-42793 (обход аутентификации → RCE), CVE-2024-27198/27199 (обход → RCE).
- **Nexus:** CVE-2024-4956 (path traversal), CVE-2019-7238 (RCE через EL).
- **Artifactory:** CVE-2024-41801, анонимный доступ, CVE-2019-9733 (обход аутентификации).
- **ArgoCD:** CVE-2022-29165 (SSRF), слабый JWT-секрет, repo SSRF.

## Шаг 5: пост-эксплуатация — движение по цепочке

Главное отличие CI/CD-атаки: цель не «сломать панель», а **пройти по конвейеру**. Из SCM достаёшь токены CI; из CI — креды облака и registry; из репозитория артефактов — пакеты; из ArgoCD — доступ к кластеру. Каждая панель — ступень к следующей.

## Шаг 6: как не сломать сборку

CI/CD-панели активно используются: их падение останавливает разработку. Поэтому: не запускай реальные сборки, не меняй пайплайны, не удаляй артефакты, не триггерь деплой. Читай и доказывай, но не трогай процесс.

## Что мы теперь знаем

- CI/CD-панели содержат секреты, исполняют код и имеют высокие права.
- Типовой пайплайн: SCM → CI → registry → CD.
- Методика: продукт → версия → анонимный доступ → default-креды → CVE.
- Ценность — не в панели, а в движении по конвейеру.
- Их нельзя ломать: на них стоит разработка.
