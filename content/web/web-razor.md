## Вопрос, с которого всё начинается

Веб-приложение на ASP.NET Core генерирует страницу из шаблона Razor. Часть шаблона берётся из параметра запроса. Ты отправляешь `@(7*7)` — и получаешь `49`. Привычные `{{...}}` не работают вовсе: это не Jinja и не Thymeleaf, а Razor, и он исполняет **C#**.

Razor — это шаблонизатор .NET, где шаблон смешан с C#-кодом. Выражения `@(...)` выводят значение, блоки `@{...}` исполняют код. Если пользовательский ввод попадает в такой блок, он исполняется как C# на сервере — с правами пула приложений.

## Razor на сервере: где это встречается

Razor — не только клиентский Blazor. Серверные сценарии:

- **MVC/Pages** — шаблоны `.cshtml`, которые рендерит сервер.
- **Razor Pages runtime compilation** — компиляция шаблона из строки во время работы.
- **Генераторы отчётов и email** — шаблон собирается из данных пользователя.
- **Blazor Server** — рендеринг компонентов на сервере, где выражения исполняются в процессе приложения.

Инъекция возникает, когда **строка шаблона** формируется из ввода. Например, приложение даёт пользователю задать формат письма, а потом рендерит его через Razor.

## Наш пример: шаблон из параметра

Договоримся о примере. Эндпоинт `https://app.target/render?tpl=...` компилирует переданную строку как Razor. Проверяем:

```
$ curl -s 'https://app.target/render?tpl=%40%287*7%29'
49
```

Символ `@` (URL-кодирование `%40`) начинает выражение Razor, `(7*7)` вычисляется. Движок подтверждён. Теперь проверяем доступ к C#-типам:

```
$ curl -s 'https://app.target/render?tpl=%40%28System.Environment.Version%29'
7.0.0
```

Доступ к классам есть. Значит, путь к исполнению кода открыт.

## Путь к RCE

Razor исполняет C# в том же процессе, что и веб-приложение, поэтому доступны все типы .NET. Простейшие пути:

- **Чтение файлов**: `@(System.IO.File.ReadAllText("/etc/passwd"))`.
- **Исполнение команд**: `@(System.Diagnostics.Process.Start("cmd","/c whoami"))`.
- **Чтение вывода процесса**: `Process.Start` не возвращает вывод, поэтому используют `ProcessStartInfo` с `RedirectStandardOutput` и читают поток.

Пример чтения файла, который сразу даёт результат:

```
$ curl -s 'https://app.target/render?tpl=%40%28System.IO.File.ReadAllText(%22%2Fflag%22%29%29'
nto{...}
```

Для команд в Windows чаще читают файл, чем возятся с перенаправлением вывода:

```
@(System.Diagnostics.Process.Start("cmd","/c type C:\\flag.txt"))
```

Команда выполнится, а результат можно прочитать отдельным запросом, если он записан в файл.

## Обход фильтров

Фильтры блокируют `System.IO`, `Process`, `@(`. Обходы:

- **Юникод и экранирование**: `%40` вместо `@`, экранированные точки.
- **Косвенный доступ**: `@(typeof(string).Assembly...)` для рефлексии и загрузки типов.
- **Сборка строк**: имя типа собирается из фрагментов.
- **Blazor-компоненты**: инъекция в параметр компонента иногда даёт доступ к `IJSRuntime` и дальше к произвольному коду.

Как и везде, чёрный список строк не закрывает возможность: типов в .NET много, и хотя бы один путь останется.

## Что мы теперь знаем

- Razor использует `@(...)` и `@{...}`, а не двойные скобки.
- Razor исполняет C# в процессе приложения с правами пула.
- Путь к RCE: `System.IO.File`, `System.Diagnostics.Process`.
- `Process.Start` не возвращает вывод — результат читают через файл или поток.
- Защита — не компилировать пользовательский ввод как шаблон.

## Blazor и серверный рендеринг: дополнительная поверхность

Razor-инъекции встречаются не только в классических `.cshtml`. Blazor добавил новую поверхность.

**Blazor Server** рендерит компоненты на сервере и держит постоянное соединение с браузером. Параметры компонентов могут приходить из URL или из состояния. Если приложение позволяет передать Razor-разметку как параметр и рендерит её через `MarkupString`, ввод исполняется. Классическая ошибка — использовать `MarkupString` для пользовательских данных: это отключает экранирование.

**Razor runtime compilation** позволяет компилировать шаблон из строки во время работы. Это удобно для CMS и генераторов отчётов, но если строка контролируется пользователем — это SSTI. Найти такую функциональность можно по вызовам `RazorTemplateEngine`, `RazorProjectEngine` и компиляции `.cshtml` из памяти.

**Динамические формы и отчёты.** Приложения, где пользователь задаёт шаблон письма или отчёта, часто используют Razor или Liquid. Оба исполняют код, если ввод становится шаблоном.

Проверять нужно именно те эндпоинты, где **пользователь влияет на разметку**, а не только на данные. Это ключевой признак: где ввод становится шаблоном, там и SSTI.

## Как искать Razor SSTI в чёрном ящике

Без исходников действуем так.

Сначала определяем платформу. Заголовки `Server: Kestrel`, cookie `.AspNetCore.Session`, `X-Powered-By: ASP.NET` указывают на .NET. Это уже сужает движки до Razor, Liquid, Scriban.

Затем ищем параметры, влияющие на разметку: шаблон письма, формат отчёта, тему оформления, язык, кастомный HTML. Для каждого отправляем `@(7*7)` и `{{7*7}}`. Если `@(7*7)` вернуло `49` — это Razor или Scriban с `@`.

Уточняем: Razor исполняет C#, поэтому проверяем `@(7*7)` и `@("a"+"b")`. Scriban имеет свой синтаксис с `{{ }}` и фильтрами. Ошибки компиляции в ответе выдают движок по именам типов.

Наконец, проверяем доступ к типам: `@(System.Environment.Version)`. Если вывелась версия — путь к `System.IO.File.ReadAllText` открыт. Дальше — чтение флага или запуск процесса.

## Ограничения и нюансы

Есть несколько практических нюансов, которые важно учитывать.

**Права процесса.** Razor исполняется с правами пула приложений (`IIS APPPOOL\<name>` или сервисный аккаунт). Это часто не администратор, но достаточно для чтения файлов приложения, конфигов с connection string и, иногда, ключей.

**Компиляция добавляет задержку.** Первый запрос с новым шаблоном компилируется, поэтому ответ может прийти медленнее. Это не ошибка — просто особенность.

**Кэш шаблонов.** Некоторые приложения кэшируют скомпилированные шаблоны по ключу, и повторный запрос может вернуть старый результат. Пробуй уникальные строки, чтобы обойти кэш.

**Вывод процесса.** `Process.Start` не возвращает stdout, поэтому для команд либо перенаправляют вывод в файл и читают его, либо используют `ProcessStartInfo` с `RedirectStandardOutput`. Для простой проверки достаточно чтения файла — оно сразу даёт результат в ответе.

## Полный walkthrough на реальной цели

Разберём сценарий целиком, как он выглядит в пентесте.

**Шаг 1. Определение платформы.** Смотрим заголовки: `Server: Kestrel`, `X-Powered-By: ASP.NET`. Cookie сессии вида `.AspNetCore.Session`. Платформа — .NET Core. Возможные движки: Razor, Scriban, Liquid.

**Шаг 2. Поиск параметра-шаблона.** Ищем функциональность, где пользователь влияет на разметку: настройка email-шаблона, конструктор отчётов, тема. Отправляем туда `@(7*7)`. Получаем `49` — движок Razor, и он исполняет C#.

**Шаг 3. Проверка доступа к типам.** Отправляем `@(System.Environment.Version)`. Видим `7.0.0`. Доступ к пространствам имён есть. Значит, `System.IO` и `System.Diagnostics` тоже доступны.

**Шаг 4. Чтение файла.** `@(System.IO.File.ReadAllText("appsettings.json"))` — читаем конфиг приложения. Там connection string, ключи, иногда секреты. Для флага: `@(System.IO.File.ReadAllText("/flag"))`.

**Шаг 5. Команда.** Если нужна команда ОС: `@(System.Diagnostics.Process.Start("cmd","/c whoami > C:\\out.txt"))`, затем читаем `C:\out.txt` тем же `ReadAllText`. Либо `ProcessStartInfo` с `RedirectStandardOutput`.

**Шаг 6. Отчёт.** Фиксируем: платформа, параметр, payload, результат. Приводим, что именно вернулось на каждом шаге.

Этот порядок универсален: определить платформу → найти параметр-шаблон → подтвердить синтаксис → дотянуться до типов → выполнить действие → зафиксировать.

## Итог

Razor SSTI — это исполнение C# в процессе веб-приложения. Определяется по `@(...)`, путь к RCE идёт через `System.IO` и `System.Diagnostics`. Ключевой признак уязвимости — эндпоинт, где пользовательский ввод становится шаблоном. Защита — держать шаблоны статическими и не использовать `MarkupString` для пользовательских данных.

## Частые вопросы и типичные ошибки

Несколько практических замечаний по Razor.

Первый вопрос: «Почему `{{7*7}}` не работает?» Razor использует `@`, а не фигурные скобки. Отправляй `@(7*7)`.

Второй вопрос: «`Process.Start` выполнился, но вывода нет». Так и должно быть: метод запускает процесс и не возвращает stdout. Читай результат через файл или `ProcessStartInfo.RedirectStandardOutput`.

Третья ошибка: путать клиентский Blazor WebAssembly с серверным. В WebAssembly код исполняется в браузере пользователя, там нет доступа к серверным файлам. Серверный Razor и Blazor Server — другое дело, там код исполняется на сервере.

Четвёртая ошибка: не проверить права. Razor работает с правами пула приложений. Читать файлы приложения обычно можно, но системные пути могут быть недоступны. Проверяй, что именно доступно, а не предполагай root.

Пятая ошибка: игнорировать кэш шаблонов. Повторный запрос может вернуть старый результат — используй уникальные строки.

Эти нюансы определяют разницу между «нашёл» и «доказал».

## Резюме ветки

Razor — .NET-движок, исполняющий C# в процессе приложения. Признак — `@(...)`, путь к RCE — через `System.IO` и `System.Diagnostics`. Главное отличие от Java-движков в том, что здесь нет «preprocessing»: инъекция либо компилируется как Razor, либо нет. Проверяй эндпоинты, где пользователь влияет на разметку, и помни, что `Process.Start` не возвращает вывод.

## Связь с другими уроками

Этот урок продолжает ветку инъекций по движкам. Razor стоит рядом с Thymeleaf (Java), Smarty (PHP) и Pug/EJS (Node) — все они исполняют код шаблона, но в своём языке. Различие в том, что Razor компилирует шаблон в C#-класс и исполняет его в процессе приложения, поэтому доступ к платформе .NET полный. Дальше по ветке — разбор десериализации, где исполнение кода идёт уже не через шаблон, а через цепочки объектов.
