CAPTCHA и anti-automation — это барьеры, которые приложение ставит перед автоматизированными атаками: брутфорсом, спамом, массовым созданием аккаунтов. Задача тестировщика — понять, **защищает ли CAPTCHA реально** или это формальность, которую обходят за минуты. В большинстве случаев защита слабее, чем кажется: сервер не проверяет ответ, проверка привязана к клиенту, токен переиспользуется, а сама CAPTCHA решается дешёвыми сервисами.

## Три уровня защиты

Различайте, что именно проверяет приложение:

1. **Клиентская** — JS/HTML-проверка, которую можно обойти, отключив JS или отправив запрос напрямую.
2. **Серверная, но отключаемая** — параметр вроде `captcha=skip`, `is_human=true`, debug-флаг.
3. **Серверная с валидацией** — сервер проверяет токен/ответ у провайдера (reCAPTCHA/hCaptcha).

Первые два уровня — почти всегда обходятся. Третий требует либо слабостей в интеграции, либо решения CAPTCHA.

## Обход 1: проверка только на клиенте

Если CAPTCHA проверяется в JS, а сервер не валидирует — просто отправьте запрос напрямую.

```bash
# смотрим, что уходит при отправке формы
# если в запросе нет captcha-токена, а сервер принимает -> защиты нет
curl -s -X POST https://t/register -d 'user=bot1&pass=Passw0rd!'
# {"ok":true}  -> сервер не требует captcha
```

## Обход 2: параметры-переключатели

Ищите параметры, которые «выключают» проверку: `captcha=`, `g-recaptcha-response=`, `is_human`, `bypass`, `debug`, `test`.

```bash
# пустой/поддельный ответ reCAPTCHA
curl -s -X POST https://t/register -d 'user=bot&pass=x&g-recaptcha-response='
# пустая строка иногда проходит, если сервер не проверяет
curl -s -X POST https://t/register -d 'user=bot&pass=x&captcha=1&is_human=true'
```

## Обход 3: переиспользование токена

CAPTCHA-токен должен быть одноразовым и привязанным к сессии/действию. Если его можно использовать многократно — защита сломана: решаем один раз, используем N раз.

```bash
# 1. получаем валидный токен (решаем капчу руками один раз)
TOKEN='03AGdBq26...'
# 2. используем его в цикле
for i in $(seq 1 100); do
  curl -s -X POST https://t/register -d "user=bot$i&pass=x&g-recaptcha-response=$TOKEN" \
    -o /dev/null -w "%{http_code}\n"
done
# если все 200 -> токен не одноразовый
```

## Обход 4: отсутствие привязки к действию

Токен, полученный для одного действия (например, логина), может приниматься для другого (регистрации, сброса пароля). Проверяйте кросс-действие.

```bash
# токен с логина пробуем на регистрации
curl -s -X POST https://t/register -d "user=x&pass=y&g-recaptcha-response=$LOGIN_TOKEN"
```

## Обход 5: решение CAPTCHA автоматически

Если серверная проверка крепкая, остаётся решение. Дешёвые сервисы (2captcha, anti-captcha) решают reCAPTCHA/hCaptcha за копейки; OCR решает простые картинки; аудио-челлендж reCAPTCHA распознаётся автоматически. Это не «взлом», а экономический обход: если стоимость решения ниже выгоды, защита неэффективна.

```bash
# пример вызова сервиса решения (псевдо)
# 1. отправляем sitekey + pageurl
# 2. получаем решение
# 3. подставляем в g-recaptcha-response
```

## Обход 6: отсутствие rate-limiting

Часто CAPTCHA — единственный барьер, и если её обойти, а rate-limiting нет, брутфорс проходит на полной скорости. Проверяйте: считается ли CAPTCHA, блокируется ли IP, есть ли задержки.

```bash
# проверяем отсутствие rate-limit
for i in $(seq 1 50); do
  curl -s -o /dev/null -w "%{http_code} " -X POST https://t/login -d 'u=admin&p=x'
done; echo
# если 50 попыток прошли без 429/блокировки -> rate-limit нет
```

## Разобранный пример: обход регистрации

```bash
# 1. форма требует captcha
$ curl -s -X POST https://t/register -d 'user=bot&pass=x'
{"error":"captcha required"}

# 2. пробуем пустой ответ
$ curl -s -X POST https://t/register -d 'user=bot&pass=x&g-recaptcha-response='
{"ok":true,"id":1337}          # сервер не валидирует ответ -> обход

# 3. массово создаём аккаунты
$ for i in $(seq 1 200); do
    curl -s -X POST https://t/register -d "user=bot$i&pass=x&g-recaptcha-response=" -o /dev/null -w "$i:%{http_code} "
  done; echo
```

Артефакт — 200 созданных аккаунтов, доказательство отсутствия anti-automation.

## Инструменты

```bash
# массовая отправка с cookie-jar и параллелизмом
ffuf -w users.txt -u https://t/register -X POST \

# проверка наличия captcha в ответе
curl -s https://t/register | grep -ioE 'recaptcha|hcaptcha|turnstile|g-recaptcha'
```

## Крайние случаи и подводные камни

- **CAPTCHA только на логине.** Регистрация/сброс пароля могут быть без неё — ищите слабое звено.
- **Токен без привязки к IP/сессии.** Можно решать с одного IP и использовать с другого.
- **Отключение в мобильном API.** Часто CAPTCHA есть в веб-форме, но нет в API — используйте API.
- **Кэш.** Ответ с валидной CAPTCHA может кэшироваться.
- **Резервный канал.** Аудио/текстовая версия CAPTCHA часто проще.
- **Этичность.** Массовое создание аккаунтов/спам — деструктивно; согласуйте с заказчиком и ограничьтесь доказательством (несколько запросов), а не тысячами.

## Что делать дальше / решение

1. **Определите уровень защиты** — клиентская, отключаемая, серверная.
2. **Проверьте параметры-переключатели** — пустой/поддельный ответ.
3. **Проверьте одноразовость** — используйте токен несколько раз.
4. **Проверьте привязку** — к действию, сессии, IP.
5. **Проверьте rate-limit** — без CAPTCHA остаётся ли барьер.
6. **Оцените экономику** — решается ли CAPTCHA автоматически.
7. **Подтвердите** минимальным PoC (несколько успешных запросов).

## Справочная таблица

| Уровень | Признак | Обход |
|---------|---------|-------|
| клиентская | проверка в JS | прямой запрос |
| отключаемая | `captcha=`, `is_human=` | подстановка параметра |
| серверная | валидация у провайдера | решение/утечка токена |
| одноразовость | токен в цикле | переиспользование |
| привязка | токен с другого действия | кросс-использование |
| rate-limit | нет блокировки | брутфорс |

## Глубже: как интегрируют CAPTCHA и где ошибки

Понимание типовой интеграции помогает находить слабости. Обычно поток такой: клиент загружает виджет, виджет выдаёт токен, форма отправляет токен на сервер, сервер проверяет его у провайдера (`siteverify`) и получает `success: true/false`. Ошибки возникают в каждом звене.

Первая ошибка — **сервер не проверяет `success`**. Иногда код вызывает `siteverify`, но игнорирует результат, либо проверяет только наличие поля токена. Вторая — **не проверяется `hostname`/`action`** в ответе провайдера: токен, полученный для одного сайта/действия, принимается для другого. Третья — **секрет провайдера захардкожен и утёк** (в JS, в репозитории), что позволяет подделывать проверку. Четвёртая — **таймаут/ошибка провайдера трактуется как успех** (fail-open): если `siteverify` недоступен, сервер пропускает запрос.

```bash
# проверяем fail-open: временно блокируем запрос к провайдеру? (в лаборатории)
# если при недоступности siteverify регистрация проходит -> fail-open

# проверяем hostname/action в ответе провайдера (должны совпадать)
# если сервер их не сверяет, токен с другого сайта/действия пройдёт
```

## Глубже: CAPTCHA vs альтернативные защиты

Иногда CAPTCHA — не единственный барьер, и это важно для оценки. Приложение может использовать: **proof-of-work** (клиент решает вычислительную задачу), **device fingerprinting**, **behavioral analysis** (движения мыши, тайминги), **email/SMS-верификацию**, **rate-limiting** по IP/аккаунту, **honeypot-поля**. Каждая из этих защит имеет свои обходы: proof-of-work решается автоматически (это и подразумевается), fingerprinting обходится через антидетект-браузер, behavioral — через эмуляцию человека, honeypot — если знать имя поля (скрытое поле, которое бот заполняет, а человек нет).

```bash
# honeypot: скрытое поле, которое нельзя заполнять
# смотрим HTML формы
curl -s https://t/register | grep -iE 'type="hidden"|display:none|style='
# заполнение скрытого поля -> пометка "бот"
```

Практический вывод: если CAPTCHA обходится, проверьте, не держится ли защита на чём-то ещё. Часто «обход CAPTCHA» не даёт результата именно потому, что реальный барьер — rate-limiting или device-проверка, а CAPTCHA была декорацией.

## Глубже: этика и границы теста

CAPTCHA защищает от автоматизации, и её обход напрямую связан с массовыми действиями: спам, создание аккаунтов, брутфорс. Такие действия могут быть деструктивными (нагрузка на сервис, нарушение ToS, реальный вред). В рамках пентеста нужно: согласовать объём (сколько запросов), ограничиться минимальным доказательством (несколько успешных запросов вместо тысяч), не использовать украденные аккаунты и не рассылать спам. Артефактом служит факт обхода (например, 3-5 успешных регистраций), а не массовый эффект. Это и этично, и достаточно для отчёта.

## Итог и приоритизация

Наиболее критичен обход, приводящий к массовой автоматизации защищённого действия (регистрация, сброс пароля, брутфорс) — это высокий уровень. Если CAPTCHA проверяется только на клиенте или принимает пустой ответ — критично, потому что защита полностью отсутствует. Переиспользуемый токен — высокий уровень. Fail-open при недоступности провайдера — средний/высокий. Отсутствие rate-limiting в дополнение к CAPTCHA — усиливает находку. И всегда фиксируйте точный артефакт: сколько запросов прошло, что именно вы получили.

## Быстрая шпаргалка по проверкам

Ниже — компактный порядок действий, который покрывает большинство реальных внедрений CAPTCHA. Начните с определения уровня защиты: посмотрите, есть ли в HTML виджет (`g-recaptcha`, `hcaptcha`, `turnstile`), и уходит ли токен в запросе. Затем отправьте форму без токена и с пустым токеном — часто этого достаточно. Далее проверьте одноразовость: получите один валидный токен и отправьте его несколько раз. Проверьте кросс-действие: токен с логина на регистрации. Проверьте rate-limiting: серия запросов без блокировки. И, наконец, оцените, решается ли CAPTCHA автоматически — если да, экономического барьера нет. Каждый шаг — одна команда `curl` и наблюдение за кодом ответа. Такой цикл занимает минуты и даёт исчерпывающую картину защиты.
