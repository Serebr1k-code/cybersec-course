## Вопрос, с которого всё начинается

В прошлом уроке мы обошли вход в MongoDB, потому что знали: сервер работает с Mongo. А как узнать это на новом объекте? NoSQL — не одна база, а целое семейство: MongoDB, Redis, Elasticsearch, CouchDB, Memcached, Neo4j. У каждой свой язык запросов и свои пути к RCE. Спутаешь — будешь писать `$where` в Redis и ждать чуда.

В этом уроке мы просканируем наш `shop.local`, определим, какие хранилища вообще рядом, и научимся выбирать вектор **до** того, как строить payload.

## Наш пример

Мы в той же сети, что и `shop.local`. Пробегаем порты, характерные для хранилищ:

```bash
$ nmap -sV -p 27017,6379,9200,5984,9042,11211,7474,8086 shop.local
PORT      STATE SERVICE      VERSION
27017/tcp open  mongodb      MongoDB 6.0.5
6379/tcp  open  redis        Redis key-value store 7.0.11
9200/tcp  open  http         Elasticsearch 8.7.1
```

Три сервиса. Прежде чем что-то делать, надо понять, что мы вообще нашли и какой у каждого вход.

## Шаг 1: фингерпринт — что за хранилище

`nmap -sV` уже назвал сервисы по баннеру. Но иногда порт нестандартный, и `-sV` ошибается. Тогда пробуем откликнуться самим протоколом:

```bash
$ curl -s http://shop.local:9200/
{
  "name" : "es-node-1",
  "cluster_name" : "shop-cluster",
  "version" : { "number" : "8.7.1" }
}
```

Elasticsearch отвечает HTTP/JSON — это его выдаёт сразу. У Redis свой текстовый протокол:

```bash
$ redis-cli -h shop.local -p 6379 PING
PONG
```

`PONG` на `PING` — безошибочный признак Redis. А MongoDB понимаешь по ошибке, если обратиться к ней по HTTP:

```bash
$ curl -s http://shop.local:28017/
It looks like you are trying to access MongoDB over HTTP on the native driver port.
```

Запомни маркеры: `PONG` — Redis; `cluster_name`/`You know, for search` — Elasticsearch; `{"couchdb":"Welcome"}` — CouchDB; `neo4j` в HTML — Neo4j.

## Шаг 2: у каждого хранилища свой вектор

Главный вывод урока: **сначала тип хранилища, потом вектор**. От типа зависит, что вообще применимо:

| Хранилище | Порт | Анонимно? | Инъекция | До RCE |
|-----------|------|:---------:|----------|:------:|
| MongoDB | 27017 | исторически да | `$ne`/`$gt`/`$regex`/`$where` | старые версии |
| Redis | 6379 | да (без `requirepass`) | CRLF в командах | **да** (запись файла) |
| Elasticsearch | 9200 | да (без security) | painless-скрипты | старые версии |
| CouchDB | 5984 | **admin party** | JSON-селекторы | через `_config` |
| Memcached | 11211 | **всегда** | — | нет |
| Neo4j | 7474 | нет | Cypher | через APOC |

Видно закономерность: **Redis — король RCE** (пишет файлы на диск), **MongoDB — король инъекции** в приложение, а Elasticsearch/CouchDB чаще ломаются просто как «открытый сервис».

Отдельно стоит Memcached: аутентификации у него нет **вообще**, но RCE через него не получить. Зато из кеша утекают сессии и токены, а иногда его используют для отравления кеша приложения (подмена значения, которое приложение потом доверчиво читает).

## Шаг 3: анонимный доступ или инъекция?

Это два **разных** сценария, и путать их — главная ошибка новичка.

**Открытый сервис (network-facing).** Порт доступен, аутентификации нет — мы подключаемся клиентом и читаем данные напрямую. У нас так:

```bash
$ redis-cli -h shop.local -p 6379 KEYS '*'
1) "session:9f2a"
2) "cart:1001"
3) "admin:reset_token"
```

Токен сброса пароля администратора, лежащий в открытом Redis, — это уже critical сам по себе.

**Инъекция (app-facing).** Порт закрыт файрволом, но приложение само передаёт в базу наш ввод — тогда подставляем оператор в параметр. На багбаунти чаще встречается именно это, в CTF и внутреннем пентесте — первое. Проверяй оба.

На практике сценарии выглядят так:

```bash
# network-facing: порт открыт — подключаемся напрямую
$ mongosh "mongodb://shop.local:27017" --eval 'db.getMongo().getDBNames()'
[ 'admin', 'shop', 'users' ]

# app-facing: порт закрыт — наш ввод идёт через приложение
$ curl -s -X POST https://shop.local/api/login -H 'Content-Type: application/json' \
>   -d '{"username":"admin","password":{"$ne":"x"}}'
{"ok":true,"token":"eyJ..."}
```

Обрати внимание: в первом случае мы вообще не строим payload — просто читаем то, что не защищено. Во втором — вся работа в том, чтобы подобрать оператор, который приложение передаст в базу без проверки типа.

## Шаг 4: универсальный алгоритм триажа

Порядок не зависит от типа базы:

```bash
# 1. Скан портов хранилищ
nmap -sV -p 27017,6379,9200,5984,9042,11211,7474,8086 shop.local

# 2. Для каждого открытого порта — анонимный пробник
redis-cli -h shop.local PING                     # PONG -> доступен
curl -s http://shop.local:9200/_cat/indices?v    # список индексов
curl -s http://shop.local:5984/_all_dbs          # список баз CouchDB

# 3. Если порты закрыты — ищем инъекцию в приложении
curl -s -X POST https://shop.local/api/login -H 'Content-Type: application/json' \
  -d '{"username":"admin","password":{"$ne":"x"}}'

# 4. Фиксируем доказательство: одна строка данных, которой не должно быть видно
```

Шаг 4 обязателен: «порт открыт» — это ещё не находка, пока ты не показал строку данных из базы.

## Почему тип хранилища важнее payload'а

Соблазн новичка — выучить один «универсальный» payload и подставлять его везде. С NoSQL это не работает, и вот почему. SQL — стандартизированный язык, поэтому `' OR 1=1--` переносится между MySQL, PostgreSQL и MSSQL с минимальными правками. NoSQL — это не язык, а набор несовместимых моделей: у Mongo документы и операторы, у Redis — текстовые команды в key-value, у Elasticsearch — JSON-запросы к индексам, у Cassandra — CQL, у Neo4j — Cypher по графу. У них нет общего синтаксиса, зато есть общая идея — «сначала пойми, что это, потом выбирай инструмент».

Практическое следствие: время, потраченное на фингерпринт, окупается многократно. Одна команда `nmap -sV` или один `PING` по протоколу отделяет семейство хранилищ друг от друга. Если ты по ошибке начнёшь слать `$where` в Redis, ты не получишь ни ошибки, ни результата — просто ничего. А `PONG` на `PING` за секунду скажет, что перед тобой Redis, и весь класс атак сменится: вместо инъекции в приложение ты пойдёшь читать ключи напрямую.

Есть и второй уровень различения — внутри одного типа. MongoDB версии 4.4 и 4.2 отличаются принципиально: `db.eval` удалён, поэтому старые RCE-цепочки не сработают. Elasticsearch до и после включения security — это два разных мира по доступности. Поэтому фиксируй **версию** вместе с типом; без неё PoC подобрать невозможно.

И, наконец, третий уровень — сценарий. «Порт открыт» и «приложение передаёт наш ввод в базу» — это разные находки с разной доказательной базой. В первом случае ты просто читаешь незащищённые данные клиентом. Во втором ты строишь payload и доказываешь, что приложение передало его без проверки типа. Смешать их — значит либо преувеличить находку, либо недооценить. Держи эти два сценария раздельно до самого отчёта.

И держи в голове, что «открытый порт» — это ещё не доказательство. Находка подтверждается только тогда, когда ты показал конкретную строку данных, которой не должно быть видно снаружи: ключ сессии, токен, пароль, чужой профиль. Сам факт `PONG` или ответа `200` на `_cat/indices` — это лишь поверхность. Разница между «сервис доступен» и «данные утекли» определяет и серьёзность, и то, как ты опишешь находку.

## Что мы теперь знаем

- NoSQL — семейство с разными моделями угроз; тип базы определяет вектор.
- Фингерпринт делают по баннеру (`nmap -sV`) и по отклику протокола (`PONG`, JSON `cluster_name`).
- Есть два сценария: открытый сервис (прямой доступ) и инъекция (ввод через приложение) — их не путают.
- Redis — лучший путь к RCE (запись файла), MongoDB — к обходу аутентификации.
- Триаж: скан → анонимный пробник → инъекция → доказательство строкой данных.

## На что смотреть дальше

- **Версия решает.** `db.eval` удалён с MongoDB 4.2, Groovy-скрипты в Elasticsearch — с 1.4.2+; без версии PoC не подобрать.
- **Дефолтные креды.** Cassandra `cassandra:cassandra`, Neo4j `neo4j:neo4j` — их меняют не всегда; проверяй перед брутом.
- **`Content-Type` важен.** Операторная инъекция в MongoDB проходит только при парсинге тела как JSON; для формы нужен `user[$ne]=x`.
- **Не ломай прод.** `redis-cli CONFIG SET` меняет живой сервер — на боевом согласуй, прежде чем перезаписывать `dbfilename`.

## Куда дальше

Карта у нас есть. Дальше — четыре практических разбора: `db-mongodb` (операторы, дамп, `mapReduce`), `db-redis` (CONFIG+SAVE, ключи, модули), `db-elasticsearch` (индексы, painless, Kibana) и `db-other` (CouchDB, Cassandra, Memcached, Neo4j). Начинай с того хранилища, которое показал фингерпринт; если портов не видно — работай по MongoDB-диалекту, операторная инъекция в JSON встречается чаще всего.

## Где пригодится

- **CTF (Web):** NoSQL-задачи сводятся к оператору `$ne` или открытому 27017/6379 — тип надо определять за секунды.
- **Bug bounty:** открытые хранилища и NoSQL-инъекции в API — частый critical; умение отличить одно от другого экономит время отчёта.
- **Пентест:** внешний скан находит десятки портов; быстрый триаж решает, какой инструмент взять.
- **Работа (AppSec):** понимание, чем опасно каждое хранилище, ложится в чек-лист ревью и hardening (auth, bind на localhost, файрвол).
