## Задача

Прежде чем что-то ломать, нужно увидеть **всё**, что отдаёт цель. Поверхность атаки — это не только главная страница: скрытые пути, файлы конфигурации, спецификации API, поддомены. Чем шире карта, тем больше дверей.

Разберём один домен и соберём его поверхность по шагам.

## Наш пример: домен target.local

Дан только домен. Строим конвейер: поддомены → живые хосты → пути → конфиги → API. Начинаем с дешёвого (пассивного) и идём к дорогому.

## Шаг 1: поддомены — пассивно

Поддомены часто обслуживают отдельные приложения (`admin`, `api`, `staging`). Собираем пассивно, без запросов к цели:

```bash
$ subfinder -d target.local -silent | tee subs.txt
api.target.local
staging.target.local
shop.target.local
```

Три хоста. Пассивный сбор дешевле и незаметнее активного перебора DNS.

## Шаг 2: живые хосты и стек

Прогоняем список через `httpx`, чтобы оставить только живые и получить «паспорт»:

```bash
$ httpx -l subs.txt -sc -title -td -silent
https://shop.target.local [200] [Shop] [nginx/1.18.0, PHP/7.4]
https://api.target.local [401] [Unauthorized] [Express]
https://staging.target.local [200] [Staging] [next.js/13.4]
```

Читаем: `shop` — nginx+PHP, `api` требует авторизацию, `staging` — Next.js 13.4. Конкретные версии — кандидаты на известные CVE.

## Шаг 3: скрытые пути

Теперь активный перебор путей по каждому хосту:

```bash
$ ffuf -w /usr/share/seclists/Discovery/Web-Content/raft-medium-directories.txt \
       -u https://shop.target.local/FUZZ -mc 200,301,302,401,403 -t 40
.git/HEAD               [Status: 200, Size: 23]
.env                    [Status: 200, Size: 214]
admin                   [Status: 301, Size: 178]
backup                  [Status: 403, Size: 153]
```

`.git`, `.env`, `admin` — три важные находки. Проверяем `.env`:

```bash
$ curl -s https://shop.target.local/.env
APP_ENV=production
DB_USER=shop
DB_PASS=Sup3rS3cret
```

Пароль БД в открытом виде. Это ещё не уязвимость приложения, но уже серьёзная находка.

## Шаг 4: конфиги и метаданные

Кроме `.env` и `.git`, ищем то, что разработчики забывают закрыть:

```bash
$ for p in robots.txt sitemap.xml .well-known/security.txt phpinfo.php; do
    echo "== $p"; curl -s -o /dev/null -w '%{http_code}\n' https://shop.target.local/$p; done
== robots.txt 200
== sitemap.xml 404
== .well-known/security.txt 404
== phpinfo.php 200
```

`robots.txt` — легальная карта сайта: в `Disallow` часто спрятаны админ-пути. `phpinfo.php` раскрывает конфигурацию и пути. Оба читаем.

## Шаг 5: API-спеки

Современные приложения документируют API — и это подарок:

```bash
$ for p in swagger.json openapi.json api-docs /graphql; do
    echo "== $p"; curl -s -o /dev/null -w '%{http_code}\n' https://api.target.local/$p; done
== swagger.json 200
== openapi.json 200
== api-docs 404
== /graphql 400
```

`openapi.json` отдаёт все пути, параметры и схемы. Из него сразу видно эндпоинты, которых нет в интерфейсе (например `/api/v1/admin/users`).

## Шаг 6: фиксируем поверхность

Сводим всё в одну карту:

| Хост | Пути/файлы | Что даёт |
|------|-----------|----------|
| shop | `.git`, `.env`, `admin`, `phpinfo` | исходники, креды БД |
| api | `openapi.json`, `/graphql` | карта API |
| staging | Next.js 13.4 | версия под CVE |

Такая карта — вход в следующий этап: контроль доступа и инъекции.

## Если не сработало

- **Wildcard DNS** — `*.target.local` резолвится в один IP; фильтруй по содержимому.
- **«Мягкие 404»** — сервер отдаёт 200 на всё; фильтруй ffuf по размеру (`-fs`).
- **SPA** — перебор каталогов бесполезен; крауль JS (`katana -jc`).
- **Нет поддоменов** — проверь сертификаты (`crt.sh`), историю (`waybackurls`).

## Что мы теперь знаем

- Поверхность строится конвейером: поддомены → хосты → пути → конфиги → API.
- Порядок задаётся стоимостью: пассивное дешевле активного.
- `.git`, `.env`, `phpinfo`, `openapi.json`, `robots.txt` — классические утечки.
- Версии фреймворков — кандидаты на известные CVE.

## Частые вопросы

**Пассивная разведка — это законно?** Да, если ты не шлёшь запросы цели: данные из публичных источников (DNS, сертификаты, архивы). Активная разведка — уже взаимодействие с целью, её согласуют в scope.

**Зачем нужны поддомены, если есть основной домен?** Поддомены часто обслуживают **отдельные** приложения (`admin`, `staging`, `api`) с другим кодом и своими багами. `staging` особенно интересен — там debug и слабые настройки.

**Что делать, если фаззинг даёт тысячи 200?** Это «мягкие 404» или wildcard. Фильтруй по размеру ответа (`-fs`) или по словам (`-fw`), а не по коду. Иначе результаты бесполезны.

**Спецификация API — это утечка?** Открытый `openapi.json`/`swagger` — не критичная утечка сам по себе, но он даёт карту всех эндпоинтов, включая админские. Это резко ускоряет атаку.

**Как не повторять работу?** Веди список уже проверенных хостов:портов и словарей. Повторный фаззинг тем же словарём — шум без новой информации.

## Ещё один сценарий: исторические URL и параметры

Архивы веб-страниц отдают забытые эндпоинты, которых уже нет в коде, но которые могут работать:

```bash
$ gau target.local | grep -E '\.(php|json|xml)$' | sort -u | head
https://target.local/api/v0/users.php
https://target.local/debug/config.json
https://target.local/export.php
```

Проверяем один:

```bash
$ curl -s https://target.local/api/v0/users.php
[{"id":1,"user":"admin","pass_hash":"..."}]
```

Старый API без авторизации — типичная находка из архивов. Так же ищем **скрытые параметры**:

```bash
$ ffuf -w params.txt -u 'https://target.local/api/products?FUZZ=1' -mc all -fs 1234
debug                   [Status: 200, Size: 2100]
```

Параметр `debug` вернул другой размер — он существует и меняет поведение.

## На что смотреть дальше

- **Архивы.** `gau`, `waybackurls` — забытые эндпоинты и параметры.
- **Параметры.** `arjun`, `ffuf ?FUZZ=1` — необъявленные параметры.
- **Версии.** `/v0`, `/v1`, `/internal`, `/beta` — старые API.
- **Конфиги.** `.env`, `.git`, `config.json`, `*.bak`, `*.sql`.
- **Виртуальные хосты.** `ffuf -H 'Host: FUZZ.target.local'`.
- **Фиксация.** Каждую находку подтверждай вручную (`curl`), прежде чем писать в отчёт.

Мы собрали поверхность — теперь идём в классы уязвимостей (`web-recon-attack-entry`), а затем к SSRF (`web-ssrf`). А пока главное запомни: **сначала увидь всё, что отдаёт цель, — карта важнее первого payload.**
