## Вопрос, с которого всё начинается

Каждый HTTP-запрос содержит заголовок `Host` — «какому сайту адресован запрос». Его присылает клиент, то есть **ты**. Если приложение доверяет этому заголовку и подставляет его, например, в ссылку сброса пароля, — можно заставить жертву перейти на твой домен.

Сегодня мы возьмём сброс пароля и покажем, как заголовок Host превращается в захват аккаунта.

## Наш пример

`shop.local` имеет форму «забыли пароль». Отправляем свой email и смотрим, что происходит:

```http
POST /forgot HTTP/1.1
Host: shop.local
Content-Type: application/x-www-form-urlencoded

email=me@shop.local
--
HTTP/1.1 200 OK
{"ok":true,"message":"reset link sent"}
```

Письмо (в тестовом окружении смотрим в логах почтового сервиса) содержит ссылку:

```text
https://shop.local/reset?token=abc123
```

Домен в ссылке — `shop.local`. Но откуда сервер его взял? Скорее всего, из заголовка `Host`. Проверим.

## Шаг 1: Host injection

Подменим `Host` на свой домен и посмотрим, что попадёт в письмо:

```bash
$ curl -s -X POST https://shop.local/forgot \
>   -H 'Host: evil.local' -d 'email=me@shop.local'
{"ok":true}
```

В логах почтовика ссылка теперь такая:

```text
https://evil.local/reset?token=abc123
```

Сервер доверился `Host`. Если жертва получит письмо с такой ссылкой и кликнет — токен сброса уйдёт на `evil.local`, где мы его прочитаем. Это **password reset poisoning** — отравление сброса пароля. Осталось заставить жертву запросить сброс так, чтобы `Host` был наш, — или найти, где приложение само берёт Host из запроса пользователя (например, при смене email).

## Шаг 2: X-Forwarded-Host

Часто приложение за прокси, и настоящий домен оно берёт не из `Host`, а из `X-Forwarded-Host`. Пробуем:

```bash
$ curl -s -X POST https://shop.local/forgot \
>   -H 'X-Forwarded-Host: evil.local' -d 'email=me@shop.local'
```

Ссылка снова указывает на `evil.local`. Другие похожие заголовки: `X-Forwarded-Server`, `X-Host`, `X-Forwarded-Server`. Все они приходят от клиента, и приложение не должно им доверять — но часто доверяет.

## Шаг 3: роутинг и vhost

`Host` влияет не только на ссылки. Многие приложения используют его для **роутинга** — выбора сайта на одном IP (виртуальные хосты). Перебор значений `Host` может открыть скрытые панели:

```bash
$ for h in admin.shop.local internal.shop.local localhost; do
>   printf '%-24s ' $h; curl -s -o /dev/null -w '%{http_code}\n' https://shop.local/ -H "Host: $h"
> done
admin.shop.local        200
internal.shop.local     403
localhost               200
```

`admin.shop.local` отвечает `200` — возможно, это внутренняя панель, доступная только «с правильным» Host. Так же иногда обходят правила WAF: правило привязано к одному домену, а по другому — не применяется.

## Шаг 4: отравление кэша через Host

Если кэш (CDN) формирует ключ без учёта `Host`, а приложение подставляет Host в HTML — можно «отравить» страницу для всех. Схема: отправляем запрос с `Host: evil.local`, CDN кэширует ответ, и все следующие посетители получают страницу со ссылками на `evil.local`. Проверяется наличием заголовков кэша:

```bash
$ curl -sI https://shop.local/ -H 'Host: evil.local' | grep -i 'x-cache\|age'
X-Cache: HIT
Age: 12
```

`X-Cache: HIT` — ответ закэширован. Если он содержит подставленный Host, это cache poisoning. Детали — в `web-cache-poisoning`.

## Полный прогон от начала до конца

Запрашиваем сброс с обычным Host — ссылка на `shop.local`. Меняем Host на `evil.local` — ссылка меняется. Пробуем `X-Forwarded-Host` — тоже. Перебираем Host для роутинга — находим `admin.shop.local`. Проверяем кэш — `HIT` с подставленным хостом. Четыре разных последствия одного доверия к заголовку. В отчёт идёт письмо/ссылка и запрос, который её сформировал.

## Инструменты

Основное — **Burp Repeater**: правишь `Host`/`X-Forwarded-Host` и смотришь, что меняется в ответе и в письме. Для перебора виртуальных хостов — **Intruder** со словарём (`admin`, `internal`, `dev`, `staging`, `localhost`, `127.0.0.1`) в поле `Host`. Для поиска заголовков, которым доверяет приложение, полезен список: `X-Forwarded-Host`, `X-Forwarded-Server`, `X-Host`, `X-Forwarded-For`, `Forwarded`. Смотреть, что попадёт в письмо, можно в логах тестового SMTP (MailHog, `smtp4dev`) — там видно ссылку целиком. И держи под рукой `curl -I` для проверки кэш-заголовков (`X-Cache`, `Age`, `Vary`).

## Если не сработало

Если Host не влияет на ссылку, проверь, где приложение **действительно** берёт домен: возможно, из конфига (тогда бага нет) или из заголовка, который ты не пробовал. Перебери весь список X-Forwarded-*. Иногда ссылка строится на клиенте — тогда смотри JS. Если Host не даёт скрытых vhost, попробуй его для обхода WAF: правила часто привязаны к одному имени. И проверь, влияет ли Host на **кэш-ключ**: если да, poisoning через него не сработает; если нет — почти наверняка сработает.

## Где это встречается в реальности

Заголовок Host влияет на больше, чем кажется. Сброс пароля и подтверждение email (ссылки в письмах). Вебхуки, которые приложение отправляет по «своему» домену. Роутинг к внутренним панелям. Формирование абсолютных URL в API-ответах. Ссылки в письмах приглашения. И кэш, если Host не входит в ключ. Поэтому, увидев любую «сгенерированную ссылку», сразу спроси: откуда взят домен? Если из запроса — это потенциальный баг.

## Как оформить находку

Покажи цепочку «запрос с подменённым Host → письмо/ответ со ссылкой на чужой домен». Для vhost — таблицу «Host → код ответа». Для кэша — `X-Cache: HIT` с подставленным хостом и обычный запрос, отдающий отраву. Доказательство — конкретный артефакт (письмо, страница), а не предположение.

## Частые вопросы

**«Куда вообще попадает Host?»** В абсолютные ссылки (письма, вебхуки, API-ответы), в роутинг к vhost и в кэш-ключ. Проверяй все три.

**«Что если приложение берёт домен из конфига?»** Тогда poisoning не сработает — это не баг. Но проверь `X-Forwarded-Host` и другие заголовки: домен может браться из них.

## Что мы теперь знаем

- `Host` приходит от клиента и не должен влиять на ссылки и логику.
- Подмена `Host`/`X-Forwarded-Host` отравляет ссылки сброса пароля.
- Host влияет на роутинг и виртуальные хосты — открывает скрытые панели.
- Host может отравить кэш для всех пользователей.
- Доказательство — письмо со ссылкой на чужой домен.
- Host — это ввод пользователя, ему нельзя доверять.
- Домены и ссылки должны браться из конфига, а не из запроса.
- Любая «сгенерированная ссылка» — повод спросить, откуда взят домен.

## На что смотреть дальше

- Ищи, где приложение строит абсолютные ссылки (сброс пароля, подтверждение email, вебхуки).
- Пробуй `Host`, `X-Forwarded-Host` и их варианты.
- Перебирай Host для поиска vhost и обхода WAF.
- Проверяй, входит ли Host в кэш-ключ.
