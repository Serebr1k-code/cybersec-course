## Задача

В прошлом уроке мы увидели слои приложения. Теперь вопрос точнее: **как эти слои разговаривают друг с другом?** Клиент шлёт запросы не только к HTML-страницам, но и к API — а API говорит на своём «языке»: REST, GraphQL, SOAP, WebSocket. Каждый язык даёт свои классы багов.

Разберём один сайт и найдём его API-поверхности.

## Наш пример: магазин shop.local и его API

Мы уже знаем, что сайт на PHP. Заглянем в JS-бандл — там почти всегда зашиты адреса API, которые не видны в ссылках:

```bash
$ curl -s https://shop.local/static/app.js | grep -oE '"/api/[a-zA-Z0-9/_-]+"' | sort -u
"/api/v1/products"
"/api/v1/orders"
"/graphql"
"/api/v1/ws"
```

Четыре эндпоинта. `products` и `orders` — похоже, REST. `graphql` — отдельный язык. `ws` — намёк на WebSocket (живые обновления). Разберём по очереди.

## Шаг 1: REST — ресурсы и версии

**REST** — стиль API, где каждая сущность — это «ресурс» по URL (`/api/v1/products/42`), а действие задаёт HTTP-метод: `GET` читать, `POST` создать, `PUT`/`PATCH` изменить, `DELETE` удалить. Пробуем список товаров:

```bash
$ curl -s https://shop.local/api/v1/products | jq '.[0]'
{
  "id": 1,
  "name": "Чайник",
  "price": 1990,
  "cost": 900,
  "supplier_id": 4
}
```

Поле `cost` — внутренняя себестоимость, а `supplier_id` — ссылка на поставщика. API отдаёт наружу больше, чем показывает интерфейс. Это **избыточная выдача** (excessive data exposure) и готовый IDOR: попробуй `supplier_id: 5` — увидишь чужого поставщика.

## Шаг 2: GraphQL — один эндпоинт, вся схема

**GraphQL** — язык запросов, где клиент сам указывает, какие поля ему нужны, а сервер отдаёт их через один URL (`/graphql`). У GraphQL есть служебный запрос **интроспекции**: он возвращает описание всей схемы. Если он открыт — ты видишь все типы и поля:

```bash
$ curl -s https://shop.local/graphql -H 'Content-Type: application/json' \
  -d '{"query":"{__schema{types{name fields{name}}}}"}' | jq '.data.__schema.types[].name' | head
"User"
"Order"
"AdminPanel"
"PasswordReset"
```

Интроспекция открыта — мы получили карту API целиком, включая `AdminPanel` и `PasswordReset`, которых нет в UI. Дальше можно запрашивать поля точечно:

```bash
$ curl -s https://shop.local/graphql -H 'Content-Type: application/json' \
  -d '{"query":"{user(id:1){email role}}"}'
{"data":{"user":{"email":"admin@shop.local","role":"admin"}}}
```

Мы прочитали `role` пользователя. Если сервер не проверяет, кто спрашивает, — это BOLA прямо в GraphQL.

## Шаг 3: SOAP — если видишь XML

Иногда API старше и говорит на **SOAP**: это XML-конверт с методом внутри. Признак — эндпоинт вида `/ws/UserService?wsdl` и ответ в XML:

```bash
$ curl -s 'https://shop.local/api/v1/ws?wsdl' | head -5
<?xml version="1.0"?>
<definitions name="UserService" targetNamespace="http://shop.local/">
  <types><xsd:schema>...</xsd:schema></types>
```

Файл `.wsdl` — это «контракт» сервиса: он описывает все доступные методы. Его наличие — приглашение изучить, какие операции сервер выполняет (часто включая административные). WSDL ищут в первую очередь у SOAP-сервисов.

## Шаг 4: WebSocket — постоянный канал

**WebSocket** — протокол постоянного двустороннего соединения: клиент и сервер держат один открытый канал и шлют сообщения без новых HTTP-запросов. Проверяем рукопожатие:

```bash
$ curl -sI https://shop.local/api/v1/ws -H 'Connection: Upgrade' -H 'Upgrade: websocket'
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
```

`101 Switching Protocols` — канал открылся. Уязвимости WebSocket: сообщения часто не проверяют авторизацию (проверка была только при рукопожатии), а сервер может принимать «команды» от кого угодно. Дальше нужно смотреть формат сообщений — но это уже тема отдельного урока.

## Шаг 5: сводим к архитектуре

| Протокол | Точка входа | Типичный баг |
|----------|-------------|--------------|
| REST | `/api/v1/...` | IDOR, избыточная выдача |
| GraphQL | `/graphql` | открытая интроспекция, BOLA |
| SOAP | `?wsdl` | доступ к админ-методам |
| WebSocket | `/ws` | отсутствие авторизации сообщений |

Один JS-бандл выдал четыре поверхности, и у каждой — свой класс уязвимостей.

## Шаг 6: версии и документация — карта бесплатно

Любой протокол выдаёт себя заголовками и служебными путями. Соберём «паспорт» API одним запросом:

```bash
$ curl -s https://shop.local/graphql -H 'Content-Type: application/json' \
  -d '{"query":"{__schema{queryType{name}}}"}'
{"data":{"__schema":{"queryType":{"name":"Query"}}}}

$ curl -s https://shop.local/openapi.json | jq '.info, (.paths|keys)'
{"title":"Shop API","version":"1.4.0"}
["/api/v1/products","/api/v1/orders","/api/v1/admin/users"]
```

Файл `openapi.json` (он же Swagger) — машинная спецификация REST: все пути, параметры и схемы. В ней сразу виден `/api/v1/admin/users`, которого нет в интерфейсе. Версия `1.4.0` — зацепка для поиска известных уязвимостей API.

Правило простое: **если API документирует себя — читай документацию, а не угадывай.** Swagger, `openapi.json`, `redoc`, `graphql` (интроспекция), `?wsdl` — четыре двери к одной карте.

## Если не сработало

- **API не видно в JS** — проверь `/swagger`, `/api-docs`, `/openapi.json`, `/redoc`: это документирующие спеки REST.
- **GraphQL без интроспекции** — пробуй поля наугад и смотри подсказки ошибок; иногда `GET /graphql` с `?query=...` обходит фильтр.
- **WebSocket не отвечает** — попробуй `wss://` и другой путь (`/socket.io/`, `/ws/v2`).
- **Нужна авторизация** — передай cookie: `curl -b cookies.txt ...`; внутри аккаунта API отдаёт больше.

## Что мы теперь знаем

- API — это отдельная поверхность, её ищут в JS, а не в ссылках.
- REST ломается на IDOR и лишних полях; GraphQL — на интроспекции и BOLA; SOAP — на WSDL; WebSocket — на слабой авторизации.
- Документирующие эндпоинты (`swagger`, `openapi.json`, `wsdl`) дают карту API бесплатно.
- Каждый протокол — мост к следующему уроку ветви.

## Частые вопросы

**Зачем искать API в JS, а не просто фаззить?** Потому что SPA генерирует пути в браузере: их нет в HTML, и перебор каталогов их не найдёт. А в JS-бандле адреса API лежат открыто.

**GraphQL — это всегда один эндпоинт?** Обычно да (`/graphql`), и через него доступны все запросы. Поэтому так важен вопрос авторизации на уровне полей.

**Что делать, если интроспекция отключена?** Пробуй угадывать поля по ошибкам (GraphQL подсказывает похожие имена), читай клиентский код — там перечислены запросы.

**SOAP ещё жив?** В корпоративных и legacy-системах — да. Признак: `?wsdl` и XML-ответы. WSDL описывает все методы.

**WebSocket — отдельная уязвимость?** Не сам протокол, а логика: авторизация только при рукопожатии, а сообщения принимаются от кого угодно.

**Как отличить REST от GraphQL на практике?** REST: много URL-путей и HTTP-методы. GraphQL: один URL, всегда `POST`, тело — запрос с полями.

## Ещё один сценарий: REST-версии и устаревшие эндпоинты

API часто живут в нескольких версиях, и старая — слабее. Проверим:

```bash
$ for v in v1 v2 v3; do
    echo "== $v"; curl -s -o /dev/null -w '%{http_code}\n' https://shop.local/api/$v/products; done
== v1 200
== v2 200
== v3 404
```

`v1` всё ещё работает. Часто в старых версиях нет проверок, которые добавили в `v2`. Сравниваем ответы:

```bash
$ curl -s https://shop.local/api/v1/products/1 | jq keys
["id","name","price","cost","supplier_id","internal_notes"]
$ curl -s https://shop.local/api/v2/products/1 | jq keys
["id","name","price"]
```

`v1` отдаёт `cost` и `internal_notes`, которых нет в `v2`. Устаревшая версия — это «окно» в старую логику.

## На что смотреть дальше

- **Версии API.** `/v1`, `/v2`, `/beta`, `/internal` — старые версии слабее.
- **Методы.** Пробуй `PUT`/`DELETE`/`PATCH` там, где ожидался только `GET`.
- **Спецификации.** `swagger`, `openapi.json`, `graphql`, `?wsdl` — карта бесплатно.
- **Избыточные поля.** API отдаёт больше, чем UI — ищи `cost`, `role`, `internal`.
- **Массовое присваивание.** Пришли лишнее поле (`role`) и смотри, примет ли сервер.
- **WebSocket.** Проверь, проверяется ли авторизация на каждом сообщении, а не только при рукопожатии.
