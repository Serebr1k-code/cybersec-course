Race condition — это баг, возникающий, когда два запроса обрабатываются **одновременно** и логика (проверка → действие) выполняется не атомарно. Классика: одноразовый купон применяется дважды, баланс уходит в минус, лимит попыток не срабатывает. Обычные «параллельные» запросы (запустить два curl одновременно) ненадёжны из-за сетевого джиттера — поэтому используют **single-packet attack**: несколько запросов отправляются в одном TCP/HTTP-2-пакете, чтобы сервер получил их максимально одновременно.

## Теория: почему обычные параллельные запросы ненадёжны

Если просто запустить `N` запросов «параллельно», они приходят на сервер с разбросом в миллисекунды — окно гонки упускается. Для успешной гонки нужно, чтобы запросы пришли **в пределах одного окна обработки**. Решения:

- **HTTP/1.1 pipelining** — отправить все запросы одним write, задержав последний байт.
- **HTTP/2 single-packet** — один TCP-пакет с несколькими HTTP/2-фреймами (все запросы «в один момент»).
- **Turbo Intruder** (Burp) — реализует оба.

## Инструмент: Turbo Intruder (Burp)

Пример скрипта для single-packet атаки (HTTP/2):

```python
def queueRequests(target, wordlists):
    engine = RequestEngine(endpoint=target.endpoint,
                           concurrentConnections=1,
                           engine=Engine.BURP2)
    for i in range(20):
        engine.queue(target.req, gate='race1')
    engine.openGate('race1')   # все запросы уходят вместе

def handleResponse(req, interesting):
    table.add(req)
```

`gate` синхронизирует отправку: все запросы буферизуются и выстреливают одновременно.

## Разобранный пример: обход одноразового купона

Цель: `POST /apply-coupon` с `code=SAVE10`, каждый купон — одноразовый.

Шаг 1 — в Burp отправляем запрос в Turbo Intruder.
Шаг 2 — скрипт с `gate` и 20 запросами.
Шаг 3 — смотрим ответы: если несколько `200 applied` — купон применён многократно.

## Разобранный пример: превышение баланса

Цель: `POST /transfer` со проверкой «balance >= amount». Отправляем 20 одновременных переводов по сумме, равной балансу. Если проверка не атомарна — баланс уходит в минус, деньги «создаются».

## Разобранный пример: обход rate-limit

Цель: `POST /login` с лимитом 5 попыток. Отправляем 20 попыток одним пакетом — счётчик инкрементируется не атомарно, и лимит не срабатывает → перебор паролей.

## Что тестировать

- Одноразовые токены/купоны/промокоды.
- Балансы/лимиты/квоты.
- Инвайты/голоса/лайки (накрутка).
- Реферальные бонусы.
- Смена пароля/подтверждение (TOCTOU).
- Rate-limit / anti-brute.

## Вариации и детали

- **Лаборатория Burp** (PortSwigger) — «Race conditions» с эталонными примерами.
- **HTTP/2 vs HTTP/1.1** — single-packet работает по-разному; на H2 надёжнее.
- **Last-byte sync** — задержать последний байт последнего запроса, чтобы все пришли вместе.
- **Connection warming** — «прогреть» соединение, чтобы первый запрос не тормозил.
- **Много соединений** — если сервер балансирует по коннектам, single-connection даёт лучший результат.

## Инструменты

- **Burp Turbo Intruder** — основной инструмент.
- **`race-the-web`/`h2-race`** — скриптовые аналоги.
- **`curl --parallel`** — грубый вариант (ненадёжен).
- **`ffuf`** — не для гонок, только для параметров.

## Что дальше / decision

1. Есть одноразовое действие → тестируйте гонку.
2. Обычные параллельные запросы не сработали → single-packet (Turbo Intruder).
3. HTTP/2 доступен → используйте H2-движок.
4. Подтвердили многократное применение → зафиксируйте PoC (N запросов → N успехов).
5. Дальше — эскалация ущерба (деньги/токены/доступ).

## Разобранный пример: накрутка голосов

Цель: `POST /vote?id=42` с лимитом «1 голос на пользователя». Отправляем 20 запросов одним пакетом (Turbo Intruder с `gate`) — счётчик инкрементируется не атомарно, голоса накручиваются. Аналогично — лайки, подписки, реферальные бонусы.

## Как измерять успех

- Считайте, сколько запросов вернули «успех» — если >1 при одноразовом действии, гонка сработала.
- Для финансов — сравните баланс до/после.
- Для лимитов — проверьте, превышен ли лимит.
- Логируйте время ответов, чтобы понять, попали ли запросы в одно окно.

## Частые ошибки

- **Запускать «параллельно» через shell.** Джиттер убивает гонку.
- **Не использовать gate.** Без синхронизации запросы расходятся.
- **Забыть прогреть соединение.** Первый запрос искажает тайминг.
- **Считать гонку неэксплуатируемой после одной попытки.** Пробуйте больше, H2, single-connection.
- **Ломать прод.** Гонки меняют данные — только с согласия.

## Turbo Intruder: полный скрипт single-packet attack

Single-packet attack отправляет N запросов в одном TCP-пакете (или в одной HTTP/2-посылке), чтобы окно гонки было минимальным.

```python
# Turbo Intruder: single-packet attack по HTTP/2
def queueRequests(target, wordlists):
    engine = RequestEngine(endpoint=target.endpoint,
                           concurrentConnections=1,
                           engine=Engine.BURP2)
    # gate 'race1' удерживает все запросы до вызова openGate
    for i in range(20):
        engine.queue(target.req, gate='race1')
    engine.openGate('race1')

def handleResponse(req, interesting):
    table.add(req)
```

```python
# вариант по HTTP/1.1 (последний байт) — для старых серверов
def queueRequests(target, wordlists):
    engine = RequestEngine(endpoint=target.endpoint,
                           concurrentConnections=1,
                           requestsPerConnection=100,
                           pipeline=False)
    for i in range(30):
        engine.queue(target.req, gate='race1')
    engine.openGate('race1')
```

Ключ — `gate`: все запросы «висят» на сервере, затем отправляются одновременно.

## Как измерять успех

Гонку нужно не только провести, но и подтвердить.

| Признак | Что означает |
|---------|--------------|
| Разные статусы/тела в ответах | операция прошла дважды |
| Баланс изменился дважды | двойное списание/начисление |
| Купон применён N раз | limit-overrun |
| Разный `Set-Cookie` | двойная выдача токена |
| Время ответа различается | окно гонки найдено |

```bash
# сравнение: после гонки проверяем состояние
curl -s https://shop.example/cart | jq '{discounts: (.discounts|length), total}'
# до: 1 купон, total=50 ; после: 5 купонов, total=0
```

## HTTP/2 single-packet: детали

HTTP/2 позволяет отправить несколько запросов в одном фрейме, а сервер обработает их «одновременно».

```text
# клиент отправляет HEADERS+DATA для N потоков, затем все WINDOW_UPDATE
# сервер параллельно доходит до уязвимой секции -> окно гонки ~микросекунды
```

Требования: поддержка HTTP/2 (h2), один TCP-коннект, `concurrentConnections=1`. Если сервер h2 не поддерживает — fallback на HTTP/1.1 «last-byte sync».

## Многоконечные гонки (multi-endpoint race)

Иногда гонка — между **разными** эндпоинтами (например, «проверка баланса» и «списание»).

```python
# два разных запроса в одной гонке
engine.queue(req_check, gate='race1')
engine.queue(req_withdraw, gate='race1')
engine.openGate('race1')
```

Проверяйте сценарии: подтверждение email + смена email, приглашение + принятие, пополнение + вывод, создание + удаление.

## Таблица «что гонять»

| Сценарий | Что может сломаться |
|----------|---------------------|
| Применение купона | многократное применение |
| Перевод/вывод | отрицательный баланс |
| Rate-limit | обход лимита |
| 2FA | перебор кода |
| Голосование | накрутка |
| Сброс пароля | многократная выдача токена |
| Регистрация | дубликаты username |
| Покупка лимитного товара | превышение лимита |

## Что делать дальше / решение

1. **Найдите одноразовые операции.** Купоны, лимиты, балансы, 2FA.
2. **Определите транспорт.** h2 → single-packet; иначе last-byte.
3. **Соберите скрипт.** Turbo Intruder + gate.
4. **Запустите гонку.** 20-50 запросов одновременно.
5. **Измерьте результат.** Состояние изменилось больше одного раза.
6. **Зафиксируйте PoC.** Скрипт + подтверждённое нарушение инварианта.

## Практические приоритеты в гонках

Гонки ценны там, где операция должна выполняться строго один раз. Составьте список таких операций (купон, перевод, голос, 2FA, лимит) и для каждой запустите single-packet attack. Начните с HTTP/2 — окно гонки минимально; если сервер h2 не поддерживает, используйте last-byte sync на HTTP/1.1. Ключ к успеху — правильно измерить результат: сравнивайте состояние до и после, а не полагайтесь на статус-коды, которые могут быть одинаковыми.

## Итог

Гонка — это не «много запросов», а синхронизация попадания в узкое окно между проверкой и изменением состояния. Single-packet attack через Turbo Intruder делает это надёжно: `gate` удерживает запросы, `openGate` отправляет их вместе. Проверяйте все одноразовые операции и обязательно подтверждайте нарушение инварианта изменением состояния, а не догадкой.

## Частые ошибки при гонках

- Использовать обычные параллельные запросы и делать вывод «гонки нет» — окно слишком велико.
- Полагаться на статус-коды вместо проверки состояния после атаки.
- Не проверять многоконечные сценарии (проверка на одном эндпоинте, изменение на другом).
- Забывать про HTTP/2: single-packet attack требует одного соединения.
- Считать, что сервер «не уязвим», если гонка не удалась с первого раза — окно может зависеть от нагрузки.

## Дополнительно: выбор момента

Окно гонки часто привязано к тяжёлым операциям (запрос к БД, внешний вызов). Если single-packet не сработал, попробуйте «разогреть» сервер и повторить, либо увеличить число запросов до 50-100. Иногда помогает отправка запросов с разными телами, чтобы сервер дольше шёл до уязвимой секции.

## Кратко

Гонка — это синхронизация попадания в окно между проверкой и изменением состояния. Single-packet attack (HTTP/2, Turbo Intruder с `gate`) делает её надёжной; успех подтверждается изменением состояния, а не статус-кодом. Проверяйте каждую одноразовую операцию и обязательно измеряйте результат до и после.
