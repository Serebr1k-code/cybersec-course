## Вопрос, с которого всё начинается

В прошлом уроке мы просто отправили 20 запросов через `xargs -P20` — и гонка сработала. Но так везёт не всегда: иногда сервер обрабатывает запросы почти последовательно, и окно гонки «проскакивает». Тогда нужен способ отправить запросы **максимально одновременно**, чтобы окно вообще появилось.

Сегодня мы возьмём жёсткий лимит «один голос на пользователя» и научимся его пробивать современными методами.

## Наш пример

`vote.local` — сервис голосования. Голос отправляется так:

```http
POST /vote HTTP/1.1
Host: vote.local
Cookie: session=me

{"candidate":7}
```

Один голос проходит, второй — отказ:

```bash
$ curl -s -X POST https://vote.local/vote -b 'session=me' -d 'candidate=7'
{"ok":true,"votes":1}
$ curl -s -X POST https://vote.local/vote -b 'session=me' -d 'candidate=7'
{"error":"already voted"}
```

Попробуем классический параллельный залп — и убедимся, что он **не** срабатывает:

```bash
$ seq 30 | xargs -P30 -I{} curl -s -X POST https://vote.local/vote \
>   -b 'session=me' -d 'candidate=7' -o /dev/null -w '%{http_code}\n' | sort | uniq -c
     29 403
      1 200
```

Только один голос прошёл. Разброс по времени между запросами слишком большой — они обрабатываются последовательно, окно не открывается. Значит, нужна синхронизация.

## Шаг 1: last-byte sync (HTTP/1.1)

Идея простая. По TCP можно отправить почти весь запрос и задержать последний байт. Тогда все запросы «зависнут» в готовом виде, а мы досылаем последние байты одновременно — сервер получает их в один момент.

Схема такая:

1. Открываем N соединений.
2. В каждое пишем тело запроса **без** последнего байта.
3. Ждём, пока все готовы.
4. Досылаем последний байт во все сразу.

Это и есть **last-byte sync**. Работает по HTTP/1.1, потому что каждый запрос — отдельное соединение.

## Шаг 2: single-packet attack (HTTP/2)

С HTTP/2 всё ещё проще: соединение одно, а запросы в нём **мультиплексируются** (летят параллельно в рамках одного потока). Если отправить несколько запросов в одном TCP-пакете, они придут к серверу практически одновременно — разброс исчезает. Это и называют **single-packet attack**.

В Burp он встроен: выдели запросы в Repeater → правый клик → *Send group in parallel (single-packet attack)*. Проверим тот же голос этим способом:

```text
# Burp Repeater, 30 копий запроса /vote, Send group in parallel
--> 200
--> 200
--> 200
...
```

Теперь несколько `200` — окно открылось. Лимит «один голос» пробит.

## Шаг 3: Turbo Intruder

Для воспроизводимости удобен **Turbo Intruder** — расширение Burp, которое отправляет запросы точно синхронно. Скрипт минимальный:

```python
def queueRequests(target, wordlists):
    engine = RequestEngine(endpoint=target.endpoint,
                           concurrentConnections=1,
                           engine=Engine.BURP2)   # single-packet
    for i in range(30):
        engine.queue(target.req, gate='race1')

    engine.openGate('race1')   # все запросы уходят разом

def handleResponse(req, interesting):
    table.add(req)
```

Здесь `gate='race1'` — «ворота»: все запросы ждут, пока не откроется `race1`, и тогда уходят вместе. Именно это и создаёт окно.

## Шаг 4: limit overrun

Приём называется **limit overrun** — превышение лимита. Он применим везде, где есть «один раз на пользователя/аккаунт/IP»:

- один голос → десять;
- один купон → применён несколько раз;
- один промокод на email → на все;
- «не более 3 попыток» → тридцать.

Проверяем на голосовании: после залпа смотрим счётчик.

```bash
$ curl -s https://vote.local/candidate/7
{"candidate":7,"votes":4}
```

Четыре голоса вместо одного. Это доказательство: счётчик — измеримое состояние.

## Полный прогон от начала до конца

Начинаем с обычного `xargs -P30` — один `200`, не воспроизводится. Понимаем: нужно синхронизировать. Собираем 30 копий запроса в Burp и жмём *Send group in parallel* — получаем несколько `200`. Для чистоты пишем Turbo Intruder-скрипт с `gate` и воспроизводим стабильно. Смотрим `/candidate/7` — четыре голоса. В отчёт идёт: лимит «один голос», число запросов, результат счётчика. Всё воспроизводимо и измеримо.

## Почему это работает на уровне сети

Чтобы понять, почему синхронизация вообще нужна, вспомни, как устроен TCP. Каждый запрос — это набор пакетов, которые идут по сети с разной задержкой. Когда мы запускаем `xargs -P30`, тридцать `curl` стартуют почти одновременно, но их пакеты приходят с разбросом в десятки миллисекунд — а сервер успевает обработать первый и записать состояние до того, как придёт второй. Single-packet attack убирает этот разброс: все запросы лежат в одном пакете и приходят в сетевой стек сервера **вместе**. Тогда обработка начинается практически одновременно, и оба запроса успевают прочитать старое состояние. Last-byte sync добивается того же на уровне приложения: запросы лежат готовыми, а мы одновременно выпускаем последние байты. Понимание этого механизма помогает выбирать способ: HTTP/2 → single-packet, HTTP/1.1 → last-byte sync.

## Инструменты

Основной инструмент — **Burp Suite**: Repeater умеет *Send group in parallel (single-packet attack)*, этого хватает в большинстве случаев. Для тонкой настройки — **Turbo Intruder** с `Engine.BURP2` и воротами `gate`. Есть и внешние утилиты на Python (`h2`, `httpx`), но начинать стоит с Burp — там синхронизация уже реализована и не нужно писать сетевой код. Ещё один приём — **HTTP/2 single-packet с 0-длиной**: несколько запросов с `Content-Length: 0` и последним байтом тела, отправленным одним пакетом. Держи под рукой счётчик запросов и всегда фиксируй состояние до/после — иначе гонку не примут как доказательство.

## Где это встречается в реальности

Single-packet и last-byte sync нужны там, где окно гонки узкое: лимиты в финтехе, голосования на CDN, «одноразовые» купоны в высоконагруженных сервисах. В таких системах простой `xargs -P` не работает — сервер обрабатывает запросы слишком быстро. Поэтому, если обычный залп не воспроизводит гонку, не делай вывод «не уязвимо» — переходи к синхронизации.

## Частые вопросы

**«Чем single-packet лучше last-byte sync?»** Работает по HTTP/2, где несколько запросов мультиплексируются в один пакет. Last-byte sync — для HTTP/1.1. Выбор зависит от того, какой протокол у сервера.

**«Нужно ли писать код?»** Нет — в Burp есть «Send group in parallel». Turbo Intruder нужен, когда хочется точного контроля и воспроизводимости.

## Что мы теперь знаем

- Простой параллелизм часто проигрывает — нужна синхронизация.
- Last-byte sync (HTTP/1.1) задерживает последний байт каждого запроса.
- Single-packet attack (HTTP/2) мультиплексирует запросы в один пакет.
- Turbo Intruder с `gate` даёт воспроизводимую гонку.
- Limit overrun — превышение любого «один раз» лимита.
- Разброс по времени — враг гонки; синхронизация его убирает.

## На что смотреть дальше

- Если `xargs -P` не воспроизводит — не сдавайся, бери single-packet.
- Ищи лимиты: голоса, купоны, попытки, приглашения.
- Проверяй по счётчику, а не по коду ответа — состояние важнее.
- Не превышай лимиты на чужих аккаунтах и не накручивай реальные голоса.
