## Вопрос, с которого всё начинается

Сотрудники работают в четырёх системах: документы — в SharePoint, почта — в Exchange, знания — в Confluence, задачи — в Jira. Все четыре стоят во внутренней сети, все четыре аутентифицируют через Active Directory, и у всех четырёх есть история критических уязвимостей, которые ломали компании по всему миру. Сегодня разберём, что у них общего и как их атаковать.

## Что общего у четырёх систем

Первое: **они связаны с AD**. SharePoint использует Windows-аутентификацию, Exchange — учётные записи домена, Confluence и Jira — LDAP/AD. Значит, компрометация приложения = доступ к учётным записям и потенциально к домену.

Второе: **у них мощные API и веб-интерфейсы**, которые исторически страдали от обхода аутентификации. Классика — Exchange ProxyLogon (CVE-2021-26855), когда один запрос без пароля давал доступ к почтовым ящикам.

Третье: **они расширяемы** (плагины, веб-части, макросы), и в расширениях часто живут баги.

## Наш пример: находим Exchange в сети

Мы во внутренней сети, видим хост `10.10.10.60`:

```
$ nmap -sV -p 443,80 10.10.10.60
443/tcp open  https  Microsoft Exchange Server (OWA)
```

Заходим на `/owa/` и видим форму входа Outlook Web Access. Проверяем версию через эндпоинт:

```
$ curl -sk https://10.10.10.60/owa/auth/logon.aspx | grep -io 'exchange [0-9.]*'
```

Или через заголовки/`/ecp/`. Точная версия определяет, применим ли ProxyLogon/ProxyShell.

## Шаг 1: Exchange — ProxyLogon и родственные цепочки

**ProxyLogon** (CVE-2021-26855 + 26857 + 26858 + 27065) — цепочка, где SSRF в одном компоненте позволял обойти аутентификацию и записать веб-шелл. **ProxyShell** (CVE-2021-34473 + 34523 + 31207) — похожая цепочка через другие эндпоинты. **ProxyNotShell** — следующая волна.

Общая идея: комбинация **SSRF** (сервер ходит по URL от пользователя) и **доверия к внутренним запросам** позволяет добраться до функций, доступных только локально, и выполнить действия от админа.

Проверка безопасная: посмотреть, отвечает ли эндпоинт, характерный для уязвимой версии. Эксплуатация — только по подтверждённому PoC, аккуратно (Exchange критичен).

## Шаг 2: SharePoint — ToolShell и ViewState

SharePoint — .NET-приложение. Его ключевые векторы: **обход аутентификации** (ToolShell-цепочки, где через подделку токена получают доступ), **десериализация ViewState** (при утечке `machineKey`) и **загрузка веб-частей** (после входа — RCE).

Типовая цепочка: обход аутентификации → доступ к `/_layouts/` → загрузка страницы/части с кодом → RCE. Либо: утечка `machineKey` → ViewState → `ysoserial.net`.

## Шаг 3: Confluence — OGNL и обход аутентификации

Confluence (Java, Atlassian) знаменит двумя классами:

- **OGNL-инъекция** (CVE-2022-26134) — RCE без аутентификации через выражение в URL;
- **обход аутентификации** (CVE-2023-22515) — создание админа через специальный эндпоинт;
- **SSRF/path traversal** (CVE-2023-22518) — доступ к функциям восстановления.

Проверка OGNL: специальный URL с выражением `${...}`, которое при уязвимости вычисляется. Безопасная проверка — арифметика (`7*7`) в ответе.

## Шаг 4: Jira — шаблоны и утечки

Jira (Java, Atlassian) уязвима к:

- **инъекции шаблонов** (Velocity) — RCE через выражение в полях;
- **обходу аутентификации** (CVE-2023-22527 и родственные);
- **утечке данных** через незащищённые API (CVE-2019-8449 — список пользователей).

Jira и Confluence часто стоят на одном сервере и делят базу/инфраструктуру, поэтому компрометация одной помогает с другой.

## Шаг 5: план атаки на коллаборационное приложение

1. **Обнаружение** — nmap/httpx, баннеры продуктов.
2. **Версия** — точная (статика, API, заголовки).
3. **CVE** — сопоставление (NVD, Atlassian/Microsoft-бюллетени).
4. **PoC** — поиск, чтение, санитизация.
5. **Проверка** — неразрушающая (арифметика/эндпоинт).
6. **Эксплуатация** — при подтверждении.
7. **Пост-эксплуатация** — креды AD, дампы, движение.

## Шаг 6: как не навредить

Exchange, SharePoint, Confluence, Jira критичны: их падение останавливает работу компании. Поэтому — точечные проверки, без массовых запросов, без деструктивных payload'ов, SSRF на свой слушатель. Приложения под мониторингом, поэтому шум = раскрытие.

## Что мы теперь знаем

- Коллаборационные приложения связаны с AD и стоят во внутренней сети.
- Их критические CVE — это обход аутентификации, SSRF, десериализация, инъекция шаблонов.
- Exchange: ProxyLogon/ProxyShell; SharePoint: ToolShell/ViewState; Confluence: OGNL/обход; Jira: Velocity/утечки.
- Версия → CVE → PoC → безопасная проверка.
- Падение этих систем недопустимо.

## Шаг 7: как отличить продукты Atlassian и Microsoft на глаз

Точное определение продукта экономит время. Признаки:

- **Exchange**: путь `/owa/`, `/ecp/`, заголовок `X-OWA-Version`, cookie `cadata`.
- **SharePoint**: заголовок `X-SharePointHealthScore`, cookie `FedAuth`, пути `/_layouts/15/`.
- **Confluence**: `/login.action`, `/dashboard.action`, cookie `JSESSIONID`, страница `atlassian-confluence`.
- **Jira**: `/secure/Dashboard.jspa`, заголовок `X-AUSERNAME`, `/rest/api/`.

Если видишь `JSESSIONID` без явных признаков — проверь `/login.action` (Confluence) и `/secure/Dashboard.jspa` (Jira). Это разные продукты с разными CVE.

## Шаг 8: как связать приложение с доменом

Коллаборационные приложения аутентифицируют через AD, поэтому после доступа к ним ценность — в **учётных записях**. Ищи: конфиги LDAP (`ldap.url`, bind-пароль), service-account'ы, токены SSO. С bind-паролем можно читать LDAP и перечислять пользователей домена. Так «доступ к вики» превращается в «доступ к домену».

## Шаг 9: как писать отчёт по коллаборационному приложению

Отчёт должен содержать: продукт и точную версию; применимые CVE (с диапазонами); подтверждённую уязвимость (с запросом/ответом); связь с AD (какие учётки/группы доступны); оценку импакта (данные, интеграции). Каждое утверждение — с доказательством. Не «возможен обход», а «POST на `/server-info.action?...` вернул 200 и создал администратора; доказательство приложено».

## Шаг 10: как искать коллаборационные приложения точечно

Не сканируй всю сеть вслепую. Ищи по характерным путям через `httpx`:

```
$ httpx -l hosts.txt -path /owa/,/owa/auth/logon.aspx,/login.action,/secure/Dashboard.jspa,/_layouts/15/start.aspx -status-code -title
```

Ответы на эти пути точно укажут продукт. Так ты находишь Exchange, Confluence, Jira и SharePoint за один проход, не поднимая шума массовыми сканами.

## Шаг 11: как выстроить порядок атаки

Начни с того продукта, у которого версия попадает в **pre-auth RCE** — это самый короткий путь. Если таких нет, переходи к обходам аутентификации, затем к SSRF/утечкам. Не трать время на продукт, где версия пропатчена и нет конфигурационных дыр.

## Куда дальше

Дальше — каждое приложение по отдельности: SharePoint, Exchange (ProxyLogon), Confluence, Jira. А пока запомни: **это AD-связанные системы с RCE-классами; версия и аккуратность решают всё.**

## Где пригодится

- Пентест внутренней сети после получения доступа.
- Red team: путь к AD через коллаборационные системы.
- CTF: задания с конкретными CVE Atlassian/Microsoft.
