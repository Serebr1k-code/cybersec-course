## Вопрос, с которого всё начинается

Сайт грузит `app.wasm` — модуль **WebAssembly**. Раньше логика была в JS, который можно прочитать. Теперь она скомпилирована в бинарный формат, и «посмотреть в исходник» не выйдет. Что это меняет для атакующего и для защиты? И какие уязвимости приносит WASM?

## Наш пример

Открываем приложение и видим, что проверка подписи/лицензии происходит не в JS, а в WASM:

```bash
$ file app.wasm
app.wasm: WebAssembly (wasm) binary module version 0x1 (MVP)
```

Попробуем понять, что внутри.

## Шаг 1: что такое WebAssembly

WASM — **бинарный формат** для исполнения в браузере (и не только). Он не заменяет JS, а работает рядом: JS загружает модуль и вызывает его функции. Внутри — компактный байткод со **линейной памятью** (большой `ArrayBuffer`), стеком и типизированными функциями. Компилируют в WASM из C/C++/Rust/Go — значит, там может быть **нативный код**, включая баги памяти.

Для клиентской безопасности это означает: логику стало труднее читать, но **не безопаснее** — модуль всё равно исполняется в браузере жертвы и доступен атакующему.

## Шаг 2: реверс WASM

Первое — строки. Строки в WASM лежат в секции **data** в открытом виде:

```bash
$ strings app.wasm | grep -i flag
flag=nto{w4sm_s3cr3ts_1n_pl41n}
```

Это базовый реверс: `strings`, затем поиск функций по имени (если модуль не strip'нут, есть **name section**). Если имён нет — используем `wasm2wat` (из WABT) для дизассемблирования в текстовый формат **WAT**, `wasm-decompile`, или поднимаем модуль в отладчике браузера (DevTools → Sources показывает WAT/WASM). Часто секрет — константа в памяти или XOR-ключ в коде.

## Шаг 3: классы уязвимостей WASM

WASM-песочница изолирует модуль: он не может напрямую читать память браузера или делать syscalls. Но есть реальные риски:

- **Баг в самом рантайме (браузера)** — escape песочницы. Такие CVE (в V8/JSC) — редкость, но крайне ценны.
- **Логика в WASM не защищена** — как мы видели, секреты лежат в модуле; «клиентская валидация» обходится.
- **WASM + JS boundary** — функции JS передают в WASM указатели/буферы. Ошибки на границе (неверная длина, use-after-free в JS-обёртке) дают утечки памяти и логические обходы.
- **Untrusted WASM** — если приложение исполняет WASM, загруженный из недоверенного источника (плагины), это код, который выполняется с правами страницы.

## Шаг 4: WASM как часть цепочки

WASM часто комбинируется с другими багами:

- **Крипто-обфускация**: секреты зашиты в WASM (лицензии, ключи API) — их извлекают.
- **Anti-bot / fingerprinting**: WASM проверяет окружение; его можно пропатчить в DevTools, чтобы обойти.
- **XSS-приёмник**: вывод WASM-функции рендерится в DOM без экранирования → XSS.

## Полный прогон от начала до конца

Находим `app.wasm` в Network. Скачиваем. `file` подтверждает формат. `strings | grep -i flag` достаёт секрет-строку. Если строки зашифрованы — дизассемблируем `wasm2wat`, ищем константы и XOR-циклы. В отчёт идёт найденный секрет и наблюдение, что клиентская проверка находится в WASM и обходится.

## Если не сработало

Если `strings` пуст — модуль может сжимать/шифровать строки в data-секции. Попробуй `wasm2wat` и поиск `i32.const` рядом с `i32.xor`. Если модуль стрипнут — ориентируйся на размеры функций и вызовы из JS (DevTools показывает соответствие). Если WASM только для производительности и не содержит логики — ищи баг на границе JS↔WASM. И помни: WASM не «чёрный ящик» — есть открытые инструменты (WABT, wasm-decompile, Ghidra с плагином).

## Что мы теперь знаем

- WASM — бинарный формат, компилируемый из C/C++/Rust/Go, с линейной памятью.
- Строки и секреты часто лежат в модуле в открытом виде — `strings` их достаёт.
- Реверс: `wasm2wat`/`wasm-decompile`/DevTools, name section помогает.
- Песочница изолирует, но баги рантайма дают escape, а клиентская логика обходится.
- Граница JS↔WASM — источник ошибок с буферами и указателями.
- Untrusted WASM = выполнение чужого кода с правами страницы.

## Инструменты реверса WASM

WASM — не чёрный ящик: есть зрелый тулчейн (WABT, Binaryen, wasm-tools). Ставим и смотрим.

```bash
$ sudo apt install wabt binaryen
$ wasm-objdump -h app.wasm
app.wasm:	file format wasm 0x1

Sections:
     Type start=0x0000000a end=0x0000002f (size=0x00000025) count: 3
   Import start=0x00000031 end=0x00000045 (size=0x00000014) count: 2
 Function start=0x00000047 end=0x0000004e (size=0x00000007) count: 3
   Export start=0x0000005a end=0x0000006f (size=0x00000015) count: 2
     Code start=0x00000071 end=0x000001c8 (size=0x00000157) count: 3
     Data start=0x000001ca end=0x000001f2 (size=0x00000028) count: 1
```

`wasm-objdump -x` покажет импорты/экспорты (какие JS-функции модуль вызывает и что отдаёт наружу), `-d` — дизассемблирует в текстовый листинг. `wasm2wat app.wasm -o app.wat` даёт читаемый WAT, `wasm-decompile app.wasm` — псевдо-C.

## Карта секций модуля

| Секция | Содержит | Зачем смотреть |
|---|---|---|
| Type | сигнатуры функций | восстановить API |
| Import | внешние функции/память | что модуль просит у JS |
| Function | индексы функций | связка тип↔код |
| Memory | границы памяти | min/max страниц (64 KiB) |
| Global | глобальные переменные | ключи, счётчики |
| Export | что доступно JS | точки входа |
| Start | авто-функция | код до первого вызова |
| Code | тела функций | байткод, константы |
| Data | инициализация памяти | **строки, ключи, таблицы** |

Секрет чаще всего — в `Data`: это дамп начального содержимого линейной памяти, где и лежат строки в открытом виде.

## Кейс: патчим клиентскую проверку

Если модуль не хранит секрет, а проверяет лицензию/anti-bot, его можно **пропатчить** прямо в браузере: DevTools → Sources → `app.wasm` → Override, либо подменить экспорт-функцию в JS-обёртке.

```js
// было: const ok = mod.exports.check_license(input);
// стало — подменяем результат в рантайме через JS-обёртку:
const orig = mod.exports.check_license;
mod.exports.check_license = () => 1;   // всегда «валидно»
```

На серверной стороне это не сработает, но если приложение **доверяет** клиентской проверке — обход тривиален. Отсюда правило: любая проверка, живущая только в WASM/JS, не защищает.

## Уязвимости WASM-рантаймов

Песочница WASM строгая, но её **реализации** (движки) ломались неоднократно:

- **V8 / JSC escape** — ошибки в JIT/компиляторе WASM давали произвольное чтение/запись памяти процесса браузера (цепочки для Pwn2Own).
- **Spectre-подобные атаки** — WASM-модуль измеряет время и утекает данные из общей памяти.
- **WASI-хосты на сервере** — если сервер исполняет пользовательский WASM (плагины, sandbox), уязвимость в wasmtime/wasmer или в предоставленных хост-функциях = SSRF/RCE за песочницей.

```bash
$ wasmtime run --dir=. untrusted.wasm     # серверный запуск — новая поверхность
```

## WASM на сервере (WASI) как SSRF-точка

Серверные рантаймы (wasmtime, wasmer, WasmEdge) дают модулю **host-функции** — доступ к файлам, сети, часам. Если приложение исполняет пользовательский модуль и разрешает сокеты, инъекция в модуль = сетевой доступ из сервиса.

```bash
$ wasmtime run --allow-network untrusted.wasm
# внутри модуля: connect() к 169.254.169.254 — SSRF
```

Это тот же принцип, что в edge: новый рантайм тянет за собой новые host-функции, и каждая — граница доверия.

## Что делать дальше / решение

Порядок анализа `app.wasm`: (1) `file` + `wasm-objdump -h` — карта секций; (2) `wasm-objdump -x` — импорты/экспорты, что зовёт JS; (3) `strings` и разбор `Data` — секреты в открытом виде; (4) `wasm2wat`/`wasm-decompile` — логика, XOR-циклы, константы; (5) DevTools → Sources — соответствие WAT↔вызовы JS; (6) при клиентской проверке — патч в рантайме. Защита: секреты и валидация только на сервере, не доверять WASM как «бинарной защите», следить за версией движка и host-функциями.

## Справочная таблица

| Инструмент | Назначение |
|---|---|
| `wasm-objdump -h/-x/-d` | карта секций, импорты/экспорты, дизасм |
| `wasm2wat` | бинарь → читаемый WAT |
| `wasm-decompile` | бинарь → псевдо-C |
| `wasm-opt` | оптимизация (и деобфускация) |
| `wasm-tools` | парсинг/валидация/метаданные |
| Ghidra + wasm-плагин | интерактивный реверс |
| DevTools → Sources | WAT и вызовы из JS |

## Практический воркфлоу: от Network до патча

Соберём полный проход по шагам с реальными командами.

```bash
# 1. Находим модуль в Network-панели (фильтр .wasm), скачиваем.
$ curl -s -o app.wasm 'https://target.local/static/app.wasm'
$ file app.wasm
app.wasm: WebAssembly (wasm) binary module version 0x1 (MVP)

# 2. Карта и строки.
$ wasm-objdump -h app.wasm | grep -E 'Data|Export'
     Export start=0x0000005a end=0x0000006f (size=0x00000015) count: 2
     Data start=0x000001ca end=0x000001f2 (size=0x00000028) count: 1
$ strings -n 6 app.wasm
license_key
nto{w4sm_s3cr3ts_1n_pl41n}
/api/validate

# 3. Читаемый листинг.
$ wasm2wat app.wasm | grep -A2 'i32.const'
```

Если `strings` пуст, а в `Data` — случайные байты, ищи XOR-цикл: в WAT рядом с `i32.const` (ключ) идут `i32.xor`. Собери скрипт на Python и повтори расшифровку:

```python
data = open('app.wasm','rb').read()
for k in range(1, 256):
    out = bytes(b ^ k for b in data)
    if b'flag' in out or b'nto{' in out:
        print(k, out[:60])
```

## Что делать дальше / решение

Не останавливайся на `strings`. Если строки в открытом виде — забирай секрет и проверь, что он даёт (ключ API, подпись лицензии). Если зашифрованы — иди в `wasm-decompile`/Ghidra, восстанавливай алгоритм. Если логика — это проверка, пропатчи её в DevTools и подтверди обход. И всегда проверяй: не лежит ли тот же секрет/логика **и на сервере** — если да, клиентский обход не даёт импакта. Импакт появляется, когда сервер **доверяет** WASM-проверке.

## Куда дальше

WASM — пример того, как новая платформа уносит логику в бинарник, но не убирает поверхность. Дальше посмотрим на **edge-вычисления** — код, который выполняется на границе сети, ближе к пользователю, и на **расширения браузера** — код внутри браузера с широкими правами.

## Где пригодится

- **CTF (Web/Rev):** задачи с `app.wasm` — достать секрет, обойти проверку.
- **Bug bounty:** извлечение вшитых ключей/лицензий, обход anti-bot.
- **Пентест:** анализ клиентской логики в SPA на WASM.
- **Работа (AppSec):** не хранить секреты в WASM, валидировать на сервере, следить за границей JS↔WASM.
