## Вопрос, с которого всё начинается

Ты тестируешь интернет-магазин `shop.local`. На главной — форма входа. Ты привык проверять SQL-инъекцию: ставишь кавычку в логин, потом `' OR 1=1-- -` — и сервер вежливо отвечает «неверный пароль». Кажется, инъекций нет.

Но приложение написано на Node.js и работает не с SQL-базой, а с **MongoDB**. Запрос там устроен совсем иначе, и «ломать» его надо другими символами. В этом уроке мы разберём три класса инъекций, у которых **нет SQL**, но есть та же ошибка: пользовательский ввод смешивается с кодом запроса.

## Наш пример

Откроем форму входа в Burp или в DevTools и посмотрим, что уходит на сервер. Это POST-запрос на `/api/login` с телом в формате JSON:

```http
POST /api/login HTTP/1.1
Host: shop.local
Content-Type: application/json

{"username":"admin","password":"secret"}
```

**JSON** — это текстовый формат «ключ: значение», которым программы обмениваются структурированными данными. Сервер отвечает:

```json
{"error":"invalid credentials"}
```

Пароль `secret` не подошёл. Пока всё честно.

## Шаг 1: как сервер строит запрос к MongoDB

Внутри приложения этот обработчик выглядит примерно так:

```js
app.post('/api/login', async (req, res) => {
  const user = await db.collection('users').findOne({
    username: req.body.username,
    password: req.body.password
  });
  if (!user) return res.json({ error: 'invalid credentials' });
  res.json({ ok: true, token: makeToken(user) });
});
```

`findOne` — «найди один документ». В MongoDB документ — это как строка в таблице, только в виде JSON. Метод принимает **фильтр**: `{username: ..., password: ...}`. Обрати внимание на ключевое: код берёт `req.body.password` и вставляет как есть, **не проверяя, что это строка**.

А что если вместо строки прислать объект? Тогда MongoDB решит, что это не значение, а **оператор** — команда для фильтра.

## Шаг 2: подменяем строку на оператор

Оператор `$ne` означает «не равно». Отправим пароль не строкой, а объектом:

```bash
$ curl -s -X POST https://shop.local/api/login \
>   -H 'Content-Type: application/json' \
>   -d '{"username":"admin","password":{"$ne":"x"}}'
{"ok":true,"token":"eyJhbGciOiJIUzI1NiJ9.eyJ1aWQiOjF9.7fQ..."}
```

Мы вошли, не зная пароля. Почему? Сервер построил фильтр «пароль **не равен** `x`» — а это истинно для любого реального пароля. MongoDB вернула первый подходящий документ — администратора — и выдала токен.

Такую атаку называют **NoSQL-инъекцией**: инъекция в язык запросов, который не является SQL. `$ne` — лишь один из операторов; есть ещё `$gt` («больше»), `$regex` (регулярное выражение), `$in`, `$where`. Подробно — в уроке `web-nosql-injection`.

## Шаг 3: тот же магазин, но другой язык запросов

Осматривая `shop.local`, мы находим ещё два портала входа. Первый — `/staff/login` для сотрудников: это форма `application/x-www-form-urlencoded` (данные как `ключ=значение&ключ=значение`), и она проверяет логин в **LDAP**.

**LDAP** — это каталог, «дерево» учётных записей (Active Directory — его родственник). Поиск в нём описывают **фильтром**:

```
(&(uid=USER)(userPassword=PASS))
```

`&` — «И», `uid` — имя пользователя, `userPassword` — пароль. Если ввод не экранируют, звёздочка `*` (в LDAP — «любые символы») ломает условие:

```bash
$ curl -s -X POST https://shop.local/staff/login -d 'user=*&password=*'
Welcome, cn=admin,ou=staff,dc=shop,dc=local
```

Фильтр стал `(&(uid=*)(userPassword=*))` — «любой пользователь с любым паролем». Каталог вернул первую запись, администратора.

Второй портал — `/legacy/login`, старый, хранит пользователей в XML-файле и ищет их через **XPath**:

```
//user[username/text()='USER' and password/text()='PASS']
```

**XPath** — язык навигации по XML-документу. Здесь всё как в SQL: кавычка и `or` делают условие всегда истинным:

```bash
$ curl -s -X POST https://shop.local/legacy/login \
>   --data-urlencode "user=' or 1=1 or ''='" -d 'password=x'
<h1>Welcome, admin</h1>
```

Флаг `--data-urlencode` у curl сам кодирует спецсимволы в `%27`, чтобы они дошли до сервера как есть. Условие превратилось в `... or 1=1 or ...` — истина.

## Шаг 4: когда данные не показываются — «да/нет» вслепую

Часто сервер не выводит данные, а только «успех» или «ошибка». Это не конец: играем в вопросы «да/нет» и вытягиваем строку посимвольно.

Для NoSQL спросим: «пароль начинается на `f`?»

```bash
$ curl -s -X POST https://shop.local/api/login -H 'Content-Type: application/json' \
>   -d '{"username":"admin","password":{"$regex":"^f"}}'
{"ok":true,"token":"eyJ..."}          # 'f' верно
$ curl -s -X POST https://shop.local/api/login -H 'Content-Type: application/json' \
>   -d '{"username":"admin","password":{"$regex":"^z"}}'
{"error":"invalid credentials"}       # 'z' неверно
```

`^` — «начало строки». Перебирая символы, скрипт восстановит пароль целиком. То же делают LDAP-звёздочкой (`user=admin)(description=fla*`) и XPath-функцией `substring()`. Детали каждого приёма — в отдельных уроках ниже.

## Шаг 5: как понять, с каким хранилищем ты говоришь

Прежде чем строить payload, надо определить язык запроса — иначе потратишь время на `$ne` там, где работает `*`. Три подсказки.

Первая — **формат ввода**. JSON-тело намекает на MongoDB или API поверх неё; обычная HTML-форма (`ключ=значение`) чаще встречается у LDAP- и XPath-приложений.

Вторая — **текст ошибки**. Сломав ввод, смотри, что вернёт сервер. `MongoError: unknown operator` — MongoDB; `javax.naming.NamingException` или `LDAPException` — каталог; `XPathException` / `Invalid expression` — XPath.

Третья — **порты**. Если у тебя есть доступ к сети, `nmap -sV` покажет 27017 (MongoDB), 389/636 (LDAP) прямо открытыми:

```bash
$ nmap -sV -p 27017,389,636 shop.local
27017/tcp open  mongodb   MongoDB 6.0.5
389/tcp   open  ldap      OpenLDAP 2.4.X
```

Открытый порт хранилища без пароля — это уже самостоятельная находка, часто более ценная, чем инъекция.

## Если не сработало

Если `{"$ne":"x"}` не проходит, причина обычно в **типизации**: сервер проверяет `typeof password === 'string'` и отбрасывает объект. Тогда попробуй соседние операторы (`$gt`, `$in`, `$regex`) или вложенность — иногда фильтр ловит только `$ne`. Если фильтруются `$`-ключи, помогает URL-кодирование (`%24ne`) или unicode (`\u0024ne`).

В LDAP иногда фильтруют `*` — тогда используй разрыв фильтра `)(`, а не wildcard. В XPath, если кавычки экранируют, помогает чередование кавычек и функция `concat()`. И помни: любой брут и слепое извлечение — только на своём стенде или аккаунте, не на боевом чужом.

## Что мы теперь знаем

- «Не SQL» ≠ «безопасно»: у MongoDB, LDAP и XPath свои языки запросов, и в них тоже бывают инъекции.
- NoSQL (MongoDB): если ввод попадает в `findOne` без проверки типа, объект-оператор `{"$ne":"x"}` обходит вход.
- LDAP: символы `(`, `)`, `*`, `|`, `&` меняют структуру фильтра; `*` даёт вход «любым» пользователем.
- XPath: кавычка и `or 1=1` ломают условие, как в SQL.
- Когда вывод скрыт, все три класса подбираются посимвольно через «да/нет» (`$regex`, wildcard, `substring()`).
- Защита везде одна: строгая проверка типа и экранирование/параметризация запроса.

## Куда дальше

Дальше мы разберём каждый класс отдельно. Сначала `web-nosql-injection` — как MongoDB-операторы (`$ne`, `$gt`, `$regex`, `$where`) дают и обход входа, и посимвольное извлечение. Потом `web-ldap-injection` — фильтры каталога и `)(`. И `web-xpath-injection` — `substring()` и слепой перебор в XML. А пока главное запомни: если ввод становится частью запроса на **любом** языке — SQL, Mongo, LDAP или XPath — ты им управляешь.

## Где пригодится

- **CTF (Web):** NoSQL-логин и LDAP-обход — частые задачи, где SQL-сканер бессилен.
- **Bug bounty:** обход аутентификации через тип-конфузию — критичный отчёт.
- **Пентест:** проверять надо все хранилища (SQL, NoSQL, LDAP, XML), а не только SQL.
- **Работа (AppSec/Dev):** типизация входа и параметризация запросов для любого хранилища — базовое требование.
