Ты открыл `shop.local` — браузер показал красивую страницу с товарами. Но «сайт» — это не один файл. За одной страницей стоит цепочка: браузер → прокси → сервер приложения → база данных. Почти каждая веб-уязвимость живёт **на стыке** двух таких компонентов. Поэтому прежде чем что-то ломать, полезно понять, из чего цель собрана.

В этом уроке мы разберём один сайт `shop.local` и по косвенным признакам восстановим его архитектуру — как археолог по черепкам.

## Наш пример: что стоит за shop.local

Зададим простой вопрос: «какие технологии отвечают на запросы?». Первый инструмент — `whatweb`, он смотрит заголовки, cookie и характерные признаки:

```bash
$ whatweb -a 3 'https://shop.local'
https://shop.local [200 OK] nginx[1.25.3], React, Next.js, Cookies[session], Country[EU]
```

Мы узнали сразу несколько слоёв: веб-сервер `nginx`, фронтенд на `React`/`Next.js`. Как это видно? По заголовкам ответа и по структуре страницы. Посмотрим заголовки сами:

```bash
$ curl -s -I 'https://shop.local/'
HTTP/1.1 200 OK
Server: nginx/1.25.3
X-Powered-By: Next.js
Set-Cookie: session=...; HttpOnly; SameSite=Lax
Content-Security-Policy: default-src 'self'
```

`Server` — какой сервер отдаёт статику и проксирует запросы. `X-Powered-By` — на чём написано приложение. `Set-Cookie: session=...` — как называется cookie сессии (часто выдаёт язык). `Content-Security-Policy` — защитный заголовок. Уже картина: **nginx стоит перед приложением на Next.js**.

## Шаг 1: разбираем слои

Типовое веб-приложение — это несколько слоёв, каждый со своей ролью и своими типовыми багами.

- **Frontend (клиент)** — HTML/CSS/JavaScript, исполняется в браузере. Здесь рождаются XSS и утечки токенов. Главное правило: **frontend не является защитой** — всё, что пришло от клиента, может быть подделано.
- **Reverse-proxy / балансировщик** (nginx, Apache, HAProxy, Cloudflare) — терминирует TLS, кэширует, маршрутизирует. Здесь настраивают WAF и заголовки `X-Forwarded-*`. Ошибки конфигурации дают path traversal, SSRF, host-header injection.
- **Application-сервер (backend)** — здесь живёт бизнес-логика: аутентификация, заказы, работа с БД. Большинство «интересных» багов (SQLi, SSTI, IDOR, command injection) — тут.
- **База данных** — MySQL/PostgreSQL/MongoDB/Redis. Прямые атаки идут через инъекции из backend.
- **Внешние сервисы** — S3, очереди, платёжные шлюзы, почта. Источник SSRF и утечек ключей.

Текстовая схема нашего магазина:

```
Browser
  └─(HTTPS)─> nginx (reverse-proxy, TLS, статика)
        └─> Next.js app (логика, API)
              └─> PostgreSQL (товары, пользователи)
                    └─> S3 (картинки товаров)
```

## Шаг 2: имя cookie выдаёт backend

Заголовок `Set-Cookie` — бесплатный паспорт технологии. Разные фреймворки дают сессии разные имена:

| Cookie | Технология |
|--------|-----------|
| `PHPSESSID` | PHP |
| `JSESSIONID` | Java (Servlet) |
| `connect.sid` | Node/Express |
| `sessionid` | Django / общее |
| `_session_id` | Ruby on Rails |

У нас `session=...` — не выдаёт однозначно, но вместе с `X-Powered-By: Next.js` (Node) картина ясна. Знание стека сразу подсказывает, какие классы проверять: PHP → обёртки и type juggling, Java → десериализация, Node → prototype pollution.

## Шаг 3: JS-бандл прячет все API

Современный SPA грузит один большой JS-файл, в котором зашиты все пути к API. Достанем его:

```bash
$ curl -s 'https://shop.local/' | grep -oE 'src="[^"]+\.js"' | head -1
src="/_next/static/chunks/main-7f3a9c.js"
$ curl -s 'https://shop.local/_next/static/chunks/main-7f3a9c.js' -o app.js
$ grep -oE '/api/[a-zA-Z0-9_/{}.-]+' app.js | sort -u
/api/products
/api/products/{id}
/api/cart
/api/admin/settings
```

Мы нашли скрытый `/api/admin/settings`, которого нет в меню. Вот почему JS-бандл — обязательный шаг разведки: интерфейс показывает не всё, а бандл знает все маршруты. Проверим, какие из них живы:

```bash
$ for p in /api/products /api/admin/settings; do
    echo -n "$p -> "; curl -s -o /dev/null -w '%{http_code}\n' "https://shop.local$p"
  done
/api/products -> 200
/api/admin/settings -> 401
```

`401` у админского эндпоинта означает: он существует, но требует аутентификации. Это цель для дальнейших проверок.

## Шаг 4: robots.txt — легальная карта сайта

Ещё один бесплатный источник — `robots.txt`, где владелец перечисляет, что не надо индексировать. Часто там прямо названы админки и служебные разделы:

```bash
$ curl -s 'https://shop.local/robots.txt'
User-agent: *
Disallow: /admin
Disallow: /internal
Disallow: /api/v2
```

`Disallow` — это не запрет доступа, а просьба к поисковикам. Для тебя это подсказка: смотри `/admin`, `/internal`, `/api/v2`.

## Шаг 5: где рождаются уязвимости — границы доверия

Главная причина большинства веб-багов — **разрыв модели доверия** на стыке слоёв. Каждый слой должен сам проверять вход, но на практике это делают «где-то в одном месте».

- **Браузер → backend:** клиентская проверка на JS — не защита, её обходят напрямую.
- **Прокси → приложение:** если прокси не перезаписывает `Host` и `X-Forwarded-*`, клиент может их подделать.
- **Приложение → БД:** конкатенация строк в SQL-запросе даёт инъекцию; нужна параметризация.
- **Сервис → сервис:** микросервисы часто доверяют друг другу без проверки («внутренняя сеть же безопасна»).

Практический приём: на каждом стыке спрашивай «а что, если этот заголовок/поле подделать?» — так ты и находишь следующий вектор.

## Шаг 6: микросервисы и API-gateway

Современное приложение — не монолит, а граф сервисов. Одна страница может обращаться к десяткам бэкендов на разных поддоменах. Картируй их через сетевую панель браузера и JS-бандлы, а не только по видимым ссылкам. Типовые точки, которые стоит проверить: `/actuator`, `/health`, `/metrics`, `/swagger`, `/v2/api-docs` — они раскрывают карту сервисов.

## Полный разбор: рекон за пять минут

Соберём всё вместе на `shop.local` одной серией команд:

```bash
$ whatweb -a 3 'https://shop.local' | tr ',' '\n' | grep -iE 'nginx|next|react'
nginx[1.25.3]
Next.js
React
$ curl -s 'https://shop.local/' | grep -oE 'src="[^"]+\.js"' | head -1
src="/_next/static/chunks/main-7f3a9c.js"
$ curl -s 'https://shop.local/_next/static/chunks/main-7f3a9c.js' | grep -oE '/api/[a-zA-Z0-9_/{}.-]+' | sort -u
/api/products
/api/cart
/api/admin/settings
$ curl -s 'https://shop.local/robots.txt' | grep -i disallow
Disallow: /admin
Disallow: /internal
```

За минуту мы узнали стек (nginx + Next.js), нашли скрытый `/api/admin/settings` и служебные разделы. Дальше — фаззинг и проверка найденных ручек.

## Что мы теперь знаем

- За сайтом стоит цепочка слоёв: клиент → прокси → приложение → БД → внешние сервисы.
- Стек определяется по заголовкам (`Server`, `X-Powered-By`), имени cookie и структуре страницы.
- JS-бандл содержит скрытые API-пути; `robots.txt` подсказывает служебные разделы.
- Frontend — не защита: любой вход от клиента может быть подделан.
- Большинство уязвимостей живёт на границах доверия между слоями.

## На что смотреть дальше

- **Поддомены.** `api.`, `admin.`, `internal.`, `staging.` — каждый со своей поверхностью; собирай через subfinder → httpx.
- **Внутренние сервисы.** `*.svc.cluster.local`, `/internal/` часто без аутентификации и доверяют сети.
- **Стек → класс багов.** `X-Powered-By: Express` → Node-специфика; `PHPSESSID` → PHP-обёртки; `Server: nginx` → alias traversal.

## Куда дальше

Мы получили карту: слои, стек, скрытые API. Дальше самое время понять, как сервер **узнаёт** пользователя между запросами — то есть как работают cookie и сессии. Этим займёмся в следующем уроке. А пока запомни: **архитектура подсказывает, куда бить; ищи разрыв доверия на стыке слоёв.**

## Где пригодится

- **CTF (Web):** понимание слоёв быстро подсказывает, куда «бить»; часто флаг лежит в скрытом API из JS.
- **Bug bounty:** карта технологий и эндпоинтов — первый шаг любого отчёта; скрытые API — самый дорогой баг.
- **Пентест:** определение архитектуры задаёт стратегию тестирования.
- **Работа (AppSec/архитектор):** ревью архитектуры и threat modeling опираются на эти слои и их границы доверия.
