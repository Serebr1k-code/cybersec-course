## Вопрос, с которого всё начинается

GitLab — это не просто «хостинг репозиториев»: это SCM + CI/CD + registry + wiki, то есть центр разработки компании. В нём лежат **исходники, секреты, токены runner'ов и ключи деплоя**. Компрометация GitLab = доступ к коду, к пайплайнам и часто к продовой инфраструктуре. И у GitLab есть критические CVE, дающие чтение файлов и RCE. Разберём.

## Наш пример: self-hosted GitLab

Цель — `https://gitlab.target.example`. Фингерпринт:

```
$ curl -s https://gitlab.target.example/api/v4/version
{"version":"16.2.0","revision":"..."}
```

`/api/v4/version` может требовать токен, тогда версию берём из `/help` или статики:

```
$ curl -s https://gitlab.target.example/help | grep -io 'gitlab [0-9.]*'
GitLab 16.2.0
```

Версия **16.2.0** — сопоставляем с CVE.

## Шаг 1: CVE-2023-2825 — path traversal

Эта уязвимость позволяет **неаутентифицированно** читать произвольные файлы через специально сформированный путь в эндпоинте вложений:

```
$ curl --path-as-is 'https://gitlab.target.example/../../../../../../etc/passwd'
```

В реальных PoC путь длиннее и обходит проверки. Через баг читают `gitlab.rb`, `database.yml` (креды БД), `secrets.yml`, а также файлы репозиториев. Это даёт доступ к секретам инфраструктуры.

## Шаг 2: CVE-2021-22205 — RCE через ExifTool

GitLab использует **ExifTool** для обработки метаданных загружаемых изображений. В определённых версиях ExifTool (и, соответственно, GitLab) можно было подсунуть изображение с вредоносными метаданными, которые ExifTool исполнял — это RCE **без аутентификации**:

```
$ python3 cve-2021-22205.py -t https://gitlab.target.example -c 'id'
```

Payload — картинка с DjVu-подобным содержимым в метаданных. Публичный PoC существует; читай и адаптируй.

## Шаг 3: токены runner'ов и пайплайны

GitLab runner'ы исполняют пайплайны (то есть код) на инфраструктуре. **Registration token** или **runner token** позволяет зарегистрировать свой runner или запустить job. Если токен утёк (в репозитории, в логах, в CI-переменной), атакующий получает выполнение кода на серверах сборки — часто в облаке или Kubernetes.

Плюс CI/CD-переменные (`.gitlab-ci.yml`, settings) хранят **секреты деплоя**: облачные ключи, SSH-ключи, токены.

## Шаг 4: план атаки на GitLab

1. Версия (`/api/v4/version`, `/help`).
2. CVE-сопоставление (traversal, ExifTool RCE).
3. Проверка traversal (чтение `gitlab.rb`).
4. Проверка ExifTool RCE (безопасный маркер).
5. Поиск токенов/секретов (репозитории, CI-переменные).
6. Пост-эксплуатация — пайплайны, деплой-ключи.

## Шаг 5: как не навредить

GitLab — центр разработки; его падение останавливает работу инженеров. RCE через ExifTool может создавать файлы/процессы. Поэтому: traversal — только чтение; RCE — с безобидным маркером; не запускай реальные пайплайны; не трогай репозитории.

## Что мы теперь знаем

- GitLab версию отдаёт `/api/v4/version` или `/help`.
- CVE-2023-2825 — traversal для чтения файлов/секретов.
- CVE-2021-22205 — ExifTool RCE без аутентификации.
- Токены runner'ов дают выполнение кода на инфраструктуре.
- CI-переменные хранят секреты деплоя.

## Шаг 7: как использовать GitLab для движения дальше

GitLab — это не конечная цель, а **транспорт** к инфраструктуре. После доступа ищи: (1) **CI/CD-переменные** (Settings → CI/CD → Variables) — облачные ключи, SSH, токены деплоя; (2) **токены runner'ов** — для запуска кода на серверах сборки; (3) **deploy keys** и **access tokens** — для доступа к другим репозиториям и API; (4) в репозиториях — закоммиченные секреты (часто в истории git).

Так одна уязвимость GitLab открывает доступ к продовой инфраструктуре через пайплайны.

## Шаг 8: как оценивать импакт GitLab-находки

ExifTool RCE = контроль сервера GitLab (критический). Traversal с чтением `gitlab.rb`/`secrets.yml` = креды БД и инфраструктуры (критический). Токены runner'ов = выполнение кода в CI (критический). Утечка репозиториев = исходники и секреты (высокий). В отчёте перечисли конкретные доступы.

## Шаг 9: типовые ошибки при работе с GitLab

Ошибка первая — путать версии (CVE-2021-22205 и CVE-2023-2825 — разные диапазоны). Вторая — запускать ExifTool PoC без чтения (может создать файлы). Третья — не проверять CI-переменные (там самое ценное). Четвёртая — игнорировать историю git (секреты в старых коммитах).

## Шаг 10: как читать публичный PoC для GitLab

PoC для ExifTool RCE (CVE-2021-22205) — это Python-скрипт, отправляющий вредоносную картинку. Прочитай: он может запускать обратную оболочку — замени адрес на свой. Убедись, что он не удаляет данные и не трогает репозитории. Для проверки используй безобидную команду (`id`/DNS).

## Шаг 11: как искать секреты в репозиториях GitLab

Даже без CVE, если репозитории доступны, ищи закоммиченные секреты: ключи, токены, пароли в истории git. Инструмент — `trufflehog` или `gitleaks`:

```
$ trufflehog git https://gitlab.target.example/group/repo.git --only-verified
```

Секреты часто лежат в старых коммитах, даже если удалены в текущем.

## Шаг 12: как защититься от GitLab-атак

Защита: обновление (CVE-2021-22205 закрыта в 13.10.3/13.9.6/13.8.8; CVE-2023-2825 — в 16.0.1); ограничение регистрации runner'ов; защита CI-переменных (masked/protected); секрет-сканирование репозиториев. Для атакующего: свежий GitLab закрывает traversal/ExifTool, и остаются конфигурационные дыры.

## Шаг 13: почему GitLab — приоритетная цель в DevOps

GitLab — центр разработки: код, пайплайны, registry, секреты деплоя. Его компрометация даёт доступ к **исходникам и к проду** через CI/CD. Поэтому в пентестах GitLab проверяют одним из первых после получения доступа в сеть. Приём: определяй версию через `/api/v4/version` (если закрыт — `/help`) и сверяй с CVE.

## Шаг 14: как оформить находку

Укажи: версию GitLab; применимый CVE; подтверждение (прочитанный файл); доступы (токены runner'ов, CI-переменные); импакт (код + прод). Отдельно — найденные секреты в репозиториях. Рекомендации: обновить, ограничить регистрацию runner'ов, защитить CI-переменные.

## Практика: безопасная проверка CVE-2021-22205

CVE-2021-22205 — RCE через загрузку изображения: ExifTool неверно парсит DJVU, и GitLab выполняет код при обработке. Проверка без вреда: загрузить **безобидный** файл и убедиться, что обработка изображений включена, а версия уязвима:

```
$ curl -sI https://gitlab.target.example/help | grep -iE 'gitlab|x-request-id'
X-Request-Id: 01H...
$ curl -s https://gitlab.target.example/api/v4/version -H 'PRIVATE-TOKEN: <token>' 
{"version":"13.10.2","revision":"..."}
```

`/api/v4/version` требует токена, но версия утекает и из `/help` (футер), и из `/assets/webpack/manifest.json`. Уязвимы 13.x<13.10.3 и 11.x/12.x. Только после подтверждения версии — публичный PoC, и только тот, что не пишет на диск лишнего.

## Практика: поиск секретов в репозиториях

GitLab — это в первую очередь **код**, а код полон секретов. Начни с публичных проектов: `/api/v4/projects?visibility=public`. Внутри — история коммитов, где часто лежат `.env`, ключи AWS, токены. Инструмент `trufflehog`/`gitleaks` по клону:

```
$ git clone --mirror https://gitlab.target.example/group/repo.git repo.git
$ gitleaks detect --source repo.git --report-format json
```

Часто находится `CI_JOB_TOKEN`, `AWS_SECRET_ACCESS_KEY`, приватные SSH-ключи. Эти креды ценнее, чем сам GitLab: они открывают прод-инфраструктуру.

## Практика: CI/CD — от runner-токена к RCE

GitLab Runner регистрируется по токену. Если токен проекта (`/api/v4/projects/<id>/runners`) утёк, можно зарегистрировать свой runner и выполнять джобы на инфраструктуре жертвы — а джобы выполняют произвольный код из `.gitlab-ci.yml`. Ещё проще — если в проекте есть `maintainer`-доступ: правишь `.gitlab-ci.yml` и получаешь shell на раннере. Это стандартный путь «GitLab → прод».

## Таблица: GitLab-векторы и версии

| Вектор | CVE | Уязвимые версии | Условие |
|---|---|---|---|
| ExifTool RCE | CVE-2021-22205 | 11.x–13.10.2 | загрузка изображения |
| Path traversal | CVE-2023-2825 | 16.0.0 | публичный проект |
| Account takeover | CVE-2022-1162 | 14.7–14.9 | предсказуемый пароль |
| Pipeline RCE | (by design) | все | maintainer + CI |
| Token leak | — | все | открытый репозиторий |

## Как использовать GitLab для движения дальше

GitLab — узел с высокой связностью: он знает про все репозитории, все CI-переменные, все деплои. После входа ищи: (1) `CI/CD → Variables` во всех проектах (там токены к облаку и БД), (2) `Settings → CI/CD → Runners` (токены раннеров), (3) `Settings → Integrations` (вебхуки, Slack-токены), (4) `Deploy Keys` (SSH-ключи к прод-серверам). Каждый из этих разделов — готовый путь к следующему узлу. Фиксируй найденное в state и передавай координатору: GitLab-компромисс почти всегда открывает облако и прод-серверы, но объём работы по ним — отдельная задача.

## Шпаргалка: команды для GitLab

Рабочий набор. Версия: `curl -s https://host/help | grep -oE 'GitLab (CE|EE) [0-9.]+'` или `curl -s https://host/assets/webpack/manifest.json`. Публичные проекты: `curl -s https://host/api/v4/projects?visibility=public`. Регистрация открыта: `curl -s -o /dev/null -w '%{http_code}' https://host/users/sign_up`. Экспорт проекта (частая утечка): `curl -s https://host/<group>/<repo>/-/archive/main/repo-main.tar.gz -o repo.tgz`. Секреты в коде: `git clone --mirror <url>` затем `gitleaks detect --source`. Версии с CVE-2021-22205 — 13.x<13.10.3. Сохраняй вывод каждой команды: утечка токена — это находка, и её надо доказать артефактом.

## Почему GitLab — вторая после Exchange цель в DevOps

GitLab хранит не данные, а **способ их менять**: исходники, пайплайны, креды к облаку и деплой-скрипты. Компромисс GitLab означает, что ты можешь влить код в прод, поменять CI и получить shell на раннере — и всё это «легально» с точки зрения системы. В матрице приоритетов GitLab стоит рядом с Exchange: оба дают путь к домену/облаку, а не просто одну находку. Поэтому, обнаружив self-hosted GitLab, сначала проверяй версию на ExifTool-RCE, затем публичные проекты на секреты, и лишь потом думай о массовых действиях — каждый этап фиксируй отдельно.

## Короткий итог по GitLab

Запомни три числа: версия (для CVE-2021-22205), права токена (для пайплайнов), путь к секретам (для облака). Эти три пункта покрывают 90% работы на self-hosted GitLab. Дальше — только терпение и аккуратная фиксация находок.
