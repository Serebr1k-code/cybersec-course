## Вопрос, с которого всё начинается

Есть приватная страница `/profile/me` — она отдаёт твои личные данные и требует авторизации. А есть кэш, который считает, что «файлы с расширением `.css`/`.png` можно кэшировать». Что если попросить `/profile/me.css`? Приложение вернёт профиль, а кэш решит, что это статика, и **закэширует приватные данные**. После этого их прочитает кто угодно.

Это **Web Cache Deception** (WCD) — обман кэша. Сегодня разберём его на одном примере.

## Наш пример

`shop.local` за CDN. Авторизуемся и заходим в профиль:

```bash
$ curl -s https://shop.local/profile/me -b 'session=me'
{"email":"me@shop.local","card":"****4242"}
```

Приватные данные, требуется сессия. Посмотрим, как CDN решает, кэшировать ли ответ. Правила обычно смотрят на **расширение** или путь. Попробуем добавить расширение статики:

```bash
$ curl -s https://shop.local/profile/me.css -b 'session=me'
{"email":"me@shop.local","card":"****4242"}
```

Приложение **проигнорировало** `.css` и вернуло тот же профиль. Теперь проверим, что решил кэш:

```bash
$ curl -sI https://shop.local/profile/me.css -b 'session=me' | grep -i 'x-cache\|cache-control'
X-Cache: HIT
Cache-Control: public
```

`X-Cache: HIT` и `public` — кэш сохранил приватный ответ как публичный. Это и есть WCD.

## Шаг 1: как кэш решает, кэшировать ли

Кэш смотрит на несколько сигналов: `Cache-Control`, наличие `Set-Cookie`, метод, и часто — **расширение** в пути. Статику (`\.css`, `\.js`, `\.png`) он кэширует агрессивно, а «страницы» — нет. Если приложение нормализует путь (`/profile/me.css` → `/profile/me`), а кэш — нет, получается расхождение: приложение отдаёт приватное, кэш считает это файлом.

## Шаг 2: path confusion

Есть несколько форм обмана:

```bash
# расширение в конце
/profile/me.css
# через точку-запятую или точку
/profile/me;.css
/profile/me%2f.css
/profile/me/.css
# с query
/profile/me?x=.css
```

Каждая из них может «обмануть» кэш, оставив путь тем же для приложения. Перебирай варианты: какой-то из них попадёт в кэш.

## Шаг 3: жертва заходит по «отравленному» URL

Ключевой момент: кэширует **ответ жертвы**, а не твой. Поэтому нужно заставить жертву открыть `/profile/me.css`. Способы: ссылка в письме, `img`/`link` на стороннем сайте, редирект. Как только жертва открывает URL, кэш сохраняет её приватную страницу как публичную.

В тестовом окружении сымитируем жертву своим вторым аккаунтом:

```bash
$ curl -s https://shop.local/profile/victim.css -b 'session=victim' -o /dev/null
$ curl -s https://shop.local/profile/victim.css | head -c 60
{"email":"victim@shop.local","card":"****1111"}
```

## Шаг 4: читаем без авторизации

Теперь — самое главное. Обращаемся к тому же URL **без** сессии:

```bash
$ curl -s https://shop.local/profile/victim.css
{"email":"victim@shop.local","card":"****1111"}
```

Кэш отдаёт приватные данные жертвы анонимному пользователю. Полная утечка. Impact: кража PII, токенов, номеров карт — всё, что было на приватной странице.

## Шаг 5: где искать и как проверить

Ищи эндпоинты, которые:
- отдают приватное (профиль, настройки, API-ключи, баланс);
- нормализуют путь (игнорируют лишние сегменты);
- за CDN с правилом «кэшировать статику по расширению».

Проверка: добавь `.css`, посмотри `X-Cache: HIT` и `Cache-Control: public`, затем запроси URL без сессии. Если вернулись чужие данные — WCD подтверждён.

## Полный прогон от начала до конца

Заходим в профиль — приватно. Добавляем `.css` — приложение отдаёт тот же профиль. Смотрим заголовки — `HIT`, `public`. Просим жертву открыть URL — кэш сохраняет её данные. Читаем без сессии — получаем приватные данные. В отчёт идёт четыре запроса: приватный, «обманный», от имени жертвы и анонимный — с одинаковым телом.

## Почему это работает

Потому что **кэш и приложение смотрят на разные вещи**. Кэш решает «кэшировать или нет» по простым правилам: расширение в пути, `Cache-Control`, наличие `Set-Cookie`. Приложение решает «что отдать» по своим правилам роутинга и нормализации. Если приложение считает `/profile/me.css` тем же, что `/profile/me`, а кэш — «статикой», получается разрыв. Второй важный момент: кэш хранит ответ **по URL**, поэтому злоумышленник не может «закэшировать себя» — нужно, чтобы по этому URL прошёл **аутентифицированный пользователь**, чей ответ и попадёт в кэш. Отсюда социальная часть: жертву нужно привести на «обманный» URL (ссылка, картинка, редирект).

## Инструменты

**Burp Repeater** — проверять заголовки `X-Cache`, `Cache-Control`, `Age` при разных вариантах пути. Полезно перебирать расширения и разделители (`;`, `%2f`, точка). Для поиска эндпоинтов, игнорирующих лишние сегменты, помогает **ffuf**/**gobuster** с варьированием пути. И всегда проверяй финал: анонимный запрос к «обманному» URL должен вернуть приватные данные — иначе это не WCD.

## Если не сработало

Если `.css` не «обманул», пробуй другие расширения: `.js`, `.png`, `.ico`, `.woff`, `.html`, `.json`. Пробуй разделители: `;`, `%2f`, `%00`, точку, `?x=.css`, `#.css`. Иногда кэш смотрит не на расширение, а на **путь** — тогда добавь лишний сегмент (`/profile/me/anything.css`). Если приложение отдаёт `404` на «обманный» путь — значит, нормализации нет, и WCD не сработает. И проверь, требует ли кэш `Set-Cookie`-free ответ: если приложение ставит cookie на каждой странице, кэш может её не сохранить.

## Как оформить находку

Покажи четыре запроса: приватный (с сессией), «обманный» (с расширением), запрос от имени жертвы (кэширование), анонимный (чтение). Именно анонимный запрос, отдающий приватные данные, — доказательство. Укажи, какие данные утекли (email, токен, карта) и почему это ценно.

## Где это встречается в реальности

WCD — регулярная находка на сайтах за CDN (Cloudflare, CloudFront, Fastly), где правило «кэшировать статику» отдельно от «не кэшировать страницы». Особенно уязвимы приложения, которые нормализуют путь, игнорируя лишние сегменты: фреймворки с «catch-all» роутами, SPA-роутеры. Проверяй приватные страницы, которые отдают данные без явного `Cache-Control: private`.

## Частые вопросы

**«Почему нельзя закэшировать себя?»** Кэш хранит ответ по URL, но нужен **аутентифицированный** ответ. Свой профиль ты и так видишь — ценность в данных **жертвы**, поэтому её надо привести на «обманный» URL.

**«Какие расширения пробовать?»** `.css`, `.js`, `.png`, `.ico`, `.woff`, `.html`. Также разделители `;`, `%2f` и лишние сегменты пути.

## Что мы теперь знаем

- Кэш решает кэшировать по расширению и правилам, а не по «приватности».
- Если приложение нормализует путь, а кэш нет — возможен WCD.
- Кэшируется ответ **жертвы**, поэтому нужно её «привести» на URL.
- Анонимный запрос затем читает приватные данные.
- Проверка: `X-Cache: HIT` + `public` + чтение без сессии.
- Кэшируется ответ жертвы, поэтому нужен «привод» на URL.
- Защита: `Cache-Control: private`, `Vary: Cookie`, корректный роутинг.

## На что смотреть дальше

- Ищи приватные страницы, которые игнорируют лишние сегменты пути.
- Пробуй расширения `.css`, `.js`, `.png`, `.ico`, `.html`.
- Пробуй `;`, `%2f`, точку и query-трюки.
- Помни: WCD — это утечка, а не выполнение кода; импакт в данных.

## Куда дальше

Дальше мы уйдём вглубь транспорта и разберём request smuggling — расхождение парсеров между фронтендом и бэкендом, которое прячет целые запросы. А пока главное: кэш кэширует по правилам, а не по смыслу — и этим можно украсть чужие данные.

## Где пригодится

- **CTF (Web):** задачи на утечку через CDN-кэш.

- **Пентест:** аудит кэш-правил и роутинга за CDN.
- **Работа (AppSec/Dev):** `private`/`no-store`, `Vary: Cookie`, корректный роутинг.
