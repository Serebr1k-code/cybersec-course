Современные сайты говорят по **HTTP/2**. Классические CL.TE-атаки там не работают напрямую, но появляются свои: фронтенд принимает H2, а бэкенд говорит H1.1 — при **downgrade** запрос пересобирается, и рассинхронизация возвращается. Плюс специфичные для H2 вещи: **псевдо-заголовки** (`:method`, `:path`), **HPACK**-сжатие, и **Rapid Reset** (CVE-2023-44487). Этот урок — про H2-специфичную поверхность.

## Теория: H2 vs H1 и downgrade

В H2 заголовки бинарные и передаются как список пар (включая псевдо-заголовки), тело — DATA-фреймы. Фронтенд (H2-терминатор) часто **транслирует** запрос в H1.1 к бэкенду. При трансляции:

- Заголовки пересобираются в текстовый вид.
- **`content-length` может быть пересчитан или продублирован.**
- Псевдо-заголовки превращаются в request-line и обычные заголовки.

Ошибки трансляции → **H2.CL / H2.TE**: вы передаёте в H2 заголовок `content-length` (или `transfer-encoding`), который фронтенд переносит в H1.1 не так, как бэкенд читает. Это smuggling через H2.

## Теория: инъекция псевдо-заголовков и CRLF

В H2 нельзя «просто» вставить `\r\n` в значение заголовка — спецификация запрещает. Но некоторые фронтенды, транслируя H2→H1.1, **не проверяют** значения и переносят их как есть. Тогда:

```
:path: / HTTP/1.1\r\nHost: target\r\n\r\nGET /admin
```

или инъекция `\r\n` в `:path`/обычный заголовок может «разрезать» запрос на бэкенде → smuggling/request splitting. Это известный класс «HTTP/2 request smuggling via CRLF in header values».

## Теория: HPACK

**HPACK** — сжатие заголовков с динамической таблицей. Атаки:
- **HPACK bomb** — сжатый заголовок, разворачивающийся в огромный (DoS по памяти).
- **Dynamic table poisoning / desync** — рассинхронизация состояния таблицы между сторонами (редко, но встречается).
- **Header name/value confusion** при неполном соответствии реализаций.

## Теория: Rapid Reset (CVE-2023-44487)

Атака использует возможность H2 отменять потоки (`RST_STREAM`). Клиент открывает поток, сразу сбрасывает его и повторяет — сервер тратит ресурсы на обработку, но клиент «не платит» за ответ. В сочетании с большим числом потоков это даёт мощный DoS при малом трафике. Затронул почти все H2-реализации (nginx, Apache, Go, Cloudflare и др.).

**Внимание:** DoS-тесты запрещены без явного разрешения — не запускайте Rapid Reset против продакшена. Это знание для защиты/отчёта.

## Теория: h2c upgrade и cleartext

`h2c` — HTTP/2 по cleartext (без TLS), обычно через `Upgrade: h2c` или prior knowledge. Проблемы:
- `Upgrade`-заголовок может использоваться для smuggling (`Connection: Upgrade` + рассинхронизация).
- Некоторые прокси некорректно обрабатывают переход H1→h2c→H1.

## Инструменты и команды

Проверить поддержку H2 и h2c:

```bash
curl -sI --http2 https://target.local/ | head -5
curl -sI --http2-prior-knowledge http://target.local/ | head -5   # h2c
```

Burp: **HTTP/2** уже встроен (Repeater → Inspector → «HTTP/2»); **HTTP Request Smuggler** имеет H2-пробы. Для Rapid Reset — специализированные PoC (используйте только в лаборатории).

Сырой H2-запрос можно отправить `nghttp`/`h2load`:

```bash
nghttp -v https://target.local/ 2>&1 | head -30
```

## Разобранный пример: H2.CL smuggling

Шаг 1. В Burp Repeater включаем HTTP/2. Отправляем запрос с заголовком `content-length` в H2, значение которого **меньше** реального тела, и «хвостом» — второй запрос:

```
:method: POST
:path: /
content-length: 0

GET /admin HTTP/1.1
Host: target.local
```

Шаг 2. Фронтенд (H2) переносит `content-length: 0` в H1.1, бэкенд читает 0 байт тела, а `GET /admin...` остаётся в соединении → выполнится как следующий запрос. Признак: ответ не соответствует запросу / второй ответ.

Шаг 3. Эскалируем до чтения чужого запроса/ответа. В отчёте — точные H2-фреймы/заголовки и доказательство.

## Разобранный пример: CRLF в псевдо-заголовке

Шаг 1. Пробуем вставить `\r\n` в значение `:path` (через сырой H2-клиент; curl/Burp могут блокировать):

```
:path: /?x=1 HTTP/1.1\r\nHost: target.local\r\n\r\nGET /admin
```

Шаг 2. Если фронтенд не санитизирует значение при downgrade, бэкенд увидит два запроса → smuggling. Проверяем реакцию (404/200 не по адресу, два ответа).

## Частые ошибки

- **Пробовать CL.TE на H2-таргете.** Нужны H2-варианты (H2.CL/H2.TE, CRLF).
- **Забывать про downgrade.** Именно трансляция H2→H1.1 возвращает десинк.
- **Запускать Rapid Reset против прода.** DoS без разрешения — нарушение.
- **Игнорировать HPACK.** Бомбы и рассинхронизация таблицы — отдельные векторы.
- **Считать H2 «безопаснее».** Другая поверхность, не меньше риска.

## Полный разбор: H2.CL smuggling (с выводом)

End-to-end на таргете, где фронтенд по H2 транслирует запрос в H1.1.

Шаг 1. Подтверждаем H2 и downgrade. В Burp Repeater включаем HTTP/2 (Inspector → HTTP/2) и отправляем запрос с заголовком `content-length` в H2, значение которого **меньше** реального «хвоста»:

```
:method: POST
:path: /
:authority: target.local
content-length: 0

GET /admin HTTP/1.1
Host: target.local
```

Шаг 2. Наблюдаем эффект. Если фронтенд переносит `content-length: 0` в H1.1, бэкенд считает тело пустым, а `GET /admin...` остаётся в соединении и выполняется как следующий запрос:

```
HTTP/1.1 200 OK
... содержимое / (первый запрос)
HTTP/1.1 200 OK
... содержимое /admin (спрятанный запрос)
```

Признак успеха: **второй ответ** на один отправленный запрос, либо ответ не соответствует `:path`.

Шаг 3. Если прямой «двойной ответ» не виден, используйте **response-queue poisoning**: отправьте пару запросов так, чтобы спрятанный запрос попал в очередь, а следующий ваш запрос получил «сдвинутый» ответ. Доказывайте минимально и не травите чужой трафик.

Шаг 4. Альтернативный H2-вектор — **CRLF в значении псевдозаголовка** (некоторые фронтенды не санитизируют при downgrade):

```
:path: /?x=1 HTTP/1.1\r\nHost: target.local\r\n\r\nGET /admin
```

Проверяйте, что бэкенд «разрезал» запрос (два ответа / ответ не по адресу).

## Reference-таблица: H2-векторы и payload'ы

| Вектор | Что делаем | Признак |
|--------|-----------|---------|
| H2.CL | `content-length` в H2 меньше тела | двойной ответ/сдвиг |
| H2.TE | `transfer-encoding: chunked` в H2 | двойной ответ |
| H2 CRLF | `\r\n` в значении заголовка/`:path` | request splitting |
| H2 tunnelling | вложенный H1-запрос через CL | доступ к внутреннему пути |
| HPACK bomb | сжатый заголовок-бомба | DoS по памяти |
| HPACK table desync | рассинхрон динамической таблицы | некорректные заголовки |
| h2c upgrade | `Upgrade: h2c` + рассинхрон | smuggling через upgrade |
| Rapid Reset | открыть/сбросить потоки | DoS (не тестировать на проде) |

## Rapid Reset и DoS: теория и защита

**CVE-2023-44487 (Rapid Reset):** клиент открывает H2-поток (`HEADERS`), сразу отправляет `RST_STREAM` и повторяет с высокой частотой. Сервер тратит CPU/память на обработку, клиент «не платит» за ответ. Амплификация огромна при малом трафике.

**Защита:** ограничение `MAX_CONCURRENT_STREAMS`, rate-limit `RST_STREAM`, патчи серверов (nginx 1.25.3+, Go 1.21.3+, Apache, Cloudflare и др.), мониторинг аномальных сбросов.

**Важно:** DoS-тесты запрещены без явного разрешения. Знание Rapid Reset нужно для отчёта/защиты, а не для атаки на прод.

## Что делать дальше / решение

1. **Подтвердить H2** (`curl --http2`, Inspector в Burp).
2. **Определить трансляцию** (H2→H1.1) — по заголовкам/поведению.
3. **Прогнать H2-пробы** HTTP Request Smuggler (H2.CL/H2.TE/CRLF).
4. **Подтвердить** двойным ответом/сдвигом (сырые H2-фреймы).
5. **Проверить h2c и HPACK** (bomb/desync).
6. **Rapid Reset** — только теория/защита, не атаковать прод.
7. **Оформить PoC** с точными H2-заголовками и доказательством десинка.

## HPACK, h2c и дополнительные векторы

**HPACK bomb:** заголовок, который при декодировании разворачивается в огромный объём (например, через повторяющиеся ссылки на динамическую таблицу), вызывает рост памяти → DoS. Проверять только в лаборатории.

**HPACK dynamic table desync:** если фронтенд и бэкенд по-разному обновляют динамическую таблицу, состояния расходятся, и заголовки интерпретируются неверно. Встречается редко, но ведёт к десинку.

**h2c upgrade:** `Upgrade: h2c` (или prior knowledge) переводит соединение в H2 по cleartext. Прокси, некорректно обрабатывающий `Connection: Upgrade`, может дать smuggling:

```
GET / HTTP/1.1
Host: target
Connection: Upgrade, HTTP2-Settings
Upgrade: h2c
HTTP2-Settings: ...

SMUGGLED
```

**Priority/`PRIORITY`-фреймы:** манипуляции с зависимостями потоков — DoS/ресурсные атаки.

**Дополнительные приёмы:**

- **Header name confusion:** `:method`/`:path` дублирование, недопустимые значения.
- **Content-Type/`te`-манипуляции** при downgrade.
- **0-length DATA + END_STREAM** для сдвига границ.

Все эти векторы требуют сырого H2-клиента (`nghttp`, Burp, `h2`-скрипт). Проверяйте только в рамках scope и без DoS.

## Порядок тестирования H2 и защита

**Порядок:**

1. Подтвердить H2 (`curl --http2`, Inspector в Burp).
2. Определить трансляцию (H2→H1.1) и версии слоёв.
3. Прогнать HTTP Request Smuggler (Detect) с H2-пробами.
4. Подтвердить ручными H2-фреймами (двойной ответ/сдвиг).
5. Проверить h2c (`--http2-prior-knowledge`) и CRLF-инъекции.
6. Проверить HPACK-аномалии (только в лаборатории).

**Защита (для отчёта):** согласованная обработка заголовков на всех слоях, отклонение `content-length`/`transfer-encoding` в H2, санитизация значений при downgrade, патчи против Rapid Reset, лимиты `MAX_CONCURRENT_STREAMS`, мониторинг аномальных `RST_STREAM`.

## Итог по HTTP/2

H2 не «безопаснее» — у него своя поверхность: десинк при downgrade (H2.CL/H2.TE), CRLF-инъекции, HPACK-аномалии и Rapid Reset. Тестируйте сырыми H2-фреймами, подтверждайте двойным ответом, и не запускайте DoS-векторы против прода. Защита — согласованная обработка заголовков и патчи.
