## Вопрос, с которого всё начинается

Java-приложение принимает XML и превращает его в объект. В XML есть тег с именем класса:

```xml
<user class="com.example.User">
  <name>alice</name>
</user>
```

XStream видит имя класса и создаёт его экземпляр. А что если указать не `User`, а класс из стандартной библиотеки, чей конструктор или сеттер исполняет команду? Тогда XML становится оружием.

XStream — популярная библиотека сериализации Java в XML. Её удобство — читаемый формат, где имена тегов совпадают с именами полей. Её проблема — та же, что у fastjson: **тип определяется данными**, а значит, атакующий может указать любой класс.

## Как работает XStream

XStream берёт XML и восстанавливает объект: имя корневого тега или атрибут `class` задаёт класс, дочерние теги — поля. Для безопасности XStream имеет механизм `allowTypes`, но по умолчанию в старых версиях он разрешал почти всё.

Из-за этого у XStream длинная история CVE, где цепочка из доступных классов приводила к RCE. Классические gadgets — `ProcessBuilder`, `java.util.PriorityQueue` с компаратором, `sun.reflect.annotation.AnnotationInvocationHandler`. Каждый релиз закрывал один путь и оставлял другой, пока XStream не перешёл на строгий allow-list по умолчанию.

## Наш пример: XML-объект из запроса

Договоримся о примере. Эндпоинт `https://api.target/import` принимает XML и десериализует его через XStream. Проверяем базовое поведение:

```
$ curl -s -X POST https://api.target/import -H 'Content-Type: application/xml' \
  -d '<user class="com.example.User"><name>alice</name></user>'
User{name=alice}
```

Объект восстановлен. Теперь подставляем класс, чей метод исполняет команду:

```
$ curl -s -X POST https://api.target/import -H 'Content-Type: application/xml' \
  -d '<java.lang.ProcessBuilder><command><string>cat</string><string>/flag</string></command></java.lang.ProcessBuilder>'
```

Если XStream разрешает этот тип, объект `ProcessBuilder` создаётся с командой `cat /flag`, и остаётся заставить его запуститься — через цепочку или через метод, который вызывается при десериализации.

## Известные цепочки

Разберём несколько типовых цепочек XStream:

- **`ProcessBuilder` напрямую.** Создаётся объект с командой; запуск происходит, когда что-то вызывает `start()`. Часто комбинируют с классом, который вызывает метод при десериализации.
- **`PriorityQueue` с компаратором.** При восстановлении `PriorityQueue` вызывает `compare` на элементах, а компаратором может быть класс, чей `compare` исполняет код.
- **`AnnotationInvocationHandler`.** Классический gadget из Java-десериализации, применимый и в XStream.
- **Событийные классы** (`EventHandler`, `ProcessBuilder`-обёртки), где вызов происходит через рефлексию.

Выбор цепочки зависит от версии XStream и подключённых библиотек. В окружениях с Spring, Commons-Collections и подобными библиотеками доступно больше gadgets.

## Защита: только allow-list

XStream закрывает уязвимость через `allowTypes` / `allowTypesByWildcard`: разрешить можно только конкретные классы приложения. Всё остальное отвергается. Это единственный надёжный подход, потому что чёрные списки классов-гаджетов неполны по определению.

Дополнительно: не десериализовать недоверенный XML вообще; использовать более безопасные форматы (JSON с фиксированной схемой); обновлять XStream и следить за CVE. В новых версиях XStream по умолчанию запрещает опасные типы, но старые приложения остаются уязвимы.

## Что мы теперь знаем

- XStream восстанавливает объект по имени тега/атрибута `class`.
- Тип определяют данные — значит, атакующий может указать опасный класс.
- Цепочки: `ProcessBuilder`, `PriorityQueue` с компаратором, `AnnotationInvocationHandler`.
- У XStream длинная история CVE; чёрные списки неполны.
- Защита — строгий allow-list разрешённых типов.

## Механика XStream: как XML превращается в объект

Разберём внутреннюю кухню, чтобы понимать, где искать gadgets и почему защита сложна.

XStream строит из XML дерево и для каждого элемента определяет класс. Класс берётся из имени тега или из атрибута `class`, если включён режим с атрибутами. Затем XStream создаёт экземпляр: в старых версиях — через конструктор без аргументов, в новых — через `sun.reflect.ReflectionFactory`, чтобы не требовать публичного конструктора. После создания он заполняет поля: для каждого дочернего элемента находит поле с тем же именем и записывает значение, преобразуя типы при необходимости.

Опасность в том, что заполнение полей может вызывать код. Некоторые классы при установке поля инициализируют ресурсы: открывают соединение, читают файл, создают процесс. Другие срабатывают при приведении типов или при вызове `readResolve`/`readObject`. XStream вызывает эти методы в процессе восстановления, и это открывает путь к исполнению.

Второй источник опасности — **динамические прокси и рефлексия**. Если класс реализует `InvocationHandler`, XStream может создать прокси, чьи вызовы перенаправляются в заданный handler. Комбинируя прокси с классами, вызывающими методы при десериализации, строят цепочки.

Понимание этой механики объясняет, почему белый список классов — единственная надёжная защита: невозможно предсказать, какие комбинации полей и типов приведут к исполнению, если разрешено много классов.

## Разбор реальных CVE

История XStream — это десятки CVE, и в каждом виден один и тот же паттерн: находится класс в стандартной библиотеке или популярной зависимости, который при десериализации исполняет код.

Один из известных классов — `java.util.PriorityQueue`. При восстановлении он вызывает `compare` на своих элементах, чтобы поддерживать порядок. Если компаратор — это класс, чей `compare` исполняет команду, происходит RCE. Компаратор тоже передаётся в XML как объект.

Другой путь — через `com.sun.org.apache.xalan.internal.xsltc.trax.TemplatesImpl`, который компилирует и исполняет байткод XSLT/Java. Третий — через `java.beans.EventHandler`, который связывает событие с вызовом метода. Комбинируя `EventHandler` с `ProcessBuilder`, получают исполнение.

XStream закрывал эти пути по одному: добавлял классы в чёрный список, ограничивал рефлексию, вводил `allowTypes`. Но каждый раз находился новый класс, пока разработчики не сделали строгий allow-list поведением по умолчанию. Урок для защищающегося: не гнаться за чёрным списком, а инвертировать логику — разрешать только нужное.

## Как строить payload для XStream

Сборка payload для XStream проще, чем для бинарных форматов, потому что XML читаем. Порядок:

Первый шаг — определить, какие типы разрешены. Отправь XML с классом из стандартной библиотеки и посмотри, восстановится ли он. Ошибка `ForbiddenClassException` покажет, что allow-list есть, а её текст иногда перечисляет разрешённые типы.

Второй шаг — выбрать цепочку под окружение. Если доступен `ProcessBuilder`, можно попробовать прямую команду. Если он запрещён, ищи комбинации: `PriorityQueue` плюс компаратор, `EventHandler` плюс метод.

Третий шаг — собрать XML. Для `ProcessBuilder` это вложенный список строк команды. Для `PriorityQueue` — элементы и компаратор.

Четвёртый шаг — заставить цепочку сработать. Иногда требуется класс-обёртка, чей метод вызывает `start()`. Тогда `ProcessBuilder` вкладывают в него.

Пятый шаг — вернуть результат. Команду пишут в файл или используют класс, возвращающий вывод, чтобы увидеть флаг в ответе.

## Защита и её нюансы

Ключевая мера — `allowTypesByWildcard` с узкими масками: разрешать только классы приложения и необходимые DTO, ничего из `java.*`, `javax.*`, `com.sun.*`, `org.springframework.*` без явной необходимости. Новые версии XStream по умолчанию запрещают опасные типы, но конфигурация может это отключить — проверяй явно.

Дополнительно: не принимай XML от недоверенных источников; если формат обмена позволяет JSON — используй JSON с фиксированной схемой; изолируй процесс десериализации; обновляй библиотеку. И помни: безопасность XStream зависит от конфигурации, а не от версии самой по себе.

## Практические советы и типичные ошибки

Первое: XStream в разных режимах по-разному называет классы. В режиме с атрибутом класс задаётся `<obj class="...">`, в режиме с тегом — корневым тегом `<java.lang.ProcessBuilder>`. Пробуй оба.

Второе: не всякий класс сразу запускает команду. `ProcessBuilder` только создаёт описание процесса; нужен вызов `start()`. Поэтому его оборачивают в класс, который вызывает метод при десериализации, либо ищут готовую цепочку.

Третье: если видишь `ForbiddenClassException`, allow-list включён. Её текст иногда перечисляет разрешённые классы — используй эту информацию, чтобы искать обход среди разрешённых.

Четвёртое: версия XStream определяет доступные обходы. Старые версии (1.4.x) гораздо опаснее новых. Определяй версию по ошибкам.

Пятое: результат команды нужно вернуть. Пиши вывод в файл и читай его, или используй класс, возвращающий строку. Иначе RCE может сработать, но остаться незамеченным.

## Резюме

XStream превращает XML в объекты, доверяя имени класса в разметке. Это делает его мощным инструментом атаки: указав `ProcessBuilder` или класс с опасным `readObject`, можно дойти до исполнения кода. История CVE показывает, что чёрные списки неполны, и единственная надёжная защита — строгий allow-list разрешённых типов. Если ты тестируешь приложение с XStream, первым делом проверь, настроен ли `allowTypes`, и определи версию библиотеки.

Дополнительно стоит помнить, что XStream применяется не только в веб-приложениях: он встречается в интеграционных шинах, в системах обмена сообщениями и в конфигурации. Любое место, где XML из внешнего источника проходит через XStream, — потенциальная точка входа. Проверяй такие места так же внимательно, как HTTP-эндпоинты.



Помни также, что XStream можно настроить на безопасный режим одной строкой конфигурации, и это стоит рекомендовать в отчёте как конкретную меру устранения.
