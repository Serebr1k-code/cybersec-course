## Вопрос, с которого всё начинается

SharePoint — это не «сайт для документов», а **платформа**: на ней строят интранеты, порталы, хранилища. Внутри — .NET, десятки эндпоинтов `/_layouts/`, интеграция с AD. Именно поэтому SharePoint годами держится в топе целей: его RCE-цепочки дают контроль над сервером в домене. Разберём, как подступиться.

## Наш пример: интранет-портал на SharePoint

Цель — `https://intranet.target.example`. Фингерпринт:

```
$ whatweb -a 3 https://intranet.target.example
https://intranet.target.example [200 OK] SharePoint, ASP.NET,
  Set-Cookie[FedAuth=...], X-SharePointHealthScore[0]
```

Заголовок `X-SharePointHealthScore` и cookie `FedAuth` — явные признаки SharePoint. Версию определяем по эндпоинтам:

```
$ curl -s https://intranet.target.example/_layouts/15/start.aspx | grep -io 'microsoft sharepoint [0-9]*'
Microsoft SharePoint 2019
```

Версия **2019** (или Subscription Edition). Дальше — сопоставление с CVE.

## Шаг 1: ToolShell и обход аутентификации

**ToolShell** — семейство цепочек в SharePoint, где через подделку токена аутентификации (или неверную проверку подписи) атакующий получает доступ к административным функциям без учётных данных. Идея: SharePoint доверяет определённым токенам/эндпоинтам, и если проверка подписи слабая (или ключ утёк), токен подделывается.

Проверка безопасная: запрос к эндпоинту `/_layouts/15/...` без cookie и наблюдение, отдаёт ли он данные вместо редиректа на логин.

## Шаг 2: ViewState-десериализация

SharePoint, как и любое ASP.NET-приложение, использует **ViewState**. Если известен `machineKey` (ключ подписи), можно подписать произвольный ViewState и добиться десериализации .NET-гаджета — это RCE. Инструмент — `ysoserial.net`:

```
$ ysoserial.exe -g TypeConfuseDelegate -f LosFormatter -c "cmd /c whoami"
```

`machineKey` добывается из `web.config` (если есть чтение файлов) или через известные утечки. Без ключа ViewState-атака не работает — ASP.NET проверяет подпись.

## Шаг 3: RCE через веб-части и страницы

Если удалось войти (или обойти аутентификацию), путь к RCE идёт через **расширяемость**: SharePoint позволяет загружать веб-части (`.webpart`, `.dwp`) и страницы. Вредоносная веб-часть содержит .NET-код, который исполняется сервером. Альтернатива — загрузка `.aspx`-страницы в библиотеку, доступную для исполнения.

Типовая цепочка: обход аутентификации → доступ к `/` → загрузка веб-части с кодом → RCE.

## Шаг 4: утечки конфигурации

SharePoint-конфиги (`web.config`, `applicationHost.config`) содержат `machineKey`, строки подключения и ключи. Если есть LFI/traversal или открыт бэкап — конфиг добывается, и ViewState-атака становится прямой. Поэтому конфиг — цель номер один после получения доступа к файловой системе.

## Шаг 5: автоматизация

```
$ nuclei -u https://intranet.target.example -tags sharepoint -silent
[CVE-2021-XXXX] [http] [critical] https://intranet.target.example/_layouts/15/...
```

Плюс ручная проверка версии и эндпоинтов.

## Шаг 6: как не навредить

SharePoint-интранет критичен: его падение останавливает документооборот. Поэтому: без массовых запросов, без деструктивных payload'ов, ViewState-тесты — на стенде или с безобидным маркером. SharePoint под мониторингом (Defender/SIEM), шум = раскрытие.

## Шаг 7: чек-лист по SharePoint

1. Версия (`/_layouts/15/`, заголовки).
2. Обход аутентификации (ToolShell-эндпоинты).
3. Точки десериализации (ViewState).
4. Утечка `machineKey`/конфигов.
5. Возможность загрузки веб-части.
6. Сопоставление с CVE.

## Что мы теперь знаем

- SharePoint узнаётся по `X-SharePointHealthScore` и `FedAuth`.
- ToolShell — обход аутентификации через подделку/слабость токена.
- `machineKey` + ViewState = RCE.
- Веб-части и страницы — путь к RCE после входа.
- Конфиг — цель номер один для получения ключей.

## Шаг 8: как искать ToolShell-эндпоинты

ToolShell-цепочки опираются на конкретные эндпоинты и на то, как SharePoint проверяет подпись токена. Чтобы не гонять PoC вслепую, сначала составь карту эндпоинтов: перечисли доступные `/_layouts/15/*.aspx`, `/_vti_bin/*.asmx`, `/api/*`. Затем проверь, какие из них отвечают **без cookie** (то есть не редиректят на логин). Именно среди них ищут обходы. Так ты находишь точку входа до того, как подбирать payload.

## Шаг 9: как оценивать импакт SharePoint-находки

Обход аутентификации = доступ к внутренним документам (высокий). RCE через ViewState = контроль сервера в домене (критический). Утечка `machineKey` = RCE-путь (критический). Доступ к конфигу с кредами = путь к БД и AD (высокий). В отчёте указывай конкретику: какой эндпоинт, какой ключ, какая команда исполнена, к каким данным получен доступ.

## Шаг 10: как защититься от SharePoint-атак

Защита: своевременные обновления (Microsoft выпускает security-патчи ежемесячно); уникальный `machineKey` для каждого сервера; ограничение доступа к `/_layouts/` для неаутентифицированных; включение аудита. Для атакующего: пропатченный SharePoint закрывает известные ToolShell-цепочки, и работа смещается к конфигурации и сторонним решениям.

## Шаг 11: как проверить версию SharePoint надёжно

Баннер может врать. Надёжнее — сравнить состав статики: имена файлов в `/_layouts/15/` и `/_layouts/16/` меняются между версиями. Плюс `/_vti_inf.html` и `/_vti_bin/_vti_aut/author.dll` (WebDAV) выдают поколение. Совокупность признаков (заголовки + пути + статика) даёт точную версию, от которой пляшет CVE-поиск.

## Шаг 12: как закрепиться, не создавая шума

Если цель — закрепление, а не разовый RCE, предпочтительны механизмы, встроенные в продукт (например, легитимные задачи/вебхуки), а не файловые веб-шеллы, которые легко находят. Но помни: на критичной корпоративной системе закрепление допустимо только при явном разрешении заказчика.

## Шаг 13: как связать SharePoint с другими системами

SharePoint — это часто «хаб»: через него открывают документы из OneDrive, общаются в Teams, ходят в другие сервисы Microsoft 365. Компрометация SharePoint-сервера даёт доступ к токенам SSO и интеграциям, а значит — к почте, файлам и иногда к Azure. Поэтому после получения доступа к SharePoint проверяй, какие сервисы он интегрирует, и какие токены хранит.

## Шаг 14: типовые ошибки при работе с SharePoint

Ошибка первая — считать код `200` доказательством доступа (мягкие 404). Вторая — гонять ViewState-payload'ы без ключа (бесполезно). Третья — игнорировать конфиг: `machineKey` — это половина атаки. Четвёртая — шумная эксплуатация на проде: SharePoint под Defender/SIEM, и подозрительные `/_layouts/` запросы логируются и алертят.
