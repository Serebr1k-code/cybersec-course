## Вопрос, с которого всё начинается

Внутри сети стоит Gitea — self-hosted репозиторий кода, куда команда пушит свои проекты. Снаружи он выглядит как «просто git». Но репозиторий — это исходники всего продукта, конфиги деплоя и часто случайно закоммиченные секреты. Если он открыт анонимно, ты получаешь весь код без единого логина. Разберём, что искать и как.

## Что такое Gitea и Gogs

**Gitea** — лёгкий self-hosted сервис Git (форк **Gogs**). Он даёт веб-интерфейс, REST API, управление пользователями и, что важно, **хуки** — скрипты, которые запускаются на сервере при событиях Git (пуш, создание репозитория). Хуки — это механизм исполнения кода по дизайну: если атакующий может их создать, он получает RCE.

Gitea/Gogs часто разворачивают в докере на порту 3000, с настройками по умолчанию. Отсюда две частые проблемы: **анонимный доступ** к репозиториям и **слабые права** у обычного пользователя.

## Наш пример: Gitea 1.21.0

Цель — `http://gitea.target.example:3000`. Определяем продукт и версию:

```
$ curl -s http://gitea.target.example:3000/api/v1/version
{"version":"1.21.0"}
```

`/api/v1/version` — открытый эндпоинт, он не требует авторизации. Версия **1.21.0**; сверяем с CVE Gitea.

## Шаг 1: анонимное перечисление репозиториев

Проверяем, что видно без логина:

```
$ curl -s 'http://gitea.target.example:3000/api/v1/repos/search' | head -c 300
{"data":[{"id":1,"name":"backend","full_name":"dev/backend","private":false,...}]}
```

`"private":false` — репозитории публичны для анонимов. Это уже утечка исходников: ты видишь структуру проектов, имена, ветки. Дальше читаем содержимое.

## Шаг 2: читаем файлы и ищем секреты

Каждый репозиторий доступен через raw-эндпоинт:

```
$ curl -s 'http://gitea.target.example:3000/dev/backend/raw/branch/main/config/database.yml'
production:
  host: db.internal
  username: app
  password: Pr0dDBpass!
```

Вот типичная находка: конфиг деплоя с паролем к продовой базе. Разработчики коммитят такое постоянно — в `.env`, `docker-compose.yml`, `config/*.yml`, CI-файлах. Это и есть главная ценность открытого SCM: **секреты в исходниках**.

## Шаг 3: ищем API-токены и CI-переменные

Дальше — то, что открывает путь в CI. В репозитории ищи файлы `.github/workflows/`, `.gitlab-ci.yml`, `.drone.yml` — там могут быть токены. А в настройках пользователя — API-токены. Если токен утёк, через API можно читать приватные репозитории, создавать хуки и менять код.

## Шаг 4: RCE через git-хуки

Если у тебя есть **права на создание хука** (свой репозиторий или админ), Gitea выполняет скрипт на сервере. CVE-2020-14144 — как раз RCE через хук: атакующий с правом создания репозитория создаёт pre-receive-хук с командой, и она исполняется от пользователя Gitea.

```
# в настройках репозитория -> Git Hooks -> pre-receive
#!/bin/sh
id > /tmp/pwned
```

Для пентеста это ключевой момент: обычный пользователь Gitea может получить RCE, если права позволяют создавать хуки.

## Шаг 5: слабости старых Gogs

У Gogs есть свои CVE: обход аутентификации в старых версиях, RCE через загрузку и обработку репозитория. Если версия старая (0.11.x и раньше) — проверь известные цепочки. Признак: Gogs отдаёт `X-Powered-By: Gogs` или характерный `/user/login`.

## Шаг 6: пост-эксплуатация

Из Gitea достают: исходники (аудит логики), секреты (креды БД/облака), токены CI, SSH-ключи деплоя. Часто именно через репозиторий находят путь в прод: в CI-файле — команда деплоя, в конфиге — ключи. SCM — это начало конвейера, а значит, и начало атаки.

## Что мы теперь знаем

- Gitea/Gogs — self-hosted Git с REST API и хуками.
- Анонимный доступ отдаёт исходники и секреты.
- В репозиториях ищут конфиги, `.env`, CI-файлы, токены.
- Хуки — механизм RCE (CVE-2020-14144).
- SCM — начало CI/CD-конвейера, оттуда идут вглубь.

## Разбираем анатомию репозитория как источника секретов

Чтобы находить секреты быстро, нужно знать, **куда** смотреть. В типовом репозитории чувствительные данные лежат не в коде, а в служебных файлах:

- `.env`, `.env.production` — переменные окружения с паролями и ключами.
- `docker-compose.yml`, `Dockerfile` — образы и креды к registry.
- `config/*.yml`, `settings.py`, `application.properties` — конфиги приложений с доступами к БД.
- `.github/workflows/*.yml`, `.gitlab-ci.yml`, `.drone.yml` — CI-пайплайны, где бывают токены деплоя.
- `id_rsa`, `*.pem`, `*.key` — приватные ключи (редко, но бывает).
- `terraform.tfstate` — состояние инфраструктуры с секретами облака.
- `.git/config` — иногда содержит URL с встроенными кредами.

Хорошая практика при пентесте SCM: не читать весь код, а **грепать по шаблонам**. Ищи строки вида `password=`, `secret`, `token`, `api_key`, `BEGIN PRIVATE KEY`. В Gitea это делается через API поиска или через клонирование и локальный grep.

## Шаг 7: проверить настройки на утечки

Помимо файлов, у Gitea есть настройки, которые иногда открыты анонимно. Проверь `/api/v1/settings/api`, `/api/v1/settings/ui` — там видны параметры инстанса, включая разрешённые регистрации. Если регистрация открыта, можно создать пользователя и получить легитимный доступ к приватным репозиториям. Это уже не утечка, а полноценный вход.

```
$ curl -s http://gitea.target.example:3000/api/v1/settings/api
{"max_response_items":50,"default_paging_num":30,"default_git_trees_per_page":1000}
```

## Шаг 8: как отличить Gitea от GitLab

Обе системы — SCM, но CVE и векторы разные. Gitea: лёгкий Go-сервис, `/api/v1/version`, порт 3000, характерный минималистичный UI. GitLab: Ruby/Go, `/api/v4/version`, порт 80/443, тяжёлый интерфейс, свои CVE (CVE-2021-22205 ExifTool RCE, CVE-2023-2825 traversal). Определяй продукт до атаки: payload'ы не взаимозаменяемы.

## Шаг 9: что писать в отчёте

Отчёт по SCM фиксирует: продукт и версию; факт анонимного доступа (что именно видно); **список утёкших секретов** (тип, но не сами значения целиком); какие системы они открывают; рекомендацию (закрыть анонимный доступ, ротировать утёкшие секреты, включить 2FA, аудит коммитов на секреты).

## Ошибки и антипаттерны

Первая — выкачивать все репозитории целиком: это гигабайты и заметно. Достаточно найти несколько секретов как доказательство. Вторая — публиковать найденные пароли в открытом виде: маскируй их в отчёте. Третья — считать «публичный репозиторий» безобидным: именно в публичных чаще всего лежат забытые `.env`.

## Практика: клонирование и локальный поиск секретов

Ручной обход API хорош для точечной проверки, но для поиска секретов удобнее склонировать репозиторий и грепать локально. В лабе роль `git` играет эмуляция, но принцип тот же:

```
$ git clone http://gitea.target.example:3000/dev/backend.git
$ cd backend
$ grep -rIn --exclude-dir=.git -E 'password|secret|token|api_key|BEGIN .* PRIVATE KEY' .
```

Так за секунды находятся все чувствительные строки. В реальном пентесте это первый шаг после обнаружения открытого SCM: клонируй и грепай. Часто в выводе сразу видны креды к базе, облаку и CI.

## Практика: как использовать найденный токен CI

Допустим, в CI-файле найден токен деплоя. Дальше проверяют, что он открывает: registry, облако, прод-сервер. Но делать это надо **аккуратно** — только читающие операции. Например, для registry — список образов, для облака — `sts get-caller-identity`. Доказательство — факт валидности токена, а не полный доступ. Это ключ к этичному пентесту: демонстрируй, не разрушай.

## Практика: как не пропустить секреты при аудите SCM

Опытный пентестер не читает код построчно — он работает по чек-листу. Сначала грепает по именам файлов: `.env`, `*.key`, `*.pem`, `id_rsa`, `credentials`, `secrets`. Потом по содержимому: `password`, `passwd`, `secret`, `token`, `apikey`, `Authorization`, `BEGIN RSA`. Затем смотрит историю коммитов: секреты часто удаляют из текущего кода, но они остаются в старых коммитах (`git log -p`). И наконец проверяет CI-файлы — там бывают токены деплоя.

В Gitea всё это доступно через API и raw-эндпоинты. Даже если анонимный доступ ограничен, обычный пользователь видит публичные репозитории и свою организацию. А утечка одного `.env` с продовыми кредами уже достаточна для отчёта уровня high.
