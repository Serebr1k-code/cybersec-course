## Вопрос, с которого всё начинается

Корпоративная сеть держится не на сайтах-визитках, а на **приложениях-платформах**: SharePoint для документов, Exchange для почты, Confluence и Jira для знаний и задач, WebLogic для Java-сервисов, vCenter для виртуализации, Citrix для удалённого доступа. Каждое из них — это одновременно «рабочий инструмент» и «большая цель», потому что за ним стоят данные и инфраструктура. Сегодня разберём, чем эти приложения отличаются от CMS и как их атаковать системно.

## Что такое корпоративные веб-приложения

Это класс систем, которые разворачивают **внутри компании** и дают сотрудникам общий доступ к данным и функциям. Их объединяют три черты. Первая: **они стоят за VPN или в внутренней сети**, то есть их обычно не видно из интернета напрямую — но как только ты получил доступ во внутреннюю сеть (через SSRF, фишинг, скомпрометированный хост), они становятся доступны. Вторая: **у них есть аутентификация на базе AD** (Kerberos/NTLM/LDAP), то есть они связаны с доменом. Третья: **они уязвимы к RCE-классам** — десериализация, инъекции шаблонов, обход аутентификации.

Именно третья черта делает их приоритетной целью: RCE на таком приложении часто означает **контроль над сервером в домене**, а значит — путь к домен-админу.

## Наш пример: находим Confluence в сети

Допустим, мы получили доступ во внутреннюю сеть и видим хост `10.10.10.50`. Сканируем порты и находим веб:

```
$ nmap -sV -p 80,443,8080 10.10.10.50
8080/tcp open  http  Atlassian Confluence 8.5.3
```

Баннер прямо говорит: **Confluence 8.5.3**. Это уже точная версия — а значит, мы можем сопоставить её с базой CVE. Дополнительно проверяем:

```
$ curl -s http://10.10.10.50:8080/login.action | grep -io 'confluence [0-9.]*'
Confluence 8.5.3
```

Теперь у нас есть и продукт, и версия. Дальше — CVE-дисциплина.

## Шаг 1: почему у этих приложений «плохая репутация»

Причина в **архитектуре**. SharePoint, Exchange, Confluence, Jira, WebLogic — большие Java/.NET-приложения с плагинами, сериализацией, шаблонизацией и десятками эндпоинтов. Каждая из этих технологий — потенциальный RCE:

- **десериализация** (Java: WebLogic T3/IIOP; .NET: ViewState) — RCE при доступе к потоку;
- **инъекция шаблонов** (Confluence OGNL, Jira Velocity) — RCE через выражение;
- **обход аутентификации** — доступ без пароля (Exchange ProxyLogon, Confluence CVE-2023-22515);
- **SSRF** — хождение по внутренним URL (Jira, Confluence).

Поэтому история этих продуктов — это история критических CVE, которые эксплуатируются в реальных атаках (APT, ransomware).

## Шаг 2: CVE-дисциплина — главный навык

Для корпоративных приложений версия решает всё. Рабочий процесс такой:

1. **Определить продукт и точную версию** (баннер, статика, эндпоинты).
2. **Сопоставить с CVE** (NVD, вендорские security-бюллетени).
3. **Найти публичный PoC** и **прочитать его**.
4. **Проверить безопасно** (неразрушающий запрос).
5. **Эксплуатировать** только при подтверждении и разрешении.

Ключевая ошибка новичка — пропустить шаг 1 и «пробовать эксплойты наугад». Это и медленно, и опасно (можно уронить сервис).

## Шаг 3: инфраструктурный контекст — что за приложением

Корпоративное приложение почти никогда не стоит одно. За Exchange — Active Directory (почтовые ящики = учётки домена). За vCenter — весь парк виртуальных машин. За Citrix — удалённый доступ сотрудников. За WebLogic — Java-сервисы, которые могут ходить в БД и другие системы.

Поэтому, атакуя такое приложение, ты атакуешь **узел инфраструктуры**. Из этого следует: (1) импакт максимальный; (2) риск максимальный — приложение критично для бизнеса, и его падение недопустимо; (3) после RCE открывается путь дальше (в домен, в другие сервисы).

## Шаг 4: план атаки на корпоративное приложение

Универсальный план:

1. **Обнаружение** — nmap/httpx по внутренней сети, баннеры продуктов.
2. **Версия** — точная, из баннера/статики/API.
3. **CVE** — сопоставление, выбор подходящих.
4. **PoC** — поиск, чтение, санитизация (репойнт колбэков).
5. **Проверка** — неразрушающая.
6. **Эксплуатация** — при подтверждении, с сохранением доказательств.
7. **Пост-эксплуатация** — дамп конфигов, поиск кред, движение к домену.

## Шаг 5: как не навредить и не раскрыться

Корпоративные приложения под **мониторингом** (SIEM, EDR, SOC). Шумные сканы и деструктивные payload'ы приводят к блокировке и раскрытию. Поэтому: точечные проверки; без массовых запросов; без `DROP`/удаления; без создания реальных пользователей; SSRF — на свой слушатель. И всегда помни: **цель должна остаться живой** — падение Exchange или vCenter остановит бизнес и тебя поймают.

## Что мы теперь знаем

- Корпоративные приложения (SharePoint, Exchange, Confluence, WebLogic, vCenter, Citrix) — узлы инфраструктуры, а не «сайты».
- Их объединяют AD-аутентификация и RCE-классы (десериализация, шаблоны, обход аутентификации, SSRF).
- Версия → CVE → PoC → безопасная проверка → эксплуатация.
- За приложением стоит инфраструктура (домен, VM, сервисы).
- Мониторинг делает шумные атаки опасными.

## Шаг 6: как искать корпоративные приложения в сети

Корпоративные приложения обычно не видны из интернета, поэтому их ищут изнутри. Рабочий конвейер: получив доступ во внутреннюю сеть, сканируй веб-порты (80/443/8080/8443/8000/9000) и снимай баннеры:

```
$ nmap -p 80,443,8080,8443,8000,9000 --open -sV 10.10.10.0/24 -oX web.xml
$ httpx -l hosts.txt -title -tech-detect -status-code
```

Затем классифицируй находки по продукту: Exchange (OWA), SharePoint (`X-SharePointHealthScore`), Confluence/Jira (`JSESSIONID`, Atlassian), WebLogic (`/console`), vCenter (`/ui`), Citrix (Netscaler). Каждый продукт — отдельный набор CVE. Так внутренняя сеть превращается в список целей с версиями.

## Шаг 7: как читать вендорские security-бюллетени

У Microsoft и Atlassian есть публичные бюллетени (MSRC, Atlassian Security Advisories). Читая их, обращай внимание на: **диапазон уязвимых версий**, **тип уязвимости** (RCE/обход), **наличие аутентификации** (pre-auth важнее) и **уровень CVSS**. Именно эти поля определяют, стоит ли вообще связываться с целью. Правило: сначала сопоставь версию с бюллетенем, потом ищи PoC — не наоборот.

## Шаг 8: как расставить приоритеты между приложениями

Не все корпоративные приложения равны. Приоритет выше, если: (1) приложение даёт доступ к **учётным записям домена** (Exchange, SharePoint, vCenter); (2) за ним **данные клиентов** (CRM-интеграции); (3) уязвимость **pre-auth** (без пароля). Ниже приоритет, если приложение изолировано и данных в нём нет. Это распределение усилий по ожидаемой ценности — не тратить часы на бесперспективный сервис.

## Куда дальше

Дальше — конкретные приложения: SharePoint и Exchange (ProxyLogon), Confluence и Jira (OGNL/шаблоны), WebLogic и vCenter (десериализация). А пока запомни: **это узлы инфраструктуры — версия, CVE, аккуратность.**

## Где пригодится

- Пентест внутренней сети: эти приложения — первое, что ищут после получения доступа.
- Red team: путь к домену через RCE на приложении.
- CTF: задания с конкретным CVE корпоративного продукта.
