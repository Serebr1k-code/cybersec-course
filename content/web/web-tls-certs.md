В прошлом уроке мы ходили по `http://shop.local` — всё было видно в открытом виде. Но в реальном интернете пароли и cookie передаются по HTTPS. Что это такое и почему иногда браузер кричит «соединение не защищено»?

В этом уроке мы возьмём тот же `shop.local`, но уже по `https://`, и разберём **одну** цепочку: как устанавливается защищённое соединение, что внутри сертификата и как проверить, что сайт настроен правильно.

## Наш пример: то же соединение, но по HTTPS

Попробуем подключиться:

```bash
$ curl -v 'https://shop.local/' 2>&1 | head -20
* Trying 203.0.113.10:443...
* Connected to shop.local (203.0.113.10) port 443
* ALPN: offers h2, http/1.1
* TLSv1.3 (OUT), TLS handshake, Client hello (1):
* TLSv1.3 (IN), TLS handshake, Server hello (2):
* TLSv1.3 (IN), TLS handshake, Certificate (11):
* SSL certificate problem: certificate has expired
* Closing connection
```

curl остановился и написал: **`certificate has expired`** — «срок действия сертификата истёк». Раньше мы получили HTML, а теперь — ошибку. Значит, HTTPS — это не просто «HTTP с шифрованием»: перед обменом данными клиент обязан проверить **сертификат** сервера. Разберёмся, что это.

## Шаг 1: что происходит при соединении

Строки `TLS handshake` — это **рукопожатие TLS**: клиент и сервер договариваются о шифровании. Упрощённо:

1. Клиент шлёт `Client hello` — список поддерживаемых версий и шифров.
2. Сервер отвечает `Server hello` и присылает **сертификат**.
3. Стороны договариваются о ключах и переходят к шифрованным данным.

**Сертификат** — это электронный документ, которым сервер доказывает: «я действительно `shop.local`, и это подтвердил удостоверяющий центр (CA, Certificate Authority)». Клиент проверяет подпись CA, срок действия и имя. Если что-то не сходится — соединение обрывается, как у нас.

TLS даёт три вещи: **шифрование** (никто не подслушает), **целостность** (никто не подменит) и **аутентификацию сервера** (мы точно говорим с тем сайтом, за который он себя выдаёт).

## Шаг 2: смотрим сам сертификат

Ошибку надо разобрать. Запросим сертификат и распечатаем его поля:

```bash
$ echo | openssl s_client -connect shop.local:443 -servername shop.local 2>/dev/null \
    | openssl x509 -noout -subject -issuer -dates
subject=CN = shop.local
issuer=C = US, O = Let's Encrypt, CN = R3
notBefore=Jan  1 00:00:00 2025 GMT
notAfter=Apr  1 00:00:00 2025 GMT
```

`openssl s_client` делает TLS-соединение и отдаёт сертификат, а `openssl x509` печатает его поля. Читаем:

- `subject=CN = shop.local` — **кому выдан** сертификат (какое имя он подтверждает).
- `issuer=… Let's Encrypt …` — **кто подписал** (какой CA).
- `notAfter=Apr 1 …` — дата окончания. Она уже прошла — вот причина ошибки.

Что делать на практике: сертификат с истёкшим сроком ломает не только браузер, но и мобильные приложения (которые часто «пинят» сертификат и падают при несовпадении). Это валидная находка low/medium.

## Шаг 3: имя хоста и SNI

Частая ошибка — смотреть только поле `CN`. Современные браузеры проверяют **`SAN`** (`subjectAltName`) — список имён, для которых сертификат действителен:

```bash
$ echo | openssl s_client -connect shop.local:443 -servername shop.local 2>/dev/null \
    | openssl x509 -noout -ext subjectAltName
X509v3 Subject Alternative Name:
    DNS:shop.local, DNS:www.shop.local, DNS:admin.shop.local
```

Интересно: в списке есть `admin.shop.local`. Значит, у магазина есть админ-поддомен, о котором мы не знали. Так сертификаты помогают в разведке: их выдают на все имена сайта, и они публичны (см. Certificate Transparency в конце урока).

Второе важное слово — **SNI** (`Server Name Indication`). На одном IP живёт много сайтов; клиент сообщает нужное имя прямо в рукопожатии. Флаг `-servername` задаёт его вручную. Если его не указать, сервер отдаст «сертификат по умолчанию» — и ты получишь ложное «несовпадение имени». Проверь поддомен отдельно:

```bash
$ echo | openssl s_client -connect 203.0.113.10:443 -servername admin.shop.local 2>/dev/null \
    | openssl x509 -noout -subject
subject=CN = admin.shop.local
```

Сертификат для `admin.shop.local` существует — поддомен реальный, хотя DNS мы не знали.

## Шаг 4: HSTS и редирект HTTP → HTTPS

Даже с хорошим сертификатом первый запрос может уйти по HTTP. Проверим, есть ли перенаправление и заголовок **HSTS** (`Strict-Transport-Security`), который приказывает браузеру всегда ходить только по HTTPS:

```bash
$ curl -s -I 'http://shop.local/' | grep -iE '^(location|strict-transport-security)'
location: https://shop.local/
strict-transport-security: max-age=31536000; includeSubDomains
```

Оба есть — значит, настроено хорошо. А теперь «плохой» случай, когда их нет:

```bash
$ curl -s -I 'http://legacy.shop.local/' | grep -iE '^(location|strict-transport-security)'
# (пусто)
```

Ни редиректа, ни HSTS. Тогда первый запрос жертвы уходит по HTTP открытым текстом — и его можно перехватить в сети (например, в публичном Wi-Fi). Это классическая связка с cookie без флага `Secure`: сессия утекает. Поэтому HSTS без HSTS называют находкой среднего уровня.

## Шаг 5: что ещё бывает не так

Быстрый аудит TLS делается инструментом `sslscan`:

```bash
$ sslscan shop.local:443 | grep -iE 'SSLv3|TLSv1\.0|TLSv1\.1|RC4|3DES'
```

Любая строка «Enabled» для `SSLv3`/`TLS1.0`/`TLS1.1` или слабого шифра (`RC4`, `3DES`) — находка: такие протоколы устарели, их можно взломать (downgrade-атака). Минимальный набор проверок:

- сертификат: срок, `SAN`, подпись CA (не SHA-1);
- HSTS и редирект HTTP → HTTPS;
- устаревшие протоколы и шифры;
- флаги `Secure`/`HttpOnly`/`SameSite` у cookie (см. урок про cookie).

Отдельно проверяй TLS на нестандартных портах (`8443`, `9443` и портах из `nmap`): внутренние панели и dev-стенды часто остаются со слабой конфигурацией и выпадают из общего аудита. Найденные имена из `SAN` стоит сразу проверить резолвом — так вскрываются внутренние сервисы, доступные только по имени.

## Разведка через Certificate Transparency

Каждый выданный сертификат попадает в публичные логи **Certificate Transparency**, и их можно искать:

```bash
$ curl -s 'https://crt.sh/?q=%25.shop.local&output=json' | jq -r '.[].name_value' | sort -u
admin.shop.local
staging.shop.local
internal-api.shop.local
```

Так вскрываются поддомены, которых нет в DNS-выдаче. Найденное имя проверяй SNI-запросом (шаг 3): если сертификат для него есть — сервис реален, даже если DNS о нём молчит.

## Что мы теперь знаем

- HTTPS = HTTP внутри шифрованного туннеля TLS.
- TLS даёт шифрование, целостность и аутентификацию сервера — через сертификат.
- Сертификат проверяют по имени (`SAN`, а не только `CN`), сроку и подписи CA.
- `SNI` выбирает нужный виртуальный хост; сертификаты помогают искать скрытые поддомены.
- HSTS + редирект на HTTPS + флаг `Secure` у cookie закрывают перехват по сети.

## На что смотреть дальше

- **mTLS.** Если сервер требует клиентский сертификат — проверь, обязателен ли он и нельзя ли обойти его заголовком (`X-Client-Cert`), которому доверяет прокси.
- **Certificate pinning.** Мобильные приложения «пинят» сертификат; при проксировании запрос падает — это hardening, а не уязвимость.
- **Нестандартные порты.** TLS бывает на 8443/9443 — они часто остаются со слабой конфигурацией и вне аудита.

## Куда дальше

Мы научились проверять защищённое соединение. Теперь мы уверены, что трафик идёт по HTTPS, — значит, смотреть на отдельные запросы бессмысленно без понимания, **какие вообще компоненты** стоят за сайтом: прокси, приложение, база данных. Этим займёмся в следующем уроке про архитектуру. А пока запомни: **сертификат — это паспорт сервера; проверяй срок, SAN и подпись, а HSTS и `Secure` закрывают перехват.**

## Где пригодится

- **CTF (Web):** SNI-виртуалхостинг часто скрывает «секретный» поддомен с флагом; слабый TLS — часть задач на конфиг.
- **Bug bounty:** отсутствие HSTS, слабые шифры, истёкшие сертификаты — валидные low/medium находки.
- **Пентест:** аудит TLS — обязательный пункт внешнего сканирования периметра.
- **Работа (SOC/IR):** анализ сертификатов и SNI помогает в детекте C2-трафика и выявлении фишинговых доменов.
