Access-токены живут минуты, а refresh-токены — дни/месяцы: ими продлевают сессию. Ошибки в lifecycle refresh-токена дают **долгоживущий захват аккаунта**. Ключевые механизмы: **ротация** (каждый refresh выдаёт новый refresh и инвалидирует старый) и **reuse detection** (повторное использование старого токена = сигнал кражи, вся цепочка отзывается). Если этого нет — украденный refresh-токен даёт вечный доступ.

## Теория: как должен работать refresh

1. Логин → выдают `access` (5–15 мин) + `refresh` (дни).
2. Когда `access` истёк → `POST /token` с `grant_type=refresh_token` → новый `access` **и новый `refresh`**.
3. Старый `refresh` инвалидируется.
4. Если приходит **старый** refresh (уже использованный) → это сигнал кражи → отозвать **всю** цепочку.

Уязвимости:
- **Нет ротации** — один refresh живёт вечно.
- **Нет reuse detection** — украденный refresh неотличим.
- **Слабый токен** — предсказуем.
- **Не привязан к клиенту/устройству** — работает из любого места.
- **Хранится в localStorage** — XSS крадёт.
- **Не инвалидируется при logout/смене пароля**.

## Атака 1: отсутствие ротации

```bash
# обмениваем refresh -> получаем access
curl -s -X POST https://idp.example/token \
  -d "grant_type=refresh_token&refresh_token=R1&client_id=app"
# -> {access:A2, refresh:R1}  (тот же R1 -> нет ротации)

# повторно используем R1
curl -s -X POST https://idp.example/token \
  -d "grant_type=refresh_token&refresh_token=R1&client_id=app"
# -> снова access -> R1 бессмертен
```

Если R1 работает бесконечно — украденный refresh = вечный доступ.

## Атака 2: обход reuse detection

Даже с ротацией бывают дыры:
- **Race:** два параллельных refresh со старым токеном; оба проходят до инвалидации.
- **Не отзывается цепочка** при reuse — только конкретный токен.
- **TTL grace period** слишком широкий.
- **Смена `client_id`** обходит привязку.

```bash
# параллельные refresh одним токеном (race)
seq 2 | xargs -P2 -I{} curl -s -X POST https://idp.example/token \
  -d "grant_type=refresh_token&refresh_token=R1&client_id=app"
# если оба выдали новые -> reuse detection обойдён
```

## Атака 3: слабая привязка и кража

- **Refresh в URL/Referer** — утечка.
- **Refresh в localStorage** — XSS (см. `web-xss`).
- **Refresh не привязан к device_id/IP/user-agent** — работает из любого места.
- **Refresh валиден после logout/смены пароля** — старый токен жив.
- **Refresh выдаётся на публичный client без client_secret** — перехват.

## Атака 4: scope/lifetime escalation

- Refresh выдаёт access с **большим** scope, чем изначально.
- Refresh не имеет абсолютного срока (вечный).
- Refresh можно использовать для получения токена другого пользователя при IDOR.

## Разобранный пример: вечный доступ

Шаг 1. Крадём refresh (XSS/логи/утечка). Проверяем его жизнь:

```bash
curl -s -X POST https://idp.example/token \
  -d "grant_type=refresh_token&refresh_token=STOLEN&client_id=app"
# -> access
```

Шаг 2. Ждём/меняем — используем повторно:

```bash
sleep 60
curl -s -X POST https://idp.example/token \
  -d "grant_type=refresh_token&refresh_token=STOLEN&client_id=app"
# -> снова access, если нет ротации
```

Шаг 3. Даже если жертва сменила пароль — проверяем, жив ли токен. Если да — постоянный доступ.

## Проверка lifecycle (чек-лист)

1. Ротация: меняется ли refresh при каждом использовании?
2. Reuse detection: что происходит при повторном использовании старого?
3. Абсолютный срок: истекает ли refresh вообще?
4. Инвалидация при logout / смене пароля / отзыве приложения.
5. Привязка к клиенту/устройству.
6. Где хранится (cookie vs localStorage).
7. Scope при продлении.

## Инструменты

- **Burp** — Repeater для цикла refresh; Turbo Intruder для race.
- **`curl`** — быстрые проверки.
- **DevTools** — где хранится токен.

## Частые ошибки

- **Проверять только один раз.** Нужен цикл «refresh → снова refresh».
- **Не тестировать race.** Reuse detection часто ломается гонкой.
- **Игнорировать logout.** Токен должен умирать.
- **Забыть про scope.** Продление не должно расширять права.
- **Считать «access истёк» концом.** Refresh — главная цель.
- **Не смотреть storage.** localStorage = XSS-кража.

## Полная карта токенов и их различий

Прежде чем тестировать refresh-механизм, разложите токены по типам.

| Токен | Время жизни | Назначение | Хранение (правильно) |
|-------|-------------|-----------|----------------------|
| Access token | минуты | доступ к API | память JS |
| Refresh token | дни/недели | обновление access | HttpOnly-cookie |
| ID token (OIDC) | минуты | данные о пользователе | не для авторизации |
| Authorization code | секунды | обмен на токены | транзиентно |
| Session cookie | часы/дни | веб-сессия | HttpOnly + Secure |

Ключевой инвариант: **refresh token — одноразовый**. При каждом использовании он должен заменяться новым, а старый — становиться недействительным. Нарушение этого инварианта — основная причина «вечного доступа».

## Атака: отсутствие ротации и reuse detection

```bash
# 1) обмениваем refresh на новую пару
curl -s -X POST https://auth.example/token \
  -d 'grant_type=refresh_token&refresh_token=RT1' | jq .
# {"access_token":"AT2","refresh_token":"RT1"}   <- RT НЕ сменился -> нет ротации
```

Если `refresh_token` вернулся тем же — ротации нет: украденный RT работает бесконечно. Если ротация есть, но нет **reuse detection**:

```bash
# 2) используем старый RT после ротации (должно ломать всю цепочку)
curl -s -X POST https://auth.example/token -d 'grant_type=refresh_token&refresh_token=RT1'
# если снова выдан AT -> reuse не детектится
```

Правильная реализация при повторном использовании старого RT **инвалидирует всю семью токенов** (token family) и требует повторного логина.

## Гонка на ротации (race condition)

Даже при ротации возможна гонка: два одновременных запроса с одним RT.

```bash
# два параллельных обмена одним и тем же refresh token
curl -s -X POST https://auth.example/token -d 'grant_type=refresh_token&refresh_token=RT1' &
curl -s -X POST https://auth.example/token -d 'grant_type=refresh_token&refresh_token=RT1' &
wait
# если оба вернули валидные пары -> ротация не атомарна
```

Последствие: атакующий, перехвативший RT, может параллельно с жертвой обновлять токены, оставаясь незамеченным. Защита — атомарная замена с блокировкой.

## Привязка к клиенту: DPoP, mTLS, client binding

Refresh token должен быть привязан к клиенту, иначе его кража = полный захват.

```bash
# DPoP: proof-of-possession — токен нельзя использовать без приватного ключа
# заголовок DPoP содержит подписанный JWT с отпечатком ключа
curl -s -X POST https://auth.example/token \
  -H "DPoP: $(gen_dpop_proof)" -d 'grant_type=refresh_token&refresh_token=RT1'
# без валидного DPoP -> invalid_dpop_proof
```

Проверяйте: привязан ли RT к `client_id`, IP, устройству; требуется ли DPoP/mTLS; можно ли использовать RT с другого клиента.

## Полный чек-лист lifecycle

| Проверка | Что должно быть | Признак проблемы |
|----------|-----------------|------------------|
| Ротация при каждом refresh | новый RT | RT не меняется |
| Reuse detection | инвалидация family | старый RT работает |
| Атомарность | блокировка | гонка даёт 2 пары |
| Привязка к клиенту | client_id/DPoP | RT переносится |
| Хранение | HttpOnly cookie | доступен из JS |
| Отзыв при logout | серверный revoke | токен жив после выхода |
| Смена пароля | revoke всех RT | старые RT живы |
| Lifetime | ограничен | бессрочный RT |

## Разобранный пример: вечный доступ

```bash
# 1) жертва логинится, атакующий перехватывает RT (XSS/лог)
RT=eyJhbGciOi...
# 2) атакующий обновляет access в фоне, пока RT не инвалидируется
while true; do
  curl -s -X POST https://auth.example/token \
    -d "grant_type=refresh_token&refresh_token=$RT" | jq -r '.access_token'
  sleep 300
done
# 3) если RT не ротируется и не отзывается — доступ бессрочный
```

Доказательство: серия обновлений на протяжении длительного времени без повторного логина.

## Что делать дальше / решение

1. **Наблюдайте обмен.** Перехватите `/token`, посмотрите, меняется ли RT.
2. **Проверьте reuse.** Используйте старый RT повторно.
3. **Проверьте гонку.** Два параллельных обмена.
4. **Проверьте привязку.** RT с другого клиента/IP.
5. **Проверьте отзыв.** logout, смена пароля, компрометация.
6. **Зафиксируйте PoC.** Цепочка обновлений/повторного использования с ответами.

## Сводка уязвимостей refresh-механизма

| Уязвимость | Проверка | Последствие |
|-----------|----------|-------------|
| Нет ротации | RT не меняется | вечный доступ |
| Нет reuse detection | старый RT работает | скрытое использование |
| Неатомарная ротация | гонка даёт 2 пары | параллельный доступ |
| Нет привязки к клиенту | RT переносится | кража = захват |
| Хранение в localStorage | доступен из JS | кража через XSS |
| Нет отзыва при logout | RT жив после выхода | доступ сохраняется |
| Долгий/бессрочный lifetime | RT живёт годами | широкое окно атаки |
| Широкий scope | RT даёт все права | эскалация |

## Хранение токенов: что безопасно

Access-токен храните в памяти (JS-переменная), refresh-токен — в `HttpOnly`-cookie с `Secure` и `SameSite`. Хранение RT в `localStorage` делает любую XSS полным захватом аккаунта. Проверяйте, где именно лежит RT, и какой флаг `SameSite` у cookie.

## Итог по refresh-токенам

Механизм refresh — это про долгую, но отзываемую сессию. Правильная реализация: одноразовый RT с ротацией, reuse detection, атомарная замена, привязка к клиенту, серверный отзыв и ограниченный lifetime. Любое нарушение этих инвариантов превращает «удобное продление сессии» в «постоянный доступ», который переживает смену пароля и выход из системы.
