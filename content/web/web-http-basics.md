Ты открываешь сайт интернет-магазина, жмёшь «Купить» — и что-то ломается. Или тебе дали URL и сказали «где-то тут флаг». С чего начать? Прежде чем ломать, нужно понять, **что именно** браузер отправляет серверу и что получает назад. Всё общение в вебе — это обмен текстовыми сообщениями по протоколу HTTP. Если ты умеешь их читать, дальше любая уязвимость — вопрос внимательности.

В этом уроке мы возьмём один учебный магазин `shop.local` и разберём **один** его запрос от начала до конца. Термины будем вводить только тогда, когда они понадобятся.

## Наш пример: один запрос

Откроем страницу товара в терминале через `curl` — это инструмент, который отправляет HTTP-запрос и печатает ответ.

```bash
$ curl -v 'http://shop.local/product?id=7'
```

Флаг `-v` («verbose») просит curl показать и то, что он **отправил**, и то, что **получил**. Вот что он печатает (сокращённо):

```http
> GET /product?id=7 HTTP/1.1
> Host: shop.local
> User-Agent: curl/8.5.0
> Accept: */*
>
< HTTP/1.1 200 OK
< Content-Type: text/html; charset=utf-8
< Content-Length: 4213
< Set-Cookie: session=9f2c8a1b; HttpOnly
<
<!doctype html><html>…<h1>Кружка «Хакер»</h1>…
```

Строки со `>` — это наш запрос, строки со `<` — ответ сервера. Разберём их по частям.

## Шаг 1: анатомия запроса

Запрос состоит из трёх частей.

**Стартовая строка** — самая первая: `GET /product?id=7 HTTP/1.1`.

- `GET` — **метод**, то есть «что я хочу сделать». GET = «дай мне ресурс».
- `/product?id=7` — путь к ресурсу. Часть после `?` называют **query-string** (строкой запроса): это пары `ключ=значение`, передающие параметры. Здесь мы просим товар с `id=7`.
- `HTTP/1.1` — версия протокола.

**Заголовки** — строки вида `Имя: значение`. `Host: shop.local` говорит серверу, какой сайт нам нужен (на одном сервере может жить сотня сайтов). `User-Agent` — чем мы пришли (браузер или инструмент). `Accept` — какие форматы ответа мы готовы принять.

**Тело** — необязательная часть после пустой строки. У `GET` тела обычно нет: мы ничего не отправляем, только просим.

Пустая строка после заголовков — сигнал серверу «заголовки закончились, дальше идёт тело».

## Шаг 2: анатомия ответа

Ответ устроен так же, только зеркально.

**Стартовая строка:** `HTTP/1.1 200 OK`. Число `200` — **код состояния**; он говорит, чем всё кончилось.

**Заголовки:** `Content-Type: text/html; charset=utf-8` — «в теле HTML в кодировке UTF-8». `Content-Length: 4213` — длина тела в байтах. `Set-Cookie: session=9f2c8a1b; HttpOnly` — сервер **устанавливает cookie** (про них ниже).

**Тело:** собственно HTML страницы — `<!doctype html>…`.

Итого: один запрос → один ответ. Сервер не помнит, что было в прошлом запросе, поэтому HTTP называют **stateless** («без состояния»). Именно поэтому придумали cookie.

## Шаг 3: методы — не только «дай»

`GET` только читает. Чтобы отправить данные (например, логин), используют `POST`; у POST тело есть.

```bash
$ curl -s -X POST 'http://shop.local/login' \
    -d 'username=admin&password=admin'
```

Флаг `-X POST` задаёт метод, `-d` кладёт данные в тело. Формат `ключ=значение&ключ=значение` называется `application/x-www-form-urlencoded` — самый простой способ передать форму.

Запомни пары «метод — смысл»:

| Метод | Смысл | Тело |
|-------|-------|------|
| `GET` | получить | нет |
| `POST` | отправить/создать | да |
| `PUT` | заменить целиком | да |
| `DELETE` | удалить | нет |
| `HEAD` | как GET, но только заголовки | нет |
| `OPTIONS` | узнать, какие методы поддерживаются | нет |

Подмена метода (`GET` там, где ждали `POST`, или `PUT` для обхода проверки) — база многих атак, но это тема отдельного урока.

## Шаг 4: cookie — как сервер «помнит» тебя

Сервер stateless, но после логина тебя надо узнавать. Решение — **cookie**: маленькая пара `имя=значение`, которую сервер шлёт заголовком `Set-Cookie`, а браузер возвращает в каждом следующем запросе заголовком `Cookie`.

Посмотрим реальный логин:

```bash
$ curl -s -i -c jar.txt -X POST 'http://shop.local/login' \
    -d 'username=admin&password=admin'
HTTP/1.1 302 Found
Location: /account
Set-Cookie: session=eyJ1c2VyIjoiYWRtaW4ifQ; HttpOnly; Secure
```

`-i` показывает заголовки ответа, `-c jar.txt` сохраняет полученные cookie в файл. Ответ `302 Found` означает «перенаправляю тебя на `/account`» (см. заголовок `Location`). Теперь используем сохранённую cookie:

```bash
$ curl -s -b jar.txt 'http://shop.local/account' | grep -o 'Добро пожаловать, [^<]*'
Добро пожаловать, admin
```

Флаг `-b jar.txt` берёт cookie из файла и отправляет их. Мы «залогинены» — сервер узнал нас по `session`. Вот почему cookie — ключ ко всей аутентификации: **кто знает твою сессионную cookie, тот ты**.

## Шаг 5: коды состояния

Первая цифра кода задаёт класс:

| Код | Класс | Пример |
|-----|-------|--------|
| `1xx` | информационные | `101` (переход на WebSocket) |
| `2xx` | успех | `200 OK`, `201 Created` |
| `3xx` | перенаправление | `302 Found`, `304 Not Modified` |
| `4xx` | ошибка клиента | `400`, `401`, `403`, `404` |
| `5xx` | ошибка сервера | `500`, `502`, `503` |

Важно не путать `401` и `403`. `401 Unauthorized` — «ты не залогинен». `403 Forbidden` — «ты залогинен, но тебе сюда нельзя». Эта разница критична при тестировании доступа: `403` говорит, что ресурс существует и защищён, а `404` — что его нет.

## Шаг 6: заголовки, которым сервер доверяет

Некоторые заголовки несут информацию «от клиента», и приложение иногда верит им без проверки. Это источник многих уязвимостей.

- `Host` — какой сайт запрошен. Если сервер строит из него ссылки (например, в письме сброса пароля), подмена уводит жертву на чужой домен.
- `X-Forwarded-For` — «с какого IP пришёл клиент». Его легко подделать; если им ограничивают доступ к админке, ограничение обходится.
- `Referer` и `Origin` — откуда пришёл запрос; проверки на них иногда обходят.

Проверим доверие к `Host` — подставим чужое значение:

```bash
$ curl -s 'https://shop.local/forgot' -H 'Host: attacker.example' | grep -o 'https://[^"]*reset[^"]*'
https://attacker.example/reset?token=...
```

Сервер построил ссылку с нашим `Host` — значит, он ему доверяет. Это уже тема отдельного урока (host header injection), но принцип общий: **где клиент может подставить значение, которое сервер примет на веру, там и живёт уязвимость.**

## Что мы теперь знаем

- HTTP — обмен текстовыми сообщениями «запрос → ответ»; сервер по умолчанию не помнит прошлое.
- Запрос = стартовая строка (метод + путь + версия), заголовки, пустая строка, тело.
- `GET` читает, `POST` отправляет; query-string — это `?ключ=значение`.
- `Set-Cookie` заводит cookie, `Cookie` возвращает её; сессионная cookie — твой «пропуск».
- Код ответа говорит, что произошло; `403` ≠ `401`.

## На что смотреть дальше

- **Расхождение парсеров.** Если прокси и приложение по-разному понимают `Content-Length`/`Transfer-Encoding`, один запрос можно «спрятать» внутри другого (request smuggling).
- **Подмена метода.** `GET` вместо `POST`, `PUT` для обхода — проверяй, какие методы принимает эндпоинт (`curl -X OPTIONS -i`).
- **Query-string против body.** Один параметр в строке запроса и в теле может обрабатываться по-разному (parameter pollution).

## HTTP/1.1, HTTP/2 и HTTP/3: что меняется

HTTP/1.1 передаёт запросы как обычный текст, по одному за раз на соединение (keep-alive позволяет переиспользовать TCP). HTTP/2 бинарный: запросы разбиты на фреймы (`HEADERS`, `DATA`, `SETTINGS`), мультиплексируются в одном соединении, а заголовки сжаты HPACK. Для атакующего это меняет поверхность: в HTTP/1.1 работают request smuggling и расхождения по `Content-Length`, в HTTP/2 — desync на уровне фреймов, `:authority` вместо `Host` и HPACK-инъекции. HTTP/3 работает поверх QUIC (UDP): нет TCP-хендшейка, но появляются свои тонкости с 0-RTT и миграцией соединений. Практический вывод: определи версию (`curl --http2 -v`), потому что техники для 1.1 и 2 различаются, и одна и та же ручка за прокси может говорить на разных версиях.

## Атрибуты cookie и тело запроса

Cookie — не просто `имя=значение`: сервер добавляет атрибуты, и они определяют поведение. `HttpOnly` запрещает доступ из JavaScript (защита от XSS-кражи), `Secure` — отправку только по HTTPS, `SameSite` управляет cross-site отправкой (`Strict`, `Lax`, `None`; `None` требует `Secure`). `Domain` и `Path` задают область видимости: слишком широкий `Domain` отдаёт cookie поддоменам. При тестировании смотри, есть ли `HttpOnly`/`Secure`: их отсутствие — прямой путь к краже сессии.

Тело запроса описывается заголовками `Content-Length` (длина в байтах) или `Transfer-Encoding: chunked` (тело блоками). Если присутствуют оба и прокси с сервером понимают их по-разному, один запрос прячется внутри другого — это основа request smuggling. Для форм тип `application/x-www-form-urlencoded`, для JSON — `application/json`, для файлов — `multipart/form-data` с границей.

## Где пригодится

- **CTF (Web):** любой challenge начинается с чтения запросов к приложению; без этого не найти ни один параметр для инъекции.
- **Bug bounty:** воспроизведение бага в отчёте делается именно curl-командой — её требует большинство платформ.
- **Пентест:** ручное воспроизведение запросов — основа доказательства эксплуатируемости; автосканер без ручной проверки даёт false positives.
- **Работа (AppSec/Dev):** понимание заголовков и кодов нужно для чтения логов, отладки API и ревью прокси/WAF.
