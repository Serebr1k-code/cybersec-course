## Вопрос, с которого всё начинается

Magento (сейчас Adobe Commerce) — тяжёлая e-commerce-платформа для крупных магазинов. Её ценность для атакующего — прямые деньги: заказы, платёжные данные, доступ к интеграциям. И у неё есть как классические SQLi, так и свежие цепочки вроде **CosmicSting**. Разберём, как подступиться.

## Наш пример: интернет-магазин на Magento

Цель — `https://shop.target.example`. Определим платформу. У Magento есть «паспортный» эндпоинт:

```
$ curl -s https://shop.target.example/magento_version
Magento/2.4.6 (Community)
```

Версия **2.4.6**. Это уже даёт нам список известных CVE для этой версии. Дополнительно структуру выдают характерные пути: `/admin`, `/rest/V1/`, `/graphql`, `/customer/account/login/`.

## Шаг 1: REST и GraphQL как поверхность

Magento отдаёт два API: REST (`/rest/V1/...`) и **GraphQL** (`/graphql`). GraphQL по умолчанию открыт для анонимов на чтение каталога, и именно через него прошла часть цепочек CosmicSting.

Проверим, что GraphQL жив:

```
$ curl -s -X POST https://shop.target.example/graphql \
  -H 'Content-Type: application/json' \
  -d '{"query":"{storeConfig{store_name}}"}'
{"data":{"storeConfig":{"store_name":"Target Shop"}}}
```

Ответ есть — значит GraphQL доступен и с ним можно работать.

## Шаг 2: SQLi в фильтрах каталога

Классика Magento — инъекции в параметрах фильтрации каталога и в сортировке. Типовой тест: подставить кавычку и смотреть, изменится ли ответ/код.

```
$ curl -s 'https://shop.target.example/catalogsearch/result/?q=test%27' -o /dev/null -w '%{http_code}\n'
500
$ curl -s 'https://shop.target.example/catalogsearch/result/?q=test' -o /dev/null -w '%{http_code}\n'
200
```

Разница `500` vs `200` — сигнал, что кавычка ломает SQL. Дальше — `sqlmap` по сохранённому запросу:

```
$ sqlmap -r req.txt -p q --batch --dbs
```

Если фильтр `q` уязвим, извлекаем таблицы `admin_user` (логины, хэши с солью) и `catalog_*`.

## Шаг 3: CosmicSting (CVE-2024-34102) — XXE в REST

**CosmicSting** — критичная уязвимость (CVSS 9.8) в обработке XML у Magento. Через REST-эндпоинт, принимающий JSON, можно подсунуть **вложенный XML**, который парсится с включёнными внешними сущностями — то есть **XXE**. Это позволяет читать локальные файлы, а в цепочке — добраться до секретов и выполнить код.

Суть эксплуатации: отправить POST с телом, где есть поле, интерпретируемое как XML, и в DOCTYPE объявить внешнюю сущность, указывающую на файл:

```
POST /rest/V1/guest-carts/1/estimate-shipping-methods HTTP/2
Content-Type: application/json

{"address":{"<foo>":...}}
```

Точная полезная нагрузка зависит от версии; публичный PoC (например, репозиторий с CosmicSting) читает `app/etc/env.php` — файл с ключом шифрования Magento. С этим ключом подделываются данные и открывается путь к RCE.

Важно: PoC — чужой код, читаем и репойнтим колбэки на свой слушатель, следим, чтобы не уронить магазин.

## Шаг 4: путь к RCE

Общая цепочка Magento-атаки:

1. XXE/SQLi → чтение `app/etc/env.php` (там `crypt` key и доступ к БД);
2. с ключом шифрования — подделка сессионных данных/токенов;
3. вход в `/admin` → включение темы/модуля с PHP-кодом → RCE.

Альтернатива — SQLi → админ-хэш → крэк → админка → RCE.

## Шаг 5: определение уязвимости сканером

```
$ nuclei -u https://shop.target.example -tags magento -silent
[CVE-2024-34102] [http] [critical] https://shop.target.example/rest/V1/...
```

Плюс `nuclei` по тегу `adobe-commerce`. Опять же: теги/имена по CVE, а не грепом по слову.

## Что мы теперь знаем

- Версию Magento отдаёт `/magento_version`.
- GraphQL (`/graphql`) и REST (`/rest/V1/`) — публичные API, поверхность атаки.
- SQLi ловится по разнице кодов 500/200 на кавычку; дальше — `sqlmap`.
- CosmicSting — XXE через REST, ведёт к чтению `env.php` и далее к RCE.
- Ключ шифрования Magento = подделка данных и путь в админку.

## Шаг 6: почему защищённые магазины всё равно ломают

Magento — тяжёлая система с сотнями модулей. Даже если ядро пропатчено, ломается **периферия**: сторонние модули оплаты, доставки, аналитики. Их пишут подрядчики, обновляют редко, а поверхность у них — те же SQLi и object injection.

Второй источник — **мисконфигурация**. По умолчанию Magento отдаёт `/magento_version`, открывает `/rest/V1/` для анонимных чтений и держит включёнными ненужные модули. Админку часто оставляют на дефолтном пути `/admin` без IP-ограничения.

Третий — **интеграции**. Магазин связан с ERP, 1С, платёжным шлюзом. Ключи интеграций лежат в БД и в `app/etc/env.php`. Прочитав их, атакующий выходит за пределы сайта — в инфраструктуру компании.

## Шаг 7: чек-лист по Magento

Порядок действий на цели:

1. **Версия** — `/magento_version`, заголовки, `composer.json` (если доступен).
2. **API** — жив ли `/graphql` (анонимный запрос), доступен ли `/rest/V1/`.
3. **Админка** — путь и доступность `/admin`.
4. **SQLi** — кавычка в фильтрах каталога, сортировке, поиске; при сигнале — `sqlmap` по сохранённому запросу.
5. **XXE/CosmicSting** — проверка версии на CVE-2024-34102 и подобные.
6. **Секреты** — если есть чтение файлов, тянуть `app/etc/env.php` (ключ шифрования + доступ к БД).

Из чтения `env.php` открывается `crypt key` — и это точка невозврата: с ним можно подделывать зашифрованные данные Magento и поднимать привилегии. Поэтому утечка этого файла в Magento приравнивается к компрометации.

Отдельно: `sqlmap` на живом магазине может быть **тяжёлым** — не гоняй его с `--risk 3 --level 5` на проде. Начни с `--batch --level 2 --risk 1` и следи за нагрузкой.

## Шаг 8: закрепление и распределение усилий

Соберём картину. Magento-атака — это почти всегда **несколько шагов**: версия → API → SQLi или XXE → чтение секретов → подделка/админка → RCE. Одиночного «магического» эксплойта мало, потому что магазин защищён послойно.

По ожидаемой ценности Magento — **высокая цель**: за ней деньги, персональные данные покупателей, интеграции с платёжными системами и ERP. Но и **риск**: активная эксплуатация может нарушить работу магазина и навредить реальным людям. Поэтому на проде — только неразрушающие проверки, а полную цепочку отрабатывают на стенде.

Если магазин — это **только витрина** без реальных заказов (демо, тестовый контур), приоритет ниже: ломать нечего, данных нет. В таком случае фиксируем находки и переходим к целям с реальным импактом.

## Шаг 9: чем Magento отличается от «обычной» CMS для атакующего

WordPress ломается быстро и шумно; Magento — медленно и аккуратно. Причины: строгая типизация, ORM вместо сырых запросов, шифрование данных, разделение на слои. Поэтому SQLi в Magento — редкость, а вот **логические и конфигурационные** дыры — норма: открытые API, слабые права модулей, утечки секретов.

Практический вывод: не жди, что `sqlmap` «сходу» найдёт инъекцию. Сначала карта: какие модули стоят, какие API открыты, что видно анонимно. И только потом — точечные проверки. Магазин вознаграждает терпеливую разведку и наказывает шумные сканы (WAF, блокировка, падение под нагрузкой).
