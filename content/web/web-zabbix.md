## Вопрос, с которого всё начинается

В сети стоит Zabbix — система мониторинга, которая следит за всеми серверами и сетевыми устройствами. Она знает про инфраструктуру больше, чем кто-либо: каждый хост, каждый порт, каждый сервис. У Zabbix есть классический дефолтный пароль и уязвимость обхода SAML-аутентификации. Разберём, как из системы мониторинга получают вход и карту сети.

## Что такое Zabbix

**Zabbix** — open-source система мониторинга. **Zabbix-сервер** опрашивает **агентов** на хостах и собирает метрики (CPU, память, доступность сервисов). Веб-интерфейс на PHP показывает дашборды, а **JSON-RPC API** (`/api_jsonrpc.php`) даёт программный доступ.

Ценность для атакующего:

- **Карта инфраструктуры.** В Zabbix перечислены все хосты и их сервисы — готовый список целей.
- **Креды.** Для опроса серверов и интеграций Zabbix хранит доступы.
- **Метрики с секретами.** В метках (tags) иногда встречаются версии, имена и даже пароли.
- **Слабые места.** Дефолтные пароли и обход SAML.

## Наш пример: Zabbix 5.4.0

Цель — `http://zabbix.target.example:8080`. Определяем продукт и версию через API:

```
$ curl -s -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","method":"apiinfo.version","params":{},"id":1}' \
  http://zabbix.target.example:8080/api_jsonrpc.php
{"jsonrpc":"2.0","result":"5.4.0","id":1}
```

`apiinfo.version` работает **без аутентификации** — это стандарт Zabbix. Версия **5.4.0** — попадает в CVE-2022-23131 (5.4.0–5.4.8, 6.0.0alpha1 и др.).

## Шаг 1: default-креды

Классический дефолт Zabbix — `Admin/zabbix` (с большой буквы `A`). Проверяем через API:

```
$ curl -s -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","method":"user.login","params":{"user":"Admin","password":"zabbix"},"id":1}' \
  http://zabbix.target.example:8080/api_jsonrpc.php
{"jsonrpc":"2.0","result":"<session-token>","id":1}
```

Если пароль не сменён — ты уже админ. С токеном можно тянуть всё: хосты, метрики, пользователей.

## Шаг 2: собрать карту хостов

С токеном запрашиваем список хостов:

```
$ curl -s -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","method":"host.get","params":{"output":["host","name"]},"auth":"<token>","id":1}' \
  http://zabbix.target.example:8080/api_jsonrpc.php
{"result":[{"hostid":"10084","host":"web01.internal","name":"Web 01"},...]}
```

Это готовая карта инфраструктуры: имена хостов, IP, группы. Дальше — метрики и элементы (items), где иногда лежат секреты.

## Шаг 3: CVE-2022-23131 — обход SAML

Если Zabbix настроен на SAML-аутентификацию, он уязвим к CVE-2022-23131. Суть: Zabbix хранит данные SAML-сессии в cookie **`zbx_session`** — это base64-encoded JSON. Он **не проверяет подпись** этой cookie. Значит, можно подделать её, указав имя любого пользователя (например, админа), и войти без пароля.

Смотрим формат cookie:

```
zbx_session = base64({"sessionid":"...","sign":"...","saml_data":{"username_attribute":"Admin"}})
```

Подделываем `saml_data.username_attribute` на `Admin`, кодируем в base64 — и сервер принимает нас как админа. Это обход аутентификации без единого пароля.

## Шаг 4: почему это работает

Ошибка — доверие к клиентским данным. Cookie `zbx_session` содержит и сессию, и данные SAML, но подпись не проверяется должным образом. То есть Zabbix доверяет тому, что прислал браузер. Это снова **trust в клиентские данные** — знакомый класс ошибок.

## Шаг 5: пост-эксплуатация

Из Zabbix достают: карту хостов и сервисов, креды к серверам (в элементах и макросах), метрики с внутренними адресами, пользователей (для дальнейшего перебора). Система мониторинга превращается в разведданные для всей сети.

## Шаг 6: как не навредить

Zabbix активно мониторит: если его сломать, команда ослепнет. Поэтому не меняй хосты, не удаляй элементы, не трогай агентов. Читай через API точечно.

## Что мы теперь знаем

- Zabbix — мониторинг с JSON-RPC API и картой хостов.
- `apiinfo.version` открыт без аутентификации.
- Дефолт `Admin/zabbix` часто не сменён.
- CVE-2022-23131 — обход SAML через подделку cookie `zbx_session`.
- Из Zabbix достают карту сети и креды.

## Разбираем, как выглядит cookie zbx_session

Понимание формата cookie — ключ к CVE-2022-23131. В обычном режиме `zbx_session` содержит JSON с полями `sessionid` и `sign` (подпись). Но при SAML-входе в cookie добавляется объект `saml_data` с атрибутами пользователя, включая имя. Zabbix использует это имя, чтобы найти пользователя в базе.

Уязвимость в том, что подпись cookie не проверяется должным образом при SAML-входе. Значит, атакующий может собрать JSON вида:

```
{"sessionid":"...","sign":"...","saml_data":{"username_attribute":"Admin"}}
```

закодировать в base64, положить в cookie `zbx_session` — и сервер примет его как сессию пользователя `Admin`. Ни пароля, ни валидной SAML-ассертации не требуется. Это классическая ошибка «доверие к данным клиента».

## Шаг 7: как найти версию и конфиг

Версия — через `apiinfo.version` (открыт). Наличие SAML — через страницу входа: если есть кнопка «Sign in with SAML», режим включён. Комбинация «версия уязвима + SAML включён» = CVE-2022-23131 применима.

## Шаг 8: что писать в отчёте

Отчёт фиксирует: версию; режим аутентификации (SAML); CVE-2022-23131; доказательство обхода (подделанная cookie + доступ к дашборду); импакт (админский доступ к мониторингу = карта сети и креды); рекомендацию (патч до 5.4.9/6.0.1+, отключить SAML, если не нужен, сменить дефолт).

## Шаг 9: защита и детект

Защита: обновить Zabbix, сменить `Admin/zabbix`, ограничить доступ к API, включить аудит. Детект: необычные cookie `zbx_session`, вход без предшествующей SAML-аутентификации, обращения к `index_sso.php` с подозрительными параметрами.

## Ошибки и антипаттерны

Первая — брутфорс `Admin` (он легко блокируется). Правильно — проверить один дефолт и перейти к CVE. Вторая — не проверить режим SAML: без него CVE-2022-23131 неприменима, и тестировщик делает ложный вывод. Третья — менять хосты в Zabbix для «доказательства»: достаточно чтения через API.

## Итог по Zabbix

Zabbix ценен как источник карты сети и кред, а его обход SAML даёт админский доступ без пароля. Порядок: версия (apiinfo.version) → режим аутентификации → дефолт или CVE → карта хостов. Ключевой вывод: мониторинг — это разведданные, а не второстепенный сервис.

## Разбор реального сценария

Пентест. Zabbix 5.4.0 на 8080, SAML включён. `apiinfo.version` отдаёт версию анонимно. `Admin/zabbix` не подошёл (сменён). Но CVE-2022-23131 применима: ты подделываешь cookie `zbx_session` с `saml_data.username_attribute=Admin`, base64 — и заходишь админом. Через API `host.get` получаешь список всех хостов с внутренними IP — готовую карту сети. В макросах некоторых хостов находишь пароль к базе. Один обход SAML дал админа мониторинга и разведданные по всей сети.

## Практический чек-лист по Zabbix

Обнаружение: порт 8080, страница Zabbix, `/api_jsonrpc.php`. Версия: `apiinfo.version`. Режим аутентификации: есть ли кнопка SAML на входе. Дефолт: `Admin/zabbix`. CVE: CVE-2022-23131 (обход SAML). Проверка: подделка cookie `zbx_session`. Пост-эксплуатация: `host.get` (карта), макросы (креды). Отчёт: версия, режим, доказательство обхода, импакт, рекомендация.

## Почему SAML-обход — это класс ошибок, а не разовый баг

Доверие к клиентским данным (cookie, заголовку, параметру) без проверки подписи — повторяющаяся ошибка. Она встречается в SAML-реализациях, в SSO, в сессионных механизмах. Если продукт хранит состояние на клиенте и не подписывает его — его можно подделать. Поэтому при пентесте всегда смотри: есть ли на клиенте данные, влияющие на решение о доступе, и проверяется ли их целостность. Zabbix — лишь один пример; тот же вопрос задавай к любой SSO-интеграции.

## Итог

Zabbix — это карта всей инфраструктуры в одном интерфейсе. Дефолтный пароль или обход SAML открывают её целиком: хосты, сервисы, креды. Поэтому Zabbix проверяют сразу после периметра — он быстро даёт разведданные для дальнейшей атаки.
