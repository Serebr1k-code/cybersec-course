В браузере видно лишь то, что приложение показывает. Но почти всегда есть **скрытые** страницы (`/admin`, `/backup`), параметры и виртуальные хосты, о которых UI молчит. Их не угадывают вручную — их находят **фаззингом**: перебором по словарю с анализом ответов.

В этом уроке мы возьмём `shop.local` и проведём **одну** разведку от словаря до конкретной находки.

## Наш пример: что отдаёт shop.local

Начнём с бесплатных карт, которые сервер даёт сам:

```bash
$ curl -s 'https://shop.local/robots.txt'
User-agent: *
Disallow: /admin
Disallow: /internal
$ curl -s 'https://shop.local/sitemap.xml' | grep -oE '<loc>[^<]+'
<loc>https://shop.local/</loc>
<loc>https://shop.local/product</loc>
<loc>https://shop.local/cart</loc>
```

`robots.txt` уже подсказал `/admin` и `/internal`. Но это лишь верхушка — перейдём к перебору.

## Шаг 1: как работает фаззинг

Идея проста: в URL есть место, куда подставляется слово из словаря. Инструмент `ffuf` перебирает слова и показывает ответы.

```
https://shop.local/FUZZ
                   ^^^^ сюда подставляется каждое слово словаря
```

Ключ к успеху — **фильтрация шума**. Почти любой несуществующий путь даёт одинаковый ответ (часто `404` или страницу-заглушку). Надо убрать эти «пустышки» и оставить необычные ответы.

## Шаг 2: фаззим пути

Запускаем перебор по списку популярных путей:

```bash
$ ffuf -u 'https://shop.local/FUZZ' -w /usr/share/seclists/Discovery/Web-Content/common.txt -mc all -fc 404
admin                   [Status: 401, Size: 1234]
backup                  [Status: 200, Size: 84521]
internal                [Status: 403, Size: 512]
api                     [Status: 301, Size: 0]
login                   [Status: 200, Size: 3021]
```

Флаги: `-mc all` показывает все коды, `-fc 404` **скрывает** пути с кодом 404 (пустышки). Читаем результат:

- `admin → 401` — существует, требует логин.
- `backup → 200` и большой размер — отдаёт что-то объёмное. Проверим руками:

```bash
$ curl -s -I 'https://shop.local/backup'
HTTP/1.1 200 OK
Content-Type: application/zip
Content-Disposition: attachment; filename=backup-2025.zip
```

`backup-2025.zip` — резервная копия сайта в открытом доступе. Это уже серьёзная находка: в архиве могут лежать исходники, `.env` с паролями, дампы БД.

- `internal → 403` — ресурс есть, но закрыт. `403` (а не `404`) означает, что он существует, — цель для обхода.
- `api → 301` — редирект на `/api/`, значит, есть API-раздел.

## Шаг 3: фаззим параметры

Теперь ищем параметры, которые меняют поведение. Подставляем слово вместо имени параметра:

```bash
$ ffuf -u 'https://shop.local/product?FUZZ=1' -w params.txt -mc all -fs 4213
debug                   [Status: 200, Size: 5021]
id                      [Status: 200, Size: 4213]
```

`-fs 4213` скрывает ответы **того же размера**, что и «обычный» (без параметра). Так `id` (обычный размер) отсеивается, а `debug` (другой размер) — виден. Запрос с ним:

```bash
$ curl -s 'https://shop.local/product?debug=1' | grep -i 'sql\|error\|query'
SQL query: SELECT * FROM products WHERE id = 7
```

Параметр `debug` раскрывает SQL-запрос. Это утечка внутренней информации и подсказка, куда бить инъекцией.

## Шаг 4: фаззим виртуальные хосты

На одном IP может жить много сайтов; какой из них отдаётся, решает заголовок `Host` (или SNI). Перебираем имена:

```bash
$ ffuf -u 'https://shop.local/' -H 'Host: FUZZ.shop.local' -w subdomains.txt -mc all -fs 4213
dev                     [Status: 200, Size: 1203]
staging                 [Status: 200, Size: 990]
```

`dev.shop.local` и `staging.shop.local` отвечают. Тестовые стенды часто менее защищены и содержат те же данные, что прод, но без WAF. Добавь их в список цели.

## Шаг 5: фиксируем находки

Результат одной разведки — конкретный список:

| Находка | Код | Что дальше |
|---------|-----|------------|
| `/admin` | 401 | проверить обход аутентификации |
| `/backup-2025.zip` | 200 | скачать и поискать секреты |
| `/internal` | 403 | попробовать обход путей |
| `?debug=1` | 200 | искать инъекции (SQLi) |
| `dev.shop.local` | 200 | тестировать тестовый стенд |

Правила гигиены фаззинга:

- **Фильтруй шум.** Без `-fc`/`-fs` результат — тысячи строк; с фильтром — единицы.
- **Не перебирай чужие данные циклом.** Для перебора путей/параметров есть `ffuf`/`gobuster`, а не `for` с `curl`.
- **Учитывай троттлинг.** Если сервер режет запросы, снижай `-t` (число потоков).
- **Читай размеры и коды.** Разница в размере/коде — это и есть сигнал.

## Шаг 6: словари и режимы

Качество разведки зависит от словаря. Для путей берут `common.txt` или `raft-*-words.txt` из SecLists, для параметров — `burp-parameter-names.txt`, для поддоменов — `subdomains-top1million-5000.txt`. Начинай с меньшего списка (быстрее, меньше шума), потом расширяй.

Полезные режимы `ffuf`:

- `-e .php,.bak,.zip` — добавить расширения к каждому слову;
- `-recursion` — рекурсивно обходить найденные каталоги;
- `-ac` — авто-калибровка фильтра по «пустышкам»;
- `-rate` / `-t` — ограничить нагрузку, если сервер троттлит;
- `-o out.json` — сохранить результат для разбора.

Проверь найденные каталоги на листинг: если открыт `/uploads/` или `/static/`, сервер отдаёт список файлов — это отдельная находка.

## Полный прогон от словаря до находки

```bash
# 1. карта от сервера
$ curl -s 'https://shop.local/robots.txt'
Disallow: /admin
# 2. перебор путей
$ ffuf -u 'https://shop.local/FUZZ' -w common.txt -mc all -fc 404
backup                  [Status: 200, Size: 84521]
internal                [Status: 403, Size: 512]
# 3. проверка находки
$ curl -s -I 'https://shop.local/backup' | grep -i content-disposition
Content-Disposition: attachment; filename=backup-2025.zip
# 4. перебор параметров
$ ffuf -u 'https://shop.local/product?FUZZ=1' -w params.txt -mc all -fs 4213
debug                   [Status: 200, Size: 5021]
```

За один прогон найдены открытый бэкап, скрытый `/internal` и отладочный параметр `debug`, раскрывающий SQL-запрос. Это и есть карта поверхности, с которой начинаются все дальнейшие атаки.

Важно читать не только код, но и **размер** ответа: `backup` (84521 байт) резко выделяется на фоне «пустышек», а `debug` (5021) отличается от обычных 4213 — именно эти различия и есть сигнал. Незнакомый размер или необычный код (`401`, `403`, `500`) — всегда повод посмотреть руками.

## Что мы теперь знаем

- Фаззинг = перебор по словарю с подстановкой в URL/заголовок.
- Ключ — фильтрация шума (`-fc`, `-fs`) по коду или размеру ответа.
- Находки разведки: скрытые пути, параметры, виртуальные хосты.
- `403`/`401` означают, что ресурс существует, — это цель для обхода.
- Результат — конкретный список целей с кодами и следующими шагами.

## На что смотреть дальше

- **Бэкапы и исходники.** `.git/`, `.env`, `*.zip`, `*.bak`, `backup/` — частые утечки.
- **Служебные эндпоинты.** `/actuator`, `/metrics`, `/debug`, `/console`.
- **Заголовки vhost.** Если `Host` меняет ответ — на том же IP есть скрытые сайты.

## Куда дальше

Мы нашли скрытые пути, параметры и стенды. Среди них был `/api/` — «машинный» интерфейс, который часто уязвимее UI. В следующем уроке разберём, как устроены REST, GraphQL и SOAP и где в них ошибки. А пока запомни: **фаззинг превращает чёрный ящик в карту; фильтруй шум и читай коды.**

## Где пригодится

- **CTF (Web):** часто флаг лежит на скрытой странице, найденной фаззингом.
- **Bug bounty:** разведка поверхности — обязательный первый шаг отчёта.
- **Пентест:** картирование скрытого контента и параметров перед эксплуатацией.
- **Работа (AppSec):** инвентаризация поверхностей и поиск забытых админок и бэкапов.
