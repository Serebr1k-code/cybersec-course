## Вопрос, с которого всё начинается

В прошлом уроке мы заняли `blog.target.com` через мёртвый GitHub Pages. Но что, если CNAME у поддомена нет вообще? Значит ли это, что takeover невозможен?

Нет. Поддомен можно «увести» и через другие типы DNS-записей — и некоторые из них дают куда больше, чем одну страницу. Вопрос этого урока: какие вообще записи бывают «висящими» и как найти их массово, а не по одной.

## Наш пример

Возьмём `internal.target.com` — внутренний поддомен компании. CNAME у него нет, зато есть делегирование:

```bash
$ dig +short NS internal.target.com
ns1.abandoned-provider.net.
ns2.abandoned-provider.net.
```

`NS` — это записи, которые говорят, какой DNS-сервер **обслуживает** зону. Здесь зону `internal.target.com` делегировали внешнему провайдеру `abandoned-provider.net`. Если тот провайдер уже не существует или позволяет зарегистрировать освободившуюся зону — вся зона `internal.target.com` у тебя. Это **NS-тейковер**, и он опаснее CNAME, потому что даёт контроль над всеми записями поддомена сразу.

## Шаг 1: разбираем типы записей

Takeover возможен везде, где запись указывает на внешний ресурс, который можно занять:

| Тип | Сценарий | Что получает атакующий |
|-----|----------|------------------------|
| `CNAME` | целевой сервис удалён | контроль поддомена (веб) |
| `NS` | делегирование на мёртвые NS | контроль всей зоны |
| `MX` | мёртвый почтовый провайдер | перехват почты домена |
| `A`/`AAAA` | IP переиспользован в облаке | занятие эластичного адреса |
| `TXT` | SPF/DKIM/verify-токен | подмена верификации сервисов |

Проверить все записи поддомена можно одной командой:

```bash
$ dig +short CNAME sub.target.com
$ dig +short NS    sub.target.com
$ dig +short MX    sub.target.com
$ dig +short A     old.target.com
```

## Шаг 2: MX и перехват почты

Особенно коварен `MX`: он говорит, куда доставлять почту для домена. Если MX указывает на отключённый почтовый сервис, а тот позволяет занять домен, ты получаешь **перехват всей входящей почты**:

```bash
$ dig +short MX mail.target.com
10 inbound.abandoned-mail.net.
```

Почта сброса пароля, письма с токенами, внутренняя переписка — всё пойдёт на твой сервер. Доказывают такой тейковер осторожно: показывают, что MX указывает на освобождённый сервис, и (в рамках scope) что домен можно там зарегистрировать.

## Шаг 3: A/AAAA и переиспользованные адреса

Dangling `A`-записи — отдельная история про облака. Когда компания освобождает «эластичный» IP (например, в AWS), этот адрес возвращается в пул и его может арендовать кто угодно. Старая A-запись продолжает на него указывать:

```bash
$ dig +short old.target.com
203.0.113.10
$ curl -s -o /dev/null -w '%{http_code}\n' http://old.target.com/
502
```

Если адрес `203.0.113.10` теперь можно арендовать — поддомен начнёт указывать на **твою** инфраструктуру. Именно поэтому проверять нужно не только CNAME, но и A/AAAA.

## Каталог отпечатков провайдеров

Каждый сервис, отдавая «нет такого ресурса», показывает характерный **отпечаток** (fingerprint) — строку, по которой его узнают. Их удобно держать списком и обновлять:

| Провайдер | Отпечаток в ответе |
|-----------|--------------------|
| GitHub Pages | «There isn't a GitHub Pages site here» |
| AWS S3 | `NoSuchBucket` |
| Heroku | «No such app» |
| Netlify | «Not Found - Request ID» |
| Shopify | «Sorry, this shop is currently unavailable» |
| Fastly | «Fastly error: unknown domain» |
| Azure | «404 Web Site not found» |
| Tumblr | «There's nothing here» |
| Zendesk | «Help Center Closed» |

Актуальный и полный список поддерживает проект **can-i-take-over-xyz** на GitHub — его подтягивают в конфиг сканеров, потому что сервисы меняют тексты ошибок.

## Пайплайн непрерывного мониторинга

Разовый скан ловит мало: записи постоянно появляются и «протухают». Соберём конвейер:

```bash
# 1) новые поддомены (в т.ч. из CT-логов)
$ subfinder -d target.com -silent -all | anew subs.txt
$ curl -s 'https://crt.sh/?q=%25.target.com&output=json' | jq -r '.[].name_value' | anew subs.txt

# 2) резолв CNAME на внешние сервисы
$ dnsx -l subs.txt -cname -resp -silent | anew cnames.txt

# 3) поиск «висящих» по отпечаткам
$ subjack -w subs.txt -t 100 -timeout 30 -ssl -v 2>&1 | anew takeovers.txt
```

Утилита `anew` добавляет только новые строки, поэтому ты видишь **дельту** — что появилось с прошлого запуска. Это и есть ключ к мониторингу: запускать по расписанию и обновлять отпечатки.

## Если не сработало

- `NS` указывает на живого провайдера, но зона занята — тейковер невозможен; зафиксируй запись как «под наблюдением».
- `MX` ведёт на живой сервис — попробуй проверить, отдаёт ли он «домен не обслуживается» для конкретного имени.
- CNAME ведёт на CDN (CloudFront/Fastly): там отпечаток зависит от версии; сверяйся с can-i-take-over-xyz, а не с одним текстом.
- **Wildcard DNS** (`*.target.com`) маскирует всё: несуществующие поддомены тоже отвечают, поэтому отпечатки смотри особенно внимательно.

## Как доказать контроль и не навредить

Захватить ресурс — это активное действие, поэтому его оформляют аккуратно. Достаточное доказательство для отчёта — три вещи вместе: сама DNS-запись, отпечаток сервиса «ресурса нет» и подтверждение, что имя свободно. Если правила позволяют фактический захват, размести безобидную страницу-маркер (обычный текст) и зафиксируй HTTP-ответ как артефакт.

Дальше оцени риск, но **без** вредоносных действий: проверь, читает ли поддомен cookie родительского домена (`document.cookie` при `Domain=.target.com`), входит ли домен в белый список CSP или OAuth `redirect_uri`. Никакого фишинга, никакого чужого JS — цель показать проблему, а не использовать её.

И отдельно — защита: удалять DNS-запись **до** отключения сервиса, не выдавать поддомены под произвольные хостинги и прогонять мониторинг по расписанию. Разовый аудит не работает: висящие записи возникают постоянно.

## Что мы теперь знаем

- Takeover — не только про CNAME: `NS` даёт зону, `MX` — почту, `A`/`AAAA` — адрес.
- Признак кандидата всегда один: запись указывает туда, где ресурса нет.
- Отпечатки сервисов — это тексты ошибок; их держат списком (can-i-take-over-xyz).
- Массовый поиск: `subfinder`/`crt.sh` → `dnsx` → `subjack`/`nuclei -tags takeover`.
- Мониторинг по расписанию важнее разового скана — записи «протухают» постоянно.
- Доказывают тейковер безобидным маркером и записью DNS-ответа.

## На что смотреть дальше

- Не останавливайся на CNAME — NS/MX/A-тейковер пропускают чаще всего, а эффект у него сильнее.
- Наличие CNAME ≠ тейковер: без отпечатка «нет ресурса» вывод преждевременен.
- Помни про wildcard: он маскирует висящие записи под живой ответ.
- Перепроверяй в моменте: DNS или сервис могли восстановиться между сканами.
- Не занимай ресурс без разрешения и не размещай ничего, кроме маркера.

## Куда дальше

В следующем уроке мы перейдём от разведки периметра к самому серверу — посмотрим на **мисконфигурации веб-сервера** (`web-server-misconfig`): открытые листинги, `/server-status`, старые версии Apache/nginx. А пока главное запомни: любая DNS-запись, ведущая в пустоту, — это потенциальный takeover, и чем «внутреннее» имя, тем серьёзнее последствия.

## Где пригодится

- **CTF (Web):** задачи на recon и контроль поддомена.
- **Bug bounty:** subdomain takeover — классическая высокая выплата.
- **Пентест:** аудит DNS-инвентаря и внешних зависимостей.
- **Работа (AppSec/Dev):** удалять осиротевшие записи, вести инвентаризацию DNS.
