## Вопрос, с которого всё начинается

Компания держит внутренние пакеты в приватном реестре. Разработчики пишут `import { config } from '@corp/internal-utils'` и спокойны: пакет приватный, чужой его не опубликует. Но резолвер пакетов устроен хитрее, чем кажется. Он смотрит на **имя**, а не на то, откуда имя должно прийти. И если точно такое же имя найдётся в публичном реестре — с большей версией, — он возьмёт его.

Это и есть **dependency confusion**. Атакующему не нужно проникать во внутреннюю сеть: достаточно угадать имя внутреннего пакета и опубликовать под ним свою версию.

## Как резолвер выбирает пакет

Менеджеры пакетов (`npm`, `pip`, `nuget`, `composer`) разрешают зависимости по имени и диапазону версий. Порядок источников задаётся конфигом: приватный реестр, потом публичный (или наоборот). Ключевая деталь — многие настройки не разделяют пространства имён. `@corp/internal-utils` из приватного реестра и `@corp/internal-utils` из npmjs — для резолвера почти одно и то же имя, а «почти» решается **версией**.

Если внутренний пакет имеет версию `1.0.3`, а в публичном реестре лежит `9.9.9`, то диапазон `^1.0.0`… стоп, тут важна деталь. `^1.0.0` не примет `9.9.9`. Но многие проекты указывают `*`, `latest` или просто имя без диапазона — тогда публичная `9.9.9` побеждает. Кроме того, сам `npm install @corp/internal-utils` без версии возьмёт **наибольшую** доступную версию из доступных источников.

## Наш пример: @corp/internal-utils

Договоримся о примере. В репозитории лежит `.npmrc`:

```
@corp:registry=https://npm.corp.internal/
registry=https://registry.npmjs.org/
```

Первая строка говорит: пакеты со scope `@corp` брать из внутреннего реестра. Вторая: всё остальное — из публичного. В `package.json`:

```json
{
  "dependencies": {
    "@corp/internal-utils": "*"
  }
}
```

Диапазон `*` означает «любая версия». Резолвер пойдёт в `npm.corp.internal`, найдёт там `1.0.3`, а потом… проверит и публичный реестр, потому что fallback не запрещён. Если атакующий опубликовал `@corp/internal-utils@99.0.0` на npmjs, выиграет `99.0.0`.

## Почему имена утекают

Как атакующий узнаёт внутренние имена? Они утекают постоянно:

- из публичных репозиториев, куда случайно закоммитили `.npmrc` или lock-файл;
- из сообщений об ошибках в открытых issue;
- из SBOM и списков зависимостей, публикуемых клиентами;
- из фронтенд-бандлов: имена модулей видны в минифицированном коде.

Собрать список scope и имён — дело техники. Дальше публикуется пакет с тем же именем и огромной версией.

## Что происходит при установке

Публичный пакет содержит `postinstall`-хук:

```json
{
  "scripts": {
    "postinstall": "node ./collect.js"
  }
}
```

`collect.js` читает переменные окружения машины сборки и отправляет их на сервер атакующего. На CI это часто токены деплоя, ключи облака, доступ к приватному реестру. Одна установка — и вся цепочка скомпрометирована.

## Как это защищают

Меры, которые реально работают:

- **Зафиксировать источники**: scope-пакеты — только приватный реестр, без fallback на публичный.
- **Использовать lock-файлы с проверкой integrity** (`npm ci`, `pip install --require-hashes`).
- **Резервировать имена**: опубликовать плейсхолдеры внутренних пакетов в публичных реестрах под своим аккаунтом.
- **Минимальные права токенов CI** и запрет `postinstall` там, где он не нужен (`npm ci --ignore-scripts`).

## Проверка цели глазами атакующего

Если ты тестируешь компанию, безопасный способ проверить гипотезу — не публиковать вредоносный пакет, а посмотреть, **разделены ли пространства имён**:

1. Найди имена внутренних пакетов (`.npmrc`, lock-файлы, бандлы).
2. Проверь, существуют ли они в публичном реестре: `curl -s https://registry.npmjs.org/<name>`.
3. Если существует и версия выше внутренней — это уязвимость конфигурации.

Публикация реального пакета в рамках пентеста — уже действие, требующее письменного согласования: оно влияет на чужие сборки.

## Что мы теперь знаем

- Dependency confusion эксплуатирует разрешение зависимостей по имени, а не по источнику.
- Побеждает та версия, которую резолвер сочтёт старшей из доступных.
- Имена внутренних пакетов утекают из репозиториев, бандлов и SBOM.
- `postinstall` превращает установку в исполнение чужого кода на машине сборки.
- Защита — жёсткая привязка scope к приватному реестру и lock-файлы с хешами.

## Реальный кейс: как это принесло 130 тысяч долларов

В 2021 году исследователь Алекс Бирсан провёл эксперимент: он не взламывал компании, а просто публиковал пакеты с именами, которые, по его предположениям, были внутренними. Имена он собирал из публичных источников — README, issue, бандлов. Для каждого публичного реестра он публиковал версию с огромным номером и безобидным `postinstall`, который лишь сообщал о факте установки.

Результат превзошёл ожидания: его код запустился внутри Apple, Microsoft, PayPal, Tesla, Netflix и десятков других компаний. Ни одной уязвимости в их коде не было — только конфигурация резолвера, допускавшая публичный fallback. Компании платили по программам bug bounty, потому что находка была настоящей: чужой код исполнился на их сборочных машинах.

Мораль проста: **имена внутренних пакетов — это секрет**, и утечка имени равна утечке доступа.

## Отличия между экосистемами

Приём везде одинаков, но детали различаются, и их важно знать.

| Экосистема | Конфиг источников | Тонкость |
|---|---|---|
| npm | `.npmrc`, поле `registry`, scope | scope-пакеты `@org/name` особенно уязвимы |
| PyPI | `pip.conf`, `--index-url`, `--extra-index-url` | `--extra-index-url` добавляет публичный источник поверх приватного |
| NuGet | `nuget.config`, `<packageSources>` | порядок источников влияет на выбор |
| Maven | `settings.xml`, `<mirrors>`, `<repositories>` | SNAPSHOT-версии часто не проверяются |

Ключевое отличие — в том, **как выражается приоритет**. Где-то источники упорядочены, где-то сливаются в один пул, и тогда побеждает старшая версия. Для пентеста важно понять модель приоритета конкретной экосистемы, потому что от неё зависит, сработает ли подмена.

## Практический чеклист проверки

Этичный способ оценить риск на реальной цели:

1. Собери список внутренних имён из lock-файлов, `.npmrc`, `pip.conf`, бандлов и SBOM.
2. Для каждого имени спроси публичный реестр: существует ли пакет?
3. Если существует — сравни версии и автора. Публичный пакет с большей версией и посторонним автором это уже подтверждённая уязвимость конфигурации.
4. Проверь, разрешён ли fallback: в конфиге не должно быть двух источников для одного имени.
5. Задокументируй: имя, реестр, версия, автор, наличие хуков.

Публикацию собственного пакета-ловушки в рамках пентеста согласовывают письменно: она влияет на чужие сборки и может быть расценена как атака на третью сторону.

## Как резолвер принимает решение: разбор по шагам

Разберём, что именно происходит в момент `npm install`, когда у пакета два источника. Резолвер идёт по дереву зависимостей и для каждого имени спрашивает у источников: «какие версии у тебя есть?» Ответы складываются в один пул, после чего выбирается версия, удовлетворяющая диапазону и наибольшая среди подходящих.

Возьмём диапазон `^1.0.0`. Символ `^` означает «совместимое обновление»: разрешены версии от `1.0.0` до `2.0.0` не включая. Публичная `99.0.0` в этот диапазон не попадает, поэтому подмена не сработает. А вот диапазон `*` или `latest` подмену примет сразу. Отсюда практический вывод: чем жёстче диапазоны и чем полнее lock-файл, тем уже окно для атаки.

Есть и вторая тонкость — **порядок источников**. В одних конфигурациях приватный реестр стоит первым и ответ из него считается окончательным. В других источники объединяются, и тогда решение зависит только от номера версии. Именно вторая конфигурация и называется «уязвимой к dependency confusion»: она не различает, откуда пришло имя.

Проверить конфигурацию можно так:

```
$ npm config get registry
https://registry.npmjs.org/
$ npm config get @corp:registry
https://npm.corp.internal/
```

Если обе строки заданы, а fallback не запрещён явно, стоит посмотреть, как ведёт себя резолвер при конфликте версий. Самый надёжный способ — воспроизвести установку в изолированном окружении на тестовом пакете, не затрагивая реальные сборки.

## Почему это трудно заметить

Dependency confusion почти невидим для код-ревью. В `package.json` всё выглядит правильно: то же имя, тот же диапазон. Отличие проявляется только в момент установки, на машине сборки, и только если публичный пакет с тем же именем существует и его версия старше. В логах установки нет предупреждения «вы взяли публичный пакет вместо приватного» — резолвер считает, что всё в порядке.

Именно поэтому защита должна быть декларативной: конфиг, где приватное имя **не может** быть разрешено публично, а не бдительность разработчика. Полагаться на то, что кто-то «посмотрит внимательно», — не мера безопасности.

## Мини-кейс: что произошло бы у нас

Вернёмся к нашему `.npmrc` со scope `@corp`. Диапазон `*` в `package.json` означает, что резолвер возьмёт наибольшую доступную версию. Публичный `@corp/internal-utils@99.0.0` существует, значит выигрывает он. Его `postinstall` исполняется на машине сборки и читает переменные окружения. В нашем примере флаг лежит прямо в README публичного пакета — это метафора того, что атакующий полностью контролирует содержимое. В реальности там был бы код, а не строка с флагом.
