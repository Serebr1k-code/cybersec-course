## Вопрос, с которого всё начинается

Kibana — панель для Elasticsearch: логи, поиск, дашборды. Через неё проходят логи всей инфраструктуры, а значит — секреты, токены, внутренние адреса. И у Kibana есть легендарная уязвимость: **prototype pollution → RCE**. Разберём её и связку с Elasticsearch.

## Наш пример: Kibana 7.5.0

Цель — `https://kibana.target.example`. Фингерпринт:

```
$ whatweb -a 3 https://kibana.target.example
https://kibana.target.example [200 OK] Kibana, Elasticsearch
```

Версию отдаёт эндпоинт статуса:

```
$ curl -s https://kibana.target.example/api/status
{"name":"kibana","version":{"number":"7.5.0"}}
```

Версия **7.5.0** — не уязвима к CVE-2019-7609 (она затрагивает 5.6.15–6.6.1), но у неё есть свои CVE. Точность версии критична.

## Шаг 1: CVE-2019-7609 — prototype pollution → RCE

В Kibana (Timelion) можно было подсунуть специально сформированный JS-объект, который **загрязнял прототип** (`__proto__`). Дальше через цепочку свойств атакующий добивался выполнения команды на сервере. Это классический пример **client-side prototype pollution**, который превращается в **server-side RCE**, потому что Kibana рендерит данные на сервере (SSR).

Схема: pollution → изменение поведения модуля → вызов `child_process.exec` → команда. PoC публиковались; их читают и адаптируют.

## Шаг 2: связка с Elasticsearch

Kibana работает поверх Elasticsearch. Если Elasticsearch открыт (без пароля, «admin party»), данные читаются напрямую:

```
$ curl -s 'http://es.target.example:9200/_cat/indices?v'
$ curl -s 'http://es.target.example:9200/logs-*/_search?q=password'
```

В логах — пароли, токены, API-ключи. Это часто ценнее RCE: за Kibana стоит весь лог-поток компании.

## Шаг 3: RCE через плагины и Timelion

Помимо pollution, Kibana уязвима через: (1) **плагины** (установка плагина = код); (2) **Timelion-выражения** (парсинг с опасными операциями); (3) **устаревшие версии** с известными CVE. Всё это — векторы к RCE при доступе.

## Шаг 4: план атаки на Kibana

1. Версия (`/api/status`).
2. Сопоставление с CVE (2019-7609 и другие).
3. Проверка Elasticsearch рядом (открыт?).
4. Поиск секретов в индексах.
5. Проверка pollution/RCE (при уязвимой версии).
6. Пост-эксплуатация — токены, креды.

## Шаг 5: как не навредить

Kibana/Elasticsearch хранят логи; их падение ослепляет мониторинг. Деструктивные операции (удаление индексов, тяжёлые запросы) запрещены. Поиск секретов — только чтение; RCE — только при разрешении.

## Шаг 6: чек-лист по Kibana

1. Версия.
2. Проверка CVE-2019-7609 (если версия в диапазоне).
3. Проверка Elasticsearch на открытость.
4. Поиск секретов в индексах.
5. Сопоставление с CVE.

## Что мы теперь знаем

- Kibana версию отдаёт `/api/status`.
- CVE-2019-7609 — prototype pollution → RCE (SSR).
- Elasticsearch рядом может быть открыт и отдавать логи с секретами.
- Плагины и Timelion — дополнительные векторы RCE.
- Логи компании — часто ценнее самого RCE.

## Шаг 7: как использовать Kibana для поиска секретов

Если Elasticsearch открыт, поиск секретов в индексах — самое быстрое и ценное действие. Используй полнотекстовый поиск по ключевым словам:

```
$ curl -s 'http://es.target.example:9200/_all/_search?q=password&size=50' | head -c 2000
$ curl -s 'http://es.target.example:9200/_all/_search?q=Authorization' | head -c 2000
```

В логах приложений часто лежат токены, пароли и API-ключи в открытом виде. Это может быть ценнее RCE.

## Шаг 8: как оценивать импакт Kibana-находки

Prototype pollution → RCE = контроль сервера (критический). Открытый Elasticsearch = доступ ко всем логам (критический, если там секреты). Утечка данных из индексов = персональные данные/креды (высокий). В отчёте укажи конкретно, какие индексы прочитаны и какие секреты найдены.

## Шаг 9: типовые ошибки при работе с Kibana

Ошибка первая — путать версию Kibana и Elasticsearch (у них разные CVE). Вторая — проверять CVE-2019-7609 на несовместимой версии. Третья — тяжёлые запросы к Elasticsearch (падает кластер). Четвёртая — не проверять соседний Elasticsearch на открытость (частая мисконфигурация).

## Шаг 10: как читать публичный PoC для Kibana

PoC для CVE-2019-7609 — это обычно HTML/JS или Python-скрипт, эксплуатирующий Timelion. Прочитай его: он может запускать обратную оболочку — замени адрес колбэка на свой. Проверь, что он не удаляет индексы. Для безопасной проверки используй безобидную команду (`id`/DNS).

## Шаг 11: как связать Kibana с лог-потоком компании

Kibana/Elasticsearch — это **центральный лог-приёмник**. В индексах: логи приложений (с токенами), логи прокси (с URL и кредами), логи аутентификации. Поэтому даже без RCE доступ к Elasticsearch даёт карту инфраструктуры и набор секретов. Это часто более ценно, чем сам сервер Kibana.

## Шаг 12: как защититься от Kibana-атак

Защита: обновление Kibana/Elasticsearch; включение аутентификации (X-Pack security) и TLS; закрытие Elasticsearch от прямого доступа; ограничение доступа к Kibana. Для атакующего: защищённый Elasticsearch (с паролем) закрывает поиск секретов, и остаётся только RCE через Kibana.

## Шаг 13: почему Kibana и Elasticsearch часто открыты

Elasticsearch исторически не имел аутентификации по умолчанию, и множество инстансов остались открытыми («admin party»). Kibana тоже часто развёрнута без auth. Поэтому их ищут через Shodan (`port:9200`, `port:5601`). Если Elasticsearch открыт — чтение логов даёт секреты без всякой эксплуатации. Это одна из самых частых находок в инфраструктурных пентестах.

## Шаг 14: как оформить находку

Укажи: версию Kibana/Elasticsearch; факт открытости; примеры индексов с секретами (замаскированными); импакт (карта инфраструктуры, креды); рекомендации (включить security, закрыть порты). Покажи, что доступ был реальным, но не публикуй сами секреты.
