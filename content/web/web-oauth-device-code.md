Представь умный телевизор, на котором надо войти в аккаунт, но нет клавиатуры. Вводить пароль пультом — мучение. Для таких устройств придумали **device code flow** (Device Authorization Grant): телевизор показывает код и ссылку, ты вводишь код на телефоне, подтверждаешь вход — и телевизор получает токен. Удобно. Но именно эта схема открыта для **фишинга**: жертва подтверждает вход на **чужом** устройстве, думая, что на своём.

Возьмём `shop.local` с входом на ТВ-приложении и разберём, где ломается этот поток.

## Наш пример: устройство просит вход

ТВ-приложение (или атакующая программа) запрашивает у провайдера код:

```bash
$ curl -s 'https://acmeid.example/device/code' \
  -d 'client_id=shop-tv&scope=openid%20profile'
{"device_code":"GmRhmhcxhwAzkoEqiMEg_DnyEysNkuNhszIySk9eS",
 "user_code":"WDJB-MJHT",
 "verification_uri":"https://acmeid.example/device",
 "expires_in":1800, "interval":5}
```

Здесь два кода: **`device_code`** (секретный, для опроса) и **`user_code`** (`WDJB-MJHT`, короткий, показывается человеку). Человек должен открыть `verification_uri`, ввести `user_code` и подтвердить. После этого устройство опрашивает сервер:

```bash
$ curl -s 'https://acmeid.example/device/token' \
  -d 'grant_type=urn:ietf:params:oauth:grant-type:device_code&device_code=GmRhm...&client_id=shop-tv'
{"access_token":"eyJ...","refresh_token":"rt_...","token_type":"Bearer"}
```

Токены уходят **устройству**. Ключевой вопрос: кто именно ввёл `user_code`?

## Шаг 1: фишинг через `user_code`

Атака проста и эффективна. Атакующий:

1. Запускает device flow **у себя** и получает `user_code=WDJB-MJHT`.
2. Придумывает повод («подтвердите вход в ваш аккаунт для синхронизации ТВ»), отправляет жертве ссылку на `verification_uri` и код.
3. Жертва вводит код и подтверждает.
4. Сервер выдаёт токены **атакующему устройству**.

Жертва нигде не вводила пароль в подозрительном месте — она вошла на **настоящем** сайте провайдера. Именно поэтому device code phishing так опасен: URL легитимный, сертификат настоящий, а токен уходит злоумышленнику.

## Шаг 2: почему это сложно заметить

У фишинга через device code почти нет признаков:

- **Настоящий домен** — `acmeid.example`, не подделка.
- **Правильный сертификат** — жертва не видит «небезопасно».
- **Никакого ввода пароля** на стороне атакующего — только код.
- **Быстро** — код живёт 30 минут, но подтверждение занимает секунды.

Единственная защита на стороне жертвы — **внимательность**: экран подтверждения показывает, **какому приложению** и с какими правами она даёт доступ. Если жертва читает «Приложение: Shop TV запрашивает доступ к вашему профилю и почте» и всё равно подтверждает — она отдала доступ.

## Шаг 3: `user_code` и перебор

`user_code` короткий (обычно 8 символов из алфавита без похожих букв), и у него есть срок. Теоретически его можно **перебирать** (brute force): если угадать чужой `user_code`, можно подтвердить **свой** device flow от чужого имени? Нет — наоборот: перебор `user_code` позволил бы атакующему **подтвердить чужое устройство**. Но сервер ограничивает попытки (rate limit) и срок. Если лимита нет — перебор возможен:

```bash
$ for code in $(seq 1 1000); do
    curl -s 'https://acmeid.example/device/approve' -d "user_code=WDJB-$(printf %04d $code)"; done
```

Если сервер не считает неудачные попытки, это отдельная находка.

## Шаг 4: привязка и «чужие» клиенты

Ошибки в реализации:

- **`user_code` не привязан к сессии пользователя**, который его вводит — любой может подтвердить чужой `device_code`.
- **`client_id` не проверяется при опросе** — токен можно получить, зная `device_code`, но не клиента.
- **Нет подтверждения приложения** — экран не показывает, какому приложению даётся доступ.
- **`device_code` утекает** — например, в логах или в URL.

## Шаг 5: `device_code` как секрет

`device_code` — длинный и случайный, он и есть секрет устройства. Если он утечёт (логи, отладка, небезопасная передача), атакующий получит токены напрямую. Также важно, что `device_code` должен **одноразово** обмениваться на токен: если сервер принимает его многократно, это расширяет окно атаки.

## Шаг 6: как это эксплуатируют на практике

Сценарии, которые встречаются в отчётах:

- **Фишинг** (Шаг 1) — самый частый; доказывается демонстрацией, что жертва подтверждает чужой код.
- **Кража токена** через утечку `device_code`.
- **Перебор `user_code`** без rate limit.
- **Повышение прав**: если scope включает широкие права (`mail`, `offline_access`), захват токена даёт доступ к почте и долгоживущим данным.
- **Обход MFA**: жертва проходит MFA на **своём** экране, но подтверждает **чужое** устройство — и MFA не мешает.

Именно комбинация «легитимный домен + настоящий MFA» делает этот вектор опасным даже для опытных пользователей.

## Шаг 7: как отличить эту атаку от обычного фишинга

Обычный фишинг заметен: поддельный домен, странный сертификат, ввод пароля на чужой странице. Device code phishing — **всё наоборот**:

- Домен **настоящий** (`acmeid.example`), сертификат валидный.
- Пароль **не вводится** на стороне атакующего — только короткий код.
- MFA **проходится честно** — жертва подтверждает себя.
- Единственное, что выдаёт атаку, — **контекст**: зачем вам вдруг подтверждать вход в ТВ-приложение, которого у вас нет.

Поэтому защита смещается на **внимательность** и на UI: провайдер обязан на экране подтверждения показать **какое** приложение и **какие** права получает. Если этого нет — жертва «слепо» отдаёт доступ.

## Шаг 8: что проверять в отчёте и как не навредить

Для доказательства device code phishing достаточно показать **полный сценарий** на своём аккаунте: запустил flow → получил `user_code` → «убедил» тестового пользователя подтвердить → получил токены на устройстве → прочитал профиль. Это доказывает impact без реального фишинга людей.

Важно не навредить: не подтверждай чужие коды, не перебирай `user_code` массово (это нагрузка и шум), не используй реальные аккаунты. Проверяй на своих тестовых учётках и фиксируй минимальный воспроизводимый сценарий. Хороший отчёт — это «вот цепочка, вот токен, вот доступ», а не «я подобрал чей-то код».

## Что мы теперь знаем

- **Device code flow** — вход на устройствах без клавиатуры (ТВ, CLI).
- `user_code` — для человека, `device_code` — секрет устройства.
- **Фишинг:** жертва подтверждает чужой `user_code` → токены уходят атакующему.
- Признаков фишинга мало: настоящий домен, правильный сертификат.
- Ошибки: нет rate limit на `user_code`, нет привязки к сессии, не показывается приложение.
- `device_code` — секрет; при утечке токен крадётся напрямую.

## На что смотреть дальше

- **Экран подтверждения:** показывает ли он **какое** приложение и **какие** права запрашивает.
- **Rate limit:** посчитай неудачные вводы `user_code`.
- **Привязка:** можно ли подтвердить чужой `device_code`.
- **Scope:** широкие права (`mail`, `offline_access`) увеличивают impact.
- **Одноразовость `device_code`:** принимается ли он повторно.
- **Длительность кода:** чем дольше живёт `user_code`, тем больше окно для фишинга и перебора.
- **Привязка к клиенту:** можно ли получить токен, зная `device_code`, но подставив другой `client_id`.
- **Одноразовость подтверждения:** можно ли подтвердить один `user_code` повторно.
- **Логирование:** фиксируется ли, с какого устройства и IP подтверждён вход.

## Как выглядит обмен по шагам

Полезно держать в голове полную последовательность, потому что каждая атака — это
вмешательство в один из её шагов.

```text
устройство            провайдер                человек
   |  POST /device/code   |                       |
   |--------------------->|                       |
   |  device_code         |                       |
   |  user_code, uri      |                       |
   |<---------------------|                       |
   |                      |   открывает uri,      |
   |                      |<--вводит user_code----|
   |                      |   подтверждает scope  |
   |  POST /device/token  |                       |
   |--------------------->|                       |
   |  access_token,       |                       |
   |  refresh_token       |                       |
   |<---------------------|                       |
```

На первом шаге устройство **анонимно**: оно ещё не знает, кто пользователь.
Именно поэтому `user_code` — это «обещание», а не аутентификация. Сервер не может
отличить, кто ввёл код: само устройство или атакующий, который переслал код жертве.
Связь между «устройством, начавшим flow» и «человеком, подтвердившим код» нигде
не проверяется криптографически.

## Чем это отличается от authorization code + PKCE

В обычном веб-входе браузер идёт на провайдера, провайдер возвращает `code` **на
`redirect_uri`, зарегистрированный за клиентом**, а клиент меняет код на токен.
`redirect_uri` жёстко привязан к приложению, поэтому перехватить код сложно, а
**PKCE** добавляет `code_verifier`, известный только инициатору.

В device flow `redirect_uri` нет вовсе: связь между устройством и подтверждением
держится **только** на `user_code`/`device_code`. Здесь нет `code_verifier`,
который доказал бы, что токен получает тот же клиент, что начал flow. Поэтому
проверка `client_id` при опросе `/device/token` критична: без неё токен может
получить кто угодно, знающий `device_code`. Это отличие и объясняет, почему
device flow традиционно рекомендуют только для устройств, которым пользователь
доверяет физически.

## Практика: минимальный PoC на своём стенде

Чтобы убедиться, что вы поняли поток, воспроизведите его целиком на своём
тестовом провайдере:

```bash
# 1. устройство просит код
$ curl -s 'https://acmeid.example/device/code' \
    -d 'client_id=shop-tv&scope=openid%20profile%20offline_access'
# 2. сохраняем device_code и user_code
# 3. подтверждаем user_code в браузере (свой аккаунт)
# 4. устройство опрашивает токен
$ curl -s 'https://acmeid.example/device/token' \
    -d 'grant_type=urn:ietf:params:oauth:grant-type:device_code' \
    -d 'device_code=<сохранённый>&client_id=shop-tv'
# 5. проверяем, что токен рабочий
$ curl -s 'https://acmeid.example/userinfo' -H 'Authorization: Bearer <access_token>'
```

Если на шаге 5 вернулся профиль — поток собран. Теперь варьируйте: уберите
`client_id` из шага 4, подставьте **другой** `client_id`, повторите запрос
`device/token` дважды. Каждый успешный «лишний» вариант — отдельная находка,
и её легко показать в отчёте одной строкой команды и ответом сервера.

## Куда дальше

Мы разобрали атаку на поток устройства. Есть и более тонкие атаки на сам процесс обмена — **mix-up** между провайдерами и **downgrade PKCE**. Об этом — следующий урок.

## Где пригодится

- **CTF (Web):** задачи с device flow — фишинг и перебор кода ведут к токену.
- **Bug bounty:** device code phishing и утечка `device_code` — high; докажи доступ к аккаунту.
- **Пентест:** проверка экрана подтверждения, rate limit и привязки `user_code`.
- **Работа (AppSec):** показывать приложение и scope, ограничивать попытки, привязывать код к сессии.
