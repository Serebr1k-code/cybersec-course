**Taint-анализ** (анализ заражения) отслеживает распространение «заражённых» данных от источников (sources) до опасных мест (sinks): если пользовательский ввод доходит до `system`/`memcpy`/SQL-запроса без проверки, это уязвимость. Вместе с **динамической бинарной инструментацией (DBI)** он позволяет анализировать закрытые бинарники, отслеживая потоки данных в рантайме. Урок разбирает статический и динамический taint, фреймворки (Triton, libdft, PIN, DynamoRIO, QBDI) и полный разобранный пример.

## Что такое taint-анализ

Идея: помечаем входные данные **меткой (taint)** и следим, как метка распространяется через вычисления. Если «заражённое» значение достигает опасной операции без санитизации — потенциальная уязвимость.

- **Source** — точка ввода (stdin, argv, сокет, файл).
- **Sink** — опасная операция (`system`, `execve`, `memcpy`, `strcpy`, SQL).
- **Sanitizer** — проверка/очистка, снимающая метку.

Применения: поиск инъекций, переполнений, утечек; классификация входов; понимание потока данных в малвари.

## Статический vs динамический taint

| Аспект | Статический | Динамический (DBI) |
|---|---|---|
| Что анализирует | код/IR без запуска | реальное исполнение |
| Покрытие | все пути (в идеале) | только исполненные |
| Точность | ложные срабатывания | точные факты |
| Требует | исходники/IR | запуск в инструментированной среде |
| Инструменты | CodeQL, Joern | Triton, libdft, PIN |

Статический taint (например, в Ghidra через скрипты или CodeQL для исходников) даёт широкое покрытие, но много ложных срабатываний. Динамический — точные пути, но только те, что реально исполнились.

## DBI-фреймворки

**Динамическая бинарная инструментация** вставляет код на каждую инструкцию, отслеживая регистры/память.

- **Intel PIN** — зрелый DBI, API на C++; `-t` для инструмента.
- **DynamoRIO** — DBI с клиентами на C/C++.
- **QBDI** — лёгкий DBI (QuarkslaB), удобен для эмуляции/taint.
- **Triton** — C++/Python фреймворк: символьное исполнение + taint.
- **libdft** — taint через Valgrind.
- **Valgrind** — memcheck-основа, но медленный.

```bash
# Intel PIN
pin -t ./mytool.so -- ./target
# DynamoRIO
drrun -c ./myclient.so -- ./target
```

## Triton: символьный + taint

Triton объединяет символьное исполнение и taint-анализ — мощный для реверса.

```python
from triton import *

ctx = TritonContext()
ctx.setArchitecture(ARCH.X86_64)
# пометить вход как tainted
ctx.taintRegister(ctx.registers.rax)
# исполнить инструкции
for opcode in disasm:
    inst = Instruction(opcode)
    ctx.processing(inst)
    if ctx.isRegisterTainted(ctx.registers.rdi):
        print("rdi tainted at", hex(inst.getAddress()))
```

Triton позволяет и «раскрасить» конкретный ввод, и решать ограничения (Z3 внутри).

## libdft: taint через Valgrind

`libdft` — популярный taint-фреймворк на базе Valgrind. Помечает ввод и отслеживает распространение.

```bash
# сборка и запуск (по документации libdft)
./libdft -file:stdin ./target
# или через VEX-инструмент с политикой источников/синков
```

Минус — скорость (Valgrind эмулирует), плюс — простота и точность на исполненных путях.

## Разобранный пример: найти command injection

Дано: сервер читает `host` из сети и вызывает `system("ping " + host)`.

**Шаг 1. Пометить source.** Ввод из сокета помечаем tainted.

**Шаг 2. Трассировать.** При исполнении видим, что метка доходит до аргумента `system`.

```python
# псевдо-Triton: taint от recv до system
ctx.taintRegister(reg_rax_after_recv)
# ... исполнение ...
if ctx.isRegisterTainted(ctx.registers.rdi) and current_func == "system":
    print("TAINTED FLOW into system:", current_func)
```

**Шаг 3. Вывод.** Данные из сети без санитизации попадают в `system` → command injection. Это точный результат: динамический taint показывает **реальный** поток, без ложных срабатываний статики.

## Практика: статический taint в Ghidra

Для закрытых бинарников можно реализовать упрощённый taint скриптом: пометить аргумент функции и проследить его использование через def-use.

```python
# идея: пометить параметр и идти по инструкциям, отслеживая регистр
from ghidra.program.model.lang import Register
# помечаем RDI, следим за MOV/LEA, ищем использование в CALL
```

Это менее точно, чем DBI, но не требует запуска и работает по всем путям.

## Частые ошибки и подводные камни

- **Только исполненные пути.** Динамический taint не видит непройденный код — комбинируйте со статикой.
- **Ложные срабатывания статики.** Проверяйте найденные потоки динамически.
- **Неправильные источники/синки.** Пропущенный sink = пропущенная уязвимость; составляйте список.
- **Санитайзеры.** Некоторые «очистки» неполны (blacklist вместо whitelist) — метка должна сниматься только корректной проверкой.
- **Скорость.** DBI/Valgrind замедляют в десятки раз; ограничивайте объём.
- **Символические указатели.** Косвенные потоки данных требуют аккуратной трактовки.

## Что дальше / решение

Маршрут: **определить sources/sinks → пометить ввод → трассировать (Triton/libdft) → найти поток в sink без санитайзера → подтвердить**. Для исходников — CodeQL/Joern; для бинарников — Triton/DBI. Дальше — `reversing-kernel-taint`, `reversing-concolic` и `reversing-symbolic-execution`.

## Построение карты sources и sinks

Перед анализом составьте списки — это половина успеха.

**Sources:** `recv`, `read`, `scanf`, `fgets`, `getenv`, `argv`, чтение файлов, `recvfrom`.
**Sinks:** `system`, `popen`, `execve`, `memcpy`, `strcpy`, `sprintf`, SQL-exec, `write` в опасный контекст.

```bash
# найти синки в бинарнике
nm -D ./target | grep -E 'system|popen|execve|strcpy|sprintf'
```

Далее в Triton/DBI помечаем данные из sources и проверяем, достигают ли они sinks.

## Динамический taint через QBDI

QBDI (QuarkslaB Dynamic Binary Instrumentation) — лёгкий DBI, удобный для taint и эмуляции.

```cpp
// псевдо-QBDI: колбэк на каждую инструкцию
QBDI::VM vm;
vm.addCodeCB(QBDI::PREINST, [](QBDI::VM *vm, QBDI::GPRState *gpr, QBDI::FPRState *fpr) {
    QBDI::rword pc = vm->getInstAnalysis()->address;
    // если pc в source/sink — обработать
    return QBDI::CONTINUE;
});
vm.call(nullptr, (QBDI::rword) target);
```

QBDI быстрее Valgrind и не требует пересборки; подходит для встраивания в анализатор.

## Комбинирование: taint + символическое

Triton позволяет не только трассировать метки, но и строить символьные выражения из tainted-данных. Это даёт лучшее из двух миров: вы знаете **и** что данные заражены, **и** какое выражение их породило.

```python
from triton import *
ctx = TritonContext(ARCH.X86_64)
ctx.symbolizeRegister(ctx.registers.rax, "input")
# ... обработка инструкций ...
expr = ctx.getSymbolicRegister(ctx.registers.rdi)   # выражение до sink
```

Из выражения можно построить ограничения (например, «содержит `;`») и решить их Z3 — то есть **синтезировать** эксплойт-вход, а не только найти поток.

## Практика: taint для реверса протоколов

В протоколах taint помогает понять, какие байты сообщения влияют на решение программы. Пометьте поле, проследите его влияние — и вы узнаете, какие поля критичны, а какие игнорируются. Это ускоряет реверс форматов и фаззинг (мутируйте только tainted-байты).

## Ограничения и как их обходить

- **Скорость** — DBI замедляет; анализируйте только целевые функции.
- **Неполное покрытие** — динамика видит лишь исполненные пути; дополняйте статикой.
- **Косвенные потоки** — taint через указатели/функции требует осторожной политики.
- **Санитайзеры** — модель должна снимать метку только при корректной проверке; иначе ложные тревоги.

## Итоговый маршрут taint-анализа

1. Определить sources/sinks.
2. Выбрать инструмент: Triton (symbolic+taint), libdft (Valgrind), QBDI/PIN (DBI).
3. Пометить ввод и трассировать.
4. Найти поток source→sink без санитайзера.
5. Подтвердить динамически (реальный вход вызывает уязвимость).
6. Для исходников — CodeQL/Joern как статическая проверка покрытия.

## Taint в исходниках: CodeQL и Joern

Когда исходники доступны, статический taint-анализ даёт широкое покрытие.

```bash
# CodeQL: запросы на taint-потоки
codeql database create db --language=cpp --source-root=./src
codeql database analyze db codeql/cpp-queries:Security/CWE-078 --format=sarif -o out.sarif
# Joern (CPG)
joern-parse ./src
joern --script taint.sc
```

Преимущество — анализируется **весь** код, включая непройденные пути. Недостаток — ложные срабатывания; подтверждайте динамикой (Triton/DBI).

## Построение собственного taint-трекера

Для узкой задачи (например, отследить один вход до одного sink) можно написать упрощённый трекер на Triton или поверх Frida.

```python
from triton import *
ctx = TritonContext(ARCH.X86_64)
ctx.setConcreteRegisterValue(ctx.registers.rsp, 0x7ffff000)
# пометить аргумент функции как tainted
ctx.taintRegister(ctx.registers.rdi)
for op in code:
    inst = Instruction(op)
    ctx.processing(inst)
    if ctx.isRegisterTainted(ctx.registers.rdi):
        print(hex(inst.getAddress()), inst.getDisassembly())
```

Такой трекер даёт точный список инструкций, по которым распространилась метка — полезно для отчёта и понимания потока.

## Taint и утечки данных

Taint-анализ применяется и для поиска **утечек секретов**: помечаем ключ/пароль как source и проверяем, не доходит ли он до сети/логов/файлов (sink). Это дополняет статический поиск секретов динамической проверкой реального потока.

## Сравнение с символьным исполнением

| Аспект | Taint | Symbolic (angr) |
|---|---|---|
| Вопрос | «куда течёт ввод?» | «какой ввод даёт цель?» |
| Метод | метки + распространение | ограничения + SMT |
| Взрыв | нет | есть (пути) |
| Выход | поток source→sink | конкретный вход |
| Комбинация | Triton даёт оба | Triton даёт оба |

Обе техники дополняют друг друга: taint находит подозрительные потоки, символьное исполнение — конкретный вход.

## Заключение

Taint-анализ отвечает на вопрос «куда течёт ввод», динамическая инструментация даёт точные факты о реальном исполнении, а Triton объединяет taint с символьными выражениями для синтеза входов. Комбинируйте со статикой (CodeQL/Joern) для полного покрытия и всегда подтверждайте найденный поток реальным запуском.
