## Вопрос, с которого всё начинается

У тебя есть функция, которая берёт данные от пользователя и что-то с ними делает. Хочется понять:
**дошли ли** эти данные до опасной операции (`system`, `memcpy`, сравнение с секретом) или были
обезврежены проверкой? Читать код глазами можно, но в большой программе поток данных разветвляется
и теряется.

Для этого придумали **taint-анализ** (анализ заражения): помечаем входные данные «меткой» и следим,
как эта метка распространяется по вычислениям. Если заражённое значение доходит до опасного места
без очистки — это потенциальная проблема. Разберём его на маленьком примере, написав свой
taint-движок.

## Наш пример

Возьмём функцию `process`: она читает первый байт входа, прибавляет 5, смешивает с константой 7 и
возвращает результат. В `main` результат сравнивается с `0x41`:

```c
static int process(const char *in){
    int x = in[0];        /* заражено: пришло из ввода */
    int y = x + 5;        /* заражено */
    int z = 7;            /* НЕ заражено: константа */
    int w = y ^ z;        /* заражено */
    return w;
}
int main(int argc, char **argv){
    if (process(argv[1]) == 0x41) puts("SINK REACHED");
    ...
}
```

Вопрос: доходит ли вход (`argv[1]`) до сравнения? Ответ «да» мы получим автоматически, а не на глаз.

Термины сразу: **source** — точка, откуда приходят данные (здесь — аргумент `argv[1]`); **sink** —
опасная операция (здесь — сравнение); **sanitizer** — проверка, снимающая метку.

## Шаг 1: что делает функция — статический взгляд

Сначала посмотрим на `process` в дизассемблере:

```
$ objdump -d -M intel target | sed -n '/<process>:/,/ret/p'
  40112a:  mov    QWORD PTR [rbp-0x18],rdi     ; сохранили указатель in
  401132:  movzx  eax,BYTE PTR [rax]           ; x = in[0]
  401138:  mov    DWORD PTR [rbp-0x10],eax     ; x на стек
  40113e:  add    eax,0x5                       ; y = x + 5
  401141:  mov    DWORD PTR [rbp-0xc],eax      ; y на стек
  401144:  mov    DWORD PTR [rbp-0x8],0x7       ; z = 7
  40114e:  xor    eax,DWORD PTR [rbp-0x8]       ; w = y ^ z
  401154:  mov    eax,DWORD PTR [rbp-0x4]       ; return w
```

Человек видит поток, но чтобы это делала **машина**, нужен формальный механизм. Статический анализ
(например, CodeQL или Joern) покрывает все пути, но даёт ложные срабатывания. Мы сделаем
**динамический** taint: будем реально исполнять код и следить за метками — точно, но только по
одному пути.

## Шаг 2: исполняем код в эмуляторе

Чтобы перехватывать каждую инструкцию, используем **эмулятор** `unicorn` (он исполняет машинный код
без реального процесса) и дизассемблер `capstone` (он разбирает инструкцию на операнды). Настроим
память, положим во входной буфер байт и пометим его заражённым:

```python
from unicorn import *
from unicorn.x86_const import *
mu = Uc(UC_ARCH_X86, UC_MODE_64)
mu.mem_map(0x400000, 0x10000)          # код
mu.mem_map(0x600000, 0x1000)           # входной буфер
taint_mem = {0x600000: True}           # вход заражён
mu.reg_write(UC_X86_REG_RDI, 0x600000) # process(in) -> rdi = &in
mu.hook_add(UC_HOOK_CODE, hook_code)   # вызывать hook на каждой инструкции
```

## Шаг 3: правило распространения метки

Вся суть taint-анализа — одно правило: **если хоть один источник инструкции заражён, заражён и её
результат**. В `hook_code` мы декодируем инструкцию `capstone`-ом и смотрим операнды: какие читаются
(READ), какие пишутся (WRITE). Если заражён любой прочитанный регистр или байт памяти — метим
записанный регистр или область памяти.

```python
def hook_code(mu, addr, size, ud):
    insn = next(md.disasm(bytes(mu.mem_read(addr, size)), addr))
    src = any(is_tainted(op, insn, mu) for op in insn.operands if op.access & CS_AC_READ)
    for op in insn.operands:
        if op.access & CS_AC_WRITE:
            set_taint(op, insn, mu, src)
```

Здесь есть тонкости, которые и делают taint-анализ нетривиальным. `xor eax, eax` **обнуляет**
регистр — результат не зависит от входа, поэтому его метку надо снять. `lea rax, [rbx]` вычисляет
**адрес**, а не читает память, — метку с адреса брать нельзя. Плюс нужно нормализовать имена
регистров: запись в `al`/`eax` меняет и `rax`, поэтому метку хранят по 64-битному «родителю».

## Шаг 4: смотрим результат

Запускаем эмуляцию `process` от входа до `ret` и печатаем трассу с метками:

```
0x401132  movzx eax, byte ptr [rax]        src_tainted=True    ; прочли заражённый вход
0x401138  mov dword ptr [rbp - 0x10], eax  src_tainted=True
0x40113e  add eax, 5                       src_tainted=True
0x401144  mov dword ptr [rbp - 8], 7       src_tainted=False   ; константа не заражает
0x40114e  xor eax, dword ptr [rbp - 8]     src_tainted=True
0x401154  mov eax, dword ptr [rbp - 4]     src_tainted=True
--- final tainted registers ---
TAINTED rax
```

Читаем вывод: вход (`in[0]`) заражён, метка прошла через `add 5` и `xor` и осталась на возвращаемом
значении `rax`. Константа `z = 7` метки **не** получила — и это правильно, ведь от входа она не
зависит. А раз `rax` заражён и он же идёт в сравнение в `main`, значит вход **достигает sink**. Мы
ответили на вопрос автоматически.

## Шаг 5: где это применяется

Динамический taint (через эмулятор, DBI или ptrace) точен: он видит только реально исполненные
инструкции. Статический (CodeQL, Joern) покрывает все пути, но ошибается чаще. На практике их
комбинируют. Применения: поиск инъекций (заражённый ввод дошёл до `system`), обнаружение
переполнений, классификация входов малвари, понимание, какие данные влияют на ключевые решения.

Ограничения тоже важно знать: если ввод **не** заражён (например, значение пришло из файла, который
мы не пометили), анализ ничего не найдёт. Если sanitizer реально проверяет данные, метка снимается —
и это правильно. А ветвление по заражённому значению («taint in control flow») — отдельная тема,
которую наш простой движок не отслеживает. В инструментах это решается тем, что метка хранится не
как флаг, а как множество источников, и её переносят и на флаги условных переходов.

## Что мы теперь знаем

- Taint-анализ отслеживает распространение метки от **source** (вход) к **sink** (опасная операция).
- Правило одно: результат инструкции заражён, если заражён любой её источник.
- Динамический taint исполняет код (unicorn) и перехватывает каждую инструкцию (capstone).
- `xor reg,reg` и `lea` — исключения, где метку надо снимать/не брать.
- Имена регистров нормализуют: `al`/`eax`/`rax` — один и тот же «родитель».
- Sanitizer снимает метку; статический и динамический taint дополняют друг друга.

## Taint на реальных бинарниках: DBI-фреймворки

Свой движок на Unicorn хорош для обучения, но реальный бинарь удобнее инструментировать динамически:

- **Frida Stalker** — перехватывает каждую инструкцию в живом процессе, умеет отслеживать регистры и память;
- **DynamoRIO** — полноценный DBI с API для анализа на уровне инструкций;
- **QBDI** — лёгкий DBI с готовыми колбэками на чтение/запись;
- **Triton** — умеет и taint, и символическое исполнение в одном фреймворке.

Схема та же: помечаем источник, на каждом колбэке переносим метку по правилу «заражён результат, если заражён источник», проверяем sink. Отличие от Unicorn — скорость и совместимость с системными вызовами.

## Пример: taint для поиска уязвимости

Классический сценарий — формат-строка или инъекция. Помечаем данные из `recv()` заражёнными и следим, дойдут ли они до `system`/`execve` без прохождения через санитайзер (проверку белого списка). Если метка дошла — есть кандидат. Так же ловят use-after-free: помечаем указатель, следим за его разыменованием уже после `free`.

## Ограничения точности

Taint-анализ — не волшебство:

- **Недо-taint:** источник не помечен (данные пришли из файла/сети, о котором забыли).
- **Пере-taint:** метка распространяется слишком широко (например, через адрес), давая ложные срабатывания.
- **Implicit flow:** ветвление по заражённому значению меняет управление, но простой движок метку на флаги не переносит.
- **Санитайзеры:** реальная проверка должна снимать метку, иначе будут ложные тревоги.

Поэтому на практике taint комбинируют с символическим исполнением и ручным чтением кода.

## Taint vs symbolic: что выбрать

Два подхода отвечают на разные вопросы. **Taint** спрашивает: «влияет ли вход на эту точку?» — и даёт ответ быстро, по одному реально исполненному пути, но без точного значения. **Символическое исполнение** спрашивает: «какой вход приведёт к этой ветке?» — и решает ограничения, находя конкретные значения, но дороже и с проблемой «path explosion». На практике их комбинируют: сначала taint-анализом находят подозрительные потоки данных (кандидаты на sink), а затем символическим исполнением строят конкретный вход, который до этого sink доводит. Triton умеет держать обе модели в одном движке: метки для taint и символьные выражения для solver. Такой тандем и лежит в основе современных инструментов поиска уязвимостей.

## Куда дальше

Мы отследили поток данных вручную, на уровне инструкций. В следующем уроке разберём **символическое
исполнение** — подход, который не просто метит данные, а решает ограничения на них и находит вход,
ведущий к нужной ветке. А пока главное запомни: taint-анализ отвечает на вопрос «дошли ли входные
данные до опасного места», и делается это одним правилом распространения метки.

## Где пригодится

- **Поиск уязвимостей:** заражённый ввод, дошедший до `system`/`memcpy`, — кандидат в инъекцию.
- **Malware analysis:** понять, какие данные влияют на решения образца.
- **Fuzzing:** определять, какие байты входа реально влияют на поведение (coverage-guided).
