## Вопрос, с которого всё начинается

Ты разбираешь сотню бинарников, и каждый раз делать одно и то же руками надоедает. Хочется автоматизировать: «найди все функции, вызывающие `strcpy`, и покажи их аргументы». Как устроен инструмент, который позволяет это писать?

## Наш пример

`target.bin` — небольшой бинарник. Мы откроем его через **Binary Ninja Python API** и вытащим декомпилированный вид функции, чтобы понять её логику и найти артефакт.

## Шаг 1: зачем нужен Binary Ninja

Binary Ninja — коммерческий дизассемблер/декомпилятор с сильным API. Его главное отличие — **промежуточные представления (IL)**: код поднимается по уровням абстракции, и на каждом уровне можно анализировать и трансформировать его скриптом.

Это делает BN не просто «интерактивным инструментом», а **платформой для автоматизации**: можно писать плагины, искать паттерны, деобфусцировать.

## Шаг 2: уровни IL

Binary Ninja поднимает код по ступеням:

| Уровень | Что это |
|---|---|
| **LLIL** | Low-Level IL — почти ассемблер, но в едином виде для всех архитектур |
| **MLIL** | Medium-Level IL — восстановлены переменные, вызовы, стек |
| **HLIL** | High-Level IL — высокоуровневый C-подобный вид (то, что показывает декомпилятор) |

Ключевая идея: анализ на **MLIL/HLIL** не зависит от архитектуры. Один и тот же скрипт работает и на x86, и на ARM.

## Шаг 3: как выглядит HLIL

Открыв функцию, BN показывает HLIL примерно так:

```c
int32_t check(char* arg1)
{
    int32_t result = strcmp(arg1, "MAGIC");
    if (result == 0)
        return 1;
    return 0;
}
```

Это не исходник — это результат подъёма из ассемблера. В HLIL уже есть `if`, вызовы и переменные, но типы могут быть угаданы неверно (`int32_t` там, где на самом деле указатель).

## Шаг 4: скрипт через API

Типичный скрипт открывает бинарник, находит функцию и печатает её HLIL:

```python
import binaryninja as bn
bv = bn.open_view("target.bin")
for func in bv.functions:
    if "check" in func.name:
        print(func.hlil)
```

Запуск:

```bash
$ python3 bn_script.py target.bin
int32_t check(char* s)
{
    if (strcmp(s, "MAGIC") == 0)
        return 1;
    // nto{bnil_hl1l_aut0m4t10n}
    return 0;
}
```

Мы нашли функцию проверки и артефакт — без ручного дизассемблирования.

## Шаг 5: зачем уровни, а не один

Почему три IL, а не один? Потому что разные задачи требуют разной точности:

- **LLIL** — когда важны конкретные инструкции (обход anti-disassembly, анализ байтов);
- **MLIL** — когда нужно отслеживать переменные и вызовы (data-flow, taint);
- **HLIL** — когда нужна читаемая логика (поиск багов, понимание алгоритма).

Автоматизация на HLIL проста, но может «сгладить» важные детали. На MLIL — точнее, но требует больше кода.

## Шаг 6: практические сценарии автоматизации

Что реально пишут на BN API:

1. **Пакетный анализ.** Пройти по папке образцов, найти вызовы опасных функций, собрать отчёт.
2. **Поиск констант.** Найти все функции, использующие конкретный байт-паттерн или строку.
3. **Деобфускация.** На MLIL применить проход, который сворачивает opaque-предикаты.
4. **Сравнение версий.** Сопоставить функции двух сборок и найти изменения.
5. **Извлечение интерфейсов.** Автоматически восстановить прототипы функций по вызовам.

## Шаг 7: сравнение с другими инструментами

BN не единственный. IDA — стандарт с богатым Hex-Rays, Ghidra — бесплатный с P-Code. BN выделяется **чистотой API** и **открытыми IL**: их легко читать и трансформировать. Для командной автоматизации BN часто удобнее IDA, а для бесплатного анализа — Ghidra. Знание BN полезно, потому что его IL-модель похожа на Ghidra P-Code и переносится.

## Что мы теперь знаем

- Binary Ninja поднимает код через LLIL → MLIL → HLIL.
- HLIL — высокоуровневый C-подобный вид, MLIL — с переменными, LLIL — низкоуровневый.
- API на Python позволяет автоматизировать анализ.
- Анализ на MLIL/HLIL не зависит от архитектуры.
- BN удобен для пакетной автоматизации и деобфускации.

## Шаг 8: MLIL и data-flow вручную

MLIL удобен для отслеживания данных. Пример: найти, откуда пришло значение в вызов.

```python
for insn in func.mlil:
    if insn.operation == MediumLevelILOperation.MLIL_CALL:
        for var in insn.vars_read:
            print("arg from:", var)
```

Так можно восстановить цепочку: аргумент функции → буфер → результат `recv`. Это основа для поиска taint-путей (например, «доходит ли сетевой ввод до `memcpy`»).

## Шаг 9: перекрёстные ссылки (xrefs)

BN даёт API для xrefs — кто вызывает функцию, кто ссылается на строку:

```python
for ref in bv.get_code_refs(addr):
    print(ref.function, ref.address)
```

Это ключ к трассировке: найдя строку `CreateRemoteThread`, ты через xrefs поднимаешься к функции, которая её использует, а затем — ко всей цепочке инъекции.

## Шаг 10: патчинг и аннотации через API

BN позволяет не только читать, но и **менять** представление:

```python
func.name = "decrypt_config"
bv.set_comment_at(addr, "XOR key = 0x5e")
func.set_user_type(...)
```

Так можно автоматически переименовывать функции по эвристике (например, все, что вызывают `memcpy` с константным размером) и добавлять комментарии — это ускоряет ручной разбор.

## Шаг 11: сравнение версий бинарников

Типовой сценарий: есть патченная версия, надо найти исправление. Загружаешь обе, сопоставляешь функции и ищешь различия:

```python
a = bn.load("app_v1")
b = bn.load("app_v2")
# сопоставить функции по хешу/сигнатуре и вывести изменённые
```

Изменённая функция часто и есть место исправленной уязвимости. Это тот же принцип, что version-diff, но на уровне инструмента.

## Шаг 12: плагины и headless-режим

BN работает и без GUI — в **headless**-режиме:

```bash
$ python3 script.py target.bin    # через BinaryNinja API без интерфейса
```

Это позволяет встроить анализ в CI: прогонять сотни образцов, собирать отчёты, искать сигнатуры. Именно поэтому BN любят в автоматизации.

## Шаг 13: таблица возможностей

| Задача | Уровень | API |
|---|---|---|
| Читаемая логика | HLIL | `func.hlil` |
| Трассировка данных | MLIL | `func.mlil` |
| Точные инструкции | LLIL | `func.llil` |
| Xrefs | — | `bv.get_code_refs` |
| Аннотации | — | `set_comment_at` |
| Пакетно | headless | `binaryninja` без GUI |

## Шаг 14: итоговый порядок работы

Открыть бинарник в headless или GUI. Пройти по функциям, найти интересные по строкам/импортам (xrefs). Поднять их в HLIL для понимания логики. При необходимости спуститься в MLIL для трассировки данных. Автоматизировать повторяющееся (переименование, отчёты). Главное: **декомпилятор — это многоуровневый подъём, и каждый уровень доступен скрипту**.

## Шаг 15: SSA-форма в MLIL

MLIL бывает в двух видах: обычный и **SSA** (Static Single Assignment), где каждой переменной присваивают значение ровно один раз. SSA удобен для анализа: он делает зависимости данных явными.

```python
ssa = func.mlil.ssa_form
for var in ssa.vars:
    print(var, "defs:", ssa.get_ssa_var_definition(var))
```

Так легко отследить, откуда пришло значение: у каждой версии переменной есть единственное определение. Это основа для taint-анализа и поиска путей «источник → сток».

## Шаг 16: поиск по сигнатурам

BN позволяет искать байт-паттерны и функции по сигнатуре. Типовой сценарий: найти все вызовы конкретной функции-обёртки или все места с магической константой.

```python
for addr, size in bv.find_all_data(0, bv.end, b"\x7fELF"):
    print("ELF header @", hex(addr))
```

Для функций удобнее искать по имени/символам и через xrefs. Для неименованных — по характерной последовательности инструкций (сигнатура).

## Шаг 17: типы и восстановление структур

BN пытается восстановить типы автоматически, но не всегда верно. API позволяет задать их вручную:

```python
struct_t = bn.Type.parse("struct Config { int version; char url[64]; }")
bv.define_user_type("Config", struct_t)
bv.set_user_type_at(addr, "Config*")
```

После этого HLIL покажет поля по именам, а не смещениями. Это критично для разбора структур конфигов и протоколов.

## Шаг 18: BN и плагины

Экосистема BN — плагины, которые добавляют готовые проходы: деобфускация, эвристики, интеграция с внешними сервисами. Их можно писать на Python и распространять. Для реверса это значит: часть работы уже сделана сообществом, не нужно изобретать.

## Шаг 19: сравнение уровней по задачам

| Задача | Лучший уровень |
|---|---|
| Понять алгоритм | HLIL |
| Трассировать данные | MLIL (SSA) |
| Анализ конкретных инструкций | LLIL |
| Деобфускация | MLIL/LLIL |
| Поиск багов | HLIL + типы |

Выбор уровня — это выбор между читаемостью и точностью. Начинай с HLIL, спускайся при необходимости.

## Шаг 20: итоговый алгоритм автоматизации

Загрузи бинарник (GUI или headless). Пройди по функциям, найди интересные по строкам/импортам через xrefs. Подними в HLIL для логики. При необходимости — в MLIL/SSA для трассировки. Восстанови типы. Напиши проход, который делает это пакетно по всем образцам. Сохрани отчёт.

Это превращает BN из интерактивного инструмента в **платформу анализа**: один раз написанный скрипт обрабатывает тысячи бинарников. Главное: **декомпилятор — это многоуровневый подъём, и каждый уровень доступен скрипту**.

## Шаг 21: почему IL важен для деобфускации

Обфускаторы часто строят вычисления, которые выглядят запутанно в ассемблере, но тривиальны в MLIL. Пример — Mixed Boolean-Arithmetic (MBA): `(x | y) + (x & y)` на самом деле равно `x + y`. В ассемблере это десяток инструкций, а в MLIL — два оператора, которые легко свернуть проходом.

```python
# упрощение MBA-паттерна в MLIL
for block in func.mlil:
    for insn in block:
        # распознать (x|y)+(x&y) и заменить на x+y
        ...
```

Именно поэтому деобфускацию делают на IL, а не на байтах: там уже нет лишнего шума регистров и флагов.
