## Вопрос, с которого всё начинается

Ты нашёл в бинарнике проверку — `if (ввод == правильный)`. Дизассемблер показал условный переход: неверный ввод уходит на «Denied». Но правильный пароль неизвестен. Что если не вычислять его, а просто **заставить программу всегда идти по ветке успеха**? Это называется патчинг — изменение машинного кода прямо в файле.

## Наш пример

Возьмём маленькую программу `gate`, которая пускает только если первый аргумент начинается с `y`:

```bash
$ ./gate n
Denied
$ ./gate y
Access granted
```

Наша задача — сделать так, чтобы `./gate n` тоже пускало, не меняя исходники (их нет). Смотрим `main` в дизассемблере:

```text
0000000000001139 <main>:
    1148: cmpl   $0x1,-0x4(%rbp)      ; argc > 1 ?
    114c: jle    1176 <main+0x3d>     ; иначе -> Denied
    1159: movzbl (%rax),%eax
    115c: cmp    $0x79,%al            ; первый символ == 'y' ?
    115e: jne    1176 <main+0x3d>     ; иначе -> Denied
    1160: lea    ... Access granted
    1176: lea    ... Denied
```

Ключевая инструкция — `jne` по адресу `0x115e`: если символ не `y`, прыжок на «Denied». Если мы уберём этот прыжок, управление «провалится» прямо в ветку успеха.

## Шаг 1: как выглядит инструкция в байтах

`jne` — это короткий переход. Посмотрим его байты (`objdump` без `--no-show-raw-insn`):

```text
    115c: 3c 79                 cmp    $0x79,%al
    115e: 75 16                 jne    1176 <main+0x3d>
```

Инструкция `jne rel8` занимает два байта: `75` (опкод «jump if not equal») и `16` (смещение +0x16). Чтобы нейтрализовать переход, заменим оба байта на **`90 90`** — это **NOP** («no operation», ничего не делает). Тогда после `cmp` выполнение продолжится на следующей инструкции, то есть в ветке успеха.

Общая идея патчинга: **найти нужную инструкцию и заменить её байты** — либо NOP-ами (убрать действие), либо на другой переход, либо на прямую загрузку нужного значения.

## Шаг 2: патчим файл

Найдём эти байты в файле и заменим. Проще всего — на Python:

```python
d = bytearray(open('gate','rb').read())
idx = d.find(bytes.fromhex('7516'))     # опкод jne + смещение
print("found at file offset", hex(idx))
d[idx:idx+2] = b'\x90\x90'              # 75 16 -> 90 90
open('gate_patched','wb').write(d)
```

```text
found at file offset 0x115e
```

Смещение совпало с виртуальным адресом, потому что в этом бинарнике `.text` лежит в файле по тому же смещению, что и в памяти. В общем случае смещение считают так: `file_offset = vaddr - section_vaddr + section_offset`.

## Шаг 3: проверяем результат

Даём файлу право на исполнение и запускаем оба варианта:

```bash
$ chmod +x gate_patched
$ ./gate n
Denied
$ ./gate_patched n
Access granted
```

Патч сработал: та же программа с аргументом `n` теперь пускает. Посмотрим дизассемблер изменённого файла:

```text
    115c: cmp    $0x79,%al
    115e: nop
    1160: lea    ... Access granted
```

На месте `jne` — `nop`, и поток выполнения идёт прямо в «Access granted». Так проверка нейтрализована без знания пароля.

## Шаг 4: варианты патча

NOP — не единственный приём. По ситуации:

- **NOP-аут** — заменить проверяющую инструкцию (`cmp`, `test`) или переход на `90`.
- **Инверсия условия** — поменять `jne` (`75`) на `je` (`74`), `jz` на `jnz` — меняет логику на противоположную.
- **Безусловный переход** — заменить условный `jne` на `jmp` (`eb`), чтобы всегда прыгать.
- **Патч константы** — заменить сравниваемое значение (`cmp $0x79` → нужный байт).
- **Патч в памяти** — не файл, а процесс: в `gdb` командой `set {char}0x...=0x90` или через Frida.

Выбор зависит от того, что проще: убрать прыжок, инвертировать условие или подменить данные.

## Шаг 5: инструменты

- **Ручной hex-редактор** — для пары байт (HxD, `xxd` + правка).
- **`objdump`** — найти инструкцию и её байты; **`objcopy`** — извлечь/заменить секцию.
- **Ghidra / IDA** — умеют патчить прямо в GUI («Patch Instruction») и применять изменения в файл.
- **`gdb`** — патч в памяти на лету: `set *(char*)addr = 0x90`.
- **LIEF (Python)** — программный патч (о нём — в следующем уроке).

Для одной проверки хватает hex-редактора и `objdump`; для массовых/сложных правок — LIEF или GUI-дизассемблер.

## Шаг 6: на что смотреть дальше

Патчинг — это финал анализа, а не его замена. Порядок:

1. **Понять проверку** — где она и что решает.
2. **Найти точку ветвления** — условный переход или `cmp`.
3. **Решить, что менять** — прыжок, условие или константу.
4. **Запатчить и проверить** — запустить и убедиться, что поведение изменилось.
5. **Помнить о защитах** — контрольные суммы и подписи могут заметить патч (см. уроки про anti-tamper).

Частая ошибка — патчить не ту инструкцию: их может быть несколько похожих. Сверяй адрес и контекст перед заменой.

## Шаг 7: патч в отладчике (без правки файла)

Иногда файл трогать нельзя (подпись, целостность), и удобнее патчить процесс в памяти. В `gdb` это делается на лету. Запускаем, ставим точку на нужную инструкцию и меняем её байты:

```text
(gdb) break *0x55555555515e
(gdb) run n
(gdb) set {char}0x55555555515e = 0x90
(gdb) set {char}0x55555555515f = 0x90
(gdb) continue
Access granted
```

Мы заменили `jne` на `nop` прямо в работающем процессе. Так можно «примерить» патч, прежде чем править файл. Аналогично в Frida: `Memory.patchCode(addr, 2, code => { code[0]=0x90; code[1]=0x90; })`. Это особенно ценно против защит, которые проверяют целостность файла: в памяти патч виден, а на диске — нет.

## Что мы теперь знаем

- Инструкция — это байты; `jne rel8` = `75 XX`, а `nop` = `90`.
- **NOP-аут** убирает действие инструкции, **инверсия** меняет условие, **jmp** форсирует ветку.
- `file_offset = vaddr - section_vaddr + section_offset` — как найти байты по адресу.
- Патчить можно файл (Python/hex) или память (`gdb`/Frida).
- Патч нейтрализует проверку, но не заменяет её анализ — сначала пойми, что меняешь.

## Куда дальше

Мы патчили байты вручную. Но если правок много или они зависят от структуры файла, удобнее делать это программно. Этому посвящён следующий урок про **LIEF** — библиотеку для разбора и модификации ELF/PE/Mach-O из Python. А пока запомни: `75` → `90 90`, и проверка обойдена.

## Частые вопросы

- **Программа всё равно не пускает** — возможно, есть вторая проверка; найди её тем же способом.
- **Файл не запускается после патча** — ты заменил не те байты (сдвиг) или повредил заголовок; сверь адрес.
- **Патч «слетает» при запуске** — включена проверка целостности (anti-tamper); её тоже надо нейтрализовать.
- **Нужно пропатчить много файлов** — переходи на LIEF и автоматизируй (следующий урок).

## Где пригодится

- **CTF Reversing:** обход проверок пароля/лицензии патчем — частый и быстрый путь к флагу.
- **Обход лицензий/телеметрии:** нейтрализация проверок в реальном ПО (в рамках легального аудита).
- **Malware analysis:** отключить антианализ/шифрование, чтобы дальше наблюдать поведение.
- **Pwn/exploit dev:** понимание кодировки инструкций и NOP-слайдов прямо переносится в разработку эксплойтов.
