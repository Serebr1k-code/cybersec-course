Патчинг — это изменение кода бинарника, чтобы изменить его поведение: обойти проверку, отключить
anti-debug, исправить баг, вставить свою логику. Патчинг — естественное продолжение реверса: когда
вы поняли, как работает проверка, её можно «выключить». Но патчинг имеет свои ловушки: контрольные
суммы, самомодифицирующийся код, подписи, защита памяти. Этот урок — про инструменты, техники и
подводные камни патчинга в PE, ELF и памяти.

## Что можно патчить

- **Условные переходы** — превратить `jne` в `je`/`nop`/`jmp`, чтобы обойти проверку.
- **Вызовы** — заменить вызов функции на `nop`/возврат константы.
- **Константы** — изменить сравниваемое значение/ключ.
- **Инструкции** — переписать блок на свой код.
- **Данные** — строки, таблицы, флаги.

Патчинг бывает **на диске** (правим файл) и **в памяти** (меняем код работающего процесса). Первый
постоянен, второй удобен для экспериментов и обхода self-checks.

## Инструменты патчинга

| Инструмент | Тип | Назначение |
|---|---|---|
| **Keypatch** (IDA) | плагин | ассемблировать патч по месту |
| **x64dbg** | отладчик | Assemble/Patch в памяти |
| **IDA/Ghidra** | дизасм | правка байтов |
| **radare2** | CLI | `r2 -w`, `wa`, `wx` |
| **lief** (Python) | библиотека | правка ELF/PE/PE-структур |
| **pefile** (Python) | библиотека | правка PE |
| **HxD / 010 Editor** | hex-редактор | ручная правка |
| **dd / python** | CLI | точечная запись байтов |

## Техника: обход условного перехода

Классика — проверка вида:
```asm
call    check_password
test    eax, eax
jne     loc_ok          ; если не ноль — успех
; ... сообщение об ошибке ...
loc_ok:
```

Варианты патча:

1. **Инверсия**: `jne` → `je`. Меняем один байт опкода (`0x75` → `0x74`).
2. **NOP**: заменить `jne` на `nop`-ы (`0x90 0x90`) — поток всегда идёт дальше.
3. **Безусловный**: `jne` → `jmp` (`0xEB`).
4. **Форсировать возврат**: заменить `call check_password` на `mov eax,1; nop...`.

Пример в hex: `75 12` (`jne +0x12`) → `EB 12` (`jmp +0x12`) или `90 90`.

## Разобранный пример: патч проверки в IDA + Keypatch

Дано: ELF, функция `main` сравнивает ввод с секретом.

**Шаг 1. Найти проверку.** В IDA видим:
```asm
call    check
test    eax, eax
jz      short loc_fail
lea     rdi, aAccessGranted
call    puts
```

**Шаг 2. Патч.** Ставим курсор на `jz` (адрес, например, `0x401234`). Открываем Keypatch
(`Ctrl+Alt+K`), пишем:
```asm
nop
nop
```
Keypatch ассемблирует и применяет патч к базе (в памяти IDA). Чтобы сохранить в файл:
`Edit → Patch program → Apply patches to input file`.

**Шаг 3. Проверка.** Запускаем патченный бинарник — «Access granted» без правильного ввода.

## Разобранный пример: патч в x64dbg (в памяти)

Дано: Windows-крякми. Быстрее проверить гипотезу в отладчике.

```text
1. Загрузить ./target в x64dbg
2. Найти адрес проверки (Ctrl+G → адрес из статики)
3. Выделить инструкцию jne, нажать Space (Assemble)
4. Ввести: jmp 0x00401250   (или nop)
5. Применить — патч действует в памяти
6. Продолжить выполнение (F9) — проверка обойдена
```

Плюс: не нужно пересобирать файл. Минус: патч исчезает при перезапуске (можно сохранить через
`File → Patch file`).

## Патчинг ELF/PE программно

Для автоматизации — библиотеки.

**lief (ELF/PE/Mach-O):**
```python
import lief
b = lief.parse("target")
# найти и пропатчить байты по смещению
b.patch_address(0x1234, [0x90, 0x90])
b.write("target_patched")
```

**pefile (PE):**
```python
import pefile
pe = pefile.PE("target.exe")
# изменить точку входа или байты
pe.OPTIONAL_HEADER.AddressOfEntryPoint = 0x1500
pe.write("patched.exe")
```

**radare2:**
```bash
r2 -w ./target
[0x00401000]> s 0x401234        # перейти
[0x00401234]> wa nop            # ассемблировать (пишет)
[0x00401234]> wx 9090           # записать байты
[0x00401234]> wq                # сохранить
```

**Прямая запись байтов:**
```python
with open("target","r+b") as f:
    f.seek(0x1234)
    f.write(b"\x90\x90")
```

## Патчинг для обхода anti-debug

Частые патчи:

- **`IsDebuggerPresent`** → заменить `call` на `xor eax,eax` (возврат 0).
- **`ptrace(PTRACE_TRACEME)`** (Linux) → `nop` вызов.
- **PEB-проверки** → патч условного перехода.
- **`rdtsc`-тайминги** → `nop` пару инструкций/патч сравнения.
- **`int 3`/`0xCC`-проверки** → аппаратные breakpoints вместо патча.

Пример для Linux: программа вызывает `ptrace` и падает под gdb.
```asm
call    ptrace
cmp     rax, 0
jl      loc_fail
```
Патч: `call ptrace` → `xor eax,eax; nop; nop` (возврат 0).

## Проблемы патчинга

- **Контрольные суммы/хеши.** Бинарник может проверять свою целостность (CRC `.text`, хеш страниц).
  Патч «ломает» проверку → программа падает или ведёт себя иначе. Решение: патчить саму хеш-функцию,
  обновлять эталон, либо патчить в памяти после проверки.
- **Цифровые подписи.** PE-подпись (Authenticode) инвалидируется при любом изменении. Для обхода —
  снять проверку подписи (а не подписывать заново).
- **Выравнивание/длина.** Патч не должен менять длину инструкций, если нет места (иначе ломается
  смещение). Используйте `nop`-padding.
- **Относительные переходы.** При замене инструкции на более длинную относительное смещение может
  не поместиться — используйте абсолютный `jmp` (требует места) или `code cave`.
- **Анти-патч.** Код может детектить изменения (сравнение с эталоном) и «откатывать» или падать.
- **Самомодификация.** Патч может быть перезаписан самим кодом в рантайме.
- **ASLR/PIE.** Адреса смещаются — патчте по RVA/смещению в файле, а не по абсолютному адресу в памяти.

## Code cave и вставка своего кода

Когда нужно добавить логику, а места нет, используют **code cave** — неиспользуемый участок
(например, выравнивающие `nop`-ы в конце секции):

1. Найти достаточно нулей/`0xCC`/`nop`.
2. Записать туда свой код.
3. Перенаправить выполнение (`jmp cave` → ваш код → `jmp back`).

В PE/ELF можно также **добавить новую секцию** (через `lief`/`pefile`) и разместить код там.

## Разобранный пример: патч с code cave

Дано: нужно логировать значение перед проверкой, места нет.

**Шаг 1. Найти cave.** В IDA ищем длинную последовательность `0x00`/`0xCC` в `.text`.

**Шаг 2. Написать код** (например, сохранить `rax` в глобальную переменную).

**Шаг 3. Перенаправить.** Патчим исходное место: `jmp cave`, в cave — логика и `jmp back`.

**Шаг 4. Сохранить.** Apply patches to input file.

Так встраивается своя логика без пересборки исходников.

## Этическая и практическая сторона

- **Легитимно**: обход своих проверок при анализе, восстановление доступа к своему ПО, CTF,
  исследование уязвимостей в рамках авторизации.
- **Нелегитимно**: обход лицензий/DRM чужого ПО, модификация чужих систем без разрешения.
- **Для malware-анализа** патчинг — стандартный инструмент: отключаем anti-debug, чтобы изучить код.

Всегда в рамках авторизованной задачи.

## Что дальше / решение

1. Понять, что именно патчить (адрес, инструкция).
2. Проверить гипотезу в отладчике (патч в памяти).
3. Зафиксировать патч на диске (Keypatch/lief/r2).
4. Учесть проверки целостности и подписи.
5. Проверить результат: поведение изменилось, программа работает.
6. Задокументировать патч (адрес, байты до/после).

Принцип: **сначала пойми, потом патчь**. Патч без понимания — это стрельба вслепую, которая
приводит к нестабильности и «магическим» падениям.

## Справочная таблица: патч → инструмент

| Задача | Инструмент |
|---|---|
| Инвертировать `jne` | Keypatch, x64dbg, hex |
| NOP-нуть вызов | Keypatch, r2 `wa nop` |
| Форсировать возврат | x64dbg assemble |
| Патч ELF/PE в файле | lief, pefile |
| Патч в памяти | x64dbg, gdb `set` |
| Вставить код | code cave, new section |
| Обновить checksum | пересчитать/патч проверки |
| Снять подпись | патч проверки Authenticode |

## Патчинг в gdb: пошаговый сценарий

На Linux патч удобно проверять прямо в отладчике, без изменения файла:

```text
(gdb) file ./target
(gdb) break *0x401234            # адрес проверки
(gdb) run
(gdb) x/4i $pc                   # смотрим инструкции
   0x401234: jz 0x401250
(gdb) set {unsigned char}0x401234 = 0x90   # nop
(gdb) set {unsigned char}0x401235 = 0x90   # nop
(gdb) disas $pc,+8
(gdb) continue                   # проверка обойдена
```

Аналогично можно заменить инструкции на «форсировать успех»:
```text
(gdb) set {unsigned int}0x401234 = 0xb8019090   # mov eax,1 + nops
```
(`0x90 0x90 0x01 0xb8` в little-endian = `nop; nop; mov eax,1`).

Патч в памяти не меняет файл — идеально для быстрой проверки гипотез. Для постоянного патча
применяем Keypatch/lief и сохраняем.

## Автоматизация: скрипт массового патча

Когда патчей много (например, отключить несколько anti-debug проверок), пишем скрипт:

```python
import lief
PATCHES = {
    0x1234: b"\x90\x90",           # nop jz
    0x1300: b"\x31\xc0\x90",       # xor eax,eax; nop
    0x1400: b"\xeb\x00",           # jmp +0
}
b = lief.parse("target")
for off, data in PATCHES.items():
    b.patch_address(off, list(data))
b.write("target_patched")
print("patched", len(PATCHES), "sites")
```

Для PE можно тем же скриптом обновить контрольную сумму заголовка:
```python
import pefile
pe = pefile.PE("patched.exe")
pe.OPTIONAL_HEADER.CheckSum = pe.generate_checksum()
pe.write("patched.exe")
```

## Проверка и откат патча

Обязательные шаги после патча:

1. **Дизасм вокруг патча** — убедиться, что инструкции выровнены и логика корректна.
2. **Запуск** — программа стартует и ведёт себя ожидаемо.
3. **Функциональная проверка** — нужное поведение изменилось, остальное сохранилось.
4. **Откат при проблемах** — храните оригинал (`cp target target.orig`) и список патчей.
5. **Версионирование** — если патчей несколько, ведите лог (адрес, байты до/после, цель).

Никогда не патчьте единственную копию бинарника без бэкапа.

## Когда патчинг не работает

- **Сильная проверка целостности** (хеш всего образа на сервере) — локальный патч не поможет.
- **Подписанный код в защищённой среде** (Secure Boot, attestation) — изменение не запустится.
- **Самомодифицирующийся код** — перезапишет патч.
- **VM/девиртуализация** — патч нативной инструкции не меняет виртуальную логику; патчить нужно
  хендлер VM или байткод.

В этих случаях применяют комбинированные подходы: патч хеш-функции, рантайм-хуки, вмешательство
на уровне VM.

## Где пригодится

- **CTF Reversing:** «always accept» — классика; патч часто быстрее, чем полный реверс алгоритма.
- **Malware analysis:** отключение анти-дебага, чтобы спокойно отлаживать образец.
- **Аудит ПО:** проверка гипотез о ветвлениях, нейтрализация телеметрии в рамках легального анализа.
- **Pwn:** патчинг для обхода проверок перед разработкой эксплойта.
- **Собес:** вопросы про байты инструкций, NOP, разницу VA/offset — базовые для RE.
