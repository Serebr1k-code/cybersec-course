## Вопрос, с которого всё начинается

Ты смотришь на дизассемблер и видишь десятки строк вида `movzx eax, BYTE PTR [rax+0x404020]`,
`xor eax, 0x33`, `mov BYTE PTR [rax+0x404020], dl`. Понять общий смысл можно, но анализировать это
как **код** тяжело: инструкции разной длины, неявные побочные эффекты (флаги, регистры),
привязка к конкретному процессору. Хочется превратить машинный код в что-то единообразное, над чем
работают обычные алгоритмы анализа.

Для этого есть **промежуточное представление** — **IR** (Intermediate Representation). Лифтинг
(lifting) — это перевод машинных инструкций в IR. Разберём его на живом примере.

## Наш пример

Возьмём маленькую функцию `decrypt`: она расшифровывает массив байт XOR-ом с ключом и печатает
результат.

```c
static unsigned char buf[16] = {0x55,0x5f,0x52,0x54, ...};
static void decrypt(void){
    for (int i = 0; i < 16; i++) buf[i] ^= 0x33;
}
```

Компилируем без оптимизаций и смотрим тело цикла в `objdump`:

```
$ objdump -d -M intel decrypt | sed -n '/<decrypt>:/,/ret/p'
  401133:  mov    eax,DWORD PTR [rbp-0x4]        ; i
  401138:  cdqe
  40113a:  movzx  eax,BYTE PTR [rax+0x404020]    ; buf[i]
  401141:  xor    eax,0x33                        ; ^= 0x33
  401144:  mov    edx,DWORD PTR [rbp-0x4]
  401147:  cdqe
  401149:  mov    BYTE PTR [rax+0x404020],dl      ; buf[i] = ...
  40114f:  add    DWORD PTR [rbp-0x4],0x1         ; i++
  401153:  cmp    DWORD PTR [rbp-0x4],0xf
  401157:  jle    401133                           ; цикл
```

Идея ясна человеку, но «для машины» это просто байты. Теперь то же самое, но через лифтер.

## Шаг 1: лифтим блок в VEX IR

Один из самых доступных лифтеров — **VEX** (его использует Valgrind и angr). Возьмём Python-модуль
`pyvex` (ставится через `pip install pyvex`) и подадим ему байты тела цикла (начиная с адреса
`0x401133`):

```python
import pyvex, archinfo
from elftools.elf.elffile import ELFFile
e = ELFFile(open('decrypt','rb')); text = e.get_section_by_name('.text')
code = text.data()[0x401133-text['sh_addr']: 0x401133-text['sh_addr']+0x40]
irsb = pyvex.IRSB(code, 0x401133, archinfo.ArchAMD64())
for st in irsb.statements:
    print(type(st).__name__, "|", str(st).strip())
```

Получаем дерево IR-операций:

```
IMark | ------ IMark(0x401133, 3, 0) ------
WrTmp | t15 = Add64(t16,0xfffffffffffffffc)     ; &i
WrTmp | t18 = LDle:I32(t15)                     ; читаем i
...
WrTmp | t22 = Add64(t19,0x0000000000404020)     ; &buf[i]
WrTmp | t26 = LDle:I8(t22)                      ; читаем buf[i]
WrTmp | t2  = Xor32(t27,0x00000033)             ; buf[i] ^ 0x33
Store | STle(t41) = t43                          ; пишем обратно
```

Сравни с ассемблером: каждая машинная инструкция превратилась в набор **простых операций** с явными
входами и выходами. `LDle:I32` — чтение 32 бит (little-endian), `Xor32` — XOR, `STle` — запись,
`Add64` — сложение, `WrTmp` — присваивание временной переменной `tN`. Никаких «неявных» флагов:
всё, что влияет на вычисление, теперь видно в явном виде.

## Шаг 2: читаем алгоритм прямо из IR

Вот главная выгода. В ассемблере ключ `0x33` спрятан среди `movzx`/`cdqe`/`add`. В IR он вылезает
наружу одной строкой: `Xor32(t27, 0x33)`. Мы восстановили алгоритм — «взять `buf[i]`, сложить по
XOR с `0x33`, записать назад» — не читая ассемблер построчно. Именно так работают деобфускаторы и
автоматические анализаторы: они смотрят на IR, а не на байты.

## Шаг 3: поток управления тоже виден

У IR есть и переходы. Спросим у блока, куда он может передать управление:

```
$ python3 lift_loop.py
jumpkind: Ijk_Boring
constant_jump_targets: ['0x401159', '0x401133']
```

`constant_jump_targets` — это адреса, куда блок может прыгнуть: `0x401133` (назад, в начало цикла)
и `0x401159` (выход). Два варианта — это и есть `jle`: «если меньше или равно — назад, иначе
дальше». Так, не заглядывая в ассемблер, получают карту переходов. А для обфускации с **косвенными**
прыжками (`jmp rax`) этот список покажет, что цель не одна константа — сигнал, что где-то есть
таблица адресов.

## Шаг 4: зачем IR — символическое упрощение

Раз код стал формулами, его можно упрощать через решатель. Классический пример — **MBA**
(Mixed Boolean-Arithmetic): обфускатор переписывает простое выражение в эквивалентную, но запутанную
форму. На IR это доказывается за секунды:

```python
>>> from z3 import *
>>> x, y = BitVecs('x y', 32)
>>> prove((x | y) - (x & y) == (x ^ y))
proved
```

То есть `(x|y)-(x&y)` — это на самом деле `x^y`. Обфускатор надеялся, что ты будешь разбирать
«сложение, побитовое ИЛИ, вычитание», а по сути там один XOR. Так же снимаются сотни тождеств —
это основа инструментов вроде SiMBA и MBA-Solver.

Второе применение IR — **эмуляция**. Раз каждая операция описана явно, IR можно исполнять без
процессора: подставить значения в «регистры» и «память» и прокрутить блок. Так работают
P-Code Emulator в Ghidra и эмулятор в unicorn. Это спасает, когда бинарник под другой архитектурой
(ARM, MIPS) и запустить его на своей машине нечем — лифтер переводит код в IR, а эмулятор выполняет
его уже на хосте.

## Шаг 5: разные IR для разных задач

VEX — не единственный IR. У каждого своя ниша:

- **Ghidra P-Code** — IR декомпилятора Ghidra: операции вида `INT_ADD`, `LOAD`, `STORE`,
  `CBRANCH`. Его удобно разбирать скриптами и эмулировать (P-Code Emulator).
- **LLVM IR** — если нужен весь аппарат оптимизаций компилятора. Инструменты `remill`, `McSema`,
  `RetDec` лифтят бинарник в LLVM IR, после чего к нему применимы пассы `opt`.
- **ESIL** (в rizin/radare2) — упрощённый IR для эмуляции отдельных инструкций.
- **VTIL** — IR, созданный специально для **девиртуализации**: он позволяет «перекомпилировать»
  код, разложенный виртуальной машиной (VMProtect и подобные), обратно в нативный.

Общий принцип один: одна сложная инструкция раскладывается на простые операции, а дальше с ними
работают единые алгоритмы — не важно, x86 это, ARM или MIPS, меняется только лифтер.

Есть и цена: лифтинг не бесплатный. IR-операций обычно в несколько раз больше, чем машинных
инструкций (сравни 8 строк ассемблера и 15 строк VEX выше), а на самолифтящихся или обфусцированных
функциях лифтер может «споткнуться» и выдать `TODO`-операцию. Поэтому для быстрого взгляда иногда
проще прочитать ассемблер, а IR включают, когда нужен масштаб: автоматический обход сотен функций,
символический анализ или деобфускация.

## Что мы теперь знаем

- **Лифтинг** — перевод машинных инструкций в промежуточное представление (IR).
- IR делает код единообразным: явные входы/выходы, простые операции (`Add`, `Xor`, `Load`, `Store`).
- В нашем примере IR сразу показал ключ XOR (`Xor32(t27, 0x33)`) и цели переходов.
- На IR работают символическое упрощение (MBA), эмуляция и девиртуализация.
- Популярные IR: VEX (pyvex/angr), Ghidra P-Code, LLVM IR (remill/McSema), ESIL, VTIL.

## Куда дальше

Мы получили IR — базу для автоматического анализа. В следующих уроках мы используем её для
**динамического taint-анализа** (отслеживание распространения входных данных) и **символьного
исполнения**. А пока главное запомни: лифтинг превращает «байты» в понятные операции, и именно на
этом уровне работают деобфускаторы и решатели.

## Где пригодится

- **CTF Reversing:** быстрый разбор обфускации, восстановление алгоритмов.
- **Деобфускация:** снятие MBA и виртуализации (VTIL, SiMBA).
- **Автоматизация:** свой анализ кода поверх IR вместо ручного чтения ассемблера.
