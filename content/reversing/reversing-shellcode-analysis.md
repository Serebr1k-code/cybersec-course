## Задача

У тебя есть файл `sc.bin` — 37 байт «сырых» данных. Это **shellcode**: машинный код без
заголовка, секций и символов, который в эксплойте исполняется там, куда его положили. Нужно
понять, что он делает. Проблема в том, что у него нет точки входа «из коробки» — это просто
blob байтов.

```bash
$ file sc.bin
sc.bin: data
$ xxd sc.bin
00000000: eb10 5e48 31c9 b10e 8036 5a48 ffc6 e2f8  ..^H1....6ZH....
00000010: eb05 e8eb ffff ff3b 1c28 3e11 2d0a 3c3a  .......;.(>.-.<:
00000020: 132c 2e12 38                             .,..8
```

## Шаг 1: дизассемблируем blob

Обычному дизассемблеру нужен формат; для сырых байт указываем его явно — архитектуру
(`i386:x86-64`) и что это просто данные:

```bash
$ objdump -D -b binary -m i386:x86-64 sc.bin
0000000000000000 <.data>:
   0:	eb 10                	jmp    0x12
   2:	5e                   	pop    %rsi
   3:	48 31 c9             	xor    %rcx,%rcx
   6:	b1 0e                	mov    $0xe,%cl
   8:	80 36 5a             	xorb   $0x5a,(%rsi)
   b:	48 ff c6             	inc    %rsi
   e:	e2 f8                	loop   0x8
  10:	eb 05                	jmp    0x17
  12:	e8 eb ff ff ff       	call   0x2
```

Читаем по-человечески:

- `jmp 0x12` — прыжок вперёд, к `call`.
- `call 0x2` — вызов «назад». Это классический приём получения **собственного адреса**:
  `call` кладёт на стек адрес следующей инструкции (0x17), а `pop %rsi` (по адресу 0x2)
  забирает его в регистр `rsi`. Так код узнаёт, где он лежит, не зная абсолютного адреса —
  это и есть **позиционная независимость**.
- `xor %rcx,%rcx` / `mov $0xe,%cl` — обнуляем счётчик и ставим длину 14 (0xe).
- `xorb $0x5a,(%rsi)` / `inc %rsi` / `loop` — цикл: XOR-им каждый байт по адресу `rsi` ключом
  `0x5a` и сдвигаемся вперёд, пока счётчик не дойдёт до нуля.

Итог: перед нами **декодер**. Он расшифровывает 14 байт, лежащих сразу за кодом, ключом `0x5a`.

## Шаг 2: снимаем слой кодирования

Закодированные байты начинаются на смещении `0x17` (туда прыгает `jmp 0x17`). Снимаем XOR
ключом `0x5a`:

```bash
$ python3 -c "d=open('sc.bin','rb').read()[0x17:]; print(bytes(b^0x5a for b in d))"
b'aFrdKwPf\`IvtHb'
```

Получилась читаемая строка `aFrdKwPf\`IvtHb` — 14 байт. В настоящем shellcode на этом месте
оказался бы **второй этап** (например, код реверс-шелла) или строка-конфиг; у нас — метка.
Ключевой урок: **пока не снят слой кодирования, дальше смотреть бессмысленно.**

## Шаг 3: почему shellcode так устроен

Особенности, которые надо держать в голове при разборе:

- **Позиционная независимость.** Нет абсолютных адресов; свой адрес берут через `call/pop`
  или `lea reg,[rip+...]`. Поэтому в дизассемблере адреса вида `0x17` — это **смещения**,
  а не реальные адреса памяти.
- **Нет заголовка.** Архитектуру (x86/x64, ARM) и точку входа задаёт аналитик.
- **API-резолвинг.** Shellcode не может просто «импортировать» функции — он ищет их вручную
  (см. ниже).
- **Кодирование.** XOR-стаб, alphanumeric (только печатные байты), самораспаковка — чтобы
  пройти через фильтры и ограничения вроде `strcpy`.

## Шаг 4: API-резолвинг (как shellcode ищет функции)

В Windows shellcode не имеет таблицы импортов. Чтобы вызвать `connect` или `CreateProcess`,
он делает **PEB walk**: идёт по структуре процесса `PEB → Ldr → InMemoryOrderModuleList`,
находит `kernel32.dll`, затем `GetProcAddress`, и уже через неё — нужные функции. В дизасме
это выглядит как доступ к `fs:[0x30]` (x86) / `gs:[0x60]` (x64).

Чтобы не тащить имена функциями, их часто сравнивают по **хешу**. Классический `ROR13`:

```python
def ror13(s):
    h = 0
    for c in s.encode():
        h = ((h >> 13) | (h << 19)) & 0xFFFFFFFF
        h = (h + c) & 0xFFFFFFFF
    return h

print(hex(ror13('LoadLibraryA')), hex(ror13('WinExec')))
```

Найдя в дизасме константы-хеши, ты сопоставляешь их с именами и переводишь «непонятные»
`call` в понятные вызовы (резолвинг, сеть, запуск процесса). Это ключ к пониманию назначения.
Приём простой: посчитай `ror13` для списка интересных функций (`LoadLibraryA`,
`GetProcAddress`, `WinExec`, `connect`, `recv`, `send`) и сравни с константами из кода —
совпадение даст имя.

## Шаг 5: эмуляция вместо запуска

**Никогда не запускай shellcode напрямую** — он может установить соединение с C2. Безопасный
путь — **эмуляция** (Unicorn/Qiling): код исполняется в изолированном движке, а ты логируешь
инструкции и видишь расшифровку:

```python
from unicorn import Uc, UC_ARCH_X86, UC_MODE_64
from unicorn.x86_const import UC_X86_REG_RSP
code = open('sc.bin','rb').read()
uc = Uc(UC_ARCH_X86, UC_MODE_64)
uc.mem_map(0x1000, 0x10000)
uc.mem_write(0x1000, code)
uc.reg_write(UC_X86_REG_RSP, 0x11000)
uc.hook_add(UC_HOOK_CODE, lambda u,a,s,d: print(hex(a)))
uc.emu_start(0x1000, 0)
```

Для Windows-API-вызовов удобен **Speakeasy** — он эмулирует `LoadLibrary`/`GetProcAddress` и
логирует вызовы, что идеально для stager'ов. Если shellcode под другую архитектуру (ARM,
MIPS), берите **Qiling** — он эмулирует системные вызовы разных ОС и архитектур, а не только
набор инструкций. Эмуляция даёт то, что статический дизасм не покажет: расшифрованные в
памяти строки и реальную последовательность вызовов.

## Шаг 6: stager'ы и многоэтапность

Shellcode часто **многоэтапный**:

```text
Этап 1 (stager): декодирует/скачивает второй этап.
Этап 2 (payload): реальная нагрузка (shell, beacon, miner).
```

Типовые семейства: **reverse shell** (`connect` на C2, дублирование сокета на stdin/stdout,
`execve`), **bind shell** (`bind`+`listen`+`accept`), **download-and-execute** (fileless),
**Meterpreter/Cobalt Strike stager** (часто с API-хешами). Распознать семейство можно по
структуре «резолвинг → connect/recv → exec».

Чтобы отлаживать shellcode удобнее, его «заворачивают» в exe-загрузчик: stub выделяет
RWX-память, копирует blob и передаёт управление (`shellcode2exe`). Запускать так можно
**только в изолированной VM без сети**.

## Если не сработало

- **Дизасм — «мусор»** — ты начал не с той точки: shellcode может начинаться с данных или
  прыжка. Ищи `jmp`/`call` вперёд.
- **После декодирования всё ещё мусор** — возможно, кодирование многослойное (XOR + alpha);
  эмулируй стаб, чтобы он сам выдал распакованный буфер.
- **Путаница 32/64 бита** — влияет и на дизасм, и на API-резолвинг (`fs` против `gs`).
- **«Странные» адреса** — это rip-relative смещения, а не реальные адреса (позиционная
  независимость).

## Что мы теперь знаем

- Shellcode — позиционно-независимый blob без заголовка; дизассемблировать надо с явной архитектурой.
- Свой адрес код получает через `call/pop`; адреса в листинге — смещения.
- Часто есть слой кодирования (XOR/alpha) — его снимают первым делом.
- API ищутся вручную (PEB walk) и по хешам (`ROR13`) — их надо восстановить.
- Безопасный способ «исполнить» — эмуляция (Unicorn/Speakeasy), не запуск.

## Куда дальше

Мы разобрали позиционно-независимый код и декодер. Но shellcode — лишь один вид «сырой»
нагрузки; часто вредоносная логика живёт в **драйвере ядра** или модуле. В следующем уроке
мы возьмём kernel-модуль и разберём его точки входа. А пока главное запомни: **сначала
определи архитектуру и точку входа, потом сними кодирование, потом разбирай логику.**

## Где пригодится

- **CTF Reversing/Pwn:** анализ эксплойтов и их полезной нагрузки.
- **Malware analysis:** разбор stager'ов и fileless-нагрузки.
- **Exploit triage:** быстрая оценка того, что делает эксплойт.
- **Работа (incident response):** разбор сетевых артефактов и дампов памяти.
