## Вопрос, с которого всё начинается

Ты нашёл в приложении проверку подписи, которая мешает запуску на модифицированном APK. Ты хочешь «выключить» её: поменять байткод так, чтобы проверка всегда проходила. Как это делается и что нужно знать о формате DEX?

## Наш пример

Возьмём `classes.dex` — скомпилированный байткод Dalvik. Прежде чем править, посмотрим, что внутри, доступными средствами:

```
$ strings -n 6 classes.dex | grep -iE 'signature|verify|license'
Lcom/example/app/IntegrityCheck;
verifySignature
isDebugBuild
```

Строки подсказывают: есть класс `IntegrityCheck` с методами `verifySignature` и `isDebugBuild`. Дальше — разбор в smali.

## Шаг 1: что такое smali и зачем он нужен

DEX — это бинарный формат байткода Dalvik. Читать его в hex тяжело. **smali** — человекочитаемое текстовое представление того же байткода: каждая инструкция Dalvik (`invoke-virtual`, `move-result`, `const/4`, `if-eqz`) записывается строкой. Инструмент `baksmali` превращает DEX в набор `.smali`-файлов (по одному на класс), `smali` собирает обратно.

`apktool` идёт дальше: он разбирает весь APK (манифест, ресурсы, DEX) в удобную структуру и собирает обратно одной командой. Обычно используют именно его.

```
$ apktool d app.apk -o app_dir
$ ls app_dir/smali/com/example/app/
IntegrityCheck.smali
```

## Шаг 2: читаем метод в smali

Откроем `IntegrityCheck.smali` и найдём `verifySignature`. Упрощённо метод выглядит так:

```
.method public verifySignature()Z
    .registers 3
    invoke-virtual {p0}, Lcom/example/app/IntegrityCheck;->getActual()Ljava/lang/String;
    move-result-object v0
    const-string v1, "expected_signature"
    invoke-virtual {v0, v1}, Ljava/lang/String;->equals(Ljava/lang/Object;)Z
    move-result v0
    return v0
.end method
```

Читается по шагам: получить фактическую подпись в `v0`, сравнить с ожидаемой строкой, вернуть результат (`Z` — boolean). Если результат `false` — приложение считает APK модифицированным.

## Шаг 3: делаем минимальную правку

Простейший обход — заставить метод всегда возвращать `true`. В smali это замена возврата на константу:

```
.method public verifySignature()Z
    .registers 2
    const/4 v0, 0x1      ; v0 = 1 (true)
    return v0
.end method
```

Теперь метод игнорирует реальную проверку и всегда возвращает «подпись верна». Это классическая правка «верни true».

Важно: `.registers` объявляет число регистров метода. Если удалить код, использующий регистры, и уменьшить `.registers`, метод станет короче. Но если число регистров не совпадает с используемыми — верификатор DEX отвергнет файл.

## Шаг 4: собираем и подписываем

Обратная сборка:

```
$ apktool b app_dir -o app_patched.apk
$ zipalign -p 4 app_patched.apk app_aligned.apk
$ apksigner sign --ks my.keystore app_aligned.apk
```

Ключевой момент: после модификации подпись APK меняется. Android откажется устанавливать APK с неверной подписью, поэтому нужен **новый ключ подписи**. Именно поэтому проверка подписи внутри приложения и мешает: код сравнивает свою подпись с «зашитой» эталонной, а ты подписал другим ключом.

## Шаг 5: ловушки repackaging

Правка smali — не всегда достаточно. Частые проблемы:

- **Multidex**: класс может лежать не в `classes.dex`, а в `classes2.dex`/`classes3.dex`. Нужно править нужный файл.
- **Верификатор**: неверное число регистров или типа-инструкции → `INSTALL_FAILED_DEXOPT`. Правку нужно делать аккуратно.
- **Проверка целостности DEX**: приложение может хешировать свой DEX и сравнивать с эталоном. Тогда правка smali сломает хеш и детект сработает. Обход — найти и отключить саму проверку хеша.
- **Нативные проверки**: часть проверок в `.so`. Правка smali их не обойдёт — придётся патчить и нативную библиотеку.

## Шаг 6: находим артефакт практики

Среди строк DEX есть и наш артефакт. Достанем его:

```
$ strings -n 5 classes.dex | grep nto
nto{sm4l1_p4tch_r3turn_tru3}
```

## Инструмент: objdump — дизассемблер

`objdump` показывает машинный код бинарника в виде ассемблера. Именно по нему считают смещения буферов, находят вызовы и адреса — основа статического разбора.

Ключи, которые пригодятся:
* `objdump -d <файл>` — дизассемблировать секцию `.text` (машинный код функций);
* `objdump -d <файл> | less` — листать вывод, искать нужную функцию по имени;
* `objdump -M intel -d <файл>` — синтаксис Intel (привычнее, чем AT&T);
* в выводе важны пролог функции (`push rbp; mov rbp,rsp`) и `sub rsp,N` — по нему видно размер кадра.

### Рабочий пример (как в лаборатории)

```
$ objdump -d classes.dex
objdump: classes.dex: file format not recognized
```

Подсказка из лаборатории: `objdump [-d] <файл> — не применимо к DEX`.

## Что мы теперь знаем

- smali — текстовое представление байткода Dalvik; DEX — его бинарная форма.
- apktool разбирает и собирает APK; baksmali/smali работают с отдельными DEX.
- Минимальный обход — заменить тело метода на `const/4 v0, 0x1; return v0`.
- После правки APK нужно пересобрать, выровнять (`zipalign`) и подписать новым ключом.
- Ловушки: multidex, верификатор, проверка хеша DEX, нативные проверки.

## Инструменты и их роли

`apktool` — «швейцарский нож»: разбирает APK в структуру (smali + ресурсы) и собирает обратно.
`baksmali`/`smali` — только DEX ↔ smali. `jadx` — декомпилятор в Java (удобен для чтения, но
не для правки). `dex2jar` — DEX в JAR для дальнейшей декомпиляции. `apksigner` — подпись.
`zipalign` — выравнивание (требуется перед подписью для корректной установки).

Типичный конвейер: `apktool d` → правка `.smali` → `apktool b` → `zipalign` → `apksigner sign`.

## Проверка целостности DEX и как её обойти

Если приложение считает SHA-256 своего DEX и сравнивает с эталоном, любая правка smali ломает
хеш. Признаки: вызовы `MessageDigest.getInstance("SHA-256")`, чтение `getPackageCodePath()`.
Обход: найти метод, возвращающий ожидаемый хеш, и подменить его результат на фактический —
или просто заставить метод сравнения всегда возвращать `true`. Это делается тем же патчем
smali.

## Частые ошибки

- Править `classes.dex`, когда код в `classes2.dex` (multidex).
- Забыть `zipalign` перед подписью — установка падает.
- Изменить число регистров метода и сломать верификатор DEX.
- Подписать APK старым ключом — конфликт с уже установленной версией.
- Патчить только Java, оставив нативную проверку активной.

## Чек-лист

1. `apktool d app.apk` — разбор.
2. Найди нужный метод в `.smali`.
3. Патч: `const/4 v0, 0x1; return v0` или инверсия условия.
4. `apktool b` → `zipalign` → `apksigner sign`.
5. Проверь установку и отключи проверку целостности DEX, если нужно.

## Разбор реального примера: патч проверки лицензии

Разберём метод `isLicensed` из `classes.dex`. Откроем его в smali:

```
.method public isLicensed()Z
    .registers 4
    invoke-virtual {p0}, Lcom/example/app/License;->getToken()Ljava/lang/String;
    move-result-object v0
    const-string v1, "valid_token_2024"
    invoke-virtual {v0, v1}, Ljava/lang/String;->equals(Ljava/lang/Object;)Z
    move-result v2
    return v2
.end method
```

Читаем. Метод получает токен (`v0`), сравнивает его с константой (`v1`) и возвращает результат
сравнения (`v2`). Чтобы обойти, заменим тело:

```
.method public isLicensed()Z
    .registers 2
    const/4 v0, 0x1
    return v0
.end method
```

Теперь метод всегда возвращает `true`. Число регистров уменьшено с 4 до 2, потому что мы больше
не используем `v0`–`v2`. Это важно: `.registers` должен быть не меньше максимального индекса
используемого регистра плюс один.

Собираем и подписываем:

```
$ apktool b app_dir -o app_patched.apk
I: Building resources...
I: Building apk file...
$ zipalign -p 4 app_patched.apk app_aligned.apk
$ apksigner sign --ks release.keystore --out app_signed.apk app_aligned.apk
```

Теперь можно устанавливать. Но если приложение проверяет свою подпись или хеш DEX, патч
сработает не сразу — нужно найти и отключить и эти проверки.

## Проверка целостности и её обход

Типичная проверка целостности: приложение читает свой APK, считает SHA-256 и сравнивает с
эталоном. Признаки в smali: `MessageDigest.getInstance`, `getPackageCodePath`,
`getPackageInfo`. Обход: найти метод, который возвращает эталонный хеш, и подменить его на
фактический — или, проще, заставить метод сравнения всегда возвращать `true`. Это тот же
smali-патч: `const/4 v0, 0x1; return v0`.

## Сравнение с Frida-обходом

Smali-патч — статический: меняет файл, требует пересборки и подписи, зато работает без внешнего
агента и не детектируется по порту Frida. Frida-хук — динамический: не трогает файл, но виден
по следам инструментации и требует запущенного сервера. Выбор зависит от задачи: для
постоянной модификации — патч; для исследования — хук.

## Правка условий, а не только возврата

Иногда недостаточно вернуть `true` — нужно сохранить остальную логику. Тогда правят условие.
В smali условные переходы: `if-eqz`, `if-nez`, `if-eq`, `if-ne`, `if-lt` и другие. Например,
метод проверяет `if-eqz v0, :cond_rooted`. Чтобы инвертировать, заменяют на `if-nez v0,
:cond_rooted`. Это точечная правка, сохраняющая структуру метода.

Другой приём — заменить `invoke-virtual ... equals` на возврат константы, если сравнение лишнее.
Важно следить за регистрами: после правки `.registers` должен соответствовать используемым.

## Работа с ресурсами

Строки интерфейса и часть констант лежат в `resources.arsc`. Их правят через `apktool` — он
декодирует ресурсы в XML. Если нужно изменить сообщение об ошибке или убрать упоминание защиты,
правь `res/values/strings.xml` и пересобирай. Это делается вместе с правкой smali.

## Инструменты для верификации

После сборки проверь, что APK корректен: `apksigner verify` подтвердит подпись, `zipalign -c`
— выравнивание, `aapt dump badging` — базовую валидность. Установи на устройство/эмулятор и
проверь, что приложение запускается. Если установка падает с `INSTALL_FAILED_DEXOPT` — проблема
в верификаторе DEX, скорее всего из-за неверного числа регистров.

<!-- b15-deep3 -->

## Что делать, если правка не помогает

Бывает, что приложение всё равно детектит модификацию. Причины: несколько независимых проверок,
проверка целостности DEX, нативная проверка, отложенный детект. Тогда действуй системно: найди
все проверки (grep по строкам и вызовам), отключи их по очереди, проверяя эффект. Не
останавливайся на первой найденной — их обычно больше одной. Веди список: что нашёл, где, чем
обошёл. Это экономит время при повторных сборках.

## Итог

Правка smali — базовый навык мобильного реверса. Ты разбираешь APK, находишь нужный метод,
меняешь байткод, собираешь и подписываешь заново. Главные подводные камни — multidex, подпись и
проверки целостности. Освоив этот конвейер, ты можешь отключать защиты и включать скрытые
функции; а если правки недостаточно, переходишь к динамической инструментации через Frida или
Xposed. Помни: каждая сборка требует нового ключа, а каждая правка может сломать верификатор
DEX — проверяй установку после каждого изменения.
