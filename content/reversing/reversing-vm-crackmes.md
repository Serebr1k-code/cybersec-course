VM-защита — это высшая лига обфускации. Идея проста и могущественна: вместо нативных инструкций
защищённый код компилируется в **собственный байткод** неизвестной архитектуры, а внутрь бинарника
встраивается **интерпретатор (VM)** этого байткода. Реверсер видит огромный `switch`/таблицу хендлеров
и поток «мусорных» байтов. Так работают VMProtect, Code Virtualizer, тигровый обфускатор Tigress и
множество CTF-крэкми. Этот урок — про то, как опознать VM, восстановить её архитектуру и
девиртуализировать код.

## Как устроена VM-защита

Компоненты:

1. **VM entry** — сохраняет контекст, инициализирует виртуальные регистры/стек, загружает байткод.
2. **Dispatcher (цикл VM)** — читает опкод, находит хендлер, передаёт управление.
3. **Хендлеры** — реализации виртуальных инструкций (`vpush`, `vadd`, `vxor`, `vjmp`, ...).
4. **VM exit** — восстанавливает контекст и возвращается в нативный код.
5. **Байткод** — зашифрованная/закодированная программа на виртуальной ISA.

Ключевое наблюдение: **реверсеру не нужно понимать весь VM** — нужно лишь восстановить
последовательность виртуальных операций, относящуюся к защищённой функции.

## Признаки VM-обфускации

- **Большой dispatcher**: цикл с `switch`/цепочкой `cmp`/таблицей переходов, десятки-сотни
  хендлеров, похожих друг на друга.
- **Виртуальный стек/регистры**: массив в `.bss`/`.data`, к которому обращаются хендлеры.
- **Константные «магические» значения**, сравниваемые с опкодами.
- **Аномальная структура** после распаковки (VMProtect/Themida часто сначала упакованы).
- **Огромное количество `jmp`** — поток управления «размазан» (control-flow flattening).

## Стратегии анализа

**1. Опознать dispatcher.** Ищем функцию, к которой сходится много xref (все хендлеры возвращаются
в неё), либо большой `switch`. В IDA/Ghidra — граф функции с десятками узлов.

**2. Понять формат байткода.** Найти, откуда dispatcher читает опкод: указатель на `bytecode`,
инкремент на размер инструкции. Определить ширину опкода (1, 2, 4 байта) и наличие операндов.

**3. Трассировать исполнение.** Самый практичный путь для CTF: записать последовательность
**виртуальных операций** на реальном входе.

- **gdb-скрипт**: breakpoint на входе в dispatcher, логировать `opcode` и обновление `vip`.
- **Pin/DynamoRIO**: инструментировать на уровне инструкций, считать частоты и переходы.
- **Unicorn**: эмулировать VM целиком, перехватывая переходы между хендлерами.
- **Intel PT / rr**: записать поток и отфильтровать.

**4. Сопоставить хендлер → операция.** По эффекту хендлера на виртуальный стек/регистры определяем
семантику: «кладёт константу», «складывает два верхних», «XOR», «сравнивает», «ветвится».

**5. Девиртуализировать.** Восстановить виртуальный CFG и перевести его в понятный псевдо-C.

## Разобранный пример: CTF VM-crackme

Дано: бинарник просит флаг, внутри — VM. Задача — найти проверку.

**Шаг 1. Находим dispatcher.** В IDA `Ctrl+P` сортируем функции по числу xref. Находим `sub_401500`
с ~60 входящими ссылками — это VM-цикл.

**Шаг 2. Смотрим структуру.**
```c
void vm_run() {
    while (1) {
        op = code[vip++];           // чтение опкода
        switch (op) {
            case 0x01: /* vpush imm */  ...
            case 0x02: /* vadd */       ...
            case 0x03: /* vxor */       ...
            case 0x10: /* vjmp */       ...
            ...
        }
    }
}
```
Уже по `case`-константам видно: 0x01 — push, 0x02 — add, 0x03 — xor. Осталось разобрать поток.

**Шаг 3. Трассируем.** Ставим breakpoint на начало цикла и логируем опкоды:
```text
(gdb) b *0x401505
(gdb) commands
> printf "%02x ", *(unsigned char*)$vip
> continue
> end
(gdb) run <<< "test_flag"
01 41 01 42 02 03 ...
```
Получаем поток виртуальных инструкций для ввода `test_flag`.

**Шаг 4. Дизассемблируем байткод вручную.** Сопоставляя опкоды и операнды, восстанавливаем:
```text
push 0x41        ; 'A'
push 0x42
add              ; 0x83
xor [v1], ...    ; проверка
```
Итеративно приходим к формуле проверки флага.

**Шаг 5. Решаем.** Реализуем восстановленную формулу на Python (обратные операции), находим флаг.

## Инструменты и техники девиртуализации

| Инструмент | Применение |
|---|---|
| gdb + Python | логирование опкодов, трассировка |
| Unicorn | эмуляция VM, перехват хендлеров |
| Intel Pin / DynamoRIO | инструментирование на уровне инструкций |
| Triton | символьное исполнение байткода |
| angr | символьное решение пути через VM |
| `vmattack`/`VMAttack` (IDA) | полуавтоматическая девиртуализация |
| Tigress-анализ | работа с control-flow flattening |
| `Miasm` | символьное/эмуляционное фреймворк для VM |

**Трассировка через Unicorn** (пример идеи):
```python
from unicorn import Uc, UC_ARCH_X86, UC_MODE_64
from unicorn.x86_const import UC_X86_REG_RIP
mu = Uc(UC_ARCH_X86, UC_MODE_64)
mu.mem_map(0x400000, 0x100000)
mu.mem_write(0x400000, open("vm","rb").read())
trace = []
def on_code(mu, addr, size, user):
    trace.append(addr)
mu.hook_add(UC_HOOK_CODE, on_code)
mu.emu_start(0x401500, 0x402000)
# последовательность адресов → последовательность хендлеров → операции
```

**Символьное исполнение.** Triton/angr позволяют смоделировать VM и найти вход, приводящий к
«успеху». Для VM это эффективно: инструментируем dispatcher, а хендлеры дают семантику.

## Control-flow flattening (Tigress)

Родственная техника: реальный поток управления «сплющивается» в один цикл с переменной-состоянием:
```c
while (1) {
    switch (state) {
        case 0: a = b + c; state = 5; break;
        case 5: if (a > 10) state = 9; else state = 2; break;
        ...
    }
}
```
Девиртуализация — восстановить граф переходов `state` и «разложить» его обратно в понятный CFG.
Инструменты: `deflat` (плагин IDA), скрипты на основе анализа `state`-переменной.

## Крайние случаи и подводные камни

- **VM внутри VM / несколько слоёв.** VMProtect может виртуализировать только часть кода и
  комбинировать с упаковкой. Снимайте слои по очереди.
- **Динамические хендлеры.** Адрес хендлера вычисляется из опкода (`table[op]`), а не `switch` —
  трассировка важнее статики.
- **Самомодифицирующийся VM.** Хендлеры меняются на лету — статический дизасм бесполезен.
- **Огромный объём.** Полная девиртуализация VMProtect — недели работы. Для CTF чаще достаточно
  **трассировать конкретный путь**, а не восстанавливать всю VM.
- **Анти-трассировка.** VM может детектить breakpoints (проверка `0xCC`, тайминги) — используйте
  аппаратные точки/эмуляцию.
- **Символьное исполнение упирается в размер.** Путь через VM может быть экспоненциальным — комбинируйте
  с трассировкой и ручным анализом.
- **Ошибки в собственных реализациях VM** (CTF-задачи) — часто есть баг, упрощающий решение;
  ищите его.

## Что дальше / решение

1. Опознать VM: dispatcher + таблица хендлеров + виртуальный стек.
2. Определить формат байткода (ширина опкода, операнды).
3. Трассировать на конкретном входе (gdb/Unicorn/Pin), получить поток операций.
4. Сопоставить хендлеры семантике, восстановить виртуальный CFG.
5. Решить задачу: реализовать проверку на Python и найти инверсный вход.
6. Для больших VM — автоматизировать (скрипты девиртуализации, символьное исполнение).

Принцип: **не пытайтесь понять всю VM — поймите только тот путь, который нужен**. Трассировка
конкретного ввода в 90% случаев быстрее полной девиртуализации.

## Справочная таблица: VM-защита → подход

| Защита | Признак | Подход |
|---|---|---|
| Кастомная VM | dispatcher + switch | трассировка + сопоставление |
| VMProtect | `.vmp0/1`, упаковка | слои + трассировка пути |
| Code Virtualizer | вирт. регистры | Unicorn + семантика |
| Tigress CFF | state-переменная | `deflat`/CFG recovery |
| Tigress opaque | всегда-истинные условия | упрощение/символика |
| Самомодиф. VM | меняется код | динамика/Pin |

## Автоматизация девиртуализации

Ручная трассировка хороша для небольших VM. Для больших — автоматизация. Идея: **перехватывать
каждый переход хендлера и записывать (opcode, vsp, vregs)**.

**Скрипт на Unicorn с семантикой хендлеров:**
```python
from unicorn import Uc, UC_ARCH_X86, UC_MODE_64
from unicorn.x86_const import UC_X86_REG_RIP, UC_X86_REG_RSP
HANDLERS = {0x401600: "push", 0x401650: "add", 0x4016a0: "xor",
            0x401700: "cmp", 0x401760: "jmp"}
trace = []
def on_code(mu, addr, size, user):
    if addr in HANDLERS:
        trace.append(HANDLERS[addr])
mu = Uc(UC_ARCH_X86, UC_MODE_64)
mu.hook_add(UC_HOOK_CODE, on_code)
# ... mem_map + mem_write + emu_start на входе VM ...
print(" ".join(trace))
```
На выходе — читаемая последовательность виртуальных операций, которую можно сопоставить с
проверкой и инвертировать.

**Символическое исполнение (Triton).** Инструментируем dispatcher, а для хендлеров задаём семантику
на уровне символических выражений. Затем решаем ограничения (например, «найти вход, при котором
проверка истинна»). Triton/angr умеют это для VM средней сложности.

**Miasm.** Фреймворк с IR и символьным исполнением; часто используется для девиртуализации: он
позволяет выразить VM как систему уравнений и упростить её.

## Семантика хендлеров: как опознать операцию

Быстрый способ понять, что делает хендлер — посмотреть, как он меняет виртуальный стек/регистры:

| Эффект хендлера | Вероятная операция |
|---|---|
| `vsp -= 1`, запись константы | push imm |
| `vsp -= 1`, чтение из vreg | push reg |
| два pop, один push, `+` | vadd |
| два pop, один push, `^` | vxor |
| pop, сравнение, условный `jmp` | vcmp/vbranch |
| изменение `vip` без стека | vjmp/vjcc |
| чтение байта из `code[vip]`, `vip++` | fetch операнда |

Составив такую таблицу для всех хендлеров, вы получаете **дизассемблер виртуальной ISA**. Дальше
восстановление программы — механическая работа.

## Практический маршрут для CTF

1. **Найти VM-цикл** (функция с максимумом xref / большой switch).
2. **Снять таблицу хендлеров**: адреса `case`-веток или `table[op]`.
3. **Определить формат байткода**: где лежит, как инкрементируется `vip`, ширина опкода.
4. **Трассировать** на тестовом входе (gdb/Unicorn).
5. **Сопоставить** хендлеры семантике по эффектам.
6. **Восстановить** виртуальный CFG и перевести в псевдо-C.
7. **Инвертировать** проверку → решить задачу.

Если VM маленькая (10–30 хендлеров), весь путь занимает часы. Если большая (VMProtect, сотни
хендлеров) — фокусируйтесь на конкретном пути и не пытайтесь восстановить всё.
