## Вопрос, с которого всё начинается

Ты открываешь crackme, а в нём нет привычной проверки пароля. Вместо этого — большой цикл, который
читает какие-то числа, сравнивает их с таблицей адресов и прыгает по этой таблице. Похоже, внутри
бинарника спрятана **собственная виртуальная машина**: логика программы переведена в «байткод», а
исполняет его интерпретатор, вшитый в тот же файл. Как разобрать такую задачу?

Опираемся на уроки про обфускацию и деобфускацию: VM — это следующий уровень, где обфусцирована не
структура переходов, а сама система команд.

## Что такое VM-based crackme

Идея простая. Автор пишет проверку пароля, но не компилирует её в машинный код, а переводит в
**байткод** — последовательность «опкодов» для вымышленного процессора. В бинарник добавляется
**интерпретатор**: цикл, который читает очередной опкод, находит по нему обработчик (handler) и
исполняет. Так работают и коммерческие протекторы (VMProtect, Themida): они «виртуализируют»
фрагменты кода, чтобы человек не читал настоящие инструкции.

Для реверсера это означает: нужно сначала понять **систему команд** вымышленной VM, а потом
перевести байткод обратно в понятную логику. Это называется **девиртуализация**.

## Наш пример

Возьмём мини-VM на Python, которая проверяет пароль. Опишем набор опкодов и программу для неё:

```python
# 1 PUSH imm | 2 XOR | 3 CMPEQ imm | 9 CMPEQ(top2) | 4 JZ addr | 5 HALT
# 6 LOAD (input[ptr]) | 7 INC ptr | 8 JMP addr | 10 PUSHP (ptr) | 11 JNZ addr
CODE = [
 6,                 # 00 LOAD
 1,0x11, 2,         # 01 PUSH 0x11 ; XOR
 3,0x22,            # 04 CMPEQ 0x22
 4,0x13,            # 06 JZ 0x13  (fail)
 7,                 # 08 INC
 10,                # 09 PUSHP
 1,0x05, 9,         # 0a PUSH 5 ; CMPEQ?
 11,0x16,           # 0d JNZ 0x16 (ok)
 8,0x00,            # 0f JMP 0x00
 ...
]
```

Программа берёт символ ввода, XOR'ит его с `0x11`, сравнивает с `0x22`, и если все пять символов
подошли — возвращает 1. Запустим её и найдём пароль перебором:

```
=== brute force (a-z0-9 len5) ===
password = 33333
```

Пароль — `33333`. Теперь разберёмся, **как** это видно без исходника.

## Шаг 1: найти интерпретатор и диспетчер

В настоящем бинарнике интерпретатор выглядит как «цикл + косвенный переход». Сначала он читает
опкод (обычно байт или слово) по указателю инструкций, затем использует его как индекс в таблице
адресов обработчиков. Ключевой признак — **косвенный вызов или прыжок** через массив:

```
mov  eax, [vm_ip]          ; текущий опкод
mov  rax, [handler_table + rax*8]
call rax                   ; или jmp rax
```

Если видишь такой паттерн в большом цикле — почти наверняка это диспетчер VM. Найди таблицу
(`handler_table`) и получишь список обработчиков: их число = число опкодов.

## Шаг 2: составить дизассемблер

Разобрав по обработчику на каждый опкод, мы знаем их семантику. Дальше пишем дизассемблер байткода
— программу, которая читает `CODE` и печатает человекочитаемый листинг. Вот результат для нашего
примера:

```
0000: LOAD
0001: PUSH   0x11
0003: XOR
0004: CMPEQ  0x22
0006: JZ     0x13
0008: INC
0009: PUSHP
000a: PUSH   0x05
000c: CMPEQ?
000d: JNZ    0x16
000f: JMP    0x00
0011: HALT
0012: HALT
0013: PUSH   0x00
0015: HALT
0016: PUSH   0x01
0018: HALT
```

Теперь логика читается напрямую: `LOAD` берёт символ, `XOR 0x11` его преобразует, `CMPEQ 0x22`
сравнивает, `JZ fail` уходит на провал при несовпадении. В конце — проверка длины через `PUSHP` и
`CMPEQ? 5`.

## Шаг 3: восстановить логику (лифтинг)

Дизассемблированный байткод — уже почти C. Сопоставляя операции со смыслом, получаем:

```c
for (i = 0; i < 5; i++) {
    if ((input[i] ^ 0x11) != 0x22) return 0;   /* input[i] == 0x33 == '3' */
}
return 1;
```

Отсюда `input[i] = 0x22 ^ 0x11 = 0x33 = '3'`, то есть пароль `33333` — ровно то, что нашёл перебор.
Девиртуализация завершена: мы **сняли** уровень VM и получили обычный код.

## Шаг 4: автоматизация

Для реальных задач байткод длинный, и вручную его не переписать. Тогда:

- **Трассировка**: запусти VM с хуком на диспетчер и логируй, какие опкоды реально исполняются и с
  какими аргументами. Получишь трассу вроде `LOAD; PUSH 0x11; XOR; CMPEQ 0x22; JZ ...`.
- **Символьное исполнение** (angr, Triton): инструмент сам проходит все пути VM и строит уравнение
  на вход — пароль находится решателем, без ручного разбора.
- **VTIL / готовые девиртуализаторы**: для VMProtect существуют фреймворки, поднимающие байткод в
  промежуточное представление и «выпрямляющие» его.

Общий принцип один: **понять систему команд → трассировать/символически пройти → восстановить
логику**.

## Сколько это занимает на практике

Учебную VM из примера разбирают за час. Реальная VMProtect-функция — это десятки обработчиков,
замусоренных вставками, и сотни строк байткода; ручная работа тут измеряется днями. Поэтому правило
такое: **сначала трассировка, потом автоматизация**. Трасса сразу показывает, какие 10% байткода
реально исполняются на нашем входе, — остальные можно игнорировать. Если и трассы мало, подключают
символьное исполнение: оно само проходит нужный путь и выдаёт уравнение на пароль.

## Если не сработало

- **Обработчики замусорены** (внутри каждого — свои ложные предикаты) → сначала упрости каждый
  handler по отдельности, потом строй таблицу.
- **Опкоды зашифрованы** (меняются между запусками) → трассировка надёжнее статики: диспетчер всё
  равно расшифрует их перед исполнением.
- **VM вложенная** (handler сам виртуализован) → это уже уровень VMProtect; без символьного
  исполнения и большого терпения не обойтись.

## Что мы теперь знаем

- **VM-based crackme** прячет логику в байткоде, который исполняет вшитый интерпретатор.
- Интерпретатор узнаётся по **диспетчеру**: чтение опкода и косвенный переход через таблицу
  обработчиков.
- Порядок работы: найти диспетчер → извлечь таблицу handler'ов → написать **дизассемблер** →
  **лифтнуть** байткод в C.
- Для больших VM используют **трассировку** и **символьное исполнение**.
- Так же устроены коммерческие протекторы — VMProtect и Themida.

## Куда дальше

Мы разобрали учебную VM. Дальше посмотрим на **коммерческие протекторы** — VMProtect, Themida,
Enigma — и научимся определять их по секциям, строкам и энтропии. А пока главное запомни: **VM
прячет логику в байткоде, и её снимают, восстановив систему команд и лифтнув байткод в C**.

## Где пригодится

- **CTF Reversing (expert):** VM-задачи — типичный «босс» категории.
- **Анализ протекторов:** VMProtect/Themida виртуализируют код тем же способом.
- **Malware analysis:** встречаются VM-обфусцированные семейства.
- **Автоматизация:** трассировка и SMT превращают ручной разбор в скрипт.
- **Собес:** «как девиртуализовать VM-based crackme?» — вопрос уровня expert.
