## Вопрос, с которого всё начинается

Тебе дали бинарник `rustcheck`, проверяющий ключ. Он **stripped**, и в дизассемблере — стена
непонятного кода. Но если приглядеться, в нём есть характерные следы: строки вида
`panicked at`, а в нестрипленной версии — имена с хеш-суффиксами. По этим следам можно
опознать язык и сильно упростить реверс.

Rust сложен для реверса по нескольким причинам: **мономорфизация** (generic-функции дублируются
под каждый конкретный тип), **манглинг** имён с хеш-суффиксами, развёрнутая обработка
`panic`/`Result`, агрессивный inline и большой объём кода рантайма (`core`, `alloc`, `std`).
Понимание этих особенностей превращает «нечитаемую кашу» в структурированную картину.

Опираемся на прошлый урок про Go: там мы восстанавливали символы через pclntab. В Rust такого
прямого хранилища имён нет, но есть свои опознавательные знаки.

## Наш пример

Смотрим на файл:

```
$ file rustcheck
rustcheck: ELF 64-bit LSB pie executable, x86-64, dynamically linked, ..., stripped
```

Запускаем:

```
$ ./rustcheck wrong
Access denied
$ ./rustcheck 'rUst4c3!'
Access granted
```

Мы ищем проверку ключа. Начнём со строк — у Rust очень узнаваемые сообщения рантайма:

```
$ strings -a rustcheck | grep -iE 'panicked|Access|rUst4c3|usage'
Access denied
Access granted
usage: rustcheck <key>
) panicked at
thread panicked while processing panic. aborting.
fatal runtime error: drop of the panic payload panicked, aborting
rUst4c3!1
```

Строки `panicked at` — это **panic**: механизм аварийного завершения Rust. Он встроен в каждый
бинарник, и по нему язык опознаётся мгновенно. Заодно мы видим кандидата в ключи — `rUst4c3!`.

## Шаг 1: манглинг и демаглинг

Чтобы имена функций не конфликтовали, Rust **манглирует** их — кодирует в длинную строку с
хеш-суффиксом. Соберём нестрипленную версию и посмотрим:

```
$ nm rustcheck_dbg0 | grep _ZN9rustcheck
00000000000161d0 t _ZN9rustcheck4main17hf001655a1c6cdc41E
0000000000016370 t _ZN9rustcheck5check17hfd99a4325aa419cfE
```

Читать это тяжело, но `nm` умеет **демаглить** — возвращать человеческие имена:

```
$ nm --demangle rustcheck_dbg0 | grep 'rustcheck::'
00000000000161d0 t rustcheck::main
0000000000016370 t rustcheck::check
```

Теперь видно обе функции: `rustcheck::main` и `rustcheck::check`. Символ `_ZN...17h<hash>E` —
это legacy-схема манглинга: `17h...` — хеш, добавленный, чтобы одноимённые generic-инстансы не
сливались. Для ручного демаглинга есть утилита `rustfilt` (или `nm --demangle` в свежих binutils).

## Шаг 2: мономорфизация и inline

Собери ту же программу с оптимизацией — и картина изменится:

```
$ nm rustcheck_dbg | grep _ZN9rustcheck
0000000000014b20 t _ZN9rustcheck4main17hf001655a1c6cdc41E
```

Функция `check` **исчезла**. Причина — **inline**: оптимизатор счёл её слишком маленькой и
вклеил её тело прямо в `main`. Это следствие **мономорфизации**: generic-функции в Rust
компилируются отдельно под каждый конкретный тип, поэтому после оптимизации их легко
продублировать или вклеить. Практический вывод: **не удивляйся, что функций «меньше», чем в
исходнике** — логика растворена в вызывающих.

## Шаг 3: идиомы std/core, которые надо узнавать

В Rust-коде много служебного кода. Научись отличать его от логики:

- **`panic`-путь.** Перед каждым `unwrap()`, делением, доступом к элементу компилятор ставит
  проверку и вызов паники. Строки `panicked at <file>:<line>` дают **имена исходных файлов и
  номера строк** — это подарок для реверса: можно восстановить структуру исходника.
- **`Result`/`Option`.** Обработка ошибок разворачивается в ветвления с проверкой дискриминанта
  enum — выглядит как сравнение с 0/1 и переходы.
- **Итераторы и `collect`.** Циклы часто спрятаны за цепочками методов; в ассемблере это
  рекурсивные вызовы `next`.
- **`Drop` и раскрутка стека (unwind).** В конце функций — вызовы `core::ptr::drop_in_place`
  и таблицы раскрутки; это шум, а не логика.
- **Проверки границ.** Rust не даёт выйти за границы слайса — перед доступом стоит сравнение
  индекса с длиной.

Отличить Rust от C++ и Go «на глаз» помогают три признака: panic-строки, хеш-суффиксы в
манглинге и обилие вызовов `core::`/`std::` с узнаваемыми именами после демаглинга.

## Шаг 4: рабочий маршрут

1. `file` + `strings` — найти `panicked at` и другие маркеры Rust.
2. Если есть символы — `nm --demangle` (или `rustfilt`), восстановить имена.
3. Если stripped — искать panic-строки с путями/номерами строк: они ведут к исходной структуре.
4. В Ghidra/IDA применять сигнатуры std (Rust-типы) — узнавать `drop_in_place`, `unwrap`.
5. Помнить про inline: логика может быть вклеена в вызывающую функцию.

## Справочник команд

| Задача | Команда |
|---|---|
| Опознать язык по panic | `strings -a bin \| grep 'panicked at'` |
| Показать манглированные имена | `nm bin \| grep _ZN` |
| Демаглить имена | `nm --demangle bin` / `rustfilt -i` |
| Найти секции/типы | `readelf -S bin`, `objdump -d` |
| Проверить, что функция инлайнилась | сравнить число `_ZN...` при `-O` и `-O0` |
| Дамп строк исходника из panic | `strings -a bin \| grep -E '\.rs:[0-9]+'` |

Полезный приём: собери **свой** аналог подозрительной функции на Rust с `-O0` и `-O`, и
сравни — так ты поймёшь, как оптимизатор Rust «прячет» логику, и быстрее узнаешь её в чужом
бинарнике.

## Шаг 5: ищем логику, когда символов нет

В stripped-версии `nm --demangle` ничего не даст — символов просто нет. Но panic-строки содержат
**пути и номера строк исходника**, и это превращается в карту кода:

```
$ strings -a rustcheck | grep -E '\.rs:[0-9]+'
src/main.rs:7:21
src/main.rs:14:9
```

Отсюда видно: логика — в `src/main.rs`, строки 7 и 14. Дальше идём от `main`: находим точку входа
(`readelf -h rustcheck | grep Entry`), в `main` ищем вызовы сравнения строк. В Rust сравнение строк —
это вызов `<str as PartialEq>::eq` или `core::str::traits::eq`, а не встроенный `strcmp`:

```
$ objdump -d -M intel rustcheck | grep -nE 'call.*(eq|memcmp|bcmp)'
```

Рядом с таким вызовом почти всегда стоит и сама строка-пароль. Если строки зашифрованы — смотри
функцию, которая вызывается до сравнения и пишет в стековый буфер: это дешифратор.

## Как выглядит мономорфизация в символах

Соберём программу, использующую generic-функцию с двумя типами:

```rust
fn id<T: Copy>(x: T) -> T { x }
fn main() { let _ = id(1u32); let _ = id(1.0f64); }
```

В символах появятся **две** отдельные функции с одним именем, но разными хеш-суффиксами:

```
$ nm --demangle generic | grep 'generic::id'
0000000000001130 t generic::id::<u32>
0000000000001150 t generic::id::<f64>
```

Вот что означает мономорфизация на практике: одна generic-функция в исходнике → несколько конкретных
функций в бинарнике. Отсюда два следствия: (1) «одинаковый» код может встречаться много раз — не
удивляйся; (2) разобрав одну копию, ты понимаешь их все — они отличаются только типом.

## Если не сработало

- **`nm` не показывает ни одного `_ZN`** — бинарник полностью stripped. Работай от panic-строк и
  точки входа, как в Шаге 5.
- **Сравнение не находится** — в Rust строки сравниваются функцией, а не инструкцией; ищи вызовы
  `eq`, `memcmp`, `bcmp` и смотри, какие адреса строк в них передаются.
- **Логика «пропала» при `-O`** — ищи вклеенный код прямо в `main`; в отладке (`-O0`) она была
  отдельной функцией, а в релизе растворена.
- **Слишком много `drop_in_place`** — это деструкторы, шум. Игнорируй их и концентрируйся на
  сравнениях и сетевых/файловых вызовах.

## Что мы теперь знаем

- Rust-бинарники опознаются по panic-строкам (`panicked at`) и манглингу имён с хеш-суффиксами.
- `nm --demangle` / `rustfilt` возвращают читаемые имена (`rustcheck::check`).
- **Мономорфизация** плодит копии generic-функций, а **inline** их растворяет в вызывающих.
- Panic-строки с именами файлов и номерами строк помогают восстановить структуру исходника.
- Логика отделяется от рантайма по идиомам: `Drop`, раскрутка стека, проверки границ,
  разворачивание `Result`.
- Даже без символов panic-строки с путями и номерами строк дают карту исходного файла.
- В Rust сравнение строк — это вызов `eq`/`memcmp`, а не встроенная инструкция: ищи вызов, а не `cmp`.
- `rustfilt` умеет демаглить имена даже из вывода `nm`/`objdump`, поданного в пайп, — это удобно
  при массовой обработке символов.

## На что смотреть дальше

- Если символы есть — сначала демаглинг, это дешевле всего.
- Не путай код рантайма (`core`, `alloc`) с логикой программы.
- Помни, что `-O` прячет мелкие функции через inline; ищи их логику в вызывающих.
- Panic-строки содержат пути вида `src/main.rs:12` — используй их как карту исходника.
- Для малвари смотри сетевые вызовы (`std::net`, `reqwest`) и `ring`/`openssl` — там C2 и крипта.
