## Вопрос, с которого всё начинается

Ты открываешь бинарник в дизассемблере — а там мусор. Ни одной осмысленной
функции, ни строк, ни нормального кода. Программа явно что-то делает, но
статически это «каша». Значит, она **упакована**: настоящий код зашифрован и
появляется только в памяти во время работы. Как добраться до оригинала? Это и
есть **распаковка** (unpacking).

## Наш пример

Возьмём программу `stub`. Снаружи она выглядит безобидно, но внутри прячет
маленький «зашифрованный» кусок кода, который расшифровывает и выполняет:

```
$ cat stub.c
unsigned char blob[] = {0x12,0x80,0xAA,0xAA,0xAA,0x69};   /* xor 0xAA -> b8 2a 00 00 00 c3 */
int main(void){
    unsigned long pg = (unsigned long)blob & ~0xfffUL;
    sc(10, pg, 0x1000, 7);                       /* mprotect(pg,4096,RWX) */
    for (unsigned i=0;i<sizeof(blob);i++) blob[i]^=0xAA;   /* расшифровка */
    int (*f)(void) = (int(*)(void))blob;
    printf("decoded result = %d\n", f());        /* вызов расшифрованного кода */
    return 0;
}
$ ./stub
decoded result = 42
```

Это уменьшенная модель настоящего упаковщика: данные на диске зашифрованы,
перед вызовом расшифровываются, страница памяти делается исполняемой
(`mprotect ... RWX` — права read/write/execute), и код выполняется.

## Шаг 1: на диске — шифр, в памяти — код

Посмотрим на `blob` до и после расшифровки прямо в отладчике. Достаточно
поставить точку после цикла XOR:

```
$ gdb -q ./stub
(gdb) break main
(gdb) run
(gdb) x/6xb 0x404018
0x404018 <blob>:	0x12	0x80	0xaa	0xaa	0xaa	0x69
(gdb) break *0x4011b3
(gdb) continue
(gdb) x/6xb 0x404018
0x404018 <blob>:	0xb8	0x2a	0x00	0x00	0x00	0xc3
(gdb) x/6i 0x404018
   0x404018 <blob>:	mov    $0x2a,%eax
   0x40401d <blob+5>:	ret
```

Вот он, ключевой момент распаковки. До цикла байты `12 80 aa aa aa 69` — мусор.
После — `b8 2a 00 00 00 c3`, а это уже валидный код: `mov eax, 0x2a` (то есть
42) и `ret`. Отсюда и «decoded result = 42». Значит, распаковка = **дождаться
момента, когда код расшифрован, и снять его из памяти**.

## Шаг 2: точка входа в оригинальный код (OEP)

У настоящего упаковщика схема та же, но масштабнее. Программа стартует со
**стаба** (stub) — маленького распаковщика. Стаб:

1. выделяет память;
2. расшифровывает в неё оригинальный код;
3. восстанавливает импорты;
4. передаёт управление на **OEP** — Original Entry Point, настоящую точку входа
   оригинальной программы.

Задача аналитика — найти OEP. Классические приёмы:

- **Дойти до OEP отладчиком.** Идти по шагам от стаба, пока не начнётся
  «нормальный» код (типичный пролог `push rbp; mov rbp, rsp`).
- **Точка на запись в секцию кода.** Ставим аппаратный watchpoint на `.text`
  (или на область, куда расшифровывается код) — сработает в момент распаковки.
- **Принцип «popad + jmp».** Многие стабы заканчиваются длинной
  последовательностью `pop` регистров и прыжком на OEP — это удобный маркер.

## Шаг 3: дамп образа из памяти

Дошли до OEP — код в памяти уже расшифрован. Осталось снять его из процесса
(«сделать дамп», memory dump). В отладчике это делают так:

```
(gdb) dump binary memory unpacked.bin 0x400000 0x406000
```

Для PE-файлов то же самое делает плагин **Scylla** (в x64dbg) или утилита
**PE-sieve**: она находит в памяти образ, снимает его и сохраняет как файл.

## Шаг 4: восстановление импортов (IAT)

После дампа получается новая проблема: таблица импортов (**IAT** — Import
Address Table) в дампе «битая». В оригинальном файле там лежали имена функций
(`GetProcAddress` и т.п.), а в памяти — уже подставленные адреса. Дизассемблер
по таким адресам имён не покажет.

Восстановление IAT делает **Scylla**: она находит вызовы, определяет, в какую
DLL и какую функцию ведёт адрес, и перестраивает таблицу в дампе. После этого
файл снова открывается в дизассемблере с осмысленными именами.

## Шаг 5: UPX — самый известный упаковщик

**UPX** (Ultimate Packer for eXecutables) — бесплатный упаковщик, который
встречается повсюду. Его легко опознать по секциям `UPX0`/`UPX1` и маркеру
`UPX!` в файле. В наших артефактах это видно:

```
$ xxd upx1.bin | head -2
00000000: 5550 5821 78da ...     UPX!x...
```

`5550 5821` — это и есть ASCII `UPX!`, а следом `78da` — заголовок
zlib-сжатия. UPX не шифрует, а **сжимает**; распаковать его обычно можно прямо
утилитой `upx -d packed.exe` (если версия UPX совпадает или модификация не
запрещена). Кастомные упаковщики так не снять — нужен ручной разбор.

## Шаг 6: если упаковщик кастомный

Порядок действий для самодельного упаковщика:

1. Найти **алгоритм расшифровки** в стабе (XOR, RC4, AES — что угодно).
2. Понять, куда пишется расшифрованный код (адрес области).
3. Поставить watchpoint на эту область или дойти до OEP.
4. Снять дамп и восстановить IAT.
5. При необходимости — **исправить заголовок**: в дампе `AddressOfEntryPoint`
   всё ещё указывает на стаб, его надо переставить на OEP.

Иногда проще «эмулировать» стаб (в Unicorn/Qiling) и получить расшифрованный
код без реального запуска — об этом в уроках по эмуляции.

## Шаг 7: анти-дамп и как с ним бороться

Настоящие упаковщики мешают снять дамп. Частые приёмы:

- **Стирание заголовков.** Стаб обнуляет PE/ELF-заголовок в памяти, чтобы дамп
  нельзя было открыть как файл. Обход — восстановить заголовок вручную
  (утилита Scylla делает это частично).
- **Несколько слоёв упаковки.** Внутренний код распаковывается позже, по частям.
  Обход — ставить несколько точек и снимать дамп после каждого слоя.
- **Проверки на отладчик и точки.** Мы разбирали это в уроках про анти-отладку:
  стаб может детектировать `0xCC` и не расшифровывать код вовсе.
- **Разреженная расшифровка.** Код расшифровывается постранично прямо перед
  вызовом, и «полного» образа в памяти никогда нет. Обход — снимать страницы по
  мере их появления.

Именно поэтому автоматические распаковщики не универсальны: чем хитрее стаб,
тем больше ручной работы.

## Частые вопросы

**Дамп снял, но дизассемблер показывает мусор.** Скорее всего, снят неверный
диапазон или код расшифровывается позже. Проверь, что попал на OEP, и что
страницы помечены исполняемыми.

**Не могу найти OEP.** Поставь watchpoint на начало секции кода — сработает в
момент записи расшифрованного кода. Или иди по шагам от стаба до типичного
пролога функции.

**`upx -d` не работает.** Версия UPX у файла нестандартная (модифицированный
магический байт или другая версия). Тогда UPX снимают вручную, как кастомный
упаковщик.

## Что мы теперь знаем

- Упакованный бинарник на диске содержит шифр/сжатие; настоящий код появляется
  в памяти.
- Наша `stub` до цикла хранит мусор `12 80 aa...`, после — валидный
  `mov eax, 0x2a; ret` (это и есть распаковка в миниатюре).
- Упаковщик стартует со **стаба**, который доходит до **OEP** — оригинальной
  точки входа.
- После дампа нужно **восстановить IAT** (Scylla, PE-sieve).
- **UPX** опознаётся по `UPX!`/секциям `UPX0/UPX1` и часто снимается `upx -d`;
  кастомные упаковщики разбирают вручную.

## Куда дальше

В следующем уроке мы разберём **коммерческие протекторы VMProtect и
Themida** — они не просто упаковывают код, а превращают его в байткод
виртуальной машины. А пока главное запомни: **распаковка — это найти момент,
когда код расшифрован в памяти, снять дамп и восстановить импорты**.
