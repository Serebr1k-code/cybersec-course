Упаковка — это сжатие или шифрование кода с добавлением распаковщика (стаба), который при запуске
восстанавливает оригинальный образ в памяти и передаёт ему управление. Легально упаковка уменьшает
размер и защищает от модификации; в malware — скрывает код от антивирусов и аналитика. Реверс
упакованного файла начинается не с логики программы, а со снятия упаковки: найти точку распаковки,
дождаться восстановления кода и снять дамп памяти. Этот урок — о том, как это делать системно.

## Зачем упаковывают код

Мотивы разные. Сжатие (UPX) уменьшает размер дистрибутива. Защита интеллектуальной собственности
мотивирует обфускацию и шифрование. Malware-авторы упаковывают образцы, чтобы:

- **Обойти антивирус**: сигнатуры ищут по байтам, а в упакованном файле исходного кода нет.
- **Затруднить статический анализ**: строки, импорты и код скрыты.
- **Обойти проверки**: каждая распаковка может давать новый образ (полиморфизм).

Понимание мотива подсказывает метод: если цель — сжатие, распаковка тривиальна; если защита —
потребуется ручной разбор стаба.

## Типы упаковщиков

Упаковщики делят на группы:

- **Простые компрессоры**: UPX, MPRESS, ASPack, FSG. Код сжимается, стаб распаковывает его в память.
  Определяются по сигнатурам секций (`.upx0`, `.MPRESS1`), по энтропии.
- **Криптоупаковщики**: код шифруется, ключ в стабе. Распаковка требует эмуляции или отладки.
- **Коммерческие протекторы**: VMProtect, Themida, Enigma — не просто упаковывают, а виртуализируют
  код, добавляют анти-отладку и проверки целостности (см. отдельный урок).
- **Кастомные упаковщики**: написаны автором малвари специально; часто используют нестандартную
  схему (XOR-цикл, нестандартный стаб), чтобы обойти автоматические распаковщики.

Определить упаковщик помогает **Detect It Easy (DIE)** — он анализирует секции, энтропию,
сигнатуры и выдаёт вердикт. Также полезен `rabin2 -I`, `pefile`, `binwalk`.

## UPX: распаковка

UPX — самый распространённый упаковщик, и для него есть готовое решение. Проверка:

```
$ upx -t ./sample
                       Ultimate Packer for eXecutables
   File size         Ratio      Format      Name
--------------------   ------   -----------   -----------
     12345 <-      4321   35.01%   linux/amd64   sample
Tested 1 file.
```

Если файл упакован UPX, распаковка одной командой:

```
$ upx -d ./sample -o ./sample_unpacked
                       Ultimate Packer for eXecutables
   File size         Ratio      Format      Name
--------------------   ------   -----------   -----------
      4321 ->     12345  285.70%   linux/amd64   sample_unpacked
Unpacked 1 file.
```

После этого бинарник готов к обычному анализу. Однако UPX можно модифицировать: изменить магию
секции (`UPX!`), удалить строку версии, чтобы `upx -d` отказался. Тогда распаковка выполняется
вручную. Также бывают «UPX с мусором» и повреждёнными заголовками — их тоже распаковывают руками.

## Кастомные упаковщики и поиск OEP

Ручная распаковка следует общему алгоритму:

1. **Найти стаб**: точка входа (`e_entry`/`AddressOfEntryPoint`) указывает не в обычный `_start`,
   а в код, который выглядит нетипично (высокая энтропия окружения, странные секции).
2. **Определить, куда распаковывается**: обычно в writable секцию (`.data`, `.bss`, или секцию с
   именем упаковщика), которая затем становится исполняемой.
3. **Поставить watchpoint на запись** в начало целевой области (см. урок про аппаратные точки).
   Срабатывание приведёт в цикл распаковки.
4. **Дождаться окончания распаковки**: обычно распаковщик заканчивается переходом (`jmp`) в
   восстановленный код. Точка назначения этого перехода — **OEP** (Original Entry Point).
5. **Поймать OEP**: поставить breakpoint на предполагаемый OEP или следить за `jmp` в
   свежераспакованную область. Часто помогает правило «переход в сегмент, который только что был
   записан и стал исполняемым».
6. **Снять дамп памяти** и восстановить импорты.

Признаки OEP: код похож на пролог функции (`push rbp; mov rbp, rsp`), вокруг появляются нормальные
строки и вызовы API. В UPX OEP восстанавливается из специальной таблицы; в кастомных упаковщиках —
вычисляется стабом.

## Дамп памяти и восстановление импортов

После остановки на OEP нужно сохранить образ. В gdb:

```
(gdb) info proc mappings
  0x400000 0x401000 ...  # .text (упакованный/распакованный)
(gdb) dump binary memory /tmp/dump.bin 0x400000 0x410000
```

В Windows — плагин **Scylla** (в x64dbg): он делает дамп процесса, находит IAT и восстанавливает
импорты, обрезая невалидные записи. Без восстановления импортов дамп может не запускаться
(загрузчик не сможет разрешить внешние вызовы). Scylla анализирует память, находит таблицу импорта
и перестраивает её в дампе; при необходимости добавляет секцию и правит заголовки.

Для ELF аналог — `dump` + инструменты вроде `lief` для правки заголовков, либо ручное
восстановление секций. Часто проще не дампить, а анализировать распакованный образ прямо в отладчике.

Отдельная тонкость: при дампе нужно сохранять не только код, но и изменённые данные (например,
расшифрованные строки), иначе логика восстановится частично. Для ELF дамп делается по диапазону из
`/proc/<pid>/maps`; для PE Scylla сохраняет весь образ по `SizeOfImage` от базы. После дампа
проверьте, что точка входа указывает на OEP, а не на стаб, — иначе образ при запуске снова начнёт
распаковываться (что может упасть, потому что стаб уже отработал).

## Практический разбор: распаковка вручную

Пусть `file ./packed` говорит `packed`, а `DIE` — «custom». Открываем в gdb:

```
$ gdb ./packed
(gdb) starti
(gdb) info proc mappings
0x400000 0x401000 r-xp  # код (стаб + упакованное)
0x600000 0x601000 rw-p  # данные (сюда будет распаковка)
(gdb) watch *(char*)0x600000
Hardware watchpoint 1: *(char*)0x600000
(gdb) continue
Hardware watchpoint 1: *(char*)0x600000
Old value = 0 '\000'
New value = 0x7f '...'
0x0000000000400150 in unpack_loop ()
(gdb) x/10i $pc
=> 0x400150: mov al, BYTE PTR [rsi]
   0x400152: xor al, 0x42
   0x400154: mov BYTE PTR [rdi], al
   0x400156: inc rsi
   0x400157: inc rdi
   0x400158: cmp rdi, rdx
   0x40015b: jne 0x400150
```

Это XOR-цикл распаковки (ключ `0x42`). Продолжаем до конца цикла, затем ставим breakpoint на
подозрительный `jmp` после цикла:

```
(gdb) break *0x400170
(gdb) continue
(gdb) x/5i $pc
=> 0x400170: jmp 0x600000        # переход в распакованный код
(gdb) stepi
(gdb) x/5i $pc
=> 0x600000: push rbp            # похоже на OEP
```

Попали на OEP. Дампуем и анализируем:

```
(gdb) delete
(gdb) dump binary memory /tmp/unpacked.bin 0x600000 0x610000
```

Дальше — правка заголовков и восстановление импортов (или анализ в отладчике).

## Распаковка UPX с изменённым заголовком

Авторы малвари часто «ломают» UPX, чтобы автоматический распаковщик отказался. Типовые изменения:
переименование секций (`UPX0` → `zzzz`), удаление строки `UPX!`, изменение версии в заголовке
(последний байт `l_info`), порча поля `UPX!` в конце файла. `upx -d` проверяет эти маркеры и
возвращает ошибку `CantUnpackException`.

Обход: восстановить оригинальные маркеры вручную (в hex-редакторе вернуть имена секций и версию),
после чего `upx -d` заработает. Если не удаётся, распаковывайте вручную: найдите стаб, поставьте
watchpoint на целевую область, дождитесь OEP и снимите дамп. Для UPX OEP обычно вычисляется из
специальной таблицы внутри стаба; эмуляция стаба в Unicorn часто восстанавливает образ целиком.

## Эмуляция распаковки

Когда реальный запуск опасен (malware) или невозможен (не та ОС), распаковку эмулируют. Qiling
загружает PE/ELF и исполняет стаб в изолированной эмуляции, перехватывая `mmap`/`VirtualAlloc`,
`mprotect`/`VirtualProtect`. В момент, когда стаб вызывает `mprotect` на распакованную область,
эмулятор фиксирует её как исполняемую — это сигнал о завершении распаковки. Затем память снимается
как образ. Unicorn даёт более низкоуровневый контроль: вы сами исполняете инструкции, ловите
момент записи и читаете память.

Преимущество эмуляции — безопасность и воспроизводимость: образец не исполняется на реальной
машине, нет сетевой активности и персистентности. Недостаток — эмуляция неполна (не все API и
инструкции поддержаны), и сложные стабы с анти-эмуляцией могут «понять», что работают под
эмулятором, и не распаковаться. Тогда возвращаются к отладке на изолированной ВМ.

## Подводные камни

Первое: `upx -d` может отказаться, если магия/заголовок изменены — тогда ручная распаковка. Второе:
OEP может быть в середине уже существующей секции, а не в новой. Третье: после дампа нужно
восстановить импорты, иначе файл не запустится. Четвёртое: некоторые упаковщики делают несколько
слоёв (распаковка внутри распаковки). Пятое: анти-дамп проверяет целостность образа в памяти и
падает при попытке снять дамп. Шестое: TLS-колбэки могут запускать распаковку до точки входа — не
пропустите их.

## Что дальше / решение

Практика: возьмите бинарник, упакуйте его `upx`, распакуйте `upx -d`, сравните. Затем возьмите
готовый кастомно-упакованный CTF-бинарник, найдите OEP через watchpoint и снимите дамп. На Windows
потренируйтесь со Scylla. Далее — `reversing-vmprotect-themida` (коммерческие протекторы) и
`reversing-integrity-checks`.
