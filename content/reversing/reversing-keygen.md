## Вопрос, с которого всё начинается

Есть программа `keygenme`, которая просит серийный номер и отвечает `License OK` или
`Invalid serial`. Исходника нет. Задача: научиться **генерировать** валидные номера, а не
подбирать их перебором. Такую программу-генератор называют **keygen** (key generator).

Чтобы её написать, нужно восстановить алгоритм проверки из бинарника и обратить его. Это
классическая задача реверса: понять, как приложение проверяет ключ, и воспроизвести алгоритм.
Разберём полный цикл на конкретном примере.

Опираемся на прошлые уроки: мы умеем смотреть на бинарник (`strings`, `objdump`) и знаем, как
выглядит код проверки. Теперь превратим это в работающий keygen.

## Наш пример

Запускаем — видим поведение:

```
$ ./keygenme AAAAAAAA
Invalid serial
```

Смотрим строки — они подскажут, что искать:

```
$ strings -a keygenme | grep -iE 'serial|license|usage'
usage: keygenme <serial>
License OK
Invalid serial
```

Строка `Invalid serial` — это ветка провала проверки. В реальном бинарнике по ссылке (`xref`) на
неё находят саму функцию проверки. Здесь, для наглядности, посмотрим на её логику напрямую.

## Шаг 1: находим проверку и таблицу

В бинарнике функция проверки сравнивает каждый байт входа, предварительно применив XOR. Ключевые
данные — **таблица ожидаемых байтов** — лежат в секции `.rodata` (область только для чтения, где
хранятся константы). Найдём её:

```
$ objdump -s -j .rodata keygenme | sed -n '1,6p'
Contents of section .rodata:
 402000 01000200 00000000 323b362a 722c6363  ........2;6*r,cc
 402010 75736167 653a206b 65796765 6e6d6520  usage: keygenme
```

Обрати внимание на байты `32 3b 36 2a 72 2c 63 63` — это и есть таблица `TARGET`. Логика
проверки такая:

```c
TARGET = { 0x32, 0x3b, 0x36, 0x2a, 0x72, 0x2c, 0x63, 0x63 }

int check(char *s) {
    for (int i = 0; i < 8; i++)
        if ((s[i] ^ 0x42) != TARGET[i]) return 0;   // XOR-маска 0x42
    return s[8] == 0;                               // длина ровно 8
}
```

Термин: **XOR** — операция «исключающее ИЛИ» над битами. Её важное свойство: она **обратима
сама себе** (`a ^ b ^ b == a`). Именно поэтому XOR-проверки легко обращаются.

## Шаг 2: пишем keygen

Мы знаем и таблицу, и маску. Чтобы получить валидный вход, «ксорим» таблицу с маской `0x42`:

```
$ python3 -c "
T = bytes([0x32,0x3b,0x36,0x2a,0x72,0x2c,0x63,0x63])
print('serial =', bytes(b ^ 0x42 for b in T).decode())
"
serial = pyth0n!!
```

Готово: `pyth0n!!` — валидный серийник. Проверяем на настоящем бинарнике — это обязательный шаг,
«на глаз» верить нельзя:

```
$ ./keygenme "$(python3 -c "print(''.join(chr(b^0x42) for b in [0x32,0x3b,0x36,0x2a,0x72,0x2c,0x63,0x63]))")"
License OK
```

Keygen воспроизвёл алгоритм — программа приняла ключ.

## Шаг 3: типы проверок и что делать

Разные проверки требуют разных стратегий:

| Тип проверки | Как устроена | Как обратить |
|---|---|---|
| Прямое сравнение | вход == константа | взять строку из бинарника |
| Алгоритмический серийник | по входу считается хеш/сумма | реализовать обратный алгоритм |
| Имя + серийник | ключ зависит от имени | вычислить ключ для конкретного имени |
| CRC/контрольная сумма | серийник удовлетворяет CRC | подобрать хвост или решить алгебраически |
| Блочный шифр | серийник — расшифрованный блок | зашифровать нужный plaintext |
| Асимметричная подпись | подпись проверяется публичным ключом | keygen **невозможен** — только патч |

Ключевой вывод: при **асимметричной подписи** (RSA/ECDSA) приватный ключ у вендора, поэтому
сгенерировать валидный ключ нельзя — остаётся **патч проверки** (инвертировать ветку или заменить
возврат функции). Инструменты патча: `keypatch` (плагин IDA), r2 `wa`, правка в x64dbg.

## Шаг 4: если алгоритм запутан

Иногда алгоритм обфусцирован: opaque-предикаты, запутанные вычисления. Тогда помогает **эмуляция**:
r2/ESIL или angr позволяют «прогнать» функцию проверки с конкретным входом и посмотреть
промежуточные значения, не разбирая алгоритм целиком. Ещё приём — **извлечение таблиц**: если
проверка использует S-box или магические константы, их копируют из дампа прямо в keygen.

Для CRC-серийников задача обратная: подобрать последние байты так, чтобы CRC совпал. Для линейных
CRC это решается алгебраически над GF(2), для остальных — перебором.

## Итоговый маршрут keygen-задачи

1. **Локализовать проверку** — строки «Invalid serial»/«license», xref от ввода.
2. **Классифицировать схему** — сравнение / алгоритм / CRC / блочный шифр / подпись.
3. **Извлечь константы и таблицы** из `.rodata` или дампа.
4. **Реализовать обратный алгоритм** на Python; при невозможности — эмулировать или подобрать.
5. **Проверить** ключ на реальном бинарнике (read-back: «License OK»).
6. **Для асимметричной крипты** — патчить проверку, а не генерировать ключ.

Для современных языков меняется только навигация по коду: в Go восстанавливай имена через
`pclntab`, в Rust — демаглингом (`nm --demangle`), в Java — декомпилятором (`cfr`/`jd-cli`).
Логика везде одна: **найти проверку → восстановить алгоритм → keygen или патч**.

## Keygen по имени: пошагово

Самый частый тип проверки — «серийник зависит от имени». Восстановим её на конкретном примере. Пусть
программа считает сумму байтов имени, умножает на `0x1337` и сравнивает результат с числом из
серийника:

```python
def serial_for(name: str) -> str:
    s = sum(name.encode()) * 0x1337 & 0xffffffff
    return f"{s:08X}"

print(serial_for("alice"))   # 00264792
print(serial_for("bob"))     # 00170AF5
```

Проверяем в программе:

```
$ ./keygenme alice 00264792
License OK
```

Порядок тут ключевой: сначала мы **выразили** серийник через имя (обратный алгоритм), потом напечатали
его в нужном формате. Формат (`08X`, дефисы, регистр) важен не меньше формулы: проверка часто
сравнивает строку целиком, поэтому лишний пробел или строчная буква провалит валидный ключ.

## Если алгоритм нелинейный: z3

Когда проверка — не XOR и не сумма, а что-то с умножениями и модулем, обращать её руками больно.
Тогда условия просто «переводят» в решатель, и он сам находит вход:

```python
from z3 import *
s = [BitVec(f's{i}', 8) for i in range(4)]
sol = Solver()
acc = BitVecVal(0, 32)
for i in range(4):
    sol.add(ULE(0x20, s[i]), ULE(s[i], 0x7e))       # печатные ASCII
    acc = acc * BitVecVal(0x1f, 32) + ZeroExt(24, s[i])
sol.add(acc == 0x322DA2)                             # цель из бинарника
if sol.check() == sat:
    m = sol.model()
    print(''.join(chr(m.eval(v).as_long()) for v in s))   # lFv~
```

Решатель не перебирает строки, а решает систему уравнений символически — это тот же приём, что
использует `angr`, только вручную и по конкретному алгоритму. Практическая деталь: `z3` умеет
работать и с массивами (`Array`/`Select`) — это пригодится, если проверка индексирует таблицу по
значению из ввода; такой индекс называют символьным указателем, и мы разберём его в уроке про `angr`.

## Если не сработало

- **Ключ не принимается, хотя формула верна** — проверь формат: длина, регистр, дефисы, ведущие
  нули. Программа может ждать `XXXX-XXXX`, а не сплошную строку.
- **Результат расходится с бинарником** — почти всегда 32-битное переполнение: в C сумма
  «заворачивается», в Python нет. Добавляй `& 0xffffffff` после каждой операции.
- **Проверка зависит от железа/даты** — посмотри, не читает ли функция проверки MAC, серийник тома
  или текущую дату; тогда keygen должен воспроизвести и эту зависимость.
- **Ветка есть, но ключ всё равно не проходит** — возможно, после keygen-проверки идёт вторая
  (например, контрольная сумма самого серийника). Ищи второй вызов проверки.

## Что мы теперь знаем

- **Keygen** восстанавливает алгоритм проверки и генерирует валидные ключи.
- Маршрут: найти проверку (`strings`/xref) → понять алгоритм → обратить его.
- XOR обратим сам себе — XOR-проверки дают keygen почти сразу.
- Константы и таблицы лежат в `.rodata`; их извлекают через `objdump -s`.
- Проверка с именем пользователя даёт ключ, зависящий от имени.
- При **асимметричной подписи** keygen невозможен — переходим к патчу.
- Формат серийника (длина, регистр, дефисы) так же важен, как формула: проверка сравнивает строку
  целиком, поэтому `00264792` и `264792` — не одно и то же.

## На что смотреть дальше

- Не пытайся писать keygen при RSA/ECDSA-подписи — сразу патчи проверку.
- Проверяй длину и формат: многие проверки требуют точное число символов, дефисы, регистр.
- Всегда проверяй сгенерированный ключ на реальном бинарнике, а не «в уме».
- Помни про переполнение: в C 32-битная сумма «заворачивается» — в Python добавляй `& 0xFFFFFFFF`.
- При обфускации эмулируй функцию, а не разбирай её вручную.
- Для Rust/Go/Java меняется только навигация по коду (демаглинг, декомпиляция), логика та же.

## Куда дальше

Мы научились обращать алгоритм проверки и генерировать ключи. Дальше возьмём продвинутую отладку —
**time-travel debugging**, где можно «отмотать» исполнение назад. А пока главное запомни:
**keygen — это обратный алгоритм**, и XOR/таблицы дают его быстро, а асимметричная крипта
заставляет патчить.

## Где пригодится

- **CTF Reversing:** задачи категории «keygen» — классический тип.
- **Аудит ПО:** понимание, как устроены лицензионные проверки и где они слабы.
- **Malware analysis:** распознавание лицензионных/активационных проверок в образцах.
- **Работа (RE-команда):** оценка стойкости схем активации.
- **Собес:** «как бы вы подошли к keygenme» — проверка навыка обращения алгоритмов.
