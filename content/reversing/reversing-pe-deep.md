## Вопрос, с которого всё начинается

ELF мы разобрали, Mach-O тоже. Остался третий формат, который ты встретишь чаще всего на CTF и в реальной работе — **PE** (Portable Executable), формат всех `.exe` и `.dll` в Windows. Он старше остальных и тащит за собой наследство: DOS-заголовок, странные смещения, «RVA» вместо адресов. Как не утонуть в этом и понять, что делает программа?

## Наш пример

Возьмём настоящий PE — `usepe.exe`, собранный под Windows:

```bash
$ file usepe.exe
usepe.exe: PE32+ executable for MS Windows 6.00 (console), x86-64, 4 sections
```

«PE32+» — 64-битный PE (для 32-битного было бы просто «PE32»), «x86-64» — архитектура, «4 sections» — сколько секций. Смотрим первые байты файла:

```bash
$ xxd usepe.exe | head -1
00000000: 4d5a 9000 0300 0000 0400 0000 ffff 0000  MZ..............
```

Первые два байта — `4d 5a`, то есть буквы **MZ**. Это магия PE (исторически — инициалы Марка Збиковски из MS-DOS). Но, в отличие от ELF и Mach-O, MZ — это ещё не «паспорт» программы, а обёртка. Разберёмся, почему.

## Шаг 1: DOS-заголовок и его «стрелка»

PE-файл начинается с **DOS-заголовка** — рудимента, оставленного для совместимости: если запустить `.exe` в DOS, он должен вежливо напечатать «This program cannot be run in DOS mode». Магии MZ достаточно, чтобы DOS-загрузчик понял: это исполняемый файл.

Главное поле этого заголовка — по смещению `0x3c`: 4 байта, которые указывают, где начинается настоящий PE-заголовок. В нашем файле это значение — `0x80`. Проверим:

```bash
$ xxd -s 0x80 -l 8 usepe.exe
00000080: 5045 0000 6486 0500                    PE..d...
```

`50 45 00 00` — это `PE\0\0`, сигнатура настоящего заголовка. То есть «стрелка» из DOS-заголовка ведёт к PE-заголовку. Запомним схему: **MZ → (по смещению 0x3c) → PE\0\0**.

## Шаг 2: RVA — адрес относительно образа

Дальше идёт PE-заголовок и «необязательный» (на деле обязательный) заголовок с ключевыми числами:

```text
ImageBase:        0x140000000
EntryPoint RVA:   0x1020
```

Обрати внимание: точка входа — `0x1020`, а не `0x140001020`. Это **RVA** (Relative Virtual Address) — смещение относительно базы образа `ImageBase`. По умолчанию Windows грузит 64-битный exe по адресу `0x140000000`, поэтому реальный виртуальный адрес кода — `ImageBase + RVA = 0x140001020`.

Зачем так? Потому что exe может быть загружен не по своей базе (если адрес занят). Тогда все адреса внутри сдвигаются на разницу баз — а RVA остаются неизменными. **RVA = адрес, независимый от того, куда загрузили образ.**

## Шаг 3: секции и перевод RVA ↔ файл

Секции PE похожи на ELF, но есть ловушка: у секции два разных адреса.

```text
  .text  RVA 0x1000  vs file offset 0x400
  .rdata RVA 0x2000  vs file offset 0x600
  .data  RVA 0x3000  vs file offset 0x800
```

Код в памяти лежит по `0x1000`, а в файле — по смещению `0x400`. Эти числа **не совпадают** из-за выравнивания: секции выравниваются в памяти по `SectionAlignment` (обычно `0x1000`), а в файле — по `FileAlignment` (обычно `0x200`). Поэтому чтобы найти байты по RVA, нужно вычесть RVA секции и прибавить её файловое смещение. Инструменты (`pefile`, Ghidra) делают это за нас, но помнить про разницу обязательно — иначе будешь «искать код не по тому адресу».

## Шаг 4: таблица импортов — какие функции зовёт программа

Программа на Windows почти всегда вызывает чужие функции из DLL. Список этих вызовов — **таблица импортов** (import table). Посмотрим её через `pefile`:

```text
Imports:
  DLL: mylib.dll
     helper RVA 0x2038
```

Читается так: `usepe.exe` при старте просит Windows загрузить `mylib.dll` и подставить адрес функции `helper`. Строка `helper` хранится в секции `.rdata` (по RVA `0x2038`), а на её место загрузчик записывает настоящий адрес функции.

Для реверса это золотая жила: по именам импортов сразу видно, что делает программа. Увидел `CreateProcessA`, `WinHttpSendRequest`, `RegSetValueEx` — перед тобой, скорее всего, загрузчик или стилер. Если имён нет (импорт «по ординалам»), это признак упаковки — об этом в уроке про пакеры.

## Шаг 5: экспорт и остальное

Обратная сторона импорта — **экспорт**: функции, которые DLL отдаёт наружу. Именно её мы использовали, когда собирали `mylib.dll`. Помимо импорта/экспорта в PE есть **ресурсы** (иконки, строки, диалоги — то, что раньше лежало в `.rsrc`), **релокации** (таблица адресов, которые надо поправить при загрузке не по базе) и **TLS-колбэки** — код, который Windows вызывает ещё до `main` (любимое место антиотладочных проверок). Все они описаны в «директориях данных» PE-заголовка.

## Шаг 6: релокации — почему exe живёт по разным адресам

Помнишь, что RVA не зависит от базы? Это возможно благодаря **релокациям**. Если Windows не может загрузить образ по `ImageBase` (адрес занят), она загружает его по другой базе и «сдвигает» все абсолютные адреса на разницу. Чтобы знать, какие адреса сдвигать, в PE есть таблица `.reloc` с их списком. У exe, который всегда грузится по своей базе, релокаций может не быть, а у DLL — почти всегда есть. Для реверса это важно: патчишь адрес в DLL — убедись, что он не попадёт в релокацию, иначе после сдвига патч «уедет».

## Шаг 7: как это выглядит в инструментах

В реальной работе тебе редко придётся читать DOS-заголовок вручную. Смотрим PE через `pefile` (Python):

```python
import pefile
pe = pefile.PE('usepe.exe')
print(hex(pe.OPTIONAL_HEADER.ImageBase), hex(pe.OPTIONAL_HEADER.AddressOfEntryPoint))
for s in pe.sections:
    print(s.Name.decode().rstrip('\x00'), hex(s.VirtualAddress))
```

```text
0x140000000 0x1020
.text 0x1000
.rdata 0x2000
.data 0x3000
.pdata 0x4000
```

А через `objdump -p usepe.exe` видны импорты (то, что мы смотрели). Для GUI-разбора используют **PE-bear** и **CFF Explorer**, для дизассемблера — **IDA**/**Ghidra**/**x64dbg**. Все они показывают одни и те же поля, которые мы разобрали.

## Шаг 8: на что смотреть дальше

Когда откроешь незнакомый `.exe`, не читай DOS-заголовок целиком. Порядок:

1. **`file`** — 32 или 64 бита, GUI или консоль, есть ли подозрение на упаковку (много секций с странными именами).
2. **Секции** — обычные `.text/.rdata/.data` или что-то вроде `UPX0`/`.aspack` (признак пакера).
3. **Импорты** — набор DLL и функций выдаёт назначение (`ws2_32` — сеть, `advapi32` — реестр/сервисы, `crypt32` — шифрование).
4. **Entry point** — по RVA найди точку входа в дизассемблере; если код там невнятный, вероятно распаковщик.
5. **Ресурсы** — `strings` и просмотр `.rsrc` часто вскрывают конфиг или строки-подсказки.

Эти шаги дают быстрый «паспорт» файла ещё до глубокого анализа.

## Что мы теперь знаем

- PE начинается с магии **MZ** (`4d 5a`), а по смещению `0x3c` лежит указатель на `PE\0\0`.
- Точка входа и другие адреса заданы как **RVA** — смещение относительно `ImageBase`.
- У секции есть и RVA (адрес в памяти), и file offset (смещение в файле) — они не равны.
- **Таблица импортов** перечисляет функции из DLL; имена импортов — быстрый способ понять назначение файла.
- **Экспорт**, ресурсы, релокации и TLS-колбэки — соседние структуры того же формата.

## Куда дальше

Мы разобрали все три формата: ELF, Mach-O, PE. Но программы редко состоят из одного файла — чаще это исполняемый файл плюс **разделяемые библиотеки**. В следующем уроке возьмём `.so`/DLL и разберём, как их реверсить отдельно: экспортируемые функции, версии, `dlopen`. А пока главное: любой формат — это «магия → заголовок → структуры → данные», и в PE ключевое слово — RVA.

## Где пригодится

- **CTF Reversing (Windows):** почти каждый Windows-crackme — это PE; понимание RVA и импортов ускоряет старт.
- **Malware analysis:** набор импортов (`WinHttp`, `CryptEncrypt`, `CreateProcess`) сразу намекает на класс малвари.
- **Vuln research:** экспорт DLL, релокации и TLS-колбэки — поверхность для эксплойтов и хайджека.
- **Кроссплатформенный реверс:** сравнивая PE с ELF/Mach-O, ты видишь общую идею «заголовок → структуры → данные».
