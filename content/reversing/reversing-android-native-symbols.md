## Вопрос, с которого всё начинается

Ты открыл нативную библиотеку `libnative.so` из приложения, но в списке функций — только `sub_1234`, `sub_5678`, без имён. Ясно, что символы вырезали. Как найти функцию, которая реализует JNI-метод, и понять, где логика?

## Наш пример

Возьмём `libnative.so`. Сначала посмотрим, что осталось:

```
$ strings -n 5 libnative.so | grep -E 'Java_|JNI'
Java_com_example_app_NativeBridge_checkLicense
Java_com_example_app_NativeBridge_getDeviceId
```

Даже при обрезанной таблице символов имена JNI-функций часто остаются в `.dynstr` — потому что они должны быть экспортированы, чтобы виртуальная машина Java их нашла.

## Шаг 1: два способа связать Java и native

JNI-методы регистрируются двумя способами. Первый — **по имени**: если нативная функция называется `Java_<пакет>_<класс>_<метод>` (точки заменяются на `_`), JVM находит её автоматически по имени. Второй — **через `RegisterNatives`**: при загрузке библиотеки вызывается функция, которая передаёт JVM таблицу соответствий «имя Java-метода → указатель на нативную функцию». В этом случае имена могут быть любыми (`sub_1234`), и найти их сложнее.

В нашем примере имена остались — значит, регистрация по имени. Если бы имена были вырезаны, мы искали бы вызов `RegisterNatives` и разбирали переданную таблицу.

## Шаг 2: почему символы вырезают и что остаётся

Компилятор по умолчанию включает в `.symtab` имена локальных функций. Флаг `-s` (strip) их убирает. Но **`.dynsym`** — таблица динамических символов — нужна загрузчику, поэтому экспортируемые функции там остаются. JNI-функции экспортируются (иначе JVM их не найдёт), поэтому их имена переживают strip.

Что теряется: имена внутренних helper-функций. Именно их приходится восстанавливать по вызовам: если `Java_..._checkLicense` вызывает `sub_4321` три раза, `sub_4321` — вероятно, вспомогательная проверка.

## Шаг 3: находим адрес и тело функции

Имя есть — нужен адрес. В обрезанном файле `nm -D` покажет динамические символы:

```
$ nm -D libnative.so | grep checkLicense
0000000000012340 T Java_com_example_app_NativeBridge_checkLicense
```

Адрес `0x12340`. Теперь дизассемблируем по нему и смотрим логику. Типичная структура JNI-функции: второй аргумент (`jobject`/`jclass`) и далее аргументы; возврат — `jboolean` (0/1) или строка.

## Шаг 4: anti-hook в нативном слое

Нативные проверки могут детектировать хуки. Типичные приёмы:

- **Проверка первых байт функции**: если по адресу стоит `b`/`br` (ARM64) вместо ожидаемого пролога, значит, кто-то вставил хук. Сравнивают первые инструкции с эталоном.
- **Чтение `/proc/self/maps`** на наличие `frida-agent`.
- **Проверка `ptrace`**: если процесс уже под отладчиком, `PTRACE_TRACEME` вернёт ошибку.
- **CRC-проверка** собственного `.text`.

Обход: перехватить `strcmp`/`memcmp`, которыми сравниваются эталонные байты, и вернуть «равно». Либо патчить саму проверку.

## Шаг 5: восстановление имён helper-функций

Когда имена вырезаны, применяют несколько приёмов. **Сигнатуры (FLIRT)**: сравнение кода с базой известных библиотек. **Строки**: функция, ссылающаяся на строку `checkLicense failed`, вероятно, и есть проверка лицензии. **Кросс-ссылки**: кто вызывается из `JNI_OnLoad` — часто инициализация. **Типы аргументов**: по использованию регистров угадывается сигнатура.

Комбинация этих приёмов позволяет восстановить структуру даже без имён. А если есть возможность запустить — Frida и трассировка вызовов дают точную картину.

## Шаг 6: находим артефакт практики

Среди строк библиотеки — наш артефакт. Достанем его:

```
$ strings -n 5 libnative.so | grep nto
nto{jni_r3g1st3rn4t1v3s_symb0ls}
```

## Что мы теперь знаем

- JNI-методы связываются по имени (`Java_<pkg>_<cls>_<meth>`) или через `RegisterNatives`.
- `strip` убирает `.symtab`, но `.dynsym` (динамические символы) остаётся — JNI-имена часто переживают.
- `nm -D` показывает экспортируемые символы и их адреса.
- Anti-hook проверяет первые байты функции, `/proc/self/maps`, `ptrace`, CRC `.text`.
- Восстановление имён: сигнатуры, строки, кросс-ссылки, трассировка.

## Разбор таблицы RegisterNatives

Если имена вырезаны, ищи вызов `RegisterNatives`. Его аргумент — массив структур `JNINativeMethod`
из трёх полей: имя (строка), сигнатура (строка), указатель на функцию. Даже при strip строки
имён и сигнатур часто остаются, потому что нужны JVM. Пройдя по массиву, ты восстановишь
таблицу «имя → адрес» и получишь имена всех обработчиков.

Сигнатура вида `(Ljava/lang/String;)Z` — это описание типов: принимает String, возвращает
boolean. Читая сигнатуры, ты понимаешь контракт каждой нативной функции до дизассемблирования.

## Типичные anti-hook приёмы и их обход

Проверка первых байт функции: код сохраняет эталонный пролог (например, `stp x29, x30, [sp,
#-16]!`) и сравнивает с текущим. Если Frida вставила `br` — детект. Обход: перехватить
`memcmp`/`strncmp` и вернуть «равно». Проверка `ptrace`: `PTRACE_TRACEME` вернёт ошибку, если
уже под отладчиком — обход через хук `ptrace` и возврат 0. CRC `.text`: обход через перехват
функции вычисления хеша.

## Частые ошибки

- Искать имена только в `.symtab` и не смотреть `.dynsym`.
- Забыть, что `strip` не убирает экспортируемые JNI-функции.
- Принять helper за обработчик JNI и неправильно понять контракт.
- Не учесть, что `RegisterNatives` может вызываться лениво, не в `JNI_OnLoad`.
- Игнорировать anti-hook и удивляться, что Frida «не видит» функцию.

## Чек-лист

1. `nm -D` — динамические символы и адреса.
2. `strings` — имена `Java_*` и сигнатуры JNI.
3. Если имён нет — найди `RegisterNatives` и разбери таблицу.
4. Определи anti-hook (первые байты, maps, ptrace, CRC).
5. Обход — перехват соответствующих libc-функций.

## Разбор реального примера: восстановление таблицы RegisterNatives

Разберём случай, когда имена вырезаны. Ищем `RegisterNatives`:

```
$ strings -n 5 libnative.so | grep -i register
RegisterNatives
JNI_OnLoad
```

Дизассемблируем `JNI_OnLoad`:

```
$ objdump -d libnative.so | grep -A12 '<JNI_OnLoad>'
 2100:  adrp    x0, 3000
 2104:  add     x0, x0, #0x40      ; x0 = &class ref
 2108:  bl      FindClass
 210c:  mov     x2, x0
 2110:  adrp    x1, 3100
 2114:  add     x1, x1, #0x80      ; x1 = &methods[]
 2118:  mov     w3, #2             ; число методов
 211c:  bl      RegisterNatives
```

Итак, `x1` указывает на массив `JNINativeMethod` из 2 элементов по адресу `0x3180`. Каждый
элемент — три указателя: имя, сигнатура, функция. Дамп памяти по `0x3180` покажет таблицу:

```
$ xxd -s 0x3180 -l 48 libnative.so
00003180: 2003 0000 0000 0000 2803 0000 0000 0000   .......(...(...
00003190: 4012 0000 0000 0000 3003 0000 0000 0000   @.......0.......
000031a0: 3803 0000 0000 0000 8012 0000 0000 0000   8...............
```

Здесь `0x0320` и `0x0330` — указатели на строки имён, `0x0328`/`0x0338` — на сигнатуры, а
`0x1240`/`0x1280` — адреса функций. Читая строки по этим адресам, восстанавливаем таблицу
«имя → адрес» и получаем имена обработчиков.

## Anti-hook: как выглядит и как обойти

Нативный anti-hook может сравнивать первые байты функции с эталоном. В ARM64 типичный пролог
— `stp x29, x30, [sp, #-16]!`, байты `fd 7b bf a9`. Если Frida вставила `br x16`, байты будут
другими, и проверка сработает. Обход: перехватить `memcmp`/`strncmp`, которыми сравниваются
байты, и вернуть «равно». Другой anti-hook читает `/proc/self/maps` в поисках `frida` — обход
через перехват `fopen`/`open` и подмену содержимого.

## Сравнение с восстановлением символов на других платформах

На Linux/Windows символы восстанавливают через FLIRT-сигнатуры и PDB/DWARF. На Android
специфика в JNI: даже обрезанная библиотека часто сохраняет имена экспортируемых JNI-функций
и строки сигнатур. Поэтому первый шаг здесь — не сигнатуры, а `nm -D` и `strings` вокруг JNI.

## Восстановление сигнатур по NDR/JNI

Сигнатура JNI (`(Ljava/lang/String;)Z`) говорит о типах аргументов и возврата. Если строки
сигнатур сохранились (а они нужны JVM при регистрации по имени), ты получаешь контракт функции
до дизассемблирования. Разбирай их так: в скобках — аргументы, после — возврат. `I` — int,
`J` — long, `Z` — boolean, `Ljava/lang/String;` — объект String, `[B` — массив байт.

Зная сигнатуру, ты знаешь, что второй аргумент функции — `jobject`, третий — `jstring`, и как
интерпретировать регистры при входе. Это сильно упрощает чтение JNI-функций.

## Динамическое восстановление имён

Если имена вырезаны и таблица `RegisterNatives` обфусцирована, помогает трассировка: Frida
перехватывает `RegisterNatives` и логирует переданный массив. Ты видишь пары «имя → адрес» в
момент регистрации. Это надёжнее статики, потому что не требует разбора структур вручную.

```javascript
Interceptor.attach(Module.getExportByName(null, 'RegisterNatives'), {
  onEnter(args) {
    var methods = args[1];
    var count = args[2].toInt32();
    for (var i = 0; i < count; i++) {
      var name = methods.add(i * 24).readPointer().readCString();
      console.log('JNI method:', name);
    }
  }
})
```

## Зачем это нужно

Без имён реверс нативного слоя превращается в угадывание. Восстановив таблицу JNI, ты получаешь
карту «что вызывает Java → где нативный код». Это отправная точка для анализа: ищи функции с
«говорящими» именами (checkLicense, decrypt, verify) и начинай с них.

## Итоговая стратегия

Порядок действий для обрезанного `.so`: сначала `nm -D` и `strings` (часто хватает), затем
поиск `RegisterNatives` и разбор таблицы, затем восстановление helper-функций по строкам и
кросс-ссылкам, и наконец — динамика через Frida. Держи в голове, что JNI-имена и сигнатуры
часто переживают strip, поэтому начинай именно с них. А anti-hook проверяй всегда — иначе хук
«не сработает» там, где приложение его уже обнаружило.
