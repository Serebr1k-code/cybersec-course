## Вопрос, с которого всё начинается

Ты открыл нативную библиотеку `libnative.so` из приложения, но в списке функций — только `sub_1234`, `sub_5678`, без имён. Ясно, что символы вырезали. Как найти функцию, которая реализует JNI-метод, и понять, где логика?

## Наш пример

Возьмём `libnative.so`. Сначала посмотрим, что осталось:

```
$ strings -n 5 libnative.so | grep -E 'Java_|JNI'
Java_com_example_app_NativeBridge_checkLicense
Java_com_example_app_NativeBridge_getDeviceId
```

Даже при обрезанной таблице символов имена JNI-функций часто остаются в `.dynstr` — потому что они должны быть экспортированы, чтобы виртуальная машина Java их нашла.

## Шаг 1: два способа связать Java и native

JNI-методы регистрируются двумя способами. Первый — **по имени**: если нативная функция называется `Java_<пакет>_<класс>_<метод>` (точки заменяются на `_`), JVM находит её автоматически по имени. Второй — **через `RegisterNatives`**: при загрузке библиотеки вызывается функция, которая передаёт JVM таблицу соответствий «имя Java-метода → указатель на нативную функцию». В этом случае имена могут быть любыми (`sub_1234`), и найти их сложнее.

В нашем примере имена остались — значит, регистрация по имени. Если бы имена были вырезаны, мы искали бы вызов `RegisterNatives` и разбирали переданную таблицу.

## Шаг 2: почему символы вырезают и что остаётся

Компилятор по умолчанию включает в `.symtab` имена локальных функций. Флаг `-s` (strip) их убирает. Но **`.dynsym`** — таблица динамических символов — нужна загрузчику, поэтому экспортируемые функции там остаются. JNI-функции экспортируются (иначе JVM их не найдёт), поэтому их имена переживают strip.

Что теряется: имена внутренних helper-функций. Именно их приходится восстанавливать по вызовам: если `Java_..._checkLicense` вызывает `sub_4321` три раза, `sub_4321` — вероятно, вспомогательная проверка.

## Шаг 3: находим адрес и тело функции

Имя есть — нужен адрес. В обрезанном файле `nm -D` покажет динамические символы:

```
$ nm -D libnative.so | grep checkLicense
0000000000012340 T Java_com_example_app_NativeBridge_checkLicense
```

Адрес `0x12340`. Теперь дизассемблируем по нему и смотрим логику. Типичная структура JNI-функции: второй аргумент (`jobject`/`jclass`) и далее аргументы; возврат — `jboolean` (0/1) или строка.

## Шаг 4: anti-hook в нативном слое

Нативные проверки могут детектировать хуки. Типичные приёмы:

- **Проверка первых байт функции**: если по адресу стоит `b`/`br` (ARM64) вместо ожидаемого пролога, значит, кто-то вставил хук. Сравнивают первые инструкции с эталоном.
- **Чтение `/proc/self/maps`** на наличие `frida-agent`.
- **Проверка `ptrace`**: если процесс уже под отладчиком, `PTRACE_TRACEME` вернёт ошибку.
- **CRC-проверка** собственного `.text`.

Обход: перехватить `strcmp`/`memcmp`, которыми сравниваются эталонные байты, и вернуть «равно». Либо патчить саму проверку.

## Шаг 5: восстановление имён helper-функций

Когда имена вырезаны, применяют несколько приёмов. **Сигнатуры (FLIRT)**: сравнение кода с базой известных библиотек. **Строки**: функция, ссылающаяся на строку `checkLicense failed`, вероятно, и есть проверка лицензии. **Кросс-ссылки**: кто вызывается из `JNI_OnLoad` — часто инициализация. **Типы аргументов**: по использованию регистров угадывается сигнатура.

Комбинация этих приёмов позволяет восстановить структуру даже без имён. А если есть возможность запустить — Frida и трассировка вызовов дают точную картину.

## Шаг 6: находим артефакт практики

Среди строк библиотеки — наш артефакт. Достанем его:

```
$ strings -n 5 libnative.so | grep nto
nto{jni_r3g1st3rn4t1v3s_symb0ls}
```

## Что мы теперь знаем

- JNI-методы связываются по имени (`Java_<pkg>_<cls>_<meth>`) или через `RegisterNatives`.
- `strip` убирает `.symtab`, но `.dynsym` (динамические символы) остаётся — JNI-имена часто переживают.
- `nm -D` показывает экспортируемые символы и их адреса.
- Anti-hook проверяет первые байты функции, `/proc/self/maps`, `ptrace`, CRC `.text`.
- Восстановление имён: сигнатуры, строки, кросс-ссылки, трассировка.
