## Вопрос, с которого всё начинается

Ты разбираешь программу на языке с **JIT** (Just-In-Time, компиляция «на лету»):
Java, JavaScript, C#. В файле — байткод, но во время работы виртуальная машина
**компилирует его в машинный код** и исполняет уже его. Значит, реальный код,
который надо реверсить, существует только в памяти и появляется динамически.
Как его найти и понять?

## Наш пример

Возьмём маленькую Java-программу, которая много раз вызывает «горячую» функцию:

```java
public class Jit {
    static int hot(int x){ int s=0; for(int i=0;i<x;i++) s+=i*i; return s; }
    public static void main(String[] a){ int r=0; for(int i=0;i<200000;i++) r=hot(50); }
}
```

Запустим JVM с ключом `-XX:+PrintCompilation` — HotSpot будет печатать, что и
когда компилирует:

```
$ java -XX:+PrintCompilation Jit
19    5       3       Jit::hot (23 bytes)
19    6       4       Jit::hot (23 bytes)
21    5       3       Jit::hot (23 bytes)   made not entrant
22    7 %     3       Jit::main @ 4 (35 bytes)
23    9 %     4       Jit::main @ 4 (35 bytes)
24    7 %     3       Jit::main @ 4 (35 bytes)   made not entrant
```

Читаем: метод `Jit::hot` скомпилирован (уровень 3, потом 4 — более
оптимизированный), затем перекомпилирован («made not entrant» — старая версия
больше не используется). Знак `%` — **OSR** (On-Stack Replacement): компиляция
тела цикла, пока он выполняется. Так мы видим, **что** JIT скомпилировал.

## Шаг 1: что такое JIT

Интерпретатор исполняет байткод медленно, поэтому виртуальная машина следит за
«горячими» местами (часто вызываемые методы, длинные циклы) и компилирует их в
машинный код. Дальше процессор исполняет уже нативный код — быстро. Компиляция
происходит **в рантайме**, поэтому:

- код лежит в памяти, а не в файле;
- адреса меняются от запуска к запуску;
- при деоптимизации код может быть «отброшен» и скомпилирован заново.

## Шаг 2: где живёт JIT-код

У каждой виртуальной машины свой «JIT-регион» в памяти:

- **HotSpot (Java)** — code cache; адреса видно через
  `-XX:+PrintCodeCache` и в `perf`/`jcmd`.
- **V8 (JavaScript)** — код в куче; инструменты `--print-opt-code`, `d8`.
- **RyuJIT (.NET)** — JIT-код в исполняемой памяти; `COMPlus_JitDisasm`.

Задача — **найти регион** с исполняемой памятью, куда VM пишет сгенерированный
код. В отладчике это область, помеченная `r-x`, содержимое которой меняется со
временем.

## Шаг 3: как смотреть сгенерированный код

Варианты:

- **Дизассемблировать код из памяти.** В gdb/lldb: найти JIT-регион
  (`/proc/<pid>/maps`), поставить точку по адресу метода и смотреть.
- **Ключи VM.** Java: `-XX:+UnlockDiagnosticVMOptions -XX:+PrintAssembly`
  (нужен плагин `hsdis`) печатает ассемблер скомпилированных методов. V8:
  `--print-opt-code`. .NET: `COMPlus_JitDisasm`.
- **Инструменты.** `perf` с JIT-символами (`/tmp/perf-<pid>.map`),
  `async-profiler`, `JITWatch` (Java).

Ключи VM — самый простой путь: не нужно искать адреса, VM сама печатает, что
сгенерировала.

## Шаг 4: деоптимизация и «плавающий» код

Важная особенность JIT — **деоптимизация**: если предположение оптимизатора
нарушилось (например, пришёл объект другого типа), код откатывается к
интерпретатору. Поэтому один и тот же метод может быть скомпилирован несколько
раз, а «made not entrant» отмечает устаревшую версию. При анализе это значит:
адрес метода не постоянен, и нужно ловить момент, когда нужный код активен.

## Шаг 5: почему JIT используют для защиты

JIT-код сложно реверсить:

- он не в файле — статический анализ не помогает;
- генерируется динамически, зависит от входных данных;
- легко **мутировать**: VM может каждый раз генерировать разный код;
- можно спрятать логику в «виртуальной машине» (как VMProtect, только на уровне
  языка).

Поэтому малварь на PowerShell/JavaScript и защищённые Java-приложения часто
используют JIT-генерацию: например, код расшифровывается и исполняется через
`eval`/`exec`, порождая новый нативный код.

## Шаг 6: практический маршрут анализа JIT

1. **Определить VM** (HotSpot, V8, RyuJIT) по строкам/поведению.
2. **Включить печать JIT** (`PrintCompilation`/`PrintAssembly`, `--print-opt-code`).
3. **Найти интересный метод** — по имени в выводе компиляции.
4. **Снять сгенерированный код** — из печати VM или из памяти.
5. **Разобрать** — с учётом оптимизаций (инлайнинг, векторизация).
6. **Сопоставить с байткодом** — понять, какой метод породил какой участок кода.

Шаг 6 важен: без сопоставления легко потеряться в оптимизированном ассемблере.
Печать VM обычно расставляет метки методов, что и служит картой.

## Шаг 7: оптимизации, которые сбивают с толку

JIT-код не похож на «наивную» компиляцию:

- **Инлайнинг** — маленькие методы встраиваются целиком, границы теряются.
- **Векторизация** — цикл превращается в SIMD-инструкции.
- **Удаление проверок** — если тип доказан, проверки выбрасываются.
- **Развёртка циклов** — тело цикла дублируется.

Поэтому читать JIT-ассемблер сложнее, чем обычный: «одна строка исходника» может
развернуться в десятки инструкций. Ориентир — строки-комментарии в
`PrintAssembly`, которые VM расставляет по методам.

## Шаг 8: V8 и JavaScript

В **V8** (движок Chrome/Node.js) JIT двухуровневый: сначала **Sparkplug**
(быстрый компилятор), потом **TurboFan** (оптимизирующий). Сгенерированный код
смотрят так:

```
$ node --print-opt-code --allow-natives-syntax script.js
```

Также есть `--trace-turbo` (дамп графа TurboFan) и `d8` (shell с отладочными
флагами). JS-малварь часто обфусцирована и генерирует код через `eval`/`Function`,
поэтому JIT-анализ тут — рабочий инструмент. Полезно ловить момент компиляции и
смотреть, какой нативный код получился из «запутанного» JS.

## Шаг 9: .NET и RyuJIT

В .NET JIT — **RyuJIT**. Дизассемблер включают переменной окружения:

```
$ COMPlus_JitDisasm=MyMethod dotnet run
```

Он печатает ассемблер метода. Как и в HotSpot, видно инлайнинг и оптимизации.
Для .NET удобен и **BenchmarkDotNet** с дизассемблером, и **perfview** для
профилирования.

## Частые вопросы

**PrintAssembly молчит.** Нужен плагин `hsdis` (дизассемблер) и флаг
`-XX:+UnlockDiagnosticVMOptions`. Без него ассемблер не печатается.

**Не могу найти адрес JIT-кода в отладчике.** Смотри `/proc/<pid>/maps` на
исполняемые регионы (`r-xp`), которые не совпадают с файлами, — это JIT-регион.
Ещё помогает `/tmp/perf-<pid>.map`, куда VM пишет символы для `perf`.

**Код меняется от запуска к запуску.** Это нормально: JIT мутирует и
перекомпилирует. Фиксируй входные данные и прогрев, чтобы получить стабильный
вариант.

**Как обойти анти-JIT защиту?** Иногда VM специально не даёт снять код (проверки
отладчика). Тогда работают на уровне байткода/интерпретатора, а не сгенерированного
кода.

## Что мы теперь знаем

- **JIT** компилирует байткод в машинный код в рантайме; код живёт в памяти, а
  не в файле.
- `-XX:+PrintCompilation` показывает, что компилируется (`Jit::hot`, уровни 3/4,
  `%` = OSR).
- JIT-регион ищут по исполняемой памяти; код смотрят через ключи VM
  (`PrintAssembly`, `--print-opt-code`) или дизассемблируя из памяти.
- **Деоптимизация** перекомпилирует метод; адреса не постоянны.
- JIT используют для защиты (мутация кода), а оптимизации (инлайнинг,
  векторизация) усложняют чтение.
