Многие современные среды не интерпретируют байткод, а **компилируют его в машинный код на лету** —
это JIT (Just-In-Time). JavaScript (V8), Java (HotSpot), .NET (RyuJIT), LuaJIT, PyPy и браузеры
используют JIT. Для реверс-инженера это создаёт уникальную проблему: машинного кода нет в файле —
он генерируется в память во время выполнения, часто с оптимизациями и переупорядочиванием. Анализ
JIT-кода требует особых приёмов: найти регион, дождаться компиляции, понять оптимизированный код.

## Что такое JIT

JIT-компилятор принимает байткод (или AST) и генерирует машинный код для конкретной архитектуры,
применяя оптимизации: инлайнинг, разворачивание циклов, спекуляцию типов, устранение проверок. Код
генерируется в исполняемую память (обычно через `mmap` с правами `RWX`, затем `mprotect` на `R-X`).
Ключевое следствие: статический анализ исходного байткода и динамически сгенерированного кода могут
сильно различаться — оптимизатор «ломает» исходную структуру.

JIT может быть **baseline** (быстрая компиляция без оптимизаций) и **optimizing** (горячие функции
перекомпилируются с оптимизациями). Функция может компилироваться несколько раз (on-stack
replacement, деоптимизация при нарушении спекуляций).

## JIT в популярных средах

- **V8 (Chrome/Node.js)**: компилирует JS через TurboFan/Maglev; генерирует код в регионах
  `code_range`. Есть `--print-code`, `--trace-opt`, `--trace-deopt`.
- **HotSpot (Java)**: C1 (быстрый) и C2 (оптимизирующий) компиляторы; код в `CodeCache`. Флаги
  `-XX:+PrintCompilation`, `-XX:+PrintAssembly` (нужен hsdis).
- **RyuJIT (.NET)**: компилирует IL; есть `COMPlus_JitDisasm`, `COMPlus_JitDump`.
- **LuaJIT**: трассирующий JIT; трассы видны через `-jdump`.
- **PyPy**: JIT для Python; `--jit trace`.

Понимание конкретной среды подсказывает, как включить дамп сгенерированного кода.

## Как найти JIT-код в памяти

Регион JIT-кода — это исполняемая память, не привязанная к файлу на диске. Признаки:

- Отображение `rwx` или `r-x` без имени файла в `/proc/<pid>/maps` (анонимное).
- Выделение через `mmap(PROT_EXEC)`/`VirtualAlloc(PAGE_EXECUTE_READWRITE)`.
- Для V8 — большой регион `code_range` (гигабайты адресного пространства).
- Изменение прав (`mprotect`) с `RW` на `RX` после генерации.

Практический приём: поставить breakpoint/trace на `mmap`/`mprotect`/`VirtualProtect`, поймать момент,
когда память становится исполняемой, и снять дамп. В Linux удобно смотреть `/proc/<pid>/maps` и
`/proc/<pid>/mem`. Для V8 есть встроенный `--print-code`, который печатает дизассемблер
сгенерированных функций без ручного поиска.

## Отладка JIT

Отладка JIT-кода осложнена тем, что код динамический. Приёмы:

- **Дамп и офлайн-анализ**: снять регион, сохранить, открыть в дизассемблере (IDA/Ghidra).
- **Встроенные дамперы**: `--print-code` (V8), `-XX:+PrintAssembly` (HotSpot), `COMPlus_JitDisasm`
  (.NET) — показывают дизассемблер с комментариями.
- **GDB с JIT-поддержкой**: HotSpot регистрирует символы в GDB через `-XX:+DebugNonSafepoints` и
  `hsdb`; V8 предоставляет `--enable-osr` и GDB JIT interface.
- **Трассировка**: логировать переходы и вызовы (Intel PT, perf) — JIT-код исполняется на реальном
  CPU, поэтому аппаратная трассировка работает.
- **Инструментация на уровне байткода**: хукать до JIT (Frida на Java/JS) — проще, чем анализировать
  оптимизированный машинный код.

Стратегия: часто проще анализировать байткод/IR, чем сгенерированный код. JIT-код смотрят, когда
нужно понять оптимизации или найти уязвимость (спекуляции, деоптимизации).

## Анти-JIT защита и JIT-шеллкоды

Малварь использует JIT для обхода статического анализа: например, PowerShell AMSI-обходы через
`.NET` JIT, V8-эксплойты с JIT-шеллкодом. Анти-JIT защита (в лицензировании) может проверять
целостность сгенерированного кода или использовать JIT для виртуализации. Для анализа:

- Дамп JIT-региона после генерации.
- Поиск паттернов шеллкода в RWX-памяти (через `mprotect`-хуки).
- Трассировка через Intel PT для понимания потока.

JIT-шеллкоды часто появляются после уязвимости (JIT spraying) — это техника, при которой
константы компилируются в предсказуемые байты, образуя шеллкод.

## Практический разбор

Анализ Node.js-скрипта, проверяющего пароль. Включаем дамп:

```
$ node --print-code crackme.js
--- Raw source ---
function verify(s) { ... }
--- Code ---
  ...
  0x3a1b2c0    push rbp
  0x3a1b2c1    mov rbp, rsp
  0x3a1b2c4    cmp qword ptr [rdi+0xf], rdx   ; проверка длины
  0x3a1b2c8    ...
```

`--print-code` печатает дизассемблер оптимизированных функций. Здесь видна проверка длины и
последующие сравнения. Для более точного контроля используем `--trace-opt` (покажет, что
оптимизировано) и `--trace-deopt` (что деоптимизировано). Если код слишком оптимизирован, читайте
байткод (через `--print-bytecode`) — он ближе к исходной логике.

Для Java: `java -XX:+PrintCompilation -XX:+UnlockDiagnosticVMOptions -XX:+PrintAssembly Crackme`.
`PrintCompilation` покажет компиляции, `PrintAssembly` (с hsdis) — дизассемблер. Для .NET:
`COMPlus_JitDisasm=Verify dotnet crackme.dll`.

## Инструменты и флаги

| Среда | Дамп кода |
|---|---|
| V8/Node | `--print-code`, `--print-bytecode`, `--trace-opt` |
| HotSpot | `-XX:+PrintAssembly`, `-XX:+PrintCompilation` |
| .NET | `COMPlus_JitDisasm`, `COMPlus_JitDump` |
| LuaJIT | `-jdump` |
| PyPy | `--jit trace` |
| Общий | GDB JIT interface, Intel PT, `/proc/pid/mem` |

## JIT и защита W^X

JIT создаёт код в памяти, но современные системы требуют W^X (нельзя одновременно писать и
исполнять). Поэтому JIT-движки используют схему: выделяют память с правами `RW`, генерируют код,
затем `mprotect` на `R-X`. Иногда память остаётся `RWX` (если W^X не enforced), что удобно для
атакующего, но заметно защите. Для анализа важно ловить именно момент перехода `RW → RX`: после
него код готов и стабилен. Если дампить раньше, получите мусор; если позже — код может быть уже
перекомпилирован.

Практический приём: перехватить `mprotect` (Linux) или `VirtualProtect` (Windows), логировать
адрес и новые права; при переходе на исполняемые — снять регион. В Frida это делается хуком на
`mprotect` и `mmap`. Так вы получаете все JIT-регионы по мере их появления.

## Деоптимизация и спекуляция

Оптимизирующий JIT строит предположения о типах и значениях (спекуляции). Если предположение
нарушается, происходит **деоптимизация**: управление возвращается в интерпретатор или baseline-код.
Это важно для анализа: функция может исполняться то как оптимизированный код, то как интерпретатор,
и поведение может различаться. Для CTF это редкость, но для анализа JIT-уязвимостей (Type
Confusion в V8) — ключевое.

Инструменты: `--trace-deopt` (V8) показывает, где и почему произошла деоптимизация; HotSpot —
`-XX:+TraceDeoptimization`. Понимание спекуляций помогает объяснять «странное» поведение: например,
функция, которая на одних данных работает, а на других падает из-за нарушения инварианта.

## Практика: дамп JIT-региона

Простейший рецепт на Linux: запустить процесс, найти анонимные исполняемые регионы, снять их.

```
$ cat /proc/$(pgrep node)/maps | grep -E "rwx|r-x" | grep -v "/"
7f8a40000000-7f8a41000000 rwxp 00000000 00:00 0
$ dd if=/proc/$(pgrep node)/mem of=/tmp/jit.bin bs=1 skip=$((0x7f8a40000000)) count=$((0x1000000))
```

Полученный файл открываем в Ghidra/IDA, задав базу `0x7f8a40000000`. Так анализируется
сгенерированный код без встроенных дамперов. Минус — нужно правильно определить регион и момент
дампа (после компиляции). Комбинация с хуком на `mprotect` автоматизирует поиск.

## JIT в интерпретаторах Python

PyPy — Python с JIT. Он компилирует горячие циклы в машинный код, что даёт ускорение, но меняет
картину для анализа. Флаги: `--jit trace` (трассировка JIT), `pypy --jit off` (отключить JIT для
сравнения поведения). Для реверса PyPy-кода полезно: если логика зависит от JIT-оптимизаций
(например, целочисленная арифметика переполняется иначе), отключение JIT даёт «эталонное» поведение.
В остальном PyPy-программы анализируют так же, как CPython (по байткоду/исходнику).

Аналогично LuaJIT: `-jdump` печатает трассы и сгенерированный код, `-joff` отключает JIT. Для
embedded LuaJIT (роутеры) анализ трасс помогает понять производительность и логику.

## Границы JIT-функций и их восстановление

Одна из практических проблем — понять, где начинается и заканчивается сгенерированная функция.
JIT-код часто не имеет пролога в привычном смысле (оптимизатор может опустить `push rbp`), а
функции расположены встык. Помогают метаданные рантайма: V8 хранит карту `Code`-объектов, HotSpot —
`CodeCache` со списком nmethods, .NET — таблицы методов. Инструменты (GDB JIT interface, `perf map`,
`hsdb`) читают эти метаданные и сопоставляют адреса с именами функций.

Если метаданных нет (снятый дамп), границы восстанавливают эвристически: по инструкциям `ret`,
по выравниванию, по вызовам. Полезно также логировать, куда JIT передаёт управление (через трассу) —
это даёт точки входа. Для оптимизированного кода граф может быть «сплющен» (инлайнинг), поэтому одна
сгенерированная функция может соответствовать нескольким исходным.

## Подводные камни

Первое: JIT-код оптимизирован — исходная структура потеряна, читайте байткод. Второе: регион может
перемещаться/перекомпилироваться (деоптимизация) — фиксируйте версию. Третье: адреса меняются при
каждом запуске (ASLR + JIT) — используйте символы/дампы. Четвёртое: `RWX`-память может быть
запрещена (W^X) — JIT использует `mprotect`. Пятое: hsdis нужно установить отдельно для
`PrintAssembly`. Шестое: анти-отладка в V8/HotSpot может реагировать на флаги. Седьмое: для
спекулятивных уязвимостей анализ JIT требует понимания оптимизаций (bounds check elimination).
Восьмое: JIT-регион может быть огромным (гигабайты для V8) — фильтруйте по моменту компиляции, а не
дампите всё подряд. Девятое: сгенерированный код может зависеть от версии рантайма — один и тот же
JS компилируется по-разному в разных версиях V8.
