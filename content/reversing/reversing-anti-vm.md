## Вопрос, с которого всё начинается

Ты запускаешь образец в лабораторной виртуалке — и он просто печатает «ничего не делаю» и выходит.
Тот же файл на «железном» ноутбуке вдруг начинает что-то писать на диск и лезть в сеть. Значит,
внутри есть проверка: «я в виртуальной машине или на реальном компьютере?». Такие проверки называют
**анти-VM** и **анти-песочница** (sandbox — изолированная среда для автоматического анализа).

Для реверсера это двойная задача: во-первых, понять, какие именно проверки делаются (часто по ним
узнают семейство вредоноса), во-вторых — снять их, чтобы образец «раскрылся» и показал настоящую
функциональность. Разберём это на маленьком примере, который соберём сами.

Опираемся на прошлый урок про анти-отладку: там проверка ловила *отладчик*, здесь — *виртуальную
машину*. Приёмы похожи, но среда детектируется иначе.

## Наш пример

Соберём крошечный «образец», который меняет поведение в зависимости от того, работает ли он под
гипервизором (hypervisor — слой, на котором запускаются виртуальные машины; так работают VMware,
VirtualBox, KVM и облачные песочницы).

```c
extern int printf(const char*, ...);
static int under_vm(void){
    unsigned a,b,c,d;
    __asm__ volatile("cpuid":"=a"(a),"=b"(b),"=c"(c),"=d"(d):"a"(1),"c"(0));
    return (c>>31)&1;                       /* гипервизорный бит CPUID.1:ECX[31] */
}
int main(void){
    if (under_vm()) { printf("sandbox: benign\n"); return 0; }
    printf("payload: real work done\n");
    return 0;
}
```

Компилируем и запускаем на этой машине (это обычный ноутбук, не виртуалка):

```
$ gcc -O0 -fno-pie -no-pie -o sample sample.c && ./sample
payload: real work done
```

Поведение «полезной нагрузки» — это ветка, которую мы хотим видеть всегда. Теперь посмотрим, как
именно устроена проверка. Вот ключевой факт из дизассемблера:

```
$ objdump -d --no-show-raw-insn -M intel sample | sed -n '/<main>:/,/ret/p'
0000000000401153 <main>:
  401153:  push   rbp
  401157:  call   401126 <under_vm>
  40115c:  test   eax,eax
  40115e:  je     401171 <main+0x1e>     ; if (eax==0) -> payload
  401160:  mov    edi,0x402004
  401165:  call   puts@plt               ; "sandbox: benign"
  401171:  mov    edi,0x402014
  401176:  call   puts@plt               ; "payload: real work done"
```

Читается по-человечески так: `call under_vm` возвращает результат в `eax`; `test eax,eax` проверяет,
ноль там или нет; `je` (jump if equal, прыжок если равно нулю) уводит на ветку payload, когда
проверка вернула 0 — то есть «я не под гипервизором». Значит, чтобы заставить образец работать,
достаточно сделать так, чтобы `under_vm` всегда возвращала 0.

## Шаг 1: аппаратные проверки — CPUID и гипервизорный бит

Самая надёжная детекция живёт на уровне процессора. Инструкция **CPUID** возвращает сведения о CPU
по номеру «листа» (leaf). В листе 1 бит 31 регистра `ecx` выставляет сам гипервизор: он говорит
гостевой системе «ты под виртуализацией». Проверим, что отдаёт наша машина:

```
$ ./antivm
CPUID.1: hypervisor bit ecx[31] = 0
CPUID.40000000 vendor = 
```

`0` в первом бите и пустая строка вендора означают «голое железо». Под VMware та же команда
показала бы `hypervisor bit = 1` и вендора вида `VMwareVMware`, под KVM — `KVMKVMKVM`, под
VirtualBox — `VBoxVBoxVBox`. Это самое простое, что проверяет малварь в первую очередь.

## Шаг 2: артефакты операционной системы

Если процессор «врёт» или проверку прячут, детект идёт по следам виртуалки в системе. Самое
доступное — DMI/SMBIOS: таблица с описанием «железа», которую заполняет производитель. Читается
из `/sys/class/dmi/id/`:

```
$ cat /sys/class/dmi/id/product_name
Nitro ANV15-51
$ cat /sys/class/dmi/id/sys_vendor
Acer
```

На настоящем Acer мы видим реальное имя модели. А вот под VirtualBox там почти всегда окажется
`VirtualBox`, под VMware — `VMware Virtual Platform`, под QEMU — `Standard PC (Q35 + ICH9, 2009)`.
Дальше в ход идут: имена процессов драйверов (`vboxguest`, `vmtoolsd`, `qemu-ga`), файлы в
`/proc/scsi/`, MAC-адреса сетевых карт по первым трём байтам (OUI — префикс производителя):

```
$ ip link show | grep -i ether | head -1
    link/ether 74:d4:dd:28:5d:21 brd ff:ff:ff:ff:ff:ff
```

`00:05:69`, `00:0C:29`, `00:50:56` — это VMware; `08:00:27` — VirtualBox; `52:54:00` — QEMU.
Префикс `74:d4:dd` ни одному гипервизору не принадлежит, поэтому и эта проверка не сработала.

## Шаг 3: поведенческие проверки

Даже если железо и ОС «чистые», песочница выдаёт себя поведением. Классика:

- **Тайминги.** `rdtsc` считает такты процессора. Если между двумя замерами провал, похожий на
  приостановку эмулятора, — значит, нас гоняют в песочнице.
- **Аптайм.** Машина, которая «включилась» две минуты назад, — почти наверняка автоматическая
  ферма. Настоящий пользовательский ноутбук живёт часами.
- **Активность пользователя.** Песочница без мыши и клавиатуры, с пустым списком недавних файлов,
  с одним ядром и 1–2 ГБ RAM — типичный признак.

Малварь комбинирует десяток таких проверок и принимает решение по большинству. Поэтому «снять одну
проверку» часто недостаточно — нужно понять всю картину.

## Шаг 4: как обойти

Есть три подхода, от простого к трудоёмкому.

**Патч ветки.** Мы нашли `je` в `main`. Если поменять байт условного перехода так, чтобы он прыгал
всегда, `under_vm` перестанет влиять на результат. Условные переходы (`je/jne/jz/jnz`) удобно
менять на безусловный `jmp` или на противоположный. Это работает, когда проверка одна и локальна.

**Хук на функцию.** Если проверок много, проще перехватить саму `under_vm` (или `ptrace`, `cpuid`)
и заставить её всегда возвращать «не VM». В отладчике это делают точкой останова на `ret` функции
и правкой `eax`; в Frida — заменой реализации.

**Правка окружения.** Иногда быстрее не трогать код, а «притвориться железом»: подменить строки
DMI, скрыть драйверы виртуалки, поправить MAC. Так работают плагины сокрытия для отладчиков и
hardened-образы для анализа.

Наш образец ловится первым способом: `under_vm` возвращает 0 на железе, поэтому нам даже не нужно
ничего патчить — мы просто запускаем его на «боевой» машине и видим payload.

## Что мы теперь знаем

- **Анти-VM** — проверки «я в виртуальной машине/песочнице?»; при срабатывании образец прячет
  настоящую функциональность.
- Детекция бывает **аппаратной** (CPUID, гипервизорный бит), **на уровне ОС** (DMI, драйверы, MAC)
  и **поведенческой** (тайминги, аптайм, активность).
- В нашем примере проверка — один гипервизорный бит; в дизассемблере она видна как `cpuid` рядом с
  условным переходом.
- Обход: **патч ветки**, **хук функции**, **правка окружения** — по возрастанию трудоёмкости.

## Почему анти-VM — это набор эвристик

Анти-VM (и анти-песочница) не опирается на один надёжный признак — это **множество эвристик**, каждая из которых по отдельности слаба, но вместе они дают уверенный сигнал. Задача защиты: если программа «подозревает» виртуализацию, она меняет поведение — не расшифровывает полезную нагрузку, не устанавливает связь с C2, имитирует бездействие. Задача исследователя — снять эти эвристики или заставить программу поверить, что она на «настоящем» железе.

Категории проверок:

- **Аппаратные** — CPUID (гипервизорный бит, бренд-строка), MSR, тайминги инструкций, число ядер, DMI/BIOS-строки.
- **Артефакты ОС** — процессы (VBoxTray, vmtoolsd), службы, драйверы, файлы, ключи реестра, MAC-префиксы, устройства.
- **Поведенческие** — реакция на действия пользователя (движение мыши, клики), uptime, размер памяти/диска, наличие «человеческих» артефактов (браузерная история, документы).

Обход строится **по одной проверке**: либо прячут артефакты (смените BIOS-строки, имена процессов, MAC), либо патчат саму проверку (NOP на ветвление), либо запускают на «закалённом» гипервизоре, который скрывает своё присутствие (KVM с патчами, VMware с правками). Универсального рецепта нет: malware постоянно добавляет новые проверки, и обход — это итеративный процесс. Важно и этическое: анализировать malware в изолированной лаборатории, не в боевой сети.

## Если не сработало

- **Программа всё равно «молчит».** Значит, есть ещё одна проверка; переберите категории (CPUID, процессы, тайминги) и найдите её динамически.
- **Патч проверки не помогает.** Проверок несколько и они взаимозависимы; ищите общий флаг-«детект» и обнулите его, либо обойдите все.
- **Слишком много артефактов.** Скрывать по одному долго; используйте «закалённый» гипервизор с набором анти-детект патчей.
- **Программа проверяет железо.** CPUID/MSR/тайминги требуют аппаратной маскировки; не на всякой виртуалке это возможно.
- **Изоляция нарушена.** Если malware «вырвался» из песочницы — это инцидент; работайте только в изолированной сети.

## Частые вопросы

**Почему одна проверка не работает?** Защита комбинирует десятки эвристик: даже если вы скрыли одну, другая выдаст виртуализацию.

**Что такое гипервизорный бит?** Бит в CPUID, сообщающий, что код исполняется под гипервизором; обход — патч гипервизора, скрывающий его.

**Помогает ли «голое железо»?** Да, физическая машина снимает большинство проверок, но это дорого и небезопасно; поэтому строят «закалённые» ВМ.

**Почему тайминги — популярная проверка?** Инструкции под VM выполняются медленнее и менее предсказуемо; аномальные тайминги выдают песочницу.

## Куда дальше

Мы научились распознавать проверки среды. Дальше возьмём образец, который не просто проверяет, а
прячет свой код — **упакованный** — и посмотрим, как найти оригинальный код внутри. А пока главное
запомни: **анти-VM — это ветка «если виртуалка, веди себя безобидно», и её всегда можно снять**.

## Где пригодится

- **Malware analysis:** заставить образец раскрыться в лаборатории, не заражая рабочую машину.
- **CTF Reversing (hard):** задачи с «сэндбокс-детектом» часто решаются именно снятием проверки.
- **Анализ защищённого ПО:** понять, какие окружения протектор считает «опасными».
- **Detection engineering:** те же проверки — хорошие индикаторы семейства вредоноса.
- **Собес:** вопрос «как малварь понимает, что она в песочнице?» — классический.
