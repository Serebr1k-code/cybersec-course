**Анти-VM и анти-песочница** — это набор техник, которыми вредоносное ПО определяет, что работает не на «боевой» машине, а в виртуальной среде или песочнице, и меняет поведение (затихает, отказывается от полезной нагрузки). Для реверс-инженера это прямая задача: понять, какие проверки делаются, и нейтрализовать их, чтобы образец «раскрылся». Урок разбирает уровни детекции (железо, ОС, артефакты, поведение), конкретные проверки с кодом, способы обхода и полный разобранный пример обхода VMware-детекции.

## Зачем малварь детектит VM

Мотивы просты: уйти от автоматического анализа (песочницы, sandbox), отложить детонацию, обмануть IR-команду. Если образец видит VM — он либо завершается, либо ведёт себя безобидно, либо ждёт «настоящего» пользователя. Задача реверсера — снять эти проверки, чтобы увидеть реальную функциональность, и/или понять их как индикаторы (по проверкам часто определяют семейство).

Классификация по уровню:

- **Аппаратный** — CPUID, hypervisor bit, имена устройств, SMBIOS, MAC-префиксы.
- **ОС/артефакты** — реестр, файлы драйверов, процессы, службы, имена хостов.
- **Поведенческий** — тайминги, активность пользователя, uptime, число CPU, RAM.
- **Песочница** — отсутствие пользовательских данных, «стерильность» диска, мышь/клавиатура.

## Аппаратная детекция

Самая надёжная для малвари — проверки, которые трудно подделать.

```c
// hypervisor bit в CPUID leaf 1, ECX bit 31
int ecx;
__cpuid(1, eax, ebx, ecx, edx);
if (ecx & (1 << 31)) { /* мы под гипервизором */ }

// строка вендора в CPUID leaf 0x40000000
char vendor[13];
__cpuid(0x40000000, eax, ebx, ecx, edx);
memcpy(vendor, &ebx, 4); memcpy(vendor+4, &ecx, 4); memcpy(vendor+8, &edx, 4);
// "VMwareVMware", "KVMKVMKVM", "Microsoft Hv", "VBoxVBoxVBox"
```

Другие аппаратные признаки: **SMBIOS/DMI** (`dmidecode`), имена дисков (`VBOX HARDDISK`, `VMware Virtual disk`), MAC-префиксы (`00:05:69`, `00:0C:29`, `00:1C:14`, `00:50:56` — VMware; `08:00:27` — VirtualBox; `52:54:00` — QEMU/KVM), количество ядер, размер RAM.

## Детекция по артефактам ОС

Самый частый класс проверок — следы гипервизора в системе.

```c
// Windows: ключи реестра
RegOpenKeyEx(HKEY_LOCAL_MACHINE,
  "SYSTEM\\CurrentControlSet\\Services\\Disk\\Enum", 0, KEY_READ, &h);
// значение "0" содержит "VMware" / "Virtual HD" / "VBOX"
```

Типовые артефакты:

- **Реестр**: `HKLM\SOFTWARE\VMware, Inc.\VMware Tools`, `HKLM\SYSTEM\...\Disk\Enum` = `VBOX HARDDISK`.
- **Файлы/драйверы**: `vmtoolsd.exe`, `VBoxService.exe`, `vboxguest.sys`, `C:\Windows\System32\drivers\vm*.sys`.
- **Процессы**: `vmtoolsd`, `VBoxTray`, `qemu-ga`.
- **MAC-адрес** — префикс OUI.
- **Имя компьютера**: `SANDBOX`, `MALWARE`, `VIRUS`, стандартные имена песочниц.
- **Имя пользователя**: `sandbox`, `user`, `admin` из шаблона песочницы.

```bash
# на Linux-стенде проверки, которые делает малварь
systemd-detect-virt
dmidecode -s system-product-name
cat /sys/class/dmi/id/product_name
ip link | grep -i 'link/ether'
```

## Поведенческая детекция и анти-песочница

Малварь смотрит не только на железо, но и на «живость» среды:

- **Uptime/время работы.** Песочница запущена минуты назад — подозрительно.
- **Активность пользователя.** Нет движений мыши/нажатий клавиш → песочница.
- **Число файлов/документов** в профиле — «стерильный» диск = песочница.
- **Разрешение экрана** и число мониторов.
- **`GetTickCount`/`QueryPerformanceCounter`** — тайминги инструкций; в VM они аномальны.
- **Sleep-ускорение** — проверяет, «пропускает» ли песочница `Sleep` быстрее реального времени.
- **Доменные/сетевые признаки** — нет домена, фиксированный DNS.

```c
// проверка активности пользователя
LASTINPUTINFO li = { sizeof(li) };
GetLastInputInfo(&li);
DWORD idle = (GetTickCount() - li.dwTime) / 1000;
if (idle < 60) { /* пользователь активен */ }
```

## Обход: стратегии нейтрализации

1. **Патч проверки.** Найти `jz/jnz` и инвертировать/занулить — быстро, но хрупко.
2. **Хук API.** Через Frida/`LD_PRELOAD`/e9patch подменить результат (`IsDebuggerPresent`, `GetSystemFirmwareTable`, `RegQueryValue`).
3. **Маскировка среды.** Убрать артефакты: переименовать службы, сменить MAC, почистить реестр, подделать DMI.
4. **Обман таймингов.** Ускорить/замедлить время, «оживить» ввод.
5. **Символическое исполнение.** angr найдёт вход, при котором проверка «проходит».

```bash
# Frida: занулить hypervisor bit-проверку и подменить имя продукта
cat > anti-vm.js <<'EOF'
Interceptor.attach(Module.getExportByName(null, "GetSystemFirmwareTable"), {
  onLeave(r) { /* подменить буфер на "Real Hardware" */ }
});
EOF
frida -f ./sample -l anti-vm.js --no-pause
```

## Разобранный пример: обход VMware-детекции

**Шаг 1. Найти проверку.** В декомпиляторе видим вызов `RegQueryValueExA` на `Disk\Enum` и сравнение с `"VMware"`.

```c
RegOpenKeyExA(HKEY_LOCAL_MACHINE, "SYSTEM\\CurrentControlSet\\Services\\Disk\\Enum", ...);
RegQueryValueExA(hKey, "0", 0, 0, buf, &len);
if (strstr(buf, "VMware")) ExitProcess(0);   // <-- проверка
```

**Шаг 2. Быстрый патч.** В Ghidra: right-click на условном переходе → Patch Instruction → `JMP`. Или байтовый патч.

```bash
# найти смещение условного перехода и заменить на безусловный
# в r2:
r2 -w ./sample -qc 'aaa; s 0x00401a2e; wx eb' 
```

**Шаг 3. Хук вместо патча (надёжнее).**

```javascript
// подменить результат RegQueryValueExA для Disk\Enum
const fn = Module.getExportByName("advapi32.dll", "RegQueryValueExA");
Interceptor.attach(fn, {
  onEnter(a) { this.name = a[1].readAnsiString(); },
  onLeave(r) {
    if (this.name === "0") { /* переписать buf на "Real HDD" */ }
  }
});
```

**Шаг 4. Проверка.** После патча образец доходит до полезной нагрузки — видно в Procmon/сети.

## Маскировка стенда: практический чеклист

- Сменить MAC-адрес (`macchanger -m`) на реальный OUI.
- Убрать VMware Tools / VBox Guest Additions.
- Почистить реестр от `VMware`/`VBox` ключей и файлов драйверов.
- Переименовать компьютер в «человеческое» имя.
- Добавить «пользовательские» файлы и историю браузера.
- «Оживить» ввод (движение мыши через скрипт).
- Установить реалистичный uptime/дату.

| Инструмент | Назначение | Пример |
|---|---|---|
| `systemd-detect-virt` | тип виртуализации | `systemd-detect-virt` |

| `VBoxManage` | настройка VM | `setextradata` для DMI |

## Частые ошибки и подводные камни

- **Патч по одному адресу.** Проверок много (5-10); патч одной не помогает — нужен общий обход (хук API).
- **Забыть про тайминги.** Даже «чистая» VM палится по аномальным `rdtsc` — нужен обман времени.
- **Оставить артефакты.** Даже после патча часть проверок идёт по реестру/файлам; маскируйте стенд.
- **Не проверить, что патч применён.** Read-back: убедитесь, что исполнение пошло по нужной ветке (лог/трасса).
- **Игнорировать мультиуровневость.** Проверки накладываются (железо + ОС + поведение); снимайте все.
- **Ломать образец.** Неверный патч → краш; делайте копию и работайте в снапшоте.

## Что дальше / решение

Маршрут: **найти все проверки (статически + динамически) → выбрать обход (хук API надёжнее патча) → маскировать стенд → проверить, что образец дошёл до payload**. Инструментально: Frida/`LD_PRELOAD`/e9patch для хуков, `dmidecode`/`macchanger` для маскировки, angr для автоматического обхода условий. Дальше — `reversing-anti-debug` (снятие анти-отладки) и `reversing-malware-dynamic` (полный динамический анализ).

## Практика: автоматический обход проверки через angr

Когда проверок много и вручную их не снять, помогает символьное исполнение: задаём цель «дойти до полезной нагрузки» и просим angr найти вход.

```python
import angr, claripy
p = angr.Project("./sample", auto_load_libs=False)
# адрес после проверки VM (найден в Ghidra)
target = 0x00402000
state = p.factory.entry_state()
sm = p.factory.simulation_manager(state)
sm.explore(find=target)
if sm.found:
    print("достижимо; вход:", sm.found[0].posix.dumps(0))
```

Если проверка — просто ветвление на константе, angr обойдёт её «сам», найдя путь. Для внешних API (реестр) — хуки (`SimProcedure`), возвращающие нужные значения.

## Сравнение песочниц и их слабых мест

| Песочница | Слабые места |
|---|---|
| Cuckoo/CAPE | известные имена процессов, артефакты, тайминги |
| Any.Run | «живой» пользователь, но VM-артефакты |
| Joe Sandbox | детект по драйверам/сервисам |
| Своя VM (KVM) | MAC/DMI/uptime, если не маскировать |

Практика: перед запуском образца в песочнице проверьте её «стерильность» тестовым анти-VM-детектором. Если он палит среду — образец тоже.

## Подводные камни таймингов

- **`rdtsc`-дельта.** В VM и особенно под эмуляцией (QEMU) дельта аномальна. Обход: хук `rdtsc`/`QueryPerformanceCounter`, возвращающий «реальные» значения.
- **Ускорение `Sleep`.** Песочницы часто пропускают сон — малварь это детектит. Обход: реальный сон.
- **`NtQuerySystemInformation`.** Число процессоров, время загрузки — VM-специфичны.

```javascript
// Frida: нормализовать QueryPerformanceCounter
Interceptor.attach(Module.getExportByName(null, "QueryPerformanceCounter"), {
  onLeave(r) { /* скорректировать значение */ }
});
```

## Ключевые выводы по анти-VM

Итог: снимайте проверки **всеми уровнями сразу** (железо + ОС + поведение), предпочитая хуки API патчам. Маскируйте стенд (MAC, DMI, реестр, uptime, ввод) и проверяйте «живость» тестовым детектором. Для массового обхода — angr. Помните: успешный обход подтверждается тем, что образец дошёл до payload, а не тем, что патч «применился».

## Маскировка DMI/SMBIOS на уровне гипервизора

Иногда проще изменить саму VM, чем хукать проверки. В QEMU/KVM можно подделать DMI-строки, чтобы `dmidecode` показывал реальное железо, а не «QEMU/KVM».

```bash
# QEMU: задать SMBIOS-поля
qemu-system-x86_64 \
  -smbios type=0,vendor="American Megatrends" \
  -smbios type=1,manufacturer="Dell Inc.",product="OptiPlex 7080",serial="ABC123" \
  -smbios type=2,manufacturer="Dell Inc.",product="0ABC1D" \
  -netdev user,id=n0 -device e1000,netdev=n0,mac=52:54:00:12:34:56
```

В VirtualBox — через `setextradata`:

```bash
VBoxManage setextradata "vm" "VBoxInternal/Devices/pcbios/0/Config/DmiSystemProduct" "OptiPlex 7080"
VBoxManage setextradata "vm" "VBoxInternal/Devices/pcbios/0/Config/DmiSystemVendor" "Dell Inc."
```

Для VMware — правки в `.vmx` (`SMBIOS.reflectHost = "TRUE"`, чтобы отражать реальный хост). Это устраняет проверки на DMI на корню и часто надёжнее рантайм-хуков.

## Комбинированная детекция: почему одиночный патч бесполезен

Реальные образцы комбинируют 5-10 проверок, и результат агрегируется (флаги «подозрительно» → payload не запускается). Патч одной ветки ничего не даёт, если остальные всё ещё срабатывают. Правильный подход — **снять все проверки** (динамически найти их через трассировку API и захукать общий агрегатор) или **сделать стенд действительно похожим на железо** (DMI + MAC + uptime + ввод + отсутствие драйверов VM). Только тогда образец раскрывается полностью, и вы видите реальный payload.

## Где пригодится

- **Malware analysis:** распознавание и обход анти-VM/анти-песочницы, чтобы образец раскрылся.
- **CTF Reversing (hard):** задачи с анти-анализом требуют именно этих приёмов.
- **Vuln research:** понимание эвазивных техник в протекторах (VMProtect, Themida).
- **Работа (threat intel/SOC):** оценка «зрелости» образца, построение устойчивых песочниц.
- **Собес:** вопросы про CPUID, анти-VM — маркер практического опыта анализа malware.
