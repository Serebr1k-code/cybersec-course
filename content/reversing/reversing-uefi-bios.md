## Вопрос, с которого всё начинается

Ты дампишь прошивку материнской платы (или ноутбука) и хочешь понять, что там
внутри. Это **UEFI** — современная замена BIOS, которая стартует до операционной
системы и отвечает за инициализацию железа и загрузку ОС. Внутри — не один
бинарник, а целый архив модулей. Как его разобрать? Начнём с самого верхнего
уровня — **тома прошивки**.

## Наш пример

Возьмём `firmware.fv` — образ **Firmware Volume** (FV, том прошивки). Это
контейнер, в котором лежат модули UEFI. Разберём его заголовок на Python:

```
$ python3 uefi.py
FVH GUID   : 8c8ce578-8a3d-4f1c-9935-896185c32dd3
FV length  : 0x1000
block size : 0x1000
PE module at FV offset 0x2c, e_lfanew=0x40
PE sig     : b'PE\x00\x00'
Machine    : 0x8664 (0x8664 = x64)
Subsystem  : 0x9090
```

Разберём, что это значит. Первые 16 байт — **GUID** (глобальный уникальный
идентификатор). Значение `8c8ce578-8a3d-4f1c-9935-896185c32dd3` — это
стандартный GUID **Firmware File System** (FFS): так помечают тома, где лежат
файлы UEFI. Дальше идут длина тома (`0x1000`) и размер блока (`0x1000`) — том
разбит на блоки, обычно по 4 КиБ или 8 КиБ.

## Шаг 1: откуда берётся дамп прошивки

Прежде чем разбирать, прошивку надо получить:

- **С дампа SPI-flash** — микросхема flash на плате читается программатором
  (CH341A + clip) или через `flashrom`. Это самый полный и надёжный способ.
- **Из обновления BIOS** — файл прошивки от производителя, часто уже содержит
  FV, но может быть сжат/зашифрован.
- **Из памяти** — дамп через `/sys/firmware/efi` или утилиты вендора.

Мы работаем с уже полученным `firmware.fv`.

## Шаг 2: структура UEFI — уровни вложенности

UEFI-прошивка устроена как матрёшка:

1. **Firmware Volume (FV)** — том; внутри много **FFS-файлов**.
2. **FFS-файл** — модуль; имеет заголовок, тип, GUID и секции.
3. **Секции** — внутри файла: код, данные, UI-строки, версии.
4. **PE-модуль** — исполняемый код (как `.exe`, но для UEFI).

В нашем дампе по смещению `0x2c` найден **PE-модуль**: сначала идёт MZ-заголовок
(`e_lfanew=0x40`), затем сигнатура `PE\0\0`, машина `0x8664` (x86-64), а
подсистема `0x9090` — это специальное значение **EFI Application** (подсистема
UEFI, а не Windows). Так выглядит модуль DXE-драйвера.

## Шаг 3: фазы загрузки — PEI, DXE, BDS

UEFI стартует поэтапно:

- **SEC** (Security) — самый первый код, проверяет целостность.
- **PEI** (Pre-EFI Initialization) — инициализация памяти и железа.
- **DXE** (Driver Execution Environment) — загрузка драйверов, здесь живёт
  основная логика.
- **BDS** (Boot Device Selection) — выбор и загрузка ОС.
- **RT** (Runtime) — сервисы, доступные после загрузки ОС.

Реверс-инженеру важно понимать: интересные вещи (проверки Secure Boot,
разделы, драйверы) живут в DXE и в **SMM** (см. ниже).

## Шаг 4: UEFITool — главный инструмент

Разбирать FV вручную (как мы начали) полезно для понимания, но для реальной
работы берут **UEFITool** (и его форк UEFITool NE). Он:

- строит дерево томов, файлов, секций и PE-модулей;
- показывает GUID, тип, размеры, зависимости;
- позволяет **извлечь** любой модуль (`Extract as is`) для анализа в Ghidra/IDA.

Дополнительно используют `uefi-firmware-parser` (Python) для скриптового
разбора и `chipsec` — для проверки защит (BIOS lock, SPI protection).

## Шаг 5: SMM — самый привилегированный режим

**SMM** (System Management Mode) — режим процессора с максимальными правами,
более привилегированный, чем ядро ОС. Код SMM (SMI-обработчики) живёт в
защищённой памяти (SMRAM) и вызывается по прерываниям SMI. Уязвимости в SMM —
это уровень, где эксплойт обходит даже Secure Boot. Их ищут в модулях
`Smm*` и в SMI-обработчиках: `SMI`-хендлеры должны быть аккуратны с
валидацией указателей, иначе получают выполнение в SMRAM.

## Шаг 6: Secure Boot и bootkit

**Secure Boot** проверяет подписи загрузчиков и ОС по цепочке доверия. Ломают
его на нескольких уровнях:

- **Ослабление политики** — заменить/удалить базу ключей (`PK`, `KEK`, `db`) в
  переменных NVRAM.
- **Подмена модуля** — пропатчить DXE-драйвер, который что-то проверяет.
- **Bootkit** — вредоносный UEFI-модуль, стартующий до ОС и выживающий
  переустановку системы (пока не перезальют прошивку).

Именно поэтому при анализе прошивки ищут **неподписанные модули** и модули, чьи
GUID/хеши не совпадают с эталонными.

## Шаг 7: практический маршрут разбора

1. Получить дамп (SPI/обновление).
2. Открыть в UEFITool, изучить дерево FV → FFS → секции.
3. Извлечь интересные PE-модули и открыть в Ghidra (архитектура — x86-64 или
   ARM, подсистема EFI).
4. Искать строки, GUID, проверки, работу с NVRAM.
5. Проверить защиты через `chipsec` (SPI lock, BIOS write enable).

## Шаг 8: NVRAM и переменные UEFI

Многие настройки UEFI хранятся не в файлах, а в **NVRAM** — энергонезависимой
памяти, привязанной к прошивке. Это переменные с GUID-пространствами имён:

- `PK`, `KEK`, `db`, `dbx` — ключи **Secure Boot** (Platform Key, Key Exchange
  Key, база разрешённых и запрещённых подписей).
- `BootOrder`, `Boot####` — порядок загрузки.
- переменные вендора (настройки железа).

В прошивке NVRAM лежит в отдельном регионе (часто в конце SPI-flash) и
называется **NVRAM store** или **UEFI variables store**. При анализе её находят
по сигнатурам и разбирают структуру: имя, GUID, атрибуты, значение. Модификация
переменной Secure Boot — классический путь ослабления защиты.

## Шаг 9: подписи и верификация модулей

UEFI проверяет модули на нескольких уровнях: **Secure Boot** — подписи
загрузчиков; **Intel Boot Guard / AMD PSP** — корень доверия в железе (проверяет
первый код прошивки). Для анализа это значит: неподписанный модифицированный
модуль может просто не запуститься. Поэтому реверс часто идёт «в обход»: не
патчить модуль, а понять его логику и повлиять через данные (NVRAM, переменные).

## Частые вопросы

**UEFITool не находит модули.** Дамп может быть сжат или это не целый регион
flash. Проверь, что захватил весь чип, и попробуй найти FV по GUID.

**PE-модуль не открывается в Ghidra.** Укажи формат PE и подсистему EFI; иногда
модуль запакован (сжатие секций LZMA) — UEFITool умеет распаковывать секции.

**Где искать проверки Secure Boot?** В модулях DXE, связанных с
`Security`, `SecureBoot`, `Variable`; смотри работу с `db`/`dbx` и вызовы
верификации образов.

## Что мы теперь знаем

- UEFI-прошивка — это **Firmware Volume** с GUID `8c8ce578-...`, внутри —
  FFS-файлы, секции и PE-модули.
- В нашем дампе по смещению `0x2c` лежит PE-модуль (x86-64, подсистема EFI
  `0x9090`).
- Загрузка идёт по фазам SEC → PEI → DXE → BDS → RT; логика — в DXE.
- **UEFITool** разбирает дерево и извлекает модули; `chipsec` проверяет защиты.
- **SMM** — привилегированный режим; **Secure Boot** ломают подменой ключей или
  модулей, а **bootkit** выживает переустановку ОС.

## Разбор FFS-заголовка и секций вручную

FV мы разобрали на верхнем уровне; спустимся на шаг внутрь. Каждый **FFS-файл** начинается с заголовка, после которого идут тип и атрибуты:

```
offset 0  : GUID файла (16 байт)
offset 16 : checksum(2) + type(1) + attributes(1)
offset 20 : size[3] (24 бита, младшие 3 байта)
offset 23 : state(1)
offset 24 : тело файла (секции)
```

Тип FFS-файла определяет его роль:

| Тип | Значение |
|---|---|
| `0x01` | RAW (данные без структуры) |
| `0x02` | FREEFORM (GUID-зависимые данные) |
| `0x03` | SECURITY_CORE |
| `0x04` | PEI_CORE |
| `0x05` | DXE_CORE |
| `0x07` | DRIVER |
| `0x09` | APPLICATION |
| `0xF0` | FFS_PAD |

Тело файла состоит из **секций**, каждая тоже с заголовком (3 байта размера + 1 байт типа). Типы секций: `0x10` — PE32-образ (код), `0x15` — UI (строки меню), `0x19` — RAW, `0x02` — GUID-defined (часто сжатие LZMA/Tiano). Чтобы добраться до кода, секцию `0x10` извлекают и, если она сжата (`0x02` с GUID компрессии), распаковывают.

На Python это выглядит так:

```python
guid = data[:16]                       # FFS GUID
csum, ftype, attrs = data[16], data[17], data[18]
size = int.from_bytes(data[20:23], 'little')
body = data[24:size]
print(hex(ftype), size, body[3])       # тип, размер, тип первой секции
```

## Практика: ищем проверки Secure Boot

Secure Boot держится на модулях, работающих с переменными `db`/`dbx` и проверяющих подписи образов. В дереве UEFITool ищите модули с именами, содержащими `SecureBoot`, `Security`, `ImageVerification`, `Variable`. В дизассемблере они вызывают `gRT->GetVariable` (Runtime Services) с GUID глобальной переменной и сравнивают результат с базой ключей.

Признаки компрометации, которые ищут при анализе bootkit:

- модуль с **непустыми** зависимостями, но отсутствующий в эталонной прошивке;
- PE-модуль, чей GUID не совпадает ни с одним известным (UEFITool NE подсвечивает «новые» GUID);
- секция `0x15` (UI) с подозрительными строками, которых нет в оригинале;
- изменения в NVRAM-регионе (сдвинутые `PK`/`KEK`).

Практический приём: сравните анализируемый дамп с **эталонным** от того же вендора/версии. Разница (diff по модулям и GUID) — самый быстрый способ найти внедрённый код, потому что «нормальная» прошивка детерминирована.
