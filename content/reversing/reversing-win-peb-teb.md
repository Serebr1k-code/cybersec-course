## Вопрос, с которого всё начинается

Ты открываешь подозрительный PE в дизассемблере и смотришь таблицу импорта. А там почти пусто: ни `LoadLibrary`, ни `GetProcAddress`, ни одной «говорящей» функции. Но бинарник явно что-то загружает и что-то вызывает. Как программа находит функции, если не импортирует их?

Ответ: она ходит в **PEB** — служебную структуру, которую Windows создаёт каждому процессу и в которой лежит список всех загруженных модулей с их адресами.

## Наш пример

Возьмём дамп небольшого участка памяти процесса — файл `peb.bin`. Это «сырые» байты, снятые из адресного пространства по смещению, где начинается PEB. Наша задача — вручную пройти по списку модулей и найти в нём след импланта.

```bash
$ xxd -l 48 peb.bin
00000000: 0000 0000 0000 0000 0000 0000 0000 0000  ................
00000010: 0000 0000 0000 0000 0000 0000 0000 0000  ................
```

Пока непонятно. Разберёмся, что такое PEB и почему он вообще существует.

## Шаг 1: что такое TEB и PEB

У каждого потока Windows есть **TEB** (Thread Environment Block) — блок с данными конкретного потока. У каждого процесса есть **PEB** (Process Environment Block) — данные всего процесса. Обе структуры создаются ядром и не документированы официально, но стабильны на протяжении десятилетий.

Ключевое: адрес TEB поток всегда знает без всяких API — он лежит в сегментном регистре `GS` (в x64) по смещению `0x30`. А PEB — в TEB по смещению `0x60`. То есть:

```
GS:[0x60]  →  адрес PEB
```

Команда `mov rax, qword ptr gs:[0x60]` — это и есть «получить PEB». Никаких вызовов, никакого импорта. Именно поэтому малварь любит PEB: это вход в мир модулей без единого API-вызова, который EDR мог бы перехватить.

## Шаг 2: где в PEB лежит список модулей

Внутри PEB на смещении `0x18` (x64) лежит указатель на структуру `PEB_LDR_DATA`. В ней по смещению `0x10` начинается **`InLoadOrderModuleList`** — двусвязный список, элементы которого описывают каждый загруженный модуль (DLL и EXE) в порядке загрузки.

Каждый элемент — структура `LDR_DATA_TABLE_ENTRY`. Нам важны её поля (x64):

| Смещение | Поле | Что это |
|---|---|---|
| `0x00` | `InLoadOrderLinks` | связи списка (`Flink`/`Blink`) |
| `0x30` | `DllBase` | базовый адрес модуля в памяти |
| `0x48` | `FullDllName` | полный путь (UNICODE_STRING) |
| `0x58` | `BaseDllName` | короткое имя, например `kernel32.dll` |

Зная эти смещения, можно пройти список и получить базу любого модуля — в том числе `ntdll.dll`, откуда потом достают `LdrLoadDll` или адреса экспортов.

## Шаг 3: разбираем дамп скриптом

Читать 64-битные указатели глазами в `xxd` неудобно. В каталоге лежит скрипт `walk_peb.py`, который повторяет то, что делает имплант: берёт PEB, идёт в `Ldr`, обходит `InLoadOrderModuleList` и печатает имена и базы.

```bash
$ python3 walk_peb.py peb.bin
PEB @ 0x00007ff7a1c00000
Ldr @ 0x00007ffb8a2c4a80
--- InLoadOrderModuleList ---
[0] base=0x00007ff7a1b80000  ntdll.dll
[1] base=0x00007ffb87f00000  KERNEL32.DLL
[2] base=0x00007ffb87e00000  KERNELBASE.dll
[3] base=0x00007ff7a0c10000  nto{ntdll_unh00k_by_hand}
```

В списке появляется модуль с флагом — в реальном образце так мог бы прятаться инжектированный модуль, которого нет в обычном списке загрузки, или поддельное имя.

## Шаг 4: зачем это в реверсе

Теперь ты понимаешь, почему в бинарнике может не быть импорта. Вместо `GetProcAddress` имплант:

1. получает PEB через `gs:[0x60]`;
2. находит `kernel32.dll` (или `ntdll.dll`) в `InLoadOrderModuleList`;
3. читает из PE-заголовка этого модуля таблицу экспортов;
4. по хешу имени функции находит её адрес.

Это называется **API hashing** — имена функций не хранятся строками, а сравниваются хешами. В дизассемблере ты видишь не `call GetProcAddress`, а цикл сравнения 32-битных чисел.

## Шаг 5: TEB и анти-отладка

TEB пригодится и для другой задачи. В `TEB->NtTib.Self` (смещение `0x00`) лежит адрес самого TEB, а в `TEB->ProcessEnvironmentBlock` (`0x60`) — PEB. Анти-отладочные трюки проверяют поля TEB: например, `BeingDebugged` в PEB (смещение `0x02`) равен 1 под отладчиком. Тот же вход — ручное чтение — позволяет эти проверки найти и обойти.

## Шаг 6: как распознать ручной обход загрузчика

В дизассемблере ищи характерные признаки:

- инструкцию `mov ..., gs:[0x60]` — почти всегда это чтение PEB;
- обход списка через `Flink`/`Blink` (цепочка `mov rax, [rax]` в цикле);
- сравнение имён модулей или их хешей;
- разбор PE-заголовка «вручную»: чтение `e_lfanew`, потом секции `.edata`.

Наличие этих шагов говорит: перед тобой код, который сознательно избегает таблицы импорта.

## Что мы теперь знаем

- TEB адресуется через `GS`, PEB — через `TEB+0x60`.
- В PEB есть `Ldr` со списком `InLoadOrderModuleList` всех модулей процесса.
- Каждый элемент — `LDR_DATA_TABLE_ENTRY` с `DllBase` и именем модуля.
- Ручной обход загрузчика даёт адреса функций без импорта и без API.
- Те же структуры используются в анти-отладке (`BeingDebugged`).

## Шаг 7: таблица экспорта — откуда берётся адрес функции

PEB даёт базу модуля. Но чтобы вызвать функцию, нужен её адрес. Он лежит в **таблице экспорта** — секции `.edata` внутри модуля. Указатель на неё в `IMAGE_DATA_DIRECTORY` (запись `Export`) PE-заголовка.

Таблица экспорта состоит из трёх массивов:

| Массив | Что содержит |
|---|---|
| `AddressOfFunctions` | RVA каждой экспортируемой функции |
| `AddressOfNames` | RVA строк-имён |
| `AddressOfNameOrdinals` | индекс имени → индекс функции |

Чтобы найти функцию по имени, ищут строку в `AddressOfNames`, берут её порядковый номер и по нему достают RVA из `AddressOfFunctions`. Прибавив `DllBase`, получают абсолютный адрес.

Именно этот цикл и повторяет имплант вручную: `PEB -> модуль -> Export Directory -> имя -> адрес`.

## Шаг 8: API hashing вручную

Хранить строки имён небезопасно — их найдут. Поэтому сравнивают **хеш имени** с константой. Простейший популярный алгоритм — ROR13 (rotate-right на 13 бит) с накоплением:

```c
uint32_t h = 0;
for (char* p = name; *p; p++) h = (h >> 13) | (h << 19), h += *p;
```

Для каждого экспорта считается такой же хеш и сравнивается с числом в бинаре. Зная алгоритм, ты строишь таблицу «хеш → имя» и переводишь все константы обратно в имена функций:

```bash
$ python3 api_hash.py --ror13 KERNEL32.dll
0x6E2E0C46  LoadLibraryA
0x7C0DFCAA  GetProcAddress
0xEC0E4E8E  CreateFileA
```

В дизассемблере такой код выглядит как цикл по списку имён с `ror` и `cmp` — по нему сразу понятно, что идёт API hashing.

## Шаг 9: типичные ошибки при разборе PEB

- **Путать разрядность.** В x64 PEB — `gs:[0x60]`, в x86 — `fs:[0x30]`. Смещения полей тоже различаются.
- **Считать, что список отсортирован.** `InLoadOrderModuleList` — порядок загрузки, не алфавит. `kernel32` может быть где угодно.
- **Забыть про `LdrpModuleBaseAddressIndex`.** Помимо списка загрузки, есть красно-чёрное дерево по базовым адресам — его тоже используют для поиска.
- **Игнорировать инициализацию.** У самого первого потока PEB ещё не полностью заполнен; анализируй после загрузки.

## Шаг 11: что дальше и решение

Если ты нашёл имплант, который обходит загрузчик, дальше два пути. Первый — восстановить, какие функции он вызывает: перевести хеши в имена (шаг 8) и получить карту вызовов. Второй — проверить, не перехвачены ли эти функции (следующий урок про хуки). Вместе это даёт полную картину: **что имплант вызывает и не подменяет ли кто-то эти вызовы**.

## Шаг 12: как имплант ищет конкретную функцию

Соберём весь путь целиком на примере. Имплант хочет вызвать `VirtualAlloc`, не импортируя её. Он делает так.

Первое — получает PEB: `mov rax, gs:[0x60]`. Второе — идёт в `Ldr`: `mov rax, [rax+0x18]`. Третье — берёт первый элемент списка: `mov rax, [rax+0x10]` (это `Flink` `InLoadOrderModuleList`). Четвёртое — проходит по списку, сравнивая имя модуля с целевым (`kernel32.dll` или `kernelbase.dll`), потому что `VirtualAlloc` экспортируется именно оттуда.

Пятое — найдя модуль, читает его `DllBase` (смещение `0x30` в `LDR_DATA_TABLE_ENTRY`). Шестое — разбирает PE-заголовок: `e_lfanew` по смещению `0x3C` даёт адрес `PE\0\0`, дальше по фиксированному смещению идёт `Export Directory`. Седьмое — обходит таблицу имён, сравнивая хеш каждого имени с нужным.

Каждый из этих шагов — несколько инструкций. В дизассемблере они образуют характерную «лесенку» разыменований и цикл сравнения. Именно по этой лесенке узнают ручной резолвинг.

## Шаг 13: почему смещения такие, и как их проверить

Смещения в PEB и LDR-структурах не документированы официально, но стабильны. Проверить их можно в отладчике символьными типами: `dt ntdll!_PEB` и `dt ntdll!_PEB_LDR_DATA`. Если у тебя нет символов, можно посмотреть исходники ReactOS или заголовки `winternl.h` — они повторяют раскладку.

Важно: между версиями Windows смещения внутри `LDR_DATA_TABLE_ENTRY` менялись (добавлялись поля вроде `BaseNameHashValue`). Поэтому «жёстко зашитое» смещение `0x58` для имени модуля работает на большинстве современных версий, но старый образец может использовать другое. В реверсе это значит: не считай смещение универсальным — проверь, к какой версии Windows привязан образец.

## Шаг 14: ручное связывание и его цена

Весь описанный механизм называют **manual mapping** или ручным связыванием. Его достоинство — обход пользовательских хуков: ты не вызываешь `LoadLibrary`, а значит, не оставляешь следа, который перехватит EDR. Цена — сложность: нужно самому обработать релокации, импорты, защиту памяти.

Импланты поэтому часто совмещают: базовые операции (резолвинг функций) делают вручную через PEB, а загрузку целого модуля — иногда всё же через `LdrLoadDll` (внутренняя функция ntdll), потому что полностью ручное связывание слишком трудоёмко.

## Шаг 15: итоговый чек-лист

- Нашёл `gs:[0x60]` — это чтение PEB.
- Увидел цепочку `+0x18` → `+0x10` → `Flink` — обход списка модулей.
- Есть цикл с `ror` и `cmp` — API hashing.
- Есть разбор `e_lfanew` и `.edata` — ручной резолвинг экспортов.
- Всё это вместе — имплант, который не импортирует API.

Запомни главное: **таблица импорта показывает только то, что программа захотела показать**.

## Куда дальше

PEB даёт тебе список модулей. Но защитные решения не просто прячут функции — они ставят **хуки** на них. В следующем уроке разберём, как устроены IAT-, inline- и VEH-хуки и как их снимать при отладке. Пока главное: **импорт в бинарнике — не истина; настоящие вызовы живут в PEB и таблицах экспорта**.

## Где пригодится

- **Malware analysis:** разбор имплантов, которые не импортируют API.
- **EDR evasion research:** понимание, как обходят пользовательские хуки.
- **CTF:** задачи, где нужно найти скрытый модуль или функцию по структурам Windows.
