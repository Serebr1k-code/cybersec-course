## Вопрос, с которого всё начинается

Ты открываешь iOS-приложение в дизассемблере и почти не видишь привычных `call` по адресу. Вместо этого — сплошные вызовы одной функции `objc_msgSend`, а рядом непонятные строки вида `viewDidLoad`. Что это и как читать такой код?

## Наш пример

У нас есть Mach-O бинарник `app.bin` (arm64). Разберём его метаданные Objective-C и восстановим классы, их методы и строки-селекторы.

## Шаг 1: Objective-C — динамический язык

В C++ вызов `obj->method()` компилируется в прямой `call` по известному адресу. В **Objective-C** метод вызывается **сообщением**: `[obj doSomething]`. Компилятор превращает это в вызов `objc_msgSend(obj, @selector(doSomething), args...)`.

Смысл: какой именно код выполнится, решается **во время выполнения**, по имени метода (селектору). Это даёт гибкость (и swizzling), но усложняет реверс: в дизассемблере ты видишь не имена методов, а вызовы `objc_msgSend`.

## Шаг 2: селекторы и строки

**Селектор** — это имя метода, интернированное в рантайме. В бинарнике селекторы хранятся как C-строки в секции `__objc_methname`:

```bash
$ strings -n 5 app.bin | grep -E '^(viewDidLoad|login|encrypt|setPassword)'
viewDidLoad
loginWithToken:
setPassword:
```

Даже без символов эти строки говорят, что делает приложение. Часто здесь же — имена классов в `__objc_classname`.

## Шаг 3: структура класса

Класс Objective-C в бинарнике — это структура `class_t`, на которую ссылается `__objc_classlist`. Внутри:

- `isa` — указатель на метакласс;
- `superclass` — родитель;
- `name` — имя класса;
- `methods` — список методов (селектор → реализация);
- `ivars` — поля экземпляра.

Метод — это пара «селектор + указатель на функцию». Значит, восстановив список, ты получаешь **карту: имя метода → адрес кода**.

## Шаг 4: разбор метаданных скриптом

Скрипт `objc_meta.py` идёт по `__objc_classlist` и печатает классы с методами:

```bash
$ python3 objc_meta.py app.bin
class LoginViewController : UIViewController
  - viewDidLoad              @ 0x100004a20
  - loginWithToken:          @ 0x100004c10
class CryptoManager
  - encryptData:             @ 0x100005120
  - secret_nto{0bjc_m3th0d_l1st_r3c0v3ry}
```

Теперь вместо голых адресов видно назначение кода: логин и шифрование — ключевые места приложения.

## Шаг 5: swizzling — перехват методов

**Method swizzling** — подмена реализации метода во время выполнения: рантайм меняет пары «селектор → реализация» местами. Так делают и легитимные библиотеки, и малварь (например, подменяют `setPassword:` или методы проверки jailbreak).

В реверсе swizzling виден как вызовы:

- `class_getInstanceMethod`, `method_exchangeImplementations`, `method_setImplementation`.

Если приложение делает это в `+load` или в раннем `main` — проверь, что именно подменяется: это классический способ обойти проверки или украсть данные.

## Шаг 6: как это ускоряет реверс

Objective-C даёт неожиданный бонус: **имена методов сохраняются в бинарнике**, даже когда C-функции обфусцированы. Поэтому анализ начинают с метаданных:

1. выгрузить классы и селекторы (`class-dump`, `objc_meta.py`);
2. найти интересные методы (крипто, сеть, проверки);
3. перейти по адресу реализации в дизассемблер;
4. уже там читать логику.

Это превращает «тысячу безымянных функций» в понятную объектную модель.

## Что мы теперь знаем

- Objective-C вызывает методы через `objc_msgSend` по селектору.
- Селекторы и имена классов хранятся строками в `__objc_methname`/`__objc_classname`.
- `class_t` в `__objc_classlist` связывает имя, методы и реализации.
- Swizzling подменяет реализации через рантайм-API.
- Анализ начинают с метаданных — имена методов часто не обфусцированы.

## Шаг 7: `objc_msgSend` в дизассемблере

Когда видишь вызов, где первый аргумент — объект, второй — селектор, а перед ним загружены ещё аргументы, это `objc_msgSend`. В ARM64 это выглядит так:

```asm
ldr x0, [x19]            ; x0 = объект
adrp x1, sel_loginWithToken@PAGE
add  x1, x1, sel_loginWithToken@PAGEOFF
bl   _objc_msgSend       ; [obj loginWithToken:]
```

`x0` — получатель, `x1` — селектор, `x2..` — аргументы. Разобрав селектор по адресу, ты получаешь имя метода. Именно поэтому селекторы — золото при реверсе: они превращают голый ассемблер в читаемую логику.

## Шаг 8: как читать структуру класса

`class_t` в памяти (упрощённо):

| Смещение | Поле |
|---|---|
| `0x00` | `isa` (метакласс) |
| `0x08` | `superclass` |
| `0x10` | `cache` (кэш методов) |
| `0x18` | `vtable` |
| `0x20` | `data` (bits: флаги, список методов) |

Флаг `RW_REALIZED` в `data` говорит, что список методов «развёрнут». До этого методы лежат в «относительной» форме. Для реверса важна уже развёрнутая `method_list_t` — там пары «селектор → IMP».

## Шаг 9: Swift и Objective-C вместе

Современные приложения смешивают Swift и Objective-C. Swift-классы, унаследованные от `NSObject`, экспортируют методы с ObjC-селекторами (с префиксом `@objc`), а чистый Swift — нет. В бинарнике это означает: часть методов видна через метаданные ObjC, часть — только через Swift-метаданные (`swift5_*`).

Если видишь секции `__swift5_types`, `__swift5_methname` — приложение на Swift, и часть логики надо искать через `swift-demangle`, а не через ObjC-селекторы.

## Шаг 10: swizzling в защитах

Частое применение swizzling — **обход проверок**:

```objc
Method orig = class_getInstanceMethod(cls, @selector(isJailbroken));
Method fake = class_getInstanceMethod(cls, @selector(alwaysFalse));
method_exchangeImplementations(orig, fake);
```

После этого `isJailbroken` возвращает «нет», хотя реальная проверка есть. В реверсе: ищи `method_exchangeImplementations`/`method_setImplementation` в `+load` — и смотри, какие селекторы подменяются. Это прямо укажет на защитные механизмы приложения.

## Шаг 11: инструменты для ObjC

| Инструмент | Задача |
|---|---|
| `class-dump` | дамп классов и методов |
| `otool -ov` | метаданные ObjC |
| `nm` | символы |
| `objc_meta.py` | разбор `__objc_classlist` |
| Hopper/Ghidra | декомпиляция |

## Шаг 12: итоговый порядок разбора

Начни с `otool -ov` или `class-dump` — получишь классы и методы. Найди интересные селекторы (крипто, сеть, проверки). Перейди по IMP в дизассемблер. Проверь `+load` на swizzling. Если приложение на Swift — используй `swift-demangle` для `swift5_*`-секций. Так объектная модель приложения раскрывается быстро.

## Шаг 13: почему это стоит знать

Objective-C-бинарники — большинство приложений macOS и iOS. Умение читать метаданные даёт огромное преимущество: ты видишь имена там, где в C-бинарнике были бы голые адреса. Это один из самых «честных» языков для реверса — при условии, что понимаешь `objc_msgSend`.

## Шаг 14: динамика и Frida

Динамически Objective-C особенно удобен: Frida умеет перечислять классы и хукать методы по имени.

```
frida -U -f com.app -l hook.js
> ObjC.classes.LoginViewController.$methods
```

Можно перехватить `-[CryptoManager encryptData:]` и посмотреть аргументы — без реверса ассемблера. Это дополняет статику: статика даёт карту, динамика — значения.

## Шаг 15: итоговый чек-лист

- `objc_msgSend(obj, sel, ...)` — любой ObjC-вызов.
- Селекторы и имена классов — строки в `__objc_methname`/`__objc_classname`.
- `class_t` в `__objc_classlist` даёт методы и реализации.
- `method_exchangeImplementations` = swizzling (часто обход проверок).
- Swift-часть ищи в `swift5_*`, деманипулируй.

Главное: **ObjC-бинарник начинают читать с метаданных — имена там сохраняются**.

## Шаг 16: селекторы как ключ к динамике

Селекторы уникальны и интернированы — в рантайме каждому соответствует один указатель. Это значит, что по селектору можно найти **все места**, где вызывается метод: сравни указатель селектора в разных функциях. В реверсе это даёт трассировку: например, найди селектор `setPassword:` и посмотри, какие функции его передают в `objc_msgSend`.

```bash
$ python3 objc_meta.py app.bin --xref setPassword:
sel 'setPassword:' used in:
  -[LoginViewController login:]     @ 0x100004c10
  -[KeychainManager store:]         @ 0x100005560
```

Так восстанавливается поток данных: от ввода пароля до записи в keychain.

## Шаг 17: категории и ассоциированные объекты

Objective-C позволяет добавлять методы к существующим классам через **категории**, а данные — через **ассоциированные объекты** (`objc_setAssociatedObject`). В бинарнике категории выглядят как отдельные списки методов с тем же именем класса, а ассоциированные объекты — как вызовы соответствующих функций.

Практическая ценность: логика класса может быть разбросана по нескольким категориям, и декомпилятор покажет их отдельно. Ищи в метаданных `__objc_catlist` — там перечислены категории.

## Шаг 18: блоки и их метаданные

Блоки (`^{...}`) в Objective-C — это объекты с указателем на функцию и захваченным контекстом. В дизассемблере блок — это структура: `isa`, флаги, указатель на invoke-функцию, затем захваченные переменные. Вызов блока идёт через `invoke`.

Полезно: если видишь функцию, вызываемую через указатель, и рядом структуру с флагом `BLOCK_HAS_SIGNATURE`, это блок. Аргументы блока передаются как у обычной функции, но контекст — из структуры.

## Шаг 19: как отличить свой код от библиотек

В бинарнике много методов из системных фреймворков. Чтобы не утонуть, фильтруй по адресу: методы с адресами в диапазоне образа (`__TEXT`) — твой код, остальные — из системных библиотек (dyld shared cache). В `class-dump` используй флаг, отсекающий системные классы.

```bash
$ class-dump --arch arm64 app.bin -H -o headers/ --filter=Login
```

Это оставит только классы приложения.

## Шаг 20: таблица секций Objective-C

| Секция | Что содержит |
|---|---|
| `__objc_classlist` | указатели на классы |
| `__objc_catlist` | категории |
| `__objc_methname` | имена методов (селекторы) |
| `__objc_classname` | имена классов |
| `__objc_methtype` | сигнатуры методов |
| `__objc_protolist` | протоколы |

## Шаг 21: итоговый алгоритм

Начни с `class-dump`/`otool -ov` и отфильтруй системные классы. Найди интересные селекторы. По xref селектора поднимись к вызывающим функциям. Перейди по IMP в дизассемблер. Проверь `+load` и категории на swizzling. Для Swift — используй `swift5_*` и `swift-demangle`. Дополни динамикой через Frida, хукая методы по имени. Так объектная модель приложения раскрывается полностью, а имена методов дают то, чего нет в C-бинарниках. Главное: **ObjC-бинарник начинают читать с метаданных**.

## Куда дальше

Runtime даёт имена — но на современном iOS код ещё и защищён **Pointer Authentication (PAC)**, из-за которого указатели нельзя просто подменить. О них в следующем уроке. Пока главное: **Objective-C-бинарник начинают читать с метаданных, а не с ассемблера**.
