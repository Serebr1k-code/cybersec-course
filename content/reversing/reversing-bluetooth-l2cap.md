## Вопрос, с которого всё начинается

У тебя есть BLE-устройство (умный замок, фитнес-браслет) и захват его обмена `ble_capture.pcap`. Официальной документации нет. Как понять, какие данные устройство передаёт и как ими управлять?

## Наш пример

Смотрим на файл:

```
$ file ble_capture.pcap
ble_capture.pcap: pcap capture file, microsecond ts (little-endian)
```

Это стандартный захват. Внутри — пакеты BLE. Прежде чем читать их, разберёмся со слоями Bluetooth Low Energy.

## Шаг 1: слои BLE

BLE-стек имеет несколько слоёв:

- **PHY** — радио (физика, частоты, модуляция).
- **Link Layer** — каналы, реклама (advertising), соединение.
- **L2CAP** — логические каналы, мультиплексирование.
- **ATT** — Attribute Protocol: обмен атрибутами (чтение/запись).
- **GATT** — Generic Attribute Profile: структура сервисов и характеристик поверх ATT.
- **GAP** — реклама и установление соединения.

Для реверса важнее всего **GATT**: именно там описано, «что можно читать/писать».

## Шаг 2: GATT — сервисы и характеристики

GATT описывает устройство как набор **сервисов**, каждый из которых содержит **характеристики** (characteristics). Характеристика — это значение (данные) с **UUID** (уникальный идентификатор). Короткие UUID (16 бит) — стандартные (`0x180f` — батарея), длинные (128 бит) — вендорские.

Например, вендорский сервис:

```
UUID: 0000fff0-0000-1000-8000-00805f9b34fb
  char 0000fff1-...  (write)   — команда
  char 0000fff2-...  (notify)  — ответ
```

Зная это, ты понимаешь, куда писать команды и откуда читать ответы.

## Шаг 3: захват трафика

Чтобы увидеть обмен, нужен захват. Варианты:

- **HCI-логи** с телефона (Android: `btsnoop`), которые содержат полные пакеты;
- **сниффер** на чипе (nRF Sniffer, Ubertooth, Ellisys);
- **отладка** собственного клиента.

Ключевая сложность: BLE шифрует соединение, и без ключей сниффер видит только зашифрованные данные. HCI-лог с устройства, которое уже подключено, даёт расшифрованный трафик.

## Шаг 4: разбор по слоям

В захвате пакеты читаются снизу вверх: L2CAP → ATT → GATT. ATT-опкоды:

```
0x0a  READ_REQUEST
0x0b  READ_RESPONSE
0x12  WRITE_REQUEST
0x1b  NOTIFICATION
```

`WRITE_REQUEST` на вендорскую характеристику — команда устройству; `NOTIFICATION` — ответ. Сопоставив UUID и данные, ты реконструируешь протокол.

## Шаг 5: восстановление протокола

Данные в характеристиках часто бинарные. Подход: собрать пары «команда → ответ» из трейса, заметить закономерности (первый байт — опкод, далее параметры, CRC в конце). Иногда первое поле — длина. Так из сырых байт восстанавливается структура сообщений.

Если данных мало, управляют устройством (нажимают кнопки, меняют состояние) и смотрят, какие характеристики меняются, — это даёт связь «действие → байты».

## Шаг 6: артефакт

Извлечём из трейса UUID и артефакт:

```
$ strings -n 5 ble_capture.pcap | head
ATT_OP_READ_REQ
GATT_PRIMARY_SERVICE
0000fff0-0000-1000-8000-00805f9b34fb
nto{ble_l2c4p_g4tt_r3v}
```

Артефакт — цель практики; в реальном анализе так находят зашитые ключи и идентификаторы.

## Что мы теперь знаем

- BLE-стек: PHY → Link Layer → L2CAP → ATT → GATT/GAP.
- GATT: сервисы и характеристики с UUID; характеристики читают/пишут/нотифицируют.
- Захват: HCI-логи (расшифрованы), сниффер (может быть зашифрован).
- ATT-опкоды: 0x0a read, 0x12 write, 0x1b notification.
- Протокол восстанавливают по парам «команда → ответ» в трейсе.
