## Вопрос, с которого всё начинается

У тебя есть BLE-устройство (умный замок, фитнес-браслет) и захват его обмена `ble_capture.pcap`. Официальной документации нет. Как понять, какие данные устройство передаёт и как ими управлять?

## Наш пример

Смотрим на файл:

```
$ file ble_capture.pcap
ble_capture.pcap: pcap capture file, microsecond ts (little-endian)
```

Это стандартный захват. Внутри — пакеты BLE. Прежде чем читать их, разберёмся со слоями Bluetooth Low Energy.

## Шаг 1: слои BLE

BLE-стек имеет несколько слоёв:

- **PHY** — радио (физика, частоты, модуляция).
- **Link Layer** — каналы, реклама (advertising), соединение.
- **L2CAP** — логические каналы, мультиплексирование.
- **ATT** — Attribute Protocol: обмен атрибутами (чтение/запись).
- **GATT** — Generic Attribute Profile: структура сервисов и характеристик поверх ATT.
- **GAP** — реклама и установление соединения.

Для реверса важнее всего **GATT**: именно там описано, «что можно читать/писать».

## Шаг 2: GATT — сервисы и характеристики

GATT описывает устройство как набор **сервисов**, каждый из которых содержит **характеристики** (characteristics). Характеристика — это значение (данные) с **UUID** (уникальный идентификатор). Короткие UUID (16 бит) — стандартные (`0x180f` — батарея), длинные (128 бит) — вендорские.

Например, вендорский сервис:

```
UUID: 0000fff0-0000-1000-8000-00805f9b34fb
  char 0000fff1-...  (write)   — команда
  char 0000fff2-...  (notify)  — ответ
```

Зная это, ты понимаешь, куда писать команды и откуда читать ответы.

## Шаг 3: захват трафика

Чтобы увидеть обмен, нужен захват. Варианты:

- **HCI-логи** с телефона (Android: `btsnoop`), которые содержат полные пакеты;
- **сниффер** на чипе (nRF Sniffer, Ubertooth, Ellisys);
- **отладка** собственного клиента.

Ключевая сложность: BLE шифрует соединение, и без ключей сниффер видит только зашифрованные данные. HCI-лог с устройства, которое уже подключено, даёт расшифрованный трафик.

## Шаг 4: разбор по слоям

В захвате пакеты читаются снизу вверх: L2CAP → ATT → GATT. ATT-опкоды:

```
0x0a  READ_REQUEST
0x0b  READ_RESPONSE
0x12  WRITE_REQUEST
0x1b  NOTIFICATION
```

`WRITE_REQUEST` на вендорскую характеристику — команда устройству; `NOTIFICATION` — ответ. Сопоставив UUID и данные, ты реконструируешь протокол.

## Шаг 5: восстановление протокола

Данные в характеристиках часто бинарные. Подход: собрать пары «команда → ответ» из трейса, заметить закономерности (первый байт — опкод, далее параметры, CRC в конце). Иногда первое поле — длина. Так из сырых байт восстанавливается структура сообщений.

Если данных мало, управляют устройством (нажимают кнопки, меняют состояние) и смотрят, какие характеристики меняются, — это даёт связь «действие → байты».

## Шаг 6: артефакт

Извлечём из трейса UUID и артефакт:

```
$ strings -n 5 ble_capture.pcap | head
ATT_OP_READ_REQ
GATT_PRIMARY_SERVICE
0000fff0-0000-1000-8000-00805f9b34fb
nto{ble_l2c4p_g4tt_r3v}
```

Артефакт — цель практики; в реальном анализе так находят зашитые ключи и идентификаторы.

## Шаг 7: реклама, сканирование и подключение (GAP)

Прежде чем обмениваться данными, устройства проходят стадии GAP. **Advertising**: устройство периодически шлёт пакеты с именем, UUID сервисов и данными (это то, что видит сканер). **Scanning**: центральное устройство слушает рекламу. **Connection**: центральное подключается к периферийному и переходит в режим соединения.

Из рекламных пакетов уже можно много узнать: имя устройства, поддерживаемые сервисы (по UUID), иногда — серийник. Инструменты (`hcitool lescan`, `bluetoothctl`) показывают это без подключения. Это первый шаг разведки.

## Шаг 8: разбор характеристик и дескрипторов

После подключения нужно **обнаружить сервисы** (Service Discovery). Клиент читает атрибуты, начиная с `0x0001` (Generic Access) и `0x0003` (Generic Attribute), затем идут вендорские сервисы. У каждой характеристики есть **дескриптор** `0x2902` (Client Characteristic Configuration Descriptor, CCCD) — он включает/выключает нотификации.

Практический приём: включить нотификации на всех характеристиках (записать `0x0100` в CCCD) и понаблюдать, какие данные приходят при работе устройства. Так выявляют поток телеметрии и команды.

## Шаг 9: шифрование и сопряжение

BLE-соединение может быть зашифровано (LE Secure Connections, AES-CCM). Ключи вырабатываются при сопряжении (pairing) — иногда с уязвимостями: «Just Works» не защищает от MITM, а старый режим с фиксированным ключом (`000000`) тривиально читается. Признаки слабого сопряжения видны в свойствах характеристик (флаги доступа).

Для реверса это важно: если соединение зашифровано, сниффер не поможет, но HCI-лог с уже сопряжённого хоста даёт расшифрованные данные. Либо можно атаковать сопряжение и получить ключ.

## Шаг 10: закрепление и вывод

Наш `ble_capture.pcap` показал: UUID сервисов, ATT-операции, строку `GATT_PRIMARY_SERVICE`. Мы разобрали слои BLE и то, как восстанавливать протокол по трейсу.

Главный вывод: BLE-реверс — это разведка (реклама), обнаружение сервисов, чтение/запись характеристик и наблюдение нотификаций. Захват трафика + сопоставление команд и ответов превращает «закрытый» гаджет в понятный протокол.

## Разбор глубже: BLE-атаки и их связь с реверсом

Типовые BLE-атаки: eavesdropping (прослушивание), MITM при слабом сопряжении, реплей, подмена устройства (spoofing), fuzzing характеристик. Понимание атак направляет реверс: если сопряжение «Just Works», ищи MITM; если есть команда записи, проверяй, не приводит ли она к опасному состоянию.

Реверс даёт «язык» атаки: какие характеристики писать, какие значения вызывать. Без него атака — слепой перебор.

## Разбор глубже: инструменты BLE-реверса

Практический набор: `bluetoothctl` (Linux, обнаружение/подключение), `gatttool`/`btgatt-client` (чтение/запись характеристик), `nRF Connect` (мобильное приложение для ручного исследования), Wireshark с BTSnoop (разбор захватов), nRF Sniffer/Ubertooth (сниффинг). Для шифрованного трафика — HCI-логи с телефона.

С этими инструментами цикл такой: обнаружить устройство → подключиться → перечислить сервисы/характеристики → включить нотификации → управлять устройством и наблюдать → восстановить протокол.

## Разбор глубже: связь с IoT-безопасностью

BLE — основной канал для умных замков, медицинских устройств, трекеров. Реверс их протокола — путь к поиску уязвимостей: слабая аутентификация, отсутствие проверки прав, возможность перепрошивки по воздуху. Часто команда «открыть замок» — просто запись нескольких байт в характеристику, без крипто-защиты.

Поэтому BLE-реверс — востребованный навык в IoT-пентесте: он превращает «чёрный ящик» в понятный интерфейс, который можно анализировать и защищать.

## Разбор глубже: от реверса к эксплуатации

Восстановленный протокол BLE открывает конкретные возможности: записать команду в характеристику, прочитать состояние, включить режим. Если аутентификация слабая, эти действия доступны любому в радиусе. Так находят уязвимости: незащищённое управление, отсутствие проверки прав, перепрошивка.

Эксплуатация — это применение восстановленного протокола. Поэтому реверс и пентест BLE неразделимы: сначала понять, потом проверить.

## Разбор глубже: типичные ошибки новичков

Новички часто: (1) не включают нотификации и не видят ответы устройства; (2) путают handle и UUID (в ATT используются handle, UUID — для идентификации); (3) игнорируют шифрование и пытаются читать зашифрованный трафик; (4) не документируют соответствие «действие → байты».

Правильный подход: систематически перечислить сервисы, включить нотификации, менять по одному параметру и записывать результат. Так строится карта протокола.

## Разбор глубже: BLE как часть экосистемы

Устройство редко существует в вакууме: BLE-гаджет связан с мобильным приложением и облаком. Реверс приложения (Android/iOS) дополняет BLE-анализ: там видны команды, ключи, логика. Комбинируя реверс приложения и трафика, ты получаешь полную картину.

Это пример того, как разные навыки (мобильный реверс, протоколы, трейсинг) работают вместе.

## Разбор глубже: классический Bluetooth против BLE

Классический Bluetooth (BR/EDR) и BLE — разные стеки, хотя делят радио. BR/EDR использует L2CAP, RFCOMM, SDP; BLE — ATT/GATT. У них разные профили и разные атаки. Реверс BLE не переносится напрямую на классику.

При анализе сначала определи, какой стек используется: по рекламе и по типу соединения. Инструменты тоже разные (`bluetoothctl` для обоих, но профили отличаются).

## Разбор глубже: как документировать протокол

Результат BLE-реверса оформляют как карту: сервис → характеристика → направление (read/write/notify) → формат данных → смысл. Это «даташит» на устройство, которого нет у вендора.

С такой картой можно: автоматизировать управление, писать тесты, искать уязвимости. Она же — основа для отчёта и для защиты (какие данные не должны быть доступны без аутентификации).

## Разбор глубже: закрепление навыка

Навык BLE-реверса ставится практикой: возьми свой гаджет (фитнес-трекер, умную лампу), просканируй, перечисли сервисы, включи нотификации, поуправляй. Записывай, что меняется.

Так ты за несколько сессий пройдёшь весь цикл и научишься читать протоколы «с нуля», без документации. Это навык, применимый к любому IoT-устройству.

## Итог по BLE

BLE-реверс — это разведка (реклама), обнаружение сервисов, чтение/запись характеристик и наблюдение нотификаций. Ключ к успеху — захват трафика и систематическое сопоставление «команда → ответ». Восстановленный протокол открывает управление устройством и поиск уязвимостей. Навык универсален для любых IoT-гаджетов.

## Практическая заметка

Сохраняй захваты с самого начала исследования: даже «шумные» пакеты рекламы содержат полезные UUID и метаданные. Позже, когда найдёшь команду, ты сможешь сопоставить её с уже записанным трафиком. Логирование каждой сессии — привычка, которая экономит часы при разборе сложного протокола.

## Инструмент: tshark — Wireshark в консоли

`tshark` — это Wireshark без графики: он читает дамп (`-r файл.pcap`) и печатает ровно то, что ты попросишь. Главный инструмент, когда графической оболочки нет или разбор надо автоматизировать.

Ключи, которые пригодятся:
* `-r <файл.pcap>` — читать дамп (без него tshark слушает живой интерфейс);
* `-nn` — не резолвить имена/порты: видно «как есть» и быстрее;
* `-Y '<фильтр>'` — display-фильтр, оставить только нужные пакеты (`http.request`, `dns`, `eapol`, `ospf`);
* `-T fields -e <поле>` — вместо сводки печатать значения полей (`-e ip.src -e tcp.dstport -e http.host`);
* `-q -z follow,tcp,ascii,N` — собрать TCP-поток номер N и показать его как текст.

### Рабочий пример (как в лаборатории)

```
$ tshark -r ble_capture.pcap
    1 0.000000  aa:bb:cc:dd:ee:ff -> ff:ff:ff:ff:ff:ff  ATT  27 Read Request
    2 0.010000  ff:ff:ff:ff:ff:ff -> aa:bb:cc:dd:ee:ff  ATT  31 Read Response
```

Подсказка из лаборатории: `tshark -r <файл> — анализ захвата`.

## Что мы теперь знаем

- BLE-стек: PHY → Link Layer → L2CAP → ATT → GATT/GAP.
- GATT: сервисы и характеристики с UUID; характеристики читают/пишут/нотифицируют.
- Захват: HCI-логи (расшифрованы), сниффер (может быть зашифрован).
- ATT-опкоды: 0x0a read, 0x12 write, 0x1b notification.
- Протокол восстанавливают по парам «команда → ответ» в трейсе.
