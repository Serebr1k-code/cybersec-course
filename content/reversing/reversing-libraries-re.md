## Вопрос, с которого всё начинается

Мы умеем разбирать один исполняемый файл. Но почти любая программа — это не один файл: рядом лежат **разделяемые библиотеки** (`.so` в Linux, `.dll` в Windows, `.dylib` в macOS). Иногда на CTF дают только библиотеку без главного файла и просят найти в ней функцию. С чего начать и как понять, что она делает, если у неё даже нет `main`?

## Наш пример

Возьмём пару файлов: программу `useauth` и библиотеку `libauth.so`, которую она использует. Программа проверяет пароль, вызвав функцию из библиотеки. Сначала — что это вообще за файлы:

```bash
$ file useauth libauth.so
useauth:    ELF 64-bit LSB pie executable, x86-64, dynamically linked, ...
libauth.so: ELF 64-bit LSB shared object, x86-64, dynamically linked, ...
```

Видишь разницу в выводе `file`: у программы — `pie executable`, у библиотеки — **`shared object`**. Это и есть определение разделяемой библиотеки: ELF-файл, который не запускается сам, а загружается в чужой процесс.

## Шаг 1: что библиотека «отдаёт наружу» — экспорт

Библиотека бесполезна, если из неё нельзя вызвать функции. Те, что она разрешает вызывать, — её **экспорт** (exported symbols). Список экспорта Linux-библиотеки показывает `nm -D` (D — dynamic):

```bash
$ nm -D libauth.so
                 w _ITM_deregisterTMCloneTable
                 w __cxa_finalize@GLIBC_2.2.5
00000000000010e9 T check_password
```

Ключевая строка — последняя. Буква `T` означает «определён в `.text`, глобальный, доступен извне», а имя — `check_password`. Дальше адрес `0x10e9` — где функция лежит. Всё остальное помечено `w` (weak, служебное от компилятора). То есть библиотека экспортирует ровно одну функцию — с неё и начнём.

## Шаг 2: как программа её вызывает — импорт

Теперь посмотрим на программу. Она **импортирует** `check_password` — просит загрузчик подставить адрес. В ELF это видно в «динамических символах»:

```bash
$ readelf --dyn-syms useauth | grep -E 'check_password|puts'
     3: 0000000000000000     0 FUNC  GLOBAL DEFAULT  UND puts@GLIBC_2.2.5
     5: 0000000000000000     0 FUNC  GLOBAL DEFAULT  UND check_password
```

`UND` (undefined) — «адрес неизвестен, найдётся при загрузке». У `puts` в имени есть версия `@GLIBC_2.2.5`, а у `check_password` — нет: он найдётся в нашей библиотеке, а не в libc. Как загрузчик понимает, где искать? По записи `NEEDED` в динамической секции:

```bash
$ readelf -d useauth | grep -E 'NEEDED|RUNPATH'
 (NEEDED)  Shared library: [libauth.so]
 (NEEDED)  Shared library: [libc.so.6]
 (RUNPATH) Library runpath: [.]
```

`NEEDED: libauth.so` — «загрузи эту библиотеку». `RUNPATH: .` — «искать её в текущей папке». Команда `ldd` показывает итог поиска:

```bash
$ ldd useauth
	libauth.so => ./libauth.so (0x00007faaf1509000)
	libc.so.6 => /usr/lib/libc.so.6 (0x00007faaf12e3000)
```

Вот полная цепочка: программа → `NEEDED` → библиотека → экспорт → подстановка адреса. Разберём, где программа зовёт функцию.

## Шаг 3: место вызова — PLT

В дизассемблере `main` вызов выглядит так:

```text
    116c:	call   1040 <check_password@plt>
    1171:	test   %eax,%eax
    1173:	je     1186 <main+0x3d>
```

`call ... <check_password@plt>` — вызов через **PLT** (Procedure Linkage Table), небольшую «прокладку». Сама прокладка:

```text
0000000000001040 <check_password@plt>:
    1040:	jmp    *0x2fc2(%rip)        # 4008 <check_password>
```

Первый вызов идёт через загрузчик, который записывает настоящий адрес `check_password` в GOT-таблицу, а последующие вызовы прыгают туда напрямую. Нам как реверсерам важно одно: **`check_password@plt` — это и есть вход в библиотечную функцию**, и `test %eax,%eax` сразу после показывает, что результат проверяется (ноль — отказ).

## Шаг 4: разбираем саму функцию

Открываем `libauth.so` в дизассемблере/Ghidra, находим `check_password`. Если быстро — ищем строки:

```bash
$ strings libauth.so | grep -E 's3cr3t'
s3cr3t_lib
```

Строка `s3cr3t_lib` — почти наверняка пароль. В `libauth.so` есть только одна содержательная функция, и она посимвольно сравнивает вход с этой строкой. На CTF этого достаточно: пароль найден. Так реверс библиотеки сводится к «найти экспорт → найти строки → прочитать сравнение».

## Шаг 5: как это грузят вручную — dlopen

Иногда библиотека не указана в `NEEDED`, а подгружается в рантайме — через `dlopen`/`dlsym` (Linux) или `LoadLibrary`/`GetProcAddress` (Windows). Это любимый приём плагинов и малвари: имя функции прячется в строке, и по таблице импортов её не видно. Если видишь в строках путь к `.so` и вызов `dlopen` — ищи рядом `dlsym` с именем искомой функции; именно её и надо реверсить.

## Шаг 6: soname и версии библиотек

У библиотеки есть «официальное» имя — **soname** (shared object name), под которым её записывают в зависимости. Проверим:

```bash
$ readelf -d libauth.so | grep SONAME
 0x000000000000000e (SONAME)  Library soname: [libauth.so]
```

Программа просит именно `libauth.so`, а не полный путь — путь ищет загрузчик по стандартным каталогам (`/lib`, `/usr/lib`) и `RUNPATH`/`LD_LIBRARY_PATH`. Отсюда и классическая атака «подмена библиотеки»: положи свой файл с тем же soname туда, откуда загрузчик возьмёт его первым. Для реверса soname полезен тем, что по нему понятно, какую библиотеку искать в системе: `find / -name 'lib*.so*'` по нужному имени.

## Шаг 7: инструменты для разбора библиотек

Что пригодится, когда библиотека не одна, а их десятки:

- **`nm -D`** — быстрый список экспорта; **`nm -C`** — ещё и демагглинг C++ имён.
- **`readelf -d`** — зависимости (`NEEDED`), soname, rpath.
- **`objdump -T`** — динамические символы с адресами.
- **`ldd`** — какая библиотека реально подхватится (учитывает rpath).
- **Ghidra / IDA** — открыть `.so` как «shared library» и разбирать функции.

Ключевой приём на CTF: если дали только `.so`, начни с `nm -D` (что экспортируется) и `strings` (что за строки). Часто этого достаточно, чтобы найти проверку пароля и не открывать дизассемблер.

## Шаг 8: на что смотреть дальше

Когда экспорт найден, но логика неочевидна, копай в таком порядке:

1. **Строки рядом с функцией** — `strings -t x libauth.so` даёт смещения, сопоставимые с адресами.
2. **Вызовы внутри функции** — импорт (`memcmp`, `strcmp`) подсказывает, что функция сравнивает.
3. **Инициализаторы** — функции с `__attribute__((constructor))` выполняются при загрузке; малварь любит прятать в них код.
4. **Обфускация** — если имён и строк нет, а код «прыгает», вероятно применён обфускатор; тогда нужен динамический анализ (Frida, ltrace).

Не пытайся сразу декомпилировать всё — начни с экспорта и строк, и в большинстве CTF-задач этого хватит.

## Что мы теперь знаем

- Разделяемая библиотека — это `shared object`, который грузится в чужой процесс, а не запускается сам.
- **Экспорт** (`nm -D`, буква `T`) — функции, доступные снаружи; с них начинаем разбор.
- **Импорт** (`readelf --dyn-syms`, `UND`) и запись `NEEDED` показывают, кто кого вызывает и откуда грузится.
- Вызов идёт через **PLT**, а `dlopen`/`dlsym` позволяют грузить функции скрытно в рантайме.

## Куда дальше

Мы разобрали, как программа и библиотека связаны во время загрузки. Но есть и другой способ собрать программу — вшить всё в один файл, **статически**. Чем статическая компоновка отличается от динамической и почему статические бинарники весят десятки мегабайт — в следующем уроке. А пока запомни: `nm -D` для экспорта, `readelf -d` для зависимостей, `strings` для быстрой зацепки.

## Где пригодится

- **CTF Reversing:** задания «дана только библиотека» решаются через `nm -D`, `strings` и разбор экспортируемой функции.
- **Malware analysis:** плагины и модули малвари почти всегда подгружаются через `dlopen`/`LoadLibrary` — их видно по строкам и импорту.
- **Vuln research:** подмена библиотеки (`LD_PRELOAD`, DLL hijack) напрямую опирается на механизм `NEEDED`/поиска.
- **Собес:** «что такое .so», «чем экспорт отличается от импорта» — базовые вопросы по системному программированию.
