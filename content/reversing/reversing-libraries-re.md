Разделяемые библиотеки — это код, многократно используемый разными программами без дублирования в
каждом бинарнике. В Linux это `.so`, в Windows — `.dll`, в macOS — `.dylib` (и `.framework`). Они
загружаются в адресное пространство процесса, экспортируют функции и данные, а иногда и сами
загружают другие модули (плагины). Для реверс-инженера библиотека — это отдельный артефакт со своими
точками входа (экспорты, `DllMain`, конструкторы), который надо анализировать иначе, чем
исполняемый файл.

## Что такое разделяемая библиотека

Формально `.so` — это ELF-файл типа `ET_DYN`, но без `PT_INTERP` и без `main`. Точки входа в
привычном смысле нет; вместо неё загрузчик вызывает функции-конструкторы (`.init_array`) при
загрузке и деструкторы при выгрузке. Экспортируемые символы помечены в `.dynsym` как `GLOBAL` с
`st_shndx != UND`; именно они доступны другим модулям. Импортируемые символы (`UND`) резолвятся из
других библиотек.

Ключевое отличие от исполняемого файла: библиотека предназначена для повторного использования, её
адрес загрузки произволен, и она не содержит фиксированной точки входа. При `dlopen` загрузчик
отображает её сегменты, применяет релокации, вызывает конструкторы, а при `dlclose` — деструкторы
(если счётчик ссылок дошёл до нуля).

## soname и версии

У библиотеки есть три имени: **real name** (файл на диске, например `libcrypto.so.3.0.8`),
**soname** (`libcrypto.so.3` — записан в `DT_SONAME`), и **linker name** (`libcrypto.so` —
символическая ссылка для сборки). Программа ссылается на soname, а не на реальный файл. Это
позволяет обновлять библиотеку, сохраняя soname (ABI-совместимость), и менять реализацию без
пересборки программы.

Посмотреть soname: `readelf -d libfoo.so | grep SONAME`. Понять, какие версии требует программа:
`readelf -d ./bin | grep NEEDED`. Если soname не совпадает с установленным, программа не запустится
(`error while loading shared libraries`). Это же — основа подмены: подложить библиотеку с нужным
soname в путь поиска.

## Версионирование символов на практике

Версии символов позволяют одной библиотеке предоставлять несколько ABI одновременно. `readelf
--version-info ./bin` покажет таблицу `Version needs section` со списком требуемых версий из каждой
зависимости. Для реверса это точный индикатор дистрибутива и версии: комбинация `GLIBC_2.34`,
`GLIBC_2.2.5`, `GLIBCXX_3.4.29` сужает круг систем. Для pwn — прямая подсказка, какую libc искать.

Внутри библиотеки каждая версия символа — отдельная запись в `.dynsym` с одинаковым именем, но
разным индексом версии. Именно поэтому `nm -D` может показать `memcpy@@GLIBC_2.14` (версия по
умолчанию) и `memcpy@GLIBC_2.2.5` (совместимость).

## Symbol interposition и порядок поиска

Когда несколько загруженных модулей экспортируют один символ, побеждает первый в порядке поиска.
Порядок задаётся: самим исполняемым файлом, затем `LD_PRELOAD`-библиотеками, затем зависимостями в
порядке `DT_NEEDED`, затем глобальным пространством. Это называется **interposition**. Оно
позволяет перехватывать функции (см. `LD_PRELOAD`), но также порождает баги, когда библиотека
неожиданно «перекрывает» чужой символ. Флаг `-Bsymbolic` при сборке библиотеки заставляет её
использовать свои собственные символы, отключая интерпозицию — полезно для производительности и
предсказуемости.

## dlopen/dlsym: ручная загрузка

Программы (и малварь) часто загружают библиотеки вручную: `dlopen("libfoo.so", RTLD_NOW)` загружает
её, `dlsym(handle, "func")` находит функцию. Это скрывает зависимости от статического анализа —
`readelf -d` их не покажет, потому что имя библиотеки передаётся строкой в рантайме. При анализе
ищите вызовы `dlopen`/`dlsym`/`LoadLibrary`/`GetProcAddress` и трассируйте их аргументы.

Флаги `dlopen`: `RTLD_LAZY` (ленивое связывание), `RTLD_NOW` (немедленное), `RTLD_GLOBAL`
(символы становятся доступны другим модулям), `RTLD_LOCAL` (только для этого). `RTLD_GLOBAL` —
важный, потому что делает interposition возможной для последующих загрузок.

Разница между `RTLD_LAZY` и `RTLD_NOW` практически значима при анализе: при `RTLD_NOW` загрузчик
немедленно разрешает все символы, и если какой-то отсутствует, `dlopen` возвращает ошибку сразу —
это удобно для проверки зависимостей. При `RTLD_LAZY` ошибка проявится только при вызове
конкретной функции. При отладке можно перехватить `dlopen` через `LD_PRELOAD` и логировать имена
загружаемых модулей — так вскрывается динамическая конфигурация малвари, которая иначе остаётся
невидимой для статического анализа.

## Практический разбор: реверс .so

Идентификация и экспорты:

```
$ file libcheck.so
libcheck.so: ELF 64-bit LSB shared object, x86-64, dynamically linked, stripped

$ readelf -d libcheck.so | grep SONAME
 0x000000000000000e (SONAME)  Library soname: [libcheck.so]

$ nm -D libcheck.so | grep ' T '
0000000000001129 T verify_license
00000000000011a0 T get_version
```

Библиотека экспортирует `verify_license` — очевидная цель. Дизассемблируем её:

```
$ objdump -d -M intel --disassemble=verify_license libcheck.so
0000000000001129 <verify_license>:
    1129: push   rbp
    ...
    1140: lea    rdi,[rip+0xe_bd]     # "invalid"
    1147: call   strcmp@plt
    114c: test   eax,eax
    114e: sete   al
    1151: ret
```

Видно сравнение со строкой по адресу. Смотрим строку:

```
$ objdump -s -j .rodata libcheck.so | head
 2000 696e7661 6c696400 73656372 657400    invalid.secret.
```

Строка `secret` — вероятно, ожидаемый пароль. Так анализ библиотеки сводится к её экспортам.

## Windows DLL: ordinals, forwarding, delay-load

В Windows DLL экспортирует функции по именам и/или **ordinals** (числовым индексам). Некоторые DLL
экспортируют функции только по ordinal — тогда `dumpbin /exports` покажет номер без имени, и надо
восстанавливать имя по документации или по поведению. **Export forwarding** — когда DLL не содержит
реализацию, а перенаправляет вызов в другую DLL (запись `KERNEL32.Sleep` в таблице экспорта);
типично для `kernel32.dll`, `ntdll.dll`. **Delay-load** откладывает загрузку DLL до первого вызова
её функции — аналог ленивого связывания.

## Mach-O dylib и @rpath

В Mach-O библиотеки — `.dylib` (или `.framework`). Путь зависимости может быть абсолютным или
относительным через `@rpath`, `@loader_path`, `@executable_path`. `@rpath` разрешается через список
`LC_RPATH` в загружающем бинарнике. Это гибко, но и опасно: подмена по `@rpath` — известный вектор
(`dylib hijacking`). Проверить зависимости: `otool -L ./bin`.

| Задача | Инструмент |
|---|---|
| Экспорты Linux | `nm -D`, `readelf --dyn-syms`, `objdump -T` |
| soname | `readelf -d \| grep SONAME` |
| Версии | `readelf --version-info` |
| Зависимости | `readelf -d`, `ldd` |
| Экспорты Windows | `dumpbin /exports`, `pefile.DIRECTORY_ENTRY_EXPORT` |
| Зависимости Mach-O | `otool -L`, `otool -l \| grep -A2 LC_RPATH` |
| Ручная загрузка | `dlopen`/`dlsym`, `ltrace`, `strace` |

## Порядок поиска библиотек

Когда программа ссылается на библиотеку по soname, загрузчик должен найти файл. Порядок поиска:
`DT_RPATH` (устаревший, но если задан — имеет приоритет), переменная `LD_LIBRARY_PATH`, `DT_RUNPATH`,
кэш `ld.so.cache`, затем стандартные каталоги `/lib`, `/usr/lib`. Понимание этого порядка критично
и для анализа (где именно лежит нужная версия), и для атаки: подложив библиотеку в каталог из
`LD_LIBRARY_PATH` или `RUNPATH`, можно подменить реализацию.

Особенно опасны `RUNPATH` с относительными путями (`$ORIGIN`, текущий каталог): если приложение
запускается из каталога, доступного на запись, злоумышленник подкладывает свою `.so` с нужным
soname и получает выполнение кода в контексте процесса. Трассировать фактический выбор файлов можно
через `LD_DEBUG=libs ./bin 2>&1 | grep -i "trying\|calling"`. Для малвари это способ понять, какие
модули она подтягивает и откуда.

## Библиотеки-плагины и их точки входа

Многие приложения строятся на плагинах: основной бинарник загружает `.so` из каталога и вызывает
функции по согласованному интерфейсу. У таких библиотек есть «магические» экспорты: `plugin_init`,
`RegisterPlugin`, `get_plugin_info`, `NPP_Initialize` (для плагинов браузера), `VSTPluginMain`
(для аудио). Анализ плагина начинается с поиска этих точек входа — они дают «ручку», за которую
можно вытянуть всю функциональность. Часто плагины экспортируют таблицу структур с указателями на
функции; в этом случае статический анализ сводится к разбору таблицы.

Для Linux-плагинов распространён приём: библиотека при загрузке регистрирует свои функции через
`dlopen`-интерфейс и конструктор. Ищите `.init_array` и вызовы регистрации. Для Windows — экспорт
`DllRegisterServer`/`DllGetClassObject` (COM). В мобильных приложениях (Android) нативный плагин
экспортирует `JNI_OnLoad` — точка входа, которую тоже стоит искать в первую очередь.

## Подводные камни

Первое: `.so` можно запустить напрямую (у него есть `_init`), но это не точка входа программы.
Второе: `nm -D` показывает только динамические символы; статические (`.symtab`) могут содержать
внутренние имена, если не stripped. Третье: экспорт может быть `WEAK` — тогда его легко перекрыть.
Четвёртое: в Windows ordinal-экспорты без имён — частая проблема анализа. Пятое: `dlopen` может
загружать библиотеку из неожиданного пути — проверяйте порядок поиска (`LD_DEBUG=libs`). Шестое:
один и тот же символ может экспортироваться несколькими модулями, и то, какая реализация
используется, зависит от порядка загрузки — не делайте выводов только по имени символа. Седьмое:
`RTLD_LOCAL` по умолчанию в некоторых языках (например, в Python `ctypes`), что отключает
интерпозицию и меняет поведение при подмене.

## Что дальше / решение

Практика: возьмите любую системную библиотеку (`libc.so.6`), выведите экспорты, soname, версии.
Напишите свою `.so` с функцией `verify`, соберите, проанализируйте экспорты и строки. Напишите
программу, которая загружает её через `dlopen`/`dlsym`, и проследите через `ltrace`. Далее —
`reversing-plt-got` для механики вызовов и `reversing-dynamic-linking` (существующий урок) для
практики.
