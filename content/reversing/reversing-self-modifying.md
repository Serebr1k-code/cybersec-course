**Self-modifying code** (SMC) — код, который изменяет собственные инструкции во время исполнения: расшифровывает следующий блок, патчит проверки, достраивает новые ветки, генерирует код на лету (JIT-подобные протекторы). Статический анализ такого кода показывает «мусор»: дизассемблер читает байты **до** модификации, а реальная логика появляется только в памяти в рантайме. SMC — основа большинства упаковщиков и анти-tamper-защит, поэтому умение его распаковывать критично. Этот урок — как распознать SMC, восстановить код через эмуляцию/дампинг/трассировку и обойти связанные защиты.

## Почему SMC ломает статику

- Дизассемблер видит байты **до** модификации — часто зашифрованные или мусорные.
- Реальная инструкция формируется в памяти в рантайме (после декодера).
- Проверки и ветвления патчатся на лету (anti-tamper): контрольная сумма кода, отключение breakpoint-байта `0xCC`.
- **Полиморфизм:** каждая генерация кода отличается, сигнатуры бесполезны.
- Часто SMC сочетается с **анти-отладкой** и **виртуализацией**, что усложняет пошаговое исполнение.

Итог: статический дизассемблер «не виноват» — он показывает корректный, но ещё не расшифрованный код. Задача аналитика — выполнить декодер и снять дамп **после** модификации.

## Как распознать SMC

Признаки в статике и динамике:

- **Запись в исполняемую секцию** (`.text`, `.vmp0`) или в регион с кодом — самый надёжный признак.
- **`mprotect`/`VirtualProtect`** на код (смена прав на RW/RWX) — снятие защиты записи.
- **XOR/ROT/ADD-декодер в цикле**, пишущий результат обратно в код.
- **Флаш инструкционного кэша**: `__builtin___clear_cache`, `FlushInstructionCache`, `sys_icache_invalidate` (ARM).
- **Динамика:** одна и та же инструкция меняет байты; `self-modifying` в трассе.

```bash
# Импорты, намекающие на SMC
objdump -T binary | grep -iE "mprotect|VirtualProtect|FlushInstructionCache|clear_cache"
# ELF: секция .text помечена W? (редко) или есть RWX-сегмент
readelf -l binary | grep -E 'LOAD|GNU_STACK' -A1
# Быстрый поиск XOR-циклов, пишущих в код (эвристика)
objdump -d -M intel binary | grep -B3 -A3 'mov.*\[r.x\], al'
```

## Подход 1: эмуляция и дампинг (Unicorn/Qiling)

Эмуляция — самый безопасный путь: декодер исполняется в контролируемой среде, без реального процесса и анти-отладки.

```python
from unicorn import *
from unicorn.x86_const import *

BASE = 0x400000
code = open('stage1.bin','rb').read()

mu = Uc(UC_ARCH_X86, UC_MODE_64)
mu.mem_map(BASE, 0x100000)
mu.mem_write(BASE, code)
# Присваиваем указатель стека
mu.reg_write(UC_X86_REG_RSP, BASE + 0xF0000)

dumps = []
def hook_mem_write(mu, access, addr, size, value, user):
    # Логируем каждую запись и запоминаем, что код меняется
    dumps.append((addr, size, value))

mu.hook_add(UC_HOOK_MEM_WRITE, hook_mem_write)

try:
    mu.emu_start(BASE, BASE + len(code), timeout=10*1000*1000)
except UcError as e:
    print('stop:', e)

# Снимаем дамп расшифрованного региона
decoded = mu.mem_read(BASE, 0x10000)
open('decoded.bin','wb').write(bytes(decoded))
```

После этого `decoded.bin` дизассемблируется как обычный код. Qiling добавляет эмуляцию системных вызовов — нужна, если декодер обращается к файлам/сети (например, читает payload из ресурса).

## Подход 2: отладчик, watchpoints и дамп

Когда эмуляция слишком сложна (периферия, много syscalls), используйте реальный процесс:

```bash
# gdb/pwndbg
gdb -q ./packed
(gdb) start
(gdb) info proc mappings            # найти исполняемый регион
(gdb) watch *(unsigned char*)0x401000   # watchpoint на байт кода
(gdb) continue                      # остановится при первой записи
(gdb) x/10i $pc                     # дизасм
# Поставить аппаратный BP на запись в диапазон (в x64dbg: Hardware BP on memory)
```

```bash
# x64dbg: Memory map -> выбрать .text -> Hardware breakpoint (access: write)
# после срабатывания: Scylla -> dump + fix IAT
```

Frida для рантайм-перехвата записи:

```js
// Перехватить mprotect (снятие защиты записи на код)
var mprotect = Module.findExportByName(null, 'mprotect');
Interceptor.attach(mprotect, {
  onEnter: function (args) {
    console.log('mprotect', args[0], 'len', args[1], 'prot', args[2]);
  }
});
```

## Подход 3: Intel PT и трассировка

Intel Processor Trace записывает реальный поток исполнения без замедления, что обходит анти-отладку:

```bash
# perf + intel_pt
perf record -e intel_pt//u ./packed
perf script --itrace=i100us -F ip,sym > trace.txt
# или WinAFL/wtracer на Windows
```

Трасса показывает, какие адреса реально исполнялись — по ней видно момент перехода в расшифрованный код. Для реконструкции из трассы используют `ptxed`/`perf script`.

## Разобранный пример: XOR-декодер end-to-end

```asm
; классический SMC-стаб
lea rsi, [rip + encoded]     ; источник — зашифрованные байты
mov rdi, rsi                 ; назначение — тот же регион (самомодификация)
mov rcx, LEN
xor rdx, rdx                 ; счётчик
decode:
    mov al, [rsi + rdx]
    xor al, KEY              ; KEY — константа или производная
    mov [rdi + rdx], al      ; запись в код!
    inc rdx
    cmp rdx, rcx
    jne decode
jmp encoded                  ; прыжок в расшифрованный код
```

Порядок действий:

```text
1) Найти в дизасме цикл с mov [..], al рядом с lea на encoded.
2) Определить KEY: константа рядом или производная (напр. XOR с индексом).
3) Вариант A (эмуляция): Unicorn, hook на запись -> дамп encoded после цикла.
4) Вариант B (отладчик): watchpoint на encoded, дойти до jmp encoded, дамп.
5) Дизассемблировать дамп, проверить, что это осмысленный код.
6) Если код расшифровывается по частям (слоями) — повторить дампинг несколько раз.
```

Быстрая «ручная» расшифровка, если алгоритм простой и KEY известен:

```python
data = bytearray(open('binary.bin','rb').read())
off, length, key = 0x1200, 0x400, 0x5A
for i in range(length):
    data[off+i] ^= key
open('patched.bin','wb').write(data)
```

## Многослойная распаковка и JIT

Продвинутые протекторы (VMProtect, Themida) применяют **несколько слоёв** SMC: первый стаб расшифровывает второй, второй — третий, и так далее. Приёмы:

- **Итеративный дампинг:** после каждого слоя снимайте дамп и продолжайте эмуляцию с новой точки входа.
- **Определение конца слоя:** обычно `jmp`/`call` в только что расшифрованный регион или смена прав памяти.
- **JIT-подобные протекторы** генерируют код блоками в куче (RWX) — дампите регион кучи, а не только `.text`.
- **Отслеживание аллокаций:** hook на `VirtualAlloc`/`mmap` с `PROT_EXEC` — там появится сгенерированный код.

## Обход анти-анализа

SMC почти всегда защищён от анализа:

- **Анти-отладка** ломает пошаговое исполнение и breakpoints (проверка `0xCC`, `IsDebuggerPresent`, `ptrace`). Решение — **эмуляция** (нет реального процесса), либо трасса PT, либо патч проверок в дампе.
- **Timing-проверки** ловят замедление от отладчика — эмуляция работает «в вакууме».
- **Контрольные суммы кода** обнаруживают breakpoint-байты и патчи — патчите в памяти, а не в файле, или эмулируйте.
- **Многослойность** требует терпения: дампите несколько раз и собирайте полную картину.

## Реконструкция образа и повторный анализ

После дампинга:

```text
1) Соберите все расшифрованные участки по корректным виртуальным адресам.
2) Исправьте заголовки (если нужно) — утилитой вроде pefile/lief или Scylla.
3) Восстановите таблицу импортов (IAT), если протектор её «спрятал».
4) Загрузите реконструированный образ в IDA/Ghidra и анализируйте как обычный бинарь.
5) Проверьте: точки входа, строки, вызовы API — теперь они видны.
```

## Частые ошибки

- **Анализировать зашифрованный код.** Статический дизасм «мусора» бесполезен — сначала дамп после расшифровки.
- **Забыть про инструкционный кэш.** На реальном железе изменённый код может не исполниться без флаша (в эмуляции проблемы нет).
- **Дамп в неверный момент.** Часть кода может ещё не расшифроваться; дампите после завершения декодера (по `jmp` в расшифрованный регион).
- **Игнорировать многослойность.** Может быть несколько этапов SMC — дампите итеративно.
- **Не учесть анти-отладку.** Отладчик может ломать SMC (или сам детектироваться) — используйте эмуляцию/PT.
- **Потеря адресов.** Для реконструкции нужны корректные базовые адреса и карта памяти.
- **Забыть про RWX-регионы.** Сгенерированный код может быть в куче, а не в `.text`.

## Что делать дальше / решение

1. Определите, что перед вами SMC: запись в код, `mprotect`/`VirtualProtect`, XOR-цикл, флаш кэша.
2. Выберите путь: эмуляция (Unicorn/Qiling) для простых декодеров; отладчик с watchpoints — когда нужны syscalls/периферия; Intel PT — против сильной анти-отладки.
3. Найдите точку завершения декодера (jmp/call в расшифрованный регион) и снимите дамп.
4. При многослойности повторите дампинг для каждого слоя, включая RWX-регионы кучи.
5. Реконструируйте образ (адреса, IAT) и перезагрузите в IDA/Ghidra.
6. Проанализируйте восстановленный код как обычный бинарь; при необходимости патчите проверки.
