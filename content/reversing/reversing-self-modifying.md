## Вопрос, с которого всё начинается

Ты снимаешь дамп памяти упакованного образца, сохраняешь его на диск, открываешь в дизассемблере —
и снова видишь мусор. Или: ставишь точку останова на функцию, запускаешь, а байты по этому адресу
уже не те, что были в файле. Это **самомодифицирующийся код** (self-modifying code): программа во
время работы переписывает собственные инструкции. Для реверсера это означает, что статический
анализ файла принципиально не даёт полной картины.

Опираемся на прошлый урок: мы умеем исполнять код в эмуляторе. Здесь это умение станет главным
инструментом, потому что статике доверять нельзя.

## Наш пример

Соберём минимальный самомодифицирующийся «образец». В памяти лежит зашифрованный блоб, стаб
разрешает исполнение страницы, расшифровывает блоб и вызывает его как функцию:

```c
unsigned char blob[] = {0x12,0x80,0xAA,0xAA,0xAA,0x69};  /* до расшифровки */
int main(void){
    unsigned long pg = (unsigned long)blob & ~0xfffUL;
    sc(10, pg, 0x1000, 7);                    /* mprotect(pg,4096,RWX) */
    for (unsigned i=0;i<sizeof(blob);i++) blob[i]^=0xAA;
    int (*f)(void) = (int(*)(void))blob;
    printf("decoded result = %d\n", f());
}
```

Здесь `sc` — обёртка над системным вызовом: номер 10 в Linux — это `mprotect`, который меняет права
на страницу памяти. Мы просим права `7` (`rwx`: чтение, запись, исполнение), чтобы после
расшифровки код можно было выполнить. Запускаем:

```
$ ./stub
decoded result = 42
```

В файле же лежит `12 80 AA AA AA 69` — набор байтов, который **не является** осмысленным кодом.

## Шаг 1: почему статика ломается

Посмотрим на дизассемблер до запуска — на секцию `.data`, где живёт `blob`:

```
0x404018 <blob>:  0x12  0x80  0xaa  0xaa  0xaa  0x69
```

Ни одной осмысленной инструкции. Дизассемблер бессилен: он читает байты из файла, а эти байты
станут кодом только после расшифровки. Причём расшифровка происходит **в памяти**, файл на диске
не меняется. Поэтому «просто открыть в Ghidra» не работает — нужно наблюдать исполнение.

## Шаг 2: поймать момент расшифровки

Ставим точку останова на инструкцию **после** цикла расшифровки, но **до** вызова `blob`:

```
$ gdb -q -batch -ex 'break *0x4011b3' -ex run -ex 'x/6xb &blob' ./stub
0x404018 <blob>:  0xb8  0x2a  0x00  0x00  0x00  0xc3
```

Вот оно: те же шесть байтов теперь читаются как `b8 2a 00 00 00 c3`. Разберём их как код: `b8` —
опкод `mov eax, imm32`, дальше `2a 00 00 00` — это 42, и `c3` — `ret`. То есть расшифрованный блоб
— это функция `mov eax, 42; ret`. Именно её вызов дал «decoded result = 42».

Мы получили расшифрованный код, **остановившись в правильный момент**. Это и есть ручная распаковка
самомодифицирующегося кода.

## Шаг 3: где здесь «модификация себя»

Ключевой момент — инструкция `mprotect` с правами `rwx`. По умолчанию страницы данных не
исполняемы (защита называется **NX**, no-execute). Чтобы код, лежащий в `.data`, можно было вызвать,
программа обязана снять NX. Эта «просьба сделать память исполняемой» — классический признак
самомодификации и распаковки. В дизассемблере это видно как вызов `mprotect`/`VirtualProtect` с
флагом «execute»:

```
401183:  call   401126 <sc>            ; mprotect(pg, 4096, 7)  — 7 = RWX
401191:  mov    eax,DWORD PTR [rbp-0x14]
401194:  movzx  eax,BYTE PTR [rax+0x404018]
40119b:  xor    eax,0xffffffaa          ; xor 0xAA
4011a3:  mov    BYTE PTR [rax+0x404018],dl   ; запись обратно в память
```

Обрати внимание: цикл **и читает, и пишет** по адресу `0x404018` — тому самому, где лежит код. Это
и есть запись в собственную исполняемую память.

## Шаг 4: распаковка через эмуляцию

Ручной breakpoint хорош для маленького примера, но для настоящего образца с сотнями блоков он
неудобен. Здесь выручает эмуляция: запускаем stub в Unicorn, и как только он запишет расшифрованные
байты в память — просто читаем её. Эмулятор не боится анти-отладки (он не отладчик) и не заражает
систему. Схема такая:

1. Смапить память и загрузить секции образца.
2. Повесить хук на запись (`UC_HOOK_MEM_WRITE`) в исполняемую область.
3. Запустить эмуляцию с точки входа stub.
4. Когда хук сработал — забрать содержимое области: это распакованный код.

Так же поступают инструменты вроде Qiling и специализированные распаковщики: они «дожимают» stub
до передачи управления на OEP и дампят память.

## Шаг 5: полиморфизм и почему это важно

Самомодификация — основа **полиморфных** вредоносов: каждый запуск код расшифровывается своим ключом
или пересобирается заново, поэтому сигнатура файла меняется, а сигнатуры в памяти нет. Отсюда два
практических вывода:

- **Файл ничего не значит.** Анализируй память после распаковки, а не байты на диске.
- **Ищи момент снятия NX.** `mprotect(...RWX)` и `VirtualProtect(...PAGE_EXECUTE*)` — надёжные
  маркеры, за которыми почти всегда следует расшифровка.

## Если не сработало

- **Breakpoint не срабатывает** — возможно, код расшифровывается по частям, перед каждым вызовом.
  Тогда ставь точку не на «после цикла», а на **запись** в исполняемую страницу (аппаратный
  watchpoint по записи).
- **Код исполняется сразу из расшифрованного буфера, не в исходной секции** — дампи не секцию, а
  тот буфер, куда писались байты.
- **Расшифровка зависит от времени/окружения** — прогони в эмуляторе с нужными значениями или
  запатчь проверку.

## Что мы теперь знаем

- **Self-modifying code** переписывает свои инструкции во время работы; статический анализ файла
  даёт неполную картину.
- Распаковка не меняет файл на диске — меняется **память**, поэтому нужен момент «после
  расшифровки, до вызова».
- Снятие защиты **NX** (`mprotect`/`VirtualProtect` с execute) — верный признак распаковки.
- **Эмуляция** позволяет безопасно прогнать stub и забрать расшифрованный код хуком на запись.
- Это основа **полиморфизма**: анализируй память, а не файл.

## Куда дальше

Мы разобрались, как код меняет себя и как это распутать. Дальше возьмём целую **виртуальную машину
внутри бинарника** — VM-based crackme, где логика вынесена в собственный байткод, — и научимся его
дизассемблировать. А пока главное запомни: **если код меняет себя в рантайме, анализируй память
после распаковки, а не файл на диске**.

## Где пригодится

- **CTF Reversing:** полиморфные и самомодифицирующиеся задачи — частый «хард».
- **Malware analysis:** почти все современные упаковщики самомодифицируются.
- **Packer research:** поиск момента снятия NX — ключ к распаковке.
- **Автоматизация:** хуки на запись в эмуляторе дают готовый распакованный код.
- **Собес:** «как ты снимешь самомодифицирующийся стаб?» — вопрос продвинутого уровня.
