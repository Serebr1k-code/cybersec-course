## Вопрос, с которого всё начинается

Ты открыл функцию в Ghidra, нажал на вкладку декомпилятора — и увидел код, похожий на C, но со
странностями: переменные зовутся `local_50` и `undefined8`, типы `undefined`, а иногда в коде
появляются конструкции, которых ты не писал. Как это читать и можно ли этому верить?

Декомпилятор не восстанавливает исходник — он **реконструирует** его из ассемблера, угадывая
типы и имена. В этом уроке разберём, как читать этот псевдокод на примере `main` из `crackme`.

## Наш пример

Возьмём функцию `main`. Вот её ассемблер (сокращённо, ключевые места):

```bash
$ objdump -d -M intel --disassemble=main crackme | sed -n '1,20p'
00000000000011ad <main>:
    11ad: 55                    push   rbp
    11ae: 48 89 e5              mov    rbp,rsp
    11b1: 48 83 ec 60           sub    rsp,0x60
    ...
    11c4: 48 8d 05 45 0e 00 00  lea    rax,[rip+0xe45]   # 2010 "Enter password: "
    11d3: e8 78 fe ff ff        call   1050 <printf@plt>
    11d8: 48 8d 45 b0           lea    rax,[rbp-0x50]    ; буфер
    11dc: ba 3f 00 00 00        mov    edx,0x3f          ; сколько читать (63)
    11e4: bf 00 00 00 00        mov    edi,0x0           ; fd = stdin
    11e9: e8 72 fe ff ff        call   1060 <read@plt>
    ...
    124e: e8 26 ff ff ff        call   1179 <check_password>
    1253: 85 c0                 test   eax,eax
    1255: 74 11                 je     1268 <main+0xbb>  ; если 0 → "Wrong"
```

Читать это можно, но медленно. Откроем `main` в декомпиляторе — Ghidra или Hex-Rays (в IDA
это клавиша `F5`). Он выдаст псевдокод примерно такого вида:

```c
undefined8 main(void) {
  long canary;
  ssize_t n;
  char local_50[64];
  long i;

  printf("Enter password: ");
  n = read(0, local_50, 0x3f);
  if (n < 1) {
    return 1;
  }
  local_50[n] = 0;
  for (i = 0; i < n; i = i + 1) {
    if (local_50[i] == '\n') {
      local_50[i] = 0;
    }
  }
  if (check_password(local_50)) {
    printf("Correct! flag{rev_basics_1s_fun}\n");
  } else {
    printf("Wrong.\n");
  }
  return 0;
}
```

Вот теперь видно **логику целиком**: читаем ввод, обрезаем перевод строки, зовём
`check_password`, печатаем флаг или ошибку. На ассемблере это заняло бы экран и десять минут,
на псевдокоде — пять секунд.

## Шаг 1: почему имена странные

`local_50`, `undefined8`, `n` — это **артефакты**. Декомпилятор не знает имён из исходника, он
придумывает свои:

- **`local_XX`** — локальная переменная по смещению `XX` от базы кадра. `local_50` = `[rbp-0x50]`.
- **`undefined8`** — «8 байт неизвестного типа»: `rax` возвращается, но тип не ясен.
- **`param_1`** — первый аргумент функции, если имя неизвестно.

Это не ошибки, а честное «я не знаю, как это называлось». Восстановление имён — часть работы.

## Шаг 2: восстанавливаем типы и имена

Хороший аналитик сразу улучшает псевдокод. В Ghidra: `L` — переименовать, `T` — задать тип,
`Ctrl+L` — изменить сигнатуру функции. После нескольких правок тот же `main` читается уже
почти как исходник:

```c
int main(void) {
  char buf[64];
  ssize_t n = read(0, buf, 63);
  if (n <= 0) return 1;
  buf[n] = 0;
  for (int i = 0; i < n; i++)
    if (buf[i] == '\n') buf[i] = 0;
  puts(check_password(buf) ? "Correct! ..." : "Wrong.");
  return 0;
}
```

Ключевой навык: увидел `local_50` там, где явно буфер под ввод, — переименовал в `buf`. Увидел
`undefined8` на возврате функции сравнения — понял, что это `bool`/`int`. Так псевдокод
превращается в читаемую логику.

## Шаг 3: откуда взялся canary и почему его «нет» в псевдокоде

В ассемблере `main` были строки с `fs:0x28` — это защита стека (canary). В декомпилированном
виде они обычно **скрыты** (или показаны как непонятная переменная `canary`). Это нормально:
canary — служебная деталь, к логике программы отношения не имеет.

Так же скрываются/упрощаются:

- **пролог и эпилог** (`push rbp` / `leave`) — их в псевдокоде нет;
- **выравнивание стека** и переходники (`thunks`);
- **библиотечные инициализаторы** (`__libc_start_main`).

Правило: если в псевдокоде что-то выглядит «лишним» и не связано с данными — вероятно, это
компиляторный или защитный код.

## Шаг 4: типичные ловушки декомпиляции

Декомпилятор иногда **ошибается**. Что нужно знать:

- **Оптимизация.** При `-O2` компилятор переставляет и склеивает код; декомпилятор может
  слить две функции или показать странный цикл. Проверяй по ассемблеру.
- **Inline-функции.** Маленькая функция «растворяется» в вызывающей — в псевдокоде её тела не
  будет отдельно.
- **Tail call.** `return f(x);` компилируется в `jmp f`, и декомпилятор может показать это как
  отдельный вызов с последующим `return`.
- **Неверный тип.** `undefined4` может быть `int`, указателем, или полем структуры — угадывать
  приходится по использованию.

Поэтому золотое правило из прошлого урока: **дизассемблер — источник правды, декомпилятор —
ускоритель.** Сомневаешься в псевдокоде — открой рядом ассемблер и сверься.

## Шаг 5: как это применяется

В CTF псевдокод — основной рабочий инструмент. Наш `main` сразу показал: секрет сравнивается в
`check_password`. Перейдя в неё (двойной клик по имени), получаем:

```c
int check_password(char *in) {
  return strcmp(in, "hunter2") == 0;
}
```

И задача закрыта. В реальном malware декомпилятор так же быстро вскрывает цикл шифрования,
сетевые вызовы или проверку ключа — надо лишь помнить про артефакты и не доверять вслепую.

## Шаг 6: как ускорить чтение

Несколько приёмов, которые экономят время:

- **Иди от строк.** Найди в окне `Strings` сообщение-подсказку и посмотри xref — сразу попадёшь
  в функцию проверки.
- **Переименовывай сразу.** Как только понял смысл переменной (`buf`, `n`, `key`), переименуй:
  псевдокод станет читаемым и для тебя, и в отчёте.
- **Меняй сигнатуры.** Если функция принимает указатель на строку, задай тип `char *`, и
  псевдокод начнёт использовать `[]` и `strlen` вместо арифметики с числами.
- **Сравнивай с ассемблером.** Если псевдокод подозрительный (непонятный цикл, «магические»
  константы) — открой вкладку дизассемблера и сверься.
- **Не верь именам `sub_`.** `sub_1179` может быть чем угодно; осмысленное имя появляется
  только после анализа.

## Что мы теперь знаем

- Декомпилятор **реконструирует** псевдо-C, угадывая типы и имена.
- `local_XX`, `param_1`, `undefined8` — артефакты отсутствия имён, а не ошибки.
- Имена и типы **восстанавливают вручную** (`L`/`T` в Ghidra, `F5` + правки в IDA).
- Canary, пролог/эпилог и служебный код в псевдокоде скрыты — это норма.
- Оптимизация, inline и tail call могут искажать псевдокод — сверяйся с ассемблером.

## Куда дальше

Статика дала нам гипотезу: `check_password` сравнивает ввод с `hunter2`. Но что если строки
зашифрованы или проверка запутана? Тогда нужен запуск — и мы переходим к **динамическому
анализу**: отладчику `gdb`, точкам останова и инспекции памяти. Об этом — в следующем уроке.
А пока главное запомни: читай псевдокод, восстанавливай имена и типы, но проверяй по
ассемблеру.

## Где пригодится

- **CTF Reversing:** псевдокод вскрывает проверки и алгоритмы в разы быстрее ассемблера.
- **Malware analysis:** восстановление логики образца — шифрование, C2, проверки анти-анализа.
- **Восстановление алгоритмов:** протоколы и форматы проприетарного ПО читаются из псевдокода.
- **Патчинг:** понимание, что править, приходит из декомпилированного кода.
- **Собес:** «чем декомпилятор отличается от дизассемблера», «что такое артефакты» — базовые вопросы.
