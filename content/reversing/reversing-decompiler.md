Декомпилятор — самый мощный инструмент реверсера: он превращает ассемблер в псевдо-C, который
читается в разы быстрее. Но слепое доверие к нему — путь к ошибкам. Чтобы пользоваться декомпилятором
профессионально, нужно понимать, **как он устроен** (SSA, анализ потока данных, восстановление типов),
**где ошибается** и **как ему помочь**. Этот урок — про теорию и практику декомпиляции: Hex-Rays,
Ghidra, RetDec, плагины и приёмы получения читаемого кода.

## Как работает декомпилятор: конвейер

Декомпиляция — это последовательность преобразований:

1. **Лифтинг.** Ассемблер переводится в **IR** (промежуточное представление): Hex-Rays — microcode,
   Ghidra — P-Code, RetDec — LLVM IR.
2. **Построение CFG.** Из инструкций строится граф базовых блоков (control-flow graph).
3. **SSA-форма.** Каждой переменной присваивается один раз (static single assignment); это упрощает
   анализ потока данных.
4. **Анализ потока данных.** Распространение констант, устранение мёртвого кода, определение
   используемых переменных.
5. **Восстановление типов.** По операциям угадываются типы (`int`, `char*`, структуры).
6. **Структурирование.** CFG превращается в `if`/`while`/`for` (structured control flow).
7. **Генерация C.** Формируется псевдо-C.

Ошибки возникают на каждом этапе: лифтинг не знает всех инструкций, CFG может быть «сплющен»,
типы угаданы неверно, структурирование ломается на `goto`-подобном коде.

## Сравнение декомпиляторов

| Декомпилятор | Хост | Плюсы | Минусы |
|---|---|---|---|
| **Hex-Rays** | IDA | лучший псевдо-C, microcode API | платный |
| **Ghidra** | Ghidra | бесплатный, P-Code API | медленнее, слабее на C++ |
| **RetDec** | CLI | открытый, LLVM IR | неточный, заброшен |
| **Reko** | CLI/GUI | открытый, много ISA | сырой вывод |
| **Binary Ninja** | GUI | отличный IL (BNIL) | платный |
| **snowman** | CLI | открытый | слабый |
| **Ghidra+RetDec** | Ghidra | комбинированный | сложная настройка |

Для x86/x64 промышленный стандарт — Hex-Rays; для ARM/MIPS/RISC-V Ghidra часто даёт результат не хуже.
RetDec/BNIL полезны, когда нужен машинный IR для кастомного анализа.

## Приёмы получения читаемого кода

**1. Типы — прежде всего.** Каждый `Y`/`Ctrl+L` улучшает вывод. Создавайте структуры, задавайте
прототипы функций (`int f(char*, size_t)`), типизируйте поля.

**2. Переименование.** `N` — имена переменных/функций. Чем осмысленнее имена, тем легче читать.

**3. Объявление массивов.** Если декомпилятор показывает `int x; int y; int z;` подряд — это,
вероятно, структура или массив. Задайте `int arr[3]` или структуру.

**4. Устранение «мусора».** Конструкции вида `(int)(char)(unsigned __int8)x` — результат
неоднозначных типов; правильный тип убирает каскад приведений.

**5. Комментарии.** `:` в IDA, `;` в Ghidra — фиксируйте понимание.

**6. Inline-ассемблер.** Hex-Rays не всегда понимает inline asm — сверяйтесь с листингом.

## Разобранный пример: типизация улучшает декомпиляцию

Дано: функция, работающая с неизвестной структурой. Изначально:
```c
int sub_401230(int a1, int a2) {
    if (*(_DWORD *)(a1 + 4) != 0x1234) return 0;
    return sub_401100(a1 + 8, a2);
}
```
Создаём структуру:
```c
struct pkt {
    int type;       // +0
    int magic;      // +4
    char data[256]; // +8
};
```
Задаём `a1` как `struct pkt *` (`Y`):
```c
int check(struct pkt *p, int len) {
    if (p->magic != 0x1234) return 0;
    return process(p->data, len);
}
```
Читаемость выросла в разы — теперь видно смысл: проверка magic и передача данных в `process`.

## Микрокод/P-Code: когда декомпилятор «врёт»

Иногда псевдо-C неверен из-за особенностей IR. Тогда спускаемся на уровень микрокода/P-Code:

- **Hex-Rays microcode** — правый клик → `Show microcode`; блоки (`mblock_t`) и инструкции (`minsn_t`).
- **Ghidra P-Code** — правый клик → `Instruction → P-Code`.

Зачем: на этом уровне видны реальные операции без искажений структурирования. Плагины деобфускации
и символьные анализаторы часто работают именно с IR.

## Крайние случаи и подводные камни

- **Косвенные вызовы.** `call [rax+0x18]` — декомпилятор не знает цель; используйте динамику/анализ
  типов виртуальных таблиц.
- **`longjmp`/`setjmp`.** Ломают структурирование — CFG становится запутанным.
- **Хвостовые вызовы.** Декомпилятор может «склеить» функции или потерять возврат.
- **Оптимизации (`-O2`).** Код переупорядочен, переменные переиспользованы — псевдо-C далёк от
  исходника. Иногда помогает деоптимизация/символика.
- **Обфускация.** Control-flow flattening, opaque predicates, MBA (mixed boolean arithmetic) —
  декомпилятор выдаёт нечитаемую кашу; нужны плагины упрощения/символика.
- **C++.** RTTI/vtables/исключения усложняют вывод; Ghidra/IDA частично восстанавливают классы.
- **Неверные типы «заражают».** Ошибка в одном месте может испортить декомпиляцию соседних функций.
- **Версии API.** Скрипты под microcode/P-Code привязаны к версии инструмента.

## Что дальше / решение

1. Дизассемблировать и декомпилировать ключевые функции.
2. Типизировать: прототипы, структуры, массивы — итеративно.
3. Переименовывать по мере понимания; фиксировать гипотезы комментариями.
4. Сверять критичные места с листингом/микрокодом.
5. Для обфускации — плагины упрощения, символическое исполнение, спуск на IR.
6. Если Hex-Rays/Ghidra не справляются — попробовать второй декомпилятор (RetDec/BNIL) для сравнения.

Принцип: **декомпилятор — это ассистент, а не оракул**. Ваша задача — дать ему максимум контекста
(типы, имена) и проверять результат там, где он может ошибиться.

## SSA: почему декомпилятор вообще работает

**Static Single Assignment (SSA)** — форма, в которой каждая переменная присваивается ровно один раз.
Если в ассемблере `eax` переиспользуется десятки раз, то в SSA появляются `eax_1`, `eax_2`, …
Каждое использование связано с определением через **phi-функции** в точках слияния ветвлений.

Зачем это нужно:
- **Поток данных становится явным** — видно, откуда пришло значение.
- **Оптимизации просты** — constant propagation, dead code elimination.
- **Типы выводятся** из операций над значениями.

Практическое следствие: **декомпилятор восстанавливает значения, а не регистры**. Если вы видите
странную переменную `v3`, за ней может стоять реальная логика. Задавая типы и переименовывая, вы
помогаете SSA-анализу и получаете чище результат.

## Разобранный пример: восстановление switch

Дано: функция с большим `switch` (например, парсер команд). Изначально декомпилятор выдаёт:
```c
switch ( a2 ) {
  case 0: ... break;
  case 1: ... break;
  ...
}
```
Но иногда видим **таблицу переходов**:
```c
if ( a2 > 9 ) return 0;
return (*(int (__fastcall **)(int))(0x402000 + 8 * a2))(a1);
```
Это **jump table** — косвенный вызов по индексу. Декомпилятор не знает адресатов. Решения:
1. В IDA нажать `Y`/преобразовать в `switch` (иногда восстанавливается автоматически).
2. Посмотреть таблицу в `.rdata` (`0x402000`) и сопоставить индексы адресам.
3. Динамически залогировать, какой адрес вызывается для какого `a2`.

Так восстанавливается семантика диспетчеров (в т.ч. VM, см. урок про VM-crackmes).

## Обфускация MBA и её упрощение

**Mixed Boolean-Arithmetic (MBA)** — замена простой операции на эквивалентную, но запутанную:
```
x + y   →   (x ^ y) + 2*(x & y)
x ^ y   →   (x | y) - (x & y)
```
Декомпилятор показывает монструозные выражения. Методы борьбы:

- **Упрощение символическим инструментом** (Z3, Triton, Miasm): выразить выражение и попросить
  упростить.
- **Плагины упрощения** (`gooMBA`, `MBA-Solver`, скрипты для IDA/Ghidra).
- **Поиск инвариантов**: часто `opaque predicate` (всегда истинное условие) маскирует реальный переход.

Пример: `((x & 0xff) ^ 0x41) - ((x & 0xff) | 0x41)` может упроститься до `-(x & 0xff)` — после
подстановки становится ясно, что это простое отрицание.

## C++ и восстановление классов

Для C++ декомпилятор сталкивается с `this`-указателями, виртуальными таблицами и исключениями:

- **`this`** — первый (или второй после `rdi` в MSVC) аргумент методов; задайте тип класса.
- **vtable** — массив указателей на виртуальные методы; создайте структуру с полями-функциями.
- **RTTI** — в бинарнике могут быть имена классов (`type_info`); ищите строки с именами и
  перекрёстные ссылки.
- **Исключения** — `__cxa_throw`, LSDA; декомпилятор иногда теряет `try/catch`.

Инструменты: `HexRaysPyTools` (IDA) и скрипты Ghidra для восстановления классов по vtable/RTTI.

## Чек-лист качественной декомпиляции

1. Загрузить, дать автоанализу завершиться.
2. Найти точку входа и ключевые функции (строки/импорты/xref).
3. Задать прототипы всех вызываемых функций.
4. Создать структуры для повторяющихся смещений (`*(_DWORD*)(a1+8)` → `p->field`).
5. Переименовать функции/переменные по смыслу.
6. Сверить подозрительные места с листингом/микрокодом.
7. Для обфускации — плагины упрощения/символика.
8. Зафиксировать понимание комментариями и перейти к реконструкции алгоритма.

Этот чек-лист превращает «кашу» из псевдо-C в читаемую программу.

## Где пригодится

- **CTF Reversing:** восстановление алгоритмов шифрования/проверки в medium/hard задачах.
- **Malware analysis:** понимание логики без запуска (какие данные собирает, как шифрует).
- **Vuln research:** поиск мест, где декомпилированный код похож на уязвимый C (переполнения).
- **Собес:** вопросы про артефакты декомпиляции, `__ROL__`, восстановление структур — часты.
- **Работа:** декомпилятор — основной инструмент реверс-инженера при работе с нативным кодом.
