## Вопрос, с которого всё начинается

Ты разбираешь `rpcserver.exe` — службу Windows, уязвимую к удалённому вызову. В импортах видишь `RpcServerRegisterIf`, `NdrServerCallAll`, но не понимаешь, какие методы доступны и как их вызывать. Как найти интерфейсы и восстановить их сигнатуры?

## Наш пример

Возьмём `rpcserver.exe`. Смотрим строки:

```
$ strings -n 6 rpcserver.exe | grep -iE 'rpc|interface|uuid'
rpcserver.exe
RpcServerRegisterIf
8a7c1d40-9e2b-4f3a-b1c5-7d6e8f9a0b12
IComputeService
ComputeHash
GetStatus
```

UUID, имя интерфейса `IComputeService` и методы `ComputeHash`/`GetStatus` — это RPC-интерфейс. Разберём, как он устроен.

## Шаг 1: что такое COM, DCOM и RPC

**COM** (Component Object Model) — модель, где программа работает с объектами через интерфейсы. Клиент не знает, где живёт объект; он вызывает метод через указатель на интерфейс. **DCOM** — тот же COM, но объект может быть на другой машине: вызовы маршалятся (сериализуются) и передаются по сети. **RPC** — транспорт, на котором DCOM ездит.

Для реверса это означает: если в бинарнике есть `CoCreateInstance`, `RpcServerRegisterIf`, UUID-строки — здесь есть интерфейсы, а значит — методы, которые могут быть вызваны удалённо. Это поверхность атаки.

## Шаг 2: UUID и интерфейсы

Каждый COM/RPC-интерфейс имеет **UUID** (глобально уникальный идентификатор). Клиент указывает UUID, чтобы получить интерфейс; сервер регистрирует его. UUID `8a7c1d40-...` из строк — это IID интерфейса `IComputeService`.

Найти интерфейсы в бинарнике можно по строкам UUID и по вызовам `RpcServerRegisterIf`. В отладочных сборках рядом лежат имена методов; в релизных их может не быть, но UUID и таблица методов останутся.

## Шаг 3: MIDL-стабы и маршалинг

RPC-интерфейс описывается в **IDL**-файле, из которого компилятор **MIDL** генерирует «стабы» — код маршалинга. Стаб знает, как превратить аргументы в поток байт (Ndr — Network Data Representation) и обратно.

В бинарнике стабы видны как функции с вызовами `NdrClientCall*` (клиент) и `NdrServerCall*` (сервер), а также структуры-описатели форматов (`MIDL_STUB_DESC`, `MIDL_SERVER_INFO`). Если у тебя есть IDL — сигнатуры известны; если нет, их восстанавливают по структурам формата.

Практический приём: найти `RpcServerRegisterIf` — её аргумент указывает на `RPC_SERVER_INTERFACE`, внутри которого лежит `MIDL_SERVER_INFO` с таблицей методов (`DispatchTable`). По ней видны смещения обработчиков.

## Шаг 4: восстановление сигнатур методов

Таблица `DispatchTable` — массив указателей на функции-обработчики. Порядок соответствует порядку методов в интерфейсе (обычно по алфавиту для COM). Зная обработчик, ты дизассемблируешь его и смотришь, как он читает аргументы: через `NdrServerCall2` они приходят в формате NDR.

Если IDL нет, можно восстановить сигнатуру по обращениям к полям входной структуры и по типам, которые передаются в `RpcStringBindingCompose`/`Ndr`-функции. Иногда в бинарнике остаются строки форматов NDR (`%s`, размеры) — они подсказывают типы.

## Шаг 5: находим уязвимость

Уязвимость в RPC-сервисе обычно — это обработчик, который доверяет входным данным. Классические ошибки: отсутствие проверки длины строки (переполнение буфера), передача указателя на функцию извне (произвольный вызов), некорректная проверка прав.

Для реверса: смотри обработчики, которые копируют входные данные в фиксированный буфер (`strcpy`, `memcpy` с длиной из входа), открывают файлы по пути из аргумента (path traversal), или вызывают `CreateProcess`/`WinExec` с непроверенной строкой. Это и есть цели для эксплуатации.

## Шаг 6: находим артефакт практики

Среди строк сервера — артефакт. Достанем его:

```
$ strings -n 5 rpcserver.exe | grep nto
nto{rpc_m1dl_stub_1nt3rf4c3}
```

## Что мы теперь знаем

- COM/DCOM/RPC: интерфейсы адресуются UUID; DCOM маршалит вызовы по сети.
- Интерфейсы находятся по строкам UUID и вызовам `RpcServerRegisterIf`.
- MIDL генерирует стабы маршалинга (Ndr); в бинарнике — `MIDL_SERVER_INFO` и `DispatchTable`.
- Сигнатуры методов восстанавливаются по обработчикам и форматам NDR.
- Уязвимости — в обработчиках, доверяющих входу: переполнения, path traversal, запуск процессов.

## Как восстановить интерфейс без IDL

Если IDL-файла нет, интерфейс восстанавливают по структурам. Точка входа — `RpcServerRegisterIf`
(или `RpcServerRegisterIfEx`): её аргумент указывает на `RPC_SERVER_INTERFACE`, внутри которого
лежит `MIDL_SERVER_INFO`. В нём есть `DispatchTable` — массив указателей на обработчики, в
порядке методов интерфейса (обычно по алфавиту для COM). Пройдя по таблице, ты получаешь адреса
всех методов и можешь их дизассемблировать.

Дополнительно `RpcServerRegisterIf` регистрирует UUID и версию — их видно как структуру
`RPC_SYNTAX_IDENTIFIER`. Сопоставив UUID со строкой в бинарнике, ты подтверждаешь интерфейс.

## Почему DCOM — вектор атаки

DCOM позволяет вызывать методы объекта на удалённой машине. Если метод принимает путь к файлу
или команду, а сервис работает под SYSTEM, удалённый вызов становится удалённым выполнением
кода. Классические уязвимости DCOM (например, в служебных интерфейсах Windows) строились
именно так. Для реверса: ищи методы, которые делают `CreateProcess`, `ShellExecute`, `MoveFile`
с непроверенным входом.

## Частые ошибки

- Искать интерфейсы только по строкам и пропустить UUID без имени.
- Путать клиентские стабы (`NdrClientCall`) и серверные (`NdrServerCall`).
- Не учесть, что `DispatchTable` может быть не в порядке объявления.
- Принять обычную функцию за RPC-обработчик.
- Игнорировать проверки прав (`RpcServerRegisterIfEx` с security callback).

## Чек-лист

1. `strings` — UUID и имена методов.
2. Найди `RpcServerRegisterIf` и структуру интерфейса.
3. Разбери `MIDL_SERVER_INFO.DispatchTable`.
4. Дизассемблируй обработчики, проверь доверие к входу.
5. Для вызова — сгенерируй IDL или используй `RpcView`/`RpcInvestigator`.

## Разбор реального примера: от UUID до метода

Разберём поиск метода по UUID. Сначала строки:

```
$ strings -n 6 rpcserver.exe | grep -iE 'uuid|[0-9a-f]{8}-'
8a7c1d40-9e2b-4f3a-b1c5-7d6e8f9a0b12
IComputeService
ComputeHash
GetStatus
```

UUID `8a7c1d40-...` — идентификатор интерфейса. Теперь найдём регистрацию. Дизассемблируем
`main`/`wmain` и ищем вызов `RpcServerRegisterIf`:

```
$ objdump -d rpcserver.exe | grep -B6 -A2 'RpcServerRegisterIf'
 140001020:  lea     rcx,[rip+0x2f19]   ; rcx = &RPC_SERVER_INTERFACE
 140001027:  xor     edx,edx
 140001029:  xor     r8d,r8d
 14000102c:  call    QWORD PTR [rip+...]  ; RpcServerRegisterIf
```

Первый аргумент (`rcx`) указывает на `RPC_SERVER_INTERFACE`. Внутри него лежит
`MIDL_SERVER_INFO`, а в нём — `DispatchTable` с указателями на обработчики. Дамп по этому
адресу даёт таблицу методов в порядке объявления (для COM — обычно по алфавиту: `ComputeHash`
перед `GetStatus`).

Дизассемблируем первый обработчик и смотрим, как он читает вход. Если он делает `memcpy` с
длиной из входного буфера без проверки — это цель для эксплуатации.

## Почему это поверхность атаки

RPC-сервис, работающий под SYSTEM, принимает вызовы от непривилегированных пользователей.
Если обработчик доверяет входу (путь, команда, длина), атакующий получает выполнение кода с
высокими правами. Именно так строились многие известные уязвимости Windows (например, в
служебных RPC-интерфейсах). Для реверса: ищи методы, которые вызывают `CreateProcess`,
`ShellExecute`, `CopyFile` с непроверенным входом.

## Сравнение с прямым вызовом функций

Обычную функцию нельзя вызвать удалённо — нужен контекст процесса. RPC/DCOM даёт «мост»: клиент
передаёт аргументы по сети, сервер маршалит их в вызов. Для атакующего это означает: не нужно
иметь код в процессе — достаточно иметь доступ к интерфейсу. Поэтому RPC-поверхность часто
шире, чем кажется по одному бинарнику.

## Инструменты для RPC-анализа

`RpcView` и `RpcInvestigator` перечисляют RPC-интерфейсы, зарегистрированные в системе, вместе с
UUID, версиями и адресами обработчиков в памяти. Это быстрее, чем разбирать бинарник вручную:
инструмент читает структуры из работающего процесса. `RpcView` показывает и клиентские, и
серверные интерфейсы, а также может вызывать методы.

Для статического анализа — `midl` (компилятор IDL) и `rpcndr`. Если у тебя есть IDL, компиляция
даст стабы, которые можно сопоставить с бинарником. Если нет — восстановление через
`DispatchTable`, как мы разбирали.

## Проверка достижимости интерфейса

Не каждый RPC-интерфейс достижим удалённо или от непривилегированного пользователя. Проверяй:
привязку (endpoint) — `RpcServerUseProtseqEp`; права доступа — security callback в
`RpcServerRegisterIfEx`; сетевой транспорт — `ncacn_ip_tcp` доступен по сети, `ncalrpc` — только
локально. Для удалённой атаки нужен сетевой протокол и разрешение доступа.

## Сравнение с прямым DCOM-вызовом

DCOM-клиент вызывает `CoCreateInstance` с UUID и получает интерфейс — код может быть на другой
машине. Для атакующего это означает возможность вызвать метод без кода в целевом процессе.
Инструменты вроде `impacket` реализуют DCOM-вызовы на Python, что удобно для эксплуатации без
своей программы.

## Итоговая стратегия анализа

Порядок: `strings` (UUID и имена), поиск `RpcServerRegisterIf`, разбор `MIDL_SERVER_INFO` и
`DispatchTable`, дизассемблирование обработчиков, проверка доверия к входу, проверка
достижимости (endpoint + права). Если есть IDL — компилируй его и сопоставляй стабы. Если нет —
восстанавливай по таблице методов. Для эксплуатации используй `impacket` (DCOM) или свой клиент
по IDL. Держи в голове, что поверхность RPC шире одного бинарника: интерфейсы могут
регистрироваться динамически.

## Итог

COM/RPC/DCOM — это «второй слой» Windows, где живёт большинство сетевых и локальных атак.
Интерфейсы адресуются UUID, методы описаны в IDL, а MIDL генерирует стабы маршалинга. В
бинарнике ты находишь `RpcServerRegisterIf`, разбираешь `DispatchTable` и получаешь адреса
обработчиков. Дальше — обычный реверс: ищи методы, доверяющие входу. Инструменты вроде RpcView
ускоряют картирование. Освоив этот слой, ты видишь поверхность атаки, невидимую при анализе
одного PE-файла.
