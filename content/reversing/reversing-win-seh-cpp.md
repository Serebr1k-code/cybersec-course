## Вопрос, с которого всё начинается

В дизассемблере C++-бинарника ты видишь `catch`-блоки, вызовы `__CxxThrowException` и странные таблицы, на которые никто явно не ссылается. Это обработка исключений — но зачем она в малвари и как её читать?

## Наш пример

У нас есть дамп секции данных `classes.bin` с типами и виртуальными таблицами. Нужно восстановить, какие классы есть в бинарнике и какие методы у них вызываются. Это ключ к пониманию логики объектно-ориентированного импланта.

## Шаг 1: что такое SEH

**SEH** (Structured Exception Handling) — механизм Windows для обработки исключений (деления на ноль, access violation, `int3`). Исторически он работал через список обработчиков, привязанный к стеку потока. В x64 Windows отказалась от стекового списка и перешла на **таблицы** — их описывает сам PE-образ.

Для нас важно: SEH используется и для защиты, и для анти-отладки. Малварь ставит свой обработчик, чтобы перехватить исключение от анти-отладочной проверки и продолжить работу, будто всё в порядке.

## Шаг 2: C++-исключения на Windows

C++ `throw`/`catch` на Windows построены поверх SEH. Когда ты пишешь `throw std::runtime_error(...)`, компилятор:

1. создаёт объект исключения в памяти;
2. вызывает `__CxxThrowException`, передавая указатели на объект и на **тип-дескриптор** (`ThrowInfo`);
3. раскручивает стек (**unwind**), находя подходящий `catch` по таблицам.

Эти таблицы (`.pdata`, `.xdata`) лежат в PE и описывают, как для каждого участка кода раскручивать стек. Дизассемблер показывает их как данные — но именно они связывают `throw` и `catch`.

## Шаг 3: RTTI и имена классов

C++ умеет во время выполнения определять тип объекта — это **RTTI** (Run-Time Type Information). Для класса компилятор генерирует:

- **type_info** — дескриптор типа с именем;
- **RTTI Complete Object Locator** — структуру, связывающую vtable с типом;
- саму **vtable** — массив указателей на виртуальные методы.

Имя класса в MSVC-мангинге выглядит как `. ?AVClassName@@` (`.?AV` = класс, `@@` = конец). Именно по этим строкам в бинарнике находят классы, когда символов нет:

```bash
$ strings -n 6 classes.bin | grep '?AV'
.?AVC2Channel@@
.?AVCryptoContext@@
.?AVnto{rtt1_vt4bl3_cl4ss_r3c0v3ry}@@
```

Даже в обфусцированном импланте имена классов часто остаются — их забывают вычистить.

## Шаг 4: разбор vtable скриптом

vtable — массив адресов методов. Нулевой слот обычно указывает на деструктор, дальше — виртуальные методы в порядке объявления. Скрипт `parse_rtti.py` находит RTTI-локаторы, восстанавливает имена классов и перечисляет методы:

```bash
$ python3 parse_rtti.py classes.bin
class C2Channel  @ 0x180012340  vtable=0x180020000
  [0] 0x180001010  ~C2Channel
  [1] 0x1800010a0  Connect
  [2] 0x180001150  Send
class CryptoContext  vtable=0x180020080
  [1] 0x1800012c0  Encrypt  (AES-256-CBC)
  [2] 0x1800013a0  Decrypt
```

Теперь видно, что имплант состоит из канала C2 и криптоконтекста — а не из абстрактных «функций».

## Шаг 5: зачем это в реверсе

Восстановив классы и vtable, ты получаешь **карту объектов** вместо плоского списка функций:

- видно, какие объекты создаются (`new`/конструкторы);
- видно, какие методы вызываются через vtable (косвенные вызовы `call [rax+8]` — это вызов виртуального метода);
- видно иерархию (наследование) — по вложенным RTTI.

Косвенный вызов `call qword ptr [rax+8]` расшифровывается так: `rax` — указатель на объект, первые 8 байт — vtable, `+8` — второй слот (первый виртуальный метод). Без восстановления vtable такой вызов выглядит как «прыжок в никуда».

## Шаг 6: anti-analysis через исключения

Продвинутая малварь злоупотребляет исключениями:

- **`int3` как точка перехода** — обработчик решает, куда идти; статически поток не виден.
- **`throw` для управления потоком** — вместо `goto` бросается исключение, `catch` продолжает логику. Декомпилятор показывает это как странный `try`.
- **SEH-обход анти-отладки** — исключение от проверки ловится и «глотается».

Когда видишь `__CxxThrowException` без очевидного `throw` в исходной логике — это почти всегда обфускация потока управления.

## Что мы теперь знаем

- SEH на x64 работает через таблицы PE (`.pdata`/`.xdata`).
- C++-исключения построены поверх SEH (`__CxxThrowException` + unwind).
- RTTI даёт имена классов (`.?AV...@@`), vtable — адреса методов.
- Косвенный вызов `call [rax+N]` — вызов виртуального метода.
- Исключения используют как anti-analysis и для обфускации потока.

## Шаг 7: unwind-данные в PE на практике

Таблицы раскрутки лежат в секции `.pdata` (x64). Каждая запись — `RUNTIME_FUNCTION`: три поля — начало функции, конец и указатель на unwind-информацию. По ним система понимает, как для любого адреса внутри функции восстановить стек.

```bash
$ python3 dump_pdata.py target.exe
RUNTIME_FUNCTION 0x1000..0x10a0  unwind=0x3000
  chained: 0x1040..0x1080        unwind=0x3020
```

Если в функции есть C++-объекты с деструкторами, unwind-информация описывает, что вызывать при раскрутке. Дизассемблер показывает это как вызовы `__CxxFrameHandler` — и именно сюда смотрит аналитик, чтобы понять порядок очистки.

## Шаг 8: восстановление catch-блоков

Связь `throw` и `catch` задаётся не потоком инструкций, а таблицами. При `throw` система идёт по стеку вверх, и для каждого кадра смотрит, есть ли обработчик, принимающий этот тип. Тип сверяется по RTTI.

Значит, чтобы понять, какой `catch` поймает исключение, нужно:

1. найти `throw` и его тип (по `ThrowInfo`);
2. пройти по кадрам вверх;
3. найти кадр с `catch` этого типа.

Статически это выглядит как данные, на которые нет прямых `call`. Поэтому декомпилятор часто показывает «мёртвый» код в обработчиках — на самом деле он вызывается только при исключении.

## Шаг 9: vtable и наследование

Восстановив vtable одного класса, можно подняться к родителю: первый слот `class_t`-подобной структуры часто указывает на RTTI-локатор, а в нём — ссылка на базовый класс. Так строится иерархия.

```bash
$ python3 parse_rtti.py classes.bin --tree
C2Channel
  └─ BaseChannel
       └─ Object
CryptoContext
  └─ Object
```

Иерархия важна: методы базового класса вызываются у наследника, и без неё легко потерять половину логики.

## Шаг 10: anti-analysis через `int3`

Продвинутый трюк — использовать `int3` (`0xCC`) не как точку останова, а как **прыжок**: обработчик исключения меняет `RIP` и продолжает в другом месте. Статически поток обрывается на `int3`, а реальный путь не виден.

Признаки:

- `int3` посреди кода, не в конце функции;
- обработчик, который меняет контекст (`RIP` в `EXCEPTION_RECORD`);
- таблицы, указывающие на «данные», которые на деле — код.

Обход — динамический: пройти под отладчиком и записать реальный поток.

## Шаг 11: таблица: что где искать

| Артефакт | Секция/структура | Что даёт |
|---|---|---|
| RUNTIME_FUNCTION | `.pdata` | границы функций, unwind |
| UNWIND_INFO | `.xdata` | как раскручивать стек |
| ThrowInfo | `.rdata` | тип и деструктор исключения |
| RTTI-локатор | `.rdata` | имя класса, база |
| vtable | `.rdata` | адреса виртуальных методов |

## Шаг 12: решение и следующий шаг

Собрав RTTI, vtable и unwind-таблицы, ты получаешь объектную модель бинарника: классы, методы, иерархию и места, где ловится исключение. Это превращает анализ большого C++-импланта из «каши» в структуру. Дальше логично перейти к драйверам: там те же принципы, но на уровне ядра — IRP, диспетчеры и IOCTL.

## Шаг 13: RTTI в статике без символов

Даже когда символов нет, имена классов часто остаются строками. Найди их и пойми, что за объекты в бинарнике:

```bash
$ strings -n 6 target.exe | grep '?AV'
.?AVC2Channel@@
.?AVCryptoContext@@
.?AVLogger@@
```

Каждому имени соответствует RTTI-локатор, а локатору — vtable. Связь ищется по указателям: локатор содержит указатель на `type_info`, в котором лежит строка имени. Пройдя от строки к локатору к vtable, ты получаешь методы класса.

## Шаг 14: декомпилятор и исключения

Декомпилятор показывает исключения не всегда корректно. `try`/`catch` в псевдокоде может выглядеть как отдельная функция-обработчик, вызванная из ниоткуда. Это потому, что связь идёт через таблицы, а не через вызовы. Если видишь функцию, которую никто не вызывает, но которая лежит рядом с `__CxxFrameHandler` — вероятно, это `catch`-блок.

Полезно: в IDA включить показ `EH`-таблиц, в Ghidra — смотреть `catch` через `Analysis > Exception Handlers`.

## Шаг 15: практический пример разбора

Пусть есть функция, которая «не вызывается». Смотрим её: она принимает указатель на исключение, читает поле типа, сравнивает с RTTI и делает что-то. Значит, это обработчик `catch (SomeType& e)`. Находим `throw` этого типа (по `ThrowInfo`) — и восстанавливаем поток: «при ошибке X ловится исключение Y и делается Z».

Так исключения, которые декомпилятор показал как «мёртвый код», превращаются в понятную логику обработки ошибок.

## Шаг 16: vtable и динамические вызовы

Косвенные вызовы `call [reg+offset]` — сердце ООП-кода. Чтобы их расшифровать, нужно знать, что лежит в `reg`. Это делается восстановлением vtable: если `reg` — объект класса `C2Channel`, то `[reg+0x10]` — третий метод его vtable.

Инструменты (IDA, Ghidra, BN) умеют это автоматически, когда распознают RTTI. Если нет — восстанови вручную: найди присваивание vtable объекту (обычно в конструкторе: `mov [rcx], offset vtable_C2Channel`) и сопоставь слоты.

## Шаг 17: итоговый чек-лист

- `.pdata`/`.xdata` — unwind-таблицы, границы функций.
- `ThrowInfo` — тип и деструктор исключения.
- `. ?AV...@@` — имена классов (RTTI).
- `call [rax+N]` — виртуальный вызов, N = слот vtable.
- `__CxxThrowException` вне очевидного `throw` — обфускация потока.

Главное: **в C++ поток управления живёт не только в инструкциях, но и в таблицах — RTTI и unwind**.
