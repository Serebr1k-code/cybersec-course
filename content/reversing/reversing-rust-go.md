## Задача

Современное ПО всё чаще пишут на **Go** и **Rust** — на этих языках собраны CLI-утилиты,
сервисы и даже malware (ради обхода сигнатур). Обычный дизассемблер без подготовки тонет в
«мусоре» из стандартной библиотеки и рантайма. Нужно уметь **опознать язык**, **восстановить
имена функций** и найти свою логику среди тысяч чужих.

У нас два бинарника: `gocheck` и `rustcheck`. Оба просят ключ. Разберём каждый.

## Данные: что это за файлы

```bash
$ file gocheck
gocheck: ELF 64-bit LSB executable, x86-64, ... statically linked, Go BuildID=uchGxYErs4...

$ file rustcheck
rustcheck: ELF 64-bit LSB pie executable, x86-64, ... dynamically linked, ...
```

Уже видно различие: `gocheck` **статически слинкован** и несёт `Go BuildID` — это Go.
`rustcheck` — обычный динамический PIE, без явных маркеров, но его выдадут символы.

## Go: версия, символы, pclntab

Go-бинарники обычно не стриппятся полностью: в секции `pclntab` лежит таблица с именами
функций. Версию узнаём одной командой:

```bash
$ go version ./gocheck
./gocheck: go1.26.1
```

Список символов даёт `go tool nm` — это «родной» `nm` для Go:

```bash
$ go tool nm gocheck | grep -E ' main\.'
  4a0000 T main.main
```

Интересно: видна только `main.main`. Куда делась функция проверки? Её **заинлайнил**
компилятор — то есть тело `check` целиком вставили внутрь `main.main`. Это важная
особенность Go: агрессивный инлайнинг «съедает» маленькие функции.

Смотрим строки — маркер «успеха» и «провала»:

```bash
$ strings -a gocheck | grep -iE 'granted|denied|key:'
key: ...Access granted...Denied
```

## Go: разбираем main.main

Дизассемблируем `main.main` и ищем проверку длины:

```bash
$ objdump -d --no-show-raw-insn gocheck | sed -n '/<main.main>:/,/ret/p' | grep -iE 'cmp|xor|jne'
  4a0165:	cmp    $0xa,%rbx           # длина ввода == 10 ?
  4a0169:	jne    4a0188 <main.main+0x188>
  4a0181:	xor    %ecx,%ecx
  4a0188:	xor    %eax,%eax
  4a018c:	je     4a01c8 <main.main+0x1c8>
```

Проверка длины `10` (0xa) прямо в `main.main` — подтверждение инлайнинга. А дальше
встречается `xor` — значит, байты ввода XOR-ятся и сравниваются с таблицей (как в обычном
C-криптме). Восстановив таблицу и ключ XOR, получаем ключ `u~ss`tyuav`:

```bash
$ printf 'u~ss`tyuav\n' | ./gocheck
key: Access granted
```

**Важный нюанс Go:** строки здесь — не C-строки с `\0`, а структура `{указатель, длина}`.
В дизассемблере это два подряд идущих значения; сравнение длин (`cmp $0xa`) — как раз работа
с полем длины.

## Rust: mangling и деманглинг

Rust кодирует имена функций в mangled-вид. Посмотрим символы:

```bash
$ nm rustcheck | grep rustcheck
00000000000152c0 t _ZN9rustcheck4main17hf001655a1c6cdc41E
```

Деманглируем (стандартный инструмент — `rustfilt`; классическую схему `_ZN...E` понимает и
`c++filt`):

```bash
$ echo '_ZN9rustcheck4main17hf001655a1c6cdc41E' | c++filt
rustcheck::main::hf001655a1c6cdc41
```

Вот и `rustcheck::main`. Функция `check` тоже не видна отдельно — Rust, как и Go, заинлайнил
её. Ускорить сопоставление помогают **строки паник** — они отмечают места проверок:

```bash
$ strings -a rustcheck | grep -iE 'unwrap|panic|index out of bounds'
called `Result::unwrap()` on an `Err` value
index out of bounds: the len is
```

Каждый `unwrap()` — потенциальное место, где ожидается корректное значение; `index out of
bounds` указывает на работу с массивом. Найдя строку паники, через перекрёстные ссылки (xref)
выходишь на условие, которое нужно удовлетворить.

Проверяем восстановленный ключ:

```bash
$ printf 're}|okqc\n' | ./rustcheck
Enter: OK
```

## Ключевые особенности и инструменты

| Особенность | Go | Rust |
|---|---|---|
| Линковка | статическая (std внутри) | обычно динамическая |
| Имена | `pclntab` → GoReSym/redress | mangling → rustfilt |
| Дженерики | — | мономорфизация |
| Рантайм | goroutines, GC | без GC, но std большой |
| Строки | `{ptr,len}` | обычные срез-структуры |

- **Go:** `redress info/funcs/types`, `GoReSym` (восстанавливает имена из `pclntab` даже
  после стриппинга), плагин `golang_loader_assist` для IDA.
- **Rust:** `rustfilt`, плагины деманглинга для Ghidra/IDA, `RUST_BACKTRACE=1` при запуске —
  имена функций появятся прямо в стеке.

**Мономорфизация** (Rust): дженерики разворачиваются в отдельные функции под каждый тип.
`Vec<u8>::push` и `Vec<i32>::push` — **разные** символы. Ищите свой тип/модуль (`myapp::`),
остальное — стандартная библиотека.

Ещё одно отличие — **ABI**. Rust использует стандартный System V ABI (аргументы в регистрах),
как C, поэтому его функции читаются привычно. Go исторически передаёт аргументы и результаты
частично через стек (регистровый ABI появился позже), поэтому в дизассемблере вызовы Go
выглядят непривычно: не удивляйся, что аргумент «не в том» регистре.

## Go: типы, интерфейсы и горутины

Go хранит метаданные о типах (`runtime._type`, `runtime.itab`), поэтому структуры можно
восстанавливать. Полезные раскладки, которые надо держать в голове при чтении дизассемблера:

- **Срез** — `{ptr, len, cap}` (три слова).
- **Интерфейс** — пара `(itab, data)`; `itab` содержит тип и таблицу методов.
- **Мапа** — `runtime.hmap`.

Инструмент `redress` выводит определения напрямую:

```bash
$ redress types ./gobin | head
$ redress funcs ./gobin | grep -iE 'runtime\.(newproc|goexit|chansend)'
```

**Горутины** — это легковесные потоки Go. Они создаются вызовом `runtime.newproc`, а каналы
работают через `runtime.chansend`/`chanrecv`. Если `main.main` запускает горутину, которая и
делает проверку, статический анализ `main` её не покажет — иди по `newproc` к целевой функции.

## Rust: обработка ошибок как карта логики

Rust-код пронизан `Result`/`Option`, и паники отмечают границы проверок. Каждый `unwrap()` —
потенциальное место, где ожидается корректное значение; `assert!`/`assert_eq!` — явные
проверки. Сопоставив строку паники с функцией через xref, ты быстро находишь условие,
которое нужно удовлетворить для «успеха»:

```bash
$ strings -a ./rustbin | grep -iE 'assert|unwrap|expect'
```

## Если не сработало

- **Слишком много кода** — не анализируйте std целиком; фильтруйте по `main`/своему модулю.
- **Stripped Go** — часть метаданных теряется, но `GoReSym` всё ещё работает по `pclntab`.
- **Stripped Rust** — имён нет; ориентируйтесь на паники, строки и размеры функций.
- **Функция «пропала»** — вероятно, заинлайнена в вызывающую; ищите её тело внутри `main`.
- **Goroutines** — если `main` запускает горутину (`runtime.newproc`), проверка может быть в
  ней, а не в `main.main`; идите по вызову.

## Что мы теперь знаем

- Go-бинарник опознаётся по `Go BuildID`, статической линковке и секции `pclntab`.
- Rust-бинарник выдаёт себя mangled-именами (`_ZN...`/`_R...`); их деманглит `rustfilt`/`c++filt`.
- Оба языка агрессивно инлайнят мелкие функции — проверка часто внутри `main`.
- Go-строки — пары `{указатель, длина}`; Rust-паники (`unwrap`, `index out of bounds`)
  отмечают проверки.

## Stripped Go: как вернуть имена

Если Go-бинарь застриплен (`-ldflags "-s -w"`), `go tool nm` пуст, но секция **`pclntab`** часто остаётся. Её разбирают специализированные инструменты:

```bash
$ GoReSym -t -d ./stripped_go     # восстановит имена функций и типов
$ redress info ./stripped_go      # версия Go, buildinfo
$ redress funcs ./stripped_go | grep -i 'main\.'
```

`pclntab` хранит отображение «адрес → имя функции», поэтому имена восстанавливаются даже без символов ELF. Если и её вырезали, ориентируются на `buildinfo` (в нём может быть список модулей и версий) и на строки в `.rodata`.

## Rust: типичная проверка ключа

Rust-криптме обычно выглядит так: ввод собирают в `Vec<u8>`, прогоняют через цикл и сравнивают с константным массивом. Компилятор часто разворачивает цикл, и в дизассемблере видна длинная серия `cmp`/`xor`. Искать полезно по:

- строке паники `assertion failed` рядом с проверкой;
- массиву констант в `.rodata` (целевой шифротекст);
- вызову `core::slice::index` (индексация с проверкой границ).

Восстановив константы и операцию (XOR, add, rotate), обращаем её и получаем ключ.

## Инструменты: что для чего

| Задача | Go | Rust |
|---|---|---|
| Версия | `go version ./bin`, `redress info` | `strings \| grep rustc` |
| Имена | `go tool nm`, GoReSym | `nm` + `rustfilt` |
| Типы | `redress types` | деманглинг + плагин Ghidra |
| Debug-имена в стеке | не нужен | `RUST_BACKTRACE=1` |
| Плагин IDA | `golang_loader_assist` | `rust-demangle` |

Общее правило: сначала опознай язык, затем достань имена штатным для языка инструментом, и только потом ищи свою логику среди стандартной библиотеки.

## Опознание языка за 30 секунд

Прежде чем звать инструменты, полезно за минуту понять, что за бинарь. Порядок быстрых проверок: `file` — покажет `Go BuildID` и статическую линковку; `strings | grep -E 'rustc|go1\.|panic'` — версия Go или следы Rust; `nm` — mangled-имена `_ZN...`/`_R...` выдают Rust; `readelf -S | grep -E 'gopclntab|\.gopclntab'` — секция `pclntab` подтверждает Go. Если ни Go, ни Rust не найдены, а функции большие и «пахнут» рантаймом, проверь `strings` на `RuntimeError`/`CPython` — возможно, это PyInstaller. Тридцать секунд такой разведки экономят час попыток применить не тот инструмент.

## Куда дальше

Мы научились опознавать Go/Rust и доставать имена. Но бывает, что перед нами вообще не
приложение, а **прошивка** — образ устройства, внутри которого файловая система и десятки
бинарников. В следующем уроке мы возьмём firmware-образ и распакуем его. А пока главное
запомни: **Go выдаёт себя `pclntab`, Rust — mangled-именами; оба любят инлайнить.**

## Где пригодится

- **CTF Reversing (hard):** Go/Rust-задачи требуют специфичных инструментов.
- **Malware analysis:** современные RAT/ransomware на Go/Rust обходят сигнатуры; нужны Go-плагины.
- **Аудит современного ПО:** CLI-утилиты и сервисы на Rust/Go — частый объект анализа.
- **Bug bounty:** поиск логических багов в Go/Rust-сервисах.
- **Собес:** Go-символы, Rust demangling, мономорфизация — маркер современного RE.
