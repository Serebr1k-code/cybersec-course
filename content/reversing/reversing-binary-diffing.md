**Бинарный диффинг** — это сравнение двух версий бинарника (до/после патча) для поиска изменений: какие функции поменялись, что именно исправили, где новая логика. Ключевой приём для анализа security-патчей (по фиксу находят уязвимость), для reverse engineering обновлений, для поиска бэкдоров в обновлении и для восстановления логики по «до/после». Урок даёт полный workflow: инструменты (Diaphora, BinDiff, bindiff-подход), пошаговый разбор патча, техники нормализации и полный разобранный пример «найти фикс CVE».

## Зачем диффить бинарники

- **Поиск уязвимости по патчу.** Security-фикс локализует баг: diff показывает, что именно изменили, а из изменения восстанавливается уязвимость (часто это `>=` вместо `>`, добавленная проверка границ и т.п.).
- **Анализ обновлений.** Что изменилось в новой версии прошивки/приложения, не появилось ли бэкдора.
- **Восстановление логики.** Если у вас есть две версии — по разнице понять назначение функций.
- **Проверка «дешифрованности».** Diff патченного и оригинального crackme.
- **Malware.** Мутации семейства: какие функции изменились между образцами.

## Подходы к диффингу

| Подход | Уровень | Устойчивость | Инструмент |
|---|---|---|---|
| Байтовый | raw bytes | низкая | `cmp`, `bsdiff` |
| Хеш-блоков | базовые блоки | средняя | BinDiff, Diaphora |
| Граф-структурный | CFG функций | высокая | Diaphora, BinDiff |
| Символический | семантика | высшая | binsec, angr-diff |
| Секционный | секции/строки | низкая | `diff` по дампам |

Байтовый diff ломается от смены адресов и перестановок; граф-структурный (CFG) — самый практичный, он сопоставляет функции по форме, а не по адресам.

## Инструменты

- **Diaphora** — плагин для IDA/Ghidra, открытый, мощный; сопоставляет функции по псевдокоду, CFG, константам.
- **BinDiff** — плагин (Google), классика; эффективен, но требует IDA/Binary Ninja.
- **radiff2** — из radare2; `radiff2 -g` для графов, `-C` для сопоставления.
- **bsdiff** — патчи; `bsdiff old new patch`.
- **diaphora / bindiff** в Ghidra — версия для бесплатного инструмента.

```bash
# radiff2: базовая сводка различий
radiff2 -s old.bin new.bin          # расстояния/хеши
radiff2 -C old.bin new.bin          # сопоставление функций
radiff2 -g main old.bin new.bin | xdot -   # граф-диff конкретной функции
```

## Diaphora: пошаговый workflow

**Шаг 1. Экспорт БД для старой версии.**

```bash
# в IDA: File -> Script file -> diaphora.py -> "Export to SQLite database"
# сохранит old.sqlite
```

**Шаг 2. Экспорт для новой версии** (то же → `new.sqlite`).

**Шаг 3. Diff.** В IDA на новой версии: `diaphora.py` → «Diff database» → выбрать `old.sqlite`. Результат — список: **identical**, **changed**, **new**, **deleted** функций.

**Шаг 4. Анализ changed.** Отсортировать по «ratio» и открыть псевдокод side-by-side.

## Разобранный пример: найти фикс CVE

Дано: версия 1.0 уязвима, 1.1 исправлена. Нужно понять уязвимость.

**Шаг 1. Диффинг (Diaphora/BinDiff).** Видим 3 изменённые функции; одна — `parse_header`.

**Шаг 2. Сравнить псевдокод.**

```c
// v1.0 (уязвимая)
len = header->len;
memcpy(dst, header->data, len);        // нет проверки границ

// v1.1 (исправленная)
len = header->len;
if (len > MAX_LEN) return -1;          // <-- добавлена проверка
memcpy(dst, header->data, len);
```

**Шаг 3. Вывод.** Уязвимость — переполнение буфера в `parse_header` из-за непроверенной длины. Это ровно то, что даёт security-патч: **изменение указывает на баг**.

**Шаг 4. Проверка.** Собрать PoC-вход с `len > MAX_LEN` и запустить на v1.0 — краш/переполнение.

## Нормализация и устойчивость диффа

Диффинг ломается, если компилятор переставил код, изменил регистры, вставил padding. Приёмы повышения устойчивости:

- **Сопоставление по CFG** (форма графа), а не по адресам.
- **Нормализация инструкций** (игнор регистров/незначимых операндов).
- **Функциональные хеши** (константы, строки, вызовы).
- **Символический дифф** — сравнение семантики (angr) для устойчивости к перестановкам.
- **Секции/строки** — быстрый «грубый» сигнал изменений.

```bash
# строковый diff — быстрый поиск новых строк/URL/команд
diff <(strings -a old.bin) <(strings -a new.bin)
```

## Diff прошивок и больших образов

Для firmware/контейнеров полезна послойная дифф-техника: сравнить разделы/слои.

```bash
# побайтовый diff двух образов с адресами изменений
cmp -l old.bin new.bin | head
# diff извлечённых ФС
diff -r rootfs_old rootfs_new | head
# binwalk + diff разделов
```

## Символический диффинг (для стойкости)

Если бинарники сильно пересобраны, помогает символьное сравнение: для каждой пары функций проверяют эквивалентность выходов на наборе входов (angr `SimProcedure`, или binsec).

```python
# псевдо: сравнить две функции на случайных входах
import angr
p_old = angr.Project("old.bin", auto_load_libs=False)
p_new = angr.Project("new.bin", auto_load_libs=False)
# для N случайных входов: запустить обе, сравнить вывод/состояние
```

Это дорого, но устойчиво к перестановкам и смене регистров.

## Частые ошибки и подводные камни

- **Разные флаги компиляции.** Сборка с `-O0` vs `-O2` даёт «ложные» изменения; сравнивайте сопоставимые сборки.
- **Смена адресов/PIE.** Байтовый diff бесполезен; нужен граф-структурный.
- **Неверный выбор версий.** Diff «соседних» версий может не содержать целевого фикса — берите именно до/после патча.
- **Игнорирование удалённых функций.** Часто фикс — это **добавленная проверка** в существующей функции, а не новая функция.
- **Переобучение на «шум».** Различия в метаданных/выравнивании не несут смысла — фильтруйте.
- **Отсутствие контекста.** Без понимания назначения функции изменение не интерпретировать — читайте обе версии целиком.

## Что дальше / решение

Маршрут: **взять до/после → экспорт в Diaphora/BinDiff → найти changed-функции → сравнить псевдокод → из изменения восстановить уязвимость/логику → проверить PoC**. Для firmware — плюс послойный diff. Для стойкости — CFG/символический дифф. Дальше — `reversing-patching` (как применять патчи) и `reversing-analysis-methodology`.

## Diaphora в Ghidra: бесплатный путь

Если нет IDA Pro, Diaphora работает и в Ghidra. Workflow похож: экспорт БД для каждой версии и diff.

```bash
# Ghidra headless с Diaphora-скриптами
$GHIDRA_HOME/support/analyzeHeadless /tmp/proj p1 -import old.bin \
  -postScript diaphora_export.py
$GHIDRA_HOME/support/analyzeHeadless /tmp/proj p2 -import new.bin \
  -postScript diaphora_export.py
# затем в GUI: Diff -> выбрать old.sqlite
```

Результат группируется по категориям: `identical`, `changed` (с процентом совпадения), `new`, `deleted`. Первым делом смотрите `changed` с высоким «ratio» — там обычно и лежит фикс.

## Практика: найти изменение в условии

Самый частый security-фикс — добавленное/изменённое условие. В псевдокоде это видно сразу.

```c
// v1.0
if (idx > count) { ... }          // off-by-one

// v1.1
if (idx >= count) { ... }         // исправлено
```

Diff покажет изменение `>` на `>=` — и вы знаете, что уязвимость в граничном условии доступа к массиву. То же для проверок длины (`len > 256` → `len >= 256`), для `strcpy`→`strncpy`, для добавленного `if (p != NULL)` (устранение null-deref).

## Диффинг прошивок и определение версий

Для firmware полезна связка с распаковкой: диффим извлечённые ФС и бинарники.

```bash
binwalk -Me old.bin -C /tmp/old
binwalk -Me new.bin -C /tmp/new
diff -rq /tmp/old/_old.bin.extracted /tmp/new/_new.bin.extracted | head
# diff конкретного бинарника
radiff2 -C /tmp/old/.../httpd /tmp/new/.../httpd | head
```

Так находят изменённые компоненты и версии (строки `version 1.2.3` в бинарнике).

## Оценка значимости изменений

Не каждое изменение — уязвимость. Приоритизируйте:

- **Функции парсинга/декодирования** (ввод) — главные кандидаты.
- **Проверки границ/длин** — типовые фиксы переполнений.
- **Аутентификация/авторизация** — логические фиксы.
- **Криптография** — исправления слабых алгоритмов.
- **Новые функции** — иногда добавлен фикс-хелпер (например, безопасная копия).

Игнорируйте изменения в метаданных, выравнивании, незначащих строках.

## Автоматизация и отчётность

Для серии версий (прошивки 1.0…1.9) полезна автоматизация: скрипт прогоняет Diaphora для каждой пары, агрегирует changed-функции и строит отчёт.

```bash
for v in 1.0 1.1 1.2; do
  analyzeHeadless /tmp/p proj_$v -import fw_$v.bin -postScript diaphora_export.py
done
# затем сравнить попарно и выписать функции, менявшиеся чаще всего
```

Функции, которые менялись в нескольких релизах, — горячие кандидаты на уязвимости.

## Ограничения бинарного диффинга

- **Разные компиляторы/оптимизации** дают много ложных различий.
- **Инлайнинг/вынос функций** меняет граф — сопоставление затруднено.
- **Обфускация** (control-flow flattening) ломает CFG-сопоставление; нужна нормализация.
- **Стриппинг** убирает имена — сопоставление только по структуре.
- **Огромные образы** (прошивки) требуют много времени/памяти.

Для сложных случаев используйте символический диффинг (angr) или ручное сопоставление по строкам/константам.

## Диффинг в связке с символическим исполнением

Когда обычный дифф не даёт ясности (сильная пересборка), применяйте символьное сравнение: для пары функций проверяют, эквивалентны ли они семантически на множестве входов. Различие в семантике указывает на реальное изменение логики, а не на шум компилятора.

```python
import angr, random
old = angr.Project("old.bin", auto_load_libs=False)
new = angr.Project("new.bin", auto_load_libs=False)
# для каждой сопоставленной пары (addr_old, addr_new):
# запустить call_state с N случайными входами, сравнить результат/память
```

Это дороже по времени, но устойчиво к перестановкам регистров и инлайнингу — там, где граф-дифф бессилен.

## Практический чеклист бинарного диффинга

1. Убедиться, что версии сопоставимы (тот же компилятор/оптимизация, если возможно).
2. Экспортировать БД (Diaphora/BinDiff) для обеих.
3. Отфильтровать `changed` с высоким ratio, отсортировать по значимости.
4. Смотреть функции ввода (парсинг, декодирование, аутентификация) первыми.
5. Восстановить из изменения гипотезу уязвимости/логики.
6. Подтвердить PoC на уязвимой версии.
7. Для firmware — диффить извлечённые ФС и бинарники по компонентам.

## Где пригодится

- **CTF Reversing:** задачи «дано до и после — найди разницу».
- **Vuln research / bug bounty:** n-day анализ патчей Windows/Android/прошивок для восстановления CVE.
- **Malware analysis:** отслеживание эволюции образцов, поиск новых возможностей между версиями.
- **Пентест:** оценка, исправлена ли найденная уязвимость, поиск регрессий после апдейта.
- **Работа (threat intel):** patch-diffing как источник свежих уязвимостей до публикации PoC.
