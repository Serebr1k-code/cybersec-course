## Задача

У тебя есть **две версии** одной программы: `xorcheck` (v1) и `xorcheck_v2` (v2). Известно,
что v2 — это «пропатченная» сборка, но что именно изменили — не сказано. Нужно найти
различие и понять, к чему оно приводит.

Это и есть **бинарный диффинг** — сравнение двух бинарников. Он незаменим, когда нужно
восстановить уязвимость по security-патчу (изменение прямо указывает на баг), проследить
эволюцию malware или понять, что поменялось в обновлении.

## Пробуем в лоб: побайтовое сравнение

Самый простой способ — сравнить файлы байт за байтом (`cmp -l` показывает позицию и
отличающиеся байты в восьмеричном виде):

```bash
$ cmp -l xorcheck xorcheck_v2 | wc -l
1117
```

**1117 отличий.** Если бы мы пошли этим путём, мы бы утонули: большая часть различий — это
**шум**. Разные сборки дают разные BuildID, адреса символов, порядок в таблице строк, да и
имя исходного файла (`xorcheck.c` против `xorcheck_v2.c`) меняет длины строк. Убедимся:

```bash
$ readelf -n xorcheck    | grep Build
    Build ID: a7af2207b64021e0389085913396eaaa6ff4a6ba
$ readelf -n xorcheck_v2 | grep Build
    Build ID: eb23819e236a59a1f325070db59e79b1e8adc124
```

Вывод: **побайтовый diff бесполезен** для поиска смысла патча. Нужно сравнивать на уровне
кода и данных.

## Диффим код

Сравним дизассемблер обеих версий. `diff` по выводу `objdump` покажет реальные изменения
инструкций:

```bash
$ diff <(objdump -d --no-show-raw-insn xorcheck) \
       <(objdump -d --no-show-raw-insn xorcheck_v2)
2c2
< xorcheck:     file format elf64-x86-64
---
> xorcheck_v2:     file format elf64-x86-64
143c143
<   4011a9:	xor    $0x5a,%eax
---
>   4011a9:	xor    $0x5b,%eax
```

Вот оно. Среди шума — **ровно одна** изменённая инструкция: `xor $0x5a` стало `xor $0x5b`.
То есть в функции `check` изменили ключ XOR-шифрования.

## Диффим данные

Но код — не вся история. Таблица, с которой сравнивается ввод, лежит в секции `.rodata`.
Сравним её отдельно:

```bash
$ objdump -s -j .rodata xorcheck    | grep 402010
 402010 3b1c283e 112d0a3c 3a132c2e 1238112f  ;.(>.-.<:.,..8./
$ objdump -s -j .rodata xorcheck_v2 | grep 402010
 402010 3b1c283e 112d0a3c 3a132c2e 1238112e  ;.(>.-.<:.,..8./
```

Последний байт таблицы изменился: `2f` → `2e`. Значит, патч затронул **и код, и данные**.
Если бы мы диффили только дизассемблер, мы бы пропустили это изменение — классическая ошибка.

## Что это значит: восстанавливаем логику

Теперь понятно, что делает патч. Вспомним логику `check`: `in[i] ^ K == table[i]`, то есть
ключ = `table[i] ^ K`. В v1 было `K = 0x5a` и таблица с `2f` в конце; в v2 — `K = 0x5b`
и `2e`. Посчитаем правильные ключи для обеих версий:

```bash
$ python3 -c 'print(bytes(b^0x5a for b in bytes.fromhex("3b1c283e112d0a3c3a132c2e1238112f")))'
b'aFrdKwPf`IvtHbKu'
$ python3 -c 'print(bytes(b^0x5b for b in bytes.fromhex("3b1c283e112d0a3c3a132c2e1238112e")))'
b'`GseJvQgaHwuIcJu'
```

Проверим на v2:

```bash
$ printf '`GseJvQgaHwuIcJu\n' | ./xorcheck_v2
Enter key: Correct!
```

Диффинг дал нам не только «что изменилось», но и **новый ключ** — просто из сравнения двух
версий.

## Как это делают в реальной работе

На большом бинарнике глазами `diff` не наглядишь — инструкции переставлены, регистры
переименованы, функции заинлайнены. Поэтому используют **структурный** диффинг: функции
сопоставляются не по адресам, а по форме.

| Подход | Что сравнивает | Устойчивость |
|---|---|---|
| Байтовый (`cmp`, `bsdiff`) | сырые байты | низкая |
| Хеш-блоков | базовые блоки | средняя |
| Граф-структурный (CFG) | форму графа функции | высокая |
| Символический (angr) | семантику | высшая |

Инструменты:

- **Diaphora** — плагин для IDA/Ghidra: сопоставляет функции по псевдокоду, CFG и константам.
  Workflow: экспорт БД для старой версии → для новой → «Diff» → список `identical`/`changed`/`new`/`deleted`.
- **BinDiff** — классика от Google (нужен IDA/Binary Ninja).
- **radiff2** — из radare2: `radiff2 -C old new` сопоставляет функции, `radiff2 -g main old new`
  рисует граф-дифф конкретной функции.

Сначала смотрят `changed` с высоким «ratio» — там обычно и лежит фикс. Приоритет — функции
**ввода**: парсинг, декодирование, аутентификация.

## Типовой «след» патча

Самый частый security-фикс — добавленное или изменённое условие. В псевдокоде это видно сразу:

```c
// v1.0 (уязвимая)
if (idx > count) { ... }        // off-by-one: неверная граница

// v1.1 (исправленная)
if (idx >= count) { ... }       // граница исправлена
```

Изменение `>` на `>=` — и ты знаешь, что уязвимость в граничном условии доступа к массиву.
То же для `len > 256` → `len >= 256` (переполнение буфера), `strcpy` → `strncpy`, или
добавленного `if (p != NULL)` (устранение null-dereference).

## Диффинг прошивок и серий версий

Тот же приём масштабируется на большие образы. Для прошивок сначала распаковывают разделы,
затем сравнивают извлечённые файловые системы и отдельные бинарники:

```bash
$ diff -rq rootfs_old rootfs_new | head          # какие файлы вообще менялись
$ radiff2 -C old/httpd new/httpd | head          # сопоставление функций в httpd
$ diff <(strings -a old.bin) <(strings -a new.bin)   # новые строки/URL/команды
```

Быстрый «грубый» сигнал — сравнение строк: новые URL, команды или номера версий
(`version 1.2.3`) сразу указывают, что искать дальше. Если у тебя серия версий (1.0…1.9),
полезно автоматизировать: скрипт прогоняет диффинг попарно и агрегирует изменённые функции.
Функции, которые менялись **в нескольких релизах**, — горячие кандидаты на уязвимости.

## Если не сработало

- **Слишком много различий** — сборки несопоставимы (`-O0` против `-O2`). Берите близкие по
  оптимизации сборки, иначе «ложные» изменения перекроют настоящий фикс.
- **PIE/смена адресов** — байтовый diff мёртв; нужен граф-структурный (CFG).
- **Stripped-бинарник** — имён нет; сопоставляйте по ссылкам на строки и константам.
- **Пропустили изменение** — вы диффили только код; проверяйте также `.rodata`/`.data`
  (как мы нашли изменение таблицы).

## Что мы теперь знаем

- Бинарный диффинг ищет различие между версиями; побайтовый diff тонет в шуме метаданных.
- Сравнивать нужно **на уровне кода** (`diff` по `objdump`) и **данных** (секции `.rodata`).
- Структурный диффинг (Diaphora/BinDiff/radiff2) устойчив к перестановкам и инлайнингу.
- Из патча восстанавливается логика: мы вытащили новый ключ прямо из разницы версий.

## Практика: radiff2 и BinDiff по шагам

Консольный диффинг radare2 не требует графики и хорошо подходит для автоматизации:

```bash
$ radiff2 -C old.bin new.bin            # сопоставление функций (счёт similarity)
$ radiff2 -g main old.bin new.bin       # граф-дифф конкретной функции
$ radiff2 -A old.bin new.bin            # все отличия по адресам
```

Вывод `-C` — список совпавших функций с процентом схожести; смотрим на «почти совпавшие» (например, 0.95) — там обычно и спрятан фикс. BinDiff делает то же в GUI: экспорт из IDA/Binary Ninja, затем «Diff» и фильтр по `Changed`.

## Автоматизация серии версий

Если у тебя 1.0…1.9, попарный диффинг вручную не масштабируется. Скрипт агрегирует результаты:

```bash
for i in $(seq 1 8); do
  a=v$i.bin; b=v$((i+1)).bin
  radiff2 -C "$a" "$b" | grep -E '0\.9[0-9]|changed' >> changed.txt
done
sort changed.txt | uniq -c | sort -rn | head
```

Функции, которые «почти совпадали» в нескольких релизах подряд, — горячие кандидаты: их правили неоднократно, значит, там активная борьба с багами.

## Диффинг символов, импортов и строк

Не всё изменение видно в коде. Полезно отдельно сравнить метаданные:

```bash
$ diff <(readelf -sW old | awk '{print $8}') <(readelf -sW new | awk '{print $8}')
$ diff <(objdump -T old | awk '{print $NF}') <(objdump -T new | awk '{print $NF}')
$ diff <(strings -a old) <(strings -a new)
```

Новые импорты (например, `memcpy` вместо `strcpy`) прямо намекают на исправленный overflow; новые строки (сообщения об ошибке, URL) указывают на изменённую логику; новые символы — на добавленную функцию. Эти три команды часто дают ответ за секунды там, где полный структурный диффинг занял бы часы.

## Инструменты диффинга: что выбрать

Побайтовое сравнение (`cmp -l`, `xxd | diff`) годится только для крошечных образцов. В реальной работе используют специализированные утилиты:

| Инструмент | Что сравнивает | Когда полезен |
|---|---|---|
| `bindiff` | функции по сигнатурам | большие бинарники, стабильные версии |
| `radiff2 -C` | функции Radare2 | быстрый обзор, скриптуемость |
| `diaphora` | функции в IDA | графы, псевдокод |
| `ghidriff` | headless Ghidra | CI, пакетная обработка |
| `diffoscope` | файлы любых форматов | прошивки, архивы, ELF |

`radiff2 -C old new` печатает процент совпадения и список различающихся функций. `bindiff` даёт визуальную матрицу совпадений: одинаковые функции образуют диагональ, а «выбивающиеся» точки — это как раз патченные места. Именно они и являются целью: патч всегда указывает на баг.

## Диффинг, когда нет символов

В стрипнутых бинарниках имена функций отсутствуют, но диффинг всё равно работает по **структуре**: по количеству инструкций, вызываемым API и контрольному потоку. Алгоритмы вроде Diaphora сопоставляют функции по хэшу графа, а не по имени. На выходе вы получаете пары «была такая-то функция → стала такой-то», даже если обе безымянные. Дальше остаётся прочитать патченную функцию декомпилятором и понять условие, которое добавили.

Отдельный приём — **якорные строки**. Строки и константы (сообщения об ошибке, magic-числа, имена файлов) почти не меняются между версиями. Найдите строку рядом с местом патча — она подскажет семантику функции. Часто патч меняет одно сравнение (`jge` → `jg`) или добавляет проверку длины перед `memcpy`.

## Диффинг данных и восстановление логики

Патчи меняют не только код, но и **данные**: таблицы переходов, строки, ключи, конфигурацию. Сравнение секций `.rodata`/`.data` часто выявляет:

- новую строку-сообщение («invalid signature» вместо «ok»),
- изменённую таблицу (например, S-box или массив констант),
- добавленный байт-флаг, который отключает уязвимый режим.

Восстановление логики идёт от патча назад: если новая версия проверяет `len <= 64`, значит в старой `len` мог быть больше — и это переполнение. Если новая версия добавила проверку подписи перед использованием буфера, значит раньше буфер использовался без аутентификации. То есть диффинг — это не просто «увидеть разницу», а **прочитать намерение разработчика-фиксёра** и вывести из него условия эксплуатации.

## Ограничения и подводные камни

- **Перекомпиляция меняет всё.** Другой компилятор/флаги (`-O0` vs `-O2`) дают настолько разные бинарники, что побайтовый диф бесполезен — нужен семантический (по функциям).
- **Инлайнинг.** Патченная функция может быть «размазана» по вызывающим; тогда диф по функциям её не найдёт, а найдёт разницу в нескольких местах.
- **ASLR и рандомизация сборки.** PIE-бинарники собираются с разными базами, но адреса внутри функций сохраняют относительные смещения — сравнивайте по смещениям, а не по абсолютным адресам.
- **Обфускация.** После обфускатора (VMProtect, OLLVM) диф показывает «всё разное»; сначала нужно деобфусцировать, потом диффить.
- **Разные версии libc.** Диффинг динамических зависимостей даёт шум — фильтруйте по секции самого приложения.

## Практический маршрут

1. Получите обе версии (патч-диф из дистрибутива, репозитория, обновления прошивки).
2. Быстрый обзор: `radiff2 -C` или `bindiff` — найдите различающиеся функции.
3. Декомпилируйте старую и новую версию спорной функции.
4. Прочитайте условие, которое изменилось; сформулируйте баг.
5. Проверьте гипотезу на старой версии (краш, обход).
6. Зафиксируйте в отчёте: версия до/после, конкретное исправление, условие эксплуатации.

## Ограничения диффинга

Бинарный диффинг не всесилен. Он не работает, если между версиями сменился компилятор или флаги оптимизации — «изменёнными» окажутся почти все функции, и настоящий фикс утонет в шуме. Плохо он справляется и с сильной обфускацией: виртуализация кода и полиморфизм ломают структурное сопоставление. Наконец, диффинг показывает **где** изменилось, но не **почему** — смысл патча всё равно восстанавливают вручную, читая псевдокод. Поэтому диффинг — инструмент приоритизации: он сужает поле до нескольких функций, а дальше начинается обычный реверс.

## Куда дальше

Мы сравнили две сборки и восстановили из патча логику. Но диффинг — это лишь один приём;
дальше предстоит разбирать целые классы бинарников со своими особенностями. В следующем
уроке мы возьмём бинарник, собранный компилятором **Go** — со статической линковкой и
своей символикой, — и увидим, чем такой реверс отличается от «обычного C». А пока главное
запомни: **сравнивай на уровне смысла (код + данные), а не байтов.**

## Где пригодится

- **CTF Reversing:** задачи «дано до и после — найди разницу».
