## Вопрос, с которого всё начинается

В `crackme` мы видим вызов `strcmp` — но самого кода `strcmp` в файле нет. Он лежит в отдельной
библиотеке `libc.so.6`. Как программа, которая не содержит этого кода, всё-таки его выполняет?
Кто и когда подгружает библиотеку и «связывает» вызов с настоящим адресом?

Ответ — **динамическая линковка**. В этом уроке разберём её механизм на примере `crackme` и
даже перехватим `strcmp` своей функцией.

## Наш пример

Тот же `crackme`, собранный динамически. Инструмент для быстрого взгляда на зависимости —
`ldd` («list dynamic dependencies»). Она показывает, какие библиотеки загрузит программа:

```bash
$ ldd crackme
        linux-vdso.so.1 (0x00007f9b17e99000)
        libc.so.6 => /usr/lib/libc.so.6 (0x00007f9b17c66000)
        /lib64/ld-linux-x86-64.so.2 => /usr/lib64/ld-linux-x86-64.so.2
```

Здесь три строки — и все важны:

- **libc.so.6** — стандартная библиотека C, где живут `printf`, `read`, `strcmp`.
- **ld-linux-x86-64.so.2** — **динамический загрузчик** (loader). Именно он подгружает
  библиотеки и связывает вызовы с адресами.
- **linux-vdso.so.1** — маленький «виртуальный» объект ядра (быстрые системные вызовы).

## Шаг 1: что программа «просит» загрузить

Список зависимостей прописан в самой программе — в динамической секции, тег `NEEDED`:

```bash
$ readelf -d crackme | grep NEEDED
 0x0000000000000001 (NEEDED)  Shared library: [libc.so.6]
```

Загрузчик читает эту запись и знает: «нужно подгрузить libc.so.6». Если бы программа
использовала, например, `libcrypto`, тут было бы несколько строк `NEEDED`.

## Шаг 2: символы — по каким именам связывать

Как загрузчик понимает, что `strcmp` из программы — это `strcmp` из libc? По имени символа.
В `crackme` символы помечены как «не определённые здесь» (`*UND*`):

```bash
$ objdump -T crackme | grep strcmp
0000000000000000      DF *UND*  0000000000000000 (GLIBC_2.2.5) strcmp
```

Загрузчик ищет в `libc.so.6` экспортированный символ `strcmp` и берёт его адрес. Так
«связываются» код программы и код библиотеки.

## Шаг 3: PLT и GOT — как устроен сам вызов

Теперь главное: как выглядит вызов `strcmp` в коде. В дизассемблере мы видели `call strcmp@plt`.
`@plt` — это **Procedure Linkage Table**, маленькая «заглушка» для каждого внешнего вызова.
Посмотрим на неё:

```bash
$ objdump -d -j .plt -M intel crackme | sed -n '/<puts@plt>:/,/^$/p;/<strcmp@plt>:/,/^$/p'
0000000000001030 <puts@plt>:
    1030: ff 25 ca 2f 00 00     jmp  QWORD PTR [rip+0x2fca]  # 4000
    1036: 68 00 00 00 00        push 0x0
    103b: e9 e0 ff ff ff        jmp  1020
0000000000001070 <strcmp@plt>:
    1070: ff 25 aa 2f 00 00     jmp  QWORD PTR [rip+0x2fa2]  # 4018
    1076: 68 02 00 00 00        push 0x2
    107b: e9 a0 ff ff ff        jmp  1020
```

Читаем `strcmp@plt`: первая инструкция `jmp QWORD PTR [rip+...]` прыгает **по адресу, взятому
из памяти** (ячейка `0x4018`). Это и есть **GOT** — Global Offset Table, таблица адресов.
Пока `strcmp` не вызвана ни разу, в ячейке стоит адрес «резолвера» (строки ниже с `push 0x2` и
`jmp 1020`). При первом вызове загрузчик находит настоящий `strcmp`, **записывает его адрес в
GOT**, и дальше вызов идёт напрямую. Это называется **ленивая привязка** (lazy binding).

Схема целиком: `call strcmp@plt` → `jmp [GOT]` → адрес в libc.

## Шаг 4: релокации — как GOT заполняется

Кто и по каким данным заполняет GOT? Релокации. Команда `readelf -r` показывает, какие ячейки
нужно «починить» при загрузке:

```bash
$ readelf -r crackme | sed -n '/rela.plt/,$p'
Relocation section '.rela.plt' contains 5 entries:
  Offset          Info           Type            Sym. Name
000000004010  000500000007 R_X86_64_JUMP_SLO  printf + 0
000000004018  000600000007 R_X86_64_JUMP_SLO  read + 0
000000004020  000700000007 R_X86_64_JUMP_SLO  strcmp + 0
```

Тип `R_X86_64_JUMP_SLO` (jump slot) означает: «в ячейку по смещению (например, `0x4018`) положи
адрес символа `strcmp`». Загрузчик берёт адрес из libc и записывает в GOT. После этого
`jmp [0x4018]` ведёт прямо в `strcmp`.

## Шаг 5: перехват через LD_PRELOAD

Динамическая линковка открывает возможность, которой нет у статических программ: **подменить
функцию библиотеки своей**. Переменная окружения `LD_PRELOAD` заставляет загрузчик подгрузить
указанную библиотеку **раньше** libc — и тогда символ `strcmp` найдётся в ней, а не в libc.

Напишем свою `strcmp`, которая всегда говорит «строки равны»:

```c
/* hook.c */
int strcmp(const char *a, const char *b) {
    (void)a; (void)b;
    return 0;              /* всегда «равны» */
}
```

Собираем как разделяемую библиотеку и подгружаем:

```bash
$ gcc -shared -fPIC -o hook.so hook.c
$ ./crackme
Enter password: nope
Wrong.
$ LD_PRELOAD=./hook.so ./crackme
Enter password: nope
Correct! flag{rev_basics_1s_fun}
```

Мы ввели неправильный пароль, но с подменённым `strcmp` проверка всегда проходит. Никакой
правки самого `crackme` не потребовалось. Так работают многие хуки, перехват API и
инструментирование.

## Шаг 6: где загрузчик ищет библиотеки

Загрузчику нужно найти `libc.so.6` на диске. Он ищет её в стандартных местах: сначала в
`/etc/ld.so.cache` (кэш, обновляется командой `ldconfig`), затем в `/lib`, `/usr/lib` и других
системных каталогах. Порядок поиска можно изменить переменной `LD_LIBRARY_PATH` — тогда
загрузчик сначала заглянет в указанные каталоги. Именно поэтому `LD_LIBRARY_PATH` и
`LD_PRELOAD` — мощные (и опасные) инструменты: они позволяют подсунуть программе «свою»
библиотеку.

Посмотреть, что реально подгружается, помогает переменная `LD_DEBUG`:

```bash
$ LD_DEBUG=libs ./crackme 2>&1 | head -3
     12345: find library=libc.so.6 [0]
     12345:   trying file=/usr/lib/libc.so.6
```

## Шаг 7: статическая и динамическая линковка

Мы всё время говорили о динамической линковке. Есть и другой способ — **статическая**: код
библиотеки целиком вшивается в бинарник при сборке. Сравним два подхода:

| | Динамическая | Статическая |
|---|---|---|
| Размер файла | меньше (код в библиотеке) | большой (всё внутри) |
| Обновление libc | обновить систему | пересобрать бинарник |
| `ldd` | покажет зависимости | `not a dynamic executable` |
| `LD_PRELOAD` | работает | не работает |
| Реверс | видны импорты и `@plt` | код «сплющен» в один блок |

Наш `crackme` — динамический: маленький, зависит от libc, и его можно перехватить через
`LD_PRELOAD`. Статический бинарник (собранный с `-static`) вёл бы себя иначе: все функции
были бы внутри, и `strings`/`objdump` показали бы код самой libc тоже.

## Что мы теперь знаем

- **ld.so** — динамический загрузчик; он читает `NEEDED` и подгружает библиотеки (`ldd`).
- Связывание идёт **по именам символов** (`objdump -T`, `*UND*` — импортируемые).
- Внешний вызов идёт через **PLT-заглушку**, которая прыгает по адресу из **GOT**.
- **Ленивая привязка**: адрес функции пишется в GOT при первом вызове (релокации `JUMP_SLOT`).
- **LD_PRELOAD** позволяет подменить функцию библиотеки своей — без правки бинарника.

## Куда дальше

Мы разобрали PLT/GOT «по верхам». В следующем уроке нырнём глубже в механизм: как именно
выглядит первый вызов, как читать `.got.plt` и почему RELRO защищает эти таблицы. А пока
главное запомни: `@plt` — заглушка, `GOT` — таблица адресов, `LD_PRELOAD` — перехват.

## Где пригодится

- **CTF Reversing:** понимание @plt и GOT объясняет, что видно в дизассемблере вызовов.
- **Pwn:** перезапись GOT — классическая техника захвата управления (ret2plt/GOT overwrite).
- **Malware analysis:** хуки через LD_PRELOAD и подмена библиотек — приём и для анализа, и для атак.
- **Патчинг:** перехват функции без правки кода удобен для аудита и обхода проверок.
- **Собес:** «как работает динамическая линковка», «что такое PLT/GOT» — вопросы уровня middle.
