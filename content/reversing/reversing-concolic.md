## Вопрос, с которого всё начинается

Ты умеешь решать уравнения через Z3 (прошлые уроки). Но что делать, если проверка — это не набор
формул, а **ветвления**: `if (x > 100) { if (x == 1337) ... }`? Ветки означают, что вход определяет,
по какому пути пойдёт программа. Чистое символьное исполнение пытается исследовать **все** пути
сразу, подставляя символы вместо всех входов — это мощно, но дорого (число путей растёт
экспоненциально).

Есть более экономный подход — **concolic** (concrete + symbolic). Он стартует с **конкретного**
входа, идёт по одной ветке за раз, запоминает условия, при которых эта ветка была выбрана, а затем
просит решатель дать вход, который пойдёт **по-другому**. Так concolic итеративно «пробивает» защиту,
двигаясь к цели. Разберём его, написав собственный движок.

## Наш пример

Возьмём функцию `check` с двумя вложенными ветками:

```c
int check(int x){
    if (x > 100){
        if (x == 1337) return 1;   /* «правильный» путь */
    }
    return 0;
}
```

В дизассемблере это две проверки и два условных перехода:

```
$ objdump -d -M intel target | sed -n '/<check>:/,/ret/p'
  40110a:  mov    DWORD PTR [rbp-0x4],edi     ; x на стек
  40110d:  cmp    DWORD PTR [rbp-0x4],0x64
  401111:  jle    401123                      ; если x <= 100 -> return 0
  401113:  cmp    DWORD PTR [rbp-0x4],0x539
  40111a:  jne    401123                      ; если x != 1337 -> return 0
  40111c:  mov    eax,0x1                      ; return 1
```

`0x64` — это 100, `0x539` — 1337. Задача: найти `x`, при котором функция вернёт 1.

## Шаг 1: запускаем с конкретным входом

Concolic начинается с любого конкретного входа — пусть `x = 0`. Мы исполняем функцию в эмуляторе
(`unicorn`), перехватывая каждую инструкцию (`capstone`). Регистр `rdi` (аргумент `x`) объявляем
**символьной переменной** `x`, а на ветках записываем, по какому пути пошли:

```python
x = BitVec('x', 32)            # символьный вход
path, ret = run(seed=0)        # конкретный прогон
```

Результат первого прогона:

```
input=0 -> ret=0  path=['T']
```

`path=['T']` означает: единственная ветка (`jle`, то есть `x <= 100`) была **взята** (`T` — taken).
Функция вернула 0. Мы никуда не «пробились».

## Шаг 2: собираем ограничения пути

Ключевой момент: на каждой ветке мы сохраняем **условие**, которое должно быть истинно, чтобы пойти
именно так. Для `x = 0` условие ветки — `x <= 100` (взяли `jle`). Это и есть **path constraint** —
набор условий, описывающих пройденный путь.

Обрати внимание: мы моделируем не «всю программу», а только те инструкции, что реально исполнились.
Это главное преимущество concolic — платим лишь за один путь.

## Шаг 3: инвертируем последнюю ветку и решаем

Теперь трюк. Мы хотим пойти **не** по этой ветке. Значит, берём последнее условие пути, отрицаем его
и просим Z3 найти вход, при котором путь станет другим:

```python
cons = [c if taken else Not(c) for c, taken in path]   # x <= 100
# инвертируем последнее:
cons2 = cons[:-1] + [Not(path[-1][0])]                  # x > 100
s = Solver(); s.add(cons2)
if s.check() == sat:
    seed = s.model().eval(x).as_long()
```

Z3 возвращает `x = 101` — первое значение, большее 100. Запускаем снова:

```
input=101 -> ret=0  path=['F', 'T']
```

Теперь первая ветка **не** взята (`F`: `x > 100` истинно), а вторая взята (`T`: `x != 1337`), и функция
снова вернула 0. Ограничения пути теперь: `x > 100` И `x != 1337`.

## Шаг 4: инвертируем ещё раз — и попадаем в цель

Повторяем тот же приём: берём текущие ограничения, инвертируем **последнее** (`x != 1337` → `x ==
1337`) и решаем:

```
input=1337 -> ret=1  path=['F', 'F']
REACHED correct branch with x = 1337
```

Третья итерация дала `x = 1337`, функция вернула 1 — мы достигли «правильной» ветки. За три прогона,
а не перебором 32-битных значений. Вот полный лог движка:

```
input=0    -> ret=0  path=['T']
input=101  -> ret=0  path=['F', 'T']
input=1337 -> ret=1  path=['F', 'F']
```

Каждый шаг — это один конкретный прогон плюс один запрос к решателю. Именно так concolic
«пробивает» вложенные проверки: инвертирует очередную ветку и уходит глубже.

## Шаг 5: как это устроено внутри

Движок состоит из трёх частей. **Конкретное исполнение** (unicorn) даёт реальные адреса и значения —
благодаря этому нам не нужно строить формулы для всего кода. **Символьное состояние** (Z3) хранит
выражения для регистров и памяти: мы обновляем их по мере исполнения (`mov`, `add`, `cmp`). **Сбор
ветвлений**: на каждом `jcc` мы записываем условие из последнего `cmp`/`test` и фактическое
направление. Соединив это, получаем движок concolic.

Тонкости те же, что в Z3 и taint-анализе: нужно правильно моделировать **знаковость** (`jle` —
знаковое сравнение, поэтому `x <= 100` в Z3 для `BitVec` знаковое) и **ширину** регистров (аргумент
`int` — 32 бита). Ошибка в модели даст неверный вход, поэтому найденное значение **всегда проверяют
на реальном бинарнике**.

## Шаг 6: concolic против чистого символьного исполнения

Чистое символьное исполнение (KLEE, angr) исследует все пути, подставляя символы везде. Плюс —
находит всё, что достижимо. Минус — «взрыв путей» на больших программах и дороговизна моделирования
библиотек. Concolic дешевле: платит только за реально исполненные инструкции, но идёт по одному пути
за раз, поэтому важна **стратегия выбора ветвлений** (какую ветку инвертировать следующей). В
реальных инструментах (Triton, angr в concolic-режиме) эти подходы комбинируют.

Практическая стратегия в нашем движке — всегда инвертировать **последнюю** ветку пути: это уводит
исследование глубже по текущему маршруту, а не распыляет его. Если решатель говорит `unsat` для
инвертированного условия, значит, другой путь из этой точки недостижим, и стоит вернуться на шаг
назад и инвертировать более раннюю ветку. Так concolic систематически обходит дерево путей, не
перебирая вход вслепую.

## Что мы теперь знаем

- Concolic = конкретное исполнение + символьные ограничения; стартует с конкретного входа.
- **Path constraint** — условия, описывающие пройденный путь (собираются на ветвлениях).
- Инвертирование последнего условия + Z3 даёт вход, идущий по другому пути.
- Мы дошли до `x = 1337` за 3 итерации вместо перебора.
- Модель должна учитывать знаковость (`jle`) и ширину (32 бита); результат проверяют на бинаре.
- Concolic дешевле полной символьной экспансии, но исследует пути по одному.

## Куда дальше

Мы собрали собственный concolic-движок. В следующем уроке поднимемся на уровень **ядра** и разберём
инструментацию системных вызовов. А пока главное запомни: concolic идёт от конкретного входа,
копит условия ветвлений и инвертирует их решателем — так он «пробивает» вложенные проверки одну за
другой.

## Где пригодится

- **CTF Reversing:** обход вложенных проверок пароля без полного перебора.
- **Поиск уязвимостей:** автоматический подбор входа, достигающего опасного места.
- **Fuzzing:** генерация входов, покрывающих новые ветки (concolic-фаззеры).
