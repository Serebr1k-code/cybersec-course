**Concolic** (concrete + symbolic) исполнение сочетает два режима: программа реально выполняется на конкретном входе (concrete), а параллельно строится **символьное выражение** для каждого вычисления, зависящего от входа (symbolic). В отличие от чистой статики, concolic работает с реально исполненными путями, поэтому автоматически обходит неподъёмные конструкции (косвенная адресация, сложная арифметика) и не «взрывается» на ветвлениях, которые программа никогда не выполняет. Инструменты: Triton (DSE) и Manticore. В этом уроке — как это работает, как извлекать ограничения и как решать реальные задачи.

## Идея concolic и чем он отличается от чистой символики

Чистое символьное исполнение (angr, KLEE) пытается исследовать все пути, подставляя символы вместо всех входов. Concolic же стартует с конкретного входа: если ветвление идёт по конкретному значению, берётся только одна ветка, а вдоль пути копится **path constraint** — набор условий, при которых этот путь был бы пройден. Дойдя до целевой точки (например, `strcmp == 0`), мы инвертируем последнее условие и просим решатель (Z3) дать вход, который пойдёт «по-другому». Так concolic итеративно «пробивает» защиту, двигаясь к цели.

Ключевое преимущество: мы не платим за символьное моделирование всего кода — только за те инструкции, что реально исполнились. Недостаток: путь исследуется один за раз, поэтому важна стратегия выбора ветвлений (search strategy).

## Triton: архитектура и запуск

Triton — C++/Python-фреймворк динамического бинарного анализа с DSE (Dynamic Symbolic Execution). Он инструментирует исполнение (через PIN/QBDI или собственный режим), строит символьные выражения и предоставляет решатель. Установка:

```bash
pip install triton-library
python3 -c "import triton; print(triton.__version__)"
```

Минимальный скрипт символьного исполнения функции с использованием Triton в режиме анализа контекста:

```python
from triton import *

ctx = TritonContext(ARCH.X86_64)
ctx.setConcreteRegisterValue(ctx.registers.rax, 0x10)
ctx.symbolizeRegister(ctx.registers.rdi, 'x')      # вход — символ

# Эмулируем несколько инструкций вручную
inst = Instruction(b"\x48\x8d\x04\x37")            # lea rax, [rdi+rsi]
ctx.processing(inst)
print(ctx.getSymbolicExpression(inst))             # symbolic AST
```

`ctx.symbolizeRegister(reg, name)` делает регистр символьным. `ctx.processing(inst)` обрабатывает инструкцию, обновляя как конкретное состояние, так и символьные выражения. `ctx.getSymbolicExpression(inst)` возвращает AST. Для проверки пути используют `ctx.getPathConstraints()` — список условий ветвлений вдоль исполнения.

## Извлечение ограничений и решение

Дойдя до целевой точки, извлекают path constraints и передают в Z3 через `ctx.getModel`/`ctx.solve`:

```python
from triton import *
ctx = TritonContext(ARCH.X86_64)
ctx.symbolizeRegister(ctx.registers.rdi, 'x')
# ... processing(...) по инструкциям пути ...
pc = ctx.getPathConstraints()
for c in pc:
    print(c.getTakenPredicate())       # условие взятой ветки

# Проверить, достижимо ли состояние при x == 0x41
ctx.pushPathConstraint(ctx.registers.rdi == 0x41)
m = ctx.getModel(ctx.registers.rdi == 0x41)
print(m)                                # {x: 65}
```

Triton умеет возвращать модель как `dict` символ→значение. Если модель найдена — подставляем её как вход и проверяем на реальном исполнении.

## Manticore: символьное исполнение «из коробки»

Manticore (проект Trail of Bits) — Python-фреймворк символьного исполнения, поддерживающий ELF, PE, Mach-O и даже смарт-контракты EVM и WASM. Он запускает бинарь под эмулятором и предоставляет высокоуровневый API:

```python
from manticore import Manticore
m = Manticore("./crackme")
@m.hook(0x401234)                       # адрес функции check
def hook(state):
    buf = state.cpu.rdi                   # указатель на вход
    data = state.read_bytes(buf, 16)
    state.constrain(data[0] == ord('f'))
    state.constrain(data[1] == ord('l'))
    print("constraints added")
m.run()
for state in m.final_states:
    print(state.solve_one(...))
```

`m.hook(addr)` — хук по адресу; `state.constrain(expr)` добавляет ограничение; `m.final_states` — достигнутые состояния; `state.solve_one(sym)` решает одно значение. Manticore автоматически исследует ветвления и складывает состояния в очередь; стратегию можно менять (`m.set_policy`), ограничивать глубину и число состояний.

## Triton vs Manticore: когда что брать

Triton быстрее и точнее на уровне инструкций, отлично подходит для извлечения constraints из конкретного пути и интеграции с эмуляторами. Он требует больше ручной работы: вы сами ведёте исполнение. Manticore проще в старте (запустил бинарь — получил состояния), но медленнее и «жаднее» по памяти. Для CTF часто берут Manticore, когда нужно быстро прощупать задачу, и Triton — когда нужен точный контроль и производительность. Оба используют Z3 под капотом.

## Практика: обход пароля с двумя ветвлениями

Рассмотрим проверку вида:

```c
if (input[0] != 'f') return 0;
if (input[1] != 'l') return 0;
if ((input[2] ^ input[3]) != 0x2a) return 0;
return 1;
```

Concolic-подход: запускаем с произвольным входом, доходим до первого `return 0`, инвертируем условие (нужно `input[0] == 'f'`), решаем — получаем 'f'. Повторяем со следующим ограничением, накапливая `input[0]=='f'`, `input[1]=='l'`, и на третьем шаге решаем уравнение с XOR. Каждая итерация добавляет одно ограничение, и Z3 быстро находит байты. Это и есть «движение по пути» к успешному возврату.

## Интеграция с эмуляторами (Unicorn, QBDI)

Triton и Manticore эмулируют код сами, но часто их комбинируют с Unicorn (чистая эмуляция) или QBDI (DBI). Схема: Unicorn даёт быстрое конкретное исполнение, а Triton перехватывает инструкции и строит символы. Так обрабатывают фрагменты, которые сложно эмулировать напрямую (сисколлы, анти-отладка). Manticore имеет встроенный эмулятор и умеет работать без реального CPU, что безопасно для malware.

## Проблемы: path explosion, таймауты, анти-символика

- **Path explosion:** число путей растёт экспоненциально; ограничивайте глубину и число состояний, используйте приоритет по «интересности» (близость к цели).
- **Таймауты Z3:** сложные формулы (крипто) не решаются; разбивайте, упрощайте, применяйте concolic только к не-крипто-части.
- **Анти-символика:** программы с хешами/шифрованием специально ломают решатель; обходите, извлекая ключ из памяти.
- **Неполнота модели окружения:** syscalls, сигналы, время; Manticore умеет их моделировать, но не всегда точно.
- **Недетерминизм:** проверки времени/случайности дают разные пути; фиксируйте окружение.

## Полный разбор: извлечение флага через Manticore

**Шаг 1 — найти адрес проверки** в Ghidra. **Шаг 2 — захукать и добавить ограничения на формат флага:**

```python
from manticore import Manticore
m = Manticore("./flag_checker")
@m.hook(0x4009a0)
def hook(state):
    buf = state.cpu.rdi
    data = state.read_bytes(buf, 32)
    for i, ch in enumerate(b"flag{"):
        state.constrain(data[i] == ch)
m.run()
```

**Шаг 3 — собрать решения** из финальных состояний:

```python
for st in m.final_states:
    print(bytes(st.solve_one(st.read_bytes(st.cpu.rdi, 32))))
```

**Шаг 4 — проверить** найденный флаг на бинаре. Если Manticore не находит состояние — уменьшите пространство (зафиксируйте длину), добавьте хуки на `strcmp`/`memcmp` для «магических» сравнений.

## Шпаргалка

| Понятие | Triton | Manticore |
|---|---|---|
| Запуск | `TritonContext(ARCH.X86_64)` | `Manticore("./bin")` |
| Символ | `symbolizeRegister` | `state.symbolize` |
| Ограничение | `pushPathConstraint` | `state.constrain` |
| Решение | `getModel` | `state.solve_one` |
| Хук | вручную processing | `@m.hook(addr)` |
| Решатель | Z3 внутри | Z3 внутри |
| Сильная сторона | точность, скорость | простота, авто-исследование |

## Что дальше / решение

Практический маршрут: (1) определите целевую точку (успешный возврат, сравнение с флагом); (2) запустите Manticore для быстрого прощупывания, добавив ограничения на формат; (3) если медленно — перейдите на Triton и ведите конкретный путь, извлекая constraints по шагам; (4) решите и **проверьте** на бинаре. Дальше изучайте angr (гибрид), DSE-интеграцию с Unicorn и стратегии обхода path explosion. Concolic — мост между ручным реверсом и полностью автоматическим символьным решением.

## Triton: полный пример с символизацией памяти

Символизация памяти позволяет моделировать входные буферы (пароли, файлы) как символьные массивы. В Triton это делается через `ctx.symbolizeMemory(MemoryAccess(addr, size), name)`:

```python
from triton import *
ctx = TritonContext(ARCH.X86_64)
# входной буфер в 16 байт по адресу 0x1000
for i in range(16):
    ctx.symbolizeMemory(MemoryAccess(0x1000 + i, CPUSIZE.BYTE), f"buf{i}")
# обрабатываем инструкции пути
inst = Instruction(b"\x0f\xb6\x04\x25\x00\x10\x00\x00")  # movzx eax, byte [0x1000]
ctx.processing(inst)
print(ctx.getSymbolicExpression(inst))     # zx(buf0)
```

Читая символьное выражение результата, мы получаем AST, из которого извлекаются ограничения. Для пути до целевой точки собирают `getPathConstraints()` и решают их через Z3 (встроенный `getModel`). Символизация памяти удобнее для буферов, чем ручное создание `BitVec` на каждый байт.

## Стратегии поиска и оптимизация

Concolic исследует пути один за другим, и от стратегии зависит, дойдём ли мы до цели за разумное время. Полезные приёмы: приоритизация состояний по «расстоянию» до целевого адреса; ограничение глубины и числа состояний; инверсия **только релевантных** ветвлений (тех, что зависят от входа); использование `solver timeout` и упрощение формул. В Manticore стратегия задаётся через `m.set_policy` и хуки, а состояния можно отбрасывать по предикату. На практике часто комбинируют: статически находят функции проверки, затем concolic применяют только к ним, а не ко всей программе — это резко снижает path explosion.

## Символизация и taint-анализ

Taint-анализ в Triton отмечает, какие регистры/память зависят от входа, что позволяет символизировать только релевантные данные и не «взрывать» пространство поиска. `ctx.taintRegister(reg)`/`ctx.taintMemory(addr)` задают источник, `ctx.isTainted(reg)` проверяет зависимость. Комбинация taint + concolic — стандартный приём для malware-анализа и поиска уязвимостей: мы отслеживаем, как пользовательские данные влияют на ветвления и адреса, и генерируем вход, приводящий к интересующему поведению. Это же лежит в основе автоматической генерации эксплойтов (AEG).
