Когда линкер собирает программу, он ещё не знает, по каким адресам окажутся код и данные — из-за
ASLR и разделяемых библиотек. Поэтому он оставляет в файле **релокации**: записи «по этому смещению
позже нужно записать адрес такого-то символа». Загрузчик при старте (или при первом вызове)
применяет релокации, подставляя реальные адреса. А **символьные таблицы** хранят имена функций и
переменных, которые связывают байты с человекочитаемыми идентификаторами. Вместе это — язык, на
котором описан механизм связывания.

## Что такое релокация

Релокация — это инструкция для линкера/загрузчика вида: «взять значение символа S, прибавить
добавку A, записать по смещению P с учётом типа». В ELF каждая запись описывается полями: смещение
(`r_offset`), тип (`r_info` → тип + индекс символа) и, для RELA, добавка (`r_addend`). Релокации
сгруппированы по назначению: `.rela.dyn` — для данных и указателей, `.rela.plt` — для ленивого
связывания внешних функций.

Без релокаций позиционно-независимый код (PIE) и разделяемые библиотеки были бы невозможны: код
содержал бы абсолютные адреса, которые пришлось бы фиксировать, что убивает ASLR и мешает
разделению памяти между процессами.

## Типы релокаций x86-64

Наиболее важные типы для реверса и pwn:

- **R_X86_64_JUMP_SLOT** — ячейка GOT для внешней функции (ленивое связывание, `.rela.plt`).
- **R_X86_64_GLOB_DAT** — ячейка GOT для внешней переменной/функции (разрешается сразу).
- **R_X86_64_RELATIVE** — записать `base + addend`; используется для указателей внутри PIE-образа
  (например, в `.init_array`, `__libc_csu`).
- **R_X86_64_64** — записать абсолютный 64-битный адрес символа.
- **R_X86_64_PC32 / PLT32** — относительные (PC-relative) ссылки, типичные для кода.
- **R_X86_64_COPY** — копирование данных символа из библиотеки в `.bss` программы (для глобальных
  переменных, определённых в исполняемом файле, но используемых библиотекой).
- **R_X86_64_IRELATIVE** — косвенная релокация для IFUNC-резолверов (например, `memcpy`,
  выбирающий реализацию по CPU).

Увидев `R_X86_64_RELATIVE` в `.init_array`, вы понимаете: там указатели на конструкторы, которые
загрузчик поправит под фактическую базу. Это ключ к анализу инициализаторов.

## REL vs RELA

Форматы различаются наличием поля добавки. **REL** (`.rel.dyn`, 32-битный ARM/x86) хранит только
смещение и тип — добавка берётся из самого места записи (in-place). **RELA** (`.rela.dyn`,
x86-64) хранит ещё и `r_addend` — добавка явная. Для 64-битных систем почти всегда RELA. Практически
это означает, что в `readelf -r` для x86-64 вы видите колонку `Addend`.

## Символьные таблицы

ELF содержит две символьные таблицы:

- **`.symtab`** — полная таблица символов для линкера и отладки; содержит локальные и глобальные
  символы, отладочную информацию. Удаляется при `strip`.
- **`.dynsym`** — динамические символы, нужные загрузчику во время выполнения (импорты и
  экспорты). Не удаляется, потому что иначе связывание не сработает.

Соответствующие строковые таблицы — **`.strtab`** и **`.dynstr`**. Индекс символа указывает на
запись в `.dynsym`, а поле `st_name` — на смещение в `.dynstr`. Символ содержит адрес (`st_value`),
размер (`st_size`), тип (`STT_FUNC`, `STT_OBJECT`, `STT_NOTYPE`), привязку (`STB_LOCAL`,
`STB_GLOBAL`, `STB_WEAK`) и индекс секции.

Именно поэтому stripped-бинарник всё ещё показывает импорты: `.dynsym` остаётся. `readelf -s` без
аргументов покажет `.symtab` (если есть) и `.dynsym`; `nm -D` — только динамические.

## Хеш-таблицы и ускорение поиска

Загрузчику нужно быстро находить символ по имени. Для этого в ELF есть хеш-таблицы: классическая
**SysV hash** (`.hash`) и более быстрая **GNU hash** (`.gnu.hash`) с Bloom-фильтром. GNU hash
сортирует символы особым образом и позволяет за один-два шага определить, есть ли символ в
библиотеке. Для аналитика это важно: структура `.gnu.hash` позволяет восстановить порядок
динамических символов, а иногда и обнаружить скрытые экспорты.

## Версионирование символов

Библиотеки экспортируют символы с версиями. В `.gnu.version` хранится массив версий для каждого
динамического символа, а `.gnu.version_r` — требуемые версии из зависимостей. Так одна libc
предоставляет `memcpy@GLIBC_2.2.5` и `memcpy@GLIBC_2.14`. При анализе `readelf --version-info`
показывает, какие версии требует бинарник, — это точный способ определить минимальную версию
glibc. Для pwn это критично: от версии зависят смещения `system`, `__free_hook` и one_gadget.

## Практический разбор: readelf -r и -s

Релокации:

```
$ readelf -r ./demo
Relocation section '.rela.dyn' at offset 0x580 contains 8 entries:
  Offset          Info           Type           Sym. Value    Sym. Name + Addend
0000000000003dc0  000000000008 R_X86_64_RELATIVE                    1140
0000000000003dc8  000000000008 R_X86_64_RELATIVE                    1100
0000000000003fd0  000000000006 R_X86_64_GLOB_DAT 0000000000000000 __libc_start_main@GLIBC_2.34 + 0

Relocation section '.rela.plt' at offset 0x610 contains 1 entry:
  Offset          Info           Type           Sym. Value    Sym. Name + Addend
0000000000003fc8  000000000007 R_X86_64_JUMP_SLOT 0000000000000000 puts@GLIBC_2.2.5 + 0
```

Здесь `R_X86_64_RELATIVE` с адресами `0x1140`/`0x1100` — это, скорее всего, элементы
`.init_array`/`.fini_array` (указатели на конструкторы). `GLOB_DAT` для `__libc_start_main` и
`JUMP_SLOT` для `puts` — внешние символы. Offset `0x3fc8` — та самая ячейка GOT.

Символы:

```
$ readelf -sW ./demo | grep -E "FUNC|OBJECT" | head
    12: 0000000000000000     0 FUNC    GLOBAL DEFAULT  UND puts@GLIBC_2.2.5 (2)
    23: 0000000000001100    31 FUNC    GLOBAL DEFAULT   14 frame_dummy
    28: 0000000000001140    21 FUNC    GLOBAL DEFAULT   14 main
```

`UND` (undefined) означает внешний символ, `GLOBAL DEFAULT 14` — определённый в секции 14
(`.text`). После `strip` записи `main`/`frame_dummy` исчезнут, но `puts@GLIBC_2.2.5` останется.

## Восстановление имён в stripped-бинарнике

Если `.symtab` удалён, есть несколько путей вернуть имена:

- **Динамические символы** (`.dynsym`) — всегда доступны для внешних вызовов.
- **Сигнатуры**: FLIRT (IDA), FID (Ghidra), `lumina`, `BinDiff` — распознают библиотечные функции
  по байтовым сигнатурам.
- **Строки и ссылки**: функция, использующая строку `"Invalid license"`, почти наверняка и есть
  проверка лицензии.
- **Отладочные данные**: если в бинарнике остался `.debug_*` (сборка без `-s`), `nm`/`objdump`
  восстановят имена даже при stripped `.symtab`.
- **LTO/версии**: иногда имена mangled сохраняются в других секциях.

## Релокации в PE и Mach-O

В PE релокации хранятся в `.reloc` в виде таблицы блоков по страницам; для ASLR загрузчик правит
базу. Типов релокаций меньше, потому что x86-64 PE в основном использует `IMAGE_REL_BASED_DIR64`
(добавить дельту к 64-битному значению). В Mach-O исторически использовались rebase/bind-опкоды
(`LC_DYLD_INFO_ONLY`), а в новых системах — chained fixups. Смысл тот же: отложить подстановку
адресов до загрузки.

## Как загрузчик применяет релокации

Алгоритм загрузчика прост и поучителен. Сначала он отображает сегменты и вычисляет фактическую
базу образа (разницу между реальным адресом первого сегмента и его `p_vaddr`). Затем проходит по
`.rela.dyn`: для `RELATIVE` пишет `base + addend`; для `GLOB_DAT` находит символ и пишет его адрес;
для `COPY` копирует данные из библиотеки. Для `.rela.plt` при частичном RELRO он не торопится:
ячейки заполняются лениво при первом вызове. После применения релокаций, если присутствует
`PT_GNU_RELRO`, загрузчик вызывает `mprotect` и делает соответствующую область read-only.

Понимание этого порядка объясняет многие явления. Например, почему `__libc_start_main` доступен
сразу (GLOB_DAT, разрешается на загрузке), а `puts` — только после первого вызова (JUMP_SLOT,
лениво). Или почему при полном RELRO (`-z now`) загрузчик принудительно разрешает все PLT-символы
на старте, чтобы затем закрыть GOT.

## Релокации и защита

Релокации тесно связаны с защитными механизмами. `BIND_NOW` (флаг в `.dynamic`) заставляет
разрешить все символы немедленно — это основа Full RELRO. `PT_GNU_RELRO` без `BIND_NOW` даёт
Partial RELRO: `.got` закрывается, а `.got.plt` остаётся writable. Флаг `DF_1_NOW` в `DT_FLAGS_1`
равнозначен `BIND_NOW`. Проверить можно через `readelf -d | grep -E "BIND_NOW|FLAGS"` и
`readelf -l | grep GNU_RELRO`.

Отдельно стоит **IFUNC** (`R_X86_64_IRELATIVE`): резолверы, выбирающие реализацию функции под
конкретный процессор (например, AVX-версию `memcpy`). Они исполняются на этапе загрузки и потому
являются интересной поверхностью: подмена IFUNC-резолвера даёт выполнение кода до `main`.

## Подводные камни

Первое: `nm` без `-D` на stripped-бинарнике скажет «no symbols», хотя `.dynsym` есть. Второе:
`R_X86_64_RELATIVE` не содержит имени символа — только добавку; не путайте с именованными
релокациями. Третье: `st_value` для `UND`-символов равен нулю — адрес появляется только после
резолва. Четвёртое: версии символов обязательны, и их несовпадение — частая причина «работает
локально, не работает на сервере». Пятое: `.gnu.hash` может отсутствовать в старых бинарниках, где
используется `.hash` — не ищите структуру, которой нет.

## Что дальше / решение

Практика: возьмите `demo`, выведите `readelf -rW`, `readelf -sW`, `readelf --version-info`.
Определите, какие релокации относятся к GOT, а какие — к данным. Соберите бинарник с
`__attribute__((constructor))` и найдите `R_X86_64_RELATIVE` в `.init_array`. Затем `strip` его и
проверьте, что `.dynsym` сохранился. Далее — `reversing-libraries-re` и практика с FLIRT-сигнатурами.
