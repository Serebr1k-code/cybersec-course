## Вопрос, с которого всё начинается

Ты открываешь бинарник в Ghidra, а вместо имён функций — `FUN_00101340`, `FUN_001014a0`. Или наоборот: линкер ругается «undefined reference to `helper`». Обе ситуации — про **символы** и **релокации**: записи о том, где в коде лежат функции и какие адреса нужно подставить при сборке. Понять их — значит понимать, откуда берутся имена и почему в stripped-файле их нет.

## Наш пример

Возьмём не слинкованную программу, а промежуточный файл — **объектный** `reloc.o`, который получается после компиляции, но до линковки:

```bash
$ file reloc.o
reloc.o: ELF 64-bit LSB relocatable, x86-64, version 1 (SYSV), not stripped
```

Обрати внимание: тип — **`relocatable`** (перемещаемый), а не `executable`. Это ещё не готовая программа: в нём есть вызовы функций, адреса которых пока неизвестны. Вот тут и появляются релокации.

## Шаг 1: символы — что за имена внутри

Сначала посмотрим **таблицу символов** — список имён и их свойств:

```bash
$ readelf -s reloc.o
   Num:    Value          Size Type    Bind   Vis      Ndx Name
     3: 0000000000000000     4 OBJECT  GLOBAL DEFAULT    3 global_counter
     4: 0000000000000000    34 FUNC    GLOBAL DEFAULT    1 compute
     5: 0000000000000000     0 NOTYPE  GLOBAL DEFAULT  UND helper
     6: 0000000000000000     0 NOTYPE  GLOBAL DEFAULT  UND _GLOBAL_OFFSET_TABLE_
```

Читаем по колонкам:

- **Name** — имя (`compute`, `global_counter`, `helper`).
- **Type** — `FUNC` (функция), `OBJECT` (переменная), `NOTYPE` (неизвестно).
- **Ndx** — в какой секции символ. Число (`1`, `3`) — определён здесь; **`UND`** — «undefined», то есть определён где-то ещё.

`compute` и `global_counter` определены в этом файле, а `helper` — нет. Команда `nm` показывает то же самое компактнее:

```bash
$ nm reloc.o
                 U _GLOBAL_OFFSET_TABLE_
0000000000000000 T compute
0000000000000000 D global_counter
                 U helper
```

Буква `T`/`D` — определён (код/данные), `U` — undefined. Именно из-за `U helper` линкер при сборке скажет «undefined reference», если не найдёт `helper` ни в одном объектном файле или библиотеке.

## Шаг 2: релокации — «заплатки» для адресов

Компилятор не знает, по какому адресу окажется `helper`, поэтому он оставляет в коде «дырку» и запись о ней — **релокацию**. Список релокаций:

```bash
$ readelf -r reloc.o
Relocation section '.rela.text' at offset 0x1d8 contains 2 entries:
  Offset          Info           Type           Sym. Value    Sym. Name + Addend
000000000011  000500000004 R_X86_64_PLT32    0000000000000000 helper - 4
000000000018  00030000002a R_X86_64_REX_GOTP 0000000000000000 global_counter - 4
```

Разберём ключевые поля:

- **Offset** — по какому смещению в секции `.text` лежит «дырка».
- **Type** — как именно вписать адрес. `R_X86_64_PLT32` — «вызов через PLT с 32-битным смещением», `R_X86_64_REX_GOTP` — «адрес через GOT».
- **Sym. Name** — на что заменить: на `helper` и `global_counter`.

Когда линкер соберёт программу, он найдёт эти символы, посчитает реальные адреса и впишет их в «дырки». Релокация — это заявка: **«сюда подставь адрес символа X»**.

## Шаг 3: два вида символов — `.symtab` и `.dynsym`

В готовом ELF символьных таблиц может быть две:

- **`.symtab`** — полная таблица для отладки и линковки. Есть только если бинарник **не stripped**.
- **`.dynsym`** — минимальная таблица для динамического загрузчика: экспорт и импорт библиотеки. Нужна всегда, иначе программа не запустится.

Вот почему `strip` не может удалить всё: `.dynsym` обязателен. Он вырезает `.symtab`, и имена внутренних функций исчезают.

## Шаг 4: stripped-бинарник — что остаётся

Проверим на stripped-файле:

```bash
$ file crackme_stripped
crackme_stripped: ELF 64-bit LSB pie executable, x86-64, ... stripped
$ nm crackme_stripped
nm: crackme_stripped: no symbols
```

`nm` молчит — `.symtab` удалена. Но `.dynsym` на месте:

```bash
$ readelf -s crackme_stripped | head -3
Symbol table '.dynsym' contains 11 entries:
   Num:    Value          Size Type    Bind   Vis      Ndx Name
```

Значит, имена библиотечных функций (`printf`, `strcmp`) и импорты сохранились — по ним и строят догадки. А вот собственные функции придётся называть `FUN_...` и разбирать вручную. В готовом (не объектном) файле релокации тоже остаются — в `.rela.dyn`:

```bash
$ readelf -r hello_dyn | grep R_X86_64 | head -3
000000003dd0  000000000008 R_X86_64_RELATIVE  1130
000000003fc0  000100000006 R_X86_64_GLOB_DAT   __libc_start_main@GLIBC_2.34 + 0
```

`R_X86_64_RELATIVE` — «прибавить базу образа» (для PIE), `GLOB_DAT` — «подставить адрес глобальной функции». Это те самые подстановки, о которых мы говорили в уроке про компоновку.

## Шаг 5: символы C++ и демагглинг

В C++ имена функций кодируют типы аргументов — это называется **манглинг**. Функция `int check(int)` превращается в символ вида `_Z5checki`. Прочитать такое глазами трудно, поэтому есть **демагглер**:

```bash
$ nm libfoo.so | grep _Z
0000000000001139 T _Z5checki
$ nm -C libfoo.so | grep check
0000000000001139 T check(int)
```

Флаг `-C` (у `nm` и `objdump`) делает демагглинг на лету: `_Z5checki` превращается в `check(int)`. Для реверса это бесценно: даже в stripped-бинарнике C++-имена экспорта и импорта могут сохраниться в `.dynsym` и подсказать назначение функций.

## Шаг 6: как восстановить имена в stripped-бинарнике

Символы удалены, но зацепки остались. Порядок действий:

1. **Импорты и экспорт** (`.dynsym`) — имена библиотечных функций на месте (`printf`, `strcmp`), по ним видно, что программа делает.
2. **Строки** — `strings -n 6 crackme_stripped` часто выдаёт подсказки и формат флагов.
3. **Сигнатуры** — Ghidra/IDA узнают стандартные функции (`strlen`, `memcpy`) по байтовым шаблонам (FLIRT/IDB), даже без имён.
4. **Связи** — по графу вызовов (`FUN_...` вызывает `printf`) восстанавливают роли функций.

Так `FUN_00101340` постепенно превращается в «функция проверки пароля» — не по имени, а по поведению.

## Шаг 7: инструменты

- **`readelf -s`** — таблица символов; **`readelf -r`** — релокации.
- **`nm`** (и `nm -C`) — компактная сводка; **`objdump -t`** — символы вместе с секциями.
- **`strip`** — удаляет `.symtab`; **`objcopy --strip-all`** — то же.
- **Ghidra / IDA** — применяют сигнатуры и переименовывают функции.

## На что смотреть дальше

Порядок работы с незнакомым бинарником по символам:

1. **`file`** — stripped или нет.
2. **`nm` / `readelf -s`** — если символы есть, сразу видны имена функций.
3. **`readelf -r`** — релокации подсказывают, какие внешние функции вызываются.
4. **`strings`** — строки и формат флага.
5. **Сигнатуры в Ghidra** — восстановить безымянные функции по шаблонам.

Если бинарник stripped, не отчаивайся: `.dynsym`, релокации и строки часто дают достаточно зацепок.

## Что мы теперь знаем

- **Символ** — именованная сущность (функция, переменная) с адресом или пометкой `UND`.
- **Релокация** — запись «по этому смещению подставь адрес символа X»; линкер применяет её при сборке.
- Объектный файл (`relocatable`) полон неразрешённых символов и релокаций.
- В ELF две таблицы: `.symtab` (полная, удаляется `strip`) и `.dynsym` (нужна загрузчику, остаётся всегда).
- В stripped-бинарнике свои функции безымянны, но импорты и строки сохраняются.

## Куда дальше

Мы разобрали, как имена и адреса связывают код воедино. Следующий шаг — научиться **читать дизассемблер и декомпилятор** так, чтобы по безымянным функциям восстанавливать логику. Этому посвящена ветка про статический анализ. А пока запомни: `readelf -s` — символы, `readelf -r` — релокации, `nm` — краткая сводка, а `strip` убирает `.symtab`, но не `.dynsym`.

## Где пригодится

- **CTF Reversing (stripped):** понимание `.symtab` vs `.dynsym` сразу говорит, за что можно зацепиться.
- **Malware analysis:** по сохранившимся импортам и строкам восстанавливают назначение безымянных функций.
- **Pwn:** поиск символов и гаджетов, адреса libc и GOT/PLT опираются ровно на эти структуры.
- **Сборка:** ошибки «undefined reference» — это неразрешённые `UND`-символы, и ты теперь знаешь, откуда они.
