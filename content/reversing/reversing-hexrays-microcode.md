## Вопрос, с которого всё начинается

Ты пишешь плагин для IDA, который должен автоматически упрощать код, но декомпилятор уже сделал половину работы. На каком уровне он это делает и можно ли на него влиять?

## Наш пример

`target.bin` — бинарник с функцией, забитой константными вычислениями (например, `x = (5 + 3) * 2`). Посмотрим, как Hex-Rays превращает её в чистое `x = 16`, и как это увидеть через microcode.

## Шаг 1: что такое microcode

**Hex-Rays** — декомпилятор IDA. Между ассемблером и псевдо-C он строит собственный промежуточный язык — **microcode** (часто «µcode»). Это низкоуровневый, но уже нормализованный вид: операции над регистрами, временными переменными и памятью, без привязки к конкретным инструкциям x86.

Microcode — не публичный стандарт, но он **открыт для плагинов**: IDA даёт API (`ida_hexrays`), которым можно читать и изменять его.

## Шаг 2: зачем промежуточный язык

Декомпиляция — это последовательность преобразований. Прямо из x86 получить C невозможно: слишком много регистров, флагов, побочных эффектов. Microcode решает это, давая:

- **единый вид** для всех архитектур;
- **явные данные о потоке** (блоки, переходы, вызовы);
- **точку для оптимизаций**, независимую от ISA.

Именно поэтому декомпилятор можно «настраивать» — писать проходы, которые упрощают microcode до того, как он станет C.

## Шаг 3: стадии и оптимизации

Microcode проходит несколько стадий:

1. **Построение** — из инструкций собираются микрооперации.
2. **Оптимизация** — свёртка констант, удаление мёртвого кода, распространение копий.
3. **Структурирование** — восстановление `if`/`while`/`for` из графа.
4. **Генерация C** — вывод псевдокода.

Свёртка констант видна так: `x = (5 + 3) * 2` на входе превращается в `x = 16` ещё в microcode — до генерации C.

## Шаг 4: смотрим microcode

Плагин/скрипт печатает microcode функции:

```bash
$ python3 mc_dump.py target.bin
; block 0
    mov  $v0.8, #5
    mov  $v1.8, #3
    add  $v2.8, $v0.8, $v1.8      ; 5+3
    shl  $v3.8, $v2.8, #1         ; *2
; after opt:
    mov  $v3.8, #16               ; nto{m1cr0c0d3_c0nst_f0ld1ng}
    ret  $v3.8
```

Видно, как оптимизатор свернул выражение в константу. В реальной обфускации microcode показывает, какие вычисления «настоящие», а какие — шум.

## Шаг 5: что пишут на microcode API

Практические плагины:

- **Деобфускация.** Проход, который на microcode распознаёт и сворачивает opaque-предикаты и MBA (Mixed Boolean-Arithmetic).
- **Упрощение выражений.** Применение алгебраических тождеств до генерации C.
- **Извлечение констант.** Найти все ключи/магические числа в вычислениях.
- **Трассировка данных.** Отследить, откуда пришло значение в конкретный вызов.

Ключевая идея: работать на microcode **удобнее**, чем на ассемблере, и **точнее**, чем на готовом C (где часть информации уже потеряна).

## Шаг 6: ограничения

Microcode — внутренний формат IDA:

- он **не документирован официально** и может меняться между версиями;
- API требует лицензии IDA и понимания её модели;
- не всё, что есть в ассемблере, представлено явно.

Поэтому плагины на microcode — для продвинутых задач. Для базового реверса достаточно декомпилированного C; microcode нужен, когда ты хочешь **изменить сам процесс декомпиляции**.

## Что мы теперь знаем

- Hex-Rays строит промежуточный язык — microcode.
- Microcode проходит стадии построения, оптимизации и структурирования.
- Свёртка констант и другие оптимизации видны в microcode.
- API IDA позволяет писать проходы по microcode (деобфускация, упрощение).
- Microcode удобнее ассемблера и точнее готового C.

## Шаг 7: как устроена микрооперация

Каждая микрооперация в microcode — это маленькое действие: `mov`, `add`, `sub`, `jz`, `call`, `ldx`, `stx` и т.д. У неё есть **назначение** (куда пишем) и **операнды** (откуда читаем). Операнды — это регистры, временные переменные (`$vN`), числа (`#N`) или память.

```text
mov  $v0.4, #0x10        ; временной переменной присвоить 0x10
add  $v1.4, $v0.4, #4    ; сложить
stx  [rbx].4, $v1.4      ; записать в память по rbx
```

Суффикс `.4`/`.8` — размер в байтах. Всё явно: нет скрытых флагов, нет «побочных эффектов» регистров. Именно поэтому microcode удобен для автоматического анализа.

## Шаг 8: стадии декомпиляции подробнее

Конвейер Hex-Rays состоит из последовательных проходов:

1. **Генерация** — ассемблер → микрооперации.
2. **Оптимизации** — свёртка констант, распространение копий, удаление мёртвого кода.
3. **Локальные оптимизации** — упрощение выражений внутри блоков.
4. **Глобальные оптимизации** — анализ потока данных между блоками.
5. **Структурирование** — восстановление циклов и ветвлений.
6. **Генерация C** — вывод псевдокода.

Плагины обычно встраиваются между стадиями 3 и 4: там код уже нормализован, но ещё не превращён в C.

## Шаг 9: свёртка констант пошагово

Наблюдать оптимизации можно, попросив декомпилятор показать microcode до и после. До:

```text
mov  $v0.8, #5
mov  $v1.8, #3
add  $v2.8, $v0.8, $v1.8
shl  $v3.8, $v2.8, #1
```

После:

```text
mov  $v3.8, #16
```

Компилятор (или декомпилятор) вычислил `(5+3)*2 = 16`. В обфусцированном коде таких «вычислимых» выражений десятки, и все они сворачиваются автоматически.

## Шаг 10: написание прохода

Проход — это функция, которая вызывается для каждой микроинструкции и может её изменить:

```python
def simplify_mba(insn):
    if insn.opcode == m_add:
        l, r = insn.l, insn.r
        if is_and(l) and is_or(r) and same_vars(l, r):
            # (x&y)+(x|y) -> x+y
            return make_add(x_of(l), y_of(l))
    return None
```

Если проход возвращает новую инструкцию, декомпилятор подставляет её. Так постепенно «расчищается» код.

## Шаг 11: практические применения

| Задача | Что делает проход |
|---|---|
| MBA-деобфускация | сворачивает булеву арифметику |
| Opaque-предикаты | вычисляет условие, убирает фальшивую ветку |
| Строковые дешифраторы | подставляет вычисленную строку |
| Удаление мусора | убирает неиспользуемые присваивания |
| Восстановление типов | подсказывает типы по использованию |

## Шаг 12: ограничения microcode

Microcode — внутренний формат IDA. Он не документирован и может меняться между версиями. API (`ida_hexrays`) требует лицензии и знания модели. Не всё представлено явно: часть информации о флагах и побочных эффектах теряется при подъёме. Поэтому microcode — инструмент для продвинутых задач, а не для базового реверса.

## Шаг 13: сравнение с P-Code и BNIL

| | microcode | P-Code (Ghidra) | BNIL |
|---|---|---|---|
| Документация | нет | есть | частично |
| Исполнение | нет | да (эмулятор) | нет |
| Уровни | один | один | три |
| API | ida_hexrays | PcodeEmulator | Python |

Microcode силён интеграцией с IDA и оптимизациями; P-Code — возможностью эмуляции; BNIL — читаемостью. Выбор зависит от задачи.

## Шаг 14: итоговый алгоритм

Включи показ microcode в IDA. Найди функцию с обфускацией. Посмотри microcode до оптимизаций — увидишь «сырые» вычисления. Напиши проход, который их сворачивает. Проверь результат в декомпилированном C. Для сложных случаев используй готовые плагины деобфускации. Главное: **декомпилятор — это конвейер, и microcode — его рабочая середина, которую можно программировать**.

## Шаг 15: почему microcode называют «честным» представлением

Ассемблер лжёт о том, что делает программа. Инструкция `xor eax, eax` обнуляет регистр, но в дизассемблере выглядит как операция над двумя регистрами; флаги меняются неявно; часть инструкций имеет побочные эффекты, о которых не написано. Microcode убирает эту ложь: каждая операция делает ровно одно действие, флаги становятся отдельными переменными, а неявные эффекты — явными операциями. Именно поэтому на microcode так удобно писать автоматические преобразования: тебе не нужно помнить сотни неочевидных деталей каждой инструкции, ты работаешь с чистым списком операций. Для аналитика это означает, что «сложный» обфусцированный код в microcode часто оказывается коротким и понятным. Обфускатор может нагромоздить десятки инструкций, но после подъёма они сворачиваются в пару операций, и логика проявляется. В этом смысле microcode — не просто внутренний формат IDA, а инструмент мышления: он показывает код таким, каким его «видит» математика, а не процессор.

## Шаг 16: как microcode помогает при разборе виртуальных машин

Кастомные VM-протекторы исполняют свой байткод через диспетчер: цикл читает опкод, выбирает handler, выполняет его и переходит к следующему. В ассемблере это огромный `switch` с косвенными прыжками, и понять семантику каждого handler-а тяжело. В microcode диспетчер виден как структура: чтение байткода, вычисление индекса, таблица переходов. Каждый handler — отдельный блок микроопераций, который делает конкретное действие над виртуальными регистрами. Прочитав все handler-ы, ты восстанавливаешь систему команд виртуальной машины: какие операции она поддерживает, сколько у неё регистров, как устроена память. Это первый шаг девиртуализации: понять ISA протектора, а затем перевести байткод обратно в исходную логику. Без IL такой разбор превращается в ручное чтение сотен инструкций; с microcode он структурирован и поддаётся автоматизации.

## Шаг 17: ограничения и когда не стоит идти в microcode

Microcode — не универсальный ответ. Во-первых, он привязан к IDA: плагины на нём не переносятся на Ghidra или BN. Во-вторых, API меняется между версиями, и плагин, написанный под 7.x, может не собраться под 8.x. В-третьих, не все оптимизации доступны для изменения: некоторые проходы зашиты в ядро декомпилятора. В-четвёртых, отладка самого плагина нетривиальна — ошибка в проходе может «сломать» декомпиляцию функции, и разобраться, какой именно проход виноват, бывает сложно. Поэтому microcode оправдан, когда задача действительно требует изменить процесс декомпиляции: массовая деобфускация, специализированные проходы, интеграция с внешними анализаторами. Для разового разбора одной функции достаточно декомпилированного C и ручной правки. Выбор инструмента — это выбор между силой и стоимостью, и microcode — инструмент для тех случаев, где сила оправдывает стоимость.

## Куда дальше
