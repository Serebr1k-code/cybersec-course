## Вопрос, с которого всё начинается

Ты запускаешь приложение на рутованном эмуляторе — и оно сразу закрывается или показывает «Устройство не поддерживается». Значит, внутри есть проверки root/эмулятора/Frida. Как их найти в бинарнике и понять, что именно они проверяют?

## Наш пример

Возьмём `libdetect.so` — нативную библиотеку, которая, судя по названию, занимается детектом. Начнём с того, что видно без декомпиляции:

```
$ strings -n 5 libdetect.so
/system/bin/su
/system/xbin/su
/sbin/su
frida-server
frida-agent
ro.build.tags=test-keys
ro.debuggable=1
```

Уже по строкам ясно, что проверяется: наличие бинарника `su`, файлов Frida и системных свойств, указывающих на нестандартную сборку.

## Шаг 1: три категории проверок

Детект на Android делится на три большие категории. **Root**: наличие `su` в типичных путях, установленный пакет `com.topjohnwu.magisk`, доступность `/system/xbin`. **Emulator**: свойства `ro.build.tags=test-keys`, `ro.debuggable=1`, отсутствие сенсоров, специфичные `ro.product.model` (например, `sdk_gphone`). **Инструментация**: порт Frida (27042), файлы `frida-server`, следы в `/proc/self/maps`.

Каждая категория оставляет **индикаторы** — строки, пути, номера портов. Твоя задача — найти эти индикаторы в бинарнике и понять, какой из них используется.

## Шаг 2: статический поиск индикаторов

Самый быстрый приём — grep по строкам. Но не только по `.so`: строки могут быть и в `classes.dex`. Разберём `libdetect.so` по секциям:

```
$ strings -n 4 libdetect.so | grep -iE 'su|frida|magisk|debuggable|test-keys'
/system/bin/su
/system/xbin/su
frida-server
ro.debuggable=1
```

Теперь ты знаешь, что функция проверяет эти пути. Дальше ищешь, **как** она это делает: `access()`/`stat()` для файлов, `__system_property_get` для свойств, `open` порта для Frida. Каждый вызов — «якорь», вокруг которого крутится логика.

## Шаг 3: найти код вокруг строки

Чтобы понять, где строка используется, нужен адрес. В ELF-секции `.rodata` строки лежат по фиксированным смещениям. Найдя смещение строки `/system/bin/su`, ты ищешь в `.text` инструкцию, которая загружает этот адрес (`adrp`/`add` в ARM64 или `lis`/`addi` в ARM32). Вокруг неё — вызов `access()` и условный переход.

Типичная картина (ARM64, упрощённо):

```
adrp x0, #str_su       ; адрес строки "/system/bin/su"
add  x0, x0, #:lo12:str_su
bl   access            ; проверить доступ
cbnz w0, rooted        ; если доступен — root найден
```

Логика проста: `access(path, F_OK)` возвращает 0, если файл существует. Ненулевой результат — ветка «чисто».

## Шаг 4: динамика — увидеть проверку в бою

Статики не всегда хватает: часть проверок спрятана в JNI или разбита на несколько функций. Тогда используется Frida: перехват `access`/`stat`/`open` и логирование аргументов.

```javascript
Interceptor.attach(Module.getExportByName(null, 'access'), {
  onEnter(args) { console.log('access:', args[0].readCString()) },
  onLeave(retval) { console.log('  ->', retval.toInt32()) }
})
```

Запускаешь — и видишь точный список путей, которые проверяет приложение. Это надёжнее, чем угадывать по строкам.

## Шаг 5: обход проверок

Есть несколько уровней обхода. **Скрыть root**: использовать Magisk с DenyList/Shamiko, чтобы `su` не был виден приложению. **Подменить ответ**: в Frida перехватить `access` и вернуть -1 (файл не найден) для путей `su`. **Патч в статике**: в `classes.dex` заменить условный переход, ведущий в ветку «rooted», на безусловный обход. **Убрать строку**: заменить `/system/bin/su` на несуществующий путь.

Важно понимать: разработчики знают об этих обходах, поэтому серьёзные приложения делают несколько независимых проверок и «отложенный» детект — реагируют не сразу, а через время, чтобы усложнить отладку. Тогда нужно найти ВСЕ проверки, а не одну.

## Шаг 6: находим артефакт практики

В нашей библиотеке среди строк есть сообщение, которое печатается, когда детект срабатывает. Достанем его:

```
$ strings -n 5 libdetect.so | grep nto
nto{r00t_d3t3ct_byp4ss3d}
```

## Что мы теперь знаем

- Детект делится на root / emulator / instrumentation, у каждой категории свои индикаторы.
- Индикаторы — это строки (пути, свойства) и вызовы (`access`, `__system_property_get`, `open`).
- Статически: найти строку → найти её адрес → найти код вокруг.
- Динамически: перехватить `access`/`stat`/`open` в Frida и увидеть реальные проверки.
- Обход: скрыть root (Magisk DenyList), подменить ответ (Frida hook), патчить переход или строку.
- Серьёзные приложения делают несколько независимых и отложенных проверок.

## Полный каталог индикаторов

Опытный аналитик держит в голове каталог. **Root**: `/system/bin/su`, `/system/xbin/su`,
`/sbin/su`, `/su/bin/su`; пакет `com.topjohnwu.magisk`; `ro.debuggable=1`; `ro.secure=0`;
наличие `busybox`. **Emulator**: `ro.build.tags=test-keys`, `ro.product.model` вида
`sdk_gphone*`/`Emulator`, отсутствие `ro.hardware` или его значение `goldfish`/`ranchu`,
отсутствие сенсоров, странный IMEI. **Instrumentation**: порт 27042 (Frida), `frida-server`
в `/proc/self/maps`, файл `/data/local/tmp/frida-server`, `XposedBridge` в classpath.

Зная каталог, ты быстрее сопоставляешь строки из бинарника с конкретной категорией детекта.

## Обход через перехват в нативном слое

Java-хук виден приложению, если оно проверяет `frida` в карте памяти. Тогда детект
перехватывают **на уровне libc**: хук на `open`/`access`/`stat`/`readlink`/`__system_property_get`.
Возвращая для путей `su` результат «не найдено», а для свойства `ro.debuggable` — «0», ты
обманываешь проверку, не меняя сам факт root. Это чище, чем патч smali, и работает даже
против нативных проверок.

## Частые ошибки

- Искать только в `classes.dex` и пропустить нативные проверки в `.so`.
- Обойти одну проверку и удивиться, что приложение всё равно падает: проверок несколько.
- Перехватывать `access`, но забыть про `stat`/`lstat`/`faccessat`.
- Патчить строку в DEX и сломать проверку целостности DEX.
- Игнорировать отложенный детект — приложение «ждёт» и реагирует позже.

## Чек-лист

1. `strings` по всем `.so` и `classes.dex`.
2. Составь список индикаторов и категорий.
3. Найди вызовы `access`/`stat`/`__system_property_get` вокруг строк.
4. Динамика: Frida-хук на libc, лог аргументов.
5. Обход: Magisk DenyList + перехват проверок.

## Разбор реального примера: находим и обходим проверку

Разберём нативную проверку целиком. Сначала строки:

```
$ strings -n 5 libdetect.so | grep -iE 'su|frida|magisk|debuggable'
/system/bin/su
/system/xbin/su
/sbin/su
frida-server
ro.debuggable=1
ro.build.tags=test-keys
```

Теперь найдём, где используется строка `/system/bin/su`. Адрес строки в `.rodata` (пусть
`0x2a10`). Дизассемблируем и ищем загрузку этого адреса:

```
$ objdump -d libdetect.so | grep -B2 -A6 '0x2a10'
 1a40:  adrp    x0, 2a000
 1a44:  add     x0, x0, #0x10      ; x0 = &"/system/bin/su"
 1a48:  mov     w1, #0             ; F_OK
 1a4c:  bl      access
 1a50:  cbz     w0, 1a70          ; если файл существует -> root
```

Логика прозрачна: `access(path, F_OK)` возвращает 0, если файл есть. `cbz w0, 1a70` —
переход на ветку «root обнаружен», если результат нулевой. Обход очевиден: либо сделать так,
чтобы файла не было (Magisk DenyList), либо заставить `access` вернуть ненулевой результат для
этого пути.

Обход через Frida:

```javascript
Interceptor.attach(Module.getExportByName(null, 'access'), {
  onEnter(args) {
    this.path = args[0].readCString()
  },
  onLeave(retval) {
    if (this.path && this.path.indexOf('/su') !== -1) {
      retval.replace(-1)   // файл «не найден»
    }
  }
})
```

Теперь проверка всегда «чисто», хотя root есть. Аналогично перехватывают `stat`, `lstat`,
`faccessat` и `__system_property_get`.

## Несколько проверок и отложенный детект

Серьёзные приложения делают несколько независимых проверок: одну на root, одну на эмулятор, одну
на Frida. Обход одной не помогает — остальные сработают. Кроме того, бывает «отложенный» детект:
приложение запускается нормально, а через 30 секунд молча завершает работу. Это затрудняет
отладку, потому что связь между причиной и следствием размыта. Правильный подход — найти ВСЕ
проверки: `strings` по всем библиотекам, анализ `__system_property_get`, перехват всех файловых
операций и логирование.

## Практический сценарий

Ты получил APK с защитой и хочешь снять её для анализа. Порядок: распаковать APK, выгрузить
строки из всех `.so` и DEX, составить список индикаторов, запустить приложение под Frida с
хуком на libc и записать все проверяемые пути и свойства. Затем — обойти каждую найденную
проверку (DenyList + перехват). После этого можно исследовать саму логику приложения.

## Перехват системных свойств

Кроме файловых проверок, детект часто читает системные свойства через `__system_property_get`.
Типичные свойства: `ro.debuggable`, `ro.secure`, `ro.build.tags`, `ro.product.model`. Функция
принимает имя свойства и буфер для результата. В дизассемблере ты видишь загрузку адреса строки
свойства и вызов `__system_property_get`, затем сравнение результата.

Обход через Frida:

```javascript
Interceptor.attach(Module.getExportByName(null, '__system_property_get'), {
  onEnter(args) { this.name = args[0].readCString() },
  onLeave(retval) {
    if (this.name === 'ro.debuggable' || this.name === 'ro.secure') {
      // переписать буфер — сложнее; проще хукнуть место сравнения
    }
  }
})
```

Проще хукнуть не саму функцию, а место, где результат сравнивается — там подменяется итог
проверки. Это общее правило: перехватывай точку принятия решения, а не источник данных.

## Проверка эмулятора по «железу»

Приложения могут проверять наличие сенсоров, камеры, телефонии. В эмуляторе их нет или они
фальшивые. Признаки: `SensorManager.getSensorList` возвращает пустой список, `TelephonyManager`
даёт `000000000000000`, `Build.FINGERPRINT` содержит `generic`. Для реверса это ещё одна группа
индикаторов, которую нужно искать. Обход — эмулировать наличие сенсоров или хукнуть методы,
возвращающие их список.

## Почему защита никогда не бывает абсолютной

Детект root/эмулятора/Frida — это гонка вооружений. Каждая новая проверка обходится новым
хуком, и наоборот. Для аналитика важно не «победить» защиту навсегда, а найти достаточно
проверок, чтобы приложение заработало в твоём окружении. Полный обход — это когда все
независимые проверки одновременно удовлетворены.
