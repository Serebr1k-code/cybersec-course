## Вопрос, с которого всё начинается

Ты запускаешь приложение на рутованном эмуляторе — и оно сразу закрывается или показывает «Устройство не поддерживается». Значит, внутри есть проверки root/эмулятора/Frida. Как их найти в бинарнике и понять, что именно они проверяют?

## Наш пример

Возьмём `libdetect.so` — нативную библиотеку, которая, судя по названию, занимается детектом. Начнём с того, что видно без декомпиляции:

```
$ strings -n 5 libdetect.so
/system/bin/su
/system/xbin/su
/sbin/su
frida-server
frida-agent
ro.build.tags=test-keys
ro.debuggable=1
```

Уже по строкам ясно, что проверяется: наличие бинарника `su`, файлов Frida и системных свойств, указывающих на нестандартную сборку.

## Шаг 1: три категории проверок

Детект на Android делится на три большие категории. **Root**: наличие `su` в типичных путях, установленный пакет `com.topjohnwu.magisk`, доступность `/system/xbin`. **Emulator**: свойства `ro.build.tags=test-keys`, `ro.debuggable=1`, отсутствие сенсоров, специфичные `ro.product.model` (например, `sdk_gphone`). **Инструментация**: порт Frida (27042), файлы `frida-server`, следы в `/proc/self/maps`.

Каждая категория оставляет **индикаторы** — строки, пути, номера портов. Твоя задача — найти эти индикаторы в бинарнике и понять, какой из них используется.

## Шаг 2: статический поиск индикаторов

Самый быстрый приём — grep по строкам. Но не только по `.so`: строки могут быть и в `classes.dex`. Разберём `libdetect.so` по секциям:

```
$ strings -n 4 libdetect.so | grep -iE 'su|frida|magisk|debuggable|test-keys'
/system/bin/su
/system/xbin/su
frida-server
ro.debuggable=1
```

Теперь ты знаешь, что функция проверяет эти пути. Дальше ищешь, **как** она это делает: `access()`/`stat()` для файлов, `__system_property_get` для свойств, `open` порта для Frida. Каждый вызов — «якорь», вокруг которого крутится логика.

## Шаг 3: найти код вокруг строки

Чтобы понять, где строка используется, нужен адрес. В ELF-секции `.rodata` строки лежат по фиксированным смещениям. Найдя смещение строки `/system/bin/su`, ты ищешь в `.text` инструкцию, которая загружает этот адрес (`adrp`/`add` в ARM64 или `lis`/`addi` в ARM32). Вокруг неё — вызов `access()` и условный переход.

Типичная картина (ARM64, упрощённо):

```
adrp x0, #str_su       ; адрес строки "/system/bin/su"
add  x0, x0, #:lo12:str_su
bl   access            ; проверить доступ
cbnz w0, rooted        ; если доступен — root найден
```

Логика проста: `access(path, F_OK)` возвращает 0, если файл существует. Ненулевой результат — ветка «чисто».

## Шаг 4: динамика — увидеть проверку в бою

Статики не всегда хватает: часть проверок спрятана в JNI или разбита на несколько функций. Тогда используется Frida: перехват `access`/`stat`/`open` и логирование аргументов.

```javascript
Interceptor.attach(Module.getExportByName(null, 'access'), {
  onEnter(args) { console.log('access:', args[0].readCString()) },
  onLeave(retval) { console.log('  ->', retval.toInt32()) }
})
```

Запускаешь — и видишь точный список путей, которые проверяет приложение. Это надёжнее, чем угадывать по строкам.

## Шаг 5: обход проверок

Есть несколько уровней обхода. **Скрыть root**: использовать Magisk с DenyList/Shamiko, чтобы `su` не был виден приложению. **Подменить ответ**: в Frida перехватить `access` и вернуть -1 (файл не найден) для путей `su`. **Патч в статике**: в `classes.dex` заменить условный переход, ведущий в ветку «rooted», на безусловный обход. **Убрать строку**: заменить `/system/bin/su` на несуществующий путь.

Важно понимать: разработчики знают об этих обходах, поэтому серьёзные приложения делают несколько независимых проверок и «отложенный» детект — реагируют не сразу, а через время, чтобы усложнить отладку. Тогда нужно найти ВСЕ проверки, а не одну.

## Шаг 6: находим артефакт практики

В нашей библиотеке среди строк есть сообщение, которое печатается, когда детект срабатывает. Достанем его:

```
$ strings -n 5 libdetect.so | grep nto
nto{r00t_d3t3ct_byp4ss3d}
```

## Что мы теперь знаем

- Детект делится на root / emulator / instrumentation, у каждой категории свои индикаторы.
- Индикаторы — это строки (пути, свойства) и вызовы (`access`, `__system_property_get`, `open`).
- Статически: найти строку → найти её адрес → найти код вокруг.
- Динамически: перехватить `access`/`stat`/`open` в Frida и увидеть реальные проверки.
- Обход: скрыть root (Magisk DenyList), подменить ответ (Frida hook), патчить переход или строку.
- Серьёзные приложения делают несколько независимых и отложенных проверок.
