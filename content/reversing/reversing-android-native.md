## Вопрос, с которого всё начинается

Ты разобрал APK, декомпилировал Java — а ключевая проверка оказалась в методе с модификатором `native`, без тела. Логика спрятана в файле `lib/arm64-v8a/libnative.so`. Как связать Java-метод с функцией в библиотеке и прочитать её, если это ARM64-код?

## Наш пример

Возьмём настоящую JNI-библиотеку `libnative.so`, собранную под Android ARM64:

```bash
$ file libnative.so
libnative.so: ELF 64-bit LSB shared object, ARM aarch64, version 1 (SYSV), dynamically linked, ...
$ readelf -h libnative.so | grep -E 'Class|Machine|Type'
  Class:                             ELF64
  Machine:                           AArch64
  Type:                              DYN (Shared object file)
```

Это обычный ELF-`.so`, но собранный под **AArch64** (ARM64). Значит, для дизассемблера нужна поддержка ARM — как в уроке про архитектуры. Ищем экспортируемые функции:

```bash
$ nm -D libnative.so
00000000000002fc T Java_com_example_app_Native_check
```

Вот она — функция, которую вызывает Java. Разберём, как получилось это имя.

## Шаг 1: JNI — как Java находит нативную функцию

Когда Java-метод объявлен `native`, JVM ищет его реализацию в загруженной библиотеке. По умолчанию действует **соглашение об именах JNI**: имя функции собирается из префикса `Java_`, имени пакета, класса и метода, где точки заменены на подчёркивания:

```text
Java_com_example_app_Native_check
      └ пакет com.example.app ┘ └ класс Native ┘ └ метод check ┘
```

То есть `com.example.app.Native.check()` в Java соответствует `Java_com_example_app_Native_check` в `.so`. Это золотое правило: **по экспорту `.so` можно восстановить Java-метод** и наоборот. Отсюда первый шаг реверса — `nm -D libnative.so` и поиск `Java_*`.

## Шаг 2: сигнатура JNI-функции

У JNI-функции особые первые два аргумента — их добавляет среда:

```c
JNIEXPORT jint JNICALL Java_com_example_app_Native_check(JNIEnv *env, jobject thiz, jint x);
```

- **`JNIEnv *env`** — указатель на таблицу функций JNI (через него Java вызывает нативные методы и наоборот).
- **`jobject thiz`** — объект, у которого вызван метод (`this`), либо `jclass` для статических.
- Дальше идут обычные аргументы (`jint x`).

Значит, пользовательский аргумент — **третий** (по ARM64-ABI он в регистре `w2`). Это важно: в дизассемблере первые два регистра «заняты» средой.

## Шаг 3: дизассемблируем ARM64

Посмотрим тело функции (через capstone, как в уроке про архитектуры):

```text
  0x02fc: sub    sp, sp, #0x10
  0x0300: str    w0, [sp, #0xc]     ; сохранить env (w0)
  0x0304: ldr    w9, [sp, #0xc]
  0x0308: mov    w10, #0x1337       ; константа
  0x0310: subs   w9, w9, w10        ; сравнить с x
  0x0314: csinc  w0, w8, wzr, ne    ; результат 0/1 в w0
  0x031c: ret
```

Читаем: `mov w10, #0x1337` — константа `0x1337`; `subs` сравнивает; `csinc w0, w8, wzr, ne` — условная установка результата (аналог `cmove`/тернарника). Функция возвращает 1, если аргумент равен `0x1337`. Та же логика `x == 0x1337`, что и везде, — только на ARM64.

## Шаг 4: динамическая регистрация — когда имён нет

Соглашение об именах можно обойти. Часто библиотека **регистрирует** функции в рантайме через `RegisterNatives`: тогда в экспорте будет только `JNI_OnLoad`, а имена методов спрятаны в таблице внутри кода. Признаки:

- экспорт `JNI_OnLoad` и почти пустой список `Java_*`;
- в `JNI_OnLoad` вызов `RegisterNatives` с массивом структур `{имя, сигнатура, указатель}`.

Тогда связь Java ↔ native ищут по этой таблице: строки-имена и сигнатуры лежат рядом в `.rodata`, а рядом — указатели на функции. Это стандартный приём обфускации в защищённых приложениях.

## Шаг 5: что усложняют и как это обходить

Нативные библиотеки в мобильной защите любят прятать логику:

- **Стриппинг** — убраны имена внутренних функций; помогает анализ по строкам и графу вызовов.
- **Обфускация (OLLVM)** — «сплющивание» графа (control-flow flattening), фиктивные переходы; читать тяжело, помогает динамика.
- **Шифрование кода** — тело функции расшифровывается в рантайме (иногда через `JNI_OnLoad`); тогда нужен дамп памяти.
- **Anti-debug/anti-root** — проверки `ptrace`, `frida-server`; обходят патчингом проверок или Frida с обходом.

Практический набор: **Ghidra** для статики (поддерживает ARM64 и JNI), **Frida** для динамики (перехват `Java_...` и `RegisterNatives`), `objdump`/capstone для быстрого просмотра.

## Шаг 6: как связать Java-метод с функцией

Быстрый практический алгоритм поиска связи:

1. **Из Java** (jadx) найди метод с `native` — запомни его класс и имя.
2. **В `.so`** ищи `Java_` + пакет + класс + метод через `nm -D`.
3. **Нет `Java_*`?** — ищи `JNI_OnLoad` и `RegisterNatives`: там таблица `{имя, сигнатура, указатель}`.
4. **Проверь сигнатуру** — первый аргумент `JNIEnv*`, второй `jobject`; дальше твои данные.
5. **Frida** — если имён нет совсем, повесь хук на `RegisterNatives` и распечатай таблицу в рантайме.

Этот порядок закрывает и статическую, и динамическую регистрацию — самый частый источник «функцию не нахожу».

## Шаг 7: полный прогон от начала до конца

Соберём разбор типичной native-задачи:

1. **`unzip -l app.apk | grep '\.so'`** — нашли `lib/arm64-v8a/libnative.so`.
2. **`file libnative.so`** — ARM aarch64.
3. **`nm -D libnative.so`** — экспорт `Java_com_example_app_Native_check`.
4. **Дизассемблируем** (Ghidra/capstone) — видим `mov w9, #0x1337; subs; csinc`.
5. **Читаем логику** — сравнение с константой; понимаем условие.
6. **Проверяем динамикой** — Frida-хук на функцию, подаём кандидатов, смотрим результат.

За шесть шагов native-библиотека разобрана. Если на шаге 4 код «сплющен» (OLLVM), переходим к динамике: хук и наблюдение часто быстрее, чем распутывание графа вручную.

## На что смотреть дальше

Порядок для незнакомой `.so`:

1. **`file` и `readelf -h`** — архитектура (arm64/arm32/x86) и тип (shared object).
2. **`nm -D`** — есть ли `Java_*` или `JNI_OnLoad`.
3. **`strings`** — пути, ключи, подсказки; часто видно, что проверяется.
4. **Дизассемблер** — Ghidra/IDA с ARM64; начать с экспортируемых функций.
5. **Динамика** — Frida: хук на функцию и её аргументы.

Не забывай: в JNI-функции первые два аргумента — среда, поэтому не путай `env`/`thiz` с данными. И проверяй, что смотришь нужную архитектуру: в APK их обычно несколько.

## Шаг 8: типичные сценарии native-задач

- **Прямая JNI-функция** — `Java_*` в экспорте; имя сразу ведёт к Java-методу.
- **Динамическая регистрация** — только `JNI_OnLoad`; ищи таблицу `RegisterNatives`.
- **Проверка строки** — функция сравнивает вход посимвольно; ищи цикл и сравнение байт.
- **Крипто в native** — AES/RC4 внутри `.so`; ищи константы (как в уроке про крипто).
- **Обфускация OLLVM** — «сплющенный» граф; переходи к динамике (Frida) вместо статики.

Общая стратегия: сначала `nm -D` и `strings`, потом дизассемблер, а если код нечитаем — сразу динамика. Не трать часы на распутывание OLLVM вручную.

## Что мы теперь знаем

- Нативные библиотеки Android — обычные ELF-`.so`, но под ARM64.
- JNI связывает Java-метод и функцию по имени `Java_пакет_класс_метод`.
- Первые два аргумента JNI-функции — `JNIEnv*` и `jobject`, пользовательские идут дальше.
- Связь может регистрироваться в рантайме через `RegisterNatives`/`JNI_OnLoad` — тогда имён в экспорте нет.
- Обфускация (стриппинг, OLLVM, шифрование кода) обходится статикой + динамикой (Ghidra + Frida).
