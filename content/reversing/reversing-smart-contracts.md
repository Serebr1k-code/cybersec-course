## Вопрос, с которого всё начинается

Ты разбираешь смарт-контракт Ethereum, но исходников нет — только **байткод**
на блокчейне. Контракт управляет деньгами, и надо понять, что он делает. Байткод
EVM — это не x86 и не ARM: у него своя архитектура, свой набор инструкций и
свои «регистры». Как его реверсить?

## Наш пример

Возьмём маленький контракт — его байткод в hex:

```
60003560005260206000f3
```

Дизассемблируем его (разберём байты по таблице опкодов EVM):

```
0000: PUSH1      0x00
0002: CALLDATALOAD
0003: PUSH1      0x00
0005: MSTORE
0006: PUSH1      0x20
0008: PUSH1      0x00
000a: RETURN
```

Прочитаем по шагам. EVM — **стековая машина**: инструкции работают не с
регистрами, а со **стеком**.

- `PUSH1 0x00` — положить на стек число 0.
- `CALLDATALOAD` — взять 32 байта входных данных по смещению со стека (0) и
  положить на стек.
- `PUSH1 0x00; MSTORE` — записать эти 32 байта в память по смещению 0.
- `PUSH1 0x20; PUSH1 0x00; RETURN` — вернуть 32 байта (`0x20`) начиная с
  смещения 0.

Итого контракт возвращает первые 32 байта своих входных данных — простейшее
«эхо». Уже из этого видно базовую механику EVM.

## Шаг 1: архитектура EVM

Что нужно знать:

- **Стек** — основное место для вычислений; глубина до 1024 элементов по 256 бит.
- **Память** (`memory`) — временная, байтовая, живёт в течение вызова.
- **Хранилище** (`storage`) — постоянное, ключ-значение, живёт между вызовами
  (это «состояние контракта»).
- **Calldata** — входные данные транзакции (неизменяемы).
- **Счётчик газа** (`gas`) — плата за вычисления; инструкции стоят по-разному.

Все числа — 256-битные (`uint256`), это важно: «обычное» переполнение тут
происходит по модулю 2^256.

## Шаг 2: диспетчер функций (function selector)

Настоящий контракт принимает разные вызовы. Различают их по **селектору** —
первым 4 байтам calldata, которые равны первым 4 байтам хэша `keccak256` от
сигнатуры функции (`transfer(address,uint256)` и т.п.). В байткоде это выглядит
как цепочка сравнений:

```
CALLDATASIZE
PUSH1 0x00
... CALLDATALOAD ; PUSH1 0xe0 ; SHR   ; получить селектор (старшие 4 байта)
DUP1 ; PUSH4 0xa9059cbb ; EQ ; PUSH2 <addr> ; JUMPI   ; transfer?
DUP1 ; PUSH4 0x70a08231 ; EQ ; PUSH2 <addr> ; JUMPI   ; balanceOf?
```

`SHR` — сдвиг вправо (чтобы оставить 4 байта), `EQ` — сравнение, `JUMPI` —
условный переход на обработчик. По константам-селекторам можно **опознать
функции**: `0xa9059cbb` — `transfer`, `0x70a08231` — `balanceOf`. Это как
таблица импортов, только для контракта.

## Шаг 3: где живёт состояние

**Storage** — постоянные данные. Чтение и запись:

- `SLOAD` — прочитать из storage по ключу (со стека);
- `SSTORE` — записать значение по ключу.

Слоты (ключи) часто вычисляются: например, `mapping(address => uint)` хранит
значение по ключу `keccak256(abi.encode(addr, slot))`. Поэтому при реверсе важно
понять, **какие слоты** используются и как вычисляются ключи. Балансы, владельцы,
флаги — всё это в storage.

## Шаг 4: типовые уязвимости

Разбирая контракт, ищут классические проблемы:

- **Reentrancy.** Контракт сначала отправляет эфир, потом меняет состояние; а
  получатель в своём `receive()` вызывает контракт снова — и цикл повторяется.
  Защита — паттерн «checks-effects-interactions» и `ReentrancyGuard`.
- **Целочисленное переполнение.** До Solidity 0.8 `uint` переполнялся молча;
  атака на балансы.
- **Access control.** Функции без проверки `msg.sender` (кто вызвал) —
  любой может слить средства.
- **`delegatecall`.** Вызов чужого кода в контексте своего storage — опасно,
  если адрес подконтролен.
- **Незащищённый `selfdestruct`.** Кто угодно может уничтожить контракт.
- **Front-running.** Видя транзакцию в мемпуле, атакующий опережает её.

## Шаг 5: инструменты

- **Etherscan** — показывает исходники, если контракт верифицирован; иначе
  байткод и дизассемблер.
- **Slither** — статический анализатор (ищет уязвимости в Solidity).
- **Mythril** — символический анализ байткода EVM (находит достижимые баги).
- **evm.codes / Panoramix** — декомпиляторы байткода в псевдокод.
- **Foundry / Hardhat** — фреймворки для локального запуска и тестов.

Полезно помнить про **верификацию**: если контракт верифицирован, у него есть
исходник и ABI (описание функций). Тогда реверс упрощается до чтения Solidity, а
байткод нужен лишь для проверки, что на цепочке лежит именно этот код.

## Шаг 6: практический маршрут

1. **Получить байткод** (Etherscan, RPC `eth_getCode`).
2. **Дизассемблировать** (Panoramix, evm.codes, свой скрипт).
3. **Найти диспетчер** и опознать функции по селекторам.
4. **Разобрать storage** — какие слоты, как считаются ключи.
5. **Проверить уязвимости** (Mythril/Slither + ручной разбор).
6. **Воспроизвести** на локальной сети (Foundry) перед выводами.

## Шаг 7: события, вызовы и газ

Ещё несколько элементов, которые видно в байткоде:

- **`LOG0`–`LOG4`** — запись событий (events) в журнал блокчейна. По ним
  приложения узнают о переводах и изменениях. В байткоде им предшествует
  `keccak`-хэш темы события.
- **`CALL`/`STATICCALL`/`DELEGATECALL`** — вызовы других контрактов. `CALL`
  может передавать эфир; `STATICCALL` — только чтение (без изменения состояния);
  `DELEGATECALL` — исполняет чужой код в своём контексте (частый источник багов).
- **`REVERT`** — откат с сообщением об ошибке (в байткоде видно строки вроде
  `"Insufficient balance"`).
- **Газ.** Каждая инструкция стоит газа. `SSTORE` дорогой, циклы по storage
  опасны (могут упереться в лимит газа). Иногда защита строится на «не хватит
  газа» — но это плохая практика.

По строкам-сообщениям (`require`-тексты) часто восстанавливают логику: они
попадают в байткод как данные и читаются как обычные строки.

## Частые вопросы

**Байткод не дизассемблируется.** Убедись, что это EVM-байткод (а не, скажем,
WASM или байткод другой сети). Начни с `PUSH1`/`PUSH32` и опкода `STOP`/`RETURN`
в конце.

**Как найти слот storage?** Смотри `SLOAD`/`SSTORE` и константы перед ними; для
`mapping` ключ вычисляется через `keccak256`. Восстанавливай по порядку
объявления переменных в Solidity (слоты идут подряд).

**Селектор не совпадает с известной функцией.** Возможно, это нестандартная или
скрытая функция; посмотри 4 байта как хэш и попробуй подобрать сигнатуру.

**Контракт верифицирован.** Тогда просто смотри исходник на Etherscan — но
проверяй, что байткод на цепочке совпадает с исходником (бывают расхождения).

## Что мы теперь знаем

- EVM — **стековая** 256-битная машина с памятью, постоянным storage и
  calldata; `PUSH`/`MSTORE`/`RETURN` работают со стеком.
- Наш мини-контракт `60003560005260206000f3` возвращает первые 32 байта входа
  (эхо).
- Функции различают по **селектору** (4 байта keccak сигнатуры); константы
  вроде `0xa9059cbb` = `transfer` опознают функцию.
- Состояние — в **storage** (`SLOAD`/`SSTORE`), ключи часто хэшируются.
- Типовые баги: reentrancy, overflow, отсутствие access control, `delegatecall`.
