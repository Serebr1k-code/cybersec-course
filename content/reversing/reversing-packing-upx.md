Упаковщик (packer) — первый слой, с которым сталкивается реверсер в ~половине реальных бинарников.
Packer сжимает/шифрует оригинальный код и добавляет распаковщик (stub), который в рантайме
восстанавливает оригинал в памяти. UPX — самый распространённый и самый простой упаковщик: он
бесплатный, кроссплатформенный, и его умеет распаковывать почти любой инструмент. Но UPX — лишь
верхушка: коммерческие протекторы (VMProtect, Themida, Enigma, ASPack) устроены куда сложнее.
Этот урок — про то, как распознать упаковку, снять UPX и вручную найти OEP у любого stub'а.

## Теория: как работает упаковщик

Стандартный packer делает три вещи:

1. **Сжимает/шифрует** секции оригинала (`.text`, `.data`) и кладёт их в новые секции.
2. **Добавляет stub** — распаковщик, который при старте:
   - выделяет память (`VirtualAlloc`/`mmap`),
   - распаковывает оригинальные секции,
   - восстанавливает таблицу импортов (IAT),
   - разрешает релокации,
   - передаёт управление на **OEP** (Original Entry Point).
3. **Меняет точку входа** PE/ELF на свой stub.

Признаки упаковки:

- Секции с именами `UPX0`/`UPX1`, `ASPack`, `.themida`, `.vmp0`, `.vmp1`, `enigma`.
- Высокая **энтропия** секций (близко к 8.0 бит/байт) — данные сжаты/зашифрованы.
- Мало импортов или только `LoadLibrary`/`GetProcAddress`.
- Точка входа в нестандартной секции.
- `file`/`die` (Detect It Easy) сообщают об упаковщике.

## Инструменты идентификации упаковщика

```bash
file ./target
die ./target                 # Detect It Easy: packer/compiler/protector
rabin2 -I ./target           # секции, энтропия
pepackcheck ./target         # PE-specific
python3 -c "import pefile" 2>/dev/null && pefile ./target  # PE headers
```

**`diec`** (CLI Detect It Easy) — самый информативный:
```bash
diec -d ./target
# Output:
# PE64
# Packer: UPX(3.95)[NRV,brute]
# Compiler: Microsoft Visual C/C++(19.29)
```

**Энтропия** секций через `rabin2`/`pefile` — если > 7.0, вероятно сжатие/шифрование:
```python
import pefile, math
pe = pefile.PE("target")
for s in pe.sections:
    data = s.get_data()
    ent = -sum((data.count(bytes([b]))/len(data))*math.log2(data.count(bytes([b]))/len(data))
               for b in set(data) if data.count(bytes([b])))
    print(s.Name.rstrip(b'\x00'), round(ent, 2))
```

## Снятие UPX: штатный путь

UPX-упакованные файлы распаковываются **самим UPX** — это самый надёжный способ:

```bash
upx -d ./packed -o ./unpacked          # распаковать
upx -l ./packed                        # информация без распаковки
upx -t ./packed                        # проверить целостность
```

Вывод:
```text
                       Ultimate Packer for eXecutables
  File size         Ratio      Format      Name
-------------------- ------ ----------- -----------
   123456 <-    45678   37.05%    linux/elf   packed
```

Частая проблема: **модифицированный UPX**. Авторы вредоносов правят заголовок UPX-секции
(например, меняют `UPX!` magic на `UPX0`), и `upx -d` отказывается: `CantUnpackException: header
corrupted`. Решения:

- Восстановить оригинальные имена/флаги секций (в PE — правкой заголовков через `pefile`).
- Использовать форк **`upx`** или скрипт `upx_fix`.
- Распаковать вручную (см. ниже).

## Ручная распаковка: поиск OEP

Когда автоматика не сработала, распаковываем вручную. Классический алгоритм (x86/x64, PE):

**Шаг 1. Открыть в x64dbg/IDA, дойти до stub.** Точка входа — распаковщик. Часто видим цикл
распаковки и вызов `VirtualAlloc`/`VirtualProtect`.

**Шаг 2. Найти переход на OEP.** Типовые приёмы:

- **Breakpoint на `VirtualProtect`** — stub снимает защиту с распакованной секции перед передачей
  управления; после вызова делаем шаг и попадаем на OEP.
  ```text
  x64dbg> bp VirtualProtect
  x64dbg> run
  # после срабатывания — F8 (step over), затем идём по коду
  ```
- **Hardware breakpoint на `esp`/`rsp`** (для pushad/popad-stub'ов): UPX часто сохраняет регистры
  `pushad`, распаковывает, потом `popad` и `jmp OEP`. Ставим аппаратную точку на `esp` после
  `pushad` — сработает на `popad`, рядом OEP.
- **Точка на `jmp`/`call` в свежераспакованную память** — stub всегда прыгает в новый регион.
- **`Scylla`/`PE-sieve`** — автоматически находят OEP и дампят процесс.

**Шаг 3. Дамп памяти.** Когда дошли до OEP:
```text
x64dbg: Plugins → Scylla → Dump
```
Или через `proc dump` в IDA, или `pe-sieve`:
```bash
pe-sieve /pid <PID> /out ./dumped
```

**Шаг 4. Починить IAT.** После дампа таблица импортов часто «сломана». Scylla:
```text
1. IAT Autosearch → Get Imports
2. Проверить/добавить недостающие записи
3. Fix Dump → выбрать ранее сохранённый дамп
```
Получаем рабочий распакованный PE.

**Шаг 5. Проверить.** Открыть дамп в IDA/Ghidra — теперь видны настоящие функции, строки, импорты.

## Разобранный пример: ручная распаковка UPX-ELF

Дано: Linux ELF, упакован UPX. `upx -d` падает (модифицированный).

**Шаг 1. Запускаем под gdb:**
```bash
gdb -q ./packed
(gdb) set disassembly-flavor intel
(gdb) b *0x400000+_start   # или info files → Entry point
(gdb) run
```

**Шаг 2. Ищем OEP по `mmap`/`mprotect`.** UPX-ELF использует `mmap` для распаковки:
```text
(gdb) catch syscall mmap
(gdb) catch syscall mprotect
(gdb) continue
# после mprotect с PROT_EXEC — распаковка завершена
```
Ставим breakpoint на адрес возврата и идём дальше — попадаем на OEP.

**Шаг 3. Дамп.** Через gdb:
```text
(gdb) info proc mappings        # найти регион оригинала
(gdb) dump memory /tmp/orig.bin 0x400000 0x4b0000
```
Затем реконструируем ELF-заголовки (например, `unstrip`/`lief` или вручную).

**Шаг 4. Восстановление с помощью `lief`:**
```python
import lief
b = lief.parse("packed")
# ... правка сегментов/entrypoint по дампу
b.write("unpacked")
```

## Альтернативы: Unicorn-эмуляция и автоматизация

Для сложных stub'ов помогает **эмуляция**: загружаем секции в Unicorn, эмулируем stub до передачи
управления на адрес, лежащий в другой (распакованной) области — это и есть OEP.

```python
from unicorn import Uc, UC_ARCH_X86, UC_MODE_64
from unicorn.x86_const import UC_X86_REG_RIP
mu = Uc(UC_ARCH_X86, UC_MODE_64)
mu.mem_map(0x400000, 0x200000)
mu.mem_write(0x400000, open("packed","rb").read())
oep = None
def hook(mu, addr, size, user):
    global oep
    rip = mu.reg_read(UC_X86_REG_RIP)
    if rip != addr:      # управление ушло в другое место
        oep = rip
        mu.emu_stop()
mu.hook_add(UC_HOOK_CODE, hook)
mu.emu_start(0x400000 + entry_off, 0, count=10_000_000)
print("OEP = 0x%x" % oep)
```

Для партий образцов: **PE-sieve**, **UnpacMe** (сервис), **x64dbg + скрипты**, **`unipacker`**
(автоматический распаковщик на Unicorn).

## Крайние случаи и подводные камни

- **Модифицированный UPX.** Правленые имена секций/заголовки ломают `upx -d` — распаковывайте вручную.
- **Anti-dump.** Некоторые packer'ы обнуляют заголовки в памяти (`.themida`), чтобы дамп не запускался.
  Лечится восстановлением заголовков из файла (`Scylla` → `PE Rebuild`).
- **Anti-debug в stub.** Stub может детектить отладчик — используйте ScyllaHide.
- **Несколько слоёв упаковки.** Файл может быть упакован UPX, внутри — ещё один packer. Распаковывайте
  послойно, проверяя энтропию после каждого слоя.
- **TLS callbacks.** В PE распаковщик может запускаться из TLS-callback до точки входа — тогда
  breakpoint на entry не срабатывает; ставьте точки на `LdrpCallInitRoutine`/TLS.
- **Дамп ≠ корректный PE.** Всегда проверяйте дамп: открывается ли, работают ли импорты, нет ли
  «битых» вызовов. Чинить IAT обязательно.
- **Юридическая сторона.** Распаковка malware — только в изолированной среде.

## Что дальше / решение

1. Определить упаковщик: `die`, `rabin2 -I`, энтропия, имена секций.
2. Попробовать `upx -d` (для UPX) — самый быстрый путь.
3. Если не вышло — ручная распаковка: найти OEP (breakpoint на `VirtualProtect`/`mprotect`,
   аппаратная точка на `esp`, эмуляция), дампнуть, починить IAT (Scylla), проверить.
4. Для партий — `pe-sieve`/`unipacker`.
5. Распакованный файл — снова прогнать через `die` (не осталось ли второго слоя) и только потом
   реверсить.

Методологический принцип: **никогда не реверсите упакованный код** — это пустая трата времени.
Сначала снять упаковку, потом анализ.

## Проверка результата распаковки

Распакованный файл **не всегда корректен** — дамп памяти ≠ валидный PE/ELF. Чек-лист проверки:

1. **Открывается ли загрузчиком.** Для PE — `pe-sieve`/`PE-bear`; для ELF — запуск и `readelf`.
2. **Импорты.** `rabin2 -i unpacked` — если список пуст или адреса вида `0x7ff...`, IAT сломан,
   нужно чинить (Scylla → Fix Dump).
3. **Энтропия секций.** `rabin2 -S unpacked` — энтропия должна упасть (была ~7.9, стала ~6.0).
4. **Строки.** `strings -a unpacked | head` — появились осмысленные строки/имена функций.
5. **Точка входа.** Теперь entry должна указывать в `.text` оригинала, а не в stub.
6. **Запуск в песочнице.** Убедиться, что программа работает так же, как оригинал.

Если после распаковки файл всё ещё «странный» — вероятно, **второй слой** (проверьте `die` снова).

## Другие упаковщики: краткий обзор

| Packer | Признак | Особенность |
|---|---|---|
| UPX | `UPX0/UPX1` | простой, распаковывается `upx -d` |
| ASPack | секции `.aspack`/`.adata` | сжатие, простой stub |
| FSG | маленький файл, 2 секции | простой, есть скрипты распаковки |
| MPRESS | секция `.MPRESS1` | сжатие LZMA |
| Petite | `petite` в секции | самораспаковка |
| Themida/WinLicense | `.themida`, `.winlice` | тяжёлый протектор, anti-dump, виртуализация |
| VMProtect | `.vmp0/.vmp1` | виртуализация критичного кода |
| Enigma | `enigma1/2` | коммерческий, лицензии |

Для ASPack/FSG/MPRESS есть готовые распаковщики и скрипты x64dbg; Themida/VMProtect — уровень
профессионального реверса (нужны devirtualization и борьба с anti-debug).

## Автоматизация распаковки

Для партий образцов полезно автоматизировать:

- **`unipacker`** — распаковывает UPX и др. через Unicorn, эмулируя stub и перехватывая передачу
  управления на OEP.
- **`pe-sieve`** — запускает процесс, ждёт распаковки, дампит.
- **Скрипт на Unicorn** — для самодельных stub'ов: эмулировать до перехода в новый регион.
- **`mal_unpack`** — автоматический распаковщик с перехватом записи-исполнения (W+X).

Общий подход: **перехватить момент, когда stub передаёт управление в свежераспакованный код** —
это и есть OEP. Реализуется либо breakpoint'ом на `jmp`/`call`, либо детектом записи с правом
исполнения (NX-нарушение), либо эмуляцией.

## Где пригодится

- **CTF Reversing (hard):** упакованные бинарники — частый барьер; UPX решается за минуты.
- **Malware analysis:** большинство образцов упакованы; распаковка — обязательный первый шаг.
- **Аудит ПО:** оценка стойкости защиты, снятие протектора для анализа.
- **Vuln research:** разбор прошивок и закрытых бинарников после снятия упаковки.
- **Собес:** вопросы про OEP, DIE, энтропию, UPX — стандартный набор RE-интервью.
