## Вопрос, с которого всё начинается

Ты открываешь бинарник в дизассемблере, а там вместо понятного кода — короткий «загрузчик» и куча
нечитаемых байт. Строк почти нет, импортов минимум, секции с именами `UPX0`, `UPX1`. Это значит,
файл **упакован**: настоящий код сжат или зашифрован, а при запуске распаковывается в памяти.
Как определить упаковку и достать оригинальный код?

Опираемся на прошлый урок: там мы снимали проверку среды. Здесь задача глубже — сначала нужно
вообще получить код, который эту проверку делает.

## Как устроен упаковщик

**Упаковщик** (packer) делает три вещи:

1. **Сжимает или шифрует** оригинальные секции (`.text`, `.data`) и кладёт результат в новые секции.
2. **Добавляет stub** — маленький распаковщик, который при старте выделяет память, распаковывает
   оригинал, восстанавливает таблицу импортов и передаёт управление на **OEP** (Original Entry
   Point — настоящая точка входа оригинальной программы).
3. **Меняет точку входа** ELF/PE на свой stub.

Значит, реверс упакованного файла — это всегда «двухходовка»: сначала снять слой упаковки, потом
разбирать то, что внутри. **UPX** (Ultimate Packer for eXecutables) — самый распространённый
упаковщик: бесплатный, кроссплатформенный, и почти все инструменты умеют его распаковывать. Он —
хорошая учебная модель: на нём видно все признаки упаковки, но снять её проще всего.

## Шаг 1: признаки упаковки

Возьмём файл, у которого есть характерные секции упаковщика, и посмотрим на его заголовки:

```
$ readelf -S packed_like | grep -E 'UPX|\.text'
  [12] .text   PROGBITS   0000000000401040  00001040
  [27] UPX1    PROGBITS   0000000000000000  00003033
  [28] UPX0    PROGBITS   0000000000000000  00003170
```

Имена `UPX0`/`UPX1` — прямой отпечаток UPX. У других упаковщиков будут свои: `ASPack`, `.themida`,
`.vmp0`/`.vmp1` (VMProtect), `enigma`. Второй признак — сигнатуры в строках:

```
$ strings -n 4 packed_like | grep -i upx
UPX!x
UPX1
UPX0
```

Магия `UPX!` в начале упакованных данных — визитная карточка. Третий, самый надёжный признак —
**энтропия**. Энтропия измеряет «случайность» байтов в битах на байт: у обычного кода она около
4–5, у сжатых/зашифрованных данных — ближе к 8. Сравним сжатый блок и обычный код:

```
UPX1              size= 317 entropy=7.07 bits/byte
.text slice       size=2048 entropy=1.53 bits/byte
```

Блок `UPX1` почти максимально «шумный» — это сжатые данные. Участок обычного кода — почти
предсказуемый (много нулей и повторяющихся байтов), энтропия 1.53. Разница видна сразу.

## Шаг 2: распаковка UPX

Для настоящего UPX есть готовая команда:

```
$ upx -d packed_binary -o unpacked_binary
```

`-d` значит decompress. UPX узнаёт свой stub, распаковывает секции, восстанавливает точку входа и
пишет нормальный исполняемый файл. Важная тонкость: UPX можно «подкрутить» (изменить байты stub,
сигнатуру), и тогда `upx -d` откажется работать — файл выглядит упакованным, но не распознаётся.
Тогда распаковку делают вручную. В нашей лаборатории `upx` не установлен, поэтому ручной способ
покажем на самодельном стабе — он устроен ровно так же.

## Шаг 3: ручная распаковка на самодельном стабе

Соберём минимальный «упакованный» файл: полезная нагрузка зашифрована XOR'ом с ключом `0xAA`, а
стаб при запуске расшифровывает её в памяти и вызывает.

```c
unsigned char blob[] = {0x12,0x80,0xAA,0xAA,0xAA,0x69};  /* xor 0xAA -> mov eax,42; ret */
int main(void){
    unsigned long pg = (unsigned long)blob & ~0xfffUL;
    sc(10, pg, 0x1000, 7);                    /* mprotect(...,RWX) — разрешить исполнение */
    for (unsigned i=0;i<sizeof(blob);i++) blob[i]^=0xAA;
    int (*f)(void) = (int(*)(void))blob;      /* вызываем расшифрованное как функцию */
    printf("decoded result = %d\n", f());
}
```

Это ровно модель упаковщика: `blob` — «упакованная» секция, `main` — стаб. Запуск:

```
$ ./stub
decoded result = 42
```

Чтобы снять упаковку вручную, ставим точку останова на момент **после** расшифровки, но **до**
вызова расшифрованного кода, и смотрим память:

```
$ gdb -q -batch -ex 'break *0x4011b3' -ex run -ex 'x/6xb &blob' ./stub
0x404018 <blob>:  0xb8  0x2a  0x00  0x00  0x00  0xc3
```

Шесть байтов `b8 2a 00 00 00 c3` — это уже настоящий код: `mov eax, 42; ret` (байт `b8` — опкод
`mov eax, imm32`). В момент до расшифровки там лежало `12 80 AA AA AA 69`. Мы нашли **OEP** — точку,
куда стаб передаёт управление. Именно на этой точке в настоящих пакерах снимают дамп памяти и
восстанавливают таблицу импортов (IAT), чтобы получить рабочий распакованный файл.

## Шаг 4: что делать с кастомными пакерами

Коммерческие и самописные упаковщики устроены сложнее UPX: несколько слоёв шифрования, проверки
целостности, анти-отладка. Универсальный рецепт:

1. Найти цикл распаковки (часто это `rep movs`/`memcpy` из одной секции в другую).
2. Поставить breakpoint на **запись** в будущую область кода или на передачу управления по адресу
   вне стаба — это и есть OEP.
3. Снять дамп памяти и пересобрать импорты (в PE — Scylla, в ELF — проще, импорты обычно резолвятся
   лениво через PLT).

Если стаб расшифровывает данные **по мере выполнения** (self-modifying), статический дамп бесполезен
— тогда идут через эмуляцию: прогоняют stub в эмуляторе и забирают память после распаковки. Об этом
— в следующих уроках.

## Шаг 5: измеряем энтропию сами

Энтропия звучит как что-то из теории информации, но считается она одной формулой, и её легко
посчитать на любом блоке. Идея: если байты распределены равномерно (все 256 значений одинаково
часты), энтропия максимальна и равна 8 бит/байт; если почти все байты одинаковы — близка к нулю.

```python
import math, collections
def entropy(data: bytes) -> float:
    n = len(data)
    counts = collections.Counter(data)
    return -sum((c/n) * math.log2(c/n) for c in counts.values())

packed = open('packed_like','rb').read()[0x3033:0x3033+317]   # блок UPX1
plain  = open('packed_like','rb').read()[0x1040:0x1040+2048]  # кусок .text
print(f"UPX1: {entropy(packed):.2f}")   # 7.07
print(f".text: {entropy(plain):.2f}")   # 1.53
```

Считаем энтропию по **байтовым частотам**: чем ровнее распределение, тем выше число. У блока `UPX1`
получаем ≈7.07 — сжатые данные почти случайны. У участка обычного кода ≈1.53 — там много нулей и
повторяющихся байтов. Эта пара чисел и есть автоматический детектор упаковки: инструменты вроде
`ent`, `Detect It Easy` (DIE) и `binwalk` делают ровно это по всем секциям.

Важная оговорка: высокая энтропия — **не доказательство** упаковки. Зашифрованные данные, сжатые
ресурсы (картинки, шрифты), уже сжатые медиа — всё это тоже шумное. Поэтому энтропию смотрят вместе
с именами секций и сигнатурами: три признака вместе дают уверенный вывод, а по отдельности могут
обмануть.

На практике удобен такой порядок: сначала `die`/`strings` дают имена секций и сигнатуры, затем `ent`
или `binwalk -E` подтверждают энтропией, и только после этого выбирается способ снятия —
автоматический `upx -d` или ручной дамп с восстановлением импортов.

## Как это видят защитники

Для антивируса и EDR упаковка — сам по себе индикатор риска: легитимный софт редко упакован, а
вредоносный — почти всегда. Практические маркеры, по которым срабатывает эвристика:

- **энтропия секций кода > 7** при крошечной таблице импортов;
- **`mprotect`/`VirtualProtect` со сменой прав на исполняемые** сразу после старта;
- **запись в собственные секции `.text`/`.data`** (self-modifying);
- **имя секции-упаковщика** в заголовке (`UPX0`, `.vmp0`, `.themida`).

Отсюда и обратный вывод для реверсера: если ты видишь эти признаки, ты почти наверняка имеешь дело
с упаковкой, и первым шагом должно быть её снятие, а не чтение «кода» в дизассемблере.

## Если не сработало

- **`upx -d` говорит `not packed by UPX`** — stub модифицирован. Проверь байты вокруг магии `UPX!`:
  если изменены версия или размеры, восстанови их по формату или распаковывай вручную.
- **Дамп памяти не запускается** — не восстановлена таблица импортов (IAT). В PE её чинят через
  Scylla; в ELF импорты обычно резолвятся лениво через PLT, поэтому дамп часто работает сразу.
- **Энтропия низкая, а код непонятный** — возможно, это не упаковка, а **обфускация**: код
  валиден, но специально запутан. Это следующий слой, и снимается он иначе.
- **Несколько слоёв упаковки** — после первого `upx -d` прогони детект заново: файл может быть
  упакован ещё раз (например, UPX внутри кастомного стаба).

## Что мы теперь знаем

- Упаковщик = **сжатие/шифрование + stub + смена точки входа**; оригинал восстанавливается в памяти.
- Признаки упаковки: имена секций (`UPX0`/`UPX1`, `.vmp0`, `.themida`), строки-сигнатуры (`UPX!`),
  **высокая энтропия** (≈7–8 бит/байт против 4–5 у кода).
- UPX снимается командой `upx -d`; модифицированный UPX и кастомные пакеры — вручную.
- Ручная распаковка = найти **OEP** (момент передачи управления оригиналу), снять дамп, восстановить
  импорты.

## Куда дальше

Мы сняли внешний слой — упаковку. Дальше возьмём код, который распаковался, и увидим, что он тоже
специально испорчен: **обфусцирован**. Посмотрим, как распознать обфускацию и control-flow
flattening. А пока главное запомни: **упакованный файл — это стаб плюс сжатый оригинал, и OEP — та
точка, где стаб отдаёт управление настоящему коду**.

## Где пригодится

- **CTF Reversing (hard):** большинство «сложных» задач начинаются с упаковщика.
- **Malware analysis:** снять упаковку — первый шаг к анализу семейства.
- **Анализ защищённого ПО:** понять, сколько слоёв защиты и где границы стаба.
- **Detection:** энтропия и имена секций — быстрые индикаторы для сканеров.
- **Собес:** вопрос «как найти OEP?» — базовый для RE-позиций.
