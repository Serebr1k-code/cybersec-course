## Вопрос, с которого всё начинается

На CTF иногда попадается бинарник на 800 килобайт, внутри которого не видно ни одной знакомой функции вроде `puts` — все вызовы «вшиты» прямо в файл. Или наоборот: файл на 16 килобайт, а половина кода где-то в системе. Почему так? Ответ — в способе **компоновки** (linking). От него зависит и размер файла, и то, как ты будешь его реверсить.

## Наш пример

Соберём одну и ту же программу двумя способами — динамически и статически:

```bash
$ gcc -o hello_dyn hello.c        # динамическая
$ gcc -static -o hello_static hello.c   # статическая
$ ls -la hello_static hello_dyn
778440  hello_static
 15896  hello_dyn
```

Один и тот же код — а разница в размере почти в 50 раз. Смотрим, что это за файлы:

```bash
$ file hello_dyn hello_static
hello_dyn:    ELF 64-bit LSB pie executable, x86-64, dynamically linked, ...
hello_static: ELF 64-bit LSB executable, x86-64, statically linked, ...
```

Вот ключевые слова: **dynamically linked** и **statically linked**. Разберём, что за ними стоит.

## Шаг 1: динамическая компоновка — «одолжи код у системы»

При динамической сборке компилятор не копирует библиотечные функции в файл. Вместо этого он записывает: «мне нужна `libc.so.6`» — и оставляет вызовы как заглушки. Проверим:

```bash
$ readelf -d hello_dyn | grep NEEDED
 (NEEDED)  Shared library: [libc.so.6]
$ ldd hello_dyn
	libc.so.6 => /usr/lib/libc.so.6 (0x00007f7814ef8000)
	/lib64/ld-linux-x86-64.so.2 => /usr/lib64/ld-linux-x86-64.so.2 (...)
```

`NEEDED` говорит, что нужна `libc.so.6`; `ldd` показывает, где она нашлась. Когда программа запускается, **загрузчик** (`ld-linux`) подгружает libc в память и подставляет адреса функций. Поэтому файл маленький: вся библиотека лежит в системе **одна** и делится между всеми процессами.

## Шаг 2: статическая компоновка — «вшить всё в файл»

При статической сборке линкер берёт код нужных функций из библиотечного архива `libc.a` и **копирует его прямо в исполняемый файл**. Проверим, что внешних зависимостей нет:

```bash
$ ldd hello_static
	not a dynamic executable
$ readelf -d hello_static
There is no dynamic section in this file.
```

Нет динамической секции, нет `NEEDED`, `ldd` отказывается. Зато посмотрим на объём кода:

```bash
$ size hello_static hello_dyn
   text    data     bss     dec     hex filename
 656760   22840   22560  702160   ab6d0 hello_static
   1292     584       8    1884    75c hello_dyn
```

У статического — 656 КБ кода, у динамического — 1 КБ. Это и есть та самая разница: статический файл таскает за собой весь нужный кусок libc. Зато он **независим**: запустится на любой Linux-системе без библиотек.

## Шаг 3: что это значит для реверса

Разница для тебя практическая:

- **Динамический бинарник** — компактный, но логика размазана: часть функций в libc. В дизассемблере вызовы идут через PLT (`call puts@plt`), а сами реализации ты смотришь в отдельной libc.
- **Статический бинарник** — всё внутри, включая реализации `printf`, `strcmp` и т.д. Имена могут сохраниться, но если бинарник **stripped**, то различать «свой» код и вшитый libc придётся по сигнатурам. Инструменты (Ghidra, FLIRT/IDB) умеют опознавать стандартные функции по байтовым шаблонам — это экономит часы.

Правило простое: **чем больше файл без явных строк-подсказок, тем вероятнее статика**. На CTF статические бинарники дают, чтобы ты не мог «одолжить» анализ у системной libc.

## Шаг 4: кто именно грузит динамический файл

У динамического бинарника в заголовке есть запись `INTERP` — путь к программе-загрузчику:

```bash
$ readelf -l hello_dyn | grep -A1 INTERP
  INTERP  0x000000000000033c ... 
      [Requesting program interpreter: /lib64/ld-linux-x86-64.so.2]
```

Ядро, запуская `hello_dyn`, сначала запускает `ld-linux-x86-64.so.2`. Уже он читает `NEEDED`, подгружает `libc.so.6`, применяет релокации и только потом передаёт управление точке входа программы. У статического файла записи `INTERP` нет — ядру не нужен посредник, оно само загружает образ и прыгает на точку входа. Отсюда и практический признак: **есть `INTERP` — динамика, нет — статика**.

## Шаг 5: подмена функций — LD_PRELOAD

У динамической компоновки есть свойство, которое важно и для атак, и для анализа. Раз адреса функций подставляются при загрузке, можно заставить процесс взять **твою** реализацию вместо системной. В Linux это делает переменная `LD_PRELOAD`:

```bash
$ LD_PRELOAD=./hook.so ./hello_dyn
```

Если `hook.so` экспортирует функцию `puts`, её вызовы в `hello_dyn` уйдут в твой хук, а не в libc. Так перехватывают функции для трассировки (что делает Frida) и так же прячутся некоторые руткиты. Аналог в Windows — «DLL hijack» (подмена библиотеки с тем же именем). Для реверса это приём №1, чтобы понять, с какими аргументами программа зовёт `strcmp` или `memcmp`.

## Шаг 6: как определить модель за пять секунд

Соберём признаки в один список — по нему ты за минуту поймёшь, что за бинарник перед тобой:

| Признак | Динамический | Статический |
|---|---|---|
| `file` | `dynamically linked` | `statically linked` |
| `ldd` | список библиотек | `not a dynamic executable` |
| `readelf -d` | есть `.dynamic`, `NEEDED` | `There is no dynamic section` |
| `readelf -l` | есть `INTERP` | нет `INTERP` |
| размер | десятки КБ | сотни КБ – мегабайты |

Этого набора достаточно для первого вывода о бинарнике — ещё до дизассемблера. На CTF полезно ещё глянуть `strings`: статический бинарник часто выдаёт имена вшитых функций (`strcmp`, `malloc`), по которым можно ориентироваться в дизассемблере.

## Шаг 7: зачем это знать про малварь

Модель компоновки — не академическая деталь. Статически слинкованные образцы малвари (некоторые семейства на Go и Rust) весят десятки мегабайт и содержат весь рантайм — их сложно анализировать, но они не зависят от библиотек жертвы. Динамические образцы меньше, но их поведение частично «спрятано» в системных библиотеках, и перехват через `LD_PRELOAD`/DLL-hijack даёт быстрый способ увидеть, что они зовут.

Ещё один практический момент: **pwn**. Статический бинарник тащит свои реализации `system`, `strlen` и т.д. — для ret2libc это меняет, куда прыгать. Динамический же зависит от libc системы, и адреса утекают через GOT. Поэтому первый вопрос при разборе эксплойта — «динамика или статика?».

## Что мы теперь знаем

- **Динамическая** сборка оставляет зависимости (`NEEDED`), файл маленький, код в общей библиотеке.
- **Статическая** вшивает код библиотек в файл: нет `.dynamic`, нет `NEEDED`, файл в десятки раз больше.
- `ldd` и `readelf -d` отличают одно от другого за секунду.
- **`LD_PRELOAD`** позволяет подменить функцию при загрузке — основа перехвата и анализа.

## Куда дальше

Мы увидели, что при динамической сборке адреса функций подставляются позже — значит, в файле должны быть специальные пометки, какие адреса куда подставить. Эти пометки называются **релокациями**, а имена функций — **символами**. Как их читать и что делать, если имена удалены (`stripped`) — в следующем уроке. А пока запомни: `ldd` — динамика или нет, `readelf -d` — зависимости, `LD_PRELOAD` — перехват.

## Где пригодится

- **CTF Reversing:** большие stripped-бинарники почти всегда статические; понимание этого задаёт стратегию анализа.
- **Malware analysis:** часть малвари линкуется статически, чтобы не зависеть от библиотек жертвы — и это видно по размеру и отсутствию `NEEDED`.
- **Vuln research:** `LD_PRELOAD` и DLL hijack — реальные векторы повышения привилегий и перехвата.
- **Инструментарий:** трассировка аргументов функций (Frida, ltrace) опирается на динамическую подстановку.
