Прежде чем программа запустится, линкер решает фундаментальный вопрос: включать код библиотек внутрь
файла или подключать их во время выполнения. От этого выбора зависит размер бинарника, наличие
PLT/GOT, поведение под ASLR, переносимость и сложность реверса. Реверс-инженер обязан уметь
определить модель компоновки с первого взгляда — от неё зависит вся стратегия анализа.

## Статическая компоновка

При статической компоновке (`gcc -static`) код всех используемых библиотек копируется прямо в
итоговый бинарник. Внешних зависимостей нет: файл самодостаточен и запустится даже там, где нет
нужной libc. Обратная сторона — размер: простейшая программа «Hello, world» может весить больше
мегабайта, потому что включает реализацию `printf`, `malloc` и всего, что они тянут за собой.

В статическом бинарнике нет `.plt`/`.got.plt` в привычном смысле (нет внешних символов для
ленивого связывания), нет `PT_INTERP`, нет `.dynsym`. Зато `.text` огромен и содержит весь
библиотечный код. Плюс: ASLR не перемещает сам код (если не собрано с `-static-pie`), адреса
фиксированы, и это упрощает эксплуатацию. Минус для аналитика: сложнее найти «свою» логику среди
тысяч библиотечных функций.

## Динамическая компоновка

Динамическая компоновка (по умолчанию) оставляет библиотечный код в отдельных `.so`-файлах,
подключаемых загрузчиком. Бинарник маленький, зависимости перечислены в `.dynamic` (`DT_NEEDED`),
внешние вызовы идут через PLT/GOT. Плюсы: экономия памяти (одна копия libc на все процессы),
возможность обновлять библиотеки без пересборки. Минусы: зависимость от наличия нужных версий
(«DLL hell» в Linux-варианте), необходимость ASLR-совместимой релокации, уязвимость к подмене
библиотек.

## Статические бинарники и libc

Статически слинкованные бинарники часто встречаются в CTF и в embedded-системах (busybox, прошивки).
Определить их просто: `file ./bin` покажет `statically linked`, а `ldd ./bin` ответит `not a dynamic
executable`. Для анализа это означает:

- **Нет PLT/GOT**: вызовы `printf` идут напрямую, но имя символа может сохраниться (если не
  stripped).
- **Огромный `.text`**: библиотечные функции внутри; полезно использовать сигнатуры (`FLIRT` в
  IDA, `lumina`, `Ghidra Function ID`), чтобы автоматически распознать libc-код и отсеять его.
- **Фиксированные адреса** (без `-static-pie`): ROP-гаджеты находятся по статическим адресам.
- **Версия libc встроена**: по строкам и коду можно определить версию и найти known-гаджеты.

С `-static-pie` бинарник становится перемещаемым целиком, что возвращает ASLR, но сохраняет
самодостаточность.

## LD_PRELOAD и перехват

Динамическая компоновка открывает возможность подмены функций. Механизм `LD_PRELOAD` заставляет
загрузчик подгрузить указанную библиотеку раньше остальных; при разрешении символа первой находится
подменённая реализация. Так перехватывают `malloc`, `read`, `open`, `time` — что угодно.

Пример библиотеки-перехватчика:

```c
#define _GNU_SOURCE
#include <stdio.h>
#include <dlfcn.h>
int puts(const char *s) {
    static int (*real)(const char*) = NULL;
    if (!real) real = dlsym(RTLD_NEXT, "puts");
    real("intercepted!");
    return real(s);
}
```

Сборка и запуск: `gcc -shared -fPIC -o hook.so hook.c -ldl`, затем
`LD_PRELOAD=./hook.so ./target`. Каждый вызов `puts` пройдёт через ваш код. Это мощный инструмент
и для реверса (трассировка вызовов), и для атаки (обход проверок), и для отладки. Обратите
внимание: `dlsym(RTLD_NEXT, ...)` ищет «следующую» реализацию, чтобы вызвать оригинал.

Аналогично `LD_LIBRARY_PATH` подменяет каталог поиска библиотек, а `rpath`/`$ORIGIN` — путь внутри
бинарника. Всё это векторы для подмены библиотек, особенно в привилегированных программах без
защиты.

## Практический разбор: собираем оба варианта

Соберём динамический и статический варианты и сравним:

```
$ gcc -O0 -o dyn hello.c
$ gcc -O0 -static -o stat hello.c
$ ls -lh dyn stat
-rwxr-xr-x 1 u u  16K dyn
-rwxr-xr-x 1 u u 760K stat

$ file dyn stat
dyn:  ELF 64-bit LSB pie executable, dynamically linked, interpreter /lib64/ld-linux-x86-64.so.2
stat: ELF 64-bit LSB executable, statically linked, for GNU/Linux 3.2.0

$ ldd dyn
	linux-vdso.so.1
	libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6
$ ldd stat
	not a dynamic executable

$ readelf -d dyn | grep NEEDED
 0x0000000000000001 (NEEDED)  Shared library: [libc.so.6]
$ readelf -d stat | grep NEEDED
(пусто)
```

Разница в размере почти в 50 раз. Дизассемблируем `main` в обоих:

```
$ objdump -d -M intel dyn | grep -A6 '<main>:'
0000000000001149 <main>:
    1149: push   rbp
    ...
    1163: call   1030 <puts@plt>       # через PLT

$ objdump -d -M intel stat | grep -A6 '<main>:'
0000000000401c8d <main>:
    401c8d: push   rbp
    ...
    401ca6: call   40dcc0 <_IO_puts>   # прямой вызов внутри .text
```

В динамическом варианте — `puts@plt` (трамплин). В статическом — прямой вызов `_IO_puts`, причём
символ сохранён, потому что не было `strip`. Если добавить `-s`, имена исчезнут, и придётся
полагаться на сигнатуры.

## Как определить модель у незнакомого бинарника

Быстрая последовательность проверок:

1. `file ./bin` — ищите `dynamically linked` vs `statically linked`.
2. `ldd ./bin` — список зависимостей или `not a dynamic executable`.
3. `readelf -l ./bin | grep INTERP` — есть ли `PT_INTERP`.
4. `readelf -d ./bin | grep NEEDED` — есть ли зависимости.
5. `readelf -S ./bin | grep -E "\.plt|\.got"` — есть ли PLT/GOT.

Если `PT_INTERP` есть, а `NEEDED` пуст — странный случай (возможна ручная загрузка через `dlopen`).

## Символьная интерпозиция и версии

Помимо `LD_PRELOAD`, существует более тонкий механизм — **symbol interposition**. Если библиотека
экспортирует символ, который уже определён в другой библиотеке, порядок загрузки определяет, какая
реализация победит. В ELF разрешение символов идёт по глобальному пространству имён в порядке
загрузки; отсюда правило «первый победил». Именно на этом основан перехват, но он же порождает
классические баги: две библиотеки определяют `malloc` или `operator new`, и поведение становится
непредсказуемым.

Версионирование символов усложняет картину. Одна библиотека может предоставлять `memcpy@GLIBC_2.2.5`
и `memcpy@GLIBC_2.14` — разные реализации. Компоновщик фиксирует требуемую версию в `.gnu.version`,
и загрузчик обязан найти именно её. При подмене библиотеки на другую версию несовпадение версий
приводит к ошибке `version 'GLIBC_2.34' not found`. Для аналитика это означает: список
`readelf --version-info` и строки версий в `strings` помогают точно определить дистрибутив и
версию glibc, что критично при подборе гаджетов и offset'ов в pwn-задачах.

## Статическая линковка в embedded и busybox

В embedded-мире статическая линковка — норма: прошивки роутеров, IoT-устройства и контейнеры часто
содержат статически слинкованные бинарники на базе **musl** или **uClibc** вместо glibc. `busybox` —
классический пример: один статический бинарник, реализующий десятки утилит (`ls`, `cat`, `wget`,
`sh`) через диспетчеризацию по `argv[0]`. Для реверса это означает, что весь код внутри, а
символов может не быть; зато `busybox` легко опознать по строкам и по таблице апплетов. musl
отличается от glibc структурой `malloc`, меньшим размером и другими строками ошибок — не
применяйте glibc-сигнатуры к musl-бинарнику, они не совпадут.

Практический приём: если `file` говорит `statically linked`, но `strings` содержит `musl`, `uClibc`
или `uclibc-ng`, вы имеете дело не с glibc — учитывайте это при поиске функций и гаджетов.

## Последствия для реверса

На практике выбор модели компоновки влияет и на размер поверхности атаки: динамический бинарник
наследует уязвимости и поведение конкретной версии библиотеки, а статический «замораживает» их
внутри себя. Обновление системной библиотеки лечит динамически слинкованные программы, но не
трогает статические — именно поэтому в embedded годами живут уязвимые статические образцы, и именно
поэтому аналитик должен уметь опознавать версию встроенной libc по строкам и сигнатурам.

Статический бинарник требует иной методики: вместо перехода по PLT вы видите прямой вызов
библиотечной функции, которую надо опознать (по сигнатуре или по строкам). Динамический бинарник
даёт подсказки через импорты (`readelf -r`), но «своя» логика перемешана с трамплинами. Для
малвари статическая сборка означает отсутствие сетевых зависимостей и часто — наличие всего
нужного для работы; это популярно в Linux-боте­тах и прошивках. Для анализа полезно держать под
рукой набор FLIRT-сигнатур популярных libc (glibc, musl, uClibc).

## Инструменты и флаги

| Задача | Команда |
|---|---|
| Модель компоновки | `file`, `ldd`, `readelf -l \| grep INTERP` |
| Зависимости | `readelf -d \| grep NEEDED`, `objdump -p` |
| Перехват | `LD_PRELOAD=./hook.so ./bin` |
| Путь библиотек | `LD_LIBRARY_PATH`, `LD_DEBUG=libs ./bin` |
| Сигнатуры libc | IDA FLIRT, Ghidra FID, `lumina` |
| Статическая сборка | `gcc -static`, `gcc -static-pie` |

## Подводные камни

Первое: `ldd` на недоверенном бинарнике может выполнить код (в старых версиях) — используйте
`readelf -d` вместо него для малвари. Второе: `-static` не означает отсутствие ASLR полностью, если
использован `-static-pie`. Третье: `LD_PRELOAD` не работает для setuid-программ (игнорируется
ради безопасности). Четвёртое: статическая сборка с `strip` лишает имён, и найти `main` сложнее.
Пятое: в embedded часто используется musl или uClibc — сигнатуры glibc не подойдут.

## Что дальше / решение

Практика: соберите «Hello» динамически и статически, сравните размер, секции, дизассемблер. Напишите
перехватчик `puts` через `LD_PRELOAD` и убедитесь, что вывод изменился. Возьмите `busybox` (обычно
статический) и попробуйте найти его команды. Далее — `reversing-relocations-symbols` для
понимания, как именно загрузчик правит адреса.
