Откройте любой динамически слинкованный ELF в дизассемблере — и почти каждый вызов библиотечной
функции пройдёт не напрямую, а через маленький трамплин в секции `.plt`, который в свою очередь
обращается к таблице `.got`. Эта двухступенчатая схема — механизм **ленивого связывания** (lazy
binding): адрес внешней функции не известен до загрузки (а иногда и до первого вызова), поэтому
бинарник резервирует ячейку в GOT и заполняет её позже. Понимание PLT/GOT критично и для реверса, и
для эксплуатации.

## Зачем нужны PLT и GOT

Внешние функции (`printf`, `malloc`, `system`) живут в разделяемых библиотеках, загружаемых по
случайным адресам (ASLR). На этапе компиляции линкер не знает их адресов, поэтому он вставляет не
прямой вызов, а обращение к ячейке, которую загрузчик заполнит в рантайме. Эта ячейка — элемент
GOT (Global Offset Table). А PLT (Procedure Linkage Table) — небольшая секция кода, по одному
трамплину на функцию, чтобы не дублировать логику разрешения адреса в каждой точке вызова.

Схема такая: код вызывает `printf@plt`; PLT-трамплин читает адрес из соответствующей ячейки GOT и
прыгает по нему; если ячейка ещё не заполнена, она указывает обратно на резолвер (часть PLT), тот
находит настоящий адрес и записывает его в GOT. Следующий вызов пойдёт напрямую.

## Ленивое связывание пошагово

Первый вызов `printf` из кода выглядит так:

```
call printf@plt
```

В `.plt`:

```
printf@plt:
  jmp    QWORD PTR [rip+0x2f12]   # прыжок по адресу из GOT
  push   0x1                       # индекс релокации (для printf)
  jmp    0x1030                    # в PLT0 (резолвер)
```

При первом вызове ячейка GOT ещё содержит адрес инструкции `push 0x1` (то есть возврат на вторую
строку трамплина). Поэтому выполняется: `push <index>` (индекс символа в `.rela.plt`), затем
`jmp PLT0`. PLT0 — общий стаб, который:

```
PLT0:
  push   QWORD PTR [rip+0x2f1a]   # push link_map / GOT[1]
  jmp    QWORD PTR [rip+0x2f1c]   # jmp *GOT[2] — резолвер dl_runtime_resolve
```

Резолвер (`_dl_runtime_resolve`) по индексу находит запись в `.rela.plt`, определяет символ,
вычисляет его реальный адрес, **записывает его в ячейку GOT** и передаёт управление функции. Со
второго вызова `jmp QWORD PTR [rip+...]` уже прыгает прямо в `printf`, минуя резолвер.

## Структура GOT и .got.plt

GOT делится на две части. `.got` содержит адреса, заполняемые на этапе загрузки (например,
указатели на данные, `__libc_start_main` при `-z now`). `.got.plt` — таблица для ленивого
связывания. Первые три записи `.got.plt` служат служебным целям: `GOT[0]` — адрес `.dynamic`,
`GOT[1]` — `link_map`, `GOT[2]` — адрес `_dl_runtime_resolve`. Реальные функции начинаются с
`GOT[3]`.

Именно `GOT[2]` — классическая цель эксплуатации: перезаписав его, можно заставить следующий
«неразрешённый» вызов перейти в контролируемое место. Но на практике чаще перезаписывают ячейку
конкретной функции (например, `printf` → `system`), чтобы получить выполнение команды.

## Первый вызов vs последующие

Ключевое различие, которое нужно видеть в отладчике:

- **До первого вызова** ячейка GOT функции указывает на `push <index>` внутри её PLT-трамплина.
- **После первого вызова** ячейка содержит реальный адрес функции в библиотеке.

Практический приём: запустите бинарник под gdb, поставьте breakpoint на `printf@plt`, посмотрите
`x/gx &GOT_entry` до и после шага через резолвер. Вы увидите, как значение меняется с адреса внутри
`.plt` на адрес в `libc.so.6`. Это прямое доказательство ленивого связывания.

## Практический разбор: дизассемблируем вызов printf

Возьмём простую программу и посмотрим секции:

```
$ readelf -r ./demo | grep -A2 printf
0000000000003fc8  000200000007 R_X86_64_JUMP_SLOT  0000000000000000 printf@GLIBC_2.2.5 + 0

$ objdump -d -j .plt -M intel ./demo
0000000000001020 <.plt>:
    1020: push   QWORD PTR [rip+0x2fe2]   # GOT[1]
    1026: jmp    QWORD PTR [rip+0x2fe4]   # GOT[2]  -> _dl_runtime_resolve
    102c: nop    DWORD PTR [rax+rax*1+0x0]

0000000000001030 <printf@plt>:
    1030: jmp    QWORD PTR [rip+0x2f92]   # 3fc8 <printf@got.plt>
    1036: push   0x0
    103b: jmp    1020 <.plt>
```

Релокация `R_X86_64_JUMP_SLOT` с адресом `0x3fc8` — это и есть ячейка GOT для `printf`. В `.plt`
трамплин `printf@plt` прыгает по ней. До резолва `0x3fc8` содержит `0x1036` (адрес `push 0x0`).

Проверим в gdb:

```
(gdb) break *main
(gdb) run
(gdb) x/gx &printf@got.plt
0x555555558fc8 <printf@got.plt>: 0x0000555555555036   # внутри .plt
(gdb) break printf
(gdb) continue
(gdb) x/gx &printf@got.plt
0x555555558fc8 <printf@got.plt>: 0x00007ffff7e3d4d0   # в libc
```

До первого вызова — адрес внутри `.plt`, после — адрес в libc. Связывание произошло.

## GOT-перезапись: механика эксплуатации

Если у вас есть примитив записи по произвольному адресу (например, format string или переполнение),
вы можете перезаписать ячейку GOT функции на адрес `system` (или на гаджет). Тогда следующий вызов
этой функции (скажем, `printf`) приведёт к `system(аргумент)`. Если аргумент — строка `/bin/sh`,
получите шелл.

Условия успеха: GOT должен быть writable (partial RELRO или его отсутствие) и вы должны знать адрес
`system` (нужна утечка из libc, если ASLR включён). При полном RELRO GOT становится read-only
после старта, и эта техника не работает — тогда переходят к другим (ret2libc через стек, one_gadget
и т.п.).

## ret2plt и утечки

`ret2plt` — приём, при котором ROP-цепочка вызывает функцию через её PLT-трамплин (например,
`call puts@plt`), чтобы вывести адрес из GOT и получить утечку libc. Например, цепочка:
`pop rdi; ret` → адрес `puts@got` → `puts@plt` — напечатает адрес `puts` в libc, вычислив её базу.
Затем второй этап использует известную базу для вызова `system`. Это фундаментальный приём в
pwn-задачах с ASLR.

## Partial vs Full RELRO

Partial RELRO (по умолчанию в большинстве сборок) делает read-only только `.got` (не `.got.plt`),
поэтому ленивое связывание сохраняется и `.got.plt` остаётся writable — GOT-перезапись возможна.
Full RELRO (`-z now`) разрешает все символы на старте и помечает `.got.plt` read-only — GOT-
перезапись невозможна. Проверить: `checksec --file=./bin` покажет `Partial RELRO` или `Full RELRO`.

| Задача | Команда |

| Динамика | `readelf -d | grep BIND_NOW` |
| Отладка | `gdb` + `x/gx &sym@got.plt` |

## Как загрузчик находит функцию

Когда резолвер получает индекс символа, ему нужно превратить имя `printf` в адрес. Процесс таков:
по индексу из `.rela.plt` берётся смещение в `.dynsym`; в записи символа есть имя (индекс в
`.dynstr`) и версия (`GLIBC_2.2.5`); загрузчик обходит список уже загруженных библиотек
(`link_map`), ищет в каждой таблицу динамических символов (`.dynsym` и GNU-хеш-таблицу), находит
подходящую версию и берёт её адрес. Поиск ускоряется хеш-таблицей GNU Hash или, в новых системах,
GNU Hash Bloom Filter (`.gnu.hash`). Именно поэтому в релокации видна версия символа: одна и та же
функция может иметь несколько версий, и компоновщик фиксирует нужную.

Если символ не найден, программа падает с `symbol lookup error`. Если найден, адрес записывается в
GOT и вызывается. Понимание этого пути объясняет, почему `LD_PRELOAD` работает: подменённая
библиотека загружается раньше и «перехватывает» имя символа — резолвер находит его в ней.

## Аналог в PE: IAT

В Windows тот же принцип реализован через IAT (Import Address Table). Загрузчик (`ntdll` + loader)
обходит таблицу импорта, для каждой DLL находит функцию по имени или ordinal и записывает её адрес
в массив `FirstThunk`. Код вызывает функцию косвенно через IAT. Различие в том, что в PE обычно
**нет** ленивого связывания по умолчанию: адреса заполняются на этапе загрузки (хотя есть механизм
delay-load). Поэтому «первого вызова с резолвом» в PE, как правило, не наблюдается, а IAT
заполняется целиком при старте. Перезапись IAT в Windows — аналог GOT-перезаписи и частый приём
малвари для перехвата API.

| Свойство | ELF | PE |
|---|---|---|
| Таблица | GOT / .got.plt | IAT |
| Трамплин | PLT | нет (косвенный call) |
| Резолв | ленивый (по умолчанию) | на загрузке |
| Релокация | R_X86_64_JUMP_SLOT | Import Directory |

## Подводные камни

Первое: адрес `printf@got.plt` в gdb записывается как `&printf@got.plt`, но для функций может
требоваться `p &printf` и ручной поиск ячейки. Второе: при `-z now` (full RELRO) ячейка уже
заполнена к моменту `main` — не удивляйтесь. Третье: с `-fno-plt` компилятор вызывает через GOT
напрямую, без PLT, что меняет картину. Четвёртое: в PIE-бинарниках адреса PLT/GOT относительны базы.
Пятое: `.plt.sec` (CET/IBT) добавляет лишний слой трамплинов — не путайте его с обычным `.plt`.

## Что дальше / решение

Практика: соберите программу с вызовом `printf`, запустите под gdb, убедитесь в смене значения
GOT. Соберите второй вариант с `-z now -z relro` и проверьте, что `.got.plt` read-only (запись
падает). Разберите `.rela.plt` через `readelf -r`. Далее — `reversing-relocations-symbols` для
глубокого понимания релокаций и `reversing-linking-models` для статической сборки.
