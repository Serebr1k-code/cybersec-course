## Вопрос, с которого всё начинается

Приложение шифрует трафик и проверяет целостность в runtime. Статический патч smali ломает подпись. Нужен способ менять поведение приложения **на лету**, не трогая файл. Как это делается на Android?

## Наш пример

Возьмём `hook.js` — Frida-скрипт, который перехватывает функцию шифрования. Посмотрим на его структуру:

```javascript
Java.perform(function () {
  var Cipher = Java.use('com.example.app.Crypto');
  Cipher.encrypt.implementation = function (data) {
    console.log('encrypt called with:', data);
    return this.encrypt(data);   // пропускаем дальше
  };
});
```

Всего несколько строк — но это уже полноценный хук. Разберём, как он работает и какие есть альтернативы.

## Шаг 1: три инструмента и три уровня

Инструментация Android бывает на трёх уровнях. **Frida** — динамическая, работает через инъекцию агента в процесс; скрипты на JavaScript, можно перехватывать и Java-методы (`Java.use`), и нативные функции (`Interceptor.attach`). **Xposed** — фреймворк, который модифицирует систему на этапе загрузки и позволяет Java-хуки «навсегда», без повторного подключения. **Zygisk** — часть Magisk, даёт нативные хуки и инъекцию на раннем этапе запуска процесса.

Выбор зависит от задачи: для быстрого исследования — Frida; для постоянной модификации — Xposed; для обхода ранних нативных проверок — Zygisk.

## Шаг 2: Frida — как подключиться и что перехватить

Frida состоит из сервера (запущенного на устройстве) и клиента (на компьютере). Подключение:

```
$ frida-ps -U                 # список процессов
$ frida -U -f com.example.app -l hook.js   # запустить и внедрить скрипт
```

Скрипт `hook.js` перехватывает метод `encrypt` класса `Crypto`. Ключевые конструкции: `Java.perform` (выполнить в контексте Java-машины), `Java.use` (получить класс), `.implementation =` (подменить тело). Внутри можно логировать аргументы, менять возвращаемое значение, вызывать оригинал.

## Шаг 3: перехват нативного слоя

Если логика в `.so`, используют `Interceptor`:

```javascript
Interceptor.attach(Module.getExportByName('libcrypto.so', 'AES_encrypt'), {
  onEnter(args) { console.log('in:', args[1].readByteArray(16)) },
  onLeave(retval) { console.log('out:', retval) }
})
```

`onEnter` срабатывает до вызова, `onLeave` — после. Это позволяет видеть ключи, plaintext и ciphertext в момент работы. Для проверок подписи перехватывают `open`/`access`/`strcmp`, а для сетевых — `SSL_write`/`SSL_read`.

## Шаг 4: Xposed и Zygisk — когда Frida не подходит

Frida оставляет следы (порт 27042, библиотека `frida-agent` в `/proc/self/maps`), и приложения, знающие об этом, её детектируют. Тогда используют Xposed: модуль регистрируется системой, и Java-хуки применяются без внешнего агента. Пример Xposed-хука:

```java
XposedHelpers.findAndHookMethod("com.example.app.Crypto", lpparam.classLoader,
    "encrypt", String.class, new XC_MethodHook() {
      protected void beforeHookedMethod(MethodHookParam p) { ... }
    });
```

Zygisk идёт ещё ниже: нативные хуки применяются к процессу zygote при его запуске, поэтому проверки, которые выполняются очень рано (до загрузки Java), уже можно обойти.

## Шаг 5: борьба с детектом инструментации

Приложение может проверять: список библиотек в `/proc/self/maps`, открытые порты, наличие `frida-server`, `ptrace`-статус. Обходы:

- **Скрыть Frida**: использовать `frida-gadget` вместо сервера, переименовать библиотеку, использовать Magisk DenyList.
- **Перехватить сам детект**: хукнуть функцию, которая ищет `frida` в maps, и вернуть «чисто».
- **Отложенный детект**: если приложение проверяет через время, хук должен стоять постоянно.

Общий принцип тот же, что и в детекте root: найди индикаторы, найди код, подмени результат.

## Шаг 6: находим артефакт практики

В `hook.js` есть пример вывода — в нём и лежит артефакт. Прочитаем:

```
$ strings -n 5 hook.js | grep nto
nto{fr1d4_h00k_j4v4_n4t1v3}
```

## Инструмент: objdump — дизассемблер

`objdump` показывает машинный код бинарника в виде ассемблера. Именно по нему считают смещения буферов, находят вызовы и адреса — основа статического разбора.

Ключи, которые пригодятся:
* `objdump -d <файл>` — дизассемблировать секцию `.text` (машинный код функций);
* `objdump -d <файл> | less` — листать вывод, искать нужную функцию по имени;
* `objdump -M intel -d <файл>` — синтаксис Intel (привычнее, чем AT&T);
* в выводе важны пролог функции (`push rbp; mov rbp,rsp`) и `sub rsp,N` — по нему видно размер кадра.

### Рабочий пример (как в лаборатории)

```
$ objdump -d hook.js
objdump: hook.js: file format not recognized
```

Подсказка из лаборатории: `objdump [-d] <файл> — не применимо`.

## Что мы теперь знаем

- Инструментация бывает на трёх уровнях: Frida (динамика), Xposed (Java-хуки), Zygisk (нативный слой).
- Frida: `Java.perform` + `Java.use` для Java, `Interceptor.attach` для нативных функций.
- `onEnter`/`onLeave` дают аргументы и возврат; можно видеть ключи и plaintext.
- Frida детектируется по порту/библиотеке; Xposed и Zygisk обходят ранние проверки.
- Обход детекта — та же схема: найти индикатор, найти код, подменить результат.

## Практический сценарий: обход SSL pinning

Один из самых частых кейсов инструментации — обход SSL pinning, чтобы видеть трафик. Приложения
проверяют сертификат сервера в нескольких местах: `X509TrustManager`, `HostnameVerifier`,
нативный `SSL_CTX_set_verify`. Frida-скрипт перехватывает все три точки и заставляет проверку
всегда проходить. После этого трафик идёт через ваш прокси и виден в Burp/mitmproxy.

Ключевая идея: не бороться с приложением, а **подменить результат проверки** в момент её
выполнения. Это работает и для лицензии, и для детекта, и для шифрования.

## Как не сломать приложение хуком

Хук меняет поведение, и неаккуратный перехват приводит к падению. Правила: сохраняй вызов
оригинала (`this.method.call(this, ...)`), не подменяй типы аргументов, лови исключения внутри
хука. Для нативных функций используй `onEnter`/`onLeave` и не блокируй поток надолго — Frida
работает в том же процессе.

## Частые ошибки

- Забыть вызвать оригинальный метод — приложение ломается.
- Хукать `encrypt`, но не `decrypt`, и видеть только половину обмена.
- Не учесть, что метод перегружен (`overload`), и хукнуть не ту версию.
- Использовать `frida-server` там, где детект по порту 27042 уже срабатывает.
- Хукать слишком поздно — проверка уже прошла до загрузки скрипта.

## Чек-лист

1. Определи уровень: Java (Frida/Xposed) или native (Interceptor/Zygisk).
2. Найди цель: `javap`/jadx или `strings` по `.so`.
3. Напиши минимальный хук и логируй.
4. Обходи детект инструментации, если приложение его имеет.
5. Переводи исследование в постоянную форму (Xposed/Zygisk), если нужно.

## Разбор реального примера: обход SSL pinning

Разберём задачу целиком. Приложение пинует сертификат, и ты хочешь видеть трафик. Сначала
находим точку проверки: строки в DEX показывают класс `CertificatePinner` или кастомный
`TrustManager`. Декомпилируем jadx и видим метод `checkServerTrusted`.

Пишем Frida-скрипт:

```javascript
Java.perform(function () {
  var X509TrustManager = Java.use('javax.net.ssl.X509TrustManager');
  var SSLContext = Java.use('javax.net.ssl.SSLContext');
  var TrustManager = Java.registerClass({
    name: 'com.custom.TrustAll',
    implements: [X509TrustManager],
    methods: {
      checkClientTrusted: function (chain, authType) {},
      checkServerTrusted: function (chain, authType) {},
      getAcceptedIssuers: function () { return [] }
    }
  });
  var TrustManagers = [TrustManager.$new()];
  var SSLContextInit = SSLContext.init.overload(
    '[Ljavax.net.ssl.KeyManager;', '[Ljavax.net.ssl.TrustManager;', 'java.security.SecureRandom');
  SSLContextInit.implementation = function (km, tm, sr) {
    SSLContextInit.call(this, km, TrustManagers, sr);
  };
});
```

Этот скрипт подменяет trust manager так, что любой сертификат считается доверенным. После этого
трафик идёт через прокси. Если пиннинг реализован нативно, добавляем перехват
`SSL_CTX_set_custom_verify` и `SSL_get_verify_result` через `Interceptor`.

## Как найти цель для хука

Прежде чем писать хук, нужно знать, что хукнуть. Три источника: `strings`/jadx (имена классов и
методов), `frida-trace` (динамическая трассировка вызовов), и `Interceptor` с логированием
нативных функций. Для сетевых задач полезно сразу хукнуть `SSL_write`/`SSL_read` — увидишь
открытый текст до шифрования. Для крипто — `AES_encrypt`/`EVP_EncryptUpdate`. Для проверок —
`open`/`access`/`strcmp`.

## Практический сценарий

Ты исследуешь приложение с детектом. Порядок: запустить под Frida с хуком на libc, записать все
проверки; найти, какие индикаторы они используют; обойти каждую; затем исследовать основную
логику. Если Frida детектируется — перейти на `frida-gadget` (встраиваемый агент) или Xposed.

## Xposed-хук на практике

Xposed-модуль — это отдельный APK, который регистрирует хуки для других приложений. Пример:

```java
public class Hook implements IXposedHookLoadPackage {
  public void handleLoadPackage(LoadPackageParam lpparam) {
    if (!lpparam.packageName.equals("com.example.app")) return;
    XposedHelpers.findAndHookMethod("com.example.app.License", lpparam.classLoader,
        "isLicensed", new XC_MethodReplacement() {
          protected Object replaceHookedMethod(MethodHookParam p) { return true; }
        });
  }
}
```

Преимущество перед Frida — хук применяется на этапе загрузки, без внешнего агента, и не виден
по порту. Недостаток — требует установки фреймворка (что само по себе детектируется) и
перезагрузки устройства.

## Zygisk и ранний перехват

Zygisk-модуль работает в процессе `zygote` до форка приложения. Это позволяет перехватывать
проверки, которые выполняются в первые миллисекунды запуска, — там, где Frida опаздывает. На
Zygisk строят и модули обхода детекта (Shamiko), и модули инструментации. Для реверса это
крайний случай, когда другие уровни не справляются.

## Выбор инструмента

Простое правило: начни с Frida (быстро, гибко), если детектируется — перейди на Xposed или
Zygisk. Если проверка в нативном коде и выполняется рано — Zygisk. Если нужна постоянная
модификация без внешнего процесса — Xposed. Правильный выбор экономит часы борьбы с детектом.

## Как писать надёжные хуки

Хук должен быть устойчивым: не падать при неожиданных типах, не блокировать поток, корректно
вызывать оригинал. Используй `try/catch` внутри реализации, проверяй аргументы на null, а для
перегруженных методов указывай `overload`. Если хук нужен только для наблюдения, не меняй
возврат — логируй и вызывай оригинал. Если меняешь — убедись, что подменённый тип совпадает с
ожидаемым, иначе приложение упадёт с `ClassCastException`. Эти мелочи отличают рабочий
инструмент от одноразового скрипта.

## Итог

Инструментация в runtime — самый гибкий способ менять поведение приложения. Frida даёт быстрый
старт и хуки на Java и native, Xposed — постоянную модификацию без внешнего процесса, Zygisk —
ранний нативный перехват. Выбор уровня зависит от того, где спрятана логика и насколько рано
она исполняется. Всегда помни про детект инструментации и обходи его тем же приёмом: найди
индикатор, найди проверку, подмени результат. Тогда защита перестанет мешать анализу.
