## Вопрос, с которого всё начинается

AFL++ запускает цель отдельным процессом на каждый вход — это дорого. Есть ли способ фаззить **внутри** процесса, чтобы было быстрее и точнее?

## Наш пример

Мы собрали цель с **libFuzzer** и нашли падение. Фаззер сохранил вход в файл `crash-xxxx`. Разберём этот вход и поймём, что именно ломает программу.

## Шаг 1: in-process фаззинг

**In-process фаззер** работает внутри самого процесса-цели: не перезапускает программу, а вызывает функцию-цель в цикле. Это убирает стоимость `fork`/`exec` и даёт огромную скорость.

Цена — изоляция: падение роняет весь фаззер, поэтому после краша нужен перезапуск. Но современные фаззеры это умеют.

## Шаг 2: libFuzzer

**libFuzzer** встроен в компилятор (Clang). Ты пишешь функцию `LLVMFuzzerTestOneInput(data, size)`, компилируешь с `-fsanitize=fuzzer`, и получаешь готовый фаззер:

```c
extern "C" int LLVMFuzzerTestOneInput(const uint8_t* data, size_t size) {
    parse(data, size);      // цель
    return 0;
}
```

```bash
$ clang -g -O1 -fsanitize=fuzzer,address -o fuzz target.c
$ ./fuzz corpus/
INFO: Running with entropic power schedule
INFO: Seed: 12345
#1248391  NEW    cov: 512 ft: 1024 corp: 42/2048b
==12345==ERROR: AddressSanitizer: heap-buffer-overflow
```

libFuzzer сам мутирует вход, следит за покрытием (компилятор вставляет счётчики) и при падении печатает **артефакт** — вход, который воспроизводит баг.

## Шаг 3: Honggfuzz

**Honggfuzz** — альтернатива, которая умеет и in-process, и внешний режим, и поддержку разных ОС (включая Windows/macOS). Она умеет:

- собирать **hardware-покрытие** (Intel PT/BTS) без инструментации;
- запускать несколько потоков;
- использовать **словари** и структуру входа.

Синтаксис близок к AFL++:

```bash
$ honggfuzz -i corpus -o out -- ./target ___FILE___
```

## Шаг 4: санитайзеры — усилитель

Ключевое отличие in-process фаззеров — тесная интеграция с **санитайзерами**:

- **AddressSanitizer (ASan)** — переполнения буфера (стек/куча), use-after-free, double-free.
- **UndefinedBehaviorSanitizer (UBSan)** — переполнение целых, сдвиги, деление на ноль.
- **MemorySanitizer (MSan)** — работа с неинициализированной памятью.

Без санитайзера многие баги не падают: переполнение на пару байт может не дать segfault. С ASan тот же баг становится явным крахом. Это главный рычаг качества фаззинга.

## Шаг 5: разбор артефакта

```bash
$ python3 read_artifact.py crash-xxxx
artifact: crash-xxxx (size 42)
reason: AddressSanitizer: heap-buffer-overflow READ of size 8
input hex: 4d41474943 00000000 6e746f7b 6c696266 ...
decoded: MAGIC\x00\x00\x00\x00nto{l1bfuzz3r_4s4n_4rt1f4ct}
```

Артефакт — это и есть вход, который надо подать программе, чтобы повторить падение. Его минимизируют (`-minimize_crash=1`) и прикладывают к отчёту.

## Шаг 6: сравнение фаззеров

| | AFL++ | libFuzzer | Honggfuzz |
|---|---|---|---|
| Режим | процесс/персистентный | in-process | оба |
| Покрытие | инструментация/QEMU | инструментация | HW (PT/BTS) |
| Санитайзеры | да | тесно встроены | да |
| Платформы | Linux/macOS/Win | Clang-платформы | много |
| Ниша | универсальность | быстрый in-process | железное покрытие |

Выбор зависит от задачи: для библиотеки на Clang — libFuzzer; для чёрного ящика с железным покрытием — Honggfuzz; для универсальности — AFL++.

## Что мы теперь знаем

- In-process фаззеры работают внутри процесса цели — быстрее AFL++.
- libFuzzer встроен в Clang и даёт артефакт при падении.
- Honggfuzz умеет hardware-покрытие и много платформ.
- Санитайзеры превращают «тихие» баги в краши.
- Артефакт — воспроизводимый вход для отчёта.

## Шаг 7: как libFuzzer мутирует вход

libFuzzer использует набор мутаций: изменение байта, вставку/удаление, перестановку, копирование блока, работу со словарём. Плюс — **entropic schedule**, который даёт больше внимания входам с новым покрытием. Всё это без перезапуска процесса.

```bash
$ ./fuzz corpus/ -max_len=4096 -dict=tokens.dict
```

Словарь (`-dict`) подсказывает токены формата (`PNG`, `IHDR`), что резко ускоряет проход проверок структуры.

## Шаг 8: как читать вывод libFuzzer

Панель показывает:

- `cov` — покрытых блоков;
- `ft` — фич (рёбер) покрытия;
- `corp` — размер корпуса;
- `exec/s` — скорость.

Рост `cov`/`ft` означает, что фаззер находит новые пути. Если он «встал», помогут: словарь, более разнообразный корпус, CmpLog-эквивалент (`-use_value_profile=1`).

## Шаг 9: ASan-отчёт

При падении libFuzzer печатает отчёт ASan:

```text
==12345==ERROR: AddressSanitizer: heap-buffer-overflow on address 0x...
READ of size 8 at 0x... thread T0
    #0 0x4a1b2c in parse /src/target.c:42
    #1 0x4a1f10 in LLVMFuzzerTestOneInput /src/target.c:60
SUMMARY: AddressSanitizer: heap-buffer-overflow /src/target.c:42
```

Стек прямо указывает строку и функцию. Тип ошибки (`heap-buffer-overflow`, `use-after-free`, `stack-overflow`) говорит о классе бага.

## Шаг 10: минимизация артефакта

Артефакт может быть большим. libFuzzer умеет минимизировать:

```bash
$ ./fuzz -minimize_crash=1 crash-xxxx
```

Минимальный вход легче анализировать и прикладывать к отчёту. Аналогично `-minimize_crash` для отдельного файла.

## Шаг 11: Honggfuzz на практике

```bash
$ honggfuzz -i corpus -o out -- ./target ___FILE___
```

Honggfuzz умеет **hardware-based feedback** через Intel PT/BTS — покрытие без инструментации. Это полезно, когда исходников нет, а QEMU-режим слишком медленный. Плюс — многопоточность «из коробки».

## Шаг 12: таблица санитайзеров

| Санитайзер | Что ловит | Флаг |
|---|---|---|
| ASan | OOB, UAF, double-free | `-fsanitize=address` |
| UBSan | переполнение, сдвиги | `-fsanitize=undefined` |
| MSan | неинициализированная память | `-fsanitize=memory` |
| TSan | гонки данных | `-fsanitize=thread` |
| LSan | утечки | часть ASan |

## Шаг 13: от краша к уязвимости

Краш — не всегда уязвимость. Разбери его в отладчике: если управление `RIP` контролируется входом — это потенциальный RCE. Если просто `null`-deref или ассерт — ценность ниже. Классификация крашей — обязательный шаг триажа: уникальные краши группируют по стеку и оставляют самые серьёзные.

## Шаг 14: сравнение с AFL++ на практике

AFL++ запускает цель отдельно (или в persistent-режиме), libFuzzer — внутри процесса. Для библиотек с чёткой точкой входа libFuzzer удобнее и быстрее. Для программ, требующих реального `fork`/`exec` и файлов на входе, AFL++ проще. Часто используют оба: AFL++ для чёрного ящика, libFuzzer для библиотек.

## Шаг 15: итоговый алгоритм

Собери цель с `-fsanitize=fuzzer,address`. Подготовь корпус из валидных примеров. Добавь словарь токенов. Запусти, следи за `cov`/`ft`. При падении — минимизируй артефакт, разбери в отладчике, классифицируй. Для чёрного ящика — Honggfuzz с PT. Главное: **in-process + санитайзеры = максимальная плотность находок**.

## Шаг 16: почему in-process даёт такую скорость

Разница между «запустить процесс на каждый вход» и «вызвать функцию в цикле» колоссальна. Запуск процесса включает `fork`, `exec`, загрузку библиотек, инициализацию рантайма — это миллисекунды. Вызов функции — наносекунды. Отсюда разница в скорости на порядки: AFL++ в обычном режиме даёт тысячи исполнений в секунду, libFuzzer в процессе — сотни тысяч. За час разница превращается в сотни миллионов дополнительных входов, а значит — в больше найденных путей и багов. Именно поэтому in-process фаззинг стал стандартом для библиотек: чем больше исполнений, тем выше шанс найти редкий баг. Цена — изоляция: падение роняет весь фаззер, но современные инструменты быстро перезапускаются и продолжают.

## Шаг 17: покрытие: инструментация против железа

Покрытие можно получать двумя способами. Первый — **инструментация**: компилятор вставляет счётчики в код (`-fsanitize=fuzzer` или `afl-cc`). Это точно и дёшево, но требует пересборки. Второй — **аппаратный**: процессор сам сообщает о выполненных ветках (Intel PT/BTS). Это работает без исходников и без пересборки, но сложнее в настройке. Honggfuzz умеет оба; libFuzzer — только инструментацию (он и есть часть компилятора). Выбор зависит от того, есть ли у тебя исходники: если да — инструментация проще; если нет — аппаратное покрытие.

## Шаг 18: как выбирать санитайзер

ASan — универсальный выбор для памяти: он ловит переполнения и use-after-free. UBSan — для арифметики и неопределённого поведения; часто включают вместе с ASan. MSan — когда подозреваешь работу с неинициализированной памятью (частый источник утечек данных). TSan — для многопоточного кода и гонок. Включать всё сразу нельзя: они конфликтуют. Поэтому выбирают по характеру цели: парсер — ASan; крипто-код — MSan; многопоточный сервер — TSan. Правильный санитайзер удваивает-утраивает число находок, неправильный — мешает.

## Шаг 19: вывод

In-process фаззеры (libFuzzer, Honggfuzz) вместе с санитайзерами — самый эффективный способ найти баги в библиотеках и парсерах. Они быстрее AFL++ за счёт отсутствия перезапуска, тесно интегрированы с компилятором и превращают «тихие» баги в явные краши. Артефакт падения — готовый вход для воспроизведения и отчёта. Освоив libFuzzer, ты получаешь конвейер: собрал цель с санитайзером, дал корпус, запустил, собрал краши, разобрал. Это базовый навык современного исследователя, и он окупается в первой же серьёзной задаче.

## Шаг 20: что запомнить про in-process фаззинг

In-process фаззинг — это про максимальную плотность исполнений. Чем больше входов в секунду, тем выше шанс добраться до редкого бага. libFuzzer встроен в компилятор и даёт эту скорость почти бесплатно: написал точку входа, собрал с санитайзером, запустил. Honggfuzz добавляет аппаратное покрытие и мультиплатформенность. Вместе они покрывают большинство задач поиска багов в библиотеках. Артефакт падения — не конец, а начало: минимизируй, разбери в отладчике, классифицируй. И помни: санитайзер — половина успеха, без него многие баги останутся невидимыми.
