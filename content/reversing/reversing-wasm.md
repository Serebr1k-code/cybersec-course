## Вопрос, с которого всё начинается

На CTF по Web всё чаще дают не JavaScript, а файл `app.wasm` — и логика проверки флага спрятана внутри. `file` показывает «WebAssembly», `objdump` его не понимает, а браузерный код просто вызывает функции из модуля. Что это за формат и как добраться до проверки?

## Наш пример

Скомпилируем функцию на C в настоящий WebAssembly-модуль `arch.wasm`:

```c
int check(int x) { if (x == 0x1337) return 1; return 0; }
```

```bash
$ file arch.wasm
arch.wasm: WebAssembly (wasm) binary version 0x1 (MVP module)
```

Смотрим первые байты:

```bash
$ xxd arch.wasm | head -1
00000000: 0061 736d 0100 0000 018c 8080 8000 0260  .asm...........`
```

Первые четыре байта — `00 61 73 6d`, то есть `\0asm`. Это **магия** WASM (как `7f ELF` у ELF). Следующие `01 00 00 00` — версия формата. Дальше начинается структура.

## Шаг 1: модуль состоит из секций

WASM-файл — это **модуль** из пронумерованных **секций**. Каждая секция начинается с номера типа и размера, поэтому их можно прочитать подряд:

```text
  section id=1 (type) size=12
  section id=2 (import) size=47
  section id=3 (function) size=3
  section id=7 (export) size=... 
  section id=10 (code) size=109
```

Имена по номерам: `1` — типы функций, `2` — импорт, `3` — список функций, `7` — экспорт, `10` — код. То есть логика «заголовок → таблицы → код» та же, что в ELF, только номера секций — это стандарт WASM. Нам важны две: экспорт и код.

## Шаг 2: экспорт — что модуль отдаёт браузеру

JavaScript не может вызвать «любую» функцию внутри модуля — только **экспортированные**. Их список:

```text
exports:
  add    (kind=0, idx=1)
  check  (kind=0, idx=2)
```

`kind=0` — функция. Видим `add` и `check` — те самые функции из нашего C. Экспорт — точка входа: именно `check` вызывает JS-код, и именно её надо разобрать.

## Шаг 3: байткод — стековая машина

Код WASM — это **байткод для стековой машины**: инструкции не работают с регистрами, как x86/ARM, а кладут значения на стек и снимают их. Посмотрим дизассемблер:

```text
  i32.const 0x10
  i32.sub
  set_local 0x2
  get_local 0x2
  get_local 0x0
  i32.store 0x2, 0xc
  get_local 0x1
  i32.store 0x2, 0x8
```

Читаем: `i32.const 0x10` кладёт 16 на стек, `i32.sub` вычитает (получаем адрес фрейма), `set_local 0x2` сохраняет его в локальную переменную. Дальше `get_local 0x0`/`get_local 0x1` достают аргументы и кладут их в память. `local` здесь — аналог регистров, `i32.store` — запись в память модуля. Непривычно, но логика прозрачна: это «стек, локальные переменные и память».

## Шаг 4: как читать это удобнее

Сырой байткод читать тяжело, поэтому его переводят в текст. Инструменты:

- **`wasm2wat`** (пакет wabt) — байткод → текстовый `WAT` с читаемыми инструкциями.
- **`wasm2c`** — превращает модуль в C-код, который потом компилируется и анализируется как обычная программа.
- **`wasm-decompile`** (wabt) — псевдо-C.
- **Ghidra / IDA** — современные версии понимают WASM и строят граф функций.
- **capstone** (Python) — дизассемблирует байткод, как мы сделали выше.

В браузере модуль запускается через `WebAssembly.instantiate`; в Node — `WebAssembly.instantiate(fs.readFileSync('arch.wasm'))`. Для динамики: оберни экспорт и логируй аргументы — получишь поведение без чтения байткода.

## Шаг 5: где живёт проверка флага

Типичная CTF-задача: JS передаёт строку в WASM-функцию, та сравнивает с секретом. Порядок разбора:

1. **Найти экспорт** — что вызывается из JS (часто имя `check`, `verify`, `_validate`).
2. **Посмотреть строки** — `strings arch.wasm`; WASM хранит данные в секции `data` (id 11), часто открытым текстом.
3. **Декомпилировать** — `wasm2c` или Ghidra, найти сравнение.
4. **Проверить динамикой** — вызвать функцию с разными входами и смотреть результат.

Секрет, как правило, лежит либо в секции данных, либо собирается посимвольно в коде — оба варианта видны после декомпиляции.

## Шаг 6: текстовый вид — WAT

Сырой байткод читать неудобно, поэтому его переводят в **WAT** (WebAssembly Text) — текстовый формат того же модуля. Команда `wasm2wat arch.wasm` выдаёт что-то вроде:

```wat
(module
  (func $check (param $x i32) (result i32)
    local.get $x
    i32.const 4919      ;; 0x1337
    i32.eq
  )
  (export "check" (func $check))
)
```

Читается почти как ассемблер: `local.get $x` берёт аргумент, `i32.const 4919` кладёт константу, `i32.eq` сравнивает. В `WAT` видны имена функций (`$check`), если они есть в секции `name` (её оставляют при сборке с отладочной информацией). Если имена есть — реверс превращается в чтение текста; если нет — всё равно видна структура. Это самый быстрый путь для CTF: `wasm2wat` и поиск сравнения.

## Шаг 7: полный прогон от начала до конца

Соберём разбор типичной задачи в одну цепочку:

1. **`file app.wasm`** — убедились, что это WASM.
2. **`xxd | head`** — увидели магию `\0asm`.
3. **Разобрали секции** — нашли `export` и `code`.
4. **`strings app.wasm`** — вытащили читаемые данные (часто флаг лежит тут открытым текстом).
5. **`wasm2wat`** — перевели в текст, нашли функцию проверки.
6. **Прочитали сравнение** — восстановили алгоритм или сам секрет.
7. **Проверили динамикой** — вызвали экспорт с кандидатом в Node и сравнили результат.

Из семи шагов пять не требуют глубоких знаний — это стандартный конвейер, применимый к любой WASM-задаче.

## Шаг 8: память и данные модуля

Отдельно стоит понять **линейную память**. У WASM-модуля есть один большой массив байт — `memory`, в который инструкции `i32.load`/`i32.store` читают и пишут. Строки и константы лежат в секции `data` (id 11) и при инициализации копируются в эту память. Отсюда два практических вывода:

- **Строки в `.wasm` открыты** — секция `data` не шифруется, и `strings`/`wasm2wat` показывают их как есть. Флаг в CTF-задаче очень часто лежит прямо там.
- **Проверки сравнивают байты в памяти** — в байткоде увидишь `i32.load` по адресу, а рядом `i32.eq` с константой. Адрес можно сопоставить с секцией `data` и увидеть, с чем именно сравнивают.

Ещё в памяти живёт **стек** модуля: инструкции `local` хранятся не в «регистрах», а на стеке фрейма, и `__stack_pointer` в списке экспорта — это указатель на него. Понимание «одна линейная память + стек фреймов» снимает большую часть загадок при чтении байткода.

## Что мы теперь знаем

- WASM-модуль начинается с магии `\0asm` и версии; далее — секции с номерами.
- Экспорт (секция 7) перечисляет функции, доступные из JS — это точки входа.
- Код (секция 10) — байткод стековой машины: значения на стеке, `local` вместо регистров.
- `wasm2wat`, `wasm2c`, Ghidra и capstone переводят байткод в читаемый вид.
- Данные и секреты лежат в секции `data`; `strings` часто вскрывает их сразу.

## Где пригодится

- **CTF Reversing / Web:** WASM-задачи решаются через экспорт + декомпиляцию; без этого флаг не достать.
- **Анализ web-клиентов:** лицензии и крипто в браузерных приложениях всё чаще прячут в WASM.
- **DRM/игры:** клиентская логика защиты компилируется в WASM, чтобы не отдавать исходник.
- **Инструменты:** `wasm2c` + компилятор дают полноценный «нативный» анализ WASM-модуля.
