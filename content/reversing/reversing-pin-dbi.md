## Вопрос, с которого всё начинается

Тебе нужно инструментировать программу: логировать каждую исполненную инструкцию, считать покрытие,
следить за потоком данных. Исходников нет. Отладчик не подходит — он **останавливает** программу на
каждом шаге и замедляет её в сотни раз. Как перехватить исполнение, не вставая на паузу?

Ответ — **DBI**, динамическая бинарная инструментация. Разберём её на классике — Intel PIN и
DynamoRIO — и тут же построим работающий аналог, чтобы увидеть модель своими глазами.

## Наш пример

Крэкми с XOR-проверкой:

```c
int check(const char *s){
    if (mylen(s) != 6) return 0;
    for (int i=0;i<6;i++)
        if (((unsigned char)s[i] ^ key[i]) != want[i]) return 0;
    return 1;
}
```

```
$ ./crackme nvumom
```

Задача: получить **трассу каждой исполненной инструкции** вместе со значениями регистров — то, что
даёт инструментированная программа.

## Шаг 1: что такое DBI

**Динамическая бинарная инструментация (DBI)** — техника, при которой код инструментируется «на
лету». Движок (PIN, DynamoRIO) разбирает инструкции, строит их копии в **кодовом кэше** и вставляет
вызовы анализа до/после нужных инструкций. Программа не останавливается, а аналитический код
получает доступ к регистрам, памяти и адресам.

Отличие от отладчика принципиально: отладчик ставит точку останова и **ждёт**; DBI выполняет код
непрерывно, просто рядом с ним работает твой обработчик. Отсюда применения: трассировка API и
сисколлов, покрытие для fuzzing, taint-анализ, детект уязвимостей, деобфускация.

## Шаг 2: модель Intel PIN

В PIN основные понятия — уровни кода: **IMG** (образ, файл), **SEC** (секция), **RTN** (рутина,
функция), **INS** (инструкция). Ты регистрируешь колбэки:

- `INS_AddInstrumentFunction` — на каждую инструкцию;
- `TRACE_AddInstrumentFunction` — на каждый трассировочный блок (выполняемый фрагмент кода);
- `IMG_AddInstrumentFunction` — на загрузку образа;
- `INS_InsertCall` — вставить вызов анализа перед/после инструкции.

Скелет pintool выглядит так:

```cpp
#include "pin.H"
#include <iostream>

VOID BeforeIns(ADDRINT ip) {
    std::cout << "exec " << std::hex << ip << std::endl;
}

VOID Instruction(INS ins, VOID *v) {
    INS_InsertCall(ins, IPOINT_BEFORE, (AFUNPTR)BeforeIns,
                   IARG_INST_PTR, IARG_END);
}

int main(int argc, char *argv[]) {
    PIN_Init(argc, argv);
    INS_AddInstrumentFunction(Instruction, 0);
    PIN_StartProgram();          // никогда не возвращается
    return 0;
}
```

Смысл: `INS_AddInstrumentFunction` вызывает наш `Instruction` для **каждой** инструкции программы, а
`INS_InsertCall` вставляет перед ней вызов `BeforeIns`. Дальше движок исполняет программу, и наш код
«подсматривает» за ней.

## Шаг 3: тот же принцип без PIN

PIN в этой среде не установлен, но модель несложно воспроизвести на **unicorn**: его хук
`UC_HOOK_CODE` вызывается перед каждой инструкцией — ровно как `INS_AddInstrumentFunction`, а наш
колбэк играет роль вставленного вызова анализа. Эмулируем `check`, печатая адрес, инструкцию и
регистры:

```python
def on_insn(mu, addr, size, ud):
    i = next(md.disasm(mu.mem_read(addr, size), addr), None)
    print(f"[INS] {addr:#08x}  {i.mnemonic} {i.op_str}")
```

Первый прогон на верном пароле:

```

  [INS] 0x401072  mov    rbp, rsp                 rax=0x0 rdi=0x500000

  [INS] 0x401079  mov    qword ptr [rbp - 0x18], rdi rax=0x0 rdi=0x500000
```

Это буквально «pintool своими руками»: адрес, дизассемблированная инструкция и снимок регистров
перед ней. Итог — **205** инструкций для верного пароля.

## Шаг 4: что даёт DBI по сравнению с трассировкой

Сравни с аппаратной трассировкой из прошлых уроков. Та давала 250 адресов, но **без данных**. DBI
отдаёт и адрес, и инструкцию, и **значения регистров и памяти** — потому что перехват идёт в
пользовательском пространстве, где всё доступно. Именно поэтому DBI — рабочий инструмент для
taint-анализа и восстановления алгоритмов, а не только для покрытия.

Обратная сторона: DBI медленнее и **заметен**. Программа может обнаружить, что её код изменили
(инструментация — это модификация исполнения), и это важно для анти-отладочных образцов.

## Шаг 5: DynamoRIO

**DynamoRIO** — второй классический фреймворк, открытый (в отличие от PIN). Идея та же, но API
другой: клиент регистрирует обработчики через `dr_client_main` и библиотеку `drmgr`, а события
(инструкции, базовые блоки, обращения к памяти) приходят в колбэки. DynamoRIO особенно силён в
построении собственных инструментов анализа — на нём основаны многие исследовательские и
коммерческие продукты.

## Шаг 6: ограничения DBI

- **Оверхед** — JIT-трансляция и колбэки замедляют в разы (меньше отладчика, но больше PT).
- **Обнаружимость** — изменённое исполнение видно анти-анализу.
- **Self-modifying code** — код, который себя переписывает, ломает кодовый кэш.
- **Платформозависимость** — свой DBI-движок под каждую архитектуру.

## Шаг 7: чего ещё добиваются от DBI

Инструментация — не только печать инструкций. На тех же колбэках строят:

- **Покрытие (coverage):** запоминать уникальные адреса (или рёбра) — сколько кода исполнилось.
  Это топливо для fuzzing: мутатор знает, привёл ли вход к новому пути. Наш трейсер уже собирает
  уникальные адреса — осталось сложить их в множество.
- **Трассировка API/сисколлов:** перехватывать вызовы по имени (`RTN` в PIN) и логировать аргументы
  — так видно, что программа делает с файлами и сетью.
- **Taint-анализ:** на каждом обращении к памяти проверять метки (это уже следующий урок про Triton).
- **Патчинг на лету:** DBI умеет не только наблюдать, но и **подменять** поведение — пропускать
  проверку, менять возвращаемое значение.

Для нашего крэкми достаточно покрытия: на верном входе исполняется 205 инструкций, и по множеству
адресов сразу видно, какие блоки «живые», а какие — нет. Именно так DBI помогает понять, какой код
реально участвует в проверке.

## Что мы теперь знаем

- **DBI** инструментирует код «на лету», не останавливая программу.
- В PIN уровни IMG/SEC/RTN/INS, а `INS_AddInstrumentFunction` даёт колбэк на каждую инструкцию.
- Тот же принцип воспроизводится хуком `UC_HOOK_CODE` в unicorn.
- DBI даёт и адреса, и данные (регистры/память) — в отличие от аппаратной трассировки.
- Цена: оверхед и обнаружимость; DynamoRIO — открытая альтернатива PIN.

## Почему DBI незаменим для трассировки

Отладчик останавливает программу на breakpoint'ах и требует ручного управления: вы ставите точки, смотрите регистры, продолжаете. Для изучения **одного** участка это идеально, но для понимания **всей** динамики программы (какие функции вызываются, какие данные текут, где читается ключ) отладчик слишком медленный и ручной. Здесь на сцену выходит **DBI** — Dynamic Binary Instrumentation.

Идея DBI: инструмент перехватывает поток инструкций и **вставляет свой код** перед/после нужных инструкций, не пересобирая программу. Intel PIN, DynamoRIO, QBDI, Triton работают по этому принципу. Вы пишете «pintool» — плагин, который реагирует на события (выполнение инструкции, вызов функции, доступ к памяти) и логирует/анализирует. Это позволяет автоматически строить трассы вызовов, считать покрытие, искать обращения к конкретному буферу и делать **taint-анализ** (отслеживать, как «заражённые» данные распространяются по программе).

Главное отличие от эмуляции: DBI инструментирует **настоящий** процесс на реальном CPU, со всеми syscall'ами и окружением. Поэтому он устойчивее к анти-эмуляции, но требует установки инструмента (Intel PIN, QBDI, Triton — отдельные пакеты) и часто прав под отладку. Для деобфускации DBI даёт то, чего не даёт статика: реальный поток управления и реальные данные. А для анализа больших бинарников — автоматизацию, недостижимую вручную.

## Частые вопросы

**Чем DBI отличается от эмуляции?** DBI исполняет код на реальном CPU с инструментацией; эмуляция исполняет код в программной песочнице. DBI быстрее и «нативнее», эмуляция изолированнее и управляемее.

**Почему Intel PIN не работает «из коробки»?** Это отдельный SDK, который надо скачать и собрать/настроить; pintool — это .so/.dll, загружаемый в процесс. Без установленного PIN примеры не запустятся.

**Что даёт taint-анализ?** Отслеживание потока данных от «источника» (ввод, ключ) к «стоку» (сравнение, вывод); он показывает, где именно секрет влияет на результат.

**Когда DBI, а когда отладчик?** Отладчик — для точечного разбора одной развилки; DBI — для трассировки всего исполнения и автоматического анализа.

## Сравнение DBI-инструментов: что выбрать

PIN и DynamoRIO — не единственные инструменты динамической инструментации. Их выбирают по задаче, а не «по вкусу»: у каждого своя модель, охват архитектур и цена.

| Инструмент | Модель | Архитектуры | Накладные расходы | Типичная задача |
|------------|--------|-------------|-------------------|-----------------|
| Intel PIN | DBI, JIT-пересборка | x86/x64 | средние | трассировка, pintools, CTF |
| DynamoRIO | DBI, открытый | x86/x64, ARM | средние | drcachesim, кастомные клиенты |
| Valgrind | DBI, IR | x86/x64, ARM | высокие (10–50×) | поиск утечек, memcheck |
| Frida | перехват на уровне функций | почти все (вкл. mobile) | низкие | хук-скрипты на JS |
| QEMU (user) | полная эмуляция | любые | очень высокие | кросс-архитектура |

Ключевое различие — **уровень**: PIN/DynamoRIO работают с инструкциями и могут инструментировать каждый базовый блок, Frida перехватывает вызовы функций, а QEMU эмулирует целиком, поэтому тянет чужой ISA, но проигрывает в скорости. Практическое правило: нужна побитовая видимость на x86 — PIN/DynamoRIO; нужно быстро влезть в чужой процесс или мобильное приложение — Frida; нужно запустить ARM-бинарь на x86 — QEMU.

## Куда дальше

Классический DBI запускает программу под своим движком. Но иногда нужно инструментировать **уже
запущенный процесс** — или работать на ARM/embedded. Для этого есть **QBDI**, встраиваемый в
процесс как библиотека. О нём — следующий урок. А пока главное: DBI даёт полный контроль над
исполнением — адреса, инструкции, регистры, память — ценой скорости и скрытности.

## Где пригодится

- **CTF Reversing:** трассировка и восстановление алгоритма по значениям регистров.
- **Malware analysis:** наблюдение за поведением образца на уровне инструкций.
- **Program analysis:** покрытие для fuzzing, taint-анализ, детект уязвимостей.
- **Tooling:** основа для собственных инструментов на DynamoRIO/PIN.
