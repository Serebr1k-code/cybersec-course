## Вопрос, с которого всё начинается

Ты читаешь про импланты, которые **переживают переустановку ОС**: их находят в прошивке материнской платы. Как вообще анализируют прошивку и как отличить легитимный UEFI-модуль от зловредного?

## Наш пример

`firmware.bin` — дамп прошивки. Это не ELF и не PE в привычном виде, а контейнер, внутри которого лежат модули в формате **PE/TE**. Разберём его и найдём подозрительный DXE-драйвер.

## Шаг 1: что такое UEFI и SMM

**UEFI** — современная замена BIOS: среда, которая инициализирует железо и загружает ОС. Она состоит из модулей-драйверов. Основной этап исполнения — **DXE** (Driver Execution Environment), где работают **DXE-драйверы**.

**SMM** (System Management Mode) — особый режим процессора, который выполняется вне ОС и вне гипервизора. Код SMM (SMI-обработчики) имеет максимальные привилегии: его не видит ни ОС, ни даже hypervisor. Именно поэтому SMM — идеальное место для импланта.

## Шаг 2: как устроен образ прошивки

Прошивка — это **Firmware Volume** (FV): контейнер с файлами. Каждый файл имеет GUID и тип. UEFI-модули хранятся как **PE/TE-образы** (TE = Terse Executable, урезанный PE). Их находят по сигнатуре `VZ` (0x5A56) в начале TE-заголовка или по сигнатуре `MZ` для PE.

Инструмент `UEFITool` показывает структуру: тома, файлы, секции, модули. `uefi-firmware-parser` делает то же из командной строки.

## Шаг 3: находим модули скриптом

Скрипт `scan_uefi.py` ищет TE/PE-образы и печатает их:

```bash
$ python3 scan_uefi.py firmware.bin
Firmware Volume @ 0x000000  size 0x800000
  [0x001200] TE image  module: DxeCore
  [0x04a800] TE image  module: UsbBusDxe
  [0x09c000] TE image  module: NetworkStack
  [0x0d4000] TE image  module: NtfsDxe_nto{uefi_dx3_dr1v3r_f0und}
  [!] module at 0x0d4000 has no known vendor GUID and references SmmInstallProtocolInterface
```

Последний модуль без вендорского GUID и со ссылкой на SMM-интерфейсы — подозрительный.

## Шаг 4: признаки зловредного DXE-драйвера

- **Нет вендорского GUID.** Легитимные модули подписаны и имеют известные GUID.
- **Ссылки на SMM.** Обычный DXE-драйвер не должен трогать SMM-интерфейсы.
- **Хук на `ExitBootServices`.** Модуль регистрируется, чтобы получить управление в момент передачи управления ОС — это техника bootkit (LoJax).
- **Патчинг других модулей.** Имплант правит чужой код в памяти (например, обходит Secure Boot-проверку).
- **Запись в NVRAM.** Установка себя как загрузочного элемента через UEFI-переменные.

## Шаг 5: SMM-имплант и почему он страшен

SMM-модуль исполняется по прерыванию SMI, в отдельном адресном пространстве. Его нельзя увидеть из ОС: ни диспетчер задач, ни антивирус, ни гипервизор не покажут его код. Найти SMM-имплант можно только:

1. **статически** — разобрав прошивку и найдя модуль, зарегистрированный как SMI-обработчик;
2. **аппаратно** — через отладчик (JTAG) на живой плате;
3. **по побочным признакам** — аномальные задержки при SMI, изменения в SMRAM.

## Шаг 6: безопасный разбор прошивки

Прошивку анализируют **на копии**, никогда не прошивая её обратно:

```bash
$ uefi-firmware-parser -e firmware.bin -o extracted/
$ ls extracted/
DxeCore  UsbBusDxe  NetworkStack  NtfsDxe_nto{...}
```

Извлечённые модули — обычные PE/TE, их открывают в Ghidra (с плагином EFI) или IDA. Так же смотрят, что модуль делает на `_ModuleEntryPoint`.

## Что мы теперь знаем

- Прошивка — контейнер Firmware Volume с модулями PE/TE.
- UEFI DXE-драйверы исполняются на этапе инициализации; SMM — вне ОС.
- Импланты находят по отсутствию вендорского GUID и ссылкам на SMM/ExitBootServices.
- SMM-имплант не виден из ОС — только статически или аппаратно.
- Разбирать прошивку надо на копии, без перепрошивки.

## Шаг 7: разбор структуры Firmware Volume

Firmware Volume — контейнер с заголовком `_FVH` (сигнатура `0x4856465F`). Внутри — файлы, у каждого свой GUID и тип. Файл состоит из секций; секция может содержать PE/TE-образ, сырые данные или сжатый блок.

```bash
$ python3 scan_uefi.py firmware.bin --volumes
FV @ 0x000000  size 0x800000  _FVH ok
  file GUID 7C04A583-9E3E-4F1C-AD65-E05268D0B4D1  type DXE_DRIVER
  file GUID A59E8B8C-...                           type PEIM
```

Так восстанавливается карта прошивки: какие модули есть и какого они типа. Дальше интересны модули типа `DXE_DRIVER` и `SMM`.

## Шаг 8: как выглядит TE-образ

TE (Terse Executable) — урезанный PE: нет DOS-заголовка, меньше полей. Сигнатура — `VZ` (`0x5A56`). Внутри — тот же код, что и в PE, но без MZ-стаба. Именно поэтому модули прошивки нельзя открыть как обычный PE — нужен конвертер (например, `TE2PE`) или плагин Ghidra.

```bash
$ xxd -l 16 module.te
00000000: 565a 9000 0300 0000 0000 0000 0000 0000  VZ..............
```

`56 5a` — это `VZ`, признак TE-образа.

## Шаг 9: SMM-модули и SMI-обработчики

SMM-модуль регистрирует **SMI-обработчик** — функцию, которая вызывается по прерыванию SMI. Регистрация идёт через `SmmInstallProtocolInterface` или через `EFI_SMM_SW_DISPATCH_PROTOCOL`. В бинарнике это видно по импортам протоколов SMM.

SMI-обработчик имеет максимальные привилегии: он исполняется в SMRAM, недоступной даже гипервизору. Зловредный SMM-модуль может перехватывать любые операции, оставаясь невидимым для ОС.

## Шаг 10: техники прошивочных имплантов

- **Bootkit через `ExitBootServices`.** Модуль регистрирует callback, который срабатывает перед передачей управления ОС, и патчит её загрузчик (LoJax).
- **Патч Secure Boot.** Имплант правит проверку подписи, чтобы загрузить неподписанный код.
- **NVRAM-персистентность.** Запись себя в UEFI-переменную, чтобы перезапускаться.
- **SMM-бэкдор.** Установка SMI-обработчика для скрытого доступа к памяти.

Каждая техника оставляет след в прошивке: лишний модуль, лишний callback, изменённый байт в чужом модуле.

## Шаг 11: инструменты для прошивки

| Инструмент | Задача |
|---|---|
| `UEFITool` | разбор/правка прошивки (GUI) |
| `uefi-firmware-parser` | извлечение модулей (CLI) |
| `chipsec` | аудит защит прошивки |
| Ghidra + EFI-плагин | декомпиляция PE/TE |
| `flashrom` | чтение/запись чипа |

## Шаг 12: где искать имплант в прошивке

Порядок: извлечь все модули, составить список GUID, сверить с известными (база вендорских GUID). Модуль с неизвестным GUID — первый подозреваемый. Затем проверить его импорты: ссылки на SMM, `ExitBootServices`, запись в NVRAM. Затем декомпилировать `_ModuleEntryPoint`. Наконец, сравнить прошивку с эталонной от вендора — diff покажет правки.

## Шаг 13: почему это важно

Прошивочный имплант — самый глубокий уровень компрометации. Он переживает переустановку ОС и смену диска. Обнаружить его антивирусом нельзя. Именно поэтому SMM/UEFI — цель продвинутых атак (APT) и объект реверса. Понимание структуры Firmware Volume и TE-образов — обязательный навык firmware-аналитика.

## Шаг 14: безопасность при разборе

Никогда не прошивай изменённую прошивку обратно на рабочее устройство: неверная правка превратит плату в «кирпич». Анализируй только копии. Если нужно проверить поведение — используй эмуляцию (QEMU с OVMF) или отдельную плату. Чтение чипа (`flashrom -r`) — тоже операция с риском: неверный доступ может повредить прошивку.

## Шаг 15: итоговый чек-лист

- Firmware Volume ищут по `_FVH`; файлы — по GUID и типу.
- UEFI-модули — TE-образы (сигнатура `VZ`), не PE.
- SMM-модули регистрируют SMI-обработчики и живут вне ОС.
- Имплант выдаёт неизвестный GUID и ссылки на SMM/ExitBootServices.
- Разбор — только на копии, без перепрошивки.

Главное: **самый глубокий имплант живёт в прошивке, и его ищут по структуре Firmware Volume и аномальным модулям**.

## Шаг 16: извлечение модулей и первый проход

После разбора томов нужно извлечь каждый модуль в отдельный файл — тогда с ним можно работать инструментами. `uefi-firmware-parser` умеет это одной командой и раскладывает модули по именам.

```bash
$ uefi-firmware-parser -e firmware.bin -o out/
$ ls out/ | head
DxeCore.efi  UsbBusDxe.efi  NetworkStack.efi  NtfsDxe.efi
```

Теперь каждый `.efi` — это PE/TE, который открывается в Ghidra с EFI-плагином. Первый проход: посмотреть список функций и импортов. Для DXE-драйвера типичны `gBS->InstallProtocolInterface`, `gBS->LocateProtocol`, работа с `EFI_SYSTEM_TABLE`. Для SMM — `SmmInstallProtocolInterface`, `SmmAllocatePool`.

## Шаг 17: проверка целостности прошивки

Ключевой приём — **сравнение с эталоном**. Прошивка вендора доступна для скачивания; сравни свою копию с эталонной побайтово. Любое различие в области кода — кандидат в имплант.

```bash
$ cmp -l firmware.bin vendor_firmware.bin | head
 1234567  12 45
 1234601 200 0
```

Несколько изменённых байт посреди модуля — почти наверняка патч. Если патч снимает проверку (например, переход по условию заменён на безусловный), это обход Secure Boot.

## Шаг 18: NVRAM и персистентность

UEFI-переменные хранятся в NVRAM и переживают перезагрузку. Имплант может записать себя туда как элемент загрузки или как «обновление». Проверить переменные можно из ОС:

```bash
$ efivar -l | grep -i boot
$ efivar -p -n 8be4df61-93ca-11d2-aa0d-00e098032b8c-BootOrder
```

Подозрительные переменные с незнакомым GUID или нестандартным содержимым — повод копнуть глубже. Так находят bootkit-и, которые прописали себя в загрузку.

## Шаг 19: SMM-модуль в статике

SMM-модуль выглядит как обычный DXE, но его код исполняется в SMRAM. Признаки: ссылки на `Smm*`-протоколы, обработчики SMI, работа с `EFI_SMM_SYSTEM_TABLE`. В дизассемблере найди функцию, которая регистрируется как SMI-обработчик, и разбери её логику. Часто SMM-модули обфусцированы сильнее обычных.

## Шаг 20: инструменты в деталях

| Инструмент | Ключ/команда | Что даёт |
|---|---|---|
| `UEFITool` | открыть образ | дерево томов и модулей |
| `uefi-firmware-parser` | `-e` | извлечение модулей |
| `chipsec` | `-m` | аудит защит |
| `efivar` | `-l`, `-p` | переменные NVRAM |
| Ghidra | EFI-плагин | декомпиляция PE/TE |
| `cmp`/`diff` | — | поиск правок |

## Шаг 21: итоговый алгоритм анализа прошивки

Первый шаг — извлечь модули и составить список GUID. Второй — сверить с базой известных вендорских GUID; неизвестные пометить. Третий — проверить их импорты на SMM/`ExitBootServices`/NVRAM. Четвёртый — декомпилировать точку входа. Пятый — сравнить прошивку с эталоном и найти правки. Шестой — проверить переменные NVRAM на персистентность.

Этот алгоритм применим к любой прошивке: от ноутбука до серверной платформы. Главное помнить про безопасность: только копия, только эмуляция, никакой перепрошивки рабочего устройства. И главное — **самый глубокий имплант живёт в прошивке, и его ищут по структуре Firmware Volume и аномальным модулям**.
