## Вопрос, с которого всё начинается

У тебя есть Java-приложение — `.class`-файл или `.jar`. Исходников нет. В Java
код компилируется не в машинные инструкции, а в **байткод JVM**, и он лежит
прямо в файле. Значит, его можно прочитать и почти восстановить исходник. Как
это делается и что важно понимать про сам байткод, его структуру и обфускацию?

## Наш пример

Возьмём класс `Hello.class`. Посмотрим, что в нём есть, через `javap` — штатный
дизассемблер JVM:

```
$ javap -c -p Hello.class
public class Hello {
  static int check(int);
    Code:
       0: iload_0
       1: sipush        4919
       4: if_icmpne     11
       7: iconst_1
       8: goto          12
      11: iconst_0
      12: ireturn
}
```

Прочитаем метод `check`. Это **стековая машина** (как EVM, но для Java):

- `iload_0` — загрузить на стек первый целочисленный аргумент (это `x`);
- `sipush 4919` — положить константу 4919;
- `if_icmpne 11` — сравнить два верхних значения; если не равны, перейти на 11;
- `iconst_1` / `goto 12` — вернуть 1;
- `iconst_0` / `ireturn` — иначе вернуть 0.

То есть `check(x) == (x == 4919)`. Логика восстановлена прямо из байткода.

## Шаг 1: структура class-файла

`.class` начинается с магии `0xCAFEBABE` и содержит:

- **версию** формата (major/minor) — важно: новые версии могут не читаться
  старыми декомпиляторами;
- **пул констант** (constant pool) — все константы: числа, строки, имена классов
  и методов;
- **описание класса** — флаги, имя, родитель, интерфейсы;
- **поля и методы** — каждый со своим **Code**-атрибутом (байткод).

Пул констант — самое ценное: там лежат строки и имена, по которым
восстанавливается смысл.

## Шаг 2: инструкции JVM

Байткод JVM — это однобайтовые опкоды (плюс операнды). Ключевые группы:

- **загрузка/сохранение**: `iload`, `aload`, `istore`, `astore` (i — int, a —
  reference);
- **арифметика**: `iadd`, `isub`, `imul`, `idiv`;
- **переходы**: `ifeq`, `if_icmpne`, `goto`;
- **вызовы**: `invokevirtual`, `invokestatic`, `invokespecial`, `invokeinterface`;
- **работа с объектами**: `new`, `getfield`, `putfield`.

Наш `check` использует ровно эти базовые инструкции. Понимая их, читаешь любой
метод.

## Шаг 3: декомпиляторы Java

`javap` даёт байткод, а декомпиляторы — почти исходный Java-код:

- **CFR** — популярный, хорошо справляется;
- **Procyon** — ещё один;
- **Fernflower** — встроен в IntelliJ IDEA;
- **JADX** — для Android (DEX → Java).

Обычно берут CFR: `java -jar cfr.jar Hello.class`. Он вернёт код вида
`if (x == 4919) return 1; else return 0;`. Если декомпилятор падает на новых
фичах — читают `javap` вручную.

Полезно уметь оба режима: декомпилятор даёт обзор всего класса, а `javap`
показывает точный байткод без «догадок». Когда декомпилированный код выглядит
странно (лямбды, `invokedynamic`, синтетические методы), именно `javap` помогает
понять, что реально делает JVM.

## Шаг 4: JAR-архивы

`.jar` — это ZIP с `.class`-файлами и `META-INF/MANIFEST.MF`. Работают так:

```
$ unzip -l app.jar          # список классов
$ unzip app.jar -d app/     # распаковать
$ java -jar cfr.jar app/    # декомпилировать каталог
```

Манифест указывает главный класс (`Main-Class`) и зависимости. В больших
приложениях классов тысячи — начинают с `Main-Class` и идут по вызовам.

## Шаг 5: обфускация Java

Java легко декомпилируется, поэтому её обфусцируют:

- **ProGuard / R8** — переименование классов/методов в `a`, `b`, `c` и удаление
  неиспользуемого кода (используется в Android).
- **Stringer** — шифрование строк.
- **Allatori / Zelix KlassMaster** — control-flow обфускация.
- **Коммерческие протекторы** — иногда с нативной частью.

Снятие: восстановление имён по поведению (декомпилятор показывает структуру, а
имена — бессмысленные буквы), расшифровка строк (найти декриптор и прогнать),
упрощение графа.

## Шаг 6: связь с Android (DEX)

Android-приложения компилируются в **DEX** (Dalvik Executable), а не в JVM
`.class`. DEX — близкий родственник: тоже стековая (регистровая, точнее) машина,
тоже байткод, но со своими опкодами. Инструменты:

- **jadx** — DEX → Java;
- **apktool** — распаковка APK и smali;
- **smali/baksmali** — ассемблер/дизассемблер DEX.

Поэтому навык чтения JVM-байткода напрямую переносится на Android (см. урок про
мобильный реверс).

## Шаг 7: практический маршрут

1. **Определить формат** — `.class` (магия `CAFEBABE`) или DEX (`dex\n`).
2. **Распаковать** (для JAR/APK).
3. **Декомпилировать** (CFR/Procyon/jadx).
4. **Если обфусцировано** — расшифровать строки, упростить граф.
5. **Найти логику** — по строкам, вызовам, константам.

## Шаг 8: пул констант и метаданные

Пул констант — это таблица всех констант класса: числа, строки, имена классов,
методов и полей, ссылки. Именно из него `javap` берёт имена вроде
`java/lang/System.out`. Посмотреть пул можно так:

```
$ javap -v Hello.class
Constant pool:
   #1 = Methodref  #2.#3   // java/lang/Object."<init>":()V
   #2 = Class      #4      // java/lang/Object
   ...
   #7 = Fieldref   #8.#9   // java/lang/System.out:Ljava/io/PrintStream;
```

Для реверса пул ценен тем, что **строки и имена методов лежат открыто** (если
нет обфускации). Даже когда декомпилятор падает, `javap -v` показывает, какие
классы и методы реально используются — по ним восстанавливают смысл.

Ещё в классе есть **атрибуты**: `Code` (байткод), `LineNumberTable` (связь с
строками исходника), `LocalVariableTable` (имена локальных переменных). Если
отладочная информация сохранена, декомпилятор восстанавливает почти исходник —
иногда даже имена переменных.

## Шаг 9: JAR и подпись

JAR — это ZIP с `META-INF/MANIFEST.MF`. Манифест описывает главный класс и
зависимости:

```
Main-Class: com.example.App
Class-Path: lib/dep.jar
```

JAR-файлы могут быть **подписаны** (`META-INF/*.SF`, `*.RSA`): подпись проверяет
целостность классов. При патче подпись ломается, и JVM отказывается запускать
JAR (аналогия с проверками целостности из другого урока). Обход — либо пересобрать
подпись (если есть ключ), либо запускать классы напрямую, минуя проверку JAR.

## Частые вопросы

**Декомпилятор не поддерживает версию.** Проверь major-версию (`javap -v`);
новый класс можно декомпилировать свежим CFR или читать `javap` вручную.

**Имена — одна буква (a, b, c).** Класс прошёл ProGuard/R8. Восстанавливай смысл
по структуре и строкам; иногда имена можно угадать по поведению.

**Строки зашифрованы.** Найди метод-декриптор (обычно вызывается в `<clinit>` или
в начале метода), прогони его на зашифрованных значениях.

**JAR не запускается после патча.** Сломана подпись — запускай классы напрямую
или пересобери без подписи.

## Что мы теперь знаем

- Java-код компилируется в **байткод JVM**; `.class` начинается с `CAFEBABE` и
  содержит пул констант, поля, методы с байткодом.
- Байткод — стековая машина; `iload_0`/`sipush`/`if_icmpne` — базовые
  инструкции.
- В нашем `Hello.class` `check(x)` возвращает `(x == 4919)`.
- Декомпиляторы (CFR, Procyon, Fernflower) восстанавливают Java; JAR —
  ZIP с классами.
- Обфускация (ProGuard, Stringer) снимается расшифровкой строк и упрощением;
  Android использует DEX (jadx/apktool).
