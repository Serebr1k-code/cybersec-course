Java компилируется не в машинный код, а в **байткод** — компактный набор инструкций для виртуальной
машины JVM. Байткод и метаданные хранятся в class-файлах, которые упаковываются в JAR. Как и в .NET,
это делает анализ удобнее: декомпиляторы восстанавливают исходный Java почти без потерь. Но
обфускаторы (ProGuard, Allatori, Zelix) переименовывают классы, шифруют строки и запутывают поток
управления. Этот урок — о том, как разбирать JVM-байткод и снимать обфускацию.

## Структура class-файла

Class-файл начинается с магии `0xCAFEBABE` (та же, что у fat Mach-O, но в другом контексте) и
содержит: minor/major version, constant pool (константы: строки, имена, типы), флаги доступа,
списки интерфейсов, полей, методов и атрибутов. Каждый метод содержит **Code**-атрибут с массивом
байткодов и таблицей исключений. Метаданные (имена классов, методов, полей) обычно сохраняются, что
и позволяет декомпилировать.

Определить Java-артефакт: `file` покажет `compiled Java class data`, `Java archive data (JAR)`;
`unzip -l app.jar` покажет содержимое; `jar tf` — список. Для Android используется формат DEX
(см. урок про Android), но принцип похож.

## javap и декомпиляторы

**javap** (входит в JDK) — штатный дизассемблер байткода:

```
$ javap -c -p -v com/example/Crackme.class
Compiled from "Crackme.java"
public class com.example.Crackme {
  public static boolean verify(java.lang.String);
    Code:
       0: aload_0
       1: ldc           #7   // String s3cr3t
       3: invokevirtual #9   // String.equals:(Ljava/lang/Object;)Z
       6: ireturn
}
```

Флаги: `-c` (байткод), `-p` (приватные), `-v` (verbose, включая constant pool), `-s` (дескрипторы).
Для восстановления исходников используют декомпиляторы: **CFR**, **Procyon**, **FernFlower**
(встроен в IntelliJ), **jd-cli**, **jadx** (для Android/DEX, но умеет и JAR). Командная строка CFR:

```
$ java -jar cfr.jar crackme.jar --outputdir out/
```

На выходе — читаемые `.java`-файлы. FernFlower часто даёт лучший результат; jadx — универсальный
инструмент с GUI.

## JAR и Android

JAR — это ZIP с class-файлами и манифестом. Распаковать: `unzip app.jar -d app/`. Внутри —
`META-INF/MANIFEST.MF` (точка входа `Main-Class`), class-файлы, ресурсы. Для запуска:
`java -jar app.jar`. Если JAR обфусцирован, имена классов будут вроде `a.b.c` или нечитаемыми
символами.

Android-приложения используют DEX (Dalvik Executable) вместо JVM class-файлов. Инструменты: `jadx`,
`apktool` (smali), `dex2jar` (DEX → JAR для декомпиляции Java). Хотя байткод Dalvik отличается от
JVM, принципы анализа те же: декомпиляция, работа с обфускацией, динамический анализ (Frida).

## Обфускация JVM

Популярные обфускаторы и их приёмы:

- **ProGuard/R8**: переименование классов/методов/полей, удаление неиспользуемого кода. Строки не
  шифрует — это «оптимизирующий», а не «защитный» обфускатор.
- **Allatori**: переименование, шифрование строк, control flow, watermark.
- **Zelix KlassMaster**: строки, поток, переименование.
- **Stringer**: шифрование строк.
- **JObfuscator**, **Branchlock**: control flow, строки.

Приёмы: **name mangling** (нечитаемые имена), **string encryption** (строки через декриптор),
**control flow obfuscation** (перестановка блоков, фейковые ветвления), **reflection** (вызовы через
`Class.forName`/`Method.invoke`), **native code** (JNI, критичная логика в `.so`).

## Практический разбор

Пусть есть `crackme.jar`. Распаковываем и смотрим:

```
$ unzip -l crackme.jar
  META-INF/MANIFEST.MF
  com/example/Crackme.class
  com/example/Checker.class

$ java -jar cfr.jar crackme.jar --outputdir out/
$ cat out/com/example/Checker.java
public class Checker {
    public static boolean verify(String s) {
        StringBuilder sb = new StringBuilder();
        for (int i = 0; i < s.length(); i++)
            sb.append((char)(s.charAt(i) ^ 0x42));
        return sb.toString().equals("s3cr3t");
    }
}
```

Алгоритм виден: XOR каждого символа с `0x42` и сравнение с `s3cr3t`. Пишем обратный XOR и получаем
пароль. Если декомпиляция «сломалась» (обфускация), смотрим байткод через `javap -c` — там логика
тоже читаема.

## Ключевые инструкции байткода

Понимание байткода помогает, когда декомпилятор не справляется:

| Инструкция | Значение |
|---|---|
| `ldc` | загрузить константу (строку/число) |
| `iload`/`aload` | загрузить локальную переменную |
| `istore`/`astore` | сохранить в локальную |
| `invokevirtual`/`invokestatic` | вызов метода |
| `invokedynamic` | динамический вызов (лямбды, строки) |
| `if_icmpne`/`ifeq` | ветвление |
| `iand`/`ixor`/`ishl` | битовые операции |
| `new`/`newarray` | создание объекта/массива |
| `areturn`/`ireturn` | возврат |

Стек-машина: инструкции работают со стеком операндов (как в CIL). Читая `javap -c`, вы восстанавливаете
вычисления даже без декомпилятора.

## Динамический анализ

Отладка JVM: JDWP (`-agentlib:jdwp=transport=dt_socket,server=y,suspend=n,address=*:5005`), подключение
через IDE или `jdb`. Инструментация: **Frida** (с `frida-java-bridge`) перехватывает методы Java без
отладчика; **Byte Buddy**/`javaagent` позволяют патчить классы в рантайме. Для Android — Frida,
`objection`, Xposed. Динамика особенно полезна против строкового шифрования: перехватываем декриптор
и логируем строки.

## Constant pool и его анализ

Constant pool — центральная структура class-файла: массив констант (UTF-8 строки, имена классов и
методов, дескрипторы типов, числовые литералы). Инструкции ссылаются на записи пула по индексу
(`ldc #7`, `invokevirtual #9`). Именно поэтому `javap -v` печатает пул: он раскрывает имена и
строки, даже если декомпилятор запутался. Для обфусцированного кода пул — кладезь информации: там
остаются имена методов, вызываемых через reflection, и строки (если не зашифрованы).

При строковом шифровании в пуле вместо читаемых строк лежат зашифрованные байты (в виде массива
`int`/`byte`), а реальные строки собираются декриптором. Приёмы анализа: найти в пуле массив
констант, декомпилировать метод-декриптор, воспроизвести алгоритм. Часто это XOR или AES с ключом
из другого места кода. Для Zelix и Allatori существуют автоматические деобфускаторы и скрипты
(например, `Simplify` для Zelix, плагины к Recaf).

## Снятие обфускации на практике

Систематический подход к обфусцированному JAR:

1. **Определить обфускатор**: по маркерам в строках (`ZKM`, `Allatori`, `ProGuard`), по структуре
   (переименованные классы, фейковые пакеты), по `MANIFEST`.
2. **Переименовать обратно**: если имена потеряны, ориентируйтесь на строки, поведение и
   API-вызовы; Recaf позволяет удобно переименовывать и комментировать.
3. **Расшифровать строки**: запустить программу под инструментацией (Frida/javaagent) и логировать
   возвраты декриптора, либо воспроизвести алгоритм.
4. **Убрать control flow**: деобфускаторы (Simplify, `threadtear`) восстанавливают порядок блоков.
5. **Нативный слой**: если логика в JNI — переходим к анализу `.so` (Ghidra/IDA).

Инструмент **Recaf** — современный редактор байткода с декомпилятором, деобфускаторами и поиском;
он объединяет то, что раньше делалось несколькими утилитами.

## JNI и нативный слой

Когда критичная логика вынесена в нативный код через **JNI** (Java Native Interface), декомпиляция
Java покажет лишь объявления `native`-методов и вызов `System.loadLibrary("secret")`. Реальная
проверка — в `libsecret.so`. Зацепки:

- Имя нативной функции по умолчанию: `Java_<package>_<Class>_<method>` (с заменой `.`/`_` на `_`).
- `RegisterNatives` в `JNI_OnLoad` регистрирует функции с произвольными именами — тогда ищите
  `JNI_OnLoad` и таблицу `JNINativeMethod`.
- Строки и алгоритмы — в `.so`; анализируйте его как обычный нативный бинарник.

Для Android нативный слой (`arm64-v8a/lib*.so`) анализируется теми же инструментами; часто там
прячут расшифровку строк и проверки целостности.

## DEX и JVM: различия

Хотя Android-байткод (Dalvik/ART, формат DEX) родственен JVM, различия существенны. DEX хранит все
классы приложения в одном файле `classes.dex`, использует регистровую модель вместо стековой, а
инструкции именуются иначе (`invoke-virtual`, `const-string`, `move-result`). Из-за регистровой
модели байткод DEX читается ближе к ассемблеру. Инструменты: `jadx` декомпилирует DEX в Java,
`apktool` — в smali (человекочитаемый ассемблер Dalvik), `baksmali`/`smali` — сборка/разбор.

Практический вывод: навыки JVM-реверса переносятся на Android, но набор инструментов другой. Для
DEX используйте `jadx` как основной декомпилятор, `apktool` — для модификации и перепаковки, а
smali — когда Java-декомпиляция не удаётся. Обфускация Android (R8, DexGuard) аналогична JVM, а
DexGuard дополнительно шифрует строки и добавляет нативную защиту.

## Подводные камни

Первое: декомпилятор может выдать невалидный Java для обфусцированного кода — сверяйтесь с `javap`.
Второе: строки могут быть зашифрованы и расшифровываться в `<clinit>` (статический инициализатор) —
проверяйте его. Третье: логика может быть вынесена в нативный `.so` через JNI — нужен нативный анализ.
Четвёртое: `invokedynamic` (лямбды, конкатенация строк в новых JDK) усложняет чтение байткода.
Пятое: Android DEX отличается от JVM — используйте соответствующие инструменты. Шестое: reflection
скрывает реальные вызовы — ищите строки с именами классов/методов. Седьмое: JAR может содержать
несколько версий одного класса или multi-release структуру (`META-INF/versions/`) — проверяйте, какая
версия используется вашей JVM. Восьмое: некоторые классы генерируются в рантайме (байткод-манипуляции) —
статически их нет.
