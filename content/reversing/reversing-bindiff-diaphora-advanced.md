## Вопрос, с которого всё начинается

Вышел патч библиотеки `libfoo`. В описании сказано «исправлена уязвимость», но деталей нет. У тебя есть обе версии — `libfoo_v1.so` и `libfoo_v2.so`. Как найти именно то место, которое исправили, и понять баг?

## Наш пример

Смотрим на файлы:

```
$ file libfoo_v1.so libfoo_v2.so
libfoo_v1.so: ELF 64-bit LSB shared object, x86-64
libfoo_v2.so: ELF 64-bit LSB shared object, x86-64
```

Две почти одинаковые библиотеки. Наивный `diff` по байтам даст горы изменений из-за сдвигов адресов. Нужен **структурный диффинг**.

## Шаг 1: почему байтовый diff бесполезен

Компиляция недетерминирована по смещениям: одна добавленная функция сдвигает все адреса, и байтовый `diff` показывает изменения везде. Поэтому инструменты диффинга работают на уровне **функций**: сначала выделяют функции в обоих бинарниках, затем сопоставляют их.

Ключевые инструменты: **BinDiff** (коммерческий, с плагинами IDA/Ghidra), **Diaphora** (открытый, плагин IDA/Ghidra), а также встроенный diff в Ghidra и radiff2 (radare2).

## Шаг 2: как сопоставляются функции

Матчинг идёт в несколько проходов:

1. **Хеши/сигнатуры** — точное совпадение по байтам (или по нормализованному коду).
2. **Имена символов** — если символы не вырезаны, совпадение мгновенное.
3. **Структурные признаки** — число базовых блоков, рёбер, вызовов.
4. **Графовый матчинг** — сопоставление вызываемых функций (call graph) итеративно, пока множество совпадений не стабилизируется.

В результате каждая функция получает оценку сходства. Пары с высокой оценкой — «та же функция», с низкой — изменённые или новые.

## Шаг 3: находим изменённую функцию

После сопоставления смотрим функции, которых нет в v1, или чей код изменился:

```
v2: foo_parse_request   [NEW]
v1: foo_parse_request   [0.42 similarity]
```

Низкое сходство при одинаковом имени — верный признак патча. Открываем обе версии рядом и сравниваем базовые блоки: в v2 появилась проверка длины, которой не было в v1. Это и есть исправление — значит, в v1 был переполнение буфера или похожий баг.

## Шаг 4: patch-diff как источник N-day

Так находят **N-day** уязвимости: вендор выпустил патч, но не раскрыл детали. Взяв старую и новую версии, ты по диффу восстанавливаешь уязвимость и можешь проверить, уязвимы ли другие сборки. Это легальный метод при наличии разрешения и важный для защиты: пока не все обновились, ты знаешь, где риск.

## Шаг 5: работа с вырезанными символами

Если символы вырезаны (`strip`), диффинг опирается на структурные признаки. Точность падает, но сходимость остаётся: одинаковые функции всё равно находят по форме графа. Дополнительно помогают строки и константы: функция, ссылающаяся на ту же строку ошибки, скорее всего та же.

## Шаг 6: практика на нашей библиотеке

Сравним версии и найдём добавленное:

```
$ strings -n 5 libfoo_v1.so libfoo_v2.so
...
libfoo_v2.so: foo_parse_request bounds_check
libfoo_v2.so: nto{p4tch_d1ff_b0unds_ch3ck}
```

Новая строка `bounds_check` в v2 — прямое указание: патч добавил проверку границ. В реальном коде вместо строки был бы новый блок с `cmp`/`jae`, а артефакт указывал бы на суть фикса.

## Что мы теперь знаем

- Байтовый diff бесполезен из-за сдвигов адресов; нужен функциональный матчинг.
- BinDiff/Diaphora сопоставляют функции по хешам, именам, структуре и графу вызовов.
- Изменённые функции находят по низкому сходству при совпадении имени.
- Patch-diff — источник N-day: по патчу восстанавливают уязвимость.
- При вырезанных символах помогает структура графа и строки.

## Куда дальше

Дальше — восстановление CFG, которое лежит в основе любого автоматического анализа. Пока главное запомни: **диффинг сопоставляет функции, а патч — это функция с низким сходством; по нему восстанавливают уязвимость**.

## Где пригодится

- **N-day research:** анализ пропатченных уязвимостей.
- **Антивирус/EDR:** поиск схожих образцов.
- **Аудит обновлений:** что реально изменилось в новой версии.
