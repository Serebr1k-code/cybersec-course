**Кастомные пакеры** — распространённая защита malware и CTF: бинарь «упакован», реальный код зашифрован и распаковывается в рантайме, а на диске виден лишь небольшой **стаб** (загрузчик). Задача аналитика — найти **OEP** (Original Entry Point), снять дамп расшифрованного кода из памяти и восстановить **IAT** (Import Address Table), чтобы получить работоспособный распакованный бинарь. Пакеры бывают простыми (один слой XOR) и сложными (многослойное шифрование, виртуализация, анти-дамп). В этом уроке — полный workflow распаковки кастомных пакеров.

## Как устроен пакер

Пакер состоит из **стаба** — кода, который исполняется первым. Стаб: расшифровывает оригинальный код в памяти, разрешает импорты (динамически загружает DLL и заполняет IAT), применяет релокации, восстанавливает секции и передаёт управление на OEP. На диске оригинальный код зашифрован, поэтому статический анализ видит только стаб. Ключевые точки: где стаб расшифровывает, куда пишет, где прыгает на OEP.

## Типы пакеров

- **Простой (XOR/RC4)**: один слой шифрования, стаб расшифровывает целиком.
- **Многослойный**: несколько стабов, каждый снимает свой слой.
- **Секционный**: каждая секция шифруется отдельно.
- **Полиморфный**: стаб меняется при каждом заражении.
- **Виртуализирующий (VMProtect/Themida)**: код превращается в байткод для кастомной VM — распаковка сложна.
- **Упаковка ресурсов/оверлеев**: данные в конце файла (overlay).

Для CTF чаще простые и средние; для malware — VMProtect и Themida.

## Поиск OEP

OEP — точка, куда передаётся управление после распаковки. Методы поиска:

1. **Хвост стаба**: в x64dbg идём по коду стаба, ищем `jmp`/`call` на адрес в другой секции (обычно `.text`). Это часто и есть OEP.
2. **Break on memory write**: ставим аппаратный брейкпоинт на запись в секцию кода; когда стаб расшифровывает, срабатывает.
3. **ESP-трюк**: на входе стаба сохраняем `ESP`, ставим аппаратный bp на запись по этому адресу — классика для UPX.
4. **Секция `.text`**: OEP обычно в начале `.text` или после распакованного блока; смотрим на изменение прав (`VirtualProtect` на `PAGE_EXECUTE_READ`).
5. **Автоматика**: плагины (Scylla, x64dbg-скрипты) ищут OEP эвристиками.

## Дамп процесса

Найдя OEP, снимают дамп памяти процесса:

- **x64dbg**: плагин **Scylla** (`Plugins → Scylla`) — дамп + восстановление IAT.
- **Process Hacker / Process Explorer**: `Create dump` (полный дамп памяти).
- **Scylla** отдельно: `Scylla.exe` → выбрать процесс → `Dump`.
- **PE-sieve**: сканирует процесс и выгружает подозрительные модули.
- **frida-dump**: через Frida (`frida-dump.py -p PID`).

Дамп снимают **после** распаковки, но **до** выполнения оригинального кода (иначе память изменится).

## Восстановление IAT

Дамп памяти содержит указатели на функции, но таблица импорта «сломана» (адреса — абсолютные, а не имена). **Scylla** восстанавливает IAT: анализирует вызовы, сопоставляет адреса с экспортами DLL и перестраивает таблицу. Процесс: `IAT Autosearch` → `Get Imports` → `Fix Dump` (применить к дампу). Без восстановления IAT дамп не запустится (нет корректных импортов). Для сложных случаев IAT собирают вручную: смотрят, какие функции вызываются, и добавляют их в таблицу.

## Инструменты и обход анти-дамп/анти-отладки

Инструменты: x64dbg (+Scylla, ScyllaHide), OllyDbg (32-bit, старые пакеры), WinDbg, `pe-sieve`, `hollows_hunter`, `unipacker` (автоматический распаковщик), `PE-bear` (анализ). Анти-анализ: проверки `IsDebuggerPresent`, `NtQueryInformationProcess`, timing, `OutputDebugString`, проверка целостности дампа (checksum), анти-дамп (стирание PE-заголовка, `SizeOfImage`). Обходы: ScyllaHide/TitanHide (скрытие отладчика), патч проверок, восстановление заголовка (Scylla), запуск без отладчика с дампом по таймеру.

## Полный разбор: распаковка кастомного пакера

**Шаг 1 — статика:** открываем в PE-bear, видим подозрительно мало импортов и высокую энтропию `.text`. **Шаг 2 — отладка:** запускаем в x64dbg с ScyllaHide, встаём на entrypoint. **Шаг 3 — поиск расшифровки:** ставим аппаратный bp на запись в `.text`; при срабатывании смотрим код стаба. **Шаг 4 — OEP:** доходим до `jmp` в `.text` — это OEP; ставим bp. **Шаг 5 — дамп:** останавливаемся на OEP, Scylla → Dump. **Шаг 6 — IAT:** Scylla `IAT Autosearch` → `Get Imports` → `Fix Dump`. **Шаг 7 — проверка:** запускаем восстановленный бинарь; если не стартует, правим релокации/заголовок вручную. **Шаг 8 — анализ:** распакованный код загружаем в Ghidra.

## Шпаргалка

| Задача | Инструмент/приём |
|---|---|
| Найти OEP | bp на запись в `.text`, ESP-трюк |
| Дамп | Scylla, Process Hacker, pe-sieve |

| Скрыть отладчик | ScyllaHide, TitanHide |

## Что дальше / решение

Маршрут: определите пакер (энтропия, импорты), запустите под отладчиком со скрытием, найдите OEP (bp на запись в код / хвост стаба), снимите дамп и восстановите IAT через Scylla, проверьте запуск. Для многослойных пакеров повторите процесс на каждом слое. Дальше изучайте VMProtect/Themida-обвязки, автоматические распаковщики и обход анти-дамп-техник.

## Определение пакера

Первый шаг — понять, что за пакер. Признаки: высокая энтропия секций (`binwalk -E`, `ent`), мало импортов (`Import Directory` пуст или содержит только `LoadLibrary`/`GetProcAddress`), необычный entrypoint (не в `.text`), наличие второй секции с кодом/данными, overlay в конце файла, строки с именами известных пакеров (UPX, ASPack, MPRESS, VMProtect). Инструменты: **Detect It Easy (DIE)** (`die sample.exe`) распознаёт десятки пакеров по сигнатурам; **PEiD** (старый); `pe-sieve` для распакованного состояния. Если пакер известен (UPX), распаковка тривиальна (`upx -d`), но кастомные требуют ручного анализа. Энтропию можно оценить: `python3 -c "import math,collections;..."` или `binwalk -E`.

## Распаковка через эмуляцию

Когда реальный запуск опасен или невозможен, стаб эмулируют. **Unicorn Engine** позволяет исполнить код стаба, отслеживая запись в память:

```python
from unicorn import *
from unicorn.x86_const import *
mu = Uc(UC_ARCH_X86, UC_MODE_64)
mu.mem_map(0x400000, 0x200000)
mu.mem_write(0x400000, open("packed.exe","rb").read())
# замапить стек, установить entrypoint, эмулировать
mu.emu_start(0x401000, 0x401000 + 0x5000)
data = mu.mem_read(0x401000, 0x1000)      # распакованный код
```

**Qiling** — фреймворк эмуляции с поддержкой Windows API (загрузка DLL, реестр), удобнее для полных бинарей: `ql = Qiling(["packed.exe"], "rootfs/x86_windows"); ql.run()`. После эмуляции снимают память и восстанавливают образ. Эмуляция особенно полезна для анти-отладочных стабов.

## Восстановление заголовка и релокаций

Дамп памяти не всегда запускается: PE-заголовок может быть стёрт (анти-дамп), а релокации — не применены. **Scylla** восстанавливает заголовок и IAT. Для релокаций: если бинарь не PIE, они могут не требоваться; для PIE/ASLR нужно перенести базовый адрес и применить `.reloc`. Инструменты: `PE-bear` (ручная правка заголовка), `Scylla` (заголовок + IAT), `lordPE`. Часто достаточно установить `ImageBase` дампа в реальную базу загрузки и восстановить `SizeOfImage`. Если секции смещены, их выравнивают (`SectionAlignment`/`FileAlignment`).

## Многослойные пакеры

Сложные образцы упакованы несколько раз: после снятия первого слоя вы снова видите пакер. Процесс повторяется: найдите OEP первого стаба, дампните, затем анализируйте дамп — возможно, это второй пакер. Признаки многослойности: после распаковки entrypoint снова подозрительный, энтропия всё ещё высокая, импорты скудные. Автоматизация: скрипт, который циклически дампит и перезапускает анализ, пока энтропия не снизится. Иногда слои разные (XOR + RC4 + LZMA) — тогда нужен анализ каждого.

## Автоматизация: unipacker и скрипты

**unipacker** — автоматический распаковщик для PE, использующий эмуляцию: `unipacker packed.exe -o unpacked.exe`. Он определяет OEP, снимает дамп и восстанавливает IAT без ручной работы. Для Windows-пакеров с API-эмуляцией — **Qiling** с кастомным скриптом. Также пишут собственные скрипты на **Frida** (`frida-dump`) или **x64dbg-скрипты** для автоматизации OEP-поиска. Для серий образцов строят пайплайн: DIE → распаковка → проверка энтропии → Ghidra-анализ.

## Типичные ошибки при распаковке

- **Дамп до распаковки**: снимаете зашифрованный код — дампните после OEP.
- **Дамп после исполнения оригинала**: память изменилась; останавливайтесь на OEP.
- **Забыли восстановить IAT**: дамп не запустится.
- **Неверная база**: PE-заголовок с другим `ImageBase` → адреса не совпадут.
- **Анти-дамп стёр заголовок**: восстановите вручную (Scylla/PE-bear).
- **Самомодифицирующийся код**: снятый дамп содержит не тот код, что исполнялся — учитывайте.
- **Проверка целостности**: после распаковки бинарь может проверять себя (см. anti-tamper).

## Практика: ручная распаковка на CTF

На CTF кастомный пакер часто встречается как отдельная задача. Типичный сценарий: бинарь печатает «Wrong», но внутри есть расшифрованный флаг. Подход: открыть в Ghidra, увидеть стаб с XOR-циклом, эмулировать цикл на Python (взять зашифрованные байты и ключ из кода), получить флаг. Если стаб самодостаточен, эмуляция Unicorn даёт результат за секунды. Для более сложных пакеров с анти-отладкой сначала снимают проверки (патч), затем распаковывают. Полезно писать скрипты-обёртки: `python unpack.py sample` → печатает распакованный код/строки. Так задача решается воспроизводимо и быстро.

## Распаковка без запуска: статическая эмуляция стаба

Если запускать образец нельзя (риск, отсутствие ОС), стаб эмулируют статически. Инструменты: **Unicorn** (чистая эмуляция), **Qiling** (с API Windows/Linux), **angr** (символическая эмуляция). Схема: замапить образ, стек, установить регистры, начать с entrypoint, а по достижении `ret`/`jmp` на распакованный код — снять память. Для стабов, использующих API (`VirtualAlloc`, `VirtualProtect`), нужен Qiling с реализацией этих вызовов. Преимущество: безопасно, воспроизводимо, можно автоматизировать. Недостаток: не все анти-эмуляционные трюки проходятся. Для CTF это быстрее всего: 20 строк Python дают распакованный код.
