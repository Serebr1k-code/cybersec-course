## Вопрос, с которого всё начинается

`upx -d` на файле не срабатывает. Секции названы нестандартно, стаб выглядит самописным, а код
распаковывается своим алгоритмом. Это **кастомный пакер** — самописный упаковщик, под который нет
готового распаковщика. Как снять такую упаковку вручную?

Опираемся на урок про UPX: там мы разобрали идею «стаб + сжатый оригинал». Кастомный пакер устроен
так же, но его нужно реверсить самому.

## Как устроен самописный пакер

Любой пакер — это две части: **стаб** (код, который распаковывает) и **упакованные данные**
(сжатый/зашифрованный оригинал). Кастомные пакеры различаются деталями:

- **алгоритм**: RLE, LZ, XOR-цепочка, свой шифр, комбинация;
- **слои**: иногда упаковано в несколько проходов (снял один — внутри второй);
- **куда пишет**: в свою секцию, в выделенную через `mmap`/`VirtualAlloc` память, поверх себя;
- **как передаёт управление**: прыжок на OEP, вызов по указателю, возврат из «функции-распаковщика».

## Наш пример

Возьмём минимальный кастомный пакер из урока про самомодификацию и снимем его вручную. Упакованные
данные лежат в `.data`, стаб расшифровывает их и вызывает:

```c
unsigned char blob[] = {0x12,0x80,0xAA,0xAA,0xAA,0x69};  /* зашифровано XOR 0xAA */
int main(void){
    unsigned long pg = (unsigned long)blob & ~0xfffUL;
    sc(10, pg, 0x1000, 7);                    /* mprotect: RWX */
    for (unsigned i=0;i<sizeof(blob);i++) blob[i]^=0xAA;
    int (*f)(void) = (int(*)(void))blob;
    printf("decoded result = %d\n", f());
}
```

Запуск даёт `decoded result = 42`. Внешне файл выглядит как обычная программа, но «полезный» код
появляется только в памяти.

## Шаг 1: найти цикл распаковки

Первым делом ищем место, где стаб **пишет** в память, которую потом исполняет. Признаки:

- вызов `mprotect`/`VirtualProtect` с флагом execute (снятие NX);
- цикл, который читает один буфер и пишет в другой (или в тот же);
- арифметика с константой (XOR, сложение, таблица) — типичный дешифратор.

В нашем дизассемблере:

```
401183:  call   401126 <sc>                 ; mprotect(pg,4096,7) — RWX
40118f:  jmp    4011ad
401191:  mov    eax,DWORD PTR [rbp-0x14]
401194:  movzx  eax,BYTE PTR [rax+0x404018]
40119b:  xor    eax,0xffffffaa              ; xor 0xAA
4011a3:  mov    BYTE PTR [rax+0x404018],dl  ; запись обратно
4011a9:  add    DWORD PTR [rbp-0x14],0x1
4011ad:  cmp    DWORD PTR [rbp-0x14],0x5
4011b1:  jbe    401191
```

Читается так: цикл по 6 байтам, каждый XOR'ится с `0xAA`, результат пишется по тому же адресу.
Алгоритм распаковки понятен.

## Шаг 2: поставить breakpoint на OEP

**OEP** (Original Entry Point) — момент, когда стаб передаёт управление распакованному коду. В нашем
примере это инструкция `call rax` после цикла:

```
4011b3:  mov    QWORD PTR [rbp-0x8],0x404018
4011bf:  call   rax                         ; <-- OEP: вызов расшифрованного кода
```

Ставим точку останова **после цикла, перед вызовом**, и смотрим память:

```
$ gdb -q -batch -ex 'break *0x4011b3' -ex run -ex 'x/6xb &blob' ./stub
0x404018 <blob>:  0xb8  0x2a  0x00  0x00  0x00  0xc3
```

Байты `b8 2a 00 00 00 c3` — это `mov eax, 42; ret`. Мы поймали расшифрованный код.

## Шаг 3: снять дамп

В настоящем пакере после распаковки оригинальный код лежит где-то в памяти. Снимаем дамп:

- **в PE**: дампим процесс (например, Scylla или `procdump`), затем восстанавливаем таблицу
  импортов (**IAT**) — пакер обычно стирает её и резолвит вызовы в рантайме;
- **в ELF**: проще — импорты обычно ленивые через PLT, достаточно дампа загруженных сегментов;
- **если стаб распаковывает лениво** (постранично, перед каждым вызовом) — дампим постранично, по
  мере исполнения, либо прогоняем в эмуляторе и забираем память.

## Шаг 4: восстановить импорты (PE)

Для PE после дампа импорты часто «пустые». Инструмент (Scylla) находит вызовы `call [addr]`,
определяет, какая функция по адресу, и строит новую таблицу импортов. Без этого дамп не запустится:
вызовы будут идти в никуда. Алгоритм:

1. Найти в дампе косвенные вызовы `call [xxxx]`.
2. Определить, какая библиотечная функция лежит по адресу `xxxx`.
3. Построить новый Import Directory и пересобрать файл.

## Что делать после дампа

Дамп — это ещё не готовый к анализу файл. Дальше:

1. **Определить базовый адрес.** Если пакер грузит код по «плавающему» адресу, нужно пересчитать
   все абсолютные ссылки (в PE — `ImageBase`, в ELF — по таблице релокаций).
2. **Восстановить заголовки.** Дизассемблеру нужны корректные секции и точка входа; иногда проще
   «пришить» дамп к копии оригинального заголовка.
3. **Прогнать статику.** Открыть в Ghidra/IDA и убедиться, что код осмысленный: появились строки,
   импорты, читаемые функции.
4. **Проверить на запуск.** Если дамп запускается и ведёт себя как оригинал — распаковка успешна.

Для ELF шаги 1–2 часто не нужны: сегменты грузятся по фиксированным адресам, а импорты резолвятся
лениво. Поэтому ELF-пакеры снимать заметно проще — начни практику с Linux-образцов, а потом переходи
к PE с Scylla.

## Частая ошибка новичка

Новички пытаются «распаковать файл» целиком, не найдя OEP, и получают мусор. Запомни: распаковка — это всегда про **память в конкретный момент**. Файл на диске остаётся упакованным, а осмысленный код существует только в рантайме, между распаковкой и повторным шифрованием. Поэтому ключевой навык — умение поймать этот момент точкой останова или хуком, а не «прочитать» файл.

## Если не сработало

- **Несколько слоёв** → сняв один слой, получишь второй стаб; повторяй процедуру, пока не увидишь
  нормальный код.
- **Распаковка по требованию** → ставь аппаратный watchpoint на **исполнение** страницы, а не на
  один адрес; лови переход на «новую» страницу.
- **Проверки целостности** рушат дамп → нейтрализуй их до правок (см. урок про integrity).
- **Алгоритм зависит от окружения** (время, железо) → прогони в эмуляторе, подставив нужные
  значения хуками.

## Что мы теперь знаем

- **Кастомный пакер** = самописный стаб + упакованные данные; готового распаковщика нет.
- Ищи **цикл распаковки**: снятие NX + чтение/запись буфера + арифметика с константой.
- **OEP** — момент передачи управления распакованному коду; там снимают дамп.
- Для PE после дампа **восстанавливают IAT** (Scylla), для ELF обычно проще.
- Многослойные пакеры снимаются послойно; ленивую распаковку ловят watchpoint'ом на исполнение.

## Куда дальше

Мы научились снимать кастомные пакеры. Дальше перейдём к защите **от изменения** — проверкам
целостности и анти-патчу: как бинарник замечает, что его код поменяли, и как это обойти. А пока
главное запомни: **кастомный пакер снимают, найдя цикл распаковки, поймав OEP и восстановив
импорты**.

## Где пригодится

- **CTF Reversing:** кастомные пакеры — частый «первый слой» сложных задач.
- **Malware analysis:** большинство образцов упакованы самописными пакерами.
- **Packer research:** понимание устройства стабов и OEP.
- **Incident response:** снять упаковку, чтобы понять, что делал образец.
- **Собес:** «как найти OEP и снять дамп?» — практический вопрос RE-собеседования.
