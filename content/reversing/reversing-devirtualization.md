## Вопрос, с которого всё начинается

В прошлом уроке мы узнали, что виртуализация — сильнейшая защита коммерческих протекторов. Теперь
задача практическая: у нас есть виртуализированная функция (например, проверка лицензии в
VMProtect), и нужно получить её **обычный код**. Как это делается по шагам? Этот процесс называют
**девиртуализацией**.

Опираемся на урок про VM-based crackme: там мы разобрали учебную VM. Здесь обобщим это до методики
для реальных протекторов.

## Что мы восстанавливаем

Виртуализация заменяет настоящие инструкции на байткод вымышленной VM. Чтобы вернуть код, нужно
пройти четыре уровня:

1. **Диспетчер** — цикл, который читает опкод и передаёт управление нужному обработчику.
2. **Таблица handler'ов** — массив адресов: `handler[opcode]`.
3. **Семантика каждого handler'а** — что делает опкод (сложить, сравнить, загрузить).
4. **Байткод** — конкретная программа в этой системе команд.

Собрав все четыре, мы «лифтим» байткод обратно в C.

## Наш пример

Напомним учебную VM из прошлого урока. Её дизассемблированный байткод:

```
0000: LOAD
0001: PUSH   0x11
0003: XOR
0004: CMPEQ  0x22
0006: JZ     0x13
0008: INC
0009: PUSHP
000a: PUSH   0x05
000c: CMPEQ?
000d: JNZ    0x16
000f: JMP    0x00
0013: PUSH   0x00
0016: PUSH   0x01
```

Это ровно то, что в реальном протекторе спрятано за диспетчером. Разница лишь в масштабе и в
количестве защит вокруг.

## Шаг 1: трассировка — самый быстрый путь

Первое, что стоит сделать, — **посмотреть, какие опкоды реально исполняются**. Повесим хук на
диспетчер и запишем трассу при вводе `33333`:

```
0000 LOAD
0001 PUSH 0x11
0003 XOR
0004 CMPEQ 0x22
0006 JZ 0x13
0008 INC
0009 PUSHP
000a PUSH 0x05
000c CMPEQ?
000d JNZ 0x16
000f JMP 0x00
0000 LOAD
...
```

Трасса показывает **линейный порядок операций** для конкретного входа — часто этого достаточно,
чтобы понять проверку. Для VMProtect трассировка тоже работает, но генерирует сотни тысяч строк,
поэтому её фильтруют: логируют только «интересные» опкоды (сравнения, доступ к памяти).

## Шаг 2: найти диспетчер и таблицу handler'ов

Статически диспетчер выглядит как косвенный переход по индексу:

```
mov   eax, [vm_ip]
movzx eax, byte [vm_code + rax]     ; опкод
mov   rax, [handler_table + rax*8]  ; адрес обработчика
jmp   rax
```

Найдя `handler_table`, мы получаем список всех обработчиков — их количество равно числу опкодов
VM. Каждый handler — маленькая функция. В реальных протекторах их десятки–сотни, и часть из них
«мусорные» (никогда не вызываются).

## Шаг 3: восстановить семантику обработчиков

Для каждого handler'а отвечаем на вопрос «что он делает со стеком VM и её регистрами». Например:

- handler опкода `PUSH` читает следующий байт байткода и кладёт его на стек VM;
- `XOR` снимает два значения и кладёт результат их XOR;
- `JZ` снимает флаг и меняет указатель инструкций.

Это самая трудоёмкая часть, но она распараллеливается: обработчики короткие, и их удобно
аннотировать по одному.

## Шаг 4: лифтинг байткода

Зная систему команд, пишем «лифтер»: он превращает байткод в промежуточное представление, а затем
в C. Для нашего примера результат лифтинга:

```c
for (i = 0; i < 5; i++) {
    if ((input[i] ^ 0x11) != 0x22) return 0;
}
return 1;
```

Вот и вся «защита». Мы получили исходную логику, не читая ни одной машинной инструкции напрямую.

## Шаг 5: символьная девиртуализация

Ручной разбор десятков handler'ов долог. Поэтому для VMProtect применяют **символьную
девиртуализацию**: инструмент (например, на базе Triton или собственных фреймворков вроде VTIL)
трассирует байткод и строит для каждого выхода **символическое выражение** через входные данные.
Дальше это выражение упрощается (как MBA в уроке про деобфускацию) и превращается в нормальный
код. Так «в лоб» восстанавливают даже проверки лицензий.

Ключевые идеи символьного подхода:

- **Trace + symbolize** — прогон с символическими входами, запись выражений.
- **Simplification** — упрощение выражений до человекочитаемого вида.
- **Recompilation** — генерация нового кода из промежуточного представления.

## Почему это вообще работает

Может показаться удивительным, что защиту «снимают» целиком. Причина в фундаментальном свойстве:
**виртуализация не меняет семантику** — она лишь переводит код в другую систему команд. Значит,
существует взаимно-однозначное соответствие между байткодом и оригиналом. Как только мы восстановили
смысл каждого опкода, байткод можно прочитать так же однозначно, как обычный ассемблер. Протектор
усложняет работу (замусоривание, слои, анти-отладка), но не создаёт новой информации — он её прячет.
Отсюда и общая стратегия: убрать шум, найти соответствия, поднять уровень абстракции обратно.

Ещё одно важное наблюдение: виртуализация **дорога по производительности**. Каждая инструкция
превращается в десяток-другой операций VM. Поэтому протекторы виртуализируют только критичные
функции (проверка лицензии, античит), а не всю программу. Это сужает область работы: девиртуализовать
нужно одну-две функции, а не весь файл.

## Практический совет

Начинай не с обработчиков, а с **диспетчера**: он один и сразу даёт список опкодов. Затем прогони трассу на нескольких разных входах — так увидишь, какие обработчики вообще используются. И только после этого разбирай семантику нужных handler'ов. Это экономит большую часть времени: в реальной VM большая часть обработчиков либо не вызывается на нашем входе, либо делает тривиальные вещи.

## Если не сработало

- **Обработчики замусорены** → сначала упрости каждый handler отдельно, потом строй таблицу.
- **Диспетчер «размазан»** (несколько копий, спрятанные переходы) → найди общий признак (чтение
  опкода) и восстанови таблицу по нему.
- **VM вложенная** (handler сам виртуализован) → это высший уровень; помогает только длительная
  символьная трассировка с агрессивным упрощением.
- **Код читается, но результат неверен** → проверь порядок аргументов на стеке VM: частая ошибка
  — перепутать `a op b` с `b op a` для несимметричных операций (`sub`, `div`, сдвиги).

## Что мы теперь знаем

- **Девиртуализация** восстанавливает код из байткода VM: диспетчер → таблица handler'ов →
  семантика → байткод.
- **Трассировка** даёт линейный порядок операций и часто уже раскрывает логику.
- **Лифтинг** переводит байткод в C.
- **Символьная девиртуализация** (Triton, VTIL) автоматизирует процесс для больших VM.
- Так же, как учебная VM, устроены VMProtect и Themida — разница в масштабе и защитах вокруг.

## Куда дальше

пакеры** — самописные упаковщики со своим стабом, слоями шифрования и поиском OEP. А пока главное
запомни: **девиртуализация — это восстановление системы команд VM и лифтинг байткода обратно в C**.
