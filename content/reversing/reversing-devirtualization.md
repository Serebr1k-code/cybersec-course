**Devirtualization** — восстановление исходной логики из кода, обёрнутого в **виртуальную машину** (VM-based obfuscation). Вместо обычных инструкций программа исполняет «свой» байткод через диспетчер: обработчики (handlers) реализуют примитивные операции, а реальная программа — это поток опкодов в data-секции. Так защищают VMProtect, Themida, Code Virtualizer и кастомные протекторы. Реверс такого кода — одна из сложнейших задач обратной инженерии, требующая понимания диспетчера, восстановления семантики обработчиков и трансляции байткода обратно в нативный вид. Этот урок — методология девиртуализации.

## Как устроена VM-обфускация

Типичная структура:

- **Диспетчер (dispatch loop).** Читает опкод, вычисляет адрес обработчика (таблица переходов, `switch`, косвенный `jmp`), передаёт управление.
- **Обработчики (handlers).** Каждый реализует примитив: сложение, XOR, загрузку/сохранение «регистров» VM, переходы, вызовы.
- **VM-регистры.** Аналог реальных регистров, но в памяти или в наборе host-регистров.
- **VM-стек.** Для операндов/адресов возврата.
- **Байткод.** Поток опкодов + константы, часто в `.data`/`.rdata`, может быть зашифрован.
- **Ключ.** Обработчики могут быть зашифрованы и расшифровываться по частям.

## Почему это сложно

- **Каждый handler — отдельная функция** с ручным/обфусцированным кодом; их десятки-сотни.
- **Нет прямого соответствия** между VM-инструкцией и нативной (1 опкод ≠ 1 инструкция).
- **Обфускация обработчиков**: MBA, junk-код, inlined-операции.
- **Разные VM-регистры** для разных «переменных»; соответствие восстанавливается анализом.
- **Многослойность**: обработчики тоже могут быть виртуализированы.

## Методология девиртуализации

```text
1) Найти диспетчер: большой switch/косвенный jmp, читающий опкод.
2) Идентифицировать VM-регистры и VM-стек (какие ячейки/регистры меняются).
3) Собрать таблицу обработчиков: адрес -> семантика (какой опкод).
4) Трассировать исполнение: записать поток (опкод, операнды) для конкретного ввода.
5) Восстановить семантику: транслировать поток в нативные операции/IR.
6) Построить граф управления и восстановить исходную функцию.
```

## Трассировка и сбор потока

Динамическая трассировка — самый практичный путь:

```python
# Псевдокод: трассировка диспетчера (Frida/PIN/QBDI)
def on_dispatch(ctx):
    opcode = read_mem(vm_ip)
    handler = handlers[opcode]
    log(vm_ip, opcode, handler, vm_regs())
```

Инструменты: **Frida** (hook диспетчера), **Intel PIN**/**DynamoRIO** (DBI), **QBDI**, **Triton** (символьная трасса), **Unicorn** (эмуляция диспетчера). Из трассы получают линейный поток опкодов, который затем упрощают.

## Восстановление семантики обработчиков

Для каждого handler определите, что он делает:

- Читает/пишет VM-регистры → сопоставьте с «переменными».
- Арифметика/логика → операция над операндами.
- Управление потоком → условный/безусловный переход VM.
- Вызов host-API → реальный вызов.

Приём: **символьное исполнение** (Triton/angr) каждого handler'а с символическими VM-регистрами даёт выражение — его упрощают (см. `reversing-binary-lifting`).

## Трансляция обратно

```text
1) Построить IR из семантики handler'ов (VTIL/LLVM IR).
2) Прогнать оптимизации (свёртка констант, dead code).
3) Рекомпилировать в нативный код или восстановить псевдо-C.
```

**VTIL** создан именно для этого: он представляет handlers в едином IR и позволяет «поднять» виртуализированный код обратно в нативный. Альтернатива — remill/McSema + LLVM `opt`.

## Инструменты

| Инструмент | Роль |
|------------|------|
| VTIL | IR для рекомпиляции/девиртуализации |
| Triton | символьная трасса и упрощение |
| angr | символьное исполнение, CFG |
| Frida / PIN / DynamoRIO / QBDI | динамическая трассировка |
| Unicorn | эмуляция диспетчера |
| Ghidra/IDA + скрипты | анализ диспетчера/обработчиков |
| VMProtect-девиртуализаторы | специализированные (research) |

## Разобранный пример: кастомная VM

```text
1) В Ghidra находим диспетчер: while(1){ op = *vm_ip++; switch(op){...} }.
2) Собираем таблицу: case 0x10 -> handler_10 (ADD), 0x11 -> XOR, 0x20 -> JMP...
3) Трассируем вход "AAAA": поток опкодов [0x10, 0x11, 0x20, ...].
4) Транслируем поток в псевдо-C: r0 = r1 + 5; r2 = r0 ^ 0x13; if(r2==...) goto...
5) Восстанавливаем проверку -> решаем (keygen/flag).
```

Для VMProtect шаги те же, но обработчики обфусцированы и их сотни — используют автоматизацию (трасса + символьное упрощение + VTIL).

## Заметки по VMProtect и большим VM

VMProtect — самый распространённый коммерческий случай. Практические наблюдения:

- **Мутация.** Обработчики генерируются заново на каждом билде: сигнатуры не работают, нужна трасса.
- **Смешанный режим.** Часть кода виртуализирована, часть — нативная (мутации); границы ищите по переходу в диспетчер.
- **Стек VM** в отдельной области; VM-регистры могут «мигрировать» между памятью и host-регистрами.
- **Многоуровневость.** Встречаются вложенные VM (диспетчер вызывает другой диспетчер).
- **Инструменты research-уровня.** Публичные девиртуализаторы неполны; реальная работа — комбинация трассы, символики и рекомпиляции (VTIL).
- **Оценка трудозатрат.** Полная девиртуализация VMProtect-функции — дни/недели; часто достаточно восстановить **одну** критичную функцию (проверку ключа), а не всё.

Начинайте с малого: найдите целевую проверку, снимите трассу только её, восстановите семантику — не пытайтесь девиртуализировать весь бинарь.

## Частые ошибки

- **Анализ обработчиков по одному вручную.** Без автоматизации это недели; используйте трассу/символику.
- **Игнорирование VM-регистров.** Без их сопоставления теряется связь с логикой.
- **Пропуск шифрования байткода.** Он может расшифровываться по частям в рантайме.
- **Опора только на статику.** Диспетчер/обработчики часто обфусцированы — нужна динамика.
- **Не учитывать многослойность.** Обработчики могут быть виртуализированы повторно.
- **Ошибки в трассировке.** Неверный ввод → неполный поток; берите несколько входов.

## Известные протекторы и их особенности

| Протектор | Особенности VM |
|-----------|----------------|
| VMProtect | «мутация» обработчиков на каждом билде, многослойность, свой IR |
| Themida/WinLicense | комбинирует виртуализацию с упаковкой и анти-отладкой |
| Code Virtualizer | кастомные VM для выбранных функций |
| Obsidium / Enigma | виртуализация + защита импортов |
| Кастомные (malware) | простые VM, часто с XOR-шифрованным байткодом |

Общее: диспетчер + таблица обработчиков + поток опкодов. Различия — в степени обфускации обработчиков и многослойности.

## Автоматизация девиртуализации

Ручной разбор сотен обработчиков нереален — нужна автоматизация:

```text
1) Трассировка (PIN/Frida/QBDI) -> поток (opcode, operands, vm_ip).
2) Для каждого уникального opcode — запись символического эффекта.
3) Символьное исполнение handler'а (Triton) -> выражение над VM-регистрами.
4) Упрощение выражений (z3/MBA-Solver) -> читаемая семантика.
5) Сборка IR потока -> оптимизация (LLVM) -> псевдо-C/нативный код.
```

**VTIL** — специализированный IR для этого: он принимает handlers и «поднимает» их в единое представление, а затем рекомпилирует. Для простых VM хватает скрипта: словарь `opcode -> lambda(regs, operands)` и интерпретация потока.

## Символика и упрощение

Каждый обработчик моделируется символически:

```python
from z3 import *
r0, r1 = BitVecs('r0 r1', 64)
# handler_10: r0 = r0 + operand
# handler_11: r1 = r1 ^ operand
# затем упрощаем составное выражение всего потока
expr = simplify((r0 + 5) ^ 0x13)
```

MBA-обфускация внутри обработчиков снимается теми же средствами, что и в `reversing-binary-lifting` (тождества, `simplify`, MBA-Solver). Так «нечитаемый» handler превращается в `add`/`xor`/`cmp`.

## Подводные камни и практические советы

- **Много входов.** Один поток опкодов для одного ввода не покрывает все обработчики. Снимите трассу для нескольких разных входов (валидный/невалидный/пустой), чтобы увидеть больше ветвей.
- **Обработчики, зависящие от контекста.** Некоторые handlers ведут себя по-разному в зависимости от флагов VM; трассируйте их состояния.
- **Зашифрованные обработчики.** Расшифровываются по мере исполнения — трасса должна идти до расшифровки; статика покажет мусор.
- **Диспетчер с несколькими уровнями.** Иногда есть вложенные диспетчеры (мета-VM) — разбирайте послойно.
- **Анти-трассировка.** VM может детектировать DBI/отладчик (timing, debug-регистры) — используйте эмуляцию (Unicorn) или аппаратную трассировку (Intel PT).
- **Логирование.** Сохраняйте поток (opcode, operands, vm_ip) в файл — это основа для последующей трансляции и воспроизведения.
- **Проверка гипотез.** Собрав семантику, прогоните её на реальном входе и сравните результат с оригиналом (эмуляция/нативная VM) — так вы убедитесь, что девиртуализация верна.

## Что делать дальше / решение

1. Локализуйте диспетчер и VM-регистры/стек.
2. Постройте таблицу обработчиков (адрес → семантика).
3. Снимите трассу потока опкодов для нескольких входов.
4. Восстановите семантику (символика/ручной анализ) и соберите IR.
5. Транслируйте обратно (VTIL/LLVM) и оптимизируйте.
6. Восстановите исходную логику и решите задачу (flag/keygen).
