## Вопрос, с которого всё начинается

На сервере нашли файл `suspicious.ko` — модуль ядра. Его никто не ставил руками, но он там есть. Что он делает и не перехватывает ли он системные вызовы?

## Наш пример

`*.ko` — это ELF-объект, но собранный для ядра. Возьмём `suspicious.ko` и разберём его: посмотрим заголовок, импортируемые символы ядра и строки. Наша цель — понять, что модуль перехватывает.

## Шаг 1: LKM — это не обычная программа

**LKM** (Loadable Kernel Module) загружается прямо в адресное пространство ядра и работает в ring0. Он не линкуется с обычной libc — вместо этого он вызывает **экспортируемые символы ядра** (`printk`, `register_kprobe`, `kallsyms_lookup_name` и т.д.).

У модуля есть важное поле — **`vermagic`**: строка вида `5.15.0-91-generic SMP mod_unload modversions`. Она говорит, для какой версии ядра и с какими опциями собран модуль. Если `vermagic` не совпадает с текущим ядром, модуль не загрузится.

```bash
$ strings suspicious.ko | grep -i vermagic
vermagic=5.15.0-91-generic SMP mod_unload modversions
```

## Шаг 2: symbol-версии

Ядро не гарантирует стабильный ABI. Чтобы модуль не вызывал «не ту» функцию после изменения структуры, используется **symbol versioning** (CRCs). Модуль хранит CRC для каждого внешнего символа; при загрузке ядро сверяет их и отказывается грузить модуль при несовпадении.

В ELF-секции `.gnu.version_r`/`.modinfo` лежат записи о версиях. Для реверса это подсказка: список импортируемых символов ядра сразу говорит, чем занимается модуль.

## Шаг 3: kprobes — перехват функций ядра

**kprobe** — штатный механизм ядра: можно «повесить» обработчик на любую инструкцию адреса ядра. Малварь (и руткиты) используют `register_kprobe`, чтобы перехватить системный вызов или сетевую функцию и подменить её поведение.

```bash
$ strings suspicious.ko | grep -E 'kprobe|kretprobe|register'
register_kprobe
register_kretprobe
kallsyms_lookup_name
```

`register_kretprobe` перехватывает **возврат** из функции — удобно, чтобы незаметно подменить результат (например, скрыть файл из `getdents`).

## Шаг 4: ftrace-хуки

Альтернатива kprobes — **ftrace**. Ядро имеет встроенную трассировку; модуль может зарегистрировать свой callback через `ftrace_set_filter_ip`/`register_ftrace_function` и вызываться до/после функции ядра. Так делают «чистые» руткиты: код не патчится, а ftrace сам вызывает чужой обработчик.

Признак в бинарнике — строки `ftrace_ops`, `ftrace_set_filter`, `FTRACE_OPS_FL_*`.

## Шаг 5: разбираем модуль скриптом

Скрипт `scan_lkm.py` печатает секции, размер и импорты ядра:

```bash
$ python3 scan_lkm.py suspicious.ko
ELF64 relocatable, arch=x86-64
sections: .text (size 0x1420)  .init.text  .data  .modinfo
undefined (imported) symbols:
  register_kprobe
  kallsyms_lookup_name
  getdents64  (patched?)
  nto{lkm_kpr0b3_g3td3nts_h00k}
```

Список импортов сразу выдаёт цель: модуль перехватывает `getdents64` — классический приём сокрытия файлов.

## Шаг 6: как анализировать безопасно

Разбор модуля ядра — рискованная задача: ошибка в загруженном `.ko` валит систему. Поэтому:

1. **Статика в первую очередь.** `objdump -d`, `readelf -a`, `strings` — без загрузки.
2. **Изолированная ВМ.** Если нужно загрузить — только в снапшоте, с отключённым модулем после.
3. **Сравнение с эталоном.** Если у тебя есть «чистый» модуль того же продукта, diff покажет добавленный код.

Никогда не грузи `suspicious.ko` на рабочей системе.

## Что мы теперь знаем

- LKM — ELF-модуль для ring0 с полем `vermagic`.
- Ядро сверяет symbol-версии (CRC), чтобы не грузить несовместимый код.
- kprobes и ftrace — штатные механизмы, которыми злоупотребляют руткиты.
- Список импортов модуля прямо указывает, что он перехватывает.
- Разбирать `.ko` надо статически и в изоляции.

## Шаг 7: разбор `.modinfo` и метаданных

У каждого LKM есть секция `.modinfo` — набор пар «ключ=значение». Это первое, что смотрят:

```bash
$ readelf -p .modinfo suspicious.ko
  [ 0] license=GPL
  [ 1] author=unknown
  [ 2] description=network helper
  [ 3] vermagic=5.15.0-91-generic SMP mod_unload modversions
  [ 4] depends=
```

Ложные `author`/`description` — частый признак руткита: он маскируется под безобидный модуль. Пустое `depends` и подозрительная лицензия — тоже повод присмотреться.

## Шаг 8: секции ELF модуля

LKM — это relocatable ELF (`ET_REL`), не исполняемый файл. Поэтому у него нет фиксированных адресов, а есть таблицы релокаций:

| Секция | Назначение |
|---|---|
| `.text` | код модуля |
| `.init.text` | код, исполняемый один раз при загрузке |
| `.exit.text` | код выгрузки |
| `.rodata` | строки и константы |
| `.data` / `.bss` | данные |
| `.rela.text` | релокации кода |

`.init.text` особенно интересен: там живёт инициализация, где модуль регистрирует хуки. Часто именно она обфусцирована.

## Шаг 9: перехват через `sys_call_table`

Старый приём руткитов — заменить адрес функции в `sys_call_table` (таблица системных вызовов ядра). Тогда вызов `sys_read` уходит в код руткита.

Современные ядра **защищают** таблицу (read-only), поэтому её сначала снимают с защиты (`set_memory_rw`), потом патчат. В бинарнике это видно по импортам:

```bash
$ strings suspicious.ko | grep -E 'set_memory|write_cr0|kallsyms'
set_memory_rw
kallsyms_lookup_name
write_cr0
```

Комбинация `write_cr0` + `kallsyms_lookup_name` + `sys_call_table` — почти диагноз.

## Шаг 10: eBPF-руткиты

Новее — руткиты на **eBPF**. Загружается BPF-программа, которая перехватывает события ядра. Преимущество: не патчится код ядра, работает «легально» через штатный механизм. Найти такой руткит статически нельзя — он в памяти как BPF-байткод; нужен `bpftool prog list` и аудит загруженных программ.

В `.ko` признак — вызовы `bpf_prog_load`/`bpf()` с нестандартными типами программ.

## Шаг 11: инструменты для LKM

| Инструмент | Задача | Команда |
|---|---|---|
| `readelf` | секции, символы | `readelf -a mod.ko` |
| `objdump` | дизассемблер | `objdump -d mod.ko` |
| `modinfo` | метаданные | `modinfo mod.ko` |
| `nm` | символы | `nm -u mod.ko` |
| `bpftool` | eBPF-программы | `bpftool prog list` |

## Шаг 12: порядок разбора и решение

Начни с `modinfo` и списка импортов: они сразу говорят, что модуль делает. Затем дизассемблируй `.init.text` — там регистрация хуков. Найди, какие функции ядра перехватываются, и сопоставь с импортами kprobe/ftrace. Если модуль использует `sys_call_table` или eBPF — это признак руткита. Дальше — только изолированная ВМ.

## Шаг 13: как устроен вызов из модуля в ядро

Когда `.ko` вызывает `printk`, это не прямой прыжок по адресу. В relocatable ELF адрес символа ещё не известен, поэтому в `.rela.text` лежит запись релокации: «по смещению X подставить адрес символа `printk`». При загрузке ядро разрешает эти релокации по своей таблице символов.

Отсюда важное следствие: **список неразрешённых (undefined) символов модуля — это и есть список того, что он вызывает в ядре**. `nm -u mod.ko` показывает его целиком.

```bash
$ nm -u suspicious.ko
U __fentry__
U kallsyms_lookup_name
U register_kprobe
U unregister_kprobe
```

Каждый `U`-символ — потенциальная зацепка. `kallsyms_lookup_name` часто используют, чтобы найти адрес внутренней функции ядра, которую нельзя импортировать напрямую.

## Шаг 14: kprobe в коде пошагово

Регистрация kprobe выглядит так:

```c
static struct kprobe kp = { .symbol_name = "sys_getdents64" };
static int handler_pre(struct kprobe *p, struct pt_regs *regs) { ... }
static int __init init(void) {
    kp.pre_handler = handler_pre;
    return register_kprobe(&kp);
}
```

В дизассемблере: заполняется структура (в неё пишется указатель на `handler_pre` и строка символа), затем вызов `register_kprobe`. Найди строку символа рядом с обработчиком — узнаешь, что перехватывается.

## Шаг 15: почему ядро борется с этим

Ядро постепенно закрывает такие возможности: `kallsyms_lookup_name` перестали экспортировать, `sys_call_table` защитили, а модули обязаны иметь подпись (при включённой проверке). Поэтому современные руткиты идут через:

- **ftrace** — легальный механизм трассировки, трудно отличим от отладки;
- **eBPF** — загрузка программ через штатный интерфейс;
- **злоупотребление легитимным драйвером** (BYOVD — bring your own vulnerable driver).

Понимание этих путей — часть реверса модулей.

## Шаг 16: таблица: что где искать

| Признак | Секция/символ | Вывод |
|---|---|---|
| `register_kprobe` | undefined symbol | перехват функции ядра |
| `ftrace_set_filter` | undefined symbol | ftrace-хук |
| `kallsyms_lookup_name` | undefined symbol | поиск внутренних адресов |
| `sys_call_table` | `.rodata`/строка | патч таблицы syscall |
| `bpf_prog_load` | undefined symbol | eBPF-программа |
| `set_memory_rw` | undefined symbol | снятие защиты памяти |

## Шаг 17: итоговый порядок разбора

Сначала `modinfo` и `readelf -p .modinfo` — метаданные. Затем `nm -u` — цели вызовов. Потом `objdump -d` по `.init.text` — регистрация хуков. Сопоставь найденные механизмы с таблицей выше. Если видишь kprobe/ftrace — это перехват; если `sys_call_table`/eBPF — это руткит. Разбирай статически, грузи только в снапшоте ВМ. Главное: **список импортов модуля говорит, что он перехватывает**.

## Шаг 18: сравнение с эталонным модулем

Самый быстрый способ понять, что добавлено в модуль, — **diff с легитимной версией**. Если у тебя есть оригинальный `.ko` того же продукта, сравни секции `.text` и списки импортов:

```bash
$ diff <(nm -u legit.ko | sort) <(nm -u suspicious.ko | sort)
> kallsyms_lookup_name
> register_kprobe
```

Лишние импорты сразу показывают, что подмешали. Если эталона нет, сравнивай с «типичным» модулем той же подсистемы: аномальные импорты kprobe/ftrace на фоне обычного сетевого драйвера — сигнал.

Это тот же принцип memory-vs-disk diff, что и в Windows: **отклонение от нормы важнее абсолютного анализа**.

## Куда дальше

Linux-модули — один низкоуровневый слой. У Apple свой аналог — kext/dext, с иной моделью и подписью. О них в следующем уроке. Пока главное: **модуль ядра — это импорт символов ядра, и по нему видно, что он перехватывает**.

## Где пригодится

- **Kernel security:** аудит модулей и поиск руткитов.
- **Malware analysis:** разбор Linux-имплантов уровня ядра.
- **Rootkit research:** понимание kprobe/ftrace-сокрытия.
