## Вопрос, с которого всё начинается

Мы прочитали ассемблер `check_password` и увидели, что секрет лежит по адресу `0x2008`. Но
откуда этот адрес взялся и что вообще находится в разных местах файла? Операционная система
не может просто «запустить байты» — ей нужно знать, какой это формат, под какой процессор,
где начинается код и что загружать в память.

За это отвечает **формат исполняемого файла**. В этом уроке разберём, как файл устроен изнутри,
на примере всё того же `crackme`.

## Наш пример

Будем смотреть `crackme` — обычный Linux-бинарник. Главный инструмент — `readelf` из binutils,
он печатает структуры ELF (формат Linux). Начнём с общей команды `file`, которую уже видели:

```bash
$ file crackme
crackme: ELF 64-bit LSB pie executable, x86-64, version 1 (SYSV),
dynamically linked, interpreter /lib64/ld-linux-x86-64.so.2, not stripped
```

Строка «ELF 64-bit LSB x86-64» — это краткая выжимка из заголовка, который мы сейчас
посмотрим целиком.

## Шаг 1: заголовок — паспорт файла

Заголовок ELF лежит в самом начале файла. Команда `readelf -h` («header») его печатает:

```bash
$ readelf -h crackme
ELF Header:
  Magic:   7f 45 4c 46 02 01 01 00 00 00 00 00 00 00 00 00
  Class:                             ELF64
  Data:                              2's complement, little endian
  OS/ABI:                            UNIX - System V
  Type:                              DYN (Position-Independent Executable file)
  Machine:                           Advanced Micro Devices X86-64
  Entry point address:               0x1080
  Start of program headers:          64 (bytes into file)
  Start of section headers:          14224 (bytes into file)
  Number of program headers:         14
  Number of section headers:         30
  Section header string table index: 29
```

Разберём ключевые поля — каждое из них отвечает на свой вопрос.

## Шаг 2: Magic — «как программа узнаёт, что это ELF»

Первое поле, **Magic** — первые байты файла: `7f 45 4c 46`. Это литерально символы `\x7f E L F`.
По ним ядро и `file` определяют формат, не читая ничего дальше. Следующие байты кодируют
разрядность (`02` = 64 бита), порядок байт (`01` = little-endian) и версию.

Смысл простой: **формат опознаётся по магии в первых байтах**. У PE (Windows) магия — `MZ`
(`4d 5a`), у Mach-O (macOS) — `cafebabe`/`feedface`. Это первое, что стоит посмотреть, если
файл «не запускается».

## Шаг 3: Type и Entry point — как файл запускается

Поле **Type: DYN (Position-Independent Executable)** объясняет `pie` из вывода `file`. DYN —
«позиционно-независимый»: грузится по случайному адресу. Бывают ещё `EXEC` (обычный
исполняемый, фиксированный адрес) и `REL` (объектный файл, ещё не слинкован).

**Machine: Advanced Micro Devices X86-64** — набор инструкций. Будь это ARM, `objdump` печатал
бы совсем другой ассемблер.

**Entry point address: 0x1080** — адрес, с которого ядро передаёт управление. Это не `main`!
По этому адресу лежит код `_start`, который готовит окружение и лишь потом вызывает `main`.
Так устроены все нормальные программы.

И два «указателя»: **Start of program headers: 64** и **Start of section headers: 14224**.
По этим смещениям в файле лежат две таблицы — о них дальше.

## Шаг 4: секции и сегменты — две карты одного файла

В ELF есть **две** структуры, описывающие содержимое, и новички их путают:

- **Секции** (sections) — для линкера и инструментов анализа. Мелкое деление: код, строки,
  символы. Список — `readelf -S`.
- **Сегменты** (segments, они же program headers) — для загрузчика в память. Грубое деление
  по правам доступа. Список — `readelf -l`.

Посмотрим список секций (обрезано до важных):

```bash
$ readelf -S crackme | grep -E 'Name|\.text|\.rodata|\.data|\.bss|\.plt'
  [Nr] Name              Type             Address           Offset
  [11] .plt              PROGBITS         0000000000001020  00001020
  [12] .text             PROGBITS         0000000000001080  00001080
  [14] .rodata           PROGBITS         0000000000002000  00002000
  [24] .data             PROGBITS         0000000000004028  00003028
  [25] .bss              NOBITS           0000000000004038  00003038
```

Читаем по имени:

- **.text** — машинный код (там наши `main` и `check_password`).
- **.rodata** — константы только для чтения. Адрес `0x2000`, а наш секрет был по `0x2008` —
  значит, он прямо здесь, в `.rodata`!
- **.plt** — таблица переходов к внешним функциям (`strcmp`, `printf`).
- **.data / .bss** — глобальные переменные: инициализированные / нулевые.

Теперь сегменты (`readelf -l`), уже по правам доступа:

```bash
$ readelf -l crackme | sed -n '/Program Headers/,/GNU_RELRO/p'
  Type           Offset             VirtAddr           Flags
  LOAD           0x0000000000000000 0x0000000000000000  R
  LOAD           0x0000000000001000 0x0000000000001000  R E
  LOAD           0x0000000000002000 0x0000000000002000  R
  LOAD           0x0000000000002dd0 0x0000000000003dd0  RW
  GNU_STACK      0x0000000000000000 0x0000000000000000  RW
  GNU_RELRO      0x0000000000002dd0 0x0000000000003dd0  R
```

Флаг `R E` означает «read + execute» — это исполняемый сегмент с кодом. `RW` — данные, куда
можно писать. `GNU_STACK ... RW` — стек неисполняемый (та самая защита NX). Права сегментов
важны для pwn, а для реверса из них следует: код читается, данные можно менять.

Проверим, что секрет правда в `.rodata`, дампом байт (`-x`):

```bash
$ readelf -x .rodata crackme
  0x00002000 01000200 00000000 68756e74 65723200 ........hunter2.
  0x00002010 456e7465 72207061 7373776f 7264 3a20 Enter password:
  0x00002020 00000000 00000000 436f7272 65637421 ........Correct!
  0x00002030 20666c61 677b7265 765f6261 73696373  flag{rev_basics
  0x00002040 5f31735f 66756e7d 0057726f 6e672e00 _1s_fun}.Wrong..
```

Справа — ASCII: видим `hunter2`, `Enter password:`, `flag{rev_basics_1s_fun}`. Слева — те же
байты в hex. То, что `strings` показал текстом, `readelf -x` показывает по адресам.

## Шаг 5: а Windows и macOS?

Формат зависит от ОС, но идея одна: **заголовок → таблица разделов → данные**.

| | Linux (ELF) | Windows (PE) | macOS (Mach-O) |
|---|---|---|---|
| Магия | `7f 45 4c 46` | `4d 5a` (MZ) | `cf fa ed fe` |
| Код | `.text` | `.text` | `__TEXT,__text` |
| Строки | `.rodata` | `.rdata` | `__TEXT,__cstring` |
| Импорты | `.plt`/`.got`, `.dynsym` | Import Table (`IAT`) | `__LINKEDIT`, dyld |
| Разбор | `readelf`, `objdump` | `objdump`, PE-bear, CFF Explorer | `otool`, `lief`, Hopper |

Инструменты разные, но логика «найди заголовок, потом разделы, потом данные» переносится
один в один. Библиотека `lief` умеет читать все три формата из Python.

## Что мы теперь знаем

- **Заголовок** — паспорт файла: магия, архитектура, тип, точка входа.
- **Магия** в первых байтах (`7f ELF`, `MZ`, `feedface`) определяет формат.
- **Entry point** — не `main`, а точка входа `_start`.
- **Секции** — мелкая карта для анализа; **сегменты** — грубая карта для загрузки (по правам).
- Секрет лежит в **.rodata** по адресу `0x2008`; `readelf -x` показывает её байтами.
- У PE и Mach-O та же схема с другими именами.

## Куда дальше

Мы знаем, что файл делится на секции и сегменты. Но как именно они превращаются в карту
памяти процесса — какие права, как выравниваются, где RELRO? Этому посвящён следующий урок
про **секции и сегменты**. А пока главное запомни: `readelf -h` — заголовок, `-S` — секции,
`-l` — сегменты, `-x` — байты конкретной секции.

## Где пригодится

- **CTF Reversing:** понимание, где искать строки и код, ускоряет любую задачу.
- **Malware analysis:** аномальные секции (пакеры, шифрованные данные) выдаются сразу.
- **Pwn:** права сегментов и RELRO напрямую влияют на эксплойт.
- **Кроссплатформенный анализ:** те же шаги для PE (`MZ`) и Mach-O (`feedface`).
- **Собес:** «что такое секция vs сегмент», «где хранятся строки» — базовые вопросы.
