Многие бинарники активно сопротивляются анализу: они проверяют, не запущены ли они под отладчиком,
не находятся ли в виртуальной машине или песочнице, и меняют поведение (или завершаются) при
обнаружении. Для реверс-инженера это не тупик, а задача: распознать проверку, понять её логику и
нейтрализовать. Этот урок систематизирует приёмы анти-анализа и методы их обхода.

## Категории анти-анализа

Проверки делят на несколько групп:

- **Анти-отладка**: обнаружение отладчика (флаги, `ptrace`, тайминги, точки останова).
- **Анти-VM**: обнаружение гипервизора (артефакты VMware/VirtualBox/Hyper-V, CPUID, устройства).
- **Анти-песочница**: обнаружение изолированной среды анализа (файлы-ловушки, отсутствие
  пользовательской активности, ограниченные ресурсы, «сухие» данные).
- **Анти-дамп**: запрет снятия образа из памяти (искажение заголовков, проверка целостности).
- **Анти-патч**: обнаружение изменений кода (контрольные суммы, self-hash).

Практически все они сводятся к «проверке условия» и «ветвлению»: если условие истинно — выход или
подмена поведения. Значит, обход — это либо изменение условия, либо маскировка среды, чтобы условие
стало ложным.

Ключевая методологическая мысль: не нужно нейтрализовать все проверки. Достаточно найти ту, которая
блокирует прогресс, и обойти её. Часто проверки избыточны и дублируют друг друга; обход одной
снимает блок. Начинайте с трассировки (какие API вызываются, какие файлы читаются), составьте
список проверок, затем выберите самую простую для обхода. Излишнее «отключение всего» повышает
риск сломать логику и сработать на анти-тампер.

## Анти-отладка на уровне API

Классика Windows: `IsDebuggerPresent()` читает `PEB->BeingDebugged`; `CheckRemoteDebuggerPresent()`
проверяет другой процесс; `NtQueryInformationProcess` с классом `ProcessDebugPort`/`ProcessDebugFlags`
даёт более тонкие признаки. В Linux аналог — `ptrace(PTRACE_TRACEME)`: если процесс уже отлаживается,
вызов вернёт ошибку; программа проверяет результат и завершается. Также читают `/proc/self/status`
поле `TracerPid`: если оно не ноль — есть отладчик.

Простейший обход — патч. Для `IsDebuggerPresent` достаточно заменить её тело на `xor eax, eax; ret`
в памяти (или через хук). Для `ptrace` — перехватить вызов и вернуть `0`, либо пропатчить ветку.
Для `TracerPid` — перехватить чтение файла и подменить содержимое.

## Анти-отладка через тайминги и структуры

Более изощрённые методы:

- **`rdtsc`-тайминги**: измеряют время между инструкциями; под отладчиком оно аномально велико.
  Обход — ускорить трассировку, отключить «медленные» точки, или пропатчить проверку.
- **`int3`-детект**: программа ставит `int3` и проверяет, перехватил ли его отладчик; либо сканирует
  свой код на наличие байтов `0xCC` (наши программные breakpoints).
- **Детект аппаратных точек**: чтение `DR0`–`DR7` через контекст потока.
- **Проверка `BeingDebugged` в PEB** напрямую (`fs:[0x30]`/`gs:[0x60]`), без вызова API.
- **`CloseHandle` с невалидным дескриптором + обработка исключения**: под отладчиком исключение
  обрабатывается иначе.

Обход: ScyllaHide перехватывает `NtQueryInformationProcess`, `GetThreadContext`, читает PEB и
подменяет флаги; это автоматизирует большинство проверок. Для нестандартных — ручной патч.

## Анти-VM и детект песочниц

Анти-VM проверяет артефакты гипервизора: строки `VMware`, `VBOX`, `VirtualBox` в
реестре/устройствах/`MAC`-адресах, `CPUID` с гипервизорным битом, наличие драйверов (`vmmouse.sys`),
специфичные `I/O`-порты. Анти-песочница идёт дальше: проверяет имя пользователя (`sandbox`, `vm`),
объём RAM/диска, число ядер, отсутствие документов на рабочем столе, наличие инструментов анализа
(`wireshark.exe`, `procmon.exe`, `ollydbg.exe`), время работы системы (мало — «свежая» песочница),
задержки сна (`Sleep` дольше, чем в реальной среде).

Обход: настроить среду так, чтобы она выглядела «обычной» — переименовать пользователя, добавить
файлы, увеличить ресурсы, скрыть драйверы и процессы анализа, отключить гостевые дополнения.
Специализированные инструменты (например, `VBoxHardenedLoader`, `pafish` для проверки) помогают
эмулировать «чистую» машину.

## Обход: патчинг

Прямолинейный путь — найти проверку и изменить её результат. Приёмы:

- **NOP-out ветвление**: заменить `jz`/`jnz` на `nop`, чтобы оба пути вели в «нормальное» поведение.
- **Инверсия ветки**: `jz` → `jnz`.
- **Подмена возвращаемого значения**: заставить функцию вернуть ожидаемое значение.
- **Патч тела API**: заменить `IsDebuggerPresent` на `xor eax,eax; ret`.

Патчинг удобен, но проверки целостности и анти-патч могут его обнаружить. Тогда патчат данные
(например, флаг в памяти после проверки) или используют условные breakpoints, которые меняют
регистр перед продолжением, не трогая код.

## Обход: хуки и плагины

Более гибкий путь — перехват. На Windows: ScyllaHide, TitanHide (ядерный), `x64dbg`-плагины. На
Linux: `LD_PRELOAD` с перехватом `ptrace`, чтения `/proc/self/status`, `clock_gettime`. В отладчике
ставят условный breakpoint на проверку с командой, меняющей результат: например, breakpoint на
`ptrace` с командой `set $rax=0; continue`. Это оставляет код неизменным — проверка целостности
не срабатывает.

Для `TracerPid` можно подменить файл через FUSE или перехватить `open`/`read`. Для `rdtsc` —
патчить обработчик или использовать эмуляцию.

## Практический разбор

Пример на Linux: бинарник вызывает `ptrace(PTRACE_TRACEME, 0, 0, 0)` и завершается, если результат
`-1`. Под gdb:

```
$ gdb ./anti
(gdb) break ptrace
(gdb) run
Breakpoint 1, ptrace () at ...
(gdb) finish
Value returned is $1 = -1
(gdb) set $rax = 0        # эмулируем успех
(gdb) continue
Program continues normally
```

Здесь мы перехватили `ptrace` и подменили результат, не меняя код. Аналогично для
`IsDebuggerPresent` в x64dbg: breakpoint на функции, `set eax=0`, continue. Для автоматизации
используйте ScyllaHide — он делает это прозрачно.

Другой пример: `rdtsc`-проверка. Находим две инструкции `rdtsc`, считаем разницу, сравниваем с
порогом. Патчим порог (увеличиваем) или заменяем `rdtsc` на константу. В x64dbg — breakpoint на
месте сравнения и ручное изменение регистра.

## Анти-дамп и как его обойти

Отдельная категория — защита от снятия образа из памяти. Приёмы: искажение заголовка PE/ELF после
загрузки (размер секции обнуляется, точка входа портится), удаление или шифрование таблицы импорта,
разбиение образа на страницы с разными правами, проверка на наличие инструментов дампа в процессе.
Цель — сделать так, чтобы снятый образ нельзя было корректно открыть или запустить.

Обход: снимать дамп до срабатывания анти-дампа (сразу после распаковки), восстанавливать заголовки
вручную (по оригинальному файлу на диске), использовать аппаратные средства и инструменты, которые
«доклеивают» секции (Scylla). Иногда помогает отключить конкретную проверку в памяти, не трогая
файл. Для ELF анти-дамп встречается реже, но бывает в кастомных упаковщиках.

## Анти-анализ в мобильных приложениях

В Android/iOS анти-анализ особенно популярен. Android-проверки: наличие `su`-бинарника, `ro.debuggable`,
проверка подписи APK, детект Frida (по имени процесса `frida-server`, по открытым портам 27042, по
сканированию памяти на строки `frida`), `ptrace`-защита, проверка `Build.TAGS`. iOS-проверки:
обнаружение jailbreak (файлы `/Applications/Cydia.app`, `/bin/bash`), детект Frida (`frida-cycript`,
порт 27042), проверка подписи и целостности.

Обход: на Android — Magisk/Zygisk со скрытием root, переименование `frida-server` и смена порта,
хуки через Frida на нативные функции проверки, патч smali. На iOS — `Liberty Lite`/`A-Bypass`,
скрытие jailbreak, переименование Frida, переподпись. Многие проверки реализованы на нативном слое
(`.so`/`.dylib`), поэтому хуки ставятся на нативные функции.

## Практические рецепты для типовых проверок

| Проверка | Обход |
|---|---|
| `IsDebuggerPresent` | `set eax=0` / патч тела |
| `ptrace(PTRACE_TRACEME)` | вернуть 0 |
| `/proc/self/status` TracerPid | подменить чтение файла |
| `rdtsc` тайминг | увеличить порог / патч |
| Детект `int3` в коде | не ставить программные BP |
| Чтение `DR`-регистров | TitanHide / ядерное скрытие |
| CPUID гипервизора | настроить ВМ / скрыть артефакты |
| Файлы-ловушки песочницы | удалить/переименовать |
| Детект Frida | переименовать, сменить порт, хуки |

Систематический подход: сначала определите, какие проверки есть (трассируйте вызовы API, ищите
строки, используйте `al-khaser` как эталон), затем выберите метод — патч, хук или маскировка среды.

## Подводные камни

Первое: не все проверки лежат в начале — некоторые срабатывают позже или по таймеру. Второе:
патчинг кода может вызвать анти-патч (проверку контрольной суммы). Третье: ScyllaHide иногда сам
детектируется продвинутыми проверками. Четвёртое: подмена времени/таймингов может сломать логику.
Пятое: анти-VM проверки могут быть в нескольких местах; обход одной не помогает. Шестое: в CTF
проверка может быть намеренно простой — не переусложняйте. Седьмое: некоторые проверки специально
сделаны так, чтобы их «обход» приводил в тупик (ложная ветка с фейковым флагом) — проверяйте
результат. Восьмое: отладчик может влиять на поведение самим фактом подключения (перехват
исключений, тайминги) — иногда проще пропатчить файл и запустить без отладчика.

## Что дальше / решение

Практика: возьмите `al-khaser` (набор анти-анализ проверок) и попробуйте пройти его под ScyllaHide.
Напишите `LD_PRELOAD`-хук, перехватывающий `ptrace` и возвращающий `0`. Разберите бинарник с
`rdtsc`-проверкой и обойдите её. Далее — `reversing-integrity-checks` (анти-патч и self-hash) и
`reversing-anti-tamper`.
