## Вопрос, с которого всё начинается

Ты запускаешь программу под отладчиком — и она тут же делает вид, что «ничего не
происходит»: печатает неверный результат, выходит или просто молчит. На свободе
же работает нормально. Значит, внутри есть **анти-отладка** — код, который
определяет, что его изучают, и меняет поведение. Как такие защиты устроены и как
их обходить? Разберём на двух маленьких примерах.

## Наш пример

Первая программа — `adbg` — проверяет, не отлаживают ли её:

```
$ cat adbg.c
int main(void){
    if (ptrace(0,0,0,0) == -1) { printf("debugger detected\n"); return 1; }
    printf("normal run\n");
    return 0;
}
$ ./adbg
normal run
$ gdb -q ./adbg
(gdb) run
debugger detected
[Inferior 1 (process 535569) exited with code 01]
```

В обычном запуске — `normal run`, под отладчиком — `debugger detected`. Вторая
программа — `antivm` — проверяет, не работает ли она внутри виртуальной машины:

```
$ ./antivm
CPUID.1: hypervisor bit ecx[31] = 0
CPUID.40000000 vendor =
```

Обе защиты нужно понять и снять.

## Шаг 1: как работает ptrace-проверка

`ptrace` — системный вызов, которым отладчик управляет процессом. Вызов
`ptrace(0,0,0,0)` с первым аргументом 0 — это запрос `PTRACE_TRACEME`:
«возьми меня под трассировку». **У процесса может быть только один
трассировщик**: если отладчик уже трассирует, второй запрос провалится и вернёт
`-1`. Именно это и проверяет программа.

Посмотрим код в дизассемблере:

```
$ objdump -d -M intel adbg | sed -n '/<main>:/,/ret/p'
  40114e: call   401040 <ptrace@plt>
  401153: cmp    rax,0xffffffffffffffff
  401157: jne    40116a <main+0x34>
  401159: mov    edi,0x402004        ; "debugger detected"
  40115e: call   401030 <puts@plt>
  ...
  40116a: mov    edi,0x402016        ; "normal run"
```

Логика читается как книга: вызвали `ptrace`, сравнили результат с `-1`
(`0xffff...ff`), и если результат **не** `-1` (`jne`), прыгнули на «normal run».
Иначе идём на «debugger detected».

## Шаг 2: обходим патчем — `jne` в `jmp`

Самый простой обход — заставить программу всегда идти по «хорошей» ветке.
Условный переход `jne` (байт `0x75`) заменим на безусловный `jmp` (байт `0xeb`).
Смещение (второй байт, `0x11`) оставим — прыгаем туда же, но всегда.

Найдём файловое смещение для виртуального адреса `0x401157` и поменяем байт:

```python
import lief
b = lief.parse("adbg_patched")
off = b.virtual_address_to_offset(0x401157)   # -> 0x1157
with open("adbg_patched","r+b") as f:
    f.seek(off); f.write(bytes([0xeb]))       # jne -> jmp
```

Проверяем под отладчиком:

```
$ gdb -q ./adbg_patched
(gdb) run
normal run
[Inferior 1 (process 549810) exited normally]
```

Защита снята: теперь даже под gdb программа считает, что отладчика нет. Байт
`0x75` действительно поменялся на `0xeb` (проверяется `xxd` по смещению).

## Шаг 3: обход без правки файла — хук ptrace

Патчить файл не всегда удобно (проверки целостности заметят). Альтернатива —
перехватить сам вызов `ptrace` и заставить его вернуть «правильное» значение.
В gdb это делают так:

```
(gdb) break ptrace
(gdb) commands
> return (long)0
> continue
> end
```

Теперь при каждом вызове `ptrace` отладчик немедленно возвращает 0 — и проверка
«== -1» никогда не срабатывает. Под Windows аналог — плагин **ScyllaHide**,
который прячет отладчик от `IsDebuggerPresent`, `NtQueryInformationProcess` и
множества других API разом.

## Шаг 4: анти-VM через CPUID

Вторая защита — проверка виртуальной машины. Инструкция `cpuid` возвращает
сведения о процессоре. Признаки виртуализации:

- **бит 31 регистра `ecx` при листе 1** — «hypervisor present»;
- **строка-вендор при листе `0x40000000`** — например, `VMwareVMware`,
  `KVMKVMKVM`, `Microsoft Hv`.

Программа печатает оба признака. В нашем запуске оба нулевые — значит, мы на
«железе»:

```
$ ./antivm
CPUID.1: hypervisor bit ecx[31] = 0
CPUID.40000000 vendor =
```

Анти-VM-проверки обычно смотрят и на другое: артефакты в реестре, имена
устройств, MAC-адрес, тайминги `rdtsc`. Обход — «замаскировать» среду: в
гипервизоре включают **скрытие CPUID** (`hypervisor=off` в KVM, `cpuid.*.ecx=...`
в VMware), убирают артефакты, выравнивают тайминги. В песочницах для малвари то
же делают патчи, хуки и подмена значений CPUID.

## Шаг 5: тайминги и другие каналы

Помимо ptrace и CPUID, распространены:

- **Тайминг-проверки.** Программа меряет время между двумя точками. Под
  отладчиком оно аномально велико. Обход — «выравнивать» время или ускорить
  проход (в gdb — `set pagination off`, аппаратные точки вместо `0xCC`).
- **Проверка флагов.** `IsDebuggerPresent`, `NtGlobalFlag` в PEB.
- **Поиск отладочных окон/процессов** (`FindWindow("OLLYDBG")`).
- **Аппаратные точки vs `0xCC`.** Обычный breakpoint вставляет байт `0xCC` в
  код — проверка целостности это увидит. Аппаратные точки код не трогают.

Общий принцип обхода: **найти точку принятия решения** (условный переход после
проверки) и либо переписать условие, либо перехватить источник данных.

## Шаг 6: методология, а не заклинания

Защит много, и заучивать каждую бесполезно. Рабочий порядок:

1. Запусти под отладчиком, найди **строку-маркер** («debugger detected», «VM»).
2. Поставь точку на неё и посмотри **стек** — откуда её позвали.
3. В вызывающем коде найди **условный переход**, который выбирает ветку.
4. Реши: патчить байт, хукать API или маскировать среду.

Именно этот путь (маркер → стек → переход → обход) работает для любой
анти-анализ-защиты, а не набор готовых трюков.

Покажем шаги 1–2 на нашем `adbg` вживую. Найти строку-маркер можно прямо в gdb:
адрес `0x402004` мы уже видели в дизассемблере. Ставим точку на вызов `puts` и
смотрим, откуда пришли:

```
(gdb) break *0x40115e
(gdb) run
Breakpoint 1, 0x000000000040115e in main ()
(gdb) x/s 0x402004
0x402004:	"debugger detected"
(gdb) bt
#0  0x000000000040115e in main ()
```

Мы подтвердили, что это именно та ветка. Теперь шаг 3: `x/8i $pc-20` покажет
инструкции перед вызовом — там и окажется `cmp rax, -1` и `jne`. Осталось
применить обход из шага 2. Такой микроразбор занимает минуту и не требует
держать в голове конкретные адреса: строку нашли — к переходу пришли.

## Частые вопросы

**Патч не помог — программа всё равно падает.** Значит, проверок несколько, или
есть проверка целостности кода (следующий урок). Ищи другие ветки с маркерами.

**Отладчик не останавливается на точке.** Возможно, код самомодифицирующийся:
байт `0xCC` перезаписан. Используй аппаратные точки (`hbreak`).

**Под Wine/эмуляцией анти-VM срабатывает ложно.** Убирай артефакты окружения
(имена устройств, записи реестра) — то же, что делают песочницы.

## Что мы теперь знаем

- Анти-отладка ловит отладчик через `ptrace`, `IsDebuggerPresent`, тайминги и
  проверки `0xCC`.
- Простейший обход — заменить условный переход (`jne`) на безусловный (`jmp`):
  байт `0x75` → `0xeb`.
- Альтернатива — перехватить источник: хук `ptrace` (gdb) или ScyllaHide
  (Windows).
- Анти-VM смотрит на CPUID (hypervisor-бит, вендор), реестр, MAC и тайминги;
  обход — скрыть признаки виртуализации.
- Работает методология «маркер → стек → переход → обход», а не список трюков.

анти-патч**: как программа обнаруживает, что её код изменили, и почему простой
