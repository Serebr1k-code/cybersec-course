## Вопрос, с которого всё начинается

Фаззеру нужно понимать **покрытие**: какие участки программы он уже «прошёл», чтобы мутировать вход в сторону новых веток. Обычный способ — инструментировать код (AFL вставляет счётчики на этапе компиляции). Но что, если исходников нет? Или если образец **сопротивляется** инструментации — malware, который детектирует DBI и отладчики?

Решение — измерять покрытие **аппаратно**, на уровне процессора. Так работают **Intel PT** и **ARM CoreSight ETM**: они записывают поток управления, не изменяя код и почти не замедляя программу. В прошлом уроке мы разобрали сам PT; теперь сравним его с ARM-аналогом и посмотрим, как это применяют для покрытия и анализа malware.

## Наш пример

Возьмём `tiny` с функцией `compute(6)`:

```c
int add(int a, int b) { return a + b; }
int compute(int x) {
    int acc = 0;
    for (int i = 0; i < x; i++) {
        if (i % 2) acc = add(acc, i);
        else       acc += 2 * i;
    }
    return acc;
}
```

Наша цель — собрать **покрытие**: список уникальных адресов, которые реально исполнились.

## Что такое аппаратная трассировка

Аппаратный трассировщик пишет компактный поток пакетов, из которого восстанавливается последовательность исполненных адресов. Intel PT кодирует переходы дельтами: записываются только «непредсказуемые» ветвления (косвенные переходы, возвраты, прерывания), а предсказуемые декодер восстанавливает по бинарнику. Это даёт очень компактные трассы (мегабайты на минуты исполнения) при замедлении всего в 2–5 %.

Вывод PT пишется в память через **ToPA** (Table of Physical Addresses) — структуру регионов вывода. Каждый регион имеет базовый адрес, размер и флаг `STOP`; когда буфер заполняется, трассировщик переходит к следующему, а по флагу `INT` генерирует прерывание — драйвер успевает выгрузить данные. Фильтры ограничивают объём: **IP-фильтр** (`IA32_RTIT_ADDR0/1`) трассирует только диапазон адресов, **CR3-фильтр** — только конкретный процесс.

## ARM CoreSight ETM

На ARM трассировка называется **CoreSight**, а компонент, пишущий поток управления — **ETM** (Embedded Trace Macrocell). Данные выводятся через ETB (встроенный буфер) или TPIU (внешний порт). Включается через CoreSight-регистры (`ETMCR`, `ETMTRACEIDR`) или инструменты OpenCSD, декодируется библиотекой **OpenCSD**:

```
# на ARM64 Linux
$ perf record -e cs_etm/@tmc_etr0/ -o etm.data -- ./target
$ perf script -i etm.data --itrace=i1000 -F ip,sym
```

Для embedded (без Linux) используют аппаратные пробники (Lauterbach, J-Link) и OpenOCD. ETM, как и PT, даёт только поток адресов — без данных.

## Проверяем поддержку и собираем покрытие

Убедимся, что PT есть на нашей машине:

```
$ grep -o -m1 'pt' /proc/cpuinfo
pt
$ cat /sys/bus/event_source/devices/intel_pt/type
12
$ ls /sys/bus/event_source/devices/intel_pt/caps/
cr3_filtering  ip_filtering  mtc  num_address_ranges  ptwrite  topa_multiple_entries
```

Флаг `pt` — поддержка процессором, каталог `intel_pt` с типом `12` — регистрация события ядром. Но `perf` на стенде не установлен, поэтому соберём покрытие ближайшим доступным способом: трассировкой через `unicorn` с дедупликацией адресов (тот же принцип — множество исполненных адресов):

```
$ python3 ucov.py tiny 0x401014 6
unique addresses: 37
0x401014
0x401015
0x401018
...
0x401061
0x401064
0x401065
```

37 уникальных адресов — это и есть покрытие функции `compute` для входа `6`. В реальном фаззере эти адреса хешируют в битмап и сравнивают между запусками: новый адрес = интересный вход.

## Применение: покрытие в фаззинге

Аппаратная трассировка идеальна для покрытия, потому что не требует инструментации кода (работает с «чёрным ящиком») и даёт точные адреса блоков. Схема: фаззер запускает цель под PT, собирает трассу, декодирует адреса базовых блоков, хеширует в битмап и сравнивает с предыдущим — новое покрытие сигнализирует об интересном входе. Инструменты: `honggfuzz` (поддержка Intel PT), `kAFL` (PT-based kernel fuzzer), AFL++ с PT-режимами. Преимущество — нет оверхеда DBI и устойчивость к анти-инструментации.

## Применение: анализ malware и посмертный анализ

Malware часто детектирует отладчики и DBI, но аппаратная трассировка для него незаметна (не меняет процесс). Запускаем образец под PT в изолированной ВМ, собираем трассу, декодируем, находим адреса расшифровки/распаковки и переход на оригинальную точку входа. PT используют и для **посмертного анализа**: при краше сохраняют трассу и восстанавливают, что привело к падению (ценно для триажа и эксплойт-разработки). TSC-метки позволяют измерять тайминги и находить крипто-операции по времени.

## Сравнение PT, ETM и DBI

| Свойство | Intel PT | ARM ETM | DBI (PIN/QBDI) |
|---|---|---|---|
| Данные | только поток управления | только поток управления | регистры и память |
| Оверхед | 2–5 % | 2–5 % | 5–100× |
| Модификация кода | нет | нет | да (JIT) |
| Требования | CPU/ОС/права | CoreSight | библиотека |
| Применение | coverage, посмертный анализ | embedded, coverage | taint, деобфускация |

PT/ETM идеальны для покрытия и анализа «чёрного ящика», DBI — для глубокой инструментации. На практике их комбинируют: PT собирает поток, DBI уточняет данные на интересных участках.

## Если не сработало

Пустая трасса обычно означает, что PT не включён в BIOS/ядре, не хватает прав или фильтр слишком узкий. Обрезанная трасса — переполнение ToPA без своевременной выгрузки: увеличьте буферы и поставьте флаг `INT`. Если адреса не совпадают — взят не тот бинарь или не учтена база ASLR: используйте тот же образ и пересчитайте адреса. Пропущенные блоки возникают на самомодифицирующемся коде, где декодер не может предсказать условный переход, — трасса теряет синхронизацию до следующего пакета `PSB`. Без CR3-фильтра в трассе смешаются несколько процессов, а в виртуальной машине PT может быть недоступен вовсе.

## Что мы теперь знаем

- **Аппаратная трассировка** пишет поток управления без модификации кода и почти без замедления.
- **Intel PT** использует пакеты TNT/TIP и буфер **ToPA**; **ARM ETM** — часть CoreSight, декодируется OpenCSD.
- Поддержку PT видно по флагу `pt` и каталогу `/sys/bus/event_source/devices/intel_pt/`.
- Покрытие собирают как множество исполненных адресов; их хешируют в битмап для фаззинга.
- PT/ETM дают только поток управления; для данных их комбинируют с DBI.

## Почему аппаратная трассировка не оставляет следов

Программные инструменты (DBI, отладчики) **меняют** процесс: вставляют код, ставят breakpoint'ы, замедляют исполнение. Программа может это заметить и повести себя иначе — анти-анализ сработает, и вы увидите не то поведение, что «в бою». **Аппаратная трассировка** решает эту проблему: процессор сам пишет компактный лог переходов (Intel PT) или детальную трассу исполнения (ARM ETM), почти не влияя на скорость программы.

Intel PT (Processor Trace) записывает поток управления в сжатом виде: какие ветвления были взяты, куда шли переходы. Программа не знает, что её трассируют, и работает почти с обычной скоростью. Декодер (`perf`, `libipt`, `ptxed`) восстанавливает из лога полную трассу исполнения и покрытие кода. ARM CoreSight ETM работает похоже на ARM-платформах, часто через отладочный интерфейс (JTAG/SWD) и внешний трассировочный модуль.

Применения: **покрытие в фаззинге** (какие пути достигнуты), **анализ malware** (поведение без анти-анализ-помех), **посмертный анализ** (что делала программа до краха). Ограничение — доступность железа: PT есть не на всех CPU, ETM требует отладочного порта, а трассы надо декодировать и хранить (объём большой). В учебном окружении без PT-железа трассировку можно получить только через DBI или симуляцию — это важно понимать, чтобы не искать несуществующий «perf intel-pt» на виртуалке.

## Частые вопросы

**Чем PT отличается от ETM?** Intel PT — для x86 (компактный лог ветвлений, декодер libipt), ARM ETM — для ARM (детальная трасса, часто через CoreSight/JTAG).

**Почему PT «невидим» для программы?** Он пишет в буфер на уровне CPU, не вставляя код и не останавливая процесс; накладные расходы минимальны.

**Почему это не работает на виртуалке?** PT/ETM — аппаратные возможности; в гостевой ВМ их либо нет, либо они не пробрасываются. Нужен физический хост с поддержкой.

**Что даёт покрытие в фаззинге?** Оно показывает, какие ветви кода достигнуты; AFL/QEMU и libFuzzer используют разные механизмы, но идея та же — вести фаззер к новым путям.

## Куда дальше

Мы научились собирать покрытие аппаратно и сравнивать PT с ETM и DBI. Дальше логично взять трассу и **использовать её для символики**: путь, записанный PT, задаёт единственную трассу для concolic-исполнения, что убирает «взрыв путей». А пока главное запомни: аппаратная трассировка даёт покрытие незаметно для программы, но только поток управления.

## Где пригодится

- **Fuzzing research:** покрытие без инструментации.
- **Malware analysis:** трассировка без DBI и отладчика.
- **CTF Reversing (expert):** анализ сложного/обфусцированного кода.
- **Работа:** performance и program analysis.
