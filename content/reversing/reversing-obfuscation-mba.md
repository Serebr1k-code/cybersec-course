## Вопрос, с которого всё начинается

Ты смотришь на проверку пароля, и там не `if (p == "rev42")`, а десяток
вычислений с `xor`, `and`, `or`, сдвигами и умножениями, собранных в
**машину состояний**. Логика вроде простая, но прочитать её глазами невозможно.
Это **обфускация**: код намеренно запутан. Один из самых распространённых
приёмов — **MBA** (Mixed Boolean-Arithmetic), смесь битовых и арифметических
операций.

## Наш пример

Возьмём программу `obf`, которая проверяет пароль. Снаружи — обычное поведение:

```
$ ./obf rev42
access GRANTED
$ ./obf nope
access DENIED
```

Но внутри — не прямое сравнение. Исходная логика такая: вернуть истину, если
пароль равен `rev42`. А реализована она через **машину состояний** — цикл со
`switch`, где переменная `state` переходит между состояниями:

```c
int state = 0, i = 0, ok = 0, x = 7;
while (state != 5) {
    switch (state) {
    case 0: ok = 1; i = 0; state = 1; break;
    case 1: if ((x*x - 14*x + 49) == 0) state = 2; else state = 5; break;
    case 2: if (p[i]==0) { state = 4; break; }
            if (p[i] != "rev42"[i]) ok = 0;
            i++; state = 3; break;
    case 3: if ((x & 1) == 1) state = 2; else state = 2; break;  /* всегда назад */
    case 4: state = 5; break;
    }
}
return ok && i == 5;
```

Здесь два приёма обфускации сразу. Разберём их.

## Шаг 1: непрозрачный предикат (opaque predicate)

В состоянии 1 стоит условие `(x*x - 14*x + 49) == 0`. При `x = 7` это
`49 - 98 + 49 = 0` — истина. Но заметь: `x` в этом коде **не меняется**, значит
условие **всегда** истинно. Такое выражение называют **непрозрачным
предикатом** (opaque predicate): результат известен аналитику, но выглядит как
настоящая проверка.

Ещё пример: `(x & 1) == 1` в состоянии 3, где обе ветки ведут в состояние 2 —
то есть ветвление бессмысленно, оно только путает.

Проверим, что `x*x - 14*x + 49` раскладывается: `(x-7)^2`. При `x=7` — ноль. То
есть автор спрятал константу 7 за квадратным уравнением.

## Шаг 2: MBA — смесь битовых и арифметических операций

Другой класс — переписать простое выражение через битовые операции. Классика:
сложение `x + y` можно выразить как `(x ^ y) + 2*(x & y)`. Проверим это
символьно (z3):

```python
from z3 import *
x, y = BitVecs('x y', 32)
s = Solver(); s.add((x ^ y) + 2*(x & y) != x + y)
print(s.check() == unsat)     # True -> выражения эквивалентны
```

```
MBA (x^y)+2*(x&y) == x+y ? True
```

Аналогично `(x | y) + (x & y) == x + y`, `x - y == (x ^ y) - 2*(~x & y)` и
сотни других тождеств. Автор обфускатора берёт `x + y` и заменяет на любую из
этих форм, часто **несколько раз вложенно**. Глазами такое не читается.

## Шаг 3: почему это работает как защита

MBA-обфускация ломает привычные эвристики декомпилятора. Вместо `x + y` он
показывает кучу `xor/and/add`, и восстановить исходное выражение непросто.
Плюс непрозрачные предикаты добавляют ветвления, которых нет в исходной логике
(контроль-флоу флаттенинг — когда весь код превращён в одну машину состояний с
`switch`).

## Шаг 4: упрощение через z3

Самый надёжный способ распутать MBA — **символическое упрощение**. Идея: пусть
переменные — символы, а мы проверяем, эквивалентны ли выражения, и ищем более
простое. Приёмы:

- **Проверка тождеств.** `Solver` + `unsat` доказывает, что два выражения равны
  на всех входах.
- **Поиск «простого» эквивалента.** Перебираем кандидаты (`x+y`, `x^y`, ...) и
  проверяем эквивалентность.
- **Инструменты.** **souper** (superoptimizer) и **SSE** ищут короткое
  выражение, эквивалентное длинному MBA.

Пример: дано `t = (x ^ y) + 2*(x & y)`. Проверяем кандидат `x + y` — z3
говорит `unsat` для неравенства, значит `t == x + y`. Так длинная «каша»
схлопывается в один `add`.

## Шаг 5: борьба с непрозрачными предикатами

Непрозрачные предикаты убирают так:

- **Постоянная свёртка.** Если условие зависит только от констант (как
  `(x*x-14x+49)==0` при фиксированном `x`), вычисляем его один раз и заменяем
  на `true`/`false`.
- **Символическая проверка.** Если условие зависит от переменной, но всегда
  истинно (доказывается z3), тоже сворачиваем.
- **Упрощение графа.** После сворачивания ветвлений машина состояний
  разваливается, и код снова становится линейным.

## Шаг 6: практический маршрут

1. **Найти проверку** — по строкам (`GRANTED`/`DENIED`) и точкам сравнения.
2. **Понять структуру** — машина состояний, диспетчер, переменные.
3. **Свернуть константы** — вычислить непрозрачные предикаты.
4. **Упростить MBA** — через z3/souper найти короткие эквиваленты.
5. **Восстановить логику** — собрать проверку заново.

В нашем примере после свёртки видно: `ok=1`, потом посимвольное сравнение с
`"rev42"`, потом `ok && i==5`. То есть обычная проверка пароля `rev42`.

## Шаг 7: контроль-флоу флаттенинг подробнее

В нашем `obf` весь код — один цикл со `switch` по переменной `state`. Это
**control-flow flattening** (выравнивание потока управления): исходные
`if/else` и циклы «размазаны» в плоский набор состояний. Прочитать такую логику
линейно нельзя — нужно мысленно ходить по состояниям, как по графу.

Упрощает дело **восстановление графа переходов**: выписать, из какого состояния
в какое ведёт каждый `case`, и нарисовать схему. Тогда `0 → 1 → 2 → 3 → 2 → ...`
превращается в обычный цикл по символам, а `state 4 → 5` — в выход. После
сворачивания непрозрачных предикатов многие переходы становятся безусловными, и
граф схлопывается в исходный линейный код.

## Частые вопросы

**z3 долго не отвечает.** Упрощай по частям и ограничивай разрядность
(`BitVec('x', 8)` вместо 32). Иногда достаточно доказать эквивалентность на
байтах, а не на 32 битах.

**Тождество не доказывается.** Возможно, выражение не эквивалентно или зависит
от переполнения. Учти разрядность: в 8 битах `x + y` переполняется иначе, чем в
32.

**Как автоматизировать?** souper/SSE подбирают короткие выражения; в IDA/Ghidra
есть плагины для MBA-упрощения. Но проверять результат всё равно стоит через z3.

**Это точно обфускация, а не настоящая логика?** Смотри на «подозрительные»
константы и выражения: квадраты, `& 1`, XOR с константой — часто это маскировка
простых действий.

## Что мы теперь знаем

- **MBA** — замена простых выражений смесью битовых и арифметических операций;
  например, `x + y == (x ^ y) + 2*(x & y)`.
- **Непрозрачный предикат** — условие, результат которого всегда известен
  (`(x*x-14x+49)==0` при `x=7`), но выглядит как проверка.
- Контроль-флоу флаттенинг превращает код в машину состояний с `switch`.
- Упрощают MBA символьно: z3 доказывает эквивалентность, souper/SSE ищут
  короткое выражение.
- Непрозрачные предикаты сворачивают в `true`/`false`, после чего логика
  восстанавливается.
