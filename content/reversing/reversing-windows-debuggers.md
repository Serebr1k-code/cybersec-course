## Вопрос, с которого всё начинается

На Linux ты привык к gdb или lldb. Но перед тобой `.exe`-файл — Windows-программа
(формат **PE**, Portable Executable). Как её отлаживать? Какими инструментами,
где ставить точки останова, как посмотреть, какие функции из каких DLL она
вызывает? В этом уроке разберём два главных Windows-отладчика — **x64dbg** и
**WinDbg** — на конкретном PE-файле.

## Наш пример

Возьмём `usepe.exe` — маленькую программу, которая вызывает функцию `helper`
из библиотеки `mylib.dll`. Сначала посмотрим на файл не отладчиком, а простым
разбором заголовков (на Python, библиотекой `pefile`):

```
$ python3 -c "import pefile; pe=pefile.PE('usepe.exe'); ..."
Machine 0x8664  Subsystem 3  Entry 0x1020  ImageBase 0x140000000
Sections: [('.text','0x1000'), ('.rdata','0x2000'), ('.data','0x3000'), ('.pdata','0x4000')]
 Import mylib.dll ['helper']
```

Разберём каждое поле, потому что оно встретится в отладчике:

- **Machine 0x8664** — это x86-64 (у 32-битных PE было бы 0x14c).
- **Subsystem 3** — консольное приложение (GUI было бы 2).
- **Entry 0x1020** — смещение точки входа от **ImageBase**.
- **ImageBase 0x140000000** — «базовый адрес», к которому прибавляются все
  смещения. Значит, реальный адрес входа — `0x140001020`.
- **.text** — код, **.rdata** — только для чтения (там имена импортов),
  **.data** — изменяемые данные, **.pdata** — таблица для раскрутки стека
  (нужна обработчику исключений Windows).

Строка `Import mylib.dll ['helper']` — самое интересное: программа берёт
функцию `helper` из внешней DLL. Это то, что в отладчике будет видно как
**таблица импортов**.

## Шаг 1: дизассемблируем точку входа

Посмотрим на код вокруг входа обычным objdump (он умеет PE):

```
$ objdump -d -M intel usepe.exe
0000000140001000 <.text>:
   140001000: sub    rsp,0x28
   140001004: mov    DWORD PTR [rsp+0x24],ecx
   140001008: mov    ecx,DWORD PTR [rsp+0x24]
   14000100c: call   QWORD PTR [rip+0x1026]   # 0x140002038
   140001012: add    eax,DWORD PTR [rip+0x1fe8]  # 0x140003000
   14000101c: ret
   140001020: jmp    0x140001022
   140001022: jmp    0x140001022
```

Здесь видно самое важное: инструкция `call QWORD PTR [rip+0x1026]` — это
**косвенный вызов через таблицу импортов**. Программа не знает заранее, где
лежит `helper` — адрес подставляется системой при загрузке. Ссылка ведёт на
`0x140002038` — это ячейка в **IAT** (Import Address Table, таблица адресов
импорта). А `jmp` сам на себя на `0x140001022` — бесконечный цикл (заглушка).

## Шаг 2: x64dbg — интерфейс и первые шаги

**x64dbg** — бесплатный отладчик с графическим интерфейсом, стандарт де-факто
для разбора Windows-малвари и crackme. Открываем файл через `File → Open`.

Горячие клавиши, которые надо знать:

| Клавиша | Действие |
|---------|----------|
| F9 | запустить / продолжить (run) |
| F8 | шаг с обходом (step over) |
| F7 | шаг с заходом (step into) |
| F2 | поставить/снять точку останова |
| F4 | бежать до курсора |
| Ctrl+G | перейти по адресу |
| Space | править инструкцию |

Слева — список модулей (exe и все DLL), по центру — дизассемблер, справа —
регистры, флаги и стек, снизу — дамп памяти. Это тот же набор, что в gdb, но
разложенный по окнам.

## Шаг 3: таблица импортов и точка на DLL-функцию

Откроем окно `Symbols` (Ctrl+S) — там видны `mylib.dll` и её экспорт `helper`.
Клик по нему — и отладчик показывает адрес. Можно поставить точку останова
прямо на функцию из DLL: правый клик → «Breakpoint → Toggle». Теперь при
запуске (F9) отладчик остановится в тот момент, когда программа войдёт в
`helper`.

Это ключевой приём: вместо того чтобы читать код `usepe.exe` построчно, мы
ставим точку на **границу модуля** и смотрим аргументы и результат. В x64dbg
аргументы видны в правой панели (`rcx`, `rdx`, `r8`, `r9` для x64), а результат
— в `rax` после возврата.

## Шаг 4: WinDbg и команды

**WinDbg** — отладчик от Microsoft, консольный (плюс графическая версия).
Его сила — в глубоком анализе Windows: краш-дампы, структуры ядра, скрипты.
Базовые команды:

| Команда | Что делает |
|---------|------------|
| `g` | продолжить (go) |
| `p` | шаг с обходом |
| `t` | шаг с заходом |
| `bp 0x14000100c` | точка останова по адресу |
| `bu mylib!helper` | точка на символ в модуле |
| `r` | регистры |
| `dq 0x140002038` | прочитать 8 байт памяти |
| `!analyze -v` | полный анализ краха |
| `k` | стек вызовов |

Особенность WinDbg — **расширения** с восклицательным знаком: `!analyze -v`
автоматически разбирает дамп, находит виновника краха и печатает стек и
сигнатуру. Это спасает при анализе чужих крашей, где нет ни символов, ни
исходников.

## Шаг 5: анализ краш-дампа

Когда программа падает, Windows может сохранить **мини-дамп** (`.dmp`). В WinDbg
его открывают так:

```
0:000> !analyze -v
FAULTING_IP:
usepe!main+0x10
EXCEPTION_CODE: (NTSTATUS) 0xc0000005 - Access violation
```

Строка `0xc0000005` — код «нарушение доступа к памяти» (access violation), самый
частый краш. `!analyze` подсказывает и адрес, и виновника. Дальше смотрим
стек (`k`), регистры (`r`) и понимаем, почему адрес оказался невалидным.

## Шаг 6: что ещё умеют эти отладчики

- **x64dbg**: встроенный скриптовый язык (команды вроде `bp`, `run`, `log`),
  плагины (Scylla для восстановления импортов после распаковки, xAnalyzer для
  авто-комментариев), патчинг прямо в дампе.
- **WinDbg**: язык `dt` для разбора структур Windows, `s` для поиска в памяти,
  `!` -расширения, отладка ядра (нужен режим ядерной отладки).

Оба отладчика умеют **аппаратные точки останова** — те же, что в gdb/lldb, но с
другим интерфейсом: в x64dbg это вкладка Breakpoints → Hardware, в WinDbg —
`ba w4 0x140003000` (breakpoint on access, размер 4 байта).

## Шаг 7: как программа замечает отладчик

Отдельная важная тема — анти-отладка. Windows-программа может спросить систему
«меня кто-то отлаживает?». Самый простой способ — функция `IsDebuggerPresent`,
которая читает флаг `BeingDebugged` в структуре **PEB** (Process Environment
Block, блок окружения процесса). Продвинутые образцы проверяют
`NtGlobalFlag`, тайминги через `rdtsc` или наличие отладочных портов.

В x64dbg такие проверки обходят плагином **ScyllaHide** — он маскирует отладчик:
подменяет PEB, скрывает обработчики исключений, притворяется, что отладчика нет.
В WinDbg есть аналогичные приёмы через `!` -расширения. Понимание этого
механизма пригодится в следующем уроке, где мы разберём аппаратные точки
останова — их часто используют как раз для обхода анти-отладки.

## Что мы теперь знаем

- PE-файл устроен как ELF, но со своими заголовками: ImageBase, секции
  `.text/.rdata/.data/.pdata`, таблица импортов.
- Вызовы чужих DLL идут через **IAT** — косвенный `call` по адресу из таблицы.
- **x64dbg** — GUI-отладчик (F7/F8/F9/F2), удобен для crackme и малвари.
- **WinDbg** — консольный, силён в анализе дампов (`!analyze -v`) и структур
  Windows.
- Аппаратные точки останова и скрипты есть в обоих; оба умеют ставить точки на
  функции из DLL.

## Условные точки останова и скрипты x64dbg

Обычная точка останова останавливает выполнение на каждом попадании, а в цикле проверки пароля это тысячи остановок. Условная точка останавливает только при истинном условии — например, когда байт на входе совпал с ожидаемым:

```
bp 0x4011A0, "[rsp+8]==0x41"
```

x64dbg поддерживает команды прямо в поле «Condition» и собственный скриптовый движок. Скрипт автоматизирует распаковку: ставит breakpoint на `VirtualAlloc`, дампит регион и снимает аппаратные точки на исполнение.

```
// снять дамп региона после распаковки
bpx VirtualAlloc
run
savedata unpacked.bin, rcx, 0x10000
```

WinDbg вместо скриптов использует встроенный язык с `.foreach`, а также расширения `!`: `!address`, `!heap`, `!peb`.

## Анализ краш-дампа: пошаговый разбор

1. Открыть дамп: `windbg -z crash.dmp`.
2. `!analyze -v` — WinDbg сам покажет исключение, модуль и стек.
3. Проверить регистры и стек: `r`, `kv` (стек с параметрами).
4. Посмотреть память по адресу сбоя: `!address <addr>`, `db <addr>`.
5. Определить владельца: `lm` (список модулей), `!lmi <module>`.

Типичный признак переполнения буфера в дампе — адрес возврата, указывающий на `0x41414141` (то есть `AAAA`). Если перезапись «умная» (heap-спрей), указатель ведёт в кучу — тогда ищи объект командой `!heap -p -a <addr>`.

## Ловушки при отладке на Windows

- **Отладчик обнаружен:** программа зовёт `IsDebuggerPresent`, `CheckRemoteDebuggerPresent`, читает `PEB->BeingDebugged` или `NtGlobalFlag`. Плагин ScyllaHide прячет эти флаги.
- **ASLR мешает адресам:** включи `Options → Preferences → Suspend on library load` или используй модульные точки (`bp module+offset`), а не абсолютные.
- **32/64 бита:** WOW64-процесс отлаживается иначе; для 32-битной цели нужен 32-битный отладчик.
- **Точка входа против `main`:** точка останова на EP даст код рантайма, а не логику — дойди до `main` через `bp` на импортируемой функции или по символам PDB.

## Куда дальше

В следующем уроке мы спустимся ниже уровня отладчиков и разберём **аппаратные
точки останова и watchpoints** — механизм в регистрах процессора DR0–DR7, на
котором они держатся. А пока главное запомни: **PE-программы отлаживают в
x64dbg (графика) или WinDbg (консоль), и ключевой приём — ставить точки на
функции из DLL и смотреть IAT**.
