## Вопрос, с которого всё начинается

Представь: на CTF тебе дали один файл с именем `challenge`. Исходников нет. Запускаешь —
он просит пароль и на неправильный отвечает «Wrong». Как узнать, что это вообще за файл,
что он делает и какой пароль правильный?

Именно этим занимается реверс-инжиниринг (reverse engineering, RE) — восстановление логики
программы по её машинному коду. В этом уроке мы возьмём один конкретный бинарник и пройдём
первый круг разведки: без отладчика, без декомпилятора — только штатными утилитами.

## Наш пример

Чтобы всё было честно и воспроизводимо, соберём подопытный бинарник сами. Вот его исходник
(файл `crackme.c`):

```c
extern int printf(const char *fmt, ...);
extern int strcmp(const char *a, const char *b);
extern long read(int fd, void *buf, unsigned long n);

static int check_password(const char *in) {
    const char *secret = "hunter2";
    return strcmp(in, secret) == 0;   /* 0, если строки равны */
}

int main(void) {
    char buf[64];
    printf("Enter password: ");
    long n = read(0, buf, 63);
    if (n <= 0) return 1;
    buf[n] = 0;
    for (long i = 0; i < n; i++) if (buf[i] == '\n') buf[i] = 0;
    if (check_password(buf))
        printf("Correct! flag{rev_basics_1s_fun}\n");
    else
        printf("Wrong.\n");
    return 0;
}
```

Компилируем и получаем тот самый «файл без исходников» — готовый ELF:

```bash
$ gcc -O0 -o crackme crackme.c
```

Дальше мы будем смотреть на `crackme` так, будто исходника у нас нет. Только утилиты.

## Шаг 1: что это за файл?

Первая команда — `file`. Она читает несколько байт заголовка и говорит, с чем мы имеем дело.

```bash
$ file crackme
crackme: ELF 64-bit LSB pie executable, x86-64, version 1 (SYSV),
dynamically linked, interpreter /lib64/ld-linux-x86-64.so.2,
BuildID[sha1]=6cbfa5..., for GNU/Linux 4.4.0, not stripped
```

Разбираем по частям:

- **ELF** — формат исполняемых файлов в Linux (как `.exe` в Windows, `.dylib`/Mach-O в macOS).
- **64-bit x86-64** — это 64-разрядная программа под процессор Intel/AMD. Значит, и инструкции
  внутри — x86-64.
- **pie executable** — «позиционно-независимый исполняемый файл»: при каждом запуске его
  грузят по случайному адресу. Это защита; подробнее — на шаге 3.
- **dynamically linked** — часть функций берётся из внешней библиотеки (`libc.so.6`), а не
  вшита в файл.
- **not stripped** — самое интересное. Буквально «не обрезан»: имена функций внутри сохранены.

## Шаг 2: строки — половина beginner-задач

Раз имена сохранены, поищем в бинарнике читаемый текст командой `strings`. Она вытаскивает
все последовательности печатных символов длиной не меньше заданной (`-n 5` — от пяти букв).

```bash
$ strings -n 5 crackme | grep -iE 'flag|pass|correct|wrong|input'
hunter2
Enter password:
Correct! flag{rev_basics_1s_fun}
Wrong.
check_password
```

Стоп. Мы ещё не запускали программу, не открывали дизассемблер — а уже видим строку
`hunter2` рядом со словами `Enter password` и `Correct`. Это и есть пароль-загадка: строка
лежит в бинарнике в открытом виде. А `check_password` — имя функции проверки.

**Вывод, который стоит запомнить:** прежде чем идти в сложные инструменты, прогони `strings`.
Очень часто ответ уже здесь.

Бывает и наоборот: `strings` выдаёт мусор или пустоту. Это первый намёк, что бинарник
**упакован** — его настоящий код сжат и распаковывается в памяти при запуске, а строки
зашифрованы. Тогда триаж продолжают проверкой секций (`readelf -S`), но это уже отдельная тема.

Какие ещё исходы бывают у триажа:

- Строки с URL, IP-адресами, командами вроде `/bin/sh` или `wget` → похоже на malware или
  загрузчик полезной нагрузки.
- Строки вида `Usage: ./prog <key>` или `Enter key:` → подсказка на формат ввода.
- Строки с алфавитом base64/hex → где-то рядом кодирование или шифрование данных.
- Вообще нет читаемых строк → упаковка, либо бинарник собран под другую задачу.

По этим «зацепкам» уже строится гипотеза, где искать ответ, — а это и есть начало настоящего
реверса.

## Шаг 3: какие защиты включены?

Теперь посмотрим, с какими механизмами защиты собран бинарник. Это нужно, чтобы понять,
как к нему вообще подступаться. Утилита `checksec` (идёт с pwntools) показывает разом всё:

```bash
$ checksec --file=crackme
[*] '/tmp/pentestcode/revdemo/crackme'
    Arch:       amd64-64-little
    RELRO:      Partial RELRO
    Stack:      Canary found
    NX:         NX enabled
    PIE:        PIE enabled
    Stripped:   No
```

Что здесь важно для реверса (детально разберём в следующих уроках):

- **PIE: enabled** — адреса меняются при каждом запуске. В дизассемблере адреса условные,
  их придётся пересчитывать.
- **NX: enabled** — стек помечен как неисполняемый (защита от запуска кода со стека).
- **Canary found** — на стеке есть «сторожевой» маркер против переполнений.
- **Stripped: No** — имена символов на месте.

Для чисто *реверса* (в отличие от pwn) эти флаги влияют меньше всего на PIE: он определяет,
как читать адреса. А вот `Stripped: No` — подарок.

## Шаг 4: а есть ли таблица имён?

Утилита `nm` показывает таблицу символов — имена функций и переменных, которые сохранились.
Отфильтруем нужное:

```bash
$ nm crackme | grep -iE ' main|check_password| strcmp| printf| read'
0000000000001179 t check_password
00000000000011ad T main
                 U printf@GLIBC_2.2.5
                 U read@GLIBC_2.2.5
                 U strcmp@GLIBC_2.2.5
```

Читаем:

- `check_password` и `main` — наши функции, с адресами (`t`/`T` — локальная/глобальная).
- Буква `U` у `strcmp`, `printf`, `read` — «undefined»: эти функции объявлены, но лежат
  не здесь, а в библиотеке `libc`. Бинарник обращается к ним по имени.

Вот и вся картина: программа читает ввод, зовёт `strcmp` для сравнения и печатает результат.
Без единой строчки ассемблера.

## Шаг 5: проверяем догадку

Мы предположили, что пароль — `hunter2`. Проверим:

```bash
$ ./crackme
Enter password: hunter2
Correct! flag{rev_basics_1s_fun}
```

Сработало. Мы «сломали» задачу, не заходя в дизассемблер, — только `file`, `strings`,
`checksec` и `nm`.

## Что мы теперь знаем

- Программа — это **ELF-файл** под x86-64, собранный динамически.
- Читаемый текст внутри ищется командой `strings` — и там часто лежит готовый ответ.
- `checksec` одним экраном показывает защиты; `Stripped: No` означает, что имена сохранены.
- `nm` даёт список функций и внешних вызовов (строки с `U` — из библиотек).
- Порядок разведки всегда один: **сначала тип файла и строки, потом уже дизассемблер**.

## Куда дальше

Мы нашли пароль «в лоб», но не поняли, *как* программа сравнивает строки — а в реальных
задачах строки часто зашифрованы или проверка спрятана. В следующем уроке мы возьмём ту же
функцию `check_password` и прочитаем её **ассемблер**: увидим, как аргументы попадают в
регистры, что делает `call` и как работает сравнение. А пока главное запомни: не открывай
дизассемблер, пока не сделал `file`, `strings` и `nm`.

## Где пригодится

- **CTF Reversing:** первичная разведка любой crackme-задачи; `file`/`strings`/`nm` — первый шаг.
- **Malware analysis:** определение типа образца, упаковщика и строк-индикаторов без запуска кода.
- **Bug bounty / vuln research:** быстрая оценка закрытого бинарника или прошивки перед глубоким анализом.
- **Работа (SOC / threat intel / RE-команда):** ежедневный триаж образцов и патчей.
- **Собес:** вопросы «что такое PIE/NX/canary», «как найти строки в бинарнике» — база любого RE-интервью.
