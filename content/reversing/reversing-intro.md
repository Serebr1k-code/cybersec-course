Реверс-инжиниринг (reverse engineering, RE) — это процесс восстановления логики программы по её
машинному коду, когда исходников нет. В CTF это отдельная категория задач: вам дают бинарник
(ELF/PE/Mach-O), иногда с обфускацией или упакованный, и просят найти флаг, пароль или ключ.
В реальной жизни тот же навык используется для анализа malware, поиска уязвимостей в закрытом
ПО, обхода лицензионных проверок и аудита проприетарных протоколов.

## Что такое реверс и зачем он нужен

Ключевая мысль: компилятор превращает читаемый исходник в машинные инструкции, но **не удаляет
смысл**. Структуры данных, ветвления, строки, вызовы функций — всё это остаётся в бинарнике,
просто в другой форме. Задача реверсера — прочитать эту форму и понять замысел автора.

Где это применяется:

- **CTF.** Задачи категории Reversing: crackme, keygen, VM-based, анти-дебаг, упакованные бинари.
- **Malware analysis.** Понять, что делает образец, куда звонит, как шифрует данные.
- **Vulnerability research.** Найти баг в закрытом бинарнике (например, в прошивке роутера).
- **Аудит и совместимость.** Разобрать проприетарный формат файла или сетевой протокол.
- **Патчинг.** Заменить проверку лицензии, убрать телеметрию, починить крэш.

Порядок анализа почти всегда один и тот же: **сначала статика** (что внутри файла), **потом
динамика** (что происходит при запуске), и только затем целенаправленное копание в конкретной
функции. Не начинайте с дизассемблера «в лоб» — сначала соберите разведданные о файле.

## Из чего состоит бинарник

Формат ELF (Linux) состоит из секций и сегментов. Для реверса важны:

- **`.text`** — исполняемый код (машинные инструкции).
- **`.rodata`** — константы только для чтения, чаще всего здесь лежат строки.
- **`.data` / `.bss`** — глобальные переменные (инициализированные / неинициализированные).
- **`.plt` / `.got`** — таблицы для вызова внешних функций (libc и т.д.).
- **Заголовок** — точка входа (`Entry point`), архитектура, тип (EXEC/PIE/shared).

Посмотреть это без запуска можно командой `file` и `readelf`:

```bash
file ./crackme
# ./crackme: ELF 64-bit LSB pie executable, x86-64, dynamically linked, not stripped

readelf -h ./crackme      # заголовок: класс, endianness, entry point, тип
readelf -S ./crackme      # список секций
readelf -s ./crackme      # символы (если не stripped)
strings -n 6 ./crackme    # печатаемые строки длиной >= 6
```

Флаг `not stripped` — большая удача: имена функций сохранились. `stripped` — имена убраны,
придётся восстанавливать вручную.

**Строки (`strings`) — первый инструмент.** Очень часто флаг или подсказка лежит прямо в
`.rodata`. Если флаг зашифрован, рядом часто видны строки вида `Correct!`, `Wrong password`,
`Usage: ...` — они указывают на функцию проверки.

## Первичная разведка: чек-лист

Прежде чем открывать Ghidra, прогоните бинарник по чек-листу. Это экономит часы.

```bash
# 1. Тип файла, архитектура, статичность
file ./target
# 2. Защиты (PIE, NX, canary, RELRO)
checksec --file=./target      # из пакета pwntools: pwn checksec ./target
# 3. Строки
strings -n 5 ./target | less
# 4. Импортируемые функции (что вызывает из libc)
objdump -T ./target | head
# 5. Символы и функции (если не stripped)
nm ./target | head -50
# 6. Как запускается
./target --help ; echo "exit=$?"
```

На что смотреть в выводе `checksec`:

- **PIE** — позиционно-независимый код (адреса случайны при каждом запуске).
- **Canary** — защита стека от переполнений.
- **NX** — стек неисполняем, shellcode на стеке не сработает.
- **RELRO** — защита таблицы GOT (Full/Partial/No).

Для *реверса* (в отличие от pwn) эти флаги важны меньше, но PIE влияет на то, как читать
адреса в дизассемблере.

## Статика vs динамика

Есть два взаимодополняющих подхода, и хороший аналитик чередует их.

| Подход | Что делаем | Плюсы | Минусы |
|--------|-----------|-------|--------|
| **Статика** | Читаем код без запуска (Ghidra, IDA, radare2, objdump) | Видим весь код сразу, безопасно, работает с malware | Обфускация/упаковка мешает, много «шума» |
| **Динамика** | Запускаем под отладчиком (gdb, x64dbg, strace, ltrace) | Видим реальные значения, обходим обфускацию | Не видим невыполненные ветки, среда может детектиться |

Практическое правило: **начните со статики** (strings + дизассемблер + декомпилятор), найдите
подозрительную функцию проверки, **затем перейдите в отладчик** и пройдите её по шагам,
наблюдая значения регистров и памяти. Иногда проще: поставить breakpoint на функции сравнения
(`strcmp`, `memcmp`) и посмотреть, с чем сравнивают ввод.

## Инструментарий

Полный набор реверсера:

- **radare2 / rizin** — консольный фреймворк, быстрый, есть почти везде.
- **Ghidra** — бесплатный декомпилятор от NSA, генерирует C-подобный псевдокод.
- **IDA Free / IDA Pro** — индустриальный стандарт, лучший декомпилятор (Hex-Rays).
- **objdump / readelf / nm** — бинарные утилиты GNU, всегда под рукой.
- **gdb + pwndbg/GEF** — динамическая отладка на Linux.
- **x64dbg** — отладчик для Windows (PE-файлы).
- **ltrace / strace** — трассировка библиотечных/системных вызовов.
- **Detect It Easy (DIE)** — определение компилятора, упаковщика, языка.

Минимальный стартовый набор для CTF: `file`, `strings`, `checksec`, `radare2`, `Ghidra`, `gdb`.

## Практический пример: разбор простого crackme

Дан бинарник `crackme`, который просит пароль. Разберём его по шагам.

**Шаг 1. Разведка.**

```bash
$ file crackme
crackme: ELF 64-bit LSB executable, x86-64, dynamically linked, not stripped

$ strings -n 6 crackme | grep -iE 'flag|pass|correct|wrong|input'
Enter password:
Correct! Here is your flag: %s
Wrong.
```

Видим форматную строку `%s` — флаг передаётся в `printf` уже готовым. Значит, где-то в коде есть
проверка пароля, после которой печатается флаг.

**Шаг 2. Поиск функции проверки.**

```bash
$ nm crackme | grep -iE 'main|check|verify'
00000000004011a6 T main
00000000004011c8 T check_password
```

Имена не убраны — сразу видим `check_password`.

**Шаг 3. Дизассемблирование (radare2).**

```bash
$ r2 -A crackme
[0x004010a0]> s sym.check_password
[0x004011c8]> pdf
```

`pdf` печатает функцию. Читаем: она сравнивает введённую строку с константой (в `.rodata`),
посимвольно или через `strcmp`. Достаём строку-пароль.

**Шаг 4. Проверка.**

```bash
$ ./crackme
Enter password: s3cr3t_pass
Correct! Here is your flag: flag{...}
```

Это классический паттерн: `strings` → символы → дизассемблер → пароль. Более сложные crackme
шифруют сравнение или используют анти-дебаг, но каркас анализа тот же.

## Типичные ошибки новичка

- **Сразу открывать декомпилятор.** Декомпилятор — не волшебство; без понимания ассемблера
  псевдокод читается как «шум». Сначала `file`/`strings`/`checksec`.
- **Игнорировать `strings`.** Половина beginner-задач решается одной командой.
- **Читать весь `main` сверху вниз.** Ищите точки интереса: вызовы `strcmp`, `memcmp`, циклы,
  обращения к строкам-подсказкам (`Correct`, `Wrong`).
- **Путать адреса при PIE.** В отладчике адреса смещены относительно базы; в Ghidra база условная
  (обычно 0x100000). Учитесь пересчитывать: `реальный = база + смещение`.
- **Забыть про endianness.** x86-64 — little-endian: `0x41424344` в памяти лежит как `44 43 42 41`.
- **Не сохранять артефакты.** Записывайте найденные строки, адреса, гипотезы — иначе потеряете нить.
- **Бояться отладчика.** Иногда один breakpoint на `strcmp` быстрее часа чтения дизассемблера.

## Куда двигаться дальше

После этой вводной идите по ветке: **ассемблер → статический анализ (Ghidra/r2) → декомпилятор**.
Это база, без которой остальные техники (анти-дебаг, распаковка, обфускация) не работают.
Отдельные боковые ветки: managed-код (.NET/Java) и Python bytecode — там свой инструментарий,
но принцип «понять логику без исходников» тот же.

## Где пригодится

- **CTF Reversing:** первичная разведка любой crackme-задачи; `strings` и `checksec` — первый шаг.
- **Malware analysis:** определение типа файла, упаковщика, строк-индикаторов компрометации.
- **Bug bounty / vuln research:** быстрая оценка закрытого бинарника или прошивки перед глубоким анализом.
- **Работа (SOC / threat intel / RE-команда):** ежедневная рутина триажа образцов и патчей.
- **Собес:** вопросы «что такое PIE/NX/canary», «как найти строки в бинарнике» — база любого RE-интервью.
