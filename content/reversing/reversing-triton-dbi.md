Динамическая бинарная инструментация (DBI) позволяет исполнять программу и перехватывать каждую
инструкцию, строя полную картину происходящего. **Triton** — фреймворк, который объединяет DBI с
символьным исполнением и taint-анализом: он не только перехватывает инструкции, но и строит для
каждого регистра/памяти символьное выражение, позволяя отвечать на вопросы «откуда пришло это
значение» и «какой вход даст нужный результат». Это мощный инструмент для восстановления алгоритмов
и анализа зависимостей данных.

## Что такое DBI

DBI — это техника, при которой код инструментируется «на лету»: перед исполнением каждой
инструкции (или базового блока) управление передаётся вашему обработчику. Вы можете читать/менять
регистры и память, логировать, пропускать инструкции. DBI не требует модификации бинарника и
работает на реальном процессе. Основные фреймворки: PIN (Intel), DynamoRIO, QBDI (QuarkslaB),
Triton (на базе PIN или собственного ядра). Triton добавляет символьное исполнение и taint.

## Triton: архитектура

Triton работает так: вы регистрируете колбэк `processing(instruction)`, который вызывается перед
каждой инструкцией. Внутри вы можете:

- Читать/писать регистры: `ctx.getConcreteRegisterValue(ctx.registers.rax)`.
- Читать/писать память: `ctx.getConcreteMemoryValue(addr)`.
- Создавать символьные переменные и связывать их с регистрами/памятью.
- Задавать ограничения и решать их через встроенный SMT-солвер (Z3).
- Помечать данные как tainted и отслеживать распространение.

Triton строит внутреннее представление (AST) для каждой инструкции, обновляя символьные выражения
регистров и памяти. Это позволяет, например, выразить `rax` после серии инструкций как функцию от
входных байтов и решить уравнение.

## Трассировка инструкций

Простейший сценарий — логирование потока инструкций:

```python
from triton import TritonContext, ARCH, Instruction

ctx = TritonContext(ARCH.X86_64)
ctx.setMode(ctx.modes.ALIGNED_MEMORY, True)
# ... загрузка бинарника и настройка памяти ...

def on_instruction(ctx, instruction):
    print(hex(instruction.getAddress()), instruction.getDisassembly())
    return True

ctx.addCallback(ctx.callbacks.PROCESSING, ctx.callbacks.instruction_processing, on_instruction)
```

Вы получите полную трассу выполнения — незаменимо для анализа обфусцированного кода, где статический
граф запутан. Трасса показывает реально исполненные ветки, что позволяет «срезать» мёртвый
обфусцирующий код.

## Символьные выражения и AST

Главная особенность Triton — символьное представление. Свяжем входной байт с символом:

```python
from triton import TritonContext, ARCH, MemoryAccess, CPUSIZE

ctx = TritonContext(ARCH.X86_64)
ctx.symbolizeRegister(ctx.registers.rax, "input")
# после выполнения инструкций:
rax_expr = ctx.getSymbolicRegister(ctx.registers.rax)
print(rax_expr)   # например: (input + 0x10) ^ 0x42
```

Теперь `rax` выражен через `input`. Можно добавить ограничение (`rax == 0xdeadbeef`) и спросить
солвер, каким должен быть `input`. Это прямое решение keygenme: не разбирая алгоритм вручную, вы
получаете вход, удовлетворяющий проверке.

## Taint-анализ

Taint-анализ отслеживает, какие входные данные влияют на конкретное значение. Помечаем буфер
ввода как tainted, исполняем программу, и смотрим, где taint «всплывает» — например, в аргументе
`strcmp` или в адресе перехода. Это отвечает на вопрос «какие байты ввода влияют на эту проверку»,
что резко сужает пространство поиска.

```python
ctx.taintRegister(ctx.registers.rdi)
# ... выполнение ...
tainted = ctx.isRegisterTainted(ctx.registers.rax)
```

Для malware-анализа taint показывает, откуда берутся данные для сетевых запросов или расшифровки:
например, конфигурация считывается из файла, «пропитывает» буфер, а затем используется как ключ.

## Практический разбор

Пусть crackme сравнивает ввод с вычисленным значением. Символизируем буфер ввода, исполняем до
`strcmp`, добавляем ограничение «аргументы равны» и решаем:

```python
# символизируем 8 байт ввода
for i in range(8):
    ctx.symbolizeMemory(MemoryAccess(BASE + i, CPUSIZE.BYTE), f"in_{i}")

# после вызова функции проверки:
rax = ctx.getSymbolicRegister(ctx.registers.rax)
ctx.pushPathConstraint(rax == 1)   # функция вернула "успех"
model = ctx.getModel(ctx.getPathConstraints())
for k, v in sorted(model.items()):
    print(k, hex(v.getValue()))
```

На выходе — значения входных байтов, при которых проверка проходит. Это автоматический keygen.
Triton сам строит выражения по инструкциям, вам не нужно вручную разбирать алгоритм.

## Сравнение DBI-фреймворков

| Фреймворк | Особенность |
|---|---|
| PIN | Классический DBI от Intel, много примеров |
| DynamoRIO | Гибкая инструментация, кроссплатформенный |
| QBDI | Лёгкий DBI от Quarkslab, без символьного анализа |
| Triton | DBI + символика + taint + Z3 |
| Frida | Динамическая инструментация на уровне функций (JS) |

Выбор: для трассировки и taint — Triton; для быстрого перехвата функций — Frida; для
низкоуровневой инструментации без символьного анализа — QBDI/PIN.

## Инструменты и флаги

| Задача | API Triton |
|---|---|
| Создать контекст | `TritonContext(ARCH.X86_64)` |
| Колбэк инструкции | `addCallback(PROCESSING, ...)` |
| Чтение регистра | `getConcreteRegisterValue` |
| Символизация | `symbolizeRegister`, `symbolizeMemory` |
| Выражение | `getSymbolicRegister` |
| Ограничение | `pushPathConstraint` |
| Решение | `getModel` |
| Taint | `taintRegister`, `isRegisterTainted` |

## Установка и загрузка бинарника

Triton ставится как Python-пакет: `pip install triton-library` (имя может отличаться в зависимости от
дистрибутива) или собирается из исходников. Для загрузки исполняемого файла обычно комбинируют
Triton с загрузчиком (например, `lief` для парсинга ELF/PE) и запускают код в режиме DBI. Есть два
режима: **внешний** (Triton инструментирует реальный процесс через PIN) и **эмуляционный** (Triton
сам исполняет инструкции через `processing`). Второй проще для скриптов и чаще используется в CTF.

Настройка включает: создание контекста под архитектуру (`ARCH.X86_64`), загрузку сегментов в память
(`ctx.setConcreteMemoryAreaValue`), установку регистров и точки входа, и настройку колбэков. Важно
включить `ALIGNED_MEMORY`, если код ожидает выровненный доступ, и корректно задать размеры памяти.

## Taint-анализ на примере

Рассмотрим malware, который читает конфигурацию из файла и использует её для расшифровки строк.
Помечаем буфер конфигурации как tainted и исполняем. В какой-то момент taint «всплывёт» в аргументе
функции расшифровки — это покажет, какие байты конфигурации образуют ключ. Далее taint появится в
строках, которые расшифровываются. Так восстанавливается связь «конфиг → ключ → строки» без ручного
разбора алгоритма.

Другой пример — сетевая активность: taint входного пакета покажет, какие его поля влияют на адреса
переходов (потенциальное переполнение) или на параметры запроса. Это ускоряет поиск уязвимостей и
понимание протокола. Taint-анализ не требует символизации всей программы — достаточно помечать
интересующие данные и наблюдать распространение.

## Символическое исполнение против эмуляции

Полезно различать три близких подхода. **Эмуляция** (Unicorn/Qiling) просто исполняет код и даёт
конкретные значения. **Символическое исполнение** (angr) исследует все пути, представляя входы
символами, и решает ограничения — идеально для «чёрного ящика», но страдает от комбинаторного взрыва.
**DBI с символикой** (Triton) идёт по конкретной трассе, но строит символьные выражения для неё —
компромисс: точность конкретного исполнения плюс символьный анализ на выбранном пути.

Практический выбор: если программа имеет чёткую проверку и вы знаете, куда идти, — Triton (точнее и
быстрее на одном пути). Если путей много и вы не знаете, какой ведёт к успеху, — angr (исследует
пути). Если нужно просто наблюдать поведение — эмуляция без символики.

## Трассировка ветвлений и обфускация

Одно из главных применений DBI — анализ обфусцированного кода. Обфускаторы вставляют сотни
фиктивных ветвлений, мёртвый код и «непрозрачные предикаты», чтобы запутать статический анализ.
DBI решает это элегантно: он записывает, какие ветки реально исполнены, а какие — нет. Построив
трассу для конкретного входа, вы «выпрямляете» поток управления: мёртвый код не исполняется и не
попадает в трассу. Повторив для разных входов, можно восстановить все реальные пути.

Triton дополнительно даёт выражения для условий ветвления: вы видите, от каких символов зависит
каждый `jcc`. Если условие зависит только от констант (непрозрачный предикат, который всегда
истинен), это видно из выражения — и фиктивное ветвление можно отбросить. Так DBI с символикой
комбинирует точность трассы с возможностью анализировать условия, что делает его мощным
инструментом против control-flow flattening и MBA-обфускации.

## Подводные камни

Первое: Triton работает медленно (символьное представление дорого) — инструментируйте только нужный
участок. Второе: символизация памяти требует правильных размеров и выравнивания. Третье: не все
инструкции поддержаны; экзотические (SSE/AVX) могут игнорироваться. Четвёртое: для решения нужен
корректный path constraint — иначе модель пуста. Пятое: анти-DBI проверки могут детектировать
инструментацию (по таймингам, по модификации памяти). Шестое: Triton и angr решают похожие задачи —
angr проще для «чёрного ящика», Triton точнее для конкретной трассы. Седьмое: символизация
памяти должна точно соответствовать доступу (размер и адрес), иначе выражение получится
некорректным. Восьмое: результат `getModel` нужно сопоставлять с исходными символами — Triton
возвращает модель по символическим переменным, а не по байтам ввода напрямую.

## Что дальше / решение

Практика: установите Triton, запустите простой keygenme, символизируйте ввод и получите решение.
Затем помечайте ввод как tainted и посмотрите, где taint появляется. Сравните с решением через angr
(см. `reversing-symbolic-recipe`). Далее — `reversing-intel-pt` (аппаратная трассировка) и
`reversing-taint-analysis` (существующий урок).

Освоив Triton, вы получаете инструмент, который закрывает разрыв между «просто эмуляцией» и
«полным символьным исполнением»: точность реальной трассы плюс символьные выражения на ней.
