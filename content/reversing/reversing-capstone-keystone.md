## Вопрос, с которого всё начинается

Ты устал вручную открывать бинарники в GUI. Нужен **свой инструмент**: прочитать код, найти нужные инструкции, при необходимости изменить байты и выполнить их в эмуляторе. С чего начать?

## Наш пример

Возьмём `engine.elf` — ELF-бинарник, на котором мы будем строить анализатор:

```
$ file engine.elf
engine.elf: ELF 64-bit LSB executable, x86-64
```

Мы напишем на Python небольшой конвейер: дизассемблировать, распознать инструкции, собрать патч и исполнить.

## Шаг 1: Capstone — дизассемблер как библиотека

**Capstone** — движок дизассемблирования с API для многих языков. Он принимает байты, архитектуру и режим, а возвращает инструкции с мнемоникой, операндами и адресами.

```
from capstone import Cs, CS_ARCH_X86, CS_MODE_64
md = Cs(CS_ARCH_X86, CS_MODE_64)
for insn in md.disasm(code_bytes, 0x1000):
    print(f"{insn.address:#x}: {insn.mnemonic} {insn.op_str}")
```

Вывод — тот же, что у `objdump`, но в структурированном виде: с этим можно писать условия («найди все `call`»), строить графы и искать паттерны.

## Шаг 2: почему библиотека, а не парсинг вывода

Парсить текстовый вывод `objdump` хрупко: меняется формат, теряются детали. Capstone даёт структуры: `insn.mnemonic`, `insn.op_str`, `insn.bytes`, `insn.groups`. Это позволяет точно находить инструкции и их операнды, не полагаясь на строки.

## Шаг 3: Keystone — ассемблер как библиотека

**Keystone** — обратный к Capstone: собирает машинный код из ассемблера. Это нужно, когда ты хочешь **пропатчить** код: собрать нужные инструкции и вставить их в бинарник.

```
from keystone import Ks, KS_ARCH_X86, KS_MODE_64
ks = Ks(KS_ARCH_X86, KS_MODE_64)
encoding, count = ks.asm("nop; ret")
```

`encoding` — список байтов. Собрав патч, ты заменяешь им байты по нужному адресу — например, чтобы убрать проверку лицензии.

## Шаг 4: Unicorn — эмулятор как библиотека

**Unicorn** — эмулятор CPU: он исполняет машинный код без реальной машины. Это безопасно (код не выйдет в сеть и не тронет файлы) и удобно для анализа функций изолированно.

```
from unicorn import Uc, UC_ARCH_X86, UC_MODE_64
uc = Uc(UC_ARCH_X86, UC_MODE_64)
uc.mem_map(0x1000, 0x1000)
uc.mem_write(0x1000, code)
uc.emu_start(0x1000, 0x1000 + len(code))
```

Так можно «прогнать» функцию с разными входами и посмотреть, что она возвращает, — не запуская весь бинарник.

## Шаг 5: собираем конвейер

Три библиотеки складываются в конвейер:

1. **Capstone** — прочитать и найти целевую функцию/инструкции.
2. **Keystone** — собрать патч (например, заменить `jne` на `nop nop`).
3. **Unicorn** — эмулировать и проверить результат.

Это база для собственных деобфускаторов, эмуляторов и fuzz-скриптов.

## Шаг 6: артефакт

Извлечём строку движка:

```
$ strings -n 5 engine.elf | head
Capstone 5.0
Keystone 0.9
Unicorn 2.0
nto{c4pst0n3_k3yst0n3_un1c0rn}
```

В реальном скрипте артефактом был бы найденный адрес или результат эмуляции, а строка подтверждает версии библиотек.

## Шаг 7: разбор PE/ELF и доступ к секциям

Чтобы дизассемблировать реальный бинарник, его надо разобрать. Простейший путь — библиотека `pefile` (для PE) или `pyelftools` (для ELF): они дают список секций, адреса и байты. Например, для ELF: прочитать секцию `.text`, получить её виртуальный адрес, передать байты в Capstone вместе с этим адресом — и адреса инструкций будут совпадать с реальными.

```
from elftools.elf.elffile import ELFFile
with open('engine.elf','rb') as f:
    elf = ELFFile(f)
    text = elf.get_section_by_name('.text')
    base = text['sh_addr']
    code = text.data()
```

Без правильной базы адрес в дизассемблере будет начинаться с нуля, и переходы не совпадут. Это частая ошибка новичков.

## Шаг 8: автоматический поиск паттернов

Сила библиотечного дизасма — в возможности писать условия. Например, найти все вызовы, идущие к конкретной функции, или все сравнения с константой:

```
for insn in md.disasm(code, base):
    if insn.mnemonic == 'cmp' and '0x1337' in insn.op_str:
        print(hex(insn.address))
```

Так ищут проверки лицензии, «магические» значения, точки ветвления по результату. В сочетании с Keystone ты можешь собрать патч (заменить `jne` на `nop`) и записать его обратно в бинарник.

## Шаг 9: эмуляция функции целиком

Unicorn позволяет выполнить функцию в изоляции. Схема: замапить память, записать код, положить аргументы (в регистры согласно ABI или по указателям в память), выставить точку входа и «стоп-адрес» (адрес возврата), запустить `emu_start`, затем прочитать результат из регистра или памяти.

```
uc.reg_write(UC_X86_REG_RDI, 0x1000)   # первый аргумент
uc.emu_start(entry, ret_addr)
print(hex(uc.reg_read(UC_X86_REG_RAX)))  # возврат
```

Так «прогоняют» крипто-функции с разными ключами, проверки пароля, парсеры — не запуская весь бинарник. Это безопасно и воспроизводимо.

## Шаг 10: закрепление на нашем примере

Наш `engine.elf`: мы разобрали роли Capstone (дизасм), Keystone (сборка патча) и Unicorn (эмуляция), увидели, почему библиотека надёжнее парсинга `objdump`, и извлекли артефакт. Это основа собственного инструмента реверса.

Дальше в реальной задаче: разобрать секции, дизассемблировать целевые функции, найти проверки, пропатчить их через Keystone и проверить результат в Unicorn. Такой конвейер лежит в основе автоматизации анализа тысяч образцов.

## Шаг 11: интеграция с Ghidra и IDA

Библиотеки Capstone/Keystone/Unicorn — не замена GUI-инструментам, а их дополнение. В Ghidra можно писать скрипты на Python/Java, которые используют эти библиотеки для специфических задач: массового поиска паттернов, эмуляции отдельных функций, генерации патчей. В IDA — через плагины и `idapython`.

Типичный гибридный workflow: в GUI ты видишь структуру и находишь интересную функцию; скриптом на Capstone/Unicorn ты её «прогоняешь» с разными входами и получаешь точные результаты. Так сочетаются интуиция аналитика и точность автоматизации.

## Шаг 12: производительность и масштаб

Для одного бинарника хватает ручного анализа, для тысяч нужен конвейер. Capstone быстр, но для больших объёмов код пишут с учётом производительности: читать только нужные секции, кешировать разбор, распараллеливать по функциям. Unicorn медленнее реального CPU, поэтому эмулируют только целевые функции, а не весь бинарник.

Масштабные задачи: кластеризация малвари по сигнатурам кода, автоматический поиск уязвимых паттернов, массовое патчение. Здесь библиотечный стек — обязательный инструмент.

## Шаг 13: от эмуляции к фаззингу

Unicorn — основа для «эмуляционного фаззинга»: ты запускаешь функцию в эмуляторе и подаёшь случайные/мутированные входы, отслеживая падения. Это быстрее и безопаснее, чем реальный запуск, и позволяет покрывать недоступные пути. Так находят уязвимости в парсерах без реальной сети.

Дополнительно эмулятор позволяет «снимать» покрытие: какие блоки функции исполнялись при данном входе. Это замыкает цикл «фаззинг → покрытие → новые входы», то есть coverage-guided fuzzing на базе эмуляции.

## Шаг 14: закрепление и вывод

Наш `engine.elf` показал стек: Capstone (дизасм), Keystone (сборка патча), Unicorn (эмуляция). Мы увидели, почему библиотеки надёжнее парсинга текста, и как собрать конвейер.

Главный вывод: собственные инструменты на Python превращают реверс из ручной работы в автоматизируемый процесс. Освоив Capstone/Keystone/Unicorn, ты можешь писать анализаторы под свои задачи — от поиска проверок до эмуляционного фаззинга.

## Разбор глубже: как писать плагины для анализаторов

Плагин для IDA/Ghidra на базе Capstone решает конкретную задачу: пометить функции, найти паттерны, собрать статистику. Каркас: получить список функций из API анализатора, для каждой прочитать байты, прогнать через Capstone, применить условие, записать результат (комментарий, переименование, отчёт).

Пример задачи: найти все функции, где есть сравнение с константой-лицензией. Плагин перебирает функции, ищет `cmp` с нужным значением, помечает найденные. За секунды вместо часов ручного поиска.

Такой плагин — «одноразовый инструмент» под задачу, но пишется за полчаса и экономит дни.

## Разбор глубже: Keystone для патчинга в бою

Патчинг через Keystone: собрать нужные инструкции, вычислить их длину, заменить соответствующий диапазон байт в файле (с учётом выравнивания — свободное место заполняют `nop`). Для ELF/PE есть библиотеки записи (`lief`), которые пересчитывают контрольные суммы и структуру.

Типичный патч — «сделать функцию всегда возвращающей true»: заменить пролог на `mov eax,1; ret`. Или «убрать проверку»: заменить условный переход на `nop`-ы.

Важно: патч должен сохранять выравнивание и не ломать CFG/CET (см. урок про CFI). Иначе бинарник упадёт.

## Разбор глубже: Unicorn для извлечения алгоритмов

Unicorn незаменим, когда нужно «вытащить» алгоритм: крипто-функцию, генератор ключей, хеш. Схема: подготовить память и регистры, запустить функцию, снять результат, повторить с разными входами, по результатам восстановить логику (или просто вызвать функцию напрямую из скрипта).

Часто это быстрее, чем реверсить алгоритм: ты просто используешь оригинальную реализацию как «чёрный ящик» через эмуляцию.

Так решают задачи, где нужен результат (расшифровать конфиг), а не понимание алгоритма.

## Что мы теперь знаем

- Capstone — дизассемблер как библиотека; даёт структурированные инструкции.
- Keystone — ассемблер как библиотека; нужен для патчей.
- Unicorn — эмулятор CPU; безопасно исполняет код изолированно.
- Вместе они образуют конвейер «прочитать → пропатчить → эмулировать».
- Парсить вывод objdump хрупко; библиотеки дают точные структуры.
