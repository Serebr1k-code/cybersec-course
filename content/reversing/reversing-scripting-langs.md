## Вопрос, с которого всё начинается

Тебе дали файл `challenge.pyc` — скомпилированный Python. Исходника нет, но
логику надо понять: что за пароль он проверяет? Скриптовые языки (Python, Lua,
Perl, Ruby) не компилируются в машинный код — они исполняются интерпретатором,
а на диске лежит **байткод**. Реверс такого байткода — отдельный навык: он
проще машинного кода, но у каждого языка свой формат и свои инструменты.

## Наш пример

Возьмём `challenge.pyc`. Это скомпилированный Python-модуль. Сначала попробуем
запустить его с разными аргументами:

```
$ python3 challenge.py pyth0n!! 
OK
$ python3 challenge.py wrong
WRONG
```

Значит, внутри есть проверка. Посмотрим на байткод через встроенный модуль
`dis` (загрузим `.pyc` и дизассемблируем функцию `check`):

```
$ python3 -c "import dis,marshal; ...; dis.dis(check)"
  4           LOAD_GLOBAL              1 (len + NULL)
              LOAD_FAST_BORROW         0 (s)
              CALL                     1
              LOAD_SMALL_INT           8
              COMPARE_OP             119 (bool(!=))
              POP_JUMP_IF_FALSE        3 (to L1)
  5           LOAD_CONST               1 (False)
              RETURN_VALUE
  6   L1:     LOAD_GLOBAL              2 (all)
              ...
              CALL                     0
```

Читаем по-человечески: если `len(s) != 8` — вернуть `False`; иначе вызвать
`all(...)` по генератору. В Python 3.13+ байткод изменился (появились
`LOAD_FAST_BORROW`, `LOAD_SMALL_INT`, `RESUME`), но смысл читается.

## Шаг 1: структура .pyc

`.pyc` — это сериализованный код:

- **магия** (4 байта) + версия формата;
- **бит-флаги**;
- метка времени/хэш исходника;
- **размер** кода;
- **маршализованный** (`marshal`) объект кода (`code object`).

Именно поэтому `.pyc` версионно-зависим: байткод Python 3.11 не совпадает с
3.13. При реверсе первым делом определяют версию — по «магическому» числу.
Затем загружают `marshal` и дизассемблируют `dis`.

## Шаг 2: читаем константы и генератор

В коде видна константа `TARGET` — массив байт. Проверка устроена как генератор:
`all((ord(c) ^ 0x42) == t for c, t in zip(s, TARGET))`. Значит, каждый символ
ввода XOR-ится с `0x42` и сравнивается с байтом из `TARGET`. Решим:

```python
TARGET = bytes([0x32, 0x3b, 0x36, 0x2a, 0x72, 0x2c, 0x63, 0x63])
print("".join(chr(t ^ 0x42) for t in TARGET))
```

```
pyth0n!!
```

Мы получили пароль `pyth0n!!` — и он действительно подходит. Заметь: байткод
дал и структуру (длина 8, XOR), и данные (`TARGET`).

## Шаг 3: декомпиляторы Python

Читать байткод вручную полезно, но долго. Есть декомпиляторы:

- **decompyle3 / uncompyle6** — для старых версий Python;
- **pycdc** (Decompyle++) — поддерживает более новые;
- **pylingual.io** — онлайн-декомпилятор.

Они возвращают почти исходный код. Важно: чем новее Python, тем чаще
декомпилятор отстаёт, и тогда приходится читать `dis`-вывод (как мы).
Версию можно понизить, если есть доступ к тому же коду — но обычно просто
работают с `dis`.

## Шаг 4: Lua — luac и unluac

**Lua** компилируется в байткод утилитой `luac` (файл начинается с сигнатуры
`\x1bLua`). Декомпиляторы:

- **luadec** — для Lua 5.1/5.2;
- **unluac** — Java-инструмент, поддерживает несколько версий.

Lua часто используют в играх (аддоны, логика) и в роутерах, поэтому её байткод
встречается в реверсе игр и прошивок.

## Шаг 5: Perl и Ruby

- **Perl** не имеет стабильного байткода на диске — скрипты обычно текстовые.
  Обфускацию делают на уровне исходника (`Acme::Bleach`), а не компиляции.
- **Ruby** компилируется в **YARV**-байткод (внутри `.rbc` или в памяти).
  Инструменты: `ruby -e 'puts RubyVM::InstructionSequence...'` для дизассемблера,
  `rbdec` для декомпиляции.

Общий принцип одинаков: понять, где лежит байткод, дизассемблировать, найти
константы и сравнения.

## Шаг 6: где прячут логику скриптов

Скриптовые бэкдоры и малварь прячут код так:

- **Обфускация исходника** — `eval` от Base64/gzip-блоба, вложенные строки.
- **Компиляция в байткод** — `.pyc` без исходника.
- **Пакеры** (PyInstaller, py2exe) — код упакован в архив внутри исполняемого
  файла; его распаковывают (`pyinstxtractor`) и получают `.pyc`.
- **Загрузка кода из сети** — `exec(requests.get(url).text)`.

Для анализа: распаковать, достать `.pyc`/байткод, дизассемблировать, найти
ключевые вызовы (сеть, файлы, выполнение команд).

Отдельно стоит **обфускация через eval**. Часто исходник выглядит так:
`exec(__import__('base64').b64decode('...'))`. Первый шаг — раскрутить
декодирование, получить следующий слой, и так по цепочке (как с конфигом
малвари). Иногда слоёв несколько: Base64 → zlib → ещё Base64. Терпение и
последовательная раскрутка быстро приводят к читаемому коду.

## Шаг 7: практический маршрут

1. **Определить язык и версию** (сигнатура, магия).
2. **Достать байткод** (если упакован — распаковать).
3. **Дизассемблировать** (`dis`, `luac -l`, YARV).
4. **Найти константы и проверки**.
5. **Восстановить логику** или решить проверку (XOR, хэш, сравнение).

## Шаг 8: как выглядит байткод Lua

Lua-байткод начинается с сигнатуры `\x1bLua` (escape + «Lua»), за которой идёт
версия формата. Дальше — заголовок, список констант и функции. Дизассемблировать
можно так:

```
$ luac -l -l challenge.luac
main <challenge.lua:0,0> (5 instructions)
    1   GETTABUP   0 0 0   ; _ENV "print"
    2   LOADK      1 1     ; "access"
    ...
```

Видно те же элементы, что и в Python: загрузка констант (`LOADK`), вызовы,
сравнения. Если есть исходник — `luac -l` покажет, во что он компилируется; если
нет — читаем байткод и восстанавливаем логику. Для Lua 5.1/5.2 обычно берут
**luadec**, для более новых — **unluac**.

## Шаг 9: Ruby (YARV) и Perl

**Ruby** компилирует код в байткод **YARV** (Yet Another Ruby VM). Внутри
процесса его можно дизассемблировать:

```ruby
puts RubyVM::InstructionSequence.compile(File.read("x.rb")).disasm
```

Вывод похож на ассемблер: `opt_plus`, `putobject`, `branchif`. Декомпилятор —
`rbdec` (для части версий). Ruby часто встречается в веб-приложениях и в
инфраструктуре (Chef/Puppet).

**Perl** не сохраняет байткод на диск: скрипты исполняются из исходника. Поэтому
«реверс Perl» — это чаще разбор **обфусцированного исходника**: длинных строк
из символов, `eval` от собранных кусков, `pack`/`unpack`. Обфускаторы вроде
`Acme::Bleach` делают текст нечитаемым, но обратимым.

## Частые вопросы

**Декомпилятор не поддерживает мою версию Python.** Понизь версию интерпретатора
(если код не использует новые фичи) или читай `dis`-вывод вручную. Иногда
помогает `xdis` — кросс-версионный дизассемблер.

**pyc не загружается в marshal.** Проверь магию: возможно, это не Python или
другая версия. Иногда .pyc обёрнут (например, в PyInstaller-архив).

**Как найти проверку в большом pyc?** Ищи строки (`strings`), вызовы `input`,
`==`, `hashlib`, а затем смотри дизассемблер вокруг них.

**Lua-файл «не той» версии.** Версия байткода строго привязана к версии Lua
(5.1 vs 5.3 несовместимы). Определи версию по заголовку и возьми подходящий
декомпилятор.

## Что мы теперь знаем

- `.pyc` — сериализованный байткод Python (магия + marshal-объект), версионно
  зависимый.
- В нашем `challenge.pyc` проверка: `len(s)==8` и `ord(c) ^ 0x42 == TARGET[i]`;
  решение — `pyth0n!!`.
- Для Python есть декомпиляторы (pycdc, uncompyle6), но новые версии часто
  приходится читать через `dis`.
- Lua компилируется в `luac`-байткод (сигнатура `\x1bLua`), декомпилируется
  luadec/unluac; Ruby — в YARV.
- Пакеры (PyInstaller) распаковывают (`pyinstxtractor`), после чего получают
  `.pyc`.
