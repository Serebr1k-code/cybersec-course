## Вопрос, с которого всё начинается

Ты нашёл условный переход, который решает «правильный ключ или нет», и
патчишь его — один байт, всё должно работать. Но программа... по-прежнему
ругается. Или вообще отказывается стартовать. Причина часто в **проверке
целостности**: программа считает хэш собственного кода и сравнивает с эталоном.
Любая правка байта — и хэш не сходится. Как это устроено и как с этим
бороться?

## Наш пример

Возьмём программу `ac`, которая считает хэш своего же кода и хэш отдельного
массива-«стража»:

```
$ ./ac
code hash  = 0x57548bf89fc254f5
guard hash = 0x20d4d8cd1c12f50
```

Внутри она делает примерно следующее:

```c
static unsigned long sum(const unsigned char *p, unsigned long n){
    unsigned long s = 0;
    for (unsigned long i = 0; i < n; i++) s = s * 131 + p[i];
    return s;
}
int main(void){
    unsigned long h = sum((const unsigned char*)main, 64);   // хэш первых 64 байт main
    printf("code hash  = 0x%lx\n", h);
    printf("guard hash = 0x%lx\n", sum(guard, 8));           // хэш массива guard
    return 0;
}
```

`sum` — простой **свёртывающий хэш** (rolling hash): каждый байт умножается на
базу 131 и прибавляется к накопленной сумме. Такой хэш чувствителен к любому
изменению: поменялся хоть один байт — изменилось итоговое число.

## Шаг 1: меняем один безобидный байт

Попробуем обмануть проверку. В `main` есть инструкция `mov eax,0` — она лишь
сообщает `printf`, что векторных аргументов нет. Семантически она
несущественна, но находится внутри хэшируемых 64 байт. Поменяем её последний
байт (иммедиат) с `0x00` на `0x01`:

```python
import lief
b = lief.parse("ac_tweak")
off = b.virtual_address_to_offset(0x4011a7)   # -> 0x11a7
with open("ac_tweak","r+b") as f:
    f.seek(off); f.write(bytes([0x01]))
```

Запускаем:

```
$ ./ac_tweak
code hash  = 0xab61761583287e86
guard hash = 0x20d4d8cd1c12f50
```

Хэш кода изменился (`0x5754...` → `0xab61...`), хотя программа работает
нормально. Именно это и заметит защита: она сравнит вычисленный хэш с
зашитым эталоном и поймёт, что код правили.

## Шаг 2: меняем данные-«страж»

Второй вариант защиты — хэшировать не код, а специальный **массив-маркер**,
который патч должен был бы перезаписать. В `ac` есть `guard[8]` с байтами
`DE AD BE EF CA FE BA BE`. Изменим их — и хэш стража изменится:

```
$ ./ac_patched
code hash  = 0x57548bf89fc254f5
guard hash = 0x321ed4784a5c6
```

`guard hash` другой, `code hash` тот же. Смысл приёма: защита кладёт «магические»
байты в место, которое эксплойт затирает, — и любая попытка обойти проверку
меняет страж.

## Шаг 3: почему одного патча мало

Разберём типичную схему самопроверки:

1. Посчитать хэш участка кода (или всего `.text`).
2. Сравнить с эталоном, зашитым в бинарник.
3. Если не совпало — испортить работу (выйти, выдать неверный результат,
   вызвать краш).

Проблема в том, что **сам код сравнения** — тоже часть кода. Проверок может
быть несколько, они могут вызываться из разных мест, хэшировать разные участки
и работать в цикле. Патч одного байта в защите ломает хэш самой защиты, и
программа уходит в «плохую» ветку.

## Шаг 4: как обходить проверки целостности

Стратегий несколько, от простой к сложной:

- **Патчить саму проверку.** Найти сравнение хэшей (`cmp`) и заменить условный
  переход. Но тогда код проверки изменится — если он тоже хэшируется, снова
  не сойдётся. Нужно найти и нейтрализовать **все** проверки.
- **Пересчитать и вписать эталон.** Если защита сравнивает вычисленный хэш с
  константой, можно посчитать хэш уже патченного файла и заменить константу.
  Работает, пока проверок не слишком много и они не перемешаны.
- **Хук функции проверки.** В отладчике — заставить функцию всегда возвращать
  «всё хорошо» (как мы делали с `ptrace`). В рантайме — перехватить вызов.
- **Остановить проверку до старта.** Иногда проверка запускается в конструкторе
  или по таймеру — тогда её просто отключают, убрав вызов.
- **Динамический дамп.** Дать программе самой распаковаться/расшифроваться и
  снять уже «живой» образ из памяти — тогда хэш посчитается по правильным
  байтам.

## Шаг 5: защита от патча через стража

Отдельный класс — **анти-патч на страже данных**. Байты `DE AD BE EF ...` не
случайны: это маркеры, которые легко заметить и которые затираются при грубом
патче. Если защита обнаружит, что страж изменён, она делает вывод «бинарник
правлен» и портит логику. Поэтому при анализе смотрят не только на код
проверки, но и на «мёртвые» данные рядом: они могут оказаться стражем.

## Шаг 6: а что если хэшируется весь `.text`

Самая жёсткая форма — хэшировать всю секцию кода целиком. Тогда любой патч
кода виден. Обходы:

- Патчить **в памяти**, после того как проверка уже прошла (например, через
  хук на более поздний момент). Файл на диске не меняется.
- Перехватить функцию чтения/хэширования и подсунуть эталонные байты.
- Найти эталонный хэш в данных и подменить его на хэш патченного файла.

Главное — понять, **что именно** хэшируется (какой диапазон, в какой момент),
и уже потом выбирать обход. Для этого удобны watchpoints на область памяти
эталона: сработает — значит, нашли момент сравнения.

## Шаг 7: проверки на уровне секций и заголовков

Хэшировать весь код не обязательно — можно проверять только **заголовки** или
**таблицы**. Частые приёмы:

- **Контрольная сумма секции.** Правка байта в `.text` меняет сумму, а правка
  где-то ещё — нет. Защита знает, какую секцию трогать нельзя.
- **Проверка таблицы импортов.** Если патч добавил вызов чужой функции, IAT
  изменилась — это тоже замечают.
- **Проверка PE-заголовков / ELF-заголовков.** Правка точки входа или размера
  секции сразу видна.

Поэтому при патче важно менять **минимум** и там, где защита не смотрит: лучше
внутри уже существующей инструкции, чем добавлять новую. А иногда проще не
патчить файл, а перехватить вызов в рантайме — тогда ни байты, ни заголовки не
меняются вовсе.

## Частые вопросы

**Как быстро найти все проверки целостности?** Ищи вызовы функций с циклами
свёртки и константы-эталоны рядом; смотри перекрёстные ссылки на адрес `main`
или начала `.text` — оттуда тянутся хэширующие функции.

**Патч «сработал», но результат неверный.** Возможно, есть вторая проверка,
срабатывающая позже (по таймеру или в другом потоке). Ставь точки на маркеры и
смотри стек.

**Можно ли вообще не патчить?** Да — пересчитай хэш и подмени эталон, или
хукни функцию сравнения. Это «чище», чем править код защиты.

## Что мы теперь знаем

- Проверка целостности считает хэш кода или данных и сравнивает с эталоном;
  свёртывающий хэш вроде `s = s*131 + byte` чувствителен к любому байту.
- Один безобидный изменённый байт в `main` меняет `code hash`, а правка
  массива-стража меняет `guard hash` — это два разных подхода.
- Простой патч проверки может сам изменить её хэш, поэтому нужно нейтрализовать
  **все** проверки.
- Обходы: пересчитать эталон, хук функции проверки, патч в памяти после
  проверки, динамический дамп.
- Watchpoint на область эталона помогает найти момент сравнения.
