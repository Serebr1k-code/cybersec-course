## Вопрос, с которого всё начинается

Ты сдампил флеш роутера и получил файл `u-boot.bin`. Это не ядро и не приложение — это **загрузчик**, который первым исполняется на устройстве. Как его разобрать и что в нём искать?

## Наш пример

Смотрим на файл:

```
$ file u-boot.bin
u-boot.bin: data
```

`file` не распознал формат — это сырой образ. Заглянем в начало:

```
$ xxd -l 16 u-boot.bin
00000000: 2705 1956 0000 0000 0000 0000 0000 0000  '..V............
```

Байты `27 05 19 56` — это **магическая сигнатура uImage** (в big-endian). Так начинается образ, который U-Boot умеет загружать. Разберём структуру.

## Шаг 1: что такое загрузчик

**Загрузчик** (bootloader) — первая программа, которая исполняется после включения. Он инициализирует железо (память, часы, консоль), загружает ядро ОС и передаёт ему управление. Популярные загрузчики embedded: **U-Boot**, **coreboot**, **Barebox**, **RedBoot**.

Они интересны реверсеру потому, что: содержат консоль (часто с паролем), переменные окружения с адресами и ключами, и живут в отдельной флеш-области, которую можно перезаписать.

## Шаг 2: контейнеры образов

U-Boot использует формат **uImage**: 64-байтовый заголовок с магией `0x27051956`, за которым идут сжатые данные. В заголовке: время создания, размер, адрес загрузки, адрес входа, контрольная сумма и имя образа.

Кроме uImage встречается **FIT** (Flattened Image Tree) — образ в формате device-tree, где описаны несколько компонентов (ядро, ramdisk, DTB). Разбор FIT требует понимания DTB (device tree blob).

## Шаг 3: environment — переменные загрузчика

U-Boot хранит настройки в **environment** — блоке переменных: `bootargs` (аргументы ядра), `bootcmd` (что загружать), `ipaddr`, `serverip`. Их удобно читать строками:

```
$ strings -n 5 u-boot.bin | grep -E 'bootargs|bootcmd'
bootargs=console=ttyS0 root=/dev/mtdblock2
bootcmd=bootm 0x80000
```

`bootargs` показывает корневую ФС и консоль, `bootcmd` — команду загрузки. По ним ты понимаешь, как система стартует, и где искать дальше.

## Шаг 4: консоль и её защита

У U-Boot есть последовательная консоль (UART). Часто она защищена паролем или скрыта. Признаки в образе: строки `U-Boot`, приглашение `=>`, переменная `bootdelay` (задержка перед автозагрузкой), `preboot`. Обход: замкнуть загрузочные пины, изменить environment в дампе, найти пароль в строках.

Консоль — это фактически shell с root-правами до загрузки ядра, поэтому её защита критична.

## Шаг 5: точки для инъекций

Реверс загрузчика ищет, куда можно внедриться: незащищённая консоль, подписываемый/неподписываемый образ ядра, `bootcmd`, читающий с внешнего носителя, доверие к unsquashfs-образу. Если ядро не проверяет подпись, ты можешь подменить его своим — это классический путь получения контроля над устройством.

## Шаг 6: артефакт

Извлечём версию и артефакт:

```
$ strings -n 5 u-boot.bin | head
U-Boot 2023.07 (Aug 01 2023)
bootargs=console=ttyS0 root=/dev/mtdblock2
nto{ub00t_env_b00targs_r3v}
```

Версия загрузчика важна: по ней ищут известные уязвимости и сравнивают с апстримом.

## Шаг 7: цепочка загрузки от ROM до ОС

Понимание загрузки помогает найти точку вмешательства. Типовая цепочка на встраиваемом устройстве: **BootROM** (неизменяемый код в чипе) → **SPL/первичный загрузчик** (инициализирует DRAM) → **U-Boot** (полноценный загрузчик с консолью) → **ядро Linux** → **initramfs/rootfs** → **init**. Каждая стадия проверяет следующую (или нет — вот где ошибки).

Если подпись не проверяется на каком-то шаге, ты можешь подменить образ. Классические слабости: BootROM без подписи (или с отладочным режимом), U-Boot без проверки ядра, ядро без проверки rootfs. Анализ цепочки показывает, где проще всего внедриться.

## Шаг 8: разбор образов и device tree

U-Boot и ядро описываются **device tree** (DTB) — структурой, которая говорит ядру, какое железо есть и по каким адресам. Разбор DTB (`dtc -I dtb -O dts`) даёт карту периферии: UART, Ethernet, SPI, GPIO. Это бесценно для реверса: ты знаешь, с каким железом работает код.

Образы (`uImage`, FIT) содержат несколько компонентов. `binwalk` рекурсивно извлекает их, `dumpimage`/`mkimage` (из U-Boot tools) разбирают uImage. FIT — это DTB с описанием образов, его читают тем же `dtc`.

## Шаг 9: типовые уязвимости загрузчиков

Исторические уязвимости U-Boot связаны с: переполнениями в парсерах (env, DHCP, TFTP), обходом проверки подписи, небезопасными умолчаниями (пустой пароль консоли). Также часты слабости в конфигурации: `bootdelay` с возможностью прервать автозагрузку, сетевые загрузки без аутентификации.

Практический сценарий атаки: получить доступ к UART → прервать загрузку → изменить environment (например, `bootargs` на `init=/bin/sh`) → получить shell. Защита — отключить консоль, включить проверку подписи, зафиксировать environment.

## Шаг 10: закрепление и вывод

Наш `u-boot.bin` показал структуру: магия uImage, заголовок, environment (`bootargs`, `bootcmd`), строки версии. Мы разобрали, где искать точки инъекций.

Главный вывод: загрузчик — первая и самая привилегированная программа на устройстве. Его разбор даёт контроль над стартом системы, а слабости в цепочке доверия — путь к полному контролю над устройством.

## Разбор глубже: подпись и цепочка доверия

Современные устройства используют **verified boot**: каждая стадия проверяет подпись следующей по встроенному публичному ключу (root of trust). Если хоть одна подпись не проверяется, цепочка рвётся, и устройство можно скомпрометировать.

Признаки проверки подписи: таблицы ключей в образе, вызовы крипто-функций (`rsa_verify`, `sha256`), строки `signature`, `key`. Отсутствие этих признаков — «зелёный свет» для подмены.

Анализ цепочки: для каждой стадии определи, проверяется ли подпись. Слабое звено — точка входа для атаки.

## Разбор глубже: environment как вектор атаки

Environment U-Boot — не только настройки, но и вектор атаки. Переменная `bootargs` может передать ядру `init=/bin/sh` (получить root-shell), `bootcmd` — загрузить произвольный образ, `preboot` — выполнить команды до загрузки. Изменение environment (в дампе или через консоль) даёт контроль над стартом.

Защита: подпись environment, запрет записи, отключение консоли. Часто этого нет — отсюда популярность атак через U-Boot.

## Разбор глубже: извлечение прошивки

Прошивку получают: с флеша (выпаивание/SPI-программатор), через консоль U-Boot (команды `sf read`), через обновление (OTA-файл), из вендорского пакета. Каждый путь даёт образ, который затем разбирают `binwalk`/`strings`/дизассемблером.

Имея образ, ты можешь найти ключи, пароли, уязвимые сервисы. Часто в прошивке остаются отладочные функции и тестовые аккаунты — наследие разработки.

## Что мы теперь знаем

- Загрузчик — первая программа; U-Boot/coreboot/Barebox — популярные.
- uImage — контейнер с магией `0x27051956` и 64-байтовым заголовком.
- Environment хранит `bootargs`/`bootcmd` и другие переменные.
- Консоль U-Boot — фактически root-shell; её защищают паролем.
- Точки инъекций: неподписанный образ, доступная консоль, внешний носитель.
