## Вопрос, с которого всё начинается

Ты уже умеешь открыть бинарник в дизассемблере и прочитать ассемблер. Но бывает так:
функция на 200 инструкций, и глазами её разбирать — полдня. Знакомо чувство «я вижу
инструкции, но не вижу смысл»?

Вот тут и появляются LLM. Они не запускают бинарь и не знают адресов — но они отлично
превращают «кашу из ассемблера» в человеческое описание. В этом уроке мы возьмём один
конкретный бинарник, руками получим его ассемблер, отдадим модели — и **проверим** её
гипотезу реальным запуском. Именно проверка отличает инженера от того, кто верит чат-боту.

## Наш пример

Соберём подопытный бинарник `xorcheck` (исходник лежит рядом, но смотреть мы его не будем —
сделаем вид, что его нет):

```c
/* check(): сравнивает ввод с зашифрованной таблицей */
```

Запускаем — он просит ключ и на неправильный отвечает `Wrong.`

```bash
$ printf 'hello\n' | ./xorcheck
Enter key: Wrong.
```

Первая разведка — `file` и `strings`:

```bash
$ file xorcheck
xorcheck: ELF 64-bit LSB executable, x86-64, ... not stripped

$ strings -n 5 xorcheck | grep -iE 'key|correct|wrong'
Enter key:
Correct!
Wrong.
```

Строк с паролем нет — только сообщения. Значит, ключ не лежит в открытом виде, его
где-то вычисляют. Идём в дизассемблер.

## Шаг 1: достаём ассемблер функции проверки

Имена сохранены (`not stripped`), поэтому сразу видим функцию `check`:

```bash
$ nm xorcheck | grep -iE ' check| main'
0000000000401166 T check
00000000004011da T main

$ objdump -d --no-show-raw-insn --disassemble=check xorcheck
0000000000401166 <check>:
  40116e:	mov    %rdi,-0x18(%rbp)      # первый аргумент (ввод) кладём на стек
  401172:	mov    -0x18(%rbp),%rax
  401179:	call   401040 <strlen@plt>    # strlen(in)
  40117e:	mov    %rax,-0x8(%rbp)
  401182:	cmpq   $0x10,-0x8(%rbp)       # длина == 16 ?
  401187:	je     401190 <check+0x2a>
  401189:	mov    $0x0,%eax              # нет -> return 0
  4011a9:	xor    $0x5a,%eax              # байт ввода XOR 0x5a
  4011b4:	movzbl 0x402010(%rax),%eax    # байт из таблицы по адресу 0x402010
  4011be:	cmp    %eax,%edx              # сравнение
  4011d3:	mov    $0x1,%eax              # всё совпало -> return 1
```

Читаем по-человечески: функция берёт строку, требует ровно 16 символов, каждый символ
**XOR-ит с `0x5a`** и сравнивает с байтом из таблицы по адресу `0x402010`. Слово
«XOR» (исключающее ИЛИ) — это побитовая операция: `a ^ 0x5a`; дважды применив её, получаешь
исходный байт, поэтому она удобна как простейшее «шифрование». Чтобы получить ключ, надо
взять таблицу и XOR-нуть её обратно с `0x5a`.

Посмотрим таблицу:

```bash
$ objdump -s -j .rodata xorcheck
 402010 3b1c283e 112d0a3c 3a132c2e 1238112f  ;.(>.-.<:.,..8./
```

16 байт: `3b 1c 28 3e 11 2d 0a 3c 3a 13 2c 2e 12 38 11 2f`. У нас уже есть всё, чтобы
посчитать ответ. Но именно здесь удобно позвать LLM — пусть объяснит и напишет декодер.

## Шаг 2: отдаём ассемблер модели

Ключевой приём: **даём контекст и требуем структурированный ответ**. Плохой промпт —
«что делает этот код?». Хороший:

```
Контекст: x86-64 ELF, not stripped, функция check(char*).
Задача: объясни логику по шагам и напиши Python-декодер ключа.
Не выдумывай адреса; если не уверен — скажи прямо.
Ассемблер:
<вставляем вывод objdump>
```

Хороший ответ модели выглядит примерно так:

> Функция проверяет: длина ввода = 16; затем для `i` от 0 до 15 байт `in[i] ^ 0x5a`
> сравнивается с таблицей по `0x402010`. Значит ключ = каждый байт таблицы XOR 0x5a:
> ```python
> table = bytes.fromhex("3b1c283e112d0a3c3a132c2e1238112f")
> print(bytes(b ^ 0x5a for b in table))
> ```

Обрати внимание: модель **не дала адрес** и не пыталась угадать флаг — она вывела формулу
из нашего кода. Это правильный режим работы.

## Шаг 3: проверяем гипотезу — обязательно

Модель могла ошибиться (например, спутать порядок байт). Прогоняем её код сами:

```bash
$ python3 -c 't=bytes.fromhex("3b1c283e112d0a3c3a132c2e1238112f"); print(bytes(b^0x5a for b in t))'
b'aFrdKwPf`IvtHbKu'
```

Теперь проверим догадку на самом бинарнике:

```bash
$ printf 'aFrdKwPf`IvtHbKu\n' | ./xorcheck
Enter key: Correct!
```

Сработало. Мы прошли путь «ассемблер → объяснение LLM → декодер → проверка» и получили ключ.
Обрати внимание: финальный шаг — **запуск**. Без него мы бы не знали, правда ли это.

## Шаг 4: где LLM помогает, а где врёт

LLM — ускоритель гипотез, а не источник истины. Что она делает хорошо:

- объясняет функцию на ассемблере/псевдо-C и предлагает осмысленные имена;
- распознаёт знакомые алгоритмы по константам (AES, CRC32, base64);
- пишет декодер/парсер по описанию формата;
- генерирует скрипты для Ghidra/IDA/r2.

Где модели опасны:

- **выдуманные адреса и символы** — «помнит» похожий бинарник и приписывает чужие функции;
- **уверенные ошибки** в криптоанализе и оценке рантайма;
- **не видит динамику** — она не запускает код;
- **утечка** — отправка приватного/malware-образца в облако нарушает NDA.

Правило простое: **гипотеза от LLM закрывается инструментом** — запуском, `gdb` или
символьным исполнением. Для секретных образцов используй локальную модель (Ollama, LM Studio),
а не облако.

## Шаг 5: промпт-инжиниринг и автоматизация

Качество ответа зависит от контекста, который ты даёшь. Три рабочих шаблона, которые стоит
держать под рукой:

```
# 1) Объяснение функции
Ты — реверс-инженер. Архитектура: x86-64, компилятор GCC -O0.
Ниже ассемблер функции. Объясни назначение, входы/выходы, побочные эффекты.
Не выдумывай адреса; если данных мало — скажи.
<objdump -d --disassemble=check>

# 2) Генерация декодера
Вот алгоритм кодирования. Напиши Python-функцию decode(data: bytes) -> bytes,
обратную к нему. Учти порядок байт и границы. Приведи пример вызова.
<ассемблер>

# 3) Восстановление структуры
Дана функция парсинга. Опиши структуру сообщения: смещения, размеры, типы полей.
Верни таблицу поле|смещение|размер|тип.
<декомпилированный C>
```

Ключевые приёмы: давать архитектуру и уровень оптимизации; просить структурированный вывод
(JSON или таблицу); разбивать длинные функции на части, потому что контекст модели ограничен.
И главное — просить модель **явно отмечать неуверенность**, тогда ты сразу видишь, где надо
перепроверить руками.

Для батч-обработки (много функций сразу) LLM встраивают скриптом: собрать псевдо-C каждой
функции, отправить модели, применить предложенные имена. Такой скрипт для IDA выглядит
примерно так:

```python
import idautils, idc, ida_hexrays
for ea in idautils.Functions():
    cf = ida_hexrays.decompile(ea)
    if not cf:
        continue
    name, desc = ask_local_llm(str(cf))   # твой вызов локальной модели
    idc.set_name(ea, name, idc.SN_NOWARN)
    idc.set_func_cmt(ea, desc, 0)
```

Обязательно логируй пары «адрес → предложенное имя»: сомнительные переименования нужно уметь
откатить. И помни: для приватных и malware-образцов такой скрипт должен звать **локальную**
модель, а не облачный API.

## Что мы теперь знаем

- LLM ускоряет реверс там, где нужен **текстовый смысл**: объяснить, назвать, написать скрипт.
- Промпт должен давать контекст (архитектура, компилятор) и требовать явно указывать неопределённость.
- Любую гипотезу модели **проверяем реальным запуском** — как мы проверили ключ на `xorcheck`.
- Для приватных образцов — только локальные модели.

## Куда дальше

Мы разобрали одну функцию и ускорили её понимание моделью. Но реальный реверс начинается не
с одной функции, а с **образа целиком** — и часто цель лежит не в отдельном ELF, а внутри
контейнера. В следующем уроке мы возьмём Docker-образ, распакуем его слои и найдём бинарник
внутри — а пока главное запомни: **LLM предлагает, инструмент подтверждает.**

## Где пригодится

- **CTF Reversing:** быстрое объяснение незнакомой функции, генерация декодера.
- **Malware analysis:** документирование кода — но только локальной моделью.
- **Bug bounty / vuln research:** триаж нативных приложений и генерация скриптов.
- **Работа (RE-команда):** батч-аннотация функций, ускорение первичного разбора.
