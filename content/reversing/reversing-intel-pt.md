## Вопрос, с которого всё начинается

Тебе нужно узнать, по какому пути идёт программа: какие ветки она выбирает, какие функции вызывает. Отладчик это умеет, но он **замедляет** программу в сотни раз и **заметен** — анти-отладка его ловит по точкам останова. DBI тоже инструментирует код, а значит, может быть обнаружен.

А хочется наблюдать за потоком управления **сбоку**: без остановок, без модификации кода, почти без замедления. Такую возможность даёт процессор — технология **Intel Processor Trace (PT)**. Разберём, как она устроена и как получить трассу.

## Наш пример

Возьмём маленькую `tiny` с функцией `compute(6)`, в которой есть цикл и ветвление:

```c
int compute(int x) {
    int acc = 0;
    for (int i = 0; i < x; i++) {
        if (i % 2) acc = add(acc, i);
        else       acc += 2 * i;
    }
    return acc;
}
```

Мы хотим увидеть поток исполнения этой функции — какие переходы и вызовы реально произошли.

## Что такое Intel PT

PT — механизм в процессорах Intel (начиная с Broadwell). Он **не записывает каждую инструкцию**, а кодирует поток управления: какие ветвления были взяты, куда ведут вызовы и возвраты, где случились косвенные переходы. Зная бинарник (его код), декодер восстанавливает полную последовательность исполненных инструкций.

Запись идёт в буфер в памяти компактными «пакетами»:

- **TNT (Taken Not Taken)** — биты, указывающие, какие условные переходы были взяты;
- **TIP (Target IP)** — целевой адрес косвенного перехода, вызова или возврата;
- **PIP/FUP** — адрес начала трассировки и её границы.

Предсказуемые ветвления (условный переход с известной целью) в потоке опускаются — декодер восстанавливает их по коду. Поэтому трасса на порядки короче полной инструкционной. Включается PT через MSR (`IA32_RTIT_CTL`), вывод пишется через **ToPA** (Table of Physical Addresses), а фильтры (`IA32_RTIT_ADDR0/1`, CR3) позволяют трассировать только нужный диапазон адресов или процесс.

## Проверяем поддержку на реальной машине

Прежде чем что-то записывать, убедимся, что процессор и ядро умеют PT. На нашем стенде это так:

```
$ grep -o -m1 'pt' /proc/cpuinfo
pt
$ cat /sys/bus/event_source/devices/intel_pt/type
12
$ ls /sys/bus/event_source/devices/intel_pt/caps/
cr3_filtering  event_trace  ip_filtering  mtc  num_address_ranges
payloads_lip   psb_cyc      ptwrite       single_range_output  topa_multiple_entries
```

Флаг `pt` в `/proc/cpuinfo` означает поддержку процессором, а каталог `intel_pt` в sysfs с типом `12` — что ядро зарегистрировало это событие. Возможности (`caps`) включают `ip_filtering` (фильтр по адресам), `cr3_filtering` (по процессу) и `topa_multiple_entries` (буферизация через ToPA).

## Захват и декодирование

Обычно PT включают через `perf`:

```
$ perf record -e intel_pt//u -o pt.data ./tiny
$ perf script -i pt.data --itrace=i1 -F ip > trace.txt
```

Флаг `u` — только пользовательский режим. Декодировать можно и отдельной утилитой `ptxed` из состава `libipt`:

```
$ ptxed --pt pt.data --insn-trace
0x401014  push rbp
0x401015  mov rbp, rsp
0x401043  call 0x401000
```

Но `perf` на нашем стенде **не установлен** (`bash: perf: command not found`), поэтому вместо него покажем тот же поток управления ближайшим доступным инструментом — трассировкой через эмулятор `unicorn` (колбэк на каждую инструкцию). Это «программная» трасса; PT даёт то же самое, но аппаратно, с минимальным оверхедом:

```
0x401014: push    rbp
0x401015: mov     rbp, rsp
0x401018: sub     rsp, 0x18
0x40102d: jmp     0x401059
0x401059: mov     eax, dword ptr [rbp - 8]
0x40105c: cmp     eax, dword ptr [rbp - 0x14]
0x40105f: jl      0x40102f
0x40102f: mov     eax, dword ptr [rbp - 8]
0x401032: and     eax, 1
0x401037: je      0x40104d
0x40104d: mov     eax, dword ptr [rbp - 8]
0x401050: add     eax, eax
...
```

Вот реально исполненные переходы и ветвления. PT записал бы ровно это — только аппаратно и без запуска под инструментацией.

## Как PT сжимает трассу

Понимание того, что именно PT **не** пишет, объясняет его эффективность. Процессор уже знает
предысторию исполнения, поэтому в трассу попадают только «неожиданные» события:

- **Прямые условные переходы** (`jcc`): пишутся одним битом в пакете TNT — взят или нет. Сам адрес
  цели декодер знает из кода.
- **Прямые безусловные переходы и вызовы** (`jmp`/`call` с фиксированной целью): вообще не пишутся —
  декодер следует за потоком по коду.
- **Косвенные переходы** (`call rax`, `ret`, `jmp [table]`): их цель непредсказуема, поэтому пишется
  полный адрес (TIP).
- **Периодически — пакет PSB** (Packet Stream Boundary): маркер синхронизации, чтобы декодер мог
  начать разбор с любого места.

Отсюда вывод: чем больше в коде косвенных переходов (а это как раз обфускация и виртуализация), тем
больше трасса. Но даже в этом случае она в разы компактнее полной инструкционной.

## Применение: обфускация и анти-отладка

Главная ценность PT — работа с кодом, который сопротивляется анализу:

- **Control-flow flattening**: обфусцированная функция превращена в диспетчер с сотнями ветвлений. Статически граф запутан, а PT показывает реально исполненные переходы для конкретного входа, «выпрямляя» поток.
- **Анти-отладка**: PT не ставит точки останова и не меняет код, поэтому проверки на отладчик его не видят.
- **Самомодифицирующийся код**: PT пишет переходы, а декодер использует код в момент исполнения — если снять образ памяти, трасса расшифруется.
- **Malware-анализ**: PT даёт поведение без запуска под отладчиком.

## Ограничения

PT записывает **только поток управления**, а не значения данных: ты знаешь «куда», но не всегда «с чем». Чтобы получить значения, комбинируют методы: PT + символика (трасса задаёт путь, решатель ищет вход), PT + точки останова, PT + DBI. Другие ограничения: только Intel (у AMD свой аналог), конечный буфер (нужен кольцевой режим и своевременная выгрузка), необходимость декодера и точного бинарника, а в виртуальных машинах PT часто отключён.

## Если не сработало

Если `perf record` не запускается, проверьте права (`perf_event_paranoid`) и поддержку ядра. Если трасса пустая — PT выключен в BIOS/гипервизоре или фильтр слишком узкий. Если трасса обрывается — переполнился буфер ToPA, увеличьте его и включите выгрузку по `INT`. Если декодер ругается на неизвестные пакеты — версия `libipt` старше формата PT; обновите библиотеку. И помните: PT пишет только поток управления, поэтому значения регистров из него не достать — для них нужны DBI или символика.

## Полный прогон от начала до конца

Соберём весь путь получения трассы:

1. Проверить поддержку: флаг `pt` в `/proc/cpuinfo` и каталог `/sys/bus/event_source/devices/intel_pt/`.
2. Записать: `perf record -e intel_pt//u -o pt.data ./tiny`.
3. Выгрузить: `perf script -i pt.data --itrace=i1 -F ip > trace.txt`.
4. Декодировать точным бинарником: `ptxed --pt pt.data --insn-trace`.
5. Получить поток: `0x401043 call 0x401000`, затем исполненные ветвления `compute`.
6. Для обфускации — прогнать конкретный вход и получить «выпрямленный» путь.

Если `perf` недоступен, тот же поток можно получить программно (эмулятор/DBI), но это уже не PT:
аппаратная трасса уникальна тем, что не трогает код.

## Как это видят защитники

PT — «невидимый» инструмент, и это одновременно подсказка для детекта. Анти-анализ ищет признаки
включённой трассировки:

- **MSR `IA32_RTIT_CTL`:** если трассировка включена, malware может прочитать этот MSR и увидеть,
  что PT активен (для этого нужен ring 0 — то есть kernel-mode rootkit).
- **ToPA-буфер в памяти:** области, помеченные под вывод PT, можно найти в дампе.
- **Аномалии производительности:** PT почти не замедляет код, поэтому по таймингам его, в отличие от
  отладчика, не поймать — это его сильная сторона.

Для защитника важнее обратное: PT позволяет **посмертно** восстановить поток управления из дампа,
если трасса писалась в память, — поэтому в некоторых продуктах его включают постоянно.

## Что мы теперь знаем

- **Intel PT** записывает поток управления аппаратно, без модификации кода и почти без замедления.
- Он кодирует ветвления пакетами **TNT** и **TIP**; вывод идёт через **ToPA**, включается через MSR, фильтруется по адресам/процессу.
- Поддержку проверяют по флагу `pt` в `/proc/cpuinfo` и по каталогу `/sys/bus/event_source/devices/intel_pt/`.
- Обычно запись делают через `perf record -e intel_pt//u`, декодируют `perf script` или `ptxed`.
- PT не пишет данные — только поток управления, поэтому его комбинируют с символикой и DBI.
- PT сжимает трассу: прямые переходы не пишутся, условные — одним битом TNT, косвенные — адресом TIP.
- Проверить поддержку можно без root: флаг `pt` в `/proc/cpuinfo` и каталог `intel_pt` в sysfs.
