Обычная трассировка через отладчик медленная и заметная: точка останова на каждой инструкции
замедляет программу в сотни раз, а анти-отладка её обнаруживает. **Intel Processor Trace (PT)** —
аппаратная возможность процессора, которая записывает поток управления (переходы, ветвления,
вызовы) в буфер без модификации кода и почти без замедления. Это делает PT идеальным инструментом
для анализа обфусцированного и анти-отладочного кода, где другие методы либо медленны, либо
обнаруживаются.

## Что такое Intel PT

PT — это механизм, встроенный в процессоры Intel (начиная с Broadwell). Он не записывает каждую
инструкцию, а кодирует **поток управления**: какие ветвления были взяты, куда ведут вызовы и
возвраты, где произошли косвенные переходы. Зная бинарник (его код), декодер восстанавливает полную
последовательность исполненных инструкций. Это ключевое свойство: PT даёт полную трассу, но требует
доступа к коду для декодирования.

Запись идёт в буфер (кольцевой или линейный) в памяти, из которого потом читается трасса. Формат
сжат: вместо адресов записываются «пакеты» (TNT — taken/not-taken биты, TIP — целевые адреса),
что снижает объём. Аппаратное кодирование и сжатие делают PT применимым даже для длительных
сессий.

## Как работает трассировка

PT записывает информацию трёх видов:

- **TNT (Taken Not Taken)**: биты, указывающие, какие условные переходы были взяты. Для
  последовательности `jcc` это компактный битовый поток.
- **TIP (Target IP)**: целевой адрес косвенного перехода, вызова или возврата (когда цель нельзя
  предсказать статически).
- **PIP/FUP**: адрес начала трассировки и границы.

Декодер идёт по коду с известной точки входа, применяет TNT-биты к условным переходам и TIP-адреса
к косвенным. В результате восстанавливается точная трасса. Поскольку записывается не всё, объём
трассы на порядки меньше полной инструкционной.

PT включается через MSR (`IA32_RTIT_CTL`) и настраивается диапазонами фильтрации (можно трассировать
только определённые адреса — `IP`-фильтры). Это позволяет сосредоточиться на интересующей функции,
не записывая весь процесс.

## Захват трассы

На Linux проще всего использовать `perf`:

```
$ perf record -e intel_pt//u -o pt.data ./target
$ perf report --stdio -i pt.data
```

Флаг `u` — трассировать только пользовательский режим. `perf record` настраивает PT, запускает
программу, собирает буфер и сохраняет. Затем `perf report` декодирует и показывает распределение
времени по функциям. Для анализа можно использовать `perf script` — он выдаёт поток событий
(инструкции/функции).

Альтернативы: `libipt` (библиотека Intel для декодирования), `ptxed` (утилита из состава libipt),
`simple-pt` (пример), `perf` (встроенная поддержка). В Windows — `Windows Performance Analyzer` и
`perfview` с поддержкой PT, либо собственные драйверы.

## Декодирование

`ptxed` декодирует сырую трассу в список инструкций:

```
$ ptxed --pt pt.data --insn
0x401000  push rbp
0x401001  mov rbp, rsp
0x401004  call 0x401050
0x401050  ...
```

Вы видите каждую исполненную инструкцию — полная трасса без отладчика. Для больших программ вывод
огромен, поэтому обычно фильтруют по адресам или агрегируют (какие функции вызваны, сколько раз).

Для программного декодирования используют `libipt` (C API) или Python-обёртки. Это позволяет
строить кастомные анализаторы: например, считать покрытие кода, находить все исполненные ветки в
обфусцированной функции, строить граф реального потока управления.

## Применение: обфускация и анти-отладка

Главная ценность PT — работа с кодом, который сопротивляется анализу:

- **Control-flow flattening**: обфусцированная функция превращена в диспетчер с сотнями ветвлений.
  Статически граф запутан; PT показывает реально исполненные переходы для конкретного входа,
  «выпрямляя» поток.
- **Анти-отладка**: PT не ставит breakpoints и не меняет код, поэтому не детектируется проверками.
  Трассировка идёт «сбоку» и незаметна программе.
- **Самомодифицирующийся код**: PT записывает переходы, а декодер использует код в момент
  исполнения — если снять образ памяти, трасса расшифруется.
- **Malware-анализ**: PT даёт полную картину поведения без запуска под отладчиком, что снижает риск
  детекта.

## Практический разбор

Задача: понять, какие ветки обфусцированной функции реально исполняются для данного входа.

```
$ perf record -e intel_pt//u --call-graph=dwarf -o pt.data ./obfuscated <<< "input"
$ perf script -i pt.data --itrace=i1ns | head -40
        target  1234 [001]  ... :   401234 decrypt_loop+0x4
        target  1234 [001]  ... :   401238 decrypt_loop+0x8
        target  1234 [001]  ... :   401250 check_byte+0x0
```

`--itrace` управляет уровнем детализации. Видно реально исполненные адреса. Собрав трассу, мы
определяем, какие ветки «живые», а какие — мёртвый обфусцирующий код. Для полного восстановления
алгоритма прогоняем несколько входов и собираем объединение трасс.

Для анти-отладочного образца: запускаем без отладчика, записываем PT, декодируем. Программа не
знает о трассировке, потому что PT не изменяет её память и не перехватывает исключения. Это
преимущество перед DBI (Triton/PIN), которые модифицируют код.

## Ограничения

PT записывает только поток управления, а не значения данных. Чтобы узнать значения регистров, нужна
дополнительная информация: либо декодирование с реконструкцией (по инструкциям и известным входам),
либо комбинирование PT с точками останова/логами. Это главное ограничение: вы знаете «куда», но не
всегда «с чем».

Другие ограничения: поддержка только Intel (AMD имеет свой аналог, менее распространённый); буфер
конечен — при переполнении часть трассы теряется (используют кольцевой режим); сложность настройки
и декодирования; для виртуализованного кода (VMProtect) трасса огромна и требует агрегации.
Наконец, PT может быть отключён в виртуальной машине или гипервизоре.

## Как включить PT программно

Под капотом `perf` делает следующее: проверяет поддержку PT (CPUID `0x14`), выделяет буфер, пишет
базовые MSR (`IA32_RTIT_OUTPUT_BASE`, `IA32_RTIT_OUTPUT_MASK_PTRS`), настраивает `IA32_RTIT_CTL`
(включая биты трассировки, фильтры адресов) и запускает. Понимание этого полезно, если вы пишете
свой сборщик (например, в драйвере для Windows или для конкретного процесса). Для фильтрации по
адресам используются MSR `IA32_RTIT_ADDR0_A/ADDR0_B` — так можно записывать только интересующую
функцию, что резко уменьшает объём.

Проверить поддержку можно через `perf list | grep intel_pt` или чтением CPUID. В контейнерах и
виртуальных машинах PT часто выключен, поэтому для анализа может потребоваться «железная» машина
или гипервизор с проброшенной поддержкой.

## Комбинирование PT с другими методами

PT даёт «куда», но не «с чем». Чтобы получить значения, комбинируйте методы:

- **PT + реконструкция**: зная код и начальные значения регистров, можно частично восстановить
  данные, симулируя инструкции вдоль трассы.
- **PT + точки останова**: PT показывает путь, а breakpoints в ключевых точках — значения. Но
  breakpoints детектируются анти-отладкой; используйте аппаратные.
- **PT + Frida/DBI**: инструментация функций даёт значения, PT — полный поток между ними.
- **PT + символика**: трасса задаёт путь для символического исполнения (angr/Triton), которое
  вычисляет входные данные.

Комбинация PT с символическим исполнением особенно сильна: PT убирает «взрыв путей», оставляя один
реальный путь, а символика решает ограничения на нём. Так анализируют обфусцированные проверки.

## Пример: восстановление алгоритма по трассе

Предположим, есть функция, которая вычисляет хеш от ввода и сравнивает с константой. Статически код
обфусцирован. Прогоняем несколько входов под PT, собираем трассы, объединяем. По трассе видим
реально исполненные инструкции: `mov`, `xor`, `rol`, `add` — типичный хеш. Сопоставляя порядок
операций для разных входов, восстанавливаем алгоритм (например, «для каждого байта: xor с 0x42,
повернуть влево на 3, сложить»). Затем пишем keygen.

Если значений не хватает, добавляем символику: символизируем ввод, исполняем по трассе и получаем
ограничение `hash(input) == const`, решаем его. Так обфускация не мешает: мы не читаем её код, а
следуем реальному потоку.

## Подводные камни

Первое: PT не записывает данные — не ждите значений регистров из трассы. Второе: нужен доступ к
коду (бинарнику) для декодирования; для самомодифицирующегося кода снимайте образ памяти. Третье:
переполнение буфера теряет трассу. Четвёртое: в ВМ PT часто недоступен. Пятое: объём трассы велик —
фильтруйте по адресам (`IP`-фильтры). Шестое: декодирование требует точного соответствия версии
бинарника (ASLR-база учитывается, но патчи памяти — нет). Седьмое: `perf` требует прав (`perf_event_paranoid`)
и поддержки ядра — в контейнерах её может не быть. Восьмое: формат PT версионно-зависим, и старые
декодеры не понимают новые пакеты.

## Что дальше / решение

Практика: на машине с Intel (Broadwell+) запишите `perf record -e intel_pt//u ./crackme`,
декодируйте через `perf script`, найдите исполненные ветки. Сравните с трассой через gdb — PT даст
ту же картину без отладчика. Для обфусцированного бинарника соберите объединение трасс для разных
входов. Далее — `reversing-hardware-trace` (существующий урок) и `reversing-time-travel`.
