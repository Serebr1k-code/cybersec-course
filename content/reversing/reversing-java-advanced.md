## Вопрос, с которого всё начинается

В прошлом уроке мы читали Java-байткод через `javap` — и он был понятен. Но реальные приложения собирают с **ProGuard** или **R8**: имена методов превращаются в `a`, `b`, `c`, строки шифруются, код запутывается. Открываешь декомпилятор — и вместо логики видишь `a.a(b, c)`. Как разобрать такой байткод?

## Наш пример

Возьмём Java-класс с «обфусцированными» именами `Obf`:

```java
public class Obf {
    static int a(int b){ return b == 0x1337 ? 1 : 0; }
    public static void main(String[] c){ System.out.println(a(4919)); }
}
```

Смотрим байткод через `javap -c -p`:

```text
  static int a(int);
    Code:
       0: iload_0
       1: sipush        4919
       4: if_icmpne     11
       7: iconst_1
       8: goto          12
      11: iconst_0
      12: ireturn
```

Даже с именем `a` логика читается: `sipush 4919` — константа `0x1337`, `if_icmpne` — сравнение. Обфускация имён **не меняет байткод** — она лишь убирает подсказки. Это ключевая мысль: байткод остаётся исполняемым и логичным, поэтому его можно читать и патчить.

## Шаг 1: что делает ProGuard/R8

- **Renaming** — классы/методы/поля получают короткие имена (`a`, `b`, `A`).
- **Removal** — удаляются неиспользуемый код и отладочная информация.
- **Optimization** — код переписывается (инлайнинг, свёртка констант).
- **String encryption** (в более сильных протекторах, напр. Allatori) — строки шифруются.

Результат: код меньше и быстрее, но читать его тяжелее. При этом **структура и типы сохраняются** — JVM должна исполнять байткод, поэтому метаданные о классах/методах остаются.

## Шаг 2: чем деобфусцировать Java

- **CFR / Procyon / Fernflower** — декомпиляторы, часто «пробивают» даже обфусцированный код и восстанавливают логику.
- **jadx** — для Android (dex), с хорошей устойчивостью к обфускации.
- **`javap`** — читать байткод напрямую, когда декомпилятор спотыкается.
- **Decompiler-плагины для Ghidra/IDA** — если нужно смешать с нативным анализом.
- **Ручной разбор** — если строки зашифрованы, ставим брейкпоинт (`jdb`) на расшифровку.

В отличие от .NET, единого «de4dot для Java» нет: протекторов много, и часто помогает именно хороший декомпилятор.

## Шаг 3: чтение байткода вручную

Когда декомпилятор выдаёт мусор, читаем `javap`-вывод. Полезно знать опкоды:

- `iload_N`/`aload_N` — загрузить локальную переменную (int/объект).
- `ldc`/`sipush`/`bipush` — положить константу.
- `invokestatic`/`invokevirtual` — вызов метода (по ссылке на `#N` в пуле констант).
- `if_icmpne`/`ifeq`/`goto` — условные/безусловные переходы.
- `areturn`/`ireturn` — возврат.

Ссылки вида `#7` — это индексы в **пуле констант** (constant pool), где лежат имена классов/методов. `javap -v` печатает пул целиком, и по нему видно, какие методы реально вызываются, даже если имена обфусцированы.

## Шаг 4: патч и пересборка

Java-байткод можно патчить так же, как нативный:

- **В байтах** — `javap` даёт инструкции, но проще патчить через декомпилятор/ASM.
- **Через ASM (библиотека)** — программно изменить метод и записать новый `.class`.
- **Декомпилировать → переписать → перекомпилировать** — если код восстанавливается в Java, проще пересобрать.
- **`jar`** — упаковать обратно: `jar cf app.jar ...`, если это `.jar`.

Для CTF часто достаточно понять проверку, а не патчить: логика видна и без запуска.

## Шаг 5: Android — тот же мир

Android-байткод (**Dalvik**) — родственник Java-байткода, и обфускация там та же (R8 — часть Android-тулчейна). Инструменты: **jadx** (устойчив к обфускации), **apktool** (smali), **dex2jar** (dex → jar → CFR). Если видел обфусцированный APK — это та же задача, только контейнер другой.

## Шаг 6: на что смотреть дальше

- **Строки** — при string encryption ставь брейкпоинт на расшифровку и смотри результат.
- **Пул констант** — `javap -v` раскрывает вызываемые методы даже под обфускацией.
- **Точка входа** — `main` обычно сохраняет имя (нужна JVM).
- **Reflection** — обфускаторы любят вызывать методы по строкам через `Class.forName`/`invoke`; ищи эти вызовы.
- **Несколько слоёв** — наряду с renaming может быть шифрование строк и контроль потока.

## Шаг 7: практический разбор обфусцированного jar

Соберём типичный процесс. Дан `app.jar`, собранный с ProGuard:

1. **Распакуй** — `unzip app.jar`; внутри `.class` с короткими именами (`a.class`, `b.class`).
2. **Декомпилируй** — `cfr app.jar` или `jadx` (для dex). CFR часто восстанавливает читаемый Java.
3. **Найди точку входа** — `Main-Class` из `META-INF/MANIFEST.MF`; `main` обычно сохраняет имя.
4. **Если декомпилятор споткнулся** — читай `javap -c -p -v` вручную: пул констант покажет вызовы.
5. **Строки зашифрованы?** — запусти под `jdb`, поставь брейкпоинт на метод расшифровки.
6. **Патч** — через ASM или декомпиляция → перекомпиляция.

Шаги 2–3 решают большинство CTF-задач: CFR/Procyon обычно «пробивают» ProGuard.

## Шаг 8: работа с пулом констант

Пул констант — главный источник информации под обфускацией. `javap -v` печатает его целиком:

```text
#7 = Methodref  #8.#9    // java/lang/System.out
#8 = Class      #10      // java/lang/System
#13 = String    #14      // "flag{...}"
```

Даже если метод называется `a`, в пуле видно, что он вызывает `System.out` и работает со строкой. Строки (`String`) лежат в пуле открытым текстом, если не применено string encryption — ищи их там в первую очередь. По `Methodref` восстанавливают, какие библиотечные методы реально вызываются, и это даёт карту поведения.

## Что мы теперь знаем

- ProGuard/R8 переименовывают и оптимизируют код, но байткод остаётся логичным.
- Обфускация имён не меняет инструкции — `javap` читается так же.
- Декомпиляторы (CFR/Procyon/jadx) часто восстанавливают логику даже из обфусцированного кода.
- Пул констант (`javap -v`) показывает реальные вызовы и строки.
- Патч: ASM/декомпиляция-перекомпиляция; для CTF часто достаточно прочитать.

## Частые вопросы

- **Декомпилятор выдаёт мусор** — читай `javap -v` вручную; пул констант всё равно всё показывает.
- **Строк нет** — включено string encryption; ищи метод расшифровки и ставь брейкпоинт.
- **Много классов `a/b/c`** — это renaming; логика в опкодах сохранилась, читай по пулу констант.
- **Android вместо jar** — используй jadx; подход тот же, контейнер — dex.
- **Нужна пакетная обработка** — декомпиляторы (CFR, Procyon) имеют CLI, так что разбор большого jar автоматизируется скриптом; для патча удобна библиотека ASM.
- **Имена классов — `a`, `b`, но методы разные** — не путай: у каждого класса своё пространство имён, поэтому ищи по вызовам из точки входа, а не по имени класса.

## Где пригодится

- **CTF Reversing:** Java-задачи часто с ProGuard; `javap`/CFR быстро возвращают логику.
- **Аудит Java-приложений:** обфускация не мешает найти логические ошибки по восстановленному коду.
- **Анализ Java-малвари:** обфусцированные `.jar` разбирают декомпилятором + отладкой.
- **Android:** R8 — тот же инструмент; навык переносится на APK.
