Java компилируется в **байткод** для JVM — платформенно-независимый, богатый метаданными и потому легко декомпилируемый. Именно поэтому Java-приложения (включая Android и серверные) активно обфусцируют: ProGuard/R8 (бесплатные, встроены в Android-сборку), Allatori, Zelix KlassMaster, Stringer, DashO (коммерческие). Обфускация переименовывает классы/методы, шифрует строки, запутывает поток управления, вставляет мусор. Этот урок — как разбирать обфусцированный Java: формат class-файла, инструменты, приёмы деобфускации и полный разбор.

## Почему Java легко и сложно одновременно

Легко: байткод сохраняет структуру (классы, методы, исключения, аннотации), а декомпиляторы (CFR, Fernflower, Procyon) восстанавливают читаемый исходник. Сложно: обфускаторы ломают имена (`a`, `b`, `c`), шифруют строковые константы, превращают линейный код в гигантский switch (control-flow flattening), вставляют недостижимые ветки и вычисления через `invokedynamic`. Всё это сохраняет **семантику** (JVM должна исполнить код), поэтому деобфускация — это восстановление читаемости, а не логики.

## Формат class-файла и байткод

Class-файл начинается с магии `0xCAFEBABE`, затем версия, пул констант (`constant_pool`), флаги доступа, `this_class`/`super_class`, поля, методы, атрибуты. Каждый метод содержит `Code`-атрибут с массивом байткода, таблицей исключений и `LineNumberTable`/`LocalVariableTable`. Инструмент для разбора:

```bash
javap -c -p -v com/example/App.class > App.txt
javap -c -p com/example/App.class | head -50
```

`-c` — байткод, `-p` — приватные члены, `-v` — подробно (пул констант). Стек-ориентированная машина: инструкции `aload_0`, `invokevirtual`, `ldc`, `if_icmpne` и т.д.

## Инструменты: декомпиляторы и анализ

- **CFR** (`java -jar cfr.jar app.jar --outputdir out`) — лучший на сегодня, устойчив к обфускации.
- **Procyon** — хорош на сложных конструкциях.
- **Fernflower** (встроен в IntelliJ) — качественный.
- **JADX** — для APK/DEX (`jadx -d out app.apk`), умеет и Java, и нативные части.
- **JD-GUI / Bytecode Viewer** — GUI.
- **Krakatau** — ассемблер/дизассемблер байткода (`python Krakatau/disassemble.py -out out.jar app.jar`).
- **Recaf** — редактор байткода с декомпилятором (удобно патчить).
- **ASM / Javassist** — программная манипуляция байткодом.
- **java-deobfuscator / de4dot-подобные** — автоматическая деобфускация (Threadtear).

## ProGuard/R8: что именно они делают

ProGuard и R8 (Android) выполняют: **shrinking** (удаление неиспользуемого кода), **optimization** (инлайн, слияние), **obfuscation** (переименование в короткие имена), **preverification**. Настраивается через `proguard-rules.pro` с `-keep`-правилами. Для реверса важно: если класс/метод в `-keep`, имя сохраняется; остальное переименовано. Mapping-файл (`mapping.txt`), если доступен, восстанавливает имена. R8 дополнительно делает более агрессивный инлайн. Признаки ProGuard: классы `a.a.a`, методы `a()`, `b()`, потеря `LocalVariableTable`.

## Коммерческие обфускаторы и их следы

- **Allatori**: шифрует строки (вызовы декриптора `a(String, int)`), control-flow flattening, водяные знаки.
- **Zelix KlassMaster**: строковое шифрование, переименование, «stringer»-подобные приёмы, anti-debug.
- **Stringer**: специализированное шифрование строк (сейчас интегрирован в Zelix).
- **DashO**: похож на Allatori.
- **Bozar / Paramorphism**: тяжёлые, с нативной поддержкой.

Следы: статический метод-декриптор, вызываемый с (String, int); огромные switch; классы с одинаковыми именами в разных пакетах.

## Ручной анализ байткода

Когда декомпилятор путается, читают байткод. Ключевые инструкции:

| Инструкция | Смысл |
|---|---|
| `aload_0` | this / локальная переменная 0 |
| `iload_1`, `istore_2` | загрузка/сохранение int |
| `ldc` / `ldc_w` | константа из пула |
| `invokevirtual` | вызов метода объекта |
| `invokestatic` | статический вызов |
| `invokedynamic` | динамический вызов (лямбды, string concat) |
| `if_icmpne` | сравнение и переход |
| `tableswitch`/`lookupswitch` | switch (часто flattening) |
| `athrow` | выброс исключения |
| `checkcast` | приведение типа |

Читая `javap -c`, восстанавливают поток: сравнения, вызовы декриптора, циклы.

## Патчинг и пересборка

Для обхода проверок патчат байткод: **Recaf** позволяет изменить инструкцию (`ifne` → `nop`), **Krakatau** — пересобрать из ассемблера. Программно — через ASM:

```java
ClassReader cr = new ClassReader(bytes);
ClassWriter cw = new ClassWriter(0);
ClassVisitor cv = new ClassVisitor(Opcodes.ASM9, cw) {
  public MethodVisitor visitMethod(int a, String n, String d, String s, String[] e) {
    MethodVisitor mv = super.visitMethod(a, n, d, s, e);
    return new MethodVisitor(Opcodes.ASM9, mv) {
      public void visitInsn(int opcode) {
        if (opcode == Opcodes.IRETURN) { super.visitInsn(Opcodes.ICONST_1); }
        super.visitInsn(opcode);
      }
    };
  }
};
cr.accept(cv, 0);
```

Так заставляют метод возвращать `true`.

## Полный разбор: деобфускация строк

**Шаг 1 — заметить декриптор.** В декомпилированном коде видим `String s = a.a("\u1234\u5678", 42);` — статический метод с двумя аргументами.

**Шаг 2 — извлечь метод.** Копируем его байткод (`javap -c`) и воспроизводим алгоритм: обычно XOR/сложение с ключом.

**Шаг 3 — автоматизировать.** Пишем скрипт на Java/Python, который вызывает декриптор для всех строк, или парсим пул констант и применяем алгоритм:

```python
def dec(s, k):
    return ''.join(chr(ord(c) ^ k) for c in s)
```

**Шаг 4 — инструмент.** **Threadtear** умеет подключать кастомные деобфускаторы и прогонять их по jar; **java-deobfuscator** — конфигурируемый.

**Шаг 5 — проверка.** Прогоняем деобфусцированный jar, убеждаемся в работоспособности.

## Что дальше / решение

Маршрут: декомпилируйте jar/apk (CFR/JADX), найдите декриптор строк и точку проверки, восстановите алгоритм, автоматизируйте деобфускацию (Threadtear), при необходимости патчите байткод (Recaf/ASM) и проверяйте результат. ## invokedynamic и лямбды: скрытые вызовы

Современные обфускаторы прячут логику за `invokedynamic` — динамически связываемыми вызовами, которые JVM разрешает в рантайме через bootstrap-метод. Лямбды и конкатенация строк (Java 9+) компилируются именно так. В `javap -v` видно `InvokeDynamic #N`, а bootstrap-метод указывает на `LambdaMetafactory` или кастомный метод. Обфускаторы используют это для скрытия вызовов: статически не видно, какой метод будет вызван. Разбор: находят bootstrap-метод в пуле констант, читают его байткод, восстанавливают целевую функцию. Динамически — ставят брейкпоинт на `LambdaMetafactory.metafactory` и смотрят аргументы.

## Threadtear и автоматическая деобфускация

Threadtear — GUI/CLI-инструмент для деобфускации jar: подключает цепочку «трансформеров» (стрип отладочной информации, дешифровка строк, свёртка switch, удаление мёртвого кода, переименование). Для кастомных обфускаторов пишут собственный трансформер на Java (интерфейс `ITransformer`). Запуск: `java -jar threadtear.jar` → выбрать jar → добавить трансформеры → `Run`. Дополнительно `java-deobfuscator` (superblaubeere27) конфигурируется JSON-скриптом и умеет выполнять произвольные байткод-преобразования через ASM. Эти инструменты экономят часы ручной работы на типовых Allatori/Zelix-защитах.

## Пример: обход лицензионной проверки

Пусть декомпилированный код:

```java
public boolean isValid(String key) {
    return License.a(key).equals(License.b());   // зашифрованные строки
}
```

**Шаг 1** — восстановить строки (дешифровка). **Шаг 2** — понять алгоритм проверки. **Шаг 3** — вместо реверса ключа пропатчить метод, чтобы он всегда возвращал `true`:

```java
public boolean isValid(String key) { return true; }
```

Через Recaf меняем байткод метода на `iconst_1; ireturn`. **Шаг 4** — пересобрать jar/apk (для Android — `apktool b`, `zipalign`, подпись `apksigner`). **Шаг 5** — проверить на устройстве. Важно: патч может сломать проверку целостности подписи (SafetyNet/Play Integrity), тогда дополнительно патчат и её или запускают в среде без проверки.

## Сравнение обфускаторов

| Обфускатор | Строки | Control-flow | Прочее | Сложность обхода |
|---|---|---|---|---|
| ProGuard | нет | частично | переименование | низкая (mapping) |
| R8 | нет | инлайн | переименование | низкая-средняя |
| Allatori | да | flattening | водяные знаки | средняя |
| Zelix | да | flattening | anti-debug, stringer | высокая |
| DashO | да | да | нативные части | высокая |
| Bozar | да | да | нативный загрузчик | очень высокая |

Чем «тяжелее» обфускатор, тем чаще в комплект входит нативная библиотека-загрузчик, которая расшифровывает байткод в памяти — тогда статическая деобфускация невозможна без дампа рантайма (через Java-агент или JVMTI).

## Android DEX против class-файлов

На Android байткод хранится в DEX (Dalvik Executable), а не в class-файлах: другая система команд (регистровая, а не стековая), общий пул строк, несколько классов в одном файле. Инструменты анализа: `baksmali` (дизассемблер в smali), `smali` (обратно в DEX), `jadx` (декомпиляция в Java), `dexdump`. Smali-синтаксис читается легче байткода: директивы `.method`, `.registers`, инструкции `invoke-virtual`, `const-string`. Для патча APK правят smali, собирают через `apktool b`, подписывают `apksigner`. Обфускация DEX — те же ProGuard/R8 (для Android), плюс нативные библиотеки. Понимание smali обязательно при работе с APK без исходников.

## Типичные ошибки при анализе обфусцированного Java

Несколько практических предостережений. Декомпилятор может молча выдать неверный код на flattening — всегда сверяйтесь с `javap -c` на критичных методах. Строковый декриптор может зависеть от глобального состояния (счётчик вызовов, статический массив), тогда простое копирование алгоритма даст неверные строки — нужно воспроизводить порядок вызовов. `invokedynamic`-обфускация прячет целевые методы, поэтому статический поиск ссылок не работает. Наконец, некоторые обфускаторы ломают `StackMapTable`, и JVM отказывается загружать модифицированный jar — пересобирайте через ASM с `COMPUTE_FRAMES`. Всегда проверяйте результат запуском и логированием.
