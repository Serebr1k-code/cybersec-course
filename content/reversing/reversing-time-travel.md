**Time-travel debugging (TTD)** — это запись исполнения программы целиком, с возможностью «отмотать» назад и посмотреть, что было до сбоя. Вместо многократного перезапуска под отладчиком вы записываете один прогон и исследуете его интерактивно: обратные шаги, точки останова «назад во времени», watchpoints, анализ race conditions. Урок разбирает два основных инструмента — **rr** (Linux, `rr record`/`rr replay`) и **WinDbg TTD** (Windows) — с полными командами и разбором вывода.

## Что такое time-travel debugging

Обычный отладчик умеет идти только вперёд. TTD записывает **детерминированную трассу** исполнения (регистры, память, системные вызовы, порядок потоков) и позволяет:

- **Обратный шаг** (`reverse-stepi`, `reverse-continue`) — «как мы сюда попали?».
- **Обратные точки останова** — остановиться на последнем обращении к адресу **до** текущего момента.
- **Watchpoints назад** — узнать, кто записал «плохое» значение.
- **Анализ без повторного запуска** — сбой воспроизводим сколько угодно раз, детерминированно.
- **Race conditions** — запись фиксирует порядок потоков; вы можете многократно «переиграть» его.

Это ключевой инструмент для задач, где баг **нестабилен** (flaky), или где нужно понять первопричину, а не симптом.

## rr: запись и воспроизведение

`rr` (Mozilla) — самый популярный TTD на Linux. Работает в user-space через `ptrace` + запись/детерминированное воспроизведение.

```bash
# запись
rr record ./target arg1 arg2
# воспроизведение (открывает gdb)
rr replay
# воспроизвести конкретный прогон
rr replay -p <trace-dir>
```

Ключевые флаги `rr record`:

| Флаг | Смысл |
|---|---|
| `-o <dir>` | каталог трассы |
| `-n` | не открывать подсказки |
| `-M` | записывать память на всех страницах |
| `--chaos` | случайный порядок планирования (для race) |
| `-h` | записывать только потоки, затрагивающие heap |
| `--nested=detach` | для вложенных процессов |

```bash
rr record -o ./trace ./target
# вывод
rr: Saving execution to trace directory `./trace`.
```

Воспроизведение:

```bash
rr replay ./trace
(rr) continue
(rr) reverse-continue      # откат к предыдущей точке останова
(rr) reverse-stepi         # шаг назад по инструкциям
(rr) when                  # текущая позиция в трассе
```

## WinDbg TTD: запись и навигация

На Windows — встроенный TTD в WinDbg (не WinDbg Preview, а современный WinDbg). Запись:

```
!ttdext.help
!ttt        # включить/выключить запись трассы
.time        # показать текущую позицию
```

Основные команды навигации:

| Команда | Действие |
|---|---|
| `!tt 0` | перейти в начало трассы |
| `!tt 100` | перейти к 100% |
| `!tt 50:0` | позиция по времени:потоку |
| `g-` / `p-` | обратный continue / шаг |
| `ba` + `!tt` | обратные точки останова |
| `.ttime` | текущее время трассы |

```windbg
0:000> g
Breakpoint hit...
0:000> g-            ; откат к предыдущему срабатыванию
0:000> r             ; регистры на этот момент
```

TTD-трасса сохраняется как `.run`-файл; её можно открыть на другой машине.

## Обратные точки останова и watchpoints

Главная сила TTD — вопрос «кто испортил память?». Ставим watchpoint и идём **назад**:

```bash
# rr
(rr) watch -l *(int*)0x7fffdead
(rr) reverse-continue     # остановится на инструкции, которая ЗАПИСАЛА значение
(rr) bt                   # стек того момента
```

Аналогично в WinDbg TTD:

```windbg
0:000> ba w4 0x7ff6dead
0:000> g-
0:000> k
```

Это позволяет за один прогон найти, где именно переменная была испорчена — то, что в обычном отладчике требовало бы десятков перезапусков.

## Разобранный пример: откат к причине краша

Дано: программа падает с `SIGSEGV` через 2 секунды после запуска, но нестабильно.

**Шаг 1. Запись.**

```bash
rr record ./crash
# ... падение
# rr: Saving execution to trace directory `./crash-0`.
```

**Шаг 2. Воспроизведение до падения.**

```bash
rr replay
(rr) continue
Program received signal SIGSEGV
(rr) bt
#0  process (p=0x0) at src.c:42
```

**Шаг 3. Откат к причине.**

```bash
(rr) frame 1
(rr) reverse-stepi        # идём назад, ищем, откуда p=0
(rr) info registers rdi
(rr) watch -l *(long*)&p
(rr) reverse-continue
# остановка на строке, где p было присвоено 0
```

**Шаг 4. Вывод.** Находим, что `p` присвоено из неудачного `lookup()`, возврат которого не проверен. Обычным отладчиком это заняло бы много перезапусков; TTD — один прогон.

## Многопоточность и race conditions

rr записывает порядок планирования и воспроизводит его **точно**. Чтобы исследовать гонки:

```bash
rr record --chaos ./target          # варьировать планирование
rr replay --chaos
# или управлять порядком вручную
(rr) continue
(rr) when
(rr) reverse-continue
```

Повторяя запись с `--chaos`, можно «поймать» гонку и затем детерминированно её анализировать. Это уникальная возможность TTD — в обычном отладчике race воспроизвести почти невозможно.

## Интеграция с gdb/pwndbg

`rr replay` открывает настоящий gdb, поэтому работают расширения:

```bash
rr replay -x ./pwndbg/gdbinit.py
(rr) pwndbg ...
(rr) vmmap
(rr) heap
```

Это сочетает мощь pwndbg (heap, ROP, поиск) с возможностью отката. Для pwn-задач с нестабильным поведением heap — бесценно.

## Ограничения и производительность

- **Только один поток пишется активно**; остальные «приостанавливаются» детерминированно — накладные расходы.
- **Не работает с некоторыми системными вызовами** (perf, ioctl, прямой доступ к железу) — нужно `rr record --disable-...`.
- **Размер трассы** растёт быстро (гигабайты на длинные прогоны); храните в быстром каталоге.
- **TTD Windows** требует современного WinDbg и процессора с поддержкой (Intel PT или программная эмуляция).
- **Не для kernel-space** (user-space только), хотя есть экспериментальные подходы.

## Частые ошибки и подводные камни

- **Запись долгого прогона.** Трасса раздувается; ставьте фильтры/точки, чтобы записать только нужное окно.
- **Забыть про `--chaos`.** Без него нестабильные гонки не поймать.
- **Путать прямой и обратный шаг.** `reverse-stepi` идёт назад, `stepi` — вперёд; после `reverse-continue` стек — на момент остановки.
- **Надежда на kernel-space.** rr не отлаживает ядро — для этого другие инструменты (drgn, kprobes).
- **Попытка «починить» без записи.** Сначала воспроизводите детерминированно, потом анализируйте.

## Что дальше / решение

Применяйте TTD, когда баг **нестабилен** или нужно понять **первопричину** записи в память: `rr record → rr replay → watch -l → reverse-continue` для Linux; WinDbg TTD с `ba`/`g-` для Windows. Это радикально сокращает время на race conditions и corruption-баги. Дальше — `reversing-advanced-debugging` (глубокие техники отладки) и `reversing-kernel-taint` для анализа на уровне ядра.

## Установка и подготовка стенда

```bash
# rr (Ubuntu/Debian)
sudo apt-get install -y rr
rr --version
# или сборка из исходников для свежей версии
git clone https://github.com/rr-debugger/rr && cd rr && cmake -B build && cmake --build build -j
```

Для rr нужен CPU с поддержкой нужных инструкций и настройка `perf_event_paranoid`:

```bash
echo 1 | sudo tee /proc/sys/kernel/perf_event_paranoid
# или запускать rr под sudo, если политика строгая
```

Для WinDbg TTD — установить современный WinDbg из Store, включить запись в меню **Settings → Time Travel**.

## rr vs gdb record/replay

У gdb есть собственный `record`/`reverse-continue`, но он ограничен: мало памяти, медленный, нестабильный на многопоточности. rr — специализированная замена с записью на диск и точным планированием.

| Критерий | gdb record | rr |
|---|---|---|
| Многопоточность | слабо | отлично |
| Размер трассы | RAM (мало) | диск (гигабайты) |
| Детерминизм | частичный | полный |
| Формат | in-memory | каталог/`.run` |
| Скорость воспроизведения | медленно | быстро |

## Практика: анализ use-after-free

Классический сценарий, где TTD незаменим.

```bash
rr record ./uaf
rr replay
(rr) continue          # падение
#0  use (p=0x...)
(rr) watch -l *(void**)0x602010
(rr) reverse-continue  # кто ОСВОБОДИЛ объект до использования
#0  free () ...
(rr) bt
```

За один прогон видно: `free` вызван в ветке, которую вы не ожидали, а `use` — позже. Без TTD пришлось бы ловить нестабильный heap.

## Оптимизация записи: снапшоты и чекпоинты

rr периодически сохраняет чекпоинты, что ускоряет прыжки по трассе. Управлять можно через переменные окружения и флаги:

```bash
RR_TRACE_DIR=/fast/disk rr record ./target   # трассу на быстрый диск
# отключить запись памяти на всех страницах (меньше трассы, но хуже откат)
rr record -M ./target
```

Для длинных прогонов держите трассу на SSD и ограничивайте окно записи точками останова.

## Анализ многопоточных багов: практический приём

```bash
rr record --chaos ./race
# запись несколько раз, пока гонка не воспроизведётся
for i in $(seq 1 20); do rr record --chaos -o t$i ./race || break; done
rr replay t7
(rr) when
(rr) reverse-continue
```

Зафиксировав «плохой» порядок, вы затем исследуете его детерминированно — то, что в реальности длится микросекунды, разворачивается в пошаговый анализ.

## Ограничения Windows TTD

- Требуется Windows 10 (1809+) или 11; старые версии не поддерживают.
- Трассы большие (сотни МБ/ГБ) — храните на быстром диске.
- Некоторые защищённые процессы (античит, PPL) не записываются.
- Точность зависит от режима: Intel PT (быстро, ограниченное покрытие) vs программный (полно, медленно).

## Ключевые выводы по TTD

Итог: TTD превращает «нестабильный баг» в детерминированную задачу. `rr record/replay` + `watch -l` + `reverse-continue` — базовый набор для Linux; WinDbg TTD с `ba`/`g-`/`!tt` — для Windows. Всегда храните трассу на быстром диске и записывайте только нужное окно.
