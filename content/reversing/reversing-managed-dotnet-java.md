## Вопрос, с которого всё начинается

Ты открываешь `.class` из Java-приложения или `.exe`, собранный на C#, — и дизассемблер показывает что-то странное: не x86-инструкции, а команды вида `iload_0`, `call`, `ldstr`. Это не машинный код, а **managed-код**: программа исполняется не процессором напрямую, а виртуальной машиной (JVM для Java, CLR для .NET). Как его реверсить и почему это часто проще, чем нативный код?

## Наш пример

Возьмём два маленьких файла с одинаковой логикой — проверкой `x == 0x1337`. Java-класс `Hello.class` и .NET-сборку `Check.exe` (C#):

```bash
$ file Hello.class Check.exe
Hello.class: compiled Java class data, version 61.0 (Java SE 17)
Check.exe:   PE32 executable ..., Intel i386 Mono/.Net assembly, 3 sections
```

Обрати внимание: `Check.exe` — это PE, но с пометкой **Mono/.Net assembly**. То есть контейнер — обычный Windows PE, а внутри — managed-код. Разберём оба.

## Шаг 1: Java — байткод и `javap`

Java компилируется не в машинный код, а в **байткод** для JVM. Смотрим его встроенным дизассемблером `javap`:

```bash
$ javap -c -p Hello.class
  static int check(int);
    Code:
       0: iload_0
       1: sipush        4919
       4: if_icmpne     11
       7: iconst_1
       8: goto          12
      11: iconst_0
      12: ireturn
```

Читаем: `iload_0` кладёт на стек первый аргумент, `sipush 4919` — константу `0x1337`, `if_icmpne 11` — «если не равны, перейти к 11», `iconst_1`/`iconst_0` кладут 1/0. Это ровно наша логика, только стековая. `javap` — первый инструмент реверса Java: без плагинов и GUI.

## Шаг 2: .NET — IL и `monodis`

.NET компилируется в **IL** (Intermediate Language). Дизассемблер `monodis` (или `ildasm`) печатает его:

```text
  .class public auto ansi beforefieldinit Check extends [mscorlib]System.Object
  {
    .method ... static int32 Verify(int32 x) cil managed
    {
      IL_0000:  ldarg.0
      IL_0001:  ldc.i4     0x1337
      IL_0006:  bne.un.s   ...
      ...
    }
  }
```

Видим тот же принцип: `ldarg.0` — первый аргумент, `ldc.i4 0x1337` — константа, `bne.un.s` — условный переход. IL, как и Java-байткод, стековый и содержит **метаданные**: имена классов, методов и типов. Именно эти метаданные делают managed-код «разговорчивым».

## Шаг 3: почему managed-код проще реверсить

Нативный бинарник после `strip` теряет имена, а managed-код их **не может** потерять: среда исполнения ищет методы по именам и типам. Отсюда следствия:

- **Метаданные всегда на месте** — имена классов, методов, полей видны как есть.
- **Типы известны** — IL строго типизирован, поэтому декомпилятор восстанавливает сигнатуры.
- **Структура сохраняется** — циклы, условия, вызовы читаются почти как исходник.

Поэтому для .NET и Java есть **декомпиляторы в исходный C#/Java**: ILSpy, dnSpy, dotPeek (для .NET); CFR, Procyon, jadx (для Java). Часто они возвращают код, почти идентичный оригинальному.

## Шаг 4: декомпиляция — и что дальше

Типичный рабочий процесс:

1. **Определить тип** — `file`: «Java class data» или «Mono/.Net assembly».
2. **Декомпилировать** — dnSpy/ILSpy (клик по сборке) или CFR/jadx (по `.jar`/`.class`).
3. **Найти проверку** — искать сравнение строк/чисел, работу с вводом.
4. **Понять алгоритм** — обычно это буквально исходный код; при желании — патчить и пересобрать.
5. **Динамика при обфускации** — если имена спрятаны (см. уроки про advanced), подключают отладчик и `Frida`/reflection.

На CTF шаг 2–3 часто решает задачу за пару минут: код виден почти как есть.

## Шаг 5: где managed-код встречается

- **Java** — серверные приложения, Android (байткод в `.dex`), CTF-задачи.
- **.NET** — Windows-софт, enterprise-приложения, много малвари (Cobalt Strike-лоадеры, стилеры).
- **Кроссплатформенный .NET** — Mono и .NET Core, тот же IL.

Понимание, что перед тобой managed-код, меняет весь подход: вместо ассемблера ты открываешь декомпилятор и читаешь почти исходник.

## Шаг 6: JVM и CLR — что общего

Несмотря на разные языки, Java и .NET устроены поразительно похоже:

| | Java | .NET |
|---|---|---|
| Формат кода | байткод (`javap`) | IL (`monodis`) |
| Виртуальная машина | JVM | CLR |
| Контейнер | `.class`/`.jar` | PE-сборка `.dll`/`.exe` |
| Метаданные | в `.class` | в PE-секции `.text`/метаданных |
| Декомпилятор | CFR, Procyon, jadx | ILSpy, dnSpy, dotPeek |

Обе VM — стековые, обе хранят типы и имена, обе исполняются по инструкциям, а не напрямую процессором. Поэтому навык «прочитать `javap`» переносится на «прочитать IL» почти без потерь: меняются имена инструкций, идея — та же.

## Шаг 7: полный разбор от начала до конца

Соберём типичную CTF-задачу в цепочку:

1. **`file app`** — «Java class data» или «Mono/.Net assembly».
2. **Декомпилятор** — открыть файл в jadx/CFR (Java) или dnSpy/ILSpy (.NET).
3. **Найти точку входа** — `main` (Java) или `Main` (.NET); от неё к проверке.
4. **Прочитать проверку** — сравнение ввода с константой/строкой; часто видно ключ.
5. **Проверить** — запустить или реализовать алгоритм в Python.
6. **Если обфусцировано** — перейти к урокам про advanced (ConfuserEx/ProGuard) и деобфускации.

На шаге 2–4 задача обычно уже решена. Это делает managed-задачи самыми быстрыми на CTF.

## Шаг 8: инструменты

- **Java:** `javap -c -p` (байткод), CFR/Procyon (декомпиляция `.jar`), jadx (Android `.dex`).
- **.NET:** `monodis`/`ildasm` (IL), ILSpy/dnSpy/dotPeek (декомпиляция), `de4dot` (снятие обфускации).
- **Отладка:** `jdb`/`jdb`-подобные для Java, dnSpy-отладчик для .NET.
- **Динамика:** Frida (для .NET через Frida-мост), Java-агенты.

Минимального набора — `javap`/`monodis` плюс один декомпилятор — достаточно для большинства задач.

## На что смотреть дальше

Когда откроешь managed-бинарник, держись такого порядка:

1. **Определи платформу** — `file`: Java class / .NET assembly / Android dex.
2. **Декомпилируй** — не читай байткод, если есть декомпилятор.
3. **Найди ввод** — откуда приходит пользовательский ввод (`main`, `onCreate`, `Main`).
4. **Найди сравнение** — строки/константы рядом с проверкой.
5. **Проверь типы** — в managed-коде сигнатуры известны, это подсказка о логике.
6. **Обфускация?** — если имена вида `a`, `b`, `c` или строки зашифрованы, иди в ветку advanced.

Главная ошибка новичка — открывать managed-файл в дизассемблере машинного кода и пытаться читать «странный ассемблер». Увидел `ldstr`/`iload` — это managed, бери декомпилятор.

## Что мы теперь знаем

- Managed-код исполняется виртуальной машиной (JVM/CLR), а не процессором.
- Java → байткод (смотреть `javap -c`); .NET → IL (смотреть `monodis`/`ildasm`).
- Метаданные (имена, типы) в managed-коде сохраняются всегда — это ключевое преимущество.
- Декомпиляторы (ILSpy/dnSpy, CFR/jadx) возвращают код, близкий к исходнику.
- `file` сразу подсказывает тип: «Java class data» или «Mono/.Net assembly».

## Куда дальше

Managed-код ветвится на две большие платформы. Ближе всего к пользователю **Android**: там байткод лежит в `.dex` внутри `.apk`. Разберём APK по шагам — от `unzip` до `dex`-классов и нативных библиотек. А пока запомни: увидел «assembly» или «class data» — бери декомпилятор, а не дизассемблер.

## Где пригодится

- **CTF Reversing:** managed-задачи решаются декомпилятором за минуты — это самый «дешёвый» тип реверса.
- **Анализ .NET/Java malware:** стилеры и лоадеры на C#/Java читаются как исходники после декомпиляции.
- **Аудит enterprise-приложений:** Java/.NET-сервисы можно проверить на логические ошибки по декомпилированному коду.
- **Android:** байткод Dalvik — родственник Java-байткода, и подход переносится один в один.
