## Вопрос, с которого всё начинается

Тебе дали прошивку IoT-устройства: файл `.bin`, внутри — код микроконтроллера.
Никакого Linux, никакой libc, ни одной привычной строки. Только код, который
выполняется «на голом железе» (bare-metal) или поверх маленькой RTOS вроде
**FreeRTOS** (Real-Time Operating System — операционная система реального
времени). Как вообще подступиться к такому бинарнику?

## Наш пример

Возьмём функцию, которая могла бы проверять лицензию на микроконтроллере. Она
считает хэш (вариант FNV) и сравнивает результат:

```c
volatile unsigned checksum;
int task_check(unsigned x){
    unsigned acc = 0x811c9dc5u;                 // FNV offset basis
    for (unsigned i = 0; i < x; i++) { acc ^= i; acc *= 16777619u; }
    checksum = acc;
    return acc == 0x1a2b3c4du;
}
```

Скомпилируем её под Cortex-M4 (ядро ARM) в режиме Thumb и посмотрим, что
получилось. Дизассемблируем с помощью capstone:

```
$ python3 -c "..."   # capstone: CS_ARCH_ARM, CS_MODE_THUMB
0x0000: movw    r1, #0x9dc5
0x0004: movt    r1, #0x811c
0x0008: cbz     r0, 0x20
0x000a: movw    r3, #0x193
0x000e: movs    r2, #0
0x0010: movt    r3, #0x100
0x0014: eors    r1, r2
0x0016: adds    r2, #1
0x0018: cmp     r0, r2
0x001a: mul     r1, r3, r1
0x001e: bne     0x14
0x0020: movw    r0, #0xc3b3
0x0024: movt    r0, #0xe5d4
0x0028: add     r0, r1
0x002a: movw    r2, #0
0x002e: clz     r0, r0
0x0032: movt    r2, #0
0x0036: lsrs    r0, r0, #5
0x0038: str     r1, [r2]
0x003a: bx      lr
```

Сразу видно **архитектурные отличия** от x86, которые надо знать:

- `movw`/`movt` — 32-битные константы собираются из двух половин (Thumb не
  умеет длинные иммедиаты). `movw r1,#0x9dc5` + `movt r1,#0x811c` = `0x811c9dc5`
  — это и есть FNV offset basis.
- `r0–r3` — первые четыре аргумента функции (как `rdi/rsi/rdx/rcx` в x86-64).
  `r0` — входной `x`, `r1` — накопитель `acc`.
- `r3 = 0x1000193` — простое число FNV (16777619).
- `str r1, [r2]` — запись `checksum` в память (r2 = 0 + релокация).
- `bx lr` — возврат (`lr` — регистр адреса возврата, аналог стека вызовов).

## Шаг 1: как выглядит bare-metal прошивка

У bare-metal кода нет операционной системы, поэтому всё держится на **таблице
векторов**. По адресу 0x00000000 (или другому, куда мапится flash) лежит:

- начальное значение `SP` (указатель стека);
- `Reset_Handler` — адрес первой инструкции после сброса;
- векторы прерываний (NMI, HardFault, SysTick и т.д.).

Прошивка — это обычно «сырой» образ, залитый по адресу `0x08000000` (flash) на
STM32 или `0x00000000` на других. При анализе важно узнать **базовый адрес**
загрузки: он в linker script и в map-файле. Без него адреса не сходятся.

## Шаг 2: где искать логику

В bare-metal нет `main` в привычном смысле — есть `Reset_Handler`, который
инициализирует память и вызывает `main`. Логику ищут:

- по строкам и константам (лицензии, ключи);
- по вызовам периферии (регистры по фиксированным адресам);
- по таблице векторов и обработчикам прерываний.

Часто прошивку сначала «раскладывают»: определяют, где `.text`, `.data`,
`.rodata`, и применяют base address. Инструменты вроде `arm-none-eabi-objdump`
или Ghidra (с выбранным процессором Cortex-M) читают такой образ.

## Шаг 3: FreeRTOS — задачи вместо потоков

**FreeRTOS** даёт простую многозадачность: есть **задачи** (tasks), каждая со
своим стеком, и **планировщик**, переключающий их. В коде это видно по
характерным вызовам:

- `xTaskCreate(task_fn, name, stack, arg, prio, handle)` — создание задачи;
- `vTaskStartScheduler()` — старт планировщика;
- `vTaskDelay()`, `xQueueReceive()`, `xSemaphoreTake()` — примитивы
  синхронизации.

В статике список задач можно восстановить по структурам `TCB` (Task Control
Block) и по вызовам `xTaskCreate`. В динамике удобно ловить переключение задач
по записи в регистр `SysTick`/`PendSV` (планировщик использует эти исключения).

## Шаг 4: восстановление символов и типов

В прошивке почти всегда нет символов. Помогают:

- **Библиотеки-сигнатуры.** FreeRTOS-функции опознаются по уникальным
  последовательностям инструкций; готовые FLIRT-сигнатуры (в IDA) или
  Ghidra-скрипты восстанавливают имена.
- **Известные адреса периферии.** Запись по адресу `0x4002_xxxx` — это UART,
  `0x4001_xxxx` — таймер и т.д. (карта конкретного MCU из datasheet).
- **Строки.** Даже в прошивке часто остаются строки-маркеры, версия, сообщения.

## Шаг 5: что искать в прошивке IoT

Типичные находки при анализе embedded:

- **Backdoor-аккаунты и токены.** Прячем в конфиге или в коде.
- **Проверка лицензии/пароля** — как наша `task_check`.
- **Хардкод-ключи** шифрования (часто одинаковые на всех устройствах).
- **Небезопасные обновления** (OTA без подписи).
- **Отладочные интерфейсы**, оставленные включёнными (см. урок про hardware).

## Шаг 6: карта памяти и линкер

Прошивка — это не просто код, а карта памяти, собранная **линкером** по
**linker script**. Типичные области:

- **Flash** (обычно `0x08000000` на STM32) — код и константы, только чтение.
- **RAM** (`0x20000000`) — переменные, стек, куча.
- **Периферия** (`0x40000000`+) — регистры устройств (UART, SPI, таймеры).

В прошивке переменные с начальными значениями живут в двух местах: сами
значения лежат в flash (секция `.data`), а при старте `Reset_Handler` копирует
их в RAM. Если этого не учесть, значения «не сойдутся». Именно поэтому в анализе
embedded первым делом определяют регионы памяти из linker script или из map-файла.

Полезный приём: если в образе видны строки-заголовки или структура (например,
`hsqs` — squashfs), это подсказывает, что часть прошивки — это файловая система,
а не код (см. урок про эмуляцию прошивок).

## Шаг 7: динамика на устройстве

Статики мало: удобно смотреть, как прошивка работает. Варианты:

- **Отладка по SWD/JTAG** (см. урок про hardware-debug) — полный контроль,
  точки останова, чтение памяти.
- **UART-консоль** — часто остаётся включённой и печатает логи.
- **Эмуляция** — запуск кода без железа (QEMU, Unicorn).

Для FreeRTOS особенно полезно смотреть переключения задач: планировщик
использует исключения `SysTick` и `PendSV`, и по ним видно, какие задачи
реально работают.

## Частые вопросы

**Прошивка не дизассемблируется.** Скорее всего, неверный базовый адрес или
архитектура (ARM vs Thumb). Уточни MCU из маркировки или datasheet.

**Нет ни одной строки.** Возможно, строки зашифрованы или сжаты — ищи
распаковщик в начале прошивки (как в уроке про распаковку).

**Как понять, что это FreeRTOS?** По вызовам `xTaskCreate`, символу
`pxCurrentTCB`, обработчикам `PendSV`/`SysTick` и структурам TCB.

## Инструмент: binwalk — поиск вложенных форматов

`binwalk` ищет внутри файла сигнатуры других форматов — архивы, ФС, сжатые данные — и при необходимости извлекает их.

Ключи, которые пригодятся:
* `binwalk firmware.bin` — сканировать на вложенные форматы;
* `binwalk -e firmware.bin` — извлечь найденное в `_firmware.bin.extracted/`;
* `binwalk -E firmware.bin` — энтропия (видно шифрование/сжатие);
* `binwalk -eM` — рекурсивное извлечение.

### Рабочий пример (как в лаборатории)

```
$ binwalk binwalk firmware.bin
DECIMAL       HEXADECIMAL     DESCRIPTION
0             0x0             ARM exception vector table
128           0x80            FreeRTOS task list (ASCII)
```

Подсказка из лаборатории: `binwalk <файл> — сигнатурный анализ образа`.

## Что мы теперь знаем

- В embedded-коде нет ОС: старт идёт от **таблицы векторов** и
  `Reset_Handler`; всё зависит от **базового адреса** загрузки.
- ARM Thumb собирает 32-битные константы через `movw`/`movt`; аргументы — в
  `r0–r3`; возврат — `bx lr`.
- В нашем примере `movw/movt` дали FNV offset basis `0x811c9dc5` и прайм
  `0x1000193`, а `str r1,[r2]` записал `checksum`.
- **FreeRTOS** даёт задачи (`xTaskCreate`), планировщик и примитивы
  синхронизации; их восстанавливают по вызовам и структурам.
- Символы и типы восстанавливают сигнатурами, картой периферии и строками.
