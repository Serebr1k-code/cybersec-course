## Вопрос, с которого всё начинается

У тебя есть бинарник `solver` из научного пакета. Он собран не на C и не на Rust: в строках мелькают `__gfortran_` и имена процедур с подчёркиваниями. Это Fortran. Как читать такой код и не утонуть в рантайме?

## Наш пример

Смотрим на файл:

```
$ file solver
solver: ELF 64-bit LSB pie executable, x86-64, dynamically linked
```

Обычный ELF. Значит, машинный код стандартный, а особенности — в соглашениях вызова и рантайме. Именно это и создаёт «экзотику».

## Шаг 1: чем Ada и Fortran отличаются в бинарнике

Компиляторы Fortran (gfortran) и Ada (GNAT) генерируют обычный x86-64 код, но добавляют **runtime-библиотеки**: `libgfortran`, `libgnat`. Они реализуют операции с массивами, строки, обработку исключений и ввод-вывод.

Из-за этого бинарник выглядит «слоёным»: твоя логика вызывает `_gfortran_*`-функции, которые делают арифметику над массивами. Реверс-инженер должен уметь отделять свой код от библиотечного.

## Шаг 2: имена символов и mangling

Fortran обычно не искажает имена так агрессивно, как C++. Имя процедуры `solve` превращается в `solve_` (один подчёркивающий символ — соглашение gfortran). Модули дают префикс: процедура в модуле `math` станет `__math_MOD_solve`.

Ada (GNAT) использует более сложную схему: `pkg__proc` (двойное подчёркивание для вложенности), а в отладочных сборках имена почти читаемы. Символы видны в `nm`:

```
$ nm solver | grep -i solve
0000000000001234 T solve_
0000000000001280 T __math_MOD_gradient
```

Это уже карта функций. По ней восстанавливается структура программы.

## Шаг 3: массивы и научные циклы

Научный код — это циклы по массивам. Fortran хранит массивы **по столбцам** (column-major), в отличие от C (row-major). Это критично при реверсе: обращение `A(i,j)` в памяти идёт по формуле `A + (i + j*N)`, а не `A + (i*N + j)`.

Типичный цикл выглядит как тройная вложенность с плавающей точкой:

```
  movsd  xmm0, [rsi+rax*8]
  mulsd  xmm0, xmm1
  addsd  xmm2, xmm0
```

`movsd`/`mulsd`/`addsd` — операции с double. Узнав их, ты понимаешь: это численное суммирование, скалярное произведение или свёртка.

## Шаг 4: соглашения вызова

gfortran передаёт аргументы по ссылке (адресу), а не по значению: даже скаляр `x` передаётся как указатель. Дополнительно в конце списка часто идут скрытые аргументы — длины строк и массивов.

Поэтому сигнатура `void foo(int* a, double* x, int* n)` в листинге на самом деле может иметь больше параметров. Понимая это, ты не путаешь «лишние» аргументы с реальными.

## Шаг 5: находим строки и версии

Runtime-библиотеки оставляют характерные строки:

```
$ strings -n 5 solver | head
GNU Fortran 13.2.0
__gfortran_st_write
nto{f0rtr4n_c0lumn_m4j0r}
```

Артефакт найден. Строки версии компилятора важны: по ним подбирают сигнатуры FLIRT и восстанавливают имена библиотечных функций, а `nto{...}` в реальном анализе был бы ключом, URL или именем модуля.

## Шаг 6: Ada и надёжность

Ada создавали для надёжных систем (авионика, военка), поэтому в её бинарниках много проверок: границы массивов, диапазоны, исключения. GNAT генерирует вызовы `__gnat_rcheck_*` при нарушении. Это подсказки: там, где стоит проверка границ, — работа с массивом; там, где обработка исключений, — критичный участок.

## Что мы теперь знаем

- Ada/Fortran дают обычный машинный код плюс runtime (`libgfortran`/`libgnat`).
- Fortran искажает имена слабо (`solve_`), Ada — через `pkg__proc`.
- Fortran хранит массивы по столбцам (column-major) — это меняет индексацию.
- Аргументы передаются по ссылке, часто со скрытыми длинами.
- Строки версии компилятора помогают восстановить библиотечные символы.
