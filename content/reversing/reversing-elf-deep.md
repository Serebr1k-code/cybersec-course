## Вопрос, с которого всё начинается

Мы знаем, что в `crackme` есть секции и сегменты. Но как программа, которая лишь ссылается на
`strcmp`, в итоге вызывает код из библиотеки `libc`, лежащий в другом файле? Где записано,
что ей нужен `libc.so.6`, и как адрес `strcmp` попадает в вызов?

Ответ — в **динамических таблицах** ELF. В этом уроке мы разберём ELF до конца: прочитаем
заголовок, динамическую секцию, таблицу символов и релокации — и поймём, как работает
динамическая линковка «под капотом».

## Наш пример

Всё тот же `crackme`, динамически слинкованный. Инструмент — `readelf`. Начнём с заголовка и
обратим внимание на два указателя в конце:

```bash
$ readelf -h crackme | tail -9
  Entry point address:               0x1080
  Start of program headers:          64 (bytes into file)
  Start of section headers:          14224 (bytes into file)
  Number of program headers:         14
  Number of section headers:         30
  Section header string table index: 29
```

Два «оглавления» лежат по смещениям 64 (program headers) и 14224 (section headers). Оба мы
уже видели: program headers — это сегменты (`-l`), section headers — секции (`-S`).

## Шаг 1: таблица символов — что программа «импортирует»

Динамически слинкованной программе нужен список функций, которые она берёт извне. Он лежит в
секции `.dynsym` (динамические символы). Посмотреть его можно через `readelf -s --dyn-syms`
или короче — `objdump -T`:

```bash
$ objdump -T crackme | grep -E 'strcmp|printf|read'
0000000000000000      DF *UND*  0000000000000000 (GLIBC_2.2.5) printf
0000000000000000      DF *UND*  0000000000000000 (GLIBC_2.2.5) read
0000000000000000      DF *UND*  0000000000000000 (GLIBC_2.2.5) strcmp
```

`*UND*` — символ «не определён здесь» (undefined), то есть берётся из библиотеки. Рядом
указана версия (`GLIBC_2.2.5`) — ABI-метка. Адрес `0000000000000000` потому, что настоящий
адрес ещё неизвестен: он появится при загрузке.

Список имён (строки вроде `strcmp`) хранится отдельно — в секции `.dynstr`. Это «таблица
строк» для символов.

## Шаг 2: динамическая секция — что загрузить

Теперь ключевой раздел — `.dynamic`. Он говорит загрузчику, какие библиотеки подключить и где
искать таблицы. Читаем через `readelf -d`:

```bash
$ readelf -d crackme
Dynamic section at offset 0x2de0 contains 26 entries:
  Tag        Type                 Name/Value
 0x0000000000000001 (NEEDED)     Shared library: [libc.so.6]
 0x0000000000000005 (STRTAB)     0x4b8
 0x0000000000000006 (SYMTAB)     0x3b0
 0x000000000000000a (STRSZ)      187 (bytes)
 0x000000000000000b (SYMENT)     24 (bytes)
 0x0000000000000003 (PLTGOT)     0x3fe8
 0x0000000000000017 (JMPREL)     0x690
 0x0000000000000014 (PLTREL)     RELA
```

Читаем по тегам:

- **NEEDED → libc.so.6** — вот ответ на вопрос урока: программе нужна библиотека `libc.so.6`.
- **STRTAB / SYMTAB** — адреса таблицы строк и таблицы символов (те, что из шага 1).
- **SYMENT = 24** — размер одной записи символа в байтах.
- **PLTGOT** — адрес таблицы GOT для вызовов через PLT (об этом в шаге 5).
- **JMPREL** — где лежат релокации для PLT.

Тег `NEEDED` может повторяться — тогда будет несколько библиотек. У нас одна.

## Шаг 3: релокации — «починить адреса при загрузке»

При PIE программа грузится по случайному адресу. Значит, все абсолютные адреса внутри неё
надо «пересчитать» под новую базу. Эта правка называется **релокацией**. Список правок —
`readelf -r`:

```bash
$ readelf -r crackme | head -12
Relocation section '.rela.dyn' at offset 0x5d0 contains 8 entries:
  Offset          Info           Type            Sym. Name + Addend
000000003dd0  000000000008 R_X86_64_RELATIVE                    1170
000000003fc0  000100000006 R_X86_64_GLOB_DAT  __libc_start_main + 0
000000003fc8  000200000006 R_X86_64_GLOB_DAT  _ITM_deregisterTM + 0
000000003fd0  000800000006 R_X86_64_GLOB_DAT  __gmon_start__ + 0
```

Два типа, которые надо узнавать:

- **R_X86_64_RELATIVE** — «прибавь базу загрузки к значению по этому смещению». Так правятся
  внутренние указатели (например, в `.init_array`).
- **R_X86_64_GLOB_DAT** — «запиши сюда настоящий адрес символа из библиотеки». Именно так
  адрес `__libc_start_main` попадает в таблицу.

Второй раздел, `.rela.plt`, относится к внешним вызовам:

```
Relocation section '.rela.plt' at offset 0x690 contains 5 entries:
000000004000  000300000007 R_X86_64_JUMP_SLO  puts + 0
000000004010  000500000007 R_X86_64_JUMP_SLO  printf + 0
000000004018  000600000007 R_X86_64_JUMP_SLO  read + 0
000000004020  000700000007 R_X86_64_JUMP_SLO  strcmp + 0
```

**JUMP_SLOT** — это ячейки, куда загрузчик положит реальные адреса `printf`, `read`, `strcmp`
при первом вызове. Их адреса (`0x4010`, `0x4018`, `0x4020`) лежат в `.got.plt`.

## Шаг 4: как это всё связано

Соберём цепочку для вызова `strcmp`:

1. В коде `main` стоит `call 1070 <strcmp@plt>` — вызов через «заглушку» `.plt`.
2. Заглушка `strcmp@plt` читает адрес из ячейки `.got.plt` (`0x4020`).
3. До первого вызова там лежит адрес «резолвера»; после — реальный адрес `strcmp` в `libc`.
4. Реальный адрес вписал загрузчик, используя релокацию `R_X86_64_JUMP_SLO` и символ
   `strcmp` из `.dynsym`.

Именно поэтому в дизассемблере мы видим `strcmp@plt`, а не адрес в libc: конкретный адрес
становится известен только во время работы.

## Шаг 5: DYNAMIC-сегмент и PLTGOT

Динамическая секция не просто «список» — она сама попадает в память отдельным сегментом
`DYNAMIC` (в `readelf -l` это `DYNAMIC 0x2de0 → VirtAddr 0x3de0 RW`). Загрузчик читает её в
первую очередь. А `PLTGOT = 0x3fe8` из шага 2 указывает на начало `.got.plt` — той самой
таблицы с адресами функций.

Вот как сходятся все части: **код** (`call ...@plt`) → **PLT-заглушка** → **GOT-ячейка** →
**адрес из libc**, который вписал загрузчик по **релокации** из **`.dynsym`**, найдя библиотеку
по тегу **NEEDED**.

Полезно запомнить разницу двух таблиц: `.got` хранит адреса, известные сразу (релокации
`GLOB_DAT`), а `.got.plt` — те, что разрешаются лениво при первом вызове (`JUMP_SLOT`).
Разделение важно в pwn: защита RELRO закрывает `.got`, но `.got.plt` при Partial RELRO
остаётся записываемой.

## Шаг 6: в реальной задаче

Что делать с этим знанием на CTF:

- Хочешь список внешних функций — `objdump -T` или `readelf --dyn-syms`.
- Нужны библиотеки — `readelf -d | grep NEEDED`.
- Хочешь понять, какие адреса правятся при загрузке — `readelf -r`.
- Ищешь ячейку, куда указывает вызов — смотри `.got.plt` и релокации `JUMP_SLO`.

А если бинарник статический (`file` скажет `statically linked`), `.dynamic`, `.dynsym` и
`.plt` будут пусты или отсутствовать — вся библиотека вшита внутрь.

## Что мы теперь знаем

- Заголовок ELF ссылается на две таблицы: **program headers** (сегменты) и **section headers**
  (секции).
- **.dynsym** — список импортируемых символов (`*UND*`), **.dynstr** — их имена.
- **.dynamic** с тегом **NEEDED** называет нужные библиотеки (`libc.so.6`).
- **Релокации** (`readelf -r`) правят адреса: `RELATIVE` — внутренние, `GLOB_DAT`/`JUMP_SLO` —
  внешние.
- Цепочка вызова: `call @plt` → `.got.plt` → адрес из libc, вписанный загрузчиком.

Теперь у нас есть полная картина «как устроен и как грузится ELF». Следующий шаг — перейти от
файла к **анализу кода**: как искать нужную функцию в большой программе, как работать с

запомни: `readelf -d` — зависимости, `-r` — релокации, `objdump -T` — импорты.

## Где пригодится

- **CTF Reversing:** разбор ELF-контейнера, поиск импортов и зависимостей без запуска.
- **Pwn:** понимание GOT/PLT и релокаций — основа для перехвата вызовов и ret2plt.
- **Malware analysis:** NEEDED и импорты выдают, что образец читает/пишет/ходит по сети.
- **Патчинг:** правка GOT/PLT — способ перехватить функцию, не трогая код.
- **Собес:** «как работает динамическая линковка», «что такое релокация» — вопросы уровня middle+.
