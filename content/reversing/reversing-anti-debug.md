## Вопрос, с которого всё начинается

Ты ставишь точку останова в `gdb`, запускаешь — и вместо нормальной работы программа печатает «Debugger detected!» и выходит. Это **анти-отладка**: бинарник сам проверяет, не следят ли за ним, и меняет поведение. Малварь и защищённое ПО делают так специально. Как понять, что именно проверяется, и как обойти защиту?

## Наш пример

Возьмём бинарник `antidebug`. Сначала запустим его нормально:

```bash
$ ./antidebug
Running clean
```

Работает. Теперь — под отладчиком:

```bash
$ gdb -q -batch -ex 'break main' -ex 'run' -ex 'continue' --args ./antidebug
Breakpoint 1, 0x000055555555514d in main ()
Debugger detected!
[Inferior 1 (process 243742) exited with code 01]
```

Программа **знает**, что её отлаживают. Как? Разберём её `main`:

```text
0000000000001149 <main>:
    114d: mov    $0x0,%ecx
    1152: mov    $0x0,%edx
    1157: mov    $0x0,%esi
    115c: mov    $0x0,%edi
    1161: call   1040 <ptrace@plt>
    1166: test   %rax,%rax
    1169: jns    1181 <main+0x38>
    116b: lea    ... "Debugger detected!"
```

Видим вызов `ptrace` с нулевыми аргументами и проверку результата. Разберём, что это значит.

## Шаг 1: ptrace — классический детект

`ptrace` — системный вызов, которым отладчик управляет процессом. Первый аргумент — код запроса. `0` — это **`PTRACE_TRACEME`**: «разреши отлаживать меня родителю». Тонкость в том, что **отлаживать процесс может только один «родитель»**. Если процесс уже под отладчиком, повторный `PTRACE_TRACEME` завершается ошибкой `-1` (`EPERM`).

Отсюда простейшая проверка:

```c
if (ptrace(PTRACE_TRACEME, 0, 0, 0) < 0) {
    puts("Debugger detected!");
    return 1;
}
```

В ассемблере это ровно то, что мы видим: `call ptrace`, `test %rax,%rax`, `jns` («jump if not sign» — если результат не отрицательный, всё хорошо) на нормальную ветку; иначе — «Debugger detected». Это самая распространённая техника на Linux.

## Шаг 2: другие способы детекта

`ptrace` — не единственный приём. Частые:

- **Timing-проверки** — замеряют время выполнения участка: под отладчиком с точками останова оно аномально большое.
- **Self-debug** — процесс сам становится отладчиком своего форка; если не вышло, значит, кто-то уже отлаживает.
- **Проверка `TracerPid`** — чтение `/proc/self/status`: если `TracerPid != 0`, есть отладчик.
- **Сигналы и исключения** — `SIGTRAP`-обработчики, ловушки на инструкции.
- **Проверка окружения** — переменные `LD_PRELOAD`, наличие `gdb`/`frida` в системе.

Каждый способ оставляет в коде узнаваемый след: вызов `ptrace`, чтение `/proc/self/status`, вызовы `clock_gettime` вокруг кода. По ним защиту и опознают.

## Шаг 3: как обойти ptrace-проверку

Раз мы знаем, что проверка — это `ptrace`, вариантов несколько:

1. **Патч ветки** — NOP-нуть `call ptrace` или инвертировать `jns` (как в уроке про патчинг). Тогда проверка не сработает.
2. **Патч в памяти** — в `gdb`: перейти сразу на нормальную ветку, пропустив проверку.
3. **Перехват `ptrace`** — `LD_PRELOAD`-хук, который всегда возвращает 0; для этого пишем свою `ptrace`, экспортируемую из `.so`:

```c
long ptrace(int req, ...) { return 0; }   // всегда «не отлаживают»
```

4. **Frida** — хук на `ptrace` из JS: подменить возврат.

Самый быстрый на CTF — патч ветки; самый «чистый» — `LD_PRELOAD`/Frida, потому что не меняет файл.

## Шаг 4: как обходить остальные проверки

- **Timing** — замени вызовы таймера (`clock_gettime`, `rdtsc`) на константу или NOP-ни их.
- **TracerPid** — хук на чтение `/proc/self/status` или подмена содержимого.
- **Self-debug** — патч/хук соответствующей ветки.
- **Анти-анти-отладка** — на Windows есть `ScyllaHide` (плагин x64dbg), который прячет отладчик от большинства проверок; на Linux аналог — Frida + набор хуков.

Общий принцип один: **найти проверку и нейтрализовать её** — патчем или хуком. Вопрос лишь в том, сколько проверок и где они спрятаны.

## Шаг 5: порядок работы с защищённым бинарником

1. **Запусти под отладчиком** — если падает/ведёт себя странно, есть анти-отладка.
2. **Найди строки-подсказки** — `strings | grep -i debug` часто выдаёт «Debugger detected».
3. **Найди системные вызовы** — `ptrace`, `/proc/self/status`, таймеры.
4. **Проверь гипотезу** — поставь точку останова на подозрительный вызов и посмотри результат.
5. **Обойди** — патч ветки или хук (`LD_PRELOAD`/Frida).
6. **Продолжай анализ** — возможно, за анти-отладкой есть ещё слои (anti-VM, anti-tamper).

## Шаг 6: на что смотреть дальше

- **Несколько проверок** — часто их не одна; обход первой может открыть вторую.
- **Проверки в конструкторах** — код может выполняться до `main` (`__attribute__((constructor))`, TLS-колбэки).
- **Условное поведение** — анти-отладка может не падать, а тихо искажать результат; следи за логикой.
- **Инструменты** — `gdb` + патч, Frida, `LD_PRELOAD`; на Windows — ScyllaHide/x64dbg.
- **Сочетание с анти-VM/anti-tamper** — это отдельные уроки этой ветки.

## Шаг 7: полный пример обхода через LD_PRELOAD

Разберём обход по шагам на нашем `antidebug`. Пишем библиотеку-хук:

```c
long ptrace(int req, void *a, void *b, void *c) { return 0; }
```

Собираем и запускаем программу с подменой:

```bash
$ gcc -shared -fPIC -o nohook.so hook.c
$ LD_PRELOAD=./nohook.so ./antidebug
Running clean
```

Программа больше не видит отладчика — её собственный вызов `ptrace` перехвачен и возвращает 0. Теперь её можно спокойно запустить под `gdb` с `LD_PRELOAD`:

```bash
$ gdb -q --args env LD_PRELOAD=./nohook.so ./antidebug
```

Так обходятся и timing-проверки (хукаем `clock_gettime`), и `TracerPid` (хукаем `open`/`read` на `/proc/self/status`). Идея одна: перехватить функцию, через которую идёт детект, и подменить её поведение. Это быстрее и чище, чем искать и патчить каждую ветку вручную.

## Шаг 8: анти-анти-отладка как борьба

На практике это гонка: защита добавляет проверку — ты добавляешь хук. Полезно помнить:

- **Проверок много** — `ptrace`, `/proc`, таймеры, сигналы; обход должен покрыть все.
- **Проверки до `main`** — конструкторы и TLS-колбэки; не пропусти их.
- **Скрытая логика** — детект может не падать, а портить данные; следи за результатами.
- **Инструменты-комбайны** — ScyllaHide (Windows) автоматически прячет отладчик от десятков проверок; на Linux аналоги собирают из хуков Frida.

## Инструмент: objdump — дизассемблер

`objdump` показывает машинный код бинарника в виде ассемблера. Именно по нему считают смещения буферов, находят вызовы и адреса — основа статического разбора.

Ключи, которые пригодятся:
* `objdump -d <файл>` — дизассемблировать секцию `.text` (машинный код функций);
* `objdump -d <файл> | less` — листать вывод, искать нужную функцию по имени;
* `objdump -M intel -d <файл>` — синтаксис Intel (привычнее, чем AT&T);
* в выводе важны пролог функции (`push rbp; mov rbp,rsp`) и `sub rsp,N` — по нему видно размер кадра.

## Что мы теперь знаем

- Анти-отладка — самопроверка бинарника на наличие отладчика.
- Классика Linux — `ptrace(PTRACE_TRACEME)`: под отладчиком возвращает `-1`.
- Другие приёмы: timing, `TracerPid`, self-debug, проверки окружения.
- Обход: патч ветки, `LD_PRELOAD`-хук, Frida; на Windows — ScyllaHide.
- Принцип один — найти проверку и нейтрализовать её, затем идти дальше.

## Куда дальше

Анти-отладка — лишь один слой защиты. Рядом стоят **anti-VM** (детект виртуалки) и **anti-tamper** (проверки целостности, которые замечают патч). Их разбираем в следующих уроках. А пока запомни: `ptrace` → `test/jns` → «Debugger detected» — и ты уже знаешь, где патчить.

## Частые вопросы

- **Хук не срабатывает** — проверь, что символ `ptrace` действительно перехватывается (функция может вызываться напрямую через `syscall`).
- **Программа всё равно детектит** — есть вторая проверка (timing, `/proc`); обходи все.
- **На Windows другой набор** — там `IsDebuggerPresent`, `NtQueryInformationProcess`; используй ScyllaHide.
- **Проверка до `main`** — ищи конструкторы и TLS-колбэки.

## Где пригодится

- **CTF Reversing (hard):** обход анти-отладки — обязательный навык для сложных задач.
- **Malware analysis:** малварь прячется от отладчиков; нейтрализация проверок открывает поведение.
- **Анализ защищённого ПО:** лицензионная защита часто включает анти-отладку.
- **Инструменты:** ScyllaHide (Windows), Frida и LD_PRELOAD (Linux) — стандартный арсенал обхода.
