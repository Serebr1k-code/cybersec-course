## Задача

У нас есть бинарник `symcheck`. Он просит ключ из 4 символов и проверяет его **несколькими
условиями сразу**. Подбирать вручную больно: нужно угадать 4 байта, каждый из которых
участвует в своём уравнении.

```bash
$ printf 'aaaa\n' | ./symcheck
key: Wrong.
```

Вместо перебора применим **символьное исполнение**: представим ввод как неизвестные, соберём
условия и отдадим их **SMT-решателю** (программе, которая находит значения переменных,
удовлетворяющие системе уравнений).

## Что такое символьное исполнение

Обычное исполнение идёт по одному пути с конкретными значениями. Символьное трактует вход
как символ `x` и, дойдя до ветвления `if (x == 5)`, создаёт **два состояния** — с условием
`x == 5` и `x != 5` — и продолжает оба. К концу пути накапливается система ограничений, а
решатель (обычно **z3**) находит конкретный `x`, который ей удовлетворяет.

Применения: crackme, обход проверок, генерация входов для фаззинга, поиск пути к уязвимости.

## Данные: читаем проверку

Дизассемблируем функцию `check`:

```bash
$ objdump -d --no-show-raw-insn --disassemble=check symcheck
  40117e:	cmp    $0x4,%rax          # длина ввода == 4
  401182:	je     40118e
  4011ca:	add    %edx,%eax          # a + b
  4011cc:	cmp    $0xd2,%eax         # == 210 (0xd2)
  4011d1:	je     4011da
  4011de:	xor    -0x2(%rbp),%al     # b ^ c
  4011e1:	cmp    $0xb,%al           # == 11 (0xb)
  4011e3:	je     4011ec
  4011f4:	sub    %eax,%edx          # d - c
  4011f6:	cmp    $0x1,%edx          # == 1
  4011f9:	je     401202
  401206:	xor    -0x1(%rbp),%al     # a ^ d
  401209:	cmp    $0x6,%al           # == 6
  40120b:	je     401214
```

Читаем четыре условия (обозначим байты `a,b,c,d`):

1. `a + b == 210`
2. `b ^ c == 11`
3. `d - c == 1`
4. `a ^ d == 6`

## Шаг 1: решаем систему через z3

Вручную такую систему решать долго. Опишем её на Python и отдадим z3. Переменные — 8-битные
(`BitVecs(..., 8)`), потому что это байты:

```python
import z3
a, b, c, d = z3.BitVecs('a b c d', 8)
s = z3.Solver()
s.add(a + b == 210)
s.add(b ^ c == 11)
s.add(d - c == 1)
s.add(a ^ d == 6)
print(s.check())          # sat — решение существует
m = s.model()
print(bytes([m[a].as_long(), m[b].as_long(), m[c].as_long(), m[d].as_long()]))
```

Запускаем:

```bash
$ python3 solve.py
sat
b'kglm'
```

z3 нашёл ключ `kglm`. Проверяем его на реальном бинарнике:

```bash
$ printf 'kglm\n' | ./symcheck
key: Correct!
```

Сработало. Мы нашли валидный ввод, разобрав четыре условия и не перебирая 4 миллиарда
комбинаций.

## Шаг 2: важный нюанс — решений может быть много

Проверим другой ключ, `code` (99,111,100,101):

```bash
$ printf 'code\n' | ./symcheck
key: Correct!
```

Оба проходят! `a+b=210`, `b^c=11`, `d-c=1`, `a^d=6` — для `code`: `99+111=210`, `111^100=11`,
`101-100=1`, `99^101=6`. Символьное исполнение находит **один** удовлетворяющий вход, а не
обязательно «тот самый». Для CTF это неважно (любой проходящий ключ даёт флаг), но держи в
голове: решатель не восстанавливает «оригинал».

## Шаг 3: angr — символьное исполнение «из коробки»

Мы вручную выписали условия из дизассемблера. **angr** делает это сам: он исполняет программу
символьно, исследует пути и собирает ограничения. Главный инструмент — `explore`:

```python
import angr

proj = angr.Project("./symcheck", auto_load_libs=False)
state = proj.factory.entry_state()
simgr = proj.factory.simulation_manager(state)
simgr.explore(find=lambda s: b"Correct" in s.posix.dumps(1),
              avoid=lambda s: b"Wrong"  in s.posix.dumps(1))
if simgr.found:
    print(simgr.found[0].posix.dumps(0))   # stdin, ведущий к успеху
```

Разберём ключевые части:

- **`auto_load_libs=False`** — обязательно: не грузить системные библиотеки, иначе анализ
  «взорвётся» по числу путей.
- **`find`/`avoid`** — цели и запреты. Их можно задавать адресами (`find=0x401234`) или
  предикатами по выводу (`b"Correct" in s.posix.dumps(1)`). Предикат по строкам устойчивее к
  пересборке.
- **`simgr.found[0].posix.dumps(0)`** — извлечь stdin найденного состояния.

Как и раньше, финальный шаг — **проверить вход на реальном бинарнике**. angr даёт гипотезу,
запуск подтверждает.

## Шаг 4: хуки — обязательны для libc

Внешние функции (`strlen`, `strcmp`, `memcpy`) angr по умолчанию пытается исполнять по коду,
что медленно и часто ломается. Их **хукают** — подменяют готовой моделью:

```python
proj.hook(0x401100, angr.SIM_PROCEDURES["libc"]["strlen"]())
# или своя реализация
class MyHook(angr.SimProcedure):
    def run(self, arg):
        return self.state.solver.BVV(0, 32)
proj.hook(0x401200, MyHook())
```

У angr есть встроенные `SimProcedures` для libc. Если функция «неизвестна» и тормозит
анализ — хукай.

## Шаг 5: взрыв путей и как с ним жить

Число состояний растёт экспоненциально с числом ветвлений; циклы особенно опасны — это
**path explosion**. Приёмы борьбы:

- **Хуки** тяжёлых функций (крипта, хеши).
- **Ограничения на вход**: формат, длина, алфавит (`flag{...}`, печатные символы).
- **`avoid`** — отсекать бесполезные пути.
- **`veritesting=True`** — слияние похожих путей.
- **Разбиение задачи** — анализировать функцию проверки отдельно от `main` (`call_state`).

```python
state = proj.factory.entry_state(args=["./symcheck", arg])
for byte in arg.chop(8):
    state.solver.add(byte >= 0x20, byte <= 0x7e)   # только печатные
```

## Шаг 6: файловый ввод и `call_state`

Проверка не всегда читает stdin. Иногда ввод приходит из файла или через аргумент, а сама
проверка — отдельная функция. angr умеет и то, и другое:

```python
# символьный файл, который читает программа
state = proj.factory.entry_state()
state.fs.insert("/tmp/input", angr.SimFile("/tmp/input", size=32))

# или войти сразу в функцию проверки с символьным аргументом
arg = claripy.BVS("arg", 8*16)
state = proj.factory.call_state(0x401166, arg)   # 0x401166 — адрес check
simgr = proj.factory.simulation_manager(state)
simgr.explore(find=0x401214)
print(simgr.found[0].solver.eval(arg, cast_to=bytes))
```

`call_state` экономит время: не нужно символьно исполнять весь пролог программы до `check` —
мы сразу входим в интересную функцию. Для символьного файла задаётся размер, а внутри можно
наложить ограничения на содержимое. Такой подход особенно полезен, когда до проверки
выполняется много неинтересного кода (инициализация, парсинг).

## Если не сработало

- **Очень медленно / висит** — забыт `auto_load_libs=False`; не захукана libc; добавь
  veritesting и ограничения.
- **Нет `found`** — неверная цель; проверь адреса/строки, добавь `avoid`.
- **Мусорный вход** — решатель вернул любое решение; наложи ограничения на формат.
- **Криптохеш (SHA-256)** — символьное решение прообраза непрактично; хукай хеш или решай
  перебором.

## Что мы теперь знаем

- Символьное исполнение трактует ввод как неизвестные и накапливает ограничения по путям.
- SMT-решатель (z3) находит конкретный вход, удовлетворяющий системе — как мы решили `symcheck`.
- Решений может быть много; решатель возвращает **одно**, не обязательно «оригинал».
- angr автоматизирует это: `entry_state` → `explore(find, avoid)` → извлечь stdin.
- `auto_load_libs=False`, хуки libc и ограничения входа — обязательны; финал всегда — проверка
  запуском.

## Куда дальше

Символьное исполнение — мощный автоматический метод, но у него есть пределы: взрыв путей,
непрактичность на криптографии. Дальше мы перейдём к **отладке** — умению заглянуть в
работающую программу и увидеть, откуда берётся значение. А пока главное запомни: **символьное
исполнение предлагает вход, а запуск бинарника его подтверждает.**

## Где пригодится

- **CTF Reversing (expert):** обход длинных цепочек проверок, VM, обфускации.
- **Автоматический поиск входов:** когда ручной реверс дорог, angr экономит часы.
- **Malware analysis:** поиск ввода, активирующего определённое поведение.
- **Vuln research:** генерация ввода, достигающего опасного участка кода.
- **Собес:** вопросы про символьное исполнение, z3, path explosion — маркер продвинутого RE.
