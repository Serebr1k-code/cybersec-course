Многие задачи реверса — это не про код внутри бинарника, а про **данные, которые он гоняет по сети**.
Протокол может быть проприетарным, бинарным, зашифрованным, с состоянием и мультиплексированием.
Умение вскрывать неизвестный протокол — навык, который применяется в malware-анализе (C2), IoT
(прошивки), играх (клиент-сервер) и API-реверсе. Этот урок — про методику: от захвата трафика до
реконструкции формата сообщений и воспроизведения сессии.

## С чего начать: захват и первичный анализ

Первый шаг — получить трафик:

```bash
# tcpdump
tcpdump -i eth0 -w capture.pcap host 10.0.0.5 and port 4444

# Wireshark (GUI) или tshark (CLI)
tshark -r capture.pcap -Y "tcp.port==4444" -x | head -50
```

Полезные фильтры Wireshark:
```text
tcp.port == 4444
ip.addr == 10.0.0.5
tcp.flags.syn == 1 && tcp.flags.ack == 0
data.len > 0
tcp contains "GET"
```

Первичные вопросы: **TCP или UDP? Есть ли TLS? Текстовый или бинарный протокол? Есть ли
длина/магия? Кто инициирует?**

## Разобранный пример: бинарный протокол C2

Дано: malware общается с сервером на порт 8443 (не TLS). Захватываем трафик.

**Шаг 1. Follow stream.** Wireshark → правый клик на пакете → `Follow → TCP Stream`. Видим:
```text
00000000  41 43 01 00 10 00 00 00  48 65 6c 6c 6f 2c 20 73  AC......Hello, s
00000010  65 72 76 65 72 21                                 erver!
```

**Шаг 2. Гипотеза формата.**
```c
struct msg {
    char magic[2];      // "AC"
    uint8_t cmd;        // 0x01
    uint8_t flags;      // 0x00
    uint32_t len;       // 0x00000010 = 16
    char payload[16];   // "Hello, server!"
};
```

**Шаг 3. Проверка.** Смотрим следующий пакет — magic `AC`, другой `cmd`, `len` совпадает с длиной
payload. Формат подтверждён (little-endian `len`).

**Шаг 4. Парсер на scapy.**
```python
from scapy.all import TCP, IP, Raw, rdpcap
pkts = rdpcap("capture.pcap")
for p in pkts:
    if p.haslayer(Raw) and p[TCP].dport == 8443:
        d = bytes(p[Raw].load)
        if d[:2] == b"AC":
            cmd, flags = d[2], d[3]
            ln = int.from_bytes(d[4:8], "little")
            print("cmd=%02x len=%d payload=%r" % (cmd, ln, d[8:8+ln]))
```

**Шаг 5. Реконструкция сессии.** Собираем все сообщения по порядку — получаем диалог. По нему
восстанавливаем команды (0x01 = hello, 0x02 = execute, ...).

**Шаг 6. Эмуляция клиента.** Пишем scapy-скрипт, который отправляет свои сообщения серверу —
проверяем гипотезы о командах.

## Протоколы с состоянием: конечные автоматы

Реальные протоколы имеют **состояния** (handshake → auth → session → close). Методика:

1. Собрать много сессий (разные сценарии).
2. Выделить сообщения и их типы (по `cmd`/`type`).
3. Построить граф переходов: какое сообщение за каким следует.
4. Найти обязательные поля (nonce, session-id, seq).

Инструмент **Netzob** умеет выводить грамматику протокола автоматически по набору сообщений.
**Canape** — интерактивный анализ и генерация.

## TLS и шифрование

Если трафик зашифрован, есть несколько путей:

- **TLS key logging.** Установите `SSLKEYLOGFILE` (переменная окружения) для клиента — Wireshark
  расшифрует сессию (`Preferences → Protocols → TLS → (Pre)-Master-Secret log filename`).
- **Дамп ключей из памяти.** Извлеките мастер-ключ/сессионные ключи из процесса (например, через
  Frida-скрипты для OpenSSL/BoringSSL).
- **MITM.** `mitmproxy` с поддельным сертификатом (если клиент не пинит сертификат). При certificate
  pinning — патч/хук проверки.
- **Собственная крипта.** Если протокол не TLS, а своя крипта — реверсим алгоритм (см. урок
  crypto-binaries) и расшифровываем.

## HTTP(S) API-реверс

Для веб-API процесс проще:

```bash
# перехват через mitmproxy
mitmproxy -p 8080
# клиент с прокси → смотрим запросы/ответы
# экспорт в спецификацию
mitmproxy2swagger -i flows -o api.yaml
```

Полезно: сравнить запросы разных действий, выявить параметры и их влияние, воспроизвести в `curl`:
```bash
curl -s -X POST https://api.target/v1/login \
  -H "Content-Type: application/json" \
  -d '{"user":"admin","pass":"x"}' | jq
```

## Разобранный пример: реверс игрового протокола

Дано: игра общается с сервером по UDP. Задача — понять, как движется персонаж.

**Шаг 1. Захват.** `tcpdump -i any udp port 27015 -w game.pcap`.

**Шаг 2. Анализ.** В Wireshark видим пакеты по 20–40 байт. Первые байты похожи на заголовок:
```text
seq(4) | type(1) | x(4) | y(4) | z(4) | ...
```

**Шаг 3. Корреляция.** Двигаем персонажа, смотрим, какие байты меняются. Плавное изменение →
координаты (float или fixed-point). Резкие скачки → события.

**Шаг 4. Интерпретация.** Пробуем `struct.unpack("<fff", data[5:17])` — получаем координаты. Сверяем
с положением в игре — совпадает.

**Шаг 5. Реконструкция.** Описываем все типы пакетов, строим клиент на Python, воспроизводим движение.

## Крайние случаи и подводные камни

- **Мультиплексирование.** Несколько логических потоков в одном TCP-соединении (как в HTTP/2) —
  нужен разбор фреймов и stream-id.
- **Сжатие.** Полезная нагрузка может быть zlib/gzip — ищите `78 9c`, `1f 8b`, пробуйте распаковать.
- **Фрагментация.** Сообщение может разбиваться на несколько пакетов — нужен буфер и сборка по длине.
- **Сериализация.** Protobuf/MessagePack/BSON имеют характерные байты; используйте `protoc --decode_raw`
  для protobuf.
- **Анти-replay.** Nonce/счётчики/таймстемпы мешают простому воспроизведению — их нужно генерировать.
- **Certificate pinning.** Мешает MITM — обходится Frida/патчем.
- **Endianness и alignment.** Бинарные протоколы могут использовать сетевой порядок (big-endian) —
  не путайте с little-endian полей.
- **Состояние на сервере.** Сервер может отвергать неожиданные сообщения — стройте сессию пошагово.

## Что дальше / решение

1. Захватить трафик (`tcpdump`/Wireshark), определить транспорт и шифрование.
2. Следовать потоку (`Follow Stream`), выделить сообщения.
3. Гипотеза формата → проверка на нескольких сообщениях.
4. Написать парсер (scapy/Python), собрать диалог.
5. Восстановить состояния/команды, эмулировать клиент.
6. При шифровании — достать ключи (keylog/Frida) или реверснуть крипту.

Принцип: **протокол — это грамматика**. Начните с алфавита (поля), затем слова (сообщения), затем
предложения (сессии). Автоматизируйте разбор как можно раньше — ручной анализ сотен пакетов не масштабируется.

## Сериализация: protobuf, MessagePack, BSON

Часто «неизвестный» протокол на самом деле — стандартная сериализация. Признаки:

- **Protocol Buffers**: компактные поля `tag = (field_number << 3) | wire_type`, часто начинается с
  небольших байтов; строки длиной-prefixed. Быстрый способ увидеть структуру без `.proto`:
  ```bash
  protoc --decode_raw < payload.bin
  ```
  Вывод покажет поля и их значения — так восстанавливается схема.
- **MessagePack**: байты `0x80–0x8f` (fixmap), `0x90–0x9f` (fixarray), `0xa0–0xbf` (fixstr).
  Парсится `msgpack` в Python.
- **BSON**: документ начинается с 4-байтовой длины (little-endian), внутри — типизированные поля.
  Парсится `bson` из `pymongo`.
- **CBOR**: похож на MessagePack, байты `0xa0+` (map), `0x80+` (array).

Если payload декодируется одним из этих форматов — не нужно реверсить бинарный протокол вручную;
описываем схему и работаем с ней.

## Разобранный пример: HTTP API с токеном

Дано: мобильное приложение общается с API. Задача — понять авторизацию.

**Шаг 1. MITM.** `mitmproxy -p 8080`, настроить прокси на устройстве, поставить CA. Видим запросы:
```http
POST /api/v2/login HTTP/1.1
Content-Type: application/json

{"user":"alice","pass":"..."}
```
Ответ: `{"token":"eyJ...","expires":3600}`.

**Шаг 2. Дальнейшие запросы.** Каждый содержит `Authorization: Bearer eyJ...`. Токен — JWT.
Декодируем:
```bash
python3 -c "import base64,json,sys; t='eyJ...'.split('.'); print(json.loads(base64.urlsafe_b64decode(t[1]+'==')))"
```
Видим claims (`sub`, `role`, `exp`).

**Шаг 3. Проверка подписи.** Если алгоритм `none`/HS256 с угадываемым секретом — можно подделать
токен (см. урок про JWT). Это уже не реверс протокола, а поиск слабости авторизации.

**Шаг 4. Воспроизведение.** Собираем `curl`-запросы и автоматизируем сценарий.

## Автоматизация: генерация фаззера по формату

Когда формат восстановлен, следующий шаг — **фаззинг**: подавать мутированные сообщения и искать
падения/аномалии. Scapy позволяет описать формат как класс:

```python
from scapy.all import Packet, ShortField, IntField, StrLenField, ByteEnumField

class C2Msg(Packet):
    name = "C2Msg"
    fields_desc = [
        StrLenField("magic", b"AC", length_from=lambda p: 2),
        ByteEnumField("cmd", 1, {1: "hello", 2: "exec", 3: "file"}),
        ByteField("flags", 0),
        IntField("len", None),
        StrLenField("payload", b"", length_from=lambda p: p.len),
    ]
```
Затем мутируем поля (`cmd`, `len`, `payload`) и шлём серверу — ищем обработку неверных значений
(переполнения, обходы). Это прямой путь к уязвимостям протокола.

## Чек-лист вскрытия протокола

1. Транспорт и шифрование определены.
2. Захвачено достаточно сессий (разные сценарии).
3. Сообщения выделены, границы определены (по длине/magic/таймауту).
4. Формат каждого типа сообщения описан.
5. Состояния/переходы восстановлены.
6. Парсер написан и проверен на всех захваченных данных.
7. Клиент эмулируется, сервер принимает сообщения.
8. При шифровании — ключи получены или крипта реверснута.
