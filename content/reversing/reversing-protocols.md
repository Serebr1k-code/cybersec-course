## Задача

Мы перехватили сетевой обмен приложения с сервером: файл `proto.pcap`. Wireshark показывает
обычный TCP с «hex-полезной нагрузкой» — своего разбора протокола у него нет, потому что
протокол **кастомный**. Нужно понять структуру сообщений: где заголовок, где данные, как
определяется длина.

Многие задачи реверса — это не код внутри бинарника, а **данные, которые он гоняет по сети**.
Умение вскрыть неизвестный протокол нужно для анализа malware C2, IoT-прошивок и клиент-серверных
игр.

## Данные: смотрим на трафик

Первое — прочитать pcap и увидеть полезную нагрузку:

```bash
$ tshark -r proto.pcap -T fields -e ip.src -e tcp.dstport -e tcp.payload
10.0.0.5	9999	feca01010c0061646d696e3a736563726574
10.0.0.9	41000	feca01020b0000746f6b5f396632623163
```

Два пакета: клиент → сервер (порт 9999) и ответ. Payload — hex-строки. Чтобы увидеть байты
по-человечески, используем «follow stream»:

```bash
$ tshark -r proto.pcap -q -z follow,tcp,hex,0
Node 0: 10.0.0.5:41000
Node 1: 10.0.0.9:9999
00000000  fe ca 01 01 0c 00 61 64  6d 69 6e 3a 73 65 63 72  ......ad min:secr
00000010  65 74                                             et
	00000000  fe ca 01 02 0b 00 00 74  6f 6b 5f 39 66 32 62 31  .......t ok_9f2b1
00000010  63                                                c
```

Читаем байты. Оба сообщения начинаются одинаково: `fe ca 01`. Дальше — разные байты, а в
конце виден ASCII: `admin:secret` и `tok_9f2b1c`.

## Шаг 1: гипотеза о структуре

Начнём с начала. Первые два байта `fe ca` повторяются в обоих сообщениях — это **магия**
(сигнатура протокола). В памяти (little-endian) она читается как `0xCAFE`. Дальше `01` —
похоже на версию. Потом байт, который различается (`01` и `02`) — **тип сообщения** (`cmd`).
Затем два байта длины: в первом `0c 00` (little-endian = 12), во втором `0b 00` (= 11).

Проверим: после заголовка в первом сообщении `admin:secret` — ровно **12** символов. Во втором
`00 tok_9f2b1c` — 11 байт. Длина совпадает! Формат подтверждён:

```text
struct msg {
    uint16_t magic;    // 0xCAFE
    uint8_t  version;  // 1
    uint8_t  type;     // 0x01 = login, 0x02 = response
    uint16_t length;   // длина payload, little-endian
    uint8_t  payload[length];
};
```

Ключевой момент: длина записана в **little-endian** (`0c 00`, а не `00 0c`). В сетевых
протоколах часто используют big-endian (сетевой порядок), но этот — локальный, поэтому
порядок байт надо определять по данным, а не угадывать.

## Шаг 2: пишем парсер

Опишем разбор на Python и проверим на обоих сообщениях:

```python
import struct
for f in ('proto_m1.bin', 'proto_m2.bin'):
    d = open(f, 'rb').read()
    magic, ver, t, ln = struct.unpack('<HBBH', d[:6])
    print(f"magic=0x{magic:04x} ver={ver} type=0x{t:02x} len={ln} payload={d[6:6+ln]!r}")
```

```text
magic=0xcafe ver=1 type=0x01 len=12 payload=b'admin:secret'
magic=0xcafe ver=1 type=0x02 len=11 payload=b'\x00tok_9f2b1c'
```

Теперь понятно: первое сообщение — логин (`type=0x01`), второе — ответ (`type=0x02`), где
первый байт payload `00` — код статуса (успех), а дальше токен `tok_9f2b1c`.

## Шаг 3: подтверждаем по бинарнику

Парсер — это гипотеза. Настоящее подтверждение — найти в бинарнике код, который **формирует**
эти сообщения. В дизассемблере ищи вызовы `send`/`recv`/`write` и рядом — обращение к
константе `0xCAFE`:

```bash
$ objdump -d --no-show-raw-insn ./client | grep -iE 'cafe|call.*(send|recv)'
```

Найдя функцию-сборщик, ты видишь точные смещения полей и порядок байт — уже не гипотезу, а
факт. Часто формат подтверждается именно так: сначала гипотеза по трафику, потом сверка с кодом.

## Шаг 4: протоколы с состоянием

Реальные протоколы — это **конечные автоматы**: `handshake → auth → session → close`. Методика:

1. Собрать много сессий (разные сценарии).
2. Выделить типы сообщений (по `type`/`cmd`).
3. Построить граф: какое сообщение за каким следует.
4. Найти обязательные поля (nonce, session-id, счётчик).

Инструменты **Netzob**/**Canape** умеют выводить грамматику протокола по набору сообщений. В
нашем случае автомат прост: `login (0x01)` → `response (0x02)`.

## Шаг 5: сериализация и шифрование

Иногда «неизвестный» протокол — это стандартная сериализация:

- **Protocol Buffers** — компактные поля; `protoc --decode_raw < payload.bin` покажет структуру
  без `.proto`.
- **MessagePack** — байты `0x80–0x8f` (map), `0x90–0x9f` (array), `0xa0–0xbf` (str).
- **BSON** — начинается с 4-байтовой длины; парсится `bson` из pymongo.
- **CBOR** — похож на MessagePack.

Если payload декодируется одним из них — не нужно реверсить бинарный протокол вручную.

Если трафик **зашифрован**, путей несколько: TLS key logging (`SSLKEYLOGFILE`, Wireshark
расшифрует сессию), дамп ключей из памяти (Frida-скрипты для OpenSSL), MITM (`mitmproxy` с
подменой сертификата, если нет pinning), либо реверс собственной крипты протокола.

## Шаг 6: собираем поток и разбираем его целиком

До сих пор мы смотрели на отдельные сообщения. Но TCP — это **поток байт без границ**: одно
сообщение может приехать двумя сегментами, а два сообщения — склеиться в один. Поэтому «прочитать
один пакет» не работает; нужен **буфер и разбор по полю длины**, которое мы уже нашли.

Правило простое: накапливай байты и, пока в буфере есть хотя бы 6 байт заголовка, читай `length`,
а затем жди, пока наберётся `6 + length` байт. Разобрал сообщение — сдвинь буфер и повторяй.

```python
import struct

def parse_stream(buf: bytes):
    out, i = [], 0
    while len(buf) - i >= 6:               # хватает на заголовок?
        magic, ver, t, ln = struct.unpack_from('<HBBH', buf, i)
        if magic != 0xCAFE:
            raise ValueError(f"bad magic 0x{magic:04x} at {i}")
        end = i + 6 + ln
        if end > len(buf):                 # тело ещё не доехало
            break
        out.append((t, buf[i + 6:end]))
        i = end
    return out, buf[i:]                    # (сообщения, остаток)

seg1 = bytes.fromhex('feca0101')                       # только 4 байта заголовка
seg2 = bytes.fromhex('0c0061646d696e3a736563726574')   # длина + тело
print(parse_stream(seg1))          # ([], b'\xfe\xca\x01\x01')  — ждём
print(parse_stream(seg1 + seg2))   # ([(1, b'admin:secret')], b'')
```

Вывод показывает главное: первый вызов вернул пустой список и весь буфер обратно (сообщение ещё не
полное), второй — уже разобранное сообщение. Именно так и должен вести себя устойчивый парсер:
**не падать на неполных данных, а ждать следующего сегмента**.

## Шаг 7: шпаргалка по «магиям»

Когда payload выглядит мусором, первым делом смотри первые байты — часто это сигнатура известного
формата, и реверс сводится к вызову готового парсера, а не к ручному разбору:

| Первые байты (hex) | Формат | Чем читать |
|--------------------|--------|-----------|
| `1f 8b` | gzip | `gunzip` |
| `78 9c` / `78 01` / `78 da` | zlib (deflate) | `zlib.decompress` |
| `42 5a 68` (`BZh`) | bzip2 | `bunzip2` |
| `fd 37 7a 58 5a 00` | xz | `xz -d` |
| `50 4b 03 04` (`PK..`) | ZIP / docx / jar | `unzip` |
| `7b` (`{`) | JSON | `jq` |
| `80`–`8f`, `a0`–`bf` | MessagePack (map/str) | `msgpack` |

В нашем случае первые байты — `fe ca`, и ни одна строка таблицы не подошла: значит, формат
действительно кастомный, и его надо реверсить руками, что мы и сделали.

## Как это же видят защитники

Знание формата нужно не только атакующему: если ты пишешь правило детекта, ты кодируешь те же поля.
Для нашего протокола правило Suricata опирается на магию и тип сообщения:

```text
alert tcp any any -> any 9999 (msg:"CAFE proto login"; \
  content:"|fe ca 01 01|"; depth:4; sid:1000001; rev:1;)
```

Здесь `content:"|...|"` — байты в hex, а `depth:4` ограничивает поиск первыми четырьмя байтами (то
есть позицией заголовка). Детект строится ровно на том, что мы восстановили: магия + версия + тип.
Если бы протокол был зашифрован, такой детект не работал бы — пришлось бы опираться на размеры и
тайминги пакетов, что куда менее надёжно.

## Если не сработало

- **Сообщение разбито на пакеты** — нужен буфер и сборка по полю длины (Шаг 6); не полагайся на границы TCP.
- **Поля «плывут»** — проверь порядок байт: сетевой (big-endian) vs little-endian.
- **Полезная нагрузка «мусор»** — возможно, сжатие (`78 9c` = zlib, `1f 8b` = gzip) или шифрование.
- **Несколько потоков в одном соединении** (как HTTP/2) — нужен разбор фреймов и stream-id.
- **Анти-replay** — nonce/счётчики/таймстемпы мешают воспроизведению; их надо генерировать.

## Что мы теперь знаем

- Кастомный протокол разбирают «с алфавита»: сначала поля (магия, длина), потом сообщения, потом сессии.
- Магия `0xCAFE` и поле длины дали каркас; ASCII в payload — подсказку о содержимом.
- Порядок байт (little-endian vs сетевой) определяется по данным, а не угадывается.
- Гипотезу из трафика подтверждают по коду бинарника (функция-сборщик сообщения).
- Зашифрованный/сжатый/сериализованный payload — отдельные случаи со своими инструментами.

## Куда дальше

Мы восстановили бинарный протокол по трафику. Но код приложения не всегда нативный — иногда
логика живёт в **байткоде** (Python, Java). В следующем уроке мы возьмём `.pyc`-файл и
разберём его байткод. А пока главное запомни: **протокол — это грамматика: начни с полей,
потом сообщения, потом сессии.**
