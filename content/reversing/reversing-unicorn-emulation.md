## Вопрос, с которого всё начинается

Бывает, что запустить образец нельзя: он ломает систему, требует редкое устройство или прячется от
отладчика. А бывает, что нам нужна только **одна функция** — например, дешифратор строк — и гонять
ради неё весь процесс незачем. Тогда на помощь приходит **эмуляция**: мы исполняем код не на
настоящем процессоре, а внутри программы-эмулятора, подсовывая свои значения и читая результат.

Опираемся на прошлый урок: там мы распутывали обфускацию динамикой. Эмуляция — это та же динамика,
но полностью под нашим контролем.

## Что такое эмуляция и чем она полезна

**Эмулятор** — программа, которая читает инструкции целевой архитектуры и выполняет их «в уме»,
меняя своё виртуальное состояние: регистры, память, флаги. Это не виртуалка: виртуалка запускает
целую ОС, а эмулятор может исполнить один фрагмент кода.

Есть два уровня:

- **Фрагментная эмуляция** — берём одну функцию и исполняем её. Для этого есть **Unicorn**:
  движок на базе QEMU, который умеет x86, ARM, MIPS, RISC-V и отдаёт полный контроль над регистрами
  и памятью.
- **Системная эмуляция** — эмулируем целый процесс с системными вызовами и файлами. Для этого есть
  **Qiling** (надстройка над Unicorn) и QEMU user mode.

Зачем это реверсеру: снять упаковку (эмулятор сам «распакует» и отдаст память), вычислить одну
функцию без запуска всего, обойти анти-анализ (эмулятор не «железо», многие проверки не срабатывают),
пройти миллион входов автоматически.

## Наш пример

Соберём маленькую библиотеку с двумя функциями и эмулируем одну из них:

```c
int add(int a, int b){ return a + b; }
int mul2(int a){ return a * 2; }
```

```
$ gcc -O0 -fno-pie -no-pie -shared -o libdemo.so lib.c
$ nm -D libdemo.so | grep -E 'add|mul2'
00000000000010e9 T add
00000000000010fd T mul2
```

Задача: выполнить `add(40, 2)` **без** запуска процесса — только эмуляцией. Нам нужно узнать адрес
функции, скопировать её байты в память эмулятора, положить аргументы в правильные регистры и
запустить.

## Шаг 1: найти адрес функции

В x86-64 аргументы функции передаются в регистрах: первый — в `rdi`, второй — в `rsi`, результат
возвращается в `eax`. Найдём адрес `add` через парсер ELF (в примере — `lief`):

```python
import lief
lib = lief.parse("libdemo.so")
sym = {s.name: s.value for s in lib.exported_symbols}
print("exported:", sym)
addr = lib.imagebase + sym["add"]
print("add at 0x%x" % addr)
```
```
exported: {'add': 4329, 'mul2': 4349}
add at 0x10e9
```

`4329` — это `0x10e9`. Теперь у нас есть адрес, по которому лежит код `add`.

## Шаг 2: подготовить эмулятор

Создаём Unicorn для x86-64, выделяем регион памяти и копируем туда байты функции:

```python
from unicorn import *
from unicorn.x86_const import *
mu = Uc(UC_ARCH_X86, UC_MODE_64)
mu.mem_map(0, 0x10000)                       # один регион 64 КБ
mu.mem_write(addr, bytes(data[off:off+32]))  # код функции
```

Дальше — самое важное: эмулятору нужно объяснить **соглашения вызова**, иначе функция вернётся «в
никуда». Ставим указатель стека (`rsp`) и указатель кадра (`rbp`) в наш регион, а по адресу возврата
кладём «стоп»-инструкцию `hlt` — когда функция сделает `ret`, управление придёт туда и эмуляция
остановится:

```python
mu.mem_write(0x8000, b"\xf4")                # hlt = стоп
mu.reg_write(UC_X86_REG_RSP, 0x9000)
mu.reg_write(UC_X86_REG_RBP, 0x9000)
mu.mem_write(0x9000, (0x8000).to_bytes(8,"little"))
```

## Шаг 3: положить аргументы и запустить

```python
mu.reg_write(UC_X86_REG_RDI, 40)
mu.reg_write(UC_X86_REG_RSI, 2)
mu.emu_start(addr, 0x8000, count=1000)
print("emu add(40,2) eax =", mu.reg_read(UC_X86_REG_EAX))
```
```
emu add(40,2) eax = 42
```

Мы получили правильный результат `42`, **не запуская** библиотеку как процесс. Никаких системных
вызовов, никакого окружения — только чистое вычисление. Именно так эмулируют отдельную функцию:
дешифратор строк, хеш-проверку, разбор конфигурации.

## Шаг 4: эмуляция «как в прошивке»

Тот же приём работает и для чужой архитектуры: подставь `UC_ARCH_ARM`/`UC_MODE_THUMB` — и эмулируй
ARM-код из прошивки, не имея ни устройства, ни кросс-компилятора. Для примера прогоним другую
функцию той же библиотеки — так эмулируют отдельные процедуры из дампов прошивок:

```python
mu.reg_write(UC_X86_REG_RDI, 21)
mu.emu_start(addr_mul2, 0x8000, count=1000)
print("emulated mul2(21) =", mu.reg_read(UC_X86_REG_EAX))
```
```
emulated mul2(21) = 42
```

## Шаг 5: системная эмуляция и хуки

Фрагментной эмуляции мало, когда функция зовёт системные вызовы или другие библиотеки. Тогда:

- **Qiling** поднимает целый процесс: подгружает ELF/PE, эмулирует ядро, файловую систему и реестр.
- **Хуки** перехватывают вызовы: перед исполнением функции можно перехватить `malloc`, `open` или
  проверку анти-отладки и вернуть своё значение. Unicorn для этого даёт `UC_HOOK_CODE` и
  `UC_HOOK_MEM_*`.

Хук на код — мощнейший инструмент деобфускации: эмулятор проходит по коду и на каждом блоке
позволяет записать трассу, вычислить, какие ветки реально достигаются, и «выпрямить» логику.

## Ограничения эмуляции

Эмуляция — не серебряная пуля. Во-первых, она **медленнее** настоящего исполнения: на каждый шаг
тратится работа движка, поэтому миллионы инструкций могут идти минутами. Во-вторых, код, который
активно общается с железом (драйверы, устройства, `rdtsc`, `cpuid`), в «голом» Unicorn просто не
имеет окружения — эти вызовы приходится **хукать** и подменять значениями. В-третьих, эмуляция
останавливается на первом же незнакомом адресе: если функция прыгает в неотмапленную память, ты
получишь ошибку `UC_ERR_...` и должен сам решить, что там должно быть. Поэтому фрагментную
эмуляцию применяют к **небольшим изолированным кускам**, а для целых процессов берут Qiling.

## Если не сработало

- **Код зависит от системных вызовов** → используй Qiling, а не «голый» Unicorn.
- **Функция обращается к данным по адресам из другого региона** → смапь больше памяти или
  скопируй нужные секции.
- **Эмуляция «улетает»** → почти всегда не выставлен `rsp`/`rbp` или отсутствует адрес возврата;
  добавь `count` как предохранитель от бесконечного цикла.

## Что мы теперь знаем

- **Эмуляция** исполняет код внутри эмулятора, без настоящего процесса и окружения.
- **Unicorn** — фрагментная эмуляция одной функции; **Qiling** — системная, с ядром и ФС.
- Перед запуском нужно задать **соглашения вызова**: аргументы в регистрах (`rdi`, `rsi`), стек
  (`rsp`/`rbp`) и адрес возврата.
- Эмуляция незаменима для распаковки, дешифраторов и обхода анти-анализа.
- **Хуки** позволяют перехватывать вызовы и строить трассы для деобфускации.

## Почему эмуляция обходит обфускацию

Эмулятор выполняет инструкции бинарника **у себя**, в песочнице, без реального запуска программы на CPU. Это даёт три преимущества перед обычной отладкой. Первое: **изоляция** — код с анти-отладочными проверками и разрушительными действиями не вредит системе, потому что он не имеет доступа к настоящим файлам и сети. Второе: **управляемость** — вы сами задаёте регистры, память, точку старта и шаг исполнения, поэтому можно запустить одну функцию с нужными аргументами, не проходя весь код до неё. Третье: **трассируемость** — эмулятор может логировать каждую инструкцию, значение регистров и обращение к памяти, что критично для деобфускации.

Именно поэтому эмуляция — ключевой инструмент против **деобфускации**: обфусцированный код часто строится так, чтобы его нельзя было прочитать статически (прыжки по вычисляемым адресам, самописная виртуальная машина). Эмулятор просто исполняет этот код и показывает реальный поток управления. Фрагментная эмуляция (Unicorn) работает на уровне CPU-инструкций без ОС; системная (Qiling) добавляет эмуляцию системных вызовов и загрузку исполняемых форматов, поэтому подходит для целых процессов и прошивок.

Важное ограничение: эмулятор — не магия. Он исполняет только тот код, до которого вы его «доведёте» (правильные аргументы, память, окружение), и не умеет эмулировать всё железо. Поэтому практика — комбинировать: сначала статический анализ, потом эмуляция конкретных функций.

## Частые вопросы

**Чем Unicorn отличается от Qiling?** Unicorn — это эмулятор CPU (инструкции, регистры, память), без ОС. Qiling — надстройка: загружает PE/ELF/Mach-O, эмулирует syscall'ы и файловую систему, то есть ближе к «полноценному запуску».

**Что делать, если функция обращается к неинициализированной памяти?** Выделите память заранее и запишите туда ожидаемые данные (строки, структуры), иначе эмуляция упадёт на первом же чтении.

**Почему эмуляция «ломается» на анти-анализе?** Анти-эмуляция проверяет окружение (наличие эмулятора, timing, CPUID); нужно пропускать или подделывать эти проверки — это часть работы.

**Можно ли эмулировать прошивку целиком?** Да, Qiling это умеет для многих архитектур, но сложные периферийные устройства придётся мокать; иногда проще запустить под qemu-user.

## Куда дальше

Мы научились исполнять код вне реального процесса. Дальше возьмём код, который **меняет сам себя
во время работы** (self-modifying), где статический дамп бесполезен, и посмотрим, как эмуляция его
распутывает. А пока главное запомни: **эмуляция — это запуск кода без запуска системы, и она даёт
полный контроль над состоянием**.

## Где пригодится

- **CTF Reversing:** прогнать функцию-проверку миллион раз или эмулировать редкую архитектуру.
- **Malware analysis:** дешифраторы строк, распаковка, обход анти-анализа в изолированной среде.
- **Firmware/IoT:** эмуляция ARM/MIPS-кода без устройства.
- **Автоматизация:** массовый прогон входов и построение трасс для деобфускации.
- **Собес:** «что такое Unicorn и Qiling?» — вопрос по продвинутому реверсу.
