## Вопрос, с которого всё начинается

Тебе дали Go-бинарник `gocheck`, который проверяет ключ. Он **собран со strip** —
`-ldflags="-s -w"`, то есть таблица символов вырезана. Кажется, что имена функций потеряны
навсегда. Но так ли это?

Go отличается от C/C++ радикально: бинарники **статически слинкованы** (несут весь рантайм),
используют собственные соглашения вызовов и — главное — хранят встроенную таблицу метаданных
**pclntab** (program counter line table). По ней восстанавливаются имена функций, файлы и строки
**даже после strip**. Go-малварь (ботнеты, стилеры) встречается всё чаще, поэтому реверс Go —
обязательный навык.

Опираемся на прошлые уроки: ты умеешь смотреть на бинарник (`file`, `strings`) и знаешь, что
декомпилятор восстанавливает логику из кода.

## Наш пример

Смотрим на файл:

```
$ file gocheck
gocheck: ELF 64-bit LSB executable, x86-64, statically linked,
Go BuildID=..., stripped
```

Два важных слова: `statically linked` (типично для Go) и `stripped`. Проверим, что запускается:

```
$ ./gocheck wrong
Access denied
$ ./gocheck 'g0l4ng!'
Access granted
```

Наша задача — понять, какая функция сравнивает ключ с `g0l4ng!`, не имея символов. Приступим.

## Шаг 1: определяем точную версию Go

Go-бинарник несёт в себе метаданные сборки. Их читает команда `go version -m`:

```
$ go version -m gocheck
gocheck: go1.26.1
	path	command-line-arguments
	build	-buildmode=exe
	build	-compiler=gc
	build	-ldflags="-s -w"
	build	CGO_ENABLED=1
```

Это критично: **байткод и рантайм привязаны к версии**. Зная `go1.26.1`, ты подбираешь совпадающую
версию инструментов (например, декомпилятор или скрипты для pclntab) — чужая версия даст мусор.
Обрати внимание: `-ldflags="-s -w"` подтверждает, что символы вырезаны.

## Шаг 2: pclntab — символы выживают после strip

Даже со strip Go оставляет таблицу **pclntab**. В ней — соответствие «адрес → имя функции,
имя файла, номер строки». Проще всего увидеть её содержимое обычным `strings`:

```
$ strings -a gocheck | grep -E '^main\.(check|main)$'
main.main
main.check
```

Имена вернулись! В нашем маленьком бинарнике таких имён около 1432 — почти все из рантайма Go
(`runtime.*`, `internal/*`). Это и есть первый шаг любого Go-реверса: **не сдавайся перед strip,
поищи символы в pclntab**.

Полноценно pclntab парсят инструменты вроде `GoReSym`, `redress` или плагины Ghidra/IDA: они
восстанавливают **все** функции с именами, а не только те, что видны в `strings`.

## Шаг 3: находим проверку

Мы знаем имя `main.check`. Теперь ищем, с чем она сравнивает. Строковые литералы в Go лежат
рядом с кодом; поищем по ключу:

```
$ strings -a gocheck | grep -o 'g0l4ng!'
g0l4ng!
```

Ключ `g0l4ng!` в бинарнике есть. Дальше — либо декомпилируем `main.check` (в Ghidra/IDA, задав
базовый адрес и язык `x86:LE:64`), либо разбираем вручную. Логика окажется тривиальной:

```go
func check(s string) bool {
    return s == "g0l4ng!"
}
```

В реальной задаче строка может быть зашифрована, и тогда важно найти саму функцию `main.check`
по pclntab, а уже потом разбирать её логику.

## Шаг 4: чем Go ломает привычный реверс

Зная имя функции, легко недооценить сложность. Три особенности, которые надо держать в голове:

- **Соглашения вызовов.** Go передаёт аргументы и результаты **по стеку**, а не по регистрам
  как System V x86-64. `RDI`/`RSI` могут не содержать аргументов — не полагайся на привычную
  картину.
- **Горутины и планировщик.** Многопоточность в Go — это лёгкие потоки (**горутины**),
  которыми управляет встроенный планировщик. В коде ты увидишь вызовы рантайма
  (`runtime.newproc`, `runtime.schedule`), а не `pthread_create`. Логика малвари часто спрятана
  в горутинах.
- **Строки, слайсы, карты, интерфейсы.** Go-строка — это пара `(указатель, длина)`, а не
  C-строка с `\0`. Слайс — тройка `(ptr, len, cap)`. Это меняет то, как выглядят структуры в
  декомпиляторе.

Поэтому Go-реверс — это «сначала вернуть символы через pclntab, потом учитывать идиомы рантайма».

## Если символы не восстанавливаются

Иногда pclntab обрезан или модифицирован обфускатором. Тогда действуй по шагам:

- проверь наличие секции: `readelf -S gocheck | grep gopclntab`;
- попробуй несколько парсеров (`GoReSym`, `redress`) — они устойчивее к разным версиям;
- ищи строки-пути вида `/home/user/app/main.go` — они тоже лежат в pclntab;
- если ничего не помогло — переходи к анализу рантайма: ищи `runtime.newproc` (запуск горутины),
  `net.Dial` (сеть), `crypto/tls` (шифрование трафика).

Отдельный нюанс: Go-строки склеены в один большой блоб, поэтому `strings` показывает «слипшиеся»
куски. Ищи **подстроку** (`grep -o 'g0l4ng!'`), а не строку целиком — так надёжнее.

## Справочник: что искать в Go-декомпиляции

| Признак | Что это значит |
|---|---|
| `runtime.newproc` | запуск горутины (лёгкого потока) |
| `runtime.gopanic` / `gopanic` | аварийное завершение, путь к ошибке |
| `net.Dial` / `http.Get` | сетевая активность (C2, загрузка) |
| `crypto/tls`, `crypto/aes` | шифрование трафика |
| пара `(ptr, len)` | Go-строка, а не C-строка с `\0` |
| тройка `(ptr, len, cap)` | слайс |

## Шаг 5: горутины в дизассемблере

В C многопоточность выглядит как `pthread_create`. В Go ты такого вызова не увидишь: горутину
запускает `runtime.newproc`. В декомпиляции это выглядит примерно так:

```text
main.main:
  ...
  call runtime.newproc(SB)     ; go worker()
  ...
main.worker:
  ...
```

То есть если в коде есть `runtime.newproc`, где-то рядом есть функция, которая исполняется
параллельно. Часто именно там прячется полезная нагрузка: фоновый цикл C2, периодическая отправка
телеметрии, ожидание команд. Найди `newproc` — и посмотри, адрес какой функции передаётся: это и
есть тело горутины.

## Полный прогон от начала до конца

Соберём весь путь в одну непрерывную историю:

```bash
$ file gocheck                              # ELF, statically linked, stripped, Go BuildID
$ go version -m gocheck                     # go1.26.1, -ldflags="-s -w"
$ strings -a gocheck | grep -E '^main\.'    # main.main, main.check  ← имена вернулись
$ strings -a gocheck | grep -o 'g0l4ng!'    # ключ найден
# декомпилятор: func check(s string) bool { return s == "g0l4ng!" }
$ ./gocheck 'g0l4ng!'                        # Access granted
```

Пять команд — и задача «stripped Go-бинарник» закрыта. В реальном образце между «нашли `main.check`»
и «поняли логику» встанет декомпиляция: функция может быть обфусцирована, а строка — зашифрована и
расшифровываться в рантайме. Но каркас тот же: **версия → pclntab → имена → логика**.

## Как это видят защитники

Go-малварь (ботнеты, стилеры, шифровальщики) растёт, поэтому аналитики ищут Go-признаки и в детекте:

- **`Go BuildID`** в выводе `file` или в заголовке — бинарник собран Go;
- **секция `gopclntab`** и множество строк `runtime.*`/`internal/*` — даже при `strip`;
- **характерные строки путей** (`/usr/local/go/src/...`, `/home/user/app/main.go`);
- **вызовы `runtime.newproc`** — запуск горутин, часто вокруг сетевой активности.

Для защитника это дешёвый способ отделить Go-образец от C/C++ и быстро перейти к анализу теми же
инструментами (`GoReSym`/`redress`), что и у реверсера.

## Шаг 6: почему `strings` показывает «слипшееся»

В Go все строковые литералы программы лежат в одном непрерывном блобе: компилятор склеивает их без
разделителей `\0`. Поэтому `strings` не может разрезать их на отдельные строки — он видит один
длинный кусок вроде `Access grantedAccess deniedg0l4ng!`. Отсюда правило: **ищи подстроку**, а не
целую строку:

```bash
$ strings -a gocheck | grep -o 'Access granted'
Access granted
```

Именно поэтому на шаге 3 мы искали `grep -o 'g0l4ng!'`, а не `grep 'g0l4ng!'` — второй вариант
требует, чтобы строка начиналась с начала вывода, и часто не находит ничего. Понимание этого
устройства экономит часы: строка в бинарнике есть, но `strings` «не показывает её целиком».

## Что мы теперь знаем

- Go-бинарники статически слинкованы и несут рантайм — они большие, но самодостаточные.
- `go version -m` даёт точную версию Go и параметры сборки.
- **pclntab** сохраняет имена функций даже после `strip` — `strings` уже многое показывает.
- Инструменты (`GoReSym`, `redress`) восстанавливают все символы полностью.
- Go использует стековые соглашения вызовов и горутины — привычная картина регистров не работает.
- Горутины запускаются через `runtime.newproc`; тело горутины — частая точка, где прячется полезная
  нагрузка (фоновый C2, телеметрия).

## На что смотреть дальше

- Всегда начинай с `go version -m` — версия определяет, какими инструментами пользоваться.
- Не трать время на `strip`-панику: сначала pclntab (`strings`, потом парсер).
- Строки в Go «склеены» в один блоб — ищи подстроку, а не строку целиком.
- Для малвари смотри на сетевые вызовы и `crypto/tls`: там обычно C2 и шифрование трафика.
- Если функция «не декомпилируется» — возможно, ты смотришь на обёртку рантайма, а не на логику.

## Инструмент: go tool nm

Символы Go-бинаря восстанавливают из таблицы `pclntab`. Даже после `strip`
утилита `nm` из тулчейна Go (`go tool nm`) находит имена функций:

```
$ go tool nm gobin2
  4b1a20 T main.main
  4b1f40 T main.checkPassword
  4c0200 T runtime.morestack
```

Префикс `T` — текстовый символ. Имя `main.checkPassword` прямо указывает на
функцию проверки: дизассемблируем её и находим сравнение. `pclntab` —
встроенная таблица соответствия адресов и имён, которую Go не убирает при
`strip`, поэтому символы «выживают».

## Куда дальше

В следующем уроке мы возьмём Rust-бинарник, где компилятор оставляет уже другие артефакты —
мономорфизацию generic-функций и развёрнутую обработку `panic`. А пока главное запомни:
**в Go `strip` почти не мешает** — pclntab хранит имена, и реверс начинается с их восстановления.

## Где пригодится

- **CTF Reversing:** Go-задачи часто «спрятаны» за strip, но легко вскрываются через pclntab.
- **Malware analysis:** ботнеты и стилеры на Go — растущая доля угроз.
- **Bug bounty:** анализ Go-сервисов, поиск логики и секретов.
- **Работа (RE-команда):** Go стал популярен в инфраструктуре, навык востребован.
- **Собес:** pclntab, соглашения вызовов Go, горутины — отличают продвинутого реверсера.
