## Вопрос, с которого всё начинается

Статический анализ дал нам гипотезу: `check_password` сравнивает ввод с `hunter2`. Но что если
строки зашифрованы, проверка размазана по коду, или хочется убедиться, что функция делает
именно это? Файл на диске не отвечает на такие вопросы — нужно **посмотреть, как программа
работает**.

Для этого есть динамический анализ: запуск под **отладчиком**. В этом уроке возьмём `crackme`
под `gdb` и научимся ставить точки останова, смотреть регистры и даже обходить проверку.

## Наш пример

Отладчик `gdb` — стандарт для Linux. Удобнее с плагином `pwndbg` (или GEF): он красиво
показывает регистры, стек и код. Запускаем:

```bash
$ gdb -q ./crackme
(gdb)
```

Первый вопрос: **где остановиться**. Точка останова (breakpoint) ставится по имени функции
или по адресу. Остановимся на входе в `check_password`:

```bash
(gdb) break check_password
Breakpoint 1 at 0x1181
(gdb) run
```

`run` запускает программу; когда управление дойдёт до `check_password`, отладчик остановит её.

## Шаг 1: остановились — что дальше?

Теперь мы «внутри» функции. Посмотрим, что там происходит. Программа ждёт ввод — но breakpoint
сработает уже после чтения. Запустим с неправильным паролем и посмотрим регистры:

```bash
Breakpoint 1, 0x0000555555555181 in check_password ()
(gdb) printf "input = %s\n", $rdi
input = totally-wrong
(gdb) x/s $rdi
0x7fffffffe120:  "totally-wrong"
```

`$rdi` — первый аргумент функции (мы это знаем из урока про ассемблер). Это указатель на строку
ввода. `x/s` («examine as string») печатает строку по адресу. Значит, `check_password` получает
ровно то, что мы ввели.

## Шаг 2: шаг за шагом и стек вызовов

Идти по одной инструкции — команды `stepi` (`si`, шаг в функции) и `nexti` (`ni`, шаг через
вызов). А команда `backtrace` (`bt`) показывает, **как мы сюда попали** — стек вызовов:

```bash
(gdb) bt
#0  check_password () at 0x1181
#1  main () at 0x1253
```

Читается снизу вверх: `main` вызвал `check_password`. В больших бинарниках `bt` — способ
понять контекст: из какой ветки кода пришёл вызов.

## Шаг 3: перехватываем сравнение — видим секрет

Самый быстрый способ найти секрет — поставить breakpoint прямо на функцию сравнения `strcmp`.
Она принимает два указателя: первый — наш ввод, второй — то, **с чем сравнивают**. Второй
аргумент и есть секрет.

```bash
$ gdb -q ./crackme
(gdb) break strcmp
(gdb) run
Breakpoint 1, 0x00007ffff7f03b50 in strcmp () from /usr/lib/libc.so.6
(gdb) printf "input (a)  = %s\n", $rdi
input (a)  = wrongpass
(gdb) printf "secret (b) = %s\n", $rsi
secret (b) = hunter2
```

Вот он, пароль — `hunter2` — прямо из памяти. Этот приём («breakpoint на `strcmp`/`memcmp` и
сравнить аргументы») решает огромное число beginner-задач и не требует читать ассемблер вообще.

## Шаг 4: PIE и реальные адреса

Заметь, что breakpoint сработал по адресу `0x0000555555555181`, хотя в файле функция была по
`0x1181`. Разница — база загрузки. Мы помним из урока про форматы: `crackme` — PIE, грузится
по случайному адресу. Посмотреть базу можно так:

```bash
(gdb) info proc mappings
Start Addr         End Addr           Perms File
0x0000555555554000 0x0000555555555000 r--p  /tmp/pentestcode/revdemo/crackme
0x0000555555555000 0x0000555555556000 r-xp  /tmp/pentestcode/revdemo/crackme
```

База — `0x555555554000`. Реальный адрес = база + смещение из файла: `0x555555554000 + 0x1181 =
0x555555555181`. Ровно то, что показал отладчик. Это то самое «пересчитывание адресов при PIE»,
о котором предупреждали раньше.

Если нужно остановиться по адресу из файла, пишут `break *main+8` или `break *0x1181` до
запуска (gdb сам добавит базу), а `info registers` показывает все регистры сразу.

## Шаг 5: патчинг на лету — обходим проверку

Отладчик позволяет **менять** ход программы. Например, заставим `check_password` вернуть `1`,
даже если пароль неверный. Команда `return` выходит из текущей функции с заданным значением:

```bash
(gdb) break check_password
(gdb) run
Breakpoint 1, 0x0000555555555181 in check_password ()
(gdb) printf "input = %s\n", $rdi
input = totally-wrong
(gdb) return (int)1
(gdb) continue
Enter password: Correct! flag{rev_basics_1s_fun}
```

Ввели мусор — получили флаг. Мы обошли проверку, не меняя файл. Так же можно править регистры
(`set $eax = 1`), память (`set {char}0x... = ...`) и даже пропускать инструкции (`jump *адрес`).
Это основа патчинга и обхода лицензионных проверок.

## Шаг 6: полезные команды отладчика

Кроме `break`/`run`/`x`, в gdb пригодится ещё десяток команд:

- `info registers` — все регистры разом (удобно, когда не помнишь имя).
- `disassemble /r` — ассемблер текущей функции с байтами.
- `ni` / `si` — шаг на одну инструкцию: `ni` не входит в вызовы, `si` входит.
- `next` / `step` — то же, но по строкам исходника (если есть отладочная информация).
- `finish` — выполнить до выхода из текущей функции.
- `x/8gx $rsp` — посмотреть восемь слов на стеке.
- `watch *(int*)0x...` — остановиться, когда значение по адресу изменится (watchpoint).
- `set {char}0x... = 0x41` — записать байт в память.

**Watchpoint** (`watch`) особенно полезен, когда не знаешь, где программа портит переменную:
ставишь наблюдение на адрес — и отладчик остановится ровно в момент записи. Это быстрее, чем
идти по инструкциям вручную.

На Linux удобно отлаживать в **pwndbg** (или GEF) — это тот же gdb с цветным выводом регистров,
стека и дизассемблера на одном экране. Для Windows-бинарников аналог — **x64dbg**: тот же набор
(точки останова, шаг, инспекция памяти, патчинг), но под PE-файлы. Освоив gdb, ты почти без
усилий перейдёшь на x64dbg: команды называются иначе, но идеи те же.

## Что мы теперь знаем

- **Breakpoint** (`break`) останавливает программу в нужном месте — по имени или адресу.
- `$rdi`, `$rsi` — аргументы функции; `x/s $rdi` показывает строку по указателю.
- **`bt`** показывает стек вызовов: кто кого вызвал.
- Breakpoint на **`strcmp`** и просмотр `$rdi`/`$rsi` — быстрый способ вытащить секрет.
- При **PIE** реальный адрес = база (`info proc mappings`) + смещение из файла.
- **`return`/`set`/`jump`** позволяют менять поведение и обходить проверки на лету.

## Куда дальше

Мы научились запускать бинарник и наблюдать его. Но когда программа зовёт `strcmp` или
`printf`, мы прыгаем в библиотеку `libc` — и в отладчике это выглядит как «ушли в неизвестный
код». Как программа вообще находит эти функции и почему вызов идёт «через таблицу»? Об этом —
в следующем уроке про **динамическую линковку**. А пока главное запомни: `break`, `run`,
`x/s $rdi`, `bt` — четыре команды, решающие большинство beginner-задач.

## На что смотреть дальше

Разобравшись с отладчиком, обрати внимание на три вещи. Во-первых, **стек вызовов**: `bt` часто
объясняет, почему функция получила именно такие аргументы. Во-вторых, **точки останова по
условию** (`break ... if $rax==0`) — они срабатывают только при нужном состоянии, что экономит
время в циклах. В-третьих, **отладка библиотечных вызовов**: `catch syscall` ловит системные
вызовы, а breakpoint на `read`/`write` показывает, что программа читает и пишет. Эти приёмы
понадобятся и в pwn, где разработка эксплойта без отладчика не обходится.

## Где пригодится

- **CTF Reversing:** перехват `strcmp`/`memcmp` и патчинг проверок — быстрые решения.
- **Pwn:** отладка эксплойтов невозможна без gdb/pwndbg (регистры, память, стек).
- **Malware analysis:** запуск в изолированной среде под отладчиком вскрывает поведение.
- **Патчинг/обход лицензий:** `set`/`jump` меняют логику без правки файла.
- **Собес:** «как найти пароль через отладчик», «что такое breakpoint» — типовые вопросы.
