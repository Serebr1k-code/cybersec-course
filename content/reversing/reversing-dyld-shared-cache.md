## Вопрос, с которого всё начинается

Ты хочешь посмотреть, как устроена системная библиотека на macOS/iOS (например, `libsystem_kernel.dylib`), но файла на диске нет — есть только огромный `dyld_shared_cache`. Где взять библиотеку?

## Наш пример

Посмотрим, что лежит в кэше:

```bash
$ ls -la /System/Library/dyld/
... dyld_shared_cache_arm64e   (гигабайты)
$ file dyld_shared_cache_arm64e
dyld_shared_cache_arm64e: data
```

Отдельных `.dylib` нет — все системные библиотеки собраны в один кэш. Разберём, зачем это сделано и как извлечь нужную библиотеку.

## Шаг 1: зачем нужен dyld shared cache

При запуске приложения система загружает десятки системных библиотек. Чтобы не читать и не связывать каждую отдельно, Apple собрала их в один общий кэш, который отображается в память одним куском. Плюсы: быстрый старт, экономия памяти (одна копия на все процессы). Минус для реверсера: библиотек «на диске» нет, они внутри кэша, а адреса в них уже привязаны. Понимание кэша нужно, чтобы анализировать системные вызовы, фреймворки и сравнивать версии между прошивками.

## Шаг 2: извлечение библиотек

Кэш можно «распаковать» инструментами: `dyld_shared_cache_util` (из проекта `dyld`), `dsc_extractor` (Apple), `jtool2 --extract`, или скрипты `dyld_cache_extract`. После извлечения получаешь обычные Mach-O файлы, которые открываются в IDA/Ghidra/Hopper. Важно: извлекать нужно на той же платформе/версии (кэш архитектурно-зависим). Для iOS кэш берут из прошивки (IPSW), для macOS — из системы. Есть и готовые наборы символов для популярных версий.

## Шаг 3: структура кэша

Кэш начинается с заголовка `dyld_cache_header` с магией `dyld_v1`, за которым идут образы (images) — по сути Mach-O без отдельных заголовков файла. В заголовке есть таблица `images` со смещениями, `slide`-информация (ASLR), а также общие для всех регионы (например, общий `__LINKEDIT`). Извлечение сводится к тому, чтобы для каждого образа собрать валидный Mach-O из его сегментов. Понимание структуры нужно, когда инструмент не справляется или нужно извлечь что-то конкретное (например, только символы).

## Шаг 4: анализ извлечённых библиотек

После извлечения библиотеки анализируются как обычные: `otool -l` (загрузочные команды), `nm` (символы, если есть), дизассемблер. Особенность: адреса в кэше уже привязаны (slide известен), и это может путать — в дизассемблере адреса не совпадают с файловыми смещениями. Полезно сравнивать извлечённую библиотеку между версиями ОС: так находят изменения в поведении (например, новые проверки). Для системных вызовов есть отдельные таблицы (syscall stubs) — их тоже можно разобрать.

## Шаг 5: символы и stubs

Системные библиотеки содержат **stubs** — короткие переходники к общим реализациям (в кэше код шарится). Символы часто экспортированы, но приватные функции — нет. Для анализа приватных API используют таблицы символов из прошивок (`dsc_extractor` + `nm`), а также публичные «дампы символов» (например, `dyld-shared-cache`-репозитории). Важно: многие интересные функции (внутренние проверки) приватны, и их ищут по строкам и паттернам, а не по именам.

## Шаг 6: инструменты

Ключевые: `dyld_shared_cache_util`/`dsc_extractor` (извлечение), `jtool2` (анализ и extract), `ipsw` (работа с прошивками и кэшем), `class-dump` (ObjC-классы), `nm`/`otool`, `IDA`/`Ghidra`/`Hopper` (дизасм), `jtool2 --analyze`. Для iOS — `ipsw` и извлечение из IPSW. Для поиска приватных символов — публичные базы. Набор закрывает почти все задачи по системным библиотекам.

## Шаг 7: где это в реальной работе

Анализ dyld cache нужен при реверсе iOS-приложений (они линкуются с системными библиотеками), при исследовании системных вызовов и приватных API, при сравнении версий ОС (что изменилось в защитах), при анализе macOS-малвари, которая использует системные функции. Это базовый навык Apple-реверсера: без умения извлечь библиотеку из кэша анализ системного уровня невозможен.

## Что мы теперь знаем

- dyld shared cache — единый файл со всеми системными библиотеками macOS/iOS.

- Библиотеки извлекаются инструментами (dsc_extractor, jtool2, ipsw) в обычные Mach-O.

- В кэше адреса привязаны (slide известен), что влияет на анализ.

- Символы/stubs дают имена; приватные функции ищут по строкам и паттернам.


## Шаг 8: работа с прошивками и версиями

Для iOS кэш извлекают из IPSW-файла прошивки. Инструмент `ipsw` умеет скачивать прошивки, распаковывать их и извлекать dyld cache, а также разбирать его. Для macOS кэш берут из установленной системы (`/System/Library/dyld/`). Ключевой момент — версия: структура кэша и набор библиотек меняются между версиями, поэтому для анализа конкретного приложения нужен кэш той версии ОС, под которую оно собрано. Публичные наборы символов для популярных версий экономят время: вместо ручного извлечения ты получаешь готовые имена функций. Это особенно важно для приватных API, которых нет в открытых SDK.

## Шаг 9: практический пример — разбор системного вызова

Допустим, приложение вызывает `ptrace` для анти-отладки. Найдём реализацию: (1) извлекаем `libsystem_kernel.dylib` из кэша; (2) открываем в Ghidra; (3) находим stub `ptrace` (или syscall-номер); (4) смотрим, как приложение его использует. Часто интереснее не сама функция, а то, как приложение её обходит — например, вызывает syscall напрямую, минуя библиотеку. Для этого смотрим на инструкции `svc` (supervisor call) в бинарнике приложения: прямой syscall виден как `svc #0x80` с номером в регистре. Понимание системных вызовов через кэш позволяет разбирать такие трюки. Без извлечённых библиотек ты бы не знал, какой номер соответствует какому вызову.

## Шаг 10: ограничения и подводные камни

Первое ограничение — приватность: часть функций в кэше не имеет символов, и их приходится искать по строкам/паттернам. Второе — адреса привязаны (slide), поэтому в дизассемблере нужно правильно выставить базу, иначе ссылки не совпадут. Третье — кэш может быть сжат/зашифрован в свежих версиях iOS, что требует дополнительных шагов. Четвёртое — размер: кэш гигабайтный, и извлекать всё не нужно — работай точечно с нужной библиотекой. Понимание этих ограничений экономит часы: не пытайся «разобрать кэш целиком», извлекай конкретную библиотеку под конкретную задачу.

## Шаг 11: почему это важно именно для безопасности

Понимание dyld cache нужно защитникам и исследователям по нескольким причинам. Во-первых, многие защиты macOS/iOS реализованы в системных библиотеках — чтобы понять, как приложение их обходит, нужно прочитать библиотеку. Во-вторых, малварь использует приватные API, которые есть только в кэше. В-третьих, сравнение кэшей между версиями показывает, какие проверки добавила Apple. В-четвёртых, для iOS-эксплуатации нужно знать точные адреса функций в кэше. Это не «академический» навык, а рабочий инструмент Apple-исследователя.

## Шаг 12: чек-лист анализа системной библиотеки

(1) Определить версию ОС/прошивки. (2) Извлечь кэш (из системы или IPSW). (3) Извлечь нужную библиотеку (`dsc_extractor`/`jtool2`/`ipsw`). (4) Открыть в Ghidra/IDA с правильной базой (slide). (5) Восстановить символы (публичные базы/`nm`). (6) Найти интересующие функции (syscall stubs, приватные API). (7) Сравнить с другой версией при необходимости. Этот чек-лист покрывает типовые задачи: разбор системных вызовов, анализ защит, поиск приватных API. Он же применим к анализу фреймворков, которые также лежат в кэше.
## Где брать символы: публичные базы и dyld info

Даже если библиотека извлечена, имён в ней может не быть. На помощь приходят:

- **`dyld_info`** (Apple) — печатает экспорты, привязки и фиксации из Mach-O;
- **`jtool2 -d`** — дампит символы, включая приватные;
- **публичные дампы символов** (репозитории с `*.symbols` для конкретных версий iOS/macOS);
- **`nm -gU`** — экспортированные символы, если таблица на месте.

Приватные функции (например, внутренние проверки песочницы или подписи) в экспортах не значатся. Их ищут по строкам-соседям и паттернам кода: находишь строку «operation not permitted», через перекрёстную ссылку выходишь на функцию и даёшь ей своё имя.

## Diff двух версий ОС

Мощный приём — сравнить извлечённую библиотеку между прошивками. Инструменты вроде **`bindiff`** или простой diff по дизассемблеру показывают, какие функции изменились. Так находят, что Apple добавила или убрала: новую проверку подписи, новый запрет, изменённую логику песочницы. Для исследования эксплойтов это ключ к ответу на вопрос «до какой версии баг работал».

## Почему свежий кэш «не читается»

В новых версиях iOS Apple применяет к части кэша **сжатие** (например, LZMA) и иногда шифрование образов. Тогда `dsc_extractor` вернёт невалидные файлы, а `file` скажет `data`. Решение — использовать свежие версии `ipsw`/`jtool2`, которые понимают новый формат, либо сначала распаковать нужные сегменты. Это же объясняет, почему для анализа всегда берут кэш **той** версии ОС, под которую собрано приложение: структура и набор символов между версиями различаются.

## Что даёт извлечённый кэш на практике

Извлечённые из кэша библиотеки решают три типовые задачи. Во-первых, **понимание системных вызовов**: имея `libsystem_kernel.dylib`, ты знаешь, какой номер соответствует `ptrace`, `mprotect` или `csops`, и можешь читать прямой `svc` в приложении. Во-вторых, **анализ защит**: проверки подписи, песочницы и AMFI живут в системных библиотеках, и их обход виден только там. В-третьих, **сравнение версий**: diff между прошивками показывает, какие проверки Apple добавила или ослабила. Во всех случаях работает один принцип — берёшь кэш ровно той версии ОС, под которую собран объект анализа, иначе адреса и логика не совпадут.
