## Задача

Программа `watchdemo` в конце печатает `v=91`. Вопрос простой: **откуда берётся это число?**
В коде есть функция `compute`, но вызывается она несколько раз, и глазами за значениями не
уследить. Отладчик — правильный инструмент, но не «F9 на всё подряд», а методично: поставить
точку там, где значение меняется, и посмотреть, кто это делает.

```bash
$ ./watchdemo
v=91
```

## Данные: что мы знаем статически

Дизассемблируем `compute` (или смотрим исходник — он есть, `-g`-сборка):

```c
int compute(int seed){ int x = seed; x = x * 3; x = x + 7; return x; }
int main(void){ int v = 0; for (int i=0;i<3;i++) v = compute(v); printf("v=%d\n", v); return 0; }
```

Логика ясна: `x = seed*3 + 7`, три итерации. Но чтобы *увидеть* поток значений, нужен отладчик.

## Шаг 1: watchpoint — «кто меняет переменную»

Главный приём: вместо того чтобы шагать по инструкциям, ставим **watchpoint** — точку
останова на **изменение значения**. Отладчик сам остановится в момент записи:

```bash
$ gdb -q ./watchdemo
(gdb) break compute
(gdb) run
Breakpoint 1, compute (seed=0) at watchdemo.c:2
(gdb) watch x
Hardware watchpoint 2: x
(gdb) continue
Hardware watchpoint 2: x
Old value = 0
New value = 7
compute (seed=0) at watchdemo.c:2
```

Читаем: `x` изменился с `0` на `7`, и остановка произошла **внутри `compute`**. Watchpoint
избавил от ручного трассирования — мы сразу видим, где именно переменная получила значение.
`watch` срабатывает на запись; `rwatch` — на чтение, `awatch` — на любое обращение.

Обрати внимание: gdb сказал «**Hardware** watchpoint» — он использует аппаратные регистры
отладки (`DR0–DR7` на x86), а не модифицирует код. Их лимит — **4** на x86/x64.

## Шаг 2: gdb-скрипт — автоматизируем логирование

Ручной `continue` каждый раз утомляет. gdb встраивает **Python**: можно написать точку
останова, которая только логирует и не останавливает программу. Класс `gdb.Breakpoint` с
методом `stop()`, возвращающим `False`, делает именно это:

```python
# wp.py
import gdb
class HitBP(gdb.Breakpoint):
    def stop(self):
        seed = int(gdb.parse_and_eval("seed"))
        print(f"[py] compute called with seed={seed}")
        return False          # не останавливать, только записать
HitBP("compute")
gdb.execute("run")
```

Запускаем:

```bash
$ gdb -q -batch -x wp.py ./watchdemo
[py] compute called with seed=0
[py] compute called with seed=7
[py] compute called with seed=28
v=91
```

Вот и вся картина: `0 → 7 → 28 → 91`. Каждый вызов получает результат предыдущего
(`0*3+7=7`, `7*3+7=28`, `28*3+7=91`). Скрипт сам обошёл программу и собрал поток значений —
это и есть «методичная отладка» вместо ручных шагов.

## Шаг 3: типы точек останова

- **Программные.** Отладчик вставляет байт `0xCC` (`int3`) по адресу. Просты, но **видны
  коду** — anti-debug их находит. В gdb — `break *0x401000`, `break main`, `break file.c:42`.
- **Аппаратные.** Через регистры `DR0–DR7`; код не меняется, поэтому их сложнее детектить.
  В gdb — `hbreak`. Лимит 4.
- **Watchpoints.** Наблюдение за памятью (`watch`/`rwatch`/`awatch`), тоже аппаратные.
- **Условные.** Останавливаться только при условии: `break func if x == 5`, или
  `condition 2 argc > 3` на существующую точку.

Полезное: `ignore 1 100` — пропустить первые 100 срабатываний точки №1.

## Шаг 4: reverse debugging — шагать назад

Иногда нужно понять, **как** программа пришла в текущее состояние. Reverse debugging позволяет
двигаться назад по исполнению:

```text
(gdb) record full
(gdb) continue
(gdb) reverse-stepi        # шаг назад
(gdb) reverse-continue     # назад до предыдущей точки
```

Альтернатива — **rr** (Mozilla): записывает всё исполнение и позволяет «отмотать» его
детерминированно (`rr record ./target`, затем `rr replay`). Незаменимо, когда падение редкое и
невоспроизводимое. Reverse debugging сильно замедляет исполнение — включай точечно.

## Шаг 5: удалённая отладка и Windows

**gdbserver** — отладка бинарника на другой машине (например, в изолированной VM):

```bash
# на цели
$ gdbserver :1234 ./target
# на хосте
$ gdb ./target -ex "target remote 10.0.0.5:1234"
```

На Windows арсенал свой: **x64dbg** (условные точки, логирование, скрипты, патчи) и **WinDbg**
(ядро, типизированные дампы структур через `dt`, TTD — time-travel debugging, аналог `rr`).
Синхронизировать GUI дизассемблера с отладчиком помогают ret-sync/ghidra-bridge.

## Шаг 6: трассировка и обход anti-debug

Когда нужно понять **весь** поток выполнения, точечные точки неэффективны. Тогда включают
трассировку. **Intel Processor Trace (Intel PT)** — аппаратная запись потока управления с
минимальным замедлением; gdb использует её через `record btrace`:

```text
(gdb) record btrace pt
(gdb) continue
(gdb) record instruction-history /m     # история инструкций
(gdb) record function-history           # история вызовов
```

Ещё есть `perf record -e intel_pt// ./target` + `perf script`, а в x64dbg — Trace record
(запись каждой инструкции с регистрами).

Вредоносный код часто **детектит отладчик**. Классические приёмы и обход:

| Детект | Обход |
|---|---|
| `IsDebuggerPresent` | патч возврата / ScyllaHide |
| PEB `BeingDebugged` | обнулить через плагин/патч |
| `ptrace(PTRACE_TRACEME)` (Linux) | патч вызова / `LD_PRELOAD` |
| `rdtsc` timing | патч сравнения |
| `0xCC`-проверки | аппаратные точки (`hbreak`) вместо `0xCC` |

В Linux проверь `/proc/self/status` (поле `TracerPid`) — его тоже часто используют для детекта.

## Если не сработало

- **Watchpoint «исчез»** — переменная вышла из области видимости; gdb удаляет watchpoint, когда
  программа покидает блок. Ставь его по адресу памяти (`watch *(int*)0x...`), а не по имени.
- **Условие в breakpoint не работает** — символ не в области видимости на этой точке (как с `i`
  вне цикла). Проверяй, где именно срабатывает точка.
- **Адреса «плывут»** — ASLR; gdb отключает его (`set disable-randomization on`) или работай по RVA.
- **Программные точки детектятся** — переходи на аппаратные (`hbreak`) или маскируй отладчик.
- **`-O2`-сборка** — переменные «исчезают», код переупорядочен; отлаживай `-O0` или смотри регистры.

## Что мы теперь знаем

- **Watchpoint** останавливает при изменении памяти — идеален для «кто портит значение».
- gdb встраивает **Python**; `gdb.Breakpoint` с `stop()` → `False` даёт логирующие точки без остановки.
- Точки бывают программные (видны коду) и аппаратные (через `DR`-регистры, лимит 4).
- Reverse debugging (`record`/`rr`) позволяет шагать назад; удалённая отладка — через `gdbserver`.
- Отладка — это цикл «гипотеза → точка → наблюдение → вывод», а не F9 на всё.

## Куда дальше

Мы научились методично отлаживать и автоматизировать рутину. Но часто нужно понять не
отдельное значение, а **формат сетевого протокола** — какие байты программа шлёт и ждёт.
В следующем уроке мы возьмём бинарный протокол и разберём его сообщения. А пока главное
запомни: **watchpoint ищет, кто меняет данные; скрипт убирает ручную рутину.**

## Где пригодится

- **CTF Reversing:** watchpoints для поиска «кто портит данные», условные точки для сложных проверок.
- **Pwn:** анализ heap/стека, трассировка аллокаций, поиск смещений.
- **Malware analysis:** удалённая отладка в изолированной VM, трассировка API.
- **Работа (RE-команда):** диагностика крашей и некорректного поведения без исходников.
- **Собес:** условные breakpoints, watchpoints, remote-отладка — практические вопросы RE-интервью.
