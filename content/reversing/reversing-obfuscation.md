## Вопрос, с которого всё начинается

Ты открываешь функцию проверки пароля в декомпиляторе, а вместо простого `if (strcmp(...) == 0)`
видишь бесконечный `while` с гигантским `switch`, десяток странных условий и переменную-«состояние».
Логика вроде бы простая, но читать её невозможно. Это **обфускация** — намеренное запутывание кода
без изменения поведения. Задача реверсера — распознать технику и распутать её.

Опираемся на прошлые уроки: мы уже умеем снимать проверки среды и упаковку. Теперь код чистый, но
специально «испорченный».

## Наш пример

Возьмём функцию, которая проверяет пароль, но написана «запутанно»:

```c
int check(const char *p){
    int state = 0, i = 0, ok = 0, x = 7;
    while (state != 5) {
        switch (state) {
        case 0: ok = 1; i = 0; state = 1; break;
        case 1: if ((x*x - 14*x + 49) == 0) state = 2; else state = 5; break;
        case 2: if (p[i]==0) { state = 4; break; }
                if (p[i] != "rev42"[i]) ok = 0;
                i++; state = 3; break;
        case 3: if ((x & 1) == 1) state = 2; else state = 2; break;
        case 4: state = 5; break;
        }
    }
    return ok && i == 5;
}
```

Поведение абсолютно нормальное:

```
$ ./obf rev42
access GRANTED
$ ./obf nope
access DENIED
```

Но давай посмотрим, во что это превратилось в машинном коде.

## Шаг 1: control-flow flattening

Компилятор не свернул структуру, и в дизассемблере видно «плоское» полотно:

```
40114a:  jmp    401254                 ; вход в цикл
40114f:  cmp    DWORD PTR [rbp-0x10],0x4
401153:  je     40124c                 ; switch (state): case 4
401159:  cmp    DWORD PTR [rbp-0x10],0x4
40115d:  jg     401254
401163:  cmp    DWORD PTR [rbp-0x10],0x3
401167:  je     401230                 ; case 3
401177:  cmp    DWORD PTR [rbp-0x10],0x2
40117b:  je     4011df                 ; case 2
401187:  cmp    DWORD PTR [rbp-0x10],0x0
40118b:  je     401198                 ; case 0
40118d:  cmp    DWORD PTR [rbp-0x10],0x1
401191:  je     4011b2                 ; case 1
```

Переменная `state` живёт по адресу `[rbp-0x10]`. В конце каждого блока она переписывается, и
управление возвращается к общему диспетчеру (`jmp 401254`). Все ветки программы «схлопнуты» в один
цикл с `switch` — это **control-flow flattening** (выравнивание графа потока управления). Смысл
приёма: убрать естественные переходы между блоками и заменить их на косвенную диспетчеризацию через
одну переменную. Человеку трудно держать в голове «где я и куда иду», а автоматическому анализатору
— трудно построить граф.

## Шаг 2: opaque predicates (ложные предикаты)

Теперь самое интересное — блок `case 1`:

```
4011b2:  mov    eax,DWORD PTR [rbp-0x4]   ; eax = x
4011b5:  imul   eax,eax                   ; eax = x*x
4011b8:  mov    ecx,eax
4011ba:  mov    edx,DWORD PTR [rbp-0x4]   ; edx = x
4011bf:  shl    edx,0x3                   ; edx = x*8
4011c2:  sub    eax,edx                   ; eax = x*x - 8x
4011c4:  add    eax,eax                   ; eax = 2*(x*x - 8x)
4011c6:  add    eax,ecx                   ; eax = 3*x*x - 16x
4011c8:  cmp    eax,0xffffffcf            ; сравнить с -49
4011cb:  jne    4011d6
```

После подстановки это `x² − 14x + 49 == 0`, то есть `(x−7)² == 0`. Поскольку `x` жёстко задано
равным 7, условие **всегда истинно** — ветка `else` недостижима. Такое всегда-истинное (или
всегда-ложное) условие называют **opaque predicate** (ложный предикат). Он добавляет «мёртвый»
код и сбивает с толку: кажется, что здесь есть развилка, но на самом деле её нет. То же и в
`case 3`: `if ((x & 1) == 1) ... else ...` — обе ветки ведут в одно место.

## Шаг 3: каталог техник обфускации

Обфускация — это целый набор приёмов. Вот основные, с признаками:

| Техника | Суть | Признак в коде |
|---|---|---|
| String encryption | строки шифруются, дешифруются в рантайме | нет читаемых строк, вызов дешифратора |
| Control-flow flattening | CFG в один цикл со `state` | гигантский `switch`/`while` |
| Opaque predicates | всегда-истинные условия | странные `if`, недостижимый код |
| MBA (mixed boolean-arithmetic) | арифметика выражена через `^ & \|` | `(x^y)+2*(x&y)` вместо `x+y` |
| Dead code / bogus flow | мусорные блоки, прыжки в никуда | код, который никогда не выполняется |
| Code virtualization | логика в байткоде своей VM | диспетчер + таблица handler'ов |
| Self-modifying | код меняет сам себя в рантайме | запись в исполняемую память |

Важно: обфускация **не меняет семантику**. Программа делает ровно то же самое, что и «чистая»
версия. Значит, восстановить поведение всегда возможно — динамикой, эмуляцией или упрощением.

## Шаг 4: как подступаться

Универсального «деобфускатора» нет, но есть порядок действий:

1. **Понять класс техники.** Если видишь `switch` по `state` — это flattening; если арифметика
   из `^ & |` — MBA; если диспетчер по числовому опкоду — виртуализация.
2. **Упростить локально.** Ложные предикаты убираются заменой ветки на безусловный переход; MBA
   сворачивается алгеброй (об этом — следующий урок).
3. **Взять динамику.** Если статика не идёт, трассируй исполнение (gdb, Frida, эмулятор) и смотри,
   какие блоки реально выполняются.
4. **Автоматизировать.** Для больших функций пишут скрипты: собирают последовательность
   переходов и восстанавливают исходный порядок блоков.

Для нашего `obf` хватит первого и второго шагов: `state` меняется по цепочке `0 → 1 → 2 → 3 → 2 →
... → 4`, а ложные предикаты просто выкидываются. После этого видно обычный цикл сравнения строк.

## Что мы теперь знаем

- **Обфускация** — запутывание кода без смены поведения; цель — замедлить и запутать реверсера.
- **Control-flow flattening** прячет граф потока в цикл со `switch` по переменной-состоянию.
- **Opaque predicate** — всегда-истинное/ложное условие; в нашем примере `(x−7)²==0` при `x=7`.
- Техник много: шифрование строк, MBA, мёртвый код, виртуализация, самомодификация.
- Раз семантика не меняется, поведение **всегда** восстановимо — упрощением или динамикой.

## Почему flattening ломает декомпилятор

Control-flow flattening («сплющивание») превращает понятный поток управления в **один большой цикл с диспетчером**. Вместо последовательности блоков, соединённых условными переходами, появляется `while (state != EXIT) { switch (state) { case 1: ...; state = ...; case 2: ...; } }`. Логика сохранена, но её «форма» разрушена: декомпилятор видит диспетчер и десятки блоков, а не структуру `if/else/loop`. Именно поэтому flattening — одна из самых распространённых и самых раздражающих обфускаций.

Обратная задача — **восстановить порядок блоков**. Ключ в том, что переменная-состояние (`state`) детерминирована: каждый блок заканчивается присваиванием `state = <число>`, и это число указывает на следующий блок. Если собрать граф переходов «блок → следующий блок», можно восстановить исходный поток и, применив анализ на доминирование, вернуть структуру `if`/`loop`. Инструменты: Ghidra/IDA-плагины для деобфускации, символьное исполнение, ручной скрипт, который трекает `state`.

Второй класс — **opaque predicates**: условия, которые всегда истинны или всегда ложны, но выглядят как проверки (например, `(x*x) >= 0`, или сложные тождества). Они добавляют ложные ветви, которые никогда не исполняются, но путают анализ. Их распознают, вычисляя предикат: если он константен — ветвь мёртвая, её вырезают. Оба приёма часто комбинируют: flattening + opaque predicates + мёртвый код.

## Если не сработало

- **Блоки не восстанавливаются.** Проверьте, что правильно определили переменную состояния; иногда их несколько (вложенный flattening).
- **Предикат не константен.** Возможно, он зависит от данных, которые надо взять из контекста; или это не opaque predicate, а настоящая проверка.
- **Декомпилятор даёт кашу.** Пробуйте разные инструменты (Ghidra, IDA, Binary Ninja) — они по-разному справляются; иногда помогает плагин деобфускации.
- **Слишком много мёртвого кода.** Отсеките его динамически: запустите программу и оставьте только реально исполненные блоки.
- **Обфускация коммерческая.** Flattening из протектора может быть нелинейным (несколько диспетчеров); потребуется символьная девиртуализация.

## Частые вопросы

**Flattening и виртуализация — одно?** Нет: flattening переписывает нативный поток управления, виртуализация переводит код в байткод своей VM. Часто их комбинируют.

**Как найти переменную состояния?** Это переменная, которая читается в начале итерации и присваивается в конце каждого блока; часто инициализируется константой.

**Помогает ли символьное исполнение?** Да: оно может «пройти» диспетчер и восстановить реальный путь, игнорируя ложные ветви.

**Насколько это обратимо?** Локальный flattening обычно обратим; глобальный с несколькими диспетчерами и мутацией — существенно тяжелее.

## Куда дальше

Мы научились **распознавать** обфускацию. Дальше возьмём её и **снимем**: упростим MBA-выражения,
удалим ложные предикаты и восстановим исходную логику. А пока главное запомни: **если код
выглядит запутанным, но ведёт себя обычно — это обфускация, и её снимают упрощением или
динамикой**.
