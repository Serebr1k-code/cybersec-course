Обфускация — это искусство делать код нечитаемым, не меняя его поведения. Она используется
защитой (DRM, античит, коммерческие протекторы), вредоносами (антианализ, уклонение от AV) и
авторами CTF-задач. Реверсеру важно **распознавать** техники обфускации: от этого зависит выбор
стратегии — статический анализ, динамика, символьное исполнение или девиртуализация. Этот урок —
каталог основных техник с признаками и подходами к их снятию.

## Зачем и какие цели у обфускации

Обфускация решает три задачи:

1. **Усложнить понимание** (anti-reversing) — чтобы человек потратил максимум времени.
2. **Затруднить автоматический анализ** (anti-AV, anti-YARA) — сломать сигнатуры.
3. **Скрыть данные/логику** (строки, ключи, алгоритмы).

Важно: обфускация **не меняет семантику** — код выполняет то же самое. Значит, всегда есть способ
восстановить поведение (динамикой, эмуляцией, упрощением). Хорошая новость для реверсера.

## Каталог техник

| Техника | Суть | Признак |
|---|---|---|
| String encryption | строки шифруются, дешифруются в рантайме | нет читаемых строк, вызов дешифратора |
| Control-flow flattening | CFG в один цикл со `state` | гигантский `switch`/`while` |
| Opaque predicates | всегда-истинные условия | странные `if`, недостижимый код |
| MBA | арифметика заменена на запутанную | монструозные выражения |
| Dead code injection | мёртвые блоки | недостижимые ветви |
| Instruction substitution | инструкция → эквивалент | лишние `xor`/`add` |
| Junk bytes / overlap | мусорные байты, перекрытие | странный дизасм |
| Virtualization | свой байткод + VM | dispatcher, хендлеры |
| Metamorphism | код меняется при копировании | нет фиксированной сигнатуры |
| Anti-debug/anti-VM | детект анализа | вызовы `IsDebuggerPresent`/`cpuid` |
| Packing/encryption | шифрование всего кода | высокая энтропия, stub |

## Строковое шифрование

Самый распространённый и самый «дешёвый» для снятия вид. Реализации:

- **XOR с константой**: `str[i] ^ 0x41`.
- **Стековая сборка**: строка кладётся по частям через `mov [rsp], ...`.
- **Функция-дешифратор**: каждая строка расшифровывается вызовом.

Признаки: отсутствие строк в `strings`, наличие функции с циклом XOR, подозрительные массивы байт.

Снятие:
- **Динамически**: breakpoint на выходе дешифратора, дамп результата. В x64dbg — условный лог;
  в Frida — хук на функцию.
- **Скриптом**: реконструировать алгоритм (часто простой XOR) и расшифровать все строки.
- **Автоматически**: `FLOSS` (FireEye) — извлекает зашифрованные/стековые строки из malware.

## Control-flow flattening

Реальный поток управления «сплющивается» в один цикл:
```c
state = 0;
while (1) {
    switch (state) {
        case 0: a = read(); state = 3; break;
        case 3: if (a > 0) state = 7; else state = 1; break;
        case 7: b = a * 2; state = 2; break;
        ...
    }
}
```
Признаки: одна функция с десятками `case`, переменная `state`, почти нет вложенных структур.

Снятие: восстановить граф переходов `state` (какой case ведёт в какой), затем «разложить» его в
нормальный CFG. Инструмент: плагин **deflat** (IDA) или скрипты на основе анализа `state`-переменной.
Символическое исполнение (angr) тоже умеет проходить такие графы.

## Opaque predicates и MBA

**Opaque predicate** — условие, которое всегда истинно/ложно, но выглядит зависящим от данных:
```c
if ((x * (x + 1)) % 2 == 0)   // всегда истинно (произведение чётного и нечётного)
    real_code();
else
    junk_code();
```
Оно добавляет мёртвые ветви и путает CFG.

**MBA (Mixed Boolean-Arithmetic)** — замена простой операции запутанной:
```
x + y   = (x ^ y) + 2*(x & y)
x ^ y   = (x | y) - (x & y)
x - y   = (x ^ -y) + 2*(x & -y)
```

Снятие:
- **Символическое упрощение** (Z3/Triton/Miasm): построить выражение и упростить.
- **Плагины** (`gooMBA`, `MBA-Solver`, скрипты IDA/Ghidra).
- **Динамический анализ**: подставить значения и наблюдать результат.

## Instruction substitution и junk code

- **Substitution**: `mov eax, 1` → `xor eax, eax; inc eax`. Поведение то же, вид другой.
- **Junk bytes**: вставка байтов, которые декодируются как «мусорные» инструкции, но исполняются;
  либо перекрытие инструкций (дизасм с неправильного смещения даёт другой код).
- **Dead code**: ветви, которые никогда не выполняются, но содержат «заманчивую» ложную логику.

Признаки: лишние операции, странный дизасм, недостижимые блоки. Снятие: оптимизация IR, динамика
(что реально исполняется), упрощение.

## Virtualization и metamorphism

**Виртуализация** (VMProtect, Tigress, Code Virtualizer) — код переводится в собственный байткод и
исполняется интерпретатором. Это самая тяжёлая техника; подробно разобрана в уроке про VM-crackmes.

**Метаморфизм** — код меняет себя при каждом запуске/копировании (перестановка блоков, подстановка
инструкций). Признак: разные байты, одинаковое поведение. Снятие: сравнение поведения (не байтов),
нормализация через IR.

## Разобранный пример: снятие строкового шифрования

Дано: бинарник, `strings` показывает мало осмысленного. Ищем дешифратор.

**Шаг 1. Найти функцию-кандидат.** В IDA сортируем функции по количеству вызовов (`Ctrl+P`). Функция,
вызываемая из десятков мест и принимающая указатель + длину, — вероятный дешифратор.

**Шаг 2. Разобрать алгоритм.**
```c
void decrypt(char *s, int n) {
    for (int i = 0; i < n; i++)
        s[i] ^= 0x5A ^ (i & 0x0f);
}
```

**Шаг 3. Воспроизвести и расшифровать.** Извлекаем все зашифрованные массивы (xref на функцию) и
расшифровываем на Python:
```python
def dec(b):
    return bytes(c ^ 0x5A ^ (i & 0x0f) for i, c in enumerate(b))
print(dec(bytes.fromhex("...")))
```

**Шаг 4. Альтернатива — динамика.** Ставим breakpoint на `return` дешифратора, логируем аргумент —
получаем все строки без ручного разбора.

## Инструменты против обфускации

| Инструмент | Против чего |
|---|---|
| **FLOSS** | зашифрованные/стековые строки |
| **deflat** (IDA) | control-flow flattening |
| **gooMBA / MBA-Solver** | MBA |
| **Triton / Z3 / Miasm** | символическое упрощение |
| **angr** | обход CFG, решение ограничений |
| **Pin / DynamoRIO / Frida** | динамика, что реально исполняется |
| **Tigress deobf** | CFF/opaque (для Tigress) |
| **D810 / IDA plugins** | комбинированное упрощение |

## Крайние случаи и подводные камни

- **Самомодифицирующийся код.** Статический дизасм бесполезен — нужна динамика/эмуляция.
- **Несколько слоёв.** Сначала распаковка, потом деобфускация, потом VM — не путайте порядок.
- **Анти-анализ.** Обфускация часто сопровождается anti-debug/anti-VM — сначала снимите их
  (ScyllaHide, hardened VM).
- **Ложная семантика.** Junk-код может выглядеть «правдоподобно» — доверяйте только тому, что
  реально исполняется.
- **Упрощение может ошибиться.** Проверяйте результат символического упрощения на тестовых значениях.
- **Время.** Полная деобфускация VMProtect — недели. Оценивайте, нужен ли весь код или только путь.
- **Производительность инструментов.** Символьное исполнение на больших бинарях «взрывается» —
  ограничивайте глубину/ветвления.

## Что дальше / решение

1. Идентифицировать техники (строки, CFF, MBA, VM, anti-debug).
2. Снять базовые слои (упаковка, anti-debug) — иначе дальше не продвинуться.
3. Строки — динамически/FLOSS; CFF — `deflat`/символика; MBA — Z3/плагины.
4. Для VM — трассировка конкретного пути (см. урок VM-crackmes).
5. Всегда проверять результат на тестовых данных.

Принцип: **обфускация не меняет поведение — значит, поведение можно восстановить**. Начните с
самого дешёвого слоя (строки), двигайтесь к самому дорогому (VM). Не пытайтесь сразу победить всё.

## Anti-debug и anti-VM как часть обфускации

Обфускация почти всегда идёт в паре с противодействием анализу. Основные приёмы:

- **Детект отладчика**: `IsDebuggerPresent`, PEB, `NtQueryInformationProcess`, тайминги.
- **Детект VM**: CPUID hypervisor bit, артефакты VMware/VirtualBox, MAC-префиксы.
- **Детект инструментирования**: проверка хуков (сравнение пролога с диском), поиск `frida-agent`,
  проверка `INT3`.
- **Самоуничтожение/обман**: при детекте — другой путь исполнения, краш, «безобидное» поведение.

Стратегия: **сначала нейтрализовать anti-анализ**, иначе вы будете анализировать не тот код, который
исполняется в реальности. Инструменты: ScyllaHide (Windows), hardened-VM, патч проверок.

## Packing vs obfuscation: не путать

Это разные слои:

- **Packing** — сжатие/шифрование всего кода, при котором оригинал восстанавливается в памяти.
  Цель — уменьшить размер и скрыть код. Снимается распаковкой (см. урок packing-upx).
- **Obfuscation** — переписывание кода с сохранением семантики (CFF, MBA, строки). Цель — усложнить
  понимание. Снимается деобфускацией (см. соседний урок).

Порядок работы: сначала **packing**, потом **obfuscation**. Пока код упакован, обфускация
недоступна для анализа.

## Рабочий процесс идентификации обфускации

Быстрый чек-лист, который стоит пройти при встрече с «нечитаемым» бинарником:

1. **Упакован?** `die`, энтропия секций, `strings`. Если да — распаковать.
2. **Строки читаемы?** Если нет — искать дешифратор (string encryption).
3. **Есть гигантский `switch`/`while`?** Признак control-flow flattening.
4. **Странные условия и мёртвый код?** Opaque predicates.
5. **Монструозная арифметика?** MBA.
6. **Диспетчер + таблица хендлеров?** Виртуализация.
7. **Вызовы `cpuid`/`IsDebuggerPresent`?** Anti-debug/anti-VM.

По результатам выбирается инструмент: FLOSS (строки), deflat (CFF), Z3 (MBA), Unicorn (VM), ScyllaHide
(anti-debug). Идентификация — половина успеха: неправильно выбранный инструмент тратит дни.

## Отчёт по обфускации

Фиксируйте: какие техники найдены, в каком порядке снимались, какими инструментами, что получилось
на выходе (деобфусцированный код/строки/CFG). Для malware это часть профиля семейства — техники
повторяются от образца к образцу.
