## Вопрос, с которого всё начинается

У жертвы зашифрованы файлы: рядом с каждым лежит `report.zip.locked`, а в папке — нота с
требованием выкупа. Можно ли восстановить данные **без** ключа атакующего? Оказывается, часто
да — потому что ransomware обычно ломается не на «сильной криптографии», а на **реализации**:
слабый генератор ключа, повторный IV, ключ на сервере.

Реверс ransomware — одна из самых прикладных задач анализа malware: понять схему шифрования,
найти слабость и, если повезёт, расшифровать файлы. Разберём это на учебном шифровальщике.

Опираемся на прошлые уроки: мы умеем делать триаж (`strings`, `binwalk`) и запускать образец в
изоляции. Теперь применим это к крипто-логике.

## Наш пример

Перед нами результат работы учебного ransomware — зашифрованный файл:

```
$ ls -l report.zip.locked
-rw-r--r-- 1 user user 48 Oct 12 10:23 report.zip.locked
$ xxd report.zip.locked | head -1
00000000: 3b4c 5a34 016d 103a 3eb4 bd23 cbcf 400c  ;LZ4.m.:>..#..@.
```

Файл начинается с непонятных байтов `3b 4c 5a 34 ...`. Судя по имени, исходник был ZIP-архивом
(у ZIP первые байты всегда `50 4B 03 04` — «PK\x03\x04»). Мы знаем открытый текст начала файла —
и это ключ к атаке. Задача: восстановить содержимое.

## Шаг 1: триаж и идентификация

Работаем **только в изолированной ВМ** без сети. Первым делом — что за образец:

```
$ strings -a -n 6 ransom.bin | grep -iE 'AES|key|seed|time|locked'
AES-256-CBC key=seed(time)
.locked
READ_ME.txt
```

Строка `key=seed(time)` — прямое указание: ключ генерируется из **времени**. Это классическая
слабость. Дальше смотрим на тип схемы шифрования.

## Шаг 2: классификация схемы

От схемы зависит вся стратегия восстановления:

| Схема | Как работает | Слабость |
|---|---|---|
| Гибридная (RSA+AES) | файлы шифрует AES, ключ — RSA | утечка/слабость RSA-ключа |
| Симметричная, общий ключ | один ключ на все файлы | утечка ключа = всё расшифровано |
| Симметричная, ключ на файл | ключ для каждого файла | нужен перебор или слабость RNG |
| XOR/RC4/самодельные | потоковые, самописные | known-plaintext, частотный анализ |
| Ключ на C2 | ключ только на сервере | offline-восстановление невозможно |

Наш пример — симметричная схема с ключом, выведенным из времени, плюс XOR. Значит, работаем по
RNG и known-plaintext.

## Шаг 3: находим слабость генератора

Декомпилируем генератор ключа (в Ghidra/IDA) — или, для учебного образца, читаем его исходник.
Ключевая логика:

```c
key = malloc(32);
srand(time(NULL));                 // <-- слабость: seed = текущее время
for (i = 0; i < 32; i++) key[i] = rand() & 0xff;
```

Здесь `srand(time(NULL))` задаёт **seed** генератора псевдослучайных чисел текущим временем. Если
seed известен — а время запуска мы знаем по метке файла (`mtime`), — то вся последовательность
`rand()` воспроизводима, а значит, и ключ. Пространство перебора — не 2²⁵⁶, а **десятки секунд**.

## Шаг 4: восстанавливаем ключ

Строим keygen-перебор: пробуем seed'ы вокруг времени создания зашифрованного файла и проверяем,
расшифровывается ли известный заголовок ZIP (`PK\x03\x04`):

```
$ python3 ransom_demo.py encrypt
encrypted report.zip -> report.zip.locked ; seed(sec) = 1791789794

$ python3 ransom_demo.py recover
seed found: 1791789794
recovered first bytes: b'PK\x03\x04' -> b'PK\x03\x04secret financial report cont'
```

Ключ восстановлен, файл расшифрован. Проверяем:

```
$ cmp report.zip report.recovered && echo "RECOVERED == ORIGINAL"
RECOVERED == ORIGINAL
```

Мы обошли шифрование, не имея ключа атакующего, — только за счёт слабости seed'а и знания
формата файла.

## Шаг 5: другие векторы восстановления

Time-seed — лишь один из классов атак. Основные векторы:

- **Слабый RNG.** `rand()` без `srand` (фиксированный seed), `GetTickCount()`, маленькое
  пространство. Перебор seed'а.
- **Повтор IV в CTR/OFB.** Если IV повторяется, XOR двух шифртекстов даёт XOR двух открытых
  текстов — «two-time pad». Восстанавливаем оба.
- **Known-plaintext.** Заголовки форматов (PNG `89 50 4E 47`, ZIP `50 4B 03 04`, PDF `%PDF`)
  позволяют восстановить **keystream** потокового шифра. Если keystream повторно используется
  для всех файлов — расшифровываем всё.
- **Слабый RSA.** Общий модуль `n` у двух ключей ломается через `gcd`; маленькая экспонента;
  факторизация.
- **Ключ в памяти.** До перезагрузки ключ часто остаётся в RAM — его достают дампом
  (`volatility3 -f memory.dmp windows.malfind`).
- **Форензика после атаки.** Теневые копии (`vssadmin list shadows`), temp/кэш, незашифрованные
  файлы, дампы памяти, журналы (Event Log, Prefetch).

Инструменты триажа и анализа: `binwalk -E` (энтропия/упаковка), `upx -d` (распаковка),
`yara -r` (сигнатуры семейства), `capa` (авто-возможности), `strings -t x` (адреса строк),
x64dbg с точками останова на `CryptEncrypt`/`BCryptEncrypt` (ключ в памяти до шифрования).

## Стенд для безопасного анализа

Правильный стенд обязателен — иначе образец опасен:

- **ВМ без сети** (снапшоты до и после), либо сеть только через INetSim.
- **Файлы-приманки** (не настоящие данные) для наблюдения шифрования.
- **Снимок диска** до запуска и инструмент отката (VirtualBox/VMware snapshots).
- **Отключённые общие папки** с хостом и буфер обмена.
- **Мониторинг** (Procmon, Sysmon, API Monitor) — чтобы видеть файлы, реестр и сеть.

Если образец отправляет ключ на C2, перехвати трафик (`inetsim`, `mitmproxy`) — часто сессионный
ключ уходит в первом POST-запросе.

## Что мы теперь знаем

- Ransomware — это в первую очередь **реализация**, а не «сильная крипта»; ошибки и есть цель.
- Триаж: `strings`/`binwalk`/`yara` → определить семейство и схему.
- Схема бывает гибридной (RSA+AES), симметричной и потоковой; от неё зависит стратегия.
- **Слабость RNG** (time-seed, `rand()`) делает ключ предсказуемым — перебираем десятки seed'ов.
- **Known-plaintext** по заголовкам форматов восстанавливает keystream потоковых шифров.
- Работать только в изолированной ВМ со снапшотами; ключ может уйти на C2 — логируй сеть.

## На что смотреть дальше

- Не «ломай AES» — ищи ошибку в **генерации и хранении** ключа.
- Всегда проверяй `mtime`/маркеры запуска: они дают время для перебора seed'а.
- Если keystream повторно используется для всех файлов — это катастрофа для атакующего.
- Анализируй не только финальный бинарник: стаб-дроппер может нести нагрузку во втором слое.
- Без снапшота один запуск «заражает» стенд навсегда — изоляция обязательна.
- Если ключ только на C2 — offline-восстановление невозможно; цель смещается к IR-отчёту.

## Куда дальше

Мы прошли путь от зашифрованного файла до восстановления данных. Дальше возьмём eBPF — технологию
наблюдения за ядром Linux, которая всё чаще встречается и в защите, и в малвари. А пока главное
запомни: **в ransomware ломай RNG и хранение ключа**, а не сам алгоритм, и всегда работай в
изоляции.

## Где пригодится

- **CTF:** Reversing/Crypto — ransomware-челленджи.
- **DFIR/IR:** восстановление данных после атаки.
- **Threat intelligence:** тактики шифровальщиков, атрибуция.
- **Работа:** malware analysis, incident response.
