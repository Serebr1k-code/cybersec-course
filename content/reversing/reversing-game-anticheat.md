Античит — это, пожалуй, самый агрессивный класс защиты, с которым сталкивается реверсер. В отличие
от DRM или лицензионных проверок, античит не просто защищает код — он **активно противодействует
анализу и модификации в рантайме**: детектит отладчики, хуки, дамперы, виртуальные машины, читает
память процесса, проверяет целостность, сканирует систему на известные читы. Реверс античита —
это отдельная дисциплина на стыке kernel/user-mode, DBI и криптографии. Этот урок даёт системную
карту техник (на концептуальном уровне) и методологию их разбора.

## Что защищает античит

Античит решает три задачи:

1. **Обнаружить** факт анализа (отладчик, VM, инструментирование).
2. **Помешать** модификации (защита памяти, integrity-чеки, обфускация).
3. **Сообщить** на сервер (телеметрия, бан).

Соответственно, реверс античита — это поиск того, **какие именно проверки выполняются и как их
нейтрализовать** (или как обойти детект при легитимном исследовании). Важно: этот урок не про
создание читов, а про понимание защиты и методологию анализа.

## Архитектура: user-mode vs kernel-mode

| Компонент | Уровень | Что делает | Сложность реверса |
|---|---|---|---|
| Game client module | user | локальные проверки, integrity | средняя |
| Anti-cheat DLL | user | детект отладчика/хуков, сканирование памяти | высокая |
| Kernel driver | ring0 | защита памяти, скрытие, мониторинг | очень высокая |
| Hypervisor (VBS) | ring -1 | изоляция, перехват | крайне высокая |
| Server-side | cloud | статистика, ML-детект | недоступна |

Современные античиты (EAC, BattlEye, Vanguard, Riot Vanguard) обязательно включают **kernel-driver**:
он читает/защищает память процесса игры и перехватывает системные вызовы. Именно поэтому реверс
античита часто упирается в анализ драйвера (`svc-*`/kernel-уроки).

## Теория: техники детекта и их признаки

**1. Debugger detection.** `IsDebuggerPresent`, `CheckRemoteDebuggerPresent`, PEB (`BeingDebugged`,
`NtGlobalFlag`), `NtQueryInformationProcess` (`ProcessDebugPort`, `ProcessDebugObjectHandle`,
`ProcessDebugFlags`), тайминги (`rdtsc`, `QueryPerformanceCounter`).

**2. VM detection.** CPUID hypervisor bit (`leaf 1, ECX bit 31`), артефакты VMware/VirtualBox в
реестре, MAC-префиксы, `cpuid` vendor (`VMwareVMware`, `KVMKVMKVM`), I/O порты (`0x5658` — VMWare
backdoor).

**3. Instrumentation/hook detection.** Сравнение пролога функций в памяти с диском (`inline hook`
checks), проверка IAT/EAT, сканирование на известные модули (`dbghelp`, `frida-agent`), проверка
`INT3`-байтов (`0xCC`) в коде, сравнение `.text` с эталонным хешем.

**4. Memory scanning.** Античит читает память игры и ищет сигнатуры известных читов/спуферов;
иногда сканирует всю систему.

**5. Integrity checks.** Хеширование сегментов кода, CRC, проверка контрольных сумм на сервере.

## Разобранный пример: снятие user-mode детекта

Дано: игровой модуль, который «вылетает» под отладчиком. Цель — найти проверку.

**Шаг 1. Импорты.** Смотрим импорты и строки:
```bash
rabin2 -i anticheat.dll | grep -Ei 'IsDebuggerPresent|NtQuery|CheckRemote'
strings -a anticheat.dll | grep -Ei 'debug|vmware|vbox|frida'
```

**Шаг 2. Xref на `IsDebuggerPresent`.** В IDA `X` на импорте → функция-обёртка. Внутри видим
классическую проверку:
```c
if (IsDebuggerPresent()) {
    report_and_exit();
}
```
Патчим `jz` на `jmp`/`nop`, либо перехватываем в отладчике возврат `0`.

**Шаг 3. PEB-проверка.** Многие античиты не зовут API, а читают PEB напрямую:
```asm
mov rax, gs:[0x60]        ; PEB
movzx eax, byte [rax+2]   ; BeingDebugged
test eax, eax
jnz  exit
```
Это видно в дизассемблере без импортов. Нейтрализуем патчем или плагином (ScyllaHide) —
он на лету правит PEB-поля, чтобы детект не срабатывал.

**Шаг 4. Тайминговые проверки.** Ищем `rdtsc`:
```asm
rdtsc
; ... некоторый код ...
rdtsc
sub eax, prev
cmp eax, threshold
ja  debugger_detected
```
Обход: замедлить/ускорить шаг, либо патчить сравнение.

## ScyllaHide и стандартный обход

**ScyllaHide** — плагин для x64dbg/IDA/OllyDbg, скрывающий отладчик:

- Правит `PEB.BeingDebugged`, `NtGlobalFlag`.
- Перехватывает `NtQueryInformationProcess` и подменяет результаты.
- Скрывает аппаратные точки останова (DR-регистры).
- Защищает секции памяти от проверок.

Установка в x64dbg: положить `ScyllaHide.dp64` в `plugins/`, в окне ScyllaHide включить профиль
(«VMProtect», «Themida» и т.д.). Это снимает большинство user-mode детектов за один шаг.

## Kernel-mode античит: что смотреть

Если детект в драйвере, реверс усложняется:

- **`DriverEntry`** — точка входа; ищите регистрацию callback'ов (`ObRegisterCallbacks`,
  `PsSetCreateProcessNotifyRoutine`, `CmRegisterCallback`).
- **SSDT/IDT hooks** — перехват системных вызовов; проверяйте через `WinDbg` + `!ssdt`.
- **EPROCESS/ETHREAD манипуляции** — драйвер может скрывать процессы/потоки, менять `KPROCESS`.
- **`MmProtectMdlSystemAddress`, `MmMapIoSpace`** — манипуляции с памятью.
- **Мониторинг `NtOpenProcess`, `NtReadVirtualMemory`** — блокировка читателей памяти.

Статически драйвер реверсят как обычный PE (Ghidra/IDA + типы `ntifs.h`). Динамически — в VM с
kernel-debug (`WinDbg` через COM/serial или `bcdedit /debug on`).

## Hypervisor-защита (VBS / ring -1)

Vanguard и подобные поднимают hypervisor, чтобы контролировать ring0. Признаки:

- CPUID leaf `0x40000000` возвращает vendor гипервизора.
- MSR-биты (`IA32_VMX_*`), включённый VT-x.
- Скрытые EPT-хуки.

Реверс hypervisor — уровень ядра исследований; обычно ограничиваются пониманием, что **memory
интроспекция блокируется**, и анализ ведут снаружи (DMA, физическая память).

## Крайние случаи и подводные камни

- **Античит как malware.** Он ставит драйвер с высокими привилегиями — запускайте только в
  изолированной VM с изолированной сетью.
- **Детект VM.** Античит может забанить/отказаться работать в VM. Для анализа используйте
  hardened-VM (скрытие артефактов, `kvm` с patched CPUID).
- **Обфускация (VMProtect/Themida).** Критические проверки виртуализированы — нужен devirtualization
  (см. урок про VM-crackmes).
- **Серверная корреляция.** Даже идеальный клиентский обход не поможет, если сервер считает статистику
  и бан­ит аномалии.
- **Юридическая/этическая сторона.** Реверс античита для создания читов нарушает ToS/закон; в рамках
  CTF/исследований/защиты — легитимно. Всегда в рамках авторизованной задачи.
- **Тайминги.** Античит-проверки часто на таймерах; их отсутствие — тоже сигнал для сервера.

## Что дальше / решение

1. Определить уровень защиты: user-only, kernel, hypervisor.
2. Для user-mode — ScyllaHide + патч проверок; начать с импортов `IsDebuggerPresent`/`NtQuery*`.
3. Для kernel — статический реверс драйвера в Ghidra/IDA с типами `ntifs.h`, затем WinDbg.
4. Для VM-обфускации — devirtualization (трассировка VM, восстановление opcode-таблицы).
5. Всегда в изолированной среде; помните про серверную телеметрию.

Методология для CTF-задач «обойти античит»: сначала **снять user-mode детекты** (ScyllaHide),
затем **найти проверку** (xref на API/строки), затем **патч или хук**. В 80% CTF-задач этого
достаточно; kernel/hypervisor — уже исследовательский уровень.

## Справочная таблица: детект → обход

| Техника детекта | Признак в коде | Обход |
|---|---|---|
| `IsDebuggerPresent` | вызов API | ScyllaHide / патч возврата |
| PEB `BeingDebugged` | `gs:[0x60]` + offset 2 | ScyllaHide / патч |
| `NtQueryInformationProcess` | импорт, `ProcessDebugPort` | хук / ScyllaHide |
| Hardware breakpoints | `GetThreadContext`, DR0-DR7 | убрать HW BP |
| `rdtsc` timing | две `rdtsc`, вычитание | патч сравнения |
| VM detection | `cpuid`, строки VMware | hardened VM |
| Hook detection | сравнение пролога с диском | убрать/переставить хук |
| Integrity (CRC) | хеш `.text` | патч хеша / рантайм-хук |

## Разобранный пример: статический анализ kernel-driver

Дано: драйвер античита `ac.sys`. Цель — понять, что он мониторит.

**Шаг 1. Импорты и строки.** `rabin2 -i ac.sys` покажет `PsSetCreateProcessNotifyRoutineEx`,
`ObRegisterCallbacks`, `CmRegisterCallbackEx`, `MmCopyVirtualMemory`. Уже по импортам ясно: драйвер
следит за созданием процессов, защищает хендлы и умеет читать память других процессов.

**Шаг 2. `DriverEntry`.** В IDA/Ghidra ищем точку входа по `DriverEntry` (или по xref на
`IoCreateDevice`). Внутри — регистрация callbacks и создание device-object с именем вида
`\\Device\\ACDriver`.

**Шаг 3. Callback-функции.** Каждая регистрация ссылается на функцию-обработчик. Разбираем её:
часто там проверка имени образа (whitelist), отказ в доступе к процессу игры, логирование.

**Шаг 4. Скрытые проверки.** Ищем `__debugbreak`/`int 3` (анти-патч), сравнения хешей модулей,
обращения к `EPROCESS`/`KTHREAD`. Типы из `ntifs.h`/`wdm.h` загружаются в Ghidra через Data Type
Manager или генерируются из PDB (если доступен symbol server Microsoft).

**Шаг 5. Динамика.** В изолированной VM включаем kernel-debug:
```text
bcdedit /debug on
bcdedit /dbgsettings serial debugport:1 baudrate:115200
# WinDbg (host) → Kernel → COM → pipe/serial
kd> lm                 ; список модулей
kd> bp ac!DriverEntry  ; breakpoint
kd> u ac!DriverEntry   ; дизассемблер
kd> !process 0 0 game.exe
```
Так можно увидеть, какие поля `EPROCESS` драйвер трогает, и какие хуки ставит.

## DMA-анализ: когда hypervisor блокирует интроспекцию

Продвинутые античиты (Vanguard) мешают даже ring0-читателям, поднимая hypervisor и защищая память
игры через EPT. Тогда единственный «честный» канал — **DMA**: внешнее устройство (например, FPGA
через PCIe, или Thunderbolt-девайс) читает физическую память в обход CPU. Это аппаратный анализ:
- PCILeech + FPGA (Screamer) — чтение/запись физической памяти по PCIe.
- Требует физического доступа и обычно исследуется в специальной лабораторной сборке.

Для обычного реверса это уже периферия: чаще достаточно понять, что **любая программная
интроспекция блокируется**, и перейти к анализу через внешние каналы или к изучению конкретной
задачи иначе (например, анализировать сетевой протокол, а не память).

## Проверка целостности и её обход

Integrity-чеки — любимый механизм античитов. Реализации:

- **CRC32/CRC64 по `.text`** — драйвер периодически хеширует секцию кода игры и сравнивает с эталоном.
- **Хеш по страницам** — сравнение постранично, чтобы детектить точечные патчи.
- **Self-checksum** — функция проверяет свой собственный байткод.
- **Серверная сверка** — клиент шлёт хеши, сервер сравнивает с эталоном для данной версии.

Обход на уровне исследования:
1. Найти функцию-хешер (xref на `RtlComputeCrc32`, таблица CRC, цикл).
2. Патчить **не код игры, а хеш-функцию** (вернуть ожидаемое значение) — это менее заметно, чем
   патч самой проверки.
3. Перехватить вызов через inline-hook в рантайме, подменяя результат.
4. Помнить: серверная сверка ломает все локальные обходы — нужна корреляция с версией бинарника.

## Настройка ScyllaHide по шагам

```text
1. Скачать ScyllaHide (репозиторий x64dbg/ScyllaHide), взять ScyllaHide.dp64/dp32.
2. Положить в <x64dbg>/plugins/.
3. Запустить x64dbg, открыть целевой процесс.
4. Plugins → ScyllaHide → Options.
5. Включить профиль (например, VMProtect/Themida) или выставить галочки вручную:
     - PEB.BeingDebugged = 0
     - NtGlobalFlag = 0
     - Hook NtQueryInformationProcess
     - Hook NtSetInformationThread (HideThreadFromDebugger)
     - Remove DR registers
6. Применить и перезапустить отладку.
```

После этого большинство user-mode детектов не срабатывает, и можно спокойно ставить breakpoints.

## Где пригодится

- **CTF Reversing:** задачи «взломай игру/получи ресурсы» — комбинация памяти, патчинга, логики.
- **Game security:** понимание читов и анти-читов для защиты игр (работа в game security командах).
- **Vuln research:** анализ kernel-mode драйверов анти-читов — отдельная ниша уязвимостей.
- **Работа (RE-команда):** реверс больших оптимизированных бинарников, работа с движками.
- **Собес:** вопросы про integrity checks, kernel-mode защиту — для позиций game security.
