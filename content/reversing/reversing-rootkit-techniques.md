## Вопрос, с которого всё начинается

Ты смотришь список процессов, но их меньше, чем должно быть: подозрительный процесс «исчез» из вывода, хотя потребляет CPU. Или файл есть, но `ls` его не показывает. Кто-то правит структуры ядра изнутри. Это руткит.

## Наш пример

Возьмём учебный руткит для Linux (`rootkit.ko`) и его поведение: модуль скрывает процесс с определённым именем. Загрузим его в изолированной ВМ и посмотрим, что происходит:

```bash
$ lsmod | grep rootkit
rootkit   16384  0
$ ps aux | grep -c hidden   # процесса нет в списке
0
$ cat /proc/hidden/status    # но он существует
Name: hidden
```

Процесс невидим для `ps`, но реально работает. Разберём, как это сделано и как это найти.

## Шаг 1: что такое руткит

**Руткит** — код, который скрывает присутствие злоумышленника в системе: процессы, файлы, соединения, драйверы, записи реестра. Руткиты бывают **user-mode** (перехват библиотек, например через `LD_PRELOAD` или хуки API) и **kernel-mode** (работа в ядре, где нет защиты памяти). Kernel-руткиты опаснее: они могут скрывать что угодно и противодействовать обнаружению. Именно их разбирают в этом уроке.

## Шаг 2: DKOM — прямая модификация объектов

**DKOM** (Direct Kernel Object Manipulation) — приём, при котором руткит меняет структуры ядра напрямую. В Linux список процессов — это двусвязный список `task_struct` (через `tasks`). Руткит находит нужный `task_struct` и **вырезает** его из списка, переставляя указатели `prev`/`next` соседей. Процесс продолжает исполняться (планировщик работает по другим структурам), но `ps`/`/proc` его не видят. В Windows аналогично правят `EPROCESS`/`ActiveProcessLinks`. Признак DKOM: расхождение между разными источниками (например, `ps` не видит, а перебор через `/proc` или счётчики — видит).

## Шаг 3: патчинг таблиц и системных вызовов

Другой класс — перехват путей. В Windows руткиты патчат **SSDT** (System Service Descriptor Table), подменяя адрес обработчика `NtQuerySystemInformation`, чтобы он не возвращал скрытые объекты. В Linux — перехватывают таблицу системных вызовов (`sys_call_table`), подменяя `sys_getdents`/`sys_kill`. Современные варианты используют **ftrace**-хуки или **kprobes** — официальные механизмы трассировки ядра, которые сложнее обнаружить, потому что они легитимны. Признак: адрес обработчика в таблице не совпадает с адресом в ядре; или на функцию стоит ftrace-hook.

## Шаг 4: eBPF-руткиты

**eBPF** — механизм, позволяющий запускать программы в ядре Linux без модуля. Атакующие используют его для сокрытия: eBPF-программа перехватывает системные вызовы и фильтрует результаты (например, скрывает PID). Плюсы для атакующего: не нужен LKM, код проверяется верификатором (но при этом легитимен), сложнее обнаружить. Признак: список загруженных eBPF-программ (`bpftool prog list`) содержит подозрительные, привязанные к `kprobe`/`tracepoint` функциям, которые читают/меняют аргументы системных вызовов.

## Шаг 5: как находить руткиты

Обнаружение строится на **расхождениях** и **инвариантах**. Первое: сравни результаты разных источников (утилиты ядра vs обход структур напрямую) — руткит скрывает не везде. Второе: проверь целостность ядра — адреса в `sys_call_table`/SSDT, наличие неизвестных ftrace-хуков (`cat /sys/kernel/debug/tracing/enabled_functions`), необычные eBPF-программы. Третье: сравни память ядра с образом на диске (для модулей). Инструменты: `Volatility` (для дампов памяти), `chkrootkit`/`rkhunter` (эвристика), `bpftool`, `ftrace`. В Windows — `GMER`, `Volatility`, проверка SSDT.

## Шаг 6: реверс ядерного модуля

Разбор самого руткита: `rootkit.ko` — это ELF-модуль, но связанный с ядром. В нём есть `init_module`/`cleanup_module` (или `module_init`/`module_exit`), таблица символьных версий (`__versions`) и вызовы ядерных API (`kallsyms_lookup_name`, `list_del`, `set_memory_rw`). Для реверса: извлеки строки (имена скрываемых процессов, константы), найди в дизассемблере операции над списками (`list_del`), патчи `sys_call_table`. Учитывай, что модуль может быть обфусцирован и содержать анти-анализ. Для Windows-драйверов — `DriverEntry`, IRP-обработчики, DKOM-операции над `EPROCESS`.

## Шаг 7: инструменты

Для Linux: `Volatility3` (плагины `linux.*`), `bpftool`, `ftrace`, `crash` (анализ kdump), `lsmod`/`/proc/modules`, `kallsyms`. Для Windows: `Volatility3` (`windows.ssdt`, `windows.dkom`), `GMER`, `WinDbg` (с ядерной отладкой), `pooltag`-анализ. Для дампов памяти — поиск аномалий в списках и таблицах. Важно: обнаружение руткита в живой системе ненадёжно (он может лгать) — надёжнее анализ дампа или offline.

## Шаг 8: где это в реальной работе

Руткиты — высшая лига малвари: их используют APT, некоторые семейства вымогателей (для сокрытия) и буткиты (в прошивке). Реверс ядерного кода нужен и в защите: EDR-продукты работают в ядре, античиты тоже, и их нужно уметь анализировать. Понимание DKOM/SSDT/eBPF — основа для разработки детектов и для понимания, почему «обычные» инструменты не видят угрозу.

## Что мы теперь знаем

- Руткиты скрывают объекты, работая в ядре без защиты памяти.

- DKOM вырезает объекты из списков ядра, не останавливая их.

- SSDT/syscall-патчинг и ftrace/eBPF-хуки перехватывают пути обнаружения.

- Ищут руткиты по расхождениям источников и инвариантам ядра.


## Шаг 9: user-mode руткиты и их место

Не все руткиты работают в ядре. **User-mode** руткиты перехватывают библиотечные вызовы: в Linux — через `LD_PRELOAD` (подмена `readdir`/`open`), в Windows — через хуки API (`IAT`/inline) в конкретном процессе или глобально через `AppInit_DLLs`. Они проще в реализации, но и проще обнаруживаются: достаточно сравнить вывод инструмента, загруженного с чистым окружением, и без него. При реверсе важно сначала определить уровень (user/kernel): от этого зависит вся методология. User-mode руткит виден как подозрительная библиотека в списке загруженных или как хук в памяти процесса.

## Шаг 10: полный прогон разбора модуля

Разберём учебный `rootkit.ko` по шагам. (1) `modinfo` даёт описание и автора. (2) `strings` показывает имена скрываемых процессов и пути. (3) `readelf -s`/`objdump -d` — символы и код: ищем вызовы `list_del`, `kallsyms_lookup_name`, `set_memory_rw`. (4) Находим в дизассемблере функцию, которая получает `task_struct` по имени и вырезает его из списка — это DKOM. (5) Смотрим, какие функции ядра перехвачены (ftrace/kprobe). (6) Строим поведенческую модель: что именно скрывается. Этот конвейер применим и к Windows-драйверам, только API другие (`PsLookupProcessByProcessId`, `ActiveProcessLinks`).

## Шаг 11: почему руткиты всё ещё актуальны

Казалось бы, современные EDR и PatchGuard (Windows) должны закрыть тему. Но руткиты эволюционировали: вместо патчинга ядра они используют легитимные механизмы (eBPF, ftrace, callbacks), а на Windows обходят PatchGuard через гипервизоры и UEFI. Буткиты (BlackLotus) живут в прошивке и переживают переустановку ОС. Поэтому навык разбора ядерного кода остаётся востребованным: защита требует понимания, как именно прячется угроза. В реверсе это одна из самых сложных, но и самых ценных областей.

## Шаг 12: инструменты для реверса ядерного кода

Помимо дизассемблера, для ядерного кода нужны специализированные средства. `Volatility3` работает с дампами памяти и умеет находить скрытые процессы/модули, сравнивая списки и сканируя память на структуры (плагины `windows.pslist`, `windows.psscan`, `linux.pslist`). `crash` анализирует kdump-дампы Linux с символами ядра. `WinDbg` с ядерной отладкой даёт доступ к структурам Windows. `bpftool`/`ftrace` показывают активные хуки в Linux. Для статики — `IDA`/`Ghidra` с загруженными символами ядра (`System.map`, PDB). Комбинация статики и offline-анализа дампа — самый надёжный путь.
## Практика: находим DKOM-руткит в дампе

Статический реверс модуля — половина дела. Вторая половина — доказать сокрытие по дампу памяти. Возьмём образ ВМ и прогоним `Volatility3`:

```
$ vol -f mem.raw linux.pslist        # список процессов из task_struct
$ vol -f mem.raw linux.psscan        # скан памяти на структуры процессов
$ vol -f mem.raw linux.check_modules # сравнение с /proc/modules
```

Сравниваем два первых вывода: если PID есть в `psscan`, но отсутствует в `pslist`, его `task_struct` **вырезан из списка** — классический признак DKOM. Для модулей `check_modules` сверяет загруженные модули с тем, что «видит» ядро; расхождение — скрытый LKM.

В Windows логика та же: `windows.pslist` (обход по `ActiveProcessLinks`) против `windows.psscan` (скан по пулам памяти). Процесс, найденный только сканом, скрыт правкой `EPROCESS`.

Важно: `pslist`-плагины доверяют структурам ядра, а `psscan` сканирует сырую память — поэтому расхождение и есть сигнал. Никогда не полагайся на один источник: руткит обманывает именно «официальный» путь.

## Сравнение механизмов сокрытия

| Механизм | Уровень | Что правит | Обнаружение |
|---|---|---|---|
| DKOM (Linux) | kernel | список `task_struct` | `pslist` vs `psscan` |
| DKOM (Windows) | kernel | `EPROCESS.ActiveProcessLinks` | `pslist` vs `psscan` |
| SSDT-патч | kernel | `NtQuerySystemInformation` | сверка адресов SSDT с ядром |
| `sys_call_table` | kernel | `sys_getdents` | сравнение с `System.map` |
| ftrace/kprobe hook | kernel | трассировочные точки | `enabled_functions`, `kprobes` |
| eBPF-программа | kernel | аргументы syscall | `bpftool prog list` |
| LD_PRELOAD | user | `readdir`/`open` | чистый env vs заражённый |
| IAT/inline-хук | user | API в процессе | дамп памяти процесса |

Общий принцип обнаружения один: **сравнивать независимые источники истины**. Чем больше слоёв руткит должен обмануть, тем вероятнее он где-то «проколется».

## Куда дальше

Ядерный реверс освоен на примере руткитов. Рядом — драйверы и их IRP-обработчики, а также буткиты в UEFI. Пока главное: **руткит живёт в ядре и искажает то, что видят инструменты, поэтому искать его нужно по расхождениям**.

## Где пригодится

- **Kernel security:** анализ руткитов и драйверов.

- **Malware analysis:** ядерные импланты APT.

- **EDR research:** понимание механизмов сокрытия.
