## Вопрос, с которого всё начинается

Ты умеешь помечать входные данные «грязными» и смотреть, куда они распространяются в **пользовательском** процессе. Но современный malware (rootkit) работает в **ядре**: он ставит хук на системный вызов, перехватывает сетевой стек, прячет файлы. Из userland ты этого не видишь — данные «утекают» в ядро, и обычный taint-анализ там обрывается.

Чтобы проследить данные от ввода через ядро и обратно, нужен **whole-system taint** — taint-анализ всей системы. Разберём его модель и то, почему для него часто поднимают **гипервизор**.

## Наш пример

Начнём с userland, чтобы понять механику. Возьмём `taint` с функцией `process`, которая сворачивает четыре байта входа в число:

```c
int process(const char *in) {
    unsigned int k = 0;
    for (int i = 0; i < 4; i++)
        k = (k << 5) ^ (unsigned char)in[i];
    if (k == 0x218024)     /* sink */
        return 1;
    return 0;
}
```

Мы пометим входные байты «грязными» и посмотрим, дойдут ли метки до сравнения — это **sink** (точка-приёмник).

## Шаг 1: модель DTA — sources, sinks, shadow

Dynamic Taint Analysis формализуется четырьмя понятиями:

| Понятие | Что это | Примеры |
|---|---|---|
| Source | откуда приходят «грязные» данные | сеть, диск, аргументы syscall, ввод |
| Sink | опасные операции-приёмники | write, execve, jmp, запись в ФС/реестр |
| Shadow memory | карта «загрязнённости» | бит/байт на каждый байт данных |
| Propagation | правила распространения | арифметика, копирование, через struct |

Правила распространения задаются вручную: результат сложения «грязный», если грязный хотя бы один операнд; адрес памяти «грязный», если грязный указатель. Качество анализа зависит от точности этих правил.

## Шаг 2: реальный мини-движок taint

Соберём движок на `unicorn` + `capstone`: помечаем входной буфер и на каждой инструкции обновляем метки регистров и памяти. Вот реальный вывод для входа `ABCD`:

```
[prop]  0x40102d: movzx  eax, byte ptr [rax]   -> rax помечен ['in[0]']
[prop]  0x40101e: mov    ecx, eax              -> rcx помечен ['in[0]']
[prop]  0x40102d: movzx  eax, byte ptr [rax]   -> rax помечен ['in[1]']
[prop]  0x40102d: movzx  eax, byte ptr [rax]   -> rax помечен ['in[2]']
[prop]  0x40102d: movzx  eax, byte ptr [rax]   -> rax помечен ['in[3]']
[SINK] 0x401042: cmp dword ptr [rbp - 4], 0x218024
       сравниваемое значение помечено: ['in[0]', 'in[1]', 'in[2]', 'in[3]']
```

Видно: метки от входных байтов дошли до регистра и до ячейки стека, а затем «всплыли» в sink-сравнении. Именно так taint отвечает на вопрос «какие данные влияют на эту операцию». Но это — **userland**: движок эмулирует код одного процесса. Как только данные уходят в системный вызов, эмуляция заканчивается.

## Шаг 3: почему userland taint не видит ядро

Когда процесс делает `read()` или `recv()`, данные попадают в буфер **через ядро**: сетевой стек → буфер сокета → копирование в память процесса. Userland-инструментация видит только результат — уже готовый буфер. Всё, что malware делает **внутри** ядра (хуки, перехват, сокрытие), остаётся «чёрным ящиком».

Решение — **hypervisor-based** инструментация: гипервизор работает на уровне **ring -1**, выше гостевого ядра, и наблюдает за ним, **не изменяя** его код. Гость не может обнаружить модификацию, потому что её нет — перехват идёт снаружи.

```
Guest OS + malware
        |
   Hypervisor (инструментация, shadow memory, taint propagation)
        |
   Host (сбор трассы, анализ)
```

Исторические инструменты этого класса: **Panoramix** (whole-system DTA через модифицированный QEMU) и **TEMU** из платформы BitBlaze. Сборка концептуально выглядит так:

```bash
# Panoramix/TEMU собираются как модифицированный QEMU
git clone <repo>/panoramix && ./configure --target-list=x86_64-softmmu && make
./qemu-system-x86_64 -m 2048 -hda guest.img -net nic -net user
```

Внутри хост-инструментатора помечает sources (сетевые пакеты) и наблюдает sinks (запись в `/etc`, `execve`, изменения реестра).

## Шаг 4: практический пайплайн анализа C2

```
1) Пометить входящий C2-трафик как «грязный».
2) Проследить: пакет -> TCP/IP стек -> буфер сокета -> read() -> память процесса.
3) Отслеживать, куда «грязные» данные попадают дальше (sink):
   - запись в /etc, ~/.ssh, автозагрузку;
   - execve с «грязным» аргументом;
   - изменение реестра/сервисов.
4) По достигнутым sinks восстановить логику malware на уровне ядра.
5) Сопоставить с сетевыми событиями (кто/когда/что).
```

Дополняют картину инструменты анализа памяти (Volatility) и аппаратная трассировка (Intel PT) — они коррелируют поток управления с данными.

## Ограничения

- **Оверхед**: whole-system taint тяжёл (инструментация всей системы замедляет её на порядки). Ограничивайте sources (только сеть) и sinks (только ФС).
- **Полнота shadow memory**: для всего ядра она огромна; применяют сегментную shadow-карту.
- **Детектируемость**: продвинутый malware замечает тайминговые аномалии; инструментацию минимизируют.
- **Специфичность**: Panoramix/TEMU старые и требуют адаптации под современные ядра.
- **Ложные срабатывания**: слишком широкий taint делает «грязным» всё подряд, и полезный сигнал теряется — уточняйте sources и правила распространения.

## Связь с аппаратной трассировкой

Whole-system taint даёт «что с чем связано», но сам по себе тяжёл. Его часто дополняют **Intel PT**: аппаратная трассировка записывает поток управления всей системы с минимальным оверхедом, а taint-анализ — зависимости данных. Комбинация PT и дампов памяти позволяет восстановить, какие данные влияли на решения, не инструментируя каждую инструкцию. Ещё один полезный спутник — Volatility: он восстанавливает структуры ядра из дампа памяти и помогает сопоставить taint-метки с конкретными объектами (процессами, сокетами, модулями).

## Что мы теперь знаем

- **Whole-system taint** отслеживает данные от ввода через ядро и обратно; userland-taint этого не умеет.
- DTA строится из **sources**, **sinks**, **shadow memory** и правил **propagation**.
- Для анализа ядра инструментируют **гипервизор** (ring -1): гость не видит изменений, потому что их нет.
- Исторические инструменты — **Panoramix** и **TEMU**; дополняют их Volatility и Intel PT.
- Главная цена whole-system taint — огромный оверхед и сложность настройки.

## Куда дальше

Мы разобрали taint от userland до ядра. В следующем уроке вернёмся к **аппаратной трассировке** — Intel PT и ARM ETM, которые дают поток управления всей системы с минимальным оверхедом и без модификации кода. А пока главное запомни: userland-taint обрывается на границе ядра, а чтобы пройти её, инструментируют гипервизор.
