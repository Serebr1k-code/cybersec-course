CTF-задачи по реверсу решаются не «случайным перебором инструментов», а системно: определить тип
задачи, применить соответствующий рецепт, проверить гипотезу, при неудаче — перейти к следующему
рецепту. Этот урок — компиляция методик из всех предыдущих тем в практический чек-лист, который
экономит время на соревнованиях и делает анализ воспроизводимым.

## Классификация CTF-задач

Первым делом определите тип:

- **Crackme/Keygenme**: программа просит пароль/серийник. Цель — найти или сгенерировать.
- **Flag checker**: вводится флаг, программа проверяет. Цель — восстановить флаг.
- **Anti-debug**: проверки мешают отладке. Цель — обойти и найти флаг.
- **Packed/Obfuscated**: код скрыт (UPX, VM, MBA). Цель — распаковать/деобфусцировать.
- **VM-based**: собственная виртуальная машина. Цель — понять байткод VM.
- **Crypto**: проверка использует криптографию. Цель — восстановить ключ/алгоритм.
- **Custom format**: нестандартный контейнер. Цель — распарсить.
- **Emulation**: бинарник для другой архитектуры (ARM/MIPS). Цель — запустить/эмулировать.

Тип диктует инструмент. Неправильная классификация — главная потеря времени.

## Чек-лист триажа

Быстрая последовательность (5–10 минут):

1. **`file`** — что это (ELF/PE/Mach-O/.pyc/.NET/Java/архив).
2. **`strings -a -n 6`** — ищите `flag`, `CTF{`, подсказки, URL.
3. **`checksec`** — защиты (RELRO, NX, PIE, canary) — важно для pwn-аспектов.
4. **Запуск** — что программа делает, что просит.
5. **`rabin2 -I` / DIE** — упакована ли, обфусцирована ли, какая архитектура.
6. **Дизассемблер** — Ghidra/IDA/r2, найти `main` и проверку.
7. **Строки вокруг проверки** — `"correct"`, `"wrong"`, сравнения.

Если на шаге 2–3 виден флаг/пароль — задача решена. Иначе переходим к рецептам.

## Рецепты по типам

**Crackme с `strcmp`**: breakpoint на `strcmp`, посмотреть аргументы — пароль виден. Либо декомпилировать
и найти строку сравнения.

**Flag checker с посимвольной проверкой**: символическое исполнение (angr) или трассировка (Triton),
либо перебор по одному байту.

**Anti-debug**: запустить под ScyllaHide/патчами, найти проверки (`ptrace`, `IsDebuggerPresent`),
обойти. Или статически: найти ветку `fail` и посмотреть, что ведёт к `success`.

**Packed (UPX)**: `upx -d`. Кастомный — найти OEP через watchpoint, снять дамп.

**VM-based**: найти диспетчер VM, восстановить опкоды, дизассемблировать байткод. Иногда проще
эмулировать VM (написать интерпретатор байткода в Python).

**Crypto**: определить алгоритм (константы AES/S-box, RC4), восстановить ключ, расшифровать.
Часто ключ в коде или выводится из ввода.

**Custom format**: распарсить структуру (`binwalk`, hex-анализ), написать парсер на Python.

**Другая архитектура**: Qiling/Unicorn для эмуляции или `qemu-user` для запуска.

## Практический разбор

Задача: `chall` — ELF, просит пароль. Триаж:

```
$ file chall
chall: ELF 64-bit LSB pie executable, x86-64, dynamically linked, not stripped
$ strings -a -n 6 chall | grep -iE "flag|correct|wrong|pass"
Enter password:
Correct!
Wrong!
```

Открываем в Ghidra, находим `main`:

```c
int main() {
    char buf[64];
    printf("Enter password: ");
    scanf("%63s", buf);
    if (check(buf)) puts("Correct!");
    else puts("Wrong!");
}
```

Смотрим `check`:

```c
bool check(char *s) {
    for (int i = 0; i < 8; i++)
        if ((s[i] ^ 0x42) != expected[i]) return false;
    return true;
}
```

`expected` — массив в `.rodata`. Извлекаем его и восстанавливаем пароль:

```python
expected = bytes.fromhex("2a0f3e...")
print("".join(chr(b ^ 0x42) for b in expected))
```

Задача решена за пару минут благодаря методичному триажу.

## Автоматизация

Для повторяющихся задач пишите скрипты. Полезные шаблоны:

- **Keygen из `strcmp`**: скрипт gdb/r2pipe, который логирует аргументы `strcmp`.
- **Брутфорс посимвольной проверки**: angr или эмуляция с перебором.
- **Извлечение констант**: скрипт, читающий `.rodata` по адресу из дизассемблера.
- **Демультиплексор VM**: интерпретатор байткода VM в Python.

Храните скрипты как артефакты (см. методику «одно оружие, много выстрелов»): в следующий раз
используйте готовый.

## Разбор: anti-debug задача

Задача запускается, но под отладчиком сразу завершается или выдаёт «Wrong». Триаж показывает строки
`debugger detected`. План:

1. Запустить под ScyllaHide (Windows) или с `LD_PRELOAD`-хуком `ptrace` (Linux).
2. Найти проверку: `strings` → xref → функция. Часто это `ptrace(PTRACE_TRACEME)` или
   `IsDebuggerPresent`.
3. Обойти: breakpoint на проверке, `set $rax=0` (или `eax=0`), continue — без патча кода.
4. Найти ветку `success` и посмотреть, что требуется (пароль/флаг).

Если проверок несколько, обходите по одной, наблюдая, какая блокирует. Динамика (трассировка через
strace/ltrace) быстро показывает, какие системные вызовы совершаются.

## Разбор: VM-задача

Задача содержит собственный интерпретатор. Триаж: в `main` виден большой цикл с `switch`/таблицей
переходов и массив «байткода». План:

1. Определить диспетчер: где читается опкод и куда идёт переход.
2. Восстановить таблицу опкодов: сопоставить каждый `case` с операцией (push, pop, add, xor, cmp,
   jmp, call).
3. Дизассемблировать байткод: написать интерпретатор на Python, который читает байткод и печатает
   операции (или сразу вычисляет).
4. Понять проверку: обычно VM вычисляет функцию от ввода и сравнивает с константой. Восстанавливаем
   алгоритм и пишем keygen.

Иногда проще трассировать VM в отладчике и логировать последовательность операций для известного
ввода, чем писать интерпретатор. Комбинация: статический разбор диспетчера + динамическая трасса.

## Разбор: packed-задача

Триаж: DIE показывает `UPX` или «unknown packer». План:

1. UPX — `upx -d chall`. Готово.
2. Кастомный — найти OEP через watchpoint на запись в `.text` (см. урок про распаковку), снять дамп.
3. Открыть распакованный образ в дизассемблере, найти `main`/проверку.
4. Если есть анти-дамп — снять дамп до его срабатывания.

Помните: после распаковки строки и код становятся читаемыми, и задача сводится к обычному crackme.

## Тайм-менеджмент на CTF

Практические правила:

- **Триаж за 5 минут**: определите тип и примерную сложность. Если задача «не ваша» (например, не
  знаете VM) — отложите и возьмите другую.
- **Тайм-бокс 20–30 минут** на подход; если прогресса нет — смените рецепт или задачу.
- **Параллельность**: запускайте длительные операции (angr, брутфорс, распаковка) в фоне и решайте
  другие задачи.
- **Документируйте**: записывайте адреса, пароли, найденные строки — не полагайтесь на память.
- **Проверяйте флаг**: формат `CTF{...}`; не гонитесь за «похожим на флаг» без проверки.

Эти правила не про реверс, а про соревнование: время ограничено, и системность важнее «глубины» в
одной задаче.

## Разбор: crypto-задача

Задача содержит проверку на основе криптографии. Триаж: строки/импорты намекают на алгоритм
(`AES`, `RC4`, `MD5`, константы S-box). План:

1. Определить алгоритм: по константам (AES S-box, RC4 init), по именам функций, по структуре.
2. Найти ключ: часто он в коде, выводится из ввода или является хешем от строки.
3. Воспроизвести алгоритм в Python (используйте `pycryptodome`), расшифровать/сравнить.
4. Если ключ неизвестен, а проверка обратима — решить символически (angr/Z3).

Важно: не пишите крипто с нуля — используйте библиотеки. Для самодельной криптографии
восстанавливайте раунды по коду. Часто «крипто» оказывается XOR/ROT с нестандартными параметрами.

## Разбор: custom format

Задача даёт файл неизвестного формата (или программа его читает). Триаж: `file`, `binwalk`,
hex-редактор. План:

1. Определить магию/заголовок: сравнить с известными форматами (binwalk подскажет).
2. Понять структуру: размеры полей, смещения, таблицы.
3. Написать парсер на Python (по образцу или через Kaitai Struct).
4. Найти «полезную» часть (флаг/ключ) и извлечь.

Kaitai Struct позволяет описать формат декларативно и сгенерировать парсер. Для простых форматов
хватает ручного разбора по смещениям.

## Подводные камни

Первое: не начинайте с самого сложного инструмента — триаж решает половину задач. Второе: не
игнорируйте `strings` и ресурсы. Третье: не патчите код, если проверка целостности — используйте
регистры. Четвёртое: не бойтесь другой архитектуры — эмуляция решает. Пятое: записывайте неудачные
подходы, чтобы не повторять. Шестое: проверяйте флаг на формат (`CTF{...}`), чтобы не гнаться за
ложным результатом. Седьмое: тайм-бокс — если рецепт не работает 15 минут, переключайтесь. Восьмое: читайте подсказки
в задаче (название, описание) — они часто намекают на технику. Девятое: не забывайте про
комбинирование методов — статический анализ плюс динамика плюс символика решают то, что по
отдельности не поддаётся. Десятое: ведите заметки по ходу решения — это ускоряет возврат к задаче
после переключения и помогает команде. Одиннадцатое: сохраняйте промежуточные артефакты (дамy,
скрипты) — они могут пригодиться в связанных задачах.
