## Вопрос, с которого всё начинается

Классический DBI (Intel PIN, DynamoRIO) запускает программу **под своим движком**: ты отдаёшь ему
бинарь, он берёт исполнение на себя. Но что если инструментировать нужно **уже запущенный процесс** —
например, мобильное приложение на телефоне, куда свой движок не встроишь? Или код под ARM/AArch64,
для которого PIN недоступен?

Ответ — **QBDI** (QuarkslaB Dynamic Binary Instrumentation): библиотека, которую можно встроить прямо
в процесс. Разберём её модель и соберём работающий аналог на доступных инструментах.

## Наш пример

Крэкми с XOR-проверкой:

```c
int check(const char *s){
    if (mylen(s) != 6) return 0;
    for (int i=0;i<6;i++)
        if (((unsigned char)s[i] ^ key[i]) != want[i]) return 0;
    return 1;
}
```

```
$ ./crackme nvumom
ACCESS GRANTED
```

Задача на этот раз — инструментировать **обращения к памяти**: увидеть каждое чтение и запись с
адресом, размером и значением. Именно для этого QBDI даёт отдельные колбэки.

## Шаг 1: чем QBDI отличается от PIN

QBDI — open-source (Apache 2.0) проект Quarkslab. Два отличия принципиальны:

- **In-process:** QBDI встраивается в сам процесс как библиотека (или подключается через Frida),
  а не запускает программу заново под своим рантаймом. Это позволяет инструментировать **живой**
  процесс.
- **Мультиархитектурность:** x86-64, x86, ARM и AArch64. Для Android/iOS и embedded это часто
  единственный практичный вариант.

Внутри QBDI исполняет код в **песочнице**: транслирует базовые блоки и выполняет их, вызывая твои
колбэки на интересующих событиях. Это тот же принцип «translate + instrument», что у PIN, но с
другой моделью встраивания.

## Шаг 2: архитектура — VM, колбэки, VMState

Три понятия QBDI:

- **VM** — виртуальная машина, которая исполняет инструментируемый код в песочнице.
- **Callbacks** — обработчики событий: на инструкцию, на **обращение к памяти**, на вызов/возврат.
  Ты регистрируешь только нужные.
- **VMState** — снимок состояния: регистры (включая `rip`, `rsp`) и доступ к памяти в момент
  колбэка.

Модель памяти-колбэков — сильная сторона QBDI: не нужно вручную разбирать инструкции, чтобы понять,
что было прочитано или записано, — движок сообщает адрес, размер и значение.

## Шаг 3: тот же принцип без QBDI

QBDI в этой среде не установлен, но его модель точно воспроизводится на **unicorn**: хуки
`UC_HOOK_MEM_READ` и `UC_HOOK_MEM_WRITE` — это и есть колбэки на обращения к памяти, а роль VMState
играет снимок регистров. Инструментируем `check` на верном пароле:

```python
def rd(mu, acc, addr, size, val, ud): log("READ ", addr, size, val)
def wr(mu, acc, addr, size, val, ud): log("WRITE", addr, size, val)
mu.hook_add(UC_HOOK_MEM_READ, rd)
mu.hook_add(UC_HOOK_MEM_WRITE, wr)
```

Покажем события, относящиеся к входному буферу и к стеку функции:

```
== QBDI-style memory callbacks: 119 events  (reads=94 writes=25) ==
  [READ ] addr=0x500000 size=1 val=0x0   <- 0x401065 movzx eax, byte ptr [rax]
  [READ ] addr=0x500001 size=1 val=0x0   <- 0x401065 movzx eax, byte ptr [rax]
  ...
  [WRITE] addr=0x5feff4 size=4 val=0x0   <- 0x401095 mov dword ptr [rbp - 4], 0
  [READ ] addr=0x500000 size=1 val=0x0   <- 0x4010ab movzx eax, byte ptr [rax]
  [WRITE] addr=0x5feff3 size=1 val=0x7f  <- 0x4010c2 mov byte ptr [rbp - 5], al
  [READ ] addr=0x5feff3 size=1 val=0x0   <- 0x4010d5 cmp byte ptr [rbp - 5], al
  ...
```

Всего **119** событий: 94 чтения и 25 записей. Каждое снабжено адресом, размером, значением и
инструкцией, которая его вызвала — ровно то, что даёт колбэк QBDI.

## Шаг 4: что видно в трассе памяти

Присмотримся к записям в стек по адресу `0x5feff3` — это временная переменная `t` из цикла. За шесть
итераций туда записались значения:

```
0x7f  0x54  0x46  0x29  0x3a  0x0b
```

Это в точности таблица `want[]` из нашего кода! Логично: при верном пароле `t = s[i] ^ key[i]` равно
`want[i]`, и каждая итерация сохраняет его в стек перед сравнением. То есть **одна трасса обращений к
памяти уже раскрыла целевую таблицу** — без чтения исходников и без дизассемблера. Вот зачем
памяти-колбэки так ценны.

## Шаг 5: интеграция с Frida

Отдельная сила QBDI — работа через **Frida**, фреймворк динамической инструментации. Модуль
`frida-qbdi` позволяет подключиться к **уже запущенному** процессу (в том числе на Android/iOS) и
навесить QBDI-колбэки: трассировку, памяти-события, покрытие. Это ключевой сценарий для мобильного
реверса, где нельзя просто «запустить бинарь под PIN».

## Шаг 6: ограничения

- **Оверхед** от JIT-трансляции и колбэков (меньше отладчика, но заметен).
- **Сложность API** — модель VMState и колбэков требует аккуратной работы с регистрами и памятью.
- **Не отладчик** — нет интерактивных точек останова; это библиотека для программной
  инструментации.
- **Обнаружимость** — как и любой DBI, меняет исполнение, что видно анти-анализу.

## Шаг 7: как поставить и с чего начать

QBDI распространяется как prebuilt-библиотеки и собирается из исходников:

```bash
git clone https://github.com/quarkslab/QBDI.git
cd QBDI && mkdir build && cd build
cmake .. -DCMAKE_BUILD_TYPE=Release -DQBDI_PLATFORM=linux -DQBDI_ARCH=X86_64
make -j$(nproc)          # на выходе build/libQBDI.so
```

Для работы через Frida ставят модуль `frida-qbdi` (`pip install frida-qbdi`), а готовые примеры
(`trace`, `instr`, `memaccess`) лежат в каталоге `examples/` репозитория. Полезно держать в голове
место QBDI среди инструментов:

| Инструмент | Модель | Архитектуры | Живой процесс |
|-----------|--------|-------------|---------------|
| Intel PIN | out-of-process | x86/x86-64 | нет |
| DynamoRIO | out-of-process | x86/x86-64/ARM | частично |
| QBDI | in-process | x86/x86-64/ARM/AArch64 | да (через Frida) |

Отсюда простое правило выбора: если цель — x86 и можно перезапустить программу, хватит PIN; если
нужен живой процесс или ARM — бери QBDI.

## Что мы теперь знаем

- **QBDI** — in-process DBI: встраивается в процесс и поддерживает ARM/AArch64.
- Модель: **VM** исполняет код в песочнице, **колбэки** ловят события, **VMState** даёт снимок.
- Колбэки на память дают адрес, размер и значение каждого чтения/записи.
- Та же модель воспроизводится хуками `UC_HOOK_MEM_READ/WRITE` в unicorn.
- Интеграция с Frida позволяет инструментировать уже запущенный процесс (мобильный реверс).

## Куда дальше

QBDI даёт готовые колбэки на события, но не отвечает на вопрос «откуда пришло это значение». Следующий
шаг — соединить DBI с **символьным исполнением и taint-анализом**: строить для каждого регистра
символьное выражение. Об этом — урок про **Triton**. А пока запомни: QBDI — это DBI, который живёт
внутри процесса и особенно полезен там, где PIN не работает (ARM, мобильные, живой процесс).

## Где пригодится

- **CTF Reversing:** трассировка памяти и восстановление таблиц/констант.
- **Mobile/embedded:** инструментация ARM/AArch64-кода, где PIN недоступен.
- **Malware analysis:** наблюдение за живым процессом через Frida.
- **Tooling:** основа собственных in-process инструментов анализа.
