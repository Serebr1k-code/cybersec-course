## Вопрос, с которого всё начинается

Ты сдампил macOS-бинарник из памяти, но при запуске он падает: система отказывается его исполнять из-за подписи. Или ты анализируешь приложение и видишь, что какие-то API оно вызывает, а какие-то — нет, будто «не имеет права». Почему?

## Наш пример

Возьмём системный бинарник `/bin/ls` и посмотрим его подпись:

```bash
$ codesign -dvvv /bin/ls
Executable=/bin/ls
Identifier=com.apple.ls
CodeDirectory v=20400 size=... flags=0x0(none) hashes=...
Signature size=...
Authority=Software Signing
Authority=Apple Code Signing Certification Authority
Authority=Apple Root CA
```

Здесь `Authority` — цепочка сертификатов, `CodeDirectory` — структура с хешами страниц кода. Разберём, что всё это значит и зачем нужно реверсеру.

## Шаг 1: что такое подпись кода

**Code signing** — механизм, при котором подпись криптографически связывает бинарник с идентификатором разработчика. Система проверяет подпись при запуске и отказывается запускать изменённый код. Внутри подписи лежит **CodeDirectory** — список хешей постранично (обычно по 4 КБ). При изменении байта кода хеш страницы не сойдётся, и проверка провалится. Для реверсера это означает: просто пропатчить байты нельзя — система это заметит. Нужно либо переподписать (для анализа), либо отключить проверку на тестовой машине.

## Шаг 2: entitlements

**Entitlements** — список разрешений, подписанных вместе с бинарником. Например, приложение может иметь право на сетевые соединения, доступ к камере или отлаживание других процессов. Посмотреть их:

```bash
$ codesign -d --entitlements - /bin/ls
[Dict]
    com.apple.security.cs.allow-jit => true
```

Некоторые entitlements критичны для анализа: `get-task-allow` разрешает отладку, `allow-unsigned-executable-memory` разрешает исполняемую память (JIT). Без нужного entitlement приложение просто не сможет работать под отладчиком. При реверсе ты смотришь entitlements, чтобы понять, какие возможности заявлены, и чтобы при необходимости подписать копию с нужными правами.

## Шаг 3: hardened runtime

**Hardened runtime** — набор защит для подписанных приложений: запрет на отладку (`ptrace`), на инъекцию библиотек, на запись исполняемой памяти, на чтение чужой памяти. Включается флагом при подписи (`--options runtime`). Многие приложения (и macOS-малварь) его используют. Для анализа это означает: отладчик не прицепится без специальных разрешений (`com.apple.security.get-task-allow`), а `DYLD_INSERT_LIBRARIES` не сработает. Обход — переподписать копию без hardened runtime и с нужными entitlements.

## Шаг 4: проверка при запуске

Проверка подписи — это цепочка: ядро проверяет подпись бинарника, `amfid` (Apple Mobile File Integrity daemon) проверяет подписи и entitlements, `Gatekeeper` проверяет нотаризацию для скачанных приложений. Если подпись недействительна или entitlement отсутствует, запуск блокируется. Понимание этой цепочки важно, потому что от неё зависит, где именно «спотыкается» твой анализ. Часто проще отключить проверку на выделенной тестовой машине, чем бороться с цепочкой.

## Шаг 5: анализ и обход

Для реверса применяют: (1) **переподпись** копии (`codesign -f -s - --entitlements ent.plist app`) с нужными правами; (2) **отключение SIP** на тестовой машине для системных бинарников; (3) **извлечение entitlements** для понимания возможностей; (4) **снятие hardened runtime** для отладки. Также полезно `otool -l` (загрузочные команды), `codesign -d --entitlements`, `spctl` (проверка Gatekeeper). Важно работать на копии и в изолированной среде — модификация системных бинарников может нарушить систему.

## Шаг 6: нотаризация и Gatekeeper

**Notarization** — дополнительный шаг для распространяемых приложений: Apple проверяет бинарник автоматически и выдаёт «тикет». **Gatekeeper** требует нотаризацию для скачанных приложений. Для реверсера это значит: скачанное приложение может не запуститься без обхода Gatekeeper (`xattr -d com.apple.quarantine`), а анализ требует переподписи. При разборе macOS-малвари понимание нотаризации помогает отличить легитимно подписанное приложение от подделки.

## Шаг 7: где это в реальной работе

Реверс Apple-платформ без понимания подписей невозможен: любой шаг (запуск, отладка, инъекция) упирается в них. Этот навык нужен в mobile reversing (iOS), в анализе macOS-малвари, в аудите приложений. Он же объясняет, почему «просто пропатчить байт» на Apple не работает: подпись проверяется постранично. Понимание entitlements — ключ к тому, почему приложение ведёт себя определённым образом.

## Что мы теперь знаем

- Code signing связывает бинарник с разработчиком через постраничные хеши (CodeDirectory).

- Entitlements — подписанные разрешения; без нужного приложение не сделает операцию.

- Hardened runtime запрещает отладку, инъекцию и исполняемую память.

- Для анализа копию переподписывают с нужными правами; Gatekeeper/нотаризация — отдельный слой.


## Шаг 8: разбор entitlements вручную

Entitlements лежат внутри подписи в формате plist. Извлечь их можно не только `codesign`, но и разбором Mach-O: подпись — это LC_CODE_SIGNATURE, а внутри неё блок entitlements. Инструменты `ldid`, `jtool2`, `codesign` показывают их в читаемом виде. Зачем это реверсеру? Entitlements описывают, что приложение *может* делать: доступ к камере, отладке, сетевым сокетам, чтению чужой памяти. Если приложение делает что-то, чего нет в entitlements, оно либо подделано, либо использует другой путь. При анализе малвари отсутствие нужного entitlement при наличии соответствующего кода — сильный сигнал. Также полезно сравнить entitlements официальной версии приложения и подозрительной: различия покажут, что злоумышленник добавил.

## Шаг 9: SIP и почему он важен

**SIP** (System Integrity Protection) защищает системные файлы и процессы от модификации даже root-пользователем. Это значит, что пропатчить системный бинарник на месте нельзя — только копию. Для реверса это важно: ты всегда работаешь с копией, а проверки подписи для системных бинарников проверяются на другой машине (без SIP) или обходятся переподписью. SIP также ограничивает инъекцию в системные процессы. Понимание SIP объясняет, почему на macOS «просто отладить системный бинарник» не выходит и почему нужна отдельная тестовая машина с отключённым SIP.

## Шаг 10: инструменты и практический конвейер

Ключевые инструменты: `codesign` (подпись/проверка/entitlements), `otool`/`jtool2` (загрузочные команды), `spctl` (Gatekeeper), `ldid` (подпись), `class-dump`/`nm` (символы), `Hopper`/`IDA`/`Ghidra` (дизасм), `frida`/`lldb` (динамика). Конвейер анализа: (1) посмотреть подпись и entitlements; (2) извлечь символы и строки; (3) если нужен запуск/отладка — переподписать копию; (4) при необходимости отключить SIP на тестовой машине; (5) разбирать код. Этот порядок экономит время: сразу видно, что приложение может и чего не может.

## Шаг 11: типичные ошибки при анализе Apple-бинарников

Первая ошибка — пытаться пропатчить оригинал на месте: SIP и подпись не дадут, а система может пострадать. Вторая — запускать неизвестный бинарник без переподписи и удивляться отказу: сначала посмотри entitlements и hardened runtime. Третья — забыть про карантин (`com.apple.quarantine`), из-за которого скачанное приложение не запускается даже корректно подписанным. Четвёртая — анализировать dyld-кэш как обычные библиотеки: файлов на диске может не быть, библиотеки лежат внутри кэша. Пятая — игнорировать версию macOS: механизмы защиты меняются между релизами. Всего этого легко избежать, если начинать с проверки подписи и работать на копии в изолированной среде.
