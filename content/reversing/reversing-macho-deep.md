## Вопрос, с которого всё начинается

Мы разобрали ELF и знаем: файл начинается с заголовка, дальше идут таблицы, описывающие содержимое. Но тот же код, собранный под macOS или iPhone, лежит в файле другого формата — **Mach-O**. На CTF по iOS/macOS, при разборе мобильной малвари или чужого приложения без исходников ты упрёшься именно в него. `readelf` такой файл не понимает. С чего тогда начать?

## Наш пример

Возьмём настоящий Mach-O — файл `macho_demo`, собранный под macOS:

```bash
$ file macho_demo
macho_demo: Mach-O 64-bit x86_64 executable, flags:<NOUNDEFS|DYLDLINK|TWOLEVEL|PIE>
```

Первое слово — формат. Дальше «64-bit x86_64» — разрядность и архитектура, «executable» — это готовая программа (а не библиотека), а `PIE` — грузится по случайному адресу, как мы видели у ELF. Тот же принцип «паспорт файла», только имя другое.

Теперь посмотрим первые байты:

```bash
$ xxd macho_demo | head -1
00000000: cffa edfe 0700 0001 0300 0080 0200 0000  ................
```

Первые четыре байта — `cf fa ed fe`. Это **магия** Mach-O: если прочитать их как число little-endian, получится `0xfeedfacf` — узнаваемое «feedface». Магия ELF была `7f 45 4c 46`, здесь — `feedface`. Дальше разберём эти байты как поля заголовка.

## Шаг 1: заголовок Mach-O

У Mach-O нет отдельной команды вроде `readelf -h`, поэтому прочитаем заголовок в Python — так видно, из чего он состоит:

```python
magic, cputype, cpusub, ftype, ncmds, sizeofcmds, flags, res = struct.unpack_from('<8I', d, 0)
print(f"magic=0x{magic:08x} cputype=0x{cputype:x} ftype={ftype} ncmds={ncmds} sizeofcmds={sizeofcmds} flags=0x{flags:x}")
```

```text
magic=0xfeedfacf cputype=0x1000007 ftype=2 ncmds=13 sizeofcmds=984 flags=0x200085
```

Читаем по полям:

- **magic = 0xfeedfacf** — 64-битный Mach-O little-endian.
- **cputype = 0x1000007** — `CPU_TYPE_X86_64` (старший бит — признак 64 бит).
- **ftype = 2** — `MH_EXECUTE`, обычная программа. У библиотеки было бы `MH_DYLIB` (6).
- **ncmds = 13** — сколько **load-команд** идёт следом (о них сейчас).
- **flags = 0x200085** — среди прочего бит `PIE` из вывода `file`.

Ключевое отличие от ELF здесь — `ncmds`. В ELF таблицы секций и сегментов лежат по известным смещениям, а в Mach-O после заголовка идёт **список команд переменной длины**. Разберём его.

## Шаг 2: load-команды — «инструкции для загрузчика»

**Load-команда** (load command) — это запись переменного размера, которая говорит загрузчику, что делать: «вот сегмент», «вот таблица символов», «точка входа тут». Каждая команда начинается с пары полей `cmd` (тип) и `cmdsize` (её длина), поэтому их можно читать подряд:

```text
  cmd[0]=0x19 (LC_SEGMENT_64) size=72 segname=__PAGEZERO
  cmd[1]=0x19 (LC_SEGMENT_64) size=392 segname=__TEXT
  cmd[2]=0x19 (LC_SEGMENT_64) size=152 segname=__DATA
  cmd[3]=0x19 (LC_SEGMENT_64) size=72 segname=__LINKEDIT
  cmd[4]=0x80000022 (LC_MAIN) size=48
  cmd[5]=0x2 (LC_SYMTAB) size=24
  ...
```

Три самых важных типа:

- **LC_SEGMENT_64 (0x19)** — описывает **сегмент**, крупный блок с правами доступа. Здесь их четыре: `__PAGEZERO`, `__TEXT`, `__DATA`, `__LINKEDIT`.
- **LC_MAIN (0x80000022)** — где лежит точка входа `main`. Это аналог `Entry point` в ELF.
- **LC_SYMTAB (0x2)** — где таблица символов (если бинарник не stripped).

Мы уже знаем из ELF, что такое сегменты и зачем они — карта памяти для загрузчика. В Mach-O их имена начинаются с двойного подчёркивания, и это важно запомнить.

## Шаг 3: сегменты __TEXT и __DATA

У Mach-O вместо `.text` и `.data` — сегменты с говорящими именами. Разберём два главных:

- **__TEXT** — код и константы только для чтения (права `r-x`). Здесь живут сами инструкции и строки-литералы.
- **__DATA** — изменяемые данные (права `rw-`): глобальные переменные, которые меняются во время работы.
- **__PAGEZERO** — «дырка» по адресу 0, чтобы разыменование нулевого указателя сразу падало (защита от NULL-deref).
- **__LINKEDIT** — служебные таблицы символов и подписи, не загружается как код.

Внутри сегмента лежат **секции** — более мелкое деление. Именуются как `сегмент,секция`: например, код — `__TEXT,__text`, строки-константы — `__TEXT,__cstring`. Если открыть `macho_demo` в Ghidra или Hopper, ты увидишь ровно эти имена. Логика «сегмент → секция → данные» та же, что в ELF, просто с префиксом `__`.

Практическое следствие: строки-подсказки ищи в `__TEXT,__cstring`. Наш `macho_demo` содержит литерал `flag{macho_1s_fun}` — он лежит именно там, и его выдаст команда `strings macho_demo`. Если строки зашифрованы или обфусцированы, значит автор прятал логику специально — это уже сигнал усложнённого задания.

## Шаг 4: кто запускает Mach-O — dyld

У ELF программу грузит ядро и `ld-linux.so`. У Mach-O этим занимается **dyld** — динамический загрузчик Apple. Он читает заголовок, идёт по load-командам, размещает сегменты и вызывает точку входа из `LC_MAIN`. Никакого `ld-linux` здесь нет — только dyld.

Практический вывод для реверса: если хочешь перехватить вызовы функций на macOS/iOS, работать надо с dyld — переменная окружения `DYLD_INSERT_LIBRARIES` делает то же, что `LD_PRELOAD` в Linux (подробнее — в уроке про библиотеки). Аналогично, `DYLD_PRINT_LIBRARIES=1` заставляет dyld печатать каждую загруженную библиотеку — простейшая трассировка загрузки.

## Шаг 5: fat-бинарник — несколько Mach-O в одном

Есть нюанс, которого нет у ELF. Программа для macOS может быть **universal (fat)** — одним файлом, внутри которого лежит несколько Mach-O, по одному на каждую архитектуру. Первые байты такого файла — `ca fe ba be` (магия `0xcafebabe`), а не `feedface`. Дальше идёт маленькая таблица: «тут Mach-O для x86_64, а вот тут — для arm64». Система выбирает нужный и запускает.

Для реверса это значит: если `file` показывает «universal binary with 2 architectures», сначала надо вырезать нужную архитектуру — утилитой `lipo -thin arm64 app -output app_arm` или просто отрезав нужный кусок. Иначе дизассемблер запутается в двух заголовках подряд.

## Шаг 6: чем смотреть Mach-O

`readelf` для Mach-O не работает. Базовый набор на macOS:

- **`otool -h app`** — заголовок; **`otool -l app`** — все load-команды (то же, что мы разбирали вручную в Python).
- **`nm app`** — символы; **`nm -m app`** — с типами и секциями.
- **`codesign -dvvv app`** — информация о подписи (важна для iOS-приложений).
- **Hopper** и **Ghidra** — дизассемблеры/декомпиляторы, понимающие Mach-O.

На нашей Linux-машине `otool` нет, поэтому мы и читали load-команды через `struct.unpack` — принцип тот же, что делает `otool -l`. Если увидишь в Ghidra слева дерево `__TEXT`/`__DATA` с секциями — это ровно то, что мы разобрали выше.

## Что мы теперь знаем

- Mach-O опознаётся по магии `feedface`/`feedfacf` (`cffa edfe` в байтах).
- За заголовком идёт список **load-команд** переменной длины, а не таблицы по фиксированным смещениям.
- `LC_SEGMENT_64` описывает сегменты `__TEXT`/`__DATA`, `LC_MAIN` — точку входа.
- Сегменты именуются с `__`, секции — как `__TEXT,__text`.
- Загрузчик Mach-O — **dyld**; `DYLD_INSERT_LIBRARIES` — аналог `LD_PRELOAD`.

## Куда дальше

Мы разобрали Linux (ELF) и macOS (Mach-O). Остался третий популярный формат — Windows **PE** с его DOS-заголовком, RVA и таблицей импортов. Ему посвящён следующий урок. А пока запомни: любой исполняемый формат — это «магия → заголовок → команды/таблицы → данные», и для Mach-O `file` плюс разбор load-команд дают полную картину.

## Где пригодится

- **CTF Reversing (macOS/iOS):** без чтения Mach-O и load-команд не разобрать бинарник Apple-платформы.
- **Malware analysis:** семейство macOS-малвари (например, загрузчики через `DYLD_INSERT_LIBRARIES`) опознаётся по этим полям.
- **Mobile:** iOS-приложения — это Mach-O внутри IPA; понимание сегментов `__TEXT,__cstring` ускоряет поиск строк.
- **Собес:** «чем Mach-O отличается от ELF», «что такое dyld» — частые вопросы по кроссплатформенному реверсу.
