## Вопрос, с которого всё начинается

У тебя есть бинарник, который проверяет ключ. Ты уже умеешь перехватывать вызовы через Frida
(динамически, извне). Но иногда нужно другое: **встроить** свой код в сам бинарник или подсунуть
ему свою реализацию функции так, чтобы он этого не заметил. Это называется **инструментацией** —
добавлением в программу наблюдения или изменения поведения.

Инструментация бывает **динамической** (код подгружается в уже работающий процесс) и **статической**
(мы меняем файл на диске). Разберём оба подхода на одном бинарнике.

## Наш пример

Соберём программу `check`, которая сравнивает введённый ключ с секретом через `strcmp`:

```c
static int check(const char *k){ return strcmp(k, "ELF-SECRET-42") == 0; }
int main(int argc, char **argv){
    puts(check(argv[1]) ? "ACCESS GRANTED" : "denied");
    return 0;
}
```

Обычное поведение:

```
$ ./check ELF-SECRET-42
ACCESS GRANTED
$ ./check bad
denied
```

Наша цель — заставить её выдать «ACCESS GRANTED» с ключом `bad`, сначала динамически, потом
статически.

## Шаг 1: динамическая инструментация через LD_PRELOAD

На Linux есть простой механизм: переменная окружения **`LD_PRELOAD`**. Динамический загрузчик
(`ld.so`) сначала грузит указанную библиотеку, и её символы **перекрывают** символы из libc. Если
мы определим в своей библиотеке функцию `strcmp`, то вызовы `strcmp` из программы попадут в нашу
версию, а не в системную.

Это и есть **перехват** (hooking). Почему это работает: вызовы внешних функций в ELF идут не
напрямую, а через таблицу **PLT** (Procedure Linkage Table) и **GOT** (Global Offset Table). Первый
вызов `strcmp` заставляет загрузчик найти символ по имени и записать его адрес в GOT. При
`LD_PRELOAD` символ с таким именем уже есть в подгруженной библиотеке, поэтому в GOT попадёт
именно он — и все последующие вызовы пойдут в наш код.

Пишем библиотеку:

```c
extern void *stderr;
extern int fprintf(void *, const char *, ...);
int strcmp(const char *a, const char *b){
    fprintf(stderr, "[hook] strcmp(\"%s\", \"%s\")\n", a, b);
    return 0;                       // всегда «строки равны»
}
```

Собираем как разделяемую библиотеку и запускаем программу с ней:

```
$ gcc -shared -fPIC -o hook.so hook.c
$ LD_PRELOAD=./hook.so ./check bad
[hook] strcmp("bad", "ELF-SECRET-42")
ACCESS GRANTED
```

Без хука было `denied`, с хуком — `ACCESS GRANTED`. Заодно в логе виден настоящий секрет
`ELF-SECRET-42`: перехват функции сравнения показывает её аргументы. Так же логируют `malloc`,
`open`, `send` — любой вызов из разделяемой библиотеки.

## Шаг 2: почему LD_PRELOAD не всегда работает

LD_PRELOAD перекрывает только **динамически** связанные функции (вызовы через PLT). Если программа
скомпилирована **статически** (`-static`), libc вшита внутрь, и подсунуть ей свою `strcmp` не
получится. Второе ограничение — встроенные функции: компилятор может заменить `strcmp` на
инлайновое сравнение, и вызова как такового не будет. Третье — защита: некоторые программы
проверяют окружение или сами вызывают `strcmp` через указатель из libc напрямую.

Поэтому динамический перехват хорош для быстрых задач, а когда нужен более надёжный контроль —
идут в **статическую** инструментацию.

## Шаг 3: статическая инструментация — правим файл

Статическая инструментация меняет сам ELF: либо патчем байтов, либо вставкой «трамплинов»
(переписыватели вроде `e9patch`). Начнём с простого патча. Смотрим решающий переход в `main`:

```
$ objdump -d -M intel check | sed -n '/<main>:/,/ret/p'
  401191:  call   401136 <check>
  401196:  test   eax,eax
  401198:  je     4011a1 <main+0x44>      ; если eax==0 -> "denied"
  40119a:  mov    eax,0x402025            ; "ACCESS GRANTED"
  4011a1:  mov    eax,0x402034            ; "denied"
```

Логика простая: `check` вернула 1 при совпадении, `test eax,eax` проверяет ноль, `je` уводит на
`denied`, когда результат нулевой. Инструкция `je` занимает два байта (`74 07` — opcode `je` и
относительное смещение 7). Заменим её на безусловный `jmp` на ту же цель:

```python
import lief
b = lief.parse("check")
addr = 0x401198
print("before:", [hex(x) for x in b.get_content_from_virtual_address(addr, 2)])
b.patch_address(addr, [0xeb, 0x00])      # eb 00 = jmp +0 -> падаем на "ACCESS GRANTED"
b.write("check_patched")
```

Здесь `lief` — библиотека для разбора и правки ELF/PE/Mach-O; `patch_address` меняет байты по
виртуальному адресу. Проверяем результат:

```
$ chmod +x check_patched
$ ./check_patched bad
ACCESS GRANTED
```

Патч работает для **любого** ключа. Обрати внимание: мы поменяли всего два байта, но изменили
поведение всей программы.

## Шаг 4: сравнение подходов

Разница принципиальна:

- **Динамическая** инструментация (`LD_PRELOAD`, Frida, ptrace-DBI) не трогает файл: библиотека
  грузится в память процесса. Плюс — оригинал цел, можно менять хуки на ходу. Минус — не работает
  на статических бинарниках и легко детектируется.
- **Статическая** (патч, `e9patch`) меняет файл на диске. Плюс — работает всегда, в том числе на
  статике. Минус — нужно разбирать ELF, а «трамплины» для сложной инструментации приходится
  аккуратно вписывать, не ломая относительные переходы.

`e9patch`/`e9tool` — это переписыватель ELF, который вставляет в код хуки автоматически и
корректирует все смещения. Им удобно перехватывать вызовы по шаблону:

```
$ e9tool -M 'symbol=strcmp' -P 'my_hook($addr, $arg0, $arg1)' -l hook.so ./check -o ./check.inst
```

Здесь `-M` задаёт, что искать (инструкции, функции, символы), а `-P` — что вставить. Результат —
новый ELF с уже вшитыми хуками.

## Шаг 5: где это применяется

Инструментация — не только для crackme. Ею **трассируют** вызовы (`malloc`, `send`) для понимания
поведения малвари; **собирают данные** о значениях и индексах; **обходят анти-отладку**, подменяя
проверки; **готовят fuzzing-обвязку** (AFL++/libFuzzer через `e9afl`) для автоматического поиска
падений. Понимание, куда именно попадают вызовы и как их перехватить, — базовый навык и для
реверса, и для анализа безопасности.

Для быстрой трассировки без своего кода есть готовые инструменты: `ltrace` показывает вызовы
библиотечных функций с аргументами, а `strace` — системные вызовы. Они не меняют бинарник и удобны
для первого взгляда, но уступают `LD_PRELOAD`/Frida там, где нужно подменять поведение, а не только
наблюдать.

## Что мы теперь знаем

- Инструментация — встраивание наблюдения/изменения в программу; бывает динамической и статической.
- `LD_PRELOAD` перекрывает символы динамически связанных функций: своя `strcmp` перехватывает вызовы.
- Перехват функции сравнения показывает её аргументы — включая секрет.
- Статический патч меняет байты ELF: `je` (`74 07`) → `jmp` (`eb 00`) обходит проверку навсегда.
- `lief` правит ELF программно; `e9patch` вставляет хуки-трамплины автоматически.
- Динамика не трогает файл, но не работает на статике; статика работает всегда, но требует разбора ELF.

## Инструмент: образец crackme6

Объект разбора — бинарь `crackme6`. Это ELF, который сравнивает введённый
пароль со строкой из `.rodata`:

```
$ strings crackme6 | grep -i -E 'pass|open'
0p3n_s3s4m3
$ objdump -d crackme6 | grep -A2 strcmp
```

Строка-пароль лежит в `.rodata` открытым текстом, а сравнение идёт через
`strcmp` (его видно в дизассемблере). Инструментация (LD_PRELOAD или патч)
позволяет подменить сравнение и получить флаг, не подбирая пароль.

## Куда дальше

Мы научились встраивать перехваты динамически и статически. В следующем уроке поднимемся на уровень
данных и разберём **taint-анализ** — как отследить, что входные данные дошли до опасной операции.
А пока главное запомни: `LD_PRELOAD` перекрывает динамические символы, а `lief`/`e9patch` меняют сам
файл — выбирай по тому, слинкован бинарник статически или нет.

- **CTF Reversing:** обход проверок без исходников, логирование сравнений.
- **Malware analysis:** трассировка вызовов, сбор аргументов.
- **Fuzzing:** обвязка для AFL++/libFuzzer через статическую инструментацию.
