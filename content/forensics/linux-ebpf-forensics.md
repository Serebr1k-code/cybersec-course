## Вопрос, с которого всё начинается

Раньше, чтобы влезть в ядро, нужен был модуль. Теперь есть **eBPF** — механизм, который
позволяет запускать код в ядре **без модуля**, легально и штатно. Беда в том, что тем же
механизмом пользуются руткиты: код живёт в ядре, но в списке модулей его нет. Как его
найти?

## Наш пример: программа, которой «не должно быть»

Начнём с того, что вообще загружено.

## Шаг 1: перечисляем eBPF-программы

```
$ sudo bpftool prog list
7: kprobe  name trace_sys_enter  tag a1b2c3d4  gpl
	loaded_at 2026-01-14T03:20:00+0000  uid 0
	...
15: tracepoint  name suspicious_recv  tag deadbeef  gpl
	loaded_at 2026-01-14T03:25:10+0000  uid 0
```

Каждая программа имеет id, тип (`kprobe`, `tracepoint`, `xdp`), имя, тег и — важно —
`loaded_at` и `uid`. Программа `suspicious_recv`, загруженная в 03:25, привлекает
внимание.

## Шаг 2: читаем детали

```
$ sudo bpftool prog show id 15
15: tracepoint  name suspicious_recv  tag deadbeef
	loaded_at 2026-01-14T03:25:10+0000  uid 0
	xlated 1024B  jited 700B  memlock 4096B
	btf_id 42
```

`xlated` — размер «скомпилированного» байткода, `jited` — после JIT. Программа
привязана к трассировочной точке (например, к приёму пакетов). Такой хук может
перехватывать данные в ядре.

## Шаг 3: куда привязана программа

```
$ sudo bpftool link list
5: tracepoint  prog 15  tp 'syscalls/sys_enter_recvfrom'
```

Ссылка (`link`) показывает, к какому событию привязана программа. `sys_enter_recvfrom`
означает перехват приёма данных — идеальное место, чтобы прятать трафик.

## Шаг 4: карты (maps) — где живут данные

eBPF-программы обмениваются данными через **карты**:

```
$ sudo bpftool map list
8: hash  name hidden_pkts  flags 0x0
	key 4B  value 512B  max_entries 1024  memlock 524288B
```

Карта `hidden_pkts` с 1024 записями — вероятно, накопитель «спрятанных» пакетов.

## Шаг 5: кто загрузил

Программа принадлежит какому-то процессу. Ищем в `/proc`:

```
$ for p in /proc/[0-9]*; do grep -l bpf "$p"/maps 2>/dev/null; done
/proc/991/maps
$ tr '\0' ' ' < /proc/991/cmdline
/opt/.hidden/bpf-loader
```

Загрузчик `bpf-loader` из скрытого каталога — вот источник.

## Что мы теперь знаем

- eBPF запускает код в ядре без модуля.
- `bpftool prog list` перечисляет программы с временем и uid.
- `bpftool link list` показывает, к чему привязана программа.
- Карты (maps) хранят данные, которыми обменивается программа.
- Загрузчик можно найти по `/proc/<pid>/maps` и `cmdline`.

## Если не сработало

- Нет bpftool? Читай `/sys/fs/bpf` и `/proc/*/maps`.
- Программа отсоединена, но карта осталась — смотри `bpftool map list`.
- Нужен дамп памяти? Volatility-плагины для eBPF ограничены — фиксируй живой вывод.

## Типы eBPF-программ и точки крепления

eBPF-программа не «витает» в ядре сама по себе — её обязательно к чему-то **крепят**
(attach). Тип программы определяется точкой крепления, и от него зависит, что программа
вообще может видеть:

| Тип | Точка крепления | Что перехватывает |
|-----|-----------------|-------------------|
| `kprobe`/`kretprobe` | вход/выход любой функции ядра | аргументы и返回值 любой внутренней функции |
| `tracepoint` | статические точки трассировки | стабильные события (syscalls, sched) |
| `xdp` | драйвер сетевой карты | пакеты до попадания в стек |
| `tc` (clsact) | трафик-контроль | пакеты на входе/выходе интерфейса |
| `socket_filter` | сокет | пакеты конкретного сокета |
| `lsm` | LSM-хуки безопасности | проверки доступа (мандатный контроль) |
| `cgroup` | cgroup | системные вызовы группы процессов |

Для форензика важно: **`xdp`/`tc`/`socket_filter`** работают с сетью — там прячут
трафик; **`lsm`** может вмешиваться в проверки безопасности; **`kprobe` на `sys_enter_*`**
перехватывает системные вызовы. Тип виден в первой колонке `bpftool prog list` и сразу
сужает круг подозреваемых.

## Карты подробнее: где живут данные

Программа не хранит состояние в «переменных» — между запусками оно теряется. Всё, что
нужно сохранить, кладут в **карты** (maps). Типы карт:

- `hash` — словарь ключ→значение (кэш перехваченных пакетов, таблица подмены);
- `array` — фиксированный массив по индексу;
- `ringbuf`/`perf_event_array` — поток событий в userspace;
- `lru_hash`, `percpu_hash` — варианты с вытеснением и по-ядерными копиями.

Содержимое карты можно прочитать — и это прямой источник улик:

```
$ sudo bpftool map dump id 8
key: 0a 00 00 00  value: 0a 00 00 07 1f 90 00 00 ...
```

Здесь видно ключи (например, IP) и значения (например, адрес перенаправления). Дамп
карты руткита часто **буквально показывает**, какие пакеты он подменял и куда слал.

## Живой анализ: кто на что навешен

Помимо `prog list`, полезны:

```
$ sudo bpftool prog show id 15 --json | jq '.run_time_ns, .run_cnt'
$ sudo bpftool prog tracelog        # лог срабатываний
$ sudo bpftool perf list            # perf-события, на которые навешены проги
```

`run_cnt` — сколько раз программа сработала. Программа-перехватчик на `recvfrom`,
которая сработала миллион раз, — это активный обработчик трафика, а не безобидный
трейсер. Сравни `run_cnt` у штатных программ (обычно небольшие) и у подозрительной.

## Куда eBPF-программы «прилипают» на диске

Программы существуют в памяти ядра, но их можно **закрепить** (pin) в
виртуальной ФС `/sys/fs/bpf/`, чтобы они пережили смерть загрузчика:

```
$ sudo ls -la /sys/fs/bpf/
drwxr-xr-x ... .
drwxr-xr-x ... xdp
-rw------- ... hidden_map
-rw------- ... pinned_prog
```

Файлы в `/sys/fs/bpf` — это не обычные файлы, а ссылки на объекты ядра. Закреплённая
программа продолжит работать даже после `kill` загрузчика — поэтому проверять надо не
только `/proc`, но и `/sys/fs/bpf`. Удалить закреплённую программу можно только явно:
`bpftool prog detach` + `rm /sys/fs/bpf/pinned_prog`.

## Как руткиты прячутся в eBPF

Прятать eBPF-руткит проще, чем модуль: в `lsmod` его нет вообще, и большинство админов
не смотрят в BPF-подсистему. Приёмы:

- **закрепление** программы в `/sys/fs/bpf` и затирание ссылки на загрузчик;
- **отсутствие имени** (`name` пустое) — программы без имени сливаются с шумом;
- **загрузка от имени штатного процесса** — uid 0, но `comm` выглядит безобидно;
- **использование `bpf_probe_write_user`** для подмены данных, возвращаемых userspace-
  инструментам (та же идея, что DKOM, но на уровне eBPF).

Против таких руткитов помогает только **кросс-вью**: сравнить вывод `bpftool` с прямым
чтением `/proc/*/maps`, с картами, с `dmesg` о загрузке BPF и с `run_cnt`. Если что-то
не сходится — есть что-то ещё.

## Сравнение с модульным руткитом

| Признак | Модульный руткит (.ko) | eBPF-руткит |
|---------|------------------------|-------------|
| Виден в `lsmod`/`/proc/modules` | да (пока не вырезан) | нет, по определению |
| Подпись/secure boot | требуется при lockdown | не требуется (ядро штатно) |
| Перезагрузка | переживает | не переживает без pinning |
| Следы загрузки | `dmesg` taint | `bpftool`, `dmesg` bpf-сообщения |
| Инструмент поиска | `lsmod`, `modinfo`, Volatility | `bpftool prog/map/link list` |

## Практический чеклист по eBPF

1. `bpftool prog list` — все программы с типом, именем, `loaded_at`, uid.
2. `bpftool link list` — к чему привязано.
3. `bpftool map list` и `bpftool map dump id N` — что лежит в данных.
4. `ls -la /sys/fs/bpf/` — что закреплено и переживёт перезагрузку.
5. `for p in /proc/[0-9]*; do grep -l bpf "$p"/maps; done` — кто держит BPF-объекты.
6. Сверить `run_cnt` подозрительных программ с ожидаемой активностью.
7. Зафиксировать вывод **до** любого detach — иначе программа исчезнет вместе с уликой.

## Сквозной разбор: перехват пакетов от загрузки до улики

Соберём всё в один сценарий. Инцидент: с хоста «утекает» трафик в обход логирования.

**1. Замечаем аномалию.** В `ss -tunap` слушающих портов нет, но исходящий трафик есть:

```
$ ss -tunap | grep -v LISTEN
tcp ESTAB 0 0 10.0.0.7:51122 203.0.113.9:443 users:(("nginx",pid=2211,fd=7))
```

Соединение принадлежит `nginx`, но идёт на неизвестный внешний адрес.

**2. Смотрим eBPF.** Именно там может сидеть перехватчик:

```
$ sudo bpftool prog list
31: socket_filter  name  tag c0ffee  gpl  run_cnt 482113  run_time_ns 912331
$ sudo bpftool link list
9: socket_filter  prog 31  ifindex 2
```

Программа **без имени** (`name` пустое), типа `socket_filter`, с `run_cnt` 482 тысячи —
она обрабатывает каждый пакет на интерфейсе 2.

**3. Читаем карту.** У программы есть карта, куда она пишет то, что перехватила:

```
$ sudo bpftool map list
12: hash  name  flags 0x0  key 4B  value 8B  max_entries 4096
$ sudo bpftool map dump id 12 | head -4
key: c0 a8 01 09  value: 1f 90 00 00 00 00 00 00
```

Ключ `c0 a8 01 09` = `192.168.1.9`, значение — порт `0x1f90` = 8080. Карта отображает
внутренние адреса на «свой» порт — признак **подмены маршрута**.

**4. Находим загрузчик.** Программа закреплена и переживает перезапуск:

```
$ sudo ls -la /sys/fs/bpf/
-rw------- 1 root root 0 ... /sys/fs/bpf/anon_prog
$ for p in /proc/[0-9]*; do grep -l bpf "$p"/maps 2>/dev/null; done
/proc/1602/maps
$ tr '\0' ' ' < /proc/1602/cmdline; echo
/usr/lib/systemd/systemd-resolved --no-foo
```

Загрузчик маскируется под `systemd-resolved`, но лежит по нештатному пути.

**5. Фиксируем и удаляем.** До удаления сохраняем дампы программ, карт и ссылок:

```
$ sudo bpftool prog dump xlated id 31 > /evidence/prog31.txt
$ sudo bpftool map dump id 12 > /evidence/map12.txt
```

Только после этого `bpftool prog detach` и `rm /sys/fs/bpf/anon_prog`.

## Ограничения eBPF-форензика

- **Не переживает перезагрузку** — без pinning программа исчезает; после reboot улик в
  BPF-подсистеме не остаётся.
- **Volatility ограничен** — плагины для eBPF в дампах памяти неполны; чаще фиксируют
  живой вывод, а не восстанавливают из дампа.
- **Именование не обязательно** — многие программы анонимны, «нет имени» не значит
  «руткит».
- **Штатные программы тоже много работают** — `run_cnt` у Cilium, Falco и системных
  трейсеров большой; сравнивай с эталоном, а не с нулём.
- **Нужны права root/CAP_BPF** — без них `bpftool` не покажет программы, что само по
  себе подсказывает: анализ веди с привилегированной учётки.
