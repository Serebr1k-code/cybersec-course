## Вопрос, с которого всё начинается

На рабочей станции данных нет, но в логах видно, что пользователь копировал что-то
«с диска S:». Диск `S:` — это **общая папка** по SMB. Где реально лежат данные и какие
следы остались?

## Наш пример: диск S:

Смотрим смонтированные ресурсы Windows (через `net use` или артефакты):

```
C:\> net use
New connections will be remembered.
Status   Local   Remote
OK       S:      \\fileserver\share
```

`\\fileserver\share` — это **SMB-шара**: общий каталог на сервере `fileserver`.

## Что такое SMB

**SMB (Server Message Block)**, он же CIFS — протокол доступа к файлам и принтерам в
сетях Windows. Он отдаёт общие папки (shares) и позволяет читать/писать файлы, как будто
они локальные. Версии: SMB1 (устаревший), SMB2, SMB3 (с шифрованием и подписью).

## Шаг 1: перечислить шары

С клиента можно спросить список общих ресурсов:

```
$ smbclient -L //fileserver -N
        Sharename       Type      Comment
        ---------       ----      -------
        share           Disk
        IPC$            IPC       Remote IPC
        ADMIN$          Disk      Remote Admin
```

`share` — обычная шара; `IPC$`/`ADMIN$` — служебные. Для форензика важен список
доступных шар и то, какие из них не требуют пароля.

## Шаг 2: посмотреть содержимое

```
$ smbclient //fileserver/share -N -c 'ls'
  .                                   D        0
  ..                                  D        0
  reports                            D        0
```

Снятие данных: либо копирование по SMB, либо (предпочтительнее) снятие сервера/шары
целиком, если есть доступ к носителю сервера.

## Шаг 3: следы на клиенте

Даже после отключения от шары на клиенте остаётся история:

- **Mapped Drives** в реестре (`HKCU\Network\<letter>`) — какие буквы на какие шары
  указывали;
- **Shellbags** — какие папки шары открывал пользователь;
- **MRU** и ярлыки — последние использованные пути;
- **Prefetch/Jump Lists** — следы работы программ с сетевыми файлами.

Вместе они показывают, **что** именно открывалось и **когда**.

## Шаг 4: следы на сервере

Сервер (или контроллер домена) фиксирует обращения:

- журнал аудита доступа к объектам (Event ID 5140/5145) — открытие шары и файлов;
- SMB-логи и журналы доступа — кто, когда, откуда;
- **SMB signing** (подпись) — если включена, трафик нельзя подделать на лету.

Именно серверные логи доказывают доступ, даже если клиент «почистили».

## Вынос данных по SMB

Типовая картина эксфильтрации: атакующий копирует данные на свою шару или в другую
подсеть. Признаки:

- всплеск чтения с файлового сервера в нетипичное время;
- доступ к шарам с новых учёток/адресов;
- большие объёмы в журналах доступа.

## Альтернативные потоки (ADS)

NTFS поддерживает **альтернативные потоки данных (ADS)** — данные, привязанные к файлу,
но невидимые в обычном листинге. Через SMB их можно передать, и они останутся на сервере.
Обнаруживают их инструментами, читающими потоки (`dir /r`, парсеры MFT).

## Что мы теперь знаем

- SMB-шара — общий каталог на сервере, доступный по сети.
- `smbclient -L` перечисляет шары, в том числе без пароля.
- На клиенте остаются Mapped Drives, Shellbags, MRU, Jump Lists.
- На сервере — журналы доступа (5140/5145) и логи SMB.
- NTFS ADS позволяют спрятать данные внутри файла при передаче по SMB.

## Разбор реального кейса: вынос данных с fileserver

Вернёмся к нашей рабочей станции. Пользователь скопировал каталог `reports` с диска `S:`
на флешку поздно вечером. Нам нужно доказать, что он **читал** данные с сервера, даже если
сам компьютер уже «почищен». Идём по цепочке артефактов от клиента к серверу.

**Шаг A. Что было смонтировано (клиент).** Смотрим реестровый куст пользователя
`NTUSER.DAT` (монтируется через `reged` или разбирается `RegRipper`/`Registry Explorer`):

```
$ reglookup -p /mnt/ntuser/NTUSER.DAT | grep -i network
/Network/Z:/RemotePath,SZ,\\fileserver\share
/Network/Z:/UserName,SZ,CORP\a.petrov
/Network/Z:/ProviderName,SZ,Microsoft Windows Network
/Network/Z:/ConnectionType,DWORD,1
```

Ключ `HKCU\Network\Z:` существует, пока буква диска «помнится», даже если сам диск отключён.
Поле `RemotePath` даёт точное имя шары — это якорь всей дальнейшей корреляции.

**Шаг B. Что открывалось (клиент).** `Shellbags` (`USRCLASS.DAT`, ветка
`Local Settings\Software\Microsoft\Windows\Shell\BagMRU`) хранит пути папок, которые
пользователь открывал в Проводнике, включая сетевые:

```
BagMRU\...\2  Shell item: Network -> \\fileserver
BagMRU\...\3  Shell item: share -> Z:\reports
BagMRU\...\4  Shell item: 2024-q4 -> Z:\reports\2024-q4
```

Ключи Shellbags содержат поля `Modified`/`Accessed` с временем, когда папка попала в список —
это даёт **когда** пользователь заходил в `reports`.

**Шаг C. Что запускалось (клиент).** `Jump Lists` (`AutomaticDestinations-ms`) и `Prefetch`
фиксируют работу приложений с сетевыми путями. Например, запись `EXCEL.EXE-*.pf` со
ссылками на `Z:\reports\summary.xlsx` показывает, что файл не только листали, но и открывали.

## Таблица: артефакты SMB и где искать

| Артефакт | Расположение | Что доказывает |
|---|---|---|
| Mapped Drives | `HKCU\Network\<letter>` | какая буква → какая шара, под какой учёткой |
| Shellbags | `USRCLASS.DAT` BagMRU/Bags | какие сетевые папки открывались и когда |
| Jump Lists | `%AppData%\...\AutomaticDestinations-ms` | файлы, открытые приложением |
| Prefetch | `C:\Windows\Prefetch\*.pf` | запуск программ + ссылки на сетевые пути |
| SRUM | `C:\Windows\System32\sru\SRUDB.dat` | сетевой трафик по процессам (в т.ч. SMB) |
| Объектный доступ (сервер) | Security log, 5140/5145 | кто, откуда, какую шару/файл открыл |
| SMB-клиент (сервер) | Microsoft-Windows-SMBServer/Operational | подключения и отключения по SMB |

## Работа с smbclient: команды и что они дают

`smbclient` — это «клиент SMB из мира Linux». Для форензика он полезен тем, что позволяет
аккуратно перечислить ресурсы и снять содержимое, не поднимая полноценную Windows.

```
$ smbclient -L //fileserver -N              # список шар без пароля
$ smbclient //fileserver/share -N           # интерактивная сессия
smb: \> recurse ON
smb: \> prompt OFF
smb: \> mget reports\*                      # забрать каталог целиком
smb: \> allinfo reports\summary.xlsx        # метаданные файла (size, mtime, attrs)
smb: \> getfacl reports                     # ACL каталога
```

Обрати внимание на `allinfo`: он отдаёт не только размер и время изменения, но и флаги
(например, атрибут «архивный») и `Change Time`. Разница между `Modification Time` и
`Change Time` помогает заметить подмену временных меток (timestomping).

## Анализ трафика SMB в pcap

Если есть перехват, `tshark` вытащит имена шар и файлов прямо из протокола:

```
$ tshark -r capture.pcap -Y 'smb2' -T fields \
    -e ip.src -e ip.dst -e smb2.filename | sort -u
10.0.5.23   10.0.5.10   reports\2024-q4\summary.xlsx
10.0.5.23   10.0.5.10   reports\2024-q4\payroll.csv
```

Фильтр `smb2.cmd == 5` (Create) показывает открытия файлов, `smb2.cmd == 8` (Read) —
чтение. Последовательность «Create → Read → Read → … → Close» на большом файле — признак
копирования целиком, а не просмотра. Для SMB1 используй `smb.cmd`/`smb.filename`.

## SMB signing и почему это важно для доказательства

**SMB signing** добавляет к каждому пакету криптографическую подпись. Если подпись
включена и обязательна (`RequireSecuritySignature=1`), то подделать трафик на лету
(relay-атака) нельзя, и перехваченные записи трафика считаются достоверными. Проверить
состояние на сервере:

```
$ nmap -p445 --script smb2-security-mode 10.0.5.10
| smb2-security-mode:
|   3.1.1:
|_    Message signing enabled and required
```

Если подпись «enabled but not required», злоумышленник мог подменить сервер и увести
данные на свой хост — тогда сетевой перехват не доказывает, **куда** реально ушли файлы,
и нужен дополнительный анализ клиентских артефактов.

## Ограничения и подводные камни

- **Клиентские артефакты говорят о намерении, серверные — о факте.** Shellbags показывают,
  что папку *открывали*; факт передачи доказывает только серверный журнал (5145) или pcap.
- **5140/5145 не логируются по умолчанию.** Аудит доступа к объектам должен быть включён
  заранее (GPO «Audit File Share» / «Audit Detailed File Share»). Если его нет — серверных
  следов не будет вообще.
- **Время на клиенте и сервере может расходиться.** При корреляции событий всегда
  проверяй NTP-синхронизацию и пояс (UTC vs локальное) — иначе таймлайн «поедет».
- **Смонтированные, но неиспользуемые диски** остаются в `HKCU\Network` и создают ложное
  впечатление доступа. Подтверждай парой «Shellbags/Jump List + серверное событие».
- **SMB3-шифрование** (`-Y 'smb2.transform_header'`) делает содержимое трафика
  нечитаемым без ключей сессии — pcap покажет лишь факт обмена, но не имена файлов.

## Сводим таймлайн: клиент + сервер

Итоговое доказательство строится как **коррелированный таймлайн**: строки клиента и сервера
сортируются по времени, и события с разницей в секунды складываются в одну картину доступа.
Соберём его простым скриптом:

```
$ cat client.csv server.csv | sort -k1,1 | column -t -s,
2024-11-03T21:58:12  client  Shellbag   open  Z:\reports\2024-q4
2024-11-03T21:58:13  server  5145       Read  \\fileserver\share\reports\2024-q4
2024-11-03T21:58:19  client  JumpList   open  Z:\reports\2024-q4\payroll.csv
2024-11-03T21:58:20  server  5145       Read  \\fileserver\share\reports\2024-q4\payroll.csv
2024-11-03T22:01:04  client  Prefetch   exec  EXCEL.EXE (Z:\reports\summary.xlsx)
```

Такая таблица отвечает на все три вопроса: **кто** (учётка из `HKCU\Network\Z:\UserName`),
**что** (пути из Shellbags/Jump Lists и серверных 5145) и **когда** (сортировка по времени).
Расхождение клиентского и серверного времени — повод применить поправку на разницу часов,
а не отбрасывать событие.

## Быстрая проверка «а не приманка ли это»

Атакующий иногда создаёт **фальшивые** Shellbags/Jump Lists, чтобы увести следствие.
Отличить подделку помогают детали: реальные записи согласованы между собой (Shellbag +
USN-журнал + серверный журнал), у поддельных часто «ломаная» связность — путь есть, а
записи в `$UsnJrnl` об открытии каталога нет. Поэтому правило простое: **любое клиентское
утверждение подтверждай вторым, независимым источником** (журнал сервера, USN, pcap).

## Куда дальше

SMB-шары — это корпоративный мир. Но данные всё чаще живут **в облаке**, а локально
остаётся лишь кэш. В следующем уроке разберём артефакты облачной синхронизации. А пока
запомни: доступ к шаре доказывают серверные события 5140/5145.

## Где пригодится

- **DFIR / Incident Response** — обнаружение доступа и выноса данных по SMB.
- **CTF Forensics** — задачи с сетевыми дисками и шары.
- **Анализ образов дисков** — корректное снятие шары.
