## Вопрос, с которого всё начинается

Тебе дали файл `access.log` с веб-сервера, который «вроде бы взломали». Внутри —
тысячи строк. Читать глазами бессмысленно. Как за пару минут найти в этом море
**аномалию** — то, что выбивается из обычного поведения?

Логи — это хроника того, что делали система и приложения. Умение быстро сузить
тысячи строк до нескольких подозрительных — базовый навык форензика. В этом уроке
мы возьмём один лог и доведём разбор до вывода.

## Наш пример: один access.log

```bash
$ wc -l access.log
15257 access.log
```

Пятнадцать тысяч строк. Ручной просмотр исключён — начинаем с агрегации.

## Шаг 1: из чего состоит строка лога

Формат **combined** (стандартный для nginx/apache) выглядит так:

```
203.0.113.9 - - [01/Mar/2024:09:12:03 +0000] "GET /index.html HTTP/1.1" 200 1043 "-" "Mozilla/5.0"
```

Поля разделены пробелами. Запомним номера: `$1` — IP клиента, `$6` — метод, `$7` —
URL, `$9` — код ответа, `$10` — размер ответа. На этих номерах строится весь
дальнейший разбор.

## Шаг 2: какие коды ответов вообще были

```bash
$ awk '{print $9}' access.log | sort | uniq -c | sort -rn
  12034 200
   3211 404
     12 500
```

`awk '{print $9}'` печатает девятое поле каждой строки, `sort | uniq -c` считает,
сколько раз встретилось каждое значение, `sort -rn` сортирует по частоте. Этот
паттерн — «частота по значению» — основной приём анализа логов.

Три тысячи «404» (страница не найдена) — уже подозрительно: обычные посетители
столько не промахиваются.

## Шаг 3: кто именно долбит 404

```bash
$ awk '$9==404 {print $1}' access.log | sort | uniq -c | sort -rn | head -3
   3201 203.0.113.9
     10 198.51.100.7
```

Один IP дал 3201 из 3211 «не найдено». Это не пользователь — это **сканер**,
автоматический перебор путей. Теперь у нас есть подозреваемый.

## Шаг 4: что именно он искал

```bash
$ grep '203.0.113.9' access.log | grep -oE 'GET [^ ]+' | sort -u | head
GET /.git/config
GET /backup.sql
GET /phpmyadmin/
```

`grep -oE 'GET [^ ]+'` вытаскивает только сам запрос (без лишнего текста), `sort -u`
убирает повторы. Видно, что IP методично ищет **утечки**: репозиторий `.git`, дамп
базы `backup.sql`, панель `phpmyadmin`. Это разведка перед атакой.

## Шаг 5: была ли эксплуатация

```bash
$ grep -iE 'cmd=|eval|system|base64' access.log | head
203.0.113.9 - - [..] "GET /upload.php?cmd=id HTTP/1.1" 200 33
```

`grep -iE` ищет по нескольким шаблонам без учёта регистра. Запрос с параметром
`cmd=id` и кодом `200` (успех) — сильный признак выполнения команд на сервере.
Наивный сканер такого не делает: значит, уязвимость нашли и использовали.

## Шаг 6: где оставили webshell

```bash
$ awk '$6=="POST" && $9==200 {print $1,$7,$10}' access.log | sort | uniq -c | sort -rn | head
   842 203.0.113.9 /upload.php 1204
```

Много POST-запросов к одному файлу с **постоянным** размером ответа — типичный
признак **webshell** (загруженной веб-оболочки): злоумышленник гоняет через неё
команды, и размер ответа почти не меняется. Цепочка замкнулась: сканер → эксплуатация
`upload.php?cmd=` → закрепление через webshell.

## Логи — это поток, а не текст

Читать лог целиком нельзя. Ротированные и сжатые файлы разворачивайте на лету:

```bash
$ zcat access.log.*.gz | grep 'Failed password'
```

А для системных журналов Linux есть `journalctl`:

```bash
$ journalctl -u nginx --since "2024-03-01" --until "2024-03-02"
$ journalctl -p err -b          # только ошибки текущей загрузки
```

## Ещё один лог: auth.log и брутфорс

Web-логи — только половина картины. Второй частый артефакт — `auth.log` (журнал входов
в Linux). Здесь атака выглядит иначе:

```bash
$ grep 'Failed password' auth.log | awk '{print $(NF-3)}' | sort | uniq -c | sort -rn | head -2
    412 203.0.113.9
$ grep -E 'Failed|Accepted' auth.log | grep '203.0.113.9' | tail -3
Failed password for root from 203.0.113.9 ...
Failed password for root from 203.0.113.9 ...
Accepted password for root from 203.0.113.9 ...
```

412 неудачных попыток с одного IP, а затем `Accepted` — это **брутфорс**: перебор
пароля, который в итоге удался. Обратите внимание: IP тот же, что сканировал веб.
Значит, это один и тот же злоумышленник, и две атаки нужно читать вместе.

## Связываем логи между собой

Каждый лог по отдельности — половина истории. Сопоставим время из веб-лога со временем
файла на диске:

```bash
$ grep 'upload.php' access.log | awk '{print $4}' | tr -d '['
$ stat -c '%y' /var/www/html/upload.php
```

Если время POST из `access.log` совпадает со временем изменения файла на диске — это
подтверждает, что через `upload.php` действительно писали файл. Так лог «склеивается»
с файловой системой в одну доказуемую картину.

## JSON-логи: `jq` вместо `grep`

Современные приложения и облака пишут логи в **JSON** (структурированный формат
«ключ-значение»). Там удобнее не `grep`, а `jq`:

```bash
$ jq -r '.Records[] | [.eventTime,.eventName,.sourceIPAddress] | @tsv' trail.json | head
$ jq '.Records[] | select(.eventName=="CreateUser")' trail.json
```

Первая команда вытаскивает три поля в таблицу, вторая оставляет только события
создания пользователя. Фильтр `select(...)` заменяет десяток `grep`.

## Полезные флаги grep для логов

| Флаг | Смысл |
|------|-------|
| `-c` | только число совпадений |
| `-i` | без учёта регистра |
| `-v` | инвертировать (строки БЕЗ совпадения) |
| `-A/-B/-C N` | N строк контекста после/до/вокруг |
| `-a` | бинарный файл читать как текст |

Флаг `-C 3` особенно полезен: он показывает три строки вокруг совпадения, и ты сразу
видишь, с каким запросом соседствует подозрительная строка. А `-v` помогает отсеять
шум — например, убрать все успешные `200`, чтобы остались только ошибки.

## Бинарные логи входов

Не все логи — текст. `wtmp`, `btmp` и `lastlog` хранят входы в **бинарном** виде, и
читать их нужно специальными командами:

```bash
$ last -f wtmp | head
bob  pts/0  203.0.113.9  Sat Mar  1 09:20   still logged in
$ lastb -f btmp | wc -l
1500
$ lastlog | grep -v 'Never'
```

`last` показывает успешные входы, `lastb` — неудачные (те самые 1500 попыток
брутфорса), а `lastlog` — время последнего входа каждого пользователя. Эти файлы
ценны тем, что злоумышленник, чистя текстовые логи, часто забывает про бинарные.

## На что смотреть дальше

- **Брутфорс SSH** — в `auth.log` много `Failed password` с одного IP, затем `Accepted`.
- **Нормализация времени** — веб-серверы часто пишут локальное время, а не UTC.
- **Корреляция** — сверьте время из лога со временем изменения файла на диске.
- **Пустоты** — если логов за период нет, их могли вычистить; это тоже улика.

## Куда дальше

Мы нашли атаку в логе и восстановили её шаги. Но найденное нужно **оформить** так,
чтобы результат можно было проверить и защитить: журнал действий, хеши, цепочка
сохранности, отчёт. Об этом — следующий урок. А пока запомни: **сначала агрегируй
(`uniq -c`), потом углубляйся в конкретный IP и время**.

## Где пригодится

- **CTF:** задачи «дан access.log — найди атаку/флаг».
- **SOC / SIEM:** первые шаги триажа алерта, проверка гипотез.
- **Incident Response:** восстановление хронологии и границ компромисса.
- **Threat Hunting:** поиск аномалий по логам до срабатывания сигнатуры.
