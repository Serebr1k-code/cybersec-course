## Вопрос, с которого всё начинается

Ты запускаешь образец в песочнице — и он ничего не делает. Не потому что безвреден, а
потому что **понял**, что это песочница. Анти-анализ — обязательная часть современной
малвари. Разберём, как это работает и как обойти.

## Наш пример: образец, который «спит»

## Шаг 1: проверка окружения

Малварь смотрит на артефакты виртуальных машин:

- имя компьютера (`SANDBOX`, `VIRUS`);
- процессы (`vboxservice`, `vmtoolsd`);
- устройства (`\\.\VBoxGuest`, MAC `08:00:27`);
- размер диска/ОЗУ (слишком маленькие).

```
$ strings sample.bin | grep -iE 'vbox|vmware|qemu' | head
vboxservice.exe
```

Наличие таких строк — признак, что образец **ищет** песочницу.

## Шаг 2: проверка пользователя

Малварь проверяет, «живой» ли пользователь:

- движение мыши;
- количество открытых окон;
- наличие документов в `Recent`;
- время работы системы (uptime).

Если всё «слишком чисто» — не запускается.

## Шаг 3: анти-отладка

Типовые приёмы:

- `IsDebuggerPresent` / PEB-флаги;
- проверка `ptrace` (Linux);
- timing-проверки (отладчик замедляет);
- `int3`-ловушки, самопатч.

```
$ strings sample.bin | grep -iE 'IsDebuggerPresent|ptrace' | head
IsDebuggerPresent
```

## Шаг 4: задержки и «спящие» ветки

Малварь ждёт часы/дни, проверяет дату, ждёт перезагрузку. Тогда в короткой песочнице
она просто не успевает проявиться.

## Шаг 5: как обходить

- **патчить проверки** (NOP-ить ветки);
- **эмулировать/менять ответы** (в Qiling задать нужные значения);
- **давать песочнице «живой» вид** (двигать мышь, добавлять документы);
- **использовать эмуляцию** вместо реального исполнения.

## Что мы теперь знаем

- Анти-анализ ищет артефакты VM и отладчика.
- Проверки пользователя (мышь, окна) отличают лабораторию.
- Задержки отсекают короткий анализ.
- Обход: патч, эмуляция, «живое» окружение.
- Строки-маркеры выдают наличие проверок.

## Если не сработало

- Образец не запускается вообще? Эмулируй по частям.
- Проверок слишком много? Патчь по одной.
- Нужна динамика? Строй максимально «настоящую» ВМ.

## Таблица: типовые анти-эмуляционные проверки

| Проверка | Как выглядит | Как обойти |
|---|---|---|
| CPUID | инструкция `cpuid` | вернуть значения реального CPU |
| RDTSC | замер тактов | нормализовать время |
| `rdtsc`-дельта | слишком ровная задержка | добавить джиттер |
| Количество ядер | `cpuid` leaf 0xB | вернуть 4+ ядра |
| Имена устройств | `\\.\VBoxGuest` | перехватить и вернуть ENOENT |
| MAC-адрес | `08:00:27` (VirtualBox) | подменить на реальный OUI |
| Размер RAM | < 2 ГБ | задать реалистичный объём |
| Uptime | почти ноль | подделать `GetTickCount` |

Большинство проверок читает окружение через API — а значит, перехватывается в
`Qiling`. Смотри, какие значения образец запрашивает, и возвращай
правдоподобные.

## Разбор примера: как образец «просыпается»

Часто малварь ждёт события, а не времени:

```
$ strings sample.bin | grep -iE 'mouse|GetCursorPos|GetLastInputInfo'
GetCursorPos
GetLastInputInfo
```

`GetCursorPos`/`GetLastInputInfo` — проверка активности пользователя. Если
курсор не двигался N секунд, образец считает окружение автоматическим и
выходит. Обход: подсунуть реальные координаты в хуке или использовать
инструмент, эмулирующий ввод.

## Песочница против эмуляции

| Критерий | Песочница | Эмуляция |
|---|---|---|
| Реальные API | да | нет (подменяются) |
| Скорость | медленнее | быстрее |
| Обнаружимость | выше | ниже |
| Полнота поведения | выше | зависит от реализации |
| Безопасность | изоляция ОС | полная (нет ОС) |

Эмуляция скрытнее и безопаснее, но менее полна. Песочница реалистичнее, но
легче обнаруживается. На практике их комбинируют: сначала эмуляция (скрытно
вскрыть обфускацию), затем песочница (наблюдать поведение).

## Если сработало

Обход анти-анализа удался — фиксируй и применяй:

1. Сохрани патч/скрипт обхода как артефакт для повторного использования.
2. Запиши поведение, которое образец скрывал (после «пробуждения»).
3. Извлеки IOC из скрытой ветки.
4. Отметь в отчёте, какие проверки использовал образец — это TTP семейства.

TTP анти-анализа ценны для детекта: правило, ловящее `GetLastInputInfo` в
подозрительном контексте, работает против целого семейства, а не одного хеша.

## Ограничения и типичные ошибки

- **Слишком «чистая» песочница** — образец не запустится; добавляй документы,
  двигай мышь, ставь реальные приложения.
- **Только одна техника** — патч одной проверки бесполезен, если их десять;
  ищи все.
- **Долгое ожидание** — образец может ждать сутки; не трать на это всё время,
  эмулируй ветку.
- **Патч меняет логику** — NOP-нув проверку, легко сломать декриптор; сверяй
  результат с эмуляцией.

## Таблица: артефакты виртуальных машин

Анти-анализ опирается на конкретные признаки среды:

| Признак | Значение | Где проверяется |
|---|---|---|
| MAC OUI | 08:00:27 (VBox), 00:0C:29 (VMware) | `GetAdaptersInfo` |
| Имя ПК | SANDBOX, MALTEST, VIRUS | `GetComputerName` |
| Процессы | vboxservice, vmtoolsd, qemu-ga | `CreateToolhelp32Snapshot` |
| Устройства | `\\.\VBoxGuest`, `\\.\vmci` | `CreateFileW` |
| Диск | < 60 ГБ | `GetDiskFreeSpaceEx` |
| RAM | < 2 ГБ | `GlobalMemoryStatusEx` |
| Число ядер | 1 | `GetSystemInfo` |
| Реестр | ключи VMware/VBox | `RegOpenKeyEx` |

Образец проверяет несколько признаков и, если срабатывает хоть один, уходит в
«спящую» ветку. Именно поэтому важно находить **все** проверки, а не одну.

## Пример: обход проверки ptrace

В Linux малварь проверяет, не под отладчиком ли она:

```
$ strace -e trace=ptrace ./sample 2>&1 | head
ptrace(PTRACE_TRACEME, 0, NULL, NULL) = -1 EPERM (Operation not permitted)
```

`PTRACE_TRACEME` возвращает `-1`, если процесс уже трассируется — тогда
образец завершается. Обход: патчим проверку (NOP) или перехватываем `ptrace`
и возвращаем `0`. После обхода образец исполняет скрытую логику.

## Если сработало

Обход удался — фиксируй скрытое поведение:

1. Запиши, какие проверки использовал образец (это TTP семейства).
2. Извлеки IOC из «проснувшейся» ветки (C2, файлы, ключи реестра).
3. Сохрани патч/скрипт обхода как переиспользуемый артефакт.
4. Напиши правило детекта на сами проверки — оно ловит всё семейство.

Правило, ловящее `GetLastInputInfo` + `ptrace` в подозрительном контексте,
работает против тысяч вариантов, а не одного хеша.

## Ограничения и типичные ошибки

- **Одна проверка из десяти** — патч единственного признака не поможет; ищи
  полный набор.
- **Патч ломает логику** — NOP-нув проверку, легко испортить декриптор;
  сверяй поведение с эмуляцией.
- **Слишком «настоящая» ВМ** — часть малвари проверяет железо (SMBIOS,
  вентиляторы); их не подделать программно.
- **Долгое ожидание** — образец может ждать часы/дни; эмулируй ветку, не
  трать реальное время.

## Итог

Анти-анализ — обязательная часть современной малвари: проверки VM,
пользователя, отладчика и времени. Обход строится на патче проверок,
эмуляции с подменой значений и создании «живого» окружения. Строки-маркеры
(`vboxservice`, `IsDebuggerPresent`, `ptrace`) заранее выдают наличие защит —
ищи их в статике, прежде чем запускать образец.

## Таблица: проверки пользователя и времени

| Проверка | API/признак | Что означает |
|---|---|---|
| Движение мыши | `GetCursorPos` | живой пользователь |
| Ввод | `GetLastInputInfo` | была активность |
| Открытые окна | `EnumWindows` | рабочая станция |
| Recent-документы | `%APPDATA%\Recent` | пользователь работал |
| Uptime | `GetTickCount` | система давно включена |
| Дата | `GetSystemTime` | не выходной/праздник |
| Задержка | `Sleep(600000)` | ждать перед запуском |
| Перезагрузка | счётчик загрузок | активироваться после N reboot |

Малварь комбинирует эти признаки: например, ждёт, пока uptime превысит
10 минут и курсор сдвинется. Только тогда активируется «боевая» ветка.

## Пример: обход проверки времени

Образец «спит» 10 минут перед запуском:

```
$ strings sample.bin | grep -iE 'Sleep|GetTickCount'
Sleep
GetTickCount
```

В эмуляции перехватываем `Sleep` и возвращаем управление сразу:

```python
def on_sleep(ql, address, params):
    return 0   # не ждём
ql.os.set_api("Sleep", on_sleep)
```

Так за секунды проходишь то, что в реальности заняло бы часы. Это ключевое
преимущество эмуляции над песочницей.

## Итог

Анти-анализ проверяет окружение (VM), пользователя (мышь, окна), отладчик
(`ptrace`, `IsDebuggerPresent`) и время (Sleep, uptime). Обход строится на
патче проверок, эмуляции с подменой возвратов и создании «живого» окружения.
Строки-маркеры в статике заранее выдают защиты — найди их до запуска.

## Как отличить анти-анализ от обычного кода

Не каждая проверка окружения — анти-анализ. Легитимное ПО тоже смотрит на версию ОС, объём памяти и число ядер. Признаки, которые выдают именно защиту: результат проверки влияет на **ветвление логики** (одна ветка «работать», другая «спать/выходить»), проверки дублируются и перемешаны с обфускацией, а рядом стоят строки вроде `SANDBOX`, `VIRUS`, `sample`. Ищи **крест-накрест**: если значение `GetSystemInfo` сравнивается с единицей и при совпадении вызывается `ExitProcess` — это фильтр, а не совместимость.

Ещё маркер — проверки на **несогласованность среды**: имя пользователя `admin` при пустом `Recent`, нулевой uptime при включённом `Explorer`, MAC `08:00:27` при «рабочей станции». Их комбинация практически однозначно означает песочницу.

## Практический чек-лист обхода

1. Статически собери **все** строки-маркеры (`vbox`, `ptrace`, `IsDebuggerPresent`, `Sleep`) — это карта проверок.
2. Определи, что каждая проверка делает при срабатывании (выход, сон, порча логики).
3. Выбери среду: эмуляция (быстро, скрытно) или ВМ (реалистично, но обнаружимо).
4. Обходи **все** проверки — патчем, хуком или правдоподобным ответом.
5. Зафиксируй, что образец делает после «пробуждения», и извлеки IOC.
6. Опиши проверки как TTP — они дают правило детекта на всё семейство.
