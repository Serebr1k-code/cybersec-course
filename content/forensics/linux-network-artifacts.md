## Вопрос, с которого всё начинается

Вредоносное ПО на Linux почти всегда «звонит домой» по сети. Но журналов может не
быть. Зато есть **текущее состояние** сети: сокеты, соединения, таблицы. Из них можно
восстановить, с кем хост общался. Разберём источники.

## Наш пример: подозрительное соединение

## Шаг 1: смотрим сокеты с процессами

```
$ sudo ss -tunap | grep ESTAB
tcp ESTAB 0 0 10.10.20.5:54322 203.0.113.5:443 users:(("x",pid=991,fd=4))
```

`ss` показывает активное соединение: локальный `10.10.20.5:54322` ↔ удалённый
`203.0.113.5:443`, и — главное — процесс `x` (PID 991). Это тот же процесс, что мы
нашли в `/proc`.

## Шаг 2: /proc/net — сырые данные

`ss` читает `/proc/net/*`. Полезно, когда `ss` недоступен:

```
$ cat /proc/net/tcp | head
  sl  local_address rem_address   st tx_queue rx_queue ...
   0: 0A0A1405: D426  CB007105: 01BB 01 ...
```

Адреса в hex и «перевёрнуты»: `0A0A1405` = `10.10.20.5`, `CB007105` = `203.0.113.5`,
порт `01BB` = 443. Уметь читать hex полезно, когда нет утилит.

## Шаг 3: conntrack — история соединений

Если включён firewall с conntrack, он помнит **все** соединения, включая закрытые:

```
$ sudo conntrack -L | grep 203.0.113.5
tcp 6 431999 ESTABLISHED src=10.10.20.5 dst=203.0.113.5 sport=54322 dport=443 ...
```

Это уже история, а не только текущее состояние — ценный источник для таймлайна.

## Шаг 4: ARP-таблица

Кто был в локальной сети:

```
$ ip neigh show
10.10.20.9 dev eth0 lladdr 02:42:0a:0a:14:09 REACHABLE
```

MAC-адрес `02:42:...` — типичный для виртуальных интерфейсов (Docker/VM). Сопоставляя
MAC и IP, понимаешь топологию и возможный источник атаки.

## Шаг 5: сопоставляем с процессами

Ключевая связка: сокет → inode → процесс. Inode сокета:

```
$ ls -l /proc/991/fd/4
lrwx------ 1 root root 64 ... 4 -> socket:[45678]
```

Затем ищем этот inode по всем `/proc`:

```
$ for p in /proc/[0-9]*; do grep -l 45678 "$p"/fdinfo/* 2>/dev/null; done
```

Так находишь **все** процессы, использующие соединение.

## Что мы теперь знаем

- `ss -tunap` показывает соединения с процессами.
- `/proc/net/tcp` — сырые hex-адреса (полезно без утилит).
- conntrack помнит закрытые соединения — история.
- `ip neigh` даёт ARP/MAC — локальная топология.
- Сокет ↔ inode ↔ процесс связывает сеть с файлами и процессами.

## Если не сработало

- Соединение закрыто? Смотри conntrack и логи firewall.
- Нет conntrack? Проверь `/var/log/` и eBPF-трассировку.
- Нужен трафик? Снимай дамп (`tcpdump`) до выключения хоста.

## Полный набор источников сетевой активности

Сеть на Linux оставляет следы в нескольких местах. Полезно знать их все:

| Источник | Что даёт | Живёт |
|---|---|---|
| `ss -tunap` | сокеты + процессы | сейчас |
| `/proc/net/tcp`, `udp` | сырые таблицы в hex | сейчас |
| `/proc/net/unix` | unix-сокеты | сейчас |
| `conntrack -L` | история соединений | пока живёт запись |
| `ip neigh` / `/proc/net/arp` | ARP/MAC | кэш |
| `nstat` / `/proc/net/netstat` | счётчики (retrans, errors) | с загрузки |
| `lsof -i` | сокеты по файлам | сейчас |
| `auditd` | execve + connect | по правилам |
| `journald`/syslog | события сети, DNS | по ротации |
| `/etc/hosts`, `resolv.conf` | статическая конфигурация | пока файл |

Комбинация «сейчас» + «история» + «конфигурация» даёт полную картину: с кем хост общался,
через какой процесс и как это настроено.

## Чтение /proc/net/tcp: hex-адреса

Когда нет `ss`/`netstat`, таблицы читают напрямую. Адрес там в hex и **little-endian по
байтам**:

```
$ cat /proc/net/tcp
  sl  local_address rem_address   st tx_queue rx_queue tr tm->when retrnsmt   uid  ...
   0: 0A0A1405:D426 CB007105:01BB 01 00000000:00000000 ...
```

- `0A0A1405` → `0A.0A.14.05` → `10.10.20.5`;
- `CB007105` → `CB.00.71.05` → `203.0.113.5`;
- `D426` = 54322, `01BB` = 443;
- `st` = `01` (ESTABLISHED), `0A` = LISTEN, `06` = TIME_WAIT.

Быстрая расшифровка:

```
$ awk 'NR>1{print $2, $3, $4}' /proc/net/tcp | while read l r s; do
    echo "$s $(printf '%d' 0x${l##*:}) <- $(printf '%d' 0x${r##*:})"
  done
```

## conntrack детально

Netfilter conntrack хранит состояние каждого потока и, в отличие от `/proc/net/tcp`,
помнит и закрытые соединения (пока запись не истекла):

```
$ conntrack -L -p tcp --dport 443
tcp 6 431999 ESTABLISHED src=10.10.20.5 dst=203.0.113.5 sport=54322 dport=443 \
    src=203.0.113.5 dst=10.10.20.5 sport=443 dport=54322 [ASSURED] mark=0 use=1
$ conntrack -L | awk '{print $5, $6}' | sort | uniq -c | sort -rn | head
```

`ESTABLISHED`, `TIME_WAIT`, `CLOSE_WAIT` показывают, какие соединения были. Если
conntrack-модуль не загружен — истории нет, остаются только логи firewall (`iptables -j
LOG`, `nft` с логированием).

## Сокет ↔ inode ↔ процесс

Ядро связывает процесс и соединение через inode сокета. Это позволяет найти все процессы,
использующие сокет:

```
$ ss -tnp | grep 203.0.113.5
tcp ESTAB 0 0 10.10.20.5:54322 203.0.113.5:443 users:(("x",pid=991,fd=4))
$ ls -l /proc/991/fd/4
... 4 -> socket:[45678]
$ grep -rl 45678 /proc/*/fdinfo/ 2>/dev/null
```

Если процесс уже завершился, inode сокета «повисает» в `/proc/net/tcp` без владельца — это
признак недавно закрытого соединения. Тогда смотри `auditd` (`connect`, `execve`) и
историю `journald`.

## Другие артефакты: DNS, auditd, eBPF

- **DNS-запросы** — `journalctl -u systemd-resolved`, `dnsmasq`-логи, `/var/log/named`;
- **auditd** — правила на `syscall connect`/`execve` дают точное время и PID;
- **eBPF** — `bpftrace`/`bcc` могут логировать соединения в реальном времени;
- **`~/.bash_history`** — команды `curl`, `nc`, `scp` выдают адреса;
- **`/etc/hosts`, `/etc/resolv.conf`** — подмена DNS-сервера часто остаётся здесь.

## Практический разбор CTF

Задача: «какой процесс связался с C2». Порядок:

```
$ ss -tunap | grep -v '127.0.0.1\|::1'      # активные соединения
$ conntrack -L 2>/dev/null | grep -v '127.0.0.1' | awk '{print $5, $6, $7, $8}' | sort -u
$ ip neigh show                               # кто был рядом
$ grep -a 'connect(' /var/log/audit/audit.log | tail
```

Найдя PID, смотрим `/proc/<pid>/exe` (что за бинарь) и `/proc/<pid>/cwd` (откуда запущен).

## Ограничения

- `/proc/net/*` показывает **только** текущие сокеты — после закрытия записи исчезают.
- conntrack хранит ограниченное число записей и очищается по таймауту.
- Без прав root часть информации (`-p`, conntrack, auditd) недоступна.
- Зашифрованный трафик виден как «соединение есть», но содержимого нет.
- Данные в `/proc` меняются ежемоментно — фиксируй их до выключения хоста.

## Карта таблиц /proc/net

`/proc/net` — это ядро, отдающее своё сетевое состояние текстом. Каждая таблица
отвечает на свой вопрос:

| Файл | Что содержит |
|---|---|
| `/proc/net/tcp` | TCP-сокеты IPv4 (состояния) |
| `/proc/net/tcp6` | TCP-сокеты IPv6 |
| `/proc/net/udp` | UDP-сокеты IPv4 |
| `/proc/net/udp6` | UDP-сокеты IPv6 |
| `/proc/net/unix` | UNIX-сокеты (локальные) |
| `/proc/net/arp` | ARP-таблица (IP↔MAC) |
| `/proc/net/route` | таблица маршрутизации |
| `/proc/net/packet` | raw/AF_PACKET (снифферы) |
| `/proc/net/nf_conntrack` | таблица conntrack |

Таблица `packet` особенно интересна: **если в ней есть сокеты, значит на хосте
работает сниффер** (tcpdump, фреймворк захвата, вредоносный дампер). Это самостоятельная
находка.

## Разбор hex-адресов вручную

В `/proc/net/tcp` адрес и порт закодированы hex и в сетевом порядке байт:

```
$ head -2 /proc/net/tcp
  sl  local_address rem_address   st tx_queue rx_queue tr tm->when retrnsmt   uid ...
   0: 0A0A1405:1F90 CB007105:01BB 01 00000000:00000000 00:00000000 00000000  1000 ...
```

`0A0A1405` — это `10.10.20.5` (каждый байт — отдельный октет: `0A`=10, `0A`=10,
`14`=20, `05`=5). Порт `1F90` = 8080. Состояние в столбце `st`:

| Код | Состояние |
|---|---|
| `01` | ESTABLISHED |
| `02` | SYN_SENT |
| `06` | TIME_WAIT |
| `0A` | LISTEN |

Умение читать hex пригодится, когда `ss`/`netstat` отсутствуют или недоступны
(например, в урезанном контейнере).

## conntrack глубже

conntrack — это таблица состояний firewall. Она хранит соединение, пока оно активно и
пока не истёк таймаут, поэтому даёт **историю**, а не только текущий срез:

```
$ sudo conntrack -L
tcp 6 431999 ESTABLISHED src=10.10.20.5 dst=203.0.113.5 sport=54322 dport=443 ...
```

Поле после протокола — оставшееся время жизни записи. Состояния:

- `NEW` — начатое соединение;
- `ESTABLISHED` — двусторонний обмен;
- `RELATED` — связанное (например, FTP-данные);
- `UNREPLIED` — пакеты были только в одну сторону (признак сканирования).

Фильтрация по цели:

```
$ sudo conntrack -L -d 203.0.113.5
```

Если conntrack не ведётся (нет firewall), история соединений недоступна — тогда
остаются логи и дампы.

## eBPF и auditd: когда /proc мало

`/proc/net` показывает **текущее** состояние. Для истории обращайся к:

- **auditd** — системные вызовы `connect`/`accept`/`bind` с PID и адресом:
  ```
  $ ausearch -m SYSCALL -sc connect | head
  ```
- **eBPF** — трассировка соединений без перезапуска (`bpftrace`, Cilium);
- **ss с расширениями** — `ss -tinp` покажет таймеры и параметры TCP;
- **journald** — записи NetworkManager, dhclient, systemd-networkd.

Комбинация «conntrack (что было) + auditd (кто и когда) + /proc (что сейчас)» даёт
полный таймлайн сетевой активности.

## Инструменты и практическая последовательность

Рабочий порядок на живом хосте:

1. `ss -tunap` — все соединения с процессами;
2. `ss -tlnp` — только слушающие (что открыто наружу);
3. `ip neigh` — ARP-таблица;
4. `sudo conntrack -L` — история;
5. `lsof -i` — альтернатива с привязкой к файлам;
6. `cat /proc/net/packet` — есть ли сниффер.

Для быстрой проверки конкретного процесса:

```
$ ss -tnp | grep 991
```
