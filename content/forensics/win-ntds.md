## Вопрос, с которого всё начинается

Ты разбираешь компрометацию контроллера домена. На диске лежит файл
`C:\Windows\NTDS\NTDS.dit` — это **база данных Active Directory**. В ней учётные записи
всего домена, включая хеши паролей. Вопрос: как её прочитать и что именно она содержит?

Проблема в том, что NTDS.dit нельзя просто «открыть» — он зашифрован, и на живом DC файл
заблокирован. Разберём сквозной пример: добудем записи из копии NTDS.dit.

## Что такое NTDS.dit

**NTDS.dit** — это база данных в формате **ESE** (Extensible Storage Engine, тот же
движок, что у `Windows.edb` и почты Exchange). Внутри — таблицы, главные из которых:

- **datatable** — объекты каталога: пользователи, компьютеры, группы.
- **linktable** — связи между объектами (членство в группах).
- **sdtable** — дескрипторы безопасности.

Имена атрибутов хранятся не строками, а ссылками на таблицу **metadatatable** (номер
колонки → имя). Поэтому «сырой» просмотр ESE без схемы малоинформативен.

## Почему нужен SYSTEM-hive

NTDS.dit **зашифрован** ключом, который называется **PEK** (Password Encryption Key).
Сам PEK хранится в ветви реестра:

```
HKLM\SYSTEM\CurrentControlSet\Control\Lsa\JD
HKLM\SYSTEM\CurrentControlSet\Control\Lsa\Skew1
HKLM\SYSTEM\CurrentControlSet\Control\Lsa\GBG
HKLM\SYSTEM\CurrentControlSet\Control\Lsa\Data
```

Четыре фрагмента, склеенные и пропущенные через перестановку, дают **boot key**
(он же syskey). Из boot key выводится PEK, а им уже расшифрованы хеши в NTDS.dit.

Вывод для аналитика: **копия NTDS.dit без hive SYSTEM бесполезна** — нечем снять
шифрование. Поэтому при сборе всегда берут пару `NTDS.dit + SYSTEM`.

## Наш пример: извлекаем записи

Допустим, у нас есть `ntds.dit` и `SYSTEM`. Сначала посмотрим на файл:

```
$ file ntds.dit
ntds.dit: MS Windows ESE database
$ ls -l ntds.dit
-rw-r--r-- 1 analyst analyst 18874368 ntds.dit
```

Восемнадцать мегабайт — типичный небольшой домен. Теперь используем **impacket**:

```
$ secretsdump.py -ntds ntds.dit -system SYSTEM LOCAL
Impacket v0.12 - Copyright ...
[*] Target system bootKey: 0x...
[*] Dumping Domain Credentials (domain\uid:rid:lmhash:nthash)
Administrator:500:aad3b435b51404eeaad3b435b51404ee:nto{ntds_d1t_p3k_unl0ck3d}::::
Guest:501:aad3b435b51404eeaad3b435b51404ee:31d6cfe0d16ae931b73c59d7e0c089c0:::
jdoe:1103:aad3b435b51404eeaad3b435b51404ee:5f4dcc3b5aa765d61d8327deb882cf99:::
[*] Kerberos keys grabbed
```

Мы получили **NTLM-хеши** всех учёток. Формат строки: `имя:RID:LM-хеш:NT-хеш`.
NT-хеш — это то, что нужно для «pass-the-hash»: пароль в открытом виде не требуется.

### Шаг: восстановить имена атрибутов

Если строки выглядят как «пустые», значит парсер не подтянул метаданные. Тогда явно
укажем файл, где лежит соответствие колонок и имён (или используем `-user-status`,
`-history` для дополнительных полей). Например, чтобы выгрузить **историю паролей**
(старые хеши, которые тоже валидны для аутентификации):

```
$ secretsdump.py -ntds ntds.dit -system SYSTEM -history LOCAL
jdoe:1103:...:...:...  (несколько исторических NT-хешей)
```

История паролей важна потому, что многие сервисы не требуют смены пароля сразу —
старый хеш может всё ещё работать.

## Что ещё интересного в NTDS.dit

- **Списки групп** (`linktable`) — членство в `Domain Admins`, `Enterprise Admins`.
- **Атрибут `userAccountControl`** — флаги «пароль не истекает», «учётка отключена»,
  «смарт-карта обязательна».
- **`servicePrincipalName`** — учётки сервисов, уязвимые к Kerberoasting.
- **`msDS-KeyCredentialLink`** — следы атак на «теневые» ключи (Shadow Credentials).
- **`whenCreated` / `whenChanged`** — время появления и правки объектов, полезно для
  таймлайна атаки.

Форензик-ценность NTDS.dit в том, что она даёт **полную картину домена на момент
снятия образа**: какие учётки были, кто в каких группах, когда менялись.

## Если файл «на живую» и заблокирован

Три пути: (1) снять **VSS-снимок** и вытащить NTDS.dit из него; (2) использовать
встроенную утилиту `ntdsutil` (снимок базы); (3) извлечь данные из **памяти** процесса
`lsass.exe`. На офлайн-образе диска вопрос снимается: копируем файл и берём SYSTEM.

## Структура ESE-базы вблизи

NTDS.dit — это файл ESE, и полезно понимать его устройство, чтобы объяснять «почему
нельзя просто прочитать».

- **Страницы (pages).** База разбита на страницы по 8 или 32 КБ. Каждая страница имеет
  заголовок с номером и типом.
- **B-дерево.** Данные хранятся в B-дереве; корень — на фиксированной странице, листья —
  на других. Поэтому «вытащить объекты» без разбора дерева нельзя.
- **Заголовок файла.** Первые байты содержат сигнатуру `0x89ABCDEF` и номер формата
  (version). По нему парсер понимает, как читать страницы.
- **Таблица метаданных.** Специальная таблица `MSysObjects` описывает остальные таблицы
  (имя → номер). Если её пропустить, колонки будут безымянными.

Файл ESE можно открыть и «вживую» через API `esentutl`, но для форензики удобнее
библиотеки `libesedb` (её использует `esedbexport`). Она выгружает таблицы в текст:

```
$ esedbexport -t out ntds.dit
$ ls out/
out.datatable.1.4  out.linktable.1.4  out.sdtable.1.4
```

После этого содержимое таблиц — обычный TSV, который можно фильтровать `grep`/`awk`.

## Атрибуты объектов, важные для расследования

| Атрибут | Что даёт аналитику |
|---------|--------------------|
| `sAMAccountName` | имя учётной записи |
| `userAccountControl` | флаги: отключена, пароль не истекает, смарт-карта |
| `pwdLastSet` | когда последний раз меняли пароль |
| `lastLogonTimestamp` | когда входили последний раз |
| `memberOf` / `linktable` | членство в группах (Domain Admins и т.д.) |
| `servicePrincipalName` | сервисные учётки (цель Kerberoasting) |
| `msDS-KeyCredentialLink` | следы «теневых» ключей (Shadow Credentials) |
| `whenCreated` | когда появился объект (новые учётки = след атакующего) |

Комбинация `whenCreated` + `lastLogonTimestamp` помогает отличить «штатную» учётку от
созданной злоумышленником для закрепления.

## Извлечение без пароля: DCSync и его следы

Если злоумышленник имел права на репликацию, он мог забрать хеши **без** копирования
файла — техникой **DCSync**. Её следы: событие **4662** (доступ к объекту с правом
`Replicating Directory Changes`) в журнале Security DC. Форензик-вывод: ищи 4662 с
непривычного аккаунта — это признак DCSync.

## Частые ошибки

- **Взяли только NTDS.dit.** Без `SYSTEM` хеши остаются зашифрованными.
- **Не тот формат хеша.** Строки могут быть в формате `$NT$`/`$DCC2$` — важно не путать.
- **Пустые LM-хеши.** У современных Windows LM-хеш всегда
  `aad3b435b51404eeaad3b435b51404ee` (значит, LM отключён) — это норма, а не ошибка.
- **Живой файл заблокирован.** На работающем DC файл держит служба; нужен VSS или
  `ntdsutil`.

## Шпаргалка команд

```
# Офлайн-извлечение
secretsdump.py -ntds ntds.dit -system SYSTEM LOCAL
secretsdump.py -ntds ntds.dit -system SYSTEM -history LOCAL   # история паролей

# Экспорт таблиц ESE
esedbexport -t out ntds.dit

# Живой DC: снимок базы
ntdsutil "activate instance ntds" "ifm" "create full C:\\ifm" quit quit

# Kerberoastable-учётки из выгрузки
grep -i servicePrincipalName out.datatable.* | head
```

## Что это даёт в отчёте

По NTDS.dit в отчёте фиксируют: сколько учётных записей затронуто, какие из них
привилегированные, есть ли новые/подозрительные учётки, кто входит в Domain Admins и
какие сервисные учётки уязвимы. Это основа оценки ущерба при компрометации домена.

## Мини-практика: находим скомпрометированные учётки

Продолжим сквозной пример и покажем, как NTDS.dit помогает ответить на главный вопрос
инцидента — **какие учётки были скомпрометированы**.

Допустим, мы уже выгрузили таблицу `datatable` из базы. Первым делом считаем учётные
записи, у которых `userAccountControl` содержит подозрительные флаги. В частности, флаг
`DONT_EXPIRE_PASSWORD` (0x10000) означает «пароль не истекает» — часто так маскируются
сервисные учётки, созданные злоумышленником.

```
$ grep -i 'DONT_EXPIRE_PASSWORD' datatable.txt | wc -l
17
```

Семнадцать учёток с неистекающим паролем — стоит проверить каждую. Далее ищем учётки,
созданные **после** даты инцидента. Атрибут `whenCreated` хранит время в формате
`FILETIME`; его можно отсортировать:

```
$ grep -i 'whenCreated' datatable.txt | sort -k2 | tail -5
whenCreated  2026-03-14 02:11:07   svc_helpdesk2
whenCreated  2026-03-14 02:09:55   backup2
whenCreated  2026-03-15 23:58:01   adm_svc
```

Три учётки, созданные ночью в дни атаки — явный признак закрепления. Дальше проверяем их
членство в группах через `linktable`: если `adm_svc` входит в `Domain Admins`, атака
получила привилегированный доступ.

```
$ grep -i 'adm_svc' linktable.txt
adm_svc -> CN=Domain Admins,CN=Users,DC=corp,DC=local
```

Ещё один приём — сопоставить **историю паролей**. Если у учётки в истории есть старые
хеши, а пароль меняли в дни инцидента, значит, злоумышленник мог пользоваться и старым
хешем. Это важно для полного списка «работающих» секретов.

Наконец, ищем следы техники **Kerberoasting**: учётки с непустым `servicePrincipalName`.
Для каждой такой можно запросить Kerberos-тикет и офлайн подобрать пароль. В отчёте
перечисляем их как потенциально слабые.

Итог практики: NTDS.dit — это не просто «мешок хешей». Из него строится **полная картина
домена на момент снятия**: кто есть кто, кто в привилегированных группах, какие учётки
появились во время атаки и какие пароли всё ещё действительны. Именно это превращает
дамп базы в содержательный вывод для расследования.

## Что мы теперь знаем

- NTDS.dit — доменная база в формате **ESE**, хранит все учётные записи AD.
- Она **зашифрована** через PEK, выводимый из boot key в hive `SYSTEM`.
- Для извлечения нужны **оба файла**: `ntds.dit` и `SYSTEM`.
- `secretsdump.py` выдаёт строки `имя:RID:LM:NT` — NT-хеши годятся для pass-the-hash.
- В базе есть не только хеши, но и членство в группах, SPN, история паролей и тайминги.

## Куда дальше

Мы разобрали главный приз домена — базу учётных записей. Дальше посмотрим на **следы
удалённых сессий RDP**: кто подключался, откуда и что видел на экране. А пока главное
запомни: **NTDS.dit без SYSTEM — просто зашифрованный файл; вместе они дают весь домен**.

## Где пригодится

- **CTF Forensics:** задачи с выгрузкой контроллера домена.
- **DFIR:** оценка масштаба компрометации AD и перечень скомпрометированных учёток.
- **Пентест AD:** извлечение хешей для дальнейшего движения (pass-the-hash).
- **Работа:** форензика серверов, реагирование на инциденты в домене.
