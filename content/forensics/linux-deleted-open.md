## Вопрос, с которого всё начинается

`rm` удалил файл. Но процесс его всё ещё держит открытым — и для ядра файл **не исчез**.
Значит, его можно восстановить, даже не трогая файловую систему. Это один из самых
эффективных приёмов живой форензики Linux.

## Наш пример: удалённый дамп

Предположим, вредоносное ПО скачало нагрузку, запустило её и удалило файл. Но процесс
всё ещё работает.

## Шаг 1: находим открытые удалённые файлы

```
$ ls -l /proc/991/fd | grep deleted
lr-x------ 1 root root 64 Jan 14 03:33 3 -> /opt/.hidden/x (deleted)
lrwx------ 1 root root 64 Jan 14 03:33 5 -> /tmp/payload.bin (deleted)
```

Символические ссылки в `/proc/<pid>/fd` показывают, что дескриптор ведёт на удалённый
файл. Числа слева — номера дескрипторов (3, 5).

## Шаг 2: читаем содержимое

Файл доступен через тот же дескриптор:

```
$ cat /proc/991/fd/5 > /evidence/payload.bin
$ ls -la /evidence/payload.bin
-rw-r--r-- 1 root root 245760 Jan 14 03:34 payload.bin
```

Мы скопировали удалённый файл целиком, не восстанавливая файловую систему. Теперь
его можно проанализировать.

## Шаг 3: lsof для массового поиска

Вручную обходить `/proc` долго. `lsof` делает это за нас:

```
$ sudo lsof +L1
COMMAND   PID USER   FD   TYPE DEVICE SIZE/OFF NLINK    NODE NAME
x         991 root    5    REG  253,0   245760     0  123456 /tmp/payload.bin
```

Флаг `+L1` показывает файлы с числом ссылок меньше 1 — то есть удалённые. Колонка
`NLINK=0` подтверждает.

## Шаг 4: удалённые файлы, которые ещё занимают место

Важно: пока файл открыт, его блоки **не освобождаются**. Значит, `df` может показывать
заполненный диск, хотя `du` не находит виновника:

```
$ df -h / | tail -1
/dev/sda1  50G  49G  1G  98% /
$ sudo lsof +L1 | awk '{s+=$7} END {print s/1024/1024 " MB"}'
820 MB
```

Вот «пропавшие» 820 МБ — это удалённые, но открытые файлы.

## Шаг 5: безопасность

Копируй через `cat`/`cp`, но **не** перезаписывай оригинал и не закрывай процесс, пока
не скопируешь всё — иначе дескриптор исчезнет и файл будет потерян навсегда.

```
$ cp -a /proc/991/fd/5 /evidence/ && sha256sum /evidence/5
```

Сразу считай хеш — для доказательства неизменности.

## Что мы теперь знаем

- Удалённый, но открытый файл жив для ядра и доступен через `/proc/<pid>/fd`.
- `ls -l /proc/<pid>/fd | grep deleted` — точечный поиск.
- `lsof +L1` — массовый поиск удалённых файлов.
- Пока файл открыт, место на диске не освобождается.
- Копируй и хешируй, не закрывая процесс.

## Если не сработало

- Процесс уже завершился? Файл потерян — переходи к восстановлению из ФС (ext4/NTFS).
- Нет прав? Нужен root или CAP_SYS_PTRACE.
- Контейнер? Проверь fd на хосте, если есть доступ.

## Механика: почему файл живёт после rm

В Unix **имя файла** и **сам файл (inode)** — разные вещи. Каталог хранит пары
«имя → номер inode», а inode содержит данные и счётчик ссылок (`nlink`). `rm` делает
`unlink`: удаляет имя и уменьшает `nlink`. Данные освобождаются **только когда `nlink=0`
и нет открытых дескрипторов**. Поэтому пока процесс держит файл открытым, ядро не
освобождает блоки — и файл можно прочитать через `/proc/<pid>/fd/`.

Это делает живую форензику Linux эффективнее: не нужно восстанавливать ФС, файл доступен
напрямую.

## Практика: восстановление пошагово

**1. Найти удалённые, но открытые:**

```
$ ls -l /proc/991/fd | grep deleted
lr-x------ 1 root root 64 Jan 14 03:33 3 -> /opt/.hidden/x (deleted)
lrwx------ 1 root root 64 Jan 14 03:33 5 -> /tmp/payload.bin (deleted)
```

**2. Массовый поиск через lsof:**

```
$ sudo lsof +L1
COMMAND   PID USER   FD   TYPE DEVICE SIZE/OFF NLINK    NODE NAME
x         991 root    5    REG  253,0   245760     0  123456 /tmp/payload.bin
```

`+L1` = «число ссылок меньше 1», `NLINK=0` подтверждает удаление.

**3. Скопировать содержимое, не трогая оригинал:**

```
$ cp -a /proc/991/fd/5 /evidence/payload.bin
$ sha256sum /evidence/payload.bin
```

**4. Проверить, что блоки «пропали» из учёта:**

```
$ df -h / | tail -1
/dev/sda1  50G  49G  1G  98% /
$ sudo lsof +L1 | awk '{s+=$7} END {print s/1024/1024 " MB"}'
820 MB
```

Разница между `df` и `du` — это удалённые открытые файлы.

## Зачем это нужно при расследовании

- **Забрать нагрузку до её исчезновения** — малварь часто `unlink`-ает свой бинарник,
  чтобы замести следы, но продолжает работать из памяти.
- **Понять, что делал процесс** — читая конфиги/данные, которые он держит открытыми.
- **Найти «пропавшее» место** — диск полон, а `du` не находит виновника.
- **Собрать улики, не останавливая систему** — копирование через `/proc` не изменяет
  состояние и не мешает работе.

## Смежные артефакты /proc

Помимо `fd`, в `/proc/<pid>/` есть:

- `exe` — путь к исполняемому файлу (симлинк; `(deleted)` — бинарник удалён);
- `cwd` — рабочий каталог процесса;
- `maps` — отображённые в память файлы (в т.ч. удалённые библиотеки);
- `cmdline` — аргументы запуска (разделены `\0`);
- `environ` — переменные окружения (часто секреты);
- `root` — корень ФС процесса (для контейнеров — свой).

Удалённые **библиотеки** тоже можно достать: `cp /proc/991/map_files/<range> ...`.

## Ограничения

- **Процесс нужно поймать живым** — после его смерти дескрипторы исчезают, и файл теряется
  (если не восстановить с диска).
- **Не перезаписывать оригинал** — `>` вместо `cp` испортит файл.
- **Права root** — без них чужие `/proc/<pid>/fd` не читаются.
- **Файл может быть разреженным/большим** — `cp` корректно читает содержимое, но размер
  может отличаться от «занятого на диске».
- **Контейнеры** — `/proc` хоста видит процессы в других namespace иначе; для контейнера
  смотри его `/proc` внутри namespace.
- **Хеш сразу** — для доказательства неизменности фиксируй `sha256sum` при копировании.

## Практический чеклист

1. `lsof +L1` — все удалённые открытые файлы.
2. `ls -l /proc/<pid>/fd | grep deleted` — по конкретному процессу.
3. Скопировать через `cp`/`cat`, **не** перезаписывая оригинал.
4. Сразу `sha256sum` — зафиксировать целостность.
5. Проверить `df` vs `lsof +L1` — найти «пропавшее» место.
6. Заглянуть в `maps`/`map_files` — удалённые библиотеки.
7. Не убивать процесс, пока не скопировано всё.

## Сценарий: забираем малварь до её исчезновения

Типовой инцидент: система «странно себя ведёт», процесс висит, файл удалён. Пошагово:

**1. Находим подозрительный процесс:**

```
$ ps aux | sort -k3 -rn | head -3
root       991  0.0  0.1  x  x  ?  S  Jan14  0:02 /opt/.hidden/x
```

**2. Смотрим его открытые файлы:**

```
$ sudo ls -l /proc/991/fd | grep -E 'deleted|\.so'
lrwx------ 1 root root 64 ... 5 -> /tmp/payload.bin (deleted)
lr-x------ 1 root root 64 ... 7 -> /usr/lib/.libs/libx.so.1 (deleted)
```

**3. Копируем всё, не останавливая процесс:**

```
$ mkdir -p /evidence/991
$ sudo cp -a /proc/991/fd/5 /evidence/991/payload.bin
$ sudo cp -a /proc/991/exe   /evidence/991/exe   # даже если (deleted)
$ sudo sha256sum /evidence/991/*
```

**4. Забираем удалённые библиотеки из maps:**

```
$ sudo grep -i 'deleted' /proc/991/maps
$ sudo cp /proc/991/map_files/7f...-7f... /evidence/991/libx.so.1
```

**5. Только теперь можно анализировать** — `strings`, дизассемблирование, AV.

## Почему `cp`/`cat`, а не восстановление ФС

Восстановление удалённых файлов с диска (extundelete, PhotoRec) работает, но:

- требует **остановки** ФС (unmount) — иначе запись перезапишет блоки;
- даёт фрагментированный, иногда неполный результат;
- **не** работает, если блоки ещё заняты открытым процессом.

Чтение через `/proc` даёт **точную, актуальную** копию файла, который процесс реально
использует — это и быстрее, и надёжнее для живого анализа.

## Временная шкала дескриптора

Дескриптор живёт ровно столько, сколько процесс его держит. Это задаёт **окно**, в
котором данные доступны:

- файл удалён в 03:31, процесс держит его — данные живы;
- процесс завершился в 03:40 — данные освобождены, `/proc` пуст;
- если файл был закэширован — часть может остаться, но гарантий нет.

Поэтому при обнаружении малвари **сначала копируем, потом изолируем**.

## Ограничения

- **Нужен root** — чужие дескрипторы не читаются без привилегий.
- **Процесс жив** — после смерти дескриптор исчезает.
- **Большие файлы** — `cp` может идти долго; следи за свободным местом.
- **Разреженные файлы** — размер может не совпасть с занятым местом.
- **Контейнеры** — смотри `/proc` внутри нужного namespace.
- **Не перезаписывай** — `>` вместо `cp` уничтожит содержимое дескриптора.

## Практический чеклист

1. `lsof +L1` — найти все удалённые открытые файлы.
2. Скопировать через `cp`/`cat` в отдельный каталог.
3. Забрать `exe`, `cwd`, `maps`, `map_files`.
4. Сразу `sha256sum` — зафиксировать улику.
5. Проверить `df` vs `lsof +L1` — «пропавшее» место.
6. Копировать **до** изоляции/убийства процесса.
7. Помнить: восстановление с диска требует unmount, `/proc` — нет.

## Итог в одну фразу

Удалённый, но открытый файл — это улика, которая живёт, пока её держит процесс: `rm`
убирает только имя, а inode с данными остаётся, потому что счётчик ссылок не достиг нуля.
Поэтому правило живой форензики Linux простое: **увидел удалённый открытый файл — скопируй
его через `/proc/<pid>/fd` и посчитай хеш, не останавливая процесс**. Это дешевле, быстрее
и надёжнее восстановления с диска.
