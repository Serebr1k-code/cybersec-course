## Вопрос, с которого всё начинается

В прошлом уроке мы научились копировать файл и смотреть его тип командой `file`.
Но что если `file` отвечает невнятно? Или картинка, которую ты точно видел рабочей,
вдруг не открывается?

Вот пример из жизни: тебе дали `logo.png`, но любой просмотрщик ругается «не удалось
открыть». Размер нормальный, имя нормальное — а файл «сломан». Этот урок — про то,
как заглянуть внутрь файла на уровне байтов, понять, что именно сломано, и починить.
Заодно узнаем, почему `file` вообще понимает тип файла.

## Наш пример: logo.png, который «не открывается»

Первая команда — та же, что и всегда:

```bash
$ file logo.png
logo.png: data
```

`data` — это ответ «я не знаю, что это». Странно: расширение `.png`, а тип не опознан.
Значит, что-то не так с самым началом файла. Смотрим первые байты:

```bash
$ xxd -l 16 logo.png
00000000: 8950 4e47 0a0d 1a0a 0000 000d 4948 4452  .PNG........IHDR
```

`xxd` показывает файл как таблицу: слева — смещение (адрес) байта, в середине —
hex-значения, справа — те же байты как символы. Мы видим `89 50 4e 47` — а справа
читается `.PNG`. Почти правильно!

Обрати внимание на две вещи. Первая: справа символы печатаются только для читаемых
байтов, остальные заменены точками — по правой колонке удобно ловить текстовые
вставки (`PK`, `%PDF`, `IHDR`). Вторая: смещения слева — шестнадцатеричные, то есть
`00000010` — это байт 16, а не десять. Эта привычка к hex-адресам понадобится
дальше, когда будем считать, где именно спрятаны данные.

## Что такое магические байты

**Магические байты** (или сигнатура) — это несколько первых байтов файла, которые
жёстко закреплены за его форматом. У PNG они такие:

```
89 50 4E 47 0D 0A 1A 0A
```

Это `\x89`, затем буквы `P N G`, затем два специальных символа перевода строки
`\r \n` (`0D 0A`), затем `1A 0A`. Именно по этой последовательности `file` и узнаёт
PNG — независимо от расширения.

А теперь посмотрим на наш файл ещё раз: `89 50 4e 47` **`0a 0d`** `1a 0a`. Байты
`0D 0A` поменяны местами — получилось `0A 0D`. Один неверный байт в сигнатуре —
и `file` уже не понимает файл.

Откуда `file` знает сигнатуры? Из базы `/usr/share/misc/magic.mgc`. Полезные флаги:

```bash
$ file -i logo.png          # показать MIME-тип: image/png
$ file -k logo.png          # не останавливаться на первом совпадении
$ file -b logo.png          # только тип, без имени файла
```

Флаг `-k` важен: он заставляет `file` показать **все** совпадения, а не только первое.
Пригодится чуть позже.

## Чиним заголовок

Файл-то целый, испорчены только 2 байта сигнатуры. Запишем правильную сигнатуру в
начало копии:

```bash
$ printf '\x89PNG\r\n\x1a\n' | dd of=logo.png bs=1 count=8 conv=notrunc status=none
$ file logo.png
logo.png: PNG image data, 8 x 8, 8-bit/color RGB, non-interlaced
```

Готово: `file` опознал PNG. Разберём команду: `printf` печатает нужные 8 байт,
`dd` копирует их в файл, `bs=1` — «работай по одному байту», `count=8` — «ровно 8 байт»,
`conv=notrunc` — «не обрезай файл после записи» (иначе от PNG остались бы 8 байт).

Приём «поправить сигнатуру в копии» — классика CTF. Файл выглядит сломанным только
из-за первого байта.

## Сюрприз: внутри PNG оказался ZIP

Мы починили картинку. Но проверим её флагом `-k` — вдруг есть вторая сигнатура?

```bash
$ file -k logo.png
logo.png: PNG image data, 8 x 8, 8-bit/color RGB, non-interlaced\012-  Zip archive, with extra data prepended\012- data
```

Три совпадения через `\012-` (это просто перевод строки). Файл одновременно PNG **и**
ZIP — такой файл называют **полиглотом**: он валиден сразу для нескольких форматов.
Картинка читается, а после её конца дописан ZIP-архив.

Найдём смещение ZIP-сигнатуры (`PK\x03\x04`) внутри файла:

```bash
$ grep -aboP 'PK\x03\x04' logo.png
75:PK
```

`-a` — «считать файл текстом даже если он бинарный», `-b` — «напечатать байтовое
смещение», `-o` — «показать только совпадение», `-P` — «понимать `\xNN` как байт».
Ответ: ZIP начинается на байте **75**.

## Вырезаем встроенный архив

Осталось отрезать ZIP, начиная с байта 75:

```bash
$ dd if=logo.png of=hidden.zip bs=1 skip=75 status=none
$ unzip -o hidden.zip -d hidden/
Archive:  hidden.zip
  extracting: hidden/secret.txt
$ cat hidden/secret.txt
CTF{mag1c_byt3s}
```

`skip=75` — пропустить 75 байт PNG-заголовка, дальше писать в `hidden.zip`. Мы
достали флаг, не имея ни имени, ни структуры архива — только по сигнатуре.

## Шпаргалка: частые сигнатуры

Эти байты стоит узнавать с первого взгляда — они встречаются в задачах постоянно:

| Формат | Сигнатура (hex) | Как читается |
|--------|-----------------|--------------|
| PNG | `89 50 4E 47 0D 0A 1A 0A` | `.PNG....` |
| JPEG | `FF D8 FF` (конец `FF D9`) | — |
| GIF | `47 49 46 38` | `GIF8` |
| PDF | `25 50 44 46` | `%PDF` |
| ZIP/JAR/DOCX | `50 4B 03 04` | `PK..` |
| RAR | `52 61 72 21 1A 07` | `Rar!..` |
| 7z | `37 7A BC AF 27 1C` | `7z..` |
| gzip | `1F 8B 08` | — |
| ELF (Linux) | `7F 45 4C 46` | `.ELF` |
| PE/EXE (Windows) | `4D 5A` | `MZ` |
| SQLite | `53 51 4C 69 74 65 20 66 6F 72 6D 61 74 20 33` | `SQLite format 3` |

Заметь: у ZIP и его «родственников» (JAR, DOCX, XLSX) одна и та же сигнатура
`PK\x03\x04` — потому что Office-документы и Java-архивы это и есть ZIP-контейнеры
с особым содержимым.

## Триаж: проверяем много файлов сразу

В реальной задаче файлов может быть сотни. Проверять их по одному неудобно, поэтому
`file` умеет работать по списку и в машинном формате:

```bash
$ find ./evidence -type f -print0 | xargs -0 file -b > types.txt
$ cut -d: -f2 types.txt | sort | uniq -c | sort -rn | head
     42 PNG image data
     11 Zip archive data
      3 ELF 64-bit LSB executable
```

Первая команда собирает список всех файлов и прогоняет их через `file -b` (только
тип, без имени). Вторая — считает, каких типов больше всего. Так за секунду видно,
что «среди фотографий затесались три исполняемых файла» — типичный сигнал атаки.

Запомним главное: файл — это не имя, а байты. Имя можно сменить, а сигнатура останется.

## Что мы теперь знаем

- Магические байты — первые байты файла, по ним определяется формат.
- `file` — это гипотеза, `xxd` — доказательство; смотри сигнатуру глазами.
- Один испорченный байт в сигнатуре ломает распознавание — лечится записью верных байт.
- `file -k` показывает все сигнатуры: файл может быть «полиглотом».
- `grep -aboP` находит смещение сигнатуры, `dd skip=` вырезает по нему встроенные данные.

## Куда дальше

Мы научились находить и вырезать встроенные данные вручную. В следующем уроке
возьмём более крупный объект — образ или прошивку с несколькими вложенными
форматами сразу — и научимся извлекать их пачкой через `binwalk` и `foremost`,
не разыскивая каждое смещение вручную. А пока запомни: **тип файла живёт в первых
байтах, а не в расширении**.

## Где пригодится

- **CTF:** половина задач Forensics решается на этом шаге.
- **Malware analysis:** определение истинного формата образца — первый шаг.
- **SOC:** триаж подозрительных вложений из почты.
- **Pentest:** анализ дампов и необычных файлов на скомпрометированных хостах.
- **Восстановление данных:** понимание структур при работе с повреждёнными носителями.
