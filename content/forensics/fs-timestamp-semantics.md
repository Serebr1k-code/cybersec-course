## Вопрос, с которого всё начинается

В отчёте у тебя есть метка времени файла из `$MFT`: «создан 2020-01-01». Но подозреваемый
мог её подделать. Как понять, что метка времени не родная? Ответ даёт NTFS: она хранит
**две независимые копии** времени для одного файла, и их расхождение — след подделки.

## Что такое SI и FN

У каждой записи в `$MFT` (Master File Table) есть набор **атрибутов**. Два из них хранят
метки времени:

- **`$STANDARD_INFORMATION` (SI)** — основной набор атрибутов. Внутри лежат четыре времени
  файла: создание, изменение, изменение записи MFT и доступ. Это то, что показывают
  Проводник и `dir`.
- **`$FILE_NAME` (FN)** — атрибут имени файла. В нём тоже четыре времени, и они относятся к
  моменту, когда этот конкретный **имя-указатель** был создан или изменён.

Смысл двойного хранения — в истории. У одного файла может быть **несколько** атрибутов
`$FILE_NAME` (жёсткие ссылки, короткие имена 8.3, разные родительские каталоги), но ровно
один SI. Сравнивая SI и FN, аналитик восстанавливает, что происходило с файлом.

## Наш пример: запись MFT с подозрительным временем

Разберём дамп одной записи MFT, сохранённый в текстовом виде:

```
$ ls -la
-rw-r--r-- 1 student student 1024 mft.rec
$ strings mft.rec | grep -Ei 'SI|FN|created|modified'
SI  created=2020-01-01 00:00:00  modified=2020-01-01 00:00:00
FN  created=2026-03-11 02:14:09  modified=2026-03-11 02:14:09
NOTE: SI backdated; real creation in FN
EVIDENCE: nto{ntfs_s1_vs_fn_t1m3st0mp}
```

Видишь картину: SI говорит «файл из 2020 года», а FN — «март 2026». Одно из двух —
подделка. Поскольку SI меняется штатным API (`SetFileTime`), а FN — только ядром при
изменении имени, **типичный timestomp подделывает SI, но забывает FN**. Отсюда правило:
**FN обычно честнее SI**, и расхождение в сторону «SI раньше FN» — красный флаг.

## Шаг 1: кто обновляет какие метки

Понимание «кто пишет» — ключ к интерпретации:

| Событие | SI | FN |
|---------|----|----|
| Создание файла | обновляется | обновляется |
| Запись данных | изменяется | не трогается |
| Переименование / смена родителя | изменяется | обновляется |
| `SetFileTime` (API) | изменяется | **не трогается** |
| Копирование с сохранением времени | изменяется | обновляется |

Главное следствие: **пользовательский инструмент может менять SI, но не FN**. Значит, FN —
более надёжный источник для «когда файл реально появился на этом томе».

## Шаг 2: точность меток

Ещё одна тонкость — **разрешение**. В NTFS времена хранятся в формате **FILETIME**: 64-бит,
число 100-наносекундных интервалов с 1601 года. Но атрибут FN хранит время с точностью до
**10 миллисекунд** (округление). Поэтому:

- SI и FN могут расходиться на доли миллисекунды **штатно** — это не подделка;
- расхождение на минуты/часы/годы — уже подозрительно;
- «слишком ровные» значения (00:00:00, секунды заканчиваются на 0) — типичный признак
  подделки через `SetFileTime`.

## Шаг 3: что искать при разборе

Рабочий чек-лист:

- **SI created < FN created.** SI «старше» FN — классический backdating: подделали SI в
  прошлое, FN остался настоящим.
- **SI created > FN created.** Бывает при копировании файла с сохранением времени: FN
  обновился, SI скопировали.
- **Нулевые времена.** SI = 0 или 1601-01-01 — программа-обнулятор.
- **Одинаковые все четыре.** Все времена равны секунда-в-секунду — подозрительно.
- **Рассинхрон с USN.** Если `$UsnJrnl` показывает создание позже FN — что-то не так.

## Шаг 4: инструменты

- **MFTECmd** — парсит `$MFT` и выводит обе группы времени рядом в CSV;
- **analyzeMFT** — Python-парсер с полями SI/FN;
- **`mft2csv` / `mftparser`** (плагин Volatility) — из дампа памяти;
- **The Sleuth Kit `istat`** — показывает обе шкалы для inode;
- **`timestomp` (Metasploit)** — атакующий инструмент; полезно знать, что он меняет.

Пример `istat`:

```
$ istat image.dd 42
...
Standard Information:
    Created: 2020-01-01 00:00:00
    File Modified: 2020-01-01 00:00:00
File Name:
    Created: 2026-03-11 02:14:09
    File Modified: 2026-03-11 02:14:09
```

## Шаг 5: как это выглядит в таймлайне

В таймлайне (plaso/Timesketch) обе группы обычно попадают отдельными событиями. Это
плюс: видно, что «создание» произошло дважды в разное время. При построении нарратива
используй **FN-время как «реальное появление»**, а SI-время — как «заявленное». Расхождение
само становится отдельным событием «возможный timestomp».

## Мини-практика: собрать доказательство подделки

Пусть у тебя есть запись MFT и `$UsnJrnl`. Порядок:

```
$ MFTECmd.exe -f '$MFT' --csv out
$ grep -i target out/*.csv
SI.Created,2020-01-01 00:00:00,FN.Created,2026-03-11 02:14:09
```

Мы получили оба времени для одного файла. Дальше сопоставляем с `$UsnJrnl`: там должна
быть запись `FILE_CREATE` на 2026-03-11 02:14:09. Если SI утверждает 2020, а два других
источника — 2026, вывод однозначен: **SI подделан**. Три источника, два против одного —
это уже не «возможно», а «подтверждено».

## Частые ошибки и подводные камни

- **Считать SI истиной.** SI — самый простой для подделки источник.
- **Игнорировать несколько FN.** У файла бывает несколько `$FILE_NAME`; сравнивай все.
- **Путать MFT-изменение и файловое.** «MFT modified» — это изменение записи, а не данных.
- **Округление FN.** Расхождение в миллисекунды — норма, а не след.
- **Часовой пояс.** NTFS хранит время в UTC; неверный пояс сдвинет всё на часы.

## Что мы теперь знаем

- NTFS хранит время дважды: в SI (легко менять) и FN (меняет ядро).
- Расхождение SI и FN — основа обнаружения timestomping.
- FILETIME — 100-нс интервалы с 1601 года; FN округляет до 10 мс.
- «SI раньше FN» — типичный признак backdating.
- Инструменты: MFTECmd, analyzeMFT, `istat`, Volatility mftparser.

## Почему атрибутов $FILE_NAME бывает несколько

У одного файла может быть **несколько** атрибутов `$FILE_NAME`, и это не ошибка:

- **жёсткие ссылки (hard links)** — один файл под несколькими именами в разных каталогах;
- **короткое имя 8.3** — DOS-совместимое имя для программ, не понимающих длинные имена;
- **перемещение между каталогами** — при перемещении создаётся новый указатель.

Каждый атрибут `$FILE_NAME` имеет **свои** метки времени. Это даёт больше зацепок: если
файл переименовали, старый `$FILE_NAME` может хранить время **до** переименования. Сравнивая
все FN между собой и с SI, ты можешь восстановить историю имени:

```
FN(short)  created=2026-03-11 02:14:09  name=EVIDEN~1.ZIP
FN(long)   created=2026-03-11 02:14:09  name=evidence.zip
SI         created=2020-01-01 00:00:00
```

Короткое и длинное имя созданы одновременно — это нормально. А вот SI, откатанный в 2020,
выбивается из ряда.

## Часовые пояса и FILETIME на практике

NTFS хранит время в **UTC**, а инструменты показывают его либо в UTC, либо в локальном
поясе — и это источник ошибок при построении таймлайна. Правила:

- **всегда фиксируй пояс**, в котором снят образ и в котором выведен отчёт;
- при сопоставлении с логами (EVTX, syslog) приводи всё к **одному поясу**;
- учитывай переходы на летнее время: файл, «созданный» в несуществующий час, — признак
  подделки или ошибки настроек;
- FILETIME не хранит пояс — только абсолютное число интервалов с 1601-01-01 UTC.

Если сомневаешься, переведи FILETIME в Unix-время вручную и сверь с двумя источниками.
Расхождение часов на хосте (clock skew) — отдельная тема, но она тоже искажает сравнение.

## Итоговая таблица признаков подделки

Соберём признаки в одну шпаргалку — она пригодится при разборе любого `$MFT`:

| Признак | Вероятная интерпретация |
|---------|-------------------------|
| SI created << FN created | backdating SI (timestomp) |
| SI created >> FN created | копирование с сохранением времени |
| SI = 1601-01-01 / 0 | обнуление меток программой |
| все четыре времени равны | подозрительно «ровное» значение |
| FN создан раньше SI, но позже USN | рассинхрон источников |
| нет FN при наличии SI | повреждённая/неполная запись MFT |

Держи эту таблицу рядом с `MFTECmd` — она экономит время и делает выводы
воспроизводимыми. Помни: один признак — повод присмотреться, два совпавших — уже основание
для вывода в отчёте.

## Практика: вывод обеих меток одним запросом

`MFTECmd` или `analyzeMFT` показывают `$STANDARD_INFORMATION` (SI) и `$FILE_NAME` (FN)
рядом, и расхождение бросается в глаза:

```
$ MFTECmd -f '$MFT' --csv /tmp --csvf mft.csv
$ python3 - <<'EOF'
import csv
for r in csv.DictReader(open('/tmp/mft.csv')):
    if 'evil' in r.get('FileName','').lower():
        print('SI mtime', r['Created0x10'], 'FN mtime', r['Created0x30'])
EOF
SI mtime 2024-03-11T18:22:04  FN mtime 2024-03-11T18:22:04
```

Если SI-метка моложе, чем FN, — файл трогали после создания (типично для затирания
таймстемпов). Если SI старее — это артефакт копирования с сохранением меток.

## Как выглядит «затирание» на практике

Классический `timestomp` меняет SI-метки, но не трогает FN (его нельзя изменить через
обычные API). Поэтому правило простое:

| Признак | SI | FN | Вывод |
|---------|----|----|-------|
| SI новее FN | 2024-03-11 | 2020-01-02 | SI подделана |
| SI и FN совпадают | X | X | похоже на правду |
| FN отсутствует | X | — | файл удалён, запись в $MFT осталась |
| FN «правильнее» SI | X | 2020 | сравните с $UsnJrnl |

## Практика: связка с $UsnJrnl и $LogFile

SI/FN — не единственные источники. `$UsnJrnl` пишет журнал изменений (кто и что менял), а
`$LogFile` — транзакции NTFS. Сверка даёт «второе мнение» о времени:

```
$ MFTECmd -f '$Extend\$UsnJrnl:$J' --csv /tmp --csvf usn.csv
$ grep -i evil /tmp/usn.csv | head
2024-03-11 18:22:04,USN_REASON_DATA_OVERWRITE,...,evil.exe
```

Если `$UsnJrnl` показывает изменение, которого нет в SI, — метки затирали.

## Если не сработало

- **Все метки совпадают.** Иногда вредонос не затирает время — тогда смотрите на аномалию
  *расположения* (файл в `System32` с датой сборки ОС) и на источник (`Zone.Identifier`).
- **Инструмент показывает пустые FN.** Антивирус или драйвер мог обнулить FN-атрибут;
  проверьте `$MFT` напрямую.
- **Файл на другом томе.** У каждого тома свой `$MFT`, `$UsnJrnl` и `$LogFile` — не смешивайте
  их в одном таймлайне без указания тома.

## Ограничение: точность и часовые пояса

FILETIME хранится в UTC с шагом 100 нс, но многие инструменты показывают локальное время, а
некоторые — «наивно». Одна и та же метка может выглядеть сдвинутой на несколько часов при
разборе в разных утилитах. Всегда фиксируйте, в каком поясе и в каком формате вывели время,
иначе вывод о подделке будет ложным.

## Куда дальше

Мы разобрали двойную шкалу времени NTFS. Дальше заглянем в **сжатие и разрежённые файлы** —
там данные выглядят «отсутствующими», но на деле упакованы. А пока главное запомни: **FN
честнее SI, и расхождение — это доказательство**.

- **Anti-forensics detection:** оценка достоверности меток.
- **Реверс-инжиниринг:** понимание, что меняет инструмент timestomp.
