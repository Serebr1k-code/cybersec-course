## Вопрос, с которого всё начинается

Нам передали файл `win10.vmdk` — диск виртуальной машины, снятый с гипервизора. Внутри должна быть Windows с уликами. Пробуем привычное: `mmls win10.vmdk` — и ничего, «unknown format». Что не так?

Дело в том, что виртуальный диск — это **не** сырой набор секторов, а контейнер с метаданными, сжатием и снапшотами. Прежде чем разбирать файловую систему, контейнер надо развернуть. Разберём диск от определения формата до чтения файлов.

## Наш пример: файл `win10.vmdk`

Начинаем с определения формата. Инструмент `qemu-img` умеет читать почти все форматы виртуальных дисков:

```bash
$ qemu-img info win10.vmdk
image: win10.vmdk
file format: vmdk
virtual size: 60 GiB (64424509440 bytes)
disk size: 24 GiB
cluster_size: 65536
```

Читаем: формат — **VMDK** (диск VMware), виртуальный размер 60 ГиБ, а файл на диске занимает 24 ГиБ. Разница как раз из-за **sparse**-формата: пустые области не хранятся физически. Каждый формат имеет свою «магию» в начале файла — QCOW2 начинается с `QFI`, VHD помечает себя строкой `conectix` в конце, VHDX — `vhdxfile`, VDI — текстовой строкой Oracle.

## Шаг 1: проверяем цепочку снапшотов

Прежде чем конвертировать, убеждаемся, что диск **самодостаточен**. У виртуальных дисков бывают **снапшоты** (снимки состояния) в виде **дельт** — отдельных файлов, где хранятся только изменения. Если конвертировать только верхний дельта-диск без базового, получишь неполную картину.

```bash
$ cat win10.vmdk | grep -E 'parentCID|createType'
createType="monolithicSparse"
parentCID=ffffffff
```

`parentCID=ffffffff` означает, что родителя **нет** — это самостоятельный монолитный диск. Если бы здесь стоял другой CID, диск был бы дельтой и пришлось бы собирать всю цепочку. Для QCOW2 то же самое показывает `qemu-img info --backing-chain`.

## Шаг 2: разворачиваем в сырой образ

Инструменты форензики (sleuthkit: `mmls`, `fls`, `icat`) понимают только **сырой** образ — просто последовательность секторов. Поэтому контейнер конвертируют:

```bash
$ qemu-img convert -O raw win10.vmdk win10.raw
$ ls -l win10.raw
-rw-r--r-- 1 user user 64424509440 win10.raw
```

Ключ `-O raw` задаёт выходной формат. Теперь `win10.raw` — обычный диск, и с ним работает весь привычный инструментарий:

```bash
$ mmls win10.raw
       Slot      Start        End          Length       Description
      00:  -----   0000000000   0000002047   0000002048   Primary Table (#0)
      01:  00:00   0000002048   0000124927   0000122880   NTFS / exFAT (0x07)
```

Появилась карта разделов: есть NTFS-раздел со смещения 2048. Дальше — как обычно:

```bash
$ fls -o 2048 -r win10.raw | head -3
r/r 5-128-1: $AttrDef
```

Файловая система читается. Контейнер перестал мешать.

## Шаг 3: монтирование без конвертации

Конвертация 60 ГиБ — долго и занимает место. Иногда удобнее **смонтировать диск напрямую** как блочное устройство. Для этого есть `qemu-nbd` — он отдаёт виртуальный диск через сетевое блочное устройство (NBD):

```bash
$ sudo modprobe nbd max_part=16
$ sudo qemu-nbd -c /dev/nbd0 --read-only win10.vmdk
$ sudo mmls /dev/nbd0
$ sudo mount -o ro /dev/nbd0p1 /mnt/vm
```

Флаг `--read-only` обязателен: без него система может что-то записать на диск и изменить улику. Аналогично, для VHD/VHDX удобен набор `libguestfs`, который сам определяет формат:

```bash
$ virt-filesystems -a disk.vhdx --all --long
$ virt-copy-out -a disk.qcow2 /etc/shadow ./out/
```

`virt-copy-out` особенно удобен, когда нужен один файл, а монтировать весь диск не хочется.

## Шаг 4: работа со снапшотами

Если диск — часть цепочки снапшотов, её нужно «склеить». Для QCOW2 помогает `--backing-chain`:

```bash
$ qemu-img info --backing-chain disk.qcow2
$ qemu-img convert -O raw disk-snapshot.qcow2 merged.raw
```

`qemu-img convert` сам подтянет базовые диски из цепочки и соберёт полный образ. У VHDX (Hyper-V) снапшоты (checkpoint) хранятся как отдельные `.avhdx`-дельты; их собирают через `guestfish --ro -a base.vhdx -a delta.avhdx`.

## Шаг 5: проверяем целостность и хеш

Перед конвертацией полезно проверить сам контейнер — QCOW2 умеет это делать:

```bash
$ qemu-img check disk.qcow2
No errors were found on the image.
```

А после конвертации обязательно посчитать хеш **сырого** образа — это докажет целостность улики (мы разбирали хеширование в `forensics-chain-custody`):

```bash
$ sha256sum win10.raw
```

## Полный разбор: от дескриптора до сырого образа

Соберём весь путь по нашему `win10.vmdk` в одну цепочку — так видно, зачем каждый шаг.

| Шаг | Команда | Результат |
|-----|---------|-----------|
| Определить формат | `file win10.vmdk` | `VMware4 disk image` |
| Увидеть цепочку | `cat win10.vmdk` (дескриптор) | список parent-дисков |
| Свести снапшоты | `qemu-img convert` | один сырой `disk.raw` |
| Смонтировать | `qemu-nbd` + `mount` | доступ к разделам |
| Проверить | `sha256sum` | целостность образа |

Ключевая мысль: VMDK — это **не один файл**, а описание плюс цепочка. Монолитный образ — один файл; sparse — растущий; при снапшотах появляются дочерние файлы, и без сведения цепочки вы увидите лишь «дельту» изменений, а не диск.

## Форматы в сравнении

| Формат | Кто использует | Магия (сигнатура) | Особенность |
|--------|----------------|-------------------|-------------|
| VMDK | VMware | `KDMV` | дескриптор + снапшоты |
| VHD | Microsoft | `conectix` | фиксированный размер |
| VHDX | Hyper-V | `vhdxfile` | до 64 ТБ, журнал |
| QCOW2 | QEMU/KVM | `QFI\xfb` | сжатие, backing-файлы |
| VDI | VirtualBox | `<<< Oracle VM VirtualBox Disk Image >>>` | фиксированный/динамический |

Магию видно в первых байтах: `xxd -l 16 disk.img`. Это и есть надёжное определение формата, независимое от расширения.

## Если не сработало

- **`qemu-img` ругается на цепочку.** Убедитесь, что все родительские файлы на месте и имена в дескрипторе совпадают; иначе снапшоты не собрать.
- **Монтируется пустой диск.** Разделы лежат со смещением — используйте `mmls`/`fdisk -l` и `mount -o offset=`.
- **Образ «только для чтения».** Для изменения копии применяйте `qemu-nbd --read-only`, а оригинал держите нетронутым.
- **VHDX не читается.** `qemu-img` поддерживает не все версии; используйте `libvhdi`/`vhdiinfo`.
- **Хеш не совпал.** Скорее всего, снимали с «живого» диска — повторите на выключенной ВМ.

## Защита и практика

- Всегда работайте на **копии**, оригинал храните read-only.
- Фиксируйте дескриптор VMDK (он текстовый) в отчёт — там видна вся цепочка.
- Для больших sparse-образов считайте фактический размер (`qemu-img info`), а не «виртуальный».

## Что мы теперь знаем

- Виртуальный диск — контейнер с метаданными, а не сырые сектора; инструменты ФС его не понимают.
- Формат определяют по магии и через `qemu-img info`: VMDK, QCOW2 (`QFI`), VHD (`conectix`), VHDX (`vhdxfile`), VDI.
- Перед конвертацией проверяют **цепочку снапшотов** (родитель/backing); дельта без родителя неполна.
- `qemu-img convert -O raw` даёт сырой образ для sleuthkit; `qemu-nbd` позволяет смонтировать без конвертации.
- `--read-only` обязателен везде, где поддерживается, чтобы не изменить улику.
- `libguestfs` (`virt-filesystems`, `virt-copy-out`) работает с форматами напрямую.

## Куда дальше

Мы развернули виртуальный диск и добрались до файловой системы. В следующем уроке (`forensics-write-blockers`) мы разберём защиту носителей от записи — ключевой элемент корректного снятия образов.
