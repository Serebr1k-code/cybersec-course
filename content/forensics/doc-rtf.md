## Вопрос, с которого всё начинается

RTF — «Rich Text Format», текстовый формат с разметкой. Его легко создать и он
поддерживает **встроенные объекты**, поэтому часто используется для доставки
эксплойтов. Разберём.

## Наш пример: подозрительный .rtf

## Шаг 1: это текст

```
$ file invoice.rtf
invoice.rtf: Rich Text Format data
$ head -c 200 invoice.rtf
{\rtf1\ansi ...
```

RTF читается как текст, но внутри — управляющие последовательности (`\objdata`, `\object`).

## Шаг 2: встроенный OLE-объект

Ключевое — `\object` + `\objdata`, где лежит OLE-объект в hex:

```
{\object\objemb{\*\objclass Package}\objw100\objh100
{\*\objdata 0105000002000000...}}
```

`objclass Package` — встроенный файл (например, `.exe`). `\objdata` — его hex-представление.

## Шаг 3: извлекаем

```
$ python3 -c "import re;d=open('invoice.rtf').read();h=re.search(r'objdata ([0-9a-fA-F]+)',d).group(1);open('obj.bin','wb').write(bytes.fromhex(h))"
$ file obj.bin
obj.bin: OLE 2 Compound Document
```

Дальше разбираем OLE-объект.

## Шаг 4: эксплойты

RTF известен эксплойтами (например, Equation Editor, OLE-уязвимости). Признаки:

- большие `\objdata` блоки;
- ссылки на уязвимые объекты;
- `\objupdate` (авто-обновление).

## Шаг 5: что искать

- встроенные OLE-объекты;
- hex-блоки (`\objdata`);
- внешние ссылки;
- необычно большой RTF.

## Что мы теперь знаем

- RTF — текстовый формат с разметкой.
- `\object`/`\objdata` несут встроенные объекты (hex).
- Объект извлекается декодированием hex.
- RTF — известный вектор эксплойтов.
- Признак — большие objdata-блоки.

## Если не сработало

- Несколько объектов? Извлекай все.
- Сжатый объект? Распакуй после декода.
- Нужен анализ? Открой OLE-парсером.

## Почему RTF вообще поддерживает встроенные объекты

RTF придуман для обмена документами между редакторами, поэтому в него
заложена возможность встраивать «чужие» объекты: таблицы Excel, картинки,
вложенные файлы. Механизм называется **OLE** (Object Linking and
Embedding). В RTF он выражается двумя командами:

- `\object` — начало встроенного объекта;
- `\objdata` — данные объекта, закодированные в hex.

Поскольку в `\objdata` может лежать любой файл, RTF стал удобной «обёрткой»
для доставки исполняемого кода. Документ выглядит как безобидный текст, а
внутри — программа.

## Анатомия встроенного объекта

Разберём настоящий фрагмент RTF по частям:

```
{\object\objemb{\*\objclass Package}\objw100\objh100
{\*\objdata 0105000002000000...}}
```

- `\object` — открывает объект;
- `\objemb` — объект встроен (embedded), а не связан;
- `\objclass Package` — тип объекта; `Package` означает «упакованный файл»
  (часто `.exe` или `.bin`);
- `\objw`/`\objh` — размеры отображения;
- `\objdata` — hex-данные самого объекта.

Именно `\objdata` нас интересует: после декодирования hex мы получим либо
OLE-контейнер, либо сразу исполняемый файл.

## Работа на примере: извлекаем и опознаём объект

Пусть у нас есть `invoice.rtf`. Сначала подтверждаем формат и находим блок
`objdata`:

```
$ file invoice.rtf
invoice.rtf: Rich Text Format data, version 1, ANSI
$ grep -o 'objdata [0-9a-fA-F]*' invoice.rtf | head -c 80
objdata 01050000020000000d000000...
```

Hex длинный, поэтому извлекаем программно. Простой скрипт берёт первую
последовательность hex после `objdata` и пишет бинарь:

```
$ python3 -c "import re;d=open('invoice.rtf').read();h=re.search(r'objdata ([0-9a-fA-F]+)',d).group(1);open('obj.bin','wb').write(bytes.fromhex(h))"
$ file obj.bin
obj.bin: OLE 2 Compound Document
```

Мы получили OLE-контейнер. Внутри него — поток `Package` с полезной
нагрузкой. Разбираем контейнер утилитой `oleid`/`oledump` или через
`oletools`:

```
$ oleid obj.bin
VBA Macros: False
Object Pool: True
```

Если внутри макросы — смотрим их; если второй файл — извлекаем и опознаём
снова (`file`, `strings`, PE-заголовок `MZ`).

## Многослойность: почему одного декодирования мало

Атакующие усложняют разбор намеренно:

- **Несколько объектов.** В одном RTF может быть несколько `\object` —
  извлекай все, а не первый.
- **Сжатие.** Внутри OLE-объекта данные могут быть в `.cab` или gzip —
  распакуй и опознай.
- **Шифрование.** Некоторые сборщики XOR-ят или шифруют нагрузку; ищи ключ
  рядом в документе.
- **Внешняя ссылка.** `\objlink` вместо `\objemb` тянет объект по URL —
  фиксируй домен как индикатор.

```
$ grep -o 'objlink[^}]*' invoice.rtf | head
```

## Красные флаги и когда они ложные

Признаки подозрительного RTF:

- большие блоки `\objdata` (десятки-сотни килобайт hex);
- `\objupdate` — команда «обнови объект», заставляющая открыть его
  автоматически без клика;
- ссылки на уязвимые объекты (Equation Editor `\objclass Equation.3`,
  OLE-уязвимости);
- несоответствие размера: «письмо на 2 КБ» весит 500 КБ.

Ложные срабатывания бывают: документы с встроенной таблицей Excel тоже
содержат `\object`/`\objdata`. Поэтому контекст обязателен — смотрим класс
объекта (`\objclass`) и наличие `\objupdate`.

## Сопоставление с почтой и сетью

RTF приходит вложением в фишинговом письме. Полезно связать файл с
инфраструктурой:

- заголовки письма (`Received`, `Message-ID`, адрес отправителя);
- хэш вложения — поиск в VirusTotal/песочницах;
- домены из `\objlink` и из распакованного кода — в списки IOC.

```
$ sha256sum invoice.rtf
3a7f...  invoice.rtf
```

Хэш — устойчивый идентификатор: даже если имя файла изменят, хэш свяжет
образцы между расследованиями.

## Справочная таблица команд RTF

| Команда | Значение |
| --- | --- |
| `\rtf1` | заголовок, версия формата |
| `\ansi` | кодировка ANSI |
| `\object` | начало встроенного объекта |
| `\objemb` | объект встроен в документ |
| `\objlink` | объект подключается по ссылке |
| `\objclass` | класс объекта (Package, Equation.3) |
| `\objdata` | hex-данные объекта |
| `\objupdate` | авто-обновление (автозапуск) |

## Если сработало / если нет

- **Объект извлёкся и это PE/OLE с нагрузкой** — зафиксируй хэш, разбери
  нагрузку, свяжи с письмом и доменами.
- **Несколько `objdata`, часть пустые** — проверяй каждый, а не первый.
- **Документ — просто текст без объектов** — не выдумывай атаку; возможно,
  это легитимный RTF, тогда отметь «объектов нет».
- **Hex слишком длинный для ручного разбора** — автоматизируй, но сохрани
  исходник: доказательство должно быть воспроизводимым.

## Анатомия RTF: группы и управляющие слова

RTF — это дерево **групп**, каждая в фигурных скобках. Первая группа объявляет версию
(`\rtf1`), кодировку (`\ansi`, `\mac`, `\pc`) и шрифтовую таблицу. Управляющее слово
начинается с обратного слеша и заканчивается пробелом или не-буквой. Ключевое для
форензики: за звёздочкой (`{\*\...}`) идут **необязательные дестинации**, которые обычный
просмотрщик пропускает, а парсер обязан прочитать. Именно там прячут данные.

```
{\rtf1\ansi\deff0
{\fonttbl{\f0 Arial;}}
{\*\generator Riched20 10.0.19041;}
Привет, мир\par
}
```

Обрати внимание: `\generator` раскрывает, чем создавали документ. Если фишинговое вложение
сгенерировано «Microsoft Word», а `\generator` показывает `Riched20`, — документ собирали
скриптом, а не человек в Word.

## Извлечение объекта без запуска

Разбирать `\objdata` руками долго. Есть готовые инструменты:

```
$ pip install olefile oletools rtfdump
$ rtfdump.py -f e --extract invoice.rtf
$ oletools/rtfobj.py invoice.rtf
```

`rtfobj.py` находит все `\objdata`, декодирует hex и (по флагу `-s`) сохраняет вложенные
файлы, не исполняя их. Это безопасный способ: мы получаем объект как данные.

Дальше объект — это **OLE Compound File** (структура «файл внутри файла» со streams).
Смотрим содержимое:

```
$ oledump.py obj.bin
  1:        114 'M'
  2:       5120 '\x01CompObj'
  3:      98304 'CONTENTS'
```

Stream `CONTENTS` у вложенного `.exe` — это уже PE-файл. Проверяем тип:

```
$ oledump.py -s 3 -d obj.bin > inner.bin
$ file inner.bin
inner.bin: PE32 executable (GUI) Intel 80386
```

## Таблица: управляющие слова, важные для расследования

| Управляющее слово | Значение | Почему интересно |
|---|---|---|
| `\object` | начало встроенного объекта | точка вложения |
| `\objdata` | hex-данные объекта | здесь лежит полезная нагрузка |
| `\objupdate` | обновить объект при открытии | авто-исполнение |
| `\objclass` | тип объекта | `Package` = вложенный файл |
| `\objemb` | объект «встроен» (emb) | в отличие от `\objlink` (ссылка) |
| `\bin` | бинарные данные после слова | не-hex вставка |
| `\pict` | картинка | стеганография в документе |
| `\field` / `\fldinst` | поле (в т.ч. `INCLUDEPICTURE`) | подгрузка внешнего ресурса |

`\objupdate` — самый тревожный: он заставляет просмотрщик обновить объект сразу при
открытии, что часто и запускает эксплойт.

## Известные уязвимости и их сигнатуры

| CVE | Компонент | Признак в RTF |
|---|---|---|
| CVE-2017-11882 | Equation Editor (`EQNEDT32.EXE`) | объект `Equation.3`, большой `\objdata` |
| CVE-2018-0802 | Equation Editor | похож на 11882, другая длина |
| CVE-2023-36884 | Word / search-ms | поле `\fldinst` со ссылкой `search-ms:` |
| CVE-2012-0158 | MSCOMCTL ListView | объект с classid ListView |

Важно: наличие уязвимого компонента в документе **не** значит, что он сработает — нужен
ещё уязвимый Office. В отчёте это формулируется как «документ содержит объект,
эксплуатирующий X при условии Y».

## Обфускация и анти-детект

Простые сигнатуры обходят тремя приёмами:

1. **Разбиение hex** — `\objdata` рвут на куски, между ними вставляют безобидные группы;
2. **`\bin` вместо hex** — бинарь вставляют сырыми байтами, а не ASCII-hex;
3. **Смена регистра управляющих слов** — в RTF регистр не важен, `\OBJDATA` работает как
   `\objdata`, а наивные regex ищут строчные.

Против этого помогает нормализация: привести документ к канонической форме перед поиском.

```
$ python3 -c "import sys;d=open('invoice.rtf','rb').read();print(d.lower().count(b'objdata'))"
1
```

## Ограничения метода

RTF-анализ не покрывает случаи, когда нагрузка приходит **не** во вложении, а по ссылке
(`INCLUDEPICTURE`, `\fldinst` с URL). Тогда в самом файле нет объекта — есть только URL,
и работать нужно с сетевыми логами. Кроме того, современные атаки всё чаще используют
**OOXML** (docx), а не RTF, потому что тот выглядит «нормальнее» в почте. RTF остаётся
популярен там, где нужно обойти проверки, ищущие макросы в OOXML.

## Если сработало: как зафиксировать доказательство

Найдя объект, зафиксируй хеши (SHA-256 всего RTF и извлечённого объекта), сохрани
`rtfobj`-вывод как артефакт и запиши версию Office, если она известна. Хеш объекта
позволяет искать тот же образец в других образах и на VirusTotal без повторного разбора.

## RTF с паролем: почему это важно

RTF умеет защищать содержимое паролем (`\password`, `\protstart`). Для
форензики это двойной сигнал: во-первых, документ что-то скрывает, во-вторых,
пароль может лежать рядом — в письме, в имени файла, в теле сообщения. Слабые
пароли (`12345`, название компании) подбираются словарём.

```
$ grep -o '\\password[^}]*' secret.rtf | head
```

Если содержимое зашифровано, встроенные объекты тоже закрыты — но сам факт
наличия объекта и его класс видны до расшифровки.

## Автоматизация: rtfobj из oletools

Ручное выдёргивание hex быстро надоедает. Инструмент `rtfobj` из пакета
`oletools` делает это сам и сразу показывает, что внутри:

```
$ rtfobj -s all invoice.rtf
Object 00000000: format=OLE2, size=24576, MD5=... 
  Extracted to: invoice.rtf_object_00000000.bin
```

Ключ `-s all` заставляет сохранять объекты на диск. После извлечения
прогоняем каждый файл через `file`, `strings` и, если это PE, через
`peframe`/`capa` — так выстраивается цепочка «документ → объект → нагрузка».

## Сравнение с OOXML: разные контейнеры, одна идея

DOCX/XLSX — это ZIP-архивы (OOXML), а RTF — текстовый формат. Но идея одна:
**внутри документа прячется что-то исполняемое**. В OOXML это макросы
(`vbaProject.bin`) или внешние связи (`externalLink`), в RTF — OLE-объекты и
`\objupdate`. Форензик-подход общий: распаковать контейнер, найти полезную
нагрузку, опознать её. Освоив RTF, ты без труда разберёшь и OOXML.

## Метаданные документа

Даже если объектов нет, метаданные дают контекст: кто создал файл, чем, когда.
В RTF метаданные хранятся в группах `\info`:

```
{\info{\title Invoice}{\author unknown}{\creatim\yr2026\mo1\dy14\hr3\min28}}
```

Дата создания (`\creatim`) и автор (`\author`) помогают связать документ с
кампанией. Подделка метаданных тривиальна, поэтому воспринимай их как
подсказку, а не как доказательство.

## Практический чек-лист разбора RTF

1. `file` — подтвердить формат.
2. `grep` по `\object`/`\objdata`/`\objlink` — найти объекты.
3. `rtfobj -s all` — извлечь объекты автоматически.
4. `file`/`strings` по каждому объекту — опознать нагрузку.
5. `sha256sum` оригинала и объектов — зафиксировать.
6. Связать с письмом, доменами, хэшем в песочницах.
7. Проверить `\objupdate`, пароли, внешние ссылки как «красные флаги».
