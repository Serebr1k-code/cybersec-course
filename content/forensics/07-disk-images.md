## Вопрос, с которого всё начинается

В прошлом уроке мы открыли готовый `disk.img` и прочитали файл по inode. Но откуда
берётся сам образ? И что делать, если файла в списке уже нет — его удалили, а запись
в каталоге стёрли?

Вот задача: у тебя есть флешка подозреваемого. Нужно снять с неё образ, доказать,
что он не изменён, и попытаться восстановить удалённый файл. Этот урок — ровно про
этот конвейер.

## Наш пример: флешка и её образ

У нас есть устройство `/dev/sdb`. Первое правило форензики — **не трогать оригинал**.
Чтобы запись на флешку была невозможна физически, используют **write blocker** —
устройство или режим, который блокирует все операции записи на носитель. После этого
снимают побайтовую копию:

```bash
$ dd if=/dev/sdb of=usb.dd bs=4M conv=noerror,sync status=progress
32212254720 bytes (32 GB) copied, 210.4 s, 153 MB/s
$ sha256sum usb.dd | tee usb.dd.sha256
9f2c...e71 usb.dd
```

Флаги `dd`: `if` — источник, `of` — куда писать, `bs=4M` — размер блока (крупные
блоки быстрее), `conv=noerror,sync` — не падать на ошибках чтения и дописывать нули,
чтобы смещения не «поехали». Для битых носителей лучше `dc3dd` или `ddrescue` — они
умеют повторять чтение и вести карту ошибок:

```bash
$ dc3dd if=/dev/sdb of=usb.dd hash=sha256 log=imaging.log
```

Хеш, снятый сразу после копирования, — это точка отсчёта. Любая дальнейшая работа
идёт с **копией**, а хеш оригинала позволяет доказать неизменность улики.

## Что это за образ

```bash
$ file usb.dd
usb.dd: DOS/MBR boot sector; partition 1 : ID=0xb, start-CHS (0x0,32,33),
startsector 2048, 16384 sectors
```

Тип раздела `0xb` — это **FAT32** (частая файловая система флешек). Смотрим разделы
и файлы:

```bash
$ mmls usb.dd
002:  000:000   0000002048   0000018431   0000016384   Win95 FAT32 (0x0b)
$ fls -r -o 2048 usb.dd
r/r 5:	notes.txt
r/r * 7:	flag.txt
r/r * 9:	photo.jpg
```

Два файла помечены звёздочкой — они **удалены**: `flag.txt` и `photo.jpg`. Имена ещё
видны, значит, записи каталога не затёрты. Попробуем прочитать `flag.txt`:

```bash
$ icat -o 2048 usb.dd 7
CTF{d3l3t3d_f1l3_r3c0v3ry}
```

Сработало: файловая система пометила место свободным, но данные на диске остались.
Так восстанавливают большинство «удалённых» файлов — пока по их блокам не записали
что-то новое.

Заметь: мы не «восстанавливаем файл из корзины» — в Linux корзины может не быть
вовсе. Мы читаем данные напрямую с носителя по записи файловой системы. Именно
поэтому способ работает и на флешках, и на серверах, и даже когда ОС считает файл
удалённым безвозвратно.

## Когда inode уже не помогает

Бывает хуже: запись каталога затёрта, и `fls` не покажет файл вовсе. Тогда
восстанавливают **carving-ом по свободному пространству**. Ключевая идея: всё, что
не занято живыми файлами, — это «неразмеченное» (unallocated) пространство. Его можно
выгрузить в сырой поток и искать в нём данные:

```bash
$ blkls -o 2048 usb.dd > unalloc.bin
$ strings -n 6 unalloc.bin | grep -i 'CTF\|password\|flag'
temporary note, then deleted
CTF{fr0m_un4ll0c4t3d_sp4c3}
```

`blkls` («block list») выводит только свободные блоки. Дальше `strings` вытаскивает
из них печатные строки, а `grep` ищет нужное. Если известна сигнатура (например,
начало JPEG), режут `dd` по смещению — ровно как в уроке про carving.

Ещё один полезный инструмент — `tsk_recover`: он выгружает все файлы (в том числе
удалённые) в каталог:

```bash
$ tsk_recover -o 2048 usb.dd recovered/
$ ls -la recovered/
-rw-r--r-- 1 user user 21  flag.txt
-rw-r--r-- 1 user user 30  notes.txt
```

## Почему файлы вообще «удаляются» не до конца

Файловая система устроена так, что при удалении она:

1. помечает запись файла как свободную;
2. помечает его блоки данных как свободные.

Но сами байты на носителе никто не затирает — это было бы медленно. Данные остаются
до тех пор, пока их место не понадобится новому файлу. Отсюда два следствия:

- **Восстановить можно почти всё сразу после удаления.** Чем меньше писали на диск
  после, тем выше шанс.
- **Работа с оригиналом губит улику.** Любая запись (даже монтирование) может занять
  свободные блоки и стереть удалённые данные. Поэтому — только образ и read-only.

## Порядок работы с образом

1. Заблокировать запись на носитель (write blocker).
2. Снять образ (`dc3dd`/`dd`) и сразу посчитать хеш.
3. Работать только с копией образа.
4. `mmls` → разделы, `fls -r` → файлы (включая удалённые).
5. Восстановить: `icat` по inode; если не вышло — `blkls` + carving, `tsk_recover`.
6. Зафиксировать в отчёте: команды, хеши, что восстановлено.

## Форматы образов: raw и не только

Наш `usb.dd` — это **raw-образ**: побайтовая копия носителя, без сжатия и метаданных.
Он прост и универсален, но занимает столько же, сколько сам диск. Кроме него бывают:

| Формат | Чем отличается |
|--------|----------------|
| `raw`/`dd` | побайтовая копия, читается любым инструментом |
| `E01` (EnCase) | сжатие, хеши и метаданные внутри одного файла |
| `AFF4` | открытый формат с компрессией и верификацией |

`E01` и `AFF4` умеют хранить контрольные суммы по сегментам и информацию о том, кто
и когда снимал образ, — поэтому в реальной работе их часто предпочитают raw. Открыть
такой образ можно теми же `fls`/`icat`, если у них есть поддержка формата.

## Что ещё смотреть в образе

Помимо файлов, в образах ищут:

- **Slack-пространство** — «хвост» последнего блока файла, куда попадают остатки
  старых данных. `fls`/`icat` могут их отдавать.
- **Unallocated-пространство** — уже знакомое нам свободное место (урок выше).
- **Журналы ФС** — `ext4`-журнал (`$JOURNAL`) хранит недавние операции; из него
  восстанавливают изменения, даже если сами файлы уже удалены.
- **Скрытые разделы** — иногда данные прячут в разделе, которого нет в таблице;
  его находят по сигнатурам прямо в образе.

Это уже следующий уровень глубины, но знать о нём полезно: не всё, что «потеряно»,
потеряно безвозвратно.

## Когда образ снимать не нужно

В CTF образ уже дан, но в реальной работе полезно понимать границы. Снимать образ
целого диска не всегда обязательно:

- **Если нужен только один файл** — можно скопировать его с сохранением атрибутов,
  но для улики лучше всё же образ: он фиксирует контекст.
- **Если носитель огромный** — сначала делают «логический» образ (только данные),
  затем физический, если нужно.
- **Живая система** — снимать образ с работающего диска можно, но данные будут
  несогласованными; для важных случаев используют средства с файловой блокировкой
  (VSS на Windows, снапшоты LVM).

Главное правило неизменно: **оригинал не трогаем, копию хешируем**.

## Что мы теперь знаем

- Оригинал защищают write blocker-ом, работают с образом, хеш фиксируют сразу.
- `dd`/`dc3dd` снимают побайтовую копию; `conv=noerror,sync` бережёт смещения.
- Удалённый файл читается по inode (`icat`), пока запись жива.
- Если записи нет — carving по свободному пространству (`blkls` + `strings`/`dd`).
- Запись на оригинал может затереть удалённые данные — только read-only.

## Куда дальше

Мы разобрали диски. Но не менее важный источник — **сетевой трафик**: в дампах PCAP
видны пароли, файлы и сессии целиком. В следующем уроке возьмём один `capture.pcap`
и восстановим из него HTTP-сессию, логин и скачанный файл. А пока запомни: **образ
снимают один раз, хешируют сразу, а удалённое ищут в свободном пространстве**.

## Где пригодится

- **CTF:** задачи «восстанови удалённый файл».
- **Data recovery:** спасение данных с флешек и дисков.
- **Incident Response:** снятие образов с машин инцидента.
- **Криминалистика:** доказательное извлечение данных.
- **Пентест:** поиск следов на скомпрометированных носителях.
