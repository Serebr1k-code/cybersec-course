## Вопрос, с которого всё начинается

В дампе памяти есть подозрительный процесс, но на диске нет соответствующего файла, а в
его памяти — странный исполняемый регион. Скорее всего, там **шеллкод**: небольшой машинный
код, который малварь внедрила и исполняет напрямую. Как его найти и понять, что он делает?

Разберём сквозной пример: извлечём шеллкод из дампа и дизассемблируем его.

## Что такое шеллкод

**Шеллкод** — это «голые» машинные инструкции (без заголовка файла), которые исполняются
прямо в памяти. Он используется при инъекциях, эксплуатации уязвимостей и в
fileless-атаках. Поскольку у него нет формата файла, антивирус не может проверить его как
PE/ELF — приходится анализировать байты вручную.

Признаки шеллкода в дампе:

- исполняемый регион памяти **без соответствующего файла** на диске;
- регион с правами **`rwx`** (одновременно запись и исполнение) — нетипично;
- регион, помеченный как **`[anonymous]`** или без имени;
- байты, начинающиеся с характерных прологов.

## Наш пример: находим внедрённый регион

Volatility-плагин `windows.malfind` (или `linux.malfind`) эвристически ищет исполняемые
регионы, не связанные с файлом:

```
$ vol -f mem.raw windows.malfind --pid 1338
PID   Process   Start      End        Protection  Tag
1338  svc.exe   0x1f0000   0x1f2000   PAGE_EXECUTE_READWRITE  VadS
```

Регион `PAGE_EXECUTE_READWRITE` без файла — почти наверняка внедрённый код. Дамп этого
региона:

```
$ vol -f mem.raw windows.malfind --pid 1338 --dump
Dumped 8192 bytes to pid.1338.0x1f0000.dmp
```

Теперь у нас есть файл с шеллкодом. Смотрим первые байты:

```
$ xxd -l 32 pid.1338.0x1f0000.dmp
00000000: fc48 83e4 f0e8 c000 0000 4151 4150 5251  .H..........AQAPRQ
```

Первый байт `fc` — это `cld` (сбросить флаг направления). Далее `48 83 e4 f0` — выравнивание
стека. Такое начало — типичный **пролог шеллкода**: он готовит окружение, не полагаясь на
среду.

## Распознавание типовых прологов

Опытный аналитик узнаёт шеллкод по первым байтам. Частые сигнатуры:

- **`fc 48 83 e4 f0`** — `cld` + выравнивание стека (Metasploit/CE).
- **`e8 00 00 00 00`** — `call` на следующую инструкцию, приём для получения адреса (PIC).
- **`31 c0`** / **`33 c0`** — обнуление `eax` (`xor eax, eax`).
- **`64 8b 30`** — доступ к PEB через `fs:[0x30]` (Windows-шеллкод ищет API по PEB).
- **`65 48 8b 04 25`** — аналог для x64 (`gs:[0x60]`).

Запомнив эти паттерны, можно быстро отличить шеллкод от обычных данных.

## Дизассемблирование

Извлечённый регион дизассемблируют. Инструменты: **objdump**, **ndisasm**, **capstone**,
**radare2**, **IDA/Ghidra**. Для «сырого» кода указывают архитектуру и разрядность:

```
$ ndisasm -b 64 pid.1338.0x1f0000.dmp | head
00000000  FC                cld
00000001  4883E4F0          and rsp,byte -0x10
00000005  E8C0000000        call 0xca
0000000A  4151              push r9
```

Читаем поток инструкций. Первые строки — подготовка. Дальше обычно идёт **разрешение
адресов API**: шеллкод находит базовый адрес `kernel32.dll` через PEB, затем ищет функции
`LoadLibrary`/`GetProcAddress`, чтобы загрузить то, что нужно. Узнать это можно по строкам
рядом с кодом:

```
$ strings pid.1338.0x1f0000.dmp
LoadLibraryA
WinExec
http://10.10.20.9/p
```

Строки подсказывают поведение: шеллкод загрузит библиотеку и выполнит команду или скачает
полезную нагрузку.

## Полный прогон

Соберём историю целиком: `malfind` нашёл регион `rwx` без файла; дамп дал байты; `xxd`
показал пролог; `ndisasm` разобрал инструкции; `strings` выдал имена API и URL. Вместе это
восстанавливает **поведение внедрённого кода** — даже без запуска малвари. Так анализ памяти
превращает «неизвестные байты» в понятную цепочку «загрузить библиотеку → выполнить
команду».

## Практический сценарий: разбираем шеллкод из задачи

Закрепим материал полным разбором. Дан дамп памяти, и известно, что малварь внедрила
шеллкод в процесс `svc.exe`. Наша цель — понять, что этот код делает.

Начинаем с `malfind`, чтобы найти внедрённые регионы именно у нужного процесса:

```
$ vol -f mem.raw windows.malfind --pid 1338 --dump
1338  svc.exe  0x1f0000  0x1f2000  PAGE_EXECUTE_READWRITE  VadS
Dumped 8192 bytes to pid.1338.0x1f0000.dmp
```

Получили файл с кодом. Смотрим его размер и первые байты:

```
$ ls -l pid.1338.0x1f0000.dmp
-rw-r--r-- 1 analyst analyst 8192 ... pid.1338.0x1f0000.dmp
$ xxd -l 16 pid.1338.0x1f0000.dmp
00000000: fc48 83e4 f0e8 c000 0000 4151 4150  .H........AQAP
```

Пролог узнаваем. Теперь ищем строки — они часто выдают назначение:

```
$ strings pid.1338.0x1f0000.dmp
LoadLibraryA
GetProcAddress
WinExec
cmd.exe /c whoami
```

Цепочка ясна: шеллкод разрешает адреса `LoadLibraryA`/`GetProcAddress` (чтобы загрузить
библиотеки), затем вызывает `WinExec` с командой `cmd.exe /c whoami`. Это **разведочный**
шеллкод — он проверяет, под какой учёткой исполняется.

Дальше дизассемблируем начало, чтобы подтвердить разрешение API:

```
$ ndisasm -b 64 pid.1338.0x1f0000.dmp | head -12
00000000  FC                cld
00000001  4883E4F0          and rsp,byte -0x10
00000005  E8C0000000        call 0xca
0000000A  4151              push r9
0000000C  4150              push r8
```

Инструкции соответствуют прологу позиционно-независимого кода: подготовка стека и вызов
для получения текущего адреса. Дальше по потоку идёт обход PEB и поиск функций по хешу
имени — классика Windows-шеллкода.

Итог: мы восстановили **поведение** внедрённого кода, не запуская малварь. Это и есть цель
анализа шеллкода — понять назначение по байтам и строкам. В реальном расследовании такой
анализ позволяет оценить, что именно делал злоумышленник: разведку, загрузку следующего
этапа или эксфильтрацию.

## Связь с другими артефактами

Шеллкод редко существует в вакууме. Найдя его, проверьте связанные источники: сетевые
соединения процесса (куда он «звонит»), созданные файлы (что он записал), правки реестра
(как закрепился). В памяти всё это рядом: `netscan`, `handles`, `registry` в Volatility.
Собирая эти данные, вы получаете полную картину — от внедрения кода до его последствий.

## Частые ошибки

- **Смотреть только строки.** Строки дают подсказку, но поведение видно в дизассемблере.
- **Забыть указать разрядность.** `ndisasm` по умолчанию 16-бит; для x64 нужен `-b 64`.
- **Игнорировать регионы без метки malfind.** Эвристика может пропустить код в
  `PAGE_EXECUTE_READ` — проверяйте и вручную.
- **Считать любой `rwx` вредоносным.** JIT-компиляторы (Java/.NET/браузеры) тоже создают
  такие регионы — важен контекст.

## Шпаргалка команд

```
# Найти и выгрузить внедрённый код
vol -f mem.raw windows.malfind --dump
# Дизассемблировать
ndisasm -b 64 dump.bin | head -40
objdump -D -b binary -m i386:x86-64 dump.bin | head -40
# Строки рядом с кодом
strings dump.bin
# Сетевые соединения процесса
vol -f mem.raw windows.netscan | grep <pid>
```

## Что это даёт в отчёте

По анализу шеллкода в отчёте фиксируют: где найден код (процесс и регион), его размер,
используемые API и строки, предполагаемое назначение и связанные сетевые/файловые
артефакты. Это превращает «неизвестные байты» в понятную цепочку действий и часто является
ключевым доказательством fileless-атаки.

## Обнаружение шеллкода без эвристики

`malfind` работает по эвристике и иногда пропускает код в регионах `PAGE_EXECUTE_READ` или
внутри легитимных модулей. Поэтому опытные аналитики применяют дополнительные приёмы.

Первый — **поиск сигнатур прологов** по всему дампу. Сканируя память на байты вроде
`fc 48 83 e4 f0` или последовательности `e8 00 00 00 00`, можно найти код, не помеченный
`malfind`. Второй — **YARA-правила** для шеллкода: набор правил от сообщества (например,
для Meterpreter/CE) ловит типовые паттерны. Третий — анализ **разрывов в модулях**: если
внутри региона загруженной библиотеки есть аномальный код, это может быть инъекция.

Отдельно проверяют **потоки** (threads): `windows.threads` покажет потоки, чьи точки входа
лежат вне известных модулей. Поток, начинающийся в анонимном регионе, — прямой признак
внедрённого кода. Комбинируя эти методы, можно найти даже хорошо замаскированный шеллкод.

## Упаковка и самодекодирующийся код

Иногда шеллкод упакован: начало расшифровывает остальную часть в памяти и передаёт
управление. Признак — цикл декодирования в начале (операции `xor`/`add` по буферу) и
переход на только что записанную область. Анализ такого кода требует либо эмуляции
(Unicorn/Qiling), либо ручного воспроизведения цикла декодирования. Для CTF часто
достаточно заметить цикл и применить те же операции к дампу скриптом, получив открытый код.

## Что это даёт в отчёте (продолжение)

По упакованному шеллкоду в отчёте отмечают: способ упаковки, применённый алгоритм
декодирования и восстановленный полезный код. Это показывает глубину анализа и позволяет
другим специалистам воспроизвести результат — что и является стандартом форензик-отчёта.

## Что мы теперь знаем

- **Шеллкод** — машинные инструкции без заголовка файла, исполняемые прямо в памяти.
- Признаки: регион **`rwx`** без файла, метка `[anonymous]`.
- `malfind` эвристически находит такие регионы и умеет их выгружать.
- Типовые прологи: `fc 48 83 e4 f0`, `e8 00 00 00 00`, `31 c0`, доступ к **PEB**.
- Дизассемблируют через `ndisasm`/`objdump`/Capstone, указывая разрядность.
- Строки рядом с кодом (`LoadLibraryA`, `WinExec`, URL) подсказывают поведение.

## Куда дальше

Мы закончили блок форензики памяти. Дальше перейдём к **сетевой форензике**: разберём
Kerberos, DNS и восстановление C2-протоколов. А пока главное запомни: **шеллкод ищут по
регионам `rwx` без файла, выгружают и дизассемблируют, а строки рядом подсказывают
поведение**.
