## Вопрос, с которого всё начинается

Ты снял образ диска с NAS-хранилища. Файловая система — не ext4, не XFS, не Btrfs.
`file` говорит **ZFS**. Обычные инструменты Linux не открывают том, а данных внутри —
терабайты. С чего начать и что вообще искать на ZFS-диске?

## Что такое ZFS и её слои

**ZFS (Zettabyte File System)** — файловая система и менеджер томов в одном. Она управляет
не отдельным диском, а **пулом (zpool)** из одного или нескольких устройств (vdev). Поверх
пула создаются **датасеты** — логические файловые системы. ZFS тоже использует
copy-on-write и хранит контрольные суммы каждого блока.

Для форензики важны три понятия, которые часто путают:

- **Uberblock** — корневой указатель на дерево данных. Их несколько (по копии в начале и
  конце каждого vdev), и каждый помечен номером транзакционной группы **txg**.
- **ARC (Adaptive Replacement Cache)** — кэш в оперативной памяти. Это не диск, но при
  снятии дампа памяти ARC может содержать недавно прочитанные блоки.
- **ZIL (ZFS Intent Log)** — журнал намерений: сюда пишутся синхронные записи до того, как
  они попадут в основное дерево (при коммите txg). **SLOG** — отдельное (быстрое) устройство
  под ZIL.

## Наш пример: образ пула

```
$ ls -la
-rw-r--r-- 1 student student 134217728 zpool.img
$ file zpool.img
zpool.img: ZFS filesystem, version 5000
```

ZFS подписывает метки vdev строкой `ZFS` в блоке L0/L1 (по 256 КБ в начале и конце
устройства). Внутри лежит **uberblock** с магией `0x00bab10c` («bab10c» — шутка
разработчиков). Найдём текстовые метаданные:

```
$ strings zpool.img | grep -Ei 'uberblock|txg|ZIL|SLOG|pool'
ZFS vdev label L0
uberblock: magic 0x00bab10c txg=4821
ZIL: 3 outstanding log records
SLOG device: nvme0n1p2
pool name: tank
POOL HISTORY: nto{zfs_z1l_ub3rbl0ck_txg}
```

Здесь видно всё сразу: uberblock с номером txg, незавершённый ZIL и метка пула. Если
записи «висят» в ZIL, они ещё не в основном дереве — это критично для свежих следов.

## Шаг 1: почему ZFS — это дерево деревьев

В отличие от NTFS с её `$MFT`, ZFS не имеет одной таблицы файлов. Всё — дерево объектов
(object set), корень которого указан в uberblock. Uberblock выбирается по **наибольшему
txg**: актуальная версия пула — это uberblock с самым большим номером транзакционной
группы. Отсюда практический вывод: **самый свежий uberblock — самый важный**.

| Структура | Роль | Аналог |
|-----------|------|--------|
| Uberblock | корень дерева + номер txg | `$MFT` (условно) |
| vdev label | метка устройства пула | boot sector |
| ZIL | журнал синхронных записей | `$LogFile` (NTFS) |
| ARC | кэш в RAM | page cache |
| SLOG | отдельное устройство под ZIL | отдельный журнал |

## Шаг 2: импорт пула только для чтения

ZFS не монтируется как обычная ФС. Сначала **импортируют пул**, потом монтируют датасет:

```
$ sudo zpool import -d /dev -o readonly=on tank
$ sudo zpool status tank
  pool: tank
 state: ONLINE
config:
        NAME        STATE
        tank        ONLINE
          nvme0n1   ONLINE
$ sudo zfs mount tank/data
```

`readonly=on` — обязательная мера: любой импорт с записью переиграет ZIL и перепишет
метаданные, уничтожив доказательства. Если пул «грязный» (был выдернут из работающей
системы), ZFS захочет выполнить replay — а нам это не нужно.

## Шаг 3: читаем историю пула — это журнал администратора

ZFS ведёт **`zpool history`** — журнал всех операций с пулом (создание, снапшоты,
уничтожение датасетов). Это буквально дневник действий:

```
$ sudo zpool history tank
History for 'tank':
2026-03-10.09:14:02 zpool create tank nvme0n1
2026-03-11.02:11:48 zfs snapshot tank/data@before
2026-03-11.22:03:19 zfs destroy tank/data@before
2026-03-12.01:20:00 zfs destroy tank/data
```

Видишь `zfs destroy` — значит, данные удалили, и есть точное время. Если снапшот
уничтожили, но уборщик (zfs_free) ещё не прошёл, блоки могут быть на диске. Это первое,
что фиксируют в отчёте.

## Шаг 4: ZIL — «недописанные» данные

Синхронные записи (например, `fsync`) сначала попадают в ZIL, и лишь при коммите txg —
в основное дерево. Если питание пропало между этими моментами, данные лежат **только в
ZIL**. Инструмент `zdb` умеет их показать:

```
$ sudo zdb -ul /dev/nvme0n1
Uberblock:
    magic = 0000000000bab10c
    txg = 4821
    ...
$ sudo zdb -ivv tank 2>/dev/null | head
    ZIL header: claim_txg 4821, unlinked 0
```

`zdb` — низкоуровневый отладчик ZFS. Он читает uberblock-и, деревья объектов и ZIL напрямую
с диска, не импортируя пул. Если импорт невозможен (пул из нескольких отсутствующих
дисков), `zdb` часто остаётся единственным способом заглянуть внутрь.

## Шаг 5: восстановление файлов

Когда пул не собирается, применяют `zdb`-ориентированные приёмы и сторонние парсеры:

- **`zdb -R pool txg:offset:size`** — читать блок напрямую по физическому адресу;
- **`zfs send`/`zfs receive`** — перенести датасет (в т.ч. снапшот) на другой пул;
- **`zpool import -o readonly=on -d <dir>`** — импорт из копий дисков;
- **сторонние инструменты** (например, ReclaiMe, ZFS-aware парсеры) для недоступных пулов.

Главное правило то же: **никогда не писать в исходный пул**.

## Частые ошибки и подводные камни

- **Импорт с записью.** ZFS переиграет ZIL и изменит метаданные. Только `readonly=on`.
- **Выбор не того uberblock.** Актуальный — с наибольшим txg, а не первый найденный.
- **Забытый SLOG.** Если был отдельный SLOG-диск и его не сняли, свежие синхронные
  данные могут быть неполными.
- **Путаница ARC и диска.** ARC — это RAM; для её анализа нужен дамп памяти, а не образ
  диска.
- **Метаданные в нескольких vdev.** Зеркало или RAIDZ разносит данные по устройствам;
  образ одного диска — это лишь часть пула.

## Что мы теперь знаем

- ZFS опознаётся по метке vdev `ZFS` и uberblock с магией `0x00bab10c`.
- Актуальное состояние пула — uberblock с наибольшим txg.
- ZIL хранит синхронные записи до коммита; SLOG — отдельное устройство под ZIL.
- `zpool history` — журнал операций с пулом (снапшоты, уничтожения).
- Инструменты: `zpool import -o readonly=on`, `zpool history`, `zdb -ul/-ivv`.

## Что фиксировать в отчёте

| Что | Зачем |
|-----|-------|
| txg самого свежего uberblock | момент последнего коммита |
| Вывод `zpool history` | кто и когда удалял/создавал данные |
| Незавершённый ZIL | данные, не попавшие в дерево |
| Список датасетов и снапшотов | что вообще было на пуле |
| Метод импорта (readonly) | воспроизводимость и сохранность |

## Мини-практика: читаем uberblock и историю пула

Когда пул не импортируется (не хватает диска), uberblock читают напрямую. Утилита `zdb`
показывает его без импорта:

```
$ sudo zdb -ul /dev/nvme0n1
----------------------------------------
LABEL 0
    version: 5000
    name: 'tank'
    state: 0
Uberblock:
    magic = 0000000000bab10c
    version = 5000
    txg = 4821
    guid_sum = 123456789
    timestamp = 1773198000
```

Обрати внимание на поле `timestamp` — это время последнего коммита txg. Если оно совпадает
с моментом инцидента, ты знаешь, что пул «жил» до этого времени. Поле `guid_sum`
подтверждает, что все диски пула на месте (если сумма не сходится — часть устройств
отсутствует, и импорт соберёт не тот пул).

Историю пула тоже можно вытащить без импорта — она хранится в метаданных и читается
парсерами. Для отчёта это ценно: `zpool history` показывает команды `zfs destroy`,
`zfs snapshot`, `zfs rollback`, `zpool export` — то есть буквально действия администратора.

## ARC в дампе памяти

ARC — это кэш в RAM, и его анализ возможен только при наличии **дампа памяти**, снятого с
работающей системы. В дампе ARC хранит недавно прочитанные и записанные блоки ZFS, включая
те, что уже «вытеснены» с диска. Это важно в двух сценариях:

- **Незакоммиченные данные.** Блок мог быть записан в ARC, но ещё не сброшен на диск —
  в образе диска его нет, а в памяти есть.
- **Ключи шифрования ZFS.** Если датасет зашифрован (`zfs set encryption=on`), ключ живёт
  в памяти, пока пул импортирован. Дамп памяти может дать доступ к расшифровке.

Практически ARC ищут в дампе по структурам ZFS (утилиты вроде `Volatility3` плагинов для
ZFS или специализированные парсеры). Прямого «файла ARC» не существует — это набор
структур в куче ядра. Поэтому правило простое: **диск + память вместе дают полную картину
ZFS**, а один диск — только закоммиченное состояние.

## Куда дальше

Мы разобрали ZFS и её журнал намерений. Дальше возьмём **журнал NTFS (`$LogFile`)** — там
похожая идея redo/undo-записей, но со своей структурой LSN. А пока главное запомни:
**самый свежий uberblock — по txg, и ZIL хранит то, что ещё не в дереве**.

## Где пригодится

- **CTF Forensics:** образы NAS/ZFS, которые не открываются обычными инструментами.
- **DFIR:** расследование на файловых серверах с ZFS и снапшотами.
- **Data recovery:** сбор пула из нескольких дисков и чтение uberblock.
- **Администрирование:** понимание, зачем нужен SLOG и как работает txg.
