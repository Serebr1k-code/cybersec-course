Анти-форензика — это приёмы сокрытия следов: изменение временных меток, затирание данных, очистка логов, руткиты, шифрование. Задача аналитика — не только знать эти приёмы, но и уметь их **обнаруживать**: любое сокрытие само оставляет следы. Этот урок — про основные техники и индикаторы их применения.

## Классификация приёмов

| Приём | Цель | Индикаторы |
|-------|------|-----------|
| Timestomping | скрыть время файла | расхождение `$SI`/`$FN`, USN |
| Wiping | уничтожить данные | нули/паттерн, «дыры» в unallocated |
| Log clearing | скрыть действия | Event ID 1102/104, пробелы во времени |
| Rootkit | скрыть присутствие | несоответствия в памяти/API |
| Шифрование | сделать нечитаемым | энтропия ~8, отсутствие сигнатур |
| ADS/hidden | спрятать файл | потоки `$DATA`, скрытые атрибуты |

## Timestomping

Изменение MAC-времен файла (например, утилитой `timestomp` из Metasploit или PowerShell `Set-ItemProperty`). Главный признак — **расхождение меток `$STANDARD_INFORMATION` и `$FILE_NAME`** в NTFS: `$FN` обновляется только при переименовании/создании и «выдаёт» реальное время, тогда как `$SI` можно подделать. Также помогает USN-журнал: запись о создании/изменении остаётся с настоящим временем.

```bash
# MFT: сравнить $SI и $FN по колонкам
$ MFTECmd.exe -f '$MFT' --csv out --csvf mft.csv
# искать строки, где SI не совпадает с FN
$ grep -i 'timestomp\|1980\|1970' out/mft.csv
```

Подробно — в уроке `forensics-timestomp`.

## Wiping (затирание)

Утилиты (`sdelete`, `shred`, `dd if=/dev/zero`, `cipher /w`) перезаписывают данные нулями, случайными байтами или паттернами. Признаки: блоки с однородным содержимым (все нули, повторяющийся паттерн) там, где ожидались файлы; аномально высокая доля нулей в unallocated; «дыры» в таймлайне.

```bash
# доля нулевых байт (высокая — признак вайпа)
$ xxd unalloc.bin | grep -c '0000 0000 0000 0000'
# энтропия: случайный вайп даёт ~8
$ binwalk -E unalloc.bin | head
```

Парадокс: полное затирание всего диска оставляет **отсутствие** артефактов — тоже индикатор. Частичное затирание легко заметить по границе «данные/паттерн».

## Очистка логов

Windows: `wevtutil cl` очищает EVTX. Событие **1102** (Security) «audit log cleared» фиксируется в самом журнале, если аудит включён; **104** (System) — очистка лога. Даже после очистки остаётся запись о факте очистки и её инициаторе.

```bash
$ evtx_dump -o json Security.evtx | jq 'select(.Event.System.EventID==1102)'
$ evtx_dump -o json System.evtx | jq 'select(.Event.System.EventID==104)'
```

Linux: `rm /var/log/*`, `journalctl --rotate --vacuum-time=1s`, `shred auth.log`. Индикаторы: пробелы в нумерации, отсутствие ожидаемых файлов, изменённые права, записи о `logrotate` вне расписания, артефакты в `~/.bash_history` (`history -c`).

## Rootkit

Руткиты прячут процессы/файлы/ключи реестра, перехватывая системные вызовы или API. Обнаружение — сравнением «двух взглядов»: пользовательский API vs сырой доступ. В памяти — скрытые потоки, модифицированные таблицы (SSDT/IDT), несоответствие списка процессов.

```bash
# Linux: сравнить ps с /proc
$ ls /proc | grep -E '^[0-9]+$' | sort -n > /tmp/proc.txt
$ ps -eo pid --no-headers | sort -n > /tmp/ps.txt
$ comm -23 /tmp/proc.txt /tmp/ps.txt     # PID в /proc, но не в ps
# Volatility: скрытые процессы
$ vol -f mem.raw windows.psscan
$ vol -f mem.raw windows.malfind
```

Windows-инструменты: `GMER`, `RootkitRevealer`, `chkrootkit`/`rkhunter` (Linux). В офлайне — `forensics-memory-injection`.

## Шифрование и сокрытие

Атакующий может шифровать данные (вымогатели, скрытые контейнеры) — энтропия близка к 8, сигнатур нет. Скрытие через **Alternate Data Streams** (NTFS), расширения, невидимые символы в именах, файлы в slack/unallocated.

```bash
# ADS в NTFS
$ fls -o 2048 -r ntfs.img | grep ':'    # потоки вида file.txt:secret
$ icat -o 2048 ntfs.img 42-128-3        # конкретный ADS
# скрытые файлы Linux
$ find / -name '.*' -type f -newer /tmp/ref
$ ls -laR / | grep -E '^\s*-.*\s\.' 
```

## Разобранный пример

Дан образ Windows. Подозрение на анти-форензику.

```bash
# 1. Очистка логов?
$ evtx_dump -o json System.evtx | jq 'select(.Event.System.EventID==104)'
{"EventData":{"SubjectUserName":"bob","Channel":"Security"}}   # факт очистки
# 2. Timestomping: расхождение SI/FN
$ MFTECmd.exe -f '$MFT' --csv out --csvf mft.csv
$ awk -F, '$10!=$14 {print $1}' out/mft.csv | head   # SI vs FN create
# 3. Вайп: нулевые блоки
$ blkls -o 2048 disk.img > unalloc.bin
$ binwalk -E unalloc.bin | awk '$3>7.9' | head       # высокая энтропия = вайп/шифр
# 4. ADS
$ fls -o 2048 -r disk.img | grep ':'
r/r 42-128-3: C:\Users\bob\docs\report.docx:secret
```

Итог: журнал очищен пользователем `bob`, в MFT — расхождения SI/FN, в unallocated — вайп-паттерны, найден скрытый поток ADS.

## Частые ошибки

- **Верить меткам файлов** — сверяйте `$SI` и `$FN`, смотрите USN.
- **Считать очищенный лог «пустым»** — факт очистки (1102/104) остаётся.
- **Игнорировать ADS** — секрет может быть в потоке, а не в `$DATA`.
- **Не сравнивать API и сырой доступ** при подозрении на руткит.
- **Забывать про `~/.bash_history`** и `history -c`.
- **Путать высокую энтропию от сжатия и от шифрования** — смотрите контекст.

## Что дальше / решение

Ищите индикаторы: расхождения меток (`forensics-timestomp`), записи об очистке (EVTX), вайп-паттерны (unallocated), ADS и руткиты (`forensics-memory-injection`). Связка: `forensics-fileless` (следы без файлов), `forensics-timeline` (пробелы во времени), `forensics-attack-mapping` (T1070 — Indicator Removal).

## Следы удаления и вайп-паттерны

Анти-форензика сама создаёт артефакты. Ищите характерные паттерны затирания: блоки, заполненные нулями, случайными байтами или повторяющейся строкой (например, `0x00`, `0xFF`, `sdelete`-паттерн `0x00/0xFF/random`). Границы между «данными» и «паттерном» выдают, где именно чистили.

```bash
# доля нулевых блоков (сигнал вайпа)
$ xxd unalloc.bin | grep -c '0000 0000 0000 0000'
# поиск паттернов sdelete/shred
$ strings -n 4 unalloc.bin | sort | uniq -c | sort -rn | head
# карта энтропии: резкие переходы = границы вайпа/шифра
$ binwalk -E -N disk.img | head -20
```

**Следы удаления** полезны не меньше: `$UsnJrnl` (NTFS) фиксирует `FILE_DELETE` с именем даже после удаления; Prefetch «Files referenced» показывает недавно открытые, а затем удалённые файлы; LNK остаётся после удаления целевого файла. Парадокс анти-форензики: чем агрессивнее чистят, тем заметнее аномалия.

## Обнаружение руткитов офлайн

Если есть дамп памяти, руткиты ищут через Volatility: сравнение «активного» списка процессов (`pslist`) со сканом пула (`psscan`) выявляет скрытые процессы; `malfind` находит инъекции; `ssdt` — модификации таблицы системных вызовов.

```bash
$ vol -f mem.raw windows.pslist > ps.txt
$ vol -f mem.raw windows.psscan > scan.txt
$ comm -23 <(sort scan.txt) <(sort ps.txt)     # только в psscan = скрытые
$ vol -f mem.raw windows.malfind
$ vol -f mem.raw windows.ssdt
```

На диске: `chkrootkit`, `rkhunter` (Linux), `GMER`/`RootkitRevealer` (Windows). Всегда помните о «двух взглядах»: если пользовательский API что-то скрывает, сырой доступ к структурам ФС/памяти покажет правду.

## Методология противодействия

Системный подход к анти-форензике:

1. **Снять образ немедленно** — до перезагрузки, которая может активировать «подчистку».
2. **Захватить память** — там руткиты и незашифрованные ключи.
3. **Сравнить источники** — ФС vs сырой доступ, метки SI vs FN, EVTX vs USN.
4. **Искать пробелы и аномалии** — отсутствие ожидаемых записей так же значимо, как наличие.
5. **Зафиксировать индикаторы** — сам факт очистки/вайпа — доказательство (T1070).
6. **Не доверять живой системе** — она под контролем атакующего.

## Типовые ошибки при разборе анти-форензики

- **Считать «нет улик» = «ничего не было»** — возможно, их уничтожили; ищите следы уничтожения.
- **Анализировать уже перезагруженную систему** — потеряна память и volatile-артефакты.
- **Игнорировать Event 1102/104** — факт очистки логов сам по себе улика.
- **Не проверять `$UsnJrnl`** — он часто остаётся при удалённых файлах.
- **Путать сжатие и шифрование** по энтропии без контекста.
