## Вопрос, с которого всё начинается

В дампе — непонятный UDP-трафик на нестандартный порт. Это VPN? И если да, можно ли
заглянуть внутрь? Ответ зависит от протокола. Разберём, как распознать и что извлечь.

## Наш пример: подозрительный туннель

## Шаг 1: распознаём протокол

```
$ tshark -r capture.pcap -T fields -e ip.proto -e udp.port -e frame.len | head
17	51820	142
17	51820	98
```

Порт `51820` — стандартный для **WireGuard**. Другие маркеры: `1194` (OpenVPN),
`500/4500` (IPsec/IKE), `443` (VPN поверх TLS).

## Шаг 2: WireGuard

WireGuard — минималистичный UDP-протокол. Он не имеет «рукопожатия в открытом виде»:
всё зашифровано с первой секунды.

```
$ tshark -r capture.pcap -Y 'udp.port==51820' -c 4
```

Внутреннее содержимое недоступно без приватного ключа пира. В расследовании факт
туннеля сам по себе — улика: трафик шёл в обход корпоративного контроля.

## Шаг 3: OpenVPN

OpenVPN узнаваем по первым байтам:

```
$ tshark -r capture.pcap -Y 'tcp.port==1194 || udp.port==1194' -c 2
```

При наличии ключа/статического ключа можно расшифровать. Часто в конфиге используется
TLS — тогда нужны ключи сессии.

## Шаг 4: IPsec

IPsec — это IKE (UDP 500/4500) для установки ключей и ESP для данных:

```
$ tshark -r capture.pcap -Y 'isakmp' -T fields -e isakmp.msg.type | head
```

IKE-фаза видна в открытом виде (идентификаторы, алгоритмы). Данные (ESP) зашифрованы.

## Шаг 5: следы на хосте

На самом устройстве остаётся конфигурация VPN:

```
$ ls /etc/wireguard/
wg0.conf
$ grep -i 'Endpoint\|AllowedIPs' /etc/wireguard/wg0.conf
Endpoint = 203.0.113.5:51820
AllowedIPs = 0.0.0.0/0
```

`AllowedIPs = 0.0.0.0/0` означает, что весь трафик уходил в туннель — признак
перенаправления всей сети.

## Что мы теперь знаем

- VPN распознаётся по порту и сигнатуре.
- WireGuard (51820) не отдаёт содержимое без ключа.
- OpenVPN (1194) можно расшифровать при наличии ключей.
- IPsec: IKE виден, ESP зашифрован.
- Конфиги на хосте показывают endpoint и маршруты.

## Если не сработало

- Трафик на 443? Возможно, VPN замаскирован под HTTPS.
- Нужны данные? Ищи ключи на хосте или в памяти.
- Нет дампа? Смотри конфиги VPN и логи демонов.

## Распознавание протоколов по сигнатурам

Первое, что делают в расследовании, — определяют, какой именно VPN перед ними. Порт и
первые байты почти всегда однозначны:

| Протокол | Транспорт/порт | Сигнатура/маркер |
|---|---|---|
| WireGuard | UDP 51820 (по умолч.) | фиксированный формат `message_type` (1–4) |
| OpenVPN | UDP/TCP 1194 | opcode в первом байте (`0x38` — P_CONTROL) |
| IPsec IKE | UDP 500 | заголовок ISAKMP (`0x01 0x10 …`) |
| IPsec NAT-T | UDP 4500 | ISAKMP + non-ESP marker `00 00 00 00` |
| L2TP/IPsec | UDP 1701 | L2TP-заголовок после ESP |
| PPTP | TCP 1723 + GRE | управляющий канал 1723, данные GRE (proto 47) |
| SSL-VPN | TCP 443 | TLS-handshake, часто с вендорным ALPN |

Порт можно и сменить, но сигнатура заголовка остаётся. Поэтому определяй по байтам, а не
только по номеру порта.

## WireGuard: рукопожатие и ключи

WireGuard использует Noise IK-подобное рукопожатие. В дампе видно:

```
$ tshark -r capture.pcap -Y 'udp.port==51820' -T fields \
    -e udp.length -e wireguard.message_type
51820  142  1     # handshake initiation
51820   92  2     # handshake response
```

Типы сообщений: 1 — initiation, 2 — response, 3 — cookie, 4 — transport data. Содержимое
зашифровано ChaCha20-Poly1305, ключи выводятся из Curve25519-ECDH. Без приватного ключа
пира прочитать payload нельзя. Но в расследовании ценно уже то, что **факт туннеля
установлен**: трафик уходил в обход корпоративного периметра. Если ключи найдены на хосте
(`/etc/wireguard/*.conf`, память), WireGuard сам не хранит сессионные ключи на диске —
нужен дамп памяти или повторное рукопожатие.

## OpenVPN: расшифровка при наличии ключей

OpenVPN можно расшифровать, если есть ключи. Способы:

```
# статический ключ (--secret)
$ openvpn --tls-auth ta.key ...            # ta.key на хосте
# сертификат + ключ клиента
$ openssl x509 -in client.crt -noout -text
```

Для расшифровки TLS-режима нужен либо `ta.key`/сертификат, либо сессионные ключи из
`--tls-key`/дампа памяти. Иногда ключи лежат в конфиге рядом: `secret`, `tls-auth`,
`pkcs12`. Формат `openvpn --dev null --ifconfig ...` в логах подсказывает топологию.

## IPsec/IKE: что видно открытым текстом

Фаза IKE-1 устанавливает ключи и часто идёт в открытом виде (кроме агрессивного режима с
PSK). Видны идентификаторы, предлагаемые алгоритмы, версия:

```
$ tshark -r capture.pcap -Y 'isakmp' -T fields \
    -e isakmp.msg.type -e isakmp.vendor_id -e isakmp.ike_version
```

По `vendor_id` можно понять производителя (Cisco, Fortinet, StrongSwan). Данные ESP
зашифрованы; расшифровать можно только при знании PSK или приватного ключа. IKEv2 с
сертификатами оставляет больше метаданных в открытом виде — это помогает идентифицировать
пиры.

## Следы на хосте: конфиги, логи, маршруты

VPN не только в сети — он настраивается на устройстве, и конфиги переживают трафик:

```
$ ls /etc/wireguard/ /etc/openvpn/ 2>/dev/null
$ grep -iE 'Endpoint|AllowedIPs|remote|proto' /etc/wireguard/wg0.conf /etc/openvpn/*.conf
$ ip route show table all | grep -i vpn
$ resolvectl status | grep -i 'DNS Servers'   # DNS leak / туннельный DNS
```

`AllowedIPs = 0.0.0.0/0` в WireGuard или `redirect-gateway def1` в OpenVPN означает
**full-tunnel** — весь трафик уходил в VPN. Наоборот, `AllowedIPs = 10.0.0.0/8` —
split-tunnel: в туннель шла только внутренняя сеть, остальное напрямую. Это различие
критично: оно определяет, какой трафик вообще мог уйти в обход.

## Практический разбор: «туннель в обход»

Сценарий: дамп с непонятным UDP на 51820 и большим объёмом. Порядок:

```
$ capinfos capture.pcap | grep -E 'Packet size|Number of packets'
$ tshark -r capture.pcap -Y 'udp.port==51820' -q -z conv,udp
$ tshark -r capture.pcap -Y 'udp.port==51820' -T fields -e ip.src -e ip.dst | sort -u
```

Видим пару «внутренний хост ↔ внешний endpoint». Дальше ищем конфиг на хосте по endpoint
(`grep -r '203.0.113.5' /etc/`) и учётные данные к нему. Часто в задачах флаг спрятан
именно в `wg0.conf` или в логе демона `openvpn.log`.

## Ограничения

- WireGuard/OpenVPN без ключей — содержимое недоступно; вывод ограничен метаданными.
- Замаскированный VPN на 443 (obfuscation/stealth) выглядит как HTTPS — нужен анализ
  TLS-фингерпринта или поведенческий.
- Обфускация (obfs4, Shadowsocks, stunnel) ещё сильнее скрывает протокол.
- Наличие туннеля не равно нарушению: это может быть штатный корпоративный VPN.

## Если сработало / не сработало

Если порт нестандартный — определяй по сигнатуре заголовка, а не по номеру. Если нужен
payload — ищи ключи на хосте или в дампе памяти. Если дампа нет — работай по конфигам и
логам демонов: они переживают сам трафик.

## Сравнение протоколов: таблица сигнатур

Первое, что нужно сделать с «непонятным» трафиком — определить протокол по порту и
байтам. Сводка:

| Протокол | Транспорт/порт | Признак в трафике | Содержимое |
|---|---|---|---|
| WireGuard | UDP 51820 | минимальные пакеты, message type 1–4 | зашифровано |
| OpenVPN | UDP/TCP 1194 | первый байт — опкод (0x01 handshake) | зашифровано |
| IPsec/IKE | UDP 500/4500 | IKE-заголовок, msg type 1/2 | IKE виден, ESP закрыт |
| PPTP | TCP 1723 + GRE | GRE-инкапсуляция | MPPE, слабый |
| L2TP/IPsec | UDP 1701 + 500 | L2TP-заголовок | зашифровано |
| SSTP | TCP 443 | TLS поверх HTTP | зашифровано |
| SoftEther | TCP 443/992 | своя сигнатура | зашифровано |

```
$ tshark -r capture.pcap -T fields -e frame.number -e ip.proto \
    -e udp.port -e tcp.port -e frame.len | head
```

Протокол, маскирующийся под 443, по порту не отличить от HTTPS — смотри
рукопожатие: настоящий TLS отдаёт `ClientHello`, а обфусцированный VPN — свои байты.

## WireGuard: что видно без ключа

WireGuard использует четыре типа сообщений: `handshake initiation`, `handshake
response`, `cookie reply` и `transport data`. Видно **факт и ритм** рукопожатий, но не
содержимое. Это позволяет:

- определить пары пиров (по IP:port);
- измерить активность (когда канал поднимался/замолкал);
- оценить объём (по размеру транспортных пакетов).

Приватные ключи и конфиги ищи на хосте:

```
$ cat /etc/wireguard/wg0.conf
[Interface]
PrivateKey = <base64>
[Peer]
PublicKey = <base64>
Endpoint = 203.0.113.5:51820
AllowedIPs = 0.0.0.0/0
```

Наличие `PrivateKey` на диске — сам по себе серьёзная находка: по нему можно
восстановить туннель и посмотреть, куда он вёл.

## Расшифровка OpenVPN и IPsec

Если есть **ключи**, туннель можно расшифровать:

- **OpenVPN со статическим ключом** (`--secret`) — используй `--tls-auth`/статический
  ключ из конфига;
- **OpenVPN с TLS** — нужен либо `--keylog`-файл сессии, либо приватный ключ сервера
  и расшифровка TLS-сессии;
- **IPsec с pre-shared key** — `tshark` умеет расшифровывать ESP при заданном PSK:
  `Preferences → ESP → try to decrypt ...` с вводом ключа;
- **IKEv2 с сертификатами** — нужен приватный ключ для расшифровки IKE-аутентификации.

Порядок: сначала ищи конфиги и ключи **на хосте**, затем применяй их к pcap. Без ключа
расшифровка невозможна — это не «недостаток инструмента», а свойство криптографии.

## Артефакты VPN на самом хосте

Трафик — лишь половина картины; вторая — следы на машине:

- **конфиги**: `/etc/wireguard/*.conf`, `/etc/openvpn/`, `~/ovpn/`;
- **сервисы**: `systemctl status wg-quick@wg0`, `openvpn-client@*`;
- **маршруты**: `ip route` покажет `default dev wg0` при full-tunnel;
- **правила**: `iptables -t nat -L` — kill-switch, маскарадинг;
- **логи**: `/var/log/syslog` с записями о поднятии/падении туннеля;
- **DNS**: переопределённый resolver (часто через VPN, чтобы не утекал DNS).

Комбинация «конфиг + активный маршрут + логи» доказывает, что туннель действительно
использовался, а не просто был настроен.

## Обфускация и сокрытие VPN

Злоумышленники прячут VPN под легитимный трафик:

- **stunnel / SSLH** — заворачивают произвольный протокол в TLS на 443;
- **obfs4 / meek** — маскируют под обычный HTTPS, устойчивы к активному зондированию;
- **Shadowsocks** — свой зашифрованный протокол, часто на нестандартном порту;
- **VPN внутри DNS** — туннель через запросы 53-го порта.

Признаки: соединения на 443 без валидного `ClientHello`, аномальные размеры, трафик к
одному адресу в нерабочее время. В таких случаях содержимое недоступно, но
**паттерн** сам по себе — улика обхода контроля.

## Лимитации и корректность выводов

- Без ключей содержимое туннеля недоступно — фиксируй только метаданные.
- Порт не доказывает протокол: 443 может быть чем угодно.
- Отсутствие расшифровки не значит «ничего не нашли» — сам туннель уже факт.
- Всегда проверяй, не является ли «VPN» штатным корпоративным каналом.
- Для суда важна целостность pcap: хешируй до и после анализа.

## Сопоставление с поведением и учётными данными

Туннель сам по себе — не приговор. Чтобы понять, был ли он легитимным, сопоставь его с
поведением пользователя и хоста:

```
$ last -F | head            # кто входил и когда
$ grep -i 'vpn\|tunnel' /var/log/syslog | tail
$ ss -tunp | grep -E '51820|1194|500|4500'
```

Признаки «нештатного» VPN:

- туннель поднят вне рабочих часов и без записи в корпоративной системе VPN;
- `AllowedIPs = 0.0.0.0/0` при том, что корпоративный VPN настроен на split-tunnel;
- endpoint — не корпоративный адрес, а VPS/хостинг;
- конфиг создан недавно, а владелец не помнит установки.

Сопоставление времени поднятия туннеля с временем инцидента часто и есть недостающее
звено между «внешним трафиком» и «конкретным пользователем».

## Быстрый чек-лист по VPN в расследовании

1. Есть дамп? Определи протокол по сигнатуре заголовка, не по порту.
2. WireGuard/OpenVPN без ключей → ограничься фактом и метаданными.
3. Есть ключи/PSK/сертификаты → попробуй расшифровать (OpenVPN, IPsec с известным PSK).
4. Нет дампа → работай по конфигам (`/etc/wireguard`, `/etc/openvpn`, реестр) и логам.
5. Проверь `AllowedIPs`/`redirect-gateway` — full или split tunnel.
6. Проверь DNS-утечки и маршруты (`ip route`, `resolvectl`).
7. Сопоставь время туннеля с сессиями пользователя и инцидентом.

## Что останется на диске после VPN

Даже если трафик не пойман, следы конфигурации и установки остаются:

- установочные пакеты (`wireguard-tools`, `openvpn`) в логах менеджера пакетов;
- ключи и сертификаты в `~/.config`, `/etc/wireguard`, хранилище сертификатов;
- `.ovpn`-профили в «Загрузках» и недавних документах;
- записи в `bash_history` о `wg-quick up`, `openvpn --config`;
- записи DNS/маршрутов, оставшиеся после отключения.

Эти артефакты переживают сам туннель и часто именно в них лежит ответ на вопрос «кто и
зачем».
