## Вопрос, с которого всё начинается

Тебе попался образ Linux-тома, который не ext4 и не XFS. Инструменты его не узнают, а
`file` пишет что-то невнятное. Ты присматриваешься — и видишь знакомые структуры, но
другой ФС. Это может быть **NILFS2** (log-structured ФС со снапшотами) или **Minix FS**
(самая первая файловая система Linux). Как их опознать и что они дают аналитику?

## Что такое NILFS2

**NILFS2 (New Implementation of a Log-structured File System)** — журнальная ФС для
Linux, включённая в ядро. Её особенность — **непрерывные снапшоты**: система регулярно
создаёт **checkpoint** (точку согласованности), и к любой из них можно вернуться. Это
делает NILFS2 любимой ФС для задач, где важна история изменений: отладка, резервное
копирование, судебная экспертиза.

Для аналитика NILFS2 — подарок: если файл удалили или перезаписали, **старая версия
часто доступна через старый checkpoint**. Нужно лишь найти подходящий снапшот.

## Что такое Minix FS

**Minix FS** — файловая система, которую Линус Торвальдс использовал в первых версиях
Linux. Она пришла из ОС Minix Эндрю Таненбаума. Сегодня встречается редко, но её надо
узнавать: она попадается на старых носителях, в учебных задачах и в специфических
встраиваемых системах. Её структура проста: суперблок, битовая карта inode, битовая
карта зон, таблица inode, зоны данных.

## Наш пример: nilfs.img

Смотрим область по смещению **1024 байта** — там суперблок NILFS2 с магией `0x3434`:

```
$ ls -la
-rw-r--r--  1 student student  4194304 nilfs.img
$ xxd -s 1024 -l 8 nilfs.img
00000400: 3434 0000 0000 0000                    44......
```

Байты `34 34` — магия NILFS2. Если бы перед нами был Minix, мы искали бы магию
`0x137F` (14-битные номера зон), `0x138F` (30-битные), `0x2468` (версия 2) или `0x2478`
(версия 3). Эти значения — «отпечатки» конкретной разновидности Minix.

## Шаг 1: текстовые метаданные

```
$ strings nilfs.img
NILFS2: checkpoints=3, snapshots=1
Minix superblock magic: 0x137F (14-bit)
CHECKPOINT: nto{n1lfs2_ch3ckp01nts_4nd_m1n1x}
```

Мы видим число checkpoint'ов и упоминание Minix — полезно, если в образе смешаны
структуры (например, NILFS2 поверх раздела, размеченного когда-то как Minix).

## Шаг 2: checkpoints и снапшоты NILFS2

NILFS2 периодически фиксирует состояние тома в checkpoint. Каждый checkpoint ссылается
на **корневой inode** на тот момент. Список checkpoint'ов смотрят утилитами
`nilfs-utils`:

```
$ lscp nilfs.img
                 CNO        DATE     TIME  MODE  FLG      NBLKINC       ICNT
                   1  2024-03-01 10:00:00   cp    -           11          5
                   2  2024-03-01 11:00:00   cp    -            3          6
                   3  2024-03-01 12:00:00   ss    s            3          6
```

Здесь `cp` — checkpoint, `ss` — snapshot (постоянный). Столбец `CNO` — номер
checkpoint'а. Зная номер, можно **смонтировать** состояние на тот момент:

```
$ mount -t nilfs2 -o cp=2 nilfs.img /mnt/nilfs
```

Это и есть главный приём: восстановление файла, которого «уже нет», из старого checkpoint.

## Шаг 3: Minix — простота как признак

Minix FS настолько проста, что её можно разобрать вручную. Суперблок содержит:

| Поле | Смысл |
|------|-------|
| `s_magic` | сигнатура (0x137F / 0x138F / 0x2468 / 0x2478) |
| `s_ninodes` | число inode |
| `s_nzones` | число зон |
| `s_imap_blocks` | размер карты inode |
| `s_zmap_blocks` | размер карты зон |
| `s_firstdatazone` | первая зона данных |
| `s_log_zone_size` | логарифм размера зоны |

Опознав `s_magic`, ты точно знаешь вариант Minix. Дальше inode и зоны читаются
напрямую — инструмент `minix` в Linux (`mount -t minix`) справляется, если ядро
собрано с поддержкой.

## Другие экзотические ФС

Кроме NILFS2 и Minix, в задачах встречаются:

| ФС | Магия / признак | Где встречается |
|----|-----------------|-----------------|
| BFS | `0x1BADFACE` | старые Unix (SCO) |
| QNX4 | `0x0000002F` | QNX-системы, автоэлектроника |
| HFS (старый) | `BD` по offset 1024 | очень старый macOS |
| UFS/UFS2 | `0x00011954` / `0x19540119` | BSD/Solaris |
| OCFS2 | `OCFSV2` | кластерные Linux-тома |

Общее правило: **сначала найди магию в hex, потом ищи инструмент под неё**. Угадывать
«а вдруг ext4» бессмысленно.

## Частые ошибки и подводные камни

- **Игнорировать смещение.** Суперблоки многих ФС лежат не по offset 0, а по 1024 или
  другому. Смотри разные смещения.
- **Путать варианты Minix.** Четыре разные магии — четыре разных формата зон.
- **Забыть про checkpoint'ы NILFS2.** Без них теряется главное преимущество — история.
- **Пытаться смонтировать «на запись».** Образ должен быть read-only, иначе снапшоты
  могут быть перезаписаны.
- **Игнорировать «битые» старые снапшоты.** Не каждый checkpoint валиден; проверяй.

## Мини-практика

Дан `nilfs.img`. Опознаём ФС и достаём checkpoint:

```
$ xxd -s 1024 -l 8 nilfs.img
00000400: 3434 0000 0000 0000                    44......
$ strings nilfs.img | grep nto > answer.txt
$ cat answer.txt
CHECKPOINT: nto{n1lfs2_ch3ckp01nts_4nd_m1n1x}
```

Мы подтвердили NILFS2 по магии `34 34` и вытащили метку. В реальном разборе дальше —
`lscp` для списка checkpoint'ов и монтирование нужного снапшота.

## Что мы теперь знаем

- NILFS2 опознаётся по магии `0x3434` по offset 1024.
- Её сила — непрерывные checkpoint'ы и снапшоты: история изменений сохраняется.
- Minix FS имеет несколько магий (0x137F/0x138F/0x2468/0x2478).
- Восстановление NILFS2 — монтирование по `cp=N`.
- Экзотику опознают по магии, а не перебором инструментов.

## Восстановление удалённого файла из checkpoint

Главная практическая ценность NILFS2 — возможность «отмотать» том назад. Разберём это
пошагово. Пусть пользователь удалил файл `secret.txt`, но на томе сохранились
checkpoint'ы. Наша цель — вернуть файл.

```
$ lscp nilfs.img
                 CNO        DATE     TIME  MODE  FLG      NBLKINC       ICNT
                   1  2024-03-01 10:00:00   cp    -           11          5
                   2  2024-03-01 11:00:00   cp    -            3          6
                   3  2024-03-01 12:00:00   cp    -            3          6
```

Смотрим, в каком checkpoint'е файл ещё существовал. Если он был удалён между 11:00 и
12:00, берём checkpoint 2:

```
$ mkdir /mnt/old
$ mount -t nilfs2 -o cp=2 nilfs.img /mnt/old
$ ls /mnt/old
secret.txt
$ cat /mnt/old/secret.txt
nto{n1lfs2_ch3ckp01nts_4nd_m1n1x}
```

Файл вернулся. Это и есть ключевой приём NILFS2: **не carving, а история**. Важно
монтировать **только для чтения** (`-o ro`), иначе новые записи могут вытеснить старые
checkpoint'ы.

## UFS/BSD: ещё один частый гость

Кроме NILFS2 и Minix, в задачах встречается **UFS (Unix File System)** — ФС BSD и
Solaris. Её суперблок лежит по смещениям 8192 (UFS1), 65536 (UFS2) или 262144 (Sun).
Магия — `0x00011954` (UFS1) и `0x19540119` (UFS2). В UFS есть **цилиндрические группы**,
inode и блоки, а также снапшоты (в UFS2) — то есть, как и в NILFS2, есть шанс восстановить
прошлое состояние.

| ФС | Магия | Смещение суперблока |
|----|-------|---------------------|
| NILFS2 | 0x3434 | 1024 |
| Minix v1/v3 | 0x137F / 0x2478 | 1024 |
| UFS1 | 0x00011954 | 8192 |
| UFS2 | 0x19540119 | 65536 |

## Практический сценарий: незнакомый образ

Ты получил образ и не знаешь ФС. Не перебирай инструменты наугад — действуй по чек-листу:

1. `file image.img` — что скажет сама система.
2. `xxd -l 32 image.img` — есть ли магия в начале.
3. `xxd -s 1024 -l 16 image.img` — суперблок многих ФС здесь.
4. `xxd -s 8192 -l 16 image.img` — область UFS.
5. `strings -n 8 image.img | head` — текстовые подсказки.
6. `binwalk image.img` — сигнатуры вложенных ФС.

```
$ binwalk image.img
DECIMAL    HEXADECIMAL   DESCRIPTION
0          0x0           Minix filesystem, magic 0x137F
```

Сопоставив магию с таблицей, ты за минуту определишь формат и возьмёшь правильный
инструмент. Такой чек-лист экономит часы на «неизвестных» образах.

## Почему это важно за пределами CTF

Экзотические ФС — это не только учебные задачи. В реальных расследованиях попадаются
серверы с NILFS2 (для истории), старые носители с Minix/UFS и встраиваемые системы с
нестандартными ФС. Умение опознать формат по магии и понять его логику — базовый навык,
без которого образ превращается в «мусор». А способность использовать снапшоты даёт то,
чего не даёт обычный recovery: **точку во времени**, а не просто «какие-то удалённые
байты».

## Forensic readiness: как это помогает расследованию

NILFS2 — редкий пример ФС, где **forensic readiness** (готовность к расследованию)
заложена в саму архитектуру. В обычных ФС удалённые данные приходится выцарапывать
carving'ом, угадывая, что было. Здесь история изменений сохраняется штатно — при
правильной настройке администратор может позже доказать, что и когда менялось.

Практические рекомендации для инцидента на NILFS2:

- **не монтируйте образ на запись** — иначе сборщик мусора вытеснит старые checkpoint'ы;
- зафиксируйте **список checkpoint'ов** (`lscp`) сразу, он и есть «шкала времени»;
- для каждого интересующего события монтируйте **предыдущий** checkpoint и сравнивайте;
- помните, что удаление checkpoint'а (`nilfs_cleanerd`) необратимо — его уже не вернуть.

Такая «шкала времени» — то, чего не хватает большинству ФС. Именно поэтому NILFS2
встречается в задачах, где нужно доказать последовательность действий, а не просто
восстановить один файл.
