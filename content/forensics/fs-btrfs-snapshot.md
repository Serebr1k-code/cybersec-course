## Вопрос, с которого всё начинается

На сервере, где стояла база данных, нашли «чистый» том — никаких следов удаления.
Но подозревают, что администратор удалил данные уже после инцидента. Как это проверить?
На выручку приходит **Btrfs**: её снапшоты хранят старые версии дерева файлов, и удалённое
«на живую» может лежать в снапшоте нетронутым.

## Что такое Btrfs и subvolume

**Btrfs (B-tree File System)** — современная файловая система Linux с поддержкой снапшотов,
сжатия, контрольных сумм и пулов устройств. Её ключевая идея — **copy-on-write (CoW,
«копирование при записи»)**: данные никогда не перезаписываются на месте. Когда файл
меняется, новая версия блока пишется в свободное место, а указатели в дереве обновляются.

Из CoW вырастает понятие **subvolume** — «подтома». Это отдельное дерево файлов внутри
общего пула Btrfs. С точки зрения пользователя subvolume выглядит как каталог, но
технически это самостоятельная корневая точка со своей нумерацией. **Снапшот (snapshot)** —
это subvolume, который создали как мгновенную копию другого subvolume. Данные при этом не
копируются физически: снапшот просто ссылается на те же блоки, а дальнейшие изменения
уходят в новые блоки. Именно поэтому снапшот мгновенный и дешёвый по месту.

## Наш пример: образ с замаскированным удалением

Мы сняли образ серверного тома и смотрим его метаданные:

```
$ ls -la
-rw-r--r-- 1 student student 67108864 server.img
$ file server.img
server.img: BTRFS Filesystem (label dbdata), sectorsize=4096, nodesize=16384
```

Команда `file` уже опознала Btrfs. Если бы она молчала, мы бы искали магию вручную.
Суперблок Btrfs лежит по смещению **65536 (0x10000)**, а его подпись — восьмибайтовая
строка `_BHRfS_M` по смещению 65600 (0x10040). Проверим:

```
$ xxd -s 0x10040 -l 8 server.img
00010040: 5f42 4852 6653 5f4d                      _BHRfS_M
```

Подпись совпала — это действительно Btrfs. Теперь смотрим текстовые метаданные:

```
$ strings server.img | grep -Ei 'BHRfS|snapshot|generation|subvol'
_BHRfS_M
subvol root gen=118
snapshot dbdata/snap-2026-03-11 gen=92
snapshot dbdata/snap-2026-03-12 gen=104
LABEL: nto{btrfs_sn4psh0t_g3n3r4t10n}
```

Мы видим два снапшота с номерами **generation** (поколение — счётчик транзакций, который
растёт при каждой записи). Разные поколения — это разные моменты времени. Если удалённый
файл существовал в поколении 92, но отсутствует в текущем дереве, он всё ещё лежит в
снапшоте `snap-2026-03-11`. Вот почему Btrfs — находка для форензики.

## Шаг 1: поколения — это «часы» файловой системы

**Generation (gen)** в Btrfs — монотонно растущее число, которое увеличивается на каждой
закоммиченной транзакции. Это не wall-clock время, но оно строго упорядочено. Сравнивая
поколения, ты можешь восстановить последовательность событий: «этот блок создан раньше,
этот — позже». Снапшот фиксирует поколение, на котором он был сделан:

| Артефакт | Что означает |
|----------|--------------|
| `gen` текущего дерева | сколько транзакций прошло с создания тома |
| `gen` снапшота | на каком поколении зафиксирован снапшот |
| generation при монтировании | минимальное поколение среди деревьев |
| `btrfs subvolume find-new` | файлы, изменённые после заданного поколения |

Команда `btrfs subvolume find-new <subvol> <gen>` показывает всё, что менялось после
указанного поколения — это прямой аналог «найти недавние изменения» для расследования.

## Шаг 2: монтируем и перечисляем subvolume

Чтобы работать с томом, его нужно смонтировать (только для чтения — важное правило
форензики). Мы **не** монтируем оригинал напрямую, а сначала делаем копию образа:

```
$ sudo losetup -r /dev/loop9 server.img
$ sudo mount -o ro,subvolid=5 /dev/loop9 /mnt/btrfs
$ sudo btrfs subvolume list /mnt/btrfs
ID 256 gen 118 top level 5 path dbdata
ID 257 gen 92  top level 5 path snap-2026-03-11
ID 258 gen 104 top level 5 path snap-2026-03-12
```

Обрати внимание на `subvolid=5`: это **корень дерева** Btrfs, под которым живут все
subvolume. Монтировать саму ФС «как есть» (без указания корня) — классическая ошибка: ты
увидишь только один subvolume и решишь, что снапшотов нет.

## Шаг 3: вытаскиваем данные из снапшота

Допустим, в текущем дереве файла `dbdata/customers.db` нет — его удалили. Проверяем снапшот:

```
$ ls -la /mnt/btrfs/snap-2026-03-11/
-rw-r--r-- 1 root root 1048576 Mar 11 02:14 customers.db
```

Файл на месте. Копируем его **на отдельный носитель** (никогда не пиши обратно в образ):

```
$ sudo btrfs restore -i -o -t 16384 /dev/loop9 /evidence/restored/
$ ls /evidence/restored/
customers.db  audit.log
```

Флаг `-t 16384` задаёт размер узла (nodesize) из суперблока — без него `btrfs restore`
может не найти дерево. `btrfs restore` умеет работать **напрямую с образом**, без монтирования:
это спасает, когда том повреждён или это единственный способ не трогать оригинал.

## Шаг 4: находим «корень» повреждённого тома

Если снапшоты не читаются — возможно, повреждён корневой указатель. Тогда пригодится:

```
$ sudo btrfs-find-root /dev/loop9
Superblock thinks the generation is 118
Superblock thinks the level is 1
Well block 30408704 (gen: 92) seems good, but generation level 0 doesn't match
Well block 30474240 (gen: 104) seems good, but generation level 0 doesn't match
```

`btrfs-find-root` перебирает кандидаты корневых блоков по всему тому и показывает их
поколения. Это как «резервные копии указателя»: даже если актуальный корень битый, старый
ещё лежит на диске.

## Частые ошибки и подводные камни

- **Монтирование с записью.** Любая запись в Btrfs меняет поколение и может запустить
  фоновый `btrfs balance`, который физически перезапишет старые блоки. Всегда `-o ro`.
- **Игнорирование subvolid=5.** Без монтирования корня снапшоты «не видны».
- **Путаница снапшота и обычного каталога.** Копирование каталога `cp -r` — это копия
  данных, а снапшот — общий указатель. Для форензики важен именно снапшот: он хранит
  блоки, которые иначе были бы освобождены.
- **Ожидание «вечных» данных.** CoW хранит старые блоки, пока на них есть ссылка. Как
  только снапшот удалили (`btrfs subvolume delete`), сборщик мусора их освободит — и
  данные исчезнут. Снапшот нужно сохранить первым делом.
- **Сжатие.** Btrfs сжимает данные (zlib/zstd/lzo), поэтому `strings` может не показать
  текст: сначала распакуй (монтирование с `compress=` покажет распакованное).

## Что мы теперь знаем

- Btrfs подписывается магией `_BHRfS_M` по смещению 0x10040.
- subvolume — отдельное дерево, снапшот — зафиксированная версия дерева.
- Generation — упорядоченные «часы» тома; по ним сравнивают версии.
- Снапшоты хранят удалённые данные, пока их не удалили и не освободили блоки.
- Инструменты: `btrfs subvolume list/show`, `btrfs restore`, `btrfs-find-root`,
  `btrfs inspect-internal dump-super`.

## Что фиксировать в отчёте

| Что | Зачем |
|-----|-------|
| Список subvolume и их gen | показать, какие версии сохранены |
| Время создания снапшотов | привязать к инциденту |
| Что нашлось в снапшоте, но удалено сейчас | доказательство удаления |
| Метод извлечения (restore/mount) | воспроизводимость |
| Хеши извлечённых файлов | целостность доказательств |

## Мини-практика: что менялось после инцидента

Снапшоты дают не только «старые файлы», но и инструмент сравнения. Допустим, инцидент
случился 11 марта. Мы хотим увидеть всё, что менялось после поколения 100:

```
$ sudo btrfs subvolume find-new /mnt/btrfs/dbdata 100
inode 257 file offset 0 len 4096 disk start 1234567 offset 0 gen 104 flags NONE dbdata/customers.db
inode 258 file offset 0 len 8192 disk start 1234890 offset 0 gen 118 flags NONE dbdata/audit.log
```

Каждая строка — файл, чей блок был создан на поколении больше 100. Если файл в списке
есть, а в текущем дереве его нет — значит, его создали и удалили после инцидента. Это
прямое доказательство активности уже **после** предполагаемого времени.

Полезно сравнить два снапшота между собой. Смонтируй оба и прогони `diff`:

```
$ sudo mount -o ro,subvol=snap-2026-03-11 /dev/loop9 /mnt/s11
$ sudo mount -o ro,subvol=snap-2026-03-12 /dev/loop9 /mnt/s12
$ diff -rq /mnt/s11 /mnt/s12
Files /mnt/s11/customers.db and /mnt/s12/customers.db differ
Only in /mnt/s11: backup.tar.gz
```

Так видно, что между 11 и 12 марта файл `backup.tar.gz` исчез, а база изменилась. Это и
есть таймлайн на уровне дерева, без разбора отдельных метаданных.

## Сравнение с другими CoW-файловыми системами

Снапшоты есть не только у Btrfs, и полезно понимать разницу:

| ФС | Механизм снимка | Особенность для форензики |
|----|-----------------|---------------------------|
| Btrfs | subvolume-снапшот | `subvolid=5` открывает все снапшоты сразу |
| ZFS | датасет-снапшот + txg | `zpool history` логирует `zfs snapshot/destroy` |
| APFS | снапшот тома | снапшоты хранятся в самом контейнере APFS |
| LVM | thin-snapshot | снимок блочного устройства, а не ФС |

Общий принцип один: CoW не перезаписывает блоки, пока на них есть ссылка, и снимок — эта
ссылка. Разница в том, **где искать список снимков** и как быстро их извлечь. На Btrfs это
`btrfs subvolume list`, на ZFS — `zfs list -t snapshot`, на APFS — `apfs_snapshots`.

Отдельная тонкость: удаление снапшота запускает освобождение блоков **асинхронно**. Если
снапшот удалили минуту назад, данные часто ещё на диске — успей снять образ. Именно поэтому
первым действием всегда делают **полную побитовую копию** носителя, а уже потом разбираются
со снапшотами.

## Куда дальше

Мы разобрали снапшоты Btrfs. Дальше возьмём **ZFS** — там похожий CoW, но свои
uberblock-и, ARC-кэш и ZIL-журнал: они объясняют, почему «свежие» записи иногда лежат
только в журнале. А пока главное запомни: **снапшот — это окно в прошлое дерева, и его
надо сохранить раньше, чем удалять**.

## Где пригодится

- **CTF Forensics:** образы Linux с Btrfs, где данные «исчезли» из основного дерева.
- **DFIR:** доказательство удаления данных после инцидента через снапшоты.
- **Data recovery:** извлечение файлов из снапшотов при сбое.
- **Администрирование:** понимание, почему снапшоты занимают место.
