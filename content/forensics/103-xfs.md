## Вопрос, с которого всё начинается

С сервера Linux сняли образ диска. По данным админов, на нём был отчёт, который сотрудник «удалил перед увольнением». Файловая система тома — не привычная ext4, а **XFS**. Задача: найти и восстановить удалённый файл.

XFS — высокопроизводительная ФС, используемая по умолчанию в RHEL/CentOS и на больших серверных томах. У неё есть особенность, которую надо понять до разбора: том делится на независимые области. Разберём том и восстановим отчёт.

## Наш пример: серверный XFS-том `disk.img`

Определяем файловую систему по «магии» в начале:

```bash
$ xxd -l 4 disk.img
00000000: 5846 5342                                XFSB
```

`XFSB` — сигнатура **суперблока** XFS, главной структуры ФС. Суперблок хранит все параметры тома. Читаем их через `fsstat`:

```bash
$ fsstat -o 2048 disk.img | head -10
File System Type: XFS
Block Size: 4096
Inode Size: 256
```

`Block Size` — размер блока (4096 байт), `Inode Size` — размер inode (256 байт). **Inode** — это структура, описывающая один файл: его права, размер и карту расположения данных.

## Шаг 1: понимаем allocation groups

Ключевое отличие XFS от ext4: том делится на **allocation groups** (AG) — независимые области, каждая со своими метаданными (копией суперблока, свободным местом, inode). В суперблоке есть два поля, задающих эту сетку: `agcount` (число AG) и `agblocks` (блоков в одной AG).

Отсюда главное следствие для аналитика: **«глобального» номера inode нет**. Номер раскладывается на пару «номер AG + индекс внутри неё»:

```
ino = (agno << agino_log) | agino
```

Если искать данные по «номеру inode» как по байтовому смещению, получишь мусор — надо раскладывать на AG. Именно поэтому XFS разбирают не «в лоб», а инструментами, которые знают про AG.

## Шаг 2: находим удалённый файл

`fls` из набора sleuthkit умеет работать с XFS и показывает удалённые записи:

```bash
$ fls -o 2048 -r -d disk.img
r/r * 131: data/report.pdf
```

Звёздочка `*` — запись удалена, `131` — номер inode. Найден `data/report.pdf` — тот самый отчёт. Восстанавливаем:

```bash
$ icat -o 2048 disk.img 131 > report.pdf
$ file report.pdf
report.pdf: PDF document, version 1.4
```

Sleuthkit сам разложил номер inode на (AG, индекс) и собрал данные. Файл восстановлен.

## Шаг 3: понимаем, где лежали данные

Как и в FAT, данные файла в XFS описываются не «подряд», а картой расположения. XFS использует **extents** — записи вида «диапазон блоков на диске». У маленьких и средних файлов карта extents лежит **прямо в inode**. У больших и фрагментированных — корень **B-дерева** в inode, а листья в отдельных блоках.

Удаление файла снимает ссылку из каталога и обнуляет счётчик ссылок (`nlink = 0`), но **extents часто остаются** в inode. Пока блоки не перезаписаны, данные читаются. Поэтому «удалённый inode с сохранившимися extents» — обычный сценарий восстановления.

## Шаг 4: глубокий разбор через xfs_db

Когда нужно заглянуть внутрь структур, используют `xfs_db`. Всегда с ключом `-r` (read-only), чтобы не изменить образ:

```bash
$ xfs_db -r -c "sb 0" -c "print" disk.img
$ xfs_db -r -c "inode 131" -c "print" disk.img
magicnum = 0x494e
mode = 0100644
nlink = 0
size = 48213
nextents = 2
```

Разберём поля. `magicnum = 0x494e` — сигнатура inode (`IN`). `mode = 0100644` кодирует тип и права: старшие биты — тип (обычный файл), младшие — права. `nlink = 0` — счётчик ссылок обнулён, признак удаления. `nextents = 2` — карта состоит из двух экстентов. Посмотреть саму карту можно командой `bmap`:

```bash
$ xfs_db -r -c "inode 131" -c "bmap -v" disk.img
```

## Шаг 5: журнал и метаданные

XFS — журналируемая ФС: все изменения метаданных сначала пишутся в **журнал** (его начало задано полем `logstart` в суперблоке). Журнал — кольцевой буфер, и в нём могут храниться **предыдущие версии** блоков: старые записи каталогов, удалённые inode, прежние extents. Это дополнительный источник восстановления:

```bash
$ xfs_logprint disk.img | head -50
```

Есть и удобный приём — дамп только метаданных, без содержимого файлов:

```bash
$ xfs_metadump disk.img meta.img
```

`xfs_metadump` создаёт образ метаданных, который можно передать коллеге для анализа, не рискуя утечкой данных клиента.

## Полный разбор: от суперблока к удалённому файлу

Прогоним разбор XFS-тома в один сценарий.

1. **Читаем суперблок.** `xfs_db -r -c 'sb 0' -c 'print' disk.img` — размер блока, число **allocation groups** (AG), версия.
2. **Идём по AG.** XFS делит том на AG; каждая — независимая единица с собственным деревом свободного места. Это ключ к масштабируемости.
3. **Смотрим inode.** `xfs_db -r -c 'inode <num>' disk.img` — тип, размер, extent'ы (где лежат данные).
4. **Ищем удалённый.** У удалённого inode меняется «режим» (link count 0), но extent'ы часто целы — читаем данные напрямую.
5. **Журнал.** XFS ведёт журнал метаданных: незавершённые операции можно «доиграть» и увидеть, что менялось до сбоя.

## Шпаргалка XFS

| Структура | Что даёт |
|-----------|----------|
| Суперблок (+копии) | параметры тома, число AG |
| Allocation Group | независимый блок управления пространством |
| Inode (v5) | метаданные файла, extent'ы |
| B-дерево каталога | сопоставление имя → inode |
| Журнал (log) | операции метаданных |

Inode v5 добавляет CRC и идентификаторы — полезно для проверки целостности при восстановлении.

## Частые вопросы

**Чем XFS отличается от ext4?** Нет «фиксированного» расположения таблиц; всё через B-деревья и AG — быстрее на больших томах, но сложнее ручной разбор.

**Как быстро найти удалённые файлы?** `xfs_db` + перебор inode, либо `xfs_repair -n` (только проверка) и карвинг.

**Почему копий суперблока несколько?** XFS хранит резервные копии в разных AG — том выживает при повреждении первой.

**Метаданные журнала восстанавливают данные?** Журнал — про метаданные, не про содержимое; данные берут из extent'ов.

## Что мы теперь знаем

- Суперблок XFS начинается с `XFSB` и хранит размер блока, inode и сетку AG.
- Том делится на **allocation groups** (AG) — независимые области; номер inode раскладывается на (AG, индекс).
- Данные файла описываются **extents**; у малых файлов карта лежит в inode, у больших — B-дерево.
- Удаление обнуляет `nlink`, но extents часто сохраняются — файл восстановим.
- `fls -r -d` находит удалённые inode, `icat` читает данные; `xfs_db -r` даёт глубокий разбор.
- Журнал (`logstart`) хранит старые версии метаданных; `xfs_metadump` делает дамп только метаданных.
