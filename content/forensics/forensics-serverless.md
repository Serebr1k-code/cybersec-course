## Вопрос, с которого всё начинается

В облаке атакующий использовал **serverless-функцию**, чтобы не поднимать сервер. Функция
отработала за секунды и исчезла. Диска нет, процесса нет, памяти нет. Что вообще можно
расследовать?

## Наш пример: подозрительная функция

Находим функцию `process-upload` в AWS Lambda. Смотрим её конфигурацию:

```
$ aws lambda get-function-configuration --function-name process-upload
{
  "FunctionArn": "arn:aws:lambda:eu-west-1:123456789012:function:process-upload",
  "Runtime": "python3.11",
  "Role": "arn:aws:iam::123456789012:role/process-upload-role",
  "Timeout": 900,
  "Environment": { "Variables": { "BUCKET": "data-bucket" } },
  "LastModified": "2026-03-10T03:14:00.000+0000"
}
```

Уже здесь много улик: роль, таймаут 900 секунд (необычно много), переменные окружения,
время последнего изменения.

## Что такое serverless

**Serverless (функция как сервис)** — модель, где ты пишешь код, а провайдер сам его
запускает по событию. Функция живёт только на время выполнения (обычно до 15 минут),
потом среда уничтожается. Диска, который можно «снять», нет. Зато провайдер ведёт
**логи** и **события управления**.

## Шаг 1: логи выполнения

Каждый запуск пишет в лог-сервис (CloudWatch Logs):

```
$ aws logs filter-log-events --log-group-name /aws/lambda/process-upload \
    --filter-pattern "ERROR"
2026-03-10T03:14:05Z  task timed out after 900.00 seconds
2026-03-10T03:14:07Z  uploading to s3://exfil-bucket/...
```

Логи показывают **что функция делала**: обращалась к подозрительному бакету
`exfil-bucket`. Это ключевая улика.

## Шаг 2: роль исполнения

Функция работает под **IAM-ролью**. Её права показывают, **что функция могла**:

```
$ aws iam get-role-policy --role-name process-upload-role --policy-name inline
{ "Action": ["s3:PutObject", "s3:GetObject", "secretsmanager:GetSecretValue"], ... }
```

Право `GetSecretValue` + `PutObject` = потенциальная утечка секретов наружу.

## Шаг 3: события управления (CloudTrail)

CloudTrail фиксирует **кто и когда** менял функцию:

```
$ aws cloudtrail lookup-events --lookup-attributes AttributeKey=ResourceName,AttributeValue=process-upload
UpdateFunctionCode  user/alice  2026-03-10T03:10:00Z
```

Видно, что код функции обновили за 4 минуты до запуска — вероятно, это и был атакующий.

## Шаг 4: версии и слои

Lambda хранит **версии** кода. Можно сравнить старую и новую:

```
$ aws lambda get-function --function-name process-upload --qualifier 3
$ aws lambda get-function --function-name process-upload --qualifier 4
```

Также проверяются **слои** (layers) — общие библиотеки, куда могли внедрить код. Всё это
даёт версии артефактов для анализа.

## Что переживает «исчезновение» функции

Хотя среда уничтожается, остаются:

- **логи** выполнения (в лог-сервисе);
- **события управления** (CloudTrail);
- **конфигурация и версии** кода;
- **роль и её политики**;
- **следы в других сервисах** (S3, KMS, базы), к которым функция обращалась.

Именно эта «периферия» и есть объект расследования.

## Как события провайдера превращаются в таймлайн

У serverless-расследования нет «диска», но есть плотный поток событий. Их сводят в один таймлайн по времени:

```
03:10:00  CloudTrail   UpdateFunctionCode  user/alice
03:14:00  Lambda       LastModified        process-upload (v4)
03:14:05  CloudWatch   task timed out after 900s
03:14:07  CloudWatch   uploading to s3://exfil-bucket/...
03:15:00  CloudTrail   AssumeRole          process-upload-role
03:16:00  S3           PutObject           exfil-bucket
```

Читаем картину: за 4 минуты до запуска кто-то обновил код функции, затем она отработала, обратилась к подозрительному бакету и выгрузила данные. Каждое событие — отдельный источник, а вместе они образуют причинно-следственную цепочку. Такой таймлайн и есть замена «образу диска».

## Полный прогон: реконструкция атаки через Lambda

```
# 1. Кто менял код и когда
$ aws cloudtrail lookup-events --lookup-attributes \
    AttributeKey=ResourceName,AttributeValue=process-upload \
    --query 'Events[].{t:EventTime,n:EventName,u:Username}'
[{"t":"2026-03-10T03:10:00Z","n":"UpdateFunctionCode","u":"user/alice"}]

# 2. Что функция делала
$ aws logs filter-log-events --log-group-name /aws/lambda/process-upload \
    --start-time 1770000000000 --filter-pattern "s3://"
uploading to s3://exfil-bucket/...

# 3. Под какой ролью и с какими правами
$ aws iam get-role --role-name process-upload-role --query 'Role.AssumeRolePolicyDocument'

# 4. Обращения к секретам
$ aws cloudtrail lookup-events --lookup-attributes \
    AttributeKey=EventName,AttributeValue=GetSecretValue
```

Если `user/alice` легитимен, но `UpdateFunctionCode` пришёл с нового IP — возможно, ключи `alice` скомпрометированы. Роль `process-upload-role` с `GetSecretValue` + `PutObject` — это готовый канал утечки: прочитать секрет и выгрузить наружу.

## Сервисы-источники улик в AWS

| Сервис | Что хранит | Ценность |
|---|---|---|
| CloudTrail | события управления (API-вызовы) | кто/что/когда менял |
| CloudWatch Logs | вывод функций и сервисов | действия во время запуска |
| Lambda | конфигурация, версии, слои | что запускалось и какой код |
| IAM | роли, политики, ключи | права и атрибуция |
| S3 (access logs) | обращения к объектам | чтение/выгрузка данных |
| VPC Flow Logs | сетевые потоки | связи с внешними адресами |
| KMS | использование ключей | расшифровка секретов |
| GuardDuty | детекты угроз | готовые находки |

## IAM-роль и принцип наименьших привилегий

Функция действует под ролью, и её политика — это её «потолок возможностей». Аудит сводится к поиску избыточных прав:

```
$ aws iam list-attached-role-policies --role-name process-upload-role
$ aws iam get-policy-version --policy-arn ... --version-id v1
```

Красные флаги: `*:*`, `iam:PassRole`, `sts:AssumeRole` на широкий круг, `s3:*` на все бакеты, `secretsmanager:GetSecretValue` без ограничения по ресурсу. Часто скомпрометированная функция с избыточной ролью становится плацдармом для всей учётной записи облака.

## Крайние случаи и ограничения

- **Короткое окно логов.** CloudWatch Logs хранятся ограниченное время (по умолчанию часто 30–90 дней); старые события исчезают, и восстановить их нельзя.
- **Логи можно отключить.** Атакующий может удалить лог-группу или отключить трассировку — тогда опора на CloudTrail (который в организации обычно отдельный).
- **Другие аккаунты.** В мультиаккаунтной среде события могут быть в отдельном лог-архивном аккаунте, доступ к которому ограничен.
- **Код перезаписан.** Если версии не сохранялись, исходный вредоносный код не достать — остаются только логи и метаданные.
- **Метаданные не защищены.** Как и в мессенджерах, содержимое логов может быть вычищено, но факт и время вызовов остаются.

## Serverless на других платформах

Тот же подход работает везде, меняются лишь названия сервисов: Azure Functions (логи — Application Insights, события — Azure Activity Log), Google Cloud Run/Functions (логи — Cloud Logging, события — Cloud Audit Logs). Принцип один: у бессерверного кода нет диска, поэтому расследование идёт по **логам выполнения**, **событиям управления** и **правам роли**. Начни с «кто мог запускать» (роль и её триггер), затем «что делал» (логи), затем «кто менял код» (аудит-события).

## Чек-лист расследования и типичные ошибки

Порядок работы с инцидентом в serverless:

1. **Идентифицируй функцию.** Найди её ARN, рантайм, таймаут, переменные окружения. Аномальный таймаут (например, 900 секунд вместо штатных 3) — сигнал.
2. **Зафиксируй роль.** Собери прикреплённые и inline-политики, найди избыточные права (`GetSecretValue`, `s3:*`, `iam:PassRole`).
3. **Пройди по событиям управления.** CloudTrail по имени функции: кто и когда менял код, конфигурацию, переменные, слои.
4. **Собери логи выполнения.** CloudWatch Logs: какие внешние адреса, бакеты, базы функция трогала.
5. **Проследи поток данных.** S3 access logs, KMS, VPC Flow Logs — куда ушли данные.
6. **Построй таймлайн.** Сведи всё по времени; ищи причинно-следственную связь «изменение кода → запуск → выгрузка».

Типичные ошибки:

- **Искать «образ».** У serverless нет диска; попытка снять «машину» бесполезна. Расследование — событийное.
- **Ограничиться одним сервисом.** Логи функции без CloudTrail не покажут, **кто** её менял; CloudTrail без логов не покажет, **что** она делала.
- **Забыть про срок хранения.** CloudWatch Logs по умолчанию хранятся ограниченно; к моменту разбора окно может закрыться. Экспорт в S3 с длительным хранением — обязательная мера.
- **Не проверить переменные окружения.** Секреты часто лежат прямо в `Environment.Variables`; утечка конфигурации = утечка секретов.
- **Игнорировать слои.** Общий слой (layer), используемый многими функциями, — идеальное место для внедрения кода сразу во все.

## Сводка по сервисам и выводам

Ключевая мысль: serverless-функция — это **эфемерная** среда, но её **метаданные** живут долго и в нескольких сервисах. Поэтому расследование строится не на «трупе» (его нет), а на «тени» — записях о том, что среда делала. Роль, конфигурация, версии кода, логи выполнения и события управления вместе заменяют отсутствующий диск. Если хотя бы два независимых источника (например, CloudWatch и CloudTrail) согласованы, вывод устойчив; если они расходятся, ищи подделку или потерю логов.

## Что запомнить

Главный вывод: у бессерверного кода нет диска, но есть **периферия** — роль, конфигурация, версии, логи и события управления. Именно она и является объектом расследования. Строй вывод на согласии минимум двух независимых источников и помни, что короткое окно хранения логов может закрыться раньше, чем начнётся разбор.

## Дополнительная заметка

Практический совет: заранее настрой экспорт логов Lambda в S3 с длительным сроком хранения и включи трассировку CloudTrail в отдельном аккаунте-архиве. Без этого к моменту разбора окно логов закроется, и восстановить картину будет нечем — а роль, конфигурация и версии без событий дают лишь догадки, а не доказательства.

## Что мы теперь знаем

- У serverless нет диска — расследуют логи, конфигурацию и события.
- Логи выполнения показывают действия функции.
- Роль исполнения показывает её права.
- CloudTrail фиксирует, кто менял код.
- Версии и слои дают артефакты для анализа.
