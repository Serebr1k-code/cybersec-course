## Вопрос, с которого всё начинается

В прошлом уроке мы вручную нашли один ZIP внутри PNG: посмотрели сигнатуру, посчитали
смещение, вырезали `dd`. Это работает, когда внутри спрятан один файл. А если их десять?
Если внутри прошивки лежит файловая система, а внутри неё — картинки и архивы?

Вручную перебирать сигнатуры по гигабайтному образу невозможно. Этот урок — про
**carving**: автоматический поиск и извлечение данных по сигнатурам, без опоры на
структуру каталогов.

## Наш пример: firmware.bin

Тебе дали файл прошивки роутера. Первая команда, как всегда:

```bash
$ file firmware.bin
firmware.bin: data
```

Опять «data» — сигнатура незнакомая. Смотрим, что внутри, сканером сигнатур:

```bash
$ binwalk firmware.bin
DECIMAL       HEXADECIMAL     DESCRIPTION
0             0x0             uImage header, header size: 64 bytes, ...
64            0x40            LZMA compressed data, properties: 0x5D, ...
1048576       0x100000        Squashfs filesystem, little endian, version 4.0, ...
2097152       0x200000        JPEG image data, JFIF standard 1.01
```

`binwalk` прошёл по файлу и нашёл сразу четыре объекта: заголовок ядра (`uImage`),
сжатый блок (`LZMA`), файловую систему (`Squashfs`) и картинку `JPEG`. Колонка
`DECIMAL` — смещение в байтах, `HEXADECIMAL` — то же в hex. Именно по этим смещениям
и работают дальше.

**Carving** (от англ. carve — «вырезать») — это и есть восстановление файлов из
сырого потока по сигнатурам. Ни имён, ни путей он не восстанавливает — только
содержимое. Поэтому carving всегда дополняют анализом структуры.

## Извлекаем всё сразу

`binwalk` умеет не только находить, но и распаковывать:

```bash
$ binwalk -e -M firmware.bin -C out/
$ find out/ -type f
out/_firmware.bin.extracted/0
out/_firmware.bin.extracted/40
out/_firmware.bin.extracted/100000.squashfs
out/_firmware.bin.extracted/200000.jpg
```

Флаги: `-e` — извлечь найденное, `-M` — спускаться во вложенное рекурсивно
(`--matryoshka`, «матрёшка»), `-C` — куда складывать результат. Каждый извлечённый
файл назван по своему смещению.

Проверим, что получилось:

```bash
$ file out/_firmware.bin.extracted/*
.../0:               Linux kernel ARM boot executable zImage
.../40:              LZMA compressed data
.../100000.squashfs: SquashFS filesystem, little endian, version 4.0, ...
.../200000.jpg:      JPEG image data, 512x512, JFIF standard 1.01
```

## Файловая система внутри прошивки

`Squashfs` — это **файловая система только для чтения** (её часто кладут в прошивки).
`binwalk` может распаковать и её, но надёжнее взять готовый инструмент `unsquashfs`:

```bash
$ unsquashfs -d fs out/_firmware.bin.extracted/100000.squashfs
$ find fs -type f | head
fs/bin/busybox
fs/etc/config/backup.cfg
fs/www/index.html
```

Внутри — содержимое роутера: бинарники, конфиги, веб-интерфейс. Уже здесь часто
лежат пароли в конфигах.

## Когда binwalk не увидел

Проверим картинку: у неё может быть дописан хвост.

```bash
$ file -k out/_firmware.bin.extracted/200000.jpg
.../200000.jpg: JPEG image data, JFIF standard 1.01\012- data
$ grep -aboP '\xff\xd9' out/_firmware.bin.extracted/200000.jpg | tail -1
18842:...
$ xxd -s 18844 -l 32 out/_firmware.bin.extracted/200000.jpg
0000499c: 504b 0304 ...                             PK..
```

`file -k` показал лишний `data` после JPEG. Маркер конца JPEG — `FF D9`; найдя его
`grep`, смотрим, что идёт следом. А следом — `50 4B 03 04`, начало ZIP, которое
`binwalk` не отметил. Вырежем хвост вручную:

```bash
$ dd if=out/_firmware.bin.extracted/200000.jpg of=tail.zip bs=1 skip=18844 status=none
$ unzip -o tail.zip -d t/
  extracting: t/flag.txt
$ cat t/flag.txt
CTF{c4rv1ng_w0rks}
```

Это важный урок: **binwalk — не истина в последней инстанции**. Он пропускает
форматы без знакомой сигнатуры и хвосты после «легального» конца файла. Поэтому
всегда смотри `file -k` на каждый извлечённый объект и добивай `grep`+`dd` вручную.

## Энтропия: есть ли вообще что извлекать

Иногда carving не помогает, потому что данные сжаты или зашифрованы. Оценить это
можно по **энтропии** — мере «случайности» данных в битах на байт:

- текст — около 4–5;
- нули — 0;
- сжатые или зашифрованные данные — 7.9–8.0.

```bash
$ binwalk -E -N firmware.bin | head
DECIMAL       HEXADECIMAL     ENTROPY
0             0x0             3.98
64            0x40            7.99
```

Резкий скачок энтропии — это граница сжатого или зашифрованного блока. Если
зашифровано и ключа нет, carving бессилен — нужен другой подход (например, искать
ключ в другом артефакте).

## Массовое восстановление: foremost и scalpel

`binwalk` хорош, когда сигнатуры известны и их немного. Если же нужно вытащить
**всё подряд** из большого образа (например, все картинки с флешки), берут carver
с базой сигнатур — `foremost`:

```bash
$ foremost -i disk.img -o out/ -v
Processing: disk.img
|***|  file1.jpg  |***|
|***|  file2.png  |***|
```

`foremost` по умолчанию ищет JPEG, PNG, GIF, PDF, ZIP, Office, HTML и вырезает
каждое совпадение в `out/`. Флаги: `-i` — входной образ, `-o` — каталог вывода,
`-t jpg,png` — ограничить типы, `-q` — тихий режим. Его форк `scalpel` настраивается
гибче через конфиг `/etc/scalpel/scalpel.conf`:

```bash
$ scalpel -c /etc/scalpel/scalpel.conf -o out/ disk.img
```

Разница простая: `foremost` работает «из коробки» и быстр, `scalpel` точнее настраивается
под конкретный тип, но требует правки конфига.

## Если binwalk «ничего не находит»

Иногда `binwalk` пуст, а данные внутри есть. Причины и что делать:

- **Формат без сигнатуры** — например, поток сжатия без заголовка. Ищи вручную:
  `grep -aboP` по характерным байтам.
- **Не установлены модули извлечения** — `binwalk -e` не распакует ZIP без `p7zip`.
  Проверь установку вспомогательных утилит.
- **Данные зашифрованы** — тогда carving бессилен без ключа (см. энтропию выше).
- **Сигнатура повреждена** — как в прошлом уроке; почини её и повтори скан.

Хорошая привычка — после любого carver-а пройтись по результату `file -k`: то, что
автомат не заметил, часто видно на глаз.

## Полный конвейер от начала до конца

Соберём весь разбор в одну последовательность — её стоит запомнить:

```
file -k firmware.bin          # 1. что это вообще
binwalk firmware.bin          # 2. какие сигнатуры внутри и где
binwalk -e -M firmware.bin    # 3. извлечь всё рекурсивно
file -k out/*                 # 4. проверить каждый извлечённый файл
unsquashfs .../100000.squashfs # 5. распаковать найденную ФС
grep -aboP '\xff\xd9' file    # 6. доискать то, что автомат пропустил
dd if=file of=tail.zip bs=1 skip=N   # 7. вырезать найденное вручную
```

Каждый шаг отвечает на вопрос предыдущего: тип → содержимое → проверка → добор.
Именно такой порядок экономит время: не надо вручную искать то, что уже нашёл
`binwalk`, и не надо слепо верить, что автомат нашёл всё.

## Что мы теперь знаем

- Carving восстанавливает файлы из сырого потока по сигнатурам, без структуры ФС.
- `binwalk` находит и (флаг `-e`) извлекает встроенное, `-M` идёт вглубь рекурсивно.
- По смещению из `binwalk` или `grep -aboP` данные вырезают `dd skip=`.
- `file -k` по каждому извлечённому файлу — обязательный шаг: автомат может пропустить.
- Высокая энтропия (~8.0) — признак сжатия/шифрования, где carving без ключа не поможет.

## Сжатие внутри сжатия: рекурсивный разбор

`binwalk -e -M` останавливается там, где заканчиваются известные ему сигнатуры. Реальные прошивки часто устроены как матрёшка: `uImage` → `LZMA` → `Squashfs` → внутри `gzip`-конфиг. Поэтому после автоматического извлечения важно **пройти по дереву вручную** и на каждом уровне задать вопрос «это финальный файл или контейнер?». Признак контейнера — знакомая сигнатура в начале (`file` скажет `gzip`, `LZMA`, `filesystem`) или несоответствие заявленного размера реальному.

Полезный приём — вести дерево извлечённых объектов в заметке: путь, смещение-родитель, тип. Когда слоёв пять, без такого дерева легко потерять, откуда взялся файл и на каком слое что сломалось.

## Смещение, размер и «жадное» извлечение

Carving по сигнатурам не знает **конца** файла — только начало. Поэтому извлечённый объект часто «длиннее», чем нужно: в него попадает всё, что идёт следом, до следующей сигнатуры или до конца образа. Отсюда практика: после `dd` всегда проверяй результат `file -k` и, если формат знает свой размер (в заголовке есть поле длины), **обрезай** файл до этого размера. Иначе `unsquashfs` или `unzip` могут ругаться на «лишние байты».

Для форматов с известным маркером конца используйте его как правую границу: JPEG — `FF D9`, PNG — `IEND` плюс CRC, GIF — `3B`, ZIP — запись `End of Central Directory` (`PK\x05\x06`). Тогда вырезка идёт не «до конца», а ровно до маркера:

```bash
$ start=$(grep -aboP 'PK\x03\x04' img.bin | head -1 | cut -d: -f1)
$ end=$(grep -aboP 'PK\x05\x06' img.bin | tail -1 | cut -d: -f1)
$ dd if=img.bin of=out.zip bs=1 skip=$start count=$((end+22-start)) status=none
```

Число `22` — минимальный размер записи `End of Central Directory`; для архивов с комментарием берётся точное значение из самого маркера.

## Что делать с нераспознанным потоком

Если `file` упорно говорит `data`, но энтропия высокая, возможны три варианта: свой формат без сигнатуры, XOR-обёртка или шифр. Порядок проверки — от простого к сложному. Сначала ищем однобайтовый XOR: `xortool -b blob -l 1` или перебор 256 ключей с проверкой, не появилась ли сигнатура (`MZ`, `PK`, `\x7fELF`) в начале результата. Затем пробуем известные обёртки по магическим байтам (`1f 8b` — gzip, `78 9c`/`78 da` — zlib, `42 5a 68` — bzip2, `fd 37 7a 58 5a` — xz). И только если ничего не подошло — делаем вывод о криптографии и ищем ключ в другом артефакте, например в конфиге рядом или в самой прошивке.

## Куда дальше

Теперь мы умеем доставать файлы из чего угодно. Очень часто извлечённый ZIP или
7z оказывается **запароленным** — и вся цепочка встаёт. В следующем уроке разберём
архивы: как определить тип шифрования, вытащить хеш и подобрать пароль, а иногда
вскрыть архив вообще без пароля. А пока запомни: **binwalk находит, `dd` вырезает,
но проверяй каждый результат руками**.

## Где пригодится

- **CTF:** основной инструмент для задач «файл в файле».
- **Data recovery:** восстановление файлов с повреждённых носителей.
- **Malware analysis:** извлечение встроенных нагрузок из дропперов.
- **Forensic triage:** быстрый разбор подозрительных вложений.
- **Bug bounty:** анализ загруженных на сервер полиглотов.
