## Вопрос, с которого всё начинается

Нужно получить **список всех файлов** в образе с метаданными — для скриптового анализа.
Кликать в GUI долго. **fiwalk** обходит образ через Sleuth Kit и выдаёт структурированный
вывод. Разберём.

## Наш пример: образ диска

## Шаг 1: что такое fiwalk

fiwalk — обёртка над Sleuth Kit, которая обходит файловую систему и печатает метаданные
каждого файла: inode, имя, размер, времена, хеши (опционально).

## Шаг 2: запуск

```
$ fiwalk -f -X out.xml disk.img
```

`-X` — XML-вывод. Для больших образов это удобно: файл можно парсить скриптом.

## Шаг 3: что внутри

```xml
<fileobject>
  <inode>12345</inode>
  <filename>report.pdf</filename>
  <filesize>24576</filesize>
  <mtime>2026-01-14T03:31:02Z</mtime>
</fileobject>
```

Отсюда строишь таблицы, фильтруешь по времени, ищешь аномалии.

## Шаг 4: практика

```bash
fiwalk -X out.xml disk.img
python3 -c "import xml.etree.ElementTree as ET; ..."  # фильтр по mtime
```

Можно генерировать списки по типам, искать файлы в окне инцидента, считать статистику.

## Шаг 5: связка с другими

- **Sleuth Kit** (`fls`, `icat`, `mmls`) — низкий уровень;
- **plaso** — таймлайн;
- **Autopsy** — GUI поверх того же движка.

fiwalk — «мост» между Sleuth Kit и скриптами.

## Что мы теперь знаем

- fiwalk обходит образ и выдаёт метаданные.
- Вывод — XML (удобно парсить).
- Даёт inode, имя, размер, времена.
- Строит основу для скриптового анализа.
- Работает поверх Sleuth Kit.

## Если не сработало

- ФС не распознана? Проверь разделы (`mmls`).
- Нужен контент? Используй `icat`.
- Нужен GUI? Используй Autopsy.

## Полный XML fiwalk: что означает каждое поле

fiwalk печатает по одному `<fileobject>` на каждый файл. Разберём типовой блок целиком:

```xml
<fileobject>
  <filename>Users/ivan/AppData/Local/Temp/payload.exe</filename>
  <filesize>77824</filesize>
  <alloc>1</alloc>
  <used>1</used>
  <inode>48211</inode>
  <meta_type>1</meta_type>
  <mode>100600</mode>
  <nlink>1</nlink>
  <uid>1000</uid>
  <gid>1000</gid>
  <mtime>2026-01-14T03:31:02Z</mtime>
  <atime>2026-01-14T03:31:05Z</atime>
  <crtime>2026-01-14T03:30:58Z</crtime>
  <ctime>2026-01-14T03:31:02Z</ctime>
  <libmagic>PE32 executable (GUI) Intel 80386</libmagic>
  <byte_runs>
    <byte_run offset="2048" img_offset="1052672" len="77824"/>
  </byte_runs>
  <hashdigest type="md5">d41d8cd98f00b204e9800998ecf8427e</hashdigest>
  <hashdigest type="sha1">da39a3ee5e6b4b0d3255bfef95601890afd80709</hashdigest>
</fileobject>
```

Ключевые поля:

- `alloc` / `used` — `1` = запись выделена (файл не удалён); `0` = удалён, но запись
  ещё в таблице;
- `meta_type` — `1` = выделенный, `0` = удалённый (то, что нужно для восстановления);
- `byte_run` — где физически лежат данные на образе (`offset` в ФС и `img_offset` от
  начала образа);
- `libmagic` — тип, определённый по сигнатуре, независимо от расширения;
- `hashdigest` — хеши, если запрошены (`-m` для MD5, `-M` для SHA-1).

`img_offset` — самое ценное поле: по нему данные файла можно выдернуть из образа
вручную, не монтируя файловую систему:

```
$ dd if=disk.img bs=1 skip=1052672 count=77824 of=payload.exe
```

## Практический сценарий: файлы в окне инцидента

Пусть инцидент датирован 14 января 2026 года. Задача — вытащить все файлы, изменённые
в тот день, и отсортировать по времени:

```python
import xml.etree.ElementTree as ET
tree = ET.parse("out.xml")
rows = []
for fo in tree.iter("fileobject"):
    name = fo.findtext("filename") or ""
    mt = fo.findtext("mtime") or ""
    if mt.startswith("2026-01-14"):
        rows.append((mt, name, fo.findtext("filesize")))
for mt, name, size in sorted(rows):
    print(mt, size, name)
```

Так из сотен тысяч записей остаётся десяток-другой релевантных. Дальше фильтруешь по
расширению (`.exe`, `.dll`, `.ps1`, `.lnk`) или по пути (`Temp`, `Startup`, `Downloads`).
Для очень больших образов XML может весить сотни мегабайт — парси потоково через
`ET.iterparse`, а не `ET.parse`.

## Карвинг против метаданных

fiwalk читает **метаданные** файловой системы: записи MFT (NTFS), inode (ext4), каталоги
(HFS+/APFS). Это быстро и точно для **существующих** файлов. Но если запись уничтожена,
имени и времён уже нет — fiwalk её не покажет. Тогда нужен **карвинг по сигнатурам**
(`photorec`, `scalpel`, `tsk_recover`): он ищет структуры файлов в неразмеченном
пространстве. Правило простое: сначала метаданные (`fiwalk`/`fls`), потом карвинг для
остатка. Карвинг даёт файлы без имён и часто с «обрезанным» началом или концом.

## Ограничения и частые ошибки

- **Зашифрованная ФС** (BitLocker, LUKS, FileVault) — fiwalk увидит только контейнер,
  не содержимое; сначала нужно расшифровать образ ключом.
- **Составные ФС** — сначала `mmls disk.img` (разделы), затем `fiwalk -o <offset>`
  (смещение раздела) или `-f ntfs`.
- **Время в UTC** — fiwalk печатает времена в UTC (ISO 8601 с `Z`). Не путай с
  локальным временем из отчётов ОС: при сопоставлении с журналами переводи в одну зону.
- **NTFS timestomping** — времена можно подделать; сравнивай `$STANDARD_INFORMATION`
  и `$FILE_NAME` (fiwalk отдаёт первые; вторые — через `fls -m`/`istat`).
- **Фрагментация** — файл может состоять из нескольких `byte_run`; склеивай их по
  порядку, иначе получишь битый контент.

## Связка fiwalk + TSK + plaso

fiwalk отвечает на вопрос «что было на диске». `icat` достаёт содержимое по inode.
`fls -r -m` даёт machine-readable список с путями. plaso (log2timeline) собирает
**супертаймлайн** из сотен артефактов, включая метаданные ФС. На практике: fiwalk/fls —
быстрый инвентарь, plaso — хронология, Autopsy — GUI поверх всего этого. Выбор
инструмента диктуется задачей: нужен скриптовый инвентарь — fiwalk; нужна полная
хронология — plaso.

## Что писать в отчёте

Указывай команду и версию инструмента, тип и размер образа, найденные артефакты с
полями (`img_offset`, `inode`, времена). Каждый вывод («файл создан в 03:30») должен
опираться на конкретный `<fileobject>`. Отдельно перечисли, что осталось вне охвата:
зашифрованные разделы, неразмеченное пространство, ФС без поддержки TSK.

## Хеши и поиск известных файлов

Если fiwalk запущен с `-m`/`-M`, каждый `<fileobject>` получит `<hashdigest>`. Это
позволяет:

- отсеять **известные хорошие** файлы по базе NSRL (hash set) и оставить только
  неизвестные;
- найти **известную малварь** по хешу, не читая содержимое;
- подтвердить, что файл не изменился (сравнить с хешем из отчёта антивируса).

Хеш надёжнее имени: атакующий может переименовать `evil.exe` в `svchost.exe`, но хеш
останется тем же. Рабочий приём — собрать множество хешей «белых» файлов и вычесть его
из списка fiwalk:

```python
known = {l.split()[0].lower() for l in open("nsrl.txt")}
for fo in tree.iter("fileobject"):
    h = fo.findtext("hashdigest[@type='sha1']")
    if h and h.lower() not in known:
        print(h, fo.findtext("filename"))
```

## Таймлайн из метаданных (MACB)

Метаданные дают четыре времени на файл: **M**odified, **A**ccessed, **C**hanged
(metadata, т.е. ctime) и **B**irth (создание). Для NTFS fiwalk отдаёт `mtime`,
`atime`, `ctime`, `crtime`. По ним строится таймлайн активности. Инструмент `fls -m`
формирует **bodyfile** — текстовый формат `MD5|name|inode|mode|uid|gid|size|atime|mtime|ctime|crtime`,
который понимает `mactime` и plaso:

```
$ fls -r -m / disk.img > bodyfile.txt
$ mactime -b bodyfile.txt -d 2026-01-14 > timeline.csv
```

Так из инвентаря получается хронология: что создавалось, читалось и менялось в
интересующем окне. Важно помнить про timestomping: если `crtime` **позже** `mtime`,
это подозрительно (создание позже изменения невозможно без подделки).

## Сравнение fiwalk, fls и tsk_recover

| Инструмент   | Что делает                                  | Когда применять                     |
|--------------|---------------------------------------------|-------------------------------------|
| `fiwalk`     | обход ФС, XML/CSV с метаданными             | скриптовый инвентарь, массовый анализ |
| `fls`        | список файлов (в т.ч. удалённых) с временами| bodyfile/таймлайн                   |
| `icat`       | содержимое файла по inode                   | вытащить конкретный файл            |
| `tsk_recover`| восстановление удалённого по метаданным     | вернуть удалённые файлы             |
| `photorec`   | карвинг по сигнатурам без метаданных        | когда записи уничтожены             |

fiwalk — «верхний» слой для отчётов; TSK-утилиты — для точечных задач; карвинг —
последняя линия.

## Автоматизация на большом парке

В крупном расследовании образов десятки. Разумный конвейер:

1. `mmls` — разметка каждого образа;
2. `fiwalk -X <image>.xml` — инвентарь;
3. сбор всех XML в одну базу (например, SQLite через `xml.etree`);
4. фильтры по IOC (имена, хеши, пути, времена);
5. ручной разбор только попавших под фильтр файлов.

Так ручная работа сокращается на порядки. Скрипт-обёртку храни в материалах дела —
воспроизводимость важнее «магии».

## Что писать в отчёте

Указывай команду и версию, тип и размер образа, найденные артефакты с полями
(`img_offset`, `inode`, времена), применённые фильтры и хеш-сеты. Каждый вывод («файл
создан в 03:30») должен опираться на конкретный `<fileobject>`. Отдельно перечисли,

## NTFS-специфика: потоки и журнал изменений

На NTFS у файла может быть несколько **потоков** (Alternate Data Streams, ADS). Классика
малвари — спрятать данные в `file.txt:hidden`. fiwalk показывает потоки отдельными
записями с именем вида `file.txt:stream`. Если видишь двоеточие в имени — это ADS.

Второй важный артефакт NTFS — журнал `$UsnJrnl` (Update Sequence Number). Он хранит
историю **создания, переименования и удаления** файлов, даже если запись MFT уже
переиспользована. fiwalk его не разбирает; для этого нужен `MFTECmd`/`usnparser`:

```
$ MFTECmd.exe -f '$UsnJrnl:$J' --csv out --csvf usn.csv
```

Связка «инвентарь fiwalk + история $UsnJrnl» даёт почти полный таймлайн файловых
операций, включая следы anti-forensics (быстрое создание и удаление файла).

## Типичные вопросы и ответы

- **Можно ли fiwalk на живой системе?** Нет, он работает по образу; для живой системы
  есть другие средства (например, `tsk` по `\\.\C:` с осторожностью).
- **Даёт ли fiwalk содержимое файлов?** Нет, только метаданные и byte_runs; контент —
  через `icat` или `dd` по `img_offset`.
- **Почему файл есть в XML, но не открывается?** Он удалён (`meta_type=0`) или
  фрагментирован; восстанавливай через `tsk_recover`/карвинг.
- **Где времена в локальной зоне?** fiwalk всегда UTC; переводи сам.
