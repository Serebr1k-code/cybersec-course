## Вопрос, с которого всё начинается

Ты извлёк из образца IP, домен и хеш. Это **IOC** — индикаторы компрометации. Но сами
по себе они мало значат: нужно понять, что за ними стоит. Это называется
**обогащение**. Разберём.

## Наш пример: набор IOC

## Шаг 1: типы IOC

- **хеши** (MD5/SHA256 файла);
- **домены и URL**;
- **IP-адреса**;
- **строки** (мутексы, ключи реестра);
- **правила YARA/Sigma**.

```
$ sha256sum sample.bin
a1b2c3...  sample.bin
```

## Шаг 2: репутация файла

Хеш проверяем в VirusTotal:

```
$ curl -s "https://www.virustotal.com/api/v3/files/a1b2c3..." -H "x-apikey: $VT_KEY" | head
```

Ответ даёт семейство, детекты AV, первый/последний раз, связи с другими образцами.

## Шаг 3: репутация сети

IP/домен:

```
$ whois 203.0.113.5 | grep -iE 'orgname|netname'
```

Смотрим ASN, геолокацию, хостинг. Часто C2 — на VPS с «серой» репутацией.

## Шаг 4: обогащение через платформы

- **MISP** — база IOC с корреляциями;
- **AlienVault OTX** — пульсы по угрозам;
- **Passive DNS** — история домена;
- **Shodan/Censys** — что ещё на этом IP.

Так одиночный индикатор превращается в «кампанию»: тот же C2, тот же сертификат, та же
инфраструктура.

## Шаг 5: применение

- **блокировка** — firewall/DNS/AV;
- **hunting** — поиск IOC по логам (SIEM);
- **отчёт** — контекст и уровень уверенности;
- **TTL** — у IOC есть срок жизни (инфраструктура меняется).

## Что мы теперь знаем

- IOC бывают файловые, сетевые, поведенческие.
- Хеш/домен проверяют в VT/OTX/MISP.
- Passive DNS и Shodan дают контекст.
- Обогащение связывает образец с кампанией.
- У IOC есть срок жизни — указывай дату и уверенность.

## Если не сработало

- Нет доступа к VT? Используй локальные базы.
- IOC «протух»? Ищи похожие по инфраструктуре.
- Нужно правило? Пиши YARA/Sigma по извлечённым строкам.

## Разбор набора IOC по шагам

Пусть из образца извлечены индикаторы. Собираем их в структуру и обогащаем:

```
$ cat iocs.txt
sha256:a1b2c3d4e5f6...
domain:cdn-update.example
ip:203.0.113.5
mutex:Global\\{8f2c1ab7}
```

Начинаем с файлового хеша — он самый «дорогой» индикатор (точно указывает на
образец). Проверяем репутацию:

```
$ curl -s "https://www.virustotal.com/api/v3/files/a1b2c3d4e5f6..." \
    -H "x-apikey: $VT_KEY" | jq '.data.attributes | {meaningful_name, last_analysis_stats}'
{
  "meaningful_name": "installer.exe",
  "last_analysis_stats": {"malicious": 47, "undetected": 8}
}
```

47 детектов из 55 — уверенный вердикт. Дальше смотрим `first_submission_date`:
если образец свежий, кампания активна прямо сейчас.

## Таблица: типы IOC и где их обогащать

| Тип IOC | Источник обогащения | Что узнаём |
|---|---|---|
| Хеш файла | VirusTotal, MalwareBazaar | семейство, AV-детекты, связи |
| Домен | Passive DNS, URLhaus | история IP, блок-листы |
| IP | Shodan, Censys, whois | ASN, хостинг, соседние сервисы |
| URL | urlscan.io, Any.run | содержимое, скриншот, редиректы |
| Мутекс | локальные базы | уникальность семейства |
| Правило YARA | YARAify | совпадения у сообщества |

Комбинируя несколько источников, ты отделяешь «протухший» индикатор от
живого. Одиночный IP без контекста почти бесполезен; IP + ASN + Passive DNS
+ сертификат дают картину кампании.

## STIX и MISP: структура

Обогащённые IOC описывают в стандартных форматах:

- **STIX 2.1** — JSON-объекты (`indicator`, `malware`, `relationship`);
- **MISP** — событие с атрибутами и корреляциями.

```
{
  "type": "indicator",
  "pattern": "[domain-name:value = 'cdn-update.example']",
  "valid_from": "2026-03-11T00:00:00Z",
  "labels": ["malicious-activity"]
}
```

Стандарт позволяет делиться индикаторами между командами и автоматически
подхватывать их в SIEM/EDR. Без структуры индикаторы остаются «текстом в
письме», который никто не применит.

## Пирамида боли (Pyramid of Pain)

Не все IOC одинаково ценны для защитника:

| Уровень | Пример | Сложность смены для атакующего |
|---|---|---|
| TTP | техника (фишинг → loader) | очень высокая |
| Инструмент | Cobalt Strike | высокая |
| Артефакт | имя файла, ключ реестра | средняя |
| Домен/IP | cdn-update.example | низкая |
| Хеш | SHA256 образца | тривиальная |

Хеш атакующий меняет за секунду (пересобрать бинарник), а технику — почти
никогда. Поэтому в отчёте ценность смещается к TTP: «использует phishing →
macro → loader» полезнее, чем один хеш.

## TTL и уверенность

Каждый IOC помечается датой и уровнем уверенности:

```
domain:cdn-update.example  first_seen:2026-02-01  confidence:high  ttl:180d
ip:203.0.113.5             first_seen:2026-03-11  confidence:low   ttl:30d
```

- **high** — подтверждён несколькими источниками и связан с образцом;
- **low** — одиночный источник, возможен false positive.

Указывай `first_seen`/`last_seen`: индикатор трёхмесячной давности мог быть
переиспользован легитимным сервисом, и блокировка нанесёт вред.

## Если сработало

Обогащение связало образец с кампанией — применяй результаты:

1. **Заблокируй** домены/IP на периметре (DNS sinkhole, ipset).
2. **Найди в логах** — hunting по всем индикаторам в SIEM:
   ```
   index=proxy (dest IN (203.0.113.5) OR url="*cdn-update.example*")
   ```
3. **Проверь другие хосты** — тот же C2 мог «звонить» с нескольких машин.
4. **Опубликуй** обезличенный STIX-набор для партнёров.
5. **Перепроверь через 30 дней** — инфраструктура меняется, TTL истёк.

## Практика: правило YARA по строкам

Из строк образца собираем правило детекта:

```yara
rule xmr_miner_linux {
  meta:
    author = "ir-team"
    date = "2026-03-11"
  strings:
    $pool = "stratum+tcp://" ascii
    $coin = "xmr" nocase
    $wallet = /wallet=[0-9a-f]{90,}/ ascii
  condition:
    uint32(0) == 0x464c457f and all of them
}
```

Условие `uint32(0) == 0x464c457f` проверяет, что файл — ELF (магическое
число `\x7fELF`). Правило найдёт любой вариант майнера, даже если хеш
изменили. Так из «протухшего» хеша рождается долгоживущий детект.

## Пример: реконструкция кампании

Обогащение превращает набор IOC в кампанию:

```
$ curl -s "https://otx.alienvault.com/api/v1/indicators/domain/cdn-update.example/general" \
    | jq '{pulse_count, tags, related_pulses}'
{ "pulse_count": 12, "tags": ["loader", "2026-campaign"], "related_pulses": 4 }
```

12 пульсов и общий тег означают, что индикатор уже известен сообществу и
связан с четырьмя другими кампаниями. Дальше Passive DNS показывает, что
домен резолвился в тот же /24, что и C2 другого инцидента, — и два инцидента
склеиваются в один.

## Быстрый триаж IOC

```
$ sha256sum sample.bin | awk '{print $1}' | xargs -I{} curl -s "https://.../{}"
$ dig +short cdn-update.example @8.8.8.8
$ whois 203.0.113.5 | grep -iE 'orgname|netname|country'
```

Хеш → детекты, `dig` → текущий IP, `whois` → владелец. Три команды дают
минимальный контекст, по которому уже можно решать, блокировать или копать
глубже.

## Пример: разбор индикатора до кампании

Проследим путь от одной строки до картины кампании:

```
$ grep -rhoE 'https?://[^"'\'' ]+' sample.bin | sort -u
http://cdn-update.example/gate.php
$ dig +short cdn-update.example
203.0.113.5
$ curl -s "https://urlhaus.abuse.ch/api/v1/host/203.0.113.5/" | jq '.urls[]?.threat'
"malware_download"
```

Один URL → домен → IP → репутация. Теперь известно, что хост раздаёт
малварь. Дальше Passive DNS покажет, какие ещё домены смотрели на этот IP, и
ты получишь список C2 всей кампании.

## Что фиксировать в отчёте

- исходные индикаторы и их тип;
- результаты обогащения (VT/OTX/Passive DNS);
- уровень уверенности и TTL;
- связи между индикаторами (кампания);
- применённые меры (блокировки, hunting).

Без TTL и уровня уверенности отчёт опасен: коллеги заблокируют легитимный
ресурс, переиспользовавший тот же IP, и получат ложное срабатывание.

## Частая ошибка: блокировать «протухший» IOC

Новичок находит IP в старом отчёте и заносит его в блок-лист. Через месяц
выясняется, что этот IP уже переиспользован легитимным сервисом (облачный
хостинг перераспределяет адреса), и блокировка ломает работу. Всегда проверяй
`first_seen`/`last_seen` и ставь TTL. Индикатор без даты — это не индикатор,
а лотерея.

## Итог

Обогащение — это превращение сырого индикатора в контекст: репутация, связи,
кампания, уровень уверенности. Начинай с хеша (самый точный), продолжай
доменом и IP, заканчивай TTP (самый ценный). Применяй результат через
блокировку, hunting и структурированный обмен (STIX/MISP).

## Краткий чек-лист

1. Собери индикаторы в список (хеш, домен, IP, мутекс).
2. Хеш → VirusTotal; домен/IP → Passive DNS, whois, Shodan.
3. Свяжи индикаторы в кампанию (общий ASN, сертификат, тег).
4. Присвой уровень уверенности и TTL.
5. Заблокируй на периметре и запусти hunting в SIEM.
6. Оформи STIX/MISP-набор для обмена.

Пункт 3 — где одиночные индикаторы превращаются в разведку. Кампания с
общим сертификатом на нескольких доменах позволяет предсказать следующий C2.
