## Вопрос, с которого всё начинается

В локальной сети устройства общаются не по IP, а по **MAC-адресам**. Протокол **ARP**
сопоставляет одно с другим. Если в дампе видно, как один MAC вдруг «присвоил» чужой
IP, — это атака. Разберём, как это устроено и как читать.

## Наш пример: ARP-таблица

## Шаг 1: как работает ARP

Отправляя пакет на `10.10.20.9`, хост спрашивает по broadcast: «кто такой 10.10.20.9?»
Владелец отвечает своим MAC. Ответ кэшируется:

```
$ ip neigh show
10.10.20.9 dev eth0 lladdr 02:42:0a:0a:14:09 REACHABLE
```

`02:42:...` — типичный MAC виртуального интерфейса. Обрати внимание на первые байты:
`02` означает «локально администрируемый» адрес (не заводской).

## Шаг 2: ARP в дампе

```
$ tshark -r capture.pcap -Y 'arp' -T fields -e arp.opcode -e arp.src.proto_ipv4 -e arp.src.hw_mac | head
1	10.10.20.5	02:42:0a:0a:14:05
2	10.10.20.9	02:42:0a:0a:14:09
```

`opcode=1` — запрос, `opcode=2` — ответ. По паре IP↔MAC строишь карту сегмента.

## Шаг 3: ARP-спуфинг

Атака: злоумышленник шлёт ответы «10.10.20.1 is at <его MAC>». Тогда весь трафик
шлюза идёт через него:

```
$ tshark -r capture.pcap -Y 'arp.opcode==2' -T fields -e arp.src.proto_ipv4 -e arp.src.hw_mac | sort | uniq -c | sort -rn | head
   900	10.10.20.1	02:42:0a:0a:14:66
     2	10.10.20.1	02:42:0a:0a:14:01
```

Один и тот же IP `10.10.20.1` анонсируется с **двух разных** MAC, причём «чужой» MAC
доминирует. Это отравление ARP — классический MITM.

## Шаг 4: следы на хосте

На скомпрометированном хосте таблица ARP может быть отравлена:

```
$ cat /proc/net/arp
IP address       HW type     Flags   HW address
10.10.20.1       0x1         0x2     02:42:0a:0a:14:66
```

Сверь MAC шлюза с эталоном — расхождение выдаёт атаку.

## Шаг 5: MAC как идентификатор

MAC-адрес (в части OUI) указывает производителя. Первые 3 байта — OUI:

```
$ grep -i '02:42' /usr/share/nmap/nmap-mac-prefixes
0242   (локально администрируемый)
```

Локально администрируемые MAC часто означают контейнеры/виртуалки или подделку.

## Что мы теперь знаем

- ARP сопоставляет IP и MAC в локальном сегменте.
- `ip neigh` и `/proc/net/arp` показывают текущую таблицу.
- `tshark -Y arp` даёт карту IP↔MAC из дампа.
- Один IP с двумя MAC = ARP-спуфинг.
- OUI в MAC указывает производителя.

## Если не сработало

- Дамп только прикладной? ARP не попал — снимай заново с L2.
- Таблица пуста? Кэш истёк — смотри логи switch.
- Нужна история? Ищи ARP в долгих дампах и на span-порту.

## Формат ARP-пакета

ARP — простой протокол с фиксированной структурой. Понимание полей помогает читать дамп:

| Поле | Размер | Смысл |
|---|---|---|
| Hardware type | 2 | 1 = Ethernet |
| Protocol type | 2 | 0x0800 = IPv4 |
| HW addr len | 1 | 6 для Ethernet |
| Proto addr len | 1 | 4 для IPv4 |
| Opcode | 2 | 1 = request, 2 = reply |
| Sender HW addr | 6 | MAC отправителя |
| Sender proto addr | 4 | IP отправителя |
| Target HW addr | 6 | MAC цели (нули в запросе) |
| Target proto addr | 4 | IP цели |

Именно поэтому в запросе `Target HW addr` пуст (хост не знает MAC), а в ответе заполнен.

## Типы MAC-адресов

Первый байт MAC кодирует тип адреса:

| Признак | Значение |
|---|---|
| младший бит 0 | unicast (один получатель) |
| младший бит 1 | multicast (группа) |
| все биты 1 (`ff:ff:ff:ff:ff:ff`) | broadcast |
| второй бит = 1 | локально администрируемый (не заводской) |
| первые 3 байта (OUI) | производитель |

`02:42:...` — второй бит выставлен, значит локально администрируемый: так задают MAC
виртуальные интерфейсы Docker (`02:42:ac:...`) и другие гипервизоры. `00:0c:29` — VMware,
`08:00:27` — VirtualBox, `52:54:00` — QEMU/KVM.

```
$ grep -iE '^(0242|000c29|080027|5254)' /usr/share/nmap/nmap-mac-prefixes
```

## ARP-спуфинг: как детектировать

Атака состоит в том, что злоумышленник шлёт **незапрошенные** ARP-ответы (gratuitous
ARP), привязывая IP шлюза к своему MAC. Детект строится на аномалиях:

- один IP анонсируется с **разных** MAC в коротком окне;
- массовые ARP-ответы без предшествующих запросов;
- MAC шлюза сменился (сверь с эталоном);
- ARP-ответы приходят чаще, чем раз в обычный таймаут кэша.

```
$ tshark -r capture.pcap -Y 'arp.opcode==2' -T fields \
    -e arp.src.proto_ipv4 -e arp.src.hw_mac | sort | uniq -c | sort -rn | head
$ tshark -r capture.pcap -Y 'arp.opcode==1' | wc -l   # сколько было запросов
```

Если ответов на порядок больше запросов — почти наверняка спуфинг.

## Gratuitous ARP и другие аномалии

- **Gratuitous ARP** (IP отправителя = IP цели) — нормален при смене MAC/старте
  интерфейса, но массовый поток — атака или misconfiguration.
- **ARP-probe** (target IP = 0.0.0.0) — проверка дубликата адреса, норма.
- **Флуд ARP** — DoS или попытка исчерпать таблицу коммутатора.
- **Reverse ARP (RARP)** — устаревший, может указывать на легаси-устройство.

Контекст решает: единичный gratuitous ARP при загрузке — норма, сотни в минуту — нет.

## IPv6: NDP вместо ARP

В IPv6 ARP заменён на **NDP** (Neighbor Discovery Protocol, ICMPv6):

```
$ tshark -r capture.pcap -Y 'icmpv6.type==135 || icmpv6.type==136'
```

Тип 135 — Neighbor Solicitation (аналог ARP-запроса), 136 — Neighbor Advertisement
(аналог ответа). Спуфинг в IPv6 называется **NA spoofing** и детектируется теми же
признаками (один адрес с разных MAC). Не забывай про IPv6 — атаки на него часто
«невидимы» для тех, кто смотрит только ARP.

## Практический разбор CTF

Задача: «найди MITM в сегменте». Шаги:

```
$ tshark -r capture.pcap -Y 'arp' -T fields -e frame.time -e arp.opcode \
    -e arp.src.proto_ipv4 -e arp.src.hw_mac > arp.tsv
$ awk '$2==2{print $3, $4}' arp.tsv | sort | uniq -c | sort -rn | head
$ awk '{print $4}' arp.tsv | sort | uniq -c          # какие MAC вообще светились
```

Дальше сопоставляем «чужой» MAC с известными вендорными префиксами и ищем хост с таким
MAC. Часто флаг лежит в MAC/имени атакующего хоста.

## Ограничения

- ARP виден только в **своём** L2-сегменте; на маршрутизаторе его уже нет.
- Кэш ARP быстро истекает — без дампа история теряется.
- Инкапсуляция (VXLAN, GRE) скрывает исходный ARP.
- Шифрованные туннели L2 (IPsec) делают ARP нечитаемым извне.

## Виды ARP-атак и их сигнатуры

ARP не аутентифицирован, поэтому уязвим. Основные атаки:

| Атака | Суть | Признак в дампе |
|---|---|---|
| ARP spoofing | ложные ответы «IP шлюза — мой MAC» | один IP с разными MAC |
| ARP poisoning | отравление кеша двух хостов | рост числа ARP-reply |
| Gratuitous ARP flood | массовые анонсы | аномальный объём ARP |
| MAC flooding | переполнение таблицы коммутатора | много уникальных MAC |
| MAC spoofing | подмена своего MAC | конфликт MAC в таблице |

Для каждого — свои сетевые и хостовые артефакты. На хосте отравление видно в
`/proc/net/arp` и `ip neigh` (неверный MAC шлюза); на коммутаторе — в таблице
MAC-адресов (`show mac address-table`).

## Инструменты

- `arp -a`, `ip neigh`, `cat /proc/net/arp` — таблица на хосте;
- `arping`, `arp-scan` — активная проверка (осторожно в проде);
- `tshark`/`tcpdump` — анализ дампа (`tcpdump -i eth0 arp`);
- `ettercap`, `bettercap` — детект и демонстрация атак (только в лаборатории);
- `arpwatch` — мониторинг изменений IP↔MAC;
- MAC/OUI-базы (`nmap-mac-prefixes`, IEEE OUI) — определение производителя.

Для быстрой сверки MAC шлюза с эталоном:

```
$ ip neigh show 10.10.20.1
```
## ARP в виртуальных сетях и контейнерах

Большая часть современной инфраструктуры виртуализирована, и это меняет картину ARP:

- **Docker** использует bridge-сеть `172.17.0.0/16` с MAC `02:42:ac:11:xx:xx` — по
  префиксу `02:42:ac:11` сразу видно контейнер;
- **KVM/QEMU** даёт гостям MAC с OUI `52:54:00`;
- **VMware** — `00:0c:29`, **VirtualBox** — `08:00:27`, **Hyper-V** — `00:15:5d`;
- **VXLAN/EVPN** инкапсулирует ARP, и на физическом коммутаторе он уже не виден.

Для форензики это значит: незнакомый MAC — не всегда «атакующий», часто это просто
виртуалка. Сверяй OUI с известными префиксами гипервизоров, прежде чем делать вывод.

## Практика: построение карты сегмента

Соберём полную карту «IP ↔ MAC ↔ вендор» из дампа:

```
$ tshark -r capture.pcap -Y 'arp.opcode==2' -T fields \
    -e arp.src.proto_ipv4 -e arp.src.hw_mac | sort -u > map.tsv
$ while IFS=$'\t' read ip mac; do
    oui=$(echo "$mac" | tr -d ':' | cut -c1-6 | tr 'A-Z' 'a-z')
    vendor=$(grep -i "^$oui" /usr/share/nmap/nmap-mac-prefixes | cut -d' ' -f2-)
    echo "$ip  $mac  ${vendor:-unknown}"
  done < map.tsv
```

На выходе — таблица, по которой сразу видно аномалии: два MAC на один IP, MAC неизвестного
вендора на месте шлюза, «локально администрируемый» MAC у устройства, которое должно быть
заводским. Именно такие расхождения и указывают на спуфинг или на скрытый хост в сегменте.
