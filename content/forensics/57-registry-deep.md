## Вопрос, с которого всё начинается

Ты снял куст реестра `NTUSER.DAT` с машины. Открыл известную ветку автозапуска — а
там пусто. Либо атакующий ничего не делал, либо **удалил** свой ключ после запуска.
Как отличить одно от другого?

Реестр Windows — это не один файл, а набор **кустов** (hives): `NTUSER.DAT` хранит
настройки пользователя, `SYSTEM` и `SOFTWARE` — системные. Чтобы понять, что можно
восстановить, надо заглянуть внутрь: там всё устроено как дерево «ячеек», и удалённые
данные часто остаются на месте.

## Наш пример: «грязный» NTUSER.DAT

В наборе улик лежат три файла:

```bash
$ ls -la NTUSER.DAT*
NTUSER.DAT        NTUSER.DAT.LOG1   NTUSER.DAT.LOG2
```

Файлы `.LOG1`/`.LOG2` — это **транзакционные журналы**. Реестр пишет изменения не
сразу в основной файл, а сначала в журнал; если система выключилась неаккуратно,
свежие изменения остались в журнале. Посмотрим на первые байты куста:

```bash
$ xxd -l 16 NTUSER.DAT
00000000: 7265 6766 0f00 0000 0100 0000 0300 0000  regf............
```

Первые четыре байта — `regf` (от «registry file»). Это **base block**, заголовок
куста. Дальше идут номера последовательностей. Если они не совпадают — куст
«грязный» (dirty), и без применения журналов ты увидишь неполную картину.

## Шаг 1: как устроен куст изнутри

После заголовка `regf` идут **hbin** — «бины» (bins) по 4 КБ. Внутри бинов лежат
**ячейки** (cells). Каждая ячейка начинается с 4-байтового заголовка: размер и тип.
Типы ячеек:

| Сигнатура | Что это |
|-----------|---------|
| `regf` | заголовок куста |
| `hbin` | блок (bin) по 4 КБ |
| `nk` | ключ (key node) |
| `vk` | значение (value) |
| `lf`/`lh`/`li`/`ri` | списки подключей |
| `sk` | дескриптор безопасности |
| `db` | «большие данные» (big data) |

Ключ (`nk`) — это «папка» реестра, значение (`vk`) — «файл» внутри неё. Понимание
этих типов нужно, чтобы вручную найти ячейку, на которую больше нет ссылок, — то есть
**удалённый** ключ.

## Шаг 2: навигация и экспорт

Для ручного просмотра удобен `hivexsh` (интерактивная оболочка):

```bash
$ hivexsh NTUSER.DAT
Welcome to hivexsh
> cd Software\Microsoft\Windows\CurrentVersion\Run
> lsval
```

Экспортировать ветку в текстовый `.reg`-файл можно так:

```bash
$ hivexregedit --export NTUSER.DAT '\Software\Microsoft\Windows\CurrentVersion\Run' run.reg
$ cat run.reg
"Updater"="C:\\ProgramData\\evil\\run.exe"
```

Вот и ключ автозапуска — он был не в той ветке, где мы искали. Но что если бы он был
удалён? Здесь в игру вступает восстановление.

## Шаг 3: применяем транзакционные журналы

Если куст «грязный», свежие изменения сидят в `.LOG`. Их применяет утилита `yarp`
(Yet Another Registry Parser):

```bash
$ python3 yarp.py NTUSER.DAT -l NTUSER.DAT.LOG1 -l NTUSER.DAT.LOG2
$ ls -la NTUSER.DAT*
NTUSER.DAT   NTUSER.DAT.LOG1   NTUSER.DAT.LOG2   NTUSER.DAT.recovered
```

Без этого шага можно потерять самые свежие (и самые интересные) ключи — те, что
атакующий создал в последние минуты.

## Шаг 4: восстанавливаем удалённые ключи

Когда ключ удаляют, его ячейка помечается свободной, но **данные остаются**, пока
ячейку не переиспользуют. `reglookup-recover` сканирует все ячейки, включая
свободные:

```bash
$ reglookup-recover NTUSER.DAT > all.txt
$ grep -iE 'evil|updater|run' all.txt | head
/Software/Microsoft/Windows/CurrentVersion/Run,Updater,C:\ProgramData\evil\run.exe
```

Мы нашли удалённый автозапуск. Это ровно тот случай, когда атакующий создал ключ,
он сработал, и злоумышленник его убрал, чтобы замести следы.

## Шаг 5: сверяем с теневой копией

Если ячейку всё же переиспользовали, спасают **теневые копии** (Volume Shadow Copy) —
автоматические снапшоты диска в `System Volume Information`. Смонтируем и достанем
старую версию куста:

```bash
$ vshadowmount disk.img /mnt/vss
$ hivexregedit --export /mnt/vss/.../NTUSER.DAT '\Software\Microsoft\Windows\CurrentVersion\Run' old.reg
$ diff <(sort old.reg) <(sort run.reg)
> "Updater"="C:\\ProgramData\\evil\\run.exe"
```

Разница мгновенно показывает, что появилось в реестре между снапшотом и текущим
состоянием.

## Продвинутые ветки, которые стоит знать

Реестр хранит куда больше, чем автозапуск. Полезные ветки:

| Ветка | Куст | Что даёт |
|-------|------|----------|
| `Amcache` | Amcache.hve | запуск/установка файлов + SHA1 |
| `AppCompatCache` | SYSTEM | присутствие (на части ОС — запуск) файлов |
| `UserAssist` | NTUSER.DAT | запуски через GUI |
| `USBSTOR` | SYSTEM | подключённые USB-устройства |
| `Shellbags` | UsrClass.dat | просмотренные папки |

`AppCompatCache` (он же ShimCache) — классический пример значения, разбитого на
несколько ячеек и сжатого. «Сырой» `hivexregedit` покажет мусор, а `RegRipper`
разберёт его правильно:

```bash
$ rip.pl -r SYSTEM -p appcompatcache
```

## Полный разбор: от «грязного» куста к удалённому ключу

Прогоним разбор `NTUSER.DAT` в один сценарий.

1. **Смотрим устройство.** Куст = набор **hbin**-блоков, внутри — **cell**'ы (ключи, значения, списки). `hivexstat NTUSER.DAT` покажет размер блока.
2. **Навигация и экспорт.** `reged -e NTUSER.DAT` или `hivexregedit --export` — читаем дерево.
3. **Применяем транзакционные журналы.** Рядом лежат `*.LOG1`/`*.LOG2`; без них свежие изменения не видны:
   ```bash
   $ yarp -r NTUSER.DAT -l NTUSER.DAT.LOG1 > clean.dat
   ```
4. **Восстанавливаем удалённые ключи.** Освобождённые cell'ы помечены, но данные часто целы — `yarp -d` извлекает их.
5. **Сверяем с теневой копией** — видно, что было удалено.

Ключ: реестр не «перезаписывает» сразу; журналы и свободные ячейки хранят историю.

## Шпаргалка транзакций и восстановления

| Файл | Роль |
|------|------|
| `NTUSER.DAT` | куст пользователя |
| `SYSTEM` | куст системы |
| `.LOG1`/`.LOG2` | транзакционные журналы |
| `yarp` | применение журналов |
| `hivexregedit` | экспорт/импорт |

Полезные ветки: `Run`/`RunOnce` (автозапуск), `RecentDocs` (недавние файлы), `TypedURLs`, `UserAssist` (запуски из GUI), `MountPoints2` (тома).

## Частые вопросы

**Почему ключ «отсутствует»?** Изменение ещё в `.LOG`-журнале — примените его `yarp`.

**Удалённые ключи восстанавливаются?** Часто да: освобождённые cell'ы не затираются мгновенно.

**Как отличить живой ключ от удалённого?** По флагу «allocated» в структуре cell; инструменты помечают их.

**Теневые копии нужны?** Очень полезны: дают «снимок» реестра на прошлый момент для сравнения.

## Что мы теперь знаем

- Куст — это дерево ячеек (`nk` — ключ, `vk` — значение) внутри блоков `hbin`.
- «Грязный» куст читается только после применения журналов `.LOG` (утилита `yarp`).
- Удалённые ключи остаются в свободных ячейках — их достаёт `reglookup-recover`.
- Теневые копии — источник старых версий кустов, когда ячейку переиспользовали.
- Продвинутые ветки (Amcache, ShimCache, UserAssist) доказывают запуск программ.

## На что смотреть дальше

- **Игнорировать `.LOG`** — потеряешь свежие ключи.
- **Не проверять «грязность»** — куст может быть неконсистентным.
- **Пропускать `reglookup-recover`** — не найдёшь удалённое.
- **Забывать про теневые копии** — единственный источник переиспользованных ячеек.
- **Путать куст и ветку** — `Amcache` лежит в отдельном файле.
- **Анализировать на живой системе** — кусты заблокированы; работай с копией.

## Куда дальше

Мы разобрали реестр на уровне ячеек и научились доставать удалённые ключи. В
следующем уроке возьмём инструмент, который собирает **таймлайн всей системы** из
тысяч артефактов сразу — чтобы события из разных источников встали в одну
хронологию. А пока запомни: **в реестре удалённый ключ почти никогда не исчезает
бесследно — его выдают свободные ячейки и журналы**.

## Где пригодится

- **CTF** — задачи на скрытый автозапуск и восстановление удалённых ключей.
- **DFIR** — вскрытие персистентности, следов выполнения, USB-истории.
- **Threat Hunting** — Amcache/ShimCache для доказательства запуска.
- **Судебная экспертиза** — работа с «грязными» кустами и журналами.
- **SOC** — детект модификаций ключевых веток реестра.
