## Вопрос, с которого всё начинается

Секрет (ключ API, пароль БД) попал к атакующему. Где он хранился и кто его читал?
Менеджеры секретов ведут аудит. Разберём.

## Наш пример: менеджер секретов

## Шаг 1: что это

Менеджер секретов (HashiCorp Vault, AWS Secrets Manager, Azure Key Vault) хранит секреты
централизованно и выдаёт их по запросу с проверкой прав.

## Шаг 2: аудит-логи

Vault:

```
$ vault audit list
$ tail /var/log/vault_audit.log | jq '.request.path'
"secret/data/db"
```

AWS Secrets Manager — через CloudTrail:

```
$ grep GetSecretValue cloudtrail.json | jq '.sourceIPAddress'
"203.0.113.5"
```

Видно: **кто**, **какой секрет** и **с какого IP** читал.

## Шаг 3: кто имел доступ

Права задаются политиками:

- кто может читать секрет;
- есть ли wildcard (`*`) в путях;
- временные креды (STS) — когда истекают.

```
$ vault policy read db-app
```

Широкие политики — частая причина компромисса.

## Шаг 4: KMS и шифрование

Секреты шифруются **ключом** (KMS). Доступ к ключу логируется отдельно:

```
$ aws kms list-keys
$ grep Decrypt cloudtrail.json
```

Если атакующий получил права на `Decrypt` — он читает зашифрованные секреты.

## Шаг 5: что искать

- необычные `GetSecretValue`/`Decrypt`;
- доступ с внешних IP;
- расширение прав (новые политики);
- использование секрета сразу после чтения.

## Что мы теперь знаем

- Менеджеры централизуют секреты с проверкой прав.
- Аудит-логи фиксируют чтение (кто/что/откуда).
- Политики определяют доступ; wildcard опасен.
- KMS-ключи логируют Decrypt отдельно.
- Сопоставляй чтение секрета с его использованием.

## Если не сработало

- Аудит не включён? Смотри CloudTrail/логи приложений.
- Секрет ротирован? Проверь, был ли он скомпрометирован.
- Нужны права? Читай политики.

## Практический разбор: путь секрета и его аудит

Проследим, как читается секрет и какие следы остаются. В Vault каждый запрос
попадает в аудит-лог в формате JSON:

```bash
$ tail -1 /var/log/vault_audit.log | jq '{time, path:.request.path, ip:.request.remote_address, op:.request.operation}'
{
  "time": "2026-01-14T03:20:11Z",
  "path": "secret/data/db",
  "ip": "10.0.0.42",
  "op": "read"
}
```

Видно время, путь секрета, IP клиента и операцию. В AWS Secrets Manager чтение
фиксируется в CloudTrail:

```bash
$ jq -r 'select(.eventName=="GetSecretValue") | "\(.eventTime) \(.sourceIPAddress) \(.userIdentity.arn)"' cloudtrail.json | tail -3
2026-01-14T03:20:11Z 203.0.113.5 arn:aws:iam::111:user/ci-runner
```

Если чтение идёт с внешнего IP или от неожиданной роли — это индикатор.

## Что фиксирует каждый источник

| Источник | Что логирует | Где смотреть |
|---|---|---|
| Vault audit | путь, клиент, операция | `vault_audit.log` |
| CloudTrail | GetSecretValue, источник | S3/CloudWatch |
| KMS | Decrypt/Encrypt по ключу | CloudTrail |
| Логи приложения | использование секрета | файлы приложения |
| IAM | изменения политик | CloudTrail |

Сопоставление «кто прочитал секрет» (аудит) и «как его использовали»
(приложение) — ключ к пониманию масштаба компромисса.

## Ротация и его следы

- **Авторотация.** Часть секретов ротируется автоматически; ищи события
  изменения и связанные с ними `PutSecretValue`.
- **Ручная ротация.** Всплеск `PutSecretValue`/`UpdateSecret` без релиза — знак
  реагирования на инцидент.
- **После ротации.** Старые версии секрета остаются в истории; проверь, не
  утекли ли они до ротации.

## Как секрет утекает: типовые сценарии

- **Wildcard-политика.** Путь `secret/data/*` в политике даёт доступ ко всем
  секретам сразу; проверь политики на `*`.
- **Долгоживущие креды.** Статичные ключи доступа не истекают; атакующий
  использует их бессрочно, в отличие от коротких STS-токенов.
- **Переменные окружения.** Секреты, переданные в env контейнера, видны через
  `/proc/<pid>/environ` и в дампах процесса.
- **Логи CI/CD.** Секреты, попавшие в вывод сборки, остаются в логах пайплайна.
- **IMDS.** На облачных ВМ метаданные-сервис может выдать временные креды
  роли, если к нему есть доступ из контейнера.

## Практический разбор: расширение прав

Ищем изменения политик, открывшие доступ:

```bash
$ jq -r 'select(.eventName=="PutRolePolicy" or .eventName=="CreatePolicyVersion") | "\(.eventTime) \(.requestParameters.policyName)"' cloudtrail.json
2026-01-13T22:41:03Z db-app-read-all
```

Политика с именем `...-read-all` и временем незадолго до чтения секрета — почти
наверняка путь атаки. Сверяем содержимое политики: есть ли `Resource: "*"` и
`Action: secretsmanager:GetSecretValue`.

## Практический разбор: чтение ключа KMS

```bash
$ jq -r 'select(.eventName=="Decrypt") | "\(.eventTime) \(.userIdentity.arn) \(.resources[0].ARN)"' cloudtrail.json | tail
2026-01-13T22:42:10Z arn:aws:iam::111:user/db-app arn:aws:kms:...:key/abc
```

Право `Decrypt` на ключ фактически равно праву читать всё, что им зашифровано.

## Ограничения и типичные ошибки

- **Аудит отключён.** Без аудит-лога Vault восстановить, кто читал секрет,
  невозможно — смотри логи приложения и CloudTrail.
- **Секрет ротирован.** Если после инцидента секрет сменили, убедись, что
  старый был скомпрометирован, а не просто устарел.
- **Разные аккаунты.** В мульти-аккаунтовых облаках логи лежат отдельно;
  собирай их в одном месте.
- **Время.** Синхронизируй часовые пояса всех источников перед сопоставлением.

## Практический разбор: обнаружение утечки по логам

Соберём картину инцидента, сопоставляя аудит секретов с другими событиями.
Начнём с выборки всех чтений за окно инцидента:

```bash
$ jq -r 'select(.eventName=="GetSecretValue") | "\(.eventTime)\t\(.sourceIPAddress)\t\(.requestParameters.secretId)"' cloudtrail.json | sort | tail -10
2026-01-13T22:44:02Z 203.0.113.5 arn:...:secret:prod/db
2026-01-13T22:45:11Z 203.0.113.5 arn:...:secret:prod/api
```

Внешний IP читает несколько секретов подряд за минуту — это выгрузка. Теперь
ищем, использовались ли секреты сразу после чтения: обращения к базе из
приложения с новыми кредами подтверждают эксплуатацию.

```bash
$ grep -E '22:4[4-5]' app-db.log | grep -i 'login failed'
```

## Секреты в Kubernetes и CI

- **Kubernetes Secrets.** base64, а не шифрование; при доступе к etcd секреты
  читаются напрямую. Проверь, включено ли шифрование at-rest.
- **ServiceAccount tokens.** Долгоживущие токены в подах — частый источник
  компромисса; предпочитай короткоживущие проекции.
- **CI/CD переменные.** Секреты пайплайна могут попасть в лог сборки; маскируй
  их и ограничивай вывод.
- **Внешние менеджеры.** Интеграция с Vault/AWS Secrets Manager через
  CSI-драйвер выдаёт секреты только нужным подам.

## Чек-лист расследования утечки секрета

1. Включён ли аудит менеджера секретов?
2. Кто и когда читал затронутые секреты?
3. С каких IP и ролей шло чтение?
4. Были ли изменения политик перед чтением?
5. Читались ли KMS-ключи (Decrypt)?
6. Использовался ли секрет сразу после чтения?
7. Проведена ли ротация и закрыты ли старые версии?

## Сравнение менеджеров секретов

| Менеджер | Аудит | Шифрование | Ротация | Особенность |
|---|---|---|---|---|
| HashiCorp Vault | свой audit-лог | барьер + KMS | динамические секреты | гибкие политики |
| AWS Secrets Manager | CloudTrail | KMS | встроенная | интеграция с RDS |
| Azure Key Vault | диагностика | HSM/KMS | ограниченная | ключи + секреты |
| GCP Secret Manager | Cloud Audit | KMS | версии | IAM-интеграция |
| Kubernetes Secrets | нет | опционально | нет | base64 по умолчанию |

Динамические секреты Vault (например, временные креды БД) живут минуты — при
утечке их окно использования мало. Статичные секреты в env опаснее.

## Практический разбор: ротация после инцидента

```bash
$ jq -r 'select(.eventName=="PutSecretValue" or .eventName=="UpdateSecret") | "\(.eventTime) \(.requestParameters.secretId)"' cloudtrail.json | tail -5
2026-01-14T01:02:00Z arn:...:secret:prod/db
```

Ротация через час после чтения с внешнего IP — реакция на инцидент. Проверь,
что старая версия признана скомпрометированной и все потребители обновлены.

## Ограничения и типичные ошибки

- **Аудит не включён по умолчанию.** В Vault аудит нужно включить явно; без
  него истории чтения нет.
- **Логи в разных аккаунтах.** В облаке логи могут лежать в отдельном
  аккаунте-архиве; собирай их централизованно.
- **Ключи без ротации.** Если KMS-ключ скомпрометирован, зашифрованные им
  секреты уязвимы до перешифрования.
- **Wildcard-политики.** Один `*` обнуляет гранулярность доступа; аудируй
  политики регулярно.
- **Секреты в git.** История репозитория — частая утечка; ищи ключи в прошлых
  коммитах.

## Типовые индикаторы компромисса секретов

| Индикатор | Что означает | Где искать |
|---|---|---|
| Чтение секрета с внешнего IP | утечка кредов | CloudTrail/Vault audit |
| Изменение политики перед чтением | повышение прав | CloudTrail |
| Массовое `GetSecretValue` подряд | выгрузка секретов | CloudTrail |
| `Decrypt` неожиданной ролью | доступ к KMS | CloudTrail |
| Секрет в логе CI | утечка в пайплайне | логи сборки |
| Долгоживущие креды | отсутствие ротации | IAM |

Каждый индикатор сам по себе слаб, но их сочетание во времени даёт уверенную
картину атаки.

## Что записать в отчёт

- Затронутые секреты и время чтения.
- Субъекты (роли/IP) и путь повышения прав.
- Использование ключей KMS и их последствия.
- Проведённые меры: ротация, отзыв кредов, правка политик.
- Ограничения: полнота логов, разные аккаунты, часовые пояса.

## Связь с IAM и ротацией

Менеджер секретов не существует отдельно от IAM: право читать секрет — это
результат политики, а политика — результат ролей и групп. Поэтому при
расследовании всегда поднимают историю изменений IAM и сопоставляют её с
чтениями секретов.

Ротация — это не только замена значения, но и обновление всех потребителей.
Если приложение продолжает использовать старый секрет, оно сломается или, что
хуже, оставит след старой скомпрометированной версии в логах.
