## Вопрос, с которого всё начинается

Файл занимает 100 байт, но кластер — 4096. Остальные ~4000 байт — **слак**: там могут
остаться данные предыдущего файла. Это бесплатная улика. Разберём FAT-слак.

## Наш пример: маленький файл

## Шаг 1: что такое слак

Файловая система выделяет место **кластерами**. Если файл меньше кластера, остаток
кластера остаётся занятым, но не перезаписанным:

```
файл A: 100 байт в кластере 4096 → 3996 байт слака
```

В слаке — «хвост» предыдущего содержимого кластера.

## Шаг 2: где искать в FAT

FAT (FAT16/FAT32) хранит цепочки кластеров в таблице. Последний кластер файла содержит
слак:

```
$ fls -r -p disk.img | grep 'file A'
r/r 5: file_A.txt
$ icat disk.img 5 | wc -c
100
```

Но кластер выделен на 4096 — остальное доступно через raw-чтение.

## Шаг 3: извлечение

Читаем кластер целиком:

```
$ dd if=disk.img bs=4096 skip=<cluster> count=1 | xxd | tail
```

Или используем карвинг: `foremost`/`scalpel` проходят по кластерам и находят сигнатуры.

## Шаг 4: что находится в слаке

- фрагменты удалённых файлов;
- старые версии;
- **RAM-slack** (из памяти) — фрагменты процессов;
- строки паролей/ключей.

## Шаг 5: практика

- слак есть в FAT, NTFS, ext;
- `slack space` собирают целиком для анализа;
- это «мусор», но часто золото.

## Что мы теперь знаем

- Слак — неиспользованный остаток кластера.
- В нём остаются данные предыдущих файлов.
- Извлекается raw-чтением кластера/карвингом.
- Может содержать фрагменты удалённого.
- Есть в FAT/NTFS/ext.

## Если не сработало

- ФС зашифрована? Слак тоже зашифрован.
- Кластеры перезаписаны? Данные потеряны.
- Нужен масштаб? Используй bulk-инструменты.

## Структура FAT: где искать данные

FAT (FAT12/16/32) — простая файловая система, состоящая из нескольких
областей:

- **Boot sector** — параметры: размер сектора, размер кластера, число FAT,
  размер корневого каталога;
- **FAT-таблицы** — цепочки кластеров (где продолжение файла);
- **Root directory** — каталог корня (в FAT12/16 фиксированный, в FAT32 —
  как обычный каталог);
- **Data area** — сами кластеры.

Из boot sector достаём **размер кластера** — ключевой параметр для слака:

```
$ xxd -l 64 disk.img
00000000: eb3c 906d 7364 6f73 362e 3000 0208 2000  .<.msdos6.0... .
```

Здесь `02 08` — 512 байт на сектор, 8 секторов на кластер → кластер 4096
байт.

## Работа на примере: находим слак

Файл занимает меньше кластера, но кластер выделяется целиком. Последний
кластер файла содержит «хвост» — **слак**. Смотрим цепочку и размер:

```
$ fls -r -p disk.img | grep file_A
r/r 5:	file_A.txt
$ istat disk.img 5 | grep -i size
size: 100
```

Файл 100 байт, кластер 4096 → около 3996 байт слака. Но `icat` вернёт
только 100 байт (логический размер). Чтобы получить слак, читаем **весь
кластер** напрямую:

```
$ dd if=disk.img bs=4096 skip=<cluster_number> count=1 | xxd | tail
```

В хвосте кластера — данные предыдущего файла, которые ещё не перезаписаны.

## Извлечение слака: raw-чтение и карвинг

Два подхода:

**1. Raw-чтение конкретного кластера.** Нужно знать номер кластера
(вычисляется из boot sector и цепочки FAT). Точно, но трудоёмко.

**2. Карвинг.** Инструменты `foremost`/`scalpel` проходят по всему образу,
ищут сигнатуры файлов и «вырезают» их:

```
$ foremost -i disk.img -o carved/
```

Карвинг находит и удалённые файлы — в том числе внутри слака, если
сигнатура уцелела.

## Виды слака

Различают три типа:

| Тип | Что это |
| --- | --- |
| RAM slack | остаток **последнего сектора** кластера (память) |
| File slack | от конца файла до конца кластера |
| Drive slack | нераспределённое пространство вне кластеров |

**RAM slack** — особенно интересен: если файл писался блоками меньше
сектора, остаток сектора может содержать фрагмент памяти процесса. Именно
отсюда в слаке иногда находят пароли и ключи.

## Что находят в слаке

- фрагменты **удалённых** файлов;
- **старые версии** текущих файлов;
- обрывки текста, URL, имён;
- строки **паролей/ключей** (особенно RAM slack);
- заголовки файлов для карвинга.

Слак — «бесплатная» улика: данные лежат там, где их не ищут.

## Ограничения

- **Перезапись** — новые записи затирают слак; чем больше активности, тем
  меньше данных.
- **Шифрование ФС** — слак тоже зашифрован, ничего не достать без ключа.
- **Мусор** — не все фрагменты осмысленны; отделяй улику от случайных байт.
- **Неоднозначность** — файл, «вырезанный» из слака, может быть неполным;
  фиксируй это в отчёте.

## Практический чек-лист

1. Определить размер кластера из boot sector.
2. Для подозрительных файлов найти последний кластер.
3. Прочитать кластер целиком (`dd`), а не через `icat`.
4. Прогнать карвинг (`foremost`/`scalpel`) по образу.
5. Собрать «slack space» целиком для поиска строк.
6. Сопоставить найденное с удалёнными файлами.
7. Зафиксировать происхождение фрагмента (какой кластер/файл).

## Работа с FAT-таблицей и цепочками

FAT хранит цепочки кластеров: для каждого кластера — номер следующего (или
маркер конца `0x0FFFFFFF`). Чтобы прочитать файл, надо пройти цепочку.
Каталог содержит имя, атрибуты, первый кластер и **логический размер**.

Полезно: в каталоге остаётся запись удалённого файла с первым кластером, но
помеченная `0xE5`. Если кластеры ещё не перезаписаны — файл восстановим:

```
$ fls -d -p disk.img | head
r/r * 5:	deleted_secret.txt
```

Флаг `*` и `-d` (только удалённые) помогают найти то, что «стёрли».

## Практический сценарий: пароль в RAM slack

Известный приём: файл писали маленькими блоками, и остаток последнего
сектора сохранил фрагмент памяти — там может лежать пароль. Ищем в слаке
строки:

```
$ dd if=disk.img bs=512 skip=<last_sector> count=1 | strings | grep -iE 'pass|key'
```

Если пароль нашёлся — это RAM slack. Он ценен тем, что данные попали туда
не из файла, а из оперативной памяти в момент записи, и могли не попасть
больше никуда.

## Сравнение слака в NTFS и ext

Слак есть не только в FAT:

| ФС | Особенность слака |
| --- | --- |
| FAT | хвост кластера, простой для чтения |
| NTFS | $MFT-записи + slack в последнем кластере |
| ext2/3/4 | хвост блока; inode хранит размер |

В NTFS дополнительно есть **MFT slack** (неиспользованная часть записи
файла) — иногда там сохраняются старые атрибуты. В ext слак извлекается
похожим образом: читаем блок целиком, а не по размеру файла.

## Итог: слак — это «хвосты» и «дыры»

Слак — не отдельный файл, а пространство между логическим размером данных и
физически выделенным местом. Именно поэтому там оседает старое содержимое:
файловая система не затирает кластеры, а лишь помечает их. Извлекать слак
надо **raw-чтением** (весь кластер/блок), а не через логическое чтение
файла. В связке с карвингом это даёт доступ к данным, которые уже «удалены».

## Инструменты карвинга подробнее

Карвинг ищет файлы по **сигнатурам** (заголовкам/хвостам). Основные
инструменты:

- **foremost** — по конфигу `/etc/foremost.conf` (JPEG, PNG, PDF, ZIP...);
- **scalpel** — быстрее, конфиг настраивается;
- **bulk_extractor** — ищет не файлы, а **шаблоны** (email, карты, ключи);
- **photorec** — восстановление медиа.

```
$ bulk_extractor -o out/ disk.img
```

`bulk_extractor` особенно полезен для слака: он находит строки-шаблоны
(номера карт, email, URL) даже в обрывках данных.

## Частые ошибки

- **Читать файл через `icat` и ждать слак** — `icat` вернёт только
  логический размер; слак требует raw-чтения кластера.
- **Забыть про размер кластера** — без него не найти границы.
- **Принять мусор за улику** — проверяй контекст найденных строк.
- **Игнорировать шифрование** — если ФС зашифрована, слак тоже.
- **Карвить по всему диску без нужды** — это долго; сначала сузь область.

## Пример: восстановление удалённого файла

Пусть нужно достать удалённый текстовый файл. Смотрим записи каталога с
флагом удаления:

```
$ fls -d -p disk.img
r/r * 7:	notes.txt
```

Запись помечена `*` — файл удалён, но первый кластер известен. Читаем по
цепочке FAT нужные кластеры и собираем содержимое:

```
$ dd if=disk.img bs=512 skip=<start> count=<n> | strings | head
```

Если кластеры перезаписаны частично — файл восстановится лишь фрагментами;
это нормально, фиксируй неполноту. Дополнительно прогони карвинг, чтобы
выловить обрывки из слака.
