## Вопрос, с которого всё начинается

Компьютер выключили — оперативная память «исчезла». Но если система уходила в **гибернацию** (спящий режим с сохранением на диск), Windows перед выключением сбрасывает всю RAM в файл `hiberfil.sys`. Значит, на диске может лежать снимок памяти, где остались пароли, ключи, содержимое процессов. Как его прочитать и что там искать?

## Наш пример: hiberfil.sys

У нас есть файл `hiberfil.sys` — образ гибернации. Посмотрим начало:

```bash
$ xxd -l 32 hiberfil.sys
00000000: 4849 4252 0100 0000 0000 0000 0000 0000  HIBR............
```

Первые байты `HIBR` — сигнатура заголовка файла гибернации. Дальше — метаданные и упакованный образ памяти. Важно: содержимое сжато (алгоритм **XPRESS**/LZX), поэтому просто `strings` по всему файлу даст мало. Правильный путь — распаковать и работать как с дампом RAM.

## Шаг 1: что вообще такое гибернация

Обычный «сон» (S3) держит память под напряжением — данные живут, пока есть питание. **Гибернация** (S4) иначе: содержимое RAM записывается на диск и питание отключается полностью. При включении образ читается обратно. Побочный эффект для форензики: **вся память оказалась на диске** — и остаётся там, даже если систему потом выключили «насовсем» (файл перезаписывается только при следующей гибернации или удаляется при отключении функции).

## Шаг 2: hiberfil против pagefile

Рядом живёт второй файл — `pagefile.sys` (файл подкачки). Разница принципиальна:

| Файл | Что хранит | Полнота |
|------|-----------|---------|
| `hiberfil.sys` | полный образ RAM на момент гибернации | высокая (снимок всей памяти) |
| `pagefile.sys` | страницы, вытесненные из RAM по мере нужды | фрагментарная (только вытесненное) |

`hiberfil` — это «стоп-кадр» всей памяти, `pagefile` — «свалка» страниц, которые давно не использовались. На практике оба ценны: hiberfil даёт полный контекст, pagefile — данные, которые могли быть вытеснены ещё до гибернации.

## Шаг 3: разбор hiberfil через Volatility

Volatility3 умеет открывать `hiberfil.sys` напрямую и распаковывать его «на лету». Плагин `windows.hibernation` восстанавливает информацию о страницах:

```bash
$ vol -f hiberfil.sys windows.info
Variable        Value
Kernel Base     0xf8000000
DTB             0x1a0000
Symbols         ntkrnlmp.pdb
```

Дальше можно применять обычные плагины памяти: `windows.pslist`, `windows.cmdline`, `windows.netscan`, `windows.hashdump`. То есть hiberfil — это полноценный дамп RAM, просто в сжатом формате.

## Шаг 4: что мы ищем внутри

В памяти остаются самые ценные артефакты:

- **Учётные данные** — пароли в открытом виде, хеши (LM/NTLM), керберос-билеты. Плагины `windows.hashdump`, `windows.lsadump`, `windows.cachedump`.
- **Ключи шифрования** — `windows.bitlocker`, `windows.truecrypt`.
- **Строки процессов** — командные строки, URL, содержимое буферов. `strings` по распакованному дампу + `grep`.
- **Флаг в CTF** — обычно спрятан в одном из буферов.

Наш учебный парсер распаковывает фрагмент и печатает найденные артефакты:

```bash
$ python3 hibparse.py
[HIBR] signature HIBR ok, 134 bytes
[HIBR] process : lsass.exe
[HIBR] cred    : admin / P@ssw0rd!2024
[HIBR] key     : nto{h1b3rfil_r4m_0n_d1sk}
```

Забираем ключ:

```bash
$ python3 hibparse.py | grep nto > found.txt
```

## Шаг 5: pagefile отдельно

Если hiberfil нет (гибернация отключена), смотрим `pagefile.sys`. Он не сжат, поэтому `strings` работает сразу:

```bash
$ strings -n 6 pagefile.sys | grep -Ei 'password|token|BEGIN .*KEY'
password=hunter2
-----BEGIN RSA PRIVATE KEY-----
```

`bulk_extractor` умеет вытаскивать из pagefile email-адреса, URL, номера карт и ключи автоматически — он не полагается на структуры, а ищет шаблоны.

## Шаг 6: анти-форензика и следы

Атакующий может попытаться «подчистить»: отключить гибернацию (`powercfg /h off`) или перезаписать pagefile при выключении. Но:

- Перезапись pagefile (`ClearPageFileAtShutdown`) — настройка реестра; сам факт её включения виден в `HKLM\SYSTEM\CurrentControlSet\Control\Session Manager\Memory Management`.
- Отключение гибернации оставляет след в журналах и в системном реестре.
- Даже после `powercfg /h off` ранее созданный образ мог остаться в резервной копии или на диске, если не был перезаписан.

## Если не сработало

- **Volatility не читает hiberfil** → проверьте версию: старый файл мог быть создан с другим форматом сжатия; попробуйте `--hibernate`/автоопределение, либо распакуйте вручную.
- **strings почти пусто** → вы читаете сжатый файл; нужна распаковка (Volatility делает это сам).
- **hiberfil отсутствует** → гибернация выключена; работайте с pagefile и с дампами, снятыми вручную.
- **Файл обрезан** → образ гибернации пишется целиком; обрезанный файл говорит о неполном сборе (проверьте носитель и хеш).

## На что смотреть защитнику

- Шифрование диска (BitLocker) защищает hiberfil: без ключа его содержимое не восстановить.
- Отключение гибернации там, где она не нужна, уменьшает «память на диске».
- Регулярная перезапись pagefile при выключении снижает утечку старых страниц.

## Что мы теперь знаем

- **Гибернация** сохраняет всю RAM в `hiberfil.sys`; это снимок памяти на диске.
- `hiberfil` сжат (XPRESS/LZX), но Volatility открывает его напрямую.
- `pagefile.sys` хранит вытесненные страницы и не сжат — годится для `strings`/`bulk_extractor`.
- В памяти ищем пароли, хеши, ключи, командные строки и флаги.
- Анти-форензика (отключение/перезапись) оставляет собственные следы.

## Шаг 7: заголовок hiberfil и структура PO_MEMORY_IMAGE

Файл гибернации начинается со структуры `PO_MEMORY_IMAGE`. Первые 4 байта — сигнатура `hibr` (в hex `68 69 62 72`), далее идут версии и геометрия образа:

```bash
$ xxd -l 64 hiberfil.sys
00000000: 6869 6272 0100 0000 0000 0000 0000 0000  hibr............
00000010: 0000 0000 0000 0000 0000 0000 0000 0000  ................
```

| Поле | Смещение | Смысл |
|------|----------|-------|
| Signature | 0x00 | `hibr` — метка образа гибернации |
| MajorVersion/MinorVersion | 0x04/0x08 | версия формата сжатия |
| Length | 0x10 | полный размер образа памяти |
| PageSize | 0x1C | размер страницы (обычно 4096) |
| FirstPage/RunLength | далее | карта сжатых страниц |

Понимание заголовка важно потому, что разные версии Windows используют разные алгоритмы сжатия: старые — XPRESS Huffman, новые — LZX/XPRESS8K. Именно поэтому старый парсер может «не увидеть» новый файл, а Volatility выбирает декомпрессор по версии из заголовка.

## Шаг 8: pagefile как источник аварийного дампа

У `pagefile.sys` есть второй, неочевидный слой. В Windows 8+ режим «автоматический дамп памяти» пишет ядровый дамп **сначала в файл подкачки**, а при следующей загрузке извлекает его в `MEMORY.DMP`. Значит, внутри pagefile может лежать полноценный kernel-дамп с сигнатурой `PAGEDU64`. Найти его можно так:

```bash
$ grep -abo 'PAGEDU64' pagefile.sys
268435456:PAGEDU64
$ dd if=pagefile.sys of=kerndump.raw bs=1 skip=268435456
```

Дальше `kerndump.raw` открывается как обычный дамп. Это спасает, когда `MEMORY.DMP` уже перезаписан, а pagefile остался. Полезно помнить, что `grep -abo` печатает байтовое смещение — именно оно становится аргументом `skip` у `dd`.

## Шаг 9: извлечение секретов из памяти

Память — лучший источник учётных данных. В Volatility3 для этого есть целый набор плагинов:

| Плагин | Что достаёт |
|--------|-------------|
| `windows.hashdump` | NTLM/LM-хеши из SAM |
| `windows.lsadump` | секреты LSA (в т.ч. пароли служб) |
| `windows.cachedump` | кэшированные доменные креды (DCC2) |
| `windows.registry.hivelist` | список кустов реестра в памяти |
| `windows.cmdline` | командные строки процессов |
| `windows.envars` | переменные окружения |
| `windows.netscan` | сетевые соединения на момент снятия |

Полученные хеши идут в `hashcat -m 1000` (NTLM) или `-m 2100` (DCC2). Помимо Volatility, «сырой» поиск даёт `strings -el` (UTF-16LE — Windows хранит строки в двухбайтовой кодировке) и `bulk_extractor`, который сам вытаскивает email, URL, номера карт и ключи по шаблонам. `strings -el` важен ещё и потому, что обычный `strings` ищет ASCII и пропускает половину артефактов Windows.

## Шаг 10: практика — конвейер от файла к флагу

Соберём всё в один сценарий:

```bash
$ file hiberfil.sys            # убедиться, что это образ, а не мусор
$ xxd -l 16 hiberfil.sys       # проверить сигнатуру hibr
$ vol -f hiberfil.sys windows.info
$ vol -f hiberfil.sys windows.pslist
$ vol -f hiberfil.sys windows.cmdline
$ vol -f hiberfil.sys windows.hashdump
$ strings -el hiberfil.sys | grep -i -E 'pass|token|nto{'
```

Если Volatility нет, а образ сжат, поможет `imagecopy`/`hibr2bin` (Volatility 2) или ручная распаковка через `python3` с XPRESS-декодером. Для pagefile распаковка не нужна — сразу `strings` и `bulk_extractor`. Такой конвейер воспроизводит реальный порядок работы аналитика: сначала метаданные, потом процессы, потом секреты.

## Шаг 11: подводные камни и частые ошибки

- **Файл затирается при следующей гибернации.** `hiberfil.sys` не «дописывается», а перезаписывается целиком; если машина уходила в сон после инцидента, старый образ мог пропасть.
- **Быстрый запуск (Fast Startup) и гибернация — разные вещи.** Fast Startup пишет урезанный образ в `hiberfil.sys`, а полноценная гибернация — весь RAM; полнота образа зависит от режима.
- **`powercfg /h off` удаляет файл.** Если функцию отключили, от `hiberfil.sys` может остаться только область в `$MFT`; проверяйте журналы и резервные копии.
- **BitLocker меняет всё.** На зашифрованном томе `hiberfil.sys` тоже зашифрован — без ключа восстановления анализ невозможен.
- **Символы Volatility.** Для плагинов ядра нужен ISF под конкретную сборку; без символов плагины памяти не запустятся.

## Куда дальше

Мы увидели, что память остаётся и на диске. В следующем уроке (`forensics-crash-dumps`) разберём аварийный дамп — снимок ядра в момент падения системы. А пока главное запомни: **hiberfil.sys — это полный образ RAM, оставшийся на диске**.

## Где пригодится

- **CTF:** флаг или пароль в hiberfil/pagefile образа.
- **IR:** восстановление учётных данных без живой системы.
- **Memory Forensics:** анализ памяти, когда дамп RAM не снимали вручную.
- **Судебная экспертиза:** доказательство действий, зафиксированных в памяти.
