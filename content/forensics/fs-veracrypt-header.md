## Вопрос, с которого всё начинается

Ты нашёл на диске файл, который выглядит как случайный шум: нет ни сигнатуры, ни заголовка.
`file` молчит. Это может быть **контейнер VeraCrypt**. И самое интересное: в таком
контейнере может быть **скрытый том**, существование которого нельзя доказать, не зная
пароля. Как расследовать то, что «невидимо»?

## Что такое VeraCrypt

**VeraCrypt** — наследник TrueCrypt, программа для создания зашифрованных томов (файлов
и разделов). В отличие от LUKS, у VeraCrypt **нет сигнатуры заголовка**: первые байты
тома выглядят как случайные данные. Это сделано намеренно — чтобы нельзя было доказать
наличие шифрования, просто посмотрев на диск.

Структура тома:

- **Основной том (outer volume)** — обычный зашифрованный том; открывается одним паролем.
- **Скрытый том (hidden volume)** — второй том **внутри свободного места** основного.
  Открывается другим паролем; при этом основной том показывает «безобидные» файлы.

## Наш пример: неотличимый от шума файл

```
$ ls -la
-rw-r--r-- 1 student student 10485760 vc.hdr
$ file vc.hdr
vc.hdr: data
$ xxd -l 32 vc.hdr
00000000: 3f8a 12d4 9e77 01bc 55a0 6f3e d812 c944  ?....w..U.o>...D
00000010: a71b 90fe 2c5d 8842 e0f3 1176 bb29 4a5c  ....,].B...v.)J\
```

Никакой магии — чистый шум. Именно так и выглядит заголовок VeraCrypt: **случайные байты**.
Поиск сигнатур тут бесполезен. Зато полезны другие признаки. Посмотрим текстовые метки,
которые кто-то мог оставить:

```
$ strings vc.hdr | grep -Ei 'hidden|header|backup|volume|nto'
hidden volume header present
backup header at offset 65536
volume uses XTS
NOTE: nto{v3r4crypt_h1dd3n_v0lum3}
```

Признаки: скрытый том, резервный заголовок по смещению 65536, режим XTS. Это уже зацепки.

## Шаг 1: где лежат заголовки

Заголовок VeraCrypt — **512 байт**. У тома есть несколько копий:

| Копия | Смещение | Назначение |
|-------|----------|------------|
| Основной заголовок | 0 | зашифрован, содержит ключ |
| Резервный заголовок | 65536 (0x10000) | копия на случай повреждения |
| Заголовок скрытого тома | в конце тома | ключ скрытого тома |

Важно: заголовок **сам зашифрован** ключом из пароля, поэтому байты внутри выглядят
случайными. Опознать его по содержимому нельзя — только по позиции и по тому, что
**первые 512 байт не соответствуют известному формату** (нет boot sector, нет магии ФС).

## Шаг 2: скрытый том — главная особенность

Идея **правдоподобного отрицания (plausible deniability)**: основной том заполнен
«безобидными» данными, а в его свободном месте лежит второй, скрытый том. Если от тебя
требуют пароль, ты отдаёшь пароль основного тома — и следователь видит только его.
Существование скрытого тома **доказать без пароля крайне трудно**.

Технически скрытый том занимает область, которую основной том считает **свободной**.
Ключевая проблема при записи в основной том — не затереть скрытый; VeraCrypt умеет
«защиту скрытого тома» при монтировании. При расследовании:

- оцени **энтропию свободного места** основного тома: если оно «слишком случайное» — там
  может быть скрытый том;
- ищи **второй заголовок** в конце тома;
- проверь, не оставлены ли следы монтирования (см. ниже).

## Шаг 3: энтропийный анализ

Раз данные зашифрованы, они статистически неотличимы от случайных. Инструменты:

- **`ent`** — считает энтропию блока; у шифротекста она близка к 8 бит/байт;
- **binwalk -E** — карта энтропии по всему файлу;
- визуально на графике энтропии видно, где кончается «нормальная» ФС и начинается
  высокоэнтропийная область.

```
$ ent vc.hdr
Entropy = 7.999812 bits per byte.
```

Энтропия ~8 — сильный признак шифрования или сжатия. Но это **не доказательство**
VeraCrypt: любой шифротекст так выглядит. Нужны дополнительные признаки.

## Шаг 4: следы монтирования

Даже если сам том неотличим, система оставляет следы его использования:

- **недавно открытые файлы** в реестре/`~/.recently-used`;
- **записи в логах** драйвера (VeraCrypt устанавливает драйвер);
- **конфигурация** VeraCrypt (история томов) в `~/.VeraCrypt` / реестре;
- **`pagefile`/`hiberfil`** могут содержать расшифрованные данные;
- **дампы памяти** — ключи в RAM, пока том смонтирован.

Это ключевая идея: **сам том невидим, но его использование — нет**.

## Шаг 5: перебор пароля

VeraCrypt применяет медленный PBKDF (по умолчанию сотни тысяч итераций). Перебор:

- **hashcat** с модулями VeraCrypt (разные для типов: `-m 13711` RIPEMD160, `-m 13721`,
  `-m 13751`, `-m 13761` и т.д.);
- словарная атака с ограниченным словарём;
- проверка режима (XTS) и хеш-функции — от них зависит модуль.

```
$ hashcat -m 13721 -a 0 hash.txt wordlist.txt
```

Важно подобрать **правильный модуль**: заголовок VeraCrypt хешируется по-разному для
разных комбинаций хеш/шифр.

## Мини-практика: признаки контейнера

```
$ file vc.hdr
vc.hdr: data
$ ent vc.hdr
Entropy = 7.999812 bits per byte.
$ strings vc.hdr | grep -Ei 'backup|hidden'
backup header at offset 65536
hidden volume header present
```

Три признака: нет формата, высокая энтропия, метки заголовков. Это не доказывает VeraCrypt
(если только метки не оставлены), но сужает круг.

## Частые ошибки и подводные камни

- **Поиск сигнатуры.** У VeraCrypt её нет — не трать время.
- **Считать энтропию доказательством.** Любой шифротекст высокоэнтропиен.
- **Игнорировать резервные заголовки.** Их несколько; повреждение основного не фатально.
- **Забыть про скрытый том.** Открытие основного тома не означает отсутствия скрытого.
- **Перебор вслепую.** Сначала определи хеш/шифр, потом выбирай модуль hashcat.

## Что мы теперь знаем

- VeraCrypt не имеет сигнатуры — заголовок выглядит случайным.
- Заголовок 512 байт; есть основная и резервная копии (offset 0 и 65536).
- Скрытый том живёт в «свободном» месте основного — правдоподобное отрицание.
- Энтропия ~8 бит/байт — признак шифрования, но не доказательство.
- Следы монтирования (логи, кэш, память) важнее самого тома.

## Что фиксировать в отчёте

| Что | Зачем |
|-----|-------|
| Отсутствие сигнатуры + энтропия | признак шифрованного тома |
| Наличие резервных заголовков | шанс восстановления |
| Признаки скрытого тома | полнота картины |
| Следы монтирования | факт использования |
| Тип хеш/шифр для перебора | выбор модуля |

## Отличия от TrueCrypt и LUKS

VeraCrypt — прямой наследник **TrueCrypt**, и полезно понимать разницу:

| Свойство | TrueCrypt | VeraCrypt | LUKS |
|----------|-----------|-----------|------|
| Сигнатура | нет | нет | `LUKS\xba\xbe` |
| PBKDF итерации | низкие | в разы выше | PBKDF2/argon2 |
| Скрытый том | да | да | нет |
| Опознание | по позиции | по позиции | по магии |
| Перебор | быстрее | медленнее | медленнее (argon2) |

Ключевое практическое следствие: VeraCrypt **специально поднял число итераций**, поэтому
старые словари и радужные таблицы TrueCrypt на нём не работают. Это важно при оценке
времени перебора: не переносить оценки TrueCrypt на VeraCrypt.

Ещё одно отличие — **заголовок скрытого тома** в VeraCrypt находится **в конце** тома, тогда
как в некоторых версиях TrueCrypt его расположение иное. Поэтому при разборе образа ищи
заголовки и в начале, и в конце.

## Практический алгоритм расследования

Порядок действий для подозрительного «шумного» файла:

1. **Отсечь очевидное.** Проверь `file`, сигнатуры известных форматов — если ничего, это
   кандидат на шифрованный том.
2. **Оцени энтропию** (`ent`, `binwalk -E`) — карта по всему файлу.
3. **Поищи заголовки** в начале и в конце; проверь offset 65536.
4. **Ищи следы использования**: конфиги, историю томов, логи драйвера, `pagefile`, дампы
   памяти.
5. **Определи тип** (хеш/шифр) для правильного модуля перебора.
6. **Словарная атака** с ограниченным словарём и оценкой времени.
7. **Зафиксируй вывод**: если скрытый том не доказан, это тоже результат, и его надо
   сформулировать корректно.

Такой порядок не тратит часы на перебор там, где сначала нужно было просто найти пароль в
конфиге.

## Анатомия заголовка: соль, magic и выбор модуля hashcat

Заголовок VeraCrypt (512 байт) устроен так: **первые 64 байта — соль** (случайная, открытая),
а **остальные 448 байт — зашифрованная часть**. Внутри зашифрованной части, после расшифровки,
лежит «магия» — строка `VERA` (или `TRUE` для совместимости с TrueCrypt) по смещению 64. Именно
её ищет любая проверка пароля: расшифровал заголовок → увидел `VERA` → пароль верный.

```
offset 0    64 bytes   salt (открытая, случайная)
offset 64   448 bytes  зашифрованный заголовок → внутри "VERA" + master keys
```

Практический вывод для подбора: соль берётся из первых 64 байт, а нужный модуль hashcat
зависит от **хеш-функции** и типа тома:

| Тип | hashcat mode |
|-----|--------------|
| VeraCrypt RIPEMD160 + XTS | 13711 |
| VeraCrypt SHA-512 + XTS | 13721 |
| VeraCrypt SHA-256 + XTS | 13731 |
| VeraCrypt Whirlpool + XTS | 13741 |
| VeraCrypt Streebog + XTS | 13751 |

Ошибка новичка — гнать все модули подряд. Сначала посмотри `strings`/метаданные (или открой
том в GUI), определи хеш, и только потом выбирай режим: лишние модули — потраченные часы.

## Ключ из памяти: RAM-форензика против шифрованного тома

Самое надёжное против шифрованного тома — застать его **смонтированным**: пока том открыт,
его мастер-ключ лежит в оперативной памяти. Дамп памяти (или `pagefile`/`hiberfil`) содержит
ключ в открытом виде, и том можно расшифровать без перебора пароля:

```bash
# поиск ключей AES в дампе памяти
$ aeskeyfind memdump.raw
Found AES-256 key schedule at offset 0x2f8a1c40:
  d4 9e 77 01 bc 55 a0 6f 3e d8 12 c9 44 a7 1b 90 ...
# альтернатива — Volatility и поиск структур драйвера VeraCrypt
$ volatility -f memdump.raw --profile=Win10x64 yarascan -Y "VERA"
```

Логика: том «невидим» на диске, но **смонтированный том виден в памяти**. Поэтому при
живом реагировании первым делом снимают память — если том отключат, ключ исчезнет. Это ещё
раз подтверждает общий принцип: артефакты использования важнее самого носителя.

## Куда дальше

Мы разобрали VeraCrypt. Дальше возьмём **BitLocker** — там снова есть опознаваемый заголовок
`-FVE-FS-`, но ключ защищён TPM и recovery-паролем. А пока главное запомни: **невидимый
том всё равно оставляет следы использования**.

## Где пригодится

- **CTF Forensics:** контейнеры, выглядящие как случайные данные.
- **DFIR:** расследование с правдоподобным отрицанием.
- **Data recovery:** работа с резервными заголовками.
- **Anti-forensics:** понимание сокрытия и его слабых мест.
