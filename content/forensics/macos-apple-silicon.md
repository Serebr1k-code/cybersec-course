## Вопрос, с которого всё начинается

Старые инструкции по форензике macOS писались для Intel. На новых Mac — **Apple
Silicon** (M1/M2/M3), и многое изменилось: другая архитектура, другой способ защиты
ключей, даже память устроена иначе. Разберём, что именно.

## Наш пример: определяем платформу

## Шаг 1: архитектура

```
$ uname -m
arm64
```

`arm64` (он же `aarch64`) означает ARM-процессор. Это не просто «другая ISA»: у ARM
другая модель памяти и загрузки. Скомпилированные под x86 инструменты работают через
Rosetta 2 — и могут оставлять свои артефакты.

## Шаг 2: унифицированная память

На Apple Silicon память **общая** для CPU и GPU (UMA). Практическое следствие:
разделение «память CPU» и «видеопамять» исчезает. При сборе дампа это меняет то, что
вообще доступно.

```
$ system_profiler SPHardwareDataType | grep -E 'Chip|Memory'
      Chip: Apple M2
      Memory: 16 GB
```

## Шаг 3: Secure Enclave

**Secure Enclave** — отдельный защищённый сопроцессор. Он хранит ключи шифрования
диска, ключи Touch ID и ключи iCloud. Из него ключи **не извлекаются** обычными
методами.

```
$ system_profiler SPiBridgeDataType 2>/dev/null | head
```

Это значит: снять ключ шифрования диска напрямую нельзя. Приходится либо знать
пароль пользователя, либо использовать живую систему с разблокированным ключом.

## Шаг 4: что это меняет для сбора

- **Шифрование диска по умолчанию**: на Apple Silicon всё шифруется аппаратно.
- **Без разблокировки** прочитать диск нельзя даже с физическим доступом.
- **Загрузка только подписанного ПО** (Secure Boot) — сложнее загрузить внешний
  форензик-образ.
- **Память**: сбор возможен, но требует отключённого SIP или особых привилегий.

## Шаг 5: проверяем защиту

```
$ csrutil status
System Integrity Protection status: enabled.
$ nvram boot-args
(none)
```

`enabled` означает, что SIP защищает системные файлы. Для живой форензики часто
требуется временно отключить SIP — но это меняет состояние системы, поэтому фиксируй
это в отчёте.

## Что мы теперь знаем

- Apple Silicon = ARM (`arm64`), x86 через Rosetta 2.
- Унифицированная память меняет модель сбора.
- Secure Enclave хранит ключи и не отдаёт их наружу.
- Диск шифруется аппаратно; без разблокировки чтения нет.
- SIP и Secure Boot ограничивают живой сбор.

## Если не сработало

- Нужен диск без разблокировки? Только официальные средства Apple (не сработает).
- Нужна память? Отключи SIP в recovery-режиме и зафиксируй это.
- Нужны ключи iCloud? Только через аккаунт пользователя.

## Что меняется в загрузке

Apple Silicon использует цепочку доверия, начинающуюся с **Boot ROM**, и проверяет
каждый этап по подписи. Это меняет подход к «загрузке с внешнего носителя»:

- **Boot Policy** — можно ли грузиться с внешнего диска, задаётся отдельно для каждой
  системы; по умолчанию запрещено.
- **Recovery** — доступна по удержанию кнопки питания; требует пароля администратора.
- **Secure Boot** — три режима: `Full`, `Medium`, `Permissive`; влияет на то, что можно
  загрузить.

```
$ bputil -d          # показать boot policy (в recovery)
$ system_profiler SPiBridgeDataType | head
```

Практический вывод: чтобы загрузить внешний форензик-образ, нужно снять boot policy —
а это **изменение состояния** системы, которое обязано быть в отчёте.

## Rosetta 2 и его артефакты

x86-бинарники на Apple Silicon исполняются через **Rosetta 2** (трансляция). Это оставляет
следы:

- пакет `/Library/Apple/usr/libexec/oah/` и `RosettaUpdateAuto`;
- записи в unified log о трансляции;
- файл `rosetta` в кэшах.

```
$ pgrep -lf oahd          # демон трансляции
$ log show --predicate 'subsystem == "com.apple.oahd"' --last 1h | head
```

Если подозрительный бинарник — x86, он всё равно запустится; но факт использования Rosetta
сужает список возможных авторов (не все тулы имеют arm64-версию).

## Secure Enclave (SEP) и что в нём

Secure Enclave Processor — отдельный сопроцессор с собственной ОС. В нём хранятся:

- ключи шифрования диска (FileVault) — выводятся из пароля + SEP;
- ключи Touch ID / Face ID;
- ключи iCloud Keychain (частично);
- ключи Apple Pay.

Извлечь ключ из SEP **штатно невозможно** — он не покидает чип. Следствия для форензики:

- без пароля пользователя расшифровать том не получится;
- Touch ID «привязан» к устройству, перенос невозможен;
- при перезагрузке нужно вводить пароль заново (SEP не хранит разблокированный ключ в
  энергонезависимом виде).

## Унифицированная память и сбор дампа

На Apple Silicon память общая для CPU, GPU и Neural Engine. Это значит:

- классического «отдельного видеопамять-дампа» нет;
- порядок размещения структур в памяти может отличаться от Intel;
- многие Intel-ориентированные плагины Volatility не работают на arm64-дампах.

Сбор живой памяти требует отключённого SIP или особых привилегий; для arm64-дампов
используют инструменты с поддержкой ARM (например, `osxpmem`-форки, `mac memory`).
Дампы снимаются **до** выключения, пока ключи FileVault ещё в памяти.

## APFS, снапшоты и раздельные тома

macOS на Apple Silicon использует APFS с несколькими томами в одной группе:

| Том | Роль |
|---|---|
| System | только чтение, подписан, монтируется в `/` |
| Data | пользовательские данные, в `/System/Volumes/Data` |
| Preboot | загрузочные данные, ключи |
| VM | swap |
| Recovery | среда восстановления |

APFS ведёт **снапшоты** (в т.ч. автоматические Time Machine local snapshots) — это
форензик-золото: можно вернуться к состоянию до атаки:

```
$ diskutil apfs listSnapshots /
$ tmutil listlocalsnapshots /
$ mount_apfs -s com.apple.TimeMachine.2026-01-13... /dev/disk3s1 /mnt
```

## Чек-лист сбора и анализа

1. Определить платформу (`uname -m`, `system_profiler SPHardwareDataType`).
2. Проверить SIP (`csrutil status`) и boot policy (`bputil -d`).
3. Снять живые данные (память, `log show`, `fseventsd`) до выключения.
4. Снять образ с разблокированного тома (FileVault открыт).
5. Найти APFS-снапшоты и сравнить состояния.
6. Учесть Rosetta-артефакты, если анализируешь x86-бинарники.

## Ограничения

- Без пароля/разблокировки — диск не прочитать (аппаратное шифрование).
- Secure Boot + boot policy затрудняют внешний сбор.
- Многие инструменты не поддерживают arm64 — проверяй совместимость.
- SEP не даёт вытащить ключи — «обойти» это невозможно штатными средствами.

## Что изменилось по сравнению с Intel

Переход на Apple Silicon — не просто смена процессора. Сравним ключевые аспекты:

| Аспект | Intel Mac | Apple Silicon |
|---|---|---|
| Архитектура | x86_64 | arm64/aarch64 |
| Память | раздельная (RAM/VRAM) | унифицированная (UMA) |
| Шифрование диска | T2 (Intel с T2) | всегда, через Secure Enclave |
| Ключи | Secure Enclave (T2) | Secure Enclave (встроен в SoC) |
| Загрузка | EFI | boot-политики, Secure Boot |
| Память (сбор) | дамп через инструменты | требует отключённого SIP |

Практический вывод: старые методички «как снять дамп памяти Mac» часто неприменимы —
у ARM другой способ доступа, а ключи диска вынесены в отдельный чип.

## Шифрование диска и FileVault

На Apple Silicon **весь** внутренний SSD шифруется аппаратно, даже если FileVault
формально «выключен». Разница в том, где хранится ключ:

- **FileVault включён** — ключ разблокировки защищён паролем пользователя/Secure Enclave;
- **FileVault выключен** — ключ доступен системе автоматически, но всё равно в
  Secure Enclave.

Проверить статус:

```
$ fdesetup status
FileVault is On.
```

Для оффлайн-анализа образа нужно, чтобы диск был расшифрован (например, снят при
разблокированной живой системе). Без этого — только метаданные.

## SIP, Secure Boot и boot-политики

Три уровня защиты ограничивают форензику:

- **SIP (System Integrity Protection)** — защищает системные пути; `csrutil status`;
- **Secure Boot** — загружается только подписанный код; для внешнего загрузочного
  носителя нужно снижать политику;
- **SSV (Signed System Volume)** — системный том подписан; любые изменения видны как
  расхождение хешей.

Проверки:

```
$ csrutil status
$ bputil -d 2>/dev/null | head       # boot-политика (в recovery)
$ system_profiler SPiBridgeDataType | head
```

Изменение этих настроек для сбора данных — **изменение состояния улик**, обязательно
фиксируй в отчёте и делай хеши до/после.

## Сбор данных: живой анализ vs образ

Два подхода и их особенности на Apple Silicon:

- **Живой анализ** — запуск инструментов на работающей системе. Плюс: ключи доступны,
  видна память. Минус: система меняется, часть данных затирается.
- **Образ диска** — копия носителя. Плюс: неизменность. Минус: нужен ключ шифрования;
  на Apple Silicon внешний сбор требует снижения boot-политик.

Порядок (volatility): сначала наименее стабильные данные (память, соединения), затем
диск, затем логи. Хешируй каждый шаг.
## Unified log и трассировка на Apple Silicon

Системный журнал macOS (`unified log`) — главный источник событий на современном Mac, и
на Apple Silicon он особенно важен, потому что многие традиционные артефакты (например,
старые `.plist`-логи) ушли. Читать его нужно через `log`:

```
$ log show --last 2h --predicate 'process == "sshd"' | head
$ log show --start "2026-01-14 03:00:00" --end "2026-01-14 04:00:00" > window.log
$ log collect --output case.logarchive --last 1d
```

`log collect` создаёт `.logarchive`, который можно анализировать офлайн. Обрати внимание:
журнал хранится ограниченное время и сжимается, поэтому для инцидента его нужно выгружать
**сразу**. На arm64 события трансляции Rosetta и работы SEP тоже попадают сюда — по ним
видно, что запускалось и когда.

## Сбор памяти: инструменты и ограничения arm64

Дамп памяти на Apple Silicon снимают только с живой системы и только при ослабленном SIP.
Инструменты должны поддерживать arm64 — Intel-бинарники через Rosetta не смогут читать
физическую память. Что важно помнить:

- порядок структур ядра (KASLR, `kernel_task`) отличается от Intel;
- плагины Volatility для macOS часто завязаны на x86 — проверяй совместимость;
- ключи FileVault и session keys живут в памяти до выключения — дамп нужно снять раньше;
- на M-серии адресное пространство единое, поэтому «градация» CPU/GPU-памяти иная.

Если собрать память нельзя, максимум извлекают из `logarchive`, APFS-снапшотов и
пользовательских артефактов — но ключи из SEP это не даст.
