## Вопрос, с которого всё начинается

Дан образ `disk.img` со старого Mac (или внешнего HFS+-диска). Внутри — файл `secret.txt`. Открываешь его, а там безобидная строка «nothing to see here». Но задание утверждает, что секрет именно в этом файле. Куда он мог деться?

HFS+ (HFS Extended) — файловая система macOS до появления APFS. У неё есть особенность, которую нужно знать, иначе половина содержимого останется невидимой. Разберём образ и найдём секрет.

## Наш пример: образ `disk.img`

Первым делом находим **volume header** — главную структуру HFS+. Она лежит не в самом начале, а со смещением 1024 байта (первые 1024 — загрузочный блок):

```bash
$ xxd -s 1024 -l 2 disk.img
00000400: 482b                                      H+
```

Магия `H+` подтверждает HFS+. Читаем параметры:

```bash
$ fsstat -o 63 disk.img | head -8
File System Type: HFS+
Block Size: 4096
```

`Block Size` — размер блока. Смещение раздела (`-o 63`) берётся из карты разделов.

## Шаг 1: листаем файлы

Смотрим содержимое и находим наш файл:

```bash
$ fls -o 63 -r disk.img | grep -i secret
r/r 23: secret.txt
```

Номер `23` — это **CNID** (Catalog Node ID), аналог inode в других ФС. Файл обычный, не удалённый. Читаем его данные:

```bash
$ icat -o 63 disk.img 23 > data.bin
$ strings data.bin
nothing to see here
```

Вот и «пустышка». Но подожди — в HFS+ у файла есть не один поток данных, а **два**. Понимание этого и есть ключ к задаче.

## Шаг 2: понимаем про data fork и resource fork

В классической Mac OS файл состоял из двух частей:

- **data fork** — основное содержимое (то, что мы прочитали);
- **resource fork** — отдельный поток: иконки, метаданные приложений, а иногда и **скрытые данные**.

В HFS+ resource fork превратился в **расширенный атрибут** (xattr) с именем `com.apple.ResourceFork`, но привычка приложений хранить там данные осталась. Классическая ловушка: смотришь только data fork — видишь пустышку, а секрет лежит в resource fork.

## Шаг 3: видим потоки

Чтобы увидеть не только файлы, но и их потоки, `fls` запускают с ключом `-p`:

```bash
$ fls -o 63 -r -p disk.img | grep '23'
r/r 23: secret.txt
r/r 23: secret.txt (com.apple.ResourceFork)
```

Теперь видно, что у файла `23` есть поток `com.apple.ResourceFork`. Читаем его, указав имя потока после двоеточия:

```bash
$ icat -o 63 disk.img '23:com.apple.ResourceFork' > rsrc.bin
$ strings rsrc.bin
flag{hfs_resource_fork}
```

Флаг найден. Он всё время был в файле — просто в другом потоке.

## Шаг 4: как устроены метаданные

Полезно понимать, откуда это берётся. Почти вся структура HFS+ — это **B-деревья** (сбалансированные деревья поиска). Их четыре, и каждое отвечает за своё:

| B-дерево | Назначение |
|----------|-----------|
| Catalog | иерархия файлов/каталогов, имена, CNID |
| Extents Overflow | дополнительные extents для больших файлов |
| Attributes | расширенные атрибуты, включая resource fork |
| Allocation | битовая карта занятости блоков |

**Catalog** хранит записи двух видов: `recordType=1` для каталога и `recordType=2` для файла. Запись файла содержит CNID, таймстампы, права и **два дескриптора fork** — по одному на data и resource. Именно второй дескриптор и указывает на данные resource fork. Понимая формат узла B-дерева один раз, ты читаешь все четыре дерева.

## Шаг 5: время и сжатие — две ловушки

Ещё две вещи, о которых легко споткнуться.

**Время.** HFS+ считает время от 1904 года, а не от Unix-эпохи 1970-го. Чтобы перевести в привычное, вычитают константу `2082844800` секунд. Без этой поправки все даты уедут на 66 лет.

**Сжатие (decmpfs).** macOS умеет прозрачно сжимать файлы. Тогда data fork содержит не сами данные, а **заголовок сжатия** с сигнатурой `cmpf` и сжатый поток:

```bash
$ xxd -l 16 <(icat -o 63 disk.img 23)
```

Если видишь `cmpf` — читать data fork «как данные» бессмысленно, нужно распаковывать (на macOS — `afscexpand`/`ditto`). Признак — наличие атрибута `com.apple.decmpfs`.

## Полный разбор: от volume header до файла

Прогоним разбор образа `disk.img` целиком.

1. **Определяем ФС.** `fsstat -f hfs disk.img` показывает тип и объём.
2. **Читаем volume header.** `dd if=disk.img bs=512 skip=2 count=1 | xxd` — сигнатура `H+` (или `HX`), размер блока, число файлов.
3. **Листаем каталог.** `fls -r -f hfs disk.img` — рекурсивный список; каждый файл = inode (**CNID**).
4. **Различаем форки.** У файла есть **data fork** (данные) и **resource fork** (иконки/ресурсы). `icat` достаёт нужный.
5. **Проверяем журнал.** HFS+ ведёт **journal**; незавершённые операции можно «доиграть» и увидеть, что делалось до сбоя.

Каждый шаг отвечает на конкретный вопрос: что за ФС → как устроена → что внутри → какие у файла части → что было до выключения.

## Шпаргалка структур HFS+

| Структура | Смещение | Что даёт |
|-----------|----------|----------|
| Volume Header | сектор 2 | сигнатура, размер блока, CNID |
| Catalog File | из header | дерево «папки/файлы» (B-tree) |
| Extents Overflow | из header | продолжение фрагментированных файлов |
| Allocation File | из header | карта занятых блоков |
| Journal | из header | незавершённые операции |

Два «специфичных для Apple» момента: **время** считается от 1904 года (не 1970), а файлы умеют быть **сжатыми** (прозрачное сжатие) — при извлечении `icat` может выдать «сжатый» контейнер, который надо распаковать отдельно.

## Если не сработало

- **`fsstat` не распознаёт.** Возможно, это APFS (новая ФС Apple) — нужен другой инструмент (`apfs-fuse`).
- **Файл читается мусором.** Скорее всего, он сжат прозрачно — проверьте атрибуты и распакуйте.
- **Не находит удалённые файлы.** У HFS+ нет простого журнала удалений, как `$UsnJrnl`; ищите в нераспределённом пространстве карвингом (`photorec`).
- **Время «уехало» на 66 лет.** Забыли про эпоху 1904-го — добавьте смещение.
- **Resource fork потерялся.** Копирование через FAT-совместимые инструменты теряет форки.

## Что мы теперь знаем

- Volume header HFS+ лежит со смещением 1024 и начинается с магии `H+`.
- У файла HFS+ два потока: **data fork** (содержимое) и **resource fork** (метаданные, иногда скрытые данные).
- В HFS+ resource fork хранится как xattr `com.apple.ResourceFork`.
- `fls -p` показывает потоки; `icat <CNID>:<attr>` читает нужный поток.
- Метаданные HFS+ — это B-деревья (Catalog, Extents Overflow, Attributes, Allocation).
- Время HFS+ — от 1904 года; файлы могут быть сжаты (decmpfs, сигнатура `cmpf`).
