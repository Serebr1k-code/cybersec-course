## Вопрос, с которого всё начинается

В CTF-задаче дан образ `disk.img` — Linux-раздел с ext4. На нём лежал файл
`flag.txt`, который кто-то удалил перед снятием образа. `ls` его не показывает. Как
его вернуть?

Мы уже знаем, что удалённый файл обычно ещё жив в метаданных. На NTFS мы читали MFT.
У Linux своя система: **inode** и **журнал ext4**. В этом уроке мы разберём один
образ и достанем флаг из удалённого файла, заглянув при необходимости в журнал.

## Наш пример: disk.img с удалённым flag.txt

Определяем раздел:

```bash
$ mmls disk.img
01: -----  0000002048-0000204799  0000204800  Linux (0x83)
```

Раздел начинается с сектора 2048 — `OFF=2048`. Смотрим параметры файловой системы:

```bash
$ dumpe2fs -h disk.img 2>/dev/null | grep -iE 'Filesystem state|Block size|Inode size|Journal inode'
Filesystem state: clean
Block size:       4096
Inode size:       256
Journal inode:    8
```

Это уже важные факты: размер блока 4096 байт (по нему считаем адреса), размер inode
256 байт, а журнал — это служебный inode номер 8. Состояние `clean` значит, что
журнал был корректно закрыт — данные в нём не «висят» незавершёнными, но история
могла сохраниться.

## Шаг 1: что такое inode

В ext4 каждый файл описывается **inode** — структурой фиксированного размера. Это
аналог записи MFT в NTFS. Inode хранит метаданные: права, владельца, размер, три
времени (доступ/изменение/создание) и **где лежат данные**.

Вот ключевые поля inode:

| Поле | Смысл |
|------|-------|
| `i_mode` | тип файла + права |
| `i_size` | размер |
| `i_atime` | время последнего доступа |
| `i_mtime` | время изменения |
| `i_dtime` | **время удаления** |
| `i_block` | указатель на данные (extent-дерево) |

Поле `i_dtime` — золото: если оно ненулевое, файл удалён, и там стоит точное время.
Смотрим все удалённые файлы:

```bash
$ fls -r -d -o 2048 disk.img
r/r * 17: flag.txt
```

Inode `17`, удалён. Пробуем достать содержимое напрямую:

```bash
$ icat -o 2048 disk.img 17 > out.bin
$ file out.bin; strings out.bin | grep -i flag
out.bin: ASCII text
CTF{ext4_inode_still_here}
```

Сработало с первой попытки — потому что при удалении ext4 не стирает данные, а лишь
помечает inode свободным в битмапе. Блоки с содержимым остаются, пока их не
переиспользует другой файл.

## Шаг 2: как inode находит данные — extent-дерево

Раньше (в ext2/ext3) inode хранил 12 прямых указателей на блоки плюс косвенные. В
ext4 это заменили на **extent-дерево**: список **экстентов** — непрерывных диапазонов
блоков. Один экстент описывает «начиная с блока X идут N блоков», что гораздо
компактнее.

Смотрим inode через `debugfs` — инструмент для разбора ext4 без монтирования:

```bash
$ debugfs -R "stat <17>" disk.img 2>/dev/null
Inode: 17   Type: regular    Mode:  0644
Links: 0    Blockcount: 8
Inode size: 256
EXTENTS:
(0): 12345-12352
```

`Links: 0` — счётчик ссылок равен нулю, файл удалён. `EXTENTS: (0): 12345-12352`
означает, что данные занимают блоки с 12345 по 12352. Зная размер блока (4096),
можно прочитать их `dd` вручную, если `icat` почему-то не сработал.

## Шаг 3: журнал JBD2 — где живут «прошлые» метаданные

ext4 ведёт журнал через **JBD2** (Journaling Block Device 2). Это механизм
**write-ahead**: прежде чем изменить структуру на диске, система записывает в
журнал «что она собирается сделать». Если питание пропадёт — журнал проигрывается
заново, и ФС остаётся целой.

Для форензика журнал ценен тем, что в нём могут лежать **старые метаданные**:
записи о inode и каталогах, которые уже изменились. Это имена и размеры удалённых
файлов, которых нет в текущем состоянии.

Читаем журнал без монтирования:

```bash
$ debugfs -R "logdump -a" disk.img 2>/dev/null | head
JBD2: journal starts at block ...
   Inode 17 block 12345: deleted
```

А можно выгрузить журнал целиком как файл и искать в нём строки:

```bash
$ debugfs -R "dump <8> journal.bin" disk.img 2>/dev/null
$ strings journal.bin | grep -i flag
flag.txt
```

`<8>` — это inode журнала. `dump` копирует его содержимое в `journal.bin`. Sleuthkit
умеет то же самое утилитами `jls` (список транзакций) и `jcat` (содержимое блока):

```bash
$ jls -o 2048 disk.img | head
$ jcat -o 2048 disk.img 123 | strings | grep -i flag
```

## Шаг 4: если inode уже переиспользован

Хуже, когда номер inode `17` занял новый файл. Тогда `icat` вернёт чужие данные.
Спасает **carving** — поиск по свободным блокам. Выгружаем только нераспределённые
(unallocated) блоки и ищем в них:

```bash
$ blkls -o 2048 disk.img > unalloc.bin
$ strings -n 6 unalloc.bin | grep -iE 'CTF\{|flag\{'
CTF{ext4_inode_still_here}
```

Для автоматизации есть `extundelete` и `ext4magic`, которые сами проигрывают журнал:

```bash
$ cp disk.img work.img          # работаем на копии!
$ extundelete work.img --restore-all --output-dir recovered/
$ ext4magic work.img -M -d recovered/    # -M = восстановить удалённые
$ ext4magic work.img -j recovered/       # -j = через журнал
```

**Критично:** эти утилиты требуют, чтобы ФС была **не смонтирована**. Иначе ядро
проиграет журнал, перезапишет inode и данные — и улики исчезнут.

## Шаг 5: slack space и unallocated

Даже когда файл восстановить не удаётся, данные могут остаться в двух местах:

- **slack space** — «хвост» последнего блока файла, куда не поместился файл. Там
  могут лежать остатки предыдущего файла, занимавшего тот же блок.
- **unallocated** — свободные блоки: туда попадают удалённые данные и фрагменты
  каталогов.

```bash
$ blkls -o 2048 disk.img > unalloc.bin
$ binwalk unalloc.bin
$ tsk_recover -o 2048 -e disk.img rec/     # извлечь всё, включая удалённое
$ grep -rai 'CTF{' rec/
```

## Что мы теперь знаем

- ext4 описывает файлы через **inode**; поле `i_dtime` — время удаления.
- Удаление лишь освобождает inode — блоки с данными остаются, пока не переиспользованы.
- `fls -d` находит удалённые, `icat` вынимает содержимое, `debugfs` показывает inode.
- **JBD2** — журнал write-ahead; в нём сохраняются прошлые метаданные и имена.
- Если inode переиспользован, спасает **carving** по свободным блокам (`blkls`).

## На что смотреть дальше

- **Не монтируйте образ read-write** — ядро переиграет журнал и затрёт удалённое.
- **`extundelete`/`ext4magic` — только на несмонтированной ФС**, иначе результат
  непредсказуем и разрушителен.
- **Помните про `-o`**: у sleuthkit он в секторах, у `mount offset=` — в байтах.
- **Обнулённое extent-дерево ≠ потерянные данные** — блоки могут лежать в unallocated.
- **Проверяйте `s_feature_incompat` на EXTENTS (0x40)**: если его нет, это ext3 с
  косвенными блоками, и разбор другой.

## Куда дальше

Мы разобрали ext4 — самую частую Linux-ФС. Дальше посмотрим на современные
copy-on-write системы — Btrfs, ZFS и XFS: там удалённые данные живут ещё дольше, а
снапшоты хранят целые предыдущие состояния. А пока запомни: **`i_dtime` — это
прямое доказательство удаления, а журнал хранит то, чего уже нет в inode**.

## Где пригодится

- **CTF:** образы Linux-дисков, удалённые файлы, журнальные артефакты.
- **Data recovery:** восстановление удалённых файлов из ext4.
- **Incident Response:** анализ Linux-хостов после компрометации.
- **Судебная экспертиза:** доказательство удаления по `i_dtime` и журналу.
- **Разработка ФС-инструментов:** понимание layout ext4.
