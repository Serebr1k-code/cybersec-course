## Вопрос, с которого всё начинается

На macOS системные библиотеки лежат не отдельными файлами, а в одном большом
**dyld shared cache**. Это важно и для анализа памяти, и для реверса. Разберём.

## Наш пример: dyld-кэш

## Шаг 1: что это

`dyld` — динамический загрузчик macOS. Чтобы ускорить запуск, все системные
библиотеки объединены в единый файл — shared cache:

```
/System/Volumes/Preboot/Cryptexes/OS/System/Library/dyld/dyld_shared_cache_arm64e
```

Отдельных `.dylib` на диске может не быть — они внутри кэша.

## Шаг 2: извлечение

```
$ dyld-shared-cache-extractor dyld_shared_cache_arm64e ./out
```

Или `dyldex`. После извлечения появляются обычные `.dylib`, пригодные для анализа.

## Шаг 3: зачем это форензике

- **анализ памяти** — адреса библиотек в дампе указывают в кэш;
- **реверс** — нужно получить «чистые» библиотеки;
- **сравнение** — подменённая библиотека в кэше = компромисс;
- **символы** — кэш хранит отладочную информацию.

## Шаг 4: в дампе памяти

В памяти библиотеки замаплены из кэша по определённым адресам. По смещениям можно
понять, какая библиотека и какая функция выполнялась:

```
$ strings mac.raw | grep -i 'libsystem' | head
```

## Шаг 5: практика

- извлекай кэш для целевой версии ОС;
- сопоставляй адреса дампа с кэшем;
- проверяй целостность (подпись).

## Что мы теперь знаем

- dyld shared cache — объединённый файл системных библиотек macOS.
- Отдельных dylib может не быть.
- Извлекается dyld-shared-cache-extractor/dyldex.
- Нужен для анализа памяти и реверса.
- Подмена кэша = компромисс.

## Если не сработало

- Кэш не извлекается? Проверь версию инструмента.
- Нужна другая ОС? Бери кэш этой версии.
- Символы отсутствуют? Используй отдельные symbol-файлы.

## Как устроен dyld shared cache

`dyld` — динамический загрузчик macOS. Чтобы приложения стартовали быстро,
системные библиотеки не читаются по одной с диска, а собраны в один большой
файл — **shared cache**. Он лежит, например:

```
/System/Volumes/Preboot/Cryptexes/OS/System/Library/dyld/dyld_shared_cache_arm64e
```

Внутри — сотни `.dylib`, отображённых по фиксированным адресам. У кэша есть
**UUID**, привязанный к версии ОС: дамп памяти одной версии не совместим с
кэшем другой. Поэтому для анализа нужно брать кэш **точно той** сборки.

## Работа на примере: извлекаем библиотеку

Извлекаем отдельные библиотеки из кэша:

```
$ dyld-shared-cache-extractor dyld_shared_cache_arm64e ./out
$ ls out/usr/lib | head
libSystem.B.dylib
libc++.1.dylib
...
```

Альтернатива — `dyldex` (умеет искать и извлекать по имени):

```
$ dyldex -e libSystem.B.dylib dyld_shared_cache_arm64e
```

После извлечения библиотеки — обычные Mach-O файлы, их можно грузить в
IDA/Ghidra, смотреть экспорты и строки.

## Связь с дампом памяти

В дампе памяти библиотеки отображены из кэша по адресам, которые зависят от
**slide** (случайного смещения ASLR). Чтобы сопоставить, нужно:

1. Узнать slide из дампа (адрес известного символа минус его адрес в кэше).
2. Применить slide к адресам кэша.
3. Получить «карту»: какой адрес какой библиотеке принадлежит.

Инструменты (Volatility3 `mac`-плагины, `vmmap`-подобные) часто делают это
автоматически, подгружая нужный кэш.

## Проверка целостности и подмены

Подмена библиотеки в кэше — признак компромисса. Проверить можно:

- **сверить UUID/размер** кэша с эталонным для версии ОС;
- **проверить подписи** извлечённых библиотек (`codesign -v`);
- **сравнить** подозрительную библиотеку с оригиналом из чистой системы.

```
$ codesign -dv --verbose=2 out/usr/lib/libSystem.B.dylib 2>&1 | head
```

Если подпись недействительна — библиотеку меняли.

## Инструменты

| Инструмент | Назначение |
| --- | --- |
| dyld-shared-cache-extractor | распаковка кэша в dylib |
| dyldex | поиск/извлечение по имени |
| jtool2 | анализ Mach-O и кэша |
| codesign | проверка подписей |
| Volatility3 | сопоставление с дампом памяти |

## Ограничения

- **Версия обязательна** — кэш от другой сборки не подойдёт.
- **Символы могут быть вырезаны** — для «чистых» символов нужны отдельные
  symbol-файлы.
- **Кэш большой** — распаковка занимает десятки гигабайт.
- **Подписи в кэше** — проверяются сложнее, чем у отдельных файлов.

## Практический чек-лист

1. Определить версию ОС и взять соответствующий кэш.
2. Извлечь нужные библиотеки.
3. Взять slide из дампа и сопоставить адреса.
4. Проверить подписи и сверить с эталоном.
5. Зафиксировать UUID кэша в отчёте.

## Что такое slide (ASLR) на примере

macOS случайно сдвигает адреса загрузки (ASLR). Поэтому одна и та же
библиотека в памяти разных запусков лежит по разным адресам. Разница между
адресом «на диске» (в кэше) и адресом «в памяти» — это **slide**.

Найти slide можно так: берём адрес известной функции из дампа, вычитаем её
адрес в кэше — получаем смещение. Применяя его ко всем адресам кэша, строим
карту памяти:

```
slide = addr_in_dump(libSystem_open) - addr_in_cache(libSystem_open)
addr_cache(x) + slide = addr_dump(x)
```

Без учёта slide адреса в дампе «не сойдутся» с кэшем, и анализ пойдёт
неверно.

## Поиск символов и строк в кэше

Кэш содержит и код, и данные. Для быстрой разведки ищем строки:

```
$ strings dyld_shared_cache_arm64e | grep -i 'ssh\|backdoor' | head
```

А для символов — используем `nm`/`jtool2` после извлечения библиотеки:

```
$ nm -gU out/usr/lib/libSystem.B.dylib | grep open | head
```

Так находится, какие функции доступны и по каким смещениям.

## Сравнение с Linux/Windows аналогами

- **Linux** — отдельные `.so` лежат на диске; кэша как единого файла нет
  (есть `ld.so.cache`, но это список путей, не код).
- **Windows** — DLL на диске + `ntdll` в памяти; есть кэш символов
  (symbol server), но не объединённый код.
- **macOS** — уникальна именно объединённым `dyld_shared_cache`.

Поэтому приём с извлечением из кэша специфичен для macOS.

## Сценарии расследования

- **Анализ памяти Mac** — сопоставить адреса дампа с библиотеками.
- **Поиск подменённого кода** — сверить библиотеку из кэша с эталоном.
- **Реверс системной функции** — получить «чистый» код без дампа.
- **Атрибуция малвари** — какие системные библиотеки использует образец.

## Если сработало / если нет

- **Извлёк библиотеку** — проверь подпись и сравни с эталоном.
- **Адреса не сходятся** — проверь версию кэша и правильность slide.
- **Символов нет** — используй отдельные symbol-файлы или переходи к анализу
  машинного кода.
- **Кэш не извлекается** — обнови инструмент; старые версии не понимают
  новые форматы.

## Практический сценарий: подмена библиотеки

Подмена системной библиотеки — серьёзный признак компромисса macOS. Как
проверить:

1. **Сверить UUID/размер кэша** с эталоном для версии ОС.
2. **Извлечь подозрительную библиотеку** и проверить подпись:

```
$ codesign -v out/usr/lib/libSystem.B.dylib
```

3. **Сравнить с оригиналом** из чистой системы (хэш, размер, экспорты).
4. **Проверить дамп памяти** — какие библиотеки реально загружены.

Если подпись недействительна или содержимое отличается — библиотеку меняли.
Это уже не «подозрение», а подтверждённая модификация.

## Кэш и обновления ОС

dyld-кэш пересобирается при обновлении системы: меняется UUID, набор
библиотек, адреса. Для форензики это важно:

- **снимок памяти** нужно сопоставлять с кэшем **той же** сборки;
- **после обновления** старый кэш может остаться на диске (например, в
  `Preboot`) — это тоже артефакт;
- **разные кэши** для разных архитектур (`arm64e`, `x86_64`).

Проверяй, какая сборка была на момент снятия дампа, иначе сопоставление
адресов даст мусор.

## Если сработало / если нет

- **Подпись невалидна** — фиксируй подмену, ищи, кто и когда.
- **Версия не совпадает** — возьми правильный кэш, не делай вывод по
  неподходящему.
- **Кэш огромный, места нет** — извлекай только нужные библиотеки.

## Извлечение символов и отладка

Для глубокого анализа библиотек нужны символы. Если в кэше их нет, тяни
отдельные symbol-файлы с серверов Apple. Затем связывай адреса:

```
$ nm -gU out/usr/lib/libSystem.B.dylib | grep -i pthread | head
```

Так находятся точки входа и имена функций. Для отладки живого процесса
можно использовать lldb, который сам подгружает кэш и разрешает символы —
но это уже про анализ работающей системы, а не форензику.

## Итог: кэш как «фундамент» памяти macOS

dyld shared cache — не экзотика, а фундамент, на котором стоит вся память
macOS. Без него нельзя корректно сопоставить адреса дампа с библиотеками,
проверить подмену кода или реверсить системные функции. Правило простое:
**возьми кэш той же сборки, что и дамп**, вычти slide, сопоставь адреса.
Тогда хаос адресов превращается в понятную карту кода.

## Итог: сопоставление, а не угадывание

Работа с dyld-кэшем — это всегда **сопоставление**: адрес в дампе ↔ адрес в
кэше, библиотека ↔ её подпись, версия ↔ UUID. Как только соответствие
установлено, дальше всё идёт по знакомым правилам анализа Mach-O. Ошибка
здесь — взять кэш не той сборки; тогда ни один адрес не сойдётся. Поэтому
первый шаг всегда один: точно определить версию ОС и взять её кэш.

## Зачем нужен UUID кэша

UUID — «отпечаток» конкретной сборки кэша. Он позволяет точно сказать, к
какой версии ОС относится дамп: если UUID дампа не совпадает с UUID кэша,
сопоставление адресов бессмысленно. Поэтому в отчёте всегда фиксируй UUID и
версию ОС — это делает анализ воспроизводимым для коллег.

## Коротко

Определи версию ОС, возьми кэш той же сборки, извлеки библиотеки
инструментом, вычисли slide из дампа и сопоставь адреса. Проверь подписи и
зафиксируй UUID. Этого достаточно, чтобы превратить сырой дамп macOS в
понятную карту кода.
