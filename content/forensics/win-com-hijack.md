## Вопрос, с которого всё начинается

Малварь закрепляется в системе, но **не создаёт служб и не пишет в `Run`**. Вместо этого
она «перепривязывает» уже существующий компонент Windows так, что при запуске легитимной
программы загружается её код. Техника называется **COM-хайджек**.

Разберём сквозной пример: найдём в реестре подменённый COM-объект.

## Что такое COM и CLSID

**COM (Component Object Model)** — механизм, по которому программы Windows вызывают
компоненты друг друга. Каждый компонент (класс) имеет уникальный идентификатор —
**CLSID** (GUID вида `{0002DF01-0000-0000-C000-000000000046}`). Windows находит код
компонента по CLSID в реестре.

Ключевая деталь: **реестр ищет CLSID в порядке приоритета**, и ветвь **HKCU** (пользователя)
имеет приоритет над **HKLM** (машины). Это и есть основа хайджека:

```
HKCU\Software\Classes\CLSID\{<CLSID>}\InprocServer32
HKLM\SOFTWARE\Classes\CLSID\{<CLSID>}\InprocServer32
```

Если в HKCU есть запись для CLSID, а в HKLM — легитимная, то Windows загрузит **ту, что в
HKCU**, то есть код атакующего.

## Наш пример: подменённый InprocServer32

Смотрим подозрительный CLSID:

```
$ reg query "HKCU\Software\Classes\CLSID\{0002DF01-0000-0000-C000-000000000046}\InprocServer32"
    (Default)    REG_SZ    C:\Users\Public\comms.dll
```

В HKLM тот же CLSID указывает на легитимный файл в `System32`. Значит, в HKCU произошла
**подмена**: при обращении к этому компоненту загрузится `C:\Users\Public\comms.dll`.

Проверить, какой именно файл должен был грузиться, можно, сравнив две ветви:

```
$ reg query "HKLM\SOFTWARE\Classes\CLSID\{0002DF01-0000-0000-C000-000000000046}\InprocServer32"
    (Default)    REG_SZ    C:\Windows\System32\legit.dll
```

Расхождение HKCU vs HKLM — **прямая улика** COM-хайджека.

## Варианты техники

- **InprocServer32** — подмена DLL, которая грузится в процесс.
- **LocalServer32** — подмена отдельного EXE-сервера.
- **TreatAs** — перенаправление одного CLSID на другой (косвенная подмена).
- **ScriptletURL** — запуск скрипта вместо компонента.
- **CLSID в HKCU** — используется, когда атакующий не имеет прав администратора: правка
  пользовательской ветви не требует повышения привилегий.

Особенно коварен **TreatAs**: он не содержит пути к коду, а указывает на **другой CLSID**.
Поэтому наивный поиск «путь в HKCU» его пропустит — нужно проверять и значение `TreatAs`.

## Как это выглядит в событиях

Sysmon пишет правки реестра (тип 12/13). Для COM-хайджека характерна запись в ветвь
`Software\Classes\CLSID`:

```
<EventID>13</EventID>
<Image>C:\\Users\\jdoe\\appdata\\local\\temp\\x.exe</Image>
<TargetObject>HKCU\\Software\\Classes\\CLSID\\{0002DF01-...}\\InprocServer32\\(Default)</TargetObject>
<Details>C:\\Users\\Public\\comms.dll</Details>
```

Плюс загрузка DLL из нестандартного пути видна в событии **7** (ImageLoad):

```
<EventID>7</EventID>
<ImageLoaded>C:\\Users\\Public\\comms.dll</ImageLoaded>
```

Комбинация 13 (правка CLSID) + 7 (загрузка DLL из Public) — сильный признак.

## Частые ошибки

- **Проверять только HKLM.** Хайджек часто живёт в **HKCU**, который приоритетнее.
- **Игнорировать TreatAs.** Косвенная подмена не содержит пути и легко пропускается.
- **Считать любую запись CLSID в HKCU вредоносной.** Легитимные программы тоже
  регистрируют свои компоненты — смотреть на **расхождение с HKLM** и на путь.
- **Не сопоставлять с ImageLoad.** Именно событие 7 подтверждает, что подменённый
  компонент **реально загружался**.

## Как CLSID-хайджек находят практически

Порядок работы аналитика по offline-hive строится вокруг сравнения ветвей. Начинаем с
hive пользователя (`NTUSER.DAT`) и ищем все ключи с `InprocServer32`:

```
$ rip.pl -r NTUSER.DAT -p clsid
CLSID: {0002DF01-...}  InprocServer32 = C:\Users\Public\comms.dll
```

RegRipper-плагин `clsid` перечисляет зарегистрированные компоненты. Далее для каждого
найденного CLSID проверяем, есть ли он **и** в машинной ветви, и сравниваем пути. Если в
HKLM путь ведёт в `System32`, а в HKCU — в `Public`/`Temp`, это подмена.

Для системных hive (`SOFTWARE`, `SYSTEM`) сравнение делают тем же способом, но с учётом
того, что HKCU всегда перекрывает HKLM. Поэтому даже «правильная» запись в HKLM не спасает:
важнее то, что лежит в HKCU конкретного пользователя.

## Анализ через события Sysmon

Две записи Sysmon почти всегда сопровождают COM-хайджек:

**Event 13 (RegistryEvent — SetValue):**

```
<EventID>13</EventID>
<Image>C:\\Users\\jdoe\\appdata\\local\\temp\\x.exe</Image>
<TargetObject>HKCU\\Software\\Classes\\CLSID\\{0002DF01-...}\\InprocServer32\\(Default)</TargetObject>
<Details>C:\\Users\\Public\\comms.dll</Details>
```

**Event 7 (ImageLoad):**

```
<EventID>7</EventID>
<Image>C:\\Windows\\explorer.exe</Image>
<ImageLoaded>C:\\Users\\Public\\comms.dll</ImageLoaded>
```

Первое показывает **кто и когда** прописал подмену, второе — **что она реально
сработала**: `explorer.exe` загрузил DLL из `Public`. Вместе это не оставляет сомнений.

## Почему это «тихая» персистентность

COM-хайджек популярен, потому что:

- не создаёт служб и не пишет в `Run` — не попадает в типовые проверки автозапуска;
- переиспользует **доверенный** процесс, поэтому код исполняется под легитимным бинарником;
- правка HKCU не требует прав администратора;
- срабатывает не сразу, а когда программа **обратится** к компоненту — то есть может
  «спать» до нужного триггера.

Именно поэтому COM-хайджек встречается в продвинутых APT-наборах и в CTF-задачах уровня
hard/expert.

## Частые ошибки

- **Сравнивать только значения по умолчанию.** Хайджек может быть в подразделе, например
  `InprocServer32\<threading model>`.
- **Забывать про `TreatAs`.** Он ссылается на другой CLSID и не содержит пути.
- **Пропускать `ScriptletURL`.** Запуск скрипта вместо компонента легко не заметить.
- **Не сопоставлять с ImageLoad.** Без события 7 нельзя доказать, что подмена сработала.

## Шпаргалка команд

```
# Найти зарегистрированные CLSID в hive пользователя
rip.pl -r NTUSER.DAT -p clsid
# Подозрительные пути DLL
strings NTUSER.DAT | grep -iE 'public|temp|appdata'
# Правки CLSID в Sysmon
evtx_dump.py Sysmon.evtx | grep -B2 -A6 'Classes\\\\CLSID'
# Проверить TreatAs
rip.pl -r NTUSER.DAT -p clsid | grep -i treatas
```

## Что это даёт в отчёте

В отчёте фиксируют: подменённый CLSID, путь к DLL/скрипту атакующего, момент внесения
правки и процесс-виновник, а также подтверждение срабатывания (загрузка DLL). COM-хайджек
часто сочетается с другими техниками — его находка нередко открывает целую цепочку.

## Практический сценарий: охота на подменённый компонент Windows

Разберём сценарий, где COM-хайджек проявляется через необычное поведение доверенной
программы. Пользователь замечает, что при открытии проводника появляется подозрительная
сетевая активность. Само по себе это не улика, но наводит на мысль о подмене компонента,
который проводник использует.

Строим гипотезу: зарегистрирован CLSID, указывающий на DLL атакующего в ветви пользователя.
Проверяем ветвь `HKCU\Software\Classes\CLSID` и сравниваем каждый CLSID с машинной ветвью
`HKLM\SOFTWARE\Classes\CLSID`. Любое расхождение путей — повод копнуть глубже.

Для найденного подозрительного CLSID читаем подключ `InprocServer32`. Если путь ведёт в
`AppData`, `Temp`, `Public` или `ProgramData`, а легитимная версия в HKLM указывает на
`System32`, это почти наверняка подмена. Проверяем также подраздел `TreatAs` — он мог
перенаправить компонент на другой CLSID без указания пути.

Дальше подтверждаем срабатывание. Sysmon событие 7 покажет, что доверенный процесс
(`explorer.exe`, `svchost.exe` и т.п.) загрузил DLL из нестандартного пути. Событие 13
покажет, какой процесс и когда внёс правку. Эти два события вместе доказывают, что подмена
не просто существует, но и **работала**.

Отдельно оцениваем **последствия**. DLL, загруженная в доверенный процесс, исполняется с
его правами. Если это `svchost.exe` с правами `SYSTEM` или `explorer.exe` пользователя —
масштаб разный. Поэтому в отчёте фиксируют, в какие процессы грузилась подмена и с какими
привилегиями.

Наконец, ищем **сообщников техники**. COM-хайджек часто идёт в связке с другими приёмами
закрепления: службами, задачами планировщика, WMI-подписками. Найдя один, проверяем
остальные ветви. Практический вывод: **COM-хайджек — это «тихое» закрепление через реестр**,
и его обнаружение требует систематического сравнения HKCU и HKLM, а не поиска по путям
исполняемых файлов. Навык пригодится и в CTF, и в реальном реагировании на инциденты.

## COM-хайджек в контексте других техник

Стоит понимать, где COM-хайджек стоит в общем наборе приёмов закрепления. Если службы и
`Run`-ключи — это «громкие» техники, которые легко заметить, то COM-хайджек относится к
«тихим»: он не создаёт новых точек автозапуска и потому невидим для типовых аудитов.
Именно поэтому его часто используют в паре с **DLL-хайджеком** (подменой пути поиска DLL)
и **COM-перехватом через `TreatAs`**.

Отдельная разновидность — хайджек через **`InprocServer32` без указания полного пути**.
Если в значении стоит только имя DLL, Windows ищет её по стандартному порядку каталогов, и
атакующему достаточно положить свою DLL в первый доступный каталог. Это роднит технику с
DLL-хайджеком и требует проверки не только значения, но и **пути поиска**.

## Итоговая методика проверки

Систематический порядок: снять `NTUSER.DAT` и `SOFTWARE`/`SYSTEM`, прогнать плагин `clsid`,
для каждого CLSID сравнить HKCU и HKLM, проверить `InprocServer32`, `LocalServer32`,
`TreatAs` и `ScriptletURL`, затем подтвердить срабатывание по Sysmon 7 и правку по Sysmon
13. Найденные пути классифицировать по «подозрительности» каталога (Temp/Public/AppData —
высокая). Результат свести в таблицу «CLSID → путь → процессы, куда грузилось → время».
Такой воспроизводимый чек-лист исключает пропуски и делает проверку персистентности
полной — от реестровых хайджеков до служб и планировщика.

## Что мы теперь знаем

- **COM** находит компонент по **CLSID**; порядок поиска отдаёт приоритет **HKCU**.
- **COM-хайджек** подменяет `InprocServer32`/`LocalServer32` в HKCU, реже через
  `TreatAs`/`ScriptletURL`.
- Признак — **расхождение HKCU и HKLM** для одного CLSID и путь в Temp/Public/Users.
- Техника не требует прав администратора (правка пользовательской ветви).
- Улики: Sysmon **13** (правка реестра) + **7** (загрузка DLL).

## Куда дальше

Мы закончили блок «хайджек загрузки». Дальше перейдём к **Linux-артефактам**: `/proc`,
история shell и точки автозапуска systemd. А пока главное запомни: **COM-хайджек — это
подмена CLSID в HKCU, ищи расхождение с HKLM и загрузку DLL из нестандартного пути**.

## Где пригодится

- **CTF Forensics:** задачи с hive-файлами и поиском закрепления.
- **DFIR:** обнаружение незаметной персистентности.
- **Threat Hunting:** охота на правки CLSID и загрузки из Public/Temp.
- **Работа:** реагирование на инциденты, анализ поведения.
