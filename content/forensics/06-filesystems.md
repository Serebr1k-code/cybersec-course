## Вопрос, с которого всё начинается

До сих пор мы работали с отдельными файлами. Но в реальных задачах часто дают
**образ диска** — файл, внутри которого лежит целый «жёсткий диск»: разделы,
файловая система, сотни файлов. Открыть такой файл в просмотрщике нельзя, а
монтировать его рискованно (можно изменить улику).

Как заглянуть внутрь образа и достать файл, ничего не испортив? В этом уроке
разберём один образ от начала до конца: найдём раздел, увидим файлы, прочитаем один.

## Наш пример: disk.img

```bash
$ file disk.img
disk.img: DOS/MBR boot sector; partition 1 : ID=0x83, start-CHS (0x0,32,33),
end-CHS (0x1,37,36), startsector 2048, 16384 sectors, ...
```

`file` сообщает важное: это **загрузочный сектор** с таблицей разделов, и первый
раздел начинается с сектора **2048**. Разберёмся, что это значит.

## Таблица разделов: карта диска

Диск разбит на **сектора** — минимальные блоки по 512 байт. Самый первый сектор
называется **MBR** (Master Boot Record) и содержит **таблицу разделов**: список
областей диска. Посмотреть её, не монтируя, можно инструментом `mmls` (из набора
Sleuth Kit):

```bash
$ mmls disk.img
DOS Partition Table
Offset Sector: 0
Units are in 512-byte sectors

      Slot      Start        End          Length       Description
000:  Meta      0000000000   0000000000   0000000001   Primary Table (#0)
001:  -------   0000000000   0000002047   0000002048   Unallocated
002:  000:000   0000002048   0000018431   0000016384   Linux (0x83)
```

Читаем построчно. Строка `Meta` — сама таблица разделов. `Unallocated` — первые
2048 секторов «пустые» (в них нет файлов). Строка `000:000` — реальный раздел:
тип `Linux (0x83)`, начинается с сектора **2048**, длина 16384 сектора.

Отсюда и берётся то самое число из `file`. Важно: `mmls` работает в **секторах**,
а большинство инструментов ждут **смещение в байтах**. Пересчёт: `2048 × 512 =
1048576` байт. Но `fls` умеет принимать смещение прямо в секторах через `-o`.

Строку `Unallocated` не игнорируй: это пространство, не занятое ни одним разделом.
Иногда именно там прячут данные, которых «не должно быть» — например, старый раздел,
удалённый из таблицы. Поэтому первое, что делают с образом, — смотрят, нет ли
чего-то вне описанных разделов.

## Файловая система: смотрим файлы без монтирования

Раздел начинается на секторе 2048. Внутри — файловая система **ext4** (стандартная
для Linux). Перечислим файлы, передав смещение разделу:

```bash
$ fls -o 2048 disk.img
d/d 11:	lost+found
r/r 13:	flag.txt
r/r * 14:	todo.txt
V/V 2049:	$OrphanFiles
```

Каждая строка — файл или каталог. Первый символ — тип (`d` — каталог, `r` — файл),
звёздочка `*` — **удалённый** файл (но его запись ещё жива), число — **inode**,
уникальный номер файла внутри файловой системы. То есть `flag.txt` — inode 13,
а `todo.txt` (inode 14) помечен как удалённый.

**Inode** — это «паспорт» файла: где на диске лежат его данные, права, размеры.
Имя файла хранится отдельно (в каталоге), а данные — по inode. Именно поэтому
удалённый файл часто можно достать: имя пропало, а данные и inode ещё не затёрты.
Практический вывод: запоминать нужно не имя файла, а его inode — по нему `icat`
достанет содержимое, даже если в каталоге записи уже нет.

## Читаем файл по inode

Достать содержимое можно через `icat` — «вывести файл по inode»:

```bash
$ icat -o 2048 disk.img 13
CTF{d3l3t3d_f1l3_r3c0v3ry}
```

И даже удалённый `todo.txt` (inode 14) читается, пока его блоки не перезаписаны:

```bash
$ icat -o 2048 disk.img 14
temporary note, then deleted
```

Вот и весь фокус «восстановления удалённых файлов»: файловая система помечает inode
как свободный, но данные физически остаются. Пока по этому месту не записали что-то
новое — файл восстановим.

## Разные файловые системы — разные детали

`fls`/`icat` понимают и другие системы, но у каждой свои особенности:

- **ext4** (Linux) — то, что мы видели: inode, каталоги-деревья, журнал.
- **FAT/exFAT** (флешки) — вместо inode таблица размещения файлов (FAT); удаление
  обнуляет первый символ имени, что даёт классический артефакт `?ile.txt`.
- **NTFS** (Windows) — файлы описаны в таблице **MFT**; есть `$UsnJrnl` — журнал
  всех файловых операций, и альтернативные потоки (ADS).

Полезные команды Sleuth Kit, которые пригодятся дальше:

| Команда | Что делает |
|---------|-----------|
| `mmls disk.img` | таблица разделов |
| `fls -o OFF disk.img` | список файлов (`-r` — рекурсивно) |
| `icat -o OFF disk.img INODE` | вывести файл по inode |
| `tsk_recover -o OFF disk.img out/` | выгрузить все файлы в каталог |
| `fsstat -o OFF disk.img` | сведения о файловой системе |

## Почему не монтировать

Соблазн прост: `mount -o loop disk.img /mnt` — и работать как с обычным диском. Но:

- монтирование **меняет** файловую систему (пишутся журналы, метки времени);
- для улики это уничтожение доказательства;
- при неизвестной ФС ядро может «починить» её и потерять удалённые файлы.

Поэтому в форензике образ читают инструментами (`fls`, `icat`), а если монтировать
всё же нужно — только **read-only**: `mount -o ro,loop`. Правило простое: **если
можно прочитать, не записывая — читай**.

## Рекурсивный обход и выгрузка всех файлов

`fls` без флага `-r` показывает только верхний уровень. Чтобы пройти по всем
каталогам, добавь `-r`; чтобы сразу выгрузить всё содержимое — `tsk_recover`:

```bash
$ fls -r -o 2048 disk.img
d/d 11:	lost+found
r/r 13:	flag.txt
r/r 12:	home/user/notes.txt
$ tsk_recover -o 2048 disk.img recovered/
Files Recovered: 3
```

`tsk_recover` сам обходит дерево и копирует файлы (включая удалённые) в каталог
`recovered/`. Это удобно, когда нужно быстро получить «всё, что было на диске»,
и уже потом искать глазами и `grep`.

Ещё полезно знать сведения о самой файловой системе:

```bash
$ fsstat -o 2048 disk.img | head
FILE SYSTEM INFORMATION
File System Type: Ext4
Block Size: 4096
```

`fsstat` показывает тип, размер блока, метку тома. Размер блока важен: именно на
него опирается расчёт смещений внутри ФС.

## Типичная ошибка: перепутать сектор и байт

Самая частая заминка новичка — смещения. `mmls` и `fls` по умолчанию считают в
**секторах**, а `dd` и многие другие инструменты — в **байтах**. Если передать
`-o 2048` туда, где ждут байты, получишь мусор. Запомни связку:

```
байты = сектор × 512
```

Но `fls`, `icat` и другие инструменты Sleuth Kit понимают `-o` именно как номер
сектора (при `-b 512` по умолчанию), поэтому `-o 2048` — это правильно. А для
`dd` то же место — `skip=1048576`. Проверять легко: если вывод «не распознан»,
скорее всего смещение неверное.

Файловая система — это не «папки», а структура на диске: разделы, блоки и inode.

## Что мы теперь знаем

- Образ диска = MBR + таблица разделов + файловые системы внутри.
- `mmls` показывает разделы в секторах; смещение в байтах = сектор × 512.
- `fls` перечисляет файлы (и удалённые — со звёздочкой), `icat` читает по inode.
- Данные удалённого файла живы, пока их блоки не перезаписаны.
- Монтировать образ нельзя; работаем `fls`/`icat`, при необходимости — `mount -o ro`.

## Сектор, кластер и блок: три разных размера

Новичок часто путает три единицы. **Сектор** — минимальная физическая единица диска, обычно 512 байт (у современных дисков — 4096). **Кластер** (в FAT/NTFS) и **блок** (в ext4) — минимальная единица, которой оперирует файловая система; обычно это 4096 байт, то есть 8 секторов. Файл всегда занимает целое число блоков, даже если он меньше — остаток называется «хвостом» и может содержать старые данные (это называют **slack space**, отдельный источник улик).

Зачем это знать: смещения в инструментах считаются по-разному. `mmls` и `fls` — в секторах, `dd` — в байтах, а `fsstat` показывает размер блока самой ФС. Поэтому при ручном разборе сначала узнай размер блока (`fsstat`), потом пересчитывай адреса. Ошибка в размерности — самая частая причина «мусора» на выходе.

## Временные метки и таймлайн

Каждый inode хранит несколько меток времени: **mtime** (изменение содержимого), **atime** (доступ), **ctime** (изменение метаданных, например прав), а в NTFS — ещё **MFT entry modified**. Их называют **MAC-временами**. Они и есть основа таймлайна: разложив все метки по порядку, видно, что происходило и когда.

Для построения таймлайна используют `fls -m` (создаёт **bodyfile** — текстовый список записей с метками) и `mactime`:

```
$ fls -m -o 2048 disk.img > bodyfile.txt
$ mactime -b bodyfile.txt -d 2026-03-01..2026-03-31
```

`mactime` сортирует события по времени и показывает, какие файлы создавались, менялись и удалялись в окне. Это превращает «просто список файлов» в историю — ключевой шаг любого расследования.

## Куда дальше

Мы научились находить разделы и читать отдельные файлы. Но что если раздел повреждён,
таблица разделов потеряна или нужно восстановить файл, у которого уже нет записи
в каталоге? В следующем уроке возьмём **сырой образ без файловой системы** и
потренируемся доставать данные carving-ом, а также разберём снятие корректного
образа. А пока запомни: **раздел — это смещение, файл — это inode**.

## Где пригодится

- **CTF:** задачи с образами дисков и восстановлением удалённых файлов.
- **Data recovery:** спасение данных с повреждённых носителей.
- **Incident Response:** анализ дисков скомпрометированных машин.
- **Криминалистика:** извлечение доказательств без изменения носителя.
- **Пентест:** поиск забытых файлов и конфигов на образах серверов.
