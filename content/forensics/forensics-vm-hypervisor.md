## Вопрос, с которого всё начинается

Атакующий работал с облачной **виртуальной машины**. У неё есть диск — но в облаке это не
«диск в шкафу», а сетевой том. Как снять его и что ещё доступно для расследования?

## Наш пример: подозрительный инстанс

Есть инстанс `i-0abc123` с диском `vol-9f8e`. Прежде чем что-то менять, снимаем **снимок**
диска — он не изменяет работающую ВМ.

```
$ aws ec2 create-snapshot --volume-id vol-9f8e --description "forensic-2026-03-10"
{
  "SnapshotId": "snap-0f1e2d",
  "State": "pending"
}
```

Снимок — это копия тома на момент времени. Дальше из него создают отдельный том и
монтируют на анализ-машину.

## Шаг 1: снять том из снимка

```
$ aws ec2 create-volume --snapshot-id snap-0f1e2d --availability-zone eu-west-1a
$ aws ec2 attach-volume --volume-id vol-new --instance-id i-analyst --device /dev/sdf
```

На анализ-машине монтируем **только для чтения** и считаем хеш — как с обычным диском.

## Шаг 2: консольные логи

У облачных ВМ есть **консольный вывод** (serial console) — то, что было бы на экране:

```
$ aws ec2 get-console-output --instance-id i-0abc123
[    3.14] systemd: Started Session 1 of user root.
Kernel panic - not syncing: ...
```

Он переживает перезагрузки и полезен, когда систему не запустить.

## Шаг 3: метаданные и user-data

У инстанса есть **метаданные** (роль, id, сеть) и **user-data** (скрипт начальной
настройки). user-data часто содержит секреты и команды:

```
$ aws ec2 describe-instance-attribute --instance-id i-0abc123 --attribute userData
IyEvYmluL2Jhc2gK...   (base64: #!/bin/bash ...)
```

Расшифровав base64, видим, что запускалось при старте.

## Шаг 4: где заканчиваются возможности

Ты **не** имеешь доступа к **гипервизору** — только к своей ВМ. Поэтому:

- снять «память» работающей ВМ напрямую нельзя (в отличие от локальной машины);
- нельзя увидеть, что делает провайдер на своём уровне;
- но есть **логи провайдера**: CloudTrail, VPC Flow Logs, GuardDuty.

Именно они показывают активность, которую не видно внутри ВМ.

## Ловушка: работающая ВМ меняется

Пока ты снимаешь снимок, ВМ продолжает работать. Поэтому:

- сначала фиксируй **время снятия** и состояние (кто вошёл, какие процессы);
- для «живой» картины используй логи и, если возможно, агент внутри ВМ;
- снимок — это состояние **на момент**, а не «сейчас».

## Что мы теперь знаем

- Снимок тома — безопасный способ снять диск облачной ВМ.
- Том из снимка монтируют только для чтения и хешируют.
- Консольные логи и user-data дают ценную информацию.
- Доступа к гипервизору нет — опираемся на логи провайдера.
- Снимок фиксирует момент времени, а ВМ продолжает меняться.

## Анатомия облачной ВМ: что вообще есть у инстанса

Инстанс в облаке — это набор сущностей, каждая из которых отдельный источник улик:

| Сущность | Что это | Форензик-ценность |
|----------|---------|-------------------|
| volume | сетевой диск (EBS и аналог) | содержимое ФС |
| snapshot | копия тома на момент | снятие без остановки ВМ |
| console output | serial console | сообщения загрузки, panic |
| user-data | скрипт при старте | команды и секреты |
| metadata | роль, id, сеть | привязка к IAM |
| security groups | правила сети | открытые порты |
| CloudTrail | API-события | кто и что делал с ВМ |
| VPC Flow Logs | метаданные трафика | сеть без пакетов |

Форензик облачной ВМ — это работа **не только** с диском, а с этим набором. Диск — центр,
но контекст даёт именно облачная обвязка.

## Практика: снять и смонтировать том

**1. Снимок** (не изменяет работающую ВМ):

```
$ aws ec2 create-snapshot --volume-id vol-9f8e \
    --description "forensic-2026-03-10" --tag-specifications \
    'ResourceType=snapshot,Tags=[{Key=case,Value=INC-2026-0310}]'
```

**2. Том из снимка** (в той же зоне доступности):

```
$ aws ec2 create-volume --snapshot-id snap-0f1e2d \
    --availability-zone eu-west-1a --volume-type gp3
$ aws ec2 attach-volume --volume-id vol-new --instance-id i-analyst --device /dev/sdf
```

**3. Монтирование только для чтения:**

```
$ sudo mount -o ro,noload,noexec /dev/nvme1n1p1 /mnt/evidence
$ sudo sha256sum /dev/nvme1n1 > /evidence/disk.sha256
```

`noload` — не проигрывать журнал ФС (сохраняет оригинал). Хеш всего тома — базовая улика.

## Что дают метаданные и user-data

```
$ TOKEN=$(curl -s -X PUT "http://169.254.169.254/latest/api/token" \
    -H "X-aws-ec2-metadata-token-ttl-seconds: 60")
$ curl -s -H "X-aws-ec2-metadata-token: $TOKEN" \
    http://169.254.169.254/latest/meta-data/iam/security-credentials/
ci-deploy
```

Метаданные показывают **роль** инстанса — какие права у ВМ в облаке. Если атакующий
дотянулся до `169.254.169.254` (SSRF), он мог украсть временные ключи этой роли. user-data
декодируется из base64:

```
$ aws ec2 describe-instance-attribute --instance-id i-0abc123 \
    --attribute userData --query 'UserData.Value' --output text | base64 -d
#!/bin/bash
export DB_PASS=Sup3rS3cret!
```

Секреты в user-data — частая находка.

## Облачные логи: то, чего не видно внутри ВМ

- **CloudTrail** — кто вызывал API (запуск инстанса, изменение группы, снятие снимка);
- **VPC Flow Logs** — IP/порты/объёмы трафика (без содержимого);
- **GuardDuty** — детекты (например, «криптомайнинг», «подозрительный DNS»);
- **Route 53 Resolver logs** — DNS-запросы из VPC.

```
$ aws cloudtrail lookup-events \
    --lookup-attributes AttributeKey=ResourceName,AttributeValue=i-0abc123
```

Именно здесь видно, что атакующий делал **с** инстансом через API, даже если внутрь
попасть нельзя.

## Ограничения

- **Нет доступа к гипервизору** — память работающей ВМ снять напрямую нельзя.
- **Снимок не мгновенный** — «момент времени» приблизителен, ВМ меняется во время снятия.
- **Шифрование тома** — без ключа KMS содержимое не прочесть.
- **Юрисдикция** — данные могут быть в другом регионе/стране; учитывай правовые границы.
- **Стоимость** — снимки и трафик платные; планируй объём.
- **Провайдерский уровень** — часть логов только у провайдера по запросу.

## Практический чеклист

1. Зафиксировать состояние ВМ (время, сессии) до любых действий.
2. `create-snapshot` — не изменяя работающую ВМ.
3. `create-volume` из снимка, `attach`, монтировать `ro,noload`.
4. `sha256sum` тома — базовая улика.
5. `get-console-output` — загрузка и ошибки.
6. `describe-instance-attribute userData` — секреты/команды.
7. Метаданные роли + CloudTrail + Flow Logs — облачный контекст.

## Сценарий: атака через SSRF на метаданные

Разберём типовой облачный инцидент. Веб-приложение на инстансе имеет SSRF.

**1. Атакующий дотягивается до метаданных:**

```
GET /fetch?url=http://169.254.169.254/latest/meta-data/iam/security-credentials/ci-deploy
```

**2. Крадёт временные ключи роли** — и получает права инстанса в облаке.

**3. Действует от имени роли.** CloudTrail фиксирует:

```
$ aws cloudtrail lookup-events --lookup-attributes AttributeKey=EventName,AttributeValue=RunInstances
RunInstances  assumed-role/ci-deploy/i-0abc123  2026-03-10T03:14Z
```

**4. Создаёт свой инстанс** для майнинга или эксфильтрации.

**5. Расследование.** Проверяем: с какого IP шёл SSRF (Flow Logs), какие ключи украдены
(метаданные роли), что делали этими ключами (CloudTrail), куда шёл трафик (Flow Logs +
DNS Resolver logs). Отзываем роль, сужаем права, включаем IMDSv2 (token-based) — который
блокирует простой SSRF.

Вывод: облачная ВМ — это ещё и **субъект IAM**, и утечка метаданных опаснее, чем кажется.

## Почему IMDSv2 важен

Старые метаданные (IMDSv1) отдаются по простому GET — уязвимы к SSRF. IMDSv2 требует
`PUT` с токеном:

```
$ TOKEN=$(curl -s -X PUT "http://169.254.169.254/latest/api/token" \
    -H "X-aws-ec2-metadata-token-ttl-seconds: 60")
```

Без токена ответ — `401`. В форензике проверяй, был ли включён IMDSv2 **на момент атаки**;
если нет — SSRF-утечка ключей более чем вероятна.

## Ограничения

- **Нет доступа к гипервизору** — память работающей ВМ напрямую не снять.
- **Снимок не мгновенный** — ВМ меняется во время снятия; момент приблизителен.
- **Шифрование тома** — без ключа KMS содержимое не прочесть.
- **Юрисдикция** — данные могут быть в другом регионе/стране.
- **Стоимость** — снимки и трафик платные.
- **Провайдерский уровень** — часть логов только у провайдера.

## Практический чеклист

1. Зафиксировать состояние ВМ до действий.
2. `create-snapshot` без остановки ВМ.
3. `create-volume` + `attach` + `mount -o ro,noload`.
4. `sha256sum` тома.
5. `get-console-output` и `describe-instance-attribute userData`.
6. Метаданные роли → проверить SSRF/IMDSv1.
7. CloudTrail + Flow Logs + DNS Resolver logs — облачный контекст.

## Сводка: что снимать в облаке

| Источник | Что даёт | Когда доступен |
|----------|----------|----------------|
| snapshot тома | содержимое ФС | пока том существует |
| console output | загрузка, panic | переживает перезагрузки |
| user-data | команды и секреты старта | пока инстанс есть |
| metadata роли | права в облаке | пока инстанс есть |
| CloudTrail | API-события | постоянно (если включён) |
| Flow Logs | сетевые метаданные | если настроены |

Порядок сбора — от самого хрупкого к самому стойкому: сначала то, что исчезнет с
инстансом, потом логи, которые живут дольше.

## Один вывод

Облачная ВМ — это диск, снимки, консоль, user-data, метаданные и логи провайдера.
Гипервизор недоступен, но снимок тома плюс CloudTrail и Flow Logs дают почти полную
картину. Начинай со снимка — он не изменяет работающую систему.
