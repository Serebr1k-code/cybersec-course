## Вопрос, с которого всё начинается

Ты подключился к расследуемому серверу. Первый вопрос — не «что случилось», а «кто
вообще здесь есть». Злоумышленник почти всегда заводит себе учётку или меняет права
существующей. Начнём с самого базового источника — списка пользователей.

## Наш пример: пользователь backdoor

Предположим, в системе найден пользователь `backdoor`. Нам надо понять, откуда он
взялся, что умеет и какие следы оставил.

## Шаг 1: список пользователей

Файл `/etc/passwd` хранит учётные записи. Формат — семь полей через двоеточие:

```
$ cat /etc/passwd | grep backdoor
backdoor:x:1002:1002::/home/backdoor:/bin/bash
```

Читаем: имя `backdoor`, пароль в отдельном файле (`x`), UID `1002`, GID `1002`,
комментарий пуст, домашний каталог `/home/backdoor`, оболочка `/bin/bash`.

UID ≥ 1000 обычно означает обычного пользователя. А вот UID `0` — это **root**.
Опасный признак: учётка с именем вроде `backdoor`, но с UID `0`.

## Шаг 2: пароли и хеши

Хеши паролей лежат в `/etc/shadow` (доступен только root):

```
$ sudo cat /etc/shadow | grep backdoor
backdoor:$6$abcd...:19500:0:99999:7:::
```

Поля: хеш, день последней смены пароля, минимальный/максимальный срок, срок
предупреждения. `$6$` — это SHA-512. Отсутствие пароля (`!` или `*`) означает, что
вход по паролю запрещён — но это не значит, что учётка не используется (по SSH-ключу
всё равно можно войти).

## Шаг 3: группы и привилегии

Права в Linux — это в первую очередь группы. Команда `id`:

```
$ id backdoor
uid=1002(backdoor) gid=1002(backdoor) groups=1002(backdoor),27(sudo)
```

Членство в группе `sudo` (или `wheel`) даёт право повышать права. Группа `docker` —
это фактически root: тот, кто может запускать контейнеры, может смонтировать хост.
Ищи такие «тихие» привилегированные группы.

## Шаг 4: правила sudoers

Смотрим, что именно разрешено:

```
$ sudo grep -rE 'backdoor|NOPASSWD' /etc/sudoers /etc/sudoers.d/
backdoor ALL=(ALL) NOPASSWD: ALL
```

`NOPASSWD: ALL` — злоумышленник может выполнить любую команду без пароля. Это
классический persistence-приём.

## Шаг 5: следы в логах

Проверим, когда учётка создавалась:

```
$ grep -i 'useradd\|new user' /var/log/auth.log | grep backdoor
Jan 14 03:12:44 host useradd[2211]: new user: name=backdoor, UID=1002, ...
```

И кто её использовал:

```
$ last -f /var/log/wtmp | grep backdoor
backdoor pts/0        10.10.20.9       Thu Jan 14 03:15   still logged in
```

Источник `10.10.20.9` — это уже зацепка для дальнейшего расследования.

## Полный разбор полей /etc/passwd и /etc/shadow

Формат `/etc/passwd` — семь полей через двоеточие. Читаем построчно:

```
backdoor:x:1002:1002::/home/backdoor:/bin/bash
└─имя──┘ │ └UID┘└GID┘└─gecos─┘└──домашний──┘└──shell──┘
         └ «x» = хеш в /etc/shadow
```

| Поле | Значение | Что важно для расследования |
|---|---|---|
| имя | логин | ищи странные/типовые (`admin`, `test`, `backdoor`) |
| пароль | `x` или хеш | `x` = хеш в shadow; пусто = без пароля |
| UID | числовой ID | **0 = root**; <1000 обычно системные |
| GID | основная группа | привязка к привилегиям |
| gecos | комментарий | пусто/странно — признак свежей учётки |
| домашний | `$HOME` | наличие каталога и его даты |
| shell | оболочка | `/bin/bash` = интерактивный доступ |

`/etc/shadow` добавляет поля сроков:

```
backdoor:$6$abcd...:19500:0:99999:7:::
         └───хеш───┘└последняя┘└min┘└max┘└warn┘
```

- `последняя` — дни с 1970 до последней смены пароля (19500 → ~2023);
- `min`/`max` — минимальный и максимальный срок действия;
- `warn` — за сколько дней предупреждать;
- последнее поле пустое — «аккаунт не истекает».

## Типы хешей и как отличить слабый

Префикс хеша говорит об алгоритме. Это прямо влияет на оценку риска и на возможность офлайн-подбора:

| Префикс | Алгоритм | Стойкость |
|---|---|---|
| `$1$` | MD5-crypt | слабый, ломается |
| `$2a$/$2b$/$2y$` | bcrypt | сильный |
| `$5$` | SHA-256-crypt | средний |
| `$6$` | SHA-512-crypt | средний/сильный |
| `$y$` | yescrypt | сильный (современный) |
| `!` или `*` | вход по паролю запрещён | — |

Практика: `$1$` и `$5$` — кандидаты на подбор (например, `hashcat -m 500` для MD5-crypt). Но помни: отсутствие хеша (`!`) не значит «учётка не используется» — вход по SSH-ключу работает независимо от пароля.

## Привилегированные группы и что они дают

Права в Linux даёт членство в группах. Не все «привилегированные» группы очевидны:

| Группа | Что даёт | Опасность |
|---|---|---|
| `sudo` / `wheel` | повышение прав через sudo | прямая |
| `docker` | запуск контейнеров | **эквивалент root** (mount хоста) |
| `lxd` / `lxc` | контейнеры | эквивалент root |
| `disk` | прямой доступ к блочным устройствам | чтение/запись диска в обход прав |
| `adm` | чтение системных логов | разведка |
| `shadow` | чтение `/etc/shadow` | офлайн-подбор паролей |
| `video`/`render` | доступ к устройствам | иногда утечки/атаки на драйверы |

Особое внимание — `docker` и `lxd`: формально «не root», фактически полный контроль над хостом.

## Опасные конструкции sudoers

`sudoers` описывает, что и как можно повышать. Опасные шаблоны:

| Конструкция | Почему опасно |
|---|---|
| `ALL=(ALL) NOPASSWD: ALL` | любые команды без пароля |
| `ALL=(ALL) NOPASSWD: /bin/bash` | прямой shell от root |
| `(ALL) NOPASSWD: /usr/bin/vi` | выход в shell из редактора |
| `NOPASSWD: /bin/systemctl` | подмена unit → команда от root |
| `NOPASSWD: /usr/bin/find` | `-exec /bin/sh` → root |
| wildcard в пути (`/opt/app/*`) | подстановка своего бинарника |
| `env_keep+=LD_PRELOAD` | инъекция библиотеки в root-процесс |

Проверка:

```
$ sudo -l
$ sudo grep -rE 'NOPASSWD|ALL=' /etc/sudoers /etc/sudoers.d/
```

## Крайние случаи и ограничения

- **Нет доступа к `/etc/shadow`.** Тогда смотри группы и `sudoers` — часто достаточно для вывода о привилегиях.
- **LDAP/SSSD-учётки.** В доменной среде пользователи не в `/etc/passwd`; смотри `getent passwd`, `sssctl`, кэш SSSD.
- **Учётка удалена, следы остались.** Файлы с осиротевшим UID: `find / -uid 1002 -ls`.
- **`sudo`-логи.** Каждое использование фиксируется в `auth.log` (`sudo: backdoor : ... COMMAND=`); журнал — ключ к реконструкции.
- **Подделка UID.** Запись с UID 0 под чужим именем — скрытый root; проверяй всех, у кого UID 0, а не только `root`.

## Сценарий: реконструкция создания backdoor

Задача — доказать, когда и как появилась учётка `backdoor`.

```
# 1. Есть ли учётка и какие права
$ getent passwd backdoor
backdoor:x:1002:1002::/home/backdoor:/bin/bash

# 2. Когда создана (auth.log)
$ grep -iE 'useradd|new user' /var/log/auth.log | grep backdoor
Jan 14 03:12:44 host useradd[2211]: new user: name=backdoor, UID=1002, GID=1002

# 3. Кто создал — сессия до этого момента
$ grep 'Accepted' /var/log/auth.log | tail -3
Jan 14 03:10:02 host sshd[2200]: Accepted password for deploy from 10.10.20.9

# 4. Права, которые выдали
$ grep -r backdoor /etc/sudoers.d/ 2>/dev/null
backdoor ALL=(ALL) NOPASSWD: ALL

# 5. Входы под ней
$ last -f /var/log/wtmp | grep backdoor
backdoor pts/0  10.10.20.9  Thu Jan 14 03:15   still logged in
```

Цепочка выстраивается: вход `deploy` с `10.10.20.9` → создание `backdoor` → выдача `NOPASSWD` → вход под ней. Каждый шаг подтверждён отдельным источником, поэтому вывод устойчив, а не построен на одном артефакте.

## Быстрая проверка: команды и сводка

Минимальный набор команд для аудита учётных записей и привилегий:

```
$ awk -F: '($3==0){print $1" UID0"}' /etc/passwd      # все с UID 0 (скрытые root)
$ getent passwd | awk -F: '$3>=1000'                  # обычные пользователи (вкл. LDAP)
$ awk -F: '($2==""){print $1" no-pass"}' /etc/passwd  # учётки без пароля
$ sudo awk -F: 'length($2)<4{print $1}' /etc/shadow   # пустые/битые хеши
$ sudo grep -rE 'NOPASSWD|ALL=' /etc/sudoers /etc/sudoers.d/
$ id                                                    # свои группы
$ groups backdoor                                       # группы цели
$ find / -nouser -o -nogroup 2>/dev/null                # осиротевшие файлы
```

Сводка по привилегированным группам, которую стоит держать под рукой:

| Группа | Даёт | Эквивалент |
|---|---|---|
| `sudo`/`wheel` | повышение прав | root (по правилам) |
| `docker` | запуск контейнеров | root хоста |
| `lxd` | управление контейнерами | root хоста |
| `disk` | доступ к блочным устройствам | чтение диска |
| `shadow` | чтение хешей | офлайн-подбор |
| `adm` | чтение логов | разведка |

Типичные ошибки: проверять только `root`, а не всех с UID 0; считать пустой пароль безопасным (вход по ключу остаётся); забывать про `sudoers.d/*` при поиске правил; игнорировать LDAP-учётки (`getent`, `sssctl`) в доменной среде. Правило прежнее: **сначала зафиксируй состояние (копию файлов), потом меняй** — правка `passwd`/`sudoers` уничтожает улики.

## Что мы теперь знаем

- `/etc/passwd` даёт список учёток; UID 0 — это root.
- Хеши и сроки — в `/etc/shadow`.
- Права даёт группа (`sudo`, `wheel`, `docker`).
- `sudoers` может разрешать `NOPASSWD` — это опасно.
- `auth.log` и `wtmp` показывают создание и входы.

## Если не сработало

- Нет доступа к `/etc/shadow`? Смотри членство в группах и `sudoers` — их часто
  достаточно.
- Логи ротированы? Проверь `auth.log.1`, `.gz` и journald (`journalctl -u ssh`).
- Учётка удалена? Ищи её UID в файлах (`find / -uid 1002`).
