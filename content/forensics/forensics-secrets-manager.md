## Вопрос, с которого всё начинается

Атакующий не хранил пароли в коде — он читал их из **менеджера секретов**. Сам менеджер
при этом не «взломан»: он честно отдал секрет тому, у кого были права. Как понять, что
секреты утекли?

## Наш пример: всплеск чтения секретов

Смотрим аудит-лог Vault:

```
$ vault audit list
Path     Type
file/    file

$ jq -r 'select(.type=="response") | "\(.time) \(.auth.display_name) \(.request.path)"' \
    /var/log/vault_audit.log | tail
2026-03-10T03:14:01Z user-alice secret/data/db/prod
2026-03-10T03:14:02Z user-alice secret/data/api/keys
2026-03-10T03:14:03Z user-alice secret/data/aws/creds
```

Один пользователь за секунды прочитал несколько разных секретов. Это **аномалия**: штатно
сервис читает свой секрет, а не «все подряд».

## Что такое менеджер секретов

**Менеджер секретов** (Vault, AWS Secrets Manager, GCP Secret Manager) хранит пароли,
ключи и токены централизованно и выдаёт их по запросу. Ключевое: у каждого обращения есть
**аудит-запись** — кто, когда, к какому секрету.

## Шаг 1: аудит-логи Vault

Vault пишет **две** записи на запрос: `request` и `response`. Полезны обе:

- `auth.display_name` / `auth.metadata` — кто обращался (пользователь, сервис);
- `request.path` — к какому секрету;
- `request.remote_address` — откуда;
- `response.data` — что вернулось (если включено).

Фильтруем по аномалиям: необычный пользователь, необычный IP, массовые чтения.

## Шаг 2: AWS — CloudTrail и KMS

В AWS чтение секрета фиксируется событием **GetSecretValue**, а расшифровка — событиями
**KMS Decrypt**:

```
$ aws cloudtrail lookup-events --lookup-attributes AttributeKey=EventName,AttributeValue=GetSecretValue
GetSecretValue  user/alice  2026-03-10T03:14:01Z  secret:db/prod
```

Массовые `GetSecretValue` с одной учётки в короткое время — сигнал компрометации.

## Шаг 3: KMS-ключи

Даже если секрет зашифрован KMS, факт **Decrypt** фиксируется. Аномалии:

- расшифровка ключом, который обычно не используется;
- расшифровка из необычного региона/аккаунта;
- `ScheduleKeyDeletion` — попытка уничтожить ключ (анти-форензика).

## Шаг 4: что делать с найденным

- **ротация**: все прочитанные секреты считать скомпрометированными и сменить;
- **сужение прав**: почему учётка имела доступ ко всем секретам;
- **проверка использования**: не появились ли новые ресурсы/подключения с этих секретов.

## Ловушки

- **Аудит выключен** — тогда следов чтения нет вообще (само по себе подозрительно).
- **Секреты в state/коде** — менеджер тут ни при чём, ищи утечку в IaC/репозитории.
- **Кэширование** — некоторые клиенты кэшируют секреты, поэтому «одно чтение» может
  использоваться многократно.

## Что мы теперь знаем

- Менеджер секретов ведёт аудит каждого обращения.
- Аномалии: необычный пользователь/IP, массовые чтения.
- В AWS чтение — GetSecretValue, расшифровка — KMS Decrypt.
- ScheduleKeyDeletion может быть анти-форензикой.
- Прочитанные секреты подлежат немедленной ротации.

## Куда дальше

Дальше — **CI/CD**: как пайплайны получают секреты и становятся точкой входа. А пока
запомни: аудит-логи менеджера секретов отвечают на вопрос «кто забрал секреты».

## Где пригодится

- **Cloud Security** — обнаружение утечки секретов.
- **DFIR / Incident Response** — оценка скомпрометированных секретов.
- **CTF Forensics** — задачи с аудит-логами.
