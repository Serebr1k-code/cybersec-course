## Вопрос, с которого всё начинается

Атакующий не хранил пароли в коде — он читал их из **менеджера секретов**. Сам менеджер
при этом не «взломан»: он честно отдал секрет тому, у кого были права. Как понять, что
секреты утекли?

## Наш пример: всплеск чтения секретов

Смотрим аудит-лог Vault:

```
$ vault audit list
Path     Type
file/    file

$ jq -r 'select(.type=="response") | "\(.time) \(.auth.display_name) \(.request.path)"' \
    /var/log/vault_audit.log | tail
2026-03-10T03:14:01Z user-alice secret/data/db/prod
2026-03-10T03:14:02Z user-alice secret/data/api/keys
2026-03-10T03:14:03Z user-alice secret/data/aws/creds
```

Один пользователь за секунды прочитал несколько разных секретов. Это **аномалия**: штатно
сервис читает свой секрет, а не «все подряд».

## Что такое менеджер секретов

**Менеджер секретов** (Vault, AWS Secrets Manager, GCP Secret Manager) хранит пароли,
ключи и токены централизованно и выдаёт их по запросу. Ключевое: у каждого обращения есть
**аудит-запись** — кто, когда, к какому секрету.

## Шаг 1: аудит-логи Vault

Vault пишет **две** записи на запрос: `request` и `response`. Полезны обе:

- `auth.display_name` / `auth.metadata` — кто обращался (пользователь, сервис);
- `request.path` — к какому секрету;
- `request.remote_address` — откуда;
- `response.data` — что вернулось (если включено).

Фильтруем по аномалиям: необычный пользователь, необычный IP, массовые чтения.

## Шаг 2: AWS — CloudTrail и KMS

В AWS чтение секрета фиксируется событием **GetSecretValue**, а расшифровка — событиями
**KMS Decrypt**:

```
$ aws cloudtrail lookup-events --lookup-attributes AttributeKey=EventName,AttributeValue=GetSecretValue
GetSecretValue  user/alice  2026-03-10T03:14:01Z  secret:db/prod
```

Массовые `GetSecretValue` с одной учётки в короткое время — сигнал компрометации.

## Шаг 3: KMS-ключи

Даже если секрет зашифрован KMS, факт **Decrypt** фиксируется. Аномалии:

- расшифровка ключом, который обычно не используется;
- расшифровка из необычного региона/аккаунта;
- `ScheduleKeyDeletion` — попытка уничтожить ключ (анти-форензика).

## Шаг 4: что делать с найденным

- **ротация**: все прочитанные секреты считать скомпрометированными и сменить;
- **сужение прав**: почему учётка имела доступ ко всем секретам;
- **проверка использования**: не появились ли новые ресурсы/подключения с этих секретов.

## Ловушки

- **Аудит выключен** — тогда следов чтения нет вообще (само по себе подозрительно).
- **Секреты в state/коде** — менеджер тут ни при чём, ищи утечку в IaC/репозитории.
- **Кэширование** — некоторые клиенты кэшируют секреты, поэтому «одно чтение» может
  использоваться многократно.

## Что мы теперь знаем

- Менеджер секретов ведёт аудит каждого обращения.
- Аномалии: необычный пользователь/IP, массовые чтения.
- В AWS чтение — GetSecretValue, расшифровка — KMS Decrypt.
- ScheduleKeyDeletion может быть анти-форензикой.
- Прочитанные секреты подлежат немедленной ротации.

## Модель угроз менеджера секретов

Менеджер секретов (Vault, AWS Secrets Manager, GCP Secret Manager, Azure Key Vault) решает
проблему «где хранить пароли». Но сам он — **цель**, а не только защита. Три сценария:

- **Легитимный доступ скомпрометирован** — атакующий получил права сервиса/пользователя и
  читает секреты «законно». Менеджер не «взломан» — им просто **пользуются**.
- **Менеджер взломан** — утечка root-токена Vault, подделка JWT, слабая политика даёт
  доступ ко всему.
- **Обход менеджера** — секреты лежат в IaC/репозитории/переменных окружения и утекают
  мимо аудита.

Форензика начинается с вопроса: **какой** из сценариев реализовался.

## Аудит Vault: структура записей

Vault пишет **две** записи на каждый запрос — `request` и `response`. Ключевые поля:

```
{
  "type": "response",
  "time": "2026-03-10T03:14:01Z",
  "auth": { "display_name": "user-alice", "metadata": {"remote_address":"10.0.0.5"} },
  "request": { "path": "secret/data/db/prod", "operation": "read" },
  "response": { "data": { "password": "..." } }
}
```

Полезные срезы:

```
$ jq -r 'select(.type=="response") | [.time,.auth.display_name,.request.path] | @tsv' \
    /var/log/vault_audit.log | awk '{print $2}' | sort | uniq -c | sort -rn | head
    148 user-alice
      3 svc-web
```

Учётка с сотнями чтений — аномалия: штатный сервис читает **один** свой секрет, а не
«все подряд». Дополнительно фильтруй по `remote_address` — доступ из необычной сети.

## AWS: GetSecretValue и KMS Decrypt

В AWS каждое чтение секрета — событие CloudTrail `GetSecretValue`, а расшифровка —
`Decrypt`. Смотрим:

```
$ aws cloudtrail lookup-events \
    --lookup-attributes AttributeKey=EventName,AttributeValue=GetSecretValue \
    --query 'Events[].[EventTime,Username,Resources[0].ResourceName]'
```

Аномалии: массовые чтения с одной учётки, доступ из неожиданного региона, чтение
секретов, к которым обычно не обращаются. Отдельно — **KMS**:

```
$ aws cloudtrail lookup-events \
    --lookup-attributes AttributeKey=EventName,AttributeValue=ScheduleKeyDeletion
```

`ScheduleKeyDeletion` — попытка **уничтожить** ключ: анти-форензика (после удаления ключа
зашифрованные секреты не прочесть).

## Vault: обнаружение компрометации токена

- **Резкое число чтений** одной учётки в короткое окно;
- **`auth.display_name` = root** там, где обычно сервисные;
- **новый IP** в `auth.metadata.remote_address`;
- **политики**, расширенные незадолго до атаки (`vault policy write` в аудите);
- **`token create`** с большим TTL — persistence атакующего;
- **отключённый аудит** (`vault audit disable`) — сам по себе красный флаг.

## Что делать с найденным

1. **Ротация** — все прочитанные секреты считать скомпрометированными; сменить.
2. **Сужение прав** — почему учётка имела доступ к «всем» секретам.
3. **Проверка использования** — не появились ли новые ресурсы/подключения с этих секретов
   (сопоставить с CloudTrail/логами).
4. **Отзыв токенов** — `vault token revoke`, отключение ключей IAM.
5. **Включить/проверить аудит** — убедиться, что все обращения логируются.

## Ограничения

- **Аудит может быть выключен** — тогда следов чтения нет вообще; это само по себе улика.
- **Логи ротируются** — старые записи уходят; нужна централизованная выгрузка.
- **Кэширование секретов** — одно «чтение» может использоваться многократно; не путай
  «мало чтений» с «мало использования».
- **`response.data` может быть скрыт** — по политике тело ответа не логируется; тогда
  видно только факт и путь, а не значение.
- **Секреты вне менеджера** — утечка из IaC/репозитория менеджером не видна; ищи отдельно.

## Практический чеклист

1. `vault audit list` / проверить включён ли аудит у AWS/GCP.
2. Выгрузить `request`/`response` записи; сгруппировать по учётке и IP.
3. Найти массовые чтения и необычные адреса.
4. Проверить CloudTrail `GetSecretValue` и `KMS Decrypt`.
5. Искать `ScheduleKeyDeletion`, `token create`, `policy write` в окне атаки.
6. Составить список скомпрометированных секретов → ротация.
7. Проверить использование секретов (новые ресурсы/соединения).

## Vault: устройство аудита и что в нём искать

Vault пишет аудит в формате JSON-lines, по **две** записи на запрос. Полезные срезы:

```
$ jq -r 'select(.type=="response") | [.time,.auth.display_name,.request.path] | @tsv' \
    /var/log/vault_audit.log | tail
2026-03-10T03:14:01Z user-alice secret/data/db/prod
2026-03-10T03:14:02Z user-alice secret/data/api/keys
2026-03-10T03:14:03Z user-alice secret/data/aws/creds
```

Красные флаги в аудите Vault:

- один `display_name` читает **много разных** путей за секунды;
- `display_name = root` в рутинное время;
- новый `remote_address` в `auth.metadata`;
- `sys/audit` disable — кто-то выключил логирование;
- `token create` с большим `ttl` — persistence;
- `policy write` — расширение прав перед атакой.

## AWS: GetSecretValue, KMS и эксфильтрация

В AWS чтение секрета — `GetSecretValue`, расшифровка — `Decrypt`. Сопоставление обоих
событий даёт полную картину:

```
$ aws cloudtrail lookup-events \
    --lookup-attributes AttributeKey=EventName,AttributeValue=Decrypt
Decrypt  user/alice  2026-03-10T03:14Z  key/4a3b...
```

Аномалии KMS: расшифровка ключом, который обычно не используется; расшифровка из
необычного региона/аккаунта; `ScheduleKeyDeletion` (уничтожение ключа = анти-форензика);
`DisableKey`. Отдельно проверь `PutSecretValue` — кто **писал** секреты (мог подменить).

## Модель «секрет прочитан» → «секрет использован»

Само чтение секрета — не конец. Важно, **использовали** ли его:

- появились новые ресурсы (инстансы, бакеты) с этой учёткой;
- новые подключения к БД/API из необычных мест;
- новые ключи IAM, созданные скомпрометированной учёткой;
- изменения в сервисах, к которым секрет давал доступ.

Это связывает утечку секрета с реальным ущербом и определяет объём ротации.

## Ротация: порядок имеет значение

1. **Изолировать** — отозвать токен/ключ, чтобы атакующий не прочитал **новый** секрет.
2. **Сменить** — все прочитанные секреты (пароли, ключи, токены).
3. **Проверить** — убедиться, что старый секрет больше не действует.
4. **Задокументировать** — какие секреты, когда, кем прочитаны.

Если сменить раньше, чем изолировать, атакующий с активной сессией прочитает новое
значение.

## Ограничения

- **Аудит выключен** — чтения не видны; отсутствие логов само подозрительно.
- **Тело ответа скрыто** — по политике `response.data` может не логироваться; видно факт,
  но не значение.
- **Кэширование** — клиенты кэшируют секреты; одно чтение может использоваться долго.
- **Секреты вне менеджера** — IaC/репозиторий/переменные окружения утекают мимо аудита.
- **Разные аккаунты/проекты** — секреты могут лежать в нескольких местах; проверяй все.

## Практический чеклист

1. Убедиться, что аудит включён (Vault `audit list`, AWS CloudTrail, GCP logging).
2. Выгрузить записи чтения; сгруппировать по учётке/IP.
3. Найти массовые чтения и необычные адреса.
4. Проверить KMS `Decrypt`/`ScheduleKeyDeletion`/`DisableKey`.
5. Сопоставить чтение секрета с его **использованием**.
6. Составить список скомпрометированных секретов.
7. Изолировать → ротировать → проверить → задокументировать.

## Сравнение менеджеров: на что смотреть

| Менеджер | Где аудит | Ключевые события |
|----------|-----------|------------------|
| HashiCorp Vault | `vault audit` (файл/syslog) | `request`/`response`, `token create` |
| AWS Secrets Manager | CloudTrail | `GetSecretValue`, `PutSecretValue` |
| AWS KMS | CloudTrail | `Decrypt`, `ScheduleKeyDeletion` |
| GCP Secret Manager | Cloud Audit Logs | `AccessSecretVersion` |
| Azure Key Vault | Azure Monitor | `SecretGet`, `SecretSet` |

Общий принцип один: **каждое обращение к секрету логируется**, и аномалия — это не
«взлом», а отклонение от обычного профиля доступа (кто, откуда, сколько и к каким
именно секретам). Именно отклонение и есть первая зацепка расследования.
