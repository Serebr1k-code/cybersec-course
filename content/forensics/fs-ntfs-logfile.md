## Вопрос, с которого всё начинается

В NTFS-образе ты видишь подозрительно «ровные» метки времени: файл создан и изменён в одну
и ту же секунду, будто его подделали. Но доказать нечем — в `$MFT` только итоговые значения.
Однако NTFS ведёт **журнал всех изменений метаданных**, и там сохраняется, что именно
менялось. Этот журнал — `$LogFile`.

## Что такое $LogFile

**`$LogFile`** — системный файл NTFS, в который драйвер пишет **журнал транзакций
(write-ahead log)**. Смысл журнала в надёжности: перед тем как изменить структуру
метаданных на диске, NTFS записывает в `$LogFile` **redo**-запись (как применить изменение)
и **undo**-запись (как откатить). Если система упадёт в середине операции, при следующей
загрузке журнал позволит либо доделать, либо откатить её.

Для форензики важны две вещи:

- журнал хранит **последовательность операций** с метаданными (создание, удаление,
  изменение атрибутов), часто с временем;
- операции нумеруются **LSN (Log Sequence Number)** — монотонно растущим номером записи,
  который упорядочивает всё во времени.

Это делает `$LogFile` ценным при **анти-форензике**: подделка меток времени (`timestomp`)
сама порождает записи в журнале, и их можно сопоставить.

## Наш пример: файл журнала

```
$ ls -la LogFile
-rw-r--r-- 1 student student 67108864 LogFile
$ file LogFile
LogFile: data
```

`file` не опознаёт журнал — это ожидаемо, у `$LogFile` нет «человеческой» подписи в начале.
Зато записи журнала содержат узнаваемые маркеры. Посмотрим текстовые метки:

```
$ strings LogFile | grep -Ei 'FILE0|LSN|REDO|UNDO|RESTART'
FILE0
LSN 000000000001a4f2 REDO_ACTION ClientRecord
LSN 000000000001a4f3 UNDO_ACTION SetNewAttributeSizes
LSN 000000000001a501 REDO_ACTION CreateFileRecord
RESTART_PAGE magic 0x52535452
EVIDENCE: nto{ntfs_l0gfile_r3d0_und0}
```

Мы видим записи redo/undo, номера LSN и `RESTART_PAGE` — «страницу перезапуска», которая
хранит контрольную точку: с какого LSN продолжать восстановление. Это каркас журнала.

## Шаг 1: структура журнала

`$LogFile` логически делится так:

| Часть | Назначение |
|-------|-----------|
| Заголовок файла (restart area) | две копии `RESTART_PAGE` — контрольные точки |
| Буфер записей | кольцевой буфер из страниц по 4096 байт |
| Записи (records) | redo/undo-операции с LSN |
| Копии restart page | на случай повреждения основной |

Ключевая особенность: журнал — **кольцевой**. Когда место кончается, старые страницы
затираются новыми. Значит, `$LogFile` хранит только **недавние** изменения, а не всю
историю. Это важно для оценки полноты: если инцидент был давно, журнал мог «завернуться».

## Шаг 2: LSN — линейка времени

**LSN (Log Sequence Number)** — 64-битный счётчик, который увеличивается на каждую запись.
Он не привязан напрямую к wall-clock, но строго упорядочен: запись с меньшим LSN произошла
раньше. Восстанавливая последовательность LSN, ты получаешь порядок операций:

```
LSN 1a4f2  SetNewAttributeSizes  (файл 42)   ← изменили размер атрибута
LSN 1a4f3  ClientRecord          (файл 42)   ← отметили использование
LSN 1a501  CreateFileRecord      (файл 77)   ← создали новый файл
```

Сравнивая LSN с соседними событиями (USN-журнал, EVTX), можно точно локализовать момент
подозрительного изменения.

## Шаг 3: чем парсить

`$LogFile` — бинарный формат, руками его не читают. Инструменты:

- **LogFileParser** (Joakim Schicht) — разбирает `$LogFile` и выдаёт записи с LSN, типом
  действия и номером записи MFT;
- **ntfs-log-tracker** — похожий парсер с выводом в человекочитаемом виде;
- **X-Ways / EnCase** — коммерческие пакеты с поддержкой журнала;
- **`fsstat` (The Sleuth Kit)** — даёт общую картину метаданных, но не разбор записей.

Пример вывода LogFileParser (упрощённо):

```
$ LogFileParser.exe -f LogFile
LSN: 1a4f2  Redo: SetNewAttributeSizes  MFT: 42
LSN: 1a4f3  Redo: ClientRecord          MFT: 42
LSN: 1a501  Redo: CreateFileRecord      MFT: 77
```

Каждая строка — одна транзакция с адресом записи MFT, которую она затронула.

## Шаг 4: что искать в журнале

Практические сценарии:

- **Подделка времени (timestomp).** Изменение `$STANDARD_INFORMATION` порождает
  `SetNewAttributeSizes`/`UpdateRecord` — их можно сопоставить с «ровными» таймстемпами.
- **Удаление файла.** Записи удаления показывают, что запись MFT освободили, — иногда
  раньше, чем это видно по другим артефактам.
- **Переименование.** Операция rename отражается как изменение `$FILE_NAME` — полезно
  при отслеживании переименованных образцов malware.
- **Создание ADS.** Потоки (`:Zone.Identifier`, скрытые данные) создаются отдельными
  транзакциями — их видно в журнале.

## Шаг 5: восстановление с журналом

При «грязном» размонтировании NTFS может переиграть журнал. Для форензики это **опасно**:
переигранный журнал меняет метаданные. Поэтому:

- монтируй образ **только для чтения** (или вообще не монтируй — парси `$LogFile`
  отдельно);
- сначала сохрани копию `$LogFile`;
- сопоставляй найденные транзакции с `$MFT` и `$UsnJrnl` для подтверждения.

## Частые ошибки и подводные камни

- **Ожидание полной истории.** Журнал кольцевой; старые записи затираются.
- **Путаница с `$UsnJrnl`.** `$UsnJrnl` (`$J`) фиксирует изменения **файлов**, а
  `$LogFile` — транзакции **метаданных**. Это разные журналы, их сопоставляют.
- **Монтирование с записью.** Переиграет журнал и изменит `$MFT`.
- **Неверный размер записи.** Формат зависит от версии NTFS (1.1, 3.1); старый парсер
  может не понять новый журнал.
- **Игнорирование restart page.** Без неё непонятно, где актуальная часть кольца.

## Что мы теперь знаем

- `$LogFile` — журнал транзакций метаданных NTFS с redo/undo-записями.
- Записи упорядочены по LSN — это линейка времени.
- Журнал кольцевой: хранит только недавние изменения.
- Он помогает доказать timestomp, удаление, переименование, создание ADS.
- Инструменты: LogFileParser, ntfs-log-tracker, X-Ways, EnCase.

## Что фиксировать в отчёте

| Что | Зачем |
|-----|-------|
| Диапазон LSN в журнале | период покрытия |
| Список транзакций с номерами MFT | какие объекты менялись |
| Сопоставление с USN/MFT | подтверждение |
| Признаки подделки времени | доказательство анти-форензики |
| Метод разбора и версия NTFS | воспроизводимость |

## Мини-практика: сопоставление LSN с другими журналами

`$LogFile` силён не сам по себе, а в связке. У NTFS есть ещё журнал изменений файлов
`$UsnJrnl` (`$Extend\$UsnJrnl:$J`). Он фиксирует события вида `FILE_CREATE`,
`DATA_EXTEND`, `FILE_DELETE` с **USN** (Update Sequence Number) и метками времени. USN и
LSN — разные счётчики, но события в них часто идут параллельно.

Типичный рабочий приём: найти в `$UsnJrnl` подозрительное `FILE_DELETE`, взять время и
номер записи MFT, а затем найти в `$LogFile` транзакции по тому же номеру MFT вблизи
этого момента. Совпадение подтверждает событие с двух независимых источников:

```
$ UsnJrnlParser.exe -f '$UsnJrnl_$J'
2026-03-12 01:19:57  FILE_DELETE  MFT: 77  name: evidence.zip
$ LogFileParser.exe -f LogFile | grep 'MFT: 77'
LSN 1a4f2  Redo: SetNewAttributeSizes  MFT: 77
LSN 1a501  Redo: DeleteFileRecord      MFT: 77
```

Две разные подсистемы NTFS показали одно и то же событие. В отчёте такое «двойное
подтверждение» весит куда больше одиночной записи.

Ещё один источник — **$MFT** и **$STANDARD_INFORMATION**. Если в `$MFT` метка изменения
раньше, чем LSN соответствующей транзакции, это несоответствие: возможно, запись
восстановили из резервной копии или метаданные меняли в обход обычного пути.

## Формат записи журнала подробнее

Каждая запись `$LogFile` начинается с заголовка, в котором есть:

- **LSN** — номер этой записи;
- **record type** — тип (ClientRecord, RedoOnly, UndoOnly, CheckPoint);
- **transaction ID** — идентификатор транзакции, объединяющий несколько записей;
- **target attribute / MFT reference** — какой объект затронут;
- **redo op** и **undo op** — конкретные операции (например, `CreateFileRecord`,
  `SetNewAttributeSizes`, `DeleteFileRecord`).

Именно поле **transaction ID** позволяет собрать несколько записей в одну логическую
операцию: одна транзакция может породить десяток записей, но все они помечены одним ID.
Если видишь `CheckPoint`-запись — это точка, после которой предыдущие транзакции
завершены и зафиксированы.

Понимание этих полей превращает сырой дамп в читаемую историю: «в 01:19 транзакция 0x9c
удалила запись MFT 77» — фраза, которая ложится в отчёт как доказательство.

## Куда дальше

Мы разобрали журнал метаданных. Дальше посмотрим, как NTFS хранит **сжатие и разреженные
файлы** — там данные выглядят «отсутствующими», но на самом деле упакованы, и это частая
ловушка при извлечении. А пока главное запомни: **LSN упорядочивает всё, и кольцо журнала
конечно**.

## Где пригодится

- **CTF Forensics:** образы, где надо доказать подделку времени или удаление.
- **DFIR:** восстановление последовательности действий злоумышленника на NTFS.
- **Anti-forensics detection:** обнаружение timestomping по транзакциям.
- **Data recovery:** проверка, что реально менялось перед сбоем.
