## Вопрос, с которого всё начинается

Тебе дали папку с файлами виртуальной машины: `web.vmx`, `web.vmdk`,
`web-000001.vmdk`, `web.vmem`. Ты открываешь `web.vmdk` и видишь старые данные —
не те, что ожидал. Почему?

Потому что у машины был **снапшот**: все изменения после него лежат в отдельном
файле-дельте. Чтобы увидеть актуальное состояние, нужно «наложить» дельту на
родительский диск. В этом уроке мы разберём набор файлов VM и соберём из него
актуальный образ.

## Шаг 1: форматы дисков VM

Виртуальный диск — это **контейнер**, а не «сырой» диск. У каждого гипервизора свой
формат:

| Формат | Гипервизор | Особенности |
|--------|-----------|-------------|
| VMDK | VMware | monolithic/split, дельта-снапшоты |
| VHD/VHDX | Hyper-V | dynamic/fixed, дельта `.avhdx` |
| QCOW2 | QEMU/KVM | backing file, снапшоты |
| VDI | VirtualBox | dynamic, снапшоты |
| raw | любой | побайтовый |

Смотрим, что за файл перед нами:

```bash
$ file web.vmdk
web.vmdk: VMware4 disk image
$ qemu-img info web.vmdk
image: web.vmdk
file format: vmdk
virtual size: 40G
```

`qemu-img` — универсальная утилита для работы с форматами виртуальных дисков. Она
читает метаданные и, главное, видит **цепочку** дельт. Помимо `info`, у неё есть
`convert` (сменить формат), `snapshot` (создать/список снапшотов) и `check`
(проверить целостность). Для разбора VM обычно достаточно `info` и `convert`.

## Шаг 2: снапшот — это дельта

**Снапшот** в виртуализации — не полная копия диска, а **дельта** изменений
относительно «родителя». Когда делают снапшот, базовый диск замораживают, а все новые
записи идут в отдельный файл. Чтобы получить состояние на момент снапшота, нужно
наложить цепочку файлов друг на друга.

Смотрим на нашу дельту:

```bash
$ qemu-img info web-000001.vmdk
image: web-000001.vmdk
file format: vmdk
backing file: web.vmdk          # <- родитель!
```

Строка `backing file: web.vmdk` — прямое указание: этот файл — дельта поверх
`web.vmdk`. Собираем полный образ:

```bash
$ qemu-img convert -O raw web-000001.vmdk web_full.raw
$ mmls web_full.raw
002:  000:00  0000002048  0000411647  NTFS (0x07)
```

`qemu-img convert` «схлопнул» цепочку в один raw-образ. Теперь в нём настоящая
файловая система. Если снапшотов несколько, `convert` применит всю цепочку от
последней дельты до базового диска автоматически — вручную накладывать файлы не нужно.

## Шаг 3: какой снапшот активен

Снапшотов может быть несколько, и они образуют дерево. Какой из них «текущий»,
описано не в имени файла, а в конфигурации: у VMware — в `.vmsd`/`.vmx`, у VirtualBox —
в `.vbox`, у Hyper-V — в `.vmcx`. Именно там указано, какая дельта соответствует
какому снапшоту.

```bash
$ VBoxManage snapshot vm list        # VirtualBox
$ grep -i snapshot web.vmx           # VMware
```

Важно: анализировать базовый `web.vmdk` в одиночку — ошибка. Вы увидите состояние
**до** снапшота, устаревшее. Нужная версия данных часто лежит именно в родителе
(например, файл, который позже удалили).

## Шаг 4: монтируем файловую систему гостя

Внутри собранного образа — обычная файловая система. Монтируем **только для чтения**:

```bash
$ sudo modprobe nbd max_part=8
$ sudo qemu-nbd --connect=/dev/nbd0 web.vmdk
$ sudo mount -o ro /dev/nbd0p1 /mnt/vm
```

`qemu-nbd` подключает виртуальный диск как блочное устройство `/dev/nbd0`, а дальше
он ведёт себя как физический. Есть и более простой путь — `guestmount`, который сам
находит разделы:

```bash
$ guestmount -a web.vmdk -i --ro /mnt/vm
```

## Шаг 5: память виртуальной машины

Память гостя хранится в отдельном файле. У VMware это `.vmem` — по сути, **raw-дамп
памяти**, который можно сразу отдать Volatility:

```bash
$ vol -f web.vmem windows.pslist | head
$ vol -f web.vmem windows.netscan | grep ESTABLISHED
```

Файл `.vmss` — это **состояние приостановки** (suspended): там и регистры процессора,
и память. Чтобы вытащить из него память для анализа, нужна конвертация. У Hyper-V
память лежит в `.bin`, у QEMU — в файле, указанном при запуске, или в дампе
`virsh dump --memory-only`.

## Шаг 6: артефакты гипервизора

Расследование VM идёт на **двух уровнях**: гость (ОС внутри) и хост (гипервизор). На
уровне хоста остаются:

- **Конфиги**: `.vmx`, `.vbox`, `.xml`, `.vmcx` — параметры гостя, сеть, диски.
- **Логи**: `vmware.log`, `VBox.log` — история запусков, подключений, снапшотов.
- **Общие папки** (shared folders) — канал обмена данными между хостом и гостем.

```bash
$ grep -iE 'displayName|memsize|ethernet0' web.vmx
$ grep -iE 'powered on|powered off|snapshot' vmware.log | tail
$ grep -iE 'sharedFolder|hgfs' web.vmx
```

Логи — золото: по ним видно, когда машину включали, какие USB-устройства и образы
подключали.

## Шаг 7: сводим время

Время в снапшотах, памяти и логах относится к **разным моментам**. При построении
таймлайна надо понимать, какой дамп/снапшот какому времени соответствует. Внутренние
часы гостя могут расходиться с хостом — для VM это нормально (особенно после
suspend/resume), но **сильный** сдвиг может указывать на манипуляции со временем.

```bash
# история запусков VM
$ grep -iE 'vmx|powered on' vmware.log | tail
```

## Шаг 8: чек-лист и ограничения

Порядок расследования VM:

1. Зафиксировать все файлы VM (диски, память, конфиги, логи, снапшоты).
2. Определить активный снапшот (`.vmsd`/`.vbox`/`*.avhdx`).
3. Собрать актуальный диск (`qemu-img convert`).
4. Смонтировать read-only (`qemu-nbd`/`guestmount`).
5. Разобрать ФС (`mmls`/`fsstat`/`fls`).
6. Проанализировать память (`.vmem` → Volatility).
7. Проверить конфиги и логи гипервизора.
8. Сверить время гостя и хоста.

Ограничения: **зашифрованные VM** (BitLocker/LUKS внутри) без ключа не читаются;
**дельта без родителя** не собирается; **повреждённый `.vmem`** ломает часть плагинов;
дерево снапшотов может быть глубоким, а активная ветвь определяется конфигом, не
именем файла. И помните: старые версии гипервизоров пишут минимум логов.

## Что мы теперь знаем

- Виртуальный диск — контейнер (VMDK/VHDX/QCOW2); `qemu-img` его читает.
- Снапшот — это дельта; актуальное состояние получают наложением цепочки.
- Какой снапшот активен, указано в конфиге (`.vmsd`/`.vbox`/`.vmcx`), а не в имени.
- Монтируют через `qemu-nbd`/`guestmount`; память гостя — в `.vmem`/`.bin`.
- На хосте остаются конфиги, логи и общие папки — второй уровень расследования.

## На что смотреть дальше

- **Анализировать базовый VMDK, игнорируя дельту** — увидите устаревшее состояние.
- **Путать `.vmss` и `.vmem`** — первое состояние CPU, второе память.
- **Монтировать read-write** — ФС/гипервизор изменят улику.
- **Забывать про логи гипервизора** — там история запусков и подключений.
- **Не конвертировать формат** перед TSK, если он не raw.
- **Зашифрованные VM** (BitLocker/LUKS внутри) — без ключа доступа нет.

## Куда дальше

Мы разобрали виртуальные машины. Дальше пойдём в конкретные артефакты Windows:
реестр, корзину, журналы — то, что остаётся на диске после работы пользователя. А
пока запомни: **в VM актуальные данные — в дельте, а история — в логах гипервизора**.

## Где пригодится

- **CTF:** задачи с VM-образами, снапшотами и памятью гостя.
- **Incident Response:** разбор виртуализированных хостов и их снапшотов.
- **Анализ VM-образов:** конвертация и работа с дельта-дисками.
- **Судебная экспертиза:** сбор артефактов гипервизора и гостя.
- **Enterprise:** форензика в VMware/Hyper-V/KVM-инфраструктурах.
