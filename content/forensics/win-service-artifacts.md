## Вопрос, с которого всё начинается

Злоумышленник закрепился в системе через службу — она стартует при загрузке и работает от
SYSTEM. Нужно найти эту службу, понять, когда её создали и что она запускает. Где искать?

## Наш пример: ветка Services в реестре

Службы описываются в реестре:

```
HKLM\SYSTEM\CurrentControlSet\Services\<имя_службы>
```

Посмотрим подозрительную службу:

```
$ reg query "HKLM\SYSTEM\CurrentControlSet\Services\WinUpdater" /v ImagePath
ImagePath    REG_EXPAND_SZ    C:\Users\Public\svc.exe
```

`ImagePath` указывает на исполняемый файл — здесь в пользовательском каталоге, что уже
подозрительно.

## Что такое служба и почему это персистентность

**Служба** — программа, которую диспетчер служб (`services.exe`) запускает в фоне, часто от
имени SYSTEM и при загрузке. Это делает службы идеальным механизмом закрепления: код
запускается автоматически и с высокими правами.

Каждая служба описывается набором значений: `ImagePath` (что запускать), `Start` (когда —
загрузка/вручную), `Type`, `ObjectName` (от чьего имени), `ServiceDll` (для служб-библиотек).
Именно эти поля и проверяет аналитик.

## Шаг 1: перечислить и отфильтровать службы

```
$ sc query type= service state= all | findstr /i SERVICE_NAME
$ reg query "HKLM\SYSTEM\CurrentControlSet\Services" /s /v ImagePath | findstr /i "Public Temp Users"
```

Фильтр по подозрительным путям (`Public`, `Temp`, `Users`) сразу выделяет кандидатов.

## Шаг 2: определить время создания

Точного «времени создания службы» в реестре нет, но его можно оценить по:

- метаданным самого исполняемого файла (создание/изменение);
- журналу **System**, событие **7045** (установка службы);
- журналу **Security**, событие **4697** (если включён аудит).

```
$ wevtutil qe System /q:"*[System[(EventID=7045)]]" /c:20 /f:text
Service Name: WinUpdater
Image Path:   C:\Users\Public\svc.exe
```

Событие 7045 даёт имя службы, путь и время установки — ключевое доказательство.

## Индикаторы вредоносной службы

| Признак | Что означает |
|---------|--------------|
| `ImagePath` вне `System32` | подозрительное расположение |
| `Start=0/1/2` у незнакомой службы | автозапуск |
| `ObjectName` = SYSTEM | высокие права |
| `ServiceDll` в нестандартном пути | перехват через svchost |
| Совпадение времени с инцидентом | связь с атакой |

## Шпаргалка команд

```
# Список служб
sc query type= service state= all

# Поля конкретной службы
reg query "HKLM\SYSTEM\CurrentControlSet\Services\<имя>" /s

# Установка служб (журнал)
wevtutil qe System /q:"*[System[(EventID=7045)]]" /f:text
```

## Что мы теперь знаем

- Службы описываются в `HKLM\SYSTEM\CurrentControlSet\Services\<имя>`.
- Ключевые поля: `ImagePath`, `Start`, `Type`, `ObjectName`, `ServiceDll`.
- Службы запускаются от SYSTEM и при загрузке — идеальный механизм персистентности.
- Время установки даёт событие 7045 (System) или 4697 (Security).
- Фильтр по путям `Public/Temp/Users` выделяет подозрительные службы.

## Сквозной пример: служба как механизм закрепления

Разберём инцидент целиком. Дано: на машине в фоне работает неизвестный процесс от SYSTEM,
который стартует при загрузке. Задача — найти службу, которая его запускает, и доказать факт
установки.

Шаг первый — перечисляем службы и фильтруем по нестандартным путям. В выводе `reg query`
находим службу `WinUpdater` с `ImagePath = C:\Users\Public\svc.exe`. Легитимные службы живут
в `System32`, поэтому путь в `Public` — сразу красный флаг. Шаг второй — читаем остальные
поля: `Start=2` (автозапуск), `ObjectName=LocalSystem` (высокие права). Вместе это описание
классической вредоносной службы. Шаг третий — ищем время установки в журнале System: событие
**7045** даёт имя службы, путь и время. Шаг четвёртый — сопоставляем время с действиями
пользователя (вход, скачивание файла) и с появлением самого `svc.exe`.

Итог: восстановлен механизм закрепления через службу, с путём, правами и временем установки.
Служба переживает перезагрузку и запускается от SYSTEM — это делает её одним из самых
«удобных» для злоумышленника механизмов.

## Тонкости: svchost и ServiceDll

Отдельный случай — службы, работающие через общий хост `svchost.exe`. Их реальный код лежит
в **DLL**, путь к которой указан в поле `ServiceDll` внутри `Parameters`. Это позволяет
маскироваться: в диспетчере видно «`svchost.exe`», а вредоносный код — в сторонней библиотеке.
Поэтому при разборе обязательно проверяй `ServiceDll` у служб типа `share`/`svchost`:

```
$ reg query "HKLM\SYSTEM\CurrentControlSet\Services\<имя>\Parameters" /v ServiceDll
ServiceDll    REG_EXPAND_SZ    C:\Users\Public\evil.dll
```

Если путь библиотеки нестандартный — это признак перехвата. Дополнительно сверь цифровую
подпись DLL: неподписанная или самоподписанная библиотека в службе — почти наверняка чужой
код.

## Полный прогон и восстановление времени

Полезный порядок работы. Первое — собери все службы и отфильтруй по путям вне `System32`.
Второе — для каждой выпиши `ImagePath`/`ServiceDll`, `Start`, `ObjectName`. Третье — найди
время установки: событие 7045 в журнале System (или 4697 в Security при аудите). Четвёртое —
свяжи с файловыми артефактами: время создания `svc.exe` по MFT, его хеш из AmCache. Пятое —
проверь, запускалась ли служба (журнал System, события запуска служб).

Если журналы ротированы и событие 7045 потеряно, оцени время по метаданным файла и по
`LastWrite` самого ключа реестра. Это менее точно, но позволяет расположить событие на
таймлайне. В отчёте укажи метод оценки времени и его погрешность.

## Что фиксировать в отчёте

Приведи имя службы, путь (`ImagePath`/`ServiceDll`), режим запуска (`Start`), учётную запись
(`ObjectName`) и время установки. Отметь нестандартность пути и отсутствие подписи у файла.
Свяжи службу с найденным образцом (по пути и хешу). Такой отчёт объясняет, почему процесс
переживает перезагрузку и работает с высокими правами, — то есть отвечает на вопрос о
механизме персистентности.

## Драйверы как службы: kernel-mode закрепление

Отдельный и особенно важный случай — службы, которые являются **драйверами ядра**. Они
запускаются в режиме ядра с максимальными привилегиями и описываются той же веткой реестра
`Services`, но с `Type`, указывающим на драйвер (например, `kernel driver`). Вредоносный
драйвер даёт полный контроль над системой и часто используется руткитами для сокрытия
процессов и файлов.

Признаки подозрительного драйвера: файл лежит вне `System32\drivers`, не имеет действительной
подписи, `Start=0` (загрузочный драйвер), необычное имя. Проверь подпись (`sigcheck`) и
сравни путь с ожидаемым. Если драйвер загружается на раннем этапе (`Start=0`) и не подписан,
это серьёзный сигнал: такой код может скрывать своё присутствие от пользовательских
инструментов. В отчёте опиши драйвер, его путь, тип и подпись — это критичная находка.

## Права, дескрипторы и целостность служб

Кроме `ImagePath` и `Start`, у службы есть **дескриптор безопасности** (`Security`), который
определяет, кто может её изменять. Ослабленный дескриптор (например, право на изменение у
обычных пользователей) — распространённая уязвимость для эскалации: пользователь может
подменить `ImagePath` легитимной службы на свой файл и получить SYSTEM. Поэтому при
расследовании смотри не только на «странные» службы, но и на **права доступа** к службам:
если служба от SYSTEM доступна на запись непривилегированному пользователю, это вектор.

Проверять дескрипторы удобно инструментом (`accesschk` из Sysinternals или `sc sdshow`). В
отчёте отметь службы с ослабленными правами и объясни риск. Дополнительно сверь службы с
эталоном: изменение существующей легитимной службы (подмена пути, добавление `ServiceDll`) —
такая же персистентность, как создание новой, но её сложнее заметить, потому что имя службы
знакомое.

## Полный чек-лист по службам

Держи порядок работы. Первое — собери все службы и отфильтруй по путям вне `System32`.
Второе — для каждой выпиши `ImagePath`, `ServiceDll`, `Start`, `Type`, `ObjectName`. Третье —
проверь цифровые подписи файлов. Четвёртое — найди время установки/изменения (7045/4697,
`LastWrite` ключа). Пятое — проверь дескрипторы на предмет ослабленных прав. Шестое — свяжи с
файловыми артефактами (MFT, AmCache) и с журналами запуска. Седьмое — сравни с эталоном
«чистой» системы, чтобы поймать подмену существующих служб.

Такой чек-лист покрывает и создание, и модификацию, и слабые права — три разных способа
использовать службы. В отчёте разложи находки по этим категориям и приведи доказательства
для каждой. Тогда вывод будет полным и не оставит непроверенных путей.

## Итоговый вывод по службам

Службы — второй по частоте механизм закрепления после планировщика. Их сила в правах и
автозапуске: служба может стартовать при загрузке и работать от SYSTEM. Различай три способа
использования: создание новой службы, модификация существующей (подмена `ImagePath` или
`ServiceDll`) и ослабление прав доступа к службе. Для каждого нужен свой признак: нестандартный
путь, изменение знакомой службы, слабый дескриптор. Подтверждай вывод журналом System
(событие 7045) и проверкой подписи файла. В отчёте свяжи службу с найденным образцом и
объясни, почему она переживает перезагрузку и с какими правами работает.

## Практический совет по приоритизации

Служб на типичной машине сотни, и проверять все подряд неэффективно. Приоритизируй так:
сначала службы с `ImagePath` вне `System32` (явная аномалия), затем службы, изменённые
незадолго до инцидента (по `LastWrite` ключа), затем службы с нестандартным `ServiceDll`,
затем службы с ослабленными дескрипторами. Такой порядок быстро выделяет подозрительное,
даже когда служб много. Дополнительно сверь список с эталоном «чистой» установки: всё, что
отличается, — на проверку. В отчёте объясни, почему та или иная служба попала в приоритет, —
это показывает методичность анализа.
