## Вопрос, с которого всё начинается

Ты разбираешь образ с Android-устройства. Раздел `/data` не открывается ни как ext4, ни
как YAFFS. Инструменты молчат, а данные нужны. Файловая система — **F2FS**. Что это,
почему её выбрали для флеш-памяти и как из неё достать содержимое?

## Что такое F2FS

**F2FS (Flash-Friendly File System)** — файловая система, которую Samsung разработала
специально для **флеш-памяти** (NAND). Её включили в ядро Linux в 2012 году, и сегодня
она широко используется в Android-устройствах (разделы `/data`, `/cache`), а также на
SD-картах и во встраиваемых системах. Идея в том, чтобы учитывать природу flash:
запись возможна только целыми блоками после стирания, а «стирается» память крупными
сегментами. F2FS организует данные так, чтобы минимизировать лишние операции.

## Наш пример: userdata.img

Смотрим начало файла и особенно область по смещению **1024 байта (0x400)** — там
находится **суперблок**, «паспорт» файловой системы:

```
$ ls -la
-rw-r--r--  1 student student  8388608 userdata.img
$ xxd -s 1024 -l 16 userdata.img
00000400: 1020 f5f2 0000 0000 0000 0000 0000 0000  ...........
```

Первые четыре байта `10 20 f5 f2` — это магия F2FS в порядке little-endian (само число
`0xF2F52010`). Видишь её — почти наверняка F2FS. Запомни смещение: **суперблок не в
нулевом байте**, а по offset `0x400`, потому что первые 1024 байта раздела занимает
загрузочная область.

## Шаг 1: текстовые метаданные

Как и в других ФС, первый быстрый проход — `strings`:

```
$ strings userdata.img
F2FS superblock: segment=2MB, cp=2
NAT/SIT/SSA present
Android /data volume
RECOVERED: nto{f2fs_s3gm3nt_ch3ckp01nt}
```

Мы видим подтверждение: размер сегмента 2 МБ, два checkpoint, наличие NAT/SIT/SSA —
это всё характерные структуры F2FS. И метку, оставленную в образе.

## Шаг 2: как устроена F2FS

F2FS делит том на **сегменты** (обычно 2 МБ), а сегменты — на блоки. Внутри живут:

| Структура | Назначение | Аналог |
|-----------|------------|--------|
| Superblock | параметры тома | суперблок ext4 |
| Checkpoint (2 шт.) | согласованное состояние | журнал |
| SIT (Segment Info Table) | состояние сегментов | bitmap занятости |
| NAT (Node Address Table) | адреса node-блоков | таблица inode |
| SSA (Summary Area) | сводка блоков сегмента | метаданные сегмента |

Ключевая особенность: F2FS — **log-structured**. Данные пишутся последовательно в
свободные сегменты, а старые освобождаются сборщиком мусора. Два checkpoint страхуют
согласованность: при сбое берётся последний валидный.

## Шаг 3: удалённые файлы — почему их трудно восстановить

В log-structured ФС удаление **не стирает данные сразу**: старая версия файла остаётся в
сегменте до сборки мусора. Но есть проблема: **имена файлов** хранятся в каталоге, а
каталог — тоже в блоках, которые перезаписываются. Поэтому часто можно восстановить
**содержимое** (по сигнатурам в сегментах), но не имя.

Практический подход:

- **`sload.f2fs -f userdata.img`** — «загружает» данные из образа в обычную ФС (по сути
  извлекает сегменты в каталог);
- **`dump.f2fs -i <ino>`** — выгружает конкретный inode;
- **`fsck.f2fs`** — проверка и «починка» метаданных перед извлечением;
- **carving** — если метаданные разбиты, содержимое достают по сигнатурам.

## Шаг 4: где искать данные на Android

Раздел `/data` в F2FS хранит почти всё пользовательское:

- базы приложений (`/data/data/<package>/databases/`);
- профили браузеров и мессенджеров;
- кэши и настройки.

После `sload.f2fs` эти каталоги появляются как обычные, и дальше работают привычные
инструменты — SQLite, grep по конфигам. Важно понимать: F2FS — только «транспорт»; сами
данные извлекаются уже из распакованной ФС.

## Частые ошибки и подводные камни

- **Искать суперблок в байте 0.** Он по offset `0x400`; в первых 1024 байтах — другое.
- **Путать F2FS и ext4.** Android переходит между ними; опознавайте по магии, а не по
  «похожести».
- **Ждать имён удалённых файлов.** В log-structured ФС их часто нет.
- **Забыть про checkpoint.** Если образ снят «грязным», берите последний валидный
  checkpoint, иначе метаданные не сойдутся.
- **Игнорировать сжатие.** Android может использовать сжатие данных на уровне FS; тогда
  `strings` даст мусор, а нужен корректный разбор.

## Мини-практика

Дан `userdata.img`. Опознаём ФС и достаём метку:

```
$ xxd -s 1024 -l 16 userdata.img
00000400: 1020 f5f2 0000 0000 0000 0000 0000 0000  ...........
$ strings userdata.img | grep nto > answer.txt
$ cat answer.txt
RECOVERED: nto{f2fs_s3gm3nt_ch3ckp01nt}
```

Мы подтвердили F2FS по магии `10 20 f5 f2` и вытащили данные. В реальном разборе дальше —
`fsck.f2fs` для проверки и `sload.f2fs` для извлечения дерева файлов.

## Что мы теперь знаем

- F2FS опознаётся по магии `10 20 f5 f2` по offset 1024.
- Том делится на сегменты; есть два checkpoint, NAT, SIT, SSA.
- ФС log-structured: данные живут до сборки мусора, но имена теряются.
- Извлечение: `fsck.f2fs` → `sload.f2fs`/`dump.f2fs`.
- F2FS — частая ФС раздела `/data` на Android.

## Checkpoint и «грязный» образ: как не потерять данные

F2FS хранит два **checkpoint** — снимка согласованного состояния метаданных. Если образ
снят при работающей системе (не «чисто» выключенной), один checkpoint может быть
незавершённым. Правило: **бери последний валидный checkpoint**, а не первый попавшийся.

Как это выглядит на практике:

```
$ xxd -s 1024 -l 8 userdata.img
00000400: 1020 f5f2 0000 0000                    ........
$ fsck.f2fs -f userdata.img
Info: Debug level = 1
Info: Segments per section = 1
Info: Sections per zone = 1
Info: Checkpoint version: 1
Info: Found checkpoint at block 1
```

`fsck.f2fs` сообщает, какой checkpoint принят за основной, и попутно «подчищает»
оборванные узлы. Только после успешной проверки имеет смысл извлекать файлы — иначе
`sload.f2fs` может выдать битое дерево.

## Сборка мусора и окно восстановления

Главная метафора F2FS — **log-structured**: том пишется как журнал, последовательно, в
свободные сегменты. Старые сегменты освобождает **сборщик мусора (GC)**. Из этого
следуют две важные вещи для форензики:

1. **Окно восстановления** — это время между удалением файла и сборкой мусора. Чем
   меньше свободного места и активнее запись, тем быстрее GC перезапишет сегмент.
2. **Данные живут в старых сегментах** даже после удаления — их видно по сигнатурам.

Поэтому сразу после снятия образа фиксируют состояние тома и **не запускают на нём
запись**. Любая запись может ускорить GC и уничтожить улики.

## Node-блоки, NAT и адресация

В F2FS у каждого файла есть **node-блок** (аналог inode), а таблица **NAT** отображает
номер узла на его физический адрес. Это значит, что «номер inode» и «физический блок» —
разные вещи, и при повреждении NAT ссылки рвутся. На практике:

```
$ dump.f2fs -i 2 userdata.img
Info: Debug level = 0
Info: Device: [0] userdata.img
i_ino [0x2] i_nlink [0x1] i_size [0x1000]
i_name [secret.db]
```

Команда `dump.f2fs -i` показывает конкретный inode по номеру. Если номер неизвестен,
его берут из каталога или из checkpoint-таблиц.

## Android и шифрование (FBE)

На современных Android раздел `/data` дополнительно защищён **FBE (File-Based
Encryption)** — шифрованием на уровне файлов. F2FS при этом остаётся «слоем ниже»:
метаданные и имена видны, а содержимое файлов зашифровано. Это меняет стратегию:

| Состояние устройства | Что доступно |
|----------------------|--------------|
| BFU (до первого разблокирования) | только метаданные, содержимое зашифровано |
| AFU (после разблокирования) | ключи в памяти, содержимое читается |

Поэтому для полного разбора нужно знать состояние устройства на момент изъятия: в BFU
даже правильный `sload.f2fs` даст «мусор» из шифротекста, а не открытые файлы.

## Типичные ошибки при извлечении F2FS

Разбор F2FS ломается на предсказуемых местах. Соберём их в один список, чтобы не
наступать на грабли:

- **Извлечение из «грязного» образа без fsck.** Если образ снят при работающей системе,
  метаданные могут быть рассогласованы. Сначала `fsck.f2fs`, потом `sload.f2fs`.
- **Попытка найти имена удалённых файлов.** Каталог в log-structured ФС перезаписывается;
  имена почти всегда теряются, а содержимое — нет.
- **Игнорирование сжатия.** Android включает сжатие данных; тогда `strings` даёт мусор,
  и нужен корректный разбор через f2fs-tools.
- **Путаница с `sload.f2fs` и `dump.f2fs`.** Первый выгружает дерево целиком, второй —
  один inode по номеру. Для «посмотреть один файл» удобнее второй.
- **Работа на образе «на запись».** Любая запись запускает сборщик мусора и уничтожает
  старые сегменты. Образ — только для чтения.

Ещё один нюанс — **размер сегмента**. Он задаётся при создании тома и обычно равен 2 МБ,
но бывает и другим. Если инструмент ошибается с размером, сегменты «съезжают», и данные
читаются неверно. Проверяй параметр `segment` в суперблоке перед извлечением.

Наконец, помни про порядок слоёв: F2FS → (опционально) FBE-шифрование → файлы
приложений. Чтобы получить открытый SQLite-файл, нужно снять оба слоя: сначала
извлечь ФС, затем — если включён FBE — расшифровать данные, имея ключи из состояния AFU.

## Куда дальше

Дальше возьмём **SquashFS** — сжатую read-only ФС прошивок и initramfs. А пока главное
запомни: **F2FS ищи по магии по offset 0x400, а не в начале файла**.

## Где пригодится

- **CTF Forensics:** Android-образы и flash-дампы.
- **Mobile forensics:** извлечение данных из раздела `/data`.
- **DFIR:** разбор встраиваемых устройств.
- **Data recovery:** восстановление содержимого flash-носителей.
