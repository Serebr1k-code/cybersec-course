## Вопрос, с которого всё начинается

В умном доме/офисе десятки устройств: датчики, камеры, хабы. Одно из них
скомпрометировано. Где смотреть? IoT-форензика — это работа с маленькими Linux-системами
и их привязкой к облаку.

## Наш пример: умная розетка

## Шаг 1: что внутри

Типичное IoT-устройство: SoC (ARM/MIPS), флеш (SPI NAND), Wi-Fi, минимальный Linux
или RTOS. Данных мало — но они есть.

```
$ binwalk -e device_firmware.bin
$ ls _device_firmware.bin.extracted/squashfs-root/
bin  etc  lib  usr
```

`binwalk` извлёк корневую ФС. Внутри — конфиги, скрипты, ключи.

## Шаг 2: локальные артефакты

- **конфиг Wi-Fi** (SSID, пароль);
- **токены облака** (привязка к аккаунту);
- **логи** (короткие, во флеше);
- **сертификаты** (для TLS к облаку).

```
$ grep -riE 'token|password|ssid' squashfs-root/etc/ | head
```

Часто токены лежат **в открытом виде** — это ключ к облачному аккаунту.

## Шаг 3: сетевые следы

IoT говорит по MQTT/CoAP/HTTP. Дамп трафика показывает:

- брокер/сервер;
- топики;
- команды.

```
$ tshark -r iot.pcap -Y 'mqtt' -T fields -e mqtt.topic | sort -u | head
```

## Шаг 4: хаб как точка сбора

Умный хаб (Hubitat/Home Assistant/SmartThings) агрегирует устройства и **хранит
логи**:

```
$ sqlite3 homeassistant.db 'SELECT * FROM states LIMIT 3;'
```

Это лучший источник: одна точка со всей историей.

## Шаг 5: облако

Производитель хранит данные в облаке. Если есть доступ к аккаунту — там история,
события, записи. Иначе — только локальные остатки.

## Что мы теперь знаем

- IoT — маленькие Linux/RTOS-устройства.
- `binwalk` извлекает ФС прошивки.
- Токены/пароли часто в открытом виде.
- Трафик — MQTT/CoAP/HTTP.
- Хаб и облако — точки сбора истории.

## Если не сработало

- Флеш зашифрована? Нужен дамп с работающего устройства.
- Нет доступа к облаку? Работай с хабом и трафиком.
- Устройство простое (RTOS)? Данных минимум — смотри сеть.

## Разбор прошивки IoT

Прошивку снимают либо с флеш-чипа программатором, либо из обновления с сайта
производителя. Разбираем извлечённую файловую систему:

```
$ binwalk -e device_firmware.bin
$ ls _device_firmware.bin.extracted/squashfs-root/
bin  etc  lib  sbin  usr  var  www
$ cat _device_firmware.bin.extracted/squashfs-root/etc/passwd
root:x:0:0:root:/root:/bin/sh
admin:$1$abc$...:0:0:admin:/:/bin/sh
```

Прошивка даёт всё сразу: учётки, скрипты запуска, конфиги, ключи. Пароль
`admin` часто хеширован слабым DES-crypt — его подбирают за секунды.

## Таблица: артефакты IoT

| Артефакт | Где | Что даёт |
|---|---|---|
| Учётные записи | `/etc/passwd`, `/etc/shadow` | вход в устройство |
| Wi-Fi конфиг | `/etc/config/wireless` | SSID и пароль |
| Токен облака | `/etc/config/*`, NVRAM | доступ к аккаунту |
| Сертификаты | `/etc/ssl/` | ключ для TLS к облаку |
| Скрипты запуска | `/etc/init.d/` | что и как стартует |
| Веб-интерфейс | `/www/` | уязвимости, API |
| Логи | `/var/log/`, NVRAM | события устройства |

Токен облака — самый ценный артефакт: он открывает аккаунт, к которому
привязаны все устройства пользователя, а не только это.

## Пример: извлечение токена облака

Ищем токены и ключи в конфигах:

```
$ grep -riE 'token|api_key|secret|password' squashfs-root/etc/ | head
squashfs-root/etc/config/cloud: option token 'eyJhbGciOiJIUzI1NiIs...'
```

JWT-токен в открытом виде — прямой путь в облачный аккаунт. Проверь его срок
жизни и права (декодировав payload):

```
$ echo 'eyJhbGciOiJIUzI1NiIs...' | cut -d. -f2 | base64 -d 2>/dev/null
{"sub":"user_12345","exp":1770000000,"scope":"device:control"}
```

## Хаб и облако

Умный хаб агрегирует устройства и хранит историю — это лучший источник:

```
$ sqlite3 homeassistant.db "SELECT entity_id, state, last_changed FROM states
    ORDER BY last_changed DESC LIMIT 3;"
light.kitchen|on|2026-03-11 03:41:00
```

Облако производителя хранит события и записи камер. Если есть доступ к
аккаунту (через украденный токен), история доступна за месяцы. Без него
остаются только локальные остатки на самом устройстве.

## Если сработало

Нашёл токен/пароль — оцени радиус и зафиксируй:

1. Проверь токен: срок жизни, права, к какому аккаунту привязан.
2. Выгрузи конфиги и логи устройства с хешами.
3. Проверь хаб — он даёт историю по всем устройствам.
4. Определи, к каким ещё устройствам даёт доступ найденный токен.
5. Ротируй скомпрометированные ключи через веб-интерфейс/облако.

Один токен часто управляет всеми устройствами аккаунта — не ограничивайся
одним «умным» устройством при оценке ущерба.

## Практика: разбор прошивки IoT-устройства

IoT-устройства — это маленькие Linux-машины с флеш-памятью. Прошивку снимают либо с самой
микросхемы (SPI-программатором), либо из OTA-обновления, либо из облака производителя.
Разбор начинается с определения структуры:

```
$ binwalk firmware.bin
DECIMAL       HEXADECIMAL     DESCRIPTION
0             0x0             uImage header
65536         0x10000         Squashfs filesystem, little endian
$ binwalk -e firmware.bin            # распаковка
$ ls squashfs-root/
bin  etc  lib  sbin  usr  www
```

Распакованная файловая система даёт всё: конфиги, скрипты автозапуска, бинарники,
**зашитые пароли и токены**. Часто именно в `etc/` лежат ключи доступа к облаку — и это
прямая улика компрометации, если устройство утекло.

## Таблица: артефакты IoT-форензики

| Артефакт | Где искать | Что показывает |
|---|---|---|
| Прошивка | SPI-флеш, OTA-кэш | версия, зашитые секреты |
| Конфиги | `etc/config`, `/var` | учётки, токены облака |
| Логи устройства | ring buffer, syslog | события, подключения |
| Локальные БД | SQLite на флеш | телеметрия, история |
| Сетевые следы | `tcpdump` на хабе/роутере | куда устройство ходило |
| Мобильное приложение | APK/IPA | API-ключи, эндпоинты |

Важная особенность: у IoT почти нет «пользовательских файлов», зато много **телеметрии** и
**облачных токенов**. Поэтому расследование обычно идёт от устройства к облаку.

## Пример: извлечение токена облака из прошивки

Типичная находка — токен, зашитый в прошивку «намертво» и одинаковый на всех устройствах
партии:

```
$ grep -rEo '"(token|api_key|secret)":\s*"[^"]+"' squashfs-root/etc/
squashfs-root/etc/cloud.conf:"token":"eyJhbGciOiJIUzI1NiIs..."
$ grep -rE 'mqtt|https://' squashfs-root/etc/ | head
/etc/cloud.conf:broker=mqtt://iot.example.com:1883
/etc/cloud.conf:api=https://api.example.com/v2
```

Дальше проверяем, ограничен ли токен: если он даёт доступ ко всем устройствам партии —
это критическая утечка. В форензике такой токен доказывает **как** устройство общалось с
облаком и **какие данные** могло туда передавать (а для атакующего — это путь к
компрометации всей партии).

## Хаб и облако: где заканчиваются локальные следы

Умный дом обычно устроен так: **устройства → хаб (или роутер) → облако**. Локально на
устройстве почти нет истории, зато хаб ведёт журнал событий, а облако — историю команд и
доступов. Поэтому сбор артефактов идёт по трём уровням:

1. **Устройство** — прошивка, локальные логи, телеметрия в ring buffer.
2. **Хаб/шлюз** — журнал событий, список устройств, локальная БД (часто SQLite).
3. **Облако** — история команд, список пользователей, токены, время доступа.

Доказательство строится **сверкой** уровней: команда в облаке → запись в хабе → изменение
состояния устройства. Совпадение по времени делает вывод устойчивым.

## Ограничения и подводные камни

- **Логи в кольцевом буфере затираются.** Устройство хранит только последние N записей;
  если его не выключить вовремя, следы исчезнут.
- **Энергонезависимая память ограничена.** Частые записи изнашивают флеш, поэтому
  прошивки пишут логи редко — истории может просто не быть.
- **Облако под контролем вендора.** Доступ к журналам часто только через API
  производителя; без него остаётся лишь локальная часть картины.
- **Прошивку можно обновить «поверх»** — OTA-обновление затирает старую версию, поэтому
  снимай образ **до** любых сетевых операций с устройством.

## Снятие локальной БД хаба

Хабы умного дома (Home Assistant, Hubitat, Zigbee-шлюзы) хранят историю событий в
**SQLite**. Это самый ценный локальный артефакт: в нём — кто и когда управлял устройствами.

```
$ sqlite3 home-assistant_v2.db ".tables"
states  events  recorder_runs  statistics
$ sqlite3 home-assistant_v2.db \
    "SELECT last_updated, entity_id, state FROM states \
     WHERE entity_id LIKE 'lock.%' ORDER BY last_updated DESC LIMIT 5;"
2024-11-03 22:11:04  lock.front_door  unlocked
2024-11-03 02:03:19  lock.front_door  locked
```

Из вывода видно ночное открытие замка — событие, которое владелец не совершал. Дальше
сопоставляем время с журналом облака и с сетевыми подключениями: если команда пришла из
облака с незнакомого аккаунта, картина сходится. Так локальная БД превращается из
«телеметрии» в **улику**.

## Мобильное приложение как источник артефактов

У многих IoT-устройств есть мобильное приложение — и это ещё один след. В APK/IPA остаются
эндпоинты API, ключи и учётные данные:

```
$ apktool d app.apk -o app/
$ grep -rEo 'https://[a-z0-9./-]+' app/res app/smali | sort -u | head
https://api.example.com/v2/devices
https://api.example.com/v2/auth/login
```

Найденные эндпоинты связывают устройство, хаб и облако в единую картину: по ним видно,
**куда** уходили данные и **какие** операции возможны. В расследовании это помогает понять
маршрут команды и найти, где ещё остались журналы.

## Энергонезависимые артефакты и затирание логов

IoT-устройства пишут логи в энергонезависимую память (NAND/NOR), но берегут ресурс, поэтому
историю ограничивают или пишут только ошибки. Практические следствия:

- **Кольцевой буфер** хранит лишь последние события; после N записей старое затирается.
- **Частые записи** изнашивают флеш, поэтому производители снижают детализацию логов.
- **После перезагрузки** часть логов может потеряться, если они хранились в RAM.

Отсюда правило: не перезагружай устройство и не обновляй прошивку до снятия артефактов.
Если есть подозрение на компрометацию, снимай дамп флеш-памяти первым делом.
