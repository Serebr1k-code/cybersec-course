## Вопрос, с которого всё начинается

На Mac файл изменён, а нужна его прежняя версия. APFS — copy-on-write ФС, поэтому старые
версии могут оставаться в **снимках** (snapshots). Разберём, как их найти и смонтировать.

## Наш пример: том APFS

## Шаг 1: что такое снимок APFS

Снимок — это «замороженное» состояние тома: все блоки на момент создания. Благодаря
copy-on-write, снимок занимает мало места, пока данные не меняются.

```
$ diskutil apfs listSnapshots /dev/disk1s1
Snapshots for disk1s1:
com.apple.TimeMachine.2026-01-14-030000.local
```

## Шаг 2: монтируем снимок

На macOS:

```
$ mkdir /tmp/snap
$ mount_apfs -s com.apple.TimeMachine.2026-01-14-030000.local /dev/disk1s1 /tmp/snap
```

На Linux/Windows (по образу) — `apfs-fuse`:

```
$ apfs-fuse -s 1 disk.img /mnt/apfs
```

`-s` указывает номер снимка.

## Шаг 3: достаём старые версии

В смонтированном снимке видны файлы на тот момент:

```
$ ls /tmp/snap/Users/user/Documents/
old_report.pdf
```

Файл, удалённый сейчас, в снимке ещё есть.

## Шаг 4: сравнение

```
$ diff /tmp/snap/Users/user/.bash_history ~/.bash_history
```

Разница показывает изменения — то, что дописал или удалил злоумышленник.

## Шаг 5: что искать

- удалённые файлы;
- прежние версии документов;
- историю правок;
- доказательства времени.

## Шаг 6: как APFS хранит снимки

APFS — copy-on-write: при изменении блока новый пишется в свободное место, а старый остаётся в снимке. Поэтому снимок — это набор ссылок на «прежние» блоки. Их можно перечислить:

```
$ apfsutil list-snapshots disk.img
```

Метаданные снимка включают имя, время создания и идентификатор.

## Шаг 7: монтирование на Linux

`apfs-fuse` монтирует и живой том, и снимок:

```
$ apfs-fuse -s 2 disk.img /mnt/apfs
$ ls /mnt/apfs
```

`-s N` — номер снимка (0 — текущий том). После монтирования файлы читаются как обычные.

## Шаг 8: восстановление удалённого

Удалённый файл в текущем томе недоступен, но в снимке — есть:

```
$ find /mnt/apfs/Users/ivan -name '*.docx' -newermt '2026-01-01'
```

Копируем его из снимка и сравниваем с текущей версией — видим, что изменили.

## Шаг 9: снимок как доказательство времени

Снимок фиксирует состояние на конкретный момент. Это позволяет утверждать: «файл в таком виде существовал 14 января в 03:00». В отличие от mtime, который можно подделать, снимок создан самой системой.

## Шаг 10: что искать

- удалённые файлы;
- прежние версии документов и конфигов;
- историю `.bash_history`/логов;
- время существования файла;
- расхождения между снимками.

## Шаг 11: локальные снимки и Time Machine

На macOS снимки бывают двух родов: локальные (создаёт система при обновлении/резервном копировании) и Time Machine:

```
$ diskutil apfs listSnapshots /dev/disk1s1
com.apple.TimeMachine.2026-01-14-030000.local
com.apple.os.update-...
```

Локальный снимок живёт, пока системе нужно место, поэтому может исчезнуть. Если инцидент свежий — снимок ещё на месте и содержит «вчерашнее» состояние.

## Шаг 12: снимки на зашифрованном томе

Если том зашифрован FileVault, снимки тоже зашифрованы. Но их можно смонтировать, если есть ключ или том разблокирован в момент снятия образа. При монтировании образа в среде, где том не разблокирован, снимки будут недоступны — это важное ограничение при работе с копией диска.

## Шаг 13: сравнение нескольких снимков

Если снимков несколько, их можно сравнивать между собой — так восстанавливается эволюция файла:

```
$ diff -r /mnt/snap1/Users/ivan/Docs /mnt/snap2/Users/ivan/Docs
```

Разница показывает, что менялось между двумя моментами. Это надёжнее, чем доверять mtime: снимок создан системой, а не приложением.

## Шаг 14: практический кейс

Сценарий: подозревают, что перед увольнением сотрудник удалил документы. Действия:

1. перечислить снимки (`diskutil`/`apfsutil`);
2. смонтировать самый ранний и самый поздний снимок;
3. найти в снимке файлы, которых нет в текущем томе;
4. скопировать и сравнить версии;
5. зафиксировать время снимков как границы существования файла.

Результат — доказательство, что документы существовали и были удалены.

## Практика: возвращаем удалённый отчёт

Дано: подозревают удаление финансового отчёта. Работаем с образом APFS.

Перечисляем снимки:

```
$ apfsutil list-snapshots disk.img
Snapshots:
  com.apple.TimeMachine.2026-02-09-040000.local
  com.apple.TimeMachine.2026-02-08-040000.local
```

Есть два снимка. Монтируем более ранний:

```
$ mkdir /mnt/s1 && apfs-fuse -s 1 disk.img /mnt/s1
```

Ищем файл:

```
$ find /mnt/s1/Users/ivan/Documents -iname '*report*'
/mnt/s1/Users/ivan/Documents/q4_report.xlsx
```

Файл есть в снимке. В текущем томе его нет — значит, удалён. Копируем и смотрим метаданные:

```
$ cp /mnt/s1/Users/ivan/Documents/q4_report.xlsx /evidence/
$ stat /evidence/q4_report.xlsx
Modify: 2026-02-08 22:14:03
```

Теперь сравним с более поздним снимком (если файл ещё жил):

```
$ apfs-fuse -s 2 disk.img /mnt/s2
$ diff /mnt/s1/Users/ivan/Documents/q4_report.xlsx /mnt/s2/Users/ivan/Documents/q4_report.xlsx
```

Если различий нет — между снимками файл не менялся, а после — исчез. Фиксируем границы: файл существовал как минимум 8 февраля и отсутствует сейчас.

## Что важно

- Снимки дают несколько точек во времени.
- `apfs-fuse -s N` монтирует конкретный снимок.
- Отсутствие файла в текущем томе + наличие в снимке = факт удаления.
- Сравнение снимков датирует изменение.

## Подводные камни

APFS-снимки — мощный, но капризный инструмент.

**Снимки удаляются автоматически.** Локальные снимки (`.local`) живут, пока системе нужно место; при нехватке диска macOS их чистит. Поэтому при свежем инциденте снимай образ **немедленно** — снимок может исчезнуть.

**Порядок снимков.** Номер в `apfs-fuse -s N` — это позиция, а не дата. Нумерация зависит от инструмента, поэтому всегда сверяй дату снимка с его именем, прежде чем делать выводы.

**Шифрование.** На томе с FileVault снимки зашифрованы. Без ключа или разблокированного тома их не прочитать. Это ограничение среды, а не дефект образа.

**Метрики времени.** У файлов в снимке те же mtime, что были на момент снятия. Не путай «время снимка» (когда сделана копия) и «время файла» (когда он менялся) — это разные вещи в отчёте.

**apfs-fuse не всесилен.** Некоторые сжатые/шифрованные файлы могут не открываться. Для полноты иногда нужен коммерческий инструмент (например, из DFIR-набора).

Вывод: снимок — это точка во времени; фиксируй и время снимка, и метаданные файлов, и не тяни со снятием образа.

## Что запомнить по снимкам APFS

Коротко о главном. APFS — copy-on-write, поэтому старые версии файлов остаются в снимках, а не перезаписываются. Снимок фиксирует состояние тома на конкретный момент, и это независимое от приложений доказательство времени. Монтировать снимки можно через `mount_apfs` (macOS) или `apfs-fuse -s N` (Linux/по образу). Если файл «пропал», сначала ищи его в снимке, а затем сравнивай версии между снимками. Помни ограничения: локальные снимки могут исчезнуть при нехватке места, а на FileVault-томе они зашифрованы. Не путай время снимка и mtime файла. Связка «copy-on-write → снимок → сравнение версий» — ключ к восстановлению удалённого на macOS.

- APFS copy-on-write хранит старые версии в снимках.
- `diskutil`/`mount_apfs`/`apfs-fuse` дают доступ.
- В снимке видны удалённые файлы.
- Сравнение выявляет изменения.
- Снимок — надёжное доказательство.

- APFS copy-on-write оставляет старые блоки в снимках.
- `apfs-fuse -s N` монтирует конкретный снимок.
- Удалённые файлы доступны из снимка.
- Сравнение версий выявляет правки.
- Снимок — независимое доказательство времени.

- Локальные снимки (`.local`) могут исчезать — работай быстро.
- На FileVault-томах снимки тоже зашифрованы.
- Сравнение нескольких снимков восстанавливает эволюцию файла.
- Кейс: удалённые документы находятся в снимке и датируются.
