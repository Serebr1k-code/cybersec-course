LVM (Logical Volume Manager) — слой абстракции между физическими разделами и файловыми системами в Linux. Он вклинивается ровно там, где начинается ФС: на «разделе» лежит не ext4, а **Physical Volume (PV)**; поверх PV — **Volume Group (VG)**, внутри которой создаются **Logical Volume (LV)**, а уже на LV — ФС. Для форензика это критично: если смотреть на образ как на обычный диск, вы увидите «мусор» вместо файловой системы, потому что ФС начинается внутри LV, а его смещение задаётся метаданными LVM.

## Три уровня абстракции

| Уровень | Что это | Аналог |
|---------|---------|--------|
| PV (Physical Volume) | физический том: раздел или целый диск | «кирпич» |
| VG (Volume Group) | пул из одного и более PV | «склад кирпичей» |
| LV (Logical Volume) | том внутри VG, где живёт ФС | «полка» |

Ключевые понятия:
- **PE (Physical Extent)** — единица аллокации PV (обычно 4 МиБ).
- **LE (Logical Extent)** — единица LV, мапится на PE.
- **Metadata** — текстовое описание конфигурации VG/LV, лежит в начале каждого PV (в нескольких копиях).

## Метаданные Physical Volume

PV начинается с **label** — сектор 1 (offset 512 байт). Структура:

| Смещение | Размер | Поле |
|---------:|-------:|------|
| 0x00 | 8 | `LABELONE` |
| 0x08 | 8 | sector number (1) |
| 0x10 | 4 | CRC |
| 0x14 | 4 | offset to data (обычно 32) |
| 0x18 | 8 | type `LVM2 001` |
| 0x20 | — | pv_header (uuid, device size, list of data areas, metadata areas) |

Сразу после label идут **metadata areas**: текстовая копия конфигурации VG в формате LVM2. В ней перечислены PV, их PE, LV и **карта LE→PE** (в каком порядке extents складываются в LV). Именно эта карта нужна, чтобы собрать логический том.

```bash
# Найти метаданные PV
xxd -s 512 -l 64 disk.img
# ищем "LABELONE" и "LVM2 001"
# Текстовая конфигурация (читаемый ASCII) начинается примерно с offset 0x1000
strings -n 6 -t x disk.img | grep -i -E 'LVM2|vg_name|lv_name' | head
```

## Сборка тома из образа

Способы (от простого к ручному):

```bash
# 1) Через loop-устройство + vgscan/vgchange
sudo losetup --find --show --partscan disk.img
# допустим, появился /dev/loop0p2 (PV)
sudo pvscan
sudo vgscan
sudo vgchange -ay          # активировать все VG
ls /dev/mapper/           # появятся vg-lv
sudo mount -o ro /dev/mapper/vg-lv /mnt/lvm

# 2) Восстановить конфигурацию из метаданных образа
sudo losetup -fP disk.img
sudo pvscan --cache
vgcfgrestore -f /etc/lvm/backup/vg vg   # если есть бэкап

# 3) Ручной расчёт смещения LV (когда авто не сработало)
#    Нужно: начало data area PV (offset в секторах) + (PE_index * PE_size)
```

Ручной путь: из метаданных вы берёте `pe_start` (сектор начала PE на PV), размер PE (`pe_size`, обычно 8192 секторов = 4 МиБ) и карту LV→PE. Тогда для LV с одним сегментом:

```bash
# LV data offset (байты) = partition_offset + pe_start*512 + PE_index*pe_size*512
# PE_index для первого extent обычно 0
sudo mount -o ro,loop,offset=$((PART_OFF + 2048*512 + 0*8192*512)) disk.img /mnt
```

## Разобранный пример: LVM-образ

```bash
$ mmls disk.img
      Slot      Start        End          Length       Description
      02:  00:00   0000002048   000000206847 000000202752  Linux LVM (0x8e)
$ xxd -s $((2048*512+512)) -l 32 disk.img
... 4c 41 42 45 4c 4f 4e 45 ... 4c 56 4d 32 20 30 30 31   LABELONE...LVM2 001
$ sudo losetup -fP disk.img
$ sudo pvscan
  PV /dev/loop0p1   VG vg0   lvm2 [100.00 GiB / 0    free]
$ sudo vgchange -ay
  1 logical volume(s) in volume group "vg0" now active
$ ls /dev/mapper/
vg0-root
$ sudo mount -o ro /dev/mapper/vg0-root /mnt/lvm
$ ls /mnt/lvm
bin  boot  etc  home  root  ...
```

## Краевые случаи и подводные камни

- **`LABELONE` в секторе 1, не 0.** Сектор 0 намеренно оставлен пустым (защита от старых инструментов).
- **Несколько PV в VG.** LV может «растягиваться» через несколько дисков; тогда PE берутся с разных PV — нужны все образы.
- **Снапшоты.** LVM snapshot — отдельный LV с copy-on-write; в метаданных он помечен как snapshot и ссылается на origin. Данные origin «на момент» снапшота — ценный источник.
- **Thin provisioning.** В thin-pool карта аллокации сложнее; PE-маппинг из метаданных не тривиален.
- **Не активируйте VG на продакшене.** `vgchange -ay` на боевом сервере поднимет тома; для анализа используйте образ и `-o ro`.
- **`pvscan` требует root.** Loop-устройства и device-mapper — привилегированные операции.
- **Повреждённые метаданные.** Копии метаданных дублируются в начале и (если есть) в конце PV; повреждённую можно восстановить из второй копии или из `/etc/lvm/backup`.
- **Смещение раздела.** `pe_start` отсчитывается от начала **PV**, а не образа; не забудьте добавить offset раздела.
- **LUKS поверх LVM и наоборот.** Бывает и `LVM → LUKS → ФС`, и `LUKS → LVM`; слой нужно снимать в правильном порядке.

## Восстановление конфигурации LVM вручную

Когда автосборка (`pvscan`/`vgchange`) не срабатывает — например, в образе один из PV повреждён или метаданные не читаются, — конфигурацию восстанавливают из текстовых метаданных. Они лежат сразу после label в каждом PV и выглядят как обычный текст LVM2:

```bash
# Найти текстовую конфигурацию
strings -n 6 -t d disk.img | sed -n '/vg0 {/,/}/p' | head -60
```

Внутри будут секции:

- `physical_volumes { pv0 { ... pe_start = 2048 ... pe_count = 25599 ... } }`
- `logical_volumes { root { ... segment_count = 1 ... segment1 { start_extent = 0 extent_count = 25599 ... } } }`

`pe_start` — первый сектор области данных PV (часто 2048 = 1 МиБ). `extent_count` × `extent_size` даёт размер LV. Если LV не фрагментирован и состоит из одного сегмента, его данные начинаются с `pe_start` и идут непрерывно — можно монтировать напрямую по offset:

```bash
# offset LV (байты) = offset_раздела_в_образе + pe_start*512
sudo mount -o ro,loop,offset=$((2048*512 + 2048*512)) disk.img /mnt/lv
```

## Снапшоты и thin-provisioning

LVM-снапшот — это COW-том: при изменении блока в origin его старая версия копируется в снапшот. Для форензика это золото: снапшот хранит **состояние данных на момент создания**. Признаки в метаданных: `status = ["READ", "WRITE", "VISIBLE"]` у origin и `status = ["READ", "WRITE", "VISIBLE", "SNAPSHOT"]` + `origin = "vg/origin"` у снапшота.

Thin provisioning (`thin-pool`, `thin`) хранит блоки на общем пуле с тонкой аллокацией; карта `thin_map` в метаданных связывает виртуальные блоки LV с физическими блоками пула. Разбор сложнее, но `thin_dump` из пакета `thin-provisioning-tools` умеет выгрузить карту.

```bash
# Если доступен thin-pool
thin_dump --format xml /dev/mapper/vg-pool > pool.xml
thin_ls /dev/mapper/vg-pool
```

## Что делать при нескольких PV

Если VG собран из нескольких физических дисков, для сборки нужны **все** образы. Порядок:

1. Определить UUID каждого PV (`pvscan` или метаданные).
2. Проверить, что `pe_count` каждого PV покрывает `extent_count` LV.
3. Подключить все PV как loop-устройства.
4. `vgscan`/`vgchange -ay` соберёт VG целиком.

Если один диск отсутствует, LV с данным, размазанными по нему, будет читаться с «дырами» (в месте отсутствующего PV). Иногда это допустимо — недостающие PE заменяются нулями, но для целостности ФС может быть критично.

## Типичные ошибки

- **Активация VG на живой системе.** `vgchange -ay` поднимет тома и ФС может быть смонтирована/изменена — только изолированная среда и образ.
- **Путаница offset раздела и PV.** `pe_start` отсчитывается от начала PV; к нему нужно добавить смещение раздела в образе.
- **Один PE ≠ один LV.** LV может начинаться не с нулевого PE и занимать лишь часть пула.
- **Thin snapshot** выглядит как обычный LV, но данные подтягиваются из пула — не ищите их на PV.
- **Забыть про слой LUKS.** Если поверх LV лежит LUKS, монтирование LV даст шифротекст; снимайте шифр раньше.
- **Метаданные в двух местах.** Копия метаданных может быть в начале и в конце PV; повреждённую берут из второй копии.

## Что дальше / решение

1. `mmls` — найти раздел с типом Linux LVM (0x8e).
2. `xxd` на секторе 1 — подтвердить `LABELONE`/`LVM2 001`.
3. `losetup -fP` + `pvscan`/`vgscan`/`vgchange -ay` — поднять VG и LV.
4. `mount -o ro /dev/mapper/...` — читать ФС.
5. Не сработало — разобрать метаданные вручную и вычислить offset LV.

Дальше — `forensics-disk-encryption` (если поверх LV лежит LUKS) и `forensics-vdisk-formats`, если образ — это виртуальный диск ВМ.
