## Вопрос, с которого всё начинается

С сервера Linux сняли образ диска `disk.img`. Открываешь его — а внутри «мусор» вместо знакомой файловой системы. Ни ext4, ни XFS не опознаются. Что происходит?

Причина в том, что между диском и файловой системой стоит прослойка — **LVM** (Logical Volume Manager, менеджер логических томов). Файловая система лежит не на «разделе», а внутри логического тома, и чтобы добраться до неё, этот том надо сначала собрать. Разберём образ и смонтируем его содержимое.

## Наш пример: `disk.img` с LVM

Смотрим карту разделов:

```bash
$ mmls disk.img
       Slot      Start        End          Length       Description
      02:  00:00   0000002048   000000206847 000000202752  Linux LVM (0x8e)
```

Тип раздела `Linux LVM (0x8e)` — прямой указатель на LVM. Файловой системы на разделе нет: вместо неё лежит **Physical Volume** (PV) — «физический том», кирпич, из которого LVM строит свою конструкцию.

## Шаг 1: понимаем три уровня LVM

Чтобы не запутаться, держим в голове простую аналогию:

| Уровень | Что это | Аналог |
|---------|---------|--------|
| PV (Physical Volume) | раздел или диск, отданный под LVM | кирпич |
| VG (Volume Group) | пул из одного или нескольких PV | склад кирпичей |
| LV (Logical Volume) | том внутри VG, где живёт файловая система | полка |

Файловая система находится на самом верхнем уровне — на **LV**. Аналог в мире не-LVM: раздел → файловая система. Здесь между ними два дополнительных слоя.

## Шаг 2: подтверждаем PV

Проверяем, что раздел действительно PV. Метка PV лежит в **секторе 1** (не 0 — первый сектор намеренно оставлен пустым, чтобы старые инструменты не приняли том за что-то своё):

```bash
$ xxd -s $((2048*512+512)) -l 32 disk.img
... 4c 41 42 45 4c 4f 4e 45 ... 4c 56 4d 32 20 30 30 31
    L  A  B  E  L  O  N  E      L  V  M  2     0  0  1
```

Видим `LABELONE` и тип `LVM2 001`. Сразу за меткой LVM хранит **метаданные** — текстовое описание конфигурации: какие PV входят в VG, какие LV созданы и как их блоки разложены по PV. Именно эта карта позволит собрать том.

## Шаг 3: собираем том (автоматически)

Самый простой путь — подключить образ как loop-устройство (виртуальный «диск» из файла) и дать LVM самому найти конфигурацию:

```bash
$ sudo losetup -fP disk.img
$ sudo pvscan
  PV /dev/loop0p1   VG vg0   lvm2 [100.00 GiB / 0    free]
$ sudo vgchange -ay
  1 logical volume(s) in volume group "vg0" now active
$ ls /dev/mapper/
vg0-root
```

`pvscan` нашёл физический том (`/dev/loop0p1`), принадлежащий группе `vg0`. `vgchange -ay` активировала тома группы, и в `/dev/mapper/` появился логический том `vg0-root`. Теперь это обычный блочный том — монтируем его только для чтения:

```bash
$ sudo mount -o ro /dev/mapper/vg0-root /mnt/lvm
$ ls /mnt/lvm
bin  boot  etc  home  root  ...
```

Вот и файловая система. Флаг `-o ro` (read-only) обязателен: мы работаем с уликой, её нельзя менять.

## Шаг 4: собираем вручную, если авто не сработало

Иногда `pvscan` не справляется — например, метаданные повреждены или в образе не все PV. Тогда смещение LV вычисляют по метаданным. Разбираем их из текстовой копии:

```bash
$ strings -n 6 disk.img | grep -E 'pe_start|extent_count|pe_count' | head
pe_start = 2048
pe_count = 25599
extent_count = 25599
```

`pe_start` — номер первого сектора области данных на PV (здесь 2048, то есть 1 МиБ). Если LV не фрагментирован и состоит из одного сегмента, его данные начинаются ровно с `pe_start`:

```bash
# offset LV = offset_раздела + pe_start*512
$ sudo mount -o ro,loop,offset=$((2048*512 + 2048*512)) disk.img /mnt/lv
```

Ключевая тонкость: `pe_start` отсчитывается от начала **PV**, а не образа, поэтому к нему прибавляют смещение раздела.

## Шаг 5: снапшоты — отдельная ценность

LVM умеет делать **снапшоты** — снимки тома на момент времени. Технически снапшот — отдельный LV с механизмом copy-on-write: когда блок в оригинале меняется, его старая версия копируется в снапшот. Для расследования это золото: снапшот хранит **состояние данных до изменений**, то есть может содержать файлы, которые позже удалили.

В метаданных снапшот помечен ссылкой на оригинал (`origin = "vg0/root"`). Если в образе есть снапшот, обязательно проверьте и его.

## Полный разбор: собираем том из сырого образа

Прогоним сборку LVM в один сценарий.

1. **Понимаем три уровня:** **PV** (Physical Volume) — физический том, **VG** (Volume Group) — пул из PV, **LV** (Logical Volume) — «раздел» внутри VG.
2. **Подтверждаем PV:**
   ```bash
   $ pvscan --cache disk.img
   $ pvs -o pv_name,vg_name,pv_size
   ```
3. **Активируем автоматически:** `vgscan` + `vgchange -ay` — ядро соберёт LV из метаданных.
4. **Вручную, если авто не сработало:** метаданные лежат в начале PV (`pv_header`), смещения — в `pvs --segments`.
5. **Снапшоты:** LVM-снапшот — замороженное состояние тома на момент; ценен для анализа «как было».

Ключ: LVM хранит метаданные на самом диске, поэтому том можно собрать из сырого образа без исходной системы.

## Шпаргалка LVM

| Объект | Команда | Что даёт |
|--------|---------|----------|
| PV | `pvs` / `pvdisplay` | физические тома |
| VG | `vgs` / `vgdisplay` | пул, размер |
| LV | `lvs` / `lvdisplay` | логические тома |
| Активация | `vgchange -ay` | собрать и подключить |
| Снапшот | `lvcreate -s` | состояние на момент |

Метаданные — текстовые копии в `/etc/lvm/backup`; полезно, если диск ещё жив.

## Частые вопросы

**`vgchange` не видит том.** Сначала `pvscan --cache`, затем `vgscan`; убедитесь, что образ доступен как block device (`losetup`).

**Почему том «missing»?** Не хватает одного PV из VG — соберите все части.

**Снапшот теряет данные?** Он растёт по мере изменений; при переполнении «ломается» — анализируйте своевременно.

**LVM на LUKS?** Сначала расшифруйте контейнер, затем собирайте LVM внутри.

## Что мы теперь знаем

- LVM — прослойка между разделом и файловой системой: PV → VG → LV.
- Раздел с типом `Linux LVM (0x8e)` содержит **Physical Volume**, а не ФС.
- Метка PV `LABELONE`/`LVM2 001` лежит в секторе 1; за ней — текстовые метаданные конфигурации.
- `losetup -fP` + `pvscan` + `vgchange -ay` собирают VG и создают `/dev/mapper/<vg>-<lv>`.
- Если авто не сработало, смещение LV считают по `pe_start` (от начала PV) вручную.
- **Снапшоты** LVM хранят состояние данных на момент создания — ценный источник.

## Куда дальше

Мы собрали логический том LVM и добрались до файловой системы. В следующем уроке (`forensics-vdisk-formats`) мы разберём форматы виртуальных дисков (VDI, VMDK, VHD), в которых часто и лежат такие образы. А пока главное запомни: **LVM вставляет два слоя между разделом и ФС, а `losetup` + `vgchange -ay` собирают логический том из сырого образа**.

- **CTF:** серверные образы, где ФС спрятана за LVM.
