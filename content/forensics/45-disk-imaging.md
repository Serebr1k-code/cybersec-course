## Вопрос, с которого всё начинается

Тебе нужно разобрать USB-флешку с уликами. Ты подключаешь её к компьютеру и
понимаешь: если просто «поработать с ней», система может что-то на неё записать —
обновить время доступа, «починить» файловую систему — и улика перестанет быть
уликой. Нужна неизменяемая копия.

Снятие образа (**imaging**) — первый и самый ответственный шаг форензики. В этом
уроке мы снимем образ флешки `/dev/sdb` так, чтобы доказать его идентичность
источнику.

## Шаг 1: зачем write blocker

**Write blocker** — «блокировщик записи»: устройство или программа, которая
физически запрещает запись на исходный носитель. Без него любое подключение может
изменить данные, и доказательство станет недопустимым.

- **Аппаратные**: Tableau, WiebeTech — включаются между носителем и рабочей станцией.
- **Программные**: монтирование только для чтения, `blockdev --setro`.

```bash
$ blockdev --setro /dev/sdb
$ blockdev --getro /dev/sdb
1
```

Единица — значит «read-only». Но помни: программная защита **не заменяет** аппаратный
блокер. Программа может дать сбой, железо — нет.

## Шаг 2: снимаем образ

`dd` — базовый инструмент побайтового копирования. Но у него есть недостатки: нет
прогресса, хеширования и устойчивости к ошибкам чтения. Поэтому в форензике берут
его улучшенные версии.

```bash
# базовый dd с прогрессом
$ sudo dd if=/dev/sdb of=disk.img bs=4M conv=noerror,sync status=progress
# dc3dd: считает хеш и ведёт лог прямо в процессе
$ sudo dc3dd if=/dev/sdb of=usb.img hash=sha256 log=usb.log
```

Что значат флаги:

| Флаг | Назначение |
|------|-----------|
| `if`/`of` | входной/выходной файл |
| `bs` | размер блока (4M — быстро и удобно) |
| `conv=noerror,sync` | не падать на ошибке, добивать блок нулями |
| `status=progress` | показывать прогресс (GNU dd) |
| `hash=sha256` | считать хеш (dc3dd) |

`conv=noerror,sync` критичен: без него при первом же сбойном секторе `dd` остановится.
`noerror` — продолжать, `sync` — добить неполный блок нулями, чтобы сохранить
выравнивание.

## Шаг 3: хеш доказывает идентичность

**Хеш** — это «отпечаток» данных фиксированной длины. Если хеш образа совпадает с
хешем источника, значит образ — точная копия. Считаем оба:

```bash
$ sha256sum /dev/sdb
3a7f9c...  /dev/sdb
$ sha256sum usb.img
3a7f9c...  usb.img
```

Совпало — целостность подтверждена. `dc3dd` считает хеш источника сам и пишет в лог:

```bash
$ grep -i hash usb.log
sha256 3a7f9c... usb.img
```

Сохрани файл хешей, чтобы позже проверить, что образ не изменился:

```bash
$ sha256sum usb.img > usb.img.sha256
$ sha256sum -c usb.img.sha256
usb.img: OK
```

Почему SHA-256, а не MD5? MD5 устарел: для него известны коллизии, то есть два
разных файла могут дать один хеш. Для доказательства нужен стойкий алгоритм.

## Шаг 4: форматы образов

| Формат | Особенности |
|--------|-------------|
| raw/dd | побайтовый, монтируется напрямую, без сжатия |
| E01 (EWF) | сжатие, сегменты, встроенные хеши, метаданные |
| AFF4 | открытый, сжатие, верификация |
| VMDK/QCOW2 | для виртуальных машин |

Raw-образ — просто копия байт в байт. E01 умеет сжимать и разбивать на части, а
главное — несёт **встроенные** хеши и метаданные, поэтому его удобно верифицировать:

```bash
$ ewfacquire usb.img          # raw -> E01
$ ewfverify evidence.E01      # проверка хешей внутри E01
$ ewfexport -t raw evidence.E01   # E01 -> raw
```

## Шаг 5: FTK Imager и GUI

FTK Imager — графический инструмент (и CLI `ftkimager`), умеет E01, raw, сжатие,
разбиение на части, хеширование и проверку:

```bash
$ ftkimager /dev/sdb evidence --e01 --frag 2G --compress 6 --verify --hash sha256
```

После снятия получаем `evidence.E01`, `evidence.E02`, … и текстовый отчёт с хешами.
Такой отчёт экономит время на документировании.

## Шаг 6: особые случаи

- **SSD/TRIM**: TRIM физически обнуляет удалённые блоки — снимайте немедленно и
  отключите TRIM, иначе восстановить удалённое не выйдет.
- **Зашифрованные диски** (BitLocker/LUKS): образ снимается, но без ключа не читается.
- **RAID**: образ снимают с каждого диска отдельно (см. урок про RAID).
- **LVM**: снимают физический том, потом собирают логические.
- **Неисправные носители**: вместо `dd` берут `ddrescue` — он переживает ошибки и
  умеет возвращаться к «плохим» участкам позже:

```bash
$ sudo ddrescue /dev/sdb disk.img disk.maplog
```

## Шаг 7: сетевое снятие образа

Иногда носитель физически недоступен — сервер стоит в стойке, и выключить его
нельзя. Тогда образ снимают **по сети**. Простейший способ — `dd` через SSH:

```bash
$ ssh user@host "dd if=/dev/sda bs=4M conv=noerror,sync" | pv > remote.img
```

`pv` показывает прогресс передачи. Если на хосте есть `dc3dd`, удобнее снять образ
локально, а потом скачать:

```bash
$ ssh user@host "sudo dc3dd if=/dev/sda of=/tmp/sda.img hash=sha256 log=/tmp/dd.log"
$ scp user@host:/tmp/sda.img .
```

Для корпоративных сетей есть агенты — F-Response, EnCase Enterprise, Velociraptor.
Важно помнить: сетевой сбор **сам по себе меняет систему** (создаёт файлы, запускает
процессы), поэтому фиксируйте это в отчёте и снимайте данные в порядке волатильности:
сначала память, потом диск.

## Шаг 8: проверяем образ перед анализом

Прежде чем разбирать образ, убедись, что он читается и целостен: проверь хеш,
посмотри таблицу разделов, смонтируй read-only. Для E01 — `ewfverify`:

```bash
$ sha256sum -c usb.img.sha256
usb.img: OK
$ mmls usb.img | head
```

Результат проверки тоже фиксируется в отчёте: он доказывает, что анализировали именно
тот образ, который сняли.

## Шаг 9: документируем цепочку хранения

**Chain of custody** («цепочка хранения») — это журнал, кто и когда держал улику.
Любой разрыв делает доказательство сомнительным. Фиксируйте минимум:

| Поле | Пример |
|------|--------|
| Улика | USB SanDisk 16GB, S/N ... |
| Изъял | имя, должность |
| Дата/время | 2024-03-01 10:00 UTC |
| Инструмент | dc3dd 7.2, write blocker Tableau |
| Хеш | SHA256 3a7f9c... |
| Хранилище | сейф, номер |

## Что мы теперь знаем

- Write blocker обязателен: без него улика меняется.
- `dc3dd`/`dcfldd`/`ftkimager` лучше `dd`: хеши, лог, прогресс.
- Хеш источника и образа должны совпадать — это и есть доказательство копии.
- Форматы: raw (простой) и E01 (сжатие + встроенные хеши).
- Каждый шаг фиксируется в chain of custody.

## На что смотреть дальше

- **Снимать без write blocker** — улика изменена, доказательство недопустимо.
- **Хешировать только образ** — нельзя доказать идентичность источнику.
- **`dd` без `conv=noerror,sync`** — зависнет на битом секторе.
- **Писать образ на тот же носитель** — затрёте источник.
- **Игнорировать память** — волатильные артефакты теряются; снимайте память раньше
  диска.

## Куда дальше

Мы научились снимать корректный образ. Дальше разберём серверный случай: как
собрать данные, когда они лежат на RAID-массиве и LVM — то есть на нескольких
дисках сразу. А пока запомни: **образ без write blocker и без совпавшего хеша —
не доказательство**.

## Где пригодится

- **CTF:** подготовка образа перед разбором (и понимание, что даёт хеш).
- **Incident Response:** корректное снятие копии инфицированного хоста.
- **Судебная экспертиза:** доказательность и chain of custody.
- **Работа:** лабораторные процедуры, SOP снятия образов.
- **Data recovery:** образ как страховка перед восстановлением.
