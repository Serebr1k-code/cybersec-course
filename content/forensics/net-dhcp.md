## Вопрос, с которого всё начинается

У тебя есть IP-адрес из лога, но какой машине он принадлежал? Адреса выдаются
динамически, поэтому IP сам по себе мало о чём говорит. Связь «IP ↔ устройство»
восстанавливается по **DHCP**. Разберём, где это искать.

## Наш пример: лиз DHCP

## Шаг 1: что делает DHCP

При подключении устройство рассылает `DHCPDISCOVER`, получает `DHCPOFFER`, запрашивает
`DHCPREQUEST` и подтверждает `DHCPACK`. Сервер запоминает выдачу в **lease** (аренду).

## Шаг 2: серверные лизы

```
$ grep -A4 'lease 10.10.20.9' /var/lib/dhcp/dhcpd.leases
lease 10.10.20.9 {
  starts 3 2026/01/14 03:15:00;
  ends 3 2026/01/14 15:15:00;
  hardware ethernet 02:42:0a:0a:14:09;
  client-hostname "kali";
}
```

Здесь всё: IP, время начала/конца аренды, **MAC** и имя клиента. Имя `kali` — уже
зацепка. Пара «IP + MAC» связывает сетевой лог с конкретным устройством.

## Шаг 3: DHCP в дампе

Если серверных логов нет, смотрим трафик:

```
$ tshark -r capture.pcap -Y 'bootp' -T fields -e ip.src -e bootp.option.hostname -e bootp.hw.mac_addr -e bootp.ip.your | head
0.0.0.0	kali	02:42:0a:0a:14:09	10.10.20.9
```

`bootp.ip.your` — запрошенный адрес. Так восстанавливаешь историю даже без сервера.

## Шаг 4: клиентские следы

На клиенте остаётся история аренды:

```
$ journalctl -u NetworkManager | grep -i dhcp | tail
Jan 14 03:15:00 host NetworkManager[500]: dhcp4 (eth0): address 10.10.20.9
```

А на Windows — в Event Log (`Microsoft-Windows-Dhcp-Client`).

## Шаг 5: сопоставляем

Собираем связку:

```
03:15:00  DHCPACK 10.10.20.9 -> 02:42:0a:0a:14:09 (kali)
03:20:00  SSH from 10.10.20.9
```

Теперь IP из SSH-лога однозначно привязан к устройству.

## Что мы теперь знаем

- DHCP выдаёт IP и запоминает аренду (lease).
- `dhcpd.leases` содержит IP, MAC, имя, время.
- В дампе DHCP виден через `tshark -Y bootp`.
- Клиентские следы — в journald/Event Log.
- Пара IP↔MAC связывает сеть с устройством.

## Если не сработало

- Сервер — Windows? Смотри `DhcpSrvLog-*.log`.
- Лиз истёк и перезаписан? Используй дамп и логи клиентов.
- Нужен производитель? Определи OUI из MAC.

## Как работает DHCP: обмен DORA

DHCP выдаёт устройствам IP-адреса автоматически. Обмен состоит из четырёх шагов, которые
легко запомнить по аббревиатуре **DORA**:

1. **Discover** — клиент широковещательно ищет сервер;
2. **Offer** — сервер предлагает адрес;
3. **Request** — клиент просит конкретный адрес;
4. **Ack** — сервер подтверждает и фиксирует лиз.

Для форензики важен **Ack**: именно в нём сервер сообщает клиенту его адрес, маску, шлюз,
DNS и срок аренды (lease time). А запрос `Request` содержит **опцию 12** — имя хоста клиента,
и **опцию 61** — идентификатор клиента (часто MAC). Это связка «MAC → имя → IP».

```
$ tshark -r dhcp.pcap -Y 'bootp.option.dhcp == 5' -T fields \
    -e frame.time -e ip.src -e bootp.hw.mac_addr -e bootp.option.hostname \
    -e bootp.ip.your -e bootp.option.ip_address_lease_time
2026-01-14 03:10:22  10.0.0.1  aa:bb:cc:11:22:33  WS-DEV-07  10.0.0.57  86400
```

Здесь видно: сервер `10.0.0.1` выдал машине `WS-DEV-07` (MAC `aa:bb:...`) адрес `10.0.0.57`
на сутки. Это готовый факт для таймлайна.

## Серверные лизы: где и как читать

На Linux-сервере ISC DHCP ведёт текстовый файл лизов:

```
$ head -20 /var/lib/dhcp/dhcpd.leases
lease 10.0.0.57 {
  starts 3 2026/01/14 03:10:22;
  ends   4 2026/01/15 03:10:22;
  binding state active;
  hardware ethernet aa:bb:cc:11:22:33;
  client-hostname "WS-DEV-07";
}
```

Это **золото** для расследования: дата начала/конца, MAC, имя хоста и статус. Ищи в файле
все записи конкретного MAC или имени, чтобы восстановить историю адресов машины:

```
$ grep -A6 'aa:bb:cc:11:22:33' /var/lib/dhcp/dhcpd.leases
```

На Windows Server лизы в реестре и в текстовых логах
(`%SystemRoot%\System32\dhcp\DhcpSrvLog-*.log`), где каждая строка — событие с кодом
(10 = новое назначение, 11 = продление, 12 = освобождение).

## Клиентские следы

Даже без сервера адрес и время аренды видны на клиенте. На Linux:

```
$ cat /var/lib/dhclient/dhclient.leases
lease {
  interface "eth0";
  fixed-address 10.0.0.57;
  option dhcp-server-identifier 10.0.0.1;
  renew 4 2026/01/15 03:10:22;
}
```

На Windows адрес и история — в реестре:
`HKLM\SYSTEM\CurrentControlSet\Services\Tcpip\Parameters\Interfaces\<GUID>` (поля
`DhcpIPAddress`, `DhcpServer`, `DhcpDefaultGateway`) и в `DhcpDomain`. Там же остаётся
**предыдущий** адрес, даже если текущий сменился.

## Дампы: фильтры и извлечение

При работе с pcap используй фильтр `bootp` (старое имя DHCP). Полезные фильтры:

- `bootp.option.dhcp == 1` — Discover;
- `bootp.option.dhcp == 5` — Ack;
- `bootp.option.hostname` — только пакеты с именем хоста.

Вытащить все уникальные пары «MAC — имя» из большого дампа:

```
$ tshark -r lan.pcap -Y 'bootp.option.hostname' -T fields \
    -e bootp.hw.mac_addr -e bootp.option.hostname | sort -u
aa:bb:cc:11:22:33   WS-DEV-07
de:ad:be:ef:00:01   printer-hp
```

Так строится **инвентарь сети** на момент захвата: кто был в сети и под каким именем.

## Таблица: поля DHCP и их ценность

| Поле / опция | Смысл | Ценность |
|---|---|---|
| chaddr (MAC) | аппаратный адрес | идентификация устройства |
| Опция 12 | имя хоста | связь MAC → имя |
| Опция 61 | идентификатор клиента | MAC или спец. строка |
| Опция 50 | запрошенный IP | что клиент просил |
| Опция 51 | lease time | срок аренды |
| Опция 54 | сервер | какой сервер ответил |
| yiaddr | выданный IP | адрес клиента |
| Опция 82 | relay agent info | VLAN/порт коммутатора |

Опция 82 — особенно ценная: она показывает **порт коммутатора**, к которому подключён
клиент. Это позволяет привязать адрес к физическому месту (розетка, кабинет).

## Сопоставление и таймлайн

Собираем цепочку: MAC → имя → IP → время. Затем соединяем с другими артефактами:

- по IP находим активность в логах (прокси, firewall, веб);
- по MAC — в ARP-таблицах и Wi-Fi-логах;
- по имени — в доменных и SMB-логах.

```
$ grep '10.0.0.57' /var/log/proxy/access.log | head
```

Так «безымянный IP» превращается в конкретное устройство с именем и владельцем.

## Ограничения

Во-первых, **лизы истекают**: сервер может хранить только активные аренды, а старые — терять.
Во-вторых, **статические адреса** не попадают в лизы вовсе — их берут из конфигов и ARP.
В-третьих, в больших сетях DHCP **ретранслируется** (relay), и в пакете виден адрес
релея, а не клиента. В-четвёртых, **ротация MAC** (рандомизация) на телефонах ломает связку
MAC↔устройство, если не включена опция 61. И часовые пояса: время в лизе — UTC сервера,
приводи к локальному.

## Если сработало: фиксируем связку

Для отчёта нужна таблица «время — MAC — имя — IP» из трёх источников (дамп, сервер, клиент).
Совпадение всех трёх делает вывод о принадлежности адреса железным, а расхождение — повод
искать подмену (спуфинг) или ручной статический адрес.

## DHCP-спуфинг и rogue-серверы

Помимо выдачи адресов, DHCP — это вектор атаки. **Rogue DHCP** (злой сервер) отвечает
быстрее легитимного и выдаёт клиенту **свой** шлюз и DNS, после чего весь трафик жертвы идёт
через атакующего (MITM). Признаки в дампе:

- два разных `server identifier` (опция 54) в одной подсети;
- шлюз, не совпадающий с корпоративным;
- аномально короткий lease time;
- ответы с незнакомого MAC (часто совпадающего с MAC шлюза — спуфинг).

```
$ tshark -r dhcp.pcap -Y 'bootp.option.dhcp == 2' -T fields -e ip.src -e bootp.option.server_id
10.0.0.1    10.0.0.1
10.0.0.99   10.0.0.99     # <- посторонний сервер
```

Найдя rogue-сервер, фиксируй его MAC и IP: это точка, откуда шёл перехват.

## Отслеживание одного устройства во времени

Практическая задача: где была машина `WS-DEV-07` в определённый день. Собираем все записи по
её MAC и имени из всех источников и сортируем по времени:

```
$ for f in /var/lib/dhcp/dhcpd.leases*; do grep -B2 -A6 'aa:bb:cc:11:22:33' "$f"; done | grep -E 'starts|client-hostname|fixed'
```

Смена адреса в течение дня означает переход между подсетями (разные VLAN — разные пулы).
Это позволяет доказать **физическое перемещение** устройства между офисами.

## Опция 82: привязка к порту коммутатора

Если коммутатор настроен с DHCP snooping и опцией 82, каждый запрос несёт информацию о
порте, на который пришёл клиент:

```
$ tshark -r dhcp.pcap -Y 'bootp.option.agent_information' -T fields \
    -e bootp.option.agent_circuit_id -e bootp.option.agent_remote_id
Gi1/0/23    aa:bb:cc:11:22:33
```

`circuit_id` вида `Gi1/0/23` — конкретный порт. Так «IP 10.0.0.57» превращается в «розетка
в кабинете 214». Для инцидентов с физическим доступом это решающий факт.

## Слияние с DNS и ARP

DHCP даёт IP в момент аренды, но имя и адрес могут меняться. Чтобы не ошибиться, соединяй:

| Источник | Что даёт | Когда полезен |
|---|---|---|
| DHCP-лизы | IP, MAC, имя, время | момент подключения |
| DNS-логи | имя → IP | разрешение имён |
| ARP-таблицы | IP ↔ MAC | кто с кем говорил |
| Коммутатор | MAC ↔ порт | физическое место |
| Wi-Fi-контроллер | MAC ↔ AP | перемещение |

Полная связка по всем источникам — это «паспорт» устройства, устойчивый к подмене одного
поля.

## Ограничения

Лизы на сервере могут быть **очищены** при перезапуске или ротации; храни резервные копии.
Часовые пояса и NTP-дрейф искажают время — фиксируй зону сервера. В гостевых сетях с
изоляцией клиентов ARP/DHCP данные неполны. И не забывай, что **виртуальные** машины имеют
свой MAC, который может совпадать по префиксу с хостом.

## Если сработало: что писать в отчёт

Для связки «IP — устройство» приведи минимум два независимых источника. Для инцидента с
MITM дополнительно опиши rogue-сервер (IP, MAC, выданные параметры) и время его активности.
Это превращает сетевой артефакт в доказательство конкретного события.
