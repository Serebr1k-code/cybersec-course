## Вопрос, с которого всё начинается

Нужно быстро узнать состояние хоста: какие процессы, соединения, автозапуск. Вместо
десятка утилит — один инструмент с **SQL**. Это **osquery**. Разберём.

## Наш пример: живой хост

## Шаг 1: идея

osquery представляет ОС как **базу данных**: процессы, сокеты, файлы, пользователи,
реестр — это таблицы. Ты пишешь SQL:

```sql
SELECT pid, name, path FROM processes WHERE name = 'sshd';
```

## Шаг 2: полезные таблицы

- `processes` — процессы;
- `listening_ports` — открытые порты;
- `logged_in_users` — кто вошёл;
- `startup_items` — автозапуск;
- `users`, `groups`.

```
osquery> SELECT * FROM listening_ports WHERE port = 4444;
```

Порт 4444 — типичный бэкдор.

## Шаг 3: форензика

Типовые запросы:

```sql
-- процессы из /tmp
SELECT * FROM processes WHERE path LIKE '/tmp/%';
-- соединения к внешним адресам
SELECT * FROM process_open_sockets WHERE remote_address != '';
```

Так быстро выявляешь подозрительное.

## Шаг 4: флот

osquery может работать как **агент** с централизованной конфигурацией: один запрос —
на тысячи хостов. Это делает его частью live-DFIR.

## Шаг 5: ограничения

- это **снимок состояния**, не история;
- данные можно подделать (руткит);
- требует прав.

osquery дополняют логированием (диффы по расписанию).

## Что мы теперь знаем

- osquery даёт SQL-доступ к системе.
- Таблицы: процессы, порты, пользователи, автозапуск.
- Запросы выявляют аномалии.
- Работает на флоте как агент.
- Это снимок, а не история.

## Если не сработало

- Нужна история? Включи логирование/диффы.
- Таблица недоступна? Проверь ОС/версию.
- Нужны удалённые хосты? Разверни агент.

## Почему SQL к состоянию системы

Обычные утилиты (`ps`, `netstat`, `ss`, `lsof`) дают каждый свою картину, и
чтобы ответить на сложный вопрос, приходится склеивать вывод вручную.
osquery идёт другим путём: он представляет систему как **реляционную базу**,
где каждая сущность — таблица. Тогда вопрос формулируется как SQL-запрос, а
не как цепочка команд.

## Полный список полезных таблиц

Кроме уже названных, в osquery есть:

| Таблица | Что показывает |
| --- | --- |
| `processes` | процессы (pid, name, path, cmdline) |
| `process_open_sockets` | сокеты процессов (соединения) |
| `listening_ports` | слушающие порты |
| `logged_in_users` | активные сессии |
| `startup_items` | автозапуск (Windows/macOS) |
| `crontab` | задания cron |
| `services` | системные сервисы |
| `users`/`groups` | учётные записи |
| `file` | метаданные файлов |
| `hash` | хэши файлов |

## Работа на примере: подозрительный процесс

Ищем процессы, запущенные из временных каталогов — типичный признак
малвари:

```sql
SELECT pid, name, path, cmdline FROM processes WHERE path LIKE '/tmp/%' OR path LIKE '/var/tmp/%';
```

Результат:

```
pid=4821 name=minerd path=/tmp/.x/minerd cmdline=/tmp/.x/minerd -o pool:3333
```

`minerd` из `/tmp` с подключением к пулу — почти наверняка майнер. Теперь
смотрим, куда он ходит по сети:

```sql
SELECT pid, remote_address, remote_port FROM process_open_sockets WHERE pid = 4821;
```

Так один запрос за другим выстраивается цепочка «процесс → сеть».

## Поиск persistence

Автозапуск — то, что атакующий ставит, чтобы выжить перезагрузку. Проверяем
сразу несколько мест:

```sql
SELECT * FROM crontab;
SELECT name, path, source FROM startup_items;
```

В `crontab` ищем задачи, тянущие скрипт из `/tmp` или по URL. В
`startup_items` — записи с путями вне стандартных каталогов.

## Файлы по хэшу и времени

osquery умеет хэшировать файлы — удобно для сопоставления с IOC:

```sql
SELECT path, sha256 FROM hash WHERE path LIKE '/etc/%';
```

И фильтровать по времени изменения через join с `file`:

```sql
SELECT f.path, f.mtime FROM file f WHERE f.directory = '/tmp';
```

## Флот и централизованный DFIR

Ключевая сила osquery — **агент**. Один и тот же запрос выполняется на
тысячах хостов, а результаты собираются централизованно (Kolide, Fleet,
свой collector). Для расследования это значит: «найди все машины, где
запущен процесс с таким хэшем» — один запрос вместо обхода по SSH.

## Ограничения и подводные камни

- **Снимок, а не история** — osquery показывает текущее состояние; для
  истории нужен режим `schedule` с логированием диффов (`--logger_plugin`).
- **Руткит может подделать** — данные берутся из ядра, и продвинутый руткит
  способен их исказить.
- **Требует прав** — часть таблиц только от root/администратора.
- **Платформенные различия** — не все таблицы есть на всех ОС.

## Практический чек-лист

1. Запусти `osqueryi` (интерактивно) или агент.
2. Проверь процессы, порты, пользователей.
3. Найди процессы из `/tmp`, соединения к внешним адресам.
4. Проверь `crontab` и `startup_items` на persistence.
5. Сопоставь хэши файлов с IOC.
6. Для истории включи schedule-логирование.
7. Зафиксируй результаты запросов как доказательства.

## Режим агента и расписание

Интерактивный `osqueryi` хорош для разового вопроса. Для постоянного
мониторинга запускают **демон** `osqueryd` с расписанием (schedule): запросы
выполняются периодически, а изменения (диффы) пишутся в лог. Так появляется
**история**, которой нет у снимка.

Пример конфигурации:

```json
{
  "schedule": {
    "listening_ports": {
      "query": "SELECT * FROM listening_ports;",
      "interval": 300
    }
  }
}
```

Событийный режим (`events`) подписывается на изменения (новые процессы,
соединения) через таблицы `*_events`. Это ближе всего к EDR-телеметрии.

## Работа на примере: расследуем beaconing

Хост периодически «стучится» на внешний адрес с равными интервалами —
классический признак C2. osquery показывает текущие соединения:

```sql
SELECT p.name, s.remote_address, s.remote_port, p.path
FROM process_open_sockets s JOIN processes p ON p.pid = s.pid
WHERE s.remote_address NOT LIKE '10.%' AND s.remote_address != '';
```

Результат:

```
name=svchost path=/tmp/.cache/svchost remote_address=203.0.113.44 remote_port=8443
```

Процесс с именем системного, но из `/tmp` и с соединением на внешний адрес
— сильный сигнал. Дальше берём хэш файла и сверяем с IOC:

```sql
SELECT path, sha256 FROM hash WHERE path = '/tmp/.cache/svchost';
```

## Расширения и кастомные таблицы

osquery расширяется: можно писать свои таблицы (на C++/Go/Python), отдающие
данные из внутренних систем. Это позволяет одним SQL-запросом объединять
состояние хоста с данными о рисках. Для форензики полезны готовые пакеты
запросов (query packs) под конкретные угрозы.

## Сравнение с другими инструментами

| Инструмент | Подход | Когда лучше |
| --- | --- | --- |
| osquery | SQL, снимок+расписание | массовый live-DFIR |
| ps/netstat | разовые команды | быстрая проверка |
| EDR | агент + детект | непрерывный мониторинг |
| Volatility | анализ дампа | после снятия памяти |

osquery не заменяет анализ дампа памяти — он работает с живой системой.
Комбинируй: osquery для «что происходит сейчас», Volatility — «что было в
памяти».

## Практический чек-лист

1. Определи задачу: разовый вопрос или мониторинг.
2. Для разового — `osqueryi` с конкретным SQL.
3. Для мониторинга — `osqueryd` + schedule/events.
4. Проверь процессы, соединения, persistence, хэши.
5. Собери результаты централизованно (Fleet/Kolide).
6. Дополни анализом дампа памяти.
