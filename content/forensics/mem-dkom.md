## Вопрос, с которого всё начинается

В дампе памяти процессов больше, чем показывает система. Один процесс «есть», но его
нигде не видно. Это не баг: кто-то **исказил структуры ядра** так, чтобы процесс выпал
из всех списков. Техника называется DKOM. Разберёмся, как она работает и как её ловить.

## Наш пример: скрытый процесс

Смотрим список процессов:

```
$ vol.py -f mem.raw windows.pslist.PsList
PID   PPID  ImageFileName
4     0     System
...
880   4     svchost.exe
```

А теперь — скан памяти:

```
$ vol.py -f mem.raw windows.psscan.PsScan
PID   PPID  ImageFileName   Offset(V)
...
880   4     svchost.exe     0x...
1337  880   evil.exe        0xffff...
```

`evil.exe` есть в `psscan`, но его нет в `pslist`. Значит, процесс скрыт.

## Что такое DKOM

**DKOM (Direct Kernel Object Manipulation)** — прямое изменение объектов ядра из
драйвера. Ядро хранит информацию о процессах в структурах (`EPROCESS` в Windows,
`task_struct` в Linux) и связывает их в список. Чтобы спрятать процесс, достаточно
**вырезать** его структуру из этого списка — перешить указатели соседей.

Ничего не удаляется: структура и её память на месте. Меняется только **доступность через
список**. Поэтому обход списка (`pslist`) скрытый объект не увидит, а скан памяти
(`psscan`) — увидит.

## Шаг 1: понять, какие представления расходятся

- `pslist` — обход связанного списка процессов, который ведёт ядро;
- `psscan` — сканирование памяти в поиск структур процессов по сигнатурам.

Расхождение — сигнал. Но DKOM умеет и больше: подделать PID, PPID, время создания,
даже подменить имя процесса на «svchost.exe», чтобы слиться с толпой.

## Шаг 2: искать аномалии внутри самого процесса

Даже скрытый процесс можно выдать по деталям:

- **нет родителя** (PPID указывает в никуда) — процесс «перешили», но связи порвали;
- **время создания** не соответствует времени появления процесса в журналах;
- **путь к образу** пустой или ведёт в странное место;
- **PID вне ожидаемого диапазона** (например, 1337 или 0xDEAD).

## Шаг 3: кросс-вью по разным объектам

DKOM может прятать не только процессы:

```
pslist  vs  psscan        -> скрытые процессы
modules vs  modscan       -> скрытые драйверы
handles vs  скан          -> скрытые дескрипторы
```

Общий принцип: **сравнивай список со сканом**. Один из двух всегда покажет правду,
потому что данные физически лежат в памяти.

## Шаг 4: почему это трудно обнаружить на живой системе

На живой системе у тебя есть только то представление, которое отдаёт ядро. Если руткит
вырезал процесс из списка — ни диспетчер задач, ни `ps` его не покажут. Дамп памяти
фиксирует **сырое состояние** памяти, поэтому скан работает независимо от списков. Это и
есть причина, по которой руткиты ищут именно в памяти.

## Как выглядит EPROCESS и ActiveProcessLinks

Чтобы понять, что именно вырезает DKOM, посмотрим на структуру. В Windows ядро описывает каждый процесс структурой **`EPROCESS`**. Внутри неё есть поле `ActiveProcessLinks` — элемент двусвязного списка, который связывает все живые процессы:

```
EPROCESS(evil.exe)
  +0x000 UniqueProcessId : 1337
  +0x0b4 ActiveProcessLinks : { Flink -> next, Blink -> prev }
  +0x... ImageFileName : "evil.exe"
```

Список обходится по `Flink` от `PsActiveProcessHead`. Чтобы спрятать процесс, руткит берёт соседей скрываемой структуры и перешивает их указатели друг на друга, минуя её:

```
prev->Flink = evil->Flink      // сосед слева теперь смотрит на правого
next->Blink = evil->Blink
// evil->Flink/Blink остаются, но на неё никто не ссылается
```

Структура и её память целы — просто недостижимы из списка. В Linux аналог — `task_struct` и поле `tasks` (список `list_head`), вырезание делается через `list_del`.

## Полный прогон: сравнение pslist и psscan

Смотрим дамп и находим расхождение, а затем копаем детали:

```
$ vol.py -f mem.raw windows.pslist.PsList | wc -l
   62
$ vol.py -f mem.raw windows.psscan.PsScan | wc -l
   63
```

Разница в один процесс. Достаём его и проверяем метаданные:

```
$ vol.py -f mem.raw windows.psscan.PsScan | grep -iE 'evil|1337'
1337  880  evil.exe  0xfffffa8001234560

$ vol.py -f mem.raw windows.cmdline.CmdLine | grep 1337
(нет строки — процесс вырезан, но командную строку можно достать из скана)
```

Проверяем родителя `880` — это `svchost.exe`, что уже подозрительно: `svchost` не должен порождать `evil.exe`. Смотрим время создания и сетевые сокеты процесса — так выходим на его поведение.

## Техники DKOM и контрмеры

| Техника | Что скрывает | Детект |
|---|---|---|
| Вырезание из `ActiveProcessLinks` | процесс | `pslist` vs `psscan` |
| Вырезание из `PsLoadedModuleList` | драйвер/модуль | `modules` vs `modscan` |
| Подмена `UniqueProcessId`/`InheritedFromUniqueProcessId` | связи процесса | аномальный PPID |
| Скрытие дескрипторов | открытые файлы/сокеты | `handles` vs скан |
| Очистка `ImageFileName` | имя процесса | пустое имя, «мусор» |
| Подмена времени создания | таймлайн | расхождение с журналами |

## Скрытие драйверов, модулей и дескрипторов

DKOM не ограничивается процессами. Тот же приём работает с:

- **Драйверами.** Ядро ведёт `PsLoadedModuleList`; вырезание прячет драйвер от `driverscan`. Сравнение `modules` (обход списка) и `modscan` (скан памяти) выдаёт скрытый драйвер.
- **Дескрипторами.** Скрытие записи в таблице дескрипторов прячет открытый файл или сокет. `handles` может не показать, а скан памяти — да.
- **Потоками.** Вырезание `ETHREAD` из списка потоков процесса.

Общий принцип один: **любой список можно вырезать, но данные остаются в памяти**. Поэтому кросс-вью «список против скана» — универсальный детект.

## Крайние случаи и ограничения

- **Ложные срабатывания `psscan`.** Скан по сигнатурам может подобрать «мёртвую» структуру освобождённого процесса — проверяй `PoolTag`, время и связи, прежде чем объявлять находку.
- **Частичный DKOM.** Руткит может вырезать процесс из одного списка, но оставить в другом; сравнение трёх представлений повышает шанс.
- **Анти-скан.** Продвинутые руткиты шифруют структуры или подменяют сигнатуры, чтобы скан не нашёл; тогда нужен ручной разбор страниц памяти.
- **Виртуализация.** При анализе виртуальной машины важно, чей дамп: гостя или гипервизора — в гипервизорном DKOM не виден из гостя.
- **Порядок и полнота.** Дамп должен быть полным и «замороженным»: живой снимок с активными изменениями даёт гонки и ложные расхождения.

## Linux: DKOM через list_del в task_struct

В Linux модуль ядра (LKM) скрывает процесс так же — удалением из списка `tasks`:

```c
// упрощённо: вырезание task_struct из списка процессов
list_del(&target->tasks);
```

После этого `ps`, `top` и обход `/proc` его не видят, но структура `task_struct` остаётся в slab-памяти. Детект тот же: сканируем память в поиск структур процессов (например, по сигнатуре `comm` и связям `mm`) и сравниваем с обходом списка. Дополнительный признак — модуль, который загрузили после инцидента: сверь `lsmod` с временем загрузки модулей в `dmesg`/`/var/log/kern.log`.

## Практика: порядок анализа дампа и инструменты

Работа с дампом памяти для поиска DKOM идёт по устойчивому порядку:

```
$ vol.py -f mem.raw windows.info.Info          # профиль и версия ОС
$ vol.py -f mem.raw windows.pslist.PsList       # процессы по списку ядра
$ vol.py -f mem.raw windows.psscan.PsScan       # процессы сканом памяти
$ vol.py -f mem.raw windows.modules.Modules     # драйверы по списку
$ vol.py -f mem.raw windows.modscan.ModScan     # драйверы сканом
$ vol.py -f mem.raw windows.cmdline.CmdLine     # командные строки
$ vol.py -f mem.raw windows.netscan.NetScan     # сетевые соединения
```

Дальше — сопоставление. Всё, что есть в скане, но нет в списке, — кандидат в скрытое. Для каждого кандидата проверяем:

- **родителя** (`PPID`): указывает ли на существующий процесс и логично ли порождение;
- **время создания**: попадает ли оно в окно инцидента;
- **путь к образу**: существует ли файл и где он лежит;
- **сетевые сокеты**: не держит ли процесс соединение с внешним адресом;
- **дескрипторы**: какие файлы открыты.

Инструменты Linux-стороны: `LiME`/`avml` для снятия дампа, `volatility3` с символами ядра, ручной поиск `task_struct` по `comm`. Типичные ошибки: анализ неполного дампа (гонки, мусор), игнорирование `PoolTag`, объявление находки по одному скану без проверки связей. Правило прежнее: **кандидат становится находкой только после подтверждения метаданными**.

## Сводка по DKOM

Скрытие через DKOM всегда оставляет один и тот же разрыв: объект физически есть в памяти, но недостижим через список ядра. Детект строится на сравнении «список против скана» (`pslist`/`psscan`, `modules`/`modscan`, `handles`/скан) и на аномалиях метаданных — PPID, время создания, путь, PID. На живой системе DKOM не виден, поэтому анализ ведут по дампу памяти, а кандидат становится находкой только после подтверждения связями и сетевыми артефактами.

## Что мы теперь знаем

- DKOM — прямое изменение объектов ядра, чаще всего вырезание из списков.
- Скрытый процесс есть в `psscan`, но отсутствует в `pslist`.
- Аномалии (PPID, время, путь, PID) выдают подделку даже у «нормального» имени.
- Кросс-вью работает по процессам, драйверам, дескрипторам.
- На живой системе обнаружить DKOM почти невозможно — нужен дамп.

## Куда дальше

Скрытие объектов ядра — высшая форма сокрытия. Дальше вернёмся к анти-форензике и разберём,
как атакующий **уничтожает** улики, а не прячет их. А пока запомни: `pslist` vs `psscan`
— главный детект DKOM.

## Где пригодится

- **CTF Forensics** — задачи со скрытыми процессами в дампах.
- **DFIR / Incident Response** — обнаружение DKOM-руткитов.
- **Анализ руткитов** — кросс-вью по всем типам объектов ядра.
