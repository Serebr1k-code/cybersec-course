## Вопрос, с которого всё начинается

В дампе памяти процессов больше, чем показывает система. Один процесс «есть», но его
нигде не видно. Это не баг: кто-то **исказил структуры ядра** так, чтобы процесс выпал
из всех списков. Техника называется DKOM. Разберёмся, как она работает и как её ловить.

## Наш пример: скрытый процесс

Смотрим список процессов:

```
$ vol.py -f mem.raw windows.pslist.PsList
PID   PPID  ImageFileName
4     0     System
...
880   4     svchost.exe
```

А теперь — скан памяти:

```
$ vol.py -f mem.raw windows.psscan.PsScan
PID   PPID  ImageFileName   Offset(V)
...
880   4     svchost.exe     0x...
1337  880   evil.exe        0xffff...
```

`evil.exe` есть в `psscan`, но его нет в `pslist`. Значит, процесс скрыт.

## Что такое DKOM

**DKOM (Direct Kernel Object Manipulation)** — прямое изменение объектов ядра из
драйвера. Ядро хранит информацию о процессах в структурах (`EPROCESS` в Windows,
`task_struct` в Linux) и связывает их в список. Чтобы спрятать процесс, достаточно
**вырезать** его структуру из этого списка — перешить указатели соседей.

Ничего не удаляется: структура и её память на месте. Меняется только **доступность через
список**. Поэтому обход списка (`pslist`) скрытый объект не увидит, а скан памяти
(`psscan`) — увидит.

## Шаг 1: понять, какие представления расходятся

- `pslist` — обход связанного списка процессов, который ведёт ядро;
- `psscan` — сканирование памяти в поиск структур процессов по сигнатурам.

Расхождение — сигнал. Но DKOM умеет и больше: подделать PID, PPID, время создания,
даже подменить имя процесса на «svchost.exe», чтобы слиться с толпой.

## Шаг 2: искать аномалии внутри самого процесса

Даже скрытый процесс можно выдать по деталям:

- **нет родителя** (PPID указывает в никуда) — процесс «перешили», но связи порвали;
- **время создания** не соответствует времени появления процесса в журналах;
- **путь к образу** пустой или ведёт в странное место;
- **PID вне ожидаемого диапазона** (например, 1337 или 0xDEAD).

## Шаг 3: кросс-вью по разным объектам

DKOM может прятать не только процессы:

```
pslist  vs  psscan        -> скрытые процессы
modules vs  modscan       -> скрытые драйверы
handles vs  скан          -> скрытые дескрипторы
```

Общий принцип: **сравнивай список со сканом**. Один из двух всегда покажет правду,
потому что данные физически лежат в памяти.

## Шаг 4: почему это трудно обнаружить на живой системе

На живой системе у тебя есть только то представление, которое отдаёт ядро. Если руткит
вырезал процесс из списка — ни диспетчер задач, ни `ps` его не покажут. Дамп памяти
фиксирует **сырое состояние** памяти, поэтому скан работает независимо от списков. Это и
есть причина, по которой руткиты ищут именно в памяти.

## Что мы теперь знаем

- DKOM — прямое изменение объектов ядра, чаще всего вырезание из списков.
- Скрытый процесс есть в `psscan`, но отсутствует в `pslist`.
- Аномалии (PPID, время, путь, PID) выдают подделку даже у «нормального» имени.
- Кросс-вью работает по процессам, драйверам, дескрипторам.
- На живой системе обнаружить DKOM почти невозможно — нужен дамп.

## Куда дальше

Скрытие объектов ядра — высшая форма сокрытия. Дальше вернёмся к анти-форензике и разберём,
как атакующий **уничтожает** улики, а не прячет их. А пока запомни: `pslist` vs `psscan`
— главный детект DKOM.

## Где пригодится

- **CTF Forensics** — задачи со скрытыми процессами в дампах.
- **DFIR / Incident Response** — обнаружение DKOM-руткитов.
- **Анализ руткитов** — кросс-вью по всем типам объектов ядра.
