## Вопрос, с которого всё начинается

Ты снял образ ноутбука с Linux, но раздел не читается: вместо файлов — случайные байты.
Это **LUKS** (шифрование диска). Данные внутри зашифрованы, но заголовок с ключами лежит
прямо в начале раздела. Как понять, что это LUKS, и что вообще можно сделать при
расследовании?

## Что такое LUKS

**LUKS (Linux Unified Key Setup)** — стандарт шифрования разделов в Linux, работающий
поверх **dm-crypt** (подсистемы ядра). Устроен он так: весь раздел шифруется одним
случайным **мастер-ключом (master key)**. Мастер-ключ никуда не пишется в открытом виде —
он хранится **зашифрованным** в **ключевых слотах (key slots)**. Каждый слот содержит копию
мастер-ключа, зашифрованную ключом, выведенным из **пароля** пользователя.

Смысл конструкции: пароль можно поменять (перезаписав один слот), не перешифровывая весь
диск. И наоборот — при расследовании пароль нужен, чтобы развернуть мастер-ключ.

## Наш пример: заголовок LUKS

```
$ ls -la
-rw-r--r-- 1 student student 16777216 luks.img
$ file luks.img
luks.img: LUKS encrypted file, ver 2 [uuid ..., sha256, argon2id]
```

`file` уже распознал LUKS2. Первые байты заголовка — магия `LUKS\xba\xbe`:

```
$ xxd -l 16 luks.img
00000000: 4c55 4b53 babe 0002 0000 0000 0000 0000  LUKS............
```

`4c55 4b53` — это ASCII `LUKS`, затем `babe` (маркер) и номер версии `0002` (LUKS2).
Посмотрим текстовые метаданные:

```
$ strings luks.img | grep -Ei 'LUKS|cipher|pbkdf|iterations|keyslot|nto'
LUKS\xba\xbe version 2
cipher: aes-xts-plain64
PBKDF: argon2id iterations=4
keyslot 0 active
keyslot 1 active
NOTE: nto{luks_h3ad3r_k3ysl0t_pbkdf2}
```

Видно всё ключевое: версия, шифр, функция вывода ключа (PBKDF) и активные слоты. Именно
эти параметры определяют, как перебирать пароль и как быстро это будет идти.

## Шаг 1: LUKS1 vs LUKS2

| Аспект | LUKS1 | LUKS2 |
|--------|-------|-------|
| Заголовок | бинарная структура | JSON в метаданных |
| PBKDF | PBKDF2 | argon2i/argon2id (по умолчанию) |
| Слотов | 8 | 32 |
| Резервные копии | в конце раздела | несколько областей |
| Гибкость | ниже | выше (перекриптование, integrity) |

Для аналитика важно: **LUKS2 хранит заголовок в JSON**, его видно глазами, а LUKS1 —
бинарный. Это влияет на то, как искать параметры.

## Шаг 2: что такое PBKDF и почему это важно

**PBKDF (Password-Based Key Derivation Function)** — функция, которая превращает пароль в
ключ, **специально медленно**. Она прогоняет пароль тысячи раз (iterations) или использует
много памяти (argon2). Смысл — затруднить перебор.

Для форензики это значит: **подбор пароля упирается в PBKDF**. Один вариант пароля стоит
не микросекунду, а десятки миллисекунд. Отсюда практика:

- сначала **словарная атака** по разумному словарю (не «миллионы»);
- учитывай число iterations: больше — медленнее;
- LUKS2 с argon2id заметно медленнее для перебора, чем LUKS1 с PBKDF2.

Инструмент перебора: `hashcat -m 14600` (LUKS1) или `-m 29511/-m 29521` (LUKS2), а также
`bruteforce-luks`.

## Шаг 3: работа с заголовком

Заголовок — самое ценное в LUKS, потому что **без него данные невосстановимы даже с
паролем**. При расследовании:

- **Сохрани копию заголовка.** `cryptsetup luksHeaderBackup /dev/sda2 --header-backup-file hdr.bin`.
- **Посмотри параметры.** `cryptsetup luksDump luks.img`.
- **Проверь слоты.** Сколько активно, какие PBKDF.

```
$ cryptsetup luksDump luks.img
LUKS header information
Version:        2
Cipher:        aes-xts-plain64
PBKDF:         argon2id
Keyslots:
  0: luks2
  1: luks2
```

## Шаг 4: анти-форензика с заголовком

Классический приём сокрытия — **затирание заголовка** (например, `dd if=/dev/zero` в начало
раздела). Тогда раздел выглядит как случайные данные, и никто не поймёт, что это LUKS.
Защита от этого:

- **Резервная копия заголовка** (`--header-backup-file`) — если она есть, раздел спасён;
- **Поиск заголовка по диску** — иногда копия лежит в другом месте (LUKS2 хранит несколько);
- **Признаки dm-crypt** — записи в `/etc/crypttab`, `fstab`, `initramfs`, конфиг GRUB.

Именно поэтому в расследовании первым делом ищут **копии заголовка** и конфигурацию
системы, а не пытаются «угадать» пароль.

## Шаг 5: открытие раздела

Если пароль или ключ есть:

```
$ sudo cryptsetup luksOpen --readonly luks.img crypt0
$ sudo mount -o ro /dev/mapper/crypt0 /mnt/plain
```

Флаг `--readonly` обязателен: любая запись в расшифрованный том изменит данные и может
переписать метаданные. Если пароля нет, но есть резервная копия заголовка с известным
паролем, можно восстановить доступ.

## Мини-практика: от заголовка к параметрам

```
$ file luks.img
luks.img: LUKS encrypted file, ver 2 [sha256, argon2id]
$ cryptsetup luksDump luks.img | grep -Ei 'Version|Cipher|PBKDF'
Version: 2
Cipher: aes-xts-plain64
PBKDF: argon2id
```

Мы получили всё для планирования перебора: версию, шифр и PBKDF. Дальше — словарная
атака `hashcat -m 29521` с ограниченным словарём и оценкой времени.

## Частые ошибки и подводные камни

- **Забыть про заголовок.** Без него данные не восстановить — сохраняй копию первым делом.
- **Монтировать с записью.** `--readonly` обязателен.
- **Огромный словарь.** PBKDF делает перебор медленным; начинай с малого.
- **Путаница версий.** Команды и модули hashcat для LUKS1 и LUKS2 разные.
- **Игнорировать конфиги.** `crypttab`/`initramfs` могут содержать ключевые файлы.

## Что мы теперь знаем

- LUKS шифрует раздел мастер-ключом, хранящимся в ключевых слотах.
- LUKS1 — бинарный заголовок с PBKDF2; LUKS2 — JSON с argon2.
- PBKDF намеренно замедляет перебор пароля.
- Заголовок критичен: без него данные невосстановимы.
- Инструменты: `cryptsetup luksDump/luksHeaderBackup/luksOpen`, hashcat, bruteforce-luks.

## Перебор пароля: практические оценки

PBKDF меняет всю математику перебора. Посчитаем на пальцах: если PBKDF настроен на 500 000
итераций, а CPU считает миллион итераций в секунду, то один вариант пароля занимает
**полсекунды**. Словарь из 10 000 слов — это ~1,4 часа; словарь из миллиона — 5,8 суток.
Отсюда правила:

- **сначала словарь по делу**: имена проектов, компании, даты, ранее найденные пароли;
- **правила мутации** (замена букв цифрами, добавление года) дают больше, чем рост словаря;
- **argon2id дороже по памяти**, поэтому GPU-перебор LUKS2 заметно медленнее, чем LUKS1;
- **не начинай с rockyou** против медленного KDF — это сожжёт время без результата.

Если пароля нет, а есть **заголовок с известным паролем** (например, старый бэкап), можно
попробовать восстановить мастер-ключ и открыть том с ним.

## LUKS и TRIM: почему данные могут исчезнуть

На SSD включённая команда **TRIM** сообщает накопителю, какие блоки больше не нужны, и тот
может физически стереть их. Для шифрованного LUKS-раздела это критично:

- при удалении файла внутри расшифрованного тома TRIM может стереть соответствующие
  блоки **на физическом носителе**;
- после этого восстановление удалённых данных **невозможно**, даже с ключом;
- если LUKS-раздел смонтирован с `discard`, удалённые данные уходят быстро.

Практический вывод: если есть подозрение, что носитель был SSD с TRIM, восстановление
удалённого из LUKS — почти безнадёжно. В этом случае фокус смещается на **снапшоты, бэкапы,
логи и память**, а не на сам диск. Зафиксируй в отчёте, что TRIM исключает восстановление —
это честный и важный вывод.

## Detached header и ключевые файлы

У LUKS заголовок может лежать **отдельно** от данных — это называют **detached header**
(`--header`). Такой приём используют, чтобы зашифрованный раздел выглядел как случайные
данные, а заголовок прятался, например, на USB или в другом файле. При расследовании:

- проверь, не открывается ли том с внешним заголовком: `cryptsetup luksOpen --header hdr.img`;
- ищи маленькие файлы размером ~2–16 МБ, похожие на заголовки;
- помни, что **без detached-заголовка** данные невосстановимы, даже если пароль известен.

Отдельная тема — **key files** (`--key-file`). Некоторые системы комбинируют пароль и файл
ключа. Файл ключа может лежать в `/boot`, `initramfs` или рядом с томом. Найденный key file
иногда заменяет пароль полностью, поэтому ищи оба компонента.
