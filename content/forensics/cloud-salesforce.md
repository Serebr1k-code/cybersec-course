## Вопрос, с которого всё начинается

Компания хранит клиентскую базу в Salesforce. Внезапно конкурент знает детали сделок.
Утечка? Salesforce — SaaS, диска нет; но у него есть **Event Log File** — журнал событий,
который фиксирует доступ к данным. Разберём, как его читать.

## Что такое Event Log File

**Event Log File (ELF)** — журнал событий Salesforce. Раз в час Salesforce формирует
файл с записями о том, что происходило в организации. Основные типы событий:

- **Login** — входы (успешные/неудачные), IP, устройство;
- **ReportExport** — выгрузка отчётов;
- **ApiTotalUsage** — вызовы API;
- **ApexExecution** — выполнение кода Apex;
- **SetupAuditTrail** — изменения настроек и прав;
- **URI** — обращения к страницам.

Поля записи: **EVENT_TYPE**, **TIMESTAMP**, **USER_ID**, **CLIENT_IP**, **URI**,
**LOGIN_STATUS** и др.

## Наш пример: журнал выгрузок

```
$ ls -la
-rw-r--r-- 1 student student 4096 sf.log
$ head -n 2 sf.log
EVENT_TYPE,TIMESTAMP,USER_ID,CLIENT_IP,URI
ReportExport,2026-03-11T02:14:09Z,005abc,203.0.113.9,/00O/report/leads
```

Первая строка — заголовок, вторая — **выгрузка отчёта** с лидами. Смотрим дальше:

```
$ grep -Ei 'ReportExport|ApiTotal|Login|nto' sf.log
ReportExport,2026-03-11T02:14:09Z,005abc,203.0.113.9,/00O/report/leads
ReportExport,2026-03-11T02:15:01Z,005abc,203.0.113.9,/00O/report/opportunities
ApiTotalUsage,2026-03-11T02:16:00Z,005abc,203.0.113.9,5000 calls
EVIDENCE: nto{sal3sf0rc3_3v3ntl0g_3xf1l}
```

Картина: пользователь **005abc** выгрузил несколько отчётов, а затем сделал 5000 API-вызовов
с одного IP. Это профиль **массового экспорта данных** — либо уход сотрудника, либо
компрометация.

## Шаг 1: типичные сценарии

| EVENT_TYPE | Что означает | Почему подозрительно |
|------------|--------------|----------------------|
| `ReportExport` | выгрузка отчёта | кража данных |
| `ApiTotalUsage` (аномально много) | API-вызовы | автоматизированная выкачка |
| `Login` (новый IP) | вход | захват |
| `SetupAuditTrail` | смена настроек | ослабление безопасности |
| `ApexExecution` | запуск кода | вредоносная логика |
| `PermissionSetAssignment` | выдача прав | эскалация |

Опасна **серия**: вход с нового IP → выдача прав → экспорт отчётов → API-выкачка.

## Шаг 2: выгрузка через SOQL

Event Log File доступен через API/SOQL:

```
$ sfdx force:data:soql:query -q \
  "SELECT Id, EventType, LogDate, LogFileLength FROM EventLogFile WHERE LogDate = LAST_N_DAYS:7" \
  -u prod
```

Каждый файл скачивается по своему `Id` через REST. Setup Audit Trail читается через
`SetupAuditTrail` SOQL-объект. Login History — через `LoginHistory`.

Срок хранения ELF — обычно **1 день** (нужно ежедневно выгружать) или дольше при
включённом долгом хранении (Event Monitoring). Это критично: пропустил день — потерял
доказательства.

## Шаг 3: разбор полей

Поле **CLIENT_IP** — ключ к атрибуции. Один IP в нескольких учётках — массовая
компрометация. **URI** показывает, какие объекты/отчёты затронуты. **USER_ID** позволяет
понять, чья учётка использовалась (или украдена). **LOGIN_STATUS** отделяет попытки от
успехов.

Для API важно смотреть **объём**: 5000 вызовов за минуту — это не человек, а скрипт.

## Шаг 4: session hijacking и connected apps

Salesforce-сессии могут быть перехвачены. Признаки:

- вход с нового IP/устройства, но **без MFA-запроса**;
- активность **connected app** с широкими scopes (OAuth);
- необычные `ApiTotalUsage` от имени приложения.

Connected apps — аналог OAuth-приложений: их выдача и использование видны в журналах.

## Шаг 5: реагирование

- заблокировать сессии пользователя (`UserLogin` → revoke);
- отозвать connected app / OAuth-токены;
- проверить и откатить изменения Setup Audit Trail;
- ограничить экспорт отчётов и API-лимиты;
- включить **Event Monitoring** для долгого хранения.

## Мини-практика: связать экспорт и API

```
$ grep -c 'ReportExport' sf.log
6
$ grep 'ApiTotalUsage' sf.log
ApiTotalUsage,2026-03-11T02:16:00Z,005abc,203.0.113.9,5000 calls
```

6 экспортов и 5000 API-вызовов за 2 минуты. Дальше — определить, какие именно объекты
утекли (по URI) и оценить ущерб.

## Частые ошибки и подводные камни

- **Не выгружать ELF ежедневно.** По умолчанию хранение короткое.
- **Игнорировать API-объём.** Скриптовая выкачка — главный признак.
- **Путать SetupAuditTrail и ELF.** Это разные объекты с разным доступом.
- **Забыть про connected apps.** OAuth-доступ без пароля.
- **Смотреть только успехи.** Неудачные входы показывают разведку.

## Что мы теперь знаем

- ELF фиксирует ReportExport, ApiTotalUsage, Login, ApexExecution и др.
- Хранение короткое (обычно 1 день) — выгружай ежедневно.
- Массовый экспорт + API-выкачка = кража данных.
- Connected apps/OAuth — доступ без пароля.
- Реакция: revoke сессий и токенов, откат настроек.

## Что фиксировать в отчёте

| Что | Зачем |
|-----|-------|
| Типы и объём событий | картина активности |
| CLIENT_IP и USER_ID | атрибуция |
| Список выгруженных отчётов/объектов | масштаб утечки |
| Изменения Setup Audit Trail | воздействие |
| Действия по устранению | реакция |

## Расширенный пример: уход сотрудника или атака?

Не всякая массовая выгрузка — атака. Спорный случай: сотрудник перед увольнением выгружает
клиентскую базу. По логам это выглядит как кража, но юридически это может быть нарушением
политики, а не взломом. Отличить помогает контекст:

- **Признаки легитимного пользователя**: знакомый `CLIENT_IP` (офис), обычное рабочее время,
  действия в течение недель, стандартные отчёты.
- **Признаки компрометации**: новый `CLIENT_IP`, ночное время, вход сразу после серии
  неудачных попыток, незнакомое устройство.

Смотри **`Login`** и **`ReportExport`** вместе. Если входы всегда с одного IP, а потом
появляется выгрузка с другого — возможно, аккаунт украли. Если IP тот же, но объём вырос —
это, скорее, «человек перед увольнением».

Полезно проверить **`ApiTotalUsage`**: обычный пользователь не делает тысячи API-вызовов.
Скриптовая выкачка (Dataloader, `simple_salesforce`) оставляет ровный поток вызовов,
нехарактерный для ручной работы в интерфейсе. Это отличает автоматизацию от человека.

## Настройка Event Monitoring и правовые аспекты

Event Log File — часть продукта **Event Monitoring**, который может требовать отдельной
лицензии. По умолчанию файлы хранятся **один день**, поэтому ключевая практика —
**ежедневная выгрузка** в собственное хранилище. Без этого расследование «постфактум»
невозможно: события просто исчезнут.

Правовые аспекты:

- **Setup Audit Trail** доступен дольше (до 180 дней в интерфейсе) — для изменений настроек;
- **Login History** хранится ограниченно — выгружай вместе с ELF;
- **GDPR/персональные данные**: выгрузки содержат данные клиентов; соблюдай минимизацию;
- **Chain of custody**: фиксируй время выгрузки, список файлов и их хеши.

В отчёте разделяй «что произошло» (события) и «что это значит» (интерпретация). Это важно,
когда вывод влияет на кадровое или юридическое решение.

## Чек-лист разбора Salesforce

1. Уточни **период** и **пользователей**.
2. Выгрузи ELF **за каждый день** окна (иначе часть потеряется).
3. Отфильтруй **ReportExport**, **ApiTotalUsage**, **Login**, **SetupAuditTrail**.
4. Посчитай **объёмы**: аномальный рост API-вызовов — ключевой признак.
5. Проверь **CLIENT_IP** и **USER_ID** на совпадения между учётками.
6. Сопоставь с **Login History** и изменениями настроек.

## Поля ELF, которые стоит знать

Понимание полей ускоряет разбор:

| Поле | Что даёт |
|------|----------|
| EVENT_TYPE | тип события (ReportExport, Login…) |
| TIMESTAMP | время (UTC) |
| USER_ID | кто действовал |
| CLIENT_IP | откуда |
| URI | объект/страница |
| LOGIN_STATUS | успех/отказ входа |
| ROWS_PROCESSED | объём обработанных данных |

Поле **ROWS_PROCESSED** особенно полезно: массовый экспорт виден по числу строк. Вместе с
`URI` оно показывает, **какие именно объекты** утекли — это основа оценки ущерба. А
сопоставление `USER_ID` и `CLIENT_IP` между событиями выявляет автоматизированную выкачку:
один скрипт, один адрес, тысячи строк.

## Что писать в отчёте

Отчёт по Salesforce фиксирует: **период** и **полноту** выгрузки ELF, **список событий** с
объёмами (`ROWS_PROCESSED`), **CLIENT_IP** и **USER_ID**, а также **изменения Setup Audit
Trail**. Отдельно оцени **ущерб**: какие объекты и сколько записей утекли (по URI и числу
строк). Если однозначно отличить «уход сотрудника» от «компрометации» не удалось, так и
напиши — это честный и корректный вывод. В конце перечисли меры: отзыв сессий, ограничение
экспорта, включение Event Monitoring.
