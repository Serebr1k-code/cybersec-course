## Вопрос, с которого всё начинается

Секрет (ключ API, пароль БД) попал к атакующему. Где он хранился и кто его читал?
Менеджеры секретов ведут аудит. Разберём.

## Наш пример: менеджер секретов

## Шаг 1: что это

Менеджер секретов (HashiCorp Vault, AWS Secrets Manager, Azure Key Vault) хранит секреты
централизованно и выдаёт их по запросу с проверкой прав.

## Шаг 2: аудит-логи

Vault:

```
$ vault audit list
$ tail /var/log/vault_audit.log | jq '.request.path'
"secret/data/db"
```

AWS Secrets Manager — через CloudTrail:

```
$ grep GetSecretValue cloudtrail.json | jq '.sourceIPAddress'
"203.0.113.5"
```

Видно: **кто**, **какой секрет** и **с какого IP** читал.

## Шаг 3: кто имел доступ

Права задаются политиками:

- кто может читать секрет;
- есть ли wildcard (`*`) в путях;
- временные креды (STS) — когда истекают.

```
$ vault policy read db-app
```

Широкие политики — частая причина компромисса.

## Шаг 4: KMS и шифрование

Секреты шифруются **ключом** (KMS). Доступ к ключу логируется отдельно:

```
$ aws kms list-keys
$ grep Decrypt cloudtrail.json
```

Если атакующий получил права на `Decrypt` — он читает зашифрованные секреты.

## Шаг 5: что искать

- необычные `GetSecretValue`/`Decrypt`;
- доступ с внешних IP;
- расширение прав (новые политики);
- использование секрета сразу после чтения.

## Что мы теперь знаем

- Менеджеры централизуют секреты с проверкой прав.
- Аудит-логи фиксируют чтение (кто/что/откуда).
- Политики определяют доступ; wildcard опасен.
- KMS-ключи логируют Decrypt отдельно.
- Сопоставляй чтение секрета с его использованием.

## Если не сработало

- Аудит не включён? Смотри CloudTrail/логи приложений.
- Секрет ротирован? Проверь, был ли он скомпрометирован.
- Нужны права? Читай политики.
