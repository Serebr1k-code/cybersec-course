## Вопрос, с которого всё начинается

В крупных расследованиях и судах используют устоявшиеся платформы — **FTK** (AccessData)
и **EnCase** (OpenText). Они проверены годами и дают принимаемые судом отчёты. Разберём,
что они делают.

## Наш пример: рабочий процесс

## Шаг 1: общий подход

Обе платформы работают по схеме:

1. **добавить образ** (E01/DD/AFF);
2. **проиндексировать** содержимое;
3. **искать** по ключевым словам/типам;
4. **проанализировать** артефакты;
5. **сформировать отчёт**.

## Шаг 2: форматы образов

E01 (Expert Witness Format) — формат EnCase с чек-суммами и сжатием:

```
$ file evidence.E01
evidence.E01: EWF/Expert Witness format
```

FTK читает E01, DD, AFF; EnCase — свои и чужие.

## Шаг 3: автоматизация

Ключевое преимущество — автоматический парсинг:

- реестр, MFT, `$LogFile`;
- браузеры, почта;
- журналы событий;
- восстановление удалённых;
- **карвинг** (FTK — силён в этом).

Плюс «known file filter»: отсеивает известные легитимные файлы (по хешам).

## Шаг 4: индексация

Индексация превращает образ в полнотекстовый поиск:

```
search: "invoice"
→ 14 hits across email, docs, browser
```

Это резко ускоряет поиск по ключевым словам (в т.ч. на других языках).

## Шаг 5: где применяются

- **крупные корпоративные** расследования;
- **юридические** дела (chain of custody);
- **eDiscovery** (FTK — часть экосистемы);
- когда нужен проверенный инструмент.

## Что мы теперь знаем

- FTK/EnCase — классические платформы.
- Работают с E01/DD/AFF.
- Автоматически парсят артефакты и карвят.
- Индексация даёт полнотекстовый поиск.
- Применяются в судебных/корпоративных делах.

## Если не сработало

- Формат не читается? Конвертируй образ.
- Нужен быстрый анализ? Индексируй и фильтруй.
- Нужна совместимость? Экспортируй в открытые форматы.

## Практический разбор: от E01 до отчёта

Разберём полный цикл на образе в формате E01. Сначала монтируем образ и
проверяем, что он читается:

```bash
$ ewfmount evidence.E01 /mnt/ewf
$ ls /mnt/ewf
ewf1
$ fls -r -p /mnt/ewf/ewf1 | wc -l
48312
```

Получили 48312 записей — образ живой. Проверяем целостность по сохранённому
внутри E01 хэшу:

```bash
$ ewfverify evidence.E01
ewfverify: MD5 hash stored in file: d41d8cd98f00b204e9800998ecf8427e
ewfverify: MD5 hash calculated over data: d41d8cd98f00b204e9800998ecf8427e
ewfverify: SUCCESS
```

Совпадение хэшей подтверждает, что образ не изменён. Далее индексируем и ищем
ключевое слово — это ядро работы платформы:

```bash
$ grep -a -r -i 'invoice' /mnt/ewf/ewf1 | head
Binary file /mnt/ewf/ewf1/.../mail.pst matches
```

В FTK/EnCase тот же поиск даёт 14 попаданий по почте, документам и браузеру —
с указанием пути и контекста.

## Форматы образов и их различия

| Формат | Расширение | Сжатие | Хэш внутри | Особенность |
|---|---|---|---|---|
| EWF/Expert Witness | E01 | да | MD5/SHA1 | формат EnCase |
| Raw/DD | dd/img | нет | нет | универсальный, простой |
| AFF | aff | да | да | открытый формат |
| AFF4 | aff4 | да | да | современный, контейнер |
| VHDX/VMDK | vhdx/vmdk | опц. | нет | для виртуалок |

Raw-образ прост, но не хранит хэш — целостность придётся доказывать отдельным
файлом контрольной суммы. E01 удобнее для суда: хэш и метаданные внутри.

## Целостность и хэши

- **При снятии.** Считай хэш источника и образа, фиксируй оба.
- **При передаче.** Веди журнал chain of custody с датами и подписями.
- **При анализе.** Работай только с копией, оригинал храни в опечатанном виде.
- **При экспорте.** Каждый извлечённый файл — с собственным хэшем.

Без хэш-верификации выводы нельзя использовать как доказательство.

## Карвинг: как восстанавливают удалённое

Карвинг ищет данные по сигнатурам, а не по метаданным. Это спасает, когда
файловая система повреждена или запись удалена. Основные сигнатуры:

| Тип | Сигнатура (hex) | ASCII |
|---|---|---|
| JPEG | FF D8 FF E0/E1 | — |
| PDF | 25 50 44 46 | %PDF |
| ZIP/DOCX | 50 4B 03 04 | PK.. |
| PNG | 89 50 4E 47 | .PNG |
| GZIP | 1F 8B | — |

```bash
$ scalpel -c scalpel.conf image.dd -o out/
$ ls out/jpg-1-0/
00000012.jpg  00004096.jpg
```

Скальпель и `photorec` восстанавливают по сигнатуре, но без имён и путей.
FTK карвит по тем же принципам, но с UI и дедупликацией по хэшам.

## Known File Filter и хэш-множества

- **NSRL.** Национальная библиотека эталонных хэшей: миллионы хэшей
  стандартных системных файлов.
- **KFF.** «Known File Filter» в FTK/EnCase отсеивает совпадающие файлы, чтобы
  аналитик видел только необычное.
- **Обратный фильтр.** «Известные вредоносные» хэши, наоборот, подсвечиваются.
- **Ограничение.** Файл, изменённый на один байт, перестаёт совпадать с хэшем
  и не отсеивается.

## Ограничения и типичные ошибки

- **Проприетарность.** EnCase и FTK — коммерческие; лицензии дороги, а форматы
  отчётов частично закрыты.
- **Время индексации.** Полнотекстовый индекс терабайтного образа строится
  часами; планируй окно заранее.
- **Зашифрованные контейнеры.** Индекс и карвинг бессильны против шифрования —
  нужен пароль/ключ.
- **Ложные срабатывания карвинга.** Сигнатура может встретиться в случайных
  данных; проверяй каждый восстановленный файл.
- **Перезапись.** Если кластеры перезаписаны, карвинг вернёт мусор или ничего.

## Проверка результата

```bash
$ md5sum out/jpg-1-0/00000012.jpg
$ file out/jpg-1-0/00000012.jpg
out/jpg-1-0/00000012.jpg: JPEG image data, JFIF standard 1.01
```

Каждый восстановленный файл проверяй по типу и открывай глазами — только так
подтверждается, что карвинг нашёл именно то, что нужно.

## Практический разбор: таймлайн из образа

Соберём единый таймлайн по всему образу — это то, ради чего платформы и нужны.
Сначала извлекаем события файловой системы через Sleuth Kit:

```bash
$ fls -r -m / image.dd > body.txt
$ mactime -b body.txt -d 2026-01-13..2026-01-14 > timeline.csv
$ head -4 timeline.csv
Date,Size,Type,Mode,UID,GID,Meta,File Name
2026-01-13T22:41:03Z,1024,m...,rw-r--r--,0,0,1284,/tmp/stage2.sh
```

Запись о создании `/tmp/stage2.sh` в 22:41 — точка входа атакующего. Сопоставим
её с логами аутентификации и браузера, импортированными тем же инструментом.
FTK/EnCase делают это автоматически: они парсят реестр, MFT, почту и браузеры
и раскладывают события по времени.

## Автоматизация и скрипты

- **Пакетный режим.** FTK Imager CLI и EnCase CLI позволяют ставить задания
  скриптом, без UI.
- **Экспорт в CSV.** Результаты выгружаются таблицей — удобно для дальнейшего
  анализа в Python/pandas.
- **Хуки и плагины.** EnCase поддерживает EnScript, FTK — внешние утилиты.
- **Повторяемость.** Скрипт фиксирует точные шаги — это требование к
  доказуемости и воспроизводимости.

```bash
$ ftkimager --verify --export-csv evidence.E01 out.csv
```

## Проверка результата

```bash
$ wc -l timeline.csv
284512 timeline.csv
$ grep -i 'stage2' timeline.csv
```

Если событие видно в таймлайне и подтверждается независимым источником (лог
аутентификации), вывод устойчив.

## Сравнение FTK и EnCase

| Критерий | FTK | EnCase |
|---|---|---|
| Форматы | E01, DD, AFF | E01 и свои |
| Карвинг | очень силён | сильный |
| Индексация | полнотекстовая | полнотекстовая |
| Скрипты | внешние утилиты | EnScript |
| Экосистема | eDiscovery | корпоративная |
| Стоимость | коммерческая | коммерческая |

Выбор зависит от задачи: FTK часто берут за карвинг и eDiscovery, EnCase — за
глубокую интеграцию и корпоративные процессы. Оба читают чужие образы, поэтому
данные переносимы.

## Отчёт и его структура

Отчёт форензик-платформы обычно содержит:

- **метаданные дела** — номер, аналитик, дата;
- **хэши образа** — доказательство целостности;
- **найденные артефакты** — с путями и временем;
- **снимки и выдержки** — подтверждение находок;
- **методику** — какие инструменты и фильтры применялись;
- **ограничения** — что не удалось установить.

Отчёт должен быть воспроизводим: другой аналитик по тем же шагам обязан прийти
к тем же выводам. Поэтому фиксируй версии инструментов и параметры запуска.

## Ограничения и типичные ошибки

- **Слепое доверие платформе.** Автоматический парсинг ошибается; проверяй
  ключевые находки вручную.
- **Забытый оригинал.** Работать нужно с копией; оригинал — в опечатанном виде.
- **Отсутствие хэшей.** Без контрольных сумм результат недоказуем.
- **Переиндексация.** Повторный запуск может изменить индекс; фиксируй состояние.

## Типичные сценарии применения

- **Корпоративное расследование.** Изъятие ноутбука сотрудника, поиск утечки
  документов, построение таймлайна по реестру и почте.
- **eDiscovery.** Отбор релевантных документов по ключевым словам для
  юридического дела; FTK встроен в эту экосистему.
- **Судебная экспертиза.** Нужен проверенный инструмент с воспроизводимой
  методикой и отчётом, принимаемым судом.
- **Инцидент-респонс.** Быстрый карвинг и индексация, чтобы понять масштаб.

## Ограничения метода

- **Стоимость и лицензии.** Обе платформы коммерческие; бюджет и обучение —
  барьер для небольших команд.
- **Проприетарные форматы отчётов.** Переносимость ограничена; для обмена
  используют CSV/PDF.
- **Ложные срабатывания.** Автопарсинг и карвинг ошибаются; нужна ручная
  верификация ключевых находок.
- **Ресурсы.** Индексация больших образов требует RAM и времени; планируй окно.

## Связь с другими инструментами

FTK и EnCase не работают в вакууме: их результаты часто переносят в открытые
инструменты. Таймлайн из FTK удобно открывать в `Timesketch`, а образы —
монтировать через `ewfmount` и разбирать Sleuth Kit. Обратный путь тоже
полезен: находки из `fls`/`mactime` можно импортировать в платформу для
единого отчёта.

Такая гибридная схема даёт лучшее из двух миров: скорость и скриптуемость
открытых утилит плюс воспроизводимый отчёт коммерческой платформы для суда.
