## Вопрос, с которого всё начинается

Тебе дали образ флешки `usb.img`. Пользователь утверждает, что «ничего не удалял», но задание говорит: на носителе был файл с флагом, и его стёрли. Задача — вернуть удалённое содержимое.

Флешки, SD-карты камер и EFI-разделы используют файловую систему **FAT**. Она устроена предельно просто — без журналов и сложных деревьев, — поэтому её удобно разбирать вручную. Пройдём весь путь от образа до восстановленного файла.

## Наш пример: образ `usb.img`

Первый вопрос — что это за носитель и какая на нём файловая система. Команда `file -s` смотрит на «магические байты» и читает параметры:

```bash
$ file -s usb.img
usb.img: DOS/MBR boot sector, OEM-ID "mkfs.fat", sectors/cluster 8,
         Media 0xf8, sectors 204800, FAT (32 bit), sectors/FAT 1595,
         reserved 32, serial 0x1a2b3c4d
```

Вывод говорит: это **FAT32**. Важные параметры — `sectors/cluster 8` (размер кластера в секторах) и `reserved 32` (зарезервированных секторов). **Кластер** — минимальная единица хранения файла: даже файл в один байт занимает целый кластер.

## Шаг 1: находим начало раздела

Образ начинается с таблицы разделов, а файловая система лежит внутри раздела со своим смещением. Инструмент `mmls` показывает карту:

```bash
$ mmls usb.img
DOS Partition Table
      Slot      Start        End          Length       Description
      00:  -----   0000000000   0000002047   0000002048   Primary Table (#0)
      02:  00:00   0000004096   000000206847 000000202752  Win95 FAT32 (0x0b)
```

FAT-раздел начинается с сектора **4096**. Запомним это смещение — все дальнейшие команды будут работать внутри раздела, а не с начала образа.

## Шаг 2: читаем параметры файловой системы

Теперь `fsstat` (из набора sleuthkit) читает **загрузочный сектор** раздела. В нём лежит **BPB** (BIOS Parameter Block) — таблица со всеми геометрическими параметрами:

```bash
$ fsstat -o 4096 usb.img | head -12
File System Type: FAT32
OEM Name: mkfs.fat
Sector Size: 512
Cluster Size: 4096
Total Cluster Range: 2 - 25340
```

`fsstat` сам вычисляет то, что иначе пришлось бы считать вручную: где начинается таблица FAT, где — область данных. Но полезно понимать, откуда берутся эти числа: `fat_start = reserved_sectors × bytes_per_sector`, а `data_start` — уже за таблицами. Если `fsstat` недоступен, эти смещения считают по BPB.

## Шаг 3: смотрим содержимое и находим удалённое

Команда `fls` листает каталоги. Ключ `-r` — рекурсивно, а `-d` — показать только **удалённые** записи:

```bash
$ fls -o 4096 -r -d usb.img
r/r * 3: flag.txt
d/d * 4: secret
r/r * 5: secret/notes.txt
```

Звёздочка `*` перед номером — маркер удалённой записи, а сам номер (`3`, `4`, `5`) — это **inode** (номер записи в каталоге). Видим три удалённых объекта: файл `flag.txt`, каталог `secret` и файл `secret/notes.txt` внутри него.

## Шаг 4: восстанавливаем файл

Зная inode, читаем содержимое командой `icat`:

```bash
$ icat -o 4096 usb.img 3 > flag.txt
$ cat flag.txt
flag{fat_recovery_works}
```

Флаг восстановлен. Почему это сработало, если файл удалили? Разберём механику.

## Шаг 5: понимаем, почему удалённое восстановимо

В FAT данные лежат не подряд, а в **цепочке кластеров**. Есть таблица **FAT** — массив, где на каждый кластер приходится одна запись. Запись говорит, что делать дальше: указывает на следующий кластер цепочки или помечает конец файла (`EOC`, End Of Chain) либо свободный кластер (`0x000`).

Когда файл удаляют, система делает две вещи:

- в записи каталога заменяет **первый байт имени** на `0xE5` — это маркер «запись удалена»;
- в таблице FAT помечает кластеры файла как свободные (`0x000`).

Но **данные в кластерах остаются** на месте, пока их не перезапишут новым файлом. `icat` читает запись каталога (размер и первый кластер целы), идёт по цепочке и собирает содержимое. Пока кластеры не переиспользованы — файл восстанавливается целиком.

Именно поэтому `0xE5` — ключ к recovery: остальные поля записи (размер, первый кластер, время) часто сохраняются.

## Шаг 6: если метаданные не уцелели

Иногда кластеры уже перезаписаны, и `icat` вернёт мусор. Тогда остаётся **карвинг** — поиск файлов по их внутренним сигнатурам (заголовкам), без опоры на файловую систему. Инструмент `photorec` ищет JPEG, PNG, PDF, ZIP по сигнатурам:

```bash
$ photorec usb.img
```

Он не знает имён и путей, но вытаскивает целые файлы из «сырых» кластеров. Это запасной путь, когда метаданные утрачены.

## Полный разбор: от BPB до восстановленного файла

Прогоним разбор `usb.img` в один сценарий.

1. **Находим раздел.** `mmls usb.img` — смещение раздела.
2. **Читаем BPB.** `fsstat -f fat -o <off> usb.img` — размер кластера, число FAT, метка тома.
3. **Листаем каталог.** `fls -f fat -o <off> usb.img` — видим файлы и, помеченные `*`, удалённые.
4. **Восстанавливаем.** `icat -f fat -o <off> usb.img <inode>` — достаём содержимое удалённого.
5. **Почему получилось.** При удалении в FAT обнуляется запись в каталоге (первый байт имени → `0xE5`), но **данные в кластерах не стираются**, пока не перезаписаны.
6. **Если метаданные погибли.** Карвинг по сигнатурам (`photorec`), когда запись каталога уже не найти.

## Шпаргалка FAT

| Структура | Где | Что даёт |
|-----------|-----|----------|
| Boot Sector (BPB) | сектор 0 | размер кластера, число FAT |
| FAT #1/#2 | после BPB | цепочки кластеров |
| Root Directory | FAT12/16 — фикс.; FAT32 — кластер | записи 8.3 и LFN |
| Data Region | далее | содержимое файлов |

Отличия версий: FAT12 (флешки, дискеты), FAT16 (малые тома), FAT32 (большие). LFN хранит длинные имена отдельными записями — при восстановлении это важно.

## Частые вопросы

**Почему удалённый файл восстанавливается?** Стирается только запись каталога и цепочка FAT, данные остаются в кластерах.

**Что ломает восстановление?** Перезапись кластеров новыми файлами — чем меньше писали на носитель, тем выше шанс.

**Чем FAT отличается от NTFS для форензика?** У FAT нет журнала и альтернативных потоков; меньше метаданных, проще структура.

**Как связать файл с флешкой?** По метке тома и по VSN из `MountedDevices`/LNK (см. урок про USB).

## Что мы теперь знаем

- FAT — простая ФС съёмных носителей и EFI-разделов; параметры лежат в BPB загрузочного сектора.
- Раздел начинается со смещения из `mmls`; `fsstat` читает его параметры (кластер, начало FAT).
- Файл — **цепочка кластеров**, которую задаёт таблица FAT.
- При удалении первый байт имени становится `0xE5`, а кластеры помечаются свободными, но данные остаются.
- `fls -r -d` находит удалённые записи, `icat` восстанавливает содержимое, пока кластеры не перезаписаны.
- Когда метаданные утрачены, помогает карвинг (`photorec`) по сигнатурам.

## Как отличить FAT12, FAT16 и FAT32

Определить версию можно по числу кластеров и по разметке BPB:

- **FAT12** — меньше 4085 кластеров; записи FAT по 12 бит (упакованы парами).
- **FAT16** — от 4085 до 65524 кластеров; записи по 16 бит.
- **FAT32** — 65525 и больше; записи по 32 бита, корневой каталог — обычная цепочка кластеров.

Разметка тоже различается: у FAT12/16 есть поле числа секторов корневого каталога (`RootEntCnt`) и поле `FATSz16`, а у FAT32 они обнулены, а вместо них — `FATSz32`, номер корневого кластера (`RootClus`) и адрес копии загрузочного сектора (`BkBootSec`). Строка `FAT32` по смещению `0x52` — лишь метка, полагаться на неё нельзя: некоторые реализации её не пишут. Надёжнее посчитать число кластеров и сверить реальные поля.

Практический приём: `fsstat` сам печатает `File System Type`, но если его нет, прочтите `BPB_BytsPerSec`, `BPB_SecPerClus`, `BPB_TotSec` и посчитайте `count_of_clusters = (TotSec - reserved - fats*size) / SecPerClus`. Полученное число однозначно указывает версию.

## VFAT: как хранятся длинные имена

В исходном FAT имена были формата **8.3**: до восьми символов имени и три — расширения, в кодировке OEM. Длинные имена появились с расширением **VFAT** и хранятся отдельными записями каталога.

Каждое длинное имя занимает несколько записей перед короткой. В каждой такой записи:

- атрибут выставлен в `0x0F` (недоступная комбинация — маркер LFN);
- байт `0x00` — порядковый номер части с флагом последней (`0x40`);
- байт `0x0D` — **контрольная сумма** короткого имени;
- символы имени лежат в трёх полях (смещения `0x01`, `0x0E`, `0x1C`) в UTF-16LE.

```python
def lfn_checksum(short):           # short — 11 байт '8.3'
    s = 0
    for b in short:
        s = (((s & 1) << 7) + (s >> 1) + b) & 0xFF
    return s
```

Порядок записей обратный: первая физически — **последняя** часть имени. Поэтому при восстановлении их собирают от последней к первой. Контрольная сумма связывает LFN с коротким именем: если она не совпадает, запись битая. Именно LFN-записи чаще всего восстанавливают в CTF — они лежат рядом с `0xE5`-записями и содержат полное имя удалённого файла.

## Инструменты: mmls, sleuthkit, mtools

Рабочий набор для FAT:

| Инструмент | Назначение |
|-----------|-----------|
| `mmls` | карта разделов образа |
| `fsstat -f fat` | параметры ФС, начало FAT |
| `fls -r -d` | файлы, включая удалённые |
| `icat <inode>` | содержимое файла по inode |
| `fatcat` | прямой доступ к кластерам |
| `mtools` (`mdir`/`mcopy`) | работа с образом без root |
| `photorec` | карвинг при утрате метаданных |

`mtools` удобен тем, что не требует монтирования: `mdir -i usb.img ::/` листает корень, а `mcopy -i usb.img ::/secret.txt .` копирует файл. Монтировать образ через `mount -o loop,ro` тоже можно, но на живых системах лучше работать с **копией** образа и только на чтение — монтирование в режиме записи может изменить метки времени.

## Где пригодится

- **CTF:** образы флешек, SD-карт, EFI-разделов — удалённые файлы и скрытые данные.
- **DFIR:** разбор съёмных носителей, которые не NTFS.
- **Data recovery:** восстановление фото/видео с камер.
- **Пентест:** анализ извлечённых флешек и прошивок.
