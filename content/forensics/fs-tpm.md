## Вопрос, с которого всё начинается

Нужно доказать, что система загружалась штатно (или что загрузчик подменили). У
современных ПК есть **TPM** — чип, который измеряет загрузку. Разберём, как это
использовать в форензике.

## Наш пример: ПК с TPM 2.0

## Шаг 1: что такое TPM и PCR

TPM — защищённый чип. Он хранит **PCR** (Platform Configuration Registers) — хеши
компонентов загрузки. Каждый этап загрузки «измеряется»: хеш записывается в PCR.

```
$ tpm2_pcrread sha256:0,4,7
sha256:
  0 : 0x3d4b...  (firmware)
  4 : 0x9a1c...  (boot loader)
  7 : 0x...      (secure boot policy)
```

## Шаг 2: измеренная загрузка

Цепочка:

1. прошивка измеряет себя → PCR0;
2. загрузчик → PCR4;
3. ОС-компоненты → PCR7+.

Если хотя бы один компонент изменён, PCR меняется. Это **доказательство** состояния
загрузки.

## Шаг 3: связь с BitLocker

BitLocker «запечатывает» ключ на значения PCR. Если PCR не совпали (загрузчик
подменили) — ключ не выдаётся:

```
Sealed to PCRs 0,2,4,11
```

Значит, изменение загрузчика **ломает** расшифровку — защита и улика одновременно.

## Шаг 4: что можно доказать

- загрузка шла штатной цепочкой (PCR совпадают с эталоном);
- **или** была подмена (PCR не совпадают);
- момент изменения (по журналу);
- связь с ключами BitLocker.

## Шаг 5: практика

- снять PCR: `tpm2_pcrread`;
- сверить с эталоном известной конфигурации;
- проверить event log (TCG log);
- учесть, что TPM можно сбросить (с потерей ключей).

## Что мы теперь знаем

- TPM хранит PCR — хеши компонентов загрузки.
- Измеренная загрузка фиксирует каждый этап.
- BitLocker печатает ключ на PCR.
- Расхождение PCR = подмена/изменение.
- PCR снимают `tpm2_pcrread`, сверяют с эталоном.

## Если не сработало

- TPM сброшен? Ключи потеряны, PCR пусты.
- Нет эталона? Сравни с известной конфигурацией.
- Нужен лог? Читай TCG event log.

## Разбор PCR и TCG event log

Снимем значения PCR и сверим с эталонной конфигурацией:

```
$ tpm2_pcrread sha256:0,1,2,3,4,7
sha256:
  0 : 0x3d4b8e...  (UEFI firmware)
  1 : 0x9a1c22...  (firmware config)
  2 : 0x7f3a01...  (option ROMs)
  3 : 0xb2c4d5...  (firmware config)
  4 : 0x11e9aa...  (boot loader / shim)
  7 : 0xcc0912...  (Secure Boot policy)
```

Теперь читаем TCG event log — он показывает, **какие** измерения дали эти
хеши:

```
$ tpm2_eventlog /sys/kernel/security/tpm0/binary_bios_measurements | head -30
Event 1: EV_S_CRTM_VERSION
  SHA256: 3d4b8e...
Event 2: EV_EFI_BOOT_SERVICES_APPLICATION
  Path: \EFI\BOOT\BOOTX64.EFI
```

Event log превращает абстрактный хеш в понятную запись: «измерен загрузчик
BOOTX64.EFI». Если путь указывает на неожиданный файл — загрузчик подменён.

## Таблица: назначение PCR

| PCR | Что измеряет |
|---|---|
| 0 | CRTM, UEFI-прошивка |
| 1 | конфигурация прошивки |
| 2 | option ROM (видео, сеть) |
| 3 | конфигурация прошивки |
| 4 | загрузчик (shim/GRUB) |
| 5 | GPT/разметка диска |
| 6 | режимы питания, wake |
| 7 | политика Secure Boot |
| 8–15 | загрузчик, ОС, драйверы |

Понимание «какой PCR за что отвечает» критично: изменение PCR4 — подмена
загрузчика, PCR7 — отключение Secure Boot, PCR5 — правка разметки диска.

## BitLocker: как проверяется seal

BitLocker «печатает» ключ (VMK) на набор PCR. Расшифровка удаётся только при
совпадении:

```
$ manage-bde -status C:
    Key Protectors:
      TPM
      Numerical Password
$ manage-bde -protectors -get C: -type tpm
    PCR Validation Profile: 0,2,4,11
```

Если PCR не совпали (например, загрузчик обновлён или подменён), TPM не
выдаёт VMK — система просит recovery-ключ. Это одновременно защита и улика:
запрос recovery-ключа в логах означает, что загрузочная цепочка изменилась.

## Практика: сверка с эталоном

Порядок действий при расследовании:

```
$ tpm2_pcrread sha256:all > /cases/pcr_now.txt
$ diff /cases/pcr_baseline.txt /cases/pcr_now.txt
4c4
< 4 : 0x11e9aa...
---
> 4 : 0x7d3b90...
```

Эталон снимается с заведомо чистой машины той же модели/прошивки. Если
эталона нет — сравнивай с известной конфигурацией или с vendor-значениями.
Расхождение по конкретному PCR укажет, **какой** компонент изменён.

## Ограничения и подводные камни

- **TPM можно сбросить.** `tpm2_clear` обнуляет PCR и уничтожает ключи — после
  сброса доказать штатную загрузку прошлых сессий нельзя.
- **PCR не хранят историю.** Это «накопительные» хеши: они показывают текущую
  цепочку, но не список прошлых значений — история только в event log.
- **Измерение ≠ защита.** PCR доказывают состояние, но не мешают загрузке;
  защита появляется только в связке с seal (BitLocker).
- **Firmware TPM vs дискретный.** Программный (fTPM) менее устойчив к
  подмене, чем дискретный чип — учитывай при оценке доверия.
- **Обновление прошивки меняет PCR.** Плановое обновление BIOS тоже изменит
  PCR0/4 — не путай его с атакой, проверяй журнал обновлений.

## Если сработало

Расхождение PCR подтвердилось — зафиксируй доказательство и оцени масштаб:

1. Выгрузи TCG event log целиком (`tpm2_eventlog` → файл).
2. Сохрани текущие PCR и эталон рядом, с хешами.
3. Определи изменённый компонент по event log (какой файл измерен последним
   нештатно).
4. Проверь, был ли запрошен recovery-ключ (события BitLocker).
5. Сопоставь время изменения с журналами обновлений и входа в систему.

Если подмена загрузчика подтверждена, считай систему скомпрометированной на
уровне ниже ОС: любые средства защиты внутри ОС уже ненадёжны.

## Сценарии атак на цепочку загрузки

TPM/измеренная загрузка интересны прежде всего как **защита от конкретных
атак**:

| Атака | Как проявляется | Что покажет TPM |
|---|---|---|
| Evil maid | подмена загрузчика на диске | PCR4 не совпадёт |
| Bootkit | вредоносный загрузчик | PCR4/8+ изменены |
| Отключение Secure Boot | правка прошивки | PCR7 не совпадёт |
| Подмена option ROM | вредоносная прошивка устройства | PCR2 изменён |
| Сброс TPM | очистка измерений | ключи потеряны, PCR пусты |

Каждая строка — это и техника атакующего, и конкретный PCR, который её
выдаст. Расследование сводится к поиску несовпавшего PCR.

## Пример: evil maid в деталях

Атакующий с физическим доступом меняет загрузчик, чтобы внедрить код до ОС.
Последовательность:

```
$ tpm2_pcrread sha256:4
sha256:
  4 : 0x7d3b90...   # не совпадает с эталоном 0x11e9aa
$ tpm2_eventlog /sys/kernel/security/tpm0/binary_bios_measurements \
    | grep -A3 'EV_EFI_BOOT_SERVICES_APPLICATION'
  Path: \EFI\BOOT\BOOTX64.EFI
  SHA256: 7d3b90...
```

Event log показывает, что измеренный загрузчик `BOOTX64.EFI` имеет хеш,
отличный от эталонного. При этом BitLocker, если он запечатан на PCR4,
потребует recovery-ключ — владелец заметит аномалию при следующей загрузке.

## Быстрый триаж цепочки загрузки

```
$ tpm2_pcrread sha256:0,4,7
$ tpm2_eventlog /sys/kernel/security/tpm0/binary_bios_measurements | tail -40
$ manage-bde -protectors -get C: -type tpm
$ journalctl -k | grep -i 'tpm\|measured'
```

Сначала снимаем PCR, затем смотрим event log (какой компонент измерен
последним), затем профиль BitLocker и ядерные сообщения TPM. Расхождение PCR4
без записи об обновлении — сигнал подмены загрузчика.

## Пример: доказательство штатной загрузки

Иногда задача обратная — **доказать**, что подмены не было:

```
$ tpm2_pcrread sha256:0,4,7 > /cases/pcr_incident.txt
$ diff /cases/pcr_baseline.txt /cases/pcr_incident.txt && echo "MATCH"
MATCH
```

Совпадение всех PCR с эталоном известной чистой конфигурации доказывает, что
загрузочная цепочка не менялась. Это опровергает версию о bootkit и
позволяет сосредоточить расследование на уровне ОС и приложений.

## Что фиксировать в отчёте

- значения всех измеренных PCR и эталон, с которым сравнивали;
- выгрузку TCG event log;
- профиль BitLocker и события запроса recovery-ключа;
- версию прошивки и историю её обновлений;
- вывод: штатная цепочка / подмена (с указанием изменённого компонента).

Отчёт по TPM ценен именно парой «эталон ↔ текущее состояние»: без эталона
отдельные значения PCR ничего не доказывают.

## Частая ошибка: доверять одному PCR

Новичок видит, что PCR0 совпал, и заключает «система чистая». Но подмена
загрузчика отражается в PCR4, отключение Secure Boot — в PCR7, правка
разметки — в PCR5. Проверяй весь профиль измерения (0,2,4,7,11), а не один
регистр. Одиночное совпадение ничего не доказывает.

## Итог

TPM даёт криптографическое доказательство состояния загрузки через PCR и
TCG event log. В связке с BitLocker он превращает изменение загрузчика в
невозможность расшифровки — защиту и улику одновременно. Ключевые шаги:
снять PCR, прочитать event log, сверить с эталоном, учесть возможность сброса
TPM.

## Краткий чек-лист

1. `tpm2_pcrread sha256:all` — снять текущие PCR.
2. `tpm2_eventlog` — прочитать, какие компоненты измерены.
3. Сравнить с эталоном чистой конфигурации.
4. Проверить профиль BitLocker (`manage-bde -protectors -get`).
5. Учесть возможность сброса TPM и историю обновлений прошивки.
6. Зафиксировать вывод: штатная цепочка или подмена.

Пункт 5 обязателен: без него плановое обновление BIOS можно принять за атаку,
а реальную подмену — за норму. Контекст обновлений отделяет одно от другого.

## Что дальше изучить

TPM — часть большой темы доверенной загрузки. Дальше изучи UEFI Secure Boot
(цепочка подписей загрузчиков), measured boot на Linux (`systemd-boot`,
`tpm2-totp`), аттестацию удалённых хостов (remote attestation) и аппаратные
модули HSM. Все они опираются на тот же принцип: измерять каждый этап и
сравнивать с эталоном, а защиту строить на привязке ключей к измерениям.
