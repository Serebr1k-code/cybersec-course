## Вопрос, с которого всё начинается

На современном Linux почти всё логируется через **systemd**, а его журнал — не текстовый
файл, а бинарная база. Ты не можешь просто `cat` её. Как её прочитать и что она даёт
следователю?

## Наш пример: журнал хоста

```
/var/log/journal/<machine-id>/system.journal
```

Это **бинарный** журнал **journald**. Файл разбит на структурированные записи: каждая имеет
поля `_PID`, `_UID`, `_COMM` (имя команды), `_EXE`, `MESSAGE` и другие. Именно поля, а не
только текст, делают журнал удобным для расследования.

## Шаг 1: почему журнал бинарный

Текстовые логи (`/var/log/syslog`) — это просто строки. journald хранит структуру: у каждой
записи есть метаданные, по которым можно фильтровать точно. Плата — формат непрозрачен для
`grep`. Зато `journalctl` умеет фильтровать по полю:

```
$ journalctl _COMM=wget --since "2025-05-01"
May 01 09:03:20 host wget[2210]: download http://198.51.100.9/x
```

Это значит: «покажи все записи, где имя команды — wget». Такой запрос по обычному логу
потребовал бы хрупкого grep.

## Шаг 2: где лежит и как читать копию

Если у тебя образ диска или копия каталога, а не живая система, указывай каталог явно:

```
$ journalctl -D /mnt/image/var/log/journal --no-pager
```

`-D` (directory) читает журнал из указанного каталога, не трогая систему. Для машин с
проблемной машиной это основной приём.

## Шаг 3: экспорт в переносимый вид

Чтобы анализировать журнал скриптами, его выгружают:

```
$ journalctl -D /mnt/image/var/log/journal -o json > journal.json
$ journalctl -D /mnt/image/var/log/journal -o export > journal.export
```

Формат `json` даёт по объекту на запись со всеми полями; `export` — построчный
key=value-формат. В нашем примере ты видишь записи с `_COMM=wget`, `_COMM=bash`, `_UID=0` —
это уже структурированные поля, готовые к фильтрации.

## Шаг 4: ключевые поля

| Поле | Что означает |
|------|--------------|
| `_PID` | идентификатор процесса |
| `_UID` | пользователь, запустивший процесс |
| `_COMM` | имя команды (wget, bash) |
| `_EXE` | полный путь исполняемого файла |
| `MESSAGE` | сам текст сообщения |
| `_SYSTEMD_UNIT` | юнит, к которому относится запись |
| `_BOOT_ID` | идентификатор загрузки |

По `_EXE` видно, откуда реально запущена команда, а по `_BOOT_ID` записи разделяются между
перезагрузками — это критично для таймлайна.

## Шаг 5: что искать

Цепочка `wget` → `bash` от `_UID=0` (как в нашем примере) — скачивание и запуск скрипта от
root. Смотри также записи `systemd` о старте юнитов: если появился новый `.service`, это
закрепление. А `_SYSTEMD_UNIT=sshd.service` с необычным IP — попытки входа. Сопоставив
`_COMM`, `_UID` и время с auditd и shell history, восстановишь полную картину.

## Что мы теперь знаем

- journald пишет бинарный структурированный журнал в `/var/log/journal/<machine-id>/`.
- Читается через `journalctl`; `-D <каталог>` — для копии/образа.
- Экспорт: `-o json` или `-o export` для анализа скриптами.
- Поля `_PID`, `_UID`, `_COMM`, `_EXE`, `MESSAGE`, `_BOOT_ID` — основа фильтрации.
- Цепочки скачивание→запуск от root и новые юниты — индикаторы атаки.

## Постоянное и волатильное хранение

journald может держать журнал в RAM (`/run/log/journal/`) или на диске
(`/var/log/journal/`). По умолчанию во многих дистрибутивах он **волатильный** — исчезает
при перезагрузке. Для расследования это критично: если журнал не был persistent, после
ребута ты его не найдёшь. Проверить и включить постоянное хранение:

```
$ grep -i storage /etc/systemd/journald.conf
Storage=persistent
```

На образе диска ищи каталог `/var/log/journal/<machine-id>/` — если он есть, журнал
пережил перезагрузки и содержит историю.

## Ротация и переполнение

Журнал ограничен по размеру (`SystemMaxUse`, `MaxFileSec`). Когда места мало, старые записи
удаляются. Значит, самые ранние события инцидента могут отсутствовать — учитывай это.
Файлы журнала именуются `system@<id>-<seq>.journal`; для таймлайна их сортируют по имени.

## Разбор случая

По нашим записям видно: `sshd` принял пароль от `jdoe` с `10.0.0.5`, затем `wget` скачал
файл, затем `bash` от `_UID=0` его выполнил. Даже без auditd этот след восстанавливается из
journald — но менее детально (нет аргументов команды целиком). Комбинация journald +
auditd даёт и контекст (кто вошёл), и детали (что запускалось).

## Интеграция и экспорт

Для внешнего анализа журнал экспортируют:

```
$ journalctl -D /mnt/img/var/log/journal -o json-pretty > j.json
$ journalctl -D /mnt/img/var/log/journal -o short-iso --since "2025-05-01" > j.txt
```

`short-iso` даёт читаемые строки с ISO-временем, `json-pretty` — структурированные записи
для SIEM. При экспорте всегда указывай `-D`, если работаешь с копией, иначе прочитаешь
журнал своей машины, а не исследуемой.

## Мини-практика: фильтрация по полю

```
$ journalctl -D /mnt/img/var/log/journal _EXE=/usr/bin/wget --no-pager
$ journalctl -D /mnt/img/var/log/journal _UID=0 _COMM=bash --no-pager
```

Первый запрос находит всё, что запускал `wget` (по полному пути бинарника), второй — все
shell-команды от root. Такой фильтр по `_EXE`/`_COMM`/`_UID` — самый быстрый способ выделить
подозрительные процессы из огромного журнала.

## Корреляция между юнитами

Поле `_SYSTEMD_UNIT` связывает запись с конкретным сервисом. Если скомпрометирован
`nginx.service`, все его записи помечены этим юнитом — и запуск shell «изнутри» веб-сервера
сразу виден. Поле `_SYSTEMD_CGROUP` даёт иерархию процессов, а `_CMDLINE` — полную
командную строку. Комбинация этих полей позволяет отделить нормальную работу сервиса от
аномальной без ручного разбора каждой строки.

## Журнал как источник таймлайна

journald даёт **точное** время с микросекундами (`__REALTIME_TIMESTAMP`) и монотонное время
загрузки (`__MONOTONIC_TIMESTAMP`). Это позволяет строить таймлайн, устойчивый к смене
системных часов: даже если злоумышленник перевёл время назад, монотонные метки останутся
согласованными. Для корреляции с внешними логами бери реальное время, для внутренней
логики — монотонное.

## Отличия от rsyslog

Классический `rsyslog` пишет текстовые файлы (`/var/log/syslog`), journald — бинарные
структурированные записи. Плюсы journald: точные поля, фильтрация, единый формат. Минусы:
непрозрачный формат и привязка к systemd. На практике на хосте обычно есть оба: journald
может **перенаправлять** записи в rsyslog (`ForwardToSyslog=yes`). Поэтому при отсутствии
бинарного журнала проверь текстовые — возможно, копия там.

## Практический чек-лист

- Найди каталог `/var/log/journal/<machine-id>/`; если его нет — журнал волатильный.
- Экспортируй журнал `-o json` или `-o export` для скриптового анализа.
- Фильтруй по `_COMM`, `_EXE`, `_UID`, `_SYSTEMD_UNIT`.
- Сопоставь с auditd (детали syscall) и с сетевыми логами.
- Проверь записи о запуске новых юнитов — возможное закрепление.

## Расширенный разбор: аномалии под нагрузкой

На реальном сервере журнал огромен, и «прочитать его глазами» нельзя. Работай от гипотез.
Первая гипотеза — компромисс сервиса: ищи запуск shell из сетевого демона по
`_SYSTEMD_UNIT`. Вторая — вход: фильтруй `sshd` по неуспешным и успешным попыткам и ищи
аномальные IP. Третья — закрепление: ищи сообщения systemd о запуске **новых** юнитов и
таймеров.

```
$ journalctl -D /mnt/img/var/log/journal -u sshd --since "2025-05-01" | grep -i 'Accepted\|Failed'
$ journalctl -D /mnt/img/var/log/journal | grep -i 'Started\|Stopped' | sort | uniq -c | sort -rn
```

Первый запрос выделяет вход по SSH, второй — частоту стартов и остановок сервисов. Сервис,
который стартовал сотни раз или появился впервые в день инцидента, заслуживает внимания.
Заверши построением таймлайна из полей `__REALTIME_TIMESTAMP` и сопоставлением с auditd.

## Проверка целостности и доверия к журналу

Как и любой лог, журнал systemd может быть изменён при наличии root. Поэтому оценивай не
только содержимое, но и **согласованность**: нет ли пропущенных `_BOOT_ID`, нет ли скачков
времени, совпадают ли счётчики. Если журнал пересылался на внешний сервер (journald умеет
`ForwardToSyslog` и отправку по сети), сверь локальную копию с удалённой. Расхождения —
сигнал, что данные правили. В отчёте всегда указывай источник журнала и то, был ли он
постоянным или волатильным: от этого зависит, насколько полной считаешь картину.

Практический вывод: journald — это не «ещё один текстовый лог», а структурированная база,
которую нужно уметь фильтровать по полям и экспортировать в переносимый вид. В связке с
auditd он даёт и контекст, и детали; в одиночку — быструю хронологию системных событий.
Если на хосте не было auditd, journald часто остаётся единственным источником, по которому
можно восстановить, какой сервис и когда запускал подозрительный процесс.
