## Вопрос, с которого всё начинается

Elasticsearch часто выставляют наружу без аутентификации — и из него утекают данные
или его используют для RCE. Разберём, где следы.

## Наш пример: Elasticsearch

## Шаг 1: открытый доступ

```
$ curl -s http://target:9200/_cat/indices?v
green open logs-2026.01.14 ...
```

Если ответ приходит без авторизации — кластер открыт. Это уже находка.

## Шаг 2: аудит-логи

Elasticsearch умеет логировать запросы (audit):

```
$ grep -i 'rest.request' /var/log/elasticsearch/audit.log | tail
```

Видно, кто и что запрашивал (в т.ч. удаление индексов).

## Шаг 3: удаление данных

Атакующий может удалить индексы (anti-forensics):

```
$ grep -i 'DELETE.*_index' audit.log | tail
```

Или перезаписать документы. Проверь целостность и бэкапы (snapshots).

## Шаг 4: RCE через скрипты

Elasticsearch позволял RCE через `script` (Groovy) и плагины:

```
$ grep -i 'script' audit.log | tail
```

Аномальные скрипт-запросы — признак эксплуатации.

## Шаг 5: что искать

- несанкционированный доступ (внешние IP);
- удаление/изменение индексов;
- скрипт-запросы;
- утечку чувствительных индексов;
- новые пользователи/роли (X-Pack).

## Шаг 6: где Elasticsearch хранит данные

Elasticsearch держит индексы в каталоге `path.data` (обычно `/var/lib/elasticsearch`). Каждый индекс — это набор сегментов (Lucene):

```
$ ls /var/lib/elasticsearch/nodes/0/indices/
```

Сегменты — это файлы `*.cfs`, `*.si`. Даже если индекс удалили через API, сегменты какое-то время остаются на диске — их можно попробовать восстановить.

## Шаг 7: audit-лог подробнее

Если включён `xpack.security.audit`, события пишутся в JSON:

```
{"type":"rest.request","event.action":"rest_request","url.path":"/logs-2026.01.14/_doc/1","method":"POST","user.name":"elastic"}
```

Здесь видно метод, путь и пользователя. Ищем обращения к чувствительным индексам:

```
$ grep -i 'secret' audit.log | tail
```

Так находим, какие данные читали или меняли и под какой учёткой.

## Шаг 8: скрипты и плагины как вектор RCE

Старые версии Elasticsearch позволяли выполнять Groovy-скрипты, а через них — команды:

```
$ grep -i 'script\|_plugins' audit.log | tail
{"url.path":"/_scripts/..."}
```

Аномальные обращения к `_scripts`, `_search?source=` с кодом или установка плагинов (`_nodes/plugins`) — признаки эксплуатации. Сопоставляем время с логами ОС.

## Шаг 9: восстановление из snapshot

Если данные удалили, проверь снимки:

```
$ curl -s http://target:9200/_snapshot/_all?pretty
$ curl -s -X POST 'http://target:9200/_snapshot/backup/snap1/_restore'
```

`_snapshot` перечисляет репозитории, `_restore` возвращает индекс. Восстановленный индекс сравнивают с текущим — это и есть доказательство удаления.

## Шаг 10: что искать

- внешние IP в audit-логе;
- `DELETE .../_index`;
- обращения к `_scripts`/плагинам;
- чтение чувствительных индексов;
- расхождение между snapshot и текущим состоянием.

## Шаг 11: скрытые и системные индексы

Некоторые индексы начинаются с точки — это служебные (`.security`, `.kibana`). По умолчанию их не видно, но при разборе их нужно явно запросить:

```
$ curl -s 'http://target:9200/_cat/indices?expand_wildcards=all&v'
```

Именно в `.security` лежат пользователи и роли, а в `.kibana` — сохранённые объекты. Атакующий часто создаёт свой пользователь в `.security`, чтобы закрепиться, — это надо искать.

## Шаг 12: логи самого кластера

Кроме audit-лога, у Elasticsearch есть лог работы кластера:

```
$ grep -iE 'authentication failed|deleting index|forbidden' /var/log/elasticsearch/*.log | tail
[WARN] [o.e.x.s.a.a...] authentication failed for user [elastic]
```

Здесь видно неудачные попытки входа, удаление индексов и ошибки прав. По времени эти строки сшиваются с audit-логом и сетевыми логами.

## Шаг 13: репозиторий snapshot на диске

Репозиторий снимков — это каталог (или S3-бакет), который тоже можно анализировать напрямую:

```
$ ls /mnt/backups/elasticsearch/indices/
```

Структура повторяет устройство индексов: метаданные и сегменты. Даже если через API снимок «удалён», физические файлы могут остаться и подлежат восстановлению — это и есть источник доказательства удаления данных.

## Шаг 14: практический итог

Порядок разбора Elasticsearch-инцидента:

1. проверить открытость (`_cat/indices` без авторизации);
2. выгрузить audit-лог и лог кластера;
3. найти удаления индексов и аномальные скрипты;
4. проверить пользователей в `.security`;
5. восстановить данные из snapshot и сравнить.

Так мы одновременно отвечаем на «что утекло» и «что уничтожили».

## Практика: разбор утечки

Сценарий: из кластера утекли данные, индексы затем удалили. Начинаем с проверки доступа:

```
$ curl -s http://target:9200/_cat/indices?v
green open customers-2026 ... 1200000 docs
```

Кластер отвечает без авторизации — уже находка. Смотрим audit-лог:

```
$ grep '"url.path":"/customers-2026' audit.log | tail -3
{"url.path":"/customers-2026/_search","method":"GET","user.name":"elastic","origin.address":"203.0.113.5"}
```

Видим поисковые запросы по чувствительному индексу с внешнего адреса. Теперь ищем удаление:

```
$ grep -i 'DELETE' audit.log | tail
{"url.path":"/customers-2026","method":"DELETE","user.name":"elastic"}
```

Индекс удалён тем же пользователем сразу после выгрузки. Это и есть «сбор → утечка → заметание следов».

Проверяем, остались ли сегменты и snapshot:

```
$ ls /var/lib/elasticsearch/nodes/0/indices/ | wc -l
$ curl -s http://target:9200/_snapshot/_all?pretty
```

Если снимок есть — восстанавливаем индекс и сравниваем с текущим состоянием. Так доказываем факт удаления и содержимое.

## Что важно

- Отсутствие авторизации — корневая причина.
- audit-лог даёт метод, путь, пользователя и IP.
- Удаление после выгрузки — типичный почерк.
- Snapshot — путь к восстановлению доказательств.

## Ограничения и типичные ошибки

Elasticsearch прощает многое, но и обманывает аналитика. Несколько ловушек.

**Аудит может быть выключен.** Если `xpack.security.audit.enabled` не включён, логов запросов просто нет. Тогда опирайся на лог кластера, логи обратного прокси и сетевые дампы — они фиксируют то же самое, только грубее.

**Открытость ≠ компромисс.** Публично доступный кластер — это экспозиция, но не обязательно взлом. Различай «кластер виден» и «из него утекали данные»: второе подтверждается запросами в аудите.

**Удаление индекса не стирает сегменты мгновенно.** Lucene освобождает место отложенно, поэтому сегменты удалённого индекса могут ещё лежать на диске. Это шанс на восстановление, но и риск принять остаточные сегменты за активные данные.

**Сравнение снимков.** Snapshot не всегда есть. Если репозиторий снимков пуст, восстановить удалённое сложнее — тогда опираешься на копии приложений и реплики.

**Скрытые индексы.** `.security` и подобные не видны в обычном `_cat/indices`. Забыв про `expand_wildcards=all`, легко пропустить созданного атакующим пользователя.

Вывод прост: собирай несколько независимых источников и не делай выводов по одному.

## Что запомнить по Elasticsearch

Коротко, чтобы не потерять главное. Первое: открытость кластера проверяется одним запросом без пароля — это самый быстрый способ понять, что он вообще виден наружу. Второе: audit-лог — это журнал того, **что** делали, а лог кластера — того, **как** он себя вёл; вместе они дают полную картину. Третье: удаление индекса и его появление в снимке — пара доказательств, подтверждающих уничтожение данных. Четвёртое: служебные индексы (`.security`) не забудь раскрыть `expand_wildcards=all`. Пятое: не путай экспозицию с компромиссом — факт взлома подтверждается только следами доступа. Держи эти пять пунктов в голове, и разбор утечки из поискового кластера станет предсказуемым.

## Что мы теперь знаем

- Открытый ES проверяется запросом без авторизации.
- Audit-лог фиксирует запросы.
- Удаление индексов — anti-forensics.
- Скрипты/плагины давали RCE.
- Смотрим доступ, изменения, скрипты.

- Данные ES лежат в `path.data` как сегменты Lucene.
- audit-лог (JSON) фиксирует метод, путь, пользователя.
- Скрипты/плагины — исторический вектор RCE.
- Snapshot восстанавливает удалённые индексы.
- Сравнение snapshot и текущего = доказательство.

- Служебные индексы (`.security`, `.kibana`) скрыты — запрашивай `expand_wildcards=all`.
- Лог кластера фиксирует входы, удаления и ошибки прав.
- Репозиторий snapshot можно анализировать прямо на диске.
- Порядок: доступ → аудит → удаления → пользователи → восстановление.

## Если не сработало

- Аудит выключен? Смотри логи балансировщика/сети.
- Нужны данные? Восстанавливай из snapshot.
- Нужны права? Читай роли X-Pack.
