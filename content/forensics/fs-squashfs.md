## Вопрос, с которого всё начинается

У тебя на руках файл прошивки роутера — один большой `.bin`. Внутри, судя по всему,
целая Linux-система: ядро, busybox, веб-интерфейс. Но просто распаковать его нечем:
это не архив, а **файловая система внутри файла**. Она называется **SquashFS**. Как её
опознать и извлечь содержимое?

## Что такое SquashFS

**SquashFS** — сжатая **read-only** файловая система для Linux. Она появилась для
встраиваемых устройств, где нужно уместить систему в маленькую флеш-память: всё дерево
файлов сжато блоками, а доступ к нему — только на чтение. Отсюда её повсеместность:

- прошивки роутеров, IP-камер, NAS, приставок;
- **initramfs** (образ начальной загрузки Linux);
- установочные образы (snap, AppImage внутри, live-CD);
- контейнеры и appliance-системы.

Название «squash» — «сжимать»: система хранит данные в сжатом виде и распаковывает их
на лету при чтении.

## Наш пример: firmware.bin

Смотрим первые байты файла:

```
$ ls -la
-rw-r--r--  1 student student  2097152 firmware.bin
$ xxd -l 16 firmware.bin
00000000: 6873 7173 0000 0000 0000 0000 0000 0000  hsqs............
```

Первые четыре байта — `68 73 71 73`, то есть ASCII-строка **`hsqs`**. Это магия
SquashFS (в little-endian порядок байт выглядит именно так). Видишь `hsqs` в начале
файла — почти наверняка SquashFS. В отличие от многих ФС, её суперблок лежит **прямо по
offset 0**.

## Шаг 1: текстовые метаданные и версия

Первый быстрый проход — `strings`, как и везде:

```
$ strings firmware.bin
hsqs
SquashFS 4.0, compression=zstd, block=131072
Files: /etc/passwd /bin/busybox /www/index.html
FW-MARKER: nto{squ4shfs_r0m0unt_f1rmw4r3}
```

Здесь видно версию (4.0), алгоритм сжатия (**zstd**) и размер блока. Это важно: разные
версии SquashFS и разные компрессоры требуют разных инструментов. SquashFS 4.0 — самая
распространённая в современных прошивках.

## Шаг 2: как устроена SquashFS

Суперблок описывает том и указывает на ключевые таблицы:

| Структура | Назначение |
|-----------|------------|
| Superblock | версия, компрессор, размер блока, счётчики inode/каталогов |
| Inode table | метаданные файлов (права, размер, uid/gid) |
| Directory table | имена и связи каталогов |
| Fragment table | хвосты маленьких файлов (сжимаются вместе) |
| Export table | быстрый доступ по номеру inode |
| ID table | таблица владельцев (uid/gid) |

Данные файлов сжаты **блоками**. Именно поэтому `strings` по образу даёт лишь фрагменты:
сжатый текст не читается напрямую. Чтобы увидеть реальные файлы, нужно распаковать том.

## Шаг 3: извлечение через unsquashfs

Основной инструмент — `unsquashfs` из пакета squashfs-tools:

```
$ unsquashfs -s firmware.bin
Found a valid SQUASHFS 4:0 superblock on firmware.bin.
Compression zstd
```
```
$ unsquashfs -l firmware.bin
squashfs-root
squashfs-root/etc
squashfs-root/etc/passwd
squashfs-root/bin
squashfs-root/bin/busybox
squashfs-root/www
squashfs-root/www/index.html
```
```
$ unsquashfs -d out firmware.bin
Parallel unsquashfs: Using 1 processor
[==========================|] 5 files
```

Ключи: `-s` — показать суперблок, `-l` — список без распаковки, `-d out` — распаковать в
каталог `out`, `-ll` — длинный список (права, размеры). После распаковки с деревом
работают обычные инструменты — grep по конфигам, поиск паролей, анализ busybox.

## Шаг 4: вложенные ФС и binwalk

Прошивки редко состоят из одной SquashFS. Часто в файле лежит **несколько** структур:
заголовок вендора, ядро, а затем SquashFS по смещению. Тогда `unsquashfs` по offset 0
не сработает — нужен поиск:

```
$ binwalk firmware.bin
DECIMAL    HEXADECIMAL   DESCRIPTION
0          0x0           SquashFS filesystem, little endian, version 4.0
1048576    0x100000      SquashFS filesystem, little endian, version 4.0
```

`binwalk` показывает смещения всех вложенных ФС. Дальше извлекают конкретную:
`binwalk -e firmware.bin` или вручную `dd if=firmware.bin bs=1 skip=1048576 | unsquashfs
-d out2 -`.

## Компрессоры SquashFS

| Компрессор | Признак | Замечание |
|------------|---------|-----------|
| gzip | `compression=gzip` | базовый, самый совместимый |
| lzma | `compression=lzma` | плотнее, но медленнее |
| lzo | `compression=lzo` | быстрый, для слабых CPU |
| xz | `compression=xz` | очень плотный |
| zstd | `compression=zstd` | современный баланс |

Если `unsquashfs` пишет «unsupported compression», твоя сборка squashfs-tools собрана
без нужной библиотеки. Решение — собрать инструмент с поддержкой (`LZMA_SUPPORT=1`,
`ZSTD_SUPPORT=1`) или взять статическую сборку.

## Частые ошибки и подводные камни

- **Искать суперблок не по offset 0.** В чистом образе он в начале, но в прошивке —
  по смещению; используй `binwalk`.
- **Ждать читаемых строк.** Сжатые блоки не видны в `strings`; нужна распаковка.
- **Путать версии.** Формат 3.x и 4.x несовместим; старый `unsquashfs` не поймёт 4.0.
- **Забыть про несколько ФС.** Часто в образе их две и больше — извлекай обе.
- **Игнорировать initramfs.** Тот же формат используется в initramfs; приём разбора
  идентичен.

## Мини-практика

Дан `firmware.bin`. Опознаём ФС и достаём метку:

```
$ xxd -l 16 firmware.bin
00000000: 6873 7173 0000 0000 0000 0000 0000 0000  hsqs............
$ strings firmware.bin | grep nto > answer.txt
$ cat answer.txt
FW-MARKER: nto{squ4shfs_r0m0unt_f1rmw4r3}
```

Мы подтвердили SquashFS по магии `hsqs` и вытащили метку. В реальном разборе дальше —
`unsquashfs -d out firmware.bin` и анализ распакованного дерева.

## Что мы теперь знаем

- SquashFS опознаётся по магии `hsqs` (обычно по offset 0).
- Это сжатая read-only ФС; данные в сжатых блоках, поэтому `strings` даёт фрагменты.
- Структуры: суперблок, inode table, directory table, fragment/export/id tables.
- Извлечение: `unsquashfs -s/-l/-d`; поиск вложенных ФС — `binwalk`.
- Поддерживаются разные компрессоры: gzip, lzma, lzo, xz, zstd.

## SquashFS в initramfs и контейнерах

SquashFS — не только прошивки. Тот же формат лежит внутри **initramfs** (образа
начальной загрузки Linux) и в некоторых контейнерных образах. Разница лишь в том, что
initramfs часто дополнительно сжат целиком (gzip/xz) и упакован в cpio — тогда сначала
распаковывают внешний слой:

```
$ file initrd.img
initrd.img: gzip compressed data, from Unix
$ zcat initrd.img > initrd.raw
$ binwalk initrd.raw
DECIMAL    HEXADECIMAL   DESCRIPTION
0          0x0           ASCII cpio archive
2097152    0x200000      SquashFS filesystem, little endian, version 4.0
```

Порядок разбора: внешнее сжатие → cpio → (при наличии) SquashFS. Пропустив первый слой,
ты будешь искать `hsqs` там, где лежит gzip, и не найдёшь его. Поэтому всегда начинай с
`file` и `binwalk`, чтобы понять **сколько слоёв** в образе.

## Работа с метаданными и правами

SquashFS хранит права, владельца и тип файла в **inode table**, а имена и связи — в
**directory table**. При распаковке `unsquashfs` восстанавливает это, но с оговорками:
uid/gid сохраняются как числовые, а «специальные» файлы (симлинки, устройства) требуют
прав. Посмотреть, что внутри, без распаковки можно так:

```
$ unsquashfs -ll firmware.bin
drwxr-xr-x root/root       0 2024-01-01 00:00 squashfs-root
drwxr-xr-x root/root       0 2024-01-01 00:00 squashfs-root/bin
-rwxr-xr-x root/root  761016 2024-01-01 00:00 squashfs-root/bin/busybox
-rw-r--r-- root/root     512 2024-01-01 00:00 squashfs-root/etc/passwd
```

Длинный список (`-ll`) показывает и права, и размеры, и владельца. Для аналитика это
важно: по датам и правам видно, какие файлы «родные» для прошивки, а какие добавлены
позже — например, при закладке бэкдора.

## Практический сценарий: поиск изменений в прошивке

Представь, что у тебя две версии прошивки одного устройства — «чистая» и «подозрительная».
Задача — найти, что изменили. Порядок действий:

1. Распаковать обе: `unsquashfs -d clean clean.bin` и `unsquashfs -d sus sus.bin`.
2. Сравнить деревья: `diff -rq clean sus`.
3. Обратить внимание на новые файлы в `/etc/init.d`, `/etc/rc.local`, `crontab`, веб-каталог.
4. Проверить изменённые бинарники по хешам.

```
$ diff -rq clean sus
Files clean/etc/rc.local and sus/etc/rc.local differ
Only in sus/www: shell.php
```

Такой `diff` мгновенно показывает, куда смотреть. Часто «лишний» файл — это веб-шелл
или скрипт автозапуска, добавленный злоумышленником. Именно поэтому SquashFS — не только
CTF-тема, но и рабочий инструмент анализа прошивок на предмет компрометации.

## Сжатие: почему это важно при разборе

SquashFS сжимает данные **блоками**, и блок сжимается целиком или не сжимается вовсе,
если выигрыша нет. Из этого следуют практические выводы. Во-первых, **нельзя искать
подстроку по всему образу** так же надёжно, как в несжатой ФС: одна и та же строка может
оказаться «разрезана» границей блока и не найтись в `strings`. Во-вторых, размер
распакованных данных больше образа — при извлечении нужно место. В-третьих, разные
блоки могут использовать разные алгоритмы (для метаданных и данных) — SquashFS допускает
смешанное сжатие.

Проверить, что реально сжато, а что хранится как есть, помогает сравнение размеров:
`unsquashfs -ll` показывает логические размеры файлов, а образ — сжатый. Если файл в
списке больше, чем весь образ, значит, он отлично сжимается (например, текстовый конфиг
или повторяющийся бинарник). Для форензики это подсказка: **хорошо сжимаемые данные —
это обычно текст**, там и лежат конфиги и ключи.

## Куда дальше

Дальше возьмём **JFFS2 и UBIFS** — журнальные ФС «сырой» NOR/NAND-памяти, которые
встречаются на встраиваемых устройствах ещё чаще SquashFS. А пока главное запомни:
**`hsqs` в начале файла — это SquashFS, и её содержимое сжато**.

## Где пригодится

- **CTF Forensics:** firmware-образы, initramfs, appliance.
- **Embedded/IoT:** разбор прошивок роутеров, камер, NAS.
- **DFIR:** анализ встраиваемых систем после компрометации.
- **Data recovery:** извлечение данных из сжатых образов.
