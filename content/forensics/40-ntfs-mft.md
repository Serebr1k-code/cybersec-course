## Вопрос, с которого всё начинается

Тебе дали образ диска Windows `disk.img`. Нужно найти файл, который кто-то удалил
перед тем, как выдернули питание. `fls` показывает список — но удалённого файла в
нём нет. Файл не исчез: Windows при удалении почти ничего не стирает. Он просто
перестаёт быть «видимым».

Чтобы его вернуть, надо понимать, как NTFS хранит файлы. В этом уроке мы разберём
один образ и найдём в нём удалённый `secret.txt`, читая **записи MFT** и **журналы**
напрямую.

## Наш пример: удалённый secret.txt в disk.img

Сначала определяем, где начинается NTFS-раздел:

```bash
$ mmls disk.img
GUID Partition Table (EFI)
00: Meta   0000000000-0000000000
01: -----  0000002048-0000409599   NTFS / exFAT
```

Раздел начинается с сектора 2048. Запомним offset `OFF=2048` — он нам понадобится
в каждой команде. Проверяем, что там NTFS:

```bash
$ fsstat -o 2048 disk.img | head -5
FILE SYSTEM INFORMATION
File System Type: NTFS
```

## Шаг 1: как NTFS хранит файл — MFT

**NTFS** — это файловая система Windows. Всё, что в ней есть, включая служебные
данные, — это **запись** в одной большой таблице: **Master File Table (MFT)**.
Каждая запись описывает один файл или каталог и имеет фиксированный размер (обычно
1024 байта).

Ключевая идея: **файл — это не «место на диске», а набор атрибутов** в записи MFT.
Самые важные атрибуты:

- `$STANDARD_INFORMATION` — времена и права;
- `$FILE_NAME` — имя файла;
- `$DATA` — собственно содержимое.

Разные атрибуты в одной записи — поэтому у файла может быть несколько имён (hard
links) и несколько потоков данных (ADS, о них ниже).

Смотрим все записи, включая удалённые. Флаг `-d` показывает только удалённые:

```bash
$ fls -r -d -o 2048 disk.img
r/r * 42-128-1: secret.txt
```

`42-128-1` — это номер записи MFT `42`, последовательность `128`, поток `1`.
Звёздочка `*` означает «удалён». Файл жив в MFT — снимаем его содержимое:

```bash
$ icat -o 2048 disk.img 42-128-1 > secret.bin
$ file secret.bin
secret.bin: ASCII text
$ strings secret.bin | grep -i flag
CTF{mft_never_lies}
```

Готово. Но почему это сработало? Потому что при удалении NTFS лишь помечает запись
MFT свободной — **кластеры с данными не затираются**, пока их не переиспользует
другой файл.

## Шаг 2: читаем времена — когда файл создали и удалили

`fls` не показывает дат. За временами идём в `istat` — он печатает метаданные
записи MFT:

```bash
$ istat -o 2048 disk.img 42
MFT Entry: 42  Sequence: 128
...
$FILE_NAME times:
  Modified:  2024-01-12 10:14:03
  Accessed:  2024-01-12 10:14:03
  MFT Changed: 2024-01-12 10:31:22
  Created:   2024-01-12 10:13:50
```

Четыре времени — **MACB** (Modified, Accessed, MFT-changed, Birth/created). Из них
`MFT Changed` часто и есть момент удаления, потому что при удалении меняется сама
запись. У нас получилось: создан 10:13, удалён 10:31. Это уже хронология.

Важная тонкость: `$STANDARD_INFORMATION` хранит **свой** набор времён, а
`$FILE_NAME` — свой. Антифорензика (timestomp) подделывает обычно только первый.
Сравнивайте оба набора — расхождение выдаёт подделку.

## Шаг 3: где данные, если они не в записи

Мелкие файлы NTFS кладёт **внутрь** записи MFT — это **resident** (resident =
«проживающий» внутри). Крупные — в обычные кластеры, а запись хранит **runlist**
(список участков). Это **non-resident**.

```bash
$ istat -o 2048 disk.img 42 | grep -A3 'Data Streams\|Runlist'
Name: $DATA
  Non-Resident
  Runlist: 43, 44, 45
```

`Runlist: 43,44,45` — данные лежат в кластерах 43, 44, 45. Зная размер кластера
(обычно 4096 байт), можно прочитать их `dd`. Но обычно хватает `icat`.

## Шаг 4: $LogFile и $UsnJrnl — журналы действий

Иногда файл удалён так давно, что запись MFT уже переиспользована. Тогда спасают
**журналы**.

**`$UsnJrnl`** — журнал изменений: лента «какое имя, когда, что с ним сделали»
(создан, перезаписан, переименован, удалён). Он хранит не содержимое, а события.

```bash
$ fls -r -o 2048 disk.img | grep -i 'usnjrnl'
r/r 42-128-3: $Extend/$UsnJrnl:$J
$ icat -o 2048 disk.img 42-128-3 > usn.bin
$ usnparser parse usn.bin > usn.csv
$ grep -i secret usn.csv
2024-01-12 10:31:22,FILE_DELETE,secret.txt
```

Теперь у нас есть точное время удаления и подтверждение события — независимо от
записи MFT.

**`$LogFile`** — журнал **транзакций метаданных**: он хранит *прежние* значения
изменённых структур. Именно он может показать, **как файл назывался раньше**, если
его переименовали перед удалением:

```bash
$ icat -o 2048 disk.img 2 > LogFile.bin
$ LogFileParser.exe -f LogFile.bin | grep -i rename
Rename: flags.txt -> secret.txt
```

Парсить `$LogFile` сложнее, чем `$UsnJrnl`, но именно он отвечает на вопрос «а что
было до переименования».

## Шаг 5: ADS — поток-невидимка

**Alternate Data Stream (ADS)** — дополнительный поток данных того же файла. В
Windows Explorer его не видно, а данные там лежат. В `fls` он показывается с
двоеточием в имени:

```bash
$ fls -r -o 2048 disk.img | grep ':'
r/r 50-128-3: notes.txt:hidden.txt
$ icat -o 2048 disk.img 50-128-3 > hidden.bin
$ strings hidden.bin
payload: http://10.0.0.9/dropper
```

В MFT это просто ещё один атрибут `$DATA` с именем. Частая уловка CTF: флаг или
дроппер спрятаны в ADS обычного файла. В Windows вскрывается `dir /r`, в Linux —
`fls | grep ':'`.

## Шаг 6: если запись MFT переиспользована

Бывает хуже: файл удалили давно, и его номер записи `42` уже занял другой файл —
**sequence number** в этом случае вырос (был `128`, стал `129`). Имя и времена
потеряны, но **кластеры с данными** могут лежать нетронутыми, если их не занял
новый файл.

Тогда работают «снизу» — по сырым блокам диска. Смотрим только нераспределённые
(unallocated) блоки и ищем в них строки:

```bash
$ blkls -o 2048 disk.img > unalloc.bin
$ strings -n 6 unalloc.bin | grep -iE 'CTF\{|flag\{'
CTF{mft_never_lies}
```

`blkls` дампит свободные блоки — то есть всё, что когда-то было записано и потом
освобождено. Если данные не перезаписаны, они здесь. Этот приём называется
**carving** («вырезание») — восстановление по содержимому, когда метаданные уже
потеряны.

## Шпаргалка по служебным файлам NTFS

Все служебные структуры NTFS — тоже записи MFT, их имена начинаются с `$`:

| Файл | Что это | Зачем форензику |
|------|---------|-----------------|
| `$MFT` | таблица всех файлов | удалённые записи, имена, времена |
| `$LogFile` | журнал транзакций метаданных | прежние значения, переименования |
| `$UsnJrnl` | лента изменений | хронология операций с именами |
| `$Bitmap` | занятость кластеров | какие блоки свободны для carving |
| `$Secure` | дескрипторы доступа | кто имел доступ к файлу |

Имена могут начинаться с `$` и в реальной ФС — так что `fls | grep '^\$'` не признак
подделки, а норма. Подозрительно другое: файл `$UsnJrnl` может отсутствовать или
быть обрезанным — атакующие иногда чистят журналы (`wevtutil`, `fsutil usn deletejournal`),
чтобы скрыть свои действия. Отсутствие журнала — сам по себе улика.

## Что мы теперь знаем

- NTFS хранит всё в записях MFT; файл = набор атрибутов, данные — лишь один из них.
- Удаление снимает флаг «занято», но **кластеры не затирает** — файл ещё читается.
- `fls -d` находит удалённые, `istat` даёт времена MACB, `icat` вынимает данные.
- `$UsnJrnl` — лента событий с именами и временем; `$LogFile` — прежние значения.
- ADS (потоки `имя:поток`) прячут данные внутри обычного файла.

## На что смотреть дальше

- **Никогда не монтируйте образ read-write** — NTFS перепишет `$LogFile`/`$UsnJrnl`,
  и улики исчезнут. Только `-o ro,loop` или sleuthkit напрямую.
- **`-o` у sleuthkit — в секторах**, а `mount offset=` — в байтах; перепутаете — мусор.
- **Проверяйте sequence number** — два разных файла могут делить номер записи MFT.
- **Сверяйте оба набора времён** (`$FILE_NAME` и `$STANDARD_INFORMATION`) — timestomp
  правит только один.

## Куда дальше

Мы научились доставать удалённые файлы и их времена. В следующем уроке мы целиком
посвятим себя журналу `$UsnJrnl` — научимся восстанавливать пары переименований
`старое -> новое` и строить из него таймлайн. А пока запомни: **удалённый файл в
NTFS жив, пока его кластеры не переиспользованы**.

## Где пригодится

- **CTF:** задачи с образами Windows — удалённые файлы, ADS, переименования.
- **Incident Response:** восстановление хронологии действий атакующего на хосте.
- **Threat Hunting:** поиск подозрительных имён и операций в `$UsnJrnl`.
- **Судебная экспертиза:** доказательство удаления/переименования файлов.
- **Разработка детектов:** сигнатуры по причинам USN (FILE_DELETE, RENAME_NEW_NAME).
