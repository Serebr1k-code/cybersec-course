## Вопрос, с которого всё начинается

Современные Android-устройства хранят ключи в аппаратной защите (TEE/StrongBox). Извлечь
их обычными методами нельзя. Разберём, как это устроено и что доступно.

## Наш пример: Android Keystore

## Шаг 1: уровни защиты

- **software** — ключи в файле (слабый);
- **TEE** (Trusted Execution Environment) — защищённое окружение в SoC;
- **StrongBox** — отдельный чип (strongest).

```
$ adb shell dumpsys keystore | grep -i 'strongbox\|tee'
```

## Шаг 2: где ключи

Ключи Android Keystore привязаны к аппаратной защите. Файлы в `/data/misc/keystore`
содержат **зашифрованные** блобы — расшифровать без чипа нельзя.

```
$ ls /data/misc/keystore/user_0/
10001_USRPKEY_...
```

## Шаг 3: что это значит

- приложения (банки, мессенджеры) хранят ключи в StrongBox/TEE;
- ключи **не покидают** защищённую зону;
- извлечь их «в лоб» невозможно;
- можно использовать ключ **только на устройстве** через API.

## Шаг 4: что доступно

- метаданные ключей (алиасы, типы);
- факт использования (логи);
- при наличии эксплойта/root — ограниченный доступ;
- на разблокированном устройстве — через API.

## Шаг 5: практика

- для расследования важнее **данные приложений**, а не сами ключи;
- если ключ нужен — извлекай через живое устройство (API);
- фиксируй версию/модель (влияет на защиту).

## Что мы теперь знаем

- Ключи хранятся в software/TEE/StrongBox.
- StrongBox — отдельный чип (максимальная защита).
- Файлы keystore содержат зашифрованные блобы.
- Ключи не покидают защищённую зону.
- Доступны метаданные и использование через API.

## Если не сработало

- Нужен ключ? Работай через живое устройство.
- Есть root? Доступ всё равно ограничен TEE.
- Нужны данные? Читай базы приложений.

## Расширенный разбор: путь ключа от чипа до приложения

Проследим, как ключ рождается и используется, и где его можно увидеть. Сначала
посмотрим, какой уровень защиты выбран приложением через Keystore:

```bash
$ adb shell dumpsys keystore 2>/dev/null | head
Keystore state: initialized
```

Список ключей приложения читается только изнутри песочницы (root/отладочная
сборка). Имя ключа обычно указывает на назначение:

```bash
$ adb shell run-as com.example.app ls -l /data/misc/keystore/user_0/ 2>/dev/null
-rw------- 1 system system  com.example.app_USRPKEY_my_signing_key
```

Ключ с префиксом `USRPKEY` создан приложением; `USRCERT` — сертификат. Если в
описании ключа есть `StrongBox`, он физически лежит в отдельном чипе:

```java
KeyGenParameterSpec spec = new KeyGenParameterSpec.Builder(
        "my_signing_key", PURPOSE_SIGN)
    .setIsStrongBoxBacked(true)
    .setUserAuthenticationRequired(true)
    .build();
```

Флаг `setUserAuthenticationRequired(true)` означает: ключ нельзя использовать,
пока пользователь не аутентифицировался (PIN/биометрия). При этом сам ключевой
материал из чипа не извлекается — наружу выходит только результат операции.

## Справочная таблица: уровни аппаратной защиты Android

| Уровень | Где ключ | Извлекаемость | Типичное использование |
|---|---|---|---|
| Software Keystore | файл в /data/misc | да (root/offline) | тесты, слабые приложения |
| TEE (TrustZone) | защищённый мир CPU | нет (только операции) | большинство банков |
| StrongBox (SE) | отдельный чип | нет | высокие требования, FIDO |
| Titan/SE (Pixel) | дискретный чип | нет | аппаратная аттестация |

## Краевые случаи и обход

- **Понижение до software.** Если приложение просит StrongBox, но чипа нет,
  система молча откатывается на TEE — проверяй `getSecurityLevel()`.
- **Attestation.** `KeyStore.getCertificateChain()` возвращает цепочку
  аттестации; её корень подписан Google, и по ней проверяют, что ключ реально
  аппаратный.
- **User authentication required.** Ключ бесполезен без разблокировки; при
  извлечении образа «на выключенном» устройстве он недоступен.
- **Обход через root.** На рутированном устройстве можно поставить хук на
  `KeyStore.getKey`, но это даёт лишь вызовы, а не сам ключ.
- **Frida-инструментация.** Перехват `Signature.sign` покажет вход, но не
  раскроет приватный ключ — только операции с ним.

## Практический разбор: аттестация аппаратного ключа

Аппаратный ключ ценен тем, что его происхождение проверяемо. Запросим цепочку
сертификатов и убедимся, что корень подписан Google:

```java
KeyStore ks = KeyStore.getInstance("AndroidKeyStore");
ks.load(null);
Certificate[] chain = ks.getCertificateChain("my_signing_key");
// chain[0] — leaf, chain[last] — корень аттестации Google
```

Атрибуты аттестации закодированы в leaf-сертификате (ASN.1 extension). Их
разбирают утилитой или библиотекой:

```bash
$ openssl x509 -in leaf.pem -text -noout | grep -A3 'Key Description'
            Security Level: StrongBox
            Verified Boot State: Verified
```

`Security Level: StrongBox` подтверждает, что ключ аппаратный, а `Verified Boot
State: Verified` — что загрузка была целостной. Если уровень `Software`, ключ
можно извлечь из файла, и доверия к нему нет.

## Типичные ошибки анализа

- **Путать TEE и StrongBox.** Приложение может запросить StrongBox, но получить
  TEE при откате — смотри фактический уровень, а не желаемый.
- **Считать, что root даёт ключ.** Root даёт файлы и вызовы, но не ключевой
  материал внутри чипа.
- **Игнорировать привязку к пользователю.** При `setUserAuthenticationRequired`
  ключ бесполезен без разблокировки, и на выключенном устройстве не работает.
- **Забыть про аттестацию.** Без проверки цепочки нельзя утверждать, что ключ
  аппаратный, — это проверяется, а не предполагается.

## Связь с другими артефактами

- **Full-disk encryption (FBE).** Ключи шифрования файловой системы тоже
  производятся в TEE/StrongBox; при выключенном устройстве они недоступны.
- **Биометрия.** `BiometricPrompt` лишь разрешает использование ключа; сам
  отпечаток не хранится и не извлекается.
- **StrongBox и FIDO.** Аппаратные ключи лежат в основе passkey-аутентификации;
  их компрометация равносильна краже личности.
- **Границы.** Форензика на включённом разблокированном устройстве даёт больше
  всего; после выключения — минимум.

## Расширенный пример: разбор аттестации по шагам

Аттестация ключа — это доказательство, что ключ реально аппаратный. Разберём
цепочку сертификатов и извлечём ключевые поля:

```bash
$ keytool -printcert -file chain.pem | grep -E 'Owner|Issuer|Valid'
Owner: CN=Android Keystore Key
Issuer: CN=Android Keystore Key Attestation CA
Valid from: Tue Jan 06 10:00:00 UTC 2026
```

Корневой сертификат должен вести к Google Hardware Attestation Root. Расширение
`Key Description` содержит уровень безопасности и состояние загрузки:

```bash
$ openssl asn1parse -in leaf.pem -i | grep -A2 '1.3.6.1.4.1.11129.2.1.17'
:  attestationVersion=3
:  securityLevel=strongbox
:  verifiedBootState=verified
```

`securityLevel=strongbox` — ключ в отдельном чипе; `verifiedBootState=verified`
— загрузка целостна. Если `securityLevel=software`, ключ извлекаем из файла и
доверия к нему нет.

## Контрольный список анализа аппаратных ключей

- [ ] Определить уровень защиты ключа (`getSecurityLevel`).
- [ ] Проверить, требуется ли аутентификация пользователя.
- [ ] Запросить цепочку аттестации и проверить корень Google.
- [ ] Разобрать `Key Description` (уровень, boot state, purpose).
- [ ] Проверить, не было ли отката StrongBox -> TEE.
- [ ] Сопоставить с FBE: доступны ли ключи шифрования ФС.
- [ ] Зафиксировать, разблокировано ли устройство в момент извлечения.

## Практические сценарии

- **Проверка банковского приложения.** Аттестация показывает, что ключ подписи
  операций аппаратный и не может быть скопирован на другое устройство.
- **Анализ вредоноса.** Если malware запрашивает StrongBox-ключ с
  `setUserAuthenticationRequired(false)`, он хочет использовать ключ без ведома
  пользователя — признак злоупотребления.
- **Passkey/WebAuthn.** Аппаратный ключ лежит в основе passkey; его
  компрометация равна краже личности, поэтому он и защищён чипом.
- **Корпоративные политики.** Требование StrongBox гарантирует, что ключи не
  выйдут за пределы устройства даже при root.

## Ограничения и типичные ошибки

- **Root не равен ключу.** Root даёт файлы и перехват вызовов, но не ключевой
  материал внутри чипа.
- **Привязка к пользователю.** При `setUserAuthenticationRequired(true)` ключ
  бесполезен без разблокировки; на выключенном устройстве недоступен.
- **Откат уровня.** Приложение может запросить StrongBox, а получить TEE —
  проверяй фактический уровень, а не желаемый.
- **Аттестация без проверки.** Если не валидировать цепочку, утверждение
  «ключ аппаратный» остаётся предположением.
- **Биометрия.** Отпечаток не хранится и не извлекается; он лишь разрешает
  операцию с ключом.

## Проверка результата

Убедись, что ключ действительно аппаратный, а не программный:

```bash
$ keytool -printcert -file chain.pem | grep -i 'hardware'
# (пусто = проверяй поле securityLevel в attestation extension)
$ openssl asn1parse -in leaf.pem -i | grep -i 'securityLevel'
:  securityLevel=strongbox
```

Если уровень `strongbox` или `trustedEnvironment` — ключ защищён чипом; если
`software` — материал извлекаем. Зафиксируй это различие в выводе.

## Что записать в отчёт

- Имя ключа, назначение (подпись/шифрование) и уровень защиты.
- Требование аутентификации пользователя (`setUserAuthenticationRequired`).
- Результат проверки цепочки аттестации (корень Google, boot state).
- Доступность ключей FBE на момент извлечения (устройство включено/выключено).
- Ограничения: неизвлекаемость материала, зависимость от разблокировки.

## Таблица: уровень защиты и извлекаемость

| Уровень | Где ключ | Извлекаемость | Пример |
|---|---|---|---|
| Software | файл /data | да (root/offline) | тесты |
| TrustedEnvironment | TEE (TrustZone) | нет | банки |
| StrongBox | отдельный чип | нет | FIDO/passkey |

Откат StrongBox -> TEE происходит молча, если чип недоступен, поэтому уровень
проверяют в аттестации, а не по коду запроса.

## Частые заблуждения

- «Root даёт ключ» — root даёт файлы и перехват вызовов, но не материал внутри
  чипа; ключ неизвлекаем.
- «Запросил StrongBox — значит StrongBox» — при недоступности чипа происходит
  молчаливый откат на TEE; проверяй фактический уровень.
- «Биометрия хранит отпечаток» — отпечаток не хранится; он лишь разрешает
  операцию с ключом.
