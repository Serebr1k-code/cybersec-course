## Вопрос, с которого всё начинается

Машина внезапно упала в синий экран (BSOD). Администратор перезагрузил её, и всё «заработало», но причину никто не знает. Windows при падении сохраняет состояние системы в **аварийный дамп** (crash dump). Если падение вызвал вредоносный драйвер, дамп — единственное место, где он себя выдал. Как его читать?

## Наш пример: MEMORY.DMP

У нас есть `MEMORY.DMP` — полный аварийный дамп. Смотрим начало:

```bash
$ xxd -l 16 MEMORY.DMP
00000000: 5041 4745 4455 3634 0000 0000 0000 0000  PAGEDU64........
```

Сигнатура `PAGEDU64` означает дамп 64-битной системы (для 32-битной — `PAGEDUMP`). В заголовке лежат: тип дампа, bugcheck-код, размер и адрес базового образа ядра.

## Шаг 1: зачем вообще дамп

При «синем экране» ядро не может продолжать работу, но **перед остановом** оно успевает записать память (полностью или частично) на диск. Причины падений разные: сбой железа, ошибка драйвера, намеренный `KeBugCheck` от руткита. Дамп фиксирует **момент падения**: какие модули загружены, что было в стеке, какой код вызвал сбой.

## Шаг 2: типы дампов

Windows умеет писать три типа, и это важно для форензики:

| Тип | Что содержит | Размер |
|-----|--------------|--------|
| Complete memory dump | всю физическую память | ~объём RAM |
| Kernel memory dump | память ядра | сотни МБ |
| Small/minidump | стек, модули, базовые структуры | десятки КБ |

Полный дамп — самый ценный (можно применять плагины памяти). Minidump беднее, но его чаще всего и находят (например, в `C:\Windows\Minidump\*.dmp`).

## Шаг 3: bugcheck-код

Первое, что смотрят, — **bugcheck** (код остановки). Он говорит, из-за чего упала система:

```bash
$ vol -f MEMORY.DMP windows.info
Variable          Value
Kernel Base       0xf8000000
DTB               0x1a0000
Symbols           ntkrnlmp.pdb
```

```bash
$ vol -f MEMORY.DMP windows.crashinfo
BugCheck Code      0x00000050  (PAGE_FAULT_IN_NONPAGED_AREA)
```

Код `0x50` — обращение к несуществующей странице памяти. Часто это ошибка драйвера. Другие частые коды: `0x7E` (необработанное исключение ядра), `0x3B` (исключение в системном сервисе), `0xD1` (ошибка драйвера). Код — лишь отправная точка, дальше смотрим, **чей** код вызвал сбой.

## Шаг 4: модули и подозрительные драйверы

Самое полезное — список загруженных модулей. Легитимные драйверы подписаны; малварь-руткит — нет, либо выдаёт себя необычным именем:

```bash
$ python3 dumpinfo.py
[DMP] type=PAGEDU64 modules=3
[DMP]  ntoskrnl.exe   signed
[DMP]  tcpip.sys      signed
[DMP]  r00tkit.sys    UNSIGNED   <-- suspicious
[DMP] key=nto{cr4sh_dump_r00tk1t_dr1v3r}
```

Забираем ключ:

```bash
$ python3 dumpinfo.py | grep nto > found.txt
```

В реальном разборе то же самое делает WinDbg:

```
0: kd> !analyze -v
BUGCHECK_CODE:  50
IMAGE_NAME:  r00tkit.sys
```

Строка `IMAGE_NAME` прямо называет виновный драйвер. Дальше проверяют его подпись (`!lmi r00tkit.sys`), путь на диске и хеш.

## Шаг 5: стек вызовов

Стек показывает цепочку вызовов, приведшую к падению:

```
0: kd> kb
 # Child-SP          RetAddr           Call Site
 0 ffff...  fffff800`...  r00tkit!HookHandler+0x1a
 1 ffff...  fffff800`...  nt!KiPageFault+0x... 
```

Если верхние кадры указывают в неизвестный модуль (`r00tkit!`), а не в `ntoskrnl`, это прямая улика: сбой вызван кодом руткита. Заодно видно технику — здесь перехват (`HookHandler`).

## Шаг 6: minidump как источник

Если полного дампа нет, работает и minidump: он содержит bugcheck, список модулей и стек. Имя файла (`041224-12345-01.dmp`) кодирует дату (`041224` → 4 декабря 2024). Совокупность minidump-ов даёт **хронологию падений** — если машина падала многократно после установки драйвера, это уже закономерность.

## Если не сработало

- **Volatility требует символы** → для `crashinfo`/`info` нужен ISF под сборку ядра; без символов используйте WinDbg.
- **`PAGE_FAULT` без модуля** → включите в дампе «полный» режим или посмотрите `!analyze -v` с `_FAILURE_BUCKET_ID`.
- **Дамп «битый»** → проверьте хеш: сбой при записи дампа возможен, но неполный дамп — тоже улика (например, руткит мешал записи).
- **Нет дампа вообще** → падение могло не привести к записи (например, отключён crash dump); проверьте `HKLM\SYSTEM\...\CrashControl`.

## На что смотреть защитнику

- Отслеживание падений с bugcheck-кодами драйверов: серия BSOD после установки софта — сигнал.
- Обязательная проверка подписи драйверов и **HVCI** блокируют незарегистрированные kernel-модули.
- Сбор minidump-ов в SIEM: `IMAGE_NAME` незнакомых модулей — повод для проверки.

## Что мы теперь знаем

- Аварийный дамп фиксирует состояние системы в момент BSOD; сигнатура `PAGEDU64`/`PAGEDUMP`.
- Типы дампов различаются полнотой: complete > kernel > minidump.
- **bugcheck-код** — отправная точка; **список модулей** и `IMAGE_NAME` называют виновника.
- Неподписанный драйвер в дампе — классический след kernel-руткита.
- Minidump-ы дают хронологию падений и годятся, когда полного дампа нет.

## Шаг 7: реестр управляет тем, какой дамп вы получите

Прежде чем искать дамп, проверяют, включён ли он и какого он типа. Всё решает ветка `HKLM\SYSTEM\CurrentControlSet\Control\CrashControl`:

| Параметр | Значение | Смысл |
|----------|----------|-------|
| `CrashDumpEnabled` | 0 | дамп отключён |
| | 1 | complete memory dump |
| | 2 | kernel memory dump |
| | 3 | small (minidump) |
| | 7 | automatic memory dump (в pagefile) |
| `DumpFile` | путь | где лежит `MEMORY.DMP` |
| `MinidumpDir` | путь | каталог `Minidump\` |
| `AutoReboot` | 0/1 | перезагружаться ли после BSOD |
| `Overwrite` | 0/1 | перезаписывать ли старый дамп |
| `IgnorePagefileSize` | 0/1 | писать дамп при малом pagefile |

Параметр `Overwrite = 1` означает, что предыдущий дамп уже затёрт новым — если после инцидента были другие падения, ценный дамп мог пропасть. Это первое, что проверяют в IR: дамп мог быть, но его перезаписали ещё до сбора образа.

## Шаг 8: WinDbg — основной инструмент ядрового разбора

Volatility удобна, но глубина анализа ядра — за WinDbg. Минимальный набор команд:

```text
0: kd> .symfix C:\symbols
0: kd> .reload
0: kd> !analyze -v
0: kd> lm t n
0: kd> !drvobj r00tkit.sys 7
0: kd> !pool <address>
0: kd> kb
0: kd> !thread
0: kd> !verifier 3 r00tkit.sys
```

`!analyze -v` автоматически называет модуль (`IMAGE_NAME`) и адрес сбоя. `lm` показывает загруженные модули с диапазонами адресов — модуль вне диапазона известных драйверов подозрителен. `!drvobj` печатает структуру объекта драйвера (таблицу обработчиков MajorFunction): если драйвер перехватывает вызовы, это видно. `!verifier` показывает статистику пула и ошибки конкретного драйвера. Начинать всегда стоит с `.symfix` + `.reload`: без символов адреса остаются «голыми» и имена модулей не раскрываются.

## Шаг 9: дамп из файла подкачки

При режиме «automatic memory dump» ядровый дамп пишется в `pagefile.sys`, а `MEMORY.DMP` появляется лишь после перезагрузки. Если система не перезагружалась, дамп лежит в pagefile:

```bash
$ grep -abo 'PAGEDU64' pagefile.sys
1073741824:PAGEDU64
$ dd if=pagefile.sys of=kernel.dmp bs=1 skip=1073741824
```

Дальше `kernel.dmp` открывается как обычный дамп. Отдельный случай — «dedicated dump file»: когда pagefile меньше объёма RAM, Windows пишет дамп в `DedicatedDumpFile`, путь к которому задан в том же `CrashControl`.

## Шаг 10: плагины Volatility для дампа

Помимо `windows.crashinfo`, к дампу применимы:

| Плагин | Что показывает |
|--------|----------------|
| `windows.crashinfo` | bugcheck-код, параметры, время сбоя |
| `windows.driverscan` | драйверы, найденные сканированием памяти |
| `windows.modules` | загруженные модули ядра (по списку) |
| `windows.modscan` | модули, найденные сканированием (ловит скрытые) |
| `windows.devicetree` | дерево устройств и их драйверов |
| `windows.malfind` | подозрительные исполняемые области |
| `windows.svcscan` | службы и их состояния |
| `windows.poolscanner` | объекты пула ядра |

Сравнение `windows.modules` и `windows.modscan` — классический приём: модуль, который есть в сканировании, но отсутствует в списке ядра, спрятан (unlinking) — прямой признак руткита.

## Шаг 11: частые bugcheck-коды

| Код | Имя | Типичная причина |
|-----|-----|------------------|
| 0x0A | IRQL_NOT_LESS_OR_EQUAL | доступ к памяти на высоком IRQL |
| 0x1E | KMODE_EXCEPTION_NOT_HANDLED | необработанное исключение ядра |
| 0x50 | PAGE_FAULT_IN_NONPAGED_AREA | обращение к невыгружаемой странице |
| 0x7E | SYSTEM_THREAD_EXCEPTION_NOT_HANDLED | сбой системного потока |
| 0x3B | SYSTEM_SERVICE_EXCEPTION | исключение в системной службе |
| 0xD1 | DRIVER_IRQL_NOT_LESS_OR_EQUAL | драйвер на неверном IRQL |
| 0xC2 | BAD_POOL_CALLER | неверная работа с пулом |
| 0x19 | BAD_POOL_HEADER | повреждение заголовка пула |
| 0x124 | WHEA_UNCORRECTABLE_ERROR | аппаратная ошибка |
| 0x139 | KERNEL_SECURITY_CHECK_FAILURE | нарушение целостности ядра |

Код — лишь гипотеза; окончательный виновник определяется по `IMAGE_NAME` и стеку вызовов, а не по одному лишь bugcheck.

## Шаг 12: сохранение и целостность дампа

Дамп — это улика, поэтому при сборе важны хеш и порядок действий. Сначала фиксируют SHA-256 дампа, потом работают с копией, а оригинал не открывают на запись. Если дамп получен из pagefile через `dd`, сохраняют и смещение (`skip`), чтобы воспроизвести извлечение. Наконец, сам факт «дамп отсутствует или обрезан» тоже улика: руткит мог мешать записи, а администратор — отключить `CrashDumpEnabled`.

## Куда дальше

Мы разобрали память и дампы. В следующем уроке (`forensics-windows-persistence`) перейдём к вопросу «как программа закрепляется в системе»: автозапуск, службы, задачи, WMI. А пока главное запомни: **аварийный дамп — снимок ядра в момент сбоя, и в нём виден виновный драйвер**.

## Где пригодится

- **CTF:** флаг в дампе или в имени подозрительного модуля.
- **IR:** диагностика BSOD после взлома, поиск kernel-руткитов.
- **Malware Analysis:** анализ драйверов без запуска.
- **Threat Hunting:** охота на незарегистрированные kernel-модули.
