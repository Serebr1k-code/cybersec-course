## Вопрос, с которого всё начинается

В журнале ты видишь вход с адреса в другой стране, которого не было. Или пользователя,
которого не существует. Кто-то **подбросил** ложные следы, чтобы увести расследование в
сторону. Как отличить подделку от настоящей записи?

## Наш пример: странная запись в auth.log

Открываем `auth.log` и видим:

```
Mar 10 03:14:15 server sshd[9999]: Accepted password for ghost from 203.0.113.9
Mar 10 03:14:16 server sshd[9999]: session opened for user ghost
```

Пользователя `ghost` в системе нет. Запись выглядит правдоподобно, но что-то не так.

## Приём первый: инъекция в журнал

Атакующий может **дописать** записи в текстовый журнал (или подделать бинарный), чтобы:

- подставить другого пользователя/адрес;
- создать ложную временную метку;
- перегрузить следователя шумом.

Признаки подделки:

- **несоответствие PID**: `sshd[9999]` — слишком «круглый» и не встречается в других
  записях; настоящие PID последовательны;
- **нет парных событий**: успешному входу обычно предшествует `session opened`, а после —
  команды; «висячая» запись подозрительна;
- **нарушение формата**: другой порядок полей, лишние/недостающие пробелы, другая кодировка;
- **несоответствие времени**: запись выбивается из общего ритма системы.

## Приём второй: подмена времени (timestomp)

Атакующий меняет временные метки файлов, чтобы отвести подозрение:

```
$ touch -d '2019-01-01 00:00:00' evil.exe
$ stat evil.exe | grep Modify
Modify: 2019-01-01 00:00:00
```

Признаки timestomp:

- **время изменено раньше времени создания** — логически невозможно;
- **несоответствие `$STANDARD_INFORMATION` и `$FILE_NAME`** в NTFS: одни метки правят,
  другие часто забывают;
- **все файлы с одинаковой меткой** — явный признак массовой правки.

## Приём третий: приманки (decoys)

Иногда подбрасывают **фальшивые улики**: «пароли.txt» с мусором, поддельные документы,
ложные следы другой атаки. Цель — чтобы следователь пошёл не туда.

Как распознать: сверять находку с **независимыми источниками**. Если «улика» нигде, кроме
одного места, не подтверждается — это может быть приманка.

## Главный принцип: перекрёстная проверка

Любой отдельный артефакт может врать. Вывод строят на **согласовании нескольких
независимых источников**:

```
журнал хоста  +  сетевой лог  +  артефакты входа  +  память  =>  вывод
```

Если запись в журнале не подтверждается сетевым логом и артефактами — она поддельная.
Если подтверждается тремя источниками — почти наверняка настоящая.

## Шаг: разбор нашей записи

- Проверяем `sshd` PID 9999: в других записях PID другие и последовательны → аномалия.
- Смотрим сетевой лог файрвола на `203.0.113.9`: соединения нет → запись не подтверждена.
- Проверяем `ghost` в `/etc/passwd`: нет → пользователь выдуман.
- Проверяем метку времени: совпадает с временем, когда журнал не писался → вставка.

Вывод: запись **внедрена** вручную. Настоящий след надо искать в других источниках.

## Чек-лист разбора поддельной записи

Когда запись выглядит подозрительно, прогони её по фиксированному списку вопросов:

1. **Существует ли субъект?** Пользователь в `/etc/passwd`, служба в `systemd`, процесс с таким PID.
2. **Есть ли парные события?** Успешному входу предшествует аутентификация, за ней — `session opened`, команды, `session closed`.
3. **Правдоподобен ли PID?** Внутри одного сеанса PID идут по возрастанию; «круглый» 9999 или скачок назад — аномалия.
4. **Согласуется ли время?** С другими записями, с системным дрейфом, с часовым поясом.
5. **Совпадает ли формат?** Число пробелов, порядок полей, кодировка, отсутствие «родных» префиксов.
6. **Подтверждается ли независимым источником?** Сетевой лог, `wtmp`, `auditd`, память.

Если хотя бы два пункта провалились — запись, скорее всего, внедрена.

## Timestomp в NTFS: $SI против $FN

На NTFS у каждого файла две группы временных меток: **`$STANDARD_INFORMATION`** (`$SI`) и **`$FILE_NAME`** (`$FN`). Инструмент вроде `timestomp` или `touch` правит обычно только `$SI`. Поэтому расхождение — сильный индикатор:

| Метка | $SI | $FN | Признак подделки |
|---|---|---|---|
| Создание | правится | редко правится | `$SI.C < $FN.C` или разные |
| Изменение | правится | редко | несовпадение |
| Доступ | правится | — | «слишком старое» |
| Запись MFT | — | — | `$SI` старше записи в MFT |

```
$ MFTECmd -f '$MFT' --csv out.csv
# $SI.CreationTime=2019-01-01  vs  $FN.CreationTime=2026-03-10  -> timestomp
```

Дополнительные улики: **номер записи в журнале `$LogFile`/`$UsnJrnl`** фиксирует изменения метаданных независимо от самих меток, а **`$SI` всех файлов с одинаковым временем** — признак массовой правки.

## Приёмы запутывания и их детект

| Приём | Цель | Детект |
|---|---|---|
| Инъекция строк в журнал | подставить пользователя/адрес | аномальный PID, нет парных событий |
| Timestomp | скрыть время файла | `$SI` vs `$FN`, `$UsnJrnl` |
| Приманка (decoy) | увести расследование | не подтверждается независимо |
| Подмена логов | скрыть вход | `wtmp`/`auditd` хранят дольше |
| Массовая правка меток | запутать таймлайн | одинаковые метки у разных файлов |
| Ложная атрибуция | подставить коллегу | IP/ключ не совпадают с сессией |

## Приманки и как не пойти по ложному следу

Приманка рассчитана на то, что следователь ухватится за первую яркую находку. Защита — дисциплина верификации:

- **Никогда не строи вывод на одном артефакте.** «Пароли.txt» на рабочем столе может быть подброшен.
- **Проверяй связность.** У настоящего следа есть предыстория (скачивание, запуск, сеть) и продолжение (использование, уход).
- **Смотри на «слишком удобное».** Идеально подходящая улика, найденная сразу, — повод насторожиться.
- **Сопоставляй с инфраструктурой.** Ложная атрибуция на коллегу не подтвердится его рабочим графиком, VPN-сессией и активностью.

## Крайние случаи и ограничения

- **Бинарные журналы сложнее.** `wtmp`/`btmp` — бинарные; их правят специальными инструментами, и повреждение структуры выдаёт вмешательство.
- **Централизованный сбор.** Если логи уходят на SIEM/удалённый сервер, локальная подчистка не помогает атакующему — но и у тебя может не быть доступа к центральному источнику.
- **Отсутствие `$UsnJrnl`.** На некоторых ФС (FAT, ext4 без ext4-журнала метаданных в том же виде) независимого источника меток нет; тогда опирайся на суперблок и журналы ОС.
- **Дрейф часов.** Неточные часы делают «несоответствие времени» ложным сигналом; всегда оценивай дрейф хоста.
- **Зашифрованные журналы.** Если логи подписаны (например, append-only через хэш-цепочку), проверка подписи сразу выявит вставку.

## Сценарий: два источника противятся одному

Разбираем конфликт: `auth.log` утверждает вход `ghost` с `203.0.113.9`, но:

```
# сетевой лог файрвола: соединений с 203.0.113.9 на порт 22 нет
$ grep 203.0.113.9 /var/log/firewall.log
(пусто)

# wtmp: сессии ghost нет
$ last -f /var/log/wtmp | grep ghost
(пусто)

# auditd: аутентификации нет
$ ausearch -ua ghost
<no matches>
```

Три независимых источника молчат — значит запись в `auth.log` **внедрена**. Настоящий след ищем там, где источники согласованы: возможно, вход был под другой учёткой, а `ghost` — отвлекающий шум. Правило простое: **вывод строится на пересечении источников, а не на самой громкой строке**.

## Инструменты и порядок проверки подделок

Рабочий набор для проверки «не подделано ли»:

```
$ grep -nE 'ghost|9999' /var/log/auth.log      # найти подозрительную запись
$ last -f /var/log/wtmp | head                 # независимый источник сессий
$ lastb -f /var/log/btmp | head                # неудачные входы (часто не чищен)
$ ausearch -ua ghost                            # auditd по пользователю
$ grep ghost /var/log/firewall.log             # был ли реальный трафик
$ stat -c '%n a=%x m=%y c=%z' suspicious.txt   # метки файла
$ MFTECmd -f '$MFT' --csv mft.csv              # $SI vs $FN в NTFS
```

Порядок проверки фиксированный: **сначала независимые источники, потом сам артефакт**. Смысл в том, что подделать один источник легко, а согласованно подделать несколько независимых — почти невозможно.

Чек-лист для каждой подозрительной записи:

1. Существует ли субъект (пользователь/процесс)?
2. Есть ли парные события (аутентификация до, действия после)?
3. Правдоподобен ли PID и его последовательность?
4. Согласуется ли время с другими записями и с дрейфом часов?
5. Совпадает ли формат строки с остальными?
6. Подтверждается ли независимым источником?

Если два и более пункта провалились — запись внедрена. Ошибки, которых стоит избегать: верить единственной яркой строке; игнорировать ротацию (`auth.log.1`, `.gz`); забывать про часовые пояса; считать, что отсутствие `auth.log` означает отсутствие событий (смотри `journald` и `wtmp`). Главное — вывод строится на пересечении источников.

## Что мы теперь знаем

- Ложные записи внедряют в журналы, чтобы увести расследование.
- Признаки: аномальные PID, отсутствие парных событий, нарушение формата и времени.
- Timestomp меняет метки; выдают расхождения между `$STANDARD_INFORMATION` и `$FILE_NAME`.
- Приманки проверяют независимыми источниками.
- Вывод строят на согласовании нескольких источников, а не на одном артефакте.
