## Вопрос, с которого всё начинается

Пользователь удалил файл `secret.txt` и очистил корзину. Файла «нет». Но нам нужно его
содержимое. Возможно ли это?

В большинстве файловых систем удаление **не стирает содержимое** — обнуляется лишь
запись о файле, а блоки с данными остаются на диске, пока их не перезапишут новые
файлы. Поэтому восстановление удалённых данных — базовый навык форензика: именно там
находят следы атак, пароли и флаги.

## Наш пример: удалённый secret.txt

Смотрим, что осталось в образе:

```bash
$ fls -r -d -o 2048 disk.img
r/r * 20: secret.txt
```

`fls` — утилита Sleuth Kit, которая перечисляет файлы в файловой системе. Флаг `-d`
показывает **удалённые** записи, а звёздочка `*` их помечает. `20` — это **inode**,
номер записи о файле. Файл «удалён», но система всё ещё помнит, где он лежал.

## Шаг 1: что происходит при удалении

| ФС | Что затирается | Что остаётся |
|----|----------------|--------------|
| ext4 | запись каталога, ссылка на inode | inode (частично), блоки данных |
| FAT | первый байт имени = `0xE5` | кластеры (цепочка может сохраниться) |
| NTFS | флаг «in use» в записи MFT | запись MFT, runlist, запись USN |

Пока блоки не переиспользованы — содержимое извлекаемо. Отсюда железное правило: **после
удаления минимизируйте запись на носитель**, иначе новые файлы затрут старые данные.

## Шаг 2: извлекаем содержимое по inode

```bash
$ icat -o 2048 disk.img 20
$ strings <(icat -o 2048 disk.img 20) | head
CTF{undelete_ext4}
```

`icat` читает содержимое файла по номеру inode и выводит его в stdout. Мы «подставили»
этот вывод в `strings` (извлекает печатные строки) и сразу увидели флаг. Проверим
метаданные, чтобы убедиться, что файл действительно удалён:

```bash
$ istat -o 2048 disk.img 20
Size: 24        Links: 0        Modified: 2024-03-01 09:20:11
```

`Links: 0` — ноль ссылок на inode: подтверждение, что файл удалён. Но данные на месте.

## Шаг 3: если inode переиспользован

Иногда inode уже занят новым файлом — тогда `icat` вернёт чужое содержимое. Здесь
спасает **журнал** файловой системы: ext4 ведёт журнал `jbd2`, куда пишет изменения, и
по нему можно восстановить недавно удалённое.

```bash
$ sudo extundelete disk.img --restore-file home/user/secret.txt
$ grep -r CTF{ RECOVERED_FILES/
CTF{undelete_ext4}
```

`extundelete` читает журнал и восстанавливает файл даже когда inode переиспользован.

## Шаг 4: slack-пространство

**File slack** — это остаток последнего кластера файла: от логического конца данных до
границы кластера. Там часто лежат фрагменты предыдущих данных.

```bash
$ icat -o 2048 -s disk.img 20 > slack.bin
$ strings -n 8 slack.bin | grep -i flag
```

Флаг `-s` у `icat` дампит именно slack. Если файл маленький, его «хвост» может тянуться
в следующий кластер — там и прячется полезное.

## Шаг 5: unallocated-пространство

**Unallocated** — свободные блоки, хранящие «мусор» удалённых файлов. Это главный
источник для **carving** (извлечения файлов по сигнатурам):

```bash
$ blkls -o 2048 disk.img > unalloc.bin
$ strings -n 8 unalloc.bin | grep -iE 'flag|password|CTF{'
$ foremost -i unalloc.bin -o carved/
```

`blkls` дампит все нераспределённые блоки, `strings` ищет текст, а `foremost` режет
поток на файлы по сигнатурам (JPEG, PNG, PDF и так далее).

## Шаг 6: инструменты восстановления

| Инструмент | ФС | Режим |
|-----------|-----|-------|
| `tsk_recover -e` | все (TSK) | массовое восстановление с unallocated |
| `extundelete` | ext3/ext4 | журнал |
| `ext4magic` | ext4 | журнал + inode |
| `ntfsundelete` | NTFS | MFT |
| `photorec`/`foremost` | все | carving по сигнатурам |
| `debugfs lsdel` | ext4 | список удалённых inode |

```bash
$ tsk_recover -o 2048 -e disk.img rec/
$ sudo ntfsundelete /dev/sda1 -u -p 100 -t txt   # все .txt
```

## Шаг 7: проверяем, что восстановили

Восстановленный файл может быть частично перезаписан — проверяйте:

```bash
$ file rec/secret.txt
$ strings -n 6 rec/secret.txt | grep -i 'CTF{'
$ istat -o 2048 disk.img 20 | grep -E 'Size|Modified'
```

Если размер и времена совпадают с метаданными, а содержимое читается — восстановление
корректно. Если `strings` вернул чужие данные, блоки переиспользованы: помечайте файл
как повреждённый.

## Шаг 8: восстанавливаем целые деревья

По одному файлу восстанавливать утомительно — для каталогов есть массовые режимы:

```bash
$ tsk_recover -o 2048 -e disk.img rec_all/     # всё, включая unallocated
$ tsk_recover -o 2048 -d 128 disk.img rec_dir/ # только каталог по inode
$ sudo extundelete disk.img --restore-all
$ sudo ntfsundelete /dev/sda1 -u -t docx -p 100
```

`tsk_recover` сохраняет структуру путей, `extundelete --restore-all` восстанавливает
целые каталоги из журнала. Полезно построить bodyfile удалённых inode (`ils -m`) и
посмотреть времена: часто удалённый файл лежит «между» соседями по времени — это
подсказывает, где искать его в unallocated.

## Шаг 9: когда восстановить нельзя

Восстановление возможно не всегда:

- **Перезапись блоков** — новые файлы затирают старые.
- **TRIM на SSD** — контроллер обнуляет блоки, данные исчезают физически.
- **Шифрование** (BitLocker/LUKS/FileVault) — без ключа восстанавливать нечего.
- **Журнал перезаписан** — ext4-журнал циклический, старые записи уходят.
- **Метаданные занулены** — вернётся содержимое без имени (только carving).

Иногда корректный вывод «данные утрачены» и есть результат расследования.

## Шаг 10: ext4-специфичные инструменты

У ext4 есть собственные средства работы с удалёнными inode:

```bash
$ debugfs -R "lsdel" disk.img      # список удалённых inode
$ debugfs -R "dump <20> /tmp/out" disk.img
$ sudo ext4magic disk.img -r -d recovered/
```

`debugfs` работает с файловой системой напрямую, `ext4magic` читает журнал и
восстанавливает по inode. Их стоит пробовать, когда `extundelete` не находит файл.

## Что мы теперь знаем

- Удаление стирает запись о файле, но не блоки данных.
- `fls -d` находит удалённые записи, `icat` извлекает содержимое по inode.
- `istat` подтверждает удаление (`Links: 0`) и даёт метаданные.
- Если inode переиспользован — выручает журнал (`extundelete`) или carving из unallocated.
- `blkls` + `foremost` вытаскивают данные из свободного места.

## На что смотреть дальше

- **TRIM на SSD** — контроллер обнуляет блоки, восстановление часто невозможно.
- **Шифрование** (BitLocker/LUKS/FileVault) — без ключа нет доступа и к удалённому.
- **Циклический журнал** — ext4-журнал перезаписывается; extundelete бессилен спустя время.
- **Не монтировать rw** — ФС «подчистит» удалённые записи при первой же записи.

## Куда дальше

Мы разобрали ext4/FAT/NTFS. Но у Apple своя файловая система — **APFS** — с
контейнерами, снапшотами и копированием при записи, из-за которых «удалённые» данные
живут дольше. В следующем уроке мы разберём образ macOS. А пока запомни: **удалили — не
значит стёрли; сначала образ, потом анализ**.

## Где пригодится

- **CTF:** классические задачи «восстанови удалённый файл».
- **Data recovery:** спасение данных после случайного удаления.
- **Incident Response:** поиск удалённых злоумышленником улик.
- **Криминалистика:** доказательство существования удалённых данных.
- **Анти-форензика:** понимание, как данные можно скрыть в slack/unallocated.
