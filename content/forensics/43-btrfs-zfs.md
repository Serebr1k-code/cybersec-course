## Вопрос, с которого всё начинается

В образе лежит файл `secret.txt`, но в текущем состоянии его нет — его удалили.
Однако сервер, с которого снят образ, использовал **снапшоты**. Возможно, старая
копия файла ещё жива в одном из них.

Обычные ФС (ext4, NTFS) при перезаписи затирают старые блоки. Современные —
**Btrfs, ZFS, XFS** — работают по принципу **copy-on-write (CoW)**: новые данные
пишутся в новые блоки, а старые не трогаются. Для форензика это подарок: предыдущие
версии файлов остаются на диске. В этом уроке разберём образ Btrfs и достанем файл
из снапшота.

## Шаг 1: принцип CoW — почему данные не исчезают

**Copy-on-write** переводится как «копирование при записи». Идея проста: система
никогда не перезаписывает существующий блок. Если нужно изменить данные, они
записываются в **свободный** блок, а ссылка в метаданных обновляется на него. Старый
блок освобождается, но физически не стирается, пока не понадобится снова.

Отсюда два следствия:

- **Предыдущие версии** файлов и метаданных остаются на диске.
- **Транзакции** и **снапшоты** хранят ссылки на прошлые состояния.

Проверяем, что у нас Btrfs. У Btrfs нет сигнатуры в нулевом блоке — суперблок лежит
со смещением 64 КиБ:

```bash
$ xxd -s 0x10000 -l 16 disk.img
00010000: 5f42 4852 6653 5f4d 0000 0000 0000 0000  _BHRfS_M........
```

Строка `_BHRfS_M` — это magic Btrfs (читается как «BHRfS M»). Она продублирована в
нескольких местах (по 64 КиБ, 64 МиБ, 256 ГиБ) — если первый суперблок повреждён,
берут копию.

## Шаг 2: читаем Btrfs без монтирования

Btrfs хранит данные в **B-деревьях** (сбалансированных деревьях). Корневое дерево
(`tree_root`) ссылается на все остальные деревья и на **снапшоты**.

Выводим список файлов прямо из образа, не монтируя:

```bash
$ btrfs restore -l disk.img | grep -i secret
Inode 257  secret.txt
```

`btrfs restore -l` — это «список» (`-l` = list). А вот восстановление содержимого
без монтирования:

```bash
$ btrfs restore disk.img out/
$ ls -R out/ | head
out/secret.txt
```

Мы вытащили файл прямо из дерева extent. Если бы он был удалён в текущем состоянии,
`btrfs restore` всё равно нашёл бы его, пока блоки не собраны сборщиком мусора (GC).

## Шаг 3: монтируем read-only и смотрим снапшоты

Снапшот — это «мгновенный снимок» состояния файловой системы на момент снятия.
Смонтируем образ **только для чтения** и поищем снапшоты:

```bash
$ sudo mount -o ro,loop disk.img /mnt/b
$ sudo btrfs subvolume list /mnt/b
ID 256 gen 30 top level 5 path @
ID 257 gen 25 top level 5 path @snapshots/2024-01-01
```

Видим снапшот `@snapshots/2024-01-01`. Файл, удалённый из текущего состояния, может
лежать в нём:

```bash
$ ls /mnt/b/@snapshots/2024-01-01/
secret.txt
$ cat /mnt/b/@snapshots/2024-01-01/secret.txt
CTF{snapshot_never_forgets}
```

Это ключевой приём форензики CoW-ФС: **удалённое в текущем состоянии ищите в
снапшотах**. Часто там же оказываются и предыдущие версии изменённых файлов.

## Шаг 4: ZFS — uberblock и `.zfs/snapshot`

ZFS устроена иначе: это **пул (zpool)** из устройств, поверх — датасеты (ФС/тома).
Корень — **uberblock**, и ZFS хранит **кольцо из 128 uberblock-ов**, каждый со своим
номером **TXG** (transaction group). Пока группа не «закреплена», старые uberblock-и
указывают на предыдущие состояния пула.

Импортируем пул из образа и сразу ставим **read-only**:

```bash
$ sudo losetup -Pf --show disk.img      # -> /dev/loop0
$ sudo zpool import -d /dev/loop0 pool_tmp -R /mnt/z -o readonly=on
$ zfs list -t snapshot
NAME                 USED  MOUNT
pool_tmp/data@old    1.2M  -
```

Снапшоты ZFS доступны как скрытый каталог `.zfs/snapshot`:

```bash
$ cat /mnt/z/pool_tmp/data/.zfs/snapshot/old/secret.txt
CTF{snapshot_never_forgets}
```

Важно: импортировать пул **только `-o readonly=on`**. Обычный импорт синхронизирует
пул, перезапишет TXG-историю и может уничтожить улики.

Прямой разбор без импорта — утилитой `zdb`:

```bash
$ zdb -l disk.img          # список uberblock-ов и их TXG
$ zdb -u disk.img          # текущий uberblock
```

## Шаг 5: XFS — allocation groups и журнал

XFS делит том на **allocation groups (AG)** — независимые группы, каждая со своим
суперблоком и B-деревьями. Magic суперблока — `XFSB`.

```bash
$ xfs_info disk.img
meta-data=/dev/loop0  isize=512  agcount=4  ...
```

Читать XFS можно через sleuthkit (он поддерживает XFS):

```bash
$ mmls disk.img
$ fls -r -o 2048 disk.img
$ icat -o 2048 disk.img <inode> > file.bin
```

А журнал XFS хранит транзакции метаданных — имена удалённых файлов, создание и
удаление inode:

```bash
$ xfs_logprint -t disk.img | head
```

## Шаг 6: универсальный подход

Независимо от типа CoW-ФС, схема одна:

```bash
# Btrfs: восстановить без монтирования
btrfs restore -D disk.img out/
# ZFS: монтируем ro и идём в .zfs/snapshot
zfs list -t snapshot
# XFS: sleuthkit + xfs_logprint
fls -r -o 2048 disk.img
# Универсально: carving по «мёртвым» блокам
strings -n 6 disk.img | grep -iE 'CTF\{'
binwalk disk.img
```

Последний приём — грубый, но работает всегда: если метаданные не помогают, ищем
строки прямо в сыром образе.

## Шаг 7: что искать в CoW-ФС в первую очередь

CoW-ФС дают форензику несколько уникальных зацепок. Проверяйте их по порядку:

1. **Снапшоты** — `btrfs subvolume list`, `zfs list -t snapshot`. Самое частое место
   «удалённого»: файл, которого нет сейчас, цел в старом снимке.
2. **Предыдущие версии** — если файл изменяли, старая версия может лежать в снапшоте.
   Сравнивайте содержимое: это доказывает, что и когда подменили.
3. **Журналы транзакций** — `xfs_logprint`, деревья Btrfs. Имена и метаданные,
   которых уже нет в текущем состоянии.
4. **«Мёртвые» блоки** — после удаления снапшота блоки освобождаются, но не затираются
   до перезаписи. `strings` по образу часто находит то, что «исчезло».

Отдельная тонкость — **timestamps снапшотов**: у Btrfs снапшот имеет своё время
создания, а у ZFS — номер TXG. По ним можно упорядочить версии файла во времени и
построить хронологию изменений, даже если обычные времена файла подделаны.

## Что мы теперь знаем

- CoW-ФС не перезаписывают блоки — предыдущие версии файлов остаются на диске.
- Суперблок Btrfs лежит по смещению `0x10000`, magic `_BHRfS_M`.
- `btrfs restore` вытаскивает файлы без монтирования; снапшоты — в `@snapshots/`.
- ZFS хранит историю в uberblock-ах; снапшоты доступны в `.zfs/snapshot`.
- XFS делит том на allocation groups; журнал хранит имена удалённых файлов.

## На что смотреть дальше

- **ZFS монтируйте только `-o readonly=on`** — обычный импорт перезапишет TXG-историю.
- **Не ищите суперблок Btrfs в нулевом блоке** — он на 64 КиБ; есть копии дальше.
- **Помните про GC/scrub** — удалённое в CoW-ФС живёт долго, но не вечно.
- **`.zfs/snapshot` — самый быстрый путь** к предыдущим версиям, не забывайте про него.
- **Повреждённый суперблок** — пробуйте его копии, прежде чем считать ФС мёртвой.

## Куда дальше

Мы разобрали, как устроены современные ФС и как доставать из них «удалённое». Дальше
возьмём весь арсенал Sleuth Kit — универсальный набор инструментов для разбора
любого образа и построения таймлайна. А пока запомни: **в CoW-ФС удалённое не
исчезает — оно ждёт тебя в снапшоте или свободном блоке**.
