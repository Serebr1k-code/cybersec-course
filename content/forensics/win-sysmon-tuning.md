## Вопрос, с которого всё начинается

На хосте установлен **Sysmon** — расширение Windows, которое логирует то, чего нет в
штатных журналах: создание процессов с хешами, сетевые соединения, загрузки драйверов.
Ты открываешь его журнал, но видишь не всё. Почему? Потому что Sysmon фильтрует события
по **конфигурации**, и от неё зависит, какие улики останутся.

Разберём сквозной пример: по журналу Sysmon восстановим цепочку запуска и поймём, что
могло быть отфильтровано.

## Что логирует Sysmon

Sysmon — служба и драйвер, которая пишет события в канал
`Microsoft-Windows-Sysmon/Operational`. Каждое событие имеет **Event ID**, свой для типа
активности:

- **1** — создание процесса (с командной строкой, хешами, родителем).
- **3** — сетевые соединения (процесс → IP:порт).
- **7** — загрузка образа (DLL).
- **8** — CreateRemoteThread (инъекция).
- **11** — создание файла.
- **12/13/14** — работа с реестром (create/set/rename).
- **15** — создание потока с Alternate Data Stream (следы «Mark of the Web»).
- **17/18** — создание/доступ к именованному каналу.
- **22** — DNS-запрос (имя хоста).
- **23/26** — удаление файла / перезапись.

Ключевое отличие от штатного 4688: Sysmon пишет **хеши**, **полную командную строку** и
**родительский процесс**, что критично для расследования.

## Наш пример: цепочка запуска

Смотрим события типа 1 (создание процесса) вокруг подозрительного времени:

```
$ evtx_dump.py Sysmon.evtx | grep -A12 'EventID>1<'
<EventID>1</EventID>
<Image>C:\\Windows\\System32\\cmd.exe</Image>
<ParentImage>C:\\Program Files\\Microsoft Office\\root\\Office16\\WINWORD.EXE</ParentImage>
<CommandLine>cmd.exe /c powershell -w hidden -enc SQBFAFgA...</CommandLine>
<Hashes>SHA256=9f1a7c...</Hashes>
```

Читаем: **WINWORD.EXE** породил **cmd.exe**, который запустил **скрытый PowerShell** с
закодированной командой. Это классическая цепочка макросного фишинга. Без Sysmon мы бы
не увидели ни родителя, ни хеша.

Дальше — сетевые события типа 3 для того же процесса:

```
<EventID>3</EventID>
<Image>C:\\Windows\\System32\\WindowsPowerShell\\v1.0\\powershell.exe</Image>
<DestinationIp>10.10.20.9</DestinationIp>
<DestinationPort>80</DestinationPort>
```

И DNS-событие 22:

```
<EventID>22</EventID>
<QueryName>cdn-update.example</QueryName>
```

Складываем: **Office → cmd → скрытый PowerShell → запрос DNS → соединение на 10.10.20.9**.
Это полная цепочка атаки.

## Конфигурация: что могло быть отфильтровано

Sysmon управляется **XML-конфигурацией**, где для каждого Event ID заданы правила
`include`/`exclude`. Типичные фильтры отсекают шум: например, не логировать процессы
`svchost.exe` или соединения на локальные адреса.

Проблема форензики: **если событие отфильтровано, оно не попадёт в лог вообще**. Поэтому
при разборе важно понять, какая конфигурация была применена. Её можно найти:

- в реестре: `HKLM\SYSTEM\CurrentControlSet\Services\SysmonDrv\Parameters`.
- в событиях: Sysmon пишет **Event ID 4** (изменение состояния службы) и **Event ID 16**
  (загрузка конфигурации) — в 16 иногда виден применённый XML.

Практический вывод: **отсутствие события в Sysmon ≠ отсутствие действия**. Всегда
проверяй, не отфильтровано ли оно.

## Тонкости, которые важно знать

- **Event ID 1 и 4688 дублируют друг друга**, но 4688 может не писать командную строку
  (если выключена политика аудита), а Sysmon пишет всегда.
- **ParentImage** может быть «подделан» техникой Parent PID Spoofing — реального
  родителя тогда видно по времени создания процессов.
- **Event ID 8 (CreateRemoteThread)** — прямой признак инъекции, но встречается и у
  легитимных программ; смотреть вместе с 10 (ProcessAccess).
- **Event ID 11 (FileCreate)** без фильтра даёт огромный объём — часто его включают
  только для конкретных каталогов.
- **Event ID 22 (DNS)** появился в новых версиях Sysmon; на старых его нет.

## Событие 8 и 10: обнаружение инъекций

Две записи Sysmon особенно ценны при подозрении на инъекцию кода.

**Event ID 8 (CreateRemoteThread)** фиксируется, когда один процесс создаёт поток в
другом. Легитимно так делают отладчики и некоторые системные службы; злонамеренно — так
внедряют код в чужой процесс.

```
<EventID>8</EventID>
<SourceImage>C:\\Users\\Public\\loader.exe</SourceImage>
<TargetImage>C:\\Windows\\System32\\lsass.exe</TargetImage>
<StartAddress>0x7ff8a1c00000</StartAddress>
```

Здесь `loader.exe` создал поток внутри `lsass.exe` — это попытка дампа учётных данных или
инъекции в критичный процесс. `StartAddress` можно сверить с адресами в загруженных
модулях: если адрес не принадлежит ни одному образу — почти наверняка бесфайловый код.

**Event ID 10 (ProcessAccess)** показывает, какие процессы открывали дескрипторы к другим
процессам, с какими правами:

```
<EventID>10</EventID>
<SourceImage>C:\\Users\\Public\\loader.exe</SourceImage>
<TargetImage>C:\\Windows\\System32\\lsass.exe</TargetImage>
<GrantedAccess>0x1410</GrantedAccess>
```

Права `0x1410`/`0x1010` (PROCESS_VM_READ + QUERY_INFORMATION) характерны для чтения памяти
`lsass.exe` — то есть для извлечения паролей. Комбинация 10 + 8 для одного источника —
сильный признак вредоносной активности.

## Как конфигурация влияет на детект

Разберём типичную ловушку. Администратор настроил Sysmon с фильтром, который **исключает**
шумные процессы, чтобы не забивать журнал:

```xml
<ProcessAccess onmatch="exclude">
  <TargetImage condition="is">C:\Windows\System32\lsass.exe</TargetImage>
</ProcessAccess>
```

Такая строка исключает **все** обращения к `lsass.exe` — и легитимные, и вредоносные.
В результате инъекция в `lsass` не попадёт в лог вообще. Форензик-вывод: перед выводами
о «чистоте» хоста нужно понять, какие фильтры стояли. Ищи применённую конфигурацию в
событии 16 (Sysmon config change) и в реестре.

Обратный случай — слишком **широкий** include: он даёт огромный журнал, в котором улику
трудно найти. Поэтому при разборе большого `Sysmon.evtx` сначала строят сводку по
Event ID и по `Image`, а потом углубляются в подозрительные процессы.

## Сопоставление с другими источниками

Sysmon силён в связке с другими журналами:

- **Security 4624/4625** — входы (успех/неудача) сопоставляются с запуском процессов.
- **PowerShell 4104** — код, который запустил процесс.
- **Загрузки браузера** — откуда пришёл файл-загрузчик.
- **Сетевые события 3/22** — куда процесс обращался.

Например, цепочка «браузер скачал `invoice.docm` → WINWORD породил `cmd` → PowerShell
запросил DNS → соединение на внешний IP» собирается из нескольких источников и даёт
полную картину фишинговой атаки.

## Частые ошибки

- **Доверять ParentImage без проверки.** PPID можно подделать; сверяй время создания.
- **Не учитывать версию Sysmon.** Новые Event ID (например, 22/23/26) есть не везде.
- **Смотреть только один Event ID.** Инъекция видна в связке 8+10, а не в одном.
- **Забыть про конфигурацию.** Отфильтрованное событие отсутствует, и это не «чисто».

## Шпаргалка команд

```
# Сводка по Event ID
evtx_dump.py Sysmon.evtx | grep -oE '<EventID>[0-9]+' | sort | uniq -c | sort -rn
# Все обращения к lsass
evtx_dump.py Sysmon.evtx | grep -B2 -A6 'TargetImage>.*lsass'
# Найти применённую конфигурацию
evtx_dump.py Sysmon.evtx | grep -A20 'EventID>16<'
```

## Что это даёт в отчёте

По Sysmon в отчёте фиксируют: полные командные строки запущенных процессов, их хеши,
родительские процессы, сетевые соединения и DNS-запросы, признаки инъекций. Это ядро
современного threat hunting и основа таймлайна атаки на хосте.

## Практический сценарий: охота на «living off the land»

Разберём сценарий, в котором атакующий не приносит своих бинарников, а использует
встроенные средства Windows — подход **living off the land**. Это самая сложная для
обнаружения тактика, и Sysmon здесь незаменим.

Предположим, в журнале мы видим необычное сочетание: `powershell.exe` порождён
`wmic.exe`, а тот — `rundll32.exe`. Каждый из этих процессов по отдельности легитимен, но
цепочка «rundll32 → wmic → powershell» нехарактерна для штатной работы и часто используется
для обхода детектов. Форензик-задача — понять, что реально делалось.

Читаем события 1 последовательно, сопоставляя время. У `wmic.exe` в командной строке может
быть запрос к классу WMI, а у `powershell.exe` — закодированная команда. Событие 3 покажет
сетевые соединения, а событие 22 — DNS. Здесь важно не «тонуть» в шуме: сначала строим
сводку по процессам, потом углубляемся только в подозрительные ветви.

Полезный приём — построение **дерева процессов** по времени. Сортируем события 1 по
`UtcTime`, строим связи «родитель → потомок». Аномальные ветви (редкие родители, нетипичные
для них дети) выделяются сразу. Например, `explorer.exe` обычно порождает `cmd.exe` по
действию пользователя, а `winword.exe` не должен порождать `powershell.exe` вовсе.

Дальше проверяем загрузки DLL (событие 7) для подозрительных процессов. Загрузка из
`Temp`/`Public`/`AppData` — красный флаг. Сопоставляя её с правками реестра (12/13), можно
увидеть, как малварь закрепляется и исполняется, не оставляя «явного» бинарника.

Ещё один важный аспект — **удаление файлов** (события 23/26). Атакующие часто заметают
следы: создают временный файл, исполняют и удаляют. Sysmon фиксирует и создание, и
удаление, поэтому даже «исчезнувший» файл остаётся в журнале. По хешу из события 1 его
можно найти в threat-intel базах.

В завершение строим сводную таблицу: процесс, командная строка, родитель, время, сетевые
адреса. Это ядро отчёта по хосту. Практический вывод: **Sysmon превращает разрозненные
события в связный таймлайн**, но только если аналитик умеет строить дерево процессов и
учитывать конфигурацию фильтров. Навык охота по Sysmon — один из самых востребованных в
современных SOC, и он же чаще всего проверяется в DFIR-задачах.

## Что мы теперь знаем

- Sysmon логирует то, чего нет в штатных журналах: **хеши, командные строки, родителей**.
- Ключевые Event ID: **1** (процесс), **3** (сеть), **8** (инъекция), **11** (файл),
  **22** (DNS).
- **Конфигурация фильтрует** события; отфильтрованное в лог не попадает.
- Применённую конфигурацию ищут в реестре и в событиях **4/16**.
- Отсутствие события не значит отсутствия действия — учитывай фильтры.

## Куда дальше

Мы разобрали телеметрию уровня процессов. Дальше посмотрим на **IFEO и COM-хайджек** —
техники закрепления, которые правят реестр и уводят запуск легитимных программ на код
атакующего. А пока главное запомни: **Sysmon даёт лучшие улики, но только в пределах
своей конфигурации**.

## Где пригодится

- **CTF Forensics:** задачи с журналами Sysmon.
- **DFIR:** восстановление цепочки выполнения и сетевой активности.
- **Threat Hunting:** охота по хешам, родителям и редким командным строкам.
- **Работа:** SOC-аналитик, инженер детектирования.
