## Вопрос, с которого всё начинается

Ты анализируешь Linux-сервер, который «странно себя ведёт»: процессы не видны в `ps`,
файлы исчезают. Это признаки **руткита** — вредоносного кода внутри ядра. Ядро Linux
расширяется модулями, и именно там прячется самое опасное ПО. Разберёмся, как это
увидеть.

## Наш пример: подозрительный модуль

Начнём с самого простого источника — списка загруженных модулей.

## Шаг 1: список модулей

```
$ lsmod | head -5
Module                  Size  Used by
nf_tables             245760  0
xt_conntrack           16384  1
```

`lsmod` читает `/proc/modules`. Три колонки: имя, размер в байтах, сколько раз
используется. Список длинный — но он не полный, если ядро заражено.

## Шаг 2: что модуль умеет

Каждый модуль можно распросить:

```
$ modinfo xt_conntrack
filename:       /lib/modules/6.1.0/kernel/net/netfilter/xt_conntrack.ko
license:        GPL
srcversion:     A1B2C3D4E5F6
depends:        nf_conntrack
```

`modinfo` показывает путь, лицензию и зависимости. Если модуль лежит не в
`/lib/modules/` или не имеет `srcversion` — это подозрительно.

## Шаг 3: подписи модулей

Ядро может требовать подписанные модули:

```
$ modinfo -F signature /lib/modules/$(uname -r)/kernel/net/netfilter/xt_conntrack.ko
(пусто, если подписи нет)
```

Если в системе включён **secure boot** и запрет неподписанных модулей, загрузить
чужой модуль нельзя. Проверить режим:

```
$ cat /sys/kernel/security/lockdown
[none] integrity confidentiality
```

`none` означает, что ограничения сняты — руткит может загрузиться.

## Шаг 4: скрытые модули

Руткит часто **вырезает** себя из списка, который показывает ядро. Тогда `lsmod` его
не покажет. Способ найти — сравнить список с реальными файлами `.ko` и с адресами
в памяти:

```
$ grep -c '' /proc/modules
142
$ find /lib/modules/$(uname -r) -name '*.ko*' | wc -l
141
```

Разница в один модуль — зацепка. Но более надёжно — искать по адресам структур ядра
(это делают Volatility/`linux_check_modules` на дампе памяти).

## Шаг 5: следы загрузки

Модуль где-то был загружен. Смотрим `dmesg`:

```
$ dmesg | grep -i 'module\|taint'
[  10.2] xt_conntrack: loading out-of-tree module taints kernel
```

«taints kernel» — ядро помечено как «грязное»: загружен модуль вне дерева. Это
признак стороннего кода.

## Что мы теперь знаем

- `/proc/modules` / `lsmod` — список загруженных модулей.
- `modinfo` показывает путь, лицензию, зависимости.
- Подписи и lockdown ограничивают загрузку.
- Руткит может скрыть себя из списка — сравнивай с файлами и памятью.
- `dmesg` с «taints kernel» сигналит о стороннем модуле.

## Если не сработало

- Нет доступа к живому ядру? Анализируй дамп памяти (Volatility).
- Модуль удалён с диска? Ищи его в кэше и в памяти.
- Всё выглядит чисто? Сравни хеши модулей с эталонными из пакета.

## Что внутри .ko: разбор через modinfo

Модуль ядра — это ELF-файл с расширением `.ko`. `modinfo` читает из него секцию
`.modinfo` и показывает метаданные:

```
$ modinfo suspicious.ko
filename:       /lib/modules/6.1.0/extra/suspicious.ko
license:        GPL
description:    "network helper"
author:         unknown
srcversion:     DEADBEEF123456
depends:        nf_conntrack
vermagic:       6.1.0 SMP mod_unload
sig_id:         PKCS#7
signer:         Build time autogenerated kernel key
sig_key:        1A:2B:3C
signature:      ...
```

| Поле | Что говорит |
|------|-------------|
| `filename` | откуда загружен — вне `/lib/modules` подозрительно |
| `license` | `GPL` vs `Proprietary` (не-GPL даёт taint) |
| `srcversion` | хеш исходников; **отсутствие** — самосборный бинарник |
| `depends` | от каких модулей зависит |
| `vermagic` | версия ядра, для которой собран |
| `sig_id`/`signer` | подпись и её владелец |
| `signature` | сами байты подписи |

Самосборный модуль без `srcversion`, без подписи, лежащий в `/opt` или `/tmp`, — типовой
руткит. Легитимные модули из дистрибутива подписаны ключом сборки и лежат в
`/lib/modules/$(uname -r)/kernel/`.

## Подписи, secure boot и lockdown

Загрузку модулей ограничивают три механизма, и их состояние — часть картины:

- **Secure Boot** — UEFI проверяет подпись загрузчика и ядра;
- **module signing** — ядро проверяет подпись `.ko` (`CONFIG_MODULE_SIG_FORCE`);
- **lockdown** — режим, запрещающий неподписанный код.

```
$ cat /sys/kernel/security/lockdown
[none] integrity confidentiality
```

- `none` — ограничений нет, любой модуль загрузится;
- `integrity` — блокирует изменения ядра (kexec, модули) из userspace;
- `confidentiality` — плюс запрет доступа к ядру (kdump, /dev/mem).

Проверить, форсируется ли подпись:

```
$ cat /sys/module/module/parameters/sig_enforce
Y
```

Если `sig_enforce=Y`, а в системе всё равно загружен неподписанный модуль — либо его
подделали, либо параметр поменяли при загрузке (ищи в `/proc/cmdline` и конфиге
загрузчика). Изменение `module.sig_enforce` в cmdline — сама по себе улика.

## Как руткит скрывает модуль

Ядро ведёт двусвязный список модулей (`struct module`, поле `list`). `lsmod` читает этот
список. Чтобы спрятаться, руткит **вырезает** свою структуру из списка (`list_del`), не
выгружая код:

```
$ lsmod | grep -c suspicious
0            # не виден
$ cat /sys/module/suspicious/refcnt
0
```

Но код и данные остаются в памяти. Признаки скрытого модуля:

- адрес модуля есть в `kallsyms`, а в `/proc/modules` его нет;
- запись есть в `/sys/module/<name>`, но не в `/proc/modules`;
- в памяти (по дампу) найден `struct module`, не связанный со списком.

## Кросс-вью: три источника против одного

Классический метод детекта — сравнить **три независимых представления**:

| Источник | Что показывает | Команда |
|----------|----------------|---------|
| список ядра | зарегистрированные модули | `lsmod` / `/proc/modules` |
| sysfs | объекты модулей | `ls /sys/module/` |
| память/диск | реальные `.ko` и структуры | `find`, Volatility `check_modules` |

```
$ comm -23 <(ls /sys/module | sort) <(awk 'NR>1{print $1}' /proc/modules | sort)
suspicious
```

Разница `sysfs` минус `/proc/modules` — модуль, который есть как объект, но вырезан из
списка. Это и есть кросс-вью-детект: руткит может перехватить **один** интерфейс, но
обмануть три согласованно — намного сложнее.

## Следы загрузки и taint

Ядро помечает себя «грязным», когда загружает сторонний код:

```
$ cat /proc/sys/kernel/tainted
12289
$ dmesg | grep -i taint
[ 10.2] suspicious: loading out-of-tree module taints kernel.
```

Битовые флаги taint (`/proc/sys/kernel/tainted`) кодируют причину: `G`/`P` — не-GPL или
проприетарный модуль, `O` — out-of-tree, `E` — неподписанный. Расшифровать:

```
$ dmesg | grep -i 'taint'   # или: cat /proc/sys/kernel/tainted
```

## Практический чеклист

1. `lsmod` и `/proc/modules` — базовый список.
2. `modinfo` подозрительных модулей — путь, `srcversion`, подпись.
3. `cat /sys/kernel/security/lockdown` и `sig_enforce` — режим защиты.
4. Кросс-вью: `comm -23 <(ls /sys/module) <(lsmod)` — искать «лишнее».
5. `dmesg | grep -i taint` и `/proc/sys/kernel/tainted` — признаки стороннего кода.
6. На дампе памяти — Volatility `linux_check_modules` / `linux_lsmod`.
7. Сравнить хеши модулей с эталонными из пакета (`rpm -V`, `debsums`).
