## Вопрос, с которого всё начинается

У тебя есть файл `msgstore.db` из мессенджера на телефоне. В нём — переписка, но
одно важное сообщение **удалено**. Нужно его вернуть.

`msgstore.db` — это **SQLite**, самая распространённая встраиваемая база данных
(одна база = один файл). Её используют браузеры, мобильные приложения, мессенджеры.
В форензике важно не только прочитать текущие данные, но и восстановить
**удалённые записи**. Разберём, как это устроено и как их достать.

## Наш пример: msgstore.db

Посмотрим на сигнатуру файла — первые 16 байт:

```bash
$ xxd -l 16 msgstore.db
00000000: 5351 4c69 7465 2066 6f72 6d61 7420 33  SQLite format 3
```

`SQLite format 3` — это заголовок базы. Файл состоит из **страниц** (обычно по 4 КБ).
Первая — заголовок, дальше — страницы с таблицами, свободные страницы и
overflow-страницы для больших записей. Узнаем базовые параметры:

```bash
$ sqlite3 msgstore.db "PRAGMA page_size; PRAGMA page_count; PRAGMA freelist_count;"
4096
120
8
```

`freelist_count = 8` — важная цифра: это **8 свободных страниц**, то есть место,
откуда ранее удалили данные. Именно там может лежать наше сообщение.

## Шаг 1: читаем текущие данные

Сначала посмотрим структуру и текущие записи:

```bash
$ sqlite3 msgstore.db ".tables"
messages  chats  ...
$ sqlite3 msgstore.db ".schema messages"
CREATE TABLE messages (key_remote_jid TEXT, data TEXT, timestamp INTEGER);
$ sqlite3 msgstore.db "SELECT key_remote_jid, substr(data,1,40) FROM messages LIMIT 3;"
```

Мы видим текущие сообщения. Но удалённого тут нет — обычный `SELECT` показывает
только «живые» строки. Идём за удалённым.

## Шаг 2: восстанавливаем удалённые записи

Когда строку удаляют, её страница помечается свободной (попадает в **freelist**), но
данные физически остаются, пока место не переиспользуют. Встроенная команда
`.recover` обходит базу целиком и вытаскивает максимум:

```bash
$ sqlite3 msgstore.db ".recover" | grep -i 'CTF{' | head
CTF{deleted_msg_recovered}
```

Удалённое сообщение восстановлено. `.recover` появилась в SQLite 3.29; она
восстанавливает и структуру таблиц, и «осиротевшие» записи. Можно собрать всё в
новую базу:

```bash
$ sqlite3 msgstore.db ".recover" | sqlite3 recovered.db
$ sqlite3 recovered.db "SELECT count(*) FROM messages;"
```

## Шаг 3: `undark` — копаем глубже

Специализированный инструмент `undark` сканирует freelist и неиспользуемое
пространство страниц ещё агрессивнее — иногда находит то, что `.recover` пропустил:

```bash
$ undark -i msgstore.db -o undark_out/
$ grep -ri 'CTF{' undark_out/ | head
```

## Шаг 4: свежие данные в WAL

SQLite пишет изменения не сразу в основной файл. Есть два механизма журналирования:

- **rollback journal** (`-journal`): старые страницы сохраняются перед изменением;
- **WAL** (Write-Ahead Logging, `-wal`): новые страницы сначала попадают в `-wal`,
  а в основную базу переносятся позже (при *checkpoint*).

Значит, **самые свежие** записи часто лежат только в `-wal`. Проверим режим:

```bash
$ sqlite3 msgstore.db "PRAGMA journal_mode;"
wal
$ ls -la msgstore.db*
msgstore.db  msgstore.db-wal  msgstore.db-shm
```

`-shm` — разделяемая память для WAL. Копируйте **все три** файла:

```bash
$ cp msgstore.db msgstore.db-wal msgstore.db-shm /evidence/
```

Важно: не выполняйте `PRAGMA wal_checkpoint` на оригинале — это перенесёт данные
из WAL в базу и **изменит улику**. Работайте с копией.

## Шаг 5: быстрый поиск без знания схемы

Часто быстрее не строить SQL-запросы, а просто поискать строки в файле:

```bash
$ strings -n 8 msgstore.db | grep -iE 'CTF\{|flag|password|token'
```

Это выручает в CTF, когда схема неизвестна: секрет может лежать в любой странице.

## Шаг 6: где ещё встречается SQLite

SQLite повсюду — полезно знать типичные источники:

| Источник | База |
|----------|------|
| Chrome/Edge | `History`, `Cookies`, `Login Data` |
| Firefox | `places.sqlite`, `cookies.sqlite` |
| WhatsApp | `msgstore.db` |
| Signal/Telegram | `signal.db`, `cache4.db` |
| iOS | `Manifest.db`, app-базы |
| macOS | `knowledgeC.db` |

Помни про **эпохи времени**: у каждого приложения свой формат (Chrome — микросекунды
с 1601, Firefox — с 1970, и т.д.). И про медиа: мессенджеры часто хранят вложения
отдельными файлами, а в базе — только ссылки.

## Что мы теперь знаем

- SQLite — один файл из страниц; заголовок `SQLite format 3`.
- Удалённые записи остаются в **freelist** и неиспользуемых областях страниц.
- **`.recover`** восстанавливает удалённое; **`undark`** копает глубже.
- Свежие данные могут лежать только в **`-wal`**; копируй все три файла.
- **VACUUM** перестраивает базу и уничтожает следы удалённых данных.

## На что смотреть дальше

- **Не копировать `-wal`/`-shm`** — потеряешь свежие данные.
- **Делать checkpoint на оригинале** — изменишь улику.
- **Игнорировать freelist** — там остаются удалённые записи.
- **Не использовать `.recover`** — обычный `SELECT` удалённое не покажет.
- **Забывать про `VACUUM`** — он мог уже затереть следы.
- **Считать базу «пустой»** — проверь WAL и freelist.

## Куда дальше

Мы научились восстанавливать удалённые записи из SQLite — источника, который
встречается и на десктопе, и на мобильных. В следующем уроке разберём более крупные
**серверные СУБД** (MySQL, PostgreSQL, MSSQL): где у них лежат данные и следы
действий атакующего. А пока запомни: **в SQLite удалённое не исчезает — оно уходит
в freelist, а свежее живёт в `-wal`**.

## Где пригодится

- **CTF** — восстановление удалённых записей в базах браузеров и приложений.
- **DFIR** — анализ активности пользователя и приложений.
- **Веб-форензика** — данные CMS/приложений на SQLite.
- **Мобильная форензика** — app-базы Android/iOS.
- **Судебная экспертиза** — доказательство фактов переписки и посещений.
