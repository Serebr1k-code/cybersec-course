## Вопрос, с которого всё начинается

На сервере данных нет — они на сетевом ресурсе. Ты не можешь снять «диск», потому что
диска нет: есть **экспорт NFS**. Прежде чем что-то делать, нужно понять, что вообще
открыто и как получить данные, не изменив их.

## Наш пример: смонтированный экспорт

Смотрим таблицу монтирования:

```
$ mount | grep nfs
server:/export/data on /mnt/data type nfs4 (rw,relatime,vers=4.2)
```

Строка `server:/export/data` — это **экспорт**: каталог `/export/data` на хосте `server`,
отданный по сети. Локально лежит только «вид» на него; байты — на сервере.

## Что такое NFS

**NFS (Network File System)** — протокол, по которому один хост отдаёт свой каталог
другим как файловую систему. Клиент видит папки и файлы так, будто они локальные.
Ключевые версии: NFSv3 и NFSv4. Разница для форензика: v4 умеет ACL и более богатую
аутентификацию, v3 часто полагается на `uid`/`gid` и доверие к клиенту.

## Шаг 1: узнать, какие экспорты открыты

С сервера (или с клиента, если разрешено) спрашиваем список:

```
$ showmount -e server
Export list for server:
/export/data  10.0.0.0/24
/export/backup (everyone)
```

`(everyone)` — экспорт доступен всем. `/export/data` ограничен подсетью `10.0.0.0/24`.
Это сразу подсказывает, кто мог обращаться.

## Шаг 2: понять права

Опасная (и частая) настройка — `no_root_squash`: тогда `root` на клиенте сохраняет права
`root` на сервере. Проверить можно по файлу экспорта на сервере:

```
$ cat /etc/exports
/export/data 10.0.0.0/24(rw,no_root_squash,sync)
```

Для расследования это важно: с такой настройкой клиент мог менять права и владельцев
файлов на сервере, и следы будут выглядеть «легитимно».

## Шаг 3: снять экспорт правильно

Экспорт — это каталог на сервере. Поэтому снимать надо **сервер** (или его снимок), а не
клиента. Если доступа к серверу нет, монтируем экспорт **только на чтение**:

```
$ mkdir -p /mnt/ro && mount -t nfs -o ro,vers=4.2 server:/export/data /mnt/ro
```

`-o ro` критично: монтирование на запись может изменить `atime` и другие метаданные,
испортив улики.

## Шаг 4: логи обращений

Сам сервер хранит следы обращений:

- `rpc.mountd` пишет, какие клиенты монтировали экспорт;
- системные журналы (`/var/log/syslog`, `messages`) фиксируют монтирования;
- на клиенте остаются записи в `/etc/fstab`, истории команд, кэше.

Совокупность «кто монтировал + когда + какие файлы читали» часто важнее содержимого.

## Ловушка: клиентский кэш

NFS-клиент кэширует атрибуты файлов. Значит, `stat` на клиенте может показывать
устаревшие данные. Для доказательств опирайся на **сервер** и его снимки, а клиентский
кэш используй как вспомогательный источник.

## Как работает монтирование: RPC, portmapper, mountd

NFS построен на **RPC** (Remote Procedure Call). Чтобы смонтировать экспорт, клиент делает несколько вызовов, и каждый оставляет след на сервере:

1. **portmapper/rpcbind (порт 111).** Клиент спрашивает, на каком порту слушает сервис монтирования. В NFSv3 это обязательно; в NFSv4 всё сведено на один порт 2049.
2. **mountd.** Клиент запрашивает разрешение на монтирование конкретного пути. Именно `rpc.mountd` пишет в журнал, **какой клиент** и **какой экспорт** запросил.
3. **nfsd.** После выдачи «файлового дескриптора» экспорта клиент обращается напрямую к серверу NFS за чтением/записью.

Для форензика это означает: следы монтирования живут в нескольких местах. `rpcbind` может быть отключён в NFSv4, но `mountd`-события и записи `nfsd` остаются. Если видишь подключение к порту 111 без последующего 2049 — это разведка (`rpcinfo -p server`), а не реальный доступ.

## NFSv3 против NFSv4: что меняется для расследования

| Аспект | NFSv3 | NFSv4 |
|---|---|---|
| Порты | rpcbind 111 + mountd + nfsd | только 2049 |
| Аутентификация | AUTH_SYS (доверие к uid/gid клиента) | RPCSEC_GSS (Kerberos), richer ACL |
| Идентификация | клиент называет свой uid | сервер знает принципала |
| Атрибуты | слабые, легко подделать uid | ACL и метки достовернее |
| Следы | много портов и сервисов | один порт, компактнее |

Практический вывод: **NFSv3 с AUTH_SYS — это доверие на слово.** Клиент говорит «я root с uid 0», и сервер, если включён `no_root_squash`, верит. Поэтому по NFSv3 доказать «кто именно читал файл» сложнее — источник можно подделать, и настоящий след остаётся только в сетевых журналах (IP).

## Атрибуты файлов и почему они важны для улик

NFS-клиент при монтировании обновляет **atime** при чтении. Это палка о двух концах: `atime` показывает, что файл читали, но само монтирование `rw` его меняет. Отсюда правило: если экспорт монтируется для экспертизы — только `-o ro,noatime`. Полезные атрибуты:

```
$ stat -c '%n  a=%x  m=%y  c=%z' /mnt/ro/secret.txt
secret.txt  a=2026-03-10 03:14:15  m=2026-01-02 09:00:00  c=2026-03-10 03:14:15
```

Здесь `mtime` (изменение содержимого) старый, а `atime` свежий — значит, файл **читали**, но не меняли. `ctime` изменился при чтении? Нет — `ctime` меняет только смена метаданных; свежий `atime` при старом `mtime` = факт чтения. Но помни: `atime` может быть подделан через `touch -a`, а `relatime` (по умолчанию) обновляет `atime` не каждый раз, а реже — это ловушка при построении таймлайна.

## Что искать на сервере и на клиенте

| Источник | Что даёт | Надёжность |
|---|---|---|
| `/etc/exports` (сервер) | какие каталоги и кому отданы, опции | высокая |
| `rpc.mountd` / syslog (сервер) | кто и когда монтировал | высокая |
| `nfsd`-статистика (сервер) | активность операций | средняя |
| `/etc/fstab`, `mount` (клиент) | постоянные и текущие монтирования | средняя |
| `~/.bash_history` (клиент) | ручные `mount`/`showmount` | средняя (чистится) |
| Снимок ФС сервера | истинное содержимое и метки | высокая |

## Крайние случаи и ограничения

- **Нет доступа к серверу.** Тогда единственный источник — клиентский кэш, а он неполон и может устареть. `nfsstat -c` покажет только агрегированную статистику, не имена файлов.
- **`no_root_squash` + NFSv3.** Клиент мог менять владельцев и метки на сервере; доказательство «root читал файл» размывается.
- **`async`-экспорт.** Записи могут теряться при крахе сервера — метки и содержимое расходятся.
- **Клиентский кэш атрибутов.** `stat` на клиенте показывает устаревшие данные (по умолчанию до 60 секунд `ac`); для улик опирайся на сервер.
- **Ротация и очистка.** Следы монтирования в `syslog` ротируются; журналы фаервола с IP-источниками часто хранятся дольше.

## Практический сценарий: реконструкция доступа

Задача: доказать, что с клиента `10.10.20.9` читали `/export/data/secret.txt`.

```
# 1. На сервере — какие экспорты открыты и кому
$ showmount -e server
/export/data 10.10.20.0/24

# 2. Кто монтировал (mountd в syslog)
$ grep -i 'mounted' /var/log/syslog | grep 10.10.20.9
Mar 10 03:14:15 server rpc.mountd[812]: authenticated mount request from 10.10.20.9:752 for /export/data

# 3. Снимок ФС: подтверждаем atime
$ stat -c '%x' /snap/export/data/secret.txt
2026-03-10 03:14:20

# 4. Фаервол: был ли реальный трафик
$ grep 10.10.20.9 /var/log/firewall.log | grep 2049
```

Совпадение трёх независимых источников (mountd + снимок ФС + фаервол) делает вывод устойчивым. Одного `stat` на клиенте недостаточно: он может врать из-за кэша.

## Инструменты и типовые ошибки расследования

Набор инструментов для NFS-расследования невелик, но их важно применять в правильном порядке:

```
$ rpcinfo -p server          # какие RPC-сервисы и порты открыты
$ showmount -e server        # список экспортов и разрешённых клиентов
$ mount -t nfs -o ro,noatime server:/export /mnt/ro   # снять только для чтения
$ nfsstat -s                 # серверная статистика операций
$ grep -i mountd /var/log/syslog                       # кто монтировал
```

Частые ошибки при разборе:

- **Монтирование на запись.** Любой `mount` без `-o ro` может обновить `atime` и испортить улику. Это ошибка номер один.
- **Доверие клиентскому `stat`.** Клиент кэширует атрибуты; для доказательств нужен сервер или его снимок.
- **Игнорирование `no_root_squash`.** При такой настройке клиентский root менял владельцев и метки на сервере — вывод «кто что делал» размывается.
- **Разные часовые пояса.** Сервер и клиент могут писать время в разных зонах; без нормализации таймлайн ломается.
- **Опора на один источник.** След монтирования надо подтверждать минимум двумя независимыми источниками (mountd + снимок ФС + фаервол).

Правило: сначала фиксируешь состояние (снимок/дамп), потом анализируешь, никогда наоборот. NFS-экспорт — это живой удалённый каталог, и любое неосторожное действие меняет сервер.

## Сводка по NFS-форензике

Итоговая схема расследования: определить версию и экспорты (`rpcinfo`, `showmount`), зафиксировать состояние сервера снимком, снять экспорт только на чтение (`-o ro,noatime`), собрать следы монтирования из `rpc.mountd` и `syslog`, подтвердить факт доступа независимыми источниками (снимок ФС, фаервол, `nfsd`-статистика). Помни, что NFSv3 с AUTH_SYS доверяет клиенту на слово, поэтому IP-источник и серверные журналы важнее клиентских метаданных.

## Что мы теперь знаем

- NFS отдаёт каталог сервера как локальную файловую систему.
- `showmount -e` показывает экспорты и их доступ.
- `no_root_squash` расширяет права клиента — важно для расследования.
- Снимать нужно сервер/снимок; монтировать только на чтение.
- Серверные логи фиксируют монтирования и доступ.
