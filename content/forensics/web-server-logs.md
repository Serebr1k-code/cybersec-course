## Вопрос, с которого всё начинается

Веб-сервер оставил гигабайты `access.log`. Где среди них атака? Нужен метод, а не
перелистывание. Разберём.

## Наш пример: access.log

## Шаг 1: формат

Стандарт (combined):

```
$ tail -1 /var/log/nginx/access.log
203.0.113.5 - - [14/Jan/2026:03:20:00 +0000] "GET /admin.php?id=1 HTTP/1.1" 200 1234 "-" "sqlmap/1.7"
```

Поля: IP, время, запрос, статус, размер, referer, **User-Agent**. UA `sqlmap` — уже
сигнал.

## Шаг 2: фильтрация

```
$ awk '{print $1}' access.log | sort | uniq -c | sort -rn | head
  9000 203.0.113.5
```

Один IP с 9000 запросами — брутфорс/сканирование.

## Шаг 3: ищем атаки

```
$ grep -iE 'union.*select|<script|\.\./|/etc/passwd' access.log | head
```

Паттерны SQLi, XSS, path traversal видны прямо в URL.

```
$ grep -E ' (4[0-9]{2}|5[0-9]{2}) ' access.log | wc -l
```

## Шаг 4: ошибки

`error.log` содержит детали:

```
$ tail -3 /var/log/nginx/error.log
... PHP Fatal error: ... in /var/www/.../shell.php
```

Ошибки выдают путь к шеллу.

## Шаг 5: корреляция

- сопоставь IP с другими логами (auth, firewall);
- найди первый запрос атакующего (точка входа);
- проверь, что было загружено (POST на upload).

## Шаг 6: варианты формата

«Combined» — не единственный формат. Бывает «common» (без referer/UA) и кастомный:

```
$ head -1 /var/log/apache2/other_vhosts_access.log
example.com:80 203.0.113.5 - - [14/Jan/2026:03:20:00 +0000] "GET / HTTP/1.1" 200 1234
```

Современные стеки пишут JSON:

```
{"time":"2026-01-14T03:20:00Z","remote_addr":"203.0.113.5","request":"GET /admin","status":200}
```

Прежде чем фильтровать, определи формат — иначе поля «поедут» и анализ будет неверным.

## Шаг 7: продвинутая фильтрация

Для агрегатов удобны `awk`/`sort`/`uniq`, для отчётов — `goaccess`:

```
$ goaccess access.log --log-format=COMBINED -o report.html
```

Полезные срезы:

```
$ awk '{print $9}' access.log | sort | uniq -c | sort -rn   # статусы
$ awk '$9 ~ /^4/' access.log | wc -l                         # клиентские ошибки
```

Резкий рост 404/403 — признак сканирования директорий.

## Шаг 8: сканеры и боты по User-Agent

Инструменты оставляют узнаваемые UA:

```
$ awk -F'"' '{print $6}' access.log | sort | uniq -c | sort -rn | head
   8200 sqlmap/1.7
   4100 Nikto/2.5
```

`sqlmap`, `Nikto`, `masscan`, `Go-http-client` — сигналы автоматизации. Но помни: UA легко подделать, поэтому это зацепка, а не доказательство. Подтверждай поведением (частота, паттерны URL).

## Шаг 9: тела POST и загрузки

По умолчанию тела POST не логируются — видно только факт и размер. Ищем крупные POST:

```
$ awk '$6 ~ /POST/ && $10 > 50000' access.log | head
```

Большой POST на эндпоинт загрузки — вероятная доставка шелла. Если настроено логирование тела (mod_dumpio), тела дадут прямой payload.

## Шаг 10: ротация и восстановление

Логи ротируются и сжимаются:

```
$ ls /var/log/nginx/
access.log  access.log.1  access.log.2.gz
$ zcat access.log.2.gz | grep -i 'union' | head
```

Чтобы восстановить полную картину, объедини старые и новые файлы по времени. Иначе легко принять «середину атаки» за начало.

## Шаг 11: практика

Дано: несколько файлов логов. Действия:

1. определить формат по первой строке;
2. агрегировать IP и статусы;
3. найти паттерны атак (`union`, `../`, `<script`);
4. раскрыть ротированные `.gz` и слить по времени;
5. выделить первый запрос атакующего — точку входа.

Результат — хронология атаки, а не список подозрительных строк.

## Что важно запомнить

- Сначала определи формат (combined/common/JSON).
- Агрегация по IP и статусам выявляет атаку.
- UA — зацепка, подтверждай поведением.
- Тела POST обычно не логируются; ищи по размеру.
- Ротированные логи нужно раскрывать и сливать.

## Разбор реального инцидента

Перед нами сутки логов и подозрение на вторжение. Начинаем с агрегата по IP и видим аномалию: адрес `203.0.113.5` сделал девять тысяч запросов, тогда как остальные — десятки. Смотрим его запросы по времени: сначала сканирование (`GET /admin`, `/backup.zip`, `/.env` с кодами 404), затем брутфорс `/wp-login.php` (много 200/302), затем успешный вход и `POST /wp-admin/admin-ajax.php` с крупным телом. Через минуту — обращения к `uploads/2026/01/x.php`, то есть к загруженному файлу. В `error.log` находим `PHP Fatal error` в этом же файле: скрипт падал при запуске. Восстанавливаем полную хронологию: разведка → брутфорс → вход → загрузка → выполнение. Каждый этап подтверждён разными строками, а точка входа — первый успешный вход — датирована точно.

## Подводные камни

Главная ловушка — неполнота логов. За обратным прокси адрес клиента подменён адресом прокси, поэтому агрегация по IP врёт; смотри `X-Forwarded-For`. Ротация обрезает историю: без раскрытия `.gz` можно принять середину атаки за начало. Временная зона: сервер может писать в UTC, а аналитик думать в локальном времени — это сдвигает всю хронологию. Тела POST по умолчанию не пишутся, поэтому «payload» придётся восстанавливать по другим источникам (кэш, WAF, дамп трафика). И наконец, коды ответов не всегда однозначны: 200 может быть и страницей ошибки приложения. Всегда подтверждай вывод вторым источником.

## Что делать после

Собранную хронологию оформляют как отчёт с таймлайном: время, IP, действие, артефакт. Затем блокируют адрес и правила WAF, откатывают изменения и меняют скомпрометированные учётки. Логи сохраняют с хэшами — они доказательство. И проверяют, не было ли второго вектора: часто после первого входа атакующий оставляет несколько точек закрепления, и по логам видно их последовательность.

## Мини-справочник по фильтрам

Собери рабочий набор команд. Агрегация по IP: `awk '{print $1}' access.log | sort | uniq -c | sort -rn | head` — кто чаще всех обращался. Статусы: `awk '{print $9}' access.log | sort | uniq -c | sort -rn` — всплеск 404/403 значит сканирование, 401 — подбор паролей, 500 — сломанные запросы (часто от шеллов). Паттерны атак: `grep -iE 'union.*select|<script|\.\./|/etc/passwd|cmd=' access.log` — SQLi, XSS, traversal, RCE. User-Agent: `awk -F'"' '{print $6}' access.log | sort | uniq -c | sort -rn` — выделяет `sqlmap`, `Nikto`, `curl`. Крупные POST: `awk '$6 ~ /POST/ && $10 > 50000' access.log` — возможная загрузка полезной нагрузки. Временные окна: `grep '14/Jan/2026:03:' access.log` — сузить до часа инцидента. Ротированные: `zcat access.log.*.gz | grep …`. Ошибки: `tail error.log`, поиск `Fatal error` и путей к файлам. Сводный отчёт: `goaccess access.log --log-format=COMBINED -o report.html`. Имея этот набор, ты быстро пройдёшь путь от «гигабайта логов» до конкретной цепочки запросов, а дальше подтвердишь вывод другими артефактами — файлами, базой, сетью.

## Что мы теперь знаем

- Формат: IP, время, запрос, статус, UA.
- Агрегация по IP выявляет брутфорс.
- Паттерны атак видны в URL.
- error.log выдаёт пути и ошибки.
- Корреляция даёт точку входа.

- STL — геометрия; OBJ/GLTF/3MF несут метаданные.
- Бинарный STL: 80-байтовый заголовок + число треугольников.
- GLB = JSON+BIN; 3MF = ZIP+XML.
- Данные прячут в комментариях, чанках и самой геометрии.
- Сравнение с эталоном выявляет встраивание.

## Если не сработало

- Логи ротированы? Проверь `.1`, `.gz`.
- Нет access.log? Смотри логи прокси/шлюза.
- Нужны тела POST? Включи отдельное логирование.
