## Вопрос, с которого всё начинается

В PCAP есть передача файла, но данные разбиты на сотни пакетов, часть потеряна или
продублирована. Как собрать из них **целый файл**? Это задача реассемблирования TCP.

Разберём сквозной пример: извлечём переданный файл из сетевого дампа.

## Почему данные разбиты

**TCP** передаёт данные потоком байт, но физически режет их на **сегменты** — куски,
умещающиеся в пакет. Каждый сегмент имеет **порядковый номер** (sequence number). Приёмник
собирает сегменты по номерам в исходный поток.

Проблемы для аналитика:

- **Переотправки** — потерянный сегмент передаётся заново, и в дампе он встречается дважды.
- **Переупорядочивание** — пакеты могут прийти не по порядку.
- **Пропуски** — часть пакетов не захвачена, и файл неполон.
- **Разные направления** — данные идут в обе стороны, их нельзя смешивать.

Поэтому «просто склеить payload всех пакетов» не работает — нужен **корректный сбор по
последовательности** и направлениям.

## Наш пример: извлекаем файл

Wireshark умеет экспортировать объекты из потоков. Сначала найдём подозрительную передачу:

```
$ tshark -r cap.pcap -Y 'tcp contains "MZ"' -T fields -e ip.src -e ip.dst -e tcp.stream
10.10.20.9  10.10.20.55  7
```

Поток `7` содержит `MZ` — значит, передаётся исполняемый файл. Извлекаем объекты:

```
$ tshark -r cap.pcap --export-objects http,out/ 2>/dev/null
$ ls out/
%5CUsers%5Cjdoe%5Cupdate.exe
```

Если передача идёт по HTTP, `tshark` соберёт объекты автоматически. Для «сырого» TCP
(без HTTP) собирают поток вручную:

```
$ tshark -r cap.pcap -q -z follow,tcp,raw,7
```

Это покажет содержимое потока в hex, который можно декодировать в файл.

## Сбор вручную через tshark

Иногда нужно извлечь данные конкретного потока скриптом. Тогда берут поле `tcp.payload`,
декодируют hex и собирают по номерам:

```
$ tshark -r cap.pcap -Y 'tcp.stream == 7' -T fields -e tcp.seq -e tcp.payload
1 4d5a900003000000...
1461 04000000ffff0000...
```

Здесь `tcp.seq` — порядковый номер, `tcp.payload` — данные в hex. Сортируем по `seq`,
убираем дубликаты (одинаковый `seq` при переотправке), декодируем hex и склеиваем. Так
собирается файл даже без встроенных экспортёров.

## Обработка переотправок и пропусков

Переотправки (retransmission) определяются по повторяющемуся `seq` с теми же данными — их
нужно **убрать**, иначе файл раздуется. Пропуски (когда `seq` «прыгает») означают, что
пакет не захвачен: файл будет неполон. В отчёте это фиксируют — «дамп неполный» важно для
интерпретации.

Фильтр для переотправок:

```
$ tshark -r cap.pcap -Y 'tcp.analysis.retransmission' | wc -l
```

Большое число переотправок говорит о плохом канале или о захвате на границе сети.

## Что извлекают из потоков

- **Файлы** (PE/ELF, документы, архивы) — по сигнатурам `MZ`, `PK`, `%PDF`.
- **Учётные данные** — логины/пароли в открытых протоколах (FTP, HTTP Basic).
- **Изображения и объекты HTTP** — через `--export-objects`.
- **Ключи и сертификаты** — TLS handshake без шифрования.

## Полный порядок извлечения файла

Разберём методику целиком. Первый шаг — **определить поток**. Фильтруем PCAP по сигнатуре
искомого файла (`tcp contains "MZ"`, `tcp contains "PK"`, `tcp contains "%PDF"`) и получаем
номер TCP-потока. Это сразу сужает анализ до одного диалога.

Второй шаг — **проверить полноту**. Считаем переотправки и разрывы в `seq`. Если есть
пропуски, честно отмечаем, что файл может быть неполон. Иногда достаточно собрать то, что
есть, чтобы получить ответ (например, флаг в начале файла).

Третий шаг — **собрать данные**. Для HTTP используем `--export-objects`; для «сырого» TCP —
`follow,tcp,raw` или скрипт по `tcp.seq`/`tcp.payload`. Собранные байты сохраняем в файл.

Четвёртый шаг — **проверить результат**. Смотрим `file` и сигнатуру: если это PE — открываем
в дизассемблере; если архив — распаковываем; если документ — читаем. Часто внутри находится
следующий этап (полезная нагрузка), и анализ продолжается.

## Восстановление учётных данных

Отдельный класс задач — извлечение логинов и паролей из открытых протоколов. FTP, HTTP
Basic, Telnet, POP3 передают данные в открытом виде. Их находят фильтрами по командам:

```
tshark -r cap.pcap -Y 'ftp.request.command == "PASS"' -T fields -e ftp.request.arg
tshark -r cap.pcap -Y 'http.authorization' -T fields -e http.authorization
```

HTTP Basic-авторизация — это base64 от `user:password`, декодируется тривиально. FTP-пароль
виден прямо. Так из PCAP достают учётные данные, которые затем используют для понимания
масштаба компрометации.

## Работа с большими дампами

Большие PCAP (гигабайты) не открывают в GUI. Их обрабатывают потоково: `tshark` с фильтрами,
`tcpflow` для разложения по потокам, `tcpdump` для выборки. `tcpflow` особенно удобен — он
автоматически раскладывает каждый поток в отдельный файл, который можно исследовать
по отдельности. Это стандартный приём при работе с крупными захватами.

## Частые ошибки

- **Смешивать направления.** Данные клиента и сервера нужно собирать раздельно.
- **Игнорировать переотправки.** Они раздувают файл и ломают сигнатуру.
- **Считать дамп полным.** Пропуски — норма; фиксируйте их в отчёте.
- **Открывать большой PCAP в GUI.** Используйте tshark/tcpflow.

## Итог

Реассемблирование TCP — базовый навык сетевой форензики. Определите поток, проверьте
полноту, соберите данные по sequence-номерам (или экспортёром объектов), проверьте результат.
Вместе с извлечением учётных данных это покрывает большинство практических задач по PCAP.

## Сравнение инструментов извлечения

Для извлечения объектов из трафика есть несколько инструментов, и полезно знать их
различия. **Wireshark** умеет экспортировать объекты HTTP/SMB/DICOM через меню и показывает
потоки визуально — удобно для ручного анализа небольших дампов. **tshark** делает то же из
командной строки (`--export-objects`, `-z follow`), что важно для автоматизации.
**tcpflow** раскладывает каждый поток в отдельный файл, что незаменимо при работе с большими
захватами. **NetworkMiner** даёт графический интерфейс с реконструкцией файлов, сессий и
учётных данных.

Выбор зависит от размера и задачи: для интерактива — Wireshark/NetworkMiner, для
скриптового конвейера — tshark/tcpflow. В CTF обычно достаточно `tshark --export-objects` и
`follow,tcp,raw`.

## Извлечение из не-HTTP протоколов

HTTP — самый простой случай, потому что формат известен. Но файлы передаются и по другим
протоколам: SMB (сетевые папки), FTP (команда RETR), SMTP (вложения), DICOM (медицина).
Для каждого есть свои приёмы. В SMB файлы видны в объектах; в FTP — в данных команды RETR;
в SMTP — в MIME-частях письма. Wireshark умеет экспортировать объекты SMB и DICOM напрямую.
Если протокол неизвестен, помогает анализ сигнатур: ищем `MZ`/`PK`/`%PDF` в payload и
собираем поток.

## Восстановление при потерях

Если дамп неполон, файл не соберётся целиком. Но часто достаточно **частичного**
восстановления: заголовок файла содержит метаданные, а тело — данные. Для CTF флаг обычно
лежит в начале или в читаемой части, поэтому даже неполный сбор даёт ответ. При этом важно
честно указать в отчёте, что образ неполон, чтобы выводы не были переоценены.

## Итог

Реассемблирование TCP — фундамент извлечения данных из сети. Освойте последовательность:
определить поток → проверить полноту → собрать по sequence-номерам или экспортёром →
проверить сигнатуру. Эти шаги покрывают и HTTP, и «сырой» TCP, и большинство практических
задач по PCAP.

## Итог

Извлечение файлов из TCP сводится к четырём шагам: определить поток по сигнатуре, проверить
полноту (переотправки и пропуски), собрать данные по sequence-номерам или экспортёром
объектов, проверить результат командой `file`. Эти шаги одинаково работают и для HTTP, и для
«сырого» TCP, и для учётных данных в открытых протоколах. Освоив их, вы покрываете большую
часть практических задач по анализу PCAP.

## Замечание о целостности доказательств

Извлечённые из PCAP файлы — это производные доказательства. Их хешируют, фиксируют источник
(имя PCAP, номер потока, фильтр) и хранят вместе с исходным дампом. Если извлечение
повторяют, результат должен совпадать. Такая дисциплина делает выводы воспроизводимыми и
защищаемыми — стандарт форензик-отчёта, который отличает профессионала от новичка.

## Ключевая мысль

TCP — это поток байт, разрезанный на сегменты. Чтобы получить из него файл, недостаточно
склеить payload: нужно собрать сегменты по sequence-номерам, убрать переотправки и учесть
пропуски. Освоив этот порядок, вы сможете извлекать файлы, учётные данные и полезную
нагрузку из любого сетевого дампа — а это половина всех задач по PCAP.

## Ещё одна мысль

Помните, что «сырой» TCP встречается не только в веб-трафике: тот же порядок сборки
применяется к SMB, FTP, почте и любым бинарным протоколам. Поэтому освоенный навык
переносится на любую задачу, где данные передаются потоком.

## Что мы теперь знаем

- TCP передаёт **поток байт**, разбитый на сегменты с **порядковыми номерами**.
- Реассемблирование — сбор сегментов по `seq` с учётом направления.
- **Переотправки** дублируют данные, их убирают; **пропуски** делают файл неполным.
- Wireshark/tshark извлекают объекты (`--export-objects`) и показывают поток
  (`follow,tcp`).
- Вручную файл собирают из `tcp.seq` + `tcp.payload` (hex).
- Сигнатуры (`MZ`, `PK`, `%PDF`) указывают тип извлечённого файла.
