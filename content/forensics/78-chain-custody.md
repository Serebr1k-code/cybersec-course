## Вопрос, с которого всё начинается

В офисе изъяли ноутбук сотрудника — есть подозрение на утечку. Технически всё просто: снять образ диска и найти улики. Но если дело дойдёт до суда или увольнения, технически безупречное исследование может **развалиться**: нельзя доказать, что улику не подменили и не изменили по пути.

Именно для этого существует **цепочка хранения** (chain of custody) — документированная история улики от изъятия до представления. Разберём её на примере изъятия того самого ноутбука.

## Наш пример: изъятие ноутбука

Цепочка хранения — это, по сути, журнал, где для каждой улики записано: что это, кто и когда изъял, как обращался и кому передавал. Минимальный набор полей:

| Поле | Пример |
|------|--------|
| Идентификатор | evidence-001 |
| Описание | Ноутбук Lenovo, S/N PF12345 |
| Кто изъял | Иванов И., инженер ИБ |
| Когда/где | 2026-03-01 10:00 UTC, офис 5 |
| Как | write blocker Tableau, dc3dd |
| Хеш | SHA256 3a7f... |
| Передачи | кто, когда, кому, зачем |

Каждая **передача** улики (от изъявшего к аналитику, от аналитика в архив) — отдельная запись с подписью. Разрыв цепочки (нет записи о том, у кого улика была вчера) — основание оспорить доказательство целиком.

## Шаг 1: защищаем носитель от записи

Прежде чем подключать диск, его надо защитить от **любой** записи. Казалось бы, мы только читаем — но подключение носителя к системе меняет время последнего доступа, может «починить» файловую систему или запустить автозагрузку. Улика будет изменена, и это заметно.

Для этого используют **write blocker** — аппаратное устройство между носителем и рабочей станцией, которое физически блокирует команды записи. Программная альтернатива — перевести устройство в режим только-чтение:

```bash
$ blockdev --getro /dev/sdb
1     # read-only — запись запрещена
```

`blockdev --getro` возвращает `1`, если устройство в режиме только-чтение. Программная защита — лишь дополнение: аппаратный блокиратор надёжнее, потому что не зависит от ошибки операционной системы.

## Шаг 2: снимаем образ с хешами

Теперь снимаем побитовую копию диска — **образ**. Ключевой момент: образ снимается **вместе с хешами**. Хеш — это криптографический «отпечаток» содержимого: если хоть один байт изменится, отпечаток станет другим. Используют `dc3dd`, который считает хеш прямо в процессе:

```bash
$ sudo dc3dd if=/dev/sdb of=laptop.img hash=sha256 log=laptop.log
```

Здесь `if` — источник (диск), `of` — файл образа, `hash=sha256` — считать хеш, `log` — журнал операции. Важно посчитать хеш **и источника, и образа** и убедиться, что они совпадают:

```bash
$ sha256sum /dev/sdb > source.sha256
$ sha256sum laptop.img > image.sha256
$ diff source.sha256 image.sha256 && echo "identical"
identical
```

Слово `identical` означает: образ побитово совпадает с диском. Если бы хеши разошлись — образ снят с ошибкой, и как улика он бесполезен.

## Шаг 3: проверяем перед каждым анализом

Перед тем как начать работу, образ верифицируют — снова сверяют хеш с сохранённым:

```bash
$ sha256sum -c image.sha256
laptop.img: OK
```

`OK` подтверждает целостность. Если образ хранится в формате E01 (собственный формат инструмента EnCase), у него есть встроенная проверка:

```bash
$ ewfverify evidence.E01
```

## Шаг 4: работаем с копией, не с оригиналом

Главное правило: **оригинал хранят нетронутым** в защищённом месте, а весь анализ ведут на **рабочей копии**. Это гарантирует, что случайная ошибка при анализе не испортит улику.

```bash
$ cp --reflink=auto laptop.img laptop_work.img
$ sha256sum laptop.img laptop_work.img
```

Хеши копии и образа должны совпадать — иначе копия негодна. Монтируют копию тоже только-для-чтения:

```bash
$ sudo mount -o ro,loop,offset=$((2048*512)) laptop_work.img /mnt/case
```

`offset` здесь пропускает первые 2048 секторов (загрузочную область), чтобы смонтировать конкретный раздел (мы разбирали это в `forensics-partition-tables`).

## Шаг 5: фиксируем инструменты и время

Чтобы результаты можно было **воспроизвести** (а без этого они не доказательство), записывают версии инструментов и окружение:

```bash
$ dc3dd --version | head -1 > tools.txt
$ uname -a >> tools.txt
$ sha256sum laptop.img >> tools.txt
```

И ещё одно правило — **время всегда в UTC**. Разные системы пишут логи в своих часовых поясах, и без единого стандарта события «разъедутся» на часы.

## Что мы теперь знаем

- Цепочка хранения — журнал: что за улика, кто/когда изъял, как обращался, кому передавал.
- Подключение носителя меняет его; защита — аппаратный **write blocker** (`blockdev --getro` = 1).
- Образ снимают вместе с хешами (`dc3dd hash=sha256`); хеши источника и образа должны совпасть.
- Перед анализом образ верифицируют (`sha256sum -c`, `ewfverify`).
- Анализ ведут на **рабочей копии**, оригинал хранят нетронутым.
- Фиксируют версии инструментов и время в UTC — для воспроизводимости.
