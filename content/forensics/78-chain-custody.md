Chain of custody (цепочка хранения) — это документированная история улики от изъятия до представления в суде. Без неё даже технически безупречное исследование может быть признано недопустимым: нельзя доказать, что улику не подменили и не изменили. Этот урок — про принципы допустимости цифровых доказательств, хеширование, write blockers, документацию и типовые ошибки.

## Что такое цепочка хранения

Цепочка хранения фиксирует для каждой улики:

| Поле | Пример |
|------|--------|
| Идентификатор | evidence-001 |
| Описание | USB SanDisk 16GB, S/N 123456789 |
| Кто изъял | имя, должность |
| Когда/где | 2024-03-01 10:00 UTC, офис 5 |
| Как | write blocker Tableau, dc3dd 7.2 |
| Хеш | SHA256 3a7f... |
| Передачи | кто, когда, кому, зачем |
| Хранение | сейф №3, пломба |

Каждая передача (от изъявшего к аналитику, от аналитика в архив) — запись с подписью. Разрыв цепочки — основание оспорить доказательство.

## Принципы допустимости

1. **Подлинность** — улика та, за которую её выдают.
2. **Целостность** — не изменена (хеши совпадают).
3. **Полнота** — собрана целиком.
4. **Достоверность** — корректно извлечена и интерпретирована.
5. **Допустимость** — получена законно (ордер/авторизация).

Эти принципы (в разных формулировках — ACPO, SWGDE, ISO 27037) лежат в основе любой методики.

## Хеширование

Хеш — криптографический «отпечаток» содержимого. Считайте его при изъятии и проверяйте при каждом доступе.

```bash
# хеш носителя и образа
$ sha256sum /dev/sdb > source.sha256
$ sha256sum disk.img > image.sha256
$ diff source.sha256 image.sha256 && echo "identical"
# dc3dd считает хеш при снятии
$ sudo dc3dd if=/dev/sdb of=disk.img hash=sha256 log=dd.log
# E01 несёт встроенные хеши
$ ewfverify evidence.E01
# проверка перед анализом
$ sha256sum -c image.sha256
```

Используйте SHA-256 (или SHA-1 + MD5 для совместимости). Хеш **источника** и **образа** должны совпадать; фиксируйте оба в отчёте.

## Write blockers

Аппаратный write blocker (Tableau, WiebeTech) — между носителем и рабочей станцией, физически блокирует запись. Программная защита (`blockdev --setro`, монтирование `ro`) — дополнение, не замена.

```bash
$ blockdev --getro /dev/sdb
1     # read-only
$ sudo mount -o ro,loop disk.img /mnt/img
```

Без блокировки подключение носителя может изменить last-access, «починить» ФС, запустить автозагрузку — улика изменена.

## Документирование

Каждое действие с уликой — в журнале: снятие образа, анализ, экспорт. Ведите отдельный документ на улику. Фиксируйте инструменты и версии (`dc3dd --version`), чтобы результаты были воспроизводимы. Скриншоты и логи инструментов — приложение к отчёту.

```bash
# фиксация инструментов и окружения
$ dc3dd --version | head -1 > tools.txt
$ uname -a >> tools.txt
$ sha256sum disk.img >> tools.txt
```

## Работа с копиями

Анализ ведите на **рабочей копии**, оригинал храните нетронутым (в сейфе). Копия должна быть побитовой и с проверенным хешем.

```bash
$ cp --reflink=auto disk.img disk_work.img
$ sha256sum disk.img disk_work.img    # должны совпадать
```

## Разобранный пример

Изъятие ноутбука.

```bash
# 1. Документировать (модель, S/N, состояние)
# 2. Извлечь диск через write blocker
$ blockdev --getro /dev/sdb    # 1
# 3. Снять образ с хешами
$ sudo dc3dd if=/dev/sdb of=laptop.img hash=sha256 hash=md5 log=laptop.log
# 4. Верифицировать
$ sha256sum /dev/sdb && sha256sum laptop.img    # совпадают
# 5. Смонтировать ro для анализа
$ sudo mount -o ro,loop,offset=$((2048*512)) laptop.img /mnt/case
# 6. Зафиксировать всё в журнале цепочки
```

| Требование | Реализация |
|-----------|-----------|
| Подлинность | серийный номер, фото |
| Целостность | SHA-256 источника и образа |
| Защита от записи | write blocker |
| Прослеживаемость | журнал передач |
| Воспроизводимость | версии инструментов, логи |
| Законность | ордер/авторизация |

## Частые ошибки

- **Нет write blocker** — улика изменена.
- **Хеш только образа** — нельзя доказать идентичность.
- **Разрыв цепочки** — нет записи о передаче.
- **Анализ оригинала** — риск изменения.
- **Отсутствие версий инструментов** — результаты невоспроизводимы.
- **Работа без авторизации** — доказательство недопустимо.
- **Ненадёжное хранение** — улика могла быть подменена.

## Что дальше / решение

Конвейер: документирование → write blocker → снятие образа с хешами → верификация → рабочая копия → журнал передач. Связка: `forensics-disk-imaging` (снятие), `forensics-reporting` (отчёт), `forensics-img-acquisition` (глубоко), `forensics-disk-images` (анализ).

## ISO 27037 и принципы ACPO

**ISO/IEC 27037** описывает обращение с цифровыми доказательствами: идентификация, сбор, изъятие, сохранение. **ACPO** (Association of Chief Police Officers) — четыре принципа:

1. Действия не должны менять данные.
2. Если доступ к оригиналу необходим — он компетентен и может быть объяснён.
3. Должна быть создана и сохранена «аудиторская тропа».
4. Ответственный за расследование несёт ответственность за соблюдение принципов.

Эти принципы применимы и в корпоративном IR: фиксируйте каждое действие, работайте с копиями, обосновывайте доступ к оригиналу.

## Формы и журналы

Практический минимум документов: форма изъятия (что, где, когда, кто), журнал цепочки (передачи), отчёт анализа (что найдено, какими инструментами), хеш-листы. Формы подписываются при каждой передаче.

```bash
# автоматическая генерация хеш-листа всего каталога улик
$ find /evidence -type f -exec sha256sum {} \; > evidence_hashes.txt
$ sha256sum -c evidence_hashes.txt
```

## Сводный чек-лист

1. Задокументировать улику (идентификатор, описание, S/N).
2. Подключить через write blocker.
3. Снять образ, зафиксировать хеши источника и образа.
4. Верифицировать (`sha256sum -c`, `ewfverify`).
5. Создать рабочую копию, оригинал — в защищённое хранилище.
6. Вести журнал передач (кто/когда/кому/зачем).
7. Фиксировать инструменты и версии.
8. Сохранять отчёт и логи анализа.

## Ограничения и риски

- **Облачные улики** — цепочка сложнее (данные у провайдера); нужны логи и заверения.
- **Мобильные устройства** — изоляция сети критична (удалённая очистка).
- **Живые системы** — сбор меняет состояние; фиксируйте порядок волатильности.
- **Шифрование** — без ключа улика недоступна; фиксируйте попытки.
- **Время** — фиксируйте в UTC, указывайте источник синхронизации.

## Оформление отчёта

Отчёт по цепочке хранения содержит: титул (дело, дата), список улик с идентификаторами, журнал передач, хеш-листы, перечень инструментов, подписи. В приложениях — логи снятия образов, скриншоты, вывод инструментов.

```bash
# приложение: журнал снятия образа
$ cat dd.log | grep -iE 'hash|time|input|output'
```

## Инструменты: сводка

| Инструмент | Задача |
|-----------|--------|
| `dc3dd`/`dcfldd` | снятие образа с хешами |
| `ewfacquire`/`ewfverify` | E01 + верификация |
| `sha256sum`/`md5sum` | хеши |
| `blockdev --setro` | read-only |
| `hashcat`/`sha256sum` | (не путать) |

## Практические приёмы

- **Единый идентификатор** для каждой улики.
- **Хеши источника и образа** — оба в отчёте.
- **Рабочая копия** — оригинал в сейфе.
- **Журнал передач** — подпись при каждой передаче.
- **Версии инструментов** — для воспроизводимости.
- **Время в UTC** — избежать путаницы.
- **Никаких действий без авторизации**.

## Значение для расследования

Соблюдение цепочки хранения защищает выводы от оспаривания: технически верное исследование теряет силу, если нельзя доказать неизменность улики. В корпоративном IR цепочка также важна — она обеспечивает доверие к отчёту и позволяет при необходимости передать материалы в правоохранительные органы.
