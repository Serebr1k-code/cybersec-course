## Вопрос, с которого всё начинается

Мы разобрали приёмы анти-форензики: timestomping, очистку логов, шифрование, удаление.
Но как **обнаружить**, что их применяли? Часто улика — не факт, а **аномалия**. Разберём
методологию.

## Наш пример: «слишком чистая» система

## Шаг 1: принцип — искать отсутствие

Анти-форензика проявляется как **недостача**:

- нет логов за период (должны быть);
- нет записей в MFT для файлов, которые есть;
- времена не сходятся;
- журналы обрываются.

```
$ ls -la /var/log/ | head
auth.log.1  auth.log.2.gz   (auth.log отсутствует)
```

Отсутствие **текущего** auth.log при наличии ротаций — аномалия.

## Шаг 2: расхождения временных меток

Timestomping выдаёт несоответствие:

- mtime в прошлом, ctime — свежий;
- SI ≠ FN на NTFS;
- время файла раньше времени создания ФС.

```
$ stat suspicious.bin | grep -E 'Modify|Change'
Modify: 2020-01-01
Change: 2026-01-14
```

## Шаг 3: полнота артефактов

Сопоставляй **независимые** источники:

- журнал событий vs. prefetch vs. MFT;
- `$UsnJrnl` vs. MFT;
- сетевые логи vs. хостовые.

Если один источник «молчит», а другие показывают активность — источник подчищен.

## Шаг 4: следы инструментов

Анти-форензика оставляет свои следы:

- строки в prefetch (`ccleaner.exe`);
- записи о запуске утилит очистки;
- удалённые, но открытые файлы;
- точки восстановления/VSS, удалённые нетипично.

## Шаг 5: методология

1. **Определи, какие артефакты должны быть** (эталон).
2. **Сравни с тем, что есть** (расхождения).
3. **Проверь времена** на согласованность.
4. **Ищи следы инструментов** очистки.
5. **Задокументируй** аномалии как находки.

## Что мы теперь знаем

- Анти-форензика проявляется как недостача/расхождение.
- Timestomping ловится по несоответствию меток.
- Сопоставление источников выявляет подчистку.
- Утилиты очистки оставляют свои следы.
- Метод: эталон → сравнение → времена → инструменты → отчёт.

## Если не сработало

- Всё согласовано? Возможно, анти-форензику не применяли.
- Нет эталона? Строй его из другой системы.
- Нужна глубина? Анализируй ФС низкого уровня.

## Строим эталон: какие артефакты ДОЛЖНЫ быть

Обнаружение анти-форензики — это сравнение с ожидаемым. Поэтому первый шаг — построить
**эталонный профиль** (baseline) системы: набор артефактов, которые обязаны существовать
на исправной машине за тот же период. Источники эталона:

- другая машина той же сборки ОС (лучший вариант);
- официальная документация по журналам и их ротации;
- «здоровый» образ той же версии ОС из лаборатории;
- сравнение нескольких пользовательских профилей на одном хосте.

Чем конкретнее эталон, тем точнее ловится аномалия. Например, на Windows Server всегда
есть `Security.evtx` с записями 4624/4634; их отсутствие за рабочий период — аномалия.

## Расхождения между источниками: где искать

Ключевой приём — сопоставление **независимых** источников, которые описывают одни и те
же события. Если один молчит, а другие активны — его подчистили.

| Событие | Источник A | Источник B | Источник C |
|---|---|---|---|
| Запуск программы | Prefetch | UserAssist (реестр) | Amcache |
| Создание файла | MFT (`$MFT`) | `$UsnJrnl` | журнал событий |
| Вход в систему | Security.evtx | SAM/LOGON | профиль NTUSER |
| Обращение к файлу | `$LogFile` | `$UsnJrnl` | LNK-файлы |
| Сетевые соединения | `SRUM` | журнал DNS | pcap |

Атака обычно чистит один-два источника и забывает про остальные. Именно «забытые»
источники и выдают подчистку.

## Следы конкретных инструментов очистки

Утилиты анти-форензики сами оставляют артефакты:

```
$ grep -ai 'ccleaner\|sdelete\|eraser' /evidence/MFT_dump.txt
$ grep -ai 'wevtutil' /evidence/Prefetch/*.txt
```

- **CCleaner / BleachBit** — записи о запуске, пути установки, `.lnk` в недавних;
- **sdelete** (`-z` / `-p`) — аномальные шаблоны записи, «пустые» сектора с `0x00`;
- **wevtutil cl** — обрыв журнала + отсутствие записи о завершении сессии;
- **timestomper** — расхождение `$STANDARD_INFORMATION` и `$FILE_NAME` на NTFS.

На Linux аналогично: `shred`, `dd if=/dev/zero`, `journalctl --vacuum-time`, ручная
правка `utmp`/`wtmp` (`last`, `lastlog`) — всё оставляет следы в `syslog`, `auditd`,
`bash_history` и в ctime самих файлов журналов.

## Практический разбор: «слишком чистая» система

Сценарий: инцидент зафиксирован в 03:00, но `auth.log` пуст, а `wtmp` за ту ночь
отсутствует. Проверяем:

```
$ stat /var/log/auth.log /var/log/wtmp
Modify: 2026-01-14 03:02   <-- момент очистки
$ ls -la /var/log/auth.log.1
-rw-r--r-- 1 root root 0 Jan 14 03:02 /var/log/auth.log.1
```

Нулевой размер ротации + свежий mtime = ручная очистка. Дальше ищем, чем чистили:

```
$ grep -aiE 'rm .*log|truncate|shred|: > ' /root/.bash_history /home/*/.bash_history
$ ausearch -ts recent -m 'execve' | grep -iE 'rm|shred|truncate'
```

Совпадение времени правки журнала с моментом сессии — сильная корреляция.

## Ложные срабатывания — не спеши с выводом

Аномалия ≠ атака. Регулярные причины «пропажи» артефактов:

- штатная ротация и `logrotate` (журнал ушёл в `.gz`);
- обновление ОС, которое пересоздаёт журналы;
- сбой питания — обрыв записи;
- антивирус/EDR, удаляющий «подозрительные» файлы сам;
- пользователь, удаливший профиль.

Поэтому вывод строится на **совокупности**: несколько независимых аномалий, совпадение по
времени и следы конкретных инструментов. Одна пропавшая запись — не приговор.

## Документирование находок

Каждую аномалию фиксируй по схеме «ожидалось / обнаружено / чем подтверждается /
альтернативное объяснение». Это защищает от ошибки и делает вывод воспроизводимым:
эксперт, читающий отчёт, должен сам убедиться, что «недостача» — не результат ротации.
Хэшируй артефакты до анализа и веди цепочку хранения (chain of custody).

## Ограничения методологии

- Нет эталона — сравнение субъективно; используй максимум внешних источников.
- Артефакт может отсутствовать по легитимной причине — проверяй альтернативы.
- Некоторые rootkits скрывают и сами расхождения — тогда нужен низкоуровневый анализ ФС
  и памяти, а не только «поверхностные» артефакты.

## Таблица индикаторов: техника → след → детект

Анти-форензика — это набор техник, и у каждой есть «анти-след», по которому её ловят.
Держи эту таблицу под рукой при расследовании:

| Техника | Ожидаемый след | Как обнаружить |
|---|---|---|
| Timestomping | согласованные времена | расхождение `mtime`/`ctime`, SI≠FN |
| Очистка логов | полные логи | обрыв, отсутствие активного файла |
| Шреддинг файла | файл + его MFT | нет MFT/USN, но есть ссылки |
| Шифрование | читаемые данные | энтропия, контейнеры, нет сигнатур |
| Удаление VSS | точки восстановления | резкое исчезновение снимков |
| Сокрытие процесса | процесс в списке | кросс-вью (ps vs /proc vs eBPF) |
| Подмена журнала | событие в логе | хеш-цепочка журнала нарушена |

Логика проста: **каждая техника оставляет несовпадение** между тем, что должно быть, и
тем, что есть.

## Расхождения на NTFS

NTFS хранит для каждого файла несколько наборов времён, и анти-форензика редко
обновляет их согласованно:

- **SI (Standard Information)** — времена, видимые в `dir`/`stat`;
- **FN (File Name)** — времена в записи имени, обновляются ядром;
- **$UsnJrnl** — журнал изменений, независимый от MFT;
- **$LogFile** — журнал транзакций метаданных.

Timestomp через API (`SetFileTime`) меняет SI, но не FN. Поэтому расхождение
`SI.mtime ≠ FN.mtime` — классический признак. Ещё сильнее: если файл правился, но в
`$UsnJrnl` нет соответствующей записи `DATA_OVERWRITE`, то журнал подчистили.

```
$ fls -m C: image.dd | head            # времена MFT
$ usnjrnl.py -f image.dd               # журнал изменений
```

## Расхождения на Linux (ext4, journal)

В Linux «времени рождения» (`btime`) долго не было, и анти-форензика работает иначе:

- **ctime** меняется при любом изменении inode, включая правку прав и владельца —
  его нельзя «поставить назад» обычным `touch`, не изменив ctime;
- `touch -d`/`touch -t` меняют `atime`/`mtime`, но **ctime становится текущим**;
- **ext4 journal** (`.journal`) хранит недавние операции метаданных — даже если файл
  удалён, там останется след;
- **`debugfs`** позволяет читать удалённые inode и journal без монтирования.

```
$ debugfs -R 'stat <12345>' image.dd
$ debugfs -R 'logdump -i <12345>' image.dd
```

Если `mtime` в 2020, а `ctime` сегодня — файл почти наверняка «омолодили» через
timestomp.

## Признаки конкретных инструментов

Утилиты зачистки оставляют собственные следы:

- **CCleaner** — строки в `prefetch`/`amcache`, записи `Software\Piriform`;
- **sdelete / cipher /w** — заполнение нулями/случайными байтами, характерные
  паттерны свободного места;
- **shred** — многопроходная перезапись, аномальная энтропия в свободных блоках;
- **timestomp** — несогласованные времена (см. выше);
- **wevtutil cl** — очистка журнала, событие `1102` («audit log cleared»), если само
  событие не подчистили.

Проверяй не только «что удалено», но и «какие инструменты запускались».

## Построение эталона и фиксация находок

Методология держится на **эталоне** — представлении о том, как выглядит «нормальная»
система того же класса:

1. Возьми похожую машину (та же ОС/версия) как baseline.
2. Составь список обязательных артефактов (журналы, prefetch, MFT, USN).
3. Сравни с исследуемой системой — расхождения = кандидаты в находки.
4. Для каждой аномалии фиксируй: **источник, доказательство, хеш**.
5. Считай хеши образов (`sha256sum`) до и после анализа — целостность улик.

Вывод строится на **совокупности** источников: одна аномалия может быть сбоем, три
согласованные — почти наверняка зачистка.

## Типичные ошибки расследования

- Объявить систему «чистой», потому что артефактов нет — отсутствие и есть улика.
- Полагаться на один источник, который как раз и подчистили.
- Игнорировать время **создания** файла в пользу `mtime`.
- Забыть про альтернативные хранилища: теневые копии, кеши браузера, память.
- Не задокументировать, что именно было «не так» — находка без фиксации теряется.

## Таймлайнинг как инструмент обнаружения

Анти-форензика ломает **согласованность** таймлайна, поэтому именно таймлайн — главный
детектор. Построй события из всех источников и наложи их:

```
$ log2timeline.py --storage-file case.plaso /evidence/
$ psort.py -o l2tcsv -w timeline.csv case.plaso
$ psort.py -o l2tcsv case.plaso 'date > "2026-01-14 02:00:00"' > window.csv
```

Признаки подчистки на таймлайне:

- **Разрыв** — плотный поток событий внезапно обрывается на несколько минут;
- **Скачок** — время прыгает назад/вперёд (смена часов или timestomping);
- **Дубликат** — одно событие есть в одном источнике и отсутствует в другом;
- **«Будущее»** — метка времени позже даты анализа;
- **Порядок** — файл изменён раньше, чем создан.

Наложив три-четыре источника на одну ось времени, аномалии видны как «дыры» и
несоответствия, даже если каждый источник по отдельности выглядит нормально.

## Специфика Linux и Windows

| Аспект | Linux | Windows |
|---|---|---|
| Очистка логов | `journalctl --vacuum`, `> /var/log/x` | `wevtutil cl`, Clear-EventLog |
| Метки времени | atime/mtime/ctime (+birth) | SI vs FN, MFT, USN |
| Следы в истории | `.bash_history`, `auth.log` | PowerShell log, Prefetch |
| Подделка времени | `touch -d` (меняет mtime/atime) | timestomper (SI, не FN) |
| Артефакт-свидетел | `auditd`, `wtmp`/`btmp` | SRUM, Amcache, ShimCache |

На Linux `ctime` подделать сложно (его меняет любое изменение inode), поэтому расхождение
`mtime` в прошлом и свежего `ctime` — сильный признак. На NTFS `$FILE_NAME`-времена почти
не поддаются подделке обычными тулами — расхождение с `$STANDARD_INFORMATION` выдаёт
timestomping.

## Быстрый чек-лист обнаружения

1. Определить ожидаемый набор артефактов (эталон).
2. Построить таймлайн из всех доступных источников.
3. Найти разрывы, скачки и дубликаты.
4. Проверить времена на согласованность (mtime vs ctime, SI vs FN).
5. Поискать следы инструментов очистки в истории и prefetch.
6. Проверить `system.log`/журналы на смену времени и обрыв.
7. Задокументировать каждую аномалию с альтернативным объяснением.
