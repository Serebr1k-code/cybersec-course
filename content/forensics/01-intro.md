Цифровая форензика — это не «набор утилит», а дисциплина мышления: вы учитесь задавать вопрос «откуда эти данные и можно ли им доверять?» раньше, чем вопрос «где флаг?». Этот урок — точка входа в ветвь: он даёт общую карту, словарь, порядок действий и минимальный рабочий набор инструментов. Всё остальное в категории — углубление отдельных артефактов (ФС, память, реестр, PCAP, логи). Если вы поймёте этот урок, любая задача Forensics перестанет быть «чёрным ящиком»: вы всегда будете знать, с какого шага начать и почему.

## Что такое цифровая форензика

Цифровая форензика (digital forensics) — это дисциплина о том, как **собрать, сохранить, исследовать и интерпретировать** данные с носителей и систем так, чтобы результат можно было предъявить (в суде, заказчику, жюри CTF) и чтобы он был воспроизводим.

Ключевое отличие форензики от «просто анализа файла» — **доказуемость**. Вы не просто находите флаг; вы должны уметь объяснить: откуда взялись данные, почему им можно доверять и не испортили ли вы их в процессе. Именно поэтому в форензике так много внимания уделяется хешам, журналам и порядку действий.

Три поддисциплины, которые полезно различать:

- **Disk forensics** — работа с образами дисков и разделами: файловые системы, удалённые файлы, журналы ФС, MFT, $UsnJrnl.
- **Memory forensics** — анализ дампов RAM: процессы, сетевые соединения, инжектированный код, ключи шифрования в открытом виде.
- **Network forensics** — анализ PCAP и логов: восстановление файлов из потоков, реконструкция сессий, выявление C2.

В CTF категория Forensics обычно означает одно из:

- вам дают **файл-контейнер** (архив, образ диска, дамп памяти, PCAP) и нужно вытащить флаг;
- вам дают **набор артефактов** (логи, реестр, EVTX) и нужно восстановить хронологию атаки;
- вам дают **«битый» или замаскированный** файл и нужно понять его истинную природу.

## Ключевые принципы работы с доказательствами

1. **Никогда не работайте с оригиналом.** Сразу делайте побайтовую копию и считайте хеш.
   ```bash
   cp evidence.img evidence.img.orig          # сохранить оригинал отдельно
   sha256sum evidence.img | tee evidence.img.sha256
   md5sum   evidence.img | tee -a evidence.img.sha256
   ```
2. **Целостность (integrity).** Хеш (MD5/SHA-1/SHA-256) фиксируется до и после анализа. Если хеши совпали — данные не изменены. Для образа это делают `dc3dd`/`dd` с опцией `hash=sha256`:
   ```bash
   dc3dd if=/dev/sdb of=disk.img hash=sha256 log=imaging.log
   ```
3. **Порядок изменчивости (order of volatility).** Сначала собирают самое «летучее»: регистры CPU, RAM, сетевые соединения, потом диск. В CTF это чаще правило «сначала сними дамп памяти, потом трогай диск».
4. **Chain of custody (цепочка сохранности).** Кто, когда и что делал с доказательством. В отчёте ведите журнал: имя файла, хеш, кто извлёк, когда, какой командой.
5. **Повторяемость.** Любой ваш шаг должен быть воспроизводим коллегой по записям команд — поэтому сохраняйте не только результат, но и команды.
6. **Минимизация вмешательства.** Если можно прочитать, не записывая — читайте. Монтировать образ только read-only (`mount -o ro,loop`), а лучше вообще не монтировать, а работать через `fls`/`icat`.

Правило-мнемоника: **«Hash first, copy second, mount third, never write»**.

## Типовые артефакты и источники данных

| Источник | Что внутри | Инструменты |
|----------|-----------|-------------|
| Файл | сигнатура, метаданные, скрытые потоки | `file`, `xxd`, `binwalk`, `exiftool` |
| Образ диска | ФС, удалённые файлы, журналы | `sleuthkit`, `autopsy`, `testdisk` |
| Дамп памяти | процессы, ключи, пароли | `volatility3` |
| PCAP | сетевой обмен, файлы в потоках | `tshark`, `wireshark`, `zeek` |
| Логи | события входа, ошибки | `grep`, `jq`, `evtx_dump` |
| Реестр Windows | автозапуск, USB, пользователи | `regripper`, `RegistryExplorer` |
| Prefetch/AmCache | запускавшиеся программы | `PECmd`, `pecmd` |
| Артефакты браузера | история, куки, загрузки | `sqlite3`, `DB Browser` |
| USN/MFT | хронология файловых операций | `MFTECmd`, `fls -m` |
| Сетевые артефакты ОС | hosts, ssh known_hosts | `cat`, `grep` |

## Инструментарий: что держать под рукой

Минимальный набор, который стоит поставить один раз:

```bash
sudo apt update
sudo apt install -y file binwalk foremost exiftool sleuthkit testdisk \
  volatility3 tshark wireshark p7zip-full unzip zip \
  john hashcat steghide radare2 python3-pip
pip3 install oletools pefile capstone yara-python
```

Разложим по задачам:

- **file / xxd / hexdump / strings** — первичная идентификация и быстрый обзор.
- **binwalk / foremost / scalpel** — извлечение встроенных данных (`binwalk -eM` рекурсивно).
- **sleuthkit (mmls, fls, icat, tsk_recover)** — работа с образами ФС без монтирования.
- **volatility3** — анализ памяти (`vol.py -f mem.dmp windows.pslist`).
- **tshark / tcpflow / networkminer** — анализ трафика из командной строки.
- **john / hashcat** — восстановление паролей (форматы `-m 1000` NTLM, `-m 16500` JWT).
- **exiftool / exiv2** — метаданные изображений и документов.
- **oletools (olevba, oleid)** — макросы в Office-документах.
- **yara** — сигнатурный поиск по артефактам.

## Порядок изменчивости и сбор данных

Порядок сбора (от самого летучего к самому статичному):

1. регистры CPU и кэш;
2. оперативная память (RAM);
3. сетевые соединения и таблицы маршрутизации;
4. временные ФС и swap;
5. диски и их разделы;
6. резервные копии, логи, облачные артефакты.

Практический вывод для CTF: если в задании есть **и дамп памяти, и образ диска** — начинайте с памяти, потому что после выключения/перезагрузки «летучие» данные (открытые соединения, расшифрованные ключи, инжектированный код) исчезнут. Если дана только RAM — это почти всегда задача на `volatility3`.

## Как читать задание CTF Forensics

Порядок размышления:

1. **Прочитайте условие дословно.** Название, подсказки, формат флага (`CTF{...}`, `flag{...}`). Иногда подсказка в самом имени файла (`flag.png.exe`).
2. **Определите тип артефакта.** `file <target>` — первая команда почти всегда.
3. **Посмотрите на размер.** 512 байт → скорее всего сектор/структура; десятки МБ → образ; гигабайты → дамп памяти/диск.
4. **Проверьте метаданные и строки.** `strings -n 8 file | less`, `exiftool file`.
5. **Ищите сигнатуру формата.** `binwalk file` покажет встроенные архивы/ФС.
6. **Действуйте от простого к сложному:** кодировки → архивы → ФС → память.
7. **Ведите журнал.** Записывайте команды — это и «доказуемость», и способ вернуться на шаг назад.

## Практический пример: разбор «неизвестного файла»

Допустим, в задании дан файл `challenge.bin` без расширения.

```bash
# 1. Истинный тип
file challenge.bin
# -> challenge.bin: Zip archive data, at least v2.0 to extract

# 2. Метаданные и строки
exiftool challenge.bin
strings -n 8 challenge.bin | head -30

# 3. Встроенные форматы
binwalk challenge.bin

# 4. Если это ZIP — список содержимого без распаковки
unzip -l challenge.bin
# 5. Извлечение
unzip -o challenge.bin -d out/
ls -la out/
```

Если внутри оказался образ ФС:

```bash
# Таблица разделов
mmls disk.img
# Список файлов в разделе (offset 2048 секторов * 512)
fls -o 1048576 disk.img
# Извлечь файл по inode
icat -o 1048576 disk.img <inode> > recovered.bin
```

Если файл оказался архивом с паролем — пароль часто лежит рядом в метаданных или извлекается `john`:

```bash
zip2john protected.zip > zip.hash
john --wordlist=/usr/share/wordlists/rockyou.txt zip.hash
```

## Практический пример 2: дамп памяти

```bash
# Список процессов
vol.py -f mem.raw windows.pslist
# Скрытые/инжектированные процессы
vol.py -f mem.raw windows.psscan
# Сетевые соединения
vol.py -f mem.raw windows.netscan
# Дамп конкретного процесса
vol.py -f mem.raw -o out/ windows.dumpfiles --pid 1234
# Поиск строк/паролей в дампе
strings -n 6 mem.raw | grep -iE 'flag\{|CTF\{|password'
```

## Частые ошибки новичка

- **Работать с оригиналом** и случайно перезаписать его (например, распаковать архив поверх).
- **Игнорировать `file`** и сразу лезть в hex — теряя очевидную подсказку о формате.
- **Забывать про `strings -e l`** для UTF-16 строк (актуально для Windows-артефактов).
- **Не проверять несколько слоёв упаковки** (zip внутри zip внутри base64).
- **Останавливаться на первом результате `binwalk`**, не посмотрев всю выдачу до конца.
- **Не считать хеши**, из-за чего невозможно доказать неизменность данных.
- **Монтировать образ rw** и «поправить» файл — это уничтожает доказательство.

## Что делать дальше / решение

Выбор следующего шага по типу артефакта:

| Что на входе | Куда идти | Первый урок ветви |
|--------------|-----------|-------------------|
| Неизвестный файл | сигнатуры, карвинг | `forensics-file-magic`, `forensics-carving` |
| Архив | вложенные слои | `forensics-archives` |
| Образ диска | ФС, удалённые файлы | `forensics-filesystems`, `forensics-disk-images` |
| Дамп памяти | процессы, артефакты | `forensics-memory` |
| PCAP | потоки, файлы | `forensics-pcap` |
| Логи/реестр | хронология | `forensics-timeline`, `forensics-windows-artifacts` |

Если сомневаетесь — начните с `file`, `binwalk`, `strings` и `exiftool`. В 80% CTF-задач этого достаточно, чтобы понять направление.

## Где пригодится

- **CTF:** категория Forensics почти всегда начинается с идентификации артефакта.
- **Incident Response:** те же шаги — изоляция, снятие образа, фиксация хешей.
- **SOC / Threat Hunting:** понимание артефактов нужно для поиска следов атаки.
- **Работа следователем/экспертом:** цепочка сохранности и повторяемость — обязательны.
- **Bug bounty / pentest:** анализ дампов и логов помогает доказать эксплуатацию.
