## Вопрос, с которого всё начинается

Нужно понять, что происходило с файлами на NTFS: создание, удаление, переименование —
даже если запись в MFT подчищена. Три источника: **$MFT**, **$LogFile** и
**$UsnJrnl**. Разберём утилиты для них.

## Наш пример: том NTFS

## Шаг 1: $MFT

Главная таблица файлов. Каждому файлу — запись с атрибутами ($STANDARD_INFORMATION,
$FILE_NAME, $DATA).

```
$ analyzeMFT.py -f MFT -o mft.csv
```

`analyzeMFT` конвертирует MFT в CSV: имя, времена (4 штуки!), размер, родитель.

## Шаг 2: две пары временных меток

Ключевая тонкость NTFS: атрибут `$STANDARD_INFORMATION` (SI) и `$FILE_NAME` (FN)
хранят **разные** времена. Расхождение SI/FN — признак **timestomping**:

```
SI.mtime = 2020-01-01  (подделано)
FN.mtime = 2026-01-14  (реальное)
```

## Шаг 3: $LogFile

Журнал транзакций ФС. Фиксирует изменения метаданных **до** их применения:

```
$ LogFileParser.py -f LOGFILE
```

Позволяет восстановить последовательность операций (создание/удаление/переименование)
и найти записи, удалённые из MFT.

## Шаг 4: $UsnJrnl

USN (Update Sequence Number) — журнал изменений:

```
$ MFTECmd.exe -f '$UsnJrnl$J' --csv out/
```

Показывает: файл, причину изменения, время. Часто сохраняется даже при очистке MFT.

## Шаг 5: что искать

- **timestomping** (SI ≠ FN);
- **удалённые файлы** (в LogFile/UsnJrnl);
- **переименования**;
- **кто менял** (по времени).

## Что мы теперь знаем

- MFT — таблица файлов с атрибутами.
- SI и FN хранят разные времена → ловят timestomping.
- $LogFile — журнал транзакций (восстановление).
- $UsnJrnl — журнал изменений (устойчив к очистке MFT).
- Всё это — ключевые источники следов.

## Если не сработало

- MFT повреждён? Используй `$LogFile`.
- Нужны удалённые имена? Ищи в UsnJrnl.
- Нужен контент? Восстанавливай по кластерам.

## Расширенный разбор: восстановление удалённого файла по $MFT

Разберём полный цикл: файл удалён, но запись в `$MFT` ещё жива. Сначала найдём
запись по имени — `$MFT` это поток, его читают через `icat`/`fls`:

```bash
$ fls -r -p image.dd | grep -i secret
r/r * 1284-128-1:    secret.docx
```

Префикс `r/r *` означает, что запись удалена (inode не занят). Номер `1284`
— это MFT-запись, `128-1` — её атрибут данных. Проверим, цел ли ещё размер:

```bash
$ istat image.dd 1284
MFT entry found at offset ...
Allocated: False
$STANDARD_INFORMATION ... Modified: 2026-01-12 09:14:02
$FILE_NAME ... Size: 51200
```

`Allocated: False` подтверждает удаление. Если кластеры данных не перезаписаны,
файл извлекается напрямую:

```bash
$ icat image.dd 1284 > recovered_secret.docx
$ file recovered_secret.docx
recovered_secret.docx: Microsoft Word 2007+
```

Ключевой момент: `icat` берёт данные из записи `$DATA`, даже если она помечена
как нераспределённая. Если размер в `$FILE_NAME` и в `$DATA` расходятся, значит
запись переиспользовалась частично.

## Справочная таблица: метафайлы NTFS

| Метафайл | Назначение | Что даёт расследованию |
|---|---|---|
| `$MFT` | записи обо всех файлах | имена, таймстампы, размеры |
| `$LogFile` | журнал транзакций | история метаданных, порядок операций |
| `$UsnJrnl` | журнал изменений | какие файлы менялись, когда |
| `$Bitmap` | карта занятости кластеров | что свободно/занято |
| `$Secure` | дескрипторы безопасности | ACL |
| `$Extend/$ObjId` | идентификаторы объектов | связь записей |

## Краевые случаи: транзакции и журналы

- **$LogFile как кольцо.** Журнал циклический; старые записи вытесняются.
  Читают `LogFileParser`/`ntfs-log-track-parse` — они восстанавливают
  последовательность операций с метаданными.
- **$UsnJrnl: причины изменений.** Записи содержат reason-коды
  (`DATA_OVERWRITE`, `FILE_CREATE`, `FILE_DELETE`), что позволяет отличить
  правку от создания и удаления.
- **USN не хранит содержимое.** Он говорит «что и когда», но не «чем»; тело
  файла надо искать в `$MFT`/`$DATA` или в теневых копиях.
- **Сжатые и разреженные файлы.** `$DATA` может быть resident, compressed или
  sparse — `icat` умеет их раскрывать, но неверный парсер выдаст мусор.
- **Timestomping.** Пару временных меток (`$STANDARD_INFORMATION` vs
  `$FILE_NAME`) сравнивают: расхождение — признак подделки времени.

## Практический разбор: таймлайн из $UsnJrnl

`$UsnJrnl` — это журнал изменений, где каждая запись говорит «какой файл и
почему менялся». Извлекаем его и превращаем в таймлайн:

```bash
$ MFTECmd.exe -f '$J' --csv /out --csvf usn.csv
$ head -3 /out/usn.csv
UpdateTimestamp,Name,Reason,Source
2026-01-12 09:14:02,secret.docx,DATA_OVERWRITE,User
2026-01-12 09:15:40,secret.docx,DATA_TRUNCATION|CLOSE,User
```

Комбинация `DATA_OVERWRITE` + `CLOSE` — типичный признак правки файла. Причины
`FILE_CREATE` и `FILE_DELETE` отделяют создание от удаления, а `RENAME_NEW_NAME`
показывает переименование, которым часто маскируют файл.

## Типичные ошибки

- **Путать USN и содержимое.** Журнал даёт метаданные, но не тело файла —
  содержимое ищи в `$MFT`/`$DATA` или теневых копиях.
- **Игнорировать перезапись кольца.** `$UsnJrnl` ограничен по размеру; старые
  записи вытесняются, и «начала истории» может не быть.
- **Считать время создания абсолютным.** Реальное создание может быть старше,
  если файл копировали — сравнивай с `$STANDARD_INFORMATION`.
- **Не учитывать MAX-поток.** У `$UsnJrnl` есть `$Max`, хранящий смещение
  начала; парсеры используют его, чтобы не читать мусор.

## Связь с теневыми копиями и $LogFile

- **VSS / теневые копии.** Позволяют восстановить версии файла на момент
  снимка; вместе с USN дают полную картину правок.
- **$LogFile.** Журнал транзакций метаданных дополняет USN: он показывает
  последовательность низкоуровневых операций, включая незавершённые.
- **$Bitmap.** Карта занятости кластеров объясняет, перезаписаны ли данные
  удалённого файла (тогда восстановление невозможно).
- **Порядок работы.** Сначала фиксируй образ целиком, затем парси `$MFT`,
  `$LogFile`, `$UsnJrnl` — и только потом восстанавливай файлы через `icat`.
- **Хэширование.** Для каждого восстановленного файла считай SHA-256: это
  подтверждает неизменность и годится как доказательство.

## Расширенный пример: восстановление с частичной перезаписью

Когда кластеры данных перезаписаны, `icat` вернёт мусор. Проверим это и
попробуем обойти через теневую копию:

```bash
$ icat image.dd 1284 > attempt.docx
$ file attempt.docx
attempt.docx: data
```

Файл повреждён: содержимое заменили новые данные. Ищем теневую копию, где
версия ещё цела:

```bash
$ vshadowinfo image.dd
VShadow ver 2.0
  Number of stores: 2
$ vshadowmount -o 10000 image.dd /mnt/vss
$ fls -r /mnt/vss/vss1/ | grep -i secret.docx
r/r * 1284-128-1:   secret.docx
$ icat /mnt/vss/vss1/ 1284 > recovered.docx
$ file recovered.docx
recovered.docx: Microsoft Word 2007+
```

Снимок сохранил версию на момент создания — восстановление удалось. Если
теневых копий нет, остаётся искать содержимое в `$LogFile` (частичные записи)
или в нераспределённом пространстве (carving по сигнатурам `PK\x03\x04`).

## Контрольный список работы с NTFS

- [ ] Снять полный образ, посчитать SHA-256.
- [ ] Собрать таймлайн: `$MFT` -> `$UsnJrnl` -> `$LogFile`.
- [ ] Найти целевые записи (`fls -r`, поиск по имени).
- [ ] Проверить `Allocated`/`Size` (`istat`).
- [ ] Восстановить данные (`icat`), проверить `file`.
- [ ] При повреждении — теневые копии (`vshadowmount`).
- [ ] При отсутствии копий — carving нераспределённого пространства.
- [ ] Посчитать хэш восстановленного файла.

## Сравнение инструментов NTFS

| Инструмент | Назначение | Особенность |
|---|---|---|
| `fls` / `icat` | листинг/извлечение | Sleuth Kit, скриптуемость |
| `istat` | запись MFT | таймстампы, атрибуты |
| `MFTECmd` | разбор `$MFT`/`$J` | быстрый CSV-вывод |
| `LogFileParser` | `$LogFile` | реконструкция транзакций |
| `ntfsundelete` | восстановление | по inode/имени |
| `photorec` | carving | по сигнатурам, без имён |

## Ограничения и типичные ошибки

- **Перезапись кластеров.** Если данные перезаписаны, восстановление
  невозможно — проверяй `$Bitmap`.
- **Кольцевой `$UsnJrnl`.** Старые записи вытесняются; начала истории может не
  быть.
- **Timestomping.** Расхождение `$STANDARD_INFORMATION` и `$FILE_NAME` — признак
  подделки времени.
- **Resident-данные.** Мелкие файлы живут прямо в `$MFT`; `icat` их достаёт, но
  неверный парсер выдаст мусор.
- **Хэш-верификация.** Всегда сверяй SHA-256 восстановленного файла — без этого
  доказательство несостоятельно.

## Проверка результата

Подтверди, что восстановленный файл — это действительно искомые данные:

```bash
$ sha256sum recovered.docx
9a1b... recovered.docx
$ file recovered.docx && unzip -l recovered.docx | head -3
recovered.docx: Microsoft Word 2007+
Archive:  recovered.docx
  Length      Date    Time    Name
    10240  2026-01-12 09:14   word/document.xml
```

Внутренняя структура OOXML и метка времени совпадают с ожидаемой — файл цел.

## Что записать в отчёт

- Хэш образа и хэш каждого восстановленного файла.
- Номер MFT-записи, имя и путь исходного файла.
- Источник восстановления (`$DATA`, теневая копия, carving).
- Таймстампы и признак timestomping (расхождение SI vs FN).
- Причину неудачи, если файл не восстановлен (перезапись кластеров).
- Ограничения метода и использованные инструменты с версиями.

## Таблица: метафайлы и их данные

| Метафайл | Данные | Применение |
|---|---|---|
| `$MFT` | записи файлов | имена, таймстампы |
| `$UsnJrnl` | журнал изменений | что/когда менялось |
| `$LogFile` | транзакции метаданных | порядок операций |
| `$Bitmap` | карта кластеров | перезапись данных |

## Частые заблуждения

- «Удалённый файл всегда восстановим» — если кластеры перезаписаны, данных нет;
  проверяй `$Bitmap`.
- «USN хранит содержимое» — он говорит «что и когда», но не «чем»; тело файла
  ищи в `$MFT`/`$DATA` или теневых копиях.
- «Время создания абсолютно» — при копировании файла реальное создание старше;
  сравнивай SI и FN.
