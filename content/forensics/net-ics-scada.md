## Вопрос, с которого всё начинается

На заводе произошла авария, и подозрение — на кибератаку. Обычные веб-логи тут не
помогут: контур говорит на **Modbus** и **DNP3**. Это простые протоколы без
аутентификации, поэтому их легко подделать. Разберём, что искать в дампе.

## Наш пример: Modbus-трафик

## Шаг 1: узнаём протокол

Modbus TCP — порт 502:

```
$ tshark -r ot.pcap -Y 'modbus' -T fields -e modbus.func_code -e ip.src -e ip.dst | head
16	10.10.30.5	10.10.30.20
6	10.10.30.5	10.10.30.20
```

`func_code=16` — Write Multiple Registers, `6` — Write Single Register. Оба **пишут**
в устройство. Чтения — это `3`/`4`.

## Шаг 2: что именно писали

```
$ tshark -r ot.pcap -Y 'modbus.func_code==6' -T fields -e modbus.reference_num -e modbus.word_cnt | head
100	1
```

`reference_num=100` — адрес регистра, в который писали. Регистры управляют
физическими процессами: клапанами, насосами, уставками. Запись в них меняет поведение
оборудования.

## Шаг 3: аномалии

Нормальный оператор читает (func 3/4) и редко пишет. Всплеск записей — подозрительно:

```
$ tshark -r ot.pcap -Y 'modbus.func_code==16' -T fields -e ip.src | sort | uniq -c | sort -rn
  500	10.10.30.99
```

Источник `10.10.30.99` — не инженерная станция, а неизвестный хост. Вот и злоумышленник.

## Шаг 4: DNP3

DNP3 (порт 20000) сложнее и используется в энергетике:

```
$ tshark -r ot.pcap -Y 'dnp3' -T fields -e dnp3.src -e dnp3.dst -e dnp3.al.func | head
```

Функции прикладного уровня (например, `OPERATE`) меняют состояние. Их тоже смотри.

## Шаг 5: что искать

- запись в регистры/уставки с необычного хоста;
- изменение конфигурации PLC (загрузка новой программы);
- «холодный» старт устройства;
- несоответствие времени (NTP-подмена).

## Что мы теперь знаем

- Modbus TCP — порт 502; func 3/4 — чтение, 6/16 — запись.
- Регистры управляют физическим процессом.
- Всплеск записей с чужого хоста — атака.
- DNP3 — энергетический протокол, функции меняют состояние.
- Аутентификации в классических протоколах нет.

## Если не сработало

- Трафик на уровне RTU/серийного? Нужен преобразователь и другой анализ.
- Нет дампа? Смотри логи HMI/SCADA.
- Нужна физика? Сопоставь с журналом датчиков.

## Карта промышленных протоколов

АСУ ТП говорит на десятке протоколов, и каждый узнаётся по порту и структуре. Держи
ориентир:

| Протокол | Порт | Назначение | Опасные операции |
|---|---|---|---|
| Modbus TCP | 502 | универсальный, PLC/датчики | Write Coil/Register |
| DNP3 | 20000 | энергетика, телеметрия | OPERATE, DIRECT_OPERATE |
| EtherNet/IP (CIP) | 44818 | Allen-Bradley | CIP write |
| S7comm | 102 | Siemens S7 | CPU Stop, download |
| IEC 60870-5-104 | 2404 | энергетика (Европа) | команды управления |
| BACnet | 47808 | здания/ОВиК | запись свойств |
| PROFINET | (L2/raw) | Siemens, real-time | изменение конфигурации |

Классические протоколы **не имеют аутентификации**: любой, кто дотянулся до порта,
может отдавать команды. Это и делает их удобной целью и трудной уликой — «кто
именно» приходится устанавливать по сетевым артефактам.

## Modbus: функции, регистры, адресация

Modbus различает четыре области данных, и функция определяет, что читают/пишут:

| Код | Функция | Область |
|---|---|---|
| 1 | Read Coils | дискретные выходы (вкл/выкл) |
| 2 | Read Discrete Inputs | дискретные входы |
| 3 | Read Holding Registers | регистры-уставки |
| 4 | Read Input Registers | регистры-измерения |
| 5 | Write Single Coil | запись выхода |
| 6 | Write Single Register | запись уставки |
| 15 | Write Multiple Coils | массовая запись выходов |
| 16 | Write Multiple Registers | массовая запись уставок |

Чтения (1–4) — нормальный режим опроса; записи (5, 6, 15, 16) меняют физический
процесс. В форензике важны **адреса** записей: `reference_num` указывает, какой
именно регистр тронули. Если это регистр уставки давления или скорости насоса —
последствия могут быть физическими.

```
$ tshark -r ot.pcap -Y 'modbus.func_code>=5' \
    -T fields -e ip.src -e modbus.func_code -e modbus.reference_num | sort | uniq -c
```

## DNP3 и S7comm: что смотреть

DNP3 имеет свою модель объектов и функции прикладного уровня:

- `READ` — чтение;
- `WRITE` — запись;
- `SELECT` / `OPERATE` — двухшаговая команда (выбрать и подтвердить);
- `DIRECT_OPERATE` — немедленная команда;
- `COLD_RESTART` — перезапуск устройства.

Именно `OPERATE`/`DIRECT_OPERATE` — управляющие команды. Их появление из недоверенной
подсети — тревожный сигнал.

S7comm (Siemens) опасен тем, что позволяет **остановить ПЛК** и загрузить новую
программу:

```
$ tshark -r ot.pcap -Y 's7comm' -T fields -e s7comm.param.func -e ip.src | sort | uniq -c
```

Функция `Stop` или `Download` в дампе = попытка изменить логику контроллера.

## Таймлайн атаки на АСУ ТП

Типичная последовательность (её и восстанавливают):

1. **Разведка** — всплеск чтений (func 3/4) с одного адреса, перебор адресов
   регистров (картирование устройства).
2. **Подготовка** — чтение конфигурации, определение уставок.
3. **Воздействие** — записи (5/6/15/16) или `OPERATE`, часто ночью или в момент
   техобслуживания.
4. **Сокрытие** — очистка логов HMI/инженерной станции, подмена времени (NTP).

Сопоставляя всплеск чтений и последующие записи, ты показываешь **намерение**, а не
просто «странный трафик».

## Следы на HMI, инженерной станции и ПЛК

Сетевой дамп — не единственный источник:

- **HMI/SCADA** — журналы оператора (кто и что нажимал), alarm-логи;
- **инженерная станция** — проектные файлы, история загрузок в ПЛК;
- **ПЛК** — журнал диагностики, флаг изменённой программы, контрольная сумма логики;
- **шлюзы/коммутаторы** — MAC-таблица, зеркалирование портов, записи о новых
  устройствах.

Ключ — **сверка**: команда из сети должна соответствовать записи в журнале оператора.
Если запись в сети есть, а в журнале — нет, журнал подчищен.

## Ограничения и осторожность

- **Не сканируй АСУ ТП активно** без согласования: неаккуратный запрос может уронить
  технологический процесс. Работай по копии трафика.
- **Serial/RTU** требует конвертера и другого инструмента (анализ RS-485).
- **Проприетарные расширения** вендоров не всегда парсятся `tshark` — смотри сырые
  байты.
- **Время** на ПЛК часто неверное — синхронизируй по независимым источникам.
- Отсутствие аутентификации означает: доказать авторство команды можно только по
  сетевой топологии и сопутствующим артефактам.

## Modbus детально: адреса и функции

Modbus оперирует четырьмя таблицами данных, и адрес говорит, о чём речь:

| Таблица | Адрес | Доступ | Смысл |
|---|---|---|---|
| Coils | 0xxxx | чтение/запись | дискретные выходы (реле) |
| Discrete Inputs | 1xxxx | только чтение | дискретные входы (датчики) |
| Input Registers | 3xxxx | только чтение | аналоговые входы |
| Holding Registers | 4xxxx | чтение/запись | уставки, параметры |

Функции: `1` Read Coils, `2` Read Discrete Inputs, `3` Read Holding, `4` Read Input,
`5` Write Single Coil, `6` Write Single Register, `15` Write Multiple Coils,
`16` Write Multiple Registers. Чтения (1–4) безопасны, записи (5,6,15,16) меняют
состояние. В дампе ищи именно записи:

```
$ tshark -r ot.pcap -Y 'modbus.func_code in {5 6 15 16}' \
    -T fields -e ip.src -e modbus.reference_num -e modbus.word_cnt | sort | uniq -c | sort -rn
   500  10.10.30.99  100  8
```

## DNP3 и IEC-104

DNP3 прикладной уровень использует объекты (binary input, analog output) и функции
`READ`, `WRITE`, `SELECT`, `OPERATE`, `DIRECT_OPERATE`. Атака часто использует
`DIRECT_OPERATE` — прямая команда без предварительного `SELECT`:

```
$ tshark -r ot.pcap -Y 'dnp3.al.func==5' -T fields -e ip.src -e dnp3.al.func
10.10.30.99  5
```

IEC-104 похож: типы ASDU (например, `C_SC_NA_1` — команда одноточечного управления).
Несвойственная команда `C_*` (command) от неинженерной станции — сильный индикатор.

## Практический разбор CTF

В задачах по OT обычно дан дамп и вопрос «какой хост атаковал». Порядок:

```
$ tshark -r ot.pcap -q -z io,phs                    # какие протоколы вообще есть
$ tshark -r ot.pcap -Y 'modbus' -T fields -e ip.src | sort | uniq -c | sort -rn
$ tshark -r ot.pcap -Y 'modbus.func_code==16' -T fields -e ip.src -e modbus.reference_num
```

Хост, который массово **пишет**, а не читает, и не является инженерной станцией, — и есть
источник. Дальше сопоставляй время записей с моментом аварии по журналу оператора.

## Физические последствия и таймлайн

Кибератака на АСУ ТП — это не «украли данные», а «изменили процесс». Поэтому таймлайн
строят из нескольких слоёв:

- сетевой дамп (команды и их время);
- журнал HMI/SCADA (что видел оператор);
- журнал контроллера (что реально исполнилось);
- журнал датчиков (физический отклик: давление, температура).

Совпадение времени команды из дампа и физического отклонения — прямое доказательство
воздействия.

## Ограничения

- Серийный Modbus RTU внутри TCP-туннеля — нужен разбор полезной нагрузки вручную.
- Проприетарные расширения (S7comm, CIP) — нужны вендорные диссекторы.
- Зашифрованный OPC UA — как TLS, нужны ключи.
- Часто нет полного дампа (только зеркало на коммутаторе) — потерянные пакеты ломают
  реконструкцию сессии.
