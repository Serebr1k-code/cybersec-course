## Вопрос, с которого всё начинается

Программу удалили, Prefetch тоже чист. Остался ли вообще какой-то след того, что этот EXE
существовал? Да — механизм совместимости приложений ведёт список «виденных» исполняемых
файлов. Разберём этот артефакт и, главное, поймём, чего он **не** доказывает.

## Наш пример: ключ AppCompatCache в hive SYSTEM

ShimCache хранится в реестре, в hive **SYSTEM**:

```
HKLM\SYSTEM\CurrentControlSet\Control\Session Manager\AppCompatCache
```

Копия hive лежит на диске как файл `C:\Windows\System32\config\SYSTEM`. Возьмём его:

```
$ file SYSTEM
SYSTEM: MS Windows registry file, NT/2000 or above
```

Это **реестровый hive** — двоичный файл. Значение `AppCompatCache` внутри него содержит
структуру с записями о файлах.

## Что такое ShimCache и зачем он существует

**ShimCache** (он же **AppCompatCache**) — часть механизма совместимости приложений
(Application Compatibility). Когда загрузчик проверяет исполняемый файл на совместимость, он
запоминает запись о нём в кэше, чтобы не проверять повторно. Кэш переживает удаление файла:
строка с путём остаётся в реестре.

Критически важный нюанс: запись означает, что файл **был проверен** (обычно — потому что его
видели в файловой системе или запускали). Формат менялся между версиями Windows, и не во всех
версиях ShimCache хранит флаг «исполнялся». Поэтому по ShimCache нельзя утверждать «файл
запускали» — только «файл существовал и был виден системе».

## Шаг 1: разобрать hive

Парсить реестр вручную тяжело; берём инструмент. На Windows — `AppCompatCacheParser` (Eric
Zimmerman), на Linux — `regripper` или `regipy`:

```
$ regripper -r SYSTEM -p appcompatcache
...
C:\Users\jdoe\Downloads\mimikatz.exe
Last Modified: 2025-05-28 21:10:44
Executed: (unknown)
```

Мы получили путь и время последнего изменения файла — даже если самого файла нет.

## Поля ShimCache и их смысл

| Поле | Смысл | Тонкость |
|------|-------|----------|
| Path | путь к файлу | может быть удалён |
| Last Modified | время изменения файла | из метаданных, не запуск |
| Insertion Flags | как запись попала в кэш | зависит от версии ОС |
| Executed | флаг исполнения | есть не во всех версиях |

## ShimCache против Prefetch: что и когда доказывает

Это ключевое различие, которое любят проверять в задачах и на собеседованиях.

| Вопрос | Prefetch | ShimCache |
|--------|----------|-----------|
| Файл существовал | косвенно | да (путь) |
| Файл запускался | да (счётчик) | не всегда (нет флага) |
| Время запуска | есть | обычно нет |
| Переживает удаление | ограниченно | да (запись остаётся) |

Практический вывод: **ShimCache — про присутствие, Prefetch — про запуск**. В отчёте не
подменяй одно другим.

## Связь с AmCache

ShimCache и AmCache дополняют друг друга: AmCache хранит путь, хеш и время установки/первого
появления, а ShimCache — факт «видимости» файла. Сверив оба, ты получаешь и хеш (для поиска
в VirusTotal), и хронологию. Если файл есть в AmCache с хешем, а в ShimCache — с путём, то
картина «программа была установлена и присутствовала» становится надёжной.

## Ограничения и подводные камни

- **Формат зависит от версии Windows.** На старых системах поля другие; парсер должен
  поддерживать конкретную версию.
- **Не доказывает запуск.** Отсутствие флага `Executed` — норма, а не «не запускали».
- **Кэш ограничен.** Как и любой кэш, ShimCache не бесконечен: старые записи вытесняются.
- **Много путей.** Записи включают системные файлы; фильтруй по интересующему каталогу.
- **Путать с AmCache.** Это разные артефакты в разных hive (SYSTEM vs SOFTWARE).

## Шпаргалка команд

```
# Windows
AppCompatCacheParser.exe -f SYSTEM --csv out

# Linux
regripper -r SYSTEM -p appcompatcache
regipy-dump SYSTEM   # или короткий скрипт на regipy

# Найти конкретный файл
regripper -r SYSTEM -p appcompatcache | grep -i '<имя>'
```

## Что мы теперь знаем

- ShimCache (AppCompatCache) живёт в hive SYSTEM, в ключе `Session Manager`.
- Он хранит пути «виденных» исполняемых файлов, включая удалённые.
- ShimCache — про **присутствие**, а не про факт запуска.
- Формат зависит от версии Windows; нужен поддерживающий парсер.
- В паре с AmCache даёт и хеш, и хронологию.

## Сквозной пример: от пути в ShimCache к хешу в AmCache

Соберём историю целиком. Дано: файла нет, Prefetch пуст, но есть hive SYSTEM. Задача —
доказать присутствие подозрительного файла и по возможности получить его хеш.

Шаг первый — разбираем ShimCache из hive SYSTEM и находим путь
`C:\Users\jdoe\Downloads\mimikatz.exe` с временем последнего изменения. Уже это доказывает,
что файл существовал: каталог `Downloads` и подозрительное имя — сильный сигнал. Шаг второй —
открываем hive `SOFTWARE`, точнее `Amcache.hve`, и ищем тот же путь. В AmCache рядом с путём
лежит SHA-1. Шаг третий — берём хеш и проверяем его в базе ВПО; детект подтверждает
вредоносность. Шаг четвёртый — ищем тот же хеш в локальном списке IOC и в отчётах с других
хостов: возможно, программа запускалась не только здесь.

Итог: один путь из ShimCache вырос в доказательство присутствия вредоносного файла с
подтверждённым хешем и потенциальными связями с другими машинами. Обрати внимание на порядок:
ShimCache дал **зацепку**, AmCache — **идентичность**, threat-intel — **оценку**.

## Разница между «видел», «устанавливал» и «запускал»

Три глагола описывают три разных артефакта, и путать их — типичная ошибка.

- **ShimCache** — «видел»: загрузчик проверял файл на совместимость. Файл существовал.
- **AmCache** — «устанавливал/присутствовал»: программа была на хосте, есть хеш.
- **Prefetch** — «запускал»: процесс стартовал, есть счётчик и время.

В отчёте формулируй вывод строго по источнику: «по данным ShimCache файл присутствовал», «по
данным Prefetch файл запускался». Такая точность не даёт защите развалить вывод на одном
неверном глаголе.

## Полный прогон: связка трёх артефактов

Практический порядок такой. Начни с самого «дешёвого» источника — ShimCache: он быстро даёт
список путей. Отфильтруй интересные (не системные, из пользовательских каталогов). Для
каждого пути поищи запись в AmCache и выпиши хеш. Для подтверждения запуска поищи
соответствующий `.pf` в Prefetch. Если все три совпали, вывод прочный. Если AmCache есть, а
Prefetch нет — возможно, программу не запускали (или Prefetch очищен). Такой прогон занимает
минуты, но даёт трёхуровневое подтверждение вместо одной догадки.

## Что фиксировать в отчёте

Опиши источники (пути к hive), инструменты и их версии, найденные пути, хеши и времена.
Явно разведи «присутствие» и «запуск», укажи, какой артефакт что подтверждает. Если хеш
проверялся во внешней базе, приведи результат проверки и дату — базы меняются, и дата важна
для воспроизводимости вывода.

## Продвинутый разбор: формат, версии и типичные ловушки

ShimCache — один из самых «капризных» артефактов, потому что его формат менялся почти в
каждой крупной версии Windows. В одних версиях запись состоит только из пути и времени, в
других добавляются флаги (например, признак исполнения), в третьих меняется порядок полей.
Поэтому главное правило: **сначала определи версию ОС**, затем выбирай парсер, который её
поддерживает. Если парсер не знает версию, он может «прочитать» мусор и выдать ложные пути —
это хуже, чем честное «формат не поддержан».

Вторая ловушка — **смешение с AmCache**. Пользователи часто ищут «AmCache в hive SYSTEM» или
наоборот; на самом деле ShimCache лежит в SYSTEM, а AmCache — в отдельном hive
`Amcache.hve`. Третья ловушка — интерпретация времени: время в ShimCache относится к
**изменению файла** (из его метаданных), а не к моменту попадания записи в кэш. Не выдавай
его за время запуска.

## Что делать, если ShimCache пуст или повреждён

Бывает, что значение `AppCompatCache` отсутствует или нечитаемо. Это не тупик. Проверь
следующее: возможно, hive снят некорректно (файл залочен) — попробуй копию из теневой копии
тома; возможно, механизм совместимости отключён групповой политикой — тогда записей просто
нет по конфигурации, и это надо оговорить. Резервные источники те же: AmCache, Prefetch,
журналы. И помни: пустой ShimCache при непустом AmCache — это не противоречие, а разные
механизмы. В отчёте опиши оба и не делай вывод об отсутствии файла только по одному
источнику.

## Итоговый вывод по ShimCache

ShimCache — это артефакт **присутствия**, и его главная ценность в том, что он переживает
удаление файла. Он не заменяет Prefetch и не доказывает запуск, но даёт то, чего у Prefetch
нет: список путей, включая давно исчезнувшие. Используй его как отправную точку: найди
интересные пути, отфильтруй системные, а затем ищи идентичность (хеш) в AmCache и запуск в
Prefetch. В отчёте формулируй строго: «по данным ShimCache файл присутствовал на хосте».
Соблюдая эту дисциплину, ты не позволишь себе превратить «видел» в «запускал» и не дашь
защите оспорить вывод на терминологии. Именно точность формулировок отличает корректный
форензик-вывод от поспешного.

## Куда дальше

ShimCache дал путь и присутствие. Дальше возьмём **AmCache** — он добавит хеши и время
установки, что позволит искать файл в базах ВПО. А пока главное запомни: **ShimCache — это
«что видел загрузчик», а не «что запускали»**.

## Где пригодится

- **CTF Forensics:** доказать присутствие удалённого файла.
- **DFIR:** связать путь с хешем через AmCache.
- **Threat Hunting:** поиск подозрительных путей (Downloads, Temp).
- **Работа:** форензика конечных точек.
