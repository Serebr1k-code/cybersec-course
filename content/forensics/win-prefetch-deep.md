## Вопрос, с которого всё начинается

Подозревается, что на машине запускали утилиту, которой уже нет на диске. Журналы событий
молчат (аудит запуска процессов не включён). Что докажет сам факт запуска и, что важнее,
**откуда** её запускали — с локального диска или с флешки? Ответ даёт Prefetch.

## Наш пример: каталог Prefetch

```
C:\Windows\Prefetch\
```

```
$ ls
CMD.EXE-4A1B2C3D.pf
NOTEPAD.EXE-9F8E7D6C.pf
PSEXEC.EXE-1A2B3C4D.pf
```

Имя файла — `<ИМЯ_ПРОГРАММЫ>-<хеш>.pf`. Хеш зависит от полного пути к программе, поэтому по
нему можно отличить один и тот же EXE, запущенный из разных каталогов.

## Что такое Prefetch и зачем он нужен

**Prefetch** — это кэш, который Windows ведёт для **ускорения запуска** программ. При первом
запуске ОС запоминает, какие файлы и библиотеки читает процесс, и в следующий раз читает их
заранее. Побочный эффект: чтобы вести кэш, система сохраняет **метаданные** о запуске —
имя, время, счётчик, список томов. Именно эти метаданные и расследуют.

Важно понимать назначение: Prefetch существует ради производительности, а не аудита. Поэтому
он включён не всегда и очищается не всегда — обе крайности влияют на расследование.

## Шаг 1: опознать файл

```
$ file CMD.EXE-4A1B2C3D.pf
CMD.EXE-4A1B2C3D.pf: MS Windows Prefetch file, version 30
```

Версия (`version 30` для Windows 10/11) важна: формат менялся, и старый парсер не прочитает
новый файл. Начиная с Windows 10 файлы Prefetch **сжаты** (XPRESS Huffman), поэтому «в
лоб» через `strings` видны далеко не все строки.

## Шаг 2: разобрать файл инструментом

Правильный путь — парсер, знающий формат. На Windows это **PECmd** (Eric Zimmerman), на
Linux — `pecmd` из пакета libyal или `prefetch-parser`:

```
$ pecmd CMD.EXE-4A1B2C3D.pf
...
[CMD.EXE]
Run count: 7
Last run: 2025-05-30 14:02:11
First run: 2025-05-12 08:41:03
Volume: \VOLUME{01d2...}
Files referenced: ...
```

Мы получили счётчик запусков и две временные метки — этого часто достаточно для вывода.

## Поля Prefetch и что они значат

| Поле | Смысл | Как использовать |
|------|-------|------------------|
| `Run count` | сколько раз запускали | частота использования |
| `Last run` | время последнего запуска | вписать в таймлайн |
| `First run` | время первого запуска | «когда впервые появилась» |
| Volume info | том(ы) запуска и серийники | доказать внешний носитель |
| Files referenced | файлы, которые читал процесс | понять назначение/данные |

## Серийные номера томов: доказательство запуска с флешки

Это самое мощное свойство Prefetch для расследований. Файл хранит **серийные номера томов**,
с которых запускалась программа. Серийник локального `C:` ты найдёшь в реестре
(`HKLM\SYSTEM\MountedDevices`); если в Prefetch есть **другой** серийник — программа
запускалась с иного тома, например USB-накопителя.

Порядок доказательства прост. Сначала выписываем серийник из Prefetch. Затем ищем его в
`MountedDevices` и в журнале `USBSTOR` (`HKLM\SYSTEM\CurrentControlSet\Enum\USBSTOR`), где
хранятся серийные номера подключённых USB-устройств. Совпадение серийника даёт связку
«программа запускалась с этого конкретного носителя» — сильное доказательство.

## Связь с другими артефактами

Prefetch редко используется в одиночку. Его сверяют с:

- **ShimCache/AmCache** — подтвердить присутствие файла и хеш;
- **UserAssist** — запускал ли программу пользователь через Explorer;
- **JumpLists** — открывал ли он связанные документы;
- **SRUM** — была ли у программы сетевая активность.

Сходимость нескольких источников превращает «в Prefetch есть запись» в надёжный вывод.

## Ограничения Prefetch

- **Не на всех системах.** На серверных редакциях Prefetch отключён по умолчанию; на SSD
  настройка может быть иной.
- **Очистка.** Утилиты «оптимизации» и антифорензика удаляют `Prefetch`; тогда факт запуска
  ищи в других артефактах.
- **Только 1024 записи.** Старые записи вытесняются — отсутствие программы в Prefetch не
  значит, что её не запускали.
- **Сжатие.** На Windows 10+ файлы сжаты; `strings` без распаковки малоинформативен.

## Частые ошибки и подводные камни

- **Читать версию не глядя.** Файл версии 30 и версии 17 парсятся по-разному.
- **Путать First run и время создания файла.** Это разные вещи; времена в Prefetch — метки
  запуска, а не создания `.pf`.
- **Игнорировать серийники.** Без них не отличить запуск с диска от запуска с флешки.
- **Считать отсутствие записи доказательством.** Prefetch ограничен по числу файлов и может
  быть очищен.
- **Забыть про SuperFetch/SysMain.** Служба `SysMain` (бывший SuperFetch) ведёт Prefetch;
  если её отключили, записей не будет.

## Шпаргалка команд

```
# Опознать версию
file *.pf

# Разбор (Windows)
PECmd.exe -d C:\Windows\Prefetch --csv out

# Разбор (Linux)
pecmd CMD.EXE-4A1B2C3D.pf

# Серийники томов
# Prefetch -> серийник; реестр -> MountedDevices; USBSTOR -> серийники USB
```

## Что мы теперь знаем

- Prefetch хранится в `C:\Windows\Prefetch` как `<имя>-<хеш>.pf`.
- Он даёт счётчик запусков, первое/последнее время и список томов.
- Серийные номера томов позволяют доказать запуск с внешнего носителя.
- На Windows 10+ файлы сжаты; нужен парсер, а не `strings`.
- Prefetch не вечен: записей ограниченное число, и его можно очистить.

## Сквозной пример: доказательство запуска утилиты с флешки

Разберём историю целиком. Задача: доказать, что на хосте запускали `psexec.exe` и делали это
с внешнего USB-накопителя.

Шаг первый — находим файл Prefetch и читаем метаданные. Имя `PSEXEC.EXE-1A2B3C4D.pf` уже
говорит о программе, а внутри лежат счётчик и серийник тома. Выписываем серийник, скажем
`0x7a1c9e42`. Шаг второй — ищем этот серийник в реестре. В `HKLM\SYSTEM\MountedDevices`
серийники сопоставлены буквам дисков; смотрим, какой букве соответствует наш номер. Если он
привязан к съёмному устройству — половина дела сделана. Шаг третий — открываем
`HKLM\SYSTEM\CurrentControlSet\Enum\USBSTOR`, где хранятся серийные номера подключённых
USB-устройств и их имена. Находим совпадение — значит, носитель действительно подключался.
Шаг четвёртый — сверяем с `Setupapi.dev.log`, где фиксируется время подключения устройства.

В итоге получаем связную цепочку: программа запускалась, запускалась с конкретного
USB-накопителя, и носитель подключался к машине. Это уже не «подозрение», а обоснованный
вывод, подкреплённый несколькими независимыми источниками. Именно такой ход — **от одного
артефакта к связке** — отличает профессиональный разбор от «нашёл строку».

## Практика: читаем Prefetch вручную и парсером

Полезно один раз разобрать `.pf` и вручную, чтобы понимать, откуда берутся данные. Файл
начинается с сигнатуры и версии; дальше — заголовок с размерами секций и таблица метаданных.
В секции с информацией о томах лежат серийные номера, в секции со строками — имена файлов,
к которым обращался процесс. На Windows 10+ содержимое строк сжато алгоритмом XPRESS
Huffman, поэтому «руками» через `strings` ты увидишь лишь часть.

Парсер делает всё это автоматически. Разница между ручным и автоматическим разбором в том,
что парсер знает смещения полей для каждой версии формата и сам распаковывает строки.
Практический совет: используй парсер для скорости, но понимай структуру, чтобы замечать,
когда результат выглядит подозрительно (например, пустой список файлов при ненулевом счётчике
запусков — признак повреждения или частичной перезаписи файла).

## Полный прогон по всем источникам

Хороший разбор запуска программы — это всегда несколько источников. Собери их в один
порядок. Сначала Prefetch: факт запуска, счётчик, время, тома. Затем ShimCache: присутствие
файла и его путь. Затем AmCache: хеш и время изменения. Затем SRUM: была ли у программы
сетевая активность и какая. Затем журналы событий: входы пользователя, создание процессов
(если аудит включён). Каждый источник отвечает на свой вопрос, и вместе они дают полную
картину: «кто, когда, откуда, с какими данными и с какой сетевой активностью». Если один
источник противоречит другому, не прячь противоречие — опиши его, это тоже часть вывода.

## Что фиксировать в отчёте

В отчёте укажи: путь к каталогу Prefetch, конкретный `.pf`-файл, версию формата, счётчик
запусков, время первого и последнего запуска, серийный номер тома и результат его
сопоставления с `MountedDevices`/`USBSTOR`. Отдельно оговори, что времена Prefetch — это
метки запуска, а не создания файла. Такая детализация делает вывод проверяемым: другой
аналитик повторит команды и получит то же самое.

## Продвинутый разбор: счётчики, устройства и контекст запуска

За пределами базовых полей Prefetch хранит ещё несколько полезных вещей. Во-первых, для
некоторых версий есть **список устройств и файлов**, которые читал процесс: по нему можно
понять, с какими данными работала программа (конфиги, DLL, документы). Во-вторых, есть
**временные метки файла `.pf`** (создание/изменение) — их полезно сверять с временами
запуска: расхождение бывает признаком того, что файл копировали или подделывали. В-третьих,
для программ с одинаковым именем, но разными путями, разные хеши в имени файла позволяют
различить запуски из `System32` и из пользовательского каталога — это прямой способ поймать
маскировку под системный процесс.

Отдельно стоит сказать про **только чтение**: Prefetch не содержит аргументов командной
строки, поэтому он не скажет, с какими параметрами запускали программу. Для аргументов нужны
журналы создания процессов (если аудит включён) или артефакты вроде PowerShell-логов. Prefetch
отвечает на «что и когда», но не на «с какими ключами».

## Как выявлять очистку Prefetch и что делать

Антифорензика часто бьёт именно по Prefetch: утилиты «чистки» удаляют `.pf`-файлы, чтобы
скрыть запуски. Признаки очистки: каталог `Prefetch` пуст или содержит только самые свежие
системные файлы; в реестре есть следы запуска чистильщика; времена создания оставшихся
файлов «сбиты» в один момент. Если видишь такую картину, не делай вывод «ничего не
запускалось» — переходи к резервным источникам: ShimCache, AmCache, SRUM, журналы. Часто
именно они сохраняют след, который чистильщик не тронул. И зафиксируй сам факт очистки: это
само по себе улика намеренного сокрытия следов.

## Куда дальше

Prefetch доказывает **запуск**. Дальше возьмём **ShimCache/AppCompatCache** — артефакт,
который отвечает на вопрос «какие EXE загрузчик вообще видел», включая уже удалённые файлы.
А пока главное запомни: **Prefetch — это счётчик запусков плюс серийники томов**.

## Где пригодится

- **CTF Forensics:** задачи «докажи запуск и откуда».
- **DFIR:** установление факта выполнения вредоносной утилиты.
- **Threat Hunting:** поиск запусков подозрительных программ.
- **Работа:** форензика конечных точек, USB-расследования.
