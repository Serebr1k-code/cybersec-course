## Вопрос, с которого всё начинается

Ты открываешь образец — а там мешанина байт и почти нет читаемых строк. Это
**обфускация**: код спрятан, чтобы затруднить анализ. Но её можно снять. Разберём
уровни.

## Наш пример: упакованный образец

## Шаг 1: упаковка (packing)

Упаковщик сжимает/шифрует настоящий код и добавляет распаковщик:

```
$ strings packed.exe | grep -i upx
UPX0
UPX1
```

`UPX0`/`UPX1` — секции UPX. Распаковать:

```
$ upx -d packed.exe -o unpacked.exe
```

После распаковки появляются импорты и строки.

## Шаг 2: криптор

Сложнее UPX — коммерческие **крипторы**: код расшифровывается в памяти, на диске —
мусор. Признаки: энтропия близка к максимуму, мало секций, странная точка входа.

```
$ python3 -c "import math,collections;d=open('sample.bin','rb').read();c=collections.Counter(d);e=-sum(v/len(d)*math.log2(v/len(d)) for v in c.values());print(round(e,2))"
7.98
```

Энтропия `7.98` (максимум 8.0) = данные зашифрованы/сжаты.

## Шаг 3: шифрование строк

Даже распакованный код может шифровать строки:

```c
char *s = decode(blob, key);
```

Строки расшифровываются в рантайме. Приём: эмулировать функцию `decode` для всех
блобов и получить строки (это делают эмуляцией или скриптом IDA/Ghidra).

## Шаг 4: обфускация потока управления

- **flattening** — код превращён в switch-диспетчер;
- **junk code** — мусорные инструкции;
- **opaque predicates** — условия, всегда истинные/ложные.

Деобфускация — полуавтоматическая: символическое исполнение, скрипты.

## Шаг 5: как подходить

1. Определи уровень (упаковка/криптор/строки).
2. Сними упаковку (`upx -d`) или распакуй в памяти.
3. Расшифруй строки эмуляцией.
4. Для flattening — используй готовые деобфускаторы.

## Что мы теперь знаем

- Упаковка (UPX) сжимает код; снимается `upx -d`.
- Крипторы расшифровывают в памяти; выдаёт высокая энтропия.
- Строки могут шифроваться и декодироваться в рантайме.
- Обфускация потока — flattening/junk/opaque.
- Подход: слой за слоем.

## Если не сработало

- Своя упаковка? Распаковывай дампом памяти после запуска.
- Много слоёв? Декодируй последовательно.
- Не хватает времени? Сфокусируйся на IOC, а не на полной логике.

## Энтропия как первый индикатор упаковки

Упакованный (сжатый/зашифрованный) код почти не содержит повторяющихся байтов, поэтому его
**энтропия Шеннона** близка к 8 бит на байт. Секции обычного кода дают 5.5-6.5. Считаем по
секциям PE-файла:

```
$ pip install pefile
$ python3 - <<'PY'
import pefile, math, collections
pe = pefile.PE('sample.exe')
for s in pe.sections:
    d = s.get_data()
    if not d: continue
    c = collections.Counter(d); n = len(d)
    h = -sum((v/n)*math.log2(v/n) for v in c.values())
    print(f"{s.Name.rstrip(chr(0)):8} size={n:8} entropy={h:.3f}")
PY
.text    size=  51200 entropy=7.982
.rdata   size=  10240 entropy=7.941
.upx0    size=  61440 entropy=7.999
```

Секция с именем `.upx0` и энтропией 7.999 — это UPX, упаковщик с открытым исходником.
Высокая энтропия `.text` без узнаваемого имени секции — признак коммерческого криптора.

## Различаем упаковщик и криптор

Это разные вещи, и путать их — частая ошибка:

- **Упаковщик (packer)** сжимает код, чтобы уменьшить размер и замедлить анализ. Он
  детерминирован и обратим: UPX, MPRESS, ASPack.
- **Криптор (crypter)** шифрует код и добавляет дешифратор, цель — уйти от антивируса.
  Часто продаётся «по подписке» и генерирует уникальный образец для каждой сборки.

Практическое следствие: упаковщик снимается автоматически, криптор — почти всегда нет.
Если UPX легко распаковать:

```
$ upx -d sample_upx.exe -o sample_unpacked.exe
$ file sample_unpacked.exe
sample_unpacked.exe: PE32 executable (GUI) Intel 80386, for MS Windows
```

то криптор с уникальным дешифратором требует ручной трассировки до момента, когда код
распакуется в памяти, и дампа уже распакованного образа.

## Распаковка из памяти

Ключевой приём: малварь **должна** себя расшифровать, чтобы работать, — значит, в какой-то
момент в памяти лежит открытый код. Дамп памяти в этот момент даёт распакованный образ.

Инструменты и порядок:

```
$ pe-sieve /pid 4321 /dump /dir out/      # дамп подозрительных модулей из процесса
$ python3 -c "import pefile;pefile.PE('out/4321.exe')"  # проверка дампа
```

`pe-sieve` умеет находить в процессе секции, которые отличаются от файла на диске (признак
самомодифицирующегося кода), и выгружать их. Альтернатива — эмуляция: `Unicorn`, `Speakeasy`,
`Qiling` запускают образец в изолированной среде и логируют вызовы API, не заражая хост.

## Шифрование строк и API-хеширование

Даже распакованный образец часто нечитаем: строки зашифрованы. Типовые схемы:

| Схема | Признак | Как вскрыть |
|---|---|---|
| XOR с одним байтом | высокая частота одного байта в блобе | перебрать 256 ключей, искать ASCII |
| XOR с многобайтным ключом | повтор ключа | найти период, статистика |
| RC4/AES | рядом вызов крипто-API | поставить брейк на выходе функции |
| Stack strings | `mov [esp+N], 'te'` по кусочкам | скрипт сборки из `mov`-ов |
| API hashing | нет строк имён API, есть хеши | сопоставить с базой хешей (CRC32/DJB2) |

Скрипт для однобайтового XOR:

```
$ python3 - <<'PY'
blob = bytes.fromhex('...')      # блоб из .rdata
for k in range(256):
    dec = bytes(b ^ k for b in blob)
    if b'http' in dec or b'.exe' in dec:
        print(hex(k), dec[:80])
PY
```

API-хеширование (ROR13, CRC32) узнаётся по циклу, который хеширует имена из `kernel32.dll`
и сравнивает с константами. Инструмент `floss` (FireEye) умеет автоматически извлекать
скрытые строки, включая декодированные.

## Обфускация потока управления

Чтобы сломать дизассемблер и граф вызовов, применяют:

- **мусорный код** — недостижимые инструкции между полезными;
- **непрозрачные предикаты** — условия, всегда истинные, но неочевидные для анализатора;
- **flattening** — цикл-диспетчер со switch, который «выравнивает» функцию в один блок;
- **виртуализация** — код превращают в байткод для собственной VM (VMProtect, Themida).

Признак flattening — маленькая функция с огромным `switch` и переменной-состоянием,
которая обновляется в каждой ветви. Восстанавливать вручную тяжело; помогают плагины к
IDA (D810) и символьное исполнение (angr) для отсечения недостижимых ветвей.

## Таблица: что говорит каждый признак

| Наблюдение | Вероятный вывод |
|---|---|
| энтропия .text > 7.5 | упаковано/зашифровано |
| одна секция с записью и исполнением (RWX) | самомодификация, криптор |
| имя секции UPX/MPRESS/.aspack | известный упаковщик |
| почти нет строк | строки зашифрованы |
| импорты только LoadLibrary/GetProcAddress | динамический резолвинг API |
| подозрительно мало функций при большом размере | обфускация потока |

## Ограничения и анти-анализ

Ни один признак не является доказательством сам по себе: легитимные установщики (InnoSetup,
NSIS) тоже упакованы и имеют высокую энтропию. Обратный случай — «ручной» криптор без
упаковки, который сохраняет нормальную энтропию, но расшифровывает код по частям. Поэтому
вывод строится на **совокупности**: энтропия + импорты + поведение в песочнице. И помни про
анти-анализ: проверки на отладчик (`IsDebuggerPresent`, timing), определение песочницы (мало
ядер, нет пользовательских данных), отложенный запуск — всё это направлено против твоих же
инструментов.

## Если сработало: фиксируем результат

После распаковки посчитай хеш открытого образа (SHA-256) — именно он идёт в отчёт и в
тиакорреляцию, потому что хеш упакованного файла у каждого образца уникален, а хеш
распакованного ядра совпадает у всей кампании. Это ключ к связыванию сотен образцов в
одно семейство.

## Динамический анализ: поведение важнее формы

Статический разбор упакованного образца быстро упирается в стену. Тогда переключаются на
**динамику** — запускают образец в контролируемой среде и наблюдают. Порядок:

1. изолированная ВМ без доступа к реальной сети, с фейковым интернетом (INetSim);
2. мониторинг файлов (`procmon`), реестра, процессов и сети (`tcpdump`, `Wireshark`);
3. логирование API через хуки (`Frida`, `API Monitor`).

Что ищем в первую очередь: **сетевые индикаторы** (домены, IP), точки персистентности
(запуск, службы, задачи), файлы, которые образец создаёт. Даже если код зашифрован, его
сетевое поведение остаётся видимым.

```
$ tcpdump -i eth0 -w run.pcap &   # в изолированной сети
$ ./sample.exe
$ tshark -r run.pcap -Y 'dns' -T fields -e dns.qry.name | sort -u
cdn-update.example.net
```

## Песочницы и их слепые зоны

Автоматические песочницы (Cuckoo, CAPE, Joe Sandbox) дают быстрый отчёт, но малварь умеет
их распознавать. Типовые проверки: количество ядер и объём RAM, наличие мышиных движений,
свежесть установки, имена пользователей (`sandbox`, `malware`), MAC-адреса производителей
виртуализации. Обход — «усыпить» проверку: запустить на «живой» ВМ, дать ей реальное время
работы, эмулировать активность пользователя.

Если отчёт песочницы пуст — это не значит «безопасно». Часто это значит «образец понял, что
его поймали».

## Связывание образцов в семейство

Обфускация уникальна для каждой сборки, но **ядро** повторяется. Сравнивают по:

- строкам после расшифровки;
- последовательностям вызовов API (behavior);
- конфигурации C2 (формат, шифрование);
- коду функций, не тронутых обфускатором.

Совпадение распакованного ядра — сильнее, чем совпадение упакованных файлов. Именно поэтому
дамп памяти и логирование API ценнее, чем сигнатура по байтам.

## Если сработало: что писать в отчёт

Для обфусцированного образца отчёт должен содержать: тип обфускации (упаковщик/криптор),
метод снятия (UPX, дамп из памяти, эмуляция), хеши исходного и распакованного файлов, и —
главное — извлечённые индикаторы (C2, строки, ключи реестра). Форма без поведения
бесполезна для защиты.

## Негативный результат

Если ни статика, ни динамика не дали индикаторов, зафиксируй это как есть и укажи, какие
методы применялись. Возможно, образец требует конкретного окружения (домена, времени,
файла-маркера) и в песочнице просто не активировался. Это тоже вывод: он направляет
следующий шаг, а не закрывает расследование.
