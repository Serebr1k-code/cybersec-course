## Вопрос, с которого всё начинается

Вся API-активность идёт через **шлюз** (Kong, nginx, AWS API Gateway). Его логи —
полная карта запросов. Разберём, как их читать.

## Наш пример: API-шлюз

## Шаг 1: что логируется

Шлюз пишет: время, клиент, метод, путь, статус, латентность, upstream.

```
$ tail -3 /var/log/kong/access.log
... "GET /api/v1/users" 200 ...
... "POST /api/v1/admin" 403 ...
```

## Шаг 2: агрегация

```
$ awk '{print $6, $7}' access.log | sort | uniq -c | sort -rn | head
  500 /api/v1/users
  120 /api/v1/admin
```

Всплеск обращений к `admin` с незнакомого клиента — аномалия.

## Шаг 3: подозрительные паттерны

- обход авторизации (401/403 пачками);
- доступ к несуществующим путям (сканирование);
- необычные методы (PUT/DELETE);
- большие тела запросов (эксфильтрация).

```
$ grep -E ' (401|403) ' access.log | awk '{print $1}' | sort | uniq -c | sort -rn | head
```

## Шаг 4: связь с бэкендом

Шлюз логирует **upstream** — какой сервис обработан:

```
... "upstream_status": "200", "service": "user-service"
```

Так понимаешь, какой бэкенд атаковали.

## Шаг 5: что искать

- клиенты с аномальной активностью;
- попытки обхода авторизации;
- сканирование путей;
- изменения конфигурации шлюза;
- запросы к чувствительным эндпоинтам.

## Что мы теперь знаем

- Шлюз логирует все API-запросы.
- Агрегация выявляет аномалии.
- Паттерны: 401/403, несуществующие пути, редкие методы.
- Upstream указывает сервис.
- Ищем обход авторизации и сканирование.

## Если не сработало

- Логи не включены? Проверь конфиг шлюза.
- Нужен контекст? Смотри логи бэкенда.
- Нужны тела? Включи debug-логирование.

## Что такое API-шлюз и зачем его логи

**API-шлюз** — это прослойка, через которую проходит весь трафик к
микросервисам. Примеры: Kong, nginx как reverse proxy, AWS API Gateway,
Apigee. Шлюз:

- маршрутизирует запросы к нужному сервису (**upstream**);
- проверяет аутентификацию (ключи, JWT, OAuth);
- ограничивает частоту (rate limit);
- **логирует** каждый запрос.

Для форензики это золото: одно место, где видно все обращения к API — и
успешные, и отклонённые. В отличие от логов отдельных сервисов, шлюз видит
картину целиком.

## Поля лога и что из них читается

Типичная строка доступа Kong/nginx содержит:

```
203.0.113.5 - - [14/Jan/2026:03:28:11 +0000] "POST /api/v1/admin HTTP/1.1" 403 512 "-" "curl/7.81.0" 0.012 upstream=admin-service
```

Разберём по частям:

- `203.0.113.5` — клиент (может быть прокси/CDN);
- `POST /api/v1/admin` — метод и путь;
- `403` — статус (отказано);
- `512` — размер ответа;
- `curl/7.81.0` — User-Agent;
- `0.012` — латентность;
- `upstream=admin-service` — какой бэкенд обрабатывал.

Каждое поле — зацепка: клиент, цель, результат, инструмент атакующего.

## Работа на примере: находим аномалию агрегацией

Сырой лог огромен. Начинаем с агрегации по путям:

```
$ awk '{print $7}' access.log | sort | uniq -c | sort -rn | head
   5000 /api/v1/users
    120 /api/v1/admin
     80 /api/v1/internal/debug
```

Пять тысяч запросов к `users` — норма. А вот `/api/v1/admin` и особенно
`/api/v1/internal/debug` должны привлечь внимание: это редкие,
привилегированные эндпоинты. Дальше смотрим, кто их вызывал:

```
$ grep '/api/v1/internal/debug' access.log | awk '{print $1}' | sort | uniq -c | sort -rn | head
     80 198.51.100.7
```

Один клиент, 80 запросов к внутреннему отладочному эндпоинту — явная
аномалия. Так агрегация превращает «море» логов в конкретную цель.

## Признаки атак в логах шлюза

- **Перебор аутентификации** — пачки `401`/`403` с одного клиента:

```
$ grep -E ' (401|403) ' access.log | awk '{print $1}' | sort | uniq -c | sort -rn | head
   340 198.51.100.7
```

- **Сканирование путей** — много `404` по разным путям от одного клиента
  (перебор эндпоинтов).
- **Необычные методы** — `PUT`/`DELETE`/`PATCH` там, где обычно только `GET`.
- **Инъекции в URL** — кавычки, `../`, `%00`, `union select` в пути или
  query.
- **Большие тела запросов** — потенциальная эксфильтрация или загрузка.

## Работа на примере: восстанавливаем атаку по времени

Видим пачку `403` на `/api/v1/admin`. Берём интервал и смотрим подробно:

```
$ grep '14/Jan/2026:03:2' access.log | grep admin | head
203.0.113.5 - - [14/Jan/2026:03:28:11 +0000] "POST /api/v1/admin HTTP/1.1" 403 512 "-" "curl/7.81.0"
203.0.113.5 - - [14/Jan/2026:03:28:11 +0000] "POST /api/v1/admin HTTP/1.1" 200 2048 "-" "curl/7.81.0"
```

Ключевое: сначала `403`, потом `200`. Значит, на второй попытке аутентификация
прошла — либо подобран ключ, либо утёк токен. Теперь ищем, что было после:

```
$ grep '203.0.113.5' access.log | tail -5
```

Это и есть цепочка: подбор → успех → действие. Шлюз дал нам её целиком,
без захода на бэкенд.

## Связь с бэкендом

Поле `upstream`/`service` говорит, какой микросервис обработан. Это позволяет:

- понять, **что именно** затронуто (например, платёжный сервис, а не
  каталог);
- сузить поиск в логах бэкенда до нужного сервиса;
- увидеть ошибки маршрутизации как признак изменения конфигурации шлюза.

Если после инцидента кто-то менял маршруты (route) или плагины (plugin),
это видно в логах администрирования шлюза — отдельный источник.

## Ограничения и что делать

- **Логи не включены** — по умолчанию тело и заголовки часто не пишутся;
  проверь конфиг (`log_level`, `custom_log_format`).
- **PII/секреты в логах** — шлюз может писать токены и тела; обращайся с
  логами как с чувствительными данными.
- **Клиент за прокси** — реальный IP ищи в `X-Forwarded-For`/`CF-Connecting-IP`.
- **Ротация** — старые логи в `.gz`; не забудь распаковать и их.

## Справочная таблица «статус → смысл»

| Код | Что значит в контексте атаки |
| --- | --- |
| 200 | успех (в т.ч. после подбора) |
| 401 | не аутентифицирован (перебор ключей) |
| 403 | аутентифицирован, но нет прав (обход авторизации) |
| 404 | путь не существует (сканирование) |
| 429 | сработал rate limit (брутфорс) |
| 500 | ошибка бэкенда (инъекция/поломка) |

## Если сработало / если нет

- **Нашёл пачку 401/403** — проверь, был ли следом 200; это точка взлома.
- **Видишь только IP прокси** — ищи реальный IP в прокси-заголовках.
- **Логи пустые** — вероятно, выключено логирование тел; задокументируй
  пробел и опирайся на логи бэкенда.
- **Подозрительных запросов нет** — возможно, атака шла напрямую к бэкенду
  в обход шлюза; проверь доступность сервиса извне.

## Rate limit и его следы

Шлюзы ограничивают частоту запросов, чтобы защититься от брутфорса и
перегрузки. Когда лимит срабатывает, клиент получает `429 Too Many Requests`.
В форензике это ценный сигнал: **сам факт 429 означает, что кто-то долбил
эндпоинт чаще нормы**. Смотрим, кто и куда:

```
$ grep ' 429 ' access.log | awk '{print $1, $7}' | sort | uniq -c | sort -rn | head
   512 198.51.100.7 /api/v1/login
```

Пятьсот `429` на `login` с одного адреса — это подбор пароля, который
защита частично отбила. Полезно проверить, были ли среди этих запросов
успешные `200` — если да, защита не спасла.

## Ошибки JWT и OAuth в логах

Если шлюз проверяет токены, ошибки аутентификации попадают в лог:

- `invalid signature` — подделка или истёкший ключ;
- `expired token` — использование старого токена;
- `invalid audience/issuer` — токен от другого сервиса (попытка подмены).

```
$ grep -iE 'invalid|expired' gateway.log | tail
14/Jan 03:28:11 POST /api/v1/pay 401 invalid signature
```

Всплеск `invalid signature` от одного клиента — признак попытки подобрать
секрет подписи или перебора украденных токенов.

## Разные шлюзы — разные форматы

Формат лога зависит от продукта, но поля похожи:

| Продукт | Особенность лога |
| --- | --- |
| nginx | combined log + `$upstream_addr`, `$request_time` |
| Kong | JSON-логи плагина `http-log`, поля `service`, `route` |
| AWS API Gateway | CloudWatch/access-логи, поля `requestId`, `integrationLatency` |
| Apigee | Message logging policy, гибкие поля |

При расследовании сначала определи продукт, затем читай его формат, а не
наоборот. Универсальные поля (клиент, метод, путь, статус, время) есть
везде.

## GraphQL и нестандартные тела

С GraphQL через шлюз проходит один эндпоинт (`/graphql`), а операции
различаются телом. Тогда анализ по пути бесполезен — смотри **тело** и
поле `operationName`. Шлюзы с включённым логированием тел позволяют
восстановить конкретные запросы:

```
{"operationName":"AdminQuery","variables":{"id":"1"}}
```

Так «один и тот же путь» раскрывается в разные операции.

## Практический чек-лист

1. Определить продукт шлюза и формат лога.
2. Снять реальный IP из прокси-заголовков.
3. Агрегировать по путям, статусам, клиентам.
4. Найти пачки 401/403/429 и связать с последующими 200.
5. Сопоставить время с изменениями конфигурации шлюза.
6. Проверить тела запросов (если логируются) на инъекции.
7. Зафиксировать цепочку «подбор → успех → действие».

## Разбор инцидента по логам шлюза: полный пример

Соберём всё в один сценарий. Есть лог nginx-шлюза. Начинаем с аномалии:
один клиент резко активизировался.

```
$ awk '{print $1}' access.log | sort | uniq -c | sort -rn | head -3
  9821 203.0.113.5
   410 198.51.100.7
    88 10.0.0.12
```

Клиент `203.0.113.5` — явный выброс. Смотрим его активность по времени и
путям:

```
$ grep '^203.0.113.5 ' access.log | awk '{print $7}' | sort | uniq -c | sort -rn | head
  4100 /api/v1/users
   980 /api/v1/users/1
   740 /api/v1/admin
```

Массовые обращения к `/api/v1/users` и перебор `/api/v1/users/1` — это
**IDOR-перебор** (перебор идентификаторов). А запросы к `/admin` — попытка
эскалации. Проверяем результат:

```
$ grep '^203.0.113.5 ' access.log | grep admin | tail -3
... "POST /api/v1/admin HTTP/1.1" 403 ...
... "POST /api/v1/admin HTTP/1.1" 200 ...
```

`403 → 200` — момент компромисса. Фиксируем время и клиента, дальше —
что делал после. Так один лог даёт полную цепочку атаки.
