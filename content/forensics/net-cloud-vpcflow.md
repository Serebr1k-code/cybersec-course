## Вопрос, с которого всё начинается

В облаке нельзя поставить span-порт и снять pcap. Зато облако само пишет **flow logs** —
журнал метаданных о каждом соединении. Это не содержимое, но для расследования часто
достаточно: кто, куда, когда, сколько. Разберём.

## Наш пример: VPC Flow Logs

## Шаг 1: что в записи

Стандартная запись AWS VPC Flow Log:

```
2 123456789010 eni-abc123 10.0.1.5 203.0.113.5 54322 443 6 20 4000 1705000000 1705000060 ACCEPT OK
```

Поля: версия, аккаунт, интерфейс, **srcaddr**, **dstaddr**, **srcport**, **dstport**,
протокол, пакеты, байты, начало, конец, действие, статус.

## Шаг 2: фильтруем по цели

```
$ grep '203.0.113.5' flow.log | awk '{print $4, $5, $7, $8, $11, $12}'
10.0.1.5 203.0.113.5 54322 443 4000 1705000060
```

Видно исходящее соединение с инстанса на внешний адрес. Это уже карта активности.

## Шаг 3: ищем аномалии

- **отказы** (`REJECT`) — попытки сканирования;
- **большой объём** исходящих байт — эксфильтрация;
- **нестандартные порты** — C2;
- **соединения к редким адресам**.

```
$ awk '$13=="REJECT"{print $4, $5, $8}' flow.log | sort | uniq -c | sort -rn | head
```

## Шаг 4: другие облака

- **Azure NSG Flow Logs** — аналогично, JSON-формат;
- **GCP VPC Flow Logs** — в Cloud Logging;
- **CloudTrail / Activity Log** — уже не сеть, а API-действия (тоже важно).

Сопоставляя flow logs и API-логи, восстанавливаешь полную картину: что делал
взломанный инстанс.

## Шаг 5: ограничения

- **нет содержимого** — только метаданные;
- **агрегация** — байты за интервал, не по пакетам;
- **задержка** — записи появляются с лагом;
- **выборка** — можно включить sampling и потерять часть.

Поэтому flow logs дополняют, а не заменяют pcap.

## Что мы теперь знаем

- Flow Logs пишут метаданные каждого соединения.
- Поля: src/dst, порты, протокол, байты, действие.
- REJECT = сканирование; объём = эксфильтрация.
- Аналоги есть в Azure и GCP.
- Содержимого нет — только метаданные.

## Если не сработало

- Логи не включены? Проверь настройки VPC/NSG.
- Нужно содержимое? Ставь host-based сбор (VPC traffic mirroring).
- Нужны API-действия? Смотри CloudTrail/Activity Log.

## Форматы и поля: v2–v5

AWS VPC Flow Logs меняли формат. Базовый набор полей (v2) — самый частый в задачах:

| Поле | Смысл | Пример |
|---|---|---|
| version | версия формата | 2 |
| account-id | аккаунт | 123456789010 |
| interface-id | ENI | eni-abc123 |
| srcaddr | источник | 10.0.1.5 |
| dstaddr | назначение | 203.0.113.5 |
| srcport | порт источника | 54322 |
| dstport | порт назначения | 443 |
| protocol | 6=TCP, 17=UDP, 1=ICMP | 6 |
| packets | пакетов | 20 |
| bytes | байт | 4000 |
| start / end | начало и конец (epoch) | 1705000000 |
| action | ACCEPT / REJECT | ACCEPT |
| log-status | OK / NODATA / SKIPDATA | OK |

В v3+ добавляются `vpc-id`, `subnet-id`, `instance-id`; в v5 — `traffic-path` и
`flow-direction`. Зная номер версии, ты знаешь, какие поля читать, — иначе `awk '{print $13}'`
попадёт не туда.

## Практика: запросы по flow logs

Простейший триаж — найти все соединения с подозрительным адресом:

```
$ awk '$5=="203.0.113.5" || $4=="203.0.113.5"' flow.log | wc -l
$ grep '203.0.113.5' flow.log | awk '{s+=$10} END{print s" bytes"}'   # объём
```

Сортировка «кто больше выгрузил» ловит эксфильтрацию:

```
$ awk '$13=="ACCEPT"{b[$5]+=$10} END{for(k in b) print b[k], k}' flow.log | sort -rn | head
```

В облаке те же данные удобнее гонять через Athena или CloudWatch Logs Insights:

```sql
SELECT srcaddr, dstaddr, dstport, sum(bytes) AS b
FROM vpc_flow_logs
WHERE action='ACCEPT' AND dstport NOT IN (80,443,53)
GROUP BY srcaddr, dstaddr, dstport
ORDER BY b DESC LIMIT 20
```

Такой запрос сразу показывает нестандартные каналы — типичный C2.

## Корреляция с CloudTrail и DNS

Flow logs говорят «куда», CloudTrail — «что делали через API». Сопоставляя по времени и
по IP/инстансу, восстанавливаешь цепочку:

```
1. 02:10  flow: 10.0.1.5 -> 198.51.100.7:8080  (ACCEPT, 120 MB out)
2. 02:12  cloudtrail: i-0abc... AssumeRole -> AdministratorAccess
3. 02:15  flow: 10.0.1.5 -> 203.0.113.9:443    (внешний C2)
```

Route 53 Resolver Query Logs дают домены, к которым обращались, — часто именно там
всплывает имя C2-домена, которого нет в flow logs (там только IP).

## Практический разбор CTF

Задача: «инстанс выгрузил данные наружу». Шаги:

```
$ grep -v ' NODATA ' flow.log | awk '$8==443 && $10>1000000'   # крупные HTTPS
$ sort -k10 -n flow.log | tail -5                              # топ по объёму
$ awk '$13=="REJECT"' flow.log | awk '{print $4}' | sort | uniq -c | sort -rn | head
```

Последняя команда показывает, кто «долбился» и получал отказ — источник сканирования.

## Ограничения, задержка и стоимость

- **Только метаданные.** Payload не пишется: что именно ушло — не видно.
- **Агрегация.** `bytes`/`packets` суммируются за окно, а не по пакетам; отдельный
  всплеск можно не заметить.
- **Задержка.** Записи появляются с лагом до нескольких минут; последние минуты инцидента
  могут ещё не успеть записаться.
- **Sampling.** Если включена выборка, часть потоков не пишется вовсе.
- **Стоимость.** Полный сбор всех потоков на большом VPC стоит денег — часто включают
  только `REJECT` или только определённые ENI.
- **Приватные ENI.** У части сервисов (NAT, эндпоинты) интерфейсы служебные, и источник
  в записи — не «настоящий» клиент.

## Если сработало / не сработало

Если данных нет — проверь, включён ли flow log на нужном VPC/подсети (по умолчанию часто
выключен). Если нужен payload — включи VPC Traffic Mirroring на инстанс или поставь
host-based сбор. Если нужны API-действия — смотри CloudTrail, а не flow logs.

## Как включаются flow logs

Flow Logs не пишутся «по умолчанию» — их нужно включить на уровне VPC, подсети или
сетевого интерфейса. Настройки важны для расследования, потому что определяют, что
вообще сохранилось:

- **назначение** — CloudWatch Logs или S3 (в S3 удобнее массовый анализ);
- **уровень** — VPC, subnet, ENI;
- **фильтр трафика** — `ALL`, `ACCEPT`, `REJECT` (ALL даёт полную картину);
- **формат полей** — от версии 2 до кастомного набора.

Пример через CLI:

```
$ aws ec2 create-flow-logs --resource-type VPC \
    --resource-ids vpc-0abc --traffic-type ALL \
    --log-destination-type s3 \
    --log-destination arn:aws:s3:::my-flow-logs
```

Версия формата `2` (как в примере урока) — минимальная. Кастомный формат позволяет
добавить `tcp-flags`, `pkt-srcaddr`, `instance-id`, `vpc-id`, что критично для
сопоставления с API-логами.

## Расширенный анализ: Athena и CloudWatch Insights

По сырым flow logs удобно ходить SQL-запросами (Athena поверх S3):

```
SELECT srcaddr, dstaddr, dstport, sum(bytes) AS total
FROM vpc_flow_logs
WHERE action = 'ACCEPT'
GROUP BY srcaddr, dstaddr, dstport
ORDER BY total DESC
LIMIT 20;
```

Это сразу выявляет **крупнейшие исходящие потоки** — кандидаты на эксфильтрацию.
Для поиска сканирования:

```
SELECT srcaddr, count(*) AS rejects
FROM vpc_flow_logs
WHERE action = 'REJECT'
GROUP BY srcaddr ORDER BY rejects DESC LIMIT 20;
```

Много `REJECT` с одного адреса = сетевое сканирование. В CloudWatch Logs Insights
синтаксис другой, но идея та же: `fields`, `filter action="REJECT"`, `stats count() by srcaddr`.

## Корреляция с CloudTrail и другими логами

Flow logs отвечают на вопрос «кто с кем говорил», но не «что делал». Полную картину
даёт **сопоставление**:

- **CloudTrail** — API-действия (создание инстансов, изменение security groups);
- **VPC Flow Logs** — сетевые соединения;
- **GuardDuty** — готовые детекты по обеим группам;
- **S3 access logs** — обращения к объектам.

Связующее звено — **ENI (сетевой интерфейс)**: он есть и в flow log (`eni-abc123`), и
в описании инстанса в CloudTrail. Сопоставив, можно доказать, что именно
скомпрометированный инстанс открывал соединение на подозрительный адрес в момент,
когда через API менялись права.

## Практические сценарии анализа

1. **Beaconing.** C2 обращается домой с регулярным интервалом. В flow logs видно
   повторяющиеся соединения на один адрес с примерно одинаковыми промежутками и
   объёмом. Ищи периодичность, а не единичный пик.
2. **Эксфильтрация.** Аномально большой `bytes` от внутреннего адреса наружу, часто
   на 443 или нестандартный порт, в нерабочее время.
3. **Боковое перемещение.** Много соединений между внутренними инстансами на порты
   22/445/3389, которых не было в норме.
4. **DNS-туннель.** Много коротких UDP/53-потоков к одному резолверу или, наоборот,
   прямо к внешнему адресу.
5. **Сканирование.** Широкий веер `REJECT` на разные порты одного хоста.

## Ограничения и подводные камни

- **Нет содержимого** — flow logs не дают payload, только метаданные.
- **Агрегация** — запись суммирует байты за окно (по умолчанию ~10 минут), поэтому
  точную последовательность пакетов не восстановить.
- **Sampling** — если включена выборка, часть соединений отсутствует вовсе.
- **Задержка доставки** — логи появляются с лагом; при инциденте смотри окно шире.
- **NAT и IPv6** — за NAT виден внешний адрес шлюза, а не клиент; IPv6-поля отдельные.
- **Стоимость** — хранение больших объёмов в S3 не бесплатно, поэтому историю часто
  ротируют — учитывай горизонт хранения.

## Приватные эндпоинты и NAT: почему источник обманчив

В flow logs «источник» — это адрес на сетевом интерфейсе, а не обязательно настоящий
клиент. Это важно при анализе:

- **NAT Gateway** — записи показывают приватный IP NAT-инстанса, а не хоста за ним;
- **VPC Endpoints** — трафик к сервисам AWS идёт на приватные IP (например, S3/DynamoDB
  через `pl-...`), и выглядит как «внутренний», хотя это выход в сервис;
- **Load Balancer** — dstaddr может быть адресом балансировщика, а не бэкенда;
- **Elastic IP** — смена EIP меняет картину, старые записи остаются на прежнем адресе.

Поэтому прежде чем делать вывод «инстанс X выгружал данные на Y», сопоставь ENI с
владельцем (`interface-id` → `describe-network-interfaces`) и проверь, не стоит ли между
ними NAT/балансировщик. Иначе можно обвинить не тот инстанс.

## Чек-лист и шаблон вывода

Практический порядок анализа flow logs:

1. Определить версию формата (v2–v5) и поля — иначе `awk` сместится.
2. Отфильтровать `NODATA`/`SKIPDATA` — это не события.
3. Найти `REJECT` — источник сканирования/брутфорса.
4. Сгруппировать `ACCEPT` по dstaddr и сумме `bytes` — искать эксфильтрацию.
5. Выделить нестандартные порты (`dstport NOT IN (80,443,53,...)`).
6. Сопоставить по времени с CloudTrail (API) и DNS-логами (домены).
7. Проверить владельцев ENI, чтобы не ошибиться с источником.

Шаблон записи в отчёт: `время | src (ENI→владелец) | dst | порт | байты | действие |
коррелирующий источник`. Такая строка воспроизводима и проверяема.

## Что искать при эксфильтрации

- **Большой исходящий объём** на один адрес — классика вывода данных.
- **Регулярный beacon** — соединения с примерно равным интервалом (C2 keep-alive).
- **DNS-туннель** — много коротких UDP/53-потоков к одному резолверу.
- **Нетипичные порты** — 4444, 8080, 8443, 53/TCP, 123/UDP как транспорт C2.
- **Прямые соединения к внешним IP** в обход балансировщика.

Эти признаки работают только в сочетании: один крупный поток может быть обычным бэкапом,
а регулярный beacon — штатным мониторингом. Контекст и корреляция решают.
