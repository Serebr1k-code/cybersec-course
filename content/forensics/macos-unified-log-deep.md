## Вопрос, с которого всё начинается

Ты снял образ Mac и хочешь понять, что происходило за минуты до инцидента: какие процессы
запускались, к каким сетевым адресам шли соединения, что писала подозрительная программа.
В macOS всё это лежит в **unified log** — едином журнале, но не в текстовом виде, а в
бинарном.

## Что такое unified logging

**Unified logging** — единая система журналирования Apple (macOS 10.12+, iOS 10+). Все
процессы пишут события в **общий бинарный журнал**, а не в отдельные текстовые файлы. На
диске это выглядит так:

- **`/var/db/diagnostics/`** — основные файлы `*.tracev3` (собственно записи);
- **`/var/db/uuidtext/`** — вспомогательные файлы: строки и метаданные, на которые
  ссылаются записи (формат `timesync` и каталоги по UUID);
- **`/var/db/diagnostics/Persist/`** — долгоживущие записи.

Ключевая особенность: записи **сжаты и ссылаются на строки** из `uuidtext`, поэтому просто
`strings` по `tracev3` даёт мало. Нужен парсер.

## Наш пример: logarchive

Чтобы работать с журналом, его собирают в **`logarchive`** — каталог со всеми нужными
файлами:

```
$ ls -la
drwxr-xr-x 1 student student 4096 system.logarchive
$ ls system.logarchive/
logdata.LiveData.tracev3  timesync  uuidtext
```

`file` на каталоге не поможет, но на `tracev3`:

```
$ file system.logarchive/logdata.LiveData.tracev3
...: Apple Unified Logging tracev3 file
```

Смотрим текстовые метки:

```
$ strings system.logarchive/logdata.LiveData.tracev3 | grep -Ei 'subsystem|process|nto'
subsystem=com.apple.network
process=curl
subsystem=com.example.malware
EVIDENCE: nto{mac0s_un1f13d_l0g_trac3v3}
```

Мы видим подсистемы и процессы — но это лишь фрагмент; полный разбор даёт парсер.

## Шаг 1: структура записи

Каждая запись unified log содержит:

- **timestamp** — время (наносекунды, с учётом timesync);
- **process** (и pid) — кто писал;
- **subsystem / category** — логическая группа (например, `com.apple.network`);
- **event message** — текст события (может содержать `<private>` для скрытых полей);
- **thread / activity id** — для корреляции.

Приватность: Apple **скрывает** часть данных (`<private>`), если не включён профиль с
подробным логированием. Это важно: некоторые поля (например, URL) могут быть отредактированы.

## Шаг 2: сбор logarchive

На живой системе:

```
$ sudo log collect --last 1d --output system.logarchive
```

На образе — просто копируешь `/var/db/diagnostics` и `/var/db/uuidtext` вместе (парсеру
нужны оба). Если снят только `tracev3` без `uuidtext`, часть строк не расшифруется.

## Шаг 3: инструменты разбора

- **`log show`** (на macOS): `log show --archive system.logarchive --predicate 'process == "curl"'`;
- **macos-unifiedlogs** (Mandiant, Python) — кроссплатформенный парсер tracev3 в JSON;
- **UnifiedLogReader** — ещё один парсер;
- **`log` CLI** даёт фильтры по времени, процессу, подсистеме.

Пример `log show`:

```
$ log show --archive system.logarchive --predicate 'subsystem == "com.apple.network"' --info
2026-03-11 02:14:09.123  curl  subsystem=com.apple.network  connection to 203.0.113.9:443
```

## Шаг 4: что искать

- **Запуски процессов** (`process` = имя) — что стартовало в подозрительное время;
- **Сетевые соединения** (`com.apple.network`) — куда шли подключения;
- **Создание/чтение файлов** — следы доступа;
- **События безопасности** (`com.apple.securityd`, TCC) — выдача разрешений;
- **Аномальные подсистемы** (`com.example.*`) — сторонние процессы.

Полезный приём: построй **таймлайн** вокруг времени инцидента и смотри, какие процессы
впервые появились.

## Шаг 5: приватность и ограничения

- **`<private>`** — поля скрыты; иногда их можно увидеть только с профилем логирования;
- **кольцевой буфер** — журнал перезаписывается; хранится ограниченное время;
- **объём** — журнал огромен; фильтруй по времени и процессу;
- **iCloud-логи** — часть событий уходит в облако и локально не видна.

Эти ограничения фиксируй в отчёте: отсутствие события не всегда означает, что его не было.

## Мини-практика: найти подозрительный процесс

```
$ log show --archive system.logarchive --predicate 'process == "curl"' --info | tail -3
2026-03-11 02:14:09.123  curl  connection to 203.0.113.9:443
2026-03-11 02:14:09.900  curl  connection to 203.0.113.9:443
$ grep -a 'com.example.malware' system.logarchive/logdata.LiveData.tracev3
com.example.malware
```

Мы нашли процесс `curl`, ходивший на внешний IP, и подсистему стороннего ПО. Дальше —
сопоставить время и построить цепочку.

## Частые ошибки и подводные камни

- **Читать tracev3 через strings.** Полный текст не виден — нужен парсер и uuidtext.
- **Забыть uuidtext.** Без него строки не расшифруются.
- **Игнорировать `<private>`.** Часть данных скрыта намеренно.
- **Не фильтровать.** Журнал огромен; работай по времени/процессу.
- **Считать отсутствие события доказательством.** Кольцевой буфер мог перезаписать запись.

## Что мы теперь знаем

- Unified log — единый бинарный журнал macOS (tracev3 + uuidtext).
- Собирается в `logarchive`; парсится `log show`, macos-unifiedlogs, UnifiedLogReader.
- Записи содержат процесс, подсистему, время и текст события.
- Часть полей скрыта (`<private>`); буфер кольцевой.
- Строим таймлайн вокруг инцидента и ищем новые процессы.

## Что фиксировать в отчёте

| Что | Зачем |
|-----|-------|
| Диапазон и источник logarchive | покрытие |
| Список процессов и подсистем | активность |
| Сетевые соединения | связь с C2/целью |
| Поля `<private>` | оговорка о скрытых данных |
| Таймлайн событий | нарратив |

## Расширенный пример: построение таймлайна

Разберём полный прогон анализа unified log. Известно, что инцидент произошёл около 02:15
11 марта. Наша цель — восстановить хронологию.

1. **Собираем журнал** (`log collect`) или берём `logarchive` из образа.
2. **Сужаем окно**: `log show --archive system.logarchive --start "2026-03-11 02:00:00" --end "2026-03-11 02:30:00"`.
3. **Ищем процессы**: фильтр по `process` показывает, что запускалось в окне.
4. **Ищем сеть**: `subsystem == "com.apple.network"` — соединения и адреса.
5. **Смотрим подозрительные подсистемы**: сторонние `com.*` — нестандартное ПО.
6. **Строим таблицу**: время — процесс — событие.

Типичный результат: в 02:14 `curl` соединяется с внешним адресом, в 02:14:30 запускается
бинарник из `/tmp`, в 02:15:10 он пишет в файл в `Library/LaunchAgents` — это закрепление.
Такая последовательность — готовый вывод для отчёта.

Важно помнить о **timesync**: в `logarchive` есть файл `timesync`, который привязывает
монотонные счётчики к wall-clock. Без него время событий может «плыть». Парсеры учитывают
это автоматически, но при ручной работе — проверяй.

## Типовые подсистемы и что они значат

Знание подсистем ускоряет анализ: ты сразу знаешь, где искать.

| Подсистема | Что логирует |
|------------|--------------|
| `com.apple.network` | сетевые соединения |
| `com.apple.securityd` | доступ к ключам, связке |
| `com.apple.TCC` | выдача разрешений приватности |
| `com.apple.launchd` | запуск и остановка процессов |
| `com.apple.xpc` | взаимодействие процессов |
| `com.apple.crashreporter` | падения приложений |
| `com.apple.opendirectoryd` | аутентификация пользователей |

Полезный приём — **фильтр по подсистеме, а не по процессу**: например, все события TCC
покажут выдачу разрешений, даже если их выдавали разные процессы. А сторонние подсистемы
(например, `com.example.*`) сразу выделяют нестандартное ПО — их стоит проверять первыми.

Помни про **`<private>`**: часть полей скрыта, и отсутствие URL в событии сети не значит,
что соединения не было. В отчёте это оформляется как ограничение, а не как «ничего не
найдено».

## Чек-лист разбора unified log

1. Собери **logarchive** (или скопируй `diagnostics` + `uuidtext`).
2. Сузь окно по **времени** — журнал огромен.
3. Фильтруй по **процессу** или **подсистеме**, а не читай всё подряд.
4. Ищи **сетевые соединения** и **запуски процессов**.
5. Проверь **сторонние подсистемы** (`com.*` вне Apple).
6. Построй **таймлайн** и отметь поля `<private>` как ограничение.

## Комбинация с другими журналами

Unified log — не единственный журнал macOS. Для полной картины сопоставляй:

| Источник | Что добавляет |
|----------|---------------|
| Unified log | процессы, сеть, события системы |
| FSEvents | изменения файловой системы |
| TCC.db | разрешения приватности |
| Keychain | обращения к секретам |
| install.log | установка пакетов |

Например, unified log покажет **запуск** процесса, FSEvents — **какие файлы** он создал, а
TCC — **какие разрешения** получил. Только вместе они дают полную хронологию. Это общий
принцип форензики: **один артефакт редко доказывает всё; вывод рождается из их совпадения**.
