## Вопрос, с которого всё начинается

Нужно проанализировать облачную VM. К ней нет физического доступа — только API. Как
снять данные и что доступно? Разберём.

## Наш пример: облачная VM

## Шаг 1: что доступно через API

- **снимки дисков** (snapshots) — можно скачать и смонтировать;
- **образы** (AMI/images);
- **метаданные** (конфигурация, сеть, теги);
- **логи** гипервизора/контроллера.

## Шаг 2: снимок диска

```
$ aws ec2 create-snapshot --volume-id vol-123
$ aws ec2 describe-snapshots --snapshot-ids snap-123
```

Снимок можно скопировать в свой аккаунт и примонтировать локально:

```
$ aws s3 cp s3://bucket/snap.raw . && mount -o ro snap.raw /mnt
```

Важно: снимок — **crash-consistent**, ФС может требовать journal-replay.

## Шаг 3: метаданные

```
$ aws ec2 describe-instances --instance-ids i-123
```

Даёт: образ, тип, сеть, security groups, теги, время запуска, IAM-профиль. Это карта
конфигурации на момент инцидента.

## Шаг 4: гипервизор

Гипервизор (Nitro/KVM) почти не даёт данных напрямую, но **логи сервисов** (CloudTrail,
VPC Flow, GuardDuty) восполняют:

- кто создал/изменил VM;
- сетевые потоки;
- подозрительная активность.

## Шаг 5: что искать

- изменения конфигурации (кто менял SG/IAM);
- новые ключи/пользователи;
- сетевые соединения (Flow Logs);
- образы/снимки, созданные злоумышленником (эксфильтрация через snapshot).

## Что мы теперь знаем

- Облачная VM доступна через API, не физически.
- Снимок диска можно скачать и смонтировать.
- Метаданные дают конфигурацию на момент инцидента.
- Гипервизор восполняется сервисными логами.
- Ищем изменения конфигурации и сеть.

## Если не сработало

- Нет прав на снимок? Запроси у администратора.
- Снимок не монтируется? Восстанови ФС/журнал.
- Нужны потоки? Включи/читай Flow Logs.
