## Вопрос, с которого всё начинается

Нужно проанализировать облачную VM. К ней нет физического доступа — только API. Как
снять данные и что доступно? Разберём.

## Наш пример: облачная VM

## Шаг 1: что доступно через API

- **снимки дисков** (snapshots) — можно скачать и смонтировать;
- **образы** (AMI/images);
- **метаданные** (конфигурация, сеть, теги);
- **логи** гипервизора/контроллера.

## Шаг 2: снимок диска

```
$ aws ec2 create-snapshot --volume-id vol-123
$ aws ec2 describe-snapshots --snapshot-ids snap-123
```

Снимок можно скопировать в свой аккаунт и примонтировать локально:

```
$ aws s3 cp s3://bucket/snap.raw . && mount -o ro snap.raw /mnt
```

Важно: снимок — **crash-consistent**, ФС может требовать journal-replay.

## Шаг 3: метаданные

```
$ aws ec2 describe-instances --instance-ids i-123
```

Даёт: образ, тип, сеть, security groups, теги, время запуска, IAM-профиль. Это карта
конфигурации на момент инцидента.

## Шаг 4: гипервизор

Гипервизор (Nitro/KVM) почти не даёт данных напрямую, но **логи сервисов** (CloudTrail,
VPC Flow, GuardDuty) восполняют:

- кто создал/изменил VM;
- сетевые потоки;
- подозрительная активность.

## Шаг 5: что искать

- изменения конфигурации (кто менял SG/IAM);
- новые ключи/пользователи;
- сетевые соединения (Flow Logs);
- образы/снимки, созданные злоумышленником (эксфильтрация через snapshot).

## Что мы теперь знаем

- Облачная VM доступна через API, не физически.
- Снимок диска можно скачать и смонтировать.
- Метаданные дают конфигурацию на момент инцидента.
- Гипервизор восполняется сервисными логами.
- Ищем изменения конфигурации и сеть.

## Если не сработало

- Нет прав на снимок? Запроси у администратора.
- Снимок не монтируется? Восстанови ФС/журнал.
- Нужны потоки? Включи/читай Flow Logs.

## Что такое облачная VM и при чём тут гипервизор

Виртуальная машина в облаке — это гость, запущенный на **гипервизоре**:
программе, которая делит физическое железо между множеством VM. У разных
провайдеров свои гипервизоры:

- **AWS** — Nitro (вынесенная виртуализация, KVM-подобная база);
- **GCP** — KVM;
- **Azure** — Hyper-V.

Для форензики важно: у тебя **нет физического доступа**. Всё, что доступно,
— через API провайдера: снимки дисков, метаданные, сервисные логи. Сам
гипервизор своих «сырых» логов обычно не отдаёт — их роль берут на себя
сервисы провайдера.

## Работа на примере: снимаем снимок диска

Первый шаг — получить копию диска. В AWS это снимок (snapshot) тома:

```
$ aws ec2 create-snapshot --volume-id vol-0a1b2c3d --description "incident-2026-01-14"
{
  "SnapshotId": "snap-0f9e8d7c",
  "State": "pending",
  ...
}
```

Снимок создаётся асинхронно; ждём состояния `completed`, затем описываем:

```
$ aws ec2 describe-snapshots --snapshot-ids snap-0f9e8d7c
```

Чтобы забрать данные в свой аккаунт, снимок **копируют** и делают том:

```
$ aws ec2 copy-snapshot --source-region us-east-1 --source-snapshot-id snap-0f9e8d7c --region eu-west-1
$ aws ec2 create-volume --snapshot-id snap-... --availability-zone eu-west-1a
```

Затем том подключают к аналитической VM и делают побайтовую копию
(`dd if=/dev/xvdf of=disk.raw`). Важно: снимок — **crash-consistent**, то есть
отражает состояние в момент создания, но файловая система может требовать
воспроизведения журнала (journal replay). Поэтому монтируй **только для
чтения**:

```
$ mount -o ro,noatime disk.raw /mnt/evidence
```

## Метаданные инстанса: карта конфигурации

Метаданные описывают VM на момент инцидента. Основные поля:

```
$ aws ec2 describe-instances --instance-ids i-0abc123
```

- **ImageId** — из какого образа создана (AMI);
- **InstanceType** — размер;
- **NetworkInterfaces** — сеть, приватный/публичный IP;
- **SecurityGroups** — какие порты открыты;
- **IamInstanceProfile** — какие права у VM (ключевой момент!);
- **Tags** — теги (владелец, назначение);
- **LaunchTime** — когда запущена.

Особенно важно **IAM-профиль**: если у VM были широкие права, её компромисс
мог затронуть весь аккаунт. Проверь, что могла делать VM.

## Сервисные логи: чем восполняют гипервизор

- **CloudTrail** — журнал API-вызовов: кто создал/изменил/удалил ресурсы.
  Ищи `RunInstances`, `CreateSnapshot`, `AuthorizeSecurityGroupIngress`,
  `CreateAccessKey`.
- **VPC Flow Logs** — сетевые потоки: source/dest, порты, объёмы. Помогает
  увидеть эксфильтрацию и C2.
- **GuardDuty** — детекты (например, «криптомайнинг», «аномальный доступ»).

```
$ aws cloudtrail lookup-events --lookup-attributes AttributeKey=EventName,AttributeValue=CreateSnapshot
```

Так находится, кто и когда снимал снимки — в том числе злоумышленник для
эксфильтрации.

## Эксфильтрация через snapshot

Известный облачный приём: атакующий с правами на EC2 делает **снимок** диска
жертвы и копирует его в **свой** аккаунт — так данные утекают без единого
сетевого соединения к внешнему адресу. Признаки:

- `CreateSnapshot`/`ModifySnapshotAttribute` (сделать снимок публичным);
- `CopySnapshot` в чужой аккаунт/регион;
- `CreateVolume` из подозрительного снимка.

Эти события видны только в CloudTrail — ещё одна причина, почему сервисные
логи обязательны.

## Ограничения

- **Нет физического доступа** — всё через API.
- **Crash-consistent снимок** — нужен replay журнала.
- **Ретенция логов** — CloudTrail/Flow Logs могут храниться ограниченно.
- **Многоаккаунтность** — событие могло произойти в другом аккаунте
  организации; проверяй Organization Trail.
- **Метаданные меняются** — describe показывает **текущее** состояние, не
  историю; историю дают только логи.

## Практический чек-лист

1. Зафиксировать инцидент и **не гасить** VM (иначе потеряешь память).
2. Снять снимки дисков, скопировать в изолированный аккаунт.
3. Смонтировать **только для чтения**, при необходимости — replay журнала.
4. Выгрузить метаданные (`describe-instances`).
5. Прочитать CloudTrail, Flow Logs, GuardDuty за период.
6. Проверить IAM-профиль и права VM.
7. Искать эксфильтрацию через снимки/копирование.

## Другие провайдеры: GCP и Azure

Хотя команды отличаются, логика везде одна — снимок + метаданные + логи.

**GCP:**

```
$ gcloud compute disks snapshot disk-1 --snapshot-names=snap-1
$ gcloud compute snapshots describe snap-1
```

Снимок можно экспортировать в Cloud Storage и забрать. Метаданные —
`gcloud compute instances describe`. Логи — Cloud Audit Logs (кто вызывал
API) и VPC Flow Logs.

**Azure:**

```
$ az snapshot create -g rg -n snap1 --source /subscriptions/.../disks/disk1
$ az snapshot show -g rg -n snap1
```

Логи — Azure Activity Log (плоскость управления) и NSG Flow Logs. Диски —
`.vhd` в хранилище.

Общее правило: **снимок диска + журнал API + сетевые потоки** — минимальный
набор для облачного расследования.

## Работа с IAM и правами VM

Ключевой вопрос: **что могла делать VM**? Если у неё был широкий IAM-профиль
(например, `AmazonS3FullAccess`), компромисс VM = доступ к данным всего
аккаунта. Проверяем:

```
$ aws ec2 describe-iam-instance-profile-associations
$ aws iam get-instance-profile --instance-profile-name <name>
```

Ищем роли с `*` в ресурсах, права на `iam:CreateAccessKey`,
`sts:AssumeRole`, доступ к бакетам. Если атакующий получил временные
креды с инстанса (через metadata endpoint `169.254.169.254`), он мог
действовать от имени роли — и это видно в CloudTrail по `userIdentity`.

## Практический сценарий: криптомайнинг в облаке

Типичная атака: слабый ключ → `RunInstances` → майнер. Признаки:

- всплеск `RunInstances` с необычным типом (GPU-инстансы);
- новые security groups с открытым портом;
- исходящие соединения на пулы (Flow Logs);
- рост счёта.

```
$ aws cloudtrail lookup-events --lookup-attributes AttributeKey=EventName,AttributeValue=RunInstances
```

Фиксируем: кто, когда, откуда (sourceIPAddress), с какими параметрами. Затем
ищем связанные события: `CreateKeyPair`, `AuthorizeSecurityGroupIngress`,
`CreateAccessKey`.

## Итог: облако — это API, а не диск

Облачная форензика строится на трёх опорах: **снимки** (данные), **метаданные**
(конфигурация) и **сервисные логи** (действия). Физический доступ заменяется
API-вызовами, а роль «журнала системы» играют CloudTrail/Flow Logs. Главное
— не гасить VM до снятия снимков и помнить, что история живёт в логах, а не
в текущем состоянии. Тогда даже без доступа к железу можно восстановить, кто
и что делал в облаке.

## Сохранение доказательств в облаке

Облачные улики легко «потерять» из-за автоматизации: авто-скейлинг удалит
инстанс, ротация затрёт логи, а TTL снимет снимки. Поэтому сразу:

- **включить защиту от удаления** (`DisableApiTermination`,
  `DeleteOnTermination=false`);
- **скопировать снимки и логи** в изолированный аккаунт/бакет;
- **зафиксировать хэши** и время создания;
- **экспортировать CloudTrail** за нужный период в неизменяемое хранилище.

Помни про «chain of custody»: у каждого артефакта должно быть время
создания, источник и хэш. В облаке это критично, потому что API-действия
оставляют след только в логах — а логи можно отключить.

## Частые ошибки

- **Гасить VM до снятия снимка** — теряешь содержимое памяти (RAM).
- **Читать метаданные как историю** — describe показывает текущее состояние.
- **Забыть про IAM** — не проверить, что могла делать VM, значит пропустить
  масштаб компромисса.
- **Не учесть Organization Trail** — событие могло быть в другом аккаунте.
- **Считать снимок «полным»** — он crash-consistent, журнал ФС может
  требовать replay.

## Пример: восстановление из снимка

Снимок подключают как том к аналитической VM, копируют в файл и монтируют
read-only:

```
$ dd if=/dev/xvdf of=evidence.raw bs=4M status=progress
$ losetup -r /dev/loop0 evidence.raw
$ mount -o ro /dev/loop0p1 /mnt/evidence
```

Если ФС требует replay журнала, сначала снимают копию, «прогоняют» журнал на
копии (например, `fsck -n` в режиме проверки), затем монтируют. Оригинал
снимка остаётся нетронутым.
