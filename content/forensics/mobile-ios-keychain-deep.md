## Вопрос, с которого всё начинается

Пароли, токены, ключи Wi-Fi — всё это в **keychain** iOS. Извлечь его — цель многих
расследований. Разберём, что возможно.

## Наш пример: keychain из бэкапа

## Шаг 1: что хранит keychain

- пароли сайтов и Wi-Fi;
- токены приложений;
- ключи шифрования;
- сертификаты.

## Шаг 2: защита

Keychain защищён аппаратным **Secure Enclave** и привязан к паролю устройства.
Обычное извлечение невозможно — нужен либо пароль, либо уязвимость.

## Шаг 3: из шифрованного бэкапа

Шифрованный бэкап содержит `keychain-backup.plist`:

```
$ iphone_backup_decrypt -i Backup/UDID -o out -p <password>
$ ls out/
keychain-backup.plist  ...
```

Пароль бэкапа разблокирует keychain-записи, доступные для бэкапа.

## Шаг 4: из живого устройства

С jailbreak:

```
$ ssh root@iphone
# sqlite3 /var/Keychains/keychain-2.db '.tables'
```

Но современные записи привязаны к Secure Enclave — часть недоступна.

## Шаг 5: что искать

- пароли Wi-Fi (полезно для расследования сети);
- токены сессий;
- сертификаты;
- ключи приложений;
- записи, доступные только на устройстве (не в бэкапе).

## Что мы теперь знаем

- Keychain хранит пароли, токены, ключи.
- Защищён Secure Enclave и паролем устройства.
- Шифрованный бэкап даёт часть записей.
- Jailbreak даёт доступ к базе (частично).
- Некоторые записи не покидают устройство.

## Если не сработало

- Нет пароля бэкапа? Keychain недоступен.
- Нужны все записи? Только живое разблокированное устройство.
- Нужны Wi-Fi? Часть паролей в бэкапе.

## Как устроен keychain внутри

На устройстве keychain — это SQLite-база `keychain-2.db` в `/var/Keychains/`. Её
таблицы отражают классы элементов:

| Таблица | Класс | Что хранит |
|---|---|---|
| `genp` | generic password | пароли приложений, Wi-Fi, токены |
| `inet` | internet password | логины сайтов (домен, порт, протокол) |
| `cert` | certificate | сертификаты |
| `keys` | cryptographic key | ключи (в т.ч. привязанные к SEP) |
| `ckperm` | access control | права доступа приложений к элементу |

Ключевой атрибут — **доступность** (`kSecAttrAccessible`), определяющая, можно ли
прочитать секрет при заблокированном экране:

- `WhenUnlocked` — только при разблокированном;
- `AfterFirstUnlock` — после первой разблокировки (часто у фоновых сервисов);
- `Always` — всегда (в бэкап попадает);
- `...ThisDeviceOnly` — не переносится и не уходит в бэкап/iCloud.

Значение `always` и отсутствие `ThisDeviceOnly` — красный флаг: секрет извлекается
даже из бэкапа.

## Защита: классовые ключи и Secure Enclave

Сами данные зашифрованы не одним ключом. Каждый элемент шифруется уникальным ключом,
а тот — «классовым» ключом, который выводится из пароля устройства и
аппаратного UID Secure Enclave. Поэтому:

- без пароля устройства классовые ключи не выводятся;
- ключи, помеченные как SEP-привязанные (P-256), **неэкспортируемы** — извлечь их
  копию невозможно в принципе;
- смена пароля переворачивает классовую иерархию, часть элементов становится
  недоступна.

## Извлечение: бэкап vs живое устройство

Из шифрованного бэкапа keychain лежит в `keychain-backup.plist`, но только те
элементы, что не помечены `ThisDeviceOnly`:

```
$ iphone_backup_decrypt -i Backup/<UDID> -o out -p <password>
$ plutil -p out/keychain-backup.plist | head
```

На живом разблокированном устройстве с jailbreak:

```
$ ssh root@iphone
# sqlite3 /var/Keychains/keychain-2.db 'SELECT svce,acct FROM genp LIMIT 10;'
```

Даже с root значения полей зашифрованы — нужен `keychain_dumper` с правами и
разблокированным экраном, чтобы расшифровать доступные классы.

## Что искать

- пароли Wi-Fi (`genp` с `svce=AirPort`) — восстановление сети;
- токены сессий и OAuth-токены приложений;
- сертификаты и приватные ключи (`cert`, `keys`);
- записи с `always` — потенциальная утечка;
- элементы `ThisDeviceOnly`, которых в бэкапе нет — признак, что смотрели не тот
  источник.

## Тонкие места

- Без пароля устройства keychain не расшифровывается — это норма, а не тупик.
- В iCloud Keychain часть элементов синхронизируется — они есть в облаке.
- Имена служб (`svce`) и аккаунтов (`acct`) читаемы даже без расшифровки.
- Приложение может ограничить элемент `access control` — доступ получит только оно.
- Старые бэкапы (iOS 9-) имеют другую схему классов — сверяй версию.

## Расширенный разбор: от бэкапа к Wi-Fi-паролю

Задача: восстановить пароль Wi-Fi из шифрованного бэкапа.

```
$ iphone_backup_decrypt -i Backup/<UDID> -o out -p <password>
$ plutil -p out/keychain-backup.plist | grep -A6 -i 'AirPort'
```

В `genp`-элементе Wi-Fi видны поля `svce` (обычно `AirPort`), `acct` (SSID) и
`data` (зашифрованный пароль). Пароль бэкапа разблокирует ключ класса, и `data`
расшифровывается. Если элемент помечен `ThisDeviceOnly`, в бэкапе его не будет —
это норма, а не повреждение.

## iCloud Keychain

Часть элементов синхронизируется через iCloud Keychain. Это значит:

- на диске их может не быть вовсе;
- в облаке они защищены отдельным ключом (iCloud Security Code);
- без доступа к аккаунту восстановить их нельзя.

Для расследования это различие критично: отсутствие записи в локальном keychain не
означает, что пароль не сохранён — он может быть в облачной синхронизации.

## Таблица классов и доступности

| Класс | Таблица | Пример |
|---|---|---|
| Generic password | `genp` | токены, Wi-Fi |
| Internet password | `inet` | логины сайтов |
| Certificate | `cert` | сертификаты |
| Key | `keys` | ключи, в т.ч. SEP |
| Access control | `ckperm` | права приложений |

| Доступность | В бэкап? | При блокировке? |
|---|---|---|
| WhenUnlocked | да | нет |
| AfterFirstUnlock | да | да (фоново) |
| Always | да | да |
| ThisDeviceOnly | **нет** | по классу |

## Ошибки

- Искать пароли в `accounts_ce.db` или `keychain-backup.plist` в открытом виде —
  значения зашифрованы.
- Считать, что root даёт все секреты: SEP-ключи неэкспортируемы.
- Забывать, что смена пароля устройства «переворачивает» классовую иерархию.
- Игнорировать iCloud Keychain и делать вывод «пароля нет».
- Путать `svce`/`acct` (метаданные, читаемы) и `data` (секрет, зашифрован).

## Разбор: токен приложения

Пусть нужно понять, к какому сервису обращается приложение. Токен лежит в
`genp`-элементе:

```
$ sqlite3 /var/Keychains/keychain-2.db "SELECT svce,acct,agrp FROM genp WHERE agrp LIKE '%example%';"
```

`svce` и `acct` читаемы без расшифровки: они дают имя сервиса и аккаунт. `agrp`
(access group) показывает, какие приложения разделяют элемент. Даже без
расшифровки `data` этих метаданных часто достаточно, чтобы понять, каким сервисом
пользовался человек и с каким аккаунтом.

## Ограничения метода

- Значения (`data`) зашифрованы; без ключа класса их не прочитать.
- SEP-привязанные ключи неэкспортируемы в принципе.
- `ThisDeviceOnly` элементы отсутствуют в бэкапе — это не повреждение.
- Часть элементов синхронизирована в iCloud.
- Смена пароля устройства делает старые классовые ключи недоступными.

## Как усилить вывод

Сопоставь `svce`/`acct` с сетевыми артефактами и с установленными приложениями:
имя сервиса из keychain, встреченное в трафике, подтверждает реальное
использование. Для расшифровки нужен либо пароль бэкапа, либо живое
разблокированное устройство.

## Итог: что реально можно извлечь

Из keychain извлекается ровно то, что разрешено моделью защиты. Из шифрованного
бэкапа доступны элементы, не помеченные `ThisDeviceOnly`, — включая пароли Wi-Fi и
часть токенов приложений. С живого разблокированного устройства с jailbreak
доступно больше, но SEP-привязанные ключи всё равно неэкспортируемы. Метаданные
(`svce`, `acct`, `agrp`) читаются всегда и часто дают ответ и без расшифровки
значения. В отчёте различай три состояния: «значение извлечено», «известен только
сервис и аккаунт» и «недоступно из-за SEP/iCloud». Такая честная градация важнее,
чем громкое «взломали keychain», за которым на деле стоит лишь список служб.

## Связка с бэкапом и облаком

Ключевой практический вопрос: где искать keychain. Есть три источника, и они дают
разные подмножества. Шифрованный бэкап содержит элементы, не помеченные
`ThisDeviceOnly`, и для их чтения нужен пароль бэкапа. Живое разблокированное
устройство с jailbreak даёт доступ к `keychain-2.db` целиком, но значения всё равно
зашифрованы классовыми ключами. iCloud Keychain синхронизирует часть элементов в
облако под отдельным ключом. Практический вывод: отсутствие элемента в одном
источнике ничего не доказывает. Если пароля бэкапа нет, проверь живое устройство;
если и его нет — проверь, не помечен ли элемент как `ThisDeviceOnly`, и не
синхронизируется ли он через iCloud. В отчёте всегда указывай, из какого источника
получен элемент и почему другие источники его не содержат: это снимает вопрос
«почему у вас нет пароля Wi-Fi», когда он просто не покидает устройство.

## Практический вывод

Keychain даёт ровно то, что разрешает модель защиты: метаданные читаются всегда,
значения — только при наличии ключа, а SEP-привязанные ключи недоступны в принципе.
Всегда указывай источник элемента (бэкап, живое устройство, iCloud) и честно
отмечай то, что извлечь нельзя, — это и есть корректный вывод.

## Что писать в отчёте

По keychain всегда указывай: класс элемента (`genp`, `inet`, `cert`, `keys`), его
доступность (`WhenUnlocked`, `AfterFirstUnlock`, `Always`, `ThisDeviceOnly`) и
источник (бэкап, живое устройство, iCloud). Различай три состояния результата:
«значение извлечено», «известны только метаданные» и «недоступно». Метаданные
`svce`/`acct` часто дают ответ и без расшифровки, поэтому не считай их
бесполезными. Такая аккуратная градация отличает настоящий отчёт от громкого
«взломали keychain» без реальных секретов.
