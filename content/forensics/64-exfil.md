## Вопрос, с которого всё начинается

Организация подозревает утечку: документы, которые не должны были покидать сеть,
оказались у конкурента. Есть `exfil.pcap` — захват трафика с рабочей машины. Как
найти канал, по которому данные ушли, и восстановить, что именно передавалось?

**Эксфильтрация** — это вынос данных за пределы защищённого периметра. Атакующий
прячет её в **легитимных** протоколах (DNS, HTTP, ICMP), чтобы не вызывать
подозрений у систем защиты. Обнаружение строится на **статистике и корреляции**:
аномалии объёмов, таймингов и паттернов выдают канал.

## Наш пример: кто передал больше всех

Начнём со статистики разговоров. В `tshark` (консольный Wireshark) есть встроенный
отчёт `conv,ip` — «conversations», все пары общавшихся адресов:

```bash
$ tshark -r exfil.pcap -q -z conv,ip | sort -k3 -rn | head -3
10.0.0.5 <-> 203.0.113.9   4521000 bytes
10.0.0.5 <-> 10.0.0.1       32000 bytes
```

Клиент `10.0.0.5` отправил на внешний `203.0.113.9` 4,5 МБ. Для рабочей станции,
которая «просто открывала документы», это много. Кандидат найден — посмотрим, каким
протоколом он пользовался:

```bash
$ tshark -r exfil.pcap -Y 'ip.dst==203.0.113.9' -q -z io,phs
dns
```

Весь объём ушёл по **DNS** — протоколу, который обычно лишь переводит имена в
адреса и почти всегда разрешён через firewall. Это очень подозрительно.

## Шаг 1: что такое DNS-туннель

DNS-запрос спрашивает: «какой IP у домена `www.example.com`?». Имя домена состоит
из **меток**, разделённых точками. Атакующий может закодировать украденные данные
в поддомене и заставить DNS-сервер их «резолвить»:

```
dGhpcyBpcyB0aGUgc2VjcmV0.evil.com
```

Первая метка — это Base64 от куска данных. DNS-сервер атакующего (`evil.com`)
получает запрос и «читает» данные. Такой канал называют **DNS-туннелем**.

## Шаг 2: находим длинные имена

Найдём самые длинные запрошенные имена:

```bash
$ tshark -r exfil.pcap -Y dns -T fields -e dns.qry.name | awk '{print length,$0}' | sort -rn | head -1
62 dGhpcyBpcyB0aGUgc2VjcmV0...evil.com
```

62 символа в имени — ненормально много (обычные домены короче 30). Посчитаем, как
часто запрашивается домен `evil.com`:

```bash
$ tshark -r exfil.pcap -Y dns -T fields -e dns.qry.name | sed 's/.*\.\(evil\.com\)/\1/' | sort | uniq -c | sort -rn | head
   47 evil.com
```

47 запросов к одному домену с длинными метками — это и есть туннель: каждый запрос
несёт очередной кусок данных.

## Шаг 3: восстанавливаем данные

Данные кодировали Base64. Возьмём первые метки всех запросов и декодируем:

```bash
$ tshark -r exfil.pcap -Y dns -T fields -e dns.qry.name | cut -d. -f1 | base64 -d 2>/dev/null | strings | head
secret document contents
```

Склеив и раскодировав метки по порядку, получаем исходный текст. Иногда используют
**Base32** (часто в DNS-туннелях — она без символов, ломающих имена):

```bash
$ tshark -r exfil.pcap -Y dns -T fields -e dns.qry.name | cut -d. -f1 | base32 -d 2>/dev/null | strings
```

Данные могут быть и в ответах, в записях типа `TXT`:

```bash
$ tshark -r exfil.pcap -Y 'dns.resp.type==16' -T fields -e dns.txt | head
```

## Шаг 4: другие скрытые каналы

DNS — не единственный вариант. Кратко разберём остальные.

**ICMP-туннель** — данные прячут в теле эхо-запросов (`ping`):

```bash
$ tshark -r exfil.pcap -Y 'icmp.type==8' -T fields -e data.data | xxd -r -p | strings | head
```

Признак — большой **постоянный** payload в каждом пакете (обычный ping почти пуст).

**HTTP-туннель** — данные в теле POST или заголовках (`Cookie`, `Referer`):

```bash
$ tshark -r exfil.pcap -Y 'http.request.method=="POST"' -T fields -e http.file_data | head
$ tshark -r exfil.pcap -Y 'http.cookie' -T fields -e http.cookie | head
```

**Domain fronting** — приём маскировки: домен в заголовке `Host` не совпадает с
SNI в TLS-рукопожатии. Трафик выглядит как обращение к легитимному CDN:

```bash
$ tshark -r exfil.pcap -Y 'tls.handshake.extensions_server_name' -T fields -e tls.handshake.extensions_server_name -e http.host
```

## Шаг 5: статистика выдаёт канал

Помимо содержимого, канал выдаёт себя **формой** трафика. Ключевые метрики:

- **асимметрия** — клиент отправил много, получил мало (вынос данных);
- **регулярность** — соединения с ровным интервалом (маячок);
- **постоянный размер пакетов** — фиксированный «чанк» туннеля.

```bash
$ tshark -r exfil.pcap -Y 'ip.dst==203.0.113.9' -T fields -e frame.time_relative | head -5
0.000000
1.001
2.003
3.002
```

Интервалы почти ровно 1 секунда — механическая регулярность, которой не бывает у
человека, открывающего документы.

## Полный разбор: от аномалии к данным

Соберём детект утечки в один сценарий.

1. **Обзор объёмов.** Кто больше всех передал наружу — `tshark -z conv,ip` или flow.
2. **DNS-туннель.** Длинные поддомены — верный признак:
   ```bash
   $ tshark -r exfil.pcap -Y dns -T fields -e dns.qry.name | awk '{print length, $0}' | sort -nr | head
   ```
3. **Восстанавливаем данные.** Собираем поддомены по времени и декодируем (base32/hex):
   ```bash
   $ tshark -r exfil.pcap -Y 'dns.flags.response==0' -T fields -e dns.qry.name > names.txt
   ```
4. **Другие каналы.** ICMP (payload в эхо), HTTP (POST на необычный URI), TLS на нестандартный порт.
5. **Статистика.** Ровные интервалы и постоянный размер = автоматизированный канал.

Ключ: скрытый канал выдаёт **ритм и форму**, а не содержимое — по ним его и находят.

## Шпаргалка каналов

| Канал | Признак |
|-------|---------|
| DNS | длинные/частые имена поддоменов |
| ICMP | большие/частые echo-пакеты |
| HTTP | POST на редкий URI, малый ответ |
| HTTPS | поток на нестандартный порт, ровный ритм |
| ICMP/DNS | аномальный объём при малом числе хостов |

## Частые вопросы

**Как отличить DNS-туннель от обычного DNS?** По длине имён, частоте и разнообразию (энтропии) меток.

**Данные можно восстановить полностью?** Если канал не потерял пакеты — да; DNS-метки декодируются в исходные байты.

**Эксфильтрация бывает «медленной»?** Да, нарочно: малыми порциями, чтобы не превышать пороги.

**Как защититься?** Ограничить DNS-резолверы, мониторить объёмы, блокировать нестандартные порты наружу.

## Что мы теперь знаем

- **Эксфильтрация** прячется в легитимных протоколах: DNS, ICMP, HTTP(S).
- **DNS-туннель** выдаёт себя длинными метками и частыми запросами к одному домену.
- Данные кодируют (Base64/Base32) и восстанавливают декодированием меток.
- **Статистика** (асимметрия, регулярность, постоянный размер) выдаёт канал без
  расшифровки содержимого.
- **Domain fronting** маскирует C2 под легитимный CDN (`Host` ≠ SNI).

## На что смотреть дальше

- **Смотреть только TCP/HTTP** — туннели живут в DNS/ICMP.
- **Не строить статистику** — аномалии видны только в агрегатах.
- **Игнорировать тайминги** — регулярность выдаёт канал.
- **Не декодировать base32/base64** — данные останутся «шумом».
- **Пропустить domain fronting** — трафик выглядит легитимным.
- **Забыть про TLS** — данные могут быть внутри HTTPS (см. урок про расшифровку).

## Куда дальше

Мы научились находить скрытые каналы утечки. В следующем уроке спустимся с уровня
сети на уровень приложений и разберём **SQLite** — базу, в которой браузеры,
мессенджеры и мобильные приложения хранят почти все свои данные, включая удалённые
сообщения. А пока запомни: **эксфильтрацию выдают форма трафика и длинные
кодированные метки, а не только содержимое**.

## Где пригодится

- **CTF** — задачи на DNS/ICMP-туннели и скрытые каналы.
- **DFIR** — оценка объёма и содержания утечки.
- **Threat Hunting** — поиск аномалий DNS/ICMP/HTTP.
- **SOC** — правила на длинные поддомены, редкие DNS-типы, большие ICMP.
- **Судебная экспертиза** — доказательство факта и объёма выноса данных.
