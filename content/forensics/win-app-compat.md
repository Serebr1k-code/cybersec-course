## Вопрос, с которого всё начинается

У нас есть подозрение, что программа запускалась, но Prefetch уже очищен, а её самой на
диске нет. Есть ли ещё один независимый источник «что запускалось на этой машине»?

## Что такое AppCompat cache

**AppCompat cache** (историческое имя — **ShimCache**) — структура в кусте `SYSTEM`
по пути:

```
HKLM\SYSTEM\CurrentControlSet\Control\Session Manager\AppCompatCache
```

Windows записывает туда пути к исполняемым файлам, которые прошли через механизм
**совместимости приложений** (shim engine). Когда приложение запускается, система
проверяет, нужен ли ему «shim» (заплатка совместимости), и попутно фиксирует путь файла.
Так кэш накапливает **пути к программам, которые запускались** — часто дольше, чем живёт
Prefetch.

## Наш пример

У нас дамп AppCompatCache.

```
$ cat appcompat.txt
C:\Windows\System32\cmd.exe
C:\Program Files\7-Zip\7zFM.exe
C:\Users\Public\svc.exe  nto{sh1mc4ch3_p4th_3x3cut3d}
C:\Windows\System32\notepad.exe
```

Четыре пути. `svc.exe` из `C:\Users\Public` снова всплывает — теперь уже как
доказательство запуска.

## Шаг 1: что именно доказывает ShimCache

Важный нюанс, который путает новичков: **наличие пути в ShimCache означает, что файл
«существовал» на момент проверки** (система просканировала каталоги), но не всегда
доказывает запуск. На разных версиях Windows формат разный:

- в **Windows 8/10** структура содержит **флаги**, среди которых признак выполнения;
- в **Windows 7 и раньше** — только путь, без надёжного признака запуска.

Поэтому ShimCache используют **вместе** с другими артефактами (Prefetch, AmCache, WER).

## Шаг 2: как читать и что искать

Разбор делают инструментами (`AppCompatCacheParser` от Eric Zimmerman). Из записей
достают:

- **путь** к исполняемому файлу;
- **время последней модификации** файла (в новых версиях);
- **флаги выполнения** (где они есть).

Ищут нестандартные пути (`Users\Public`, `Temp`, `ProgramData`), двойные расширения и
известные IOC.

## Шаг 3: связка с другими источниками

Правильная схема вывода:

```
ShimCache (путь)  +  Prefetch (время запуска)  +  WER/EVTX  =>  запуск доказан
```

Каждый артефакт по отдельности может дать ложную уверенность. Только пересечение
нескольких независимых источников делает вывод обоснованным.

## Что мы теперь знаем

- AppCompat cache/ShimCache лежит в SYSTEM hive и хранит пути к программам.
- В новых Windows содержит флаги выполнения; в старых — только путь.
- Разбирается инструментами; ищем нестандартные пути и IOC.
- Использовать только в связке с Prefetch/AmCache/WER.

## История форматов ShimCache

ShimCache менял формат от версии к версии, и это важно для интерпретации. В старых
Windows (XP/2003/7) структура содержала **только путь** и иногда время последней
модификации — **признака запуска не было**. Начиная с Windows 8 структура расширилась:
добавились **флаги**, среди которых есть бит, указывающий, что файл был **выполнен**
(а не просто просканирован). В Windows 10 формат менялся ещё раз — добавились поля с
временем и признаком «сжат».

Практический вывод: если вы видите путь в ShimCache на Windows 7, вы **не можете**
утверждать, что программа запускалась. На Windows 10 — можете, но с оговоркой, что
флаги интерпретируются версионно-зависимо. Поэтому разбор всегда делают инструментом,
который знает версию формата.

## Байтовая раскладка записей

Внутри значения `AppCompatCache` лежит заголовок (сигнатура `10ts` для Win10, `00ts`
для Win8, `badc0ffe` для Win7), затем — массив записей. Каждая запись Win10 содержит:

- длину записи (4 байта);
- максимум пути (2 байта);
- длину пути (2 байта);
- **путь** в UTF-16LE;
- **LastModified** (8 байт, FILETIME);
- **DataSize** (4 байта) и **Data** (флаги исполнения и др.);
- признак «файл был выполнен» в поле данных.

Знание раскладки нужно, когда под рукой нет парсера: можно найти пути и времена прямо
в hex-дампе значения.

## Чтение с AppCompatCacheParser

Стандартный инструмент — **AppCompatCacheParser** (Eric Zimmerman). Он умеет:

- читать куст напрямую (`-f SYSTEM`);
- выгружать в CSV с колонками `Path`, `LastModifiedTimeUTC`, `Executed`, `CacheEntryPosition`;
- работать с «dirty» кустом, к которому надо предварительно применить transaction-логи.

Типовой запуск:

```
AppCompatCacheParser.exe -f C:\case\SYSTEM -o C:\case\out
```

Колонка `Executed` — то, ради чего всё делается: она показывает, помечен ли файл как
выполненный (там, где версия Windows это поддерживает).

## Корреляция и ограничения

ShimCache — это **не таймлайн**, а набор «следов». Важные ограничения:

- **Нет точного времени запуска.** `LastModified` — это время изменения файла, а не
  запуска; на старых системах времени нет вовсе.
- **Порядок записей — не порядок запуска.** Записи не упорядочены по времени.
- **Ограниченный размер.** Старые записи вытесняются новыми; давняя активность может
  исчезнуть.
- **Ложные срабатывания.** Антивирус и индексатор тоже обращаются к файлам, оставляя
  пути.

Поэтому ShimCache используют как **подтверждающий** артефакт: он либо согласуется с
Prefetch/AmCache/WER, либо добавляет путь, которого больше нигде нет. В отчёте его
всегда подают в связке, а не как единственное доказательство.

## ShimCache против AmCache и Prefetch

Три артефакта часто путают, хотя у них разные роли:

- **ShimCache (AppCompat cache)** — пути файлов, прошедших через shim-движок; на новых
  Windows есть флаг исполнения. Отвечает на вопрос «существовал ли файл / запускался».
- **AmCache** — база `Amcache.hve` с записями о запущенных/установленных программах и
  их **SHA-1**. Даёт хеш файла, что бесценно для сверки с VirusTotal.
- **Prefetch** — файлы `C:\Windows\Prefetch\*.pf`, по одному на программу, с **временем
  запуска** и счётчиком. Самый точный источник «когда и сколько раз запускалось».

Идеальная связка: Prefetch (когда) + AmCache (что, с хешем) + ShimCache (откуда). Если
все три указывают на один файл — сомнений нет.

## Разбор значения вручную

Когда нет инструмента, значение `AppCompatCache` можно разобрать в hex. Ищем сигнатуру
`10ts` (Win10), затем читаем записи подряд: длина, длина пути, сам путь в UTF-16LE,
время в FILETIME, затем флаги. Пути в UTF-16LE дают характерный «перемежающийся нулями»
вид в hex-дампе:

```
$ xxd AppCompatCache.bin | head
0000: 31 30 74 73 ... 43 00 3a 00 5c 00 55 00 73 00 65 00
```

`43 00 3a 00 5c 00` — это `C:\` в UTF-16LE. Так вручную находят пути, даже без парсера.

## Что писать в отчёте

Формулировка вывода важна для корректности. Нельзя писать «программа запускалась», если
источник — только ShimCache на Windows 7. Корректно:

> В кусте SYSTEM (AppCompatCache) обнаружен путь `C:\Users\Public\svc.exe`,
> LastModified 2024-03-02 10:12 UTC. На данной версии Windows запись содержит флаг
> выполнения, что в совокупности с Prefetch (время запуска 10:13) указывает на запуск
> программы с указанного пути.

Такой стиль фиксирует источник, время, ограничение метода и подтверждающий артефакт —
именно так и строится защищаемый форензик-вывод.

## Откуда берётся AppCompatCache и когда он обновляется

Значение `AppCompatCache` пишется при обращении системы к каталогам с исполняемыми
файлами — индексатором, сканером или при запуске. Поэтому оно обновляется не только при
запуске, но и при простом «просмотре» каталога системой. Отсюда важная оговорка: запись
доказывает, что файл **существовал** на диске и был замечен, но не всегда что его
запускал пользователь.

На практике кэш обновляется при перезагрузке и при сканировании, а старые записи
вытесняются новыми. Поэтому AppCompatCache — это «окно» последних нескольких сотен
путей, а не полная история. Для долгой ретроспективы его комбинируют с AmCache, который
хранит больше записей и хеши.

## Частая ошибка интерпретации

Самая распространённая ошибка новичка — прочитать путь в ShimCache как «файл
запускался». Корректная логика: путь означает «файл присутствовал». Признак запуска
появляется только там, где версия Windows пишет соответствующий флаг, и только вместе с
подтверждающим артефактом (Prefetch, AmCache, WER, событие 4688). В отчёте всегда
указывают версию Windows и наличие флага — иначе вывод легко опровергнуть.

## Извлечение из куста: «грязный» hive и транзакционные логи

На диске куст `SYSTEM` часто оказывается «грязным» — часть изменений осталась в
**транзакционных логах** (`.LOG1`, `.LOG2`), и без их применения ты увидишь устаревшее
значение. Поэтому копируй не только `SYSTEM`, но и `SYSTEM.LOG1`/`SYSTEM.LOG2`. Если куст
примонтирован (машина работала), сначала снимай образ или используй теневую копию.

Способы прочитать значение без Windows:

```bash
# regipy — чтение куста и значения AppCompatCache
python3 -c "from regipy.registry import RegistryHive; \
  h=RegistryHive('SYSTEM'); \
  print(h.get_key('\\\\ControlSet001\\\\Control\\\\Session Manager').get_value('AppCompatCache'))"
# hivex — выгрузить значение в файл для последующего разбора
hivexregedit --export SYSTEM '\ControlSet001\Control\Session Manager' AppCompatCache > appcompat.bin
xxd appcompat.bin | head
```

Если под рукой `AppCompatCacheParser`, он сам умеет применять transaction-логи к грязному
кусту — поэтому в отчёте указывай, применялись ли логи, иначе доказательство оспоримо.

## Как отличить индексацию от запуска: практический пример

Разберём типичную ситуацию. В AppCompatCache есть путь `C:\Users\Public\svc.exe`, и встаёт
вопрос: программа запускалась или система просто просканировала каталог?

Порядок проверки:

1. **Флаг исполнения.** Открой запись в парсере и посмотри колонку `Executed`. Если она
   пуста/ложь — доказательства запуска из ShimCache нет.
2. **LastModified.** Сравни время изменения файла с временем индексации (перезагрузка,
   работа антивируса). Совпадение с моментом сканирования говорит против запуска.
3. **Prefetch.** Есть ли `SVC.EXE-*.pf`? Наличие и его время запуска решают вопрос.
4. **AmCache.** Есть ли запись с **SHA-1** файла? Это подтверждает, что файл был выполнен
   (AmCache фиксирует исполнение и установку).

Если все четыре согласуются — запуск доказан. Если только путь в ShimCache — пиши
осторожно: «файл присутствовал», не «запускался».

## Практика в CTF: порядок действий

В CTF-задаче на Windows-артефакты порядок обычно такой:

```
# 1) найти нужный куст в образе
find . -iname 'SYSTEM' -o -iname 'Amcache.hve' -o -iname '*.pf'
# 2) вытащить путь и время
AppCompatCacheParser.exe -f SYSTEM -o out --csv
# 3) подтвердить Prefetch
ls out/ | grep -i '<имя>.pf'
# 4) собрать таймлайн
```
