## Вопрос, с которого всё начинается

Ты загрузил подозрительный драйвер на тестовую машину, а `lsmod` его не показывает.
Может, он не загрузился? А может — он загружен, но **скрылся**. Разница принципиальная:
во втором случае на машине работает руткит.

## Наш пример: модуль, которого нет в списке

Загружаем драйвер и смотрим список модулей ядра:

```
$ lsmod | grep -i evil
(пусто)
```

`lsmod` читает `/proc/modules` — файл, который ядро формирует из своего **связанного
списка** модулей. Если модуль из списка вырезали, его там не будет. Но в памяти он
останется.

## Как устроен список модулей

Каждый загруженный модуль — это структура в памяти ядра (в Linux — `struct module`).
Модули связаны в двусвязный список. Чтобы спрятать модуль, достаточно «перешить»
указатели соседей так, чтобы наш модуль выпал из цепочки:

```
было:  A <-> B <-> C
стало: A <-> C            (B выпал, но сам объект в памяти остался)
```

Это уже разновидность **DKOM** — прямого искажения объектов ядра. Сам объект никуда не
исчез, он просто больше не достижим обходом списка.

## Шаг 1: сравнить список и скан

В дампе памяти сравниваем два представления:

```
$ vol.py -f mem.raw linux.lsmod.Lsmod
Address            Module       Size   Used
0xffff...a1c00000  nf_conntrack ...
...
$ vol.py -f mem.raw linux.check_modules.Check_modules
(модуль evil.ko найден сканом, но отсутствует в lsmod)
```

Скан ищет структуры модулей по сигнатурам и адресам, а не по списку. Поэтому находит то,
что список потерял. **Расхождение** — доказательство сокрытия.

## Шаг 2: не только Linux

В Windows аналог — `windows.modules.Modules` (список) против
`windows.modscan.ModScan` (скан). В macOS — список kext против скана по памяти. Принцип
один: список ведёт ядро, скан читает память.

## Шаг 3: косвенные признаки

Даже если модуль скрыт, он «светится» косвенно:

- **занятая память**: скан показывает регион, не принадлежащий ни одному известному модулю;
- **ссылки из других структур**: драйвер регистрирует обработчики, устройства, таймеры —
  они ссылаются на код, которого «нет»;
- **строки**: в памяти остаются имена, пути, сообщения модуля.

Поэтому ищут не только сам модуль, но и то, что на него **ссылается**.

## Шаг 4: где смотреть дальше

После обнаружения скрытого модуля важно:

- выяснить, что он делает (дизассемблировать код из дампа);
- найти точку его загрузки (как он попал в ядро — автозапуск, драйвер, эксплойт);
- проверить, не прячет ли он ещё что-то (процессы, файлы, сетевые соединения).

## Что мы теперь знаем

- `lsmod`/`/proc/modules` — это связанный список, который можно подделать.
- Вырезание модуля из списка — разновидность DKOM.
- Скан памяти (`modscan`, `check_modules`) находит то, что список потерял.
- Расхождение списка и скана — признак руткита.
- Скрытый модуль выдаёт себя занятой памятью и ссылками из других структур.

## Если не сработало

- Модуль не находится и сканом? Возможно, он не загружен, а код внедрён иначе
  (shellcode в ядре, патч существующего драйвера).
- Скан шумит ложными срабатываниями? Сверяй адреса с картой памяти и известными модулями.
- Нет символов ядра? Используй подходящий профиль/символы, иначе адреса не сопоставить.

## Практика: ручное сравнение списка и скана

Автоматический `check_modules` хорош, но в CTF полезно понимать, что именно он делает.
Начнём с того, что список модулей в Linux — это `/proc/modules`, а каждый модуль в памяти
начинается со структуры `struct module`, в начале которой лежит имя модуля (поле `name`,
массив из 56 байт). Отсюда простой офлайн-скан дампа:

```
$ strings -a -t x mem.raw | grep -E '\.ko$' | sort -u
   ffffffff81a3c000 evil.ko
   ffffffff81a3c040 clean.ko
$ vol.py -f mem.raw linux.lsmod.Lsmod | awk '{print $2}' | sort -u
clean.ko
```

Имя `evil.ko` встречается в дампе как строка (кандидат в структуру `module`), но его нет в
выводе `lsmod`. Дальше проверяем, действительно ли это структура модуля, а не просто строка:
смотрим окрестность адреса и убеждаемся, что рядом лежат правдоподобные указатели
(на `kallsyms`, `struct module_kobject`, секции `.text`/`.data`).

## Таблица: структуры и инструменты по ОС

| ОС | Структура модуля | Список (лжёт) | Скан (правда) |
|---|---|---|---|
| Linux | `struct module` | `linux.lsmod` | `linux.check_modules`, `modscan` |
| Windows | `KLDR_DATA_TABLE_ENTRY` | `windows.modules` | `windows.modscan` |
| Windows (драйверы) | `_DRIVER_OBJECT` | `windows.driverscan` | `windows.drivermodule` |
| macOS | `kmod_info_t` | `mac.kext_list` | `mac.kext_scan` |

Логика одна: «список» — это то, что ядро само о себе рассказывает, а «скан» — независимый
поиск структур по памяти. **Расхождение между ними и есть улика.**

## Разбор реального руткита: как это выглядит на практике

Классический пример сокрытия модуля — техника, известная по руткитам вроде **Reptile** и
**Diamorphine**. Diamorphine при загрузке не только вырезает себя из списка `modules`, но и
перехватывает `sys_call_table`, чтобы скрывать файлы, процессы и порты. В памяти это видно
как комбинация нескольких аномалий:

- модуль есть в скане, но отсутствует в `lsmod`;
- указатели `sys_call_table[__NR_getdents64]` и `sys_call_table[__NR_kill]` указывают **не**
  в адрес оригинального обработчика, а в регион «безымянного» модуля;
- у модуля нет записи в `sysfs` (`/sys/module/...`), хотя объект `module` существует.

Поэтому при разборе дампа всегда сопоставляй три вещи: список модулей, скан структур и
таблицу системных вызовов. Совпадение аномалий по адресам снимает ложные срабатывания.

## Что делать с найденным модулем

Найдя адрес структуры скрытого модуля, извлекаем его код и метаданные:

```
$ vol.py -f mem.raw linux.dump_map --pid 0 2>/dev/null | grep -A2 evil
$ vol.py -f mem.raw linux.malfind.Malfind --dump-dir=out/
$ objdump -D -b binary -m i386:x86-64 out/module.0xffffffff81a3c000.bin | head -40
```

Дизассемблированный код покажет, что модуль делает: хукает вызовы, скрывает объекты,
крадёт данные. Затем ищем **точку загрузки**: автозапуск через `initramfs`, `modprobe.d`,
`/etc/modules`, systemd-юнит или эксплуатацию уязвимости ядра. Без этого нельзя ответить на
вопрос «как он снова окажется на машине после перезагрузки».

## Ограничения и подводные камни

- **Скан шумит.** `modscan` ищет по эвристике и на больших дампах выдаёт ложные кандидаты —
  всегда подтверждай структуру по связному содержимому, а не по одной строке имени.
- **Нет символов — нет адресов.** Без подходящего профиля (`linux.zip`/`--symbols`) часть
  сканов не сопоставит адреса с именами; результат придётся интерпретировать вручную.
- **Вырезание из списка — не единственный способ.** Код может быть внедрён в ядро без
  регистрации модуля (shellcode, патч чужого драйвера) — тогда `modscan` его не найдёт
  вообще, и искать нужно через `malfind`, аномальные исполняемые страницы и хуки.
- **Живая система vs дамп.** На живой системе руткит может «прятаться» и от твоих
  инструментов (перехват `read`/`getdents`); анализ делай по **снятому дампу**, а не по
  работающей машине.

## Порядок действий при подозрении на руткит

Когда есть подозрение, что в ядре работает скрытый код, действуй по чек-листу — так ничего
не забудешь и получишь воспроизводимый результат:

1. **Сними дамп памяти** до любых изменений (LiME/AVML на Linux, WinPmem/DumpIt на Windows).
2. **Определи профиль** (`banners.Banners`, `--symbols`) — без него адреса бессмысленны.
3. **Сравни список и скан** модулей (`lsmod` vs `check_modules`/`modscan`).
4. **Проверь таблицу системных вызовов** на хуки (`check_syscall`).
5. **Найди аномальные исполняемые регионы** (`malfind`, `linux.malfind`).
6. **Извлеки и дизассемблируй** код найденного модуля.
7. **Определи точку загрузки** (initramfs, modprobe.d, драйвер, эксплойт).
8. **Задокументируй** адреса, хеши, строки — чтобы результат был воспроизводим.

## Сравнение методов обнаружения

| Метод | Что находит | Слепое пятно |
|---|---|---|
| `lsmod` / список | легитимные модули | скрытые из списка |
| `modscan` / скан | структуры `module` в памяти | код без структуры модуля |
| `check_syscall` | хуки в `sys_call_table` | inline-хуки внутри функций |
| `malfind` | исполняемые анонимные регионы | код в легитимных модулях |
| `kallsyms` | адреса символов | подделанное содержимое |

Ни один метод не полон в одиночку: руткит обходит список, но выдаёт себя хуками; обходит
`sys_call_table`, но выдаёт себя inline-патчем. **Ценность в сопоставлении** — чем больше
источников совпало на одном адресе, тем достовернее находка.

## Как задокументировать находку

Для отчёта и для CTF важно зафиксировать не «нашёл руткит», а **проверяемые данные**:

- виртуальный и физический адрес структуры модуля;
- имя модуля и хеш (SHA-256) извлечённого кода;
- какие указатели `sys_call_table` изменены (индекс, было/стало);
- строки, вытащенные из региона (имена устройств, сообщения, пути);
- точку загрузки и время первой загрузки (из `dmesg`, если доступно).

Такой набор позволяет другому аналитику повторить вывод, а не поверить на слово. В CTF
именно эти детали (адрес, строка, хеш) чаще всего и есть «флаг» или путь к нему.

## Куда дальше

Скрытый модуль — частный случай сокрытия. Дальше посмотрим на общую технику **DKOM**:
как из структур ядра вырывают процессы и что показывает сравнение `pslist` и `psscan`. А
пока запомни: список модулей можно подделать, а скан памяти — нет.

## Где пригодится

- **CTF Forensics** — задачи со скрытыми драйверами.
- **DFIR / Incident Response** — поиск руткитов в дампах памяти.
- **Анализ руткитов** — понимание сокрытия через связанные списки.
