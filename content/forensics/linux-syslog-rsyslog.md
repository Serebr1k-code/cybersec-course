## Вопрос, с которого всё начинается

Ты открываешь `/var/log/syslog` — и видишь тысячи строк без явной структуры. Где тут
полезное, а где шум? Классический syslog читается не «сверху вниз», а по колонкам и
приоритетам. Разберём его анатомию.

## Наш пример: строка syslog

Возьмём одну строку:

```
Jan 14 03:12:44 web01 cron[2211]: (root) CMD (cd /tmp && ./update.sh)
```

## Шаг 1: разбираем поля

Слева направо:

- `Jan 14 03:12:44` — время (без года!);
- `web01` — имя хоста (hostname);
- `cron[2211]` — процесс и его PID;
- `(root) CMD (...)` — само сообщение.

Отсутствие года — важная ловушка. Если логи охватывают новый год, придётся
восстанавливать год по дате файла или по другим источникам.

## Шаг 2: приоритеты и facility

В сыром syslog приоритет обычно уже отфильтрован в отдельные файлы:
`auth.log`, `kern.log`, `mail.log`. Но при централизованном сборе приходит и число:

```
<134>Jan 14 03:12:44 web01 cron[2211]: ...
```

`134 = 16*8 + 6`. Первая часть — **facility** (16 = local0), вторая — **severity**
(6 = info). Severity идут от `0` (emerg) до `7` (debug). Для расследования важны
`0–4` (emerg/alert/crit/err).

## Шаг 3: находим подозрительный cron

Наша строка показывает, что root-крон запускает скрипт из `/tmp`. Это классический
persistence-приём: `/tmp` доступен на запись, скрипт легко подменить. Проверим:

```
$ grep -i 'CMD' /var/log/syslog | grep '/tmp'
Jan 14 03:12:44 web01 cron[2211]: (root) CMD (cd /tmp && ./update.sh)
Jan 14 04:12:44 web01 cron[2400]: (root) CMD (cd /tmp && ./update.sh)
```

Повторяется каждый час — значит, запись в crontab устойчивая.

## Шаг 4: rsyslog и централизация

В крупных системах логи отправляются на центральный сервер. Конфигурация — в
`/etc/rsyslog.conf` и `/etc/rsyslog.d/`:

```
$ grep -rE '^\*\.\*|@@|@' /etc/rsyslog.d/
*.* @@logserver.internal:514
```

`@@` — это TCP, `@` — UDP. Если логи уходили на центральный сервер, локальный файл
мог быть очищен, но копия осталась на сервере — это важнейшая зацепка.

## Шаг 5: сопоставление с journald

Современный Linux пишет и в бинарный journald. Сопоставим:

```
$ journalctl -u cron --since "2026-01-14 03:00" --until "2026-01-14 04:00"
Jan 14 03:12:44 web01 cron[2211]: (root) CMD (cd /tmp && ./update.sh)
```

journald хранит структурированные поля и не теряет год. Если syslog подчищен, а
journald нет — восстановишь картину.

## Полный прогон: разбор инцидента по syslog

Соберём картину из сырого syslog. Сначала сузим по времени и процессу:

```
$ awk '$1=="Jan" && $2=="14" && $3>="03:00:00" && $3<="04:00:00"' /var/log/syslog | grep -iE 'cron|sudo|su\[|useradd'
Jan 14 03:12:44 web01 cron[2211]: (root) CMD (cd /tmp && ./update.sh)
Jan 14 03:13:01 web01 sudo:   deploy : TTY=pts/0 ; PWD=/tmp ; USER=root ; COMMAND=/bin/bash
Jan 14 03:13:40 web01 useradd[2300]: new user: name=backdoor
```

Цепочка выстраивается сама: root-крон запускает скрипт из `/tmp`, пользователь `deploy` получает root через `sudo`, создаётся учётка `backdoor`. Три разных демона (`cron`, `sudo`, `useradd`) — три независимых подтверждения одной атаки.

Теперь проверим cron-запись подробнее:

```
$ grep -i 'CMD' /var/log/syslog | grep -c '/tmp'
360
```

360 запусков в час — значит, запись в crontab повторяется каждые 10 секунд, то есть это не разовая, а устойчивая закладка. Дальше смотрим, когда запись появилась:

```
$ grep -iE 'crontab|REPLACE' /var/log/syslog | head
Jan 14 03:11:50 web01 cron[2200]: (root) REPLACE (root)
```

`REPLACE (root)` — момент, когда root-овый crontab был заменён. Это точка внедрения.

## Facility и severity

| Facility | Число | Что это |
|---|---|---|
| kern | 0 | сообщения ядра |
| user | 1 | пользовательские процессы |
| mail | 2 | почта |
| daemon | 3 | системные демоны |
| auth/authpriv | 4/10 | аутентификация |
| cron | 9 | планировщик |
| local0–7 | 16–23 | прикладные нужды |

| Severity | Число | Значение |
|---|---|---|
| emerg | 0 | система неработоспособна |
| alert | 1 | требуется немедленное действие |
| crit | 2 | критическая ошибка |
| err | 3 | ошибка |
| warning | 4 | предупреждение |
| notice/info/debug | 5/6/7 | информационные |

`priority = facility*8 + severity`. Для расследования отбирают `0–4`; остальное — фон.

## Приоритеты, фильтры и rsyslog-правила

rsyslog маршрутизирует сообщения по `facility.severity` и действиям:

```
$ cat /etc/rsyslog.d/50-default.conf
auth,authpriv.*                 /var/log/auth.log
*.*;auth,authpriv.none          -/var/log/syslog
kern.*                          -/var/log/kern.log
*.emerg                         :omusrmsg:*
```

Читаем: аутентификация — в отдельный файл, всё остальное (кроме auth) — в `syslog`, ядро — в `kern.log`, `emerg` — всем пользователям. Знание этих правил объясняет, **почему** запись попала в тот или иной файл, и где её искать. Если инцидент связан с аутентификацией, а `auth.log` очищен, ищи ту же запись в централизованной копии.

## Форвардинг, шаблоны и потеря логов

При пересылке важно, что именно уходит на сервер:

```
*.* @@logserver.internal:514
$template RemoteLogs,"/var/log/remote/%HOSTNAME%/%PROGRAMNAME%.log"
*.* ?RemoteLogs
```

`@@` — TCP (надёжнее, с подтверждением), `@` — UDP (быстро, но теряется при перегрузке). При UDP-пересылке часть событий может просто **не дойти** до сервера — это надо учитывать, чтобы не принять потерю за отсутствие события. Шаблон `%HOSTNAME%` раскладывает логи по хостам, что критично в мультихостовой среде.

## Крайние случаи и ограничения

- **Нет года в метке.** Классический syslog пишет без года; при переходе через новый год восстановление года — отдельная задача.
- **Часовой пояс.** Время локальное; при сведении с UTC-источниками (сеть) нужен сдвиг.
- **UDP-потери.** Пересылка по UDP теряет события при перегрузке; «нет записи» ≠ «не было события».
- **Ротация.** События могут быть в `syslog.1`, `syslog.2.gz`; `zgrep` ищет внутри сжатых.
- **Подчистка.** `auth.log` правят чаще всего; `journald` и централизованная копия переживают её.

## Сопоставление syslog, journald и auth.log

Три источника дополняют друг друга:

| Источник | Формат | Особенность |
|---|---|---|
| `syslog` | текст | общий поток, много шума |
| `auth.log` | текст | только аутентификация, чистится чаще |
| `journald` | бинарный | структурированные поля, есть год |
| `wtmp`/`btmp` | бинарный | сессии и неудачные входы, чистятся редко |

Рабочий приём: нашёл событие в `syslog` — подтверди в `journald` и `wtmp`. Если запись есть только в одном источнике, а остальные молчат, это повод проверить подделку (см. урок про запутывание следов).

## Быстрые команды и чек-лист

Набор однострочников для работы с syslog:

```
# отфильтровать по времени и процессу
$ grep '^Jan 14 03:' /var/log/syslog | grep -iE 'cron|sudo|sshd'

# топ сообщений (нормализуем PID)
$ sed -E 's/\[[0-9]+\]/[PID]/' /var/log/syslog | awk '{$1=$2=$3=$4="";print}' | sort | uniq -c | sort -rn | head

# все записи cron с командой
$ grep -i 'CMD' /var/log/syslog

# включить и посмотреть централизованные логи
$ zgrep -i 'update.sh' /var/log/syslog.*.gz

# сопоставить с journald
$ journalctl --since "2026-01-14 03:00" --until "2026-01-14 04:00" -o short-precise
```

Чек-лист разбора инцидента по syslog:

1. Определи временное окно инцидента и нормализуй часовой пояс.
2. Отфильтруй по ключевым процессам: `cron`, `sudo`, `su`, `sshd`, `useradd`, `systemd`.
3. Проверь ротации и сжатые файлы — событие могло уйти в `.1` или `.gz`.
4. Найди централизованную копию (rsyslog-форвардинг) — она переживает локальную подчистку.
5. Сопоставь с `journald`, `wtmp`, `auth.log`.
6. Отдели шум от сигнала: успех важнее тысяч неудач, аномальная команда важнее рутины.

## Сводка по источникам журналирования

Классический syslog — это **текстовый, плоский, децентрализованный** журнал: каждый демон пишет строки, приоритет определяет маршрут, год отсутствует, а централизация через rsyslog создаёт независимую копию. journald — **бинарный, структурированный**, с годом и полями, но живёт локально. `wtmp`/`btmp` — **бинарные** записи о сессиях и неудачных входах, которые чистят реже всего. Ни один из них не полон в одиночку. Рабочий метод — сопоставление: событие, подтверждённое несколькими источниками, считается установленным; событие из единственного источника проверяется на подделку. Именно поэтому в хорошо настроенной системе логи уходят на центральный сервер, где их не может тронуть локальный атакующий.

## Что запомнить

syslog читают не сверху вниз, а по колонкам и приоритетам: время, хост, процесс с PID, сообщение. Помни про отсутствие года, про маршрутизацию через `facility.severity` и про централизованную копию, которая переживает локальную подчистку. Событие считается установленным только при согласии нескольких источников.

## Что мы теперь знаем

- Формат syslog: время, хост, процесс[PID], сообщение.
- Года нет — восстанавливай по контексту.
- Facility × 8 + severity = число приоритета; важны 0–4.
- `@@`/`@` в rsyslog = пересылка на центральный сервер.
- journald — второй, бинарный источник; сопоставляй оба.

## Если не сработало

- Файл пуст? Проверь ротацию и `/var/log/remote/` на центральном сервере.
- Только journald? Используй `journalctl --output=json`.
- Время не сходится? Учти часовой пояс и `timedatectl`.
