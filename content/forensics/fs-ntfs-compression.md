## Вопрос, с которого всё начинается

Ты копируешь файл с NTFS-образа и получаешь **меньший размер**, чем ожидалось, или наоборот
— файл «весит» гигабайты, но реально занимает килобайты. Обычные средства показывают одно,
а данные — другое. Причина в **сжатии и разрежённости**: NTFS умеет хранить данные не так,
как они выглядят снаружи.

## Что такое сжатие в NTFS

В NTFS у каждого файла есть **атрибут данных** (`$DATA`), в котором лежат **data runs** —
списки диапазонов кластеров. Обычно run указывает на реальные кластеры. Но есть два
специальных случая:

- **Сжатие (compression).** Файл сжат алгоритмом **LZNT1**, а в атрибуте выставлен флаг
  `COMPRESSED` (0x800). Данные делятся на **units сжатия** по 16 кластеров (64 КБ при
  кластере 4 КБ). Каждый unit сжимается отдельно.
- **Разреженность (sparse).** Флаг `SPARSE` (0x8000). Диапазоны нулей не хранятся на
  диске вовсе — run помечает их как «дырки».

Обе техники экономят место, но ломают наивное «прочитать файл по кластерам»: часть кластеров
содержит упакованные или вовсе отсутствующие данные.

## Наш пример: подозрительный файл

```
$ ls -la secret.dat
-rw-r--r-- 1 student student 131072 secret.dat
$ file secret.dat
secret.dat: data
```

`file` не узнаёт формат — типично для LZNT1-потока (это не самодостаточный формат с
магией, а поток сжатых блоков). Заглянем в содержимое:

```
$ xxd -l 32 secret.dat
00000000: 1f00 0500 0010 0000 5a4e 5446 4c5a 4e54  ........ZNTFLZNT
00000010: 3100 756e 6974 3d313620 636c 7573 7465  1.unit=16 cluste
```

Мы видим упоминание **LZNT1** и параметр `unit=16 cluster`. В реальном NTFS это лежало
бы в атрибуте `$DATA`, но для разбора нам важен сам факт сжатия. Посмотрим метки:

```
$ strings secret.dat | grep -Ei 'LZNT1|Wof|sparse|nto'
LZNT1 compressed stream
WofCompressedData alternative stream present
SPARSE run: 12 clusters not allocated
EVIDENCE: nto{ntfs_lznt1_w0f_sp4rs3}
```

Три подсказки сразу: классический LZNT1, системное сжатие через **WOF** и разрежённые run-ы.
Разберём каждую.

## Шаг 1: unit сжатия — почему «частично сжатый»

Ключевая деталь: NTFS сжимает файл **блоками по 16 кластеров**, а не целиком. Каждый unit
независим. Если unit сжался — он записан компактно; если нет — записан как есть. Поэтому
один файл может быть **частично сжатым**. Это объясняет странные размеры: файл из 100
кластеров может занимать 40, если 60 % unit-ов сжались хорошо.

| Флаг атрибута | Значение | Смысл |
|---------------|----------|-------|
| `COMPRESSED` 0x0800 | файл сжат LZNT1 | data runs указывают на сжатые units |
| `SPARSE` 0x8000 | разрежённый файл | дырки не занимают кластеры |
| `ENCRYPTED` 0x4000 | зашифрован (EFS) | данные зашифрованы |

## Шаг 2: WOF — системное сжатие Windows

Начиная с Windows 10 появилось **WOF (Windows Overlay Filter)** — «системное сжатие»
(CompactOS). Оно работает иначе: файл **не** сжат в `$DATA`. Вместо этого:

- в `$DATA` лежит маленький «заглушечный» файл-манифест;
- сжатые данные хранятся в **альтернативном потоке** `:WofCompressedData`;
- атрибут данных помечен как **reparse point**, который перенаправляет чтение в фильтр WOF.

Для аналитика это ловушка: если читать только основной `$DATA`, ты увидишь «пустышку».
Настоящие данные — в `:WofCompressedData`. Поэтому при извлечении важно смотреть **все
потоки файла**, а не только безымянный.

## Шаг 3: чем извлекать

- **`ntfs-3g`** (Linux) — читает сжатые и разрежённые файлы прозрачно при монтировании;
- **The Sleuth Kit** — `icat` умеет отдавать поток; для ADS указывай имя потока
  (`icat image inode WofCompressedData`);
- **MFTECmd / MFT Explorer** — показывают флаги `$DATA` и наличие потоков;
- **`ntfs-3g` + `ntfsinfo`** — показывают флаги `COMPRESSED`/`SPARSE` и data runs;
- **7-Zip / `ntfsdump`** — иногда распаковывают LZNT1 вручную.

Пример:

```
$ ntfsinfo -f image.dd 42 | grep -i -A2 'Attribute: DATA'
Attribute: DATA
    Flags: Compressed | Sparse
    Name: $WofCompressedData
```

## Шаг 4: разрежённые файлы и «дырки»

Разрежённый файл (`SPARSE`) — частый приём при передаче больших образов: диск кажется
занятым, а реально пуст. При копировании образа **не сохраняй «дырки» как нули** —
используй образы, поддерживающие разрежённость (или `dd conv=sparse`). Иначе гигабайты
нулей раздуют файл и исказят хеши.

Важно: в разрежённом файле **нули не равны отсутствию данных**. Отсутствующий run означает
«здесь ноль», а не «здесь не прочитано». Не путай повреждение образа с разрежённостью.

## Шаг 5: сопоставление с `$MFT`

Чтобы понять, сжат ли файл, смотри запись MFT: флаги атрибута `$DATA` и его **data runs**.
У сжатого файла runs короткие и «рваные» (unit-ы), у разрежённого — с пропусками в VCN
(virtual cluster number). Инструмент `MFTECmd` выводит это в удобной таблице.

## Частые ошибки и подводные камни

- **Чтение только `$DATA`.** Пропустишь `:WofCompressedData` — и получишь пустышку.
- **Ожидание «целиком сжатого» файла.** Сжатие по units означает частичное сжатие.
- **Потеря разрежённости при копировании.** `dd` без `conv=sparse` раздувает образ.
- **Неверный алгоритм.** LZNT1 ≠ zlib/gzip; не пытайся распаковать «универсально».
- **EFS поверх сжатия.** Флаг `ENCRYPTED` означает, что данные ещё и зашифрованы —
  нужен ключ EFS.

## Что мы теперь знаем

- NTFS сжимает файлы алгоритмом LZNT1 блоками по 16 кластеров (unit).
- Разрежённые файлы (`SPARSE`) не хранят нулевые диапазоны.
- WOF/CompactOS хранит сжатые данные в потоке `:WofCompressedData`, а `$DATA` — манифест.
- Извлекать надо все потоки; монтирование `ntfs-3g` читает сжатие прозрачно.
- Флаги атрибута `$DATA`: `COMPRESSED`, `SPARSE`, `ENCRYPTED`.

## Что фиксировать в отчёте

| Что | Зачем |
|-----|-------|
| Флаги `$DATA` файла | сжат / разрежён / зашифрован |
| Наличие потока `WofCompressedData` | системное сжатие |
| Размер логический vs физический | объяснить «странные» размеры |
| Метод извлечения и инструмент | воспроизводимость |
| Хеш извлечённого содержимого | целостность |

## Мини-практика: извлекаем поток WOF и сверяем размеры

Пусть у нас образ NTFS и известно, что файл сжат через WOF. Смотрим потоки записи MFT:

```
$ icat -f ntfs image.dd 42 > manifest.bin
$ icat -f ntfs image.dd 42 WofCompressedData > compressed.bin
$ ls -la manifest.bin compressed.bin
-rw-r--r-- 1 student student     4096 manifest.bin
-rw-r--r-- 1 student student  1048576 compressed.bin
```

Обрати внимание: основной поток — 4 КБ «пустышка», а реальные данные (мегабайт) лежат в
`WofCompressedData`. Если бы мы извлекли только `$DATA`, то получили бы манифест и решили,
что файл пуст. Именно так теряются доказательства.

Проверим флаги через `ntfsinfo`:

```
$ ntfsinfo -f image.dd 42 | grep -iE 'Flags|Name'
Flags: Compressed
Name: $WofCompressedData
```

Флаг `Compressed` в сочетании с потоком `WofCompressedData` — верный признак системного
сжатия. Для классического LZNT1 флага `Compressed` достаточно, а потока не будет.

## Сжатие и хеши: почему размеры не сходятся

Частая путаница при верификации доказательств: **логический размер** (сколько байт в
файле) и **физический размер** (сколько кластеров занято на диске) различаются для сжатых
и разрежённых файлов. Хеш считается по **логическому** содержимому — то есть по тому, что
вернёт чтение файла, а не по сырым кластерам.

Практические следствия:

- **Хеш сырых кластеров ≠ хеш файла.** Если хешировать только выделенные кластеры, для
  сжатого файла получишь другое значение. Всегда извлекай файл «как файл».
- **Разрежённые образы.** При копировании диска с разрежённостью используй инструмент,
  сохраняющий «дырки» (`dd conv=sparse`, `ewfacquire`). Иначе хеш образа изменится, хотя
  данные те же.
- **Сравнение с эталоном.** Если у тебя есть оригинал файла, сверяй SHA-256 **после**
  корректного извлечения, а не по кластерам.
- **Частичное сжатие.** Один файл может занимать разное число кластеров в зависимости от
  того, какие unit-ы сжались; не удивляйся «неровному» расходу.

Правило простое: **сжатие и разрежённость — это про то, как байты лежат на диске, а не про
то, что в файле**. Разделяй эти понятия — и хеши сойдутся.

## Куда дальше

Мы разобрали сжатие и разрежённость NTFS. Дальше разберём **семантику таймстемпов NTFS** —
почему `$STANDARD_INFORMATION` и `$FILE_NAME` могут расходиться и что это доказывает. А
пока главное запомни: **смотри все потоки и флаги `$DATA` — иначе данные «исчезнут»**.

## Где пригодится

- **CTF Forensics:** образы, где «пустой» файл на деле содержит данные.
- **DFIR:** корректное извлечение сжатых артефактов Windows.
- **Data recovery:** не потерять данные при копировании разрежённых образов.
- **Anti-forensics:** понимание, как данные можно спрятать в потоках.
