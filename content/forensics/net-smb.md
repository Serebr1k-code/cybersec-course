## Вопрос, с которого всё начинается

В корпоративной сети файлы ходят по **SMB**. В дампе — гигабайты трафика, и где-то
среди них переданный документ или эксфильтрованный архив. Как достать файл прямо из
сети? Разберём.

## Наш пример: SMB-сессия

## Шаг 1: узнаём протокол

```
$ tshark -r capture.pcap -Y 'smb2' -c 3
  1  ... SMB2 Negotiate Protocol Request
  2  ... SMB2 Negotiate Protocol Response
```

SMB2 (порт 445) — современный обмен файлами Windows. SMB1 (порт 139) — устаревший, но
встречается на старых системах.

## Шаг 2: что делали

```
$ tshark -r capture.pcap -Y 'smb2.cmd==5' -T fields -e smb2.filename | sort -u | head
\\secret\finance\report.xlsx
\\secret\finance\archive.zip
```

`smb2.cmd==5` — это Create (открытие файла). Так видно, какие пути открывали. Список
файлов — уже ценный результат.

## Шаг 3: извлекаем файлы

Для SMB есть готовые экспортеры:

```
$ tshark -r capture.pcap --export-objects smb,./exported/ 2>/dev/null
$ ls ./exported/
report.xlsx  archive.zip
```

`--export-objects smb` собирает переданные объекты. Если трафик не шифрован (SMB3 с
шифрованием усложняет), файлы достаются целиком.

## Шаг 4: сопоставляем с хостом

Кто обращался:

```
$ tshark -r capture.pcap -Y 'smb2' -T fields -e ip.src -e ip.dst | sort | uniq -c | sort -rn | head
```

Пара «кто → к какому серверу» показывает боковое перемещение. Частое обращение к
админским шарам (`C$`, `ADMIN$`) — признак атаки.

## Шаг 5: следы на сервере

Если сервер доступен, там свои логи:

```
$ grep -i 'report.xlsx' /var/log/samba/*.log
```

А в Windows — Security Event Log (5140/5145) фиксирует доступ к объектам.

## Что мы теперь знаем

- SMB2 — порт 445, современный файловый обмен.
- `smb2.cmd==5` показывает открытые файлы.
- `tshark --export-objects smb` извлекает переданные файлы.
- Обращение к `C$`/`ADMIN$` — признак атаки.
- Серверные логи дублируют доступ.

## Если не сработало

- SMB3 с шифрованием? Нужны ключи сессии.
- Файл не экспортируется? Проверь, не сжат ли он (compression).
- Нужны метаданные? Ищи NTFS-артефакты на сервере.

## Протокол SMB и его версии

SMB (Server Message Block) — протокол обмена файлами и принтерами в Windows-сетях. Важные
факты:

- порт **445** (SMB напрямую по TCP) и **139** (старый, через NetBIOS);
- диалекты: SMB1 (устаревший, уязвимый), SMB2, SMB3 (шифрование, подпись);
- аутентификация: NTLM или Kerberos;
- операции: `TREE_CONNECT` (подключение к шаре), `CREATE` (открытие файла), `READ`/`WRITE`.

```
$ tshark -r smb.pcap -Y 'smb2' -T fields -e frame.time -e ip.src -e ip.dst -e smb2.cmd | head
2026-01-14 03:20:11  10.0.0.57  10.0.0.10  3      # TREE_CONNECT
2026-01-14 03:20:12  10.0.0.57  10.0.0.10  5      # CREATE
2026-01-14 03:20:13  10.0.0.57  10.0.0.10  8      # READ
```

Число в `smb2.cmd` — код операции. По последовательности видно, что клиент подключался к
шаре и читал файлы.

## Что делали: восстанавливаем операции

Из дампа вытаскиваем имена файлов и шары:

```
$ tshark -r smb.pcap -Y 'smb2.filename' -T fields -e smb2.filename | sort -u
\srv\share\secret.xlsx
\srv\share\payroll\2026.docx
```

Фильтр `smb2.filename` показывает пути, к которым обращались. Так строится список
**прочитанных и записанных** файлов. Для записи смотри `smb2.cmd == 9` (WRITE) и
соответствующие пути.

## Извлечение файлов из дампа

Wireshark и tshark умеют реконструировать переданные файлы:

```
$ tshark -r smb.pcap --export-objects smb,out/ 
$ ls out/
secret.xlsx  2026.docx  ...
```

Извлечённые объекты можно хешировать и передать на анализ. Так восстанавливается содержимое
файлов, даже если на диске их уже нет — сетевой захват хранит сами данные.

## Аутентификация в захвате

SMB-сессии содержат **NTLMSSP**-сообщения с именами пользователей, доменами и хешами
ответов (не паролями). Из дампа достаётся логин:

```
$ tshark -r smb.pcap -Y 'ntlmssp.auth.username' -T fields -e ntlmssp.auth.username -e ntlmssp.auth.domain
svc_backup  CORP
```

Имя пользователя и домен — важная атрибуция. NTLM-ответ можно использовать для
офлайн-перебора, но это уже активное действие, требующее отдельного согласования.

## Следы на сервере

Если есть доступ к серверу, смотри его журналы. На Windows:

- **Event 5140** — доступ к сетевой шаре (кто, к какой);
- **Event 5145** — детальный доступ к объекту (файл, тип доступа);
- **Event 4624** — вход (тип 3 — сетевой).

На macOS/Linux с Samba — логи `smbd`:

```
$ grep -E 'connect to service|opened file' /var/log/samba/log.* | tail
```

Серверные логи показывают **обе стороны**: и что запрашивали, и что было отдано.

## Таблица: SMB-артефакты и их ценность

| Артефакт | Источник | Что даёт |
|---|---|---|
| TREE_CONNECT | дамп | к какой шаре подключились |
| CREATE / filename | дамп | какие файлы открывали |
| WRITE | дамп | что загружали на сервер |
| NTLMSSP username | дамп | кто (логин, домен) |
| Event 5140/5145 | сервер | детальный аудит доступа |
| smbd logs | Samba | операции файловой системы |
| Файлы из export | дамп | содержимое переданного |

## Ограничения

Во-первых, SMB3 умеет **шифрование** — тогда в дампе только зашифрованный трафик, и нужен
ключ сессии. Во-вторых, большие передачи могут быть **фрагментированы** и не полностью
попасть в захват. В-третьих, на сервере аудит доступа включается не всегда — по умолчанию
многие события выключены. В-четвёртых, NTLM-хеши требуют GPU для перебора и часто
непрактичны. И учитывай, что имена пользователей в SMB могут быть **служебными учётками**,
а не людьми.

## Если сработало: цепочка доступа

Для отчёта нужно показать: кто (логин из NTLM), к какой шаре подключился (TREE_CONNECT),
какие файлы открыл/скачал (filename, WRITE) и когда. Содержимое извлечённых файлов — это уже
доказательство утечки. Соединяй сетевой захват с серверными логами: два независимых
источника надёжнее одного.

## Восстановление сессии шаг за шагом

SMB-сессия разворачивается в понятную последовательность. Разберём её по дампу:

1. **Negotiate** — согласование диалекта (SMB2/3);
2. **Session Setup** — аутентификация (NTLM/Kerberos);
3. **TREE_CONNECT** — выбор шары (`\\server\share`);
4. **CREATE** — открытие файла по пути;
5. **READ/WRITE** — чтение или запись данных;
6. **CLOSE** — закрытие.

```
$ tshark -r smb.pcap -Y 'smb2.cmd' -T fields -e frame.number -e smb2.cmd -e smb2.filename | head
1  0  -
2  1  -
3  3  -
4  5  \srv\share\payroll.xlsx
5  8  \srv\share\payroll.xlsx
6  6  -
```

Каждый код операции (`smb2.cmd`) — шаг. По этой цепочке восстанавливается, что именно
происходило, даже без содержимого файлов.

## Различаем чтение и запись

Ключевой вопрос расследования: файл **скачали** (утечка) или **загрузили** (внедрение)?
Смотрим направление данных:

- `READ` (`cmd 8`) с ответом большого размера — сервер отдаёт данные клиенту;
- `WRITE` (`cmd 9`) от клиента к серверу — клиент заливает файл.

```
$ tshark -r smb.pcap -Y 'smb2.cmd == 9' -T fields -e ip.src -e smb2.filename | sort -u
10.0.0.57  \srv\share\payload.exe
```

Запись `payload.exe` на сервер с рабочей станции — почти наверняка **доставка полезной
нагрузки** (lateral movement). Обратный случай (READ `payroll.xlsx`) — утечка.

## Скрытые и админские шары

Помимо обычных, SMB имеет **административные шары** с суффиксом `$`:

- `C$`, `ADMIN$` — доступ к системному диску и `%SystemRoot%`;
- `IPC$` — межпроцессное взаимодействие (используется для анонимных перечислений).

```
$ tshark -r smb.pcap -Y 'smb2.tree' -T fields -e smb2.tree | sort -u
\\10.0.0.10\C$
\\10.0.0.10\ADMIN$
```

Подключение к `C$`/`ADMIN$` — сильный признак удалённого администрирования (легитимного или
атакующего). Само по себе это не малварь, но в сочетании с записью файла в `ADMIN$` —
классический признак **PsExec-подобного** перемещения.

## Сопоставление с хостом

Сетевой захват даёт стороны и операции, но не объясняет **зачем**. Соединяем с артефактами
на хосте:

| В дампе | На хосте | Вывод |
|---|---|---|
| TREE_CONNECT к `C$` | служба PsExec, Event 7045 | удалённый запуск |
| WRITE `payload.exe` | файл в `ADMIN$`, процесс | доставка |
| READ `payroll.xlsx` | доступ через Explorer | утечка |
| NTLM-логин `svc_backup` | учётка с правами | атрибуция |

Так «файл был передан» превращается в «атакующий с учёткой X доставил нагрузку на хост Y».

## Таблица: коды операций SMB2

| Код | Операция | Значение |
|---|---|---|
| 0 | NEGOTIATE | согласование |
| 1 | SESSION_SETUP | аутентификация |
| 3 | TREE_CONNECT | подключение к шаре |
| 4 | TREE_DISCONNECT | отключение |
| 5 | CREATE | открытие файла |
| 6 | CLOSE | закрытие |
| 8 | READ | чтение |
| 9 | WRITE | запись |

## Ограничения

SMB3-шифрование делает содержимое недоступным без ключа сессии; в этом случае доступны лишь
метаданные (объём, время). Фрагментированные передачи могут не собраться полностью. На
сервере аудит доступа часто выключен, а логи Samba не всегда детальны. И не забывай про
**ложные срабатывания**: легитимные бэкапы и файловые серверы выглядят как массовый обмен.
Всегда проверяй, есть ли у учётки основание для доступа.

## Если сработало: что фиксировать

Приведи: учётку (NTLM/Kerberos), шару, список файлов с направлением (чтение/запись) и время.
Если есть извлечённое содержимое — хеши и результаты анализа. Это позволяет отличить утечку
от внедрения — принципиально разные выводы для реагирования.
