## Вопрос, с которого всё начинается

Тебе дали файл `broken.png` — картинку, которую ни один просмотрщик не открывает.
Ошибка на ошибке. Файл вроде бы не пустой, но «сломан». Как понять, что именно не
так, и починить, **не имея исходника**?

Когда автоматика не справляется — нестандартный формат, повреждённый заголовок, байты,
спрятанные после конца данных, — ты открываешь файл и читаешь **байты напрямую**.
Это и есть работа с hex-редактором.

## Наш пример: broken.png, который не открывается

Сначала — что о файле говорит система:

```bash
$ file broken.png
broken.png: PNG image data, 800 x 600, 8-bit/color RGBA, non-interlaced
```

`file` определил формат — значит, сигнатура на месте, но что-то испорчено дальше.
Смотрим первые байты вручную:

```bash
$ xxd -l 16 broken.png
00000000: 89 50 4e 47 0a 0d 1a 0a 00 00 00 0d 49 48 44 52  .PNG........IHDR
```

## Шаг 1: как читать hex-дамп

`xxd` показывает файл в виде строк: адрес (слева), байты в **шестнадцатеричном** виде
(каждый байт — два знака) и их ASCII-отображение (справа, точки вместо непечатаемых).
Один байт = два hex-знака. Так видно и сигнатуры, и длины, и смещения.

Правильная сигнатура PNG — `89 50 4E 47 0D 0A 1A 0A`. А в нашем файле после
`89 50 4E 47` идёт `0A 0D` вместо `0D 0A`. **Байты переставлены** — вот почему
просмотрщик падает. Файл «сломан» ровно в четырёх байтах.

## Шаг 2: инструменты для просмотра

В консоли достаточно двух команд. У `xxd` (входит в состав vim, есть почти везде)
полезны такие флаги:

| Флаг | Назначение |
|------|-----------|
| `-l N` | показать первые N байт |
| `-s OFFSET` | начать со смещения (`-s -N` — от конца) |
| `-c N` | N байт в строке (по умолчанию 16) |
| `-g N` | группировать по N байт |
| `-p` | только hex, без адресов и ASCII |
| `-r` | обратное преобразование: hex → бинарь |

У `hexdump` канонический вид даёт флаг `-C`:

```bash
$ hexdump -C broken.png | head -2
00000000  89 50 4e 47 0a 0d 1a 0a  00 00 00 0d 49 48 44 52  |.PNG........IHDR|
```

Для больших образов используйте `-s`/`-l`, чтобы открыть только нужный диапазон.

## Шаг 3: правим байты

Работаем **только с копией** — оригинал улики не трогаем:

```bash
$ cp broken.png fixed.png
$ printf '\x89PNG\r\n\x1a\n' | dd of=fixed.png bs=1 count=8 conv=notrunc
$ file fixed.png
fixed.png: PNG image data, 800 x 600, 8-bit/color RGBA, non-interlaced
```

`printf '\x89PNG\r\n\x1a\n'` создаёт правильные восемь байт сигнатуры, `dd` записывает
их в начало файла. Флаг `conv=notrunc` обязателен: без него `dd` **обрезал** бы файл
до восьми байт и уничтожил остальное. Файл открывается.

## Шаг 4: убеждаемся, что изменили только нужное

```bash
$ cmp -l broken.png fixed.png
     5 012 015
     6 015 012
```

`cmp -l` перечисляет отличия: позиция (нумерация с 1) и два байта в восьмеричном виде.
Изменились ровно байты 5 и 6 — те, что мы и хотели. Это и доказательство правки, и
страховка от «задели лишний байт».

## Шаг 5: hex нужен не только для починки

Часто задача — **найти**, а не исправить. Сигнатуры ищут по смещению:

```bash
$ grep -aboP '\x89PNG' disk.img
$ xxd -p file.bin | tr -d '\n' | grep -bo '504b0304'
```

Первая команда находит все вхождения сигнатуры PNG в образе с их смещениями (это
пригодится при **carving** — извлечении файлов). Вторая переводит файл в одну строку
hex и ищет сигнатуру ZIP (`50 4B 03 04`).

## Шаг 6: когда нужны структурные шаблоны

Вручную сопоставлять сотни байт с полями формата утомительно. На помощь приходят
редакторы со **структурными шаблонами**: `010 Editor`, `ImHex`, `Kaitai`. Ты
описываешь структуру формата один раз —

```
struct PNG {
    uint64 signature;          // 89 50 4E 47 0D 0A 1A 0A
    uint32 length;             // длина чанка
    char   type[4];            // например IHDR
    byte   data[length];
    uint32 crc;
}
```

— и редактор сам подсвечивает поля, показывает значения и позволяет переходить по
структуре. Это ускоряет разбор PE-заголовков, записей MFT, чанков PNG в разы.

## Ниже байта: биты и XOR

Иногда данные прячут в отдельных битах или «шифруют» простым XOR — побитовым
исключающим «или». Ключ может быть один байт или повторяющаяся строка:

```bash
$ xxd -b -l 8 image.png        # битовое представление первых байт
$ python3 -c "d=open('enc.bin','rb').read();print(bytes(b^0x42 for b in d))" > dec.bin
```

Типичная «матрёшка» CTF: hex → base64 → XOR → gzip. Разворачивать слои удобно в
`CyberChef` — там эти операции собираются в цепочку мышкой.

## Проверка целостности при правке

После любой правки убедитесь, что не задели лишнее. Кроме `cmp -l` помогают:

```bash
$ sha256sum original.bin fixed.bin
$ xxd -s 4 -l 4 fixed.bin
00000004: 0d 0a 1a 0a                                ....
```

Первый вывод покажет, что хеши разные (файл действительно изменён), второй — что
нужные байты на месте. Так правка становится доказуемой: видно и факт изменения, и его
точные границы.

## Ищем данные после конца формата

Частый приём — спрятать файл или флаг **после** логического конца формата. У PNG
данные заканчиваются маркером `IEND`; всё, что лежит дальше, — подозрительно:

```bash
$ grep -aboP 'IEND' image.png
   8123:IEND
$ xxd -s 8127 image.png | head -2
00001fbf: 50 4b 03 04 14 00 00 00 08 00              PK........
```

Первая команда находит смещение конца, вторая показывает содержимое после него. А там
`50 4b 03 04` — сигнатура ZIP: внутри картинки спрятан архив. Так hex-анализ находит
«вклеенные» данные, которые не видны при обычном открытии.

## Большие образы: работаем диапазонами

Гигабайтный образ в GUI тормозит и опасен случайной записью. Открывайте только нужный
кусок:

```bash
$ xxd -s 1048576 -l 64 disk.img       # 64 байта с отметки 1 МиБ
$ dd if=disk.img of=chunk.bin bs=1 skip=1048576 count=4096
$ grep -aboP 'PK\x03\x04' disk.img | head
```

`-s` задаёт смещение, `dd ... skip` вырезает фрагмент, а потоковый `grep` ищет сигнатуру
по всему образу, не загружая его целиком в память.

## На что смотреть дальше

- **Правьте только копию** и фиксируйте хеш до и после.
- **Порядок байтов (endianness)** — длина и CRC читаются по-разному на разных ФС.
- **Большие образы** — не открывайте целиком в GUI; ищите `grep -aboP` потоково.
- **Лишние данные после конца файла** — проверьте, нет ли байт после сигнатуры `IEND`.

## Куда дальше

Мы научились читать и править байты одного файла. Но образ диска — это не один файл, а
целая **структура**: таблица разделов, файловые системы, каталоги. В следующем уроке
мы разберём таблицу разделов MBR/GPT и поймём, где именно на диске начинается
нужный раздел. А пока запомни: **правишь — только копию, и фиксируй хеш**.

## Где пригодится

- **CTF:** правка magic-байтов, XOR-декод, поиск appended data.
- **Malware analysis:** разбор заголовков PE/ELF вручную, патчинг анти-анализа.
- **Восстановление данных:** исправление повреждённых структур.
- **Reverse engineering:** понимание форматов, ручное патчирование.
- **Incident Response:** извлечение фрагментов из больших дампов по смещению.
