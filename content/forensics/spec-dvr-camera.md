## Вопрос, с которого всё начинается

Нужно установить, что происходило у входа. Записи — на **DVR/NVR** или IP-камере.
Устройство своё, файловая система проприетарная, видео может быть удалено. Разберём,
как достать записи.

## Наш пример: NVR с диском

## Шаг 1: носитель

DVR/NVR хранит записи на HDD, часто в проприетарной ФС:

```
$ fdisk -l /dev/sdb
Disk /dev/sdb: 2 TiB
/dev/sdb1  2048  4294967295  Linux filesystem
```

`file -s /dev/sdb1` может показать `ext4`, `xfs` или вендорный формат. Некоторые
вендоры используют **собственные** форматы — тогда монтировать не получится.

## Шаг 2: штатный экспорт

Самый чистый способ — экспорт через интерфейс устройства:

- веб-интерфейс → выбрать интервал → скачать `.mp4`/`.dav`;
- USB-экспорт;
- вендорная утилита (Hikvision/Dahua).

Это даёт корректные файлы с метаданными.

## Шаг 3: извлечение с диска

Если устройство не работает, снимаем диск и анализируем:

```
$ ddrescue /dev/sdb dvr.img dvr.map
$ binwalk -e dvr.img
```

`binwalk` находит видео-потоки и БД внутри образа. Некоторые вендоры хранят записи
как поток с индексной базой.

## Шаг 4: восстановление удалённого

Записи циклически перезаписываются. Удалённые фрагменты ищут карвингом по сигнатурам
(H.264/H.265) или по индексам БД:

```
$ foremost -t mp4 -i dvr.img -o out/
```

Индексная база может сохранить **время и длительность** удалённых записей, даже если
сам видеофайл затёрт.

## Шаг 5: метаданные и время

Ключевое — **правильное время**. Камеры часто хранят время в UTC/локальном/с дрейфом.
Сверяй по событиям и другим источникам.

## Что мы теперь знаем

- DVR/NVR — свой носитель и часто своя ФС.
- Штатный экспорт даёт корректные файлы.
- С диска — `ddrescue` + `binwalk`.
- Удалённое восстанавливают карвингом и по индексам.
- Время камер надо верифицировать.

## Если не сработало

- Проприетарный формат? Используй вендорную утилиту.
- Диск зашифрован? Нужны ключи устройства.
- Нужен интервал? Индексная БД подскажет, где он на диске.

## Внутреннее устройство NVR: чанки и индекс

Большинство сетевых регистраторов (NVR) пишут видео не как «файлы по дням», а как поток
**чанков** (сегментов) фиксированной длительности — обычно 30–60 минут. Каждый чанк
получает запись в индексной базе, где указаны: время начала и конца, камера, тип события
(непрерывная запись, движение, тревога) и физическое расположение чанка на диске. Именно
поэтому для расследования индекс важнее самого видео: даже если чанк перезаписан, строка в
индексе может сохранить **время и факт** события.

Типичная структура на диске:

```
$ ls /mnt/nvr/
  ├─ index/        # БД сегментов (часто SQLite или проприетарная)
  ├─ data/         # сами чанки (raw H.264/H.265 или контейнеры)
  ├─ log/          # журнал событий и тревог
  └─ snapshot/     # кадры-превью по событиям
```

## Вендорные форматы: что монтируется, а что нет

| Вендор | Формат на диске | Чем снять |
|---|---|---|
| Hikvision | проприетарный, чанки + индекс | iVMS-4200, `binwalk`, карвинг |
| Dahua | `.dav` контейнеры | Smart Player, конвертер `.dav`→`.mp4` |
| Xiongmai (XM) | «.h264» в каталогах по дням | прямая конкатенация + `ffmpeg` |
| Китайские OEM | часто ext4/xfs | монтирование только для чтения |
| Axis | open-стандарт, RTSP/ONVIF | штатный экспорт |

Для Dahua `.dav` — это контейнер с заголовками, поэтому простое переименование в `.mp4`
не работает; нужен `dahua-dav-converter` или `Smart Player`. Для Xiongmai сырые `.h264`
файлы склеиваются в один поток.

## Работа с индексной базой

Если индекс — SQLite, его можно прочитать напрямую:

```
$ file index/*.db
index/record.db: SQLite 3.x database
$ sqlite3 index/record.db '.tables'
records  events  cameras
$ sqlite3 index/record.db 'SELECT start,end,camera,status FROM records ORDER BY start DESC LIMIT 5;'
```

Поле `status` часто содержит `deleted` для перезаписанных интервалов — это и есть
«удалённые» записи, которые нужны в расследовании. Для проприетарных БД используй
`strings` + `grep` по времени или вендорную утилиту.

## Практический разбор CTF

В задачах на DVR обычно дан либо образ диска, либо выгрузка индекса. Порядок действий:

```
$ binwalk -e dvr.img                     # вытащить вложенные структуры
$ grep -a 'deleted' index_dump.txt       # найти удалённые интервалы
$ foremost -t mp4,h264 -i dvr.img -o carved/   # карвинг видео
$ ffprobe carved/*.h264                  # проверить, что поток валиден
```

Если в задаче спрятан флаг, он часто в метаданных кадра (`snapshot`) или в поле
`camera name` индексной БД, а не в самом видео.

## Часовые пояса и дрейф времени

Самая частая ошибка — принять время камеры за истину. Камеры:

- хранят время в локальном поясе без зоны;
- дрейфуют, если нет NTP;
- сбрасываются при потере питания на «эпоху»;
- показывают разное время в разных интерфейсах (web vs. OSD).

Всегда сверяй время камеры с независимым событием: срабатыванием датчика, логом
мобильного телефона рядом, сетевым трафиком NVR. Сдвиг в час — это почти наверняка
переход на летнее время или неверная зона, а не подделка.

## Извлечение из IP-камеры (а не с диска)

Если запись велась на карту SD внутри камеры, а не на NVR:

```
$ rtsp://admin:pass@10.0.0.9:554/Streaming/Channels/101   # живой поток
$ curl -s 'http://10.0.0.9/ISAPI/ContentMgmt/record/...'  # Hikvision ISAPI
```

Прошивку и список учётных записей достают через ONVIF или веб-интерфейс. Часто именно в
конфиге камеры (а не в видео) лежат учётные данные к другим системам.

## Ограничения

- Проприетарная ФС без документации — нужна вендорная утилита.
- Шифрование диска (некоторые модели) — нужен ключ устройства.
- Циклическая перезапись затирает старые чанки физически — восстановишь не всё.
- Время не верифицировано — таймлайн может «съехать» на часы.

## Если сработало / не сработало

Если карвинг даёт битые потоки — добавь `-t h264,h265` и проверь выравнивание по
стартовым кодам (`00 00 00 01`). Если индекс не читается — используй вендорную утилиту
или `strings`. Если видео пустое — проверь, не включено ли шифрование на устройстве.

## Файловые системы видеорегистраторов

DVR/NVR почти никогда не хранят записи «просто как mp4 в папке». Разберём, что
встречается:

- **ext4 / XFS / FAT32** — «честные» вендоры: записи лежат файлами с индексной базой
  рядом;
- **проприетарные ФС** — Dahua `.dav`-контейнеры, Hikvision-раскладка с блоками
  фиксированного размера;
- **циклический буфер** — старое стирается под новое, поэтому «удалённое» часто
  затёрто лишь частично.

```
$ file -s /dev/sdb1
/dev/sdb1: Linux rev 1.0 ext4 filesystem data
$ mount -o ro,noexec /dev/sdb1 /mnt/dvr
```

Если `file -s` показывает «data» и монтирование не удаётся — смотри строки внутри:
часто в начале образа лежит сигнатура вендора и версия прошивки.

## Индексные базы: где живут временные интервалы

Даже когда сам видеопоток затёрт, **индексная база** хранит, *что и когда* писалось.
Она обычно SQLite или проприетарный бинарный формат. Типичные таблицы:

| Поле | Смысл |
|---|---|
| `start_time` | начало интервала записи |
| `end_time` | конец интервала |
| `channel` | номер камеры |
| `stream` | main/sub поток |
| `size` | размер блока |
| `status` | `normal` / `deleted` / `lost` |

Именно `status=deleted` (или флаг `0x02` в бинарной базе) указывает на интервал, запись
которого удалена. Сопоставляя такие интервалы с промежутками в видеопотоке, можно
доказать, что фрагмент **был и исчез** — это часто и есть ответ в задаче.

## Форматы видео и починка контейнеров

Камеры пишут H.264/H.265. Контейнеры бывают разные:

- `.mp4` / `.avi` — стандартные, читаются любым плеером;
- `.dav` (Dahua) — обёртка вокруг потока, открывается `ffmpeg`;
- **сырой поток** без контейнера — с точки зрения ФС это «мусор», но карвинг его
  находит.

Сырой поток начинается с NAL-заголовков; ключевой кадр (IDR) помечен стартовым кодом
`00 00 00 01` с типом `65` (в H.264). Если поток «не открывается», часто достаточно
собрать его в контейнер:

```
$ ffmpeg -f h264 -i raw_stream.h264 -c copy fixed.mp4
```

Для H.265 стартовый код тот же, но тип NAL другой (`0x26` для IDR в HEVC).

## Карвинг и восстановление удалённого

Порядок действий при утраченном индексе:

```
$ foremost -t mp4,avi -i dvr.img -o out/
$ photorec /d /dev/sdb1          # интерактивно, тип video
$ scalpel -c scalpel.conf dvr.img
```

Карвинг идёт **по сигнатурам**: находит начало каждого видеофрагмента и тянет данные
до следующей сигнатуры. Проблема в том, что кадры без контейнера не имеют длины —
файлы могут получаться «склеенными». Решение: резать по ключевым кадрам (GOP) или
сверяться с индексной базой.

## Время камер и корреляция событий

Самая частая ошибка — принять время камеры за истину. Что проверять:

- **часовой пояс** — камера может писать локальное время, а метаданные — UTC;
- **DST** — переход на летнее время сдвигает записи на час;
- **дрейф** — дешёвые устройства уходят на минуты;
- **NTP** — если синхронизация была, время надёжнее.

Сверяй время камеры с независимыми источниками: событием на другой камере, логом
контроллера доступа, файловой системой. В отчёте всегда фиксируй, какое время
использовано и почему.

## Ограничения и тонкие места

- Зашифрованный носитель — нужен ключ устройства, карвинг бессилен.
- Проприетарный формат — без вендорной утилиты часть данных нечитаема.
- Циклическая перезапись стирает старое — чем раньше снят образ, тем больше шансов.
- Не монтируй оригинал на запись: только `-o ro`, иначе повредишь улики.

## Событийный слой: тревоги и детекция движения

Видео — не единственный источник. Регистраторы ведут **журнал событий**, и он часто
информативнее самой картинки: кто, когда и по какому каналу сработал.

```
$ ls log/
motion.log  alarm.log  system.log  access.log
$ cat log/alarm.log | tail -5
2026-01-14 03:07:11 CH3 motion start
2026-01-14 03:07:44 CH3 motion stop
2026-01-14 03:09:02 CH3 door forced (alarm)
```

- `motion.log` — интервалы детекции движения по каналам;
- `alarm.log` — тревоги (вскрытие, потеря видео, датчики);
- `system.log` — перезагрузки, изменение настроек, смена времени;
- `access.log` — кто подключался к веб-интерфейсу и с какого IP.

`system.log` особенно ценен: смена времени на камере оставляет запись, и это объясняет
«съехавший» таймлайн. `access.log` показывает, что злоумышленник мог подключиться к
регистратору и стереть/выгрузить записи.

## Восстановление из «мусора» и типичные ошибки

Когда штатный экспорт невозможен, а индекс повреждён, работают с сырыми секторами:

```
$ ddrescue -f -n /dev/sdb dvr.img dvr.map     # сначала быстрый проход
$ ddrescue -d -r3 /dev/sdb dvr.img dvr.map    # добить «плохие» сектора
$ grep -abo $'\x00\x00\x00\x01' dvr.img | head   # стартовые коды H.264
```

Типичные ошибки:

- **Монтирование проприетарной ФС как ext4** — «пустой» диск, хотя данные есть.
- **Игнорирование часового пояса** — таймлайн смещён на несколько часов.
- **Поиск видео там, где оно сжато/зашифровано** — нужен ключ устройства.
- **Опора только на видео** — журнал событий и индекс дают больше, чем картинка.

## Чек-лист

1. Определить вендора (`banner`, `strings`, веб-интерфейс).
2. Снять диск через `ddrescue`, зафиксировать хэш.
3. `file -s` по разделам, попытка `binwalk -e`.
4. Найти и прочитать индекс (`sqlite3`/вендорная утилита) → интервалы и статусы.
5. Сопоставить `log/` (события) с индексом и видео.
6. Верифицировать время по независимому источнику.
7. Восстановить удалённое карвингом по сигнатурам H.264/H.265.
