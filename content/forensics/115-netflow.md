## Вопрос, с которого всё начинается

Иногда PCAP нет вообще — сеть слишком быстрая, чтобы писать все пакеты, а хранить гигабайты содержимого дорого. Но администраторы всё равно собирают **метаданные** о трафике. Как по ним понять, что хост сливал данные, если самих пакетов не сохранилось?

## Наш пример: каталог nfcapd-файлов

Нам дали каталог с файлами вида `nfcapd.202403010000`. Это выгрузки **NetFlow** — агрегированные записи о трафике, которые создаёт экспортёр (маршрутизатор или сервер) и складывает утилита `nfcapd`. Содержимого пакетов тут нет — только «кто, кому, по какому протоколу, сколько».

## Шаг 1: что такое flow

**Flow** (поток) — набор пакетов с общими полями, агрегированный по времени. Типовая запись NetFlow содержит:

| Поле | Значение |
|------|----------|
| srcaddr / dstaddr | IP-адреса |
| srcport / dstport | порты |
| protocol | TCP/UDP/ICMP |
| packets / bytes | объёмы |
| first / last | время начала/конца |
| tcp_flags | OR флагов за поток |

Есть несколько стандартов: NetFlow v5/v9 (Cisco), **IPFIX** (NetFlow v10, расширяемый стандарт с шаблонами) и **sFlow** (семплированные потоки). IPFIX описывает набор полей через **шаблоны** (templates), поэтому парсер должен сначала получить шаблон — иначе запись не разобрать.

## Шаг 2: строим топы

Основной инструмент — `nfdump`. Начнём с вопроса «кто больше всех отправил»:

```bash
$ nfdump -r nfcapd.* -s srcip/bytes -n 5
Date first seen   Duration Proto Src IP Addr        Flows  Packets   Bytes
2024-03-01 22:00  0:05:12  TCP  10.0.0.5            1420  1048576  524288000
```

Читаем: хост `10.0.0.5` передал **~500 МБ** (524288000 байт) за 1420 потоков. Само по себе много, но не приговор — может, это бэкап или обновление. Нужно смотреть детали.

## Шаг 3: сужаем фильтром

У `nfdump` свой язык фильтров — по адресу, порту, протоколу:

```bash
$ nfdump -r nfcapd.* 'src ip 10.0.0.5 and dst port 8443' -o fmt:'%ts %da %byt'
2024-03-01 22:01:03  203.0.113.9  380928
2024-03-01 22:02:11  203.0.113.9  512000
...
```

Вот и аномалия: тот же хост передаёт данные на `203.0.113.9:8443` — **нестандартный порт** (обычный HTTPS — 443) — мелкими порциями в течение нескольких минут. Это типичная картина эксфильтрации: данные дробят, чтобы не привлекать внимания объёмом. Дальше — искать соответствующий PCAP или файловые артефакты.

## Шаг 4: что ещё искать в потоках

Потоковые данные хороши для поиска поведенческих аномалий:

- **Beaconing.** Регулярные соединения к одному адресу с постоянным интервалом и малым объёмом — признак C2 (управляющего сервера).
- **Эксфильтрация.** Один хост, много исходящих байт на нетипичный адрес/порт.
- **Сканирование.** Много коротких потоков к разным портам одного адреса.
- **Туннели.** Аномально большой объём по DNS/ICMP (скрытый канал).

```bash
# Соединения на нестандартные порты
$ nfdump -r nfcapd.* 'proto tcp and not port 80 and not port 443 and not port 22'
# Периодичность к адресу (beaconing) — считаем потоки по минутам
$ nfdump -r nfcapd.* 'dst ip 203.0.113.9' -o fmt:'%ts' | cut -c1-16 | uniq -c
```

Если есть только PCAP, потоковые записи можно построить: `tshark -r capture.pcap -q -z conv,ip` даёт таблицу разговоров «кто с кем и сколько».

## Шаг 5: базовая линия и корреляция

Аномалию видно только на фоне нормы. Сначала соберите базовые показатели — типичные порты, объёмы, обычные внешние адреса, — а затем ищите отклонения: объём выше обычного, ночная активность, соединения к новым ASN.

Потоки почти никогда не используют в одиночку. Связки:

- **Flow + DNS-логи** — сопоставить домены с IP-потоками.
- **Flow + Suricata** — алерт по 5-tuple → найти полный поток.
- **Flow + DHCP** — понять, какой хост был за IP в момент инцидента.

```bash
$ grep "10.0.0.5" dhcpd.log | tail     # кто был за IP
$ grep "203.0.113.9" dns.log | head    # какой домен
```

Так из абстрактных «500 МБ на адрес» получается конкретный пользователь, домен и процесс.

## Полный разбор: от каталога к инциденту

Соберём расследование в одну историю. Вход — каталог `nfcapd.*`; выход — вывод о том, что хост `10.0.0.5` сливал данные.

**Шаг А. Обзор.** Смотрим, кто вообще много передавал:

```bash
$ nfdump -r nfcapd.* -s srcip/bytes -n 3
2024-03-01 22:00  TCP  10.0.0.5   1420 flows  524288000 bytes
2024-03-01 09:00  TCP  10.0.0.20   210 flows   18000000 bytes
```

**Шаг Б. Проверяем назначение.** Топ по байтам — это подозрение, а не вывод. Смотрим, куда шли данные:

```bash
$ nfdump -r nfcapd.* 'src ip 10.0.0.5' -s dstip/bytes -n 5
203.0.113.9   1420 flows  520000000 bytes
```

**Шаг В. Сужаем по порту.** 520 МБ ушли на один внешний адрес. На какой порт?

```bash
$ nfdump -r nfcapd.* 'src ip 10.0.0.5 and dst ip 203.0.113.9' -s dstport/bytes
8443   520000000
```

Порт **8443** (не 443) — уже сигнал: легитимный HTTPS был бы 443. Смотрим распределение по времени:

```bash
$ nfdump -r nfcapd.* 'src ip 10.0.0.5 and dst ip 203.0.113.9' -o fmt:'%ts %byt'
2024-03-01 22:01:03  380928
2024-03-01 22:02:11  512000
2024-03-01 22:03:20  498176
```

Порции примерно по 400–500 КБ каждые ~70 секунд. Это не бэкап (тот шёл бы крупным потоком) и не обычный сёрфинг (тот — на 443). Картина «дробим данные на куски с ровным интервалом» = эксфильтрация с троттлингом.

**Шаг Г. Коррелируем.** По DHCP узнаём, кто был за `10.0.0.5`, по DNS — что за домен у `203.0.113.9`, и получаем ответ «пользователь → домен → процесс». Только теперь вывод обоснован.

## Если не сработало

- **Записи не читаются.** IPFIX-файл без шаблона не парсится; убедитесь, что в каталоге есть соответствующий template-файл (`nfcapd` кладёт его рядом).
- **Счётчики странные.** Если используется sFlow, объёмы — оценка по семплам, не точные байты. Не сравнивайте sFlow и NetFlow напрямую.
- **Времени не хватает.** Потоки агрегированы по интервалам; для точной секунды нужен PCAP.
- **Слишком широкий фильтр.** Добавьте конкретику: `and dst port 8443`, `and proto tcp`, временное окно.
- **Нет внешней активности, а данные ушли.** Возможно, exfil шёл через DNS/ICMP или внутренний прокси — проверьте аномальные объёмы по этим протоколам.

## Шпаргалка nfdump

| Задача | Команда |
|--------|---------|
| Топ по байтам | `-s srcip/bytes` |
| Топ по потокам | `-s dstip/flows` |
| Фильтр по порту | `'dst port 8443'` |
| Фильтр по протоколу | `'proto icmp'` |
| Вывод только времени и байт | `-o fmt:'%ts %byt'` |
| Список файлов | `nfdump -r nfcapd.* -s record/bytes` |

Строить потоки из PCAP: `tshark -r capture.pcap -q -z conv,tcp` — таблица «кто с кем и сколько».

## Защита и мониторинг

- Держите **базовую линию** трафика: типичные порты и объёмы. Аномалию видно только на фоне нормы.
- Оповещения на исходящие соединения на **нестандартные порты** и на ночную активность.
- Храните flow-данные **дольше** PCAP (они компактнее) — это дешёвая ретроспектива.
- Обязательно держите DNS- и DHCP-логи: без них flow почти бесполезен для атрибуции.

## Что мы теперь знаем

- **Flow** — агрегированная запись о трафике (5-tuple + счётчики), без содержимого.
- **IPFIX** отличается расширяемостью: поля описываются шаблонами.
- `nfdump -s` строит топы, фильтры сужают по адресу/порту/протоколу.
- Признаки атаки: beaconing, эксфильтрация, сканирование, туннели.
- **sFlow** семплирует трафик, поэтому байты — оценка, а не точное значение.
- Потоки ценны в корреляции с DNS, DHCP, Suricata.

## Куда дальше

Мы научились находить аномалии без содержимого пакетов. В следующем уроке (`forensics-tshark-deep`) спустимся на уровень пакетов — глубокие фильтры `tshark` и извлечение объектов. А пока главное запомни: **NetFlow показывает, кто, куда и сколько передал; топы и фильтры `nfdump` выявляют эксфильтрацию и beaconing, но детали добирают PCAP'ом**.

## Где пригодится

- **CTF:** задачи с flow-данными или большими PCAP.
- **DFIR:** быстрый обзор сетевой активности при инциденте.
- **Threat Hunting:** поиск beaconing и эксфильтрации.
- **SOC:** мониторинг и построение базовых линий трафика.
