## Вопрос, с которого всё начинается

На диске тысячи файлов, а в логах миллионы строк. Искать «глазами» бессмысленно. Нужен способ один раз описать, что мы считаем **плохим**, и применить это описание к тысячам объектов. Для содержимого и для событий логов такие языки разные.

## Наш пример: ищем флаг в каталоге улик

У нас есть каталог `/evidence` с извлечёнными файлами. Напишем правило, которое найдёт шаблон флага.

## Шаг 1: YARA — правила для содержимого

**YARA** ищет байтовые паттерны в файлах и памяти. Правило состоит из трёх частей: `meta` (описание), `strings` (что искать) и `condition` (когда правило срабатывает):

```yara
rule CTF_Flag {
    strings:
        $f = /flag\{[a-z0-9_]+\}/
    condition:
        $f
}
```

Применяем к каталогу рекурсивно (`-r`):

```bash
$ yara -r hunt.yar /evidence
CTF_Flag /evidence/secret.txt
```

Правило нашло флаг в файле. Ключевые элементы строк:

| Элемент | Значение |
|---------|----------|
| `$a = "text"` | текстовая строка |
| `nocase` | без учёта регистра |
| `wide` | UTF-16LE (типично для Windows) |
| `$h = { 4D 5A ?? ?? }` | hex с wildcards |
| `$r = /regex/` | регулярное выражение |
| `#a > 3` | счётчик вхождений |

## Шаг 2: более реалистичное правило

Для детекта малвари правила комбинируют несколько условий. Например, ищем подозрительный PE-файл:

```yara
rule SuspiciousPE {
    strings:
        $mz = { 4D 5A }
        $api = "VirtualAlloc"
        $url = /https?:\/\/[a-z0-9.\-]+\/[a-z0-9]+/ nocase
    condition:
        uint16(0) == 0x5A4D and $api and $url
}
```

`uint16(0) == 0x5A4D` проверяет первые два байта (сигнатуру `MZ`). Порядок условий важен: дешёвые проверки ставят первыми. Для больших наборов правил применяют таймаут (`-a`) и компиляцию (`yarac`):

```bash
$ yara -a 60 -r rules/ /evidence/
$ yarac rules.yar rules.compiled
```

## Шаг 3: Sigma — правила для логов

**Sigma** — YAML-описание событий логов, независимое от конкретного SIEM. Опишем подозрительный запуск PowerShell с закодированной командой:

```yaml
title: Suspicious PowerShell Encoded Command
logsource:
  product: windows
  service: security
detection:
  selection:
    EventID: 4688
    CommandLine|contains:
      - '-enc'
      - '-EncodedCommand'
  condition: selection
level: high
```

`logsource` описывает источник, `detection` — условия, `condition` комбинирует селекторы (`and`, `or`, `not`, `1 of`, `all of`).

## Шаг 4: конвертация Sigma под свой SIEM

Sigma ценна тем, что одно правило превращается в запросы разных систем через `sigma convert`:

```bash
$ sigma convert -t es-qs ps.yml
(CommandLine:*\\-enc*)
$ sigma convert -t splunk ps.yml
```

Готовые правила берут из репозитория **SigmaHQ**, а не пишут с нуля. Для YARA — из `Neo23x0/signature-base`, `elastic/protections-artifacts`, `awesome-yara`.

## Шаг 5: производительность и корреляция

YARA-регулярки дороги. Советы: якорьте строки, ставьте дешёвые проверки первыми, используйте `yarac` для повторных прогонов. Sigma конвертируют один раз и хранят готовые запросы.

Две системы дополняют друг друга:

- **YARA** — «что это за файл/код».
- **Sigma** — «что произошло в логах».

Пример цепочки: YARA ловит beacon в памяти → Sigma-правило находит запуск `rundll32` с этим файлом в логах → коррелируете время и хост. Правила полезно встроить в CI (YARA по артефактам сборки), SIEM (Sigma как детекты) и EDR.

## Полный прогон: от подозрения до рабочего детекта

Разберём, как рождается правило, а не как выглядит готовое. Предположим, в `/evidence` найден подозрительный бинарь `upd.exe`. Начинаем с гипотезы и уточняем её по шагам.

**Шаг А. Собираем строки.** Смотрим, что вообще есть внутри:

```bash
$ strings -n 6 upd.exe | head
VirtualAlloc
GetProcAddress
http://198.51.100.23/gate.php
SOFTWARE\Microsoft\Windows\CurrentVersion\Run
```

**Шаг Б. Выбираем «якоря».** Не берём `http` (слишком широко) — берём комбинацию редких признаков: `VirtualAlloc` + конкретный URL-хост + ключ автозапуска.

**Шаг В. Пишем правило и проверяем на «хорошем» файле.** Правило обязано молчать на легитимных файлах:

```bash
$ yara upd.yar /usr/bin/ls
# (пусто — правило не сработало, это правильно)
$ yara upd.yar /evidence/upd.exe
SuspiciousUpd /evidence/upd.exe
```

**Шаг Г. Переносим сигнатуру в лог-детект.** Теперь опишем, как этот файл мог *запуститься*, в Sigma:

```yaml
title: Suspicious Updater Execution
logsource:
  product: windows
  service: security
detection:
  selection:
    EventID: 4688
    NewProcessName|endswith: '\upd.exe'
  condition: selection
level: high
```

**Шаг Д. Конвертируем и коррелируем.** Получаем запрос для своего SIEM и связываем два мира — файл (YARA) и событие (Sigma):

```bash
$ sigma convert -t es-qs upd_exec.yml
EventID:4688 AND NewProcessName:*\\upd.exe
```

Если YARA находит образец на диске, а Sigma — его запуск в логах, значит у вас есть и «что», и «когда». Это и есть цель обеих систем вместе.

## Если не сработало

- **Правило не компилируется.** Проверьте отступы: в YARA `strings:`/`condition:` на одном уровне, в Sigma важна корректная YAML-вложенность. Линт: `sigma check rule.yml`.
- **YARA падает по таймауту на большом каталоге.** Разбейте правила на группы, используйте `yarac` (компиляция) и `-a <сек>` для таймаута.
- **Слишком много ложных срабатываний.** Сузьте строки (добавьте `fullword`, якорь в начале), уберите общие термины (`"powershell"`, `"http"`), добавьте второе независимое условие через `and`.
- **Sigma-правило даёт 0 совпадений.** Проверьте `logsource` (product/service), имя поля (`CommandLine` vs `command_line`) и наличие самого события в вашем источнике.
- **Строка не находится, хотя в файле есть.** Для Windows-строк добавьте `wide` (UTF-16LE); для регистронезависимого поиска — `nocase`; помните, что `ascii` и `wide` — разные строки, нужны обе.

## YARA vs Sigma: как не перепутать

| Вопрос | YARA | Sigma |
|--------|------|-------|
| Объект | файл, память, процесс | событие в логе |
| Язык | собственный DSL | YAML |
| Единица | строка/hex/regex | поле события |
| Применение | `yara -r`, `vol yarascan` | `sigma convert -t <backend>` |
| Хранение | `.yar` в git | `.yml` в git |
| Результат | «файл X — это малварь» | «в 22:10 был запуск Y» |

Держите оба набора в репозитории и обновляйте из апстримов (SigmaHQ, signature-base, awesome-yara). Детект без обновлений устаревает за месяцы.

## Частые вопросы

**Можно ли одним YARA-правилом искать и файлы, и память?** Да, правило одно — меняется только способ применения: `yara rule.yar /evidence` по файлам или `vol -f mem.raw yarascan --yara-file rule.yar` по дампу памяти. В памяти строки могут быть разорваны страницами, поэтому для неё избегайте очень длинных паттернов.

**Чем Sigma лучше прямого запроса в SIEM?** Переносимостью. Один `.yml` конвертируется в Elastic, Splunk, Sentinel, QRadar — не нужно переписывать детект при смене платформы. Это удешевляет поддержку десятков правил.

**Как часто обновлять правила?** Регулярно и автоматически: подпишитесь на SigmaHQ и signature-base, а в CI добавьте прогон новых правил по «золотому» набору чистых файлов — так ложные срабатывания отлавливаются до продакшена.

**Что делать, если правило ловит легитимный софт?** Сузьте условие: добавьте второй независимый признак (`and`), исключите известные хорошие хеши (`and not pe.imphash() == "..."`), либо поднимите порог счётчика (`#a > 5`).

## Что мы теперь знаем

- **YARA** — содержимое (файлы/память); **Sigma** — события логов.
- Правило YARA: `meta` + `strings` + `condition`; условия ставят от дешёвых к дорогим.
- `wide` — строки UTF-16LE, типичные для Windows.
- Sigma конвертируется в запросы SIEM командой `sigma convert -t <backend>`.
- Готовые репозитории (SigmaHQ, signature-base) экономят недели.
- Тестируйте правила на ложные срабатывания до продакшена.

## На что смотреть дальше: модули и отладка

YARA умеет разбирать форматы через модули, что делает правила точнее:

```yara
import "pe"

rule SuspiciousPE {
    condition:
        pe.is_pe and pe.imports("kernel32.dll", "VirtualAlloc")
}
```

- `pe` — секции, импорты, ресурсы, timestamp.
- `elf` — структуры ELF; `math` — вычисления (энтропия); `hash` — md5/sha1/sha256 содержимого.

Отладка правил: проверьте синтаксис (`yara -d rule.yar`), прогоните на «хорошем» файле (`yara rule.yar /usr/bin/ls` — срабатывать не должно). В Sigma модификаторы полей (`contains`, `startswith`, `endswith`, `re`, `base64`, `cidr`) позволяют описывать сложное поведение. Типичные ошибки: слишком широкие строки (`"http"` даст тысячи совпадений), отсутствие `nocase`/`wide`, незаанкоренный regex в начале правила, неверный `logsource`. Правила храните в git, тестируйте на ложные срабатывания и обновляйте из SigmaHQ/signature-base.
