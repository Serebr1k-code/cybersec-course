## Вопрос, с которого всё начинается

Нам нужно понять **намерения** пользователя: что он искал накануне инцидента. Даже если он
ничего не открыл, сами поисковые запросы — это след мысли. Windows хранит и историю
поиска, и историю голосового ассистента.

## Наш пример: поисковая история в профиле

Запросы поиска и Cortana оседают в нескольких местах профиля. Типичный источник —
база поиска и файлы истории. Начнём с того, что найдём кандидатов:

```
$ find . -iname '*.db' -path '*Search*'
./AppData/Local/Packages/Microsoft.Windows.Search_.../LocalState/...
```

```
$ file query.db 2>/dev/null
query.db: SQLite 3.x database
```

Многие из этих файлов — **SQLite**. Для Cortana/поиска характерна таблица с текстом
запроса и временем.

## Как Windows хранит поисковые запросы

Пользователь набирает запрос в меню «Пуск» или голосом. Windows сохраняет его, чтобы
показывать подсказки и «недавние поиски». Хранение бывает в двух видах:

- **SQLite-база** с историей запросов (текст + время).
- **Файлы журналов/кэша** в каталоге пакета `Microsoft.Windows.Search` и в профиле
  `AppData\Local\Packages\...\LocalState`.

Ключевая идея: **запрос = намерение**. «как удалить журнал событий», «bitlocker recovery
key», «vpn client download» — такие строки сами по себе рассказывают историю.

## Шаг 1: найти базы и посмотреть схему

```
$ sqlite3 query.db ".tables"
SearchHistory  ...
$ sqlite3 query.db ".schema SearchHistory"
CREATE TABLE SearchHistory(QueryText TEXT, TimeStamp INTEGER, ...);
```

## Шаг 2: вытащить запросы во времени

```
$ sqlite3 -header query.db \
  "SELECT datetime(TimeStamp,'unixepoch'), QueryText FROM SearchHistory ORDER BY TimeStamp;"
TimeStamp            QueryText
2025-06-01 22:10:03  how to clear event logs
2025-06-01 22:12:44  nto{c0rt4n4_s34rch_1nt3nt}
```

Порядок и время запросов — это уже маленькая история расследования.

## Шаг 3: связать с другими артефактами

Поисковый запрос редко живёт в одиночку. Сопоставь его с:

- **Timeline (`ActivitiesCache.db`)** — что открыл сразу после запроса;
- **Windows Search (`Windows.edb`)** — какие файлы оказались рядом по теме;
- **браузерной историей** — куда перешёл после поиска.

Так из одной строки вырастает цепочка: «искал → открыл → скачал».

## Что искать в поисковой истории

| Тип запроса | Что означает |
|-------------|--------------|
| Имена утилит (`psexec`, `mimikatz`) | подготовка инструментария |
| «как удалить/очистить …» | намерение скрыть следы |
| Пути/имена файлов | поиск конкретных данных |
| Сервисы (`vpn`, `bitlocker`) | подготовка доступа/шифрования |

## Частые ошибки и подводные камни

- **Искать только одну базу.** Запросы разбросаны по нескольким файлам/пакетам — собери все.
- **Забыть про голосовые запросы.** Cortana пишет и распознанный текст, не только ввод с
  клавиатуры.
- **Путать с браузером.** Поиск в «Пуске» и поиск в браузере — разные хранилища; нужны оба.
- **Кодировка.** Как и везде, тексты могут быть UTF-16LE.
- **Синхронизация/облако.** Часть истории может подтягиваться из аккаунта; локальная копия
  не всегда полная.

## Шпаргалка команд

```
# Найти кандидатов
find . -iname '*.db' -path '*Search*'

# Схема и запросы
sqlite3 query.db ".tables"
sqlite3 -header query.db "SELECT * FROM SearchHistory ORDER BY TimeStamp;"

# Читаемые строки, если база неочевидна
strings -el query.db | grep -i '<слово>'
```

## Что мы теперь знаем

- Поисковые запросы и история Cortana хранятся в профиле (SQLite и кэш пакетов).
- Запросы содержат текст и время — это готовый мини-таймлайн намерений.
- Полезно сопоставлять запросы с Timeline, Windows.edb и браузерной историей.
- Источников несколько; собирай все, включая голосовые запросы.
- Кодировка часто UTF-16LE.

## Сквозной пример: от запроса к загрузке

Соберём цепочку намерения целиком. Дано: пользователь подозревается в подготовке к
антифорензике. Начинаем с истории поиска:

```
$ sqlite3 -header query.db "SELECT datetime(TimeStamp,'unixepoch'), QueryText FROM SearchHistory;"
2025-06-01 22:10:03   how to clear event logs
2025-06-01 22:12:44   wevtutil cl security
```

Запросы идут один за другим: сначала «как очистить логи», затем конкретная команда. Это уже
сильный сигнал. Теперь связываем с другими артефактами:

- в **Timeline** ищем сессию `cmd.exe`/`powershell.exe` сразу после 22:12;
- в **Windows.edb** смотрим, не искали ли документацию/утилиту;
- в **браузерной истории** проверяем, куда перешли после запроса.

В идеале получаем: `искал → перешёл по ссылке → запустил команду`. Именно такая **цепочка
намерения** отличает подозрение от доказательства: сам запрос — это ещё не действие, но в
связке с последующим запуском он становится частью картины.

## Классификация запросов

Чтобы быстро ориентироваться в истории, полезно раскладывать запросы по категориям:

| Категория | Примеры | Что означает |
|-----------|---------|--------------|
| Инструменты | `psexec`, `mimikatz`, `rclone` | подготовка утилит |
| Антифорензика | `clear event log`, `wipe free space` | сокрытие следов |
| Данные | имена файлов, «export», «archive» | подготовка выноса данных |
| Доступ | `vpn`, `bitlocker`, `password reset` | подготовка/обход доступа |

Такой разбор помогает за минуту понять, к чему вообще готовился пользователь, и выбрать
направление дальнейшего поиска.

## Сверка с браузерной историей

Поиск в «Пуске» и поиск в браузере — разные хранилища, и они дополняют друг друга. В
браузере ты видишь URL результатов и переходы, в истории Cortana — сам текст запроса.
Сопоставив время, восстанавливаешь путь: пользователь набрал запрос в системе, затем открыл
браузер и перешёл по ссылке. Расхождение (запрос есть, перехода нет) тоже информативно: он
мог получить ответ из подсказок системы и не открывать браузер.

## Приватность и настройки

Сбор истории поиска зависит от настроек приватности и учётной записи. Отсутствие записей не
означает отсутствия поисков — пользователь мог очистить историю или отключить сбор. Как и с
другими базами профиля, исторический снимок из VSS иногда содержит то, что текущая база уже
потеряла. Всегда указывай это ограничение, чтобы не строить вывод на пустоте.

## Что фиксировать в отчёте

В отчёте приведи источник (путь к базе), список запросов с временем (в явном поясе) и
сопоставление с последующими действиями. Отдельно отметь категории запросов и оговорку об
ограничениях хранения. Помни: **поисковый запрос — это сохранённое намерение, но не
доказанное действие**; доказательством он становится только в связке с другими артефактами.

## Полный прогон: от запроса к выводу об антифорензике

Пройдём сценарий целиком. Дано: подозрение, что пользователь пытался скрыть следы.
Шаг первый — извлекаем запросы с временем и сортируем. Шаг второй — категоризируем:
запросы про очистку журналов и «wipe» попадают в антифорензику. Шаг третий — ищем
**последствия**: в Timeline — сессии `cmd.exe`/`powershell.exe`, в Prefetch — запуск
утилит, в журнале — событие очистки (`wevtutil`). Шаг четвёртый — формулируем вывод:
«пользователь искал способ очистить журналы и вскоре выполнил соответствующую команду».
Именно связка «запрос + последующее действие» превращает догадку в обоснованный вывод.

## Где ещё хранятся поисковые данные

Кроме основной базы, следы поиска встречаются в нескольких местах профиля: кэш пакета
`Microsoft.Windows.Search`, файлы подсказок, а иногда — в истории браузера, если поиск
уходил в веб. Полезно сделать общий проход по профилю:

```
$ find . -iname '*.db' -o -iname '*history*' | head -20
```

Не ограничивайся одним файлом: цель — собрать **все** источники и свести их в один
таймлайн. Тогда даже если часть истории очищена, оставшиеся следы позволят восстановить
картину.

## Настройки и реестр

Поведение поиска и Cortana регулируется настройками приватности (ключи в реестре и
политики). Для аналитика это важно по двум причинам. Во-первых, по настройкам видно,
**собирал ли** хост историю вообще: если сбор отключён, пустая история — ожидаема, а не
подозрительна. Во-вторых, изменения этих настроек перед инцидентом сами могут быть уликой.
Проверяй ветки политик поиска, но не переоценивай их: настройки говорят о конфигурации, а
не о конкретных действиях.

## Итоговый вывод по артефакту

Поисковая история — это редкий тип артефакта, который фиксирует **намерение**, а не
результат. В отличие от запущенного процесса или созданного файла, запрос показывает, что
пользователь хотел сделать, и потому хорошо работает как отправная точка расследования.
Собери запросы, разложи их по категориям, свяжи по времени с последующими действиями и
обязательно оговори ограничения (сбор мог быть отключён, историю могли очистить). В отчёте
запросы лучше приводить таблицей: время, текст, категория и сопоставленное действие — так
читатель видит не разрозненные строки, а выстроенную линию поведения.

## Разбор истории поиска: от файла к таблице

Покажем полный путь от обнаружения файла до готовой таблицы запросов. Сначала находим
кандидатов в профиле — базы и кэш поиска:

```
$ find . -iname '*.db' | grep -iE 'search|cortana|history' | head
```

Затем для каждого файла проверяем, что это SQLite, и смотрим таблицы:

```
$ file query.db
query.db: SQLite 3.x database
$ sqlite3 query.db ".tables"
SearchHistory  Suggestions  ...
```

Дальше выгружаем запросы с временем и сохраняем в CSV, чтобы дальше работать с ними как с
данными:

```
$ sqlite3 -csv query.db "SELECT datetime(TimeStamp,'unixepoch'), QueryText FROM SearchHistory ORDER BY TimeStamp;" > queries.csv
$ column -s, -t queries.csv | head
```

Такой прогон даёт воспроизводимый артефакт: таблицу, которую можно приложить к отчёту и
которую другой аналитик получит из того же файла теми же командами. Это важная черта
хорошей форензики — **воспроизводимость**: вывод должен опираться на команды, а не на
«я посмотрел глазами».

## Сводная картина по намерениям

Когда таблица запросов готова, полезно свести её в короткую сводку по времени и темам.
Раздели запросы на до и после ключевого события инцидента — это покажет подготовку и
реакцию. Отметь запросы, напрямую связанные с инструментами или антифорензикой, и для
каждого найди подтверждение в других артефактах. В итоге получается не список строк, а
связная линия поведения пользователя, где каждый запрос подкреплён фактом. Именно такая
сводка идёт в отчёт, а сырые запросы — в приложение как исходные данные.

## Куда дальше

Модуль активности закрыт. Дальше переходим к **глубокому разбору артефактов выполнения**
(Prefetch, ShimCache, AmCache, SRUM) — там мы уже перейдём от «что делал пользователь» к
«что и как запускалось». А пока главное запомни: **поисковый запрос — это сохранённое
намерение**.

## Где пригодится

- **CTF Forensics:** флаг в истории поиска.
- **DFIR:** реконструкция подготовки к инциденту.
- **Insider threat:** поиск следов подготовки к утечке.
- **Работа:** eDiscovery и форензика конечных точек.
