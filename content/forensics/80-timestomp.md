## Вопрос, с которого всё начинается

При разборе заражённой Windows-машины в системной папке найден файл `evil.exe`. Смотрим на его дату создания — она выглядит как у системного файла, «старая и солидная». Но что-то не сходится: вредонос не мог появиться три года назад. Возможно, атакующий **подделал время файла**, чтобы тот слился с окружением.

Такая подделка называется **timestomping**. Хорошая новость: подделать **все** записи о времени почти невозможно. Разберём, где именно остаются следы.

## Наш пример: файл `evil.exe`

В NTFS (файловой системе Windows) у каждого файла есть **два независимых набора** временных меток:

- **`$STANDARD_INFORMATION` ($SI)** — набор в главной записи файла (MFT-записи). Он обновляется при обычных операциях — записи, чтении. Именно его меняют утилиты timestomp.
- **`$FILE_NAME` ($FN)** — набор в записи имени (в каталоге). Он обновляется только при создании или переименовании файла.

Мысль простая: обычный инструмент подделки трогает `$SI`, но не знает про `$FN`. Значит, если два набора **расходятся** — это сильный признак подделки.

## Шаг 1: выводим оба набора

Инструмент `MFTECmd` разбирает MFT (главную таблицу файлов NTFS) и умеет печатать оба набора в CSV:

```bash
$ MFTECmd.exe -f '$MFT' --csv out --csvf mft.csv
$ awk -F, '$1 ~ /evil.exe/ {print "SI:", $10, "FN:", $14}' out/mft.csv
SI: 2019-01-01 00:00:00  FN: 2024-03-01 12:00:00
```

Расхождение налицо. По `$SI` файл «создан» 1 января 2019 года (подделка под старый системный файл), а `$FN` показывает реальное время — 1 марта 2024-го. Это и есть **timestomping**: атакующий поменял `$SI`, но `$FN` остался честным.

## Шаг 2: подтверждаем через USN-журнал

Одного расхождения мало для уверенного вывода — нужен **независимый источник**. В NTFS есть **USN-журнал** (`$UsnJrnl:$J`) — журнал изменений, куда система пишет реальное время создания, переименования и удаления файлов. Подделать его сложнее, и он служит перекрёстной проверкой:

```bash
$ MFTECmd.exe -f '$J' --csv out --csvf usn.csv
$ grep -i evil out/usn.csv
evil.exe, created 2024-03-01 12:00:00
```

USN подтверждает: файл реально появился 1 марта 2024 года, как и говорил `$FN`. Два независимых источника против подделанного `$SI`.

## Шаг 3: прямое событие в Sysmon

Если на машине работает **Sysmon** (расширенное логирование Windows), он пишет в журнал событий EVTX событие с идентификатором **2** — «файл изменён во времени». Это прямое доказательство факта timestomping:

```bash
$ evtx_dump -o json Sysmon.evtx | jq 'select(.Event.System.EventID==2) | .Event.EventData'
{ "Image": "...\\evil.exe", "CreationUtcTime": "2019-01-01T00:00:00Z" }
```

Событие 2 фиксирует, что время создания `evil.exe` было изменено на 2019-01-01 — то есть инструмент подделки запускался. Лучшего доказательства не найти.

## Шаг 4: ищем аномалии в самой MFT

Помимо прямого сравнения, полезно искать **аномальные закономерности**. Например, метки «из будущего» или целую группу файлов с одинаковым временем (скрипт проставил одно значение сразу многим):

```bash
$ awk -F, '$10 > "2026-01-01" {print}' out/mft.csv | head
$ awk -F, '{print $10}' out/mft.csv | sort | uniq -c | sort -rn | head
```

Время «из будущего» (позже текущей даты) — явная ложь. А десятки файлов с секунда-в-секунду одинаковым временем создания выдаёт массовую подделку скриптом.

## Шаг 5: Linux и другие файловые системы

В Linux подделка тоже возможна — командой `touch -t`. Но и здесь есть независимый источник. Файловая система **ext4** хранит отдельное поле `crtime` (время создания файла, «birth time»), которое `touch` **не меняет**. Если `crtime` позже `mtime` — это подозрительно:

```bash
$ debugfs -R 'stat /path/evil' /dev/sda1 | grep -iE 'crtime|ctime|mtime'
crtime: 0x65e1a2b0:... -- 2024-03-01 12:00:00
mtime:  0x5c2b3c40:... -- 2019-01-01 00:00:00
```

`crtime` (2024) новее `mtime` (2019) — так не бывает у настоящего файла: нельзя создать файл позже, чем его последний раз меняли. Это верный признак подделки.

## Шаг 6: корреляция с сетью и облаком

Иногда подделку внутри файловой системы не видно вовсе — атакующий аккуратен. Тогда помогают метки **вне** ФС: сетевые логи и облачные аудиты. Если файл «создан» в 2019-м, но в перехваченном трафике он впервые появился в 2024-м — противоречие:

```bash
$ tshark -r capture.pcap -Y 'http.request.uri contains "evil.exe"' -T fields -e frame.time | head
```

Межсетевая корреляция обличает подделку, которую не видно внутри одного источника.

## Полный разбор: доказываем подмену времени

Соберём доказательство по шагам на нашем `evil.exe`.

1. **Смотрим два набора времён** в одном inode — `$STANDARD_INFORMATION` (SI) и `$FILE_NAME` (FN):
   ```bash
   $ MFTECmd.exe -f '$MFT' --csv out
   $ grep evil out/*.csv
   evil.exe, SI Modified: 2019-01-01 00:00:00, FN Modified: 2025-03-01 22:11:03
   ```
2. **Замечаем расхождение.** SI говорит «2019 год», FN — «2025». Легитимный файл имеет близкие значения; расхождение на годы — красный флаг.
3. **Подтверждаем через USN-журнал** (`$UsnJrnl`): там запись о создании в 2025-м, что противоречит SI.
4. **Смотрим Sysmon 2** (изменение времени файла) — прямое событие подмены.
5. **Вывод:** метка была изменена инструментом (`SetFileTime`/`timestomp`). Файл не «старый», а специально «состарен».

Комбинация двух независимых источников (USN + Sysmon) делает вывод доказательным, а не вероятностным.

## Шпаргалка признаков timestomping

| Признак | Где смотреть |
|---------|--------------|
| SI и FN расходятся | MFT (`$STANDARD_INFORMATION` vs `$FILE_NAME`) |
| Время «в будущем» или «в прошлом» | MFT, USN |
| Создание позже изменения | USN, MFT |
| Событие 2 Sysmon | журнал Sysmon |
| Время без наносекунд | SI (некоторые инструменты обнуляют младшие разряды) |

Часто подмена оставляет **обнулённые наносекунды** в SI — живой Windows их заполняет, а инструменты атакующего нет.

## Если не сработало

- **USN-журнал пуст.** Он ограничен по размеру и затирается; тогда опирайтесь на MFT и Sysmon.
- **Sysmon не установлен.** Сравнивайте SI/FN и журнал `$LogFile`/теневые копии.
- **Не NTFS.** На ext4/FAT другой набор меток — сравнивайте ctime/mtime и суперблок.
- **Время выглядят нормально.** Атакующий мог скопировать метки с легитимного файла — ищите несоответствие с журналами событий.
- **Только одна метка.** Некоторые ФС не хранят второй набор — используйте внешние источники (EVTX, USN).

## Защита и мониторинг

- **Sysmon** (событие 2) — прямое обнаружение изменения времени файла.
- Включённый **USN-журнал** даёт независимую историю операций с файлами.
- Оповещения на изменение меток в системных каталогах (`System32`, `Temp`).
- Помните: timestomping — это **антифорензика**, и сам факт её применения — сильный индикатор атаки.

## Что мы теперь знаем

- В NTFS два набора меток: `$SI` (меняется при операциях, его подделывают) и `$FN` (меняется при создании/переименовании).
- Расхождение `$SI` и `$FN` — сильный признак timestomping.
- USN-журнал и Sysmon событие 2 — независимые подтверждения.
- Метки «из будущего» и группы файлов с одинаковым временем выдают подделку.
- В Linux ext4 хранит `crtime`, который `touch` не меняет; `crtime` > `mtime` — аномалия.
- Сеть и облако дают внешние метки для перекрёстной проверки.
