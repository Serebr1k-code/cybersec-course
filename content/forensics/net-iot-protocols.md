## Вопрос, с которого всё начинается

В сети сотни датчиков и умных устройств. Они общаются не по HTTP, а по **MQTT** и
**CoAP** — лёгким протоколам. Если устройство взломали, следы будут именно там.
Разберём, как их читать.

## Наш пример: MQTT-трафик

## Шаг 1: что такое MQTT

MQTT — протокол «публикация/подписка» через брокер. Порт 1883 (или 8883/TLS).
Устройства публикуют в **топики** (например, `home/livingroom/temp`) и подписываются
на них.

```
$ tshark -r iot.pcap -Y 'mqtt' -T fields -e mqtt.conack.flags -e mqtt.topic -e mqtt.msg | head
```

## Шаг 2: CONNECT без пароля

Классическая слабость — брокер без аутентификации:

```
$ tshark -r iot.pcap -Y 'mqtt.conflags' -T fields -e ip.src -e mqtt.username | head
10.10.40.5	
10.10.40.9	admin
```

Пустое поле `mqtt.username` означает анонимное подключение — любой может
публиковать и подписываться. Так злоумышленник получает контроль над всеми
устройствами через брокер.

## Шаг 3: подмена команд

Найдём публикации в управляющие топики:

```
$ tshark -r iot.pcap -Y 'mqtt.msgtype==3' -T fields -e mqtt.topic -e mqtt.msg | grep -i 'cmd\|set'
home/garage/door/cmd	OPEN
```

Публикация `OPEN` в топик двери гаража — прямое управление физическим устройством.
Неавторизованная такая публикация = компромисс.

## Шаг 4: CoAP

CoAP — UDP-протокол для ограниченных устройств (порт 5683):

```
$ tshark -r iot.pcap -Y 'coap' -T fields -e coap.code -e coap.opt.uri_path | head
1	config
```

`code=1` (GET) или `2` (POST). POST на `/config` может менять настройки устройства.

## Шаг 5: следы и слабости

- дефолтные пароли (`admin`/`admin`);
- открытый брокер MQTT;
- прошивки без подписи;
- устройства с постоянными уязвимостями.

Смотри логи брокера (Mosquitto):

```
$ grep -i 'New client connected' /var/log/mosquitto/mosquitto.log | tail
```

## Что мы теперь знаем

- MQTT — pub/sub через брокер (1883).
- Анонимный MQTT = полный контроль над устройствами.
- Публикации в `.../cmd` управляют физикой.
- CoAP — UDP-протокол для мелких устройств (5683).
- Логи брокера фиксируют подключения.

## Если не сработало

- Трафик шифрован (8883)? Нужны ключи.
- Нет дампа? Читай логи брокера и устройства.
- Нужны команды? Смотри MQTT-топики и CoAP POST.

## MQTT: модель публикации-подписки

MQTT — лёгкий протокол для IoT, построенный на брокере и **топиках**. Клиенты не общаются
напрямую: они публикуют сообщения в топик и подписываются на топики. Схема:

```
датчик  --PUBLISH--> [broker] --PUBLISH-->  подписчик
             тема: home/room1/temp
```

Брокер (Mosquitto, HiveMQ) маршрутизирует сообщения. Для форензики важны: адрес брокера,
имя клиента, топики и — при незащищённой конфигурации — **отсутствие пароля**.

## Разбор MQTT из дампа

Фильтр `mqtt` в tshark показывает пакеты протокола. Смотрим CONNECT (кто подключился) и
PUBLISH (что передано):

```
$ tshark -r iot.pcap -Y 'mqtt.msgtype == 1' -T fields -e ip.src -e mqtt.clientid -e mqtt.username
192.168.1.50  sensor-42  -
$ tshark -r iot.pcap -Y 'mqtt.msgtype == 3' -T fields -e mqtt.topic -e mqtt.msg | head
home/livingroom/light  ON
home/door/lock         OPEN
```

`mqtt.clientid` — имя устройства, `mqtt.topic` — адрес сообщения, `mqtt.msg` — само значение.
Отсутствие `mqtt.username` означает **анонимное** подключение — брокер не требует пароля.

## Атака через подписку на wildcard

Если брокер открыт, злоумышленник подписывается на `#` (все топики) и получает **весь**
трафик. Это видно в дампе как SUBSCRIBE с топиком `#`:

```
$ tshark -r iot.pcap -Y 'mqtt.msgtype == 8' -T fields -e ip.src -e mqtt.topic
192.168.1.99  #
```

Подписка на `#` с неизвестного адреса — признак разведки. Хуже — **публикация** команд в
управляющие топики: отправив `home/door/lock` = `OPEN`, атакующий открывает замок. При
отсутствии ACL брокер выполнит команду без проверки прав.

## CoAP: аналог для UDP

CoAP — REST-подобный протокол на UDP для ограниченных устройств. Методы: GET, POST, PUT,
DELETE. Сообщения компактны, а защита (DTLS) включается не всегда.

```
$ tshark -r iot.pcap -Y 'coap' -T fields -e ip.src -e coap.code -e coap.uri_path
192.168.1.50  1  /sensors/temp
192.168.1.50  2  /actuators/relay
```

`coap.code 1` — GET, `2` — POST. Читаем путь ресурса и понимаем, что запрашивалось. Открытый
CoAP без DTLS позволяет и читать, и изменять состояние устройства.

## Следы на устройствах и в облаке

Помимо сети, следы IoT живут:

- в **конфигах устройств** (Wi-Fi, MQTT-брокер, учётные данные);
- в **логах брокера** (кто подключался, какие топики);
- в **облачных панелях** (история команд, привязка аккаунтов);
- в **мобильном приложении** устройства (токены, история).

```
$ grep -iE 'mqtt|broker|password' /etc/config/*.conf 2>/dev/null
```

Часто пароль к брокеру лежит в открытом виде в прошивке или конфиге.

## Таблица: IoT-протоколы и их слабости

| Протокол | Транспорт | Порт | Типичная слабость |
|---|---|---|---|
| MQTT | TCP | 1883 / 8883 | анонимный доступ, нет ACL |
| CoAP | UDP | 5683 / 5684 | нет DTLS, открытый доступ |
| Zigbee | радио | — | слабый ключ, сброс |
| BLE | радио | — | сопряжение без PIN |
| Modbus | TCP | 502 | нет аутентификации |
| HTTP | TCP | 80/443 | дефолтные пароли |

## Ограничения

MQTT over TLS (8883) шифрует содержимое — видны только метаданные соединения. Некоторые
брокеры используют нестандартные порты. Дампы IoT часто фрагментированы и содержат помехи
от других устройств. CoAP с DTLS нечитаем без ключей. И помни, что «открытый порт» в дампе
не всегда означает уязвимость — важно, есть ли реальный доступ и права.

## Если сработало: фиксируем

Опиши: адрес брокера, подключившихся клиентов (clientid), использованные топики и
подозрительные публикации (особенно в управляющие топики). Наличие подписки на `#` или
команды `OPEN`/`ON` в дампе — конкретное доказательство воздействия на физическое устройство.

## Как выглядит взлом IoT по шагам

Разберём типичную цепочку на примере MQTT-устройства:

1. **Разведка** — сканирование сети, поиск открытых портов 1883/8883;
2. **Проверка доступа** — подключение к брокеру без пароля;
3. **Перечисление** — подписка на `#`, сбор всех топиков;
4. **Воздействие** — публикация команды в управляющий топик;
5. **Закрепление** — создание своего подписчика или правила.

В дампе каждый шаг оставляет след. Шаг 2 виден как CONNECT без `mqtt.username`, шаг 3 — как
SUBSCRIBE на `#`, шаг 4 — как PUBLISH в топик вида `.../set` или `.../cmd`.

```
$ tshark -r iot.pcap -Y 'mqtt.msgtype == 3 and mqtt.topic contains "set"' -T fields -e ip.src -e mqtt.topic -e mqtt.msg
192.168.1.99  home/alarm/set  DISARM
```

`DISARM` в топике тревоги от постороннего адреса — прямое доказательство компромисса.

## Учётные данные в трафике и на устройстве

Многие IoT-устройства передают токены и пароли в открытом виде или хранят их локально:

- MQTT CONNECT с `mqtt.username`/`mqtt.password` в открытом виде (без TLS);
- HTTP-запросы с токеном в URL;
- пароли в конфиг-файлах прошивки;
- ключи Wi-Fi в `wpa_supplicant.conf`.

```
$ tshark -r iot.pcap -Y 'mqtt.msgtype == 1 and mqtt.pass' -T fields -e ip.src -e mqtt.username -e mqtt.pass
192.168.1.50  sensor-42  S3cr3t!
```

Перехваченный пароль брокера позволяет подключиться к нему повторно — это уже учётные данные
для дальнейших действий.

## Связь с облачной панелью

Многие IoT-устройства управляются через облако (Tuya, AWS IoT, собственный бэкенд). Тогда
локальный MQTT — только часть картины. Артефакты:

- **токены привязки** в мобильном приложении;
- **история команд** в облачной панели;
- **API-логи** производителя.

Соединяя локальный трафик с облачными логами, восстанавливается полная цепочка «приложение →
облако → устройство».

## Таблица: что искать и где

| Индикатор | Где | Вывод |
|---|---|---|
| CONNECT без username | дамп MQTT | анонимный доступ |
| SUBSCRIBE на `#` | дамп MQTT | разведка/перехват |
| PUBLISH в `/set`, `/cmd` | дамп MQTT | воздействие |
| пароль в CONNECT | дамп MQTT | утечка креды |
| открытый CoAP POST | дамп CoAP | управление устройством |
| дефолтный пароль | конфиг/веб | слабая защита |

## Ограничения

TLS (8883) закрывает содержимое MQTT — остаются метаданные. Нестандартные порты и
проприетарные обёртки усложняют разбор. Часть устройств шлёт данные пачками и шифрует
payload отдельно (на уровне приложения). Некоторые дампы содержат только broadcast-трафик,
если точка доступа изолирует клиентов. Всегда проверяй, полон ли захват.

## Если сработало: доказательная ценность

IoT-инциденты часто связаны с **физическим** воздействием (замки, датчики, камеры). Поэтому
в отчёте важно связать сетевой факт с физическим событием: команда `DISARM` → отключение
тревоги; `OPEN` → доступ в помещение. Указывай время, источник (IP/MAC) и сам топик с
командой — это и есть доказательство.

## Сравнение с промышленными протоколами

Те же принципы работают и в АСУ ТП: Modbus, DNP3 и IEC 60870-5 тоже не имеют встроенной
аутентификации, и команды видны в открытом виде. Разница лишь в транспорте и формате. Освоив
разбор MQTT/CoAP, ты легко переносишь подход на промышленные протоколы: находишь дамп,
извлекаешь команды и сопоставляешь с состоянием оборудования. Логика «протокол без защиты →
команда видна и подделываема» универсальна.
