## Вопрос, с которого всё начинается

Хост мог общаться с внешним миром — но куда именно? Прямой дамп снять не всегда
удается, зато остаются логи **firewall** и **прокси**. Это готовый журнал сетевых
решений. Разберём, как из них выжать картину.

## Наш пример: логи прокси

## Шаг 1: что логирует прокси

Squid пишет строки в формате, похожем на access.log:

```
$ tail -3 /var/log/squid/access.log
1705000000.123  200 10.10.20.9 TCP_MISS/200 4523 GET http://203.0.113.5/payload.dmg - HIER_DIRECT/203.0.113.5 application/octet-stream
```

Поля: время (unix), статус, клиент, размер, метод, URL, тип. Здесь видно загрузку
`payload.dmg` с `203.0.113.5`.

## Шаг 2: агрегируем

```
$ awk '{print $3, $7}' /var/log/squid/access.log | sort | uniq -c | sort -rn | head
   120 10.10.20.9 http://203.0.113.5/
    40 10.10.20.9 https://update.example/
```

Аномально частые обращения к одному внешнему хосту — признак beaconing или
эксфильтрации.

## Шаг 3: firewall

Linux `iptables`/`nftables` не логирует по умолчанию — нужны правила LOG. Логи
попадают в kernel log:

```
$ grep -i 'DPT=443' /var/log/kern.log | tail
IN=eth0 OUT= SRC=10.10.20.9 DST=203.0.113.5 DPT=443 ... SYN
```

Отсюда видно, кто и куда инициировал соединения. Для DNS:

```
$ grep -i 'DPT=53' /var/log/kern.log | awk '{print $12, $13}' | sort -u | head
```

## Шаг 4: DNS-запросы

Если логируется DNS, видно домены:

```
$ grep -i 'query' /var/log/named/query.log | tail
14-Jan-2026 03:29:00.123 client 10.10.20.9#53: query: update.example A
```

Домен `update.example` — зацепка. Сопоставь с известными IOC.

## Шаг 5: эксфильтрация

Ключевой вопрос: уходили ли данные? Признаки:

- большой исходящий объём (колонка размеров);
- соединения на нестандартные порты;
- регулярные запросы фиксированного размера (beaconing);
- использование доменов, похожих на легитимные (DGA/тайпсквоттинг).

## Что мы теперь знаем

- Прокси логирует URL, клиента, размер, статус.
- Агрегация выявляет аномалии (beaconing, эксфильтрация).
- Firewall логирует через правила LOG в kern.log.
- DNS-логи показывают домены.
- Большой исходящий объём + нестандартные порты = эксфильтрация.

## Если не сработало

- Логи не ведутся? Проверь конфиг и включи (но это уже после инцидента).
- Прокси прозрачный? Смотри DNS и NetFlow.
- Нужен объём? Используй NetFlow/IPFIX.

## Зачем firewall и proxy в расследовании

Между устройством и интернетом почти всегда стоят **firewall** (фильтр пакетов) и **proxy**
(посредник для HTTP/HTTPS). Оба ведут логи, которые отвечают на два вопроса:

- **куда** пыталось пойти устройство (в т.ч. заблокированные попытки);
- **что** было разрешено и прошло.

Заблокированная попытка часто ценнее успешной: она показывает намерение, даже если защита
сработала. А разрешённый трафик к подозрительному домену — уже факт утечки.

## Логи firewall

На macOS/BSD используется **pf**; на Linux — iptables/nftables. Логи пишутся в системный
журнал (pf) или в отдельный файл:

```
$ log show --predicate 'process == "kernel" and eventMessage contains "pf"' --last 1h | tail
... pf: block out on en0 proto tcp 10.0.0.57:51422 -> 185.220.101.5:8443
```

Формат: действие (`block`/`pass`), направление, протокол, источник, назначение. На Linux:

```
$ journalctl -k | grep -i 'iptables\|nft' | tail
```

Собираем все заблокированные соединения в узкое окно времени — это карта попыток C2.

## Логи proxy

Squid и корпоративные прокси пишут в `access.log` строки, похожие на веб-серверные, но с
кодом решения:

```
$ tail -3 /var/log/squid/access.log
1768360000.123  450 10.0.0.57 TCP_MISS/200 4512 GET http://malware.example.net/beacon - HIER_DIRECT/185.220.101.5
1768360060.456   12 10.0.0.57 TCP_DENIED/403 0 GET http://blocked.example.net/ - NONE/- -
```

`TCP_MISS/200` — запрос прошёл напрямую, `TCP_DENIED/403` — заблокирован. `HIER_DIRECT/IP`
показывает **реальный IP** за доменом — полезно, когда нужен адрес, а не имя.

## Признаки beaconing

Вредоносное ПО регулярно «отбивает» сигнал на C2. Признак — **строгая периодичность**
запросов к одному домену:

```
$ awk '{print $1, $7}' /var/log/squid/access.log | grep 'example.net' | head
1768360000 http://malware.example.net/beacon
1768360060 http://malware.example.net/beacon
1768360120 http://malware.example.net/beacon
```

Интервал ровно 60 секунд — машина не делает так случайно. Считаем распределение интервалов:

```
$ awk '/beacon/{print $1}' access.log | python3 -c "import sys;t=[float(x) for x in sys.stdin];print([round(t[i+1]-t[i]) for i in range(len(t)-1)][:10])"
[60, 60, 60, 60]
```

Ровные интервалы — почти подпись малвари.

## Таблица: источники сетевых логов

| Источник | Файл / команда | Что даёт |
|---|---|---|
| pf (macOS/BSD) | `log show` | разрешено/заблокировано |
| iptables/nftables | `journalctl -k` | фильтрация пакетов |
| Squid | `access.log` | URL, решение, IP |
| Корп. прокси | syslog/панель | категории, пользователь |
| DNS | `mDNSResponder` логи | разрешение имён |
| NetFlow/IPFIX | коллектор | объёмы и сессии |

## Сопоставление с DHCP и DNS

Отдельный IP мало что значит. Соединяем: DHCP даёт владельца адреса, DNS — какие имена он
разрешал, proxy — какие URL запрашивал. Вместе получается полная картина активности
конкретного устройства.

```
$ grep '10.0.0.57' access.log | awk '{print $7}' | sed 's|https\?://||;s|/.*||' | sort | uniq -c | sort -rn | head
```

## Ограничения

HTTPS скрывает **содержимое** (виден только домен, если не включена инспекция TLS). Всё
больше трафика идёт через CDN, и один IP обслуживает тысячи сайтов — по IP судить нельзя.
Логи ротируются и теряются. Прокси может работать в «прозрачном» режиме и не логировать URL.
И помни: **отсутствие** записи не значит отсутствие соединения — логи могут быть неполными
или выключенными.

## Если сработало: строим таймлайн

Для отчёта собери: устройство (IP/MAC), время, назначение (домен и реальный IP), решение
(разрешено/заблокировано). Периодические запросы к одному домену — выделяй отдельно как
beaconing. Это превращает сетевые логи в доказательство C2-активности.

## Определяем устройство за прокси

В корпоративной сети за прокси стоят сотни устройств. Чтобы понять, кто именно ходил на
подозрительный домен, соединяем прокси-лог с DHCP:

```
$ grep 'malware.example.net' access.log | awk '{print $3}' | sort -u
10.0.0.57
$ grep -A6 '10.0.0.57' /var/lib/dhcp/dhcpd.leases | grep client-hostname
client-hostname "WS-DEV-07";
```

Так «какой-то IP» превращается в «рабочая станция WS-DEV-07». Дальше — к владельцу по
инвентаризации.

## Различаем эксфильтрацию и обычный трафик

Эксфильтрация — это **объём** данных наружу. Ищем аномалии:

- большие `POST`/`PUT` на незнакомые домены;
- длительные сессии к одному внешнему адресу;
- ночные выгрузки, не свойственные рабочему времени;
- использование облачных хранилищ (pastebin, file.io) для передачи.

```
$ awk '$7 ~ /POST/ {print $3, $7, $5}' access.log | sort -k3 -nr | head
```

## Тоннелирование поверх разрешённого

Атакующие прячут трафик в легитимных каналах: DNS-туннели, HTTPS к обычным сервисам,
WebSocket. Признаки DNS-туннеля — аномально длинные поддомены и высокая частота запросов к
одному домену:

```
$ log show --predicate 'process == "mDNSResponder"' --last 10m | grep -oE '[a-z0-9]{40,}\.evil\.net' | head
aGVsbG8gd29ybGQgdGhpcyBpcyBleGZpbA.evil.net
```

Длинные base32/base64-подобные метки в поддоменах — почти наверняка туннель.

## Таблица: паттерны и их значение

| Паттерн в логах | Возможное значение |
|---|---|
| регулярные запросы (ровный интервал) | beaconing/C2 |
| массовые 403 к одному домену | обход блокировки |
| большой POST на новый домен | эксфильтрация |
| длинные поддомены | DNS-туннель |
| соединения в 3-4 утра | автоматизация/малварь |
| домен, зарегистрированный недавно | фишинг/C2 |

## Ограничения

HTTPS скрывает URL и тело; при инспекции TLS видно больше, но не всегда включена. CDN
скрывают реальные серверы за общими IP. Логи ротируются и могут быть неполными. Транзитный
трафик, не проходящий через прокси, вообще не виден. И не забывай о **ложных
срабатываниях**: легитимные обновления и облачные сервисы выглядят как beaconing.

## Если сработало: что фиксировать

Для отчёта: устройство (IP/MAC/имя), назначение (домен + реальный IP), решение
(разрешено/заблокировано), время и объём. Для beaconing — интервал между запросами. Для
эксфильтрации — объём и направление. Это конкретные индикаторы для блокировки и охоты.

## Сравнение с EDR-телеметрией

Сетевые логи показывают «куда», но не «какой процесс». EDR-телеметрия добавляет процесс и
командную строку, что позволяет связать соединение с конкретным исполняемым файлом. Если
EDR недоступен, используй sysmon-подобные источники (например, `netstat`/`lsof` в памяти,
логи аудита), чтобы хотя бы приблизиться к ответу. Полная картина — это всегда соединение
сетевого факта с процессным.

## Итог и приоритеты анализа

Сетевые логи firewall и прокси — самый быстрый способ увидеть «куда ходило устройство».
Начинай с заблокированных соединений: они показывают намерение без последствий. Затем ищи
периодические запросы к одному домену как признак beaconing, после чего оценивай объём
исходящих данных на предмет эксфильтрации. Каждый вывод подкрепляй вторым источником —
DHCP для привязки устройства и DNS для подтверждения имён. Фиксируй время, домен, реальный
IP и объём: это готовые индикаторы для блокировки и последующей охоты по инфраструктуре.

## Хранение и целостность логов

Сетевые логи быстро растут и ротируются, поэтому при реагировании первым делом выгружай
нужные интервалы на отдельный носитель и считай их хеши. Без этого через несколько часов
часть записей может исчезнуть, и вывод станет недоказуемым. Храни исходные файлы в
неизменном виде, а анализ веди на копиях — так результат останется воспроизводимым.
