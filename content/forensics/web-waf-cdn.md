## Вопрос, с которого всё начинается

Перед сайтом стоит **WAF/CDN** (Cloudflare/Akamai/AWS). Он не только защищает, но и
**логирует** всё: запросы, блокировки, реальные IP. Разберём.

## Наш пример: Cloudflare

## Шаг 1: логи WAF

WAF логирует решения: пропущено/заблокировано/челлендж.

```
$ grep BLOCK waf.log | head
203.0.113.5  GET /?id=1' OR '1'='1  BLOCK  SQLi
```

Здесь видно атаку (SQLi) и её источник.

## Шаг 2: реальный IP за прокси

CDN прячет настоящий IP клиента. В логах есть заголовки:

```
$ grep -i 'cf-connecting-ip\|x-forwarded-for' access.log | head
```

`CF-Connecting-IP` — настоящий адрес. Без него ты видишь только IP CDN.

## Шаг 3: кэш как источник

CDN кэширует ответы. В кэше могут остаться:

- версии страниц (в т.ч. удалённые);
- ответы API;
- статические файлы.

```
$ curl -s http://cdn/old-page | head
```

Проверь `Cache-Control`/`Age` — если страница из кэша, она «заморожена».

## Шаг 4: восстановление запросов

Логи WAF/CDN показывают полный URL и заголовки:

```
$ jq '.ClientRequestURI, .ClientIP' cdn_log.json | head
```

Это позволяет восстановить, что именно отправлял атакующий (payload).

## Шаг 5: что искать

- блокировки по типам атак (SQLi/XSS/RCE);
- реальные IP за прокси;
- запросы, прошедшие WAF (bypass);
- изменения конфигурации WAF;
- страницы из кэша.

## Что мы теперь знаем

- WAF/CDN логирует запросы и решения.
- Реальный IP — в `CF-Connecting-IP`/`X-Forwarded-For`.
- Кэш хранит версии страниц.
- Логи дают полный payload.
- Ищем блокировки, bypass, смену правил.

## Если не сработало

- Логи не экспортируются? Включи Logpush/журналирование.
- Нужны тела? Смотри логи бэкенда.
- Прокси без логов? Анализируй сеть.

## Чем WAF отличается от CDN (и почему их путают)

Часто WAF и CDN стоят «в одном флаконе» (Cloudflare, Akamai), но это разные
функции:

- **CDN** (Content Delivery Network) — кэширует и раздаёт контент ближе к
  пользователю, ускоряя сайт;
- **WAF** (Web Application Firewall) — фильтрует запросы, блокируя атаки по
  сигнатурам (SQLi, XSS, RCE).

Для форензики важно, что оба **логируют**. CDN оставляет следы в кэше и
заголовках, WAF — решения «пропущено/заблокировано».

## Как читать решение WAF

Типичная строка лога WAF:

```
203.0.113.5 - [14/Jan/2026:03:28:11] "GET /?id=1' OR '1'='1" BLOCK SQLi rule=942100
```

Здесь видно: клиент, полный payload, решение (`BLOCK`), категорию атаки и
идентификатор правила. Правило (OWASP CRS `942100`) говорит, что именно
сработало — это помогает понять технику атакующего. Если решения `PASS` для
похожих payload — возможен bypass, и это важнее блокировок.

## Работа на примере: ищем bypass

Атакующий редко сдаётся после блокировки. Ищем, что **прошло**:

```
$ grep 'PASS' waf.log | grep -iE 'union|select|<script|\.\./' | head
198.51.100.7 - [14/Jan/2026:03:31:02] "GET /search?q=1 UNION/**/SELECT ..." PASS
```

Обфускация (`/**/` вместо пробела) обошла правило. Теперь ищем, к чему это
привело в логе бэкенда:

```
$ grep '14/Jan/2026:03:31' backend.log | grep search | head
```

Так WAF и бэкенд складываются в единую картину: обход → эксплуатация.

## Реальный IP за прокси: заголовки

CDN прячет адрес клиента, подставляя свой. Настоящий адрес — в заголовках:

```
$ grep -io 'cf-connecting-ip[^,]*' access.log | head
CF-Connecting-IP: 203.0.113.5
```

Полезные заголовки: `CF-Connecting-IP` (Cloudflare), `X-Forwarded-For`,
`X-Real-IP`, `True-Client-IP` (Akamai). Важно: эти заголовки **подделываемы**,
если запрос пришёл не от доверенного прокси. Поэтому при расследовании
учитывай, кто именно их ставит.

## Кэш CDN как источник улик

Кэш может сохранить то, что уже удалено с сервера — например, страницу с
данными или старую версию API-ответа:

```
$ curl -sI http://cdn.example/old-page | grep -iE 'age|cache-control|x-cache'
age: 86400
x-cache: HIT
```

`X-Cache: HIT` и большой `Age` означают, что ответ из кэша. Полезно искать
удалённые страницы через публичные архивы кэша. Осторожно: кэш — не улика
сам по себе, а указатель; подтверждай на источнике.

## Практический чек-лист

1. Определить вендора (Cloudflare/Akamai/AWS) и включён ли экспорт логов.
2. Извлечь реальные IP из прокси-заголовков.
3. Разделить решения WAF: BLOCK (атаки) и PASS (возможные bypass).
4. Для каждого PASS-подозрения найти последствие в логах бэкенда.
5. Проверить кэш на удалённые страницы.
6. Проверить изменения конфигурации WAF (смена правил = возможная зачистка
   следов).
7. Зафиксировать payload целиком, а не только категорию.

## Вендоры и экспорт логов

У каждого WAF/CDN свой способ выгрузки логов — но принцип один: нужно
**включить** журналирование, по умолчанию его часто нет.

- **Cloudflare** — Logpush выгружает JSON в S3/R2 или в SIEM; есть
  GraphQL Analytics API для агрегатов.
- **Akamai** — DataStream (v2) отдаёт события в облако/поток.
- **AWS** — WAF logs пишутся в CloudWatch/Kinesis, CloudFront access-логи в
  S3.
- **Fastly** — real-time log streaming (Syslog/HTTP).

Для расследования важно заранее знать, куда настроена выгрузка и какова
**ретенция** (срок хранения). Если логи пишутся «в никуда» с коротким TTL,
ценные данные могут исчезнуть за сутки.

## Анализ больших объёмов: jq и агрегация

Логи в JSON удобно разбирать через `jq`. Считаем клиентов с блокировками:

```
$ jq -r 'select(.Action=="block") | .ClientIP' cdn_log.json | sort | uniq -c | sort -rn | head
  412 198.51.100.7
   38 203.0.113.9
```

А так — самые атакуемые пути:

```
$ jq -r 'select(.Action=="block") | .ClientRequestURI' cdn_log.json | sed 's/?.*//' | sort | uniq -c | sort -rn | head
  380 /wp-login.php
   42 /xmlrpc.php
```

Всплеск на `wp-login.php` — попытка подобрать пароль админки; `xmlrpc.php`
— abuse для брутфорса в обход.

## Bot-менеджмент и челленджи

Современные CDN используют «челленджи» (JS-проверку), а не только блок.
В логах решение выглядит как `challenge`/`jschallenge`. Для форензики это
означает: атакующий мог пройти челлендж автоматически (headless-браузер), и
тогда блокировок не будет. Ищи клиентов, которые получали челленджи часто,
но в итоге прошли — это признак автоматизации.

## Что даёт кэш, а что нет

Кэш полезен для восстановления удалённых **публичных** страниц. Но:

- кэш не хранит запросы к `POST`/`DELETE` (они не кэшируются);
- приватные ответы (с `Cache-Control: private`) не попадают в общий кэш;
- содержимое кэша зависит от ключа (`Vary`), поэтому одна и та же страница
  может иметь несколько версий.

Не превращай кэш в «доказательство»: он даёт версию, но не подтверждает
факт и время доставки конкретному пользователю. Для этого нужен лог.

## Ретенция и пробелы в данных

При расследовании первым делом выясняй **срок хранения** логов. У CDN он
обычно 7–30 дней, у SIEM — зависит от лицензии. Если инцидент старше
ретенции, часть картины потеряна безвозвратно. Тогда опирайся на то, что
осталось: агрегаты (суточные метрики), логи бэкенда, кэш. Явно отмечай
пробел в отчёте — это честнее, чем строить выводы на неполных данных.

## Практический сценарий: атака через CDN

1. WAF логирует пачку `BLOCK SQLi` с одного IP.
2. Позже видно `PASS` с обфусцированным payload — обход.
3. В логе бэкенда появляется `500` на том же эндпоинте — инъекция сработала.
4. Дальше — аномальные ответы `200` с большим размером (эксфильтрация).

Каждый шаг подтверждается своим источником. Складывая их, получаешь
доказательную цепочку «попытка → обход → эксплуатация → утечка». Без
какого-то звена вывод был бы гаданием.

## Ложные срабатывания WAF

WAF может блокировать легитимный трафик (ложное срабатывание): строка
`select` в поиске, символ `<` в отзыве, `union` в названии компании. При
расследовании не путай настоящую атаку с «шумом». Признаки реальной атаки:

- payload синтаксически осмысленный (полный SQL/JS), а не случайное слово;
- серия попыток с нарастающей обфускацией;
- совпадение по времени с другими аномалиями (скан, брутфорс).

## Что фиксировать для отчёта

- точное время (с таймзоной);
- реальный IP (из прокси-заголовка) и вендора CDN;
- полный payload, а не только категорию;
- решение WAF (block/pass) и id правила;
- последствие в логе бэкенда.

## Справочная таблица: решения и их смысл

| Решение WAF | Что значит |
| --- | --- |
| block | атака распознана и отклонена |
| pass | запрос пропущен (проверь на bypass) |
| challenge | показана JS-проверка |
| log | только зафиксирован (режим обучения) |

Режим `log` часто включают на «обкатке» — тогда атаки не блокируются, но
видны в логах. Для форензики это подарок: полный список попыток без
фильтрации.

## Когда WAF не поможет расследованию

- **Запросы в обход CDN** — если реальный IP сервера известен, атакующий
  может бить напрямую, минуя WAF и его логи.
- **Внутренний трафик** — восток-запад между сервисами через шлюз не всегда
  логируется так же подробно.
- **Шифрование** — тело HTTPS видно только если терминация на шлюзе;
  при passthrough содержимое недоступно.

Поэтому всегда проверяй, не осталось ли у сервера «открытого» IP, и учитывай
внутренние источники.

## Если сработало / если нет

- **Нашёл пачки блокировок** — смотри, был ли следом `pass` и успех на
  бэкенде; это путь от попытки к компромиссу.
- **Видишь только челленджи** — проверь, прошёл ли клиент их; признак
  автоматизации.
- **Логи короткие/отсутствуют** — зафиксируй пробел и опирайся на логи
  сервера и кэш.
- **Много легитимных блокировок** — отсекай шум по синтаксису payload, не
  принимай каждое срабатывание за атаку.
