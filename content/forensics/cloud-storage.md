## Вопрос, с которого всё начинается

Из облачного бакета утекли данные. Нужно понять: что, кто и когда читал. Объектные
хранилища ведут **логи доступа**. Разберём.

## Наш пример: S3-бакет

## Шаг 1: что такое объектное хранилище

S3/Blob/GCS хранят **объекты** (файлы) в бакетах. Доступ — по API, с правами (политики,
ACL). Каждое действие логируется.

## Шаг 2: логи доступа

Два уровня:

- **server access logs** — по каждому запросу;
- **CloudTrail data events** — API-действия.

```
$ grep 'GET' access.log | awk '{print $6, $8}' | sort | uniq -c | sort -rn | head
  450 10.10.20.9 report.pdf
```

Видно, кто и что читал.

## Шаг 3: публичные бакеты

Классика — **открытый** бакет:

```
$ aws s3 ls s3://company-backups --no-sign-request
2026-01-14 report.pdf
```

`--no-sign-request` без креденшелов: если листинг работает — бакет публичный.

## Шаг 4: версионирование

Включённое версионирование хранит **все** версии объекта — даже удалённые:

```
$ aws s3api list-object-versions --bucket b --prefix report
```

Так восстанавливают удалённое и находят изменения.

## Шаг 5: что искать

- массовое скачивание (эксфильтрация);
- доступ с незнакомых IP;
- изменения политик/ACL;
- публичные бакеты;
- загрузку данных нарушителем.

## Что мы теперь знаем

- Объектные хранилища ведут access logs и data events.
- Публичный бакет проверяется `--no-sign-request`.
- Версионирование хранит удалённые версии.
- Ищем массовое скачивание и смену прав.
- Логи дают «кто/что/когда».

## Если не сработало

- Логи не включены? Смотри CloudTrail.
- Нужен объект? Восстанови из версии.
- Нужны права? Читай политики бакета.

## Формат server access log S3

Server access log — по строке на запрос, поля разделены пробелами, а имена и ключи
заключены в кавычки. Типовая строка:

```
79a5 example-bucket [14/Jan/2026:03:20:11 +0000] 10.10.20.9 arn:aws:iam::123:user/ci 3F1C GET /report.pdf HTTP/1.1 200 - 24576 - 12 "-" "aws-cli/2.15.0" - HostId=... SigV4 TLS_AES_128_GCM_SHA256 AuthHeader=...
```

Разберём поля: владелец бакета, имя бакета, время, **IP клиента**, идентичность
(`arn` или `-` для анонимного), Request-ID, операция (`GET`/`PUT`/`LIST`), ключ
объекта, статус (`200`/`403`), число отданных байт, время обработки, User-Agent.
Именно пара «IP + identity + User-Agent» и выдаёт атакующего.

Быстрый анализ:

```
$ awk '{print $5, $6, $7, $8}' access.log | sort | uniq -c | sort -rn | head
  812 10.10.20.9 arn:aws:iam::123:user/ci GET
```

Массовые `GET` одного клиента по разным ключам — это выкачивание бакета.

## CloudTrail data events: кто и что

Server access log фиксирует **чтение объектов**, а CloudTrail **data events** —
API-операции над объектами (`GetObject`, `PutObject`, `DeleteObject`) с полной
идентификацией. В записи есть `userIdentity` (кто), `sourceIPAddress` (откуда),
`userAgent` (чем), `requestParameters.bucketName` и `key`, `eventTime`. Data events
по умолчанию **выключены** — их надо включать отдельно, поэтому в расследовании их
часто нет. Если есть — это золото: по ним строится точный таймлайн «кто скачал что и
когда».

```
$ aws cloudtrail lookup-events --lookup-attributes AttributeKey=EventName,AttributeValue=GetObject --max-results 20
```

Management events (по умолчанию включены) показывают смену политик, создание бакетов
и ролей — их тоже обязательно проверяют.

## Как выглядит эксфильтрация

Признаки в логах:

- **сначала `ListBucket`**, затем шквал `GET` — типичный паттерн `aws s3 sync`/`rclone`;
- **незнакомый User-Agent** (`rclone/`, `s3cmd`, `boto3`, старый `aws-cli`) там, где
  обычно только веб-приложение;
- **объём данных** — сумма отданных байт резко выше нормы;
- **доступ с новых IP/ASN**, особенно вне рабочих часов;
- **`GET` на бэкапы/дампы** (`backup.sql`, `users.csv`, `*.pem`);
- **`PutObject` нарушителем** — загрузка инструментов или шифровальщика.

Собрав эти сигналы, ты отвечаешь на вопрос «что и сколько утекло», который обычно и
стоит в задаче.

## Политики, ACL и Public Access Block

Публичность бакета определяется **bucket policy** и **ACL**, а блокируется настройкой
Public Access Block. Проверка:

```
$ aws s3api get-public-access-block --bucket b
$ aws s3api get-bucket-policy --bucket b --query Policy --output text
$ aws s3api get-bucket-acl --bucket b
```

В политике ищи `"Principal": "*"` и `"Effect": "Allow"` без условия — это открытый
доступ. Важный форензик-аспект: **изменение** политики логируется в CloudTrail
(`PutBucketPolicy`), поэтому можно установить, когда бакет стал публичным и кто это
сделал — атакующий или неосторожный администратор.

## Версионирование, Delete Markers и Object Lock

Включённое версионирование хранит все версии объекта. Удаление создаёт **delete
marker** (объект «исчезает», но версии целы):

```
$ aws s3api list-object-versions --bucket b --prefix report
$ aws s3api get-object --bucket b --key report.pdf --version-id 3sL4kqtJlcpXroDTDmJ --out report.pdf
```

Так восстанавливают удалённое и видят историю изменений. **Object Lock** (WORM) делает
версии неизменяемыми — полезно для доказательств, но мешает «зачистке». Если видишь
массовое `DeleteObject`, проверь, не было ли это попыткой anti-forensics, и восстанови
версии.

## Другие облака: GCS и Azure Blob

- **Google Cloud Storage** — логи в Cloud Logging (Data Access logs, тоже надо
  включать), поле `principalEmail`, `resourceName`.
- **Azure Blob** — логи в Storage Analytics (`$logs` контейнер) и Activity Log;
  идентичность — `callerIpAddress`, `identity`.
- Везде логика одна: **кто (identity), что (объект), когда, откуда (IP), чем
  (UA)**. Отличаются только имена полей и способы включения логирования.

## Что писать в отчёте

Укажи источник логов (server access / CloudTrail data events / Storage Analytics),
период, список операций и ключей, затронутых клиентов, объём выгруженных данных,
признаки смены прав и восстановленные версии. Каждое утверждение подкрепляй строкой
лога. Отдельно отметь, было ли логирование включено на момент инцидента — если нет,
честно зафиксируй пробел.

## Практический разбор: дело об утечке

Из компании утекли персональные данные, хранившиеся в S3. Ход расследования:

1. **Собираем логи.** Server access logs бакета + CloudTrail management events. Если
   data events были включены — берём и их.
2. **Ищем аномалию.** Сортируем по IP и User-Agent, смотрим новых клиентов:

```
$ awk '{print $5, $9, $10}' access.log | sort | uniq -c | sort -rn | head -20
```

3. **Проверяем паттерн.** Кто-то сделал `ListBucket`, затем серию `GET` на `*.csv`,
   `backup*.sql` — классическая эксфильтрация.
4. **Идентифицируем клиента.** По `arn` видно, ключом какого пользователя/роли
   пользовались; по `sourceIPAddress` — откуда; по `userAgent` — чем (rclone, aws-cli).
5. **Считаем объём.** Суммируем отданные байты по этому клиенту — получаем оценку
   утечки.
6. **Проверяем права.** Не стал ли бакет публичным (`PutBucketPolicy`) и кто это сделал.
7. **Фиксируем.** Прикладываем строки логов, времена в UTC, IP и identity.

Итог — воспроизводимая картина: кто, когда, чем и сколько выкачал.

## Сопоставление с другими источниками

Логи хранилища почти никогда не единственный источник. Полезно сопоставить:

- **логи веб-приложения/прокси** — тот же IP/сессия заходил в приложение?
- **IAM-логи** — создавался ли новый ключ доступа перед инцидентом;
- **сетевые потоки (VPC Flow Logs)** — подтверждают объём и направление трафика;
- **логи CI/CD** — не «слил» ли ключ пайплайн;
- **DNS-логи** — обращения к `s3.amazonaws.com` и endpoint-ам.

Совпадение времени и клиента в двух источниках резко повышает достоверность вывода.

## Инструменты и запросы

- **`aws s3api`** — `list-object-versions`, `get-bucket-policy`, `get-bucket-acl`;
- **`aws cloudtrail lookup-events`** — поиск по EventName;
- **`grep`/`awk`/`sort`** — быстрый анализ access-логов;
- **Athena/CloudWatch Logs Insights** — SQL-запросы к логам на объёме;
- **`jq`** — разбор JSON CloudTrail.

Пример запроса Athena по access-логам: выбрать клиентов с суммой отданных байт выше
порога за сутки — сразу видно выбросы.

## Частые ошибки

- **Забывают про часовой пояс.** В логах S3 время в UTC (`+0000`); сравнивая с
  локальными отчётами, переводи зону.
- **Смотрят только access-логи.** Смена прав и создание ключей — только в CloudTrail.
- **Путают identity.** Анонимный доступ (`-`) и доступ роли — разные вещи; различай.
- **Игнорируют User-Agent.** `rclone`/`s3cmd` там, где ожидается только приложение,
  — сильный сигнал.
- **Не проверяют версионирование.** Удалённое может быть восстановлено, и это
  доказательство.

## Мини-шпаргалка по полям

| Поле              | Что означает                                  |
|-------------------|-----------------------------------------------|
| IP клиента        | откуда был запрос                             |
| identity (`arn`)  | чьими правами пользовались                    |
| operation         | `GET`/`PUT`/`LIST`/`DELETE`                   |
| key               | какой объект затронут                         |
| status            | `200` успех, `403` отказ в доступе            |
| bytes sent        | объём выгруженных данных                      |
| User-Agent        | клиент (браузер, CLI, SDK)                    |

Держи эту таблицу под рукой при разборе логов — большинство вопросов снимается
первыми четырьмя полями.

## Мини-чек-лист расследования

1. Собери server access logs и CloudTrail за период.
2. Построй топ клиентов по IP и User-Agent.
3. Найди `ListBucket` + массовые `GET` (эксфильтрация).
4. Проверь смену политик и создание ключей.
5. Проверь публичность бакета (`--no-sign-request`).
6. Восстанови удалённые версии, если нужно.
7. Сопоставь с прокси/приложением/VPC Flow Logs.
8. Зафиксируй выводы со ссылками на строки логов.

Этого набора достаточно для большинства дел об утечке из объектного хранилища.

## Почему это важно

Объектные хранилища — это «свалка» корпоративных данных: бэкапы, дампы БД, документы,
ключи. Именно поэтому они первая цель атакующих и частая причина утечек. Умение
читать логи доступа, проверять публичность и восстанавливать версии превращает
облачное хранилище из чёрного ящика в источник доказательств. Без логов инцидент
остаётся «что-то утекло»; с логами — становится «кто, когда, чем и сколько».
