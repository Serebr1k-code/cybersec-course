## Вопрос, с которого всё начинается

Сотрудника подозревают в утечке: он якобы отправлял документы наружу, а потом всё «стёр». С рабочей станции сняли один файл — `archive.pst`, личный почтовый архив Outlook. Пользователь уверяет, что никаких писем с вложениями не отправлял. Как проверить это по одному файлу?

Из предыдущего урока (`forensics-email`) мы знаем, как читать **заголовки** письма: от кого, кому, через какие серверы шло. Теперь задача другая — достать сами письма из **хранилища**, в том числе те, что пользователь удалил. Здесь мы разберём один архив от начала до конца.

## Наш пример: файл `archive.pst`

Сначала выясняем, что это вообще за файл. Команда `file` смотрит на «магические байты» в начале файла и говорит, какой это формат.

```bash
$ file archive.pst
archive.pst: Microsoft Outlook Personal Folders file, version 23
```

Расширение `.pst` (Personal Storage Table) — это личный архив Outlook. Внутри — не текст, а база на структуре B-дерева в контейнере Microsoft. Читать её глазами бессмысленно, нужен парсер. Самый надёжный — `libpff` (набор утилит `pffinfo`, `pffexport`).

## Шаг 1: смотрим сводку хранилища

Прежде чем что-то экспортировать, получаем «паспорт» архива:

```bash
$ pffinfo archive.pst
pffinfo 20240101

PST file: archive.pst
Encryption: none
Message store type: pst
Number of items: 12453
```

Три важных факта. `Encryption: none` — архив не защищён паролем, читаем свободно. `Number of items: 12453` — это общее число объектов: письма, встречи календаря, контакты, задачи. Если бы тут стояло `Encryption: ...`, нам пришлось бы сначала искать пароль (он может лежать в реестре или в дампе памяти — см. `forensics-memory-keys`).

## Шаг 2: экспортируем всё содержимое

`pffexport` умеет раскладывать хранилище по папкам. Ключ `-m` задаёт, **что** экспортировать: `all` — всё, `items` — только элементы, `attachments` — только вложения, `deleted` — удалённые.

```bash
$ pffexport -m all archive.pst -t out/
$ ls out/
Inbox  Sent Items  Drafts  Deleted Items  Calendar  Contacts
```

Каждая папка Outlook стала каталогом, а письма — отдельными файлами. Теперь вопрос из легенды: отправлял ли он что-то? Смотрим `Sent Items` — что и кому уходило.

## Шаг 3: достаём удалённое

Наивное предположение: удалённых писем нет, ведь пользователь их «стёр». Это неверно. В Outlook удаление — двухступенчатое:

- письмо сначала попадает в **Deleted Items** (удалённые, но восстановимые);
- если удалить и оттуда, оно уходит в **Recoverable Items** (в Exchange/OST это называют «dumpster») и живёт там до истечения политики хранения.

Экспорт с `-m all` папку `Deleted Items` захватывает, но неглубокие «дважды удалённые» элементы надёжнее доставать отдельно. `libpst`-утилита `readpst` умеет то же самое и часто показывает больше:

```bash
$ readpst -D -o out2 archive.pst
$ find out2 -path '*Deleted*' -name '*.eml' | head -3
out2/archive/Deleted Items/Re_ Invoice 4471.eml
out2/archive/Deleted Items/Re_ Q3 numbers.eml
out2/archive/Deleted Items/FW_ password reset.eml
```

Ключ `-D` — «включить удалённые». Без него `readpst` молча пропустит их, и вы решите, что писем не было. Уже по именам видно письмо `Re_ Invoice 4471` — ровно то, что искали.

## Шаг 4: достаём вложения

Письма сами по себе — половина дела. Нагрузку обычно несут **вложения**. Их удобнее выгрузить массово:

```bash
$ pffexport -m attachments archive.pst -t att/
$ find att -type f | head -3
att/Inbox/0000001-application-pdf-invoice.pdf
att/Deleted Items/0000002-application-vnd.ms-word.document.macroEnabled-invoice.docm
att/Sent Items/0000003-application-zip-archive-data.zip
```

Обратите внимание: имя файла кодирует исходное имя MIME-типа и оригинальное имя вложения. Видим `.docm` — документ Word **с макросами**. Именно так выглядят типичные фишинговые нагрузки.

## Шаг 5: фиксируем хеши и разбираем вложение

Для доказательной базы каждое вложение хешируем — хеш (отпечаток содержимого) позволяет позже доказать, что файл не подменяли, и сверить его с VirusTotal.

```bash
$ sha256sum att/Deleted\ Items/*.docm
3f9a...c1  att/Deleted Items/0000002-...-invoice.docm
$ file att/Deleted\ Items/*.docm
...: Microsoft Word 2007+ (ZIP)
```

Дальше `.docm` разбираем как Office-документ с макросом — этим занимается следующий урок (`forensics-office-macros`), а PDF — урок `forensics-pdf`. Здесь важно зафиксировать: вложение существует, оно подозрительно, его хеш записан.

## Шаг 6: заголовки для атрибуции

Чтобы доказать, что письмо реально **уходило** (а не лежит в черновиках), смотрим заголовки экспортированного `.eml`. Это обычный текст, и в нём есть поля `From`, `To`, `Date` и цепочка `Received` — след прохождения через почтовые серверы.

```bash
$ grep -aE '^(From|To|Date|Subject):' "out2/archive/Deleted Items/Re_ Invoice 4471.eml"
From: Ivan Petrov <i.petrov@corp.example>
To: drop@mailinator.com
Date: Mon, 06 Oct 2025 14:22:07 +0300
Subject: Re: Invoice 4471
```

Теперь картина сложилась: письмо с вложением-макросом ушло на внешний адрес. Ключевое — папка `Deleted Items`, то есть пользователь его удалил, но данные остались.

## Если архив не читается

Иногда `pffinfo` ругается на повреждение, а `file` показывает обрезанный файл. Причины две — шифрование и обрыв записи.

Если архив защищён паролем (`Encryption: ...` в `pffinfo`), пароль ищут не в самом файле, а рядом: в реестре рабочей станции или в дампе оперативной памяти (`forensics-memory-keys`). Без него письма не прочитать.

Если файл **обрезан** (копирование оборвалось), часть писем утеряна, но уцелевшее `libpff` всё равно вытащит — он устойчив к повреждениям:

```bash
$ pffexport -m all broken.pst -t out/
```

А если сам `.pst` был удалён с диска, его вырезают из нераспределённого пространства по сигнатуре `!BDN` (первые байты файла). Это уже задача карвинга (`forensics-carving`):

```bash
$ grep -aboP '\!BDN' disk.img
$ dd if=disk.img of=carved.pst bs=1 skip=<offset> status=none
```

Отдельно стоит помнить про `.ost` — это **кэш Exchange**, а не личный архив. Он может содержать письма, которых уже нет на сервере, и наоборот, поэтому в корпоративном расследовании часто нужны обе стороны.

## Что мы теперь знаем

- `.pst` — это контейнер-база, а не текст; читается парсером (`libpff`/`libpst`), а не глазами.
- `pffinfo` даёт сводку: шифрование, число элементов.
- Удаление в Outlook двухступенчатое: `Deleted Items` → `Recoverable Items`; достать удалённое помогает `readpst -D` и `pffexport -m deleted`.
- Вложения выгружаются ключом `-m attachments`, их хешируют (`sha256sum`) и разбирают отдельно.
- Заголовки `.eml` (`From`/`To`/`Received`) доказывают факт отправки и позволяют атрибутировать.

## Куда дальше

Мы вытащили письмо и подозрительное вложение `.docm`. В следующем уроке (`forensics-office-macros`) мы возьмём ровно такой документ и разберём его макрос: что он запускает, куда обращается, какой PowerShell скачивает. А пока главное запомни: **удалённое в Outlook не исчезает — оно переезжает в Deleted Items и Recoverable Items, и оттуда его достаёт `readpst -D` или `pffexport -m deleted`**.

## Где пригодится

- **CTF:** задачи с почтовым архивом и вложением-малварью.
- **DFIR:** анализ фишинга, переписки злоумышленника, утечек.
- **Корпоративные расследования:** доказательство факта переписки и отправки.
- **Анализ малвари:** извлечение вложений для YARA/VT.
- **Судебная экспертиза:** восстановление удалённой переписки с сохранением целостности.
