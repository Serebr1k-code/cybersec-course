## Вопрос, с которого всё начинается

Подозрение на утечку данных: кто-то мог выгружать файлы наружу. Журналы прокси неполные, но
Windows ведёт собственную базу сетевой активности по приложениям. Где она и как из неё
увидеть, **какое приложение и сколько передало**?

## Наш пример: SRUDB.dat

```
C:\Windows\System32\sru\SRUDB.dat
```

```
$ file SRUDB.dat
SRUDB.dat: Extensible Storage Engine (ESE) Database File (edb)
```

Это **ESE-база**, тот же движок, что у `Windows.edb`. Парсить надо инструментом,
понимающим ESE, а не текстовым просмотром.

## Что такое SRUM

**SRUM (System Resource Usage Monitor)** — подсистема Windows, которая собирает статистику
использования ресурсов: сколько данных приложение передало по сети, сколько CPU/диска
потратило, как долго работало. Данные хранятся в `SRUDB.dat` с привязкой к приложению и
пользователю.

Для форензики SRUM ценен тем, что показывает **сетевую активность в разрезе приложений** —
это прямой ответ на вопрос «кто и сколько передал наружу».

## Шаг 1: разобрать ESE-базу

На Windows — **SRUMDump** (Mark Baggett) или `esedbexport` (libyal), на Linux —
`esedbexport` плюс скрипт-обёртка:

```
$ esedbexport -t out SRUDB.dat
$ ls out.1
SruDbIdMapTable.table  NetworkUsages.table  ...
```

Таблица **`NetworkUsages`** — то, что нам нужно: сетевой трафик по приложениям.

## Шаг 2: связать ID приложения с именем

В SRUM приложения хранятся как числовые **AppId**. Чтобы получить имя, используется таблица
**`SruDbIdMapTable`**:

```
$ grep -a -i svchost out.1/SruDbIdMapTable.table
42  \Device\...\svchost.exe
```

Связка «AppId → имя процесса» обязательна: без неё выгрузка трафика бессмысленна.

## Поля NetworkUsages и их смысл

| Поле | Смысл | Как использовать |
|------|-------|------------------|
| AppId | идентификатор приложения | связать с именем процесса |
| UserId | пользователь | отделить сессии |
| BytesSent | байт передано | искать большие выгрузки |
| BytesRecv | байт принято | искать загрузки |
| Timestamp | интервал | вписать в таймлайн |

## Как выявить эксфильтрацию

Метод прост: отсортировать приложения по `BytesSent` за интересующий период и посмотреть на
аномалии. Большая передача у неизвестного приложения, или всплеск у `powershell.exe`,
`curl.exe`, `rclone.exe` — сильный сигнал. Дальше связываем с другими артефактами: Prefetch
(запуск утилиты), AmCache (хеш и путь), сетевые логи (куда именно шла передача). Так SRUM
превращается из «статистики» в **доказательство выгрузки данных**.

## Ограничения и подводные камни

- **Не все приложения.** SRUM собирает данные не для каждого процесса; отсутствие записи не
  означает отсутствия трафика.
- **Интервалы, а не точные времена.** Данные агрегированы по интервалам (обычно час), не по
  отдельным пакетам.
- **Срок хранения.** База ротируется; старые записи исчезают — работай с историческим
  снимком, если он есть.
- **Идентификаторы.** Без `SruDbIdMapTable` AppId бесполезен.
- **Сброс данных.** Пользователь может очистить SRUM; отсутствие — не доказательство.

## Шпаргалка команд

```
# Разобрать ESE
esedbexport -t out SRUDB.dat
# Windows
SRUMDump.exe -f SRUDB.dat --csv out

# Найти имена процессов
grep -a -i '<имя>' out.1/SruDbIdMapTable.table

# Топ по переданным байтам (после выгрузки NetworkUsages)
sort -t, -k4 -nr out.1/NetworkUsages.csv | head
```

## Что мы теперь знаем

- SRUM хранится в `C:\Windows\System32\sru\SRUDB.dat` и это ESE-база.
- Таблица `NetworkUsages` даёт сетевой трафик по приложениям и пользователям.
- Имена приложений берутся из `SruDbIdMapTable` по AppId.
- Сортировка по `BytesSent` выявляет возможную эксфильтрацию.
- Данные агрегированы по интервалам и ротируются.

## Сквозной пример: выявление эксфильтрации через SRUM

Разберём инцидент целиком. Дано: подозрение на утечку данных, сетевые логи неполные. Задача —
по базе SRUM понять, какое приложение и сколько передало наружу.

Шаг первый — разбираем `SRUDB.dat` и выгружаем таблицу `NetworkUsages`. Шаг второй — через
`SruDbIdMapTable` связываем числовые `AppId` с именами процессов. Шаг третий — сортируем по
`BytesSent` за интересующий период. Видим аномалию: неизвестный процесс передал сотни
мегабайт, тогда как обычные приложения — килобайты. Шаг четвёртый — для подозрительного
процесса ищем подтверждения: Prefetch (запускался), AmCache (путь и хеш), журналы (вход
пользователя). Шаг пятый — сопоставляем с сетевыми логами, если они есть, чтобы узнать
назначение (адрес/домен).

Итог: SRUM дал **объём и направление** передачи по приложению, а связка с другими
артефактами — контекст: какая программа, кем запущена и когда. Это стандартный путь
расследования утечки, когда прокси-логи неполны.

## Агрегация по интервалам: как читать временные метки

SRUM хранит данные не по отдельным пакетам, а **агрегированно по интервалам** (обычно час).
Это значит, что ты не увидишь точное время каждого соединения — только «в этот интервал
приложение передало столько байт». Для расследования это нормально: цель SRUM — выявить
**факт и объём** передачи, а точное время уточняется по другим логам. Помни об этом, чтобы не
делать ложных выводов: всплеск в интервале не означает, что передача шла всю минуту — она
могла произойти за секунды внутри часа.

## Полный прогон: от байтов к атрибуции

Хороший разбор утечки строится так. Сначала SRUM: топ приложений по `BytesSent`. Затем для
подозрительного приложения — путь и хеш через AmCache и Prefetch. Затем пользователь,
от имени которого шла передача, — из `UserId` и журналов входа. Затем сетевые логи (прокси,
файрвол) — куда именно шла передача. В конце — вывод: какая программа, от чьего имени и куда
передала данные. Каждый шаг опирается на отдельный источник, и вместе они дают атрибуцию, а
не просто «была сетевая активность».

## Что фиксировать в отчёте

Укажи путь к `SRUDB.dat`, инструмент разбора, период данных, таблицу `NetworkUsages`, имена
процессов и объёмы (`BytesSent`/`BytesRecv`). Оговори агрегацию по интервалам и срок хранения
базы. Если удалось связать передачу с конкретным адресом, приведи и его, но с пометкой об
источнике. Так отчёт показывает и технический факт, и его ограничения.

## Продвинутый разбор: пользователи, приложения и аномалии

SRUM полезен не только объёмами. Он привязывает активность к **пользователю** (`UserId`) и
**приложению** (`AppId`), поэтому отвечает на вопрос «кто именно» и «чем именно». Это важно,
когда на машине несколько учётных записей: всплеск трафика может принадлежать не тому
пользователю, которого вы подозреваете. Отдельно смотри системные и служебные процессы: у
них часто есть фоновый трафик (обновления, телеметрия), и его надо уметь отличать от
аномалий, чтобы не поднять ложную тревогу.

Как искать аномалии: построй топ приложений по `BytesSent` и сравни с обычным профилем
машины. Неизвестный процесс в топе, скриптовый интерпретатор с большим исходящим объёмом,
клиент облачного хранилища там, где его не должно быть, — всё это сигналы. Дальше ищи
подтверждение в других артефактах и в сетевых логах. И не забывай про **входящий** трафик
(`BytesRecv`): большая загрузка тоже бывает признаком — например, доставки инструмента.

## Ограничения и что делать при ротации базы

SRUM хранит данные ограниченное время и ротирует их. Если интересующий период уже вытеснен,
текущая `SRUDB.dat` бесполезна — ищи **теневые копии тома**, где сохранилась более ранняя
версия базы. Сравнение двух снимков (старой и новой базы) позволяет восстановить активность,
которая уже исчезла. Это стандартный приём: когда «живые» данные вычищены ротацией или
чистильщиком, работай с историческим снимком. В отчёте укажи, из какого снимка взяты данные и
за какой период, — иначе вывод будет выглядеть произвольным.

## Практический чек-лист по SRUM

Порядок работы прост и воспроизводим. Первое — определи, что перед тобой ESE-база, и выбери
инструмент (`esedbexport`/`SRUMDump`). Второе — выгрузи таблицу `NetworkUsages`. Третье —
обязательно свяжи `AppId` с именами через `SruDbIdMapTable`; без этого шага цифры
бессмысленны. Четвёртое — построй топ приложений по `BytesSent` и `BytesRecv` за интересующий
период. Пятое — для аномалий найди подтверждения в Prefetch, AmCache и журналах. Шестое —
зафиксируй период данных и ограничение агрегации. В конце сохрани выгрузку в CSV как
приложение к отчёту. Каждый шаг опирается на один источник и легко проверяется повторно.

## Частые ошибки при работе с SRUM

Соберём типичные промахи в одном месте. Первый — читать `SRUDB.dat` как текст и делать выводы
по обрывкам строк: нужен полноценный разбор ESE. Второй — забыть про `SruDbIdMapTable` и
приводить числовые `AppId` без имён процессов; такие цифры ничего не значат. Третий — путать
агрегированные интервалы с точным временем и утверждать, что передача шла «ровно в 14:00»,
хотя данные относятся к часу целиком. Четвёртый — не отделять фоновый трафик системных служб
от аномалий и поднимать ложную тревогу. Пятый — игнорировать ротацию базы и делать вывод об
отсутствии активности по усечённым данным. Учитывая эти пять пунктов, ты будешь читать SRUM
корректно и не переоценивать его точность.

Помни главное: SRUM показывает объём и направление сетевой активности по приложениям, но не заменяет точные сетевые логи.

## Куда дальше

Модуль глубокого разбора выполнения закрыт: Prefetch (запуск), ShimCache (присутствие),
AmCache (хеш), SRUM (сеть). Дальше ветка уходит в **инфраструктурные артефакты Windows**
(SMB, WinRM, GPO, печать). А пока главное запомни: **SRUM — это сетевой след по приложениям**.

## Где пригодится

- **CTF Forensics:** задачи про утечку/передачу данных.
- **DFIR:** оценка объёма выгрузки при инциденте.
- **Threat Hunting:** аномалии сетевой активности процессов.
- **Работа:** форензика конечных точек, data-exfiltration расследования.
