## Вопрос, с которого всё начинается

Файлы реестра на диске повреждены или зашифрованы. Но реестр был загружен в память —
и его можно оттуда достать. Разберём.

## Наш пример: дамп Windows

## Шаг 1: реестр в памяти

Ядро держит загруженные кусты в памяти. Volatility умеет их находить:

```
$ vol.py -f mem.raw windows.registry.hivelist
Offset      FileFullPath
0x...  \SystemRoot\System32\Config\SOFTWARE
0x...  \??\C:\Users\Ivan\NTUSER.DAT
```

`hivelist` перечисляет загруженные кусты и их адреса в памяти.

## Шаг 2: дампим куст

```
$ vol.py -f mem.raw windows.registry.hivedump --hive-offset 0x... -o SOFTWARE.hive
```

Получаем настоящий файл-куст, который можно открыть RegRipper/Registry Explorer.

## Шаг 3: зачем

- файлы на диске зашифрованы (BitLocker без ключа) — память даёт реестр;
- куст повреждён — память даёт целую версию;
- нужно **актуальное** состояние (на момент снятия).

## Шаг 4: что искать

- автозапуск (`Run`);
- недавние изменения;
- подключённые USB;
- пароли/секреты (иногда в открытом виде);
- конфигурацию.

## Шаг 5: практика

- дампи **все** кусты (SYSTEM, SOFTWARE, SAM, SECURITY, NTUSER);
- анализируй RegRipper-плагинами;
- сопоставляй с дисковыми копиями (расхождения = активность).

## Шаг 6: какие кусты искать первыми

`hivelist` показывает все загруженные кусты. Приоритет такой:

- `SYSTEM` — службы, драйверы, USB;
- `SOFTWARE` — установленный софт, Run;
- `SAM` — локальные пользователи;
- `SECURITY` — LSA-секреты;
- `NTUSER.DAT` — активность пользователя.

```
$ vol.py -f mem.raw windows.registry.hivelist | grep -iE 'SYSTEM|SOFTWARE|SAM|SECURITY'
```

## Шаг 7: дамп всех кустов сразу

Вместо по одному — скриптом по адресам:

```
$ for off in $(vol.py -f mem.raw windows.registry.hivelist --json | jq -r '.[].Offset'); do
    vol.py -f mem.raw windows.registry.hivedump --hive-offset $off -o hive_$off
  done
```

Так получаешь полный набор для RegRipper за один проход.

## Шаг 8: разбор RegRipper

```
$ rip.pl -r SOFTWARE.hive -p run
$ rip.pl -r SYSTEM.hive -p services
```

`-p run` показывает автозапуск, `-p services` — службы. Это быстрый ответ на вопрос «что стартовало само».

## Шаг 9: сравнение с диском

Если есть и дисковый, и «памятный» куст — сравни:

```
$ diff <(rip.pl -r disk_SOFTWARE.hive -p run) <(rip.pl -r mem_SOFTWARE.hive -p run)
```

Расхождение означает, что реестр меняли уже после последней записи на диск — то есть в момент снятия дампа.

## Шаг 10: что искать

- автозапуск (`Run`, службы);
- подключённые USB;
- локальных пользователей;
- LSA-секреты;
- расхождения диск/память.

## Шаг 11: когда диск недоступен

Главный сценарий для этого урока: диск зашифрован BitLocker, а ключ утерян, либо куст повреждён. Память же содержит загруженные кусты в открытом виде — потому что ядро работает с ними постоянно. Дамп памяти становится «обходом» шифрования диска, что делает его ключевым артефактом в сложных делах.

## Шаг 12: транзакционные логи реестра

У каждого куста есть файлы `.LOG1`/`.LOG2` — журналы транзакций. Если куст на диске «грязный» (незавершённая запись), его состояние достраивают, проиграв логи. Из памяти обычно достаётся уже консистентный куст, но логи полезны, чтобы понять **какие последние изменения** не успели записаться на диск:

```
$ ls /var/lib/...  # .LOG1 .LOG2 рядом с кустом
```

## Шаг 13: сличение с файловым кэшем

Volatility умеет находить не только кусты, но и файловый кэш. Иногда один и тот же куст присутствует и как файл, и как загруженный образ — их сравнение показывает, что изменилось после последнего сброса на диск. Это прямой индикатор «живой» активности в момент снятия дампа.

## Шаг 14: практический кейс

Сценарий: после инцидента злоумышленник очистил журналы и удалил ключи автозапуска из реестра. Действия:

1. снять/взять дамп памяти;
2. перечислить кусты (`hivelist`);
3. сдампить `SOFTWARE` и `SYSTEM`;
4. прогнать RegRipper на `run` и `services`;
5. сравнить с дисковыми кустами — найти удалённое.

Результат — восстановленные ключи автозапуска, которых на диске уже нет.

## Практика: восстанавливаем автозапуск из дампа

Сценарий: на диске реестр почищен, ключ автозапуска удалён. Работаем с дампом памяти.

Перечисляем кусты:

```
$ vol.py -f mem.raw windows.registry.hivelist | grep -i software
0xffff...  \SystemRoot\System32\Config\SOFTWARE
```

Дамим SOFTWARE:

```
$ vol.py -f mem.raw windows.registry.hivedump --hive-offset 0xffff... -o SOFTWARE.hive
```

Разбираем RegRipper:

```
$ rip.pl -r SOFTWARE.hive -p run | grep -i 'CurrentVersion\\Run'
Run  HKLM\...\Run  Updater = C:\Users\ivan\AppData\updater.exe
```

Ключ `Updater` найден — на диске его уже нет. Смотрим детали:

```
$ rip.pl -r SOFTWARE.hive -p run | grep -A2 Updater
LastWrite: 2026-01-14 03:19:55
```

Время последней записи ключа совпадает с инцидентом. Теперь проверим, что это тот же реестр, что был на диске:

```
$ diff <(rip.pl -r disk_SOFTWARE.hive -p run) <(rip.pl -r SOFTWARE.hive -p run)
> Run Updater = ...
```

Строка есть только в «памятной» версии — доказательство, что ключ удалили с диска уже после снятия дампа.

## Что важно

- Память отдаёт куст целиком, даже если на диске он почищен.
- `hivelist` → `hivedump` → RegRipper — рабочий конвейер.
- `LastWrite` ключа датирует изменение.
- Diff диск/память доказывает удаление ключа.

## Ограничения метода

Реестр из памяти достаётся не всегда и не целиком.

**Куст может быть не найден.** Если `hivelist` не показывает нужный куст, проверь версию/профиль Volatility и корректность символов. Без подходящего профиля адреса неверны.

**Частичный дамп.** При снятии памяти часть страниц могла быть выгружена на диск (`pagefile`). Тогда куст окажется «дырявым»; фрагменты можно поискать в `pagefile.sys` отдельно.

**Устаревший снимок.** Память отражает состояние на момент снятия. Если дамп сняли позже инцидента, а систему перезагружали, — загруженные кусты уже «новые», и следов может не быть.

**Ложные срабатывания.** RegRipper выдаёт и нормальные записи. Сравнение с дисковым кустом отделяет норму от аномалии.

**Юридический аспект.** Дамп памяти содержит персональные данные и секреты. Обращайся с ним как с чувствительным доказательством: фиксируй хэш, не изменяй оригинал.

Вывод: память — ценный, но нестабильный источник. Всегда подкрепляй её дисковыми артефактами.

## Что мы теперь знаем

- Загруженные кусты живут в памяти.
- `hivelist` находит их, `hivedump` извлекает.
- Память спасает, когда диск зашифрован/повреждён.
- Из кустов достаём автозапуск, USB, секреты.
- Дампь все кусты и сопоставляй.

- Приоритетные кусты: SYSTEM, SOFTWARE, SAM, SECURITY, NTUSER.
- Дампят все кусты скриптом.
- RegRipper (`-p run`, `-p services`) разбирает куст.
- Сравнение диск/память выявляет «живые» правки.
- Из кустов достаём USB, автозапуск, секреты.

- Память даёт кусты в открытом виде, даже если диск зашифрован.
- Файлы `.LOG1`/`.LOG2` показывают незаписанные транзакции.
- Сравнение куста из памяти и с диска выявляет «живые» правки.
- Кейс: удалённые ключи автозапуска восстанавливаются из дампа.

## Если не сработало

- Hive не найден? Проверь профиль/версию.
- Куст повреждён в дампе? Пробуй другие адреса.
- Нужен разбор? Используй RegRipper.

## Как устроен куст: regf, hbin и ячейки

Чтобы понимать, что именно вы вырезаете из дампа, полезно знать формат куста.
Файл-куст начинается с сигнатуры **`regf`** — первых четырёх байт. Дальше идут
**hbin**-блоки («hive bin», обычно по 4096 байт), а внутри них — **ячейки** (cells):
небольшие блоки, в которых лежат ключи, значения и списки. Ячейка начинается с
4-байтного поля размера (знакового: положительный — занята, отрицательный — свободна).

```text
+--------+  сигнатура "regf"
| regf   |  заголовок куста: номер последовательности, время последней записи
+--------+
| hbin   |  блок; внутри — ячейки
|  cell  |  ключ (nk), значение (vk), список (lf/lh/li/ri), данные
|  cell  |
|  ...   |
+--------+
```

Это важно для практики: **`hivelist` в Volatility ищет в памяти сигнатуру `regf`** и
оттуда вычисляет адрес куста. Если куст повреждён в начале, но цел в середине,
инструмент может его не найти. Тогда применяют **carving**: сканируют дамп на
сигнатуру `hbin` и вырезают блоки вручную. Именно так восстанавливают реестр, когда
заголовок куста уже перезаписан.

## Carving руками: когда Volatility бессилен

Если плагин не находит куст, работает поиск по сигнатурам в самом файле дампа:

```bash
$ grep -abo 'hbin' mem.raw | head
1048576:hbin
1052672:hbin
1056768:hbin
```

Каждое совпадение — начало блока. Блоки одного куста идут подряд с шагом 4096,
поэтому, найдя цепочку, её вырезают и собирают обратно в файл, добавив заголовок
`regf` из соседней (уцелевшей) копии куста. Полученный «сшитый» куст открывают в
Registry Explorer. Метод кропотливый, но он вытаскивает данные, которые обычный
дамп-плагин пропустил.

## Почему снимать память нужно быстро

Загруженные кусты меняются постоянно: система пишет в реестр при каждом запуске
службы, установке программы, подключении USB. Поэтому дамп памяти — это **снимок
одного мгновения**, и его ценность падает с каждой минутой после инцидента. Если
сначала перезагрузить машину, а потом снять дамп, вы получите «чистый» реестр без
следов атаки: вредоносные ключи автозапуска могли быть удалены при штатном
завершении, а сами кусты — перечитаны заново с диска. Отсюда золотое правило DFIR:
**память снимают до всего остального**, до перезагрузки и до любых «исправлений».
