## Вопрос, с которого всё начинается

Ты снял образ с серверного тома Windows Server. Открываешь его привычным набором для
NTFS — `fls`, `icat`, `MFTECmd` — и ничего: таблица `$MFT` не находится, дерево файлов
пустое, будто на диске нет данных. А данные точно есть. Диск размечен не NTFS, а **ReFS**.
Как её опознать и что с ней делать?

## Что такое ReFS

**ReFS (Resilient File System, «устойчивая файловая система»)** — формат Microsoft,
появившийся в Windows Server 2012 и развиваемый в Server 2016/2019/2022. Слово
*resilient* — «устойчивый»: система спроектирована переживать повреждения носителя и
хранить целостность данных. ReFS ставят на серверы: тома Hyper-V, Storage Spaces,
большие архивы. На клиентских Windows она встречается редко.

Главное отличие от NTFS лежит в **архитектуре метаданных**. В NTFS всё завязано на одну
таблицу `$MFT` (Master File Table) — каждая запись в ней описывает один файл. В ReFS
единой таблицы **нет**: метаданные разложены по **B+-деревьям** (сбалансированным
деревьям поиска, где данные лежат в листьях и отсортированы). Именно поэтому NTFS-парсер
не находит `$MFT` и молчит.

## Наш пример: том с меткой ReFS

Откроем образ и посмотрим самые первые байты. У любого тома Windows есть **boot sector** —
первый сектор (512 байт), с которого начинается файловая система:

```
$ ls -la
-rw-r--r--  1 student student  4194304 refs.img
$ xxd -l 16 refs.img
00000000: 5265 4653 2020 2020 0002 0800 0000 0000  ReFS    ........
```

Видишь `ReFS` в самом начале? Это **OEM-поле** boot sector — строка, которой файловая
система подписывает себя. У NTFS здесь было бы `NTFS    `. То есть первое, что мы делаем
с незнакомым образом, — смотрим начало и читаем подпись. Тут она однозначна: **ReFS**.

## Шаг 1: подтвердить, что это действительно ReFS

Подписи недостаточно — можно наткнуться на копию или на данные, случайно похожие на текст.
Дополнительные признаки ReFS:

- размер **кластера** и **страницы метаданных** задаются в boot sector (у ReFS страница
  метаданных обычно 16 КБ);
- на томе есть область **object table** — таблица объектов (файлов, каталогов, потоков);
- включены **integrity streams**, если том создавали с контролем целостности.

Посмотрим текстовые метаданные образа — `strings` вытаскивает всё, что похоже на текст:

```
$ strings refs.img
ReFS
META: ReFS B+ tree root @ page 2
ObjectTable: 512 entries
IntegrityStreams: enabled
NOTE: nto{r3fs_bplus_tr33_r3s1l13nt}
```

Мы видим подтверждение: корень B+-дерева, таблица объектов и признак integrity streams.
А заодно — метку, которую кто-то оставил в метаданных. В CTF такие метки и есть флаг.

## Шаг 2: как устроены метаданные ReFS

Чтобы осмысленно работать с ReFS, запомни её ключевые структуры:

| Структура | Аналог в NTFS | Назначение |
|-----------|---------------|------------|
| B+-дерево метаданных | `$MFT` | описание объектов тома |
| Object table | записи MFT | таблица объектов (файл/каталог/поток) |
| Integrity streams | `$Secure`/checksums | контроль целостности данных |
| Allocation bitmap | `$Bitmap` | занятость кластеров |
| Block cloning | — | «дешёвое» копирование диапазонов |

Важное следствие для аналитика: **адресация объектов идёт через деревья**, поэтому
прямого «пробега по MFT» не существует. Инструменты ReFS читают деревья и строят
список объектов уже поверх них.

## Шаг 3: метки времени и целостность

ReFS хранит метки времени **не в `$STANDARD_INFORMATION`**, как NTFS, а внутри метаданных
объекта. Это значит, что привычные рассказы «SI vs FN» к ReFS не применимы: сравнивать
две шкалы времени, как в NTFS, здесь не получится. Зато ReFS добавляет то, чего нет в
NTFS: **integrity streams** — контрольные суммы на данные. Если integrity включён, любое
повреждение блока видно сразу, а сам том может самовосстанавливаться (при наличии копии).

Практический вывод: при расследовании на ReFS ищи не расхождение таймстемпов, а
**журнал операций и признаки block cloning** — клонирование блоков оставляет файлы,
которые «делят» одни и те же данные, и это часто объясняет странные результаты recovery.

## Восстановление и удаление

ReFS не поддерживает in-place обновление метаданных и использует копирование при записи,
поэтому **удалённые данные живут дольше**: блок перезаписывается только когда освобождённый
кластер реально понадобится. Но имён удалённых объектов в лёгкой форме может не остаться —
B+-дерево перестраивается. Для восстановления применяют:

- **`refsutil salvage`** — встроенная утилита Windows Server для спасения данных с
  повреждённого ReFS-тома (режимы `-x` — извлечь файлы, `-f` — указать том);
- **X-Ways Forensics / EnCase** — коммерческие пакеты с поддержкой ReFS;
- **raw carving** — если метаданные недоступны, содержимое файлов достают по сигнатурам.

## Частые ошибки и подводные камни

- **Ожидание `$MFT`.** Первая ошибка новичка — искать MFT на ReFS. Её там нет; не
  тратьте время на NTFS-парсеры.
- **Путаница с ReFS-версиями.** Формат менялся (1.1, 3.x). Старый парсер может не понять
  новый том.
- **Integrity streams и копии.** Том с integrity может содержать дублирующиеся блоки —
  не принимайте их за дубликаты файлов.
- **Storage Spaces.** ReFS часто лежит поверх Storage Spaces; тогда физический образ —
  это не один диск, а пул. Сначала соберите виртуальный диск из пула, потом читайте ФС.
- **`file` не поможет.** Команда `file` не всегда узнаёт ReFS; опознавайте по OEM-полю
  вручную.

## Мини-практика

Перед тобой `refs.img`. Нужно подтвердить тип ФС и вытащить метку из метаданных.

```
$ xxd -l 16 refs.img
00000000: 5265 4653 2020 2020 0002 0800 0000 0000  ReFS    ........
$ strings refs.img | grep nto > answer.txt
$ cat answer.txt
NOTE: nto{r3fs_bplus_tr33_r3s1l13nt}
```

Два шага: подтвердили подпись `ReFS` и вытащили текстовую метку. В реальном деле вместо
метки ты искал бы имена объектов и содержимое через `refsutil salvage`.

## Что мы теперь знаем

- ReFS опознаётся по OEM-полю `ReFS` в boot sector, а не по `$MFT`.
- Метаданные ReFS живут в B+-деревьях; единой таблицы файлов нет.
- Integrity streams дают контроль целостности — то, чего нет в NTFS.
- Удалённые данные живут дольше из-за copy-on-write, но имена могут не сохраниться.
- Инструменты: `refsutil salvage`, X-Ways, EnCase.

## ReFS и Storage Spaces: сначала собери диск

На серверах ReFS почти никогда не лежит на «голом» диске — она работает поверх
**Storage Spaces** (программного RAID Microsoft). Это значит, что образ, снятый с
физического носителя, может быть лишь **частью пула**, а не готовым томом. Прежде чем
читать файловую систему, виртуальный диск нужно **собрать** из составляющих.

Порядок действий:

1. Определи, из каких физических дисков собран пул (метаданные Storage Spaces лежат в
   начале каждого диска).
2. Восстанови **layout**: зеркало, чётность (parity) или simple (JBOD).
3. Собери виртуальный том в порядке чередования (stripe) и получи единый образ.
4. Только после этого читай ReFS.

Если пропустить этот шаг, инструмент увидит «мусор»: данные разложены по нескольким
дискам, и на одном из них нет ни boot sector, ни деревьев. Типичный признак такой
ошибки — boot sector читается, а object table «пустой».

## Что фиксировать в отчёте

Форензик-отчёт по ReFS отличается от NTFS-отчёта. Вместо «дампа $MFT» фиксируют:

| Что | Зачем |
|-----|-------|
| Версия ReFS и размер кластера | совместимость с инструментами |
| Признак integrity streams | объясняет дубли блоков |
| Список объектов (object table) | что вообще было на томе |
| Признаки block cloning | какие файлы «делят» данные |
| Источник тома (Storage Spaces) | как собран образ |

Это важно для оценки достоверности: если том собран из зеркала с ошибками, часть
данных может быть неполной.

## Сравнение инструментов ReFS

| Инструмент | Плюсы | Минусы |
|------------|-------|--------|
| `refsutil salvage` | встроен в Windows Server | только Windows, ограниченные режимы |
| X-Ways Forensics | полный разбор ReFS, GUI | коммерческий |
| EnCase | поддержка ReFS, отчёты | дорогой, тяжёлый |
| raw carving | работает без метаданных | теряются имена и структура |

## Проверка гипотезы «это ReFS»

Когда подпись сомнительна, используй простой чек-лист. Он экономит часы:

```
$ xxd -l 16 image.img        # OEM-поле: ReFS, а не NTFS
$ xxd -s 0x200 -l 8 image.img # параметры кластера/страницы
$ strings -n 8 image.img | grep -i 'b+ tree'
```

Если три признака совпали — перед тобой ReFS. Если `strings` не находит ни «b+ tree»,
ни «integrity», возможно, том пустой или повреждён; тогда сначала проверь целостность
носителя, а не ФС.

Ещё одна тонкость: **ReFS не поддерживает загрузку ОС**. Том с ReFS — это всегда том
данных. Поэтому искать на нём `\Windows\System32` бессмысленно, и отсутствие системных
файлов не означает, что образ «пустой».

## Куда дальше

Мы разобрали серверный ReFS. Дальше возьмём **оптические и firmware-образы** — ISO9660
и UDF: там данные прячутся в дескрипторах тома, Joliet/Rock Ridge и slack-пространстве.
А пока главное запомни: **нет `$MFT` — смотри OEM-поле и B+-деревья**.

## Где пригодится

- **CTF Forensics:** образы серверных томов, которые не открываются NTFS-инструментами.
- **DFIR:** расследование на Windows Server со Storage Spaces и ReFS.
- **Пентест:** анализ вывезенных серверных дисков.
- **Работа:** восстановление данных с ReFS после сбоя.
