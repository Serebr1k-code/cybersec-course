## Вопрос, с которого всё начинается

До сих пор мы работали с образами — снял диск, принёс, анализируешь. Но что делать, если систему **нельзя выключить**? Это критичный сервер, или в памяти ещё живёт вредоносный процесс, который исчезнет при перезагрузке. Тогда применяют **live-forensics** — сбор данных с работающей системы.

## Наш пример: «странный» Linux-сервер

Есть работающий Linux-сервер, который вдруг начал отдавать данные наружу. Выключать его нельзя. Мы собираем улики, пока он жив. Главный принцип здесь — **порядок волатильности**: сначала забирают то, что исчезнет быстрее всего, и только потом то, что живёт долго.

Классический порядок (от самого недолговечного):

1. **Регистры и кэш CPU** — исчезают мгновенно, на практике почти недоступны.
2. **Память (RAM)** — процессы, соединения, ключи, расшифрованные данные.
3. **Сетевые соединения, ARP, маршруты** — меняются постоянно.
4. **Запущенные процессы и их состояние** — живут минуты-часы.
5. **Временные файлы, swap** — могут быть перезаписаны.
6. **Диск, логи, реестр** — сохраняются дольше всего.

Собирая диск первым, вы теряете память; собирая память первой, сохраняете максимум. Для CTF правило то же: дали живой образ — начинайте с памяти.

## Шаг 1: снимаем память

Память (RAM) — самое волатильное из доступного. На Linux её снимают утилитой `avml` (Microsoft) или модулем ядра `LiME`:

```bash
$ sudo avml /evidence/mem.lime
$ sha256sum /evidence/mem.lime
9f2c...  /evidence/mem.lime
```

Память снимают **на изолированный носитель** (внешний диск или по сети) и сразу считают хеш. На Windows аналогично работают `winpmem` или `DumpIt`. После сбора дамп разбирают в Volatility3 (см. `forensics-volatility-deep`).

## Шаг 2: сеть — соединения и соседи

Соединения меняются за секунды, поэтому фиксируем их сразу:

```bash
$ ss -tunap
tcp ESTAB 0 0 10.0.0.5:51234 203.0.113.9:443 users:(("update",pid=1234,fd=3))
$ ip neigh        # ARP-таблица: соседи по сети
$ ip route        # маршруты
```

Вот улика: процесс `update` (PID 1234) держит соединение с внешним адресом `203.0.113.9:443`. Не забудьте **DNS-кэш** — он показывает недавние домены.

## Шаг 3: процессы с полными командными строками

```bash
$ ps -eo pid,ppid,user,etime,cmd --sort=-%mem | head
  PID  PPID USER CMD
 1234     1 root /tmp/.hidden/update --daemon
```

Тот же PID 1234, но путь — `/tmp/.hidden/update`. Запуск из скрытой папки в `/tmp` от `root` — сильная аномалия: легитимные демоны там не живут. Полезно вытащить **окружение** процесса — там часто лежат C2-адреса и ключи:

```bash
$ tr '\0' ' ' < /proc/1234/environ
```

## Шаг 4: пользователи, автозапуск, логи

```bash
$ who -a; last -a | head -20          # активные сессии и история входов
$ crontab -l; ls -la /etc/cron.*      # автозапуск
$ systemctl list-units --state=running
$ cp -a /var/log /evidence/var_log    # копируем логи целиком
```

Автозапуск ищут, чтобы найти **персистентность** — как атака переживает перезагрузку. Логи (`/var/log`, `journalctl`) дают контекст: когда процесс появился, что делал.

## Шаг 5: изоляция вывода и хеширование

Золотое правило: **не пишите на скомпрометированный том** — рискуете перезаписать улики. Вывод идёт на внешний носитель:

```bash
$ mount /dev/sdc1 /evidence -o rw,noexec,nosuid
$ sha256sum /evidence/mem.lime > /evidence/mem.sha256
```

Параллельно фиксируйте метаданные: время (UTC), имя аналитика, версию инструмента. Помните: **сами инструменты меняют систему** — создают файлы и процессы; это нужно документировать, чтобы потом не спутать с активностью атакующего.

## Полный порядок сбора

Живой сбор всегда идёт по одному правилу — **от самого волатильного к самому устойчивому**. Запомните порядок:

1. **Память** — RAM, кэши, ключи шифрования.
2. **Сеть** — активные соединения, ARP/соседи, таблица маршрутов.
3. **Процессы** — командные строки, открытые файлы, handles.
4. **Пользователи и сессии** — кто вошёл, что запущено.
5. **Автозапуск и персистентность** — cron, systemd, реестр.
6. **Логи** — journald/syslog/auditd.
7. **Диск** — образ уже на копии.

Почему именно так: сеть и процессы исчезают при перезагрузке; логи и диск переживут её. Если начать с диска, память потеряется навсегда.

```bash
# 1. Память
$ sudo avml /evidence/mem.lime
# 2. Сеть
$ ss -tunap > /evidence/net.txt ; ip neigh > /evidence/arp.txt
# 3. Процессы
$ ps auxwwf > /evidence/ps.txt ; ls -l /proc/*/exe 2>/dev/null > /evidence/exe.txt
# 4. Автозапуск
$ crontab -l > /evidence/cron.txt ; systemctl list-units --type=service > /evidence/svc.txt
# 5. Логи
$ journalctl --since "-2d" > /evidence/journal.txt
```

Каждый файл — с хешем в манифест, чтобы позже доказать неизменность.

## Частые вопросы

**Почему нельзя просто выключить машину?** Выключение стирает RAM и активные соединения — именно то, что нужно атакующему, чтобы замести следы. Живой сбор сохраняет это.

**Чем живой сбор отличается от «мёртвого»?** Мёртвый (по образу диска) даёт устойчивые артефакты, но не память и не сеть. Живой дополняет его, но слегка меняет систему — потому его и делают в порядке волатильности.

**Насколько «меняет» система при сборе?** Каждая команда создаёт процессы и трогает ФС. Минимизируйте: используйте read-only-инструменты, пишите вывод на внешний носитель, не запускайте ничего лишнего.

**Что если атакующий активен прямо сейчас?** Сначала сохраните волатильные данные (память, сеть), затем изолируйте; не выключайте питание до сбора.

## Что мы теперь знаем

- **Порядок волатильности** — закон live-forensics: память первой, диск последним.
- Память снимают `avml`/LiME (Linux) или `winpmem`/`DumpIt` (Windows), на внешний носитель, с хешем.
- Сеть (`ss`, ARP, DNS-кэш) меняется за секунды — фиксируют сразу.
- Процессы собирают с полными командными строками и окружением; аномальные пути (`/tmp`, `AppData`) — сигнал.
- Сами инструменты оставляют следы — документируйте свои действия.
- Live-сбор — вход для анализа (Volatility, plaso, таймлайн), а не самоцель.

## Если не сработало: подводные камни живого сбора

Живой сбор опасен тем, что вы вмешиваетесь в систему. Частые грабли:

- **Вы меняете систему.** Запуск инструментов создаёт файлы, процессы, записи в реестре. Документируйте, что и когда запускали, — иначе спутаете со следами атакующего.
- **Дамп неполон.** Часть страниц могла быть вытеснена в swap до сбора.
- **Антифорензика.** Малварь может детектировать коллектор и самоуничтожиться; иногда безопаснее сначала изолировать сеть.
- **Привилегии.** Многие команды требуют root/Administrator — без них сбор неполон.
- **Сетевой сбор.** Соединения меняются за секунды — фиксируйте время; ARP-таблица и DNS-кэш исчезают первыми.

Для масштабного инцидента ручной сбор невозможен — используют агенты (`Velociraptor`, `Wazuh`, `UAC`) и центральное хранилище, а также out-of-band канал, не зависящий от скомпрометированной сети.

## Куда дальше

Мы научились собирать данные с живой системы в правильном порядке. В следующем уроке (`forensics-ir-nist`) разберём сам процесс реагирования на инциденты по NIST SP 800-61 — где live-сбор занимает своё место. ## Где пригодится

- **CTF:** задачи с живыми системами и дампами памяти.
- **IR:** сбор данных с работающих серверов и рабочих станций.
- **Threat Hunting:** live-hunting через Velociraptor/KAPE.
- **Судебная экспертиза:** обоснованный порядок сбора.
