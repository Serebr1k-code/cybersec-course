## Вопрос, с которого всё начинается

Представь: на сервер пришёл шифровальщик и зашифровал документы. Система ещё жива, но файлы в привычном виде недоступны. Есть ли способ увидеть их **до** шифрования? В Windows — да: операционная система регулярно делает снимки тома целиком, и в них сохраняются старые версии файлов. Эти снимки называют **теневыми копиями** (Volume Shadow Copies, VSS). Разберёмся, что это, где живёт и как из них достать данные.

## Наш пример: образ с теневой копией

У нас есть вывод `vssadmin list shadows` в файле `shadows.txt` и фрагмент **дифф-области** (diff area) теневых копий — `diffarea.dat`. Дифф-область — это область на томе, куда VSS складывает блоки, изменившиеся после создания снимка. Сначала посмотрим список снимков:

```bash
$ cat shadows.txt
vssadmin 1.1 - Volume Shadow Copy Service administrative command-line tool
Contents of shadow copy set ID: {4f7c1e2a-9b3d-4a11-8e77-2b6a0c1d9e01}
   Contained 1 shadow copies at creation time: 12.03.2024 03:14:07
   Shadow Copy ID: {a1b2c3d4-1111-2222-3333-444455556666}
      Original Volume: (C:)\\?\Volume{9f8e7d6c-0000-0000-0000-000000000000}\
      Shadow Copy Volume: \\?\GLOBALROOT\Device\HarddiskVolumeShadowCopy1
      Originating Machine: WIN-SRV01
      Service Machine: WIN-SRV01
      Provider: 'Microsoft Software Shadow Copy provider 1.0'
      Type: ClientAccessible
      Attributes: Persistent, No auto release, No differ
```

Что мы узнали:

- Снимок создан **12.03.2024 03:14:07** — это «точка во времени», на которую мы можем откатиться.
- Том `C:` имеет путь `\\?\GLOBALROOT\Device\HarddiskVolumeShadowCopy1` — это и есть «точка монтирования» снимка.
- Атрибут `ClientAccessible` означает, что копию можно открыть обычным способом (например, «Предыдущие версии» в проводнике).

## Шаг 1: как читать снимок

Смонтировать снимок можно двумя путями. Первый — через саму Windows (если система жива): в проводнике «Свойства → Предыдущие версии». Второй — офлайн, на образе диска, инструментом **libvshadow**:

```bash
$ vshadowinfo -o disk.raw
VShadow ver 20231014
Volume: 1
  Volume size: 50000000000
  Number of stores: 2
  Store: 0
    Shadow copy ID: {a1b2c3d4-...}
    Creation time: Mar 12, 2024 03:14:07
```

`vshadowmount` превращает снимок в обычный файл-устройство, который затем можно прочитать sleuthkit-ом (`fls`, `icat`) так же, как любой образ.

## Шаг 2: почему в снимке остаётся «старое»

Механизм **copy-on-write**: когда файл впервые меняется после создания снимка, его старые блоки копируются в дифф-область, и только потом на их место пишется новое содержимое. Поэтому снимок всегда «помнит» версию на момент создания. Удалённый файл тоже остаётся: удаление меняет только метаданные, а блоки ещё не перезаписаны.

Посмотрим, что лежит в нашей дифф-области. Это бинарник, и в нём смешаны блоки разных файлов:

```bash
$ xxd -l 64 diffarea.dat
00000000: 5668 7364 0001 0000 1203 2024 03 14 07  Vhsd......  ..
```

Строки в начале блока — это остатки старого файла. Наш учебный парсер `vssparse.py` проходит дифф-область, находит текстовые блоки и показывает восстановленный файл:

```bash
$ python3 vssparse.py
[VSS] diff area: diffarea.dat
[VSS] found file block at 0x00001000 (orig C:\\Users\\admin\\secret.txt)
recovered: key=nto{vss_sh4d0w_c0py_r3c0v3r}
```

Мы восстановили файл, которого в «живой» системе уже нет — он был удалён (или перезаписан) после создания снимка. Достаточно перенаправить вывод в файл, чтобы забрать результат:

```bash
$ python3 vssparse.py | grep nto > found.txt
```

## Шаг 3: теневые копии против шифровальщика

Современные шифровальщики первым делом удаляют теневые копии (`vssadmin delete shadows /all /quiet`), чтобы жертва не могла откатиться. Поэтому **наличие** снимков — важный факт:

```bash
$ vssadmin list shadows
No items found that satisfy the query.
```

Пустой список на машине, где снимки обычно есть, — тревожный признак. А в журналах видно саму команду удаления:

```
EventID 4688: Process Creation
  New Process Name: C:\Windows\System32\vssadmin.exe
  Process Command Line: vssadmin delete shadows /all /quiet
```

Это уже прямая улика: зафиксировано, кто и когда уничтожил копии.

## Шаг 4: что искать в снимках

| Что ищем | Зачем |
|----------|-------|
| Удалённые малварь/скрипты | восстановить payload для анализа |
| Конфиги и БД «до атаки» | понять изменения |
| Документы до шифрования | вернуть данные (и CTF-флаги) |
| Предыдущие версии реестра | увидеть, что правил атакующий |

Важно: снимки могут содержать **несколько** поколений одного файла. Сравнивая версии (например, хешами), вы строите хронологию изменений.

## Шаг 5: таймстемпы и идентификация

Каждый снимок — отдельная «вселенная» метаданных со своими временами. Сопоставляя время создания снимка с временами файлов внутри, вы понимаете, что менялось до, а что после:

```bash
$ fls -o <offset> -r shadow.raw | grep secret.txt
r/r 128-128-1: secret.txt
```

Если файл присутствует в снимке, но отсутствует в текущем томе — он был удалён между снимком и «сейчас». Это и есть таймлайн-зацепка.

## Если не сработало

- **`vssadmin` не видит копий** → копии могли удалить; проверяйте Event ID 4688 и журнал `Microsoft-Windows-VSS`/`System`.
- **Снимок не монтируется** → для образов используйте `vshadowmount`, а не Windows-проводник; проверьте, что образ не сжат.
- **Дифф-область «пустая»** → возможно, снимок типа `No differ` (полная копия) или данные в другом store; смотрите все store в `vshadowinfo`.
- **Восстановленный файл битый** → блоки в дифф-области могут быть фрагментированы; собирайте по метаданным файла, а не «подряд».

## На что смотреть защитнику

- Мониторинг запуска `vssadmin delete shadows`, `wmic shadowcopy delete`, `wbadmin delete` — классический шаг перед шифрованием.
- Отдельный, защищённый от изменений бэкап-контур: копии, которые атакующий не может удалить с той же машины.
- Централизованный сбор VSS-событий (создание/удаление снимков) в SIEM.

## Что мы теперь знаем

- **Теневая копия** — снимок тома на момент времени; хранит старые версии файлов по механизму copy-on-write.
- Список копий даёт `vssadmin list shadows`; на образе работают `vshadowinfo`/`vshadowmount`.
- В **дифф-области** остаются блоки изменённых и удалённых файлов.
- Удаление копий (`vssadmin delete shadows`) — характерный шаг шифровальщика; факт удаления виден в Event ID 4688.
- Снимки — источник данных «до атаки» и хронологии изменений.

## Куда дальше

Мы научились доставать «прошлое» с тома. В следующем уроке (`forensics-hibernation`) разберём другой системный файл — `hiberfil.sys`: там лежит целый снимок оперативной памяти, оставшийся на диске. А пока главное запомни: **теневая копия — это снимок тома, и в нём живут удалённые файлы**.

## Где пригодится

- **CTF:** флаг в удалённом файле, который остался в теневой копии образа.
- **IR:** восстановление удалённых улик и проверка факта уничтожения копий.
- **Ransomware-разбор:** поиск версий файлов до шифрования.
- **Судебная экспертиза:** доказательство «что было» на конкретный момент времени.
