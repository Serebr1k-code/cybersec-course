## Вопрос, с которого всё начинается

Сработала тревога: в Kubernetes-кластере кто-то читал секреты и запускал необычные поды. К моменту, когда дежурный подключился, «подозрительный» под уже удалён. Вопрос: как восстановить, что делал атакующий, если контейнеры **эфемерны** — их удалили, и файловой системы как будто не было?

Контейнеры и правда исчезают быстро. Но Kubernetes оставляет логи: что запрашивали у API-сервера, какие объекты создавали, с каких адресов. Это ядро расследования. Разберём один инцидент по его audit-логу.

## Наш пример: `audit.log` API-сервера

**API-сервер** (`kube-apiserver`) — центральный компонент Kubernetes: через него проходит **каждое** действие в кластере. Если включён аудит, он пишет каждое действие в **audit-лог** — построчный JSON. Вот одна запись:

```bash
$ head -1 audit.log | jq .
{
  "kind": "Event",
  "stage": "ResponseComplete",
  "verb": "list",
  "requestURI": "/api/v1/namespaces/default/secrets",
  "user": { "username": "system:serviceaccount:default:compromised" },
  "sourceIPs": ["10.1.2.3"],
  "responseStatus": { "code": 200 }
}
```

Разбираем поля, вводя термины. `verb` — тип действия (`list`, `get`, `create`, `delete`). `requestURI` — что именно запрошено: здесь список **секретов** (`secrets`) — объектов, в которых хранят пароли, токены и ключи. `user.username` — кто действовал; `system:serviceaccount:...` означает **service account** — учётную запись, от имени которой работает под (не человек). `sourceIPs` — откуда пришёл запрос. `responseStatus.code = 200` — запрос **успешен**.

## Шаг 1: находим подозрительного пользователя

В логе тысячи записей. Фильтруем по интересному пользователю — `jq` умеет выбирать JSON-объекты по условию:

```bash
$ jq -c 'select(.user.username | test("compromised"))' audit.log | wc -l
142
$ jq -r 'select(.user.username | test("compromised")) | "\(.verb) \(.requestURI)"' audit.log | sort | uniq -c | sort -rn | head
  31 create /api/v1/namespaces/default/pods
  18 list   /api/v1/namespaces/default/secrets
  12 create /api/v1/namespaces/default/pods/.../exec
```

Картина проясняется: сервисная учётная запись `compromised` массово читала секреты, создавала поды и делала `exec` (запуск команд внутри пода). Для нормального приложения это аномалия.

## Шаг 2: восстанавливаем цепочку атаки

Отсортировав события по времени, видим последовательность — типичный путь эскалации:

1. **`list secrets`** — украдены секреты (часто внутри облачные ключи и токены БД).
2. **`create pods`** — запущен новый под, вероятно привилегированный.
3. **`create pods/exec`** — внутрь пода выполнен вход для команд.
4. **`create clusterrolebinding`** — себе выданы права администратора кластера.

Последнее — самое опасное. **RBAC** (Role-Based Access Control) — система прав в Kubernetes; `ClusterRoleBinding` привязывает роль ко пользователю на весь кластер. Создание такой привязки себе — прямая эскалация до полных прав:

```bash
$ jq -c 'select(.objectRef.resource | test("clusterrolebinding"))' audit.log
{"verb":"create","user":{"username":"system:serviceaccount:default:compromised"},
 "objectRef":{"resource":"clusterrolebinding","name":"pwn"}}
```

Так по логу восстанавливается вся цепочка: от чтения секретов до закрепления.

## Шаг 3: снимаем снимок контейнера

Если под ещё жив, его файловую систему нужно сохранить **до** удаления. Контейнер работает на **overlayfs** — слоёной файловой системе: нижние слои (`lowerdir`) — это базовый образ, а верхний (`upperdir`) содержит все изменения рантайма. Именно в `upperdir` окажутся файлы, созданные атакующим.

Снимок можно сделать через Docker:

```bash
$ docker export <container_id> > container_fs.tar
```

`docker export` отдаёт файловую систему контейнера одним архивом. А можно скопировать сам верхний слой:

```bash
$ mount | grep overlay
$ cp -a /var/lib/docker/overlay2/<id>/diff /evidence/
```

В кластерах на containerd/CRI-O те же действия делают через `ctr` или `crictl`.

## Шаг 4: снимаем снапшот etcd

**etcd** — key-value хранилище, где Kubernetes держит **всё состояние** кластера: поды, секреты, RBAC, конфигурации. Снапшот etcd — это «золотая жила»: в нём история всех объектов. Атакующий с доступом к etcd (порт 2379) получает вообще всё.

```bash
$ ETCDCTL_API=3 etcdctl snapshot save /evidence/etcd.db
$ auger dump --etcd /evidence/etcd.db --output /evidence/objects/
```

Инструмент `auger` разбирает снапшот на отдельные объекты — секреты, роли, поды — которые можно читать по одному.

## Шаг 5: изолируем, не разрушая

Правильный порядок действий — **не удалять** поды и узлы. Чтобы остановить распространение, узел помечают `cordon` — это запрещает планировать на него новые поды, но **не трогает уже запущенные**:

```bash
$ kubectl cordon <node>
$ kubectl get pods -A -o wide
$ kubectl logs <pod> --previous
```

Ключевой момент: команда `drain` (которую иногда тянет выполнить) **удалит** поды с узла — и вместе с ними улики. Для форензики используют именно `cordon`. `--previous` в `kubectl logs` показывает логи контейнера **до** перезапуска — там часто и лежит полезное.

## Полный разбор: от audit-лога к контейнеру

Соберём расследование Kubernetes в один сценарий.

1. **Смотрим audit-лог API-сервера.** Ищем аномального пользователя/SA:
   ```bash
   $ jq 'select(.user.username|test("system:serviceaccount"))' audit.log | head
   ```
2. **Восстанавливаем цепочку.** `create pods` → `exec` в под → `get secrets` — типичная эскалация.
3. **Снимаем контейнер.** `crictl inspect <id>` / `docker export` — сохраняем ФС для анализа.
4. **Снапшот etcd.** Вся конфигурация кластера; снимок = «диск» для control plane.
5. **Изолируем, не разрушая.** `kubectl cordon` (не трогать узел), затем разбор на копии.

Ключ: в K8s нет «диска узла» — доказательства живут в audit-логах, etcd и слоях контейнеров.

## Шпаргалка артефактов K8s

| Источник | Что даёт |
|----------|----------|
| audit.log API-сервера | кто что делал (`verb`, `resource`, `user`) |
| etcd snapshot | вся конфигурация, секреты |
| `crictl`/`docker` | слои и состояние контейнера |
| runtime-логи (containerd) | запуск, монтирования |
| node logs (kubelet) | действия на узле |

## Частые вопросы

**Где audit-логи?** На control plane, если включён `--audit-policy-file`; по умолчанию их может не быть — это важная оговорка.

**Как понять, что под скомпрометирован?** Аномальный образ, привилегированный контейнер, смонтированный `docker.sock`/hostPath.

**Секреты доступны в etcd?** Да, но часто в base64 (не шифрование) — проверяйте `EncryptionConfiguration`.

**Как изолировать, не убив улики?** `cordon`/`drain` с сохранением подов, снимок до удаления; не делайте `delete pod` первым.

## Что мы теперь знаем

- API-сервер пишет **audit-лог** — построчный JSON с полями `verb`, `user`, `requestURI`, `sourceIPs`.
- `system:serviceaccount:...` — учётная запись пода; аномалии по ней видны сразу.
- Цепочка эскалации: `list secrets` → `create pods` → `exec` → `create clusterrolebinding`.
- Файловая система контейнера — overlayfs; изменения атакующего в `upperdir`, снимок — `docker export`.
- Снапшот **etcd** хранит всё состояние кластера, включая секреты и RBAC.
- Изоляция — `cordon`, а не `drain` (drain удалит поды вместе с уликами).
