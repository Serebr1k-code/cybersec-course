## Зачем отдельная форензика контейнеров

Контейнеры эфемерны: под удалили — и следы исчезли. Однако остаются **слои образов** (overlayfs), **логи** (API-сервер, kubelet, runtime), **audit-логи**, **метаданные etcd**, **артефакты узла**. Задача форензики Kubernetes — восстановить, что делал атакующий: как попал, что запускал, какие секреты украл, куда двигался. Ключевое отличие от классического DFIR: артефакты распределены между узлами, control-plane и внешними системами (облачные логи).

## Что происходит при компрометации

Типичная цепочка: уязвимое приложение → RCE в поде → доступ к service account token → обращение к API-серверу → эскалация (создание привилегированного пода, чтение секретов, доступ к узлу через hostPath/privileged) → закрепление. Каждый шаг оставляет артефакты.

## Audit-логи API-сервера

Главный источник. `kube-apiserver` пишет audit-логи (если включён `--audit-policy-file`). Формат — JSON-строки с полями: `user`, `verb`, `resource`, `namespace`, `requestURI`, `responseStatus`, `sourceIPs`.

```bash
# Пример записи
{"kind":"Event","apiVersion":"audit.k8s.io/v1","level":"RequestResponse",
 "auditID":"...","stage":"ResponseComplete","requestURI":"/api/v1/namespaces/default/secrets",
 "verb":"list","user":{"username":"system:serviceaccount:default:compromised"},
 "sourceIPs":["10.1.2.3"],"responseStatus":{"code":200}}
```

Что искать:

- **Создание привилегированных подов** (`create pods` с `securityContext.privileged`).
- **Чтение секретов** (`get/list secrets`).
- **Создание ClusterRoleBinding** (эскалация прав).
- **`exec` в поды** (`create pods/exec`).
- **Доступ к `nodes/proxy`** (kubelet API).
- **Анонимные/подозрительные SA** (`system:serviceaccount:*`).

```bash
# Фильтр по verb и resource
jq -c 'select(.verb=="create" and .objectRef.resource=="pods")' audit.log
jq -c 'select(.requestURI|test("secrets"))' audit.log
```

## Runtime-артефакты и снимок контейнера

Контейнер нельзя «останавливать и снимать образ» без потери состояния — поэтому делают **снимок**: `docker commit`, `docker export`, копирование overlayfs-слоёв.

```bash
# Docker: сохранить файловую систему контейнера
docker export <container_id> > container_fs.tar
# или коммит в образ
docker commit <container_id> forensic_snapshot:latest
docker save forensic_snapshot:latest -o snapshot.tar

# containerd/CRI-O
ctr -n k8s.io containers list
ctr -n k8s.io snapshots ls
```

Слои overlayfs: `lowerdir` (базовый образ), `upperdir` (изменения рантайма). Изменения атакующего — в `upperdir`.

```bash
# Найти overlay-монтирование
mount | grep overlay
# Скопировать upperdir
cp -a /var/lib/docker/overlay2/<id>/diff /evidence/
```

## Логи и метаданные

- **kubelet:** `/var/log/pods/<ns>_<pod>_<uid>/<container>/*.log`.
- **container runtime:** journald (`journalctl -u containerd`), `/var/log/containers`.
- **etcd:** снапшот базы (`etcdctl snapshot save`) — содержит все объекты (секреты, RBAC, поды).
- **events:** `kubectl get events --all-namespaces`.
- **admission controllers:** логи о отклонённых/принятых объектах.

```bash
etcdctl snapshot save /evidence/etcd.db
# анализ через etcd-dump или k8s-forensics
kubectl get pods --all-namespaces -o yaml > pods.yaml
kubectl get secrets --all-namespaces -o yaml > secrets.yaml
```

## Секреты и доступ к узлу

- **Secrets** в etcd (base64, не шифрованы по умолчанию — включайте encryption at rest).
- **ServiceAccount tokens** монтируются в поды (`/var/run/secrets/kubernetes.io/serviceaccount/token`).
- **hostPath** и **privileged** дают доступ к узлу.
- **kubelet API (10250)** — `exec`/`logs` без аутентификации (если `--anonymous-auth`).

```bash
# Проверить, был ли под привилегированным
kubectl get pod <pod> -o jsonpath='{.spec.containers[*].securityContext}'
# Проверить hostPath
kubectl get pod <pod> -o jsonpath='{.spec.volumes}'
```

## Практический пример: расследование

1. **Соберите audit-лог** за окно инцидента.
2. **Найдите подозрительного пользователя** (SA, `sourceIPs`).
3. **Восстановите цепочку** verb/resource (list secrets → create pod → exec).
4. **Снимите образ пода** (`docker export`) до удаления.
5. **Извлеките секреты**, к которым был доступ.
6. **Проверьте узел** на persistence (cron, systemd, новый образ).
7. **Оформите таймлайн.**

## etcd и RBAC: глубинный анализ

**etcd** — key-value хранилище всего состояния кластера. Снапшот etcd — «золотая жила»: в нём объекты всех типов (Pods, Secrets, RBAC, ConfigMaps, ServiceAccounts). Атакующий с доступом к etcd (2379/2380) получает **всё**.

```bash
# Снапшот (нужен доступ к control-plane)
ETCDCTL_API=3 etcdctl --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key \
  snapshot save /evidence/etcd.db
# Анализ: etcd-dump / auger / k8s-forensics
auger dump --etcd /evidence/etcd.db --output /evidence/objects/
```

**RBAC** (Role/ClusterRole + Binding) определяет права. Форензика RBAC: ищите **созданные** атакующим привязки, дающие `*`/`cluster-admin`, и `serviceaccounts` с чрезмерными правами.

```bash
# Кто имеет cluster-admin
kubectl get clusterrolebindings -o json | \
  jq '.items[] | select(.roleRef.name=="cluster-admin") | .subjects'
# Аудит-события создания RBAC
jq -c 'select(.objectRef.resource|test("rolebinding|clusterrolebinding"))' audit.log
```

## Изоляция и сбор улик

Правильный порядок: **не удалять** поды/узлы, снять снимки, зафиксировать audit-логи, взять снапшот etcd, пометить узел `cordon` (не drain — drain удалит поды!).

```bash
kubectl cordon <node>              # запретить новое планирование, НЕ удалять поды
kubectl get pods -A -o wide        # зафиксировать состояние
kubectl describe pod <pod>         # события
kubectl logs <pod> --previous      # логи прошлого контейнера
```

Для пода: `kubectl exec` для сбора (осторожно — меняет состояние), `kubectl cp` файлов, `docker export`/`ctr` для ФС.

## Цепочки атак в Kubernetes

Типичные пути эскалации:

1. **RCE в поде → service account token → API.**
2. **Token с правами → создание privileged-пода → mount hostPath `/` → доступ к узлу.**
3. **Доступ к `nodes/proxy`/kubelet 10250 → exec в любой под.**
4. **Чтение секретов** (часто содержат облачные ключи, токены, пароли БД).
5. **Cloud metadata (169.254.169.254)** из пода → IAM-креды облака.
6. **DaemonSet/Static Pod** — закрепление на узле.
7. **Mutating Webhook** — перехват/модификация.

Каждый шаг виден в audit-логе как verb/resource — восстановите цепочку.

## Инструменты и команды

```bash
# Сбор состояния кластера
kubectl get all --all-namespaces -o yaml > cluster_state.yaml
kubectl get events --all-namespaces --sort-by=.lastTimestamp
kubectl get pods -A -o custom-columns=NS:.metadata.namespace,POD:.metadata.name,NODE:.spec.nodeName

# Логи
kubectl logs <pod> -n <ns> --since=24h
journalctl -u kubelet --since "2024-01-01"
cat /var/log/pods/<ns>_<pod>_<uid>/*/*.log

# Runtime
docker ps -a; docker inspect <id>
crictl ps -a; crictl inspect <id>
ctr -n k8s.io containers list

# Audit
cat /var/log/kubernetes/audit/audit.log | jq -c 'select(.verb!="get")'

# Специализированные инструменты
# k8s-forensics, KubeForensics, Peirates (для пентеста), kube-hunter
```

**Peirates** и **kube-hunter** — для оценки поверхности атаки (что мог использовать злоумышленник). **Sysdig Falco** — runtime-детекты.

## Резюме: план расследования

1. **Изолировать** (cordon, не drain) и **сохранить** состояние.
2. **Audit-логи** — восстановить действия (кто, что, откуда).
3. **Снимок подов** — файловая система.
4. **etcd-снапшот** — полная история объектов.
5. **Секреты** — что украдено.
6. **Узлы** — persistence.
7. **Таймлайн** и **отчёт**.

## Сетевая политика и сегментация

**NetworkPolicy** ограничивает трафик между подами. Отсутствие политик = «flat network»: скомпрометированный под видит всё. Для форензики важно проверить, были ли политики и обходил ли их атакующий.

```bash
kubectl get networkpolicies -A
kubectl get pods -A -o wide    # какие поды на каких узлах
# DNS-политики, egress-политики
kubectl get networkpolicy -A -o yaml
```

**Service mesh** (Istio/Linkerd) добавляет свои логи (mTLS, трафик) — дополнительный источник.

## Частые ошибки

- **Удалить под до снимка.** Потеря улик.
- **Игнорировать audit-логи** (часто не включены — тогда kubelet/runtime логи).
- **Забыть про etcd-снапшот** (там вся история объектов).
- **Не проверить `hostPath`/`privileged`.** Это путь к узлу.
- **Смотреть только один узел.** Инцидент распределён.
- **Забыть про облачные audit-логи** (EKS/AKS/GKE).

## Как не застрять

- **Audit-логи — первым делом.**
- **Снимок контейнера** до удаления.
- **etcd-снапшот** для полной картины.
- **Ищите привилегированные поды и чтение секретов.**
- **Проверьте узлы** на persistence.
- **Соберите единый таймлайн.**
