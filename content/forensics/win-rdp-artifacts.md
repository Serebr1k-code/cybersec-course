## Вопрос, с которого всё начинается

Злоумышленник зашёл на хост **по RDP** и что-то делал на экране. Ты видишь только файлы.
Можно ли узнать, **что именно он видел** и **откуда подключался**? Оказывается, Windows
оставляет для этого целый набор следов — от журналов до **картинок экрана в кэше**.

Разберём сквозной пример: по копии профиля восстановим, кто подключался и что было на
экране.

## Как RDP оставляет следы

**RDP (Remote Desktop Protocol)** — протокол удалённого рабочего стола. Чтобы картинка
передавалась быстрее, клиент и сервер кэшируют **фрагменты изображения** (битмапы). Эти
фрагменты сохраняются на диск, и по ним можно **частично восстановить экран**. Плюс
служба RDP ведёт **журналы сессий** и пишет следы в реестр.

Ключевые артефакты:

- `%LOCALAPPDATA%\Microsoft\Terminal Server Client\Cache\` — кэш клиента (файлы `bcache*`,
  `Cache0000.bin`).
- `C:\Users\<user>\AppData\Local\Microsoft\Terminal Server Client\Default\` — история
  подключений (`MRU` — список последних адресов).
- Журналы `Microsoft-Windows-TerminalServices-*` (канал Operational).
- Ветви реестра с настройками и последними адресами.

## Наш пример: кэш битмапов

На клиентской машине найдём каталог кэша:

```
$ ls -la Cache/
-rw-r--r--  Cache0000.bin   1032192
-rw-r--r--  Cache0001.bin    524288
```

Файлы `Cache*.bin` — это **кэш битмапов** (формат `bcache2`). Внутри — сжатые плитки
изображения, которые сервер отправлял клиенту. Смотрим заголовок:

```
$ xxd -l 16 Cache0000.bin
00000000: 6263 6163 6832 0000 0000 0000 0000  bcache2........
```

Магия `bcache2` подтверждает формат. Дальше файл надо разобрать на отдельные плитки. Это
делает утилита **bmc-tools** (Python):

```
$ python3 bmc-tools.py -s Cache/ -d out/
[i] Found 2 cache files
[+] 37 tiles extracted -> out/
```

Из кэша извлекаются отдельные **плитки** — кусочки экрана. Их собирают мозаикой, и иногда
удаётся прочитать текст, который был на экране злоумышленника (открытый документ,
терминал, браузер).

### Что искать в плитках

- Фрагменты **командной строки** и вывода инструментов.
- Открытые **документы** и **окна браузера**.
- Логотипы/интерфейсы инструментов атакующего (Cobalt Strike, Rubeus и т.п.).

## Журналы сессий

Параллельно смотрим журналы. В канале
`Microsoft-Windows-TerminalServices-LocalSessionManager/Operational` фиксируются
подключения и отключения:

```
$ evtx_dump.py LocalSessionManager.evtx | grep -E "EventID|Address|User"
<EventID>21</EventID>  Session logon succeeded
<Address>10.10.20.55</Address>
<User>CORP\jdoe</User>
<EventID>24</EventID>  Session disconnected
<EventID>25</EventID>  Session reconnection succeeded
```

Event ID **21** — успешный вход в сессию, **24/25** — отключение и повторное
подключение. Поле `Address` — адрес клиента, `User` — учётка. Так восстанавливается
**список сессий с адресами**.

### Следы в реестре

- `HKCU\Software\Microsoft\Terminal Server Client\Default` — история `MRU0..MRU9`
  с адресами, к которым подключались **с этой машины**.
- `HKCU\...\Terminal Server Client\Servers\<addr>` — параметры для конкретного сервера.
- `HKLM\SYSTEM\...\Terminal Services` — настройки сервера RDP.

## Что ещё: время и способ входа

Event ID **4624** (в Security) с `Logon Type = 10` означает вход **по RDP**
(интерактивно по сети). А `Logon Type = 3` — сетевой вход. Комбинация 4624 (type 10) +
журнал TerminalServices + кэш битмапов даёт полную картину: **кто, откуда, когда и что
видел**.

## Если битмапы не собираются

Иногда плитки повреждены или кэш очищен. Тогда опираемся на журналы (адреса и времена) и
на **MRU** в реестре. Если и журналы подчищены — ищем косвенные следы: файлы, созданные в
период сессии, `USN`-записи, историю браузера на сервере.

## Формат bcache2 подробнее

Кэш битмапов — это файл с заголовком и последовательностью блоков. Понимание формата
помогает, когда стандартный инструмент не справляется.

- **Заголовок.** Первые байты — магия `bcache2`, затем поля с размером кэша и числом
  плиток.
- **Плитки (tiles).** Каждая плитка — прямоугольный фрагмент 64×64 пикселя, сжатый
  алгоритмом RLE (в новых версиях — более сложное сжатие). Плитки складываются в мозаику
  по индексам.
- **Ключевой индекс (key).** Первая плитка часто содержит «ключ» — уменьшённую карту
  экрана, по которой видно, где какая плитка стояла. Без ключа собрать картинку сложно.

Инструмент **bmc-tools** (`-s` источник, `-d` назначение) разбирает файл на отдельные
`.bmp`-плитки. Их затем собирают вручную или скриптом. Для CTF важнее то, что в плитках
встречается **читаемый текст**: строки терминала, заголовки окон, пути файлов.

## Следы RDP в реестре и файловой системе

Кроме кэша и журналов, есть «тихие» артефакты:

| Артефакт | Путь | Что даёт |
|----------|------|----------|
| MRU подключений | `HKCU\...\Terminal Server Client\Default` | адреса последних серверов |
| Настройки сервера | `HKCU\...\Terminal Server Client\Servers\<addr>` | имя пользователя, порт |
| Журнал сессий | `...\TerminalServices-LocalSessionManager\Operational` | Event 21/24/25 |
| Журнал подключений | `...\TerminalServices-RemoteConnectionManager\Operational` | Event 1149 |
| Кэш клиента | `%LOCALAPPDATA%\Microsoft\Terminal Server Client\Cache` | плитки экрана |
| Файл `Default.rdp` | профиль пользователя | параметры последнего подключения |

Event **1149** (RemoteConnectionManager) фиксирует **попытку** аутентификации по RDP —
полезно, чтобы увидеть неудачные подключения (брутфорс). Event **21** — уже успешный
вход.

## Как отличить атакующего от администратора

Само по себе RDP-подключение — норма. Признаки аномалии:

- **Адрес клиента** — внешний IP или необычная подсеть.
- **Время** — подключения в 3 часа ночи вне окна работ.
- **Учётка** — сервисная, которую люди обычно не используют интерактивно.
- **Совпадение с другими событиями** — создание файла, установка службы сразу после входа.
- **Много неудачных 1149** перед успешным 21 — признак перебора пароля.

Складывая эти признаки, аналитик отличает штатный доступ администратора от
злоумышленника.

## Частые ошибки

- **Путать type 10 и type 3.** RDP — это type 10; сетевой доступ — type 3. Если смотреть
  только 4624, легко принять сетевой вход за RDP.
- **Искать кэш не в том профиле.** Кэш лежит в профиле **пользователя**, который
  подключался, а не того, к кому подключались.
- **Считать плитки «мусором».** Даже частично восстановленные плитки часто содержат
  читаемый текст — их стоит просматривать.
- **Забыть про `Default.rdp`.** В этом файле остаются настройки последнего подключения,
  включая имя пользователя.

## Шпаргалка команд

```
# Разбор кэша битмапов
python3 bmc-tools.py -s Cache/ -d tiles/
# Дамп журнала сессий
evtx_dump.py LocalSessionManager.evtx | grep -E 'EventID|Address|User'
# MRU в реестре (через regripper)
rip.pl -r NTUSER.DAT -p rdpmp
# Файл последнего подключения
cat Default.rdp | grep -iE 'full address|username'
```

## Что это даёт в отчёте

В отчёте по RDP фиксируют: перечень сессий (адрес, учётка, время входа/выхода), способ
доступа (Logon Type 10), восстановленные фрагменты экрана и связь сессий с другими
событиями (создание файлов, запуск служб). Это восстанавливает «историю атаки» на хосте.

## Мини-практика: собираем мозаику экрана

Закрепим работу с кэшем битмапов на сквозном примере. У нас есть каталог `Cache/` с
двумя файлами и цель — понять, что делал злоумышленник на экране.

Сначала разберём кэш на плитки:

```
$ python3 bmc-tools.py -s Cache/ -d tiles/
[i] Found 2 cache files
[+] 37 tiles extracted -> tiles/
$ ls tiles/ | head
tile_0000.bmp  tile_0001.bmp  ...
```

Каждая плитка — отдельный BMP 64×64. Смотрим их по одной. В CTF флаг часто вшит прямо в
одну из плиток как текст:

```
$ for f in tiles/*.bmp; do strings "$f" | grep -q nto && echo "FLAG in $f"; done
FLAG in tiles/tile_0021.bmp
$ strings tiles/tile_0021.bmp
nto{rdp_b1tm4p_c4ch3_r3c0v3ry}
```

Плитка `tile_0021.bmp` содержит флаг. В реальном расследовании по плиткам собирают
**мозаику** — так восстанавливается картинка экрана. Если плитки пронумерованы по
позиции, их можно склеить скриптом; иначе ориентируются по «ключевой» плитке с
уменьшённой картой.

Параллельно смотрим журнал сессий, чтобы привязать картинку ко времени и адресу:

```
$ evtx_dump.py LocalSessionManager.evtx | grep -E 'EventID|Address|User'
<EventID>21</EventID>
<Address>10.10.20.55</Address>
<User>CORP\\jdoe</User>
```

Теперь картина складывается: **пользователь `CORP\jdoe` вошёл по RDP с `10.10.20.55`,
и в кэше битмапов сохранился фрагмент экрана с флагом**. Это и есть типичный сценарий
форензик-задачи по RDP.

Отдельно проверяем MRU в реестре — чтобы увидеть **все** адреса, к которым подключались
с этой машины:

```
$ rip.pl -r NTUSER.DAT -p rdpmp
rdpmp v.20200525
MRU0  tsclient.corp.local
MRU1  10.10.20.55
```

Итог: кэш битмапов даёт «что видел», журнал — «кто и откуда», реестр — «куда ещё
подключались». Три источника вместе восстанавливают полную историю удалённого доступа,
и ни один из них в одиночку её не даёт.

## Что мы теперь знаем

- RDP оставляет **кэш битмапов** (`bcache2`) — из него извлекаются плитки экрана.
- `bmc-tools.py` разбирает кэш на плитки; из них иногда читается содержимое экрана.
- Журналы `TerminalServices-*` дают **адрес клиента, учётку и время** сессий (Event 21/24/25).
- В реестре (`Terminal Server Client\Default`) — список адресов последних подключений.
- Вход по RDP в Security — это Event **4624** с `Logon Type 10`.

## Куда дальше

Мы восстановили картину удалённого доступа. Дальше разберём **LSA-секреты**: какие
пароли сервисных учёток и кэш доменных логинов хранит операционная система. А пока
главное запомни: **кэш битмапов + журналы TerminalServices = «что видел» и «откуда зашёл»**.

## Где пригодится

- **CTF Forensics:** задачи с выгрузкой профиля и кэша RDP.
- **DFIR:** установление способа доступа и действий атакующего.
- **Threat Hunting:** поиск аномальных RDP-подключений (новые адреса, время).
- **Работа:** реагирование на инциденты с латеральным движением по RDP.
