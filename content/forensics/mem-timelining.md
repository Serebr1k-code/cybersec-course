## Вопрос, с которого всё начинается

В дампе памяти лежат процессы, соединения, модули. Но чтобы понять **сценарий** атаки,
нужно не просто перечислить объекты, а расположить их **по времени**: что произошло
раньше, что позже. Как собрать таймлайн из памяти?

## Наш пример: дамп с событиями

У нас есть `mem.raw`. Первым делом извлекаем объекты с временными метками. Volatility 3
умеет собирать их в один поток:

```
$ vol.py -f mem.raw timeliner.Timeliner --output csv > timeline.csv
```

Получаем строки вида `время, объект, описание`. Это сырьё для таймлайна.

## Откуда в памяти берётся время

Разные объекты хранят разные метки:

- **процессы** — время создания (`CreateTime`);
- **сетевые соединения** — время установки;
- **модули/DLL** — время загрузки;
- **файловые объекты** — время последнего доступа;
- **события журналов**, ещё не сброшенные на диск.

Каждая метка — точка на оси времени.

## Шаг 1: нормализовать время

Метки приходят в разных форматах: **FILETIME** (100-нс тики с 1601 года), Unix-время,
строки. Прежде чем объединять, их приводят к **одному формату и одному часовому поясу**
(обычно UTC). Иначе события «перепутаются» во времени.

```
$ head -3 timeline.csv
2026-03-10T03:14:10Z,process,evil.exe created
2026-03-10T03:14:12Z,network,10.0.0.5:4444 connect
2026-03-10T03:14:15Z,module,evil.dll loaded
```

## Шаг 2: читать таймлайн как сценарий

По порядку видно историю: процесс создан → открыл соединение → загрузил модуль. Это уже
сценарий. Форензик ищет **корреляции**:

- процесс, созданный незадолго до подозрительного соединения;
- модуль, загруженный вне обычного времени;
- несколько событий в одну секунду (скрипт/автоматизация).

## Шаг 3: сопоставить с другими источниками

Таймлайн памяти — один источник. Его сверяют с дисковыми артефактами (Prefetch, EVTX),
сетевыми логами, журналами EDR. Совпадение времени по нескольким источникам делает вывод
устойчивым.

## Ловушка: время в памяти «плавает»

- **часовой пояс**: метки могут быть в локальном времени, а не UTC;
- **дрейф часов**: часы могли «убегать», особенно на виртуалках;
- **перезагрузка**: после неё в памяти нет старых объектов — таймлайн начинается заново.

Поэтому таймлайн памяти покрывает **сессию с момента загрузки**, а не всю историю. Более
ранние события ищи на диске.

## Что мы теперь знаем

- Таймлайн собирают из временных меток объектов памяти.
- Метки нужно привести к одному формату и UTC.
- Порядок событий даёт сценарий атаки.
- Таймлайн сверяют с дисковыми и сетевыми источниками.
- Память покрывает только текущую сессию — раньше ищи на диске.

## Форматы времени и почему их нужно сводить

Память хранит метки в разных системах счисления, и это первая ловушка таймлайна:

- **FILETIME** — 64-битное число 100-наносекундных тиков с 1 января **1601** года. Так
  хранит время Windows и Volatility для Windows-объектов.
- **Unix epoch** — секунды с 1 января 1970 года. Так живут Linux-структуры (`struct
  task_struct`, `struct sock`).
- **POSIX timespec** — секунды + наносекунды, используется в Linux-метаданных.
- **Строки** — человекочитаемый вид, приходящий из логов в памяти.

Свести их можно через конвертер. FILETIME → Unix:

```
$ python3 -c "print(133801796400000000/10**7 - 11644473600)"
1768300044.0
```

(вычитаем 11644473600 секунд — разницу эпох). Без приведения к одному формату событие из
Linux-структуры и событие из Windows-структуры встанут «врозь», и корреляция сломается.

## Источники меток в памяти

| Объект | Метка | Что говорит |
|--------|-------|-------------|
| `EPROCESS` (Windows) | `CreateTime` | когда запущен процесс |
| `task_struct` (Linux) | `start_time` | когда запущена задача |
| TCP endpoint / `struct sock` | время установки | когда открыто соединение |
| `_LDR_DATA_TABLE_ENTRY` | время загрузки DLL | когда загружен модуль |
| `_CM_KEY_NODE` (реестр) | `LastWriteTime` | когда изменён ключ реестра |
| файловые объекты | atime/mtime | доступ/изменение |
| буферы журналов | `TimeGenerated` | события, не сброшенные на диск |

Особенно ценны **буферы журналов**: события, которые ещё не записаны в EVTX на диске,
живут в памяти и могут быть утеряны после выключения. Их извлекают плагином
`windows.evtx`/`dumpfiles` и добавляют в таймлайн.

## Сборка «супер-таймлайна»

Один поток из Volatility — только начало. Настоящий таймлайн объединяет память, диск и
сеть в один файл. Для этого используют **plaso/log2timeline**:

```
$ log2timeline.py --storage-file case.plaso /evidence/disk.img
$ psort.py -o l2tcsv -w super.csv case.plaso "date > '2026-03-10 03:00:00'"
```

Память в plaso добавляют отдельным источником. Полученный CSV сортируют по времени и
фильтруют окно атаки. Плюс супер-таймлайна: события из **разных** источников видны
рядом, и корреляция не требует ручного сопоставления.

## Часовые пояса и дрейф часов

- **Часовой пояс**: FILETIME всегда UTC, а Linux-логи могут быть в локальном времени.
  Приведи всё к UTC **до** объединения.
- **Дрейф часов**: на виртуалках часы «убегают»; расхождение в секунды между хостом и ВМ
  ломает точную корреляцию. Сверяй по `w32time`/NTP-событиям.
- **Перезагрузка**: `uptime`/`SystemUpTime` показывает, с какого момента машина живёт —
  события **до** этого времени в памяти отсутствуют.

```
$ vol.py -f mem.raw windows.info.Info | grep -i 'SystemTime\|Uptime'
```

`SystemTime` — время снятия дампа; `Uptime` — сколько система работает. Всё, что раньше
`SystemTime - Uptime`, в памяти не сохранится.

## Ограничения таймлайна из памяти

- **Только текущая сессия** — после перезагрузки старых объектов нет.
- **Неполнота** — не все структуры содержат метки; закрытые и вычищенные объекты
  отсутствуют.
- **Смещение времени** — «плавающие» часы дают ошибки в секунды и минуты.
- **Шум** — тысячи штатных событий маскируют одно вредоносное; нужна фильтрация.
- **Зависимость от версии ядра/ОС** — профили Volatility привязаны к конкретным сборкам.

## Практический чеклист

1. `vol.py ... timeliner.Timeliner` — собрать события с метками.
2. Привести все метки к **UTC** и одному формату.
3. Определить `SystemTime` и `Uptime` — границу «что вообще может быть в памяти».
4. Добавить буферы журналов (`windows.evtx`) — события, не сброшенные на диск.
5. Объединить с диском/сетью в супер-таймлайн (`plaso`).
6. Отфильтровать окно атаки и искать корреляции (процесс → соединение → модуль).
7. Помнить про дрейф часов при сопоставлении с внешними логами.

## От «списка событий» к «сценарию атаки»

Сырой таймлайн — это сотни строк. Форензик превращает его в рассказ через **корреляцию**.
Полезные шаблоны:

- **Цепочка запуска**: родительский процесс → дочерний. `winword.exe` порождает
  `powershell.exe` — макрос. Смотрим `ppid` в `pstree`/`pslist`.
- **Процесс → сеть**: процесс, созданный за секунды до соединения, — почти наверняка
  инициатор. Сопоставляем `CreateTime` процесса и время endpoint'а.
- **Процесс → файл**: обращение к `lsass.exe` или создание файла в `%TEMP%`.
- **Всплеск событий**: несколько действий в одну секунду — скрипт или автоматизация, а не
  человек.
- **Несоответствие времени**: файл с «старым» mtime, но созданный только что, — подделка.

Пример «прочитанного» окна:

```
03:14:10  process   winword.exe created
03:14:11  process   powershell.exe created (parent: winword.exe)   ← макрос
03:14:12  network   powershell.exe -> 203.0.113.9:4444 ESTABLISHED ← C2
03:14:15  module    amsi.dll patched (unusual)                     ← обход защиты
03:14:20  file      C:\Users\bob\AppData\Local\Temp\x.dll created
```

Читается однозначно: фишинг-документ → макрос → обратная оболочка → обход AMSI →
дроппер. Такой вывод идёт в отчёт.

## Работа с шумом: фильтрация и приоритеты

В дампе штатных событий в разы больше вредоносных. Приёмы фильтрации:

- отсечь системные PID (4, 0) и известные службы;
- исключить ожидаемые соединения (обновления, домен, NTP);
- оставить окно атаки (`date >`/`date <`);
- сгруппировать по `comm`/`image` и искать редкие имена;
- сортировать по «подозрительности», а не по времени.

```
$ vol.py -f mem.raw timeliner.Timeliner --output csv | \
    grep -vE 'System|svchost|services|explorer' | sort -t, -k1 | head -20
```

## Сопоставление с EDR и сетевыми логами

Память — один свидетель. Устойчивый вывод строится на **нескольких независимых**
источниках, совпавших по времени:

| Источник | Что подтверждает |
|----------|------------------|
| память (Volatility) | объекты и их метки «здесь и сейчас» |
| диск (MFT, Prefetch, EVTX) | что осталось после выключения |
| EDR | детекты и блокировки в реальном времени |
| сеть (NetFlow, proxy) | куда шёл трафик |
| аутентификация (DC-логи) | под какой учёткой действовали |

Совпадение трёх-четырёх источников по времени делает вывод практически неопровержимым.

## Ограничения

- **Метки неполны** — не каждый объект имеет время; часть событий вообще без метки.
- **Порядок внутри секунды** — при равных секундах нужна миллисекундная точность, которой
  может не быть.
- **Разные эпохи** — FILETIME и Unix легко перепутать; ошибка даёт сдвиг в 369 лет.
- **Анти-форензика** — атакующий может подделать метки (`timestomp`); сверяй с
  независимыми источниками.
- **Дамп снят поздно** — после выключения/перезагрузки память пуста; таймлайн придётся
  строить по диску.

## Практический чеклист

1. Собрать события с метками (`timeliner`).
2. Привести всё к UTC и одному формату.
3. Определить границу сессии (`SystemTime`, `Uptime`).
4. Добавить буферы журналов и (по возможности) дисковые источники.
5. Отфильтровать шум, сфокусироваться на окне атаки.
6. Искать корреляции: родитель→потомок, процесс→сеть, всплески.
7. Подтвердить вывод минимум двумя независимыми источниками.

## Куда дальше

Таймлайн даёт время. Дальше добавим к нему **сеть**: с кем и куда соединялся хост. А пока
запомни: таймлайн памяти покрывает текущую сессию, а раньше — ищи на диске.

## Где пригодится

- **CTF Forensics** — задачи на восстановление порядка событий.
- **DFIR / Incident Response** — реконструкция сценария атаки.
- **Анализ образов дисков** — корреляция памяти и диска.
