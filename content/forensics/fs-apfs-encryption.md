## Вопрос, с которого всё начинается

Том APFS зашифрован. Чтобы прочитать данные, нужны ключи. Где они и как устроены?
Разберём **keybag** — хранилище ключей APFS.

## Наш пример: зашифрованный том

## Шаг 1: как шифруется APFS

APFS шифрует **каждый файл** своим ключом. Ключи хранятся в **keybag** — структуре с
несколькими «связками» (keybags):

- `Bag1` — том (volume);
- `Bag2` — метаданные;
- `Bag3` — пользователи.

## Шаг 2: где keybag

На macOS ключи привязаны к **Secure Enclave** (аппаратный чип). Извлечь их «в лоб»
нельзя. При анализе образа keybag лежит внутри тома:

```
$ apfs-fuse --help | grep -i keybag
```

## Шаг 3: пароль и ключи

Расшифровка возможна, если есть:

- **пароль пользователя** (для user keybag);
- **recovery key**;
- **институциональный ключ** (MDM/FileVault).

```
$ apfs-fuse -p <password> disk.img /mnt/apfs
```

`-p` передаёт пароль для разблокировки user keybag.

## Шаг 4: что внутри keybag

Keybag содержит зашифрованные ключи (wrapped keys). Чтобы их развернуть, нужен
KEK (key-encryption key), выводимый из пароля:

```
(password) → PBKDF2 → KEK → unwrap → VEK → decrypt volume
```

Без пароля цепочка не запускается.

## Шаг 5: практика

- если пароль известен — `apfs-fuse -p`;
- если есть Secure Enclave — нужен живой разблокированный Mac;
- brute-force пароля FileVault практически невозможен (сильный KDF).

## Что мы теперь знаем

- APFS шифрует файлы; ключи — в keybag.
- Keybags: том, метаданные, пользователи.
- На Apple Silicon ключи в Secure Enclave.
- Пароль разблокирует user keybag (apfs-fuse -p).
- Без пароля расшифровка невозможна.

## Если не сработало

- Нет пароля? Ищи recovery key у владельца.
- Secure Enclave? Нужен живой Mac.
- MDM? Проверь институциональный ключ.

## Разбор keybag

Keybag — это контейнер с ключами APFS. Он лежит в метаданных тома и
описывается структурой `apfs_keybag`. Просматриваем его заголовок:

```
$ apfsutil list /dev/disk2s1
Volume: Macintosh HD
  Encrypted: yes
  Keybag:    present (2 keybags)
  Keybag entries: 5
```

Каждая запись keybag — это «обёрнутый» ключ для конкретного класса защиты.
Сама структура (упрощённо):

```
struct apfs_keybag {
  uint16 version;
  uint32 num_entries;
  struct apfs_wrapped_key entries[];   // uuid, type, wrapped key
}
```

Тип (`type`) говорит, чем защищён ключ: паролем пользователя, ключом
аппаратного модуля или ничего (unprotected).

## Таблица: типы ключей APFS

| Класс | Тип защиты | Чем разблокировать |
|---|---|---|
| A | пользовательский пароль | пароль/логин macOS |
| B | ключ устройства | доступ к Secure Enclave |
| C | iCloud-ключ | восстановление через Apple ID |
| D | institutional | MDM/корпоративный ключ |
| F | unprotected | ничем (ключ в открытом виде) |

Если у тома есть запись класса F (unprotected) — ключ хранится без защиты,
и том можно расшифровать без пароля. Это встречается у томов, созданных
до включения FileVault, или при ошибке конфигурации.

## Пароль, KEK и unwrap

Пароль пользователя не шифрует диск напрямую. Схема такая:

1. Пароль → KDF (PBKDF2) → ключ-обёртка (KEK).
2. KEK разворачивает (`unwrap`) ключ класса A из keybag.
3. Ключ класса A расшифровывает тома.

```
$ python3 -c "import hashlib; print(hashlib.pbkdf2_hmac('sha256', b'secret', b'salt', 100000).hex()[:32])"
9f2c1ab7...
```

Это значит: без пароля ключ класса A не получить, а brute-force упирается в
стоимость PBKDF2 (сотни тысяч итераций). Поэтому в форензике APFS чаще
используют **уже разблокированный** том или ключ из памяти.

## Практика: разблокировка

На живой системе том уже разблокирован, и ключ есть в памяти ядра. На образе
используют внешние утилиты:

```
$ apfs-fuse -o allow_other /dev/disk2s2 /mnt/apfs
$ libfvdeinfo /dev/disk2s2
$ libfvde-mount /dev/disk2s2 /mnt/fvde -X recovery_key.txt
```

`libfvde` работает с FileVault 2 (CoreStorage/APFS) и умеет использовать как
пароль, так и recovery-ключ. Recovery-ключ (48 символов) хранится в
корпоративном хранилище и часто доступен IR-команде.

## Границы метода и типичные ошибки

- **Secure Enclave.** На Apple Silicon ключ класса B привязан к чипу; без
  самого устройства расшифровать образ невозможно даже с паролем.
- **Несколько пользователей.** У каждого своя запись keybag — пароль одного
  не открывает тома другого, если ключи не общие.
- **Повреждённый keybag.** Обрыв записи в метаданных делает том частично
  нечитаемым; сначала делай посекторную копию.
- **Живой том.** Никогда не монтируй оригинал на запись — только read-only
  образ, иначе изменишь метаданные и потеряешь доказательства.

## Если сработало

Том разблокирован — немедленно снимай посекторную копию расшифрованного
представления, пока ключ жив:

```
$ dd if=/dev/disk2s2 of=decrypted.img bs=1M status=progress
$ sha256sum decrypted.img > decrypted.img.sha256
```

Фиксируй хеш сразу: целостность расшифрованного образа придётся доказывать
в отчёте, а ключ после перезагрузки исчезнет навсегда.

## Как выглядит keybag на диске

Метаданные APFS лежат в checkpoint-области контейнера. Найти keybag можно
по сигнатуре структуры:

```
$ xxd -l 64 -s 0x1000 disk.img
00001000: 4b42 4147 0100 0000 0500 0000 0000 0000  KBAG............
```

`KBAG` — сигнатура обёрнутого ключа (wrapped key block). Она встречается в
keybag тома и в per-file ключах. Число записей (`05 00 00 00`) — 5 ключей,
что совпадает с выводом `apfsutil`.

## Схема обёртки ключей

```
Пароль ──PBKDF2──> KEK ──AES-KW──> wrapped_key (класс A)
                                  │
Recovery Key ─────────────────────┘ (альтернативный путь)
                                  │
Secure Enclave (класс B) ─────────┘
```

AES Key Wrap (RFC 3394) не шифрует ключ, а «оборачивает» его с проверкой
целостности: неверный KEK даст ошибку разворачивания, а не мусорный ключ.
Это позволяет быстро проверить, подходит ли пароль, не расшифровывая том.

## Практическая проверка пароля

Проверяем кандидат пароля без полного монтирования:

```
$ libfvdeinfo -X candidate_key.txt /dev/disk2s2
libfvde: recovery key set
$ python3 -c "
from Crypto.Cipher import AES
# unwrap проверяет целостность: неверный KEK -> ValueError
"
```

Recovery-ключ (48 символов, обычно разбит на группы по 4) часто есть у
компании. Если есть — расшифровка не требует пароля пользователя и не
упирается в PBKDF2.

## Много-томные контейнеры

APFS-контейнер может содержать несколько томов (System, Data, VM), и у
каждого — свой keybag. Расшифровка ключа одного тома **не** даёт ключ другого:

```
$ apfsutil list /dev/disk2
Container: disk2
  Volume: Macintosh HD   (encrypted)
  Volume: Macintosh HD - Data  (encrypted, shared key)
  Volume: VM             (encrypted, own key)
```

Тома System и Data обычно используют **общий** ключ (shared key), поэтому
разблокировка одного открывает оба. VM — отдельный. Учитывай это при оценке
объёма доступных данных.

## Что портит расшифровку

- **Сбитая копия.** Если образ снят с работающего тома, метаданные могли
  измениться в момент копирования — том не смонтируется.
- **Обрезанный образ.** Keybag в конце контейнера; неполная копия его теряет.
- **Несовпадение версий APFS.** Утилиты старее версии APFS могут не понять
  структуру — обновляй `apfs-fuse`/`libfvde`.
- **T2/Secure Enclave.** На машинах с T2 аппаратный ключ недоступен вне
  устройства — образ без машины не расшифровать.

## Инструменты APFS/FileVault

| Задача | Инструмент |
|---|---|
| Список томов/keybag | `apfsutil`, `diskutil apfs list` |
| Монтирование APFS | `apfs-fuse` |
| FileVault-расшифровка | `libfvde`, `dislocker` (BitLocker) |
| Живой ключ из памяти | `volatility`, `osxpmem` |
| Анализ образа | `dd`, `sleuthkit`, Autopsy |

`diskutil apfs list` на живой macOS показывает, **разблокирован ли** том и
сколько у него keybag-записей — это самый быстрый способ оценить достижимость.

## Резервный ключ как приоритет

В корпоративной среде recovery-ключ FileVault хранится централизованно
(MDM/Jamf/Intune). Это делает расшифровку рутинной:

```
$ sudo fdesetup changerecovery -personal   # посмотреть текущий ключ
$ jamf ... --get-filevault-key             # выгрузить из MDM
```

Порядок действий при изъятии Mac: сначала получить recovery-ключ из MDM
(пока есть доступ), потом снимать образ. Без ключа и без машины (Secure
Enclave) образ остаётся зашифрованным навсегда.
