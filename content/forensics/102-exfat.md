## Вопрос, с которого всё начинается

С карты памяти камеры изъят образ `card.img`. Известно, что подозреваемый снял видео, а потом удалил его — на карте остались только более старые кадры. Задача: вернуть удалённый видеоролик.

Карты SDXC, USB-флешки на десятки гигабайт и карты дронов используют файловую систему **exFAT**. Мы уже разбирали FAT (`forensics-fat`); exFAT — её развитие для больших носителей. Разберём карту и восстановим видео.

## Наш пример: карта `card.img`

Начинаем с определения файловой системы. `file -s` читает загрузочный сектор:

```bash
$ file -s card.img
card.img: DOS/MBR boot sector, code offset 0x76+2, OEM-ID "EXFAT   ",
          sectors/cluster 64, Media 0xf8, ...
```

Метка `EXFAT` и «code offset 0x76» указывают на exFAT. Зачем она появилась? FAT32 упиралась в два предела: файл не больше 4 ГиБ и том не больше 2 ТиБ. Для 4K-видео и больших карт этого мало — exFAT убрала эти ограничения, оставшись «простой» (без журнала). Это и делает восстановление с камер реалистичным: метаданные лежат в предсказуемых местах.

## Шаг 1: находим раздел и параметры

Смотрим карту разделов и читаем параметры ФС:

```bash
$ mmls card.img
       Slot      Start        End          Length       Description
      00:  00:00   0000008192   000000999999 000000991808  FAT32 (0x0b)
$ fsstat -o 8192 card.img | sed -n '1,12p'
File System Type: EXFAT
Cluster Size: 32768
Cluster Heap Offset (sectors): 512
Root Directory Cluster: 4
```

Раздел начинается с сектора `8192`. `fsstat` сообщает размер кластера (`32768` байт — 32 КиБ, типично для видео) и смещение области кластеров. Корневой каталог начинается с кластера `4`.

## Шаг 2: смотрим удалённые записи

Листаем каталоги с флагом удалённых записей:

```bash
$ fls -o 8192 -r -d card.img
r/r * 42: DCIM/100VIDEO/VID_0007.MP4
```

Звёздочка `*` — удалённая запись, `42` — её inode. Найден удалённый видеофайл `VID_0007.MP4` в папке `DCIM/100VIDEO` (стандартный путь камер). Восстанавливаем:

```bash
$ icat -o 8192 card.img 42 > vid0007.mp4
$ ls -l vid0007.mp4
-rw-r--r-- 1 user user 104857600 vid0007.mp4
```

Сто мегабайт видео восстановлены целиком. Почему — разберём механику exFAT.

## Шаг 3: понимаем структуру метаданных

В FAT32 запись каталога была одна: имя, атрибуты, первый кластер. В exFAT метаданные файла **разделены на несколько 32-байтовых записей**, идущих подряд и образующих **набор** (entry set). У каждой записи свой **тип** в первом байте:

| Тип | Запись | Что хранит |
|-----|--------|-----------|
| 0x85 | File | атрибуты и таймстампы (создание/изменение/доступ) |
| 0xC0 | Stream Extension | первый кластер, длину данных, флаги |
| 0xC1 | File Name | до 15 символов UTF-16, продолжения для длинных имён |

Набор идёт по порядку: File → Stream Extension → Name. Именно **Stream Extension** хранит **первый кластер** и **длину данных** — то, что нужно для восстановления.

## Шаг 4: почему видео восстановилось целиком

В exFAT есть флаг **NoFatChain**. Если он выставлен, данные файла лежат **непрерывно** от первого кластера, и всю цепочку задаёт пара «первый кластер + длина данных» — таблица FAT не нужна. Для видеофайлов на картах камер это норма.

Именно поэтому `icat` смог прочитать файл: запись Stream Extension сохранила и первый кластер, и длину, а кластеры (непрерывный диапазон) не были перезаписаны.

Проверить восстановленное видео можно через `ffprobe`:

```bash
$ ffprobe -v error -show_entries format=duration -of csv=p=0 vid0007.mp4
10.0
```

Длительность 10 секунд — файл целый, не битый.

## Шаг 5: что ещё учесть в exFAT

Несколько особенностей, которые ломают наивный анализ:

- **Учёт занятости** в exFAT ведётся **Allocation Bitmap** (файл `$Bitmap` в корне) — по одному биту на кластер. Таблица FAT необязательна и часто пуста. Поэтому если файл фрагментирован (NoFatChain не выставлен), цепочку надо искать именно в FAT.
- **Valid Data Length (VDL)** может быть меньше длины данных — хвост файла «не инициализирован». Для форензика это лакомый кусок: там могут лежать **остатки прежних данных**.
- **Длинные имена** собираются из нескольких записей `0xC1`; последняя помечена битом `0x40`.
- **Кластеры 0 и 1 зарезервированы**, корень обычно кластер 4.
- **Удаление**: у записи File сбрасывается бит «in-use» (тип `0x85` → `0x05`), но Stream и Name могут остаться — по ним и восстанавливают.

## Шаг 6: если метаданные утеряны

Когда запись каталога переиспользована, метаданные теряются, и остаётся **карвинг** — поиск файлов по сигнатурам. На картах памяти это особенно эффективно, потому что содержимое — это медиа с узнаваемыми заголовками (JPEG, MP4, MOV):

```bash
$ photorec card.img
$ foremost -i card.img -o out/ -t jpg,mp4,mov
```

Важно помнить: карвинг восстанавливает **только содержимое** — без имён, времени и путей. Если нужно доказать существование конкретного файла, метаданные важнее.

## Полный разбор: от boot sector к восстановленному видео

Прогоним разбор `card.img` в один сценарий.

1. **Находим раздел.** `mmls card.img` → смещение.
2. **Читаем boot sector.** `fsstat -f exfat -o <off> card.img` — размер кластера, таблицы, bitmap.
3. **Смотрим удалённые записи.** `fls -f exfat -o <off> card.img` — удалённые помечены; каталог — **набор записей** (File/Directory/Stream/Name).
4. **Понимаем, почему видео цело.** У больших файлов extent'ы лежат отдельными записями; даже после удаления они часто указывают на ещё не перезаписанные кластеры.
5. **Восстанавливаем.** `icat -f exfat -o <off> card.img <inode>`.

Ключ: exFAT (для SD/флешек) хранит данные «широко» — непрерывные области, которые легко восстановить.

## Шпаргалка exFAT

| Структура | Роль |
|-----------|------|
| Boot Sector | параметры ФС |
| FAT | цепочки кластеров (если не continuous) |
| Allocation Bitmap | карта занятости |
| Directory Entries | записи файлов (set) |

Отличие от FAT32: exFAT убрал 8.3-ограничение, поддержал огромные файлы и наборы записей.

## Частые вопросы

**Почему большие файлы восстанавливаются лучше мелких?** Их данные занимают непрерывную область, которую сложнее перезаписать целиком.

**Что если метаданные утеряны?** Карвинг по сигнатурам (фото — JPEG, видео — MP4).

**Чем exFAT лучше FAT32 для форензика?** Меньше ограничений, но структура чуть сложнее (bitmap + наборы записей).

**TRIM на SD-карте?** Некоторые карты стирают блоки — восстановление может быть невозможно.

## Что мы теперь знаем

- exFAT — ФС больших карт и флешек; метка `EXFAT` в загрузочном секторе.
- Метаданные файла — **набор** записей: File (`0x85`), Stream Extension (`0xC0`), Name (`0xC1`).
- Stream Extension хранит первый кластер и длину данных; флаг **NoFatChain** = непрерывная раскладка.
- Учёт занятости — **Allocation Bitmap** (`$Bitmap`), а не FAT.
- `fls -r -d` находит удалённые записи, `icat` восстанавливает содержимое; VDL может хранить остатки.
- Без метаданных помогает карвинг (`photorec`), но он не вернёт имена и время.
