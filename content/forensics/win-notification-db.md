## Вопрос, с которого всё начинается

Мессенджер показывал уведомление с текстом, но само приложение уже удалено, а логи пусты.
Остался ли где-то **текст** этого уведомления? Да — Windows хранит историю тостов в
отдельной базе.

## Наш пример: wpndatabase.db

Файл истории уведомлений лежит в профиле:

```
C:\Users\jdoe\AppData\Local\Microsoft\Windows\Notifications\wpndatabase.db
```

```
$ file wpndatabase.db
wpndatabase.db: SQLite 3.x database
```

Это **SQLite**-база, как и браузерные истории. Значит, читается `sqlite3`.

## Что такое «уведомления» в Windows

**Toast-уведомление** — всплывающее сообщение в правом нижнем углу от приложения. Чтобы
показывать «Центр уведомлений» (Action Center) и историю, Windows сохраняет каждое
уведомление в `wpndatabase.db`: приложение, время, заголовок, текст, а иногда вложение.

Для аналитика это ценно тем, что **текст уведомления — это то, что видит пользователь**:
сообщение мессенджера, письмо, напоминание, алерт безопасности. Приложение может удалить
свои данные, но копия тоста остаётся в системной базе.

## Шаг 1: посмотреть таблицы

```
$ sqlite3 wpndatabase.db ".tables"
Notification  NotificationHandler  HandlerSettings  ...
```

Главная таблица — `Notification`. В ней поля с приложением (`HandlerId`), временем и
содержимым.

## Шаг 2: вытащить уведомления

```
$ sqlite3 -header wpndatabase.db \
  "SELECT datetime(ExpiryTime,'unixepoch'), HandlerId FROM Notification LIMIT 5;"
ExpiryTime            HandlerId
2025-06-02 09:55:00   ...!App
```

`HandlerId` — идентификатор приложения-источника. Содержимое уведомления хранится в полях
типа `Payload`/`Content` и часто **сжато** или в виде XML — поэтому «просто SELECT» даёт
нечитаемое; нужен разбор payload.

## Шаг 3: разобрать содержимое

Payload уведомления — это XML-структура (тот же формат, что шлёт приложение). Практично
сначала поискать по базе читаемые строки:

```
$ strings -el wpndatabase.db | grep -iE 'nto|password|meeting|urgent' | head
Meeting at 15:00 with the finance team
nto{wpnd_n0t1f_t0ast}
```

Метка в тексте тоста — типичный CTF-приём: содержимое уведомления специально содержит
искомую строку.

## Что даёт база уведомлений

| Вопрос | Что показывает |
|--------|----------------|
| Какие приложения уведомляли | `HandlerId` / список хендлеров |
| Когда пришло уведомление | временные поля записи |
| Что было в тексте | payload (XML/строка) |
| Получал ли пользователь алерт | текст системного уведомления |

## Частые ошибки и подводные камни

- **Читать payload как обычный текст.** Он часто XML и/или сжат; сначала `strings -el`,
  потом структурированный разбор.
- **Путать с журналом событий.** Уведомления не в EVTX; это отдельная база в профиле.
- **Одна база на пользователя.** У каждого профиля свой `wpndatabase.db` — не пропусти
  нужный.
- **Ограниченный срок хранения.** История уведомлений не бесконечна; старые тосты Windows
  чистит, поэтому база из теневой копии может быть полнее текущей.
- **Кодировка.** Тексты часто в UTF-16LE — снова `strings -el`.

## Шпаргалка команд

```
# Таблицы и схема
sqlite3 wpndatabase.db ".tables"
sqlite3 wpndatabase.db ".schema Notification"

# Список уведомлений
sqlite3 -header wpndatabase.db "SELECT * FROM Notification LIMIT 5;"

# Читаемые строки (UTF-16LE)
strings -el wpndatabase.db | grep -i '<слово>'
```

## Что мы теперь знаем

- История уведомлений Windows лежит в `wpndatabase.db` (SQLite) в профиле.
- Таблица `Notification` хранит приложение, время и payload уведомления.
- Payload часто XML/сжат — начинай со `strings -el`.
- База на пользователя и имеет ограниченный срок хранения (VSS помогает).
- Тексты тостов — самостоятельный источник улик и контекста.

## Сквозной пример: восстановление переписки из тостов

Разберём реальный сценарий: приложение-мессенджер удалили, чаты недоступны, но нужно
доказать, что пользователь получал конкретное сообщение.

Начинаем с поиска читаемых строк в базе. Тексты тостов часто в UTF-16LE:

```
$ strings -el wpndatabase.db | grep -iE 'http|meeting|invoice|urgent' | head
Invoice #4471 is overdue - pay today
Meeting moved to 15:00
```

Дальше уточняем приложение-источник. В таблице `Notification` есть `HandlerId`, который
указывает на приложение. Сопоставив `HandlerId` с таблицей хендлеров, получаем имя
программы:

```
$ sqlite3 -header wpndatabase.db \
  "SELECT n.HandlerId, datetime(n.ExpiryTime,'unixepoch') FROM Notification n LIMIT 5;"
HandlerId             datetime(...)
Slack!App             2025-06-02 09:55:00
```

Итог: из системной базы восстановлен текст сообщения и приложение, даже если сам мессенджер
уже удалён. Это классический пример, когда **системный артефакт переживает приложение**.

## Структура payload уведомления

Тост-уведомление в Windows описывается XML-шаблоном, и именно этот XML (или его фрагмент)
сохраняется в базе. Внутри — текст (`<text>`), иногда изображение и привязка к действию
(`<action>`). Если приложение шлёт картинку, в базе может остаться ссылка на файл-вложение
в кэше уведомлений. Разбор payload полезен, когда `strings` выдаёт «склеенный» XML: тогда
сохрани payload в файл и прогони через `xmllint` или парсер:

```
$ sqlite3 wpndatabase.db "SELECT Payload FROM Notification WHERE HandlerId LIKE '%Slack%';" > p.xml
$ xmllint --format p.xml | grep -i text
```

## Связь уведомлений с приложениями

| Элемент | Что даёт | Зачем аналитику |
|---------|----------|-----------------|
| `HandlerId` | идентификатор приложения | определить источник тоста |
| `HandlerSettings` | настройки хендлера | какие приложения уведомляли |
| Временные поля | когда показан тост | вписать в таймлайн |
| Payload | текст/структура тоста | восстановить содержимое |

Список хендлеров сам по себе ценен: он показывает, **какие приложения были установлены** и
показывали уведомления, даже если их файлы уже удалены.

## Ограничения хранения и роль VSS

История уведомлений не бесконечна: Windows периодически чистит старые записи. Поэтому
текущая база может быть «короткой». Решение — та же теневая копия тома: в историческом
снимке профиля сохраняется более ранняя и часто более полная `wpndatabase.db`. Сравнивая
два снимка, можно увидеть то, что уже исчезло из текущего состояния.

## Что фиксировать в отчёте

Зафиксируй путь к базе, `HandlerId` источника, извлечённый текст и время. Обязательно
оговори, что текст восстановлен из системной истории уведомлений, а не из самого
приложения — это влияет на оценку достоверности. Если payload был сжат/повреждён, укажи,
каким способом декодирован.

## Практика: извлечение ссылок и вложений из тостов

Многие тосты содержат **ссылку** или имя вложения. Их можно достать, не поднимая полный
парсер:

```
$ strings -el wpndatabase.db | grep -iE 'https?://|\.pdf|\.xlsx|\.docx' | head
https://files.example.com/invoice_4471.pdf
```

Ссылки ценны двумя вещами: домен показывает, с каким сервисом работал пользователь, а имя
файла связывает уведомление с конкретным документом. Дальше эту ссылку можно сопоставить с
браузерной историей и сетевыми логами — получится цепочка «пришло уведомление → открыл
ссылку → скачал файл».

## Сравнение уведомлений с журналами событий

База уведомлений и журнал событий смотрят на разные вещи. EVTX фиксирует **системные**
события (входы, службы, ошибки), а `wpndatabase.db` — то, что **видел пользователь**. В
расследовании они дополняют друг друга: журнал скажет, что служба запустилась, а база
уведомлений — что пользователю прилетел тост об этом. Держи оба источника под рукой: иногда
именно текст уведомления даёт контекст, которого нет в формальном журнале.

## Полный прогон от начала до конца

Соберём всю практику вместе. Дано: образ диска, задача — доказать получение конкретного
сообщения. Шаг первый: находим базу в профиле и опознаём формат (`file wpndatabase.db`).
Шаг второй: ищем читаемые строки (`strings -el ... | grep -i <слово>`). Шаг третий: если
нужен контекст, выгружаем payload и смотрим приложение-источник по `HandlerId`. Шаг
четвёртый: сопоставляем время с журналом событий и Timeline. На выходе — восстановленный
текст, источник, время и связь с другими действиями. Вся цепочка занимает несколько команд
и не требует запуска Windows: всё делается над копией файла.

## Типичные сценарии и что они доказывают

Уведомления особенно полезны в трёх ситуациях. Первая — восстановление коммуникаций, когда
само приложение удалено: текст тоста остаётся в системной базе. Вторая — подтверждение
**времени** события: тост о встрече или платеже датирует взаимодействие, даже если других
логов нет. Третья — установление **списка приложений**: хендлеры в базе показывают, какие
программы уведомляли пользователя, что косвенно говорит о его инструментарии. Во всех трёх
случаях база уведомлений выступает независимым источником, и его ценность растёт, когда
другие данные вычищены. Помни только об ограничении срока хранения и по возможности
работай с историческим снимком профиля.

## Разбор payload уведомления шаг за шагом

Разберём, как из «сырой» записи получить человекочитаемый текст. В базе payload хранится
как blob, часто в виде XML или сжатой структуры. Первый приём — выгрузить конкретную
запись в файл и посмотреть её тип:

```
$ sqlite3 wpndatabase.db "SELECT Payload FROM Notification ORDER BY ExpiryTime DESC LIMIT 1;" > payload.bin
$ file payload.bin
payload.bin: XML 1.0 document, UTF-8 text
```

Если `file` говорит, что это XML, — форматируем и читаем текст напрямую. Если это
«data» или «zlib compressed data» — распаковываем (`zlib-flate -uncompress` или короткий
скрипт на Python) и повторяем опознание. Такой пошаговый подход спасает, когда приложение
шлёт уведомления в нестандартной упаковке. Второй приём — если payload разбит на несколько
полей (заголовок и тело отдельно), собери их вместе: только в паре они дают полный смысл
уведомления. Третий приём — ищи привязку к действию: тосты с кнопками содержат идентификатор
действия, который иногда указывает на конкретную ссылку или объект в приложении.

## Что делать, когда база почти пуста

Бывает, что в текущей `wpndatabase.db` всего пара уведомлений — пользователь чистил историю
или система давно её ротировала. Не спеши делать вывод «уведомлений не было». Проверь три
вещи. Первое — соседние профили: у каждой учётной записи своя база, и на машине их может
быть несколько. Второе — теневые копии тома: исторический снимок профиля часто содержит
более полную базу. Третье — кэш уведомлений: вложения и картинки из тостов могут лежать
отдельно от самой базы, и по ним восстанавливается контекст. Только собрав все три слоя,
можно утверждать, что истории уведомлений действительно нет.

## Куда дальше

Мы посмотрели, что система **сообщала** пользователю. Дальше возьмём **Cortana и поисковую
историю** — что пользователь **искал сам**. А пока главное запомни: **база уведомлений
хранит то, что приложение могло уже стереть**.
