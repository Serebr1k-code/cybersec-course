## Вопрос, с которого всё начинается

Тебе дали образ диска `disk.img` с машины, где, по словам админа, «что-то произошло
в ночь на 1 марта». Файлов в образе тысячи, и у каждого — своя история. Как понять,
**в каком порядке** всё случилось: что скачали, что запустили, когда закрепились?
Разрозненные факты — это ещё не картина. Картину делает **хронология**.

В этом уроке мы построим хронологию одного подозрительного хоста от начала до конца.
Термины будем вводить по мере надобности.

## Наш пример: один файл и четыре времени

Начнём с самого простого. В образе есть файл `update.exe`. У каждого файла есть не
одно «время», а несколько — их называют **временными метками** (timestamps).
Посмотрим на них:

```bash
$ stat update.exe
  File: update.exe
  Size: 1024       Blocks: 8    IO Block: 4096  regular file
Modify: 2024-03-01 09:12:03.000000000 +0000
Access: 2024-03-01 09:12:05.000000000 +0000
Change: 2024-03-01 09:12:03.000000000 +0000
 Birth: 2024-03-01 09:12:01.000000000 +0000
```

Уже отсюда видно: файл **создан** в 09:12:01, **изменён** в 09:12:03, **прочитан**
в 09:12:05. События разнесены по секундам — значит, мы можем выстроить
последовательность. Это и есть заготовка хронологии.

## Шаг 1: четыре буквы MACB

В форензике метки принято обозначать аббревиатурой **MACB**:

| Буква | Англ. | Что значит |
|-------|-------|-----------|
| **M** | Modified | менялось содержимое |
| **A** | Accessed | файл читали/открывали |
| **C** | Changed | менялись метаданные (права, имя) |
| **B** | Birth | файл создан |

Важно понять разницу между **B** (создание) и **C** (изменение метаданных). Если файл
переименовали, метка `C` обновится, а `B` останется прежней. Именно на этом различии
мы позже поймаем подделку.

## Шаг 2: в NTFS меток вдвое больше

Наш образ — с Windows, а там файловая система **NTFS** (основная ФС Windows) хранит
метки **дважды**: в служебной записи `$STANDARD_INFORMATION` (сокращённо `$SI`) и в
`$FILE_NAME` (`$FN`). Проще говоря, одно и то же время записано в двух разных местах.

```bash
$ MFTECmd.exe -f '$MFT' --csv out --csvf mft.csv
```

В полученном CSV мы увидим колонки вроде `SI Creation` и `FN Creation`. Если значения
`$SI` и `$FN` **расходятся** — это почти всегда признак **timestomping** (подделки
меток): злоумышленник подправил «главное» время `$SI`, но не тронул `$FN`. Глубже —
в уроке `forensics-timestomp`.

## Шаг 3: собираем метки в один файл

Сравнивать метки по одной неудобно. Есть общий текстовый формат — **bodyfile**: каждая
строка — один файл и все его метки.

```
MD5|name|inode|mode|UID|GID|size|atime|mtime|ctime|crtime
```

Собрать его из образа проще всего инструментом `fls` из набора **Sleuth Kit** (набор
утилит для разбора образов дисков):

```bash
$ fls -r -m "C:/" -o 2048 disk.img > bodyfile.txt
```

`-r` — рекурсивно по всем папкам, `-m` — «выдай в формате bodyfile», `-o 2048` —
смещение начала раздела в секторах (его мы узнаём из `mmls`). На выходе — список
всех файлов с метками.

## Шаг 4: превращаем метки в таймлайн

Теперь утилита `mactime` разложит bodyfile по времени:

```bash
$ mactime -b bodyfile.txt -z UTC 2024-03-01..2024-03-02 | head
Date,Size,Type,Mode,UID,GID,Meta,File Name
2024-03-01 09:12:03,1024,macb,r/rrwxrwxrwx,0,0,1234-128-2,C:/Users/bob/Downloads/update.exe
2024-03-01 09:12:05,0,a..b,r/rrwxrwxrwx,0,0,1234-128-3,C:/Windows/Temp/run.bat
2024-03-01 09:12:09,0,...b,r/rrwxrwxrwx,0,0,1234-128-4,C:/ProgramData/evil/svc.exe
2024-03-01 09:14:44,0,m...,r/rrwxrwxrwx,0,0,5678-144-1,C:/Windows/System32/Tasks/Updater
```

Колонка `Type` — это как раз MACB: `macb` значит «совпали все четыре метки», `a..b` —
только access и birth, `...b` — только создание. Точка означает «этой метки нет».

Читаем цепочку сверху вниз: `update.exe` появился в 09:12:03, через две секунды
создан `run.bat`, ещё через четыре — `svc.exe` в `ProgramData`, а через две минуты
возникла задача `Updater` в Tasks. Это классическая цепочка **dropper → payload →
закрепление** (persistence). Мы не читали ни одного файла целиком — просто
упорядочили метки.

Флаг `-z UTC` нормализует все метки к одному часовому поясу — зачем, объясним ниже.

## Шаг 5: когда нужен «супертаймлайн»

`mactime` показывает только метки файловой системы. Но события есть и в реестре, и в
логах, и в Prefetch. Чтобы свести **всё** в одну ленту, используют **plaso** (он же
`log2timeline`) — он парсит десятки форматов в единую модель. Два шага: собрать и
вывести.

```bash
$ log2timeline.py --parsers 'winreg,evtx,mft,prefetch,lnk' --storage-file t.plaso /evidence
$ psort.py -o l2tcsv -w timeline.csv t.plaso "date > '2024-03-01' and date < '2024-03-02'"
```

Первая команда строит хранилище `t.plaso` из папки с артефактами, вторая выгружает
окно времени в CSV. Выражение `"date > ..."` — язык запросов plaso; им удобно сузить
миллионы событий до нужного часа.

## Шаг 6: где ещё живут метки

Файловая система — не единственный источник времени. У Windows есть несколько «часов»,
и каждый добавляет деталь:

| Источник | Что даёт |
|----------|----------|
| `$UsnJrnl:$J` | журнал изменений: создание/переименование/удаление с временем |
| Prefetch | время последнего запуска программы (до 8 записей) |
| EVTX | время событий: входы, запуск процессов, службы |
| Реестр | время последнего изменения ключей |
| LNK / JumpLists | время открытия файлов пользователем |

Сопоставляя их, можно восстановить не только «что было», но и «кто это сделал».
Например, Prefetch скажет, что `update.exe` **запускался**, даже если сам файл уже
удалён, — и это уличит злоумышленника.

## Шаг 7: ищем аномалии в готовом таймлайне

Таймлайн — главный инструмент обнаружения сокрытия следов. Смотрим на странности:

```bash
$ awk -F, '$1 > "2026-01-01" {print}' timeline.csv | head   # события «из будущего»
$ awk -F, '$1 < $4 {print}' timeline.csv | head             # изменён раньше создания
```

Первая команда ищет метки позже сегодняшней даты — почти всегда подделка. Вторая —
файлы, изменённые раньше, чем созданные, что физически невозможно. Такие строки —
первое, на что смотрит эксперт.

## Часовой пояс — главная ловушка

Самая частая ошибка новичка — сравнивать метки из разных источников, не приведя их к
одному поясу. EVTX и NTFS хранят время в **UTC**, а вот FAT — в **локальном** времени.
Смешаешь их — события встанут «не в том порядке», и вывод окажется ложным.

Поэтому нормализуйте всегда: `mactime -z UTC`, `psort.py --timezone UTC`. Тогда
«скачивание → запуск → закрепление» действительно окажется в правильной
последовательности.

## Что мы теперь знаем

- У файла не одно время, а несколько: **MACB** — modified, accessed, changed, birth.
- В NTFS метки дублируются (`$SI` и `$FN`), и их расхождение выдаёт подделку.
- `fls -m` собирает метки в bodyfile, `mactime` превращает их в таймлайн.
- Для всех источников сразу — `plaso` + `psort`.
- Любые метки надо привести к UTC, иначе порядок событий перепутается.

## На что смотреть дальше

- **События «из будущего»** — метка позже текущего времени: почти всегда подделка.
- **Метка раньше установки ОС** — файл не мог появиться раньше системы.
- **Пробелы** — период без событий там, где активность точно была (следы чистки логов).
- **Расхождение `$SI`/`$FN`** — один и тот же файл «появляется дважды» при сортировке.

## Куда дальше

Мы собрали хронологию из файловой системы. Но половина событий лежит в **логах**: кто
входил, какие команды выполнял, что отвечал веб-сервер. В следующем уроке мы возьмём
один `access.log` и найдём в нём атаку — от сканирования до webshell. А пока запомни
главное: **сначала приведи время к UTC, потом выстраивай порядок**.

## Где пригодится

- **CTF:** задачи «восстанови хронологию» — классика категории Forensics.
- **DFIR:** ключевой метод анализа инцидента.
- **Threat Hunting:** выявление аномалий по времени до срабатывания сигнатуры.
- **Криминалистика:** доказуемая последовательность событий.
- **Анти-форензика:** понимание, как детектится подделка меток.
