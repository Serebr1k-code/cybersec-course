## Вопрос, с которого всё начинается

Компания использует Okta как единую точку входа (SSO) во все приложения. Ночью кто-то вошёл
в Okta под легитимной учёткой, а утром в логах приложений — странная активность. Пароль
могли и не украсть: есть способы обойти MFA. Как разобраться по журналу Okta?

## Что такое Okta System Log

**Okta System Log** — журнал событий IdP-провайдера Okta. Каждое событие имеет
**eventType** — строку вида `user.session.start`, `user.authentication.sso`,
`policy.evaluate_sign_on`, `group.privilege.grant`. Поля события:

- **actor** — кто (пользователь, приложение, admin);
- **client** — откуда (IP, гео, device, user-agent);
- **outcome** — `SUCCESS` / `FAILURE` / `ALLOW` / `DENY`;
- **target** — над кем/чем (пользователь, группа, приложение);
- **published** — время (ISO 8601, UTC);
- **authenticationContext** — детали аутентификации (credential type, MFA).

Доступ: встроенный Log UI, API `/api/v1/logs`, а также экспорт в SIEM.

## Наш пример: журнал входов

```
$ ls -la
-rw-r--r-- 1 student student 6144 okta.log
$ head -n 2 okta.log
{"published":"2026-03-11T02:14:09Z","eventType":"user.session.start","actor":{"alternateId":"alice@corp.com"},"client":{"ipAddress":"203.0.113.9"},"outcome":{"result":"SUCCESS"}}
{"published":"2026-03-11T02:15:02Z","eventType":"user.authentication.sso","actor":{"alternateId":"alice@corp.com"},"client":{"ipAddress":"203.0.113.9"},"outcome":{"result":"SUCCESS"}}
```

Обычный вход с одного IP. Теперь ищем аномалию:

```
$ grep -Ei 'mfa|factor|admin|token|nto' okta.log
{"published":"2026-03-11T02:16:40Z","eventType":"user.mfa.factor.deactivate","actor":{"alternateId":"alice@corp.com"},"outcome":{"result":"SUCCESS"},"EVIDENCE":"nto{okta_syst3m_l0g_mf4_push}"}
```

**Деактивация MFA-фактора** — красный флаг. Если злоумышленник сначала вошёл (например,
через MFA-фатинг), а затем отключил второй фактор, он закрепляется в аккаунте.

## Шаг 1: типичные сценарии атак

| eventType | Что означает | Почему подозрительно |
|-----------|--------------|----------------------|
| `user.mfa.factor.deactivate` | отключён MFA | закрепление |
| `user.mfa.okta_verify.push` (много) | push-фатинг | бомбардировка запросами |
| `user.account.privilege.grant` | выданы права | эскалация |
| `admin.api_token.create` | создан API-токен | постоянный доступ |
| `policy.rule.update` | изменена политика | ослабление MFA |
| `user.session.start` (новый IP/страна) | вход | захват |

Смотри последовательность: множество push → успех → отключение фактора → создание токена.

## Шаг 2: MFA-фатинг

**MFA fatigue (push fatigue)** — атака, при которой злоумышленник, зная пароль, шлёт
пользователю десятки запросов на подтверждение, пока тот не нажмёт «Approve» от усталости
или из-за паники. В журнале это выглядит как **шквал** событий `user.mfa.okta_verify.push`
с `outcome: FAILURE`, за которым следует `SUCCESS`.

Признаки в логе: много push за минуты, разные IP, затем успешный вход. Именно поэтому
важно смотреть **частоту**, а не только результат.

## Шаг 3: выгрузка журнала

Через API:

```
$ curl -s -H "Authorization: SSWS ${OKTA_TOKEN}" \
    "https://corp.okta.com/api/v1/logs?since=2026-03-10T00:00:00Z&until=2026-03-13T00:00:00Z" \
    -o okta.json
```

Через SIEM-коннектор — потоковая выгрузка. Срок хранения Okta — обычно **90 дней**, поэтому
выгружай сразу. Ключ API выдаётся отдельно и тоже подлежит аудиту (создание токена —
событие).

## Шаг 4: разбор контекста

`authenticationContext` показывает, **как** прошла аутентификация: пароль, SSO, MFA. Если
вход прошёл с `credentialProvider: OKTA`, а MFA не было — значит, фактор отключён или
политика не применилась. Поле `securityContext` даёт ASN/IP-репутацию. Поле `device`
показывает, доверено ли устройство.

Сопоставляй **actor** и **client.ipAddress**: один IP в нескольких разных учётках — признак
массовой компрометации.

## Шаг 5: что делать после

- отозвать активные сессии (`user.session.end` / admin action);
- удалить rogue API-токены и приложения;
- включить/усилить MFA (например, number matching вместо простого push);
- проверить политики (`policy.rule.update` — не ослабили ли их);
- зафиксировать временную шкалу в отчёте.

## Мини-практика: найти деактивацию MFA

```
$ grep 'mfa.factor.deactivate' okta.log
{"eventType":"user.mfa.factor.deactivate","actor":{"alternateId":"alice@corp.com"},"outcome":{"result":"SUCCESS"}}
$ grep -c 'okta_verify.push' okta.log
37
```

Мы нашли деактивацию фактора и 37 push-запросов до неё. Это готовый нарратив атаки.

## Частые ошибки и подводные камни

- **Смотреть только успехи.** Неудачные push — часть атаки.
- **Игнорировать частоту.** Десятки событий за минуту важнее одного результата.
- **Забыть про API-токены.** Создание токена — постоянный доступ.
- **Истечение хранения.** Okta хранит логи ~90 дней.
- **Путать actor и target.** actor — кто, target — над кем действие.

## Что мы теперь знаем

- Okta System Log описывает аутентификацию через eventType/actor/client/outcome.
- MFA-фатинг виден как шквал `okta_verify.push` перед успехом.
- Отключение MFA и создание API-токена — закрепление атакующего.
- Хранение ~90 дней; выгружай через API/SIEM.
- Сопоставляй actor и IP между учётками.

## Что фиксировать в отчёте

| Что | Зачем |
|-----|-------|
| Диапазон и полнота выгрузки | покрытие |
| Список подозрительных eventType | доказательства |
| Частота MFA-push | признак фатинга |
| Созданные токены/права | закрепление |
| Действия по устранению | реакция |

## Расширенный пример: реконструкция сессии атакующего

Разберём полный сценарий компрометации Okta. У атакующего есть пароль, но нет MFA. Он
запускает **MFA-фатинг**: в журнале появляется серия событий `user.mfa.okta_verify.push` с
`outcome: FAILURE` — иногда десятки за несколько минут. Уставший пользователь нажимает
«Approve», и атакующий входит.

Дальше видно, как он **закрепляется**:

1. **`user.mfa.factor.deactivate`** — отключает второй фактор, чтобы входить только по
   паролю.
2. **`user.account.privilege.grant`** или **`group.privilege.grant`** — добавляет себя в
   привилегированную группу.
3. **`admin.api_token.create`** — создаёт API-токен для программного доступа, который
   переживает смену пароля.
4. **`policy.rule.update`** — ослабляет политику (например, убирает требование MFA).

Собрав эти события по времени, ты получаешь **полную цепочку** от первого push до rogue
admin. В отчёте важно указать `actor.alternateId`, `client.ipAddress` и
`client.geographicalContext` для каждого шага.

Полезный приём — **график частоты событий**: всплеск push-запросов виден глазом и сразу
отделяет фатинг от обычного входа. А поиск одного `ipAddress` по всем пользователям
показывает, не скомпрометированы ли другие аккаунты.

## Интеграция с SIEM и типовые детекты

Okta System Log обычно стримится в SIEM (Splunk, Sentinel, Elastic) через System Log API
или коннекторы. Это даёт возможность строить **правила детекции**:

- **MFA-фатинг**: N и более `okta_verify.push` за 5 минут для одного пользователя;
- **Rogue admin**: `privilege.grant` от неадминистратора или в нерабочее время;
- **Новый API-токен**: `admin.api_token.create` — всегда стоит внимания;
- **Смена политики**: `policy.rule.update` с ослаблением MFA;
- **Новый гео-контекст**: успешный вход из страны, где компания не работает.

Эти же правила помогают **threat hunting**: ты ищешь аномалию в поведении, а не конкретное
событие. Поле `client.geographicalContext` и `securityContext` дают основу. Важно помнить
про **ложные срабатывания**: командировка или VPN могут выглядеть как аномалия, поэтому
детекты проверяют контекст, а не только факт.

## Чек-лист разбора Okta

Порядок действий для каждого инцидента:

1. Определи **actor** (учётку) и **временное окно**.
2. Выгрузи все события по пользователю, а не только подозрительные.
3. Посчитай **частоту** `okta_verify.push` и других событий — всплеск важнее единичного.
4. Отметь **изменения состояния**: deactivate фактора, grant привилегий, create токена.
5. Проверь **ipAddress** по всем пользователям — нет ли массовой компрометации.
6. Зафиксируй **client.geographicalContext** и **securityContext** для атрибуции.
7. Сопоставь с журналами приложений, куда был SSO-доступ.

## Разница между «событием» и «аномалией»

Важно различать: журнал фиксирует **события**, а расследование ищет **аномалии**.
Один вход с нового IP — событие; вход с нового IP плюс отключение MFA плюс создание
токена за 10 минут — аномалия. Именно **совокупность и последовательность** дают вывод, а
не отдельная запись. Поэтому в отчёте всегда показывай контекст: соседние события, время
между ними, связанные идентичности. Это отличает качественное расследование от простого
перечисления строк лога.

## Что писать в отчёте

Отчёт по Okta-инциденту должен отвечать на четыре вопроса: **кто** (actor), **откуда**
(client.ipAddress), **что** (eventType), **когда** (published). Дополнительно укажи
**последовательность** действий и **какие меры** приняты (отзыв сессий, удаление токенов).
Если атака была MFA-фатингом, приведи **число push-запросов** и интервал — это количественно
показывает атаку. И обязательно отметь, была ли MFA включена до инцидента: если нет, это
корневая причина, которую нужно устранить. Отдельно перечисли все **созданные или
изменённые** объекты: API-токены, привилегии, политики — чтобы при устранении ничего не
пропустить.

## Разбор JSON-лога утилитой jq

Okta System Log — построчный JSON, поэтому его удобно разбирать `jq`. Частотный анализ
MFA-push в одну строку:

```bash
$ jq -r 'select(.eventType=="user.mfa.okta_verify.push") | .published' okta.log \
  | cut -c1-16 | sort | uniq -c | sort -rn
     31 2026-03-11T02:14
      6 2026-03-11T02:15
```

Тридцать один push в одну минуту — это уже не «пользователь нажал не туда», а атака.
Такой же приём показывает все смены состояния:

```bash
$ jq -r 'select(.outcome.result=="SUCCESS") | [.published,.eventType,.actor.alternateId] | @tsv' okta.log
2026-03-11T02:16:40Z  user.mfa.factor.deactivate  alice@corp.com
2026-03-11T02:17:12Z  admin.api_token.create      alice@corp.com
```

## Карта категорий eventType

| Префикс | Что покрывает |
|---|---|
| `user.session.*` | начало/конец сессии (вход, выход) |
| `user.authentication.*` | проверка пароля/SSO |
| `user.mfa.*` | факторы: enroll, verify, deactivate |
| `user.account.*` | изменение самой учётки |
| `group.*` / `group.privilege.*` | членство и привилегии |
| `policy.*` | правила доступа и MFA |
| `admin.api_token.*` / `app.*` | интеграции и программный доступ |

По префиксу сразу понятно, к какому слою относится событие, и какой вопрос задавать.

## Краевой случай: пробелы в выгрузке

System Log можно забирать двумя способами — **polling** (периодический запрос API) и
**streaming** (SIEM-коннектор). У polling есть окно между запросами, и при высокой частоте
события могут быть отброшены или продублированы; у streaming — риск потери при разрыве
соединения. Поэтому в отчёте всегда фиксируйте **метод сбора** и проверяйте монотонность
времени. Если между двумя событиями `published` зияет дыра, а вокруг — подозрительная
активность, это может быть не пауза атакующего, а пропуск в выгрузке.
