## Вопрос, с которого всё начинается

Ты снял образ Mac. На нём точно были сохранены пароли — в браузере, в почте, в SSH. Где
они лежат и можно ли их достать? Ответ — **Keychain**, связка ключей macOS. Но это не
обычный файл: записи зашифрованы, а ключ привязан к паролю пользователя.

## Что такое Keychain

**Keychain (связка ключей)** — защищённое хранилище macOS для паролей, токенов,
сертификатов и ключей. Основные файлы:

- `~/Library/Keychains/login.keychain-db` — связка пользователя (самое ценное);
- `/Library/Keychains/System.keychain` — системная связка;
- `~/Library/Keychains/<UUID>/` — iCloud-связка и прочее.

Современный формат (`keychain-db`) — это **SQLite-база**. Внутри — таблицы по типам
записей:

- **genp** — generic passwords (пароли приложений, Wi-Fi, SSH);
- **inet** — internet passwords (сайты, учётные данные веб-форм);
- **cert** — сертификаты;
- **keys** — криптографические ключи.

## Наш пример: база связки ключей

```
$ ls -la
-rw-r--r-- 1 student student 32768 login.keychain-db
$ file login.keychain-db
login.keychain-db: SQLite 3.x database
```

`file` сразу говорит, что это SQLite. Смотрим на содержимое:

```
$ strings login.keychain-db | grep -Ei 'genp|inet|cert|keychain|nto'
CREATE TABLE genp (acct TEXT, svce TEXT, data BLOB)
CREATE TABLE inet (srvr TEXT, acct TEXT, data BLOB)
keychain db version 9
EVIDENCE: nto{mac0s_k3ych41n_g3np_db}
```

Мы видим таблицы и их схему. Ключевые колонки: `acct` (аккаунт), `svce`/`srvr` (сервис или
сайт) и `data` — **зашифрованный BLOB** с паролем. Именно `data` и есть цель.

## Шаг 1: как устроено шифрование

Связка ключей использует **иерархию ключей**:

- у каждой записи есть **свой ключ**, которым зашифрован её `data`;
- ключ записи зашифрован **keychain-ключом**;
- keychain-ключ выводится из **пароля входа** пользователя (через PBKDF2) и хранится
  (защищённо) в системной связке.

Следствие: **без пароля пользователя расшифровать `data` нельзя**. Но при живом входе или
при известном пароле — можно. Иногда ключ утекает через **дамп памяти** (пока связка
разблокирована).

## Шаг 2: что видно без пароля

Даже без пароля база даёт много:

- **`acct` и `svce`/`srvr`** — не шифруются: видно, **какие** сервисы/сайты и **какие**
  логины сохранены;
- **метки времени** создания и изменения записей;
- **тип записи** (genp/inet/cert) — какие категории есть;
- **наличие iCloud-связки** — синхронизация.

Это уже полезно: можно доказать, что на машине были, например, корпоративные учётки.

## Шаг 3: инструменты

- **`security`** (на самом macOS) — `security dump-keychain` (требует пароль/разблокировки);
- **chainbreaker** — Python-инструмент: разбирает `keychain-db` и расшифровывает записи при
  известном пароле;
- **`keychaindump`** — извлекает ключ из памяти разблокированной системы;
- **sqlite3** — для просмотра незашифрованных полей.

Пример `chainbreaker`:

```
$ python3 chainbreaker.py --dump-all login.keychain-db password
[genp] svce=SSH acct=admin pw=hunter2
[inet] srvr=mail.corp.com acct=alice pw=Secret123
```

## Шаг 4: что искать при расследовании

- **Учётные данные корпоративных сервисов** (VPN, почта, внутренние порталы) — путь к
  латеральному движению;
- **Wi-Fi-пароли** — доступ к сети;
- **SSH-ключи** (в `keys`) — доступ к серверам;
- **токены и API-ключи** приложений — доступ к SaaS;
- **сертификаты** — подпись/клиентская аутентификация.

Обрати внимание: **наличие записи** само по себе — уже находка, даже если пароль не
расшифрован.

## Шаг 5: связка с другими артефактами

Keychain не существует в вакууме. Сопоставляй:

- **TCC.db** — давал ли браузер/приложение доступ, который позволил сохранить пароль;
- **unified logs** — когда создавалась/читалась запись;
- **браузерные базы** (Chrome/Safari) — там могут быть свои хранилища паролей;
- **bash/zsh history** — команды `security add-generic-password` и т.п.

## Мини-практика: перечислить сохранённые сервисы

```
$ strings login.keychain-db | grep -Ei 'genp|inet'
CREATE TABLE genp (acct TEXT, svce TEXT, data BLOB)
CREATE TABLE inet (srvr TEXT, acct TEXT, data BLOB)
$ sqlite3 login.keychain-db 'SELECT svce, acct FROM genp;'
SSH|admin
Wi-Fi|corp-net
```

Мы получили список сервисов и логинов без расшифровки. Дальше, при наличии пароля —
`chainbreaker` для самих паролей.

## Частые ошибки и подводные камни

- **Ждать пароли без пароля.** `data` зашифрован; без ключа не прочитать.
- **Путать login и System keychain.** Системная связка — отдельный файл.
- **Игнорировать iCloud-связку.** Часть записей синхронизирована и лежит отдельно.
- **Не заметить, что база — SQLite.** Многие ищут «бинарный формат» и удивляются.
- **Забыть про память.** Разблокированная связка оставляет ключ в RAM.

## Что мы теперь знаем

- Keychain — SQLite-база (`login.keychain-db`) с таблицами genp/inet/cert/keys.
- Поле `data` зашифровано ключом, производным от пароля пользователя.
- Без пароля видно сервисы, логины и метки времени.
- Инструменты: `security`, chainbreaker, keychaindump, sqlite3.
- Наличие записи — уже находка для расследования.

## Что фиксировать в отчёте

| Что | Зачем |
|-----|-------|
| Список сервисов и логинов | какие учётки были |
| Тип записей (genp/inet/cert) | категории секретов |
| Расшифрованные пароли (если есть пароль) | доступ |
| Метки времени записей | хронология |

## Расширенный пример: восстановление доступа к связке

Разберём полный сценарий разбора Keychain при расследовании. У нас есть образ Mac и
известен пароль пользователя (например, он же использовался для разблокировки образа).

1. **Извлекаем базу.** Копируем `~/Library/Keychains/login.keychain-db` из образа.
2. **Смотрим незашифрованные поля.** Через `sqlite3` получаем список сервисов и логинов.
3. **Расшифровываем.** `chainbreaker` с паролем пользователя выводит записи в открытом виде.
4. **Проверяем приоритеты.** Сначала — корпоративные сервисы (VPN, почта, внутренние
   порталы), затем Wi-Fi и SSH.
5. **Сопоставляем.** Найденные учётки проверяем по другим артефактам — не устарели ли они.

Типичная проблема: пароль пользователя неизвестен. Тогда остаются два пути — **память**
(если система была разблокирована) и **социальная инженерия/правовые механизмы** (запрос
пароля у владельца по процедуре). Технически «взломать» саму связку без пароля нельзя —
это by design.

Если известен только **частичный** доступ (например, пароль от входа, но связка
синхронизирована с iCloud и защищена иначе), может понадобиться iCloud-ключ.

## iCloud Keychain и синхронизация

Современный Keychain может синхронизироваться через **iCloud Keychain**. Это меняет картину:

- часть записей хранится **в облаке**, а локально может отсутствовать;
- синхронизация защищена сквозным шифрованием, ключ привязан к **устройству/паролю**;
- в `~/Library/Keychains/` появляется каталог с **UUID** — это iCloud-связка;
- при расследовании важно понять, была ли синхронизация включена.

Если iCloud Keychain активен, локальный образ может быть **неполным**: часть паролей
лежит в облаке и недоступна без учётной записи Apple. Это нужно отразить в отчёте — «на
локальном устройстве найдено N записей; остальное, возможно, синхронизировано».

Полезно также проверить **iCloud-бэкапы**: они могут содержать связку в другом формате и
иногда извлекаются иначе, чем локальная база.

## Чек-лист разбора Keychain

1. Найди все файлы связки (`login.keychain-db`, System, iCloud-UUID).
2. Определи **формат** (SQLite) и перечисли таблицы.
3. Выпиши **незашифрованные поля** (acct, svce, srvr) — это уже находки.
4. Проверь, есть ли **пароль** или доступ к памяти.
5. Расшифруй записи (chainbreaker) и приоритизируй корпоративные сервисы.
6. Сопоставь найденное с другими артефактами (TCC, логи, браузеры).

## Юридические и практические оговорки

Связка ключей содержит **личные** секреты пользователя, поэтому при работе с ней важны
процедуры: фиксируй, откуда взят файл, кто имел к нему доступ, и не расшифровывай лишнее.
В корпоративном расследовании обычно достаточно доказать **наличие** учётной записи; сами
пароли извлекают только при необходимости и по политике. Помни, что «не удалось
расшифровать» — это не «секретов нет»: база может содержать записи, которые ты не открыл.

## Что писать в отчёте

В отчёте по Keychain укажи: **файл связки** и его источник, **список сервисов и логинов**
(даже без паролей), **какие записи удалось расшифровать**, и **метод** (пароль/память).
Если пароля не было, честно отметь, что `data` остались зашифрованными. В корпоративном
контексте вывод обычно звучит так: «на устройстве сохранены учётные данные для сервисов X,
Y, Z; часть расшифрована, часть защищена паролем пользователя».

## Частые вопросы по Keychain

**Можно ли расшифровать `data` без пароля пользователя?** Нет. Ключ выводится из пароля
через PBKDF2, и без него записи остаются закрытыми — это не «слабое» шифрование, а
by-design. Единственные обходные пути — живая память разблокированной системы
(`keychaindump`) или известный пароль.

**Чем `login.keychain-db` отличается от `login.keychain`?** Старый формат
`login.keychain` — проприетарный блоб; современный `keychain-db` — SQLite. На новых
macOS вы почти всегда встретите второй.

**Какие таблицы, кроме genp/inet/cert/keys, бывают?** Служебные: `agrp` (access groups —
какие приложения имеют доступ), `tversion` (версия схемы), `sqlite_sequence`. Они полезны,
чтобы понять, какие приложения могли читать записи.

**Что делать, если базы нет, а пароли были?** Проверьте iCloud-связку (каталог с UUID) и
браузерные хранилища — Chrome/Edge держат свои пароли в `Login Data` (SQLite), Safari — в
Keychain.

**Даёт ли что-то `security` на живой машине?** Да: `security dump-keychain -d` при
разблокированной связке и `security find-generic-password -s <svce> -w` возвращают пароль
в открытом виде — если запускать от имени владельца и с разрешением на доступ.

## Куда дальше

Мы разобрали Keychain. Дальше возьмём **TCC.db** — базу согласий приватности: она покажет,
какие приложения получили доступ к камере, микрофону и диску. А пока главное запомни:
**даже без пароля Keychain выдаёт, какие учётки на машине были**.

## Где пригодится

- **CTF Forensics:** образы macOS с сохранёнными паролями.
- **DFIR:** сбор учётных данных для латерального движения.
- **macOS forensics:** доказательство наличия корпоративных учёток.
- **Пентест:** понимание, что даёт доступ к Mac.
