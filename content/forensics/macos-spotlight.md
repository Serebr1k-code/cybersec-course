## Вопрос, с которого всё начинается

Файл удалён, но macOS его «помнит». Индекс **Spotlight** хранит метаданные обо всём,
что когда-либо было в системе: имена, пути, размеры, даты. Это архив теней удалённых
файлов. Разберёмся, как его читать.

## Наш пример: удалённый документ

## Шаг 1: где индекс

```
$ ls ~/Library/Application\ Support/com.apple.spotlight/
index.V2  store.db  ...
```

`store.db` — это SQLite-база индекса. Откроем и посмотрим таблицы:

```
$ sqlite3 store.db '.tables'
...
```

## Шаг 2: метаданные через mdls

Проще всего — встроенный инструмент `mdls`, он читает метаданные файла:

```
$ mdls -name kMDItemDisplayName -name kMDItemContentCreationDate /Users/user/Documents/report.pdf
kMDItemDisplayName = "report.pdf"
kMDItemContentCreationDate = 2026-01-14 03:31:02 +0000
```

`kMDItem*` — это атрибуты Spotlight. Их десятки: автор, где создан, какой программой,
сколько раз открывали.

## Шаг 3: поиск через mdfind

Найти файлы по метаданным:

```
$ mdfind -onlyin /Users/user 'kMDItemWhereFroms == "*203.0.113.5*"'
/Users/user/Downloads/payload.dmg
```

`kMDItemWhereFroms` — откуда файл скачан. Так можно найти всё, что пришло с
подозрительного адреса, даже если оно переименовано.

## Шаг 4: удалённые файлы в индексе

Если файл удалили, но индекс не перестроили, запись может остаться:

```
$ sqlite3 store.db 'SELECT * FROM ... LIMIT 5;'
```

Структура `store.db` недокументирована, поэтому на практике используют утилиты вроде
`mac_apt` или `Spotlight`-парсеры. Они извлекают имена, пути и даты удалённых файлов.

## Шаг 5: что ещё в индексе

Spotlight индексирует не только документы, но и:

- почту (`kMDItemContentType = com.apple.mail.emlx`);
- историю браузера (заголовки страниц);
- переписку;
- музыку/фото с метаданными.

Поэтому `mdfind` — быстрый способ найти «всё про X» по всей системе.

## Что мы теперь знаем

- Spotlight хранит индекс метаданных в `store.db` и `index.V2`.
- `mdls` показывает атрибуты одного файла.
- `mdfind` ищет по метаданным по всей системе.
- `kMDItemWhereFroms` = источник скачивания.
- Удалённые файлы могут остаться в индексе.

## Если не сработало

- Индекс отключён? Проверь `mdutil -s /`.
- Индекс перестроен? Используй бэкап Time Machine.
- Нужны детали? Парси `store.db` утилитами mac_apt.

## Что такое индекс Spotlight и где он лежит

Spotlight — это системный поиск macOS, который заранее **индексирует содержимое и
метаданные** файлов. Индекс хранится в каталоге `.Spotlight-V100` в корне тома:

```
$ ls -la /System/Volumes/Data/.Spotlight-V100/Store-V2/
-rw-------  store.db          # база метаданных
-rw-------  live.0.index      # живой индекс
-rw-------  psid.db
```

Для форензики ценно, что индекс содержит **свойства файлов, которые уже удалены**: имя,
путь, размер, время создания, автора, иногда — фрагменты текста. То есть Spotlight — это
архив «того, что когда-то лежало на диске».

## Чтение метаданных через mdls

На живой системе (или примонтированном образе) свойства файла достаются командой `mdls`:

```
$ mdls -name kMDItemFSName -name kMDItemContentCreationDate -name kMDItemAuthors report.pdf
kMDItemFSName               = "report.pdf"
kMDItemContentCreationDate  = 2026-01-10 09:14:33 +0000
kMDItemAuthors              = ("Ivan Petrov")
```

Список атрибутов огромен: `kMDItemWhereFroms` (откуда скачан), `kMDItemLastUsedDate`,
`kMDItemKind`, `kMDItemPixelHeight` для картинок. Атрибут `kMDItemWhereFroms` — прямой
аналог метки «скачано из интернета» и часто содержит исходный URL.

## Поиск по индексу: mdfind

`mdfind` выполняет запросы к индексу, а не обход диска, поэтому работает и по удалённым
файлам, оставшимся в базе:

```
$ mdfind -onlyin ~/Documents 'kMDItemTextContent == "*password*"'
$ mdfind 'kMDItemWhereFroms == "*example.net*"'
```

Запрос по `kMDItemWhereFroms` находит все файлы, скачанные с конкретного домена — даже если
сами файлы удалены, но ещё не вычищены из индекса.

## Удалённые файлы в индексе

Ключевой сценарий: пользователь создал документ, потом удалил. На диске его нет, но в
`store.db` остались метаданные. Запрос по имени или автору вытащит запись:

```
$ mdfind 'kMDItemFSName == "salaries.xlsx"'
/Users/user/Documents/salaries.xlsx
$ ls -la /Users/user/Documents/salaries.xlsx
ls: ...: No such file or directory
```

Индекс знает о файле, файловой системы он уже нет. Дальше можно попытаться **карвить**
содержимое из нераспределённого пространства тома, используя имя и размер из индекса как
подсказку.

## Таблица: полезные атрибуты Spotlight

| Атрибут | Смысл | Ценность для DFIR |
|---|---|---|
| `kMDItemFSName` | имя файла | поиск по имени |
| `kMDItemContentCreationDate` | дата создания | таймлайн |
| `kMDItemLastUsedDate` | последний запуск | активность |
| `kMDItemWhereFroms` | источник загрузки | URL-происхождение |
| `kMDItemAuthors` | авторы | атрибуция документа |
| `kMDItemTextContent` | текст внутри | поиск по содержимому |
| `kMDItemDownloadedDate` | дата скачивания | связь с сетью |
| `kMDItemKind` | тип | фильтрация |

## Работа с индексом как с базой

`store.db` — это SQLite. Примонтировав образ, можно читать её напрямую:

```
$ sqlite3 /mnt/.Spotlight-V100/Store-V2/*/store.db '.tables'
$ sqlite3 .../store.db "SELECT * FROM ZATTRIBUTEVALUES LIMIT 5;"
```

Схема внутренняя и версионно-зависимая, поэтому надёжнее использовать `mdls`/`mdfind` на
примонтированном томе. Но прямой доступ к базе полезен, когда система не загружается.

## Ограничения

Во-первых, индекс **не мгновенный**: только что созданные/удалённые файлы могут быть не
проиндексированы. Во-вторых, он **чистится**: система удаляет записи об исчезнувших файлах
через некоторое время. В-третьих, содержимое индексируется только для поддерживаемых типов
(текст, офис, PDF), а бинарники — нет. В-четвёртых, на зашифрованных томах (FileVault)
индекс недоступен без ключа. И `kMDItemTextContent` может содержать лишь фрагмент, не весь
текст.

## Если сработало: восстанавливаем факт существования

Найдя запись об удалённом файле, зафиксируй: путь, размер, даты и источник (`WhereFroms`).
Этого достаточно, чтобы доказать, что файл **существовал** и **когда** — даже без его
содержимого. Сопоставь с историей браузера (откуда скачали) и с корзиной (если файл там).

## Восстановление содержимого удалённого файла

Запись в индексе говорит, что файл был. Следующий шаг — попытаться вернуть **содержимое**.
Порядок:

1. Определяем том и файловую систему (APFS/HFS+);
2. Ищем данные в нераспределённом пространстве (unallocated) по сигнатурам типа файла;
3. Используем имя и размер из индекса как якорь.

```
$ dd if=/dev/rdisk2 bs=1m skip=... count=... of=unalloc.img   # фрагмент unallocated
$ foremost -t xlsx,pdf,docx -i unalloc.img -o carved/
```

Карвинг по сигнатурам (`PK` для офисных форматов, `%PDF`) возвращает файлы, но без имён.
Сопоставляя найденный размер с размером из `kMDItemFSSize`, можно привязать вырезанный файл
к записи индекса.

## Версии файлов и локальные снимки APFS

Если включены локальные снимки Time Machine или APFS-снапшоты, удалённый файл может
существовать в **старой версии** тома:

```
$ tmutil listlocalsnapshots /
com.apple.TimeMachine.2026-01-13-120000.local
$ mount_apfs -s com.apple.TimeMachine.2026-01-13-120000.local /dev/disk3s1 /mnt/snap
```

В примонтированном снапшоте ищем файл по пути из индекса — часто он там цел и невредим. Это
самый надёжный способ восстановления, когда снапшоты есть.

## Индекс как источник таймлайна

Помимо отдельных файлов, индекс даёт **плотный таймлайн** событий: когда файл создан,
изменён, в последний раз открыт. Соединяя эти метки с другими артефактами, видно активность
пользователя по минутам:

```
$ mdfind -onlyin ~ 'kMDItemLastUsedDate >= $time.today(-1)' | while read f; do mdls -name kMDItemLastUsedDate "$f"; done | sort | uniq -c
```

Так обнаруживаются всплески активности — например, массовое открытие документов в ночь
инцидента.

## Связь с «Where Froms» и карантином

Атрибут `kMDItemWhereFroms` и метка `com.apple.quarantine` дополняют друг друга: первый
хранится в индексе (может пережить удаление файла), второй — в расширенных атрибутах самого
файла. Если файл удалён, но запись в индексе осталась, `WhereFroms` всё ещё покажет URL —
это единственный способ узнать источник для уже исчезнувшего файла.

## Ограничения и предостережения

Первое — **индекс не является полным архивом**: он хранит не все атрибуты и не весь текст.
Второе — записи **вычищаются** при переиндексации или когда система «замечает» удаление.
Третье — на APFS с FileVault индекс зашифрован вместе с томом. Четвёртое — `mdfind` на
примонтированном образе может не работать без загруженного `mds`, поэтому надёжнее читать
`store.db` напрямую или применять сторонние парсеры (`spotlight-parser`).

## Если сработало: доказываем существование и содержимое

Для отчёта разделяй два вывода: (1) файл **существовал** — доказывается записью в индексе с
путём, размером и датами; (2) файл **содержал X** — доказывается только восстановленным
содержимым (карвинг или снапшот). Не смешивай их: запись в индексе сама по себе не
показывает, что было внутри.

## Итог

Spotlight — это «память» системы о файлах, которые могли уже исчезнуть. Индекс сохраняет
имена, пути, даты, авторов и источники загрузки, позволяя доказать существование файла даже
после удаления. Для содержимого нужны снапшоты или карвинг. Всегда разделяй доказательство
существования и доказательство содержимого — это два разных вывода.

## Практический пример: связываем индекс с сетью

Расследуем подозрение на кражу документа. Запрос `mdfind 'kMDItemWhereFroms == "*files.example.net*"'`
находит файл, скачанный с внешнего хранилища, а `kMDItemDownloadedDate` даёт точное время
загрузки. Сопоставляем это время с историей браузера и сетевыми логами: если визит на
`files.example.net` и создание файла совпадают, цепочка «зашёл → скачал → сохранил»
подтверждена тремя независимыми источниками. Если сам файл уже удалён, запись в индексе всё
равно фиксирует факт и время его существования, а восстановить содержимое помогают снапшоты
APFS или карвинг нераспределённого пространства тома.


## Замечание о целостности

Работай только с копией образа: любое обращение к живому тому меняет его состояние.

## Сравнение с Windows Search и другими индексами

Аналогичный артефакт есть и на других платформах: `Windows.edb` (Windows Search) хранит
индекс файлов и свойства, а на Linux индексы создают `tracker` или `recoll`. Логика та же:
индекс переживает удаление файлов и хранит метаданные дольше, чем файловая система. Освоив
приём на Spotlight, ты легко переносишь его на другие ОС — меняется формат базы, но не идея.
