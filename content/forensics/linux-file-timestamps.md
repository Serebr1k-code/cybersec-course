## Вопрос, с которого всё начинается

Ты смотришь на файл и хочешь понять, когда его создали, изменили и читали. `ls -l`
показывает одну дату. Но на самом деле у файла их несколько, и они значат **разное**.
Путаница в метках — самая частая ошибка в таймлайне.

## Наш пример: подозрительный файл

Возьмём `/opt/.hidden/x`.

## Шаг 1: полный набор меток

```
$ stat /opt/.hidden/x
  File: /opt/.hidden/x
  Size: 245760      Blocks: 480        IO Block: 4096   regular file
Device: 253,0       Inode: 123456      Links: 1
Access: (0755/-rwxr-xr-x)  Uid: (0/root)   Gid: (0/root)
Access: 2026-01-14 03:33:10.123456789 +0000
Modify: 2026-01-14 03:31:02.987654321 +0000
Change: 2026-01-14 03:33:12.000000000 +0000
 Birth: 2026-01-14 03:31:02.987654321 +0000
```

## Шаг 2: что каждая метка значит

- **Access (atime)** — последнее **чтение** файла.
- **Modify (mtime)** — последнее **изменение содержимого**.
- **Change (ctime)** — последнее изменение **метаданных** (права, владелец, ссылки).
  Меняется и при изменении содержимого тоже.
- **Birth** — время создания inode (не на всех ФС).

Ключевое: `ctime` нельзя подделать, не изменив его сам. Если злоумышленник меняет
`mtime` через `touch -d`, `ctime` всё равно обновится на «сейчас».

## Шаг 3: ловим подделку mtime

Предположим, атакующий выставил mtime в прошлое:

```
$ touch -d "2020-01-01 00:00:00" /opt/.hidden/x
$ stat /opt/.hidden/x | grep -E 'Modify|Change'
Modify: 2020-01-01 00:00:00.000000000 +0000
Change: 2026-01-14 03:35:00.000000000 +0000
```

`Modify` в 2020, а `Change` — сегодня. Это противоречие и есть улика: содержимое
якобы старое, а метаданные менялись только что.

## Шаг 4: atime может врать

Многие системы монтируют ФС с `noatime`/`relatime`, чтобы не писать на диск при каждом
чтении. Тогда `atime` не обновляется вовсе:

```
$ mount | grep ' / '
/dev/sda1 on / type ext4 (rw,relatime)
```

`relatime` означает, что atime обновляется не всегда. Не делай выводов «файл не
читали» только по atime.

## Шаг 5: строим таймлайн

Правильный порядок: используй **все** метки и сопоставляй с другими источниками
(журналы, MFT/`ext4`-журнал, bash_history).

```
$ find /opt -newermt "2026-01-14 03:00" ! -newermt "2026-01-14 04:00" -exec stat -c '%y %n' {} \;
```

Так находишь всё, что трогали в окне атаки.

## Что мы теперь знаем

- atime = чтение, mtime = содержимое, ctime = метаданные, birth = создание.
- `ctime` обновляется всегда — по нему ловят подделку mtime.
- `noatime`/`relatime` делают atime ненадёжным.
- Расхождение mtime/ctime — прямой признак timestomping.
- Таймлайн строят по всем меткам и сопоставляют с другими источниками.

## Если не сработало

- ФС без birth? Используй журнал (ext4 journal) или `debugfs`.
- Метки одинаковы? Возможно, файл только что скопирован (cp сбрасывает метки).
- Нужен порядок? Учти наносекунды — они различимы.

## Четыре метки в деталях

У файла на ext4/xfs их несколько, и каждая отвечает на свой вопрос:

| Метка | Полное имя | Что меняет | Можно ли подделать |
|-------|-----------|------------|--------------------|
| atime | access time | чтение файла | да (`touch -a`) |
| mtime | modify time | изменение **содержимого** | да (`touch -m`) |
| ctime | change time | изменение **метаданных** (права, владелец, ссылки, размер) | **нет** — всегда «сейчас» |
| btime/birth | creation time | создание inode | зависит от ФС |

Ключевой форензик-факт: **`ctime` нельзя выставить в прошлое**, не изменив его сам.
Любое `touch -m -d "2020-01-01"` изменит `mtime` на 2020, но `ctime` станет «сейчас».
Именно это противоречие выдаёт подделку.

Важно: `ctime` меняется и при изменении **содержимого** (потому что меняется размер/
inode), и при `chmod`/`chown`/`mv` — всё, что трогает метаданные.

## Практика: найти подделку mtime

Смотрим файл:

```
$ stat /opt/.hidden/x | grep -E 'Modify|Change'
Modify: 2020-01-01 00:00:00.000000000 +0000
Change: 2026-01-14 03:35:00.000000000 +0000
```

`Modify` в 2020, а `Change` — сегодня. Содержимое якобы «старое», но метаданные менялись
только что. Это **timestomping** — приём анти-форензики (T1070.006). Найти такое по
всему дереву:

```
$ find / -newer /tmp/ref 2>/dev/null -printf '%TY-%Tm-%Td %p\n' | sort
```

где `/tmp/ref` — файл с «эталонной» меткой. Или окном:

```
$ find /opt -newermt "2026-01-14 03:00" ! -newermt "2026-01-14 04:00" \
    -exec stat -c '%y %z %n' {} \;
```

`%y` — mtime, `%z` — ctime. Если `%z` заметно новее `%y` — вероятная подделка.

## atime и монтирование: почему «не читали» — плохой вывод

`atime` обновляется при каждом чтении, поэтому его отключают ради производительности:

- `noatime` — atime **не** обновляется вообще;
- `relatime` — обновляется только если старее mtime или прошло больше суток;
- `strictatime` — обновляется всегда (редко).

```
$ mount | grep ' / '
/dev/sda1 on / type ext4 (rw,relatime)
```

При `relatime` отсутствие обновления `atime` **ничего не значит**. Вывод «файл не читали»
строить на atime нельзя. Обратное тоже: `atime` может быть «свежим» из-за бэкапа или
индексатора, а не человека.

## btime и файловые системы

`Birth` — время создания inode. Есть не везде:

- **ext4** — да, если включён `enable_extra_isize` и ФС создана свежим `mke2fs`;
- **XFS** — да (`crtime`);
- **NTFS** — да (MFT `$STANDARD_INFORMATION`);
- **FAT** — только отдельные поля (с точностью 2 секунды).

```
$ stat /opt/.hidden/x | grep Birth
 Birth: 2026-01-14 03:31:02.987654321 +0000
```

Если `Birth` новее `mtime` — файл **пересоздали** (атакующий часто удаляет оригинал и
создаёт новый, надеясь запутать). Для NTFS помни: `$STANDARD_INFORMATION` можно
подделать, а `$FILE_NAME` — сложнее; расхождение между ними — улика.

## Временные метки в других артефактах

Метки есть не только у файлов:

- **MFT (NTFS)** — по одной записи на файл, с MACB-временами;
- **journal ext4** — журнал транзакций ФС, хранит операции с временем;
- **bash_history** — не имеет времени, но `HISTTIMEFORMAT` может его писать;
- **systemd journal** — события с точным временем;
- **web/DB-логи** — обращения с timestamp.

Сопоставление файловых меток с журналами (что файл изменили, и что в этот момент была
сессия входа) подтверждает авторство действия.

## Ограничения

- **`ctime` не панацея** — его можно подделать из ядра/руткита или изменением системных
  часов.
- **Часовой пояс** — `stat` печатает в локальной TZ; сравнивай в UTC (`TZ=UTC stat`).
- **Точность** — разные ФС дают разную точность (FAT — 2 секунды, NTFS — 100 нс).
- **Сетевые ФС** — NFS/SMB могут не сохранять часть меток или отдавать время сервера.
- **`relatime`/`noatime`** — atime ненадёжен по определению.

## Практический чеклист

1. `stat` файла — все четыре метки (`TZ=UTC`).
2. Сравнить `mtime` и `ctime` — расхождение = подделка.
3. `find ... -newermt` — что трогали в окне атаки.
4. Проверить `mount` — `relatime`/`noatime` обесценивают atime.
5. Для NTFS — сверить `$STANDARD_INFORMATION` и `$FILE_NAME`.
6. Сопоставить метки с журналами входа/логами — подтвердить авторство.
7. Помнить: `birth` новее `mtime` = файл пересоздан.

## Сценарий: timestomping в малвари

Разберём реальный шаблон. Атакующий кладёт нагрузку в `/usr/lib/.libs/` и выставляет ей
«старую» метку, чтобы файл сливался с системными библиотеками:

```
$ stat /usr/lib/.libs/libx.so.1 | grep -E 'Modify|Change|Birth'
Modify: 2024-05-01 10:00:00.000000000 +0000
Change: 2026-01-14 03:35:12.000000000 +0000
 Birth: 2026-01-14 03:31:02.000000000 +0000
```

Читается однозначно: содержимое якобы «2024», но `Change` и `Birth` — сегодня. Подделка
`mtime` не тронула `ctime` и `birth`, и они выдают файл. Вывод: **всегда смотри `ctime` и
`birth`, а не только `mtime`**.

## Массовый поиск аномалий по меткам

Ручной `stat` не масштабируется. Ищем «ctime сильно новее mtime» по дереву:

```
$ find / -xdev -type f -printf '%C@ %T@ %p\n' 2>/dev/null | \
    awk '$1-$2 > 86400 {print $3}' | head
```

`%C@` — ctime в epoch, `%T@` — mtime. Разница больше суток — кандидат на подделку. Ещё
полезно искать файлы, созданные в окне атаки, но лежащие «в системных» каталогах:

```
$ find /usr /lib /etc -newermt "2026-01-14 03:00" ! -newermt "2026-01-14 04:00" -type f
```

## Связь с MFT и журналом

На NTFS метки живут в MFT: `$STANDARD_INFORMATION` (легко подделать) и `$FILE_NAME`
(обновляется ядром, подделать сложнее). Расхождение между ними — классический признак
timestomping. На ext4 аналогичную роль играет журнал ФС: операции записи сохраняются с
временем, и по нему можно увидеть, что файл писали позже, чем говорит его `mtime`.

## Ограничения

- **Подделка `ctime` из ядра** — руткит может изменить `ctime`; тогда полагайся на
  независимые источники (журнал ФС, бэкапы).
- **Смена системных часов** — если часы «открутили», все метки согласованно сдвинуты;
  сравнивай с внешним временем (NTP-логи, серверные логи).
- **ФС без `birth`** — на некоторых не будет времени создания; не делай выводов.
- **Точность и часовой пояс** — сверяй в UTC.
- **NFS/SMB** — время может быть временем сервера, а не клиента.

## Практический чеклист

1. `TZ=UTC stat` — все метки файла.
2. Искать `ctime` ≫ `mtime` — кандидаты на timestomping.
3. Искать `birth` новее `mtime` — файл пересоздан.
4. `find` по окну атаки в системных каталогах.
5. Для NTFS — сверить `$STANDARD_INFORMATION` и `$FILE_NAME`.
6. Сопоставить с журналом ФС и логами входа.
7. Помнить: подделать `ctime` можно только из ядра — иначе он выдаёт.
