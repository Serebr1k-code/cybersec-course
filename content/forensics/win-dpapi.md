## Вопрос, с которого всё начинается

Ты получил образ диска с рабочей станции. В профиле пользователя `C:\Users\jdoe` лежат
файлы Chrome, папка `AppData\Roaming\Microsoft\Protect`, и хочется достать **пароль от
корпоративной Wi-Fi-сети** и сохранённый логин. Пароль нигде не записан открытым текстом —
он **зашифрован** механизмом Windows под названием **DPAPI**.

Как расшифровать то, что Windows специально прятала? Разберём сквозной пример: добудем
секрет из профиля пользователя, зная только его пароль.

## Что такое DPAPI и зачем он нужен

**Data Protection API (DPAPI)** — это встроенный в Windows способ зашифровать данные «под
пользователя» или «под машину», не заботясь о ключах. Приложение вызывает функцию
`CryptProtectData`, передаёт ей секрет, и получает шифротекст. Расшифровать его обратно
(`CryptUnprotectData`) может только тот же пользователь на той же машине.

Ключевая идея: приложение **не хранит ключ шифрования**. Ключ выводится из секретов
операционной системы. Значит, чтобы расшифровать секрет, аналитику нужно восстановить
цепочку ключей — и вот из чего она состоит:

- **Мастер-ключ (Master Key)** — случайный 64-байтовый ключ, которым зашифрован секрет.
  Хранится в профиле: `%APPDATA%\Microsoft\Protect\<SID>\`.
- **Пароль пользователя** — из него выводится ключ, которым защищён сам мастер-ключ.
- **SID пользователя** — соль для вывода ключа из пароля.
- **CREDHIST** — если пароль меняли, старые мастер-ключи защищены старыми паролями, и
  их список хранится в файле `CREDHIST` в той же папке `Protect`.

То есть расшифровка — это не «взлом шифра», а **восстановление цепочки ключей**:
пароль → ключ → мастер-ключ → секрет.

## Наш пример: профиль пользователя jdoe

Допустим, у нас есть копия каталогов:

```
C:\Users\jdoe\AppData\Roaming\Microsoft\Protect\S-1-5-21-...-1001\
C:\Users\jdoe\AppData\Roaming\Microsoft\Protect\CREDHIST
```

и мы знаем пароль пользователя `Summer2025!`. Посмотрим, что в папке `Protect`:

```
$ ls -la Protect/S-1-5-21-...-1001/
-r--r--r--  dpapi_masterkey  5560fa6e-....  (мастер-ключи, GUID-имена)
-r--r--r--  CREDHIST
-r--r--r--  Preferred
```

Файлы с именами-идентификаторами GUID — это и есть мастер-ключи. `Preferred` указывает,
какой ключ использовать по умолчанию, а `CREDHIST` — история старых паролей.

### Шаг 1: прочитать структуру мастер-ключа

Сначала посмотрим, что внутри. Файл начинается с заголовка, где есть GUID и версия:

```
$ xxd -l 64 5560fa6e-...-...
00000000: 0300 0000 6e9a aaaa ...  ....
```

Здесь важно поле с **версией** и **GUID** — их сверяют с ветвью реестра
`HKLM\SOFTWARE\Microsoft\Cryptography\Protect\Providers`, чтобы понять алгоритм.
Вручную это кропотливо, поэтому используем готовый инструмент.

### Шаг 2: расшифровать мастер-ключи

Инструмент **impacket** (модуль `dpapi`) и **mimikatz** умеют всю цепочку сразу.
Возьмём impacket, передав SID, пароль и каталог `Protect`:

```
$ dpapi.py masterkey -file Protect/S-1-5-21-...-1001/5560fa6e-...-... \
      -sid S-1-5-21-...-1001 -password 'Summer2025!'
Impacket v0.12 - Copyright ...
[MASTERKEYFILE]
Version     : 2
Guid        : 5560fa6e-...
Flags       : 0
MasterKey   : 7f3b9c1e88aa...  (получен!)
```

Мы получили **открытый мастер-ключ**. Именно им расшифровываются секреты, которые он
защищает.

### Шаг 3: расшифровать конкретный секрет

Секрет хранится в виде файла с **blob** — структурой из заголовка, соли и шифротекста.
Формат называется DPAPI blob. Зная мастер-ключ, расшифруем:

```
$ dpapi.py unprotect -file secret.blob -masterkey 7f3b9c1e88aa...
Decrypted: {"user":"jdoe","password":"nto{dp4p1_m4st3rk3y_ch41n}"}
```

Вот и флаг — пароль, который Windows прятал за двумя слоями шифрования.

## CREDHIST: когда пароль меняли

Если пользователь менял пароль, часть мастер-ключей защищена **старыми** паролями.
`CREDHIST` хранит цепочку: `SID` → список «старых» ключей-обёрток. Разбирать её вручную
тяжело; `mimikatz` делает это командой `dpapi::credhist /file:CREDHIST`. Смысл для
аналитика: **старые мастер-ключи всё ещё расшифровываются старыми паролями**, поэтому
даже если известен только прежний пароль, часть секретов достаётся.

Практический вывод: собирай **всю** папку `Protect` вместе с `CREDHIST` и `Preferred` —
без них цепочка рвётся.

## Если пароль неизвестен

Цепочка «пароль → мастер-ключ» защищена не только паролем. У пользователя есть ещё
**SECURITY-хеш** (в hive `SECURITY`), и по нему тоже можно вывести ключ. Второй путь —
извлечь мастер-ключи прямо из **памяти** процесса `lsass.exe` (mimikatz
`sekurlsa::dpapi`), пока система работала. Третий — расшифровать мастер-ключ через
**доменный** секрет DPAPI (для доменных учёток). Все три пути сходятся к одному:
сначала ключ, потом секрет.

## DPAPI в реальных приложениях

Разберём, где именно встречаются DPAPI-секреты, которые чаще всего ищут в задачах.

**Chrome / Edge (Chromium).** Логины и пароли лежат в SQLite-базе
`%LOCALAPPDATA%\Google\Chrome\User Data\Default\Login Data`, а поле `password_value` —
это **DPAPI blob**. Ключ шифрования извлекается из значения `encrypted_key` в таблице
`meta` — это base64 от DPAPI-защищённого ключа AES. То есть Chromium использует
**двухуровневую** схему: DPAPI защищает AES-ключ, AES шифрует пароли.

**Wi-Fi-профили.** Пароли сохранённых сетей лежат в
`C:\ProgramData\Microsoft\Wlansvc\Profiles\Interfaces\<GUID>\<profile>.xml`, поле
`<keyMaterial>` — DPAPI blob (в base64). Команда `netsh wlan show profile name=X key=clear`
показывает пароль, но только на живой системе под нужным пользователем.

**RDP-креды.** Сохранённые пароли RDP лежат в `Credentials` внутри профиля как
DPAPI blob, привязанные к `TERMSRV/<host>`.

**Vault / Credential Manager.** Учётные данные «Веб-учётные данные» и «Windows-учётные
данные» хранятся в `%APPDATA%\Microsoft\Credentials` и `%LOCALAPPDATA%\Microsoft\Credentials`
как DPAPI blob-файлы с именами-GUID.

Вывод: почти все «сохранённые пароли» Windows — это DPAPI. Научившись разбирать цепочку
ключей, ты автоматически получаешь доступ ко всем этим источникам.

## Разбор DPAPI blob по шагам

Полезно понимать структуру blob, чтобы отлаживать расшифровку. Файл секрета — это:

| Поле | Смысл |
|------|-------|
| `dwVersion` | версия формата (обычно 1) |
| `guidProvider` | GUID провайдера (часто AES-256) |
| `dwMasterKeyVersion` | версия мастер-ключа |
| `guidMasterKey` | **GUID мастер-ключа**, которым зашифрован blob |
| `dwFlags` | флаги (например, «привязан к машине») |
| `szDescription` | текстовое описание секрета (иногда прямо подсказка!) |
| `pOptionalEntropy` | дополнительная энтропия, если приложение её передавало |
| `pSalt` / `pBlob` | соль и шифротекст |

Ключевой момент — `guidMasterKey`. Именно по нему мы находим нужный файл в каталоге
`Protect\<SID>\`. Если расшифровка «не сходится», чаще всего не тот мастер-ключ или не
учтена `pOptionalEntropy`.

## Частые ошибки и подводные камни

- **Не тот SID.** Мастер-ключи лежат в подкаталоге с SID **пользователя**. Если взять
  SID администратора, ключ не сойдётся.
- **Забытая энтропия.** Некоторые приложения (например, старые версии Chrome) передавали
  `pOptionalEntropy`. Без неё `unprotect` вернёт ошибку.
- **CREDHIST не собран.** Если пароль меняли, а CREDHIST потеряли, старые ключи не
  расшифровать — нужен либо старый пароль, либо путь через память/доменный секрет.
- **Машина vs пользователь.** Часть мастер-ключей привязана к **машине** (системный
  профиль `C:\Windows\System32\Microsoft\Protect\`). Их ключ выводится из пароля
  локального администратора, а не из пользовательского.
- **Русские имена пользователей.** Каталог `Protect` не зависит от имени — он по SID,
  поэтому локаль не мешает.

## Шпаргалка команд

```
# Мастер-ключ из пароля и SID
dpapi.py masterkey -file <MK> -sid <SID> -password <pass>

# С hive SECURITY вместо пароля
dpapi.py masterkey -file <MK> -sid <SID> -security SECURITY -system SYSTEM

# Расшифровать blob известным ключом
dpapi.py unprotect -file secret.blob -masterkey <hex>

# Из памяти живого хоста
mimikatz # sekurlsa::dpapi
mimikatz # dpapi::masterkey /in:<MK> /password:<pass>
mimikatz # dpapi::cred /in:<credfile>

# История паролей
mimikatz # dpapi::credhist /file:CREDHIST
```

## Как это выглядит в отчёте

В форензик-отчёте по DPAPI фиксируют: перечень расшифрованных секретов, к каким
учёткам/сервисам они относятся, какой мастер-ключ использован и из какого источника
получен. Это важно для оценки масштаба утечки: одно дело — один сохранённый пароль, и
совсем другое — мастер-ключ, под которым расшифровываются **все** секреты пользователя.

## Мини-практика: расшифровка Wi-Fi-пароля

Пройдём ещё один сквозной пример целиком, чтобы закрепить цепочку. На образе есть профиль
пользователя `jdoe` и файл Wi-Fi-профиля. Наша цель — пароль сети.

Сначала находим профиль. Профили Wi-Fi лежат в каталоге службы WLAN, а их имена привязаны
к интерфейсу:

```
$ find . -path '*Wlansvc*' -name '*.xml'
./Wlansvc/Profiles/Interfaces/{a1b2...}/CORP-WiFi.xml
```

Смотрим содержимое. Нас интересует поле `keyMaterial` — это DPAPI blob в base64:

```
$ grep -o '<keyMaterial>[^<]*' CORP-WiFi.xml
<keyMaterial>AQAAANCMnd8BFdERjHoAwE/Cl+sBAAAA...
```

Это base64. Декодируем в бинарный blob:

```
$ echo 'AQAAANCMnd8BFdERjHoAwE/Cl+sBAAAA...' | base64 -d > wifi.blob
$ xxd -l 32 wifi.blob
00000000: 0100 0000 d08c 9ddf 0100 0000 0000 0000  ................
```

Первое поле `01000000` — версия. Дальше идёт `guidProvider`, затем — самое важное —
`guidMasterKey`. Извлекаем его и находим соответствующий файл в `Protect\<SID>\`:

```
$ strings wifi.blob | grep -iE '^[0-9a-f-]{36}$'
5560fa6e-2b1c-4d3a-9f11-7c8e2a4b0d19
$ ls Protect/S-1-5-21-...-1001/ | grep 5560fa6e
5560fa6e-2b1c-4d3a-9f11-7c8e2a4b0d19
```

Теперь восстанавливаем мастер-ключ по паролю пользователя и расшифровываем blob:

```
$ dpapi.py masterkey -file Protect/S-1-5-21-...-1001/5560fa6e-... \
      -sid S-1-5-21-...-1001 -password 'Summer2025!'
MasterKey : 7f3b9c1e88aa...
$ dpapi.py unprotect -file wifi.blob -masterkey 7f3b9c1e88aa...
Decrypted : CORP-WiFi:Str0ngW1Fi!
```

Пароль сети получен. Вся цепочка заняла четыре шага: найти blob → извлечь GUID →
восстановить мастер-ключ → расшифровать. Если бы пароль пользователя был неизвестен, мы
взяли бы `SECURITY`+`SYSTEM` и вывели мастер-ключ оттуда, либо дампнули память `lsass`.

Главный вывод практики: **DPAPI почти всегда сводится к одной и той же последовательности
шагов**, и однажды отработанная цепочка переносится на любой источник — Chrome, Wi-Fi, RDP
или Credential Manager.

## Что мы теперь знаем

- DPAPI — это **цепочка ключей**, а не один шифр: пароль → мастер-ключ → секрет.
- Мастер-ключи лежат в `%APPDATA%\Microsoft\Protect\<SID>\`, а `CREDHIST` хранит старые
  пароли для старых ключей.
- Зная пароль и SID, impacket `dpapi.py masterkey` восстанавливает ключ, а `unprotect`
  расшифровывает blob.
- Собирать нужно **весь** каталог `Protect` (мастер-ключи + CREDHIST + Preferred).
- Альтернативные источники ключа: hive `SECURITY` и память `lsass.exe`.

## Куда дальше

Мы научились вытаскивать секреты **пользователя**. Дальше возьмём hive `SECURITY` и
разберём **LSA-секреты** — пароли сервисных учёток и кэш доменных логинов. А пока главное
запомни: **DPAPI — это цепочка ключей, и пароль пользователя — лишь первое звено**.

## Где пригодится

- **CTF Forensics:** задачи с профилем пользователя и зашифрованными секретами.
- **DFIR:** восстановление утёкших паролей после компрометации.
- **Пентест Windows:** расшифровка сохранённых кредов с хоста.
- **Работа:** форензика конечных точек, реагирование на инциденты.
