## Вопрос, с которого всё начинается

Вам дали образ NTFS-диска. Внутри — обычные файлы: документы, картинки, ничего примечательного. Но подозрение есть: на таких дисках злоумышленники прячут данные так, что в обычном проводнике их **вообще не видно**. Как найти то, чего «нет»?

## Наш пример: образ с «лишним» потоком

Смотрим список файлов утилитой `fls` из The Sleuth Kit — она показывает содержимое ФС по записям (inode). Обратите внимание на флаг `-r` (рекурсивно):

```bash
$ fls -r -o 2048 disk.img | grep ':'
r/r 64-128-1: notes.txt
r/r 64-128-3: notes.txt:hidden.txt
r/r 70-128-2: photo.jpg:Zone.Identifier
```

Странно: `notes.txt` есть, но рядом появилась запись `notes.txt:hidden.txt` — как будто у одного файла два имени. Двоеточие здесь не опечатка, а разделитель. Мы наткнулись на **Alternate Data Stream** (ADS, альтернативный поток данных).

## Шаг 1: что такое ADS

В NTFS любой файл — это набор **атрибутов** в записи MFT (Master File Table). Обычные данные лежат в атрибуте `$DATA`. У стандартного файла есть один такой атрибут — **без имени**. ADS — это ещё один атрибут `$DATA`, но **с именем**. Отсюда запись `file:stream`.

Что из этого следует:

- У одного файла может быть много потоков, каждый — со своим размером и содержимым.
- В обычном `dir` ADS не виден. В проводнике Windows 7+ размер ADS может «прилипнуть» к размеру папки, но сам поток не отображается.
- Поток бывает **resident** (мелкий, лежит прямо в MFT) или non-resident (в кластерах).
- ADS существует **только на NTFS**. При копировании на FAT/exFAT он теряется или вызывает ошибку.

## Шаг 2: достаём спрятанное

Запись в `fls` имеет формат `inode-type-id`. Чтобы прочитать **конкретный поток**, а не основной файл, нужно указать полный inode — `64-128-3` (а не `64-128-1`):

```bash
$ icat -o 2048 disk.img 64-128-3 > hidden.bin
$ file hidden.bin
hidden.bin: PE32 executable (GUI) Intel 80386
```

Поток `hidden.txt` оказался **исполняемым файлом PE** — то есть в безобидном `notes.txt` спрятана программа. Это классический приём малвари: payload живёт в потоке, а «носитель» выглядит безобидно.

Второй поток, `photo.jpg:Zone.Identifier`, читается так же:

```bash
$ icat -o 2048 disk.img 70-128-2
[ZoneTransfer]
ZoneId=3
ReferrerUrl=https://evil.example/payload
```

## Шаг 3: Mark-of-the-Web — тоже ADS

Поток `Zone.Identifier` — это не малварь, а **Mark-of-the-Web** (MOTW): метка, которую Windows ставит на файл, скачанный из интернета. Содержимое:

```
[ZoneTransfer]
ZoneId=3
ReferrerUrl=https://evil.example/payload.exe
```

`ZoneId=3` — интернет, `2` — доверенная зона, `4` — restricted. Наличие MOTW — сильный признак скачивания из сети. Удаление этого потока (`Remove-Item -Stream Zone.Identifier`) — распространённый шаг обхода SmartScreen; поэтому отсутствие MOTW у файла, который «якобы скачали», само по себе подозрительно.

## Шаг 4: как искать ADS в масштабе

На большом образе нельзя открывать файлы по одному. Ищем все потоки сразу и фильтруем подозрительные — с исполняемыми расширениями внутри:

```bash
$ fls -r -o 2048 disk.img | grep ':' > streams.txt
$ wc -l streams.txt
$ grep -Ei ':(.*\.(exe|dll|ps1|bat|vbs|scr))' streams.txt
r/r 64-128-3: notes.txt:hidden.txt
```

Затем каждый поток извлекаем по inode и прогоняем `file`/`strings`/YARA. `istat` подскажет, сколько потоков у файла:

```bash
$ istat -o 2048 disk.img 64
Attribute: Name: N/A   Type: Data   Size: 128
Attribute: Name: hidden.txt Type: Data Size: 14336
```

Две строки `Type: Data` — два потока. Это самый быстрый способ убедиться в наличии скрытых данных.

## Шаг 5: зачем это злоумышленнику

ADS активно применяется в атаках:

- **Хранение payload** — EXE/DLL в потоке безобидного файла.
- **Персистентность** — служба с `ImagePath`, указывающим на `file.txt:evil.exe`.
- **Сокрытие конфигов** — C2-конфиг в ADS.
- **Обход простых сканеров** — некоторые антивирусы исторически не проверяли ADS.

Поэтому при поиске персистентности проверяют `HKLM\SYSTEM\CurrentControlSet\Services\*\ImagePath` и задачи планировщика на наличие `:` в пути.

На Windows ADS создаётся тривиально:

```powershell
echo "hidden payload" > secret.txt:hidden.txt
type payload.exe > benign.txt:evil.exe
Get-Item -Path secret.txt -Stream *      # список потоков
dir /r                                    # в cmd: показать потоки
```

## Полный разбор: находим и извлекаем поток

Прогоним сценарий от подозрения до извлечённого содержимого.

1. **Замечаем аномалию.** `dir /r` показывает «лишнюю» строку рядом с файлом — это и есть ADS:
   ```cmd
   > dir /r report.docx
   report.docx                 10240
   report.docx:hidden.txt     524288
   ```
2. **Извлекаем поток** на анализ:
   ```cmd
   > powershell -c "Get-Content -Path report.docx -Stream hidden.txt -Encoding Byte -TotalCount 8"
   77 90 90 0   # MZ — внутри PE-файл!
   ```
3. **Сохраняем и проверяем:**
   ```cmd
   > powershell -c "Get-Content report.docx -Stream hidden.txt -Encoding Byte -ReadCount 0 | Set-Content payload.bin -Encoding Byte"
   > certutil -hashfile payload.bin SHA256
   ```
4. **Вывод.** Внутри «обычного» документа спрятан исполняемый файл — классический приём доставки малвари. Теперь его хеш можно проверить на VirusTotal.

Ключевой момент: `report.docx` для проводника — один файл, но NTFS хранит внутри него несколько независимых потоков данных.

## Шпаргалка по ADS

| Задача | Linux (ntfs-3g) | Windows |
|--------|-----------------|---------|
| Список потоков | `getfattr -n user.* file` | `dir /r` |
| Прочитать поток | `cat file:stream` (через ntfs-3g) | `Get-Content -Stream` |
| Создать поток | `echo x > file:stream` | `echo x > file:stream` |
| Скопировать | `cp --streams` (ограниченно) | `Get-Content`/`Set-Content` |
| Найти все | `fls -r` показывает потоки | `streams.exe -s .` |

`Mark-of-the-Web` (`Zone.Identifier`) — тоже ADS: браузер помечает скачанный файл, и Windows показывает предупреждение при запуске.

## Если не сработало

- **`dir /r` не показывает поток.** Вы на не-NTFS томе (FAT/exFAT) — там ADS нет вовсе.
- **Поток есть, но не читается.** Поток может быть удалён вместе с файлом; восстанавливайте через sleuthkit (`fls`/`icat`).
- **Копирование теряет поток.** Многие утилиты (FAT-совместимые) копируют только основной поток — используйте NTFS-aware инструменты.
- **Антивирус удалил файл.** Ищите остатки в нераспределённом пространстве или теневых копиях.
- **Слишком много ложных `Zone.Identifier`.** Это норма (все скачанные файлы), фильтруйте по содержимому.

## Защита и мониторинг

- Ограничьте запуск исполняемых файлов из «неожидаемых» мест (AppData, Temp).
- **Sysmon** событие 15 логирует создание ADS — прямое обнаружение.
- Просматривайте `Zone.Identifier` у файлов из почты/загрузок.
- Помните: ADS — легитимный механизм NTFS, но частый спутник малвари.

## Что мы теперь знаем

- **ADS** — дополнительный именованный атрибут `$DATA` у того же файла в NTFS.
- В `fls` потоки видны как записи с `:` в имени; читать их надо по **inode потока** (`<ino>-<type>-<id>`), а не по основному.
- `istat` показывает все потоки файла — быстрый способ их найти.
- ADS теряется при копировании на FAT/exFAT и при архивации в ZIP/TAR.
- **Zone.Identifier** — тоже ADS; хранит Mark-of-the-Web (происхождение файла).
- Мелкие потоки (resident) лежат в MFT и не находятся carving'ом по сигнатурам.

## Resident-потоки: почему carving их не находит

Мелкий поток (обычно до ~700 байт) NTFS хранит **resident** — прямо в записи MFT, а не в кластерах. Это меняет тактику поиска:

- **Carving по сигнатурам промахивается.** Инструмент вроде `photorec` ищет `MZ`, `PK` и другие заголовки в нераспределённом пространстве, но resident-поток вообще не лежит в кластерах — он внутри `$MFT`.
- **Искать надо в самом `$MFT`.** Извлеки метафайл (`icat disk.img 0 > mft.bin`) и разбери его (`analyzeMFT`, `mft2csv`, `MFTECmd`). В записи будут строки вида `notes.txt:hidden.txt` — так видно потоки даже там, где `fls` их пропустил по фильтру.
- **Удалённый поток остаётся в MFT.** Пока запись не переиспользована, атрибут `$DATA:name` доступен — это ещё один источник восстановления.

Отсюда правило: **на NTFS ищи скрытое не только в свободных кластерах, но и в `$MFT`** — resident-данные туда никогда не попадут carving'ом.

## Обнаружение в масштабе

На живой системе ADS находят не по одному файлу, а перебором потоков:

```powershell
Get-ChildItem -Path C:\ -Recurse -File -ErrorAction SilentlyContinue |
  Get-Item -Stream * |
  Where-Object { $_.Stream -ne ':$DATA' } |
  Select-Object FileName, Stream, Length
```

То же делает Sysinternals `streams.exe -s C:\` и `dir /s /r`. Главный источник события — **Sysmon Event ID 15** (`FileCreateStreamHash`): он логирует создание потока и считает его хеш. Это самое прямое обнаружение — не нужно сканировать диск, событие появляется в момент записи payload в поток.

Фильтровать стоит по расширению потока (`.exe`, `.dll`, `.ps1`, `.js`) и по расположению файла-носителя: поток у `report.docx` в `Downloads` — норма для MOTW, а поток `.exe` у файла в `%APPDATA%` — сильный признак малвари.

## Антифорензика через ADS

ADS используют и для сокрытия **следов**, не только payload:

- **`$Extend\$Deleted`** и другие метафайлы NTFS могут хранить имена удалённых объектов;
- поток может содержать **альтернативный конфиг** или скрипт, который «основной» файл не показывает;
- очистка потока `Remove-Item -Stream Zone.Identifier` снимает MOTW и обходит SmartScreen — поэтому отсутствие `Zone.Identifier` у «скачанного» файла само по себе подозрительно.

При разборе образа имеет смысл отдельно сравнить `$MFT` и обычный листинг: **расхождение между тем, что видит проводник, и тем, что лежит в метаданных, — и есть след сокрытия.**

## ADS в памяти и в сети

Поток не обязательно лежит на диске. Если процесс читает данные из ADS и держит
их открытыми, содержимое остаётся в RAM — и находится обычным `strings` по дампу
памяти. Инжект через ADS часто оставляет именно такой след: на диске «пусто», а в
памяти — исполняемый код.

В сети ADS проявляется косвенно: загрузка с удалённого ресурса вида
`\\host\share\file.txt:payload.exe` выглядит для логов как обращение к `file.txt`,
хотя исполняется совсем другой поток. Поэтому в разборе сетевого трафика потоковые
пути (`:stream`) нужно искать отдельно — они прячутся за безобидным именем.

## Проверяем и обходим сокрытие

Иногда стандартные средства поток не видят: `dir /r` может не показать его, а
`Get-Item -Stream *` вернуть пусто, если это resident-поток, целиком уместившийся в
MFT. Тогда работают альтернативные способы:

- **`MFTECmd`** и `analyzeMFT` — читают записи MFT и показывают потоки прямо из
  метаданных, минуя файловую систему.
- **`sleuthkit` (`fls -r`, `icat`)** — находят потоки на образе и извлекают их по
  идентификатору.
- **`Get-Content -Stream`** в PowerShell — быстрый способ на живой системе, когда
  антифорензика не мешает.

Главное правило: если подозреваешь поток, а `dir` его не показывает, не верь
файловой системе — читай метаданные напрямую.

## Куда дальше

Мы научились находить и извлекать скрытые потоки NTFS. В следующем уроке мы вернёмся к сетевым артефактам и разберём **Suricata** — сигнатурный анализ PCAP. А пока главное запомни: **ADS — это дополнительный `$DATA` с именем; его видно по `:` в `fls`, читают по inode потока, и он теряется вне NTFS**.

## Где пригодится

- **CTF:** задачи с сокрытием данных в NTFS.
- **IR:** поиск замаскированной малвари и признаков запуска из потоков.
- **Malware Analysis:** анализ персистентности через ADS.
- **Судебная экспертиза:** доказательство сокрытия данных.
