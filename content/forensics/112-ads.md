Alternate Data Streams (ADS) — возможность NTFS хранить у одного файла **несколько независимых потоков данных**. Основной поток — `$DATA` без имени, дополнительные — `$DATA` с именем: `secret.txt:hidden.txt`. Пользователь видит только основной поток, поэтому ADS — классический способ спрятать данные, полезную нагрузку или даже целый исполняемый файл.

## Устройство ADS

В NTFS файл — это набор атрибутов в записи MFT (см. `forensics-ntfs-mft`). Данные — атрибут `$DATA`. Основной поток — атрибут `$DATA` без имени; каждый ADS — ещё один атрибут `$DATA` **с именем**. Отсюда:

- У файла может быть много потоков, каждый — со своим размером и содержимым.
- ADS не виден в обычном `dir`; в проводнике Windows 7+ размер ADS может учитываться в размере папки, но не отображается.
- ADS может быть **resident** (в MFT) или non-resident (в кластерах).
- ADS есть только на NTFS; при копировании на FAT/exFAT/SMB он теряется или вызывает ошибку.

## Создание и просмотр (Windows)

```powershell
# Создать ADS с текстом
echo "hidden payload" > secret.txt:hidden.txt
# Записать бинарь в ADS
type payload.exe > benign.txt:evil.exe
# Просмотреть
Get-Item -Path secret.txt -Stream *
# Прочитать
Get-Content -Path secret.txt -Stream hidden.txt
# Удалить поток
Remove-Item -Path secret.txt -Stream hidden.txt
# Список всех ADS в дереве
Get-ChildItem -Recurse | ForEach-Object { Get-Item $_.FullName -Stream * } | Where-Object { $_.Stream -ne ':$DATA' }
```

В `cmd`: `dir /r` показывает потоки (например, `secret.txt:hidden.txt:$DATA`).

## Обнаружение на образе (Linux/sleuthkit)

```bash
# fls -r показывает ADS как отдельные записи с ':' в имени
fls -r -o <offset> disk.img | grep ':'
# Пример:
#  r/r 128-128-3: secret.txt:hidden.txt

# Извлечь конкретный поток по inode (формат inode-type-id)
icat -o <offset> disk.img 128-128-3 > hidden.bin
strings hidden.bin

# Через монтирование ntfs-3g (streams_interface)
sudo mount -t ntfs-3g -o ro,streams_interface=xattr disk.img /mnt/ntfs
getfattr -n user.ADS /mnt/ntfs/secret.txt
getfattr -d /mnt/ntfs/secret.txt
# или напрямую
cat '/mnt/ntfs/secret.txt:hidden.txt'
```

`streams_interface=xattr` отображает потоки в xattr `user.ADS`; значение — список имён. Есть также `streams_interface=windows`, где поток читается как `file:stream`.

## Использование в малвари

ADS активно применяется злоумышленниками:
- **Хранение payload** — EXE/DLL в потоке безобидного файла.
- **Персистентность** — через `wmic`/реестр с запуском из потока; например, служба с `ImagePath`, указывающим на `file.txt:evil.exe`.
- **Сокрытие конфигов** — C2-конфиг в ADS.
- **Обход простых сканеров** — некоторые антивирусы исторически не проверяли ADS.
- **Mark-of-the-Web** — Windows хранит MOTW в потоке `Zone.Identifier`; его удаление — типичный шаг обхода защит.

```bash
# Zone.Identifier — тоже ADS
icat -o <offset> disk.img <inode>-128-2 > zone.bin   # по inode потока Zone.Identifier
cat zone.bin
# [ZoneTransfer]
# ZoneId=3
```

## Разобранный пример

```bash
$ fls -r -o 2048 disk.img | grep ':'
r/r 64-128-1: notes.txt
r/r 64-128-3: notes.txt:hidden.txt
r/r 70-128-2: photo.jpg:Zone.Identifier
$ icat -o 2048 disk.img 64-128-3 > hidden.bin
$ file hidden.bin
hidden.bin: PE32 executable (GUI) Intel 80386
$ icat -o 2048 disk.img 70-128-2
[ZoneTransfer]
ZoneId=3
ReferrerUrl=https://evil.example/payload
```

Поток `hidden.txt` содержит PE-файл — замаскированная малварь; `Zone.Identifier` указывает на скачивание из интернета.

## Краевые случаи и подводные камни

- **Не путать `:` в выводе fls.** В `fls` двоеточие — это разделитель потока; проверяйте inode.
- **`icat` с суффиксом.** Формат: `<inode>-<type>-<id>`. Если указать только основной inode, прочитаете `$DATA`, а не ADS.
- **ADS не переносится через FAT/exFAT.** Копирование на флешку уничтожит поток — важный признак при анализе.
- **`dir /r` нужен явно.** Обычный `dir` ADS не показывает.
- **Zone.Identifier — тоже ADS.** Его наличие/отсутствие говорит о происхождении файла.
- **Resident ADS.** Мелкие потоки лежат в MFT; при carving их не найти по сигнатурам — только через метаданные.
- **Антифорензика.** Потоки могут быть удалены, но `$UsnJrnl`/`$LogFile` сохранят следы создания.
- **Инструменты.** `fls`/`icat` (Linux), `MFTECmd`, `AdsSpy`, PowerShell (Windows).

## ADS на уровне байтов

Чтобы понять ADS, полезно увидеть его в записи MFT. Основной поток — атрибут `$DATA` (тип 0x80) **без имени**. Каждый ADS — атрибут `$DATA` **с именем** (длина имени > 0 в заголовке атрибута). Если данные маленькие (resident), они лежат прямо в MFT; если большие — non-resident, с runlist.

```bash
# Дамп записи MFT и поиск нескольких атрибутов 0x80
icat -o <offset> disk.img 0 > MFT.bin
xxd MFT.bin | grep -A1 '80 00 00 00'   # заголовки атрибутов DATA
# istat показывает все потоки и их размеры
istat -o <offset> disk.img <inode>
```

`istat` для файла с ADS выведет несколько строк `Attribute: Name: ... Type: Data` — по одной на поток. Это самый быстрый способ убедиться в наличии скрытых потоков.

## Обнаружение в масштабе

На большом образе нужно найти все ADS, а не открывать файлы по одному:

```bash
# Все потоки во всех каталогах
fls -r -o <offset> disk.img | grep ':' > streams.txt
wc -l streams.txt

# Только подозрительные (исполняемые расширения в потоке)
fls -r -o <offset> disk.img | grep -Ei ':(.*\.(exe|dll|ps1|bat|vbs|scr))'

# Извлечь все потоки скриптом по inode
while read -r line; do
  ino=$(echo "$line" | awk '{print $2}')
  icat -o <offset> disk.img "$ino" > "stream_${ino//[:\/]/_}.bin"
done < streams.txt
```

Затем — `file`/`strings` по извлечённым потокам и YARA-сканирование.

## ADS в персистентности

Классические схемы:

- **Служба из ADS.** `sc create svc binPath= "C:\path\file.txt:evil.exe"` — Windows выполнит поток.
- **Планировщик.** Задача, ссылающаяся на поток в триггере/действии.
- **WMI.** Event subscription с payload в ADS.
- **Загрузчик.** Некоторые трояны читают второй этап из ADS безобидного файла.

Поиск: проверить `HKLM\SYSTEM\CurrentControlSet\Services\*\ImagePath` на наличие `:` в пути; проверить задачи планировщика.

```bash
# Ссылки на потоки в реестре
regipy-dump SOFTWARE --path 'Microsoft\Windows NT\CurrentVersion\Schedule\TaskCache\Tasks' -o tasks.json
grep -i ':' tasks.json | head
```

## MOTW и Zone.Identifier

Mark-of-the-Web — это ADS `Zone.Identifier` со содержимым:

```
[ZoneTransfer]
ZoneId=3
ReferrerUrl=https://evil.example/payload.exe
HostUrl=https://evil.example/payload.exe
```

`ZoneId=3` — интернет; `2` — доверенная зона; `4` — restricted. Наличие MOTW — сильный признак скачивания из сети. Удаление потока (`Remove-Item -Stream Zone.Identifier`) — распространённый шаг обхода SmartScreen; отсутствие MOTW у файла, который «скачали», подозрительно.

## Извлечение и анализ

```bash
# Монтирование с потоками как xattr
sudo mount -t ntfs-3g -o ro,streams_interface=xattr disk.img /mnt/ntfs
getfattr -d -m - /mnt/ntfs/suspect.txt
# Прочитать конкретный поток
getfattr --only-values -n 'user.ADS' /mnt/ntfs/suspect.txt
cat '/mnt/ntfs/suspect.txt:evil.exe' > /tmp/evil.exe
file /tmp/evil.exe
```

Для больших образов удобнее `fls`+`icat` (без монтирования) — быстрее и не меняет метаданные.

## Типичные ошибки

- **Обычный `dir`.** Не покажет ADS; нужен `dir /r`.
- **`icat` по основному inode.** Прочитает `$DATA`, а не поток; нужен inode потока (`<ino>-<type>-<id>`).
- **Копирование на FAT.** Поток потеряется.
- **Игнорирование Zone.Identifier.** Это тоже ADS и важный индикатор.
- **Пропуск resident-потоков.** Мелкие потоки в MFT не найдутся carving'ом.
- **Забыть про `$UsnJrnl`.** Следы создания потока остаются в журнале даже после удаления.

## ADS в сетевых шарах и архивах

Важный практический момент: ADS живёт только на NTFS. При передаче файла по SMB на NTFS-шару он **может** сохраниться (зависит от реализации и клиента), но при архивации в ZIP/TAR — теряется. Это даёт аналитику два вывода:

- Если образ шёл через архив/флешку, ADS мог быть утерян при копировании — не делайте вывод «потока не было».
- Если ADS присутствует на образе, файл, вероятно, не покидал NTFS-том (или копировался инструментом, сохраняющим потоки, например `robocopy /copyall`).

```bash
# robocopy сохраняет потоки на Windows
robocopy src dst /copyall /e
# На Linux — через ntfs-3g и tar с xattr, либо icat/fls
```

Для восстановления порядка создания потоков сверяйтесь с `$UsnJrnl`: события с причиной `DATA_EXTEND`/`DATA_OVERWRITE` по inode потока покажут, когда ADS появился.

## Итоговая шпаргалка по ADS

| Задача | Команда |
|--------|---------|
| Найти все потоки | `fls -r -o OFF disk.img \| grep ':'` |
| Извлечь поток | `icat -o OFF disk.img <ino>-<type>-<id> > out.bin` |
| Показать атрибуты inode | `istat -o OFF disk.img <ino>` |
| Смонтировать с xattr | `mount -t ntfs-3g -o ro,streams_interface=xattr disk.img /mnt` |
| Список потоков | `getfattr -d -m - /mnt/file` |
| Windows: список | `dir /r` или `Get-Item file -Stream *` |
| MOTW | `cat file:Zone.Identifier` |

ADS — не экзотика, а штатная возможность NTFS, которую активно используют и легитимные приложения, и малварь. Поэтому проверяйте потоки в каждом Windows-образе.

## Что дальше / решение

1. `fls -r | grep ':'` — найти все потоки.
2. `icat <inode>-<type>-<id>` — извлечь содержимое.
3. Проверить `Zone.Identifier` (MOTW) для происхождения.
4. Свериться с `$UsnJrnl`/`$LogFile` — когда поток создан.
5. Искать ссылки на ADS в реестре/службах (персистентность).

Дальше — `forensics-registry-deep` (автозапуск) и `forensics-fileless` (малварь без файла).
