## Вопрос, с которого всё начинается

У тебя есть образ Windows. Известно, что атакующий запускал вредонос — но под
каким именем? В текущем списке файлов ничего подозрительного нет: всё либо удалено,
либо переименовано в безобидное `svchost.exe`. Как восстановить, **что и когда** с
файлами делали?

В предыдущем уроке мы видели, что NTFS хранит запись о каждом файле в MFT. Но у
неё есть ограничение: она хранит **текущее** состояние. Историю изменений держит
отдельный журнал — `$UsnJrnl`. В этом уроке мы разберём его на конкретном образе и
восстановим цепочку переименований.

## Наш пример: подозрительный образ с journal

У нас есть `disk.img` с NTFS-разделом, начинающимся с сектора 2048. Первым делом
находим сам журнал. `$UsnJrnl` лежит в служебном каталоге `$Extend` (запись MFT 11):

```bash
$ fls -o 2048 disk.img 11
d/d 42-128-1: $UsnJrnl
```

У `$UsnJrnl` есть **два потока** — то есть два «содержимого» одного файла:

| Поток | Что внутри |
|-------|-----------|
| `$Max` | служебные метаданные (максимальный USN, версия) |
| `$J` | сами записи журнала — то, что нам нужно |

Нам нужен `$J`. Находим его поток и вытаскиваем:

```bash
$ fls -r -o 2048 disk.img | grep -i 'usnjrnl'
r/r 42-128-3: $Extend/$UsnJrnl:$J
$ icat -o 2048 disk.img 42-128-3 > usn.bin
$ ls -l usn.bin
-rw-r--r-- 1 user user 4194304 usn.bin
```

Четыре мегабайта записей. Каждая запись — событие на томе.

## Шаг 1: что такое USN и почему это лента

**USN** расшифровывается как Update Sequence Number — «номер последовательности
обновлений». Это журнал, который NTFS ведёт с момента создания тома и в который
попадает **каждое** изменение: файл создан, перезаписан, переименован, удалён,
изменены права. У каждой записи есть:

- номер (USN) — порядковый, монотонно растёт;
- время (в формате FILETIME, UTC);
- имя файла;
- **Reason** — битовая маска, «что именно произошло».

Именно `Reason` делает журнал таким ценным: он не просто говорит «файл изменён»,
а различает создание, удаление, переименование и даже работу с потоками ADS.

Разбираем записи в удобный CSV. Для этого есть Python-парсер `usnparser`:

```bash
$ pip install usnparser
$ usnparser parse usn.bin > usn.csv
$ head -4 usn.csv
Timestamp,USN,Reason,Name,ParentPath
2024-01-12 10:03:11,50012,FILE_CREATE,update.exe,C:\Users\bob\Downloads
2024-01-12 10:03:15,50040,DATA_OVERWRITE,update.exe,C:\Users\bob\Downloads
2024-01-12 10:04:02,50101,RENAME_OLD_NAME,update.exe,C:\Users\bob\Downloads
```

Мы уже видим историю: в 10:03 создан `update.exe`, через секунды перезаписан, а в
10:04 — начало переименования.

## Шаг 2: расшифровываем Reason

`Reason` — это **битовая маска**: одно число, в котором каждый бит означает флаг.
Комбинируются флаги через побитовое «И» (`&`). Основные:

| Значение | Флаг | Что означает |
|---------:|------|--------------|
| `0x00000100` | FILE_CREATE | создание |
| `0x00000200` | FILE_DELETE | удаление |
| `0x00002000` | RENAME_OLD_NAME | старое имя при переименовании |
| `0x00004000` | RENAME_NEW_NAME | новое имя при переименовании |
| `0x00000400` | SECURITY_CHANGE | смена прав |
| `0x00400000` | STREAM_CHANGE | создан/удалён поток ADS |
| `0x80000000` | CLOSE | файл закрыт (финал операции) |

Почему это важно: один «клик» пользователя (например, переименование) рождает
**две** записи — `RENAME_OLD_NAME` и `RENAME_NEW_NAME` — с **одинаковым USN**. Чтобы
понять, во что переименовали, эти две записи надо сшить.

## Шаг 3: сшиваем пары переименований

Пишем маленький скрипт: группируем записи по USN, собираем «старое» и «новое» имя:

```python
import csv, collections
pairs = collections.defaultdict(dict)
for row in csv.DictReader(open('usn.csv', encoding='utf-8')):
    usn = row['USN']; r = int(row['Reason'], 0)
    if r & 0x00002000:
        pairs[usn]['old'] = row['Name']
    if r & 0x00004000:
        pairs[usn]['new'] = row['Name']
    pairs[usn]['ts'] = row['Timestamp']
for usn, d in sorted(pairs.items()):
    if 'old' in d and 'new' in d:
        print(f"{d['ts']}  {d['old']}  ->  {d['new']}")
```

Запускаем:

```bash
$ python3 rename_pairs.py
2024-01-12 10:04:02  update.exe  ->  svchost.exe
2024-01-12 10:07:41  svchost.exe  ->  svchost.exe.bak
```

Вот и ответ: `update.exe` переименовали в `svchost.exe`, чтобы замаскировать под
системный процесс, а позже — в `.bak`. Без журнала мы бы этого не увидели: в
текущем состоянии файла `svchost.exe.bak` уже может не быть.

## Шаг 4: ищем удаления и признаки шифровальщика

Теперь ищем удаления — флаг `FILE_DELETE`:

```bash
$ grep -i 'FILE_DELETE' usn.csv | head
2024-01-12 10:08:03,FILE_DELETE,svchost.exe.bak,C:\Users\bob\Downloads
```

Одно удаление — мелочь. А вот **массовые** удаления с одновременным переименованием
в файлы с одним расширением — классическая подпись ransomware:

```bash
# сколько событий в каждую минуту
$ cut -d, -f1 usn.csv | cut -c1-16 | sort | uniq -c | sort -rn | head
    842 2024-01-12 10:15
    790 2024-01-12 10:16
$ grep -iE 'RENAME_NEW_NAME' usn.csv | grep -c '\.locked'
4210
```

В 10:15–10:16 произошло 842 + 790 событий, а 4210 файлов получили расширение
`.locked`. Это не человек за клавиатурой — это шифровальщик. Журнал USN даёт нам
время начала атаки с точностью до минуты.

## Шаг 5: строим таймлайн

USN — один источник. Приводим его к общему виду и объединяем с временами из MFT и
событиями из логов Windows (EVTX):

```bash
$ python3 - <<'EOF' > usn_bodyfile.txt
import csv
for r in csv.DictReader(open('usn.csv', encoding='utf-8')):
    print(f"0|{r['ParentPath']}/{r['Name']}|-|-|{r['Timestamp']}|{r['Reason']}")
EOF
$ cat mft_bodyfile.txt usn_bodyfile.txt | sort -t'|' -k5 | head
```

Получаем единую ленту: файл → время → источник. Время в USN всегда UTC, поэтому при
сопоставлении с локальными логами учитывай часовой пояс хоста, иначе события
«разъедутся» на несколько часов.

## Что мы теперь знаем

- `$UsnJrnl` — лента всех изменений на томе; записи лежат в потоке `$J`.
- У каждой записи есть номер, время, имя и битовая маска `Reason`.
- Переименование — две записи (`RENAME_OLD_NAME` + `RENAME_NEW_NAME`) с одним USN.
- `FILE_DELETE` показывает удаления; их всплеск — признак шифровальщика.
- USN удобно сливать с MFT и EVTX в единый таймлайн.

## На что смотреть дальше

- **Не путайте `$J` и `$Max`** — записи только в `$J`.
- **Журнал разреженный (sparse)** — старые записи вытесняются нулевыми «дырками»;
  парсер должен уметь их пропускать. Отсутствие записи ≠ отсутствие действия.
- **Сшивайте rename по USN, а не по времени** — время может совпасть до секунды.
- **`STREAM_CHANGE` (`0x400000`)** означает работу с ADS — не пропускайте его.
- **Очистка журнала** (`fsutil usn deletejournal`) — сам по себе признак: честный
  пользователь журнал не удаляет.

## Разбираем запись вручную: что внутри USN_RECORD_V2

Иногда под рукой нет парсера, и журнал приходится читать побайтово. Запись
`USN_RECORD_V2` — это структура с фиксированным заголовком и именем в конце. Вот
её поля по порядку:

| Смещение | Размер | Поле | Смысл |
|---|---|---|---|
| 0x00 | 4 | RecordLength | длина всей записи (шаг до следующей) |
| 0x04 | 2 | MajorVersion | 2 для V2 |
| 0x08 | 8 | FileReferenceNumber | ссылка на запись MFT |
| 0x10 | 8 | ParentFileReferenceNumber | ссылка на родительский каталог |
| 0x18 | 8 | USN | номер записи |
| 0x20 | 8 | TimeStamp | FILETIME (UTC) |
| 0x28 | 4 | Reason | битовая маска события |
| 0x30 | 2 | FileNameLength | длина имени в байтах |
| 0x32 | 2 | FileNameOffset | смещение имени от начала записи |
| 0x34 | 2 | FileName | UTF-16LE, длина = FileNameLength |

Ключ к чтению — поле `RecordLength`: записи идут **подряд**, и, чтобы перейти к
следующей, нужно прибавить именно это число, а не фиксированный размер. Имя в
UTF-16LE легко прочитать: два байта на символ, младший байт первым. Поэтому
`svchost.exe` в hex выглядит как чередование буквы и `00`.

Важно, что `FileReferenceNumber` и `ParentFileReferenceNumber` — это ссылки в MFT
(старшие 48 бит — номер записи, младшие 16 — sequence number). Именно по ним USN
связывается с `$MFT`: журнал даёт **событие**, а MFT — **текущее состояние** записи,
на которую событие ссылается.

## Чего в USN нет — границы метода

У журнала есть слепые зоны, и их важно знать, чтобы не переоценить находку:

- **Содержимого файлов** нет — только метаданные (имя, время, причина).
- **Кто именно** сделал действие — не указано: нет пользователя, процесса, PID.
- **Полнота ограничена**: `$J` разреженный, старые записи вытесняются по мере роста
  тома, поэтому «нет события» может означать «запись уже потеряна», а не «действия
  не было».
- **Отключение журнала** возможно (`fsutil usn deletejournal`), и тогда история
  начинается заново.

Поэтому USN никогда не используют в одиночку. Его сила — в связке: имя из USN →
запись MFT (какой размер, какие потоки) → событие в EVTX (какой процесс создал
файл) → сетевая активность. Только вместе они дают доказательство, а не догадку.

Мы восстановили историю действий с файлами на NTFS. Дальше пойдём в мир Linux и
разберём, как устроена ext4: её журнал, inode и extent-дерево — чтобы так же

## Где пригодится

- **CTF:** задачи, где надо доказать переименование/удаление файла.
- **Incident Response:** восстановление последовательности действий атакующего.
- **Ransomware-анализ:** массовые rename/delete за короткое время.
- **Threat Hunting:** поиск запусков из Temp/Downloads по именам из USN.
- **Судебная экспертиза:** объективная лента операций с файлами.
