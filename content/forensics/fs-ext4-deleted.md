## Вопрос, с которого всё начинается

На Linux-сервере удалили файл с логами. Ты снял образ раздела и хочешь его вернуть. На
ext2/ext3 восстановление часто проходило легко — а тут `extundelete` молчит. Причина в
том, что **ext4 по-другому освобождает данные**. Разберём, что именно происходит и как
это обойти.

## Что такое ext4 и его inode

**ext4 (Fourth Extended Filesystem)** — основная ФС Linux. Как и в ext2/ext3, каждый файл
описан **inode** — записью с метаданными: права, владелец, размер, метки времени и
**указатели на блоки данных**. Сами блоки лежат отдельно.

Главное отличие ext4 — **extents**. Вместо перечисления блоков по одному (как в ext3),
ext4 хранит **диапазоны**: «начиная с логического блока N, идут M подряд идущих
физических блоков». Это компактнее и быстрее. Extent-ы образуют **дерево**: корень в
inode, при разрастании — дополнительные узлы.

## Наш пример: образ с удалённым файлом

```
$ ls -la
-rw-r--r-- 1 student student 33554432 disk.img
$ file disk.img
disk.img: Linux rev 1.0 ext4 filesystem data, UUID=...
```

Смотрим метаданные inode удалённого файла. При удалении ext4:

- обнуляет **`i_links_count`** (счётчик ссылок → 0);
- записывает **`i_dtime`** — время удаления;
- освобождает блоки в битмапе;
- **в современных ext4 обнуляет указатели на extent-дерево**.

Именно последний пункт — причина, почему данные «исчезают»: даже если блоки физически не
перезаписаны, inode больше не знает, где они. Посмотрим метки:

```
$ strings disk.img | grep -Ei 'i_dtime|extent|inode|nto'
inode 1048577 i_links_count=0 i_dtime=1773200000
extent tree zeroed on delete
jbd2 journal: transaction 8821 committed
EVIDENCE: nto{ext4_1n0d3_dt1m3_jbd2}
```

Три подсказки: inode освобождён (links=0), extent-дерево обнулено, но **журнал jbd2**
хранит транзакции. Журнал — часто единственный источник старых указателей.

## Шаг 1: почему ext4 сложнее ext3

| Аспект | ext3 | ext4 |
|--------|------|------|
| Указатели | прямые/косвенные блоки | extent-дерево |
| При удалении | блоки часто остаются в inode | extent-дерево обнуляется |
| Восстановление | extundelete хорошо работает | сложнее, нужен журнал |
| Журнал | jbd2 | jbd2 |
| Inode | 128 байт | 256 байт (больше полей) |

Практический вывод: **на ext4 «сырое» восстановление по inode часто невозможно** — нужно
идти через журнал или карать (carving) по сигнатурам.

## Шаг 2: журнал jbd2 как источник

**jbd2 (journaling block device 2)** — журнал транзакций ext4. Как и `$LogFile` в NTFS,
он хранит redo-записи: что именно должно быть записано на диск. Если удаление произошло
недавно, в журнале могут остаться **старые extent-записи** — то есть карта блоков до
удаления. Инструменты:

- **`ext4magic`** — читает журнал и восстанавливает файлы по inode и времени;
- **`extundelete`** — работает с журналом и блоками, но на ext4 ограничен;
- **`debugfs`** — низкоуровневый доступ: `debugfs -R 'lsdel'` показывает удалённые inode;
- **`e2fsck -E journal_only`** — переиграть журнал (осторожно: меняет ФС).

Пример работы `debugfs`:

```
$ debugfs -R 'lsdel' disk.img
 Inode  Owner  Mode    Size    Blocks   Time deleted
1048577   0    100644  4096    8/8      Thu Mar 12 01:19:57 2026
```

`lsdel` показывает удалённые inode с временем удаления — отправная точка для поиска.

## Шаг 3: восстановление через журнал

```
$ ext4magic disk.img -r -a 1773190000 -b 1773210000 -d /evidence/restored
...
Files recovered: 3
```

Флаги `-a` (after) и `-b` (before) задают окно времени: восстанавливаем файлы, удалённые
между двумя моментами. Это точный приём, когда известно время инцидента.

Если журнал уже «завёрнут» (старые транзакции перезаписаны), остаётся **carving**:
сканирование сырых блоков по сигнатурам (см. урок про фрагментированный carving).

## Шаг 4: что проверять при восстановлении

- **Не перезаписывай образ.** Любая запись освободит/переиспользует блоки.
- **Сначала копия.** Смонтируй образ только для чтения или работай с копией.
- **Проверь целостность.** Восстановленный файл может быть частично перезаписан —
  сверь с ожидаемым содержимым.
- **Смотри метки времени.** `i_dtime` даёт время удаления; сопоставь с `syslog`/`auditd`.

## Шаг 5: сопоставление с другими источниками

На Linux удаление часто видно в нескольких местах:

- **`auditd`** — события `unlink`, `unlinkat` с путём и PID;
- **`syslog`/`journald`** — если файл удаляла служба;
- **`bash_history`** — команда `rm`;
- **atime/mtime других файлов** — косвенные следы.

Совпадение времени `i_dtime` и записи в auditd — сильное доказательство.

## Мини-практика: от образа к файлу

Полный прогон:

```
$ file disk.img
disk.img: Linux rev 1.0 ext4 filesystem data
$ debugfs -R 'lsdel' disk.img | grep 1048577
 1048577   0  100644  4096  8/8  Thu Mar 12 01:19:57 2026
$ ext4magic disk.img -r -a 1773190000 -b 1773210000 -d ./out
$ ls out/
lost+found  recovered_log.txt
```

Три шага: опознали ФС, нашли удалённый inode с временем, восстановили через журнал в окне
времени. В реальном деле дальше сверяют хеши и строят таймлайн.

## Частые ошибки и подводные камни

- **Монтирование с записью.** Запустит переиспользование блоков.
- **Ожидание «магии» ext4.** `file` иногда не различает ext2/3/4 — смотри суперблок.
- **Игнорирование journal_only.** Переигрывание журнала меняет ФС; делай это на копии.
- **Путаница i_dtime и mtime.** `i_dtime` — время удаления, `mtime` — изменения данных.
- **Забытая опция mount.** На живой системе `relatime`/`noatime` меняют доступное время.

## Что мы теперь знаем

- ext4 использует extent-дерево; при удалении указатели обнуляются.
- `i_links_count=0` и `i_dtime` — признаки удалённого inode.
- Журнал jbd2 может хранить старые extent-записи.
- Инструменты: `debugfs lsdel`, `ext4magic`, `extundelete`, `e2fsck -E journal_only`.
- Если журнал затёрт — остаётся carving по сигнатурам.

## Суперблок, группы блоков и где искать блоки файла

Чтобы понять ext4, нужно знать про **суперблок** и **группы блоков**. Суперблок (offset
1024) описывает весь том: размер блока, число inode, число групп, состояние ФС. Группы
блоков делят том на части, у каждой — свой битмап блоков и таблица inode. При удалении
файла:

- бит в **битмапе блоков** сбрасывается — блок считается свободным;
- в **битмапе inode** сбрасывается бит занятости inode;
- поля inode обнуляются (включая extent-дерево).

Для аналитика это значит: **битмап — карта того, что свободно сейчас**, но не того, что
было занято раньше. Если ты видишь подозрительно большой «свободный» участок, это может
быть недавно освобождённый файл. Полезные команды `debugfs`:

```
$ debugfs -R 'stats' disk.img | head
Filesystem volume name:   <none>
Block size:               4096
Inode size:               256
$ debugfs -R 'show_super_stats' disk.img | grep -i 'free blocks'
Free blocks:              8123
```

Сравнив `Free blocks` до и после (если есть два образа), можно оценить объём удалённого.

## Правовые и практические аспекты восстановления

Восстановление удалённых данных — не только техника, но и процедура:

- **цепочка сохранности (chain of custody)**: фиксируй, кто, когда и как снял образ;
- **хеш образа** до и после работы — доказательство, что источник не изменён;
- **работа с копией**: оригинал запечатывается, все эксперименты — на дубликате;
- **документирование неудач**: если файл восстановить не удалось, это тоже вывод, и его
  нужно обосновать (перезапись, отсутствие журнала);
- **оценка достоверности**: частично восстановленный файл помечается как таковой.

Именно поэтому в отчёте рядом с каждым восстановленным файлом указывают метод, инструмент,
версию и степень уверенности. «Я восстановил файл» без этих деталей — не доказательство.

## Куда дальше

Мы разобрали восстановление в ext4. Дальше займёмся **фрагментированным carving-ом** — что
делать, когда метаданных нет вовсе и файл разбросан по диску. А пока главное запомни:
**на ext4 без журнала extent-дерево не вернуть — иди через jbd2 или сигнатуры**.
