## Вопрос, с которого всё начинается

Атакующий не трогал продакшн напрямую — он влез в **CI/CD-пайплайн**, у которого были
права на облако. Пайплайн «легитимно» развернул то, что нужно атакующему. Как это
расследовать?

## Наш пример: подозрительный запуск

В CI-системе видим запуск:

```
$ ci list-builds --pipeline deploy-prod --limit 5
#1240  main      success   2026-03-10T03:08:00Z  alice
#1241  feature/x  success   2026-03-10T03:12:00Z  bot
```

Сборка #1241 запущена из ветки `feature/x` пользователем `bot` — нетипично для деплоя в
прод.

## Почему CI/CD — лакомая цель

Пайплайны обычно имеют **широкие права**: доступ к облаку, секретам, реестрам образов.
Если атакующий может изменить код пайплайна или запустить его, он получает эти права
**легально** — с точки зрения облака это «санкционированный» деплой.

## Шаг 1: логи запусков

Каждый запуск хранит: кто запустил, из какой ветки/коммита, какие шаги выполнялись, что
вывелось. Ищем:

- запуски из неожиданных веток или форков;
- запуски «ботом» или сервисным аккаунтом в нетипичное время;
- шаги, которых нет в обычном пайплайне.

## Шаг 2: артефакты сборки

Пайплайн создаёт **артефакты**: образы, архивы, манифесты. Атакующий может внедрить код в
образ:

```
$ ci get-artifact #1241
app:1.2.4-x  (образ)
```

Сравниваем образ с предыдущим (`docker history`, диффы слоёв) — ищем добавленные файлы.

## Шаг 3: доступ к секретам

Пайплайн получает секреты из менеджера или переменных CI. Проверяем аудит:

- какие секреты читал этот запуск;
- не расширили ли права пайплайна перед запуском.

## Шаг 4: раннеры

**Раннер** — машина, где выполняется пайплайн. Если раннер скомпрометирован (например,
через уязвимость или доступ к хосту), атакующий может влиять на все сборки. Проверяем:

- кто имел доступ к раннеру;
- какие процессы на нём запускались;
- не менялся ли образ раннера.

## Ловушка: пайплайн «доверенный»

Сложность в том, что действия пайплайна выглядят легитимно: он и должен разворачивать
инфраструктуру. Поэтому ключ — **сравнение с нормой**: что обычно делает пайплайн и что
сделал этот запуск.

## Что мы теперь знаем

- CI/CD часто имеет широкие права в облаке.
- Логи запусков показывают кто/откуда/что делал.
- Артефакты (образы) могут содержать внедрённый код.
- Секреты, прочитанные пайплайном, подлежат ротации.
- Раннер — потенциальная точка компрометации.

## Типы CI/CD и их артефакты

Каждая система хранит свой набор следов, и знать их важно:

| Система | Где искать историю | Особенность |
|---|---|---|
| GitHub Actions | API `/actions/runs`, artifacts | логи в вебе, ephemeral runners |
| GitLab CI | `/pipelines`, job logs | `CI_*` переменные |
| Jenkins | `builds/`, `jenkins.log` | Groovy-скрипты, `build.xml` |
| ArgoCD | Application history | sync-события в кластер |
| Azure DevOps | `/pipelines/runs` | service connections |

Общее правило: у каждой системы есть **история запусков** (кто, когда, из какого
коммита), **логи шагов** и **артефакты**. Их комбинация и восстанавливает атаку.

## Логи запусков: что смотреть

Запуск описывается набором полей, и аномалия почти всегда в одном из них:

```
$ ci list-builds --pipeline deploy-prod --limit 10
#1239  main        success  2026-03-09T10:00:00Z  alice
#1240  main        success  2026-03-10T03:08:00Z  alice
#1241  feature/x   success  2026-03-10T03:12:00Z  bot    <-- аномалия
```

Красные флаги:

- ветка/форк, из которой деплой в прод обычно не идёт;
- сервисный аккаунт (`bot`) вместо человека;
- нетипичное время (03:12 ночи);
- изменение самого файла пайплайна (`.github/workflows/*.yml`) в том же коммите;
- шаги, которых нет в обычном пайплайне (`curl` на внешний хост, установка тула).

## Секреты и их ротация

Пайплайн читает секреты из менеджера или переменных CI. При компрометации нужно понять,
**какие** секреты утекли и их отозвать:

```
$ ci get-run #1241 --secrets-accessed
$ vault audit list -path=secret/
```

Проверяй аудит менеджера секретов (Vault, AWS Secrets Manager, GitLab masked variables):
кто и когда читал секреты, не расширяли ли права перед запуском. Все прочитанные во время
инцидента секреты подлежат ротации — даже если неясно, утекли ли они.

## Раннеры: компрометация и следы

Раннер — машина, исполняющая пайплайн. Если это self-hosted раннер, он часто живёт
долго и хранит кэши, ключи и рабочие каталоги между запусками:

```
$ ls ~/actions-runner/_work/ /var/lib/jenkins/workspace/
$ grep -aiE 'token|secret|password' ~/actions-runner/_diag/*.log | head
```

Признаки компрометации раннера: изменение его образа, установка пакетов вне пайплайна,
обращения к секретам из шага, который их не должен видеть, сетевые соединения к внешним
адресам во время сборки. Ephemeral (одноразовые) раннеры снижают риск, но затрудняют
форензику — машина уже уничтожена, остаются только логи.

## Артефакты и образы: диффы

Самый частый вектор — **внедрение кода в артефакт сборки** (образ). Сравнение с
предыдущим артефактом выдаёт добавленное:

```
$ docker history app:1.2.4-x
$ docker save app:1.2.4-x -o new.tar && docker save app:1.2.3 -o old.tar
$ mkdir n o && tar -xf new.tar -C n && tar -xf old.tar -C o
$ diff -rq o/ n/ | head
```

Любой лишний слой, файл или изменённый бинарник — след. Также проверяй манифесты,
SBOM и подписи (`cosign verify`).

## Практический разбор CTF

Задача: «через какой запуск произошла компрометация». Порядок:

```
$ ci list-builds --limit 50 | grep -vE 'main .* alice'    # нетипичные запуски
$ ci get-build #1241 --logs | grep -iE 'curl|wget|chmod|base64|token'
$ ci get-build #1241 --changed-files
$ docker history app:1.2.4-x | grep -iE 'ADD|COPY|RUN'
```

Флаг часто лежит в логе шага (вывод `env`, случайно залогированный токен) или в
добавленном файле артефакта.

## Ограничения

- Логи CI хранятся ограниченное время (у GitHub Actions по умолчанию 90 дней) — потом
  исчезают.
- Ephemeral-раннеры уничтожаются — живых артефактов нет.
- Секреты в логах могут быть замаскированы (`***`) — тогда их не восстановить из логов.
- Пайплайн может быть «доверенным» — вывод строится только на сравнении с нормой.

## Если сработало / не сработало

Если логи недоступны — работай по артефактам и метаданным запусков (кто/когда/коммит).
Если раннер уничтожен — ищи его логи и внешние обращения. Если подозрение на секреты —
ротируй всё, к чему имел доступ запуск, не дожидаясь доказательств утечки.

## Карта артефактов CI/CD

Расследование пайплайна — это работа с несколькими независимыми источниками:

| Артефакт | Что показывает |
|---|---|
| История запусков | кто, когда, из какой ветки, статус |
| Логи шагов (job log) | команды, вывод, ошибки |
| Конфиг пайплайна (`.gitlab-ci.yml`, workflow) | что должно выполняться |
| Артефакты сборки | образы, архивы, манифесты |
| Аудит секретов | какие секреты читались |
| Метаданные раннера | где и на чём выполнялось |

Ключ — **сравнение** «что должно быть» (конфиг в репозитории) с «что было» (лог
запуска). Расхождение и есть компрометация.

## GitHub Actions / GitLab CI: где искать

У разных систем свои точки хранения:

- **GitHub Actions**: вкладка Actions → конкретный run → job log; артефакты в
  `actions/upload-artifact`; секреты в Settings → Secrets; события — в Audit log
  организации.
- **GitLab CI**: `CI/CD → Pipelines → Job → Log`; артефакты (`artifacts:`); переменные
  в Settings → CI/CD; аудит — в `admin/audit_log`.
- **Jenkins**: `builds/<job>/<num>/log`, `config.xml`, история SCM.
- **Argo CD / Tekton**: свои CRD и логи контроллера.

Пример поиска подозрительного шага:

```
$ ci get-log #1241 | grep -iE 'curl|wget|base64|eval|export AWS'
```

Команды вида `curl ... | sh`, `eval $(...)`, выгрузка переменных окружения — маркеры
внедрённого шага.

## Атаки на пайплайны и их следы

Типовые сценарии компрометации:

| Атака | Как | След |
|---|---|---|
| Poisoned Pipeline Execution | правка кода пайплайна/скрипта | новый шаг в логе |
| Secret exfiltration | печать/отправка секретов | секрет в выводе job |
| Runner takeover | захват раннера | новые процессы, изменённый образ |
| Artifact tampering | подмена образа | дифф слоёв с предыдущим |
| Dependency confusion | подмена зависимости | новый источник пакета |
| OIDC abuse | получение временных кред | AssumeRoleWithWebIdentity в аудите |

Ищи: запуски из форков/веток с правом на секреты, изменение `.gitlab-ci.yml` перед
запуском, шаги с сетевыми запросами наружу.

## OIDC и временные креды

Современные пайплайны не хранят долгоживущие ключи, а получают **временные** через
OIDC (например, GitHub → AWS):

```
$ aws cloudtrail lookup-events --lookup-attributes \
    AttributeKey=EventName,AttributeValue=AssumeRoleWithWebIdentity
```

В `CloudTrail` видно, **какой субъект** (репозиторий/ветка) получал креды и **что потом
делал**. Если креды получил форк или неожиданная ветка — это признак взлома пайплайна.
Срок жизни кред короткий, поэтому ротация сама по себе не решает проблему — нужно
устранить точку входа.

## Практический таймлайн

Собери события в одну ленту:

1. Коммит/мерж, изменивший пайплайн — `git log`.
2. Запуск сборки — лог CI (время, автор, ветка).
3. Выполнение подозрительного шага — job log.
4. Получение кред — CloudTrail/OIDC-аудит.
5. Развёртывание артефакта — деплой-лог, изменения в облаке.
6. Откат/удаление следов — аудит.

Каждый пункт — независимый источник; согласованный таймлайн доказывает атаку.

## Куда дальше

Мы закончили облачную ветку. Дальше можно вернуться к диску и памяти — или к другим
категориям дерева. А пока запомни: пайплайн с широкими правами — это «легальный» путь
атакующего в облако.

## Где пригодится

- **Cloud Security** — аудит CI/CD как поверхности атаки.
- **DFIR / Incident Response** — расследование компрометации пайплайна.
- **CTF Forensics** — задачи с логами сборок.
