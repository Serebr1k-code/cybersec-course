## Вопрос, с которого всё начинается

У тебя есть образ диска и дамп памяти. Ты нашёл подозрительный процесс в памяти, подозрительный
файл на диске и подозрительное соединение в сетевом логе. Но по отдельности это три разрозненных
факта. Как понять, что это **одно** событие, и восстановить историю атаки целиком?

## Что такое cross-artifact корреляция

**Cross-artifact корреляция** — это объединение событий из разных артефактов в единую шкалу
времени и выявление связей между ними. Результат — **супер-таймлайн**: одна таблица, где
события из реестра, журналов, файловой системы, сети и памяти выстроены по времени.

Смысл в том, что каждый артефакт отвечает лишь на часть вопроса. Реестр знает о закреплении,
журнал — о входе, файловая система — о созданных файлах, сеть — о соединениях, память — о
процессах. Только вместе они дают историю.

## Наш пример: три артефакта, одно событие

Возьмём инцидент и соберём наблюдения:

```
Память:    процесс python3 /dev/shm/.index, PID 1842, старт 09:14:02
Диск:      файл /dev/shm/.index создан 09:13:58
Сеть:      соединение 10.0.0.5:44312 -> 203.0.113.9:443, начало 09:14:03
```

Три источника — три времени, но они складываются в одну историю: файл создан в 09:13:58,
через четыре секунды запущен процесс, через секунду он открыл соединение с внешним адресом.
Это не три события, а **один эпизод**.

## Как объединять: ключи корреляции

Чтобы связать события, нужны **ключи** — общие значения, по которым они совпадают:

- **PID** — связывает процесс в памяти с файлом и сетью;
- **путь файла** — связывает файловую систему с процессом;
- **время** — базовая ось для всех;
- **имя пользователя / SID** — связывает действия с человеком;
- **сетевой адрес** — связывает хост с внешним миром.

Пример ключа: PID 1842 встречается и в списке процессов, и в списке открытых файлов, и в
сетевых соединениях. Это и есть связка.

## Наш пример: связываем по PID

Пройдёмся по ключу:

```
Память:    PID 1842 -> python3 /dev/shm/.index
Файлы:     PID 1842 держит fd на /dev/shm/.index
Сеть:      PID 1842 владеет сокетом на 203.0.113.9:443
Журнал:    в 09:13:55 был вход по SSH с внешнего IP
```

Теперь картина полная: вход, создание файла, запуск процесса, соединение с C2. Каждый факт
подтверждён минимум одним источником, а вместе они образуют причинную цепочку.

## Порядок сборки

Собирать супер-таймлайн лучше по шагам:

1. **Привести время к UTC** и скорректировать дрейф.
2. **Выгрузить события** из каждого артефакта в единый формат (время, источник, событие).
3. **Объединить** в одну таблицу и отсортировать по времени.
4. **Отфильтровать шум** (нормальные системные события) по базовой линии.
5. **Связать** оставшиеся события по ключам.
6. **Проверить** на «невозможные» последовательности.

Инструменты вроде Plaso/log2timeline и Timesketch автоматизируют шаги 2–3, но шаги 4–6 —
работа аналитика.

## Что даёт корреляция

- **Полнота.** Ни один артефакт не даёт всей картины; вместе — дают.
- **Уверенность.** Факт, подтверждённый двумя источниками, весомее одного.
- **Причинность.** Видно не только «что», но и «почему».
- **Точки пропуска.** Видно, где данные отсутствуют — и это тоже вывод.

## Типичные ошибки

- **Смешивать пояса и игнорировать дрейф** — ломает порядок.
- **Смотреть артефакты по отдельности** — теряется связь.
- **Принимать совпадение по времени за связь.** Совпадение без ключа — не корреляция.
- **Забывать про отсутствующие данные.** Пропуск в логе — тоже сигнал.
- **Не фильтровать шум.** В супер-таймлайне миллионы строк, без фильтра он бесполезен.

## Что мы теперь знаем

- Cross-artifact корреляция объединяет события из разных источников в супер-таймлайн.
- Связывают события по ключам: PID, путь, пользователь, адрес, время.
- Порядок сборки: UTC → выгрузка → объединение → фильтр → связка → проверка.
- Совпадение по времени без ключа — ещё не связь.
- Инструменты автоматизируют сбор, но связка и выводы — за аналитиком.

## Формат супер-таймлайна

Чтобы объединять события из разных источников, их приводят к единому формату. Минимальный
набор полей:

| Поле | Значение |
|------|----------|
| timestamp | время в UTC |
| source | откуда событие (файл, журнал, дамп) |
| host | на каком хосте |
| user | под кем |
| event | что произошло |
| key | ключ корреляции (PID, путь, IP) |

Такой формат позволяет сортировать всё вместе и фильтровать по любому полю. Инструменты
вроде Plaso генерируют подобную структуру автоматически из десятков артефактов.

## Почему каждый артефакт частичен

Полезно понимать ограничения каждого источника, чтобы не ждать от него лишнего:

- **Реестр** знает о настройках и закреплении, но не о времени запуска процессов.
- **Журналы событий** знают о входах и службах, но не о содержимом файлов.
- **Файловая система** знает о созданных/изменённых файлах, но таймстемпы можно подделать.
- **Сеть** знает о соединениях, но не о том, что процесс делал локально.
- **Память** знает о живых процессах и соединениях, но только на момент снятия.

Отсюда вывод: **полнота достигается только совокупностью**. Пропуск любого слоя оставляет
дыру в картине, и её нужно честно отметить.

## Связь событий: пример с закреплением

Разберём, как корреляция вскрывает закрепление. Наблюдения из разных источников:

```
Реестр:    Run-ключ "Updater" -> C:\Users\Public\u.exe
Файлы:     C:\Users\Public\u.exe создан 11:02:10
Процессы:  u.exe запущен 11:05:00 (родитель explorer.exe)
Сеть:      u.exe -> 198.51.100.7:8443
```

По отдельности: ключ реестра (подозрительный), файл (неизвестный), процесс (запущен),
соединение (внешнее). Вместе — полная цепочка: закрепление создано, файл лежит, процесс
запущен, C2 установлен. Ключ корреляции — путь файла и PID процесса.

## Как отделять сигнал от шума

В супер-таймлайне миллионы событий, и большая часть — нормальная. Чтобы не утонуть:

- построй **базовую линию**: какие процессы, задачи, соединения типичны;
- фильтруй по **редкости**: редкое событие — кандидат;
- фильтруй по **времени**: окно вокруг подозрительного эпизода;
- фильтруй по **сущности**: конкретный пользователь, хост, процесс.

Хороший приём — начать с одного «якорного» события (подозрительный процесс) и раскручивать
связи вокруг него, а не просматривать всё подряд.

## Ограничения корреляции

Корреляция не всесильна. Она может:

- **объединить несвязанное** — если ключ совпал случайно (например, одинаковый PID в разное
  время);
- **пропустить связь** — если ключа нет (процесс завершился, следов не осталось);
- **ввести в заблуждение** — если таймстемпы подделаны.

Поэтому корреляцию всегда сопровождают **provenance** (откуда каждое событие) и оценкой
уверенности. Связь без обоснования — это гипотеза, а не факт.

## Мини-упражнение

Возьми два артефакта (например, историю команд и список процессов) и попробуй связать их
события по общему ключу. Определи, какие связи подтверждены, а какие — только по времени.
Отметь, где данных не хватает для уверенного вывода.

## Ключи корреляции: подробнее

Выбор ключа определяет, какие связи ты найдёшь. Разберём типовые ключи и что они связывают:

| Ключ | Связывает |
|------|-----------|
| PID | процесс ↔ файлы ↔ сокеты |
| путь | файл ↔ процесс ↔ реестр |
| SID/UID | действия ↔ учётная запись |
| IP:port | процесс ↔ внешний адрес |
| hostname | хост ↔ DNS ↔ логи |
| hash | файл ↔ база IOC |

Важно: ключ действует **в пределах времени жизни**. PID переиспользуется после завершения
процесса, IP выдаётся на время аренды. Поэтому связку всегда проверяют на пересечение
интервалов: если окна не пересекаются — ключ совпал случайно.

## Ручная корреляция: пример

Иногда инструментов под рукой нет, и связать события приходится вручную. Порядок:

```
$ grep -n "1842" proc.txt        # найти PID во всех артефактах
$ grep -n "/dev/shm/.index" *    # найти путь во всех артефактах
$ grep -n "203.0.113.9" *        # найти внешний адрес
```

Каждый `grep` вытаскивает строки, где встречается ключ. Собрав их вместе и отсортировав по
времени, ты получаешь ручной супер-таймлайн. Это медленнее автоматизации, но на маленьком
эпизоде часто быстрее, чем настраивать платформу.

## Почему совпадение по времени — не связь

Соблазн велик: два события в одну секунду «наверняка связаны». Но совпадение по времени без
общего ключа ничего не доказывает. В системе одновременно происходят тысячи событий, и часть
из них совпадёт случайно.

Правило: **связь обосновывается ключом**, а время лишь упорядочивает уже связанные события.
Если ключа нет, событие может быть «рядом», но не «вместе».

## Как проверять корреляцию

После сборки супер-таймлайна прогони проверки:

- у каждого ребра связи есть источник (provenance);
- временные окна пересекаются;
- нет «невозможных» последовательностей;
- ключ не переиспользовался между разными сущностями.

Эти проверки отсеивают ложные связи и делают вывод защищаемым. Без них красивый граф может
оказаться набором совпадений.

## Куда дальше

События связаны, но остаётся вопрос: кто именно стоит за действиями? Следующий урок —
**«Entity resolution: один человек под разными именами»**.

## Где пригодится

- **DFIR:** восстановление полной картины инцидента.
- **CTF Forensics:** задачи, где улики разбросаны по артефактам.
- **Threat Hunting:** связывание событий из разных систем.
- **Отчётность:** доказательная история вместо списка фактов.
