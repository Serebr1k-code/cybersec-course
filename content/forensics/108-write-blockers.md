## Вопрос, с которого всё начинается

С изъятого ноутбука нужно снять образ диска `sdb`. Технически просто: подключить и скопировать. Но есть ловушка: как только ты подключаешь диск к обычной операционной системе, она **начинает его менять** — обновляет время доступа, монтирует файловую систему и дописывает журнал, создаёт служебные файлы. Улика портится ещё до того, как ты её скопировал.

Как снять образ, не изменив оригинал ни на байт? Ответ — **write blocker**. Разберём процедуру на примере этого диска.

## Наш пример: диск `sdb` (120 ГБ)

Сначала убеждаемся, что диск ещё не смонтирован и не тронут системой:

```bash
$ lsblk -o NAME,SIZE,RO,TYPE,MOUNTPOINT
NAME   SIZE RO TYPE MOUNTPOINT
sdb    120G  0 disk
```

Колонка `MOUNTPOINT` пуста — диск не смонтирован. Колонка `RO` = `0` означает, что запись **разрешена** — это плохо, надо запретить.

## Шаг 1: включаем защиту от записи

**Write blocker** бывает аппаратный и программный. Аппаратный — отдельное устройство между диском и компьютером, которое пропускает только чтение и физически блокирует запись. Это стандарт судебной практики: он не зависит от драйверов и ошибок операционной системы.

Когда аппаратного нет, используют программную защиту — пометить блочное устройство «только для чтения»:

```bash
$ sudo blockdev --setro /dev/sdb
$ sudo blockdev --getro /dev/sdb
1
```

`--getro` вернул `1` — устройство теперь read-only. Но помни: программная защита слабее, она зависит от корректности хоста. Аппаратный блокиратор надёжнее, потому что не доверяет операционной системе вообще.

## Шаг 2: снимаем образ с хешами

Копируем диск побайтово. Обычный `dd` тут плох: он молча пропускает ошибки чтения и не считает хеши. Поэтому используют `dc3dd` — «форк» `dd` с прогрессом, хешами и логированием:

```bash
$ sudo dc3dd if=/dev/sdb of=/evidence/sdb.dd hash=sha256 log=/evidence/sdb.log
dc3dd 7.2.646 started at 2026-10-11 10:00:00
42949672960 bytes (40 G) copied, 1234.5 s, 34.8 M/s
```

Здесь `if` — источник (диск), `of` — файл образа, `hash=sha256` — считать хеш, `log` — журнал операции. В журнал попадают и ошибки чтения («bad sectors») — их обязательно прикладывают к отчёту.

## Шаг 3: верифицируем хеши

**Хеш** — это отпечаток содержимого. Если хоть один байт изменится, хеш станет другим. Ключевой шаг: хеши **источника** и **образа** должны совпасть.

```bash
$ cat /evidence/sdb.log | grep -i sha256
sha256 3f5a...c9  /dev/sdb
sha256 3f5a...c9  /evidence/sdb.dd
```

Значения одинаковы — доказано, что копия побайтово идентична диску. Если бы они разошлись, образ был бы негоден. Для суда используют SHA-256 (или оба хеша: MD5 + SHA-256).

## Шаг 4: выбираем формат образа

Сырой образ (`.dd`) — самый совместимый, но занимает полный размер диска. В судебной практике часто берут **EWF/E01** — формат с сжатием, разбиением на сегменты и встроенными хешами и метаданными:

```bash
$ ewfacquire /dev/sdb -t /evidence/sdb -f encase6 \
    -C "Case 2026-001" -D "sdb image" -E "Ivanov" -m fixed -M sha256 -c deflate
$ ewfinfo evidence.E01
```

`ewfacquire` принимает метаданные (номер дела, описание, имя эксперта), считает хеши и сжимает. Такой образ монтируется напрямую или конвертируется в raw:

```bash
$ ewfmount evidence.E01 /mnt/ewf
$ mmls /mnt/ewf/ewf1
```

Проверить целостность EWF можно встроенной командой `ewfverify evidence.E01`.

## Шаг 5: обрабатываем сбойные секторы

На реальных дисках бывают повреждённые секторы. `dd` на них спотыкается и может остановиться, поэтому для «больных» дисков используют `ddrescue` с многопроходным чтением:

```bash
$ sudo ddrescue -f -n /dev/sdb /evidence/sdb.dd /evidence/sdb.map
$ sudo ddrescue -f -r 3 /dev/sdb /evidence/sdb.dd /evidence/sdb.map
```

Первый проход (`-n`) быстро пропускает проблемные области, второй (`-r 3`) делает до трёх попыток на каждую. Файл `.map` хранит карту прочитанного, поэтому процесс можно продолжить после сбоя. Для деградирующих дисков лучше специализированное оборудование.

## Если что-то пошло не так

Несколько правил, нарушение которых обесценивает доказательство:

- **Никогда не пиши образ на тот же диск**, который снимаешь, и не на ту же файловую систему — это уничтожит улики.
- **SSD и TRIM**: твердотельные диски могут фоново «чистить» удалённые данные. Фиксируй время снятия и используй блокиратор, поддерживающий блокировку TRIM.
- **Не монтируй оригинал**: даже монтирование «только для чтения» может менять метаданные.
- **Фиксируй время** начала и конца в UTC, серийный номер и модель диска (`smartctl -i /dev/sdb`).

## Полный разбор: снятие образа с диска sdb

Соберём процедуру в один проход.

1. **Убеждаемся, что диск не смонтирован:** `lsblk` — у `sdb` нет точек монтирования.
2. **Включаем защиту от записи:** аппаратный блокер в разрыв кабеля (или `blockdev --setro /dev/sdb` как программный вариант для съёмных носителей).
3. **Проверяем read-only:** попытка записи должна завершиться ошибкой.
   ```bash
   $ sudo dd if=/dev/zero of=/dev/sdb bs=512 count=1
   dd: failed to open '/dev/sdb': Read-only file system
   ```
4. **Снимаем образ с хешами:**
   ```bash
   $ sudo dc3dd if=/dev/sdb of=disk.dd hash=sha256 log=disk.log
   ```
5. **Верифицируем:** хеш источника == хеш образа.
6. **Фиксируем формат** (RAW/E01/AFF) и заводим манифест.

## Шпаргалка форматов образов

| Формат | Плюс | Минус |
|--------|------|-------|
| RAW (dd) | простота, читается везде | размер = объём диска |
| E01 (EWF) | сжатие, метаданные, хеши внутри | нужен libewf |
| AFF | открытый, метаданные | меньше поддержки |
| VHDX | нативный для Hyper-V | не судебный стандарт |

Для суда чаще берут E01: внутри уже хранятся хеши и метаданные сегментов.

## Если что-то пошло не так

- **Диск смонтирован.** ОС пишет журнал даже при чтении — размонтируйте или используйте блокер.
- **Сбойные сектора.** `ddrescue` с картой ошибок: читает всё читаемое, помечает плохое.
- **Хеш не совпал.** Проверьте кабель/контроллер, повторите; не «списывайте» расхождение.
- **Нет аппаратного блокера.** Программный read-only лучше, чем ничего, но менее надёжен — фиксируйте это в отчёте.
- **Образ «завис» на 99%.** Возможно, диск уходит в offline при ошибке; используйте `ddrescue`.

## Что мы теперь знаем

- Подключение диска к обычной ОС меняет его; защита — **write blocker**.
- Программная защита — `blockdev --setro` (проверка `--getro` = 1); аппаратная надёжнее.
- Образ снимают с хешами (`dc3dd hash=sha256`); хеши источника и образа должны совпасть.
- EWF/E01 хранит сжатие, сегменты, хеши и метаданные; проверяется `ewfverify`.
- Сбойные секторы обрабатывают многопроходным `ddrescue` с картой.
- Образ нельзя писать на тот же носитель; время и серийник фиксируют.
