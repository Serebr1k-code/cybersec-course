Сбор образа — первый и самый ответственный шаг форензики. Ошибка здесь обесценивает всё дальнейшее: если носитель был изменён при снятии, доказательство недопустимо. **Write blocker** — устройство или режим, физически запрещающий запись на носитель, — ключевой элемент корректной процедуры.

## Зачем нужен write blocker

При подключении диска к обычной ОС она может: обновить access time, смонтировать ФС и записать журнал, просканировать и создать `System Volume Information`, изменить флаги «грязного» тома. Всё это **модифицирует оригинал**. Write blocker блокирует любые команды записи на уровне интерфейса (ATA/SATA/NVMe/USB), пропуская только чтение.

Виды:
- **Аппаратный** — отдельный девайс между диском и хостом (Tableau, WiebeTech). Наиболее надёжен, стандарт для судебной практики.
- **Программный** — режим ОС/драйвера: Linux `blockdev --setro`, макросы в ядре, `hdiutil` в macOS. Дешевле, но зависит от хоста.
- **Read-only адаптеры** — USB-SATA с аппаратной защитой записи.

```bash
# Программная защита (Linux): пометить устройство read-only ДО монтирования
sudo blockdev --setro /dev/sdb
sudo blockdev --getro /dev/sdb      # 1 = read-only

# Проверка, что носитель не смонтирован
lsblk -f
cat /proc/mounts | grep sdb
```

## Форматы образов и инструменты

| Формат | Инструмент | Особенность |
|--------|-----------|-------------|
| RAW/DD | `dd`, `dc3dd`, `dcfldd` | побайтовая копия, самый совместимый |
| EWF/E01 | `ewfacquire` (libewf) | сжатие + метаданные + хеши внутри |
| AFF | `affconvert` | открытый формат с сегментами |
| AFF4 | `aff4` | современный, гибкий |

```bash
# RAW с хешами и логом
sudo dc3dd if=/dev/sdb of=/evidence/sdb.dd hash=md5,sha256 log=/evidence/sdb.log

# EWF с метаданными (эксперт, кейс, описание)
ewfacquire /dev/sdb -t /evidence/sdb -f encase6 -C "Case 2024-001" \
  -D "sdb image" -E "Ivanov" -e "case2024" -m fixed -M md5,sha256 -c deflate

# Проверить образ на ошибки чтения
dc3dd if=/dev/sdb of=/dev/null hash=md5 2>&1 | tail

# Снять только нераспределённое/занятое (осторожно: не для суда)
# — не рекомендуется как основной метод
```

`dc3dd`/`dcfldd` — форки `dd` с прогрессом, хешами и логированием; `dd` без них легко «забывает» показать ошибки чтения.

## Работа с EWF

EWF/E01 — стандарт в судебной практике: сжатие, разбиение на сегменты (E01, E02…), встроенные хеши и метаданные. Монтировать можно напрямую.

```bash
ewfinfo evidence.E01                  # метаданные, хеши
ewfmount evidence.E01 /mnt/ewf        # появятся ewf1
mmls /mnt/ewf/ewf1                    # работаем как с raw
# или конвертировать
ewfexport evidence.E01 -t out -f raw
```

## Разобранный пример: корректный сбор

```bash
$ lsblk -o NAME,SIZE,RO,TYPE,MOUNTPOINT
NAME   SIZE RO TYPE MOUNTPOINT
sdb    120G  0 disk
$ sudo blockdev --setro /dev/sdb
$ sudo blockdev --getro /dev/sdb
1
$ sudo dc3dd if=/dev/sdb of=/evidence/sdb.dd hash=sha256 log=/evidence/sdb.log
dc3dd 7.2.646 started at 2026-10-11 10:00:00
...
42949672960 bytes (40 G) copied, 1234.5 s, 34.8 M/s
$ cat /evidence/sdb.log | grep -i sha256
sha256 3f5a...c9  /dev/sdb
sha256 3f5a...c9  /evidence/sdb.dd
```

Хеш источника и образа совпадают — доказано, что копия идентична. Лог с ошибками чтения (`bad sectors`) прикладывается к отчёту.

## Краевые случаи и подводные камни

- **Смонтированный носитель нельзя копировать.** Даже «только для чтения» монтирование может менять метаданные; снимайте с raw-устройства, а не с точки монтирования.
- **SSD и TRIM.** SSD могут «чистить» удалённые данные фоново (garbage collection) и при TRIM — образ может не содержать то, что было ещё вчера. Фиксируйте время снятия.
- **Bad sectors.** `dd` молча пропускает ошибки; используйте `dc3dd`/`ddrescue` с логом. `ddrescue` умеет многопроходное чтение.
- **Несколько проходов.** Для повреждённых дисков: сначала быстрый проход (skip bad), потом дозаполнение (`ddrescue -r 3`).
- **Хеш-алгоритм.** MD5 достаточно для целостности, но для суда лучше SHA-256 (или оба).
- **Образ на том же диске.** Никогда не пишите образ на носитель, который снимаете, и не на ту же ФС, что может перезаписать улики.
- **Метки времени.** Фиксируйте время начала/конца снятия, часовой пояс, состояние питания.
- **Шифрование при снятии.** Если диск зашифрован, вы снимаете шифротекст; нужен ключ для дальнейшего анализа.

## Аппаратные write blockers в деталях

Аппаратный write blocker ставится **между** носителем и хостом и работает на уровне интерфейса. Он пропускает команды чтения и блокирует любые команды записи — независимо от того, что пытается сделать ОС. Это делает процедуру воспроизводимой и не зависящей от версии драйверов хоста.

Варианты исполнения:

- **SATA/IDE блокеры** (Tableau T35u, T356789) — для внутренних дисков.
- **USB-блокеры** — для флешек и внешних дисков.
- **NVMe/PCIe блокеры** — для современных SSD.
- **Read-only адаптеры** (например, USB-to-SATA с переключателем) — дешевле, но не всегда гарантируют защиту на всех уровнях.

Важный нюанс: **write blocker должен поддерживать TRIM/DISCARD-блокировку**. Иначе SSD может «оптимизировать» данные по команде хоста и уничтожить удалённые улики.

## Программная защита записи

Когда аппаратного блокера нет, используют программную защиту — но она слабее и зависит от корректности хоста.

```bash
# Linux: пометить блочное устройство read-only
sudo blockdev --setro /dev/sdb
sudo blockdev --getro /dev/sdb          # ожидаем 1

# Проверить, что ничего не смонтировано
findmnt | grep sdb || echo "not mounted"
# Отключить automount (systemd) на время работы
sudo systemctl stop udisks2 2>/dev/null || true

# dmesg: убедиться, что устройство не изменило режим
dmesg | tail -5
```

Дополнительно: загрузка с forensic-дистрибутива (CAINE, Tsurugi, Kali) даёт политику «не монтировать автоматически» и набор инструментов.

## Процедура сбора: пошагово

1. **Документирование.** Фото носителя, серийный номер, состояние, время, кто присутствовал.
2. **Изоляция.** Не подключать к рабочей ОС; использовать write blocker или forensic-стенд.
3. **Идентификация.** `lsblk`, `smartctl -a`, размер в байтах.
4. **Снятие.** `dc3dd`/`ewfacquire` с хешами и логом.
5. **Верификация.** Сравнить хеши источника и образа; при EWF — `ewfverify`.
6. **Хранение.** Оригинал — в пломбе; образ — на защищённом носителе с копиями.
7. **Отчёт.** Лог снятия, хеши, ошибки чтения, время.

```bash
# Верификация EWF
ewfverify evidence.E01
# Верификация raw
sha256sum /dev/sdb /evidence/sdb.dd
```

## Обработка ошибок чтения

Повреждённые секторы — норма для реальных дисков. Стратегия многопроходного чтения:

```bash
# ddrescue: сначала быстро пропустить bad, потом дозаполнить
sudo ddrescue -f -n /dev/sdb /evidence/sdb.dd /evidence/sdb.map
sudo ddrescue -f -r 3 /dev/sdb /evidence/sdb.dd /evidence/sdb.map
```

`-n` — первый проход без повторных попыток (быстро), `-r 3` — до 3 попыток на проблемный блок. Карта (`.map`) сохраняет, что уже прочитано, и позволяет продолжить после сбоя. Помните: каждый проход может немного «нагружать» носитель, поэтому для деградирующих дисков лучше специализированное оборудование (PC-3000).

## Правовые и процессуальные аспекты

- **Цепочка сохранности** должна документировать каждое перемещение носителя и образа.
- **Хеши** — обязательны; их фиксируют в отчёте и сверяют при каждой передаче.
- **Копии** — оригинал не анализируют; работают с верифицированными копиями.
- **Полномочия** — сбор должен быть санкционирован; для CTF это формальность, для суда — критично.
- **Журнал действий** — что делали, чем, когда; это защищает от обвинений в порче доказательств.

## Типичные ошибки

- **Автомонтирование при подключении.** Даже «посмотреть» диск может изменить его.
- **`dd` без лога.** Ошибки чтения останутся незамеченными.
- **Один проход на битом диске.** Нужен многопроходный `ddrescue`.
- **Хеш только образа.** Сверяйте с источником (или встроенным хешем EWF).
- **Запись образа на тот же диск.** Уничтожает улики.
- **Игнорирование TRIM.** SSD может «почистить» данные до снятия.

## Логирование снятия и отчётность

Даже если вы не пишете судебный отчёт, фиксируйте процедуру. Минимальный набор в логе:

- устройство и его серийный номер (`smartctl -i /dev/sdb`);
- размер в байтах (точно, не «120 ГБ»);
- время начала и конца (UTC и локальное, с указанием пояса);
- применённые хеши и их значения для источника и образа;
- число и адреса сбойных секторов (`ddrescue`/`dc3dd` лог);
- инструмент и его версия.

```bash
smartctl -i /dev/sdb | grep -Ei 'serial|model|capacity'
date -u +%FT%TZ
dc3dd if=/dev/sdb of=/evidence/sdb.dd hash=sha256 log=/evidence/sdb.log
```

Такой лог делает результат воспроизводимым: другой аналитик может повторить снятие и получить тот же хеш.

## Чек-лист корректного снятия

1. Носитель не смонтирован, automount отключён.
2. Включён write blocker (аппаратный или `blockdev --setro`).
3. Зафиксированы модель/серийник/размер (`smartctl -i`).
4. Снятие с хешами и логом (`dc3dd`/`ewfacquire`).
5. Ошибки чтения обработаны (`ddrescue`), карта сохранена.
6. Хеши источника и образа совпали.
7. Оригинал опечатан, образ сохранён в двух копиях.
8. Процедура задокументирована и подписана.

Нарушение любого пункта снижает ценность доказательства; в судебной практике — может сделать его недопустимым.

## Что дальше / решение

1. Убедиться, что носитель **не смонтирован** (`lsblk`, `/proc/mounts`).
2. Включить защиту записи (аппаратный блокер; `blockdev --setro`).
3. Снять образ с хешами и логом (`dc3dd`/`ewfacquire`).
4. Проверить хеши источника и образа.
5. Задокументировать процедуру и передать образ аналитику.

Дальше — `forensics-disk-imaging` (техника образов) и `forensics-evidence-handling` (обращение с доказательствами).
