## Вопрос, с которого всё начинается

Ты получил извлечение с iPhone. Нужно понять, что происходило на устройстве: какие
приложения запускались, куда ходили в сеть, были ли попытки подбора пароля. На iOS для
этого есть **unified log** — та же система, что на macOS, но со своими особенностями
хранения и извлечения.

## Что такое unified log в iOS

iOS использует **ту же подсистему unified logging**, что и macOS (tracev3-файлы). Журнал
хранится на устройстве:

- **`/var/db/diagnostics/`** — основные `*.tracev3`-файлы;
- **`/var/db/uuidtext/`** — строки и метаданные (timesync, по UUID);
- **`/var/db/diagnostics/Persist/`** — долгоживущие записи.

Отличие от macOS — в способе **извлечения**: на iPhone нельзя просто скопировать файлы без
джейлбрейка или полного извлечения. Основной источник — **sysdiagnose** (диагностический
пакет, который пользователь может сформировать сам) или данные из полного образа.

## Наш пример: logarchive с iPhone

```
$ ls -la
drwxr-xr-x 1 student student 4096 ios.logarchive
$ ls ios.logarchive/
logdata.LiveData.tracev3  timesync  uuidtext
$ file ios.logarchive/logdata.LiveData.tracev3
...: Apple Unified Logging tracev3 file
```

Структура та же, что на macOS. Смотрим метки:

```
$ strings ios.logarchive/logdata.LiveData.tracev3 | grep -Ei 'subsystem|process|nto'
subsystem=com.apple.network
process=Safari
subsystem=com.apple.securityd
EVIDENCE: nto{10s_un1f13d_l0g_tr4c3v3}
```

Видно подсистемы (сеть, безопасность) и процесс Safari. Для полного разбора нужен парсер.

## Шаг 1: чем iOS отличается от macOS

| Аспект | macOS | iOS |
|--------|-------|-----|
| Формат | tracev3 | tracev3 (тот же) |
| Извлечение | копирование файлов | sysdiagnose / полный образ |
| Парсер | log show, macos-unifiedlogs | те же |
| Приватность | `<private>` | `<private>` |
| Доступ | обычно есть root | нужен джейлбрейк/извлечение |

Главное практическое отличие: на iOS **извлечь журнал сложнее**, и часто он приходит уже
в виде `sysdiagnose`-архива или внутри полного извлечения.

## Шаг 2: sysdiagnose

**sysdiagnose** — диагностический пакет, содержащий логи, состояние системы и часть
unified log. Формируется комбинацией кнопок (на новых устройствах — громкость + кнопки) или
через настройки. Внутри:

- **`system_logs.logarchive/`** — собственно unified log;
- **`logs/`** — дополнительные журналы;
- **`crashes/`** — отчёты о падениях;
- **`powerlogs/`** — энергопотребление.

sysdiagnose ценен тем, что **не требует джейлбрейка** и его может сделать сам пользователь —
это частая точка сбора при расследовании.

## Шаг 3: разбор

Инструменты те же, что для macOS:

- **`log show --archive system_logs.logarchive`** (на macOS);
- **macos-unifiedlogs** (Python, кроссплатформенный);
- **UnifiedLogReader**;
- коммерческие пакеты (Cellebrite, Magnet AXIOM) с встроенными парсерами.

Пример:

```
$ log show --archive ios.logarchive --predicate 'process == "Safari"' --info | tail -3
2026-03-11 02:14:09.123  Safari  subsystem=com.apple.network  connection to 203.0.113.9:443
```

## Шаг 4: что искать

- **Запуски приложений** (`process`) — активность ПО;
- **Сетевые соединения** (`com.apple.network`) — контакты с адресами;
- **События безопасности** (`com.apple.securityd`, `com.apple.security`) — разблокировки,
  доступ к ключам;
- **Сбои и краши** (`com.apple.crashreporter`) — падения;
- **Подсистемы сторонних приложений** — нестандартные `com.*`.

Особенно ценно для расследования **попыток разблокировки** и **подключения к сети** —
это прямой след действий пользователя/атакующего.

## Шаг 5: ограничения и приватность

- **`<private>`** — поля скрыты; без профиля логирования текст не виден;
- **кольцевой буфер** — старые записи перезаписываются (обычно хранится несколько дней);
- **объём** — фильтруй по времени и процессу;
- **шифрование бэкапа** — часть журналов доступна только в расшифрованном извлечении.

Фиксируй эти ограничения: отсутствие события не доказывает его отсутствие.

## Мини-практика: найти сетевую активность

```
$ log show --archive ios.logarchive --predicate 'subsystem == "com.apple.network"' --info | tail -2
2026-03-11 02:14:09.123  Safari  connection to 203.0.113.9:443
2026-03-11 02:14:10.500  unknown  connection to 198.51.100.7:8443
$ grep -a 'com.apple.securityd' ios.logarchive/logdata.LiveData.tracev3
com.apple.securityd
```

Мы нашли соединения Safari и подозрительное соединение неизвестного процесса. Дальше —
сопоставить с временем инцидента.

## Частые ошибки и подводные камни

- **Читать tracev3 через strings.** Полный текст не виден — нужен парсер и uuidtext.
- **Ждать файлы без извлечения.** На iPhone их не скопировать без джейлбрейка.
- **Игнорировать `<private>`.** Часть данных скрыта.
- **Не фильтровать.** Журнал огромен.
- **Путать sysdiagnose и полный образ.** Это разные источники с разным покрытием.

## Что мы теперь знаем

- iOS использует unified logging (tracev3) — как macOS.
- Журнал лежит в `/var/db/diagnostics`; извлекается через sysdiagnose или образ.
- Парсеры: `log show`, macos-unifiedlogs, UnifiedLogReader, коммерческие пакеты.
- Полезные данные: запуски процессов, сетевые соединения, безопасность.
- Ограничения: `<private>`, кольцевой буфер, объём.

## Что фиксировать в отчёте

| Что | Зачем |
|-----|-------|
| Источник (sysdiagnose/образ) | покрытие |
| Диапазон журнала | ограничения |
| Процессы и соединения | активность |
| События безопасности | разблокировки/доступ |
| Поля `<private>` | оговорка |

## Расширенный пример: анализ активности приложения

Разберём, как по unified log восстановить действия подозрительного приложения на iPhone.
Пусть есть `sysdiagnose` с журналом за нужные сутки.

1. **Открываем журнал**: `log show --archive system_logs.logarchive`.
2. **Фильтруем по процессу**: `--predicate 'process == "SuspiciousApp"'` — все события
   приложения.
3. **Смотрим сеть**: `subsystem == "com.apple.network"` и тот же процесс — куда ходил.
4. **Ищем доступ к данным**: события `com.apple.securityd` — обращения к ключам.
5. **Проверяем краши**: `com.apple.crashreporter` — падения (иногда malware «сыпется»).

Типичный результат: приложение запускается в 02:14, соединяется с внешним IP, читает
данные и пишет во временный каталог. По этим событиям строится таймлайн и делается вывод
о поведении.

Важно: **`<private>`** может скрывать URL и содержимое. Если в организации включён профиль
подробного логирования, поля будут видны; иначе — только факт соединения и IP.

## sysdiagnose vs полное извлечение

Два основных источника журнала дают разное покрытие:

| Источник | Плюсы | Минусы |
|----------|-------|--------|
| sysdiagnose | без джейлбрейка, делает пользователь | короче окно, не всё |
| Полный образ | максимум данных | нужен джейлбрейк/доступ |
| iCloud-бэкап | часть логов и данных | ограничено, шифрование |

**sysdiagnose** удобен, когда нужно быстро собрать данные и нет полного доступа: его может
сформировать сам пользователь, и он содержит unified log, краши и часть системных журналов.
**Полный образ** даёт больше (включая данные приложений), но требует либо джейлбрейка, либо
инструментов вроде Cellebrite/GrayKey, зависящих от версии iOS.

При расследовании комбинируй: sysdiagnose даёт быстрый снимок, образ — глубину. В отчёте
указывай **источник и окно** журнала, потому что от этого зависит, какие выводы корректны.

## Чек-лист разбора iOS unified log

1. Получи **источник**: sysdiagnose или полное извлечение.
2. Найди `system_logs.logarchive` (или `diagnostics` + `uuidtext`).
3. Сузь окно по **времени** и **процессу**.
4. Ищи **сетевые соединения**, **запуски**, **события безопасности**.
5. Отметь **сторонние подсистемы**.
6. Зафиксируй **поля `<private>`** как ограничение.

## Ограничения и типичные сложности

iOS-журнал даёт много, но с оговорками:

- **кольцевой буфер** — обычно хранится несколько дней; старые записи перезаписаны;
- **`<private>`** — чувствительные поля скрыты без профиля подробного логирования;
- **объём** — журнал большой, работай фильтрами;
- **шифрование извлечения** — часть журналов доступна только в расшифрованном виде;
- **разные версии iOS** — набор подсистем и формат могут отличаться.

Практический вывод: unified log — мощный, но **неполный** источник. Его всегда дополняют
данными приложений, keychain и системными артефактами. А отсутствие события в журнале не
означает, что его не было — возможно, оно просто не попало в окно хранения.

## Что писать в отчёте

Отчёт по iOS-журналу фиксирует **источник** (sysdiagnose или образ), **окно** журнала,
**список процессов и соединений**, **события безопасности** и **ограничения** (`<private>`,
кольцевой буфер). Если анализ опирается на конкретные события, приведи их время и процесс.
И укажи, что журнал — лишь часть картины: выводы подтверждаются данными приложений и
системными артефактами.

## Структура tracev3: catalog, chunks и uuidtext

tracev3 — не «текстовый лог», а бинарный контейнер. Полезно понимать его слои, чтобы осознать,
почему `strings` почти бесполезен:

- **Catalog** — каталог событий: хранит индекс записей и ссылки на их метаданные.
- **Chunks** — блоки сжатых событий (данные сообщений); каждое событие лежит в чанке.
- **uuidtext** — словарь строк и метаданных по UUID подсистемы/процесса. Имена подсистем и
  формат-строки вынесены сюда, чтобы не дублировать их в каждом событии.

Именно поэтому для полного разбора нужны **оба** каталога: `diagnostics` (события) и
`uuidtext` (строки). Без uuidtext парсер не сможет подставить имена подсистем, и в выводе
будут UUID вместо читаемых строк. Парсеры (`macos-unifiedlogs`, `UnifiedLogReader`) умеют
объединять их автоматически — поэтому при извлечении всегда копируй обе папки целиком.

```bash
$ python3 -m macos_unifiedlogs /evidence/ios.logarchive --output out.csv
$ head -2 out.csv
timestamp,process,subsystem,message
2026-03-11 02:14:09.123,Safari,com.apple.network,"connection to 203.0.113.9:443"
```

## Приватность: как «раскрыть» поля `<private>`

По умолчанию iOS помечает чувствительные значения (URL, имена файлов, IP) как `<private>`.
Но есть механизм, который заставляет систему **показывать их в открытом виде** — профиль
**verbose logging** (в организациях — конфигурационный профиль с включённым подробным
логированием для нужных подсистем). Если профиль был установлен **до** сбора журнала, поля
видны; если нет — восстанавливать их нечем.

Практический вывод для расследования: перед анализом проверь, был ли на устройстве профиль
подробного логирования. Это меняет выводы кардинально — «соединение с IP» против «соединение
с конкретным URL». Зафиксируй в отчёте, что часть полей скрыта `<private>`, иначе легко
переоценить полноту данных.

## Сведение unified log в таймлайн с другими артефактами

Unified log ценен в связке. Типовой таймлайн мобильного инцидента:

| Источник | Что добавляет |
|----------|---------------|
| unified log | запуски процессов, соединения, события безопасности |
| keychain | сохранённые токены и пароли приложения |
| данные приложения (`/var/mobile/Containers`) | кэш, БД, файлы |
| `knowledgeC.db` | активность пользователя и приложений по времени |
| powerlogs (в sysdiagnose) | пробуждения и фоновая активность |

Порядок работы: из unified log берём «когда» и «что» (время и процесс), из keychain —
«с чем» (токены), из данных приложения — «какие файлы». Сопоставив время события в журнале с
записью в `knowledgeC.db`, можно доказать, что приложение было **на переднем плане** в момент
подозрительной сетевой активности. Одиночный журнал такого вывода не даёт.
