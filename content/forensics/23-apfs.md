## Вопрос, с которого всё начинается

Тебе дали образ `mac.dd` с MacBook. Нужно понять: что на него скачали и как
злоумышленник закрепился? На Linux привычные инструменты не видят ни одного знакомого
раздела. Что это за файловая система и как её читать?

Ответ — **APFS** (Apple File System), современная ФС всех устройств Apple. У неё
необычное устройство, и в этом уроке мы пройдём образ от монтирования до артефактов.

## Наш пример: mac.dd

Смотрим начало образа:

```bash
$ xxd -l 16 mac.dd
00000000: 4e58 5342 0000 0000 ...   NXSB....
```

Сигнатура `NXSB` (container superblock) говорит: перед нами **APFS-контейнер**.

## Шаг 1: контейнер, а не том

Главное отличие APFS: это не «раздел с файлами», а **контейнер** — пул блоков, внутри
которого лежит несколько **томов**. Обычно это тома `System`, `Data`, `Preboot`,
`Recovery`, `VM`, и они делят место динамически. Поэтому в `fdisk` «раздел» macOS
выглядит странно: раздел один, а томов внутри много.

## Шаг 2: монтируем на Linux

```bash
$ sudo apfs-fuse mac.dd /mnt/apfs
$ ls /mnt/apfs
```

`apfs-fuse` — драйвер, который монтирует APFS-образ в режиме только для чтения. Если
томов несколько, нужный выбирают опцией `-o vol=N`.

## Шаг 3: откуда скачан файл

У macOS есть атрибут **quarantine** — метка, которую система ставит каждому
скачанному файлу. Она хранит, чем файл скачан и когда:

```bash
$ getfattr -d /mnt/apfs/Users/bob/Downloads/malware.app
user.com.apple.quarantine="0083;5f8a1b2c;Safari;..."
```

`Safari` в атрибуте означает, что файл пришёл из браузера. Так мы отвечаем на вопрос
«откуда он взялся», даже не заходя в историю браузера.

## Шаг 4: как закрепились

Ищем автозапуск — у macOS это **LaunchAgents** (агенты пользователя) и **LaunchDaemons**
(системные):

```bash
$ ls /mnt/apfs/Users/bob/Library/LaunchAgents/
com.evil.updater.plist
$ plutil -p /mnt/apfs/Users/bob/Library/LaunchAgents/com.evil.updater.plist
{ "ProgramArguments" => [ "/Users/bob/Library/evil/run.sh" ] }
```

`plist` — это формат настроек Apple (аналог реестра), а `plutil -p` печатает его
читаемо. Агент запускает `run.sh` при входе пользователя — классическая персистентность.

## Шаг 5: подтверждаем запуск

События macOS пишет **Unified Log** — единый системный журнал:

```bash
$ unifiedlog_parser /mnt/apfs/var/db/diagnostics/*.tracev3 | grep -i evil | head
```

Журнал подтверждает, что процесс действительно запускался. Так три независимых
артефакта — quarantine, LaunchAgent и Unified Log — складываются в одну картину.

## Шаг 6: снапшоты — золотая жила

APFS использует **copy-on-write** (COW): изменение блока создаёт новую версию, а старая
остаётся в предыдущем checkpoint. А **снапшоты** (Time Machine, локальные) фиксируют
состояние тома. Значит, удалённый файл может сохраниться в снапшоте, снятом до удаления.

```bash
$ tmutil listlocalsnapshots /
com.apple.TimeMachine.2024-03-01-120000.local
$ fsapfsinfo -H mac.dd | grep -i snapshot
```

Для офлайн-образа снапшоты извлекают через `apfs-fuse`/`libfsapfs` и сравнивают
содержимое с текущим томом — так находят удалённое.

## Шаг 7: HFS+ и шифрование

APFS пришла на смену **HFS+** (старая ФС Apple), где данные лежат в B-tree каталоге и
удалённые записи живут там до переиспользования:

```bash
$ hfsutils
hfs> mount disk.img
hfs> ls
```

А **FileVault** шифрует том целиком. Без пароля или recovery key данные недоступны.
Ключ иногда лежит в конфигах, iCloud-бэкапах или памяти — его стоит поискать, прежде
чем считать образ «нечитаемым».

## Шаг 8: объектная карта и разбор томов

Внутри контейнера APFS есть **OMAP** (object map) — таблица соответствия виртуальных
адресов томов физическим блокам. Каждый том имеет суперблок `APSB` и своё B-tree с
записями (inode, каталоги, extents). Когда `apfs-fuse` не справляется с повреждённым
образом, эти структуры читают вручную:

```bash
$ fsapfsinfo mac.dd                 # список томов и их UUID
$ fsapfsinfo -H mac.dd | grep -i snapshot
```

## Шаг 9: Time Machine и версии файлов

Time Machine на APFS хранит не копии целиком, а **локальные снапшоты** тома `Data`.
Версии файлов лежат в старых снапшотах и доступны офлайн — удалённый файл может
существовать в снимке, сделанном до удаления:

```bash
$ mkdir /tmp/snap && mount_apfs -s com.apple.TimeMachine.2024-03-01-120000.local / /tmp/snap
$ ls /tmp/snap/Users/bob/Documents/
```

## Шаг 10: ключи и шифрование

APFS шифрует на трёх уровнях: контейнера, тома и отдельного файла. Ключи лежат в
**keybag** — структуре в начале контейнера, защищённой паролем пользователя или Secure
Enclave. Если том не зашифрован, данные читаются напрямую:

```bash
$ diskutil apfs list | grep -i encrypted
$ apfs-fuse -o pass=SECRET mac.dd /mnt/apfs
```

## Шаг 11: сравнение с HFS+

| Свойство | HFS+ | APFS |
|----------|------|------|
| Структура | B-tree (catalog/extents) | OMAP + B-tree на том |
| Снапшоты | ограниченные | встроены (Time Machine) |
| Шифрование | FileVault 2 | многоуровневое |
| Удаление | запись в B-tree | COW, старая версия в checkpoint |
| Инструмент | `hfsutils`, `hfsplus` | `apfs-fuse`, `libfsapfs` |

COW означает, что «удалённые» данные APFS живут дольше: старые версии блоков остаются
в предыдущих checkpoint, пока их не перезапишут новые.

## Шаг 12: другие артефакты macOS

Кроме Unified Log и LaunchAgents, на macOS есть ещё несколько источников:

| Артефакт | Путь | Что даёт |
|----------|------|----------|
| FSEvents | `.fseventsd/` | журнал изменений файлов |
| Spotlight | `.Spotlight-V100/` | метаданные и история поиска |
| plist | `~/Library/Preferences/*.plist` | настройки и история приложений |
| Keychain | `~/Library/Keychains/login.keychain-db` | пароли, сертификаты |

```bash
$ plistutil -i Info.plist -o out.xml   # plist в читаемый XML
$ fseventsparse /mnt/apfs/.fseventsd   # события файловой системы
```

FSEvents покажет, какие файлы менялись и когда, а plist — настройки приложений. Вместе с
Unified Log они закрывают почти все вопросы о поведении пользователя. Spotlight хранит
метаданные файлов, в том числе уже удалённых, поэтому его база `.store.db` — тоже
источник. А Keychain без пароля пользователя зашифрован, но при его наличии даёт
сохранённые пароли приложений и сертификаты.

## Что мы теперь знаем

- APFS — контейнер с несколькими томами, а не один раздел.
- `apfs-fuse` монтирует образ только для чтения на Linux.
- quarantine хранит источник загрузки файла, LaunchAgents — персистентность.
- Unified Log подтверждает события, снапшоты хранят старые версии файлов.
- FileVault шифрует том; без ключа данные недоступны.

## На что смотреть дальше

- **Не путать контейнер и том** — монтируйте нужный том, а не первый попавшийся.
- **Не монтировать rw** — COW создаст новые версии блоков и изменит образ.
- **Игнорировать снапшоты** — самая частая потеря: удалённое часто есть в снапшоте.
- **Забыть про Unified Log** — основной источник событий на macOS.

## Разбор container superblock (NXSB)

Монтирование через `apfs-fuse` скрывает внутреннее устройство, но когда образ повреждён или зашифрован, приходится читать структуры руками. Начинается всё с **container superblock** — блока 0 с сигнатурой `NXSB`:

```bash
$ xxd -l 64 mac.dd
00000000: 4e58 5342 0000 0000 0000 0000 0000 0000  NXSB............
00000010: 0000 0000 0000 0000 0000 0000 0000 0000  ................
```

Разберём ключевые поля (смещения условны, зависят от версии структуры):

| Поле | Смысл |
|---|---|
| `nx_magic` | `NXSB` — признак container superblock |
| `nx_block_size` | размер блока, обычно 4096 |
| `nx_block_count` | число блоков в контейнере |
| `nx_xid` | номер транзакции — монотонно растёт при каждом checkpoint |
| `nx_omap_oid` | OID объектной карты контейнера |
| `nx_fs_oid[]` | список томов (volume superblocks) |
| `nx_uuid` | идентификатор контейнера |
| `nx_xp_desc_base` | где искать область описаний checkpoint |

Главное поле — `nx_xid`. APFS постоянно пишет **checkpoint** (контрольные точки): при каждом изменении создаётся новая версия метаданных, и все суперблоки-копии размечены своим `xid`. Валидным считается суперблок с **наибольшим** `xid`, прошедший проверку контрольной суммы. Это и есть механизм восстановления: если «свежий» суперблок побит, откатываются к предыдущему checkpoint.

## Проверка целостности: Fletcher-64 и xid

У каждого объекта APFS первые 8 байт — **контрольная сумма Fletcher-64**, затем идёт заголовок объекта:

| Смещение | Поле | Смысл |
|---|---|---|
| 0x00 | `o_cksum` | Fletcher-64 от остального объекта |
| 0x08 | `o_oid` | идентификатор объекта |
| 0x10 | `o_xid` | транзакция, в которой объект создан |
| 0x18 | `o_type` | тип объекта (суперблок, B-tree, OMAP и т. д.) |
| 0x1c | `o_subtype` | подтип |

Практический приём: прежде чем доверять структуре, пересчитай Fletcher-64. Если сумма не сходится, блок повреждён или подделан — читать из него дальше бессмысленно. Сравнение `o_xid` у нескольких копий метаданных даёт ответ на вопрос «какая из них свежее» и позволяет собрать непротиворечивую картину, даже если часть блоков потеряна.

## Что делать, если образ не монтируется

Типичные причины и порядок действий. Во-первых, `apfs-fuse` может не понять **несколько томов** — перечисли их через `fsapfsinfo mac.dd`, найди нужный по UUID/имени и монтируй с `-o vol=N`. Во-вторых, образ может быть **зашифрован FileVault** — тогда без пароля или recovery key данные недоступны; ключ ищут в keybag, iCloud-бэкапах и памяти, но угадывать пароль онлайн против FileVault бессмысленно. В-третьих, том может быть «снят» в состоянии **checkpoint-незавершённой транзакции** — тогда помогает выбор более старого суперблока по `xid`.

Отдельная ловушка — **сжатие прозрачных файлов**: APFS умеет хранить файл в сжатом виде, и при монтировании на Linux декомпрессия может не сработать, дав пустой или битый файл. В таких случаях содержимое достают из resource fork вручную. И последнее: монтируй образ **только для чтения** (`-o ro` или копию образа), потому что любой инструмент, «дописывающий» метаданные, меняет `xid` и уничтожает доказательственную ценность исходника.

## Куда дальше

Мы разобрали macOS. Но самый частый объект расследований — Windows, и там почти каждое
действие оставляет след в **реестре**. В следующем уроке мы разберём кусты SAM, SYSTEM,
SECURITY и NTUSER.DAT и вытащим из них хеши и автозапуск. А пока запомни: **APFS хранит
старые версии данных дольше обычных ФС — проверь снапшоты**.
