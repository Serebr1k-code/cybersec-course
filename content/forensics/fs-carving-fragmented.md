## Вопрос, с которого всё начинается

Ты разбираешь сырой дамп диска без метаданных — только байты. Файл точно был, его
сигнатура в дампе есть, но простой «поиск начала и конца» даёт мусор: картинка
восстанавливается наполовину, документ не открывается. Причина — **фрагментация**: файл
разбит на куски, разбросанные по диску.

## Что такое carving

**File carving** («вырезание файлов») — восстановление файлов **без опоры на метаданные**,
только по содержимому. Основной приём — **biphasic carving**: ищем **сигнатуру заголовка**
(header, например `\xFF\xD8\xFF` для JPEG) и **сигнатуру конца** (footer, `\xFF\xD9`).
Всё, что между ними, — файл.

Наивный carving работает, пока файл лежит **непрерывно**. Но файловые системы размещают
данные блоками и **фрагментируют** крупные файлы: первый блок здесь, второй — через
мегабайт. Тогда biphasic carving «склеит» чужие байты между блоками и получит битый файл.

## Наш пример: дамп с фрагментами

```
$ ls -la
-rw-r--r-- 1 student student 16777216 dump.bin
$ file dump.bin
dump.bin: data
```

`file` не опознаёт — это сырой дамп. Ищем сигнатуры и служебные метки:

```
$ strings dump.bin | grep -Ei 'fragment|carv|block|nto'
fragment 1/3 offset 0x00100000
fragment 2/3 offset 0x00700000
fragment 3/3 offset 0x00d00000
carving requires reassembly
EVIDENCE: nto{fr4gm3nt3d_c4rv1ng_sm4rt}
```

Видно: файл состоит из **трёх фрагментов** по разным смещениям. Чтобы собрать его, нужно
знать порядок и границы. Простой header/footer тут не сработает — середина файла лежит
в другом месте.

## Шаг 1: почему фрагментация ломает carving

Представь JPEG из двух блоков. Первый блок лежит по смещению A, второй — по смещению B,
между ними — другой файл. Biphasic carving найдёт header в A, дойдёт до footer... но
footer лежит в блоке B. Если между A и B вклинился другой файл, carving либо «затянет»
его в JPEG, либо вообще не найдёт footer. Отсюда три подхода к фрагментации.

## Шаг 2: стратегии фрагментированного carving

| Стратегия | Идея | Плюсы | Минусы |
|-----------|------|-------|--------|
| Biphasic | header + footer | просто, быстро | ломается на фрагментах |
| Structure-aware | проверяем внутренние структуры (размеры, счётчики) | отсекает мусор | нужен парсер формата |
| SmartCarving | моделируем размещение ФС | восстанавливает фрагменты | сложно, медленно |
| Metadata-assisted | используем остатки метаданных | точно | нужны метаданные |

**Structure-aware** carving особенно полезен: например, у JPEG в header есть поле длины
сегмента; у ZIP — размер записи. Проверяя эти поля, инструмент понимает, где файл реально
кончается, и не «переливает» лишнее.

## Шаг 3: инструменты

- **PhotoRec** — классический carving по сигнатурам, поддерживает много форматов;
- **Foremost** — настраивается через `foremost.conf`, умеет header/footer;
- **Scalpel** — быстрый и гибкий, конфигурируется, поддерживает разные форматы;
- **bulk_extractor** — сканирует дамп на **извлекаемые сущности** (email, URL, кредитки,
  ключи), не «файлы целиком», а интересные строки;
- **`binwalk`** — находит встроенные структуры и сигнатуры.

Пример `scalpel`:

```
$ scalpel -c scalpel.conf -o ./out dump.bin
$ ls out/
jpg-0-0/  pdf-1-0/  zip-2-0/
```

`scalpel` создаёт каталоги по типам; внутри — извлечённые файлы с номерами фрагментов.

## Шаг 4: ручная сборка фрагментов

Когда автоматика не справляется, фрагменты собирают руками. Приём:

1. найти все header/footer и кандидаты блоков;
2. проверить, что «хвост» одного фрагмента логически продолжает «голову» другого
   (например, JPEG-энтропия не прерывается);
3. склеить в правильном порядке;
4. проверить, что файл открывается.

Инструмент `binwalk` помогает найти границы, а `dd` — вырезать и склеить:

```
$ dd if=dump.bin bs=1 skip=$((0x100000)) count=$((0x200000)) of=frag1.bin
$ dd if=dump.bin bs=1 skip=$((0x700000)) count=$((0x200000)) of=frag2.bin
$ cat frag1.bin frag2.bin > reassembled.bin
```

## Шаг 5: оценка результата

Carving всегда **вероятностный**: восстановленный файл может быть частично неверным.
Поэтому:

- проверяй открытие/валидность файла (magic, парсинг);
- сверяй с любыми оставшимися метаданными;
- помечай в отчёте степень уверенности;
- помни, что отсутствие метаданных означает потерю имён и путей.

## Мини-практика: от сигнатуры к файлу

```
$ binwalk dump.bin | head
DECIMAL       HEXADECIMAL     DESCRIPTION
1048576       0x100000        JPEG image data
7340032       0x700000        JPEG image data
$ foremost -i dump.bin -o ./out
$ ls out/jpg/
00000000.jpg  00000001.jpg
```

Мы нашли сигнатуры и извлекли кандидаты. Дальше — проверка: открывается ли JPEG, нет ли
обрезки. Если файл фрагментирован, часть картинки будет серой/битой — это сигнал, что
нужна ручная сборка.

## Частые ошибки и подводные камни

- **Доверие header/footer.** Без проверки структуры «вырезается» мусор.
- **Игнорирование фрагментации.** Крупные файлы почти всегда фрагментированы.
- **Слепое `dd`.** Считай смещения в байтах аккуратно; ошибка на 512 байт ломает файл.
- **Перезапись источника.** Работай с копией дампа.
- **Ложные сигнатуры.** Последовательность байт может случайно совпасть с сигнатурой.

## Что мы теперь знаем

- Carving восстанавливает файлы по содержимому, без метаданных.
- Biphasic (header/footer) ломается на фрагментации.
- Structure-aware и SmartCarving проверяют внутренние структуры.
- Инструменты: PhotoRec, Foremost, Scalpel, bulk_extractor, binwalk.
- Результат всегда вероятностный — проверяй валидность.

## Оценка качества восстановления

Carving не даёт гарантий, поэтому качество восстановления нужно **измерять**. Простые
метрики:

- **открывается ли файл** штатным просмотрщиком/парсером;
- **валидны ли внутренние структуры** (для JPEG — маркеры сегментов; для ZIP — записи и
  центральный каталог; для PDF — таблица xref);
- **нет ли «швов»** — резких переходов, серых полос, обрывов текста в середине;
- **сходится ли размер** с ожидаемым (если есть хоть какая-то подсказка).

Практический приём: для изображений проверяй декодирование через библиотеку (PIL) — если
декодер ругается на обрезанный файл, значит, footer найден неверно. Для архивов пробуй
распаковать: повреждённый ZIP сообщит, какая запись битая.

Результат carving всегда оформляют с **уровнем уверенности**: «полный», «частичный
(восстановлено 70 %)», «только сигнатура, данные невалидны». Это защищает от ложных
выводов при построении отчёта.

## Особенности отдельных форматов

Разные форматы требуют разного подхода к carving:

| Формат | Признак начала | Сложность carving |
|--------|----------------|-------------------|
| JPEG | `FF D8 FF` | средняя: маркеры сегментов помогают |
| PNG | `89 50 4E 47` | высокая: чанки с CRC |
| PDF | `%PDF` | средняя: xref-таблица |
| ZIP/OOXML | `PK\x03\x04` | средняя: локальные заголовки |
| SQLite | `SQLite format 3` | низкая: страницы по 4096 |
| MP4 | `ftyp` | высокая: атомы (boxes) |

Зная внутреннюю структуру, ты можешь **валидировать** фрагменты: например, у SQLite
каждая страница начинается с заголовка, и битая страница видна сразу. Для MP4 порядок
атомов жёстко определён, поэтому перепутанные фрагменты не «склеятся» в валидный файл.
Чем лучше знаешь формат — тем точнее carving.

## Метаданные как подсказка для сборки

Даже когда «метаданных нет», их остатки часто есть. Прежде чем собирать фрагменты вслепую,
проверь:

- **битмапы и таблицы inode** — они могут пережить удаление и подсказать порядок блоков;
- **журналы ФС** (`jbd2`, `$LogFile`) — там сохраняются старые указатели на блоки;
- **NTFS `$MFT`** — записи удалённых файлов с data runs;
- **индексные записи каталогов** — имена и размеры удалённых файлов.

Зная размер файла и список кандидатов-блоков, сборка перестаёт быть перебором: ты
упорядочиваешь фрагменты по логике содержимого (начало JPEG, продолжение энтропии, конец).
Инструменты вроде `fls`/`icat` (The Sleuth Kit) и `extundelete` дают эти подсказки ещё до
carving. Правило: **сначала выжми метаданные, потом карай** — это экономит часы.

## Куда дальше

Мы разобрали carving фрагментов. Дальше займёмся **шифрованием дисков** — LUKS, VeraCrypt
и BitLocker: где лежат их заголовки, как устроены ключевые слоты и что делать, когда
заголовок повреждён. А пока главное запомни: **без структуры carving гадает, и фрагментация
— главный его враг**.

## Где пригодится

- **CTF Forensics:** дампы без метаданных, где надо собрать файл.
- **DFIR:** извлечение доказательств с повреждённых носителей.
- **Data recovery:** восстановление после форматирования.
- **Anti-forensics:** понимание, что удаление не гарантирует невосстановимость.
