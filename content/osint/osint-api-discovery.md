## Вопрос, с которого всё начинается

У компании есть API. Его эндпоинты — это карта её сервисов: пользователи, заказы, админка. Иногда разработчики публикуют документацию API прямо в интернет, и по ней видно всё: какие методы есть, какие параметры принимаются, где админские пути.

Задача: найти спецификацию API и перечислить эндпоинты — не отправляя на них никаких данных, кроме безопасных запросов.

## Наш пример: спецификация OpenAPI

Держим объект `https://api.example.com`. Первый вопрос: **есть ли публичная спецификация?** Современные фреймворки генерируют документ OpenAPI (бывший Swagger) и часто отдают его по типовым путям.

```bash
curl -s https://api.example.com/openapi.json | jq .
```

```json
{"openapi":"3.0.1","info":{"title":"Example API","version":"2.3.0"},
 "paths":{"/v1/users":{},"/v1/orders":{},"/v1/admin/keys":{}}}
```

Читаем: `paths` перечисляет эндпоинты. Мы сразу видим `/v1/users`, `/v1/orders` и — что особенно интересно — `/v1/admin/keys`. Последний путь намекает на управление ключами. Это готовая карта API, полученная легально.

## Шаг 1: типовые пути документации

Спецификации лежат по узнаваемым адресам. Полезно проверять их списком:

```text
/openapi.json      /swagger.json
/openapi.yaml      /swagger.yaml
/api-docs          /v3/api-docs
/redoc             /docs
/swagger-ui.html   /swagger/index.html
```

Если один из них отвечает JSON с полем `paths` или `swagger` — документация найдена. Иногда она спрятана за `/api/`, `/v1/`, `/internal/` — стоит проверять и вложенные пути.

## Шаг 2: GraphQL и интроспекция

GraphQL — другой стиль API: один эндпоинт, много запросов. Если включена интроспекция, схему можно прочитать целиком:

```bash
curl -s -X POST https://api.example.com/graphql \
  -H 'Content-Type: application/json' \
  -d '{"query":"{__schema{types{name}}}"}' | jq -r '.data.__schema.types[].name'
```

```text
User
Order
AdminKey
```

Список типов `User`, `Order`, `AdminKey` рассказывает о доменной модели приложения. Отключённая интроспекция — признак зрелой безопасности; включённая — открытая книга.

## Шаг 3: эндпоинты из JavaScript

Если спецификации нет, её собирают из фронтенда. Скрипты приложения содержат пути, к которым обращается браузер:

```bash
curl -s https://example.com/app.js | grep -oE '/api/v[0-9]+/[a-zA-Z0-9_/]+' | sort -u
```

```text
/api/v1/users
/api/v1/orders
/api/v1/admin/keys
```

Так находят скрытые эндпоинты, которых нет в документации. Ещё глубже — динамические пути, собираемые из переменных; их выявляют анализом кода или перебором.

## Шаг 4: границы

Мы читаем спецификации и делаем безопасные запросы (интроспекция схемы, GET без параметров). Мы **не отправляем данные, не вызываем изменяющие методы, не подбираем параметры**. Спецификация — это карта, а не разрешение на действия.

## Полный прогон

```bash
# 1. спецификация
curl -s https://api.example.com/openapi.json | jq -r '.paths|keys[]'
# → /v1/users, /v1/orders, /v1/admin/keys
# 2. GraphQL
curl -s -X POST https://api.example.com/graphql -d '{"query":"{__schema{types{name}}}"}' | jq -r '.data.__schema.types[].name'
# → User, Order, AdminKey
# 3. из JS
curl -s https://example.com/app.js | grep -oE '/api/v[0-9]+/[a-z/]+' | sort -u
```

Непрерывно: домен → типовые пути → спецификация → эндпоинты → GraphQL → схема → карта API.

## Если не сработало

**Спецификация закрыта.** Тогда эндпоинты собирают из JS и перебором путей.
**GraphQL без интроспекции.** Схему восстанавливают по ошибкам и по фронтенду.
**API не документирован.** Перебирай типовые пути (`/api/v1/`, `/v2/`) и смотри JS.

## Частые ошибки

**Ошибка: вызывать изменяющие методы.** POST/DELETE могут менять данные — это не разведка.
**Ошибка: игнорировать админские пути.** `/admin/` в спецификации — сигнал для отчёта.
**Ошибка: забыть про версии.** `/v1/`, `/v2/` могут отличаться по безопасности.
**Ошибка: не смотреть заголовки.** `Server`, `X-Powered-By` выдают фреймворк.

## Справочная таблица: типовые пути спецификаций

| Путь | Формат |
|------|--------|
| `/openapi.json` | OpenAPI 3 |
| `/swagger.json` | Swagger 2 |
| `/v3/api-docs` | Spring Boot OpenAPI |
| `/api-docs` | общий |
| `/redoc` | Redoc UI |
| `/graphql` | GraphQL-эндпоинт |

## Разбор кейса: от домена до админского пути

Дано: домен `example.com`. Шаг первый — находим `api.example.com`. Шаг второй — `/openapi.json` отвечает, `paths` перечисляет эндпоинты. Шаг третий — среди них `/v1/admin/keys`; это признак административного API. Шаг четвёртый — GraphQL-интроспекция отдаёт типы `User`, `Order`, `AdminKey`. Вывод: API задокументирован публично, в нём есть админские пути и доменная модель. Разведчик зафиксировал карту и передал в отчёт.

## Рабочий воркбук: полное расследование API

**Этап 1. Обнаружение.** Собери поддомены `api`, `api-v2`, `gateway`, `internal`. Проверь типовые пути спецификаций.

**Этап 2. Спецификация.** Если найден OpenAPI/Swagger — выгрузи список `paths` и параметров. Это карта.

**Этап 3. GraphQL.** Проверь интроспекцию. Если включена — выгрузи типы и запросы.

**Этап 4. JS-анализ.** Собери пути из скриптов фронтенда; сопоставь со спецификацией, найди недокументированные эндпоинты.

**Этап 5. Фиксация.** Сведи эндпоинты, версии, админские пути и доменную модель в отчёт. Не вызывай изменяющих методов.

## Частые вопросы

**Почему спецификация утекает?** Её часто генерируют автоматически и забывают закрыть в проде. Иногда она нужна внешним интеграторам.

**Что такое интроспекция GraphQL?** Возможность запросить схему API. Если она включена, любой видит все типы и поля.

**Как найти недокументированные эндпоинты?** Из JS-кода и перебором типовых путей. Иногда через ошибки API.

**Опасно ли читать спецификацию?** Сама по себе — нет, она публична. Опасны действия по ней без авторизации.

**Это законно?** Чтение публичной документации — да. Отправка данных и вызов методов — нет.

## Термины

**OpenAPI / Swagger** — стандарт описания REST API.

**GraphQL** — язык запросов к API с единым эндпоинтом.

**Интроспекция** — запрос схемы GraphQL.

**Эндпоинт** — адрес метода API.

**Paths** — раздел спецификации со списком эндпоинтов.

## Что мы теперь знаем

1. Спецификации API лежат по типовым путям.

## Три истории из практики разведки API

**История первая: забытая документация.** Команда выкатила новую версию API и закрыла старую, но спецификация `/openapi.json` осталась опубликованной. В ней были не только актуальные эндпоинты, но и устаревшие админские пути, которые «временно» не убрали. Разведчик выгрузил полный список `paths` и обнаружил `/v1/internal/export` — путь для выгрузки данных. Одна забытая документация выдала целый пласт возможностей.

**История вторая: интроспекция GraphQL.** Публичный GraphQL-эндпоинт не отключал интроспекцию. Запрос схемы вернул десятки типов, включая `AdminMutation` с операциями над пользователями. Даже не вызывая их, разведчик получил полную доменную модель приложения: какие сущности существуют, какие поля у них есть, какие операции доступны. Для планирования авторизованного теста это бесценно.

**История третья: эндпоинты из бандла.** У приложения не было публичной документации, зато фронтенд-бандл содержал список путей. Разбор JavaScript дал эндпоинты, которых не было ни в одном справочнике: `/api/v2/beta/`, `/api/v1/debug/`. Так разведка нашла «теневые» API, оставшиеся от разработки.

Все три истории говорят одно: карта API редко бывает спрятана. Она либо в документации, которую забыли закрыть, либо в схеме, где не отключили интроспекцию, либо в коде фронтенда. Разведчик просто знает, где смотреть, и собирает эндпоинты раньше, чем начинается любая проверка.

## Сигнатуры фреймворков и полная методология

Разные фреймворки оставляют разные следы, и это помогает разведке. Spring Boot отдаёт `/v3/api-docs` и `/actuator`, часто с заголовком `X-Application-Context`. FastAPI публикует `/openapi.json` и `/docs` (Swagger UI) и `/redoc`. Express с `swagger-jsdoc` отдаёт `/api-docs`. Django REST Framework показывает `/api/schema/`. ASP.NET Core публикует `/swagger/v1/swagger.json`. Ruby on Rails с rswag — `/api-docs/v1/swagger.json`. Зная фреймворк (по заголовкам `Server`, `X-Powered-By` или по структуре ответов), ты сразу проверяешь характерные для него пути документации и служебные эндпоинты вроде `/actuator/health`, `/metrics`, `/env`.

Методология разведки API укладывается в пять шагов. Первый — обнаружение: собери поддомены и хосты, связанные с API (`api`, `gateway`, `internal`, `partner`). Второй — документация: проверь типовые пути спецификаций, выгрузи `paths` и параметры. Третий — схема: если есть GraphQL, проверь интроспекцию и выгрузи типы. Четвёртый — фронтенд: разбери JS-бандлы, собери недокументированные пути, сопоставь со спецификацией. Пятый — фиксация: сведи эндпоинты, версии, админские пути и служебные эндпоинты в отчёт. Ни на одном шаге ты не вызываешь изменяющих методов: разведка читает, а не действует.

Полезно помнить и про служебные эндпоинты. Actuator в Spring Boot (`/actuator/env`, `/actuator/beans`, `/actuator/heapdump`) в проде иногда открыт и выдаёт переменные окружения, включая секреты. `/metrics` в Prometheus-формате раскрывает имена сервисов и внутренние адреса. `/debug` и `/health` дают версии и состояние. Эти эндпоинты — не «API» в классическом смысле, но для разведки они не менее ценны: они показывают, как приложение устроено внутри. Проверяй их наряду со спецификациями, потому что именно там чаще всего остаются забытые двери, оставленные для удобства разработки.

## Заметка о версионировании

Обрати внимание на версии в путях: `/v1/`, `/v2/`, `/beta/`. Старые версии часто оставляют включёнными ради обратной совместимости, но патчи и защиту в них не переносят. Поэтому при разведке проверяй не только текущую версию API, но и предыдущие: устаревший `/v1/` может оказаться менее защищённым, чем свежий `/v3/`. Это не призыв к эксплуатации, а сигнал для отчёта: наличие старых версий — отдельная строка риска.
