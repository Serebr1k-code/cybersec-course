## Вопрос, с которого всё начинается

У тебя 200 новостных статей и 50 постов о цели — на нескольких языках. Прочитать всё вручную нереально, а пропустить важное нельзя. Может ли языковая модель помочь разгрести этот объём — и где ей нельзя доверять?

Разберём AI-assisted OSINT на этом самом корпусе: где модель ускоряет, а где врёт.

## Наш пример: корпус из 250 документов о цели

Введём термин. **LLM** (Large Language Model, большая языковая модель) — модель, обученная на огромных текстах, которая генерирует и обрабатывает текст. Её ключевое свойство для нас — **галлюцинации**: она уверенно выдумывает факты, которых нет. Поэтому в OSINT LLM — это **ускоритель обработки**, а не источник истины.

## Шаг 1: где модель сильна, а где нет

| Задача | LLM помогает? | Почему |
|---|---|---|
| Суммаризация | да | языковая задача |
| Перевод | да | языковая задача |
| Извлечение сущностей (NER) | да (с проверкой) | паттерны |
| Генерация кода | да | код — язык |
| **Установление фактов** | **нет** | галлюцинации |
| **Точные цифры и даты** | **нет** | выдумывает |

Правило: **LLM обрабатывает, но не подтверждает**. Любой факт из модели проверяется по первичному источнику.

## Шаг 2: суммаризация и перевод

Собрали 250 статей — LLM сжимает их в дайджест:

```bash
cat articles.txt | llm "Выдели факты о компании: партнёры, руководство, даты, технологии. Без домыслов."
```

Перевод местных СМИ (китайских, арабских) открывает источники, недоступные без языка. Но: **проверяй имена и цифры** — модель может «поправить» транслитерацию.

## Шаг 3: извлечение сущностей

LLM вытаскивает из текста людей, организации, места, даты:

```python
prompt = """Из текста извлеки JSON: {"people":[], "orgs":[], "locations":[], "dates":[]}.
Только то, что есть в тексте, ничего не выдумывай.
Текст: <статья>"""
```

Для продакшена лучше классический NER (`spaCy`, `Stanza`) — он не галлюцинирует. Комбинация: LLM для черновика, spaCy для валидации.

## Шаг 4: эмбеддинги и кластеризация

**Эмбеддинги** — векторные представления текста: каждому фрагменту сопоставляется набор чисел, отражающий его смысл. Близкие по смыслу тексты получают близкие векторы:

```python
from sentence_transformers import SentenceTransformer
m = SentenceTransformer("paraphrase-multilingual-MiniLM-L12-v2")
vecs = m.encode(posts)
# косинусная близость → кластеры
```

Это ML-часть без галлюцинаций — чистая математика. Мы находим 3 темы в корпусе: продукт, руководство, инциденты.

## Шаг 5: генерация гипотез

LLM хорош как «второй мозг» — предлагает векторы, о которых ты не подумал:

```
«Дано: фото, GPS, ник. Предложи 15 гипотез, где может быть флаг, и инструменты для каждой.»
```

Модель выдаёт чек-лист, ты его исполняешь. Гипотезы валидируются, а не принимаются.

## Шаг 6: обязательная валидация вывода

Каждый факт из LLM проверяется программно или по источнику:

```python
import json, requests
data = json.loads(llm_output)
for url in data["urls"]:
    r = requests.head(url, timeout=5, allow_redirects=True)
    print(url, r.status_code)   # 200 = существует, 404 = выдуман
```

Проверка URL на существование ловит большинство выдуманных ссылок. Имена и даты сверяй с первичными источниками.

## Шаг 7: локальная модель для чувствительного

Не отправляй в облачные LLM персональные данные и секреты. Для чувствительного запусти модель локально:

```bash
curl -fsSL https://ollama.com/install.sh | sh
ollama pull llama3.1:8b
ollama run llama3.1:8b "Суммаризируй текст и выдели сущности: <текст>"
```

Плюс: данные не уходят наружу. Минус: качество ниже топовых облачных моделей.

## Шаг 8: RAG — ответы по своим документам

**RAG** (Retrieval-Augmented Generation) подключает LLM к твоей базе документов. Вместо «знаний модели» ответ строится по найденным фрагментам:

```
1. Индексируем документы (эмбеддинги в векторную БД: Chroma, Qdrant).
2. Запрос → ищем ближайшие фрагменты.
3. LLM отвечает, опираясь на эти фрагменты и цитируя их.
```

Это резко снижает галлюцинации: модель цитирует твои данные, а не «вспоминает». Для OSINT RAG идеален — вся база находок становится «умной».

## Шаг 9: OCR и мультимодальность

Модель с vision-возможностями распознаёт текст на изображениях. Локально — Tesseract:

```bash
tesseract screenshot.png - -l rus+eng
```

Для геолокации OCR вывесок критичен: комбинация «OCR извлекает текст → LLM структурирует» работает лучше, чем каждый по отдельности. Но модель может «додумать» детали — используй её как второе мнение.

## Шаг 10: оцениваем качество вывода

Метрики доверия к выводу LLM:

- **Проверяемость** — можно ли подтвердить факт источником?
- **Согласованность** — не противоречит ли другим данным?
- **Специфичность** — конкретика или общие слова?
- **Источник** — есть ли ссылка или цитата?

Вывод без источника — это гипотеза. Требуй цитаты (для этого и нужен RAG) и проверяй.

## Что мы теперь знаем

- LLM обрабатывает текст, но не подтверждает факты.
- Суммаризация, перевод, NER, генерация кода — её сильные стороны.
- Эмбеддинги и кластеризация — чистая математика, без галлюцинаций.
- Каждый факт проверяется программно или по источнику.
- Чувствительные данные обрабатывают локальной моделью или через RAG.

## Частые ошибки

- **Принимать вывод LLM за факт.** Главная ошибка. Всё проверяем.
- **Сливать PII в облако.** Используй локальные модели.
- **Не ревьюить сгенерированный код.** В нём бывают уязвимости и утечки ключей.
- **Доверять переводу имён.** Модель может исказить транслитерацию.
- **Игнорировать дату обучения.** Свежие события модель не знает.

## На что смотреть дальше

Ключевой элемент любого пайплайна — функция `verify`: ни один факт не идёт в отчёт без подтверждения источником. Дальше разберём **картирование поверхности атаки** — как свести все находки в единый граф. А пока главное запомни: LLM — это черновик и ускоритель, а подтверждение всегда за первичным источником.

## Шаг 11: считаем деньги, лимиты и приватность

Модель — это не только качество, но и бюджет. Стоимость считается в **токенах** — кусочках текста, примерно по 3–4 символа на токен для английского и меньше для русского. Держи формулу прикидки: `токены ≈ слов × 1.5`. Корпус из 250 документов по 500 слов — это ~190 000 токенов только на вход, и столько же, если ты передаёшь его на каждый вопрос.

Отсюда два практических правила:

1. **Батчинг.** Не гоняй по документу на запрос — группируй по 10–20 и проси единый структурированный вывод. Это в разы дешевле.
2. **Ограничение окна.** У каждой модели есть **контекстное окно** — максимум токенов, которые она видит за раз. Если корпус больше окна, его режут на чанки (для RAG) или суммируют каскадом.

Приватность важнее денег: отправляя чувствительные документы на чужой API, ты выносишь их за периметр. Для реальных расследований бери **локальную модель** (Llama, Mistral, Qwen через Ollama/llama.cpp) — она работает на твоём железе и никуда не отправляет данные.

## Промпт-шаблоны для разведки

Хороший результат даёт не «попроси модель», а жёстко заданная структура ответа. Два рабочих шаблона:

**Извлечение сущностей.** Проси строго JSON, иначе получишь прозу:

```
Из текста ниже извлеки сущности. Верни ТОЛЬКО JSON:
{"people":[], "orgs":[], "emails":[], "phones":[], "locations":[], "dates":[]}
Не выдумывай: если чего-то нет — пустой список.
ТЕКСТ: <...>
```

**Проверка гипотезы.** Проси модель опровергать, а не подтверждать:

```
Вот гипотеза: <X>. Ниже — фрагменты данных.
Приведи 3 довода ЗА и 3 довода ПРОТИВ. Укажи, какие данные
противоречат гипотезе. Если данных мало — так и скажи.
```

Второй шаблон борется с главной бедой — модель склонна соглашаться с тобой и «галлюцинировать» недостающие факты.

## Если не сработало

- **Модель выдумывает факты (галлюцинация).** Требуй цитату-источник для каждого утверждения: «укажи фрагмент, из которого взят факт». Нет цитаты — нет факта.
- **Ответ обрезается.** Значит, упёрся в лимит выходных токенов. Проси короче или разбей задачу на части.
- **OCR выдаёт мусор.** Прогони страницу через предобработку (повышение контраста, deskew — выравнивание наклона) и повтори. Плохой скан — плохой текст.
- **Стоимость выросла внезапно.** Проверь, не отправляешь ли весь корпус на каждый вопрос; переходи на RAG (поиск релевантных чанков вместо всего).
- **Разные ответы на один вопрос.** Это нормально для генеративных моделей; фиксируй `temperature=0`, чтобы повысить воспроизводимость.

## Мини-практика: разбор одного документа моделью

Пройдём один документ целиком, чтобы увидеть весь конвейер. Возьмём пресс-релиз компании и прогоним его через три шага.

**Шаг А — суммаризация.** Просим модель дать три предложения, и получаем сжатый смысл вместо простыни текста.

**Шаг Б — извлечение сущностей.** Тем же документом просим JSON с людьми, организациями и датами. На выходе — структура, которую можно сравнить с другими документами.

**Шаг В — проверка.** Каждую извлечённую дату и имя сверяем с текстом вручную. Всё, что не подтверждается цитатой, отбрасываем. Модель помогает собрать черновик, но окончательный факт ставит человек.

Такой цикл «суммаризация → извлечение → валидация» масштабируется на весь корпус и не требует держать всё в голове.

## Куда дальше

Мы разобрали, где AI ускоряет разведку и как не дать ему соврать. В следующем уроке — **картирование поверхности атаки**: как свести все разрозненные находки в единый связный граф. А пока главное запомни: модель обрабатывает, но не подтверждает — эта граница неприкосновенна.

## Где пригодится

- **CTF (OSINT):** быстрый разбор больших текстов и переводов под дедлайн.
- **Расследования:** обработка больших корпусов документов.
- **Threat intelligence:** кластеризация отчётов и извлечение IOC.
- **Автоматизация:** генерация скриптов разведки.
- **Медиамониторинг:** суммаризация потока новостей.
