## Вопрос, с которого всё начинается

Компания-контрагент заявляет, что «всё в порядке». Но где-то в даркнете уже висит её имя на сайте утечек ransomware-группы. Как узнать об этом раньше, чем разразится скандал? Нужен **мониторинг leak-sites** — сайтов, куда группы выкладывают украденное.

Задача: прочитать данные leak-site и оценить риск для конкретной организации.

## Наш пример: список жертв

Держим объект `victims.json` — выгрузку с мониторингового агрегатора.

```bash
cat victims.json
```

```text
[{"group": "LockEx", "victim": "RetailCo", "sector": "retail", "deadline": "2026-02-01"},
 {"group": "LockEx", "victim": "BankCo", "sector": "finance", "deadline": "2026-02-05"}]
```

Читаем: две жертвы одной группы `LockEx`, у каждой — сектор и дедлайн публикации. Мы можем отфильтровать нужный нам сектор.

## Шаг 1: что такое leak-site

**Leak-site** — сайт в даркнете, куда ransomware-группа выкладывает данные жертв, которые не заплатили выкуп. Обычно это часть схемы **double extortion**: сначала шифруют данные, потом угрожают опубликовать украденное. Мониторинговые агрегаторы (например, Ransomwatch) собирают посты со всех сайтов и делают их доступными в структурированном виде — легально, без входа в даркнет.

## Шаг 2: что в записи о жертве

Запись содержит **группу**, **жертву**, **сектор**, **дату/дедлайн** и иногда объём данных. Сектор важен для приоритизации: банк и розница реагируют по-разному. Дедлайн показывает, сколько времени до публикации.

```bash
python3 -c "import json;v=json.load(open('victims.json'));print([x['victim'] for x in v if x['sector']=='finance'])"
```

```text
['BankCo']
```

Фильтр по сектору `finance` сразу выделил релевантную жертву.

## Шаг 3: агрегаторы вместо даркнета

Лезть в даркнет вручную опасно и медленно. Агрегаторы решают это: они индексируют посты и отдают JSON/CSV. Это тот же принцип, что и threat-intel фиды — структурированный поток.

```bash
# иллюстративно: публичный фид Ransomwatch
curl -s https://raw.githubusercontent.com/joshhighet/ransomwatch/main/posts.json | jq '.[0]'
# → {"group_name": "lockex", "post_title": "BankCo", "discovered": "2026-02-05"}
```

## Шаг 4: от жертвы к группе

Мониторинг — не только про свою компанию. Группа, атакующая конкурента, придёт и к вам. Поэтому аналитики смотрят **паттерны**: какие секторы группа выбирает, как быстро публикует, каким шифровальщиком пользуется. Это снова путь к TTP и атрибуции.

## Шаг 5: реакция

Обнаружив свою организацию в leak-site, команда IR должна: подтвердить факт, оценить объём утечки, уведомить по закону, подготовить коммуникацию. Мониторинг даёт **время на реакцию** — это его главная ценность.

## Полный прогон

```bash
# 1. все жертвы
python3 -c "import json;print([x['victim'] for x in json.load(open('victims.json'))])"
# → ['RetailCo', 'BankCo']
# 2. по сектору
python3 -c "import json;print([x['victim'] for x in json.load(open('victims.json')) if x['sector']=='finance'])"
# → ['BankCo']
# 3. группа
python3 -c "import json;print(json.load(open('victims.json'))[1]['group'])"
# → LockEx
```

Непрерывно: фид → записи → фильтр по сектору → группа → реакция.

## Если не сработало

**Компании нет в списке.** Это не гарантия безопасности — могли просто не опубликовать.
**Группа новая.** У новых групп ещё нет паттерна; следи за динамикой.
**Дубликаты.** Одна жертва может появиться у нескольких агрегаторов — дедуплицируй.

## Частые вопросы

**Законно ли смотреть leak-sites?** Через агрегаторы — да; сами данные украдены, их нельзя скачивать.
**Что такое double extortion?** Шифрование плюс угроза публикации.
**Насколько свежи фиды?** Обычно часы-сутки; для реакции этого хватает.
**Что делать при находке?** Немедленно передать в IR и юристам.

## Термины

**Leak-site** — сайт публикации украденных данных.

**Double extortion** — шифрование + шантаж публикацией.

**Агрегатор** — сервис, индексирующий leak-sites.

**Дедлайн** — срок до публикации данных.

**Виктимология** — изучение выбора жертв группой.

## Что мы теперь знаем

1. Leak-sites публикуют данные не заплативших.
2. Агрегаторы дают структурированный поток.
3. Сектор и дедлайн — ключевые поля.
4. Паттерны группы ведут к TTP.
5. Мониторинг покупает время на реакцию.

## Разбор кейса: контрагент под угрозой

Дано: агрегатор показывает `BankCo` из сектора `finance` на сайте группы `LockEx` с дедлайном через три дня. Шаг первый — подтверждаем запись по двум независимым агрегаторам. Шаг второй — оцениваем сектор и объём данных. Шаг третий — смотрим паттерн группы: `LockEx` бьёт по финансам и публикует быстро. Шаг четвёртый — передаём в IR и юристам, готовим коммуникацию. У нас есть три дня — ровно то время, которое даёт мониторинг.

## Источники мониторинга

| Источник | Что даёт | Свежесть |
|----------|----------|----------|
| Агрегатор (Ransomwatch) | структурированный JSON | часы |
| Пост leak-site | первоисточник | минуты |
| Новости ИБ | контекст | дни |
| Внутренний SIEM | свои алерты | реальное время |

Агрегатор — компромисс между скоростью и безопасностью; в даркнет лезут только при необходимости.

## Чек-лист реакции

1. Подтвердить факт публикации.
2. Оценить объём и чувствительность данных.
3. Определить юридические обязательства по уведомлению.
4. Уведомить руководство и юристов.
5. Подготовить внешнюю коммуникацию.
6. Зафиксировать хронологию для отчётности.

## Типичные ошибки

**Ошибка: паниковать из-за ложной записи.** Проверяй по двум источникам.
**Ошибка: скачивать украденные данные.** Это незаконно; работай с метаданными.
**Ошибка: игнорировать дедлайн.** Именно он задаёт окно реакции.
**Ошибка: недооценивать группу по одной атаке.** Смотри паттерн по секторам.

## Расширенный пример: фильтр по сектору и группе

```bash
# жертвы в финансах
jq -r '.[] | select(.sector=="finance") | .victim' victims.json
# → BankCo
# группы и их цели
jq -r '.[] | [.group, .sector] | @tsv' victims.json
# → LockEx	retail
# → LockEx	finance
```

Так из потока записей выделяется то, что касается твоей организации и её сектора.

## Экономика ransomware

Чтобы понять leak-sites, надо понять экономику. Группа получает доступ, шифрует данные и требует выкуп. Если жертва не платит, данные публикуют. Существует целая экосистема: одни продают доступ, другие — шифровальщик, третьи — ведут переговоры. Некоторые группы работают как Ransomware-as-a-Service: разработчик даёт программу, партнёры проводят атаки и делят выкуп. Эта модель объясняет, почему инструменты и почерк «переходят» между кампаниями: их используют разные партнёры одной платформы. Для аналитика отсюда следует важное: совпадение шифровальщика не всегда означает одну группу — возможно, это одна RaaS-платформа с разными операторами.

## Что говорит объём данных

В записи о жертве часто указывают объём украденного. Это не просто цифра: она подсказывает, насколько серьёзна утечка и что могло попасть. Гигабайты обычно означают выгрузку файловых серверов и баз; сотни мегабайт — выборочную кражу документов. Сопоставляя объём с сектором, аналитик строит гипотезу о типе данных: персональные, финансовые, коммерческая тайна. Это помогает команде IR заранее понять масштаб и подготовить уведомления по закону.

## Мониторинг как процесс

Разовый просмотр агрегатора ничего не даёт. Нужен процесс: ежедневный сбор фида, фильтрация по своей организации, сектору и ключевым поставщикам, дедупликация, алертинг. Хороший процесс ловит не только прямую угрозу, но и косвенную: появление в списке близкого партнёра — сигнал, что цепочка поставок под ударом. Дополнительно мониторят группы: новая группа, активно бьющая по твоему сектору, — это риск до первой атаки на тебя. Процесс превращает сырой фид в систему раннего предупреждения.

## Юридическая сторона

Утечка запускает юридические обязательства: в разных юрисдикциях есть сроки и формы уведомления регуляторов и пострадавших. OSINT-мониторинг помогает выиграть время, но не заменяет юридическую оценку. Важно разделять: агрегатор даёт **факт публикации**, а объём обязательств определяют юристы по составу данных. Аналитик фиксирует хронологию — когда замечено, что подтверждено, какие шаги предприняты — потому что эти записи понадобятся и регулятору, и суду. Документирование с первого часа — часть работы, а не формальность.

## Пределы мониторинга

Мониторинг не всевидящ. Не все группы публикуют; некоторые держат данные закрыто и продают в приватных каналах. Отсутствие записи не означает отсутствия утечки. Крупные инциденты иногда всплывают через месяцы. Поэтому мониторинг — один слой из нескольких, наряду с внутренней детекцией и threat hunting. Его ценность в скорости и широте охвата, а не в полноте.

## Итоговая картина

Leak-sites — это окно в экономику вымогательства. Через агрегаторы ты видишь, кого и как атакуют, какие секторы под ударом и какие группы активны. Сектор, дедлайн и объём данных превращают сырую запись в оценку риска. Процесс мониторинга — фильтрация, дедупликация, алертинг — даёт организации драгоценное время. А юридическая аккуратность превращает техническую находку в законную и управляемую реакцию.

## Связь с threat hunting

Leak-site — не только повод для реакции, но и источник гипотез для проактивного поиска. Если группа бьёт по твоему сектору через VPN-уязвимость, охотник проверяет: нет ли следов эксплуатации той же уязвимости у нас. Если группа любит определённый инструмент бокового перемещения, охотник ищет его артефакты в логах. Так внешняя разведка превращается во внутренние детекты: то, что происходит у соседей, становится проверяемой гипотезой у тебя. Это и есть практическая польза мониторинга — не пассивное наблюдение, а запуск собственных охот.
