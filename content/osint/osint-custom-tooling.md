## Вопрос, с которого всё начинается

Готовые инструменты (SpiderFoot, Maltego, recon-ng) закрывают большинство задач, но как только источников становится три-четыре, а прогон нужно повторять каждый день, начинается ручная рутина: скопировал из одного окна, вставил в другое, забыл, откуда пришла строка. Разумный шаг — собрать свой маленький конвейер, который делает это сам. В этом уроке мы построим такой конвейер от начала до конца и посмотрим, где именно ломаются самодельные инструменты.

Читателю уже знакомы отдельные источники (crt.sh, DNS, Shodan) и идея графа связей из прошлых уроков. Здесь мы соединяем их в один скрипт.

## Наш пример: пайплайн для домена

Возьмём один домен — `example.com` — и построим для него минимальный, но настоящий конвейер. Он должен: забрать поддомены из журналов Certificate Transparency (CT — публичные логи выданных TLS-сертификатов, где видны все имена домена), привести всё к одной схеме, убрать дубли и сохранить результат.

Важная деталь: любой серьёзный конвейер разбит на **этапы** — это не украшение, а способ не утонуть. У нас их четыре:

1. **Сбор (collectors)** — модули на каждый источник: CT-логи, DNS, WHOIS, сканеры.
2. **Нормализация** — привести разные данные к одной схеме.
3. **Хранение** — положить в базу, а не в кучу файлов.
4. **Визуализация** — собрать граф, чтобы увидеть связи.

Начнём со схемы, потому что именно её отсутствие — главная причина, по которой самодельные инструменты рассыпаются.

## Шаг 1: единая схема сущности

Если один источник отдаёт строку «`dev.example.com`», а другой — «`198.18.0.17`», то без общей модели их не склеить. Введём **сущность** (entity) — минимальную единицу данных о цели:

```
{type, value, source, confidence}
```

- `type` — что это: `subdomain`, `ip`, `asn`, `email`, `cert`.
- `value` — само значение.
- `source` — откуда пришло (`crt.sh`, `dns`).
- `confidence` — вес источника от 0 до 1: насколько мы ему верим.

Последнее поле многие пропускают зря. Без него, когда два источника противоречат, вы не знаете, какому верить.

## Шаг 2: сборщик и нормализация

Пишем первую версию конвейера. CT-логи мы уже получили заранее и сохранили в файл `crtsh_example.json` (живой сервис отвечает медленно и с лимитами — сохранять ответ на диск полезно ещё и для повторяемости):

```python
import json, socket, sys

ENTITIES = []

def add(t, v, s, c=0.5):
    ENTITIES.append({"type": t, "value": v, "source": s, "confidence": c})

def crtsh(domain, path):
    for row in json.load(open(path)):
        for name in row["name_value"].split("\n"):
            add("subdomain", name.strip().lower(), "crt.sh", 0.9)

def resolve(name):
    try:
        for ip in socket.gethostbyname_ex(name)[2]:
            add("ip", ip, "dns", 0.7)
    except socket.gaierror:
        pass

def main(domain, path):
    crtsh(domain, path)
    for s in {e["value"] for e in ENTITIES if e["type"] == "subdomain"}:
        resolve(s)
    seen, uniq = set(), []
    for e in ENTITIES:
        k = (e["type"], e["value"])
        if k not in seen:
            seen.add(k); uniq.append(e)
    json.dump(uniq, open("entities.json", "w"), ensure_ascii=False, indent=2)
    print(f"{len(uniq)} уникальных сущностей")

if __name__ == "__main__":
    main(sys.argv[1], sys.argv[2])
```

Запускаем:

```
$ python3 recon.py example.com crtsh_example.json
12 уникальных сущностей
```

Скрипт нашёл 6 поддоменов в CT-логах и резолвнул их в IP — итого 12 уникальных сущностей. Обратите внимание на три вещи, без которых это не инструмент, а одноразовый скрипт:

- **`.lower()`** при нормализации: `Dev.Example.com` и `dev.example.com` — одно и то же.
- **`set()` для дедупликации** в конце: один поддомен мог встретиться в нескольких сертификатах.
- **`confidence`** у каждой сущности: у CT-логов 0.9, у DNS 0.7.

## Шаг 3: хранение с идемпотентностью

JSON на диске хорош для первого прогона, но не для ежедневного: файл перезаписывается, история теряется, а повторный запуск плодит дубли. Переходим на SQLite — встроенную базу данных (одна библиотека, один файл, ничего ставить не надо):

```python
import sqlite3, json
db = sqlite3.connect("osint.db")
db.execute("""CREATE TABLE IF NOT EXISTS entities(
  type TEXT, value TEXT, source TEXT, confidence REAL, ts TEXT,
  PRIMARY KEY(type, value, source))""")
for e in json.load(open("entities.json")):
    db.execute("INSERT OR IGNORE INTO entities VALUES (?,?,?,?,datetime('now'))",
               (e["type"], e["value"], e["source"], e["confidence"]))
db.commit()
```

Приём здесь — составной **первичный ключ** `(type, value, source)` вместе с `INSERT OR IGNORE`. Прогоним дважды подряд и посмотрим на результат:

```
rows after two runs: 12
('ip', '198.18.0.17', 'dns', 0.7)
('ip', '198.18.0.18', 'dns', 0.7)
...
```

Двенадцать строк после двух запусков — значит, повторный прогон не создал дублей. Это свойство называется **идемпотентность**: запустил один раз или десять — результат одинаковый. Без него любой планировщик (cron) за месяц раздует базу мусором.

## Шаг 4: работа с API и лимиты

Пока мы читали сохранённый файл. Но рано или поздно конвейер пойдёт в живой API, а у любого API есть **лимит** — сколько запросов в минуту он принимает. Игнорирование лимитов — самая частая причина, по которой самодельный инструмент перестаёт работать: сервис отвечает кодом `429` («слишком много запросов») и блокирует ключ.

Правильная обёртка над запросом делает три вещи: ставит **таймаут** (иначе скрипт зависнет на медленном источнике), повторяет попытку при `429` с **экспоненциальной задержкой** (каждая следующая пауза вдвое длиннее) и ограничивает число попыток:

```python
import os, time, requests
KEY = os.environ["CRTSH"]  # ключ — из окружения, не в коде

def get(url, tries=3):
    for i in range(tries):
        r = requests.get(url, timeout=20)
        if r.status_code == 429:
            time.sleep(2 ** i)   # 1s, 2s, 4s...
            continue
        r.raise_for_status()
        return r
    return None
```

Ключ берётся из `os.environ` и никогда не хардкодится: строка с ключом в коде рано или поздно утечёт через репозиторий.

## Шаг 5: плагины — чтобы источники добавлялись без правки ядра

Когда источников станет десять, монолитный `main` превратится в кашу. Решение — **декоратор-регистрация**: каждый источник — отдельная функция, а ядро просто перебирает их:

```python
COLLECTORS = {}
def collector(name):
    def deco(fn):
        COLLECTORS[name] = fn
        return fn
    return deco

@collector("crtsh")
def crtsh(domain): ...

@collector("dns")
def dns(domain): ...

def run(domain):
    for name, fn in COLLECTORS.items():
        try:
            fn(domain)
        except Exception as e:
            print("collector", name, "failed:", e)
```

Два выигрыша сразу: новый источник — это новая функция, ядро не трогаем; и **изоляция ошибок** — падение одного коллектора не роняет весь прогон.

## Шаг 6: граф связей

Наконец, визуализация. Строим граф «домен → поддомен» и сохраняем в формате DOT (текстовый формат Graphviz, который потом рендерится в картинку):

```python
import networkx as nx, json
G = nx.DiGraph()
for e in json.load(open("entities.json")):
    G.add_node(e["value"], type=e["type"])
for n, d in list(G.nodes(data=True)):
    if d.get("type") == "subdomain":
        G.add_edge("example.com", n)
print("nodes:", G.number_of_nodes(), "edges:", G.number_of_edges())
nx.drawing.nx_pydot.write_dot(G, "graph.dot")
```

```
nodes: 13 edges: 6
```

В графе 13 узлов (домен, 6 поддоменов, 6 IP) и 6 рёбер. Читаем его так: **кластеры** — инфраструктура одной организации, **изолированные узлы** — новые активы, **мосты** — критичные связи (общие IP, подрядчики). Граф часто вскрывает то, что не видно в таблице.

## Шаг 7: мониторинг через дифф

Смысл ежедневного прогона — увидеть новое. Сравним два сохранённых результата:

```
$ comm -13 <(jq -r '.[].value' old.json | sort -u) \
           <(jq -r '.[].value' new.json | sort -u)
api.example.com
```

Всё, что вывелось, — появилось между прогонами. Это и есть мониторинг: новые поддомены, сертификаты, IP. На него вешают уведомления (бот, письмо).

## Что мы теперь знаем

- Конвейер разбивается на этапы: сбор → нормализация → хранение → визуализация.
- Единая схема `{type, value, source, confidence}` — фундамент; без неё данные не склеиваются.
- `PRIMARY KEY` + `INSERT OR IGNORE` дают идемпотентность и дедупликацию бесплатно.
- Лимиты API уважают через таймаут, backoff и ограничение попыток; ключи — из окружения.
- Плагинная архитектура позволяет добавлять источники и изолирует их ошибки.

## Куда дальше

В следующем уроке мы возьмём один-единственный индикатор компрометации и покажем, как его обогащают контекстом — то есть наполняют те самые сущности данными из десятка сервисов. А пока главное запомни: свой конвейер начинается не с кода, а со схемы сущности и с уважения к лимитам источников.

## Где пригодится

- **CTF (OSINT):** быстро собрать все источники по цели одним скриптом.
- **Bug bounty:** непрерывный мониторинг новых поддоменов и активов.
- **Threat intel:** пайплайн обогащения индикаторов.
- **Работа:** построение внутренней разведывательной платформы.
