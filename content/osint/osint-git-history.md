Git хранит **всю** историю проекта: каждый коммит, каждая версия файла. Разработчики часто коммитят секреты, а потом «удаляют» их — но в истории они остаются навсегда. Для OSINT и bug bounty это один из самых доходных векторов: одна утечка API-ключа или пароля в старом коммите может дать доступ к инфраструктуре. Здесь важны и умение искать, и умение правильно интерпретировать находки.

## Почему git хранит всё

Git — распределённая система контроля версий. Каждый коммит — снимок состояния, а не «дельта». Даже если вы удалите файл и закоммитите удаление, старые версии остаются в объектах репозитория. `git log`, `git show`, `git blame` позволяют вернуться к любой точке. Если репозиторий публичный (или слит), вся история доступна. **Переписывание истории** (`git filter-repo`/BFG) возможно, но если репозиторий уже был склонирован — у кого-то осталась копия.

## Удалённый код остаётся

Типовой сценарий: разработчик коммитит `.env` с ключами, замечает, удаляет файл и коммитит `Remove .env`. В текущем состоянии файла нет, но:

```bash
git log --all --full-history -- .env
git show <commit>:.env
```

выдадут ключи. Аналогично — пароли в старых версиях конфигов, внутренние хосты в комментариях, токены в тестовых файлах.

## Инструменты

- **gitleaks** — сканирует репозиторий (и историю) на секреты по правилам.
- **trufflehog** — ищет и **верифицирует** ключи (проверяет валидность).
- **git-secrets** — pre-commit-хук и скан.
- **gitleaks detect --source . --log-opts="--all"`** — по всей истории.
- **GitHub secret scanning** — встроенный (для владельцев).
- **`git log -p`** — ручной просмотр.
- **`trufflehog github --org=target`** — скан организации.

```bash
# Скан всей истории
gitleaks detect --source ./repo --log-opts="--all" -v
# Верификация ключей
trufflehog git file://./repo --only-verified
# Скан организации GitHub
trufflehog github --org=target --only-verified
```

## Разобранный пример

1. Клонируем публичный репозиторий (или находим через GitHub search).
2. Сканируем историю:
   ```bash
   gitleaks detect --source ./repo --log-opts="--all" -v
   ```
3. Получаем находки: например, AWS-ключ в коммите 3 года назад.
4. Проверяем валидность:
   ```bash
   trufflehog git file://./repo --only-verified
   ```
5. Если ключ валиден — фиксируем (в рамках bug bounty — сообщаем владельцу, не используем).
6. Смотрим, какие ещё секреты рядом: конфиги, внутренние хосты.

## Что искать

| Тип | Пример |
|---|---|
| API-ключи | AWS, GCP, Stripe, Slack |
| Токены | GitHub PAT, OAuth, JWT |
| Пароли | .env, config, docker-compose |
| Внутренние хосты | staging.internal, 10.x |
| Приватные ключи | id_rsa, .pem |
| Строки подключения | postgres://user:pass@... |

## Обнаружение .git на сайте

Иногда на веб-сервере остаётся каталог `.git`, доступный извне:

```bash
curl -s http://target/.git/HEAD
# ref: refs/heads/main
# Далее выкачиваем через git-dumper
git-dumper http://target/.git/ ./dumped
```

`git-dumper` восстанавливает исходники — часто с секретами. Проверяйте `/.git/config`, `/.git/HEAD`, `/.svn/`.

## Защита

| Мера | Эффект |
|---|---|
| Секреты вне репозитория (.env в .gitignore) | Нет утечки |
| Pre-commit-хуки (gitleaks/git-secrets) | Блокировка коммита |
| Secret scanning в CI | Раннее обнаружение |
| Ротация ключей при утечке | Ограничение ущерба |
| Не отдавать .git с сервера | Защита исходников |
| Приватные репозитории + доступ по least privilege | Снижение поверхности |

## Подводные камни

- **«Удалил — значит, нет».** Нет: история хранит всё.
- **Форк-репозитории.** Секреты могут остаться в форках после удаления в оригинале.
- **Публичные дампы.** Репозитории попадают в дампы и зеркала.
- **Ложные срабатывания.** Не каждый «ключ» валиден — проверяйте (trufflehog).
- **Юридические рамки.** Найденные секреты используйте только в рамках договора.
- **Этические нормы.** Не эксплуатируйте чужой доступ без разрешения.

## GitHub Actions и CI-секреты

Отдельный пласт утечек — **CI/CD**. В GitHub Actions секреты хранятся в настройках репозитория, но их можно «слить» через:

- `echo $SECRET` в логах workflow (если логи публичны/доступны);
- незащищённые `pull_request_target`-воркфлоу (выполняют код из PR с доступом к секретам);
- кэш/артефакты, содержащие токены;
- переменные окружения, печатаемые отладочными шагами.

Проверка публичных репозиториев: смотреть `.github/workflows/*.yml` на `pull_request_target`, `secrets.*` в `run:` и `echo`. Эксплуатация CI — тема `svc-cicd` (skill); для OSINT важно понимать, что **история workflow-логов** тоже может содержать секреты (логи хранятся и иногда доступны).

## Кейс: от коммита к доступу

Типичная цепочка в bug bounty:

1. Находим публичный репозиторий организации.
2. `gitleaks detect --log-opts="--all"` → ключ Stripe в коммите 2 года назад.
3. `trufflehog --only-verified` → ключ **валиден**.
4. Смотрим, к какому сервису он даёт доступ (тестовый/боевой).
5. В рамках bug bounty — **не эксплуатируем**, а фиксируем и сообщаем владельцу с доказательством валидности.
6. Рекомендуем ротацию ключа и pre-commit-хуки.

Ключевой принцип: **возможность не равна праву**. Утечка — это находка, а не лицензия на доступ.

## Правила безопасного тестирования

Скан чужих репозиториев — активность с юридическими границами. Придерживайтесь правил:

- **Публичный код** — можно читать и сканировать (он и так публичен), но **не** использовать найденные секреты.
- **Верификация ключей** (trufflehog `--only-verified`) должна быть **минимально инвазивной**: один безопасный запрос, не выкачивание данных.
- **При находке в bug bounty** — немедленно сообщить владельцу через программу, не публиковать и не эксплуатировать.
- **Приватные репозитории** — только при явной авторизации (pen-test контракт).
- **Логирование** — фиксируйте шаги для отчёта, но не сохраняйте чужие секреты дольше необходимого.

Нарушение этих правил превращает исследование в неавторизованный доступ — с реальной ответственностью.

## Полезные команды для ручного анализа

Помимо сканеров, история читается вручную:

```bash
git log --all --oneline                  # все коммиты
git log --all -- '*.env' '*.pem' '*.key' # коммиты, менявшие секреты
git log -S 'password' --all --oneline    # коммиты, добавлявшие строку
git grep 'AKIA' $(git rev-list --all)    # поиск строки во всей истории
git show <sha>:path/to/file              # файл из коммита
```

`git log -S` (pickaxe) находит коммиты, где строка появилась/исчезла, — идеально для поиска удалённых секретов. `git grep` по `rev-list --all` сканирует все версии. Эти команды не требуют внешних инструментов и работают на любом клоне.
