## Вопрос, с которого всё начинается

Разработчик закоммитил `.env` с ключами, заметил ошибку, удалил файл и закоммитил «Remove .env». Кажется, проблема решена. Но так ли это?

**Git хранит всю историю проекта.** Каждый коммит — это снимок состояния. Даже удалив файл, вы не стираете старые версии: они остаются в объектах репозитория. Разберём, как достать «удалённое» и как это использовать.

## Наш пример: репозиторий example/app

У нас один объект — публичный репозиторий `example/app`. Введём термин: **коммит** — сохранённое состояние проекта с уникальным хэшем (например, `3f2a1c`). Задача — найти в истории то, что из текущей версии убрали.

## Шаг 1: убеждаемся, что история хранит всё

Посмотрим все коммиты, которые когда-либо меняли файлы с секретами:

```bash
git clone https://github.com/example/app && cd app
git log --all -- '*.env' '*.pem' '*.key'
```

```
commit 3f2a1c...
Author: dev <dev@example.com>
    Remove .env

commit 9b7d2e...
Author: dev <dev@example.com>
    add config
```

Второй коммит — тот, где файл **добавили**. Удаление в `3f2a1c` не мешает нам вернуться в `9b7d2e`.

## Шаг 2: достаём удалённый файл

Покажем содержимое файла из старого коммита:

```bash
git show 9b7d2e:.env
```

```
DB_PASSWORD=Sup3rS3cret!
AWS_ACCESS_KEY_ID=AKIA...
```

Вот и секреты, которых нет в текущем дереве. Ключевое правило: **удаление файла ≠ удаление истории**.

## Шаг 3: ищем по строкам через pickaxe

Иногда неизвестно, в каком файле был секрет. Тогда помогает `git log -S` — режим **pickaxe**: он находит коммиты, где строка появилась или исчезла:

```bash
git log -S 'password' --all --oneline
```

```
9b7d2e add config
3f2a1c Remove .env
```

Пара «добавил — удалил» сразу выдаёт подозрительное место. А для поиска по всем версиям сразу используют `git grep` по списку коммитов:

```bash
git grep 'AKIA' $(git rev-list --all)
```

## Шаг 4: сканируем историю инструментами

Ручной просмотр хорош точечно, а для полного охвата нужен сканер. **Gitleaks** проходит всю историю по правилам:

```bash
gitleaks detect --source . --log-opts="--all" -v
```

```
Finding:     AWS Access Key
File:        .env
Commit:      9b7d2e
```

А **trufflehog** с флагом `--only-verified` ещё и проверяет, живой ли ключ, отсекая ложные срабатывания:

```bash
trufflehog git file://./app --only-verified
```

## Шаг 5: находим открытый каталог .git на сайте

Иногда история доступна не через GitHub, а прямо на веб-сервере — если администратор не закрыл каталог `.git`:

```bash
curl -s http://target/.git/HEAD
```

```
ref: refs/heads/main
```

Ответ `ref: refs/heads/main` означает, что каталог `.git` отдаётся наружу. Восстанавливаем весь репозиторий инструментом **git-dumper**:

```bash
git-dumper http://target/.git/ ./dumped
```

Дальше в `./dumped` лежат исходники — часто вместе с секретами. Заодно проверяйте `/.git/config`, `/.svn/`, `/.hg/`. Каталог `.git` открывают по ошибке при деплое статики — это одна из самых частых находок в bug bounty.

## Шаг 6: что делать с находкой

Правила те же, что и для любого секрета. Публичный код можно читать и сканировать, но **использовать** найденные ключи нельзя. Порядок:

1. Зафиксировать доказательство: коммит, файл, тип ключа.
2. Верифицировать минимально и read-only.
3. Остановиться на доказательстве.
4. Сообщить владельцу и рекомендовать ротацию.

Ключевой принцип: **возможность не равна праву**. Утечка — это находка, а не лицензия на доступ. Логируйте свои шаги для отчёта, но не храните чужие секреты дольше необходимого.

## Шаг 7: защита

| Мера | Эффект |
|---|---|
| Секреты вне репозитория (`.gitignore`) | утечки нет |
| Pre-commit хуки (gitleaks) | коммит блокируется |
| Secret scanning в CI | раннее обнаружение |
| Ротация ключей при утечке | ограничение ущерба |
| Не отдавать `.git` с сервера | защита исходников |

Важно понимать: переписывание истории (`git filter-repo`) помогает, но если репозиторий уже кто-то склонировал или форкнул — копия у него осталась. Поэтому для защиты используют не чистку истории, а недопущение секрета в неё с самого начала.

## Полезные команды для ручного анализа

Помимо сканеров, история читается вручную:

```bash
git log --all --oneline                   # все коммиты
git log --all -- '*.env' '*.pem' '*.key'  # коммиты, менявшие секреты
git log -S 'password' --all --oneline     # коммиты, добавлявшие строку
git grep 'AKIA' $(git rev-list --all)     # поиск строки во всей истории
git show <sha>:path/to/file               # файл из коммита
```

Команда `git log -S` (pickaxe) находит коммиты, где строка появилась или исчезла, — идеально для поиска удалённых секретов. `git grep` по `rev-list --all` сканирует все версии. Эти команды не требуют внешних инструментов и работают на любом клоне.

## CI-секреты

Отдельный пласт — **CI/CD**. В GitHub Actions секреты хранятся в настройках репозитория, но их можно слить через `echo $SECRET` в логах workflow, через незащищённые `pull_request_target`-воркфлоу или через артефакты сборок. Для OSINT достаточно понимать: **имена** секретов (`secrets.AWS_KEY`) видны в `.github/workflows/*.yml` и сами по себе раскрывают инфраструктуру.

## Что мы теперь знаем

- Git хранит всю историю: удалённый файл остаётся в старых коммитах.
- `git log --all -- '*.env'` находит коммиты, менявшие секреты.
- `git show <commit>:<file>` достаёт содержимое удалённого файла.
- `git log -S` (pickaxe) ищет строку по всей истории.
- Gitleaks и trufflehog автоматизируют скан истории и верификацию.
- Открытый `/.git` на сайте восстанавливается через git-dumper.
- Защита — это `.gitignore`, pre-commit хуки и ротация, а не удаление файла.
- Переписывание истории не помогает, если репозиторий уже склонировали или форкнули.

## На что смотреть дальше

Разберись с **CI/CD-спецификой**: `.github/workflows/*.yml` раскрывают имена секретов, а `pull_request_target`-воркфлоу выполняют код из PR с доступом к ним. Изучи форки: чистка оригинала их не чистит. Отдельно проверь, не отдаёт ли веб-сервер каталоги `/.svn/` и `/.hg/` — там история хранится так же, как в `.git`. Дальше это ведёт к supply chain security и к теме реестров пакетов.

## Разбор глубже: reflog, stash и packfiles

`git log` показывает достижимые коммиты, но это не вся история. Есть ещё **reflog** — журнал перемещений указателя HEAD: он помнит даже коммиты, которые уже не видны ни в одной ветке. И **stash** — отложенные изменения. Если разработчик отложил правки с ключом и забыл, они лежат в stash-объектах.

Проверить их можно так:

```bash
git reflog --all
git stash list
```

Reflog хранится локально, поэтому в публичном клоне его не будет — он остаётся у того, кто работал с репозиторием. Зато в клоне доступны все объекты, включая «висячие» (dangling). Найти их помогает `git fsck --lost-found`: команда перечисляет объекты, на которые не ссылается ни одна ветка. Среди них часто и оказываются удалённые файлы.

Ещё один источник — **packfiles**. Git сжимает объекты в пакеты (`.pack`). При агрессивной сборке мусора (`git gc`) «старая» история может быть упакована, но не удалена. Пока объект физически есть в `.git/objects` или в pack, его можно извлечь.

## Если не сработало

**`git log --all` ничего не показывает по нужному пути.** Возможно, файл никогда не коммитили в эту ветку, а только в удалённую или в ветку форка. Попробуй `git log --all --source -- '*.env'` — флаг `--source` подскажет, из какой ветки пришёл коммит.

**Файл был в подмодуле (submodule).** Подмодуль — это отдельный репозиторий, вложенный в основной. Его история лежит отдельно; сканировать надо каждый подмодуль своим запуском gitleaks.

**Репозиторий shallow-клон (`--depth 1`).** В таком клоне истории физически нет — только последний коммит. Переклонируй без `--depth`.

**Секрет найден в форке, а не в оригинале.** Проверь, чей это форк и когда он разошёлся с оригиналом. Форки часто не синхронизируют и остаются с устаревшими ключами.

## Частые вопросы

**Можно ли удалить секрет из истории навсегда?** Да, но это переписывание истории: `git filter-repo` или BFG Repo-Cleaner. Важно: после этого ключ надо всё равно отозвать — он уже мог быть склонирован другими.

**Чем `git log -S` отличается от `git log -G`?** `-S` (pickaxe) ищет коммиты, где менялось число вхождений строки. `-G` ищет по диффу — коммиты, где строка появилась в патче. Для вопроса «когда добавили ключ» удобнее `-S`, для «где упоминается» — `-G`.

**А если репозиторий приватный?** Тогда это уже не открытый источник. Проверять его можно только с разрешения владельца; иначе это выход за рамки законной разведки.

## Мини-практика: поднимаем удалённый файл

Сделай тестовый репозиторий: добавь файл `secret.txt`, закоммить, затем удали его и закоммить «remove». Теперь восстанови. Первый способ — `git log --diff-filter=D -- secret.txt` находит коммит удаления, а `git show <hash>^:secret.txt` возвращает содержимое версии до удаления. Второй способ — `git checkout <hash>^ -- secret.txt`. Третий — `git cat-file -p` по хешу блоба, если известен объект. Три разных пути к одному результату показывают главное: пока объект жив в `.git/objects`, данные не потеряны. Именно это свойство git и делает его таким ценным источником для OSINT.

## Куда дальше
