## Вопрос, с которого всё начинается

Сотрудник переслал письмо: «Ваш аккаунт будет заблокирован, подтвердите вход». В письме — ссылка на домен `secure-login.example`. Вопрос простой: что это за домен и насколько ему можно верить? Строка сама по себе не отвечает ни на что — «secure-login.example» выглядит обычно, и по одному виду не понять, фишинг это или легитимный сервис. Ценность появляется, когда мы добавим к строке **контекст**. Этим и занимается обогащение индикаторов.

Читателю уже знакомы граф связей и единая схема сущности из прошлого урока. Здесь мы работаем с одной сущностью и наполняем её данными из множества сервисов.

## Наш пример: один индикатор

**Индикатор компрометации (IOC, Indicator of Compromise)** — наблюдаемый признак атаки: IP, домен, URL, хэш файла, email. У нас есть один такой индикатор — домен `secure-login.example`.

Голый индикатор почти бесполезен: аналитику он ничего не говорит. Работа состоит из двух операций:

- **Обогащение** — добавить контекст: кто владелец, когда зарегистрирован, что о нём говорят антивирусы.
- **Пивотинг** — перейти от индикатора к связанным с ним сущностям: какие ещё домены живут на том же IP, тот же сертификат, тот же регистрант.

Именно вторая операция превращает одну строку в карту инфраструктуры кампании. Разберём обе по шагам.

## Шаг 1: типы индикаторов

Индикаторы бывают разных типов, и каждый обогащают по-своему:

| Тип | Пример | Что обогащаем |
|---|---|---|
| IP | `45.61.136.7` | ASN, гео, репутация, passive DNS |
| Домен | `secure-login.example` | WHOIS, CT-логи, passive DNS, детекты |
| URL | `http://…/verify` | urlscan, категория, редиректы |
| Хэш | `sha256:…` | VirusTotal, семейство, imphash |
| Email | `a@evil.example` | утечки, SPF, соцсети |

В нашем случае индикатор — домен, поэтому идём по второй строке.

## Шаг 2: обогащение через сервисы

Первый источник — **VirusTotal** (VT): мультиантивирусный сервис, который отдаёт вердикт по домену и его историю. Чтобы получить отчёт по URL, VT требует не сам URL, а его **идентификатор** — base64url от строки ссылки без выравнивающих `=`. Считаем его локально:

```python
import base64
u = "http://secure-login.example/verify?token=abc123"
print(base64.urlsafe_b64encode(u.encode()).decode().rstrip("="))
```

```
aHR0cDovL3NlY3VyZS1sb2dpbi5leGFtcGxlL3ZlcmlmeT90b2tlbj1hYmMxMjM
```

Теперь отчёт по домену. Живой API отдаёт большой JSON; мы сохранили ответ и разбираем его через `jq` — консольный фильтр JSON (запрос вида `.data.attributes.last_analysis_stats.malicious` достаёт конкретное поле):

```
$ jq -r '.data.attributes | "malicious=\(.last_analysis_stats.malicious) suspicious=\(.last_analysis_stats.suspicious) rep=\(.reputation)"' vt_domain.json
malicious=7 suspicious=2 rep=-13
```

Семь антивирусов из движков VT пометили домен как вредоносный, два — как подозрительный, а репутация отрицательная (−13). Это уже не «выглядит обычно», это сигнал. Посмотрим, к какой категории его отнесли:

```
$ jq -r '.data.attributes.categories' vt_domain.json
{
  "Forcepoint ThreatSeeker": "phishing",
  "Sophos": "malware"
}
```

Категории — `phishing` и `malware`. Контекст собран: домен из письма действительно опасен.

## Шаг 3: пивотинг — от одного домена к инфраструктуре

Один домен — это ещё не кампания. Пробуем перейти к связанным сущностям. Первый рычаг — **passive DNS**: исторические записи о том, в какие IP резолвился домен и какие ещё домены жили на тех же IP. Это сторонние базы, накопленные из ответов DNS по всему интернету.

Разберём сохранённый ответ passive DNS:

```
$ jq -r '.passive_dns[] | [.hostname,.address]|@tsv' pdns.json | sort -u
cdn-update.example      45.61.136.7
secure-login.example    45.61.136.7
verify-login.example    45.61.136.7
```

Наш домен и ещё два (`verify-login.example`, `cdn-update.example`) живут на одном IP `45.61.136.7`. Это классический признак: злоумышленник держит целый набор фишинговых доменов на одном сервере. Проверим уникальность:

```
$ jq -r '[.passive_dns[].address]|unique|.[]' pdns.json
45.61.136.7
$ jq -r '[.passive_dns[].hostname]|unique|length' pdns.json
3
```

Один IP, три домена. Дальше цепочку можно продолжать: этот IP → reverse IP (все домены на нём), эти домены → CT-логи по их сертификатам → ещё поддомены. Каждый шаг удлиняет список связанных сущностей. Другие рычаги пивотинга:

- **хэш → другие файлы семейства** (imphash, ssdeep);
- **TLS-сертификат → все домены с тем же сертификатом**;
- **JARM/favicon-хэш → все C2 того же инструмента**;
- **email регистранта → все его домены** (reverse WHOIS).

## Шаг 4: оценка уверенности

Не все индикаторы равны, и нельзя объявлять «атака» по одному детекту. Строим шкалу из взвешенных сигналов. Простой скоринг:

```python
vt_detections = 7; abuse_score = 68; domain_age_days = 14; has_mx = 1
score = 0
score += 2 if vt_detections > 5 else 0
score += 1 if abuse_score > 50 else 0
score += 1 if domain_age_days < 30 else 0
score += 1 if has_mx else 0
verdict = "high" if score >= 4 else "medium" if score >= 2 else "low"
print("score", score, "verdict", verdict)
```

```
score 5 verdict high
```

Пять баллов из пяти — уверенность **высокая**. Обратите внимание: сам по себе ни один сигнал не решает, вердикт складывается из совокупности. Ориентиры:

- **Высокая** — подтверждено несколькими независимыми источниками, свежее, совпадает с известной кампанией.
- **Средняя** — один надёжный источник с контекстом, но без перекрёстного подтверждения.
- **Низкая** — единственный детект, возможен ложный.

## Шаг 5: срок жизни и связь с ATT&CK

Два правила, которые отличают зрелый анализ от поверхностного.

**Первое — у индикатора есть срок годности.** Атакующий меняет IP и домены за часы. Индикатор старше 90 дней называется **устаревшим** (decay), и его вердикт пересматривают: тот же IP мог перейти к новому владельцу. Поэтому каждому индикатору ставят TTL — время жизни.

**Второе — привязка к техникам атаки.** Вместо «вредоносный IP» пишут «C2-сервер кампании, техника T1071». **MITRE ATT&CK** — каталог таких техник, каждая с номером:

- T1071 — Application Layer Protocol (C2 через обычный HTTP/HTTPS);
- T1566 — Phishing;
- T1041 — Exfiltration Over C2 Channel.

Такая привязка делает отчёт понятным: читатель видит не строку, а роль индикатора в атаке.

## Что мы теперь знаем

- Голый IOC бесполезен — ценность даёт контекст (обогащение) и переходы (пивотинг).
- Обогащение собирает факты из сервисов: VT, AbuseIPDB, passive DNS, WHOIS.
- Пивотинг превращает один домен в список связанных: 3 домена на одном IP.
- Вердикт складывается из совокупности сигналов (скоринг), а не из одного детекта.
- У каждого индикатора есть TTL и привязка к техникам ATT&CK.

## Куда дальше

В следующем уроке мы разберём подозрительную ссылку целиком — не только домен, но и её структуру, редиректы и загружаемые ресурсы, не открывая её в своём браузере. А пока главное запомни: один индикатор — это не ответ, а начало цепочки, и всю ценность раскрывает пивотинг.

## Где пригодится

- **Threat intel:** обогащение индикаторов и построение вердиктов.
- **Blue team:** приоритизация алертов и triage инцидентов по контексту.
- **Пентест:** понимание, как ваша инфраструктура выглядит в threat-базах.
- **CTF (OSINT):** связать разрозненные подсказки в одну кампанию.
