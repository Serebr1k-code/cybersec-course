## Вопрос, с которого всё начинается

Ты собрал поддомены цели и проверяешь их один за другим. Большинство отдают нормальные страницы, но `docs.example.com` отвечает странным 404: «There isn't a GitHub Pages site here». Ты заходишь на сам GitHub — и понимаешь, что страницы там больше нет. А поддомен компании всё ещё указывает на неё.

Это **subdomain takeover** — одна из самых «вкусных» находок в bug bounty. Разберём, как он возникает и как его найти.

## Наш пример: docs.example.com с висящим CNAME

Введём термин. **CNAME** — это DNS-запись-«псевдоним»: она говорит «имя `docs.example.com` на самом деле указывает на другое имя». Часто компании настраивают поддомен так, чтобы он указывал на внешний сервис (GitHub Pages, Heroku, S3). **Dangling CNAME** («висячий») — это когда ресурс на том конце удалили, а DNS-запись осталась.

Схема нашей уязвимости:

1. Компания создала `docs.example.com` → CNAME на `example.github.io`.
2. Документацию закрыли, репозиторий на GitHub удалили.
3. **DNS-запись осталась** — её забыли убрать.
4. Теперь `docs.example.com` указывает в пустоту.
5. Любой, кто займёт имя `example` на GitHub Pages, получит контроль над `docs.example.com`.

## Шаг 1: собираем поддомены и их CNAME

Сначала — поддомены (из CT-логов, subfinder, amass). Потом вытаскиваем CNAME:

```bash
for h in $(cat subdomains.txt); do
  cname=$(dig +short CNAME "$h")
  [ -n "$cname" ] && echo "$h -> $cname"
done
```

Вывод:

```
blog.example.com -> myblog.herokuapp.com
shop.example.com -> example-shop.s3.amazonaws.com
docs.example.com -> example.github.io
old.example.com  -> example.azurewebsites.net
```

Мы видим четыре кандидата — поддомены, указывающие на внешние сервисы.

## Шаг 2: проверяем, «жив» ли целевой ресурс

Если целевой хост не резолвится (NXDOMAIN) — это сильный признак висячего указателя:

```bash
for h in $(cat subdomains.txt); do
  cname=$(dig +short CNAME "$h" | head -1)
  [ -z "$cname" ] && continue
  if ! dig +short "$cname" | grep -q .; then
    echo "CANDIDATE: $h -> $cname (NXDOMAIN)"
  fi
done
```

## Шаг 3: проверяем по HTTP

Часто CNAME резолвится, но отдаёт «сервис-специфичную» страницу, которая выдаёт незанятость:

```bash
curl -sI "https://docs.example.com" | head -1
curl -s "https://docs.example.com" | grep -iE 'no such app|github pages|nosuchbucket|not found'
```

Вывод:

```
HTTP/2 404
404 There isn't a GitHub Pages site here.
```

Каждый сервис оставляет свой характерный текст:

| Сервис | Признак незанятости |
|---|---|
| Heroku | `No such app` |
| GitHub Pages | `There isn't a GitHub Pages site here` |
| AWS S3 | `NoSuchBucket` |
| Azure | `Error 404 - Web app not found` |
| Shopify | `Sorry, this shop is currently unavailable` |
| Fastly | `Fastly error: unknown domain` |

## Шаг 4: сверяемся со списком уязвимых сервисов

Не все сервисы уязвимы. Проект **can-i-take-over-xyz** на GitHub ведёт актуальный список. Классические кандидаты: AWS S3, GitHub Pages, Heroku, Azure, Shopify, Fastly, Pantheon, Zendesk, Bitbucket, Surge.sh.

Важно: современные Netlify и Cloudflare Pages требуют **верификации домена** — они не уязвимы. Список нужно перепроверять, статусы меняются.

## Шаг 5: автоматизируем поиск

Инструменты — `subjack`, `subover`, `dnsReaper`, `nuclei`:

```bash
subjack -w subdomains.txt -t 100 -timeout 30 -o takeover.txt -ssl -c fingerprints.json
nuclei -l subdomains.txt -t http/takeovers/ -silent -o takeovers.txt
```

Они прогоняют список поддоменов и сверяют ответы с базой отпечатков сервисов.

## Шаг 6: подтверждаем кандидата (без захвата)

Для `docs.example.com` мы уже видели 404 GitHub Pages. Проверяем, что имя `example` на GitHub свободно:

```bash
curl -sI "https://example.github.io" | head -1
```

Если имя свободно, поддомен **уязвим**. Но здесь критичный момент: фактическая регистрация ресурса — это уже активная атака, требующая явной авторизации. В OSINT-фазе мы только **находим и подтверждаем кандидатов**, не захватывая.

## Шаг 7: оцениваем влияние

Захват поддомена — это не просто «чужой сайт» на твоём домене. Последствия:

- **Фишинг** на доверенном домене (высокий клик-рейт).
- **Кража cookie** родительского домена, если cookie без ограничения `Domain`.
- **Обход CSP** — доверенный origin в белом списке.
- **OAuth redirect** — если поддомен в списке разрешённых.
- **Утечка токенов** через `document.domain`.

В отчёте указывай: поддомен, CNAME-цель, сервис, признак свободности, потенциальное влияние и рекомендацию (удалить запись или занять ресурс).

## Шаг 8: что делать blue team

Для защиты от этого класса нужна дисциплина:

- **Инвентаризация DNS** — регулярная сверка записей с реальными активами.
- **Мониторинг** — оповещения на изменение CNAME.
- **Удаление записей** при выводе сервиса из эксплуатации.
- **Верификация домена** в облачных платформах (закрывает класс целиком).
- **CAA** ограничивает выпуск сертификатов на захваченный поддомен.

## Что мы теперь знаем

- Dangling CNAME — DNS-запись на удалённый ресурс внешнего сервиса.
- Уязвимость возникает, когда имя ресурса занимается «кто первый».
- NXDOMAIN целевого хоста и сервисный текст ошибки — признаки кандидата.
- Сервисы с верификацией домена (Netlify, Cloudflare Pages) не уязвимы.
- Захват без авторизации — активная атака; в OSINT только подтверждаем.

## Частые ошибки

- **Путать NXDOMAIN с takeover.** Иногда CNAME указывает на внутреннее имя.
- **Игнорировать верификацию сервиса.** Современные платформы защищены.
- **Захватывать без авторизации.** Регистрация ресурса = активная атака.
- **Считать общий 404 признаком.** Нужен именно сервисный текст ошибки.
- **Не перепроверять список сервисов.** Статусы меняются со временем.

## На что смотреть дальше

Для защиты от этого класса сервисы вводят верификацию домена, а компании — инвентаризацию DNS и мониторинг изменений CNAME. Дальше разберём **WHOIS, ASN и карту IP-инфраструктуры** — основу атрибуции, на которой держатся остальные ветки. А пока главное запомни: висячий CNAME — это мост от разведки к эксплуатации, и его надо находить до атакующего.

## Справочник: сервисы с частыми takeover

Захват поддомена (subdomain takeover) возможен, когда CNAME ведёт на сервис, где ресурс уже не занят. Чаще всего это:

| Сервис | Признак «не занято» |
|---|---|
| GitHub Pages | 404 от `github.io` |
| Heroku | «No such app» |
| Netlify | «Not Found — Netlify» |
| AWS S3 | «NoSuchBucket» |
| Azure | «404 Web Site not found» |
| Shopify | «Sorry, this shop is currently unavailable» |
| Fastly | «Fastly error: unknown domain» |
| Zendesk | «Help Center Closed» |
| Tumblr | «There's nothing here» |

Признак один: DNS ещё указывает на сервис, а ресурс на стороне сервиса уже удалён.

## Мини-практика: от CNAME до подтверждения

Порядок действий без реального захвата:

1. **Собери поддомены** (`subfinder`) и их CNAME (`dnsx -cname`).
2. **Найди «висящие»** — те, чей CNAME ведёт на сторонний сервис.
3. **Проверь HTTP-ответ** — совпадает ли он с сигнатурой «не занято» из таблицы.
4. **Сверься со списком** (`can-i-take-over-xyz` на GitHub).
5. **Зафиксируй доказательство** (CNAME + ответ сервиса), но **не захватывай** без разрешения.

Подтверждение = воспроизводимая пара «DNS-запись + ответ сервиса». Этого достаточно для отчёта.

## Если не сработало

- **CNAME ведёт на живой ресурс.** Тогда takeover нет — поддомен занят.
- **HTTP 200 с контентом.** Сервис отвечает, значит ресурс существует; проверь, чей это контент.
- **DNS не отдаёт CNAME.** Поддомен может быть за A-записью или проксирован CDN; проверь `dig +short CNAME` без кэша.
- **Сервис сменил сигнатуру.** Обновляй список `can-i-take-over-xyz` — сообщения сервисов меняются.
- **Захват запрещён scope.** Фиксируй находку и сообщай владельцу; сам захват — за рамками авторизации.

## Справочник: инструменты обнаружения

Ручной поиск не масштабируется — используй специализированные утилиты:

| Инструмент | Что делает |
|---|---|
| `subjack` | проверяет список поддоменов на takeover |
| `subzy` | то же, с обновляемыми сигнатурами |
| `nuclei -t takeover` | шаблоны для десятков сервисов |
| `dnsx -cname` | быстро достаёт CNAME из списка |
| `can-i-take-over-xyz` | справочник сигнатур (не инструмент) |
| `whois`/`dig` | ручная проверка конкретного кандидата |

Логика: сначала `dnsx`/`subfinder` собирают кандидатов, затем `subjack`/`subzy`/`nuclei` проверяют их автоматически, а последний шаг — ручное подтверждение через `dig` + HTTP-ответ.

## Шпаргалка: подтверждение takeover

- `dig +short CNAME поддомен` → ведёт ли на сторонний сервис.
- HTTP-ответ → совпадает с сигнатурой «не занято».
- Сверка с `can-i-take-over-xyz` → известный ли это сервис.
- Доказательство = CNAME + ответ сервиса.
- Без разрешения — только фиксируй, не захватывай.
- Обновляй сигнатуры: сообщения сервисов меняются со временем.
- Проверяй и вложенные поддомены: `a.b.example.com` тоже может висеть.

## Куда дальше

Мы научились находить и подтверждать висячие CNAME, не выполняя захват. В следующем уроке — **WHOIS, ASN и карта IP-инфраструктуры**: научимся по одному адресу определять владельца, провайдера и границы сети. А пока главное запомни: висячий указатель — это уязвимость, которую надо успеть найти раньше других.

## Где пригодится

- **Bug bounty:** subdomain takeover — высокооплачиваемая находка.
- **CTF (OSINT):** висячий CNAME ведёт к контрольному ресурсу с флагом.
- **Мониторинг:** регулярный скан поддоменов на висячие указатели.
- **Пентест:** расширение периметра за счёт облачных «сирот».
- **Blue team:** инвентаризация DNS и удаление забытых записей.
