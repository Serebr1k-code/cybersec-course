## Вопрос, с которого всё начинается

Ты знаешь домен `example.com`, но не знаешь, какие у него поддомены. Перебирать словарь долго и шумно, а многие имена в словаре вообще отсутствуют.

Есть источник, который отдаёт поддомены **пассивно** и почти бесплатно: **Certificate Transparency**. Это публичный журнал всех выпущенных TLS-сертификатов, и в каждом сертификате перечислены все имена, на которые он выдан. Разберём, как вытащить из него карту поддоменов.

## Наш пример: домен example.com

Работаем с одним доменом — `example.com`. Задача: собрать максимум его поддоменов, не посылая запросов к цели. Начнём с того, что вообще такое CT-лог.

## Шаг 1: что такое CT-лог

Каждый удостоверяющий центр обязан публиковать выданные сертификаты в публичный журнал. Главное свойство лога — он **append-only**: запись нельзя удалить. Даже если компания отозвала сертификат и снесла DNS-запись, имя навсегда осталось в журнале.

Ключевые термины простыми словами:

- **SCT** (Signed Certificate Timestamp) — доказательство, что сертификат занесён в лог; браузеры требуют его наличия.
- **Merkle tree** — структура из хэшей, позволяющая доказать включение записи, не скачивая весь лог.
- **Precertificate** — предварительная запись сертификата, которая тоже попадает в лог.

Вывод: если домен когда-либо выпускал сертификат на `vpn.example.com` или `jenkins.example.com`, эти имена навсегда остались публичными — даже если DNS уже не резолвится.

## Шаг 2: выгружаем имена через crt.sh

Самый простой вход — crt.sh, публичный поисковик по CT-логам, который умеет отдавать JSON без ключей.

```bash
curl -s "https://crt.sh/?q=%25.example.com&output=json" \
  | jq -r '.[].name_value' | tr '[:upper:]' '[:lower:]' | sort -u
```

```
api.example.com
dev.example.com
*.example.com
jenkins.example.com
vpn.example.com
```

Разберём запрос: `%25` — это URL-кодирование символа `%`, то есть шаблон `%.example.com` (всё, что содержит подстроку). Параметр `exclude=expired` убирает истёкшие сертификаты. Важно: в одном сертификате может быть несколько имён, разделённых переводом строки или запятой, поэтому `name_value` перед дедупликацией нормализуют.

## Шаг 3: читаем SAN правильно

Имена в сертификате лежат в поле **SAN** (Subject Alternative Name). По записям видно многое:

| Что видно | Что это значит |
|-----------|----------------|
| `*.example.com` | wildcard: имена скрыты, но зона существует |
| `a.example.com`, `b.example.com` в одном SAN | один сервер обслуживает несколько хостов |
| `dev.example.com` в CT, но DNS не резолвится | «мёртвый» хост — кандидат на takeover |
| сертификат на IP-адрес | сервис без домена — прямой кандидат на порт-скан |

Важный нюанс: wildcard `*.example.com` не раскрывает конкретные имена, но подтверждает, что зона живёт. Не считай это пустым результатом.

## Шаг 4: нормализуем и проверяем резолв

Имя из CT ещё не живой хост: многие сертификаты выданы на тестовые среды. Поэтому список чистят и проверяют резолв.

```bash
grep -v '^\*' names.txt | grep -v '^example.com$' | sort -u > clean.txt
dnsx -l clean.txt -a -resp -o alive.txt
comm -23 <(sort clean.txt) <(cut -d' ' -f1 alive.txt | sort) > dead.txt
```

`alive.txt` — хосты с A-записями, `dead.txt` — имена без DNS, но с сертификатом. Мёртвые имена особенно интересны.

## Шаг 5: ищем takeover-кандидатов

Для «мёртвых» имён проверяем CNAME: если он указывает на сторонний сервис, ресурс на котором удалён, возможен **subdomain takeover**.

```bash
while read h; do dig +short CNAME "$h"; done < dead.txt | sort -u
```

```
foo.example.com. CNAME cname.vercel-dns.com.
```

Такая строка — сигнал проверить, не занят ли ресурс на стороне провайдера. Типичные висячие цели: `*.s3.amazonaws.com`, `*.github.io`, `*.herokuapp.com`.

## Шаг 6: мониторим новые сертификаты

CT полезен и в динамике. Сервис **certstream** подписывается на поток новых сертификатов и отдаёт их в момент выпуска.

```python
import certstream
def on_message(message, context):
    if message["message_type"] != "certificate_update":
        return
    for name in message["data"]["leaf_cert"]["all_domains"]:
        if "example.com" in name:
            print(name)
certstream.listen_for_events(on_message, url="wss://certstream.calidog.io/")
```

Как только у цели появится новый `staging.example.com`, ты узнаешь об этом сразу.

## API CT-логов напрямую

Когда crt.sh перегружен, запросы идут к самому логу — каждый реализует методы RFC 6962.

```bash
curl -s "https://ct.googleapis.com/logs/argon2024/ct/v1/get-sth"
curl -s "https://ct.googleapis.com/logs/argon2024/ct/v1/get-entries?start=0&end=63" \
  | python3 -c 'import sys,json;[print(e["leaf_input"][:40]) for e in json.load(sys.stdin)["entries"]]'
```

Поле `leaf_input` — это base64-структура MerkleTreeLeaf, имена внутри закодированы в ASN.1. Разбирать её вручную не нужно: используй библиотеку `certstream` или агрегаторы. Список всех активных логов держит Google.

## Агрегаторы и мониторинг

Кроме crt.sh, имена отдают Censys (`services.tls.certificates.leaf_data.names`), FOFA (`cert="example.com"`) и SSLMate certspotter. А для защиты CT превращается в систему раннего предупреждения: если кто-то выпустил сертификат на твой домен без ведома команды — это сигнал компрометации.

```bash
curl -s "https://crt.sh/?q=%25.example.com&output=json" | jq -r '.[].name_value' | sort -u > today.txt
comm -13 <(sort prev.txt) today.txt   # только новые имена
```

## Инструменты и флаги

| Инструмент | Команда | Назначение |
|-----------|---------|-----------|
| crt.sh | `curl "https://crt.sh/?q=%25.d&output=json"` | массовая выгрузка имён |
| subfinder | `subfinder -d example.com -all -silent` | агрегирует CT и другие источники |
| amass | `amass enum -passive -d example.com` | пассивный сбор, включая CT |
| dnsx | `dnsx -l names.txt -a -resp` | проверка резолва |
| certstream | python-библиотека | поток новых сертификатов |

## Почему CT незаменим

Главное достоинство CT — полнота и постоянство. Другие источники поддоменов (словари, поисковики) неполны, а CT хранит каждое имя, на которое когда-либо выпускался сертификат, и не позволяет его удалить. Поэтому для охвата внешней поверхности CT обычно даёт больше имён, чем любой другой пассивный метод.

## Что мы теперь знаем

По-простому:

1. CT-логи публичны и append-only: удалить запись нельзя.
2. Каждый сертификат перечисляет имена в поле SAN.
3. crt.sh отдаёт все имена по домену в JSON.
4. Имя из CT ≠ живой хост — нужен резолв.
5. Мёртвые имена с висячим CNAME — кандидаты на takeover.

## На что смотреть дальше

- **Не игнорируй wildcard.** Он не даёт имён, но подтверждает зону.
- **Не забудь `exclude=expired`.** Иначе получишь тысячи исторических записей.
- **Не считай CT «навсегда пассивным».** DNS-запросы к найденным именам уже заметны.
- **Нормализуй `name_value`.** Там бывают запятые и переводы строк.
- **Учти перегрузку crt.sh.** Добавляй `--retry 3 --retry-delay 5`.

## Разбор кейса: сертификат раскрывает невидимое

Certificate Transparency (CT) — это публичные логи, куда попадает каждый выданный TLS-сертификат. Владелец сайта не может это отключить. Из этого следует мощное свойство: CT показывает имена хостов, которые никогда не светились в DNS-зоне и в поиске. Разберём.

Запрос к crt.sh: `curl -s "https://crt.sh/?q=%25.example.com&output=json" | jq -r '.[].name_value' | sort -u`. Знак `%25` — это закодированный `%` (wildcard). Ответ содержит все имена из поля SAN каждого сертификата. Там могут быть `dev.example.com`, `jenkins.example.com`, `vpn.example.com` — имена, о которых ты не знал.

| Поле | Что даёт |
|---|---|
| name_value | имена из SAN |
| issuer_name | кто выдал сертификат |
| not_before | когда выдан |

Второй шаг — нормализовать и проверить резолв. Часть имён — wildcard (`*.example.com`), их надо раскрывать отдельно. Часть — мёртвые. Живые — новые активы. Третий шаг — искать takeover-кандидатов: поддомен, который больше не резолвится, но когда-то имел сертификат, может быть захвачен, если указывает на облачный сервис. Четвёртый шаг — мониторинг. Новые сертификаты появляются в реальном времени, и подписка на поток показывает, когда организация выдаёт новый сертификат — значит, запускает новый сервис.

## Мини-практика: конвейер CT

Построй конвейер: crt.sh, нормализация, dnsx, httpx. Он собирает имена, резолвит и проверяет веб-слой. Прогони для домена и отметь новые хосты. Повтори через неделю — увидишь новые сертификаты и новые имена. Заведи таблицу «имя, дата, источник, статус».

## Если не сработало

**Пусто.** Домен без TLS или сертификаты не логировались. Проверь поддомены отдельно.

**Ошибка JSON.** crt.sh иногда тормозит. Повтори или используй API напрямую.

**Слишком много имён.** Фильтруй по домену и дедуплицируй.

**Мёртвые имена.** Часть истории. Проверь takeover-кандидатов.

## Частые вопросы

**Что такое SAN?** Поле сертификата со списком имён, на которые он выдан. Один сертификат может покрывать десятки имён.

**Почему CT обязателен?** Это требование браузеров: сертификат без записи в логе не принимается.

**Зачем мониторить?** Новый сертификат означает новый сервис. Это раннее предупреждение о расширении поверхности.

## Вопросы и ответы

**Что такое Certificate Transparency?** Публичные логи, куда попадает каждый выданный TLS-сертификат. Владелец не может это отключить, поэтому CT показывает имена хостов, которых нет в DNS и поиске.

**Что такое поле SAN?** Список имён, на которые выдан сертификат. Один сертификат может покрывать десятки имён, и именно оттуда CT-поиск достаёт поддомены.

**Как искать по CT?** Запрос к crt.sh по `%.example.com` возвращает JSON со всеми именами. Затем нормализуй, раскрой wildcard и проверь резолв, чтобы отделить живые имена от мёртвых.

**Почему CT полезен для поиска takeover?** Поддомен, который больше не резолвится, но когда-то имел сертификат, мог указывать на облачный сервис. Если запись осталась, поддомен можно захватить.

**Зачем мониторить новые сертификаты?** Новый сертификат означает новый сервис. Подписка на поток (crt.sh, CertStream) показывает, когда организация запускает что-то новое.

**В чём ограничение CT?** Он покрывает только хосты с TLS-сертификатами. Внутренние имена без сертификатов там не появятся, поэтому CT дополняют, а не заменяют другие методы.

## Куда дальше

В следующем уроке мы возьмём **облачные хранилища** — S3, Azure Blob, GCS — и научимся находить открытые бакеты по предсказуемым именам. А пока запомни главное: CT — лучший пассивный источник поддоменов, потому что имена в журнале остаются навсегда.

## Где пригодится

- **CTF:** задачи на поиск скрытого поддомена, где имя утекло только в CT.
- **Bug bounty:** расширение охвата scope за счёт забытых dev/staging-хостов.
- **Пентест:** картирование внешней поверхности и поиск целей для subdomain takeover.
- **Blue team:** инвентаризация собственных сертификатов и поиск утечек внутренних имён.
