## Задача

Ты получил домен `example.com` на bug bounty. Сканировать его пока нельзя — сначала нужно понять публичную поверхность. Идея в том, что поисковики уже проиндексировали чужие файлы и страницы, и часть из них может быть интересна: конфиги, ключи, открытые каталоги.

**Доркинг** — это поиск через специальные операторы, которые уточняют обычный запрос: «искать только на этом сайте», «только файлы такого типа», «только в заголовке». Базовые `site:` и `filetype:` мы прошли в `osint-search-operators`. Сейчас — продвинутый уровень.

## Полный набор операторов Google

| Оператор | Назначение | Пример |
|---|---|---|
| `site:` | домен/поддомен | `site:api.example.com` |
| `inurl:` / `allinurl:` | слово в URL | `inurl:reset` |
| `intitle:` / `allintitle:` | слово в `<title>` | `intitle:"index of"` |
| `intext:` / `allintext:` | слово в тексте | `intext:"BEGIN RSA PRIVATE KEY"` |
| `filetype:` / `ext:` | расширение | `filetype:sql` |
| `inanchor:` | в тексте ссылок | `inanchor:"login"` |
| `related:` | похожие сайты | `related:example.com` |
| `cache:` | кэш страницы | `cache:example.com` |
| `AROUND(n)` | слова в пределах n слов | `password AROUND(3) file` |
| `before:` / `after:` | по дате | `after:2024-01-01` |
| `-` | исключение | `site:example.com -inurl:www` |
| `OR` | альтернатива | `filetype:env OR filetype:ini` |
| `*` | wildcard | `"password is *"` |
| `..` | диапазон чисел | `inurl:id=1..999` |

Комбинация редких операторов даёт очень точные запросы. Например `inurl:id=1..999 -inurl:404 "user"` ищет страницы с числовым параметром, исключая заглушки.

## Пробуем в лоб: почему просто «example.com config» не работает

Обычный запрос вернёт миллион страниц со всего интернета, где встречается слово «config». Нам нужны **файлы на нашем домене**. Значит, комбинируем `site:` + `filetype:` + `intext:`. Это и есть дорк.

## Наш пример: ищем конфиги и ключи на example.com

Собираем набор дорков под задачу:

```
site:example.com (filetype:env OR filetype:ini OR filetype:yml)
site:example.com inurl:.git
site:example.com intitle:"index of" ".ssh"
site:example.com intext:"AKIA"
```

Что здесь происходит:

- Первый дорк ищет конфиги трёх типов на домене.
- Второй — открытый каталог `.git` (частая утечка исходников).
- Третий — листинг каталога `.ssh`.
- Четвёртый — строку `AKIA` (это начало ключа доступа AWS) в тексте.

## Полный прогон: от дорка к подтверждению

Дорк находит **проиндексированное**, а не обязательно **доступное**. Поэтому каждый URL проверяем. Самый безопасный способ — запросить только заголовки:

```bash
$ curl -sI https://example.com/.env
HTTP/2 200
content-type: text/plain
```

`HTTP/2 200` и непустой ответ — файл реально отдаётся. А вот так выглядит уже закрытый путь:

```bash
$ curl -sI https://example.com/old-config.php
HTTP/2 404
content-type: text/html
```

`404` значит, что страница в индексе есть, но живой её уже нет — в отчёт не берём. Так мы отсеиваем ложные срабатывания.

Полный цикл выглядит так: дорк → список URL → `curl -sI` по каждому → оставляем только `200` с подходящим `Content-Type` → фиксируем URL, источник и дату проверки.

## Автоматизация

Ручной перебор не масштабируется. Инструменты:

- **googler** (CLI) — скриптуемый поиск Google из терминала.
- **Pagodo** — автоматический прогон дорков из GHDB.
- **httpx** — массовая проверка найденных URL.
- **SerpAPI / Bing API** — официальные API, чтобы не получить бан.

Цикл на Bash (с паузами — иначе бан):

```bash
while read -r dork; do
  echo "== $dork"
  googler --json -n 20 "$dork" | jq -r '.[].url'
  sleep 5
done < dorks.txt
```

Не долбите поисковик: бан за автоматизацию приходит быстро. Используйте API, паузы и ротацию User-Agent.

## Обход блокировок выдачи

Поисковики режут автоматизацию. Приёмы, которые продлевают жизнь дорку: разные движки (Google → Bing → Yandex → DuckDuckGo — разные индексы и лимиты), паузы и джиттер (`sleep $((RANDOM%10+5))`), ротация User-Agent и прокси — но для поисковика, а не для целевого сайта, — и официальные API вместо скрейпинга.

## GHDB — каталог готовых дорков

**Google Hacking Database (GHDB)** — каталог дорков по категориям (пароли и ключи, открытые каталоги, логи, панели, чувствительные каталоги). Он на Exploit-DB. Берите идеи оттуда, но **всегда адаптируйте под цель** — чужой дорк под ваш домен почти всегда даёт мусор.

Классические категории:

```
filetype:pem "PRIVATE KEY"
filetype:env DB_PASSWORD
intitle:"index of" access.log
intitle:"Jenkins" "Dashboard"
filetype:sql "INSERT INTO"
```

## Что мы теперь знаем

По-простому:

1. Дорк = обычный запрос + уточняющие операторы (`site:`, `filetype:`, `intitle:`…).
2. Редкие операторы (`AROUND`, `..`, `-`) дают точные запросы.
3. Дорк находит проиндексированное, а не обязательно доступное — всегда проверяй `curl -sI`.
4. GHDB — источник готовых идей, но их надо адаптировать.
5. Автоматизация требует пауз и API, иначе бан.

## На что смотреть дальше

- **Ложные срабатывания.** `200` в индексе не значит `200` сейчас — валидируй каждый URL.
- **Персонализация выдачи.** Google подстраивается под профиль; отключайте пузырь (инкогнито, отдельный профиль).
- **Бан за скорость.** После бана перебор тем же движком бессмысленен — меняй движок или API.
- **Гигиена.** Найденный файл не открывай на рабочей машине: достаточно `curl -sI` и пары строк.
- **Чужие домены.** Оператор `-site:` и `site:` помогают не уехать за пределы цели.

## Различия движков

**Google** — самый полный индекс, но персонализирует выдачу. **Bing** поддерживает `ip:` (поиск по IP), `feed:`, `language:`, `loc:` — полезен для страниц, выпавших из Google. **Yandex** — лучший индекс Рунета: `mime:` вместо `filetype:`, `title:` вместо `intitle:`, `rhost:` (обратные ссылки), лучше покрывает VK и локальные форумы. **DuckDuckGo / Startpage / Searx** — приватные фронтенды; Searx можно поднять локально.

```
ip:203.0.113.10
site:example.com mime:docx "конфиденциально"
site:example.com mime:doc "приказ"
```

Держите оба движка: Google найдёт англоязычные утечки и GitHub, Yandex — локальные документы.

## Форматы утечек и что в них искать

| Формат | Что внутри | Дорк-намёк |
|---|---|---|
| `.env` | пароли БД, API-ключи | `filetype:env DB_PASSWORD` |
| `.json` | конфиги, токены | `filetype:json "token"` |
| `.yml` | CI/CD, секреты деплоя | `filetype:yml "password"` |
| `.sql` | дампы БД с хэшами | `filetype:sql "INSERT INTO"` |
| `.pem`/`.key` | приватные ключи | `filetype:pem "PRIVATE KEY"` |
| `.log` | пути, учётки, ошибки | `filetype:log inurl:error` |

Найдя файл, извлекай только доказательство (ключ или строку), не выгружая весь дамп.

## Операторы, которых нет в шпаргалках

Базовый набор (`site:`, `inurl:`, `intitle:`, `filetype:`) знают все. Разницу делает редкая комбинаторика и «побочные» операторы:

- **`AROUND(n)`** — слова в пределах `n` друг от друга: `"api key" AROUND(3) site:example.com` резко сокращает шум.
- **`before:` / `after:`** — временной срез индекса: ищем старые страницы, которые уже удалены, но остались в кэше выдачи.
- **`source:`** — новостной источник (Google News): `site:example.com source:reuters`.
- **`imagesize:` / `size:`** — находит крупные изображения и большие документы, где чаще прячутся дампы.
- **`intext:` / `allintext:`** — поиск только в тексте, без заголовков и ссылок.
- **`cache:`** — снимок страницы в кэше поисковика (часто уже отдаёт удалённое).
- **`related:`** — похожие сайты; полезно для поиска «брата»-инфраструктуры.
- **`-` (минус)** — исключение шума: `filetype:env -inurl:github`.

Комбинация из трёх-четырёх операторов в одном запросе — норма. Один оператор даёт тысячи результатов, четыре — единицы.

```bash
# Через googler с явным языком и лимитом
$ googler -l ru --json --count 50 \
    'site:example.com (ext:env OR ext:yml OR ext:bak) -inurl:github'
```

## Защита от ложных срабатываний

Главная беда доркинга — **шум**: страницы, которые формально совпали, но не содержат ничего. Три приёма:

1. **Негативные операторы.** Исключай известный мусор: `-inurl:login -inurl:register -intitle:"index of"`.
2. **Точные кавычки.** `"DB_PASSWORD"` даёт намного меньше ложных, чем `DB_PASSWORD`.
3. **Двойная верификация.** Дорк — это **гипотеза**. Прежде чем заносить находку в отчёт, скачай страницу (`curl -s`) и проверь, что она реально отдаёт секрет, а не 404-заглушку или форму логина.

```bash
# От дорка к подтверждению — без открытия браузера
$ googler -C --json 'site:example.com ext:env' | jq -r '.[].url' \
  | while read u; do code=$(curl -s -o /dev/null -w '%{http_code}' "$u"); \
    echo "$code $u"; done | grep '^200'
```

Ещё одна ловушка — **регион и язык**: одна и та же выдача зависит от `gl=`/`hl=`. Если результат «есть у коллеги, нет у тебя», проверь геолокацию запроса. И помни: поисковик показывает **свой индекс**, а не реальность — страница могла быть удалена минуту назад. Всегда подтверждай живым запросом.

Наконец, **этика и границы**: дорк, вскрывший чужой конфиг, — это не «бесплатный доступ», а находка, которую надо задокументировать и сообщить по правилам программы. Не скачивай больше, чем нужно для доказательства.

## Куда дальше

В следующем уроке мы выйдем за пределы Google и разберём специализированные поисковики и базы под конкретные типы данных — код, науку, людей, компании. А пока запомни главное: дорк — это точный запрос, а его результат нужно проверять `curl -sI`, прежде чем верить.

## Где пригодится

- **Bug bounty:** массовый поиск утечек, панелей и открытых конфигов по домену.
- **CTF (OSINT):** точный поиск скрытой страницы по подсказке.
- **Пентест:** быстрый снимок публичной поверхности до сканирования.
- **Threat intel:** поиск упоминаний бренда и утёкших данных в открытом вебе.
