Универсальный поисковик — плохой инструмент для узкой задачи. Когда нужно найти **код**, **научную статью**, **патент**, **датасет** или **старую версию страницы**, вертикальные (специализированные) поисковые системы дают на порядок лучший результат. Для OSINT и recon это критично: значительная часть ценных данных лежит не в общем индексе, а в тематических базах.

## Что такое вертикальный поиск

Вертикальный поиск — это поиск внутри одного домена данных: только код, только научные работы, только документы, только изображения. Такие системы умеют индексировать структуру (например, функции кода или разделы статьи) и часто поддерживают специфичный синтаксис. Задача OSINT-аналитика — знать **какая вертикаль** нужна под каждый вопрос.

## Академический поиск

- **Google Scholar** — статьи, цитирования, PDF; `author:`, `source:`, `intitle:`.
- **PubMed** — медицина/биология, MeSH-термины.
- **arXiv** — препринты (физика, CS, математика).
- **Semantic Scholar** — связи и цитирования, API.
- **ResearchGate / Academia.edu** — профили учёных.
- **Sci-Hub** (легальность зависит от юрисдикции) — доступ к платным статьям.

```bash
# Semantic Scholar API
curl -s "https://api.semanticscholar.org/graph/v1/paper/search?query=osint+reconnaissance&limit=5" | jq .
```

Академический поиск полезен для проверки экспертизы человека (что публиковал) и для понимания технологий компании.

## Поиск по коду

- **GitHub Search** — `in:file`, `language:`, `path:`, `org:`, `user:`.
- **grep.app** — regex-поиск по миллионам репозиториев.
- **Sourcegraph** — поиск по коду с переходами.
- **Searchcode** — агрегатор кода.
- **PublicWWW** — поиск по HTML/JS-сниппетам (аналитика, фингерпринты).

```
# GitHub: ключи в коде
org:target "AKIA" in:file
# PublicWWW: сайты с определённым счётчиком
"UA-XXXXXXX"
```

Поиск по коду — основа поиска утечек секретов (см. `osint-secret-scanning`, `osint-github-recon`).

## Данные и датасеты

- **Kaggle Datasets** — датасеты с кодом и обсуждениями.
- **data.gov / EU Open Data Portal** — государственные открытые данные.
- **Zenodo / Figshare** — научные данные.
- **Google Dataset Search** — метапоиск по датасетам.
- **Awesome-списки** (GitHub) — курированные ссылки.

## Документы, патенты, стандарты

- **Google Patents / Lens.org / Espacenet** — патенты (авторы, assignee, цитирования).
- **Google Books / Internet Archive** — книги.
- **Scribd / Docsity** — загруженные документы.
- **ISO/IETF RFC** — стандарты.

## Торренты, пасты и архивы

- **Torrent-индексы** — иногда содержат слитые базы; использовать только в рамках закона.
- **Pastebin/Paste.ee/Ghostbin** — пасты с утечками.
- **Wayback Machine / archive.today** — история страниц.
- **Common Crawl** — открытый веб-корпус (петабайты HTML) для кастомного анализа.

## Разобранный пример: рекон компании через вертикали

1. Академический: ищем публикации инженеров компании (Scholar `author:`, arXiv).
2. Код: GitHub `org:target` и grep.app по уникальным строкам из их SDK.
3. Секреты: GitHub-дork по `org:target` + ключи (`osint-secret-scanning`).
4. Патенты: Lens.org по assignee — выявляем направления R&D.
5. Архив: Wayback для удалённых страниц (вакансии, сотрудники, API-доки).
6. Датасеты: проверяем, не публиковали ли они данные на Kaggle/Zenodo.

Так строится многомерный профиль компании из «непоисковых» источников.

## Подводные камни

- **Слепо доверять одному источнику.** Вертикали имеют смещения (Scholar не видит всё).
- **Игнорировать дату.** Патенты/статьи стареют; проверяйте актуальность.
- **Не учитывать лицензии.** Использование датасетов/паст может нарушать закон.
- **Пропускать API.** Многие вертикали дают API — это быстрее и стабильнее парсинга.
- **Забывать про кэш.** Даже удалённое находится в архивах.

## Что дальше / решение

Вертикали — «длинный хвост» OSINT. Свяжите с `osint-search-operators`, `osint-github-recon`, `osint-secret-scanning`, `osint-wayback-archives` и `osint-metadata`. Дальше — автоматизация (SpiderFoot/recon-ng). Для CTF тренируйтесь искать флаг в патентах/архивах/коде.

## Метапоиск и агрегаторы

Метапоисковики объединяют несколько движков и убирают дубликаты: **SearxNG** (self-hosted, десятки движков), **Startpage** (результаты Google), **MetaGer**, **Dogpile**. Для OSINT ценен **SearxNG**: вы поднимаете его сами, настраиваете список движков и получаете единый интерфейс без трекинга — идеально под легенду и без утечки запросов в чужой лог.

```bash
# SearxNG в Docker
docker run -d -p 8888:8080 --name searxng searxng/searxng
# Запрос через JSON-API
curl -s "http://localhost:8888/search?q=osint&format=json" | jq '.results[0:3]'
```

Агрегаторы утечек и паст (**Intelligence X**, **DeHashed**, **HIBP**) — тоже вертикали: они индексируют то, чего нет в общем поиске. Intelligence X особенно полезен: он ищет по домену, email, IP и хранит историю.

## Специализированные базы по регионам

Помимо глобальных вертикалей, есть **национальные** базы: реестры компаний (Companies House UK, Handelsregister DE, ЕГРЮЛ RU), судебные решения (CourtListener US, ГАС «Правосудие» RU), земельные кадастры, патентные ведомства (USPTO, EPO, Роспатент). Для OSINT они незаменимы: официальные документы содержат имена, адреса, должности и связи, которых нет в соцсетях. Многие дают API или машиночитаемые выгрузки.

## Лаборатория: построение профиля из вертикалей

1. Выберите публичную компанию.
2. **Патенты**: Lens.org по assignee → направления R&D и авторы.
3. **Код**: GitHub `org:` + grep.app по их SDK → технологии и, возможно, секреты.
4. **Академия**: Scholar `author:` сотрудников → публикации.
5. **Реестры**: Companies House/ЕГРЮЛ → директора, адрес, связи.
6. **Архив**: Wayback → удалённые страницы «Команда», «API».
7. Сведите всё в таблицу сущностей и связей.

Так из «непоисковых» источников собирается детальный профиль.

## Автоматизация вертикального поиска

Вертикали хорошо автоматизируются через API. Практический конвейер:

```python
# 1) GitHub code search (через API/токен)
# GET https://api.github.com/search/code?q=AKIA+org:target
# 2) crt.sh для сертификатов
# GET https://crt.sh/?q=%25.target.com&output=json
# 3) Wayback CDX для истории URL
# GET http://web.archive.org/cdx/search/cdx?url=target.com*&output=json
# 4) Semantic Scholar для публикаций
# GET https://api.semanticscholar.org/graph/v1/paper/search?query=target
```

Соберите обёртку, которая по домену/имени прогоняет все вертикали и сводит результаты в один JSON. Это ядро собственного recon-пайплайна. Обязательно кэшируйте ответы (чтобы не долбить API) и уважайте rate-limit: у GitHub — 10–30 запросов/мин для code search, у Wayback CDX — throttle при больших запросах.

## Оценка качества и достоверности источников

У вертикалей разная надёжность, и это надо учитывать. Официальные реестры и патентные базы — первичные источники (высокая достоверность). Пасты и торрент-индексы — вторичные, требуют перекрёстной проверки. Академические препринты (arXiv) не рецензируются, поэтому выводы могут быть предварительными. Практические правила:

- **Первичный источник** (сайт компании, госреестр, оригинал документа) > вторичный (агрегатор, форум).
- **Дата** важна: проверяйте актуальность патентов/вакансий/постов.
- **Перекрёстная проверка**: находка из пасты должна подтверждаться другим источником.
- **Цепочка цитирований**: у статьи/патента смотрите, кто ссылается — это расширяет картину.

Для OSINT-отчёта фиксируйте не только факт, но и **источник и его надёжность** — так выводы проверяемы.

## Где пригодится

- **Работа:** патентный и академический анализ.
- **CTF:** поиск артефактов в неочевидных базах.
