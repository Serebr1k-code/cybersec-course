## Задача

У тебя есть только домен компании — `example.com`. Общий поисковик уже показал главную страницу и пресс-релизы. Но нужно понять, чем компания занимается на самом деле: какие технологии, кто инженеры, какие патенты, что было на сайте раньше.

Общий поисковик здесь плохой помощник. Нужен **вертикальный поиск** — поиск внутри одного класса данных: только код, только патенты, только научные статьи, только архив страниц.

## Наш пример: профиль компании example.com

Мы идём по вертикалям и на каждой отвечаем на свой вопрос. Всё складываем в одну таблицу сущностей.

## Шаг 1: код — GitHub и grep.app

Разработчики оставляют в публичном коде email, ключи, внутренние адреса. GitHub ищет по репозиториям и файлам, grep.app — по фрагментам кода на миллионах репозиториев.

```
org:example in:file "AKIA"
```

Здесь `org:` ограничивает организацию, `in:file` ищет по содержимому файлов, `AKIA` — начало ключа доступа AWS. grep.app умеет regex, поэтому находит уникальные строки из SDK компании.

## Шаг 2: архив — Wayback Machine

Сайт меняется: страницы «Команда», «API-документация», «Вакансии» часто удаляют. **Wayback Machine** хранит исторические копии. Быстрый способ получить список всех сохранённых URL — **CDX API**:

```bash
$ curl -s "http://web.archive.org/cdx/search/cdx?url=example.com&output=json&limit=3"
[["urlkey","timestamp","original","mimetype","statuscode"],
 ["com,example)/","20020120142510","http://example.com:80/","text/html","200"],
 ["com,example)/","20020328012821","http://www.example.com:80/","text/html","200"]]
```

Колонка `timestamp` — когда сохранён снимок, `original` — адрес, `statuscode` — код ответа. Так можно найти удалённые страницы и посмотреть, как они выглядели.

## Шаг 3: патенты — Lens.org и Google Patents

Патентные базы ищут по **assignee** — владельцу патента. Это показывает направления R&D и авторов-инженеров:

```
assignee:example
```

Так мы узнаём, над какими технологиями компания работала и кто конкретно.

## Шаг 4: академия — Scholar и arXiv

**Google Scholar** (`author:`, `source:`, `intitle:`), **arXiv**, **Semantic Scholar** связывают имя, организацию и тему. Публикация — подтверждённый факт, поэтому она отлично годится для атрибуции сотрудников. Semantic Scholar даёт API:

```bash
$ curl -s "https://api.semanticscholar.org/graph/v1/paper/search?query=osint&limit=3&fields=title,year"
```

## Шаг 5: данные и пасты

- **Датасеты:** Kaggle, data.gov, Zenodo, Google Dataset Search.
- **Пасты и утечки:** Pastebin, Intelligence X, HIBP (только проверка, с учётом легальности).
- **Документы:** Scribd, DocumentCloud.

Проверь, не публиковала ли компания данные на Kaggle и не утекали ли её адреса в пасты.

## Шаг 6: вертикали по людям и контактам

Кроме кода, патентов и архивов есть вертикали, заточенные под людей:

- **People search** (Spokeo, Whitepages) — собранные из открытых источников адрес, телефон, родственники.
- **Утечки** (Have I Been Pwned, DeHashed) — факт появления адреса в базах; только проверка, без использования данных.
- **Реестры** (OpenCorporates, Companies House) — директора и владельцы компаний.
- **Госзакупки** (SEC EDGAR, госзакупки РФ) — кто и на что получал контракты.

Каждая из них — тоже вертикаль: она ищет в одном классе данных и потому точнее общего поисковика. Но у неё своя этика — утечки и персональные данные используют только в законных рамках.

## Шаг 7: как читать выдачу вертикали

Вертикаль возвращает не «страницу вообще», а структурированные записи. Смотри на поля:

- **источник** — кто записал факт (реестр надёжнее агрегатора);
- **дата** — патент 2009 года не описывает текущий продукт;
- **идентификатор** — номер патента, ORCID, DOI: по нему факт проверяем;
- **связи** — соавторы, совладельцы, организации: они и есть будущий граф.

Один факт без идентификатора — гипотеза; факт с номером и первоисточником — доказательство.

## Полный прогон: от домена к карте источников

Собираем всё вместе на `example.com`:

1. **Код** — `org:example in:file "AKIA"` в GitHub и `example.com` в grep.app: ищем ключи и внутренние адреса.
2. **Архив** — `curl "http://web.archive.org/cdx/search/cdx?url=example.com*&output=json"`: список удалённых страниц, среди них — «Команда» и «API».
3. **Патенты** — `assignee:example`: направления R&D и имена изобретателей.
4. **Академия** — `author:` плюс название компании в Scholar и Semantic Scholar: сотрудники и темы.
5. **Люди и реестры** — OpenCorporates: директора; people search: адреса и телефоны.
6. **Утечки** — HIBP по найденным адресам: где они уже светились.

На выходе — таблица «сущность → источник → надёжность → дата». Именно она, а не разрозненные скриншоты, и есть результат разведки.

## Таблица «вертикаль → системы»

| Вертикаль | Примеры |
|---|---|
| Академия | Scholar, PubMed, arXiv, Semantic Scholar |
| Код | GitHub, grep.app, Sourcegraph |
| Данные | Kaggle, data.gov, Zenodo |
| Патенты | Google Patents, Lens.org, Espacenet |
| Архив | Wayback, archive.today |
| Пасты | Pastebin, Intelligence X |

## Что мы теперь знаем

По-простому:

1. Вертикаль — поиск внутри одного класса данных, точнее общего.
2. Код ищется в GitHub/grep.app, патент — по assignee.
3. Wayback хранит удалённые страницы; CDX API даёт список URL.
4. Академические базы связывают имя, организацию и тему.
5. Многие вертикали дают API — это стабильнее парсинга.

## На что смотреть дальше

- **Слепое доверие одному источнику.** У вертикалей есть смещения: Scholar видит не всё.
- **Дата.** Патенты и статьи стареют — проверяй актуальность.
- **Лицензии.** Использование датасетов и паст может нарушать закон.
- **API вместо парсинга.** Многие вертикали дают API — быстрее и стабильнее.
- **Кэш.** Даже удалённое находится в архивах, не считай «удалено» синонимом «исчезло».

## Оценка качества источников

У вертикалей разная надёжность:

- **Первичные** (госреестр, оригинал документа, сайт компании) — высокая достоверность.
- **Вторичные** (агрегатор, форум, паста) — требуют перекрёстной проверки.
- **Препринты** (arXiv) не рецензируются — выводы предварительные.

Правило: фиксируй не только факт, но и **источник и его надёжность** — тогда вывод проверяем.

## Автоматизация

Вертикали хорошо автоматизируются через API. Конвейер по домену:

```python
# 1) GitHub code search:  GET https://api.github.com/search/code?q=AKIA+org:target
# 2) crt.sh:              GET https://crt.sh/?q=%25.target.com&output=json
# 3) Wayback CDX:         GET http://web.archive.org/cdx/search/cdx?url=target.com*&output=json
# 4) Semantic Scholar:    GET https://api.semanticscholar.org/graph/v1/paper/search?query=target
```

Соберите обёртку, которая по домену прогоняет все вертикали и сводит результат в один JSON. Обязательно кэшируйте ответы и уважайте rate-limit: у GitHub code search — 10–30 запросов в минуту.
