## Вопрос, с которого всё начинается

Тебе нужно узнать, кто владеет доменом, когда он зарегистрирован и через какого регистратора. Ты запускаешь `whois`, но получаешь рыхлый текст без структуры — и хочешь разобрать его автоматически, скриптом. Есть ли способ надёжнее?

Да: **RDAP** — современная JSON-замена WHOIS. Разберём оба протокола и научимся доставать из них нужное.

## Наш пример: домен example.com

Введём термины. **WHOIS** — старейший протокол регистрационных данных: кто владеет доменом или IP, когда создан, какие NS и статусы. **RDAP** (Registration Data Access Protocol) — его замена на базе HTTPS с ответом в формате **JSON** (структурированный текст с полями). Разница принципиальна для скриптов.

## Шаг 1: сравниваем WHOIS и RDAP

| | WHOIS | RDAP |
|---|---|---|
| Транспорт | TCP/43, текст | HTTPS/JSON |
| Формат | свободный текст | структурированный JSON |
| Аутентификация | нет | есть (по бутстрапу) |
| Будущее | устаревает | стандарт (RFC 7480-7484) |

```bash
whois example.com
whois 93.158.134.144
```

WHOIS-вывод — текст, который приходится парсить регулярками. RDAP отдаёт поля напрямую.

## Шаг 2: ключевые поля WHOIS

Что искать в выводе:

- **Registrar** — через кого зарегистрирован домен.
- **Creation / Updated / Expiry Date** — возраст домена.
- **Name Server** — DNS-провайдер (Cloudflare, Yandex, reg.ru).
- **Registrant / Admin / Tech** — контакты (часто скрыты из-за GDPR).
- **Status** — `clientHold`, `pendingDelete`, `ok`.
- **DNSSEC** — подписан ли домен.

Свежесть домена + приватность + NS, не соответствующий компании, — признак фишинга или «одноразовой» инфраструктуры.

## Шаг 3: запрашиваем RDAP

```bash
curl -s https://rdap.org/domain/example.com | python3 -m json.tool
```

Достаём только даты и NS:

```bash
curl -s https://rdap.org/domain/example.com \
  | python3 -c 'import sys,json;d=json.load(sys.stdin);print(d.get("events"));print([n["ldhName"] for n in d.get("nameservers",[])])'
```

Из ответа извлекаем `events` (регистрация, истечение), `entities` (роли registrar/registrant), `nameservers`, `status`. RDAP парсится стабильно — в отличие от текстового WHOIS.

## Шаг 4: разбираем ответ RDAP детально

```bash
curl -s https://rdap.org/domain/example.com \
  | jq '{handle, ldhName, status, events,
         nameservers: [.nameservers[].ldhName],
         entities: [.entities[] | {roles, handle}]}'
```

- `events` — массив `{eventAction, eventDate}`: `registration`, `expiration`, `last changed`, `transfer`.
- `entities` — роли `registrar`, `registrant`, `administrative`, `technical`.
- `nameservers` — список NS; их домены указывают на DNS-провайдера.
- `secureDNS` — DNSSEC-статус.

## Шаг 5: работаем с бутстрапом IANA

`rdap.org` — редирект-сервис, но для надёжности можно обратиться к авторитетному RDAP-серверу напрямую. Бутстрап-файл IANA подсказывает сервер по TLD:

```bash
curl -s https://data.iana.org/rdap/dns.json | jq -r '.services[] | select(.[0][]=="com") | .[1][]'
curl -s https://rdap.verisign.com/com/v1/domain/example.com | jq '{ldhName,status,events}'
```

Для IP-адресов бутстрап аналогичен (`rdap/ipv4.json`), а авторитетный сервер зависит от RIR (ARIN/RIPE/APNIC/LACNIC/AFRINIC).

## Шаг 6: RDAP для IP

Для IP-адресов RDAP-ответ приходит от **регионального интернет-регистратора** (RIR). В ответе важны:

- `handle` и `name` — объект аллокации (NET-блок).
- `startAddress` / `endAddress` — границы диапазона.
- `entities` с ролью `registrant` — организация-владелец.
- `events` — даты выделения и изменений.

```bash
curl -s https://rdap.org/ip/93.158.134.144 \
  | jq '{handle,name,startAddress,endAddress,country}'
```

Дальше диапазон уходит в BGP (ASN, префиксы) и reverse DNS.

## Шаг 7: обходим приватность и GDPR

После введения GDPR большинство регистраторов скрывают персональные данные (`REDACTED FOR PRIVACY`). Что всё равно остаётся: дата регистрации, NS, email регистратора (не владельца). А вот **исторические WHOIS** — до GDPR данные были открыты, и сервисы вроде WhoisXML, DomainTools, ViewDNS хранят снимки. Это часто единственный способ найти настоящий контакт.

## Шаг 8: разбираем статусы домена

Поле **Status** — важный сигнал состояния:

| Статус | Значение |
|---|---|
| `ok` / `active` | нормальное состояние |
| `clientHold` | регистратор приостановил (часто неоплата) |
| `serverHold` | реестр приостановил |
| `pendingDelete` | домен скоро удалят (кандидат на перехват) |
| `redemptionPeriod` | период восстановления после удаления |

`pendingDelete` и `redemptionPeriod` интересны: если домен бренда утекает, его может перехватить злоумышленник.

## Шаг 9: обратный WHOIS

**Reverse WHOIS** ищет все домены с тем же email, именем или организацией — это вскрывает «портфель» владельца:

```bash
curl -s "https://reverse-whois.whoisxmlapi.com/api/v1?apiKey=$WX_KEY&searchType=current&mode=preview&basicSearchTerms={\"include\":[\"example.com\"]}"
```

Так один домен вытягивает за собой десятки связанных.

## Шаг 10: массовая проверка и мониторинг

Для списка доменов собирают ключевые поля одной командой:

```bash
for d in $(cat domains.txt); do
  echo "== $d =="
  whois "$d" 2>/dev/null | grep -iE 'creation|registrar:|name server|status' | head -5
done
```

Сервисы (DomainTools, WhoisXML, ViewDNS) дают API для массового WHOIS и алертов на изменения. Для blue team настройте мониторинг новых регистраций доменов с брендом — это раннее обнаружение фишинга.

## Что мы теперь знаем

- RDAP — HTTPS/JSON-замена WHOIS, парсится стабильно.
- Ключевые поля: даты, статус, NS, контакты, DNSSEC.
- Для IP RDAP отдаёт аллокацию: диапазон, организацию, ASN.
- GDPR скрывает контакты, но исторические снимки их сохраняют.
- `pendingDelete` — кандидат на перехват домена.
- Reverse WHOIS раскрывает портфель доменов владельца.

## Частые ошибки

- **Считать `REDACTED` тупиком.** Смотри исторические снимки и NS/registrar.
- **Путать registrar и registrant.** Регистратор — посредник, не владелец.
- **Игнорировать даты.** Возраст домена — сильный признак.
- **Не проверять статус.** `clientHold`/`pendingDelete` меняют интерпретацию.
- **Пропускать обратный WHOIS.** Он вскрывает весь портфель владельца.

## На что смотреть дальше

Правило интерпретации: домен описывается **набором** признаков (возраст + статус + NS + регистратор + история), а не одним полем. Дальше разберём **тайпсквоттинг** — как системно искать домены-двойники бренда и оценивать их риск. А пока главное запомни: RDAP — это WHOIS для скриптов, и он не требует установки отдельной утилиты.

## Справочник: поля RDAP и что они значат

RDAP возвращает JSON, и каждое поле отвечает на конкретный вопрос. Держи карту:

| Поле | Смысл |
|---|---|
| `ldhName` | имя домена латиницей (ASCII) |
| `unicodeName` | имя в Unicode (для IDN-доменов) |
| `handle` | внутренний идентификатор записи |
| `status` | статусы домена (active, clientTransferProhibited…) |
| `events` | регистрация, обновление, истечение, последняя смена |
| `entities` | registrar, registrant, abuse-контакт |
| `nameservers` | NS-серверы домена |
| `secureDNS` | включён ли DNSSEC |

Из `events` берут дату регистрации (возраст домена) и дату истечения (риск дропа). Из `entities` — регистратора и контакт для жалоб. `secureDNS.delegationSigned: true` означает подписанный DNSSEC.

## Мини-практика: разбор ответа по шагам

Порядок чтения RDAP-ответа всегда один и тот же, и он экономит время:

1. **`ldhName`** — убедись, что пришёл ответ именно про твой домен, а не про похожий.
2. **`events`** — вытащи дату регистрации. Домен «вчерашний» — красный флаг для фишинга.
3. **`status`** — `clientHold` или `pendingDelete` означают, что домен вот-вот освободится (риск дропа и захвата).
4. **`entities`** — найди registrar и abuse-контакт: туда уходит жалоба.
5. **`nameservers`** — сверь с DNS-ответом; расхождение говорит о недавней смене хостинга.

Такой проход занимает минуту и даёт возраст, владельца и «здоровье» домена без единого платного сервиса.

## Если не сработало

- **Пустые `entities`.** Это GDPR-редактирование: регистрационные данные скрыты законно. Смотри registrar и даты — они остаются.
- **Неверный RDAP-сервер.** Для `.com` запрашивай verisign-эндпоинт, для `.org` — PIR. Универсальный путь — бутстрап IANA: он сам укажет сервер для TLD.
- **429 / лимит.** RDAP-серверы ограничивают частоту. Добавь задержку между запросами при массовой проверке.
- **Домен не найден (404).** Это результат: домен свободен или не зарегистрирован. Не путай с ошибкой запроса.

## Мини-практика: от домена к владельцу инфраструктуры

Один домен — это вход, а не финал. Проследим цепочку до организации:

1. **Домен → nameservers.** Из RDAP берём `nameservers`. Если они на `cloudflare.com` или `awsdns`, хостинг анонимный — владельца там не видно.
2. **Домен → IP.** `dig +short example.com A` даёт адрес, а `dig +short NS` — серверы.
3. **IP → ASN.** По IP узнаём автономную систему и её владельца (`whois` или `bgp.he.net`).
4. **ASN → организация.** Владелец ASN — часто хостинг-провайдер, но иногда и сама компания, если у неё свой блок адресов.
5. **Сверка.** Если registrar скрыт GDPR, а ASN принадлежит конкретной фирме — это и есть зацепка для атрибуции.

Вывод: RDAP даёт «паспорт» домена, а связка DNS → IP → ASN превращает его в карту инфраструктуры.

## Шпаргалка: быстрые проверки домена

- Возраст: `events` → `registration`. Молодой домен — повод насторожиться.
- Владелец: `entities` → registrar и abuse-контакт.
- Статус: `pendingDelete`/`clientHold` → домен уходит или заморожен.
- DNSSEC: `secureDNS.delegationSigned` → подписан ли домен.
- Для IP — отдельный RDAP-запрос: он вернёт ASN и организацию.

## Куда дальше

Мы научились доставать регистрационные данные через RDAP и обходить приватность. В следующем уроке — **тайпсквоттинг**: как искать домены-двойники бренда и отличать безобидный паркинг от реальной фишинг-инфраструктуры. А пока главное запомни: RDAP — это структурированный WHOIS, удобный для автоматизации.

## Где пригодится

- **CTF:** определить владельца и связанные домены для следующего шага.
- **Bug bounty:** выявить «портфель» доменов одной организации.
- **Пентест:** контакты и даты для социальной инженерии и оценки риска.
- **Blue team:** мониторинг регистраций похожих доменов (бренд-защита).
- **Аудит:** проверка сроков и статусов собственных доменов.
