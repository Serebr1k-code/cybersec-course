## Вопрос, с которого всё начинается

Ты зарегистрировался в bug bounty программе, получил доступ к `*.example.com` — и не знаешь, с чего начать. Открываешь главную страницу сайта, осматриваешь её… и ничего. Так проходит неделя без находок. Почему? Потому что все интересные баги живут не на главной, а на десятках поддоменов, которые никто не проверяет.

Разведка (OSINT) — фундамент bug bounty: именно она определяет, сколько ты найдёшь. Разберём конвейер от чтения scope до первой находки.

## Наш пример: программа *.example.com

Введём термины. **Scope** — список активов, которые разрешено тестировать. **In-scope** — то, что можно, **out-of-scope** — что нельзя. Разведка работает строго внутри scope: найти уязвимость на чужом активе — не награда, а бан.

## Шаг 1: читаем scope внимательно

Scope-страница программы задаёт:

- **in-scope:** `*.example.com`, `api.example.com`, конкретные IP, мобильные приложения.
- **out-of-scope:** `marketing.example.com`, третьи стороны, соцсети.
- **правила:** запрет на DoS, авто-сканеры, социальную инженерию.

Критичный нюанс: `*.example.com` **не** всегда включает `example.com` и **не** включает аффилированные домены (`example-cdn.net`). Всегда перечитывай. Сохрани scope в файл и валидируй каждый найденный актив:

```bash
grep -E '\.example\.com$' all_subdomains.txt > in_scope.txt
```

## Шаг 2: собираем активы пассивно

Классический конвейер начинается с пассивных источников поддоменов:

```bash
subfinder -d example.com -all -silent > subs.txt
curl -s "https://crt.sh/?q=%25.example.com&output=json" | jq -r '.[].name_value' \
  | sed 's/\*\.//g' | sort -u >> subs.txt
amass enum -passive -d example.com >> subs.txt
sort -u subs.txt -o subs.txt
```

Вывод (проверяем объём):

```
$ wc -l subs.txt
312 subs.txt
```

312 поддоменов — вот где настоящая поверхность.

## Шаг 3: проверяем живость и снимаем технологии

**httpx** — сердце конвейера: он проверяет, какие хосты отвечают, и сразу определяет технологии:

```bash
httpx -l subs.txt -sc -title -tech-detect -silent | grep -v '000' | tee live.txt
```

Вывод:

```
https://dev.example.com [200] [Dev Portal] [nginx, React]
https://api.example.com [401] [API] [Express]
https://old.example.com [200] [Legacy] [Apache, PHP 5.6]
```

Флаги: `-sc` (статус-код), `-title`, `-tech-detect`, `-server`, `-cdn`, `-ip`, `-cname`.

## Шаг 4: приоритизируем

Не все активы равны. Приоритет — по признакам «интересности»:

| Признак | Почему важно |
|---|---|
| dev/staging/test | слабее защита, отладочные функции |
| admin/panel/internal | панели управления |
| api/graphql | бизнес-логика, IDOR |
| old/legacy | устаревший стек, CVE |
| `.git`, `.env`, backup | утечки |

```bash
grep -iE 'dev|staging|test|admin|api|internal|old|legacy|uat|qa' live.txt | tee priority.txt
```

`old.example.com` на PHP 5.6 — устаревший, `dev.example.com` — среда разработки. Оба приоритетны.

## Шаг 5: ищем кандидатов на находку

Проверяем приоритетный хост перебором путей:

```bash
ffuf -u https://old.example.com/FUZZ -w /usr/share/seclists/Discovery/Web-Content/common.txt \
  -mc 200,301,403 -t 50 -s | grep -iE 'git|backup|env|sql'
```

Вывод:

```
.git/config
backup.sql
```

Открытый `/.git/config` — возможен дамп исходников, отдельный вектор. Первый кандидат найден.

## Шаг 6: собираем URL и сканируем

Дополняем карту URL из архивов и краулеров:

```bash
gau example.com | sort -u > urls.txt
katana -u https://example.com -d 3 -silent >> urls.txt
nuclei -l live.txt -severity critical,high -silent -o findings.txt
```

**gau** собирает URL из архивов и Common Crawl, **katana** — краулит живой сайт, **nuclei** прогоняет шаблоны известных уязвимостей.

## Шаг 7: ищем секреты в JS и репозиториях

JS-бандлы часто содержат API-ключи и внутренние URL:

```bash
grep -iE '\.js$' urls.txt | sort -u > js.txt
cat js.txt | while read -r u; do curl -s "$u"; done > alljs.txt
grep -oE '(api[_-]?key|token|secret|aws_|AIza)[^"]{0,60}' alljs.txt | sort -u
```

Для GitHub-репозиториев:

```bash
trufflehog github --org=example-org --only-verified
```

## Шаг 8: непрерывная разведка

Программа живёт долго, активы появляются постоянно. Настрой мониторинг:

```bash
subfinder -d example.com -silent | notify -silent -bulk
```

Автоматизация через cron и `notify` даёт «первым» заходить на новые хосты — важное преимущество.

## Шаг 9: смотрим мобильные приложения

Если в scope есть мобильные приложения, они часто раскрывают API, недоступный из веба:

```bash
apktool d app.apk -o src
grep -rniE 'https?://[a-z0-9.-]+' src | grep -vE 'schemas|w3.org' | sort -u | head
```

`jadx` декомпилирует код, **MobSF** делает авто-анализ, **Frida** обходит SSL pinning для перехвата API.

## Шаг 10: держим границы

- **Не выходи за scope.** Активы вне scope — не твои, даже если уязвимы.
- **Не запускай авто-сканеры, если запрещено.**
- **Не тестируй third-party.** CDN и SaaS-вендоры обычно out-of-scope.
- **Не эксплуатируй сверх PoC.** Минимальное доказательство, затем отчёт.
- **Не публикуй без разрешения.**

## Что мы теперь знаем

- OSINT в bug bounty занимает этапы scope → recon → enumeration.
- Пассивные источники дают поддомены, httpx — живые хосты и технологии.
- Приоритет — dev/staging, admin, api, legacy и файлы утечек.
- Автоматика строит карту, находки даёт ручная работа.
- Scope — жёсткая граница: выход за неё = бан.

## Частые ошибки

- **Игнорировать scope-правила.** Бан из программы — потеря доступа.
- **Сканировать только главную.** 90% находок — на поддоменах.
- **Забывать про мобильные приложения.** Часто в scope, но их не трогают.
- **Полагаться только на автоматизацию.** Ручная логика находит то, что не найдёт шаблон.
- **Не сохранять результаты.** Без истории ты пересканируешь одно и то же.

## На что смотреть дальше

Автоматика находит кандидатов, но логика (IDOR, race), цепочки (SSRF → metadata → cloud) и аутентификация (JWT, OAuth) требуют ручного анализа. Дальше разберём **AI-assisted OSINT** — как ускорить обработку данных моделью, не доверяя ей факты. А пока главное запомни: в bug bounty побеждает не тот, кто лучше сканирует, а тот, кто шире нарисовал карту активов в рамках scope.

## Шаг 11: фиксируем доказательства и пишем отчёт

Разведка бесполезна, если находку нельзя доказать. В bug bounty платят за **воспроизводимый** результат, поэтому каждый шаг фиксируй сразу, а не по памяти:

- **Скриншот + сырой ответ.** Сохраняй `curl -i` или вывод инструмента целиком — это первичное доказательство.
- **Точная команда.** В отчёте должна быть команда, которую повторит триажер, а не «я где-то нашёл».
- **Время и версия.** Дата и версия сервиса отделяют актуальную уязвимость от уже исправленной.
- **Минимальный PoC.** Не «взломай всё», а одно действие, доказывающее проблему.

Хороший отчёт отвечает на три вопроса: **что** уязвимо, **как** воспроизвести, **какой** эффект. Если триажер не может воспроизвести — находка уходит в «informative» без выплаты.

## Справочник: этапы разведки и инструменты

| Этап | Цель | Инструменты |
|---|---|---|
| Scope | понять границы | текст программы, `in/out of scope` |
| Пассивный сбор | активы без касания | crt.sh, SecurityTrails, amass passive |
| Живость | что реально отвечает | httpx, dnsx |
| Технологии | стек и версии | httpx -tech-detect, Wappalyzer |
| Приоритизация | куда смотреть | фильтр по «интересным» сервисам |
| URL и сканы | поверхность атаки | katana, gau, nuclei |
| Секреты | ключи и токены | trufflehog, gitleaks |
| Мониторинг | новое вовремя | cron + дифф |

Правило: **пассивное раньше активного**. Активные запросы (сканы) видны цели и могут нарушить правила программы.

## Если не сработало

- **Ассеты не находятся.** Переключись с поддоменов на другие типы: диапазоны IP, мобильные приложения, публичные репозитории, CT-логи.
- **Много «мёртвых» хостов.** Фильтруй `httpx` по коду ответа: 200/401/403 интересны, 404 и таймауты — нет.
- **Найден «запрещённый» актив.** Немедленно остановись и зафиксируй в отчёте — выход за scope карается баном, а не наградой.
- **Секрет найден, но неактивен.** Проверь его **read-only** запросом; если не работает — это не находка, а мусор.
- **Дубликат.** Проверь, не отчётывал ли уже — дубликаты не оплачиваются.

## Шаблон отчёта о находке

Единый шаблон экономит время и повышает шанс выплаты. Держи минимальный каркас:

```
Заголовок: <тип> на <хост> — <краткий эффект>
Severity:  <critical/high/medium/low>
Scope:     <подтверждение, что актив в программе>

Шаги воспроизведения:
  1. <команда/запрос>
  2. <наблюдаемый ответ>
  3. <вывод>

Доказательство: <сырой ответ, скриншот, лог>
Эффект:        <что может сделать атакующий>
Рекомендация:  <как чинить>
```

Пиши так, чтобы триажер прошёл путь за минуту. Чем меньше шагов и яснее эффект — тем выше шанс, что находку примут, а не отправят в «informative». И не смешивай в одном отчёте несколько находок: каждая проблема — отдельный тикет со своим PoC.

## Чек-лист перед отправкой отчёта

- [ ] Актив подтверждён в scope программы.
- [ ] Воспроизведение по шагам работает с нуля.
- [ ] Есть сырое доказательство (запрос и ответ), а не только описание.
- [ ] Указан реальный эффект, а не «теоретически возможно».
- [ ] Одна находка — один тикет.
- [ ] Проверено, что это не дубликат.

## Куда дальше

Мы прошли полный конвейер от scope до первой находки. В следующем уроке — **AI-assisted OSINT**: где языковые модели ускоряют разведку, а где врут и требуют проверки. А пока главное запомни: сначала карта активов, потом уязвимости — и всё строго в рамках scope.

## Где пригодится

- **Bug bounty:** системный конвейер разведки и приоритизации.
- **Пентест:** адаптация под авторизованный внешний периметр.
- **Red team:** карта активов для выбора вектора.
- **CTF:** структурированный подход к веб/infra-задачам.
- **Мониторинг:** отслеживание появления новых поддоменов.
