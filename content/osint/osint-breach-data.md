## Вопрос, с которого всё начинается

Тебе сказали: «проверь, не утекли ли учётки сотрудников компании `example.com`». Новичок сразу лезет скачивать «базу утечек» — и это первый шаг к нарушению закона.

Работа с утечками — область, где важен не инструмент, а **порядок действий**: сначала бесплатные и пассивные проверки, и только потом — активные, и то при наличии правового основания. Разберём это на одном домене.

## Наш пример: домен example.com

У нас один объект — домен `example.com`. Задача: оценить, насколько его сотрудники засветились в утечках, и что это значит для защиты. Ответ мы будем собирать из двух источников: **пассивного** (факт утечки) и **активного** (сами данные).

Сначала определимся с терминами. **Утечка** (breach) — это когда база данных сервиса попала в руки злоумышленников и была опубликована. **PII** (personally identifiable information) — персональные данные: ФИО, телефон, адрес, паспорт. **Credentials** — пары «логин:пароль».

## Шаг 1: пассивная проверка в HIBP

**HIBP** (Have I Been Pwned) — сервис, который сообщает **факт** утечки, но не отдаёт сами данные. Это ключевое отличие: он говорит «этот email встречался в утечке X», а не «вот его пароль».

Проверим конкретный адрес через API:

```bash
curl -s -H "hibp-api-key: $KEY" -H "user-agent: osint-research" \
  "https://haveibeenpwned.com/api/v3/breachedaccount/user@example.com" | jq '.[].Name'
```

```
"LinkedIn"
"Dropbox"
"Adobe"
```

Три утечки. Теперь посмотрим, какие именно данные утекли в каждой:

```bash
curl -s -H "hibp-api-key: $KEY" \
  "https://haveibeenpwned.com/api/v3/breach/LinkedIn" | jq '{Name, BreachDate, DataClasses}'
```

```
{
  "Name": "LinkedIn",
  "BreachDate": "2012-05-05",
  "DataClasses": ["Email addresses", "Passwords"]
}
```

Здесь важно прочитать `DataClasses`: если в списке только `Email addresses`, пароль не утёк — риск ниже. Если есть `Passwords` — это уже серьёзно. Список всех известных утечек целиком можно получить так:

```bash
curl -s "https://haveibeenpwned.com/api/v3/breaches" | jq '.[0] | {Name, BreachDate, PwnCount}'
```

## Шаг 2: проверяем пароль, не отправляя его

Отдельный вопрос: встречался ли конкретный пароль в утечках? Отправлять пароль на сервис нельзя — это плохая гигиена. HIBP решает это приёмом **k-anonymity** (анонимность на основе k): вы отправляете только первые 5 символов SHA-1-хэша пароля, а сервис возвращает список всех суффиксов, начинающихся на этот префикс.

```bash
echo -n "Summer2024!" | sha1sum | tr a-f A-F
```

```
4C0E7F... (полный хэш)
```

Берём первые 5 символов префикса и запрашиваем диапазон:

```bash
PREFIX=$(echo -n "Summer2024!" | sha1sum | cut -c1-5 | tr a-f A-F)
SUFFIX=$(echo -n "Summer2024!" | sha1sum | cut -c6-40 | tr a-f A-F)
curl -s "https://api.pwnedpasswords.com/range/$PREFIX" | grep -i "^$SUFFIX"
```

```
<SUFFIX>:32567
```

Число после двоеточия — сколько раз пароль встречался. Наш пароль — в базе 32 567 раз: значит, он словарный и сезонный. Сам пароль при этом не покидал нашу машину — ушёл только префикс хэша.

## Шаг 3: активные сервисы — только с основанием

Если нужны **сами** данные, а не факт, используют активные сервисы: DeHashed, LeakCheck, Snusbase, IntelX. Они отдают записи по `email:`, `domain:` или `username:`.

Здесь начинается юридическая граница. Активный сервис отдаёт персональные данные конкретных людей. Работать с ним можно **только при наличии правового основания**: согласие организации, авторизованное задание, официальное расследование. Для CTF границы задаёт **условие задачи**, а не удобство.

Концептуально запрос выглядит так: `domain:example.com` — и вы получаете список утёкших записей этого домена. Именно такие результаты — самые чувствительные, и их нельзя публиковать.

## Шаг 4: от факта утечки к паттернам

Гораздо полезнее и безопаснее работать не с конкретными людьми, а с **паттернами** домена. Проверим домен целиком (нужен ключ с правом domain search):

```bash
curl -s -H "hibp-api-key: $KEY" -H "user-agent: osint-research" \
  "https://haveibeenpwned.com/api/v3/breacheddomain/example.com" | jq 'keys | length'
```

```
412
```

412 адресов домена фигурируют в утечках. Смотрим префиксы — они выдают структуру подразделений:

```bash
curl -s -H "hibp-api-key: $KEY" \
  "https://haveibeenpwned.com/api/v3/breacheddomain/example.com" | jq -r 'keys[]' | cut -d@ -f1 | sed 's/[0-9]//g' | sort | uniq -c | sort -rn | head -5
```

```
  88 dev
  61 admin
  40 hr
  27 sales
  19 support
```

Вывод не «мы нашли пароли», а **оценка парольной гигиены**: домен в 412 утечках, доминируют технические учётки, есть сезонные пароли вида `Company2024!`. Это законный и полезный для аудита артефакт.

## Шаг 5: корреляция «email → username → человек»

Утечка — это мост от цифрового следа к реальному человеку. Цепочка такая:

1. Утёкший email → поиск по username и в соцсетях.
2. Username → другие аккаунты (люди переиспользуют ник).
3. Профиль → компания, город, круг общения.
4. Сверка с открытыми реестрами — **только в рамках задания**.

Именно потому, что цепочка приводит к персональным данным, работа с утечками должна быть обоснована и ограничена.

## Шаг 6: credential stuffing и его этика

**Credential stuffing** — это использование утёкших логинов/паролей для входа в **другие** сервисы (люди переиспользуют пароли). Для пентеста это ценный аргумент в отчёте, но **вход в чужие аккаунты без авторизации — преступление**, а не пентест.

Если программа разрешает проверку, действуйте строго: берите только email в scope, проверяйте малую выборку, соблюдайте rate-limit, фиксируйте результат и немедленно останавливайтесь.

## Что мы теперь знаем

- HIBP сообщает **факт** утечки, DeHashed отдаёт **сами данные** — это разные риски и разная легальность.
- k-anonymity позволяет проверить пароль, не отправляя его целиком.
- Анализ домена даёт измеримые индикаторы (сколько учёток, какие префиксы, какие паттерны).
- От email через username можно дойти до человека — и поэтому нужна правовая дисциплина.
- Credential stuffing без задания — правонарушение.

## На что смотреть дальше

Разберись с изоляцией рабочего процесса: отдельная ВМ, шифрование данных **at-rest** (`gpg --symmetric`), удаление через `shred -u` вместо `rm`. Изучи, как пастам-сайты и Telegram-каналы публикуют свежие дампы — их можно **наблюдать** (фиксировать факт и дату), но не хранить. Дальше это пригодится в threat intelligence.

## Куда дальше

Мы научились оценивать компрометацию домена и отличать пассивные источники от активных. В следующем уроке — **пастам-сайты и Telegram-каналы**: где появляются свежие дампы, как за ними наблюдать и где проходит этическая граница. А пока главное запомни: утечки — это сначала факт и паттерны, и только потом данные, и только при наличии основания.

## Где пригодится

- **CTF (OSINT):** найти человека по email из утечки.
- **Threat intelligence:** оценить компрометацию домена и организации.
- **Bug bounty:** подтвердить credential stuffing в рамках программы.
- **Работа:** incident response и fraud-анализ.
