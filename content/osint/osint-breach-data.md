Утечки — самый прямой источник персональных данных: email, пароли, телефоны, адреса. Для OSINT это мост между «цифровым» и «реальным» человеком. Но работа с ними — область, где **легальность критична**: одно дело — проверить свой email в публичном сервисе, другое — скачивать и использовать базы.

В этом уроке — типы данных, пассивные и активные сервисы, корреляция, этические границы и разобранные примеры.

## Типы данных в утечках

- **Credentials** (email:password) — самое ценное для корреляции.
- **PII**: ФИО, телефон, адрес, паспортные данные.
- **Финансы**: карты (устаревшие), счета.
- **Корпоративные**: внутренние логины, доступы к VPN.
- **Сессионные токены/cookie** — иногда позволяют войти без пароля.
- **Метаданные** (IP регистрации, даты) — для атрибуции.

## Пассивные vs активные сервисы

| Тип | Пример | Что делает | Легальность |
|---|---|---|---|
| Пассивный | HIBP | сообщает факт утечки | проверка своего/корпоративного email |
| Активный | DeHashed, LeakCheck | отдаёт сами данные по запросу | требует авторизации/задания |
| Поиск по хэшам | CrackStation | сопоставление хэша | публичный |
| Мониторинг | HIBP Domain Search | следит за доменом | для организаций |

Ключевое различие: пассивный сервис говорит «этот email встречался в утечке X», активный — «вот пароль из этой утечки». Второе — чувствительно и допустимо только в рамках авторизованного задания.

## HIBP (Have I Been Pwned)

HIBP — **пассивный** сервис: вы проверяете email/домен, не скачивая базы.

```bash
# API (нужен ключ)
curl -s -H "hibp-api-key: $KEY" \
  "https://haveibeenpwned.com/api/v3/breachedaccount/user@example.com"

# список всех утечек
curl -s "https://haveibeenpwned.com/api/v3/breaches" | python3 -m json.tool | head

# проверка пароля по k-anonymity (первые 5 символов SHA-1)
echo -n "password" | sha1sum | cut -c1-5
curl -s "https://api.pwnedpasswords.com/range/5BAA6" | grep -i "$(echo -n password | sha1sum | cut -c6-40 | tr a-f A-F)"
```

`pwnedpasswords` использует k-anonymity: вы отправляете первые 5 символов хэша, сервис возвращает список суффиксов — сам пароль не уходит. Это корректный с точки зрения приватности способ.

## DeHashed и активные сервисы

DeHashed, LeakCheck, Snusbase, IntelX отдают записи по email/username/домену/паролю. Работа с ними:

- требует подписки/авторизации;
- допустима только при наличии правовых оснований (согласие, задание, расследование);
- результаты — персональные данные, их нельзя публиковать.

Типичный запрос (концептуально): `email:user@example.com`, `domain:example.com`, `username:jdoe`. По домену можно оценить, сколько корпоративных учёток утекло.

## Credential stuffing и его этика

Credential stuffing — использование утёкших логинов/паролей для входа в **другие** сервисы (люди переиспользуют пароли). Для пентеста это ценно как аргумент в отчёте (риск переиспользования), но **вход в чужие аккаунты без авторизации — незаконен**. В рамках задания допустимо только тестирование собственных/разрешённых систем.

## Анализ паттернов паролей

Даже без доступа к самим паролям полезно анализировать паттерны (по обезличенным данным или статистике):

- длина и состав (словарные vs случайные);
- сезонные паттерны (`Summer2024!`);
- переиспользование (один пароль на несколько сервисов);
- связь с брендом/названием компании.

Вывод такого анализа — рекомендации по парольной политике: длина важнее сложности, MFA, менеджеры паролей, проверка на утечки при смене.

## Разобранный пример: проверка корпоративного домена

1. HIBP Domain Search по `example.com` — получаем список утечек, где встречались адреса домена.
2. По каждой утечке — класс данных (только email или ещё пароли).
3. Оцениваем, сколько учёток скомпрометировано и в каких сервисах.
4. Проверяем, используются ли эти email во внутренних системах (SSO).
5. Вывод для отчёта: домен присутствует в N утечках; для M учёток утекли пароли; рекомендовать принудительную смену, MFA, мониторинг.

## Разобранный пример: от email к человеку

1. Утёкший email → поиск в соцсетях и по username.
2. Username → другие аккаунты (корреляция).
3. Из профиля — компания, город.
4. Сверка с открытыми реестрами (телефон, адрес — только в рамках задания).

Так «цифровой след» превращается в профиль — и именно поэтому работа с утечками должна быть обоснована и ограничена.

## Этические и правовые границы

- Проверка **своего** email — всегда легальна.
- Проверка корпоративного домена — с согласия организации.
- Скачивание и использование чужих баз — как правило, незаконно.
- Публикация персональных данных — нарушение (GDPR и аналоги).
- Использование для входа в чужие аккаунты — прямое правонарушение.

Правило: работайте с **фактом утечки** и **паттернами**, а не с персональными данными конкретных людей, если нет правовых оснований.

## Инструменты

| Инструмент | Тип | Назначение |
|---|---|---|
| HIBP | пассивный | факт утечки email/домена |
| Pwned Passwords | пассивный | проверка пароля (k-anonymity) |
| DeHashed/LeakCheck | активный | поиск записей |
| IntelX | активный | поиск по разным источникам |
| CrackStation | хэши | сопоставление хэш→пароль |
| Dehashed API | активный | автоматизация |

## Частые ошибки

- Путать «факт утечки» (HIBP) и «сами данные» (DeHashed).
- Считать устаревший пароль неважным — переиспользование делает его актуальным.
- Игнорировать k-anonymity и загружать пароли целиком.
- Публиковать найденные персональные данные.
- Забывать про легальность при скачивании баз.

## Что дальше / решение

Начните с HIBP (пассивно, безопасно), затем — при наличии оснований — активные сервисы. Анализируйте паттерны, а не конкретных людей. Для защиты: MFA, мониторинг утечек домена, запрет переиспользования паролей, проверка при смене. Утечки — мощный, но юридически чувствительный инструмент; дисциплина здесь важнее находок.

## Чек-лист работы с утечками

1. Определить правовые основания (своё/корпоративное/задание).
2. Проверить домен/email в HIBP (пассивно).
3. Оценить класс утёкших данных (только email или пароли).
4. При наличии оснований — активные сервисы по конкретным индикаторам.
5. Проанализировать паттерны паролей (обезличенно).
6. Сопоставить email с username/соцсетями (корреляция).
7. Сформулировать рекомендации (MFA, смена, мониторинг).
8. Не публиковать персональные данные; хранить результаты защищённо.

## Разобранный пример: анализ паттернов паролей (обезличенно)

Задача — оценить зрелость парольной политики организации по статистике утечек.

1. По домену собираем агрегаты (не сами пароли): доля словарных, средняя длина, наличие цифр/символов.
2. Смотрим сезонные паттерны (`Company2024!`, `Summer24`).
3. Оцениваем переиспользование: сколько email встречаются в нескольких утечках.
4. Сопоставляем с внутренней политикой (минимальная длина, сложность, срок жизни).
5. Формулируем выводы: длина важнее сложности; внедрить MFA; проверять пароли по HIBP при смене; запретить переиспользование; менеджер паролей.

Так отчёт говорит не «мы нашли пароли», а «политика незрелая, вот измеримые индикаторы и план улучшения» — что и требуется заказчику.

## Проверка домена и сотрудников

Корпоративная утечка — это не один email, а паттерн. Проверяйте **домен целиком**:

```bash
# HIBP domain search (нужен ключ с правом domain search, владелец подтверждает домен)
curl -s -H "hibp-api-key: $KEY" -H "user-agent: osint-research" \
  "https://haveibeenpwned.com/api/v3/breacheddomain/example.com" | jq .
```

Дальше — оценка масштаба:

- Сколько уникальных адресов домена фигурирует в утечках.
- Какие утечки самые свежие (актуальность).
- Какие префиксы доминируют (`dev@`, `admin@`, `hr@`) → структура подразделений.
- Есть ли **корпоративные** пароли в паттерне (например, `Company<год>`).

Это даёт не «список жертв», а **оценку парольной гигиены организации** — законный вывод для аудита.

## Telegram-каналы и пастам: этика работы

Свежие дампы часто появляются в Telegram-каналах и на pastebin. Правила:

- **Пассивное наблюдение** за каналом (чтение заголовков, заявленных объёмов) — как правило, допустимо для оценки рисков.
- **Скачивание и хранение** дампа с персональными данными — обычно нет; вы становитесь держателем чужих ПД.
- **Использование** данных для доступа — незаконно.
- **Фиксация факта** («домен фигурирует в дампе X от даты Y») — законный артефакт для отчёта.

Для CTF/авторизованного пентеста границы задаёт **задание**, а не удобство.

## Построение безопасного рабочего процесса

Если работа с утечками разрешена, изолируйте её:

```bash
# отдельная ВМ/контейнер без доступа к личным аккаунтам
# данные шифруем at-rest
gpg --symmetric --cipher-algo AES256 dump.txt      # → dump.txt.gpg
# работаем только с .gpg, плейнтекст удаляем
shred -u dump.txt
```

Правила гигиены:

- Никогда не используйте найденные пароли для входа, кроме явного PoC по правилам программы.
- Минимизируйте: храните только те записи, что нужны для вывода.
- Логируйте доступ к данным (кто, когда, зачем).
- По завершении — **удалите** дампы (shred, а не rm).
- Отчёт пишите **без** сырых PII — только выводы и агрегаты.

## Оценка credential stuffing

Если программа bug bounty разрешает проверку:

1. Возьмите **только** email в scope (сотрудники/домен).
2. Проверьте **малую** выборку через официальный endpoint (не автоматизируйте массово).
3. Соблюдайте rate-limit и не создавайте нагрузки.
4. Зафиксируйте: сколько сработало, на каком сервисе, дата.
5. Немедленно остановитесь и сообщите — не продолжайте перебор.

Никогда не применяйте «молчаливый» credential stuffing к третьим сервисам — это преступление, а не пентест.

## Чек-лист работы с утечками

- [ ] Есть правовое основание/задание.
- [ ] Использованы пассивные источники, где возможно.
- [ ] Данные изолированы и зашифрованы.
- [ ] Персональные данные не покидают изолированную среду.
- [ ] Проверки (если разрешены) — малые, read-only, rate-limited.
- [ ] Выводы сформулированы без раскрытия PII.
- [ ] Данные удалены после завершения.
- [ ] Отчёт содержит оценку риска и рекомендации (MFA, ротация, обучение).

## Где пригодится

- **CTF (OSINT):** найти человека по email из утечки.
- **Threat intelligence:** оценить компрометацию домена/организации.
- **Bug bounty:** подтвердить credential stuffing в рамках программы.
- **Работа:** incident response и fraud-анализ.
