## Вопрос, с которого всё начинается

Ты уже умеешь собирать поддомены руками через `crt.sh` и `dig`, но на реальной цели имён сотни. Ручной обход превращается в часы, а часть хостов всё равно остаётся незамеченной. Нужен **конвейер** инструментов, который соберёт, проверит и отфильтрует всё автоматически.

Разберём этот конвейер на одном домене от начала до конца.

## Наш пример: домен example.com

Введём термины. **Пассивный сбор** — поиск поддоменов по чужим базам (логи сертификатов, архивы, поисковики), без запросов к самой цели. **Активный сбор** — прямые DNS-запросы и брутфорс словарём, он заметен для цели. Наша цель `example.com`; посмотрим, сколько имён реально скрыто.

## Шаг 1: пассивный сбор через subfinder

**subfinder** опрашивает десятки пассивных источников (CT-логи, пассивный DNS, поисковики):

```bash
subfinder -d example.com -silent
```

Вывод (фрагмент):

```
www.example.com
api.example.com
dev.example.com
staging.example.com
mail.example.com
```

Флаг `-all` включает все источники, `-recursive` — рекурсивный поиск, `-t` задаёт потоки. Инструмент пассивен и незаметен для цели.

## Шаг 2: расширяем охват через amass и другие источники

**amass** тяжелее и мощнее. Режим `intel` особенно полезен — он перечисляет домены, связанные с автономной системой:

```bash
amass intel -asn 200350
amass enum -passive -d example.com -o amass.txt
```

Дополняют картину:

- **assetfinder** — `assetfinder --subs-only example.com`.
- **chaos** — публичная база ProjectDiscovery: `chaos -d example.com`.
- **gau** — URL-ы из архивов: `gau example.com | grep -oE '[a-z0-9.-]+\.example\.com' | sort -u`.

Источник `gau` вытаскивает имена, которых сегодня нет в DNS, но которые когда-то существовали — часто это забытые стенды.

## Шаг 3: резолвим и проверяем живой веб-слой

Собрали список — теперь отбрасываем мёртвые. Сначала резолв через **dnsx**:

```bash
subfinder -d example.com -silent > subs.txt
assetfinder --subs-only example.com >> subs.txt
sort -u subs.txt -o subs.txt
dnsx -l subs.txt -silent -a -resp -o resolved.txt
```

Затем проверяем, кто из них реально отвечает по HTTP, через **httpx**:

```bash
httpx -l subs.txt -silent -status-code -title -tech-detect -o live.txt
```

Вывод:

```
https://dev.example.com [200] [Dev Portal] [nginx,React]
https://staging.example.com [401] [Staging] [nginx]
https://api.example.com [403] [AmazonS3] [cloudfront]
```

Мы сразу видим статус, заголовок и технологии. `dev` с 200 и `staging` с 401 — приоритетные цели. Флаг `-td` включает tech-detect, `-sc` — статус-код, `-title` — заголовок страницы.

## Шаг 4: приоритизируем находки

Отсортируем по «интересности»:

1. **Живые** (200/401/403) важнее мёртвых.
2. **Имена-намёки**: `admin`, `dev`, `staging`, `test`, `internal`, `jenkins`, `git`, `vpn`, `api`, `db`.
3. **Нестандартные порты** (`:8080`, `:8443`) — часто внутренние сервисы.
4. **Дубли по IP** — один сервер, много имён.

Отдельно стоит проверить имена, которых нет в DNS сегодня, но которые всплыли в архивах или коде: они часто указывают на снятые с продакшена, но всё ещё живые стенды.

```bash
grep -iE 'admin|dev|staging|test|internal|jenkins|git|vpn|api|db' live.txt
```

## Шаг 5: ищем subdomain takeover

**Subdomain takeover** — это сценарий, когда поддомен имеет `CNAME` на внешний сервис (GitHub Pages, Heroku, S3), который больше не обслуживается. Атакующий регистрирует ресурс и «занимает» поддомен. Признаки видны в теле ответа:

```bash
dig +short dev.example.com CNAME
curl -s "http://dev.example.com" | grep -iE 'NoSuchBucket|There isn.t a GitHub Pages site|No such app'
```

Для автоматизации — **subjack** и шаблоны nuclei:

```bash
nuclei -l subs.txt -t http/takeovers/ -silent
```

Список сервисов и их признаков ведётся в проекте **can-i-take-over-xyz**. Важно: **не эксплуатируй** takeover даже если нашёл — сначала убедись, что домен **в scope**, и следуй правилам программы.

## Шаг 6: обходим wildcard DNS

Крупные цели часто включают **wildcard DNS**: `*.example.com` резолвится в один IP, и любой случайный поддомен «жив». Это ломает перебор — получаешь тысячи ложных попаданий. Проверка:

```bash
dig +short random123.example.com
```

Если отвечает — wildcard активен. Обход: сравнивай ответы и отбрасывай совпадающие (одинаковый IP), используй уникальные метки (`random-<uuid>.example.com`), а `puredns` умеет `--wildcard-tests` и отфильтровывает их сам.

## Шаг 7: обогащаем результат

На живых хостах добавляют признаки, которые находят «невидимые» стенды:

- **JARM** — отпечаток TLS-сервера; одинаковый JARM выдаёт хосты одного продукта.
- **Favicon hash** — `httpx -favicon`, затем поиск хэша в Shodan/FOFA находит забытые стенды.
- **CDN-признак** — `httpx -cdn` показывает, за CDN ли хост; хосты без CDN — прямые цели.

```bash
httpx -l subs.txt -silent -jarm -favicon -cdn -o enriched.txt
```

## Шаг 8: работаем с большими целями

На крупных программах поддоменов тысячи, и наивный перебор упирается в скорость DNS. Приёмы масштабирования:

- **Свой список резолверов** (`dnsx -r resolvers.txt`) вместо системного — в разы быстрее и устойчивее.
- **Массовый резолв** через `massdns`/`puredns` для десятков тысяч имён:

```bash
puredns resolve subs.txt -r resolvers.txt -w resolved.txt
```

- **Потоки** — `dnsx -t 100`, `httpx -t 100`, но следи за нагрузкой на цель.
- **Инкрементальность** — храни прошлые списки и считай diff, чтобы видеть только новые хосты.

## Что мы теперь знаем

- Пассивный сбор (subfinder, amass, chaos, gau) незаметен для цели.
- dnsx резолвит список, httpx отбирает живой веб-слой.
- Приоритет — имена-намёки (`dev`, `staging`, `admin`) и нестандартные порты.
- Subdomain takeover ищут по dangling CNAME и признакам в теле ответа.
- Wildcard DNS ломает перебор, если его не фильтровать.

## Частые ошибки

- Использовать один инструмент и считать охват полным.
- Не проверять резолв — половина списка мертва.
- Игнорировать takeover-признаки в теле ответа.
- Забывать про wildcard и тонуть в ложных попаданиях.
- Эксплуатировать takeover вне scope.

## На что смотреть дальше

Пассивные инструменты не дают 100% покрытия — комбинируй несколько и храни списки между запусками, считая diff (`comm -13 <(sort prev.txt) <(sort subs.txt)`) — так видишь новые хосты. Дальше разберём **брутфорс поддоменов**: активный метод там, где пассивного не хватает. А пока главное запомни: охват — это конвейер «собрать → резолвить → проверить → приоритизировать».

## Разбор кейса: subdomain takeover на практике

Subdomain takeover — это когда поддомен цели указывает (через CNAME) на сервис, который больше не существует. Например, `blog.example.com` → `example-blog.herokuapp.com`, а приложение на Heroku удалено. Тогда любой может зарегистрировать то же имя на Heroku и получить контроль над `blog.example.com`. Это классическая находка в bug bounty.

Пайплайн поиска: сначала собрать поддомены (subfinder), затем резолвить (dnsx) и получить CNAME (`dig CNAME`). Затем сверить CNAME с базой «уязвимых» сервисов: herokuapp, github.io, s3.amazonaws.com, azurewebsites.net, cloudfront.net. Если CNAME указывает на такой сервис, а сам сервис отдаёт «not found» — это кандидат. Проверка кандидата: запрос к поддомену возвращает страницу-заглушку сервиса («There is no app here»). Это сильный признак. Но подтверждать надо осторожно: захват чужого поддомена — это уже действие, требующее авторизации. В рамках программы достаточно зафиксировать доказательство и отправить в отчёт. Инструмент `subjack` автоматизирует сверку, но даёт ложные срабатывания, поэтому финальную проверку делают вручную.

## Если не сработало

**subfinder не находит поддоменов.** Добавь источники: `-all`, `-recursive`, плюс CT-логи через crt.sh. Часто нужный поддомен есть только в одном источнике.

**CNAME не виден.** Используй `dig +noall +answer CNAME` или `dnsx -cname`. Иногда CNAME скрыт за CDN.

**Заглушка похожа, но сервис жив.** Проверь HTTP-код и тело ответа. «404» на сервисе — не то же самое, что «сервис не существует».

**Нет базы уязвимых сервисов.** Веди свою: список сервисов, которые позволяют занять имя. Он пополняется по мере находок.

## Частые вопросы

**Это законно?** Находить и фиксировать — да. Захватывать — только в рамках авторизованной программы.

**Почему это опасно?** Захваченный поддомен доверенный: он на домене цели, значит, его можно использовать для фишинга, кражи cookie, обхода CSP.

**Как защититься?** Убирать CNAME при удалении сервиса, мониторить «висячие» записи, использовать проверку владения.

## Мини-практика: конвейер одной строкой

Собери базовый пайплайн в одну строку и посмотри, как он работает на реальном домене (в рамках авторизации):

```bash
subfinder -d example.com -silent | dnsx -silent -a -cname -resp | httpx -silent -sc -title -tech-detect
```

Здесь subfinder собирает имена, dnsx резолвит их и вытаскивает CNAME, httpx проверяет живой веб-слой и технологии. Прогони дважды с разницей в день — увидишь, как меняется поверхность. Затем добавь проверку takeover: `subjack -w subs.txt -t 100 -ssl`. Отдельно проверь wildcard: если `httpx` показывает одинаковый заголовок для всех имён, домен использует wildcard, и результат надо фильтровать. Этот прогон учит главному: поддомены — не статичный список, а живой слой, который надо проверять регулярно и не доверять одному инструменту.

## Проверка гигиены DNS

Собранный список поддоменов — это ещё и аудит гигиены. Отметь: поддомены с истёкшими CNAME (кандидаты на takeover), устаревшие стенды (dev, test, old), имена с внутренними терминами, оставшиеся в публичном DNS по ошибке. Такой список полезен и заказчику: он показывает, где инфраструктура «протекает». Регулярный прогон пайплайна и сравнение снимков превращает разовую разведку в мониторинг поверхности атаки.

## Куда дальше

Мы собрали конвейер пассивного перечисления и научились приоритизировать находки. В следующем уроке — **брутфорс поддоменов**: активный метод и то, как его применять, не нарушая правила программы. А пока главное запомни: поддомен, которого нет в пассивных базах, всё ещё может существовать — его находит словарь.

## Где пригодится

- **CTF:** полный охват домена из задания.
- **Bug bounty:** максимизация охвата scope и поиск takeover.
- **Пентест:** инвентаризация внешней поверхности перед атакой.
- **Blue team:** контроль собственных «висячих» записей.
