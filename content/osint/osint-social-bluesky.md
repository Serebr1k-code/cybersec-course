## Вопрос, с которого всё начинается

В Bluesky у аккаунта есть ник вида `@nordwind.bsky.social`, но за ним стоит **DID** — постоянный идентификатор, который нельзя переиспользовать. А ещё у каждого аккаунта есть свой сервер данных (PDS). Как получить это из публичного API, не создавая аккаунт?

Задача: по DID получить документ и вытащить адрес PDS и связанный хендл.

## Наш пример: DID из профиля

Держим идентификатор `did:plc:abc123example`. AT Protocol хранит такие DID в открытом **PLC directory** — это реестр, который можно опросить без авторизации.

```bash
curl -s https://plc.directory/did:plc:abc123example > did.json
```

## Шаг 1: что такое DID и AT Protocol

**AT Protocol** (ATProto) — открытый протокол, на котором работает Bluesky. Вместо «аккаунт на одном сервере» здесь есть:
- **DID** — децентрализованный идентификатор (`did:plc:...`), постоянный;
- **handle** — удобный ник (`nordwind.bsky.social`), привязанный к DID;
- **PDS** — персональный сервер данных, где лежат записи пользователя.

DID не меняется, даже если пользователь сменит хендл. Поэтому для атрибуции DID надёжнее ника.

## Шаг 2: резолвим DID

PLC directory возвращает JSON-документ:

```bash
cat did.json
```

```text
{"id":"did:plc:abc123example",
 "alsoKnownAs":["at://nordwind.bsky.social"],
 "service":[{"type":"AtprotoPersonalDataServer","serviceEndpoint":"https://pds.example.net"},
            {"type":"AtprotoLabeler","serviceEndpoint":"https://labeler.example.net"}],
 "x_flag":"nto{blu3sky_pds_r3s0lv3d}"}
```

Ключевые поля: `alsoKnownAs` — связанный хендл, `service` — сервисы, среди них PDS.

## Шаг 3: достаём PDS и хендл

```bash
jq -r '.service[]?.serviceEndpoint' did.json
```

```text
https://pds.example.net
https://labeler.example.net
```

Первый — PDS, то есть сервер, где живут записи пользователя. Второй — лейблер (сервис маркировки контента).

```bash
jq -r '.alsoKnownAs[]' did.json
```

```text
at://nordwind.bsky.social
```

Теперь у нас есть и хендл, и сервер данных — этого достаточно, чтобы запросить публичные записи через API PDS.

## Шаг 4: публичный API

Публичный читающий API Bluesky доступен по адресу `public.api.bsky.app/xrpc/...`. Например, профиль:

```bash
# иллюстративно
# curl -s 'https://public.api.bsky.app/xrpc/app.bsky.actor.getProfile?actor=nordwind.bsky.social'
```

```text
{"did":"did:plc:abc123example","handle":"nordwind.bsky.social","displayName":"Nordwind"}
```

Обрати внимание: API принимает и хендл, и DID. Хендл может смениться — DID нет.

## Полный прогон

```bash
curl -s https://plc.directory/did:plc:abc123example > did.json
jq -r '.alsoKnownAs[]' did.json            # хендл
jq -r '.service[]?.serviceEndpoint' did.json  # PDS + labeler
```

Непрерывно: DID → документ → хендл → PDS → публичные записи.

## Если не сработало

**DID не резолвится.** Возможно, это `did:web`, а не `did:plc` — тогда документ лежит на самом домене.
**Хендла нет.** Аккаунт мог быть удалён или заблокирован.
**PDS недоступен.** Сервер мог отключиться — записи недоступны, но DID остаётся.

## Частые ошибки

**Ошибка: путать DID и хендл.** Хендл меняется, DID — нет.
**Ошибка: думать, что нужен аккаунт.** Публичный API читается анонимно.
**Ошибка: игнорировать `alsoKnownAs`.** Именно там лежит связь с хендлом.
**Ошибка: считать один PDS единственным.** У крупных сервисов своя инфраструктура.

## Справочная таблица: артефакты AT Protocol

| Артефакт | Пример | Что даёт |
|----------|--------|----------|
| DID | `did:plc:abc123example` | постоянный идентификатор |
| Handle | `nordwind.bsky.social` | удобный ник |
| PLC document | `plc.directory/<did>` | хендл + сервисы |
| PDS | `pds.example.net` | сервер записей |
| Public API | `public.api.bsky.app/xrpc/...` | чтение без аккаунта |

## Что мы теперь знаем

1. В Bluesky за ником стоит постоянный DID.
2. PLC directory отдаёт документ с хендлом и сервисами.
3. PDS — сервер, где лежат записи пользователя.
4. Публичный API читается без авторизации.
5. Для атрибуции DID надёжнее хендла.

## Разбор кейса: от хендла к записям

Проследим путь. На входе — хендл `nordwind.bsky.social`. На выходе — DID, PDS и публичные записи.

**Шаг первый.** Резолвим хендл в DID через публичный резолвер (или через документ `did:plc`). Получаем `did:plc:abc123example`.

**Шаг второй.** Запрашиваем `plc.directory/did:plc:abc123example`. Из документа достаём `alsoKnownAs` (хендл) и `service` (PDS, labeler).

**Шаг третий.** По адресу PDS читаем публичные записи через XRPC-методы. Например, профиль и ленту заметок.

**Шаг четвёртый.** Фиксируем DID как якорь: даже если человек сменит хендл, DID останется и позволит найти его заново.

**Итог.** Мы получили устойчивый идентификатор и источник данных без аккаунта.

## Рабочий воркбук: Bluesky за пять шагов

1. **Хендл → DID.** Разреши хендл в DID (резолвер или DNS-запись `_atproto`).
2. **DID-документ.** Запроси документ и выпиши `alsoKnownAs` и `service`.
3. **PDS.** Найди сервер данных пользователя.
4. **Чтение.** Через XRPC получи профиль и записи.
5. **Якорь.** Сохрани DID — это ключ для повторного поиска.

## Частые вопросы

**Нужен ли аккаунт Bluesky?** Для чтения публичных данных — нет.

**Что если DID — `did:web`?** Тогда документ лежит на самом домене, а не в PLC directory.

**Можно ли связать Bluesky и Mastodon?** Обе федеративны, но протоколы разные (ATProto и ActivityPub). Связь ищут через одинаковые хендлы и контент.

**Что такое labeler?** Сервис маркировки контента, тоже указан в DID-документе.

**Почему DID надёжнее ника?** Ник меняется, DID — постоянный идентификатор.

## Термины

**AT Protocol** — открытый протокол, на котором работает Bluesky.

**DID** — децентрализованный идентификатор, постоянный.

**Handle** — удобный ник, привязанный к DID.

**PDS** — персональный сервер данных пользователя.

**PLC directory** — публичный реестр `did:plc`-документов.

**XRPC** — HTTP-методы AT Protocol для чтения/записи.

## Связь с другими уроками

Bluesky — часть блока федеративных платформ (`osint-mod-social-federated`) вместе с **Nostr** и **Matrix**. Приём «резолв публичного идентификатора» общий: у Nostr это `npub`, у Matrix — homeserver, у Bluesky — DID. Освоив его, ты работаешь с любой федеративной сетью.

## Практикум: связать Bluesky с Mastodon

Федеративные сети не связаны напрямую, но человека можно найти в обеих по одинаковому нику или контенту.

**Шаг первый.** В Bluesky получаем хендл `nordwind.bsky.social` и DID.

**Шаг второй.** Ищем тот же ник на Mastodon-инстансах: `@nordwind@mastodon.example`.

**Шаг третий.** Сравниваем био и аватары. Совпадение двух признаков — гипотеза, трёх — уверенность.

**Шаг четвёртый.** Ищем перекрёстные упоминания: ссылки из одного профиля на другой.

Что важно: в ATProto ключ — DID, в ActivityPub — `@user@server`. Оба идентификатора публичны, но устроены по-разному. Твоя задача — не спутать их и корректно сопоставить.

## Сценарии CTF и расследований

**CTF, базовая задача.** Дан DID. Нужно достать PDS. Решение: запросить документ и выписать `serviceEndpoint`.

**CTF, средняя задача.** Дан хендл. Нужно получить постоянный идентификатор. Решение: резолв хендла в DID.

**Расследование.** Аккаунт сменил ник. Нужно найти его снова. Решение: по сохранённому DID.

**Мониторинг.** Нужно отслеживать записи. Решение: периодический запрос к публичному API по DID.

Ключевой навык — работать с DID как с якорем: хендлы меняются, DID — нет.

## Расширенный разбор: DID как якорь атрибуции

Почему в ATProto так важен DID и как это меняет разведку — разберём подробно.

В централизованных сетях идентификатор — это ник или внутренний числовой ID, привязанный к одному серверу. Сменил ник — потерял связь. Удалил аккаунт — всё исчезло. В ATProto иначе: есть DID, который не меняется, и есть хендл, который можно менять сколько угодно. Хендл — это удобство для человека, DID — это якорь для данных.

Практический вывод: если ты сохранил DID, ты найдёшь аккаунт даже после смены ника. Более того, DID-документ содержит историю сервисов и текущий хендл, поэтому по одному DID можно восстановить связи. Это делает атрибуцию устойчивой во времени.

Дальше — PDS. В классической сети все данные на одном сервере. В ATProto пользователь может перенести данные на другой PDS. Это значит, что один и тот же DID может обслуживаться разными серверами в разное время. Для разведки это важно: старый PDS может хранить копии, а новый — актуальные записи. Опроси оба.

Ещё один нюанс — публичность. ATProto проектировался как «глобально читаемый» протокол: записи доступны через публичный API. Это не утечка, а свойство дизайна. Но публичность не отменяет этику: читать можно, преследовать — нет.

Отдельно про связку с ActivityPub. Bluesky и Mastodon — разные протоколы, но иногда одного человека можно найти в обеих сетях. Мост — не технический, а человеческий: одинаковый ник, одинаковый контент, перекрёстные ссылки. Ищи эти совпадения, но не выдавай их за тождество без подтверждений.

Наконец, про верификацию. Хендл можно подтвердить через DNS-запись `_atproto` на собственном домене. Если человек использует домен как хендл, это даёт дополнительный признак: владение доменом. Так технический артефакт превращается в подтверждённую связь.

## Итоговая шпаргалка

| Объект | Стабильность | Что даёт |
|--------|-------------|----------|
| DID | постоянный | якорь атрибуции |
| Хендл | меняется | удобный поиск |
| PDS | может меняться | источник записей |
| `_atproto` DNS | проверяемый | подтверждение хендла |

Сохраняй DID — это твой самый надёжный ключ в федеративной сети.

## Практическое замечание о повторном поиске

Bluesky-аккаунты меняют хендлы, но DID остаётся. Это значит, что твой рабочий процесс должен хранить DID, а не ник. Сделай простую привычку: как только нашёл аккаунт, сразу выпиши его DID в отдельный список. Периодически прогоняй этот список через резолвер — так ты заметишь смену хендла и не потеряешь объект. Дополнительно сохраняй DID-документ целиком: он содержит и хендл, и список сервисов на момент проверки. Разница между старым и новым документом покажет, что изменилось, и это само по себе является разведывательным сигналом.

- **Атрибуция:** постоянный DID вместо меняющегося ника.
