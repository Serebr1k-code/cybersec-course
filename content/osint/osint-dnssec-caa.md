## Вопрос, с которого всё начинается

Ты смотришь на домен цели и видишь обычный сайт. Но под ним лежит слой, который рассказывает о зрелости её безопасности: подписывает ли она свои DNS-ответы, ограничивает ли, кто может выпустить ей сертификат, защищена ли почта от спуфинга. Всё это — **защитные DNS-записи**, и они открыты.

Разберём, как из них собрать «профиль гигиены» домена и что каждая слабость означает.

## Наш пример: профиль гигиены example.com

Введём термины. **DNS-запись** — это строка в зоне домена: например, адрес сервера (`A`) или почтовый сервер (`MX`). Кроме них есть **защитные записи**, которые объявляют правила безопасности. Совокупность этих записей — «профиль зрелости» домена. Пройдём по нему для `example.com`.

## Шаг 1: проверяем DNSSEC

**DNSSEC** криптографически подписывает DNS-ответы, чтобы их нельзя было подменить. Проверяем:

```bash
dig +dnssec +multi example.com A
```

Смотрим флаг `ad` (Authenticated Data) в ответе:

```
;; flags: qr rd ra ad; QUERY: 1, ANSWER: 1, ...
```

`ad` — резолвер подтвердил подпись. Если флага нет — либо DNSSEC не настроен, либо резолвер не проверяет. Смотрим цепочку доверия:

```bash
dig +dnssec example.com DNSKEY +short
dig +dnssec example.com DS +short
```

Важный нюанс: **broken DNSSEC** — это когда `DNSKEY` есть, а `DS` у родительской зоны нет. Такая зона ломается для проверяющих резолверов и хуже, чем полное отсутствие DNSSEC.

## Шаг 2: читаем CAA

**CAA** (Certification Authority Authorization) ограничивает, какие удостоверяющие центры вправе выпустить сертификат на домен:

```bash
dig +short example.com CAA
```

Вывод:

```
0 issue "letsencrypt.org"
0 issuewild "letsencrypt.org"
0 iodef "mailto:security@example.com"
```

Типы: `issue` — кто может выпускать обычные сертификаты, `issuewild` — wildcard, `iodef` — куда сообщать о нарушениях (email безопасности — отличный pivot). Если CAA отсутствует, любой CA может выпустить сертификат — риск **misissuance**. Если CAA разрешает только Let's Encrypt, а живой сертификат выдан DigiCert — это аномалия, требующая объяснения.

## Шаг 3: разбираем TXT-записи

TXT — самая насыщенная разведданными зона. Смотрим все:

```bash
dig +short example.com TXT
```

Вывод:

```
"v=spf1 include:_spf.google.com include:mailgun.org -all"
"google-site-verification=abc123"
"MS=ms12345678"
"v=DMARC1; p=reject; rua=mailto:dmarc@example.com"
"stripe-verification=..."
```

Разбор:

- **SPF** — список авторизованных отправителей почты. `include:` раскрывает почтовых провайдеров (Google, Mailgun). Суффикс `-all` — жёсткая политика (запрет остальных), `~all` — мягкая, `+all` — открытый релей (плохо).
- **DMARC** — политика `p=` (`none`/`quarantine`/`reject`).
- **Верификационные TXT** (`google-site-verification`, `MS=`, `stripe-verification`) — это **прямой список SaaS-вендоров компании**. Ценный результат сам по себе.

## Шаг 4: проверяем MTA-STS и TLS-RPT

```bash
dig +short _mta-sts.example.com TXT
# "v=STSv1; id=20260101T000000;"
dig +short _smtp._tls.example.com TXT
# "v=TLSRPTv1; rua=mailto:tlsrpt@example.com"
```

**MTA-STS** говорит: «мой SMTP требует TLS». **TLS-RPT** — отчёты о TLS-проблемах. Наличие обеих записей = зрелая почтовая гигиена; их отсутствие — вектор downgrade-атаки на почту.

## Шаг 5: разбираем DMARC детально

DMARC-запись содержит теги, каждый из которых влияет на защиту:

```
v=DMARC1; p=reject; sp=quarantine; pct=100; rua=mailto:dmarc@example.com; adkim=s; aspf=r
```

| Тег | Значение |
|---|---|
| `p` | политика для домена: none/quarantine/reject |
| `sp` | политика для поддоменов |
| `pct` | процент писем под политику |
| `rua` | адрес агрегированных отчётов |
| `adkim` / `aspf` | выравнивание DKIM/SPF (strict/relaxed) |

Опасные конфигурации: `p=none` (только мониторинг, спуфинг возможен), `pct<100` (часть писем не фильтруется), `aspf=r` (relaxed — позволяет поддомены в `From`), отсутствие `rua` (никто не видит атак).

## Шаг 6: перебираем DKIM-селекторы

DKIM-ключи лежат по адресу `selector._domainkey.domain`. Селекторы перебирают из распространённых:

```bash
for s in default selector1 selector2 google s1 mail dkim; do
  key=$(dig +short "$s._domainkey.example.com" TXT)
  [ -n "$key" ] && echo "$s: ${key:0:60}..."
done
```

Найдя селектор, проверяют длину ключа: 1024 бита — слабо, 2048 — норма.

## Шаг 7: собираем профиль целиком

Один скрипт — полный профиль:

```bash
D=example.com
echo "== DNSSEC =="; dig +dnssec $D A | grep -o 'flags:[^;]*'
echo "== CAA ==";    dig +short $D CAA
echo "== SPF ==";    dig +short $D TXT | grep spf1
echo "== DMARC ==";  dig +short _dmarc.$D TXT
echo "== MTA-STS ==";dig +short _mta-sts.$D TXT
```

Итог для `example.com`: DNSSEC настроен (хорошо), но CAA нет, SPF `~all` (мягко), DMARC `p=none` (спуфинг возможен), MTA-STS нет. Профиль — «частично зрелый»: домен потенциально уязвим к email-спуфингу и misissuance сертификата.

## Шаг 8: смотрим инструменты и историю

Для быстрой проверки без ручного `dig` есть готовые сервисы:

| Инструмент | Что проверяет |
|---|---|
| `dig +dnssec` | DNSSEC, флаг `ad` |
| `dmarcian` / `MXToolbox` | SPF/DKIM/DMARC |
| `testssl.sh` | TLS-конфигурация |
| `hardenize.com` | полный профиль домена |

Гигиена меняется во времени: сравнивая записи через архивы, видно эволюцию. Год назад DMARC был `p=none`, сейчас `p=reject` — компания усилила почту; бывает и регресс. Такие тренды ценны для отчёта и оценки зрелости.

## Что мы теперь знаем

- Защитные DNS-записи — это публичный профиль зрелости домена.
- Флаг `ad` в `dig +dnssec` подтверждает валидную DNSSEC-подпись.
- CAA ограничивает список CA; его отсутствие = риск misissuance.
- Верификационные TXT раскрывают используемые SaaS-сервисы.
- DMARC `p=none` и SPF `~all` оставляют домен уязвимым к спуфингу.

## Частые ошибки

- **Путать отсутствие DNSSEC с поломкой.** Broken DNSSEC (есть DNSKEY, нет DS) хуже.
- **Считать CAA абсолютной защитой.** CA может проигнорировать её при компрометации.
- **Игнорировать верификационные TXT.** Это список SaaS-вендоров.
- **Смотреть только SPF.** DMARC без SPF/DKIM бессмыслен.
- **Доверять кэшу резолвера.** Для актуальной картины — `+trace`.

## На что смотреть дальше

Слабая гигиена — это готовый вектор: `DMARC p=none` плюс отсутствие SPF `-all` дают email-спуфинг, отсутствие CAA — misissuance сертификата, broken DNSSEC — DNS-подмену. Дальше разберём **dangling CNAME и захват поддомена** — самый опасный класс DNS-ошибок. А пока главное запомни: защитные записи — это не только защита, но и признание в слабости.

## Куда дальше

Мы научились читать защитные записи и собирать профиль зрелости домена. В следующем уроке — **захват поддомена через dangling CNAME**: как висячая DNS-запись превращается в полноценную уязвимость. А пока главное запомни: слабая гигиена — это находка, а не просто «плохая практика».

## Где пригодится

- **Bug bounty:** слабая email-гигиена (DMARC none) — валидная находка.
- **CTF (OSINT):** в TXT-записях спрятаны верификационные токены и подсказки.
- **Аудит:** оценка зрелости DNS-конфигурации организации.
- **Пентест:** выявление SaaS-вендоров и векторов спуфинга.
- **Blue team:** проверка собственной гигиены (CAA, DNSSEC, DMARC).
