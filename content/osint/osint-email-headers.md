## Вопрос, с которого всё начинается

Тебе пришло письмо «от банка» с просьбой срочно войти в аккаунт. На глаз — настоящий логотип и подпись. Как понять, подделка это или нет?

У каждого письма есть **заголовки** (headers) — служебные поля, которые фиксируют путь письма через серверы и подлинность домена отправителя. Читать их — обязательный навык. Разберём это на одном письме.

## Наш пример: файл message.eml

У нас один объект — `message.eml`. **`.eml`** — это канонический формат письма: текстовый файл, где заголовки идут до первой пустой строки, а дальше — тело. Экспортировать письмо в `.eml` умеют все клиенты (в Gmail — «Показать оригинал»).

## Шаг 1: сравниваем From и Return-Path

Первое, что смотрят, — расхождение полей:

```bash
grep -iE '^(From|Return-Path|Reply-To):' message.eml
```

```
From: Sberbank <info@sberbank.ru>
Return-Path: <bounce@evil.example>
Reply-To: support@sberbank-secure.evil.example
```

Поле `From` — это то, что видит получатель, и оно подделывается за секунды. А `Return-Path` — реальный адрес отправителя на уровне SMTP. Здесь они не совпадают: письмо «от банка» фактически отправлено с `evil.example`. Первый красный флаг.

## Шаг 2: читаем цепочку Received

Поле `Received` добавляется каждым сервером, через который прошло письмо. Читать его надо **снизу вверх** — самая нижняя строка это первый (исходный) сервер отправителя:

```bash
grep -i '^Received:' message.eml | tail -1
```

```
Received: from evil.example (evil.example [45.13.22.100])
        by mx.google.com with ESMTPS id abc123
        for <me@gmail.com>; Mon, 12 May 2025 14:33:01 +0300
```

Исходный сервер — `evil.example` с IP `45.13.22.100`. Признаки подделки, на которые смотрят: рассинхрон часов между хопами, отсутствие обратной DNS-записи у IP и слово `localhost` в нижней строке (значит, письмо сгенерировано локальным скриптом).

## Шаг 3: смотрим готовый вердикт

Почтовый сервер уже проверил письмо и оставил результат в поле `Authentication-Results`:

```bash
grep -iE 'Received-SPF|Authentication-Results' message.eml
```

```
Authentication-Results: mx.google.com; spf=fail dkim=none dmarc=fail
```

Расшифруем три проверки:

- **SPF** — списком в DNS домен заявляет, какие серверы вправе слать от его имени. `fail` значит: IP отправителя не авторизован.
- **DKIM** — криптоподпись письма. `none` значит: подписи нет.
- **DMARC** — политика, что делать при провале SPF/DKIM. `fail` значит: письмо провалило проверку.

`spf=fail dkim=none dmarc=fail` — домен подделан.

## Шаг 4: выясняем, что за IP

Смотрим, кому принадлежит IP отправителя:

```bash
whois 45.13.22.100 | grep -Ei 'country|netname|org'
```

```
country:  NL
netname:  HOSTING-EXAMPLE
org:      Example Hosting BV
```

Хостинг в Нидерландах, причём это **VPS**-провайдер. Автоматические рассылки и фишинг часто идут именно с хостингов, а не с корпоративных почтовых серверов.

## Шаг 5: определяем клиент отправителя

Заголовок `X-Mailer` показывает, чем письмо отправлено:

```bash
grep -iE 'X-Mailer|User-Agent' message.eml
```

```
X-Mailer: PHPMailer 6.5
```

`PHPMailer` — библиотека отправки из PHP-скрипта. Корпоративный банк не рассылает письма через PHPMailer — это признак массовой автоматической рассылки.

## Шаг 6: проверяем ссылки и вложения

Не переходя по ссылкам в своём браузере, извлекаем их из файла:

```bash
grep -oiE 'https?://[^ ">]+' message.eml | sort -u
```

```
https://sberbank-secure.evil.example/login
```

Домен `sberbank-secure.evil.example` — **тайпсквот**: имя, похожее на настоящее, но на чужом домене. Отдельно проверяем вложения:

```bash
grep -iE 'Content-Disposition|filename=' message.eml
```

Имя вложения — тоже улика: двойное расширение (`invoice.pdf.exe`) или юникод-гомоглифы выдают подделку.

## Шаг 7: сводим вердикт

| Признак | Легитимно | Подозрительно |
|---|---|---|
| SPF | pass | fail, softfail, none |
| DKIM | pass | none, fail |
| DMARC | pass | fail |
| Return-Path | совпадает с From | чужой домен |
| X-Mailer | корпоративный клиент | PHPMailer, скрипт |
| Ссылки | официальный домен | тайпсквот |

Если SPF, DKIM и DMARC все провалились, а `Return-Path` не совпадает с `From` — это почти наверняка фишинг. Наше письмо набрало все «подозрительные» признаки.

## Шаг 8: не забываем про трекинг-пиксели

В HTML-части почти всегда спрятана невидимая картинка:

```html
<img src="https://track.example.com/open?id=USER123" width="1" height="1">
```

При открытии письма клиент запрашивает её, и отправитель узнаёт, что письмо прочитано, когда и с какого IP. Поэтому отключайте автоматическую загрузку удалённого контента и смотрите подозрительные письма в изолированной среде.

## Шаг 9: извлекаем все адреса и IP из письма

В заголовках оседают не только отправитель, но и все промежуточные адреса и узлы:

```bash
grep -oiE '[a-z0-9._%+-]+@[a-z0-9.-]+\.[a-z]{2,}' message.eml | sort -u
grep -oiE '\[?[0-9]{1,3}(\.[0-9]{1,3}){3}\]?' message.eml | sort -u
```

Первый запрос вытащит `From`, `Return-Path`, `Reply-To` и адреса из тела, второй — IP всех хопов. Каждый IP прогоняем через `whois`: расхождение «письмо от банка, а IP — хостинг в другой стране» усиливает вердикт.

## Шаг 10: проверяем письмо целиком в песочнице

Заголовки дают факты, но безопаснее разобрать письмо в изоляции. Сохрани `.eml`, открой его в отдельной ВМ без доступа к сети, а ссылки прогони через `urlscan.io` и `VirusTotal` — они откроют страницу за тебя. Так ты получишь и вердикт по домену, и скриншот фишинговой страницы, не рискуя своим хостом.

## Что мы теперь знаем

- `From` подделывается легко; доверять нужно `Return-Path`, `Received` и `Authentication-Results`.
- Цепочку `Received` читают снизу вверх — нижняя строка и есть исходный сервер.
- SPF, DKIM и DMARC — три проверки подлинности домена; их результат уже готов в заголовках.
- IP отправителя и `X-Mailer` выдают тип рассылки.
- Ссылки проверяют в песочнице, а вложения — по хэшу, не открывая.
- Трекинг-пиксели сообщают отправителю о прочтении.

## На что смотреть дальше

Разберись с **SPF, DKIM и DMARC домена** как отдельной проверкой: их записи лежат в DNS (`dig _dmarc.example.com TXT`), и по ним оценивают защищённость почтового домена. Изучи декодирование MIME-частей (`base64`, `quoted-printable`) и проверку вложений по хэшу на VirusTotal. Дальше — SMTP-энумерация и обогащение найденных IP.

## Куда дальше

Мы научились разбирать письмо и выносить вердикт. В следующем уроке — **анализ DMARC**: разберём политики домена детальнее и научимся оценивать, насколько легко подделать отправителя. А пока главное запомни: `From` не значит ничего, смотри `Received`, `Authentication-Results` и IP.

## Где пригодится

- **CTF (OSINT):** в письме-приложении спрятана подсказка или флаг в заголовках.
- **Blue team и антифишинг:** подтвердить подделку домена и выявить рассылку.
- **Bug bounty:** анализ писем, которые цель шлёт (спуфинг, open relay).
- **Пентест:** оценка защищённости почтового домена (SPF, DKIM, DMARC).
- **Расследования:** установить реальный источник письма.
