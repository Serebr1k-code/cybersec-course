## Вопрос, с которого всё начинается

У тебя есть IP-адрес сервера цели. Ты хочешь понять: кому он принадлежит, в чьём облаке живёт, где находится и какие ещё адреса рядом. Без этого дальнейшая разведка слепа — ты не знаешь ни владельца, ни границ инфраструктуры.

Ответ даёт **WHOIS** — публичный реестр регистрантов. Разберём, как из одного адреса развернуть целую карту инфраструктуры.

## Наш пример: адрес 93.158.134.144

Введём термины. **WHOIS** — публичный реестр: кто владеет доменом или диапазоном IP, когда зарегистрировано, какие контакты и DNS. **ASN** (Autonomous System Number) — номер автономной системы, то есть сети, которой управляет один оператор (провайдер, облако, компания). Все IP внутри ASN маршрутизируются вместе. Пройдём путь от адреса к владельцу.

## Шаг 1: WHOIS для IP

```bash
whois 93.158.134.144
```

Смотрим ключевые поля:

- **netname** — имя сети, часто содержит аббревиатуру компании.
- **OrgName / OrgId** — организация-владелец.
- **CIDR / inetnum** — диапазон адресов.
- **country**, **descr**, **abuse-c** — страна и контакт для жалоб.

Если в `netname` стоит `YANDEX`, а в `descr` — `Yandex LLC`, мы знаем: адрес в инфраструктуре Яндекса.

## Шаг 2: выбираем правильный региональный реестр

IP-адреса распределены между пятью региональными интернет-реестрами (**RIR**):

| RIR | Регион |
|---|---|
| ARIN | Северная Америка |
| RIPE NCC | Европа, Ближний Восток, Центральная Азия |
| APNIC | Азиатско-Тихоокеанский |
| LACNIC | Латинская Америка |
| AFRINIC | Африка |

Для России и СНГ актуален **RIPE**. Его сервер — `whois.ripe.net`:

```bash
whois -h whois.ripe.net 93.158.134.144
```

## Шаг 3: определяем ASN

Узнать ASN по IP можно через WHOIS или внешний сервис:

```bash
whois 93.158.134.144 | grep -i origin
curl -s "https://ipinfo.io/93.158.134.144/json"
```

Вывод `ipinfo.io`:

```json
{"org":"AS200350 Yandex.Cloud LLC","city":"Moscow","country":"RU"}
```

Это сразу говорит: адрес в облаке Яндекс. ASN `200350`, провайдер — `Yandex.Cloud`.

## Шаг 4: получаем все префиксы оператора

**BGP** — протокол маршрутизации между ASN. Зная ASN, можно получить все префиксы оператора:

```bash
curl -s "https://api.bgpview.io/asn/200350/prefixes" | jq -r '.data.ipv4_prefixes[].prefix'
```

Вывод (фрагмент):

```
93.158.128.0/18
93.158.134.0/24
...
```

Это бесценно для расширения разведки — но осторожно: если программа покрывает `*.example.ru`, а домен хостится в большом облаке, ты понимаешь границы, но **не** автоматически расширяешь scope. Правила программы важнее технической связности.

## Шаг 5: читаем CIDR-нотацию

WHOIS и BGP оперируют **CIDR-нотацией**: `93.158.134.0/24` — это 256 адресов, `/16` — 65536, `/32` — один адрес. Понимание нотации нужно, чтобы разворачивать диапазоны в списки IP:

```bash
python3 -c "import ipaddress;[print(ip) for ip in ipaddress.ip_network('93.158.134.0/24').hosts()]" | head
```

Из ASN ты получаешь **набор** префиксов; объединяй их для полного диапазона. И помни: большой ASN (облако) содержит адреса множества клиентов — сканировать их все нельзя.

## Шаг 6: атрибуция домена

Для домена тот же WHOIS работает иначе:

```bash
whois example.com
```

Что искать:

- **Registrar** — через кого зарегистрирован домен.
- **Creation / Updated / Expiry Date** — возраст (свежие домены = подозрительные).
- **Registrant Org / Country** — владелец (часто скрыт privacy-сервисом).
- **Name Server** — DNS-провайдер.
- **Status** — `clientHold`, `pendingDelete` (домен умирает), `ok`.

Если владелец скрыт (`REDACTED FOR PRIVACY`), смотри **NS-серверы** и **MX** — они часто выдают реальную компанию или хостера.

## Шаг 7: современная замена — RDAP

**RDAP** — это HTTP/JSON-версия WHOIS, удобная для скриптов:

```bash
curl -s https://rdap.org/ip/93.158.134.144 | jq '{handle,name,startAddress,endAddress}'
curl -s https://rdap.org/domain/example.com | jq '{ldhName,status,events}'
```

Преимущества: структурированный JSON, стабильный парсинг. Для домена смотри `events` (даты) и `entities` (роли), для IP — `handle`, `name` и границы диапазона.

## Шаг 8: подтверждаем права на префикс (RPKI)

Анонс в BGP не гарантирует право на префикс. Есть **RPKI/ROA** — криптографически подписанное разрешение:

```bash
curl -s "https://stat.ripe.net/data/rpki-validation/data.json?resource=AS200350&prefix=93.158.134.0/24" | jq '.data.status'
```

Статус `valid` — подтверждён, `invalid` — анонс противоречит ROA (возможный hijack), `not-found` — ROA нет.

## Шаг 9: собираем карту

Сведём всё вместе:

```
домен → A-запись → IP → WHOIS netname → ASN → провайдер → страна
```

Пример корреляции:

- `api.example.ru` → `93.158.134.144` → `Yandex` → `AS200350 Yandex.Cloud` → Россия.
- `cdn.example.ru` → CNAME на `cloudfront.net` → AWS → США.

Вывод: часть сервисов в собственном облаке, часть — за CDN. Это определяет, где искать origin и где применимы техники атаки.

## Шаг 10: обратный WHOIS и связи доменов

WHOIS даёт связи не только по IP, но и между доменами:

- **Reverse WHOIS** — все домены с тем же email, организацией или регистрантом: «портфель» владельца.
- **Общий NS** — домены с одним набором NS часто принадлежат одной организации.
- **Общий registrar** — слабый сигнал, но полезен в комбинации.

Так один домен вытягивает за собой десятки связанных — это расширяет карту за пределы исходной цели.

## Что мы теперь знаем

- WHOIS раскрывает владельца домена и диапазона IP.
- ASN — сеть одного оператора; ipinfo/bgpview дают ASN и префиксы.
- Для России и СНГ актуален реестр RIPE.
- RDAP — структурированная JSON-замена WHOIS.
- RPKI подтверждает право оператора на префикс.

## Частые ошибки

- **Путать registrar и registrant.** Регистратор — посредник, не владелец.
- **Считать REDACTED тупиком.** Смотри NS/MX и историю.
- **Принимать гео-IP за точное.** Anycast и VPN искажают.
- **Считать ASN владельцем адреса.** Часто это провайдер или облако.
- **Расширять scope по технической связности.** Правила программы важнее.

## На что смотреть дальше

Из ASN вырастает целая ветка: префиксы → reverse DNS → пассивный DNS → CT-логи, и один IP разворачивается в инфраструктуру с владельцем и хостами. Дальше разберём **RDAP** детально — как современный интерфейс к тем же данным. А пока главное запомни: WHOIS и ASN превращают одиночный адрес в часть карты инфраструктуры.

## Разбор кейса: один IP, три разных владельца

Классическая ловушка: ты делаешь WHOIS по IP и получаешь «провайдера», хотя думаешь, что это компания цели. Почему так? Адрес может быть арендован у хостинг-провайдера, делегирован региональному реестру и «прописан» на конечного клиента только в поле `descr`. В WHOIS эти роли смешаны, и новичок читает первую строку как истину.

Разберём три уровня. **RIR** — региональный реестр (RIPE, ARIN, APNIC), который владеет диапазоном на верхнем уровне. **LIR/оператор** — провайдер, которому RIR делегировал блок; именно он анонсирует префикс в BGP. **Конечный пользователь** — тот, кто арендует адрес; его имя часто указано в `netname` или `descr`, но не всегда. Практический вывод: WHOIS по IP отвечает на вопрос «чей это адрес у провайдера», а не «кто цель». Чтобы понять владельца, смотри на домен, который на этом IP хостится, и на сертификат.

Ещё одна тонкость — **исторические данные**. Адрес мог сменить владельца: год назад он был у цели, сейчас у провайдера. Поэтому важно смотреть дату и, где возможно, историю. RDAP (современная замена WHOIS) отдаёт те же данные в JSON, что удобнее для автоматизации и позволяет сравнивать снимки.

## Если не сработало

**WHOIS молчит или отдаёт «no match».** Попробуй другой сервер: `whois -h whois.ripe.net <ip>` для Европы, `whois.arin.net` для Америки. Реестр определяется по диапазону, и неверный сервер даст пустоту.

**Данные скрыты privacy-сервисом.** Для доменов это часто заглушка регистратора. Тогда ищи контакт через RDAP, историю WHOIS или косвенно — по сертификату и MX-записям.

**Один и тот же адрес у разных целей.** Значит, это shared-хостинг. Не приписывай его одной цели; проверяй по домену.

**AS не совпадает с ожидаемой.** Возможно, цель использует CDN. Тогда реальный origin спрятан, и WHOIS покажет адрес CDN, а не сервера цели.

## Частые вопросы

**Чем RDAP лучше WHOIS?** RDAP — это HTTP/JSON-протокол: ответы структурированы, поддерживают историю и разграничение доступа. Для скриптов он удобнее, WHOIS — «сырой» текст.

**Что такое netname?** Короткое имя блока адресов в реестре, часто отражающее владельца. Полезная подсказка, но не гарантия.

**Как читать CIDR?** `93.158.134.0/24` — блок из 256 адресов; `/24` означает, что первые 24 бита фиксированы. Чем больше число после слэша, тем меньше блок.

## Мини-практика: строим карту блока

Возьми один IP и поднимись на уровень выше — к блоку. Команда `whois 93.158.134.144 | grep -iE 'netname|descr|route|origin'` покажет имя блока и анонсирующий AS. Затем получи весь блок: `whois -h whois.ripe.net 93.158.134.0/24`. Теперь у тебя есть диапазон из 256 адресов — потенциальная поверхность. Прогони по нему реверс-DNS и посмотри, какие имена там живут: часто один блок содержит и веб-серверы, и почту, и служебные адреса. Сравни `netname` блока с названием компании цели: совпадение — сильная подсказка о владении. Этот опыт показывает, что один IP почти никогда не бывает «одиноким»: он часть блока, и блок часто рассказывает о цели больше, чем сам адрес.

## Куда дальше

Мы прошли путь от IP до владельца, провайдера и границ сети. В следующем уроке — **RDAP**: современный JSON-интерфейс к тем же регистрационным данным, удобный для автоматизации. А пока главное запомни: WHOIS и ASN — базовый навык атрибуции, на котором держатся почти все ветки OSINT.

## Где пригодится

- **CTF:** задачи «кому принадлежит IP или домен».
- **Bug bounty:** определение облака и хостера, поиск origin за CDN.
- **Пентест:** расширение карты инфраструктуры, понимание границ.
- **Threat intel:** атрибуция IP-адресов атакующим группам.
