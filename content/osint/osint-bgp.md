BGP (Border Gateway Protocol) — протокол маршрутизации между автономными системами (AS), из которых состоит интернет. Для разведки он даёт главное: **какие IP-префиксы принадлежат какой организации** и как они связаны. Это позволяет атрибутировать адреса, находить хостинг-соседей и замечать маршрутные аномалии.

## Автономная система и префикс

- **AS (Autonomous System)** — сеть под единым управлением, идентифицируется номером `ASxxxxx`.
- **Префикс** — блок IP-адресов, анонсируемый в BGP (`93.158.134.0/24`).
- **Origin AS** — AS, изначально анонсирующая префикс; владелец адресов.
- **AS-path** — цепочка AS, через которые маршрут прошёл.
- **ASN** — номер AS; бывает 16-битный (0–65535) и 32-битный (`AS200350`).

```bash
# узнать ASN и префикс для IP
whois -h whois.cymru.com " -v 93.158.134.144"
# или
curl -s "https://api.bgpview.io/ip/93.158.134.144" | python3 -m json.tool
```

Вывод Team Cymru содержит `AS | IP | BGP Prefix | CC | Registry | Allocated | AS Name` — это однострочная атрибуция, удобно для скриптов: `... | cut -d'|' -f1,7`.

## Инструменты

- **bgp.he.net** (Hurricane Electric) — ASN, префиксы, пиры, апстримы, точки присутствия.
- **RIPEstat** (`stat.ripe.net`) — история анонсов, `bgp-state`, `prefix-overview`, `routing-history`.
- **BGPView / bgp.tools** — API, whois-подобный доступ.
- **BGPStream / RouteViews / RIPE RIS** — коллекторы обновлений BGP в реальном времени.
- **PeeringDB** — кто с кем пирится, где стоит железо (IX, PoP).

```bash
# префиксы, анонсируемые AS
curl -s "https://api.bgpview.io/asn/13238/prefixes" \
  | python3 -c 'import sys,json;[print(p["prefix"]) for p in json.load(sys.stdin)["data"]["ipv4_prefixes"]]'

# все AS, анонсирующие конкретный префикс (детект hijack)
curl -s "https://api.bgpview.io/prefix/93.158.134.0/24" | python3 -m json.tool
```

## Чтение AS-path

Пример: `93.158.134.0/24 -> AS13238 -> AS3356 -> AS174`. Значит, до сети прошёл путь через указанные AS. Апстримы (крупные транзитные AS — Level3, Cogent, Telia) видны как «шум» в конце. Важны:

- **Origin** — владелец (последний AS перед префиксом, если смотреть с точки наблюдения).
- **Пиры и апстримы AS** — кто связан с организацией (партнёры, подрядчики).
- **Разнообразие путей** — наличие нескольких апстримов у AS (устойчивость и «вес» организации).

AS-path можно получить через `bgp.tools`, `bgp.he.net` или `stat.ripe.net/data/bgp-state`.

## Аномалии: hijack и leak

- **BGP hijack** — кто-то анонсирует чужой префикс (или более специфичный `/25`), перехватывая трафик.
- **Route leak** — маршрут утекает через AS, которому не должен был (например, транзит по ошибке).
- **Префикс с двумя origin AS** — признак конфликта/хайджека.
- **MOAS (Multiple Origin AS)** — нормально для anycast (Cloudflare, Google DNS), но подозрительно для обычного клиента.

```bash
# проверить, сколько AS анонсируют префикс (норма — один origin)
curl -s "https://stat.ripe.net/data/prefix-overview/data.json?resource=93.158.134.0/24" | python3 -m json.tool
```

Сервисы мониторинга: `bgpstream.com` (событийный), `isbgpsafe.com`, RIPE Labs, Cloudflare Radar.

## RPKI, ROA и IRR

Префиксы не всегда «принадлежат» анонсирующей AS — существуют системы подтверждения:

- **IRR (Internet Routing Registry)** — база объектов `route:`/`route6:`, где владелец разрешает AS анонсировать префикс.
- **RPKI/ROA** — криптографически подписанное разрешение (Route Origin Authorization) для AS + префикс.
- **RPKI validation** — «valid/invalid/not-found»; `invalid` = возможный hijack.

```bash
# проверка RPKI-статуса префикса
curl -s "https://stat.ripe.net/data/rpki-validation/data.json?resource=AS13238&prefix=93.158.134.0/24" \
  | jq '.data.status'
```

Если статус `invalid` — анонс противоречит ROA, это красный флаг.

## Связь с разведкой

1. IP → ASN → **владелец диапазона** (кто такой, страна, роль).
2. ASN → **все префиксы** → reverse-DNS и сканирование диапазона.
3. ASN → **пиры/апстримы** → карта связанных организаций.
4. Аномалии → инциденты безопасности (угон трафика).

Это замыкает цепочку: домен → IP → ASN → диапазон → другие хосты и организации.

## Соседи по префиксу и reverse IP

Собрав префиксы AS, переходите к «наполнению»:

```bash
# префиксы оператора
curl -s "https://api.bgpview.io/asn/200350/prefixes" | jq -r '.data.ipv4_prefixes[].prefix' > prefixes.txt

# обратный DNS по диапазону (см. osint-reverse-dns)
seq 1 254 | sed 's/^/93.158.134./' | dnsx -silent -ptr -resp-only
```

Так из одного IP вырастает карта всего хостинг-диапазона: почтовые серверы, VPN, панели, «забытые» сервисы.

## Пиры и апстримы: граф связей организаций

AS связываются через **пиринг** и **транзит**. Граф этих связей раскрывает партнёрства и подрядчиков:

- **Upstreams** — крупные транзитные провайдеры (Level3, Cogent, Telia).
- **Peers** — равноправные обмены (часто партнёры/филиалы).
- **Downstreams** — клиенты, арендующие транзит.

```bash
curl -s "https://api.bgpview.io/asn/200350/peers" | jq '.data.ipv4_peers[] | {asn, name}'
# PeeringDB: точки присутствия и контакты
curl -s "https://www.peeringdb.com/api/net?asn=200350" | jq '.data[].name'
```

Если у двух «независимых» организаций общий редкий апстрим/пир — стоит проверить связь.

## Историческая перспектива анонсов

Префикс может сменить владельца/оператора. История анонсов помогает понять «кто чем был»:

```bash
# RIPEstat: история анонсов префикса
curl -s "https://stat.ripe.net/data/routing-history/data.json?resource=93.158.134.0/24&min_peers=5" | jq '.data.by_origin'
```

Если префикс раньше анонсировался другой AS — это сигнал смены хостинга, продажи адресов или перехвата. Для атрибуции важно знать **текущего** origin и историю.

## Разобранный пример: от IP к сети организации

```bash
# 1) IP -> ASN
whois -h whois.cymru.com " -v 93.158.134.144" | awk -F'|' '{print $1, $7}'
# 2) ASN -> префиксы
curl -s "https://api.bgpview.io/asn/13238/prefixes" | jq -r '.data.ipv4_prefixes[].prefix' > p.txt
# 3) префиксы -> живые PTR
cat p.txt | while read p; do
  base=$(echo "$p" | cut -d/ -f1 | cut -d. -f1-3)
  for i in $(seq 1 254); do echo "$base.$i"; done
done | dnsx -silent -ptr -resp-only | sort -u > hosts.txt
wc -l hosts.txt
```

Результат — список именованных хостов всей AS. Из него легко вычленить `mail.*`, `vpn.*`, `git.*` — кандидаты на дальнейший анализ.

| BGPView API | `api.bgpview.io/asn/N/prefixes` | префиксы AS |
| RIPEstat | `stat.ripe.net/data/...` | история, RPKI, bgp-state |
| bgp.he.net | веб | пиры, апстримы |
| PeeringDB | `peeringdb.com/api` | IX, PoP, контакты |
| BGPStream | библиотека | события в реальном времени |

## Частые ошибки

- **Путать ASN владельца и хостинг-провайдера**: origin AS часто провайдер, а не сам клиент.
- **Считать один whois источником истины**: сверяйте bgp.he.net, RIPEstat, BGPView.
- **Игнорировать более специфичные префиксы** (`/25`): именно они участвуют в hijack.
- **Забыть про IPv6**: у AS отдельные IPv6-префиксы и часто отдельная картина анонсов.
- **Не проверять историю анонсов**: префикс мог сменить владельца.
- **Принимать MOAS за hijack**: anycast-сервисы легитимно анонсируют один префикс из многих мест.

## Что делать дальше / решение

- **Атрибуция IP** → Team Cymru whois + RIPEstat `prefix-overview`, зафиксировать ASN и владельца.
- **Расширение периметра** → все префиксы AS → reverse-DNS и сканирование (`osint-reverse-dns`).
- **Карта связей** → пиры/апстримы через BGPView/PeeringDB.
- **Мониторинг аномалий** → подписаться на BGPStream/Cloudflare Radar по своим префиксам.

## Разбор реального хайджека

Типовая картина при захвате префикса: в `prefix-overview` появляется **второй origin AS**, которого раньше не было, и он находится в другой стране. Шаги анализа:

1. Зафиксировать префикс и список origin AS (`RIPEstat prefix-overview`).
2. Проверить RPKI-статус: `invalid` — сильное подтверждение.
3. Сравнить AS-path из разных точек наблюдения (RouteViews, RIS) — угонщик может быть виден не везде.
4. Проверить `routing-history` — когда появился новый origin.
5. Сопоставить AS угонщика с известными «плохими» списками (spamhaus, BGP hijack-трекеры).

Хайджеки часто короткие (минуты-часы) и делаются для перехвата трафика к конкретным сервисам (DNS, криптобиржи), поэтому обнаруживаются по историческим данным, а не в реальном времени.

## Практические источники и лимиты

| Источник | Что даёт | Доступ |
|---|---|---|
| RIPEstat API | история, RPKI, bgp-state | без ключа, лимит по частоте |
| BGPView API | префиксы, пиры, IP | без ключа, мягкий лимит |
| bgp.he.net | визуализация ASN | веб |
| PeeringDB API | IX, PoP, контакты | без ключа |
| RouteViews / RIS | сырые MRT-дампы | скачивание |
| Cloudflare Radar | тренды, аномалии | веб/API |

При автоматизации ставьте паузы и кэшируйте ответы: коллекторы не любят частые запросы, а данные меняются медленно (раз в часы).

## IPv6-префиксы и двойной стек

У AS почти всегда есть отдельные IPv6-анонсы, и картина может отличаться от IPv4:

- **IPv6-префиксы** анонсируются независимо; иногда их анонсирует другая AS (managed-сервис).
- **Специфичность** в IPv6 важнее: `/48` или `/56` могут указывать на отдельные сайты/клиенты.
- **Обратные зоны** `ip6.arpa` делегируются по нибблам — PTR встречается реже.

```bash
curl -s "https://api.bgpview.io/asn/200350/prefixes" | jq -r '.data.ipv6_prefixes[].prefix'
```

При атрибуции не забывайте проверять оба семейства: организация может «жить» в IPv4 у одного провайдера, а в IPv6 — у другого.
