## Вопрос, с которого всё начинается

Ты уже знаешь ASN для IP — например, `AS200350`. Но что это даёт на практике? Оказывается, зная номер автономной системы, можно получить **все** адреса оператора, понять, кто его апстримы и партнёры, и даже заметить маршрутный угон. Как это делается?

Разберём BGP на одном IP от начала до конца.

## Наш пример: IP 93.158.134.144

Введём термины. **BGP** (Border Gateway Protocol) — протокол маршрутизации между автономными системами (AS), из которых состоит интернет. **Префикс** — блок IP-адресов, анонсируемый в BGP, например `93.158.134.0/24`. **Origin AS** — та AS, что изначально анонсирует префикс, то есть фактический владелец адресов.

## Шаг 1: от IP к ASN и префиксу

Быстрее всего — сервис Team Cymru:

```bash
whois -h whois.cymru.com " -v 93.158.134.144"
```

Вывод:

```
AS | IP | BGP Prefix | CC | Registry | Allocated | AS Name
200350 | 93.158.134.144 | 93.158.134.0/24 | RU | ripencc | 2019-06-05 | Yandex.Cloud LLC
```

Это однострочная атрибуция: ASN, префикс, страна, реестр, дата выделения и имя оператора. Удобно для скриптов: `... | cut -d'|' -f1,7`.

## Шаг 2: получаем все префиксы оператора

```bash
curl -s "https://api.bgpview.io/asn/200350/prefixes" \
  | jq -r '.data.ipv4_prefixes[].prefix'
```

Вывод (фрагмент):

```
93.158.128.0/18
93.158.134.0/24
...
```

Теперь ты знаешь весь диапазон адресов оператора — это расширяет разведку с одного IP на целую сеть.

## Шаг 3: читаем AS-path

**AS-path** — цепочка автономных систем, через которые прошёл маршрут. Пример: `93.158.134.0/24 → AS13238 → AS3356 → AS174`. До сети путь прошёл через указанные AS. Важны:

- **Origin** — владелец (AS, откуда анонс).
- **Пиры и апстримы AS** — кто связан с организацией.
- **Разнообразие путей** — несколько апстримов говорят об устойчивости и «весе» организации.

Крупные транзитные AS (Level3, Cogent, Telia) видны как «шум» в конце пути.

## Шаг 4: наполняем диапазон через reverse DNS

Собрав префиксы, переходим к «наполнению» — ищем имена хостов в диапазоне:

```bash
seq 1 254 | sed 's/^/93.158.134./' | dnsx -silent -ptr -resp-only
```

Вывод (фрагмент):

```
mail.yandex.example
vpn.yandex.example
```

Так из одного IP вырастает карта всего хостинг-диапазона: почтовые серверы, VPN, панели, «забытые» сервисы.

## Шаг 5: находим аномалии — hijack и leak

- **BGP hijack** — кто-то анонсирует чужой префикс (или более специфичный `/25`), перехватывая трафик.
- **Route leak** — маршрут утекает через AS, которой не должен был.
- **Префикс с двумя origin AS** — признак конфликта или хайджека.
- **MOAS** (Multiple Origin AS) — нормально для anycast (Cloudflare, Google DNS), но подозрительно для обычного клиента.

Проверяем, сколько AS анонсируют префикс:

```bash
curl -s "https://stat.ripe.net/data/prefix-overview/data.json?resource=93.158.134.0/24" \
  | jq '.data.asns'
```

Норма — один origin. Если появился второй, да ещё из другой страны, — это красный флаг.

## Шаг 6: подтверждаем права через RPKI

Анонс в BGP не гарантирует право на префикс. Система **RPKI/ROA** — криптографически подписанное разрешение «AS X имеет право анонсировать префикс Y»:

```bash
curl -s "https://stat.ripe.net/data/rpki-validation/data.json?resource=AS200350&prefix=93.158.134.0/24" \
  | jq '.data.status'
```

Статус `invalid` — анонс противоречит ROA, сильное подтверждение хайджека.

## Шаг 7: строим граф связей

AS связываются через **пиринг** и **транзит**. Граф этих связей раскрывает партнёрства:

- **Upstreams** — крупные транзитные провайдеры.
- **Peers** — равноправные обмены (часто партнёры).
- **Downstreams** — клиенты, арендующие транзит.

```bash
curl -s "https://api.bgpview.io/asn/200350/peers" | jq '.data.ipv4_peers[] | {asn, name}'
curl -s "https://www.peeringdb.com/api/net?asn=200350" | jq '.data[].name'
```

Если у двух «независимых» организаций общий редкий апстрим — стоит проверить связь.

## Шаг 8: смотрим историю анонсов

Префикс может сменить владельца. История анонсов помогает понять «кто чем был»:

```bash
curl -s "https://stat.ripe.net/data/routing-history/data.json?resource=93.158.134.0/24&min_peers=5" \
  | jq '.data.by_origin'
```

Если префикс раньше анонсировался другой AS — это сигнал смены хостинга, продажи адресов или перехвата. Хайджеки часто короткие (минуты-часы), поэтому обнаруживаются по историческим данным.

## Шаг 9: не забываем про IPv6

У AS почти всегда есть отдельные IPv6-анонсы, и картина может отличаться:

```bash
curl -s "https://api.bgpview.io/asn/200350/prefixes" | jq -r '.data.ipv6_prefixes[].prefix'
```

Организация может «жить» в IPv4 у одного провайдера, а в IPv6 — у другого. При атрибуции проверяй оба семейства.

## Шаг 10: держим инструменты и лимиты под рукой

| Источник | Что даёт | Доступ |
|---|---|---|
| RIPEstat API | история, RPKI, bgp-state | без ключа, лимит по частоте |
| BGPView API | префиксы, пиры, IP | без ключа, мягкий лимит |
| bgp.he.net | визуализация ASN | веб |
| PeeringDB API | IX, PoP, контакты | без ключа |

При автоматизации ставь паузы и кэшируй ответы: коллекторы не любят частые запросы, а данные меняются медленно — раз в часы.

## Что мы теперь знаем

- Origin AS — фактический владелец префикса.
- Team Cymru whois даёт IP → ASN/префикс одной строкой.
- Префиксы AS расширяют разведку на весь диапазон адресов.
- Второй origin AS и RPKI `invalid` — признаки хайджека.
- Пиры и апстримы строят граф связей организаций.

## Частые ошибки

- **Путать ASN владельца и хостинг-провайдера.** Origin AS часто провайдер, а не клиент.
- **Считать один whois источником истины.** Сверяй bgp.he.net, RIPEstat, BGPView.
- **Игнорировать более специфичные префиксы** (`/25`) — именно они участвуют в hijack.
- **Принимать MOAS за hijack.** Anycast-сервисы легитимно анонсируют один префикс из многих мест.
- **Не проверять историю анонсов.** Префикс мог сменить владельца.

## На что смотреть дальше

Из ASN вырастает вся карта периметра: префиксы → reverse DNS → хосты → сервисы. Для мониторинга своих префиксов подписываются на BGPStream и Cloudflare Radar. Дальше переходим к **CTF-рецептам** — практическому применению всей разведки в задачах. А пока главное запомни: BGP показывает, кому реально принадлежат адреса и как они связаны.

## Разбор кейса: как выглядит BGP hijack

**BGP** (Border Gateway Protocol) — протокол, которым сети обмениваются информацией о том, «через кого» доступен тот или иной диапазон IP. Каждый такой анонс — это утверждение: «адреса такого-то префикса доступны через меня». Протокол доверяет анонсам, поэтому ложный анонс может увести трафик.

**BGP hijack** — это когда кто-то анонсирует чужой префикс как свой. Классический пример — оператор анонсирует более специфичный префикс (например, `/24` вместо `/22`), и трафик части адресов идёт через него. Более специфичный маршрут всегда выигрывает — это называется **longest prefix match**. Признаки hijack при разборе: в AS-path неожиданно появляется AS, не связанная с владельцем; маршрут пропадает и появляется; в RPKI-проверке анонс помечен как **invalid**. RPKI — это криптографическая проверка права анонсировать префикс: владелец публикует подписанный ROA-объект, и любой может проверить, что анонс законен.

**Route leak** — родственная проблема: сеть передаёт маршрут не тому, кому следует, и трафик уходит по неоптимальному пути. Это чаще ошибка конфигурации, чем атака, но для атрибуции IP важно так же. Практическая ценность для разведки: зная AS и её префиксы, ты можешь найти «соседей» цели — другие адреса той же сети. Аномалии в AS-path помогают понять, был ли перехват трафика, что важно при расследовании инцидента.

## Если не сработало

**whois не показывает AS.** Для IP-адреса смотри не только whois, но и `bgp.he.net`, RIPEstat или `whois -h whois.radb.net`. Разные источники знают разное.

**Префикс слишком большой.** Для крупной сети один префикс — это миллионы адресов. Разбивай на более мелкие и работай по частям, иначе задохнёшься в объёме.

**Историю анонсов не видно.** Бесплатные сервисы дают историю ограниченно. Для глубокого анализа нужны архивы (RIPE RIS, RouteViews) — их можно скачать и разобрать локально.

**RPKI говорит «not found».** Отсутствие ROA не значит «незаконно» — многие сети просто не публикуют объекты. Это «неизвестно», а не «подделка».

## Частые вопросы

**Что такое AS?** Автономная система — совокупность сетей под единым управлением, у которой есть номер. Провайдер обычно соответствует одной AS.

**Зачем IPv6?** У IPv6 своя маршрутизация и свои префиксы; если цель анонсирует IPv6, а ты смотришь только IPv4, ты теряешь половину поверхности.

**Как это связано с атрибуцией?** По AS видно, чей это адрес и какие сети рядом. Но один и тот же адрес может быть перепродан — поэтому атрибуция по BGP всегда вероятностная, её подтверждают WHOIS и доменом.

## Мини-практика: читаем AS-path глазами

Возьми произвольный IP и посмотри на его маршрут через `bgp.he.net`. AS-path читается справа налево: крайний справа — источник анонса (кто владеет префиксом), крайний слева — твоя точка наблюдения. Если в середине появляется AS, не связанная с владельцем, это повод проверить аномалию. Сравни путь из двух разных точек наблюдения: у одной он может быть коротким, у другой — длинным. Так ты на практике видишь, что «маршрут» — это не один путь, а множество, зависящих от того, откуда смотришь.

## Куда дальше

Мы научились превращать один IP в целую сеть и находить маршрутные аномалии. В следующем уроке — **CTF-рецепты**: типовые задачи категории OSINT и чек-листы под каждый тип ввода. А пока главное запомни: BGP — это карта владения адресами, и она отвечает на вопрос «чей это диапазон».

## Где пригодится

- **CTF:** атрибуция IP и поиск хостов в диапазоне.
- **Bug bounty:** определение владельца инфраструктуры и связанных диапазонов.
- **Пентест:** расширение периметра через префиксы и пиры AS.
- **Blue team:** мониторинг маршрутных аномалий и хайджека своих префиксов.
