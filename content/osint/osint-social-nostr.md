## Вопрос, с которого всё начинается

Ты видишь подпись с ключом `npub1...`. Что это и как из него получить профиль человека? Nostr — децентрализованная сеть, где нет «одного сервера», зато есть публичные ключи и релеи, которые можно опросить без аккаунта.

Задача: превратить `npub` в hex-ключ и вытащить профиль (событие kind 0).

## Наш пример: публичный ключ из подписи

Держим файл `npub.txt`:

```bash
cat npub.txt
```

```text
npub1nordwindexamplekey9x8y7z6w5v4u3t2s1r0q
```

Первый вопрос: что за кодировка и как получить из неё рабочий идентификатор?

## Шаг 1: bech32 и ключи Nostr

`npub1...` — это **bech32**, формат с человекочитаемым префиксом и контрольной суммой. `npub` — публичный ключ (открытый), `nsec` — секретный. **Никогда не трогай `nsec`.** Внутри `npub` закодирован 32-байтовый hex-ключ.

```bash
python3 decode_npub.py
```

```text
hex: 5f2a1b0c9d8e7f60a1b2c3d4e5f60718293a4b5c6d7e8f90a1b2c3d4e5f60718
```

Теперь у нас есть hex-идентификатор, с которым работают релеи.

## Шаг 2: что такое релей и события

**Релей** — сервер, который принимает и отдаёт события Nostr. Событие — подписанная запись с полем `kind`: kind 0 — метаданные профиля (имя, «о себе», аватар), kind 1 — заметка, kind 3 — список контактов. Релеи публичны и часто позволяют читать без регистрации.

## Шаг 3: получаем профиль

```bash
python3 fetch_profile.py
```

```text
event kind=0
name: Nordwind
about: infra & osint
relays: wss://relay.damus.io, wss://nos.lol
nto{n0str_k1nd0_pr0f1l3}
```

Мы получили имя и описание из события kind 0. Список релеев — из того же профиля: он показывает, где человек публикуется.

## Шаг 4: kind 3 и граф связей

Событие kind 3 — это список контактов (кого человек читает). Он публичен и даёт граф. По нему можно связать аккаунты: если два профиля ссылаются друг на друга, это вероятная связь.

```bash
# иллюстративно
# запрос kind 3 к релею: {"kinds":[3],"authors":["<hex>"]}
```

## Полный прогон

```bash
cat npub.txt               # ключ
python3 decode_npub.py     # bech32 -> hex
python3 fetch_profile.py   # событие kind 0
```

Непрерывно: npub → hex → запрос к релею → профиль → релеи → граф связей.

## Если не сработало

**Ключ не декодируется.** Проверь контрольную сумму bech32 — возможно, опечатка.
**Профиля нет.** Пользователь мог не публиковать kind 0.
**Релей не отвечает.** Попробуй другой публичный релей — они взаимозаменяемы.

## Частые ошибки

**Ошибка: трогать `nsec`.** Это секретный ключ; работай только с `npub`.
**Ошибка: думать, что нужен аккаунт.** Публичные релеи читаются анонимно.
**Ошибка: считать профиль неизменным.** kind 0 — событие; его можно перезаписать.
**Ошибка: игнорировать kind 3.** Именно там граф связей.

## Справочная таблица: артефакты Nostr

| Артефакт | Значение |
|----------|----------|
| `npub1...` | публичный ключ (bech32) |
| `nsec1...` | секретный ключ — НЕ трогать |
| kind 0 | метаданные профиля |
| kind 1 | заметка |
| kind 3 | список контактов (граф) |
| релей | сервер, отдающий события |

## Что мы теперь знаем

1. `npub` — bech32-кодировка публичного ключа.
2. `nsec` — секрет, его нельзя трогать.
3. Релеи публичны и читаются без аккаунта.
4. kind 0 — профиль, kind 3 — граф связей.
5. Профиль — это событие, его можно перезаписать.

## Разбор кейса: от npub к графу

Проследим путь. На входе — `npub1nordwind...`. На выходе — профиль и связи.

**Шаг первый.** Декодируем bech32 и получаем hex-ключ.

**Шаг второй.** Запрашиваем событие kind 0 у публичного релея. Получаем имя, «о себе», релеи.

**Шаг третий.** Запрашиваем kind 3 — список контактов. Получаем граф: кого человек читает.

**Шаг четвёртый.** Ищем взаимные связи: если два профиля ссылаются друг на друга, это сильный сигнал.

**Итог.** Мы получили профиль и граф связей без аккаунта и без единого «взлома».

## Рабочий воркбук: Nostr за пять шагов

1. **Декодирование.** Преврати `npub` в hex.
2. **Профиль.** Запроси kind 0 у релея.
3. **Релеи.** Выпиши список релеев из профиля.
4. **Граф.** Запроси kind 3 и построй список контактов.
5. **Взаимность.** Найди взаимные ссылки как подтверждение связей.

## Частые вопросы

**Что делать, если профиля нет?** Человек мог не публиковать kind 0 — тогда работай по заметкам (kind 1).

**Можно ли подделать профиль?** Событие подписано ключом; подделать без `nsec` нельзя, но владелец может перезаписать свои данные.

**Релеи разные — данные разные?** Да, релей может не иметь всех событий. Опроси несколько.

**Почему bech32, а не просто hex?** Префикс и контрольная сумма уменьшают ошибки при копировании.

**Можно ли удалить событие?** Можно попросить релей удалить, но копии у других релеев могут остаться.

## Термины

**Nostr** — децентрализованный протокол публикации заметок.

**npub / nsec** — публичный / секретный ключ в bech32.

**Релей** — сервер, отдающий события.

**kind** — тип события: 0 — профиль, 1 — заметка, 3 — контакты.

**bech32** — формат кодирования с префиксом и контрольной суммой.

## Связь с другими уроками

Nostr — часть блока федеративных платформ. Его логика «ключ → событие → релей» похожа на **Bluesky** (DID → запись → PDS). Дальше — **Matrix**, где роль ключа играет homeserver. Освоив три протокола, ты уверенно работаешь с децентрализованным вебом.

## Практикум: собрать граф связей

Граф в Nostr строится из событий kind 3. Покажем полный цикл.

**Шаг первый.** Декодируем `npub` в hex.

**Шаг второй.** Запрашиваем kind 3 у двух-трёх релеев, чтобы не потерять события.

**Шаг третий.** Получаем список pubkey, на которые подписан человек.

**Шаг четвёртый.** Для каждого контакта запрашиваем kind 0 — имя и описание.

**Шаг пятый.** Ищем взаимность: у кого в kind 3 есть наш исходный ключ.

Результат — направленный граф «кто кого читает». Взаимные рёбра — самые сильные сигналы связи. Дополнительно можно смотреть репосты (kind 6/16) и реакции (kind 7) — они уточняют реальное взаимодействие, а не просто подписку.

## Сценарии CTF и расследований

**CTF, базовая задача.** Дан `npub`. Нужно получить hex. Решение: декодировать bech32.

**CTF, средняя задача.** Дан ключ. Нужно найти профиль. Решение: запросить kind 0.

**Расследование.** Нужно связать два аккаунта. Решение: найти взаимные kind 3 или перекрёстные упоминания.

**Мониторинг.** Нужно отслеживать заметки. Решение: подписаться на события kind 1 по автору.

Ключ к Nostr — «ключ, событие, релей»: три слова описывают весь протокол.

## Расширенный разбор: от подписки к реальному взаимодействию

Список контактов (kind 3) — это только начало. Разберём, как углубить граф.

Подписка в Nostr означает «я читаю этого автора». Но подписки бывают формальными и массовыми: некоторые аккаунты подписываются на сотни других механически. Поэтому голый kind 3 может вводить в заблуждение. Чтобы понять реальные связи, смотри взаимодействия.

Взаимодействия видны в других событиях. Репост (kind 6) означает, что человек распространил чужую заметку. Реакция (kind 7) — что он отреагировал. Ответ (kind 1 с тегом reply) — что он вступил в диалог. Эти события показывают, с кем человек реально общается, а не просто формально подписан.

Построение графа тогда становится многослойным. Первый слой — подписки (kind 3). Второй — репосты и реакции. Третий — прямые диалоги. Чем больше слоёв совпадает, тем сильнее связь. Если два аккаунта подписаны друг на друга, репостят друг друга и отвечают друг другу — это почти наверняка близкие контакты.

Дальше — временной анализ. Nostr-события имеют метку времени. Строя хронологию, можно увидеть активность: когда человек публикует, в каких часовых поясах, с какой периодичностью. Это даёт геолокационные и поведенческие подсказки — разумеется, вероятностные.

Отдельно про релеи. Один и тот же автор публикуется на нескольких релеях. Список релеев из профиля показывает, где искать. Но релей может не отдавать все события — поэтому опрашивай несколько и объединяй результаты. Отсутствие события на одном релее не значит, что его нет.

Наконец, про подлинность. Каждое событие подписано ключом. Это значит, что подделать авторство нельзя — можно лишь украсть ключ. Для разведки это плюс: граф связей в Nostr проверяем криптографически, в отличие от многих централизованных сетей.

## Итоговая шпаргалка

| Слой графа | Событие | Что показывает |
|------------|---------|----------------|
| Подписки | kind 3 | формальные связи |
| Репосты | kind 6 | распространение |
| Реакции | kind 7 | интерес |
| Диалоги | kind 1 (reply) | реальное общение |

Совпадение нескольких слоёв — сильный сигнал. Один слой — лишь гипотеза.

## Практическое замечание о работе с релеями

Релеи в Nostr не синхронизированы автоматически. Один релей может хранить заметку, другой — нет. Поэтому рабочий процесс строится так: составь список релеев из профиля, опроси их по очереди, объедини события и убери дубликаты по идентификатору. Если какой-то релей не отвечает, не считай это потерей данных — просто перейди к следующему. Полезно вести журнал: какой релей какие kind отдал. Со временем ты поймёшь, какие релеи наиболее полны для твоих целей, и будешь начинать с них.
