## Вопрос, с которого всё начинается

Ты нашёл поддомен `example.okta.com`. Что это даёт? Okta — один из крупнейших провайдеров единого входа (SSO). Если организация держит вход в свои приложения через Okta, то этот поддомен — её «парадная дверь»: через неё входят в десятки сервисов.

Задача: понять, что за организация стоит за этим адресом, и собрать её публичные метаданные — без единого логина.

## Наш пример: организация в Okta

Okta у каждой организации выдаёт свой поддомен вида `<company>.okta.com`. Иногда — `<company>-admin.okta.com` для админки, иногда региональные: `.okta-emea.com`, `.oktapreview.com`.

Держим объект `example.okta.com`. Первый вопрос: **отдаёт ли он публичные метаданные организации?** Да — через API-эндпоинт `/api/v1/org`.

```bash
curl -s https://example.okta.com/api/v1/org | jq .
```

```json
{"id":"00o1abcdefGHIJKLmn","subdomain":"example","companyName":"Example Corp",
 "status":"ACTIVE","created":"2019-04-02T10:11:12.000Z","country":"US"}
```

Читаем: `subdomain: example` подтверждает имя орг, `companyName` — юридический бренд, `status: ACTIVE` — орг жива, `created` — когда заведена. Это уже полноценный профиль: мы знаем, что компания Example Corp использует Okta с 2019 года.

## Шаг 1: находим организацию по домену

Организацию находят по DNS и сертификатам. Ищи поддомены с ключевыми словами `okta`, `sso`, `login`, `idp`:

```bash
curl -s 'https://crt.sh/?q=%25.okta.com&output=json' | jq -r '.[].name_value' | grep example
# в реальности: сертификаты <org>.okta.com видны в CT-логах
```

Часто в CNAME видно привязку: `sso.example.com → example.okta.com`. Это надёжное подтверждение, что вход компании идёт через Okta.

## Шаг 2: читаем OIDC-конфигурацию

Как и у Azure AD, Okta публикует документ OpenID Connect с эндпоинтами:

```bash
curl -s https://example.okta.com/oauth2/default/.well-known/openid-configuration | jq -r .issuer
```

```text
https://example.okta.com/oauth2/default
```

Здесь виден `authorization_endpoint`, `token_endpoint`, `jwks_uri`. `jwks_uri` — адрес публичных ключей подписи токенов; он подтверждает, что орг реально выдаёт токены. Наличие этой конфигурации — сильный признак живого SSO-провайдера.

## Шаг 3: изучаем страницу входа

Страница входа Okta живёт по адресу `/login/login.htm`. Она рассказывает, какие методы включены: пароль, MFA, вход через внешний IdP (Okta умеет федерацию с ADFS, Azure AD и др.).

```bash
curl -s https://example.okta.com/login/login.htm | grep -iE 'sign in|factor|mfa' | head
```

```text
<title>Sign In</title>
```

Если на странице виден брендинг организации — это ещё одно подтверждение. Если появляется редирект на сторонний IdP — значит, Okta сама делегирует вход дальше, и разведку надо продолжать там.

## Шаг 4: перечисление и его границы

У Okta есть эндпоинт аутентификации `/api/v1/authn`, который по имени пользователя отвечает, существует ли он и какие факторы ему доступны. Ответы различаются для существующего и несуществующего пользователя — это и есть основа перечисления.

```text
POST https://example.okta.com/api/v1/authn
{"username":"ceo@example.com","password":""}

→ 401 {"errorCode":"E0000004","errorSummary":"Authentication failed"}
```

Осторожно: Okta агрессивно троттлит и логирует такие запросы. Перечисление — это карта, а не вход: один-два запроса для подтверждения, дальше стоп. Массовый перебор — это уже не разведка, а атака, и она заметна.

## Полный прогон

```bash
# 1. орг-метаданные
curl -s https://example.okta.com/api/v1/org | jq -r '.subdomain, .companyName, .status'
# → example / Example Corp / ACTIVE
# 2. OIDC-конфигурация
curl -s https://example.okta.com/oauth2/default/.well-known/openid-configuration | jq -r .issuer
# → https://example.okta.com/oauth2/default
# 3. страница входа
curl -s -o /dev/null -w '%{http_code}\n' https://example.okta.com/login/login.htm
# → 200
```

Непрерывная история: поддомен → орг-метаданные → OIDC → страница входа → профиль SSO организации.

## Если не сработало

**`/api/v1/org` закрыт.** Некоторые орг отключают публичный доступ — тогда опирайся на OIDC и страницу входа.
**Нет поддомена okta.** Организация может использовать кастомный домен (`sso.example.com`) — проверь CNAME.
**Регион.** Орг может жить в `okta-emea.com` или `oktapreview.com` — проверь и их.

## Частые ошибки

**Ошибка: считать `subdomain` секретом.** Он публичен и нужен клиентам для входа.
**Ошибка: перебирать `/api/v1/authn`.** Быстрый троттлинг и алерты; подтверждай единичными запросами.
**Ошибка: игнорировать федерацию.** Если Okta делегирует вход внешнему IdP, реальный провайдер — там.

## Что мы теперь знаем

1. Организация Okta живёт на `<company>.okta.com`.
2. `/api/v1/org` отдаёт публичный профиль орг.
3. OIDC-конфигурация раскрывает эндпоинты и JWKS.
4. Страница входа показывает методы и федерацию.
5. Перечисление — карта, не вход; троттлинг реален.

## Справочная таблица: эндпоинты Okta

| Эндпоинт | Аутентификация | Что даёт |
|----------|----------------|----------|
| `/api/v1/org` | нет | id, subdomain, companyName, статус |
| `/oauth2/default/.well-known/openid-configuration` | нет | эндпоинты OIDC, jwks_uri |
| `/login/login.htm` | нет | страница входа, методы, брендинг |
| `/.well-known/apple-app-site-association` | нет | мобильные приложения орг |
| `/api/v1/authn` | POST | существование пользователя (троттлится) |

Шпаргалка: начинай с `/api/v1/org`, подтверждай через OIDC и страницу входа, а к `/api/v1/authn` обращайся в самую последнюю очередь и единично.

## Разбор кейса: от CNAME до федерации

Дано: домен `example.com`. Шаг первый — в CT-логах и DNS ищем поддомен Okta.

```bash
dig +short CNAME sso.example.com
# → example.okta.com.
```

CNAME прямо указывает на Okta — значит, вход компании идёт через неё. Шаг второй — читаем орг-метаданные:

```bash
curl -s https://example.okta.com/api/v1/org | jq -r '.subdomain, .companyName'
# → example / Example Corp
```

Шаг третий — OIDC-конфигурация показывает `issuer`. Шаг четвёртый — страница входа `/login/login.htm`: если она редиректит на сторонний IdP, значит Okta делегирует вход, и настоящий провайдер — там. Так разведчик проходит путь «домен → SSO → федерация» и понимает, где на самом деле проверяются пароли.

## Частые вопросы

**Okta — это что?** Провайдер единого входа: организация подключает к нему десятки приложений, а сотрудники входят один раз. Для разведчика — публичная «парадная дверь» ко всем приложениям компании.

**Почему `/api/v1/org` открыт?** Клиентам и приложениям нужно знать, к какой организации они обращаются, до входа. Поэтому сервис отдаёт базовый профиль без аутентификации.

**Что такое jwks_uri?** Адрес публичных ключей, которыми Okta подписывает токены. Он подтверждает, что орг реально выдаёт токены, а не просто держит страницу входа.

**Можно ли перечислить всех пользователей Okta?** Нет, массового открытого перечисления нет. `/api/v1/authn` позволяет проверить отдельные адреса, но быстро упирается в троттлинг и алерты.

**Чем Okta отличается от Azure AD?** Это конкурирующие провайдеры идентичности. Azure AD — родной для Microsoft-экосистемы; Okta — независимый и часто объединяет разнородные приложения.

## Термины

**Организация (org)** — изолированный тенант Okta с поддоменом и идентификатором.

**OIDC** — OpenID Connect, надстройка над OAuth 2.0, публикует эндпоинты и ключи.

**Issuer** — идентификатор, который выдаёт токены; у Okta — URL орг.

**JWKS** — набор публичных ключей для проверки подписи токенов.

**Федерация** — делегирование входа внешнему IdP; Okta умеет и принимать, и отдавать вход.

**Троттлинг** — ограничение частоты запросов; в Okta агрессивный и логируемый.

## Рабочий воркбук: полное расследование организации Okta

Разведка Okta почти всегда идёт одним и тем же маршрутом, и полезно один раз пройти его целиком, чтобы дальше делать на автомате.

**Этап 1. Найти организацию.** Ты начинаешь с корпоративного домена `example.com`. Ищешь поддомены с ключевыми словами `sso`, `login`, `okta`, `idp`. Иногда это видно сразу по CNAME: `sso.example.com → example.okta.com`. Если CNAME нет, смотри CT-логи: сертификаты `*.okta.com` с именем организации в SAN видны в публичных логах прозрачности. К этому моменту ты знаешь адрес организации.

**Этап 2. Снять профиль.** Обращаешься к `/api/v1/org`. Ответ содержит `id` (внутренний идентификатор орг), `subdomain`, `companyName`, `status`, `created`. Записывай всё: `id` неизменяем и пригодится для дедупликации, `created` подсказывает, когда компания перешла в облако, `companyName` может отличаться от юридического имени и дать зацепку к ребрендингу.

**Этап 3. Прочитать OIDC.** Документ `/.well-known/openid-configuration` для дефолтной авторизации даёт `issuer`, `authorization_endpoint`, `token_endpoint` и `jwks_uri`. Это подтверждает, что организация реально выдаёт токены. Если у компании несколько приложений, могут существовать дополнительные авторизационные серверы вида `/oauth2/<app>/` — их можно искать перебором имени, но осторожно.

**Этап 4. Изучить страницу входа.** `/login/login.htm` показывает методы: пароль, MFA, внешние IdP. Брендинг на странице подтверждает организацию. Если есть редирект на сторонний IdP, ты понимаешь, что Okta лишь «фасад», а реальная проверка пароля — в другом месте. Это меняет всю дальнейшую тактику.

**Этап 5. Аккуратно подтвердить пользователей.** В самом конце, если это действительно нужно для отчёта, можно единичными запросами к `/api/v1/authn` подтвердить существование одного-двух адресов. Массовый перебор запрещён: он троттлится и вызывает алерты. Помни: разведка строит карту, а не входит.

Пройдя эти пять этапов, ты получаешь полный публичный профиль SSO-провайдера организации: адрес, идентификатор, эндпоинты, методы входа, наличие федерации. Этого достаточно, чтобы планировать авторизованную фазу или закрыть задачу CTF.

## Почему Okta популярна у крупных компаний

Okta решает боль, знакомую любой растущей организации: приложений становится десятки, у каждого свой вход, и администраторы тонут в учётных записях. Okta становится единой точкой входа: сотрудник логинится один раз и получает доступ ко всему, а ИТ-служба централизованно отключает уволенных. Именно поэтому Okta так часто встречается у крупных компаний, и именно поэтому её поддомен — ценная находка для разведчика. Один найденный `*.okta.com` открывает список приложений, методов входа и внешних провайдеров, которым организация доверяет. Для CTF это часто ключ к следующему шагу, для пентеста — точка входа в карту идентичности всей компании.
