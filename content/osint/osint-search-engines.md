Обычный Google не индексирует всё. Многие данные лежат в **вертикальных** поисковиках и специализированных базах. Знание, куда идти за конкретным типом данных, экономит часы. В этом уроке — карта источников по типам данных.

## Код и репозитории

| Ресурс | Что ищет |
|---|---|
| GitHub / GitLab | репозитории, файлы, коммиты (`org:`, `filename:`, `path:`) |
| grep.app | полнотекстовый поиск по открытому коду |
| Sourcegraph | код по многим хостингам |
| searchcode | метапоиск по коду |
| PublicWWW | поиск по HTML/JS-сниппетам (какие сайты используют код) |

Пример: найти, какие сайты подключают чужой API-ключ.

```
# PublicWWW: ищем фрагмент кода/ключа на сайтах
"AIzaSy" site:example.com
```

## Научные и академические

- **Google Scholar** — статьи, цитирования, авторы.
- **arXiv / PubMed / Semantic Scholar** — препринты и медицина.
- **ResearchGate** — профили исследователей и их аффилиации.
- **Connected Papers** — граф связей статей.

Академические источники хороши для атрибуции: публикация связывает имя, организацию, соавторов и тему — это подтверждённый факт, а не слух.

## Компании и реестры

- **OpenCorporates** — компании по всему миру.
- **SEC EDGAR** — filings американских публичных компаний.
- **Crunchbase / PitchBook** — стартапы, инвестиции, основатели.
- **Госреестры** (ЕГРЮЛ/ЕГРИП, реестры других стран) — юрлица.

Эти источники дают **связи**: учредители, адреса, дочерние компании — отличные зацепки для корреляции.

## Домены, IP и инфраструктура

- **crt.sh** — Certificate Transparency (поддомены из сертификатов).
- **SecurityTrails / ViewDNS / DNSdumpster** — исторический DNS.
- **urlscan.io** — что видел сканер на странице (скриншоты, запросы).
- **Robtex** — связи IP/домена.
- **bgp.he.net / RIPEstat** — ASN и маршруты.

## Файлы и документы

- **Google/Bing filetype:** — прямые файлы.
- **FilePursuit / Filestack** — поиск файлов по типу.
- **Scribd / SlideShare** — документы и презентации.
- **DocumentCloud** — журналистские документы.

## Утечки и архивы

- **HaveIBeenPwned** — по email/домену (только проверка).
- **DeHashed / IntelX** — поиск по утечкам (легальность!).
- **Wayback Machine / archive.today** — исторические версии.
- **Google Cache** — свежие копии.

## Изображения и медиа

- **Google Images / Yandex Images / Bing Visual Search / TinEye** — обратный поиск.
- **PimEyes** — поиск лиц (этика!).
- **YouTube/Invid** — метаданные и проверка видео.

## Люди и контакты

- **Have I Been Pwned** — email/домен (см. osint-breach-data).
- **TruePeopleSearch / Whitepages** (US) — адрес, родственники.
- **Pipl / Spokeo** — агрегаторы профилей.
- **Whatsmyname / Maigret** — username (см. osint-username-enum).
- **DeHashed/IntelX** — утечки.

## Нишевые и региональные

- **Yandex** — лучше для Рунета; **Baidu** — Китай; **Naver** — Корея.
- **PublicWWW** — по HTML/JS-сниппетам.
- **FOFA/ZoomEye/Censys** — интернет-сканеры (см. osint-censys-fofa).
- **Intelligence X** — архивы, утечки, документы.
- **Dataset search (Google)** — научные датасеты.

## Метапоиск и приватность

- **Searx/SearxNG** — самохостинг, агрегация десятков движков, без трекинга.
- **Startpage** — Google-результаты приватно.
- **DuckDuckGo** — Bing-бэкенд, без пузыря.
- **Carrot2** — кластеризация результатов.

```bash
# SearxNG локально (docker) для приватного агрегированного поиска
docker run -d -p 8080:8080 searxng/searxng
```

## Как выбирать источник

1. Определите **тип данных**: код? документ? человек? компания? инфраструктура?
2. Выберите **вертикальный** поисковик под этот тип, а не общий.
3. Проверьте **несколько** источников — индексы различаются.
4. Зафиксируйте источник каждого результата.

Таблица «тип данных → куда идти»:

| Нужно найти | Источник |
|---|---|
| утёкший код/ключ | GitHub, grep.app, PublicWWW |
| юрлицо и связи | OpenCorporates, ЕГРЮЛ, SEC EDGAR |
| поддомены | crt.sh, SecurityTrails |
| скриншот страницы | urlscan.io, Wayback |
| человека | HIBP, whatsmyname, TruePeopleSearch |
| научную публикацию | Scholar, arXiv, Semantic Scholar |
| старую версию сайта | Wayback, archive.today |

## Разобранный пример

Нужно найти разработчиков, связанных с доменом `example.com`.

1. GitHub: `org:example` → список репозиториев и контрибьюторов.
2. grep.app: `"@example.com"` → утечки email в коде.
3. crt.sh: `%.example.com` → поддомены.
4. OpenCorporates: `example` → юрлицо, адрес, директора.
5. Google Scholar: `"Example Inc"` → публикации сотрудников.

Из пяти источников складывается картина: кто, где, что делает.

## Инструменты и флаги

| Инструмент | Как использовать |
|---|---|
| `grep.app` | веб, полнотекстовый по коду |
| `publicwww.com` | `"строка"` или `"строка" site:example.com` |
| `urlscan.io` | `domain:example.com` в поиске |
| `crt.sh` | `curl "https://crt.sh/?q=%25.example.com&output=json"` |
| SearxNG | `docker run -d -p 8080:8080 searxng/searxng` |
| theHarvester | `theHarvester -d example.com -b all` |

## Частые ошибки

- **Ограничиваться Google** — терять 30–50% данных.
- **Не проверять источник на свежесть** (индекс устаревает).
- **Игнорировать легальность** некоторых баз утечек.
- **Путать «проиндексировано» и «доступно».**
- **Не сверять несколько источников** — разное покрытие.
- **Забывать про язык/регион** — локальные поисковики индексируют лучше.

## Что делать дальше / решение

- **Определили тип данных** → идите в вертикальный источник из таблицы.
- **Мало результатов** → смените движок/регион (Yandex, Baidu).
- **Нужна приватность** → SearxNG/Startpage вместо Google напрямую.
- **Нужна корреляция** → соберите результаты в одну таблицу с указанием источника.

## Работа с API вертикальных поисковиков

Вертикальные источники дают API — это стабильнее веб-скрейпинга и не ломается при смене вёрстки:

- **GitHub API**: `https://api.github.com/search/code?q=...` (нужен токен), `org:<name>`.
- **urlscan.io API**: `https://urlscan.io/api/v1/search/?q=domain:example.com`.
- **HIBP API**: `https://haveibeenpwned.com/api/v3/breacheddomain/example.com` (ключ).
- **crt.sh**: JSON без ключа.
- **SEC EDGAR**: `https://data.sec.gov/submissions/CIK##########.json`.

```bash
curl -s "https://urlscan.io/api/v1/search/?q=domain:example.com&size=100" \
  | jq -r '.results[].page.url' | sort -u | head
```

API-подход позволяет строить повторяемые конвейеры и легко дедуплицировать результаты между запусками.

## Верификация и дедупликация результатов

Данные из разных источников пересекаются и противоречат. Практика:

1. **Нормализуйте** поля: домен, IP, email, имя — в единый формат.
2. **Дедуплицируйте** по ключу (например, `sort -u` по URL).
3. **Помечайте источник** и дату для каждого факта.
4. **Разрешайте конфликты** в пользу более свежего/авторитетного источника.
5. **Отделяйте факт от вывода** — в отчёте это разные столбцы.

```bash
cat source_*.txt | sort -u > merged.txt
wc -l merged.txt
```

Без этого шага «карта» превращается в свалку, а выводы становятся невоспроизводимыми.

## Чек-лист: как не утонуть в источниках

Источников сотни, но перегружать себя ими — ошибка. Рабочий чек-лист:

- [ ] Сформулировать **вопрос** (PIR), а не «собрать всё».
- [ ] Определить **тип данных** (код/компания/человек/инфраструктура/файл).
- [ ] Выбрать **2–3 вертикальных** источника под этот тип.
- [ ] Зафиксировать **источник и дату** каждого факта.
- [ ] **Сверить** минимум два источника перед выводом.
- [ ] **Дедуплицировать** и нормализовать.
- [ ] Отделить **факт** от **интерпретации**.
- [ ] Закрыть вопрос, а не продолжать сбор бесконечно.

Правило трёх попыток: если источник не дал данных за 3 запроса — переходите к следующему, не долбите один сервис. И держите результаты в одном файле: `merged.tsv` со столбцами `type, value, source, date, confidence`.

## Приватность при работе с вертикальными источниками

Каждый запрос оставляет след: у поисковика, у API-провайдера, а иногда и у самой цели (если источник активный). Гигиена:

- **Пассивное вперёд**: crt.sh, Wayback, реестры — не касаются цели.
- **API вместо веб**: официальный API не требует логина в чужой аккаунт и не «палит» профиль.
- **Отдельный профиль/прокси** для чувствительных запросов (например, reverse image на лицо).
- **Не логиньтесь** в соцсети под личным аккаунтом при сборе — используйте sock puppet или только публичные превью.
- **Фиксируйте OPSEC**: часовой пояс, язык, User-Agent могут связать ваши запросы.

Для bug bounty это ещё и вопрос scope: пассивный источник можно использовать всегда, активный — только по правилам программы. См. `osint-opsec` для деталей.

## Типичные CTF-задачи и источники

В CTF вертикальные источники решают задачи, где Google бессилен:

- **Найти утёкший секрет в коде** → GitHub `filename:`, grep.app, PublicWWW.
- **Определить компанию по домену** → OpenCorporates, SEC EDGAR.
- **Найти скриншот страницы** → urlscan.io, Wayback.
- **Связать username** → whatsmyname/Maigret.
- **Найти научную публикацию** → Scholar/arXiv.
- **Восстановить старую версию сайта** → Wayback/archive.today.

Порядок действий в задаче: прочитать подсказку → определить тип данных → выбрать 2–3 профильных источника → собрать → сверить → зафиксировать. Не тратьте время на общий поиск, если подсказка явно указывает на тип данных.

## Где пригодится

- **CTF (OSINT):** быстро найти нужный тип данных в подходящем источнике.
- **Bug bounty:** искать утечки кода и ключей через PublicWWW/grep.app.
- **Расследования:** реестры и архивы для установления связей.
- **Работа:** подбор источников под конкретный PIR.
