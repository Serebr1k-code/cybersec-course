## Задача

У тебя есть только домен — `example.com`. Обычный Google выдаст главную страницу и пару новостей. Но нам нужно больше: поддомены, утечки в коде, юридическое лицо, публикации сотрудников. Для каждого типа данных есть свой **вертикальный поисковик** — специализированный источник, который индексирует не весь веб, а конкретный класс информации.

Цель урока: научиться по одному домену собирать картину, выбирая источник под тип данных.

## Пробуем в лоб: почему Google не хватит

Google индексирует текст страниц. Но он не индексирует **сертификаты** (оттуда видны поддомены), **реестры юрлиц**, **публикации в академических базах**. Эти данные лежат в отдельных источниках, у каждого — свой интерфейс. Знание, куда идти за конкретным типом, экономит часы.

## Наш пример: строим картину по example.com

Мы идём по шагам, и на каждом выбираем источник под тип данных. Все результаты складываем в одну таблицу с указанием источника.

## Шаг 1: поддомены — Certificate Transparency

Когда сайту выдают TLS-сертификат, это фиксируется в публичных логах — **Certificate Transparency (CT)**. Сайт **crt.sh** ищет по этим логам и показывает все домены, для которых выпускали сертификат. Это пассивно: цели мы не касаемся.

```bash
$ curl -s "https://crt.sh/?q=%25.example.com&output=json" | jq -r '.[].name_value' | sort -u
api.example.com
mail.example.com
vpn.example.com
```

Мы получили три поддомена, которых не было на главной странице. Каждый — потенциальная точка входа для дальнейшего recon.

## Шаг 2: код — GitHub и поиск по коду

Разработчики часто оставляют в публичном коде email, ключи и внутренние адреса. **GitHub** ищет по репозиториям и файлам, а **grep.app** и **PublicWWW** — по фрагментам кода на многих сайтах.

```bash
$ curl -s "https://api.github.com/search/repositories?q=example&per_page=1" | jq '.total_count, .items[0].full_name'
1984037
"goexample/example"
```

Поиск по организации (`org:example`) даёт список репозиториев и контрибьюторов, а `filename:.env` — попытку найти забытый конфиг. Ключевое: искать нужно **по коду**, а не по страницам.

## Шаг 3: что видел сканер — urlscan.io

**urlscan.io** — публичная база сканирований: сервис заходит на сайты и сохраняет скриншоты, запросы и DOM. Это как «архив наблюдений» за страницей.

```bash
$ curl -s "https://urlscan.io/api/v1/search/?q=domain:example.com&size=2" | jq -r '.results[].page.url'
yahoo.com
```

Так можно увидеть, какие страницы домена уже кто-то сканировал и что там было — без единого запроса к цели.

## Шаг 4: юрлицо — реестры компаний

Чтобы понять, кто за доменом, идём в реестры: **OpenCorporates** (компании по всему миру), **SEC EDGAR** (отчёты публичных компаний США), **ЕГРЮЛ** (российские юрлица). Здесь находятся учредители, адреса, связанные фирмы — то, что не видно в вебе.

## Шаг 5: публикации — академические базы

**Google Scholar**, **arXiv**, **Semantic Scholar** связывают имя, организацию, соавторов и тему. Публикация — это подтверждённый факт, а не слух, поэтому академический источник отлично подходит для атрибуции: «сотрудник X работает в Y над темой Z».

## Таблица «тип данных → источник»

| Нужно найти | Источник |

| поддомены | crt.sh, SecurityTrails |
| утёкший код/ключ | GitHub, grep.app, PublicWWW |
| что видел сканер | urlscan.io, Wayback |
| юрлицо и связи | OpenCorporates, ЕГРЮЛ, SEC EDGAR |

## Что мы теперь знаем

По-простому:

1. Google — не всё: данные лежат в вертикальных источниках.
2. Под каждый тип данных — свой источник (код, реестры, CT-логи…).
3. Многие источники дают API — это стабильнее и повторяемо.
4. Результаты надо складывать в одну таблицу с указанием источника и даты.
5. Пассивные источники (crt.sh, Wayback, реестры) безопасны: цели не касаются.

## На что смотреть дальше

- **Не ограничивайся Google** — теряешь 30–50% данных.
- **Свежесть индекса.** Источник мог устареть: сверяй дату.
- **Легальность.** Часть баз утечек использовать нельзя — проверяй правила.
- **«Проиндексировано» ≠ «доступно».** Факт наличия страницы в базе ещё не значит, что она живая.
- **Несколько источников.** Покрытие у всех разное, пересечение — это подтверждение.
- **Язык и регион.** Локальные поисковики (Yandex, Baidu, Naver) индексируют свой сегмент лучше.

## Метапоиск и приватность

**SearxNG** — самохостинговый метапоисковик: агрегирует десятки движков и не трекает. **Startpage** отдаёт результаты Google приватно, **DuckDuckGo** — на бэкенде Bing. Поднять SearxNG можно так:

```bash
$ docker run -d -p 8080:8080 searxng/searxng
```

Приватность при работе с источниками: каждый запрос оставляет след. Гигиена — пассивное вперёд, API вместо логина в чужой аккаунт, отдельный профиль для чувствительных запросов.

## Чек-лист: как не утонуть в источниках

- [ ] Сформулировать **вопрос**, а не «собрать всё».
- [ ] Определить **тип данных** (код/компания/человек/инфраструктура).
- [ ] Выбрать **2–3 вертикальных** источника.
- [ ] Зафиксировать **источник и дату** каждого факта.
- [ ] Сверить минимум два источника.
- [ ] Отделить **факт** от **вывода**.

Правило трёх попыток: если источник не дал данных за 3 запроса — переходи к следующему.

## Работа с API вертикальных поисковиков

Вертикальные источники дают **API** — это стабильнее скрейпинга веб-страниц и не ломается при смене вёрстки:

- **GitHub API:** `https://api.github.com/search/code?q=...` (нужен токен), `org:<name>`.
- **urlscan.io API:** `https://urlscan.io/api/v1/search/?q=domain:example.com`.
- **HIBP API:** `https://haveibeenpwned.com/api/v3/breacheddomain/example.com` (ключ).
- **crt.sh:** JSON без ключа.
- **SEC EDGAR:** `https://data.sec.gov/submissions/CIK##########.json`.

```bash
$ curl -s "https://urlscan.io/api/v1/search/?q=domain:example.com&size=100" \
    | jq -r '.results[].page.url' | sort -u | head
```

API-подход позволяет строить повторяемые конвейеры и легко дедуплицировать результаты между запусками.

## Верификация и дедупликация

Данные из разных источников пересекаются и противоречат. Порядок работы:

1. **Нормализуйте** поля: домен, IP, email, имя — в единый формат.
2. **Дедуплицируйте** по ключу (например, `sort -u` по URL).
3. **Помечайте источник** и дату для каждого факта.
4. **Разрешайте конфликты** в пользу более свежего или авторитетного источника.
5. **Отделяйте факт от вывода** — в отчёте это разные столбцы.

```bash
$ cat source_*.txt | sort -u > merged.txt
$ wc -l merged.txt
```

Без этого шага «карта» превращается в свалку, а выводы становятся невоспроизводимыми.

## Куда дальше

В следующем уроке мы разберём региональные поисковики — Яндекс, Baidu, Naver — и увидим, почему для русскоязычных целей Google проигрывает. А пока запомни главное: под каждый тип данных есть свой источник, и их нужно сверять между собой.

## Где пригодится

- **CTF (OSINT):** быстро найти нужный тип данных в подходящем источнике.
- **Bug bounty:** искать утечки кода и ключей через PublicWWW/grep.app.
- **Расследования:** реестры и архивы для установления связей.
- **Работа:** подбор источников под конкретный исследовательский вопрос.
