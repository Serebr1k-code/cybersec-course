## Вопрос, с которого всё начинается

Домен `target.com` выглядит защищённым: у него строгий SPF и `p=reject` в DMARC. Новичок на этом останавливается и пишет в отчёте «спуфинг невозможен».

Но подделывать письма можно не только от корневого домена. Разберём полный аудит на одном домене и его поддомене.

## Наш пример: target.com и mail.target.com

У нас один объект разведки — почтовая инфраструктура `target.com`. Задача: найти любую точку, откуда можно отправить письмо «от имени» организации. Всё делается пассивно, через DNS.

## Шаг 1: читаем SPF корневого домена

```bash
dig +short TXT target.com | grep spf1
```

```
"v=spf1 include:_spf.google.com include:mailgun.org -all"
```

Разберём запись по механизмам и квалификаторам. Механизмы перечисляют, кто вправе слать почту: `include:` подтягивает чужой SPF-список (здесь Google и Mailgun). Квалификаторы задают результат для всех остальных:

| Квалификатор | Значение | Эффект |
|---|---|---|
| `+` | pass | разрешено (по умолчанию) |
| `-` | fail | запрещено жёстко |
| `~` | softfail | вероятно запрещено, часто «в спам» |
| `?` | neutral | без мнения |

У `target.com` стоит `-all` — жёсткий запрет. Это правильно.

## Шаг 2: проверяем лимит SPF в 10 запросов

Здесь есть скрытая ловушка: SPF допускает максимум **10 DNS-запросов** на проверку. Каждый `include:`, `a`, `mx` — это запрос. Превышение даёт **permerror**, и письмо вообще не проходит проверку.

```bash
for inc in $(dig +short TXT target.com | grep -oE 'include:[^ ]+'); do
  d=${inc#include:}; echo "$d -> $(dig +short TXT $d | head -1)"; done
```

Каждый `include:` может тянуть за собой ещё несколько — так цепочка незаметно превышает лимит. Частая мисконфигурация.

## Шаг 3: ищем DKIM-селекторы

DKIM подписывает письмо; публичный ключ лежит в DNS по адресу `селектор._domainkey.домен`. Селектор заранее неизвестен, поэтому перебираем типовые:

```bash
for s in default google mail s1 selector1 k1 dkim; do
  echo "== $s"
  dig +short TXT $s._domainkey.target.com
done
```

Нашли `s1` со `v=DKIM1; k=rsa; p=MIIBIjANBg...`. Смотрим на ключ: короткий (`p=` на 1024 бита и меньше) — слабость, пустой `p=` — домен вообще не подписывает.

## Шаг 4: читаем DMARC корневого домена

```bash
dig +short TXT _dmarc.target.com
```

```
"v=DMARC1; p=reject; rua=mailto:dmarc@target.com; pct=100; adkim=s; aspf=s"
```

`p=reject` означает «отклонять подделки» — это строгая защита. Поля `adkim=s` и `aspf=s` задают строгое выравнивание, а `rua` — адрес, куда уходят агрегированные отчёты. По этим отчётам видно, кто уже пытался спуфить домен.

## Шаг 5: проверяем поддомены — вот здесь дыра

Главная ошибка новичка — проверять только корень. У поддоменов своя политика:

```bash
for h in mail.target.com news.target.com; do
  echo "== $h =="
  dig +short TXT _dmarc.$h
  dig +short TXT $h | grep spf1
done
```

```
== mail.target.com ==
"v=spf1 ?all"
== news.target.com ==
"v=spf1 -all"
```

У `mail.target.com` нет DMARC и стоит `?all` (нейтральный квалификатор). Значит, от этого поддомена можно слать подделку — политика корня его не закрывает, потому что `sp` не задан.

## Шаг 6: подтверждаем спуфинг лабораторно

Утверждение проверяем тестовым письмом (в рамках авторизованного задания):

```bash
swaks --to victim@target.com --from ceo@mail.target.com --server mail.target.com \
  --header "Subject: test" --body "spoof test"
```

Письмо проходит SPF (`?all` ничего не блокирует) и не отбивается DMARC (записи нет). Фиксируем: поддомен подделываем.

## Шаг 7: сводим таблицу рисков

| Состояние | Риск |
|---|---|
| Нет SPF или DMARC | высокий |
| `+all` или `?all` в SPF | спуфинг |
| `p=none` в DMARC | письма проходят |
| `sp=none` при `p=reject` | поддомены уязвимы |
| `pct<100` | часть писем проходит |
| Нет DKIM | нет криптоподписи |

Для отчёта рекомендация: задать `sp=reject` и опубликовать DMARC для поддоменов, ужесточить SPF поддомена.

## Шаг 8: читаем готовый вердикт в заголовке письма

Аудит по DNS показывает потенциал; подтверждение приходит в заголовке реального письма. Почтовый сервер оставляет результат проверок в поле `Authentication-Results`:

```
Authentication-Results: mx.google.com;
  spf=softfail (google.com: domain of ceo@mail.target.com does not designate ...);
  dkim=none; dmarc=pass (p=REJECT sp=NONE) header.from=target.com
```

Читаем: SPF дал **softfail** (сработал мягкий квалификатор), DKIM нет вовсе, а DMARC вынес `pass` — но только потому, что подделка пришла от **корневого** `target.com`, у которого `p=reject`. Для `mail.target.com` выравнивание провалилось бы, и DMARC дал бы `fail`. Вот оно, место `sp=NONE`: политика корня поддомен не закрывает.

## Шаг 9: массовый аудит доменов

В bug bounty доменов много, поэтому проверку автоматизируют. `checkdmarc` умеет работать со списком:

```bash
checkdmarc --names target.com,mail.target.com,news.target.com -f csv
```

На выходе — таблица: домен, наличие SPF, строгость квалификатора, DMARC-политика, `sp`, найденные DKIM-селекторы. Сортируй по слабости: сначала домены без DMARC, затем с `p=none`, затем с `?all`. Так из сотни доменов за минуту находится десяток реально подделываемых.

## Что мы теперь знаем

- SPF перечисляет разрешённые отправители, а квалификатор задаёт строгость.
- Лимит SPF — 10 DNS-запросов; превышение ломает проверку.
- DKIM-ключ ищут перебором типовых селекторов; слабый ключ — уязвимость.
- DMARC `p=reject` защищает корень, но поддомены — отдельно.
- Массовая проверка поддоменов находит реальные точки спуфинга.
- Спуфинг подтверждают тестовым письмом через `swaks`.

## На что смотреть дальше

Разберись с **выравниванием** (`adkim`/`aspf`) и байпасами: lookalike-домены (`examp1e.com`), relay через доверенный сервис, разные `From` и `Return-Path`. Изучи инструменты массового аудита (`checkdmarc`, `dmarcian`, MXToolbox) и научись сводить результат по многим доменам в одну таблицу для bug bounty.

## Шаг 10: справочник по механизмам SPF и тегам DMARC

Чтобы читать чужие записи уверенно, держи под рукой две шпаргалки. Механизмы SPF отвечают на вопрос «кто вправе слать»:

| Механизм | Смысл |
|---|---|
| `ip4:` / `ip6:` | конкретный IP или подсеть |
| `a` | IP из A-записи домена |
| `mx` | хосты из MX-записей домена |
| `include:` | подтянуть SPF другого домена |
| `exists:` | проверка существования имени |
| `ptr` | обратная DNS-проверка (не рекомендуется) |
| `all` | «все остальные» — всегда последним |

Теги DMARC отвечают на вопрос «что делать с результатом»:

| Тег | Значение | Эффект |
|---|---|---|
| `p=` | none/quarantine/reject | политика для корня |
| `sp=` | то же | политика для поддоменов |
| `pct=` | 0–100 | доля писем под политикой |
| `adkim` / `aspf` | r/s | строгое (s) или мягкое (r) выравнивание |
| `rua=` | mailto | куда слать агрегированные отчёты |
| `ruf=` | mailto | куда слать forensics-отчёты |

Держи в голове: `p=reject` без `sp=` защищает **только** корень, а `pct=50` применяет политику лишь к половине писем — оба случая выглядят «защищёнными», но оставляют дыру.

## Если не сработало

- **`dig` не отвечает / таймаут.** Укажи резолвер явно: `dig @1.1.1.1 +short TXT _dmarc.target.com`. Локальный резолвер мог заблокировать или закешировать.
- **Записи нет вовсе (NXDOMAIN).** Это тоже результат: домен не публикует DMARC. Фиксируй «не защищён», а не «проверить не удалось».
- **Wildcard TXT.** Если `dig +short TXT random.target.com` возвращает что-то осмысленное, у домена wildcard-TXT — не спутай его с реальной DMARC-записью.
- **Селектор не угадан.** Вместо перебора списка селекторов попробуй найти реальный в заголовке `DKIM-Signature` любого письма от домена (`s=` в подписи) — это надёжнее.

## Реагирование: что делать с найденным спуфингом

Находка бесполезна без рекомендации. В отчёте по каждому уязвимому домену дай владельцу конкретный план:

1. **Поддомен без DMARC** → опубликовать `_dmarc.<поддомен>` с `p=reject` либо задать на корне `sp=reject`, чтобы политика распространялась вниз.
2. **`?all` / `+all` в SPF поддомена** → заменить на `-all`, а нужные сервисы перечислить через `include:`.
3. **`p=none`** → после сбора отчётов (`rua`) перейти к `p=quarantine`, затем `p=reject`.
4. **Слабый DKIM-ключ (1024 бита)** → ротировать на 2048 бит, сменить селектор.
5. **Нет MTA-STS** → добавить `_mta-sts` и политику, чтобы защитить транспорт (TLS).

Порядок важен: сначала включают `rua`, наблюдают неделю за легитимными потоками, потом ужесточают. Резкий `p=reject` без наблюдения ломает легитимную рассылку — это классическая ошибка внедрения.

## Частые ошибки

- **Проверять только корень.** Поддомен со своим SPF живёт отдельной жизнью — смотри и его.
- **Считать `p=reject` полной защитой.** Без `sp=` поддомены остаются открытыми.
- **Забыть про `pct`.** `pct<100` применяет политику не ко всем письмам.
- **Угадывать селектор вслепую.** Реальный селектор быстрее достать из `DKIM-Signature` письма.
- **Путать SPF-`include` с разрешением.** `include:` — это «подтяни чужой список», а не «разреши всё».
- **Не чинить вслепую.** Сначала собери `rua`-отчёты за неделю, иначе жёсткая политика отрежет легитимную почту.

## Куда дальше

Мы научились находить точки спуфинга по DNS. В следующем уроке — **SMTP-энумерация**: проверим, можно ли через почтовый сервер выяснить, какие пользователи существуют. А пока главное запомни: защищённый корневой домен ещё не значит защищённую организацию.

## Где пригодится

- **CTF:** задачи на спуфинг и чтение почтовых заголовков.
- **Bug bounty:** домены, допускающие подделку отправителя, — валидная находка.
- **Пентест:** оценка фишинг-поверхности и планирование рассылок.
- **Blue team:** аудит собственной почтовой защиты и её ужесточение.
