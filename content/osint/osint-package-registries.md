## Вопрос, с которого всё начинается

Ты хочешь понять внутреннюю архитектуру компании `company`. Новичок смотрит на её сайт и вакансии.

Но есть источник честнее вакансий — **реестры пакетов**: npm, PyPI, Maven, Docker Hub. Инженеры публикуют артефакты «для себя», не задумываясь, что метаданные и код видны всему интернету. Разберём это на одной организации.

## Наш пример: скоуп @company в npm

У нас один объект — **скоуп** `@company` в npm. Скоуп — это пространство имён, под которым организация публикует свои пакеты (`@company/имя`). Задача: собрать пакеты, найти утечки и реконструировать структуру.

## Шаг 1: смотрим метаданные пакета

У каждого пакета есть метаданные: автор, репозиторий, зависимости. Начнём с одного:

```bash
npm view @company/internal-tools
```

```
name: @company/internal-tools
version: 2.3.1
author: dev <dev@company.com>
repository: git+https://github.com/company/internal-tools.git
maintainers: dev <dev@company.com>
```

Мы уже получили email сотрудника, ссылку на репозиторий и структуру. Метаданные `maintainers` — это готовый список людей для дальнейшего OSINT.

## Шаг 2: скачиваем артефакт

Публичный пакет можно скачать, не устанавливая:

```bash
npm pack @company/internal-tools
tar -xzf company-internal-tools-*.tgz
```

**Тарбол** — это архив пакета. Внутри — код, а иногда конфиги и тестовые файлы, которые в репозиторий не попали.

## Шаг 3: ищем секреты в коде

Прогоняем распакованное по типовым отпечаткам секретов:

```bash
grep -rEi 'AKIA|sk-|password|api[_-]?key|BEGIN .*PRIVATE' package/
```

```
package/test/fixtures/config.js: const AWS_KEY = 'AKIA...'
```

Нашли ключ AWS в тестовом файле. Такое встречается часто: тестовые данные «случайно» берут настоящие ключи. Проверять их можно только минимально и read-only — как мы разбирали в уроке про секреты.

## Шаг 4: для Python — PyPI

Тот же приём для Python:

```bash
pip download company-internal-tools --no-deps -d ./pkg
cd pkg && unzip -o *.whl -d extracted
grep -rEi 'password|secret|api[_-]?key|token' extracted/
```

Формат `.whl` — это zip-архив. Внутри лежат `setup.py`, `METADATA` и код. Метаданные PyPI отдают автора, лицензию и зависимости:

```bash
curl -s https://pypi.org/pypi/company-tools/json | jq '.info | {author, license, requires_dist}'
```

## Шаг 5: Docker Hub и слои образа

Контейнеры — отдельная золотая жила. Образ состоит из **слоёв**, и удалённые файлы остаются в истории:

```bash
docker pull company/app:dev
docker save company/app:dev -o app.tar
mkdir -p layers && tar -xf app.tar -C layers
grep -rEi 'AKIA|sk-|password|BEGIN .*PRIVATE' layers/ | head
```

Частая находка: `.env` с ключами, оставшийся в раннем слое. В финальном образе файл «удалён», но в предыдущем слое он есть. Тег `dev` или `staging` особенно ценен: там меньше чистят.

## Шаг 6: реконструируем архитектуру из имён

Соберём все пакеты скоупа и прочитаем их как карту сервисов:

```bash
npm search @company
```

```
@company/auth-service
@company/payments-sdk
@company/internal-billing
```

По именам видно микросервисную архитектуру: аутентификация, платежи, биллинг. Сопоставив с вакансиями и доменами, получаем карту инженерных команд.

## Шаг 7: проверяем dependency confusion

**Dependency confusion** — атака на цепочку поставок: если внутреннее имя не занято в публичном реестре, злоумышленник может опубликовать под ним свой пакет, и сборка подтянет его. Для разведки мы просто проверяем, свободно ли имя:

```bash
npm view @company/utils
```

```
404 Not Found
```

Ответ `404` означает: имя свободно, риск существует. Аналогично для Python:

```bash
pip index versions company-utils
```

```
ERROR: No matching distribution found
```

Вывод для отчёта: имя не занято плюс публичный индекс приоритетнее — риск захвата. Рекомендация: зарегистрировать имя и настроить приоритет приватного индекса.

## Шаг 8: читаем граф зависимостей

Зависимости раскрывают стек и указывают на уязвимые версии:

```bash
npm ls --all --json | jq -r 'paths(scalars) as $p | $p|join(" > ")' | head
```

```
app > express@4.18.2
app > axios@0.21.1
```

Старая версия `axios@0.21.1` имеет известные CVE. Для Python используют `pipdeptree`, для Go — `go mod graph`. По графу видно, какие компоненты доминируют и где сосредоточены риски.

## Что искать в самом пакете

- **API-ключи** — в коде, `.env` и тестовых файлах.
- **Приватные ключи** — `*.pem`, `id_rsa`.
- **Внутренние URL и хосты** — в конфигах и комментариях.
- **Учётные данные** — в скриптах деплоя.
- **История `.git`** — в слоях Docker.
- **Токены CI** — в workflow-файлах.

## Таймлайн релизов

История релизов реестра — это таймлайн активности организации:

```bash
curl -s https://pypi.org/pypi/company-tools/json \
  | jq -r '.releases | to_entries[] | "\(.value[0].upload_time // "?")  \(.key)"' | tail -5
```

```
2023-01-14T09:02:11  1.2.0
2023-06-30T16:44:03  1.3.0
2024-02-11T11:20:57  2.0.0
```

Внезапная смена мейнтейнера или релиз «не тем» автором — сигнал компрометации пакета. Для разведки важны и **заброшенные** пакеты: последний релиз годы назад означает уязвимый, неподдерживаемый код, который всё ещё тянется в проекты.

## Что мы теперь знаем

- Реестры пакетов отдают метаданные, авторов, зависимости и иногда секреты.
- Скачать артефакт можно без установки (`npm pack`, `pip download`).
- Слои Docker хранят удалённые файлы — тег `dev` особенно ценен.
- Имена пакетов реконструируют микросервисную архитектуру.
- Свободное внутреннее имя в публичном реестре — риск dependency confusion.
- Граф зависимостей указывает на устаревшие и уязвимые компоненты.
- История релизов выдаёт заброшенные пакеты и внезапную смену мейнтейнера.
- Реестры — публичная витрина внутренней кухни: то, что инженеры считают приватным, часто лежит в открытом доступе просто потому, что об этом не подумали.

## На что смотреть дальше

Разберись с **provенансом и attestations**: некоторые реестры хранят, какой workflow собрал артефакт, — это связывает пакет с CI. Изучи кэши и зеркала (unpkg, jsDelivr): удалённый пакет часто остаётся там. И посмотри, как защищаться: регистрация внутренних имён, приоритет приватного индекса, secret scanning и многоэтапные сборки, чтобы секреты не попадали в слои.

## Куда дальше

Мы научились разбирать реестры пакетов и находить в них утечки. В следующем уроке — **метаданные файлов**: возьмём документ и фотографию и вытащим из них автора, устройство и историю правок. А пока главное запомни: реестры — это «слишком публичная» часть внутренней инфраструктуры.

## Где пригодится

- **CTF:** задачи с утёкшими секретами в опубликованных пакетах.
- **Bug bounty:** утечки в публичных артефактах и supply-chain-проблемы.
- **Пентест:** анализ зависимостей и версий для поиска уязвимостей.
- **Blue team:** контроль публикаций и защита цепочки поставок.
