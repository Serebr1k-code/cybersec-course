Реестры пакетов (npm, PyPI, RubyGems, Maven, Docker Hub, NuGet) — публичные базы метаданных и кода. Они выдают внутренние имена, структуру организации, контакты авторов и иногда прямые секреты. Это недооценённый, но богатый источник supply-chain-разведки: организация публикует артефакты «для себя», не задумываясь, что это видно всему интернету.

В этом уроке — что искать в каждом реестре, как это связано с атаками на цепочку поставок и как защищаться.

## Что даёт реестр

- **Внутренние имена**: пакеты `@company/internal-*` раскрывают структуру команд и сервисов.
- **Email авторов**: `author`/`maintainers` → сотрудники для дальнейшего OSINT.
- **Исходники**: опубликованный пакет содержит код, иногда с секретами (ключи, пароли, внутренние URL).
- **Зависимости**: граф библиотек и версий → устаревшие/уязвимые компоненты.
- **Typosquat-пакеты**: подделки под популярные имена (атака на цепочку поставок).
- **История версий**: когда и как менялся пакет, кто публиковал.
- **CI/CD-метаданные**: некоторые реестры хранят provenance (какой workflow собрал артефакт).

## npm (JavaScript)

```bash
# метаданные пакета
npm view @company/internal-tools
npm view lodash versions --json
# кто поддерживает
npm view express maintainers
# поиск пакетов организации
npm search @company
# скачать тарбол без установки
npm pack @company/internal-tools
tar -xzf company-internal-tools-*.tgz
```

Ищем в `package.json` поля `author`, `repository`, `homepage`, а в коде — строки с ключами (`AKIA`, `sk-`, `-----BEGIN`). Часто во внутренних пакетах остаются конфиги и URL внутренних API.

## PyPI (Python)

```bash
pip download company-internal-tools --no-deps -d ./pkg
cd pkg && unzip -o *.whl -d extracted
grep -rEi 'password|secret|api[_-]?key|token' extracted/
# метаданные
curl -s https://pypi.org/pypi/requests/json | python3 -m json.tool | head -40
```

В `.whl`/`.tar.gz` ищем `setup.py`, `METADATA`, `PKG-INFO` и любые `.env`/конфиги. PyPI-метаданные отдают автора, лицензию, зависимости и ссылки.

## RubyGems, Maven, NuGet

```bash
# RubyGems
gem info rails
gem fetch internal-gem && gem unpack internal-gem-*.gem

# Maven (Java)
curl -s https://search.maven.org/solrsearch/select?q=g:com.company
mvn dependency:tree

# NuGet (.NET)
nuget list packageid:Company.Internal.*
```

Maven-координаты (`groupId:artifactId`) раскрывают структуру Java-проектов; NuGet — .NET-решения.

## Docker Hub и контейнеры

Образы содержат **слои**, и удалённые файлы остаются в истории:

```bash
docker pull company/app:latest
docker history company/app:latest
# извлечь слои и искать секреты
docker save company/app:latest -o app.tar
mkdir layers && tar -xf app.tar -C layers
grep -rEi 'password|secret|key' layers/ | head
```

Частая находка: `.env`, `.git`, приватные ключи, оставшиеся в слое до «удаления» файла. Также смотрите теги (dev/staging) — там меньше чистят.

## Supply chain: typosquatting и dependency confusion

- **Typosquatting**: злоумышленник публикует `reqeusts` (опечатка `requests`) и ждёт, пока кто-то ошибётся.
- **Dependency confusion**: если компания использует внутреннее имя `@company/utils`, но публичный реестр не занят — атакующий публикует свой пакет с тем же именем. При неправильной конфигурации (публичный реестр приоритетнее) сборка подтянет вредоносный пакет.

```bash
# проверить, свободно ли внутреннее имя в публичном реестре
npm view @company/utils     # 404 → имя свободно → риск dependency confusion
pip index versions company-utils
```

Именно поэтому имена внутренних пакетов (видимые в реестрах) — это и разведданные, и поверхность атаки.

## Разобранный пример: секреты во внутреннем пакете

1. Находим в npm скоуп `@company/`.
2. `npm pack @company/deploy-tools` → распаковываем.
3. `grep -rEi 'AKIA|sk-|BEGIN.*PRIVATE' .` → находим `AWS_ACCESS_KEY_ID` в тестовом файле.
4. Проверяем ключ (в рамках авторизованного теста) — активен.
5. Вывод: утечка секрета через публичный реестр; рекомендация — ротация и secret scanning в CI.

## Разобранный пример: структура организации из имён

1. Собираем все пакеты скоупа `@company/*`.
2. По именам (`@company/auth-service`, `@company/payments-sdk`, `@company/internal-billing`) реконструируем микросервисную архитектуру.
3. По `maintainers` собираем список команд и их зоны ответственности.
4. Сопоставляем с вакансиями и доменами — получаем карту инженерных команд.

## Edge cases и подводные камни

- **Удалённые пакеты** остаются в кэшах/зеркалах (unpkg, jsDelivr) — ищите там.
- **Скоупы** (`@company`) легко спутать с публичными одноимёнными.
- **Секреты могут быть неактуальны** — проверяйте, но не публикуйте.
- **Лицензии** могут запрещать использование кода — учитывайте.
- **Провенанс** (attestations) есть не у всех реестров — отсутствие не означает подделку.
- **Не путать разведку с атакой**: публикация вредоносного пакета — недопустимо; мы только читаем.

## Защита

- Регистрировать внутренние имена в публичных реестрах (занять их).
- Настроить приоритет приватного реестра (npm scope config, pip index).
- Secret scanning в CI, provenance/attestations для сборок.
- Минимальные образы, многоэтапная сборка, чтобы секреты не попадали в слои.

## Что дальше / решение

Практика: возьмите любую известную компанию, найдите её npm-скоуп или PyPI-пакеты, выпишите авторов и зависимости. Затем проверьте, не осталось ли секретов в тарболе. Реестры — это публичная, структурированная и часто «слишком честная» витрина внутренней кухни компании.

## Reference-таблица: реестры и их метаданные

| Реестр | Язык/среда | Что отдаёт API |
|---|---|---|
| npm | JavaScript | author, maintainers, deps, versions |
| PyPI | Python | author, license, deps, URLs |
| RubyGems | Ruby | authors, deps, homepage |
| Maven Central | Java | groupId, artifactId, deps |
| NuGet | .NET | authors, deps, project URL |
| Docker Hub | контейнеры | теги, слои, история |
| crates.io | Rust | авторы, deps |
| Go modules | Go | модули, версии |

## Reference-таблица: типы утечек в пакетах

| Утечка | Где искать | Риск |
|---|---|---|
| API-ключи | код, `.env`, тесты | доступ к сервисам |
| Приватные ключи | `*.pem`, `id_rsa` | SSH/подпись |
| Внутренние URL | конфиги | карта сети |
| Учётные данные | скрипты деплоя | прямой доступ |
| `.git`-история | Docker-слои | полный код + секреты |
| Токены CI | workflow-файлы | доступ к пайплайну |

## Чек-лист разведки по реестрам

1. Найти скоуп/неймспейс организации (`@company`, `com.company`).
2. Собрать все пакеты и выписать авторов/maintainers.
3. Проанализировать зависимости и версии (устаревшие/уязвимые).
4. Скачать артефакты и прогнать secret-scan (`trufflehog`, `grep`).
5. Для контейнеров — разобрать слои (`docker save` + распаковка).
6. Проверить, свободны ли внутренние имена в публичном реестре (dependency confusion).
7. Сопоставить находки с доменами, вакансиями, соцсетями авторов.
8. Задокументировать только публичные данные; не публиковать найденные секреты.

## Разобранный пример: dependency confusion вживую

Сценарий (в лаборатории, без публикации вредоносного кода): компания использует внутренний пакет `company-utils`, но в публичном PyPI он не зарегистрирован.

1. Проверяем:

```bash
pip index versions company-utils
# ERROR: No matching distribution found → имя свободно
```

2. Смотрим конфигурацию установки (`pip.conf`, `--extra-index-url`). Если публичный индекс указан как дополнительный, pip может предпочесть публичную версию с большим номером.
3. Вывод для отчёта: имя не занято + публичный индекс приоритетнее = риск захвата имени. Рекомендация — зарегистрировать имя и настроить приоритет приватного индекса.

Аналогично для npm: `npm view @company/utils` → 404 означает свободный скоуп.

## Разобранный пример: разбор Docker-слоя

```bash
docker pull company/app:dev
docker save company/app:dev -o app.tar
mkdir -p layers && tar -xf app.tar -C layers
ls layers/                       # манифест и blob'ы слоёв
grep -rEi 'AKIA|sk-|password|BEGIN .*PRIVATE' layers/ | head
```

Типичная находка: `.env` с ключами, оставшийся в раннем слое (в финальном образе файл «удалён», но остался в истории). Поэтому важны многоэтапные сборки и чистка слоёв.

## Связка с другими ветками

- Секреты из пакетов → проверка через другие сервисы, ротация.
- Авторы/maintainers → поиск людей и их соцсетей.
- Внутренние имена → реконструкция архитектуры и поиск связанных доменов.
- Уязвимые зависимости → сопоставление с CVE-базами.
- Docker-слои → карта сервисов и конфигураций.

Реестры пакетов — это «слишком публичная» часть внутренней инфраструктуры. То, что инженеры считают приватным, часто лежит в открытом доступе просто потому, что об этом не подумали.

## Граф зависимостей как карта стека

Зависимости пакета раскрывают стек технологии. Собрав их, вы получаете карту того, что использует цель:

```bash
# npm: полный список зависимостей с версиями
npm ls --all --json | jq -r 'paths(scalars) as $p | $p|join(" > ")' | head
```

Вывод:

```text
app > express@4.18.2
app > express@4.18.2 > body-parser@1.20.1
app > axios@0.21.1
```

Устаревшие версии (`axios@0.21.1` — известные CVE) прямо указывают на потенциальные уязвимости. Для Python — `pipdeptree`; для Go — `go mod graph`. По графу видно, какие компоненты доминируют и где сосредоточены риски.

## Итоговый конвейер реестровой разведки

1. GitHub → стек (язык, менеджер пакетов).
2. Реестры → пакеты/образы организации (npm/PyPI/Docker/Maven/Go).
3. Скачивание → метаданные, слои, конфиги.
4. Секреты → `grep`/`trufflehog` по распакованному.
5. Зависимости → граф версий → CVE.
6. Захват имён → проверка dependency confusion.
7. Отчёт → находки, риски, рекомендации.

## Версионирование пакетов и таймлайн релизов

История релизов реестра — это таймлайн активности организации:

```bash
# PyPI: даты последних релизов
curl -s https://pypi.org/pypi/company-tools/json \
  | jq -r '.releases | to_entries[] | "\(.value[0].upload_time // "?")  \(.key)"' | tail -10
```

Вывод:

```text
2023-01-14T09:02:11  1.2.0
2023-06-30T16:44:03  1.3.0
2024-02-11T11:20:57  2.0.0
```

Внезапная смена мейнтейнера или релиз «не тем» автором — сигнал компрометации пакета. Для разведки важны и **заброшенные** пакеты: последний релиз годы назад означает уязвимый, не поддерживаемый код, который всё ещё тянется в проекты.

## Где пригодится

- **CTF:** задачи с утёкшими секретами в опубликованных пакетах.
- **Bug bounty:** утечки в публичных артефактах и supply-chain-проблемы.
- **Пентест:** анализ зависимостей и версий для поиска уязвимостей.
- **Blue team:** контроль публикаций и защита цепочки поставок.
