## Вопрос, с которого всё начинается

Пассивный сбор дал тебе список поддоменов `target.com`, но `dev.` и `staging.` в нём не оказалось — а именно такие стенды обычно и самые уязвимые. Пассивные базы знают только то, что кто-то когда-то засветил. Что делать с именами, которых там нет?

Ответ — **активный перебор** словарём. Разберём его на конкретной цели.

## Наш пример: ищем скрытые стенды target.com

Введём термины. **Пассивный сбор** — поиск по чужим базам (CT-логи, архивы, поисковики), без запросов к цели. **Активный перебор** — мы сами отправляем DNS-запросы: подставляем слова из словаря к домену и смотрим, что резолвится. Второй полнее, но заметнее — запросы видны резолверу цели.

Наша цель — `target.com`; хотим найти `staging-api.target.com` и подобные.

## Шаг 1: сначала пассивно, потом активно

Правильная тактика — комбинация. Пассивный сбор быстр, тих и даёт базу:

```bash
subfinder -d target.com -all -silent | sort -u > subs.txt
amass enum -passive -d target.com -silent >> subs.txt
```

Только потом, когда база собрана, добираем активным перебором. Активный брут — только по авторизации: в пентесте в рамках договора, в bug bounty — если разрешено правилами программы.

## Шаг 2: берём словарь

Качество словаря важнее скорости. Источники — репозиторий **SecLists**, каталог `Discovery/DNS/`:

```bash
wget https://raw.githubusercontent.com/danielmiessler/SecLists/master/Discovery/DNS/subdomains-top1million-110000.txt
```

Популярные словари: `subdomains-top1million-5000.txt` (5k), `subdomains-top1million-110000.txt` (110k), `dns-Jhaddix.txt` (2M+). Правило: начинай с небольшого точного словаря, затем расширяй. Плюс генерируй **собственные** варианты из уже найденных имён.

## Шаг 3: брутим с валидацией и wildcard-фильтром

Ключевой инструмент — **puredns**: он делает высокоскоростной перебор через massdns и сразу отбрасывает wildcard-мусор:

```bash
puredns bruteforce subdomains-top1million-110000.txt target.com \
  -r resolvers.txt -w brute.txt --wildcard-tests 10
```

Вывод `brute.txt` (фрагмент):

```
staging-api.target.com
dev.target.com
jenkins.target.com
old-admin.target.com
```

Мы получили имена, которых не было в пассивных базах. `resolvers.txt` — список публичных резолверов, которые puredns использует для запросов.

## Шаг 4: объединяем и резолвим

Складываем пассивный и активный результаты и проверяем, что всё живо:

```bash
cat subs.txt brute.txt | sort -u | dnsx -a -resp -silent -o resolved.txt
httpx -l resolved.txt -title -status-code -silent -o alive.txt
```

`httpx` отбирает хосты, которые реально отвечают по HTTP, с заголовком и статусом. `staging-api` со статусом 200 — приоритетная цель.

## Шаг 5: обходим wildcard DNS

Главная проблема брутфорса — **wildcard DNS**: `*.target.com` резолвится в один IP, и перебор даёт тысячи «ложных» поддоменов. Проверка:

```bash
dig +short $(head -c8 /dev/urandom | base32).target.com
```

Если случайное имя резолвится — wildcard активен. Решения:

- **Фильтровать по ответу**: отбрасывать имена, резолвящиеся в тот же IP, что и случайное.
- **puredns/shuffledns** делают это автоматически (`--wildcard-tests`).
- Сравнивать CNAME, а не только факт резолва.

## Шаг 6: permutations — расширяем из найденного

Когда базовый словарь исчерпан, генерируют **перестановки** из известных имён: `api.target.com` → `api-dev`, `dev-api`, `api-staging`, `api2`. Инструменты — `altdns`, `dnsgen`, `gotator`:

```bash
cat subs.txt | dnsgen - | puredns resolve -r resolvers.txt -w perms.txt
```

Это находит стенды, которые не угадываются одним словом, но собираются из уже известных частей. Например, из `api.target.com` dnsgen породит `dev-api`, `api-staging`, `api2`, `api-old` — и часть из них окажется живой.

## Шаг 7: vhost-фаззинг

Бывает, что поддомена нет в DNS вообще, но сайт на том же IP живёт — это **виртуальный хост**. Его ищут через заголовок `Host`:

```bash
ffuf -u http://10.0.0.5 -H "Host: FUZZ.target.com" -w wordlist.txt -fs 0
```

Так находят сервисы, невидимые для DNS-брута. `-fs 0` отбрасывает ответы нулевого размера (заглушки). Vhost-фаззинг особенно полезен на общем хостинге, где один IP обслуживает десятки сайтов.

## Шаг 8: производительность и резолверы

Скорость перебора определяется резолверами и инструментом:

- Собери **большой список** публичных резолверов (репозитории `public-dns`).
- Используй `massdns`/`puredns` с параллелизмом — тысячи запросов в секунду.
- Учитывай **rate-limit**: слишком агрессивно — бан и потеря времени.
- Для тихого recon предпочитай пассивные источники; активный брут — по необходимости.

Оптимальный баланс: сначала пассивная база, затем точечный добрут небольшим словарём, а не «долбёж» миллионами имён.

## Шаг 9: автоматизируем пайплайн

Для регулярного recon цепочку сворачивают в один скрипт:

```bash
#!/usr/bin/env bash
D=target.com
subfinder -d $D -all -silent > subs.txt
amass enum -passive -d $D -silent >> subs.txt
puredns bruteforce subdomains-top1million-110000.txt $D -r resolvers.txt -w brute.txt --wildcard-tests 10
cat subs.txt brute.txt | sort -u > all.txt
dnsx -l all.txt -a -resp -silent > resolved.txt
httpx -l resolved.txt -title -status-code -tech-detect -silent > alive.txt
```

Результат `alive.txt` — список живых сервисов, готовый к анализу. Запускай по расписанию и считай diff — новые поддомены означают новые активы.

## Что мы теперь знаем

- Пассивный сбор быстр и тих, активный — полнее, но заметен для цели.
- puredns сочетает брутфорс, валидацию и фильтр wildcard.
- Wildcard DNS ломает перебор, если его не отфильтровать.
- Permutations и vhost-фаззинг находят имена, которых нет в DNS.
- Активный брут допустим только по авторизации.

## Частые ошибки

- **Wildcard ломает брут.** Без фильтра — тысячи ложных попаданий.
- **Публичные резолверы блокируют.** Rate-limit; используй свой список.
- **Медленный брут одним потоком.** Часы вместо минут; нужен massdns/puredns.
- **Забыть про vhost.** Поддомена нет в DNS, но сайт живёт.
- **Юридические рамки.** Активный брут — только по авторизации.

## На что смотреть дальше

Один этап recon порождает несколько векторов: `staging-api` может отдавать Swagger без авторизации, `jenkins.target.com` — открытую CI-панель, `dev.target.com` — исходники с `.git`. Дальше разберём **DNSSEC и CAA** — защитные DNS-записи, которые сами по себе являются разведданными. А пока главное запомни: поддомен, которого нет в пассивных базах, всё ещё может существовать — его находит словарь.

## Разбор кейса: ложный рост из-за wildcard

**Wildcard DNS** — это запись вида `*.example.com`, которая отвечает на любое имя. Новичок запускает перебор и видит: `random123.example.com` резолвится, `asdf.example.com` тоже. Кажется, что домен «разросся» до тысяч поддоменов. На самом деле это одна wildcard-запись, которая лжёт.

Проверка проста: запроси заведомо несуществующее имя из случайных символов.

```bash
dig +short zzq7random123.example.com
```

Если вернулся адрес — wildcard есть. Тогда перебор надо фильтровать: сравнивать ответы и отбрасывать всё, что совпадает с wildcard-ответом. Инструменты вроде `puredns` и `dnsx` делают это автоматически, но проверить настройку всё равно нужно.

Второй подвох — **CNAME на CDN**. Если поддомен указывает на Cloudflare, любой ответ будет отдавать «живой» IP, но это не значит, что за ним что-то есть. Отличай реальный хост от заглушки CDN. Третий подвох — **«мёртвые» поддомены**: имя резолвится, но по HTTP ничего не отвечает. Это всё ещё актив: он может быть перехвачен (dangling CNAME → subdomain takeover). Поэтому после резолва всегда проверяй веб-слой и ищи висячие CNAME.

## Если не сработало

**Словарь не даёт результатов.** Возможно, имена нестандартные (`k8s-`, `-prod-`, хеши). Попробуй permutations из уже найденных имён — часто новые поддомены собираются из частей старых.

**DNS-сервер ограничивает запросы.** Не бей одним резолвером. Используй список публичных резолверов и `massdns` — он разгоняет перебор и умеет распределять нагрузку.

**Перебор слишком медленный.** Уменьши словарь до релевантного, включи параллелизм, но не переусердствуй: агрессивный брут — это шум, который заметен в логах защитных систем.

**Нашёл много, но всё не в scope.** Отфильтруй по правилам программы: чужие домены и инфраструктура провайдера — не цель.

## Частые вопросы

**Пассивный или активный перебор?** Сначала пассивный (crt.sh, SecurityTrails, Wayback) — он не шумит и даёт готовые имена. Активный брут — когда пассив закончился, чтобы найти то, что нигде не публиковалось.

**Сколько резолверов нужно?** Для небольшой цели хватает 5–10 надёжных. Слишком много — риск попасть в бан у резолверов и потерять время на ретраи.

**Vhost — это то же самое?** Нет. Vhost-фаззинг ищет имена, которые не в DNS, а настраиваются на веб-сервере (виртуальные хосты). Часто за одним IP прячется десяток сайтов, невидимых в DNS.

## Мини-практика: подтверждаем wildcard

Проверь любой домен на wildcard до брута. Запроси три случайных имени и сравни ответы:

```bash
for i in 1 2 3; do dig +short $i$(openssl rand -hex 4).example.com; done
```

Если все три вернули один и тот же адрес — wildcard есть, и перебор без фильтра даст ложный результат. Если ответы пустые — можно брутить. Этот простой опыт экономит часы: без него новичок собирает тысячи «поддоменов», которых не существует, и потом не понимает, почему веб-проверка показывает одинаковую заглушку для всех.

## Куда дальше

Мы научились добирать имена активным перебором и обходить wildcard. В следующем уроке — **DNSSEC и CAA**: защитные записи, из которых видно, насколько зрелая у домена безопасность и каких вендоров он использует. А пока главное запомни: сначала пассивно, потом активно — и всегда с фильтром wildcard.

## Где пригодится

- **Recon и пентест:** расширение поверхности атаки.
- **Bug bounty:** поиск забытых стендов.
- **Работа/SOC:** инвентаризация внешних активов.
- **CTF:** поиск скрытого поддомена с флагом.
