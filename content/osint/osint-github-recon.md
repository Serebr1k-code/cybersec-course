## Вопрос, с которого всё начинается

Ты хочешь понять, чем занимается организация `example` и нет ли у неё утечек. Новичок смотрит только на её сайт.

Но у разработчиков есть **публичные репозитории** — это «письма, которые никто не отправлял, но все читают». Туда коммитят `.env`, ключи и пароли, а потом «удаляют» — но история git и форки всё помнят. Разберём это на одной организации.

## Наш пример: организация example

У нас один объект — организация `example` на GitHub. Введём термины. **Репозиторий** — папка с кодом под контролем версий. **Коммит** — сохранённое изменение с историей. **Секрет** — ключ, пароль или токен, который не должен быть публичным.

## Шаг 1: ищем по операторам GitHub-поиска

У GitHub-поиска есть операторы — уточняющие слова в запросе:

| Оператор | Что делает |
|---|---|
| `org:` | ограничивает организацией |
| `filename:` | ищет по имени файла |
| `path:` | ищет по пути |
| `extension:` | по расширению (`.pem`) |
| `in:file` | ищет текст в файлах |

Наш первый запрос — поиск файлов `.env` в организации:

```
org:example filename:.env
```

```
example/backend   app/.env   (removed)
```

Важное ограничение: GitHub-поиск по умолчанию смотрит только в **основную ветку** и **не заглядывает в историю**. То, что файл «removed», ничего не значит — он остался в коммитах.

## Шаг 2: клонируем и сканируем историю

Клонируем репозиторий и прогоняем его через **gitleaks** — инструмент, который ищет секреты во всей истории:

```bash
git clone https://github.com/example/backend.git
gitleaks detect --source backend --report report.json
```

```
Finding:     DB_PASSWORD=Sup3rS3cret!
Secret:      Sup3rS3cret!
RuleID:      generic-api-key
File:        app/.env
Commit:      a1b2c3d4
```

Gitleaks нашёл пароль базы в старом коммите, хотя в текущей версии файла его уже нет. Есть и второй инструмент — **trufflehog**; его отличие в том, что он умеет **верифицировать** ключи, то есть делать тестовый запрос и проверять, живой ли ключ:

```bash
trufflehog git https://github.com/example/backend.git --json | tee truffle.json
```

## Шаг 3: достаём «удалённый» секрет вручную

Даже без инструментов история git открыта. Посмотрим, какие файлы `.env` когда-либо существовали, по **всем** веткам:

```bash
cd backend
git log --all --full-history -- '*.env'
```

```
commit a1b2c3d4...
Author: dev <dev@example.com>
    add config

    app/.env
```

Флаг `--all` включает все ветки, а не только текущую. Теперь покажем содержимое файла из того коммита:

```bash
git show a1b2c3d4:app/.env
```

```
DB_PASSWORD=Sup3rS3cret!
AWS_ACCESS_KEY_ID=AKIA...
AWS_SECRET_ACCESS_KEY=...
```

Вот и утечка — включая ключ AWS с характерным префиксом `AKIA`.

## Шаг 4: ищем по отпечаткам секретов

Секреты узнают по началу строки. Зная отпечатки, вы быстро фильтруете шум:

| Секрет | Отпечаток |
|---|---|
| AWS Access Key | `AKIA` или `ASIA` |
| Google API | `AIza` |
| Slack token | `xox[baprs]-` |
| GitHub PAT | `ghp_` или `github_pat_` |
| Приватный ключ | `-----BEGIN` |

Например, поиск `"AKIA" org:example` находит ключи AWS прямо в индексе GitHub.

## Шаг 5: проверяем ключ — осторожно

Найденный ключ надо подтвердить, но **минимально**. Для AWS безопасный способ — спросить, кто мы, не трогая данные:

```bash
AWS_ACCESS_KEY_ID=AKIA... AWS_SECRET_ACCESS_KEY=... aws sts get-caller-identity
```

```
{
    "Account": "123456789012",
    "Arn": "arn:aws:iam::123456789012:user/dev"
}
```

Ключ валиден. На этом проверку надо **остановить**: дальнейшее использование — уже атака, а не разведка.

## Шаг 6: масштабируем на организацию

Один репозиторий — капля в море. Получаем список всех и сканируем пачкой:

```bash
curl -s "https://api.github.com/orgs/example/repos?per_page=100" | jq -r '.[].clone_url' > repos.txt
while read u; do git clone --quiet "$u" repo_$(basename "$u" .git); done < repos.txt
gitleaks detect --source . --report org_report.json
```

Дополнительно **grep.app** и **Sourcegraph** ищут по индексу тысяч репозиториев без клонирования, а **GH Archive** отдаёт события платформы — так находят свежие пуши в реальном времени. Для большой организации полезно не только собирать список репозиториев, но и следить за новыми: свежий коммит с секретом живёт до ротации считанные часы.

## Шаг 7: что делать с находкой

Валидный секрет — это ответственность. Порядок такой:

1. Не использовать ключ дальше минимального подтверждения.
2. Определить владельца по `org`, домену и почте из коммитов.
3. Сообщить через `security.txt`, программу bug bounty или напрямую.
4. Не публиковать ключ до исправления.
5. Задокументировать репозиторий, коммит, время и тип ключа.

Для своей организации настройте автоматический secret scanning и ротацию ключей.

## Инструменты и флаги

| Инструмент | Команда | Назначение |
|---|---|---|
| GitHub search | `org: filename: path:` | поиск по коду |
| gitleaks | `detect --source repo` | секреты в истории |
| trufflehog | `git <url> --only-verified` | верификация ключей |
| git log | `--all --full-history -- '*.env'` | история файлов |
| grep.app / Sourcegraph | веб | поиск по многим репозиториям |
| GH Archive | датасеты | события платформы |

## Что мы теперь знаем

- Публичные репозитории — источник кода, людей и секретов.
- GitHub-поиск видит только основную ветку; историю надо клонировать.
- Gitleaks находит секреты в истории, trufflehog умеет их верифицировать.
- `git log --all --full-history` и `git show` достают «удалённые» файлы.
- Секреты опознаются по отпечаткам (`AKIA`, `ghp_`, `BEGIN`).
- Найденный ключ подтверждают минимально и передают владельцу.
- GitHub-поиск видит только основную ветку, а `grep.app` и Sourcegraph — по индексу тысяч репозиториев.

## На что смотреть дальше

Разберись с **secret scanning** как отдельной дисциплиной: он сканирует не только git, но и CI-конфиги (`.github/workflows`), где секреты живут в переменных. Изучи поиск по форкам и зеркалам: удалённый коммит часто остаётся у форка. Дальше это перерастёт в supply chain security.

## Куда дальше

Мы научились искать секреты в репозиториях и истории. В следующем уроке — **secret scanning**: разберём глубже, как искать ключи в CI-конфигах, артефактах и по отпечаткам, и как настроить проверку для своей организации. А пока главное запомни: «удалено» в git не значит «стёрто».

## Где пригодится

- **Bug bounty:** утёкшие ключи — высокооплачиваемый класс находок.
- **Supply chain:** аудит своих репозиториев и репозиториев зависимостей.
- **CTF (OSINT):** найти секрет в «случайном» репозитории.
- **Пентест:** получить первый доступ через утёкший токен.
