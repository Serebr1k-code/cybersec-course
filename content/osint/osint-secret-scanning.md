## Вопрос, с которого всё начинается

Ты нашёл в публичном репозитории подозрительную строку, похожую на API-ключ. Новичок сразу пытается её «проверить на удачу» — и это может обернуться либо блокировкой, либо реальным инцидентом.

Автоматический поиск секретов — один из самых высокооплачиваемых приёмов bug bounty: валидный ключ AWS или Stripe часто даёт прямой доступ к инфраструктуре. Но работать надо дисциплинированно. Разберём это на одной организации.

## Наш пример: организация targetorg

У нас один объект — организация `targetorg`. Введём термины. **Секрет** — ключ, токен или пароль, который даёт доступ к сервису. **Верификация** — безопасная проверка, жив ли ключ. **Read-only** — вызов, который только читает данные и ничего не меняет.

## Шаг 1: запускаем gitleaks

Первый инструмент — **gitleaks**. Он быстрый, работает офлайн и ищет секреты по регулярным выражениям как в текущем дереве, так и в истории:

```bash
gitleaks detect --source . --report-format json --report-path leaks.json
```

```
Finding:     AWS Access Key
Secret:      AKIA...
RuleID:      aws-access-token
File:        config/settings.py
Commit:      3f2a1c
```

Ключевая деталь: флаг `--no-git` заставил бы сканировать только текущее дерево. Мы его **не** ставим — именно история хранит секреты, которые «удалили».

## Шаг 2: подключаем trufflehog с верификацией

У gitleaks есть слабое место — ложные срабатывания. **trufflehog** решает это верификацией: он делает безопасный запрос к сервису и проверяет, живой ли ключ. Флаг `--only-verified` оставляет только подтверждённые находки:

```bash
trufflehog github --org=targetorg --only-verified
```

```
Found verified result
Detector Type: AWS
Account: 123456789012
Detector Type: Slack
Team: targetorg
Detector Type: SendGrid
```

Три верифицированных ключа. Теперь мы точно знаем: это не шум, а реальные активы.

## Шаг 3: смотрим, где именно нашёлся секрет

Для находки в git важно зафиксировать место. Достаём коммит:

```bash
git show 3f2a1c -- config/settings.py
```

```
AWS_ACCESS_KEY_ID = "AKIA..."
AWS_SECRET_ACCESS_KEY = "..."
```

Файл в текущем дереве уже без ключа — но коммит остался. Это и есть разница между «текущее дерево» и «история».

## Шаг 4: верифицируем сами — только read-only

Даже с trufflehog стоит уметь проверить ключ вручную. Главное правило: **только чтение**, ничего не создавать и не удалять. Для AWS безопасный вызов — «кто я»:

```bash
AWS_ACCESS_KEY_ID=AKIA... AWS_SECRET_ACCESS_KEY=... aws sts get-caller-identity
```

```
{
    "Account": "123456789012",
    "Arn": "arn:aws:iam::123456789012:user/deploy"
}
```

Аналогично для других сервисов:

```bash
curl -s -H "Authorization: token $TOKEN" https://api.github.com/user
curl -s -H "Authorization: Bearer $TOKEN" https://slack.com/api/auth.test
curl -s https://api.stripe.com/v1/balance -u "$KEY:"
```

## Шаг 5: оцениваем blast radius

Прежде чем сообщать, надо понять масштаб доступа. Смотрим списки — снова только чтение:

```bash
aws iam list-attached-user-policies --user-name deploy
```

```
PolicyName: BackupReadOnly
```

Роль `deploy` имеет право `s3:GetObject` на бакет `backups-prod`. Вывод: чтение бэкапов, возможно, с персональными данными. **Дальше не развиваем доступ** — останавливаемся на доказательстве.

## Шаг 6: ищем секреты вне git

Секреты живут не только в коде. Полезные точки:

- **CI-логи** открытых сборок: ищите `echo $SECRET`, `printenv`, `set -x`.
- **Workflow-файлы**: `.github/workflows/*.yml` раскрывают **имена** секретов.

```bash
curl -s -H "Authorization: token $GH_TOKEN" \
  "https://api.github.com/search/code?q=secrets.+org:targetorg+filename:.yml" | jq -r '.items[].html_url'
```

```
https://github.com/targetorg/app/blob/main/.github/workflows/deploy.yml
```

Так вы узнаёте имена `secrets.AWS_KEY` и `secrets.DEPLOY_TOKEN` — это уже карта инфраструктуры, даже без самих значений.

- **Бинарники**: ключ, вшитый в сборку, виден через `strings`.

```bash
strings ./binary | grep -E 'AKIA|ghp_|sk_live_|xox|AIza'
```

Особенно часто ключ вшит во фронтенд-бандл или мобильное приложение — тогда он виден любому пользователю.

## Шаг 7: что делать с находкой

Порядок реагирования строгий:

1. Зафиксировать доказательство: где найден, тип, дата.
2. Проверить валидность — только read-only.
3. Оценить blast radius — списки, не действия.
4. Остановиться на доказательстве.
5. Сообщить владельцу с рекомендацией ротации.
6. Замаскировать ключ в отчёте (`AKIA…XXXX`).

Пример аккуратной формулировки в отчёте:

```
Ключ: AKIA…(маскирован)
Роль: deploy
Права: s3:GetObject (бакет backups-prod)
Impact: чтение бэкапов с PII
Рекомендация: немедленная ротация + ограничение политики
```

## Где ещё переживают секреты

- **История коммитов** — файл удалён, коммит остался.
- **Форки** — не содержат чистку оригинала.
- **Кэш CI** — артефакты сборок хранят переменные окружения.
- **Docker-слои** — «удалённый» `.env` остаётся в слое образа.
- **Wayback Machine** — старая версия страницы с ключом.
- **gist и pastebin** — фрагменты кода, часто с ключами.

Вывод один: удаление файла — не защита. Единственная надёжная мера — отзыв и ротация ключа плюс secret scanning на входе.

## Защита собственных репозиториев

Те же инструменты работают «в свою сторону»:

- **pre-commit хук**: `gitleaks protect --staged` не даёт закоммитить секрет.
- **CI-скан**: gitleaks или trufflehog на каждом pull request.
- **GitHub secret scanning**: встроенная защита и push protection.
- **Ротация**: любой секрет, попавший в историю, считается скомпрометированным — его меняют, а не просто удаляют файл.
- **Проверка форков**: форки наследуют историю, и удаление в апстриме их не чистит.

Флаг `--redact` маскирует значения секретов в выводе — это важно для публичных логов CI.

## Что мы теперь знаем

- Gitleaks ищет секреты в дереве и истории, trufflehog верифицирует находки.
- Текущее дерево и история — разные вещи: удалённый файл живёт в коммитах.
- Верификация допустима только read-only; дальше доказательства не идём.
- Секреты живут в CI-логах, workflow-файлах, бинарниках и фронтенд-бандлах.
- Удаление файла — не защита; нужна ротация ключа.

## На что смотреть дальше

Разберись с **защитой своих репозиториев**: pre-commit хук `gitleaks protect --staged` не даёт закоммитить секрет, а CI-скан с `--redact` маскирует значения в публичных логах. Изучи форки и зеркала: чистка оригинала не чистит форки. И разберись, как секреты переживают удаление в Docker-слоях и кэше сборок.

## Куда дальше

Мы освоили автоматический поиск секретов и их безопасную верификацию. В следующем уроке — **история git**: разберём глубже, как доставать удалённые файлы, находить потерянные коммиты и что остаётся в форках. А пока главное запомни: удаление файла — не защита, защита — это ротация.

## Где пригодится

- **CTF:** задачи с утёкшими ключами в приложенном репозитории.
- **Bug bounty:** утёкшие ключи — частый высокооплачиваемый отчёт.
- **Пентест:** доступ через секреты в коде организации.
- **Blue team:** аудит собственных репозиториев и pre-commit-хуки.
