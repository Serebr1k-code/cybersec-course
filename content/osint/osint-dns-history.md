## Вопрос, с которого всё начинается

Домен `shop.example.com` закрыт Cloudflare — CDN, который прячет настоящий сервер. Обычный DNS-запрос вернёт только адрес Cloudflare, и до реального сервера так не добраться.

Но инфраструктура **меняется во времени**: раньше домен мог резолвиться напрямую, а потом «переехал» под CDN. Исторические DNS-записи хранят это прошлое. Разберём, как по ним найти настоящий сервер.

## Наш пример: shop.example.com за Cloudflare

Работаем с одним доменом — `shop.example.com`. Задача: найти его **origin-IP** (настоящий сервер за CDN) и проверить поддомены на висячие CNAME. Начнём с понимания, откуда вообще берётся история.

## Шаг 1: что такое пассивный DNS

**Пассивный DNS** (passive DNS, pDNS) — это архив DNS-ответов, собранный сенсорами у рекурсивных резолверов и корневых серверов. Сервис отдаёт то, что **кто-то уже спрашивал раньше**, не посылая ни одного запроса к цели. Это полностью пассивная разведка: цель не видит нас.

| Сервис | Особенность |
|--------|-------------|
| SecurityTrails | история A/CNAME/MX/TXT, API |
| PassiveTotal (RiskIQ) | история, WHOIS, соседи |
| ViewDNS.info | бесплатные разовые запросы |
| DNSdumpster | визуальная карта поддоменов |
| RapidDNS | бесплатный и быстрый |

Ключевое свойство: база видит только то, что кто-то спрашивал, поэтому редкие имена могут отсутствовать. Покрытие зависит от расположения сенсоров, значит разные провайдеры дают разные срезы.

## Шаг 2: смотрим исторические A-записи

A-запись сопоставляет имя и IP-адрес. В истории видно все адреса, на которые домен указывал за годы.

```bash
curl -s "https://api.securitytrails.com/v1/history/example.com/dns/a" \
  -H "APIKEY: $ST_KEY" | python3 -m json.tool
```

```
{
  "records": [
    { "ip": "203.0.113.10", "first_seen": "2023-01-10", "last_seen": "2024-06-01" },
    { "ip": "198.51.100.7", "first_seen": "2021-02-01", "last_seen": "2022-12-20" }
  ]
}
```

Для каждой записи важны `first_seen` и `last_seen`. Адрес, активный до переезда под CDN, — кандидат в origin.

## Шаг 3: отсеиваем CDN по ASN

Не все исторические IP полезны: часть принадлежит самому CDN. Чтобы их отсеять, смотрим **ASN** — номер автономной системы, то есть сетевого оператора.

```text
203.0.113.10  → AS13335 (Cloudflare) → это CDN, не origin
198.51.100.7  → AS64500 (хостинг-провайдер) → «серый» IP, кандидат в origin
```

Остаётся `198.51.100.7` — адрес вне сети Cloudflare. Именно его проверяем дальше.

## Шаг 4: проверяем кандидата запросом с Host

Origin-сервер обычно отвечает на тот же домен. Поэтому делаем запрос к найденному IP, но в заголовке `Host` указываем целевое имя.

```bash
curl -sI https://198.51.100.7 -H 'Host: shop.example.com'
```

```
HTTP/2 200
server: nginx
x-shop: v2
```

Ответ совпал с тем, что отдаёт домен, — значит, origin найден. Дополнительные источники origin: сертификаты CT, старые MX и SPF, поиск по favicon в Shodan, утечки в GitHub.

## Шаг 5: CNAME и subdomain takeover

Отдельный класс находок — висячие CNAME. Смотрим цепочку:

```bash
dig +short sub.example.com CNAME
```

```
sub.example.com.  CNAME  bucket.s3.amazonaws.com.
```

Если CNAME указывает на сторонний сервис, а ресурс там уже удалён, хост отдаёт ошибку вроде `NoSuchBucket`. Тогда имя можно «занять» — это **subdomain takeover**. Типичные висячие цели: `*.s3.amazonaws.com`, `*.cloudfront.net`, `*.azurewebsites.net`, `*.github.io`, `*.herokuapp.com`.

```bash
curl -s "http://sub.example.com" | grep -iE 'NoSuchBucket|No such app|GitHub Pages'
```

В bug bounty такой takeover награждается, но эксплуатировать его без scope нельзя.

## Шаг 6: соседи по хостингу

Пассивный DNS позволяет найти другие домены на том же IP — обратный IP.

```bash
curl -s "https://api.viewdns.info/reverseip/?host=198.51.100.7&apikey=$VD_KEY&output=json"
```

```
domains: [api.example.com, dev.example.com, mail.example.com]
```

Соседи выдают связанные проекты компании и инфраструктуру подрядчика — ещё один слой для расширения периметра.

## Как работает сбор passive DNS

Понимание механики помогает интерпретировать данные и их пробелы. Провайдеры ставят **сенсоры** в точках, где виден DNS-трафик: у крупных рекурсивных резолверов, в корневых узлах, у провайдеров. Сенсор логирует пары «запрос → ответ» и складывает их в базу с метками времени. Отсюда важные свойства: база видит только то, что кто-то спрашивал, поэтому редкие имена могут отсутствовать; покрытие зависит от расположения сенсоров; данные обновляются с задержкой. Именно поэтому одну цель смотрят сразу в нескольких базах и объединяют результаты.

## Пассивный DNS для MX, TXT и IPv6

Историю смотрят не только по A-записям:

- **MX** — старые почтовые серверы выдают прежних провайдеров; почтовый origin часто не за CDN.
- **TXT/SPF** — включают сторонние сервисы через `include:`, перечисляя используемые SaaS и подрядчиков.
- **NS** — смена DNS-провайдера видна в истории и выдаёт миграции.
- **AAAA (IPv6)** — у домена может быть отдельная история IPv6, где CDN включили позже.

```bash
curl -s "https://api.securitytrails.com/v1/history/example.com/dns/mx" -H "APIKEY: $ST_KEY" | jq
```

Совокупность MX, SPF и исторических A часто выводит на origin быстрее, чем один только A-историк.

## Мониторинг изменений DNS

Историю используют не только для разового разбора, но и для регулярного мониторинга. Периодически выгружай A/CNAME/MX через API и сравнивай со прошлым снимком:

```bash
curl -s ".../domain/example.com/subdomains" -H "APIKEY: $ST_KEY" > today.json
diff <(jq -r '.subdomains[]' prev.json) <(jq -r '.subdomains[]' today.json)
```

Новый CNAME на сторонний сервис — потенциальный takeover-риск. Исчезнувшая A-запись у важного хоста — сигнал сбоя или миграции. Смена NS — переход к другому DNS-провайдеру.

## Быстрая шпаргалка

| Задача | Команда или сервис |
|--------|--------------------|
| история A | SecurityTrails `/history/<d>/dns/a` |
| поддомены | SecurityTrails `/domain/<d>/subdomains` |
| обратный IP | ViewDNS `/reverseip/?host=<ip>` |
| takeover | `subjack -w subs.txt -ssl` |
| origin-проверка | `curl -sI https://<ip> -H 'Host: <d>'` |

## Что мы теперь знаем

По-простому:

1. Пассивный DNS — история ответов, без запросов к цели.
2. Исторические A-записи выдают origin до переезда под CDN.
3. ASN отсеивает адреса самого CDN.
4. Кандидата проверяют запросом с заголовком `Host`.
5. Висячий CNAME — потенциальный subdomain takeover.

## На что смотреть дальше

- **Сверяй несколько баз.** Разные сенсоры видят разное — SecurityTrails, RiskIQ, ViewDNS.
- **Не путай пассивный и активный.** Сама база — пассивна, но `dig` к найденному имени уже активен.
- **Смотри даты.** Старая запись может быть полностью мёртвой.
- **Не считай CDN-IP origin-ом.** Сначала проверь ASN.
- **Не пропускай CNAME.** Висячие CNAME — отдельный класс уязвимостей.

## Разбор кейса: домен сменил хостинг

DNS меняется со временем: домен переезжает с одного хостинга на другой, меняет почтового провайдера, теряет поддомены. История DNS показывает эти изменения — и часто выдаёт забытые активы. Разберём.

Первый шаг — **исторические записи**. Сервисы вроде SecurityTrails и PassiveTotal хранят снимки DNS за годы. Запрос по домену покажет: какие IP были раньше, какие MX использовались, какие поддомены существовали. Второй шаг — **анализ изменений**. Если домен год назад указывал на IP хостинга X, а сейчас на Y — на IP X мог остаться старый сайт или тестовый стенд. Заброшенные стенды — частая находка.

Третий шаг — **исторические поддомены**. Поддомен, который сегодня не резолвится, мог существовать раньше и всё ещё указывать на сервис. Проверь старые CNAME: возможно, там висит ссылка на облачный сервис — кандидат на takeover.

Четвёртый шаг — **WHOIS-история**. Смена регистранта, контактов, NS — всё это сигналы. Если домен сменил владельца, старые данные могут содержать связи с прежней организацией.

## Если не сработало

**История недоступна бесплатно.** Часть данных за подпиской. Используй бесплатные срезы и Wayback.

**Записей нет.** Домен молодой или не менялся. Это тоже результат.

**Противоречия в датах.** Разные сервисы снимают в разное время. Сверяй по датам.

**Слишком много данных.** Ограничь период и типы записей.

## Частые вопросы

**Что такое PassiveTotal?** Сервис пассивного DNS с историей. Аналог SecurityTrails.

**Зачем искать старые IP?** На них могут остаться стенды, панели, бэкапы — забытые активы.

**Как связать историю с takeover?** Старый CNAME на облачный сервис + отсутствие записи сегодня = возможный захват.

## Мини-практика: таймлайн домена

Построй таймлайн одного домена: год за годом — IP, MX, NS, поддомены. Отметь изменения и проверь старые IP на живость. Сопоставь смены хостинга с событиями компании (ребрендинг, слияние). Так история DNS превращается в рассказ о жизни организации.

## Вопросы и ответы

**Зачем смотреть историю DNS?** DNS меняется со временем, и прошлые записи выдают забытые активы: старые IP, прежние поддомены, сменившихся провайдеров. Это расширяет поверхность атаки за пределы текущего состояния.

**Что даёт смена IP?** Если домен год назад указывал на хостинг X, на этом IP мог остаться старый сайт или тестовый стенд. Заброшенные стенды — частая находка, потому что о них забывают.

**Как исторические поддомены помогают с takeover?** Поддомен, который сегодня не резолвится, мог раньше указывать на облачный сервис. Если запись сохранилась, а сервис удалён, поддомен можно захватить — классический takeover.

**Почему важна WHOIS-история?** Смена регистранта, контактов и NS указывает на смену владельца или инфраструктуры. Старые данные могут содержать связи с прежней организацией и людьми.

**Где брать исторические данные?** В SecurityTrails, PassiveTotal, Wayback и агрегаторах. Часть данных платные, поэтому начинай с бесплатных срезов и архивов.

**Как не запутаться в датах?** Разные сервисы снимают DNS в разное время, поэтому сверяй даты и указывай их в отчёте. Точная привязка ко времени делает выводы проверяемыми.

## Куда дальше

В следующем уроке мы возьмём **зону домена** и разберём, что такое AXFR-трансфер и когда он отдаёт всю карту имён сразу. А пока запомни главное: пассивный DNS ничего не трогает у цели, но всегда неполон — поэтому его читают по нескольким базам сразу.

## Где пригодится

- **CTF:** восстановление скрытой истории домена, поиск флага на забытом хосте.
- **Bug bounty:** origin discovery за CDN и поиск takeover-уязвимостей.
- **Пентест:** карта инфраструктуры и связанных доменов для расширения периметра.
- **Blue team:** мониторинг собственных висячих CNAME и устаревших записей.
