## Вопрос, с которого всё начинается

Обычно разведка идёт от имени к адресу: есть домен — узнаём его IP. Но что если у тебя есть только **IP-адрес** или целый диапазон? Например, ты нашёл подсеть хостинга цели и хочешь понять, что там живёт.

Ответ даёт **обратный DNS** (reverse DNS): он отвечает на вопрос «какое имя у этого IP». Разберём его на одном диапазоне.

## Наш пример: диапазон 93.158.134.0/24

Возьмём подсеть `93.158.134.0/24` — 254 адреса. Задача: узнать, какие имена там живут и какие роли у этих хостов. Пойдём от одиночного запроса к свипу всего диапазона.

## Шаг 1: что такое PTR

Обратная зона DNS называется `in-addr.arpa` для IPv4 (и `ip6.arpa` для IPv6). Адрес `93.158.134.144` превращается в имя `144.134.158.93.in-addr.arpa` — байты идут в обратном порядке. Запись типа **PTR** связывает этот адрес с именем.

```
93.158.134.144  →  144.134.158.93.in-addr.arpa  →  mail.example.com
```

Не у каждого IP есть PTR: многие хостинги его не заводят. И это само по себе информативно — часто отсутствие обратной записи указывает на динамический или внутренний адрес.

## Шаг 2: одиночный PTR

Проверить один адрес просто — у `dig` есть флаг `-x`, который сам разворачивает адрес в обратное имя.

```bash
dig -x 93.158.134.144 +short
```

```
mail.example.com.
```

Мы получили имя `mail.example.com` — и сразу понятно, что на этом адресе почтовый сервер. `host 93.158.134.144` делает то же самое, но короче.

## Шаг 3: реверс-свип диапазона

Чтобы узнать имена во всей подсети, перебираем адреса и запрашиваем PTR. Вручную это медленно, поэтому используем `dnsx` — он опрашивает десятки потоков параллельно.

```bash
seq 1 254 | sed 's/^/93.158.134./' | dnsx -silent -ptr -resp-only
```

```
mail.example.com
vpn.example.com
db01.hosting.net
static-93-158-134-7.example.net
```

`dnsx -ptr` фильтрует пустые ответы, поэтому в выводе остаются только адреса с обратной записью. Для больших диапазонов применяют `massdns`, который держит миллионы запросов в секунду, но о нагрузке поговорим ниже.

## Шаг 4: FCrDNS — проверяем согласованность

PTR-запись может указывать на что угодно, поэтому имя нужно проверить. **FCrDNS** (forward-confirmed reverse DNS) — это проверка согласованности: если PTR говорит `mail.example.com`, то прямой запрос `dig mail.example.com A` должен вернуть тот же IP.

```bash
ip=93.158.134.144
name=$(dig +short -x $ip | sed 's/\.$//')
echo "$name -> $(dig +short $name)"
```

```
mail.example.com. -> 93.158.134.144
```

Совпадение повышает доверие к имени; расхождение — признак подделки или устаревшей записи. Почтовые серверы часто требуют FCrDNS от отправителей.

## Шаг 5: фильтруем по ролям

Из списка имён самое ценное — те, что говорят о роли хоста. Прогоняем результат через `grep`.

```bash
grep -E 'mail|smtp|vpn|git|jenkins|db|ns[0-9]' hosts.txt
```

```
mail.example.com    → почта
vpn.example.com     → удалённый доступ
db01.hosting.net    → база данных у хостинг-провайдера
```

А шаблонные имена вроде `static-93-158-134-7.example.net` — это динамический пул, обычно не цель. Так из «безымянного» диапазона появляется список серверов с ролями.

## Шаг 6: пассивный reverse DNS

Активный свип — это запросы, которые цель может заметить. Пассивные источники отдают историю соответствий IP↔имя без обращения к цели: PassiveTotal, SecurityTrails, VirusTotal, а также Censys и Shodan, которые показывают имена из сертификатов.

```bash
curl -s "https://ipinfo.io/93.158.134.144/json" | jq '{ip,hostname,org,asn}'
```

```
{
  "ip": "93.158.134.144",
  "hostname": "mail.example.com",
  "org": "Example Hosting",
  "asn": "AS64500"
}
```

Пассивный подход безопаснее и часто богаче: он показывает имена, которых уже нет в живой зоне. И помни про нагрузку — свип `/16` это 65 тысяч запросов, заметная активная разведка; ограничься `/24` или согласуй больший диапазон.

## Прямая и обратная зона: делегирование

Прямая и обратная зоны — **разные деревья DNS** и часто разные администраторы. Прямую зону `example.com` держит владелец домена, а обратную `134.158.93.in-addr.arpa` — владелец IP-диапазона, то есть провайдер или регистратор. Поэтому PTR для своего адреса клиент часто не может задать сам — только через провайдера. Отсюда практический вывод: отсутствие PTR у сервера в датацентре — норма, а не «пустой» результат.

## Чек-лист реверс-разведки диапазона

- Получить диапазон (whois/ASN), подтвердить владельца.
- Развернуть в список IP, ограничиться `/24` или согласовать больший.
- Свип PTR через `dnsx -ptr` (или `massdns` для крупных).
- Отделить имена с ролями (`mail|vpn|db|git|ns`).
- Проверить FCrDNS для важных имён.
- Обогатить пассивно (passive DNS, Censys, CT).
- Зафиксировать: IP, PTR, роль, источник, дата.

## Массовый реверс-свип и нагрузка

Для диапазонов больше `/24` используют быстрые резолверы. `massdns` держит миллионы запросов в секунду, `dnsx` — разумную параллельность.

```bash
seq 1 254 | sed 's/^/93.158.134./' > ips.txt
dnsx -l ips.txt -ptr -rl 200 -silent -resp-only > hosts.txt
```

Важно про нагрузку: свип `/16` — это 65 тысяч запросов, уже заметная активная разведка. В bug bounty проверь правила программы; в остальных случаях ограничься `/24` и пассивными источниками.

## IPv6 и обратные зоны

У IPv6-адресов тоже есть PTR, но зона `ip6.arpa` огромна, и обратный свип по ней нецелесообразен. PTR для IPv6 встречается реже, но иногда выдаёт уникальные имена, которых нет в IPv4. Для IPv6-разведки лучше работают пассивные источники — CT-логи и passive DNS.

## Компактный конвейер

Весь процесс сводится к одной цепочке команд:

```bash
seq -f "93.158.134.%g" 1 254 \
  | dnsx -silent -ptr -resp-only | sort -u \
  | tee names.txt \
  | grep -E 'mail|vpn|db|git' | httpx -silent -title -status-code
```

## Что мы теперь знаем

По-простому:

1. PTR отвечает на вопрос «какое имя у этого IP».
2. `dig -x <ip>` делает одиночный обратный запрос.
3. `dnsx -ptr` свипит весь диапазон параллельно.
4. FCrDNS проверяет, что PTR не врёт.
5. Пассивный reverse DNS даёт историю без запросов к цели.

## На что смотреть дальше

- **Не свипи огромные диапазоны.** `/16` — шумная активная разведка.
- **Не верь PTR как имени.** Подтверждай прямым запросом (FCrDNS).
- **Не забудь про IPv6.** `ip6.arpa` иногда выдаёт уникальные имена.
- **Не путай отсутствие PTR с отсутствием хоста.** Хост жив, просто без записи.
- **Учти кэш резолверов.** Публичные могут отдавать устаревший PTR.

## Разбор кейса: соседи по хостингу

Реверс-DNS (PTR) сопоставляет IP с именем. Это кажется мелочью, но именно PTR выдаёт «соседей» — другие хосты на том же блоке, которые могут быть связаны с целью. Разберём.

Начнём с одного IP: `dig -x 93.158.134.144 +short`. Ответ — имя вида `host144.provider.net`. Уже видно провайдера. Теперь реверс-свип блока: пройди по всем 256 адресам `/24` и собери PTR-имена. Получится список хостов провайдера. Среди них — почтовые серверы, панели, служебные адреса.

Следующий шаг — **FCrDNS** (forward-confirmed reverse DNS). Проверь, что прямой A-запись PTR-имени указывает обратно на тот же IP. Если да — согласованность есть, имя реальное. Если нет — это «мусорный» PTR, часто автоматически сгенерированный. Согласованные PTR ценнее: они обычно принадлежат сервисам с настроенным DNS.

Затем — **фильтрация по ролям**. Имена вроде `mail-`, `ns-`, `vpn-`, `gw-` подсказывают роль хоста. Имена с именем компании — принадлежность. Так из 256 адресов ты выбираешь 10-15 осмысленных и строишь карту хостинга.

## Мини-практика: компактный конвейер

Собери PTR для блока одной строкой:

```bash
seq 1 254 | xargs -P 20 -I{} dig -x 93.158.134.{} +short | grep -v '^$' | sort -u
```

Флаг `-P 20` ускоряет перебор, `grep -v '^$'` убирает пустые строки. Сохрани результат в файл и отсортируй по ролям. Отдельно проверь FCrDNS для каждого имени. Так ты получишь карту блока за минуту.

## Если не сработало

**PTR пусто.** Многие адреса без обратной записи — это норма. Не делай вывод «хостов нет».

**PTR автоматический.** Имена вида `static-93-158-134-144.isp.net` — генерируются провайдером, ценности почти нет. Ищи согласованные.

**Свип блокируется.** Уменьши параллелизм и добавь паузы. Резолвер может забанить за агрессивность.

**IPv6 не отвечает.** Обратные зоны IPv6 (`ip6.arpa`) делегированы по-разному. Проверяй отдельно.

## Частые вопросы

**Что такое FCrDNS и зачем он?** Проверка, что PTR и A-запись согласованы. Используется в антиспаме, но полезна и в разведке.

**Опасно ли свипать диапазон?** Умеренный реверс-свип — нормальная практика. Агрессивный брут заметен и неэтичен.

**Что даёт делегирование зоны?** По NS-записям обратной зоны видно, кто ей управляет. Иногда зона делегирована клиенту.

## Вопросы и ответы

**Что такое PTR-запись?** Обратная DNS-запись, сопоставляющая IP с именем. Она выдаёт провайдера и часто — роль хоста (`mail`, `ns`, `vpn`), что полезно для картирования блока.

**Зачем нужен FCrDNS?** Это проверка согласованности: прямой A-запись PTR-имени должна указывать обратно на тот же IP. Согласованные записи ценнее, потому что принадлежат настроенным сервисам.

**Как свипать диапазон?** Пройди по адресам блока и собери PTR-имена. Умеренный свип — нормальная практика, но агрессивный брут заметен и неэтичен, поэтому снижай параллелизм.

**Почему многие PTR пустые?** Не у всех адресов есть обратная запись — это норма, а не признак отсутствия хостов. Отсутствие PTR не означает, что сервиса нет.

**Что даёт делегирование обратной зоны?** По NS-записям видно, кто управляет зоной. Иногда зона делегирована клиенту, что указывает на его инфраструктуру и администраторов.

**Как работать с IPv6?** Обратные зоны IPv6 (`ip6.arpa`) делегируются иначе и проверяются отдельно. Не забывай про IPv6, иначе потеряешь половину поверхности.

## Куда дальше

В следующем уроке мы возьмём **иконку сайта** (favicon) и научимся искать серверы по её хэшу — приём, который находит origin за CDN и связанные проекты. А пока запомни главное: обратный DNS позволяет начать разведку с адреса, а не с домена, и превращает «пустой» диапазон в список серверов с ролями.

## Где пригодится

- **CTF:** найти хост по данному IP или имя для обратной зоны.
- **Bug bounty:** обнаружить дополнительные хосты и сервисы в диапазоне цели.
- **Пентест:** картирование подсетей и ролей серверов до сканирования портов.
- **Blue team:** проверка корректности обратных зон и выявление «чужих» записей.
