Прямой DNS отвечает на вопрос «какой IP у имени». Обратный DNS (reverse DNS, rDNS) отвечает на обратный вопрос — «какое имя у этого IP». Для разведки это способ **начать с адреса**, а не с домена: получив диапазон провайдера или подсеть, вы можете «прочесать» его и узнать, какие имена там живут.

## PTR-записи

Обратная зона называется `in-addr.arpa` для IPv4 и `ip6.arpa` для IPv6. IP `93.158.134.144` превращается в `144.134.158.93.in-addr.arpa`. Запись типа `PTR` связывает этот адрес с именем.

```bash
dig -x 93.158.134.144 +short
host 93.158.134.144
nslookup 93.158.134.144
```

Не у каждого IP есть PTR — многие хостинги его не заводят. Отсутствие PTR само по себе информативно: часто это динамические или внутренние адреса.

## Реверс-свип диапазона

Чтобы узнать имена во всей подсети, перебирают адреса и запрашивают PTR:

```bash
# быстрый свип /24 через dnsx
seq 1 254 | sed 's/^/93.158.134./' | dnsx -silent -ptr -resp-only

# то же вручную (медленно, но наглядно)
for i in $(seq 1 254); do
  dig +short -x 93.158.134.$i
done
```

`dnsx -ptr` умеет параллельно опрашивать десятки потоков и фильтровать пустые ответы. Для больших диапазонов используют `massdns` — он держит миллионы запросов в секунду.

## Что даёт PTR для разведки

- **Имена серверов**: `mail.example.com`, `vpn.example.com`, `db01.hosting.net` — сразу видно роль хоста.
- **Признаки хостинга**: PTR вида `*.your-server.de`, `*.linode.com` выдают провайдера и часто номер «соседнего» клиента.
- **Обратный маппинг ASN**: связка IP → PTR → ASN достраивает карту инфраструктуры (следующий урок про BGP).
- **Случайные имена**: `static-1-2-3-4.isp.net` — динамический пул, обычно не цель.

## Forward-confirmed reverse DNS (FCrDNS)

Проверка «обратной-прямой» согласованности: если PTR говорит `mail.example.com`, то `dig mail.example.com A` должен вернуть тот же IP. Совпадение повышает доверие к имени; расхождение — признак подделки или устаревшей записи. Почтовые серверы часто требуют FCrDNS от отправителей.

```bash
ip=93.158.134.144
name=$(dig +short -x $ip | sed 's/\.$//')
echo "$name -> $(dig +short $name)"
```

## Соседи и виртуальный хостинг

Один IP часто обслуживает десятки доменов (shared hosting). Реверс-свип находит только те, у кого есть PTR. Чтобы найти остальные, нужны reverse-IP сервисы (см. урок про исторический DNS) или сертификаты CT: `crt.sh` по IP иногда отдаёт все имена, обслуживаемые сервером.

```bash
# имена из CT по IP (через Censys)
curl -s "https://search.censys.io/api/v2/hosts/93.158.134.144" -u "$CENSYS_ID:$CENSYS_SECRET" \
  | python3 -c 'import sys,json;d=json.load(sys.stdin);print(d["result"]["names"])'
```

## Массовый реверс-свип и инструменты

Для диапазонов больше /24 используют быстрые резолверы:

```bash
# massdns: миллионы PTR-запросов
seq 1 254 | sed 's/^/93.158.134./' > ips.txt
echo "93.158.134.144.in-addr.arpa PTR" >> queries.txt
massdns -r resolvers.txt -t PTR -o S queries.txt > ptr_results.txt

# dnsx с большим списком IP
dnsx -l ips.txt -ptr -silent -resp-only
```

**Важно про нагрузку**: свип /16 — это 65k запросов; это уже активная и заметная разведка. В bug bounty проверяйте правила программы; в остальных случаях ограничьтесь /24 и пассивными источниками.

## IPv6 и обратные зоны

IPv6-адреса тоже имеют PTR, но зона `ip6.arpa` огромна. Практически:

- PTR для IPv6 встречается реже, но иногда выдаёт уникальные имена.
- Обратный IPv6-свип нецелесообразен; используйте пассивные источники (CT, passive DNS).
- Некоторые сервисы отдают только AAAA — не забывайте проверять оба семейства.

## Разобранный пример: диапазон → карта

```bash
# 1) получаем диапазон (например, из ASN цели)
curl -s "https://api.bgpview.io/asn/200350/prefixes" | jq -r '.data.ipv4_prefixes[].prefix' > p.txt

# 2) разворачиваем /24 в список IP и свипим PTR
head -1 p.txt | cut -d/ -f1 | cut -d. -f1-3 | xargs -I{} seq -f "{}."%g 1 254 > ips.txt
dnsx -l ips.txt -ptr -silent -resp-only | sort -u > hosts.txt

# 3) фильтруем по ролям
grep -E 'mail|smtp|vpn|git|jenkins|db|ns[0-9]' hosts.txt
```

Итог: из «безымянного» диапазона появляется список серверов с ролями. Дальше — HTTP-проверка (`httpx -l hosts.txt -title -status-code`) и связка с ASN/CT.

## От PTR к картированию инфраструктуры

Реверс-свип — не самоцель, а вход в картирование:

```
IP-диапазон → PTR-имена → роли (mail/vpn/db) → HTTP-проверка → технологии
```

Дальше связываете с ASN (см. osint-bgp), passive DNS (см. osint-dns-history) и CT (см. osint-cert-transparency). Так из «пустого» диапазона появляется список сервисов и их владельцев.

## Инструменты и флаги

| Инструмент | Команда | Назначение |
|---|---|---|
| dig | `dig -x IP +short` | одиночный PTR |
| host | `host IP` | быстрый PTR |
| dnsx | `dnsx -l ips.txt -ptr -resp-only` | параллельный свип |
| massdns | `massdns -t PTR -o S` | массовый свип |
| nslookup | `nslookup IP` | PTR (Windows) |
| Censys API | `hosts/<ip>` | имена из сертификатов |

## Частые ошибки

- **Свипить огромные диапазоны**: `/16` — это 65k запросов, это уже активная и шумная разведка; согласуйте с политикой.
- **Верить PTR как имени**: PTR может указывать на что угодно; подтверждайте прямым запросом (FCrDNS).
- **Забыть про IPv6**: `ip6.arpa` существует и иногда выдаёт уникальные имена, которых нет в IPv4.
- **Путать отсутствие PTR с отсутствием хоста**: хост жив, просто без обратной записи.
- **Игнорировать скорость**: `dnsx`/`massdns` в разы быстрее ручного цикла `dig`.
- **Забыть про резолверы**: публичные резолверы могут кэшировать старые PTR — используйте авторитетные.

## Что делать дальше / решение

- **Нужны имена в диапазоне** → `dnsx -ptr` по /24, при необходимости `massdns`.
- **Нужна валидация имени** → FCrDNS (PTR + прямой A).
- **Нужны все домены на IP** → reverse-IP сервисы и Censys/CT.
- **Нужна карта ролей** → фильтр `grep` по mail/vpn/db + `httpx -title`.

## Прямая и обратная зона: делегирование

Прямая и обратная зоны — **разные деревья DNS** и часто разные администраторы:

- Прямую зону `example.com` держит владелец домена.
- Обратную зону `134.158.93.in-addr.arpa` держит **владелец IP-диапазона** (провайдер/регистратор RIR).
- Поэтому PTR для своего IP клиент часто не может задать сам — только через провайдера.

Практический вывод: отсутствие PTR у клиентского сервера в датацентре — норма, а не «пустой» результат. Иногда провайдер отдаёт PTR вида `static-93-158-134-144.example.net` — это его шаблон, и по нему виден пул.

## Пассивный reverse DNS

Активный свип — это запросы. Пассивные источники отдают историю PTR без обращения к цели:

- **PassiveTotal / RiskIQ**, **SecurityTrails**, **VirusTotal** — хранят историю резолвов IP↔имя.
- **Censys/Shodan** — отдают PTR и имена из сертификатов по IP.
- **`ipinfo.io/<ip>` / `bgp.he.net`** — PTR, ASN, whois-агрегация.

```bash
curl -s "https://ipinfo.io/93.158.134.144/json" | jq '{ip,hostname,org,asn}'
```

Пассивный подход безопаснее и часто богаче: показывает имена, которых уже нет в живой зоне.

## Практические грабли: кэш, TTL и резолверы

- **Кэш резолвера**: публичный резолвер может отдавать устаревший PTR — используйте авторитетный сервер зоны или `+trace`.
- **TTL**: обратные записи меняются редко, но при переезде хостинга старый PTR живёт до истечения TTL.
- **Скорость**: `dnsx`/`massdns` быстрее ручного `dig`, но создают нагрузку; для /24 хватает `dnsx`.
- **Пустые ответы**: `NXDOMAIN` и «нет PTR» — разные вещи; логируйте оба.

## Чек-лист реверс-разведки диапазона

- [ ] Получить диапазон (whois/ASN/`osint-bgp`), подтвердить владельца.
- [ ] Развернуть в список IP, ограничиться /24 (или согласовать больший).
- [ ] Свип PTR через `dnsx -ptr` (или `massdns` для крупных).
- [ ] Отделить имена с ролями (`mail|vpn|db|git|ns`).
- [ ] Проверить FCrDNS для важных имён.
- [ ] Обогатить пассивно (passive DNS, Censys, CT) — имена без живого PTR.
- [ ] HTTP-проверка живых (`httpx -title -tech-detect`).
- [ ] Зафиксировать: IP, PTR, роль, источник, дата.

Компактный конвейер:

```bash
seq -f "93.158.134.%g" 1 254 \
  | dnsx -silent -ptr -resp-only | sort -u \
  | tee names.txt \
  | grep -E 'mail|vpn|db|git' | httpx -silent -title -status-code
```

## Автоматизация и контроль нагрузки

Реверс-свип легко автоматизируется, но именно здесь чаще всего нарушают границы:

- **`dnsx`** — дефолтная параллельность безопасна для /24; не поднимайте потоки ради /16.
- **`massdns`** — миллионы запросов в секунду; применяйте только к своим или явно разрешённым диапазонам.
- **Свои резолверы** — список публичных резолверов (`resolvers.txt`) снижает риск, что один сервер вас забанит.
- **Паузы между диапазонами** — вежливость и снижение заметности.
- **Логирование** — сохраняйте исходный IP и найденное имя: результат нужен для отчёта.

```bash
# dnsx: разумная параллельность + вывод только непустых
dnsx -l ips.txt -ptr -rl 200 -silent -resp-only > out.txt
```

Для bug bounty добавьте проверку scope: диапазон из ASN цели может включать чужие сети, сканирование которых запрещено программой.

## Типичные сценарии применения

- **Найти хост по IP** (CTF): `dig -x` → имя → открыть в браузере.
- **Картировать хостинг** (bug bounty): PTR-свип /24 → роли → httpx.
- **Проверить почтовый сервер**: FCrDNS обязателен для доверия.
- **Обнаружить динамические пулы**: шаблонные PTR (`static-…`) → не цель.
