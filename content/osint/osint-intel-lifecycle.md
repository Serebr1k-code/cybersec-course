Разведка — это не «найти что-нибудь интересное», а **управляемый процесс**, который начинается с вопроса и заканчивается решением. Без цикла вы собираете факты бесконечно и не понимаете, когда остановиться. Этот урок — методологический каркас, на который нанизываются все остальные темы категории. Он отвечает на три вопроса: что собирать, как не утонуть в данных и как превратить сырые факты в вывод, на который можно опереться.

## Зачем нужен цикл

Классический intelligence cycle — итеративный контур из шести шагов. Каждый шаг влияет на следующий, а последний замыкает петлю обратно на первый. Если хотя бы один шаг пропущен, разведка превращается в «поиск ради поиска»: данных много, решений нет.

```
Требования → Планирование → Сбор → Обработка → Анализ → Распространение
     ↑                                                          │
     └──────────────────── обратная связь ──────────────────────┘
```

Ключевая мысль: разведка обслуживает **решение**. Если факт не может изменить решение — он не является разведывательным требованием.

## Шаг 1. Требования (Requirements)

Сначала формулируем **что именно** нам нужно знать и **зачем**. В профессиональной разведке это называется PIR — Priority Intelligence Requirements.

- **PIR** (приоритетные) — вопросы, ответ на которые меняет решение. Например: «Есть ли у компании публично доступные S3-бакеты с клиентскими данными?»
- **SIR** (вторичные) — полезно, но не критично (например, список технологий сайта).
- **EEI** — Essential Elements of Information, конкретные факты, закрывающие PIR.

Правило: **вопрос должен быть проверяемым**. «Всё про компанию» — не требование. «Кто владелец домена X и какие поддомены у него в публичном DNS» — требование. Хороший PIR содержит объект, признак и критерий ответа.

## Шаг 2. Планирование (Planning & Direction)

Планирование отвечает на три вопроса: **какие источники**, **какими инструментами**, **в каком порядке**.

| Тип источника | Пример | Риск раскрытия |
|---|---|---|
| Открытые данные (публичные) | WHOIS, DNS, сайт компании | Нулевой |
| Полуоткрытые | соцсети, форумы, утечки | Низкий |
| Технические сенсоры | Shodan, сканеры | Средний (активные запросы) |
| Люди (HUMINT) | соц. инженерия | Высокий |

Составьте **collection plan** — таблицу: требование → источник → инструмент → статус → уверенность. Это ваш чек-лист и одновременно отчёт о покрытии. Порядок всегда «пассивное перед активным»: сначала исчерпайте публичные источники, только потом касайтесь цели.

## Шаг 3. Сбор (Collection)

Собирайте **с указанием источника и времени**. Любой факт без provenance (откуда взят) для аналитика бесполезен: его нельзя проверить.

Правила сбора:

- Пассивное перед активным: не касайтесь цели, пока хватает публичных данных.
- Фиксируйте всё в одном месте (заметка, база, таблица) с датой и URL.
- Скриншоты + архивные копии: страница может измениться через час.
- Не «кликайте» по подозрительным ссылкам с рабочей машины.

Пример фиксации с автоматической датой:

```bash
echo "$(date -Iseconds) | whois acme.test | $(whois acme.test | grep -i 'creation date')" >> collection.log
```

## Шаг 4. Обработка (Processing)

Сырые данные приводятся к единому виду: дедупликация, нормализация (единый формат IP/домен/дата), перевод часовых поясов, привязка к сущностям.

Инструменты: `jq` для JSON, `sort -u` для списков, `csvkit`, скрипт на Python. На выходе — структурированный набор сущностей:

```
domain: example.com
  ip: 203.0.113.10
  asn: AS12345
  subdomains: [www, api, mail]
```

Практический пример нормализации списка поддоменов:

```bash
cat subs_raw.txt | tr 'A-Z' 'a-z' | sed 's/^\*\.//' | sort -u > subs_clean.txt
wc -l subs_clean.txt
# 42 subs_clean.txt
```

## Шаг 5. Анализ (Analysis)

Анализ — это **интерпретация**, а не пересказ. Здесь вы отвечаете: «что это значит?».

Ключевые приёмы:

- **Корреляция** — связывание сущностей (email ↔ username ↔ домен).
- **Гипотеза и проверка** — сформулируйте альтернативные объяснения и отсеките их.
- **Оценка источника** — по шкале Admiralty (достоверность источника A–F, достоверность информации 1–6).
- **Таймлайн** — упорядочивание событий; часто противоречия исчезают сами.
- **Diamond Model** — четыре вершины: adversary, infrastructure, capability, victim.
- **ACH (Analysis of Competing Hypotheses)** — таблица гипотез против свидетельств; побеждает гипотеза с наименьшим числом опровержений, а не с наибольшим числом подтверждений.

## Шаг 6. Распространение и обратная связь

Результат оформляется так, чтобы его **использовал** заказчик: краткий вывод сверху (BLUF — bottom line up front), детали ниже, уровень уверенности для каждого утверждения (low / moderate / high).

Если PIR не закрыт — цикл повторяется с новым планом. Разведка никогда не «заканчивается», она заканчивается только для конкретного вопроса.

## Оценка источника по Admiralty

| Источник | Значение | Достоверность | Значение |
|---|---|---|---|
| A | Полностью надёжен | 1 | Подтверждено другими |
| B | Обычно надёжен | 2 | Вероятно правда |
| C | Довольно надёжен | 3 | Возможно правда |
| D | Не всегда надёжен | 4 | Сомнительно |
| E | Ненадёжен | 5 | Маловероятно |
| F | Достоверность неизвестна | 6 | Нельзя оценить |

Записывайте код прямо рядом с фактом: `A1`, `C3`. Это дисциплинирует и защищает от построения выводов на слухах.

## Инструменты и команды

| Задача | Инструмент |
|---|---|
| Нормализация JSON | `jq`, `python3 -m json.tool` |
| Работа с CSV | `csvkit` (`csvcut`, `csvgrep`) |
| Дедупликация | `sort -u`, `uniq` |
| Граф связей | Maltego, Gephi, Graphviz |
| Таймлайн | Excel/Sheets, `timeline` (Timesketch) |
| Заметки с provenance | Obsidian, CherryTree, Markdown + git |

Пример извлечения и дедупликации IP из JSON:

```bash
curl -s https://example.com/api/hosts | jq -r '.[].ip' | sort -u > ips.txt
```

## Разобранный пример

Требование (PIR): «Определить внешнюю поверхность домена `acme.test`».

1. Планируем: WHOIS → DNS → поддомены → TLS-сертификаты → Shodan.
2. Собираем: `whois acme.test`, `dig`, `crt.sh`, `subfinder`, `shodan`.
3. Обрабатываем: сводим все поддомены в один файл, `sort -u`.
4. Анализируем: какой хостинг, какие сервисы, есть ли dev/staging.
5. Распространяем: отчёт «внешняя поверхность = N хостов, из них M вне продакшена».
6. Обратная связь: заказчик просит детальнее по dev — новый цикл на подмножество.

## Метрики покрытия и критерий остановки

Чтобы не собирать бесконечно, задайте **критерий остановки** заранее:

- **Покрытие источников**: все источники из collection plan пройдены.
- **Насыщение**: последние N (например, 3) новых источника не дали новых сущностей.
- **Закрытие PIR**: на каждый PIR есть ответ с уровнем уверенности.

Как только все три выполнены — цикл завершается для этого требования.

## Частые ошибки

- Сбор без требований → бесконечный список, который никто не читает.
- Потеря provenance → невозможно проверить факт.
- Оценка «по ощущениям» без Admiralty → переоценка слухов.
- Активные действия на первом шаге → раскрытие и шум в логах цели.
- Смешение сбора и анализа → предвзятость (искали подтверждение гипотезы).
- Confirmation bias → собирали только то, что подтверждает любимую гипотезу.

## Справочные таблицы

| Шаг | Вход | Выход | Типичная ошибка |
|---|---|---|---|
| Требования | Задача заказчика | PIR/SIR/EEI | Размытые вопросы |
| Планирование | PIR | Collection plan | Начать с активного |
| Сбор | План | Сырые факты + источник | Потеря provenance |
| Обработка | Сырые факты | Нормализованные сущности | Дубликаты |
| Анализ | Сущности | Выводы + уверенность | Смешение с обработкой |
| Распространение | Выводы | Отчёт/решение | Без уровней уверенности |

## Уровни уверенности в формулировках

Один из главных навыков аналитика — честно называть степень уверенности. Используйте устойчивую шкалу:

- **High** — подтверждено независимыми источниками (A1/A2), сомнений почти нет.
- **Moderate** — вероятно, есть косвенные подтверждения, но не полное.
- **Low** — правдоподобно, но единичный источник или слабая связь.

В отчёте для каждого утверждения пишите уровень явно: «вероятно (moderate), что staging-домен существует — найден в CT-логе, но DNS не резолвится». Это защищает от того, что заказчик примет гипотезу за факт.

## Ведение журнала и повторяемость

Разведка должна быть **воспроизводимой**: коллега по вашим заметкам должен прийти к тем же выводам. Поэтому фиксируйте не только результат, но и **команду**:

```text
2026-10-11T14:00Z | dig +short api.acme.test | 203.0.113.20 (A) | источник: локальный resolver
2026-10-11T14:05Z | crt.sh?q=acme.test | 42 записи | источник: crt.sh
```

Такой журнал — это и audit trail, и основа для отчёта, и способ воспроизвести вывод через месяц.

## Что дальше / решение

Цикл — это рамка для всех остальных уроков категории: каждый инструмент (WHOIS, DNS, Shodan, соцсети) закрывает конкретный шаг. Дальше осваивайте **модель Diamond**, **ACH** и **таймлайн-анализ** как отдельные техники анализа, а также практикуйте ведение collection plan в реальном расследовании. Итог: разведка = вопрос → план → сбор → нормализация → интерпретация → решение, и цикл повторяется, пока требование не закрыто.

## Где пригодится

- **CTF (OSINT)**: дисциплинирует поиск — вы не «тыкаетесь», а закрываете требования по порядку.
- **Threat intelligence**: построение отчётов с уровнями уверенности.
- **Пентест / Bug bounty**: корректное планирование пассивного сбора перед активной фазой.
- **Работа**: в SOC/IR и корпоративной разведке цикл — стандарт де-факто.
