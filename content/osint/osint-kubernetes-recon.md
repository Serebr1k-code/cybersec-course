## Вопрос, с которого всё начинается

Компания переехала в Kubernetes. Наружу остались «двери»: API-сервер, агент на каждом узле (kubelet), иногда дашборд. Каждая из них по-своему рассказывает, как устроен кластер, — а иногда пускает без аутентификации.

Задача: найти открытые компоненты Kubernetes, прочитать версию и проверить, отдаются ли данные анонимно — не выполняя никаких действий в кластере.

## Наш пример: API-сервер

Держим объект `https://k8s.example.com:6443`. Порт 6443 — стандартный порт API-сервера Kubernetes. Первый вопрос: **какая версия и отвечает ли он?**

```bash
curl -s -k https://k8s.example.com:6443/version | jq .
```

```json
{"major":"1","minor":"28","gitVersion":"v1.28.2","platform":"linux/amd64"}
```

`gitVersion: v1.28.2` — точная версия. Как всегда, это гипотеза об уязвимости, а не доказательство: по версии сверяются с базами CVE, но выводов раньше времени не делают. Уже здесь видно, что API-сервер доступен извне — это само по себе находка.

## Шаг 1: проверяем анонимный доступ

Ключевой вопрос — что отдаётся без токена. Kubernetes поддерживает анонимную аутентификацию; если RBAC настроен небрежно, анонимный пользователь увидит ресурсы.

```bash
curl -s -k https://k8s.example.com:6443/api/v1/namespaces | jq -r '.items[].metadata.name'
```

```text
default
kube-system
production
```

Если запрос вернул список пространств имён — значит, анонимный доступ открыт. Мы видим, что в кластере есть `production`. Дальше можно (в авторизованном тесте) перечислить поды, сервисы, секреты — но только если это разрешено задачей.

## Шаг 2: kubelet на порту 10250

У каждого узла есть агент — kubelet, слушающий на порту 10250. Он отдаёт информацию о подах на узле:

```bash
curl -s -k https://k8s.example.com:10250/pods | jq -r '.items[].metadata.name'
```

```text
web-7d9f
```

`/pods` и `/runningpods` дают список контейнеров узла. Если kubelet доступен без аутентификации, это серьёзная ошибка конфигурации: через него можно получить доступ к логам и, в старых версиях, к выполнению команд.

## Шаг 3: etcd и дашборд

**etcd** — база, где Kubernetes хранит всё состояние, включая секреты. Он слушает на 2379. Открытый etcd — критичная находка: его `/version` отвечает без входа, а при слабой конфигурации можно читать ключи.

```bash
curl -s https://k8s.example.com:2379/version | jq -r .etcdserver
```

**Дашборд** Kubernetes — веб-панель, иногда открытая на 8001 или 8443. Он показывает кластер в удобном виде, но при неверной настройке даёт доступ к тем же данным.

## Шаг 4: границы

Мы фиксируем открытость и читаем метаданные. Мы **не создаём, не удаляем и не изменяем ресурсы**, не читаем секреты дальше подтверждения и не выполняем команды в подах. Открытый кластер — это находка для отчёта с доказательством, а не площадка для эксперимента.

## Полный прогон

```bash
# 1. версия API-сервера
curl -s -k https://k8s.example.com:6443/version | jq -r .gitVersion        # → v1.28.2
# 2. анонимный доступ
curl -s -k https://k8s.example.com:6443/api/v1/namespaces | jq -r '.items[].metadata.name'
# → default, kube-system, production
# 3. kubelet
curl -s -k https://k8s.example.com:10250/pods | jq -r '.items[].metadata.name'
# → web-7d9f
```

Непрерывно: порт → версия → анонимный доступ → пространства имён → поды → карта кластера.

## Если не сработало

**Анонимный доступ закрыт.** Это правильно настроенный кластер — фиксируй версию и закрытый доступ.
**Порт нестандартный.** API может слушать на другом порту — проверь 6443, 8443, 443.
**kubelet на localhost.** Часто он привязан к 127.0.0.1 и снаружи не виден — это норма.

## Частые ошибки

**Ошибка: считать версию уязвимостью.** Версия — вход в сверку, а не доказательство.
**Ошибка: менять ресурсы.** Любая запись — это эксплуатация и шум.
**Ошибка: читать секреты без нужды.** Подтверди доступ, не выкачивай данные.
**Ошибка: игнорировать порты.** Открытый kubelet или etcd важнее самого API.

## Справочная таблица: компоненты и порты

| Компонент | Порт | Эндпоинт | Что даёт |
|-----------|------|----------|----------|
| API-сервер | 6443 | `/version`, `/api/v1/namespaces` | версия, ресурсы |
| kubelet | 10250 | `/pods`, `/runningpods` | поды узла |
| etcd | 2379 | `/version`, `/v2/keys` | версия, ключи (если открыт) |
| dashboard | 8001/8443 | `/` | веб-панель кластера |

## Разбор кейса: от поддомена до карты кластера

Дано: домен `example.com`. Шаг первый — находим `k8s.example.com`, порт 6443 открыт, `/version` отдаёт `v1.28.2`. Шаг второй — `/api/v1/namespaces` анонимно возвращает `production`; значит, RBAC не закрыт. Шаг третий — kubelet на 10250 отдаёт `/pods`, виден под `web-7d9f`. Шаг четвёртый — проверяем etcd на 2379: закрыт. Вывод: API-сервер и kubelet открыты анонимно, в кластере есть прод. Разведчик зафиксировал находки с доказательствами и остановился.

## Рабочий воркбук: полное расследование кластера

**Этап 1. Обнаружение.** Ищи поддомены и хосты `k8s`, `kubernetes`, `api`, `dashboard`, `rancher`. Проверь порты 6443, 10250, 2379, 8001, 8443.

**Этап 2. Версия.** Для каждого открытого порта снимай версию: `/version` у API и kubelet, `/version` у etcd. Записывай дату проверки.

**Этап 3. Анонимный доступ.** Пробуй читать `/api/v1/namespaces`, `/api/v1/pods`. Если отдаётся — доступ открыт; зафиксируй, что именно видно.

**Этап 4. Kubelet.** Пробуй `/pods` и `/runningpods` на 10250. Список подов раскрывает рабочие нагрузки узла.

**Этап 5. Фиксация.** Сведи всё в отчёт: какие компоненты открыты, версии, что видно анонимно. Ничего не меняй и не читай секреты дальше подтверждения.

## Частые вопросы

**Почему открытый Kubernetes так опасен?** Потому что кластер управляет всей инфраструктурой: приложениями, секретами, сетью. Анонимный доступ к API — это доступ к карте всего.

**Что такое kubelet?** Агент на каждом узле, который запускает поды и отдаёт их статус. Его API слушает на 10250.

**Зачем проверять etcd?** etcd хранит состояние кластера, включая секреты. Открытый etcd — критичная находка.

**Можно ли читать секреты?** Только подтвердить доступ, если задача это допускает. Массовая выкачка — вне рамок разведки.

**Это законно?** Чтение открытых метаданных — да. Изменение ресурсов и чтение секретов — нет.

## Термины

**API-сервер** — центральный компонент Kubernetes, принимающий запросы.

**kubelet** — агент узла, слушающий на 10250.

**etcd** — распределённое хранилище состояния кластера.

**Namespace** — логическое разделение ресурсов (default, kube-system, production).

**RBAC** — управление доступом на основе ролей; его ошибки открывают анонимный доступ.

## Что мы теперь знаем

1. Kubernetes-компоненты слушают на известных портах.
2. `/version` даёт версию без входа.
3. Анонимный доступ к API раскрывает ресурсы кластера.
4. kubelet и etcd — отдельные поверхности риска.
5. Разведка фиксирует открытость, не меняя ресурсы.

## Три истории из практики разведки кластеров

**История первая: API без анонимного доступа, но с открытым kubelet.** Кластер `k8s.example.com` был настроен грамотно: анонимный доступ к API-серверу закрыт, `/api/v1/namespaces` отвечал `403`. Однако на том же хосте порт 10250 отдавал `/pods` без аутентификации. Разведчик увидел список подов продакшена и имена сервисов. Ошибка была в конфигурации kubelet, а не самого API: админы защитили центральный компонент и забыли про агент узла. Мораль: проверяй все компоненты, а не только самый очевидный.

**История вторая: дашборд на 8001.** Kubernetes Dashboard был опубликован на порту 8001 без авторизации. Панель в удобном виде показывала пространства имён, деплойменты и даже давала формы для действий. Формально это «просто интерфейс», но фактически — полный доступ к кластеру через браузер. Разведка зафиксировала открытый дашборд как критичную находку.

**История третья: etcd, оставленный наружу.** Иногда etcd (порт 2379) случайно публикуют вместе с API. Его `/version` отвечает анонимно, а при слабой конфигурации доступны ключи, где Kubernetes хранит всё — включая секреты сервисов. Даже без чтения ключей сам факт открытого etcd — серьёзная находка, потому что это хранилище всего состояния кластера.

Общий вывод: Kubernetes состоит из нескольких компонентов, и защита одного не защищает остальные. Разведчик обходит их по очереди — API, kubelet, etcd, dashboard — и фиксирует каждый открытый порт как отдельную находку.

## Сигнатуры компонентов и как от них защищаться

Разведчик распознаёт компоненты Kubernetes по характерным ответам. API-сервер на 6443 отвечает на `/version` JSON с полем `gitVersion`, а на `/healthz` — строкой `ok`. На анонимный запрос к `/api/v1/namespaces` защищённый кластер вернёт `403 Forbidden` с сообщением о запрете, а открытый — список пространств имён. Kubelet на 10250 отвечает на `/pods` JSON с полем `kind: PodList`; на `/healthz` — `ok`; на `/metrics` — метрики Prometheus. etcd на 2379 отдаёт `/version` с полем `etcdserver`, а `/health` — `{"health":"true"}`. Dashboard на 8001 или 8443 показывает HTML-страницу входа Kubernetes. Зная эти сигнатуры, ты за секунды отличаешь кластер от других сервисов на тех же портах.

Защита строится вокруг сетевой изоляции. Первое — API-сервер не должен быть доступен из интернета: только через VPN, bastion или приватную сеть. Второе — анонимная аутентификация должна быть выключена, а RBAC — ограничивать даже аутентифицированных пользователей. Третье — kubelet слушает только на внутреннем интерфейсе, а его API закрыт для анонимного доступа. Четвёртое — etcd доступен только управляющим узлам и обязательно с TLS-клиентской аутентификацией. Пятое — дашборд не публикуется наружу и требует входа. Понимая, как разведка находит компоненты, ты понимаешь, какие именно настройки проверять в аудите.

Отдельно стоит помнить про облачные managed-кластеры. В них провайдер (EKS, AKS, GKE) обычно закрывает управляющий API от публичного доступа по умолчанию, но иногда пользователь открывает его сам ради удобства. Kubelet в managed-кластерах недоступен снаружи. Поэтому в облаке разведка чаще находит не открытые кластеры, а утёкшие kubeconfig-файлы и сервис-аккаунт-токены в репозиториях. Это смещает фокус: если поддоменов `k8s` нет, ищи конфиги и токены в коде. Оба режима — self-hosted и managed — стоит держать в голове, потому что картина атакуемой поверхности у них разная.
