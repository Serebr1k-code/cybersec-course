Разведка начинается со сбора «сырья»: что вообще есть в открытых источниках по цели. Этот модуль объединяет две базовые ветки сбора — **поисковые операторы и дорки** (найти документы, панели, утечки) и **WHOIS/ASN** (понять, кому принадлежат домен и IP-адреса, как устроена инфраструктура). Это первые шаги любого OSINT-исследования: они дешёвые, не оставляют следов на самой цели и сразу очерчивают поверхность.

Модуль — навигатор: он показывает, что даёт каждая ветка и в каком порядке их проходить, а детали — в уроках внутри. Но навигатор — не только оглавление. Ниже разобраны сам цикл сбора, полный набор поисковых операторов, практическая работа с WHOIS/RIR и построение ASN-карты, чтобы вы могли начать собирать данные уже здесь.

| Урок | Ветка | Что даёт |
|------|-------|----------|
| [osint-search-operators](osint-search-operators) | Поиск и дорки | операторы Google/Bing/Yandex, поиск утёкших документов, панелей и файлов |

Обе ветки **пассивны**: вы обращаетесь к публичным базам (поисковик, WHOIS-сервер, BGP-коллекторы), а не к серверам цели. Именно поэтому с них и начинают — риск обнаружения нулевой, а поверхность для дальнейших шагов максимальная.

## Базовый цикл разведки: от вопроса к источнику

Любой сбор начинается не с инструмента, а с **вопроса**. Плохой вопрос: «что есть про example.com?». Хороший вопрос: «какие поддомены example.com отдают страницы вне продакшена?» или «кто владелец домена и на каком AS он хостится?». Формулировка задаёт инструмент.

Цикл выглядит так:

1. **Вопрос (PIR).** Сформулируйте, что именно нужно узнать и зачем.
2. **Источник.** Выберите публичную базу, которая на этот вопрос отвечает (поисковик, WHOIS, BGP, DNS).
3. **Запрос.** Составьте точный запрос (дорк, `whois`, DNS-запись).
4. **Артефакт.** Сохраните результат с датой и ссылкой (скриншот, дамп, хэш).
5. **Следующий вопрос.** Каждая находка порождает новый вопрос — так растёт карта.

Ключевое правило: **не «собирать всё», а идти по цепочке вопросов**. Иначе вы утонете в данных и потеряете цель.

## Поисковые операторы и дорки

Поисковый движок — это база данных по проиндексированному интернету. Операторы сужают её до нужного среза. Базовый набор Google:

| Оператор | Назначение | Пример |
|---|---|---|
| `site:` | только указанный домен | `site:example.com` |
| `inurl:` | слово в URL | `inurl:admin` |
| `intitle:` | слово в заголовке `<title>` | `intitle:"index of"` |
| `intext:` | слово в тексте страницы | `intext:"password"` |
| `filetype:` | формат файла | `filetype:pdf` |
| `cache:` | копия страницы из кэша | `cache:example.com` |
| `-` | исключить термин | `site:example.com -www` |
| `OR`/`|` | альтернатива | `site:example.com inurl:login OR inurl:signin` |
| `""` | точная фраза | `"internal use only"` |
| `..` | диапазон чисел | `site:example.com inurl:id=1..100` |

Типовые «жадные» дорки, которые сразу дают поверхность:

```text
# открытые листинги каталогов
site:example.com intitle:"index of"
# конфиги и бэкапы
site:example.com (ext:env OR ext:bak OR ext:old OR ext:sql)
# панели и входы
site:example.com (inurl:admin OR inurl:login OR intitle:"admin panel")
# документы и таблицы
site:example.com (filetype:pdf OR filetype:xlsx OR filetype:docx)
# утёкшие ключи в коде на площадках
"example.com" (filetype:env OR filetype:yml) "password"
```

Yandex использует похожий синтаксис (`site:`, `mime:`, `title:`, `url:`), а Bing — `site:`, `filetype:`, `intitle:`, `inbody:`. Для полноты прогоняйте дорк минимум по двум движкам: индексы не совпадают.

## Разобранный пример: дорк → документ → владелец

Задача: найти публичные документы организации `example.com`.

Шаг 1 — дорк по документам:

```text
site:example.com filetype:pdf
```

Выдача (сокращённо):

```text
example.com/reports/annual-2023.pdf
example.com/docs/internal-policy.pdf
example.com/vendor/contract-scan.pdf
```

Шаг 2 — имя файла `internal-policy` намекает на внутренний документ. Скачиваем и смотрим метаданные:

```bash
curl -s -o policy.pdf "https://example.com/docs/internal-policy.pdf"
exiftool policy.pdf | grep -iE 'author|creator|producer|create'
```

Вывод:

```text
Author          : Ivan Petrov
Creator         : Microsoft Word
Create Date     : 2023:04:11 09:22:13
Producer        : Acrobat Distiller
```

Шаг 3 — метаданные дали **имя автора** (`Ivan Petrov`). Ищем его в LinkedIn/GitHub → находим сотрудника и его роль. Так один дорк превращается в «человека».

## WHOIS: домен и IP

WHOIS отвечает на вопрос «кому принадлежит». Это **два разных реестра**:

- **WHOIS домена** — регистратор, даты регистрации/истечения, NS-серверы, иногда контакты (часто скрыты privacy-сервисом).
- **WHOIS IP** — организация-владелец блока (RIR: ARIN, RIPE, APNIC, LACNIC, AFRINIC), сеть (CIDR), abuse-контакт.

```bash
# домен
whois example.com | grep -iE 'registrar|creation|expiry|name server|registrant'
# IP — какой организации принадлежит и в каком диапазоне
whois 203.0.113.10 | grep -iE 'orgname|netrange|cidr|country|abuse'
```

Вывод по домену (сокращённо):

```text
Registrar: Example Registrar, Inc.
Creation Date: 2009-08-14
Registry Expiry Date: 2027-08-14
Name Server: NS1.EXAMPLE.NET
Name Server: NS2.EXAMPLE.NET
Registrant Organization: Example Inc.
```

Исторический WHOIS (когда домен менял владельца) смотрят в сервисах вроде WhoisXML/ViewDNS — свежий WHOIS часто уже перезаписан privacy-защитой, а история хранит прежние данные.

## ASN и BGP: карта инфраструктуры

ASN (Autonomous System Number) — номер автономной системы, которой принадлежит блок IP-адресов. Зная ASN, вы получаете **все префиксы организации** — а это список целей для сканирования.

```bash
# IP → ASN (Team Cymru)
whois -h whois.cymru.com " -v 203.0.113.10"

# все префиксы ASN (bgp.tools / RIPEstat)
curl -s "https://stat.ripe.net/data/announced-prefixes/data.json?resource=AS64500" \
  | jq -r '.data.prefixes[].prefix'
```

Вывод по IP (сокращённо):

```text
AS      | IP           | BGP Prefix       | CC | Registry | Allocated
64500   | 203.0.113.10 | 203.0.113.0/24   | US | arin     | 2011-06-02
```

Вывод по префиксам:

```text
203.0.113.0/24
198.51.100.0/22
192.0.2.0/24
```

Так вы получаете **полную карту IP-пространства** организации, даже если часть хостов не резолвится через DNS.

## Связка веток в один маршрут

Две ветки работают в паре:

```text
домен из дорка → WHOIS → организация-владелец
организация    → ASN   → префиксы (диапазоны IP)
префиксы       → DNS/сканеры интернета (Shodan/Censys) → сервисы
сервисы        → новые дорки (по баннерам, заголовкам) → новые домены
```

Каждый шаг — это переход «данные → новые цели». Не выбрасывайте промежуточные сущности (организация, ASN, префикс) — именно они связывают разрозненные находки в единую картину.

## Инструменты и команды

```bash
# дорки (ручной прогон через браузер либо через API поисковиков)

# WHOIS домена и IP
whois example.com
whois 203.0.113.10

# ASN по IP (Team Cymru)
whois -h whois.cymru.com " -v 203.0.113.10"

# префиксы ASN
curl -s "https://stat.ripe.net/data/announced-prefixes/data.json?resource=AS64500" | jq .

# исторический WHOIS и DNS (пассивно)
#   ViewDNS, WhoisXML, SecurityTrails, crt.sh
```

Полезные публичные базы: `bgp.tools`, `bgp.he.net`, RIPEstat, `whois.cymru.com` (ASN), ARIN/RIPE/APNIC lookup. Все они пассивны — цель не увидит ваших запросов.

## Подводные камни и частые ошибки

- **Гнаться за глубиной без плана.** Сначала общая картина (владелец, хостинг), потом детали.
- **Путать WHOIS домена и IP.** Это разные реестры и разные владельцы; смотрите оба.
- **Забывать про OPSEC.** Прямые запросы от своего имени видны цели; при необходимости используйте прокси/пассивные источники.
- **Верить одному источнику.** WHOIS бывает скрыт приватностью; сверяйте с ASN/BGP и историей.
- **Игнорировать даты.** Домен, зарегистрированный вчера, и домен 2009 года — разные сигналы доверия.
- **Считать ASN вечным.** Префиксы переезжают между AS; всегда проверяйте дату аллокации.

## Что дальше / решение

Собрав базовую картину (кто владелец, какие IP, где хостинг), переходите к специализированным веткам:

- **DNS** — поддомены, зоны, MX/TXT/SPF (см. `osint-dns`).
- **Сканеры интернета** — Shodan/Censys/FOFA по найденным префиксам.
- **Утечки и репозитории** — поиск по домену и почтовым паттернам.
- **Люди** — найденные имена/контакты из WHOIS и метаданных → соцсети.

Правило завершения этого этапа: у вас есть **владелец, диапазоны IP и хотя бы один живой сервис**. Если нет — уточняйте вопрос и повторяйте цикл, прежде чем уходить глубже.

## Рабочая тетрадь разведчика

Чтобы сбор не превращался в хаос, ведите единый журнал. Минимальный набор колонок:

| Поле | Что писать | Пример |
|---|---|---|
| Цель | домен/IP/организация | `example.com` |
| Вопрос | что хотели узнать | «кто владелец» |
| Источник | инструмент/база | WHOIS, RIPE |
| Результат | суть находки | «Example Inc., AS64500» |
| Уверенность | low/mod/high | high |
| Дата | UTC | 2026-10-11 |
| Артефакт | ссылка/хэш | `whois.txt`, sha256… |

Журнал решает две задачи: (1) воспроизводимость — любой коллега повторит ваш путь; (2) контроль пробелов — видно, какие ветки вы ещё не открывали. Без журнала через час работы вы не вспомните, откуда взялся тот или иной IP.

## Пассивность и OPSEC на этом этапе

Обе ветки модуля пассивны, но это не значит «безопасно по умолчанию». Нюансы:

- **Поисковики** видят ваш запрос и IP; чувствительные дорки (по внутренним именам) лучше прогонять через выделенный браузер/прокси.
- **WHOIS** прямого запроса к цели не делает, но регистраторы логируют обращения.
- **Публичные веб-сервисы** (ViewDNS, RIPE) фиксируют, какие домены вы ищете — это тоже утечка интереса.
- **Скачивание артефактов** с сервера цели (PDF, страницы) — уже активный контакт: сервер видит ваш IP в логах.

Правило: чем ближе шаг к серверам цели, тем важнее прокси и пассивные зеркала (кэш, Wayback, CT-логи).

## Где пригодится

- **CTF (OSINT):** быстро найти скрытую страницу, документ или упоминание по операторам и WHOIS.
- **Bug bounty:** дорки вскрывают панели, конфиги и утечки; WHOIS/ASN очерчивают scope и инфраструктуру.
- **Пентест:** карта владельцев и диапазонов IP — основа для дальнейшей разведки и приоритизации.
- **Работа (Threat Intel):** атрибуция инфраструктуры и поиск публичных артефактов по цели.
