## Вопрос, с которого всё начинается

В прошлом уроке мы вытащили из одной строки `example.com` владельца, IP и поддомены. Но каждый ответ рождал новый вопрос: какие ещё документы есть про этот домен? Кому принадлежит найденный IP? Где хостится вся организация, а не только главный сайт?

Отвечать на такое наугад — плохой план. Нужен **системный сбор**: повторяемый процесс «вопрос → источник → запрос → артефакт → новый вопрос». В этом уроке мы прогоним его на том же домене `example.com` и пройдём по двум базовым веткам: **поисковые операторы (дорки)** и **реестры WHOIS/ASN**.

## Наш пример: один домен и один вопрос

Держим в голове объект — домен `example.com`. Первый осмысленный вопрос: **кто им владеет и какие документы организация выложила в открытый доступ?**

Начнём с владельца. Раньше для этого шли в `whois`, но сегодня проще и надёжнее использовать **RDAP** — это «новый WHOIS»: тот же реестр, но отдаёт структурированный JSON вместо текста. JSON удобно фильтровать и складывать в таблицу.

## Шаг 1: владелец через RDAP

```
$ curl -s https://rdap.verisign.com/com/v1/domain/example.com | jq '{ldhName,status,events}'
{
  "ldhName": "EXAMPLE.COM",
  "status": [
    "client delete prohibited",
    "client transfer prohibited",
    "client update prohibited"
  ],
  "events": [
    { "eventAction": "registration", "eventDate": "1995-08-14T04:00:00Z" },
    { "eventAction": "expiration",   "eventDate": "2027-08-13T04:00:00Z" }
  ]
}
```

Читаем: домен называется `EXAMPLE.COM`, создан в 1995 году, истекает в 2027. Три статуса `client * prohibited` — это «замок» от регистратора: домен нельзя удалить или перенести без снятия запрета.

`jq` — утилита для разбора JSON. Выражение `{ldhName,status,events}` означает «показать только эти три поля». Без `jq` ответ был бы длинной простыней; с ним — только нужное.

Для реальной цели здесь были бы **registrant-контакты**, часто с пометкой `REDACTED FOR PRIVACY`. Это нормально — не застревайте, владельца добьём через ASN.

## Шаг 2: дорк — ищем документы

Второй вопрос: что организация выложила публично. Для этого используем **операторы поиска**. Оператор — слово с двоеточием, которое сужает выдачу: `site:` (только этот сайт), `filetype:` (формат файла), `inurl:` (слово в адресе), `intitle:` (слово в заголовке).

Запрос из операторов называется **дорком**. Составим дорк «покажи PDF на этом домене»:

```
site:example.com filetype:pdf
```

Что мы получили бы у реальной цели — список документов. Типовой «жадный» дорк-набор, который сразу очерчивает поверхность:

```text
site:example.com intitle:"index of"                       # открытые листинги каталогов
site:example.com (ext:env OR ext:bak OR ext:sql)          # конфиги и бэкапы
site:example.com (inurl:admin OR inurl:login)             # панели входа
site:example.com (filetype:pdf OR filetype:xlsx)          # документы и таблицы
"example.com" (filetype:env OR filetype:yml) "password"   # утёкшие ключи
```

Дорки пассивны: вы спрашиваете поисковик, а не сервер цели. Поэтому с них и начинают — цель не видит вас в логах.

Как читать выдачу. Не смотрите на первые десять ссылок — смотрите на **закономерности**. Если в выдаче мелькают `dev.`, `staging.`, `jenkins.`, значит у организации есть непубличные среды, которые часто защищены слабее продакшена. Если попадаются `.pdf` с пометкой `internal`, — это документы, которые не собирались показывать наружу. Каждый такой факт — гипотеза, которую дальше проверяют.

## Шаг 3: от домена к IP, от IP к организации

Теперь инфраструктура. Мы уже знаем IP сайта. Спросим у реестра, **кому принадлежит блок адресов**, в который входит этот IP:

```
$ curl -s https://rdap.org/ip/8.8.8.8 -L | jq '{handle,name,startAddress,endAddress}'
{
  "handle": "NET-8-8-8-0-2",
  "name": "GOGL",
  "startAddress": "8.8.8.0",
  "endAddress": "8.8.8.255"
}
```

Это **WHOIS для IP** (в терминах RDAP — IP-запрос). Он отвечает не «кто владелец домена», а «какая организация держит диапазон адресов»: тут — блок `8.8.8.0/24` на организацию `GOGL`. Домен и IP — **разные реестры**, их владельцы не обязаны совпадать.

## Шаг 4: ASN — карта всего IP-пространства

IP-блоки объединены в **автономные системы** — их обозначают номером **ASN**. Зная ASN организации, вы получаете **все её префиксы** (диапазоны адресов), а не один IP.

Получив организацию из шага 3, смотрим её префиксы через публичные сервисы (`bgp.tools`, RIPEstat). Например, REST-запрос к RIPEstat:

```
$ curl -s "https://stat.ripe.net/data/announced-prefixes/data.json?resource=AS15169" \
  | jq -r '.data.prefixes[].prefix'
8.8.4.0/24
8.8.8.0/24
...
```

Так появляется список диапазонов — целей для дальнейшей (уже активной) разведки. Даже если часть хостов не резолвится через DNS, они есть в ASN.

## Полный прогон: от вопроса до карты

Соберём весь маршрут на одном вопросе — «какая инфраструктура у организации за `example.com`?»:

1. Дорк `site:example.com` даёт список поддоменов и документов в индексе поисковика.
2. RDAP по домену отдаёт дату регистрации и статусы.
3. RDAP по IP показывает организацию-владельца блока адресов.
4. ASN этой организации — список всех её префиксов.
5. Каждый префикс — вход для сканеров интернета (Shodan/Censys), которые перечислят сервисы.

Результат — не одна ссылка, а таблица, которую можно продолжать: организация, ASN, префиксы, сервисы. Именно это отличает «погуглил» от «провёл сбор». И каждый шаг оставляет артефакт — JSON-ответ, список префиксов, — который ложится в журнал.

## Связка веток в один маршрут

Две ветки работают в паре, и это главная мысль урока:

```text
домен из дорка → RDAP → организация-владелец
организация    → ASN  → префиксы (диапазоны IP)
префиксы       → сканеры интернета (Shodan/Censys) → сервисы
сервисы        → новые дорки (по баннерам) → новые домены
```

Каждый шаг — переход «данные → новые цели». Не выбрасывайте промежуточные сущности (организация, ASN, префикс): именно они связывают разрозненные находки в единую картину.

## Рабочая тетрадь разведчика

Чтобы сбор не превращался в хаос, ведите журнал. Минимальные колонки: цель, вопрос, источник, результат, уверенность, дата, артефакт (ссылка или хэш). Журнал даёт две вещи: **воспроизводимость** (коллега повторит ваш путь) и **контроль пробелов** (видно, какие ветки вы ещё не открывали). Без него через час работы вы не вспомните, откуда взялся тот или иной IP.

## Что мы теперь знаем

По-простому:

1. **Дорк** — запрос из операторов (`site:`, `filetype:`), пассивный и дешёвый.
2. **RDAP** заменяет текстовый WHOIS и отдаёт JSON: владелец домена и владелец IP — разные реестры.
3. **ASN** превращает один IP в список всех диапазонов организации.
4. **Журнал** превращает разрозненные находки в воспроизводимый маршрут.

## На что смотреть дальше

- **Сверяйте два движка.** Индексы Google и Яндекс/Bing не совпадают — один дорк по двум поисковикам даёт разные документы.
- **Не путайте WHOIS домена и IP.** Это разные владельцы и разные базы.
- **Помните про историю.** Текущий RDAP мог быть перезаписан privacy-сервисом; исторический WHOIS и архивы хранят прежние данные.
- **Считайте даты.** Домен 1995 года и домен, зарегистрированный вчера, — разные сигналы доверия.

## Куда дальше

Дальше мы разберём две ветки подробно: **поисковые операторы и дорки** (как строить сложные запросы и не утонуть в выдаче) и **WHOIS/ASN** (как из одного IP вырастить полную карту адресов). А пока главное запомни: сбор — это маршрут «вопрос → источник → новый вопрос», а не бесконечный список ссылок.

## Где пригодится

- **CTF (OSINT):** быстро найти скрытую страницу, документ или упоминание по операторам и WHOIS.
- **Bug bounty:** дорки вскрывают панели, конфиги и утечки; WHOIS/ASN очерчивают scope и инфраструктуру.
- **Пентест:** карта владельцев и диапазонов IP — основа для дальнейшей разведки.
- **Threat Intel:** атрибуция инфраструктуры и поиск публичных артефактов по цели.
