## Вопрос, с которого всё начинается

Сайт `www.example.com` закрыт Cloudflare, и настоящий IP сервера скрыт. Новичок пробует `ping` и `dig` — и получает адреса Cloudflare, а не origin.

Но есть слой, который почти каждый сайт обязан иметь и который выдаёт лишнее: **TLS**. Из одного соединения извлекаются имена, удостоверяющий центр и даже отпечаток стека. Разберём это на одном домене.

## Наш пример: www.example.com за CDN

У нас один объект — `www.example.com`. Введём термины. **TLS** (Transport Layer Security) — протокол шифрования трафика. **CDN** (content delivery network) — сеть раздачи контента, которая прячет настоящий сервер. **Origin** — тот самый настоящий сервер за CDN.

## Шаг 1: подтверждаем, что это CDN

Смотрим заголовки ответа:

```bash
curl -sSI https://www.example.com | grep -i 'server\|cf-ray'
```

```
server: cloudflare
cf-ray: 8a1b2c3d4e5f-LHR
```

Заголовок `server: cloudflare` и `cf-ray` — признаки Cloudflare. Значит, IP из DNS принадлежит CDN, а не серверу.

## Шаг 2: читаем сертификат

**Сертификат** — это удостоверение сервера, выданное удостоверяющим центром (CA). В нём есть список имён, на которые он выдан. Смотрим:

```bash
echo | openssl s_client -connect www.example.com:443 -servername www.example.com 2>/dev/null \
  | openssl x509 -noout -subject -issuer -dates -ext subjectAltName
```

```
subject=CN = example.com
issuer=C = US, O = Let's Encrypt, CN = R3
notBefore=Sep 10 00:00:00 2026 GMT
notAfter=Dec  9 23:59:59 2026 GMT
X509v3 Subject Alternative Name:
    DNS:www.example.com, DNS:example.com, DNS:origin.example.com
```

Ключевая строка — **SAN** (Subject Alternative Name): список всех доменов сертификата. Здесь светится `origin.example.com` — прямой кандидат на настоящий сервер.

Важный флаг — `-servername`. Он передаёт **SNI** (Server Name Indication) — имя сайта ещё до установки шифрования. Без SNI сервер может отдать сертификат по умолчанию, и вывод будет неверным.

## Шаг 3: проверяем кандидата

Проверим, куда указывает найденное имя:

```bash
dig +short origin.example.com
```

```
203.0.113.42
```

Адрес `203.0.113.42` не входит в диапазоны Cloudflare. Теперь попробуем обратиться к нему с заголовком целевого домена:

```bash
curl -sSI https://origin.example.com -H 'Host: www.example.com' | head -1
```

```
HTTP/1.1 200 OK
```

Origin найден: сервер отвечает по имени цели с адреса, не принадлежащего CDN. Это классический обход CDN через утечку в SAN.

## Шаг 4: смотрим цепочку сертификатов

Сервер отдаёт не один сертификат, а цепочку до корневого. Она показывает, кто выпустил сертификат:

```bash
echo | openssl s_client -connect www.example.com:443 -servername www.example.com -showcerts 2>/dev/null | grep -E 's:|i:'
```

```
 0 s:CN = example.com
   i:C = US, O = Let's Encrypt, CN = R3
 1 s:C = US, O = Let's Encrypt, CN = R3
   i:C = US, O = Internet Security Research Group, CN = ISRG Root X1
```

Цепочка ведёт к Let's Encrypt — значит, сертификат, скорее всего, выпущен автоматически (certbot). А вот цепочка к внутреннему CA вида `CN=Corp-Enterprise-CA` — сильная находка: это признак корпоративного периметра.

## Шаг 5: JA3 и JA4 — отпечаток стека

Когда клиент начинает TLS-соединение, он в сообщении `ClientHello` перечисляет версию, наборы шифров (**cipher suites**) и расширения. Их состав и порядок зависят от библиотеки (OpenSSL, BoringSSL, Go crypto). Хэш от этой комбинации — это **JA3**, отпечаток TLS-стека.

Отпечаток клиента видно из перехваченного трафика:

```bash
tshark -r capture.pcap -T fields -e tls.handshake.ja3 -Y 'tls.handshake.type==1'
```

```
cd08e31494f9531f560d64c695473da9
```

Что с ним делать:

- **Искать в базах.** Серверные JA3 индексируются (Shodan показывает `ssl.ja3s`). Один и тот же отпечаток связывает хосты одного стека.
- **Определять ПО.** У известных ботов и малвари опубликованы характерные JA3.
- **Различать origin.** У настоящего сервера часто «голый» стек, отличный от CDN-прослойки.

Современная версия — **JA4**: она учитывает больше полей, версию TLS и ALPN, а также устойчива к рандомизации порядка (GREASE), которую используют для сокрытия отпечатка.

## Шаг 6: коррелируем хосты по TLS

Одинаковый отпечаток стека и похожие сертификаты связывают хосты, формально стоящие на разных доменах:

```bash
for h in a.example.com b.example.net c.example.org; do
  echo "== $h =="
  echo | openssl s_client -connect $h:443 -servername $h 2>/dev/null \
    | openssl x509 -noout -issuer -serial 2>/dev/null
done
```

Если совпадают `issuer` и `serial`, вероятно, это один сервер или один шаблон выпуска. Ещё надёжнее — совпадение отпечатка публичного ключа: он одинаков, даже если сертификат перевыпущен.

## Частые ошибки

- **Забыть `-servername` (SNI).** Без него сервер отдаёт дефолтный сертификат, и вывод становится неверным.
- **Считать SAN исчерпывающим.** Wildcard `*.example.com` скрывает конкретные имена — смотрите CT-логи.
- **Путать серверный и клиентский JA3.** Это разные отпечатки: клиентский видно только из перехваченного трафика.
- **Игнорировать срок действия.** Просроченный сертификат — сигнал заброшенного или теневого хоста.
- **Доверять самоподписанным как «цели».** На публичном IP это часто админка, но иногда и honeypot.

## Что мы теперь знаем

- TLS выдаёт имена (SAN), удостоверяющий центр и срок действия сертификата.
- SAN часто содержит origin-имя, которое обходит CDN.
- Без флага `-servername` (SNI) вывод может быть неверным.
- JA3 и JA4 — отпечатки TLS-стека, по ним коррелируют хосты и опознают клиентов.
- Цепочка к внутреннему CA — признак корпоративного периметра.

## На что смотреть дальше

Разберись с **Certificate Transparency** (`crt.sh`): там хранятся исторические сертификаты, включая имена, которых уже нет в живом SAN. Изучи дополнительные методы поиска origin — исторический DNS, заголовок `Received` в почте, поддомены вроде `direct.` и `ftp.`, которые часто вне CDN. И проверь гигиену TLS через `testssl.sh`.

## Шаг 7: вытаскиваем сертификат напрямую через openssl

Когда `curl`/`httpx` показывают только заголовки, сертификат достают утилитой `openssl s_client`. Она устанавливает TLS-соединение и отдаёт всю цепочку:

```
$ echo | openssl s_client -connect example.com:443 -servername example.com 2>/dev/null \
    | openssl x509 -noout -subject -issuer -dates -ext subjectAltName
subject=CN=example.com
issuer=C=US, O=SSL Corporation, CN=Cloudflare TLS Issuing ECC CA 3
notBefore=Sep 26 22:49:11 2026 GMT
notAfter=Dec 25 22:56:35 2026 GMT
X509v3 Subject Alternative Name:
    DNS:example.com, DNS:*.example.com
```

Читаем: `subject` — на кого выдан, `issuer` — кто подписал (здесь промежуточный CA Cloudflare). `subjectAltName` перечисляет все имена, на которые сертификат действителен: `example.com` и wildcard `*.example.com`. Это готовый список хостов за одним сертификатом — по нему и строят корреляцию.

## Справочник: поля сертификата и TLS-отпечатки

| Поле / параметр | Что показывает |
|---|---|
| `subject CN` | основное имя (часто давно устарело) |
| `issuer` | удостоверяющий центр (ACME Let's Encrypt, Cloudflare, DigiCert) |
| `subjectAltName` | все имена, на которые выдан сертификат |
| `notBefore`/`notAfter` | срок действия (новые даты = свежий авто-сертификат) |
| серийный номер | уникален, помогает связать копии |
| JA3 / JA4 | отпечаток клиента TLS (набора шифров, расширений) |
| шифрнабор | набор согласованных алгоритмов |

`JA3`/`JA4` — это хэш параметров TLS-рукопожатия. Один и тот же инструмент (например, `curl` или `nmap`) даёт стабильный отпечаток, поэтому по нему отличают автоматический сканер от браузера.

## Если не сработало

- **Сертификат wildcard.** Имена поддоменов из него не вытащить — нужен CT-лог (crt.sh), где видна история выдачи.
- **Самоподписанный сертификат.** `issuer == subject` — значит, доверия нет, но это тоже признак: часто так делают внутренние сервисы, случайно попавшие в интернет.
- **Сертификат просрочен.** Не спеши с выводом: сервис может работать по старому конфигу, а актуальный сертификат лежит на другом хосте.
- **`openssl` не подключается.** Проверь, не блокирует ли исходящие соединения прокси или файрвол; для HTTP-хостов сертификат виден и через `curl -vI`.

## Мини-практика: ищем origin за CDN

Типовая задача — сайт за Cloudflare, а нужно найти реальный сервер (origin). Сертификат и отпечаток помогают:

1. **Собери SAN из сертификата.** Имена из `subjectAltName` могут содержать внутренние хосты (`origin.example.com`), случайно попавшие в публичный сертификат.
2. **Сравни JA3/JA4.** Если у двух IP одинаковый отпечаток TLS-стека, вероятно, это один сервис — реальный и замаскированный.
3. **Смотри цепочку.** Промежуточный CA и серийный номер уникальны: тот же сертификат на «сером» IP — сильный признак origin.
4. **Проверь кандидата.** `curl -k --resolve example.com:443:<IP>` покажет, отдаёт ли найденный IP тот же контент.
5. **Зафиксируй.** Пара «IP + совпавший сертификат» и есть доказательство.

Так из «сайт за CDN» получается конкретный IP, к которому можно обращаться напрямую.

## Шпаргалка: что смотреть в сертификате

- `subjectAltName` — все хосты на одном сертификате (зацепка для pivot).
- `issuer` — кто выдал; ACME/Let's Encrypt значит авто-выпуск.
- `notBefore` — свежая дата = сертификат только что перевыпустили (часто после смены хостинга).
- серийный номер — совпал у двух IP → это один и тот же сервис.
- JA3/JA4 — отпечаток стека; одинаковый у сканера и сервиса связывает их.

## Куда дальше

Мы научились читать TLS и находить origin за CDN. В следующем уроке — **Shodan-дорки**: соберём продвинутые запросы по заголовкам, портам и favicon, чтобы находить панели и открытые сервисы. А пока главное запомни: TLS — это не только шифрование, но и удостоверение, выданное серверу, которое он не может скрыть.

## Где пригодится

- **CTF (OSINT):** в SAN или истории сертификата спрятан нужный поддомен.
- **Bug bounty:** обход CDN и поиск origin для теста защиты.
- **Threat intelligence:** идентификация клиентского ПО по JA3, поиск C2.
- **Пентест:** корреляция хостов одной инфраструктуры по TLS-стеку.
- **Blue team:** инвентаризация сертификатов и поиск теневых или просроченных.
