## Вопрос, с которого всё начинается

Компания `example.com` хранит файлы в облаке — S3, Azure Blob или Google Cloud Storage. Иногда такие **бакеты** (хранилища) остаются открытыми для всех, и внутри оказываются бэкапы, конфиги и дампы.

Как их найти, если прямых ссылок нет? Ответ в том, что имена бакетов **предсказуемы**: чаще всего это название компании плюс осмысленный суффикс. Разберём поиск на примере одного бренда.

## Наш пример: компания example.com

Работаем с одним объектом — брендом `example`. Задача: найти его облачные бакеты и корректно проверить доступ. Ничего не скачиваем и не меняем — только смотрим коды ответов и листинг.

## Шаг 1: ищем имена бакетов в открытых данных

Первое — понять, как компания называет свои бакеты. Их URL часто «утекают» в исходники сайта, конфиги и мобильные приложения.

```bash
curl -s https://example.com/app.js | grep -Eo 'https?://[a-z0-9.-]+\.(s3[.-][a-z0-9-]*\.amazonaws\.com|blob\.core\.windows\.net|storage\.googleapis\.com)[^"'\'' ]*'
```

```
https://example-static.s3.amazonaws.com/
https://example-assets.s3.eu-west-1.amazonaws.com/
```

Дополняем поисковыми операторами и архивами URL:

```text
site:s3.amazonaws.com "example"
site:blob.core.windows.net "example"
inurl:amazonaws.com example.com
```

```bash
gau example.com | grep -Eo 'https?://[^ ]*(s3|blob\.core|googleapis)[^ ]*'
```

Теперь мы знаем шаблон: `example-<что-то>`.

## Шаг 2: генерируем кандидатов по шаблону

Зная шаблон, генерируем кандидатов из бренда и типичных суффиксов.

```bash
for suffix in assets backup static dev prod media uploads logs data; do
  echo "example-$suffix"
done
```

```
example-assets
example-backup
example-static
example-dev
example-prod
example-media
example-uploads
example-logs
example-data
```

Предсказуемость — именно то, что делает облако «дешёвым» источником: не нужно сканировать порты, достаточно перебрать имена.

## Шаг 3: проверяем S3 по кодам ответов

Для каждого кандидата делаем запрос к листингу объектов и смотрим код ответа.

```bash
curl -s "https://example-assets.s3.amazonaws.com/?list-type=2" | head
```

```
<?xml version="1.0" encoding="UTF-8"?>
<ListBucketResult>...</ListBucketResult>
```

Коды ответов говорят всё:

- `200` + XML `<ListBucketResult>` → **публичный листинг**.
- `403 AccessDenied` → бакет есть, но закрыт.
- `404 NoSuchBucket` → не существует.

Запомни: `403` — это НЕ отсутствие. Бакет существует, просто закрыт, и это тоже информация о структуре.

## Шаг 4: Azure Blob и GCS

S3 — не единственный провайдер. Та же логика работает для Azure и Google Cloud.

```bash
curl -s "https://example.blob.core.windows.net/?comp=list"            # Azure: контейнеры
curl -s "https://storage.googleapis.com/example-assets"                # GCS
curl -s "https://storage.googleapis.com/storage/v1/b/example-assets/o" # GCS JSON API
```

У Azure признак публичности — `200` с тегом `EnumerationResults`, у GCS — XML или JSON листинг. Для масштаба используют `cloud_enum`, `S3Scanner`, `GCPBucketBrute`, `MicroBurst`.

## Шаг 5: что искать внутри

Если бакет открыт на чтение, самое ценное — служебные файлы:

- `backup*.zip`, `*.sql`, `*.env`, `credentials.*`;
- выгрузки БД, дампы, логи;
- исходники с картами (`*.map`, `*.js`);
- `terraform.tfstate` — часто содержит секреты и внутреннюю топологию.

```bash
curl -s "https://example-assets.s3.amazonaws.com/?list-type=2" | grep -oE '<Key>[^<]+</Key>'
```

```
<Key>backup/2023-11.zip</Key>
<Key>terraform.tfstate</Key>
```

Имена файлов часто раскрывают структуру внутренних систем — это уже карта для дальнейшей разведки.

## Шаг 6: фиксируем без вреда

Открытый бакет — это находка, а не «поле для грабежа». Правила простые:

1. **Зафиксируй** имя, права (read/write), первые ключи листинга, источник ссылки.
2. **Не скачивай** весь объём — только доказательство (листинг, пара образцов).
3. **Не удаляй и не изменяй** ничего.
4. **Сообщи** владельцу через программу или контакт из `security.txt`.
5. Для **записи** — только пробный PUT с немедленным DELETE и явным разрешением.

```text
Вывод: example-assets (S3, eu-west-1), read=public, write=403,
  ключи: backup/2023-11.zip, terraform.tfstate.
Источник: ссылка в app.js.
```

## Автоматизация перебора имён

Ручная проверка сотен имён не масштабируется, поэтому используют инструменты:

- **cloud_enum** — перебор S3, Azure и GCS по словарю и шаблонам компании.
- **S3Scanner** — находит открытые на чтение и запись бакеты.
- **GCPBucketBrute** — GCS-бакеты.
- **MicroBurst** — Azure (blob, ключи, подписки).

```bash
cloud_enum -k example -k examplecorp --disable-azure
s3scanner -bucket-file names.txt -enumerate
```

## IAM-ключи и секреты внутри бакетов

Открытый на чтение бакет — это ещё не доступ, но внутри часто лежат **ключи**, и вот они опасны. Что искать: AWS Access Key ID (начинается с `AKIA` или `ASIA`) вместе с `aws_secret_access_key`; Google service-account JSON (`"type": "service_account"`, поле `private_key`); Azure connection string (`AccountKey=...`); файлы `.env`, `terraform.tfstate`, `id_rsa`. Найдя такой ключ, **не используй** его — это выход за рамки находки и часто нарушение закона. Правильное действие: зафиксировать факт утечки (путь, префикс ключа, время) и передать владельцу.

## Другие облачные хранилища

S3, Azure и GCS — не единственные цели. **Firebase** хранит файлы в бакетах `project-id.appspot.com`, а Realtime Database — в `project-id.firebaseio.com` (проверяется запросом `/.json`). **DigitalOcean Spaces** и **Backblaze B2** имеют свои форматы URL, и `cloud_enum` умеет их проверять. Правило одно: если сервис даёт предсказуемое имя из бренда — он входит в словарь перебора.

## Что делать с находкой

Открытый бакет — это находка, а не поле для грабежа:

1. **Зафиксируй** имя, права (read/write), первые ключи листинга, источник.
2. **Не скачивай** весь объём — только доказательство.
3. **Не удаляй и не изменяй** ничего.
4. **Сообщи** владельцу через программу или контакт из `security.txt`.
5. Для **записи** — только пробный PUT с немедленным DELETE и явным разрешением.

Так же работает связь с другими находками: бакет из JS связывается с доменом, имя с `dev`/`staging` означает отдельную поверхность, а `terraform.tfstate` раскрывает имена VPC, ролей и БД — готовую карту облачной инфраструктуры.

## Что мы теперь знаем

По-простому:

1. Имена бакетов предсказуемы: бренд плюс суффикс.
2. URL бакетов утекают в JS, конфиги и архивы URL.
3. Код `200` — листинг, `403` — закрыт, `404` — нет.
4. Azure и GCS проверяются аналогично S3.
5. Открытый бакет — фиксируем, но не грабим.

## На что смотреть дальше

- **Не проверяй запись без разрешения.** Это вред и юридический риск.
- **Не считай `403` отсутствием.** Бакет есть, просто закрыт.
- **Не забудь про регион.** `s3.<region>.amazonaws.com` даёт другой результат.
- **Не игнорируй Azure и GCS.** Не только S3 бывает открыт.
- **Ищи ключи внутри.** `AKIA...`, service-account JSON, `.env` — критическая находка.

## Разбор кейса: публичный бакет с бэкапами

Облачные хранилища — частый источник утечек, потому что настраивать права доступа легко и ошибиться тоже легко. Разберём путь к публичному бакету.

Первый шаг — **сгенерировать имена**. Имя S3-бакета глобально уникально, поэтому его угадывают по шаблонам: `example`, `example-backup`, `example-dev`, `example-logs`, `example-uploads`. Компании часто используют единый нейминг. Второй шаг — **проверить по кодам ответов**. Запрос `curl -s -o /dev/null -w "%{http_code}" https://<bucket>.s3.amazonaws.com/` вернёт `200` (публичный листинг), `403` (существует, но закрыт) или `404` (не существует). Код `403` тоже ценен: бакет существует, просто закрыт.

Третий шаг — **посмотреть содержимое**. Если листинг открыт, ты увидишь список файлов. Часто там бэкапы (`backup.sql`), конфиги (`config.json`), логи. Четвёртый шаг — **не скачивать всё**. Достаточно зафиксировать факт публичного доступа: скриншот листинга, HTTP-код, дату. Скачивание бэкапов — это уже выгрузка данных, что выходит за рамки разведки.

Azure Blob и GCS работают похоже, но с другими шаблонами URL и другими кодами. Проверяй их так же системно.

## Если не сработало

**Все бакеты возвращают 403.** Возможно, имена неверные или листинг закрыт. Собери больше кандидатов из открытых источников (код, JS, документация).

**404 на все варианты.** Нейминг нестандартный. Ищи имена в JS-бандлах и в конфигах на GitHub.

**Слишком много кандидатов.** Ограничь перебор релевантным словарём и не перегружай сервис.

**Бакет найден, но пустой.** Это всё ещё находка: имя занято, права настроены.

## Частые вопросы

**Что такое листинг бакета?** Разрешение видеть список объектов. Само по себе это уже утечка: видны имена файлов.

**Как проверить права, не скачивая?** По коду ответа на `HEAD`-запрос к объекту. `200` — объект публичен, `403` — закрыт.

**Зачем искать IAM-ключи в бакете?** Иногда в бэкапах лежат ключи доступа. Их наличие — критическая находка, но использовать их нельзя.

## Правовые границы

Публично доступный бакет — открытые данные, но скачивание содержимого и использование ключей — уже выход за рамки. Фиксируй факт, сообщай владельцу, не выгружай. Это и этично, и безопасно.

## Вопросы и ответы

**Почему облачные хранилища так часто утекают?** Права доступа настраивать легко, и ошибка (публичный бакет) встречается постоянно. Имя бакета глобально уникально, поэтому его можно угадать по шаблону и проверить.

**Как понять, что бакет существует?** По коду ответа: `200` — публичный листинг, `403` — существует, но закрыт, `404` — нет. Код `403` тоже ценен: он подтверждает, что имя занято и права настроены.

**Что делать с публичным листингом?** Зафиксировать факт: скриншот, код ответа, дату. Не скачивать содержимое — это уже выгрузка данных, выходящая за рамки разведки.

**Где искать имена бакетов?** В JS-бандлах, конфигах на GitHub, документации и по шаблонам компании (`example-backup`, `example-dev`). Часто один нейминг используется во всех проектах.

**Чем отличаются S3, Azure Blob и GCS?** Разными форматами URL, кодами ошибок и правами. Логика проверки похожа, но детали (например, параметры аутентификации) разные, поэтому шаблоны нужно адаптировать.

**Что делать при находке?** Сообщить владельцу через security-контакт и зафиксировать доказательство. Использовать найденные ключи или данные нельзя — это нарушение, даже если доступ был открыт.

## Куда дальше

В следующем уроке мы возьмём **домен за CDN** и разберём, как найти его настоящий сервер — origin — обходя Cloudflare. А пока запомни главное: облачные бакеты находятся по предсказуемым именам, а с найденным открытым бакетом работают как с находкой, а не как с добычей.

## Где пригодится

- **Bug bounty:** поиск открытых бакетов с данными — частый класс находок.
- **Cloud audit:** инвентаризация облачных активов организации.
- **CTF (OSINT):** найти публичный бакет с подсказкой или флагом.
- **Пентест:** расширение поверхности через облачные ресурсы.
