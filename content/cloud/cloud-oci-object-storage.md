## Вопрос, с которого всё начинается

В логах CI или в истории браузера инженера ты находишь длинную ссылку вида `https://objectstorage.../p/...`. Она ни на что не похожа: ни ключа, ни токена — просто URL. Вопрос: что она открывает и насколько это опасно? В Oracle Cloud такие ссылки называются pre-authenticated requests, и они часто оказываются самым коротким путём к данным — короче, чем утёкший API-ключ.

## Что такое Object Storage

Object Storage — хранилище файлов в OCI: бакеты и объекты внутри них. Бакет имеет **уровень доступа** (visibility): `Private` (доступ только по политикам/ключам) или `Public` (чтение всем). Объекты внутри бакета читаются и пишутся через API, а права определяются IAM-политиками — теми самыми, что мы разбирали ранее. Но есть второй, «беспарольный» путь: **pre-authenticated request**.

## Сквозной пример: утёкшая ссылка

Смотрим найденный файл:
```
$ cat urls.txt
https://objectstorage.eu-frankfurt-1.oraclecloud.com/n/acme/b/backups/o/db-2024.tar.gz
https://objectstorage.eu-frankfurt-1.oraclecloud.com/p/AbCdEf123456/n/acme/b/backups/o/
```
Первая ссылка — обычный путь к объекту; она требует аутентификации. Вторая содержит сегмент `/p/` — это и есть PAR: параметр доступа зашит в саму ссылку. Если PAR создан с широкими правами, по нему читается весь бакет без ключей.

## Как устроен pre-authenticated request

PAR — это временная (или бессрочная) ссылка, выпущенная на объект или на бакет. При создании задаются:
- **target** — конкретный объект или весь бакет;
- **access type** — `ObjectRead`, `ObjectReadWrite`, `AnyObjectRead`, `AnyObjectReadWrite`;
- **expiry** — дата истечения (может быть пустой!).

Два поля определяют риск. Если target — бакет, а access type — `AnyObjectReadWrite`, то по ссылке можно читать **и писать** любые объекты. Запись особенно опасна: атакующий может подменить артефакт, который потом скачает CI, — это уже supply-chain.

## Публичные бакеты и листинг

Второй путь утечки — `Public` бакет. Публичным делают «чтобы отдавать статику», а потом складывают туда дампы. В OCI у бакета есть возможность разрешить **список объектов** (list objects) — тогда по URL видно всё содержимое, и не нужно угадывать имена. При аудите проверяем: visibility бакета, разрешён ли листинг, есть ли в бакете чувствительные имена (`*.env`, `*.sql`, `backup`, `credentials`).

## Lifecycle, версии и восстановление

Object Storage умеет версионирование и правила жизненного цикла (удалять через N дней, переводить в архив). Для атакующего это важно по двум причинам. Первая: удалённый объект может остаться в предыдущей версии — «секрет убрали», а старая версия доступна. Вторая: правила lifecycle иногда оставляют копии в другом бакете. Проверяй версии, если включено версионирование.

## Цепочка атаки

Типичный сценарий: PAR утёк из логов CI → читаем бакет с бэкапами → находим в бэкапе конфиг приложения → в конфиге ключи от БД или другой PAR с `ReadWrite` → пишем подменённый артефакт → CI разворачивает его. Одна ссылка превращается в захват цепочки поставки. Именно поэтому PAR считают «креденшелом, который выглядит как URL»: его надо ротировать и логировать так же строго, как ключ.

## Как проверить руками

```
$ oci os bucket list --compartment-id <ocid>
$ oci os object list --bucket-name backups
$ oci os preauth-request list --bucket-name backups
```
Список PAR покажет target, access-type и expiry — этого достаточно, чтобы оценить риск. Публичный бакет проверяется обычным `curl` на URL объекта без заголовков авторизации.

## OCI Object Storage: доступ и находки

Object Storage в OCI — бакеты с объектами. Доступ управляется IAM-политиками, pre-authenticated requests (PAR — ссылка с токеном), и visibility (public/private). Типичные ошибки: публичный бакет, PAR без срока/ограничений, широкие политики.

```bash
oci os bucket list --compartment-id <id>
oci os object list --bucket-name <b> --namespace <ns>
```

PAR — особенно интересны: ссылка вида `https://objectstorage.../p/<token>/...` даёт доступ без аутентификации. Если PAR утёк (в логах, коде), доступ открыт.

## Практика: PAR и публичные бакеты

Что искать: публичные бакеты (анонимный листинг), PAR (в коде/логах/URL), объекты с секретами, широкие политики. Проверка публичного бакета: `curl https://objectstorage.<region>.oraclecloud.com/n/<ns>/b/<bucket>/o/`. Инструменты: `oci os`, `curl`, `cloud_enum`.

```bash
curl "https://objectstorage.us-ashburn-1.oraclecloud.com/n/<ns>/b/<bucket>/o/"
```

Типичная находка — PAR без ограничений, дающий доступ ко всему бакету.

## Защита

Меры: приватные бакеты, PAR с коротким сроком и ограниченным доступом, шифрование, мониторинг, аудит публичных бакетов и PAR. Для пентеста — перечисление и чтение публичного; модификация — с разрешения.

## Расширенный разбор: pre-authenticated requests

PAR (pre-authenticated request) — URL с токеном, дающий доступ к бакету/объекту без аутентификации. PAR бывает на чтение, запись, список. Если PAR утёк (в коде, логах, письме), доступ открыт, пока PAR не истечёт. Проверь PAR на бакетах: какие созданы, какой срок, какой доступ.

```bash
oci os preauth-request list --bucket-name <b> --namespace <ns>
curl "https://objectstorage.<region>.oraclecloud.com/p/<token>/n/<ns>/b/<b>/o/"
```

Типичная находка — PAR на запись с длинным сроком, позволяющий загрузить вредоносный контент.

## Расширенный разбор: публичные бакеты и политики

Бакет может быть публичным (анонимный листинг/чтение). Проверь `oci os bucket get` на `publicAccessType`. Также проверь IAM-политики, дающие доступ к бакетам: широкая политика (`manage object-family`) даёт доступ ко всем бакетам компартмента.

```bash
oci os bucket get --bucket-name <b> --namespace <ns>
```

Собери цепочку: политика/ACL/PAR → бакет → объекты → данные. Каждая находка — самостоятельна.

## Защита и вывод

Меры: приватные бакеты, PAR с коротким сроком и минимальным доступом, шифрование, минимальные политики, мониторинг, аудит публичных бакетов и PAR. Вывод: OCI Object Storage — обычное объектное хранилище; аудит — ACL, PAR, политики, объекты.

## Разбор кейса: PAR на запись

История из практики. Для приёма загрузок от партнёра создали pre-authenticated request на запись в бакет со сроком «навсегда». PAR попал в документацию партнёра и утёк. Атакующий загрузил в бакет вредоносный контент, который затем раздавался как часть сайта. Вывод: PAR должен иметь минимальный доступ и короткий срок; «навсегда» — находка сама по себе.

## Вывод по OCI Object Storage

Аудит: бакеты (публичность) → PAR (срок, доступ) → IAM-политики → объекты. Защита: приватные бакеты, короткие PAR, минимальные политики, шифрование, мониторинг.

## Что мы теперь знаем

- Object Storage: бакеты с visibility Private/Public и объекты внутри.
- PAR — самодостаточная ссылка; утечка PAR = утечка доступа.
- Опасная комбинация: target=бакет + `AnyObjectReadWrite` + пустой expiry.
- Публичный бакет с листингом отдаёт всё содержимое по URL.
- Версионирование может сохранить «удалённый» секрет.

Практический чек-лист: перечисли бакеты; проверь `publicAccessType`; найди все PAR и их сроки; проверь IAM-политики на `manage object-family`; скачай доступное и поищи секреты; оцени импакт по содержимому. PAR на запись особенно опасен: он позволяет загрузить вредоносный контент, который затем может раздаваться как часть сайта или использоваться для отравления данных. Проверяй такие PAR в первую очередь. Для отчёта собери цепочку: политика/ACL/PAR → бакет → объекты → данные. Каждая находка самостоятельна, но вместе они дают полный доступ к хранилищу.

Проверь также политики на уровне compartment: если политика разрешает `manage object-family` всему тенанту, любой пользователь получает доступ ко всем бакетам, включая production. Это часто незаметно, потому что политика выглядит «нормальной», а импакт — полный. И оцени срок жизни PAR: PAR «навсегда» — находка, даже если сейчас он не утёк, потому что рано или поздно попадёт в лог или документацию.

Итог по OCI Object Storage: проверяй три механизма доступа — IAM-политики, pre-authenticated requests и публичность бакета. Каждый из них может открыть данные независимо от остальных, поэтому проверять надо все три, а не только ACL. Особое внимание — PAR: они обходят аутентификацию полностью, поэтому их срок и область должны быть минимальны. В отчёте покажи, какие объекты доступны через какой механизм, и оцени чувствительность данных.

Практическое замечание: прежде чем делать вывод, проверь, действительно ли объект доступен без аутентификации — иногда 403 приходит только из-за отсутствия заголовка или неверного namespace. Убедись в находке воспроизводимым запросом и зафиксируй его в отчёте. Если доступ подтверждён, оцени объём и чувствительность данных: количество объектов, их типы, наличие персональных данных. Это определит критичность находки.

Рекомендация заказчику: настроить автоматический аудит публичных бакетов и сроков PAR, а также выгрузку логов доступа в мониторинг, чтобы факт скачивания данных можно было отследить и расследовать.

Помни, что объектное хранилище часто содержит самые чувствительные артефакты — бэкапы, дампы, ключи — поэтому даже «пустой» бакет стоит проверить. ## Квиз

## Где пригодится

- Пентест хранилищ Oracle Cloud: быстрый поиск публичных бакетов и PAR.
