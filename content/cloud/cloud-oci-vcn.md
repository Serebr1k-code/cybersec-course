## Вопрос, с которого всё начинается

Ты получил утёкший Terraform-репозиторий, который описывает сеть в Oracle Cloud. Из него надо понять, что доступно из интернета и куда можно пройти дальше. Сеть в облаке — это не только «открытые порты»: OCI строит изоляцию из подсетей, списков безопасности и шлюзов, и мисконфиг в одном правиле открывает весь путь. Разберём, как это читать.

## Что такое VCN

VCN (Virtual Cloud Network) — виртуальная сеть внутри tenancy, аналог VPC в AWS. Внутри VCN нарезаются **подсети** (subnets) — публичные и приватные. Подсети соединяются со внешним миром через **шлюзы**: Internet Gateway (двусторонний выход в интернет), NAT Gateway (только исходящий трафик), Service Gateway (доступ к сервисам Oracle без интернета) и Dynamic Routing Gateway (связь с on-premise). Трафик фильтруется двумя разными механизмами: **security lists** на уровне подсети и **NSG** (network security groups) на уровне ресурса.

## Сквозной пример: конфиг сети

Смотрим фрагмент конфига:
```
$ cat vcn.json
{
  "subnet": "public-subnet",
  "security_list": [
    {"protocol": "tcp", "port": 22,   "source": "0.0.0.0/0"},
    {"protocol": "tcp", "port": 3389, "source": "0.0.0.0/0"},
    {"protocol": "tcp", "port": 1521, "source": "10.0.0.0/16"}
  ]
}
```
Три правила. Первое открывает SSH всему интернету, второе — RDP (Windows), третье — порт Oracle Database (1521), но только из внутренней сети. Уже видно: машина в публичной подсети с открытым SSH/RDP — приманка для брутфорса. Дальше посмотрим на шлюзы и подсети.

## Security lists против NSG

**Security list** — набор правил ingress/egress, привязанный к подсети. Действует на все ресурсы в ней. **NSG** — тот же набор правил, но привязанный к конкретным VNIC (сетевым интерфейсам). Итоговое разрешение — это пересечение: трафик должен быть разрешён и security list, и NSG, если NSG применён. Частый мисконфиг — широкое правило в security list, которое «забыли» сузить, плюс отсутствие NSG. Тогда фильтрация фактически одна.

При аудите смотри на `source`: `0.0.0.0/0` для управляющих портов (22, 3389, 1521, 6443) — красный флаг. Дальше проверь, есть ли NSG, который это сужает.

## Шлюзы и маршрутизация

Route table подсети определяет, куда идёт трафик. Публичная подсеть обычно имеет маршрут `0.0.0.0/0 -> Internet Gateway`. Приватная — `0.0.0.0/0 -> NAT Gateway`. Если у приватной подсети ошибочно стоит Internet Gateway, изоляция ломается: ресурсы, которые считались недоступными, начинают отвечать из интернета. При разборе конфига всегда сопоставляй: подсеть → route table → шлюз.

Service Gateway — отдельная история: через него ресурс ходит в Object Storage и другие сервисы OCI, не выходя в интернет. Атакующему это интересно как путь эксфильтрации, который не виден в egress-логах интернет-шлюза.

## Изоляция и типовые ошибки

Сетевая изоляция в OCI ломается предсказуемо:
- публичная подсеть для баз данных «чтобы удобнее»;
- `0.0.0.0/0` на управляющие порты;
- security list, разрешающий весь TCP (все порты) для внутренней сети;
- отсутствие NSG на чувствительных ресурсах;
- SSH-ключ без пароля, оставленный на инстансе с публичным IP.

Каждая из этих ошибок превращает «внутренний» ресурс в доступный. На пентесте мы идём по цепочке: открытый порт → уязвимый сервис → инстанс → instance principal (см. прошлый урок) → права.

## Как проверить руками

С конфигом CLI можно перечислить сети и правила:
```
$ oci network vcn list --compartment-id <ocid> --all
$ oci network security-list list --compartment-id <ocid> --vcn-id <ocid> --all
$ oci network nsg list --compartment-id <ocid> --all
```
Вывод даёт объекты, но не их смысл — смысл мы добавляем сами: сопоставляем порты с сервисами и источники с зонами доверия.

## OCI VCN: сеть и её поверхность

VCN (Virtual Cloud Network) — изолированная сеть OCI: подсети, security lists, network security groups (NSG), route tables, internet/nat/service gateways. Ошибки: security list с `0.0.0.0/0` на чувствительные порты, отсутствие сегментации, публичные подсети для внутренних сервисов, открытые сервисные шлюзы.

```text
VCN -> subnets -> security lists / NSG -> instances
```

Аудит: инвентаризация VCN, подсетей, правил; поиск `0.0.0.0/0`; проверка маршрутизации (куда ведут gateway).

## Практика: анализ сети

Что проверять: (1) security lists и NSG (входящие/исходящие правила); (2) публичные vs приватные подсети; (3) route tables (интернет/nat/peering); (4) VCN peering (связи между VCN); (5) VPN/FastConnect. Инструменты: `oci network`, `nmap`.

```bash
oci network security-list list --compartment-id <id> --vcn-id <vcn>
oci network subnet list --compartment-id <id> --vcn-id <vcn>
```

Типичная находка — публичная подсеть с SSH/RDP из интернета и отсутствием сегментации между окружениями.

## Защита

Меры: приватные подсети, минимальные NSG, bastion/VPN для доступа, сегментация по окружениям, мониторинг flow logs. Для пентеста — чтение конфигурации и проверка доступности портов (без нагрузки).

## Расширенный разбор: security lists и NSG

Security list применяется к подсети, NSG — к ресурсам (VNIC). Правила бывают stateful/stateless. Типичная ошибка — security list с `0.0.0.0/0` на 22/3389/3306, или исходящее правило `0.0.0.0/0` (разрешает exfiltration). Проверь оба уровня и их приоритет.

```bash
oci network security-list list --compartment-id <id> --vcn-id <vcn>
oci network nsg list --compartment-id <id>
```

Ищи: широкие входящие правила, отсутствие ограничений по источнику, разрешающие исходящие. Каждое — находка.

## Расширенный разбор: маршрутизация и peering

Route tables определяют, куда идёт трафик: internet gateway (публичный), NAT (исходящий), service gateway (сервисы OCI), peering (между VCN), DRG (к on-prem). Ошибка маршрутизации может открыть путь между окружениями или к on-prem. Проверь peering и его правила (кто с кем связан).

```bash
oci network route-table list --compartment-id <id> --vcn-id <vcn>
oci network vcn list --compartment-id <id>
```

Собери карту: подсети → маршруты → gateways → внешние связи. Это показывает, куда можно дотянуться из точки входа.

## Защита и вывод

Меры: приватные подсети, минимальные NSG, bastion/VPN, сегментация, flow logs, аудит peering. Вывод: сетевой аудит VCN — это карта подсетей, правил и маршрутов; ищи широкие правила и лишние связи.

## Разбор кейса: открытый порт в публичной подсети

История из практики. База данных стояла в публичной подсети, а security list разрешал порт 5432 с `0.0.0.0/0` «для отладки». Атакующий нашёл порт сканером и подобрал слабый пароль. Вывод: публичная подсеть для БД — ошибка; security list должен ограничивать источник. Проверяй оба уровня (security list и NSG) и маршрутизацию.

## Вывод по OCI VCN

Сетевой аудит: подсети (публичные/приватные) → security lists/NSG → route tables → gateways/peering. Ищи широкие правила и лишние связи. Защита: приватные подсети, минимальные NSG, bastion/VPN, сегментация, flow logs.

## Что мы теперь знаем

- VCN — виртуальная сеть; внутри — публичные и приватные подсети.
- Фильтрация: security lists (на подсеть) + NSG (на ресурс); действует пересечение.
- `0.0.0.0/0` на управляющих портах — главный красный флаг.
- Route table решает, каким шлюзом уходит трафик; ошибка в маршруте ломает изоляцию.
- Service Gateway — скрытый путь к сервисам OCI без выхода в интернет.

Практический чек-лист: перечисли VCN и подсети; проверь, какие подсети публичные; собери security lists и NSG и найди широкие правила (`0.0.0.0/0`); проверь route tables и gateways; проверь peering и VPN; оцени путь от точки входа к внутренним сервисам. Обрати внимание на исходящие правила: разрешающий `0.0.0.0/0` исходящий доступ позволяет exfiltration данных из скомпрометированного ресурса. Ограничение исходящего трафика — важная, но часто забываемая мера. Для отчёта построй карту: подсети → маршруты → gateways → внешние связи. Это показывает, куда можно дотянуться и какие связи лишние.

Отдельно оцени, включены ли flow logs: без них невозможно расследовать, кто и куда ходил по сети, и это самостоятельная находка. Для пентеста flow logs полезны как источник карты трафика, если есть доступ.

Итог по OCI VCN: сетевой аудит — это карта подсетей, правил и маршрутов. Ищи публичные подсети с чувствительными сервисами, широкие правила `0.0.0.0/0` и лишние связи (peering, VPN). Каждая из этих находок самостоятельно повышает риск, а вместе они открывают путь от точки входа к внутренним данным.

Практическое замечание: перед выводом о «публичной подсети» проверь, действительно ли порт отвечает извне — иногда мешает NAT или промежуточный firewall. Подтверди доступность запросом и укажи это в отчёте.

Рекомендация заказчику: вынести внутренние сервисы в приватные подсети и ограничить доступ через bastion, а также включить flow logs для расследования сетевых инцидентов.

## Куда дальше

В следующем уроке — OCI Object Storage: как устроены бакеты, что такое pre-authenticated request и почему одна утёкшая ссылка стоит дороже, чем утёкший ключ. А пока главное: сеть в OCI читается как цепочка «подсеть → маршрут → шлюз → правило».

## Где пригодится

- Пентест сетей Oracle Cloud: быстрая карта «что открыто наружу».
- Разбор инцидентов: понять, как атакующий попал на инстанс.
- Проектирование: не оставлять управляющие порты в `0.0.0.0/0`.
