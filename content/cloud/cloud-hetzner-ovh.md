## Вопрос, с которого всё начинается

В `.env` CI-проекта лежит переменная `HCLOUD_TOKEN` — длинная строка из букв и цифр. Рядом нет ни пароля, ни ключа. Вопрос: что даёт этот токен и как далеко можно зайти? У Hetzner, OVH и Scaleway модель доступа предельно проста: один bearer-токен открывает API, а API умеет пересоздавать серверы, менять SSH-ключи и включать rescue mode. Из этого вырастает прямой путь к shell на машине.

## Что за провайдеры

Hetzner Cloud, OVH и Scaleway — европейские провайдеры, популярные у малого и среднего бизнеса. Они дают виртуальные и bare-metal серверы, снапшоты, сети и балансировщики. Их IAM заметно проще, чем у большой тройки: часто есть только один API-токен на проект, с полными правами и без MFA. Именно эта простота делает утечку токена особенно опасной: нет гранулярных ролей, которые могли бы ограничить ущерб.

## Сквозной пример: токен в .env

Смотрим файл:
```
$ cat .env
HCLOUD_TOKEN=EXAMPLEnotarealtokenlongstring
```
Токен Hetzner Cloud. API — REST по адресу `https://api.hetzner.cloud/v1`. Первый запрос — проверить, что токен жив:
```
$ curl -s -H "Authorization: Bearer $HCLOUD_TOKEN" https://api.hetzner.cloud/v1/servers
{"servers":[{"id":42,"name":"prod-web-1","status":"running",...}]}
```
Токен работает. Теперь у нас список серверов аккаунта.

## Что умеет API-токен

Дальше — самое важное. Через API можно не только читать, но и менять:
- **пересоздать сервер** (`POST /servers`) с уже известным публичным SSH-ключом;
- **сменить SSH-ключ** существующего сервера (в некоторых сценариях через пересоздание);
- **включить rescue mode** (`POST /servers/{id}/actions/enable_rescue`) — загрузиться в аварийную систему;
- **создать снапшот** и скачать его;
- **удалить сервер** (деструктивно!).

Rescue mode — ключевой приём: сервер загружается в минимальную систему, куда провайдер кладёт временный root-пароль, который возвращает API. Получив пароль, атакующий входит по SSH и монтирует рабочий диск — то есть получает доступ к данным и настройкам сервера, обходя его обычную аутентификацию.

## OVH и Scaleway

OVH использует подпись запросов (Application Key + Application Secret + Consumer Key) и консоль, где токены тоже живут долго. Scaleway — bearer-токены (`SCW_...`) с ограничением по правам, но по умолчанию с широкими. Логика атаки одна: найти токен → определить его права → выполнить действие, которое даёт shell или доступ к данным. У OVH и Scaleway тоже есть rescue/reboot-механики.

## Снапшоты как обход

Снапшот — копия диска. Даже если на живом сервере хорошая защита, снапшот можно скачать или подключить к новому серверу и прочитать содержимое диска напрямую: конфиги, ключи, базы. Поэтому «создать снапшот → подключить к своему инстансу» — стандартный обход, когда rescue mode выключен.

## Цепочка атаки

Типичный путь: токен утёк из `.env` → перечисляем серверы → включаем rescue mode → получаем root-пароль → входим → читаем данные и ищем ключи → используем найденные ключи для lateral movement. Альтернатива: снапшот → подключение к своему серверу → чтение диска. Оба пути упираются в одно: один долгоживущий токен = контроль над инфраструктурой.

## Как проверить руками

```
$ curl -s -H "Authorization: Bearer $HCLOUD_TOKEN" https://api.hetzner.cloud/v1/servers
$ curl -s -H "Authorization: Bearer $HCLOUD_TOKEN" https://api.hetzner.cloud/v1/ssh_keys
$ curl -s -H "Authorization: Bearer $HCLOUD_TOKEN" https://api.hetzner.cloud/v1/volumes
```
Список SSH-ключей показывает, чьи ключи привязаны к аккаунту, — часто там ключ самого CI, который можно использовать для входа.

## Hetzner/OVH: что это и поверхность

Hetzner и OVH — «классические» европейские хостинг-провайдеры: VPS, выделенные серверы, объектное хранилище, сети. Поверхность: API-токены, root-доступ к серверам, объектное хранилище (S3-совместимое), DNS, firewall. Типичные находки: открытые серверы, слабые пароли, публичные бакеты, утёкшие API-токены.

```bash
hcloud server list          # Hetzner Cloud CLI
openstack server list       # OVH (OpenStack)
```

Отличие от «больших» облаков: меньше управляемых сервисов, больше ответственности пользователя, но и меньше встроенной безопасности (нет IAM с ролями по умолчанию).

## Практика: аудит и находки

Что проверять: (1) инвентаризация серверов и открытых портов; (2) API-токены (Hetzner: `HCLOUD_TOKEN`; OVH: OpenStack-креды); (3) объектное хранилище (публичные бакеты); (4) DNS и firewall; (5) снапшоты и бэкапы. Инструменты: `hcloud`, `openstack`, `s3cmd`/`aws s3`, `nmap`.

```bash
hcloud server list
aws --endpoint-url https://s3.<region>.cloud.ovh.net s3 ls
```

Типичная находка — токен в CI, дающий доступ ко всем серверам.

## Защита

Меры: минимальные API-токены, ротация, firewall на серверах, приватное объектное хранилище, отдельные проекты на окружения, мониторинг, бэкапы с проверкой. Для пентеста — только чтение конфигурации.

## Расширенный пример: утёкший API-токен

История из практики. В публичном репозитории лежал `HCLOUD_TOKEN`. Атакующий перечислил серверы, увидел один с открытым SSH (пароль в другом файле репозитория) и получил root. Отдельной уязвимости не было — только токен с полными правами и слабый доступ к серверу. Вывод: API-токены хостинга равны контролю над всей инфраструктурой.

```bash
hcloud server list
hcloud server describe <id>
```

Практический вывод: аудит начинается с поиска токенов в коде/CI, затем — инвентаризация серверов и портов.

## Практика: аудит хостинга

Порядок: (1) найти токены/креды; (2) перечислить серверы и снапшоты; (3) проверить открытые порты; (4) проверить объектное хранилище; (5) проверить DNS и firewall; (6) оценить, что даёт токен (полный контроль или ограниченный). Инструменты: `hcloud`, `openstack`, `nmap`, `s3cmd`.

```bash
hcloud server list; hcloud volume list; hcloud firewall list
```

Типичные находки: сервер с открытым RDP/SSH, публичный бакет, токен с правами на удаление. Всё фиксируй в отчёте.

## Защита

Меры: минимальные API-токены, ротация, отдельные проекты, firewall по умолчанию, ключевой SSH-доступ (без паролей), приватное хранилище, мониторинг API-вызовов, бэкапы. Для пентеста — чтение конфигурации.

## Расширенный разбор: от токена к серверам

Полная цепочка: токен → инвентаризация → доступ → данные. Первое — найти токен (GitHub, CI, логи). Второе — `hcloud server list`/`openstack server list`. Третье — проверить открытые порты и доступ к серверам. Четвёртое — объектное хранилище. Пятое — снапшоты (могут содержать старые данные).

```bash
hcloud server list; hcloud image list; hcloud volume list
nmap -sV <server-ip>
```

Типичная находка — токен с полными правами и сервер с открытым SSH. Это прямой путь к данным.

## Практика и защита

Практика: инвентаризация серверов, портов, хранилища, снапшотов; поиск токенов. Инструменты: `hcloud`, `openstack`, `nmap`, `s3cmd`. Защита: минимальные токены, ротация, firewall, ключевой SSH, приватное хранилище, мониторинг. Вывод: хостинг-провайдеры дают прямой доступ к инфраструктуре, поэтому токен = контроль.

## Чек-лист аудита хостинга

1. Поиск токенов/кредов. 2. Инвентаризация серверов, образов, томов. 3. Открытые порты. 4. Объектное хранилище (ACL). 5. DNS и firewall. 6. Снапшоты (старые данные). Инструменты: `hcloud`, `openstack`, `nmap`, `s3cmd`.

## Разбор кейса: токен в публичном репозитории

История из практики. Разработчик запушил `.env` с `HCLOUD_TOKEN` в публичный репозиторий на несколько минут, но этого хватило: сканеры секретов находят ключи за секунды. Атакующий перечислил серверы, нашёл один с открытым SSH и слабым паролем (тоже из репозитория) и получил root. Дальше — доступ к базе. Вывод: токен хостинга с полными правами равен контролю над инфраструктурой, а «несколько минут публичности» не спасают — ключ надо считать скомпрометированным и ротировать.

## Что мы теперь знаем

- У Hetzner/OVH/Scaleway доступ часто сводится к одному долгоживущему токену.
- Токен умеет не только читать, но и пересоздавать серверы, менять ключи, включать rescue.
- Rescue mode даёт временный root-пароль → вход в аварийную систему.
- Снапшот можно скачать/подключить и прочитать диск напрямую.
- API-токен хостинг-провайдера = контроль над инфраструктурой без MFA.
