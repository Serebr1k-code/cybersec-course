## Вопрос, с которого всё начинается

В функции подключён layer и несколько extensions. Ты можешь добавить свой слой или расширение (через деплой или PR). Вопрос: что именно исполняется внутри песочницы функции, видит ли этот код секреты окружения и вызовы, и почему «просто слой с библиотекой» может быть полноценным имплантом внутри serverless?

## Что такое extensions и layers

Lambda extensions — процессы, которые запускаются в том же окружении, что и функция, и живут дольше одного вызова: они стартуют при инициализации песочницы и могут работать между вызовами. Layers — архивы, которые добавляются в файловую систему функции (библиотеки, бинарники). Вместе они позволяют добавлять код, который видит окружение функции, её переменные и может перехватывать обращения через Runtime API.

## Сквозной пример: расширение

Смотрим конфигурацию:
```
$ aws lambda get-function-configuration --function-name billing
{
  "Layers": [{"Arn": "arn:aws:lambda:eu-west-1:123456789012:layer:monitoring:3"}],
  "Environment": {"Variables": {"DB_PASSWORD": "***", "API_KEY": "***"}},
  "Layers": [ ... ]
}
```
Слой `monitoring` содержит расширение. Оно запускается при старте песочницы и видит переменные окружения, включая секреты. Если слой можно подменить или добавить свой, ты получаешь исполнение кода с доступом к этим секретам.

## Runtime API и доступ к вызовам

Расширения общаются с функцией через Runtime API (`AWS_LAMBDA_RUNTIME_API`): получают события, регистрируют обработчики, могут влиять на поток вызовов. Это значит, что расширение может перехватывать входные данные (включая токены и пароли, переданные в вызове) и модифицировать ответы. Возможности расширения близки к возможностям самой функции, но реализуются в отдельном процессе.

## Persistence в песочнице

Песочницы переиспользуются между вызовами (warm start). Расширение может записать состояние в `/tmp` или изменить окружение и «пережить» вызовы до тех пор, пока песочница жива. Это не вечная persistence (песочница в итоге перезапускается), но достаточно для перехвата нескольких вызовов и сбора данных. Плюс расширение может повторно инициализироваться при каждом cold start — то есть загружаться снова и снова.

## Supply chain слоёв

Слои часто берут из общего аккаунта или из публичного источника. Если слой общий для многих функций, его компромисс затрагивает все. Если ты можешь опубликовать новую версию слоя или подменить ARN, ты внедряешь код во все функции, которые его используют. Версии слоёв иммутабельны, но ARN можно указать на нужную версию — и если конфиг функции меняется, ты можешь подсунуть свою.

## Secrets в окружении и logs

Секреты функции обычно лежат в переменных окружения (иногда зашифрованы KMS, но расшифровываются при старте). Расширение видит их в открытом виде. Кроме того, расширение может логировать данные, которые увидело, в CloudWatch или отправлять их наружу. Это прямой канал утечки секретов функции без эксплуатации её логики.

## Типовые мисконфиги

| Мисконфиг | Последствие | Как искать |
|---|---|---|
| Слой из общего/публичного источника | supply chain | Layers ARN |
| Расширение с сетевым доступом | exfil секретов | конфиг функции |
| Секреты в env без KMS | чтение расширением | Environment |
| Право менять конфиг функции | внедрение кода | IAM |
| Нет контроля версий слоя | подмена кода | versioning |
| Расширение из PR | RCE в песочнице | CI деплой |

## Полный прогон: от слоя к секретам

Шаги. Первый: перечислить функции и их слои/расширения. Второй: определить, откуда берутся слои и можно ли их менять. Третий: проверить, есть ли право обновлять конфигурацию функции. Четвёртый: добавить своё расширение (через слой или `Extensions`). Пятый: дождаться вызова, собрать env и события. Шестой: отправить данные наружу. Седьмой: закрепиться (расширение живёт в песочнице).

## Инструменты и команды

Полезны: `aws lambda get-function-configuration`, `aws lambda list-layer-versions`, `aws lambda publish-layer-version`, `aws lambda update-function-configuration`. Для разбора слоя — скачивание (`get-layer-version` даёт URL), распаковка, анализ содержимого. Для наблюдения за Runtime API — заголовок `AWS_LAMBDA_RUNTIME_API` в env.

## OPSEC и детект

Добавление слоя/расширения видно в CloudTrail (`UpdateFunctionConfiguration`, `PublishLayerVersion`). Сетевые вызовы расширения видны в VPC Flow Logs и в логах. Расширение, обращающееся к внешнему адресу, — сильный индикатор. Тихий сценарий — использовать существующий слой с сетевым доступом для чтения env, не добавляя новых.

## Частые вопросы

Живёт ли расширение вечно? Нет, до перезапуска песочницы. Видит ли секреты? Да, env доступно процессу. Можно ли добавить без прав? Нужно право менять конфиг функции. Опасны ли общие слои? Да, компромисс затрагивает всех. Помогает ли KMS-шифрование env? Частично — расшифровка всё равно происходит при старте.

## Что не сработает

Без права менять конфигурацию функции свой слой не добавить. Иммутабельные версии слоя нельзя перезаписать — только указать новую. Если секреты не в env, а берутся из внешнего провайдера в момент вызова, расширение увидит их только через перехват. И если функция изолирована от сети, exfil не пройдёт.

## Разбор кейса: слой monitoring

История из практики. Команда использовала общий слой `monitoring`, который ставил расширение для сбора метрик. Слой лежал в общем аккаунте, и права на публикацию были у нескольких команд. Атакующий, получив доступ к одной из них, опубликовал новую версию слоя с расширением, которое читало переменные окружения функций и отправляло их на внешний адрес. Обновив конфиг целевых функций на этот слой, он собрал облачные креды из нескольких сервисов. Компромисс одного слоя затронул весь парк функций.

## Runtime API на практике

Переменная `AWS_LAMBDA_RUNTIME_API` в окружении содержит хост и порт Runtime API. Расширение делает к нему HTTP-запросы: регистрируется (`/register`), получает события (`/next`), отправляет ответы. Так расширение видит входные данные каждого вызова — включая токены и параметры, переданные пользователем. Оно может и ответы модифицировать. Для атакующего это канал перехвата: не нужно ломать логику функции, достаточно слушать поток вызовов из расширения.

## Защита extensions и layers

Меры: использовать только доверенные слои из своего аккаунта; фиксировать версии и проверять содержимое; ограничить права публикации слоёв; не хранить секреты в env без внешнего менеджера; ограничить сетевой доступ функции; аудит изменений конфигурации функций и публикации слоёв. Дополнительно — сканировать слои на подозрительный код. Каждая мера закрывает один шаг: подмену слоя, чтение env, эксфильтрацию.

## Частые заблуждения

Первое: «слой — просто библиотека». Он может содержать расширение-процесс. Второе: «расширение не видит секреты». Env доступно любому процессу в песочнице. Третье: «версии слоя неизменяемы, значит безопасно». Неизменяемость не мешает указать новую версию. Четвёртое: «расширения нужны только для метрик». Они дают полноценный доступ к вызовам. Пятое: «песочница изолирована от сети». Часто у неё есть egress.

## Инвентаризация слоёв и расширений

Для каждой функции выпиши её слои (`get-function-configuration`) и определи, какие из них содержат расширения. Проверь, откуда берутся слои: свой аккаунт, общий аккаунт, публичный источник. Посмотри, у кого есть право `PublishLayerVersion` и `UpdateFunctionConfiguration`. Найди функции, использующие один и тот же слой, — их компромисс через слой затронет всех. Эта карта показывает точки supply chain и функции-жертвы.

## Extensions vs сама функция

Расширение исполняется рядом с функцией, но в отдельном процессе. Оно может делать то, что и функция: читать env, обращаться в сеть, писать файлы. Разница в том, что расширение не зависит от логики функции и живёт между вызовами. Поэтому даже если функция «безопасна», вредоносное расширение собирает данные. Для атакующего это способ обойти аудит кода функции: код лежит в слое, а не в репозитории приложения.

## Итоговая цепочка атаки

Атакующий получает право публиковать слои или менять конфигурацию функций. Он публикует слой с расширением, читающим env и события Runtime API, и указывает его для целевых функций. При следующем вызове расширение собирает секреты и отправляет их наружу. Цепочка держится на правах менять функции и на доверии к слоям. Ограничь права публикации и используй только свои слои — и она рвётся.

## Взаимодействие с Runtime API

Расширение регистрируется через `POST /register` и далее опрашивает `GET /next` для получения событий. Ответы и ошибки тоже проходят через Runtime API. Это значит, что расширение видит не только входные данные, но и момент вызова, и может влиять на результат. Для атакующего достаточно одного расширения, чтобы перехватывать все вызовы функции, пока песочница жива. При этом расширение не требует изменений в коде самой функции — только в конфигурации слоёв/расширений.

## Этика и границы

Внедрение расширения в чужую функцию — это исполнение кода в чужой инфраструктуре. При пентесте это надо делать в согласованных границах, с минимальным набором действий (доказать доступ к env), и удалять внедрённое после проверки. Не собирай реальные секреты больше, чем нужно для доказательства, и не оставляй активных имплантов. Слои и конфигурации функций легко оставить «забытыми» — проверь, что всё вернул в исходное состояние.

## Что мы теперь знаем

1. Extensions — процессы внутри песочницы, живущие дольше вызова.
2. Они видят env-секреты и могут перехватывать вызовы через Runtime API.
3. Слои — supply chain: общий слой затрагивает все функции.
4. Расширение даёт persistence на время жизни песочницы.
5. Право менять конфиг функции = внедрение кода в песочницу.
