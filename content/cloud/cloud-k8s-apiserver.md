## Вопрос, с которого всё начинается

Ты получаешь токен service account (или доступ к API server). Вопрос: как API server решает, кто ты и что тебе можно, можно ли выдать себя за другого, и как из «есть токен» получить полный контроль над кластером. Начнём с того, что API server — единственная точка управления, и его безопасность строится из аутентификации (кто ты) и авторизации (что можно), а ошибки в обеих дают эскалацию.

## Что такое API server

kube-apiserver — центральный компонент: через него читают и меняют все объекты кластера (Pod, Secret, RBAC, CRD). Аутентификация бывает: клиентские сертификаты, bearer-токены service account, OIDC, webhook, а также анонимный доступ (если включён). Авторизация — RBAC (роли и привязки), ABAC, Node, webhook. Каждый запрос проходит цепочку: кто ты → можно ли тебе это → выполняем. Все остальные компоненты (kubelet, controller, scheduler) тоже ходят через API server.

## Сквозной пример: токен SA

Смотрим права токена:
```
$ kubectl auth can-i --list --token=$TOKEN
Resources: pods, secrets
Verbs:     get, list
$ kubectl auth can-i impersonate users --token=$TOKEN
yes
```
Токен может читать Pod и Secret, а также impersonate пользователей. Право `impersonate` — это возможность выдать себя за кого угодно (например, за cluster-admin), и это классический путь эскалации. Дальше смотрим, за кого можно выдать себя.

## Анонимный доступ

Если API server запущен с `--anonymous-auth=true` (исторически бывало), неаутентифицированные запросы получают группу `system:unauthenticated`. Обычно ей ничего не разрешено, но иногда RBAC-привязка случайно даёт ей права (например, на discovery или на чтение чего-то). Проверяй анонимный доступ: `curl -k https://<api>:6443/api` без токена. Это частая находка в неправильно настроенных кластерах и в managed-кластерах с нестандартными настройками.

## Impersonation

Право `impersonate` (users, groups, serviceaccounts) позволяет выполнять запросы от имени другого principal. Если SA может impersonate cluster-admin, эскалация тривиальна. Impersonation используется для отладки, но выдаётся слишком широко. Проверяй RBAC на `impersonate`: это один из самых прямых путей к админу. Плюс есть `--as` и `--as-group` у kubectl, которые работают при наличии права.

## Aggregation и APIService

API server умеет агрегировать дополнительные API через APIService: сторонний сервер регистрируется как расширение API (metrics-server, custom metrics, некоторые операторы). Агрегированный API server доверяет запросу, пришедшему от основного, и часто не проверяет пользователя сам. Если ты можешь создать APIService, указывающий на подконтрольный сервер, ты получаешь все запросы, проходящие через него, включая токены. Это тонкий, но мощный вектор.

## Abuse: exec, port-forward, attach

Права `pods/exec`, `pods/port-forward`, `pods/attach` дают доступ внутрь контейнеров и к их сети. Через exec можно выполнить команду в чужом Pod, через port-forward — дотянуться до сервисов внутри кластера. Часто эти права выданы широко (для отладки), и они равны доступу к данным и токенам подов. Проверяй, у кого есть эти права: они не выглядят как «админские», но дают много.

## Типовые мисконфиги

| Мисконфиг | Последствие | Как искать |
|---|---|---|
| Анонимный доступ включён | доступ без аутентификации | флаг/запрос |
| Право impersonate | выдача за админа | RBAC |
| Широкий exec/port-forward | доступ к подам | RBAC |
| Можно создать APIService | перехват запросов | RBAC на apiservices |
| Слабые SA-токены | кража токена | срок/аудитория |
| Аудит выключен | слепые зоны | audit policy |

## Полный прогон: от токена к контролю

Шаги. Первый: проверить, кто ты (`kubectl auth whoami`). Второй: перечислить права (`auth can-i --list`). Третий: искать impersonate, exec, port-forward, create на RBAC/APIService. Четвёртый: при impersonate — выдать себя за cluster-admin. Пятый: при exec — войти в под с интересным SA. Шестой: при APIService — зарегистрировать перехват. Седьмой: закрепиться (новый SA/токен) и учесть аудит.

## Инструменты и команды

Полезны: `kubectl auth can-i --list`, `kubectl auth whoami`, `kubectl get --raw`, `kubectl --as=... --as-group=...`, `kubectl exec`, `kubectl port-forward`, `kubectl create --raw /apis/...`. Для анонимного доступа — curl к API. Для RBAC-разведки — `kubectl get rolebindings,clusterrolebindings -o yaml`, инструменты вроде `rbac-tool`/`kubectl-who-can`.

## OPSEC и детект

Все запросы к API server логируются (если включён audit). Impersonation виден в аудите как `impersonatedUser`. Создание APIService, exec в поды и port-forward — заметные события. Тихий сценарий — читать то, к чему есть прямой доступ, без impersonation и exec. Если аудит выключен, следов меньше, но это и признак слабой защиты.

## Частые вопросы

Нужен ли токен? Да, либо анонимный доступ. Даёт ли impersonate админа? Если можно impersonate админа — да. Виден ли exec? Да, в аудите. Помогает ли OIDC? Да, как альтернативная аутентификация. Оставляет ли след? Да, при включённом аудите.

## Что не сработает

Строгий RBAC без impersonate и exec ограничит эскалацию. Анонимный доступ выключен — не пройдёт. Создание APIService требует прав, которых обычно нет. И без аудита ты не узнаешь, что тебя засекли, но и защита слепа.

## Разбор кейса: impersonate у приложения

История из практики. Service account приложения имел право impersonate групп — «для интеграции с RBAC». Атакующий, получив токен SA через SSRF, выдал себя за группу `system:masters` и стал cluster-admin. Урок: impersonate — это право администратора, замаскированное под отладочное; проверяй его в первую очередь.

## Что мы теперь знаем

1. API server — единственная точка управления; всё проходит через authn + authz.
2. Анонимный доступ (если включён) даёт запросы без аутентификации.
3. Право impersonate позволяет выдать себя за другого и часто ведёт к админу.
4. Aggregation/APIService может перехватывать запросы, включая токены.
5. exec/port-forward/attach дают доступ внутрь подов и к их сети.

## Discovery, метрики и утечки через API

API server отдаёт не только объекты, но и discovery-информацию: список API-групп, ресурсов, версий, а также метрики и healthz. Даже с минимальными правами discovery бывает открыт и раскрывает, какие CRD и операторы установлены. Метрики (`/metrics`) иногда доступны анонимно и показывают нагрузку, версии, внутренние адреса. Плюс API server проксирует запросы к сервисам (`/api/v1/namespaces/<ns>/services/<svc>:<port>/proxy/`) — если это разрешено, ты ходишь во внутренние сервисы от имени API server. Проверяй discovery и proxy-эндпоинты: они дают разведку и, иногда, доступ.

## Токены service account и аудитории

Токены SA выдаются как JWT и подписываются ключом кластера; в новых версиях они привязаны к аудитории и сроку (projected tokens). Старые долгоживущие токены (в Secret `type: kubernetes.io/service-account-token`) всё ещё встречаются и дают постоянный доступ. Если у тебя есть токен SA, проверь его права через `auth can-i --list` и срок жизни. Кража токена — самый частый способ получить доступ к API server, поэтому ищи токены в подах, в логах и в смонтированных volumes.

## Итог по API server

API server — это центр кластера, и атака здесь идёт по двум линиям: аутентификация (токены, анонимный доступ) и авторизация (impersonate, exec, RBAC). Ищи impersonate в первую очередь — он превращает рядовой токен в админа. Затем — exec/port-forward и proxy-эндпоинты. И помни про аудит: если он включён, твои действия видны, поэтому точный доступ лучше массового перебора прав.

## Практический чек-лист по API server

Начни с `kubectl auth whoami` и `auth can-i --list`: пойми, кто ты и что можешь. Ищи в правах impersonate, exec, port-forward, create на RBAC и APIService, proxy на services. Проверь анонимный доступ отдельным запросом без токена. Посмотри discovery и метрики: они раскрывают CRD и внутренние адреса. Затем проверь токены SA: срок жизни и аудиторию. И оцени аудит кластера: включён ли он и что в него попадает. Приоритет — impersonate: если он есть, эскалация почти решена, и остальное можно не искать.

## Чего ожидать на практике

Самая частая находка — широкие права на exec/port-forward у сервисных аккаунтов «для отладки», которые дают вход в поды и доступ к их токенам. Вторая — impersonate, замаскированный под интеграционную возможность. Третья — долгоживущие токены SA в Secrets, которые дают постоянный доступ. Поэтому в первую очередь смотри RBAC: impersonate, exec, create на RBAC/APIService. Анонимный доступ — редкость в managed-кластерах, но в самосборных встречается, и его стоит проверить одним запросом.

## Коротко о приоритетах

Если времени мало, проверь impersonate и exec: они дают админа и доступ к подам. Анонимный доступ и APIService — реже, но проверяются одним запросом. RBAC — самое ценное, что можно прочитать с рядовым токеном.
