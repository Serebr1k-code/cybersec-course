## Вопрос, с которого всё начинается

Ты находишь ключ и endpoint Azure OpenAI в конфиге приложения. Вопрос: что даёт этот ключ, к каким моделям он открывает доступ, можно ли через prompt injection вытащить системные инструкции или чужие данные, и как злоупотребить квотой. Начнём с того, что у Azure AI-сервисов, как и у Cosmos, есть ключ data-plane, который открывает API в обход ролей.

## Что такое Azure AI Services

Azure AI Services (бывшие Cognitive Services) — семейство API: Vision, Speech, Language, Translator, Document Intelligence, Azure OpenAI. Каждый ресурс имеет endpoint и ключи доступа. Приложение вызывает сервис, передавая ключ в заголовке. Альтернатива — Entra ID и RBAC (роль Cognitive Services User). Ключ и Entra — снова два независимых пути. Azure OpenAI — самый интересный: за одним ресурсом стоят deployments моделей, и ключ открывает их все.

## Сквозной пример: ключ Azure OpenAI

Смотрим утёкший конфиг:
```
$ cat .env
AZURE_OPENAI_ENDPOINT=https://acme-openai.openai.azure.com/
AZURE_OPENAI_KEY=EXAMPLEnotarealkey0123456789
$ curl -s $AZURE_OPENAI_ENDPOINT/openai/deployments?api-version=2024-02-01 \
  -H "api-key: $AZURE_OPENAI_KEY" | jq ".data[].id"
"gpt-4o"
"text-embedding-3-large"
```
Ключ открыл список deployments. Дальше можно вызывать модели, а через них — пытаться вытащить данные и инструкции приложения.

## Ключи и endpoints

У ресурса два ключа (для ротации) и один endpoint. Ключ даёт доступ к API data-plane: генерация, embeddings, распознавание. Он не привязан к пользователю и не различает роли внутри ресурса. Если приложение кладёт ключ в клиент (мобильное, веб), ключ считается публичным. Практический шаг после утечки: перечислить deployments/модели, оценить квоты и стоимость, проверить, нет ли за ключом доступа к данным.

## Entra ID и RBAC

Второй путь — Entra ID с ролями Cognitive Services User / OpenAI User на ресурс. Тогда токен живёт недолго и привязан к principal-у. Для атакующего это означает: если local auth отключён, ключ не сработает, и остаётся либо украсть токен пользователя/managed identity, либо заставить сервис выполнить запрос под своей identity. Часто в тенантах local auth включён, и ключ из конфига работает — проверяй в первую очередь.

## Prompt injection и exfil

Если за ключом стоит приложение (чат-бот, RAG), ключ даёт возможность говорить с моделью напрямую, минуя бизнес-логику. Это позволяет обойти guardrails, вытащить системный промпт, а через RAG — чужие документы, если они попадают в контекст. Прямой prompt injection — это когда ввод пользователя меняет поведение модели; косвенный — когда вредоносный текст лежит в документе, который модель читает. Оба вектора превращают «ключ к модели» в «доступ к данным приложения».

## Квоты, стоимость и abuse

У ресурса есть квоты (requests/tokens в минуту) и стоимость. Украденный ключ можно использовать для бесплатного инференса, для перебора, для генерации контента или для майнинга внимания модели (resource abuse). Это не кража данных, а финансовый ущерб и нарушение ToS. Проверяй квоты: они показывают, насколько «дорогой» ресурс и сколько можно выжать до обнаружения.

## Типовые мисконфиги

| Мисконфиг | Последствие | Как искать |
|---|---|---|
| Ключ в клиенте/репо | abuse и утечка | grep endpoint/key |
| Local auth включён | обход RBAC | свойства ресурса |
| Нет ограничения по сети | доступ извне | firewall ресурса |
| RAG без фильтрации | exfil документов | код приложения |
| Нет логирования запросов | незаметный abuse | диагностика |
| Избыточная квота | крупный abuse | квоты ресурса |

## Полный прогон: от ключа к моделям и данным

Шаги. Первый: подтвердить ключ и endpoint. Второй: перечислить deployments и модели. Третий: оценить квоты и стоимость. Четвёртый: если есть приложение — попробовать prompt injection и вытащить промпт/данные. Пятый: проверить, есть ли за ресурсом доступ к хранилищу (RAG). Шестой: зафиксировать и учесть, что запросы могут логироваться.

## Инструменты и команды

Полезны: `az cognitiveservices account list`, `az cognitiveservices account keys list`, прямые REST-запросы к `/openai/deployments`, SDK (`openai`, `azure-ai-*`). Для prompt injection — обычный HTTP-клиент и набор техник из урока про prompt injection. Для поиска ключей — grep по конфигам и CI.

## OPSEC и детект

Azure AI пишет диагностические логи; обращения по ключу видны как запросы к ресурсу. Всплеск запросов (abuse) заметен по метрикам и стоимости. Тихий сценарий — несколько запросов к нужному deployment. Если включён Defender for AI, подозрительные промпты и утечки дают алерт.

## Частые вопросы

Работает ли ключ при отключённом local auth? Нет. Даёт ли ключ доступ к другим ресурсам? Нет, только к этому. Можно ли вытащить обучающие данные? Обычно нет, только то, что попало в контекст. Помогает ли firewall? Да, ограничивает источник. Оставляет ли след? Да, запросы и метрики.

## Что не сработает

Отключённый local auth не даст использовать ключ. Firewall не пустит с незнакомого IP. Prompt injection не поможет, если модель не имеет доступа к данным. И если ресурс не связан с приложением, ключ даёт только инференс.

## Разбор кейса: ключ в frontend

История из практики. Команда встроила ключ Azure OpenAI в веб-приложение, чтобы «быстрее». Ключ достали из бандла, и через него стали бесплатно гонять модель и обходить guardrails чат-бота, вытаскивая системные инструкции и куски базы знаний. Урок: ключ AI-сервиса в клиенте — это открытый API с твоим счётом; для клиентов нужен прокси на сервере с аутентификацией пользователя.

## Что мы теперь знаем

1. Azure AI-сервисы аутентифицируются ключом или Entra-RBAC — независимые пути.
2. Ключ открывает data-plane API и все deployments ресурса.
3. Прямой и косвенный prompt injection превращают доступ к модели в доступ к данным приложения.
4. Украденный ключ — это финансовый abuse и обход guardrails.
5. Firewall и отключение local auth ограничивают утечку ключа.

## Responsible AI и guardrails

Azure AI-сервисы поддерживают content filters и guardrails, которые ограничивают генерацию нежелательного контента. Для атакующего guardrails — это то, что нужно обойти при prompt injection. Обходы бывают техническими (кодировки, роли, разбиение инструкции на части) и логическими (переопределение задачи, «представь, что ты...»). Важно понимать: guardrails защищают модель, но не приложение. Если за моделью стоит RAG с доступом к документам, обход guardrails даёт доступ к данным, которые модель видит в контексте, — и это уже утечка, а не просто генерация.

## Embeddings и векторные базы

Многие AI-приложения строят RAG: документы разбиваются на куски, превращаются в embeddings и складываются в векторную базу. Embeddings считаются «производными» от данных, но их можно использовать для поиска похожих фрагментов и для частичного восстановления исходного текста. Если у тебя есть ключ к ресурсу embeddings, ты можешь генерировать вектора для своих запросов и сравнивать их с базой, вытаскивая содержимое. Плюс сама векторная база (часто это тот же Azure AI Search) может быть открыта и содержать исходные документы.

## Квоты, стоимость и abuse

У AI-ресурса есть квоты на запросы и токены в минуту, а также стоимость за использование. Украденный ключ позволяет бесплатно пользоваться моделями, обходить бизнес-логику и наращивать расходы владельца. Это отдельный класс ущерба: не кража данных, а abuse ресурса и финансовые потери. Проверяй квоты и текущее потребление — они показывают, насколько ресурс нагружен и сколько можно выжать до обнаружения. Всплеск запросов обычно замечают по метрикам и по счёту, поэтому abuse почти всегда детектируется, вопрос лишь в скорости.

## Развёртывания моделей и версии

У ресурса Azure [OI] модели не «включены» сами по себе: их разворачивают как deployments с именем и версией модели. Ключ открывает все deployments, а значит, даёт доступ к разным моделям, включая дорогие и мощные. Разные версии модели ведут себя по-разному, и то, что заблокировано на одной, может пройти на другой. Если приложение ходит к конкретному deployment, атакующий с ключом может обратиться к тому же ресурсу напрямую и выбрать модель без guardrails приложения. Проверяй список deployments, их модели и версии: это карта возможностей ресурса. Иногда за одним ресурсом стоит несколько приложений, и ключ открывает их все сразу.

## Отличие ключа от токена

Ключ ресурса долгоживущий и не привязан к пользователю: пока его не ротировали, он работает. Токен Entra живёт минуты и привязан к principal-у, поэтому его нужно добывать заново. Из этого следует практика: если в тенанте включён local auth, ключ из конфига — самый быстрый путь; если выключен, ищи токен managed identity сервиса. Проверяй оба варианта параллельно, потому что один мисконфиг (включённый local auth) полностью меняет приоритеты и делает длинную цепочку с токеном ненужной.
