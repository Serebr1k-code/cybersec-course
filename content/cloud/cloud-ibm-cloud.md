## Вопрос, с которого всё начинается

В CI-конфиге ты находишь переменную `IBMCLOUD_API_KEY`. Рядом — `IBMCLOUD_ACCOUNT_ID` и имя ресурсной группы. Приложение развёрнуто в IBM Cloud и работает с объектным хранилищем. Вопрос: что даёт этот ключ, как понять его права и как добраться до бакетов, не имея доступа к консоли? IBM Cloud встречается реже AWS, поэтому важно уметь разбирать его с нуля.

## IBM Cloud и его место

IBM Cloud — облако IBM, сильное в корпоративном сегменте: банки, госсектор, интеграция с мейнфреймами и Watson. IAM здесь построен вокруг аккаунта, ресурсных групп, access groups и service IDs. Модель близка к Azure: есть account (аналог подписки), resource group (контейнер ресурсов), access group (набор прав для набора субъектов) и service ID (технический «пользователь» для приложений). Понимание этой иерархии — ключ к разбору прав.

## Сквозной пример: утёкший API-ключ

Ключ IBM выглядит как длинная строка. Вместе с account ID он образует рабочую пару:
```
$ env | grep IBMCLOUD
IBMCLOUD_API_KEY=Kx8vExampleApiKeyValue0000000000000000000
IBMCLOUD_ACCOUNT_ID=abc123def456abc123def456abc123de
```
API-ключ может принадлежать пользователю или service ID. От того, кому он принадлежит, зависят права: ключ service ID несёт права этого service ID, ключ пользователя — права пользователя. Проверить, кто ты, можно командой `ibmcloud iam api-key-details` или через REST-запрос к `/v1/apikeys`.

## IAM-модель IBM: account, resource group, access group

Иерархия такая: account → resource groups → ресурсы. Политики (access policies) привязываются к субъекту и определяют роль на ресурсе. Роли бывают платформенные (`Viewer`, `Editor`, `Operator`, `Administrator`) и сервисные (`Reader`, `Writer`, `Manager`). Широкий доступ — `Administrator` на весь аккаунт. Access group собирает субъекты и политики: если ключ входит в мощную группу, он наследует её права. При разборе ищи ключ в списке членов access group.

## Service ID, пользователи и trusted profiles

Три типа субъектов. Пользователь — человек с IBMid. Service ID — технический аккаунт без пароля, аутентифицируется API-ключом; именно service ID чаще всего утекает из CI. Trusted profile — способ выдать права «без ключа»: доверенный субъект (compute resource, service ID, федерация) получает временные токены. Ошибка конфигурации — trusted profile с широким условием (например, доверяет всем service ID в аккаунте), что делает любой из них носителем прав профиля.

## API-ключи: где живут и как утекают

IBM API-ключи утекают из `.env`, CI-переменных, `~/.bluemix/config.json`, Terraform-состояния и логов `ibmcloud` CLI. Файл `~/.bluemix/config.json` содержит account ID, region и имя пользователя. Ключ часто лежит рядом в переменной окружения. Поиск по репозиторию — grep по `IBMCLOUD_API_KEY` и `apikey`. Помни: ключ service ID может не иметь срока годности, поэтому действует до ручного отзыва.

## COS: HMAC-ключи и публичный доступ

IBM Cloud Object Storage (COS) — S3-совместимое хранилище. Доступ бывает двумя путями: через IAM (сервисные роли) или через HMAC-ключи (Access Key ID + Secret, как в S3). HMAC-ключи создаются на уровне аккаунта или service ID и дают прямой доступ к бакетам. Бакеты бывают приватными и публичными; публичный бакет отдаёт объекты по прямому URL. Найденный HMAC-ключ проверяют через любой S3-клиент, указав endpoint региона IBM.

## Trusted profiles и compute resource identities

Чтобы приложения не хранили ключи, IBM даёт trusted profiles: compute-ресурс (например, VM или кластер) получает временный токен на основе доверия. Условие доверия задаётся правилом. Если правило слишком широкое («любой compute в ресурсной группе»), то любой поднятый там ресурс получает права профиля. Это та же проблема, что dynamic group в OCI: узкое правило ссылается на конкретный ресурс, широкое — на группу.

## Типовые мисконфиги IBM Cloud

| Мисконфиг | Последствие | Как искать |
|---|---|---|
| `Administrator` на аккаунт | полный админ | разбор политик |
| Ключ service ID без ротации | долгий доступ | возраст ключа |
| Широкий trusted profile | любой ресурс = права | условия доверия |
| Публичный COS-бакет | утечка данных | ACL бакета |
| HMAC-ключ в репозитории | прямой доступ к COS | grep по Access Key |
| Ключ в `~/.bluemix` | полный доступ CI | разбор конфига |

## Полный прогон: от ключа к захвату

Шаги. Первый: определить владельца ключа (`ibmcloud iam api-key-details`). Второй: перечислить ресурсные группы и политики (`ibmcloud iam access-groups`, `ibmcloud resource groups`). Третий: если есть доступ к COS — перечислить бакеты (`ibmcloud cos buckets`) и выкачать данные. Четвёртый: если есть права `Administrator` — создать нового service ID с ключом для персистентности. Пятый: если прав мало, искать trusted profile и способ получить его токен.

## Инструменты и команды

Основной инструмент — `ibmcloud` CLI. Полезные команды: `ibmcloud iam api-key-details <key>` (владелец), `ibmcloud iam service-ids` (service ID), `ibmcloud iam access-groups` (группы), `ibmcloud resource groups` (ресурсные группы), `ibmcloud cos buckets` (бакеты), `ibmcloud account users` (пользователи). Для COS через HMAC подходит любой S3-клиент (`aws s3 --endpoint-url ...`). Terraform-провайдер IBM тоже раскрывает структуру ресурсов.

## OPSEC и детект

IBM Cloud Activity Tracker пишет события IAM и сервисов: `iam-identity.create-api-key`, `cloud-object-storage.object.read`. События содержат initiator (кто), target и время. Массовые `list`-вызовы и создание ключей хорошо видны. Если задача — тихо прочитать бакет, ограничься одним `get` вместо перебора. Помни: API-ключи имеют метку последнего использования — админ может увидеть аномалию.

## Разведка без ключа

Даже без ключа IBM Cloud даёт зацепки. Публичные COS-бакеты видны по URL вида `https://<bucket>.s3.<region>.cloud-object-storage.appdomain.cloud`. Регион и endpoint раскрываются в документации и клиентском JS. Account ID иногда утекает в публичных логах и статус-страницах. Собрав endpoint и имя бакета, можно проверять публичность пассивно, без аутентификации.

## Что не сработает

Ключ service ID с узкой политикой вернёт `403` на лишних действиях. Публичные бакеты часто пусты. Trusted profile с корректным условием не даст получить токен «чужому» ресурсу. HMAC-ключ действует только в своём регионе и на свои бакеты. И если ключ отозван, CLI вернёт ошибку аутентификации — нужен другой креденшел.

## Разбор кейса: ключ в Terraform-состоянии

Типичная история: команда управляет IBM Cloud через Terraform, а состояние лежит в бакете или в репозитории. В состоянии оказывается `ibm_iam_api_key` с реальным значением. Кто получил доступ к состоянию — получил ключ. Поэтому ищи не только `.env`, но и `terraform.tfstate`, `*.tfvars` и бэкенд-бакеты. В IBM-провайдере часто встречается `ibm_resource_key` — это тоже креденшел сервиса (например, HMAC для COS).

## Частые вопросы

Можно ли работать без API-ключа? Да, через trusted profile и временные токены. Что если ключ только на чтение? Тогда смотри trusted profiles и access groups — возможно, есть путь к временному токену с большими правами. Как быстро проверить владельца ключа? `ibmcloud iam api-key-details` или REST `/v1/apikeys`. Опасен ли публичный COS-бакет? Да: любой читает объекты, а иногда и пишет. Что делать, если ключ отозван? Искать HMAC-ключ COS или trusted profile.

## Сравнение с Azure и AWS

IBM Cloud ближе всего к Azure. Account ≈ subscription, resource group ≈ resource group, access group ≈ роль/группа, service ID ≈ service principal, trusted profile ≈ managed identity/federated credential, COS ≈ Blob/S3, Activity Tracker ≈ Activity Log/CloudTrail. Поняв это, ты переносишь навыки Azure-пентеста на IBM почти без изменений — меняются лишь имена CLI-команд и API.

## Автоматизация разведки

Для IBM Cloud нет такого зрелого набора инструментов, как `cloudfox`/`pacu` для AWS, поэтому разведку часто пишут на месте. Минимальный скрипт: аутентификация, затем обход ресурсных групп и политик, выгрузка результатов в JSON. Полезно логировать владельца ключа, его группы и максимальную роль. Это даёт карту прав за десяток запросов — без шумного перебора всех сервисов аккаунта.

## Практический чек-лист пентеста IBM Cloud

Порядок действий. Один: подтвердить ключ (`ibmcloud iam api-key-details`). Два: выяснить владельца — пользователь или service ID. Три: собрать access groups и понять максимальную роль. Четыре: проверить trusted profiles на широкие условия. Пять: перечислить COS-бакеты и оценить их публичность. Шесть: если прав хватает — прочитать данные, не создавая новых ключей. Семь: при необходимости зафиксировать персистентность новым service ID. Минимизируй число вызовов: Activity Tracker видит всё.

## Что мы теперь знаем

1. API-ключ IBM принадлежит либо пользователю, либо service ID — от этого зависят права.
2. Иерархия: account → resource group → ресурс; роли платформенные и сервисные.
3. Access group собирает права; trusted profile выдаёт временные токены без ключа.
4. COS доступен через IAM или через HMAC-ключи (S3-совместимо).
5. Широкий trusted profile и публичный бакет — типовые точки эскалации и утечки.
