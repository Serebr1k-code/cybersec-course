## Вопрос, с которого всё начинается

Ты находишь доступ к CyberArk — корпоративной системе управления привилегированным доступом (PAM). В ней лежат пароли администраторов домена, root-учётки серверов, креды баз данных. Вопрос: как через API получить эти учётки, что мешает их «просто прочитать» и как обойти контроль сессий? CyberArk — высшая цель в корпоративной среде.

## CyberArk и PAM

PAM (Privileged Access Management) — класс систем, которые хранят и выдают привилегированные учётки, а также контролируют их использование. CyberArk — лидер рынка. Он хранит пароли в «сейфах», выдаёт их по запросу и может изолировать сессии (пользователь работает с сервером через прокси CyberArk, не видя пароль). Для атакующего PAM ценен тем, что содержит креды ко всей критичной инфраструктуре.

## Сквозной пример: доступ к API

CyberArk предоставляет API (PVWA REST):
```
$ curl -s https://pvwa.company.com/PasswordVault/api/Accounts \
    -H "Authorization: Bearer <token>"
```
Ответ — список accounts (привилегированных учёток). Аутентификация даёт токен, которым запрашивают пароли: `POST /api/Accounts/{id}/Password/Retrieve`. Если у токена есть права на нужные сейфы, пароли возвращаются. Ключевой вопрос — какие сейфы и accounts доступны этому пользователю.

## Сейфы и accounts

CyberArk организует учётки в сейфы (Safes) с правами на уровне сейфа и объекта. Права бывают: Retrieve (получить пароль), List (видеть), Use (использовать без просмотра). Атакующий ищет сейфы с правами Retrieve на критичные accounts (domain admin, root, service accounts). Часто права выданы шире, чем нужно: разработчик с доступом к сейфу «dev» может видеть и прод-учётки, если сейфы не разделены.

## Аутентификация и CCP/CP

CyberArk поддерживает разные способы: логин в PVWA (веб), API-токены, Central Credential Provider (CCP) — сервис, через который приложения получают пароли без человека. CCP-запросы аутентифицируются сертификатом приложения или IP-адресом. Если CCP настроен на доверие по IP, атакующий с внутреннего адреса может запросить пароли. Это частая слабость: защита по IP, а не по строгой идентичности.

## Обход и захват

Пути. Первый: слабые права на сейфы — Retrieve на лишние accounts. Второй: CCP/CP с доверием по IP — запрос паролей с разрешённого адреса. Третий: утёкший API-токен или сессия администратора. Четвёртый: обход session isolation — если сессия не изолирована, пароль виден. Пятый: атака на сам сервер CyberArk (высокая ценность, но хорошо защищён). Цель — получить привилегированные креды.

## Session isolation

CyberArk может изолировать сессии: пользователь подключается к серверу через прокси, а пароль вводится автоматически и не показывается. Это защищает от кражи пароля, но не от действий в сессии: атакующий, получивший сессию, может выполнять привилегированные операции. Обход — если изоляция отключена для части accounts или если можно подключиться напрямую в обход PAM (если пароль известен/сменён вне PAM).

## Типовые мисконфиги

| Мисконфиг | Последствие | Как искать |
|---|---|---|
| Слишком широкие права сейфов | доступ к лишним учёткам | разбор прав |
| CCP доверяет по IP | запрос паролей с адреса | конфиг CCP |
| API-токен в репозитории | доступ к API | grep cyberark |
| Изоляция сессий отключена | пароль виден | настройки |

| Общие сейфы для dev/prod | утечка прод-кред | структура сейфов |

## Полный прогон: от доступа к паролям

Шаги. Первый: получить доступ к PVWA API (токен или сессия). Второй: перечислить accounts (`GET /api/Accounts`). Третий: определить доступные сейфы и права. Четвёртый: запросить пароли (`POST .../Password/Retrieve`). Пятый: использовать привилегированные учётки (домен-админ, root, БД). Шестой: закрепиться. Седьмой: учесть аудит — retrieve пароля логируется.

## Инструменты и команды

REST API CyberArk (PVWA): `/api/Accounts`, `/api/Accounts/{id}/Password/Retrieve`, `/api/Safes`. CCP API: `/AIMWebService/api/Accounts`. Через `curl` с токеном/сертификатом. Для разведки — перебор сейфов и accounts. Для использования полученных паролей — обычные инструменты (psexec, ssh, sqlplus). Официальный CLI/PS модуль CyberArk тоже доступен.

## OPSEC и детект

CyberArk ведёт подробный аудит: кто, когда и какой пароль запросил, какие сессии открывал. Retrieve привилегированного пароля — громкое событие, часто с алертом. Изоляция сессий и запись сессий (recording) фиксируют действия. Тихий сценарий — запросить минимум паролей и использовать их аккуратно. Помни: PAM существует именно для того, чтобы такие действия были заметны.

## Частые вопросы

Можно ли прочитать пароль без retrieve? Нет, если права только List/Use. Обходит ли session isolation кражу пароля? Да, пароль не показывается, но действия в сессии видны. Опасен ли CCP? Да, если доверяет по IP. Как эскалировать? Через широкие права сейфов или слабый CCP. Как защититься? Минимум прав, строгая идентичность в CCP, изоляция и запись сессий, аудит.

## Что не сработает

Права List без Retrieve не дадут пароль. Session isolation скроет пароль. CCP с проверкой сертификата приложения не примет запрос по IP. И если аудит включён, извлечение привилегированного пароля заметят.

## Разбор кейса: CCP доверяет по IP

История из практики. Приложения получали пароли БД через CCP, который доверял запросам с определённого диапазона внутренних адресов. Атакующий, оказавшись на машине в этом диапазоне (через компромисс обычного сервера), отправил CCP-запрос и получил пароль привилегированной учётки БД. Никакого доступа к самому CyberArk не потребовалось. Доверие по IP — распространённая слабость PAM: адрес подделать или занять проще, чем украсть сертификат приложения.

## CyberArk и облачные креды

CyberArk хранит не только доменные учётки, но и креды облаков: ключи AWS, service principals Azure, сервисные аккаунты GCP. Часто именно там лежат «break-glass» креды для аварийного доступа к облаку. Получив их, атакующий обходит все обычные ограничения. Поэтому PAM — мост и в корпоративную сеть, и в облако одновременно. Его захват даёт доступ к обоим мирам.

## Потребители PAM

Как и Vault, CyberArk имеет потребителей: скрипты администрирования, CI/CD, системы мониторинга. Они аутентифицируются в PAM через API-токены, сертификаты или CCP. Эти креденшелы часто лежат в конфигах и репозиториях. Атаковать потребителя проще, чем PAM: украденный API-токен даёт те же права, что и у легитимного потребителя. При пентесте ищи, кто и как ходит в CyberArk.

## Практический чек-лист пентеста CyberArk

Порядок действий. Один: получить доступ к PVWA API или CCP. Два: перечислить accounts и сейфы. Три: определить права (Retrieve/List/Use). Четыре: запросить пароли критичных учёток. Пять: использовать их (домен, root, БД, облако). Шесть: проверить session isolation. Семь: закрепиться. Восемь: учесть аудит — retrieve паролей логируется.

## Что дальше в дереве

Модуль секрет-менеджеров завершён. Этим закрывается большой блок облачной идентичности, секретов и CI/CD. Дальше дерево уходит в постэксплуатацию и детект: персистентность, exfiltration и обход мониторинга. А пока главное: CyberArk хранит креды ко всей инфраструктуре, и доступ к API с широкими правами равен доступу к ним.

## CyberArk и контроль сессий

CyberArk не только хранит пароли, но и контролирует их использование: PSM (Privileged Session Manager) изолирует сессии и записывает их. Пользователь подключается к серверу через прокси, не видя пароль. Для атакующего это значит: даже с доступом к сейфу можно не получить пароль, а только изолированную сессию. Обход — если для части accounts изоляция отключена или если пароль известен вне PAM. Записи сессий при этом фиксируют все действия, что помогает защитникам.

## Защита PAM

Меры: минимум прав на сейфы (Retrieve только тем, кому действительно нужен пароль), строгая идентичность в CCP/CP (сертификаты приложений вместо доверия по IP), обязательная изоляция и запись сессий для критичных учёток, аудит и алерты на retrieve привилегированных паролей, ротация паролей. Разделение сейфов по средам (dev/prod) и ролям. Эти меры делают PAM действительно барьером, а не просто хранилищем.

## Итоговая цепочка захвата PAM

Соберём сценарий. Атакующий получает API-токен CyberArk из конфига скрипта администрирования. Токен имеет право Retrieve на сейф Domain-Admins. Он запрашивает пароль break-glass-админа и получает его. С этим паролем он входит в домен как администратор, создаёт свою учётку и закрепляется. Вся цепочка держится на утёкшем токене с широкими правами. Минимизация прав на сейфы и строгая защита токенов разрывают её. Даже одно ограничение — токен без права Retrieve или сейф без break-glass-учётки — остановило бы атаку на первом шаге. Именно поэтому PAM строят по принципу минимальных прав и записывают каждое извлечение пароля.

## Что мы теперь знаем

1. CyberArk/PAM хранит привилегированные учётки в сейфах с правами Retrieve/List/Use.
2. API-токен или сессия с широкими правами даёт доступ к паролям.
3. CCP с доверием по IP — частая слабость.
4. Session isolation скрывает пароль, но не действия.
5. Аудит PAM делает извлечение привилегированных паролей заметным.
