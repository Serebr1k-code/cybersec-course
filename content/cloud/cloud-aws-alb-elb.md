## Вопрос, с которого всё начинается

Приложение за ALB требует аутентификации на уровне правил: если путь `/admin`, то проверяется заголовок или cookie. Ты отправляешь `GET /admin/../public HTTP/1.1` — и попадаешь в админку без проверки. Вопрос: почему балансировщик и бэкенд по-разному разобрали один запрос, и как это превращается в устойчивый обход?

## Что такое ELB/ALB/NLB

ELB (Elastic Load Balancing) — семейство балансировщиков. ALB (Application Load Balancer) работает на уровне HTTP: понимает пути, заголовки, хосты, маршрутизирует по правилам. NLB (Network Load Balancer) работает на уровне TCP/UDP: просто передаёт соединения, не разбирая HTTP. ELB Classic — устаревший. Разница важна: ALB можно «запутать» HTTP-разбором, NLB — нет.

## Сквозной пример: listener rules

Смотрим правила listener-а:
```
$ aws elbv2 describe-rules --listener-arn arn:aws:elasticloadbalancing:...:listener/app/acme/abc/def
{
  "Rules": [
    {"Priority": 1, "Conditions": [{"Field": "path-pattern", "Values": ["/admin*"]}],
     "Actions": [{"Type": "authenticate-oidc"}]},
    {"Priority": 2, "Conditions": [{"Field": "path-pattern", "Values": ["/*"]}],
     "Actions": [{"Type": "forward"}]}
  ]
}
```
Правило с `authenticate-oidc` ловит только путь, начинающийся с `/admin`. Всё остальное уходит в forward без аутентификации. Если бэкенд нормализует путь иначе, чем ALB, обход аутентификации становится тривиальным.

## Request smuggling на ALB

Smuggling (контрабанда запросов) — расхождение в разборе HTTP между балансировщиком и бэкендом. Классика: заголовки `Content-Length` и `Transfer-Encoding: chunked` вместе. ALB выбирает один способ, бэкенд — другой, и «лишний» запрос исполняется в контексте следующего пользователя. На AWS ALB есть собственные правила обработки (он отклоняет часть конфликтов), но при связке ALB→бэкенд с другим парсером окно остаётся. Ищи расхождения в трактовке `Transfer-Encoding`, дублирующихся заголовков, абсолютных URL.

## Health-checks и раскрытие бэкендов

ALB периодически проверяет бэкенды health-check-запросами. Если правило health-check указывает на путь, который отдаёт данные (например, `/debug` или `/metrics`), оно раскрывает внутренние сервисы. Кроме того, ответы health-check видны при переборе: разные коды на разные пути выдают карту бэкендов. Проверяй настройки target group: путь, интервал, ожидаемый код.

## NLB и его особенности

NLB не разбирает HTTP, поэтому smuggling к нему неприменим. Но NLB имеет свои особенности: сохраняет исходный IP клиента (что полезно для IP-allowlist-обхода — можно представиться «доверенным» адресом), поддерживает TLS-терминацию и cross-zone. Если бэкенд доверяет source IP, пришедшему «через NLB», это заблуждение: NLB передаёт настоящий адрес клиента, и allowlist по IP обходится через любой прокси.

## TLS и сертификаты

ALB/NLB терминируют TLS: сертификаты лежат в ACM. Ошибки: устаревшие протоколы/шифры, отсутствие HSTS, расхождение SNI. Если несколько сайтов на одном ALB, проверь, какой сертификат отдаётся на какой SNI — иногда раскрывается внутренний домен. Ищи также, не разрешён ли HTTP без редиректа на HTTPS.

## Типовые мисконфиги балансировщиков

| Мисконфиг | Последствие | Как искать |
|---|---|---|
| Правило аутентификации только на `/admin*` | обход через нормализацию пути | describe-rules |
| Расхождение парсинга CL/TE | request smuggling | ручной тест |
| Health-check на чувствительный путь | раскрытие | target group |
| Доверие source IP за NLB | обход allowlist | правила бэкенда |
| HTTP без редиректа | перехват/даунгрейд | listener |
| Широкий SNI с внутренним сертификатом | раскрытие доменов | openssl s_client |

## Полный прогон: от правил к обходу

Шаги. Первый: найти ALB (DNS, CNAME). Второй: выяснить правила (если есть права — describe-rules; иначе — поведением). Третий: определить, где аутентификация. Четвёртый: проверить нормализацию пути (`/admin/..`, `%2f`, двойные слеши). Пятый: тестировать smuggling (осторожно). Шестой: проверить health-check-пути. Седьмой: зафиксировать обход и его причину.

## Инструменты и команды

Полезны: `aws elbv2 describe-listeners/describe-rules`, `curl --path-as-is` (чтобы клиент не нормализовал путь), Burp для smuggling, `openssl s_client -servername` для SNI. Для проверки IP-allowlist — запросы через разные прокси. Важен `curl --path-as-is`: без него клиент сам схлопывает `..`, и ты не увидишь расхождение с ALB.

## OPSEC и детект

Smuggling-запросы и аномальные пути видны в access-логах ALB и WAF. Обход аутентификации оставляет 200 там, где ожидается 401/302 — заметно. Health-check-перебор даёт всплеск 404. Тихий сценарий: точечная проверка нормализации пути, без массового smuggling. Помни: ALB access logs пишут путь как его увидел ALB, а бэкенд может видеть иначе — расхождение в логах и есть след.

## Разведка без доступа

Без прав видно: CNAME на `*.elb.amazonaws.com`, заголовки ответа, поведение на разных путях. Коды 401/403/302 на `/admin` выдают наличие правила аутентификации. Ошибки раскрывают имена target group. По этому строится гипотеза о правилах.

## Частые вопросы

ALB уязвим к smuggling? Меньше, чем generic-прокси, но связка с бэкендом может расходиться. NLB разбирает HTTP? Нет. Можно ли обойти authenticate-oidc? Да, через расхождение путей. Health-check опасен? Может раскрывать сервисы. Помогает ли WAF? Частично, на edge.

## Что не сработает

Если правило аутентификации покрывает `/*`, обход через путь не поможет. Если ALB и бэкенд используют один и тот же строгий парсер, smuggling не проходит. NLB не даст smuggling вообще. И если бэкенд сам проверяет сессию, обход на уровне ALB бесполезен.

## Сценарий: обход админки через путь

Цепочка. Правило `path-pattern /admin*` включает OIDC. Отправляем `curl --path-as-is https://app.example.com/admin/..%2fadmin HTTP/1.1` — ALB видит путь, не начинающийся с `/admin`, и пропускает без аутентификации; бэкенд нормализует `..%2f` в `/admin/` и отдаёт админку. Аутентификация обойдена. Фиксируем: расхождение нормализации путей между ALB и бэкендом.

## Практический чек-лист пентеста балансировщиков

Порядок. Один: найти балансировщик и его тип. Два: собрать правила/поведение. Три: найти точки аутентификации. Четыре: проверить нормализацию путей. Пять: тестировать smuggling. Шесть: проверить health-checks. Семь: проверить TLS/SNI. Восемь: оценить логи ALB/WAF.

## Что мы теперь знаем

1. ALB разбирает HTTP и маршрутизирует по правилам; NLB — нет.
2. Аутентификация на уровне правил обходится расхождением нормализации путей.
3. Расхождение парсинга CL/TE ведёт к request smuggling.
4. Health-checks могут раскрывать внутренние сервисы.
5. Доверие source IP за NLB — заблуждение.
