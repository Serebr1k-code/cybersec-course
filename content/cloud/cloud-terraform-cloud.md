## Вопрос, с которого всё начинается

Ты находишь токен `TF_API_TOKEN` и адрес `https://app.terraform.io`. Вопрос: что даёт этот токен в Terraform Cloud, можно ли прочитать секретные переменные workspace, запустить `apply` с изменённым кодом и вытащить state? Ответ зависит от прав токена и от того, как настроены workspaces и агенты.

## Что такое Terraform Cloud

Terraform Cloud (TFC) и его self-hosted версия Terraform Enterprise — облачная плоскость для запуска Terraform. Ты подключаешь репозиторий (VCS), TFC при изменениях запускает `plan` и `apply` на своей инфраструктуре, хранит state и переменные. Рабочая единица — workspace: у него свои переменные, свой state, своя привязка к VCS и своя команда. Ключевой факт: apply выполняется не у тебя, а в TFC — с переменными, которые туда загружены.

## Сквозной пример: токен и переменные

Проверяем токен и читаем переменные workspace:
```
$ curl -s -H "Authorization: Bearer $TF_API_TOKEN" \
  https://app.terraform.io/api/v2/account/details | jq .data.attributes.username
"ci-bot"
$ curl -s -H "Authorization: Bearer $TF_API_TOKEN" \
  "https://app.terraform.io/api/v2/workspaces/ws-abc/vars" | jq ".data[].attributes | {key,category,sensitive}"
{"key":"AWS_SECRET_ACCESS_KEY","category":"env","sensitive":true}
{"key":"db_password","category":"terraform","sensitive":true}
```
API отдаёт имена и признак `sensitive`, но не значения секретных переменных. Однако право на запуск позволяет вытащить их через код в workspace.

## API-токены и права

TFC использует несколько типов токенов: user-токены (права пользователя), team-токены (права команды на конкретные workspaces), organization-токены. Права делятся на plan/read/write/admin. `write` позволяет менять workspace и запускать run; `admin` — управлять доступами. Токен CI-бота обычно имеет доступ к переменным и запуску apply. Утёкший write-токен — это возможность исполнить свой код в контексте workspace.

## Переменные и их утечка

Переменные бывают Terraform-переменными (`terraform`) и переменными окружения (`env`), секретные помечаются `sensitive`. Значения sensitive не показываются в UI и API, но передаются в run как `TF_VAR_*` или env. Значит, любой код, исполняемый в run, видит их. Способы вытащить: изменить Terraform-код в workspace (через VCS или через API), добавить шаг, печатающий окружение, или использовать `external`/`local-exec` для отправки env наружу.

## Run-триггеры и cross-workspace

Run-триггер запускает workspace B после apply в workspace A. Это создаёт зависимости между workspaces и каналами: успешный run в одном может запустить другой с другими правами. Если ты можешь изменить workspace A (например, его код), ты можешь инициировать цепочку, которая доберётся до workspace B с более широкими правами. Плюс state может передаваться между workspace через data sources — тоже канал.

## Remote state

TFC хранит state (включая секреты) и отдаёт его по API. Токен с правом чтения state выгружает все атрибуты: пароли, ключи, идентификаторы. Команда `terraform state pull` в remote-backend-режиме делает это штатно. State можно читать через API `GET /workspaces/:id/current-state-version` и скачивание артефакта.

## Агент-пулы и self-hosted runners

TFC может запускать runs в собственных агентах (agent pools) — это машины в твоей инфраструктуре. Тогда run исполняется на них с доступом к внутренней сети, а переменные и креды — на агенте. Компромисс агента даёт RCE в твоей сети. Плюс агент часто имеет доступ к облаку через instance profile — отдельный канал эскалации.

## Типовые мисконфиги TFC

| Мисконфиг | Последствие | Как искать |
|---|---|---|
| Write-токен в CI/репо | запуск своего кода | grep TF_API_TOKEN |
| Широкий доступ команды | чужие workspaces | team access |
| Sensitive-переменные + VCS-write | утечка секретов | vars + VCS |
| Run-триггеры без аудита | cross-workspace | triggers |
| State без ограничения доступа | чтение секретов | RBAC state |
| Публичный агент-пул | RCE в своей сети | agent pools |

## Полный прогон: от токена к секретам

Шаги. Первый: подтвердить токен (`/api/v2/account/details`). Второй: перечислить организации и workspaces. Третий: прочитать список переменных и найти sensitive. Четвёртый: определить, можешь ли менять код workspace (VCS-write или API-run). Пятый: добавить код, печатающий env/отправляющий его наружу. Шестой: запустить run и забрать значения. Седьмой: использовать креды, закрепиться.

## Инструменты и команды

Полезны: API `/api/v2/account/details`, `/api/v2/organizations`, `/api/v2/workspaces`, `/workspaces/:id/vars`, `/workspaces/:id/runs`, скачивание state. CLI: `terraform login`, `terraform workspace list`, `terraform state pull`. Для self-hosted — GraphQL (TFE) API.

## OPSEC и детект

TFC ведёт audit trail: кто читал переменные, кто запускал runs, кто менял конфигурацию. Запуск run с необычным кодом и массовое чтение state заметны. Run-триггеры создают цепочки, которые тоже логируются. Тихий сценарий — выгрузить state одного workspace, который уже содержит нужный секрет, без запуска кода.

## Частые вопросы

Можно ли прочитать sensitive-переменную по API? Напрямую нет — только имя и признак. Как вытащить значение? Через код в run или через state. Нужен ли VCS-доступ? Или API-run. Опасен ли state? Да, он содержит секреты. Что даёт агент-пул? RCE в своей сети.

## Что не сработает

Read-only токен без права запускать runs не даст вытащить sensitive-значения. Если переменные хранятся во внешнем secrets-провайдере, к которому у workspace нет доступа, — пусто. Запрет на изменение кода workspace закрывает путь через run. И если state шифруется ключом, к которому нет доступа, читать нечего.

## Разбор кейса: write-токен CI-бота

История из практики. В CI хранили `TF_API_TOKEN` team-токен с правами write на несколько workspaces. Токен утёк через лог сборки. Атакующий через API перечислил workspaces, увидел sensitive-переменные (имена и признак), изменил VCS-ветку одного workspace, добавил в Terraform-код `external`-источник, отправляющий переменные окружения наружу, и запустил run. Значения `AWS_SECRET_ACCESS_KEY` и пароля базы утекли. Всё через штатный API, без эксплуатации уязвимостей. Вывод: право запускать run равно праву читать секреты workspace.

## TFC и внешние secrets-провайдеры

В зрелых настройках TFC не хранит секреты сам, а берёт их из внешнего провайдера (Vault, AWS Secrets Manager) через dynamic credentials или OIDC. Это меняет атаку: вместо чтения переменных TFC атакующий ищет, как получить токен федерации или обойти условие OIDC. Если workspace запускается в self-hosted агенте, у него может быть instance profile с широкими правами — тогда run получает облако через сам агент, независимо от переменных. Проверяй и переменные, и идентичность агента.

## Защита Terraform Cloud

Меры защиты. Первое: токены с минимальными правами и коротким сроком, отдельно на чтение и на запуск. Второе: запретить изменение VCS/кода из недоверенных PR. Третье: не давать sensitive-переменные сборкам PR. Четвёртое: ограничить доступ к state и включить шифрование. Пятое: использовать dynamic credentials вместо статичных ключей. Шестое: аудит runs, изменений конфигурации и чтения state. Каждая мера ломает конкретный шаг: разведку, запуск кода, чтение секретов.

## Частые заблуждения

Первое: «sensitive-переменные защищены от чтения». Защищены от API, но не от кода в run. Второе: «токен read-only бесполезен». Он даёт разведку и часто чтение state. Третье: «run-триггеры — удобство». Это каналы cross-workspace. Четвёртое: «state — это только инфраструктура». Там секреты. Пятое: «агент-пул безопаснее облачных runners». Он даёт RCE в твоей сети.

## OIDC и dynamic credentials

Современный TFC умеет получать облачные креды по OIDC: workspace предъявляет подписанный токен, облако выдаёт временную роль по условиям (`sub`, `aud`). Это лучше статичных ключей, но условия можно настроить слишком широко. Например, разрешить любой workspace организации или любой репозиторий. Тогда атакующий с правом создать workspace получает облачную роль. Проверяй trust-политики OIDC так же внимательно, как роли CDK: подпись подтверждает, что токен от TFC, но не что его выдал именно нужный workspace.

## Как искать TFC-доступ

Ищи токены с префиксом, характерным для TFC, в CI-переменных, конфигах и логах. Проверь, есть ли self-hosted агенты (они в твоей сети). Посмотри, какие workspaces привязаны к репозиториям, которые ты можешь менять, и какие у них переменные. Ключевая связка: «токен с write + workspace, чей код ты можешь изменить» = исполнение кода с секретами. Без этого TFC остаётся только источником разведки через чтение state.

## Sentinel и policy-as-code

Terraform Enterprise использует Sentinel — policy-as-code, которая проверяет run до apply: разрешены ли ресурсы, регионы, типы. Если политики включены, часть опасных изменений блокируется, и атака через «измени код и запусти run» упирается в правила. Но Sentinel проверяет то, что описано, и не мешает прочитать state или использовать переменные. Плюс сама политика может быть изменена, если у токена есть права на неё. Смотри, какие политики enforced, а какие — advisory: разница определяет, что вообще можно применить.

## Итоговая цепочка атаки

Атакующий находит токен TFC (в CI или репозитории) и проверяет его права. С read-правами он читает state и переменные (имена и sensitive-флаги) — разведка. С write-правами он меняет код workspace (через VCS или API) так, чтобы run вывел окружение, и запускает run. Секреты утекают. При self-hosted агенте run даёт ещё и RCE в своей сети. Дальше — использование облачных кредов и закрепление в workspace/организации.

## Что мы теперь знаем

1. TFC запускает apply за тебя, хранит state и переменные.
2. API-токены бывают с разными правами; write даёт запуск кода.
3. Sensitive-переменные видны исполняемому коду и state.
4. Run-триггеры связывают workspaces в цепочки.
5. Агент-пулы возвращают RCE в твою сеть.
