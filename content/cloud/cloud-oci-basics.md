## Вопрос, с которого всё начинается

На пентесте ты находишь в Git-репозитории файл `~/.oci/config` и приватный ключ. Внутри — странные строки вида `ocid1.user.oc1..aaaa...` и `fingerprint=ab:cd:...`. Это Oracle Cloud. Вопрос: что даёт этот ключ и как понять, насколько глубоко можно зайти, не имея доступа к консоли? Отвечать придётся с помощью командной строки, потому что именно так работает атакующий, у которого есть только текстовые креденшелы.

## Что такое OCI и почему его надо уметь читать

Oracle Cloud Infrastructure (OCI) — облако Oracle, популярное в корпоративном сегменте: банки, ERP-системы, Oracle Database, интеграционные платформы. Модель прав здесь своя, и её часто настраивают «как получилось», выдавая CI-пользователям широкие политики. Атакующему важно быстро ответить на три вопроса: какой это tenancy, какие compartment доступны и какие права несёт ключ. Ответ на все три даёт один небольшой инструмент — OCI CLI.

## Сквозной пример: конфиг OCI CLI

Посмотрим на утёкший конфиг. Это обычный INI-файл, который читает утилита `oci`:
```
$ cat ~/.oci/config
[DEFAULT]
user=ocid1.user.oc1..aaaaaaaauser
fingerprint=ab:cd:ef:01:23:45:67:89:ab:cd:ef:01:23:45:67:89
tenancy=ocid1.tenancy.oc1..aaaaaaaatena
region=eu-frankfurt-1
key_file=/home/ci/.oci/oci_api_key.pem
```
Читаем человеческим языком: есть пользователь (`user`), его отпечаток публичного ключа (`fingerprint`), аккаунт (`tenancy`), регион и путь к приватному ключу. Все четыре поля вместе — это и есть API-креденшел OCI. Приватный ключ лежит рядом, поэтому пара «config + pem» полностью рабочая: её достаточно, чтобы начать отдавать команды от имени пользователя.

## OCID: как читать идентификаторы ресурсов

Каждый ресурс OCI имеет OCID — строку вида `ocid1.<тип>.<realm>.<регион>.<уникальный-суффикс>`. Тип бывает `user`, `tenancy`, `compartment`, `instance`, `bucket`, `vcn`. Realm (`oc1`) — это группа регионов, регион указывает дата-центр. Зная тип и регион, ты понимаешь, что за объект перед тобой, ещё до запроса к API. Это удобно при разборе дампов: увидев `ocid1.compartment.oc1..aaa`, ты сразу знаешь, что это контейнер ресурсов, а не сервер.

## IAM-политики: verb + resource-type + compartment

Права в OCI описываются предложениями вида `allow group X to manage instances in compartment Y`. Разберём по частям. `allow` — разрешение. Субъект (`group X`, `dynamic-group`, `any-user`) — кому. Действие (`inspect`, `read`, `use`, `manage`) — что именно: `inspect` даёт метаданные, `read` — чтение, `use` — использование без изменения, `manage` — полный контроль. `resource-type` — тип ресурса (`instances`, `buckets`, `virtual-network-family`). `in compartment Y` — область. Ошибка админов — `manage all-resources in tenancy`, то есть полный админ на весь аккаунт.

## Dynamic groups и instance principals

Чтобы не хранить ключи на серверах, OCI даёт instance principals: инстанс аутентифицируется своим сертификатом, а права получает через dynamic group. Правило dynamic group сопоставляет инстансы по атрибутам (compartment, tag, OCID). Если правило слишком широкое (например, «все инстансы в compartment»), то любой поднятый там инстанс получает те же права. Компромисс одного сервера = компромисс роли. Проверяй matching rule: узкое правило указывает конкретный OCID или тег, широкое — целый compartment.

## Object Storage и pre-authenticated requests

Бакеты OCI бывают `private` и `public`. Помимо ACL есть PAR (pre-authenticated request) — временная ссылка на объект или бакет. PAR может быть на чтение, запись или и то и другое, и легко утекает через логи и шаринг. Публичный бакет или широкий PAR — классическая точка exfiltration. При разборе важно смотреть не только на ACL, но и на список активных PAR: забытый PAR на запись позволяет атакующему подложить объект в бакет приложения.

## VCN, security lists и NSG

Сеть строится из VCN, подсетей, security lists (правила на подсеть) и NSG (правила на группу ресурсов). По умолчанию security list пропускает только нужное, но админы часто открывают `0.0.0.0/0` на 22/3389 «на время». Такие правила — входная точка для lateral movement после захвата ключа: получив `manage` на сеть, атакующий правит security list и открывает себе путь к внутренним сервисам.

## Типовые мисконфиги OCI

| Мисконфиг | Последствие | Как искать |
|---|---|---|
| `manage all-resources in tenancy` | полный админ | разбор политик CI-групп |
| Широкое правило dynamic group | любой инстанс = роль | matching rule |
| Публичный бакет | утечка данных | `oci os bucket list` |
| PAR без срока | постоянный доступ | список PAR |
| `0.0.0.0/0` на 22 | вход в сеть | security list |
| Ключ без ротации | долгий доступ | возраст ключа |

## Полный прогон: от конфига к захвату

Шаги атакующего. Первый: настроить CLI из утёкших файлов и проверить, жив ли ключ (`oci iam user list`). Второй: перечислить compartment и политики, понять реальные права. Третий: если есть `manage`, поднять инстанс со своим SSH-ключом или выкачать бакеты. Четвёртый: персистентность — создать нового IAM-пользователя или API-ключ, чтобы не потерять доступ при ротации утёкшего.

## Инструменты и команды

Основной инструмент — `oci` CLI. Полезные команды: `oci iam user list` (пользователи tenancy), `oci iam compartment list` (контейнеры), `oci iam policy list` (политики), `oci os bucket list` (бакеты), `oci compute instance list` (серверы). Для разведки без API-ключа используют `oci setup repair-file-permissions` и статические файлы. Альтернатива — облачные сканеры (ScoutSuite, Prowler-подобные), но для OCI чаще хватает самого CLI.

## OPSEC и детект

OCI пишет Audit-логи: каждая команда CLI, сделанная по API-ключу, оставляет след с OCID пользователя и IP-адресом. Поэтому шумные действия (создание пользователей, массовое скачивание бакетов) легко заметить. В аккуратном сценарии сначала читают права (`inspect`/`read`), затем делают минимум изменений. Если ключ чужой и подозрительный, лучше работать через один аккуратный `read`-запрос, а не веер команд.

## Разведка без API-ключа

Даже без рабочего ключа OCI даёт полезные сведения. Публичные бакеты видны через прямые URL вида `https://objectstorage.<region>.oraclecloud.com/n/<namespace>/b/<bucket>/o/<object>`. Namespace tenancy иногда утекает в клиентском JS. Публичные документация и статус-страницы раскрывают регион. Собрав namespace и регион, можно перебирать имена бакетов. Это чистая пассивная разведка: запросов к API нет, следов в Audit-логах тоже.

## Как переносится опыт AWS

Если ты знаешь AWS, OCI читается легко по таблице соответствий. Tenancy ≈ AWS account, compartment ≈ OU/проект, IAM policy ≈ IAM policy, dynamic group ≈ роль с trust на инстанс, instance principal ≈ instance profile, OCID ≈ ARN (но проще: без учёта аккаунта внутри строки), Object Storage ≈ S3, VCN ≈ VPC, security list ≈ security group/NACL. Разница в деталях: в OCI нет «политик, привязанных к пользователю» — политики живут на уровне compartment и ссылаются на группы.

## Работа с Audit-логами

OCI Audit пишет события вида `com.oraclecloud.identity.CreateUser`, `...DeleteApiKey`, `...GetObject`. Каждое событие содержит `principalId` (OCID пользователя), `ipAddress` и `eventTime`. При расследовании инцидента фильтруют по principalId утёкшего ключа и смотрят, что он делал: только `List` (разведка) или `Create`/`Delete` (действия). Атакующему эти же логи подсказывают, насколько шумно он себя ведёт.

## Частые вопросы

Можно ли аутентифицироваться только приватным ключом? Нет — нужны ещё `user`, `fingerprint`, `tenancy`. Что если ключ «только на чтение»? Тогда ищи другой креденшел: часто рядом в CI лежит второй, с `manage`. Опасен ли публичный бакет, если в нём нет данных? Он всё равно позволяет залить объект и подменить контент приложения. Что делать, если ключ отозван? Искать STS-токен роли инстанса или другой ключ в окружении.

## Что не сработает

Ключ без соответствующей политики вернёт `NotAuthorized`. Публичные бакеты часто оказываются пустыми — реальные данные лежат в private-бакетах, к которым нужен `read`. Dynamic group может требовать тег, которого у поднятого инстанса нет. И наконец, ротация ключей: если утёкший ключ уже отозван, CLI вернёт ошибку аутентификации — тогда нужен другой креденшел.

## Практический чек-лист пентеста OCI

Порядок действий на реальной цели. Один: настроить CLI (`oci setup config` или вручную разложить файлы). Два: проверить аутентификацию — `oci iam user list`. Три: собрать compartment (`oci iam compartment list --compartment-id <tenancy>`). Четыре: выгрузить политики (`oci iam policy list`) и найти широкие. Пять: перечислить бакеты (`oci os bucket list`) и инстансы (`oci compute instance list`). Шесть: если есть права — выкачать данные или поднять инстанс. Семь: зафиксировать персистентность. Каждый шаг — один-два запроса, чтобы минимизировать шум в Audit-логе.

## Расширенный сценарий: от read к manage

Частая ситуация: ключ даёт `read` на всё, но не `manage`. Тогда ищем путь эскалации. Вариант первый — `use` на `instance-family`: можно создать instance principal с ролью. Вариант второй — `manage` на `groups` в узком compartment: добавить себя в привилегированную группу. Вариант третий — права на `policies`: переписать политику, добавив себе `manage all-resources`. Во всех случаях финальная цель одна — получить полный контроль, оставаясь в рамках формально разрешённых действий.

## Что мы теперь знаем

1. Конфиг OCI + приватный ключ — это полноценный API-креденшел.
2. OCID кодирует тип и регион ресурса — читается без запросов.
3. Права OCI читаются как `verb + resource-type + compartment`; `manage all-resources in tenancy` — полный админ.
4. Dynamic groups с широким правилом делают любой инстанс носителем роли.
5. Public-бакеты, широкие PAR и `0.0.0.0/0` — точки exfiltration и входа.
