## Вопрос, с которого всё начинается

Ты нашёл AccessKeyId и AccessKeySecret от Alibaba Cloud. Прежде чем что-то делать, надо понять, что этот ключ умеет. В Alibaba права живут в **RAM** (Resource Access Management) — это аналог AWS IAM. И здесь есть всё то же, что мы видели в других облаках: пользователи, группы, политики, роли и STS. Разберём, как читать RAM-политику и где искать эскалацию.

## Что такое RAM

RAM — система управления доступом Alibaba Cloud. **RAM-пользователь** — это учётка с ключами. **Группа** — набор пользователей. **Политика** — JSON-документ с правилами `Effect`/`Action`/`Resource`. **Роль** — сущность, которую можно «взять» (AssumeRole) и получить временный STS-токен. Роль полезна тем, что её права не привязаны к человеку: её берут сервисы и доверенные аккаунты.

## Сквозной пример: политика и роль

Смотрим конфиг:
```
$ cat ram.json
{
  "Policy": {"Statement": [
    {"Effect": "Allow", "Action": "oss:*", "Resource": "*"},
    {"Effect": "Allow", "Action": "ram:GetRole", "Resource": "*"}
  ]},
  "Role": {
    "Name": "DeployRole",
    "TrustPolicy": {"Principal": {"Service": "ecs.aliyuncs.com"}}
  }
}
```
Здесь два факта. Первый: политика разрешает `oss:*` над всеми ресурсами — полный доступ к объектному хранилищу. Второй: есть роль `DeployRole`, которой доверяет сервис ECS — то есть любой ECS-инстанс может её взять. Это и есть заготовка confused deputy.

## Пользователи, группы и AccessKey

AccessKey — это пара Id/Secret, которой подписываются API-запросы. Как и в AWS, ключ долгоживущий, если его не ротировать. Пользователь может входить в группы, а группы несут политики. Поэтому первый шаг при разборе утёкшего ключа — узнать, в каких группах пользователь и какие политики на этих группах. Именно так мы получаем список действий.

## Роли и AssumeRole

Роль в Alibaba берётся через `sts:AssumeRole`. Кто может её взять — определяет **TrustPolicy** (политика доверия). Если там `Service: ecs.aliyuncs.com`, роль может взять любой ECS-инстанс. Если `Account`, роль берёт доверенный аккаунт. Если условие слишком широкое (например, доверие всей организации без дополнительных условий), атакующий, имеющий возможность запустить ECS или войти в доверенный аккаунт, получает права роли. После AssumeRole выдаётся STS-токен с ограниченным сроком — но на время его жизни это полноценные права.

## Confused deputy через сервисы

Классическая проблема: роль доверяет сервису, а сервис действует по запросу пользователя. Если проверка запроса слабая, пользователь заставляет сервис взять роль от его имени. В Alibaba это встречается в ролях для ECS, OSS, Function Compute и CI-сервисов. Проверяй TrustPolicy на предмет:
- доверия сервису без условия на конкретный ресурс;
- доверия аккаунту без `Condition` на внешний ID;
- разрешения `sts:AssumeRole` для широкого круга principal-ов.

## Эскалация прав

Пути эскалации в RAM повторяют другие облака:
- политика с `Action: "*"` и `Resource: "*"` — полный админ;
- `ram:AttachPolicyToUser`/`ram:CreatePolicy` — выдать себе права;
- `ram:CreateAccessKey` — создать новый ключ для чужого пользователя;
- `oss:*` на `*` — прочитать все бакеты (и найти там секреты);
- `ecs:RunInstances` + роль с доверием ECS — поднять инстанс и взять роль.

Каждый такой пункт в политике — это шаг по цепочке. Наша задача — соединить их в путь.

## Как проверить руками

С утёкшим ключом (алиас `aliyun`):
```
$ aliyun ram ListUsers
$ aliyun ram ListPolicies
$ aliyun ram ListRoles
$ aliyun ram GetPolicy --PolicyName <name> --PolicyType Custom
```
Вывод покажет документы политик. Дальше — сопоставление: пользователь → группы → политики → действия, и проверка, какие роли можно взять.

## Что мы теперь знаем

- RAM — IAM Alibaba: пользователи, группы, политики, роли, STS.
- AccessKey — долгоживущий ключ; его права = сумма политик групп пользователя.
- Роль берётся через AssumeRole, а кто может — решает TrustPolicy.
- Слишком широкое доверие (сервис/аккаунт без условий) = confused deputy.
- Эскалация — это `Action: "*"`, управление RAM или запуск ECS с ролью.
