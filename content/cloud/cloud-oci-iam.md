## Вопрос, с которого всё начинается

В прошлом уроке мы нашли конфиг OCI CLI и поняли, что он даёт доступ к tenancy. Но доступ — это ещё не права. Ключ отвечает на вопрос «кто ты», а на вопрос «что тебе можно» отвечают **политики** OCI. И вот здесь начинается самое интересное: в OCI политики пишут люди, и пишут их часто слишком широко. Задача этого урока — научиться читать политику как атакующий: где здесь лишняя власть и как из неё вырастает эскалация.

## Что такое IAM в OCI

IAM (Identity and Access Management) в OCI состоит из трёх простых сущностей. **Пользователь** (user) — это человек или приложение с API-ключом. **Группа** (group) — набор пользователей. **Политика** (policy) — текст на почти человеческом языке, который говорит: «группе X разрешено действие Y над ресурсами Z в области W». Пользователь сам по себе почти ничего не может — все права приходят через группы. Поэтому первый вопрос при разборе утёкшего ключа: в какие группы входит этот пользователь?

## Сквозной пример: утёкшая политика

В репозитории рядом с конфигом лежит файл с политиками тенанта. Смотрим:
```
$ cat policies.txt
allow group ci-deploy to manage all-resources in tenancy
allow group developers to read buckets in compartment Dev
allow dynamic-group ci-runners to use instances in compartment Build
```
Три строки — три разных уровня риска. Первая даёт группе `ci-deploy` полный контроль над всем tenancy. Вторая — только чтение бакетов в одном compartment. Третья — dynamic group, про которую мы поговорим отдельно. Разберём, из чего состоит строка политики.

## Анатомия политики: subject, verb, resource, location

Каждая политика читается по шаблону: **кому** (subject) **какое действие** (verb) **над чем** (resource) **где** (location). В нашем примере subject — `group ci-deploy`, verb — `manage`, resource — `all-resources`, location — `in tenancy`.

Глаголы образуют строгую иерархию, и это критично для оценки риска:

| Глагол | Что разрешает |
|--------|----------------|
| `inspect` | видеть метаданные (имя, OCID), но не содержимое |
| `read` | читать содержимое (данные, конфиги) |
| `use` | использовать ресурс (запустить инстанс, подключить) |
| `manage` | полный контроль: создать, изменить, удалить |

`manage` включает в себя всё остальное. Поэтому строка `manage all-resources in tenancy` — это фактически «администратор тенанта», даже если формально это «просто группа для CI».

## Compartment и наследование политик

Compartment — это папка для ресурсов. Политики, написанные на уровне tenancy, действуют на все compartments ниже, если явно не ограничены. Отсюда типичный мисконфиг: инженер хотел дать доступ к одному проекту, написал `in tenancy`, и случайно выдал права на всю организацию. При разборе всегда проверяй location: `in tenancy` — это красный флаг, `in compartment ProjectX` — уже узко.

Есть и обратная тонкость: политика `manage all-resources in tenancy` позволяет управлять **самими группами**. То есть пользователь с такой политикой может добавить себя в любую другую группу — и это уже неявная эскалация.

## Dynamic groups и instance principals

Dynamic group — это группа, в которую входят не пользователи, а **ресурсы**: инстансы, функции, автономные БД. Правило входа задаётся условием (matching rule), например «все инстансы с тегом `role=ci` в compartment Build». Ресурс, попавший в dynamic group, получает её права автоматически — через механизм **instance principal**. Это удобно (не надо хранить ключи на машине) и опасно: если условие слишком широкое, любой инстанс, поднятый в нужном compartment, наследует права группы.

Смотрим на третью строку: `allow dynamic-group ci-runners to use instances in compartment Build`. Если правило входа — «любой инстанс в Build», то атакующий, имеющий право создать инстанс в Build, автоматически получит права `ci-runners`. Это классический confused deputy: сервис действует от имени группы по нестрогому условию.

## Эскалация: от read к manage

Путь эскалации в OCI почти всегда такой: найти глагол, который позволяет **менять членство или политики**. Например:
- `manage groups` — добавить себя в админскую группу;
- `manage policies` — переписать политику и выдать себе всё;
- `manage users` — создать нового пользователя с ключом;
- `use instance-principals` — заставить инстанс действовать от твоего имени.

Даже скромный `read` на секреты (Vault, Object Storage) — уже утечка. Поэтому при разборе утёкшего ключа мы всегда перечисляем: какие группы у пользователя, какие политики на эти группы, и есть ли среди них `manage` на сущности IAM.

## Как проверить это руками

С конфигом CLI можно выполнить:
```
$ oci iam user list --all
$ oci iam group list --all
$ oci iam policy list --compartment-id <tenancy-ocid> --all
```
Вывод покажет пользователей, группы и тексты политик. Дальше сопоставляем: наш пользователь → его группы → политики этих групп → итоговые права. Это и есть «чтение политики как атакующий».

## OCI IAM: модель и поверхность

OCI IAM: users, groups, dynamic groups, policies. Политика — человекочитаемая строка: `Allow group Admins to manage all-resources in tenancy`. Ошибки: `manage all-resources` (полный доступ), dynamic group по широкому правилу (например, все инстансы компартмента), отсутствие compartment-ограничений, федерация без строгих условий.

```text
Allow <subject> to <verb> <resource> in <compartment> [where <condition>]
```

Аудит: собрать все политики, найти `manage all-resources`, проверить dynamic groups и их правила, проверить условия.

## Практика: эскалация в OCI IAM

Векторы: (1) dynamic group, которой можно стать (например, правило по тегу, который можно поставить), (2) политика, разрешающая `manage users`/`manage groups`, (3) `manage all-resources`, (4) федерация с доверием широкому IdP. Инструменты: `oci iam`.

```bash
oci iam policy list --compartment-id <tenancy>
oci iam dynamic-group list --compartment-id <tenancy>
```

Строй граф: идентичность → политики → ресурсы → следующая идентичность. Цель — найти путь до `manage all-resources`.

## Защита

Меры: минимальные политики, compartment-ограничения, условия (`where`), строгие dynamic groups, MFA, мониторинг. Для пентеста — чтение политик и построение графа.

## Расширенный разбор: чтение политик OCI

Политики OCI — текстовые строки вида `Allow group X to manage Y in compartment Z where C`. Читать их просто: собери все и найди `manage all-resources`, широкие subject (groups/dynamic-groups), отсутствие `where`-условий и ограничений compartment. Каждая такая политика — потенциальная эскалация.

```bash
oci iam policy list --compartment-id <tenancy> | jq -r ".data[].statements[]"
```

Ищи: `manage all-resources`, `manage users`, `manage groups`, `use` на чувствительные ресурсы. Строй граф.

## Расширенный разбор: федерация

OCI может быть федеративным (SAML с внешним IdP). Ошибка — доверие широкому IdP (например, любому пользователю домена) или маппинг групп, который можно подделать. Проверь настройки федерации и маппинг атрибутов.

```text
IdP group -> OCI group mapping -> roles
```

Если маппинг широкий (все в одну группу с широкими правами) — это находка. Для пентеста: оцени, какие группы IdP дают какие права OCI.

## Защита и вывод

Меры: минимальные политики, compartment-ограничения, условия, строгие dynamic groups, узкая федерация, MFA, мониторинг. Вывод: OCI IAM-аудит — чтение политик и построение графа до `manage all-resources`.

## Что мы теперь знаем

- Права в OCI приходят через группы, а не напрямую пользователю.
- Политика = subject + verb + resource + location; глаголы `inspect < read < use < manage`.
- `in tenancy` действует на все compartments — частый источник чрезмерных прав.
- Dynamic group выдаёт права ресурсам; слишком широкое условие = confused deputy.
- Эскалация — это `manage` на сущности IAM (groups/policies/users) или на секретах.
