## Вопрос, с которого всё начинается

Ты находишь в CI переменную `DATABRICKS_TOKEN` и адрес workspace. Databricks — платформа для Spark-аналитики, где инженеры запускают ноутбуки на кластерах, которые читают данные из облачных хранилищ. Вопрос: что даёт этот токен, можно ли через него выполнить код и дотянуться до бакетов, к которым у кластера есть доступ? Ответ — да, и это прямой путь к данным.

## Что такое Databricks и почему это цель

Databricks — управляемая платформа Spark/ML поверх облака. Она объединяет ноутбуки, кластеры, задания, каталог данных и секреты. Кластеры читают данные из S3/ADLS/GCS через instance profile (роль), а пользователи работают через workspace. Токен Databricks даёт API-доступ к workspace: запускать задания, читать ноутбуки, смотреть кластеры. А код на кластере исполняется в правах его роли — то есть в правах на данные.

## Сквозной пример: персональный токен

Токен выглядит так:
```
$ env | grep DATABRICKS
DATABRICKS_HOST=https://acme.cloud.databricks.com
DATABRICKS_TOKEN=dapi1234567890abcdef1234567890ab
```
Токен `dapi...` — это персональный access token пользователя. Он не истекает, пока его не отзовут, и наследует права владельца. Через API (`/api/2.0/...`) можно перечислить кластеры, задания, ноутбуки и секреты. Если владелец — админ workspace, токен даёт админские права.

## Кластеры и исполнение кода

Ключевая возможность — запустить код на кластере. Через API создаётся job или интерактивная команда, исполняющая Python/Scala. Код на кластере имеет доступ к: instance profile (роль облака), смонтированным хранилищам, секретам Databricks, внутренней сети. То есть токен workspace превращается в исполнение кода в облачных правах. Это самый прямой путь к данным.

## Instance profile и доступ к хранилищам

Кластер ассоциирован с instance profile — ролью IAM, дающей доступ к S3/ADLS/GCS. Код на кластере читает бакеты от имени этой роли. Часто роль широкая («чтобы аналитикам было удобно»). Поэтому компромисс токена = доступ к тем же бакетам, что и у кластера. Проверяй, какие бакеты видит роль, и не ограничен ли доступ префиксом.

## Секреты Databricks

Databricks хранит секреты в secret scopes: токены, пароли БД, ключи. Доступ к scope регулируется ACL. Через API (`/api/2.0/secrets/scopes/list`, `/secrets/get`) можно прочитать секреты, если есть права. Часто там лежат креденшелы к другим системам — это эскалация за пределы Databricks.

## Ноутбуки и их содержимое

Ноутбуки часто содержат захардкоженные секреты, строки подключения и ключи (несмотря на secret scopes). Через API их можно выгрузить все и грепнуть. Ноутбуки — это ещё и код, который можно изменить: подменить ноутбук задания — способ персистентности и внедрения в пайплайн.

## Типовые мисконфиги Databricks

| Мисконфиг | Последствие | Как искать |
|---|---|---|
| Персональный токен без срока | долгий доступ | срок токена |
| Токен админа workspace | полный контроль | права владельца |
| Широкая instance profile | доступ к бакетам | права роли кластера |
| Секреты в ноутбуках | утечка | выгрузка ноутбуков |
| Открытый secret scope | кража секретов | ACL scope |
| Кластер без ограничений сети | доступ к внутренним сервисам | конфиг кластера |

## Полный прогон: от токена к данным

Шаги. Первый: проверить токен (`/api/2.0/clusters/list`). Второй: перечислить кластеры, задания, ноутбуки. Третий: выгрузить ноутбуки и грепнуть секреты. Четвёртый: прочитать secret scopes. Пятый: запустить код на кластере для чтения бакетов (instance profile). Шестой: персистентность — создать новый токен или подменить ноутбук задания.

## Инструменты и команды

Инструменты: `databricks` CLI, `curl` к REST API, Python SDK (`databricks-sdk`). Полезные вызовы: `GET /api/2.0/clusters/list`, `GET /api/2.0/jobs/list`, `GET /api/2.0/workspace/list`, `GET /api/2.0/secrets/scopes/list`, `POST /api/1.2/commands/execute`. Для запуска кода — jobs API или interactive commands. Для выгрузки ноутбуков — workspace export.

## OPSEC и детект

Databricks пишет audit-логи: запуск заданий, доступ к секретам, изменения. Аномальные запуски команд и массовая выгрузка ноутбуков заметны. Создание новых токенов и заданий — события. Тихий сценарий: прочитать секреты и данные одним заданием, не создавая лишних объектов. Помни: audit-логи есть у workspace admin и могут отправляться в SIEM.

## Разведка без токена

Без токена видно: домен workspace (публичная страница входа), версия и брендинг. Ошибки API раскрывают структуру. Иногда публичные ноутбуки доступны по ссылке. Вакансии и документация раскрывают, какие данные там. Этого достаточно, чтобы оценить цель.

## Частые вопросы

Истекает ли персональный токен? По умолчанию — нет, до отзыва. Можно ли выполнить код по токену? Да, через jobs/commands API. Опасен ли только read-токен? Меньше, но секреты и ноутбуки всё равно доступны. Что если кластер выключен? Его можно запустить, если есть право. Помогает ли ограничение сети? Затрудняет доступ к внутренним сервисам.

## Что не сработает

Токен без прав на запуск заданий не выполнит код. Кластер без instance profile не даст облачных бакетов. Secret scope с корректным ACL не отдаст секреты. И отозванный токен вернёт `401`.

## Сценарий: от токена к S3

Цепочка. Токен найден в CI. Перечисляем кластеры, находим один с instance profile `databricks-data-read`. Запускаем на нём команду, читающую `s3://acme-data-lake/` — получаем листинг. Выгружаем интересующие префиксы. Читаем secret scopes: находим пароль к prod-БД. Выгружаем ноутбуки и находим ещё ключи. Фиксируем персистентность новым токеном.

## Практический чек-лист пентеста Databricks

Порядок. Один: проверить токен. Два: перечислить кластеры и задания. Три: выгрузить ноутбуки и найти секреты. Четыре: прочитать secret scopes. Пять: запустить код на кластере с instance profile. Шесть: прочитать бакеты. Семь: зафиксировать персистентность. Восемь: оценить audit-логи.

## Что мы теперь знаем

1. Персональный токен Databricks наследует права владельца и обычно не истекает.
2. Через API можно выполнить код на кластере — в правах его роли.
3. Instance profile открывает облачные бакеты; secret scopes — другие креденшелы.
4. Ноутбуки часто содержат захардкоженные секреты.
5. Audit-логи фиксируют запуск заданий и доступ к секретам.

## SQL Warehouse и каталог Unity

Помимо кластеров, Databricks предоставляет SQL Warehouse — движок для BI-запросов. Он тоже подключается к данным и работает в правах пользователя или сервисного принципала. Каталог Unity описывает таблицы и их права (на уровне схем, таблиц, колонок). Если у токена есть доступ к каталогу, он читает данные через SQL Warehouse, минуя кластеры. Проверяй оба пути: и код на кластере, и SQL.

## Сервисные принципалы и их токены

Для автоматизации в Databricks используют service principals с OAuth-токенами. Эти токены, как и персональные, утекают из CI. У сервисного принципала часто шире права, чем у человека, и он не привязан к конкретному сотруднику — значит, его отзыв заметнее по последствиям. При разведке ищи и персональные токены (`dapi`), и OAuth-креденшелы принципалов.

## Мониторинг и аудит

Databricks умеет отправлять audit-логи в облачное хранилище или SIEM. Если это настроено, действия видны: запуск команд, доступ к секретам, изменения кластеров. Если нет — след остаётся только внутри workspace. Для атакующего важно понять, включён ли экспорт логов: от этого зависит, насколько тихо можно действовать. Защищающимся стоит включить экспорт и алерты на запуск команд.

## Итог по Databricks

Токен workspace — это доступ к платформе, а кластер с instance profile — доступ к облачным данным. Ноутбуки и secret scopes дают дополнительные креденшелы. Защита: узкие права принципалов, короткие сроки токенов, ограничение instance profile и экспорт audit-логов.

## Практика на реальной цели

Работа с утёкшим токеном Databricks строится по шагам. Сначала проверяем токен безобидным вызовом (`clusters/list`), чтобы не привлекать внимания созданием объектов. Затем перечисляем задания и ноутбуки и выгружаем их — именно там чаще всего лежат забытые секреты. После этого читаем secret scopes: оттуда достаются пароли к базам и облакам. Только если нужны сами данные, запускаем код на кластере с instance profile — это самый заметный шаг, поэтому его делают последним и один раз. В конце фиксируем персистентность новым токеном с нейтральным именем.

## Что чаще всего находят

На практике в Databricks чаще всего находят: захардкоженные ключи в ноутбуках, широкие instance profile с доступом ко всему озеру и secret scopes, открытые для всех пользователей workspace. Всё это — следствие удобства: аналитикам проще положить ключ в ноутбук, чем настроить scope. Атакующему достаточно выгрузить ноутбуки и грепнуть их по `password`, `key`, `token`, `sk-`.

## Сравнение с EMR и другими Spark-платформами

Databricks — не единственная Spark-платформа в облаке: есть AWS EMR, GCP Dataproc. Логика похожа: кластеры с ролью, ноутбуки/шаги, доступ к хранилищам. Различия — в интерфейсах и в способе запуска кода. Поняв Databricks, ты переносишь подход на EMR (bootstrap-скрипты, шаги) и Dataproc (jobs). Везде ключевой вопрос один: какая роль у кластера и что она читает.
