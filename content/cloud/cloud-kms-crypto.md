## Вопрос, с которого всё начинается

Ты нашёл в S3-бакете зашифрованный файл. Скачать его ты можешь, но содержимое — мусор. Рядом лежит зашифрованный «ключ данных». Что делать, если сам ключ шифрования (KMS key) тебе недоступен? Ответ: KMS — это сервис, и если у тебя есть право его «попросить», он расшифрует данные **за тебя**. Разберёмся, как.

## Наш пример: зашифрованный бэкап

Объект урока — объект `s3://mycompany-backups/db.dump.enc`, зашифрованный KMS-ключом. Скачаем и посмотрим, что это.

```
$ aws s3 cp s3://mycompany-backups/db.dump.enc .
download: s3://mycompany-backups/db.dump.enc to ./db.dump.enc
$ file db.dump.enc
db.dump.enc: data
```

`file` не узнаёт формат — файл зашифрован. KMS-шифрование работает так: данные шифруют **ключом данных**, а ключ данных шифруют KMS-ключом. Этот зашифрованный ключ хранится рядом с данными. Чтобы прочитать данные, нужно расшифровать ключ данных через KMS.

## Шаг 1: что такое KMS

**KMS** (Key Management Service) — облачный сервис, который хранит ключи шифрования и выполняет операции с ними, **не отдавая сам ключ**. Ты не можешь «скачать» KMS-ключ — ты можешь только попросить его расшифровать или зашифровать что-то, если у тебя есть право.

Аналоги в других облаках: Azure Key Vault, GCP Cloud KMS. Смысл один: ключ живёт в сервисе, доступ — через права.

## Шаг 2: смотрим ключ и его политику

Сначала узнаем, каким ключом зашифрован объект. Метаданные объекта содержат идентификатор ключа:

```
$ aws s3api head-object --bucket mycompany-backups --key db.dump.enc --query "SSEKMSKeyId"
"arn:aws:kms:us-east-1:123456789012:key/abcd1234-5678-90ab-cdef-1234567890ab"
```

Теперь у ключа есть **key policy** — политика, которая решает, кому что можно. Посмотрим её:

```
$ aws kms get-key-policy --key-id abcd1234-5678-90ab-cdef-1234567890ab --policy-name default
{
  "Statement": [
    { "Sid": "AllowAccountAdmin", "Effect": "Allow",
      "Principal": {"AWS": "arn:aws:iam::123456789012:root"}, "Action": "kms:*", "Resource": "*" },
    { "Sid": "AllowDecryptForBackup", "Effect": "Allow",
      "Principal": {"AWS": "arn:aws:iam::123456789012:role/backup-role"}, "Action": "kms:Decrypt", "Resource": "*" }
  ]
}
```

Читаем: полный доступ у аккаунта, а роль `backup-role` может только `kms:Decrypt`. Значит, если ты находишься под `backup-role` (или получил её), ты можешь расшифровать бэкап.

## Шаг 3: расшифровываем через KMS

Если у тебя есть `kms:Decrypt`, ты просишь KMS расшифровать зашифрованный ключ данных, а затем расшифровываешь сам файл. На практике для S3 проще всего скачать объект **от имени роли с правом** — S3 сам расшифрует на лету:

```
$ aws sts get-caller-identity
{"Arn": "arn:aws:sts::123456789012:assumed-role/backup-role/i-0abc", "Account": "123456789012"}
$ aws s3 cp s3://mycompany-backups/db.dump.enc db.dump
$ file db.dump
db.dump: PostgreSQL custom database dump, ...
```

Теперь файл читается — S3 расшифровал его, потому что наша роль имеет `kms:Decrypt`. Ключ нам не понадобился: за нас его применил KMS.

## Шаг 4: grants — тонкая настройка доступа

Кроме key policy, доступ выдаётся через **grants** — временные разрешения на конкретное действие:

```
$ aws kms list-grants --key-id abcd1234-5678-90ab-cdef-1234567890ab
{
  "Grants": [
    { "GranteePrincipal": "arn:aws:iam::123456789012:role/backup-role",
      "Operations": ["Decrypt"], "Constraints": { "EncryptionContextSubset": { "app": "backup" } } }
  ]
}
```

Grant ограничен **encryption context** — набором пар «ключ-значение», которые передаются при шифровании. Это важно: даже с grant расшифровать можно только данные с нужным контекстом. Иногда контекст раскрывает имена и роли — полезно для разведки.

## Шаг 5: ключ как оракул

Даже без данных KMS может быть **оракулом**: если у тебя есть `kms:Decrypt`, ты можешь расшифровывать произвольные «блобы». Иногда другие сервисы шифруют KMS-ключом пароли и токены, и ты можешь расшифровать их, не имея доступа к исходному хранилищу. Это расширяет поверхность: ищи по аккаунту объекты, зашифрованные доступным тебе ключом.

## Шаг 6: эскалация через grants и key policy

KMS сам по себе — вектор эскалации. Если у тебя есть право `kms:CreateGrant`, ты можешь **выдать себе** доступ к ключу, даже если изначально его не имел. А право менять key policy (`kms:PutKeyPolicy`) — это полный контроль над ключом. Поэтому в таблице путей эскалации KMS-права стоят рядом с IAM: они дают доступ к данным, которые считались защищёнными.

## Шаг 7: почему это важно

Шифрование в облаке защищает данные **от провайдера и от утечки диска**, но не от того, у кого есть права. Если у злоумышленника есть `kms:Decrypt` — шифрование не мешает. Поэтому оценка облачной безопасности обязательно включает аудит key policies и grants.

## Шаг 8: envelope encryption — почему это важно

KMS не шифрует большие файлы напрямую: он шифрует **ключ данных** (data key). Схема называется envelope encryption (конвертное шифрование): сами данные шифруются быстрым симметричным ключом, а этот ключ — KMS-ключом. Поэтому рядом с данными всегда лежит зашифрованный ключ данных. Для нас это значит: имея `kms:Decrypt`, мы расшифровываем ключ данных и через него — всё остальное. То есть право на KMS-ключ эквивалентно праву на все данные, которые им защищены.

## Шаг 9: аудит ключей

Что проверять при оценке: кто имеет `kms:Decrypt` на чувствительные ключи; нет ли grants с широкими операциями; не отдан ли `kms:*` всему аккаунту; включено ли автоматическое вращение ключей. Эти четыре пункта покрывают большинство проблем KMS. Если `kms:*` есть у широкой роли — считай, шифрование не защищает ничего.

## Шаг 10: Key Vault и Cloud KMS — отличия

Термины у других провайдеров свои, но принцип тот же. В Azure это **Key Vault**: там хранятся ключи, секреты и сертификаты, а доступ даётся через access policies или RBAC. В GCP — **Cloud KMS** с key rings и key versions, а доступ — через IAM-роли вроде `roles/cloudkms.cryptoKeyDecrypter`. И там, и там действует то же правило: если у тебя есть право расшифровать — шифрование тебе не помеха. Поэтому при пентесте мультиоблачной среды аудит ключей проводят во всех трёх системах одинаково: смотрят, кому выдано право на расшифровку и не слишком ли оно широкое.

## Частые вопросы

**«Нужен ли мне сам ключ?»** Нет. KMS не отдаёт ключ — он выполняет операции за тебя, если у тебя есть право.

**«Почему файл расшифровался сам?»** Потому что S3 расшифровывает объект на лету от имени роли, у которой есть `kms:Decrypt`.

**«Что такое encryption context?»** Набор пар «ключ-значение», которым ограничен grant. Без нужного контекста расшифровать не выйдет.

**«Как эскалировать через KMS?»** Право `kms:CreateGrant` позволяет выдать себе доступ, а `kms:PutKeyPolicy` — взять ключ под контроль.

## Что мы теперь знаем

По-простому:

1. KMS хранит ключи и выполняет операции, не отдавая ключ.
2. Доступ к ключу описан в key policy и grants.
3. С `kms:Decrypt` ты расшифровываешь данные, не имея ключа.
4. Grants ограничиваются encryption context.
5. `kms:CreateGrant` и `kms:PutKeyPolicy` — пути эскалации.

## На что смотреть дальше

- **Ищи `kms:Decrypt` у своих ролей.** Это прямой доступ к данным.
- **Смотри grants.** Они часто шире, чем key policy.
- **Помни про контекст.** Без нужного context grant не сработает.
- **Проверяй `CreateGrant`.** Он позволяет выдать себе доступ.
