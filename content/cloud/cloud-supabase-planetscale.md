## Вопрос, с которого всё начинается

Ты открываешь фронтенд-бандл современного SaaS и видишь ключ вида `eyJ...` и URL `https://xyz.supabase.co`. Это anon-ключ Supabase — он публичен по дизайну, но за ним стоит база PostgreSQL. Вопрос: можно ли вытащить данные, если ключ «публичный», и что именно защищает таблицы? Ответ — Row Level Security, и её ошибки — самая частая причина утечек.

## Что такое serverless-базы

Serverless-базы — это управляемый PostgreSQL без администрирования. Supabase добавляет поверх базы REST-API (PostgREST), аутентификацию, storage и edge-функции. PlanetScale — MySQL-совместимый сервис, Neon — serverless PostgreSQL с ветвлением. Все три выдают строку подключения (connection string) с логином, паролем и хостом. Утечка такой строки = прямой доступ к базе. У Supabase доступ идёт ещё и через публичный API с anon-ключом.

## Сквозной пример: anon-ключ в бандле

Ключ выглядит так:
```
$ grep -o eyJ[A-Za-z0-9_.-]* app.js | head -1
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJyb2xlIjoiYW5vbiJ9.XXXX
```
Это JWT. Декодируем полезную нагрузку: `role` равно `anon`. Anon-ключ встроен в клиентский JS по дизайну: любой пользователь сайта его видит. Значит, безопасность зависит не от секретности ключа, а от политик на таблицах.

## Supabase: anon-ключ против service_role

У Supabase два ключа. Anon-ключ (роль `anon`) предназначен для клиента и подчиняется RLS. Service-role ключ (роль `service_role`) обходит RLS и даёт полный доступ к базе — его нельзя класть в клиент. Если в бандле оказался `service_role`-ключ, это критическая утечка: любой читает и пишет все таблицы. Проверка — декодировать JWT и посмотреть поле `role`.

## RLS: как работает и как ломается

Row Level Security — механизм PostgreSQL, при котором каждая строка проверяется политикой. Политика привязана к таблице и операции (`SELECT`, `INSERT`, `UPDATE`, `DELETE`) и использует `auth.uid()` (кто запросил). Если RLS выключен на таблице — anon-ключ читает всё. Если включён, но политика написана как `USING (true)` — тоже читает всё. Частые ошибки: забыли включить RLS на новой таблице, политика только на `SELECT` (но нет на `UPDATE`), или политика доверяет полю из запроса.

## PostgREST API и обход

Supabase отдаёт таблицы через PostgREST: `GET /rest/v1/<table>?select=*`. Запрос с anon-ключом вернёт строки, разрешённые RLS. Фильтры передаются в query: `?id=eq.1`, `?order=created_at.desc`, лимиты `?limit=1000`. Обходы: если RLS нет, видно всё; если политика зависит от JWT-claim, который можно подделать, — видно чужое; если есть view без `security_invoker`, он может выполняться с правами владельца и игнорировать RLS.

## Storage-бакеты и их политики

Supabase Storage — это тоже объектное хранилище с политиками на бакеты. Публичный бакет отдаёт файлы по URL. Приватный требует подписанную ссылку. Ошибка — бакет с `public` и предсказуемыми именами файлов: тогда перебирают имена и выкачивают документы. Отдельная зона риска — политика, разрешающая `INSERT` в публичный бакет: атакующий заливает HTML и получает stored XSS на домене приложения.

## Edge Functions

Supabase Edge Functions — код на Deno, исполняемый рядом с базой. Функции имеют доступ к секретам (service-role ключ, ключи сторонних API). Если функция принимает входные данные и передаёт их в SQL без параметризации — SQL-инъекция. Если возвращает ошибки с содержимым переменных — утечка секретов. Часто функции оставлены без аутентификации, и их можно вызывать напрямую, получая доступ к привилегированным операциям.

## PlanetScale и Neon: connection strings

PlanetScale и Neon не дают публичного REST-API по умолчанию — доступ идёт по connection string `mysql://user:pass@host/db` или `postgresql://user:pass@host/db`. Такие строки утекают из `.env`, CI, Docker-образов и `*.tfvars`. У PlanetScale есть ветки (branches) с отдельными строками; у Neon — ветвление, и строка может указывать на ветку с реальными данными. Найденная строка проверяется подключением и запросом к системным таблицам.

## Типовые мисконфиги serverless-баз

| Мисконфиг | Последствие | Как искать |
|---|---|---|
| RLS выключен | чтение всех строк | запрос к таблице |
| Политика `USING (true)` | чтение всех строк | разбор политик |
| service_role в бандле | полный доступ | декод JWT |
| Публичный storage | утечка файлов | список бакетов |
| Connection string в репо | прямой доступ к БД | grep postgres:// |
| Edge Function без auth | доступ к привилегиям | вызов функции |

## Полный прогон: от ключа к данным

Шаги. Первый: найти anon-ключ и URL в бандле. Второй: декодировать JWT и убедиться, что роль `anon`. Третий: перечислить таблицы через PostgREST (`GET /rest/v1/`). Четвёртый: запросить подозрительные таблицы и оценить объём утечки. Пятый: проверить storage-бакеты. Шестой: если есть service-role-ключ — прочитать всё напрямую. Седьмой: зафиксировать результат, не изменяя данные.

## Инструменты и команды

Декод JWT — любой base64-декодер или `jwt_analyze`. Запросы к PostgREST — `curl` с заголовками `apikey` и `Authorization: Bearer`. Для Postgres/MySQL — `psql` и `mysql` с найденной строкой. Для перебора таблиц полезен небольшой список типовых имён (`users`, `profiles`, `orders`, `payments`). Supabase CLI (`supabase`) помогает локально, но для атаки достаточно `curl`.

## OPSEC и детект

Supabase логирует запросы к API, но по умолчанию не все и не всегда хранит их долго. Массовый перебор таблиц виден по числу запросов и объёму ответов. Тихий сценарий — несколько точных запросов к конкретным таблицам вместо полного перебора. Если читаешь storage, помни: скачивание файлов фиксируется в логах бакета. Для PlanetScale/Neon запросы видны в метриках базы.

## Разведка без ключа

Даже без anon-ключа можно определить, что проект на Supabase: по домену `*.supabase.co` в сетевых запросах, по заголовкам, по структуре URL. Публичный storage-бакет виден по прямому URL. Открытые таблицы иногда раскрываются через публичные страницы. Собрав домен проекта, можно попробовать стандартные пути `/rest/v1/` — но без ключа они вернут `401`.

## Что не сработает

С выключенным RLS anon-ключ читает всё, но с включённым и корректной политикой — ничего лишнего. Публичный storage-бакет часто пуст. service-role-ключ может быть отозван. Connection string может указывать на пустую ветку. И прямые запросы к базе блокируются firewall, если IP не в allowlist.

## Разбор кейса: RLS забыли на новой таблице

Типичный инцидент. Команда добавила таблицу `invoices`, но забыла включить RLS — а Supabase по умолчанию отдаёт такие таблицы через PostgREST с anon-ключом. Пентестер запрашивает `GET /rest/v1/invoices?select=*` и получает все счета клиентов: имена, суммы, адреса, иногда номера карт. Уязвимость не в коде приложения, а в одной забытой галочке в базе. Отсюда правило: при аудите Supabase сначала перебирай таблицы и смотри, какие отвечают на anon-ключ.

## Частые вопросы

Как понять, что RLS выключен? Запрос к таблице с anon-ключом вернёт строки вместо пустого массива. Можно ли подделать anon-ключ? Нет смысла: он публичен. Что если политика зависит от пользовательского поля? Тогда подставь чужой id в фильтр и проверь, отдаст ли база чужие строки. Опасен ли публичный storage? Да: перебирай имена файлов. Что делать, если всё закрыто? Ищи Edge Functions без аутентификации и connection strings в других местах.

## Сравнение Supabase и Firebase

Обе платформы — BaaS с клиентским ключом. Firebase использует security rules на Firestore/Storage; Supabase — RLS на PostgreSQL. В Firebase забытая rule открывает коллекцию; в Supabase выключенный RLS открывает таблицу. Ошибка «открыли на чтение для теста и забыли» встречается в обеих. Разница в инструментах: для Firebase — REST и эмуляторы, для Supabase — PostgREST и `psql`. Модель атаки одинаковая: публичный ключ + слабая политика = утечка.

## Практический чек-лист пентеста Supabase

Порядок действий. Один: найти anon-ключ и URL проекта в бандле. Два: декодировать JWT, убедиться в роли. Три: перечислить таблицы через PostgREST. Четыре: запросить каждую и оценить утечку. Пять: проверить storage-бакеты на публичность. Шесть: найти Edge Functions и проверить их без аутентификации. Семь: искать service-role-ключ и connection strings. Восемь: зафиксировать результат, не изменяя данные.

## Что дальше в дереве

Дальше мы переходим к SaaS-идентичности (`cloud-saas-identity`): Okta, Microsoft 365, Google Workspace и SAML. Там креденшелы живут не в конфигах, а в токенах единого входа, и защита строится на доверии между IdP и приложением. Общая нить со serverless-базами одна: публичный идентификатор + слабая политика = доступ к чужим данным. Только политикой здесь служит уже не RLS, а правила федерации и MFA.

## Что мы теперь знаем

1. Anon-ключ Supabase публичен по дизайну; защита — RLS, а не секретность ключа.
2. service_role-ключ обходит RLS — его утечка критична.
3. RLS ломается выключением на таблице или политикой `USING (true)`.
4. Connection strings PlanetScale/Neon утекают из `.env` и CI.
5. Edge Functions и storage-бакеты — дополнительные точки входа и утечки.
