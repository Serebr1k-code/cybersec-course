## Вопрос, с которого всё начинается

В CI ты находишь JSON-файл сервисного аккаунта Google: `client_email`, `private_key`, `project_id`. Рядом — переменная с супер-админом (`admin@company.com`). Вопрос: что даёт этот ключ, можно ли читать почту и файлы всех сотрудников и как это связано с domain-wide delegation? Google Workspace — распространённый корпоративный тенант, и утечки ключей сервисных аккаунтов случаются регулярно.

## Google Workspace и его место

Google Workspace — облачный пакет Google: Gmail, Drive, Docs, Calendar, Admin Console. Аутентификация и управление идут через Google Cloud-проект и Admin SDK. Ключевая особенность — сервисные аккаунты: это технические аккаунты с ключом, которые приложения используют для доступа к API. Если сервисному аккаунту выдано domain-wide delegation (DWD), он может действовать от имени любого пользователя домена — это самая опасная конфигурация.

## Сквозной пример: ключ сервисного аккаунта

Файл ключа выглядит так:
```
$ cat sa-key.json
{
  "type": "service_account",
  "project_id": "acme-ci",
  "client_email": "ci-bot@acme-ci.iam.gserviceaccount.com",
  "private_key_id": "abc123",
  "private_key": "-----BEGIN PRIVATE KEY-----\nMIIE...EXAMPLE...\n-----END PRIVATE KEY-----\n"
}
```
С этим файлом можно аутентифицироваться как сервисный аккаунт. Проверка: получить access-токен (`gcloud auth activate-service-account --key-file sa-key.json`) и запросить Admin SDK. Если DWD настроен, токен позволит действовать от имени пользователей домена.

## Domain-Wide Delegation (DWD)

DWD — механизм, при котором сервисный аккаунт может «выдать себя» за любого пользователя домена. В Admin Console ему сопоставляют набор OAuth-scopes. Если среди scopes есть `https://mail.google.com/` или `https://www.googleapis.com/auth/drive`, сервисный аккаунт читает всю почту и все файлы. Атакующий с таким ключом указывает `subject=admin@company.com` при запросе токена — и получает доступ к данным админа. Это фактически захват всего тенанта.

## OAuth-клиенты и их секреты

Помимо сервисных аккаунтов в Workspace есть OAuth-клиенты (для веб-приложений). Они хранят `client_id` и `client_secret`. Слабый `redirect_uri` открывает перехват кода авторизации. Consent screen с широкими scopes и статусом «verified» позволяет собирать доступ к данным пользователей. Утечка `client_secret` даёт возможность выпускать токены от имени приложения. При разведке проверяй все OAuth-клиенты проекта: один из них почти всегда настроен слабее.

## Admin SDK и Directory API

Admin SDK Directory API — управление пользователями, группами, устройствами и ролями. С DWD-токеном (`subject=admin`) можно перечислить всех пользователей (`/admin/directory/v1/users`), группы и их членство, роли администраторов. Это даёт полную карту организации: кто чем управляет, какие группы дают доступ к приложениям. Через тот же API можно создавать пользователей и менять пароли — то есть закрепляться.

## Gmail: фильтры и пересылка

В Gmail есть настройки фильтров и пересылки. Атакующий с доступом к ящику (или с DWD от имени пользователя) добавляет фильтр: письма с определёнными словами пересылаются наружу или помечаются, минуя входящие. Как и правила Exchange, это тихая персистентность: работает до обнаружения. Ещё опаснее — настройка «forwarding» на весь домен, если у атакующего есть админские права на Gmail.

## Drive: sharing-ссылки

Google Drive хранит файлы с настройками доступа. Частая ошибка — файлы или папки, открытые «для всех, у кого есть ссылка». Такие данные читаются без токена вообще, по прямой ссылке. С DWD-токеном читается любой файл домена, включая закрытые. При разведке ищи два класса: анонимные ссылки (утечка без доступа) и общие диски (shared drives), где права часто шире, чем нужно.

## Супер-админ и делегированные роли

В Workspace есть супер-админ (полный контроль) и делегированные админы с ограниченными ролями (User Management, Help Desk, Services). Супер-админ незаменим, поэтому его аккаунт — приоритетная цель. Через Admin SDK видно, кто супер-админ и какие роли назначены. Если утёкший сервисный аккаунт имеет scope на управление ролями, атакующий может выдать себе роль или создать нового админа.

## Типовые мисконфиги Workspace

| Мисконфиг | Последствие | Как искать |
|---|---|---|
| Ключ SA в репозитории | доступ через DWD | grep private_key |
| DWD с широкими scopes | чтение всех данных | Admin Console |
| Анонимные ссылки Drive | утечка без доступа | настройки sharing |
| OAuth consent со широкими scopes | сбор данных | consent screen |
| Супер-админ без MFA | захват | политики |
| Фильтры Gmail без аудита | тихая утечка | Gmail settings |

## Полный прогон: от ключа к данным

Шаги. Первый: активировать сервисный аккаунт (`gcloud auth activate-service-account`). Второй: проверить наличие DWD, запросив токен с `subject=admin`. Третий: перечислить пользователей и роли через Admin SDK. Четвёртый: прочитать Gmail и Drive целевых пользователей. Пятый: добавить фильтр пересылки для персистентности. Шестой: при наличии прав — создать нового админа. Седьмой: зафиксировать результат, не удаляя данные.

## Инструменты и команды

Основной инструмент — `gam` (Google Apps Manager): `gam user admin@company.com show messages`, `gam print users`, `gam user <user> add forwardingaddress`. Также `gcloud` для активации SA и получения токена, `curl` для Admin SDK и Gmail API. Для Drive — `gdrive` или API напрямую. Для проверки DWD достаточно запросить токен с параметром `subject`.

## OPSEC и детект

Workspace ведёт Admin audit log: входы, изменения пользователей, настройки Gmail, доступ к Drive. Создание админов и смена паролей — громкие события. Чтение через API логируется в зависимости от сервиса: Gmail и Drive фиксируют доступ. Тихий сценарий — чтение через DWD с минимумом изменений. Помни: сервисный аккаунт с DWD выделяется в отчётах, если им пользуются необычно много.

## Разведка без ключа

Даже без ключа домен Workspace частично прозрачен. Проверка `https://www.google.com/a/<domain>` или MX-записей (`aspmx.l.google.com`) подтверждает Workspace. Публичные документы Google индексируются и находятся поиском. Ошибки OAuth раскрывают зарегистрированные `redirect_uri`. Список сотрудников собирается из публичных источников и LinkedIn. Эти зацепки готовят фишинг и поиск слабых креденшелов.

## Частые вопросы

Можно ли обойтись без DWD? Да, но тогда сервисный аккаунт видит только свои ресурсы. Как понять, что DWD включён? Запрос токена с `subject` вернёт токен, а API — данные чужого пользователя. Опасен ли ключ без DWD? Он даёт доступ к GCP-ресурсам проекта, что тоже ценно. Что если ключ отозван? Ищи другой ключ или OAuth-клиент. Как быстро заметят фильтр? Зависит от аудита; часто — при расследовании.

## Что не сработает

Ключ без DWD не даст читать чужую почту. Отозванный ключ вернёт ошибку аутентификации. MFA супер-админа не даст войти паролем. Анонимные ссылки Drive могут быть уже закрыты. И если в Admin Console отключены менее безопасные приложения, часть legacy-доступов не сработает.

## Персистентность в Google Workspace

Закрепившись, атакующий старается не зависеть от утёкшего ключа. Способы: создать новый ключ сервисного аккаунта, добавить OAuth-клиент с широкими scopes, выдать себе делегированную админскую роль, настроить пересылку Gmail или фильтр, добавить второго супер-админа. Самый устойчивый путь — создать собственный сервисный аккаунт с DWD: он выглядит как обычная автоматизация и переживает смену паролей. Обнаружить его можно только аудитом ключей и scopes.

## Сравнение Workspace с M365

Google Workspace и Microsoft 365 решают одну задачу, но разными средствами. В Workspace центральна фигура — сервисный аккаунт с DWD; в M365 — приложение с application-разрешениями и admin consent. Инструменты: `gam` и Admin SDK против Graph PowerShell. Общее: обе платформы ведут аудит, обе уязвимы к утечке ключа приложения, обе позволяют закрепиться через создание нового технического аккаунта. Освоив одну, легко перейти к другой.

## Практический чек-лист пентеста Workspace

Порядок действий. Один: активировать сервисный аккаунт ключом. Два: проверить DWD и доступные scopes. Три: перечислить пользователей и админов. Четыре: прочитать Gmail и Drive целевых пользователей. Пять: проверить анонимные ссылки Drive. Шесть: оценить OAuth-клиенты и их redirect_uri. Семь: закрепиться новым SA с DWD или админской ролью. Восемь: помнить об Admin audit log.

## Расширенный сценарий: от ключа к супер-админу

Представим полную цепочку. Утёкший ключ сервисного аккаунта имеет DWD с scope на Admin SDK. Атакующий запрашивает токен с `subject=admin@company.com`, получает права супер-админа и через Directory API перечисляет всех пользователей. Затем он создаёт нового пользователя с админской ролью — это персистентность, не зависящая от утёкшего ключа. Настроив фильтр Gmail на пересылку, он забирает переписку. Вся цепочка выглядит как работа легитимной автоматизации, поэтому обнаруживается только аудитом ключей и ролей.

## Что дальше в дереве

Дальше — SAML, протокол, лежащий под всеми SSO, включая Okta, M365 и Workspace. Там мы разберём атаки на сам механизм доверия: XSW, усечение комментариями и Golden SAML. А пока главное: в Workspace ключ сервисного аккаунта с DWD равен доступу ко всем данным домена.

## Что мы теперь знаем

1. Ключ сервисного аккаунта + DWD = доступ от имени любого пользователя домена.
2. OAuth-scopes определяют, к каким данным откроется доступ.
3. Admin SDK даёт карту пользователей, групп и ролей.
4. Фильтры Gmail и sharing-ссылки Drive — тихие каналы утечки.
5. Супер-админ без MFA — приоритетная цель для захвата.
