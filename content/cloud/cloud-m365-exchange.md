## Вопрос, с которого всё начинается

В репозитории ты находишь Azure-приложение: `tenant_id`, `client_id` и `client_secret`. Это приложение с разрешением `Mail.Read` для всего тенанта Microsoft 365. Вопрос: что можно сделать с этим секретом, как прочитать почту всех сотрудников и как из временного доступа сделать постоянный? Microsoft 365 — один из самых распространённых корпоративных тенантов, и утечка app secret встречается постоянно.

## Microsoft 365 и Exchange Online

Microsoft 365 — облачный пакет Microsoft: почта (Exchange Online), файлы (SharePoint, OneDrive), чаты (Teams), офисные приложения. Всё это привязано к тенанту Entra ID (бывший Azure AD). Аутентификация идёт через Entra, а данные доступны через Microsoft Graph API. Для атакующего это означает: одна точка входа (Entra) открывает доступ ко всем сервисам. Если утёк креденшел приложения с широкими разрешениями, читается вся почта и файлы организации.

## Сквозной пример: утёкший app secret

Конфиг приложения выглядит так:
```
$ cat appsettings.json
{
  "tenant_id": "00000000-0000-0000-0000-000000000000",
  "client_id": "11111111-1111-1111-1111-111111111111",
  "client_secret": "EXAMPLE~notarealsecretEXAMPLEnotareal"
}
```
С этими тремя значениями можно получить токен приложения: `POST /oauth2/v2.0/token` с `grant_type=client_credentials` и `scope=https://graph.microsoft.com/.default`. Ответ содержит `access_token`, действующий от имени приложения, без пользователя.

## Delegated и application permissions

В Entra два типа разрешений. Delegated — приложение действует от имени вошедшего пользователя, ограничено его правами. Application — приложение действует само, с правами, выданными администратором, и требует согласия админа (admin consent). Утёкший app secret с application-разрешениями — самый опасный случай: он не привязан к конкретному человеку и работает, пока секрет не отозван. Типичные опасные разрешения: `Mail.Read`, `Mail.Send`, `Files.ReadWrite.All`, `Directory.ReadWrite.All`.

## Правила почты: перенаправление и сокрытие

Exchange Online позволяет создавать правила входящей почты (`InboxRule`). Атакующий с `Mail.ReadWrite` добавляет правило: все письма от финансового директора перенаправляются на внешний адрес, а оригинал помещается в скрытую папку. Владелец ничего не замечает. Аналогично работают транспортные правила (на уровне тенанта) и делегирование ящиков. Правила — это тихая персистентность: они переживают смену пароля и работают, пока их не найдут.

## eDiscovery и Content Search

eDiscovery (Content Search) — легитимный инструмент комплаенса для поиска по всем ящикам и сайтам тенанта. С правами `eDiscovery` или админскими ролями атакующий создаёт поиск по ключевым словам («пароль», «счёт», «договор») и экспортирует результаты. Это способ массовой кражи данных, замаскированный под работу комплаенса. Экспорт больших объёмов оставляет след, поэтому аккуратные атакующие предпочитают точечные Graph-запросы.

## Захват тенанта через приложение

Ключевой приём: получив доступ к приложению с `AppRoleAssignment.ReadWrite.All` или `Application.ReadWrite.All`, атакующий создаёт своё приложение (или добавляет секрет к существующему) с `Mail.Read` и выдаёт ему согласие. Теперь у него постоянный доступ к почте всего тенанта. Если есть права на роли (`RoleManagement.ReadWrite.Directory`), он выдаёт себе Global Administrator. Так временный секрет превращается в полный захват тенанта.

## SharePoint, OneDrive и Teams

Те же application-разрешения открывают файлы: `Files.ReadWrite.All` даёт доступ ко всем сайтам SharePoint и дискам OneDrive. Ссылки общего доступа (`sharing links`) часто настроены «для всех в организации» или даже анонимно — тогда файлы читаются без токена, по прямой ссылке. Teams-сообщения читаются через `ChannelMessage.Read.All`. При разведке ищи самые доступные точки: анонимные ссылки, публичные сайты, внешние гости.

## Global Admin и роли

В Entra множество ролей: Global Administrator, Exchange Administrator, SharePoint Administrator, Application Administrator, Privileged Role Administrator. Роль можно получить напрямую или активировать через PIM (Privileged Identity Management), где назначения временные. Постоянные (permanent) назначения — красный флаг: их стоит искать. Если утёкший креденшел имеет права на роли, эскалация до Global Admin — дело пары запросов.

## Типовые мисконфиги M365

| Мисконфиг | Последствие | Как искать |
|---|---|---|
| app secret в репозитории | чтение почты/файлов | grep client_secret |
| Секрет без срока | долгий доступ | разбор приложения |
| Постоянный Global Admin | полный захват | роли |
| Правила почты без аудита | тихая утечка | mailbox audit |
| Анонимные sharing-ссылки | утечка файлов | настройки sharing |
| Legacy-протоколы | обход MFA | transport config |

## Полный прогон: от секрета к почте

Шаги. Первый: получить токен приложения (`client_credentials`). Второй: проверить разрешения через `/me` и Graph (`/users`). Третий: перечислить пользователей тенанта. Четвёртый: прочитать почту целевых ящиков (`/users/{id}/messages`). Пятый: добавить правило перенаправления для персистентности. Шестой: если есть права — создать своё приложение с `Mail.Read` и согласием, чтобы не зависеть от утёкшего секрета.

## Инструменты и команды

Основное — Microsoft Graph API через `curl` или Graph PowerShell. Полезно: `mfcmapi` для разбора MAPI-свойств, `AADInternals` для работы с Entra, `o365creeper`/`MailSniper` для проверки валидности аккаунтов. Graph-запросы: `GET /v1.0/users`, `GET /v1.0/users/{id}/messages`, `GET /v1.0/users/{id}/mailFolders/inbox/messageRules`, `POST` для создания правил. Токен берётся через `oauth2/v2.0/token`.

## OPSEC и детект

Microsoft ведёт Unified Audit Log: входы, создание правил, экспорт eDiscovery, изменения приложений — всё пишется. Mailbox audit логирует доступ к почте, если включён (по умолчанию для админов — да). Шумные действия: создание новых приложений, выдача согласия, массовый экспорт. Тихий сценарий: чтение через Graph и одно аккуратное правило. Помни: новое приложение с `Mail.Read` почти наверняка попадёт в отчёты безопасности.

## Разведка без токена

Даже без секрета тенант частично прозрачен. Проверка существования тенанта — `login.microsoftonline.com/<domain>/v2.0/.well-known/openid-configuration`. Публичный `GetUserRealm` раскрывает тип аутентификации (managed/federated). Утечки в GitHub ищут по `client_secret` и `tenant_id`. Список пользователей иногда собирается через перебор email (o365creeper). Эти зацепки готовят почву для фишинга или поиска более слабого креденшела.

## Частые вопросы

Можно ли читать почту только одного пользователя? Да, если приложению выдан доступ через application access policy. Что если секрет только для одного сервиса? Тогда он бесполезен для почты — смотри разрешения. Опасен ли delegated-токен? Да, но только в пределах прав пользователя. Как быстро заметят правило? Зависит от аудита; часто — только при расследовании. Что делать, если секрет отозван? Искать другой — часто в старых коммитах или у других приложений.

## Что не сработает

Секрет без application-разрешений вернёт `403` на почту. Conditional Access может блокировать приложение по IP. Admin consent иногда требует подтверждения второго админа. eDiscovery-экспорт большого объёма упирается в лимиты и логируется. И если включён строгий mailbox audit, чтение чужих ящиков заметят.

## Conditional Access и его обход

Conditional Access — политики Entra, которые решают, при каких условиях вход разрешён: с какого IP, с какого устройства, с каким уровнем риска, требуется ли MFA. Политики — главный барьер после утёкшего креденшела. Обходы: если политика требует compliant-устройство, а атакующий имеет PRT такого устройства, он проходит; если политика ограничивает по IP, но не покрывает все приложения, остаётся лазейка; legacy-протоколы иногда исключены из политик. При разведке выгружай список политик и ищи исключения.

## Персистентность в M365

Захватив тенант, атакующий закрепляется. Способы: добавить секрет к существующему приложению (`Application.ReadWrite.All`), создать новое приложение с `Mail.Read` и admin consent, выдать себе роль через PIM или напрямую, добавить правило почты, добавить федерацию в домен (для полного контроля аутентификации). Самый устойчивый — зарегистрированное приложение с секретом без срока: оно переживает смену пароля и обнаруживается только аудитом приложений.

## Сравнение M365 с другими IdP

M365 тесно связан с Entra ID и использует Microsoft Graph. Okta — независимый IdP с REST API. Google Workspace опирается на сервисные аккаунты и DWD. Общая логика: есть токен приложения/пользователя, есть приложения с разрешениями, есть админские роли. Различия — в инструментах (Graph PowerShell против gam) и в деталях аудита. Поняв M365, ты переносишь навык на остальные с поправкой на API.

## Практический чек-лист пентеста M365

Порядок действий. Один: получить токен приложения или пользователя. Два: проверить разрешения и роли. Три: перечислить пользователей тенанта. Четыре: прочитать почту целевых ящиков через Graph. Пять: оценить файлы SharePoint/OneDrive и sharing-ссылки. Шесть: проверить Conditional Access на лазейки. Семь: закрепиться приложением или правилом. Восемь: не забыть про аудит — изменения приложений громкие.

## Что дальше в дереве

Следующий урок — Google Workspace. Там та же логика (утёкший креденшел приложения открывает тенант), но вместо Entra и Graph — сервисные аккаунты и domain-wide delegation. Держи в голове общую схему: получить токен приложения → понять разрешения → дотянуться до почты и файлов.

## Что мы теперь знаем

1. Три значения (tenant_id, client_id, client_secret) дают токен приложения без пользователя.
2. Application-разрешения с admin consent — самый опасный класс креденшелов M365.
3. Правила почты и eDiscovery — тихие способы кражи данных.
4. Постоянный Global Admin и секреты без срока — красные флаги.
5. Unified Audit Log фиксирует изменения, поэтому тише всего чтение через Graph.
