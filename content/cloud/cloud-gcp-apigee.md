## Вопрос, с которого всё начинается

Ты тестируешь API за Apigee. Вопрос: как устроены прокси, можно ли влиять на target-сервер, есть ли политики, которые можно обойти, и как из «API-шлюз» получить SSRF или доступ к внутренним сервисам. Начнём с того, что Apigee — это прокси, который принимает запрос и пересылает его на бэкенд, и любой параметр, влияющий на адрес бэкенда, — потенциальный SSRF.

## Что такое Apigee и API Gateway

Apigee — платформа управления API: прокси (proxy) принимает внешний запрос, применяет политики (аутентификация, трансформация, rate-limit, JavaScript) и пересылает запрос на target-сервер (бэкенд). API Gateway — более простой вариант с конфигурацией в OpenAPI. Обе сущности стоят между клиентом и бэкендом и оперируют «переменными потока» (flow variables) — request.path, request.header.*, target.url и другими. Политики могут менять запрос, и ошибки в них дают уязвимости.

## Сквозной пример: динамический target

Смотрим фрагмент прокси:
```
<AssignMessage name="setTarget">
  <AssignVariable>
    <Name>target.url</Name>
    <Value>https://{request.header.x-backend}/api</Value>
  </AssignVariable>
</AssignMessage>
```
Здесь target.url собирается из заголовка `x-backend`, который присылает клиент. Значит, атакующий может указать свой адрес и заставить шлюз сходить куда угодно — классический SSRF. Дальше проверим, есть ли ограничения на значения и доступна ли metadata-сервис.

## Политики и переменные потока

Apigee-политики бывают: VerifyAPIKey, OAuthV2, JWT, BasicAuthentication, AssignMessage, ExtractVariables, JavaScript, MessageLogging. Каждая работает с переменными потока. ExtractVariables парсит параметры, AssignMessage задаёт значения, JavaScript исполняет код (в песочнице, но с доступом к переменным). Ошибка в политике — это, например, доверие к заголовку, который клиент может подделать, или передача клиентского значения прямо в target. Ищи места, где клиентский ввод становится адресом, заголовком или параметром запроса к бэкенду.

## Обход аутентификации

Прокси может требовать API-ключ, OAuth-токен или JWT. Обходы ищут в несоответствии проверки и маршрутизации: проверяется один путь, а исполняется другой (path confusion), политика применяется не ко всем условным потокам (conditional flows), или проверка стоит после трансформации. Плюс API-ключи часто попадают в клиенты (мобильные, веб) и утекают. Если ключ есть, а scope не проверяется, ключ может дать больше, чем задумано.

## SSRF через прокси

SSRF в шлюзе особенно опасен, потому что шлюз обычно находится внутри периметра и имеет доступ к внутренним сервисам и metadata-серверу (169.254.169.254). Если target можно задать динамически, попробуй внутренние адреса: другие прокси, сервисы без аутентификации, metadata (для получения токена service account). Даже ограничение «только https» обходится редиректами. Проверяй, какие адреса достижимы и есть ли фильтрация приватных диапазонов.

## Утечка ключей и конфигураций

API-ключи разработчика (developer keys), OAuth-клиенты и секреты хранятся в Apigee. Если у тебя есть доступ к среде (портал, API), ты можешь их прочитать. Плюс конфигурация прокси и target-серверов раскрывает внутреннюю топологию: имена бэкендов, порты, пути. Это ценная разведка перед атакой на внутренние сервисы. Ищи dev-среду: она часто менее защищена, но связана с прод-бэкендами.

## Типовые мисконфиги

| Мисконфиг | Последствие | Как искать |
|---|---|---|
| Динамический target из ввода | SSRF | конфиг прокси |
| Доверие к заголовкам | подмена бэкенда/идентичности | политики |
| Условные потоки без auth | обход проверки | conditional flows |
| Ключи в клиентах | abuse API | клиентский код |
| Dev-среда связана с прод | тест = прод | среды |
| Нет фильтрации внутренних адресов | SSRF к metadata | target rules |

## Полный прогон: от API к внутренним сервисам

Шаги. Первый: собрать конфигурацию прокси (если доступна) или пройтись по эндпоинтам. Второй: найти параметры, влияющие на target/заголовки. Третий: попробовать SSRF к внутренним адресам и metadata. Четвёртый: проверить обход аутентификации через условные потоки/пути. Пятый: достать ключи и топологию. Шестой: зафиксировать доступ. Седьмой: учесть логи шлюза.

## Инструменты и команды

Полезны: curl/ffuf для эндпоинтов, Burp для анализа потоков, `gcloud apigee`/портал для конфигурации, metadata-сервер для проверки SSRF. Для обхода — вариации путей и заголовков. Для ключей — grep по клиентам. Для топологии — конфигурация target-серверов.

## OPSEC и детект

Apigee логирует запросы, ошибки политик и обращения к бэкендам. SSRF к внутренним адресам виден в логах как запросы к неожиданным target. Обход аутентификации оставляет серию неудачных/успешных запросов. Тихий сценарий — точные проверки внутренних адресов, а не сканирование диапазона.

## Частые вопросы

Нужен ли API-ключ? Зависит от прокси; некоторые эндпоинты открыты. Виден ли target? Через конфигурацию или через поведение. Обходится ли «только https»? Часто через редиректы. Даёт ли SSRF metadata? Да, если шлюз в той же сети. Оставляет ли след? Да, логи шлюза.

## Что не сработает

Если target статичен и фильтруется, SSRF не выйдет. Если все потоки требуют валидный токен с проверкой scope, обход не пройдёт. Если шлюз в изолированной сети без доступа к metadata, SSRF ограничен. И если ключи не утекли, abuse API невозможен.

## Разбор кейса: заголовок, который стал адресом

История из практики. В прокси Apigee target.url собирался из заголовка клиента для «маршрутизации между регионами». Атакующий подставил в заголовок адрес metadata-сервера и получил токен service account шлюза, а через него — доступ к внутренним API. Урок: любой клиентский параметр, попадающий в адрес бэкенда, — это SSRF; в шлюзе он ценнее, потому что шлюз внутри периметра.

## Что мы теперь знаем

1. Apigee — прокси между клиентом и бэкендом с политиками и переменными потока.
2. Клиентский ввод, влияющий на target, даёт SSRF.
3. Обходы аутентификации живут в условных потоках и рассинхроне путей.
4. Ключи и конфигурации раскрывают топологию и дают abuse.
5. Шлюз внутри периметра — ценная точка для SSRF к metadata и внутренним сервисам.
