## Вопрос, с которого всё начинается

В конфигурации приложения на IBM Cloud ты находишь пару ключей, похожих на S3: `cos_hmac_keys`. Рядом — endpoint вида `s3.eu-de.cloud-object-storage.appdomain.cloud`. Вопрос: как этим пользоваться и что можно сделать без консоли IBM? Ответ прост и приятен для атакующего: IBM COS совместим с S3-API, а значит обычный `aws-cli` (или `s3cmd`) работает с ним напрямую.

## Что такое IBM Cloud Object Storage

COS — объектное хранилище IBM Cloud. Оно построено на S3-совместимом API: те же бакеты и объекты, те же операции `GET`/`PUT`/`DELETE`. Аутентификация бывает двух видов: **IAM-токен** (Bearer, от сервисного ID или пользователя) и **HMAC-ключи** (Access Key ID + Secret Access Key), которые работают как в AWS S3. Именно HMAC-ключи чаще всего утекают — они выглядят как обычные S3-креды и их копируют в конфиги.

## Сквозной пример: утёкшие креды

Смотрим файл:
```
$ cat cos-credentials.json
{
  "apikey": "EXAMPLEnotarealapikey",
  "cos_hmac_keys": {
    "access_key_id": "EXAMPLEACCESSKEY",
    "secret_access_key": "EXAMPLEnotarealsecret"
  },
  "endpoints": "https://s3.eu-de.cloud-object-storage.appdomain.cloud"
}
```
Здесь есть и API-key (для IAM), и HMAC-пара. Для атаки проще HMAC: настраиваем `aws-cli` с этим endpoint и ключами — и работаем с COS как с S3.

## Использование HMAC-ключей

Настройка профиля:
```
$ aws configure --profile cos
AWS Access Key ID: EXAMPLEACCESSKEY
AWS Secret Access Key: EXAMPLEnotarealsecret
Default region name: eu-de
```
Далее — обычные S3-команды, но с флагом endpoint:
```
$ aws --profile cos --endpoint-url https://s3.eu-de.cloud-object-storage.appdomain.cloud s3 ls
$ aws --profile cos --endpoint-url https://s3.eu-de.cloud-object-storage.appdomain.cloud s3 ls s3://acme-backups
```
Если ключ валиден, `s3 ls` перечислит бакеты, доступные этому сервисному ID. Дальше — чтение объектов.

## Права сервисного ID

HMAC-ключ принадлежит **сервисному ID** (service ID) — это «учётка для приложения», аналог service account. Права сервисного ID определяет его политика IAM: какие роли на какие сервисы. Частая ошибка — выдать сервисному ID роль `Manager` на весь COS, чтобы «не возиться». Тогда утёкший HMAC-ключ читает и пишет все бакеты аккаунта. При аудите всегда уточняй: какой сервисный ID, какие у него роли, и есть ли среди них Writer/Manager.

## Bucket policy и публичный доступ

У бакета COS есть **bucket policy** (JSON, как в S3) и **public access**. Публичный бакет отдаёт объекты по обычному HTTPS-URL без ключей. Bucket policy может разрешить анонимные `GetObject`/`ListBucket` — это тот же мисконфиг, что мы видели в OSS и S3. Проверяй оба: и креды (доступ с ключом), и policy (доступ без ключа).

## Шифрование и версии

COS поддерживает управляемое и собственное шифрование (SSE-C, Key Protect), а также версионирование. Для атакующего версионирование важно тем же, чем везде: «удалённый» объект может сохраниться в старой версии. Собственное шифрование (SSE-C) означает, что для чтения объекта нужен ещё и ключ шифрования — тогда утёкших HMAC недостаточно. Проверяй, какое шифрование включено, прежде чем считать данные доступными.

## Как проверить руками

Помимо `aws-cli`, удобен `s3cmd` или `rclone`. Минимальная проверка валидности ключа — `s3 ls` на корне endpoint. Если команда возвращает список бакетов, ключ жив и несёт хотя бы `ListBuckets`. Дальше — по бакетам, которые видны.

## IBM COS: объектное хранилище

IBM Cloud Object Storage (COS) — S3-совместимое хранилище. Доступ управляется IAM-политиками и ACL бакетов. Типичные ошибки: публичный бакет, политика с `service:cloud-object-storage` и действием `*`, HMAC-ключи в открытом виде.

```bash
ibmcloud cos buckets
curl https://<bucket>.s3.<region>.cloud-object-storage.appdomain.cloud/   # анонимно
```

Проверка анонимного доступа и листинга — первый шаг. Дальше — поиск объектов с секретами.

## Практика: находки и эскалация

Что искать: публичные бакеты, объекты с секретами, HMAC-ключи (в конфигах/CI), service credentials с широкими правами. Эскалация: получив креды, использовать `ibmcloud`/S3 API для доступа к другим бакетам и сервисам. Инструменты: `ibmcloud`, `aws s3` (совместимо), `rclone`.

```bash
aws --endpoint-url https://s3.<region>.cloud-object-storage.appdomain.cloud s3 ls s3://<bucket>/
```

Типичная находка: service credentials с `Manager`-ролью, дающие полный доступ к COS.

## Защита

Меры: приватные бакеты, минимальные IAM-политики, ротация HMAC-ключей, шифрование, мониторинг доступа. Для пентеста — перечисление и чтение публичного; модификация — с разрешения.

## Расширенный пример: от HMAC-ключа к бакетам

Полный маршрут. Первое — найти HMAC-ключ или service credentials (в CI, конфигах, логах). Второе — проверить идентичность: `ibmcloud iam api-key-details` или `aws --endpoint-url ... s3 ls`. Третье — перечислить бакеты. Четвёртый — скачать объекты с секретами. Пятый — оценить, какие ещё сервисы доступны (COS — не единственный).

```bash
aws --endpoint-url https://s3.us-south.cloud-object-storage.appdomain.cloud s3 ls
aws --endpoint-url https://s3.us-south.cloud-object-storage.appdomain.cloud s3 cp s3://<b>/.env .
```

Шестой — задокументировать путь и импакт. Именно сочетание «ключ с широкой ролью + публичные/доступные бакеты» даёт полный доступ к данным.

## Частые находки в IBM COS

Находки: (1) service credentials с ролью `Manager` (полный доступ к COS); (2) публичный бакет с данными; (3) HMAC-ключ без ротации; (4) объекты с секретами; (5) бакеты, доступные по прямым URL. Проверяй также связанные сервисы IBM Cloud (Cloud Functions, Databases) — те же креды могут давать к ним доступ.

```text
Manager role -> all buckets -> read/write/delete
```

Для пентеста: перечисление и чтение; модификация — только с разрешения.

## Расширенный разбор: цепочка доступа к COS

Полная цепочка: креды → IAM-политика → сервис → данные. Первое — найти service credentials или HMAC-ключ (в CI, конфигах, логах). Второе — определить, какие роли у идентичности (`Viewer`, `Writer`, `Manager`). Третье — перечислить бакеты. Четвёртое — скачать интересное. Пятое — проверить, нет ли доступа к другим сервисам IBM Cloud с теми же кредами.

```bash
ibmcloud iam api-key-details <key>
ibmcloud cos buckets
```

Типичная находка — `Manager`-роль на COS, дающая полный доступ. Для пентеста: перечисление и чтение; запись/удаление — только с разрешения.

## Частые ошибки и защита IBM COS

Ошибки: публичный бакет, `Manager`-роль у сервисной идентичности, HMAC-ключ без ротации, креды в репозитории. Защита: приватные бакеты, минимальные IAM-политики, ротация, шифрование, мониторинг. Вывод: COS — обычное S3-совместимое хранилище, и аудит такой же: ACL, политики, креды, объекты с секретами.

## Практический чек-лист COS

1. Найти креды (service credentials, HMAC-ключ) в CI/конфигах/логах. 2. Определить роль идентичности (`Viewer`/`Writer`/`Manager`). 3. Перечислить бакеты. 4. Проверить анонимный доступ. 5. Скачать объекты с секретами. 6. Проверить доступ к другим сервисам. Инструменты: `ibmcloud`, `aws s3` (совместимо), `rclone`. Модификацию не выполняй без разрешения.

## Разбор кейса: утёкшие service credentials

История из практики. Service credentials IBM COS лежали в переменных CI и попали в лог сборки. Идентичность имела роль `Manager` на сервисе COS. Атакующий, получив ключ, перечислил все бакеты организации, скачал выгрузки баз и обнаружил во одном из бакетов резервные копии с ключами шифрования. Отдельной уязвимости не было: сработала связка «широкая роль + утечка ключа». Вывод: сервисные идентичности для объектного хранилища должны иметь минимальную роль и короткий срок жизни, а секреты — не попадать в логи.

## Дополнительно: связанные сервисы

Креды COS часто переиспользуются: та же идентичность может иметь доступ к IBM Cloud Databases, Cloud Functions, Kubernetes. Поэтому после находки ключа проверь не только бакеты, но и весь список сервисов, доступных идентичности (`ibmcloud iam`). Типичный сценарий: ключ для бэкапов имеет также доступ к базе, и через него утекают данные. Строй карту «идентичность → сервисы → данные» и оцени, где остановится атакующий.

## Вывод по IBM COS

IBM COS — S3-совместимое хранилище с IAM-политиками. Аудит: креды → роли → бакеты → объекты → связанные сервисы. Ключевые находки — публичный бакет и `Manager`-роль у сервисной идентичности. Защита: минимальные роли, приватные бакеты, ротация, мониторинг.

## Что мы теперь знаем

- IBM COS — S3-совместимое хранилище; работает с `aws-cli` через `--endpoint-url`.
- HMAC-ключи ведут себя как S3-креды и часто утекают.
- Права определяет сервисный ID и его роли IAM (Writer/Manager опасны).
- Публичный доступ даёт bucket policy и public access.
- Версионирование и SSE-C меняют картину доступа.

Отдельно проверь логирование доступа к COS: если оно выключено, факт чтения данных невозможно доказать или отследить, что само по себе риск. Включение Activity Tracker и алертов на массовое скачивание — обязательная мера.

Для отчёта собери полную цепочку: найденный ключ, его роль, доступные бакеты, скачанные объекты и связанные сервисы. Такая цепочка показывает реальный импакт, а не просто «найден ключ».

Проверь также ключи, которые «не используются»: старые HMAC-ключи часто остаются активными и не ротируются, и именно они утекают в старые конфиги и логи. Для защищающейся стороны регулярный автоматический аудит публичных бакетов и ролей сервисных идентичностей обязателен — ручная проверка не масштабируется и пропускает «временные» настройки. Итог: COS-аудит — это цепочка «креды → роли → бакеты → объекты → связанные сервисы», и каждая находка в ней самостоятельна, но вместе они дают полный контроль над данными.
