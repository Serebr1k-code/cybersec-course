## Зачем этот урок

Облако меняет модель угроз: периметр размывается, а идентичность становится главным рубежом. Прежде чем атаковать S3, IAM или Kubernetes, нужно понять, чем облако отличается от классического хостинга, кто за что отвечает и какие инструменты нужны для работы.

## Чем облако отличается от классического хостинга

- **API-first**: вся инфраструктура управляется через API, а значит — через креденшелы.
- **Идентичность = периметр**: утечка ключа равна проникновению.
- **Эфемерность**: ресурсы создаются и удаляются автоматически, конфигурации устаревают мгновенно.
- **Разделяемая ответственность**: часть безопасности — на провайдере, часть — на вас.
- **Метаданные**: каждый инстанс/пода имеет endpoint метаданных (169.254.169.254) — источник креденшелов при SSRF.

## Модель разделяемой ответственности

| Слой | Провайдер | Клиент |
|------|-----------|--------|
| Физическая инфраструктура | ✓ | — |
| Гипервизор/сеть | ✓ | — |
| ОС (IaaS) | — | ✓ |
| Патчи ОС | — | ✓ |
| IAM-политики | — | ✓ |
| Данные | — | ✓ |
| Конфигурация сервисов | — | ✓ |

Понимание границы помогает понять, что искать: провайдер не «пропустит» вас в чужой аккаунт, но ваши собственные мисконфиги — ваша проблема.

## IaaS, PaaS, SaaS, FaaS

- **IaaS** (EC2, GCE, Azure VM) — вы управляете ОС, максимум свободы атакующего.
- **PaaS** (App Service, Elastic Beanstalk) — управляете приложением, но не ОС.
- **FaaS** (Lambda, Cloud Functions) — только код; креды через роль.
- **SaaS** (M365, Salesforce) — только конфигурация и данные.

Чем выше уровень абстракции, тем меньше поверхность, но тем важнее идентичность и конфигурация.

## Карта поверхности атаки в облаке

- **Утечка креденшелов**: GitHub, бакеты, CI-логи, `.env`.
- **Мисконфиги хранилищ**: публичные бакеты, SAS-токены.
- **IAM-эскалация**: PassRole, CreatePolicyVersion, AssumeRole.
- **Compute-компрометация**: SSRF → metadata → роль.
- **Контейнеры/K8s**: escape, SA-токены, kubelet.
- **Serverless**: переполнение прав роли, event injection.
- **CI/CD**: секреты пайплайнов, OIDC-доверие.
- **Supply chain**: зависимости, образы, Terraform.

## Практика: разворачиваем учебный стенд

1. Создайте тестовый AWS-аккаунт (или используйте `LocalStack`).
2. Создайте пользователя с ограниченными правами и ключами.
3. Создайте S3-бакет с намеренной публичной политикой.
4. Создайте роль с широким trust.
5. Прогоните `enumerate-iam` и `prowler`, сравните с ожиданиями.
LocalStack: `docker run -p 4566:4566 localstack/localstack` — локальный эмулятор AWS.

## Что дальше / решение

Освоив модель, переходите к конкретике: `cloud-iam-basics` → `cloud-privesc-iam` → `cloud-storage-s3` → `cloud-container-runtime`. Стройте карту «идентичность → права → ресурсы» и ищите разрывы.

## Регионы, зоны и границы

Ресурсы привязаны к регионам (`us-east-1`, `eu-central-1`). Это влияет на: доступность данных (резидентность), цены, задержку и — для атакующего — на то, где создавать ресурсы, чтобы обойти условия политик (`aws:RequestedRegion`). Availability Zones внутри региона изолированы по питанию и сети; Global Services (IAM, Route 53, CloudFront) не привязаны к региону, и это стоит учитывать при анализе доверия.

## Стоимость и биллинг как источник разведки

Биллинг раскрывает, какие сервисы используются (Cost Explorer, `ce:GetCostAndUsage`). Атакующий с правом на биллинг видит карту инфраструктуры; защитник — аномалии (всплеск EC2 в новом регионе = криптомайнинг). GuardDuty детект `CryptoCurrency:EC2/BitcoinTool.B` ловит такое.

## Практика: LocalStack для безопасных экспериментов

```bash
docker run -d -p 4566:4566 -e SERVICES=s3,iam,sts localstack/localstack
export AWS_ENDPOINT_URL=http://localhost:4566
aws --endpoint-url http://localhost:4566 s3 mb s3://test
aws --endpoint-url http://localhost:4566 iam create-user --user-name alice
```

LocalStack эмулирует AWS API локально — идеально для отработки `enumerate-iam`, политик и сценариев эскалации без риска и затрат. Аналоги: `moto` (Python), `minio` (S3), `kind`/`minikube` (K8s).

## Глоссарий

- **Principal** — сущность, выполняющая запрос.
- **Action** — операция API.
- **Resource** — объект, над которым операция.
- **ARN** — уникальный идентификатор ресурса.
- **STS** — сервис временных креденшелов.
- **IMDS** — Instance Metadata Service (169.254.169.254).
- **IRSA** — IAM Roles for Service Accounts (EKS).
- **SCP** — Service Control Policy (ограничение организации).

## Типовые ошибки новичка

- Путать «нет прав в консоли» и «нет прав в API» — консольные права ограничены отдельно.
- Считать регион незначимым — политики и ресурсы региональны.
- Игнорировать биллинг как вектор разведки.
- Начинать атаку без тестового стенда.
- Не вести лог своих действий (важно для отчёта и OPSEC).

## Пользователи против ролей: почему роли безопаснее

Пользователь с ключами — постоянный секрет: утёк — компрометация навсегда, пока не отзовут. Роль выдаёт временные креды (часы) и привязана к условиям доверия. Поэтому best practice — не создавать долгоживущие ключи, а использовать роли, federation и OIDC. С точки зрения атакующего это меняет приоритеты: ключи в репозиториях и бакетах ценнее, чем «право на роль», но роль часто даёт больше прав.

Проверьте, сколько долгоживущих ключей в аккаунте: `aws iam list-access-keys` для каждого пользователя. Каждый — потенциальная утечка.

## Практическое задание

Разверните LocalStack, создайте пользователя с `iam:CreatePolicyVersion` и политикой, привязанной к нему самому. Затем воспроизведите эскалацию: создайте версию политики с `Action:*` и `--set-as-default`. Убедитесь, что права расширились. Это безопасный способ отработать технику перед реальным engagement.

Дополнительно: включите CloudTrail в эмуляторе (если поддерживается) и посмотрите, как выглядит `CreatePolicyVersion` в логах — так вы научитесь и атаковать, и детектировать.

## Порог входа: с чего начать пентест облака

Начните с разведки идентичности: какие креды есть (env, файлы, метаданные), какие роли и права. Затем — карта ресурсов (S3, EC2, IAM). Далее — поиск путей эскалации (PassRole, CreatePolicyVersion, AssumeRole). И только потом — эксплуатация. Такой порядок экономит время и снижает шум: вы точно знаете, какие API вызывать, вместо слепого перебора.

## Быстрый старт

1. Определите, какие креды у вас есть (env, файлы, метаданные).
2. `aws sts get-caller-identity` / `gcloud auth list` / `az account show`.
3. Перечислите ресурсы (S3, EC2, IAM).
4. Ищите пути эскалации.
Такой порядок экономит время и снижает шум: вы точно знаете, какие API вызывать.

## Где пригодится

- **Пентест облачной инфраструктуры** — это стартовая карта, к которой вы возвращаетесь на каждом шаге.
- **Bug bounty** — программы AWS/GCP/Azure и компаний с облачными активами.
- **CTF** — категория Cloud почти всегда начинается с рекона по этой схеме.
- **Blue team / IR** — понимание поверхности атаки нужно для детекта и приоритизации (см. `cloud-logging-detection`).
- **DevSecOps** — те же мисконфиги ловятся на этапе IaC-сканирования (Terrascan, Checkov).
