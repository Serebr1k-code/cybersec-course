## Вопрос, с которого всё начинается

Ты находишь в репозитории строку подключения к Cosmos DB: endpoint и account key. Вопрос: что даёт этот ключ, как он соотносится с ролями Azure, можно ли читать все базы, и где здесь инъекция, если база NoSQL? Ответ начинается с того, что в Cosmos есть две разные плоскости — управление (ARM) и данные (data-plane) — и ключ открывает вторую напрямую.

## Что такое Cosmos DB

Cosmos DB — глобально распределённая многомодельная база Azure. Она умеет разные API: SQL (документы), MongoDB, Gremlin (граф), Cassandra, Table. Каждая база живёт внутри «аккаунта Cosmos», а аккаунт аутентифицирует клиентов одним из способов: ключом аккаунта, Entra ID (бывш. Azure AD) токеном с RBAC-ролью, или resource token от брокера. Ключ и RBAC — это два независимых пути к одним данным, и это ключ к атаке: даже если в тенанте выключен публичный доступ по ключу, старая строка подключения может работать.

## Сквозной пример: строка подключения

Смотрим утёкший конфиг приложения:
```
$ cat appsettings.json | jq -r .Cosmos
AccountEndpoint=https://acme-prod.documents.azure.com:443/;AccountKey=EXAMPLEnotarealkey==
```
Здесь два компонента: endpoint (адрес аккаунта) и AccountKey (primary key). Ключ — это секрет аккаунта, который даёт полный доступ ко всем базам и контейнерам внутри. Дальше проверим, работает ли он вообще и что за ним лежит.

## Ключи доступа и их права

У аккаунта Cosmos два ключа: primary и secondary (чтобы можно было ротировать без простоя). Любой из них — это admin по данным: чтение, запись, удаление, смена настроек консистентности на уровне данных. Ключ не привязан к пользователю и не логируется как пользователь — в логах видно только, что обращались с ключом. Если ключ утёк, ротация обязательна, но пока её не сделали, доступ есть. Практический шаг: перечислить базы и контейнеры, затем прочитать документы.

## RBAC и Entra-аутентификация

Второй путь — Entra ID с data-plane RBAC: встроенные роли (Cosmos DB Built-in Data Reader, Data Contributor) выдаются principal-у на аккаунт, базу или контейнер. Здесь права гранулярны, а токен живёт недолго. Для атакующего это означает: украсть ключ проще, но если ключ отключён (`disableKeyBasedMetadataWriteAccess`, отключение local auth), остаётся либо токен managed identity сервиса, либо похищение токена пользователя. Проверяй оба пути, потому что мисконфиг часто оставляет включённым именно ключ.

## Инъекции в SQL API

Cosmos SQL-API — это запросы вида `SELECT * FROM c WHERE c.user = @u`. Параметризация (@u) безопасна; конкатенация строк — нет. Если приложение строит запрос склейкой, атакующий может изменить предикат и вытащить чужие документы (классический NoSQL-injection, аналог `$ne`/`$gt` в Mongo). Cosmos не исполняет произвольный код, поэтому эффект ограничен чтением/изменением данных, но это и есть цель. Ищи места, где пользовательский ввод попадает в запрос без параметров.

## Gremlin, Mongo и Cassandra API

Gremlin-API принимает Gremlin-запросы: `g.V().has(...)`. Здесь тоже возможна инъекция в предикаты, если строку собирают вручную. Mongo-API — та же логика операторов, что в MongoDB (`$ne`, `$regex`), и та же защита через параметры. Cassandra-API — CQL. Общее правило: любой API, который принимает запрос как строку, уязвим к инъекции при конкатенации. Проверяй, какой API включён на аккаунте, — от него зависит набор техник.

## Локальный эмулятор

Для разработки есть Cosmos DB Emulator — он поднимается локально и использует предсказуемый well-known key. Если эмулятор выставлен в сеть или его ключ попал в CI, атакующий читает тестовые данные и понимает схему, что помогает на проде. Эмулятор — не прод, но он раскрывает модели данных, имена контейнеров и часто содержит реальные дампы, залитые для отладки.

## Типовые мисконфиги

| Мисконфиг | Последствие | Как искать |
|---|---|---|
| Ключ в конфиге/репо | полный доступ к данным | grep AccountKey |
| Публичный доступ к аккаунту | доступ из интернета | firewall аккаунта |
| Ключ в CI/логах | утечка | переменные/логи |
| Конкатенация в запросе | инъекция | код приложения |
| Эмулятор в сети | раскрытие схемы | порты эмулятора |
| Избыточная роль Contributor | эскалация | data-plane RBAC |

## Полный прогон: от ключа к документам

Шаги. Первый: подтвердить ключ (`az cosmosdb` или REST с заголовком авторизации). Второй: перечислить базы и контейнеры. Третий: прочитать несколько документов, чтобы понять модель данных. Четвёртый: найти в документах секреты и персональные данные. Пятый: проверить, есть ли ключ в других сервисах (приложения, функции). Шестой: зафиксировать доступ и подумать о ротации ключа как о следе, который ты оставляешь.

## Инструменты и команды

Полезны: `az cosmosdb list`, `az cosmosdb keys list`, прямые REST-запросы к `https://<acct>.documents.azure.com/dbs` с заголовком `Authorization`, SDK для нужного API (`azure-cosmos`, `pymongo`, `gremlinpython`). Для поиска ключей — grep по конфигам, `.env`, CI-переменным. Для эмулятора — `curl` к локальному порту с well-known key.

## OPSEC и детект

Cosmos ведёт диагностические логи на уровне аккаунта; обращения по ключу видны как data-plane операции, но без имени пользователя. Массовое чтение всех контейнеров заметно по объёму. Тихий сценарий — прочитать один контейнер, где явно лежат нужные данные. Если в тенанте включён Defender for Cloud, подозрительный доступ по ключу из незнакомого IP даёт алерт.

## Частые вопросы

Можно ли обойти ключ через RBAC? Нет, это независимые пути. Работает ли ключ при отключённом local auth? Нет — тогда только Entra. Даёт ли ключ доступ к ARM? Нет, только к данным. Что если контейнер имеет partition key? Он влияет на запросы, но не на права. Помогает ли firewall? Да, он ограничивает источник, но ключ всё равно нужен.

## Что не сработает

Отключённый local auth не даст использовать ключ. Сетевой firewall не пустит с неразрешённого IP. Параметризованный запрос не даст инъекцию. Роль Data Reader не даст писать. И если приложение вообще не хранит секретов в Cosmos, читать будет нечего.

## Разбор кейса: ключ в мобильном приложении

История из практики. Команда положила строку подключения к Cosmos в мобильное приложение, «чтобы проще». Приложение декомпилировали, достали AccountKey и прочитали всю прод-базу: заказы, адреса, токены интеграций. Ключ был primary, ротация не проводилась. Урок: data-plane-ключ в клиенте — это публичный ключ. Для мобильных приложений нужен брокер resource token, а не ключ аккаунта.

## Что мы теперь знаем

1. Cosmos аутентифицирует данные ключом или Entra-RBAC — это два независимых пути.
2. Primary key равен полному admin-доступу к данным и не логируется как пользователь.
3. SQL/Gremlin/Mongo API уязвимы к инъекции при конкатенации запросов.
4. Эмулятор с well-known key раскрывает схему и тестовые данные.
5. Firewall ограничивает источник, но не заменяет управление ключами.

## Разделение на базы и контейнеры

Аккаунт Cosmos содержит базы, база — контейнеры, контейнер — документы, разложенные по partition key. Partition key определяет физическое разбиение данных и влияет на запросы: если в фильтре нет ключа раздела, запрос идёт по всем разделам (cross-partition) и стоит дороже. Для атакующего это две практические вещи. Первая: доступ и ключи выдаются на уровне аккаунта, базы или контейнера, поэтому смотри, на каком уровне выдан ключ, — от этого зависит, что ты видишь. Вторая: зная partition key, ты читаешь нужные данные точечно и тихо, не сканируя всю базу. Имена разделов часто угадываются: tenantId, userId, region. Это помогает быстро выбрать цель и не поднимать шум.

## Смена ключей и аудит

Утечка ключа — это инцидент с обязательной ротацией: перегенерировать оба ключа и обновить все приложения, иначе доступ сохраняется. В диагностических логах Cosmos видны операции data-plane, но по ключу нельзя понять, какой именно человек обращался. Поэтому защита строится на сетевом ограничении и отключении local auth, а детект — на аномалиях объёма и источника. Для пентестера это значит: не рассчитывай спрятаться за ключ — источник и объём операций всё равно фиксируются, а Defender for Cloud умеет отмечать доступ по ключу из неожиданного места.

## Cosmos и managed identity

Если приложение ходит в Cosmos не по ключу, а по managed identity, то утечка конфига не даёт доступа — нужен токен сервиса. Зато компромисс самого сервиса (App Service, Function) автоматически открывает данные, потому что токен выдаётся платформой. Проверяй оба сценария: строку подключения в конфиге и права identity сервиса. В одном приложении часто встречаются оба, и путь через identity оказывается короче, потому что не требует искать секрет.
