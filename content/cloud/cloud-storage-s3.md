## Вопрос, с которого всё начинается

Компания хранит бэкапы и конфиги в облаке. Ты не знаешь ни ключей, ни аккаунта — только домен компании. Реально ли добраться до её данных, вообще не имея доступа?

Да, если хранилище настроено неверно. В облаке данные лежат в **объектных хранилищах** — S3 у AWS, Cloud Storage у GCP, Blob Storage у Azure. Это не диски, а плоские «склады» объектов: у каждого объекта есть имя (ключ) и содержимое, а доступ определяется политиками. Ошибка в политике — и склад открыт всему интернету.

## Наш пример: бакет acme-backups

Пойдём от простого. По названию компании `acme` предположим имя бакета. **Бакет** — это контейнер для объектов; у AWS его имя глобально уникально и часто совпадает с названием компании.

Проверим, отвечает ли он анонимно. Флаг `--no-sign-request` означает «запрос без учётных данных» — мы стучимся как случайный прохожий:

```
$ aws s3 ls s3://acme-backups --no-sign-request
                           PRE db/
                           PRE configs/
```

Сработало. `PRE` — это «префикс», аналог папки: в объектном хранилище нет настоящих директорий, «путь» — просто часть имени ключа. Значит, анонимный **ListBucket** (право перечислять содержимое) разрешён. Посмотрим глубже:

```
$ aws s3 ls s3://acme-backups/configs/ --no-sign-request
2024-06-01 09:10:11        412 app.env
2024-06-01 09:10:11       2048 db.conf
```

## Шаг 1: скачиваем объект (GetObject)

Право **GetObject** — читать конкретный объект по имени. Скачаем `app.env` — файл с переменными окружения, где разработчики обычно держат ключи:

```
$ aws s3 cp s3://acme-backups/configs/app.env . --no-sign-request
$ cat app.env
AWS_ACCESS_KEY_ID=AKIAIOSFODNN7EXAMPLE
AWS_SECRET_ACCESS_KEY=wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY
```

Один анонимный запрос дал ключи доступа к аккаунту. Это и есть типичная цепочка: утечка хранилища → креденшелы → полный доступ. Проверим ключи так же, как в уроке про охоту за секретами:

```
$ aws sts get-caller-identity
{ "Account": "123456789012", "Arn": "arn:aws:iam::123456789012:user/backup-bot" }
```

## Шаг 2: почему бакет вообще открылся

За доступ отвечают несколько механизмов, и важно понимать, какой сработал:

- **Bucket policy** — JSON-политика на весь бакет. Классическая утечка — разрешение для всех:
  ```json
  {"Effect":"Allow","Principal":"*","Action":"s3:GetObject",
   "Resource":"arn:aws:s3:::acme-backups/*"}
  ```
  Здесь `Principal: "*"` означает «любой», а без условия это делает объекты публичными.
- **ACL** — старая модель прав на объект или бакет (`READ`, `WRITE`).
- **IAM policy** — права конкретной учётной записи.
- **Block Public Access** — «рубильник», который перекрывает публичные политики, даже если те разрешают доступ.

Посмотрим, что настроено у нашего бакета:

```
$ aws s3api get-public-access-block --bucket acme-backups --no-sign-request
An error occurred (NoSuchPublicAccessBlockConfiguration): ...
```

Вывод: защита `Block Public Access` не включена — поэтому публичная политика и сработала.

## Шаг 3: запись в бакет — PutObject

Право **PutObject** позволяет загружать свои файлы. Это опаснее, чем кажется: на доверенном домене можно разместить фишинговую страницу или вредоносный JS. Проверяем аккуратно — только маркером, чтобы ничего не разрушить:

```
$ echo "test-marker" > poc.txt
$ aws s3 cp poc.txt s3://acme-backups/ --no-sign-request
upload: ./poc.txt to s3://acme-backups/poc.txt
```

Загрузка прошла — бакет writable. Убери маркер сразу после проверки: `aws s3 rm s3://acme-backups/poc.txt --no-sign-request`.

## Шаг 4: версии «удалённых» объектов

Если включено **версионирование**, удалённый объект не исчезает: создаётся delete-marker, а старая версия остаётся. Часто в старой версии лежит то, что «почистили»:

```
$ aws s3api list-object-versions --bucket acme-backups --no-sign-request \
  --query 'Versions[].{Key:Key,VersionId:VersionId,Size:Size}' --output table
```

Так секрет, удалённый из текущего файла, всё ещё читается по `VersionId`.

## Шаг 5: подписанные ссылки (presigned URL)

Иногда бакет закрыт, но кто-то поделился ссылкой на объект. Такая ссылка называется **presigned URL** — она подписана ключом владельца и действует ограниченное время. Выглядит так:

```
https://acme-backups.s3.amazonaws.com/db/dump.sql?X-Amz-Expires=604800&X-Amz-Credential=AKIA...
```

Внутри видно `X-Amz-Expires` (срок жизни в секундах: 604800 — это неделя) и `X-Amz-Credential`, где светится идентификатор ключа и регион. Слишком длинный срок — риск: если ссылка утечёт, доступ останется надолго. Разобрать параметры можно так:

```
$ echo 'https://acme-backups.s3.amazonaws.com/f?X-Amz-Expires=604800&X-Amz-Credential=AKIA...' \
  | tr '&' '\n' | grep -E 'Expires|Credential'
X-Amz-Expires=604800
X-Amz-Credential=AKIA...
```

## Шаг 6: ищем бакеты массово

Вручную угадывать имена долго. Инструменты:

```
$ cloud_enum -k acme -k acme-backup --quickscan
$ s3scanner scan --bucket acme-backups
$ trufflehog s3 --bucket acme-backups
```

`cloud_enum` перебирает вариации имён (`acme`, `acme-dev`, `acme-assets`), `s3scanner` проверяет права (list/read/write), `trufflehog` ищет секреты внутри. Полезны и поисковые дорки: `site:s3.amazonaws.com "index of" acme`.

## То же самое у GCS и Azure

Логика одинакова, отличаются названия и «рубильники»:

| Возможность | AWS S3 | GCP Cloud Storage | Azure Blob |
|-------------|--------|-------------------|------------|
| Публичный доступ | bucket policy + Block Public Access | IAM для `allUsers` + public access prevention | access level контейнера + Allow Blob public |
| Анонимный листинг | ListBucket | `storage.objects.list` для allUsers | public container |
| Подписанные ссылки | presigned URL | signed URL | SAS-токен |
| Имена | глобально уникальны | глобально уникальны | уникальны в аккаунте |

Ещё один слой — **шифрование**. У S3 это `SSE-S3` (ключи провайдера, прозрачно) и `SSE-KMS` (ключи в сервисе KMS). Во втором случае `AccessDenied` при чтении объекта может означать не отсутствие `s3:GetObject`, а запрет на `kms:Decrypt`:

```
$ aws s3api get-bucket-encryption --bucket acme-backups --no-sign-request
```

Если видишь `SSE-KMS`, проверь политику ключа — иногда она разрешает расшифровку слишком широкому кругу лиц.

## Что мы теперь знаем

1. Объектное хранилище — плоский склад объектов; «папки» — лишь префиксы в именах.
2. Ключевые права: ListBucket (список), GetObject (чтение), PutObject (запись).
3. Публичность задаётся bucket policy/ACL, а Block Public Access может её перекрыть.
4. Ключи из `.env` внутри бакета часто дают доступ ко всему аккаунту.
5. Версионирование хранит «удалённые» секреты.

## На что смотреть дальше

- **«Private policy» ≠ безопасно.** Проверяй ACL и Block Public Access.
- **Ответ 403 тоже информативен.** Листинг закрыт, но объект по прямому ключу может читаться — проверь `HeadObject`.
- **Не качай всё подряд.** Массовое скачивание шумит и стоит владельцу денег; сначала метаданные, потом точечно.
- **Проверяй CORS и website-конфиг.** Широкий `AllowedOrigin: *` и статический хостинг превращают бакет в вектор XSS.

## Глазами защитника

S3 защищают Block Public Access на уровне аккаунта и бакета, bucket policies без `Principal: *`, отключённый ACL (Object Ownership). Включают versioning и логирование доступа, шифрование. Presigned URL делают короткоживущими. Аудит: какие бакеты публичны, кто может писать, есть ли старые версии с секретами. Помнят, что «удалённый» объект живёт в версиях.

## Частые вопросы

**Чем ACL отличается от bucket policy?**

ACL — старый механизм на уровне объекта и бакета; bucket policy — resource policy. Ошибка в любом открывает доступ.

**Почему бакет открылся?**

Публичный bucket policy, ACL `public-read` или отсутствие Block Public Access. Проверяй политику и статус публичности.

**Что даёт версионирование?**

Даже после удаления объекта старая версия остаётся доступной. Это часто источник «удалённых» секретов.

**Что такое presigned URL?**

Временная подписанная ссылка на объект. Утечка даёт доступ до истечения срока.

**Как искать бакеты массово?**

По именам компаний, сканерами, через список бакетов при наличии прав. Часто имя бакета совпадает с доменом.

**Что искать в бакете?**

Бэкапы, `.env`, terraform state, дампы, конфиги — новые креды и данные.

**Как защититься?**

Block Public Access, узкие политики, отключённый ACL, шифрование, короткие presigned URL, аудит.

**Помогает ли Object Ownership?**

Да, он отключает ACL и передаёт контроль владельцу бакета, убирая целый класс ошибок с ACL.

## Разбор: публичный бакет с бэкапами

Бакет `acme-backups` доступен на чтение всем. Атакующий листит его через `aws s3 ls s3://acme-backups --no-sign-request` и находит дамп БД и `.env`. Скачивает их и получает пароль к продовой БД. Даже если объект потом удалили, версия осталась. Защита — Block Public Access на аккаунте, узкие политики и контроль доступа к версиям.

## Что чаще всего упускают

Версии: «удалённый» объект остаётся доступным, если версионирование включено. Второе — presigned URL: бакет может быть закрыт, а ссылка открыта. Третье — ACL на объектах при включённом bucket policy: доступ может открываться в обход политики. Вывод: проверяй все механизмы доступа, а не только статус публичности бакета.

**Можно ли перезаписать публичный бакет?**

Только при наличии прав на запись; иначе он остаётся источником утечки. Проверь политику на `s3:PutObject`.

**Что даёт `s3:ListAllMyBuckets`?**

Список всех бакетов аккаунта — быстрая карта целей без угадывания имён.

**Что даёт флаг `--no-sign-request`?**

Анонимный запрос к S3 без кред. Если бакет публичный, вернётся листинг или объект — быстрый тест на публичность.
