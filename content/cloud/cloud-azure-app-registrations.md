## Вопрос, с которого всё начинается

В Azure каждое приложение, обращающееся к Microsoft Graph или к ресурсам, регистрируется как **app registration**. У неё есть права и секрет. Если секрет утёк, приложение можно выдать за себя и работать со всеми его правами — а они бывают очень широкими. Разберём одну такую регистрацию.

**App registration** — это «паспорт» приложения в каталоге Entra ID. Когда приложение входит в Azure, оно представляется через **service principal** — экземпляр регистрации в конкретном тенанте.

## Наш пример: приложение reporting-app

Объект урока — app registration `reporting-app` с client secret. Допустим, у нас есть доступ к каталогу и мы хотим оценить риск.

## Шаг 1: находим приложение

Перечислим регистрации:

```
$ az ad app list --query "[].{name:displayName, appId:appId}" -o table
Name           AppId
reporting-app  c3f1d2e4-...
sp-admin-tool  7a8b9c0d-...
```

Берём `reporting-app`. Дальше смотрим его права и секреты.

## Шаг 2: читаем API permissions

У приложения есть разрешения (API permissions) на ресурсы. Посмотрим их:

```
$ az ad app permission list --id c3f1d2e4-...
[
  { "resourceAppId": "00000003-0000-0000-c000-000000000000",
    "resourceAccess": [ { "id": "810c84a8-...", "type": "Role" } ] }
]
```

`00000003-...` — Microsoft Graph. Тип `Role` — **application permission** (работает без пользователя). Расшифруем конкретное право:

```
$ az ad sp show --id 00000003-0000-0000-c000-000000000000 \
    --query "appRoles[?id=='810c84a8-...'].{name:displayName,value:value}"
[ { "name": "Mail.Read", "value": "Mail.Read" } ]
```

`Mail.Read` — приложение может читать почту **всех** пользователей тенанта. Одно утёкшее приложение = доступ к переписке компании.

## Шаг 3: находим client secret

У приложения может быть секрет или сертификат для входа. Смотрим:

```
$ az ad app credential list --id c3f1d2e4-...
[
  { "keyId": "...", "displayName": "ci-secret",
    "startDateTime": "2024-01-01T00:00:00Z", "endDateTime": "2026-01-01T00:00:00Z" }
]
```

`ci-secret` живёт **два года**. Если он утёк — два года доступа. Значение секрета показывается только при создании, но если оно попало в репозиторий или переменные CI, оно уже «в дикой природе».

## Шаг 4: получаем токен по секрету

Если у нас есть `appId` и секрет, получаем токен на Graph:

```
$ curl -s -X POST "https://login.microsoftonline.com/72f988bf-.../oauth2/v2.0/token" \
    -d "client_id=c3f1d2e4-..." \
    -d "client_secret=SECRET" \
    -d "scope=https://graph.microsoft.com/.default" \
    -d "grant_type=client_credentials"
{"access_token":"eyJ0eXAiOiJKV1Qi...","expires_in":3599,"token_type":"Bearer"}
```

`grant_type=client_credentials` — вход без пользователя, только приложением. Дальше работаем с Graph.

## Шаг 5: используем доступ

Читаем почту, скажем, финансового директора:

```
$ curl -s -H "Authorization: Bearer eyJ0eXAi..." \
    "https://graph.microsoft.com/v1.0/users/cfo@acme.onmicrosoft.com/messages?\$top=5"
{"value":[{"subject":"Q3 acquisition plan", ...}]}
```

Мы прочитали почту без единого пароля пользователя. Так же читаются файлы (SharePoint), каталог, календари — всё, на что есть права у приложения.

## Шаг 6: admin consent — важная деталь

Application permissions обычно требуют **admin consent** — одобрения администратора. Но часто админ выдаёт consent «на всё приложение» сразу, и тогда у приложения появляется широкий доступ навсегда. Для атакующего это означает: одного украденного секрета достаточно, чтобы воспользоваться уже одобренными правами. Ещё есть **illicit consent** — злоумышленник регистрирует своё приложение и убеждает пользователя нажать «Разрешить», получая доступ к его данным.

## Шаг 7: как эскалировать

С `AppRoleAssignment.ReadWrite.All` или `Application.ReadWrite.All` можно **самому выдать** приложению любые права или создать новое приложение. Это прямой путь к контролю каталога. А через гибридную синхронизацию — и к локальному AD. Поэтому app registrations — один из главных векторов эскалации в Azure.

## Шаг 8: как защищаться

- минимизировать application permissions и удалять лишние;
- использовать сертификаты и короткие сроки вместо долгих секретов;
- хранить секреты в Key Vault, а не в репозиториях;
- ограничить, кто может выдавать admin consent;
- мониторить создание новых регистраций и выдачу прав.

## Шаг 9: практический чек-лист оценки

Для каждого приложения собери: (1) список секретов и сертификатов и их сроки; (2) API permissions — отдельно application и delegated; (3) наличие admin consent; (4) кто владелец приложения и кто может выдавать consent. Затем выдели приложения с широкими application permissions (`Mail.Read`, `Files.ReadWrite.All`, `Directory.ReadWrite.All`) — это главные цели. И проверь, кто вообще может создавать регистрации: если это доступно широкому кругу, путь к эскалации открыт.

## Шаг 10: illicit consent — атака на пользователя

Отдельный вектор — **незаконный consent**. Злоумышленник регистрирует своё приложение с delegated-разрешением, например `Mail.Read`, и отправляет жертве ссылку «Разрешить доступ». Пользователь нажимает — и приложение получает доступ к его почте, причём без пароля. Защита — запрещать пользователям выдавать consent (admin consent workflow) и мониторить новые регистрации и выданные согласия. С точки зрения пентеста это ещё один способ добраться до данных, не трогая учётные записи напрямую.

## Шаг 11: шпаргалка по app registrations

Три вопроса решают всё: какие application permissions выданы (и одобрены ли через admin consent), какие секреты существуют и сколько живут, кто может создавать регистрации и выдавать согласия. Если ответы «широкие права», «долгий секрет», «многие могут» — каталог под угрозой.

## Шаг 12: где это встречается в CTF

В CTF Azure-задачи часто дают `appId` и client secret в файле конфигурации или переменных. Задача — получить токен на Graph и прочитать флаг из почты, файлов или каталога. Схема ровно та, что мы разобрали: секрет → токен → данные. Главное — не забыть про `grant_type=client_credentials` и правильный scope.

## Практический совет

Смотри в первую очередь на приложения с широкими application permissions и долгими секретами — это главные цели.

## Частые вопросы

**«Что такое service principal?»** Это экземпляр app registration в конкретном тенанте — «действующее лицо» приложения.

**«Почему application permission опаснее delegated?»** Он работает без пользователя и сразу даёт доступ ко данным всего тенанта.

**«Что делать с долгими секретами?»** Считать их риском: два года жизни секрета — два года доступа для того, кто его украл.

**«Что такое illicit consent?»** Атака, при которой пользователя убеждают нажать «Разрешить» и выдать приложению доступ к своим данным.

## Что мы теперь знаем

По-простому:

1. App registration — «паспорт» приложения, service principal — его экземпляр.
2. API permissions типа Role работают без пользователя.
3. Client secret позволяет получить токен и работать со всеми правами.
4. Admin consent одобряет права приложения навсегда.
5. Право менять регистрации — путь к контролю каталога.

## На что смотреть дальше

- **Ищи application permissions.** Они не требуют пользователя.
- **Смотри сроки секретов.** Долгий секрет — долгий доступ.
- **Проверяй admin consent.** Одобренные права уже активны.
- **Помни про illicit consent.** Пользователь может выдать доступ сам.

## Куда дальше

Мы разобрали app registrations. Дальше — **разросшиеся секреты**: где в облаке утекают ключи (репозитории, логи, артефакты) и как их находить и валидировать. А пока запомни главное: утёкший секрет приложения с широкими правами — это постоянный доступ к данным всей компании.

## Где пригодится

- **Пентест:** аудит app registrations и consent.
- **Bug bounty:** over-permissive приложения.
- **Red team:** доступ к Graph через украденный секрет.
- **Blue team:** минимизация permissions, короткие секреты, контроль consent.
