## Зачем этот урок

Облачный инцидент отличается от традиционного: нет физического периметра, ресурсы эфемерны, а атакующий действует через API. Поэтому IR в облаке строится вокруг **идентичностей, логов и API**. Этот урок — практический playbook: что делать по фазам, какие команды выполнять, как сохранять доказательства и как искать закрепление. Он полезен и blue team, и red team (чтобы понимать, как вас будут искать), и пентестеру (чтобы оценивать готовность заказчика).

## Фазы облачного IR

1. **Подготовка.** Доступ к логам (CloudTrail/Activity Log/Audit Logs), SIEM, права на изоляцию, контакты, runbooks, заранее определённые «break-glass» аккаунты.
2. **Обнаружение и анализ.** Что произошло, кто, когда, откуда. Источники: GuardDuty/Defender/SCC findings, CloudTrail, flow logs, SIEM.
3. **Сдерживание.** Остановить распространение: отозвать сессии, отключить/ротировать ключи, изолировать ресурсы, заблокировать сеть.
4. **Устранение.** Удалить персистентность: нежелательные пользователи/ключи, роли, Lambda, SSM-ассоциации, ресурсы.
5. **Восстановление.** Вернуть сервисы, ротировать все затронутые креды, проверить целостность.
6. **Уроки.** Улучшить детект и контроль, обновить runbooks.

Ключевые принципы: **сохраняй доказательства до изменений**, **ротируй все креды, которые могли быть затронуты**, **ищи персистентность**, **не удаляй ресурсы до сбора форензики**.

## Инструменты и команды

Первичная триаж-разведка:

```bash
# Кто и что делал (CloudTrail)
aws cloudtrail lookup-events --lookup-attributes AttributeKey=AccessKeyId,AttributeValue=AKIA... \
  --start-time 2026-10-01T00:00:00Z --max-results 50

# Активность principal
aws cloudtrail lookup-events --lookup-attributes AttributeKey=Username,AttributeValue=attacker \
  --max-results 50

# GuardDuty findings
aws guardduty list-findings --detector-id <id> --finding-criteria '{"Criterion":{"service.archived":{"Eq":["false"]}}}'
```

Сдерживание:

```bash
# Отозвать временные сессии роли (revoke)
aws iam put-role-policy --role-name compromised-role --policy-name revoke \
  --policy-document '{"Version":"2012-10-17","Statement":[{"Effect":"Deny","Action":"*","Resource":"*","Condition":{"DateLessThan":{"aws:TokenIssueTime":"2026-10-11T00:00:00Z"}}}]}'

# Деактивировать ключ пользователя
aws iam update-access-key --access-key-id AKIA... --status Inactive --user-name attacker

# Удалить/заблокировать IAM-пользователя (после сбора)
aws iam delete-login-profile --user-name attacker

# Изолировать инстанс (заменить SG)
aws ec2 modify-instance-attribute --instance-id i-0abc --groups sg-quarantine
```

Форензика:

```bash
# Снапшот тома для анализа (не запускать на живом)
aws ec2 create-snapshot --volume-id vol-0abc --description "IR evidence"

# Скачать логи CloudTrail из бакета
aws s3 sync s3://audit-logs/AWSLogs/123456789012/CloudTrail/ ./trail/

# Запросить через CloudTrail Lake (SQL)
aws cloudtrail start-query --query-statement \
  "SELECT eventTime, eventName, userIdentity.arn FROM <eventDataStoreId> WHERE userIdentity.accessKeyId='AKIA...'"
```

## Разобранный пример: расследование компрометации ключа

Сценарий: GuardDuty выдал finding о необычном использовании ключа `AKIA...`.

Шаг 1 — **не удалять ключ сразу**. Сначала собираем контекст. Находим все события по ключу:

```bash
aws cloudtrail lookup-events --lookup-attributes AttributeKey=AccessKeyId,AttributeValue=AKIA... \
  --start-time 2026-10-09T00:00:00Z --output json > key-activity.json
```

Шаг 2 — строим таймлайн: какие API, из каких IP, в каком порядке. Ищем первый вызов (входная точка), затем эскалацию (`CreateUser`, `AttachUserPolicy`, `CreateAccessKey`, `PassRole`, `CreatePolicyVersion`).

Шаг 3 — определяем, кто ключ использовал: `userIdentity`, `sourceIPAddress`, `userAgent`. Если IP внешний и User-Agent — CLI/SDK, это атакующий.

Шаг 4 — **сдерживание**: отзываем сессии роли (revoke policy), деактивируем ключ, изолируем затронутые ресурсы. Но **до** удаления сохраняем доказательства (снапшоты, логи).

Шаг 5 — **поиск персистентности**. Атакующий мог создать:

```bash
# Новые пользователи и ключи
aws iam list-users
aws iam list-access-keys --user-name <user>

# Роли с подозрительными trust policies
aws iam list-roles --query 'Roles[].{Name:RoleName,Trust:AssumeRolePolicyDocument}'

# Lambda-функции (backdoor)
aws lambda list-functions

# SSM-ассоциации (persistence)
aws ssm list-associations

# Новые инстансы/ресурсы
aws ec2 describe-instances --filters Name=instance-state-name,Values=running
```

Шаг 6 — **устранение**: удаляем всё, что создал атакующий, но фиксируем в отчёте. Ротируем **все** креды, которые могли быть затронуты (не только ключ): другие ключи пользователя, роли, которые он мог ассумировать, секреты.

Шаг 7 — **восстановление**: возвращаем сервисы, проверяем, что доступы восстановлены корректно и не осталось backdoor. Мониторим на повторное появление индикаторов.

Шаг 8 — **уроки**: почему ключ утёк, почему детект сработал/не сработал, что улучшить.

## Варианты и подводные камни

- **Удаление ключа до сбора.** Теряются доказательства и понимание объёма. Сначала — логи и контекст.
- **Смена пароля вместо отзыва сессий.** Временные креды остаются валидными; нужен revoke policy.
- **Ротация только одного ключа.** Атакующий мог создать другие; ротируйте все и ищите новые.
- **Игнорирование персистентности.** IAM-пользователи, Lambda, SSM, роли, launch templates — частые backdoor.
- **Удаление ресурсов до форензики.** Снапшот и логи нужно сохранить.
- **Отсутствие логов.** Если CloudTrail не был включён, расследование почти невозможно — это находка сама по себе.
- **Организация.** Инцидент может затрагивать несколько аккаунтов; проверьте trust и cross-account.

## Доказательства и их сохранность

- **Логи:** CloudTrail (S3 + CloudWatch), flow logs, GuardDuty findings, приложенческие логи. Экспортируйте в изолированный аккаунт/бакет.
- **Диски:** снапшоты EBS/дисков для офлайн-анализа (монтирование в изолированном аккаунте).
- **Память:** в облаке обычно недоступна без агента; фиксируйте это ограничение.
- **Метаданные:** теги, время создания/изменения ресурсов, история развёртываний.
- **Цепочка хранения:** хэшируйте и фиксируйте доступ к доказательствам.
- **Время:** синхронизируйте часовые пояса; CloudTrail — UTC.

## Защита (профилактика)

- **Логи везде и изолированно** (org trail, отдельный аккаунт, Object Lock).
- **GuardDuty/Defender/SCC включены** на всех аккаунтах и регионах, findings в SIEM.
- **MFA и короткоживущие креды**, запрет долгоживущих ключей (org policy).
- **Least privilege** и permission boundaries; периодический аудит.
- **Break-glass процедуры** для IR (доступ к логам и изоляции).
- **Runbooks** для типовых сценариев (утечка ключа, публичный бакет, компромисс EC2).
- **Автоматизация реакции** (Lambda/Logic App на findings).

## Форензика в облаке: что реально доступно

Классическая форензика (память, живой диск) в облаке ограничена:

- **Память.** Без заранее установленного агента дамп памяти получить нельзя; для живых инстансов это редко возможно. Фиксируйте это ограничение в отчёте.
- **Диск.** Снапшот EBS/диска — основной источник. Анализируйте в изолированном аккаунте, чтобы не загрязнить среду. Монтируйте снапшот как дополнительный диск на forensic-инстанс.
- **Логи.** CloudTrail/Activity Log/Audit Logs — основной источник таймлайна. Экспортируйте в изолированное хранилище до изменений.
- **Метаданные.** Теги, время создания/обновления ресурсов, история развёртываний, изменения IAM — восстанавливают часть картины.
- **Сетевые данные.** Flow logs, DNS-логи, GuardDuty findings.
- **Контейнеры.** Логи контейнеров, образы (digest), audit logs API-сервера, Falco/детект-события.

Порядок: сначала **экспорт логов** (они могут исчезнуть по retention или быть удалены атакующим), затем **снапшоты** для анализа, затем построение таймлайна. Никогда не начинайте с удаления/остановки ресурсов — это уничтожает доказательства.

## Практический чек-лист IR

1. Подтвердить инцидент (finding, алерт, жалоба) и определить scope (какие аккаунты/сервисы).
2. Немедленно экспортировать логи в изолированное хранилище.
3. Сделать снапшоты затронутых дисков/инстансов.
4. Построить таймлайн по CloudTrail: первый подозрительный вызов, principal, IP, User-Agent.
5. Определить входную точку (утечка ключа, SSRF, публичный ресурс).
6. Сдержать: revoke-сессии, деактивировать ключи, изолировать ресурсы (SG quarantine).
7. Найти персистентность: IAM-пользователи/ключи, роли, Lambda, SSM, launch templates, webhooks.
8. Устранить: удалить найденное (зафиксировав в отчёте).
9. Восстановить: ротировать **все** потенциально затронутые креды, вернуть сервисы.
10. Мониторить повторное появление индикаторов; извлечь уроки и обновить runbook.

Этот чек-лист — скелет реакции; для каждого типа инцидента (утечка ключа, публичный бакет, компромисс EC2) его детализируют в runbook.

## Коммуникация, координация и роли

Облачный инцидент почти всегда затрагивает несколько команд: security/IR, платформенная команда (владеет аккаунтом), разработчики (владеют сервисом), иногда юридические и коммуникационные. Ключевые практики:

- **Единая точка координации.** Один инцидент-менеджер, один канал связи, единый таймлайн.
- **Разделение ролей.** Кто-то собирает форензику, кто-то сдерживает, кто-то общается. Не смешивайте — иначе действия конфликтуют.
- **Осторожно с разрушительными действиями.** Удаление ресурсов/ключей до согласования лишает доказательств и может нарушить бизнес; фиксируйте каждое решение.
- **Согласование с бизнесом.** Ротация ключей может сломать сервисы; предупредите и запланируйте окно.
- **Документирование в реальном времени.** Каждое действие с временем, исполнителем и обоснованием — основа будущего отчёта и разбора.
- **Облачный провайдер.** Для серьёзных инцидентов может потребоваться поддержка провайдера (AWS Support/Azure/Microsoft), особенно при удалении аккаунтов/данных.
- **Уведомления.** Регуляторные и клиентские уведомления — по политике организации.

Для пентестера этот раздел объясняет, почему заказчик может быть медленным и осторожным: каждое действие имеет цену. В отчёте полезно указать, что destructive-демонстрации требуют согласования и не входят в стандартный объём.

## Что дальше / решение

Облачный IR — это дисциплина работы с идентичностями и логами. Порядок действий: сохранить доказательства → построить таймлайн → определить входную точку и объём → сдержать (revoke, изоляция) → устранить персистентность → восстановить с ротацией всех кредов → извлечь уроки. Никогда не удаляйте ресурсы до сбора форензики и не ротируйте только один ключ. Для пентестера этот playbook — карта того, как вас будут искать: действуйте тихо и не создавайте явных backdoor. Для blue team — основа готовности. Записывайте индикаторы и рекомендации как находки отчёта.
