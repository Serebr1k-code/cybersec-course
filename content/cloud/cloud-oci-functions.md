## Вопрос, с которого всё начинается

Ты нашёл в репозитории код serverless-функции, которая работает в Oracle Cloud. Ключей рядом нет — их там и не должно быть: функция получает права автоматически, от имени специального principal. Вопрос: как именно это работает, и что сможет сделать атакующий, если получит возможность менять код или конфигурацию функции? Ответ — и есть путь к захвату прав, выданных сервису.

## Что такое OCI Functions

Functions — serverless-платформа OCI: ты пишешь функцию, кладёшь её в образ, деплоишь в приложение (application), и она запускается по событию или HTTP. Секретов внутри кода нет — код получает **resource principal**: токен, удостоверяющий саму функцию как ресурс. Права этому principal даёт dynamic group (мы разбирали её в уроке про IAM). Так функция читает Object Storage, обращается к БД и другим сервисам, не храня ни одного ключа.

## Сквозной пример: функция и её конфиг

Смотрим конфиг и код:
```
$ cat func-config.json
{
  "application": "reports",
  "function": "render-report",
  "dynamic_group": "fn-reports",
  "memory_mb": 256,
  "config": {"BUCKET": "reports", "PREFIX": "daily/"}
}
```
```
$ cat func.py
def handler(ctx, data):
    p = principal.get_resource_principal()
    ...
```
Функция входит в dynamic group `fn-reports`. Значит, её права — это права группы. Дальше выясняем, что умеет `fn-reports`: если у неё `manage` на бакеты или больше, то код функции — это и есть доступ.

## Как выдаются права resource principal

Ресурс (функция, инстанс) аутентифицируется в OCI автоматически: платформа выдаёт короткоживущий токен resource principal, а IAM сопоставляет его с dynamic group по matching rule. Ключевое следствие: **компромисс кода = компромисс прав группы**. Не нужен ни пароль, ни ключ — достаточно заставить функцию выполнить твой код. А заставить её это сделать можно через инъекцию в пользовательский ввод.

## Инъекции в функцию

Serverless-функция принимает события. Если функция строит запрос к БД или к другому сервису склейкой строк, ввод атакующего может изменить поведение. Классические векторы:
- **command injection** — если код вызывает shell с частью события;
- **SQL/NoSQL injection** — если запрос собирается конкатенацией;
- **SSRF** — если функция делает HTTP-запрос по URL из события (а metadata-эндпоинт может отдать креды);
- **template injection** — если рендерится шаблон с пользовательскими данными.

Через любую из них выполняется код внутри функции — то есть уже под resource principal. Эффект: чтение/запись данных, доступ к другим сервисам группы.

## API Gateway как точка входа

API Gateway публикует функции наружу: маршрут `/reports/render` → функция. Здесь свои мисконфиги: отсутствие авторизации на маршруте, слишком широкий CORS, логирование тел запросов (утечка секретов в логи). Если маршрут не защищён, атакующий вызывает функцию напрямую — и это уже эксплуатация, а не разведка.

## Захват через конфигурацию

Отдельный вектор — не код, а **конфигурация**. Переменные окружения функции (`config`) часто содержат секреты: строки подключения, токены. Если у атакующего есть `manage functions` в IAM, он может прочитать конфиг или **изменить код** функции на свой и перезапустить её — получив resource principal группы. Это персистентность: функция продолжает работать и ходить под своими правами, пока её не заметят.

## Как проверить руками

```
$ oci fn application list --compartment-id <ocid>
$ oci fn function list --application-id <ocid>
$ oci fn function get --function-id <ocid>
```
Последняя команда покажет конфиг и образ. Дальше — сопоставь dynamic group функции с её политиками: именно это определяет масштаб последствий.

## OCI Functions: как устроены и где ломаются

OCI Functions (Fn Project) — serverless: функции в контейнерах, запускаемые по событию (API Gateway, Events, cron). Поверхность: (1) application с недостаточными правами или, наоборот, с широкой dynamic group; (2) переменные окружения функции с секретами; (3) доступ к метаданным инстанса, если функция запущена на инстансе; (4) образ функции из публичного реестра (supply chain).

```text
function -> dynamic group -> policies -> resources
```

Ключевой риск: функция наследует права dynamic group, и если она широкая, вызов функции даёт эти права.

## Практика: анализ и эксплуатация

Что проверять: (1) список приложений и функций; (2) конфигурацию (env, image, timeout); (3) dynamic group и policies; (4) точки вызова (API Gateway, Events); (5) секреты в env. Инструменты: `oci fn`, `oci iam`, `oci ce`. Эксплуатация: если есть `InvokeFunction`, вызови функцию с контролируемым входом и посмотри, что она делает (инъекция, чтение ресурсов).

```bash
oci fn function list --application-id <id>
oci fn function get --function-id <id>
```

Типичная находка — секреты в переменных окружения функции.

## Защита

Меры: минимальные dynamic group и policies, секреты в Vault (не в env), образы из доверенного реестра с фиксированными тегами, ограничение вызова функции, логирование. Для пентеста — чтение конфигурации; вызов — только в тестовом тенанте.

## Расширенный разбор: dynamic group и права

Функция выполняется от имени сервиса и получает права через **dynamic group** — правило, которое сопоставляет ресурсы (например, функции конкретного приложения) с группой. Если правило широкое (все функции компартмента), любая функция наследует широкие права. Проверь правило и политики группы.

```bash
oci iam dynamic-group list --compartment-id <tenancy>
oci iam policy list --compartment-id <tenancy>
```

Типичная находка — dynamic group с `manage all-resources`, дающая функции полный доступ.

## Расширенный разбор: env и секреты

Переменные окружения функции содержат конфигурацию, часто секреты (пароли БД, ключи API). Они видны при `oci fn function get` (в некоторых конфигурациях) или через ошибки функции. Проверь env и оцени, что там лежит. Правильно — хранить секреты в OCI Vault и подтягивать во время выполнения.

```bash
oci fn function get --function-id <id> | jq .data.config
```

Если секреты в env — это находка (они утекают при чтении конфигурации).

## Защита и вывод

Меры: минимальные dynamic group и policies, секреты в Vault, доверенные образы, ограничение вызова, логирование. Вывод: serverless-функция наследует права dynamic group, поэтому её конфигурация и права — ключевые точки аудита.

## Что мы теперь знаем

- Functions получают права через resource principal + dynamic group, без ключей в коде.
- Компромисс кода функции = компромисс прав её группы.
- Инъекции (command/SQL/SSRF/template) выполняют код под resource principal.
- API Gateway без авторизации даёт прямой вызов функции.
- `manage functions` позволяет подменить код/конфиг и закрепиться.
