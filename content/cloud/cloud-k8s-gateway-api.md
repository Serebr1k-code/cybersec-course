## Вопрос, с которого всё начинается

Ты тестируешь приложение за Kubernetes Gateway API. Вопрос: как устроены маршруты, можно ли обойти path-матчинг, есть ли доступ к бэкендам из других namespace, и можно ли через фильтры заставить шлюз сходить не туда. Начнём с того, что Gateway API — это набор CRD (Gateway, HTTPRoute), и правила матчинга определяют, какой трафик куда попадёт, а их неточность даёт обход.

## Что такое Gateway API

Gateway API — преемник Ingress: вместо одного объекта Ingress есть GatewayClass (реализация, например Envoy/NGINX), Gateway (точка входа с listeners) и HTTPRoute (правила маршрутизации). Роут матчит запрос по hostname, path (PathPrefix, Exact, RegularExpression) и заголовкам, затем направляет на backendRefs (Service). Плюс фильтры: URLRewrite, RequestHeaderModifier, RequestRedirect. Это более выразительная модель, но и больше места для мисконфигов.

## Сквозной пример: HTTPRoute

Смотрим роут:
```
$ kubectl get httproute acme-route -o yaml
spec:
  rules:
    - matches: [ { path: { type: PathPrefix, value: /api } } ]
      backendRefs: [ { name: api-svc, port: 80 } ]
    - matches: [ { path: { type: PathPrefix, value: /admin } } ]
      filters: [ { type: RequestHeaderModifier, ... } ]
      backendRefs: [ { name: admin-svc, port: 80 } ]
```
Роут направляет `/api` на api-svc, а `/admin` — на admin-svc с модификацией заголовка. Дальше проверяем, как реализация нормализует пути: `//api`, `/api/../admin`, кодировки — и не приводит ли это к обходу.

## Path-матчинг и обход

PathPrefix матчит по префиксу: `/api` совпадёт с `/api/users`, но и с `/api` и `/apiXYZ` (в зависимости от реализации). Exact матчит точно. RegularExpression даёт гибкость, но и ошибки. Обходы: разное представление пути (`//`, `%2f`, `..`), двойная нормализация, регистр, трейлинг-слэш. Если один роут ведёт на защищённый бэкенд, а другой — на открытый, обход матчинга перекидывает запрос на защищённый в обход правил. Проверяй все формы пути.

## Cross-namespace и backendRefs

HTTPRoute может ссылаться на backend в другом namespace, если это разрешено ReferenceGrant. Это полезная функция и вектор: если роут в одном namespace может направлять трафик на сервис в другом, то слабый роут даёт путь к чужому бэкенду. Плюс backendRefs могут указывать на внешние адреса (через Service без селектора и EndpointSlice) — это путь к SSRF: шлюз ходит туда, куда указывает роут. Проверяй, куда указывают backendRefs и можно ли их изменить.

## Фильтры и URLRewrite

Фильтры меняют запрос: URLRewrite переписывает путь, RequestHeaderModifier добавляет/удаляет заголовки, RequestRedirect перенаправляет. Неточный URLRewrite может создать обход: например, переписывает `/public/` в `/` и открывает внутренние пути. RequestHeaderModifier может подставить доверенный заголовок, которому бэкенд верит (например, X-Forwarded-User), что даёт подмену идентичности. Проверяй, какие заголовки добавляются и как это использует бэкенд.

## SSRF через Gateway

Если шлюз ходит на backendRefs, а backend можно указать на произвольный адрес (внешний Service, EndpointSlice с IP metadata-сервера), ты получаешь SSRF: шлюз внутри кластера дотянется до внутренних сервисов и metadata. Особенно опасно, если у тебя есть право создавать HTTPRoute: ты направляешь запрос на нужный адрес и читаешь ответ. Проверяй, кто может создавать роуты и можно ли ссылаться на внешние адреса.

## Типовые мисконфиги

| Мисконфиг | Последствие | Как искать |
|---|---|---|
| Неточный path-матчинг | обход к защищённому бэкенду | правила роутов |
| Широкий ReferenceGrant | доступ к чужому namespace | grants |
| backendRef на внешний адрес | SSRF | backendRefs |
| URLRewrite без проверки | обход путей | filters |
| RequestHeaderModifier доверенный бэкендом | подмена идентичности | filters |
| Можно создавать роуты | перенаправление трафика | RBAC |

## Полный прогон: от роута к бэкенду

Шаги. Первый: перечислить Gateway, HTTPRoute и их правила. Второй: понять path-матчинг и найти неточности. Третий: попробовать обходы пути. Четвёртый: проверить cross-namespace ссылки и ReferenceGrant. Пятый: проверить фильтры (URLRewrite, заголовки). Шестой: при праве создавать роуты — направить на внутренний адрес. Седьмой: зафиксировать и учесть аудит.

## Инструменты и команды

Полезны: `kubectl get gateway,httproute -A -o yaml`, `kubectl get referencegrant -A`, curl с разными формами пути, `kubectl get svc,endpointslices`. Для SSRF — создание роута на внешний адрес. Для RBAC — `kubectl auth can-i create httproutes`. Для сравнения — Ingress-правила (если есть оба).

## OPSEC и детект

Изменения Gateway/HTTPRoute логируются в API server audit. Создание роута на внешний адрес — заметное событие. Обходы пути видны в access-логах шлюза. Тихий сценарий — использовать существующие роуты и обходы матчинга, без создания новых объектов.

## Частые вопросы

Отличается ли от Ingress? Да, Gateway API выразительнее и по-другому устроен. Даёт ли SSRF? Через backendRef на внешний адрес. Обходится ли PathPrefix? Часто, формами пути. Виден ли обход? Да, в access-логах. Нужны ли права на роуты? Для создания — да.

## Что не сработает

Точный Exact-матчинг и нормализация закроют обход пути. Строгий ReferenceGrant не даст cross-namespace. Без права создавать роуты SSRF не выйдет. И если бэкенды не доверяют заголовкам, подмена не сработает.

## Разбор кейса: обход path-матчинга

История из практики. Gateway направлял `/api` на публичный сервис, а `/internal` — на внутренний, но реализация нормализовала `/api/../internal` в `/internal` только после матчинга, из-за чего запрос попадал на публичный роут, а бэкенд видел внутренний путь. Тестировщик дошёл до внутреннего API. Урок: матчинг и нормализация должны быть согласованы; расхождение между шлюзом и бэкендом — источник обхода.

## Что мы теперь знаем

1. Gateway API — CRD-роутинг: GatewayClass, Gateway, HTTPRoute.
2. Неточный path-матчинг и разная нормализация дают обход.
3. Cross-namespace backendRefs и ReferenceGrant расширяют доступ.
4. Фильтры (URLRewrite, заголовки) могут создавать обход и подмену.
5. Право создавать роуты с внешним backendRef — это SSRF изнутри кластера.

## Сравнение с Ingress и миграционные дыры

Gateway API постепенно заменяет Ingress, и во многих кластерах работают оба. Миграция — источник мисконфигов: правила могут дублироваться, конфликтовать или применяться по-разному. Например, Ingress ведёт на один бэкенд, а HTTPRoute — на другой, и порядок применения зависит от реализации. Плюс аннотации Ingress (rewrite-target, use-regex) не всегда имеют прямой аналог в Gateway API, поэтому поведение меняется. Проверяй оба слоя и их взаимодействие: обход может быть не в одном из них, а в их сочетании.

## Аутентификация на шлюзе и внешний авторизационный сервис

Gateway API поддерживает расширения через policy-объекты и внешний authz (например, интеграция с oauth2-proxy или ext_authz-фильтрами). Если аутентификация реализована фильтром, она может применяться не ко всем роутам или не ко всем путям. Проверяй, какие роуты защищены, а какие — нет: часто защищён основной путь, а вспомогательный (webhook, статика, health) открыт и ведёт к тому же бэкенду. Список роутов и их фильтров — это карта того, где аутентификация есть, а где нет.

## Итог по Gateway API

Gateway API даёт выразительную маршрутизацию и потому больше точек для ошибок. Ключевые векторы: обход path-матчинга (нормализация), cross-namespace ссылки, фильтры (URLRewrite, заголовки) и SSRF через backendRef на внешний адрес. Начни с роутов и их матчей, затем проверь фильтры и ReferenceGrant, и только потом ищи обход. Если есть право создавать роуты — SSRF почти гарантирован.

## Практический чек-лист по Gateway API

Начни с `kubectl get gateway,httproute -A -o yaml`: какие роуты есть и куда ведут. Разбери матчи по путям и хостам: где PathPrefix, где Exact, где regex. Проверь фильтры: URLRewrite, RequestHeaderModifier, RequestRedirect. Посмотри cross-namespace ссылки и ReferenceGrant. Затем пройдись по формам пути: `//`, `%2f`, `..`, регистр, трейлинг-слэш. И проверь, можешь ли ты создавать роуты: если да — SSRF через backendRef на внутренний адрес. Отдельно сравни с Ingress, если он тоже есть: миграция оставляет дубли и конфликты.

## Чего ожидать на практике

Самая частая находка — расхождение нормализации путей между шлюзом и бэкендом, из-за которого PathPrefix обходится. Вторая — фильтр RequestHeaderModifier, подставляющий заголовок вроде X-Forwarded-User, которому бэкенд доверяет. Третья — незащищённые вспомогательные роуты (health, статика, webhook), ведущие к тому же бэкенду. Поэтому начни с роутов и их матчей, а фильтры и заголовки проверь сразу после — они часто дают подмену идентичности без всякой инъекции.

## Коротко о приоритетах

Если времени мало, разбери роуты и формы путей: обход матчинга — самый частый результат. Фильтры и заголовки проверь сразу после — они дают подмену идентичности без инъекции. Создание роутов — бонус, если есть права.
