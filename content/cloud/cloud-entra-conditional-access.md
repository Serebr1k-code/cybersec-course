## Вопрос, с которого всё начинается

Организация внедрила Conditional Access: вход разрешён только с managed-устройств, из доверенных сетей, с MFA. Казалось бы, украденный пароль бесполезен. Но атакующие всё равно входят. Вопрос: где в политиках остаются дыры? Ответ — в **условиях и исключениях**: политики почти никогда не покрывают всё, и именно непокрытое приложение или протокол становится входной точкой.

## Что такое Conditional Access

Conditional Access (CA) — механизм Entra ID, который решает, разрешить ли вход, на основе условий. Политика состоит из:
- **assignments** — кому (пользователи/группы), к чему (приложения), при каких условиях (платформа, местоположение, клиент, риск устройства);
- **controls** — что требовать (MFA, compliant device, hybrid-joined, terms of use) или блокировать.

По умолчанию Entra ничего не блокирует: если политики нет — вход разрешён. Поэтому CA эффективен ровно настолько, насколько полон охват.

## Сквозной пример: выгрузка политик

Смотрим сохранённую выгрузку:
```
$ cat ca-policies.json
{
  "policies": [
    {"name": "Require MFA all users",
     "apps": ["All"], "excluded_apps": ["LegacyAuthApp"],
     "conditions": {"client_apps": ["browser", "mobile"]}},
    {"name": "Require compliant device",
     "apps": ["Office365"], "conditions": {"platforms": ["Windows", "macOS"]}}
  ]
}
```
Два факта. Первая политика исключает приложение `LegacyAuthApp`. Вторая применяется только к Office365 и только к Windows/macOS. Значит, вход в `LegacyAuthApp` не требует MFA, а вход в Office365 с Linux/Android — не требует compliant device. Это и есть пробелы.

## Условия и где их обходят

**Client apps**: если политика покрывает только `browser` и `mobile`, то **legacy authentication** (IMAP/POP/SMTP/EWS, без современной аутентификации) остаётся открытой. Legacy auth не умеет MFA — поэтому это классический обход. Правильная политика блокирует `other`/legacy клиентов отдельно.

**Platforms**: если политика требует compliant device только для Windows/macOS, вход с Linux, Android, iOS или «неизвестной» платформы проходит без требования.

**Locations**: политика «только доверенные сети» обходится, если есть исключение для гостевых сетей или VPN-выхода, или если атакующий компрометировал машину внутри доверенной сети.

**Device compliance**: требование compliant/managed device — самое сильное, но обходится, если есть исключения для конкретных групп (например, сервисных аккаунтов), у которых нет устройства.

## Исключения — главный источник дыр

Почти всегда в политике есть `excluded_users`, `excluded_groups`, `excluded_apps`. Их добавляют, чтобы «не мешать» сервисам и VIP-пользователям. Для атакующего исключения — это карта обхода:
- сервисный аккаунт без MFA → если его пароль известен, вход без второго фактора;
- исключённое приложение → прямой вход;
- исключённая группа → ищем в ней пользователя, которого можно скомпрометировать.

При аудите выгружай все политики и строй таблицу: какие приложения/платформы/группы **не** покрыты ни одной политикой.

## Report-only и теневые политики

Политики бывают в режиме **report-only** — они считают, но не блокируют. Если администратор «тестирует» политику месяцами, реального контроля нет. Проверяй `state` каждой политики: `enabled` или `enabledForReportingButNotEnforced`.

## Гибридные и легаси-пути

В гибридных средах есть дополнительные пути: Entra Connect (синхронизация), on-prem AD, RDP в внутреннюю сеть. Conditional Access покрывает облако, но не защищает локальный вход, а из локального можно прийти в облако через гибридную идентичность. Это стык с уроком про Entra Connect.

## Как проверить руками

С токеном и модулями:
```
$ az rest --method GET --url "https://graph.microsoft.com/v1.0/identity/conditionalAccess/policies"
```
Вывод покажет политики, их состояние и исключения. Дальше — поиск непокрытых приложений и legacy-протоколов.

## Conditional Access: как работает

Conditional Access (CA) в Microsoft Entra ID — правила «если условие, то требование»: если пользователь в недоверенной сети / на несоответствующем устройстве / с высоким риском — требуй MFA, compliant device или блокируй. Правила оцениваются при входе; применяются к приложениям, пользователям, условиям.

```text
if (user in group) and (app = X) and (location = untrusted) then require MFA
```

Поверхность атаки: (1) исключения (excluded users/groups) — классическая лазейка; (2) отсутствие политики для legacy-аутентификации (она обходит CA); (3) слишком широкие условия; (4) «report-only» режим, который ничего не блокирует.

## Практика: поиск лазеек

Что проверять: список политик, их состояние (`enabled`/`report-only`/`disabled`), исключения, покрытие приложений и пользователей, обработка legacy-протоколов. Лазейка: исключённый сервисный аккаунт без MFA, через который можно войти; или legacy-протокол (IMAP/POP/SMTP), не покрытый CA.

```bash
# Microsoft Graph: список политик CA
az rest --method get --url "https://graph.microsoft.com/v1.0/identity/conditionalAccess/policies"
```

Для пентеста: оцени, какие условия реально применяются, и найди путь обхода (исключение, legacy-протокол, устройство).

## Типичные ошибки

Ошибки: (1) политика в режиме `report-only` (думают, что работает); (2) исключение админ-аккаунта «чтобы не заблокироваться»; (3) непокрытые legacy-протоколы; (4) условие по устройству, которое не проверяется; (5) отсутствие политики для регистрации устройств. Каждая — путь обхода.

```text
excluded admin account -> bypass CA -> no MFA
```

Вывод: CA — мощный инструмент, но его эффективность определяется отсутствием лазеек. Проверяй исключения и legacy-протоколы в первую очередь.

## Расширенный разбор: условия и исключения

CA-политика: assignments (users/groups, apps, conditions: location, device, risk, client app) + access controls (grant: MFA, compliant device, terms; session: sign-in frequency). Каждое условие — точка анализа. Исключения (excluded users/groups/apps) — самые частые лазейки.

```text
assignments + controls - exclusions = real coverage
```

Проверь: покрыты ли все приложения, есть ли исключения админов, покрыта ли legacy-аутентификация (она обходит CA, если не заблокирована).

## Практика: обход CA

Векторы обхода: (1) исключённый аккаунт без MFA; (2) legacy-протокол (IMAP/SMTP/POP) — CA применяется не всегда; (3) `report-only` политика; (4) устройство, которое не проверяется; (5) приложение, не покрытое политикой. Для пентеста: найди путь, который не требует MFA.

```bash
az rest --method get --url "https://graph.microsoft.com/v1.0/identity/conditionalAccess/policies"
```

Типичная находка: исключение для сервисного аккаунта или непокрытый legacy-протокол.

## Защита

Меры: блокировать legacy-аутентификацию, минимум исключений (только break-glass с мониторингом), enabled (не report-only), покрытие всех приложений, compliant device, sign-in frequency. Вывод: CA эффективен при отсутствии лазеек.

## Расширенный разбор: legacy-аутентификация

Legacy-протоколы (IMAP/POP/SMTP, Exchange ActiveSync) не всегда покрываются CA. Если их не заблокировать, злоумышленник может войти по ним без MFA, даже когда CA включён для современных клиентов. Это классическая лазейка.

```text
CA enabled for modern auth; legacy IMAP not blocked -> bypass MFA
```

Проверь: есть ли политика, блокирующая legacy-аутентификацию, или условие `client app = other clients`. Если нет — это путь обхода.

## Практика и защита

Практика: перечисли политики, исключения, покрытие приложений, legacy-условия. Инструменты: Microsoft Graph, `az rest`. Защита: блокировка legacy, минимум исключений, enabled (не report-only), покрытие всех приложений, sign-in frequency. Вывод: CA — сильная мера, но её эффективность определяется отсутствием лазеек.

## Чек-лист Conditional Access

1. Список политик и режим (enabled/report-only/disabled). 2. Покрытие приложений и пользователей. 3. Исключения. 4. Условия (location/device/risk/client app). 5. Блокировка legacy-аутентификации. 6. Sign-in frequency. Инструменты: Microsoft Graph, `az rest`.

## Разбор кейса: обход через legacy IMAP

История из практики. Организация включила Conditional Access с MFA для современных клиентов, но не заблокировала legacy-аутентификацию. Атакующий, имея пароль, вошёл по IMAP и обошёл MFA, потому что CA не применялась к legacy-протоколу. Вывод: CA без блокировки legacy-аутентификации — дыра. Всегда проверяй условие `client app = other clients` и наличие политики, блокирующей старые протоколы.

## Что мы теперь знаем

- CA решает вход по условиям; без политики доступ разрешён по умолчанию.
- Legacy authentication часто не покрыт и не умеет MFA — классический обход.
- Ограничение по platforms оставляет Linux/Android/unknown без требований.
- Исключения (users/groups/apps) — главный источник пробелов.
- Политика в режиме report-only не защищает.
