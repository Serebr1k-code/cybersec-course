## Задача

В прошлых уроках мы убегали из контейнера через **мисконфигурации**: `privileged`, `hostPath`, открытый `docker.sock`. Но есть второй класс побегов, не зависящий от настроек: **уязвимости в самом рантайме** — программе, которая создаёт контейнер. Если версия рантайма устарела, побег возможен даже из идеально настроенного пода.

Цель урока: научиться определять версии рантайма на ноде и сопоставлять их с известными CVE, чтобы понять — уязвим ли кластер.

## Данные, с которыми работаем

Мы уже на узле (через побег из прошлых уроков) и видим всю цепочку. Разберём её, потому что понимание стека — половина дела:

```
kubectl → kubelet → CRI (containerd/CRI-O) → containerd-shim → runc → процесс
```

- **runc** — низкоуровневый **OCI-рантайм**: именно он создаёт namespaces и cgroups для контейнера. OCI — открытый стандарт контейнеров.
- **containerd** / **CRI-O** — высокоуровневые рантаймы, реализующие **CRI** (Container Runtime Interface — интерфейс, через который kubelet общается с рантаймом).
- **containerd-shim** — прослойка, которая держит процесс контейнера.

Важный вывод: уязвимость в **runc** затрагивает всех, кто его использует, — то есть почти всех.

## Шаг 1: определяем версии

Проверяем каждый слой:

```bash
$ runc --version
runc version 1.1.11
spec: 1.0.2-dev
go: go1.21.4
$ containerd --version
containerd github.com/containerd/containerd v1.7.11
$ crictl version
RuntimeName:  containerd
RuntimeVersion:  v1.7.11
```

Мы видим: **runc 1.1.11** и **containerd 1.7.11**. Обе версии надо сопоставить с базой CVE. Запоминаем: `1.1.11` — это ключ.

## Шаг 2: сопоставляем с CVE — CVE-2024-21626

**CVE-2024-21626** — уязвимость runc, при которой контейнер мог получить доступ к файловому дескриптору (fd) хостовой файловой системы. Файловый дескриптор — это числовой «хэндл» открытого файла; `/proc/self/fd/<n>` — ссылка на него. Если runc оставляет открытым fd, ведущий на каталог хоста, контейнер может через него выйти наружу.

Исправлено в **runc 1.1.12**. У нас `1.1.11` → **версия уязвима**. Это и есть вся суть version-diff: **фикс-релиз указывает прямо на уязвимость**.

Проверяем косвенно, что мы вообще в контейнере и какие fd открыты:

```bash
$ ls -la /proc/self/fd | head -5
lrwx------ 1 root root 64 ... 0 -> /dev/pts/0
lrwx------ 1 root root 64 ... 1 -> /dev/pts/0
lr-x------ 1 root root 64 ... 3 -> /var/lib/containerd/...
```

Последняя строка — fd, ведущий в каталог containerd на **хосте**. Именно такие утечки fd и эксплуатируются.

## Шаг 3: как это эксплуатируется в общих чертах

Точный PoC зависит от окружения, но принцип такой: при создании контейнера runc неправильно обрабатывает `WORKDIR` (рабочий каталог). Если указать в образе `WORKDIR` вида `/proc/self/fd/<n>`, где `<n>` — унаследованный fd на каталог хоста, процесс стартует **внутри хостовой файловой системы**.

Поэтому эксплойт требует контроля над образом — а значит, подходит сценарий «загрузить свой образ через CI/registry». Проверка же начинается с простого: определить версию и подтвердить, что она ниже фикса.

## Если не сработало: другие классы уязвимостей рантайма

| CVE | Компонент | Суть | Фикс |
|-----|-----------|------|------|
| 2019-5736 | runc | перезапись runc при `exec` | 1.0-rc6+ |
| 2022-0492 | ядро/cgroup v1 | release_agent | патч ядра |
| 2021-30465 | runc | symlink-race при монтировании | 1.0.0-rc95 |
| 2024-21626 | runc | утечка fd | 1.1.12 |
| 2020-15257 | containerd | abstract socket namespace | 1.4.3 |
| 2024-24789 | containerd | обход digest | 1.7.13 |

- **CVE-2019-5736** — контейнер перезаписывает бинарник runc на хосте, и при следующем `exec` выполняется вредоносный код. Требует `exec` в контейнер.
- **CVE-2022-0492** — через cgroup v1 `release_agent` выполняется команда на хосте. Требует `CAP_SYS_ADMIN`.
- **CVE-2020-15257** — доступ к управляющему abstract-socket containerd из контейнера = управление контейнерами хоста.

## Где искать версии в реальном кластере

Версия runc **на ноде** не видна из пода. Узнать её можно:
- с ноды (через побег или node-debug);
- косвенно из пода: `uname -r` (версия ядра — важна для cgroup-CVE), `/proc/1/cgroup`, наличие `/run/containerd/containerd.sock`;
- из API: `kubectl get nodes -o jsonpath='{.items[*].status.nodeInfo.containerRuntimeVersion}'`.

Помни: **обновление ноды не обновляет образы** — там может быть свой runc/containerd. Их нужно пересобирать.

## Частые ошибки и подводные камни

- **Проверять версию только на ноде.** Образ может нести собственный runc/containerd; обновление ноды не обновляет образы.
- **Игнорировать версию ядра.** Некоторые CVE (например, cgroup `release_agent`) зависят именно от ядра, а не от runc.
- **Использовать теги вместо digest.** Тег — mutable-указатель; `:latest` можно подменить, а digest фиксирует содержимое.
- **Полагаться только на конфигурацию.** Даже идеально настроенный под уязвим, если рантайм устарел.
- **Забывать про rootless.** User namespaces снижают последствия побега, но не убирают их полностью.

- **Не проверять сокет рантайма.** `/run/containerd/containerd.sock` внутри контейнера эквивалентен открытому демону — доступ к нему даёт контроль над контейнерами.
- **Считать gVisor/Kata панацеей.** Sandbox-рантаймы уменьшают поверхность, но у них тоже бывают свои уязвимости.

- **Не вести таблицу версий.** Составьте «нода → runc → containerd → ядро» и сопоставьте с advisory, иначе легко потерять трек при оценке кластера.

- **Не проверять права на CRI-сокет.** Если `/run/containerd/containerd.sock` доступен на запись, вы управляете всеми контейнерами ноды — как через docker.sock.

## Что мы теперь знаем

- Стек: kubelet → CRI (containerd/CRI-O) → shim → **runc** (создаёт namespaces).
- Уязвимость runc затрагивает всех, кто его использует.
- Version-diff: фикс-релиз прямо указывает на уязвимую версию (1.1.11 → уязвим, фикс 1.1.12).
- Классы CVE: overwrite runc, cgroup `release_agent`, утечка fd, abstract socket.
- Rootless/user namespaces снижают риск, но не убирают его.
- Версии на ноде и в образах различаются — проверяй оба.

## Глазами защитника

Обновления рантайма (runc, containerd, CRI-O) — основная защита. PSA restricted и запрет privileged уменьшают поверхность. Более сильная изоляция (gVisor, Kata) нейтрализует часть уязвимостей. Детект (Falco, audit) ловит аномалии: `nsenter`, монтирование, доступ к `/proc/1`. Аудит версий и образов. Важно понимать, что уязвимость рантайма обходит конфигурацию пода.

## Частые вопросы

**Какие рантаймы бывают?**

runc, crun, containerd, CRI-O — низкоуровневые; Docker, Podman — высокоуровневые. Уязвимость может быть в любом.

**Что такое CVE-2024-21626?**

Leaky Vessels: runc оставлял открытым FD рабочей директории, что давало доступ к файловой системе хоста.

**Как определить версию?**

`runc --version`, `containerd --version`, `crio --version` на узле; в managed — в node image.

**Чем уязвимость рантайма отличается от мисконфига?**

Мисконфиг требует опасных настроек; уязвимость работает даже на «правильном» поде.

**Что делать без патча?**

Ограничить привилегии, включить PSA restricted, изолировать узлы, детектить аномалии, ускорить обновление.

**Помогает ли seccomp?**

Частично: он ограничивает системные вызовы и может заблокировать эксплойт, но не гарантирует защиту.

**Как защититься?**

Обновления, PSA restricted, seccomp и AppArmor, read-only rootfs, изоляция, детект.

**Как проверить, уязвим ли кластер?**

Сопоставить версии рантайма с базой CVE и проверить, доехал ли патч до узлов.

## Разбор: от версии к CVE

Атакующий на узле выполняет `runc --version` и видит версию ниже патченной. Сопоставляет её с CVE-2024-21626 и запускает эксплойт через `runc exec` с рабочим каталогом на хостовом FD. Получает доступ к файловой системе хоста и читает `kubelet.conf`. Никаких привилегий у пода не было — сработала уязвимость рантайма. Защита — обновить runc и включить детект на аномальные обращения к FD.

## Что чаще всего упускают

Версии рантайма на узлах, а не только версию Kubernetes. Уязвимость может быть в runc при полностью обновлённом control plane. Второе — считать seccomp достаточной защитой: он помогает, но не гарантирует. Третье — отсутствие инвентаря: без знания версий рантайма невозможно понять, уязвим ли кластер. Вывод: собери версии runc/containerd/CRI-O, сопоставь с CVE, обнови узлы и включи детект аномалий.

**Где искать CVE для рантайма?**

В базе CVE по продукту (runc, containerd, CRI-O) и в advisories Kubernetes. Сопоставь установленную версию с исправленной и проверь дату релиза образа узла.

**Помогает ли обновление control plane?**

Нет: побег происходит на узле, поэтому обновлять нужно node image и сам рантайм на каждом узле, а не только API-сервер.

**Что делать, если кластер managed?**

Дождись обновления node pool или создай новый с актуальным образом. Проверь, что патч доехал до всех узлов, а не только до части.
