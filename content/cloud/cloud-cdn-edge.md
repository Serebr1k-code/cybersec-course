## Вопрос, с которого всё начинается

Сайт `www.acme-corp.com` защищён CDN и WAF: перебор путей блокируется, прямые атаки не проходят. Но где-то за этим «фасадом» стоит обычный сервер-источник, который, скорее всего, защиты не имеет. Как его найти? Именно это — первый шаг в обходе любого облачного edge.

CDN (Content Delivery Network) — это сеть узлов по миру, которые кэшируют и раздают контент от твоего имени. WAF (Web Application Firewall) — фильтр, который отбрасывает подозрительные запросы. Разберём, как их обойти на одном сайте.

## Наш пример: сайт за CloudFront

Объект урока — `www.acme-corp.com`. Сначала посмотрим, кто реально отвечает.

```
$ dig +short www.acme-corp.com
d111111abcdef8.cloudfront.net.
```

Ответ — не IP, а имя `*.cloudfront.net`: сайт отдаёт AWS CloudFront. Значит, где-то есть **origin** — исходный сервер (или S3-бакет), откуда CloudFront забирает контент. Наша цель — обратиться к origin напрямую, минуя CloudFront.

## Шаг 1: смотрим заголовки ответа

CDN оставляет в ответах следы. Запросим заголовки:

```
$ curl -sI https://www.acme-corp.com
HTTP/2 200
server: CloudFront
via: 1.1 d111111abcdef8.cloudfront.net (CloudFront)
x-amz-cf-id: AbCdEf123...
x-cache: Hit from cloudfront
```

Читаем: `server: CloudFront` и `x-amz-cf-id` прямо говорят, что перед нами CloudFront. А `x-cache: Hit` означает, что ответ пришёл из кэша edge-узла, а не от origin. Заголовки — это подсказки о том, как устроен edge, и часто через них утекает информация об origin.

## Шаг 2: ищем настоящий адрес origin

Есть несколько способов «докопаться» до источника.

**Исторические DNS.** Раньше домен мог указывать прямо на сервер. Смотрим архивные записи:

```
$ curl -s "https://api.crtsh.io/..."  # пример источника
```

На практике используют исторические базы DNS (SecurityTrails, crt.sh, архив DNS). Если домен раньше резолвился в IP вроде `203.0.113.10`, а теперь — в CloudFront, этот старый IP, вероятно, и есть origin.

**Сертификаты.** Если origin отдаёт свой TLS-сертификат, его имя может совпасть с внутренним именем сервера. Смотрим сертификат edge:

```
$ echo | openssl s_client -connect www.acme-corp.com:443 -servername www.acme-corp.com 2>/dev/null | openssl x509 -noout -subject -ext subjectAltName
subject=CN = *.acme-corp.com
X509v3 Subject Alternative Name:
    DNS:*.acme-corp.com, DNS:acme-corp.com
```

Здесь дополнительных имён нет, но часто в SAN попадают внутренние хосты вроде `origin.acme-corp.com`.

## Шаг 3: проверяем гипотезу с прямым обращением

Предположим, мы нашли кандидата `origin.acme-corp.com` (или IP `203.0.113.10`). Обратимся к нему, но **с заголовком Host** сайта:

```
$ curl -sI https://203.0.113.10 -H "Host: www.acme-corp.com" -k
HTTP/1.1 200 OK
server: nginx/1.24.0
```

Ответил `nginx` — это уже не CloudFront, а наш origin. Так подтверждается обход: обращаясь к серверу напрямую, мы попадаем на него **до** фильтров WAF, которые стоят только на edge. Дальше можно тестировать обычные веб-уязвимости, которые CDN блокировал.

## Шаг 4: почему это работает

Схема защиты часто строится так:

```
пользователь → CloudFront (+WAF) → origin (сервер)
```

Origin должен принимать трафик **только** от CloudFront. На практике этого не делают: сервер доступен из интернета по IP, а WAF фильтрует лишь то, что идёт через edge. Отсюда правило: **найди origin — и WAF перестаёт мешать**.

Чтобы origin был защищён, ему нужно разрешать трафик только из диапазонов CloudFront и требовать общий секрет (в AWS это заголовок `X-Origin-Verify`, значение которого проверяет сервер).

## Шаг 5: Cloudflare и другие edge

У Cloudflare другая картина: по умолчанию он **скрывает** IP origin за своими адресами, и найти его сложнее. Но утечки бывают:

- **Прямой IP в старых записях.** Если DNS-запись когда-то не была «проксирована» через Cloudflare (оранжевое облако выключено), исторические базы покажут реальный IP.
- **Поддомены без прокси.** Часто `mail.acme-corp.com` или `dev.acme-corp.com` не проксируются и светят тот же IP, что и origin.
- **Утечки через ошибки и заголовки.** Некоторые серверные приложения возвращают свой внутренний адрес в ответе.

Сравнение типовых «подписей» edge:

| Заголовок/сервис | Кто это |
|------------------|---------|
| `server: CloudFront`, `x-amz-cf-id` | AWS CloudFront |
| `server: cloudflare`, `cf-ray` | Cloudflare |
| `x-azure-ref` | Azure Front Door |
| `via: 1.1 google` | Google Cloud CDN |

## Шаг 6: мисконфиги кэша и заголовков

Edge — это не только про поиск origin. Неправильная настройка кэша и заголовков тоже создаёт уязвимости:

- **Кэширование приватного.** Если CDN кэширует ответы, зависящие от пользователя (например, страницу с чужими данными), их может получить другой. Проверяется просто: запроси ресурс дважды и сравни `x-cache`.
- **Кэш-ключ без cookie.** Когда CDN не учитывает cookie в ключе кэша, авторизованный ответ может «протечь» неавторизованному.
- **Утечка внутренних заголовков.** Origin иногда отдаёт `X-Backend-Server`, `X-Forwarded-For` с внутренним IP — прямая подсказка для поиска origin.

```
$ curl -sI https://www.acme-corp.com/api/me
x-cache: Miss from cloudfront
cache-control: private, max-age=0
```

Здесь `cache-control: private` — правильно: приватный ответ не кэшируется на общих узлах. Если бы стояло `public`, данные могли бы утечь.

## Шаг 7: WAF — не стена, а фильтр

Важно понимать: WAF блокирует **известные шаблоны** атак, а не любую подозрительную активность. Он пропускает то, чего не знает. Поэтому обход WAF — это не «взлом», а подбор кодировок, регистра, разбиения запроса, которые фильтр не распознаёт. И самый надёжный обход — вообще не идти через WAF, а обратиться к origin напрямую, как мы делали выше.

## Частые вопросы

**«Разве CDN не защищает сайт?»** Он защищает **от нагрузки и части атак**, но не заменяет защиту origin. Если origin доступен напрямую, все фильтры edge обходятся.

**«Почему нельзя просто закрыть origin файрволом?»** Можно и нужно, но origin должен принимать трафик от CDN — значит, его нужно ограничить диапазонами адресов CDN и общим секретом. Часто этого не делают.

**«Как быстро понять, что передо мной CDN?»** По заголовкам: `server: CloudFront`, `cf-ray`, `via: 1.1 google`. Плюс DNS-запись ведёт на домен CDN, а не на IP.

**«Что опаснее — обход WAF или origin?»** Origin: обход WAF можно залатать правилом, а открытый origin остаётся открытым, пока его не изолируют.

## Что мы теперь знаем

По-простому:

1. CDN/WAF — это фасад; за ним обычно стоит незащищённый origin.
2. Заголовки ответа (`server`, `via`, `x-cache`) выдают тип edge.
3. Origin ищут по историческим DNS, сертификатам и незащищённым поддоменам.
4. Обращение к origin с нужным заголовком `Host` обходит WAF.
5. Защита origin — разрешать трафик только от CDN и проверять общий секрет.

## На что смотреть дальше

- **Не бей в лоб WAF.** Сначала ищи origin — это обходит фильтр естественным путём.
- **Смотри заголовки кэша.** `x-cache: Hit` значит, ты видишь кэш, а не origin.
- **Проверяй поддомены.** Именно они чаще всего светят реальный IP.
- **Помни про риск.** Обход edge — это громко; фиксируй время и объём.
