## Вопрос, с которого всё начинается

Ты получил API-токен Okta — может быть, read-only, а может, и нет. Okta — это IdP, через который сотрудники входят во все остальные сервисы. Вопрос: как из ограниченного токена добраться до уровня, с которого видно всех и можно выдать себе что угодно? В Okta это делается через **административные роли** и группы. Разберём, где здесь путь эскалации.

## Что такое Okta и почему он цель

Okta — облачный Identity Provider: SSO, MFA, жизненный цикл пользователей, интеграции с сотнями приложений. Если атакующий контролирует Okta-тенант, он контролирует вход во все подключённые сервисы: можно выдавать себе доступ, читать приложения, менять MFA. Поэтому Okta — одна из самых ценных целей в облачной инфраструктуре, и её админские роли — прямой аналог domain admin.

## Сквозной пример: роли и группы

Смотрим выгрузку ролей:
```
$ cat roles.json
{
  "roles": [
    {"type": "HELP_DESK_ADMIN", "targets": {"groups": ["it-support"]}},
    {"type": "APP_ADMIN", "targets": {"apps": ["*"]}},
    {"type": "GROUP_MEMBERSHIP_ADMIN", "targets": {"groups": ["*"]}}
  ]
}
```
Три роли. `HELP_DESK_ADMIN` может сбрасывать MFA и пароли — уже серьёзно. `APP_ADMIN` управляет всеми приложениями. `GROUP_MEMBERSHIP_ADMIN` меняет членство в группах — а это и есть эскалация, потому что администраторы назначаются через группы.

## Модель админских ролей

В Okta есть встроенные роли: Super Admin, Org Admin, App Admin, Group Admin, Help Desk Admin, Read-Only Admin и другие. Ключевые для эскалации:
- **Super Admin** — полный контроль, включая назначение ролей;
- **Group Admin / Group Membership Admin** — управление группами;
- **Help Desk Admin** — сброс MFA и паролей пользователей;
- **App Admin** — управление приложениями и их назначениями.

Идея эскалации проста: если у тебя есть роль, которая позволяет менять **членство в группе**, а в какой-то группе лежит админская роль, — ты добавляешь себя в эту группу и получаешь роль.

## Группы и назначение ролей

Okta назначает роли либо напрямую пользователю, либо **группе**. Если группа несёт роль Super Admin, то любой её участник — супер-админ. Значит, `GROUP_MEMBERSHIP_ADMIN` на `*` (все группы) = путь к супер-админу. На практике это самый частый сценарий эскалации в Okta: не ломают криптографию, а добавляют себя в правильную группу.

## Help Desk как обход MFA

`HELP_DESK_ADMIN` может сбрасывать факторы MFA. Это обход MFA без единого взлома: сбрасываем MFA жертвы, задаём свой фактор, входим. Отсюда правило: help desk admin — это фактически доступ к любому аккаунту. При аудите проверяй, у кого есть эта роль и нет ли её у сервисных аккаунтов.

## App-консент и impersonation

Помимо ролей, есть **app consent** — разрешение приложению действовать от имени пользователя. Атакующий может выдать вредоносному OAuth-приложению консент, и оно получит доступ к данным тенанта (почта, файлы), оставаясь «легитимным» приложением. Плюс есть механизм impersonation (вход от имени пользователя) — если он включён и не логируется, это тихая персистентность.

## Пути эскалации: сводка

- `GROUP_MEMBERSHIP_ADMIN` на `*` → добавить себя в группу с админ-ролью;
- `HELP_DESK_ADMIN` → сброс MFA/пароля жертвы → вход;
- `APP_ADMIN` → выдать себе назначение на приложение;
- API-токен с `okta.apps.manage` → создать приложение с redirect на свой сервер;
- app consent → OAuth-приложение читает почту/файлы;
- слабые кастомные роли, выданные группам, которые можно менять.

## Как проверить руками

С API-токеном:
```
$ curl -s -H "Authorization: SSWS $TOKEN" https://acme.okta.com/api/v1/users
$ curl -s -H "Authorization: SSWS $TOKEN" https://acme.okta.com/api/v1/groups
$ curl -s -H "Authorization: SSWS $TOKEN" https://acme.okta.com/api/v1/iam/roles
```
Ответы покажут пользователей, группы и роли. Дальше — сопоставление: какие группы несут админские роли и можем ли мы менять их членство.

## Okta: роли и поверхность

Okta — IdP с ролями (Super Admin, Org Admin, App Admin, Group Admin и др.). Роли выдаются пользователям и группам, приложения подключаются через SAML/OIDC. Поверхность: (1) широкая роль у сервисного аккаунта, (2) API-токен Okta с большими правами, (3) OIDC-приложение с `client_secret` в открытом виде, (4) SAML без подписи (подделка assertion).

```text
role -> permissions -> apps/users -> escalation
```

Ключевая цель — API-токен или роль, дающая управление пользователями/приложениями.

## Практика: эскалация в Okta

Векторы: (1) `Group Admin` может менять членство групп → добавить себя в привилегированную группу; (2) `App Admin` может изменить SAML-приложение → инъекция атрибутов; (3) API-токен с `okta.users.manage` → создание/изменение пользователей; (4) weak SAML (без подписи) → подделка assertion. Инструменты: Okta API, `aws sso`-подобные.

```bash
curl -H "Authorization: SSWS <token>" https://<org>.okta.com/api/v1/users
```

Типичная находка — сервисный аккаунт с широкой ролью и токеном в открытом виде.

## Защита

Меры: минимальные роли, ротация API-токенов, подпись SAML, ограничение admin-приложений, MFA для админов, мониторинг (Okta System Log). Для пентеста — чтение конфигурации; изменение — только с разрешения.

## Расширенный разбор: Group Admin → Super Admin

Классический путь: роль `Group Admin` позволяет управлять членством групп. Если есть группа с более широкой ролью (например, `Super Admin` выдана группе), ты добавляешь себя в неё и получаешь права. Аналогично `App Admin` может изменить SAML-приложение и выдать себе роли через атрибуты.

```text
Group Admin -> add self to "Okta Admins" group -> Super Admin
```

Проверь, какие роли выданы группам и кто может менять членство. Это частый путь эскалации в Okta.

## Расширенный разбор: SAML и OIDC

SAML-приложения: если assertion не подписан (или подпись не проверяется), можно подделать пользователя/атрибуты. OIDC-приложения: `client_secret` в открытом виде позволяет выдать себя за приложение. Проверь настройки приложений: подпись, audience, attribute statements.

```text
unsigned SAML -> forge assertion -> login as admin
```

Для пентеста: проверь подпись SAML и секреты OIDC. Защита: обязательная подпись, ротация секретов.

## Защита и вывод

Меры: минимальные роли, не выдавать широкие роли группам, подпись SAML, ротация API-токенов и client_secret, MFA для админов, мониторинг System Log. Вывод: Okta-эскалация идёт через роли групп и слабую федерацию; проверяй их в первую очередь.

## Разбор кейса: токен сервисного аккаунта

История из практики. Сервисный аккаунт для интеграции имел API-токен с ролью, позволяющей управлять пользователями. Токен лежал в переменной CI и попал в лог. Атакующий создал себе пользователя с админской ролью через Okta API. Вывод: API-токены Okta должны иметь минимальные права и храниться в секрет-сторе; «сервисный аккаунт» — не повод давать широкую роль.

## Вывод по Okta

Okta-эскалация идёт через роли групп (Group Admin → Super Admin), широкие API-токены и слабую федерацию (SAML без подписи). Аудит: роли, группы, приложения, токены. Защита: минимальные роли, подпись SAML, ротация, MFA для админов, мониторинг.

## Что мы теперь знаем

- Okta — IdP; контроль над ним = контроль входа во все приложения.
- Админские роли назначаются пользователям или группам.
- `GROUP_MEMBERSHIP_ADMIN` → добавить себя в админ-группу = эскалация.
- `HELP_DESK_ADMIN` сбрасывает MFA → обход второго фактора.
- App consent и impersonation — тихие пути доступа и персистентности.

Практический чек-лист: перечисли роли и группы; найди группы с широкими ролями; проверь, кто может менять членство; проверь API-токены и их права; проверь SAML-приложения на подпись; проверь OIDC-приложения на утечки секретов; оцени путь до Super Admin. Отдельно проверь настройки MFA для администраторов: если админ может войти без второго фактора, роль группы становится особенно опасной. MFA для админов — обязательная мера. Для отчёта опиши путь эскалации пошагово: от найденной роли/токена до Super Admin, с указанием каждого шага и его обоснования.

Проверь также логирование: если System Log не выгружается в SIEM, действия атакующего (создание пользователя, смена группы) останутся незамеченными. Это превращает техническую уязвимость в успешную атаку и должно быть отмечено как процессная слабость.

Итог по Okta: основной путь эскалации — роли групп и слабая федерация. Проверяй, кто может менять членство в привилегированных группах, и есть ли SAML-приложения без подписи. Добавь к этому аудит API-токенов и их прав. В отчёте опиши конкретный путь до Super Admin, если он существует, — это самое ценное доказательство.

Практическое замечание: проверяй права токенов по факту (какие API-вызовы проходят), а не только по названию роли — названия бывают неочевидными. Подтверди эскалацию конкретным вызовом в тестовом тенанте.

Рекомендация заказчику: не выдавать широкие роли группам, требовать MFA для администраторов и выгружать System Log в SIEM, чтобы активации и изменения ролей были видны и расследовались.

Помни, что IdP — это «корень доверия» для всех подключённых приложений, поэтому компромисс Okta даёт доступ к ним всем.

## Куда дальше

В следующем уроке — OAuth 2.0/OIDC-атаки: redirect_uri, PKCE и consent phishing, то есть эксплуатация доверия между приложением и IdP. А пока главное: в Okta эскалация — это путь через группы и роли, а не через взлом.

- Пентест облачных IdP и SSO-инфраструктур.
- Разбор инцидентов с компрометацией Okta-токенов.
