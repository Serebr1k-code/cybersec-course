## Вопрос, с которого всё начинается

В репозитории статического сайта ты находишь ключи вида `spaces_access_key` и endpoint `nyc3.digitaloceanspaces.com`. Сайт раздаётся через CDN, но ключи лежат рядом. Вопрос: что даёт эта пара и можно ли по ней прочитать чужие данные? DigitalOcean Spaces и Vultr Object Storage — S3-совместимые хранилища, поэтому ответ знаком: работаем `s3cmd`/`aws-cli`, а ключ даёт ровно те права, что выданы пользователю Spaces.

## Что такое Spaces и Vultr Object Storage

DigitalOcean Spaces и Vultr Object Storage — S3-совместимые объектные хранилища, привязанные к региону (у DO это `nyc3`, `ams3`, `sgp1`; у Vultr — свои локации). У каждого бакета есть S3-эндпоинт и, опционально, CDN-эндпоинт (например, `<bucket>.nyc3.cdn.digitaloceanspaces.com`). Ключи доступа (Access Key + Secret) выдаются на пользователя аккаунта и работают как S3-креды.

## Сквозной пример: конфиг Spaces

Смотрим файл:
```
$ cat spaces.config
spaces_access_key = DO00EXAMPLEKEY
spaces_secret_key = EXAMPLEnotarealsecret
endpoint = https://nyc3.digitaloceanspaces.com
bucket = acme-assets
```
Это готовый набор для `s3cmd`. Настроим профиль:
```
$ s3cmd --configure
Access Key: DO00EXAMPLEKEY
Secret Key: EXAMPLEnotarealsecret
Default Region: nyc3
S3 Endpoint: nyc3.digitaloceanspaces.com
```
Теперь можно листать бакеты:
```
$ s3cmd ls
2024-01-01 00:00  s3://acme-assets
2024-02-01 00:00  s3://acme-backups
```
Ключ видит два бакета. Один из них — «assets» (статика), второй — «backups», который явно не предполагался публичным.

## Публичные бакеты и CDN

Бакет можно сделать публичным: тогда объекты отдаются по обычному HTTPS-URL (`https://<bucket>.<region>.digitaloceanspaces.com/<key>`) без ключей. Если разрешён листинг — видно всё содержимое. CDN-эндпоинт добавляет второй путь: даже если прямой S3-доступ закрыт, CDN может кэшировать и отдавать объекты. При аудите проверяй: публичность бакета, листинг, настройки CDN, и нет ли чувствительных файлов среди «статики».

## Права пользователя Spaces

Ключ принадлежит пользователю аккаунта, а не отдельному бакету. Значит, по умолчанию он видит все бакеты, к которым у пользователя есть доступ, — в примере это и `acme-assets`, и `acme-backups`. Частая ошибка — завести один ключ для сайта и переиспользовать его для бэкапов. Тогда утечка ключа из фронтенд-репозитория открывает бэкапы.

## Presigned URL

Как и в других S3-совместимых хранилищах, есть presigned URL — ссылка с подписью и сроком. Она безопасна, пока срок короткий и права минимальны. Опасность в тех же случаях: бессрочная ссылка, ссылка на запись, ссылка, утёкшая в лог. Проверяй параметры `X-Amz-Expires` и метод (`PUT` против `GET`).

## Цепочка атаки

Типичный путь: ключи утекли из фронтенд-репозитория → `s3cmd ls` показывает бэкапы → скачиваем бэкап → внутри конфиг БД или ключи от основного облака → движемся дальше. Альтернатива: публичный бакет с листингом → находим `.env`/дампы → читаем без ключей. Оба пути ведут от «простого хостинга» к корпоративным данным.

## Как проверить руками

```
$ s3cmd ls
$ s3cmd ls s3://acme-backups
$ s3cmd get s3://acme-backups/db.tar.gz -
```
Для публичного бакета достаточно `curl` на прямой URL. Для CDN — `curl` на CDN-эндпоинт, чтобы проверить, отдаётся ли объект в обход.

## Vultr Object Storage: доступ и находки

Vultr Object Storage — S3-совместимое хранилище. Доступ через API-ключ и S3-совместимые креды. Типичные ошибки: публичный бакет, ключ в открытом виде, широкие права.

```bash
aws --endpoint-url https://<region>.vultrobjects.com s3 ls
curl https://<bucket>.<region>.vultrobjects.com/   # анонимно
```

Проверка анонимного листинга — первый шаг. Дальше — объекты с секретами.

## Практика: от ключа к данным

Что искать: публичные бакеты, креды (в CI/конфигах), объекты с секретами, широкие API-ключи. Эскалация: получив креды, использовать S3 API для доступа к другим бакетам. Инструменты: `aws s3`, `s3cmd`, `rclone`, `nmap`.

```bash
aws --endpoint-url https://<region>.vultrobjects.com s3 cp s3://<b>/.env .
```

Типичная находка — публичный бакет или ключ с полным доступом к аккаунту Vultr.

## Защита

Меры: приватные бакеты, минимальные API-ключи, ротация, шифрование, мониторинг. Для пентеста — перечисление и чтение публичного; модификация — с разрешения.

## Расширенный разбор: перечисление и чтение

Перечисление начинается с имён бакетов: они часто содержат название проекта и видны в CNAME, JS-коде, публичных конфигах. Проверь анонимный листинг: `curl https://<bucket>.<region>.vultrobjects.com/`. Если открыт — скачай список и ищи объекты с расширениями `.env`, `.pem`, `.sql`, `.bak`. Дальше — чтение найденного и извлечение секретов.

```bash
curl -s https://company-backup.ewr1.vultrobjects.com/ | head
aws --endpoint-url https://ewr1.vultrobjects.com s3 cp s3://company-backup/config/.env .
```

Отдельно проверь версионирование: старые объекты могут содержать удалённые секреты. И логирование: если включено, факт доступа отслеживается.

## Расширенный разбор: ключ с полным доступом

API-ключ Vultr даёт доступ ко всему аккаунту: серверы, хранилище, DNS, биллинг. Если ключ утёк, атакующий может перечислить серверы и хранилище, создать новый сервер, изменить DNS. Проверь, где могут лежать ключи (CI, конфиги, скрипты), и оцени импакт: полный контроль над инфраструктурой.

```bash
curl -H "Authorization: Bearer <key>" https://api.vultr.com/v2/instances
```

Типичная находка — ключ в публичном репозитории, дающий контроль над всем аккаунтом. Вывод: ключ хостинга надо считать критическим секретом.

## Защита и вывод

Меры: приватные бакеты, минимальные API-ключи (если поддерживаются), ротация, ограничение по IP, мониторинг, аудит публичных бакетов. Вывод: Vultr Object Storage — S3-совместимое хранилище, аудит такой же: ACL, ключи, объекты с секретами.

## Разбор кейса: публичный бакет с бэкапами

История из практики. Компания хранила ночные бэкапы в Vultr Object Storage. Бакет был создан публичным «для отдачи статики», а позже переиспользован для бэкапов, и ACL остался открытым. Имя бакета утекло через CNAME. Атакующий скачал дампы, получил хэши паролей и персональные данные. Отдельной уязвимости не было: сработала комбинация публичного ACL и утёкшего имени. Вывод: бакеты проверяй автоматически, а имя бакета не секрет.

## Вывод по Vultr

Vultr Object Storage — S3-совместимое хранилище. Аудит: имена бакетов → ACL → объекты с секретами → ключи API. Защита: приватные бакеты, минимальные ключи, ротация, мониторинг. Помни, что API-ключ Vultr даёт доступ ко всему аккаунту.

## Что мы теперь знаем

- Spaces и Vultr Object Storage — S3-совместимые хранилища с региональным эндпоинтом.
- Ключи Spaces работают как S3-креды (`s3cmd`, `aws-cli`).
- Ключ пользователя видит все его бакеты — переиспользование опасно.
- Публичность + листинг + CDN = три пути утечки без ключей.
- Presigned URL опасен при бессрочности/записи.

Практический чек-лист: собери имена бакетов из CNAME, JS-кода и публичных конфигов; проверь каждый на анонимный листинг; скачай найденное и поищи секреты; проверь ключи API в CI и репозиториях; оцени, какие серверы и ресурсы доступны по найденному ключу. Отдельно проверь логирование: если доступ к хранилищу не логируется, факт утечки данных невозможно отследить, и это самостоятельная находка. Включение аудита и алертов на массовое скачивание — обязательная мера. Помни, что «приватный» бакет с утёкшим PAR или ключом перестаёт быть приватным, поэтому аудит всегда включает не только ACL, но и все ссылки и ключи, дающие доступ.

Дополнительно проверь права найденного ключа: если он даёт доступ к биллингу и созданию ресурсов, это позволяет не только читать данные, но и развернуть инфраструктуру атакующего за счёт жертвы. В отчёте разделяй чтение данных и полный контроль аккаунта — это разные уровни критичности, и заказчику важно видеть оба. Наконец, проверь, включён ли двухфакторный вход в панель Vultr: без него компромисс пароля даёт тот же полный контроль, что и утёкший ключ.

Итог по Vultr Object Storage: аудит сводится к четырём вопросам — какие бакеты существуют, какие из них публичны, какие ключи дают к ним доступ и что лежит внутри. Каждый вопрос самостоятелен, но вместе они дают полную картину. Не забывай, что API-ключ Vultr — это не только хранилище: он даёт доступ к серверам, DNS и биллингу, поэтому утёкший ключ означает полный контроль над аккаунтом. Рекомендация заказчику: минимальные ключи, ротация, приватные бакеты и автоматический аудит публичного доступа.

Практическое замечание: имена бакетов можно перебирать по словарю названий компании, но не создавай нагрузку и не сканируй чужие аккаунты. Работай в рамках согласованного периметра и фиксируй только подтверждённые находки.

Рекомендация заказчику: включить автоматическую проверку публичного доступа к бакетам и алерты на создание новых публичных ресурсов, чтобы такие настройки не оставались незамеченными и не переиспользовались под бэкапы.

Хостинг-провайдер не защищает данные за тебя: ответственность за конфигурацию хранилища лежит на пользователе, и именно конфигурация чаще всего и подводит. ## Квиз
