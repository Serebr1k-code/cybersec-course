## Зачем этот урок

Современная защита supply chain строится на **подписи артефактов** (Sigstore/cosign), **SBOM** (список компонентов) и **provenance/attestations** (откуда и как собран артефакт, SLSA-уровни). Идея: деплоить только то, что подписано доверенным ключом и собрано в доверенном пайплайне. Но, как и любая защита, она обходится: верификация может быть **необязательной**, теги — **mutable** (TOCTOU), ключ подписи — **скомпрометирован**, а SBOM может не проверяться вовсе. Этот урок — про устройство этой защиты и практические способы её обойти или обмануть.

## Как устроены SBOM, подпись и provenance

- **SBOM** — список компонентов артефакта (SPDX, CycloneDX). Генерируется `syft`, `trivy`, `cdxgen`. Используется для поиска уязвимых зависимостей (`grype`, `trivy`).
- **Подпись.** `cosign` подписывает образ/артефакт ключом (или keyless через OIDC). Подпись хранится в registry рядом с образом.
- **Attestation.** Подписанное утверждение о артефакте (например, provenance сборки). Формат in-toto.
- **SLSA.** Уровни зрелости сборки: SLSA 1–4. Чем выше, тем строже provenance и изоляция сборки.
- **Verification.** При деплое admission-контроллер (Kyverno, OPA/Gatekeeper, cosign policy-controller) проверяет подпись/attestation.

Ключевые понятия для атаки:

- **Mutable tags.** Тег `latest`/`v1` можно перезаписать после верификации.
- **Verification policy.** Что именно проверяется: подпись? attestation? issuer? `subject`? Часто — только «есть подпись», без привязки к репозиторию.
- **Keyless.** Подпись привязана к OIDC identity (репозиторий/ветка); слабые условия — вход.
- **Trust root.** Где хранится публичный ключ; если его можно подменить — верификация бессмысленна.

## Инструменты и команды

Генерация и проверка SBOM:

```bash
syft myimage:latest -o spdx-json > sbom.spdx.json
trivy image --format cyclonedx myimage:latest > sbom.cdx.json
grype sbom:sbom.spdx.json
```

Подпись и проверка (cosign):

```bash
# Подпись ключом
cosign sign --key cosign.key myregistry/myimage@sha256:<digest>

# Проверка
cosign verify --key cosign.pub myregistry/myimage:latest
cosign verify-attestation --key cosign.pub --type slsaprovenance myregistry/myimage:latest

# Keyless
cosign sign myregistry/myimage@sha256:<digest>
cosign verify --certificate-identity-regexp 'https://github.com/org/repo/.+' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com myregistry/myimage:latest
```

Верификация в admission:

```yaml
# Kyverno: проверка подписи cosign
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata: { name: verify-images }
spec:
  validationFailureAction: Enforce
  rules:
    - name: verify-signature
      match: { any: [{ resources: { kinds: [Pod] } }] }
      verifyImages:
        - imageReferences: ["myregistry/*"]
          attestors:
            - entries:
                - keys: { publicKeys: "-----BEGIN PUBLIC KEY-----..." }
```

## Разобранный пример: обход верификации через mutable-тег

Сценарий: в кластере admission-контроллер проверяет, что образ подписан. Проверка настроена на **тег**, а не digest.

Шаг 1 — убеждаемся, что проверка слабая. Смотрим политику:

```bash
kubectl get clusterpolicy verify-images -o yaml | grep -A3 imageReferences
# imageReferences: ["myregistry/*"]
```

Если политика проверяет тег `myregistry/app:v1`, а не `@sha256:...`, возникает **TOCTOU**: подпись проверяется для текущего содержимого тега, а между проверкой и pull тег может измениться.

Шаг 2 — если у нас есть push в `myregistry` (например, через украденные креды CI), мы:

```bash
# 1. Подписываем свой образ (или используем уже подписанный доверенный)
# 2. Пушим его под тегом, который проверяется
docker tag myimage myregistry/app:v1
docker push myregistry/app:v1
# 3. Перезаписываем тег на свой (неподписанный) образ
docker tag malicious myregistry/app:v1
docker push myregistry/app:v1
```

Если верификация была на digest — не сработает; на тег — есть окно.

Шаг 3 — обход через **слабую политику**: если проверяется только «есть подпись любым ключом» или «любой issuer», мы можем подписать своим ключом/OIDC и пройти. Проверяем:

```bash
kubectl get clusterpolicy verify-images -o yaml | grep -iE 'keys|issuer|subject|identity'
```

Отсутствие привязки к `identity`/`issuer` — дыра.

Шаг 4 — обход через **keyless с широким условием**: если policy принимает любую OIDC-identity из организации, мы получаем подпись из своего репозитория (как в `cloud-gcp-wif`, но для cosign).

Шаг 5 — **компрометация ключа подписи.** Если приватный ключ cosign утёк (в CI, в Git, в бакете), мы подписываем произвольные образы, и верификация проходит легитимно. Ищите `cosign.key` в артефактах и логах.

Шаг 6 — **SBOM не проверяется.** Если SBOM/attestation не верифицируются, уязвимые зависимости проходят; SBOM — только документация.

## Варианты атак и обходов

- **Mutable tags (TOCTOU).** Верификация тега, а не digest.
- **Слабая политика.** Проверка «есть подпись» без привязки к ключу/identity.
- **Keyless с широким условием.** Любая identity организации проходит.
- **Компрометация ключа.** Утёкший приватный ключ = легитимная подпись.
- **Подмена trust root.** Изменение публичного ключа в политике/ConfigMap.
- **Registry poisoning.** Push в репозиторий, который деплоится (`cloud-artifact-registry`).
- **Dependency confusion.** Внутреннее имя пакета в публичном registry с большей версией.
- **Typosquatting.** Похожие имена пакетов/образов.
- **Build-time injection.** Компромисс пайплайна до подписи: артефакт подписывается, но уже вредоносный.
- **Provenance forgery.** Если provenance не привязан к изолированной сборке (SLSA 1–2), его можно подделать.

## Частые ошибки и подводные камни

- **Проверять тег вместо digest.** Классический TOCTOU.
- **Не привязывать подпись к identity/issuer.** Проверка становится бессмысленной.
- **Хранить приватный ключ в CI-переменной.** Утечка = полный контроль подписи.
- **Считать SBOM защитой.** SBOM — документация, а не контроль; нужна верификация и сканирование.
- **Игнорировать SLSA-уровень.** Низкий уровень означает слабый provenance.
- **Забывать про build-time.** Подпись не спасает, если пайплайн скомпрометирован до подписи.

## Защита и детект

- **Верификация по digest**, не по тегу.
- **Строгие политики:** конкретный ключ/issuer/identity, конкретные репозитории.
- **Keyless с узкими условиями** (репозиторий + ветка).
- **Изоляция ключей подписи** (KMS/HSM, короткоживущие сертификаты).
- **SLSA 3–4** для сборки; изолированные, воспроизводимые сборки.
- **Сканирование SBOM** (grype/trivy) и политики на критические уязвимости.
- **Детект.** Логи admission-контроллера (отказы верификации), изменения политик, push в защищённые репозитории, изменения trust root. Алерты на новые подписи от неизвестных identity, на перезапись тегов.
- **Immutable tags** в registry (`immutableTags` в ECR/ACR), чтобы исключить TOCTOU.

## Практические цепочки атаки на supply chain

Соберём типовые цепочки, которые встречаются в реальных пентестах:

1. **CI-компромисс → подписанный backdoor.** Если пайплайн скомпрометирован до шага подписи, вредоносный артефакт подписывается легитимным ключом и проходит верификацию. Подпись не защищает от build-time инъекции — нужен SLSA 3+ с изоляцией.
2. **Украденные креды registry → подмена образа.** Push в репозиторий, который деплоится, под тегом/дайджестом, который уже доверяют. Если тег mutable — TOCTOU; если нет — прямая подмена.
3. **Dependency confusion.** Внутреннее имя пакета (`@company/utils`) не занято в публичном registry; атакующий публикует свою версию с большим номером, и сборщик подтягивает её. Защита — scoped-реестры и приоритет внутреннего источника.
4. **Typosquatting.** Похожее имя пакета/образа; разработчик опечатывается. Защита — проверка имён и allowlist.
5. **Утечка ключа подписи.** `cosign.key` в Git/бакете/CI-логе → выпуск произвольных подписей. Ищите ключи в артефактах.
6. **Слабый keyless.** Условие доверия по организации, а не по репозиторию/ветке → любой репозиторий подписывает.
7. **Provenance forgery.** SLSA 1–2 позволяет подделать attestation; без верификации сборки provenance не гарантирует ничего.
8. **SBOM как маскировка.** Наличие SBOM без сканирования создаёт иллюзию контроля; уязвимые зависимости проходят.

Каждая цепочка начинается с одного слабого звена: необязательная верификация, слабое условие, утёкший ключ или контроль источника. На пентесте ищите именно это звено.

## SLSA-уровни на практике

SLSA описывает зрелость цепочки сборки, и это прямо влияет на то, что вы можете подделать:

- **SLSA 1.** Есть provenance, но он генерируется самим пайплайном без гарантий — его легко подделать. Подписи нет или она не связана с изолированной сборкой.
- **SLSA 2.** Хостингуемая сборка с генерацией подписанного provenance, но без строгой изоляции. Атакующий с доступом к пайплайну может повлиять на артефакт.
- **SLSA 3.** Изолированная сборка, provenance подписан сервисом сборки, артефакт нельзя изменить после. Значительно сложнее подделать.
- **SLSA 4.** Плюс двухфакторное ревью и воспроизводимая сборка. Максимальная строгость.

Практический вывод для атакующего: **низкий SLSA = слабый provenance**, и подделка attestation возможна. Если заявлен SLSA 2, но нет проверки изоляции, вы можете внедриться в сборку. Для защиты: стремитесь к SLSA 3+, проверяйте provenance в admission, привязывайте его к конкретному builder и репозиторию. При оценке supply chain выясняйте фактический уровень (по конфигурации CI), а не заявленный в документации.

## Что дальше / решение

Подпись артефактов — мощная защита, но только если она **обязательна, строга и привязана к digest/identity**. При оценке supply chain проверьте: по чему верифицируют (тег или digest), что именно проверяют (ключ/issuer/identity), где хранится trust root, кто может пушить в деплоящиеся репозитории, не утёк ли ключ подписи. Ищите TOCTOU, слабые keyless-условия и компромисс пайплайна. Для пентеста это часто путь от CI-доступа к произвольному коду в проде. Записывайте, какой слой верификации не сработал.
