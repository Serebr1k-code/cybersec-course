## Задача

В прошлых уроках мы подкладывали пакеты и образы. Но что, если организация всё проверила — ставит только подписанные образы и генерирует SBOM? Задача этого урока — понять, **как именно** устроены SBOM, подписи (Sigstore/cosign) и attestations, и где верификацию можно обмануть. Разберём на конкретном образе.

## Данные: образ и его подпись

У цели есть образ `registry.acme.io/payments/api:v1`. Организация хвастается, что «всё подписано». Проверяем подпись самим инструментом cosign:

```
$ cosign verify --key cosign.pub registry.acme.io/payments/api:v1
Error: no matching signatures: signature not found
```

Подписи нет. Но образ всё равно где-то используется — значит, верификация либо не включена, либо включена не везде. Это первая трещина.

## Что такое SBOM, подпись и attestation

- **SBOM** (Software Bill of Materials) — инвентарь: какие компоненты и версии внутри артефакта. Нужен, чтобы знать, что у тебя внутри, и реагировать на инциденты.
- **Подпись** — криптографическая метка: кто-то, владеющий ключом, удостоверил артефакт. У Sigstore ключ короткоживущий и привязан к identity через OIDC.
- **Attestation** — подписанное утверждение **об** артефакте (например, «собран из коммита X пайплайном Y»). В экосистеме Sigstore это хранится рядом с образом.

Посмотрим, что прикреплено к образу:

```
$ cosign triangulate registry.acme.io/payments/api:v1
registry.acme.io/payments/api:sha256-9f2c....sig
$ cosign verify-attestation --key cosign.pub --type slsaprovenance registry.acme.io/payments/api:v1
Error: no matching attestations
```

Ни подписи, ни attestation. Верификация, скорее всего, объявлена, но не enforced.

## Пробуем в лоб: подменяем тег

Раз подпись не проверяется на деплое, вернёмся к mutable-тегу из `cloud-artifact-registry`. Но теперь проверим, не отвергнет ли деплой неподписанный образ по политике:

```
$ docker push registry.acme.io/payments/api:v1
$ kubectl set image deploy/api api=registry.acme.io/payments/api:v1
deployment.apps/api image updated
```

Обновилось. Политика admission не отклонила неподписанный образ — значит, наша подмена пройдёт.

## Приём: где верификация обманывается

Даже если подпись проверяется, есть классические дыры:

1. **Mutable-тег + проверка тега, а не digest.** Подписан `v1@sha256:AAAA`, а деплой тянет `v1` и получает `sha256:BBBB`. Это **TOCTOU** (time-of-check to time-of-use): проверили одно, использовали другое.
2. **Необязательная проверка.** Флаг вида `--enforce=false` или отдельный «предупреждающий» режим. Ошибка логируется, деплой продолжается.
3. **Компрометация ключа подписи.** Если приватный ключ подписи лежит в CI или в репозитории — подпись перестаёт что-либо гарантировать.
4. **Подделка provenance.** Если attestation строится из переменных, которые контролирует атакующий (имя коммита, workflow), можно подписать «легитимное» происхождение для своего кода.

Проверка, enforced ли политика:

```
$ kubectl get validatingwebhookconfigurations | grep -i cosign
$ kubectl describe clusterimagepolicy
```

Пусто — политики нет. Значит, вся «подпись» — декларация.

## Полный прогон: от «всё подписано» до RCE

1. **Проверяем подпись.** `cosign verify` → «signature not found».
2. **Проверяем attestation.** `verify-attestation` → пусто.
3. **Проверяем enforcement.** Ищем admission-политику — её нет.
4. **Подменяем.** Push своего образа под тем же тегом.
5. **Деплой.** `kubectl set image` — образ принят.
6. **Код исполняется** с правами пода: читаем service-account токен и идём в облако (см. `cloud-post-exploit`).

Организация «подписывала» артефакты, но не проверяла их — и это то же самое, что не подписывать.

## SBOM — тоже канал утечки

Парадокс: инструмент, который должен повышать безопасность, сам бывает источником данных для атакующего. SBOM перечисляет **точные версии** всех компонентов — идеальную карту для подбора уязвимых зависимостей. Если SBOM публикуется вместе с релизом, атакующий получает готовый список целей.

Смотрим опубликованный SBOM:

```
$ curl -s https://registry.acme.io/payments/api/v1/sbom.json | jq -r '.components[] | "\(.name)@\(.version)"'
log4j-core@2.14.1
spring-core@5.2.0
```

Версии конкретные — по ним мгновенно видно, что версия уязвима. Проверка на известные дыры:

```
$ grype sbom:sbom.json
NAME          INSTALLED  VULNERABILITY  SEVERITY
log4j-core    2.14.1     CVE-2021-44228 Critical
```

Так SBOM ускоряет атаку, а не защиту — если не сопровождается своевременным патчингом.

## SLSA: уровни, а не галочка

**SLSA** (Supply-chain Levels for Software Artifacts) — лестница гарантий сборки от 1 до 4:

- **L1** — процесс сборки задокументирован и выдаёт provenance.
- **L2** — сборка на хостед-платформе, provenance подписан.
- **L3** — сборка изолирована, provenance не подделывается.
- **L4** — двухфакторная проверка + герметичная сборка.

Ключевое: SLSA описывает **гарантии**, а не «мы включили cosign». Без enforced-проверки provenance уровень фиктивен.

## Защита и что реально ломает обман

- **Deploy по digest**, не по тегу — закрывает TOCTOU.
- **Enforced admission-политика** (Kyverno/OPA/Cosign policy controller), отклоняющая неподписанное.
- **Ключ подписи в KMS/HSM**, не в CI-переменной.
- **Проверка provenance** в дополнение к подписи образа.
- **Публикация SBOM** и сверка его с реальным содержимым.

## Если не сработало

- **Admission отклоняет неподписанное** — нужен ключ подписи.
- **Deploy по digest** — подмена тега бесполезна.
- **Ключ в HSM** — подпись не подделать.
- **Attestation обязателен** — придётся добывать подписывающий ключ или искать обход в самом пайплайне.

## Мини-сценарий: неподписанный образ целиком

1. **Проверка подписи.** `cosign verify --key cosign.pub registry.acme.io/payments/api:v1` → `signature not found`.
2. **Проверка attestation.** `cosign verify-attestation --type slsaprovenance ...` → `no matching attestations`.
3. **Проверка enforcement.** `kubectl get validatingwebhookconfigurations | grep -i cosign` → пусто. Политики нет.
4. **Подмена.** `docker tag payload:evil registry.acme.io/payments/api:v1` → `docker push`.
5. **Деплой.** `kubectl set image deploy/api api=registry.acme.io/payments/api:v1` → обновлено, образ принят.
6. **Код.** Наш образ читает SA-токен пода и идёт в облако.
7. **Вывод.** «Подписано» было декларацией: подпись не проверялась.

Подпись защищает только тогда, когда её отсутствие **блокирует** деплой.

## Что мы теперь знаем

1. SBOM — инвентарь, подпись — удостоверение, attestation — утверждение о сборке.
2. Подпись без enforced-проверки ничего не защищает.
3. Mutable-тег + проверка тега дают TOCTOU.
4. Ключ подписи в CI ломает всю модель доверия.
5. SLSA — уровни гарантий, а не галочка «мы подписываем».

## На что смотреть дальше

- `cosign verify`/`verify-attestation` — есть ли подписи вообще.
- Admission-политики: `ClusterImagePolicy`, `validatingwebhookconfigurations`.
- Deploy по тегу или по digest.
- Где лежит приватный ключ подписи.
- Есть ли реальный provenance и какого SLSA-уровня.

## Частые ошибки при верификации

- **Подписывают, но не проверяют.** Самая частая: подпись есть, enforcement выключен.
- **Проверяют тег, а деплоят digest (или наоборот).** Несоответствие — окно для TOCTOU.
- **Ключ подписи в CI-переменной.** Любой, кто дотянется до пайплайна, подпишет что угодно.
- **Verify «предупреждает», но не блокирует.** В логах ошибка, деплой продолжается.
- **SBOM генерируется, но не сверяется.** Инвентарь есть, а с реальным образом не сличается.
