## Вопрос, с которого всё начинается

В организации деплоят через Atlantis: комментарий `atlantis apply` в pull request запускает `terraform apply` на сервере. Ты нашёл репозиторий, где PR можно открыть от своего имени, и конфиг `atlantis.yaml`. Вопрос: можно ли заставить сервер выполнить твой код, как это связано с облачными кредами и почему «просто открыть PR» здесь опасно?

## Что такое Terragrunt и Atlantis

Terragrunt — обёртка над Terraform, которая убирает дублирование: общий backend, версии, зависимости между модулями. Atlantis — сервер, который слушает webhooks из GitHub/GitLab и по команде в комментарии PR запускает `terraform plan` и `apply`. Spacelift и env0 — SaaS-аналоги. Все они решают одну задачу: применить инфраструктурный код автоматически, из pull request. Значит, у сервера есть и облачные креды, и право исполнять код из PR.

## Сквозной пример: atlantis.yaml

Смотрим конфигурацию проекта Atlantis:
```
$ cat atlantis.yaml
version: 3
projects:
- name: prod
  dir: infra/prod
  workflow: custom
  apply_requirements: []
```
`apply_requirements: []` означает, что для apply не нужны ни аппрув, ни пройденный plan. `workflow: custom` ссылается на workflow, который может быть изменён. Если сервер доверяет `atlantis.yaml` из PR, ты управляешь тем, что и как он исполняет.

## Terragrunt и remote state

Terragrunt описывает, где лежит state (`remote_state`), как генерировать backend-конфиг и как связывать модули через `dependency`. Секреты тут те же, что у Terraform: state может содержать пароли и ключи. Плюс Terragrunt умеет `run-all` — применить много модулей сразу. Если один модуль скомпрометирован, `run-all` распространяет эффект на все.

## Как Atlantis исполняет код

Atlantis на каждый PR запускает `terraform` в директории проекта. Ключевой факт: Terraform-код может исполнять произвольные команды. Например, `external` data source запускает программу, `local-exec` provisioner выполняет shell, а `null_resource` — команды. Значит, `terraform plan` (не только apply!) уже может исполнить код. Если PR вызывает plan на сервере с кредами, ты получаешь RCE на этом сервере.

## Вебхуки и секреты

Atlantis принимает вебхуки от VCS и проверяет подпись секретом. Если секрет утёк, можно отправить поддельный вебхук, имитирующий комментарий, и запустить план/apply без реального PR. Дополнительно Atlantis хранит креды VCS-токена и облака; компромисс сервера Atlantis = компромисс всего пайплайна деплоя.

## Workflows и кастомизация

`workflow` в Atlantis описывает шаги (`init`, `plan`, `apply`) и может включать произвольные команды (`run` step). Если `allowed_overrides`/`allow_custom_workflows` включены, PR может подсунуть свой workflow и выполнить любую команду на сервере. Это самый прямой путь: не нужно ломать Terraform-провайдер, достаточно добавить шаг `run: curl ...`.

## Spacelift и SaaS-плоскость

Spacelift/env0 исполняют apply в своих worker'ах, а к облаку ходят через интеграцию (роль, которую принимают workers). Атака смещается: вместо RCE на твоём сервере — использование доверия SaaS к твоему аккаунту. Утёкший API-токен Spacelift даёт очередь запусков и доступ к переменным окружения, включая секреты. Плюс self-hosted worker'ы (private workers) возвращают нас к RCE.

## Типовые мисконфиги автоматизации

| Мисконфиг | Последствие | Как искать |
|---|---|---|
| `apply_requirements: []` | apply без аппрува | atlantis.yaml |
| `allow_custom_workflows` | RCE через workflow | server-side config |
| Утёкший webhook-секрет | подделка запуска | секреты |
| `external`/`local-exec` в модулях | RCE при plan | код Terraform |
| Широкие креды деплоя | эскалация | роль/ключ |
| Публичный Atlantis UI | разведка проектов | сетевой доступ |

## Полный прогон: от PR к RCE

Шаги. Первый: найти Atlantis (UI, API, подпись вебхука). Второй: изучить `atlantis.yaml` и `apply_requirements`. Третий: проверить, разрешены ли custom workflows. Четвёртый: добавить в Terraform модуль `external`-источник или `local-exec`, читающий окружение. Пятый: открыть PR и вызвать `atlantis plan`. Шестой: забрать результат (секреты, реверс-шелл). Седьмой: закрепиться.

## Инструменты и команды

Полезны: `atlantis` CLI и API (`/api/plan`, `/api/apply`), просмотр `atlantis.yaml` и server-side repo config, разбор Terraform-модулей на `external`/`local-exec`/`null_resource`. Для Spacelift — API-токен и GraphQL. Для проверки подписи вебхука — заголовок `X-Atlantis-Signature`.

## OPSEC и детект

Atlantis логирует все plan/apply и комментарии. Добавление `run`-шага или `local-exec` в PR — заметное изменение, видимое ревьюеру и в diff. Поддельный вебхук оставляет запись без соответствующего комментария — аномалия. Тихий сценарий — использовать уже существующий `external`-источник с параметризуемым аргументом.

## Частые вопросы

Достаточно ли plan для RCE? Часто да — через `external`/`local-exec`. Нужен ли apply? Не всегда. Опасен ли Terragrunt? Да, `run-all` распространяет эффект. Что даёт API-токен Spacelift? Очередь запусков и доступ к переменным. Помогает ли аппрув? Только если он реально обязателен.

## Что не сработает

Если `apply_requirements` требуют аппрув доверенного пользователя и plan не исполняет код, PR не поможет. Запрет custom workflows и `external`-источников закрывает основной путь. Строгая проверка подписи вебхука не даст подделать запуск. И изолированный worker без облачных кредов не даст эскалации.

## Разбор кейса: PR добавил run-шаг

История из практики. Atlantis был настроен с `allow_custom_workflows: true`, чтобы команды могли экспериментировать. Атакующий открыл PR, в `atlantis.yaml` сослался на свой workflow с шагом `run`, который читал окружение сервера и отправлял его наружу. Комментарий `atlantis plan` запустил workflow на сервере с облачными кредами. Секреты деплоя утекли. Никакой уязвимости в Atlantis не было: конфигурация сама разрешала исполнять произвольные команды из PR. Это классический пример, почему «гибкость» в CI-инструментах равна RCE.

## Terragrunt и зависимости

Terragrunt-блок `dependency` позволяет одному модулю читать выходы другого. Это создаёт граф и означает, что компромисс одного модуля может влиять на другие: подменив output, ты меняешь вход другого модуля. `run-all` применяет всё разом, поэтому одна ошибка в общем модуле распространяется на весь стек. При пентесте строй карту зависимостей (`terragrunt graph-dependencies`) — она показывает, куда дотянется изменение.

## Защита автоматизации деплоя

Меры защиты. Первое: обязательный аппрув на apply (`apply_requirements: [approved, mergeable]`). Второе: запретить custom workflows и `external`/`local-exec` из недоверенных PR. Третье: изолировать сервер Atlantis — отдельная сеть, минимальные креды. Четвёртое: защитить webhook-секрет и ротировать его. Пятое: не давать PR-сборкам секретов продакшна. Шестое: аудит команд и diff-ов. Каждая мера закрывает один из путей к исполнению кода.

## Частые заблуждения

Первое: «plan безопасен, он ничего не меняет». Plan исполняет код через `external` и provisioners. Второе: «PR пройдёт ревью, значит безопасно». Ревьюер может не заметить добавленный run-шаг или подменённый workflow. Третье: «Atlantis — просто удобная автоматизация». Это сервер с правами деплоя. Четвёртое: «Spacelift изолирует нас от RCE». Self-hosted workers возвращают ту же проблему. Пятое: «Terragrunt — просто обёртка». Он расширяет поверхность зависимостями и `run-all`.

## Atlantis API и вебхуки

Atlantis предоставляет HTTP API (`/api/plan`, `/api/apply`) и принимает вебхуки от VCS. API защищён токеном, вебхуки — подписью. Если токен API утёк, можно запускать планы без PR. Если утёк webhook-секрет, можно подделать событие VCS. Оба пути ведут к исполнению Terraform на сервере. Проверяй также UI: открытый интерфейс раскрывает проекты, их статусы и историю — полезная разведка перед попыткой запуска.

## Как искать автоматизацию деплоя

Ищи признаки Atlantis: файл `atlantis.yaml` в репозиториях, сервис `atlantis` в DNS, комментарии-команды в PR, сервер на порту 4141. Для Spacelift/env0 — API-токены в CI и упоминания в конфигах. Для Terragrunt — `terragrunt.hcl` с `remote_state` и `dependency`. Собрав это, ты видишь, где инфраструктура применяется автоматически, какие у сервера креды и насколько легко подсунуть ему свой код.

## Spacelift и self-hosted workers

SaaS-плоскости (Spacelift, env0, Scalr) исполняют apply на своих серверах, а к облаку ходят через интеграцию: роль, которую принимают их workers, либо OIDC-федерацию. Если используется стандартный runner, RCE на твоём сервере не нужен — ты работаешь через API-токен: создаёшь run с изменённым кодом, и секреты переменных резолвятся на стороне SaaS. Но как только включают private/self-hosted workers (чтобы достать до внутренней сети), возвращается RCE на машине в твоей инфраструктуре. Смотри, где именно исполняется run: это определяет, куда идти.

## Итоговая цепочка атаки

Соберём всё вместе. Атакующий находит сервер автоматизации деплоя (Atlantis/Spacelift). Изучает конфигурацию: нужен ли аппрув, разрешены ли custom workflows. Если да — открывает PR, добавляет шаг, читающий окружение, и вызывает plan/apply. Сервер исполняет Terraform с облачными кредами и отправляет секреты наружу. Дальше атакующий использует креды и закрепляется. Цепочка держится на двух допущениях: код из PR исполняется и у сервера есть секреты. Закрой любое из них — и атака не проходит.

## Что мы теперь знаем

1. Terragrunt — DRY-обёртка Terraform; state всё так же содержит секреты.
2. Atlantis исполняет Terraform из PR, а Terraform умеет запускать код.
3. `apply_requirements: []` и custom workflows открывают RCE.
4. Утёкший webhook-секрет позволяет подделать запуск.
5. Spacelift переносит атаку на доверие SaaS к аккаунту.
