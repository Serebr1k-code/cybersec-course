## Вопрос, с которого всё начинается

Ты скомпрометировал инстанс в dev-VPC и хочешь дойти до prod-базы в другом VPC. Прямого маршрута, как кажется, нет — сети изолированы. Но администраторы соединили VPC через peering или Transit Gateway для общих сервисов. Вопрос: существует ли транзитивный путь из dev в prod, и как его найти, не имея доступа к консоли? Ответ — в таблицах маршрутов и в топологии соединений.

## Зачем сети соединяют

Облачные сети по умолчанию изолированы. Но компаниям нужно, чтобы сервисы разных VPC видели друг друга: общие базы, мониторинг, CI, общий DNS. Для этого используют VPC peering (прямое соединение двух сетей), Transit Gateway (хаб, к которому подключены многие VPC) и hub-spoke (звезда с центральным VPC). Каждое соединение расширяет достижимость — и для бизнеса, и для атакующего.

## Сквозной пример: таблицы маршрутов

Смотрим маршруты инстанса, на котором сидим:
```
$ ip route
default via 10.0.0.1 dev eth0
10.0.0.0/16 dev eth0 scope link
10.1.0.0/16 via 10.0.0.1 dev eth0
```
Строка `10.1.0.0/16 via 10.0.0.1` означает, что трафик в сеть `10.1.0.0/16` (другой VPC) идёт через шлюз `10.0.0.1`. Значит, peering существует, и из dev-сети `10.0.0.0/16` достижима сеть `10.1.0.0/16`. Это ребро графа: из dev можно пробовать ходить в prod-диапазон.

## Peering, Transit Gateway и hub-spoke

VPC peering соединяет две сети напрямую: маршруты добавляются в обе таблицы. Transit Gateway — центральный хаб: к нему подключаются десятки VPC, и он маршрутизирует между ними (если разрешено). Hub-spoke — звезда: spoke-сети видят хаб, но не друг друга напрямую (если маршруты не настроены). Разница важна: при peering достижимость точечная, при Transit Gateway — широкая, а hub-spoke зависит от правил на хабе.

## Чтение топологии без консоли

Без консоли топологию восстанавливают по: `ip route` на инстансах, DNS-именам (зоны раскрывают сегменты), traceroute, ответам сервисов, конфигам в репозиториях, метаданным и логам. Каждое найденное CIDR-соединение добавляется в карту. Часто peering виден по маршруту к диапазону, которого нет в своей сети.

## Обход изоляции

Предполагаемая изоляция ломается транзитивностью. Пример: dev соединён с общим VPC, общий VPC соединён с prod — значит, из dev есть путь в prod через общий. Второй случай: Transit Gateway с широкими route tables пропускает трафик между VPC, которые «не должны» видеть друг друга. Третий: общий DNS или прокси-хост, доступный из обоих сегментов, служит мостом. Ищи транзитивные пути, а не только прямые.

## Security groups и NACL как барьеры

Даже при наличии маршрута трафик может блокироваться security groups (на инстансе) и NACL (на подсети). При пентесте это уточняет карту: маршрут есть, но порт закрыт. Проверяй, какие порты открыты между сегментами — часто это 443/22/3306 «для интеграции», и именно они дают доступ. Security group с широким `10.0.0.0/8` пропускает трафик из всех сегментов.

## Типовые мисконфиги соединений

| Мисконфиг | Последствие | Как искать |
|---|---|---|
| Peering в prod из dev | lateral movement | таблицы маршрутов |
| Transit Gateway без сегментации | широкий доступ | route tables TGW |
| SG с `10.0.0.0/8` | трафик из всех VPC | правила SG |
| Общий прокси в обоих сегментах | мост | список сервисов |
| Открытый DNS между VPC | разведка | резолвинг |
| NACL разрешает всё | нет барьера на подсети | NACL |

## Полный прогон: от инстанса к prod

Шаги. Первый: прочитать маршруты (`ip route`, метаданные). Второй: собрать CIDR-диапазоны сегментов. Третий: проверить достижимость (`ping`/`nc`/`curl`) целевых диапазонов. Четвёртый: найти транзитивные пути через общие VPC. Пятый: просканировать достижимые сервисы на открытые порты. Шестой: дойти до цели и зафиксировать доступ.

## Инструменты и команды

Инструменты: `ip route`, `traceroute`, `nc`, `nmap` (из облака), DNS-резолвинг (`dig`), облачные CLI для чтения route tables (`aws ec2 describe-route-tables`). Полезные приёмы: `for cidr in ...; do nc -zv -w1 ...; done` для проверки достижимости, `nmap -Pn -p 22,443,3306 <cidr>`. В облаке сканирование внутренних диапазонов часто разрешено политикой — используй это.

## OPSEC и детект

Сканирование внутренних сетей заметно: VPC Flow Logs фиксируют соединения, IDS/IPS может алертить на горизонтальный скан. Шумно — перебирать все порты во всех сегментах. Тихий сценарий: проверять конкретные сервисы и порты, найденные из конфигов. Помни: flow logs с незнакомого инстанса — заметный след.

## Разведка без доступа

Без инстанса видно: публичные диапазоны, DNS-зоны, имена сервисов. Ошибки приложений раскрывают внутренние адреса. Документация и вакансии — топологию. Этого достаточно, чтобы построить гипотезу о соединениях и планировать движение.

## Частые вопросы

Всегда ли peering даёт доступ? Нет, мешают SG/NACL. Опасен ли Transit Gateway? Да, он расширяет достижимость. Как найти транзитивный путь? По маршрутам к общим сегментам. Помогает ли сегментация? Да, если route tables разделены. Что если маршрут есть, а порт закрыт? Ищи другой порт или другой путь.

## Что не сработает

Без маршрута трафик не пойдёт (если нет NAT/прокси). SG без нужного порта заблокирует доступ. NACL может резать на уровне подсети. И изолированные spoke-сети в hub-spoke не видят друг друга без маршрутов на хабе.

## Сценарий: dev → prod через общий VPC

Цепочка. Сидим на инстансе в `10.0.0.0/16`. В маршрутах видим путь в `10.2.0.0/16` (общий VPC). Сканируем его — находим прокси и CI-раннер. С раннера есть маршрут в `10.1.0.0/16` (prod). Через раннер (или SSRF на прокси) доходим до prod-базы. Так транзитивность через общий сегмент превращает два изолированных VPC в один путь.

## Практический чек-лист пентеста сетей

Порядок. Один: собрать маршруты и CIDR. Два: проверить прямую достижимость. Три: найти транзитивные пути. Четыре: просканировать достижимые сервисы. Пять: найти порты «для интеграции». Шесть: дойти до цели. Семь: зафиксировать доступ. Восемь: оценить flow logs.

## Что мы теперь знаем

1. Соединения VPC (peering, TGW, hub-spoke) расширяют достижимость.
2. Топология читается по маршрутам, DNS и ответам сервисов.
3. Транзитивность через общий сегмент ломает предполагаемую изоляцию.
4. SG/NACL — барьеры; часто открыты порты «для интеграции».
5. Внутреннее сканирование заметно в VPC Flow Logs.

## Топология hub-spoke на практике

В hub-spoke все spoke-сети подключены к центральному hub-VPC, но не друг к другу. Это удобно для управления, но важно понять, что маршрутизация задаётся route tables на hub. Если hub пропускает трафик между spoke-сетями (а часто пропускает, «чтобы работало»), изоляция ломается: из одного spoke можно дойти до другого. Проверяй route tables hub-а: есть ли маршруты к spoke-диапазонам и разрешён ли между ними трафик. Часто именно hub становится узлом, через который атакующий обходит сегментацию.

## Shared services как мост

Практически в любой организации есть общие сервисы: DNS, мониторинг, CI, бастион, прокси, логирование. Они доступны из многих сегментов. Такой сервис — естественный мост: если из dev можно дойти до общего CI, а из CI — до prod, то dev и prod связаны. При построении карты ищи не только прямые peering, но и общие сервисы, к которым открыт доступ из нескольких сетей. Затем проверь, есть ли у них доступ дальше.

## Проверка достижимости без сканера

Не всегда есть nmap или разрешение сканировать. Тогда используй точечные проверки: `nc -zv -w1 host port`, `curl --max-time`, `ping`, `traceroute` до целевого диапазона. По времени ответа и ошибкам можно понять, есть ли маршрут и открыт ли порт. Это тише, чем полный скан, и достаточно для подтверждения гипотезы о пути. Начинай с портов, найденных в конфигах, а не с полного перебора.

## Итог по соединениям VPC

Соединения сетей — это рёбра графа, по которым планируется lateral movement. Peering, Transit Gateway и hub-spoke расширяют достижимость по-разному, а транзитивность через общие сегменты ломает предполагаемую изоляцию. Защита: сегментация route tables, узкие security groups и контроль общих сервисов.

## Метаданные инстанса как источник карты

Метаданные инстанса (например, `169.254.169.254` в AWS) отдают не только креденшелы, но и сведения о сети: subnet-id, VPC-id, MAC, иногда route table. Из них восстанавливается, в каком сегменте ты находишься и как он связан. Собери всё, что отдают метаданные, прежде чем сканировать: это дешевле и тише. Часто там же лежит имя security group и роль — то есть сразу видно и сеть, и права.

## Peering между аккаунтами

Peering бывает не только между VPC одного аккаунта, но и между разными аккаунтами (cross-account). Тогда соединение требует принятия запроса с обеих сторон. Если оно существует, оно связывает две организации внутри одной компании (или компанию с партнёром). Cross-account peering — редкое, но очень ценное ребро: через него можно выйти за пределы своего аккаунта. Ищи его по маршрутам к диапазонам, которых нет в твоём аккаунте.

## Ограничение сканирования

В облаке внутреннее сканирование может нарушать политики и привлекать внимание. Ограничивай себя: сканируй только подтверждённые маршруты, только нужные порты, с разумной скоростью. Полный `nmap -p-` по всему `/8` — это и шумно, и долго. Лучше пройти по CIDR из маршрутов и проверить порты, найденные в конфигах. Эффективность важнее полноты.

## Итог по соединениям VPC

Карта сети строится из маршрутов, метаданных и ответов сервисов. Транзитивность через общие сегменты и cross-account peering расширяют достижимость за пределы ожидаемого. Защита: сегментация route tables, узкие security groups и контроль общих сервисов и cross-account соединений.
