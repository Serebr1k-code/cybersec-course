## Вопрос, с которого всё начинается

Компания спрятала внутренние приложения за Cloudflare Access: снаружи всё выглядит как обычный домен, а на самом деле доступ закрыт политикой, которая пускает только сотрудников через SSO. Вопрос: где здесь слабое место и как атакующий обходит Zero Trust? Ответ — в механизмах доверия: service tokens, JWT и `cloudflared`-туннели. Разберём их по очереди.

## Что такое Cloudflare Zero Trust и Access

Zero Trust — модель, где нет «внутренней сети по умолчанию»: каждый запрос проверяется. Cloudflare Access — реализация этой модели: перед приложением стоит прокси Cloudflare, который проверяет у пользователя **JWT-токен**, выданный после аутентификации (через SSO: Google, Okta, Azure AD, One-Time PIN). Плюс есть **service tokens** — для машин: пара Client ID/Secret, которой сервис предъявляет себя без человека. И **cloudflared-туннели** — агент внутри сети, который выставляет приложение в Cloudflare без открытых портов.

## Сквозной пример: политика Access

Смотрим конфиг:
```
$ cat access-policy.json
{
  "app": "internal-wiki.acme.com",
  "policies": [
    {"name": "employees", "decision": "allow",
     "include": [{"email_domain": "acme.com"}]},
    {"name": "ci-bot", "decision": "non_identity",
     "include": [{"service_token": "ci-bot"}]}
  ]
}
```
Две политики. Первая пускает любой email с доменом `acme.com` — то есть всех сотрудников. Вторая пускает сервисный токен `ci-bot` без идентичности. Уже здесь видно два вектора: если атакующий может получить почту в домене (или SSO-аккаунт) — он проходит; если утечёт service token — он проходит в обход SSO.

## Service tokens: утечка = обход SSO

Service token предъявляется двумя заголовками:
```
CF-Access-Client-Id: <id>.access
CF-Access-Client-Secret: <secret>
```
Если эти значения утекли (из CI, из конфига сервиса, из репозитория), атакующий обращается к приложению с ними — и Cloudflare пускает его как сервис, не спрашивая MFA. Это и есть самый частый обход Zero Trust на практике: не ломают криптографию, а находят токен. Проверяй, где хранятся service tokens и не переиспользуются ли они между средами.

## JWT и проверка на приложении

После аутентификации Access добавляет заголовок `Cf-Access-Jwt-Assertion` с JWT. Приложение, если оно за прокси Cloudflare, может доверять этому заголовку. Опасность в двух случаях: приложение доступно в обход прокси (по внутреннему адресу), но всё ещё доверяет заголовку, — тогда заголовок можно подделать; либо проверка подписи JWT выключена. Правильная конфигурация — проверять подпись по публичным ключам Cloudflare (`/cdn-cgi/access/certs`).

## cloudflared-туннели

`cloudflared` запускается внутри сети и соединяется с Cloudflare. Токен туннеля (или файл `cert.pem`) — это креденшел. Если он утёк, атакующий может поднять свой туннель под тем же аккаунтом и выставить свои сервисы на доверенном домене — классический захват туннеля. Либо, что хуже, прочитать конфиг туннеля и увидеть внутренние адреса (`ingress`-правила), то есть карту внутренней сети.

## Обходы и что проверять

Типичные обходы Zero Trust:
- утёкший service token (обход SSO);
- широкое правило `email_domain` (любой сотрудник, включая скомпрометированный);
- приложение, доступное напрямую по IP в обход Cloudflare;
- заголовок `Cf-Access-Jwt-Assertion`, которому доверяют без проверки;
- утёкший токен туннеля (`cloudflared`) → свой туннель;
- отсутствие MFA в политике (только email).

При аудите проверяй: какие политики, есть ли `non_identity`/service token, можно ли дотянуться до приложения в обход прокси, и где хранятся токены.

## Как проверить руками

Запрос с service token:
```
$ curl -H "CF-Access-Client-Id: $ID" -H "CF-Access-Client-Secret: $SECRET" \
       https://internal-wiki.acme.com/
```
Если ответ 200 — токен валиден и обходит SSO. Проверка прямого доступа: `curl` по внутреннему IP приложения, минуя Cloudflare.

## Что мы теперь знаем

- Cloudflare Access проверяет JWT после SSO; service tokens — для машин.
- Утечка service token = обход SSO (частый практический путь).
- Широкое правило `email_domain` пускает любого сотрудника.
- Приложение в обход прокси, доверяющее `Cf-Access-Jwt-Assertion`, уязвимо к подделке.
- Утёкший токен `cloudflared` = захват туннеля и карта внутренней сети.
