## Вопрос, с которого всё начинается

Компания спрятала внутренние приложения за Cloudflare Access: снаружи всё выглядит как обычный домен, а на самом деле доступ закрыт политикой, которая пускает только сотрудников через SSO. Вопрос: где здесь слабое место и как атакующий обходит Zero Trust? Ответ — в механизмах доверия: service tokens, JWT и `cloudflared`-туннели. Разберём их по очереди.

## Что такое Cloudflare Zero Trust и Access

Zero Trust — модель, где нет «внутренней сети по умолчанию»: каждый запрос проверяется. Cloudflare Access — реализация этой модели: перед приложением стоит прокси Cloudflare, который проверяет у пользователя **JWT-токен**, выданный после аутентификации (через SSO: Google, Okta, Azure AD, One-Time PIN). Плюс есть **service tokens** — для машин: пара Client ID/Secret, которой сервис предъявляет себя без человека. И **cloudflared-туннели** — агент внутри сети, который выставляет приложение в Cloudflare без открытых портов.

## Сквозной пример: политика Access

Смотрим конфиг:
```
$ cat access-policy.json
{
  "app": "internal-wiki.acme.com",
  "policies": [
    {"name": "employees", "decision": "allow",
     "include": [{"email_domain": "acme.com"}]},
    {"name": "ci-bot", "decision": "non_identity",
     "include": [{"service_token": "ci-bot"}]}
  ]
}
```
Две политики. Первая пускает любой email с доменом `acme.com` — то есть всех сотрудников. Вторая пускает сервисный токен `ci-bot` без идентичности. Уже здесь видно два вектора: если атакующий может получить почту в домене (или SSO-аккаунт) — он проходит; если утечёт service token — он проходит в обход SSO.

## Service tokens: утечка = обход SSO

Service token предъявляется двумя заголовками:
```
CF-Access-Client-Id: <id>.access
CF-Access-Client-Secret: <secret>
```
Если эти значения утекли (из CI, из конфига сервиса, из репозитория), атакующий обращается к приложению с ними — и Cloudflare пускает его как сервис, не спрашивая MFA. Это и есть самый частый обход Zero Trust на практике: не ломают криптографию, а находят токен. Проверяй, где хранятся service tokens и не переиспользуются ли они между средами.

## JWT и проверка на приложении

После аутентификации Access добавляет заголовок `Cf-Access-Jwt-Assertion` с JWT. Приложение, если оно за прокси Cloudflare, может доверять этому заголовку. Опасность в двух случаях: приложение доступно в обход прокси (по внутреннему адресу), но всё ещё доверяет заголовку, — тогда заголовок можно подделать; либо проверка подписи JWT выключена. Правильная конфигурация — проверять подпись по публичным ключам Cloudflare (`/cdn-cgi/access/certs`).

## cloudflared-туннели

`cloudflared` запускается внутри сети и соединяется с Cloudflare. Токен туннеля (или файл `cert.pem`) — это креденшел. Если он утёк, атакующий может поднять свой туннель под тем же аккаунтом и выставить свои сервисы на доверенном домене — классический захват туннеля. Либо, что хуже, прочитать конфиг туннеля и увидеть внутренние адреса (`ingress`-правила), то есть карту внутренней сети.

## Обходы и что проверять

Типичные обходы Zero Trust:
- утёкший service token (обход SSO);
- широкое правило `email_domain` (любой сотрудник, включая скомпрометированный);
- приложение, доступное напрямую по IP в обход Cloudflare;
- заголовок `Cf-Access-Jwt-Assertion`, которому доверяют без проверки;
- утёкший токен туннеля (`cloudflared`) → свой туннель;
- отсутствие MFA в политике (только email).

При аудите проверяй: какие политики, есть ли `non_identity`/service token, можно ли дотянуться до приложения в обход прокси, и где хранятся токены.

## Как проверить руками

Запрос с service token:
```
$ curl -H "CF-Access-Client-Id: $ID" -H "CF-Access-Client-Secret: $SECRET" \
       https://internal-wiki.acme.com/
```
Если ответ 200 — токен валиден и обходит SSO. Проверка прямого доступа: `curl` по внутреннему IP приложения, минуя Cloudflare.

## Zero Trust: как устроен доступ

Cloudflare Zero Trust заменяет VPN моделью «проверяй каждого»: пользователь проходит аутентификацию в IdP, а Cloudflare (Access) применяет политики на каждый запрос к приложению. Технически трафик идёт через Cloudflare-прокси (или через `cloudflared`-туннель к приватным ресурсам). Поверхность атаки: слабые политики (разрешить всем), обход через сервисные токены, утёкшие JWT Access, неправильная настройка `cloudflared`.

```text
user -> IdP -> Cloudflare Access -> app (policy per request)
```

Ключевое отличие от VPN: доступ проверяется на уровне приложения, а не сети. Это лучше, но политики надо настраивать строго — иначе «zero trust» превращается в «anyone trust».

## Практика: анализ политик и токенов

Что проверять: (1) политики Access (какие условия: email domain, группа, IP, устройство); (2) сервисные токены (`CF-Access-Client-Id/Secret`) — не утекли ли; (3) JWT Access — срок жизни, проверка подписи на бэкенде; (4) конфигурация `cloudflared` (какие сервисы опубликованы); (5) аутентификация IdP.

```bash
curl -H "CF-Access-Client-Id: <id>" -H "CF-Access-Client-Secret: <secret>" https://app/
```

Типичная находка: политика разрешает `Everyone` или домен `*`, либо сервисный токен с широкими правами лежит в открытом репозитории.

## Типичные ошибки конфигурации

Ошибки: (1) политика по email-домену без проверки владения доменом; (2) доверие JWT без проверки подписи (подделка); (3) публикация внутреннего сервиса без политики (просто туннель); (4) долгоживущие сервисные токены; (5) отсутствие логирования Access. Каждая ошибка ломает модель Zero Trust.

```text
policy: allow email_domain = * -> effectively public
```

Для пентеста: перечисли политики, проверь токены и JWT, оцени, что доступно без аутентификации. Не пытайся «пробить» Cloudflare — ищи ошибки конфигурации.

## Расширенный разбор: туннель и Access

Cloudflare Tunnel (`cloudflared`) публикует приватный сервис через Cloudflare без открытия портов. Access-политика защищает доступ. Поверхность: (1) туннель без Access-политики (сервис публичен); (2) слабая политика (Everyone/`*`-домен); (3) сервисные токены в открытом виде; (4) JWT Access без проверки на бэкенде.

```text
cloudflared tunnel -> public hostname -> Access policy (optional!)
```

Ключевой риск — забыть Access-политику: туннель сам по себе делает сервис публичным.

## Практика: анализ конфигурации

Что проверять: (1) список туннелей и опубликованных hostname; (2) Access-политики (условия); (3) сервисные токены; (4) JWT (срок, подпись); (5) IdP-интеграцию. Инструменты: Cloudflare API/dashboard, `cloudflared`, анализ JWT.

```bash
curl -s https://<public-hostname>/   # доступно ли без Access?
```

Типичная находка: hostname без Access-политики или политика `allow everyone`.

## Защита

Меры: Access-политика на каждый hostname, строгие условия (группа, IdP, устройство), проверка JWT на бэкенде, короткие токены, ротация сервисных токенов, логирование. Вывод: Zero Trust работает только при строгих политиках; «туннель без политики» — публичный сервис.

## Расширенный разбор: проверка JWT на бэкенде

Cloudflare Access выдаёт JWT (`CF_Authorization`), который бэкенд должен проверять (подпись через JWKS Cloudflare, `aud`, `exp`). Если бэкенд не проверяет подпись, можно подделать JWT и обойти Access. Это частая ошибка «мы за Cloudflare, значит безопасно».

```text
backend trusts CF_Authorization without verifying -> forge JWT -> bypass
```

Проверь: как бэкенд валидирует токен. Если он просто доверяет заголовку — это находка.

## Практика и защита

Практика: список hostname, Access-политики, сервисные токены, JWT, IdP. Инструменты: Cloudflare API, `cloudflared`, анализ JWT. Защита: Access на каждый hostname, строгие условия, проверка JWT на бэкенде, короткие токены, ротация, логирование. Вывод: Zero Trust — это политики и валидация, а не сам туннель.

## Чек-лист Zero Trust

1. Список туннелей и hostname. 2. Access-политика на каждый hostname. 3. Условия политики. 4. Сервисные токены (утечки). 5. Проверка JWT на бэкенде. 6. Логирование. Инструменты: Cloudflare API, `cloudflared`, анализ JWT.

## Разбор кейса: туннель без Access-политики

История из практики. Администратор поднял `cloudflared`-туннель к внутреннему приложению и опубликовал hostname, но забыл создать Access-политику. Приложение стало публично доступным в интернете, без аутентификации. Атакующий нашёл hostname через сертификат-логи (Certificate Transparency) и получил доступ. Вывод: сам туннель не защищает — защищает Access-политика; её отсутствие делает сервис публичным, а имена hostname утекают через CT-логи и DNS.

## Что мы теперь знаем

- Cloudflare Access проверяет JWT после SSO; service tokens — для машин.
- Утечка service token = обход SSO (частый практический путь).
- Широкое правило `email_domain` пускает любого сотрудника.
- Приложение в обход прокси, доверяющее `Cf-Access-Jwt-Assertion`, уязвимо к подделке.
- Утёкший токен `cloudflared` = захват туннеля и карта внутренней сети.
