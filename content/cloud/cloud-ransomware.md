## Зачем этот урок

Ransomware в облаке выглядит иначе, чем на рабочих станциях. Здесь не нужен шифровальщик на каждом хосте: достаточно **удалить бэкапы и снапшоты**, **отключить версионирование**, **удалить KMS-ключи** и **заменить/зашифровать данные** — и организация теряет доступ к ним без всякого локального шифрования. Это часто быстрее и «чище», чем классический ransomware. Этот урок — про облачные destructive-техники, их порядок, детект и то, как оценивать восстановимость (для пентеста — в рамках согласованных правил; для blue team — что защищать). Мы разбираем механику и защиту, **не** призывая к разрушению: в реальном пентесте destructive-действия выполняются только с явного согласия и в контролируемом виде.

## Как выглядит облачный ransomware

Классическая цепочка:

1. **Компромисс кредов** с широкими правами (админ/`Owner`/роль с доступом к бэкапам).
2. **Разведка бэкапов.** Найти снапшоты (EBS, RDS), версии объектов (S3 versioning), бэкапы (AWS Backup, Azure Backup, GCP Backup), репликацию (CRR, GRS), immutable-хранилища.
3. **Уничтожение восстановления.** Удалить снапшоты, бэкапы, отключить версионирование, удалить реплики, ослабить retention.
4. **Шифрование/замена данных.** Клиентское шифрование объектов (SSE-C или предварительное шифрование своим ключом), перезапись содержимого, удаление.
5. **Удаление ключей.** `ScheduleKeyDeletion` для KMS-ключа → данные нечитаемы даже если остались.
6. **Требование выкупа** (в реальных атаках).

Ключевая особенность: **уничтожение бэкапов предшествует шифрованию** — иначе жертва восстановится.

## Инструменты и команды (в контролируемом пентесте)

Разведка бэкапов:

```bash
# Снапшоты EBS/RDS
aws ec2 describe-snapshots --owner-ids self
aws rds describe-db-snapshots
aws backup list-backup-plans
aws backup list-backup-vaults

# Версионирование и репликация S3
aws s3api get-bucket-versioning --bucket prod-data
aws s3api get-bucket-replication --bucket prod-data
aws s3api get-object-lock-configuration --bucket prod-data
```

Destructive-действия (только с согласия; в пентесте — как демонстрация риска, часто без реального применения):

```bash
# Удаление снапшота
aws ec2 delete-snapshot --snapshot-id snap-123

# Приостановка версионирования
aws s3api put-bucket-versioning --bucket prod-data --versioning-configuration Status=Suspended

# Удаление версий и delete-markers
aws s3api delete-objects --bucket prod-data \
  --delete "$(aws s3api list-object-versions --bucket prod-data --query '{Objects: Versions[].{Key:Key,VersionId:VersionId}}' --output json)"

# Планирование удаления KMS-ключа (destructive!)
aws kms schedule-key-deletion --key-id <id> --pending-window-in-days 7
```

Azure/GCP аналоги: удаление snapshots, отключение soft delete, удаление Blob versions, удаление Key Vault keys, `gcloud storage rm`.

## Разобранный пример: оценка восстановимости (без разрушения)

Сценарий: пентест с задачей оценить, может ли атакующий уничтожить данные. **Не выполняем destructive-шаги** — только оцениваем возможности и документируем риск.

Шаг 1 — проверяем права (это и есть демонстрация риска):

```bash
aws iam simulate-principal-policy --policy-source-arn <our-arn> \
  --action-names ec2:DeleteSnapshot rds:DeleteDBSnapshot s3:PutBucketVersioning \
  kms:ScheduleKeyDeletion backup:DeleteBackupVault
```

Если эти действия разрешены — риск подтверждён без разрушения.

Шаг 2 — оцениваем защиту бэкапов:

```bash
# Object Lock (WORM) на бакете бэкапов
aws s3api get-object-lock-configuration --bucket prod-backups
# Версионирование
aws s3api get-bucket-versioning --bucket prod-backups
# MFA Delete
aws s3api get-bucket-versioning --bucket prod-backups   # Status + MFADelete
# Отдельный аккаунт для бэкапов
aws backup describe-backup-vault --backup-vault-name prod-vault
```

Шаг 3 — оцениваем KMS. Если ключ удаляется (`ScheduleKeyDeletion`) и нет отдельного бэкап-ключа, данные не восстановить. Проверяем key policy и права.

Шаг 4 — оцениваем репликацию и immutable. Cross-region replication, Object Lock в compliance-mode, отдельный аккаунт — всё это делает восстановление возможным вопреки атаке.

Шаг 5 — вывод: документируем, какие destructive-действия были бы возможны, какая защита стоит и где дыры. Это и есть результат — **без** фактического уничтожения. Если заказчик хочет демонстрацию, согласуйте объём (например, удаление тестового снапшота).

## Варианты атак и обходы

- **Удаление снапшотов и бэкапов.** Первый шаг ransomware — лишить восстановления.
- **Отключение версионирования.** Без версий удаление объекта необратимо.
- **Удаление KMS-ключа.** `ScheduleKeyDeletion` делает данные нечитаемыми.
- **Object Lock обход.** Compliance-mode нельзя обойти; governance-mode — можно при `s3:BypassGovernanceRetention`.
- **MFA Delete обход.** Если MFA Delete включён, удаление версий требует MFA — защита.
- **RDS/Azure SQL.** Удаление автоматических бэкапов, point-in-time recovery окна.
- **Replication как защита и как риск.** Репликация помогает восстановиться, но если атакующий удалит и реплику — нет.
- **Storage account key rotation (Azure).** Смена ключей может нарушить доступ.
- **Soft delete (Azure Blob/Key Vault).** Временное окно восстановления; можно попытаться очистить.
- **Backup vault lock.** Если vault не locked, бэкапы можно удалить.

## Частые ошибки и подводные камни

- **Начинать с шифрования.** Если бэкапы целы, жертва восстановится — сначала бэкапы.
- **Считать версионирование защитой.** Версии можно удалить при наличии прав.
- **Игнорировать отдельный аккаунт бэкапов.** Он переживает компромисс рабочего аккаунта.
- **Забывать про Object Lock.** Compliance-mode делает удаление невозможным.
- **Не проверять MFA Delete.** Включённый MFA Delete сильно усложняет атаку.
- **Разрушать в пентесте.** Destructive-действия — только с согласия; иначе это инцидент, а не пентест.

## Защита и детект

- **Бэкапы в отдельном аккаунте**, с ограниченным доступом.
- **Object Lock (compliance)** и **MFA Delete** на критичных данных.
- **Версионирование** включено и защищено (deny на `PutBucketVersioning`).
- **Immutable backup vaults** (AWS Backup Vault Lock).
- **KMS:** отдельные ключи для бэкапов, запрет `ScheduleKeyDeletion` без контроля.
- **Deny-политики/SCP** на destructive-действия (`DeleteSnapshot`, `ScheduleKeyDeletion`, `PutBucketVersioning`).
- **Детект.** GuardDuty `Impact:*`, `Policy:S3/BucketBlockPublicAccessDisabled`, `Stealth:*`. Алерты на `DeleteSnapshot`, `DeleteDBSnapshot`, `PutBucketVersioning`, `ScheduleKeyDeletion`, массовое `DeleteObject`, `DeleteBackup`. Аномалии объёма удалений.
- **Тестирование восстановления.** Регулярные учения: можете ли вы восстановиться, если бэкапы уничтожены? (Ответ должен быть — да, из immutable-копии.)

## Почему облачный ransomware эффективнее классического

Классический ransomware шифрует файлы локально, и восстановление возможно, если есть офлайн-бэкапы. В облаке атакующий сначала **лишает жертву восстановления**, и это делает атаку намного эффективнее:

- **Бэкапы в том же аккаунте.** Если снапшоты и версии живут рядом с данными, а у атакующего широкие права — он удаляет и то, и другое одной серией вызовов.
- **Единая модель доступа.** Один `Owner`/админ-ключ открывает и данные, и бэкапы, и KMS. Нет «разделения обязанностей» по умолчанию.
- **API-скорость.** Удаление тысяч объектов — это несколько API-вызовов, а не часы шифрования. Атака занимает минуты.
- **Отсутствие «воздушного зазора».** Без отдельного аккаунта/immutable-хранилища бэкапы уязвимы так же, как данные.
- **KMS как рычаг.** Удаление ключа мгновенно делает нечитаемыми все данные, зашифрованные им, — включая копии.

Отсюда контрмеры: изоляция бэкапов (отдельный аккаунт), immutable-хранилища (Object Lock compliance, Vault Lock), MFA Delete, разделение прав (никто не имеет одновременно `DeleteSnapshot` и `ScheduleKeyDeletion` на прод), deny-политики на destructive-действия, и регулярные учения по восстановлению. Оценка этих мер — важная часть пентеста облака: если бэкапы не изолированы, риск destructive-атаки критичен.

## Что означает «восстановимость» в облаке

Восстановимость — центральное понятие облачного ransomware. Данные могут быть «уничтожены» не только физически, но и логически: ключ удалён, версии стёрты, снапшоты удалены. Восстановимость определяется тем, сколько **независимых** копий существует и насколько они защищены:

- **Независимость.** Бэкап в том же аккаунте, с теми же правами — не независимый. Отдельный аккаунт, другое облако, immutable-хранилище — независимые.
- **Защищённость.** Object Lock (compliance), Vault Lock, MFA Delete делают копии неудаляемыми даже при компромиссе прав.
- **Ключи.** Если бэкап зашифрован ключом, который можно удалить, — копия бесполезна. Нужны отдельные ключи с ограниченным доступом.
- **Время.** Retention и частота бэкапов определяют, сколько данных потеряется (RPO). Point-in-time recovery — только в пределах окна.
- **Тестирование.** Реально ли вы восстанавливались из изолированной копии? Непроверенный бэкап — не бэкап.

Практика оценки: для каждого критичного ресурса выясните, где его копии, кто может их удалить, зашифрованы ли они ключом, доступным атакующему, и проводились ли учения. Если копия одна и в том же аккаунте — риск критичен. Для пентеста это документируется как находка с оценкой критичности; destructive-действия не применяются без согласия.

## Итоговая мысль

Облачный ransomware — это в первую очередь атака на **восстановление**, а не на данные. Поэтому защита строится не вокруг шифрования (оно и так есть), а вокруг **независимости и неудаляемости бэкапов**: отдельный аккаунт, immutable-хранилища, MFA Delete, разделение прав, deny-политики на destructive-действия и регулярные учения по восстановлению. Для пентеста ключевой результат — оценка того, может ли атакующий с полученными правами уничтожить восстановление, и какие меры это предотвращают. Это делается симуляцией, без фактического разрушения, и документируется как находка с критичностью.

## Что дальше / решение

Облачный ransomware — это прежде всего **уничтожение восстановления**, а потом — шифрование. Для пентеста: оцените, какие destructive-права у вас есть (симуляцией, без разрушения), какая защита стоит на бэкапах и ключах, и документируйте риск. Для blue team: изолируйте бэкапы (отдельный аккаунт, Object Lock, MFA Delete, immutable vault), запретите destructive-действия политиками и мониторьте их. Для IR: при подозрении на destructive-атаку немедленно проверьте бэкапы и KMS-ключи — их сохранность определяет восстановимость. Записывайте результаты оценки как находки с оценкой критичности.
