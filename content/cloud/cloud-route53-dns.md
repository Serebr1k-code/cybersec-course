## Вопрос, с которого всё начинается

У компании есть поддомен `shop.acme-corp.com`. Ты открываешь его в браузере — и видишь страницу с текстом `NoSuchBucket`. Никакого взлома вроде не было: кто-то просто удалил хранилище, а DNS-запись осталась. Вопрос: можно ли этим воспользоваться и почему это считается серьёзной находкой?

Ответ кроется в том, как облачный DNS ссылается на ресурсы. Разберём один такой поддомен по шагам.

## Наш пример: поддомен, который «висит»

Объект нашего урока — `shop.acme-corp.com`. Мы не будем сканировать всю компанию; проследим только одну запись от DNS до облачного хранилища и посмотрим, что произойдёт, когда хранилища уже нет.

DNS — это «телефонная книга» интернета: по имени она подсказывает адрес. Спрашивать её умеет утилита `dig`.

```
$ dig +short shop.acme-corp.com
acme-corp-shop.s3-website-us-east-1.amazonaws.com.
```

Обрати внимание: ответ — не IP-адрес, а **другое имя**. Это запись типа `CNAME` (canonical name, «каноническое имя») — псевдоним. Она говорит: «`shop.acme-corp.com` — это на самом деле `acme-corp-shop.s3-website-us-east-1.amazonaws.com`». Мы получили первый важный факт: поддомен указывает на облачный сервис AWS S3 (хранилище файлов).

## Шаг 1: что находится по этому адресу

Раз DNS ведёт на S3, спросим сам S3, что там лежит. Обратимся прямо к целевому имени:

```
$ curl -s http://acme-corp-shop.s3-website-us-east-1.amazonaws.com
<?xml version="1.0" encoding="UTF-8"?>
<Error><Code>NoSuchBucket</Code>
<Message>The specified bucket does not exist</Message>
<BucketName>acme-corp-shop</BucketName>
</Error>
```

Код `NoSuchBucket` означает буквально: «такого хранилища нет». Но DNS-запись на него всё ещё указывает. Получается **dangling-запись** («висящая»): имя ведёт в никуда.

## Шаг 2: почему «висит» — это опасно

Имена S3-хранилищ глобально уникальны: в мире не может быть двух бакетов `acme-corp-shop`. Когда-то этот бакет существовал, компания его удалила, а CNAME забыли убрать.

Теперь ключевой момент: **имя освободилось**. Любой, кто создаст бакет с точно таким же именем, автоматически начнёт отдавать контент по адресу `shop.acme-corp.com`. Это и называется **subdomain takeover** — захват поддомена.

Проверим, что имя действительно свободно, — попробуем его занять:

```
$ aws s3 mb s3://acme-corp-shop --region us-east-1
make_bucket: acme-corp-shop
```

Занялось без ошибки — значит, никто другой его не держит. Теперь положим туда файл-маркер и убедимся, что он виден на поддомене компании:

```
$ echo "taken-over-by-tester" > index.html
$ aws s3 cp index.html s3://acme-corp-shop/index.html
upload: ./index.html to s3://acme-corp-shop/index.html
$ curl -s shop.acme-corp.com
taken-over-by-tester
```

Наш текст отдаётся на домене компании. Пока это только «наш маркер», но в руках атакующего так появляется фишинговая страница на доверенном домене, перехват cookies домена или обход проверок, которые доверяют `*.acme-corp.com`.

## Шаг 3: где ещё бывают висящие записи

S3 — не единственный сервис. Та же схема работает везде, где CNAME указывает на облачный ресурс, который можно удалить и пересоздать:

| Целевое имя в CNAME | Сервис | Признак «свободно» |
|---------------------|--------|--------------------|
| `*.s3-website-*.amazonaws.com` | S3 website | `NoSuchBucket` |
| `*.cloudfront.net` | CloudFront | `Bad request`/ошибка распределения |
| `*.azurewebsites.net` | Azure App Service | `404 Web Site not found` |
| `*.github.io` | GitHub Pages | `404 There is no GitHub Pages site here` |
| `*.herokuapp.com` | Heroku | `No such app` |

Логика одна: если сервис отдаёт «такого ресурса нет», а DNS на него ведёт — запись потенциально захватываема.

## Шаг 4: как искать такие записи массово

Вручную перебирать поддомены долго. Собираем список имён и прогоняем его через сканер, который знает «отпечатки» ошибок облачных сервисов:

```
$ subjack -w subs.txt -t 100 -ssl -v -c fingerprints.json
[SUCCESS] shop.acme-corp.com is vulnerable: CNAME -> s3-website-us-east-1.amazonaws.com
[SUCCESS] cdn.acme-corp.com is vulnerable: CNAME -> cloudfront.net
```

`subs.txt` — список поддоменов (его получают из сертификатов, зон, поисковиков), `fingerprints.json` — база признаков «свободных» сервисов. На выходе — список захватываемых имён.

Сам список поддоменов удобно собирать через DNS-перебор (`dnsx`, `amass`) и пассивные источники (crt.sh), а затем сразу фильтровать записи, чей CNAME заканчивается на известные облачные домены.

## Шаг 5: как этим управляют в облаке

Записи лежат в **hosted zone** — «зоне» домена, которой управляет компания. В AWS это Route 53. Посмотреть зоны и записи можно через CLI:

```
$ aws route53 list-hosted-zones --query "HostedZones[].Name" --output text
acme-corp.com.
$ aws route53 list-resource-record-sets --hosted-zone-id Z123456ABCDEF --query "ResourceRecordSets[?Type=='CNAME'].[Name,ResourceRecords[0].Value]" --output text
shop.acme-corp.com.    acme-corp-shop.s3-website-us-east-1.amazonaws.com.
```

Если у тебя есть доступ к зоне (например, через скомпрометированный ключ с правом `route53:*`), ты можешь не только читать записи, но и **менять** их — это уже захват домена целиком, а не одного поддомена.

## Шаг 6: DNS-логи и GCP Cloud DNS

В Route 53 можно включить **query logging** — журнал всех запросов к зоне. Для защитника это способ заметить перебор поддоменов. Для атакующего — источник информации: иногда логи выгружаются в открытый S3-бакет, и тогда видно, какие поддомены существуют и кто их спрашивает.

У GCP аналогичный сервис — **Cloud DNS**. Зоны живут в проекте, и если у тебя есть право `dns.zones.update`, ты так же можешь менять записи. Посмотреть зоны можно командой:

```
$ gcloud dns managed-zones list
NAME        DNS_NAME          VISIBILITY
acme-zone   acme-corp.com.    public
```

Смысл один: где бы ни жила зона — в AWS, GCP или Azure, — доступ к ней равен доступу к DNS компании. А значит, и к её трафику.

## Шаг 7: почему записи «забывают»

Причина почти всегда организационная: команда удаляет ресурс (бакет, распределение, приложение), но забывает убрать DNS-запись. Записи правят руками, а ресурсы — кодом, поэтому они и расходятся. Хорошая гигиена — держать DNS в том же IaC, что и инфраструктуру, и удалять запись автоматически вместе с ресурсом.

## Что мы теперь знаем

По-простому:

1. DNS-запись `CNAME` — это псевдоним, указывающий на другое имя, часто облачное.
2. Если ресурс за записью удалён, а запись осталась — это dangling-запись.
3. Свободное имя облачного ресурса можно занять и начать отдавать контент на чужом поддомене.
4. Subdomain takeover ищут сканером, который сравнивает ответы сервисов с «отпечатками» ошибок.
5. Если есть доступ к DNS-зоне, можно менять записи — это ещё опаснее.

## На что смотреть дальше

- **Проверяй CNAME, а не только A-записи.** Хайджек живёт именно в псевдонимах.
- **Читай текст ошибки.** `NoSuchBucket` — S3; `404 Web Site not found` — Azure; каждая строка указывает на сервис.
- **Не путай takeover с «сайт недоступен».** Висящая запись отдаёт ошибку именно облачного сервиса, а не таймаут.
- **Помни про доказательство.** Для отчёта достаточно маркера на поддомене, не выкладывай туда ничего вредоносного.

## Куда дальше

В следующем уроке мы разберём **CDN и edge**: как за облачным ускорителем (CloudFront, Cloudflare) найти настоящий сервер-источник, который часто защищён слабее. А пока запомни главное: поддомен с CNAME на удалённый облачный ресурс — это не «мелкая ошибка», а реальный вектор захвата.

## Где пригодится

- **Bug bounty:** subdomain takeover — классическая находка с хорошей выплатой.
- **Пентест:** оценка гигиены DNS и прав на зоны в облаке.
- **Red team:** доверенный поддомен компании удобен для фишинга и обхода allow-list.
- **Blue team:** регулярный аудит висящих записей как профилактика.
