## Вопрос, с которого всё начинается

Ты тестируешь интеграцию приложения с IdP через OAuth. Приложение открывает окно входа, пользователь соглашается, и приложение получает код, который обменивает на токен. Вопрос: где в этой цепочке ошибка, которая позволяет атакующему перехватить чужой токен? Ответ почти всегда один из трёх: **redirect_uri**, **PKCE** или **state**. Разберём каждый.

## Что такое OAuth 2.0 и OIDC

OAuth 2.0 — протокол делегирования доступа: приложение (клиент) получает от пользователя разрешение (authorization) действовать от его имени, не зная пароля. OIDC — надстройка над OAuth для аутентификации (добавляет `id_token`). Основной поток — **authorization code flow**: клиент отправляет пользователя на `/authorize`, тот логинится и соглашается, IdP редиректит обратно с `code`, клиент меняет `code` на `access_token` и `id_token` на `/token`. Вся безопасность держится на том, что `code` достаётся только законному клиенту.

## Сквозной пример: authorize-запрос

Смотрим параметры клиента и запроса:
```
$ cat client.json
{
  "client_id": "acme-web",
  "redirect_uris": ["https://app.acme.com/cb", "https://app.acme.com/cb/evil"]
}
```
```
$ cat authorize-url.txt
https://idp.acme.com/authorize?response_type=code
  &client_id=acme-web
  &redirect_uri=https://app.acme.com/cb/evil
  &scope=openid+email+offline_access
  &state=abc123
```
В списке `redirect_uris` есть лишний путь `/cb/evil`. Это красный флаг: если сервер разрешает подстановочные или слишком широкие URI, атакующий может увести `code` на контролируемый им адрес.

## redirect_uri: главный вектор

`redirect_uri` говорит IdP, куда вернуть `code`. Правильная проверка — **точное** совпадение с заранее зарегистрированным значением. Ошибки, которые эксплуатируются:
- префиксное совпадение (`https://app.acme.com` разрешает `https://app.acme.com.evil.com`);
- подстановочные домены (`https://*.acme.com`);
- open redirect внутри доверенного домена (`/cb?next=https://evil`);
- path traversal в пути callback.

Перехватив `code`, атакующий обменивает его на токен (если нет привязки к клиенту) и получает доступ к данным жертвы. Поэтому `redirect_uri` — первое, что проверяют при аудите OAuth.

## PKCE и почему его отсутствие опасно

PKCE (Proof Key for Code Exchange) привязывает `code` к клиенту: клиент генерирует `code_verifier`, отправляет его хеш (`code_challenge`) на `/authorize`, а на `/token` предъявляет исходный `code_verifier`. Без PKCE перехваченный `code` можно обменять без знания секрета — что критично для публичных клиентов (SPA, мобильные приложения). Если приложение не использует PKCE, кража `code` через redirect_uri становится полной компрометацией.

## state и CSRF

`state` — случайная строка, которую клиент проверяет при возврате. Она защищает от CSRF: без неё атакующий может подсунуть жертве свой `code`, и жертва «привяжет» к себе чужой аккаунт. Отсутствие/игнорирование `state` — отдельная уязвимость, часто идущая в паре с redirect_uri.

## Consent phishing и app-консент

Не всегда нужно ломать протокол. **Consent phishing** — это когда атакующий регистрирует своё OAuth-приложение с похожим именем и просит жертву «разрешить доступ». Пользователь жмёт «Согласен» — и приложение получает токены для чтения почты/файлов. Это легальный с точки зрения протокола доступ, поэтому защита — в политиках консента (требовать админского одобрения, ограничивать scope, проверять издателей приложений).

## Что проверять при аудите

- точное ли совпадение `redirect_uri`;
- используется ли PKCE и обязателен ли он;
- проверяется ли `state`;
- есть ли open redirect на callback-домене;
- привязан ли `code` к клиенту и одноразовый ли он;
- какие scope запрашиваются и есть ли `offline_access` (refresh-токены);
- настроен ли admin consent и проверка издателя приложений.

## Как проверить руками

Подставь `redirect_uri` на свой домен в authorize-запрос и посмотри, вернёт ли IdP `code` без ошибки:
```
$ curl -sI "https://idp.acme.com/authorize?response_type=code&client_id=acme-web&redirect_uri=https://evil.example/cb&scope=openid"
```
Если редирект ведёт на `evil.example` с `code` — проверка URI сломана.

## OAuth: потоки и слабости

OAuth 2.0 — делегирование доступа: клиент получает токен для доступа к ресурсу от имени пользователя. Потоки: authorization code (с PKCE), implicit (устаревший), client credentials (машинный), device code. Слабости: (1) отсутствие PKCE → перехват кода; (2) открытый redirect_uri → кража кода/токена; (3) implicit flow → токен в URL; (4) слабая валидация `state` → CSRF; (5) client secret в публичном клиенте.

```text
authorization code + no PKCE + open redirect -> steal code -> exchange -> token
```

Каждая слабость — конкретный сценарий атаки на конкретный поток.

## Практика: эксплуатация

Маршрут: (1) найти OAuth-клиент и его `redirect_uri`; (2) проверить, принимает ли сервер поддомены/посторонние URL (open redirect); (3) если PKCE нет, перехватить код; (4) проверить `state`; (5) проверить scope (не слишком ли широкий). Инструменты: Burp, `oauth-`плагины, ручной анализ запросов.

```text
redirect_uri=https://app.evil.com -> code sent to attacker
```

Отдельно — device code flow: если включён, можно заставить пользователя авторизовать устройство атакующего (device code phishing).

## Типичные ошибки и защита

Ошибки реализации: (1) нет PKCE в public-клиентах; (2) wildcard `redirect_uri`; (3) нет проверки `state`; (4) долгоживущие токены без refresh-rotation; (5) избыточные scope; (6) device code без ограничений. Защита: PKCE обязательно, строгий `redirect_uri` (точное совпадение), `state`, короткие токены, минимальные scope, ограничение device code.

```text
PKCE: code_challenge/code_verifier -> intercepted code useless
```

Для пентеста: проверь каждый параметр потока и оцени, можно ли украсть код/токен или повысить scope.

## Расширенный разбор: кража кода и токена

Сценарий кражи authorization code: клиент без PKCE, `redirect_uri` допускает поддомен атакующего или open redirect. Атакующий заставляет жертву пройти авторизацию с подменённым redirect, получает `code`, обменивает его на токен. С PKCE это невозможно, потому что для обмена нужен `code_verifier`, которого у атакующего нет.

```text
no PKCE + open redirect -> steal code -> exchange -> token
```

Второй сценарий — implicit flow: токен возвращается в URL и утекает через Referer, логи, историю. Третий — device code phishing: жертва авторизует устройство атакующего.

## Практика: анализ OAuth-клиента

Маршрут: (1) найти клиент (`client_id`) и `redirect_uri`; (2) проверить валидацию redirect (поддомены, путь, схема); (3) проверить PKCE; (4) проверить `state`; (5) проверить scope; (6) проверить device code flow. Инструменты: Burp, ручной анализ, `oauth2-proxy` для стенда.

```text
redirect_uri=https://app.evil.com  -> allowed? then code leak
```

Для пентеста: каждую слабость оценивай как сценарий кражи кода/токена или повышения scope.

## Защита

Меры: PKCE обязательно для public-клиентов, точное совпадение `redirect_uri`, `state`, короткие токены + refresh rotation, минимальные scope, ограничение device code, привязка токена к клиенту. Вывод: большинство OAuth-атак — следствие ошибок реализации, а не протокола.

## Расширенный разбор: device code phishing

Device code flow позволяет авторизовать устройство по коду: пользователь вводит код на странице IdP и подтверждает. Если flow включён и не ограничен, атакующий инициирует вход, получает код и просит жертву «подтвердить устройство» — после чего получает токен. MFA при этом может не требоваться.

```text
attacker requests device code -> victim approves -> attacker gets token
```

Защита: ограничить device code flow, требовать MFA, мониторинг. Для пентеста — проверь, включён ли flow и какие ограничения.

## Практика и защита

Практика: проверь `redirect_uri` (точное совпадение), PKCE, `state`, scope, device code. Инструменты: Burp, ручной анализ. Защита: PKCE, строгий redirect, `state`, короткие токены, минимальные scope, ограничение device code. Вывод: OAuth-атаки — почти всегда следствие ошибок реализации, и их надо искать в каждом параметре.

## Чек-лист OAuth

1. `client_id` и `redirect_uri` (валидация). 2. PKCE. 3. `state`. 4. Scope. 5. Device code flow. 6. Срок токена и refresh rotation. Инструменты: Burp, ручной анализ. Оценивай каждую слабость как сценарий кражи кода/токена.

## Разбор кейса: кража кода без PKCE

История из практики. OAuth-клиент не использовал PKCE, а `redirect_uri` допускал любой поддомен. Атакующий зарегистрировал поддомен, заманил жертву на авторизацию с подменённым redirect и получил authorization code, который обменял на токен. Вывод: отсутствие PKCE в public-клиенте плюс слабая валидация redirect — прямой путь к краже токена. PKCE делает перехваченный код бесполезным, поэтому его отсутствие — критическая находка.

## Дополнительно: scope и refresh-токены

Избыточный scope даёт больше прав, чем нужно приложению: если клиент запрашивает `mail.readwrite` для чтения, атака расширяет импакт. Refresh-токены без ротации живут долго, поэтому утечка одного токена даёт длительный доступ. Проверь scope каждого клиента и настройку refresh rotation. Для пентеста: попробуй повысить scope (если сервер не проверяет) или использовать украденный refresh.

## Вывод по OAuth

OAuth-атаки — следствие ошибок реализации: нет PKCE, слабый redirect_uri, нет `state`, избыточный scope, device code без ограничений. Проверяй каждый параметр потока и оценивай как сценарий кражи кода/токена. Защита: PKCE, точный redirect, `state`, короткие токены, минимальные scope.

## Что мы теперь знаем

- OAuth code flow отдаёт `code` клиенту; вся защита — в привязке `code` к клиенту.
- `redirect_uri` должен совпадать точно; префиксы/подстановки = кража `code`.
- PKCE обязателен для публичных клиентов; без него кража `code` фатальна.
- `state` защищает от CSRF; его отсутствие — отдельная уязвимость.
- Consent phishing не ломает протокол, а злоупотребляет доверием пользователя.
