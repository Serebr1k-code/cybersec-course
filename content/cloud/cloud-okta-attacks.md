## Вопрос, с которого всё начинается

В репозитории инфраструктуры ты находишь переменную `OKTA_API_TOKEN` и строку `https://acme.okta.com`. Токен выглядит как длинная строка без префикса. Это Okta — система единого входа компании. Вопрос: что даёт этот токен, к каким приложениям он открывает доступ и как понять, добрался ли ты до админства тенанта?

## Что такое Okta и почему это ценная цель

Okta — облачный IdP: сотрудники входят через него в десятки приложений (почта, CRM, Git, облака). Если компания использует Okta, то Okta — центральная точка доверия. Захват тенанта Okta означает доступ ко всем подключённым приложениям сразу: не нужно ломать каждое по отдельности. Именно поэтому Okta — приоритетная цель в реальных атаках (вспомни громкие кампании против Okta-клиентов).

## Сквозной пример: утёкший API-токен

Токен Okta передаётся в заголовке `Authorization: SSWS <token>`. Пример конфига:
```
$ cat .env
OKTA_ORG_URL=https://acme.okta.com
OKTA_API_TOKEN=00EXAMPLENOTAREALTOKEN000000000000000000000
```
Проверка одним запросом: `curl -H "Authorization: SSWS $TOKEN" https://acme.okta.com/api/v1/users/me`. Если ответ — профиль пользователя, токен жив. Токен наследует права своего владельца: если это админ, у тебя админские права.

## Перечисление через API

Okta API богат. Полезные эндпоинты: `/api/v1/users` (пользователи), `/api/v1/groups` (группы), `/api/v1/apps` (приложения), `/api/v1/factors` (факторы), `/api/v1/logs` (System Log). Начинай с `/users/me`, чтобы понять, кто ты и какие роли у тебя есть. Затем `/apps` — какие приложения подключены и какие у них настройки. Затем `/users` — сколько сотрудников и какие профили.

## OIDC-приложения и их секреты

Каждое подключённое приложение в Okta имеет тип и настройки. Для OIDC-приложений это `client_id`, `client_secret`, `redirect_uris` и разрешённые scopes. Через API (`/api/v1/apps/{id}`) можно прочитать эти настройки. Секрет приложения (`client_secret`) — это креденшел: с ним можно выпускать токены для приложения. Слабый `redirect_uri` (без точного совпадения) открывает OAuth-перехват.

## Факторы MFA и их сброс

Okta хранит факторы аутентификации пользователей: `push`, `totp`, `sms`, `webauthn`. Через API их можно перечислить (`/api/v1/users/{id}/factors`) и, при наличии прав, сбросить (`DELETE`). Сброс фактора — прямой обход MFA: пользователь остаётся с одним паролем, который можно подобрать или сбросить. Это одна из самых опасных операций, доступных администратору.

## Роли администратора и имперсонация

Okta различает Super Admin, Org Admin, Group Admin, App Admin, Help Desk Admin и Read-Only Admin. Роли выдаются группам или пользователям. Эскалация: если у токена есть права на изменение групп (`/api/v1/groups`), можно добавить себя в админскую группу. Имперсонация: админ может войти «от имени» пользователя, получив его сессию в приложениях. Это мощнее кражи пароля, потому что не требует знания пароля вообще.

## Сессионные токены и sid

Помимо API-токенов Okta выдаёт сессионные cookie (`sid`) при входе в приложения. Кража `sid` позволяет переиспользовать сессию. Okta также выпускает OIDC-токены (id_token, access_token) для приложений; их можно украсть из браузера или перехватить. Для атакующего важно: API-токен даёт управление, а сессионный токен — доступ «как пользователь».

## Полный прогон: от токена к тенанту

Шаги. Первый: подтвердить токен (`/users/me`) и узнать свои роли. Второй: перечислить приложения (`/apps`) и их секреты. Третий: перечислить пользователей и группы. Четвёртый: если есть права — добавить себя в админскую группу или сбросить MFA нужного пользователя. Пятый: имперсонировать пользователя или выпустить токены приложений для доступа к данным. Шестой: зафиксировать персистентность новым API-токеном.

## Инструменты и команды

Основной инструмент — `curl` с заголовком `Authorization: SSWS`. Есть и CLI-обёртки, и инструмент `mfa`/скрипты сообщества для работы с Okta. Полезные запросы: `GET /api/v1/users`, `GET /api/v1/apps`, `GET /api/v1/groups`, `GET /api/v1/logs?since=...`. Для OAuth-перехвата используют прокси (например, evilginx-подобные) — но это уже про обход MFA.

## OPSEC и детект

Okta пишет System Log: каждое действие через API и консоль попадает туда с актором и IP. Создание пользователей, сброс факторов и изменение групп — заметные события. Чтение (`GET`) менее шумное, но тоже логируется. Тихий сценарий: сначала только чтение, затем минимально необходимое изменение. Помни: у API-токена есть дата последнего использования — владелец заметит незнакомую активность.

## Разведка без токена

Даже без токена Okta частично прозрачна. Публичная страница входа (`https://acme.okta.com`) подтверждает использование Okta. Некоторые тенанты отдают список приложений на странице входа. Ошибки OAuth с `redirect_uri` раскрывают зарегистрированные адреса. Email-домен компании часто совпадает с именем тенанта. Это даёт карту для дальнейшей атаки — например, для фишинга под страницу входа Okta.

## Частые вопросы

Можно ли подделать API-токен? Нет, это случайная строка, проверяемая на сервере. Что если токен read-only? Тогда читай конфигурацию и ищи секреты приложений. Как обойти MFA без токена? Через fatigue, AiTM или legacy-протоколы — этому посвящён отдельный урок. Опасен ли доступ только к одному приложению? Да: приложение может иметь доступ к данным компании.

## Что не сработает

Отозванный токен вернёт `401`. Read-only токен не даст менять группы и сбрасывать факторы. MFA, обязательный для всех, не даст войти паролем. И если приложение использует проверку `redirect_uri` с точным совпадением, простой OAuth-перехват не сработает.

## Okta и обход MFA: детали

Okta поддерживает несколько факторов: push-уведомление в приложении Verify, одноразовый код (TOTP), SMS и аппаратный ключ WebAuthn. Атака на push — MFA fatigue: атакующий, зная пароль, инициирует входы десятки раз, пока уставший пользователь не нажмёт «Подтвердить». Более изящный вариант — AiTM-прокси (Evilginx): фишинговая страница стоит между пользователем и Okta, забирает пароль и перехватывает уже выданный сессионный токен, обходя MFA полностью. Защита — number matching, phishing-resistant WebAuthn и короткие сессии.

## Имперсонация и сессии

Отдельная сильная техника — имперсонация. Администратор Okta может «войти от имени» пользователя, получив доступ ко всем его приложениям без пароля и без второго фактора. Через API это делается эндпоинтом имперсонации, возвращающим ссылку на приложение от лица пользователя. Для атакующего это идеальный способ тихо действовать от чужого имени: с точки зрения приложений вход выглядит легитимным, а пользователь ничего не вводит. Именно поэтому админские роли Okta так ценны.

## Работа с OAuth-приложениями

Приложения в Okta бывают SAML и OIDC. Для OIDC ключевые поля — `client_id`, `client_secret`, `redirect_uris`, `grant_types` и scopes. Если `redirect_uri` разрешает подстановочные адреса или не проверяется строго, атакующий перенаправляет код авторизации на свой сервер. Если утёк `client_secret`, можно выпускать токены от имени приложения — а это доступ к его данным. При разведке выгружай настройки всех приложений: одно из них почти всегда настроено слабее остальных.

## Автоматизация разведки Okta

Разведку удобно автоматизировать: один токен и несколько `GET`-запросов дают полную картину тенанта. Скрипт последовательно обходит `/api/v1/users` (сотрудники и их профили), `/api/v1/groups` (группы и членство), `/api/v1/apps` (приложения и их настройки), `/api/v1/authenticators` (доступные факторы), `/api/v1/policies` (политики паролей и MFA). Результат складывается в JSON. Так за десяток запросов ты получаешь карту: кто админ, какие приложения подключены и где MFA слабее всего.

## Сравнение Okta с Entra и Workspace

Три IdP похожи по сути, но различаются деталями. Okta — независимый IdP с чистым REST API и токеном SSWS. Entra ID (Microsoft) теснее связан с M365, использует OAuth-приложения и Graph API. Google Workspace опирается на OAuth-клиенты и сервисные аккаунты с domain-wide delegation. Общее: везде есть токен, везде есть приложения с секретами, везде есть админские роли. Поняв Okta, ты легко переносишь логику на двух других.

## Практический чек-лист пентеста Okta

Порядок действий. Один: подтвердить токен (`/users/me`). Два: выяснить роли и максимальные права. Три: выгрузить приложения и их секреты. Четыре: перечислить пользователей и группы. Пять: найти админские группы и проверить, можно ли в них себя добавить. Шесть: оценить политики MFA и найти пользователей без второго фактора. Семь: при необходимости — имперсонация. Восемь: зафиксировать персистентность новым токеном.

## Что дальше в дереве

Следующий урок — Microsoft 365. Там та же идея (утёкший токен открывает тенант), но добавляется почтовая специфика: правила перенаправления, eDiscovery и захват через зарегистрированное приложение. Держи в голове общую схему: найти токен IdP → понять его права → дотянуться до приложений и данных.

## Что мы теперь знаем

1. API-токен Okta наследует права владельца — админский токен равен админству.
2. OIDC-приложения хранят client_secret — это отдельные креденшелы.
3. Сброс факторов MFA и имперсонация — прямые пути к захвату.
4. Сессионный токен (`sid`) даёт доступ «как пользователь».
5. System Log фиксирует все действия — тише всего только чтение.
