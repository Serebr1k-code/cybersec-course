## Вопрос, с которого всё начинается

Ты находишь URL вида `https://abc123.lambda-url.eu-west-1.on.aws/` и отправляешь обычный GET — в ответ приходят данные без всякой авторизации. Вопрос: почему функция доступна напрямую, какие режимы авторизации бывают, что за этим стоит и как ошибка в одном флаге (`AuthType`) открывает внутренние данные и создаёт SSRF-поверхность?

## Что такое Function URL

Function URL — это прямая HTTPS-точка входа к функции, которую облако генерирует без API Gateway. Она нужна, когда не хочется поднимать шлюз: одна функция, один URL. Аналогично работают HTTP-триггеры в других облаках. Ключевой параметр — режим авторизации: `AWS_IAM` (нужна подпись SigV4) или `NONE` (доступ без авторизации). Ошибка в выборе режима делает функцию публичной.

## Сквозной пример: публичный URL

Смотрим конфигурацию и ответ:
```
$ aws lambda get-function-url-config --function-name reports
{
  "FunctionUrl": "https://abc123.lambda-url.eu-west-1.on.aws/",
  "AuthType": "NONE",
  "Cors": {"AllowOrigins": ["*"], "AllowMethods": ["*"]}
}
$ curl -s https://abc123.lambda-url.eu-west-1.on.aws/report
{"report": "...", "customer_id": "..."}
```
`AuthType: NONE` и `AllowOrigins: *` означают: любой из интернета вызывает функцию и читает ответ. Это частая находка — «мы же просто быстро протестировали».

## Режимы авторизации

`AWS_IAM` требует, чтобы вызывающий подписал запрос своим IAM-креденшелом и имел право `lambda:InvokeFunctionUrl`. `NONE` не требует ничего. Отдельно — resource-based policy функции: она может разрешать вызов конкретным принципалам или аккаунтам. Проверяй и `AuthType`, и политику: даже при `AWS_IAM` политика может разрешать `Principal: *`.

## CORS и браузерный доступ

CORS на Function URL определяет, какие источники могут вызывать функцию из браузера. `AllowOrigins: *` вместе с `NONE` означает, что любой сайт может читать ответ. Даже при `AWS_IAM` неверный CORS может позволить CSRF-подобные вызовы, если браузер прикладывает креды. Проверяй `AllowCredentials` и заголовки.

## SSRF и внутренние вызовы

Функция за URL часто делает исходящие запросы. Если URL функции доступен без авторизации, а параметры управляют исходящим запросом, получается SSRF: можно заставить функцию обратиться к внутренним сервисам, метаданным или другим функциям. В облаке это особенно опасно, потому что у функции есть роль с правами. Комбинируя открытый URL и SSRF, ты используешь роль функции как прокси.

## Прямой доступ vs шлюз

API Gateway даёт авторизаторы, throttling, WAF, валидацию. Function URL этих слоёв лишён: нет авторизатора, нет rate limiting (кроме общих квот), нет WAF. Поэтому публичная функция без шлюза — это не только открытые данные, но и возможность вызывать её сколько угодно (abuse, перебор, криптоджекинг при дорогой работе). Отсутствие слоёв — часть поверхности.

## Перечисление Function URL

URL-ы предсказуемы по формату (`<id>.lambda-url.<region>.on.aws`), но `id` — случайный. Перечислять их напрямую сложно, но их можно найти в других местах: в JS-коде фронтенда, в логах, в конфигах, в описаниях. Часто URL функции «протекает» в клиентский код или в документацию. Проверяй также API Gateway и CloudFront, которые могут проксировать функцию.

## Типовые мисконфиги

| Мисконфиг | Последствие | Как искать |
|---|---|---|
| `AuthType: NONE` | публичный доступ | get-function-url-config |
| Политика с `Principal: *` | доступ всех | get-policy |
| `AllowOrigins: *` + credentials | CSRF/чтение | Cors |
| SSRF в параметрах | доступ к внутренним | код функции |
| Нет throttling | abuse/перебор | URL напрямую |
| URL в клиентском коде | раскрытие точки входа | JS/логи |

## Полный прогон: от URL к данным

Шаги. Первый: найти Function URL (код фронта, логи, конфиги). Второй: проверить доступ без авторизации (`curl`). Третий: прочитать конфиг (`AuthType`, `Cors`, policy). Четвёртый: перебрать эндпоинты/параметры функции. Пятый: при SSRF — обратиться к внутренним сервисам. Шестой: использовать роль функции для доступа к её ресурсам. Седьмой: зафиксировать и учесть логи.

## Инструменты и команды

Полезны: `curl -i` (проверка доступа), `aws lambda get-function-url-config`, `aws lambda get-policy`, `aws lambda list-functions`. Для SSRF — `curl` с параметрами, указывающими на внутренние адреса. Для поиска URL — grep по репозиториям, JS-бандлам, логам.

## OPSEC и детект

Вызовы функции логируются в CloudWatch; аномальный объём и необычные параметры заметны. Обращения функции к внутренним адресам видны в VPC Flow Logs и в логах. Тихий сценарий — один запрос к нужному эндпоинту, а не массовый перебор. Помни: публичный URL видят все, поэтому защита может заметить сканирование.

## Частые вопросы

Всегда ли Function URL публичен? Нет, при `AWS_IAM` нужна подпись. Опасен ли CORS `*`? Да, вместе с отсутствием авторизации. Можно ли обойти `AWS_IAM`? Только если политика разрешает `*`. Что даёт SSRF? Доступ к внутренним сервисам через роль функции. Как найти URL? В клиентском коде и логах.

## Что не сработает

При `AuthType: AWS_IAM` и строгой политике без кредов не вызвать. Если функция не делает исходящих запросов, SSRF не получится. WAF/шлюз перед функцией может блокировать перебор. И если роль функции минимальна, доступ к её ресурсам ограничен.

## Разбор кейса: URL в JS-бандле

История из практики. Фронтенд вызывал Lambda Function URL напрямую, и адрес был зашит в JavaScript-бандл. Плюс конфиг был `AuthType: NONE`. Любой мог скачать бандл, извлечь URL и вызывать функцию без авторизации. Функция возвращала отчёты с персональными данными и умела принимать параметр `url` для выгрузки — то есть давала SSRF. Цепочка: публичный бандл → URL функции → чтение данных → SSRF во внутренние сервисы. Типичная ошибка «быстро выставили функцию наружу».

## API Gateway vs Function URL

API Gateway добавляет авторизаторы (Lambda, Cognito, IAM), throttling, валидацию запросов, WAF, стадии и канареечные релизы. Function URL всего этого не имеет. Поэтому при пентесте важно понять, что перед функцией: если есть шлюз, атакуй его конфигурацию (авторизаторы, ресурсные политики); если нет — саму функцию напрямую. Часто встречается смешанная схема: шлюз для одних путей и прямой URL для других, и именно прямой URL оказывается незащищённым.

## Защита Function URL

Меры: использовать `AWS_IAM` там, где нет публичной необходимости; строгая resource-based policy без `Principal: *`; ограниченный CORS без `*` и без credentials; авторизация на уровне приложения для публичных функций; throttling и WAF через шлюз; логирование и алерты на аномальные вызовы. Плюс не встраивать URL в клиентский код без необходимости. Каждая мера закрывает один из векторов: публичный доступ, чтение данных, abuse.

## Частые заблуждения

Первое: «URL случайный, значит защищён». Случайность не заменяет авторизацию. Второе: «функция просто возвращает данные». Она ещё и делает исходящие запросы. Третье: «CORS защищает». CORS — браузерное ограничение, не авторизация. Четвёртое: «без шлюза дешевле и не хуже». Без шлюза нет защитных слоёв. Пятое: «`AWS_IAM` всегда включён по умолчанию». Нет, `NONE` — частый выбор для «теста».

## Инвентаризация эндпоинтов

Ищи Function URL в клиентском коде, JS-бандлах, логах, конфигах и документации. Формат предсказуем (`<id>.lambda-url.<region>.on.aws`), но `id` случаен, поэтому перечисление напрямую непрактично. Проверяй также API Gateway и CloudFront, которые могут проксировать функцию: их домены проще найти, а за ними — та же функция. Собрав список эндпоинтов, проверь каждый на авторизацию и лимиты, затем — на параметры, управляющие исходящими запросами.

## Abuse и стоимость

Открытая функция без throttling позволяет не только читать данные, но и злоупотреблять: перебор, дорогие операции, привязка к внешним сервисам за счёт владельца. Если функция вызывает платные API или GPU, abuse становится финансовой атакой. Проверь, что функция делает внутри: часто это прокси к базе или внешнему сервису, и её цена на вызов высока. Учитывай квоты облака — массовый abuse может их исчерпать.

## Итоговая цепочка атаки

Атакующий находит Function URL (в бандле/логах), проверяет `AuthType: NONE` и вызывает функцию без авторизации. Он перебирает эндпоинты и параметры, читает данные и при SSRF обращается к внутренним сервисам. Через роль функции он получает доступ к её ресурсам. Цепочка держится на открытом режиме доступа и сетевых возможностях функции. Включи `AWS_IAM` и ограничь egress — и она рвётся.

## Поиск URL по формату

Function URL имеют формат `<url-id>.lambda-url.<region>.on.aws`. `url-id` — случайный, но URL часто попадают в клиентские приложения, документацию, скриншоты, логи и CI-артефакты. Ищи по строке `lambda-url` в репозиториях, бандлах и индексах. Также проверяй CloudFront-дистрибуции и API Gateway: их домены проще найти, а за ними может стоять та же функция. Найденный URL — вход, дальше проверяй режим доступа.

## Этика и границы

Публичная функция без авторизации — это открытые данные и потенциальный abuse. При пентесте ограничься доказательством доступа (один запрос, возвращающий безобидный результат), а не выгрузкой персональных данных. Не запускай перебор, который нагружает функцию и внешние сервисы за ней. Если функция делает дорогие операции, минимизируй вызовы. Зафиксируй находку и передай владельцу, не эксплуатируя её дальше необходимого.

## Что мы теперь знаем

1. Function URL — прямой доступ к функции без шлюза.
2. `AuthType: NONE` делает функцию публичной; `AWS_IAM` требует подписи.
3. CORS `*` с отсутствием авторизации открывает данные.
4. SSRF в функции использует её роль как прокси.
5. Без шлюза нет throttling/WAF — функция уязвима к abuse.
