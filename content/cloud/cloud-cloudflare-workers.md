## Вопрос, с которого всё начинается

Ты смотришь на edge-приложение: запрос обслуживается кодом, который исполняется в дата-центре Cloudflare рядом с пользователем. Где-то в этом коде лежит токен к внутренней базе. Вопрос: как edge-функции хранят секреты, чем секрет отличается от обычной переменной и какие права даёт утёкший токен развёртывания? Ответ начнём с артефакта — конфигурации воркера.

## Что такое edge и Cloudflare Workers

Edge — это исполнение кода на границе сети, ближе к пользователю, чем классический сервер. Cloudflare Workers — платформа таких функций: ты пишешь JS/TS, деплоишь, и код отвечает на HTTP-запросы в сотнях точек присутствия. Вокруг воркеров есть хранилища: KV (key-value), R2 (S3-совместимое объектное хранилище), D1 (SQLite), Durable Objects (состояние). Для атакующего edge интересен двумя вещами: секретами в коде и доступом к внутренним сервисам.

## Сквозной пример: конфиг воркера

Развёртыванием управляет `wrangler.toml`:
```
$ cat wrangler.toml
name = "api-gateway"
main = "src/index.js"
compatibility_date = "2024-01-01"
[vars]
PUBLIC_HOST = "api.example.com"
[kv_namespaces]
binding = "CACHE"
id = "abcd1234"
[r2_buckets]
binding = "UPLOADS"
bucket_name = "user-uploads"
```
Читаем: воркер называется `api-gateway`, к нему привязаны KV-пространство `CACHE` и R2-бакет `user-uploads`. В `[vars]` лежат НЕ секреты — эти значения видны в конфиге. Настоящие секреты задаются отдельно, через `wrangler secret put`.

## Воркер-код: где живут секреты

Код получает секреты через объект `env`. Пример обработчика:
```
export default {
  async fetch(request, env) {
    const key = env.ADMIN_TOKEN
    const url = new URL(request.url)
    if (url.pathname === "/fetch")
      return fetch(url.searchParams.get("u"))
    return new Response("ok")
  }
}
```
Здесь `env.ADMIN_TOKEN` — секрет, а обработчик `/fetch` принимает URL из параметра и делает запрос. Это и есть SSRF: если не фильтровать `u`, воркер сходит куда угодно, включая внутренние адреса Cloudflare и адреса, доступные только из edge-сети.

## Vars против Secrets

`[vars]` в `wrangler.toml` — открытые переменные: они попадают в конфиг и видны любому с доступом к дашборду. Secrets задаются командой `wrangler secret put NAME` и хранятся зашифрованными; в код приходят тем же `env.NAME`. Классическая ошибка разработчиков — положить токен в `[vars]`, потому что «так быстрее». Тогда утечка конфига = утечка секрета. При разборе всегда проверяй, нет ли в `[vars]` строк, похожих на ключи.

## Биндинги: KV, R2, D1, Durable Objects

Биндинг — это привязка хранилища к воркеру под именем. KV хранит пары ключ-значение (кэш, сессии, флаги). R2 — объекты (файлы, бэкапы). D1 — реляционная SQLite-база. Durable Objects — объекты с состоянием для координации. Из кода они доступны через `env.CACHE.get(...)`, `env.UPLOADS.get(...)`, `env.DB.prepare(...)`. Если воркер читает данные из R2 или D1 без проверки прав, уязвимость в воркере открывает доступ к данным напрямую.

## Роуты и workers.dev

Воркер отвечает на маршруты: либо на своём `*.workers.dev` поддомене, либо на кастомном домене через Routes. Публичный `workers.dev`-адрес часто забывают — он остаётся доступным даже когда кастомный домен защищён WAF. Проверка: перебрать `<name>.<account>.workers.dev`. Если воркер не проверяет хост и путь, его можно вызвать напрямую в обход основного фронта.

## SSRF из edge

Edge-воркер умеет делать `fetch` к произвольным адресам. Это удобно для прокси и интеграций, но опасно: `fetch` не ограничен внешней сетью. Если параметр URL контролируется, атакующий может обратиться к внутренним сервисам, метаданным облака (если воркер интегрирован с другим провайдером) или локальным адресам. Защита — allowlist хостов, запрет приватных диапазонов, проверка протокола.

## Утечка секретов

Секреты утекают тремя путями. Первый: через API Cloudflare, если утёк API-токен с правом `Workers Scripts:Edit` — можно выкачать скрипт и его биндинги. Второй: через дашборд при слабом пароле и отсутствии MFA. Третий: через сам код, если он логирует `env` или возвращает ошибку с содержимым переменных. API-токен Cloudflare (вида длинной строки) проверяется запросом к `/user/tokens/verify`.

## Типовые мисконфиги Workers

| Мисконфиг | Последствие | Как искать |
|---|---|---|
| Секрет в `[vars]` | утечка через конфиг | разбор wrangler.toml |
| Публичный workers.dev | обход WAF | перебор поддоменов |
| SSRF в `fetch` | доступ к внутренним сервисам | разбор кода |
| API-токен с Edit | выкачка скриптов | verify токена |
| Логирование env | секреты в логах | разбор кода |
| Открытый R2-бакет | утечка объектов | публичный URL |

## Полный прогон: от конфига к данным

Шаги. Первый: найти `wrangler.toml` и исходники воркера (часто в репозитории). Второй: проверить `[vars]` на секреты и понять биндинги. Третий: если есть API-токен Cloudflare — подтвердить его и выкачать скрипты и секреты. Четвёртый: проверить `workers.dev`-адрес и SSRF-обработчики. Пятый: если есть R2-биндинг с открытым доступом — выкачать объекты.

## Инструменты и команды

Основной инструмент — `wrangler`: `wrangler whoami` (аккаунт), `wrangler secret list` (имена секретов), `wrangler deployments list`, `wrangler tail` (живые логи). Через REST: `GET /accounts/{id}/workers/scripts` (список скриптов), `GET /accounts/{id}/r2/buckets`. Для проверки API-токена: `GET /user/tokens/verify`. Публичный `workers.dev` проверяется обычным `curl`.

## OPSEC и детект

Cloudflare Audit Logs фиксируют изменения воркеров, секретов и биндингов. Чтение данных из R2 и KV не всегда логируется, но изменения — да. Поэтому тихий сценарий: только чтение (`GET`), без деплоя и правок секретов. `wrangler tail` оставляет след в логах аккаунта. Если работаешь через API-токен, помни: он привязан к аккаунту и виден в списке токенов — владелец заметит незнакомый токен.

## Разведка без ключа

Даже без токена edge-приложение частично прозрачно. Публичный `workers.dev`-поддомен выдаёт факт использования Workers. Заголовки ответа (`cf-ray`, `server: cloudflare`) подтверждают Cloudflare. Ошибки воркера иногда раскрывают имена биндингов и структуру кода. Проверка пути `/fetch?u=` может показать наличие SSRF-обработчика ещё до получения секретов.

## Что не сработает

Секрет, заданный через `secret put`, не виден в `wrangler.toml` — его не «вытащить» из конфига. API-токен с правом только `Read` не позволит выкачать скрипт с секретами. `fetch` к приватным адресам может блокироваться самой платформой. И отозванный токен вернёт `401` на `/user/tokens/verify`.

## Разбор кейса: API-токен Cloudflare в CI

История из практики. В CI-переменных лежит `CLOUDFLARE_API_TOKEN`, которым пайплайн деплоит воркеры. Токен имеет права `Workers Scripts:Edit` и `Account Settings:Read`. Утёкший токен позволяет выкачать все скрипты аккаунта вместе с их секретами: команда `GET /accounts/{id}/workers/scripts/{name}` возвращает код, а биндинги и секреты читаются отдельными вызовами. Дальше атакующий либо ищет секреты внутри скриптов, либо деплоит свой воркер, который читает KV и R2. Это полный захват edge-плоскости через один токен CI.

## Частые вопросы

Видны ли секреты в дашборде? Только их имена, значения скрыты — но API-токен с нужным правом их вернёт. Можно ли читать KV без деплоя? Да, если есть скрипт с биндингом и возможность его вызвать. Что если `workers.dev` отключён? Тогда ищи кастомный роут и проверяй его напрямую. Опасен ли read-only API-токен? Он раскрывает конфигурацию и имена, но не выкачивает секреты. Что делать, если токен отозван? Искать другой — в логах CI, в `.dev.vars`, в переменных пайплайна.

## Сравнение edge-платформ

| Платформа | Модель | Секреты | Хранилища |
|---|---|---|---|
| Cloudflare Workers | изоляты V8 | secret put | KV, R2, D1 |
| AWS Lambda@Edge | контейнеры | env/SSM | S3, DynamoDB |
| Deno Deploy | изоляты V8 | env | KV |
Общая идея: код исполняется на границе, секреты передаются как переменные окружения, данные лежат в привязанных хранилищах. Отличаются именами команд и API, но модель атаки одна: утёкший токен деплоя = доступ к коду и секретам.

## Практический чек-лист пентеста Workers

Порядок действий. Один: найти `wrangler.toml` и исходники. Два: проверить `[vars]` на секреты. Три: подтвердить API-токен через `/user/tokens/verify` и узнать его права. Четыре: выкачать скрипты и секреты. Пять: проверить публичный `workers.dev` и SSRF-обработчики. Шесть: прочитать KV/R2/D1 через биндинги. Семь: зафиксировать результат, не деплоя своих воркеров без необходимости.

## Что дальше в дереве

В следующем уроке мы спустимся с edge-кода к базе, к которой он ходит, — serverless-базам Supabase, PlanetScale и Neon. Там ты увидишь вторую половину этой истории: даже идеально закрытый воркер бесполезен, если таблица отдаёт данные по публичному ключу. Держи в голове связку: edge-код + хранилище = одно приложение, и защищать их надо вместе.

## Что мы теперь знаем

1. `[vars]` — открытые значения, secrets — зашифрованные; их путают чаще всего.
2. Биндинги KV/R2/D1 открывают данные напрямую из кода.
3. Публичный `workers.dev` обходит защиту кастомного домена.
4. `fetch` из воркера — источник SSRF к внутренним сервисам.
5. API-токен Cloudflare с правом Edit позволяет выкачать скрипты и секреты.
