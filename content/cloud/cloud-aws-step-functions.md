## Вопрос, с которого всё начинается

У тебя есть право `states:StartExecution` на state machine, но сама машина тебе не принадлежит. Запускаешь её — и в логах видно, что она создала IAM-пользователя с ключом. Вопрос: как запуск workflow от твоего имени привёл к созданию пользователя, и куда делся ключ? Ответ — в определении машины и в роли, которой она исполняется.

## Что такое Step Functions

Step Functions — оркестратор рабочих процессов (workflows). Ты описываешь state machine (машину состояний): последовательность шагов (states), переходы, ветвления, повторы. Каждый шаг вызывает сервис: Lambda, ECS-задачу, DynamoDB, другой Step Functions. Машина исполняется от имени execution role — и все шаги действуют с её правами.

## Сквозной пример: определение машины

Смотрим определение:
```
$ aws stepfunctions describe-state-machine --state-machine-arn arn:...:stateMachine:provision
{
  "roleArn": "arn:aws:iam::123456789012:role/sfn-admin",
  "definition": {
    "StartAt": "CreateUser",
    "States": {
      "CreateUser": {"Type": "Task", "Resource": "arn:aws:states:::aws-sdk:iam:createUser",
         "Parameters": {"UserName.$": "$.username"}, "Next": "Done"},
      "Done": {"Type": "Succeed"}
    }
  }
}
```
Машина исполняется от имени `sfn-admin` и на шаге `CreateUser` вызывает `iam:createUser` с именем из входных данных (`$.username`). Значит, любой, кто может запустить эту машину, создаёт IAM-пользователей с правами `sfn-admin` — даже если сам такой роли не имеет. Это и есть эскалация через workflow.

## PassRole как двигатель эскалации

`iam:PassRole` позволяет передать роль сервису. В Step Functions роль задаётся при создании машины (`roleArn`) и при некоторых вызовах. Если у тебя есть `states:CreateStateMachine` + `iam:PassRole`, ты создаёшь машину с мощной ролью и исполняешь через неё любые действия. Даже без Create — если `StartExecution` доступен на существующую машину с широкой ролью, этого достаточно.

## Входные данные и инъекция

Вход (input) машины — произвольный JSON. Определение подставляет поля (`$.username`) в параметры шагов. Если вход не валидируется, ты управляешь тем, что делают шаги: имя пользователя, содержимое сообщения, путь к объекту. Это тот же класс, что инъекция событий: данные становятся инструкциями.

## Вложенные и Express-машины

Step Functions бывают Standard (долгие, с историей) и Express (короткие, высоконагруженные). Вложенные машины (`states:startExecution.sync`) позволяют одной машине запускать другую — цепочка ролей. Если верхняя машина может запустить нижнюю с другой ролью, эскалация идёт по цепочке. Проверяй, какие машины запускают какие и с какими ролями.

## Типовые мисконфиги Step Functions

| Мисконфиг | Последствие | Как искать |
|---|---|---|
| Машина с широкой ролью и открытым StartExecution | эскалация | roleArn + политика |
| `iam:PassRole` без ограничения роли | создание машины с админ-ролью | IAM-политика |
| Вход без валидации | инъекция в шаги | определение |
| Вложенные машины с разными ролями | цепочка эскалации | определения |
| Секреты в определении | утечка | definition |
| Логи с входом/выходом | раскрытие данных | logging config |

## Полный прогон: от StartExecution к правам

Шаги. Первый: найти state machines (`aws stepfunctions list-state-machines`). Второй: прочитать определения и роли. Третий: найти машину с широкой ролью и доступным запуском. Четвёртый: понять, какие входные поля управляют шагами. Пятый: запустить (`start-execution`) с подконтрольным входом. Шестой: забрать результат (созданный пользователь, ключ, данные). Седьмой: зафиксировать доступ.

## Инструменты и команды

Полезны: `aws stepfunctions list-state-machines/describe-state-machine/start-execution/describe-execution`, `aws iam list-roles/get-role`. Для чтения истории — `get-execution-history`. Для создания машины с чужой ролью — `create-state-machine` (нужен PassRole). Часто достаточно `start-execution` и просмотра истории.

## OPSEC и детект

StartExecution логируется в CloudTrail; необычный вход (например, `username: attacker`) заметен. Машина создаёт ресурсы — след остаётся в IAM/логах. История исполнения хранит вход/выход. Тихий сценарий: запуск с минимальным, «легитимным» входом. Помни: если логирование включено, твой вход виден в execution history.

## Разведка без доступа

Без прав видно: имена машин в коде/репозиториях, ARNs в логах, описания в документации. Определения часто лежат в IaC-репозиториях. По ним восстанавливается, какие роли и шаги используются.

## Частые вопросы

Нужен ли PassRole для StartExecution? Нет, только для создания/обновления машины. Опасна ли машина без широкой роли? Меньше. Можно ли передать вход? Да, это ключ к управлению. Что если вход валидируется? Тогда инъекция не пройдёт. Помогает ли аудит? Да, CloudTrail видит запуски.

## Что не сработает

Машина с узкой ролью (только чтение) не даст эскалации. Если StartExecution ограничен конкретным principal, запуск не пройдёт. Валидация входа закрывает инъекцию. И если PassRole ограничен списком ролей, создать машину с админ-ролью нельзя.

## Сценарий: workflow создаёт админа

Цепочка. У нас есть `states:StartExecution` на машину `provision` с ролью `sfn-admin` (создаёт пользователей). Запускаем с входом `{"username":"backup-svc"}` — машина создаёт IAM-пользователя. Далее (если в определении есть шаг createAccessKey) получаем ключ. Теперь у нас постоянный доступ, не зависящий от исходных прав. Фиксируем: эскалация через workflow с широкой ролью.

## Практический чек-лист пентеста Step Functions

Порядок. Один: перечислить машины. Два: прочитать определения и роли. Три: найти широкую роль + доступный запуск. Четыре: понять управляющие входные поля. Пять: запустить с подконтрольным входом. Шесть: забрать результат. Семь: зафиксировать персистентность. Восемь: оценить логи CloudTrail.

## Step Functions: состояния и роли

Step Functions — оркестратор (state machine): последовательность состояний (Task, Choice, Parallel, Map, Wait), каждое Task может вызывать Lambda, ECS, DynamoDB и т.д. Определение — Amazon States Language (JSON). Поверхность: роль исполнения (execution role) с правами на все задачи, входные данные, доступ к `StartExecution`.

```bash
aws stepfunctions list-state-machines
aws stepfunctions describe-state-machine --state-machine-arn <arn>
```

Ключевой риск: если кто-то может `StartExecution` (или есть public API), он может запустить цепочку, которая выполнит действия с ролью state machine.

## Практика: инъекция через input

Определение state machine принимает JSON-вход. Если задача подставляет вход в команду (например, `aws:executeScript` или Lambda), возможна инъекция. Дополнительно проверь роль исполнения: если она широкая, запуск цепочки даёт её права.

```bash
aws stepfunctions start-execution --state-machine-arn <arn> \
  --input '{"key":"value"}'
```

Так «безобидный» оркестратор становится путём эскалации: input → задача → роль → ресурсы. Проверь также Map-состояния (массовое выполнение) и ошибки/retry.

## Защита

Меры: минимальная роль исполнения, валидация входа (не подставлять вход в команды напрямую), ограничение `StartExecution`, логирование (CloudWatch/CloudTrail), мониторинг. Для пентеста — чтение определений и оценка путей, без запуска в продакшне.

## Расширенный разбор: роли и цели

Роль исполнения state machine определяет, что может делать цепочка. Проверь её политики: если она даёт `s3:*`, `lambda:Invoke`, `iam:*` — запуск цепочки равен этим правам. Также проверь, кто может `StartExecution` (политики, API Gateway, EventBridge) — это точка входа.

```bash
aws stepfunctions describe-state-machine --state-machine-arn <arn> | jq .roleArn
aws iam list-attached-role-policies --role-name <role>
```

Собери цепочку: кто → StartExecution → роль → действия. Если точка входа доступна низкопривилегированному пользователю, это путь эскалации.

## Расширенный разбор: инъекция в задачи

Задачи могут подставлять вход в команды. Например, `aws:executeScript` или Lambda, которая строит SQL/shell из input. Если вход не валидируется, возможна инъекция. Также `Map`-состояние может массово обрабатывать вход, усиливая эффект.

```json
{"Type":"Task","Resource":"arn:aws:states:::lambda:invoke",
 "Parameters":{"Payload.$":"$"}}
```

Для пентеста: прочитай определение, найди места, где вход идёт в команду, и оцени возможность инъекции. Не запускай в продакшне.

## Защита

Меры: минимальная роль исполнения, валидация входа, ограничение StartExecution, логирование, мониторинг. Для пентеста — чтение определений и оценка путей.

## Разбор кейса: цепочка как эскалация

История из практики. State machine имела роль с `lambda:Invoke` и `s3:*`, а `StartExecution` был доступен через API Gateway без строгой авторизации. Атакующий запустил цепочку с входом, который вызвал Lambda, читающую бакет, и получил данные. Эскалация произошла через оркестратор, а не через прямой доступ. Вывод: точки входа в цепочки надо защищать так же строго, как API.

## Чек-лист аудита Step Functions

1. Список state machines и их роли.
2. Политики ролей (что может цепочка).
3. Точки входа (`StartExecution`).
4. Валидация входа (инъекции).
5. Логирование и мониторинг.

Инструменты: `aws stepfunctions`, `aws iam`. Только чтение.

## Вывод по Step Functions

State machine — оркестратор с ролью, часто широкой. Точка входа (`StartExecution`) — путь эскалации, если доступна низкопривилегированному пользователю. Проверь роль, точки входа и валидацию входа. Защита: минимальная роль, ограничение входа, логирование.

## Что мы теперь знаем

1. State machine исполняется от имени execution role.
2. PassRole + CreateStateMachine позволяют создать машину с мощной ролью.
3. StartExecution на существующую машину уже даёт её права.
4. Вход workflow — управляемые данные, если нет валидации.
5. Вложенные машины образуют цепочки ролей.

Для защищающейся стороны важно не только ограничить роль, но и закрыть точку входа: если StartExecution доступен широко, оркестратор становится публичным API с правами роли.

Также проверь, не передаётся ли во вход чувствительная информация: если StartExecution логируется, входные данные могут утекать в CloudWatch.
