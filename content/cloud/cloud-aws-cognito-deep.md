## Вопрос, с которого всё начинается

Ты нашёл в приложении `identityPoolId` и `userPoolId`. Вопрос: какие IAM-роли выдаёт identity pool, можно ли получить роль без регистрации (unauthenticated), что она позволяет, и как из «клиентское приложение» получить креды AWS. Начнём с того, что Cognito состоит из двух частей: user pool (аутентификация пользователей) и identity pool (обмен токена на IAM-креды), и именно вторая часто раздаёт роли слишком широко.

## Что такое Cognito

Cognito — управляемый identity-сервис AWS. User pool хранит пользователей, умеет регистрацию, вход, MFA, федерацию. Identity pool обменивает токен (из user pool или внешнего IdP) на временные AWS-креды через STS, сопоставляя пользователя с IAM-ролью. Роли бывают для authenticated и unauthenticated (гостей). Если приложение использует identity pool, то клиент получает реальные AWS-креды, и их широта зависит от роли.

## Сквозной пример: identity pool

Смотрим конфигурацию:
```
$ aws cognito-identity get-identity-pool-roles --identity-pool-id eu-west-1:EXAMPLE-pool-id
{ "IdentityPoolId": "eu-west-1:EXAMPLE-pool-id",
  "Roles": { "unauthenticated": "arn:aws:iam::111111111111:role/Cognito_guest",
             "authenticated": "arn:aws:iam::111111111111:role/Cognito_auth" } }
```
Identity pool выдаёт две роли: для гостей и для аутентифицированных. Даже unauthenticated роль — это настоящие AWS-креды. Дальше проверяем, что позволяет `Cognito_guest`: часто это доступ к S3 или другим сервисам.

## User pool и identity pool

User pool — это база пользователей и аутентификация: ты получаешь ID/access/refresh токены. Identity pool — это обмен токена на креды AWS. Путаница между ними — источник ошибок: разработчики думают, что «Cognito = только вход», и не замечают, что identity pool раздаёт IAM-роли. Атакующему интересна вторая: если роль широкая, любой, кто может получить токен (в том числе гость или новый self-signup пользователь), получает креды.

## Маппинг ролей по группам и claim-ам

Identity pool может выбирать роль по claim из токена: например, по группе (`cognito:groups`) или по атрибуту. Ошибка конфигурации — правило, которое выбирает широкую роль по подделываемому или легко получаемому claim-у. Если пользователь может сам задать атрибут (self-signup) и этот атрибут влияет на выбор роли, он может получить роль выше своей. Проверяй правила выбора роли: какой claim используется и можно ли его контролировать.

## Кража токенов

Токены Cognito хранятся в клиенте (localStorage, cookies) и утекают через XSS, небезопасное хранение или перехват. Access/ID токен даёт доступ к API, refresh токен — к обновлению сессии. Если у приложения есть identity pool, украденный токен можно обменять на AWS-креды. Плюс refresh токены долгоживущие, поэтому их кража даётпостоянный доступ. Проверяй, где хранятся токены и как долго живут.

## Квоты, self-signup и abuse

Cognito имеет квоты на операции, и self-signup может быть открыт. Открытая регистрация позволяет создать пользователя и получить токен, а через identity pool — роль. Плюс существуют операции, доступные по client id, которые можно злоупотребить (перечисление пользователей, сброс пароля). Проверяй настройки user pool: открыт ли self-signup, какие операции доступны клиенту, есть ли защита от перебора.

## Типовые мисконфиги

| Мисконфиг | Последствие | Как искать |
|---|---|---|
| Широкая unauthenticated роль | креды гостю | identity pool roles |
| Маппинг по подделываемому claim | роль выше своей | rules mapping |
| Открытый self-signup | получение токена | user pool settings |
| Токены в localStorage | кража через XSS | клиентский код |
| Нет защиты от перебора | брутфорс | advanced security |
| Долгий refresh токен |постоянный доступ | token validity |

## Полный прогон: от pool id к кредам

Шаги. Первый: найти identityPoolId и userPoolId в клиенте. Второй: запросить роли identity pool (`get-identity-pool-roles`). Третий: получить identity id (гостю — без токена). Четвёртый: обменять на AWS-креды (`get-credentials-for-identity`). Пятый: определить, что позволяет роль (`sts get-caller-identity`, затем — разведка). Шестой: при необходимости зарегистрировать пользователя и получить более широкую роль. Седьмой: учесть CloudTrail.

## Инструменты и команды

Полезны: `aws cognito-identity get-identity-pool-roles`, `get-id`, `get-credentials-for-identity`, `aws cognito-idp describe-user-pool`, `list-user-pools`. Для клиента — анализ JS на identityPoolId. Для кредов — `aws sts get-caller-identity`, затем `aws iam`/`s3` для разведки. Для токенов — анализ хранилища браузера.

## OPSEC и детект

Получение кредов через Cognito логируется в CloudTrail (GetCredentialsForIdentity, AssumeRoleWithWebIdentity). Использование роли из неожиданного места заметно. Открытый self-signup и массовая регистрация видны в логах user pool. Тихий сценарий — использовать существующую сессию и одну роль, без создания множества пользователей.

## Частые вопросы

Нужен ли аккаунт? Для unauthenticated роли — нет. Даёт ли Cognito креды AWS? Да, через identity pool. Что если identity pool не используется? Тогда только токены user pool. Даёт ли украденный refresh токенпостоянный доступ? Да, пока не истёк/не отозван. Оставляет ли след? Да, CloudTrail.

## Что не сработает

Без identity pool креды AWS не выдаются. Строгая unauthenticated роль ограничит доступ. Маппинг по неподделываемому claim не даст повысить роль. И отозванный refresh токен не сработает.

## Разбор кейса: гостевая роль с S3

История из практики. В мобильном приложении был identity pool с ролью для unauthenticated пользователей, которой по ошибке дали `s3:GetObject` на весь бакет. Атакующий достал identityPoolId из APK, запросил гостевые креды и скачал приватные файлы. Урок: гостевая роль — это настоящие AWS-креды; её права нужно ограничивать так же строго, как права пользователя.

## Что мы теперь знаем

1. Cognito = user pool (аутентификация) + identity pool (обмен токена на IAM-креды).
2. Identity pool выдаёт роли authenticated и unauthenticated; гость получает креды.
3. Маппинг по подделываемому claim может повысить роль.
4. Токены в клиенте утекают; refresh токен даётпостоянный доступ.
5. Открытый self-signup и слабая гостевая роль — частые точки входа.

## Federation и внешние IdP

Cognito умеет федерацию: пользователь входит через внешний IdP (Google, Facebook, SAML, OIDC), а Cognito выдаёт свои токены. Для identity pool это значит, что креды AWS можно получить и через внешний аккаунт. Если федерация настроена неаккуратно (доверие к непроверенному issuer, приём токена без проверки аудитории), атакующий может подделать вход и получить роль. Проверяй настройки федерации: какие IdP, какие условия приёма токенов, какой claim используется для маппинга.

## Перечисление и abuse user pool

User pool предоставляет операции по client id, которые можно злоупотребить: регистрация, сброс пароля, подтверждение, иногда перечисление пользователей. Если нет защиты от перебора (advanced security), пароль можно подбирать. Если self-signup открыт, можно завести пользователя и получить токен, а через identity pool — креды. Проверяй, какие операции доступны клиенту и есть ли ограничения. Часто client id и client secret (или его отсутствие) — это ключ к abuse.

## Итог по Cognito

Cognito — это две разные вещи: аутентификация (user pool) и выдача IAM-кредов (identity pool). Атака обычно нацелена на вторую: найти identityPoolId, запросить креды (гостю — без входа), определить роль и её права. Затем — при возможности — зарегистрировать пользователя и получить роль шире. Ключевые мисконфиги: широкая гостевая роль, маппинг по подделываемому claim, открытый self-signup и токены, которые легко украсть из клиента.

## Практический чек-лист по Cognito

Начни с клиента: найди identityPoolId, userPoolId, client id. Проверь identity pool: какие роли выдаются для authenticated и unauthenticated. Определи права этих ролей. Попробуй получить гостевые креды без входа и оцени, что они позволяют. Затем посмотри user pool: открыт ли self-signup, есть ли advanced security, какие операции доступны клиенту. Проверь маппинг ролей: по какому claim выбирается роль и можно ли его контролировать. И оцени, как хранятся и как долго живут токены. Этот проход отвечает на главный вопрос: можно ли получить IAM-роль и насколько она широка.

## Чего ожидать на практике

Самая частая находка — гостевая роль с доступом к S3 или другим сервисам, потому что её настраивали «чтобы гости смотрели картинки» и забыли ограничить. Вторая — маппинг роли по атрибуту, который пользователь задаёт сам при регистрации. Третья — открытый self-signup и слабая защита от перебора. Поэтому в первую очередь проверяй identity pool и права гостевой роли, а уже потом возись с токенами и федерацией.

## Отличие от IAM-пользователя

Ключевое отличие Cognito-кредов от обычного IAM-пользователя в том, что они временные и выдаются по identity. Это значит, что в CloudTrail видно не «пользователь X», а роль и identity id, что затрудняет атрибуцию. Плюс роль может быть одна на всех гостей, поэтому по логам трудно понять, кто именно действовал. Для защитной стороны это повод ограничивать гостевые роли жёстко, а для атакующего — повод использовать гостевой путь, где след размыт. Но помни: сам факт получения кредов логируется, поэтому не стоит считать этот путь полностью невидимым.
