## Вопрос, с которого всё начинается

У компании есть сайт, отдаваемый через CloudFront, а бакет S3 «спрятан» за дистрибуцией. Кажется, что бакет недоступен напрямую. Но ты находишь его имя в клиентском JS, пробуешь `curl https://bucket.s3.amazonaws.com/file` — и получаешь файл. Вопрос: зачем вообще CloudFront, если origin открыт, и что ещё можно вытащить через ошибки edge-конфигурации?

## Что такое CloudFront

CloudFront — это CDN (content delivery network): сеть edge-серверов по всему миру, которая кэширует и раздаёт контент ближе к пользователю. Дистрибуция (distribution) описывает, откуда брать контент (origin) и по каким правилам его отдавать (behaviors). Origin — это S3-бакет, ALB, API Gateway или произвольный HTTP-хост. CloudFront получает запрос, при промахе кэша идёт к origin, забирает ответ и кэширует его.

## Сквозной пример: конфиг дистрибуции

Смотрим конфигурацию дистрибуции через CLI:
```
$ aws cloudfront get-distribution-config --id E1234EXAMPLE
{
  "Origins": {"Items": [{
     "DomainName": "acme-assets.s3.amazonaws.com",
     "S3OriginConfig": {"OriginAccessIdentity": ""}
  }]},
  "DefaultCacheBehavior": {"ViewerProtocolPolicy": "allow-all"}
}
```
Поле `OriginAccessIdentity` пустое. Это значит, что дистрибуция НЕ использует OAI — то есть ходит к бакету как обычный анонимный клиент. Если политика бакета при этом публичная, origin доступен напрямую, и весь смысл «спрятать бакет» потерян.

## Origin access: OAI и OAC

OAI (Origin Access Identity) — устаревший механизм: специальная идентичность CloudFront, которой в политике бакета дают `s3:GetObject`. OAC (Origin Access Control) — современная замена: подписывает запросы к S3 через SigV4 и работает с KMS-шифрованием. Разница практическая: с OAI/OAC политика бакета разрешает чтение только «этой дистрибуции», а прямой анонимный доступ запрещён. Если в конфиге origin access не настроен, проверь политику бакета — она почти наверняка разрешает больше, чем нужно.

## Origin-экспозиция

CloudFront не «прячет» origin сам по себе. Если бакет публичный или ALB открыт в интернет, атакующий бьёт по origin напрямую — минуя WAF, rate-limit и подписанные URL, настроенные на edge. Это классический обход защиты: правила живут на CloudFront, а origin доступен. Найди имя origin (в ошибках, DNS, JS), проверь его напрямую. Часто там же виден внутренний API, который «не должен» быть публичным.

## Подписанные URL и cookies

CloudFront умеет отдавать приватный контент только по подписанным URL или cookies. Подпись делается приватным ключом CloudFront (key pair): в URL попадают `Policy`, `Signature`, `Key-Pair-Id`. Атаки: утечка приватного ключа (лежит в приложении/CI), длинный срок действия подписи, повторное использование подписи (нет привязки к IP), обход через `*.cloudfront.net` другого тенанта. Проверяй, где хранится приватный ключ и насколько широко выдаются подписи.

## Кэш и его отравление

Behaviors определяют, что кэшировать и по каким ключам. Если в cache key не входят важные заголовки или query-параметры, разные пользователи получают один и тот же кэшированный ответ — это cache poisoning/deception. Пример: `X-Forwarded-Host` или `Host` не в ключе, но origin их учитывает — тогда ответ для одного хоста кэшируется и отдаётся всем. Ищи поведения с широким `PathPattern` и узким cache key.

## Типовые мисконфиги CloudFront

| Мисконфиг | Последствие | Как искать |
|---|---|---|
| Публичный origin при закрытом edge | обход WAF | curl напрямую в origin |
| Пустой OAI/OAC | прямой доступ к бакету | конфиг дистрибуции |
| Приватный ключ подписи в приложении | подделка URL | поиск ключа в коде/CI |
| Широкий срок подписи | переиспользование | поле `Expires`/`DateLessThan` |
| Узкий cache key при вариативном origin | cache poisoning | behaviors |
| `ViewerProtocolPolicy: allow-all` | даунгрейд на HTTP | конфиг behavior |

## Полный прогон: от дистрибуции к бакету

Шаги. Первый: найти домен CloudFront (DNS, JS). Второй: определить origin (ошибки 502/403, заголовок `X-Amz-Bucket-Region`, имя в конфиге). Третий: проверить origin напрямую (`curl`). Четвёртый: если бакет публичный — читать объекты. Пятый: проверить подписи (есть ли приватный ключ). Шестой: искать cache poisoning. Седьмой: зафиксировать, что именно даёт доступ — edge-мисконфиг или открытый origin.

## Инструменты и команды

Полезны: `aws cloudfront get-distribution-config`, `aws s3api get-bucket-policy`, `curl -I` (заголовки edge/origin), `dig` (CNAME на `*.cloudfront.net`), анализ фронтенд-бандлов на имена бакетов. Для проверки подписанного URL — декодируй `Policy` (base64url) и смотри условия. Для cache poisoning — сравнивай ответы с разными `Host`/`X-Forwarded-*`.

## OPSEC и детект

Обращения напрямую в origin в обход CloudFront видны в логах S3/ALB (не в логах дистрибуции) — расхождение «запрос был, а в CloudFront-логах нет» заметно. Подбор подписанных URL даёт всплеск 403. Cache poisoning может отразиться в кэше и задеть пользователей — это громко. Тихий сценарий: один прямой `curl` origin и чтение конфига, без массовых запросов.

## Разведка без доступа

Без креденшелов видно: CNAME доменов на CloudFront, заголовки edge, имена бакетов в JS, ошибки с регионом. Из публичной документации узнаётся структура. По этим данным строится гипотеза об origin. Многие конфиги дистрибуции (distribution IDs, ARNs) утекают в публичных репозиториях.

## Частые вопросы

CloudFront заменяет WAF? Нет, WAF можно подключить, но origin всё равно надо закрыть. OAI и OAC взаимозаменяемы? OAC современнее и работает с KMS. Можно ли подделать подписанный URL без ключа? Нет, нужен приватный ключ CloudFront. Опасен ли публичный бакет за CloudFront? Да, это обход edge-защиты. Что если origin — ALB? Проверь его security group и listener на публичность.

## Что не сработает

Бакет с политикой только-для-OAC не отдаст объект напрямую. Подписанный URL с привязкой к IP не переиспользуешь с другого адреса. Origin в приватной сети (VPC origin) недоступен из интернета. WAF с rate-limit на edge защитит от массового перебора, хотя и не от одиночного мисконфига.

## Сценарий: от JS к бакету

Цепочка. В клиентском JS находим `https://acme-assets.s3.amazonaws.com/`. Пробуем `curl https://acme-assets.s3.amazonaws.com/config.json` — 200. Значит, бакет публичный, а CloudFront лишь кэширует. Перечисляем объекты через `aws s3 ls s3://acme-assets --no-sign-request`, находим `backup/` с дампами. Фиксируем: edge-слой не защищал origin. Это типичная находка при аудите AWS-фронтендов.

## Практический чек-лист пентеста CloudFront

Порядок. Один: собрать домены и distribution IDs. Два: прочитать конфиг дистрибуции (если есть права). Три: определить origin. Четыре: проверить origin напрямую. Пять: проверить политику бакета/security group ALB. Шесть: искать приватный ключ подписи. Семь: тестировать cache poisoning. Восемь: оценить расхождение логов edge/origin.

## Что мы теперь знаем

1. CloudFront — edge-слой, но сам origin он не закрывает.
2. OAI/OAC ограничивают доступ к бакету; их отсутствие = прямой доступ.
3. Публичный origin обходит WAF и подписанные URL.
4. Подпись URL держится на приватном ключе — его утечка ломает всю модель.
5. Узкий cache key при вариативном origin ведёт к cache poisoning.
