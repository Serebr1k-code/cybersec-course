## Вопрос, с которого всё начинается

В прошлых уроках мы защищали ключи через TPM. Но у TPM есть предел: он привязывает секрет к состоянию загрузки, а вот *использовать* секрет всё равно приходится обычной ОС — а её можно скомпрометировать. Что если ключ вообще не должен покидать чип?

Для этого придумали **TEE** (Trusted Execution Environment) — доверенную среду: процессор делится на два мира, и в «доверенном» живут ключи и криптография, недоступные обычной ОС.

Вопрос урока: как устроена такая изоляция, и как исследовать доверенный мир, если обычные инструменты его не видят?

## Наш пример: Android-телефон с TrustZone

Перед нами телефон на ARM-процессоре с Android и включённым **TrustZone**. Мы уже имеем root в Android — но ключи платёжного токена всё равно недоступны. Цель — понять, как Android общается с доверенным миром, и где искать слабое место.

## Шаг 1: зачем нужна доверенная среда

TEE решает три задачи:

1. **Изоляция секретов** — ключи диска, платёжные токены, биометрия не должны быть доступны обычной ОС даже при её полной компрометации.
2. **Аттестация** — устройство доказывает удалённой стороне, что загрузилось «правильно».
3. **Защищённые операции** — подпись транзакций, разблокировка по отпечатку, DRM.

Главное свойство: **обычная ОС не может читать память TEE.** Даже с ядром и root ключ «просто прочитать» не выйдет.

## Шаг 2: ARM TrustZone — два мира

TrustZone делит процессор на два состояния: **Secure World** и **Normal World**. Переключение делается инструкцией `SMC` (Secure Monitor Call) и обрабатывается **Secure Monitor** — кодом, который живёт на самом высоком уровне привилегий.

| Уровень | Назначение |
|---------|-----------|
| EL0 | приложения (Normal) |
| EL1 | ядро ОС (Normal) |
| EL2 | гипервизор |
| EL3 | Secure Monitor — граница миров |
| S-EL0/1 | приложения и ядро Secure World |

Память тоже делится: контроллер (TZASC/TZPC) помечает регионы как secure или non-secure. Обращение Normal-мира к secure-региону вызывает исключение. Периферию (криптоакселератор, блок биометрии) тоже можно отдать доверенному миру.

## Шаг 3: программные TEE

Поверх TrustZone работают TEE-ОС:

- **OP-TEE** — открытый TEE от Linaro, часто на ARM-платах; в нём запускаются **trusted applications** (TA).
- **Trusty** — TEE от Google для Android, интегрирован в Android Verified Boot.
- **QSEE/QTEE** — проприетарные TEE Qualcomm.
- **Kinibi, TEEGRIS** — решения Trustonic/Samsung.

**Trusted application** — аналог обычного приложения, но внутри secure-мира. Проверим, есть ли OP-TEE на нашем устройстве:

```bash
$ ls /dev/tee*
/dev/tee0  /dev/teepriv0
$ dmesg | grep -i optee
[    2.1] optee: OP-TEE version: 3.18.0
```

`/dev/tee0` означает, что TEE доступен через стандартный интерфейс. Запустим тесты:

```bash
$ xtest
+-----------------------------------------------------+
| Registration of the OP-TEE test suite...            |
| 1000 subtests, 0 failed                             |
+-----------------------------------------------------+
```

## Шаг 4: как Normal-мир разговаривает с TEE

Обмен идёт по строгой схеме через **shared memory** — регион, доступный обоим мирам:

```text
Normal World                 Secure World
------------                 ------------
app -> /dev/tee0 -> driver
      SMC (SMC_FC_...)  --> Secure Monitor
                          --> OP-TEE kernel
                          --> TA handler
      shared memory     <--  результат
```

Драйвер готовит буфер, выполняет `SMC` с номером функции, Secure Monitor переключает мир, TA обрабатывает запрос и возвращает результат через тот же буфер.

## Шаг 5: где именно ломается изоляция

Уязвимости живут **на границе** миров:

- **Валидация параметров** — если TA доверяет длине или указателю из Normal-мира, получим переполнение в secure-памяти.
- **TOCTOU** — между проверкой буфера и его использованием Normal-мир меняет содержимое.
- **Утечка через shared memory** — если TA не чистит буфер, секрет остаётся в обычной памяти.
- **DMA-атаки** — неверный IOMMU позволяет периферии читать secure-память.

Вот как выглядит классический TOCTOU в TA:

```c
void handle_cmd(void *buf, size_t len) {
    if (!validate(buf, len)) return;   /* CHECK */
    /* Normal-мир может изменить buf через DMA */
    memcpy(dst, buf, len);             /* USE — данные уже другие */
}
```

Защита — копировать данные в secure-память **сразу** и работать с копией.

## Шаг 6: план исследования

Перед атакой на TEE строят модель угроз: что защищено (ключ диска, токен, биометрия), доступна ли прошивка TEE, открыт ли JTAG, какая версия TEE. План по приоритету стоимости:

1. **Реверс TA.** Извлечь `.ta` из прошивки и найти парсеры SMC-команд.
2. **Фаззинг интерфейса.** Из Normal-мира фаззить SMC-команды (осторожно — можно уронить устройство).
3. **Физические методы.** Если прошивка недоступна и fuse закрыты — side-channel/glitch.

```bash
$ find firmware -name '*.ta' -o -name '*.elf' | grep -i ta
$ file secure_ta.elf
secure_ta.elf: ELF 64-bit LSB shared object, ARM aarch64
```

## Шаг 7: трассировка SMC на отладочной плате

На devkit можно включить трассировку переходов в secure-мир — это самый быстрый способ понять протокол:

```bash
$ echo 1 > /sys/kernel/debug/tracing/events/arm_smccc/enable
$ cat /sys/kernel/debug/tracing/trace_pipe
tee-0  [000] smc: smc_fid=0x32000001 ...
tee-0  [000] smc: smc_fid=0x32000003 ...
```

По частоте и аргументам видно, какие TA вызываются. На production трассировка обычно выключена.

## Шаг 8: Apple Secure Enclave — другой подход

Apple использует не TrustZone-режим, а отдельный сопроцессор **Secure Enclave (SEP)**. Он имеет собственное ядро и загрузочную ROM, хранит ключи, привязанные к UID-ключу, который вообще недоступен софту, и не отдаёт ключи наружу — только результаты операций. Это «аппаратный сейф»: атаковать можно только физически (side-channel, glitch) или через баги прошивки SEP.

## Что мы теперь знаем

1. TEE изолирует секреты в «доверенном мире», недоступном обычной ОС даже с root.
2. ARM TrustZone делит процессор на Secure/Normal World; переход — через `SMC` и Secure Monitor (EL3).
3. Поверх TrustZone работают TEE-ОС (OP-TEE, Trusty, QSEE), а в них — trusted applications.
4. Normal-мир общается с TEE через SMC и shared memory; уязвимости живут на этой границе.
5. Основные векторы: невалидированные параметры, TOCTOU, утечки, DMA, баги Secure Monitor.
6. Apple SEP — отдельный сопроцессор, а не режим основного ядра.

## На что смотреть дальше

- **Ожидание «root = доступ к ключам».** С root вы всё ещё в Normal-мире.
- **Игнорирование версии TEE.** Уязвимости OP-TEE/QSEE закрывают патчами — сверяйте версию.
- **Отладка secure-мира на серийной плате.** На production fuse закрыты; devkit-трюки не работают на устройстве.
- **Путаница TEE и secure element.** TEE — среда на основном SoC; secure element — отдельный чип.
- **Неверная модель угроз.** Иногда side-channel дешевле, чем реверс всей TEE.

## Куда дальше

TEE повышает планку, но не делает чип неуязвимым. В следующем уроке по дереву мы спустимся к ещё более аппаратному уровню — secure element: отдельному чипу, который держит ключи платежей и часто атакуется физически. А пока главное: **доверенная среда изолирует секрет, но граница миров — это код, а в коде бывают ошибки.**
