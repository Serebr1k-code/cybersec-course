Обычная операционная система — плохое место для хранения ключей: root-доступ, отладчик или ядро с багом раскроют любой секрет. Поэтому современные чипы умеют разделять себя на два мира: «обычный», где работает ваша ОС, и «доверенный», где живут ключи и криптография. Это TrustZone в ARM и secure enclave в устройствах Apple. Понимание этой модели — ключ к анализу самых защищённых устройств.

## Теория: зачем нужна доверенная среда

Доверенная среда исполнения (TEE, Trusted Execution Environment) решает три задачи:

1. **Изоляция секретов.** Ключи шифрования диска, ключи платёжных токенов, биометрические шаблоны не должны быть доступны обычной ОС даже при её полной компрометации.
2. **Аттестация.** Устройство должно уметь доказать удалённой стороне, что загрузилось в «правильном» состоянии (verified boot), и что секрет доступен только доверенному коду.
3. **Защищённые операции.** Подпись транзакций, разблокировка по отпечатку, DRM — всё это выполняется в изолированном мире.

Ключевое свойство: **обычная ОС не может читать память TEE**. Даже с ядром и root нельзя просто «прочитать» ключ из доверенного мира. Именно поэтому TEE — главный барьер при анализе современных телефонов.

## ARM TrustZone: два мира

TrustZone делит процессор на два состояния: **Secure World** и **Normal World**. Переключение происходит через инструкцию `SMC` (Secure Monitor Call) и обрабатывается **Secure Monitor** (в ARMv8 — EL3).

| Уровень | Назначение |
|---------|-----------|
| EL0 | пользовательские приложения (Normal) |
| EL1 | ядро ОС (Normal) |
| EL2 | гипервизор |
| EL3 | Secure Monitor — граница миров |
| S-EL0/1 | приложения и ядро Secure World |

Память тоже делится: контроллер (TZASC/TZPC) помечает регионы как secure или non-secure. Обращение Normal-мира к secure-региону вызывает исключение. Периферия может быть назначена доверенному миру — например, криптоакселератор или блок биометрии.

## Программные TEE: OP-TEE и Trusty

Поверх TrustZone работают TEE-ОС:

- **OP-TEE** — открытый TEE от Linaro, часто на ARM-платах и в SoC. Имеет собственное ядро, драйверы и «trusted applications» (TA), которые запускаются в secure-мире.
- **Trusty** — TEE от Google для Android, интегрирован в Android Verified Boot.
- **QSEE/QTEE** — проприетарные TEE Qualcomm.
- **Kinibi, TEEGRIS** — решения Trustonic/Samsung.

Trusted application (TA) — аналог обычного приложения, но внутри secure-мира. Общение Normal-мира с TA идёт через **SMC + shared memory**: Normal-мир передаёт буфер, secure-монитор копирует данные, TA обрабатывает. Ошибки в этом интерфейсе (неверная проверка указателей, TOCTOU) — классический источник уязвимостей.

## Secure enclave у Apple

Apple использует не TrustZone-подход, а отдельный сопроцессор **Secure Enclave (SEP)**. Он:

- имеет собственное ядро и загрузочную ROM;
- хранит ключи, привязанные к UID-ключу, который вообще недоступен софту;
- выполняет проверку отпечатка/Face ID и подписывает операции;
- не отдаёт ключи наружу — только результаты операций.

Это модель «аппаратного сейфа»: ключ физически не покидает чип. Атаковать такой дизайн можно только физически (side-channel, glitch) или через баги в прошивке SEP.

## Инструменты и команды

- **`optee_client` / `xtest`** — тесты и общение с OP-TEE из Normal-мира.
- **`tee-supplicant`** — демон, обслуживающий запросы TEE.
- **`ftrace`/`perf`** — трассировка SMC-вызовов на отладочных платах.
- **`Trustonic/TEE` SDK** — для анализа проприетарных TEE.
- **`Ghidra`/`IDA`** — реверс прошивки TEE (если извлечена).
- **`JTAG` + `openocd`** — отладка secure-мира на отладочных платах.
- **`ChipWhisperer`** — side-channel/glitch против TEE (учебный сценарий).

```bash
# Проверка наличия OP-TEE на устройстве
ls /dev/tee*           # /dev/tee0, /dev/teepriv0
dmesg | grep -i optee
# Запуск тестов
xtest
# Трассировка SMC (на отладочной сборке)
echo 1 > /sys/kernel/debug/tracing/events/smc/enable
```

## Разобранный пример: SMC-вызов и границы доверия

Разберём, как Normal-мир общается с TEE и где искать ошибку.

1. **Идентификация TEE.** На устройстве есть `/dev/tee0`. Значит, TEE доступен через стандартный интерфейс OP-TEE.
2. **Обмен данными.** Приложение открывает сессию с TA, передаёт буфер. Secure-монитор копирует данные в secure-память.

```text
Normal World                 Secure World
------------                 ------------
app -> /dev/tee0 -> driver
      SMC (SMC_FC_...)  --> Secure Monitor
                          --> OP-TEE kernel
                          --> TA handler
      shared memory     <--  результат
```

3. **Где искать баг.** В интерфейсе обмена: если TA доверяет длине/указателю из Normal-мира без проверки, возможна запись за границы. Если между проверкой и использованием буфер меняется — TOCTOU.
4. **Проверка изоляции.** Попытка Normal-мира прочитать secure-регион должна давать fault. Если не даёт — ошибка конфигурации TZASC.

## Атаки на TEE

- **Уязвимости в TA.** Неверная валидация параметров SMC, переполнения в парсерах команд — самый частый вектор.
- **Fault injection.** Глитч в момент проверки подписи или доступа к ключу.
- **Side-channel.** По потреблению/EM восстанавливают ключи, даже если память изолирована.
- **Утечка через shared memory.** Если TEE не очищает буфер, секрет остаётся в обычной памяти.
- **DMA-атаки.** Некорректно настроенный IOMMU позволяет периферии читать secure-память.
- **Атаки на Secure Monitor.** Баги в EL3-коде открывают границу миров.

## Взаимодействие SMC и shared memory подробнее

Обмен Normal-мира с Trusted OS (OP-TEE/QSEE/Trusty) идёт по строгой схеме. Драйвер в обычном ядре готовит буфер в **shared memory** (регион, доступный обоим мирам: non-secure для Normal и secure для TEE через TZASC). Затем выполняется инструкция `SMC` с номером функции; Secure Monitor (EL3) переключает мир и передаёт управление в TEE-ядро. TEE копирует параметры во внутреннюю память, обрабатывает запрос в trusted application (TA) и возвращает результат через тот же shared-буфер.

Уязвимости живут именно на границе: **валидация указателей и длин** — если TA доверяет длине из Normal-мира без проверки, получаем переполнение в secure-памяти; **TOCTOU** — между проверкой буфера и его использованием Normal-мир (второй поток или ядро) может изменить содержимое, и TA работает с другими данными; **отсутствие копирования** — если TA читает прямо из shared-памяти, возможна гонка; **утечки** — если TA не чистит буфер, секрет остаётся в обычной памяти и его может прочитать ядро.

Инструменты для исследования: `tee-supplicant` (демон OP-TEE), `xtest`, `/dev/tee0`, трассировка `smc` через ftrace, реверс TA (`.ta`-файл) в Ghidra/IDA. На отладочных платах доступен JTAG secure-мира — это самый прямой путь к внутренностям TEE.

## Модель угроз и практический план

Перед атакой на TEE постройте модель угроз и план, иначе усилия уйдут впустую. Ключевые вопросы: (1) что именно защищено (ключ диска, платёжный токен, биометрия); (2) доступна ли прошивка TEE из дампа или только интерфейс SMC; (3) открыт ли отладочный доступ (JTAG, fuse); (4) какая версия TEE и закрыты ли известные CVE; (5) есть ли физический доступ к чипу.

План по приоритету стоимости:
1. **Реверс TA.** Извлеките `.ta` из прошивки (`binwalk`, распаковка), найдите обработчики SMC и парсеры команд. Ошибка валидации параметров — самый частый и дешёвый вектор.
2. **Фаззинг интерфейса.** Из Normal-мира фаззите SMC-команды и параметры (осторожно — можно уронить устройство).
3. **Физические методы.** Если прошивка недоступна и fuse закрыты — side-channel/glitch (`hardware-power-analysis`, `hardware-laser-fault`).
4. **Платёжные сценарии.** Переходите к `hardware-secure-element` — часто ключ лежит не в TEE, а в отдельном чипе.

Вывод: TEE повышает планку, но не делает чип неуязвимым. Комбинация реверса TA, фаззинга границы миров и, при необходимости, физических атак обычно находит путь.

## Частые ошибки и подводные камни

- **Ожидание «root = доступ к ключам».** С root вы всё ещё в Normal-мире.
- **Игнорирование версии TEE.** Уязвимости в OP-TEE/QSEE закрывают патчами — сверяйте версию.
- **Отладка secure-мира на серийной плате.** На production fuse закрыты, и то, что работает на devkit, не работает на устройстве.
- **Путаница TEE и secure element.** TEE — это среда на основном SoC; secure element — отдельный чип.
- **Неправильная модель угроз.** Если нужен только один ключ, side-channel может быть дешевле, чем реверс всей TEE.

## Что дальше / решение

Если ключ нужен из TEE — сначала ищите уязвимость в TA (реверс прошивки TEE, поиск парсеров SMC). Если прошивка недоступна и fuse закрыты — переходите к физическим методам: fault injection (`hardware-laser-fault`) и power analysis (`hardware-power-analysis`). Для платёжных сценариев следующий шаг — `hardware-secure-element`. Если задача CTF и есть отладочная плата, начните с трассировки SMC и реверса TA — это даёт самый быстрый результат.

## OP-TEE: сборка и запуск на учебной плате

Чтобы понять TEE изнутри, полезно собрать OP-TEE самому. Типовой сценарий — QEMU или отладочная плата.

```bash
# Клонирование манифеста
repo init -u https://github.com/OP-TEE/manifest.git -m qemu_v8.xml
repo sync -j4
# Сборка
cd build && make toolchains && make run
# Внутри QEMU появляется Normal Linux + Secure World (OP-TEE)
```

После загрузки в Normal-мире доступны `/dev/tee0` и утилита `xtest`:

```bash
xtest
# +-----------------------------------------------------+
# | Registration of the OP-TEE test suite...            |
# | 1000 subtests, 0 failed                             |
# +-----------------------------------------------------+
```

Отладочная сборка позволяет вести трассировку переходов между мирами и видеть, как SMC передаёт управление Secure Monitor.

## Реверс trusted application

Trusted application (TA) — обычный бинарник, но запускается в secure-мире. Если удалось извлечь прошивку TEE, TA реверсят в Ghidra/IDA.

```bash
# Найти TA-бинарники в прошивке
find firmware -name '*.ta' -o -name '*.elf' | grep -i ta
# Определить архитектуру
file secure_ta.elf
# secure_ta.elf: ELF 64-bit LSB shared object, ARM aarch64
# Загрузить в Ghidra и искать парсеры SMC-команд
```

Ключевые цели анализа: разбор параметров команды, проверка длины буфера, работа с указателями из shared memory. Именно здесь чаще всего находят переполнения и TOCTOU.

## Атака TOCTOU на shared memory

Классическая уязвимость интерфейса Normal↔Secure — **time-of-check to time-of-use**. TA проверяет указатель/длину, а Normal-мир меняет содержимое буфера между проверкой и использованием.

```c
/* Уязвимый код в TA (упрощённо) */
void handle_cmd(void *buf, size_t len) {
    if (!validate(buf, len)) return;   /* CHECK */
    /* ... Normal-мир может изменить buf через DMA ... */
    memcpy(dst, buf, len);             /* USE — данные уже другие */
}
```

Защита — копировать данные в secure-память **сразу** и работать с копией, а также использовать IOMMU, чтобы Normal-мир не мог менять буфер под TA.

## Сравнение TEE-платформ

| Платформа | Вендор | Особенности | Типичные CVE |
|-----------|--------|-------------|--------------|
| OP-TEE | Linaro | открытый код, ARM | уязвимости в TA |
| QSEE/QTEE | Qualcomm | проприетарный | широко исследован |
| Trusty | Google | Android | интеграция с AVB |
| Kinibi | Trustonic | мобильный | меньше публичных |
| SEP | Apple | отдельный чип | только физика |

Открытые TEE (OP-TEE) легче аудировать: код доступен, есть тесты. Проприетарные (QSEE) чаще ломают через реверс прошивки и поиск ошибок в парсерах SMC.

## Трассировка SMC: что видно

На отладочной плате можно включить трассировку переходов в secure-мир:

```bash
echo 1 > /sys/kernel/debug/tracing/events/arm_smccc/enable
cat /sys/kernel/debug/tracing/trace_pipe
# tee-0  [000] smc: smc_fid=0x32000001 ...
# tee-0  [000] smc: smc_fid=0x32000003 ...
```

По частоте и аргументам SMC видно, какие TA вызываются и с какими командами. На production трассировка обычно выключена, но на devkit это самый быстрый способ понять протокол обмена.

## DMA и IOMMU: почему периферия может читать TEE

Если IOMMU настроен неверно, устройство с DMA (сетевая карта, PCIe, отладочный интерфейс) может читать физическую память, помеченную как secure. Это ломает всю модель изоляции. Проверка:

```bash
# Проверить наличие IOMMU
dmesg | grep -i iommu
# Список групп устройств
ls /sys/kernel/iommu_groups/
```

Защита — включить IOMMU, назначить периферию только Normal-миру и запретить DMA в secure-регионы. Ошибка конфигурации здесь равносильна отсутствию TEE.
