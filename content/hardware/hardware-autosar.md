## Вопрос, с которого всё начинается

Мы видели, что CAN и SOME/IP не аутентифицируют сообщения. Значит, производитель должен добавить защиту где-то выше. В мире AUTOSAR это называется **SecOC** — Secure Onboard Communication.

Вопрос урока: как SecOC защищает сообщение и где эта защита может сломаться.

## Наш пример: защищённый CAN-кадр

У нас есть дамп CAN с сообщением, защищённым SecOC: в кадре есть данные, **MAC** (код аутентичности сообщения) и **счётчик свежести**. Мы проверим MAC вручную и посмотрим, что произойдёт при подмене.

## Шаг 1: что такое AUTOSAR

**AUTOSAR** (AUTomotive Open System ARchitecture) — стандарт архитектуры ПО для ECU. Он делит софт на слои: приложение (SWC — software components), RTE (runtime environment) и базовый софт (BSW) с драйверами и коммуникацией. Идея — переносимость: один и тот же софт работает на ECU разных производителей.

Для нас важно, что в BSW есть модуль **SecOC**, который встраивается в путь отправки/приёма сообщений.

## Шаг 2: как SecOC защищает сообщение

SecOC добавляет к полезной нагрузке:

- **MAC** — криптографический «отпечаток» сообщения, посчитанный на общем секретном ключе.
- **Freshness Value** (счётчик) — число, которое увеличивается с каждым сообщением.

Получатель считает MAC заново и сравнивает; если совпало — сообщение подлинное. Счётчик защищает от повторной отправки старого сообщения (replay).

Типичный алгоритм MAC — **AES-CMAC**. Посчитаем CMAC на Python (упрощённо, на учебном ключе):

```text
$ python3 -c "from cryptography.hazmat.primitives.cmac import CMAC; from cryptography.hazmat.primitives.ciphers import algorithms; c=CMAC(algorithms.AES(bytes(16))); c.update(b'data+ctr'); print(c.finalize().hex())"
7d4b... (первые байты MAC)
```

Ключ и алгоритм заданы в конфигурации SecOC; обе стороны должны знать ключ заранее.

## Шаг 3: где SecOC ломается

Криптография AES-CMAC надёжна, но конфигурация — нет:

1. **Общий ключ на весь автомобиль** — если ключ одинаков для всех узлов, компрометация одного даёт доступ ко всем.
2. **Короткий MAC (truncated MAC)** — ради экономии полосы MAC обрезают (например, до 24 бит). Тогда возможен перебор.
3. **Повторяющиеся счётчики** — если счётчик сбрасывается, replay снова возможен.
4. **«Смешанные» сегменты** — где-то SecOC включён, где-то нет; слабое сообщение можно использовать как рычаг.

Именно эти слабости делают SecOC интересным для исследования.

## Шаг 4: проверка вручную

Предположим, у нас есть ключ `000102...0f` и счётчик `0x0000002A`. Считаем CMAC и сравниваем с MAC в кадре:

```text
$ python3 -c "from cryptography.hazmat.primitives.cmac import CMAC; from cryptography.hazmat.primitives.ciphers import algorithms; k=bytes(range(16)); c=CMAC(algorithms.AES(k)); c.update(b' 0@'+ (42).to_bytes(4,'big')); print(c.finalize()[:3].hex())"
(3-байтовый truncated MAC)
```

Если наш MAC совпал с кадровым — мы можем генерировать валидные сообщения для этого ключа и счётчика.

## Шаг 5: атаки

1. **Replay при сбросе счётчика** — после рестарта ECU счётчик может пойти заново.
2. **Брутфорс truncated MAC** — если MAC 16–24 бита, подобрать реально.
3. **Ключ из прошивки** — если ключ SecOC хранится в образе ПО, его можно извлечь.
4. **Понижение до незащищённого сообщения** — если есть дубль без SecOC.

## Что мы теперь знаем

- AUTOSAR — слоистая архитектура ПО ECU; SecOC — модуль защиты сообщений.
- SecOC = MAC (обычно AES-CMAC) + счётчик свежести.
- Надёжность зависит от конфигурации: ключи, длина MAC, управление счётчиком.
- Truncated MAC и общий ключ — главные практические слабости.
- Ключ можно искать в прошивке ECU.

## Расширенный разбор: как SecOC встроен в стек

Чтобы понимать SecOC, полезно увидеть, где он живёт. AUTOSAR делит софт на слои: приложение (SWC), RTE и базовый софт (BSW). SecOC — модуль BSW, через который проходят защищаемые сигналы.

Когда приложение отправляет сигнал, SecOC:

1. Берёт **freshness value** (счётчик) для этого сигнала.
2. Считает MAC на ключе: обычно AES-CMAC по данным и счётчику.
3. Приклеивает усечённый MAC к сообщению.
4. Передаёт дальше — в PduR и на шину.

На приёме — обратный порядок: пересчёт MAC, сравнение, проверка свежести. Если MAC не совпал или счётчик «старый», сообщение отбрасывается.

Ключи SecOC распространяются через **key management** (например, SHE — Secure Hardware Extension). Отсюда важный вывод: компрометация key management ломает защиту всех сообщений сразу.

## Вендорные особенности

Разные производители по-разному настраивают длину MAC, период freshness, набор защищаемых сигналов. Некоторые защищают только критичные (тормоза, руль), оставляя остальное открытым. Именно эти «незащищённые остатки» и становятся рычагом атаки: через них можно косвенно влиять на защищённые узлы.

## Пошаговое упражнение

1. Возьмите учебный SecOC-кадр с известным ключом и счётчиком.
2. Посчитайте MAC на Python (AES-CMAC).
3. Сравните с MAC в кадре — убедитесь, что совпало.
4. Измените один бит данных и пересчитайте — MAC изменится.
5. Попробуйте подобрать 16-битный усечённый MAC — оцените сложность.

## Детект и защита

Детект SecOC-аномалий: рост числа отброшенных сообщений (неверный MAC), «застрявший» freshness value, сообщения с устаревшим счётчиком. Защита — уникальные ключи на узел, достаточная длина MAC, строгое управление счётчиками и защита key management.
