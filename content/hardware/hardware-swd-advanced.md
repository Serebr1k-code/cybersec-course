## Вопрос, с которого всё начинается

У тебя ARM-устройство. UART закрыт, зато на плате есть два пятачка, похожих на SWD. Через SWD обычно можно остановить ядро и посмотреть память — но что, если остановка ломает устройство или защита её блокирует? Тогда нужен другой подход: **наблюдать за выполнением, не останавливая ядро**.

Этот урок — про продвинутую отладку ARM: трассировку, вывод сообщений без UART и восстановление логики прошивки по потоку инструкций.

## Наш пример: устройство, которое проверяет лицензию

Возьмём ARM Cortex-M устройство, которое при старте проверяет лицензионный ключ. Нужно понять алгоритм проверки. UART закрыт, но SWD доступен. Идём по шагам: подключимся, посмотрим карту отладочных компонентов, поймаем отладочные сообщения, а затем поток инструкций.

## Шаг 1: что такое SWD и CoreSight

**SWD** (Serial Wire Debug) — двухпроводная альтернатива JTAG для ARM: только `SWCLK` (такт) и `SWDIO` (данные), опционально `nRESET` (сброс). Простота обманчива: за ней стоит **CoreSight** — целая подсистема отладки и трассировки на кристалле:

| Компонент | Назначение |
|-----------|-----------|
| DAP (Debug Access Port) | доступ к памяти и регистрам |
| ITM | программный вывод трассировки (аналог printf) |
| DWT | аппаратные watchpoints и счётчики |
| ETM | полный поток выполненных инструкций |
| ETB | встроенный буфер трассировки |
| TPIU | вывод трассировки наружу (через SWO) |
| ROM Table | карта всех этих компонентов |

**SWO/ITM** позволяет прошивке писать отладочные сообщения по одному проводу, без UART. **ETM** даёт поток исполненных инструкций — по нему можно реконструировать, что именно делала программа.

## Шаг 2: подключаемся и смотрим карту

Находим пятачки SWCLK/SWDIO (как искать пины — в уроке про JTAG), подключаем адаптер CMSIS-DAP и просим **pyOCD** показать цель:

```
$ pyocd list
  #   Probe/Board       Unique ID    Target
  0   Generic CMSIS-DAP  0x...        nrf52840
```

pyOCD нашёл чип `nrf52840`. Теперь заглянем в **ROM Table** — карту компонентов CoreSight, чтобы понять, какие возможности отладки вообще есть:

```
> dap info 0
ROM table entries:
  0xE0001000  ETM (Embedded Trace Macrocell)
  0xE0000000  ITM (Instrumentation Trace Macrocell)
  0xE0002000  DWT (Data Watchpoint and Trace)
  0xE000ED00  ...
```

`dap info 0` перечисляет компоненты по адресам. Видим ETM и ITM — значит, доступны и трассировка инструкций, и вывод сообщений. На дешёвых Cortex-M0 этих блоков может не быть, поэтому проверять ROM Table нужно всегда.

## Шаг 3: ловим отладочные сообщения (SWO/ITM)

Настроим вывод ITM через OpenOCD. Параметр `tpiu config` задаёт частоты: первое число — системная частота, второе — скорость SWO:

```
$ openocd -f interface/cmsis-dap.cfg -f target/nrf52.cfg \
  -c "tpiu config internal /tmp/swo.log uart off 64000000 2000000" \
  -c "itm port 0 on" -c "init" -c "reset run"
```

Пока устройство работает, прошивка может писать в ITM-порт 0. Если она это делает, в `/tmp/swo.log` появятся сообщения:

```
LICENSE: reading key from flash
LICENSE: verifying signature
LICENSE: check failed
```

Это отладочные строки, которые разработчик оставил в прошивке. Уже отсюда видно этапы проверки. Главное: ядро при этом **не остановлено** — мы просто читаем его вывод.

## Шаг 4: поток инструкций через ETM

Если сообщений нет, включаем **ETM** — он пишет поток выполненных инструкций в буфер. Прогоняем сценарий (вводим неверный ключ), затем читаем трассировку и сопоставляем адреса с дизассемблером. Так видно, какие функции реально выполнялись, даже если прошивка ничего не «печатает».

Прелесть ETM в том, что он неинтрузивен: **отладка без halt**. Некоторые защиты блокируют остановку ядра (или прошивка сбрасывает ключи в RAM при остановке) — тогда только трассировка и даёт картину.

## Шаг 5: точка останова в нужном месте

Самый быстрый путь к алгоритму — аппаратный breakpoint на функции сравнения. Найдя адрес (по трассировке или дизассемблеру), ставим точку останова:

```
> hb 0x08001234
> resume
```

`hb` (hardware breakpoint) останавливает ядро именно в этой функции. Смотрим регистры и память в момент проверки — и восстанавливаем алгоритм без дизассемблирования всей прошивки. Дальше алгоритм либо воспроизводим (генерируем валидный ключ), либо оформляем как доказательство уязвимости.

## Чем SWD отличается от JTAG на практике

Оба интерфейса дают доступ к чипу, но SWD компактнее: четыре сигнала JTAG (TCK/TMS/TDI/TDO) против двух (SWCLK/SWDIO). На плате с ограниченным местом производители почти всегда разводят именно SWD. Важно и то, что SWD рассчитан именно на ARM и напрямую говорит с DAP — точкой доступа к памяти, поэтому чтение и запись идут быстрее и проще. JTAG остаётся нужен, когда на плате несколько чипов в цепочке или когда надо использовать boundary scan.

## Практический стенд

Для тренировки подойдёт любая отладочная плата на Cortex-M — например, STM32 или nRF52, — и недорогой пробник CMSIS-DAP или ST-Link. Напишите маленькую прошивку, которая проверяет «ключ» и печатает через ITM этапы проверки, зашейте её и попробуйте восстановить алгоритм: сначала по сообщениям SWO, потом по ETM-трассировке, потом точкой останова. Это безопасно и воспроизводимо, в отличие от попыток «на живой» плате.

## Обход debug-lock

Многие чипы после прошивки блокируют SWD (debug lock). Обходы те же, что и для JTAG: массовое стирание специальной последовательностью, glitching в момент проверки защиты или чтение через альтернативный интерфейс (boot ROM, JTAG). Иногда защиту снимает сам загрузчик по определённой команде. Если `halt` не проходит — не считайте чип «мёртвым»: попробуйте неинтрузивные методы.

## Если не сработало

- **SWD без nRESET.** Без линии сброса подключение нестабильно, особенно после `halt` — подключайте `nRESET`.
- **Неверная скорость SWCLK.** Слишком быстро на длинных проводах даёт ошибки; начните с 1 МГц.
- **SWO выдаёт мусор.** Частота TPIU должна точно совпадать с системной — ошибка в множителе превращает поток в кашу.
- **Ждёте ETM на всех чипах.** Дешёвые Cortex-M0 его не имеют; проверяйте ROM Table.
- **Забыли про защиту.** `halt` может блокироваться — переходите к неинтрузивной трассировке.

## Что мы теперь знаем

1. SWD — двухпроводной интерфейс; за ним стоит подсистема CoreSight.
2. ROM Table показывает, какие компоненты (ITM, ETM, DWT) доступны.
3. SWO/ITM — это printf прошивки по одному проводу, без UART.
4. ETM даёт поток инструкций и работает без остановки ядра.
5. Аппаратный breakpoint на функции сравнения быстро вскрывает логику.
