Криптоключи — самое ценное в устройстве: они защищают прошивки, обновления, связь, платёжные операции. Производители прячут их в защищённую память, secure element, OTP-области. Но физический доступ почти всегда даёт путь к ключам: через прошивку, отладочный интерфейс, шину между чипами или side-channel. Этот урок — систематический обзор методов извлечения ключей и обхода защит.

## Где живут ключи

| Место | Пример | Доступ |
|-------|--------|--------|
| Прошивка (флеш) | AES-ключи, API-токены | дамп SPI/NAND |
| Конфиг | пароли, сертификаты | rootfs |
| OTP/fuse | уникальные ключи | чтение через отладку |
| Secure element | платёжные/ID-ключи | внутренний доступ |
| TPM | ключи платформы | TPM-атаки |
| RAM (в рантайме) | сессионные ключи | cold-boot |

Первый вопрос: ключ **статический** (вшит) или **генерируется/выводится** (из UID, OTP)? От этого зависит метод.

## Логические методы

Самые дешёвые — без физического вмешательства:

```bash
# Дамп прошивки и поиск секретов
binwalk -e firmware.bin
grep -rIn -E 'BEGIN (RSA|PRIVATE|EC) ' squashfs-root/
grep -rIn -E '(api[_-]?key|secret|password|token)\s*[:=]' squashfs-root/ | head
# Поиск ключей по энтропии (бинарные ключи)
python3 - <<'EOF'
import math
data = open('blob.bin','rb').read()
for i in range(0, len(data)-32, 16):
    chunk = data[i:i+16]
    ent = -sum((chunk.count(b)/16)*math.log2(chunk.count(b)/16) for b in set(chunk) if chunk.count(b))
    if ent > 3.8:
        print(hex(i), chunk.hex())
EOF
```

Часто ключи лежат прямо в rootfs или в конфигах. Это первое, что нужно проверить.

## Через отладку (JTAG/SWD)

Если отладка не залочена, можно прочитать всю память:

```bash
# OpenOCD: подключение и чтение
openocd -f interface/ftdi/xxx.cfg -f target/stm32f4x.cfg
# В сессии:
> halt
> dump_image firmware.bin 0x08000000 0x100000
> mdw 0x1FFF7A10 16      # чтение уникального ID
```

Часто ключ **выводится из уникального ID** чипа (UID) — тогда, зная алгоритм и UID, его вычисляют. Дамп памяти через отладку даёт всё содержимое флеша и RAM, включая ключи.

## Через шину (SPI/I2C)

Если secure element общается с главным чипом по SPI/I2C, шину можно перехватить:

```bash
# Логический анализатор + PulseView
# Захват SPI: MOSI/MISO/CLK/CS
# Декодирование и поиск команд чтения ключа
# Либо активный I2C-сниффер/шпион
```

Иногда ключи передаются между чипами в открытом виде при загрузке — их ловят логическим анализатором (см. `hardware-logic-analysis`).

## Side-channel и fault injection

Когда ключ внутри secure element и наружу не выходит, применяют:

- **Power analysis (SPA/DPA)** — по потреблению восстанавливают ключ.
- **EM analysis** — по электромагнитному излучению.
- **Fault injection (glitch)** — сбой проверки/вычисления для утечки или обхода.
- **Chip-off** — выпаивание и чтение памяти напрямую.

Это дорого и требует оборудования (ChipWhisperer, Riscure), но обходит «логические» защиты.

## Обход readout protection

Многие MCU имеют бит защиты от чтения (RDP, flash lock, security fuse). Обходы:

- **Glitch при проверке RDP** — сбросить защиту сбоем.
- **Извлечение через bootROM** — загрузка своего кода, читающего флеш.
- **Эмуляция/восстановление** — атаки на известные реализации (например, STM32 RDP1).
- **Чтение OTP через отладку** до залочки.

История знает десятки обходов RDP для популярных MCU — это частая тема CTF.

## Разобранный пример: ключ из прошивки и UID

```bash
# 1. Дамп флеша (SPI/отладка)
flashrom -p ch341a_spi -r dump.bin
# 2. Разбор и поиск секретов
binwalk -e dump.bin
grep -rIn 'BEGIN PRIVATE KEY' _dump.bin.extracted/ 2>/dev/null
# 3. Если ключ не найден, но есть алгоритм из UID:
#    прочитать UID через отладку/bootROM
# 4. Восстановить ключ по алгоритму (реверс функции деривации)
# 5. Проверить ключ на расшифровке трафика/прошивки
```

## Правовые аспекты

Извлечение ключей — чувствительная операция. Законно — на своём устройстве и в рамках согласованного пентеста. Извлечение ключей чужого устройства, обход защит, клонирование — противоправно. Даже в пентесте фиксируйте, что ключи будут извлекаться, и обращайтесь с ними как с секретами (не публикуйте, передавайте безопасно).

## Частые ошибки и подводные камни

- **Искать только строки**: бинарные ключи не видны в `strings` — используйте энтропию/hex.
- **Забыть про UID-деривацию**: ключ может не лежать в памяти, а вычисляться.
- **RDP ломается необратимо**: неверная попытка обхода может «убить» чип.
- **Side-channel требует калибровки**: без неё DPA не сработает.
- **Ключ в RAM, а не во флеше**: нужен cold-boot/дамп RAM.
- **Обфускация**: ключи могут быть закодированы/XOR-нуты.

## Атаки на деривацию ключа из UID

Многие устройства **выводят** ключ из уникального идентификатора чипа (UID/OTP) через проприетарный алгоритм. Тогда ключа в памяти нет — его надо вычислить:

1. Собрать несколько пар (UID, известный результат) — например, расшифровать два известных блока.
2. Реверсить функцию деривации в прошивке (Ghidra/radare2).
3. Воспроизвести алгоритм для своего устройства.

```bash
# Прочитать UID (пример через OpenOCD)
openocd -f interface.cfg -f target.cfg -c "init; mdw 0x1FFF7A10 4; exit"
# Реверс функции деривации: искать в бинарнике константы и циклы
```

Если алгоритм слабый (простой хэш от UID без секрета), ключ вычисляется для любого устройства. Это классическая уязвимость «security by obscurity».

## Cold-boot и дамп RAM

Ключи могут жить только в RAM (сессионные, развёрнутые из защищённого хранилища). Тогда их достают:

- **Cold-boot**: охладить память, быстро перезагрузить и снять дамп RAM.
- **Через отладчик**: `dump_image` пока устройство работает.
- **Через крэш-дамп**: заставить устройство выгрузить память.
- **Через JTAG halt**: остановить CPU и прочитать память.

```bash
# Дамп RAM через OpenOCD
openocd -f interface.cfg -f target.cfg
> halt
> dump_image ram.bin 0x20000000 0x20000
```

В дампе RAM ищите ключи по энтропии и по известным структурам.

## Практический стенд

- **Своя плата** (STM32/ESP32) — для отработки дампа и RDP-обхода.
- **CH341A + SOP8-клипса** — дамп SPI без выпаивания.
- **OpenOCD + JTAG/SWD** — чтение памяти.
- **Логический анализатор** — перехват шин.
- **ChipWhisperer** — power/glitch (для продвинутых).

Начните с простого: дамп флеша и `grep` — часто ключ там. Только если не нашли, переходите к отладке, шинам и физическим атакам.

## Защита ключей на устройстве

Как производители защищают ключи (и как это обходят):

- **Secure element** — ключ внутри защищённого чипа; обход через side-channel/fault.
- **RDP/flash lock** — запрет чтения флеша; обход через glitch/bootROM.
- **Шифрование прошивки** — ключ зашифрован; обход через извлечение ключа из RAM.
- **OTP/fuse** — уникальные ключи, нечитаемые; обход через деривацию/отладку.
- **Обфускация** — XOR/кодирование; обход через анализ.

Ни одна мера не абсолютна при физическом доступе; цель — сделать атаку дорогой.

## Практические сценарии

- **Дамп флеша** и поиск статических ключей.
- **Чтение памяти** через отладку при незалоченном интерфейсе.
- **Деривация ключа** из UID по реверснутому алгоритму.
- **Перехват шины** между чипами.
- **Side-channel/fault** против secure element.

Порядок: от дешёвых логических методов к дорогим физическим. В 80% случаев хватает дампа и `grep`.

## Итог: порядок действий

Извлечение ключей — это последовательность от дешёвого к дорогому: дамп флеша → поиск секретов → отладка (если открыта) → перехват шин → деривация из UID → side-channel/fault. Начинайте с простого: в большинстве случаев ключ лежит в прошивке или вычисляется из UID. Физические атаки — последний рубеж, когда логические исчерпаны.
