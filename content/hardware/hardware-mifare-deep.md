## Вопрос, с которого всё начинается

В прошлом уроке мы узнали, что **Mifare Classic** защищена шифром Crypto1 и что `autopwn` восстанавливает ключи. Но что именно происходит «под капотом»? Почему одна атака работает секунды, а другая — часы?

Разберём атаки на Crypto1 подробно: как они устроены и когда какую применять.

## Наш пример: карта с неизвестными ключами

Перед нами Mifare Classic 1K, ключи которой мы не знаем. Есть Proxmark3. Задача — восстановить все ключи и снять полный дамп. Начнём с устройства карты.

## Шаг 1: как устроена карта

Mifare Classic 1K — это 16 секторов по 4 блока (по 16 байт). Каждый сектор защищён **двумя ключами**: A и B. Последний блок сектора, **trailer**, содержит ключи A и B и **биты доступа** (Access Bits), которые определяют права на чтение и запись.

**Crypto1** — потоковый шифр с 48-битным ключом и 48-битным внутренним состоянием на основе LFSR (сдвигового регистра). Несмотря на то что шифр полностью сломан, атака требует «диалога» с картой — обмена аутентификацией.

## Шаг 2: словарь ключей — самый быстрый старт

Прежде чем атаковать криптографию, проверим типовые ключи. Многие карты оставляют заводские значения:

```
pm3 --> hf mf chk --1k -f default_keys.dic
```

`hf mf chk` проверяет список ключей по всем секторам. Частые «заводские» ключи — `FFFFFFFFFFFF` и `A0A1A2A3A4A5`. Очень часто хотя бы один сектор открыт — и тогда дальше всё пойдёт быстро.

## Шаг 3: nested — когда один ключ уже есть

Идея **nested**-атаки: при аутентификации карта использует **nonce** — случайное число. Зная один ключ, можно вынудить карту зашифровать nonce для другого сектора и восстановить ключ. То есть одного известного ключа достаточно, чтобы вытащить остальные:

```
pm3 --> hf mf nested --1k --blk 0 -a -k FFFFFFFFFFFF
```

Здесь `-a` — использовать ключ A, `-k` — сам ключ. Атака работает секунды. Её слабое место — «статичные» карты (некоторые клоны не генерируют настоящий nonce), для них нужен вариант `staticnested`.

## Шаг 4: darkside — когда ключей нет

Если ни один ключ не известен, применяют **darkside**. Она извлекает ключ из nonce, используя особенность реализации: карта определённым образом отвечает на «неправильные» запросы аутентификации:

```
pm3 --> hf mf darkside
```

Работает минуты, но не на всех картах — зависит от партии и «открытости» nonce. Если darkside не сработал, остаётся третий вариант.

## Шаг 5: hardnested — надёжно, но долго

**hardnested** не требует ни известных ключей, ни уязвимого nonce. Это статистическая атака: она собирает много обменов и перебирает варианты:

```
pm3 --> hf mf hardnested --blk 0 -a -k FFFFFFFFFFFF --tk
```

Работает надёжно, но занимает от десятков минут до часов. Запускайте с запасом времени и логируйте прогресс.

## Шаг 6: автопилот — `autopwn`

Не обязательно выбирать атаку вручную. Команда `hf mf autopwn` проходит всю цепочку сама:

```
pm3 --> hf mf autopwn
# словарь -> nested -> darkside -> hardnested
# результат: dump.bin + keys.bin
```

Сначала проверяются типовые ключи, затем nested (если ключ найден), потом darkside и hardnested. Для большинства карт этого достаточно.

## Шаг 7: дамп, анализ и клон

Получив ключи, снимаем дамп и анализируем данные:

```
pm3 --> hf mf dump
pm3 --> hf mf chk --1k -f keys.bin
```

В дампе — UID, данные секторов и ключи. Часто СКУД использует UID плюс один-два сектора, а номер карты хранится в BCD-кодировке. Дальше клон: `hf mf cload -f dump.bin` в UID-перезаписываемую карту или эмуляция `hf mf sim`.

## Все атаки в одной таблице

| Атака | Условие | Время | Надёжность |
|-------|---------|-------|-----------|
| словарь | типовые ключи | секунды | зависит от карты |
| nested | известен ≥1 ключ | секунды | высокая |
| darkside | ключей нет | минуты | средняя |
| hardnested | ключей нет | часы | высокая |
| staticnested | известен ключ, карта «статичная» | быстро | зависит от карты |

Логика выбора проста: сначала словарь, затем nested (если есть ключ), потом darkside, и только в крайнем случае — hardnested.

## Сектора, блоки и биты доступа

Разберём структуру внимательнее. Mifare Classic 1K — 16 секторов по 4 блока по 16 байт. Последний блок сектора — **trailer**: Key A, **Access Bits** и Key B. Access Bits задают права на чтение и запись как данных, так и самих ключей. Зная Key A или Key B, вы читаете сектор; для записи нужны соответствующие права.

Частая ошибка новичков — забыть, что после восстановления ключей запись может быть запрещена: читать сектор получится, а писать — нет.

```
pm3 --> hf mf chk --1k -f keys.txt
pm3 --> hf mf rdbl --blk 0 -a -k FFFFFFFFFFFF
```

## Как защищаться

- перейти на **Mifare DESFire** EV2/EV3 с AES;
- использовать **уникальные ключи** на каждую карту;
- включить антипассбэк и мониторинг использования;
- заменить Mifare Classic там, где это возможно.

## Практика: полный цикл от карты до клона

Соберём всё вместе на своей карте. Сначала считайте её и проверьте дефолтные ключи, затем примените darkside или nested для извлечения неизвестных. Получите полный дамп, разберите trailer-блоки и определите права доступа. Затем запишите дамп на UID-болванку и проверьте клон на своём считывателе. Такой цикл повторяет реальный аудит СКУД и сразу показывает, где именно система полагается на сломанную криптографию.

## Если не сработало

- **Нет ключа и darkside не работает.** Остаётся hardnested (часы) или fault injection.
- **«Статичная» карта.** Клон не генерирует настоящий nonce — nested не сработает, нужен staticnested.
- **Плохой контакт и питание.** Атаки чувствительны; Proxmark должен получать стабильное питание.
- **Биты доступа.** После восстановления ключей запись может быть запрещена — читать можно, писать нет.
- **Правовые рамки.** Клонирование чужих карт — преступление.

## Что мы теперь знаем

1. Mifare Classic 1K — 16 секторов по 4 блока, каждый защищён ключами A/B.
2. Crypto1 сломан, но атака требует обмена аутентификацией с картой.
3. nested работает при одном известном ключе, darkside — без ключей, hardnested — когда ничего не сработало и нужно терпение.
4. `autopwn` проходит всю цепочку атак автоматически — это самый быстрый путь к полному дампу карты.
5. После восстановления ключей карта читается полностью и клонируется на UID-болванку.

## Разбор реального дампа: что именно искать в секторах

После `hf mf dump` появляется файл `dump.bin` размером 1024 байта (для 1K) — это 16 секторов по 4 блока по 16 байт. Разберём, как читать его глазами. Полезная нагрузка почти всегда лежит не в блоке 0, а в одном из последующих секторов. Смотрим трейлер сектора (последний блок): первые 6 байт — Key A, затем 3 байта access bits, затем 4 байта — Key B. Если в дампе видно `FF FF FF FF FF FF` для Key A и `FF FF FF FF` для Key B — значит, на этом секторе стоят дефолтные ключи, и он читается без единой атаки.

```bash
$ xxd dump.bin | sed -n '1,8p'
00000000: 1234abcd 8804 0000 0000 0000 0000  ...............
00000010: 0000 0000 0000 0000 0000 0000  ...............
```

Дальше ищем осмысленные данные: `strings dump.bin | grep -E '[0-9]{6,}'`. Номер карты в СКУД почти всегда хранится в **BCD-кодировке** — по одному десятичному разряду на полубайт. Если видишь байты `12 34 56 78`, это не число `0x12345678`, а строка `"12345678"`. Именно поэтому `strings` находит десятичные последовательности, которые выглядят как «обычный текст», а `xxd` показывает их как байты. Ещё одно место — блок 0: там UID (4 байта), BCC (XOR-контрольная сумма UID), SAK и ATQA. UID можно менять только на картах с перезаписываемым UID (обычно помечены как «UID writable»); на «магических» болванках Gen2 меняется весь блок 0, а на Gen1 — только UID.

## Откуда берутся дефолтные ключи и что такое диверсификация

Словарь из шага 2 работает не «по удаче», а потому что заводы печатают целые партии карт с одним и тем же Key A. Самые частые ключи: `FFFFFFFFFFFF`, `A0A1A2A3A4A5`, `D3F7D3F7D3F7`, `000000000000`, `AABBCCDDEEFF`. Производители СКУД долго рекомендовали именно `A0A1A2A3A4A5` как «стандартный» ключ — и тысячи систем по всему миру так и остались на нём.

Правильная защита называется **диверсификацией ключей**: для каждой карты ключ вычисляют как `K_card = AES(master_key, UID)`. Тогда компрометация одной карты не открывает остальные, а словарь из дефолтов бесполезен, потому что ключи у всех разные. Если система этого не делает, восстановление ключей одной карты почти наверняка даёт ключи всей системы.

## Ограничения, о которых забывают

- **Счётчик `-h` в `autopwn` не бесконечен.** hardnested может идти часами; ставьте таймаут и сохраняйте промежуточные ключи.
- **«Магические» карты Gen1a** нельзя перезаписать обычной командой — сначала нужна команда `40`/`43` (backdoor), которую не все болванки поддерживают.
- **Клонирование UID не всегда достаточно.** Некоторые считыватели проверяют BCC и SAK или ведут журнал «UID уже входил» (антипассбэк).
- **Правовая сторона.** Даже чтение чужой карты без письменного разрешения — нарушение; в отчёте пентеста фиксируйте только карты, переданные заказчиком.

## Полный скрипт: разбор дампа и поиск секрета

После `hf mf dump` остаётся `dump-mf.txt` — текстовый дамп всех 64 блоков. Разберём его и найдём секрет, не полагаясь на глаза:

```python
blocks = {}
for line in open("dump-mf.txt"):
    line = line.strip()
    if not line or line.startswith("#"):
        continue
    num, _, rest = line.partition(":")
    hexdata = rest.replace(" ", "").replace("|", "")
    blocks[int(num, 16)] = bytes.fromhex(hexdata[:32])

# 1) вытащим ASCII-флаг из блоков данных (trailer пропускаем)
for n, b in sorted(blocks.items()):
    if n % 4 != 3 and b"nto{" in b:
        print("flag block", hex(n), b)

# 2) декодируем UID и BCD-номер карты
print("UID:", blocks[0][:4].hex().upper())
print("BCD:", " ".join(f"{v>>4}{v&0xf}" for v in blocks[1][:8]))
```

```text
flag block 0x5 b'flag{m1f4r3_cryp701}\x00...'
UID: 9A3B7C11
BCD: 0012 3456 7890 1234
```

Первый цикл ищет флаг в блоках данных (trailer-блоки пропущены — там ключи и биты доступа), второй показывает UID и номер карты в BCD. Номер в СКУД часто сравнивают именно в этом формате, поэтому при клонировании важно сохранить и UID, и BCD-поле.

## Справочная таблица: команды Proxmark3

| Команда | Что делает |
|---------|-----------|
| `hf mf chk --1k -f keys.dic` | проверка словаря ключей по секторам |
| `hf mf nested --1k --blk 0 -a -k <key>` | nested при известном ключе |
| `hf mf darkside` | восстановление ключа без словаря |
| `hf mf hardnested --blk 0 -a -k <key> --tk` | статистическая атака |
| `hf mf autopwn` | вся цепочка автоматически |
| `hf mf dump` | снять полный дамп |
| `hf mf rdbl --blk N -a -k <key>` | прочитать блок |
| `hf mf cload -f dump.bin` | записать дамп в UID-болванку |
| `hf mf sim` | эмулировать карту |

## Ограничения: почему Crypto1 не «взломали одним запросом»

Crypto1 полностью сломан, но не «одним запросом»: атаки работают только в диалоге с картой, потому что nonce генерируется ею и не покидает её памяти в открытом виде. Отсюда ограничения:

- **nested** требует хотя бы одного известного ключа — на карте со всеми случайными ключами он не стартует.
- **darkside** зависит от партии чипа: клоны с «правильным» nonce его не поддают.
- **hardnested** статистически надёжен, но требует десятков минут и стабильного питания; сбой питания обнуляет прогресс.
- **fault injection** (глитчи питания) может обойти защиту, но требует лабораторного оборудования и рискует «убить» карту.

Вывод: сломанный шифр не означает мгновенный доступ — реальное ограничение задают **интерфейс** (нужен физический диалог) и **качество карты** (nonce, партия).
