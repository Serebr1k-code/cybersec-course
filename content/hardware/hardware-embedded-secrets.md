## Вопрос, с которого всё начинается

Ты уже умеешь снимать прошивку устройства и распаковывать её файловую систему. В руках — папка `squashfs-root` с сотнями файлов. С чего начать поиск того, ради чего всё затевалось: паролей, токенов, ключей?

Это самый результативный этап hardware-пентеста: часто достаточно одного удачного `grep`, чтобы получить доступ к устройству и к его облаку. Разберём системный подход.

## Наш пример: распакованная прошивка роутера

Продолжим с образом, который сняли в уроке про SPI. Распакуем всё, что внутри:

```
$ binwalk -eM firmware.bin
$ cd _firmware.bin.extracted/squashfs-root
$ ls
bin  dev  etc  lib  mnt  overlay  root  sbin  tmp  usr  var  www
```

Перед нами обычная корневая файловая система Linux. Идём по чек-листу: учётки, ключи, токены, строки подключения, бэкдоры. Общий принцип такой: сначала самое дешёвое — текстовый поиск, потом конкретные форматы, потом базы и бинарные блоки.

## Шаг 1: ищем очевидные секреты строками

Начнём с простого — текстового поиска по распакованному дереву:

```
$ grep -rIn -E 'password|passwd|secret|api[_-]?key|token|credential' . | head -5
./etc/config/wireless: option key 'SuperSecret123'
./usr/lib/lua/luci/model/cbi/admin: password = "admin"
```

Уже находка: в конфиге Wi-Fi лежит пароль в открытом виде, а в скрипте — жёстко зашитый `admin`. Ключевой момент: `grep -rIn` рекурсивно (`-r`) ищет по строкам, показывает имена файлов (`-I` пропускает бинарники) и номера строк (`-n`). Часто этого достаточно.

## Шаг 2: ищем конкретные форматы ключей

Слова «password» и «secret» — не единственные маркеры. У многих токенов есть узнаваемый префикс, и по нему их ищут точечно:

```
$ grep -rIn -E 'AKIA[0-9A-Z]{16}' .        # AWS access key
$ grep -rIn -E 'AIza[0-9A-Za-z_-]{35}' .   # Google API key
$ grep -rIn -E 'xox[baprs]-' .             # Slack token
$ grep -rIn -E -- '-----BEGIN [A-Z ]+-----' .  # ключи и сертификаты
```

Каждый шаблон — это сигнатура конкретного сервиса. `AKIA` — начало ключей AWS, `AIza` — Google, `xox` — Slack. Такие ключи почти всегда дают доступ к чему-то внешнему, поэтому они особенно ценны.

## Шаг 3: учётные записи и хэши

Дальше — самое классическое место секретов:

```
$ cat etc/passwd
root:x:0:0:root:/root:/bin/ash
$ cat etc/shadow 2>/dev/null
root:$1$xyz$Rk...:0:0:99999:7:::
```

`/etc/passwd` показывает пользователей, а `/etc/shadow` — хэши их паролей. Хэш вида `$1$...` — это MD5-крипт, `$5$` — SHA-256, `$6$` — SHA-512. Их не «расшифровывают», а **взламывают офлайн**: перебором в `hashcat` или `john`. Но иногда пароль лежит рядом в открытом виде — тогда он сразу применим.

## Шаг 4: ключи и сертификаты

Приватный ключ подписи обновлений — особенно ценный трофей: с ним можно создавать «легитимные» прошивки, которые устройство примет.

```
$ find . -type f \( -name '*.pem' -o -name '*.key' -o -name 'id_rsa*' \)
./etc/ssl/private/update_signing.key
$ openssl rsa -in ./etc/ssl/private/update_signing.key -check -noout
RSA key ok
```

`openssl rsa -check` подтверждает, что перед нами валидный приватный ключ, а не мусор. Такой ключ позволяет подписать собственный образ обновления.

## Шаг 5: строки подключения к облаку

Отдельная категория — данные, которыми устройство ходит в облако производителя:

```
$ grep -rIn -E 'mqtts?://[^ ]+:[^ ]+@' .
./etc/config/cloud: option url 'mqtts://device:FleetPass99@mqtt.vendor.io:8883'
```

Это строка подключения с логином и паролем к MQTT-брокеру. Именно такие находки часто критичнее доступа к одному устройству: с этими учётками можно подключиться к брокеру и увидеть **весь флот** — тысячи устройств. Если токен ведёт к API производителя, стоит проверить его права: часто это полный доступ.

## Шаг 6: когда `grep` молчит

Если ничего не нашлось, секреты могут быть закодированы. Проверим base64 и hex:

```
$ grep -rIn -E '[A-Za-z0-9+/]{40,}={0,2}' . | head
$ grep -rIn -E '([0-9a-fA-F]{2}){16,}' . | head
```

А если данные под XOR-обфускацией — перебираем однобайтовый ключ и ищем узнаваемую строку:

```
$ python3 - <<'EOF'
data = open('suspicious.bin','rb').read()
for k in range(1,256):
    dec = bytes(b ^ k for b in data[:64])
    if b'http' in dec or b'BEGIN' in dec:
        print('key', k, dec[:32])
EOF
```

Ещё один приём — **энтропийный анализ**: `binwalk -E firmware.bin` рисует график, и высокоэнтропийные участки — это сжатие или шифрование. Именно там могут прятаться ключи, которых не видно текстом.

## Ещё два места, которые часто забывают

Помимо конфигов, проверяйте **веб-интерфейс** и **логи**. В веб-интерфейсе устройства ключи и адреса API часто захардкожены прямо в JS:

```
$ find www -name '*.js' | xargs grep -In -E 'token|api|endpoint' | head
$ grep -rIn -oE '/api/[a-zA-Z0-9_/]+' www/ | sort -u | head
```

А в отладочных логах и истории shell остаётся то, что убрали из конфигов, но забыли вычистить из образа:

```
$ find . -name '*.log' -o -name '*.bak' | head
$ grep -rIn -E 'password=|Authorization: Bearer|token=' var/ 2>/dev/null | head
$ cat root/.ash_history 2>/dev/null
```

В `ash_history` нередко сохранились команды с паролями, а в старых логах — токены и внутренние URL.

## Ответственное обращение с секретами

Найденные ключи и токены — чувствительные данные, и обращаться с ними надо аккуратно. Не публикуйте их даже в отчёте — маскируйте значение, оставляя префикс для доказательства. Передавайте по защищённому каналу и храните зашифрованно. Не используйте чужие ключи за пределами согласованного теста и сообщайте вендору через responsible disclosure. Ценность пентеста — в доказательстве уязвимости, а не в самом секрете.

## Если не сработало

- **Ищете только слово password.** Токены и ключи его не содержат — расширяйте шаблоны.
- **Игнорируете бинарники.** Секреты часто вшиты в демоны, а не в текстовые конфиги.
- **Пропускаете веб-интерфейс.** В JS-файлах бывают захардкожены API-ключи и эндпоинты.
- **Не читаете базы.** SQLite часто хранит токены и учётки: `sqlite3 base.db '.tables'`.
- **Не распаковали всё.** Секреты в сжатых блоках — сначала `binwalk -eM`.

## Что мы теперь знаем

1. Секреты ищут системно: распаковка → `grep` по паттернам → конфиги → ключи → базы → JS.
2. У токенов есть сигнатуры (AKIA, AIza, xox), по ним их находят точечно.
3. Хэши паролей взламывают офлайн, а не «расшифровывают».
4. Приватный ключ подписи обновлений — самый ценный трофей.
5. Строки подключения к облаку могут открыть доступ ко всему флоту устройств.

## Реальная сессия: binwalk + strings

Разберём работу с прошивкой роутера по шагам. Сначала определяем формат и раскладываем её на компоненты:

```bash
$ binwalk firmware.bin
DECIMAL       HEXADECIMAL     DESCRIPTION
0             0x0             uImage header, "Linux-3.4.113"
64            0x40            LZMA compressed data
1179648       0x120000        Squashfs filesystem, little endian
$ binwalk -e firmware.bin
```

После `-e` получаем дерево `_firmware.bin.extracted/` с корневой файловой системой. Дальше — стандартный набор: `strings`, `grep`, поиск конфигов, скриптов, ключей. Часто в `/etc/` лежат `passwd`, `shadow`, конфиги Wi-Fi и SSH-ключи.

```bash
$ find _firmware.bin.extracted -name '*.conf' -o -name 'passwd' -o -name '*.pem'
$ strings -n 8 squashfs-root/bin/busybox | grep -iE 'api|token|secret'
```

## Что искать в конкретных прошивках

| Цель | Где искать |
|------|-----------|
| учётные записи | `/etc/passwd`, `/etc/shadow`, скрипты init |
| ключи API/облака | бинарники, `/etc/config`, JSON-конфиги |
| приватные ключи | `*.pem`, `*.key`, `/etc/ssl` |
| строки подключения | `mongodb://`, `mqtt://`, `postgres://` |
| пароли по умолчанию | веб-панель, `default.cfg`, `nvram` |
| URL бэкенда | `grep -rE 'https?://' .` |

Полезный приём — искать не только по форматам, но и по энтропии: высокоэнтропийные участки внутри бинарника часто оказываются встроенным ключом или зашифрованным blob. Инструмент `binwalk -E` строит карту энтропии и помогает их заметить.

## Когда `grep` молчит

Если строки не находятся, вероятны три причины: **сжатие** (blob сжат zlib/LZMA — распакуйте), **шифрование** (данные зашифрованы, нужен ключ из другого места) или **кодирование** (base64/hex — декодируйте подозрительные строки). Также помогает поиск по **магическим байтам** и сигнатурам конкретных форматов (PEM начинается с `-----BEGIN`, JWT — с `eyJ`). Для сжатых blob'ов используйте `binwalk` повторно или ручную распаковку по найденной сигнатуре.

## Ответственное обращение с секретами

Найденные ключи и пароли — чувствительные данные. Правила: не используйте их за пределами согласованного объёма, не публикуйте в открытых каналах, фиксируйте в отчёте в обезличенном виде (первые/последние символы), уведомляйте заказчика как можно раньше. Если ключ ведёт к реальному облаку или продакшену — это критическая находка, и её нужно эскалировать немедленно, а не «проверять руками» без разрешения.
