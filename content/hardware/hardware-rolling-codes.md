## Вопрос, с которого всё начинается

Ты записал сигнал брелока автосигнализации, повторил его — и ничего не произошло. Дверь не открылась. Причина в том, что производитель добавил **rolling code**: при каждом нажатии передаётся новое значение, а приёмник принимает только «следующие» коды из окна. Простейший replay перестаёт работать. Разберём, как устроен rolling code и почему алгоритм KeeLoq всё равно поддаётся атаке.

## Как работает rolling code

Брелок и приёмник имеют общий счётчик (или генератор последовательности). При нажатии брелок увеличивает счётчик, шифрует его (или хэширует с секретом) и передаёт результат вместе с частью открытых битов. Приёмник хранит последнее принятое значение и проверяет, что приходящий код — «следующий» в допустимом окне впереди.

Окно нужно потому, что нажатия могут «теряться» (помехи, дальность). Если бы приёмник принимал строго +1, любое потерянное нажатие рассинхронизировало бы пару. Поэтому окно, например, от +1 до +16: принимаются коды в этом диапазоне, а счётчик «прыгает» вперёд. Отсюда:

- **Replay старого кода** отвергается (он позади счётчика).
- **Захват одного кода** бесполезен — нужно воспроизвести код, который приёмник ещё не видел.
- **Десинхронизация** — если перехватить и «съесть» несколько нажатий, брелок уйдёт вперёд, и пользователь будет вынужден синхронизировать заново (двойным нажатием). Именно это эксплуатирует RollJam.

## Наш пример: брелок автосигнализации HCS301

Дано: автосигнализация с брелоком на rolling code (микросхема HCS301), 433.92 МГц.

## Шаг 1: подтверждаем, что код меняется

```bash
rtl_433 -f 433.92M -A -F json | tee hcs.json
# {"model":"HCS301","id":1234567,"code":18324521,...}
# {"model":"HCS301","id":1234567,"code":87654321,...}   <- меняется
```

Код меняется при каждом нажатии → это rolling code, а не фиксированный.

## Шаг 2: простой replay не работает

Пробуем воспроизвести последний записанный код (Flipper Replay). Не срабатывает: приёмник отверг старое значение, потому что оно позади его счётчика.

## Шаг 3: KeeLoq — что внутри

**KeeLoq** — блочный шифр, разработанный для Microchip HCS-серии (HCS301, HCS360, HCS200). Ключ — **64 бита** (в HCS это 64-битный manufacturer key + 32-битный device key + serial). Алгоритм нелинейный, с 528 раундами, работает побитово: каждый такт сдвигает регистр и применяет нелинейную функцию NLF.

Кадр HCS301 — 66 бит: 32 зашифрованные (hopping code), 28 — serial number, 4 — статус (батарея, кнопки). Передаётся по OOK/ASK на 433 МГц. Serial открытый, поэтому приёмник находит пару по serial и проверяет код.

## Шаг 4: где ломается KeeLoq

Полный 64-битный ключ перебрать нельзя. Но реальные реализации используют **слабые ключи**:

- manufacturer keys утекали из прошивок;
- device keys иногда выводятся из серийного номера.

Если manufacturer key известен (для ряда производителей он опубликован/утечён), остаётся 32-битный device key — перебор на GPU за часы/дни. Есть и академические атаки: slide attacks, algebraic attacks, guess-and-determine, а также side-channel по питанию/ЭМИ при шифровании в микроконтроллере.

## Шаг 5: RollJam

Если ключ недоступен, остаётся **RollJam**: глушим частоту и записываем два кода жертвы (жертва жмёт дважды, думая, что не сработало). Уходим с первым кодом, ждём, пока жертва уйдёт, и воспроизводим один из записанных — приёмник примет его как «следующий». Нужны два радио (глушилка + приёмник) или Flipper с дополнительным модулем.

## Восстановление ключа на практике

1. **Собрать пары (plaintext, ciphertext)** — известные пары «счётчик → hopping code». Зная serial и предполагая, что счётчик начинается с 0 при выпуске, можно построить пары для малых значений.
2. **Знать manufacturer key** (или перебрать слабый). Если есть device key из прошивки — совсем просто.
3. **Перебрать device key** на GPU, проверяя по собранным парам.
4. **Воспроизвести** код для нужного счётчика — брелок скомпрометирован навсегда.

## Атаки на rolling code

| Атака | Условие | Результат |
|-------|---------|-----------|
| Replay старого кода | нет | отвергается |
| RollJam | захват двух кодов + глушение | открытие |
| Code grabbing | реальное время | иногда |
| Десинхронизация | перехват нескольких нажатий | пользователь пересинхронизирует |
| Key recovery (KeeLoq) | слабый ключ / утечка | полный контроль |
| Side-channel | физический доступ к брелоку | извлечение ключа |
| Jamming | всегда | DoS, но не доступ |

## Микросхемы HCS

| Чип | Ключ | Кадр | Применение |
|-----|------|------|------------|
| HCS301 | KeeLoq 64-bit | 66 бит | гаражи, ворота |
| HCS360 | KeeLoq | 69 бит | авто |
| HCS200 | KeeLoq | 66 бит | брелоки |

По длине кадра (66 бит) и наличию открытого serial можно определить, что перед нами именно HCS-серия, и сверяться с даташитом Microchip при разборе битов.

## Если не сработало

- **Пытаться replay rolling-кода.** Не сработает и сдвинет счётчик жертвы. Сначала убедитесь, что код фиксированный.
- **Путать code grabbing и RollJam.** Code grabbing работает только для фиксированных кодов или в очень узком окне; RollJam — активная атака с глушением.
- **Неверная частота/модуляция.** HCS301 — OOK/ASK, 433.92 МГц (иногда 315/868).
- **Игнорировать синхронизацию.** Если брелок «убежал» вперёд, понадобится пересинхронизация.
- **Слабый ключ не гарантирован.** Многие производители перешли на AES-128 challenge-response — там KeeLoq-атаки не работают.

## Почему окно — это компромисс, а не дыра

Важно понять логику проектировщика: окно приёма добавляют не по недосмотру, а потому что радиоканал ненадёжен. Нажатие может не дойти (помеха, далеко, севшая батарейка), и если приёмник требовал бы строго «следующий код», любой пропуск навсегда ломал бы пару. Поэтому приёмник принимает не только +1, но и несколько значений вперёд, а сам «перепрыгивает» на принятый. Плата за устойчивость — окно, в которое можно втиснуть ранее записанный код. Именно поэтому RollJam не ломает криптографию: он эксплуатирует саму логику синхронизации.

## Шаг 6: десинхронизация вживую

Проще всего увидеть проблему так: приёмник хранит счётчик N. Пока вы глушите сигнал, брелок увеличивает свой счётчик при каждом нажатии, но приёмник их не видит. Через 20 нажатий брелок на N+20, а приёмник всё ещё ждёт окно [N+1..N+16]. Код с брелока теперь за пределами окна — дверь не открывается. Пользователь думает, что брелок сломался, и жмёт ещё. Часто система спасается тем, что при удержании или двойном нажатии брелок передаёт «resync»-последовательность, по которой приёмник сдвигает окно. Для атакующего это означает: кратковременный джем — это DoS, а не доступ, и пользователь восстановится сам.

## Частые вопросы

**Чем фиксированный код отличается от rolling на практике?**
Фиксированный код одинаков при каждом нажатии — его достаточно записать и повторить. Rolling меняется, поэтому перехвата одного кадра мало. Проверить тип просто: `rtl_433` покажет, меняется ли поле `code` при повторных нажатиях.

**Можно ли отличить RollJam от простого глушения?**
Да, по поведению: при глушении жертва жмёт несколько раз, но код не воспроизводится. RollJam сначала собирает два кода, а потом воспроизводит один из них — то есть в какой-то момент приёмник получает валидный «следующий» код, которого сам брелок в этот момент не слал.

**Работают ли эти атаки на современные авто?**
На старые HCS-системы (гаражи, шлагбаумы, сигнализации 2000-х) — да. Современные автомобили используют challenge-response: приёмник шлёт случайное число, брелок подписывает его AES-128 секретным ключом. Там ни replay, ни RollJam не работают, потому что каждый ответ уникален и привязан к запросу.

**Что делать для защиты?**
Переходить на challenge-response с AES, не использовать слабые или утекшие manufacturer keys, применять side-channel-устойчивые реализации (маскирование), а для критичных объектов — дублировать радио-доступ вторым фактором (PIN, мобильное приложение).

**Почему manufacturer key так важен?**
В KeeLoq секрет складывается из двух частей: общего для всех устройств производителя manufacturer key и уникального device key. Если manufacturer key утёк (а его не раз извлекали из прошивок и публиковали), то у атакующего остаётся перебрать только 32-битный device key — это часы-дни на GPU вместо невозможного перебора 64 бит. Поэтому утечка «общего» ключа обесценивает всю линейку устройств одного производителя.

## Что мы теперь знаем

1. Rolling code меняет значение при каждом нажатии; replay старого отвергается.
2. Окно приёма нужно для устойчивости к потерям, но именно оно даёт RollJam.
3. KeeLoq — 64-битный блочный шифр; слабость в manufacturer/device key.
4. RollJam — активная атака с глушением и захватом двух кодов.
5. Современные системы уходят на challenge-response с AES.
