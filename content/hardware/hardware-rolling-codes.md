Когда производитель брелока понимает, что фиксированный код можно записать и повторить, он добавляет rolling code: при каждом нажатии передаётся новое значение, а приёмник принимает только «следующие» коды из окна. Простейший replay перестаёт работать. Но rolling code — не серебряная пуля: у него есть слабости в синхронизации, а алгоритм KeeLoq, десятилетиями стоявший в автосигнализациях и воротах, поддаётся криптоанализу при слабых ключах.

В этом уроке мы разберём анатомию rolling code, устройство KeeLoq (блочный шифр на 528-битном ключе), атаки десинхронизации и RollJam, а также инструменты для работы с ними. Отдельно — как отличить rolling code от фиксированного и что делать в каждом случае.

## Как работает rolling code

Брелок и приёмник имеют общий счётчик (или генератор последовательности). При нажатии брелок увеличивает счётчик, шифрует его (или хэширует с секретом) и передаёт результат вместе с частью открытых бит. Приёмник хранит последнее принятое значение и проверяет, что приходящий код — «следующий» в допустимом окне впереди.

Окно нужно потому, что нажатия могут «теряться» (помехи, дальность). Если бы приёмник принимал строго +1, любое потерянное нажатие рассинхронизировало бы пару. Поэтому окно, например, от +1 до +16: принимаются коды в этом диапазоне, а счётчик «прыгает» вперёд. Отсюда классические проблемы:

- **Replay старого кода** отвергается (он позади счётчика).
- **Захват одного кода** бесполезен — нужно воспроизвести код, который приёмник ещё не видел.
- **Десинхронизация** — если злоумышленник перехватит и «съест» несколько нажатий, легитимный брелок уйдёт далеко вперёд, и пользователь будет вынужден синхронизировать заново (обычно двойным нажатием). Это и эксплуатирует RollJam.

## KeeLoq: устройство алгоритма

KeeLoq — блочный шифр, разработанный для Microchip HCS-серии (HCS301, HCS360, HCS200). Ключ — **64 бита** (в HCS хранится 64-битный «manufacturer key» + 32-битный «device key» + serial), но блок и раунды устроены так, что эффективная стойкость зависит от реализации. Алгоритм нелинейный, с 528 раундами (528-битный внутренний регистр), работает побитово — каждый такт сдвигает регистр и применяет нелинейную функцию NLF.

Кадр HCS301: 66 бит, из которых 32 — зашифрованная часть (hopping code), 28 — serial number, 4 — статус (батарея, кнопки), плюс guard-биты. Передаётся по OOK/ASK на 433 МГц. Важно: **hopping code** — это результат KeeLoq-шифрования счётчика, а serial — открытый, поэтому приёмник находит пару по serial и проверяет код.

Криптостойкость KeeLoq:
- Полный 64-битный ключ перебрать нельзя.
- Но реальные реализации используют **слабые ключи**: manufacturer keys утекали из прошивок, а device keys иногда выводятся из серийного номера. Если manufacturer key известен (а для ряда производителей он опубликован/утечён), остаётся 32-битный device key — перебор на GPU за часы/дни.
- Есть атаки: **slide attacks**, **algebraic attacks**, **guess-and-determine**, **side-channel** (по питанию/ЭМИ при шифровании в микроконтроллере).

## Криптоанализ KeeLoq на практике

Полный путь восстановления ключа брелока:
1. **Собрать пары (plaintext, ciphertext)**. Нужны известные пары «счётчик → hopping code». Собрать их можно, перехватывая множество нажатий: зная serial и предполагая, что счётчик начинается с 0 при выпуске, можно построить пары для малых значений.
2. **Знать manufacturer key** (или перебрать слабый). Если у вас есть device key из прошивки — вообще всё просто.
3. **Перебрать device key** на GPU (hashcat-подобные реализации KeeLoq), проверяя по собранным парам.
4. **Воспроизвести** код для нужного счётчика — брелок скомпрометирован навсегда.

Инструменты: `keeloq` (эталонные реализации), GPU-крекеры (специализированные KeeLoq-cracker'ы), `flipper` с модулем KeeLoq (для некоторых серий), side-channel стенд (ChipWhisperer) для атак по питанию.

## Инструменты и команды

```bash
# --- rtl_433: перехват HCS/Keeloq брелоков 433 МГц ---
rtl_433 -f 433.92M -A -F json | tee hcs.json

# --- анализ: собрать hopping codes и serial ---
jq -r 'select(.model) | [.id, .code] | @tsv' hcs.json | sort -u

# --- Flipper Zero: Sub-GHz → Read → Save, затем Replay ---
# (для rolling-кодов прямой replay не сработает — только фиксируем)

# --- URH (Universal Radio Hacker): разбор модуляции и битов ---
urh capture.iq

# --- rfcat (CC1101): передача сырых кадров ---
rfcat -r
>>> d.setFreq(433920000); d.setMdmModulation(MOD_ASK_OOK)
>>> d.RFxmit(b'\xAA\xBB\xCC...')
```

Для side-channel: **ChipWhisperer** + `chipwhisperer` Python-API; для GPU-перебора — специализированные KeeLoq-крекеры (например, на OpenCL/CUDA). Эталонный KeeLoq легко реализуется на C/Python (известный код из публикаций Garcia и др.).

## Разобранный пример: десинхронизация и захват

Дано: автосигнализация с брелоком на rolling code (HCS301), 433.92 МГц.

**Шаг 1 — приём.** Записываем несколько нажатий:

```bash
rtl_433 -f 433.92M -A -F json | tee hcs.json
# {"model":"HCS301","id":1234567,"code":18324521,...}
# {"model":"HCS301","id":1234567,"code":87654321,...}   <- меняется
```

Код меняется при каждом нажатии → rolling code.

**Шаг 2 — подтверждение.** Пробуем replay последнего кода (Flipper Replay). Не срабатывает → приёмник отверг старый код.

**Шаг 3 — RollJam.** Глушим частоту и записываем ДВА кода жертвы (жертва жмёт дважды, думая, что не сработало). Уходим с первым кодом, ждём, пока жертва уйдёт, и воспроизводим один из записанных — приёмник примет его как «следующий». Для этого нужны два радио (глушилка + приёмник) или Flipper с дополнительным модулем.

**Шаг 4 — вывод.** Если ключ недоступен, RollJam — единственный рабочий путь. Если manufacturer/device key извлечены из прошивки — генерируем код напрямую и обходим синхронизацию.

## Атаки на rolling code

| Атака | Условие | Результат |
|-------|---------|-----------|
| Replay старого кода | нет | отвергается |
| RollJam | нужен захват двух кодов + глушение | открытие |
| Code grabbing | реальное время | иногда |
| Десинхронизация | перехват нескольких нажатий | пользователь пересинхронизирует |
| Key recovery (KeeLoq) | слабый ключ / утечка | полный контроль |
| Side-channel | физический доступ к брелоку | извлечение ключа |
| Jamming | всегда | DoS, но не доступ |

## Частые ошибки и подводные камни

- **Пытаться replay rolling-кода.** Это не сработает и сдвинет счётчик жертвы. Сначала убедитесь, что код фиксированный.
- **Путать code grabbing и RollJam.** Code grabbing работает только для фиксированных кодов или в очень узком окне; RollJam — активная атака с глушением.
- **Неверная частота/модуляция.** HCS301 — OOK/ASK, 433.92 МГц (иногда 315/868). FSK — другая серия.
- **Правовые риски.** Глушение и открытие чужих ворот/авто — преступление. Работайте на своём оборудовании.
- **Игнорировать синхронизацию.** Если брелок «убежал» далеко вперёд, понадобится пересинхронизация (двойное нажатие) — учтите это в атаке.
- **Слабый ключ не гарантирован.** Многие производители перешли на AES-128 challenge-response; там KeeLoq-атаки не работают.

## Что дальше / решение

Развитие темы: (1) отработайте side-channel атаку на KeeLoq через ChipWhisperer на учебной плате; (2) соберите GPU-крекер device key для известного manufacturer key; (3) изучите современные схемы (AES-128 challenge-response, Texas Instruments, NXP HITAG) и убедитесь, что они не ломаются replay. Для защиты: уходите от KeeLoq к challenge-response с AES, не используйте дефолтные/общие manufacturer keys, обновляйте прошивки брелоков, где возможно. В авторизованном пентесте документируйте модель брелока, тип кодирования и применимость RollJam — это и есть результат оценки.

## Практический стенд и OPSEC

Чтобы отрабатывать rolling code безопасно и воспроизводимо, соберите изолированный стенд. Минимальный набор: приёмник-приёмник на базе RTL-SDR (для пассивного наблюдения), передатчик на HackRF или плата CC1101/CC1111 под управлением `rfcat`, и учебный брелок/приёмник, который вы вправе вскрывать (например, комплект «шлагбаум-конструктор» или старый брелок от собственного гаража). Никогда не тестируйте на чужом оборудовании без письменного разрешения: открытие чужих ворот и авто — уголовно наказуемо, а глушение (jamming) регулируется законом о радиочастотах.

Порядок работы на стенде:

1. **Инвентаризация.** Зафиксируйте модель брелока и приёмника, частоту (433.92 МГц чаще всего), модуляцию (OOK/ASK для HCS301), тип кодирования.
2. **Пассивный сбор.** Запишите 10-20 нажатий, сохраните hopping codes и serial. Убедитесь, что код меняется (иначе это фиксированный код, и вся ветка KeeLoq неактуальна).
3. **Определение алгоритма.** По длине кадра (66 бит), наличию serial и структуре битов определите, HCS301 это или другая серия. Сверьтесь с даташитом Microchip.
4. **Оценка ключа.** Проверьте, не используется ли дефолтный или общеизвестный manufacturer key; при наличии прошивки брелока — поищите device key.
5. **Модель атаки.** Только после этого выбирайте между RollJam (если ключ недоступен) и прямой генерацией кода (если ключ извлечён).

Журналируйте каждый шаг: записанные кадры, serial, гипотезы о ключе, результаты. В отчёте пентеста ценность представляет не «мы открыли ворота», а воспроизводимая цепочка доказательств: тип кодирования → собранные пары → восстановленный/не восстановленный ключ → применимая атака. Отдельно отметьте правовые рамки и то, что активные атаки (RollJam, jamming) проводились только в лабораторных условиях. Для защиты дайте заказчику конкретику: перейти на challenge-response с AES-128, не использовать общий manufacturer key, обновлять прошивку брелоков и приёмников, а для критичных объектов добавить второй фактор (PIN, смартфон).
