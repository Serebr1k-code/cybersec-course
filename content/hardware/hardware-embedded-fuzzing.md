## Вопрос, с которого всё начинается

Мы умеем распаковывать прошивку и запускать её сервисы. Но чтение кода руками в дизассемблере — медленное занятие: чтобы найти уязвимость, надо вручную разобрать функции парсера. А что, если поручить поиск падений компьютеру?

Так работает **фаззинг**: программа сама подаёт на вход тысячи случайных и полуосмысленных данных и следит, где сервис упадёт. Разберём это на бинарнике из нашей прошивки роутера.

## Наш пример: бинарник cfgmgr

В корневой системе роутера есть бинарник `usr/sbin/cfgmgr` — программа, которая читает файл конфигурации. Парсеры конфигов — классическая цель: они разбирают внешние данные, и ошибка в них означает уязвимость. Цель: найти в нём падение и понять, опасно ли оно.

## Шаг 1: определяем архитектуру и пробуем запустить

Первым делом узнаём, для какого процессора собран бинарник:

```
$ file squashfs-root/usr/sbin/cfgmgr
squashfs-root/usr/sbin/cfgmgr: ELF 32-bit LSB executable, MIPS, MIPS32, dynamically linked
```

Это MIPS — на нашем x86-компьютере такой файл не запустится напрямую. Нужен **эмулятор** `qemu-user`, который переводит команды одной архитектуры в другую. Запускаем через `chroot` (сделать rootfs «корнем» системы):

```
$ sudo cp /usr/bin/qemu-mips-static squashfs-root/usr/bin/
$ sudo chroot squashfs-root /usr/bin/qemu-mips-static /usr/sbin/cfgmgr
cfgmgr: can't load library 'libc.so.0'
```

Ошибка: программа не нашла свою библиотеку `libc`. Даже с `chroot` интерпретатор иногда ищет библиотеки не там. Решение — явно указать префикс флагом `-L`:

```
$ qemu-mips -L ./squashfs-root ./squashfs-root/usr/sbin/cfgmgr
usage: cfgmgr <config-file>
```

Теперь бинарник запустился и даже подсказал, как его вызывать. Мы готовы фаззить.

## Шаг 2: готовим seed'ы

Фаззеру нужны начальные входные данные, **seed'ы** — примеры правильного ввода, от которых он будет мутировать. Возьмём реальные конфиги из прошивки:

```
$ mkdir -p seeds out
$ cp squashfs-root/etc/config/* seeds/
$ ls seeds/
network  wireless  dhcp
```

Без хороших seed'ов фаззер почти не покрывает код — это как искать клад с завязанными глазами.

## Шаг 3: запускаем AFL++

`AFL++` — популярный фаззер. Поскольку исходников у нас нет, используем **QEMU-режим** (флаг `-Q`): он запускает бинарник под особым, инструментированным QEMU, который считает покрытие кода.

```
$ AFL_QEMU_ARCH=mips afl-fuzz -Q -i seeds/ -o out/ -m none -t 2000 -- \
    ./qemu-mips -L ./squashfs-root ./squashfs-root/usr/sbin/cfgmgr @@
american fuzzy lop ++4.10
[+] Found 3 initial seeds
[+] Fuzzing... exec speed: 850/s
```

`-i` — папка с seed'ами, `-o` — куда писать результаты, `-m none` — снять лимит памяти (MIPS-эмуляции нужно много), `@@` — место, куда фаззер подставляет входной файл. Фаззер погнал: сотни запусков в секунду.

## Шаг 4: находим краш

Фаззер складывает падения в подпапку `crashes`:

```
$ ls out/default/crashes/
id:000000,sig:11,src:000002,time:12345,execs:98765,op:havoc,rep:4
```

`sig:11` — это сигнал `SIGSEGV`, то есть программа обратилась к несуществующей памяти и упала. Воспроизведём вручную:

```
$ ./qemu-mips -L ./squashfs-root ./squashfs-root/usr/sbin/cfgmgr out/default/crashes/id:000000...
Segmentation fault
```

Падение стабильно воспроизводится. Но само по себе падение — ещё не уязвимость: надо понять, контролируем ли мы выполнение.

## Шаг 5: триажим краш в отладчике

Запускаем бинарник под отладчиком `gdb-multiarch` через удалённую отладку QEMU:

```
$ qemu-mips -g 1234 -L ./squashfs-root ./squashfs-root/usr/sbin/cfgmgr crash_input &
$ gdb-multiarch ./squashfs-root/usr/sbin/cfgmgr
(gdb) target remote :1234
(gdb) c
Program received signal SIGSEGV
(gdb) info registers
ra: 0x41414141
```

Ключевая строка — `ra: 0x41414141`. Регистр `ra` (адрес возврата) содержит `0x41414141` — это байты `AAAA` из нашего ввода. Значит, переполнение позволило перезаписать адрес возврата нашими данными. Такое падение **эксплуатируемо**: подобрав адрес, атакующий может выполнить свой код. Это уже не просто DoS.

## Шаг 6: если нужно фаззить сетевой сервис

Одного бинарника мало, если демон зависит от сети и NVRAM. Тогда запускают всю прошивку целиком через **FirmAE** (обёртка над эмулятором целой машины):

```
$ sudo ./run.sh -c router -a mips firmware.bin
[+] Network: 192.168.0.1
```

Устройство получает IP, и дальше можно фаззить его веб-интерфейс с хоста или писать **harness** — маленькую программу, которая передаёт запросы в целевой парсер. Harness нужен, когда мы фаззим конкретную функцию, а не весь демон.

## Что мы теперь знаем

По-простому:

1. Фаззинг автоматизирует поиск падений, подавая тысячи входов.
2. Встраиваемый бинарник запускается на хосте через `qemu-user` (флаг `-L` для библиотек).
3. Seed'ы — примеры правильного ввода — обязательны для покрытия кода.
4. AFL++ в режиме `-Q` фаззит бинарник без исходников.
5. Падение опасно, если регистр возврата/PC содержит байты из ввода (потенциальный RCE).

## Как это выглядит целиком

Маршрут в одну историю: `file` показывает MIPS-бинарник, `qemu-mips -L ./squashfs-root` запускает его (после подсказки `usage:`). Собираем seed'ы из реальных конфигов и гоняем `afl-fuzz -Q -i seeds/ -o out/ -m none`. Фаззер складывает `sig:11` в `crashes/`, воспроизводим вручную, затем в `gdb-multiarch` видим `ra: 0x41414141` — байты нашего ввода в адресе возврата. Значит, это не просто DoS, а потенциальный RCE. Вся цепочка: запустить → засеять → фаззить → воспроизвести → триажить.

## На что смотреть дальше

- **`can't load library`.** Скопируйте `libc`/`ld` или используйте `chroot`/`-L`.
- **Не тот QEMU.** Для MIPS little-endian нужен `qemu-mipsel`, для big-endian — `qemu-mips`.
- **Нет seed'ов.** AFL топчется на месте — дайте реальные конфиги и запросы.
- **`-m` слишком мал.** MIPS-эмуляция требует памяти; ставьте `-m none`.
- **Любой краш ≠ уязвимость.** Триаж обязателен: без контроля регистров это лишь DoS.

## Если не сработало

- **Бинарник не стартует.** Скопируйте `libc`/`ld` или укажите `-L`; проверьте эндианность.
- **AFL не растёт.** Дайте реальные seed'ы — с пустого входа покрытие почти нулевое.
- **Краш не воспроизводится.** Включите детерминизм (`AFL_NO_AFFINITY=1`, фиксированный вход).
- **Падение, но регистры чистые.** Скорее всего DoS, а не RCE — триаж обязателен.

## Куда дальше

Мы научились автоматически находить уязвимости в бинарниках прошивки. Дальше в ветке — атака на сетевую сторону IoT-устройств: какие сервисы они открывают и как их эксплуатируют. А пока запомни главное: фаззинг превращает ручной поиск падений в автоматический, но найденное падение ещё нужно проверить на эксплуатируемость.
