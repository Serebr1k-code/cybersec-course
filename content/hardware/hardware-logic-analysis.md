## Вопрос, с которого всё начинается

В прошлых уроках мы нашли на плате интерфейсы — UART, SPI, I2C. Но знать, что шина есть, и понимать, что по ней передаётся, — разные вещи. Как увидеть байты, которыми обменивается процессор с флеш-памятью?

Ответ — **логический анализатор**: прибор, который записывает состояние линий (0/1) во времени и декодирует протоколы.

## Наш пример: SPI-флеш на плате роутера

Перед нами плата роутера. К чипу флеш-памяти подключены четыре линии (CLK, MOSI, MISO, CS) и земля. Мы хотим понять, что загрузчик читает из флеш при старте.

## Шаг 1: анализатор vs осциллограф

Логический анализатор отличается от осциллографа: он оцифровывает сигнал в порог (0 или 1) с высокой частотой дискретизации, а не показывает аналоговую форму. Для цифровых протоколов этого достаточно.

| Параметр | Что значит | Практика |
|----------|-----------|----------|
| Частота дискретизации | сколько раз в секунду читается линия | минимум 4–10× быстрее линии |
| Число каналов | сколько линий пишем | 8 хватает для SPI + CS + reset |
| Порог (threshold) | уровень, выше которого = 1 | 3.3 В / 1.8 В — под плату |
| Глубина памяти | сколько времени влезает | компромисс: долго или часто |
| Триггер | условие старта записи | ловить редкие события |

Осциллограф показывает форму (амплитуду, фронты, шум), анализатор — только логические уровни. Для «есть ли сигнал» годится осциллограф, для «какие байты» — анализатор.

## Шаг 2: инструменты

- **Saleae Logic** — коммерческий, лучший софт, но дорого.
- **sigrok + PulseView** — открытый стек, поддерживает дешёвые клоны ($10–20), много декодеров.
- **sigrok-cli** — консольная часть, удобна для скриптов.
- **DSLogic / Kingst** — средний класс, совместимы с sigrok.

```bash
$ sudo apt install sigrok pulseview sigrok-firmware-fx2lafw
$ sigrok-cli --list-supported | grep -i "logic"
$ sigrok-cli --list-protocol-decoders
```

## Шаг 3: припаиваемся

Подключаемся к тест-поинтам или ножкам чипа: GND → любой GND платы, CLK/MOSI/MISO/CS → каналы D0..D3. Питание платы лучше подать штатно. **GND подключается первым делом** — без общего провода сигнал «плавает».

## Шаг 4: захватываем при включении

Ставим частоту 4 МГц (SPI-флеш на старте медленная), глубину — до 1 секунды. Подаём питание, ловим первые команды:

```bash
$ sigrok-cli --driver fx2lafw --config samplerate=4m \
    --channels D0,D1,D2,D3 --time 1s -o boot.sr
```

## Шаг 5: декодируем SPI

Назначаем линии: CS=D3, CLK=D0, MOSI=D1, MISO=D2, режим 0.

```bash
$ sigrok-cli -i boot.sr \
    --protocol-decoder spi:clk=D0:mosi=D1:miso=D2:cs=D3:cs_polarity=active-low \
    -A spi=mosi-data,miso-data
```

Читаем результат: первые байты — `9F` (JEDEC ID, запрос модели чипа), затем `03` (Read) с адресом. Видим, что загрузчик читает регион с адреса `0x000000` — там обычно таблица векторов. Это ориентир для дальнейшего дампа.

## Шаг 6: сохраняем декодированные байты

Для последующего анализа пишем бинарный поток в файл:

```bash
$ sigrok-cli -i boot.sr \
    --protocol-decoder spi:clk=D0:mosi=D1:miso=D2:cs=D3 \
    -B spi=miso-data > read.bin
$ binwalk read.bin
```

Так перехваченный обмен превращается в файл, который можно разбирать обычными инструментами.

## Шаг 7: тот же приём для I2C

У чипа 24Cxx рядом с процессором — две линии (SDA, SCL) и подтяжки к питанию:

```bash
$ sigrok-cli --driver fx2lafw --config samplerate=1m \
    --channels D0,D1 --time 1s -o i2c.sr
$ sigrok-cli -i i2c.sr --protocol-decoder i2c:sda=D0:scl=D1 -A i2c=address-read,data-read
```

Видим адрес устройства (`0x50` для EEPROM) и поток данных. Адрес `0x50` говорит, что это 24Cxx — дальше читаем даташит и при необходимости дампим содержимое.

## Шаг 8: триггер и глубина памяти

Без триггера анализатор пишет буфер до события, и можно пропустить нужный кадр. Триггер запускает запись по условию:

```bash
$ sigrok-cli --driver fx2lafw --config samplerate=4m --channels D0,D1,D2,D3 \
    --trigger D3=r --time 0.5s -o spi.sr
```

`D3=r` — сработать по переднему фронту CS (начало транзакции SPI). Дешёвые анализаторы имеют фиксированную память, делимую между частотой и временем: выше частота — короче окно. Поэтому для длительных процессов используют триггер, а не пишут всё подряд.

## Шаг 9: декодируем UART тем же прибором

Анализатор пригодится и для UART, если консоль закрыта, но шина доступна. Назначаем канал TX и скорость:

```bash
$ sigrok-cli -i uart.sr --protocol-decoder uart:rx=D0:baudrate=115200 -A uart=rx-data
```

Декодер покажет текст, который устройство печатает при загрузке. Часто там оказываются версия прошивки, имена сервисов и даже отладочные сообщения — ценная разведка без подключения к консоли.

**Проверка гипотезы.** Если декодер выдаёт мусор, включите отображение сырых переходов и вручную проверьте несколько байт: корректный UART-текст виден глазом, а корректный SPI начинается с известных команд (`0x9F`/`0x03` для флеш). Это быстрая проверка правильности назначения каналов.

## Что мы теперь знаем

1. Логический анализатор оцифровывает линии в 0/1 и декодирует протоколы.
2. Частота дискретизации — минимум 4–10× частоты линии; порог — около половины питания.
3. GND подключается первым; без него сигнал «плавает».
4. sigrok/PulseView поддерживает UART, SPI, I2C, 1-Wire, CAN и десятки других декодеров.
5. Триггер ловит редкие события вместо записи всего подряд.
6. Декодированные байты (`-B`) сохраняются в `.bin` для `binwalk`/`strings`.

## На что смотреть дальше

- **Слишком низкая частота дискретизации.** Линия 10 МГц при записи 1 МГц = мусор. Правило: ≥4× частоты линии.
- **Неправильный порог.** Плата 1.8 В, порог 3.3 В — анализатор не увидит переключений.
- **Перепутаны каналы.** MOSI/MISO легко поменять; симптом — «все FF». Сверяйтесь с даташитом.
- **Забыли про триггер.** Буфер заполнится до события.
- **Пассивное чтение под напряжением.** Не подавайте 5 В на вход 3.3-вольтового анализатора.
