Логический анализатор — «мультиметр для цифровых сигналов»: он записывает состояние линий (0/1) во времени и позволяет декодировать протоколы. Это базовый навык для реверса любого устройства: пока вы видите байты на шине, вы понимаете, что делает прошивка. Урок закрывает разрыв между «нашёл UART/SPI/I2C» и «прочитал данные с шины».

## Теория

Логический анализатор отличается от осциллографа: он оцифровывает сигнал в порог (0 или 1) с высокой частотой дискретизации, а не показывает аналоговую форму. Этого достаточно для цифровых протоколов.

Ключевые параметры:

| Параметр | Что значит | Практика |
|----------|-----------|----------|
| Частота дискретизации | сколько раз в секунду читается линия | минимум 4–10× быстрее самой быстрой линии в шине |
| Число каналов | сколько линий пишем одновременно | 8 достаточно для SPI + chip select + reset |
| Порог (threshold) | уровень, выше которого = 1 | 3.3 В / 1.8 В — подбирается под целевую плату |
| Глубина памяти | сколько времени влезает | на дешёвых — компромисс: либо долго, либо часто |
| Триггер | условие старта записи | ловить редкие события (например, первую команду) |

Что можно декодировать «из коробки» в sigrok/PulseView: UART, SPI, I2C, 1-Wire, JTAG, SWD, CAN, LIN, RS-232/485, Manchester, DMX, PS/2, USB (низкоскоростной), SD/MMC, а также десятки других. Список декодеров — главный аргумент за sigrok: он открытый и расширяемый на Python.

**Разница между анализатором и осциллографом:** осциллограф показывает форму (амплитуда, фронты, шум), анализатор — только логические уровни. Для «есть ли сигнал вообще» годится осциллограф; для «какие байты» — анализатор. На практике часто нужны оба.

## Инструменты и команды

- **Saleae Logic / Logic 8** — коммерческий, лучший софт, но дорого. Проприетарный формат `.sal`.
- **sigrok + PulseView** — открытый стек, поддерживает дешёвые клоны (8/16 каналов за $10–20), множество декодеров.
- **sigrok-cli** — консольная часть, удобна для скриптов.
- **DSLogic / Kingst** — средний класс, совместимы с sigrok.
- **Осциллограф** — для проверки наличия/формы сигнала до захвата.

```bash
# Установка sigrok на Debian/Ubuntu
sudo apt install sigrok pulseview sigrok-firmware-fx2lafw

# Список поддерживаемых устройств
sigrok-cli --list-supported | grep -i "logic"

# Простой захват 2 секунд по 4 каналам на частоте 1 МГц в файл
sigrok-cli --driver fx2lafw --config samplerate=1m --channels D0,D1,D2,D3 \
  --time 2s -o capture.sr

# Декодирование UART в консоль
sigrok-cli -i capture.sr --protocol-decoder uart:rx=D0 -A uart=rx-data

# Показать список доступных декодеров
sigrok-cli --list-protocol-decoders

# Проверить конкретный декодер и его опции
sigrok-cli -P uart:help
```

В PulseView: подключаете устройство, выбираете частоту, каналы, жмёте Run, затем `Add protocol decoder` → выбираете декодер → назначаете каналы → читаете декодированные байты в отдельной панели.

## Полезные флаги sigrok-cli

| Флаг | Назначение |
|------|-----------|
| `--driver <name>` | драйвер устройства (`fx2lafw`, `demo`, `saleae-logic16`) |
| `--config samplerate=4m` | частота дискретизации |
| `--channels D0,D1` | какие каналы писать |
| `--time 2s` | длительность захвата |
| `--samples 1000000` | число сэмплов (вместо времени) |
| `--trigger D0=r` | триггер (r = rising) |
| `-o file.sr` | сохранить захват |
| `-i file.sr` | читать захват |
| `--protocol-decoder spi:...` | декодер и назначение линий |
| `-A spi=mosi-data` | аннотации декодера в вывод |
| `-B spi=mosi-data` | вывод декодированного потока в бинарный файл |
| `-P <decoder>:help` | справка по декодеру |

## Разобранный пример: снимаем обмен с SPI-флеш на плате роутера

**Дано:** плата с чипом флеш, к которой подключены 4 линии (CLK, MOSI, MISO, CS) и выводы GND. Нужно понять, что читается из флеш.

**Шаг 1 — припаиваемся.** К аккуратным тест-поинтам или к ножкам чипа: GND → любой GND платы, CLK/MOSI/MISO/CS → каналы D0..D3. Питание платы не обязательно подавать: многие SPI-флеш отвечают в пассивном режиме при чтении, но лучше подать питание штатно.

**Шаг 2 — захват при включении.** Ставим частоту 4 МГц (SPI-флеш обычно до 50 МГц, но на старте медленно), глубина — до 1 секунды. Подаём питание, ловим первые команды.

```bash
sigrok-cli --driver fx2lafw --config samplerate=4m \
  --channels D0,D1,D2,D3 --time 1s -o boot.sr
```

**Шаг 3 — декодируем SPI.** Назначаем CS=D3, CLK=D0, MOSI=D1, MISO=D2, режим 0.

```bash
sigrok-cli -i boot.sr \
  --protocol-decoder spi:clk=D0:mosi=D1:miso=D2:cs=D3:cs_polarity=active-low \
  -A spi=mosi-data,miso-data
```

**Шаг 4 — читаем команды.** Первые байты — `9F` (JEDEC ID), затем `03` (Read) с адресом. Видим, что загрузчик читает регион с адреса `0x000000` — там обычно таблица векторов. Это ориентир для дальнейшего дампа.

**Шаг 5 — что делать с результатом.** Декодированные байты складываем в `.bin` (через `sigrok-cli -A ... -B spi=...` в бинарный файл), затем `binwalk`/`strings` для анализа содержимого.

```bash
sigrok-cli -i boot.sr \
  --protocol-decoder spi:clk=D0:mosi=D1:miso=D2:cs=D3 \
  -B spi=miso-data > read.bin
binwalk read.bin
```

## Разобранный пример: перехват I2C-EEPROM

**Дано:** чип 24Cxx рядом с SoC, две линии (SDA, SCL) и подтяжки к Vcc.

```bash
# Захват 1 секунда, 1 МГц
sigrok-cli --driver fx2lafw --config samplerate=1m \
  --channels D0,D1 --time 1s -o i2c.sr
# Декодируем I2C: SDA=D0, SCL=D1
sigrok-cli -i i2c.sr --protocol-decoder i2c:sda=D0:scl=D1 -A i2c=address-read,data-read
```
Видим адрес устройства (например, `0x50` для EEPROM) и поток данных. Адрес 0x50 говорит, что это 24Cxx — дальше читаем даташит и, при необходимости, дампим содержимое.

## Частые ошибки

- **Слишком низкая частота дискретизации.** Если линия на 10 МГц, а вы пишете 1 МГц — байты будут мусором. Правило: ≥4× частоты линии.
- **Неправильный порог.** Плата 1.8 В, а порог выставлен на 3.3 В — анализатор не увидит переключений. Ставьте порог около половины Vcc.
- **Не подключён общий GND.** Без общего провода сигнал «плавает», декодирование ломается. GND — первым делом.
- **Перепутаны каналы.** MOSI/MISO легко поменять; симптом — «все FF» или бессмысленные данные. Сверяйтесь с даташитом чипа.
- **Земляные петли и наводки.** Длинные провода = наводки. Держите их короткими, а частоту дискретизации разумной.
- **Пассивное чтение под напряжением.** Не подавайте 5 В на вход 3.3-вольтового анализатора — спалите вход.
- **Забыли про триггер.** Без триггера буфер заполняется до события. Ставьте триггер на первую команду/фронт CS.

## Триггеры и глубина памяти на практике

Без триггера анализатор пишет буфер до события, и вы можете пропустить нужный кадр. Триггер запускает запись по условию:

```bash
# Захват по фронту CS (начало транзакции SPI)
sigrok-cli --driver fx2lafw --config samplerate=4m --channels D0,D1,D2,D3 \
  --trigger D3=r --time 0.5s -o spi.sr

# Триггер по уровню (ждущий режим): ждать низкий уровень
sigrok-cli --driver fx2lafw --config samplerate=1m --channels D0 \
  --trigger D0=l --time 1s -o uart.sr
```

**Глубина vs частота.** Дешёвые анализаторы (fx2lafw, 8 каналов) имеют фиксированную память, делимую между частотой и временем: выше частота — короче окно. Для длительных процессов используйте триггер, чтобы поймать событие, а не писать всё подряд.

**Декодирование потоком (streaming).** На устройствах с потоковым режимом (DSLogic, Saleae) можно писать долго на высокой частоте. Проверьте поддерживаемые режимы: `sigrok-cli --list-supported | grep -A5 <device>`.

**Аннотации vs бинарный вывод.** `-A <decoder>=<annotation>` печатает человекочитаемые аннотации; `-B <decoder>=<annotation>` пишет бинарный поток. Для разбора протокола удобнее `-A`, для последующего анализа — `-B` в файл.

**Синхронизация с другими инструментами.** Если нужен одновременный захват нескольких шин, используйте несколько каналов одного анализатора и общий GND. Для корреляции с прошивкой держите рядом лог UART.

**Проверка гипотезы.** Если декодер выдаёт мусор, включите отображение сырых переходов и вручную проверьте несколько байт: корректный UART «ASCII-текст» видно глазом, корректный SPI начинается с известных команд (0x9F/0x03 для флеш). Это быстрая проверка правильности назначения каналов.

## Что дальше / решение

- **Получили байты** → сохраните в `.bin`, прогоните `binwalk`/`strings`, определите структуру.
- **Мусор вместо данных** → поднимите частоту, проверьте порог и назначение каналов.
- **Сигнал есть, декодер молчит** → проверьте режим (CPOL/CPHA), полярность CS, скорость.
- **Нужен постоянный мониторинг** → используйте триггер и большую глубину памяти.
- **Провал** → `record_vector attempted`, зафиксируйте частоту/каналы и переходите к другому интерфейсу.
