## Вопрос, с которого всё начинается

В базовом уроке про смарт-карты мы научились читать данные командами APDU. Но карта — это полноценный защищённый микрокомпьютер с операционной системой, файловой системой и приложениями. Как заглянуть глубже и что там можно сломать?

Разберём внутреннее устройство: GlobalPlatform, Java Card и механизмы безопасности.

## Наш пример: карта JCOP

Перед нами карта с USB-ридером. Задача — определить, что за платформа внутри, и понять, какие механизмы её защищают. Начнём с «визитки» карты.

## Шаг 1: ATR — визитка карты

Карта — это защищённый микроконтроллер с криптосопроцессором, работающий по ISO 7816 (контакты) или ISO 14443 (бесконтакт). Внутри — операционная система (Java Card, MULTOS), файловая система и приложения (EMV, SIM, eID). Первое, что отдаёт карта, — **ATR** (Answer To Reset):

```
$ pcsc_scan
Reader ... ATR: 3B F8 13 00 00 81 31 FE 45 4A 43 4F 50 ...
```

`ATR` описывает карту при сбросе: по нему определяют платформу, а иногда даже партию. В примере видно `JCOP` — это популярная платформа Java Card от NXP.

## Шаг 2: обмен командами APDU

Обмен идёт **APDU**. Команда (**C-APDU**) выглядит как `CLA INS P1 P2 [Lc] [Data] [Le]`, а ответ (**R-APDU**) — как `[Data] SW1 SW2`, где `SW1SW2` это статус (`90 00` — успех, `6A 82` — файл не найден).

```
$ scriptor
> 00 A4 04 00 07 A0000000031010 00
< 6F ... 9000
```

Здесь `A4` — SELECT, `A0000000031010` — AID приложения. Всё взаимодействие с картой — от платежа до чтения eID — это последовательность APDU.

## Шаг 3: файловая система ISO 7816

Карта организована как дерево файлов: **MF** (master file) → **DF** (dedicated file, каталог) → **EF** (elementary file, данные). Файлы выбирают командой SELECT и читают через READ BINARY или READ RECORD:

```
> 00 A4 00 00 02 3F00   # SELECT MF
< 9000
> 00 B0 00 00 10        # READ BINARY, 16 байт
```

Ключи и сертификаты лежат в защищённых EF, и доступ к ним требует аутентификации (VERIFY PIN, EXTERNAL AUTHENTICATE).

## Шаг 4: GlobalPlatform и Secure Channel

**GlobalPlatform (GP)** — стандарт управления приложениями на карте: установка и удаление апплетов, управление ключами. GP-команды идут через **Secure Channel (SCP)** — защищённый канал, устанавливаемый по ключам (SCP01/02/03):

```
80 50 00 00 08 <host challenge> 00     # INITIALIZE UPDATE
84 82 <seq> <data>                     # EXTERNAL AUTHENTICATE
```

Первая команда передаёт карте челлендж, карта возвращает свой челлендж и криптограмму, вторая завершает аутентификацию. Если GP-ключи дефолтные или утекли, можно **установить свой апплет** на карту — это мощнейший вектор атаки.

## Шаг 5: Java Card и атаки на неё

**Java Card** позволяет загружать апплеты; **JCOP** — популярная платформа. Апплеты исполняются в песочнице, но исторически было много атак:

- **Fault injection** на проверках байткода;
- **Type confusion** в виртуальной машине карты;
- **Байткод-атаки** через специально сформированные апплеты;
- **Логические баги** апплетов — слабый PIN, отсутствие защиты от подбора.

Загрузка своего апплета через GP открывает возможность исследовать карту «изнутри».

## Шаг 6: атаки на PIN

PIN проверяется командой `VERIFY` (офлайн) или на хосте (онлайн):

```
> 00 20 00 80 08 <encrypted pin block>
< 9000          # верно
< 63Cx          # неверно, x попыток осталось
```

Обратите внимание на статусные слова: они сообщают **число оставшихся попыток**. Векторы атак: PIN bypass через логическую ошибку апплета, подбор при слабой защите, смена PIN без знания старого при ошибке прав, fault injection на сравнении.

## Шаг 7: персонализация и типовые ошибки

**Персонализация** — процесс «прошивки» карты: создание приложений, загрузка ключей, установка прав. Ошибки персонализации — частая причина уязвимостей:

- **дефолтные ключи**, не заменённые при выдаче;
- **одинаковые ключи** на всю партию;
- **слабые ключи** (короткие, предсказуемые);
- **лишние права** — файлы доступны без аутентификации.

При аудите полезно сравнить реально используемые ключи с дефолтными наборами платформы.

## EMV как приложение на карте

Платёжная карта — это Java Card с приложением платёжной системы (Visa/Mastercard). Логика оплаты выполняется прямо на карте: ридер шлёт команды, карта отвечает криптограммами.

```
00 A4 04 00 07 A0000000031010 00    # SELECT AID (Visa)
80 A8 00 00 02 83 00 00             # GET PROCESSING OPTIONS
00 B2 01 0C 00                      # READ RECORD
80 AE 80 00 ...                     # GENERATE AC
```

Атаки на EMV — **relay** (дистанционные платежи), **skimming**, подмена суммы и валюты, downgrade до магнитной полосы. Сами карты защищены криптограммой и CVM, но интеграция терминалов бывает слабой.

## Аппаратные атаки на карту

Логических методов не всегда достаточно, тогда применяют физические:

- **Fault injection** — глитч при проверке PIN или аутентификации;
- **Side-channel** — анализ потребления при криптооперациях;
- **Chip-off** — вскрытие чипа и чтение памяти;
- **Оптический анализ** — микроскопия для поиска тест-поинтов.

Это требует оборудования (ChipWhisperer, Riscure) и лаборатории, но именно так обходят даже стойкую криптографию.

## Практический стенд

Минимальный набор для работы со смарт-картами:

- **USB-ридер** (ACR38, Omnikey, ACR122U для бесконтактных);
- **pcscd и pcsc-tools** — работа с ридером;
- **GlobalPlatformPro** — управление апплетами;
- **ChipWhisperer** — fault injection и side-channel;
- **свои карты** — для экспериментов, никогда не боевые платёжные.

## Если не сработало

- **Неверный CLA/INS.** Карта вернёт `6E 00` или `6D 00`.
- **Путаница Le и Lc.** Перепутанная длина ломает обмен.
- **Файл не выбран.** `READ BINARY` без предварительного `SELECT` даёт ошибку.
- **Блокировка PIN.** Три неверных попытки блокируют карту.
- **Secure Channel обязателен.** GP-команды без установленного SC отклоняются.

## Что мы теперь знаем

1. Смарт-карта — защищённый микроконтроллер с операционной системой, файловой системой и набором приложений, работающий по ISO 7816 или ISO 14443.
2. ATR определяет платформу карты при сбросе — по нему выбирают дальнейшую тактику аудита.
3. Обмен идёт APDU; файлы организованы как дерево MF/DF/EF, а доступ к ним защищён условиями.
4. GlobalPlatform управляет апплетами через Secure Channel, устанавливаемый по ключам.
5. Уязвимости чаще в персонализации и апплетах, чем в самой криптографии карты. Именно поэтому аудит начинают с ключей и конфигурации, а не с попыток «взломать шифр».
