Смарт-карта — это защищённый микроконтроллер с криптосопроцессором, работающий по ISO 7816 (контакты) или ISO 14443 (бесконтакт). Внутри — операционная система (Java Card, MULTOS), файловая система и приложения (EMV, SIM, eID, FIDO). Для пентестера важно понимать APDU-обмен, структуру файлов и механизмы безопасности (Secure Channel, PIN, GlobalPlatform). Этот урок — углубление после базового знакомства со смарт-картами.

## APDU: язык обмена

Обмен с картой идёт **APDU** (Application Protocol Data Unit). Есть командные (C-APDU) и ответные (R-APDU).

C-APDU: `CLA INS P1 P2 [Lc] [Data] [Le]` — класс, инструкция, два параметра, длина, данные, ожидаемая длина ответа.
R-APDU: `[Data] SW1 SW2` — данные и статус (например, `90 00` = успех, `6A 82` = файл не найден).

```bash
# Чтение через pcsc-tools / scriptor
pcsc_scan                 # найти карту
scriptor                  # интерактивно отправлять APDU
# Пример: выбрать файл (SELECT by AID)
# 00 A4 04 00 07 A0000000031010 00
# -> 6F ... 9000
```

Понимание APDU — база: любое взаимодействие с картой (платёж, чтение eID, SIM) — это последовательность APDU.

## Файловая система ISO 7816

Карта организована как дерево файлов: **MF** (master file), **DF** (dedicated file, каталог), **EF** (elementary file, данные). Файлы выбираются командой `SELECT`, читаются `READ BINARY`/`READ RECORD`. Доступ защищён условиями (PIN, Secure Channel).

```bash
# Выбрать MF
# 00 A4 00 00 02 3F00
# Прочитать EF
# 00 B0 00 00 10     (READ BINARY 16 байт)
```

Ключи и сертификаты лежат в защищённых EF; доступ к ним требует аутентификации (VERIFY PIN, EXTERNAL AUTHENTICATE).

## GlobalPlatform и Secure Channel

**GlobalPlatform (GP)** — стандарт управления приложениями на карте: установка/удаление апплетов, управление ключами. GP-команды идут через **Secure Channel (SCP)** — защищённый канал, устанавливаемый по ключам (SCP01/02/03).

```text
# Установка Secure Channel (пример SCP02)
80 50 00 00 08 <host challenge> 00
# -> карта возвращает card challenge + криптограмму
84 82 <seq> <data>             # EXTERNAL AUTHENTICATE
```

Если ключи GP слабые (дефолтные) или утекли, можно установить свой апплет на карту — это мощнейший вектор.

## Java Card и JCOP

**Java Card** позволяет загружать апплеты; **JCOP** (NXP) — популярная платформа. Апплеты исполняются в песочнице, но исторически было много атак:

- **Fault injection** на проверках байткода (см. `hardware-fault-injection`).
- **Type confusion** в JVM карты.
- **Байткод-атаки** через специально сформированные апплеты.
- **Логические баги** апплетов (слабый PIN, отсутствие защиты от подбора).

Загрузка своего апплета (через GP) открывает возможность исследовать карту «изнутри».

## Разобранный пример: чтение и идентификация карты

```bash
# 1. Идентифицировать карту
pcsc_scan
# Reader ... ATR: 3B F8 13 00 00 81 31 FE 45 4A 43 4F 50 ...
# ATR содержит инфо о платформе (JCOP, Java Card)
# 2. Отправить SELECT MF
scriptor
# > 00 A4 00 00 02 3F 00
# < 90 00
# 3. Прочитать ATR-историю и определить ОС
# 4. Попробовать дефолтные GP-ключи (только на своей карте!)
# 5. Проверить, есть ли открытые EF с данными
```

ATR (Answer To Reset) — «визитка» карты: по нему определяют платформу и иногда даже партию.

## Частые ошибки и подводные камни

- **Неверный CLA/INS**: карта вернёт `6E 00`/`6D 00`.
- **Le vs Lc**: перепутанная длина ломает обмен.
- **Не выбран файл**: `READ BINARY` без `SELECT` даёт ошибку.
- **Блокировка PIN**: 3 неверных попытки блокируют карту.
- **Secure Channel обязателен**: GP-команды без SC отклоняются.
- **Разные ATR**: одна модель карты может иметь разные ATR/маски.

## EMV: приложение на карте

EMV-карта — это Java Card с приложением платёжной системы (Visa/Mastercard). Логика оплаты выполняется на карте: ридер посылает команды (SELECT AID, GET PROCESSING OPTIONS, READ RECORD, GENERATE AC), карта отвечает криптограммами. Разбор этой логики — ключ к пониманию платежей.

```bash
# Выбор платёжного AID (Visa)
# 00 A4 04 00 07 A0000000031010 00
# GET PROCESSING OPTIONS
# 80 A8 00 00 02 83 00 00
# READ RECORD
# 00 B2 01 0C 00
# GENERATE AC
# 80 AE 80 00 ...
```

Атаки на EMV: **relay** (дистанционные платежи), **скimming** (перехват данных), подмена суммы/валюты, downgrade до магнитной полосы. Современные карты защищены (cryptogram, CVM), но интеграция терминалов бывает слабой.

## Атаки на PIN и верификацию

PIN на карте проверяется командой `VERIFY` (offline) или на хосте (online). Векторы:

- **PIN bypass** через логическую ошибку апплета.
- **Подбор PIN** при слабой защите от неверных попыток.
- **PIN change без знания старого** при ошибке прав.
- **Fault injection** на сравнении PIN.
- **Social engineering / shoulder surfing** — не технические, но эффективные.

```text
# VERIFY PIN (пример)
# 00 20 00 80 08 <encrypted pin block>
# -> 9000 (верно) / 63Cx (неверно, x попыток)
```

Обратите внимание на статусные слова: они сообщают число оставшихся попыток.

## Практический стенд

Для работы со смарт-картами нужен стенд:

- **USB-ридер** (ACR38, Omnikey, ACR122U для бесконтактных).
- **pcscd + pcsc-tools** — работа с ридером.
- **GlobalPlatformPro** — управление апплетами.
- **ChipWhisperer** — fault injection/side-channel.
- **Свои карты** — для экспериментов (не боевые платёжные!).

Правило: никогда не экспериментируйте с реальными платёжными/ID-картами вне согласованного пентеста. Используйте тестовые карты и образы (Java Card dev kit).

## Защита и рекомендации

- **Не дефолтные ключи**: смена GP-ключей, уникальные ключи на партию.
- **Secure Channel обязателен** для управления.
- **Минимизация доступа**: файлы с данными защищены отдельными ключами.
- **Fault-injection-устойчивость**: счётчики, дублирование проверок.
- **Мониторинг**: логирование GP-операций и аномалий.

Для пентестера вывод: ищите дефолтные ключи, слабые апплеты и ошибки конфигурации; криптография карты обычно стойкая.

## Персонализация карт и управление ключами

**Персонализация** — процесс «прошивки» карты: создание приложений, загрузка ключей, установка прав. Ошибки персонализации — частая причина уязвимостей:

- **Дефолтные ключи**, не заменённые при выдаче.
- **Одинаковые ключи** на всю партию.
- **Слабые ключи** (короткие, предсказуемые).
- **Лишние права**: файлы доступны без аутентификации.

```text
# Установка ключа через GlobalPlatform
80 D4 01 <keyver> <keytype> <keylen> <encrypted key data> <kcv>
# Проверка: успех -> 9000
```

Для аудита полезно проверить, какие ключи реально используются, и сравнить их с дефолтными наборами платформы (JCOP, Java Card).

## Практические сценарии

- **Чтение eID/пропуска**: определить AID, проверить доступные EF.
- **Анализ платёжной карты**: снять APDU-обмен, понять логику приложения.
- **Проверка GP-ключей**: попытка дефолтных ключей (на своих картах).
- **Fault injection**: обход проверок на тестовой карте.
- **Разбор апплета**: декомпиляция и анализ Java Card-апплета.

Каждый сценарий начинается с идентификации (ATR, SELECT, GetVersion) и продолжается в зависимости от найденного.

## Аппаратные атаки на карту

Логические методы не всегда работают, тогда применяют физические:

- **Fault injection** — глитч при проверке PIN/аутентификации.
- **Side-channel** — анализ потребления при криптооперациях.
- **Chip-off** — вскрытие чипа и чтение памяти.
- **Оптический анализ** — микроскопия для поиска тест-поинтов.

Это требует оборудования (ChipWhisperer, Riscure) и часто — лаборатории. В CTF встречаются упрощённые версии.
