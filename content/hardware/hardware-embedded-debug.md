## Зачем этот урок

Кроме классических JTAG/SWD существуют более продвинутые отладочные интерфейсы: трассировка инструкций (ETM/CoreSight), BDM у Freescale/NXP, Background Debug Mode, debugWIRE/UPDI у AVR и отладочные мониторы. Они дают не только останов/шаг, но и **поток исполнения** — бесценно при реверсе, когда прошивка «молчит». Здесь — карта интерфейсов по архитектурам и практика извлечения пользы.

## Карта интерфейсов по архитектурам

| Архитектура | Интерфейс | Что даёт |
|-------------|-----------|----------|
| ARM Cortex-M/A | SWD, JTAG, SWO, ETM | Отладка + трассировка |
| Freescale/NXP HCS08/12 | BDM | Чтение/запись памяти, останов |
| ColdFire/PowerPC | BDM/JTAG | Отладка |
| AVR | debugWIRE, JTAG, UPDI | Отладка/программирование |
| RISC-V | JTAG (DM) | Отладка, trace |
| x86 | ITP/XDP, DCI | Низкоуровневая отладка |

## CoreSight: обзор компонентов

ARM CoreSight — набор компонентов отладки и трассировки: **ETM** (Embedded Trace Macrocell — поток инструкций), **ITM** (Instrumentation Trace — printf-стиль), **SWO** (Serial Wire Output — однопроводный вывод), **DWT** (Data Watchpoint — точки останова по данным), **TPIU** (Trace Port Interface Unit — вывод трассировки наружу).

## ETM: трассировка инструкций

ETM записывает поток исполненных инструкций (сжато, с адресами и ветвлениями). Требует внешнего trace-захвата (например, J-Trace или ETB-буфер). Результат — покрытие кода: видно, какие функции исполнялись, что помогает понять логику без дизассемблирования целиком. Для CTF это способ «увидеть» алгоритм проверки флага.

## ITM и SWO: printf без UART

ITM позволяет прошивке писать отладочные сообщения в каналы (0..31), а SWO выводит их по одному проводу. Это спасает, когда UART не разведён или «молчит»:

```bash
openocd -f interface/stlink.cfg -f target/stm32f4x.cfg \
  -c "init; tpiu config internal /tmp/swo.log uart off 16000000"
# В GDB:
monitor itm port 0 on
```

## DWT: watchpoints по данным

DWT даёт аппаратные точки останова по доступу к данным (чтение/запись адреса). Это лучший способ поймать момент, когда прошивка записывает секрет/флаг в буфер: ставим watchpoint на адрес и останавливаемся на записи.

## OpenOCD: настройка SWO/ITM

OpenOCD конфигурирует TPIU/SWO. Ключевые параметры: частота SWO (обычно HCLK), формат (uart/parallel), путь к логу. Если SWO «пустой» — почти всегда неверная тактовая частота. Проверьте `tpiu config` и совпадение с настройками прошивки.

## BDM (Freescale/NXP)

Background Debug Mode — интерфейс HCS08/HCS12/ColdFire. Даёт останов ядра, чтение/запись регистров, памяти и флеша, точки останова. Адаптеры: P&E Multilink, usbdm. На серийных устройствах BDM часто закрыт (secured), на дешёвых MCU — открыт.

## debugWIRE и UPDI (AVR)

У AVR есть debugWIRE (однопроводная отладка, использует RESET) и UPDI (Unified Program and Debug Interface у новых ATtiny). Оба позволяют читать/писать флеш и отлаживать. debugWIRE занимает линию RESET — при отладке она недоступна как GPIO.

## RISC-V debug module

RISC-V использует JTAG Debug Module (DM) с абстрактными командами: halt, resume, read/write GPR, доступ к памяти. Трассировка — через trace-модуль (Nexus/специфичный). OpenOCD поддерживает большинство RISC-V-таргетов.

## x86 ITP/XDP/DCI

На x86 низкоуровневая отладка — через ITP (In-Target Probe), XDP (eXtended Debug Port) и DCI (Direct Connect Interface). Это уровень прошивки/платформы: доступ к процессорным отладочным регистрам до загрузки ОС. Применяется в исследовании firmware и обходе защит.

## Отладочные мониторы и UART-консоли

Часто прошивка сама даёт отладочный монитор: скрытые команды в UART-консоли или bootloader с `dump`/`read`/`write`.

```bash
picocom -b 115200 /dev/ttyUSB0
# Ищите: help, ?, version, dump, md, mw, boot, unlock
```

## Определение baud и подключение

Если baud неизвестен — переберите стандартные (9600, 19200, 38400, 57600, 115200) или используйте автоопределение через логический анализатор. Убедитесь в уровне напряжения (3.3 В vs 5 В) — неправильный уровень портит адаптер.

## Разобранный пример: реверс через трассировку

1. Подключаемся SWD через OpenOCD, включаем ITM-канал 0 и SWO-логирование.
2. Запускаем устройство; в `swo.log` видим отладочные сообщения.
3. По сообщениям восстанавливаем состояние и ветвления.
4. При наличии J-Trace включаем ETM — получаем поток инструкций и покрытие.
5. Ставим DWT-watchpoint на адрес буфера — ловим запись секрета.

## Защита (secured chip, фьюзы)

Производители закрывают отладку фьюзами/битами защиты: `RDP` (STM32), `SEC`-фьюзы (AVR), BDM security. Обходы: глитчинг, стирание флеша (для RDP level 1), поиск незакрытых интерфейсов. Но часть методов требует оборудования и авторизации.

## Правовые аспекты

Отладка чужого устройства без разрешения — противоправно. Все работы по обходу защит — только на собственном оборудовании или в рамках пентест-контракта.

## Частые ошибки

- **Путать SWD и SWO.** SWD — отладка; SWO — вывод трассировки.
- **Забыть тактирование трассировки.** SWO/ETM требуют корректной частоты (HCLK).
- **Считать BDM мёртвым.** На старых MCU он жив и полезен.
- **Игнорировать отладочный монитор.** Иногда достаточно UART и `help`.
- **Не снять защиту (secured chip).** Интерфейсы блокируются фьюзами.

## Что дальше / решение

- ARM → SWD/JTAG + SWO/ITM; при наличии — ETM.
- Freescale/NXP → BDM.
- Есть UART → ищите отладочный монитор.
- Смежные: `hardware-jtag`, `hardware-swd-advanced`, `hardware-jtag-deep`.

## OpenOCD: команды и конфигурация

OpenOCD запускается с конфигами интерфейса и цели:

```bash
openocd -f interface/stlink.cfg -f target/stm32f4x.cfg
openocd -f interface/cmsis-dap.cfg -f target/nrf52.cfg -c "init; halt"
```

Команды в telnet-консоли (4444): `halt`, `resume`, `reg`, `mdw <addr> <count>`, `mww <addr> <val>`, `flash write_image`, `dap info`. Скрипт `-c` позволяет автоматизировать последовательность.

## GDB: удалённая отладка через OpenOCD

```bash
arm-none-eabi-gdb firmware.elf
(gdb) target extended-remote :3333
(gdb) monitor reset halt
(gdb) load
(gdb) break main
(gdb) continue
```

`monitor` передаёт команды в OpenOCD. Так реверсится прошивка: точки останова, чтение переменных, дизассемблирование `disassemble`.

## Захват трассировки и анализ покрытия

ITM/SWO-лог собирают в файл, затем парсят (`orbtrace`, `swo_parse`, скрипты). ETM-трассировку открывают в анализаторе (например, Percepio Tracealyzer или вендорский). Покрытие показывает, какие ветки кода исполнялись, — это резко ускоряет реверс.

## Сравнение интерфейсов

| Интерфейс | Провода | Трассировка | Типичное применение |
|-----------|---------|-------------|---------------------|
| JTAG | 4–5 | да (ETM) | Универсальная отладка |
| SWD | 2 | SWO | Cortex-M, экономия пинов |
| BDM | 1–2 | нет | Freescale/NXP |
| debugWIRE | 1 | нет | Малые AVR |
| UPDI | 1 | нет | Новые ATtiny |

## Итоговый чеклист встроенной отладки

1. Определите архитектуру MCU (по маркировке/даташиту).
2. Найдите отладочные пины (SWD/JTAG/BDM/UPDI) мультиметром/прозвонкой.
3. Подключите адаптер, проверьте ID через OpenOCD.
4. Если чип secured — оцените защиту (RDP/фьюзы) и возможность обхода.
5. Поднимите сессию: SWD/JTAG для отладки, SWO/ITM для логов, ETM для покрытия.
6. Проверьте UART на отладочный монитор (`help`, `dump`).
7. Задокументируйте интерфейс, скорость и уровень напряжения.

## Что даёт трассировка при реверсе

Поток исполнения (ETM) показывает реально выполненные ветки — это отличает реверс «по чтению» от реверса «по факту». В сочетании с DWT-watchpoints (момент записи данных) и ITM-логами (сообщения прошивки) вы получаете полную картину работы алгоритма без полного дизассемблирования. Для CTF это способ восстановить логику проверки флага, наблюдая, какие сравнения и переходы реально срабатывают при вводе.
