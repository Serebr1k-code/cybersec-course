Есть память, которую нельзя стереть: один раз записали — навсегда. Это e-fuse (электронные предохранители) и OTP (one-time programmable). Именно там производители хранят корневые ключи, флаги secure boot, счётчики anti-rollback и серийные номера. Понимание e-fuse объясняет, почему некоторые устройства «не вскрываются» программно и почему единственный путь — физические атаки.

## Теория: как работает e-fuse

**e-fuse** — массив пережигаемых элементов на кристалле. «Запись» физически меняет состояние элемента (пережигает поликремниевый предохранитель или пробивает антифьюз). Обратного пути нет: записанный бит нельзя вернуть.

**OTP-память** — та же идея, реализованная через память с однократной записью. Часто OTP и e-fuse используют как синонимы, хотя технически это разные структуры.

Типичное содержимое e-fuse:

| Область | Назначение |
|---------|-----------|
| Root key hash | хэш корневого ключа подписи |
| Secure boot enable | флаг включения проверки подписи |
| Debug disable | флаг закрытия JTAG/SWD |
| Anti-rollback counter | счётчик минимальной версии |
| Device ID / serial | уникальный идентификатор |
| Calibration | калибровочные данные (не для атаки) |

Когда e-fuse содержит **хэш** корневого ключа, а не сам ключ, восстановить ключ из e-fuse невозможно — там только хэш. Это важное отличие: вы можете проверить, какой ключ зашит, но не можете его извлечь.

## Инструменты и команды

- **`espefuse.py` / `esptool.py`** (ESP32) — чтение и запись e-fuse, но запись необратима.
- **`stm32mp-tools` / `STM32CubeProgrammer`** — работа с OTP STM32MP.
- **`sunxi-fel`** (Allwinner) — чтение e-fuse через FEL.
- **`openocd`** — иногда читает fuse-регистры через отладочный интерфейс.
- **`rockchip`/`rkdeveloptool`** — доступ к e-fuse у Rockchip.
- **`binwalk`** — для поиска конфигурации в прошивке, где упоминаются fuse-биты.
- **Микроскоп + side-channel/glitch** — когда чтение fuse-регистров закрыто.

```bash
# ESP32: чтение e-fuse (НЕ пишите без понимания!)
espefuse.py --port /dev/ttyUSB0 summary
espefuse.py --port /dev/ttyUSB0 read_protect_efuse BLOCK0
# Rockchip: чтение e-fuse через rkdeveloptool
rkdeveloptool rfi
```

## Разобранный пример: анализ e-fuse у ESP32

1. **Чтение summary.** Подключаемся и смотрим, какие fuse-блоки записаны.

```text
espefuse.py --port /dev/ttyUSB0 summary
EFUSE_NAME             Description                = Value
MAC                    Factory MAC address        = 24:6f:28:xx:xx:xx
SPI_BOOT_CRYPT_CNT     Flash encryption count     = 0
SECURE_BOOT_EN         Secure boot enable         = False
DIS_DOWNLOAD_MODE      Disable download mode      = False
```

2. **Интерпретация.** `SPI_BOOT_CRYPT_CNT = 0` означает, что шифрование флеша выключено, `SECURE_BOOT_EN = False` — проверка подписи не включена. Если бы они были включены, прошивку нельзя было бы подменить без ключа.
3. **Проверка защиты чтения.** Если установлен `RD_DIS` для блока, чтение вернёт ошибку — тогда остаётся side-channel или glitch.
4. **Ключи.** У ESP32 ключ шифрования флеша и ключ secure boot лежат в отдельных блоках и при `RD_DIS` не читаются. Их нельзя извлечь чтением — только атакой.

```text
# Пример уже защищённого чипа:
SPI_BOOT_CRYPT_CNT = 7 (0b111)   # включено
SECURE_BOOT_EN = True
DIS_DOWNLOAD_MODE = True
```

## Частые ошибки и подводные камни

- **Случайная запись fuse.** Одна команда может навсегда закрыть устройство (например, `DIS_DOWNLOAD_MODE`). Никогда не пишите fuse на чужом/рабочем устройстве.
- **Ожидание «прочитать ключ».** В e-fuse часто только хэш ключа; сам ключ недостижим.
- **Игнорирование anti-rollback.** Даже если вы нашли старую прошивку, счётчик не даст её загрузить.
- **Путаница fuse и flash.** Изменение flash не меняет fuse; защита на уровне fuse переживает перепрошивку.
- **Неверный адрес/блок.** Запись не туда может заблокировать загрузку.
- **Отсутствие бэкапа.** Перед экспериментами сохраните `summary` — это единственная «карта» устройства.

## Что дальше / решение

Если fuse не мешает — работайте с прошивкой напрямую. Если `SECURE_BOOT_EN` и `RD_DIS` установлены, программный путь закрыт: переходите к fault injection (`hardware-laser-fault`, `hardware-fault-injection`), чтобы «пропустить» проверку, или к power analysis (`hardware-power-analysis`) для извлечения ключа. Для устройств с anti-rollback ищите уязвимость в текущей (последней) версии — откат недоступен. Помните: e-fuse — это последний рубеж защиты, и обход требует оборудования и времени.

## Как читают e-fuse: интерфейсы и регистры

Доступ к e-fuse зависит от платформы:

- **ESP32/ESP8266** — через UART-загрузчик (`espefuse.py`), пока не закрыт download mode.
- **STM32MP** — через `STM32CubeProgrammer` и OTP-регистры; часть битов доступна из TF-A/U-Boot.
- **Allwinner** — через FEL-режим и `sunxi-fel efuse`.
- **Rockchip** — через `rkdeveloptool` и сервисные регистры.
- **NXP i.MX** — через `imx_otp`/`fuse`-драйверы и `OCOTP`.
- **Broadcom/Realtek (роутеры)** — часто через загрузчик и `nvram`-подобные утилиты.

Общий принцип: пока загрузчик открыт, e-fuse часто читается. Как только включён secure boot и закрыт download mode, чтение блокируется, и остаются только физические методы.

```bash
# Allwinner: чтение e-fuse из FEL
sunxi-fel efuse dump
# Rockchip: чтение info (включая fuse-биты)
rkdeveloptool rfi
# NXP i.MX: чтение OTP через утилиту
./imx-otp -r
```

## Обход защиты чтения fuse

Если установлен флаг `RD_DIS` (read disable), прямой путь закрыт. Что остаётся:

1. **Fault injection.** Короткий глитч по питанию или такту в момент проверки права чтения может «пропустить» её и вернуть значение. Это самый частый обход.
2. **Side-channel.** По потреблению можно восстановить содержимое защищённого блока (особенно ключей), не читая его напрямую.
3. **Утечка через периферию.** Иногда fuse-значение косвенно влияет на поведение (например, длина задержки), и его можно вывести по наблюдаемому таймингу.
4. **Заводская уязвимость.** Некоторые загрузчики имеют команды, читающие fuse в обход защиты (ищите CVE по загрузчику).

Важно: обход `RD_DIS` — это уже физическая атака уровня side-channel/glitch, а не «ещё одна команда».

## Практический кейс: анализ защищённого ESP32

Возьмём устройство с включённым secure boot и шифрованием флеша.

```text
espefuse.py --port /dev/ttyUSB0 summary
SPI_BOOT_CRYPT_CNT   = 7 (0b111)  # шифрование включено
SECURE_BOOT_EN       = True
DIS_DOWNLOAD_MODE    = True       # UART-загрузчик закрыт
BLOCK_KEY0 RD_DIS    = True       # ключ шифрования не читается
```

Выводы для атакующего:

- Прошить свою прошивку нельзя — подпись не сойдётся.
- Прочитать ключ из fuse нельзя — `RD_DIS`.
- UART-загрузчик закрыт — `DIS_DOWNLOAD_MODE`.
- Единственный путь — glitch/side-channel либо поиск бага в **уже подписанной** прошивке (переполнение в сетевом сервисе, слабая проверка в OTA).

Это типичная картина «закрытого» устройства: софт не поможет, и нужно решать, оправданы ли физические атаки по бюджету и времени.

## Защита и детект

Правильная настройка e-fuse — ключ к стойкости устройства:

- включайте `SECURE_BOOT_EN` и `RD_DIS` для ключевых блоков;
- устанавливайте `DIS_DOWNLOAD_MODE`, чтобы закрыть UART-загрузчик;
- используйте anti-rollback счётчик, чтобы запретить откат;
- храните в fuse **хэш** ключа, а не сам ключ;
- заводите отдельные ключи на устройство/партию (уникальность).

Детектировать попытки чтения fuse сложно, но аномалии питания и такта (глитчи) можно ловить аппаратными детекторами. На стороне производителя это отдельная дисциплина — secure element и tamper-механизмы.

## Сравнение: e-fuse, OTP и обычная флеш

Три вида энергонезависимой памяти путают, хотя роли у них разные.

| Свойство | e-fuse | OTP | Флеш (NOR/NAND) |
|----------|--------|-----|-----------------|
| Перезапись | нет | нет | да (многократно) |
| Типичный объём | сотни бит | Кбит–Мбит | Мбит–Гбит |
| Основное назначение | ключи, флаги защиты | серийники, калибровка | код, данные |
| Чтение | часто ограничено | часто ограничено | обычно свободно |
| Влияние на атаку | закрывает откат/подпись | уникальные данные | основной объект анализа |

Практический вывод: **флеш — это то, что вы читаете и модифицируете; e-fuse/OTP — это то, что ограничивает ваши возможности**. Не путайте «перепрошил флеш» с «обошёл защиту»: защита часто живёт именно в e-fuse.

## Терминологическая разминка

Полезно уметь различать термины на слух, потому что в документации они встречаются вперемешку: fuse, efuse, OTP, ROM, mask ROM. Mask ROM — память, записанная на заводе при изготовлении маски кристалла; её нельзя ни стереть, ни перезаписать. OTP — можно запрограммировать один раз на устройстве. e-fuse — разновидность OTP, реализованная пережиганием элементов. Понимание этих различий помогает быстро оценить, что в конкретном чипе вообще можно изменить, а что — нет.

## Практика: дамп fuse-области и сравнение

Полезный навык — снять дамп fuse-области и сравнить его с эталоном (например, с соседним устройством той же партии). Различия показывают, что уже «сожжено».

```bash
# ESP32: выгрузить все e-fuse в файл
espefuse.py --port /dev/ttyUSB0 dump /tmp/efuse1.bin
# Повторить для второго устройства
espefuse.py --port /dev/ttyUSB1 dump /tmp/efuse2.bin
# Сравнить
cmp -l /tmp/efuse1.bin /tmp/efuse2.bin | head
# 129  0 1     <- бит на позиции 129 различается
```

Различия в блоках `BLOCK0` (флаги защиты) и ключевых блоках — самое важное. По ним видно, включён ли secure boot, закрыт ли download mode, отличается ли ключ.

## Как читать fuse на разных платформах

| Платформа | Команда чтения | Ограничение |
|-----------|----------------|-------------|
| ESP32 | `espefuse.py summary` | нужен открытый download mode |
| STM32MP | `STM32_Programmer_CLI` + OTP | часть битов только из TF-A |
| Allwinner | `sunxi-fel efuse dump` | нужен FEL-режим |
| Rockchip | `rkdeveloptool rfi` | сервисный режим |
| NXP i.MX | `imx_otp -r` | доступ через OCOTP |

```bash
# STM32MP: чтение OTP-области
STM32_Programmer_CLI -c port=SWD -otp_read 0x0 0x40
# Allwinner: только нужные fuse-слова
sunxi-fel efuse dump | head
```

Общий принцип: пока загрузчик открыт — fuse читается; после включения secure boot и закрытия download mode остаются только физические методы.

## Сравнение e-fuse и OTP-EEPROM

Иногда e-fuse и OTP различают по назначению:

| Критерий | e-fuse | OTP-EEPROM |
|----------|--------|------------|
| Принцип записи | пережигание элемента | пробой/заряд в ячейке |
| Гранулярность | бит | байт/слово |
| Типичное содержимое | флаги, хэши ключей | серийники, калибровка |
| Восстановление | невозможно | невозможно |

Для атакующего разница невелика: обе памяти однократны и защищены от записи. Важнее знать, какие именно биты влияют на загрузку и чтение, — именно они и определяют, закрыт ли программный путь.
