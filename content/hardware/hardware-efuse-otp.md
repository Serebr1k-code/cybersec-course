## Вопрос, с которого всё начинается

Ты снял прошивку, нашёл в ней уязвимость, собрал исправленную версию — и не можешь её загрузить: устройство отказывается принимать неподписанный образ. Или наоборот: читаешь память, а на месте ключа — только его хэш. Почему так?

Ответ — в **e-fuse** и **OTP**: памяти, которую нельзя стереть. Разберём, что там лежит и почему это меняет всю стратегию атаки.

## Наш пример: устройство на ESP32

Возьмём плату на чипе **ESP32** с открытым UART-загрузчиком. Сначала посмотрим, что вообще «записано» в его энергонезависимых настройках — а потом сравним с закрытым устройством.

## Шаг 1: что такое e-fuse и OTP

**e-fuse** (электронные предохранители) — массив пережигаемых элементов на кристалле. «Запись» физически меняет состояние элемента: пережигает поликремниевый предохранитель или пробивает антифьюз. Обратного пути нет — записанный бит вернуть нельзя.

**OTP** (one-time programmable) — та же идея, реализованная через память с однократной записью. Часто эти термины используют как синонимы. Типичное содержимое e-fuse:

| Область | Назначение |
|---------|-----------|
| Root key hash | хэш корневого ключа подписи |
| Secure boot enable | флаг включения проверки подписи |
| Debug disable | флаг закрытия JTAG/SWD |
| Anti-rollback counter | счётчик минимальной версии |
| Device ID / serial | уникальный идентификатор |

Важное отличие: когда в e-fuse лежит **хэш** корневого ключа, а не сам ключ, восстановить ключ из fuse невозможно — там только хэш. Вы можете проверить, какой ключ зашит, но не извлечь его.

## Шаг 2: читаем fuse у ESP32

Пока загрузчик открыт, fuse часто читается. У ESP32 это делается утилитой `espefuse.py`:

```
$ espefuse.py --port /dev/ttyUSB0 summary
EFUSE_NAME             Description                = Value
MAC                    Factory MAC address        = 24:6f:28:xx:xx:xx
SPI_BOOT_CRYPT_CNT     Flash encryption count     = 0
SECURE_BOOT_EN         Secure boot enable         = False
DIS_DOWNLOAD_MODE      Disable download mode      = False
```

Читаем: `SPI_BOOT_CRYPT_CNT = 0` — шифрование флеша выключено, `SECURE_BOOT_EN = False` — проверка подписи не включена. Это **открытое** устройство: прошивку можно подменить без ключа.

## Шаг 3: как выглядит закрытое устройство

Теперь сравним с защищённым чипом:

```
SPI_BOOT_CRYPT_CNT   = 7 (0b111)   # шифрование включено
SECURE_BOOT_EN       = True
DIS_DOWNLOAD_MODE    = True        # UART-загрузчик закрыт
BLOCK_KEY0 RD_DIS    = True        # ключ шифрования не читается
```

Выводы для атакующего однозначны:

- прошить свою прошивку нельзя — подпись не сойдётся;
- прочитать ключ из fuse нельзя — стоит `RD_DIS` (read disable);
- UART-загрузчик закрыт — `DIS_DOWNLOAD_MODE`.

Единственные пути — glitch/side-channel либо поиск бага в **уже подписанной** прошивке: переполнение в сетевом сервисе, слабая проверка в OTA-обновлении.

## Шаг 4: как читают fuse на разных платформах

Доступ к e-fuse зависит от платформы, но принцип один: пока загрузчик открыт — fuse читается; после включения secure boot остаются только физические методы.

| Платформа | Команда чтения | Ограничение |
|-----------|----------------|-------------|
| ESP32 | `espefuse.py summary` | нужен открытый download mode |
| STM32MP | `STM32_Programmer_CLI -otp_read` | часть битов только из TF-A |
| Allwinner | `sunxi-fel efuse dump` | нужен FEL-режим |
| Rockchip | `rkdeveloptool rfi` | сервисный режим |
| NXP i.MX | `imx_otp -r` | доступ через OCOTP |

## Шаг 5: сравниваем fuse двух устройств

Полезный приём — снять дамп fuse-области и сравнить с эталоном (например, с соседним устройством той же партии). Различия показывают, что уже «сожжено»:

```
$ espefuse.py --port /dev/ttyUSB0 dump /tmp/efuse1.bin
$ espefuse.py --port /dev/ttyUSB1 dump /tmp/efuse2.bin
$ cmp -l /tmp/efuse1.bin /tmp/efuse2.bin | head
129  0 1
```

`cmp -l` показывает различающиеся байты. Различия в блоке `BLOCK0` (флаги защиты) и ключевых блоках — самое важное: по ним видно, включён ли secure boot, закрыт ли download mode, отличается ли ключ.

## Шаг 6: если стоит RD_DIS

Если установлен флаг `RD_DIS`, прямой путь закрыт. Что остаётся:

1. **Fault injection.** Короткий глитч по питанию или такту в момент проверки права чтения может «пропустить» её и вернуть значение. Самый частый обход.
2. **Side-channel.** По потреблению можно восстановить содержимое защищённого блока, особенно ключей.
3. **Утечка через периферию.** Иногда fuse-значение косвенно влияет на поведение — например, на длину задержки.
4. **Заводская уязвимость.** Некоторые загрузчики имеют команды, читающие fuse в обход защиты (ищите CVE по загрузчику).

Обход `RD_DIS` — это уже физическая атака уровня side-channel, а не «ещё одна команда».

## Чем e-fuse отличается от обычной флеш

Три вида энергонезависимой памяти часто путают, хотя роли у них разные:

| Свойство | e-fuse | OTP | Флеш (NOR/NAND) |
|----------|--------|-----|-----------------|
| Перезапись | нет | нет | да, многократно |
| Типичный объём | сотни бит | Кбит–Мбит | Мбит–Гбит |
| Назначение | ключи, флаги защиты | серийники, калибровка | код и данные |
| Чтение | часто ограничено | часто ограничено | обычно свободно |

Практический вывод: **флеш — это то, что вы читаете и модифицируете; e-fuse и OTP — то, что ограничивает ваши возможности**. Поэтому «перепрошил флеш» и «обошёл защиту» — не одно и то же: защита часто живёт именно в e-fuse.

## Если не сработало

- **Случайная запись fuse.** Одна команда может навсегда закрыть устройство; никогда не пишите fuse на рабочем чипе.
- **Ожидание «прочитать ключ».** В e-fuse часто только хэш ключа — сам ключ недостижим.
- **Игнорирование anti-rollback.** Даже со старой прошивкой счётчик не даст её загрузить.
- **Путаница fuse и flash.** Изменение flash не меняет fuse; защита на уровне fuse переживает перепрошивку.
- **Неверный адрес/блок.** Запись не туда может заблокировать загрузку.

## Что мы теперь знаем

1. e-fuse и OTP — однократно программируемая память; записанный бит не вернуть.
2. Там хранят хэши ключей, флаги secure boot, debug disable и счётчики anti-rollback.
3. Пока загрузчик открыт, fuse читается; после включения secure boot — нет.
4. Флеш — это то, что вы читаете и меняете; e-fuse — то, что ограничивает вас.
5. Обход `RD_DIS` и secure boot — это физические атаки уровня glitch и side-channel, а не софт.

## Anti-rollback: как он ломает откат

Счётчик anti-rollback — монотонная величина в e-fuse, которая только увеличивается при обновлении. Прошивка несёт в заголовке свою «минимальную версию»; если она меньше записанного в fuse счётчика, загрузчик отказывается её запускать. Атакующий вывод: даже если вы нашли старую уязвимую версию и подписали её (или добыли валидную), загрузить её не даст счётчик. Обойти программно нельзя — счётчик в fuse. Остаются glitch в момент сравнения версий или атака на сам загрузчик.

## Таблица: известные glitch-подходы к fuse

| Цель | Метод | Идея |
|---|---|---|
| Обойти проверку fuse | voltage/clock glitch | «пропустить» инструкцию чтения |
| Пропустить secure boot | fault в момент сверки подписи | заставить принять `true` |
| Прочитать RD_DIS-блок | side-channel (SPA/DPA) | восстановить биты по потреблению |
| Откатить версию | glitch на сравнении счётчика | обойти anti-rollback |
| Разблокировать JTAG | fault при проверке debug disable | открыть отладку |

Общий принцип: fuse-значение читается и проверяется **в конкретный момент**; если этот момент «смазать», проверка возвращает неверный, но удобный результат.

## Практика: разбор дампа OTP

Дамп fuse-области — это несколько блоков по 32 бита. Разбирать его удобно побитово, потому что каждый флаг — конкретные биты:

```bash
$ espefuse.py --port /dev/ttyUSB0 dump /tmp/efuse.bin
$ xxd /tmp/efuse.bin | head
00000000: 0000 0000 0100 0000 0000 0000 0000 0000  ................
```

Сопоставив дамп с картой полей конкретного чипа (из даташита или `espefuse.py summary`), вы видите, какие флаги установлены: `SECURE_BOOT_EN`, `RD_DIS`, `DIS_DOWNLOAD_MODE`. Полезно хранить эталонный дамп «чистого» устройства и диффить с ним — различия сразу показывают, что уже «сожжено».

## Краткий чек-лист

1. Пока загрузчик открыт — сними дамп fuse (`espefuse.py summary`/`dump`).
2. Сопоставь дамп с картой полей чипа: флаги secure boot, RD_DIS, download mode.
3. Диффни с эталонным устройством той же партии — различия покажут, что «сожжено».
4. Если стоит RD_DIS — программный путь закрыт, переходи к glitch/side-channel.
5. Проверь anti-rollback: старую прошивку загрузить не даст счётчик.
6. Никогда не пиши fuse на рабочем устройстве.

## Куда дальше

Мы разобрали память, которую нельзя изменить. Теперь понятно, почему некоторые устройства «не вскрываются» программно. В следующем уроке разберём, что происходит при обновлении прошивки и как защита от отката версий (anti-rollback) ломает привычные сценарии. А пока запомни главное: не путайте «перепрошил флеш» с «обошёл защиту» — защита часто живёт именно в e-fuse.
