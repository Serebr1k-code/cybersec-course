## Вопрос, с которого всё начинается

В прошлых уроках мы видели, что в промышленных сетях ходит Modbus и что читать его безопасно, а писать — опасно. Но что конкретно мы читаем? Что за числа лежат в регистрах ПЛК и как понять, какое из них за что отвечает?

Разберём Modbus изнутри — на одном конкретном контроллере.

## Наш пример: ПЛК на 10.0.0.10

У нас есть контроллер ПЛК по адресу `10.0.0.10`, слушающий порт 502. Мы на согласованном пентесте и работаем аккуратно: только чтение, пока не поймём систему. Цель — составить карту регистров: какой номер за что отвечает.

## Шаг 1: понимаем модель данных Modbus

**Modbus** — простейший протокол: запрос содержит адрес устройства, код функции и данные; ответ — те же поля с результатом. Аутентификации и шифрования в нём нет.

Данные Modbus организованы в четыре таблицы:

| Таблица | Размер | Доступ |
|---------|--------|--------|
| Coils | 1 бит | чтение/запись |
| Discrete Inputs | 1 бит | только чтение |
| Input Registers | 16 бит | только чтение |
| Holding Registers | 16 бит | чтение/запись |

Грубо: **coils** — это отдельные «выключатели» (биты), **registers** — числа по 16 бит. Input-таблицы только для чтения (датчики), holding и coils можно менять (уставки и команды).

## Шаг 2: разбираемся с адресацией

Здесь прячется классическая ловушка. В документации регистры нумеруют «по-человечески»: holding register 40001, 40002 и так далее. А в самом протоколе используется нумерация с нуля. Поэтому «holding register 40001» в запросе — это адрес `0`. Путаница с этим — самая частая ошибка новичка.

## Шаг 3: читаем регистры

Для работы с Modbus удобна библиотека `pymodbus`. Сначала — «паспорт» устройства функцией идентификации:

```
$ python3 - <<'PY'
from pymodbus.client import ModbusTcpClient
c = ModbusTcpClient('10.0.0.10', port=502)
c.connect()
r = c.read_device_information()
print(r)
PY
vendor: Acme Controls, model: PLC-200, version: 1.4
```

Теперь читаем десять holding-регистров, начиная с адреса 0. Параметр `slave=1` — это **unit ID**: за одним IP может стоять несколько устройств за шлюзом, и обращаться надо к правильному.

```
$ python3 - <<'PY'
from pymodbus.client import ModbusTcpClient
c = ModbusTcpClient('10.0.0.10', port=502)
c.connect()
r = c.read_holding_registers(0, 10, slave=1)
print(r.registers)
c.close()
PY
[0, 100, 0, 1, 23, 0, 0, 0, 0, 0]
```

Мы получили числа, но что они значат — пока непонятно.

## Шаг 4: реверсим карту регистров

Ключевой приём — **корреляция**: снимаем состояние, ждём изменения в процессе и смотрим, какие регистры изменились. Так регистр «привязывается» к физической величине:

```
$ python3 - <<'PY'
import time
from pymodbus.client import ModbusTcpClient
c = ModbusTcpClient('10.0.0.10'); c.connect()
def snap():
    return c.read_holding_registers(0, 100, slave=1).registers
a = snap(); time.sleep(2); b = snap()
for i,(x,y) in enumerate(zip(a,b)):
    if x != y: print(f'reg {i}: {x} -> {y}')
PY
reg 4: 23 -> 41
```

Регистр номер 4 изменился с 23 на 41 — скорее всего, это температура. Сопоставляя такие изменения с показаниями на панели оператора, восстанавливают всю карту. Иногда ускоряет официальная документация производителя.

## Шаг 5: разбираемся с coils и функциями

Кроме регистров есть биты-«выключатели». Прочитать их можно функцией чтения coils:

```
$ python3 - <<'PY'
from pymodbus.client import ModbusTcpClient
c = ModbusTcpClient('10.0.0.10'); c.connect()
r = c.read_coils(0, 8, slave=1)
print(r.bits)
PY
[True, False, False, False, False, False, False, False]
```

Первый бит включён — возможно, насос работает. Запомним коды основных функций: `01` — читать coils, `03` — читать holding-регистры, `05` — записать один бит, `06` — записать один регистр, `16` — записать несколько регистров.

## Шаг 6: почему мы НЕ пишем в этот ПЛК

Соблазн — записать в coil и выключить насос, доказав уязвимость. Но запись (`05`, `06`, `16`) меняет физический процесс: можно открыть клапан или остановить линию. Поэтому на реальном ПЛК мы останавливаемся на чтении.

Чтобы отработать запись, поднимают **стенд** — программный Modbus-сервер или симулятор:

```
$ python3 -c "
from pymodbus.server import StartTcpServer
from pymodbus.datastore import ModbusSequentialDataBlock, ModbusSlaveContext, ModbusServerContext
store = ModbusSlaveContext(hr=ModbusSequentialDataBlock(0, [0]*100))
StartTcpServer(context=ModbusServerContext(slaves=store, single=True))
"
```

На этом стенде можно сколько угодно писать, спуфить датчики и отрабатывать атаки — без риска для производства. Так же поступают с honeypot-инструментами вроде Conpot.

## Что мы теперь знаем

По-простому:

1. Modbus хранит данные в четырёх таблицах: coils и registers (чтение/запись), input-таблицы (только чтение).
2. Документация нумерует регистры с 40001, а протокол — с нуля.
3. `pymodbus` читает и пишет регистры; `unit ID` выбирает устройство за шлюзом.
4. Карту регистров восстанавливают корреляцией: что меняется — то и измеряем.
5. Запись в реальный ПЛК меняет процесс — только стенд.

## Как это выглядит целиком

Маршрут в одну историю: `read_device_information` возвращает `PLC-200 v1.4`, `read_holding_registers(0,10)` даёт числа. Корреляция (снимок → пауза → снимок) показывает `reg 4: 23 -> 41` — это температура. `read_coils(0,8)` показывает первый бит `True` — возможно, насос. Карта регистров собрана только чтением. Запись отрабатываем на локальном `StartTcpServer`-стенде, а не на ПЛК. От идентификации к карте — и без единой записи в прод.

## На что смотреть дальше

- **Адресация 0-based против 1-based.** «40001» в запросе — это адрес 0.
- **Не тот unit ID.** Ответ будет пустым или с ошибкой.
- **Слишком частый опрос.** Старый ПЛК перегружается от потока запросов.
- **Byte order.** У части устройств слова или байты переставлены (word swap).
- **Modbus over TLS.** Редко, но встречается на порту 802; проверьте, не обходится ли downgrade до открытого.
- **Modbus RTU через шлюз.** Если ПЛК за шлюзом TCP↔RTU, unit ID и таймауты важнее, чем кажется.
- **Пустой ответ.** Не тот unit ID или адрес за границей карты — уточните диапазон регистров.
- **Пропущенные регистры.** Сканируйте диапазон постранично (например, по 100 адресов), чтобы не потерять рабочие ячейки.
- **RTU-таймаут.** На медленной линии увеличьте таймаут клиента, иначе ответы теряются.
