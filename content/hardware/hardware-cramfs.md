## Вопрос, с которого всё начинается

Мы разобрали Squashfs — самую частую файловую систему прошивок. Но не всякая прошивка её содержит. Старые и «тонкие» устройства часто используют куда более простые форматы. И это хорошая новость: их разбирают нативные инструменты Linux, без эмуляции и редких утилит.

Разберём четыре простых случая на одном образе, в котором они встречаются все сразу.

## Наш пример: прошивка камеры с тремя ФС

Возьмём `camera_fw.bin` — прошивку IP-камеры. Прогоним её через `binwalk`, чтобы понять состав:

```
$ binwalk camera_fw.bin
DECIMAL       HEXADECIMAL     DESCRIPTION
0             0x0             uImage header
1048576       0x100000        gzip compressed data
2097152       0x200000        CRAMFS filesystem
6291456       0x600000        ext4 filesystem
```

В одном образе сразу три формата: сжатый архив, CRAMFS и ext4. Каждый распаковывается своим инструментом — и мы пройдём по всем.

## Шаг 1: распознаём формат по сигнатуре

Формат определяют по **сигнатуре** — характерным первым байтам:

| ФС | Сигнатура (hex) | Как выглядит | Инструмент |
|----|-----------------|--------------|------------|
| CRAMFS | `45 3d cd 28` | `cramfs` | `cramfsck`, `mount` |
| romfs | `2d 72 6f 6d` | `-rom` | `mount -t romfs` |
| ext2/3/4 | `53 ef` (по смещению 1024) | `ext` | `mount`, `debugfs`, `7z` |
| cpio (initramfs) | `30 37 30 37` | `070701` | `cpio -idmv` |
| gzip | `1f 8b` | — | `zcat` |

Команда `file` показывает формат по этой сигнатуре:

```
$ file rootfs.cramfs
rootfs.cramfs: Linux Compressed ROM File System data, little endian, size: 4194304
```

## Шаг 2: разбираем initramfs (cpio)

Первый раздел — `gzip compressed data` по смещению `0x100000`. Это **initramfs**: не файловая система, а архив `cpio`, сжатый gzip. Ядро распаковывает его в память при загрузке. Сначала снимаем сжатие, потом разбираем архив:

```
$ binwalk -e camera_fw.bin
$ cd _camera_fw.bin.extracted
$ cpio -idmv < initramfs.cpio
etc/init.d/rcS
bin/busybox
...
```

`cpio -idmv` — «извлечь, создать каталоги, подробно». Если сжатие не gzip, а `xz` или `lz4`, используйте `xz -dc` или `lz4 -dc` перед `cpio`.

## Шаг 3: разбираем CRAMFS

Второй раздел — CRAMFS по смещению `0x200000`. Это сжатая read-only ФС с ограничением: файл не может быть больше 16 МБ. Вырезаем её и распаковываем `cramfsck` (пакет `cramfsprogs`):

```
$ dd if=camera_fw.bin of=rootfs.cramfs bs=1 skip=2097152 count=4194304
$ cramfsck -x cramfs_root/ rootfs.cramfs
$ ls cramfs_root/
bin  dev  etc  lib  sbin  usr  var
```

`cramfsck -x` работает **без прав root** — удобно в контейнере. Альтернатива — примонтировать: `mount -o loop,ro rootfs.cramfs /mnt/cramfs`.

## Шаг 4: разбираем ext4 без root

Третий раздел — ext4 по смещению `0x600000`. Обычно его монтируют напрямую, но в изолированной среде прав root может не быть. Тогда на помощь приходит `debugfs` из пакета `e2fsprogs` — он читает ext без монтирования:

```
$ dd if=camera_fw.bin of=data.ext4 bs=1 skip=6291456
$ debugfs -R "ls -l /etc" data.ext4
$ debugfs -R "dump /etc/passwd /tmp/pw" data.ext4
$ cat /tmp/pw
root:x:0:0:root:/root:/bin/sh
```

`debugfs` с флагом `-R` выполняет одну команду и выходит. Тот же результат даёт `7z x data.ext4 -oext_out/`.

## Шаг 5: ищем секреты

Теперь, когда все три системы распакованы, ищем учётные данные и ключи обычным `grep`:

```
$ grep -rE 'root:|admin:' cramfs_root/etc/passwd
root:x:0:0:root:/root:/bin/sh
$ grep -rEi 'password|secret|api_key' cramfs_root/etc/
cramfs_root/etc/config/system: option password 'cam12345'
```

Пароль в открытом виде. В ext4-разделе может лежать больше — логи, история, пользовательские данные.

## Шаг 6: собираем обратно

Для модификации прошивки нужна обратная сборка. Каждый формат собирается своей утилитой:

```
$ mkcramfs cramfs_root/ new.cramfs
$ mkfs.ext4 -d cramfs_root/ -b 4096 new.ext4 -F
$ cd cramfs_root && find . | cpio -o -H newc | gzip -9 > ../initramfs.cpio.gz
```

При пересборке CRAMFS помните про лимит 16 МБ на файл, а для initramfs — про сохранение прав (`find . | cpio -o -H newc` их сохраняет). Перед прошивкой проверьте результат монтированием на хосте.

## Как это выглядит целиком

Маршрут в одну историю: `binwalk camera_fw.bin` показывает три раздела. По смещению `0x100000` — gzip-архив initramfs: `binwalk -e` распаковывает, `cpio -idmv < initramfs.cpio` даёт дерево с `etc/init.d/rcS`. По `0x200000` — CRAMFS: вырезаем `dd`, распаковываем `cramfsck -x cramfs_root/`. По `0x600000` — ext4: `debugfs -R "dump /etc/passwd /tmp/pw" data.ext4` вытаскивает файл без монтирования. В конце `grep -rEi 'password|secret'` по всем деревьям находит открытый пароль в `etc/config/system`. Три разных формата — три разных инструмента, но единый маршрут.

## Почему форматов так много

Новичку кажется, что «одной файловой системы хватило бы всем». На самом деле выбор диктует железо и задача. CRAMFS и romfs — read-only и максимально простые: они нужны там, где содержимое меняется только при перепрошивке, а памяти мало. ext4 — полноценная ФС с журналом, её берут для разделов, куда пишутся данные (логи, настройки, пользовательские файлы). initramfs — не ФС, а архив: ядру нужно смонтировать корень ещё до того, как появится драйвер реального носителя, и архив в памяти решает эту задачу. Понимание этой логики помогает не гадать: увидев read-only-раздел, вы ожидаете там прошивочные бинарники и конфиги, а writable ext4 — логи и данные, где чаще и живут секреты.

## Шаг 7: что делать с raw-flash ФС

Иногда `binwalk` показывает не ext4 и не CRAMFS, а JFFS2 или UBIFS — они встречаются на устройствах с raw NAND. Их нельзя просто примонтировать как файл-образ: JFFS2 читается через `jefferson`, а UBIFS требует `ubireader` (сначала `ubireader_extract_images`, потом `ubireader_extract_files`). Важно не путать: попытка смонтировать JFFS2 через `mount -o loop` даст ошибку, потому что у неё нет сигнатуры, привязанной к началу, — структура размазана по блокам NAND.

## Частые вопросы

**Почему CRAMFS ограничена 16 МБ на файл?**
Формат использует 24-битное поле для размера, отсюда жёсткий потолок. Для прошивок этого обычно хватает, но крупный бинарник (например, база данных) в CRAMFS не влезет — тогда раздел делают ext4.

**Можно ли писать в CRAMFS?**
Нет, это read-only ФС по дизайну. Чтобы что-то поменять, распаковывают, правят, собирают `mkcramfs` заново и прошивают.

**Зачем вообще `debugfs`, если есть `mount`?**
В контейнере или на машине без root монтирование недоступно, а `debugfs` читает ext напрямую из файла и позволяет вытащить отдельный файл одной командой. Это безопаснее: образ не монтируется в систему, нет риска случайно изменить данные.

**Как понять, какой раздел главный?**
Обычно корневой — тот, где лежат `/bin`, `/etc`, `/sbin`. Прошивочные бинарники и конфиги там же, поэтому секреты ищут именно в корневом разделе, а не в загрузочном.

**Что делать, если `binwalk` не находит границ?**
Формат может быть проприетарным или выровнен нестандартно. Тогда помогает ручной поиск сигнатур (`grep -abo $'\x45\x3d\xcd\x28' image.bin`), анализ таблицы разделов из заголовка загрузчика и просмотр энтропии (`binwalk -E`) — участки с низкой энтропией обычно и есть заголовки ФС, а с высокой — сжатые данные.

## Что мы теперь знаем

По-простому:

1. Прошивка может содержать несколько простых ФС одновременно.
2. Формат определяют по сигнатуре; `file` и `binwalk` делают это автоматически.
3. CRAMFS → `cramfsck -x`; ext4 → `debugfs` или `7z` (без root); cpio → `cpio -idmv`.
4. initramfs — это сжатый архив cpio, а не файловая система.
5. Пересборка: `mkcramfs`, `mkfs.ext4 -d`, `cpio -o`.

## На что смотреть дальше

- **Файл больше 16 МБ.** Значит, это не CRAMFS — вероятно, ext4.
- **Монтирование требует root.** В контейнере используйте `cramfsck -x`, `debugfs`, `7z`.
- **`premature end of file` при cpio.** Не то сжатие — сначала определите его командой `file`.
- **ext4 с журналом.** `debugfs` не «доигрывает» журнал; при сомнениях монтируйте `-o ro,noload`.
- **Пропущенное смещение.** `dd` без `skip` даст мусор — берите offset из `binwalk`.

## Если не сработало

- **`cramfsck` не установлен.** Поставьте пакет `cramfsprogs` или используйте `mount -o loop,ro`.
- **ext4 не читается `debugfs`.** Образ повреждён или это f2fs — проверьте `file` и попробуйте `7z`.
- **`cpio` ругается на формат.** Не то сжатие: определите его `file` и распакуйте `xz -dc`/`lz4 -dc` перед `cpio`.
- **`dd` даёт мусор.** Неверный `skip`/`count` — берите точные значения из `binwalk`.
- **Сигнатура найдена, но ФС не читается.** Формат может быть выровнен не по границе раздела — пересчитайте смещение кратно сектору (512/4096).

## Куда дальше

Мы разобрали простые форматы. Дальше в ветке — журналируемые ФС для NAND: JFFS2 и UBIFS, которые встречаются на «серьёзных» устройствах и требуют эмуляции flash-контроллера. А пока запомни главное: простые ФС разбираются нативными инструментами Linux, и в изолированной среде это делается без root.
