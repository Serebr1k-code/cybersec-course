## Вопрос, с которого всё начинается

В прошлых уроках мы обходили защиты программно: консоль, bootargs, откат прошивки. Но что если память не читается, secure boot включён и отладочный порт закрыт? Тогда остаются **физические** атаки: наблюдение за энергопотреблением и намеренное внесение сбоев.

Вопрос урока: как, не зная пароля, «уговорить» устройство пропустить проверку — и как извлечь ключ, измеряя его потребление?

## Наш пример: учебная плата с проверкой пароля

Перед нами учебная цель **ChipWhisperer** — плата, на которой прошита программа с проверкой пароля. Внутри крутится логика вида «сравни введённое с секретом, при совпадении — разблокируй». Память не читается. Наша цель — попасть внутрь двумя разными способами.

## Шаг 1: два класса атак

**Side-channel analysis** — извлечение информации из физических характеристик работы, а не из логики:

- **SPA (Simple Power Analysis)** — визуальный анализ графика потребления: разные операции дают разные «профили».
- **DPA (Differential Power Analysis)** — статистика по тысячам трасс: корреляция потребления с гипотезами о ключе.
- **CPA (Correlation Power Analysis)** — вариант DPA с корреляцией по модели потребления (Hamming weight).

**Fault injection** (glitching) — намеренная поломка вычисления в нужный момент:

- **Voltage glitching** — короткая просадка питания.
- **Clock glitching** — лишний или пропущенный такт.
- **EM glitching** — импульс электромагнитного поля.

## Шаг 2: почему glitching вообще работает

Смотрите на код:

```c
if (check_password() == OK)
    unlock();
```

Компилятор не обязан быть устойчивым к сбоям. Если сбой произойдёт точно в момент сравнения, ветка `unlock()` может выполниться без верного пароля. Ошибка «проскакивает» проверку.

## Шаг 3: инструменты

- **ChipWhisperer** (Lite/Nano/Husky) — учебный стандарт: захват трасс и глитчер в одном.
- **PicoScope / осциллограф** — захват сигнала питания.
- **ChipWhisperer Capture / Analyzer** — софт для захвата и анализа.

```bash
$ pip install chipwhisperer
$ chipwhisperer
```

Захват трассы в Python выглядит так:

```python
import chipwhisperer as cw
scope = cw.scope()
target = cw.target(scope)
scope.default_setup()
scope.adc.samples = 24400
scope.arm()
target.simpleserial_write('p', key)
scope.capture()
trace = scope.get_last_trace()
```

**Трасса** — массив точек: значения потребления, снятые через равные интервалы времени.

## Шаг 4: обходим проверку пароля глитчингом

1. **Цель.** Найти момент проверки. Если прошивка есть, находим функцию проверки в Ghidra; если нет — ищем по поведению (мигание LED, лог при неверном пароле).
2. **Синхронизация.** Глитчер должен сработать точно в момент сравнения. Триггер — аппаратный сигнал (UART TX, GPIO), а не таймер хоста.
3. **Sweep.** Перебираем ширину и смещение импульса:

```text
offset:  от 0 до N тактов
width:   от 1 до нескольких тактов
```

Для каждого сочетания отправляем неверный пароль и смотрим, «прошло» ли. Успешный глитч = устройство разблокировалось без верного пароля. Один удачный сбой из тысячи — норма.

## Шаг 5: обход secure boot

Аналогично глитчим в момент проверки подписи загрузчика. Иногда достаточно одного удачного сбоя, чтобы ядро загрузилось с изменённым образом — это прямое продолжение урока про secure boot.

## Шаг 6: извлекаем ключ через CPA

Если есть криптооперация (AES) с секретным ключом, работает статистика. Порядок:

1. Собираем 5000–20000 трасс, шифруя известные блоки.
2. Для байта 0 ключа перебираем 256 гипотез.
3. Для каждой считаем `S-box(plaintext ^ key)`.
4. Моделируем потребление (число единичных бит — Hamming weight).
5. Коррелируем модель с трассами (корреляция Пирсона).
6. Гипотеза с максимальной корреляцией — правильный байт.

Повторяем для остальных байт и проверяем ключ на расшифровке. ChipWhisperer поставляется с учебными целями (например, `cw305` с AES) — начинать надо с них.

## Шаг 7: как от этого защищаются

- **Маскирование** — разбить значение на случайные доли.
- **Скрытие** — случайные задержки, перемешивание операций.
- **Constant-time** — устранение зависимостей от данных.
- **Детекторы** аномальных измерений (света, напряжения).

Отдельно стоит подчеркнуть: side-channel — это не «взлом алгоритма». AES остаётся стойким; атакуется **реализация**, которая физически «протекает» данными.

## Шаг 8: почему это вообще возможно

Любая физическая реализация криптографии «протекает»: потребление, электромагнитные эмиссии и время выполнения зависят от обрабатываемых данных и ключа. Side-channel-атака использует эту зависимость, чтобы восстановить секрет, не вскрывая алгоритм.

Ключевое условие — вы можете многократно запускать криптооперацию с **контролируемым входом** (например, шифровать выбранные блоки) и измерять физический сигнал. Именно поэтому смарт-карты, токены и embedded-устройства с локально доступным криптоядром уязвимы: атакующий сам подаёт входные данные и сам снимает трассы.

Важно и то, что атака не требует вскрытия чипа: достаточно осциллографа и математики. Это делает side-channel доступным для CTF и учебных стендов, хотя против защищённых коммерческих чипов нужны десятки тысяч трасс и аккуратная предобработка данных.

## Что мы теперь знаем

1. Side-channel извлекает информацию из потребления/излучения; glitching ломает вычисление.
2. SPA — одна трасса, DPA/CPA — статистика по тысячам.
3. Glitching обходит проверки, потому что код не устойчив к сбоям.
4. Нужен точный аппаратный триггер и sweep по offset/width.
5. CPA на AES восстанавливает ключ по байтам через корреляцию.
6. Защита: маскирование, скрытие, constant-time, детекторы.

## На что смотреть дальше

- **Нет стабильной синхронизации.** Без аппаратного триггера глитч «промахивается».
- **Слишком большой/маленький глитч.** Окно успеха узкое — нужен sweep.
- **Испорченное устройство.** Неудачный глитч может «окирпичить» или стереть память — работайте на копиях.
- **Шум в трассах.** Плохое заземление и длинные провода портят DPA; нужны короткие щупы и экран.
- **Ожидание «магии».** Side-channel требует тысяч трасс и статистики.
- **Правовые ограничения.** Fault injection на чужих устройствах — тяжёлое нарушение.

## Шаг 9: строим карту успеха глитча

Sweep — это не хаос, а построение двумерной карты. Для каждого сочетания (offset, width) несколько раз повторяем попытку и отмечаем, разблокировалось ли устройство:

| offset \ width | 2 | 3 | 4 | 5 |
|----------------|---|---|---|---|
| 120 | · | · | · | · |
| 124 | · | ✓ | ✓ | · |
| 128 | · | · | · | ✗ |
| 132 | · | · | · | · |

`✓` — успешный глитч (устройство открылось), `✗` — сбой, из-за которого цель повисла или перезагрузилась, `·` — без эффекта. Видно, что окно успеха — узкая полоса: width 3–4 при offset 124. Чем уже полоса, тем точнее нужно попадать — и тем важнее стабильный аппаратный триггер.

Одна и та же точка может давать успех не всегда. Поэтому каждую пробуют 5–10 раз и считают долю успехов. «Один удачный сбой из тысячи» — это про редкость попадания в окно, а не про случайность: попав в окно, вы будете попадать снова и снова.

## Если не сработало

- **Глитч никогда не «проходит».** Скорее всего, неверный триггер: глитчер срабатывает не в момент сравнения. Сузьте окно триггера и замените программный таймер на аппаратный сигнал.
- **Цель каждый раз перезагружается.** Импульс слишком широкий или просадка слишком глубокая — уменьшите width и глубину просадки.
- **Устройство перестало отвечать совсем.** Глитч «окирпичил» цель: работайте на копии платы или на учебном стенде ChipWhisperer, а не на единственном экземпляре.
- **DPA не выделяет ключ даже на 20000 трассах.** Проверьте выравнивание трасс (обрезка по триггеру), заземление и модель потребления. Обычно помогает предобработка: синхронизация по точке запуска и фильтрация шума.

## Где проходит граница

Side-channel и glitching — самые дорогие и наименее «чистые» атаки: нужен физический доступ, оборудование и терпение. Поэтому их применяют последними. Прежде чем глитчить secure boot, стоит исключить более простые пути: чтение памяти через отладчик, утечку ключа в прошивке, обход через UART. И обязательно — законность: без письменного разрешения физическое воздействие на чужое устройство недопустимо.

## Шаг 10: захват трасс в ChipWhisperer

CPA/DPA — это не «одна кнопка», а конвейер: захват трасс → выравнивание → корреляция с
моделью утечки. В учебной среде используют **ChipWhisperer**:

```python
import chipwhisperer as cw
scope = cw.scope()
scope.clock.clkgen_freq = 7.37e6
scope.arm(); target.go(); trace = scope.get_last_trace()
```

Набирают 500–2000 трасс при случайных данных, затем считают корреляцию Пирсона между
каждым семплом и моделью (обычно **Hamming weight** промежуточного значения после
подстановки S-box). Пик корреляции на конкретном семпле указывает правильный байт ключа.

Типичные сложности: **несинхронные трассы** (нужно выравнивание по триггеру), **шум**
(усреднение/фильтрация), **маска-контрмеры** (корреляция резко падает, нужен более
высокий порядок или учёт маски). Поэтому перед атакой проверяют, что триггер стабилен, а
число трасс достаточно: для немаксированного AES обычно хватает тысяч, для
замаскированного — на порядки больше.

## Куда дальше

Мы научились вытаскивать секреты физикой. Дальше по дереву применим это к криптографии встраиваемых устройств: где искать ключи, как ломать слабый RNG и как защищаться. А пока главное: **если устройство не защищено от физических измерений, программные проверки — лишь видимость.**

## Где пригодится

- **CTF:** продвинутые Hardware-задачи, где защита снимается физически.
- **Пентест:** оценка secure boot, смарт-карт, HSM, защищённых микроконтроллеров.
- **Bug bounty:** редко; в основном в аппаратных программах вендоров.
- **Работа:** hardware security research, сертификация (Common Criteria, FIPS), разработка защищённых чипов.
- **Дальше по дереву:** `hardware-crypto`, `hardware-power-analysis`.
