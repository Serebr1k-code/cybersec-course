## Вопрос, с которого всё начинается

В прошлом уроке мы узнали, что загрузчик в embedded-устройствах почти всегда — U-Boot, и что через его консоль можно получить root. Но у U-Boot есть и вторая жизнь: его **окружение** — набор настроек — лежит прямо в прошивке отдельным блоком. Что если забрать это окружение из дампа и прочитать спокойно, а потом ещё и подсунуть плате свой образ?

Разберём U-Boot по-настоящему — с двух сторон: из дампа и с живой консоли.

## Наш пример: окружение роутера в дампе

У нас на руках `dump1.bin` — полный образ SPI-флеша роутера из урока про SPI. `binwalk` показал, что по смещению `0x40000` (это 262144 байт) лежит **окружение U-Boot**. Окружение — это обычный текст вида `ключ=значение`, и оно часто хранит больше, чем кажется.

Начнём с того, что достанем его из дампа, а затем сверимся с живой консолью.

## Шаг 1: вырезаем окружение из образа

Вырежем кусок начиная с `0x40000` утилитой `dd` и посмотрим на него как на текст:

```
$ dd if=dump1.bin of=env.bin bs=1 skip=$((0x40000)) count=$((0x10000))
65536 bytes copied
$ strings -n 4 env.bin
baudrate=115200
bootdelay=1
bootcmd=sf probe 0; sf read 0x80000000 0x100000 0x400000; bootm 0x80000000
bootargs=console=ttyS0,115200 root=/dev/mtdblock4 rw
ipaddr=192.168.1.1
serverip=192.168.1.10
```

`strings` вытаскивает из бинарного файла куски читаемого текста. Мы видим те самые переменные. Разберём главные:

| Переменная | Смысл |
|-----------|-------|
| `bootcmd` | команды обычной автозагрузки |
| `bootargs` | аргументы, передаваемые ядру Linux |
| `ipaddr`/`serverip` | сетевые адреса устройства и сервера |
| `baudrate` | скорость консоли |
| `bootdelay` | пауза перед автозагрузкой |

Заметили `bootdelay=1`? Это значит, что на нажатие клавиши для прерывания загрузки даётся всего одна секунда. Меняется она тем же `setenv`.

## Шаг 2: правим окружение с консоли

Подключаемся по UART, ловим `Hit any key to stop autoboot` и попадаем в `=>`. Смотрим окружение целиком и меняем ключевые поля:

```
=> printenv bootargs
bootargs=console=ttyS0,115200 root=/dev/mtdblock4 rw
=> setenv bootargs 'console=ttyS0,115200 root=/dev/mtdblock4 rw init=/bin/sh'
=> saveenv
Saving Environment to SPI Flash... done
=> boot
```

`printenv` показывает переменную, `setenv` присваивает новое значение, `saveenv` пишет его обратно во флеш. Если `saveenv` отвечает ошибкой — область окружения защищена от записи, и правка будет действовать только до перезагрузки.

## Шаг 3: загружаем свой образ по сети

Второй мощный приём — заставить U-Boot загрузить не свою систему, а нашу. Для этого на хосте поднимают **TFTP** — простой протокол передачи файлов по сети, которым умеет пользоваться U-Boot. Кладём в его корень файл `rescue.itb` (спасательный образ) и указываем плате, где его искать:

```
=> setenv ipaddr 192.168.1.50
=> setenv serverip 192.168.1.10
=> tftpboot 0x81000000 rescue.itb
Bytes transferred = 4194304 (0x400000)
=> bootm 0x81000000
```

`tftpboot` скачивает файл в память по адресу `0x81000000`, `bootm` запускает то, что там оказалось. Так можно загрузить собственную систему с shell, не перепрошивая устройство вообще.

## Шаг 4: что такое FIT-образ

Файл `rescue.itb` — это **FIT-образ** (Flattened Image Tree). FIT — контейнер, внутри которого упакованы сразу ядро, описание железа (**device tree**, DTB) и, при желании, подпись. Собирают его на хосте утилитой `mkimage`:

```
$ mkimage -A arm -O linux -T kernel -C none -a 0x80008000 -e 0x80008000 \
    -n "Linux" -d zImage uImage
Image Name:   Linux
Created:      Mon Oct 12 10:00:00 2026
Image Type:   ARM Linux Kernel Image (uncompressed)
Data Size:    4194304 Bytes
```

Посмотреть заголовок уже готового образа можно той же утилитой с флагом `-l`. А если FIT подписан (RSA-подпись), то подменить образ своим не получится — это уже часть механизма secure boot.

## Шаг 5: восстанавливаем окирпиченное устройство

Если плата не грузится, но U-Boot жив, он же и спасает. Стираем флеш и записываем по сети нормальный образ:

```
=> tftpboot 0x80000000 recovery.bin
=> sf probe 0
=> sf erase 0x0 0x800000
=> sf write 0x80000000 0x0 ${filesize}
=> reset
```

`${filesize}` — переменная, в которую U-Boot сам записал размер только что скачанного файла. `sf erase` очищает область, `sf write` пишет новый образ. Если и U-Boot повреждён, понадобится программатор или режим bootROM.

## Шаг 6: работаем с разделами, а не со всей флеш

Выгружать весь флеш каждый раз неудобно. U-Boot знает про **разделы** — именованные области памяти (загрузчик, env, ядро, rootfs, данные). Команда `mtdparts` (от «Memory Technology Device») показывает раскладку:

```
=> mtdparts
device nor0 <spi0.0>, # parts = 5
 0: uboot    0x00000000 0x00040000
 1: env      0x00040000 0x00010000
 2: kernel   0x00050000 0x00300000
 3: rootfs   0x00350000 0x00a00000
 4: data     0x00d50000 0x002b0000
```

Теперь можно читать и писать только нужный кусок — скажем, перепрошить лишь ядро, не трогая rootfs. Та же раскладка видна внутри работающей системы в файле `/proc/mtd`.

## Шаг 7: что ещё прячет окружение

Список переменных из примера выглядит безобидно, но в реальных устройствах env — это часто «кладовка» секретов. Производители складывают туда то, что должно быть доступно загрузчику до монтирования ФС: пароль загрузчика, адрес и учётные данные для автообновления, иногда ключ подписи, заводской MAC и серийный номер. Особенно интересны переменные с префиксами производителя (`hw_`, `oem_`, `wifi_`): по ним видно, как устройство получает конфигурацию. Практический приём: вырезав env из дампа, прогоните `strings -n 4 env.bin` и просмотрите всё — не только `bootargs`. Если в env есть `password=`, это может быть хеш пароля загрузчика, который иногда ломается офлайн. И наоборот: перед `env default -a` (сбросом) обязательно сохраните текущий env — там уникальные значения, которых больше нигде нет.

## Почему окружение — «кладовая» и как её защищают

Окружение — это компромисс между удобством и безопасностью. Загрузчику нужны параметры (откуда грузить, с какими аргументами, какие адреса), и хранить их в самом U-Boot неудобно: они меняются от модели к модели и от версии к версии. Поэтому их выносят в отдельный записываемый блок. Проблема в том, что этот блок обычно не защищён: его можно прочитать из дампа и изменить с консоли. Защита возможна — включить secure boot (подписывать FIT), запретить запись env (`saveenv` даёт ошибку), закрыть консоль паролем, — но на большинстве устройств этого нет, потому что «и так работает». Отсюда практический вывод для пентеста: если есть дамп прошивки, начинайте с env — это самый дешёвый способ узнать модель загрузки и найти секреты.

## Частые вопросы

**Что делать, если `saveenv` возвращает ошибку?**
Это значит, что область окружения защищена от записи (например, раздел env помечен read-only или в U-Boot запрещена запись env). Тогда правка `bootargs` действует только в текущей сессии до перезагрузки. Этого часто достаточно, чтобы один раз загрузиться с `init=/bin/sh` и сделать что нужно (например, прочитать или изменить rootfs).

**Почему `bootdelay=1` — проблема?**
Одна секунда — очень короткое окно, чтобы успеть нажать клавишу и прервать автозагрузку, особенно вручную. Решение: подключиться заранее и удерживать клавишу или слать символы потоком (скриптом), либо изменить `bootdelay` в env (если можете записать) и перезагрузиться. На некоторых устройствах `bootdelay=-1` вообще отключает прерывание.

**Как узнать, подписан ли FIT?**
Посмотрите заголовок: `mkimage -l rescue.itb` покажет, есть ли у образа подпись и какие ключи используются. Если подпись есть, а в env включена проверка, подмена образа не пройдёт — ядро откажется его загружать. Тогда вектор — либо правка env (если разрешена), либо работа с самим SPI (программатор), либо поиск уязвимости в проверке подписи.

**Можно ли по TFTP грузить что угодно?**
Технически U-Boot скачает любой файл с TFTP-сервера, но запустить (`bootm`) он сможет только корректный образ с правильной архитектурой и (при secure boot) валидной подписью. Поэтому свой rescue-образ надо собрать под ту же архитектуру, что и устройство (например, ARM), и указать корректный `loadaddr`, иначе `bootm` упадёт.

## Что мы теперь знаем

По-простому:

1. Окружение U-Boot — это текст `key=value`, лежащий в прошивке отдельным блоком.
2. `printenv`/`setenv`/`saveenv` читают, меняют и сохраняют его.
3. `bootdelay=1` почти не даёт времени прервать загрузку — его увеличивают.
4. `tftpboot` + `bootm` запускают ваш образ без перепрошивки.
5. FIT — контейнер с ядром, DTB и (иногда) подписью; собирается `mkimage`.

## На что смотреть дальше

- **`bootargs` без `console=`.** Вы теряете консоль и не видите загрузку — всегда оставляйте `console=`.
- **Неверный `loadaddr`.** Образ грузится поверх нужных данных и падает.
- **TFTP-таймауты.** Проверьте `serverip`, маску сети и firewall.
- **Подписанный FIT.** При включённом secure boot неподписанный образ не загрузится.
- **Сброс окружения.** Перед `env default -a` сохраните текущий env — там MAC и серийный номер устройства.

## Как это выглядит целиком

Маршрут в одну историю: `dd` вырезает env по `0x40000`, `strings` показывает `bootcmd`/`bootargs`/`bootdelay=1`. С UART-консоли `setenv bootargs ... init=/bin/sh`, `saveenv`, `boot` — получаем shell. Для восстановления: `tftpboot 0x80000000 recovery.bin`, `sf probe 0`, `sf erase 0x0 0x800000`, `sf write 0x80000000 0x0 ${filesize}`, `reset`. `mtdparts` показывает разделы, чтобы перепрошить только ядро. От дампа до восстановления платы.

## Куда дальше

Мы прошли U-Boot вдоль и поперёк: окружение, правку `bootargs`, загрузку своих образов. Дальше спустимся ещё глубже — к самому первому коду на плате, bootROM, который зашит в кремний и не меняется никогда. А пока запомни: окружение U-Boot — это текст в прошивке, и он часто открывает больше, чем сама система.
