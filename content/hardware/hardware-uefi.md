## Вопрос, с которого всё начинается

В прошлом уроке мы обходили secure boot на встраиваемом роутере. Но такой же механизм есть и на обычном компьютере — только там он называется **UEFI** (Unified Extensible Firmware Interface). Это прошивка, которая запускается до операционной системы и имеет полный доступ к железу.

Вопрос урока: где живёт эта прошивка, как её прочитать и что будет, если поместить туда вредоносный код? Спойлер: такой код переживёт переустановку операционной системы.

## Наш пример: ноутбук с прошивкой в SPI-флеш

Перед нами ноутбук, к которому у нас есть физический доступ. Прошивка UEFI лежит в **SPI-флеш** на материнской плате — той же микросхеме, что мы снимали с роутера, только крупнее (8–32 МБ). Цель — понять, можно ли внедрить **буткит** (вредоносный код в прошивке), и оценить защиты.

Сначала посмотрим, из чего вообще состоит прошивка:

| Компонент | Носитель | Роль |
|-----------|----------|------|
| UEFI/BIOS | SPI-флеш (8–32 МБ) | инициализация железа, загрузка ОС |
| Intel ME / AMD PSP | часть SPI | управление, защита |
| NVRAM | SPI | переменные (в т.ч. Secure Boot) |
| Опциональные ROM | PCIe | прошивки устройств |

## Шаг 1: извлекаем прошивку

Прочитать SPI можно двумя способами. Программно из-под Linux — если флеш не защищена от записи:

```bash
$ sudo flashrom -p internal -r bios.bin
Reading flash... done.
```

Или офлайн — программатором CH341A с клипсой (как в уроке про SPI), тогда ноутбук обесточен и никакая защита не мешает:

```bash
$ sudo flashrom -p ch341a_spi -r bios.bin
Found Macronix flash chip "MX25L12805D" (16384 kB, SPI).
```

Мы получили дамп `bios.bin`. Дальше — резервная копия обязательна: без неё обратная запись может превратить ноутбук в «кирпич».

## Шаг 2: разбираем структуру

Прошивка UEFI — это контейнер из **томов**, **файлов** и **секций**. Разбирать её удобно инструментом **UEFITool** (структура) и **UEFIExtract** (извлечение модулей):

```bash
$ UEFIExtract bios.bin
$ ls bios.bin.dump | head
0 UEFI_APPLICATION  ...  Setup
1 DXE_DRIVER        ...  PchInit
2 DXE_DRIVER        ...  AhciController
```

Что искать в разборе:

- **DXE-драйверы** — исполняемый код UEFI (обычные PE-файлы, их можно открыть в Ghidra).
- **SMM** (System Management Mode) — режим максимальных привилегий; уязвимости там критичны.
- **NVRAM-переменные** — `SecureBoot`, `db`, `dbx`, `PK`, `KEK`.
- **Модули вендора** — часто с недостаточной валидацией входных данных.

Быстрый поиск интересных строк:

```bash
$ strings -a bios.bin | grep -iE 'SecureBoot|Setup|password|Admin'
SecureBoot
Setup
AdminPassword
```

Отдельно стоит поискать **UEFI Shell** — это встроенный в прошивку командный интерпретатор. Если он доступен, можно запускать EFI-приложения до загрузки ОС, а иногда и обойти проверки. Ещё один частый класс багов — **SMM callout**: обычный DXE-драйвер вызывает код SMM и передаёт ему невалидированный указатель, из-за чего получает выполнение в максимально привилегированном режиме.

## Шаг 3: что проверяет Secure Boot

**Secure Boot** проверяет подпись загрузчиков по базам ключей. `db` — разрешённые, `dbx` — отозванные, `PK` — платформенный ключ, `KEK` — ключ обмена. Если загрузчик не подписан доверенным ключом — загрузка блокируется.

Состояние можно посмотреть из-под Linux:

```bash
$ mokutil --sb-state
SecureBoot enabled
$ efibootmgr -v
BootCurrent: 0001
```

Типовые обходы:

- **Уязвимый подписанный загрузчик** — если `db` содержит загрузчик с CVE (класс BootHole).
- **Отключение через NVRAM** — при админском/физическом доступе `SecureBoot=0`.
- **SBAT-обходы** — старые загрузчики с известными багами.
- **Неполнота `dbx`** — отсутствие отзыва нужного загрузчика.

## Шаг 4: аудит платформы через chipsec

**CHIPSEC** — фреймворк для проверки конфигурации прошивки и защит платформы. Перед «атакой» им проверяют, что вообще открыто:

```bash
$ sudo python3 chipsec_main.py -m common.bios_wp
[+] BIOS region write protection is enabled
```

`common.bios_wp` показывает, защищён ли BIOS от записи. Если **не** защищён, атакующий с локальным доступом может перезаписать прошивку. Ещё смотрим переменные Secure Boot и делаем дамп SPI:

```bash
$ chipsec_main -m common.secureboot.variables
$ chipsec_util uefi var-list
$ chipsec_util spi dump firmware.bin
```

## Шаг 5: почему буткит так опасен

Собрав всё вместе, проигрываем сценарий внедрения буткита:

1. Считываем SPI программатором: `flashrom -p ch341a_spi -r bios.bin`.
2. Открываем в UEFITool, находим DXE-драйверы и SMM-модули.
3. Проверяем защиты: **Boot Guard** (подпись ключевых модулей) и **BIOS Write Protect**.
4. Если защиты слабы — модифицируем модуль или подменяем загрузчик и прошиваем обратно.
5. В операционной системе буткит незаметен — **переустановка ОС его не удаляет**.

Вот в чём суть: прошивка — это постоянная точка присутствия, живущая «ниже» операционной системы. Именно поэтому её анализируют и защищают отдельно.

## Шаг 6: как защищаются

- **Boot Guard / Verified Boot** — подпись ключевых модулей прошивки.
- **BIOS Write Protect** — запрет записи из ОС.
- **Измерения в TPM** (регистры PCR) — детект изменений прошивки.
- **CHIPSEC** — регулярный аудит конфигурации.

## Почему прошивочный имплант так трудно обнаружить

Главная причина — прошивка находится «ниже» всех инструментов, которыми её ищут. Антивирус работает в операционной системе, а код в SPI исполняется до неё и может влиять на то, что ОС увидит: например, подменять данные, отдаваемые по ACPI или SMBIOS, скрывать изменения в файлах, перехватывать загрузку. Форензика «изнутри» системы поэтому почти бесполезна — чтобы найти имплант, нужен либо внешний программатор (снять SPI и сравнить с эталоном), либо измерения TPM (регистры PCR), либо CHIPSEC, который читает железо напрямую. Отсюда практический вывод для защитника: доверять системе, работающей на подозрительном железе, нельзя — нужен независимый канал проверки.

## Почему Secure Boot — не панацея

Secure Boot проверяет подписи, но его модель доверия шире, чем кажется. Он доверяет всему, что подписано ключом из `db` — а туда попадают десятки загрузчиков и драйверов от разных вендоров, и любой из них с уязвимостью становится «легальной дверью» (класс BootHole). Кроме того, база отзыва `dbx` обновляется с задержкой, поэтому скомпрометированный подписанный загрузчик ещё какое-то время работает. И, наконец, при физическом или административном доступе Secure Boot просто выключают в настройках. Итог: Secure Boot закрывает класс «случайный самодельный загрузчик», но не защищает от эксплуатируемого доверенного кода и не спасает при физическом доступе.

## Частые вопросы

**Чем UEFI-буткит отличается от руткита в ОС?**
Руткит живёт внутри операционной системы: переустановка ОС или загрузка с чистого носителя его удаляет. UEFI-буткит лежит в SPI-флеш на плате и исполняется до ОС, поэтому переживает переустановку, смену диска и часто незаметен антивирусу. Единственный надёжный способ убрать его — перепрошить SPI эталонным образом.

**Что даёт физический доступ по сравнению с удалённым?**
При удалённой атаке вы ограничены тем, что доступно через ОС и сеть, а прошивка обычно защищена от записи (BIOS Write Protect) и подписана (Boot Guard). При физическом доступе вы можете подключиться программатором прямо к микросхеме, обойдя все программные защиты, — если только производитель не зашифровал прошивку и не запер доступ (например, Intel Boot Guard с fused-ключом).

**Зачем анализировать SMM-модули?**
SMM (System Management Mode) работает на самом высоком уровне привилегий и невидим для ОС. Уязвимость там (например, SMM callout, когда обычный драйвер передаёт SMM невалидированный указатель) даёт выполнение кода с полным доступом к памяти и железу, минуя все защиты ядра. Поэтому SMM — приоритетная цель при аудите прошивки.

**Как понять, что прошивку изменили?**
Сравнить дамп SPI с эталонным образом от производителя (побайтово или по модулям через UEFITool) и проверить измерения TPM: если значения PCR расходятся с ожидаемыми, значит, что-то в цепочке загрузки изменилось. Регулярный CHIPSEC-аудит и мониторинг PCR — практическая защита.

## Что мы теперь знаем

1. Прошивка UEFI живёт в SPI-флеш на материнской плате, рядом с Intel ME/AMD PSP.
2. Читают её через `flashrom` — программно из ОС или программатором офлайн.
3. Структуру разбирают UEFITool/UEFIExtract; модули — обычные PE-файлы.
4. Secure Boot проверяет подпись загрузчиков по `db`/`dbx`; обходится уязвимым загрузчиком или доступом к NVRAM.
5. CHIPSEC показывает, защищён ли BIOS от записи и включён ли Secure Boot.
6. Буткит в прошивке переживает переустановку ОС — это постоянная точка присутствия.

## На что смотреть дальше

- **Не думайте, что переустановка ОС удалит буткит.** UEFI-имплант переживает её.
- **Не игнорируйте SMM.** Уязвимости в System Management Mode дают максимальные привилегии.
- **Проверьте Boot Guard.** Он блокирует модификацию прошивки — без него внедрение возможно.
- **Всегда делайте бэкап дампа** перед прошивкой, иначе «кирпич».
- **Помните про ME/PSP.** Это отдельная прошивка со своими уязвимостями.
- **Правовые рамки.** Модификация чужого железа — только с разрешения.
