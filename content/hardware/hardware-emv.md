EMV — стандарт чиповых платёжных карт. Карта — это смарт-карта с криптографией, которая аутентифицирует транзакцию. Урок разбирает техническую сторону EMV (APDU, бесконтактный режим) и известные классы атак — исключительно для понимания защиты и в рамках закона.

## Теория

EMV-карта поддерживает:
- **Контактный интерфейс** (ISO 7816) — 8 контактов.
- **Бесконтактный** (ISO 14443, NFC) — PayPass/PayWave.
- **Приложения**: каждая карта имеет AID (например, `A0000000031010` — Visa).

Транзакция (упрощённо):
1. SELECT PPSE / AID.
2. Read Application Data (PAN, expiry, сертификаты).
3. GET PROCESSING OPTIONS.
4. READ RECORD (данные транзакции).
5. GENERATE AC (Generate Application Cryptogram) — карта выдаёт криптограмму, подписанную её ключом.

Стандартные APDU:
| Команда | INS | Назначение |
|---------|-----|-----------|
| SELECT | A4 | выбрать приложение |
| GET PROCESSING OPTIONS | A8 | начать транзакцию |
| READ RECORD | B2 | читать записи |
| GENERATE AC | AE | сгенерировать криптограмму |
| VERIFY | 20 | PIN |

Известные классы атак (исторические/исследовательские):
- **Replay/relay** бесконтактной транзакции (NFC relay).
- **Downgrade** — принуждение к fallback (магнитная полоса).
- **PIN bypass** в офлайн-режиме (при отсутствии онлайн-аутентификации).
- **Fault injection** на чип для обхода проверок (в лаборатории).
- **Skimming** магнитной полосы (не чипа) — старая угроза.

Современные карты (DDA/CDA, online PIN) устойчивы; многие «атаки» требуют физического доступа и специального оборудования.

## Инструменты и команды

- **pyscard + ридер ACR122U** — чтение бесконтактных карт.
- **pcsc-tools** (`pcsc_scan`) — определение.
- **EMV-библиотеки** (например, `emv` на Python).
- **Proxmark3** — анализ ISO14443.
- **Smartcard reader** — контактный интерфейс.

```bash
# Читаем PPSE бесконтактной карты (только своя карта!)
python - <<'PY'
from smartcard.System import readers
from smartcard.util import toHexString
r = readers()[0]; c = r.createConnection(); c.connect()
# SELECT PPSE
apdu = [0x00,0xA4,0x04,0x00,0x0E]+list(b'2PAY.SYS.DDF01')
data, sw1, sw2 = c.transmit(apdu)
print(f'PPSE SW={sw1:02X}{sw2:02X}', toHexString(data))
PY

# pcsc_scan покажет ATR и тип
pcsc_scan
```

## Разобранный пример: разбор бесконтактной карты (своя)

**Дано:** своя бесконтактная карта, ACR122U. Цель — понять, какие данные отдаёт карта.

**Шаг 1 — SELECT PPSE.** Отправляем `00 A4 04 00 0E 2PAY.SYS.DDF01`. Получаем список приложений (AID).

**Шаг 2 — SELECT AID.** Выбираем приложение (например, Visa AID). Получаем FCI с версией.

**Шаг 3 — Read Application Data.** Читаем записи: PAN (номер карты), expiry, имя. Для защиты PAN часто маскируется (частично), но исторически был риск полного PAN.

**Шаг 4 — GPO.** `80 A8 00 00 ...` — карта возвращает AIP и AFL (указывает, какие записи читать).

**Шаг 5 — READ RECORD.** Читаем записи транзакции по AFL.

**Шаг 6 — GENERATE AC.** Формируем криптограмму — карта подписывает данные. Это ядро аутентификации; без ключей банка подделать нельзя.

**Шаг 7 — границы.** Мы можем читать публичные данные, но не можем (и не должны) проводить реальные транзакции без авторизации. Демонстрация уязвимостей — только на тестовых картах/в лаборатории эмитента.

## Частые ошибки

- **Попытка реальной транзакции.** Это мошенничество. Никогда не проводите реальные платежи.
- **Чтение чужих карт.** Незаконно. Только своя/тестовая карта.
- **Ожидание полного PAN.** Современные карты не отдают полный PAN бесконтактно.
- **Игнорирование SDA/DDA/CDA.** Понимание метода аутентификации важно: DDA/CDA стойкие, SDA слабее.
- **Скимминг магнитной полосы.** Это отдельная (старая) угроза, не EMV-чипа.
- **Отсутствие авторизации.** Любая работа с платёжными системами требует письменного разрешения (PCI DSS, эмитент, программа bug bounty).

## Теория: EMV и бесконтактные карты

EMV (Europay/Mastercard/Visa) — стандарт банковских карт. Бесконтактные (NFC) работают по ISO 14443. Обмен: SELECT (выбор приложения), GPO (get processing options), READ RECORD, GENERATE AC (криптограмма). Данные, читаемые без PIN: PAN, срок, имя — их достаточно для некоторых мошеннических схем (например, покупки без верификации на малые суммы).

## Инструменты

```bash
# чтение бесконтактной карты (своей!)
proxmark3 /dev/ttyACM0
hf search
hf 14a reader
# с ACR122U
pcsc_scan
# эмуляция/анализ — собственные карты и тестовые стенды
```

Важно: работать только со своими картами и в рамках закона. Тестирование чужих карт — незаконно.

## Разобранный пример 2: разбор своей карты

1. `hf search` определяет тип (Mifare DESFire / EMV).
2. `hf 14a reader` показывает UID.
3. Эмуляция EMV-транзакции на тестовом терминале.
4. Анализ, какие данные отдаются без аутентификации.
5. Вывод: PAN и срок доступны; криптограмма требует ключей карты.

## Таблица защиты

| Механизм | Что защищает |
|----------|--------------|
| CVV/CVC | онлайн-транзакции |
| iCVV (чип) | подделка магнитной полосы |
| DDA/CDA | клонирование карты |
| PIN | офлайн-транзакции |
| Токенизация | замена PAN на токен |

## Токенизация и мобильные платежи

Apple Pay / Google Pay используют токенизацию: PAN заменяется токеном, привязанным к устройству. Реальные данные карты не передаются мерчанту. Для атакующего это означает: перехват NFC-транзакции не даёт PAN. Криптограмма формируется Secure Element, извлечь ключи оттуда крайне сложно.

## Защита

- Токенизация вместо PAN.
- DDA/CDA (динамическая аутентификация данных).
- Лимиты на бесконтактные транзакции.
- Мониторинг аномалий транзакций.
- Для терминалов — аттестация и шифрование PIN-блока (DUKPT).

## Практика

С собственной картой: считайте публичные данные (PAN, срок), объясните, какие механизмы защищают транзакции (криптограмма, CDA), и почему перехват не даёт полноценного клона. Оформите вывод: какие данные доступны без аутентификации, а какие защищены ключами карты.

## Итог

Бесконтактные платежи защищены криптографией карты и токенизацией: публичные данные (PAN, срок) читаются, но полноценный клон невозможен без ключей Secure Element. Работайте только со своими картами; тестирование чужих незаконно. Для защиты — токенизация, DDA/CDA и лимиты.

## Криптограмма, CDA и почему клон невозможен

При оплате карта генерирует криптограмму (ARQC) на основе ключа, известного только карте и банку-эмитенту. Терминал передаёт криптограмму в банк, который проверяет её. Без ключа карты сгенерировать валидную криптограмму невозможно, поэтому простой клон данных (PAN + срок) не проходит онлайн-проверку. DDA (Dynamic Data Authentication) и CDA (Combined DDA) дополнительно защищают от клонирования: карта доказывает владение приватным ключом в реальном времени.

Именно поэтому перехват NFC-обмена (например, через проксимити-атаку) даёт лишь публичные данные, но не позволяет совершить произвольную транзакцию. Единственные реальные векторы — relay-атака (ретрансляция сигнала в реальном времени на другой терминал) и компромисс терминала/эмитента, а не клонирование карты. Для защитника это означает: основной риск смещается с карты на терминалы и процессинг, где нужны аттестация, шифрование PIN-блока (DUKPT) и мониторинг аномалий.

С практической точки зрения в пентесте NFC-платежей вы работаете с собственными картами и тестовыми терминалами, анализируя, какие данные отдаются без аутентификации, и демонстрируя, что криптографически защищённые поля недоступны. Это законный и корректный подход: показать границу между «читаемо» и «подделываемо».
