## Вопрос, с которого всё начинается

Ты купил USB-адаптер «для пентеста», воткнул в ноутбук, запустил `airmon-ng start wlan0` — а `tshark` показывает только broadcast и ничего полезного. Значит, адаптер не видит чужие кадры. Почему так и что вообще означают «кадры», «каналы» и «monitor mode»? Начнём с самого эфира.

## Наш пример: один дамп с одной точкой доступа

Возьмём файл `capture.pcap` — запись эфира на канале 6, где работает одна точка доступа с SSID `office`. Первым делом смотрим, какие кадры вообще есть:

```
$ tshark -r capture.pcap -Y 'wlan.fc.type == 0' -T fields -e wlan.fc.type_subtype | sort | uniq -c
    412 8      # beacon
     37 4      # probe request
     21 5      # probe response
     12 11     # authentication
      9 0      # association request
```

Мы отфильтровали management-кадры (`type == 0`) и увидели: точка доступа 412 раз рекламировала себя beacon-кадром, клиенты слали probe request, шла аутентификация и ассоциация. Это и есть «жизнь» Wi-Fi-сети — обмен служебными кадрами.

## Шаг 1: три типа кадров 802.11

802.11 делит все кадры на три класса:

- **Management (type 0)** — служебные: beacon, probe, authentication, association, deauth. Они не несут данных, но управляют сетью.
- **Control (type 1)** — подтверждения и управление доступом к среде: ACK, RTS, CTS, Block Ack.
- **Data (type 2)** — собственно данные (в защищённой сети — зашифрованные).

Именно management-кадры нас интересуют в первую очередь: из beacon видно SSID и возможности точки, из probe — какие сети ищут клиенты, а deauth/disassoc — инструмент для атак.

## Шаг 2: каналы и ширина

Каждый кадр передаётся на некоторой частоте — **канале**. В диапазоне 2.4 ГГц каналы 1–13, в 5 ГГц — десятки, в 6 ГГц (Wi-Fi 6E) — ещё больше. Посмотрим, на каком канале работает наша точка:

```
$ tshark -r capture.pcap -Y 'wlan.fc.type_subtype == 8' -T fields -e wlan.ssid -e radiotap.channel.freq -c 1
office  2437
```

2437 МГц — это канал 6. Частота важна, потому что **один адаптер слушает один канал за раз**: чтобы увидеть сеть на канале 36, надо переключиться туда. Ширина канала (20/40/80/160 МГц) влияет на скорость и на то, сколько соседних каналов «перекрывается».

## Шаг 3: monitor mode и почему без него ничего не видно

Обычная сетевая карта в **managed mode** отбрасывает любой кадр, не адресованный ей: драйвер отдаёт ОС только «свою» сеть. Чтобы видеть весь эфир, адаптер переводят в **monitor mode** — режим, в котором драйвер передаёт вверх все кадры без фильтрации.

```
$ iw dev wlan0 set type monitor
$ iw dev wlan0 info
Interface wlan0
        type monitor
        channel 6 (2437 MHz), width: 20 MHz
```

Если после этого `tshark` всё равно видит мало — дело в **чипсете**. Не все адаптеры умеют injection (отправку) и полноценный monitor: Realtek многих моделей режут часть кадров, а Atheros/MediaTek/MEDIATEK MT7921 и старые Atheros AR9271 славятся поддержкой. Поэтому «чипсет важнее софта»: программно не включить то, чего драйвер не отдаёт.

## Шаг 4: что видно в beacon

Beacon-кадр — это «визитная карточка» точки. Из него берут SSID, поддерживаемые скорости, тип защиты и возможности:

```
$ tshark -r capture.pcap -Y 'wlan.fc.type_subtype == 8'     -T fields -e wlan.ssid -e wlan.rsn.akms.type -c 1
office  1
```

`rsn.akms.type == 1` — это PSK (WPA2-Personal). Значение `2` было бы WPA-Enterprise, `8` — SAE (WPA3). Уже по одному кадру видно, какую сеть мы имеем и какой класс атак применим.

## Шаг 5: probe request как разведка клиентов

Клиенты постоянно шлют **probe request** — «есть ли тут моя сеть?». В этих кадрах иногда светится SSID сети, которую клиент ищет, даже если она скрыта:

```
$ tshark -r capture.pcap -Y 'wlan.fc.type_subtype == 4' -T fields -e wlan.ssid | sort -u
office
HomeNet
<MISSING>
```

Это даёт список известных клиенту сетей — материал для Evil Twin и для понимания, куда ходит сотрудник.

## Что мы теперь знаем

- 802.11 делит кадры на management/control/data; начинаем с management.
- Кадр живёт на конкретном канале и частоте; адаптер слушает один канал за раз.
- Monitor mode снимает фильтрацию драйвера; без поддержки чипсета часть кадров теряется.
- Beacon даёт SSID и тип защиты, probe request — сети, которые ищет клиент.

## Шаг 6: radiotap — метаданные радиуровня

До сих пор мы читали поля 802.11, но у каждого кадра есть ещё «обёртка» — **radiotap-заголовок**. Это набор метаданных, которые драйвер прикладывает к кадру: на какой частоте он принят, с какой мощностью, каким темпом. Именно radiotap отличает запись эфира от обычного дампа проводной сети.

```
$ tshark -r capture.pcap -c 1 -T fields \
    -e radiotap.channel.freq -e radiotap.dbm_antsignal -e radiotap.datarate
2437     -42     54
```

Здесь `-42 dBm` — уровень сигнала (чем ближе к нулю, тем громче точка), а `54` — скорость в Мбит/с. По уровню сигнала судят о близости: точка с `-35` почти наверняка за стеной рядом, `-80` — далеко. Это первое, что смотрят при поиске rogue-точки внутри офиса: обойти здание с адаптером и найти место, где чужой BSSID «звучит» громче всего.

## Шаг 7: диапазоны 2.4, 5 и 6 ГГц

Каналы не разбросаны хаотично — они лежат в трёх диапазонах, и от диапазона зависит и дальность, и «забитость».

| Диапазон | Каналы | Ширина канала | Особенности |
|---|---|---|---|
| 2.4 ГГц | 1–13 (14 в Японии) | 20/40 МГц | дальнобойный, но всего 3 неперекрывающихся канала (1/6/11) |
| 5 ГГц | 36–165 | 20/40/80/160 МГц | больше каналов, часть под DFS (радар) |
| 6 ГГц (Wi-Fi 6E) | 1–233 | до 160 МГц | новый, пока свободный, только Wi-Fi 6E-устройства |

Ключевой практический вывод: в 2.4 ГГц соседние каналы **перекрываются**, поэтому точка на канале 3 «глушит» и канал 1, и канал 6. В 5 ГГц каналы шире и почти не пересекаются, зато часть из них — **DFS**: если точка слышит радар (метео/авиа), она обязана уйти с канала. Иногда «пропавшая» сеть — это не атака, а DFS-переключение, и это важно не спутать при разборе инцидента.

Ещё одно следствие: **один адаптер слушает один канал за раз**. Если у тебя один интерфейс, ты не увидишь одновременно точку на канале 1 и клиента на канале 44. Отсюда трюк «channel hopping» (быстрое переключение) и практика ставить второй адаптер для слежки за конкретным каналом.

## Шаг 8: проверяем возможности адаптера до выезда

Половина провалов на объекте — из-за того, что адаптер не умеет injection или режет кадры. Проверить это надо **до** выезда:

```
$ iw list | grep -A8 'Supported interface modes'
        * IBSS
        * managed
        * AP
        * monitor
        * P2P-client
        * P2P-GO
```

Если в списке есть `monitor` — адаптер умеет пассивный захват. Но monitor — это ещё не injection. Injection проверяют реальным тестом:

```
$ aireplay-ng --test wlan0
Trying broadcast probe requests...
Injection is working!
```

Строка `Injection is working!` — единственное надёжное подтверждение. Без неё деаутентификация и PMKID-ассоциация не пройдут, и придётся менять адаптер. Именно поэтому в чемодане пентестера лежит второй адаптер на резервном чипсете.

## Шаг 9: скрытый SSID и как его всё равно раскрыть

Точка может не писать SSID в beacon — поле пустое (`<MISSING>`). Это **скрытая сеть**, но скрыта она лишь от пассивного взгляда: как только реальный клиент подключается, он шлёт probe request и association с настоящим именем сети в открытом виде.

```
$ tshark -r capture.pcap -Y 'wlan.ssid && wlan.fc.type_subtype == 4' \
    -T fields -e wlan.ssid | sort -u
office
```

Мы поймали SSID `office` из probe request клиента, хотя beacon его прятал. Дополнительно имя раскрывается в **probe response** (если мы сами отправим probe с пустым SSID) и в association request. Вывод: «скрытый SSID» — это не защита, а лишь мелкое неудобство; в отчёте это фиксируют как факт, а не как меру.

## Частые грабли

- **Адаптер в managed mode** — видно только свою сеть; переключись в monitor (`iw dev wlan0 set type monitor`).
- **Слушают не тот канал** — `airodump-ng` показывает каналы всех точек, но для слежки за одной надо `-c <N>`.
- **DFS-канал «пропадает»** — это не атака; проверь `dmesg`, там будет `radar detected`.
- **Много USB-адаптеров на одном хабе** — не хватает питания, драйвер сбоит; используй powered-хаб.
- **Регуляторный домен** — некоторые каналы/мощности запрещены; `iw reg set <DOM>` перед работой.

## Полный прогон: от «сырого» дампа до карты сети

Соберём всё вместе на нашем `capture.pcap`. Сначала — какие точки в эфире:

```
$ tshark -r capture.pcap -Y 'wlan.fc.type_subtype == 8' \
    -T fields -e wlan.bssid -e wlan.ssid -e radiotap.channel.freq | sort -u
aa:bb:cc:00:11:22   office   2437
de:ad:be:ef:00:99   <MISSING>  2437
```

Две точки: наша `office` и скрытая. Достаём каналы и сигнал, чтобы понять, кто где:

```
$ tshark -r capture.pcap -Y 'wlan.bssid == aa:bb:cc:00:11:22' \
    -T fields -e radiotap.channel.freq -e radiotap.dbm_antsignal | sort -u | head -3
2437     -42
```

`-42 dBm` — точка близко. Теперь список сетей, которые ищут клиенты (из probe request), — это карта «куда ходят люди»:

```
$ tshark -r capture.pcap -Y 'wlan.fc.type_subtype == 4 && wlan.ssid' \
    -T fields -e wlan.ssid | sort | uniq -c | sort -rn
     12 office
      4 HomeNet
```

Итог разбора: одна близкая WPA2-точка `office`, одна скрытая рядом, клиенты ищут ещё и `HomeNet`. Это уже полноценная разведкарта объекта — и всё это из одного пассивного дампа, без единого отправленного кадра.

## Куда дальше

Теперь, когда мы умеем читать эфир и держать адаптер в monitor mode, в следующем уроке мы поймаем **рукопожатие WPA2** и разберём его покадрово. А пока главное запомни: Wi-Fi — это обмен кадрами на конкретном канале, и без monitor mode ты видишь только своё.
