Загрузчик — первый код, который исполняет устройство после включения. Он инициализирует память, поднимает периферию и передаёт управление ядру ОС. Для пентестера это «золотая дверь»: через консоль U-Boot часто доступны команды чтения/записи флеша, загрузки образов по TFTP и даже полноценный shell. Этот урок — обзор семейств загрузчиков и того, как через них попадают в устройство.

## Роль загрузчика

Загрузчик выполняет:

1. **Инициализацию** — DRAM, часы, питание, минимальный набор периферии.
2. **Самотестирование** — проверка целостности образа ядра (иногда).
3. **Загрузку ОС** — чтение ядра и rootfs из flash, TFTP, USB, eMMC.
4. **Консоль/режим восстановления** — доступ для отладки и обновления.

Ошибки и «сервисные» функции загрузчика — частый источник доступа: отладочная консоль без пароля, режим загрузки с произвольного носителя, команды записи в защищённые области.

## Семейства загрузчиков

| Загрузчик | Платформы | Особенности |
|-----------|-----------|-------------|
| U-Boot | ARM, MIPS, RISC-V, x86 | самый распространённый в embedded |
| UEFI/EDK2 | x86, ARM (ServerReady) | стандартизован, DXE/BDS |
| coreboot | x86, ARM | быстрый, открытый, payload-based |
| bootROM | любой SoC | неизменяемый, first-stage |
| Barebox | ARM, x86 | альтернатива U-Boot |
| RedBoot/CFE | старые роутеры | устаревшие |

В embedded Linux доминирует **U-Boot**. В серверных и потребительских x86 — **UEFI**. **bootROM** — это код внутри SoC, который запускается самым первым и умеет грузить следующий этап (например, из SPI или по USB).

## U-Boot: консоль и команды

U-Boot обычно даёт консоль на UART. Прервав автозагрузку (любая клавиша в первые секунды), вы попадаете в prompt `=>`.

```text
U-Boot 2018.03 (Nov 12 2019 - 10:23:45 +0000)
DRAM:  128 MiB
NAND:  256 MiB
In:    serial
Out:   serial
Hit any key to stop autoboot:  2
=> 
```

Типовые команды:

```text
=> help                     # список команд
=> printenv                 # переменные окружения (bootcmd, bootargs, ipaddr)
=> md 0x80000000 0x100      # memory display
=> mw 0x80000000 0xdeadbeef # memory write
=> sf probe 0               # инициализировать SPI flash
=> sf read 0x80000000 0x0 0x100000   # прочитать 1 МБ в RAM
=> tftpboot 0x80000000 kernel.bin    # загрузить по TFTP
=> setenv bootargs 'init=/bin/sh'
=> saveenv
=> boot
```

Ключевой приём: изменить `bootargs`, добавив `init=/bin/sh` или `single`, чтобы ядро запустило shell вместо нормальной инициализации. Иногда достаточно `setenv bootargs ... single` — и вы получаете root.

## Как через загрузчик извлечь прошивку

U-Boot умеет читать флеш в память и выгружать по сети/последовательному порту:

```text
=> sf probe 0
=> sf read 0x80000000 0x0 0x800000   # весь образ 8 МБ в RAM
=> md.b 0x80000000 0x40             # посмотреть начало
=> setenv ipaddr 192.168.1.50
=> setenv serverip 192.168.1.10
=> tftpput 0x80000000 0x800000 dump.bin   # отправить на TFTP-сервер
```

На хосте поднимают TFTP-сервер (`tftpd-hpa`, `atftpd`) и принимают дамп. Это быстрее, чем выпаивать флеш.

## UEFI: кратко

UEFI — стандартизованная прошивка с фазами SEC/PEI/DXE/BDS. Настройки хранятся в NVRAM (переменные `Boot####`, `SecureBoot`, `db/dbx`). UEFI Shell и меню дают доступ к файловой системе ESP и загрузке произвольных приложений. Обход Secure Boot — отдельная тема (`hardware-secure-boot`).

## bootROM: первая ступень

bootROM зашит в кремний и не меняется. Он умеет:

- читать образы из SPI/NAND/eMMC по фиксированным смещениям;
- принимать образ по USB/DFU/UART (режим восстановления);
- проверять подпись первого этапа (если включён secure boot).

Режим bootROM recovery — точка входа для «окирпиченных» устройств: часто он позволяет залить произвольный образ без проверки подписи, если защита не настроена.

## Разобранный пример: root shell через U-Boot

```text
=> printenv bootcmd
bootcmd=sf probe 0; sf read 0x80000000 0x20000 0x300000; bootm 0x80000000
=> setenv bootargs 'console=ttyS0,115200 root=/dev/mtdblock3 rw init=/bin/sh'
=> saveenv
=> boot
# ... ядро стартует
/bin/sh: can't access tty; job control turned off
/ # id
uid=0(root) gid=0(root)
```

Если `saveenv` недоступен (защищено), можно задать `bootargs` в текущей сессии без сохранения — на время одной загрузки.

## Частые ошибки и подводные камни

- **Не тот бод-рейт**: консоль «мусорит» — перебирайте 115200/57600/38400.
- **`sf probe` без номера шины**: на некоторых платах нужен `sf probe 0:0`.
- **Сохранение окружения в защищённую область**: `saveenv` может упасть с ошибкой записи.
- **Загрузка «чужого» ядра**: несовместимое ядро/DTB → устройство не стартует.
- **Окирпичивание**: правка `bootcmd` без бэкапа окружения — риск. Сначала `printenv` и сохраните вывод.
- **Пароль на консоль**: некоторые загрузчики требуют пароль; обход — через чтение флеша программатором.

## coreboot и payload-модель

**coreboot** (ранее LinuxBIOS) — открытый загрузчик, который инициализирует железо за считанные миллисекунды и затем передаёт управление **payload**: это может быть UEFI (Tianocore/EDK2), SeaBIOS (BIOS-совместимость), GRUB, LinuxBoot или даже прямая загрузка ядра. Такая архитектура важна для пентеста по двум причинам. Во-первых, payload — отдельный компонент: замена payload меняет всю загрузочную логику, и проверки целостности могут его не покрывать. Во-вторых, coreboot часто используется в защищённых устройствах (Chromebook, серверы), и его настройки (write-protect SPI, bootblock) определяют, можно ли перепрошить firmware. Если SPI не защищён аппаратно, атакующий с физическим доступом может заменить coreboot целиком — это классический «evil maid»-сценарий.

## Связь загрузчика с Secure Boot

Загрузчик — центральное звено цепочки доверия. В UEFI именно boot manager проверяет подписи образов по ключам `db`/`dbx`. В U-Boot роль проверки выполняет либо встроенный **verified boot**, либо отдельный этап (SPL/TPL), который проверяет FIT-подпись. Ключевой вывод для атакующего: если проверка подписи реализована в самом загрузчике, а загрузчик не защищён от записи, её можно обойти, заменив загрузчик. Поэтому настоящая цепочка доверия начинается с **bootROM** (неизменяемого) и продолжается через подписанные этапы. Как только в цепочке появляется неподписанный или незащищённый этап, вся защита рушится. Практически это означает, что для обхода Secure Boot нужно найти самое слабое звено — обычно это отладочный режим, старый загрузчик с уязвимостью или незащищённая область окружения.

## Отладка загрузки: куда смотреть

Когда устройство не грузится, диагностика начинается с консоли:

- **UART-лог** — самый информативный источник: видно, где именно остановился загрузчик.
- **Индикация** — мигание LED, звуки, коды на семисегментном индикаторе.
- **bootROM-лог** — на некоторых SoC bootROM печатает причину (нет загрузочного носителя, ошибка подписи).
- **Режим восстановления** — позволяет перепрошить или запустить образ из RAM.

Типовые сообщения и их смысл: `Bad Magic Number` (неверный заголовок uImage), `Bad Linux ARM zImage magic` (не тот формат ядра), `mmc init failed` (нет доступа к eMMC), `hash mismatch`/`signature verification failed` (провал проверки подписи). Умение читать эти логи экономит часы и позволяет точно понять, что сломалось — окружение, образ или железо.

## Взаимодействие загрузчика с прошивкой и env

Область окружения (env) часто лежит отдельным разделом и содержит как настройки, так и «жёстко зашитые» пути. При разборе дампа полезно найти env по маркерам (`bootcmd=`, `bootargs=`, `baudrate=`) и прочитать его как обычный текст. Если env дублируется (primary + redundant copy), сравнивайте обе копии: в старой могут остаться пароли, IP-адреса, отладочные флаги, которые убрали из новой. Это ещё один источник утечек, помимо rootfs.
