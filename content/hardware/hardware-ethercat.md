## Вопрос, с которого всё начинается

Modbus и Profinet мы уже разбирали. Но есть протокол, который работает иначе: кадр не «приходит и обрабатывается», а **проходит сквозь все устройства на лету**, и каждое на ходу вставляет свои данные. Это **EtherCAT**. Зачем такая схема и как её атаковать?

## Наш пример: запись EtherCAT-трафика

Перед нами `ethercat.log` — упрощённая запись кадра EtherCAT. Смотрим:

```
$ head -8 ethercat.log
ETH dst=01:01:05:00:00:00 type=0x88A4 (EtherCAT)
ECAT cmd=APRD addr=0x1000 wkc=3
ECAT cmd=APWR addr=0x1001 wkc=3
ECAT datagram 1: LRW 0x0100 len=4 data=00000001
ECAT working counter=3 (all slaves processed)
```

Здесь ключевые слова: `EtherCAT`, `APRD`, `APWR`, `LRW`, `working counter`. Разберёмся.

## Шаг 1: что такое EtherCAT

**EtherCAT** (Ethernet for Control Automation Technology) — промышленный Ethernet-протокол с **жёстким реальным временем**. Идея: один Ethernet-кадр с набором **datagram**-ов проходит по кольцу устройств. Каждое устройство на лету читает и записывает **свою** часть данных, не задерживая кадр. В итоге один кадр обслуживает всю сеть за микросекунды.

Особенности:

- EtherType `0x88A4`.
- Топология «кольцо» (логически), физически — линия с возвратом.
- Устройства (**slaves**) обрабатывают кадр в железе, без процессора.

## Шаг 2: кадр и datagram

EtherCAT-кадр содержит последовательность **datagram**-ов. У каждого — команда, адрес и данные:

| Команда | Смысл |
|---------|-------|
| APRD | Auto-increment Physical Read |
| APWR | Auto-increment Physical Write |
| APRW | Read + Write |
| LRW | Logical Read + Write (самая частая) |
| BRD | Broadcast Read |

**Working Counter (WKC)** — счётчик, который каждое устройство увеличивает, когда успешно обработало свой datagram. Мастер по WKC понимает, все ли slave'ы ответили.

## Шаг 3: почему это быстро

Обычный Ethernet: кадр приходит коммутатору, тот пересылает, устройство обрабатывает процессором — задержки и джиттер. EtherCAT: устройство обрабатывает кадр **в FPGA/ASIC на лету**, задержка — единицы микросекунд и предсказуема. Это и есть детерминизм: критично для приводов и роботов.

## Шаг 4: синхронизация

Для точного управления нужны общие часы. EtherCAT использует **Distributed Clocks (DC)** — механизм синхронизации времени между slave'ами. Мастер рассылает метки, устройства подстраивают свои счётчики. Без DC невозможно согласованное движение осей.

## Шаг 5: поверхности атаки

EtherCAT — это «голый» Ethernet без встроенной аутентификации. Значит:

1. **Инъекция кадров** — подключиться к сегменту и слать свои datagram.
2. **Подмена данных процесса** — переписать выходы приводов (в стенде!).
3. **Сброс/перевод в SafeOp** — нарушить синхронизацию, вызвать остановку.
4. **Подмена WKC** — мастер может не заметить потерю slave.
5. **Прослушивание** — трафик открыт, видно состояние процесса.

Важно: у EtherCAT нет шифрования и аутентификации по дизайну. Защита строится на **физической изоляции** и сегментации сети.

## Шаг 6: что мы нашли в логе

В файле есть datagram с полезной нагрузкой:

```
$ grep data ethercat.log
ECAT datagram 3: LRW 0x0200 len=24 data=nto{3th3rc47_fr4m3_1nj3ct}
```

Мы достали флаг чтением кадра — ровно то, что делает атакующий с доступом к сегменту. В реальном пентесте это первый шаг: **подтвердить, что трафик открыт и его можно читать и подделывать**.

## Шаг 7: инструменты

- **Wireshark** с диссектором EtherCAT.
- **SOEM** (Simple Open EtherCAT Master) — библиотека для мастера на ПК.
- **Собственные скрипты** на `Scapy`/raw socket для инъекции.
- **Анализатор** для проверки таймингов и WKC.

## Шаг 8: защита

- **Физическая сегментация** — EtherCAT-сеть изолирована от IT.
- **Мониторинг WKC и таймингов** — аномалии видны.
- **Контроль доступа к портам** — лишний кабель = компрометация.
- **Резервирование топологии** — кольцо с обнаружением обрыва.
- **Процедуры безопасного останова** — чтобы инъекция не привела к аварии.

## Что мы теперь знаем

1. EtherCAT — промышленный Ethernet с обработкой кадра **на лету**.
2. Кадр содержит datagram-ы (APRD/APWR/LRW), WKC считает ответивших.
3. Детерминизм даёт задержки в микросекунды — для приводов и роботов.
4. **Distributed Clocks** синхронизируют время между устройствами.
5. Аутентификации нет: защита — сегментация и мониторинг.

## Детали кадра EtherCAT

Разберём структуру кадра подробнее, чтобы читать дампы уверенно. После Ethernet-заголовка (EtherType `0x88A4`) идёт EtherCAT-заголовок, а затем — цепочка **datagram**-ов. Каждый datagram содержит:

| Поле | Смысл |
|------|-------|
| Command | тип операции (APRD/APWR/LRW/BRD) |
| Index | идентификатор для отслеживания |
| Address | физический/логический адрес |
| Length | длина данных |
| Data | полезная нагрузка |
| Working Counter | счётчик обработки |
| Interrupt | флаг прерывания |

**Auto-increment** адресация: устройство в кольце увеличивает адрес на единицу, поэтому `APRD` читает «следующего». **Logical** адресация: мастер заранее сопоставляет логический адрес группе устройств, и один `LRW` читает/пишет несколько slave'ов сразу. Именно поэтому один кадр обслуживает всю сеть.

После прохода по кольцу мастер читает **Working Counter**: сколько устройств обработали datagram. Если WKC меньше ожидаемого — кто-то выпал (обрыв, сбой).

## Топология и режимы работы

EtherCAT физически обычно строится как **линия** с возвратом в мастер (логическое кольцо). Есть несколько режимов:

- **Free Run** — slave'ы обновляют выходы как получится, без синхронизации с мастером.
- **SM-Synchronous** — синхронизация по флагу SyncManager.
- **DC-Synchronous** — синхронизация по Distributed Clocks (точный детерминизм).

Для приводов используют DC: только он даёт согласованное движение осей. Для простых дискретных I/O достаточно Free Run. При аудите важно понять режим: от него зависит, насколько критична задержка и что произойдёт при инъекции.

## Инструменты и стенд

Для лаборатории нужны:

- **Wireshark** с диссектором EtherCAT — чтение кадров.
- **SOEM** (Simple Open EtherCAT Master) — реализация мастера на ПК, годится для тестов.
- **Scapy** — ручное формирование кадров для инъекции.
- **Анализ WKC** — скрипт, который следит за счётчиком.
- **EtherCAT-железо** — плата мастера и несколько slave'ов для стенда.

Типовой сценарий: поднять `SOEM`-мастер и slave'ы, снять дамп, разобрать цикл обмена. Затем — на своём стенде — проверить, что произойдёт при подмене данных в `LRW`. Это безопасно и даёт полную картину.

## Сценарий аудита EtherCAT

1. **Есть ли сегментация?** EtherCAT не должен быть доступен из IT-сети.
2. **Кто в кольце?** Перечислить slave'ы и их функции.
3. **Какие данные критичны?** Выходы приводов, команды пуска/останова.
4. **Мониторинг WKC** — детект выпадения устройств.
5. **Реакция на инъекцию** — что происходит при подделке кадра.

Результат — карта доверия: какие данные можно подделать, к каким последствиям это ведёт и что включить для защиты.

## Почему нет аутентификации

EtherCAT проектировали для скорости и детерминизма. Криптографическая защита кадра потребовала бы вычислений в каждом slave'е на каждом цикле — это замедлило бы обработку и усложнило железо. Поэтому защиту вынесли наружу: физическая изоляция, сегментация, контроль доступа к портам. Это осознанный компромисс, и при аудите его надо назвать явно.

## Практический вывод

EtherCAT — пример того, что промышленный протокол не обязан быть защищённым «изнутри». Безопасность обеспечивается **архитектурой сети**: изоляцией, мониторингом, резервированием. Пентестер, попавший в EtherCAT-сегмент, получает полный контроль над процессом — и именно поэтому сегментация здесь критичнее, чем в IT.

## Куда дальше

EtherCAT управляет приводами. Но в электроэнергетике правит другой протокол — **IEC 61850**, где подстанция описывается сотнями логических узлов, а GOOSE-сообщения летят в реальном времени. О нём — следующий урок. А пока главное: **EtherCAT быстр, потому что обрабатывает кадр на лету — и именно поэтому его трафик нельзя аутентифицировать задним числом.**
