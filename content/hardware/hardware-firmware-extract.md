## Вопрос, с которого всё начинается

В уроке про SPI мы сняли дамп флеша роутера — файл `dump1.bin` на 16 МБ. Это «сырой» бинарник: внутри него подряд лежат загрузчик, ядро и файловые системы, но снаружи он выглядит как мусор. Как превратить этот блоб в обычное дерево папок, по которому можно пройтись `grep`'ом и найти пароли?

Именно это — самая продуктивная фаза hardware-анализа.

## Наш пример: тот же дамп роутера

Возьмём наш `dump1.bin`. Цель: дойти от сырого образа до файла `/etc/shadow` с хешами паролей. Пойдём по шагам: сначала узнаем, что где лежит, потом распакуем нужную часть, потом поищем секреты.

## Шаг 1: находим границы разделов

Прошивка собрана из образов, идущих друг за другом со смещениями, кратными размеру сектора (обычно 4 или 64 КБ). Найти эти границы помогает `binwalk` — он сканирует файл в поисках известных сигнатур (характерных байтов в начале формата) и печатает, что где начинается:

```
$ binwalk dump1.bin
DECIMAL       HEXADECIMAL     DESCRIPTION
0             0x0             uImage header (U-Boot)
131072        0x20000         Squashfs filesystem, little endian, size: 7340032 bytes
8519680       0x820000        JFFS2 filesystem, little endian
```

Читаем: по адресу `0x0` — загрузчик U-Boot, по `0x20000` (это 131072) — файловая система **Squashfs** размером 7340032 байта, а по `0x820000` — **JFFS2**. Уже понятно, где искать корневую систему.

## Шаг 2: понимаем, какие бывают файловые системы

Файловая система — это способ, которым данные на носителе организованы в файлы и папки. Во встраиваемых устройствах их несколько типов, и важно уметь их различать по сигнатуре:

| Формат | Признак (магия) | Особенность |
|--------|-----------------|-------------|
| Squashfs | `hsqs` | сжатая, только для чтения — самая частая |
| JFFS2 | `0x1985` | для NOR-памяти, журнальная |
| UBIFS | `UBI#` | для NAND, нужен разбор контейнера |
| Cramfs | `0x28cd3d45` | старая сжатая, только чтение |

В нашем дампе корневая система — Squashfs. Это логично: она сжимается и занимает меньше места, а менять её на устройстве не планируется.

## Шаг 3: вырезаем и распаковываем rootfs

Вырезаем только Squashfs-область утилитой `dd` (по смещению `0x20000`, длиной 7340032 байта) и распаковываем:

```
$ dd if=dump1.bin of=rootfs.sqfs bs=1 skip=$((0x20000)) count=$((7340032))
7340032 bytes copied
$ unsquashfs -d rootfs rootfs.sqfs
Parallel unsquashfs: Using 8 processors
created 1432 files, 289 directories
```

Теперь у нас папка `rootfs` с полноценным деревом файлов. Дальше — обычная работа с файлами.

## Шаг 4: ищем секреты

Первым делом — учётные данные. В Linux хеши паролей лежат в `/etc/shadow`, а список пользователей — в `/etc/passwd`:

```
$ grep -r "root:" rootfs/etc/shadow
root:$1$Xy9a$Zq...:0:0:root:/root:/bin/sh
```

Мы видим хеш `$1$...`. Префикс `$1$` означает схему **MD5-crypt** — старый, но распространённый способ хранить пароль в виде необратимой суммы. Затем ищем прочие секреты по конфигам:

```
$ grep -rEi "password|secret|api[_-]?key|token" rootfs/etc/ | head
rootfs/etc/config/wireless: option key 'HomeWifi2024'
rootfs/etc/config/system: option password 'admin123'
```

Тут уже видны пароли в открытом виде — так бывает чаще, чем хотелось бы производителю.

## Шаг 5: ломаем хеш офлайн

Хеш из `shadow` можно попробовать восстановить перебором по словарю. `john` (John the Ripper) перебирает слова из списка `rockyou.txt` — известной базы утёкших паролей:

```
$ john hash.txt --wordlist=/usr/share/wordlists/rockyou.txt
Loaded 1 password hash (md5crypt, crypt(3) $1$)
admin            (root)
Session completed
```

Пароль root — `admin`. Всё офлайн, устройство даже не включено.

## Шаг 6: не забываем про вторую файловую систему

В дампе была ещё JFFS2 по адресу `0x820000`. Это **overlay** — область, куда устройство записывает изменённые данные и пользовательские настройки. Там часто лежат конфиги, которых нет в Squashfs:

```
$ dd if=dump1.bin of=overlay.jffs2 bs=1 skip=$((0x820000))
$ jefferson -d overlay overlay.jffs2
```

Извлекать нужно обе части: в Squashfs — заводские файлы, в JFFS2 — то, что появилось уже при работе.

## Что мы теперь знаем

По-простому:

1. Дамп — это контейнер: `binwalk` показывает, что и по какому смещению лежит.
2. Корневая ФС чаще всего Squashfs; распаковывается `unsquashfs`.
3. `dd` вырезает нужную область по смещению и размеру из вывода `binwalk`.
4. Секреты ищут в `/etc/shadow`, `/etc/passwd` и конфигах; хеши ломают офлайн `john`.
5. Кроме корневой ФС есть overlay (JFFS2/UBIFS) — её тоже извлекают.

## На что смотреть дальше

- **`binwalk` не берёт squashfs.** Другая эндианность или формат — используйте `sasquatch` или `unblob`.
- **Неверное смещение.** Всегда берите числа из вывода сканера, а не на глаз.
- **Забытый overlay.** Изменённые конфиги лежат не в Squashfs, а в JFFS2/UBIFS.
- **Только `grep` по всему подряд.** Ограничьте области (`/etc`, `/www`, `/usr/bin`) — иначе утонете в выводе.
- **Шифрованный rootfs.** Если данных не видно — нужен ключ из загрузчика.

## Как это выглядит целиком

Маршрут в одну историю: `binwalk dump1.bin` показывает `uImage`, Squashfs по `0x20000` и JFFS2 по `0x820000`. Вырезаем `dd skip=0x20000 count=7340032`, `unsquashfs -d rootfs` даёт дерево. В `etc/shadow` находим хеш `$1$`, `john --wordlist=rockyou.txt` вскрывает пароль `admin`, а `grep -rEi 'password|token'` по `etc/` показывает открытый `HomeWifi2024`. Затем `jefferson` разбирает JFFS2-overlay, где лежат изменённые конфиги. Итог: из сырого блоба — дерево файлов и пароли.

## Если не сработало

- **`unsquashfs` не берёт образ.** Другая эндианность или нестандартный LZMA — `sasquatch`/`unblob`.
- **Смещение неверное.** Берите числа из вывода `binwalk`, а не на глаз.
- **Хеш не ломается.** Смените словарь или режим: `john --format=md5crypt`.
- **Секретов нет.** Проверьте overlay (JFFS2/UBIFS) — изменённые данные лежат там.
- **Rootfs пустой.** Возможно, раздел зашифрован — переходите к анализу энтропии.
- **Много ручного `dd`.** `binwalk -eM` извлекает вложенные образы рекурсивно сам.

## Шаг 7: ищем секреты не только в /etc

`/etc/shadow` и конфиги — очевидное место, но секреты прячутся и глубже. Пройдёмся по всему дереву сразу несколькими шаблонами:

```bash
$ grep -rEi "BEGIN (RSA|EC|OPENSSH) PRIVATE KEY" rootfs/ | head
$ find rootfs/ -name "*.pem" -o -name "*.key" -o -name "*.crt"
$ grep -rEi "api[_-]?key|secret|token|passwd|password" rootfs/ 2>/dev/null | head
```

Отдельно стоит проверить: скрипты инициализации в `/etc/init.d` (там бывают пароли к облаку), бинарники (ключи в виде строк) и веб-каталог (`/www`, `/web`) — там нередко лежат бэкдоры и отладочные CGI.

Строки в бинарниках удобно искать через `strings`:

```bash
$ strings -n 6 rootfs/usr/sbin/httpd | grep -iE "admin|backdoor|secret|debug"
```

Если в прошивке есть сертификаты или приватные ключи TLS, их извлекают и проверяют срок и владельца: общий ключ на весь парк устройств — серьёзная находка.

## Если не сработало

- **`unsquashfs` не открывает образ.** Смените эндианность или формат сжатия; попробуйте `sasquatch` (поддержка нестандартного LZMA) и `unblob`.
- **`binwalk` показывает кашу из смещений.** Укажите эндианность и отсеките ложные сигнатуры вручную.
- **Нет `/etc/shadow`.** Некоторые системы держат пароли в `/etc/passwd` или в NVRAM-конфиге — ищите по всему дереву.
- **`john` не подбирает хеш.** Сначала определите тип (`john --list=formats`), затем попробуйте словарь побольше и правила (`--rules`).
- **Правка не загружается.** Squashfs пересобрана несовместимыми параметрами сжатия/блока — сверьтесь с оригиналом.

## Как защититься

- Не класть пароли и ключи в прошивку в открытом виде; генерировать их на устройстве.
- Использовать стойкие схемы хранения паролей (bcrypt/argon2), а не MD5-crypt.
- Подписывать прошивку и включать secure boot; запрещать загрузку неподписанных образов.
- Уникальный ключ/сертификат на каждое устройство вместо общего на весь парк.

## Куда дальше

Мы добрались до файлов и секретов внутри прошивки. В следующем уроке научимся сравнивать две версии одной прошивки и находить, что изменилось между обновлениями, — это ещё один способ обнаружить закладки и незадокументированные учётки. А пока запомни главное: дамп — это контейнер, и `binwalk` вскрывает его за одну команду.
