## Вопрос, с которого всё начинается

В прошлых уроках мы научились извлекать прошивку, обходить загрузку и даже снимать ключи физикой. Но где вообще живут ключи во встраиваемом устройстве и как их искать?

Вопрос урока: как найти криптографический ключ в прошивке — и что делать, если он «спрятан» правильно?

## Наш пример: прошивка умного замка

Перед нами распакованная прошивка умного замка. Замок общается с приложением по сети, шифруя команды. Мы хотим понять, как устроено это шифрование, и найти ключ. Начнём с поиска по строкам.

## Шаг 1: где живут ключи

| Место | Риск | Как искать |
|-------|------|-----------|
| Прошивка (rootfs) | хардкод ключей и паролей | `grep`, `strings`, entropy |
| Конфиг/NVRAM | ключи в открытом виде | дамп флеша |
| Bootloader | ключ подписи, иногда приватный | U-Boot env, FIT |
| Secure element / TPM | ключ внутри чипа | атаки через API, glitching |
| OTP/eFuse | ключ, пережжённый в кремний | chip-off |
| Код | ключ, выведенный из серийника | реверс алгоритма |

**Классы проблем:** хардкод, слабый RNG, утечки памяти, слабая реализация крипто, fault injection на проверке.

## Шаг 2: ищем хардкод

Проходимся по образам и скриптам:

```bash
$ grep -rEi "aes[_-]?key|hmac|secret|password|api[_-]?key|token" \
    squashfs-root/ 2>/dev/null | head
$ grep -rEi "BEGIN (RSA|EC|OPENSSH|PRIVATE)" squashfs-root/ 2>/dev/null
$ find squashfs-root -name "*.pem" -o -name "*.key" -o -name "*.crt"
```

И вот в скрипте инициализации находка:

```sh
AES_KEY="6f70656e736573616d6531323334353637"
```

Это hex, который декодируется в ASCII `opensesame1234567` — ключ в открытом виде.

## Шаг 3: проверяем ключ на реальном трафике

Ключ найден, но надо доказать, что он тот самый. Перехватываем обмен и пробуем расшифровать:

```bash
$ tshark -r cap.pcap -Y "tcp.port==8888" -T fields -e data.data | head
$ python3 - <<'PY'
from Crypto.Cipher import AES
key = bytes.fromhex("6f70656e736573616d6531323334353637")
ct  = bytes.fromhex("<hex from pcap>")
iv  = b"\x00"*16   # частая ошибка прошивки
print(AES.new(key, AES.MODE_CBC, iv).decrypt(ct))
PY
```

Если открытый текст читается — ключ подтверждён, уязвимость доказана воспроизводимо. Обратите внимание на `iv = нули`: фиксированный IV — вторая проблема, он ломает CBC.

## Шаг 4: слабый RNG

В другом бинарнике — генерация «случайного» кода доступа:

```c
srand(time(NULL));
code = rand() % 1000000;
```

Сид предсказуем (время!), значит все коды можно перебрать по окну времени:

```python
import hashlib, time
for t in range(1700000000, 1700000100):
    cand = hashlib.md5(str(t).encode()).hexdigest()
    # сравнить с известным ключом из прошивки
```

Так же опасен ключ, выведенный из серийного номера:

```bash
$ python3 -c "import hashlib; print(hashlib.sha256(b'SN-12345').hexdigest()[:16])"
```

Любое устройство с известным серийником имеет известный ключ.

## Шаг 5: если ключ «в чипе»

Когда ключ спрятан в secure element или TPM, порядок такой:

- **Логические атаки** — отладочные команды, слабые права API, чтение конфигурационной зоны.
- **Glitching** — обход проверки подписи (см. `hardware-sidechannel`).
- **Chip-off** — при физическом доступе, если ключ в OTP.

Но прежде чем браться за физику, ищите ошибку интеграции: ключ, продублированный в прошивке, обесценивает самый хороший чип.

## Шаг 6: side-channel как последний рубеж

Если ключ недоступен логически, в дело вступает физика:

- **SPA/DPA** — по потреблению восстанавливают ключ.
- **CPA** — корреляция потребления с гипотезами о ключе (ChipWhisperer).
- **Timing** — время выполнения зависит от ключа (сравнение не за постоянное время).
- **EM** — те же утечки, но снимаются антенной.

Fault injection (voltage/clock/EM glitching) помогает «проскочить» сравнение подписи или проверку пароля. Это нужно, только если логические методы исчерпаны, есть физический доступ и авторизация.

## Шаг 7: последствия и раскрытие

Найденный ключ подписи прошивки позволяет собрать свою прошивку и обойти secure boot — компрометация всего класса устройств. Ключ TLS — расшифровка трафика парка. Ключ API — доступ к облаку вендора.

**Ответственное раскрытие.** Найденный ключ вендора — секрет уровня всей линейки. Действуйте строго по правилам программы и закона; не публикуйте ключ и не эксплуатируйте чужие устройства.

## Шаг 8: инструменты под рукой

| Задача | Инструмент |
|--------|-----------|
| Поиск строк и ключей | `grep`, `strings`, `firmwalker` |
| Энтропия/разделы | `binwalk -E`, `binwalk` |
| Реверс вывода ключа | `Ghidra`, `radare2` |
| Офлайн-крэк хэшей | `hashcat`, `john` |
| Физические атаки | `ChipWhisperer` |

Начните с самого дешёвого: `strings` и `grep` по rootfs. Ключи удивительно часто лежат в открытом виде — в скриптах инициализации, конфигах, `.pem`-файлах. Только исчерпав текстовый поиск, переходите к entropy-анализу, реверсу и физике.

## Что мы теперь знаем

1. Ключи живут в прошивке, конфиге, bootloader, secure element, eFuse или выводятся из кода.
2. Хардкод-ключи находятся `grep`/`strings` и подтверждаются расшифровкой трафика.
3. Слабый RNG (`srand(time())`) делает ключи предсказуемыми.
4. Ключ из серийника известен для любого устройства с этим серийником.
5. Повтор IV/nonce ломает CBC/CTR/GCM даже с сильным ключом.
6. Side-channel и glitching — последний рубеж, когда ключ защищён физически.

## На что смотреть дальше

- **Искать только строки.** Ключи бывают в base64/hex и бинарных блобах — нужен entropy-анализ (`binwalk -E`).
- **Игнорировать bootloader.** Приватный ключ подписи иногда лежит в U-Boot env или рядом.
- **Пренебречь RNG.** «Случайный» код из времени — классика; всегда проверяйте предсказуемость.
- **Chip-off без плана.** Выпаивание BGA-чипа без опыта убивает плату — тренируйтесь на мусоре.
- **Онлайн-перебор ключа.** Ключи в embedded не брутят онлайн — их извлекают из образа или перебором малого пространства (окно RNG).

## Шаг 9: ключ в бинарном блобе — анализ энтропии

`grep` и `strings` находят ключи только в текстовом виде. Но ключ может лежать в образе как «сырые» байты — тогда строки его не покажут. Здесь помогает анализ энтропии.

**Энтропия** — мера «случайности» байтов: у сжатых и зашифрованных данных она близка к 8 битам на байт, у текста и кода — заметно ниже. `binwalk -E` строит график энтропии по всему образу:

```bash
$ binwalk -E firmware.bin
DECIMAL       HEXADECIMAL     ENTROPY
...
1048576       0x100000        Rising entropy edge (0.98)
```

Резкий рост энтропии в середине образа — почти всегда сжатый или зашифрованный блок. Его вырезают и проверяют отдельно:

```bash
$ dd if=firmware.bin of=blob.bin bs=1 skip=1048576 count=65536
$ file blob.bin
blob.bin: data
```

Высокая энтропия ещё не значит «внутри ключ» — это может быть сжатый rootfs. Поэтому дальше смотрим, что блок делает в коде: ищем ссылку на его адрес и функцию, которая его читает.

## Шаг 10: ключ, собранный в рантайме

Часто в образе нет самого ключа — есть только функция, которая собирает его из кусочков. Тогда поиск строк бесполезен, и мы идём в реверс:

```bash
$ r2 -A firmware.bin
[0x08000000]> axt @ str.APPSECRET
[0x08000000]> pdf @ sym.derive_key
```

Читаем дизасм и записываем алгоритм словами: например, «ключ = XOR трёх констант плюс серийный номер». После этого ключ для любого устройства считается за секунды — реверс заменяет физику.

## Если не сработало

- **`grep` ничего не нашёл, а устройство шифрует.** Не делайте вывод «ключа нет»: переходите к анализу энтропии и реверсу функции вывода ключа (шаги 9–10).
- **Ключ подтверждён, но трафик не расшифровывается.** Проверьте режим (CBC/CTR/GCM), порядок байтов ключа (hex/ASCII/base64) и IV. Один неверный IV даёт мусор даже с правильным ключом.
- **API отвечает «access denied».** Ищите не ключ, а ошибку интеграции: тот же ключ часто продублирован в скрипте инициализации.
- **Нужен физический доступ, а его нет.** Зафиксируйте находку и вернитесь, когда появятся права: side-channel без авторизации недопустим.

## Как защититься

- Не хранить ключи в прошивке: генерировать внутри secure element и не выносить наружу.
- Использовать аппаратный RNG (TRNG) и не сеять `rand()` временем.
- Каждому устройству — свой ключ; не выводить его из серийного номера.
- Запрещать чтение защищённой зоны и отключать отладку на серийном образце.
- Использовать уникальный IV/nonce на каждое сообщение — иначе даже сильный ключ не спасает.
