Встраиваемые устройства используют криптографию повсеместно: подпись прошивок, TLS-соединения, шифрование данных, аутентификация. Но реализация часто страдает: ключи захардкожены в образе, RNG предсказуем, а защита «защищённого элемента» обходится. Этот урок — о том, как находить и извлекать ключи, завершая цепочку hardware-атаки.

## Теория

Где живут ключи в embedded-устройстве:

| Место | Риск | Как искать |
|-------|------|-----------|
| Прошивка (rootfs) | Хардкод ключей и паролей | `grep`, `strings`, entropy-анализ |
| Конфиг/NVRAM | Ключи в открытом виде | дамп флеша, `hardware-spi` |
| Bootloader | Публичный ключ подписи, иногда приватный | U-Boot env, FIT-образы |
| Secure element / TPM | Ключ внутри чипа | атаки через API, glitching |
| OTP/eFuse | Ключ, пережжённый в кремний | chip-off, микроскопия |
| Код | Ключ, выведенный из пароля/серийника | реверс алгоритма |

**Классы проблем:**

1. **Hardcoded keys** — ключ/пароль прямо в прошивке или в коде.
2. **Слабый RNG** — предсказуемая генерация ключей (фиксированный seed, таймер, `rand()` без инициализации).
3. **Утечки памяти** — ключ можно прочитать из RAM через JTAG или дамп.
4. **Слабая реализация крипто** — самописные шифры, ECB, отсутствие проверки целостности, повторное использование nonce/IV.
5. **Fault injection на крипто** — обход проверки подписи или извлечение байтов ключа глитчингом.

**Secure element / TPM** — чип, хранящий ключи и не выдающий их наружу. Атаки: логические (через API — плохие права, отладочные команды), физические (glitching, chip-off, микроскопия).

**Почему это критично.** Найденный ключ подписи прошивки = возможность собрать свою прошивку и обойти secure boot → полная компрометация класса устройств. Ключ TLS = расшифровка всего трафика парка. Ключ API = доступ к облаку вендора.

## Инструменты и команды

- **binwalk, strings, grep, entropy** — поиск ключей в образе.
- **firmwalker / find** — быстрый обход rootfs по типам файлов.
- **ChipWhisperer** — glitching на крипто, DPA.
- **chip-off** (перепайка флеша) — если интерфейсы закрыты.
- **Proxmark3 / логический анализатор** — перехват ключей на шинах.
- **Ghidra / radare2** — реверс алгоритма вывода ключа.
- **hashcat / john** — офлайн-крэк найденных хэшей.

```bash
# Поиск ключей и секретов в распакованной прошивке
grep -rEi "BEGIN (RSA|EC|OPENSSH|PRIVATE)" squashfs-root/ 2>/dev/null
find squashfs-root -name "*.pem" -o -name "*.key" -o -name "*.der" -o -name "*.crt"
# Хардкод-секреты
grep -rEi "aes[_-]?key|hmac|secret|password|passphrase|api[_-]?key|token" \
  squashfs-root/ 2>/dev/null | grep -vi "\.html\|\.js\.map" | head -50
# Base64-подобные строки (кандидаты в ключи)
grep -rEo "[A-Za-z0-9+/]{32,}={0,2}" squashfs-root/ | head -50

# Анализ энтропии (высокая энтропия = ключ/шифротекст)
binwalk -E dump1.bin
# Извлечение строк из бинарника
strings -n 8 squashfs-root/usr/sbin/crypto_svc | grep -i key
```

```python
# Проверка слабого RNG: если ключ выводится из времени
import hashlib, time
# Гипотеза: key = md5(str(int(time.time()))) — перебор окна времени
for t in range(1700000000, 1700000100):
    cand = hashlib.md5(str(t).encode()).hexdigest()
    # сравнить с известным ключом из прошивки
```

## Поиск ключей: методика

1. **Строки.** `strings -n 6` по всем бинарникам; ищем `key`, `secret`, `token`, PEM-заголовки.
2. **Типовые файлы.** `*.pem`, `*.key`, `*.der`, `*.crt`, `authorized_keys`, `shadow`, `passwd`.
3. **Скрипты.** Shell/Python/Lua-скрипты прошивки часто содержат ключи в открытом виде.
4. **Энтропия.** `binwalk -E` — регионы с высокой энтропией могут быть шифротекстом/ключами.
5. **Реверс алгоритма.** Если ключ не найден в открытом виде, ищите функцию его вывода (из серийника/пароля) в Ghidra.

## Разобранный пример: хардкод-ключ и предсказуемый RNG

**Дано:** распакованная прошивка умного замка.

**Шаг 1 — поиск ключей:**
```bash
grep -rEi "aes|secret|key" squashfs-root/etc/ squashfs-root/usr/sbin/ 2>/dev/null
```
Находим в скрипте:
```sh
AES_KEY="6f70656e736573616d6531323334353637"
```

**Шаг 2 — проверка.** Ключ — ASCII `opensesame1234567`. Проверяем на реальном трафике: перехватываем обмен приложения и устройства, пробуем расшифровать AES-CBC с этим ключом. Если IV фиксирован/нулевой — ещё одна проблема.

**Шаг 3 — слабый RNG.** В другом бинарнике видим генерацию «случайного» кода доступа:
```c
srand(time(NULL));
code = rand() % 1000000;
```
Перебор по времени даёт все возможные коды — устройство предсказуемо.

**Шаг 4 — ключ из серийного номера.** Если ключ выводится из UID/серийника:
```bash
# Находим алгоритм в Ghidra, воспроизводим
python3 -c "import hashlib; print(hashlib.sha256(b'SN-12345').hexdigest()[:16])"
```
Любое устройство с известным серийником имеет известный ключ.

**Шаг 5 — защищённый элемент.** Если ключ «в чипе», пробуем:

- логические атаки: отладочные команды, слабые права API;
- glitching на проверке подписи (`hardware-sidechannel`);
- при физическом доступе — chip-off и анализ, если ключ в OTP.

**Шаг 6 — последствия.** Найденный ключ подписи прошивки позволяет собрать собственную прошивку и обойти secure boot — полная компрометация класса устройств. Задокументируйте impact.

## Разобранный пример: расшифровка трафика по найденному ключу

```bash
# Перехваченный TLS/собственный шифрованный обмен в pcap
tshark -r cap.pcap -Y "tcp.port==8888" -T fields -e data.data | head
# Известен AES-128-CBC ключ из прошивки
python3 - <<'PY'
from Crypto.Cipher import AES
key = bytes.fromhex("6f70656e736573616d6531323334353637")
ct  = bytes.fromhex("<hex from pcap>")
iv  = b"\x00"*16   # частая ошибка прошивки
print(AES.new(key, AES.MODE_CBC, iv).decrypt(ct))
PY
```
Если открытый текст читается — ключ подтверждён и уязвимость доказана воспроизводимо.

## Частые ошибки

- **Искать только строки.** Ключи бывают в base64/hex, в бинарных блобах. Используйте entropy-анализ и `binwalk`.
- **Игнорировать bootloader.** Приватный ключ подписи иногда лежит в U-Boot env или рядом.
- **Пренебречь RNG.** «Случайный» код, выведенный из времени, — классика. Всегда проверяйте предсказуемость.
- **Забыть про повтор IV/nonce.** Даже с сильным ключом reuse ломает CBC/CTR/GCM.
- **Chip-off без плана.** Выпаивание BGA-чипа без опыта убивает плату. Отрабатывайте на мусорных платах.
- **Эксплуатация без ответственного раскрытия.** Найденный ключ вендора — критичный секрет; следуйте правилам программы/закона.
- **Онлайн-перебор ключа.** Ключи в embedded обычно не брутят онлайн — их извлекают из образа/памяти или перебором малого пространства (RNG-окно).

## Side-channel и fault injection на крипто

Когда ключ недоступен логически, в дело вступает физика.

**Side-channel (утечка по побочному каналу):**

- **SPA/DPA (power analysis)** — по потреблению чипа восстанавливают ключ. DPA (дифференциальный) работает даже при сильном шуме, усредняя множество трасс.
- **CPA (correlation power analysis)** — коррелируют потребление с гипотезами о ключе; реализовано в ChipWhisperer.
- **Timing** — время выполнения зависит от ключа (например, сравнение байт не за постоянное время).
- **EM (электромагнитные)** — те же утечки, но снимаются антенной рядом с чипом.

**Fault injection (внесение сбоя):**

- **Voltage glitching** — кратковременная просадка питания сбивает выполнение на нужном такте.
- **Clock glitching** — лишний/пропущенный такт ломает проверку.
- **EM glitching** — импульс рядом с чипом.
- **Цель:** пропустить сравнение подписи, обойти проверку пароля, «проскочить» чтение байта ключа.

**Практика с ChipWhisperer:**

```bash
# Типовой workflow (упрощённо)
# 1. Захват трасс потребления при операциях с известным/неизвестным ключом
# 2. CPA/DPA-анализ в ChipWhisperer Analyzer
# 3. Получение байтов ключа по одному
```

**Когда это нужно.** Только если ключ защищён и логические методы не работают, и только при физическом доступе и наличии авторизации. Для большинства задач хватает хардкод-поиска и слабого RNG — side-channel это «последний рубеж».

**Ответственное раскрытие.** Найденный ключ вендора — секрет уровня всей продуктовой линейки. Действуйте строго по правилам программы bug bounty и законодательству; не публикуйте ключ и не эксплуатируйте чужие устройства.

## Что дальше / решение

- **Нашли ключ подписи** → соберите свою прошивку, докажите обход secure boot (в лаборатории).
- **Нашли TLS-ключ** → расшифруйте трафик, найдите токены и новые эндпоинты.
- **Нашли API-токен** → проверьте BOLA/IDOR в облаке вендора.
- **Ключ в secure element** → логические атаки через API; физические — только при наличии оборудования и авторизации.
- **Ничего не нашли** → проверьте entropy-регионы, реверсните вывод ключа, перейдите к side-channel.
- **Провал** → `record_vector attempted`, зафиксируйте, что искали, и передайте в отчёт.

## Справочные таблицы

**Что искать в образе:**

| Паттерн | Значение |
|---------|----------|
| `-----BEGIN ... PRIVATE KEY-----` | приватный ключ |
| `-----BEGIN CERTIFICATE-----` | сертификат |
| `aes_key`, `hmac_secret` | симметричный ключ |
| `api_key`, `token` | доступ к облаку |
| длинная base64/hex-строка | кандидат в ключ |

**Атаки на крипто в embedded:**

| Атака | Условие | Результат |
|-------|---------|-----------|
| Хардкод-ключ | ключ в образе | полная расшифровка |
| Слабый RNG | ключ из времени/rand | предсказание ключа |
| IV/nonce reuse | фиксированный IV | восстановление текста |
| Glitching | физический доступ | обход проверки подписи |
| Chip-off | физический доступ | извлечение OTP/eFuse |
