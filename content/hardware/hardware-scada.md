SCADA/ICS управляет физическим миром: электростанции, водоканалы, заводы, трубопроводы. Протоколы здесь проектировались для надёжности, а не безопасности: без аутентификации, шифрования и с проверками, которых нет. Урок — обзор OT-безопасности с акцентом на безопасность при тестировании.

## Теория

Уровни модели Purdue:

| Уровень | Что | Примеры |
|---------|-----|---------|
| 0 | физический процесс | датчики, приводы |
| 1 | контроллеры | ПЛК, RTU |
| 2 | supervisory | SCADA, HMI |
| 3 | операции | историки, инженерные станции |
| 4 | IT | корпоративная сеть |
| 5 | enterprise | интернет |

Протоколы:

| Протокол | Транспорт | Безопасность | Особенности |
|----------|-----------|--------------|-------------|
| **Modbus** | TCP/RTU | нет | простой, register-based |
| **DNP3** | TCP/serial | опционально (SAv5) | часто в энергетике |
| **S7comm** | TCP (102) | слабая | Siemens PLC |
| **EtherNet/IP** | TCP/UDP | нет | Rockwell |
| **IEC 104** | TCP | слабая | энергетика |
| **OPC UA** | TCP | есть (сертификаты) | современный |

Классы атак:
- **Несанкционированное чтение** — утечка состояния процесса.
- **Подмена команд** — изменение уставок (опасно для физики!).
- **Отказ в обслуживании** — остановка ПЛК.
- **MITM** — перехват/модификация между HMI и ПЛК.
- **Прошивка ПЛК** — загрузка вредоносной логики (Stuxnet-подобные).

## Инструменты и команды

- **nmap** с ICS-скриптами (`modbus-discover`, `s7-info`).
- **Metasploit** модули для Modbus/S7 (осторожно).
- **pymodbus / pymodbus3** — Modbus-клиент.
- **snap7** — Siemens S7.
- **Wireshark** — разбор протоколов.
- **GRASSMARLIN / Zeek** — пассивная инвентаризация.

```bash
# Пассивная инвентаризация (безопаснее всего)
nmap -p 502,102,20000 --open 10.0.0.0/24
nmap -p 502 --script modbus-discover 10.0.0.10
nmap -p 102 --script s7-info 10.0.0.10

# Modbus: ЧТЕНИЕ регистров (относительно безопасно)
python - <<'PY'
from pymodbus.client import ModbusTcpClient
c = ModbusTcpClient('10.0.0.10', port=502)
c.connect()
rr = c.read_holding_registers(0, 10, slave=1)
print(rr.registers)
c.close()
PY

# S7: чтение
python - <<'PY'
import snap7
plc = snap7.client.Client()
plc.connect('10.0.0.10', 0, 1)
print(plc.get_cpu_info())
PY
```

## Разобранный пример: оценка Modbus-сети (безопасно)

**Дано:** авторизованный тест сегмента АСУ ТП. КРИТИЧНО: не нарушить производство.

**Шаг 1 — пассивная инвентаризация.** Никаких сканов «в лоб». Сначала зеркалируем трафик на SPAN-порту и анализируем в Wireshark/Zeek. Определяем устройства, протоколы, роли.

**Шаг 2 — белый список.** Согласуем с владельцем, какие устройства можно трогать, а какие — категорически нет (регуляторы, приводы).

**Шаг 3 — безопасное чтение.** На согласованных устройствах читаем регистры Modbus (функция 03) — это обычно не влияет на процесс. Фиксируем отсутствие аутентификации.

**Шаг 4 — анализ конфигурации.** Проверяем: есть ли сегментация между IT и OT, есть ли межсетевой экран перед ПЛК, логируются ли изменения.

**Шаг 5 — НЕ пишем вслепую.** Запись регистров (функция 06/10) может изменить уставки и навредить. Только на тестовом ПЛК/в стенде, с письменным разрешением и аварийным планом.

**Шаг 6 — отчёт.** Фиксируем: открытые протоколы, отсутствие аутентификации, слабая сегментация, устаревшая прошивка. Рекомендации: сегментация (Purdue), unidirectional gateway, IDS для OT, обновление.

## Частые ошибки

- **Сканы «в лоб».** Активное сканирование может уронить ПЛК 1990-х. Начинайте пассивно.
- **Запись вслепую.** Функция write меняет физический процесс — риск аварии. Никогда без разрешения/стенда.
- **Правовые рамки.** ICS — критическая инфраструктура; несанкционированный доступ уголовно наказуем.
- **Игнорирование физического риска.** «Просто проверить» может привести к остановке завода/травме.
- **Нет аварийного плана.** При тестировании всегда имейте связь с оператором и план отката.
- **Путаница IT и OT.** Принципы и приоритеты разные: в OT доступность важнее конфиденциальности.

## Протоколы OT и их слабости

| Протокол | Порт | Аутентификация | Шифрование | Слабость |
|----------|------|----------------|------------|----------|
| Modbus TCP | 502 | нет | нет | запись регистров |
| Modbus RTU | serial | нет | нет | физический доступ |
| DNP3 | 20000 | опционально | опционально | replay, spoof |
| S7comm | 102 | пароль (слабый) | нет | stop PLC, read/write |
| EtherNet/IP | 44818 | нет | нет | управление |
| OPC UA | 4840 | да | да | misconfig |

Промышленные протоколы проектировались для надёжности, а не безопасности: они доверяют сети. Если вы в ней — вы можете управлять ПЛК.

## Инструменты

```bash
nmap -Pn -sU -p 502,20000,102 --script modbus-discover <target>
nmap -p 102 --script s7-info <target>
mbtget -r -a 1 -n 10 <target>          # чтение holding-регистров
mbtget -w 5 -a 1 <target>              # запись (осторожно!)
plcscan 192.168.1.0/24
python3 -m pymodbus.server start       # поднять тестовый сервер
snap7-client <target>                  # S7
```

`mbtget -r` — read, `-w` — write, `-a` — адрес, `-n` — количество. `plcscan` перебирает подсеть на ПЛК.

## Безопасная оценка OT

Правила: НЕ писать в регистры продакшен-ПЛК (это может остановить производство или повредить оборудование). Сначала read-only: перечислить устройства, прочитать регистры, задокументировать. Любая запись — только на тестовом стенде или с письменного согласования. OT-инцидент = физический ущерб, поэтому осторожность важнее полноты.

## Разобранный пример 2: инвентаризация Modbus-сети

1. `plcscan` по подсети → список ПЛК.
2. `nmap --script modbus-discover` → unit id и функция.
3. `mbtget -r -a 0 -n 100` → карта регистров.
4. Сопоставление с документацией — какие регистры критические.
5. Вывод: какие устройства доступны и что ими можно управлять.

## Защита OT

- Сегментация (Purdue-модель), firewall между IT и OT.
- Не выставлять ПЛК в интернет.
- Unidirectional gateways для критичных сетей.
- Мониторинг аномалий (Nozomi, Claroty).
- Физический контроль доступа.

## Почему OT отличается от IT

В IT приоритет — конфиденциальность; в OT — доступность и безопасность людей. ПЛК управляет физическим процессом: неверная запись регистра может открыть клапан, остановить конвейер или повредить оборудование. Поэтому в OT-пентесте действует принцип «не навреди»: read-only по умолчанию, любые записи — только на изолированном стенде. Кроме того, в OT много legacy-протоколов без аутентификации, а оборудование работает десятилетиями и не патчится. Это делает сегментацию и мониторинг главными мерами защиты.

## Быстрая проверка

```bash
nmap -Pn -sU -p 502,20000,102 --script modbus-discover,s7-info <target>
plcscan 192.168.1.0/24
mbtget -r -a 0 -n 10 <target>
```

Начните с обнаружения ПЛК и чтения регистров. Никаких записей без письменного согласования — OT-инцидент = физический ущерб.
