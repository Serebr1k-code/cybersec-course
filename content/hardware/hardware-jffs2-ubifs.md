## Вопрос, с которого всё начинается

В уроке про файловые системы мы упомянули, что JFFS2 и UBIFS — «неудобные»: их нельзя просто примонтировать как образ. Но почему? И как всё-таки достать из них файлы?

Возьмём дамп NAND-роутера и разберём обе ФС на практике — а заодно поймём, почему они устроены именно так.

## Наш пример: дамп NAND-роутера

У нас есть `nand_dump.bin` — дамп NAND-памяти роутера, снятый программатором. Прогоним его через `binwalk`:

```
$ binwalk nand_dump.bin | head
DECIMAL       HEXADECIMAL     DESCRIPTION
0             0x0             UBI erase count header, version: 1
2097152       0x200000        UBIFS filesystem superblock
```

Мы видим две сущности: **UBI** и внутри неё **UBIFS**. Прежде чем их разбирать, поймём, откуда вся сложность.

## Шаг 1: почему raw-flash ФС особые

Флеш-память физически не похожа на жёсткий диск:

- **Сначала стереть, потом записать.** Записать можно только в стёртый блок; обратно «из нуля в единицу» бит не переходит без стирания всего блока.
- **Ограниченный ресурс.** Блок выдерживает около ста тысяч стираний, потом изнашивается.
- **«Плохие» блоки.** У NAND часть блоков дефектна с рождения.
- **Крупные блоки.** Стирание идёт блоками по 64–256 КБ, а не байтами.

Поэтому файловая система для raw-flash добавляет поверх данных **журнал изменений** (чтобы не стирать блок ради одного изменения) и **выравнивание износа** (чтобы блоки изнашивались равномерно). Именно из-за журнала образ нельзя прочитать «как есть»: в нём лежат и старые, и новые версии одних и тех же данных.

## Шаг 2: JFFS2 — узлы и сигнатура

**JFFS2** (Journalling Flash File System 2) — журнальная ФС для NOR-памяти. Она состоит из последовательности **узлов**, и каждый узел начинается с сигнатуры `0x1985` (в little-endian — байты `85 19`). Узлы бывают нескольких типов: метаданные файла, запись каталога, сжатые данные, маркер стёртого блока.

Поскольку изменения дописываются новыми узлами, парсер должен пройти весь журнал и собрать актуальное состояние. Для этого есть утилита `jefferson`:

```
$ pip3 install jefferson
$ jefferson -d jffs2_out/ part.jffs2
LZMA compression detected
Extracting files to jffs2_out/
$ ls jffs2_out/
etc  bin  lib  www  usr
```

`-d` задаёт папку для результата, `-e big` — big-endian (для MIPS/ARM с обратным порядком байтов).

## Шаг 3: если jefferson не справляется — эмулируем MTD

Иногда высокоуровневый парсер спотыкается. Тогда идут низким путём: создают в памяти виртуальное flash-устройство (**MTD**) и монтируют образ как настоящую ФС. Делается это модулем ядра `mtdram`:

```
$ sudo modprobe mtdram total_size=65536 erase_size=256
$ sudo modprobe mtdblock
$ sudo dd if=part.jffs2 of=/dev/mtdblock0 bs=1
$ sudo mount -t jffs2 /dev/mtdblock0 /mnt/jffs2
$ ls /mnt/jffs2
```

`total_size` должен быть не меньше образа (лишнее останется пустым). Ошибка `Magic bitmask is not 0x1985` означает неверный endian или смещение.

## Шаг 4: UBI и UBIFS — два уровня

На NAND картина на уровень сложнее. Здесь работает слой **UBI** (Unsorted Block Images) — он управляет физическими блоками NAND: выравнивает износ, помечает плохие блоки, раздаёт логические блоки. А поверх томов UBI уже лежит файловая система **UBIFS**.

То есть в нашем дампе сначала идёт контейнер UBI, а внутри — UBIFS. Сигнатура UBI — `UBI#`. Разбирают это утилитой `ubireader`:

```
$ pip3 install ubi_reader
$ ubireader_list_volumes nand_dump.bin
   vol_id  vol_type  name
   0       dynamic   rootfs
   1       dynamic   data
$ ubireader_extract_files nand_dump.bin
$ ls
ubifs-rootfs  ubifs-data
```

`ubireader_extract_files` сама находит тома и вытаскивает из них файлы. Если том не распознан, помогает флаг `-e big`.

## Шаг 5: монтирование UBIFS через nandsim

Если `ubireader` не справляется, эмулируют сам NAND-чип модулем `nandsim`. Здесь критично указать **точный идентификатор чипа** — от него зависит геометрия (размер страниц, блоков):

```
$ sudo modprobe nandsim first_id_byte=0xec second_id_byte=0xd3 \
    third_id_byte=0x51 fourth_id_byte=0x95
$ sudo flash_erase /dev/mtd0 0 0
$ sudo ubiformat /dev/mtd0 -f nand_dump.bin
$ sudo ubiattach -m 0
$ sudo mount -t ubifs /dev/ubi0_0 /mnt/ubifs
```

Неверный ID даёт `UBI error: bad magic` — и это почти всегда про геометрию чипа, а не про испорченные данные. Правильный ID можно подсмотреть в строке ядра внутри прошивки.

## Шаг 6: ищем файлы и помним про удалённые

Файлы на месте — ищем учётные данные и ключи:

```
$ grep root ubifs-rootfs/etc/passwd
root:x:0:0:root:/root:/bin/sh
$ find ubifs-rootfs -name '*.pem' -o -name shadow
```

А теперь важное для форензики. В JFFS2 удаление файла — это запись специального узла-«надгробия», а не физическое стирание. Поэтому в сыром образе часто остаются **уже удалённые** данные: старые версии `/etc/shadow`, прежние ключи, конфиги с паролями. Даже после смены пароля старый хеш может лежать в журнале и поддаваться восстановлению.

## Шаг 7: как отличить JFFS2 от UBIFS без даташита

Прежде чем звать парсер, полезно понять, что за формат перед вами. Три быстрых признака. Первый — сигнатуры в `binwalk`: `UBI#` на смещении 0 и `UBIFS` чуть дальше означают связку UBI+UBIFS. Если `binwalk` молчит, а в hex видны повторяющиеся `85 19` — это JFFS2 (её узлы начинаются с `0x1985`). Второй — размер стирания: JFFS2 чаще живёт на NOR-флеше (маленькие блоки), UBIFS — на NAND. Третий — наличие OOB-области: если в дампе между страницами видны лишние 16/64 байта, снимали «сырой» NAND с OOB, и её нужно удалить (или использовать `nandump --nooob`), иначе ни один парсер не справится. Это самая частая причина «испорченного» образа.

## Почему журнал — это подарок для форензики

Обычная ФС при удалении файла освобождает блоки, и данные могут быть перезаписаны. JFFS2 и UBIFS устроены иначе: удаление — это запись узла-надгробия или смена флага, а сами данные остаются в старых блоках, пока их не перезапишут при выравнивании износа. На практике это значит: в дампе прошивки можно найти предыдущие версии `/etc/shadow`, отозванные сертификаты и ключи, старые пароли Wi-Fi, следы обновлений. Для анализа прошивки полезно не только собрать текущее дерево, но и вытащить *все* версии файла из журнала: `jefferson` может показать и «мёртвые» узлы, а сырой поиск `grep -a` по дампу найдёт строки, которых в смонтированной ФС уже нет.

## Частые вопросы

**Почему нельзя просто примонтировать JFFS2 через loop?**
У JFFS2 нет суперблока с сигнатурой в начале, как у ext4: её структура — это журнал узлов, размазанный по блокам. Ядру нужен MTD-интерфейс (реальный чип или эмуляция `mtdram`), а не блочное устройство. `mount -o loop` такого не умеет.

**Что такое OOB и почему он ломает разбор?**
OOB (out-of-band) — служебная область NAND, где хранятся ECC-коды и маркеры плохих блоков. При чтении программатором она попадает в дамп между страницами данных. Если её не убрать, смещения «съезжают», и парсер видит мусор. Решение: снимать дамп с флагом, исключающим OOB, или вырезать её постобработкой.

**Почему UBI двухуровневый?**
Потому что NAND «плохая» физически: блоки изнашиваются, бывают битые. UBI берёт на себя всю черновую работу — выравнивание износа, переназначение плохих блоков, тома. UBIFS поверх него работает с уже «идеальными» логическими блоками и не думает о железе.

**Как восстановить удалённые файлы?**
Смонтировать журнал (или разобрать его парсером) и собрать все версии узлов, а не только актуальные. В UBIFS помогает `ubireader_extract_files`, извлекающий в том числе «устаревшие» версии; в JFFS2 — пройти все узлы вручную. Часто прежние `shadow` и `authorized_keys` лежат именно там.

## Что мы теперь знаем

По-простому:

1. Raw-flash ФС добавляют журнал и выравнивание износа — поэтому их не монтируют как образ.
2. JFFS2 — журнальная ФС из узлов с сигнатурой `0x1985`; разбирается `jefferson`.
3. UBI — слой управления NAND; UBIFS лежит поверх его томов; разбирается `ubireader`.
4. Если парсер не справляется — эмулируют MTD (`mtdram`) или NAND (`nandsim`).
5. В журнале остаются удалённые данные — ценный источник для форензики.

## На что смотреть дальше

- **Обрезанный образ.** Не захвачен конец раздела — последние узлы теряются, часть файлов пропадёт.
- **Неверный endian.** Big-endian требует `jefferson -e big` и `ubireader -e big`.
- **`bad magic` у nandsim.** Почти всегда неверная геометрия чипа, а не битые данные.
- **`mtdram` меньше образа.** `dd` обрежет, и монтирование даст пустую ФС.
- **Две копии UBI (A/B).** В «старом» разделе часто остаются учётки и ключи, удалённые из нового.

## Как это выглядит целиком

Маршрут в одну историю: `binwalk nand_dump.bin` показывает `UBI erase count header` и `UBIFS superblock`. `ubireader_list_volumes` перечисляет тома `rootfs`/`data`, `ubireader_extract_files` вытаскивает `ubifs-rootfs`/`ubifs-data`. В `etc/passwd` находим root, а в журнале — старые версии `shadow` с прежними хешами. Если бы парсер споткнулся, эмулировали бы чип `nandsim` с точным ID и смонтировали `/dev/ubi0_0`. От дампа NAND до удалённых секретов.

## Куда дальше

Мы умеем разбирать любую файловую систему прошивки. Дальше в ветке — поиск зашифрованных областей по энтропии: как понять, что часть прошивки зашифрована, и где искать ключ. А пока запомни главное: raw-flash ФС требуют парсера или эмуляции чипа, но зато хранят в журнале даже удалённые данные.
