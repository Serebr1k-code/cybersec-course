Большинство встраиваемых прошивок работают на RTOS (real-time OS): FreeRTOS, Zephyr, ThreadX, RT-Thread. Это не «просто код» — это планировщик, задачи, очереди, мьютексы. Реверс такой прошивки требует понимания структур RTOS. Урок — практическое введение с полным инструментарием.

## Что добавляет RTOS

RTOS поверх «голого» кода даёт:

- **Задачи (tasks/threads)** — независимые потоки с приоритетами.
- **Планировщик** — переключает задачи по приоритету/таймеру (PendSV/SysTick).
- **Очереди/семафоры/мьютексы** — синхронизация.
- **Куча (heap)** — динамическая память (`pvPortMalloc`).
- **Отдельный стек каждой задачи.**

| RTOS | Сигнатуры-маркеры | Особенности |
|------|-------------------|-------------|
| FreeRTOS | `xTaskCreate`, `vTaskStartScheduler`, `pxCurrentTCB` | Самая распространённая |
| Zephyr | `k_thread_create`, `osThreadNew` | Устройства как объекты |
| ThreadX | `tx_thread_create`, `_tx_thread_current_ptr` | Часто в коммерческих |
| RT-Thread | `rt_thread_create` | Китайские IoT-устройства |

## Инструменты и команды

```bash
# Определить RTOS по строкам и сигнатурам
strings -a firmware.bin | grep -iE "freertos|zephyr|threadx|rt-thread|vTask|tx_thread"
binwalk firmware.bin

# Найти символы, если не стрипнута
nm -C firmware.elf | grep -iE 'vTask|xTask|pvPort'
# В Ghidra: Window -> Symbols, фильтр по "vTask"

# Эмуляция в QEMU (если есть подходящий machine)
qemu-system-arm -M <machine> -kernel firmware.bin -nographic -d in_asm

# Живой анализ через OpenOCD + GDB
openocd -f interface/stlink.cfg -f target/stm32f4x.cfg
# затем в GDB: monitor halt; x/1xw &pxCurrentTCB
```

Плагины для Ghidra: скрипты распознавания TCB (FreeRTOS-TCB, RTOS-helper). Tracealyzer — для трассировки задач по SWO/ETM.

## Ключевые структуры FreeRTOS

- **TCB (Task Control Block)** — `pxTopOfStack`, `xStateListItem`, `uxPriority`, `pxStack`, `pcTaskName`.
- **Списки готовых задач** (`pxReadyTasksLists[]`) — по приоритетам.
- **`pxCurrentTCB`** — указатель на текущую задачу (глобальная переменная).
- **Очереди** (`Queue_t`) — `pcHead`, `uxMessagesWaiting`, `uxLength`.

Зная смещения полей, можно обходить список задач в памяти и получать имена и стеки.

## Разобранный пример: восстановление задач FreeRTOS

**Дано:** прошивка Cortex-M на FreeRTOS (не стрипнута), нужно понять, какие задачи запущены.

**Шаг 1 — подтвердить FreeRTOS.** `strings | grep -i freertos` находит символы. Загружаем в Ghidra.

**Шаг 2 — найти точку входа.** Функция `main` вызывает `xTaskCreate(...)` для каждой задачи и затем `vTaskStartScheduler()`.

**Шаг 3 — извлечь задачи.** В `xTaskCreate` аргументы: указатель на функцию задачи, имя, размер стека, параметр, приоритет. Составляем список задач: `vTaskSensor`, `vTaskComms`, `vTaskControl`.

**Шаг 4 — проанализировать задачу.** Переходим в `vTaskComms` — видим работу с UART/сетью. В `vTaskControl` — управление железом. Так понимаем архитектуру прошивки.

**Шаг 5 — найти уязвимость.** Смотрим, как задачи обмениваются данными (очереди). Если задача парсит внешний ввод без проверки длины — возможен overflow. В RTOS уязвимость в задаче с высоким приоритетом критичнее.

**Шаг 6 — живой анализ.** Через OpenOCD подключаемся к работающей плате, читаем `pxCurrentTCB`, обходим список задач, смотрим стеки и переменные в реальном времени.

```gdb
# GDB: обход списка задач FreeRTOS
p pxCurrentTCB
x/8xw pxCurrentTCB
# xStateListItem -> xItemValue, pxNext...
```

## Анализ кучи и поиск уязвимостей

```bash
# Сигнатуры аллокаторов
strings -a firmware.bin | grep -iE 'pvPortMalloc|heap_4|ucHeap'
# В Ghidra: найти вызовы pvPortMalloc/pvPortFree, проверить размеры
```

Частые баги: use-after-free в очередях, overflow при копировании в буфер задачи, отсутствие проверки границ при парсинге пакетов.

## Частые ошибки

- **Реверс как монолита.** RTOS-код многозадачен; линейный анализ сбивает. Стройте карту задач.
- **Игнорирование планировщика.** Вызовы `taskYIELD`, `vTaskDelay` меняют поток.
- **Неверная база стека.** Стек задачи — отдельная область; не путайте с main-стеком.
- **Стрипнутая прошивка.** Символов нет — ищите сигнатуры (PendSV-обработчик, константы RTOS).
- **Пропуск heap-уязвимостей.** `pvPortMalloc`/`pvPortFree` — частая цель.
- **Правовые рамки.** Реверс чужой прошивки без разрешения может нарушать лицензии/закон.

## Что дальше / решение

- Не стрипнута → идите по символам `xTaskCreate`/`vTaskStartScheduler`.
- Стрипнута → ищите PendSV/SysTick и константы списков приоритетов.
- Есть живая плата → OpenOCD и обход `pxCurrentTCB`.
- Смежные уроки: `hardware-firmware-emulation`, `hardware-embedded-debug`, `hardware-iot-firmware-diff`.

## FreeRTOS: структуры и восстановление задач

FreeRTOS хранит список задач в `pxCurrentTCB` и связанных списках. В дампе памяти ищите сигнатуры имён задач (часто строки рядом со структурами TCB). Ключевые поля TCB: `pxTopOfStack`, `pxStack`, `pcTaskName`. Инструменты: Ghidra (скрипт для поиска TCB), `r2` с плагинами, Volatility для Linux-подобных образов. Восстановление задач даёт карту: какие потоки существуют, их приоритеты, стеки. Это помогает понять логику устройства, не имея исходников.

```bash
# поиск имён задач в дампе
strings -n 5 firmware.bin | grep -iE 'task|idle|timer|comm|main'
# анализ в Ghidra
# Symbol Tree → ищите vTaskDelay, xTaskCreate
```

## Анализ кучи и поиск уязвимостей

RTOS-куча (heap_1..heap_5 в FreeRTOS) часто простая, без защиты. Переполнение буфера в обработчике может перезаписать соседние блоки и указатели. Ищите: фиксированные буферы, `strcpy`/`sprintf`, обработчики сетевых пакетов. Отсутствие ASLR и stack canary в embedded делает эксплуатацию проще — достаточно перезаписать адрес возврата или указатель функции. Определите архитектуру (ARM/MIPS/RISC-V), endianness и адреса функций из дампа.

## Практика

Распакуйте прошивку на FreeRTOS, найдите имена задач и обработчики сетевого ввода, определите потенциальное переполнение. Опишите цепочку эксплуатации: перезапись адреса возврата → ROP/вызов функции. Это ключевой навык реверса embedded.

## Отличие RTOS от «голого» металла

RTOS добавляет планировщик, задачи, семафоры, очереди и кучу. Для реверса это значит: в бинарнике есть узнаваемые функции (`xTaskCreate`, `vTaskDelay`, `xQueueSend`) и структуры (TCB, списки). Наличие RTOS упрощает анализ: по именам задач и вызовам API можно восстановить архитектуру приложения, не имея исходников. В «голом» металле такой структуры нет — всё в одном цикле. Определите, есть ли RTOS, по строкам и сигнатурам, затем стройте карту задач. Это отправная точка для поиска обработчиков ввода и уязвимостей.

## Итог

RTOS-прошивки удобнее для реверса: узнаваемые API и структуры позволяют восстановить карту задач. Ищите обработчики ввода, фиксированные буферы и переполнения — при отсутствии ASLR и canary эксплуатация упрощается. Начинайте с определения RTOS и архитектуры, затем стройте модель приложения.
