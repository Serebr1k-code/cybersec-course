## Вопрос, с которого всё начинается

В прошлом уроке мы слушали CAN-шину и подделывали кадры. Но есть интерфейс куда мощнее: дилерское оборудование через ту же шину читает ошибки, меняет конфигурацию и **перепрошивает** блоки. Этот протокол называется **UDS**.

Вопрос урока: что это за «API автомобиля» и можно ли обойти его защиту?

## Наш пример: ECU с защищённой диагностикой

Перед нами блок управления (**ECU**) автомобиля, доступный по CAN. Через диагностические ID мы можем отправлять UDS-запросы. Но самые интересные операции закрыты аутентификацией. Наша цель — понять механизм и, имея дамп прошивки ECU, обойти защиту.

## Шаг 1: как устроен UDS

**UDS** (Unified Diagnostic Services, ISO 14229) — стандарт диагностики. Сообщение отправляется в диагностический CAN-ID: обычно `0x7E0` для запроса и `0x7E8` для ответа. Формат: `[длина][SID][параметры]`.

Основные сервисы (**SID** — Service ID):

| SID | Сервис | Назначение |
|-----|--------|-----------|
| 0x10 | DiagnosticSessionControl | переключить сессию |
| 0x27 | SecurityAccess | seed-key аутентификация |
| 0x22 | ReadDataByIdentifier | чтение DID (VIN, калибровки) |
| 0x2E | WriteDataByIdentifier | запись DID |
| 0x34 | RequestDownload | начать загрузку прошивки |
| 0x36 | TransferData | передача блоков |
| 0x3E | TesterPresent | поддержание сессии |

## Шаг 2: отправляем первый запрос

Простой запрос через `cansend`: `02` — длина, `10 03` — переключение в extended-сессию:

```bash
$ cansend can0 7E0#0210030000000000
$ candump can0,7E8:7FF
```

Смотрим ответы ECU. То же самое удобнее через `python-uds`:

```python
import udsoncan
from udsoncan.connections import PythonIsoTpConnection
from udsoncan.client import Client
import isotp, can
bus = can.interface.Bus('can0', bustype='socketcan')
tp = isotp.socket(); tp.bind('can0', isotp.Address(isotp.AddressingMode.Normal_11bits, rxid=0x7E8, txid=0x7E0))
conn = PythonIsoTpConnection(tp)
with Client(conn, request_timeout=2) as c:
    c.change_session(udsoncan.services.DiagnosticSessionControl.Session.extendedDiagnosticSession)
    seed = c.request_seed(0x01).service_data['securitySeed']
    print('seed', seed.hex())
```

## Шаг 3: SecurityAccess — главный барьер

Сервис `0x27` работает так:

1. Тестер шлёт `27 01` (request seed).
2. ECU отвечает `67 01 <seed>`.
3. Тестер вычисляет key из seed (секретный алгоритм) и шлёт `27 02 <key>`.
4. ECU проверяет; при успехе — `67 02`.

Алгоритм key часто «зашит» в прошивке ECU или в закрытом софте. Реверс алгоритма = полный доступ.

```bash
$ isotp-send -d can0 -t 0x7E0 02 10 03
$ isotp-send -d can0 -t 0x7E0 02 27 01     # request seed
$ isotp-send -d can0 -t 0x7E0 06 27 02 <key>
```

## Шаг 4: обходим защиту

**Шаг 4.1 — расширенная сессия.** `10 03` → ответ `50 03` + тайминги. Теперь доступны защищённые сервисы.

**Шаг 4.2 — запрос seed.** `27 01` → `67 01 <seed>`. Seed может быть фиксированным (плохо) или случайным.

**Шаг 4.3 — проверка фиксированного seed.** Если seed одинаков при каждом запросе, возможно, ECU принимает и фиксированный key — пробуем стандартные.

**Шаг 4.4 — реверс алгоритма.** В дампе прошивки ищем обработчик SecurityAccess: таблицу SID (`0x27`), вызовы CRC и умножений. Часто `key = CRC8(seed)` или просто `seed XOR константа`. Дизассемблируем в Ghidra и восстанавливаем.

**Шаг 4.5 — отправка key.** Считаем key, шлём `27 02 <key>`, получаем `67 02` — доступ разрешён.

**Шаг 4.6 — эксплуатация.** Читаем защищённые DID (`22 F1xx` — калибровки, VIN), пишем конфиг (`2E`), при необходимости — загружаем свою прошивку (`34/36/37`).

## Шаг 5: сессии и привилегии

UDS использует сессии: `default`, `programming`, `extended`. Привилегированные операции доступны только в extended/programming **после** SecurityAccess. Обход строится на:

- слабом алгоритме seed-key,
- отсутствии ограничения попыток,
- **backdoor-ключе**, оставленном разработчиком.

Проверьте также `0x27 0x03/0x04` (suppress positive response) и тайминги P2/P2*.

## Шаг 6: читаем ответы правильно

Отрицательный ответ выглядит как `7F <SID> <NRC>`, где NRC — код причины. Например, `7F 27 35` — «invalidKey» (неверный ключ). Всегда читайте NRC: он объясняет, почему запрос отклонён.

## Шаг 7: как от этого защищаются

- **Сильный алгоритм seed-key** вместо простого XOR/CRC.
- **Ограничение попыток** (после N неудач — блокировка).
- **Аутентификация диагностики** (закрытый доступ к 0x7E0).
- **Gateway-сегментация** — диагностика изолирована от приводных шин.

## Шаг 8: что читать и как не сломать

DID (Data Identifier) — это адреса данных внутри ECU. Стандартные диапазоны: `0xF190` — VIN, `0xF187` — номер запчасти, `0xF1xx` — калибровки производителя. Читать их безопасно:

```bash
$ isotp-send -d can0 -t 0x7E0 03 22 F1 90
```

Ответ `62 F1 90 <VIN>` вернёт VIN. Запись (`2E`) — уже вмешательство: сначала всегда читайте текущее значение, сохраняйте его и только потом пишите. Ошибка в записи калибровки может превратить ECU в «кирпич», поэтому на живом авто такие операции недопустимы.

Ещё один приём — **сканирование DID**: перебор диапазона `22 F1xx` показывает, какие идентификаторы поддерживает блок. Ответ `7F 22 31` (requestOutOfRange) означает, что DID не существует, а `62 ...` — что есть и отдаёт данные. Так составляется карта внутренних параметров ECU.

## Что мы теперь знаем

1. UDS — «API автомобиля» поверх CAN; запросы идут в `0x7E0`, ответы — из `0x7E8`.
2. Формат: `[длина][SID][параметры]`; ключевые SID — 0x10, 0x27, 0x22, 0x2E.
3. SecurityAccess (`0x27`) — seed-key аутентификация, главный барьер.
4. Алгоритм key реверсится из прошивки ECU; часто это CRC или XOR.
5. Пройдя SecurityAccess, можно читать/писать данные и перепрошивать ECU.
6. Отрицательный ответ `7F <SID> <NRC>` объясняет причину отказа.

## На что смотреть дальше

- **Нет TesterPresent.** Сессия истекает (таймер ~5 с) — шлите `3E 80` периодически.
- **Неверный адрес/CAN-ID.** Разные ECU используют разные ID (`0x7E0..0x7E7`) — сканируйте.
- **Прямая запись без чтения.** Сначала читайте (`22`), потом пишите (`2E`), иначе «окирпичите» ECU.
- **Игнорирование NRC.** Отрицательный ответ говорит причину — читайте его.
- **Фаззинг вслепую.** Случайные запросы могут сбросить ECU — работайте на стенде.
- **Правовые рамки.** Прошивка чужого авто или отключение иммобилайзера — преступление.

## Как это выглядит целиком

Маршрут в одну историю: `10 03` переключает ECU в extended-сессию, `27 01` возвращает seed, из дампа прошивки реверсим алгоритм (`key = CRC8(seed)`), шлём `27 02 <key>` и получаем `67 02` — доступ открыт. Дальше `22 F1 90` читает VIN, `22 F1xx` сканирует карту DID, а `34/36/37` при необходимости загружают прошивку. Периодический `3E 80` держит сессию. От seed до ключей от машины — четыре шага.

## Куда дальше

UDS даёт полный диагностический контроль над автомобилем. Дальше по дереву нас ждут промышленные протоколы и SCADA — та же логика «нет аутентификации», только на заводах. А пока главное: **пройдя SecurityAccess, вы получаете ключи от машины — и это самый серьёзный риск в automotive.**
