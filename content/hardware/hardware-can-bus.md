## Вопрос, с которого всё начинается

В прошлом уроке мы перехватывали шины на плате — SPI, I2C. Но самый массовый объект hardware-пентеста сегодня — автомобиль, где десятки электронных блоков (**ECU**) связаны шиной **CAN**. И у неё есть особенность: любой участник может отправить кадр с любым идентификатором.

Вопрос урока: как подключиться к CAN-шине автомобиля, понять, какие кадры чем управляют, и почему подделка кадра так опасна?

## Наш пример: автомобиль с OBD-II

Перед нами автомобиль (в рамках авторизованного теста на своём авто). Под рулём — диагностический порт **OBD-II** (разъём J1962), который даёт доступ к CAN. Наша цель — понять, какие кадры управляют замками дверей.

## Шаг 1: что такое CAN

CAN (Controller Area Network) — дифференциальная двухпроводная шина (CAN-High, CAN-Low), скорость обычно 125/250/500 кбит/с. Кадр состоит из полей:

| Поле | Назначение |
|------|-----------|
| ID (11 или 29 бит) | идентификатор сообщения; младший ID = выше приоритет |
| DLC | длина данных (0–8 байт) |
| Data | до 8 байт полезной нагрузки |
| CRC | контрольная сумма |

Ключевые свойства:

- **Broadcast + arbitration** — все видят всё; приоритет по ID (низкий ID выигрывает арбитраж).
- **Нет аутентификации** — любой узел может подделать любой кадр.
- **Нет шифрования** — данные в открытом виде.

Популярные ID (зависят от авто): `0x0C9` — обороты, `0x1A0` — двери, `0x0C5` — скорость.

## Шаг 2: поднимаем интерфейс

Используем адаптер CANable и Linux-стек **SocketCAN**:

```bash
$ sudo ip link set can0 up type can bitrate 500000
```

**Скорость критична**: 500 кбит/с для CAN, 125 — для комфорт-шины. Неверная скорость = мусор и ошибки шины. Ещё нужны **терминаторы** 120 Ом на концах шины.

## Шаг 3: пассивно наблюдаем

Сначала — только слушаем, ничего не отправляем:

```bash
$ candump can0
$ cansniffer can0
```

`candump` показывает поток кадров. `cansniffer` группирует по ID и подсвечивает меняющиеся байты — это ключевой инструмент для поиска нужного кадра.

## Шаг 4: находим кадр замков

Нажимаем «закрыть двери» на ключе и смотрим, какой ID и какой байт меняются **синхронно** с действием. Так находим кадр замков. Проверяем гипотезу в контролируемых условиях:

```bash
$ cansend can0 1A0#0000000000000001
```

**Только на своём авто или стенде!** Случайная отправка может сломать состояние ECU.

## Шаг 5: разбираем сигналы (DBC)

Чтобы интерпретировать биты как физические величины (скорость, обороты, угол руля), используют **DBC-файл** — описание, какие биты что значат:

```python
import can, cantools
db = cantools.database.load_file('vehicle.dbc')
bus = can.interface.Bus('can0', bustype='socketcan')
for msg in bus:
    try:
        print(db.decode_message(msg.arbitration_id, msg.data))
    except Exception:
        pass
```

## Шаг 6: где тут уязвимости

- **Принимает ли шина команды без проверки состояния** (двери на скорости)?
- **Есть ли диагностические режимы**, доступные без авторизации?
- **Можно ли подделать критичный кадр** (в симуляторе!)?

Именно отсутствие аутентификации делает CAN классическим объектом атак.

## Шаг 7: защита

- **Gateway/сегментация** — не всё на одной шине.
- **SecOC** (Secure Onboard Communication) — MAC и «свежесть» (freshness) к кадрам, защита от подделки и повтора.
- **Мониторинг аномалий** — IDS для CAN.
- **Ограничение диагностического доступа.**

Важно: даже с SecOC ошибки в реализации (слабые ключи, отсутствие freshness) оставляют вектор. Поэтому защиту оценивают в комплексе, а не по наличию одной технологии.

**CAN-FD** расширяет данные до 64 байт и повышает скорость, но **безопасности не добавляет**. При аудите проверьте: используется ли SecOC, есть ли gateway-сегментация, логируются ли аномалии.

## Шаг 8: фаззинг и диагностика

Отдельный вектор — **фаззинг** шины: генерация большого числа кадров с разными ID и данными и наблюдение, не сломается ли какой-то блок. Для этого есть `cangen`:

```bash
$ cangen can0 -g 10 -I 0C9 -D i
```

`-g 10` — интервал между кадрами, `-I` — ID, `-D i` — случайные данные. Фаззинг может увести ECU в нештатное состояние, поэтому — только на стенде.

Ещё один канал — стандартные диагностические PID через OBD-II. Запросы вида `02 01 00` (mode 01, PID 00) отдают поддерживаемые параметры; так составляется карта того, что вообще доступно на шине:

```bash
$ cansend can0 7DF#0201000000000000
```

`0x7DF` — широковещательный диагностический ID. Ответы приходят от разных ECU, и по ним видно, какие блоки отвечают и какие данные отдают.

Отдельно стоит помнить, что современные авто делят CAN на несколько шин: приводную (powertrain), комфортную (comfort) и информационно-развлекательную (infotainment). Через OBD-II часто доступна только диагностическая, а к приводной ведёт gateway. Именно поэтому при пентесте сначала составляют карту: какая шина куда ведёт и что за gateway их разделяет.

Итоговая последовательность работы на стенде проста: поднять интерфейс на верной скорости, пассивно записать поток, найти кадр действия через `cansniffer`, воспроизвести его и задокументировать. Всё остальное — детали.

## Что мы теперь знаем

1. CAN связывает десятки ECU; кадр = ID + DLC + до 8 байт данных + CRC.
2. Аутентификации и шифрования нет — любой узел может подделать любой кадр.
3. Приоритет задаёт ID: чем меньше, тем выше.
4. OBD-II (J1962) даёт доступ к CAN; поднимается через SocketCAN.
5. `candump` слушает, `cansniffer` находит меняющиеся байты, `cansend` отправляет.
6. Защита: SecOC, gateway-сегментация, мониторинг.

## На что смотреть дальше

- **Неверная скорость шины.** 500 кбит/с вместо 125 = мусор и ошибки.
- **Отправка вслепую.** Случайный `cansend` может сломать состояние ECU — сначала слушайте.
- **Отсутствие терминатора.** CAN требует 120 Ом на концах.
- **Подключение к приводной шине напрямую.** Это опасно (тормоза, руль) — работайте на стенде.
- **Bus-off.** Слишком активная отправка уводит узел в bus-off — дозируйте.
- **Правовые рамки.** Вмешательство в чужой автомобиль — преступление.

## Куда дальше

Мы научились слушать и подделывать кадры. Но в автомобиле есть и более мощный интерфейс — диагностический протокол **UDS**, через который дилер читает ошибки и перепрошивает блоки. В следующем уроке разберём его и попробуем обойти аутентификацию. А пока главное: **CAN доверяет всем — и именно это делает его управляемым.**
