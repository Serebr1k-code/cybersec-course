## Вопрос, с которого всё начинается

В прошлом уроке мы распаковали прошивку и нашли пароли. Но производители не публикуют списки уязвимостей своих устройств. Как понять, есть ли в прошивке что-то опасное, о чём вендор молчит?

Есть приём, который работает почти всегда: сравнить две версии одной прошивки. Всё, что вендор тихо исправил в новом релизе, — это и есть список его уязвимостей, поданный на блюде.

## Наш пример: две версии прошивки роутера

У нас есть `firmware_v1.bin` и `firmware_v2.bin` — прошивки одного роутера до и после обновления. Вендор пишет в changelog «улучшена безопасность». Наша задача: выяснить, что именно он исправил, и понять, чем это было опасно в старой версии.

## Шаг 1: распаковываем обе версии

Сначала получаем из каждой прошивки дерево файлов. `binwalk` с флагом `-e` извлекает вложенные образы, а `-C` задаёт папку для результата:

```
$ binwalk -e firmware_v1.bin -C out_v1
$ binwalk -e firmware_v2.bin -C out_v2
$ ls out_v1/_firmware_v1.bin.extracted/
squashfs-root
```

Теперь у нас два каталога `squashfs-root` — старый и новый. Сравнивать их целиком «в лоб» бесполезно: различий будет слишком много, и мы утонем. Нужен более умный подход.

## Шаг 2: сравниваем по хешам файлов

Сначала поймём, **какие файлы вообще изменились**. Для каждого файла посчитаем md5 — короткий отпечаток содержимого — и сравним списки. Совпал отпечаток — файл тот же; разошёлся — файл изменили:

```
$ (cd out_v1/_firmware_v1.bin.extracted/squashfs-root && find . -type f -exec md5sum {} \; | sort) > v1.txt
$ (cd out_v2/_firmware_v2.bin.extracted/squashfs-root && find . -type f -exec md5sum {} \; | sort) > v2.txt
$ diff v1.txt v2.txt
< 3a1f... ./usr/sbin/httpd
> 7c9e... ./usr/sbin/httpd
< 2b4d... ./usr/lib/libssl.so.1.1
> 8e0a... ./usr/lib/libssl.so.1.1
```

`diff` показывает, что изменились всего два файла: веб-сервер `httpd` и библиотека шифрования `libssl`. Это уже сильное сужение — с тысяч файлов до двух.

## Шаг 3: разбираем изменившийся бинарник

Файл `httpd` — это **бинарник**, скомпилированная программа, а не текст. Чтобы понять, что в ней поменялось, обе версии открывают в дизассемблере (**Ghidra** — бесплатный инструмент, показывающий машинный код в виде функций). Сравниваем обработчик, принимающий данные из сети, и видим:

- в v1.0 длина входной строки копируется функцией `strcpy` — без ограничения;
- в v2.0 вместо неё стоит `strncpy` с указанием максимума.

`strcpy` копирует строку, пока не встретит конец, — если строка длиннее буфера, она переполняет его. Это классическое **переполнение буфера**: специально подобранный длинный запрос может перезаписать память и выполнить чужой код. `strncpy` ограничивает копирование, закрывая дыру. Мы нашли исправленную уязвимость.

## Шаг 4: смотрим версии библиотек

Второй изменённый файл — `libssl`, библиотека шифрования. Её версию видно по строкам внутри:

```
$ strings out_v1/_firmware_v1.bin.extracted/squashfs-root/usr/lib/libssl.so.1.1 | grep -i openssl
OpenSSL 1.0.2k  26 Jan 2017
$ strings out_v2/_firmware_v2.bin.extracted/squashfs-root/usr/lib/libssl.so.1.1 | grep -i openssl
OpenSSL 1.1.1w  11 Sep 2023
```

Старая версия — OpenSSL 1.0.2k 2017 года. Такие версии тянут за собой целый шлейф известных уязвимостей. Проверяем их через `searchsploit` — локальную базу эксплойтов:

```
$ searchsploit openssl 1.0.2
OpenSSL 1.0.2 < 1.0.2ze - ... | multiple/remote/...
```

Список непустой. Любая из этих CVE — потенциальный путь атаки на устройство со старой прошивкой.

## Шаг 5: ищем секреты и строки

Дальше — самый дешёвый источник находок: поиск секретов прямо в распакованном rootfs. `grep` по конфигам часто находит хардкод-учётки:

```
$ grep -rIn "password\|secret\|api_key\|token" out_v1/_firmware_v1.bin.extracted/squashfs-root/etc
/etc/config/system: option admin_password 'SuperSecret123'
```

А для бинарников работает `strings` — она вытаскивает читаемый текст из любого файла:

```
$ strings -n 8 firmware_v1.bin | grep -iE 'password|api_key|token' | head
debug_password=root
```

Иногда секреты лежат прямо в образе, а не в конфигах.

## Шаг 6: собираем отчёт

Находка превращается в отчёт, когда у неё есть конкретика: версия устройства, уязвимый компонент, тип уязвимости, доказательство. Здесь: прошивка v1.0 содержит `httpd` с переполнением буфера и устаревший OpenSSL 1.0.2k. Перед публикацией обязательно проверяем актуальность — устройство могло быть пропатчено, а версия на нём — свежее той, что мы разбирали.

## Что мы теперь знаем

По-простому:

1. Сравнение двух версий прошивки показывает, что вендор исправил, — то есть его уязвимости.
2. Сначала сравнивают по хешам: так находят изменившиеся файлы.
3. `strcpy` → `strncpy` в дизассемблере указывает на исправленное переполнение.
4. Устаревшие библиотеки (`libssl`) тянут известные CVE — их проверяют `searchsploit`.
5. Секреты ищут `grep` по конфигам и `strings` по бинарникам.

## На что смотреть дальше

- **Разные пути и симлинки.** Ложные различия — сравнивайте осмысленно, а не всё подряд.
- **Бэкпорт без смены версии.** Вендор мог пропатчить библиотеку, не меняя номер, — проверяйте код.
- **Слишком большой diff.** Начинайте с изменившихся бинарников и конфигов.
- **Ядро — отдельная тема.** Уязвимости ядра ищут по его версии (`uname -r` внутри прошивки).
- **Актуальность.** Найденная CVE могла быть закрыта в более новой ревизии устройства.

## Как это выглядит целиком

Маршрут в одну историю: `binwalk -e` обеих версий, `find -exec md5sum` в `v1.txt`/`v2.txt`, `diff` оставляет два файла — `httpd` и `libssl`. В Ghidra видим `strcpy`→`strncpy` (исправлено переполнение), а `strings` показывает OpenSSL `1.0.2k` → `1.1.1w`. `searchsploit openssl 1.0.2` даёт список CVE. Плюс `grep` по `etc/` находит `admin_password 'SuperSecret123'`. Из «улучшена безопасность» в changelog получился готовый список уязвимостей и секретов.

## Если не сработало

- **Слишком большой diff.** Начните с изменившихся бинарников и конфигов, а не с полного дерева.
- **Версия та же, а баг закрыт.** Вендор мог бэкпортировать патч — сверяйте код, а не только номер.
- **`binwalk` не извлёк образ.** Попробуйте `unblob` или укажите смещение вручную.

## Шаг 7: когда хеши совпали, а дыра осталась

Иногда файл «не изменился» по хешу, но уязвимость в нём есть — просто вендор её не исправлял. Хеш говорит только о факте изменения, а не о безопасности. Поэтому одного диффа мало: параллельно проверяйте **версии компонентов** во всех бинарниках, а не только в изменившихся.

Соберём инвентарь версий по всему rootfs:

```bash
$ strings -n 8 out_v1/.../squashfs-root/usr/lib/*.so* \
    | grep -iE "openssl|libcurl|busybox|dropbear|lighttpd" | sort -u
OpenSSL 1.0.2k
libcurl/7.52.1
BusyBox v1.24.2
```

Каждую строку прогоняем через `searchsploit` и сопоставляем с CVE. Устаревший BusyBox, curl или dropbear сами по себе дают десятки известных уязвимостей — их не нужно «диффить», они видны по версии.

Для точного сравнения функций без исходников используют **бинарный диффинг** (Bindiff/Diaphora): он сопоставляет функции двух бинарников и показывает не только замену `strcpy`→`strncpy`, но и добавленные проверки границ. Это быстрее, чем глазами в Ghidra, когда бинарник большой.

## Если не сработало

- **`binwalk -e` не распаковал образ.** Смените эндианность или используйте `unblob`; проверьте, не зашифрован ли раздел.
- **Дифф даёт тысячи различий.** Отфильтруйте служебное (даты, пути, симлинки) и сравнивайте по хешам только `bin`/`sbin`/`lib`, а не весь rootfs.
- **Ghidra не находит различий.** Обе версии собраны с разными оптимизациями — используйте бинарный диффинг, а не текстовое сравнение дизасма.
- **`searchsploit` пуст.** Версия может быть уже пропатчена или это вендорский форк — проверьте `nvd.nist.gov` по точной строке версии.
- **Нет второй версии прошивки.** Ищите образ на FTP вендора, в архивах или у сообщества — дифф без второй версии невозможен.

## Как защититься

- Обновлять сторонние компоненты и не тянуть устаревшие OpenSSL/BusyBox в новые релизы.
- Не полагаться на «security by obscurity»: закрытые changelog не мешают диффу прошивок.
- Использовать безопасные функции работы со строками и включать защиты компилятора.
- Публиковать advisory по исправленным уязвимостям — это снижает риск, а не повышает.

## Справочник: инструменты для диффа прошивок

Одних `diff` и `md5sum` хватает не всегда. Разные задачи требуют разного уровня сравнения:

| Инструмент | Что сравнивает | Когда нужен |
|---|---|---|
| `md5sum`/`sha256sum` | файлы по хешу | быстро найти изменённые файлы |
| `diff -rq` | деревья каталогов | изменившиеся конфиги и скрипты |
| `cmp`/`vbindiff` | бинарники побайтово | точечные правки в образе |
| `radiff2` | функции в бинарниках | патч одной функции без исходников |
| Diaphora/BinDiff | графы функций | большой бинарник, много изменений |
| `searchsploit` | версии компонентов | подбор CVE к устаревшим библиотекам |

Порядок эффективен такой: сначала дешёвый хеш-дифф (какие файлы изменились), затем бинарный дифф именно этих файлов, и параллельно — инвентарь версий всех компонентов. Так вы не утонете в полном дереве.

## Ограничения дифф-подхода

- **Хеш ≠ безопасность.** Совпавший хеш говорит лишь, что файл не менялся, а не что в нём нет дыры: вендор мог просто не исправлять уязвимость.
- **Бэкпорт без смены версии.** Патч мог быть наложен без изменения номера версии — сравнивайте код, а не только строку версии.
- **Разные пути и симлинки** дают ложные различия; сначала нормализуй структуру каталогов.
- **Пересборка меняет всё.** Даже без функциональных правок пересобранный образ отличается тысячами байт — ориентируйся на семантику, не на байты.
- **Ядро — отдельная история.** Уязвимости ядра не видны в userland-диффе; их ищут по версии `uname -r` внутри прошивки.

## Куда дальше
