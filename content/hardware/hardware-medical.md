Медицинские устройства — особая категория hardware-пентеста. С одной стороны, это обычные встраиваемые системы с BLE, Wi-Fi, UART и прошивками: глюкометры, инсулиновые помпы, кардиомониторы, пульсоксиметры, инфузионные насосы, носимые холтеры, дефибрилляторы с телеметрией. С другой — цена ошибки здесь измеряется здоровьем и жизнью пациента. Поэтому тестирование медицинских устройств всегда сочетает технический навык с клиническим надзором и строгим разрешением.

Этот урок разбирает, из чего состоит типичное медицинское устройство, какие беспроводные интерфейсы оно использует, где искать уязвимости, какими инструментами работать и почему регуляторика (FDA, MDR, ГОСТ) диктует правила игры.

## Классы медицинских устройств

Устройства различаются по критичности и регуляторному классу:

| Класс | Примеры | Риск |
|-------|---------|------|
| Диагностика | глюкометр, тонометр, пульсоксиметр | низкий/средний |
| Терапия | инсулиновая помпа, инфузионный насос | высокий |
| Мониторинг | холтер, кардиомонитор, CGM | средний/высокий |
| Импланты | кардиостимулятор, нейростимулятор | критический |
| Визуализация | УЗИ, рентген, МРТ | средний |
| Лаборатория | анализаторы крови | средний |

Чем выше класс, тем строже регулирование и тем осторожнее тест. Импланты и терапийные устройства в рамках пентеста почти всегда тестируются только «на столе», без живого пациента и с разрешением производителя.

## Беспроводные интерфейсы

Медицинские устройства используют несколько каналов:

- **BLE (Bluetooth Low Energy)** — самый частый. GATT-профили, характеристики, нотификации. Часто без pairing или с фиксированным PIN (000000). Служебные сервисы (battery, device information) раскрывают модель и версию.
- **Wi-Fi** — для стационарных устройств и передачи данных в госпитальную сеть (HL7/FHIR через шлюз).
- **ANT+ / 2.4 ГГц проприетарные** — фитнес-трекеры, датчики пульса.
- **Sub-GHz** — некоторые телеметрийные системы, импланты (MICS-диапазон 402-405 МГц).
- **NFC/RFID** — идентификация пациента, расходников, настроек.
- **Инфракрасный** — старые устройства.
- **Проводные** — USB, UART (сервисный), иногда Ethernet.

BLE — основная поверхность. Профиль **HDP (Health Device Profile)** и **GATT-сервисы** стандартизированы, но производители добавляют проприетарные характеристики, которые часто не проверяют права доступа.

## GATT и BLE-атаки

BLE-устройство предоставляет **сервисы** (services), внутри — **характеристики** (characteristics) с **дескрипторами**. Каждая характеристика имеет **UUID** (16-бит для стандартных, 128-бит для проприетарных) и **права** (read/write/notify). Классические проблемы:

- **Отсутствие аутентификации** — чтение/запись характеристик без pairing.
- **Just Works pairing** — нет MITM-защиты, ключ не проверяется.
- **Фиксированный/слабый PIN** — 000000, 123456.
- **Write без проверки** — запись в терапевтическую характеристику (доза инсулина).
- **Replay** — повтор команд управления.
- **Eavesdropping** — если шифрование выключено.

Инструменты для BLE:

```bash
# --- сканирование BLE ---
hcitool lescan
# или
btmon &
bluetoothctl scan on

# --- подключение и перечисление GATT ---
gatttool -b AA:BB:CC:DD:EE:FF -I
# > connect
# > primary        (список сервисов)
# > characteristics (список характеристик)
# > char-read-uuid 0x2a00

# --- Bettercap (BLE-модуль) ---
sudo bettercap -eval "ble.recon on"
# затем: ble.show, ble.enum <MAC>, ble.write <MAC> <uuid> <hex>

# --- nRF Connect / LightBlue (мобильные GUI) ---
# удобны для ручного перечисления сервисов и характеристик

# --- Frida на Android для приложения-компаньона ---
frida -U -f com.example.medicalapp -l hook_ble.js
```

## Разобранный пример: перечисление и запись в BLE-устройство

Дано: носимый монитор с BLE, разрешение на тест в лаборатории. Нужно понять, можно ли писать в служебные характеристики без аутентификации.

**Шаг 1 — сканирование.** Находим MAC и имя:

```bash
sudo hcitool lescan
# OUTPUT:
# AA:BB:CC:DD:EE:FF HealthMonitor_1234
```

**Шаг 2 — перечисление сервисов.** Подключаемся gatttool:

```bash
gatttool -b AA:BB:CC:DD:EE:FF -I
# > connect
# Connection successful
# > primary
# attr handle: 0x0001, end grp handle: 0x0005 uuid: 00001800-0000-1000-8000-00805f9b34fb  (Generic Access)
# attr handle: 0x0006, end grp handle: 0x000f uuid: 0000180a-0000-1000-8000-00805f9b34fb  (Device Information)
# attr handle: 0x0010, end grp handle: 0x0020 uuid: 0000fff0-0000-1000-8000-00805f9b34fb  (Vendor)
```

**Шаг 3 — характеристики.** Ищем права записи:

```bash
# > characteristics
# handle: 0x0011, char properties: 0x02, char value handle: 0x0012, uuid: 0000fff1-...  (read)
# handle: 0x0013, char properties: 0x08, char value handle: 0x0014, uuid: 0000fff2-...  (write)
# handle: 0x0015, char properties: 0x10, char value handle: 0x0016, uuid: 0000fff3-...  (notify)
```

`properties: 0x08` — это Write Without Response, без аутентификации.

**Шаг 4 — запись.** Пробуем записать тестовый байт:

```bash
# > char-write-cmd 0x0014 0100
# OUTPUT: (нет ошибки — запись прошла)
```

**Шаг 5 — вывод.** Устройство принимает запись без pairing. Если характеристика управляет параметром терапии — это критическая уязвимость. Дальше проверяем диапазоны и валидацию значений (можно ли выставить заведомо опасное значение).

## Телеметрия и госпитальная сеть

Стационарные устройства шлют данные в **госпитальную информационную систему (HIS)** через **HL7** (v2.x, MLLP-порт 2575) или **FHIR** (REST/JSON). Проблемы:

- **Незашифрованный HL7** — перехват и подмена данных пациента.
- **Слабые креденшелы** к HIS/шлюзу.
- **Отсутствие сегментации** — устройство в общей сети, из него можно прыгнуть дальше.
- **Scan-to-email** — лабораторные анализаторы шлют результаты по SMTP с вшитым паролем.

Для анализа HL7 используют **hl7apy** (Python), Wireshark с dissector, а для FHIR — обычный REST-тест (curl/ffuf).

## Безопасные методы тестирования

Медицинские устройства требуют особого подхода:

- **Только с письменным разрешением** производителя и/или клиники, с определением объёма.
- **Клинический надзор** — рядом должен быть медик, понимающий последствия.
- **Не трогать живого пациента.** Тесты — на стенде, на выключенном/тестовом устройстве, с фантомами.
- **Не выводить из строя имплант.** Для имплантов — только анализ прошивки и лабораторные измерения.
- **Фиксировать всё** — каждое действие и результат, для отчёта и расследования.
- **Готовность к откату** — иметь план восстановления (перепрошивка, сброс).
- **Не публиковать эксплойт** до согласованного раскрытия (coordinated disclosure).

Регуляторика: FDA (США) требует postmarket cybersecurity; в ЕС действует MDR 2017/745; в РФ — ГОСТ и требования Росздравнадзора. Производители обязаны выпускать патчи и SBOM. Это создаёт правовую рамку, которую пентестер обязан учитывать.

## Edge cases и подводные камни

- **BLE-адрес рандомизируется** — устройство может менять MAC; используйте name/сервис для идентификации.
- **Pairing может блокироваться** после нескольких попыток — не перебирайте PIN агрессивно.
- **Запись в характеристику может необратимо сбить калибровку** — фиксируйте исходные значения перед изменением.
- **ANT+ не шифруется вообще** — но и не даёт управления, только данные.
- **Импланты работают в MICS (402-405 МГц)** — нужен специализированный SDR/антенна, и тестировать их вне лаборатории нельзя.
- **Проприетарные UUID** — их нужно реверсить из приложения-компаньона (Frida/static).
- **Юридически** несанкционированный доступ к медицинскому устройству — тяжкое нарушение, даже без вреда.

## Что дальше / решение

Практический маршрут в лаборатории: (1) отсканируйте BLE-эфир и составьте список устройств; (2) перечислите GATT-сервисы и характеристики, отметьте writable; (3) проверьте, требуется ли pairing и какой; (4) в рамках разрешения протестируйте запись и валидацию значений; (5) реверсните приложение-компаньон, чтобы понять проприетарные UUID и логику. Для защиты: включайте аутентифицированное шифрованное pairing (LESC), проверяйте права и диапазоны значений на устройстве, сегментируйте медицинскую сеть, шифруйте HL7/FHIR, обновляйте прошивки и ведите SBOM. И помните: техническая находка без клинического контекста ничего не значит — всегда оценивайте реальный риск для пациента.

## Реверс приложения-компаньона

Почти у каждого носимого медицинского устройства есть мобильное приложение-компаньон, и именно в нём лежит ключ к проприетарной логике: UUID характеристик, форматы команд, алгоритмы калибровки и часто — вшитые секреты. Реверс приложения начинается с распаковки APK (для Android) или IPA (для iOS). Дальше ищут строки с UUID, адресами, ключами, названиями характеристик и эндпоинтами облачного API. Если логика в нативном коде, помогает анализ `.so` в Ghidra, а для динамики — Frida: перехват методов BLE-стека (writeCharacteristic, readCharacteristic) показывает реальные команды в момент исполнения.

Типичный результат реверса — карта: какой UUID управляет дозой, какой отдаёт измерения, какой включает сервисный режим. Дальше эта карта используется для точечных тестов на устройстве. Отдельно проверяйте облако: приложение ходит в backend производителя, где хранятся данные пациента; слабая аутентификация, IDOR или отсутствие проверки владельца дают доступ к чужим данным. Всё это — в рамках официального разрешения и без воздействия на живого пациента.

## Носимые устройства и CGM

Непрерывные мониторы глюкозы (CGM) — яркий пример, где безопасность напрямую связана с терапией. Датчик шлёт значения по BLE, а приложение или помпа принимает решения о дозе. Здесь особенно важны целостность и аутентичность данных: если атакующий подменяет показания, система может ввести неверную дозу. Проверяйте, подписываются ли пакеты, проверяется ли источник и есть ли защита от replay. Для исследователя это полигон для изучения BLE-безопасности в чувствительном контексте: тесты только на тестовом датчике, с фиксацией исходных настроек и готовностью к откату. Помните, что найденная техническая уязвимость оценивается через реальный клинический риск, а не только через CVSS.
