## Вопрос, с которого всё начинается

Перед тобой носимый медицинский монитор, который по Bluetooth шлёт врачу показания. Технически это обычная BLE-система — но цена ошибки здесь измеряется здоровьем пациента. Как безопасно проверить, можно ли записать в служебную характеристику без аутентификации, и почему медицинские устройства тестируют иначе? Разберём на примере.

## Что такое медицинское устройство

Глюкометры, инсулиновые помпы, кардиомониторы, пульсоксиметры, инфузионные насосы, холтеры — всё это встраиваемые системы с BLE, Wi-Fi, UART и прошивками. Различаются по критичности и регуляторному классу:

| Класс | Примеры | Риск |
|-------|---------|------|
| Диагностика | глюкометр, тонометр | низкий/средний |
| Терапия | инсулиновая помпа, насос | высокий |
| Мониторинг | холтер, CGM | средний/высокий |
| Импланты | кардиостимулятор | критический |

Чем выше класс, тем строже регулирование (FDA, MDR 2017/745, ГОСТ) и тем осторожнее тест. Импланты и терапийные устройства почти всегда тестируют только «на столе», с разрешением производителя.

## Беспроводные интерфейсы

- **BLE (Bluetooth Low Energy)** — самый частый. GATT-профили, характеристики, нотификации. Часто без pairing или с фиксированным PIN (`000000`).
- **Wi-Fi** — стационарные устройства и передача данных в госпитальную сеть.
- **ANT+ / проприетарные 2.4 ГГц** — фитнес-трекеры, датчики пульса.
- **Sub-GHz** — телеметрия, импланты (MICS-диапазон 402–405 МГц).
- **NFC/RFID** — идентификация пациента и расходников.

Стандартные BLE-сервисы, которые полезно узнавать в перечислении: `0x1800` (Generic Access), `0x180A` (Device Information), `0x180D` (Heart Rate), `0x1810` (Blood Pressure), `0x181D` (Weight Scale). Всё, что не попадает в этот список и имеет 128-битный UUID (`0000fff0-...`), — проприетарная логика производителя, её придётся реверсить.

## Наш пример: носимый монитор с BLE

Дано: монитор с именем `HealthMonitor_1234`, разрешение на тест в лаборатории. Нужно понять, можно ли писать в характеристики без аутентификации.

## Шаг 1: сканируем BLE

```bash
sudo hcitool lescan
# AA:BB:CC:DD:EE:FF HealthMonitor_1234
```

## Шаг 2: перечисляем GATT

BLE-устройство предоставляет **сервисы** (services), внутри — **характеристики** (characteristics) с **UUID** и правами (read/write/notify). Подключаемся `gatttool`:

```bash
gatttool -b AA:BB:CC:DD:EE:FF -I
# > connect
# Connection successful
# > primary
# attr handle: 0x0001, end grp handle: 0x0005 uuid: 00001800-... (Generic Access)
# attr handle: 0x0006, end grp handle: 0x000f uuid: 0000180a-... (Device Information)
# attr handle: 0x0010, end grp handle: 0x0020 uuid: 0000fff0-... (Vendor)
```

Сервис `0x180A` (Device Information) раскрывает модель и версию — хорошая разведка.

## Шаг 3: ищем записываемые характеристики

```bash
# > characteristics
# handle: 0x0011, char properties: 0x02, uuid: 0000fff1-...  (read)
# handle: 0x0013, char properties: 0x08, uuid: 0000fff2-...  (write)
# handle: 0x0015, char properties: 0x10, uuid: 0000fff3-...  (notify)
```

`properties: 0x08` — это Write Without Response: запись без подтверждения и аутентификации.

## Шаг 4: пробуем записать

```bash
# > char-write-cmd 0x0014 0100
# (нет ошибки — запись прошла)
```

Устройство приняло запись без pairing. Если характеристика управляет параметром терапии — это критическая уязвимость. Дальше проверяем диапазоны и валидацию значений (можно ли выставить заведомо опасное значение).

## Инструменты

```bash
hcitool lescan / bluetoothctl scan on   # сканирование BLE
gatttool -b <MAC> -I                     # GATT вручную
sudo bettercap -eval "ble.recon on"      # BLE recon/attack
frida -U -f com.example.app -l hook.js   # хук приложения-компаньона
```

nRF Connect и LightBlue (мобильные GUI) удобны для ручного перечисления сервисов.

## Реверс приложения-компаньона

Почти у каждого носимого устройства есть мобильное приложение, и в нём — проприетарная логика: UUID характеристик, форматы команд, алгоритмы калибровки и часто вшитые секреты. Реверс начинают с распаковки APK/IPA, ищут строки с UUID и ключами, а нативный код смотрят в Ghidra; динамику — через **Frida**: перехват методов BLE-стека (`writeCharacteristic`, `readCharacteristic`) показывает реальные команды в момент исполнения.

Типичный результат — карта: какой UUID управляет дозой, какой отдаёт измерения, какой включает сервисный режим. Отдельно проверяйте облако: приложение ходит в backend производителя, где хранятся данные пациента; слабая аутентификация или IDOR дают доступ к чужим данным.

## Телеметрия и госпитальная сеть

Стационарные устройства шлют данные в госпитальную систему через **HL7** (MLLP-порт 2575) или **FHIR** (REST/JSON). Проблемы: незашифрованный HL7 (перехват и подмена данных пациента), слабые креденшелы к шлюзу, отсутствие сегментации (прыжок дальше по сети), scan-to-email анализаторов с вшитым паролем. Для HL7 используют **hl7apy** и Wireshark-dissector, для FHIR — обычный REST-тест.

## Носимые CGM

Непрерывные мониторы глюкозы (CGM) — пример, где безопасность прямо связана с терапией: датчик шлёт значения по BLE, а помпа принимает решения о дозе. Если атакующий подменяет показания, система введёт неверную дозу. Проверяйте, подписываются ли пакеты, проверяется ли источник и есть ли защита от replay. Здесь тесты — только на тестовом датчике, с фиксацией исходных настроек.

## Безопасные методы тестирования

- **Только с письменным разрешением** производителя и/или клиники.
- **Клинический надзор** — рядом должен быть медик.
- **Не трогать живого пациента.** Тесты — на стенде, с фантомами.
- **Не выводить из строя имплант.** Для имплантов — только анализ прошивки.
- **Готовность к откату** — план восстановления (перепрошивка, сброс).
- **Coordinated disclosure** — не публиковать эксплойт до согласования.

## Если не сработало

- **BLE-адрес рандомизируется** — устройство может менять MAC; используйте name/сервис.
- **Pairing блокируется** после нескольких попыток — не перебирайте PIN агрессивно.
- **Запись может необратимо сбить калибровку** — фиксируйте исходные значения.
- **ANT+ не шифруется**, но и не даёт управления — только данные.
- **Проприетарные UUID** — их нужно реверсить из приложения-компаньона.

## Шаг 5: слушаем нотификации

Устройство может само отдавать измерения — через *нотификации*. Нотификация — это push от характеристики: подписался один раз, и устройство шлёт значения по мере появления. Подписка делается записью `0100` в *Client Characteristic Configuration Descriptor* (CCCD, стандартный дескриптор `0x2902`), после чего включаем прослушивание:

```bash
# > char-write-req 0x0016 0100
# Characteristic value was written successfully
# > listen
# Notification handle = 0x0015 value: 48 65 00 00 00 00
```

Первые два байта `48 65` — это, скорее всего, показание в little-endian (`0x6548 = 25928`), дальше — статус и время. Точный формат интерпретируется после реверса приложения-компаньона, но даже сырые байты полезны: сравнивая значения при разных состояниях датчика, можно построить соответствие «байты → измерение», не имея исходников.

Отсюда естественный вопрос: а можно ли не только читать, но и *притвориться* устройством и подсунуть врачу ложные показания? Да, если данные не подписаны и нет проверки источника. Именно поэтому мониторы непрерывной глюкозы и инсулиновые помпы проверяют на replay и подмену: там неверное показание превращается в неверную дозу.

## Частые вопросы

**Почему нельзя просто перебрать PIN при BLE-спаривании?**
У BLE pairing есть счётчик неудачных попыток и таймаут: после нескольких ошибок устройство перестаёт принимать попытки или требует перезагрузки. Плюс часть устройств использует *Just Works* — pairing без ввода ключа вообще, где перебирать нечего, но который уязвим к MITM, потому что ключ не аутентифицирован.

**Чем ANT+ отличается от BLE для теста?**
ANT+ — узкополосный вещательный протокол для датчиков (пульс, каденс, мощность). Он не шифруется и не требует сопряжения, поэтому его легко перехватить, но он почти никогда не даёт канала управления — только данные. Угроза для ANT+ — приватность, а не изменение терапии.

**Что делать, если прошивка зашифрована?**
Сначала смотрим, нет ли доступа к интерфейсу обновления (DFU, BLE OTA), нет ли ключа в приложении-компаньоне или в облачном API. Часто ключ расшифровки прошивки лежит прямо в APK или приходит с сервера. Если ничего — переходим к анализу по побочным каналам (потребление, время), но для медицины это уже за рамками безопасного теста.

**Можно ли тестировать на реальном пациенте?**
Нет. Даже пассивный перехват чужого устройства — это вмешательство в приватность и потенциальный риск. Работаем на стенде с фантомами и тестовыми датчиками, строго с письменным разрешением.

**Что писать в отчёте производителю?**
Не «уязвимость CVSS 9.8», а сценарий: какое действие злоумышленника приводит к какому клиническому исходу, при каких условиях это достижимо и как воспроизвести на стенде. Медицинские регуляторы оценивают риск для пациента, а не абстрактную техническую критичность, поэтому описание должно связывать технику с терапией: «запись без pairing в характеристику дозы позволяет изменить дозу на X, что при Y-состоянии пациента приводит к Z».

## Что мы теперь знаем

1. Медицинское устройство — обычная встраиваемая система с BLE/Wi-Fi/прошивкой.
2. BLE-сервисы и характеристики — основная поверхность; write без pairing критичен.
3. Проприетарную логику достают из приложения-компаньона (Frida/Ghidra).
4. Телеметрия идёт через HL7/FHIR и часто без шифрования.
5. Тест всегда с разрешением, надзором и клинической оценкой риска.
