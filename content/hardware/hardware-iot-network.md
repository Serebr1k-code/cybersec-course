## Вопрос, с которого всё начинается

Мы разобрали прошивку устройства и знаем, что внутри. Но IoT-устройство — это ещё и сетевой узел: оно общается с приложением, с облаком и с другими устройствами. И именно в этих каналах чаще всего прячется то, что даёт удалённую компрометацию всего парка сразу.

Разберём сетевую поверхность атаки на примере умной лампы.

## Наш пример: умные лампы с MQTT-брокером

У нас есть система умных ламп. Устройства общаются через **MQTT** — лёгкий протокол обмена сообщениями, любимый IoT. Наша цель: выяснить, можно ли захватить управление лампами, не имея пароля.

## Шаг 1: что вообще открыто

Начнём с сетевой разведки. `nmap` сканирует порты и определяет, какие сервисы на них слушают:

```
$ nmap -sV -p- 192.168.1.50
1883/tcp open  mqtt   Mosquitto
80/tcp   open  http   lighttpd
```

`-p-` означает «все порты» — это важно: IoT-устройства прячут сервисы на нестандартных портах. `-sV` определяет версию сервиса. Мы видим два: MQTT на 1883 и веб-интерфейс на 80.

## Шаг 2: понимаем, что такое MQTT

**MQTT** работает по модели «издатель-подписчик». Устройства **публикуют** сообщения в именованные каналы — **топики** — и **подписываются** на нужные. Например, лампа публикует своё состояние в топик `devices/lamp01/status` и слушает команды в `devices/lamp01/cmd`.

Ключевая особенность: подписка на символ `#` означает «все топики». Если брокер не требует пароля, любой в сети увидит весь обмен и сможет публиковать команды.

## Шаг 3: проверяем анонимный доступ

Пробуем подключиться без учётных данных:

```
$ mosquitto_sub -h 192.168.1.50 -t '#' -v
devices/lamp01/status {"on":false,"brightness":50}
devices/lamp01/telemetry {"power":3.2}
devices/lamp02/status {"on":true,"brightness":100}
```

`-t '#'` — подписка на всё, `-v` — показывать топики. Брокер пустил нас без пароля и тут же вылил состояние всех ламп. Уже это — утечка, но пойдём дальше.

## Шаг 4: захватываем управление

Из потока сообщений видно управляющий топик. Публикуем в него команду:

```
$ mosquitto_pub -h 192.168.1.50 -t 'devices/lamp01/cmd' -m '{"on":true}'
```

Лампа включается. Это **полная компрометация без пароля**: мы не просто читаем данные, а управляем устройством. Причём `#` показал топики всех ламп — значит, одно правило на брокере управляет всем парком. Для оценки критичности это ключевой факт: одна точка отказа на много устройств.

## Шаг 5: смотрим на облако

Устройство наверняка связано с облаком вендора. Найти адреса и токены можно прямо в прошивке:

```
$ grep -rE "https?://[a-z0-9.-]+" squashfs-root/ | grep -vi "w3.org" | head
squashfs-root/etc/config: option cloud_url 'https://api.lamps.vendor.com/v1'
$ grep -rEi "api[_-]?key|token|secret" squashfs-root/ | head
squashfs-root/etc/config: option api_token 'eyJhbGciOi...'
```

Найденный токен проверяем на **IDOR** (Insecure Direct Object Reference — доступ к чужим объектам по чужому идентификатору). Меняем `device_id` в запросе: если сервер отдаёт данные чужой лампы, это дыра в авторизации облака.

## Шаг 6: другие протоколы IoT

Сетевая поверхность IoT не ограничивается MQTT. Запомним типовые протоколы и их слабости:

| Протокол | Порт | Типовая проблема |
|----------|------|------------------|
| MQTT | 1883/8883 | брокер без аутентификации |
| CoAP | 5683 (UDP) | нет авторизации, REST для сенсоров |
| UPnP/SSDP | 1900 (UDP) | открытие портов, RCE в IGD |
| TR-069 | 7547 | RCE через сервер управления провайдера |
| RTSP (камеры) | 554 | нет аутентификации |

Важно: **CoAP и SSDP работают по UDP**, поэтому обычный TCP-скан их не видит — нужен `nmap -sU`.

## Шаг 7: command injection в веб-интерфейсе

Второй классический класс уязвимостей IoT — веб-интерфейс, вызывающий системные команды с параметрами пользователя. Проверим диагностический ping:

```
$ curl -s "http://192.168.1.50/cgi-bin/diag.cgi?host=127.0.0.1;id"
uid=0(root) gid=0(root)
```

Символ `;` разделяет команды, и вместе с ping выполнилась `id` — вернула root. Это RCE. Но помните: у устройства мало ресурсов, и тяжёлые действия могут его «уронить». Сначала одна проверочная команда, потом аккуратная стабилизация.

## Как это выглядит целиком

Маршрут в одну историю: `nmap -sV -p-` находит MQTT (1883) и веб (80). Подписываемся на `#` без пароля и видим состояние всех ламп. Публикуем в `devices/lamp01/cmd` — лампа включается, полная компрометация без учётки. Из прошивки `grep` вытаскивает `cloud_url` и `api_token`, проверяем токен на IDOR, меняя `device_id`. В веб-интерфейсе находим command injection в `diag.cgi` (`;id` → `uid=0`). За один проход — управление парком, доступ к облаку и RCE на устройстве.

## Что мы теперь знаем

По-простому:

1. IoT-устройство атакуют по сети: веб-интерфейс, MQTT, UPnP, TR-069, облачный API.
2. MQTT без пароля позволяет читать все топики (`#`) и публиковать команды.
3. Токены и адреса облака лежат в прошивке — их проверяют на IDOR/BOLA.
4. Часть протоколов (CoAP, SSDP) работает по UDP — сканируйте `-sU`.
5. Command injection в CGI даёт RCE через один параметр.

## На что смотреть дальше

- **Скан только популярных портов.** IoT-сервисы живут на 8080, 9999, 7547 — сканируйте `-p-`.
- **Забыли про UDP.** CoAP (5683) и SSDP (1900) по TCP не видны.
- **Игнорирование облака.** Даже защищённое локально устройство может иметь дырявый API.
- **Брутфорс по MQTT/вебу.** Устройства слабые и падают; сначала пробуйте анонимный доступ и дефолтные учётки.
- **«Тяжёлые» команды.** `reboot`, `nvram commit`, прошивка могут окирпичить цель — без нужды не трогайте.

## Если не сработало

- **Брокер требует пароль.** Пробуйте дефолтные (`admin`/`public`) и токены из прошивки.
- **`-p-` слишком медленно.** Ограничьте `--top-ports 1000` плюс известные IoT-порты (7547, 9999, 49152).
- **CoAP/SSDP не видны.** Они по UDP — добавьте `nmap -sU -p 5683,1900`.
- **Устройство «упало».** Тяжёлые команды недопустимы: сначала проверочная `id`, потом пауза.
