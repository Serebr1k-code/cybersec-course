## Вопрос, с которого всё начинается

В прошлых уроках мы разобрали TPM и PCR по отдельности. Но как они работают вместе при загрузке? Оказывается, есть два разных механизма с похожими названиями: **Secure Boot** *блокирует* недоверенные компоненты, а **измеряемая загрузка** (measured boot) только *фиксирует* их состояние в PCR.

Вопрос урока: как по шагам строится цепочка доверия, что именно попадает в каждый PCR и как по журналу измерений понять, что загрузку изменили?

## Наш пример: ноутбук с Linux и systemd-boot

Перед нами ноутбук с Linux, загружающийся через **systemd-boot** и включённым Secure Boot. В прошлом уроке мы запечатывали секрет к PCR 7. Теперь разберёмся, откуда эти значения берутся и как их читать.

## Шаг 1: чем измеряемая загрузка отличается от Secure Boot

| Свойство | Secure Boot | Measured Boot |
|----------|-------------|---------------|
| Что делает | проверяет подпись, блокирует | хэширует в PCR, не блокирует |
| Основа | ключи подписи (db/dbx) | TPM + PCR |
| Результат | загрузка разрешена/запрещена | состояние платформы в PCR |

Их комбинируют: Secure Boot гарантирует, что грузится только подписанное, а measured boot даёт **доказательство** состояния для удалённой аттестации. Даже если Secure Boot обошли, «неправильные» PCR выдадут подмену — если кто-то их проверяет.

## Шаг 2: цепочка доверия по шагам

При загрузке каждый этап измеряет следующий:

1. **RTM** (Root of Trust for Measurement) — неизменяемый код в прошивке, который первым измеряет firmware.
2. **Firmware (UEFI)** измеряет свою конфигурацию и передаёт управление загрузчику.
3. **Загрузчик** (systemd-boot, GRUB, Windows Boot Manager) измеряет ядро и cmdline.
4. **Ядро** измеряет initramfs.
5. **ОС** продолжает измерения (IMA на Linux).

Каждый шаг делает **extend** в свой PCR. Если хотя бы один компонент изменён — значение PCR отличается.

## Шаг 3: читаем PCR после загрузки

Смотрим, что оказалось в PCR:

```bash
$ sudo tpm2_pcrread sha256:4,7,8,9,12
sha256:
  4 : 0x9A1B...C2
  7 : 0x3C5D...A9
  8 : 0x71E4...0F
  9 : 0x22AB...31
  12: 0xD0F1...8E
```

Что означает каждый:

- **PCR 4** — код загрузчика (bootloader stage).
- **PCR 7** — состояние Secure Boot (включён/выключен, ключи).
- **PCR 8** — команды и конфиг GRUB.
- **PCR 9** — файлы, загруженные GRUB.
- **PCR 12** — kernel + initrd + cmdline (их измеряет systemd-stub).

Чтобы сказать «всё хорошо», нужно сравнить эти значения с **эталонными** (good-known-values). Сами по себе числа ничего не значат.

## Шаг 4: systemd-stub измеряет ядро сам

В современном Linux ядро — это PE-бинарник, и **systemd-stub** сам измеряет kernel/initrd/cmdline в PCR 12. Поэтому отдельный TPM-модуль GRUB больше не нужен. Посмотреть измерения можно через `tpm2_pcrread` и `systemd-analyze`.

## Шаг 5: журнал измерений — что именно и куда попало

Значение PCR — это итог, но непонятно, *из чего* он сложился. Ответ даёт **TCG event log** — журнал измерений: в нём видно, какой компонент и в какой PCR попал.

```bash
$ ls /sys/kernel/security/tpm0/binary_bios_measurements
/sys/kernel/security/tpm0/binary_bios_measurements
$ tpm2_eventlog /sys/kernel/security/tpm0/binary_bios_measurements | head
```

Разберём только события PCR 4 (загрузчик):

```bash
$ tpm2_eventlog /sys/kernel/security/tpm0/binary_bios_measurements | grep -A3 'PCR 4'
```

Если, скажем, Secure Boot выключили, в логе изменится событие для PCR 7 — и мы сразу поймём причину. Это экономит часы диагностики «почему BitLocker просит recovery».

## Шаг 6: удалённая аттестация

Сервер проверяет клиента так: клиент посылает **quote** (подпись PCR ключом AK) вместе с **nonce** (одноразовым числом от сервера). Сервер сверяет подпись, nonce и PCR с эталоном.

```bash
$ echo -n "$(head -c16 /dev/urandom | xxd -p)" > nonce.bin
$ tpm2_quote -c ak.ctx -l sha256:0,4,7,12 -q nonce.bin -m q.msg -s q.sig -o q.pcr
```

Если PCR «правильные» — платформа считается доверенной. Это основа zero-trust и device identity.

## Шаг 7: где это ломают

- **Отключение Secure Boot** меняет PCR 7 — привязка BitLocker к PCR 7 «сломается».
- **shim + MOK** — загрузка неподписанного ядра через подписанный shim, если MOK разрешён.
- **dbx-обход** — использование отозванных, но всё ещё загружаемых бинарников.
- **TOCTOU** — изменение компонента после измерения, но до исполнения.
- **TPM-атаки** — cold-boot, fault injection, перехват шины.
- **Кража recovery-ключа** — часто проще найти его в AD/Entra ID, чем ломать TPM.

## Шаг 8: DRTM — «чистая» точка доверия

Обычная (SRTM) загрузка измеряет **снизу вверх**: сначала прошивку. Её слабость — если скомпрометирован ранний код, измерения можно подделать. **DRTM** (Dynamic Root of Trust) решает это: CPU запускает небольшой проверенный код в изолированной среде (**tboot** для Intel TXT, **SKINIT** для AMD), который **перезапускает** измерения в отдельные PCR (17–22):

```bash
$ grep -o 'txt' /proc/cpuinfo | head -1
$ sudo tpm2_pcrread sha256:17,18,19
```

DRTM не доверяет BIOS, но сложнее в настройке и требует поддержки CPU/чипсета.

## Шаг 9: как настроить правильно

Чтобы measured boot реально защищала, мало её «включить»:

- **Secure Boot включён**, dbx актуален, MOK не разрешён без нужды.
- **BitLocker привязан к PCR 7 + 11**, а не только к TPM без PIN.
- **TCG event log** сохраняется и мониторится в SIEM.
- **Remote attestation** проверяет PCR с эталоном, а не «любую подпись».
- **Обновления прошивки** контролируются: смена firmware меняет PCR.

## Шаг 10: как устроен extend и почему PCR нельзя «сбросить»

Ключевое, что нужно понимать про PCR, — это не «место хранения хеша», а накопитель, который обновляется операцией **extend**. Формула такая: `новое_значение = HASH(старое_значение || измеряемый_компонент)`. То есть каждый замер не перезаписывает PCR, а «вклеивает» хеш в цепочку, зависящую от всех предыдущих. Практические следствия: во-первых, порядок измерений важен — переставьте два компонента, и PCR изменится, хотя набор тот же. Во-вторых, вернуться к прежнему значению нельзя: если измерить что-то лишнее, PCR уже не сбросить (кроме перезагрузки). В-третьих, чтобы проверить состояние, нужно пересчитать всю цепочку по event log и сравнить с эталоном — сами числа по себе бессмысленны. Именно поэтому PCR 0–15 сбрасываются при перезагрузке, а PCR 17–22 (DRTM) перезапускаются заново в момент старта доверенной среды.

## Шаг 11: диагностика «почему BitLocker просит recovery»

Самый частый практический вопрос — почему после обновления прошивки или смены настроек система просит ключ восстановления BitLocker. Ответ всегда один: изменился PCR, к которому привязан ключ. Разбор идёт так. Сначала смотрим, к каким PCR привязан BitLocker (`manage-bde -protectors -get C:` покажет идентификаторы, например PCR 7 и 11). Затем читаем event log и ищем, какое событие изменилось — часто это обновление firmware (PCR 0/1), отключение Secure Boot (PCR 7) или смена загрузчика (PCR 4). Сравниваем текущие PCR с эталонными и видим расхождение. Это не «BitLocker сломался», а защита сработала как задумано: целостность цепочки доверия нарушена, поэтому ключ не отдаётся. Для защитника это сигнал, что кто-то (или обновление) изменил загрузочную конфигурацию.

## Частые вопросы

**Чем fTPM отличается от дискретного TPM для измерений?**
fTPM — программная реализация TPM внутри прошивки (часто в AMD PSP или Intel ME), дискретный — отдельная микросхема на плате. Значения PCR у них разные, и устойчивость к атакам тоже: fTPM зависит от корректности прошивки и может быть скомпрометирован вместе с ней, а дискретный TPM имеет собственный кристалл и шину. Для аттестации это важно: эталонные значения PCR для fTPM и дискретного TPM не взаимозаменяемы.

**Почему нельзя просто доверять подписи quote?**
Потому что подпись доказывает только то, что PCR прочитаны ключом AK, но не то, что значения «правильные». Если ранний код скомпрометирован, он может измерить ложные данные и подписать их легитимным ключом. Поэтому сервер аттестации обязан сравнивать PCR с эталоном (good-known-values), а не просто проверять подпись. Иначе attestation превращается в формальность.

**Что даёт DRTM, если уже есть SRTM?**
SRTM (обычная измеряемая загрузка) измеряет снизу вверх, начиная с прошивки, — и если прошивка скомпрометирована, вся цепочка недостоверна. DRTM (tboot/Intel TXT, SKINIT/AMD) запускает небольшой проверенный код в изолированной среде и перезапускает измерения в чистые PCR 17–22, не доверяя BIOS. Это «чистая» точка доверия, но сложнее в настройке и требует поддержки CPU и чипсета.

**Как настроить measured boot правильно?**
Мало включить Secure Boot: нужны актуальная dbx, запрет ненужного MOK, привязка BitLocker к PCR 7 и 11 (а не только к TPM), сохранение и мониторинг event log в SIEM, контроль обновлений прошивки и аттестация с проверкой эталона. Без этих условий measured boot «фиксирует», но никто не смотрит на фиксацию — а значит, она не защищает.

## Что мы теперь знаем

1. Secure Boot *блокирует*, measured boot *фиксирует*; вместе дают доказательство состояния.
2. Цепочка: RTM → firmware → загрузчик → ядро → ОС; каждый extend'ит свой PCR.
3. PCR 4 — загрузчик, PCR 7 — Secure Boot, PCR 12 — kernel/initrd/cmdline.
4. TCG event log показывает, что именно и в какой PCR измерялось.
5. Обходы: отключение Secure Boot, shim+MOK, TOCTOU, TPM-атаки, кража recovery.
6. DRTM (tboot/SKINIT) даёт чистую точку доверия в PCR 17–22.

## На что смотреть дальше

- **Обновление прошивки меняет PCR 0/1** — секреты, привязанные к ним, станут недоступны.
- **Отключённый Secure Boot меняет PCR 7** — BitLocker запросит recovery.
- **TCG log не включён** — без него трудно понять, что изменилось.
- **fTPM vs discrete** — разные значения PCR и разная устойчивость к атакам.
- **MOK разрешён** — Secure Boot можно обойти легально; это конфигурационная слабость.
