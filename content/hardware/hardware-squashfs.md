## Вопрос, с которого всё начинается

В прошлом уроке мы распаковали Squashfs и нашли пароли. Но что, если нам нужно не прочитать файловую систему, а **изменить** её — добавить свою учётную запись или SSH-ключ — и собрать образ обратно так, чтобы устройство приняло его и загрузилось?

Для этого нужно понимать, как Squashfs устроена изнутри. Разберём её на нашем же образе `rootfs.squashfs`.

## Наш пример: модифицируем корневую систему роутера

У нас есть `rootfs.squashfs`, вырезанный из дампа роутера. Задача: добавить пользователя `pentest` с известным паролем, собрать образ обратно и не сломать загрузку. Пройдём весь путь и по дороге разберём формат.

## Шаг 1: читаем суперблок

Любой образ Squashfs начинается с **суперблока** — служебной структуры на 96 байт, где записано, как этот образ читать. Первые четыре байта — сигнатура `hsqs`. Посмотреть содержимое можно флагом `-s`:

```
$ unsquashfs -s rootfs.squashfs
Found a valid SQUASHFS 4:0 superblock on rootfs.squashfs.
Filesystem size 6291456 bytes
Compression gzip
Block size 131072
Number of inodes 1204
```

Читаем главное: версия формата `4.0`, сжатие `gzip`, размер блока `131072` байта (128 КБ). Эти три параметра нам понадобятся при обратной сборке — образ должен быть собран **теми же** настройками.

## Шаг 2: распаковываем образ

Распаковка проста:

```
$ unsquashfs -d rootfs rootfs.squashfs
Parallel unsquashfs: Using 8 processors
created 1204 files
created 300 directories
created 200 symlinks
```

`-d rootfs` задаёт папку назначения. Всегда указывайте её: если распаковать в текущую директорию, а внутри окажутся симлинки с абсолютными путями, они могут «зацепить» вашу систему.

Если Squashfs лежит внутри большого дампа, `dd` не обязателен — `unsquashfs` умеет читать по смещению:

```
$ unsquashfs -o 131072 -d rootfs dump1.bin
```

`-o 131072` — это offset `0x20000`, где начинается образ.

## Шаг 3: что ищем в распакованном rootfs

Пройдёмся по типовым местам:

```
$ cd rootfs
$ grep -vE 'nologin|false|sync' etc/passwd
root:x:0:0:root:/root:/bin/sh
$ grep -rE 'telnetd|dropbear|nc -l' etc/ | head
etc/init.d/S50telnetd: telnetd -l /bin/sh
```

Вторая находка показательна: скрипт инициализации запускает `telnetd` с оболочкой `sh` — это фактически бэкдор, доступный без пароля. Такие вещи в прошивках встречаются регулярно.

## Шаг 4: модифицируем образ

Добавим учётную запись. Пароль в Linux хранится не открытым текстом, а в виде хеша; сгенерируем его утилитой `openssl` (схема `-1` — md5crypt):

```
$ NEWHASH=$(openssl passwd -1 -salt abc 'hunter2')
$ echo "pentest:$NEWHASH:0:0::/root:/bin/sh" >> rootfs/etc/passwd
```

Или добавим SSH-ключ, чтобы входить без пароля:

```
$ mkdir -p rootfs/root/.ssh
$ cat id_rsa.pub > rootfs/root/.ssh/authorized_keys
```

## Шаг 5: собираем обратно теми же параметрами

Сборкой занимается `mksquashfs`. Критично повторить сжатие и размер блока из суперблока:

```
$ mksquashfs rootfs/ rootfs_new.squashfs -comp gzip -b 131072 -noappend -all-root
Parallel mksquashfs: Using 8 processors
Filesystem size 6311520 bytes
```

Флаг `-noappend` запрещает дописывание в существующий образ, `-all-root` выставляет владельца `root:root` на все файлы — на устройстве иначе сервисы могут не запуститься.

## Шаг 6: проверяем и вшиваем на место

Собранный образ проверяем локально, примонтировав его (это требует прав root):

```
$ sudo mount -o loop,ro rootfs_new.squashfs mnt
$ ls mnt/etc/passwd
mnt/etc/passwd
$ sudo umount mnt
```

И вот здесь — главная ловушка. Новый образ получился **больше** исходного (6311520 против 6291456 байт). Если вшить его по тому же смещению, он затрёт следующий раздел, и устройство не загрузится:

```
$ dd if=rootfs_new.squashfs of=dump_new.bin bs=1 seek=131072 conv=notrunc
```

Решение — уместить образ в исходный размер: собрать с более сильным сжатием (`-comp xz`) или удалить ненужные файлы (документацию, кэш пакетов). В нашем случае помогает `xz`: он даёт примерно втрое лучшее сжатие, чем `gzip`.

## Шаг 7: если формат нестандартный

Иногда обычный `unsquashfs` отказывается читать образ с сообщением `Filesystem uses unknown compression`. Это значит, что производитель использовал нестандартный LZMA. Справится патченая сборка `unsquashfs-lzma`. А если в `file` указана `version 3.0` — это старый формат, для него нужен соответствующий инструмент.

## Как это выглядит целиком

Маршрут в одну историю: `unsquashfs -s rootfs.squashfs` показывает сжатие `gzip` и блок `131072`. `unsquashfs -d rootfs rootfs.squashfs` распаковывает, `grep -vE 'nologin|false' etc/passwd` показывает root, а `grep -rE 'telnetd'` находит бэкдор. Добавляем `pentest` через `openssl passwd -1`, собираем `mksquashfs rootfs/ rootfs_new.squashfs -comp gzip -b 131072 -noappend -all-root`. Новый образ больше исходного — пересобираем с `-comp xz`, чтобы уложиться в раздел, и вшиваем `dd`. Вся цепочка: прочитать суперблок → распаковать → изменить → собрать теми же параметрами → уложиться в размер.

## Что мы теперь знаем

По-простому:

1. Squashfs начинается с суперблока, где записаны версия, сжатие и размер блока.
2. Распаковка — `unsquashfs -d dir`; для образа внутри дампа есть флаг `-o`.
3. Обратная сборка — `mksquashfs` с **теми же** сжатием и блоком.
4. Новый образ не должен быть больше исходного, иначе затрёт соседний раздел.
5. Нестандартный LZMA и версию 3.0 обычный `unsquashfs` не читает.

## На что смотреть дальше

- **Неверный `count` при `dd`.** Обрезанный образ даёт «failed to read fragment table».
- **Распаковка в текущую папку.** Абсолютные симлинки могут затереть систему — всегда `-d dir`.
- **Другое сжатие.** Собрали `xz`, а ядро ждёт `gzip` — монтирование упадёт.
- **Образ больше исходного.** Затирание соседнего раздела и нерабочая прошивка.
- **Права.** Без `-all-root` владельцы будут с хоста, и сервисы могут не стартовать.

## Если не сработало

- **`Filesystem uses unknown compression`.** Нестандартный LZMA — нужен `unsquashfs-lzma`.
- **Образ не влезает в раздел.** Пересоберите с `-comp xz` или удалите лишние файлы.
- **Сервисы не стартуют после прошивки.** Забыт `-all-root` — владельцы файлов не root.
- **`failed to read fragment table`.** Обрезан `dd` — неверный `count`.
- **Образ не монтируется локально.** Ядро должно поддерживать выбранное сжатие (`xz`/`lzo`); иначе проверяйте через `unsquashfs -s`.

## Шаг 7: если устройство проверяет образ

Модифицированная Squashfs загрузится, только если загрузчик не проверяет её целостность. Проверок бывает три уровня, и обход зависит от уровня:

| Проверка | Как выглядит | Обход |
|----------|--------------|-------|
| CRC/checksum | контрольная сумма в заголовке | пересчитать после сборки |
| Подпись образа | RSA/ECDSA в заголовке | нужен приватный ключ (иначе не обойти) |
| Verified boot | цепочка доверия от bootROM | аппаратная, требует glitch/уязвимости |

Часто устройство проверяет только CRC ядра, а rootfs — нет. Тогда достаточно заменить Squashfs, а заголовок с суммой оставить прежним. Смотрим, как выглядит заголовок прошивки:

```bash
$ binwalk dump1.bin
0             0x0             uImage header (U-Boot)
```

`uImage`-заголовок содержит CRC образа — если загрузчик его проверяет, после сборки пересчитывают CRC и записывают обратно (утилитой `mkimage` или скриптом).

Если же стоит полноценная подпись, а ключа нет — путь один: не трогать образ, а менять поведение в рантайме (например, монтировать свой overlay поверх) либо искать обход через уязвимость загрузчика.

## Если не сработало

- **Устройство не грузится после заливки.** Не совпали параметры сборки (сжатие/блок) или размер образа вышел за раздел — сверьтесь с `unsquashfs -s`.
- **Файлы «пропали».** Забыли `-all-root` — сервисы не читают файлы от чужого владельца.
- **`unsquashfs` падает на образе.** Нестандартное сжатие — используйте `sasquatch` или `unblob`.
- **Образ грузится, но правки нет.** Загрузчик взял rootfs из другого раздела (overlay перекрыл изменения) — проверьте `bootargs` и `mtdparts`.
- **Проверка целостности мешает.** Найдите уровень проверки (CRC или подпись) и обходите соответственно.

## Как защититься

- Подписывать прошивку и проверять подпись в загрузчике, а не только CRC.
- Включать secure boot с цепочкой доверия от bootROM.
- Шифровать rootfs ключом из OTP, чтобы модификация была бесполезна.
- Проверять целостность на каждом этапе загрузки (ядро, rootfs, overlay).
