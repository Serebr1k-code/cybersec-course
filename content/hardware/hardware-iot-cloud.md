Умное устройство — это не только железо, но и облако, с которым оно связано. Часто именно облачный канал слабее локального: MQTT без аутентификации, предсказуемые топики, ключи в прошивке. Урок — практическое введение в поверхность атаки IoT-облака.

## Теория

Типовая архитектура:

```
Устройство  <--MQTT/TLS-->  Брокер (облако)  <--MQTT/HTTPS-->  Мобильное приложение
      |                                                              |
      +---------------- HTTPS REST API ------------------------------+
```

**MQTT** — лёгкий pub/sub-протокол:
- **Broker** — сервер (Mosquitto, EMQX, AWS IoT Core).
- **Topic** — иерархия (`home/room/device/state`).
- **Wildcards** — `+` (один уровень), `#` (все уровни).
- **QoS** — уровень доставки 0/1/2.
- **Retain** — хранить последнее сообщение.

Типовые слабости:
| Слабость | Как выглядит |
|----------|--------------|
| Анонимный брокер | подключение без логина/пароля |
| Wildcard-подписка | `#` даёт все сообщения |
| Ключи в прошивке | MQTT-креды/сертификаты в образе |
| Предсказуемые топики | `device/<MAC>/cmd` |
| Нет проверки авторизации | любой клиент шлёт команды |
| Открытый REST API | команды без токена |
| Слабые облачные креды | AWS IoT ключи в открытом виде |

## Инструменты и команды

- **mosquitto_pub / mosquitto_sub** — MQTT-клиенты.
- **MQTT Explorer** — GUI.
- **Wireshark** — разбор MQTT.
- **binwalk/strings** — извлечение ключей из прошивки.
- **nmap** — поиск брокеров (1883, 8883).
- **aws-iot / tuya API** — облачные вызовы.

```bash
# Найти MQTT-брокеры
nmap -p 1883,8883 --open 192.168.1.0/24

# Анонимная подписка на всё
mosquitto_sub -h broker.local -p 1883 -t '#' -v

# Публикация команды
mosquitto_pub -h broker.local -p 1883 -t 'home/lamp/cmd' -m '{"state":"on"}'

# С аутентификацией
mosquitto_sub -h broker -u user -P pass -t '#' -v
mosquitto_sub -h broker --cafile ca.crt --cert client.crt --key client.key -t '#' -v

# Поиск кредов в прошивке
strings squashfs-root/usr/bin/* | grep -i "mqtt\|broker\|password"
```

## Разобранный пример: атака на умную лампу через MQTT

**Дано:** умная лампа, приложение, локальная сеть. Нужно понять канал управления.

**Шаг 1 — поиск брокера.** `nmap` находит MQTT на 1883 у устройства. Или приложение подключается к облачному брокеру (смотрим трафик телефона через proxy).

**Шаг 2 — проверка анонимности.** Пробуем `mosquitto_sub -h <broker> -t '#' -v` без кредов. Если получаем поток — брокер открыт.

**Шаг 3 — топики.** В потоке видим топики: `lamp/XX:XX:XX/cmd`, `lamp/XX:XX:XX/state`. Структура предсказуема.

**Шаг 4 — подписка на всё.** С `#` видим команды всех устройств. Если видим чужие — нет изоляции по аккаунту.

**Шаг 5 — отправка команды.** Публикуем `lamp/XX:XX:XX/cmd` с `{"state":"on"}`. Если лампа реагирует — нет авторизации.

**Шаг 6 — облачный API.** Если управление через облако — ищем ключи в прошивке (`strings`) и пробуем напрямую вызвать REST API. Проверяем IDOR: чужой deviceId.

**Шаг 7 — вывод.** Фиксируем: анонимный брокер / wildcard / отсутствие авторизации. Рекомендации: TLS, аутентификация, ACL по топикам, изоляция аккаунтов.

## Частые ошибки

- **Атака на чужие устройства.** Вмешательство в чужие IoT-устройства — преступление. Только свои/тестовые.
- **Игнорирование TLS.** На 8883 нужен TLS; без сертификатов не подключиться. Извлекайте их из прошивки.
- **Публикация опасных команд.** `{"state":"unlock"}` на замке — риск. Работайте на стенде.
- **Не тот топик.** Ошибка в иерархии = команда не дойдёт. Копируйте топик точно из потока.
- **Забыть про retain.** Retained-сообщения приходят сразу при подписке — не путайте с live-трафиком.
- **Слабые облачные ключи.** AWS IoT требует подписи SigV4; просто «ключ» не сработает. Читайте документацию.

## Теория: как IoT-устройства выходят в облако

Устройство подключается к MQTT-брокеру или HTTP-API. Аутентификация — по сертификату, токену или (часто) вообще без неё. Прошивка содержит адрес брокера и креды. Поверхность атаки: сам брокер, протокол (MQTT/CoAP), прошивка, облачный backend.

## Инструменты

```bash
# MQTT
mosquitto_sub -h broker -t '#' -v
mosquitto_pub -h broker -t 'cmd/device' -m 'on'
mqtt-pwn --host broker
# CoAP
coap-client -m get coap://device/status
# прошивка
binwalk -Me firmware.bin
strings firmware.bin | grep -iE 'mqtt|broker|token|api'
```

`mosquitto_sub -t '#'` подписывается на все топики — если брокер без auth, виден весь трафик.

## Разобранный пример 2: извлечение токена из прошивки

1. Распаковываем прошивку лампы.
2. Находим в строках адрес брокера и токен.
3. Подключаемся: `mosquitto_sub -h broker -t 'device/#' -v`.
4. Публикуем команды управления (в рамках теста).
5. Оцениваем: можно ли управлять всеми устройствами аккаунта.

## Таблица

| Вектор | Инструмент | Условие |
|--------|-----------|---------|
| Открытый MQTT | mosquitto_sub | нет auth |
| Слабый токен | перебор | короткий/статичный |
| Hardcoded-креды | strings/binwalk | доступ к прошивке |
| CoAP без auth | coap-client | UDP 5683 |
| Небезопасный OTA | анализ обновления | нет подписи |

## CoAP: детали

CoAP — UDP-протокол для constrained-устройств (5683/5684). Аналог HTTP, но легковесный. Часто без аутентификации. Проверка:

```bash
coap-client -m get coap://device/.well-known/core
coap-client -m get coap://device/status
coap-client -m put coap://device/config -e 'admin=true'
```

`.well-known/core` перечисляет ресурсы — отправная точка. Отсутствие DTLS (5684) означает открытый трафик.

## Защита IoT

- Аутентификация на брокере (логин/пароль, сертификаты, mTLS).
- Шифрование (TLS/DTLS).
- Не хранить долгоживущие креды в прошивке (использовать провижининг).
- Подписанные OTA-обновления.
- Изоляция устройств в отдельном VLAN.
- Мониторинг аномалий трафика.

## Разведка облачного backend

Помимо MQTT/CoAP, устройства обращаются к HTTP-API вендора. Извлеките из прошивки URL и токены, затем проверьте API на IDOR/отсутствие auth. Часто один токен даёт доступ ко всем устройствам аккаунта — это классический IoT-мисконфиг. Проверяйте эндпоинты вида `/api/v1/device/<id>/command` на подстановку чужого id.

## Итог

IoT-поверхность = устройство + протокол + облако. Атакуйте самый слабый слой: открытый MQTT, hardcoded-токен или IDOR в API. Для защиты — аутентификация, шифрование, провижининг и изоляция устройств.

## Разбор топиков MQTT и IDOR в облаке

MQTT-топики строятся по шаблону: `device/<id>/status`, `device/<id>/command`, `account/<id>/#`. Если брокер не проверяет права на топик, подписка `#` показывает трафик всех устройств, а публикация в `device/<чужой-id>/command` управляет чужими устройствами. Проверка:

```bash
mosquitto_sub -h broker -p 1883 -t '#' -v
mosquitto_sub -h broker -t 'account/#' -v --cafile ca.crt
mosquitto_pub -h broker -t 'device/1234/command' -m '{"on":true}'
```

Аналогично в HTTP-API вендора: эндпоинт `/api/v1/devices/<id>` без проверки владельца даёт IDOR. Меняя `<id>` в запросе, можно читать состояние и отправлять команды чужим устройствам. Часто id последовательны (1,2,3...), что делает перебор тривиальным. Это одна из самых частых и опасных находок в IoT: один пользователь управляет устройствами всех остальных.

Отдельно проверяйте, где хранится токен: если он один на весь продукт (hardcoded в прошивке), то любой владелец устройства имеет доступ к брокеру и может подписаться на общие топики. Правильная архитектура — уникальные креды на устройство, ACL на топики по account/device, TLS.
