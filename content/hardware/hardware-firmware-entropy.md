Вы распаковали прошивку, `binwalk` показал кучу разделов — а внутри ничего не читается: ни squashfs, ни строк, ни ELF. Причина почти всегда одна из двух: данные **сжаты** или **зашифрованы**. Разница принципиальна: сжатие можно распаковать стандартными утилитами (zlib, LZMA, gzip), а шифрование — нет, пока не найден ключ. Первый диагностический инструмент здесь — **энтропия**: мера «случайности» данных. Этот урок учит читать графики энтропии, отличать сжатие от шифрования и находить ключи.

Мы разберём теорию энтропии, `binwalk -E`, утилиту `ent`, типичные профили сжатия/шифрования, пример анализа зашифрованного образа и методы поиска ключа — от `strings` до дампа secure element.

## Что такое энтропия данных

Энтропия (в контексте анализа бинарников) — это оценка того, насколько «непредсказуемы» байты в окне. Если все байты одинаковые (0x00, 0xFF) — энтропия низкая (близко к 0 бит/байт). Если байты равномерно распределены по 0-255 — энтропия максимальная (близко к 8 бит/байт). Считается по формуле Шеннона на скользящем окне.

Практический смысл:

- **Низкая энтропия (<4 бит/байт)** — пустые области, таблицы, текст, код ARM/x86 (у него повторяющиеся паттерны), выровненные структуры.
- **Средняя энтропия (4-6)** — смешанные данные: код + данные, простые сжатия, таблицы.
- **Высокая энтропия (7.5-8)** — либо сильное сжатие (zlib, LZMA, xz), либо шифрование (AES). Оба выглядят как шум.

Ключевой вывод: **высокая энтропия — необходимое, но не достаточное условие шифрования**. Сжатый образ тоже даёт ~8. Различают их по контексту: наличие сигнатур/заголовков, поведение при распаковке, структура.

## binwalk -E: графики энтропии

`binwalk` умеет строить график энтропии по образу. Запуск:

```bash
binwalk -E firmware.bin
```

На выходе — PNG-график `firmware.bin.png` (если собран с matplotlib) и текстовые маркеры. График показывает энтропию по оси X (смещение) и бит/байт по Y. Интерпретация:

- Ровные плато на 8.0 → зашифрованные/сжатые регионы.
- Провалы к 0-3 → пустые области, таблицы разделов, заголовки.
- Ступеньки → разные разделы с разной обработкой.

Дополнительные флаги `binwalk`:

```bash
binwalk -E -J firmware.bin       # -J: JSON-вывод энтропии
binwalk -E --save firmware.bin   # сохранить график
binwalk -A firmware.bin          # -A: сигнатуры сжатия/шифрования
binwalk -W firmware.bin          # -W: исключить дубликаты
```

## Как отличить сжатие от шифрования

Признаки:

| Признак | Сжатие | Шифрование |
|---------|--------|------------|
| Энтропия | ~7.5-8.0 | ~7.9-8.0 (ровнее) |
| Сигнатуры | zlib `78 9C`, gzip `1F 8B`, xz, LZMA | нет |
| Распаковка | успешна стандартными утилитами | провал |
| Реакция на изменение байта | ломает весь поток после точки | ломает блок целиком |
| Границы | чёткие по заголовкам | выровнены по блокам (AES — кратно 16) |
| Повторяемость блоков | нет | в ECB могут повторяться блоки |

Практика: если энтропия 8.0, а `binwalk` не находит ни одной сигнатуры сжатия — это, скорее всего, шифрование. Если находит zlib/gzip/LZMA — распаковываем.

## Инструменты: полный набор с флагами

```bash
# --- binwalk: энтропия и сигнатуры ---
binwalk -E firmware.bin
binwalk -A -Y firmware.bin          # сигнатуры + «показывать всё»
binwalk -eM firmware.bin            # извлечение, рекурсивно
binwalk -D 'lzma:lzma' firmware.bin # кастомный экстрактор

# --- ent: статистика энтропии файла ---
ent firmware.bin
# Entropy = 7.999821 bits per byte.
# Chi square distribution for 4194304 samples is 254.11

# --- radare2: энтропия по секциям ---
r2 -q -c 'iS' firmware.bin
r2 -q -c '/x 1f8b' firmware.bin     # поиск gzip magic

# --- unblob: современный автокаскад ---
unblob -d outdir firmware.bin -v

# --- dd/xxd: ручное вырезание ---
xxd -s 0x10000 -l 64 firmware.bin
dd if=firmware.bin of=part.bin bs=1 skip=$((0x10000)) count=$((0x40000))
```

Для сжатия: `zlib-flate -uncompress`, `lzma -d`, `xz -d`, `unlzma`, `gzip -d`. Для шифрования: `openssl enc`, `cryptsetup` (если найден ключ), кастомные скрипты.

## Разобранный пример: анализ зашифрованного образа

Дано: `router.bin` — прошивка роутера, `binwalk` не находит ФС.

**Шаг 1 — график энтропии.**

```bash
binwalk -E router.bin
# (график: ровное плато 8.0 от 0x10000 до 0x800000)
```

Плато на 8.0 → регион сжат или зашифрован.

**Шаг 2 — поиск сигнатур сжатия.**

```bash
binwalk -A router.bin
# DECIMAL   HEX   DESCRIPTION
# 65536     0x10000  Zlib compressed data
```

Найдена zlib-сигнатура! Значит, это сжатие, а не шифрование.

**Шаг 3 — распаковка.**

```bash
dd if=router.bin of=z.bin bs=1 skip=65536
zlib-flate -uncompress < z.bin > rootfs.bin
file rootfs.bin
# rootfs.bin: Squashfs filesystem, little endian, version 4.0
unsquashfs rootfs.bin
```

**Шаг 4 — вывод.** Это было сжатие — распаковали. Если бы сигнатур не было, переходили бы к поиску ключа.

## Поиск ключа при шифровании

Если подтверждено шифрование, ключ ищут в:

1. **Прошивке загрузчика (bootloader).** U-Boot/CFE часто содержат ключ расшифровки ядра или указывают на него. `strings bootloader.bin | grep -i key`.
2. **Открытом регионе прошивки.** Ключ может лежать в незашифрованном заголовке (первые 4 КБ) или в отдельном разделе.
3. **Дампе RAM.** Загруженная прошивка расшифрована в памяти — снимаем дамп RAM через JTAG/UART и ищем распакованную ФС.
4. **Secure element / OTP.** Ключ в efuse/OTP/secure element; извлекается side-channel/glitch-атаками.
5. **Конфигурационных файлах.** `/etc/config`, NVRAM, `env` U-Boot.
6. **Аппаратных интерфейсах.** SPI-флеш с ключом на отдельном чипе.

```bash
# поиск ключей/строк
strings -n 8 bootloader.bin | grep -iE 'key|aes|crypt|secret'
# поиск 16/32-байтных ключей в открытом регионе
xxd -s 0 -l 4096 firmware.bin
# env U-Boot
strings uboot.bin | grep -E 'bootargs|mtdparts|aes'
```

## Шифрование на лету (on-the-fly) и MTD

Многие SoC расшифровывают флеш **прозрачно**: контроллер (или ядро через `dm-crypt`/MTD) расшифровывает данные при чтении. Тогда дамп через JTAG/`nanddump` даёт зашифрованные байты, а чтение «изнутри системы» (через `cat /dev/mtdblockX`) — уже расшифрованные. Практический приём: если есть shell/доступ, читайте разделы изнутри; если только дамп — ищите ключ.

MTD-разделы: `cat /proc/mtd` показывает карту; `mtdblock` даёт блочный доступ; для UBI поверх MTD — `ubiblock`.

## Расшифровка: практические пути

- **Дамп из памяти.** Загрузитесь, подключите JTAG, снимите RAM — там ФС в открытом виде.
- **Перехват ключа.** Если контроллер расшифровывает на лету, ключ есть на шине (SPI/eMMC) — снимите логику логическим анализатором и найдите ключ в трафике.
- **Атака на загрузчик.** Многие загрузчики печатают ключ в debug-консоль или принимают команды расшифровки.
- **Brute-force.** Для слабых ключей (например, пароль-строка) — перебор словарём.
- **Fault injection.** Сбой в момент проверки/расшифровки — обход.

## Частые ошибки и подводные камни

- **Путать сжатие с шифрованием.** Всегда сначала ищите сигнатуры сжатия — распаковать проще, чем расшифровать.
- **Игнорировать первые/последние байты.** Заголовок часто не зашифрован; ключ/параметры могут быть там.
- **Считать энтропию 8.0 приговором.** Сжатый образ тоже 8.0; ищите `binwalk -A`.
- **Неверное выравнивание AES.** Шифрование блочное; вырезание не по границе блока даёт мусор.
- **Забыть про RAM.** Прошивка в памяти расшифрована — это самый быстрый путь.
- **Игнорировать U-Boot env.** Там часто mtdparts, ключи, команды.
- **Слишком маленькое окно энтропии.** Пропустите короткие зашифрованные регионы.

## Справочные таблицы

Сигнатуры сжатия:

| Формат | Magic | Утилита |
|--------|-------|---------|
| gzip | `1F 8B` | gzip -d |
| zlib | `78 9C` / `78 DA` | zlib-flate |
| LZMA | `5D 00 00` | unlzma |
| xz | `FD 37 7A 58 5A 00` | xz -d |
| bzip2 | `42 5A 68` | bzip2 -d |
| LZ4 | `04 22 4D 18` | lz4 -d |
| zstd | `28 B5 2F FD` | zstd -d |

Энтропия и вывод:

| Значение | Интерпретация |
|----------|---------------|
| 0.0-2.0 | пусто/константа |
| 2.0-4.0 | структурированные данные, код |
| 4.0-6.0 | смешанные данные, слабое сжатие |
| 6.0-7.5 | сжатие/частичное шифрование |
| 7.5-8.0 | сильное сжатие ИЛИ шифрование |

## Что дальше / решение

Дальнейшие шаги: (1) если нашли сигнатуру сжатия — распакуйте и перейдите к анализу rootfs; (2) если шифрование — снимите дамп RAM/перехватите шину; (3) проверьте U-Boot env и первые КБ образа на ключи; (4) для on-the-fly-шифрования читайте разделы изнутри системы. Для защиты: храните ключи в secure element/OTP, используйте аппаратное шифрование, не оставляйте ключ в открытом заголовке, отключайте debug-интерфейсы. В авторизованном пентесте зафиксируйте: тип защиты (сжатие/шифрование), метод обхода и найденные артефакты.

## Практикум: от графика к решению

Закрепим методологию на сквозном упражнении. Возьмите три-четыре реальные прошивки (роутер, IP-камера, NAS, фитнес-трекер) и для каждой постройте график `binwalk -E`. Заведите таблицу со столбцами: смещение региона, энтропия, найдены ли сигнатуры сжатия (`binwalk -A`), удалось ли распаковать, похоже ли на шифрование. Через десяток образов вы начнёте узнавать «почерк»: типичная прошивка роутера даёт чередование низкоэнтропийного загрузчика, среднего ядра и высокого squashfs, а зашифрованная — ровное плато почти на всём объёме с коротким открытым заголовком.

Полезно вести дневник признаков. Если `binwalk -A` находит `Zlib compressed data` — почти наверняка это сжатие, и дальше вы работаете с `zlib-flate`/`unlzma`. Если сигнатур нет, но энтропия ровная и блоки выровнены по 16 байт — это AES-подобное блочное шифрование. Если в первых килобайтах есть строка вроде `AES-128-CBC` или `KEY=` — вы нашли подсказку о схеме, и стоит поискать ключ рядом. Иногда ключ лежит прямо в открытом заголовке: производители экономят и «шифруют» образом, где ключ известен любому, кто прочитал первые 4 КБ.

Отдельно потренируйтесь на «on-the-fly» случаях: если у вас есть shell на устройстве, сравните байты, полученные `dd` из `/dev/mtdblockX`, и байты, снятые тем же `dd` через JTAG. Расхождение означает прозрачную расшифровку контроллером, и тогда самый быстрый путь — читать разделы изнутри. Наконец, оформите результат в виде дерева решений: «энтропия высокая → есть сигнатура сжатия? → да: распаковать / нет: искать ключ → ключ в заголовке? / в RAM? / в secure element?». Такое дерево — рабочий артефакт, который экономит часы на следующем образе.
