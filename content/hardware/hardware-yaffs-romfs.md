## Вопрос, с которого всё начинается

Squashfs, JFFS2 и UBIFS покрывают большинство прошивок. Но иногда `binwalk` показывает что-то, чего мы ещё не видели, а привычные инструменты отказываются работать. Две такие «редкие» файловые системы — **YAFFS** и **ROMFS** — встречаются в устройствах на NAND-памяти и в маленьких образах.

Разберём обе на двух примерах: дампе NAND-камеры и прошивке с нестандартным разделом.

## Наш пример: дамп NAND и прошивка камеры

У нас два артефакта. Первый — `nand.bin`, сырой дамп NAND-памяти устройства. Второй — `firmware.bin`, прошивка IP-камеры, в которой есть подозрительный раздел. Начнём с YAFFS в дампе NAND.

## Шаг 1: почему YAFFS устроена необычно

Чтобы понять YAFFS, нужно помнить, как устроена NAND-память. Она делится на **блоки**, а блоки — на **страницы** (обычно 2048 или 4096 байт). У каждой страницы есть дополнительная область **OOB** (out-of-band, «вне полосы») на 64–128 байт для служебных данных. И главное: NAND нельзя перезаписать постранично — только стереть целый блок.

**YAFFS** (Yet Another Flash File System) спроектирована именно под это: файл разбит на куски — **chunks**, размером со страницу, а метаданные каждого куска (какой это файл, какая часть, сколько байт) лежат в **OOB**-области страницы. Такая схема отлично переживает обрывы питания, но она же и главная ловушка: без OOB файловую систему не собрать.

## Шаг 2: определяем YAFFS в дампе

Прогоняем дамп через `binwalk`:

```
$ binwalk nand.bin
DECIMAL       HEXADECIMAL     DESCRIPTION
0             0x0             YAFFS filesystem, little endian
```

Сигнатуры как таковой у YAFFS нет — она опознаётся по структуре. Прежде чем извлекать, проверим, есть ли в дампе OOB-области. Если дампер их отбросил, восстановить ФС будет невозможно:

```
$ python3 - <<'EOF'
data = open('nand.bin','rb').read()
page, spare = 2048, 64
print("pages:", len(data)//(page+spare))
print("first OOB:", data[page:page+16].hex())
EOF
pages: 512
first OOB: ffffffff00000001...
```

`first OOB` не пустой — служебные данные на месте, значит извлечение возможно.

## Шаг 3: извлекаем YAFFS

Для YAFFS2 есть инструмент `unyaffs2` (или набор `yaffs2utils`):

```
$ unyaffs2 nand.bin outdir/
$ ls outdir/
bin  dev  etc  lib  proc  sbin  usr  var  www
```

Получили полноценное дерево файлов. Смотрим учётные записи:

```
$ cat outdir/etc/passwd
root:x:0:0:root:/root:/bin/sh
admin:$1$abc$...:1000:1000::/home/admin:/bin/sh
```

Хеш пароля `admin` на месте — его можно ломать офлайн.

## Шаг 4: переходим к ROMFS

**ROMFS** — предельно простая read-only ФС: минимум метаданных, плоский список inode'ов. Её придумали для экономии места, и она до сих пор встречается в recovery-разделах, маленьких rootfs и образах прошивок. Признак — сигнатура `-rom1fs-` в начале образа.

Ищем её прямо в прошивке камеры, не полагаясь на `binwalk`:

```
$ grep -aboP '\-rom1fs\-' firmware.bin
0x00310000:-rom1fs-
```

`grep -abo` печатает смещение найденной строки. ROMFS начинается с `0x310000`.

## Шаг 5: вырезаем и монтируем ROMFS

Прочитаем заголовок: после сигнатуры (8 байт) идёт размер образа в big-endian:

```
$ xxd -s 0x310000 -l 32 firmware.bin
00000000: 2d72 6f6d 3166 732d 000c 0000 0000 0000  -rom1fs-........
```

Размер — `0x000c0000`, то есть 786432 байта. Вырезаем этот кусок и монтируем (модуль romfs встроен в ядро Linux):

```
$ dd if=firmware.bin of=romfs.img bs=1 skip=$((0x310000)) count=$((0x0c0000))
$ sudo mount -t romfs romfs.img /mnt/romfs
$ ls /mnt/romfs
bin  etc  lib  sbin  www
```

Внутри — скрипты инициализации и бинарники веб-интерфейса. ROMFS read-only, но её содержимое полностью доступно.

## Шаг 6: где хранятся настройки

Важный нюанс: ROMFS нельзя записать, значит изменяемая конфигурация устройства лежит где-то ещё — обычно в отдельном JFFS2 или UBI-разделе. Поэтому, найдя ROMFS, не останавливайтесь: посмотрите на остальную прошивку, там будет записываемая часть.

## Как это выглядит целиком

Соберём маршрут в одну историю. Берём `firmware.bin` камеры, `binwalk` показывает разделы, `grep -aboP '\-rom1fs\-'` находит сигнатуру на смещении `0x310000`, читаем big-endian размер (`0x000c0000`), вырезаем `dd` и монтируем. Внутри — `etc/init.d/rcS`, с которого начинается разбор: какие сервисы стартуют, какие логины и пароли зашиты в скрипты. Параллельно смотрим NAND-дамп: если он снят с OOB, `unyaffs2` даёт второе дерево, где обычно лежит записываемая конфигурация с хешем `admin`. ROMFS read-only — значит, все изменяемые настройки ищите в этом втором дереве или в JFFS2/UBI-разделе. Два дерева вместе дают полную картину: неизменяемый код и то, что устройство хранит о себе.

## Что мы теперь знаем

По-простому:

1. YAFFS — журнальная ФС для NAND; метаданные кусков лежат в OOB-области страниц.
2. Без OOB в дампе YAFFS не восстановить — это первое, что нужно проверить.
3. YAFFS2 извлекают `unyaffs2`; важно знать размер страницы (2048/4096).
4. ROMFS — минимальная read-only ФС с сигнатурой `-rom1fs-`; монтируется нативно.
5. Раз ROMFS read-only, настройки устройства хранятся в другом разделе.

## На что смотреть дальше

- **Потерянные OOB.** Дампер мог отбросить spare-область — тогда YAFFS мёртв.
- **YAFFS1 против YAFFS2.** Разные раскладки chunkId; берите правильный инструмент.
- **Неверный размер страницы.** 512/2048/4096 — при ошибке извлекается мусор.
- **ROMFS big-endian.** Размер и поля читаются как big-endian, не путайте.
- **Перекрытие форматов.** ROMFS может лежать внутри другого образа — используйте `binwalk -eM`.

## Если не сработало

- **`unyaffs2` падает с ошибкой.** Скорее всего неверный размер страницы: попробуйте 512, 2048 и 4096 байт по очереди.
- **Файлы извлекаются «пустыми».** Дамп снят без OOB или это YAFFS1, а не YAFFS2 — нужен другой инструмент (`unyaffs`).
- **ROMFS не монтируется.** Проверьте, что скопировали ровно столько байт, сколько указано в заголовке; лишний хвост ломает ФС.
- **Ничего не находится.** Образ может быть зашифрован или сжат — переходите к анализу энтропии.
- **Хеши паролей не ломаются.** Возможно, это `$6$` (sha512crypt) — считайте офлайн с `hashcat`, не онлайн.
- **`binwalk` не находит ROMFS.** Сигнатура может быть выровнена по границе блока — ищите вручную через `grep -aboP` и `dd` по найденному смещению.
- **Дамп разбит на несколько файлов.** Склейте их `cat` в правильном порядке, иначе страницы перемешаются и ФС не соберётся.
