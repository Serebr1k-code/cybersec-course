## Вопрос, с которого всё начинается

В прошлом уроке мы поняли правила игры в АСУ ТП: чтение безопасно, запись опасна. Но чтобы оценивать промышленную сеть, нужно видеть её целиком — какие там вообще устройства, как они связаны и откуда на них можно напасть.

Разберём архитектуру АСУ ТП и карту векторов атак.

## Наш пример: карта участка АСУ ТП

Вернёмся на тот же участок промышленной сети. Наша задача — не просто прочитать один ПЛК, а понять, из каких компонентов состоит система и как они образуют единый организм.

## Шаг 1: разбираем компоненты

Промышленная система состоит из нескольких типов устройств, и у каждого своя роль:

- **ПЛК** (Programmable Logic Controller) — контроллер, который исполняет логику управления: «если датчик показывает X, открыть клапан Y».
- **RTU** (Remote Terminal Unit) — удалённый терминал для сбора телеметрии, часто на объектах без оператора.
- **HMI** (Human-Machine Interface) — операторская панель, экран с кнопками и показаниями.
- **SCADA-сервер** — собирает данные со всех устройств и управляет ими.
- **Historian** — архив измерений: база, куда пишется вся телеметрия.
- **Инженерная станция** — компьютер, с которого программируют ПЛК (например, TIA Portal для Siemens).

Увидеть их можно пассивно — по зеркалированному трафику. Каждое устройство оставляет свой «почерк»: ПЛК отвечает на Modbus, historian тянет данные, HMI шлёт команды.

## Шаг 2: раскладываем по уровням Purdue

Чтобы понять, где что находится и как атака идёт «сверху вниз», используют модель **Purdue**:

| Уровень | Название | Что там |
|---------|----------|---------|
| 0 | Process | датчики, приводы |
| 1 | Basic control | ПЛК, RTU |
| 2 | Supervisory | HMI, SCADA |
| 3 | Operations | historian, инженерные станции |
| 3.5 | DMZ | шлюзы, прокси |
| 4 | Enterprise | корпоративная IT |
| 5 | Internet | внешний мир |

Уровень 3.5 (**DMZ**) — это буферная зона, которая должна отделять IT от OT. На практике её часто нет, и корпоративная сеть напрямую видит контроллеры.

## Шаг 3: смотрим на протоколы OT

Каждый уровень общается своими протоколами:

| Протокол | Порт | Особенность |
|----------|------|-------------|
| Modbus TCP | 502 | без аутентификации |
| DNP3 | 20000 | «защищённый» режим редко включён |
| S7comm | 102 | проприетарный, Siemens |
| EtherNet/IP | 44818 | Rockwell |
| IEC 104 | 2404 | энергетика |
| OPC UA | 4840 | современный, с шифрованием |

Подавляющее большинство legacy-протоколов **не имеют аутентификации**: кто угодно в сети может читать и записывать значения.

## Шаг 4: строим карту векторов атак

Теперь, зная компоненты и уровни, перечислим, откуда можно атаковать:

- **Прямой доступ к ПЛК.** Чтение/запись регистров по Modbus/DNP3 — мы это уже умеем.
- **Изменение логики.** Перепрошивка ПЛК через инженерную станцию или сеть.
- **Спуфинг датчиков.** Подмена показаний, чтобы оператор принял неверное решение.
- **DoS на шину.** Забить сеть, вызвать срабатывание защиты и останов.
- **Компрометация HMI.** Через уязвимости Windows или веб-интерфейса панели.
- **Прыжок IT→OT.** Через плохо сегментированные сети и общие учётные записи.

Атака обычно идёт сверху вниз: скомпрометировав корпоративную сеть (уровень 4), атакующий ищет незащищённый мост в OT.

## Шаг 5: цель №1 — инженерная станция

Среди всех компонентов самый лакомый — инженерная станция. Именно с неё **перепрошивают ПЛК** и меняют логику. Захват станции равносилен полному контролю над процессом. Типовые слабости:

- старые операционные системы (Windows XP/7) без патчей;
- общие учётки и пароли на несколько станций;
- отсутствие многофакторной аутентификации и сегментации;
- файлы проектов логики без защиты — их можно похитить и изменить.

Поэтому в оценке OT проверяют не только контроллеры, но и станции: как к ним попадают, какие учётки используются, есть ли изоляция.

## Шаг 6: защита строится на сегментации

Главная мера защиты OT — правильная сегментация. Уровень DMZ (3.5) должен пропускать между IT и OT только нужные данные и, где возможно, в одну сторону:

```
IT (4)  --[firewall]-->  DMZ (3.5)  --[firewall]-->  OT (0-3)
```

Частые ошибки: прямой доступ из корпоративной сети к ПЛК, общие учётки, RDP из IT в OT, отсутствие логирования. Для пентестера это первые точки входа, а для защитника — первое, что нужно закрыть. Рамки этой работы описаны стандартами **IEC 62443** и **NIST SP 800-82**, и находки удобно формулировать в их терминах.

## Что мы теперь знаем

По-простому:

1. АСУ ТП состоит из ПЛК, RTU, HMI, SCADA-сервера, historian и инженерных станций.
2. Модель Purdue раскладывает их по уровням 0–5; DMZ (3.5) отделяет IT от OT.
3. Протоколы OT (Modbus, DNP3, S7) обычно без аутентификации.
4. Атака идёт сверху вниз, из IT в OT, через слабо сегментированные мосты.
5. Инженерная станция — самая ценная цель: с неё меняют логику ПЛК.

## На что смотреть дальше

- **Запись в регистр «на пробу».** Может открыть клапан или остановить насос — только стенд.
- **Неверный адрес регистра.** Чтение не той ячейки даёт ложную картину.
- **Путаница unit ID.** За одним шлюзом может быть несколько устройств.
- **Активное сканирование.** Может уронить legacy-ПЛК — начинайте пассивно.
- **Игнорирование таймингов.** OT-сети чувствительны к задержкам.
- **За одним IP — несколько устройств.** Уточняйте unit ID и не путайте ответы разных ПЛК.

## Как это выглядит целиком

Маршрут в одну историю: пассивно с зеркала трафика собираем карту — ПЛК отвечает на Modbus, historian тянет данные, HMI шлёт команды. Раскладываем по Purdue: 0 — датчики, 1 — ПЛК, 2 — SCADA, 3 — historian. Ищем мост IT→OT: если DMZ нет, корпоративная сеть видит контроллеры напрямую. Самая ценная цель — инженерная станция на старом Windows без патчей: с неё меняют логику ПЛК. Отчёт — сегментация, изоляция, логирование в терминах IEC 62443.
