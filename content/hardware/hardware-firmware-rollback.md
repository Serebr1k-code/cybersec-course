Вы нашли уязвимость в старой версии прошивки и хотите залить её на устройство, чтобы получить доступ. Но устройство отказывается: «rollback detected». Это anti-rollback — механизм, который запрещает загрузку прошивки ниже минимально допустимой версии. Он превращает «нашёл старую уязвимость» в бесполезное открытие, и понимание его работы экономит дни работы.

## Теория: verified boot и цепочка доверия

**Verified boot** — это проверка подписи каждого этапа загрузки:

1. BootROM проверяет подпись первого загрузчика по ключу, зашитому в e-fuse/ROM.
2. Первый загрузчик проверяет подпись следующего этапа.
3. И так далее до ядра и, в Android, до системного раздела.

Если подпись не сходится — загрузка останавливается или уходит в recovery. В Android это **Android Verified Boot (AVB)** с метаданными `vbmeta`, содержащими хэши разделов и подпись.

**Anti-rollback** — дополнительный слой поверх verified boot. Он хранит **минимальную допустимую версию** (rollback index) в защищённом месте: в e-fuse, в TPM или в аппаратном хранилище. При загрузке текущий rollback index прошивки сравнивается с сохранённым: если он меньше — загрузка блокируется.

## Anti-rollback и счётчики версий

Механика проста, но необратима:

| Компонент | Роль |
|-----------|------|
| Rollback index (в прошивке) | версия данного образа |
| Stored rollback index (в fuse/TPM) | минимально разрешённая версия |
| При загрузке | если index < stored → отказ |
| При обновлении | stored обновляется вверх, обратно — нельзя |

Как только устройство обновилось до версии N, откат на N-1 запрещён навсегда: stored index в e-fuse уже равен N. Даже полный дамп старой прошивки не поможет — проверка идёт до запуска кода.

В Android rollback index хранится в `vbmeta` и в **tamper-evident storage**; в устройствах с TPM — в TPM NV-памяти, защищённой от сброса. В embedded-устройствах часто используют e-fuse-биты, где каждый «сожжённый» бит поднимает минимальную версию.

## Как устроен rollback в Android/AVB

В Android:

- `vbmeta` содержит `rollback_index` для каждого раздела и подпись.
- Загрузчик (ABL/XBL) проверяет подпись `vbmeta` по ключу.
- Сравнивает `rollback_index` с сохранённым в RPMB/fuse.
- При несовпадении — блокирует и пишет событие в лог.

**RPMB (Replay Protected Memory Block)** — защищённая область eMMC/UFS, доступ к которой требует ключа и счётчика. Она защищена от повторного проигрывания: даже с полным дампом вы не подделаете запись в RPMB без ключа.

## Инструменты и команды

- **`avbtool`** — чтение и проверка `vbmeta`, извлечение rollback index.
- **`fastboot`** — `fastboot getvar all` показывает анти-роллбэк-переменные; `flash vbmeta` — для отладочных устройств.
- **`adb`/`dmesg`** — логи загрузки с сообщениями о rollback.
- **`binwalk`** — поиск `vbmeta` и метаданных в образе.
- **`unpackbootimg`** — разбор boot/recovery образов.
- **`efivarfs`** (UEFI) — переменные secure boot и rollback.
- **`tpm2-tools`** — чтение NV-индексов TPM.

```bash
# Читать vbmeta и увидеть rollback index
avbtool info_image --image vbmeta.img
# Проверить переменные устройства (отладочный режим)
fastboot getvar all 2>&1 | grep -i rollback
# Разбор образа
binwalk -e firmware.img
```

## Разобранный пример: попытка откатить прошивку

Допустим, вы нашли RCE в старой прошивке и пытаетесь её залить.

1. **Сбор данных.** Смотрим текущую версию и rollback index.

```text
$ avbtool info_image --image vbmeta.img
Rollback Index: 3
```

2. **Попытка прошивки старого образа (rollback index 1).** Загрузчик сравнивает: 1 < 3 → отказ.

```text
$ fastboot flash system system_old.img
FAILED (remote: 'rollback index 1 < stored 3')
```

3. **Попытка прошить vbmeta с меньшим index.** Подпись `vbmeta` не сойдётся (ключ в fuse), либо проверка stored index всё равно отклонит.
4. **Вывод.** Пока stored index = 3, путь через откат закрыт. Остаётся либо уязвимость в **текущей** версии, либо физический обход (glitch при сравнении).

```text
# На отладочном устройстве (userdebug) можно отключить проверку:
$ fastboot flashing unlock
$ fastboot --disable-verity --disable-verification flash vbmeta vbmeta.img
# На production — нельзя.
```

## Обход anti-rollback

Возможные пути (все — сложные):

- **Fault injection.** Глитч в момент сравнения index может «пропустить» проверку. Требует точного тайминга и оборудования.
- **Уязвимость в загрузчике.** Ошибка в парсере `vbmeta` или в логике сравнения — редкая, но самая «чистая» атака.
- **Сброс stored index.** Если он в e-fuse — невозможно; если в перезаписываемой памяти с багом — иногда да.
- **Downgrade через официальный путь.** Некоторые производители разрешают откат по политике — это легальный «обход».
- **Эксплуатация текущей версии.** Практичный путь: искать баг в актуальной прошивке, а не бороться с rollback.

## Устройство RPMB и tamper-evident storage

**RPMB (Replay Protected Memory Block)** — защищённая область в eMMC/UFS, доступ к которой требует аутентификации по ключу (обычно 256-битному) и монотонного счётчика записи. Каждая запись подписывается MAC, а в ответе устройства есть счётчик, который хост обязан проверять. Благодаря этому нельзя «отмотать» состояние: даже имея полный дамп eMMC, вы не сможете корректно перезаписать RPMB, не зная ключ. Именно в RPMB многие загрузчики хранят stored rollback index, состояние verified boot и anti-rollback счётчики.

Помимо RPMB, используются **e-fuse (OTP)**: однократно программируемые биты, которые физически нельзя вернуть в исходное состояние. Каждый «сожжённый» бит поднимает минимальную версию, и это необратимо. В устройствах с TPM stored index живёт в **NV-памяти**, защищённой политиками и, опционально, привязанной к PCR. Tamper-evident storage означает, что любая попытка отката состояния будет обнаружена — либо по MAC, либо по несоответствию счётчика.

Практический вывод для атакующего: если rollback index в RPMB/e-fuse/TPM, то подделка невозможна без ключа или физического вмешательства. Единственные реальные пути — глитч в момент сравнения или баг в парсере, читающем vbmeta. Проверка: `tpm2_nvread` для TPM NV-индексов, `mmc extcsd read /dev/mmcblk0` для RPMB-параметров, `fastboot getvar all` для anti-rollback переменных.

## Политики OTA и управление версиями

Anti-rollback — часть более широкой политики обновлений. Производитель задаёт: минимальную версию, разрешённые ключи, порядок применения разделов, поведение при сбое (A/B-слоты). В Android это **A/B OTA** с метаданными и пост-установочной верификацией; в embedded — цепочка образов с версиями.

Слабые места политики, которые ищет пентестер: **отладочные образы** с выключенным anti-rollback (userdebug/eng), которые часто попадают в утечки прошивок; **неполная проверка**, когда подписан boot, но не подписан recovery или vbmeta отладочным ключом; **официальный downgrade**, который некоторые вендоры разрешают по запросу (легальный обход); **смешение ключей**, когда старые устройства с отладочным ключом не отозваны после релиза; **OTA-канал** — если обновление принимается по HTTPS без проверки подписи пакета, можно подсунуть свой образ.

Защита строится на: монотонном rollback index в RPMB/e-fuse, подписи всех образов одним корневым ключом, отзыве отладочных ключей, обязательной пост-установочной верификации и запрете откатов на production. При аудите важно понять, где именно хранится stored index и как он обновляется — это определяет, реализуема ли атака.

## Частые ошибки и подводные камни

- **Ставка на откат.** Если rollback index поднят, старый образ бесполезен — не тратьте время.
- **Попытка прошить vbmeta.** На production-устройстве подпись не сойдётся.
- **Путаница unlock и rollback.** `fastboot flashing unlock` открывает прошивку, но не сбрасывает anti-rollback.
- **Неверная интерпретация логов.** «Rollback detected» может означать и несовпадение подписи, и anti-rollback — читайте точное сообщение.
- **Забыли про RPMB.** Подделка RPMB невозможна без ключа — не рассчитывайте на неё.

## Что дальше / решение

Если rollback закрыт, направьте усилия на анализ **актуальной** прошивки: сетевые сервисы, OTA-обновление, парсеры. Если нужен именно обход — переходите к fault injection (`hardware-fault-injection`) для глитча проверки. Для устройств с TPM — `hardware-tpm-deep`. И всегда проверяйте политику производителя: иногда официальный откат разрешён, и это самый простой путь.

## Разбор vbmeta: структура и команды

`vbmeta` — это метаданные Android Verified Boot. Внутри: дескрипторы разделов (хэши или hashtree), флаг `flags` (например, `HASHTREE_DISABLED`), rollback index и подпись. Разбирать удобнее всего `avbtool`.

```bash
# Полная информация об образе
avbtool info_image --image vbmeta.img
# Показать конкретный дескриптор
avbtool info_image --image vbmeta.img --key_name
# Извлечь публичный ключ, которым подписан образ
avbtool extract_public_key --key blobs/pubkey.bin
```

Пример вывода:

```text
Minimum libavb version:   1.0
Header Block:             256 bytes
Authentication Block:     576 bytes
Auxiliary Block:          1600 bytes
Algorithm:                SHA256_RSA2048
Rollback Index:           3
Flags:                    0
Rollback Index Location:  0
Descriptors:
    Hashtree descriptor:
      Partition Name:      system
      Image Size:          1073741824
      Root Digest:         a1b2c3...
      Hash Algorithm:      sha256
```

Обратите внимание на `Rollback Index` и `Rollback Index Location` — именно эти поля сравниваются с защищённым хранилищем.

## RPMB: почему запись нельзя подделать

RPMB (Replay Protected Memory Block) — область внутри eMMC/UFS для защищённых данных. Доступ к ней требует:

- **аутентификации ключом** (HMAC-SHA256), который знает только SoC и чип;
- **монотонного счётчика записи**, который увеличивается при каждой записи.

Механика: хост формирует кадр с данными, считает HMAC по ключу и передаёт в RPMB. Чип проверяет HMAC и счётчик; при несовпадении — отказ. Даже имея полный дамп RPMB, вы не подделаете запись: без ключа HMAC не сойдётся, а счётчик не даст «проиграть» старую запись заново. Поэтому rollback index, хранимый в RPMB, устойчив к откату через подмену дампа.

## UEFI Secure Boot и anti-rollback: dbx и SBAT

В мире ПК аналог anti-rollback — списки отзыва и **SBAT** (Secure Boot Advanced Targeting).

- **db/dbx** — базы ключей и отозванных хэшей/сертификатов в UEFI-переменных. Отозванный загрузчик больше не запустится.
- **SBAT** — механизм версионирования компонентов загрузки: если версия ниже минимальной, загрузка блокируется. Это защита от отката на уязвимый shim/GRUB.

```bash
# Просмотр UEFI-переменных
efi-readvar -v dbx
# Проверка SBAT-уровня
mokutil --list-sbat-revocations
```

Типичная проблема: производитель забыл обновить dbx или SBAT, и старая уязвимая версия снова загружается. Это и есть «anti-rollback bypass» — не сломанная криптография, а пропущенное обновление политики.

## Хранилища rollback index по платформам

| Платформа | Где хранится index | Защита |
|-----------|--------------------|--------|
| Android/AVB | vbmeta + RPMB/fuse | подпись + RPMB |
| UEFI PC | TPM NV / SBAT | TPM, dbx |
| Embedded (SoC) | e-fuse | необратимость |
| Apple | SEP + fuse | аппаратная привязка |
| ChromeOS | TPM | verified boot + TPM |

Общий принцип один: хранилище должно быть **монотонным** и **защищённым от записи обычной ОС**. Как только индекс попадает в перезаписываемую память без защиты, anti-rollback превращается в рекомендацию.

## Практика: анализ образа на anti-rollback

Разберём, как найти и оценить механизм в прошивке.

```bash
# 1. Извлечь разделы из образа
binwalk -e firmware.img
# 2. Найти vbmeta
find _firmware.img.extracted -name 'vbmeta*'
# 3. Проверить каждый
avbtool info_image --image vbmeta.img | grep -i rollback
# Rollback Index: 5
# Rollback Index Location: 0
# 4. Посмотреть, как загрузчик реагирует на несовпадение
strings abl.elf | grep -i "rollback"
# "rollback index %u < stored %u"
```

Строки в загрузчике (ABL/XBL) часто прямо сообщают формат сравнения — это подсказка, где искать уязвимость (например, целочисленное переполнение при сравнении).

## Известные обходы: SBAT bypass и downgrade-уязвимости

Исторические примеры показывают, что anti-rollback ломается на уровне логики, а не криптографии:

- **SBAT bypass.** Если компонент не объявляет SBAT-версию, политика не применяется — старый загрузчик проходит.
- **Downgrade через recovery.** Некоторые recovery-образы не проверяют rollback index и позволяют загрузить старую систему.
- **Отладочные сборки.** На `userdebug` проверки часто отключаются — production и debug ведут себя по-разному.
- **Целочисленные ошибки.** Сравнение индексов как беззнаковых/знаковых чисел может дать обход при больших значениях.

Вывод: перед отказом от пути «через откат» проверьте, не забыл ли производитель обновить политику — это дешевле, чем fault injection.

## Чеклист пентестера по anti-rollback

1. Определите версию текущей прошивки и rollback index (`avbtool`, `fastboot getvar`).
2. Выясните, где хранится индекс (fuse, RPMB, TPM) — от этого зависит возможность сброса.
3. Проверьте политику производителя: разрешён ли официальный откат.
4. Поищите уязвимость в логике сравнения (строки в загрузчике, SBAT, recovery).
5. Если откат закрыт — переключитесь на анализ **актуальной** версии.
6. Только в последнюю очередь — физические методы (glitch сравнения).
