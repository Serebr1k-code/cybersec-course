## Вопрос, с которого всё начинается

Ты нашёл уязвимость в старой версии прошивки устройства и хочешь залить её обратно, чтобы получить доступ. Но устройство отказывается загружаться: «rollback detected». Казалось бы, вот же уязвимый код — почему он не работает?

Ответ — в механизме **anti-rollback**, который запрещает загрузку прошивки ниже минимально допустимой версии. Понимание его работы экономит дни бесполезных попыток.

## Наш пример: попытка откатить прошивку

Возьмём Android-устройство с проверкой подписи. Мы нашли RCE в старой сборке (rollback index 1) и пытаемся её прошить. Разберём по шагам, что происходит.

## Шаг 1: verified boot — цепочка доверия

Сначала поймём, что проверяется. **Verified boot** — это проверка подписи на каждом этапе загрузки:

1. BootROM проверяет подпись первого загрузчика по ключу, зашитому в e-fuse или ROM.
2. Первый загрузчик проверяет подпись следующего этапа.
3. И так далее — до ядра и системного раздела.

Если подпись не сходится, загрузка останавливается. В Android это **Android Verified Boot (AVB)**, где метаданные `vbmeta` содержат хэши разделов и подпись.

## Шаг 2: anti-rollback — слой поверх

**Anti-rollback** — дополнительная защита поверх verified boot. Он хранит **минимально допустимую версию** (rollback index) в защищённом месте: в e-fuse, в TPM или в RPMB. При загрузке текущий индекс прошивки сравнивается с сохранённым: если он меньше — загрузка блокируется.

| Компонент | Роль |
|-----------|------|
| Rollback index (в прошивке) | версия данного образа |
| Stored index (в fuse/TPM/RPMB) | минимально разрешённая версия |
| При загрузке | если index < stored → отказ |
| При обновлении | stored обновляется вверх, обратно нельзя |

Механика необратима: как только устройство обновилось до версии N, откат на N-1 запрещён навсегда — stored index уже равен N. Даже полный дамп старой прошивки не поможет, потому что проверка идёт **до** запуска кода.

## Шаг 3: смотрим rollback index

Разберём образ утилитой `avbtool`:

```
$ avbtool info_image --image vbmeta.img
Algorithm:                SHA256_RSA2048
Rollback Index:           3
Rollback Index Location:  0
```

`Rollback Index: 3` — версия текущего образа, а `Location` говорит, с каким защищённым хранилищем его сравнивать. Теперь мы знаем, какой порог нужно преодолеть.

## Шаг 4: пробуем прошить старый образ

Пытаемся залить прошивку с индексом 1:

```
$ fastboot flash system system_old.img
FAILED (remote: 'rollback index 1 < stored 3')
```

Загрузчик сравнил: `1 < 3` — отказ. Именно это сообщение и называют «rollback detected». Прямой путь через откат закрыт.

## Шаг 5: почему подделать индекс не выходит

Казалось бы, можно прошить свой `vbmeta` с меньшим индексом. Но не выйдет:

- подпись `vbmeta` не сойдётся — ключ лежит в e-fuse;
- даже с валидной подписью проверка сравнит stored index и отклонит образ.

В Android rollback index хранится в `vbmeta` и в **tamper-evident storage**. На устройствах с TPM — в NV-памяти, защищённой от сброса. В embedded-устройствах часто используют биты e-fuse, где каждый «сожжённый» бит поднимает минимальную версию необратимо.

## Шаг 6: RPMB — почему запись нельзя подделать

Многие загрузчики держат stored index в **RPMB** (Replay Protected Memory Block) — защищённой области eMMC/UFS. Доступ к ней требует:

- **аутентификации ключом** (HMAC-SHA256), который знают только SoC и чип;
- **монотонного счётчика записи**, растущего при каждой записи.

Даже имея полный дамп eMMC, вы не подделаете запись в RPMB: без ключа HMAC не сойдётся, а счётчик не даст «проиграть» старую запись заново. Проверить параметры RPMB можно через `mmc extcsd read /dev/mmcblk0`.

## Шаг 7: UEFI и SBAT — тот же принцип на ПК

В мире ПК аналог anti-rollback — списки отзыва и **SBAT** (Secure Boot Advanced Targeting). **db/dbx** — базы ключей и отозванных хэшей в UEFI-переменных; отозванный загрузчик больше не запустится. **SBAT** — версионирование компонентов загрузки: если версия ниже минимальной, загрузка блокируется. Проверяются они так:

```
$ efi-readvar -v dbx
$ mokutil --list-sbat-revocations
```

## Практика: как найти anti-rollback в образе

Разберём, как оценить механизм в конкретной прошивке:

```
$ binwalk -e firmware.img
$ find _firmware.img.extracted -name 'vbmeta*'
$ avbtool info_image --image vbmeta.img | grep -i rollback
Rollback Index: 5
Rollback Index Location: 0
$ strings abl.elf | grep -i rollback
"rollback index %u < stored %u"
```

Строки в загрузчике (ABL/XBL) часто прямо сообщают формат сравнения — это подсказка, где искать уязвимость. Например, сравнение индексов как знаковых чисел может дать обход при больших значениях.

## Хранилища rollback index по платформам

| Платформа | Где хранится index | Защита |
|-----------|--------------------|--------|
| Android/AVB | vbmeta + RPMB/fuse | подпись и RPMB |
| UEFI PC | TPM NV / SBAT | TPM, dbx |
| Embedded (SoC) | e-fuse | необратимость |
| ChromeOS | TPM | verified boot + TPM |

Общий принцип один: хранилище должно быть **монотонным** и **защищённым от записи** обычной ОС. Как только индекс попадает в перезаписываемую память без защиты, anti-rollback превращается в рекомендацию.

## Слабые места политики обновлений

Anti-rollback ломается чаще на уровне логики, чем криптографии, и пентестеру стоит проверять именно эти места:

- **Отладочные образы** (`userdebug`/`eng`) с выключенным anti-rollback, которые утекают вместе с прошивками.
- **Неполная проверка** — подписан boot, но не подписан recovery или vbmeta отладочным ключом.
- **Официальный downgrade** — некоторые вендоры разрешают откат по запросу, и это легальный обход.
- **SBAT bypass** — если компонент не объявляет SBAT-версию, политика к нему не применяется.
- **OTA-канал** — если пакет принимается по HTTPS без проверки подписи, можно подсунуть свой образ.

Вывод: перед отказом от пути «через откат» проверьте, не забыл ли производитель обновить политику — это дешевле, чем fault injection.

## Если не сработало

- **Ставка на откат.** Если rollback index поднят, старый образ бесполезен — не тратьте время.
- **Попытка прошить свой vbmeta.** На production-устройстве подпись не сойдётся.
- **Путаница unlock и rollback.** `fastboot flashing unlock` открывает прошивку, но **не** сбрасывает anti-rollback.
- **Неверная интерпретация логов.** «Rollback detected» может означать и несовпадение подписи, и anti-rollback — читайте точное сообщение.
- **Забыли про RPMB.** Подделка RPMB невозможна без ключа.

## Что мы теперь знаем

1. Verified boot проверяет подпись на каждом этапе загрузки.
2. Anti-rollback хранит минимально допустимую версию в fuse/TPM/RPMB.
3. Откат невозможен после обновления: stored index необратимо поднят.
4. Подделать RPMB или e-fuse без ключа нельзя.
5. Практичный путь при закрытом откате — искать баг в **актуальной** прошивке.

## Куда дальше

Мы поняли, почему старые уязвимые версии бесполезны. Остаётся один физический путь — «сломать» саму проверку в момент её выполнения. Об этом в следующем уроке про лазерную инъекцию ошибок. А пока запомни главное: anti-rollback — это не криптография, а монотонный счётчик, и обойти его программно нельзя.
