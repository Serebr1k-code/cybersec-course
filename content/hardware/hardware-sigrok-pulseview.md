## Вопрос, с которого всё начинается

На плате между микроконтроллером и периферийным чипом идут две дорожки. Что это за шина — UART, I2C, что-то проприетарное? Документации нет, отладочный интерфейс закрыт. Как узнать, о чём чипы переговариваются по этим проводам?

Ответ — подключить **логический анализатор** и декодировать сигналы. Разберём, как это делается с помощью открытого фреймворка **sigrok** и его графической оболочки **PulseView**.

## Наш пример: две неизвестные дорожки

Наша цель — превратить сырые импульсы на двух линиях в читаемые байты. Инструмент — дешёвый USB-анализатор на 8 каналов (например, Saleae-клон). sigrok состоит из нескольких частей: **libsigrok** (ядро и драйверы), **libsigrokdecode** (движок декодеров на Python), **sigrok-cli** (консоль) и **PulseView** (графический интерфейс).

## Шаг 1: подключаемся и проверяем устройство

Припаиваем щупы `D0` и `D1` к дорожкам, а землю анализатора — к земле платы. Затем убеждаемся, что анализатор виден:

```
$ sigrok-cli --scan
fx2lafw:conn=3.12 - FX2 LA (8 channels)
```

`sigrok-cli --scan` перечисляет подключённые устройства. Мы видим FX2-клон на 8 каналов. Забегая вперёд: **земля обязательна** — без общей земли сигналы «плывут» и декодеры выдают мусор.

## Шаг 2: грубая оценка активности

Сначала непонятно даже, как часто переключаются линии. Ставим высокую частоту дискретизации и короткий захват:

```
$ sigrok-cli --driver fx2lafw --config samplerate=24m --time 0.5s \
    --channels D0,D1 -o unknown.sr
```

`--config samplerate=24m` — 24 МГц, `--time 0.5s` — полсекунды, `-o unknown.sr` — сохранить в файл. Теперь у нас есть сырые данные, которые можно разбирать офлайн, многократно, без риска снова дёргать живую шину. На этом шаге важно просто понять, переключаются ли линии вообще: если обе неподвижны, возможно, обмена в этот момент нет и нужен триггер.

## Шаг 3: гипотеза UART

Смотрим на линии: если одна «молчит», а другая меняется, это похоже на **UART**, где активна только линия передачи. Пробуем декодер с разными скоростями:

```
$ sigrok-cli -i unknown.sr -P uart:rx=D1:baudrate=9600
$ sigrok-cli -i unknown.sr -P uart:rx=D1:baudrate=115200
uart-1: 01 03 00 00 00 0A C5 CD
```

Опция `-P uart:rx=D1:baudrate=115200` накладывает декодер UART на канал `D1` со скоростью 115200. Когда скорость угадана, сырые импульсы превращаются в байты: `01 03 00 00 00 0A C5 CD`. Если скорость неверна, декодер выдаст мусор или ничего.

## Шаг 4: гипотеза I2C

Другой сценарий: на одной линии виден частый такт, а на другой — редкие изменения. Это может быть **I2C**, где такт идёт по линии SCL, а данные — по SDA:

```
$ sigrok-cli -i unknown.sr -P i2c:scl=D0:sda=D1
i2c-1: Start, Address write 0x48, Data write 0x01, Stop
```

Декодер не только восстановил байты, но и разобрал структуру: старт, адрес устройства `0x48`, данные, стоп. Теперь понятно, что на шине сидит I2C-периферия с адресом `0x48`.

## Шаг 5: строим стек декодеров

Декодеры можно соединять в **стек**: один питается от выхода другого. Например, `SPI` → `SD card` → `FAT` — так от сырых импульсов доходят до имён файлов. Полезные декодеры sigrok: `uart`, `spi`, `i2c`, `onewire_link`, `can`, `jtag`, `swd`, `usb_power_delivery`, `sdcard_spi`, `modbus`. Список всех доступных — `sigrok-cli -L`. Декодеры пишутся на Python, поэтому сообщество постоянно добавляет новые — от USB Power Delivery до DMX512.

## Шаг 6: триггеры для редких событий

Иногда нужное событие случается раз в минуту (команда прошивки при загрузке). Тогда захват запускают **триггером** по фронту или уровню:

```
$ sigrok-cli --driver fx2lafw --config samplerate=4m \
    --config trig=D0=r --time 2s -o trig.sr
```

`trig=D0=r` — запуск по нарастающему фронту на канале `D0`. В PulseView триггер настраивается в разделе Trigger визуально. Для отладки загрузки триггер на сброс (NRST) ловит самое начало инициализации.

## Продвинутый анализ и автоматизация

PulseView удобен для ручного разбора, но при массовой работе выручает `sigrok-cli` и скрипты. Декодированные данные можно экспортировать в JSON для дальнейшего анализа:

```
$ sigrok-cli -L | grep -i -E "uart|spi|i2c|can|swd"
$ sigrok-cli -i capture.sr -P uart:rx=D0:baudrate=115200 -A uart=data -o out.json
```

Первая команда показывает, какие декодеры установлены, вторая сохраняет расшифрованные байты в JSON. Для самодельных анализаторов на Raspberry Pi Pico есть прошивка sigrok, дающая десятки каналов на высокой частоте — отличное соотношение цены и возможностей. Если нужного декодера нет, его несложно написать на Python в libsigrokdecode, описав переходы состояний.

## Анализ протоколов «с нуля»

Часто шина оказывается не стандартной, а проприетарной. Тогда стратегия такая: сначала определить тип кодирования (синхронная или асинхронная, есть ли отдельный такт, какая полярность), затем найти границы кадров по повторяющемуся паттерну, после — выделить поля (адрес, команда, данные, CRC). Логический анализатор даёт точные тайминги, по которым вычисляются битовая скорость и порядок битов. Для шифрованных шин дополнительно снимают трафик при разных входных воздействиях и сопоставляют изменения — так становится понятно, какие поля чем управляют.

Особый интерес для пентеста представляют **скрытые сервисные интерфейсы**: отладочный UART, не выведенный на разъём, но живой на площадках; SPI-шина к внешней флеш-памяти; I2C к EEPROM с секретами. Захват этих шин анализатором часто даёт больше, чем попытки подключиться к «закрытому» JTAG.

## Если не сработало

- **Слишком низкая частота.** UART 115200 требует минимум 1 МГц, I2C 400 кГц — от 4 МГц. Правило: частота дискретизации ≥ 4–10x скорости шины.
- **Кончилась память.** У FX2-клонов буфер мал; уменьшайте время захвата или число каналов.
- **Нет земли.** Без GND сигналы плывут и декодеры дают мусор — подключайте землю всегда.
- **Инвертированный UART.** SBUS и подобные интерфейсы инвертированы; декодеру нужна опция `invert`.
- **Декодер молчит.** Пробуйте другие параметры: полярность, порядок битов, размер слова.

## Что мы теперь знаем

1. Логический анализатор превращает импульсы в байты; sigrok + PulseView — открытый стек. Сам анализатор лишь записывает уровни, всю работу по смыслу делают декодеры.
2. Земля обязательна, а частота дискретизации должна быть в 4–10 раз выше скорости шины, иначе фронты «размажутся» и декодер ошибётся.
3. Декодеры накладываются на каналы одной командой, например `-P uart:rx=D1:baudrate=115200`.
4. Декодеры строятся в стек: от физического уровня до прикладного.
5. Триггер запускает захват по событию, чтобы не писать часы пустого трафика и не терять память анализатора.
