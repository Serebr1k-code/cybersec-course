Когда UART закрыт (пароль, отсутствие shell, только лог), следующим шагом идёт аппаратная отладка. JTAG и SWD дают доступ к ядру процессора: можно остановить его, прочитать и изменить память, снять дамп прошивки и обойти защиту от чтения. Это самый мощный интерфейс, и часто он оставлен включённым.

## Теория

**JTAG (IEEE 1149.1)** — стандартный интерфейс граничного сканирования (boundary scan) и отладки. Минимум сигналов:

| Сигнал | Назначение |
|--------|-----------|
| **TDI** | Test Data In — данные в цепочку |
| **TDO** | Test Data Out — данные из цепочки |
| **TCK** | Test Clock — такт |
| **TMS** | Test Mode Select — управление состоянием |
| TRST | Test Reset (опционально) |

JTAG поддерживает цепочку устройств (daisy chain), поэтому один порт может обслуживать несколько чипов. Через JTAG можно делать boundary scan — «пощупать» любой пин чипа, не имея его распиновки.

**SWD (Serial Wire Debug)** — двухпроводный протокол отладки ARM (используется на Cortex-M/A):

| Сигнал | Назначение |
|--------|-----------|
| **SWDIO** | данные |
| **SWCLK** | такт |
| SWO | trace (опционально) |

SWD проще, чем JTAG, и почти на всех ARM-чипах есть. Для ARM-плат начинайте с SWD.

**IDCODE** — JTAG-устройство отдаёт 32-битный идентификатор при сбросе. По IDCODE определяют модель SoC и, соответственно, как с ним работать.

**Readout protection (RDP / flash lock)** — бит защиты, запрещающий чтение памяти через отладчик. Иногда его можно снять (массовое стирание), иногда он защищён fuse-битами, которые пережигаются навсегда.

**Boundary scan** — режим, при котором через JTAG можно управлять любым пином чипа и читать его состояние. Полезно, когда распиновка неизвестна: можно «прозвонить» логику программно.

## Инструменты и команды

- **JTAGulator** — автоматический брутфорс пинов JTAG (или самодельный на Raspberry Pi Pico).
- **OpenOCD** — универсальный софт для JTAG/SWD, поддерживает сотни адаптеров.
- **J-Link** — быстрый коммерческий адаптер (есть клоны).
- **FT2232H / FT232H** — дешёвый адаптер, работает с OpenOCD.
- **Raspberry Pi** — GPIO можно использовать как JTAG-адаптер (OpenOCD config `raspberrypi-native`).
- **urJTAG** — альтернатива для boundary scan.
- **gdb-multiarch** — отладка через OpenOCD gdb-server.

```bash
# Установка
sudo apt install openocd gdb-multiarch urjtag

# Поиск цепочки JTAG (OpenOCD с адаптером FT2232)
openocd -f interface/ftdi/ft2232.cfg -f target/your_soc.cfg

# Пример: Raspberry Pi как JTAG-адаптер к ARM
openocd -f interface/raspberrypi-native.cfg -f target/stm32f1x.cfg

# urJTAG: определить IDCODE (пины уже известны)
jtag> cable ft2232
jtag> detect
```

## Полезные команды OpenOCD

| Команда | Назначение |
|---------|-----------|
| `init` | инициализировать адаптер и цель |
| `reset halt` | сброс и остановка ядра |
| `dap info` | информация о DAP (SWD) |
| `scan_chain` | список устройств JTAG (IDCODE) |
| `flash banks` | список флеш-банков цели |
| `dump_image fw.bin 0x08000000 0x100000` | снять дамп памяти |
| `program fw.bin 0x08000000` | записать прошивку |
| `adapter speed 1000` | скорость адаптера (кГц) |
| `mdw 0x08000000 16` | прочитать 16 слов памяти |

## Поиск JTAG/SWD на плате

1. **Ищите гребень.** Часто 10/14/20-контактные площадки рядом с SoC, иногда подписанные `JTAG`, `J1`, `DEBUG`.
2. **Поиск GND/VCC** мультиметром (как в `hardware-uart`).
3. **JTAGulator** — подключаете каналы к неизвестным пинам, устройство само перебирает комбинации TDI/TDO/TCK/TMS и сообщает найденные IDCODE. Это самый быстрый путь для незнакомой платы.
4. **Без JTAGulator** — определяете вручную: TCK обычно звонится с GND (мало, десятки Ом) или имеет характерный сигнал; TDI/TDO — высокоомные; TMS — подтянут к VCC.
5. **SWD** — ищите пары рядом, подписанные `SWDIO`/`SWCLK`, или `SWD`, `DIO`, `CLK`. Часто это 4 пина: VCC, SWDIO, SWCLK, GND.

## Разобранный пример: дамп прошивки через SWD

**Дано:** ARM-устройство, SWD-гребень из 4 пинов.

**Шаг 1 — подключение.**
```text
Адаптер 3.3V ── плата VCC (или питание платы отдельно)
Адаптер GND  ── плата GND
Адаптер SWDIO ── плата SWDIO
Адаптер SWCLK ── плата SWCLK
```

**Шаг 2 — определение цели.** Читаем IDCODE:
```bash
openocd -f interface/cmsis-dap.cfg -c "transport select swd" \
        -f target/unknown.cfg -c "init; dap info; shutdown"
```
Если модель известна, подставляем готовый target-конфиг. Иначе смотрим IDCODE и ищем SoC по базе.

**Шаг 3 — остановка ядра и чтение памяти.** Подключаемся через GDB:
```bash
# терминал 1
openocd -f interface/cmsis-dap.cfg -f target/stm32f4x.cfg

# терминал 2
gdb-multiarch -ex "target extended-remote :3333" \
  -ex "monitor reset halt" \
  -ex "monitor flash banks"
```

**Шаг 4 — снять дамп флеша:**
```bash
# В GDB или через OpenOCD
openocd -f interface/cmsis-dap.cfg -f target/stm32f4x.cfg \
  -c "init; reset halt; dump_image fw.bin 0x08000000 0x100000; shutdown"
```
Получаем `fw.bin` — прошивку целиком, которую дальше разбираем (`hardware-firmware-extract`).

**Шаг 5 — если включена readout protection.** OpenOCD сообщит об ошибке чтения или вернёт нули. Варианты: снять защиту (стирание чипа, теряя прошивку), использовать glitching (`hardware-sidechannel`), либо искать другой путь (SPI-дамп, UART).

## Разобранный пример: поиск JTAG на неизвестной плате

**Дано:** 14 непаяных площадок в два ряда рядом с SoC, документации нет.

**Шаг 1 — GND/VCC** мультиметром (см. `hardware-pcb-reversing`).

**Шаг 2 — JTAGulator:**
```text
JTAGulator> j
# Перебор каналов...
# IDCODE: 0x4BA00477 (ARM Cortex-M) on channels 2,4,6,8
```
JTAGulator сам находит TCK/TMS/TDI/TDO и отдаёт IDCODE.

**Шаг 3 — сопоставить IDCODE.** `0x4BA00477` — ARM Cortex-M (ARM DAP). Дальше ищем target-конфиг по SoC.

**Шаг 4 — подключиться OpenOCD** с найденными пинами и снять дамп.

**Шаг 5 — если JTAG не находится** — возможно, отладка отключена fuse-битами; переходите к SWD или SPI-дампу.

## Частые ошибки

- **Не тот адаптер/скорость.** OpenOCD может требовать `adapter speed 1000` или ниже для дешёвых адаптеров и длинных проводов.
- **Плата не в сбросе.** Некоторые цели требуют удерживать reset или снять его в определённый момент — используйте `monitor reset halt`.
- **Пины перепутаны.** Симптом: OpenOCD не видит IDCODE. Пробуйте переставить TDI/TDO, проверить TMS.
- **Питание от адаптера.** Не подавайте питание на VCC цели, если она уже запитывается — конфликт.
- **Readout protection.** Не думайте, что дамп «пустой» из-за ошибки — возможно, защита включена; проверьте регистр защиты.
- **Длинные провода.** JTAG на длинных неподключённых проводах работает нестабильно. Держите их короткими (<10 см).
- **Игнорирование общего GND.** Без общего провода адаптера и цели связь нестабильна или отсутствует.

## Boundary scan на практике

Boundary scan (IEEE 1149.1) позволяет через JTAG управлять любым пином чипа и читать его состояние, не имея распиновки. Это полезно для:

- **Проверки цепей.** Программно «прозвонить» дорожку между чипами: выставить выход одного, прочитать вход другого.
- **Чтения состояния пинов.** Понять, что подключено к неизвестным ногам.
- **Поиска интерфейсов.** Обнаружить, какие пины ведут к флеш/разъёмам.

```bash
# urJTAG: обнаружение цепочки и BS-регистров
jtag> cable ft2232
jtag> detect
jtag> bsdl path /usr/share/urjtag/bsdl
jtag> bsdl dump <IDCODE>
jtag> instruction SAMPLE/PRELOAD
jtag> shift ir
jtag> shift dr
jtag> get signal <PIN_NAME>
```

BSDL-файл (Boundary Scan Description Language) описывает, как пины чипа связаны с ячейками boundary scan. Он идёт от вендора; без него boundary scan не работает, но `detect` и IDCODE доступны всегда.

## Readout protection: варианты обхода

| Тип защиты | Поведение | Обход |
|-----------|-----------|-------|
| RDP level 1 | чтение запрещено, можно стереть | mass erase (теряя прошивку) |
| RDP level 2 | отладка отключена навсегда | glitching, chip-off |
| Flash lock (STM32) | flash не читается | glitch RDP, bootloader-атаки |
| Secure boot | подпись ядра | ключ подписи, glitching проверки |
| Debug disable fuse | JTAG отключён | SWD (если не отключён), glitch fuse |

**Практический порядок:** сначала пробуем SWD (часто не отключён), затем JTAG; при защите — glitching или альтернативные пути (SPI-дамп флеш, UART). Chip-off — крайняя мера: дорого, рискованно, требует оборудования.

## Дополнительные конфиги OpenOCD

Готовые target-конфиги лежат в `/usr/share/openocd/scripts/target/`. Если вашего SoC нет, используйте generic (`cortex_m.cfg`, `stm32f1x.cfg` как шаблон) и правьте размеры flash/RAM. Скорость адаптера подбирается экспериментально: начните с `adapter speed 1000` (кГц), снижайте при нестабильности. Для длинных проводов снижение скорости часто решает проблему «не видит IDCODE».

## Что дальше / решение

- **IDCODE найден** → подберите target-конфиг, остановите ядро, снимите дамп.
- **Дамп нулевой/ошибка чтения** → включена защита; glitching, chip-off или SPI-дамп.
- **OpenOCD не видит цель** → проверьте пины, скорость, reset, питание.
- **Нужно изменить память** → `monitor mww`/`program` (осторожно, есть риск «кирпича»).
- **Дамп есть** → `hardware-firmware-extract` для разбора.
- **Провал** → `record_vector attempted`, зафиксируйте IDCODE/симптом и переходите к SPI/UART.

## Справочные таблицы

**JTAG vs SWD:**

| Критерий | JTAG | SWD |
|----------|------|-----|
| Проводов | 4–5 | 2 (+GND, VCC) |
| Архитектуры | многие | ARM |
| Boundary scan | да | нет |
| Daisy chain | да | нет |
| Простота | ниже | выше |

**Типовые IDCODE (примеры):**

| IDCODE | Устройство |
|--------|-----------|
| 0x4BA00477 | ARM Cortex-M DAP |
| 0x0B73B02F | Xilinx Spartan |
| 0x020A50DD | STM32 (пример) |

**Состояния при проблемах:**

| Симптом | Причина | Решение |
|---------|---------|---------|
| Нет IDCODE | пины/скорость | перебрать пины, снизить speed |
| Нули при чтении | readout protection | glitch/chip-off/SPI |
| Нестабильно | длинные провода | укоротить, добавить GND |
