## Вопрос, с которого всё начинается

В доме стоят «умные» устройства: лампы и датчики на **Zigbee**, а дверной замок — на **Z-Wave**. Хозяин управляет ими с телефона. Вопрос: можно ли перехватить и повторить эти команды со стороны, не имея доступа к приложению?

Оба протокола шифруют трафик, и на первый взгляд перехватить их бесполезно. Но у обоих есть общая слабость — **момент спаривания** нового устройства с сетью. Разберём это на конкретной сети.

## Наш пример: Zigbee-сеть с новым датчиком

Возьмём Zigbee-сеть: есть **хаб** (в терминах Zigbee — координатор) и несколько устройств. Мы знаем, что хозяин как раз сейчас добавляет в сеть новый датчик движения — это и есть тот самый момент спаривания. Наша цель — вытащить из этого события сетевой ключ.

## Шаг 1: Zigbee или Z-Wave?

Прежде чем хвататься за инструменты, надо понять, с чем имеем дело. Это два разных стандарта:

| | Zigbee | Z-Wave |
|---|---|---|
| Частота | 2.4 ГГц (IEEE 802.15.4) | sub-GHz: 868 МГц (EU) / 908 МГц (US) |
| Каналы | 16 каналов | один канал на частоте |
| Шифрование | AES-CCM* с сетевым ключом | AES-128: устаревшее S0 и новое S2 |
| Сниффер | CC2531 / nRF52840 / ApiMote | Zniffer, sub-GHz-приёмник |

Zigbee живёт в перегруженном 2.4 ГГц рядом с Wi-Fi, поэтому у него 16 каналов и устройства умеют по ним «прыгать». Z-Wave работает на sub-GHz, где дальность выше, а эфир чище. Инструменты не взаимозаменяемы: для Zigbee нужен **802.15.4-трансивер**, для Z-Wave — **Zniffer** или sub-GHz-приёмник.

## Шаг 2: находим сеть — канал и PAN ID

Zigbee-сеть опознаётся парой: **PAN ID** (идентификатор сети) и канал. Найти её можно утилитой из набора **KillerBee** — инструментов для работы с 802.15.4:

```bash
$ zbid
Dev  Product            FW Ver  Role
0    CC2531            1.0     sniffer
$ zbstumbler
Searching for ZigBee networks...
PAN: 0x1a2b  Channel: 15  Ext PAN: 00:12:4b:00:...
```

`zbid` показал наш адаптер CC2531. `zbstumbler` прошёлся по каналам и нашёл сеть: PAN ID `0x1a2b` на канале 15. Если канал неизвестен, а устройства прыгают, сеть ищут параллельно по всем 16 каналам — иначе сниффер просто не увидит трафик.

## Шаг 3: записываем трафик

Теперь пишем эфир на найденном канале:

```bash
$ zbdump -c 15 -w zigbee.pcap
Capturing on channel 15 -> zigbee.pcap
```

`-c 15` — канал, `-w` — файл для записи. Полученный `zigbee.pcap` открывается в Wireshark, у которого есть готовый диссектор Zigbee (фильтр `wpan`). Пока трафик выглядит как шифротекст — ключа у нас ещё нет.

## Шаг 4: ищем момент спаривания

Ключ передаётся ровно один раз — когда новое устройство входит в сеть. В этот момент координатор (хаб) посылает устройству команду **Transport Key**: в ней лежит сетевой ключ. Найти её в Wireshark просто — по имени команды:

```
ZigBee Network Layer
  Command: Transport Key (0x05)
  Key Type: Network Key (0x01)
  Key: <encrypted>
```

Важно успеть записать именно это окно: если датчик уже добавлен, сетевой ключ повторно никто не передаёт. Именно поэтому атака привязана к моменту джойна.

## Шаг 5: извлекаем сетевой ключ

Ключ в Transport Key зашифрован **TC link key** — ключом связи между устройством и доверенным центром (Trust Center). И вот главная проблема Zigbee: у многих сетей этот ключ оставлен **заводским по умолчанию**. Он одинаков для всех и равен строке `ZigBeeAlliance09`, то есть байтам:

```
5A 69 67 42 65 65 41 6C 6C 69 61 6E 63 65 30 39
```

Если сеть не сменила этот ключ, мы можем расшифровать Transport Key и вытащить сетевой ключ. Это и есть корень атаки: перехват джойна + дефолтный TC link key = полный доступ.

## Шаг 6: расшифровываем трафик

Вводим добытый сетевой ключ в Wireshark: *Preferences → Protocols → ZigBee → Pre-configured keys*. После этого весь захваченный и будущий трафик сети читается в открытом виде:

```
ZigBee Application Support Layer
  Command: On/Off
  Endpoint: 1
  Payload: ON
```

Теперь видны команды управления: что включается, какие состояния меняются, какие коды используются. С этим знанием можно эмулировать устройство и слать команды самому.

## Соседний протокол: Z-Wave и его S0/S2

С Z-Wave история похожая, но со своей деталью. Старое шифрование **S0** использует AES-128, однако при обмене ключами применяет **постоянное** значение (nonce), из-за чего ключ можно восстановить из перехваченного обмена. Из-за этого S0 считается скомпрометированным.

Современное **S2** использует обмен ключами по эллиптической криптографии (ECDH на Curve25519): подслушав обмен, ключ получить нельзя. Здесь перехват джойна не помогает — остаются другие пути: извлечение ключа из прошивки контроллера или компрометация облака производителя.

Практически Z-Wave снимают **Zniffer** (адаптер Silicon Labs) и разбирают в Wireshark: для S0 восстанавливают ключ из обмена, для S2 анализируют хотя бы метаданные (команды, топологию) без содержимого.

## Три уровня ключей Zigbee

Чтобы не запутаться, разложим ключи Zigbee по уровням:

- **Network key** — шифрует весь трафик сети. Один на всю сеть, и именно его мы добываем.
- **Link keys** — ключи связи между конкретными парами устройств.
- **TC link key** — ключ между устройством и Trust Center на время джойна; им зашифрован Transport Key.

Атака бьёт в слабое звено: если **TC link key** оставлен заводским, то Transport Key (а с ним и network key) расшифровывается. В новых сетях Zigbee 3.0 применяют **install code** — уникальный ключ устройства, передаваемый внеполосно (наклейка с QR-кодом). Тогда дефолтный ключ не используется, и перехват джойна сам по себе ключа не даёт — путь идёт через прошивку или облако производителя.

## Защита

- В Z-Wave переходить на **S2** и отказываться от S0.
- В Zigbee сменять заводской **TC link key** (install code / out-of-band).
- Включать шифрование и аутентификацию на всех устройствах.
- Обновлять прошивки контроллеров и хабов, мониторить аномальные джойны и replay.

## Что мы теперь знаем

- Zigbee и Z-Wave — разные стандарты: 2.4 ГГц против sub-GHz, разные снифферы.
- Ключ Zigbee передаётся **один раз**, при джойне нового устройства.
- Заводской TC link key (`ZigBeeAlliance09`) сводит защиту на нет.
- В Z-Wave устаревшее **S0** восстанавливается из перехвата, современное **S2** — нет.
- С сетевым ключом трафик читается целиком, вплоть до команд управления.
