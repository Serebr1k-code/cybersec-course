**NFC (Near Field Communication)** — это набор стандартов для связи на расстоянии до нескольких сантиметров (13.56 МГц). Технически NFC — надмножество ISO 14443 (бесконтактные карты) и ISO 18092 (peer-to-peer). NFC используется в платежах, пропусках, метках, смартфонах. Для пентестера важны: чтение/запись тегов, эмуляция карт, relay-атаки и работа с NDEF-данными. Этот урок — углубление после базового знакомства с RFID/NFC.

## Стандарты и режимы

NFC работает в трёх режимах:

- **Reader/Writer** — телефон/ридер читает теги и карты.
- **Card Emulation** — устройство представляется картой (для оплаты/пропуска).
- **Peer-to-peer** — обмен между двумя NFC-устройствами.

Стандарты: **ISO 14443-A** (Mifare, большинство карт), **ISO 14443-B** (eID, паспорта), **ISO 15693** (Vicinity, дальние метки), **FeliCa** (Япония).

## NDEF: формат данных тега

**NDEF (NFC Data Exchange Format)** — стандартный формат записей на NFC-тегах. Запись содержит тип (URI, текст, MIME), ID и полезную нагрузку.

```bash
# Чтение тега через nfcpy (Python)
python3 -c "
import nfc
clf = nfc.ContactlessFrontend('usb')
tag = clf.connect(rdwr={'on-connect': lambda t: print(t.ndef) or False})
"
# Пример вывода: [NDEF Text Record 'Hello', URI Record 'https://...']
```

Типы тегов: NTAG21x, Mifare Ultralight, Mifare Classic, FeliCa. NTAG/Ultralight — самые дешёвые, часто используются как метки.

## Чтение и запись через ACR122U

ACR122U — популярный USB-ридер. Через `nfcpy`/`libnfc`:

```bash
# libnfc: список устройств и чтение
nfc-list
nfc-poll
# nfcpy: запись URI на NTAG
python3 -c "
import nfc
clf = nfc.ContactlessFrontend('usb')
def on_connect(tag):
    tag.ndef.records = [nfc.ndef.UriRecord('https://example.com')]
    return False
clf.connect(rdwr={'on-connect': on_connect})
"
```

Запись NDEF-записи позволяет создавать «умные метки» (открыть сайт, запустить приложение).

## Эмуляция карт

Эмуляция — ключевой приём: устройство представляется картой, чтобы система приняла его за оригинал.

- **Proxmark3**: `hf 14a sim` — эмуляция ISO14443-A.
- **ChameleonMini/Tiny**: эмуляция нескольких карт.
- **Android HCE**: Host Card Emulation — телефон эмулирует карту.
- **Flipper Zero**: эмуляция некоторых HF-карт.

Эмуляция UID-только карт (без криптографии) тривиальна: достаточно воспроизвести UID. Для криптокарт (DESFire) эмуляция требует ключей.

## Relay-атаки

**NFC relay** — ретрансляция обмена между картой и ридером на расстояние. Два устройства (или телефон + прокси) передают APDU туда-обратно, и ридер «думает», что карта рядом. Это атака на **дистанцию**, а не на криптографию: даже защищённая карта может быть использована удалённо, если владелец приложил её к ретранслятору.

```text
[Ридер] <-> [Ретранслятор A у ридера] ~~~ (сеть) ~~~ [Ретранслятор B у карты] <-> [Карта]
```

Защита: distance-bounding протоколы, ограничение по времени ответа, требование физического присутствия.

## Разобранный пример: клонирование NFC-метки

```bash
# 1. Считать тег
nfc-list
python3 -c "
import nfc
clf = nfc.ContactlessFrontend('usb')
def on_connect(tag):
    print('UID:', tag.identifier.hex())
    print('NDEF:', tag.ndef)
    return False
clf.connect(rdwr={'on-connect': on_connect})
"
# 2. Если это NTAG/Ultralight — UID и данные можно воспроизвести
# 3. Записать на «болванку» через nfcpy (см. выше)
# 4. Или эмулировать через Proxmark: hf 14a sim
```

## Частые ошибки и подводные камни

- **Только UID vs полная карта**: многие системы проверяют лишь UID — их легко обойти.
- **Драйверы ACR122U**: на Linux нужны udev-правила/PCSC.
- **NDEF-lock**: тег можно «залочить» от записи.
- **Relay требует двух устройств** и низкой задержки.
- **Дальность**: NFC — сантиметры; антенна и ориентация критичны.
- **Паспорта (ISO 14443-B)** защищены BAC/PACE — просто так не читаются.

## NFC в мобильных платежах и HCE

Современные телефоны поддерживают **Host Card Emulation (HCE)**: приложение на телефоне эмулирует бесконтактную карту, а защищённый элемент (SE) или облако хранит ключи. В Android за это отвечает сервис `HostApduService`. С точки зрения анализа это означает, что платёжный обмен можно наблюдать и реверсить на телефоне, а не только на физической карте.

```java
// Фрагмент Android HCE-сервиса
public class MyHceService extends HostApduService {
    @Override
    public byte[] processCommandApdu(byte[] apdu, Bundle extras) {
        // разбор APDU от ридера
        return new byte[]{(byte)0x90, 0x00}; // SW=9000
    }
}
```

Ключевые векторы: подмена приложения-HCE (на рутованном устройстве), перехват APDU между ридером и телефоном, анализ логики приложения. Для пентеста важно понимать, что «карта» — это софт, и её логику можно реверсить.

## Анализ и фаззинг NFC

Фаззинг NFC-протоколов ищет падения в ридерах и телефонах. Основные подходы:

- **Мутация APDU**: отправлять ридеру/карте нестандартные команды и наблюдать поведение.
- **Fuzzing UID/ATQA/SAK**: поддельные параметры карты могут ломать парсер ридера.
- **Эмуляция через Proxmark/Chameleon**: быстро менять ответы и ловить аномалии.
- **Логирование обмена**: PCSC-логи (`pcscd`), Wireshark с NFC-декодером.

```bash
# Логирование PCSC для анализа APDU
export PCSCLITE_DEBUG=1
# В другом терминале — операция с картой, затем разбор лога
```

Для ответственного раскрытия фиксируйте воспроизводимый PoC и минимальный сценарий.

## Защита NFC-систем

Как защищать бесконтактные системы:

- **Не доверять только UID** — использовать криптографическую аутентификацию (DESFire EV2, SE).
- **Distance-bounding** — ограничение по времени ответа против relay.
- **Ротация и защита ключей** — не дефолтные, не утекающие в прошивку.
- **Мониторинг аномалий** — частые чтения, странные UID.
- **Физическая защита** — экранирующие чехлы для карт, блокировка ретрансляции.

Проверка конфигурации: какие данные доступны без аутентификации, какие ключи используются, есть ли защита от replay/relay.

## Практический стенд для NFC

Для безопасной практики:

- **ACR122U/ACR1252** — USB-ридер.
- **Proxmark3** — эмуляция и анализ.
- **ChameleonMini/Tiny** — эмуляция нескольких карт.
- **Теги NTAG/Ultralight** — для опытов с NDEF.
- **Изолированное помещение** — чтобы не мешать чужим системам.

Правило: не эмулируйте чужие карты в реальных системах и не проводите relay без письменного согласия. NFC — это физический доступ, и его последствия реальны.

## NFC-теги: типы и ёмкость

| Тип | Чип | Память | Примечание |
|-----|-----|--------|-----------|
| Type 1 | Topaz | 96–512 б | устаревший |
| Type 2 | NTAG/Ultralight | 48–888 б | самый частый |
| Type 3 | FeliCa | — | Япония |
| Type 4 | DESFire | до 8 КБ | защищённый |
| Type 5 | ISO 15693 | до 64 КБ | дальние метки |

Понимание типа тега определяет возможности: NTAG можно перезаписывать и клонировать, DESFire защищён, ISO 15693 работает на большем расстоянии. Для анализа сначала определите тип через `nfc-list`/Proxmark.

## Практические сценарии

- **Умные метки**: создать NDEF-запись с URL/приложением.
- **Клонирование пропуска**: считать NTAG/Ultralight и записать на болванку.
- **Анализ оплаты**: снять APDU-обмен между телефоном и терминалом.
- **Relay-демонстрация**: показать риск удалённого использования карты.
- **Инвентаризация**: определить, какие теги используются в системе.

Всегда фиксируйте scope: NFC — это физический доступ, и его последствия реальны.

## Безопасность на уровне приложения

Помимо транспорта (relay, клонирование), уязвимости бывают в **логике приложения**, использующего NFC:

- **Доверие к UID/NDEF** без проверки — подмена метки даёт неверные данные.
- **Парсинг NDEF** — переполнения при разборе вредоносной записи.
- **Автозапуск действий** — телефон, считав метку, открывает URL/приложение; возможен фишинг.
- **Replay** легитимных меток.

Проверяйте, как приложение обрабатывает данные с тега, и можно ли подсунуть поддельный тег, чтобы изменить поведение.
