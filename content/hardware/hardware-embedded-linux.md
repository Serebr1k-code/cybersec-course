## Вопрос, с которого всё начинается

В прошлом уроке мы реверсили RTOS-прошивку. Но многие устройства — роутеры, камеры, умные колонки — работают на настоящем Linux. Правда, он сильно отличается от десктопного: нет `systemd`, нет `apt`, нет привычного bash.

Вопрос урока: как быстро понять, «из чего собрана» такая система, и где в ней искать точки входа для анализа?

## Наш пример: прошивка роутера

У нас есть образ прошивки роутера. В прошлых уроках мы научились распаковывать из него файловые системы. Теперь распакуем корневую (`rootfs`) и разберёмся, что внутри:

```bash
$ unsquashfs -d rootfs/ rootfs.squashfs
created 1432 files, 289 directories
```

Дальше — серия простых вопросов: что за система, что запускается при старте, какие есть сервисы.

## Шаг 1: чем встраиваемый Linux отличается от десктопа

| Аспект | Десктоп | Встраиваемая система |
|--------|---------|---------------------|
| libc | glibc | musl, uClibc |
| init | systemd | BusyBox init, procd |
| shell | bash | BusyBox ash |
| утилиты | coreutils | BusyBox applets |
| rootfs | rw, большой | ro, squashfs/UBIFS |
| обновление | пакетный менеджер | весь образ |

**libc** — стандартная библиотека C; **init** — первая программа, запускающая всё остальное. Из таблицы сразу следуют выводы: `strings` по busybox покажет почти все «стандартные» команды, а обновляется система целиком, а не отдельными пакетами.

## Шаг 2: определяем фреймворк сборки

Встраиваемый Linux собирают одним из трёх фреймворков:

- **Buildroot** — простой, Makefile-based, собирает toolchain, ядро и rootfs из `.config`.
- **Yocto/OpenEmbedded** — мощный, слоистый, в промышленности.
- **OpenWrt** — специализирован под роутеры: `opkg`, `procd`, UCI-конфиги, `sysupgrade`.

По маркерам в rootfs видно, кто это:

```bash
$ cat etc/openwrt_release 2>/dev/null
DISTRIB_ID='OpenWrt'
$ ls etc/config 2>/dev/null
network  system  wireless
```

`etc/openwrt_release` и каталог `etc/config` — это точно OpenWrt. Знание фреймворка бесценно: под GPL производитель обязан выложить исходники, и вместо реверса бинарников вы будете читать код.

## Шаг 3: устройство — через device tree

Ядро под встраиваемую систему собирают под конкретный SoC. Его периферию описывает **device tree** (`.dtb`/`.dts`): адреса регистров, прерывания, шины I2C/SPI, GPIO. Без правильного DTB ядро не найдёт железо.

```bash
$ dtc -I dtb -O dts -o board.dts board.dtb
$ cat /sys/firmware/devicetree/base/model
```

Device tree — клад для пентестера: он показывает **все** интерфейсы платы, включая отладочные UART и адреса памяти. Иногда производитель оставляет в нём комментарии и отладочные узлы.

## Шаг 4: понимаем разделы образа

Прошивка обычно состоит из:

1. **bootloader** (U-Boot) — отдельный раздел.
2. **kernel** (zImage/uImage/FIT) — с DTB.
3. **rootfs** (squashfs/UBIFS) — система.
4. **data/overlay** (JFFS2/UBIFS) — изменяемые данные.
5. **env** — окружение загрузчика.

`binwalk` покажет границы разделов, а таблица `mtdparts` — их назначение.

Отдельно стоит помнить про **overlay**: изменяемые данные и конфиги могут жить не в самом rootfs, а в наложенном разделе (JFFS2/UBIFS). Тогда правки пользователя сохраняются отдельно, а образ остаётся read-only — это важно и при анализе, и при модификации прошивки.

## Шаг 5: ищем точки входа

Теперь пройдёмся по стандартным местам:

```bash
$ ls -l etc/init.d/ | head
-rwxr-xr-x 1 root root 1234 rcS
-rwxr-xr-x 1 root root 2345 dropbear
$ ls usr/sbin/ usr/bin/ 2>/dev/null
$ ls -la www/ 2>/dev/null
$ file www/cgi-bin/* 2>/dev/null
```

Что важно:

- **`/etc/init.d`, `/etc/rc.d`** — что стартует при загрузке.
- **`/etc/config` (UCI)** — конфигурация сервисов.
- **`/usr/sbin`, `/usr/bin`** — демоны, включая проприетарные.
- **`/www`, `/usr/lib/cgi-bin`** — веб-интерфейс, частый источник RCE.
- **`/etc/passwd`, `/etc/shadow`** — учётки.

## Шаг 6: карта сервисов

Чтобы понять поверхность атаки, составляем таблицу сервисов:

| Сервис | Порт | Конфиг | Риск |
|--------|------|--------|------|
| BusyBox httpd | 80/443 | `/etc/httpd.conf` | CGI, path traversal |
| dropbear (SSH) | 22 | `/etc/config/dropbear` | слабые ключи |
| telnetd | 23 | init-скрипт | открытый shell |
| dnsmasq | 53 | `/etc/dnsmasq.conf` | подмена DNS |
| uhttpd | 80 | UCI | Lua/CGI RCE |

Для каждого сервиса проверьте: под каким пользователем запущен, какие файлы отдаёт, есть ли аутентификация. Часто демоны работают от root и не проверяют входные данные.

## Шаг 7: собираем «паспорт» системы

Если устройство доступно, отладку начинают с базовых команд — они дают мгновенный портрет системы:

```bash
$ uname -a
$ cat /proc/cmdline
$ mount
$ ps auxw 2>/dev/null || ps
$ cat /proc/mtd 2>/dev/null
```

Очень полезен `/proc/cmdline` — там видны `bootargs`, включая отладочные параметры, которые оставил производитель. Если встречаете `init=/bin/sh` или `single`, устройство уже частично открыто. Ещё один приём — `/proc/1/environ`: переменные окружения главного процесса иногда содержат токены и пути к секретам.

## Шаг 8: GPL — «золотая жила»

Большая часть встраиваемого Linux под **GPL**, что обязывает производителя отдавать исходники. Ищем их прямо в прошивке:

```bash
$ find rootfs -iname 'COPYING*' -o -iname 'LICENSE*' -o -iname '*.patch' | head
```

Даже если производитель выложил не всё, GPL-компоненты (ядро, BusyBox, U-Boot) сопоставляются с апстримом по версии — и различия покажут «фичи» вроде скрытых учёток.

## Что мы теперь знаем

1. Встраиваемый Linux — урезанный: musl/uClibc, BusyBox, read-only rootfs.
2. Фреймворк (Buildroot/Yocto/OpenWrt) определяется по маркерам в rootfs.
3. Device tree описывает всё железо платы, включая отладочные интерфейсы.
4. Образ делится на bootloader, kernel+DTB, rootfs, data и env.
5. Точки входа: init-скрипты, конфиги, демоны, CGI, учётки.
6. GPL-исходники часто доступны и заменяют реверс бинарников.

## На что смотреть дальше

- **Динамические бинарники требуют libc.** Для запуска в QEMU нужна правильная libc/ld.so.
- **musl vs glibc.** Символы и поведение отличаются — не тащите десктопную libc.
- **Нет DTB.** Ядро не найдёт периферию.
- **BusyBox вместо coreutils.** Флаги команд урезаны, не все привычные опции есть.
- **Overlay.** Изменённые конфиги могут жить в overlay, а не в самом rootfs.
