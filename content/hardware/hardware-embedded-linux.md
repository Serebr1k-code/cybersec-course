Встраиваемый Linux — тот же Linux, что и на десктопе, но собранный под конкретное железо и урезанный до минимума. Здесь нет привычных `systemd`, `apt` и glibc: часто используется **BusyBox**, **musl**, статически собранные бинарники и read-only rootfs. Понимание того, как такие системы собирают и из чего они состоят, критично для реверса прошивок: вы будете знать, где искать инициализацию, конфиги и уязвимости. Этот урок — карта встраиваемого Linux.

## Чем встраиваемый Linux отличается от десктопа

| Аспект | Десктоп | Встраиваемая система |
|--------|---------|---------------------|
| libc | glibc | musl, uClibc, glibc (редко) |
| init | systemd | BusyBox init, procd, sysvinit |
| shell | bash | BusyBox ash |
| утилиты | coreutils | BusyBox applets |
| rootfs | rw, большой | ro, squashfs/UBIFS |
| обновление | пакетный менеджер | весь образ (sysupgrade) |
| ядро | модульное | монолитное, без модулей |

Из этого следуют практические выводы: `strings` по busybox покажет почти все «стандартные» команды; конфиги лежат в `/etc/config` (OpenWrt) или `/etc` (обычный); обновления — целиком образ, а не отдельные пакеты.

## Как собирают встраиваемый Linux

Три основных фреймворка:

- **Buildroot** — Makefile-based, генерирует toolchain, ядро и rootfs из конфига (`.config`). Простой и предсказуемый.
- **Yocto/OpenEmbedded** — мощный, слоистый, используется в промышленности; результатом является SDK и образ.
- **OpenWrt** — специализирован под роутеры: `opkg`, `procd`, UCI-конфиги, `sysupgrade`.

```bash
# Buildroot: минимальный пример
make menuconfig     # выбрать target, toolchain, пакеты
make                # собрать
ls output/images/   # zImage, rootfs.squashfs, rootfs.tar
```

Зная фреймворк, можно найти исходники и патчи производителя — иногда в открытом виде (GPL-требование). Это бесценно: вместо реверса бинарников вы читаете код.

## Ядро и device tree

Ядро для встраиваемой системы собирают под конкретный SoC. Ключевой файл — **device tree** (`.dtb`/`.dts`), который описывает железо: адреса регистров, прерывания, шины I2C/SPI, GPIO. Без правильного DTB ядро не найдёт периферию.

```bash
# Разобрать DTB обратно в текст
dtc -I dtb -O dts -o board.dts board.dtb
# Посмотреть дерево устройств на живой системе
ls /sys/firmware/devicetree/base/
cat /sys/firmware/devicetree/base/model
```

Device tree — клад для пентестера: он показывает **все** интерфейсы платы (включая отладочные UART), адреса памяти, подключённые чипы. Часто производитель оставляет в DTS комментарии и отладочные узлы.

## Разделение образов

Прошивка обычно состоит из:

1. **bootloader** (U-Boot) — отдельный раздел.
2. **kernel** (zImage/uImage/FIT) — с DTB.
3. **rootfs** (squashfs/UBIFS/ext) — система.
4. **data/overlay** (JFFS2/UBIFS) — изменяемые данные, конфиги.
5. **env** — окружение загрузчика.

При анализе важно понимать, где что: `binwalk` покажет границы, а таблица разделов (`mtdparts`, GPT) — их назначение.

## Точки входа для анализа

- **`/etc/init.d` и `/etc/rc.d`** — что стартует при загрузке.
- **`/etc/config` (UCI) или `/etc/*.conf`** — конфигурация сервисов.
- **`/usr/sbin` и `/usr/bin`** — бинарники, включая проприетарные демоны.
- **`/www`/`/usr/lib/cgi-bin`** — веб-интерфейс, частый источник RCE.
- **`/etc/passwd`, `/etc/shadow`** — учётки.
- **`/root`, `/home`** — скрипты, ключи, история.

## Разобранный пример: от прошивки к пониманию системы

```bash
# 1. Распаковать rootfs (см. hardware-filesystems)
unsquashfs -d rootfs/ rootfs.squashfs
cd rootfs
# 2. Определить фреймворк по маркерам
cat etc/openwrt_release 2>/dev/null      # OpenWrt
ls etc/config 2>/dev/null                # UCI
cat etc/os-release 2>/dev/null
# 3. Понять инициализацию
ls -l etc/init.d/ | head
cat etc/init.d/rcS 2>/dev/null
# 4. Найти демоны и их конфиги
ls usr/sbin/ usr/bin/ 2>/dev/null
# 5. Веб-интерфейс
ls -la www/ 2>/dev/null
file www/cgi-bin/* 2>/dev/null
# 6. Проверить, есть ли исходники (GPL)
find . -name '*.c' -o -name '*.h' 2>/dev/null | head
```

| Инструмент | Назначение |

| `file`/`strings` | идентификация бинарников |

| `readelf`/`objdump` | анализ ELF |
| `ghidra`/`radare2` | реверс демонов |

## Частые ошибки и подводные камни

- **Динамические бинарники требуют libc**: для запуска в QEMU нужна правильная libc/ld.so (см. `hardware-firmware-emulation`).
- **musl vs glibc**: символы и поведение отличаются; не тащите десктопную libc.
- **Отсутствие DTB**: ядро не найдёт периферию.
- **BusyBox вместо coreutils**: флаги команд урезаны — не все привычные опции есть.
- **Overlay**: изменения конфигов могут жить в overlay, а не в rootfs.

## Отладка встраиваемой системы

Когда устройство доступно, отладка начинается с базовых команд. Полезно сразу собрать «паспорт» системы: версию ядра, модель платы, список процессов, монтирования, сетевые интерфейсы и модули.

```bash
uname -a
cat /proc/cpuinfo
cat /proc/cmdline
mount
ps auxw 2>/dev/null || ps
lsmod 2>/dev/null
cat /proc/mtd 2>/dev/null
```

На многих устройствах нет `ps`/`mount` в привычном виде — используйте BusyBox-аналоги. Если система не даёт shell, диагностика идёт через UART-лог загрузки (см. `hardware-uart`). Очень полезен `/proc/cmdline` — там видны `bootargs`, включая отладочные параметры, которые оставил производитель. Если в cmdline есть `init=/bin/sh` или `single`, устройство уже частично открыто. Ещё один приём — посмотреть `/proc/1/environ` и переменные окружения демонов: там иногда лежат токены и пути к секретам.

## Лицензии и GPL: как получить исходники

Большая часть встраиваемого Linux лицензирована под **GPL**, что обязывает производителя предоставлять исходники. Это золотая жила для пентеста: вместо реверса бинарников вы читаете настоящий код.

- Ищите в прошивке каталоги `src/`, архивы `.tar.gz`, файлы `COPYING`/`LICENSE`, `*.patch`.
- На сайте производителя — раздел «Open Source» / «GPL».
- Для OpenWrt исходники доступны в git; для Buildroot/Yocto — по конфигу.

```bash
find rootfs -iname 'COPYING*' -o -iname 'LICENSE*' -o -iname '*.patch' | head
```

Даже если производитель не выложил всё, GPL-компоненты (ядро, BusyBox, U-Boot) можно сопоставить с апстримом по версии и найти различия — именно в патчах часто прячутся «фичи» вроде скрытых учёток.

## Типичные сервисы и их конфигурация

Чтобы понять поверхность атаки, составьте карту сервисов:

| Сервис | Порт | Конфиг | Риск |
|--------|------|--------|------|
| BusyBox httpd | 80/443 | `/etc/config`/`/etc/httpd.conf` | CGI, path traversal |
| dropbear (SSH) | 22 | `/etc/config/dropbear` | слабые ключи, пароли |
| telnetd | 23 | init-скрипт | открытый shell |
| dnsmasq | 53 | `/etc/dnsmasq.conf` | подмена DNS |
| uhttpd | 80 | UCI | Lua/CGI RCE |
| UPnP (miniupnpd) | 1900/5000 | `/etc/config/upnpd` | port-mapping abuse |

Для каждого сервиса проверьте: под каким пользователем запущен, какие файлы отдаёт, есть ли аутентификация. Часто демоны работают от root и не проверяют входные данные.

## Практические сценарии анализа

Типовые задачи, где нужен этот материал:

- **Найти способ загрузки**: определить фреймворк, понять `bootcmd` и разделы, найти сервисный режим.
- **Понять поверхность атаки**: составить список демонов, портов и CGI.
- **Извлечь секреты**: пройтись по `/etc`, `/root`, конфигам, ключам и сертификатам.
- **Найти бэкдор**: сверить GPL-исходники с апстримом, поискать патчи и «сервисные» ветки.
- **Подготовить эмуляцию**: определить libc и архитектуру для запуска бинарников в QEMU.

Все эти шаги опираются на одно: понимание того, из чего собрана система. Без него вы будете реверсить бинарники вслепую, а с ним — читать исходники и конфиги, где ответы уже написаны.

## Итог

Встраиваемый Linux — это предсказуемая система: известный набор фреймворков, стандартное расположение файлов, BusyBox вместо coreutils. Задача пентестера — быстро определить «сборку» и дальше идти по стандартному чек-листу: конфиги, демоны, CGI, ключи, исходники.
