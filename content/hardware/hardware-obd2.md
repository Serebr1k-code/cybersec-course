## Вопрос, с которого всё начинается

У тебя есть автомобиль и адаптер OBD-II. Диагностический софт показывает обороты и коды ошибок — но это же скучно. Гораздо интереснее понять: **какие именно кадры летят по шине, когда водитель жмёт кнопку**, и можно ли их повторить. Именно с этого начинается любой automotive-пентест — с умения подключиться и читать шину как есть.

Этот урок — практика: как настроить интерфейс, прочитать диагностику и увидеть «команды» в потоке кадров.

## Наш пример: адаптер и первая запись

Подключим адаптер, который даёт **сырой** доступ к CAN (не только готовые OBD-команды). Это может быть CANtact, Macchina M2 или плата на MCP2515. В Linux такой адаптер становится обычным сетевым интерфейсом `can0` — подход называется **SocketCAN**:

```
$ sudo ip link set can0 type can bitrate 500000
$ sudo ip link set can0 up
$ ip -details link show can0
2: can0: <NOARP,UP,LOWER_UP> mtu 16 qdisc pfifo_fast state UNKNOWN
    link/can  promiscuity 0
    can state ERROR-ACTIVE (berr-counter tx 0 rx 0) restart-ms 0
    bitrate 500000 sample-point 0.875
```

Что мы сделали: `type can bitrate 500000` задаёт скорость 500 кбит/с (её надо угадать под шину — типичны 125, 250 и 500), `up` включает интерфейс. Состояние `ERROR-ACTIVE` значит, что узел здоров и видит шину. Теперь читаем трафик:

```
$ candump can0
  can0  2F0   [8]  01 02 03 04 05 06 07 08
  can0  3A0   [2]  00 00
  can0  1A0   [8]  00 00 00 00 00 00 00 00
```

`candump` печатает каждый кадр: интерфейс, ID (`2F0`), длину `[8]` и байты. Никакой магии — просто поток. Задача урока: превратить этот поток в понятную картину.

## Шаг 1: читаем стандартную диагностику

Прежде чем искать «команды», посмотрим, что отдаёт штатная диагностика OBD-II. Режим **Mode 01** — текущие данные, **Mode 03** — коды ошибок (**DTC**, Diagnostic Trouble Codes). Через адаптер ELM327 это делает библиотека `python-OBD`:

```
$ python3 -c "
import obd
conn = obd.OBD()
print('RPM:', conn.query(obd.commands.RPM).value)
print('SPEED:', conn.query(obd.commands.SPEED).value)
print('DTC:', conn.query(obd.commands.GET_DTC).value)
"
RPM: 812 rpm
SPEED: 0 kph
DTC: [('P0420', 'Catalyst System Efficiency Below Threshold')]
```

Мы получили живые параметры и код ошибки. Каждый параметр запрашивается по своему **PID** (Parameter ID): `0x0C` — обороты, `0x0D` — скорость, `0x05` — температура охлаждающей жидкости. `P0420` — это «катализатор работает ниже порога». Уже отсюда видно: диагностика не только читает, она рассказывает о состоянии блоков.

## Шаг 2: находим кадры, отвечающие за действия

Теперь самое интересное. Записываем трафик, пока водитель жмёт кнопки, и ищем, что изменилось:

```
$ candump -L can0 > drive.log &
$ echo "жми: дверь, свет, стекло..."
$ sleep 60 && kill %1
$ awk '{print $3}' drive.log | sort | uniq -c | sort -rn | head
    340 1A0
    300 2F0
    120 3A0
     44 19B
```

`-L` пишет лог в формате, который потом можно проиграть через `canplayer`. Считаем частоты: `1A0` и `2F0` идут постоянно (датчики), а `19B` — редко, событийно. Именно редкие ID реагируют на действия. Смотрим кадры подозрительного ID:

```
$ grep '19B' drive.log | head
  can0  19B   [8]  00 00 00 00 00 00 00 01
  can0  19B   [8]  00 00 00 00 00 00 00 00
```

Последний байт меняется с `01` на `00` — это «дверь». Так, сопоставляя моменты нажатий с изменениями байтов, находят **команды**.

## Шаг 3: воспроизводим и проверяем

Найденный кадр можно отправить самому:

```
$ cansend can0 19B#0000000000000001
```

`cansend` шлёт ровно один кадр `ID#DATA`. Если функция сработала, мы подтвердили, что нашли команду — а значит, научились спуфингу и можем её автоматизировать. Проверить реакцию на поток кадров помогает генератор:

```
$ cangen can0 -g 10 -I 19B -L 8 -D 0000000000000001 -n 20
```

`-g 10` — интервал 10 мс, `-n 20` — всего 20 кадров.

## Шаг 4: диагностика, которая умеет писать (UDS)

Кроме базового OBD-II производители используют **UDS** (ISO 14229) — расширенную диагностику с чтением, записью и прошивкой. Запросы идут по тем же CAN-ID (обычно `0x7E0` — запрос, `0x7E8` — ответ). Критичные операции защищены сервисом **Security Access** (seed/key):

```
$ cansend can0 7E0#02 10 03          # переход в extended session
$ cansend can0 7E0#02 27 01          # запрос seed
$ candump can0 | grep 7E8            # ответ с seed: 67 01 XX XX
$ cansend can0 7E0#06 27 02 AA BB CC DD   # отправка ключа
```

Если алгоритм ключа слабый, его реверсируют из прошивки блока и разблокируют ECU. Это уже путь к перепрошивке — и к изменению поведения автомобиля.

## В машине не одна шина

Полезно понимать, что видно в потоке, а что нет. У автомобиля обычно **несколько CAN-шин**, и они доступны на разных контактах разъёма: силовая (powertrain, 500 кбит/с — двигатель и коробка), кузовная (comfort — двери, свет, стеклоподъёмники) и диагностическая. Если адаптер подключён только к одной, часть сообщений просто не видна. Для второй шины нужен мультипиновый адаптер или прямое подключение к нужным проводам. Поэтому «нет нужного ID в логе» не значит «его нет в машине» — возможно, вы смотрите не ту шину.

## Если не сработало

- **Интерфейс не поднимается.** Скорее всего, неверный **bitrate** — переберите 125/250/500 кбит/с.
- **Каша в данных, ошибки шины.** Проверьте **терминаторы** по 120 Ом на концах шины: без них сигнал отражается и искажается.
- **ELM327-«клон» врёт.** Дешёвые адаптеры поддерживают не все протоколы; для сырого CAN берите CANtact или M2.
- **Части сообщений нет.** Шлюз не пускает весь трафик через OBD; на разных пинах (6/14 и 3/11) могут быть разные шины.
- **Запись в ECU необратима.** Диагностические сервисы записи могут «окирпичить» блок — работайте на своём авто или симуляторе.

## Что мы теперь знаем

1. SocketCAN превращает CAN-адаптер в обычный интерфейс `can0`.
2. `candump` читает, `cansend` шлёт один кадр, `cangen` — поток, `canplayer` — реплей.
3. Диагностика читается по PID; DTC — это коды ошибок.
4. Действия водителя находят, сопоставляя момент нажатия с изменением редких ID.
5. UDS умеет писать; защита — seed/key, и её слабость реверсится из прошивки.
