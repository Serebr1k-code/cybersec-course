## Вопрос, с которого всё начинается

Банковские карты, SIM, паспорта, корпоративные ID — всё это **контактные смарт-карты** (стандарт ISO 7816). В отличие от простых RFID-меток, внутри такой карты настоящий мини-компьютер с файловой системой и командами.

Как с ней вообще разговаривать и что из неё можно вытащить? Разберём на конкретной карте.

## Наш пример: SIM-карта в ридере

Перед нами обычная SIM-карта и USB-ридер. Задача — понять её структуру: какие данные доступны без PIN, а какие защищены. Инструмент — библиотека **pyscard** и утилиты **pcsc**.

## Шаг 1: как карта устроена

У смарт-карты восемь контактов: `Vcc`, `RST`, `CLK`, `GND`, `I/O` и другие. Обмен идёт полудуплексно и асинхронно (протоколы T=0 или T=1). Карта хранит данные в **файловой системе**, а доступ к файлам регулируется условиями: свободно, по PIN или по административному ключу.

## Шаг 2: язык команд — APDU

Карта общается **командами APDU** (Application Protocol Data Unit). Команда выглядит так:

```
CLA INS P1 P2 Lc Data Le
```

| Поле | Значение |
|------|----------|
| CLA | класс команды (00 — стандарт) |
| INS | инструкция (A4 = SELECT, B0 = READ BINARY, 20 = VERIFY) |
| P1/P2 | параметры |
| Lc | длина данных |
| Data | данные |
| Le | ожидаемая длина ответа |

Ответ — это `Data SW1 SW2`, где `SW1SW2` — **статус**: `9000` значит успех, `6A82` — файл не найден, `6982` — условия безопасности не выполнены.

Типовые инструкции: `A4` SELECT (выбрать файл или приложение по AID), `B0` READ BINARY (читать прозрачный файл), `B2` READ RECORD (читать запись), `20` VERIFY (проверить PIN), `88` INTERNAL AUTHENTICATE.

## Шаг 3: определяем карту

Сначала находим ридер и читаем **ATR** — «ответ на сброс», по которому определяют тип карты. Разные карты — SIM, банковская, паспорт — отличаются ATR и набором приложений, поэтому этот шаг задаёт весь дальнейший план работы:

```
$ pcsc_scan
Card ATR: 3B 6F 00 FF ...
```

`ATR` — это отпечаток карты: производитель, протокол, поддерживаемые функции. Дальше работаем через pyscard:

```
$ python3 - <<'PY'
from smartcard.System import readers
r = readers()[0]
conn = r.createConnection()
conn.connect()
print('ATR:', conn.getATR())
apdu = [0x00,0xA4,0x04,0x00,0x07,0xA0,0x00,0x00,0x00,0x03,0x10,0x10]
data, sw1, sw2 = conn.transmit(apdu)
print(f'SW={sw1:02X}{sw2:02X}')
PY
```

`conn.transmit(apdu)` отправляет команду и возвращает данные и статус. Здесь `A4` — SELECT, а `A0 00 00 00 03 10 10` — AID приложения (в примере — Visa).

## Шаг 4: обходим файловую систему

Файловая система смарт-карты трёхуровневая: **MF** (master file) → **DF** (dedicated, приложения) → **EF** (elementary, данные). Идём по дереву:

```
> 00 A4 00 00 02 7F 20   # SELECT DF GSM
> 00 A4 00 00 02 2F E2   # SELECT EF ICCID
> 00 B0 00 00 0A         # READ BINARY, 10 байт
```

Сначала выбираем каталог GSM (`7F20`), затем файл ICCID (`2FE2`), а `READ BINARY` возвращает его содержимое — серийный номер SIM, обычно в BCD-кодировке. Так же читается IMSI из файла `6F07`.

## Шаг 5: защищённые файлы

Файлы с телефонной книгой и сообщениями защищены **PIN**. Проверка идёт командой VERIFY:

```
> 00 20 00 01 08 <pin>
```

Здесь важно понимать: **у PIN всего три попытки**. После трёх неверных карта блокируется и потребует PUK. Перебирать PIN вслепую нельзя — за несколько секунд можно безвозвратно заблокировать карту.

## Шаг 6: почему это сложнее клонировать

В отличие от 125 кГц-карт, смарт-карта **выполняет код** и хранит секреты в защищённой памяти. Клонирование требует либо извлечения ключей (side-channel, fault injection), либо атаки на реализацию апплета. Обычное чтение даёт только публичные данные.

Для пентеста это означает: работайте с моделью угроз — ищите не «клон», а уязвимость в апплете. Часто слабое место не в криптографии, а в **логике**: проверка PIN реализована так, что при определённой последовательности команд флаг «аутентифицирован» остаётся установленным. Такие ошибки ищут фаззингом APDU. Для JavaCard-апплетов используют **GlobalPlatformPro**:

```
$ gp --list
$ gp --install app.cap
```

## Шпаргалка по командам APDU

Соберём типовые инструкции в одну таблицу:

| Команда | CLA INS | Назначение |
|---------|---------|------------|
| SELECT | 00 A4 | выбрать приложение или файл |
| READ BINARY | 00 B0 | читать данные |
| GET RESPONSE | 00 C0 | забрать ответ |
| VERIFY | 00 20 | проверка PIN |
| INTERNAL AUTH | 00 88 | аутентификация карты |

А коды статуса, которые встречаются чаще всего: `9000` — успех, `6A82` — файл не найден, `6982` — не удовлетворены условия безопасности, `6700` — неверная длина.

## Как защищают смарт-карты

- **PIN/PUK** и блокировка после нескольких неудачных попыток.
- **Криптографические апплеты** (JavaCard) с секретами в защищённой памяти.
- **Аттестация апплетов** — проверка, что установленный код подлинный.
- **Защита от side-channel** — маскирование и случайные задержки против анализа потребления.

Именно поэтому банковские карты и SIM используют этот класс: обычное чтение даёт лишь публичные данные, а секреты защищены и кодом, и железом.

## Если не сработало

- **Перебор PIN.** Три неверных попытки — блокировка (PUK). Никогда не брутфорсите PIN на реальной карте.
- **Неверный протокол.** T=0 и T=1 имеют разные тайминги; библиотека обычно выбирает сама.
- **Нет Le в APDU.** Некоторые карты требуют явный Le, иначе возвращают `6700` (wrong length).
- **Игнорирование SW.** Всегда проверяйте `SW1SW2`: `9000` — успех, иначе — причина отказа.
- **Скачки питания.** Они могут «залочить» карту; используйте штатный ридер.
- **Правовые рамки.** Чтение чужой SIM или банковской карты — преступление.

## Что мы теперь знаем

1. Смарт-карта — это мини-компьютер с файловой системой MF/DF/EF и защищённой памятью.
2. Обмен идёт командами APDU вида `CLA INS P1 P2 Lc Data Le`, а ответ заканчивается статусом.
3. Статус `9000` означает успех; `6A82` и `6982` — типовые причины отказа в доступе.
4. PIN имеет три попытки, после чего карта блокируется и требует PUK — брутфорс тут бесполезен и опасен.
5. Клонировать карту сложно: уязвимость обычно в логике апплета, а не в шифре.
