## Вопрос, с которого всё начинается

EtherNet-IP — промышленный Ethernet, популярный у Allen-Bradley/Rockwell. Он несёт **CIP** — Common Industrial Protocol, объектную модель, похожую на то, что мы видели в BACnet, но в АСУ ТП.

Вопрос урока: как разобрать CIP-обмен и найти теги, которые можно записать.

## Наш пример: CIP-обмен с ПЛК

У нас есть дамп EtherNet-IP-трафика с контроллером. Видны сессия ENIP, затем CIP-запросы к объектам. Разберём и найдём записываемый тег.

<!-- lab -->

## Шаг 1: два уровня — ENIP и CIP

**EtherNet-IP** — это обёртка над **CIP**. Сообщение состоит из:

- **ENCAP** (Encapsulation) — заголовок ENIP с командами сессии (ListIdentity, RegisterSession, SendRRData).
- **CIP** — собственно запрос: service + class + instance + attribute.

```text
$ grep -m2 'ENIP' enip.log
ENIP: cmd=ListIdentity -> reply vendor=Rockwell device=1756-L83E
ENIP: cmd=RegisterSession session=0x01020304
```

Порт по умолчанию — **44818/TCP** (явные сообщения) и **2222/UDP** (неявные/IO).

## Шаг 2: объектная модель CIP

CIP описывает устройство как набор **объектов** (class), у каждого — **instances** и **attributes**. Ключевые классы:

- **Identity (0x01)** — информация об устройстве.
- **Message Router (0x02)** — маршрутизация.
- **Assembly (0x04)** — сборки данных IO.
- **Symbol (0x6B)** — доступ к тегам ПЛК.

```text
$ grep -n 'class=' enip.log | head -3
CIP: service=0x0E (Get_Attribute_Single) class=0x01 inst=1 attr=1
CIP: service=0x52 (Unconnected_Send) path=Tag/Setpoint
```

## Шаг 3: чтение тегов

Теги ПЛК (`Setpoint`, `Run`, `Valve_1`) читаются и пишутся CIP-сервисами. Сервис `0x4C` (Read Tag) и `0x4D` (Write Tag) работают с Symbol object.

```text
$ grep -n 'Read Tag\|Write Tag' enip.log
CIP: Read Tag Setpoint = 70.0
CIP: Write Tag Setpoint = 100.0
```

Если Write Tag доступен анонимно, вы управляете процессом.

## Шаг 4: явный и неявный обмен

- **Explicit messaging** (TCP 44818) — запрос/ответ: чтение тегов, диагностика.
- **Implicit messaging** (UDP 2222) — циклический IO-обмен в реальном времени, часто без аутентификации и с фиксированными сборками.

Неявный обмен сложнее подделать (нужны тайминги и сборки), но и там бывают инъекции.

## Шаг 5: атаки

1. **Анонимное чтение** — вытянуть всю логику и теги.
2. **Запись тегов** — изменить уставки, запустить/остановить.
3. **Stop CPU** — некоторые контроллеры имеют сервис остановки (CIP Security).
4. **Спуфинг IO** — подменить неявные данные.
5. **Выгрузка проекта** — скачать проект ПЛК через CIP.

Инструменты: `cpppo`, `enip`, Scapy, Wireshark-профиль ENIP, `nmap --script enip-info`.

## ENIP и CIP: два уровня

**EtherNet/IP (ENIP)** — транспортный слой поверх TCP/UDP: сессии, `List Identity`, `Register Session`, явные сообщения по TCP-порту 44818 и неявные (I/O) по UDP-порту 2222. **CIP** — прикладной слой: объектная модель, сервисы, теги. Пакет ENIP инкапсулирует CIP-запрос.

```text
ENIP header: command | length | session | status | sender_context | options
  command 0x0063 = ListIdentity (discovery)
  command 0x006F = SendRRData (unconnected explicit)
CIP: service (0x4C ReadTag) | path (class/instance/attr) | data
```

Понимание этой двухуровневости — основа анализа: фильтруй по `ListIdentity` для разведки и по `SendRRData` для обмена тегами.

## Чтение и запись тегов

Теги — именованные переменные ПЛК (`Motor1.Speed`, `Tank_Level`). Их читают сервисом `Read Tag` (0x4C) и пишут `Write Tag` (0x4D). Инструменты: `cpppo` (Python), `pycomm3`, `enip-cli`. Пример чтения через `pycomm3`:

```python
from pycomm3 import LogixDriver
with LogixDriver("192.168.1.10") as plc:
    print(plc.read("Tank_Level"))
    # plc.write("Motor1.Speed", 0)   # только в тестовой среде!
```

Запись тега меняет поведение оборудования. Для разведки достаточно `List Identity` и `Read Tag`: они дают модель процесса, версии, имена тегов — основу для отчёта.

## Атаки на CIP/EtherNet-IP

Первое — **неаутентифицированный доступ**: по умолчанию CIP не требует аутентификации, и любой в сети может читать и писать теги. Второе — **изменение уставок** (перевод оборудования в опасный режим). Третье — **fault injection** через `Write Tag` в управляющие переменные. Четвёртое — **DoS**: повторный `Register Session` или завершение сессий других.

Защита: сегментация (ПЛК в изолированном сегменте), firewall с правилами на CIP-сервисы, включение режима `run/program` с защитой ключом, мониторинг записей в управляющие теги. Инструмент аудита — `nmap --script enip-info` для инвентаризации.

## Разбор обмена CIP в дампе

Чтобы уверенно работать с EtherNet/IP, разберём обмен вручную. Открой захват в Wireshark с фильтром `enip` (или `cip`). Первое, что видно, — `List Identity` (команда 0x0063) по UDP 2222: это discovery-запрос, на который ПЛК отвечает своим именем, версией и типом. По этим ответам строится инвентарь без единого логина.

Дальше идёт установка сессии: `Register Session` (0x0065) по TCP 44818. Обрати внимание — она не требует аутентификации. После регистрации начинается обмен `SendRRData` (0x006F) с вложенными CIP-запросами. Внутри CIP видно сервис: `0x4C` (Read Tag), `0x4D` (Write Tag), `0x52` (unconnected send). Путь (`path`) указывает, к какому объекту/тегу обращаются.

Из дампа ты восстанавливаешь: какие теги читаются, с какой периодичностью, какие значения. Это даёт карту процесса и понимание, какие теги управляющие. `tshark -Y cip.service==0x4D` покажет все записи — если они есть, значит кто-то уже пишет, и точки уязвимы.

## Инструменты для практической работы

Для чтения и записи тегов удобны библиотеки. `pycomm3` — простой интерфейс к Logix-контроллерам; `cpppo` — более низкоуровневый, работает с любым CIP-устройством; `enip` и `scapy` — для ручного конструирования пакетов. Сканер `nmap --script enip-info` даёт быструю инвентаризацию.

```bash
nmap -p 44818 --script enip-info 192.168.20.0/24
python3 -c "from cpppo.server.enip.get_attribute import proxy_simple as p; print(p(['@1/1/1']))"  # чтение объекта
```

Отдельно проверяй UDP-порт 2222 (implicit I/O) — по нему идёт реальное управление в реальном времени. Перехватив его, ты видишь не «чтение тега», а сам поток управления оборудованием, включая команды пуска/останова. Для DoS достаточно залить этот порт мусором — но это опасно для производства, поэтому только в тестовой сети.

## Поверхность атаки и защита

EtherNet/IP спроектирован для доверенной сети, поэтому аутентификации в базовом протоколе нет. Поверхность: анонимное чтение (разведка), анонимная запись (изменение процесса), `Register Session` flooding (DoS), неверный путь (crash парсера). Отдельно — **CIP Security** (существует, но редко включён), который добавляет TLS и аутентификацию.

Защита: сегментация сети ПЛК (отдельный VLAN, firewall только для нужных сервисов), включение ключа в режиме run/program, аудит записей в управляющие теги, мониторинг неожиданных `List Identity` (признак сканирования). Для пентеста — инвентаризация и чтение; запись только на стенде, потому что CIP-запись в управляющий тег может остановить производство или повредить оборудование.

## От инвентаризации к оценке импакта

После инвентаризации EtherNet/IP-сети нужно оценить импакт. Начни с классификации устройств: контроллеры (Logix, SLC), remote I/O, drives, HMI. По `List Identity` ты видишь тип и версию каждого — это определяет, какие теги и сервисы доступны.

Дальше — определить, какие теги управляющие. Обычно это теги с именами вида `*_Cmd`, `*_Start`, `*_Setpoint`, `*_Enable`. Их запись меняет процесс. Читая дамп, ты видишь, какие теги реально пишет HMI или SCADA — это и есть управляющие точки.

Третий шаг — оценить защиту. Проверь, включён ли ключ в режиме `RUN` (запрещает изменение программы), требует ли запись аутентификации (обычно нет), включён ли CIP Security. Часто ответ «нет» на все три — тогда запись доступна анонимно.

```bash
nmap -p 44818 --script enip-info 192.168.20.0/24
tshark -r plc.pcap -Y "cip.service==0x4d" -T fields -e ip.src -e cip.symbol | sort -u
```

Импакт формулируй по последствиям: чтение — утечка процесса; запись — изменение производства; DoS — остановка. Не преувеличивай: «возможна запись» — это не «производство остановлено».

## Итог по CIP/EtherNet-IP

EtherNet/IP не имеет аутентификации в базовом виде: `List Identity` для разведки, `Register Session` без пароля, `Read Tag`/`Write Tag` для доступа к процессу. Безопасный аудит — инвентаризация и чтение; запись опасна для производства. Защита — сегментация, ключ run/program, CIP Security, аудит записей. Помни про UDP 2222 — это реальное управление в реальном времени, а не диагностика.

## Быстрый чек-лист EtherNet/IP

Порядок: `nmap --script enip-info` → `List Identity` (инвентарь) → `Register Session` → `Read Tag` (карта тегов) → поиск управляющих тегов. Инструменты: `cpppo`, `pycomm3`, Wireshark (`enip`). Ключевая находка — анонимная запись в управляющий тег. UDP 2222 — реальное управление, не диагностика.

## Резюме и рекомендации

EtherNet/IP — протокол доверенной сети: аутентификации в базовом виде нет, `List Identity` и `Register Session` работают анонимно, а `Read Tag`/`Write Tag` дают доступ к тегам процесса. Практический вывод: инвентаризация и чтение тегов безопасны и дают полную картину, а запись в управляющий тег — это изменение производства, которое может остановить линию или повредить оборудование. UDP-порт 2222 несёт реальное управление в реальном времени, поэтому его нельзя трогать вне стенда.

Рекомендации: сегментировать сеть ПЛК в отдельный VLAN с firewall, разрешающим только необходимые сервисы; включить ключ контроллера в режим `RUN`; внедрить CIP Security (TLS и аутентификация) там, где поддерживается; включить аудит записей в управляющие теги; мониторить неожиданные `List Identity` как признак сканирования. В отчёте разделяй «возможна запись» и «запись выполнена»: первое — находка, второе — инцидент.

## Что мы теперь знаем

- EtherNet-IP = ENIP-обёртка + CIP-объекты.
- Порты: 44818/TCP (явный), 2222/UDP (неявный IO).
- CIP: service + class + instance + attribute; теги через Symbol object.
- Чтение/запись тегов и остановка CPU — ключевые сервисы для атаки.
- По умолчанию аутентификации нет (CIP Security — редкое исключение).
