## Вопрос, с которого всё начинается

В прошлых уроках мы научились **говорить** с контроллерами: читать теги, слать команды. Но это ещё не значит, что мы понимаем, что контроллер делает. ПЛК — это маленький компьютер, который циклически исполняет программу и управляет железом: клапанами, насосами, приводами.

Вопрос урока: как понять логику ПЛК и что произойдёт, если её изменить? Это самый опасный класс действий в OT — здесь ошибка ведёт не к утечке данных, а к аварии.

## Наш пример: Siemens S7 на линии розлива

Перед нами ПЛК Siemens S7-315 на адресе `10.0.0.20`, управляющий линией розлива. Мы уже умеем находить устройства. Начнём с идентификации — узнаем, что это за контроллер:

```bash
$ nmap -p 102 --script s7-info 10.0.0.20
PORT    STATE SERVICE
102/tcp open  iso-tsap
| s7-info:
|   Module: 6ES7 315-2AG10-0AB0
|   Version: 2.6.11
|   System Name: PLC_LINE1
|_  Module Type: CPU 315-2 DP
```

Мы получили модель (`CPU 315-2 DP`), версию прошивки (`2.6.11`) и системное имя (`PLC_LINE1`). Версия — вход для поиска известных уязвимостей этой модели.

## Шаг 1: как ПЛК вообще работает

Контроллер исполняет программу бесконечным циклом — **scan cycle**:

1. **Чтение входов** (Input Image) — снимок состояния датчиков.
2. **Исполнение логики** — программа (ladder, FBD, SCL).
3. **Обновление выходов** (Output Image) — запись на приводы.
4. **Обслуживание связи** — ответы SCADA, обработка команд.

Длительность цикла — от миллисекунд до сотен миллисекунд. Детерминизм критичен: если цикл нарушить, контроллер уйдёт в ошибку или аварийный останов. Всё, что мы будем делать, влияет именно на этот цикл.

## Шаг 2: лестничная логика

Основной язык ПЛК — **лестничная диаграмма** (ladder). Она рисуется как реле-схема: контакты (`-| |-` нормально разомкнутый, `-|/|-` нормально замкнутый) и катушки (`-( )-`). Классический пуск/стоп насоса:

```text
  Start   Stop     Motor
---| |----|/|------( )---
    I0.0   I0.1    Q0.0
```

Читается так: при нажатии `Start` (вход `I0.0`) и отпущенном `Stop` (вход `I0.1`) включается катушка `Motor` (`Q0.0`), которая самоблокируется. Изменение одного контакта меняет поведение всей установки — поэтому логика и есть главная цель.

## Шаг 3: читаем и пишем память Siemens

Память ПЛК организована в **DB** (Data Block) — блоки данных. Обращаться к ним из Python удобно через `snap7` (соединение задаётся парой `rack`/`slot` — физическое положение CPU в стойке):

```python
import snap7
from snap7.util import *
plc = snap7.client.Client()
plc.connect('10.0.0.20', 0, 1)          # rack=0, slot=1
print(plc.get_cpu_state())
data = plc.read_area(snap7.types.Areas.DB, 1, 0, 2)  # DB1, offset 0, 2 байта
print(get_int(data, 0))
```

Вывод:

```text
S7CpuStatusRun
2345
```

`S7CpuStatusRun` означает, что программа исполняется. `2345` — значение из DB1. Запись делается так же, но **это уже вмешательство в процесс**:

```python
plc.write_area(snap7.types.Areas.DB, 1, 0, set_int(1234))
```

## Шаг 4: выгружаем программу — разведка процесса

Выгрузив блоки, можно понять процессную логику: уставки, блокировки, аварийные пороги. Перечислим, что вообще есть в контроллере:

```python
import snap7
c = snap7.client.Client(); c.connect('10.0.0.20', 0, 1)
print(c.get_cpu_info().ModuleTypeName)
print(c.list_blocks())
```

```text
CPU 315-2 DP
['OB1', 'OB100', 'DB1', 'FB1', 'FC1']
```

`OB1` — главный цикл, `OB100` — блок старта, `FB`/`FC` — функции. По названиям часто угадывается назначение (например, `FB_Pump_Control`). Это чистая разведка: мы ещё ничего не изменили.

## Шаг 5: режимы RUN / STOP

У ПЛК есть режимы: **RUN** (исполняет программу), **STOP** (остановлен), **PROGRAM** (редактирование). Переключить их из сети можно двумя вызовами:

```python
c.stop()     # перевести в STOP
c.start()    # вернуть в RUN
```

Перевод в STOP останавливает линию. Это **DoS уровня процесса**, а не сети: сеть работает, а завод встал.

## Шаг 6: защита паролем — есть или нет

Современные ПЛК умеют защищаться: у Siemens — защита блоков (read/write protection) и «know-how protection» (код можно читать, но не выгружать), у Rockwell — Security Authority и подпись проекта. Проверка простая — попробовать прочитать без пароля:

```python
try:
    c.read_area(snap7.types.Areas.DB, 1, 0, 2)
    print("NO PROTECTION: read allowed")
except Exception as e:
    print("Protected:", e)
```

Если чтение прошло — защиты нет. В нашем примере прошло.

## Шаг 7: опасные действия

Некоторые операции особенно разрушительны, потому что обходят логику:

- **Force** — принудительно задать вход/выход, игнорируя реальные сигналы датчиков.
- **Запись в output image** напрямую — включить привод в обход программы.
- **Сброс уставок аварий** — отключить защиты.
- **Маскирование алармов** — оператор не увидит проблему.

Пример (в лаборатории!) — включить выход в обход логики через `pycomm3`:

```python
from pycomm3 import LogixDriver
with LogixDriver('10.0.0.30') as plc:
    plc.write('Local:1:O.Data[0]', 1)
```

Ещё глубже — **PLCinject**: он внедряет код в лестничную логику работающего Allen-Bradley через ENIP, маскируя его под легитимные rungs. То есть и сама логика может быть скомпрометирована без доступа к инженерной станции.

## Шаг 8: safety-логика — красная линия

Современные ПЛК делят программу на **стандартную** и **safety** (функциональная безопасность, SIL). Safety-логика реализует аварийные остановы и защиту людей; часто она исполняется на отдельном CPU (Siemens F-CPU).

Для нас это значит:

- Запись в standard-логику не отключает safety — «защита держит».
- Safety-параметры могут быть доступны через сеть, если не защищены.
- Компрометация инженерной станции с правами на safety — крайне опасна.
- **Никогда не трогайте safety-логику «для проверки».**

## Шаг 9: обнаружить вмешательство

Ключевая техника OT-форензики — сравнить проект до и после инцидента. Выгружаем программу, нормализуем (убираем таймстемпы) и сравниваем:

```bash
$ diff -u baseline_ladder.txt current_ladder.txt
```

Изменённые rungs указывают на инъекцию логики или на легитимную правку. Это самый надёжный способ найти скрытое вмешательство.

## Что мы теперь знаем

1. ПЛК исполняет программу циклически (scan cycle); вмешательство нарушает детерминизм.
2. Логика описывается лестничной диаграммой; один контакт меняет поведение установки.
3. `snap7` читает и пишет DB-блоки; `get_cpu_state` показывает RUN/STOP.
4. `stop()`/`start()` — DoS уровня процесса; `Force` и прямая запись выхода обходят логику.
5. Safety-логика — отдельный слой; её трогать нельзя.
6. Изменения находят сравнением выгруженных проектов (project diff).

## На что смотреть дальше

- **Нет подключения к Siemens.** Проверьте `rack`/`slot`: неверные значения = нет связи.
- **Мусор вместо значения.** Ошибка в offset на 1 байт; S7 — big-endian, многие инструменты ждут little-endian.
- **Блок читается, но не выгружается.** Это know-how protection: код защищён, но данные видны.
- **Force «застрял».** Забытый Force-бит может жить до перезагрузки контроллера.
- **Конфликт с инженерной станцией.** Мультимастер: ваш скрипт и SCADA дерутся за соединение.
