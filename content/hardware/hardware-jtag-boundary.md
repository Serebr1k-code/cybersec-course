**Boundary scan** — это часть стандарта **IEEE 1149.1 (JTAG)**, которая не имеет отношения к отладке ядра. Каждый вывод чипа, поддерживающего boundary scan, окружён ячейкой сдвигового регистра (boundary-scan cell), и через цепочку JTAG можно принудительно задать или прочитать логический уровень на этих выводах. Это позволяет «прощупать» плату: проверить пайку, найти обрывы, определить, куда идёт дорожка, и прочитать состояние пинов, даже если процессорное ядро отключено, прошивка стёрта или чип не запускается. Для реверса и hardware-пентеста boundary scan — инструмент второго эшелона, который выручает, когда обычный JTAG-отладчик бессилен.

В этом уроке: архитектура цепочки JTAG, TAP-контроллер, IDCODE, инструкции boundary scan, BSDL-файлы, инструменты (UrJTAG, OpenOCD) и практические примеры чтения выводов.

## TAP-контроллер и цепочка JTAG

JTAG управляется **TAP (Test Access Port)** — конечным автоматом с четырьмя (или пятью) сигналами:

| Сигнал | Назначение |
|--------|------------|
| TCK | такт |
| TMS | выбор режима (управляет автоматом) |
| TDI | вход данных |
| TDO | выход данных |
| TRST | сброс TAP (опционально) |

Внутри TAP — 16 состояний (Test-Logic-Reset, Run-Test/Idle, Shift-DR, Shift-IR, Capture-DR, Update-DR и др.). Данные сдвигаются через **IR (Instruction Register)** — командный регистр, и **DR (Data Register)** — регистр данных. По цепочке соединены несколько чипов: TDO одного идёт в TDI следующего, образуя **daisy-chain**. Именно поэтому JTAG-сканер должен знать длину цепочки и позиции каждого чипа.

Ключевая идея boundary scan: между «ядром» и физическим выводом чипа стоит ячейка, которую можно перехватить. Инструкция **SAMPLE/PRELOAD** захватывает состояние выводов, **EXTEST** управляет выводами, **INTEST** работает с внутренними цепями.

## IDCODE и идентификация

При сбросе TAP каждый чип выдаёт **IDCODE** (32-бит): версия, part number, производитель (JEDEC-код), контроль. IDCODE — первый шаг: по нему определяют модель чипа и, что важнее, его **BSDL**-файл.

Формат IDCODE (IEEE 1149.1):

| Биты | Поле |
|------|------|
| 31:28 | версия |
| 27:12 | part number |
| 11:1 | JEDEC-код производителя |
| 0 | всегда 1 |

Инструкция **IDCODE** (опкод `0x01`) или **BYPASS** (все нули/единицы) позволяют перечислить цепочку. Для чтения IDCODE служат `BYPASS`-цепочки: сканируя длину и данные, находят границы чипов.

## BSDL-файлы

**BSDL (Boundary Scan Description Language)** — это файл на подмножестве VHDL, описывающий boundary-scan-структуру конкретного чипа:

- `entity` и `generic` — параметры (например, `PHYSICAL_PIN_MAP`).
- `port` — выводы и их направление (in/out/bidir).
- `attribute BOUNDARY_LENGTH` — число ячеек.
- `attribute BOUNDARY_REGISTER` — карта ячеек: номер, тип (BC_1, BC_0, BC_4, ...), управляющий бит, disable-значение.
- `attribute INSTRUCTION_OPCODE` — опкоды инструкций (SAMPLE, EXTEST, IDCODE, …).
- `attribute INSTRUCTION_CAPTURE` — паттерн захвата IR.

Без BSDL вы не знаете, какая ячейка соответствует какому выводу. Файлы BSDL открыто лежат на сайтах вендоров (Xilinx, Intel/Altera, TI, NXP, Lattice) и в базах вроде `bsdl.info`.

## Инструменты: UrJTAG, OpenOCD

**UrJTAG** — классический инструмент для boundary scan и JTAG в целом:

```bash
# --- запуск интерактивной оболочки ---
urjtag
# > cable usbblaster        (выбор адаптера)
# > detect                  (обнаружение цепочки)
# > part 0                  (выбор чипа)
# > idcode
# > bsdl path /usr/share/urjtag/bsdl/
# > instruction SAMPLE
# > shift ir
# > shift dr
# > print signal            (состояние выводов)

# --- с собственным адаптером FTDI ---
urjtag
# > cable ft2232 pid=0x6010
# > frequency 1000000
# > detect
```

**OpenOCD** тоже умеет boundary scan через команды `svf`/`bsdl`:

```bash
openocd -f interface/ftdi/olimex-arm-usb-tiny-h.cfg -f target/xilinx_xc9500xl.cfg
# в telnet:
# > svf device 0 xc2c64a.bsd
# > scan_chain
# > svf_progress
```

Другие инструменты: **JTAGenum** (Arduino-скетч для определения JTAG-пинов), **TopJTAG Probe**, **Flyswatter**.

## Разобранный пример: чтение состояния выводов

Дано: плата с CPLD Xilinx XC9500XL, есть JTAG-разъём, но ядро не даёт отладки. Хотим понять, куда подключён конкретный сигнал.

**Шаг 1 — подключение и обнаружение.**

```bash
urjtag
# > cable usbblaster
# > detect
# OUTPUT:
# IR length: 8
# Chain length: 1
# Device Id: 00001001011000000000000000000001 (0x09600001)
#   Manufacturer: Xilinx
#   Part(0):      XC95144XL
#   Stepping:     0
```

**Шаг 2 — загрузка BSDL.**

```bash
# > bsdl path ./bsdl/
# > part 0
# > print              (список сигналов из BSDL)
```

**Шаг 3 — SAMPLE.** Захватываем текущее состояние:

```bash
# > instruction SAMPLE
# > shift ir
# > shift dr
# > print signal
# OUTPUT:
#   SIGNAL1 = 0
#   SIGNAL2 = 1
#   ...
```

**Шаг 4 — EXTEST.** Управляем выводами (осторожно: можно конфликтовать с другими драйверами):

```bash
# > instruction EXTEST
# > shift ir
# > set signal SIGNAL1 1
# > shift dr
# > print signal
```

**Шаг 5 — вывод.** Мы видим логические уровни на выводах. Комбинируя SAMPLE с внешним воздействием (замыкание/подача), можно определить, какие выводы соединены — это и есть boundary-scan-прозвонка.

## Определение неизвестной JTAG-распиновки

Часто на плате нет подписанного разъёма. Методы:

- **JTAGenum** (Arduino) — перебирает пины и ищет TAP по IDCODE.
- **Проба вслепую** — подать TCK/TMS и смотреть, появится ли отклик на TDO.
- **Замер мультиметром** — TDI/TDO/TMS обычно подтянуты, TCK может звониться на землю.
- **Поиск по дорожкам** — от чипа к площадкам.
- **Даташит платы** — если известна модель.

## Edge cases и подводные камни

- **Несколько чипов в цепочке.** Нужно знать IR-длины и порядок; иначе данные сдвинутся. `detect` в UrJTAG помогает, но иногда требуется ручной `register`.
- **BSDL не совпадает с чипом.** Даже близкие модели могут отличаться числом ячеек — берите точный файл.
- **EXTEST может конфликтовать.** Если вывод уже драйвится другим чипом, возникнет короткое замыкание/конфликт уровней. Начинайте с SAMPLE.
- **Не все чипы имеют boundary scan.** Микроконтроллеры без BSDL не «прощупать» этим методом.
- **TAP может быть отключён fuse-битом.** Тогда цепочка не отвечает.
- **Уровни напряжения.** JTAG на 1.8/2.5/3.3 В — не подавайте 5 В.
- **Цепочка может требовать TRST.** Иногда без сброса TAP состояние нестабильно.

## Справочные таблицы

Основные инструкции JTAG:

| Инструкция | Назначение |
|------------|------------|
| BYPASS | пропуск чипа (1-битный регистр) |
| IDCODE | чтение идентификатора |
| SAMPLE/PRELOAD | захват состояния выводов |
| EXTEST | управление внешними выводами |
| INTEST | тест внутренних цепей |
| CLAMP | фиксация выводов |
| HIGHZ | перевод выводов в Z |

Типы boundary-scan-ячеек (BSDL):

| Тип | Поведение |
|-----|-----------|
| BC_1 | управляемая ячейка (in/out) |
| BC_0 | ячейка без управления |
| BC_2 | выход с 2 состояниями |
| BC_4 | ячейка с захватом |
| BC_7 | двунаправленная |

## Что дальше / решение

Практический маршрут: (1) найдите JTAG-разъём и определите распиновку (JTAGenum/даташит); (2) считайте IDCODE и определите чипы; (3) скачайте точные BSDL-файлы; (4) выполните SAMPLE для чтения состояния выводов; (5) при необходимости — EXTEST для прозвонки. Boundary scan не заменит обычную отладку, но когда ядро недоступно, он даёт уникальное окно в плату. Для защиты: не оставляйте JTAG-разъём на серийных изделиях, блокируйте TAP fuse-битом, ограничивайте доступ к цепочке.

## Практика: определение JTAG-пинов вслепую

Когда на плате нет подписанного разъёма, распиновку JTAG восстанавливают методичным перебором. Простейший инструмент — **JTAGenum** на Arduino: он перебирает пары пинов, ищет TAP по IDCODE и сообщает найденные TDI/TDO/TCK/TMS. Альтернатива — Bus Pirate или программатор с ручным управлением сигналами. Перед перебором полезно сузить круг: TDI/TDO/TMS обычно имеют подтяжку к питанию, TCK часто звонится на землю через резистор, а VCC и GND определяются мультиметром однозначно.

После обнаружения цепочки считываем IDCODE и определяем IR-длину. Если чипов несколько, `detect` покажет порядок и длины, а при неудаче длину IR подбирают вручную, наблюдая, при каком значении сдвига данные стабилизируются. Затем загружаем точные BSDL-файлы и выполняем SAMPLE для чтения состояния выводов. Для проверки дорожек удобно чередовать SAMPLE и внешнее воздействие (кратковременная подача уровня), наблюдая, какой бит меняется, — так восстанавливается соответствие «ячейка → вывод → дорожка».

## Boundary scan в производстве и безопасности

Boundary scan изначально создавался для тестирования пайки на производстве: EXTEST подаёт тестовые паттерны на выводы и проверяет целостность дорожек, INTEST тестирует внутренние цепи. В безопасности эта же функция — мощный инструмент реверса: через неё можно «прощупать» плату, не имея прошивки и не запуская ядро. Для защиты производители применяют fuse-биты, отключающие TAP, и убирают отладочные разъёмы с серийных изделий. Пентестер должен учитывать, что boundary scan не даёт доступа к памяти сам по себе — только к выводам, поэтому его комбинируют с другими методами (chip-off, glitch, чтение по SPI). Комбинирование методов — общий принцип hardware-пентеста: когда один интерфейс закрыт, ищем другой путь к тем же данным.
