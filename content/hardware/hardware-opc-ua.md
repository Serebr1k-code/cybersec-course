## Вопрос, с которого всё начинается

OPC UA задуман как безопасный промышленный протокол: шифрование, подписи, сертификаты. Но в реальных АСУ ТП он часто настроен так, что «безопасность» остаётся на бумаге.

Вопрос урока: как устроена защита OPC UA и где она ломается конфигурацией.

## Наш пример: OPC UA-сервер

У нас есть дамп сессии с OPC UA-сервером. Видны эндпоинты, согласование политики безопасности и чтение узла. Разберём, какая политика была выбрана и что это значит.

## Шаг 1: адресное пространство и узлы

OPC UA представляет данные как **узлы** (nodes) в адресном пространстве: переменные, объекты, методы. У каждого узла есть **NodeId** (идентификатор) и атрибуты, главный — **Value**.

```text
$ grep -m2 'NodeId' opcua.log
Read ns=2;s=Machine.Temperature -> 72.4
Read ns=2;s=Machine.Setpoint -> 70.0
```

Здесь `ns=2;s=Machine.Temperature` — строковый NodeId в пространстве имён 2. Чтение значения — базовый сервис.

## Шаг 2: эндпоинты и security policy

При подключении клиент запрашивает **GetEndpoints** — список доступных точек входа, у каждой своя **SecurityPolicy**. Политики бывают:

- **None** — без шифрования и подписи.
- **Basic128Rsa15 / Basic256 / Basic256Sha256** — разные уровни.
- **Aes128Sha256RsaOaep / Aes256Sha256RsaPss** — современные.

```text
$ grep -n 'SecurityPolicy' opcua.log
Endpoint: SecurityPolicy=None, SecurityMode=None
Endpoint: SecurityPolicy=Basic256Sha256, SecurityMode=SignAndEncrypt
```

Сервер отдаёт оба. Если клиент выберет **None**, сессия будет открытой.

## Шаг 3: анонимные сессии

Даже при хорошей политике сервер может разрешить **Anonymous** аутентификацию. Тогда любой подключается без учётных данных.

```text
$ grep -n 'UserToken' opcua.log
UserTokenPolicy: Anonymous
UserTokenPolicy: UserName
ActivateSession: anonymous=true -> OK
```

Частая ошибка: политика SignAndEncrypt, но токен Anonymous. Шифрование есть, но доступа лишён никто.

## Шаг 4: сертификаты

OPC UA использует X.509-сертификаты. Слабые места:

1. **Self-signed без проверки** — сервер принимает любой сертификат.
2. **Просроченные сертификаты** — приложение отключает проверку, чтобы «работало».
3. **Один сертификат на всех** — компрометация одного даёт доступ ко всем.
4. **Доверие всему хранилищу** — если в trust list попал лишний сертификат.

## Шаг 5: практический обход

Типичный сценарий пентеста:

1. `GetEndpoints` → найти эндпоинт с `None`.
2. Если его нет — проверить, разрешён ли Anonymous.
3. Если и это закрыто — посмотреть, принимает ли сервер произвольный сертификат (MITM).
4. Через разрешённую сессию — перечислить узлы и найти методы (методы могут выполнять действия на оборудовании).

```text
$ python3 -c "print('UAExpert / opcua-client: connect, browse, read, call method')"
UAExpert / opcua-client: connect, browse, read, call method
```

Инструменты: UaExpert, `opcua-client`, Prosys, `nmap --script opcua-info`.

## Адресное пространство и как по нему ходить

OPC UA моделирует всё как узлы (nodes) в адресном пространстве. Каждый узел имеет `NodeId` (например, `ns=2;s=Machine1.Temperature`), набор атрибутов (`Value`, `DataType`, `AccessLevel`) и ссылки на другие узлы (`Organizes`, `HasComponent`, `HasProperty`). Корень — `Root`, от него `Objects`, `Types`, `Views`. Практически разведка начинается с `Browse` от `Objects`: ты рекурсивно обходишь дерево и собираешь все переменные с их `NodeId`. Это даёт полную карту процесса — то же, что список тегов в CIP, но стандартизованное.

Инструменты: `opcua-client` (GUI, python-opcua), `UaExpert` (графический браузер), `opcua` (Python) для скриптов. Пример обхода на Python:

```python
from opcua import Client
c = Client("opc.tcp://192.168.1.20:4840")
c.connect()
for node in c.get_objects_node().get_children():
    print(node, node.get_browse_name())
```

Ключевой момент: `Browse` часто доступен анонимно даже когда запись требует аутентификации — поэтому разведка проходит почти всегда.

## Эндпоинты, SecurityPolicy и режимы

OPC UA-сервер публикует список **endpoints** через `GetEndpoints` (доступно анонимно). Каждый endpoint описывает `SecurityPolicy` (`None`, `Basic128Rsa15`, `Basic256Sha256`, `Aes128Sha256RsaOaep`, ...) и `SecurityMode` (`None`, `Sign`, `SignAndEncrypt`). Классическая ошибка конфигурации — сервер оставляет доступным endpoint с `SecurityPolicy: None` и `SecurityMode: None`, через который можно подключиться без шифрования и аутентификации, даже если остальные endpoints защищены.

```bash
# перечислить endpoints
python3 - <<PY
from opcua import Client
c = Client("opc.tcp://T:4840"); c.connect()
for e in c.get_endpoints():
    print(e.SecurityMode, e.SecurityPolicyUri, e.UserTokenPolicyIds)
PY
```

Проверяй оба: и наличие незащищённого endpoint, и `UserTokenPolicy` (Anonymous, UserName, Certificate). Часто анонимный токен разрешён вместе с None-политикой — это полный доступ.

## Сертификаты, анонимные сессии и обход

Безопасность OPC UA строится на X.509-сертификатах. Сервер доверяет сертификатам из своего trust-list; клиент — сертификату сервера. Слабые места: самоподписанные сертификаты без проверки (клиент принимает любой — MITM), доверие по цепочке без проверки CN/SAN, и сертификаты с длинным сроком/слабым ключом. Если сервер принимает анонимные сессии с `None`, вся криптография обходится.

Практический обход: подключиться к незащищённому endpoint, выполнить `Browse` для разведки, затем прочитать значения (`Read`) и, если разрешено, записать (`Write`). Запись `Value` в управляющую переменную меняет физическое состояние — это самое опасное действие, применяй только на стенде. Для защиты: убрать `None`-endpoint, требовать `SignAndEncrypt`, использовать доверенные CA и валидировать сертификаты строго.

## Практический сценарий аудита OPC UA

Сценарий начинается с `GetEndpoints` — анонимной операции, которая не требует аутентификации. Ты получаешь список endpoint-ов с их SecurityPolicy и SecurityMode. Дальше проверяешь, есть ли незащищённый (`None/None`) — если да, вся криптография обходится.

Второй шаг — подключиться к доступному endpoint (анонимно или с известными кредами) и выполнить `Browse` от корня `Objects`. Это даёт дерево переменных. Ты сохраняешь `NodeId` всех интересных узлов: управляющих, диагностических, конфигурационных. По именам (`BrowseName`, `DisplayName`) часто видно назначение.

Третий шаг — `Read` значений: ты видишь текущее состояние процесса. Четвёртый шаг — проверка `AccessLevel`/`UserAccessLevel` каждого узла: если у управляющего узла стоит `CurrentWrite`, он доступен для записи. Именно эти узлы — цель атаки. Пятый шаг — оценка импакта: запись в управляющий узел меняет физическое состояние. На этом этапе останавливаешься и фиксируешь находку без выполнения записи.

```python
# проверить права узла
n = c.get_node("ns=2;s=Machine1.SpeedSetpoint")
print(n.get_access_level())
```

Такой маршрут — чтение → анализ прав → оценка импакта — безопасен и даёт полный отчёт без риска для производства.

## Защита OPC UA и типовые ошибки

Защита: убрать endpoint с `SecurityPolicy: None`; требовать `Basic256Sha256` + `SignAndEncrypt`; настроить `UserTokenPolicy` так, чтобы анонимный доступ был только там, где он реально нужен; использовать доверенные сертификаты и строгую валидацию (проверять CN/SAN, срок, отзыв); включить аудит операций `Write` и `Call`.

Типовые ошибки аудитора: считать, что наличие защищённого endpoint означает безопасность (забывают про `None`); игнорировать `UserTokenPolicy`; не проверять сертификаты на слабые ключи (RSA-1024, MD5-подпись); путать `Read` (безопасно) и `Write`/`Call` (опасно). Ещё одна ошибка — не заметить, что OPC UA-сервер доступен из корпоративной сети: тогда компромисс офисного хоста открывает путь к промышленному оборудованию. В отчёте разделяй подтверждённое (анонимный `Browse`, чтение) и потенциальное (запись, если права позволяют).

## Оценка находок и приоритет

Классификация находок OPC UA по критичности. Низкая: анонимный `GetEndpoints` и `Browse` — раскрытие структуры, но не управление. Средняя: чтение значений технологических переменных — утечка процесса. Высокая: доступный для записи узел, которым можно управлять, — потенциальное физическое воздействие. Критическая: анонимная запись в узел жизнеобеспечения (безопасность, аварийная остановка).

В отчёте указывай `NodeId`, `BrowseName`, текущий `AccessLevel` и обоснование критичности. Отдельно отметь наличие `None`-endpoint как самостоятельную находку: даже без записи он означает отсутствие шифрования и аутентификации. Рекомендации — конкретные настройки (`SecurityPolicy`, `UserTokenPolicy`, сертификаты), а не общие слова.

## Быстрый чек-лист OPC UA

Порядок проверки: `GetEndpoints` (анонимно) → есть ли `None/None` → `Browse` дерева → `Read` значений → проверка `AccessLevel` управляющих узлов → оценка импакта. Инструменты: `opcua` (Python), `UaExpert`, `nmap --script opcua-info`. Ключевые находки: незащищённый endpoint, анонимный токен, узел с `CurrentWrite` среди управляющих. Активные действия (запись) — только на стенде.

## Что делать с находкой и как её защитить

После того как ты нашёл незащищённый endpoint или узел с правом записи, важно правильно оформить находку и дать конкретную рекомендацию. Формулировка должна включать: адрес и порт сервера, URI endpoint, SecurityPolicy и SecurityMode, список доступных анонимно узлов, и — если есть — узлы с `CurrentWrite`, которыми можно управлять. Импакт описывай по последствиям: анонимный `Browse` — раскрытие структуры процесса; чтение технологических переменных — утечка производственных данных; запись в управляющий узел — потенциальное изменение физического процесса, вплоть до аварийной остановки или повреждения оборудования.

Рекомендации должны быть настройками, а не лозунгами. Убери endpoint с `SecurityPolicy: None`; для остальных включи `Basic256Sha256` с `SignAndEncrypt`; настрой `UserTokenPolicy` так, чтобы анонимный доступ остался только там, где он осознанно нужен; введи строгую проверку сертификатов (CN/SAN, срок, отзыв); включи аудит операций `Write` и `Call`; сегментируй OPC UA-сервер от корпоративной сети. Отдельно отметь, доступен ли сервер из общей сети: если да, компромисс офисного хоста открывает путь к промышленному оборудованию, и это надо поднять в отчёте как связку рисков. Так находка превращается из «есть уязвимость» в понятный план устранения.

## Что мы теперь знаем

- OPC UA описывает данные как узлы с NodeId и атрибутами.
- Каждый эндпоинт имеет SecurityPolicy; политика None = открытая сессия.
- Anonymous-токен обнуляет смысл шифрования.
- Сертификаты часто не проверяются — возможен MITM.
- Методы-узлы могут управлять оборудованием.
